### Title
Unbounded recursion depth in address/asset definition evaluation causes stack overflow on deeply nested `and`/`or` conditions - (File: `definition.js`)

### Summary
`definition.js`'s recursive `evaluate()` function — used both in `validateDefinition()` and in `validateAuthentifiers()` — walks the definition tree of an address or asset spending condition recursively for every `and`, `or`, `r of set`, and `weighted and` node. Unlike the sibling recursive evaluators in `formula/validation.js` (explicit `depth > 100` check) and `aa_validation.js` (explicit `depth > MAX_DEPTH` check), the `definition.js` evaluator only bounds recursion indirectly via `complexity`/`count_ops` counters, not via an explicit call-stack depth guard. Since nesting depth scales with these counters and `async.eachSeries` executes synchronously when each array only has a single pending branch, a sufficiently deep chain of nested `and`/`or` nodes can drive native JS call-stack depth to the point of a stack overflow, mirroring the Suricata CVE-2025-64331 bug class where recursion/processing depth scaled directly with an attacker-controlled input size rather than being independently capped.

### Finding Description
`evaluate(arr, path, bInNegation, cb)` in `definition.js` recurses for `or`/`and` ( [1](#0-0) ), `r of set` ( [2](#0-1) ), and `weighted and` ( [3](#0-2) ) nodes. Each recursive call only increments `complexity`/`count_ops` and checks against `constants.MAX_COMPLEXITY`/`constants.MAX_OPS` ( [4](#0-3) ) — there is no explicit stack-depth counter comparable to the ones used elsewhere in the codebase for structurally similar recursive walks: `formula/validation.js`'s `evaluate` tracks `depth` and aborts at `depth > 100` ( [5](#0-4) ), and `aa_validation.js`'s `validate`/`validateFieldWrappedInCases` abort at `depth > MAX_DEPTH` ( [6](#0-5) [7](#0-6) ). Because `and`/`or` require only `args.length >= 2` ( [8](#0-7) ), a definition author can build a linear chain (e.g. `and(sig, and(sig, and(sig, ...)))`) whose recursion depth grows roughly linearly with `complexity`, without ever hitting a dedicated depth cap. This same `evaluate` logic is invoked twice per unit: once from `validateDefinition()` for structural validation and once more from `validateAuthentifiers()`'s own local `evaluate` for signature checking during normal unit processing ( [9](#0-8) ), so the deep recursive walk happens on every unit that references the address, not just once at definition time.

### Impact Explanation
If crafted deep enough to exceed V8's default call-stack limit before `MAX_COMPLEXITY`/`MAX_OPS` is reached, this causes the full node process to crash with an uncaught `RangeError: Maximum call stack size exceeded` while validating a normally-formed unit, address definition, or asset spending condition. This is reachable by any unpermissioned actor who can post a unit defining an address, an asset with issue/transfer conditions, or an AA-embedded nested address definition — i.e., a standard unit poster or asset issuer, no privileged access required. A crash triggered during consensus-relevant validation on every full node that processes the same unit results in a denial of service against the network's ability to validate and confirm new units.

### Likelihood Explanation
Likelihood depends on the exact numeric values of `constants.MAX_COMPLEXITY` and `constants.MAX_OPS` relative to the JS engine's effective stack depth for this call chain (each `evaluate` frame plus its `async.eachSeries` closures). I was not able to retrieve the exact values of `constants.MAX_COMPLEXITY`/`MAX_OPS` within available tool calls, so I cannot conclusively confirm the counters are large enough to reach the native stack limit before being rejected — this is the main uncertainty in this analog. However, the structural gap is clear: this is the only major recursive validator in the address/AA validation code path that lacks an explicit depth guard, which is a real code-quality/robustness gap regardless of whether the current constants happen to mask it today.

### Recommendation
Add an explicit recursion-depth counter to `evaluate()` in `definition.js` (both instances, in `validateDefinition` and `validateAuthentifiers`), analogous to the `depth`/`MAX_DEPTH` checks already used in `formula/validation.js` and `aa_validation.js`, and reject definitions/authentifier evaluations exceeding a conservative depth (e.g., 100) independent of the complexity/ops counters.

### Proof of Concept
Construct an address definition (or asset `issue_condition`/`transfer_condition`) as a deeply right-nested chain:
```
["and", [["sig", {...}], ["and", [["sig", {...}], ["and", [ ... N levels ... ]]]]]]
```
Repeat nesting N times such that `complexity`/`count_ops` stay under `constants.MAX_COMPLEXITY`/`MAX_OPS` but N is large enough to exhaust the JS call stack when `evaluate()` in `definition.js` recurses through `async.eachSeries` for each `and` level ( [1](#0-0) ). Post a unit defining this address (or an asset with this condition) and observe validation crash the node with a stack overflow instead of returning a graceful validation error, unlike the depth-guarded evaluators in `formula/validation.js` and `aa_validation.js`.
