### Title
Webhook signature is verified against an organization taken from the unverified payload, letting any GitHub App owner write commit statuses for commits belonging to other repositories/organizations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's webhook secret to verify the HMAC signature against by reading `repository_owner`/`organization.login` straight out of the *unverified* JSON body. Once verification passes, the full, attacker-controlled body is handed to handlers (e.g. `StatusHandler`) that act on repository/commit data taken from the same body without ever confirming that data belongs to the organization whose secret produced the signature. This breaks the binding "organization whose secret authenticated the signature" == "repository/commit actually written to".

### Finding Description
`verify_signature` computes the organization used for HMAC verification from fields inside the request body itself, before the body is authenticated: [1](#0-0) [2](#0-1) 

Because `repository_owner` is read from the same JSON blob whose signature is being checked, an attacker who legitimately owns *any* GitHub App/organization configured in Shipit (i.e. knows *a* valid `webhook_secret`) can craft an arbitrary payload, set `repository.owner.login` (or `organization.login`) to their own organization so verification succeeds against a secret they know, while other fields in the same payload (`repository.full_name`, `sha`, etc.) reference a completely different, victim repository/commit.

Once `verify_signature` passes, `create` dispatches the *raw* `params` (not re-scoped to the verified organization) to every registered handler for the event: [3](#0-2) 

The base `Handler` class derives the target repository from `payload.dig('repository', 'full_name')` — again from the unverified-against-org body — and several handlers (e.g. `StatusHandler`) don't even scope by repository at all: [4](#0-3) [5](#0-4) 

`StatusHandler#process` looks up `Commit` purely `by sha` across the entire `commits` table, with no repository/organization filter whatsoever, then writes a GitHub-status record onto it via `Commit#create_status_from_github!`. Since commit SHAs are public (git commit hashes are visible in any push/PR), an attacker who owns one legitimate, low-privilege GitHub App installation on Shipit can forge a `status` webhook, sign it with their own known secret (choosing `repository.owner.login` = their own org to pass `verify_signature`), and target `sha` of a commit belonging to a totally different, victim stack/repository.

### Impact Explanation
Commit statuses drive Shipit's CI-gating and merge-queue logic (`ci.require`, blocking statuses, deploy safety checks referenced in `README.md`/`CHANGELOG.md`). Being able to inject fabricated "success" statuses onto arbitrary commits — from an organization the attacker does not own or have any write access to — lets an unprivileged attacker with only one benign GitHub App installation on the Shipit instance bypass CI/status gating and enable/trigger an unauthorized deploy of another team's stack. This crosses the "unauthorized deploy" impact bar since status manipulation is a documented deploy-safety gate.

### Likelihood Explanation
Requires only that Shipit is configured with more than one GitHub organization/App (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications") and that the attacker controls at least one of those orgs/App installations (any tenant onboarded onto the shared Shipit instance). No repository write access, no session, no `ApiClient` token, and no knowledge of the victim organization's webhook secret are needed — only a legitimately obtained secret for *some* org configured on the instance, plus the target commit's SHA (public information). This is realistic in any multi-tenant Shipit deployment.

### Recommendation
After `verify_signature` succeeds, do not trust `repository`/`organization` fields from the payload to select records to mutate; instead, cross-check that the repository being resolved by the handler (`Repository.from_github_repo_name`, or `Commit#stack`) actually belongs to the same organization (`repository_owner`) that was used to authenticate the signature, and reject the webhook (422) on mismatch. Additionally, `StatusHandler` should scope its `Commit` lookup by the repository derived from the (now cross-checked) payload rather than searching by `sha` alone across the entire table.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `victim-org` (secret unknown to attacker) and `attacker-org` (attacker owns installation, knows its `webhook_secret`).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<sha of a commit belonging to victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using their own known `webhook_secret` for `attacker-org` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully (per `app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (per `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), finds the victim's commit purely by SHA (no org/repo scoping), and calls `create_status_from_github!`, injecting a forged "success" status onto a commit the attacker never had access to — potentially satisfying `ci.require`/blocking-status checks and unblocking a deploy on `victim-org/victim-repo`.
