### Title
Full atomic revert of an entire AA trigger chain on a single secondary-trigger bounce lets one malicious/broken recipient AA permanently freeze batched payouts and DoS the caller AA - (File: aa_composer.js)

### Summary
`handleTrigger()`'s secondary-trigger dispatch treats the whole tree of AA calls spawned by one primary trigger as a single all-or-nothing unit: if *any* secondary AA in the tree bounces, the primary trigger's entire state/balance changes — including those of unrelated, already-successfully-executed sibling secondary AAs — are rolled back via a savepoint rollback. This mirrors the Knox report's pattern where one failing sub-call (Premia's `withdraw`) inside a batched operation (fee collection) reverts the whole transaction and blocks unrelated withdrawals/epoch progress, except here the failure-prone "external call" is simply paying an arbitrary address that happens to be an AA.

### Finding Description
When a primary AA trigger sends a payment whose output addresses include other AA addresses, `handleSecondaryTriggers()` invokes each of those AAs as secondary triggers in series [1](#0-0) . If any secondary trigger bounces, the error propagates back up through `async.eachSeries`; since the caller here is the *primary* trigger (`!bSecondary`), it calls `revert()` rather than merely `bounce()` [2](#0-1) .

`revert()` performs a hard rollback of **all** state accumulated by the entire trigger tree — not just the failing branch — by clearing the write batch and rolling back to the `initial_balances` savepoint, then discards all previously-collected responses: [3](#0-2) . This means any secondary AA that already executed successfully and moved funds within the same primary trigger has its effects erased too, purely because a sibling AA bounced.

The set of addresses that get secondary-triggered is derived directly from payment message outputs sent by the (primary or secondary) AA [4](#0-3) , so any address controllable/definable as an AA by an attacker can be inserted into that set simply by being a recipient of a payout.

### Impact Explanation
An AA that batches payouts to multiple recipients in one trigger response (e.g., a vault/reward-pool AA that iterates a pending-withdrawal queue held in state vars and pays several users in one message set) is exposed to a griefing/DoS vector: if even one recipient in the batch is (or later becomes) an AA whose definition/logic causes it to bounce on receipt, the entire batch — including all the other, legitimate withdrawals bundled with it — is reverted. Because state-var updates (e.g., marking a withdrawal as processed, or advancing an epoch/queue pointer) are also part of the same trigger's state changes, they get rolled back along with the payments. If the queue/pointer isn't advanced, every subsequent trigger re-attempts the identical batch, hits the same bad address, and reverts again — indefinitely freezing funds for all other unrelated participants and permanently blocking that AA's core operation (the exact "AA fund loss/freezing" analog to the vault epoch-initialization block in the report).

### Likelihood Explanation
Any address is freely definable as an AA in Obyte, so an attacker can register a recipient AA that deterministically bounces (e.g., zero balance for a required asset, a `bounce` condition in oscript, or intentionally malformed response). Any application AA that pays out to multiple, user-influenced addresses within a single trigger (batch withdrawal/dividend/vault-style contracts) is reachable by any user who can get their address included as a payout recipient — a common pattern for shared pools/vaults.

### Recommendation
Do not let a single secondary AA's bounce roll back unrelated sibling secondary AAs' already-committed effects within the same primary trigger. Options: (a) isolate each top-level secondary AA invocation in its own savepoint so a bounce only reverts that AA's own sub-tree, not siblings that already succeeded; and/or (b) document this atomicity semantic prominently for AA authors so batch-processing AAs are written to process one recipient per trigger (queue-and-drain pattern) instead of relying on all recipients in a single message succeeding together.

### Proof of Concept
1. Deploy AA `Vault` that maintains a `stateVar` queue of pending withdrawals and, on each keeper-triggered call, sends a `payment` message with outputs to N different addresses (draining the queue) in one trigger response, updating `stateVars` to mark them processed as part of the same execution.
2. Have an address `X` request a withdrawal, so it is included as an output in `Vault`'s next batched payment; `X` is defined as an AA whose oscript conditions cause it to bounce upon receiving that payment (e.g., asset balance check failure, per `sendDummyUnit`'s negative-balance handling at [5](#0-4) , or any bounce path in its own definition).
3. When `Vault`'s trigger fires, `handleSecondaryTriggers` calls `X` as a secondary trigger; `X` bounces, and because `Vault`'s own trigger is primary, `revert()` rolls back the entire batch [6](#0-5) , undoing the state-var updates that would have marked withdrawals as processed and the payments to all other legitimate recipients in the same batch.
4. On the next keeper-triggered call, the same queue (including `X`) is retried and bounces again, repeating indefinitely and freezing all other queued withdrawals.
