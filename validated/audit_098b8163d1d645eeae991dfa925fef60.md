### Title
Unbounded consumption of unspent outputs when an AA composes a payment response allows dust-flooding to inflate unit size beyond consensus limits - (File: aa_composer.js)

### Summary
`sendUnit()`'s `completePaymentPayload()` in `aa_composer.js` accumulates AA-owned outputs via `readStableOutputs()`/`readUnstableOutputsSentByAAs()` and `iterateUnspentOutputs()` with no upper bound on how many outputs it will consume, unlike the analogous wallet coin-selection code in `inputs.js` (`pickDivisibleCoinsForAmount`), which explicitly caps queries at `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2`. [1](#0-0) [2](#0-1) 

### Finding Description
When an AA composes its response payment, `iterateUnspentOutputs(rows)` loops over every row returned from `readStableOutputs`/`readUnstableOutputsSentByAAs` (queries have no `LIMIT`) and pushes each into `payload.inputs`, `arrUsedOutputIds`, and `arrConsumedOutputs` until the accumulated amount covers the target, with no cap on iteration count or resulting `payload.inputs.length`. [3](#0-2) [1](#0-0) 

Any unprivileged unit poster can send many small (but above the ~60-byte dust-filter threshold, see the comment at `aa_composer.js:1144`) outputs directly to a public AA address. Because the dust filter only screens amounts below `FULL_TRANSFER_INPUT_SIZE`, an attacker can post hundreds/thousands of outputs each just above that threshold, all of which pass the filter and get queued as spendable by the AA. When the AA is next triggered and must pay out its balance in a base-asset (or asset) payment, `completePaymentPayload` will keep pulling in these outputs without a cap, producing a `payload.inputs` array that can exceed `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (128).

Critically, `validatePaymentInputsAndOutputs()` in `validation.js` skips the `MAX_INPUTS_PER_PAYMENT_MESSAGE` check specifically for AA-generated units (`objValidationState.bAA` is true), so the "too many inputs" defense normally protecting wallet-composed payments does not apply here. [4](#0-3) 

Instead, the composed AA unit will be rejected by other limits such as `MAX_MESSAGES_PER_UNIT`/`MAX_UNIT_LENGTH`/`headers_commission`/`payload_commission` mismatches or oversize fee checks during `validateAndSaveUnit`, causing `bounce(err)` to fire. [5](#0-4) 
Because the dust outputs sent to the AA are never spent (the transaction that would have spent them is rejected and reverted every time), they remain permanently in the AA's UTXO set and will be re-selected on every subsequent trigger, causing the AA to bounce every future attempt to pay from that balance path indefinitely.

### Impact Explanation
This results in permanent freezing of AA funds: once an attacker floods a public AA address with enough small (non-dust) outputs, the AA can never again successfully compose a valid payment that spends its accumulated balance, since the coin-selection logic always re-includes the poisoned outputs and always exceeds the unit-size/oversize constraints, causing repeated bounces. Legitimate users and the AA's own balance become permanently unusable/stuck — a fund-freezing condition explicitly listed as an acceptable, in-scope impact.

### Likelihood Explanation
The attack requires only ordinary unit-posting capability (no privileged position, no hub/peer compromise): send many outputs, each barely above the dust-filter threshold, to any target AA's address, then trigger it. This is fully within reach of "an unpaired unit poster" as required by scope rules. The number of outputs required scales with `MAX_MESSAGES_PER_UNIT`/`MAX_UNIT_LENGTH`, which is a bounded, achievable cost for an attacker (a moderate number of dust-adjacent transactions).

### Recommendation
Add an explicit cap in `aa_composer.js`'s `iterateUnspentOutputs`/`completePaymentPayload` limiting the number of outputs consumed per payment message to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (with headroom for fee/change inputs), mirroring the existing protection in `inputs.js`'s `pickDivisibleCoinsForAmount` and `indivisible_asset.js`'s `pickIndivisibleCoinsForAmount` (`arrPayloadsWithProofs.length >= constants.MAX_MESSAGES_PER_UNIT - 1`). If the AA cannot fund a response within that cap, it should either split spending across multiple secondary triggers/responses or explicitly bounce with a "too many unspent outputs" error rather than silently accumulating an unbounded input set.

### Proof of Concept
1. Deploy or identify any public AA address that pays out on trigger (e.g. a bounce-back/forwarder AA).
2. From an unprivileged wallet, post N units, each sending a small payment output to the AA's address with `amount` just above `FULL_TRANSFER_INPUT_SIZE` (~60 bytes worth), for N large enough that the combined inputs would exceed `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` or `constants.MAX_UNIT_LENGTH` when consumed together.
3. Trigger the AA normally (send it a small additional payment to invoke its response logic).
4. Observe that `aa_composer.js`'s `sendUnit`/`completePaymentPayload` selects all N dust-adjacent outputs (no cap in `iterateUnspentOutputs`), producing a unit that fails validation checks (unit too large / oversize fee mismatch), causing `bounce()`; the outputs remain unspent and are re-selected on every subsequent trigger, permanently freezing the AA's spendable balance.
