### Title
Unprivileged third-party `supply` restamps a victim's collateral risk parameters to current (lower) listing values, bypassing the `update_account_threshold` health-factor guard - (File: contracts/controller/src/positions/supply.rs)

### Summary

`Controller::supply` deliberately permits any address to top up supply legs that already exist on someone else's account (`require_third_party_existing_supply` only rejects *new* assets for non-owner/non-delegate callers, `supply.rs:78-97`). However, every supplied leg — including a dust-sized third-party top-up — passes through `merge_supply_leg`, which unconditionally calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple` (`supply.rs:288-296`), overwriting that position's stored entry LTV and liquidation threshold with the *current* listing values. Unlike `update_account_threshold` (the intended permissionless restamp path, which with `has_risks` requires a resulting HF ≥ 1.05 WAD — `THRESHOLD_UPDATE_MIN_HF_RAW`), the supply path performs no post-action health-factor check at all: `process_supply` calls `finalize_position_flow` on `PositionSides::Supply` without `enforce_post_pool_solvency` (`supply.rs:63-73`), matching the documented rule that ordinary supply does not run the solvency gate.

This is the same bug class as Teller's `commitCollateral`: an unprivileged caller can mutate the committed collateral terms of a position belonging to another user, outside the state/checks the victim agreed to.

### Finding Description

- `supply(caller, account_id, spoke_id, assets)` calls `validation::require_authorized_caller` (which only requires the caller's own auth) and `require_third_party_existing_supply`, so any attacker may call it against any `account_id` as long as every supplied `HubAssetKey` is already a supply position of that account (`supply.rs:61, 86-96`).
- `process_deposit` → `merge_supply_leg` then restamps the leg's full risk tuple (`RiskRefreshScope::FullTuple`, `supply.rs:288-296`) from the current spoke asset config.
- If governance has since reduced that asset's `collateral_factor_bps`/`liquidation_threshold_bps` (or the leg was opened under more favorable stored parameters), the attacker forces the victim's liquidation-weighted collateral down — with no HF floor — where the owner themselves could not restamp via `update_account_threshold(has_risks=true)` without reverting unless HF ≥ 1.05.
- The attacker then calls `liquidate(...)` on the now-underwater account and seizes collateral at the HF-based bonus, funded purely by a dust deposit (which they could also frame as top-up "donation").

### Impact Explanation

Theft of user funds / forced liquidation. A healthy account whose stored liquidation parameters predate a parameter downgrade can be pushed below HF 1.0 by an attacker spending a dust amount, then liquidated for the bonus. If the restamp is strictly monotonic upward (unverified — see below), the impact collapses; assuming `FullTuple` overwrites stored values with current config as the name and the `leg_may_restamp_risk_params` gating on withdraws suggest, this enables collateral seizure at a discount.

### Likelihood Explanation

Requires a listing's liquidation parameters to have been lowered since the victim's leg was last restamped — a routine governance event (risk-off market adjustments). Cost to attacker is one dust token transfer; the victim cannot prevent it because third-party top-ups of existing legs are explicitly allowed and unrevocable. Reachable by any unprivileged address via a single `supply` call followed by `liquidate`.

### Recommendation

Gate the restamp, not the deposit: in `merge_supply_leg` (and third-party top-up paths generally), only apply `refresh_supply_risk_params` when the caller is owner/delegate, or skip `RiskRefreshScope::FullTuple` restamping for positions whose existing stored parameters are more conservative/favorable — e.g., apply `min(stored, current)` for LTV but never lower a live position's stored liquidation threshold without owner authorization. Alternatively, enforce a post-supply HF ≥ `THRESHOLD_UPDATE_MIN_HF_RAW` check when the caller is not owner/delegate, mirroring `update_account_threshold`.

### Proof of Concept

```text
1. Governance lowers liquidation_threshold_bps for XLM in spoke S from 80% to 60%
   (legitimate risk-off change; existing accounts keep stored 80% per design).
2. Victim holds account A: 100 XLM supplied (stored threshold 80%), debt D such
   that HF = 1.10 under the stored threshold, but 0.82 under the current 60%.
3. Attacker calls controller.supply(attacker, A, S, [(hub_asset(XLM), 1)]).
   - require_third_party_existing_supply passes: XLM leg already exists.
   - merge_supply_leg restamps the leg's FullTuple to the current 60%.
   - No solvency/HF check runs on the supply path.
4. is_liquidatable(A) now returns true; attacker calls liquidate(A, debt_payments,
   SeizeMode::Transfer) and seizes collateral at the liquidation bonus.
```

**Caveat / unverified:** I could not confirm the body of `refresh_supply_risk_params` in `contracts/controller/src/risk/params.rs` — if it preserves stored thresholds when they are stricter than current config (or only restamps on owner-initiated flows), this analog does not hold. The finding depends on `FullTuple` restamp overwriting stored per-position parameters with current listing values, which is consistent with the documented behavior that supplying to a leg triggers a "gated liquidation-parameter refresh" and with `leg_may_restamp_risk_params` treating the restamp as a risk-relevant event.
