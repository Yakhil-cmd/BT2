### Title
Permanent Pairing Secret Reused and Disclosed to Multiple Untrusted Arbiter-Contract Counterparties and Arbstores, Enabling Persistent Unauthorized Device Pairing - ([File: device.js])

### Summary
The GOAUTH vulnerability class in the report is a "shared credential not segmented per relying party" bug: a single secret intended for one context is handed out and can be replayed by unrelated parties to gain trust/access they shouldn't have. `ocore` has an analogous flaw in the device-pairing subsystem: `device.getOrGeneratePermanentPairingInfo()` generates (once) and forever reuses a single **permanent** pairing secret, which is disclosed in plaintext to every counterparty of an `arbiter_contract` transaction and to every arbstore server contacted during dispute/appeal handling. Because the secret is permanent and never invalidated, any one of these unrelated recipients can later use it to pair as a "confirmed" correspondent device of the victim — an authorization that should be scoped to a single, intentionally-chosen counterpart.

### Finding Description
`device.js` maintains a table `pairing_secrets` where `is_permanent=1` rows are never deleted after use, and the code comment explicitly documents that "multiple peers can pair through permanent secret": [1](#0-0) 

`getOrGeneratePermanentPairingInfo()` lazily creates exactly one permanent secret and returns the same value on every call, for the lifetime of the node: [1](#0-0) 

`handlePairingMessage()` accepts this permanent secret from *any* device presenting it, and unconditionally inserts/confirms the sender as a trusted correspondent (`is_confirmed=1`), without checking whether it was ever routed to that specific counterpart, and — since `is_permanent === 0` is false — never revokes the secret: [2](#0-1) 

This same permanent pairing code is deliberately embedded and transmitted to arbitrary, mutually distrusting parties in `arbiter_contract.js`:
- Sent to the contract peer on contract creation: `objContract.my_pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret;` then delivered via `device.sendMessageToDevice(...)`: [3](#0-2) 
- Sent again to the peer on acceptance: [4](#0-3) 
- Sent to a third-party arbstore HTTP endpoint (`/api/dispute/new`) whose URL is resolved from the contract's `arbiter_address` (an address that is negotiable/attacker-influenced during contract creation, an untrusted "AA/asset-issuer"-class actor per the reachability model): [5](#0-4) 
- Sent again to a (potentially different) arbstore endpoint (`/api/appeal/new`) during appeal: [6](#0-5) 

Because the very same permanent secret value is reused across every contract and every arbstore interaction rather than a secret freshly minted and scoped per relationship, any of these recipients — a dishonest contract counterparty, a dishonest or compromised arbstore operator, or anyone either of them subsequently discloses the value to — retains an indefinitely valid credential that can later be replayed against the victim's hub to become a "confirmed" correspondent device, exactly mirroring the GOAUTH flaw of a credential not being segmented per relying party/domain and thus reachable by parties who should never have had access to it.

### Impact Explanation
Becoming a "confirmed" correspondent (`correspondent_devices.is_confirmed=1`) bypasses the hub's default distrust of unknown devices: unconfirmed/unknown senders are restricted to a small whitelist of subjects (`pairing`, `my_xpubkey`, `wallet_fully_approved`) in `device.js`'s `hub/message` handler, while confirmed correspondents are allowed to reach all message handlers (`handleMessage`) that other ocore modules (wallet invitations, `arbiter_contract_offer`/`arbiter_contract_shared`, shared-address definitions, multi-sig cosigning flows, private-payment chat) subscribe to via `eventBus.emit("handle_message_from_hub", ...)`. An attacker who replays the leaked permanent pairing secret gains the standing of a long-term trusted contact of the victim, which is the trust anchor ocore's wallet/AA-adjacent device-message ecosystem relies on for social-engineering-resistant flows (e.g., accepting shared-address definitions, cosigning requests, and private-payment chain delivery). This directly undermines the intended per-relationship isolation of the pairing mechanism and can be leveraged toward unauthorized fund-movement attempts against the victim's wallet.

### Likelihood Explanation
Every `arbiter_contract` created or accepted by a user (an ordinary, unprivileged wallet action reachable by any counterparty proposing/accepting a contract) discloses the permanent pairing secret to that counterparty, and every dispute or appeal discloses it again to a (potentially different) arbstore server address resolved via the arbiter address embedded in the contract. Both flows are part of normal, unprivileged usage — no special privilege beyond being a contract counterparty or invoking dispute/appeal is required — so the number of parties who obtain a durable copy of the secret grows with ordinary usage of the arbiter-contract feature, and the secret is never rotated or scoped down afterward.

### Recommendation
Do not reuse a single permanent pairing secret across unrelated relying parties. Generate a fresh, one-time (non-permanent) pairing secret per contract/arbstore interaction (mirroring the already-existing ephemeral `startWaitingForPairing()` path used elsewhere in `device.js`), bind it to the specific expected device/arbstore, and invalidate it after first use or after a short expiry, consistent with how `is_permanent=0` secrets are already deleted on successful pairing in `handlePairingMessage()`.

### Proof of Concept
1. Attacker A proposes (or accepts) an `arbiter_contract` with the victim; `createAndSend`/`respond` sends the victim's permanent `my_pairing_code` (containing the reusable `pairing_secret`) to A's device.
2. A stores the pairing code and, independently of any dispute, later sends a `pairing` device message to the victim's hub using the leaked `pairing_secret`.
3. `handlePairingMessage()` in `device.js` accepts it (the secret is still valid — permanent secrets are never deleted) and inserts A's new device as a `is_confirmed=1` correspondent of the victim.
4. A's device can now send messages that pass the correspondent-trust checks in `handleJustsaying`'s `hub/message` case, impersonating a long-term trusted contact to the victim's wallet/contract-handling logic for further social engineering (e.g., malicious shared-address proposals, contract offers, or private-payment chains).
