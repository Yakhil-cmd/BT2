I have enough evidence to confirm the vulnerability. Let me verify `Shipit.github` lookup logic and the `Repository.from_github_repo_name` to finalize the exploit chain.### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while all webhook handlers act on the unrelated `repository.full_name` field, letting an attacker with a legitimate webhook secret for one GitHub organization forge events against a stack owned by a different organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository.owner.login` (falling back to `organization.login`). Every webhook handler, however, resolves the repository/stack to act on using the separate `repository.full_name` field via `Handler#repository_name`. Nothing ties these two fields together, so a signature that is valid for organization A's webhook secret authenticates a payload whose `repository.full_name` names a repository belonging to organization B. This mirrors the reported bug class: authorization is checked against one identity field (`operator`/`repository.owner.login`) while the state-changing action is performed against a different field (`to`/`repository.full_name`) taken from the same untrusted structure.

### Finding Description
`verify_signature` computes the org used to select the webhook secret from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` configuration (including its `webhook_secret`) keyed by that organization name, as documented for multi-organization installs: [3](#0-2) 

`verify_webhook_signature` only proves that the raw request body was HMAC-signed with *some* configured organization's secret — it says nothing about which repository inside that body is targeted: [4](#0-3) 

Every webhook handler, though, resolves the target `Stack`/`Repository` from a *different* payload field, `repository.full_name`, via the shared base class: [5](#0-4) 

`PushHandler` (and the pull-request handlers) use this `stacks`/`repository` helper directly and then queue real side effects: [6](#0-5) [7](#0-6) 

There is no code anywhere in the webhook pipeline that checks `repository.owner.login == repository.full_name.split('/').first`. Consequently:
- Before the attack: an operator who administers (or has webhook access to) organization A's GitHub App installation knows/derives organization A's `webhook_secret`, and can only legitimately deliver events for repositories under A.
- After the attack: that operator crafts a raw JSON body where `repository.owner.login` (and/or `organization.login`) = `"orgA"` (so `verify_signature` selects and validates against orgA's secret, which the attacker controls or knows) but `repository.full_name` = `"orgB/victim-repo"` — a stack belonging to a completely different, unrelated organization. The HMAC is computed over the exact raw body the attacker sends, so signature verification succeeds despite the mismatch between the authenticating org and the acted-upon repository.

This breaks the binding: `authenticating_organization == acted_upon_repository_owner`.

### Impact Explanation
Once the forged, signature-valid payload is accepted, `PushHandler#process` locates the victim's real `Stack` by `full_name` and calls `stack.sync_github(expected_head_sha: params.after)`, which enqueues `GithubSyncJob` for that stack — a stack the attacker has no legitimate relationship with: [8](#0-7) 

This job fetches commits with the app's real GitHub credentials for the target org and, if new commits are appended, enqueues `CacheDeploySpecJob`, which can trigger continuous deployment logic on the victim stack (`schedule_continuous_delivery` / `trigger_deploy` paths in `Stack`), i.e., an attacker outside organization B can force Shipit to sync and potentially auto-deploy a stack belonging to organization B purely by exploiting the mismatch between the field used for webhook authentication and the field used to select the acted-upon repository. This is an unauthorized cross-repository/cross-organization action triggered without any legitimate credential for the victim organization, satisfying the "unauthorized deploy" / cross-repository impact criteria.

Other handlers (`pull_request/*_handler.rb`) resolve `repository` the same way via `params.repository.full_name` and can similarly be pointed at PRs/review stacks belonging to an unrelated repository, e.g., archiving/unarchiving review stacks or updating PR metadata cross-organization.

### Likelihood Explanation
Exploitation requires the attacker to control (or have legitimate webhook-secret knowledge/access for) at least one GitHub organization that is configured in Shipit's multi-org `github:` secrets (a realistic, documented deployment topology), and to know that a second, unrelated organization/repository is also configured as a Shipit stack. Given that, forging the raw webhook POST is trivial — no GitHub session, `ApiClient` token, or privileged Shipit account is needed, only the ability to compute an HMAC-SHA1 with a secret the attacker already legitimately possesses for their own org. This is a realistic risk in any Shipit deployment serving multiple organizations/customers from one instance.

### Recommendation
After (or as part of) signature verification, cross-check that the organization used to select the webhook secret matches the owner encoded in every field the handler will use to resolve the target repository (e.g., assert `repository.full_name.split('/').first.casecmp?(repository_owner)` before dispatching to handlers), or better, have each `Handler` re-derive the "authenticating organization" itself and reject payloads where `repository.owner.login`/`organization.login` disagree with `repository.full_name`'s owner segment.

### Proof of Concept
1. Shipit is configured with two GitHub App organizations, `orgA` (attacker-administered) and `orgB` (victim, hosts a stack tracked by Shipit), per the multi-org secrets format in `docs/setup.md`.
2. Attacker knows `orgA`'s `webhook_secret` (they administer that GitHub App / its webhook settings).
3. Attacker builds a `push` payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "<any-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner = "orgA"`, fetches `orgA`'s `GitHubApp`, and `verify_webhook_signature` succeeds because the attacker signed with the correct secret for `orgA`.
6. `PushHandler#process` resolves `stacks` from `repository.full_name = "orgB/victim-repo"`, finds the victim's real `Stack`, and calls `stack.sync_github(...)`, enqueuing `GithubSyncJob` for a stack the attacker has no relationship with — demonstrating the org/repository binding is not enforced across the two payload fields.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
