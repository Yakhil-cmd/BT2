### Title
Headers-commission fee rounding lets a unit author zero out commission payouts while the network permanently marks the commission as spent - ([File: headers_commission.js])

### Summary
`headers_commission.js` distributes a parent unit's `headers_commission` to the winning child unit's author(s) using `Math.round(full_amount * share / 100.0)`. A unit author fully controls the `earned_headers_commission_share` percentages assigned to co-recipients (via the unit's `earned_headers_commission_recipients` list). By choosing a small enough `full_amount`/`share` combination, the rounded amount for one or more recipients becomes `0`, while the bookkeeping state (`max_spendable_mci`, `headers_commission_contributions`/`headers_commission_outputs`) advances irreversibly past that MCI. This mirrors the reported bug class: a fee computation rounds down to zero while the state that gates re-collection is updated anyway, permanently destroying the fee that should have been paid out.

### Finding Description
In `calcHeadersCommissions` (`headers_commission.js:144-216`), for each winning child unit the full `headers_commission` amount inherited from a parent unit is split among recipients:

```js
var amount = Math.round(full_amount * share / 100.0);
...
var amount = (row.earned_headers_commission_share === 100)
    ? full_amount
    : Math.round(full_amount * row.earned_headers_commission_share / 100.0);
``` [1](#0-0) 

`full_amount` is the tiny `headers_commission` fee attached to a single parent unit (typically on the order of tens of bytes), and `share` is an integer percentage that the unit author freely sets for each `address` in `earned_headers_commission_recipients` (validated only as an integer share in `validation.js`/stored via `writer.js`). If a unit author lists co-authors/recipients with sufficiently small shares (e.g., 1%) relative to a small `full_amount`, `Math.round(full_amount * share / 100.0)` rounds to `0` for some or all recipients.

Regardless of whether any non-zero amount was actually inserted, the pipeline still advances `since_mc_index` / `max_spendable_mci` for the processed range:

```js
conn.query("SELECT MAX(main_chain_index) AS max_spendable_mci FROM headers_commission_outputs", function(rows){
    max_spendable_mci = rows[0].max_spendable_mci;
    cb();
});
``` [2](#0-1) 

Because `calcHeadersCommissions` only ever processes MCIs `> since_mc_index` going forward (`since_mc_index = max_spendable_mci` from the previous run, `headers_commission.js:12-19`), there is no retry or accumulation mechanism analogous to `Math.Rounding.Floor` "carry-over": once an MCI's commission distribution rounds to zero for a recipient, that fraction of the commission is permanently lost - the same behavior described in the report, where `_takeFee`'s state (`lastFeeCollectionTimestamp`) advances even though the rounded `sharesToMint` is zero, silently forfeiting the fee instead of accruing it for the next collection.

The same rounding-and-state-advance pattern also occurs for payload/witnessing commissions in `paid_witnessing.js`, where `Math.round(objUnit.payload_commission / countPaidWitnesses[v.unit])` can round individual witness payouts to `0` while `count_paid_witnesses` is written to the `balls` table unconditionally, permanently finalizing witnessing payout state for that unit:

```js
amountsByAddress[v.address] += Math.round(objUnit.payload_commission / countPaidWitnesses[v.unit]);
...
conn.query("UPDATE balls SET count_paid_witnesses=? WHERE unit=?", [count_paid_witnesses, objUnitProps.unit], ...);
``` [3](#0-2) [4](#0-3) 

### Impact Explanation
This causes irreversible loss of protocol-designated fee income for legitimate parties (co-authors/witnesses), since the commission tracking state (`max_spendable_mci`, `count_paid_witnesses`) moves forward regardless of whether the rounded payout was actually credited. An attacker who structures multi-author units with deliberately fragmented `earned_headers_commission_share` values can cause commissions that would otherwise be paid to be silently destroyed instead of paid or carried forward, and this can be repeated on every unit the attacker authors. While this does not by itself let an attacker steal others' funds, it is a concrete instance of the exact rounding/state-advance class from the report causing unrecoverable fund loss at the protocol-fee layer.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires an author to deliberately construct multi-recipient `earned_headers_commission_recipients` with small shares and/or units whose `headers_commission`/`payload_commission` is small enough (a handful of bytes) for `Math.round` to floor to zero for at least one recipient. This is fully within a normal unit author's control and requires no special privilege, matching the "unprivileged unit poster" reachability required by scope.

### Recommendation
1. Round headers/witnessing commission shares in favor of the recipients (or in favor of not destroying value) - e.g., accumulate remainders and carry them to the next distribution instead of discarding fractions via `Math.round`.
2. Alternatively, only advance `max_spendable_mci` / mark `count_paid_witnesses` as finalized once the full `headers_commission`/`payload_commission` has been fully accounted for (sum of distributed amounts equals the input amount, with any remainder explicitly assigned to a recipient, e.g., the largest-share recipient) rather than unconditionally advancing state after a lossy rounding split.

### Proof of Concept
1. Attacker authors a unit `U` with two authors/recipients and sets `earned_headers_commission_recipients` shares such that, for at least one parent unit `P` with a small `headers_commission` (e.g., `P.headers_commission = 10` bytes), one recipient's share (e.g., `1%`) yields `Math.round(10 * 1 / 100) = 0`.
2. `U` becomes the winning child unit for `P`'s headers commission (`getWinnerInfo` in `headers_commission.js:249-259`).
3. `calcHeadersCommissions` runs, computes `amount = 0` for that recipient via the rounding at `headers_commission.js:183/202`, inserts a `0`-amount contribution (or no credit), and then unconditionally advances `max_spendable_mci` past `P`'s MCI.
4. The fractional commission owed to that recipient is now permanently unrecoverable - there is no future recomputation for that MCI - repeating this pattern across many self-authored units lets the attacker (or any author) systematically zero out fee income that should have accrued to co-authors/witnesses.
