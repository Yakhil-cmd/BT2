The webhook signature is verified against the GitHub App configured for `repository.owner.login` (or `organization.login`), but the actual repository acted upon by handlers is derived independently from `repository.full_name` — a separate field in the same attacker-influenced JSON body that is never cross-checked against `repository.owner.login`.

### Title
Webhook signature verified against `repository.owner.login`'s org secret while handlers act on an unbound `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`) read straight out of the unverified JSON body. [1](#0-0) [2](#0-1)  Once the signature is accepted, every registered `Handler` resolves the target `Repository`/`Stack` using a *different* field of the same body, `repository.full_name`, via `Repository.from_github_repo_name`, with no re-validation that `full_name`'s owner segment matches the `repository.owner.login`/`organization.login` used to pick the verifying secret. [3](#0-2) [4](#0-3) 

### Finding Description
The equality that should hold is: `organization whose secret authenticated the request == organization that owns the repository the handler mutates`. In this engine that binding is broken because two independently attacker-suppliable JSON fields are used for two different purposes:

- `repository_owner` (from `repository.owner.login` or `organization.login`) picks the `GithubApp`/webhook secret used by `verify_signature`. [1](#0-0) 
- `repository.full_name` is what every `Handler` subclass (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull_request handlers, etc.) uses to look up the `Repository`/`Stack` to act on, through `Handler#repository_name` / `Repository.from_github_repo_name`. [3](#0-2) 

If a multi-tenant Shipit deployment configures more than one GitHub organization (as the sample `secrets.development.shopify.yml` shows is a supported configuration with a distinct `webhook_secret` per org) [5](#0-4) , an attacker who legitimately controls a repository/webhook under organization A (and therefore possesses or can trigger a validly-signed delivery using org A's `webhook_secret`) can craft a payload where `repository.owner.login`/`organization.login` still says `"A"` (so `verify_signature` picks A's secret and the HMAC matches) while `repository.full_name` is set to `"B/some-repo"` for a stack belonging to a different organization B configured on the same Shipit instance. `verify_signature` never checks that these two fields are consistent, and no handler re-derives the owner from the verified organization before acting. [6](#0-5) 

### Impact Explanation
Handlers gated by this repository lookup drive state changes: `PushHandler` triggers `stack.sync_github` for the resolved stack based on attacker-chosen `ref`/`after`, [7](#0-6)  and `StatusHandler`/`check_suite`-family handlers write commit statuses that gate the merge queue and deploy safety checks. Because `repository.full_name` is never bound to the organization whose secret validated the request, an attacker holding a valid signing secret for organization A can forge events that mutate commit/CI/merge state for stacks belonging to organization B — a cross-repository/cross-tenant write achieved purely by mismatching two fields of one payload, analogous to the APC report's core bug class (acting on a field never covered by the value that was actually verified).

### Likelihood Explanation
Exploitability depends on the attacker already possessing a valid webhook secret for at least one organization configured on the instance (e.g., by owning/administering a repo under organization A that is onboarded to the same multi-org Shipit deployment as the victim organization B). This is a real, documented supported configuration (multiple orgs sharing one Shipit host, each with its own `webhook_secret`), not a hypothetical misconfiguration, so the precondition is squarely in-scope and unprivileged with respect to organization B.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the signature against the org selected via `repository_owner`, enforce that `repository.full_name`'s owner segment (or `organization.login`) equals the same `repository_owner` before dispatching to handlers, rejecting mismatched payloads with `422`. Alternatively, have `Handler#repository_name` receive and check the authenticated organization explicitly rather than re-reading it from the unauthenticated repository sub-object.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (as supported by `config/secrets.development.shopify.yml`).
2. As an attacker who administers a repo under `org-a`, capture/craft a `push` webhook payload signed with `org-a`'s `webhook_secret`, setting: `repository.owner.login = "org-a"`, but `repository.full_name = "org-b/victim-repo"`.
3. `WebhooksController#verify_signature` computes `repository_owner = "org-a"`, fetches `org-a`'s `GithubApp`, and successfully verifies the HMAC signature (attacker knows `org-a`'s secret). [1](#0-0) 
4. `PushHandler.call(params)` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")`, finds the `org-b` stack, and calls `stack.sync_github(expected_head_sha: ...)`, mutating state for a repository the attacker never proved control of or authenticated against. [7](#0-6) [4](#0-3)
