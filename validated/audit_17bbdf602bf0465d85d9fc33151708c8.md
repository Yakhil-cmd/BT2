### Title
API client stack-scope bypass in CI status endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` reimplements its own `stack` lookup instead of using the tenant-scoped `stack`/`stacks` helpers defined in `Shipit::Api::BaseController`. This breaks the binding "the stack a token authorizes == the stack the token can touch": an `ApiClient` created with a restrictive `stack_id` (meant to confine it to a single stack) can be used to read CI/build status for *any* stack in the installation by simply supplying a different `stack_id` parameter.

### Finding Description
`Shipit::Api::BaseController` defines the authorization boundary that scopes API clients to the stack they were issued for: [1](#0-0) 

`stacks` returns only the stack matching `current_api_client.stack_id` when that field is set on the `ApiClient` record, otherwise all stacks; `stack` then resolves `params[:stack_id]` **within that scope**. This is the mechanism that makes a scoped `ApiClient` (see fixture `here_come_the_walrus`, which has `stack: shipit`) safe to hand out to a single consumer without leaking data about other stacks — confirmed by the test asserting "an api client scoped to a stack will only see that one stack": [2](#0-1) 

However, `Api::CCMenuController` overrides `stack` to bypass this scoping entirely: [3](#0-2) 

Instead of calling the inherited `stacks.from_param!(params[:stack_id])`, it calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model. The only authorization check performed is `require_permission :read, :stack`, which merely checks that the client's `permissions` array contains the string `"read:stack"` — a global capability check, not a per-stack check: [4](#0-3) 

So the equality the code is supposed to preserve — *stack authorized by the token* == *stack acted upon by the controller* — is broken: any client holding a token with `read:stack` permission (even one explicitly created with a `stack_id` restricting it to a single project) can supply an arbitrary `stack_id` in the request and receive that other stack's CI state.

### Impact Explanation
This is a scope-escalation vulnerability: possession of a token intentionally restricted to one stack (a common integration pattern, e.g. for CCTray/CI dashboard widgets, as seen in `CCMenuUrlController#client` which creates a `read:stack`-only token attached to a specific stack) grants the holder unauthenticated (from the target stack's perspective) read access to build/deploy status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of every other stack managed by the Shipit instance, including private/internal projects the token was never meant to see. This matches the "unauthorized read of stack state" class of High-impact findings.

### Likelihood Explanation
Exploitation requires only a valid, low-privilege `ApiClient` token with the `read:stack` permission — no special privilege beyond what is routinely issued for CI-badge integrations (see `CCMenuUrlController`). The attacker does not need write access to any repository, does not need a Shipit session, and does not need to know or forge any secret beyond the token they already legitimately hold for their own stack. This is a straightforward parameter-substitution attack (`stack_id` in the query string), requiring no timing or race conditions.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, properly scoped lookup instead of querying `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the override entirely so it inherits `BaseController#stack`/`#stacks`, thereby honoring `current_api_client.stack_id` scoping the same way every other API controller does.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to Stack A with permission `read:stack` only, e.g. as done automatically by `CCMenuUrlController#client` for stack A (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with `stack: A`).
2. Obtain that client's `authentication_token`.
3. Send: `GET /api/stacks/<STACK_B_ID>/ccmenu.xml?token=<TOKEN_SCOPED_TO_A>` where `STACK_B_ID` is a different stack the token holder should not be able to see.
4. Observe: `authenticate_api_client` in `CCMenuController` accepts the token (it only checks `params[:token]` validity, not stack scope), `require_permission :read, :stack` passes (client has `read:stack`), and `stack` resolves to Stack B via the unscoped `Stack.from_param!`, returning Stack B's CI status XML — confirming the token's intended single-stack scope was bypassed.
