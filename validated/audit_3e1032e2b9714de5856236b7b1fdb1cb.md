### Title
Webhook signature verification selects its trust anchor from unauthenticated payload data, allowing forged webhooks for arbitrary repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to verify a webhook against by reading `repository_owner` straight out of the still-unverified JSON body, then hands the *same* untrusted body to handlers that look up the target `Stack` from a completely different, independently attacker-controlled field (`repository.full_name`). Combined with `GitHubApp#verify_webhook_signature` returning `true` whenever the selected organization has no `webhook_secret` configured, an attacker who can name any org with a blank secret bypasses signature verification entirely while pointing the payload at any other repository/stack in the instance. This breaks the intended binding: "organization that authenticated" (used to look up the verification secret) must equal "the repository that is (subsequently) written/acted on".

### Finding Description
`verify_signature` derives the verification key purely from payload data, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves this attacker-chosen org against `secrets.github`, and `GitHubApp#verify_webhook_signature` treats a blank/unset `webhook_secret` as automatic success: [3](#0-2) 

The sample multi-org secrets file demonstrates that per-organization `webhook_secret` can legitimately be left unset for some entries while others are configured: [4](#0-3) 

Once `verify_signature` passes (because the chosen org has no secret), the raw payload — never actually authenticated — is dispatched to handlers. Handlers determine which `Stack` to act on from a *different* field, `repository.full_name`, with no check that it belongs to the organization used for verification: [5](#0-4) 

For example, the push handler triggers a GitHub sync for any matching stack purely from that unverified `repository.full_name`: [6](#0-5) 

This is the direct analog of the audit's "global state variable collision": the value used to establish trust (`repository_owner`, analogous to the storage slot chosen for `params`) is not guaranteed to correspond to the value the rest of the system subsequently trusts and acts on (`repository.full_name`, analogous to the pool slot actually written). There is no invariant tying the two together, and the "verified" flag is attached to the request as a whole rather than to the specific repository/organization pairing being acted upon.

### Impact Explanation
This is an authentication-bypass class issue (Critical per the engine's stated impact list): a forged, entirely unsigned webhook is accepted as authentic for the instance as soon as one configured organization has an unset `webhook_secret`, and the attacker can direct the resulting (falsely trusted) event handling at any repository/stack tracked by the deployment, not just the org whose (absent) secret was used. Downstream effects depend on which event/handler is invoked (e.g., forcing `GithubSyncJob` runs, membership/team webhook handling, check-run refreshes) against a stack the attacker does not control on GitHub, undermining the "only GitHub can produce a validly-signed event for a given repo" guarantee the rest of the engine relies on.

### Likelihood Explanation
Requires only unauthenticated HTTP access to `Shipit::WebhooksController#create` (no session, API token, or GitHub write access needed) and requires the deployment to have at least one configured GitHub organization/app with no `webhook_secret` set — a state the shipped sample secrets file explicitly shows as a supported configuration, and a plausible operational mistake (e.g., an org added only for OAuth team mapping, or a not-yet-configured second org in a multi-tenant install).

### Recommendation
- Never treat a missing `webhook_secret` as "verification succeeds"; instead, fail closed (return false / reject) when a webhook_secret is not configured for the resolved organization, and require every configured GitHub organization to have a secret.
- Do not resolve the verification key from the same untrusted payload used later for repository targeting. If multiple organizations/secrets are supported, either verify against every configured secret and only proceed if the *same* organization's key both authenticates and matches `repository.full_name`'s owner, or require an unambiguous transport-level indicator (e.g., a per-org URL path) to select the key, independent of body content.
- After successful verification, assert `repository.full_name`'s owner equals the organization whose secret verified the signature before dispatching to handlers.

### Proof of Concept
1. Configure (or find, in a multi-org deployment) an organization entry in `secrets.github` where `webhook_secret` is blank, e.g. `someothergithuborg` per `config/secrets.development.shopify.yml`.
2. Send `POST /webhooks` (mounted route for `Shipit::WebhooksController#create`) with header `X-Github-Event: push` and a body:
```json
{
  "organization": { "login": "someothergithuborg" },
  "repository": { "owner": { "login": "someothergithuborg" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "deadbeef"
}
```
No valid `X-Hub-Signature` header is required, since `Shipit.github(organization: "someothergithuborg")` resolves a `GitHubApp` whose `webhook_secret` is blank, making `verify_webhook_signature` return `true` unconditionally [7](#0-6) .
3. `PushHandler#process` then looks up stacks solely via `victim-org/victim-repo` (from `repository.full_name`) [5](#0-4)  and triggers `stack.sync_github` for that unrelated, real, secured stack — a repository never associated with the organization whose (absent) secret satisfied verification.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
