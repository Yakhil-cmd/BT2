## Analysis

The bug‑class in TRST‑M‑6 is: a privileged operation is bound to something the code never actually validates against the field the operation later reads. `shipit-engine`'s webhook ingestion pipeline has the same class of defect: **the organization whose secret validated the HMAC signature is not the organization/repository the resulting handlers act on.**

### Finding Description

`WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate the signature against using `repository_owner`, which reads `repository.owner.login` (or `organization.login`) straight out of the **unauthenticated** JSON body: [1](#0-0) [2](#0-1) 

Once the signature is accepted, every event handler resolves the *actual* repository/commits to act on using a **different field of the same payload**: [3](#0-2) 

`Handler#repository_name` reads `repository.full_name`, an independent JSON key that has no relationship enforced with `repository.owner.login` used for signature/secret selection. Because the HMAC (`verify_webhook_signature`, `lib/shipit/github_app.rb:76-83`) simply signs the raw POST body, an attacker who legitimately administers **any one** of the multiple GitHub orgs Shipit is configured to trust (a supported multi‑org configuration, see `docs/setup.md:182-209`) knows that org's `webhook_secret`. That attacker can compute a valid signature over an arbitrary payload where:
- `repository.owner.login` = `"attacker-org"` (their own trusted org → picks a secret they know), and
- `repository.full_name` = `"victim-org/victim-repo"` (any repository actually tracked by Shipit, owned by a completely different, unrelated org).

`verify_signature` will accept it, and the handler will act on `victim-org/victim-repo`'s `Stack`s.

The impact is worse for `StatusHandler`, which doesn't even scope by repository — it looks up commits purely by `sha` across the whole install: [4](#0-3) 

So the same attacker, using only their own org's `webhook_secret`, can forge a `status` event with `state: "success"` for *any commit sha in the entire Shipit instance* (not just their own repos), calling `Commit#create_status_from_github!` on it.

### Impact Explanation

A forged "success" status on a victim's commit can satisfy the checks that `Stack#deployable?`/continuous-deployment gating rely on. `ContinuousDeliveryJob#perform` triggers `stack.trigger_continuous_delivery` once a stack is `continuous_deployment?` and not occupied — no additional GitHub state re‑verification happens beyond the `Status` records Shipit itself stores: [5](#0-4) 

This gives an unprivileged (w.r.t. the victim org) attacker who merely controls one org already onboarded to a multi-org Shipit instance a path to fabricate passing CI status for a victim's commit and cause an **unauthorized deploy** of that stack — the exact "cross-repository writes / unauthorized deploy" impact class called out in scope. The equality that should hold but doesn't is:

`organization whose secret authenticated the webhook == organization/repository the handler subsequently mutates`

### Likelihood Explanation

Requires only: (a) the target Shipit instance configured with the multi-org `github:` block (a documented, supported configuration, `docs/setup.md:182-209`), and (b) the attacker administers/controls one of those configured orgs (owns its GitHub App and therefore its `webhook_secret`) — no Shipit session, `ApiClient` token, or repository write access on the victim org is required, satisfying the "unprivileged attacker" constraint.

### Recommendation

In `WebhooksController#verify_signature`, after selecting the app/secret by `repository_owner`, re-validate that `repository_owner` matches the owner implied by `repository.full_name` (and reject if they differ) before dispatching to handlers. Additionally, scope `StatusHandler#process` (and `Handler#stacks`) to only affect commits/stacks belonging to the repository whose owner was actually verified, rather than a global `Commit.where(sha:)` lookup.

### Proof of Concept

1. Shipit is configured with two trusted GitHub orgs, `attacker-org` and `victim-org`, per the multi-org config in `docs/setup.md`. Attacker administers `attacker-org` and knows its `webhook_secret`.
2. Attacker crafts a `status` event body:
```json
{
  "sha": "<victim commit sha already tracked by Shipit>",
  "state": "success",
  "context": "ci/forced",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` selects `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the signature validates [1](#0-0) .
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — globally, regardless of `attacker-org` vs `victim-org` — and records a fabricated "success" status [4](#0-3) .
6. If this satisfies the victim stack's deployability checks, the next `ContinuousDeliveryJob` run deploys the victim's commit without any legitimate CI signal.
