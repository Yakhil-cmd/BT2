### Title
Arbiter contract "paid" status is set from an unstable, non-final payment - premature release of escrowed/private funds ([File: arbiter_contract.js])

### Summary
`arbiter_contract.js` marks a private-asset arbiter contract as `paid` as soon as it observes a matching-amount output with `sequence='good'`, without waiting for the underlying unit to become stable (`is_stable=1`). This mirrors the reported bug class (releasing a paid-for asset/service without a solid payment-status check): the contract's payer or beneficiary can be induced to treat funds as "received" and proceed to `complete()` (release of escrowed private-asset ownership / countersign the payout) while the paying unit can still be overturned by DAG resolution before it stabilizes.

### Finding Description
The event handler that flips a `wallet_arbiter_contracts` row to `status='paid'` only requires `units.sequence='good'`: [1](#0-0) 

`sequence='good'` is assigned to a unit as soon as it doesn't currently conflict with a known competitor, but it is explicitly *not* final — conflicting units are resolved only once the relevant part of the DAG stabilizes, and a currently-`good` unit can later flip to `final-bad` (see `validation.js`, where `checkInputDoubleSpend`/`acceptDoublespends` shows unstable inputs whose uniqueness is only settled at stabilization): [2](#0-1) [3](#0-2) 

Once the contract row is `status='paid'`, the application-level `complete()` function is unlocked to release the counterparty's/arbstore's share of the escrow, or (for the private-asset branch) to post the `CONTRACT_DONE_*` data-feed message that finalizes handoff: [4](#0-3) 

No stability check (`is_stable=1`) is performed anywhere in this flow before `status` becomes `'paid'`, nor before `complete()` is allowed to run (`complete()` only checks `objContract.status !== "paid" && objContract.status !== "in_dispute"`). This is the same root cause class as the referenced advisory: a "payment received" state is derived from a payment that has not yet reached a final/confirmed status, and that state is used to authorize release of value.

### Impact Explanation
A malicious private-payment counterparty (the buyer/`peer_address` in the contract) can send the required amount to the shared escrow address in a way that is momentarily `sequence='good'`, causing the counterparty's wallet to auto-flag the contract `paid`. If the payer/vendor (or an automated integration built on this API) reacts to that status by releasing the private asset, service, or by counter-signing the `complete()` payout before the unit is stable, the buyer can subsequently cause the paying unit to become `final-bad` (e.g. by getting a conflicting double-spend to win before stabilization), leaving the seller/arbiter-contract counterparty with no payment but having already released the good/finalized the deal. This is unauthorized/uncompensated fund loss for the party that trusted the premature `paid` status.

### Likelihood Explanation
The attacker only needs to be the counterparty of a private (or otherwise) arbiter contract — a normal, unprivileged wallet user reachable through the standard "private payment" flow (`new_my_transactions` fires for any wallet after `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` accept a chain with `sequence='good'`, which does not require stability). Constructing a temporarily non-conflicting but ultimately reversible spend is a known and previously-exploited technique against unstable/`sequence='good'` units in DAG-based ledgers, making this reachable without any special privileges, only requiring precise timing around DAG stabilization.

### Recommendation
Require `is_stable=1` (not merely `sequence='good'`) before transitioning a contract to `status='paid'` in the `new_my_transactions` listener, and/or add an explicit stability check inside `complete()` before releasing escrowed funds or posting the `CONTRACT_DONE_*` finalization message. Alternatively, expose and document the pending/stable distinction so integrators cannot release goods based on the `paid` status alone.

### Proof of Concept
1. Attacker (buyer) and victim (seller) create an arbiter contract for a private asset over a shared address; contract status is `signed`.
2. Attacker sends the contract's private-asset payment amount to the shared address, but structures it so it is only momentarily non-conflicting (`sequence='good'`) while not yet stable — e.g., by sending it as part of a private payment chain and, before the unit stabilizes, using another linked wallet/output to attempt a double-spend of one of the payment's own inputs.
3. `new_my_transactions` fires; the query in `arbiter_contract.js` lines 826-833 finds `SUM(outputs.amount) >= amount AND units.sequence='good'` and sets `status='paid'`, per [1](#0-0) .
4. Seller's wallet/UI, observing `status==='paid'`, calls `complete()` (or the seller manually ships/unlocks the private asset), per [4](#0-3) .
5. Attacker's conflicting double-spend later wins during DAG stabilization, flipping the original payment unit to `final-bad`; the seller has released the good/service and payment never finalizes.
