### Title
`pox_rollover_v5` accepts a roll-over from *any* locked balance, not just an existing PoX-5 lock — double-counts STX still locked under PoX-4 as fresh PoX-5 stake - (File: `pox-locking/src/pox_5.rs`)

### Summary
The node-side handler that applies a PoX-5 `stake`/`register-for-bond` result decides whether to treat the call as a fresh lock or a roll-over solely by checking `snapshot.has_locked_tokens()` — a version-agnostic predicate. When it dispatches to the roll-over path (`pox_rollover_v5`), that function *also* only checks `has_locked_tokens()` and then unconditionally overwrites the account's balance with a `LockedPoxFive` lock via `set_lock_v5`, without ever confirming the existing lock actually belongs to PoX-5.

### Finding Description
`handle_lockup_pox_v5` computes:
```
let already_locked = { ... snapshot.has_locked_tokens()? };
let lock_result = if already_locked { pox_rollover_v5(...) } else { pox_lock_v5(...) };
``` [1](#0-0) 

`has_locked_tokens()` is true for *any* PoX lock (v1 through v5) — it does not distinguish which contract owns the lock. Compare this to the STX-database layer's own `increase_lock_v5`, which explicitly rejects the operation unless `is_v5_locked()` is true: [2](#0-1) 

and to `pox_lock_update_v5` (used by `stake-update`), which routes through `increase_lock_v5` and therefore does enforce that version check: [3](#0-2) 

`pox_rollover_v5`, however, bypasses this check entirely. It only verifies `has_locked_tokens()` and total-balance sufficiency, then calls `snapshot.set_lock_v5(new_total_locked, unlock_burn_height)` directly — never confirming the lock being rolled over is a PoX-5 lock: [4](#0-3) 

Because PoX stacking locks span up to 12 reward cycles (`MAX_POX_REWARD_CYCLES`) while the chain's "active PoX contract" can switch from PoX-4 to PoX-5 cycle-by-cycle, a staker can still be holding an *active PoX-4 lock* (locked via `pox-4.clar`'s `stack-stx`, see `contrib/boot-contracts-unit-tests/boot_contracts/pox-4.clar:571-621` / `stackslib/src/chainstate/stacks/boot/pox-4.clar:571-621`) at the moment PoX-5 is active. On the PoX-5 contract side, `stake()` only asserts `(is-none (get-staker-info tx-sender))` and checks its own `protocol-bond-memberships`/`staker-info` maps — it has no way to see, and does not check, that `tx-sender`'s tokens are currently locked by a *different* contract (PoX-4): [5](#0-4) 

So the following sequence breaks the "locked value == what a contract's own accounting says is locked" equality:
1. Staker locks STX via PoX-4 `stack-stx` for `lock-period` cycles (e.g. 12), entering PoX-4's reward-cycle accounting (`stacking-state`, per-cycle reward set entries) for those cycles.
2. Before that lock naturally expires, PoX-5 becomes the active contract for a later cycle inside that lock window. Staker calls PoX-5's `stake` (first-ever PoX-5 call — `staker-info` is `none`, so the contract's own gate passes).
3. `handle_lockup_pox_v5` on the node observes `has_locked_tokens() == true` (because the PoX-4 lock is still active) and — even though the *PoX-5 contract* believes this is a *fresh* stake, not a roll-over — dispatches to `pox_rollover_v5` instead of `pox_lock_v5`.
4. `pox_rollover_v5` blindly converts the account's balance to `LockedPoxFive { amount_locked: new_total_locked, unlock_height: unlock_burn_height }`, discarding/overwriting the PoX-4 lock state at the account level, while PoX-4's own contract-side reward-cycle maps (`stacking-state`, per-cycle reward-set entries added by the original `add-pox-addr-to-reward-cycles`) are never cleared or reconciled — they still reference the original locked amount for the remaining PoX-4 cycles.

The net effect: the *same* underlying STX amount is simultaneously (a) counted by PoX-4's still-live reward-cycle bookkeeping as backing a PoX-4 reward slot for its remaining cycles, and (b) counted by PoX-5's newly created `staker-info`/signer-cycle bookkeeping as backing a PoX-5 stake/signer weight — a double-count of one locked-STX position across two PoX systems, i.e. reward slots / signing weight exceeding the value actually and singularly locked.

### Impact Explanation
This inflates reward-eligibility/signing weight beyond what is actually backed by a single, uniquely-owned lock of STX — matching the "High" bucket: *"signing weight or reward slots exceeding locked value."* It also risks freezing/mis-crediting the account's balance state (the PoX-4 unlock schedule is silently discarded and replaced), which can cause temporary freezing of the staked funds relative to what the staker/PoX-4 contract expected.

### Likelihood Explanation
This requires no privileged access — any staker who has an active PoX-4 lock spanning the PoX-4→PoX-5 transition window and who calls PoX-5 `stake`/`register-for-bond` for the first time triggers the mismatch between the contract-level "first-time stake" gate and the node-level "any lock present" gate. The overlap window (multi-cycle locks crossing a contract-version boundary) is a normal, expected occurrence during a live PoX-4→PoX-5 migration, not a contrived edge case.

### Recommendation
`handle_lockup_pox_v5` and `pox_rollover_v5` should determine "already locked by PoX-5" using a version-specific check (e.g. an `is_v5_locked()` predicate, mirroring what `increase_lock_v5` already enforces) rather than the version-agnostic `has_locked_tokens()`. If the account is locked by a different PoX version, the call should be rejected (or the older lock explicitly resolved/settled) rather than silently rolled over into a `LockedPoxFive` state.

### Proof of Concept
Conceptual reproduction (cannot be executed without a live devnet):
1. Staker `S` calls PoX-4's `stack-stx` locking `N` uSTX for the maximum `lock-period` (12 cycles), while PoX-4 is still the active contract.
2. Before those 12 cycles elapse, the chain configuration transitions to PoX-5 as the active contract for a subsequent cycle still within `S`'s PoX-4 lock window.
3. `S` calls PoX-5's `stake` for a fresh `amount-ustx` (PoX-5's `staker-info` map has no entry for `S`, so the contract's `ERR_ALREADY_STAKED` gate does not fire) — see `stake` gating at `stackslib/src/chainstate/stacks/boot/pox-5.clar:1025-1049`.
4. Node-side, `handle_lockup_pox_v5` sees `has_locked_tokens() == true` (from the still-active PoX-4 lock) and calls `pox_rollover_v5`, which overwrites `S`'s balance to a `LockedPoxFive` lock reflecting only the PoX-5 amount/unlock height (`pox-locking/src/pox_5.rs:315-344`), while PoX-4's `stacking-state` and per-cycle reward-set entries for `S` are left untouched.
5. Result: `S`'s original PoX-4-locked STX are counted in PoX-4's remaining-cycle reward set *and* the (possibly different) amount is now counted in PoX-5's signer/reward accounting — a double count of stacked value not actually singularly backed.

pub fn pox_rollover_v5(
    db: &mut ClarityDatabase,
    principal: &PrincipalData,
    unlock_burn_height: u64,
    new_total_locked: u128,
) -> Result<STXBalance, LockingError> {
    if new_total_locked == 0 {
        return Err(LockingError::PoxInvalidLockAmount);
    }

    let mut snapshot = db.get_stx_balance_snapshot(principal)?;

    if !snapshot.has_locked_tokens()? {
        return Err(LockingError::PoxExtendNotLocked);
    }

    let bal = snapshot.canonical_balance_repr()?;
    let total_amount = bal
        .amount_unlocked()
        .checked_add(bal.amount_locked())
        .ok_or(LockingError::PoxBalanceOverflow)?;
    if total_amount < new_total_locked {
        return Err(LockingError::PoxInsufficientBalance);
    }

    if unlock_burn_height <= bal.unlock_height() {
        return Err(LockingError::PoxInvalidUnlockHeight);
    }

    snapshot.set_lock_v5(new_total_locked, unlock_burn_height)?;
