### Title
Cross-tenant status write via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no scoping to the repository/organization whose webhook signature was verified, and calls `commit.create_status_from_github!(params)` on every match. Since `verify_signature` in `WebhooksController` only proves that the payload was signed by *some* app matching `repository_owner` in the payload, but the handler never re-checks that the matched `Commit` rows actually belong to that repository, a validly-signed status payload for repo A can mutate `Status` rows on a `Commit` belonging to a completely different `Stack`/repo B if the shas coincide.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `payload.repository.full_name == commit.stack.repository.full_name` for every `commit` mutated by `StatusHandler#process`. Instead the code only guarantees `verified_signature_for(payload.repository.owner) == true`, which is a weaker, unrelated fact.

Code path:
- `WebhooksController#verify_signature` [1](#0-0)  resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and calls `verify_webhook_signature`, which checks the HMAC signature against that org/app's `webhook_secret` [2](#0-1) . This only proves the payload was signed by the app configured for that *organization* — it says nothing about which `Commit` rows the payload should be allowed to touch, and multiple orgs/apps can be mounted per the multi-org setup.
- `WebhooksController#create` dispatches to registered handlers with the raw parsed JSON: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .
- `StatusHandler#process` then does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . This query has **no** `stack_id`, `repository_id`, or any join back to the `repository`/`owner` fields present in the same payload (`params.dig('repository', ...)` is available on the controller but is never passed into or checked by the handler).
- `Commit#create_status_from_github!` unconditionally creates a `Status` row scoped to `stack_id` for that commit [5](#0-4) , and that status feeds into `required_statuses`/`blocking_statuses`/CI-gating via `Status::Group` and `Commit#blocked?`/`#deployable?` [6](#0-5) .

Exploit flow: attacker registers a GitHub App/webhook on their own fork repo pointed at the shared Shipit host (a legitimate, unprivileged configuration action for a repo they own), obtaining a correctly signed `status` event for their own installation. They set `sha` in that payload to a commit sha that also exists as a `Commit` row in a victim's `Stack` (achievable deliberately by forking and cherry-picking/replaying the victim's exact commit, which preserves the content-addressed sha). Because `StatusHandler` never checks `commit.stack.repository` against the payload's own `repository`, every `Commit` row across every tenant sharing that sha gets `create_status_from_github!` called with the attacker-controlled `state`/`context`/`description`/`target_url`.

None of the existing guards close this gap: `verify_signature` authenticates only the app/org identity of the sender, not per-commit repo ownership; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema in `StatusHandler.params` only validates payload shape, not scope; there is no `require_permission!`, `stacks` scope, or model validation anywhere in this path that ties `Commit.where(sha:)` back to the authenticated app/org.

### Impact Explanation
A single crafted, validly-signed webhook from an attacker's own repo/app installation can write a `Status` (CI check state, description, target_url) onto a `Commit` belonging to an arbitrary victim `Stack`/organization whenever a sha collision can be engineered (trivial via fork + cherry-pick of a real commit that the victim also has, e.g., a shared base/vendor commit or an intentionally replicated commit prior to a PR). This corrupts `required_statuses`/`blocking_statuses` evaluation, `Commit#deployable?`, and `Commit#blocked?`, which drive merge-queue and deploy-gating logic — an attacker can force a victim's blocked/pending commit to appear `success` (unblocking an unauthorized merge/deploy) or force a healthy commit to `error`/`failure` (denial of legitimate deploys). This is a payload for one repository mutating another repository's commit/stack state, matching the Critical category explicitly listed in scope.

### Likelihood Explanation
Preconditions are all attacker-controllable and require no victim or Shipit secrets: the attacker only needs (1) their own GitHub repo/fork with a webhook/App pointed at the shared Shipit host — a normal, permitted configuration action for a repo owner — and (2) a commit sha that collides with one recorded in a victim stack, achievable by cherry-picking/replaying the victim's real commit into their own fork/branch and pushing a `status`-triggering action (or directly crafting the JSON body of a `status` webhook, since nothing besides the HMAC signature is checked). Signing itself is not a barrier since the attacker's own app's secret is legitimately theirs. The attack is repeatable against any victim commit sha the attacker can learn or reproduce (e.g., via public commit history in a fork lineage) and requires no rate-limiting bypass, no privileged role, and no compromise of any secret.

### Recommendation
Scope the commit lookup to the repository/app identified by the verified signature. Pass the payload's `repository` (owner/name) from `WebhooksController` into the handler context, and change `StatusHandler#process` to filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: ..., name: ... })` (or equivalent `stack.repository` match) before calling `create_status_from_github!`, rejecting/skipping any `Commit` whose stack's repository does not match the payload's repository. Apply the same repository-scoping fix to any other handler that queries `Commit`/`Stack` by content-derived identifiers (sha, branch) without tying back to the authenticated repository.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create two `Stack`s in two different `Repository`s (owner/name pairs), e.g. `repo_a = shipit/repo-a`, `repo_b = victim/repo-b`.
2. Create `Commit` rows with the identical `sha = "deadbeef...".ljust(40, '0')` in each stack: `commit_a = create(:commit, stack: stack_a, sha: sha)`, `commit_b = create(:commit, stack: stack_b, sha: sha)`.
3. Build a `status` webhook JSON body with `repository.owner.login = 'shipit'`, `repository.name = 'repo-a'`, `sha: sha, state: 'success', context: 'ci/attacker'`.
4. Sign it with `repo_a`'s configured `webhook_secret` (the attacker's own, legitimately obtained secret for their app/repo) and POST to `/webhooks` with `X-Github-Event: status` and correct `X-Hub-Signature`.
5. Assert: `commit_a.statuses.reload.last.context == 'ci/attacker'` (expected, same-tenant write) AND assert `commit_b.statuses.reload.empty?` (must remain empty — this assertion currently **fails** given the code, demonstrating `commit_b`, belonging to `victim/repo-b`, also received `create_status_from_github!` despite the signature only authenticating `shipit/repo-a`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
