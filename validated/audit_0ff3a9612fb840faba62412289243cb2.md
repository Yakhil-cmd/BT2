### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's build/deploy state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single `stack_id`, and `Shipit::Api::BaseController` enforces that scope by resolving `stack` through the client-scoped `stacks` relation. `Shipit::Api::CCMenuController`, however, overrides `stack` to look up `Stack.from_param!(params[:stack_id])` directly, completely bypassing the scoping relation. Any holder of a stack-scoped API token (with only `read:stack` permission on their own stack) can request the CCMenu XML for an arbitrary `stack_id` belonging to a different stack/repository and read its build status, last build label, and deploy activity.

### Finding Description
`BaseController` defines the scoping invariant that the token binds to: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` resolves `params[:stack_id]` only within that scoped relation — i.e. the invariant `token.stack_id == resolved_stack.id` (when the token is scoped) is enforced here.

`CCMenuController` reimplements authentication and stack resolution independently, and its `stack` method does **not** go through the scoped `stacks` relation at all: [2](#0-1) 

It only calls `require_permission :read, :stack` (a permission check, not a scope check) and then resolves the target unconditionally via `Stack.from_param!(params[:stack_id])`, which searches across all stacks: [3](#0-2) 

The `ApiClient` model itself only checks the permission list (`read:stack`, etc.); it has no built-in enforcement that a scoped `stack_id` matches the stack being acted on — that enforcement is solely the responsibility of each controller's `stack`/`stacks` helper: [4](#0-3) 

The existing test fixture and test explicitly demonstrate the intended invariant for other controllers (a stack-scoped client sees only its own stack): [5](#0-4) [6](#0-5) 

But `CCMenuControllerTest` never exercises a stack-scoped client against a *different* `stack_id`, so this gap is untested: [7](#0-6) 

This is the direct analog of the "position NFT can be spammed" bug class: the report describes a binding that is authorized/checked for one entity (the position/NFT the caller is meant to act on) but the state actually mutated/read belongs to a different, unauthorized entity, because the authorization check and the actual target resolution diverge. Here, the equality that should hold — "the stack the ApiClient's scope authorizes" == "the stack the CCMenu action actually touches" — is broken by `CCMenuController#stack`.

### Impact Explanation
An attacker who obtains (legitimately, as an unprivileged normal user) an API client token scoped to one stack (e.g. their own team's stack, with only `read:stack` permission) can use that token to read the build/deploy status of any other stack tracked by the Shipit instance, including stacks belonging to repositories/teams they have no access to. This is an authorization-scope escape: `read:stack` + `stack_id` scoping was intended to be a hard boundary (per `BaseController#stacks`/`#stack`), but this endpoint silently drops the `stack_id` restriction. This matches the accepted High-impact category: "escalation into `Shipit.github_teams` authorization... or unauthenticated [cross-scope] read of stack state, task streams or deploy output" — here it is a scoped-token holder reading state outside their granted scope.

### Likelihood Explanation
High. No special privilege is required beyond possessing any valid, stack-scoped API token (which is a normal, low-privilege credential type explicitly supported by this engine, e.g. the `here_come_the_walrus` fixture). The attacker only needs to know or guess another stack's `to_param`/id and issue a single authenticated GET request; there is no rate limiting or additional check standing in the way.

### Recommendation
Change `CCMenuController#stack` to resolve the stack through the client-scoped `stacks` relation (as `BaseController#stack` does), e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` cannot resolve stacks outside its assigned `stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (e.g. equivalent to the `here_come_the_walrus` fixture).
2. Authenticate with that token's `authentication_token` via HTTP Basic Auth (or `?token=` query param, which `CCMenuController` explicitly supports).
3. Request `GET /stacks/:owner/:repo/:environment/ccmenu.xml` (or the equivalent `stack_id` route) for a different stack `B` that the token was never scoped to.
4. Observe `CCMenuController#show` renders `B`'s build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, etc.) successfully, because `stack` resolves `Stack.from_param!(params[:stack_id])` for `B` without ever checking `current_api_client.stack_id`. [8](#0-7)

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
