### Title
Cross-repository status forgery — `StatusHandler#process` writes a `status` webhook to every commit matching the raw SHA regardless of stack/repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and writes the incoming `context`/`state` to *all* matches, with no filter on the repository/organization that authenticated the webhook. Because `verify_signature` only proves the payload was signed by the secret configured for `repository_owner` (an org-level HMAC key, not tied to a specific repository), and `Commit#sha` is indexed only by `(stack_id, sha)` — not uniquely across the whole install — a status event legitimately signed for one onboarded organization/repository can silently overwrite the CI status of a same-SHA commit belonging to a different stack/repository.

### Finding Description
The broken binding is: **the commit(s) updated by a `status` event should equal only the commit(s) belonging to the repository that authenticated the event**, i.e. `Commit.where(sha:).stack.repository == payload.repository`. The code instead implements: `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` [1](#0-0) , which never consults `params.repository` or the stack's `Repository` to restrict the query.

Upstream, `WebhooksController#verify_signature` only checks that the raw payload is HMAC-signed with the webhook secret configured for `repository_owner` (an organization-level key from `Shipit.github_app_config`) [2](#0-1) ; it does not check that the specific `repository.full_name` in the payload matches any particular stack, nor that the `sha` actually belongs to that repository's stacks. The database index on `Commit` is `(stack_id, sha)`, so `sha` is not globally unique — two different stacks (potentially backed by two different `Repository` records/orgs) can each have a `Commit` row with the same SHA, e.g. when a repo is forked, mirrored, migrated/renamed, or when shared history exists between two onboarded repositories. `create_status_from_github!` then unconditionally creates a `Status` row on the matched commit and calls `add_status`, which recomputes `status`, fires `deployable_status`/`commit_status` hooks, and schedules `ProcessMergeRequestsJob` [3](#0-2) , directly affecting `deployable?`/merge eligibility of the victim commit.

Existing guards do not stop this: `drop_unhandled_event`/`check_if_ping` are unrelated; `ExplicitParameters` schema (`params do requires :sha ... end`) only validates types/presence, not repository scoping [4](#0-3) ; `verify_signature` authenticates the *sender org*, not the *target repository/stack*; and no model validation on `Status`/`Commit` cross-checks repository identity before writing.

### Impact Explanation
Any request that is validly signed for *some* organization/repository onboarded to this Shipit instance can flip the CI status (`context: ci/kubernetes`, `state: failure`) of a same-SHA commit in a completely different stack, altering that victim commit's aggregated `status`/`deployable?` and triggering `stack.schedule_merges` or blocking a required merge — this is a payload for one repository mutating another repository's stack/commit records, matching the "Critical" category explicitly listed (cross-repo/cross-tenant state manipulation). The blast radius covers every Shipit installation that manages more than one repository/stack sharing SHA space (forks, mirrors, monorepo splits, repo renames), and the write is repeatable per request with no rate limiting bypass needed.

### Likelihood Explanation
Exploitation requires the attacker to already have a repository/organization onboarded to the same Shipit instance and be able to produce (or have GitHub emit) a genuinely signed `status` webhook for that org, and requires a same-SHA collision with the victim commit — which is not automatic for arbitrary unrelated repositories owned by different, unrelated GitHub organizations, since `verify_signature` requires the correct per-organization `webhook_secret` in `Shipit.github_app_config`. Feasibility therefore depends heavily on deployment topology: it is straightforward within a single organization hosting multiple repositories/stacks (one shared webhook secret, shared or forked commit history), but not demonstrated as reachable across two organizations that don't share Shipit's trust and don't share git history. This is a real logic flaw in `StatusHandler#process`, but the "unprivileged attacker" framing in the question (owns an arbitrary repo, no relation to the victim's org) is not fully substantiated without further evidence that the target Shipit instance shares one webhook secret across the victim's and attacker's repositories, or that cross-org SHA collisions are achievable by the attacker.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository/stacks corresponding to the authenticated `repository_owner`/`repository.full_name` in the payload (e.g. join through `Stack`/`Repository` and filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { ... })` matching the payload's owner/name) rather than a bare `Commit.where(sha: ...)` scan across the whole database.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status for one repo's SHA does not affect another stack's commit with the same SHA" do
  victim_stack = shipit_stacks(:shipit) # requires ci/kubernetes in ci.require
  attacker_stack = Shipit::Stack.create!(repository: shipit_repositories(:other_repo), environment: 'attacker')

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'victim')
  Shipit::Status.create!(stack: victim_stack, commit: victim_commit, state: 'success', context: 'ci/kubernetes')

  attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'attacker')

  before_state = victim_commit.reload.state
  before_deployable = victim_commit.deployable?
  assert_equal 'success', before_state

  params = { 'sha' => shared_sha, 'state' => 'failure', 'context' => 'ci/kubernetes' }
  Shipit::Webhooks::Handlers::StatusHandler.new(params).call

  after_state = victim_commit.reload.state
  after_deployable = victim_commit.deployable?

  # Binding under test: attacker's own-repo status webhook must not change the victim's commit
  refute_equal before_state, after_state           # currently FAILS -> victim commit flips to 'failure'
  refute_equal before_deployable, after_deployable # currently FAILS -> deployability changes
end
```
Note: this PoC demonstrates the code-level flaw (no repository scoping in `StatusHandler#process`); confirming full unauthenticated cross-organization exploitability additionally requires verifying that `verify_signature`'s per-organization webhook secret is shared or bypassable across the attacker's and victim's repositories, which was not established from the code reviewed here.       github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
