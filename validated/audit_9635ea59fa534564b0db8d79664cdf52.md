### Title
`StatusHandler` updates every `Commit` row matching a sha across all repositories, not just the one that sent the webhook - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves commits with a bare `Commit.where(sha: params.sha)`, with no scoping to the repository or stack named in the webhook payload. Since `sha` is only enforced unique per `stack_id` (`index_commits_on_stack_id_and_sha`), a status webhook legitimately signed for one repository can flip the CI status of a `Commit` row belonging to a completely unrelated stack/tenant, provided the two commits share the same git sha.

### Finding Description
The broken binding: the code implicitly assumes `sha` uniquely identifies a commit tenant-wide, i.e. `Commit.find_by(sha: X).stack.repository == payload.repository`. In reality the DB schema only guarantees `(stack_id, sha)` uniqueness (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), so `sha == sha` across two different stacks does NOT imply `stack == stack` or `repository == repository`.

Code path:
- `WebhooksController#create` dispatches the parsed JSON payload to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) .
- `verify_signature` only checks that the payload is validly signed by *some* configured GitHub App organization matching `repository.owner.login` in the payload [2](#0-1) . It never checks that this organization/repository actually owns the commit sha being referenced.
- `StatusHandler#process` then runs: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This is a global, unscoped query across the entire `commits` table - it does not join through `stacks`/`repositories` to filter by `payload.dig('repository', 'full_name')`, unlike sibling handlers such as `CheckSuiteHandler`, which correctly scopes via `stacks.where(branch: ...)` derived from `Repository.from_github_repo_name(repository_name)` [4](#0-3)  and the base `Handler#stacks` helper [5](#0-4) .

Exploit flow: attacker owns/pushes to a repository under an organization that is legitimately registered with Shipit's GitHub App (`attacker-org`). They push a commit whose tree/parents/timestamps/message are copied verbatim from a known commit already tracked by Shipit under a *different* tenant's stack (e.g., a vendored open-source commit both repos happen to include) - this produces an identical git sha without needing an actual SHA-1 collision. GitHub then delivers (or the attacker replays with a validly-signed) a `status` event for that sha from `attacker-org`'s installation. `verify_signature` passes because the signature is valid for `attacker-org`'s own webhook secret. `StatusHandler#process` then updates **every** `Commit` row in the database sharing that sha, including the victim tenant's row, corrupting its CI/status state (`commit.status`, gating deploys/merges that key off status).

Existing guards do not stop this: `verify_signature` authenticates the *organization*, not the *commit ownership*; `ExplicitParameters` only validates payload shape, not repository scoping; there is no `require_permission!`/`stacks` filter applied inside `StatusHandler`.

### Impact Explanation
A payload legitimately signed for one repository/organization mutates a `Commit` row (and its `statuses`) belonging to a different, unrelated repository's stack — this is a cross-tenant write not authenticated for that tenant, matching "a payload for one repository mutating another's stack/commit/task" (Critical). Corrupted commit status can be leveraged to unblock a merge or deploy gated on required/blocking statuses. It is repeatable against any sha collision the attacker can arrange (shared vendored/cherry-picked commits are common), against any stack that happens to track that sha.

### Likelihood Explanation
Requires: (1) the attacker controls a repository under a GitHub organization/App already configured in Shipit (`Shipit.github(organization:)` must resolve, i.e. `GithubOrganizationUnknown` not raised), (2) some victim stack already tracks a `Commit` with an identical sha (realistic via shared vendored commits/cherry-picks/forked history, not requiring true hash collision), and (3) the attacker can get a validly-signed `status` webhook delivered for that sha (naturally, via GitHub itself, by pushing/tagging that commit into their own repo which has the app installed). No secrets, sessions, or elevated roles are needed beyond normal push access to an org-linked repo already known to Shipit.

### Recommendation
Scope `StatusHandler#process` to the repository named in the webhook payload, mirroring `Handler#stacks`/`CheckSuiteHandler`, e.g. resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and only update commits belonging to that repository's stacks (`stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`), instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status event does not update commits belonging to a different repository's stack" do
  attacker_stack = shipit_stacks(:shipit) # repository X
  victim_stack   = create_stack_with_repository('victim/repo') # repository Y, different repo
  shared_sha = 'deadbeef' * 5

  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/repo', 'owner' => { 'login' => 'attacker-org' } },
    'branches' => [{ 'name' => attacker_stack.branch }]
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal 'success', attacker_commit.reload.status
  assert_not_equal 'success', victim_commit.reload.status # currently FAILS: both flip
end
```
Before the fix both assertions on `attacker_commit` and `victim_commit` succeed identically (both flip to `success`), proving the binding `sha == sha` was wrongly treated as `repository == repository`.
