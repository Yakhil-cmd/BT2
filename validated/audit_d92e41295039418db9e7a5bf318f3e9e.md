Confirmed: `Shipit.github(organization:)` supports a multi-org config schema where each organization key in `secrets.github` has its own independent `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which app/secret to verify the HMAC against using `repository_owner`, which is read straight from the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`) — not from the raw signed bytes' association with any specific tenant record [2](#0-1) . Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#stacks` looks up the target `Repository`/`Stack` using a **different** field from the same body: `payload.dig('repository', 'full_name')` [3](#0-2) . `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack [4](#0-3) , which enqueues `GithubSyncJob`, causing Shipit to fetch commits and cache the deploy spec for that stack using the organization's own GitHub credentials [5](#0-4) [6](#0-5) .

### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while the handler acts on the unrelated `repository.full_name` field, allowing cross-tenant webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The binding the signature is supposed to protect — "the organization whose secret authenticated this HMAC" == "the repository the handler will act on" — is broken because two different attacker-controlled JSON fields are used for these two purposes.

### Finding Description
`verify_signature` derives the org used to pick the verification secret from `repository_owner`, itself `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [7](#0-6) . This is the only piece of the payload consulted to decide which `GitHubApp`/`webhook_secret` (per-org config from `secrets.github`) validates the HMAC [1](#0-0) . The HMAC itself only proves "whoever built this exact byte string knew organization `owner_login`'s secret" — it says nothing about which repository the handler subsequently targets, because handlers resolve their target stack from `repository.full_name`, a sibling JSON field never covered by the signature-selection logic [3](#0-2) .

Any principal who legitimately administers an organization/repository already onboarded to this Shipit instance (and therefore can trigger, or otherwise learn/replay, a real signed webhook delivery for that org) can freely construct a JSON body where `repository.owner.login` remains their own org (so `verify_signature` selects and validates against their own known secret) while `repository.full_name` is set to `victim-org/victim-repo`. This is the Queue-`remove` bug class analog: like `contains(...)` returning stale `True` for state that was supposed to have been fully invalidated, here the "authenticated organization" binding is treated as still valid for a repository reference that was never actually checked against that authentication.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" boundary called out in the rules. With a forged `push` event whose `full_name` targets a victim's stack, an attacker triggers `PushHandler#process` → `stack.sync_github(expected_head_sha: ...)` → `GithubSyncJob` against a stack they do not own [4](#0-3) [5](#0-4) . This causes Shipit to sync commit state using its own privileged GitHub credentials against a repository the attacker doesn't control, and other handlers (`status`, `check_suite`, `membership`, `pull_request`) similarly resolve their target via `repository.full_name`/`sender.login` independent of the org used for signature verification. This can lead to unauthorized state changes on stacks/tasks belonging to other tenants of the same Shipit instance (e.g., spurious syncs, membership/team/user creation) — a cross-repository write performed without the attacked repository's own webhook authorization.

### Likelihood Explanation
Requires the attacker to be an unprivileged external actor with respect to the victim, but a legitimate/authenticated administrator of some other organization already configured in the same multi-tenant Shipit deployment (a normal, low-privilege position for a shared Shipit instance) — no session, `ApiClient` token, or GitHub App private key for the victim organization is needed. All that's required is knowledge of one's own org's webhook secret, which is inherent to being an onboarded tenant. This is realistic in the documented multi-org (`per-organization webhook_secret`) configuration mode.

### Recommendation
Verify the webhook signature against the secret for the organization actually associated with the repository the handler will operate on, and cross-check that `repository.owner.login`/`organization.login` used for signature selection is consistent with `repository.full_name` used by the handler (reject the request if they disagree). Alternatively, resolve the target `Repository` first, verify the signature using that repository's own organization/secret, and only then dispatch to handlers — never let two independent fields of the same unauthenticated payload pick "authenticator" and "target" separately.

### Proof of Concept
1. Shipit is configured with multi-org GitHub config: org `attacker-org` (attacker-administered, real webhook secret known/derivable to attacker) and org `victim-org` (containing a tracked stack for `victim-org/victim-repo`).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `Shipit.github(organization: 'attacker-org')`, and the HMAC validates successfully [8](#0-7) .
5. `PushHandler.call(params)` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')`, matching the victim's stack, and calls `stack.sync_github(expected_head_sha: params.after)`, enqueuing `GithubSyncJob` for the victim's stack [4](#0-3) , even though the victim organization never issued or authorized this webhook.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post

      head(422) unless verified

      Rails.logger.info([

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
