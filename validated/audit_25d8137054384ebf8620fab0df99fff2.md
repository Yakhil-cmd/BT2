### Title
`OpenedHandler#provision?` ignores `repository.review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors due to `&&`/`||` precedence - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`PullRequest::OpenedHandler#provision?` only applies the `repository.review_stacks_enabled` guard to the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches are evaluated unconditionally due to Ruby's `&&`/`||` precedence. An unprivileged PR author can therefore trigger creation of a `Shipit::ReviewStack` even when the repository has review stacks explicitly disabled, as long as `provisioning_behavior` is `allow_with_label` (with the label applied) or `prevent_with_label` (without the label).

### Finding Description
The claimed broken binding is: `repository.review_stacks_enabled == false` at the repository **should imply** no `ReviewStack` is ever created for that repository, for any `provisioning_behavior`.

The actual code in `provision?` is:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as three independent `||`-joined terms:
- `term1 = repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?`
- `term2 = repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?`
- `term3 = repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?`

`review_stacks_enabled` only appears in `term1`. If `review_stacks_enabled == false` but `provisioning_behavior == :allow_with_label` and the PR carries the label matching `repository.provisioning_label_name`, `term2` evaluates to `true` independent of `review_stacks_enabled`, so `provision?` returns `true`.

`respond_to_pull_request_opened?` then returns `true` for the `"opened"` action [2](#0-1) , and `process` calls `ReviewStackAdapter#find_or_create!`, which calls `create!`, persisting a new `Shipit::ReviewStack` (a `Shipit::Stack` subclass), building its `PullRequest`, and enqueueing it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [3](#0-2) .

Attacker exploit path: a GitHub user with permission to open a PR against the target repository (any user on a public repo, or a fork-based PR) opens a PR and applies (or the repo's webhook payload includes) a label whose name equals `repository.provisioning_label_name`. GitHub sends a genuine, correctly-signed `pull_request` "opened" webhook (attacker does not need any Shipit secret — the webhook signature is real GitHub-issued). This reaches `OpenedHandler#process`, `provision?` incorrectly returns `true`, and a `ReviewStack`/`Stack` row is created and queued for provisioning with `branch: params.pull_request.head.ref` pointed at the attacker's own branch [4](#0-3) .

Existing guards do not prevent this: webhook signature verification only authenticates that GitHub sent the payload, not that the payload should trigger provisioning; `ExplicitParameters` validates payload shape, not business logic; `NullRepository` only matters for untracked repos. None of these touch the `provision?` precedence bug.

Downstream, the actual provisioning step in `ReviewStackProvisioningQueue#provision` separately consults `stack.provisioner.provision?` (a `ProvisioningHandler`, distinct method) before invoking `stack.provision` [5](#0-4) , which was not verified within this scope to also gate on `review_stacks_enabled`. Regardless, the question's stated scoped impact — an unauthorized `Shipit::Stack` record being created for a repository with review stacks disabled — is confirmed at the `OpenedHandler`/`ReviewStackAdapter` layer, matching the `assert_difference -> { Shipit::Stack.count }` proof idea.

### Impact Explanation
An unprivileged PR author can force creation of a `Shipit::ReviewStack` (with associated `PullRequest` record) for a repository whose operator explicitly disabled review stacks (`review_stacks_enabled = false`), as long as `provisioning_behavior` is `allow_with_label` (attacker applies the label) or `prevent_with_label` (attacker simply omits the label, which is the default state of any new PR). The created stack tracks the attacker's own branch (`head.ref`) and is queued for provisioning, which can lead to a deploy/build pipeline running against attacker-controlled branch content if the downstream provisioner does not independently re-check `review_stacks_enabled`. This is repeatable per PR/branch and scoped to any repository configured with `allow_with_label`/`prevent_with_label` and `review_stacks_enabled = false` — a plausible operator configuration (e.g., a repo temporarily paused for review stacks but still using label-based rules). This matches the Critical category of "an unauthorized deploy... of attacker-controlled code."

### Likelihood Explanation
Preconditions: target repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` and `review_stacks_enabled = false`. No Shipit credentials, session, or team membership are required — only the ability to open a PR (and, for `allow_with_label`, apply a label matching `provisioning_label_name`, which any PR author or a maintainer collaborator could do, or which could already be present via repo-configured auto-labeling). For `prevent_with_label`, no label action is even needed — the default absence of the label already satisfies `term3`. This makes the `prevent_with_label` + `review_stacks_enabled=false` combination trivially exploitable on every "opened" PR. Feasibility is high and cost is a single PR open.

### Recommendation
Explicitly parenthesize the guard so `review_stacks_enabled` gates all three branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the identical fix to any sibling handlers with the same pattern (e.g., `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`) if they share this logic.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks when review_stacks_enabled is false, even with allow_with_label + matching label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "does not create stacks when review_stacks_enabled is false, with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Both assertions currently fail (a `Stack` is created) against the unpatched `provision?`, and pass once the parenthesization fix is applied — demonstrating `repository.review_stacks_enabled == false` no longer implies "no `ReviewStack` created."
