### Title
Webhook signature is verified against the organization named in `repository.owner.login`/`organization.login`, but the handlers act on a repository/commit selected from a *different, unchecked* payload field — allowing a webhook signed by one organization to write to another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` derives which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against from `params.dig('repository', 'owner', 'login')` (or `organization.login`) taken from the *unverified* JSON body itself. [1](#0-0) [2](#0-1) 

Once the signature check passes, the actual event handlers select which record to mutate using a *different* field of the same body, without re-checking that it belongs to the organization that authenticated:
- `Handler#stacks` resolves the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`, independent of `repository.owner.login`. [3](#0-2) 
- `StatusHandler#process` doesn't even use the repository at all — it matches `Commit.where(sha: params.sha)` globally across every stack/repository in the installation. [4](#0-3) 
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the (attacker-chosen) `full_name`/branch. [5](#0-4) 

Shipit explicitly supports multiple independent GitHub App/organization configurations, each with its own `webhook_secret`, in a single install: [6](#0-5) 

### Finding Description
The binding the code implicitly assumes is: *organization that authenticated the request* (via `repository_owner` used to pick the `webhook_secret`) `==` *repository/commit that gets acted upon* (via `repository.full_name` / `Commit.sha`). This equality is never enforced.

Before the attacker's request: the webhook secret for organization A only ever signs requests describing organization A's own events, because A only ever sends its own webhooks.

After the attacker's request: an operator who legitimately controls organization A's GitHub App/webhook secret (a supported, documented multi-org Shipit configuration) can POST directly to `/webhooks` with:
- `X-Github-Event: push` (or `status`)
- `X-Hub-Signature` computed with organization A's own known `webhook_secret` over a crafted JSON body
- `repository.owner.login` = `"org-a"` (so `verify_signature` fetches and validates against org A's config, and it passes)
- `repository.full_name` = `"victim-org/victim-repo"` and `ref`/`after` pointing at a commit in a *victim* stack (for `push`), or `sha` set to a known commit SHA belonging to any stack (for `status`)

`verify_webhook_signature` only checks that the raw body was signed with *some* organization's configured secret — it never checks that the signing organization matches the repository the payload claims to describe. [7](#0-6) 

### Impact Explanation
- Via the `push` event, an attacker can force `GithubSyncJob`/`sync_github` to run against any tracked stack belonging to a different organization, and on stacks configured for continuous deployment this drives the normal deploy pipeline off attacker-chosen `expected_head_sha`, effectively triggering deploy/rollback activity the attacker does not have any GitHub permission over.
- Via the `status` event, `StatusHandler` writes a CI/commit status (`state`, `context`, `description`) for **any commit SHA in the entire installation**, with no repository scoping check at all. Since CI status is used by Shipit to gate merges/deploys (required contexts), an attacker in control of only their own organization's webhook secret can mark required checks "success" for a commit in a repository/organization they have no access to, enabling an unauthorized deploy of that commit.
- This is a cross-organization/cross-repository write achieved purely through the webhook endpoint, without needing an `ApiClient` token, a Shipit session, or write access to the victim's GitHub repository — satisfying the "unauthorized deploy/rollback" and "cross-repository writes" Critical impact criteria.

### Likelihood Explanation
Any party that legitimately administers one organization/installation registered in Shipit's multi-org `github:` configuration (a supported, documented setup) already possesses that organization's `webhook_secret` and can freely craft and sign arbitrary JSON bodies. No interaction with the victim organization, no compromise of TLS, and no privileged Shipit account is required — only knowledge of the Shipit `/webhooks` endpoint URL and the attacker's own webhook secret, both of which the attacker is entitled to have for their own configured organization.

### Recommendation
After locating the GitHub App configuration via `repository_owner`, cross-check that the same configuration's organization matches every place a repository/commit is subsequently derived from the payload (`repository.full_name`'s owner segment) before dispatching to handlers. `StatusHandler` should additionally scope `Commit.where(sha:)` lookups to stacks belonging to the authenticated organization, e.g. by joining through `Repository`/`Stack` filtered on `repository_owner`, instead of matching bare SHA values installation-wide.

### Proof of Concept
1. Configure two organizations in Shipit per `docs/setup.md`'s multi-org example: `victim-org` (tracked stack `victim-org/victim-repo`) and `attacker-org` (attacker's own installation, attacker knows `attacker-org`'s `webhook_secret`).
2. Attacker crafts:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<known victim commit sha>",
  "state": "success",
  "context": "required-ci-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"` from the body, fetches `Shipit.github(organization: "attacker-org")`, and the signature validates successfully. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit (any stack, no ownership check), and calls `commit.create_status_from_github!`, injecting a forged "success" status onto a commit the attacker never had permission over. [4](#0-3)

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
