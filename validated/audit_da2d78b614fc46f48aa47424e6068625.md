### Title
Cross-user unauthorized deletion of a pending shared-address (multisig) definition via `reject_new_shared_address` device message - ([File: wallet.js])

### Summary
The `wallet.js` device-message handler for the `reject_new_shared_address` subject deletes an entire pending multisig ("shared address") negotiation by `address_definition_template_chash` without verifying that the sending device (`from_address`) is actually one of the invited cosigners for that specific negotiation. This mirrors the Kimai favorite-endpoint flaw: an authenticated peer supplies an object identifier belonging to a shared resource among multiple parties, and the backend performs a destructive state change referencing that identifier without checking that the caller is authorized to act on it.

### Finding Description
When a device wants to abandon a proposed multi-cosigner ("shared") address, it sends a `reject_new_shared_address` message. The handler in `wallet.js` only validates that `body.address_definition_template_chash` looks like a valid address/hash, then immediately deletes the pending offer: [1](#0-0) 

```
case "reject_new_shared_address":
    // {address_definition_template_chash: "BASE32"}
    if (!ValidationUtils.isValidAddress(body.address_definition_template_chash))
        return callbacks.ifError("invalid addr def c-hash");
    walletDefinedByAddresses.deletePendingSharedAddress(body.address_definition_template_chash);
    callbacks.ifOk();
    break;
```

Note that `from_address` (the device address derived from the verified sender pubkey) is **not** passed into `deletePendingSharedAddress`, and the underlying function performs an unconditional delete keyed only by the chash: [2](#0-1) 

```
function deletePendingSharedAddress(address_definition_template_chash){
	db.query("DELETE FROM pending_shared_address_signing_paths WHERE definition_template_chash=?", [address_definition_template_chash], function(){
		db.query("DELETE FROM pending_shared_addresses WHERE definition_template_chash=?", [address_definition_template_chash], function(){});
	});
}
```

This is in stark contrast to the sibling handler `approve_new_shared_address`, whose backing function `approvePendingSharedAddress` scopes its `UPDATE` with `WHERE device_address=?` bound to `from_address`, so a device can only mutate its own row: [3](#0-2) 

It is also inconsistent with the analogous `cancel_new_wallet` handler for keys-based wallets, which passes `from_address` into `deleteWallet` and that function explicitly checks that the rejecting device is a registered member of the wallet before deleting anything: [4](#0-3) [5](#0-4) 

Thus `reject_new_shared_address` is the odd one out: it deletes `pending_shared_addresses` and all `pending_shared_address_signing_paths` rows for the given `definition_template_chash` regardless of who is sending the message, as long as the sender is any paired correspondent device of the local node. Any correspondent that learns (or is later told, or reuses from a prior unrelated flow) a `definition_template_chash` can destroy a shared-address negotiation between other cosigners that they are not a party to, without the consent of the legitimate participants.

### Impact Explanation
This breaks the intended cooperative multi-party workflow for constructing shared (multisig) addresses (`wallet_defined_by_addresses.js`, used for shared wallets, arbiter/prosaic contract shared addresses, etc.). A correspondent device with no relationship to a specific pending negotiation can silently wipe it out mid-flight, denying the legitimate cosigners the ability to complete creation of the intended multisig address definition and forcing the initiating parties to restart the negotiation — a cross-user business-state tampering analogous to Kimai's improper-authorization bug, where referencing another user's resource identifier allowed unauthorized mutation of shared state (add/remove favorite) without an ownership check.

### Likelihood Explanation
Exploitation requires only that the attacker be a paired correspondent device of the victim node (a normal, low-privilege trust relationship established via pairing, not administrative access) and know or guess the `definition_template_chash` value (which is a deterministic hash derived from the address definition template and is transmitted in plaintext device messages such as `create_new_shared_address`/`new_shared_address` to all participants, and could be replayed/observed by any correspondent who has previously interacted in any shared-address flow, or supplied by a malicious cosigner who is a party to the negotiation but exploits the missing check to affect other rows sharing the same chash format). No cryptographic proof of participation is required, only knowledge of the identifier.

### Recommendation
Require the handler to verify that `from_address` is one of the device addresses registered in `pending_shared_address_signing_paths` for the given `definition_template_chash` before performing any deletion, mirroring the pattern used in `approvePendingSharedAddress` (scope the `DELETE` with `AND device_address=?`) or, if a single rejection should cancel the whole negotiation, require the rejecting device to be validated as a registered participant first (as `deleteWallet` does for `cancel_new_wallet`), and only then cascade the deletion.

### Proof of Concept
1. Device A initiates a shared-address creation involving cosigners B and C (`createNewSharedAddressByTemplate` → `pending_shared_addresses` / `pending_shared_address_signing_paths` rows keyed by `definition_template_chash`), and sends the offer to B and C via `create_new_shared_address` (which necessarily includes the address definition template, from which `definition_template_chash` is deterministically computable, `objectHash.getChash160(arrAddressDefinitionTemplate)`).
2. Attacker device M, who is only a generic paired correspondent of A (not a participant in this negotiation, e.g., learned the chash by observing an earlier `create_new_shared_address`/`new_shared_address` message sent to some other party, or simply reusing a chash from a template it once saw), sends A a `hub/message` with subject `reject_new_shared_address` and `body.address_definition_template_chash` equal to the target chash.
3. On A's node, `handleMessageFromHub` dispatches to `wallet.js`'s `reject_new_shared_address` case, which calls `walletDefinedByAddresses.deletePendingSharedAddress(chash)` unconditionally, deleting the `pending_shared_addresses` row and all `pending_shared_address_signing_paths` rows for that chash — regardless that M was never a party to the negotiation.
4. B and C's approvals (if already recorded) and the whole pending negotiation are destroyed on A's node without A, B, or C's consent, forcing the legitimate parties to restart shared-address creation.
