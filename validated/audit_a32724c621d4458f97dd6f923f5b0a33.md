### Title
Cross-organization forged commit status via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` in the *unverified* JSON body, and only proves that the request was signed by *some* configured organization's `webhook_secret`. `StatusHandler#process`, which handles the resulting `status` event, then looks up the target `Commit` purely `Commit.where(sha: params.sha)` with no scoping to the repository/stack that authenticated the request. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` resolves the app config from the attacker-controlled `repository.owner.login`/`organization.login` field and only checks the signature against that organization's `webhook_secret`: [1](#0-0) 

Once verified, `WebhooksController#create` dispatches the whole (still fully attacker-controlled) JSON payload to the registered handler for the event, with no re-derivation or enforcement that the payload's other fields belong to the authenticating organization: [2](#0-1) 

For the `status` event, `StatusHandler#process` resolves the target record purely by commit SHA, globally, across the entire `commits` table — it never joins/filters by `stack`, `repository`, or the `repository.full_name` present in the same payload: [3](#0-2) 

Compare this to other handlers (e.g. `AssignedHandler`, `EditedHandler`), which explicitly scope lookups through `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any record: [4](#0-3) 

Shipit explicitly supports multiple, independently configured GitHub organizations sharing one instance, each with its own `webhook_secret`: [5](#0-4) 

Since SHA-1 commit hashes are globally unique content identifiers (not namespaced per repository in Shipit's DB), an org that legitimately owns a webhook secret for its own onboarded repository can compute a valid `X-Hub-Signature` for its own org, but embed a `sha` value belonging to a commit tracked under a completely different organization's stack. `StatusHandler` will happily attach the forged status to that foreign commit.

**Binding broken**: organization authenticated by `verify_signature` (`repository.owner.login`/`organization.login` ⇒ matching `webhook_secret`) ≠ repository/stack whose commit is mutated by `StatusHandler` (`Commit.where(sha:)`, unscoped).

### Impact Explanation
`Commit#create_status_from_github!` feeds directly into `Status::Group`/`add_status`, which drives `Commit#deployable?` (`success? && !blocked?`) and `Commit#blocked?`/`blocking_statuses`, and also triggers `stack.schedule_merges` on success: [6](#0-5) [7](#0-6) 

An attacker who legitimately controls one onboarded organization's webhook secret (an unprivileged attacker with respect to *other* organizations/stacks hosted on the same Shipit instance) can forge a "success" CI status for a commit belonging to a victim organization's stack, satisfying CI requirements and unblocking `continuous_deployment?`/merge queue processing for a repository they have no legitimate access to — this can result in an unauthorized deploy or merge, matching the "unauthorized deploy" High/Critical impact bucket.

### Likelihood Explanation
Requires only that the attacker already has a valid `webhook_secret` for any organization configured on the shared Shipit instance (a documented, supported multi-tenant configuration) plus knowledge of a target commit SHA (obtainable from public GitHub activity, PRs, or the Shipit UI itself, which is not gated per-organization). No repository write access, Shipit session, or `ApiClient` token is needed — only the ability to send an HTTP POST with a correctly signed body using credentials the attacker legitimately possesses for their own org.

### Recommendation
In `StatusHandler` (and any other handler resolving records solely by content-derived fields like `sha`), scope the lookup through the repository identified in the payload and the organization that authenticated the request, e.g. `stacks.commits.where(sha: params.sha)` using the `repository_name`/`stacks` helper already available on `Handler`, and additionally verify that `params.repository.full_name`'s owner matches the organization used in `verify_signature`.

### Proof of Concept
1. Shipit instance hosts two orgs, `attacker-org` and `victim-org`, each with independent `webhook_secret`s (per `config/secrets.development.example.yml` multi-org format).
2. Victim org has a stack with a tracked commit `sha = abcdef123...` currently pending/unsuccessful CI.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org webhook_secret, body)` for a `status` event JSON body:
```json
{
  "sha": "abcdef123...",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, verifies successfully against attacker's own secret. [8](#0-7) 
5. `StatusHandler#process` runs `Commit.where(sha: "abcdef123...")`, finds the victim's commit (regardless of the `attacker-org/some-repo` repository field), and calls `commit.create_status_from_github!(params)`, injecting a forged "success" status onto the victim's commit. [3](#0-2) 
6. If the victim stack is `continuous_deployment?` and this was the last blocking status, `schedule_continuous_delivery`/`schedule_merges` proceeds, resulting in an unauthorized deploy/merge triggered by a party outside the victim organization.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
```
