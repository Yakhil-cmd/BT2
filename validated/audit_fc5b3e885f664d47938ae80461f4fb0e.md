### Title
`StatusHandler#process` writes GitHub commit statuses by bare SHA across all repositories, letting an attacker flip a victim production stack's required context - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` [1](#0-0) , which has no repository/stack scoping at all. Because `verify_signature` in `WebhooksController` only checks that the payload was signed for the *organization derived from the payload's own `repository.owner.login`* [2](#0-1) , it never restricts which `Commit` rows in the database the handler is allowed to touch — the handler operates purely on the bare `sha` string, independent of which repository authenticated the webhook.

### Finding Description
The broken binding is:

`authenticated_repository(webhook) == repository_of(commit_rows_mutated_by(webhook))`

`verify_signature` only proves the request was signed by the GitHub App/secret belonging to `repository_owner = params.dig('repository','owner','login')` [3](#0-2) . It does **not** bind the `context`/`sha` values inside the JSON body to that same repository. `StatusHandler#process` then does:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This is a global, cross-tenant query — any `Commit` record in the entire installation whose `sha` matches the attacker-supplied value will have a status written to it, regardless of which stack/repository it belongs to. `create_status_from_github!` then calls `add_status`, which recomputes `status`/`deployable?` and can trigger `stack.schedule_merges` on success [4](#0-3) , and `deployable?` is defined purely from `success?`/`blocked?`/`locked?` with no repository check [5](#0-4) .

Exploit flow: an attacker who owns/controls any repository whose commit history shares a SHA with a victim's production stack (e.g., a shared upstream commit that exists identically in the attacker's fork and the victim's tracked branch before any rebase, or any other means of producing a real commit object with an identical SHA to one already recorded for the victim stack) sends a legitimate, properly-signed `status` webhook from their own GitHub repository with `context: deploy/production`, `state: success`. `verify_signature` passes because the webhook is genuinely signed for the attacker's own org/repo. `StatusHandler#process`, however, updates **every** `Commit` row with that SHA — including the victim's, in a different stack/repository — flipping `deploy/production` to success for the victim's commit, which can unblock deploy or trigger merges for the victim's production stack.

None of the existing guards prevent this: `verify_signature` authenticates the sender's org, not the target rows; `ExplicitParameters` in `StatusHandler` only validates types (`sha`, `state`, `context` are plain strings) [6](#0-5) , with no repository binding; and there is no `stack.github_repo_name == params.dig('repository','full_name')` check anywhere in the handler.

### Impact Explanation
An attacker can force a `success` status on `deploy/production` for a victim's commit in a stack they do not own or authenticate for, potentially unblocking `deployable?` and triggering `stack.schedule_merges` for that victim stack — i.e., an unauthorized deploy/merge trigger for a repository that did not authenticate the webhook. This matches "Critical - a payload for one repository mutating another's stack/commit... or an unauthorized deploy, rollback or merge." Blast radius: every stack across every tenant hosted by the same Shipit instance whose commits table happens to contain a SHA the attacker can also produce in a repo they control.

### Likelihood Explanation
The attacker needs no Shipit credentials — only the ability to own a GitHub repository and send its normal status webhooks (which GitHub does automatically/via API for any repo owner). The limiting precondition is producing (or naturally sharing) an identical commit SHA between the attacker-owned repo and the victim's tracked stack, which requires either a genuinely shared commit object (fork before divergence, vendored/subtree code, shared submodule commit) or another means of engineering a SHA collision; this is a real but non-trivial precondition, not a purely theoretical one, since forks/mirrors commonly share unmodified commits with upstream. The underlying code defect (unscoped `Commit.where(sha:)`) itself is unconditional and 100% reproducible once a shared SHA exists.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and similarly in `CheckRunHandler` if it has the same pattern) to the repository that authenticated the webhook, e.g. join through `stack` and filter by `stack.repository.owner/name == params.dig('repository','full_name')`, or pass the authenticated repository from the controller into the handler and require `commit.stack.github_repo_name == repository_full_name` before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` (attacker-controlled, arbitrary repo) and `stack_b` (victim, production environment, `required_status_contexts` including `deploy/production`).
2. Create `commit_b` under `stack_b` with a given `sha` (e.g. `"deadbeef" * 5`) and no existing `deploy/production` status (`commit_b.deployable?` == `false`).
3. Create `commit_a` under `stack_a` with the **same** `sha` value (simulating a shared/forked commit).
4. Build a `status` webhook payload: `{ sha: <same sha>, state: 'success', context: 'deploy/production', repository: { owner: { login: stack_a.repository owner }, full_name: stack_a.repository.full_name } }`.
5. Call `StatusHandler.new.call(payload)` directly (bypassing controller since signature verification is orthogonal and already scoped to `stack_a`'s org).
6. Assert: `commit_b.reload.deployable?` changed from `false` to `true` even though the webhook was only signed/authenticated for `stack_a`'s repository — i.e. `authenticated_repository == stack_a.repository.full_name` but `mutated_commit.stack.repository.full_name == stack_b.repository.full_name`, proving the two sides of the binding diverge.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
