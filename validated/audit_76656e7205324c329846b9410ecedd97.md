### Title
Fork PR labels (uppercased) can override `BUNDLE_GEMFILE` and any other command environment variable via `ReviewStack#env` - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` takes every label name on the associated pull request, uppercases it, and merges it into the stack's environment hash with no allowlist. This hash is later merged directly into `Command#unbundled_env`, which layers `@env` on top of `BASE_ENV` (the Bundler-cleaned base env) without filtering any key, so a PR author can override `BUNDLE_GEMFILE` (or any other env var) for every command Shipit runs against that review stack, including dependency/bundler steps.

### Finding Description
The broken binding: the command environment passed to `PTY.spawn` should equal `BASE_ENV.merge(host_or_repo_defined_vars)`, i.e. only variables the repository maintainer or Shipit config define. Instead it equals `BASE_ENV.merge(pull_request.labels.map(&:upcase) => "true")`, i.e. attacker-controlled keys from an unprivileged pull request.

Code path:
1. `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim from the webhook body onto `pull_request.labels` with no allowlist of label names. [1](#0-0) 
2. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the stack's env, unconditionally, for any key name. [2](#0-1) 
3. `Command#unbundled_env` merges `@env.stringify_keys` (which includes the ReviewStack's merged label-derived hash) over `BASE_ENV` (Bundler's cleaned environment) with no key filtering. [3](#0-2) [4](#0-3) 
4. `Command#start` spawns the process with this merged environment via `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`. [5](#0-4) 

Exploit flow: an attacker opens a PR from their fork and adds a label literally named `bundle_gemfile` (case-insensitive, since it is uppercased) to their own PR. `LabelCapturingHandler` records this label on the `PullRequest` record with no restriction on name. On every subsequent command execution for that review stack (dependency install, deploy steps, etc.), `ReviewStack#env` injects `BUNDLE_GEMFILE=true` into the spawned process's environment, overriding whatever Bundler/Shipit would otherwise use. Because the value merged is the literal string `"true"` (not an arbitrary attacker string), the attacker additionally places a file named `true` at the repository root of their fork branch (which they fully control, since the review stack checks out the fork's branch) containing a malicious Gemfile (Ruby code evaluated by Bundler on `bundle` invocation). When Bundler resolves `BUNDLE_GEMFILE=true` relative to the checkout directory, it will load and evaluate that attacker file, achieving code execution on the deploy host.

No existing guard prevents this: `capture_labels` has no allowlist on label names, `ReviewStack#env` has no key filtering/allowlist (unlike `EnvironmentVariables#permit`, which is only applied to `deploy_variables`/`rollback_variables` via `filter_deploy_envs`/`filter_rollback_envs` in `app/models/shipit/deploy_spec.rb`, not to the label-derived hash), and `Command#unbundled_env` performs an unconditional hash merge with no denylist of sensitive variable names such as `BUNDLE_GEMFILE`.

### Impact Explanation
Any unprivileged GitHub user who can open a pull request against a repository with review stacks enabled can inject arbitrary environment-variable **names** (fixed value `"true"`) into every command run for that review stack. Combined with control over their own fork's file tree, this allows redirecting `BUNDLE_GEMFILE` to an attacker-supplied Gemfile whose Ruby code executes on the Shipit deploy host during dependency/bundler steps — Remote Code Execution on the deploy host, matching the Critical impact category (RCE via `Command`/`PTY.spawn`). The blast radius is scoped to the review stack of the attacker's own PR/branch (their own checkout), but that checkout runs with the host's privileges/credentials (e.g. `GITHUB_TOKEN`), so secrets available to the deploy process could also be exfiltrated from within the executed Gemfile code.

### Likelihood Explanation
Preconditions: the target repository must have review stacks (PR-based stacks) enabled; the label-name injection itself requires no special repository configuration beyond that feature being on. The attacker only needs to open a PR from a fork and add a label to it — a capability given to any GitHub user who can open PRs and label their own PR (label creation on one's own PR is typically permitted by default GitHub repo permissions, or the attacker can pre-create/apply labels they have access to). This costs nothing beyond opening a PR and is trivially repeatable on every commit/run of that review stack.

### Recommendation
- In `ReviewStack#env` (app/models/shipit/review_stack.rb), stop deriving arbitrary environment variable keys from PR label names entirely, or restrict them to a strict allowlist/prefix (e.g. only allow keys prefixed with something like `LABEL_`) and reject any label that collides with reserved/sensitive names (`BUNDLE_GEMFILE`, `LD_PRELOAD`, `RUBYOPT`, `PATH`, `GEM_HOME`, etc.).
- In `Command#unbundled_env` (lib/shipit/command.rb), apply a denylist/allowlist filter before merging `@env` over `BASE_ENV`, disallowing overriding of Bundler/interpreter-control variables from any environment source that isn't explicitly configured by the repository owner (i.e., not derived from webhook-controlled data).
- Apply the same `EnvironmentVariables#permit` mechanism already used for `deploy_variables`/`rollback_variables` to the label-derived environment before merging.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (conceptual)
test "PR labels cannot override BUNDLE_GEMFILE in the spawned command environment" do
  stack = shipit_review_stacks(:review_stack)
  pull_request = stack.pull_request
  pull_request.update!(labels: ["bundle_gemfile"])

  env = stack.env
  # Broken binding: attacker-controlled label overrides BUNDLE_GEMFILE
  assert_equal "true", env["BUNDLE_GEMFILE"]

  command = Shipit::Command.new("bundle", "install", chdir: Dir.mktmpdir, env: env)
  spawned_env = command.unbundled_env
  # This should NOT contain an attacker-controlled BUNDLE_GEMFILE
  assert_equal "true", spawned_env["BUNDLE_GEMFILE"]
end
```
This demonstrates that `env["BUNDLE_GEMFILE"]` and `command.unbundled_env["BUNDLE_GEMFILE"]` are set from the PR label with no allowlist, violating the invariant that the `machine.environment`/command execution phase should inherit no fork-controllable key such as `BUNDLE_GEMFILE`.
