### Title
Bridge `handle*Transfer` Functions Don't Gate on `isRunning`, Allowing In-Flight Requests to Complete After Bridge Is Stopped — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

### Summary

The Kaia service-chain bridge enforces `isRunning` only on the **request** side (`_requestKLAYTransfer`, `_requestERC20Transfer`, `_requestERC721Transfer`), but not on the **handle** side (`handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`). When the bridge owner calls `setRunningStatus(false)` to halt the bridge — typically in response to a security incident — operators can still call the handle functions to complete any `RequestValueTransfer` events that were emitted before the stop, transferring KAIA or bridged tokens out of the destination bridge contract.

### Finding Description

`BridgeTransfer.sol` exposes `setRunningStatus(bool)` (owner-only) which sets `isRunning`. The three request-side internal functions each enforce this flag:

The three handle-side functions — `handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer` — contain **no** `isRunning` check. They only verify nonce ordering and operator authorization before executing the asset transfer:

```solidity
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }
    // ... directly transfers KLAY
    (bool ok, ) = _to.call.value(_value)("");
``` [4](#0-3) 

```solidity

The `setRunningStatus` comment explicitly states its purpose is to "allow or disallow the value transfer request," but the implementation only enforces this on the initiation path, not the completion path. [7](#0-6) 

### Impact Explanation

When the bridge owner stops the bridge (e.g., after detecting an exploit or a misconfigured token registration), any `RequestValueTransfer` events already emitted on the source chain remain actionable. Bridge operators — which are commonly automated relayer processes — will continue to call `handleKLAYTransfer`/`handleERC20Transfer`/`handleERC721Transfer` for every pending nonce in sequence. This causes:

1. **Unauthorized KAIA transfer**: The destination bridge's KLAY balance is drained to attacker-controlled `_to` addresses for all in-flight KLAY requests.
2. **Unauthorized ERC20 mint or transfer**: In mint-burn mode, tokens are minted to the attacker; in lock-unlock mode, tokens held by the bridge are transferred out.
3. **Unauthorized ERC721 mint or transfer**: Same as ERC20.

The `_lowerHandleNonceCheck` enforces sequential nonce processing, so an attacker who submitted a request at nonce `N` before the stop will have it processed as long as nonces `0…N-1` are also processed — which automated operators do by default. [8](#0-7) 

### Likelihood Explanation

- Bridge operators are typically automated relayer processes that process all pending `RequestValueTransfer` events without manual review of `isRunning` state.
- The window between the owner calling `setRunningStatus(false)` and the operators being reconfigured or operator roles being revoked is non-zero and can span multiple blocks.
- The trigger (operator calling `handle*Transfer`) is a semi-trusted, routine operation — not an exotic attack vector.
- The only mitigation available to the owner is a separate, additional step of revoking all operator roles, which is not atomic with `setRunningStatus`.

### Recommendation

Add an `isRunning` guard to all three handle functions, mirroring the pattern already used on the request side:

```diff
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
+   require(isRunning, "stopped bridge");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}

function handleERC20Transfer(...) public onlyOperators {
+   require(isRunning, "stopped bridge");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}

function handleERC721Transfer(...) public onlyOperators {
+   require(isRunning, "stopped bridge");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}
```

Alternatively, introduce a separate `isHandlingRunning` flag so that the owner can independently halt new requests and halt in-flight completions, giving finer-grained emergency control.

### Proof of Concept

1. Bridge is deployed and running (`isRunning = true`). Operators are registered.
2. Attacker calls `requestKLAYTransfer` on the source bridge, depositing 100 KAIA. A `RequestValueTransfer` event is emitted with `requestNonce = 42`.
3. Bridge owner detects the attack and calls `setRunningStatus(false)`. New requests revert with `"stopped bridge"`.
4. The automated operator relayer, which monitors `RequestValueTransfer` events, sees nonce 42 and calls `handleKLAYTransfer(txHash, attacker, attacker, 100 KAIA, 42, blockNum, "")` on the destination bridge.
5. `handleKLAYTransfer` passes all checks (nonce valid, operator authorized, vote threshold met) and executes `_to.call.value(100 KAIA)("")`, transferring 100 KAIA to the attacker on the destination chain.
6. The bridge is stopped but the attacker has received their funds — the stop had no effect on the in-flight request.

        bytes32 _requestTxHash,
        address _from,
        address payable _to,
