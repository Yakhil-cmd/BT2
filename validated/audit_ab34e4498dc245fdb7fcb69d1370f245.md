### Title
Webhook signature verified against `repository.owner.login` while repository lookup uses the independent `repository.full_name` field, allowing cross-organization event injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`. [1](#0-0) [2](#0-1)  However, every webhook handler resolves the target `Repository`/`Stack` using a completely different field of the same JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2)  Both fields are attacker-controlled parts of the same signed body, and nothing enforces that `repository.owner.login` and the owner segment of `repository.full_name` refer to the same organization.

### Finding Description
Shipit supports multi-organization GitHub App configuration, where each organization has its own `webhook_secret` used to verify inbound webhooks (see `test/dummy/config/secrets_double_github_app.yml`, which configures `OrgOne` and `OrgTwo` with distinct secrets). [4](#0-3) 

The controller's `verify_signature` filter picks the app/secret with `Shipit.github(organization: repository_owner)` where `repository_owner` reads `repository.owner.login` from the JSON body, then HMACs the raw request body against that org's secret. [1](#0-0)  `verify_webhook_signature` in `Shipit::GithubApp` performs a straightforward HMAC-SHA1 compare using whatever `webhook_secret` was selected. [5](#0-4) 

Crucially, the value that decided *which secret to check against* (`repository.owner.login`) is never re-checked against the value later used to decide *which repository/stack the event acts on* (`repository.full_name`, consumed via `Handler#repository_name` / `Repository.from_github_repo_name`). [3](#0-2)  `Repository.from_github_repo_name` simply splits `full_name` on `/` and looks up any repository row by owner/name, with no linkage back to the signature-selecting owner. [6](#0-5) 

Because a legitimate customer organization onboarded onto the same Shipit instance knows its own `webhook_secret` (it is configured to receive it from GitHub and can also replay it directly, since the endpoint has no other authentication — `skip_before_action :verify_authenticity_token`, no session/API-token check), that organization's operator can craft a POST to `/webhooks` where:
- `repository.owner.login = "OrgA"` (their own org, so `verify_signature` selects `OrgA`'s secret and the HMAC they compute passes),
- `repository.full_name = "OrgB/victim-repo"` (a different organization's repository/stack hosted on the same Shipit instance).

The equality that should hold is: `organization authenticated (repository.owner.login) == organization whose repository is written (owner segment of repository.full_name)`. This binding is never enforced, so it can be broken.

### Impact Explanation
With a forged `full_name`, an attacker who only controls their own organization's webhook secret can drive handlers that act on an arbitrary victim stack:
- `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` for any branch/stack matched by the forged `full_name`, forcing an unscheduled GitHub sync using an attacker-chosen `after` SHA. [7](#0-6) 
- `StatusHandler` creates fabricated commit statuses (`state`, `context`, `target_url`, `description`) on arbitrary commits by `sha`, independent of which repo the commit truly belongs to lookup-wise, since `Commit.where(sha:)` is not scoped to the resolved repository at all. [8](#0-7)  Forged/passing CI statuses are exactly the kind of signal Shipit deployability logic relies on to allow deploys.
- `CheckSuiteHandler` schedules `schedule_refresh_check_runs!` for commits on a victim stack's branch, letting an attacker force check-run refresh/CI state processing against a repository they don't own. [9](#0-8) 

The most severe consequence is manipulation of a victim stack's deployability signals (fake commit statuses / forced sync) toward triggering an unauthorized deploy path, which matches the engine's Critical impact bucket ("unauthorized deploy" via injected commit-status/CI signal).

### Likelihood Explanation
This requires the attacker to control at least one organization's genuine `webhook_secret` that is configured on the same Shipit instance — realistic in shared/multi-tenant Shipit deployments (explicitly supported per `secrets_double_github_app.yml`) where multiple, mutually-untrusted GitHub orgs are onboarded. [4](#0-3)  No GitHub write access, Shipit session, or `ApiClient` token is needed — only the ability to POST directly to the public `/webhooks` endpoint with a correctly-signed body for the attacker's own org while spoofing an unrelated `repository.full_name`.

### Recommendation
In `Shipit::WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the owner segment of `repository.full_name` matches `repository.owner.login` (or, more robustly, resolve the repository/stack strictly by the same organization value that authenticated the signature) and reject the webhook otherwise. Alternatively, derive the target repository lookup solely from the authenticated `repository_owner` rather than trusting `full_name` independently.

### Proof of Concept
1. Shipit instance configured with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `secrets_double_github_app.yml`).
2. Attacker (member/operator of `OrgA`) builds a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` selects `OrgA`'s app via `repository_owner` (`OrgA`) and the HMAC check passes. [1](#0-0) 
5. `PushHandler#process` resolves stacks via `repository.full_name` = `OrgB/victim-repo`, and calls `sync_github(expected_head_sha:)` on `OrgB`'s stack the attacker does not control. [7](#0-6) [3](#0-2) 

Note: I was not able to fully trace `Shipit.github`/organization-resolution edge cases (e.g., single-org vs. multi-org config fallback behavior in `lib/shipit.rb`) within the available iterations; this could affect exact preconditions (single-secret deployments where `verify_webhook_signature` returns `true` unconditionally when no secret is configured would trivially allow this too, but that is a separate, already-known "no secret configured" condition). [10](#0-9)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
