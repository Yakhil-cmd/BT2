Confirmed root cause. Every incoming unit is written via `writer.saveJoint`, which acquires the global `write` mutex at [1](#0-0)  and only releases it after fully processing any AA triggers unlocked by that write's stabilization. When a unit stabilizes an MCI that has AA triggers, `saveJoint` awaits `aa_composer.handleAATriggers()` synchronously while still holding the lock, before calling `unlock()` at [2](#0-1) [3](#0-2) . `handleAATriggers` itself pulls **all** pending rows from the `aa_triggers` table and processes them one at a time with `async.eachSeries`, each iteration taking its own DB connection, running a full transaction and a synchronous kvstore batch write: [4](#0-3) . The insertion of new trigger rows for a newly-stabilized MCI is itself unbounded — every unit at that MCI that outputs to an AA address is queued: [5](#0-4) . There is no `maxFillsPerUpkeep`-style cap; the loop only stops when the table is empty, and `saveJoint` even chains further stabilizations in a `while(true)` loop, still under the same lock, invoking `handleAATriggers()` again after each one: [6](#0-5) .

### Title
Unbounded serial AA-trigger processing while holding the global `write` mutex allows a DoS on new-unit confirmation - (File: writer.js, aa_composer.js)

### Summary
`saveJoint` holds the process-wide `write` mutex for the entire duration of AA trigger execution triggered by MCI stabilization. `handleAATriggers` processes an unbounded queue of pending `aa_triggers` rows strictly sequentially, with each entry costing a full DB transaction plus a synchronous disk-flushed kvstore batch write. An attacker can cheaply inflate the number of AA triggers that become due at once, causing the write lock to be held for a very long time and preventing the node from validating/saving any other unit in the meantime.

### Finding Description
`writer.saveJoint` acquires the global `["write"]` mutex before doing anything else: [1](#0-0) . This lock is not released until the very end of the function, at line 776, only after all cascading MCI stabilizations and their AA trigger executions have completed: [3](#0-2) .

Whenever the unit being saved causes an MCI to stabilize, the number of qualifying AA triggers for that MCI is computed and inserted into `aa_triggers` without any cap: [5](#0-4) . Immediately afterward, `saveJoint` awaits `aa_composer.handleAATriggers()` while still holding the write lock: [2](#0-1) . That function selects *all* outstanding rows from `aa_triggers` (across possibly multiple MCIs left over from previous runs too) and processes them one-by-one via `async.eachSeries`, where each single trigger requires taking a connection from the pool, opening a SQL transaction, executing (bounded-but-still-costly) AA formula evaluation, and performing a synchronous (`sync: true`) kvstore batch write before moving to the next: [4](#0-3) [7](#0-6) .

Furthermore, `saveJoint` loops to advance stability further and re-invokes `handleAATriggers()` again for each additional MCI that stabilizes, still under the same lock, before ever calling `unlock()`: [6](#0-5) .

This mirrors the reported Solidity bug class exactly: a queue built from attacker-controllable, individually cheap entries is drained strictly sequentially with no per-call cap, and while it drains, a shared, exclusive resource (there: gas/`performUpkeep` slot for other ITM orders; here: the process-wide `write` mutex needed by every other unit save) is unavailable to legitimate participants.

An attacker can post many low-value units, each sending bytes to one or more autonomous agent addresses (their own cheap AAs, or any AA cheap enough for the attacker to fund), timed so that a large batch of them stabilizes together in one MCI (or across consecutive MCIs picked up by the `while(true)` loop). Each such unit adds a row to `aa_triggers` at negligible cost (bytes transfer fee only), but each row costs the node a full DB round trip and an fsync'd disk write to process.

### Impact Explanation
While `handleAATriggers` drains the inflated queue, the global `write` mutex stays locked, so `saveJoint` cannot be entered for *any* other unit arriving at the node (from any peer, for any purpose) — the node is unable to confirm/write new units for the entire duration of the drain. On a hub or heavily-connected full node this stalls the propagation and confirmation of legitimate transactions network-wide until the malicious backlog is cleared, matching the "network unable to confirm new units" impact class.

### Likelihood Explanation
The cost to the attacker is proportional only to the bytes-transfer fee per triggering unit (dust amounts suffice, since even a triggering unit that fails/bounces on the AA still gets processed and removed from `aa_triggers` one at a time). Achieving a burst of many units stabilizing within the same or few consecutive MCIs is realistic given normal DAG batching behavior, especially by simply posting a flood of units in a short window. No special privileges (witness, hub operator, etc.) are required — any unprivileged unit poster with modest funds can trigger this.

### Recommendation
- Do not hold the `write` mutex across AA trigger execution; release it once the triggering unit itself is committed, and process `aa_triggers` under a separate, non-blocking lock (similar in spirit to the existing `['aa_triggers']` mutex already used inside `handleAATriggers`).
- Add a per-call/per-batch cap on how many AA triggers `handleAATriggers` processes before yielding, so newly arriving units can be validated/saved between batches, resuming trigger processing afterward (analogous to `maxFillsPerUpkeep` in the referenced report).
- Consider rate-limiting/capping the number of AA triggers a single MCI stabilization or a bounded time window can enqueue, or charging a proportionally higher fee for AA-triggering outputs, to reduce the attacker's ability to cheaply inflate the queue.

### Proof of Concept
1. Attacker deploys or targets an existing cheap AA address `A`.
2. Attacker repeatedly posts unrelated small units to their own addresses to keep building up the DAG, then, in a short burst, posts N units each with a payment output to `A` (or several attacker AAs to accumulate more rows through `count_aa_triggers`), spending minimal bytes each.
3. As units get added, the DAG advances such that many of these attacker units become part of one (or a handful of consecutive) newly-stabilized MCI(s), as computed in `handleAATriggers()` in `main_chain.js` [5](#0-4) , inserting N rows into `aa_triggers`.
4. The unit that causes this stabilization is written via `writer.saveJoint`, which — still holding the global `write` mutex acquired at [1](#0-0)  — calls `aa_composer.handleAATriggers()`, which serially processes all N rows with `async.eachSeries`, each incurring a DB transaction and synchronous batch write [4](#0-3) .
5. During this processing (proportional to N), any other legitimate unit arriving at the node cannot be validated/saved because `saveJoint` blocks on the same `write` mutex, demonstrating the DoS on new-unit confirmation.
