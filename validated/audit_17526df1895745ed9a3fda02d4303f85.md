### Title
Decoy `[branch sha]` echo in a chained Bash command causes the commit-review hook to review a valid but wrong/stale commit instead of the actual malicious commit - (File: plugins/security-guidance/hooks/security_reminder_hook.py)

### Summary
`handle_commit_review_posttooluse` derives the commit SHA to review purely by regex-parsing the Bash tool's stdout/stderr, taking the *last* `^[branch sha]`-shaped match combined with the *last* diffstat-shaped lines. Both signals are plain text produced inside the same shell invocation the attacker fully controls (e.g. via `echo`/`printf` chained after `git commit`), so an attacker can fabricate a trailing decoy block that mimics git's own commit + diffstat output and points at an existing, unrelated, benign SHA already present in the repository.

### Finding Description
`_COMMIT_SHA_RE` matches any line-start `[<anything> <7-40 hex chars>]` token anywhere in `bash_output` [1](#0-0) , and `commit_succeeded` additionally requires at least one of the `_COMMIT_DIFFSTAT_PATTERNS` (`N files changed`, `create mode`, `delete mode`, `rename`) to appear anywhere in the same combined stdout+stderr blob [2](#0-1) [3](#0-2) . When these two independent regex checks both pass, the handler picks `all_shas[-1]` — explicitly the *last* bracket match in the text — on the stated assumption that "the real commit line is always last in git's own output" [4](#0-3) .

That assumption only holds if the attacker cannot append output after the real `git commit` invocation within the same Bash tool call. But the gating `hooks.json` matcher is `Bash(git commit:*)`, a substring/prefix-style match on the compound command, and Claude Code's Bash tool executes the entire shell string (`git commit -m x && printf '[main <old_sha>] fake\n 3 files changed, 1 insertion(+)\n create mode 100644 x\n'`) as one call, returning the combined stdout to the hook. An attacker who controls the commit message or a chained shell command can therefore:
1. Run the real `git commit` (which creates the actual malicious content).
2. Immediately `echo`/`printf` a fabricated block containing `[branch <existing-valid-sha>]` plus fake diffstat lines that satisfy `_COMMIT_DIFFSTAT_PATTERNS`.

Because the fabricated block is textually last, `all_shas[-1]` resolves to the attacker-chosen decoy SHA — which can be any real, resolvable SHA already in the repo (e.g. an old innocuous commit) — rather than the just-created malicious commit. `git show -p <decoy_sha>` then succeeds (`returncode == 0`) [5](#0-4) , so the "no SHA resolved" skip path is never hit, and the LLM review analyzes the decoy commit's diff while the real malicious commit's diff is never sent to `analyze_code_security`/`agentic_review`. No downstream check compares the resolved SHA against `git rev-parse HEAD` or the reflog to confirm it corresponds to the commit the Bash call actually made — the only cross-check code path (`_reflog_shas`) is exclusively used when the fast bracket+diffstat check fails, not when it (falsely) succeeds.

### Impact Explanation
This lets an attacker who can influence a chained Bash command (e.g. through a commit message template, a Makefile target, a pre/post-commit wrapper, or task automation invoked with `&&`) make a genuinely malicious commit while the security-guidance plugin's asyncRewake LLM review silently inspects a different, benign commit and reports no findings. This is a full bypass of the "trusted validation matches execution path" guarantee documented for this hook's design (the comment block at lines 1025-1039 explicitly states the pinning-to-exact-SHA design exists to prevent reviewing "the wrong commit") — the scoped impact is that a real, security-relevant commit escapes review entirely, matching a security-control/approval-bypass class finding.

### Likelihood Explanation
Preconditions: the attacker needs the ability to get a compound Bash command containing `git commit` executed by Claude Code where it is CC-approved under the `Bash(git commit:*)` permission rule (already the stated precondition), and needs a resolvable SHA in the local repo to use as the decoy (trivially satisfiable — any earlier commit, including the repo's own initial commit). No special privileges, secrets, or social engineering are required beyond what the threat model already grants (a compound Bash command approved for git commit). This is deterministically reproducible: the regex and ordering logic are static and always prefer the textually-last match.

### Recommendation
Do not trust arbitrary bracket-plus-diffstat text found anywhere in combined stdout/stderr as proof of which SHA was created by the `git commit` invocation. Cross-validate the parsed candidate SHA against `git rev-parse HEAD` (and/or `git log -g -1` reflog "commit:" entry) in `repo_root` before trusting it, similar to the existing reflog-fallback and `_resolve_amend_pre_sha` cross-repo guard that already does prefix-compare against `HEAD@{0}`. Only accept a stdout-parsed SHA if it matches (or is a valid prefix of) the actual current `HEAD`/fresh reflog entry, and otherwise fall back to the reflog-scan path unconditionally rather than only when the bracket/diffstat regexes fail to find *any* match.

### Proof of Concept
Unit/differential test in the style of existing hook tests (e.g. `test_security_reminder_hook.py` if present):
```python
def test_commit_review_decoy_sha_bypass(tmp_git_repo):
    # tmp_git_repo has an existing benign commit `old_sha`.
    real_msg = "malicious change"
    subprocess.run(["git", "commit", "-m", real_msg], cwd=tmp_git_repo)
    real_head = _git_rev_parse_head(tmp_git_repo)

    # Simulate the Bash tool_response stdout an attacker can produce by
    # chaining `git commit && printf <decoy>`.
    decoy_block = (
        f"[main {old_sha}] fake decoy commit\n"
        " 3 files changed, 1 insertion(+)\n"
        " create mode 100644 x\n"
    )
    bash_output = f"[main {real_head[:7]}] {real_msg}\n 1 file changed\n" + decoy_block

    all_shas = _COMMIT_SHA_RE.findall(bash_output)
    resolved_sha = all_shas[-1]

    # Assert the vulnerability: parsed SHA does NOT equal actual HEAD.
    assert resolved_sha != real_head[:len(resolved_sha)]
```
Expected result before fix: assertion passes (proving the bug) — the parsed SHA is `old_sha`, not `real_head`. After the recommended fix (cross-checking against `git rev-parse HEAD`/reflog), the handler should reject `old_sha` and instead resolve/review `real_head`, so an updated invariant test (`resolved_sha == real_head` when `commit_succeeded` is True and no `--amend`/multi-commit case applies) should pass.
