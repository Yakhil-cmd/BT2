Key finding: `verify_signature` in `WebhooksController` verifies against the webhook secret for `Shipit.github(organization: repository_owner)`, where `repository_owner` is derived from the incoming payload's own `repository.owner.login` field. This means an attacker who owns their own GitHub org/repo configured (or onboarded) in Shipit can send a webhook whose payload claims `repository.full_name` matching a *different* victim repository, while `repository.owner.login` still needs to match an org whose `webhook_secret` the attacker can produce a valid HMAC for — i.e., their own org. So the signature check only proves the payload was signed by *some* org's webhook secret, not that the `sha`/`state` in the payload actually belongs to the repository named in that payload.

Critically, `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This is a global, cross-repository, cross-stack lookup by `sha` alone — it is **not** scoped to `repository_name`/`stacks` the way other handlers are (compare `Handler#stacks`, which scopes via `Repository.from_github_repo_name(repository_name)`) [2](#0-1) . Since git SHAs are content-addressed and can coincidentally or deliberately collide across unrelated repos/forks (e.g., an attacker forks/rebases to produce a commit with an identical tree at a specific SHA is infeasible to force arbitrarily, but the real practical risk is simpler: an attacker who has push access to *their own* repo that is *also configured as a Shipit stack* can create a commit whose SHA equals a commit's SHA already present in a victim's stack via a shared ancestor/cherry-pick — same commit content pushed to two repos yields the identical SHA legitimately). Given a shared/forked-repo scenario, the attacker's own org's legitimately-signed status webhook for their own commit will write a `Status` row attached to `commit.stack_id` for **every** `Commit` record across the database sharing that `sha`, including the victim's, because `Commit.where(sha:)` is unscoped by stack or repository.

However, per the rules, I must check whether this actually breaks the stated binding for *arbitrary* victim repos with unrelated SHAs (i.e., true cross-repo forgery without any real relationship). The attack as generally described in security literature for this codebase requires the attacker's forged webhook to reference a `sha` that also exists as a `Commit` row in the victim's stack. That is only possible if:
1. The victim stack already has a `Commit` record with that exact SHA (i.e., same commit content, e.g. via shared history/fork), and
2. The attacker can get a signed status webhook accepted for *an org they control* referencing that SHA.

This is a real, demonstrable defect: `StatusHandler` (and similarly `CheckRunHandler`, likely) never verifies that the commit's `stack`/`repository` matches the webhook's own `repository_name`, unlike essentially all other handlers which scope via `stacks`. This directly matches the question's described binding break: `success?` state of a commit consulted by `deployable?` can be set by a status webhook whose repository does not match the stack owning that commit.

### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enabling false CI green light - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone, with no scoping to the repository named in the webhook payload, unlike every other webhook handler which scopes via `Repository.from_github_repo_name(repository_name)`. Any org with a validly signed webhook (i.e., any org already onboarded with a `webhook_secret` in Shipit, however unrelated to the victim stack) can attach a `success` status to any `Commit` row in the database that happens to share the same `sha`, letting `Commit#blocked?`/`Commit#deployable?` see it as CI-green for a stack it was never validated for.

### Finding Description
The broken binding: `commit.success?` (consulted by `Commit#deployable?` at `app/models/shipit/commit.rb:227-229`) should equal "a status legitimately produced by CI for `commit.stack.github_repo_name`", but `StatusHandler#process` makes it equal "a status produced by CI for *any* signed org, applied to *every* `Commit` record sharing `sha`, regardless of stack/repository" [1](#0-0) . `Handler#stacks`/`repository_name` exist precisely to scope by the payload's own repository [2](#0-1) , but `StatusHandler` never calls `stacks` — it queries `Commit` globally. `WebhooksController#verify_signature` only proves the payload's HMAC matches the webhook secret of whatever org is named as `repository_owner` inside the *same, attacker-controlled* payload [3](#0-2) ; it does not prove that the `sha` belongs to that org's repo, nor that it belongs to the victim's stack. Root cause: missing repository/stack scoping in `StatusHandler#process`. Exploit requires the attacker to control an org onboarded to Shipit (with its own `webhook_secret`) and to produce/know a commit `sha` that also exists as a `Commit` record in the victim's stack (e.g., shared fork history, cherry-picks, or squash-merges producing identical trees/parents/timestamps — SHA equality is content-derived and not attacker-forgeable at will against an arbitrary unrelated victim SHA). `Commit#blocked?` then only inspects the *range* of other commits between `last_deployed_commit` and the forged commit for `blocking?` status — it does not re-validate that the forged commit's own status came from the correct repository, so the forged commit itself reports `success? == true`.

### Impact Explanation
A forged `success` status written to a victim's `Commit` causes `Commit#deployable?` to potentially return `true` for that commit (if it is not itself blocked and not locked), which feeds `Stack#trigger_continuous_delivery`/`schedule_continuous_delivery` and can trigger an unauthorized deploy for the victim's stack [4](#0-3) . This is a payload from one (attacker-controlled) repository/org mutating another (victim) stack/commit's state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). Blast radius is limited to stacks that share commit SHAs with an attacker-controlled, Shipit-onboarded repo (forks/mirrors), so it is not exploitable against arbitrary unrelated victims without a real SHA collision precondition.

### Likelihood Explanation
Requires: (1) attacker controls or operates an org/repo already configured in Shipit with a `webhook_secret` (i.e., not a fully anonymous internet attacker — some onboarding as a legitimate-but-untrusted tenant), and (2) a genuine SHA overlap between attacker's repo and the victim's stack (fork/mirror/shared-history scenario), which is a real but non-universal precondition — SHAs cannot be forged to collide with an arbitrary unrelated commit. Given the question explicitly frames the attacker as controlling "an unrelated verified org" with a legitimate webhook secret and a shared/forked commit, likelihood is plausible in multi-tenant Shipit deployments with shared/forked repositories, but not a fully unauthenticated, zero-precondition attack.

### Recommendation
Scope `StatusHandler#process` (and `CheckRunHandler` if similarly unscoped) to only update commits belonging to stacks resolved from the payload's own `repository_name`, mirroring `Handler#stacks`, e.g. iterate `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan under `test/models/shipit/commit_test.rb` or `test/models/shipit/webhooks/handlers/status_handler_test.rb`:
1. Create `stack_a` (victim) and `stack_b` (attacker-controlled, different `Repository`/org with its own `webhook_secret`), each with a `Commit` sharing the identical `sha` value (simulating fork/shared history).
2. In `stack_a`, create an earlier commit with a `blocking?` status so `stack_a.commits.reachable.newer_than(last_deployed_commit).older_than(target).any?(&:blocking?)` is true, matching preconditions.
3. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` with `payload['repository']['full_name']` set to `stack_b`'s repo (legitimately signed for org B) and `sha` equal to the shared SHA, `state: 'success'`.
4. Assert `stack_a.commits.find_by(sha: shared_sha).success?` is `true` even though no status webhook was ever sent for `stack_a`'s repository — i.e., assert `commit_a.reload.success? == true` while `commit_a.stack_id != commit_b.stack_id` and the webhook `payload['repository']['full_name']` never equals `stack_a`'s `github_repo_name`, demonstrating the equality "status consulted by `deployable?`" == "status legitimately produced for that stack's repo" is broken.
