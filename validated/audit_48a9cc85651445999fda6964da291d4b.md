### Title
Webhook signature verification is bound to `repository.owner.login`, not to the `repository.full_name` actually acted upon, allowing cross-organization/cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a signature against using the untrusted `repository.owner.login` field taken from the raw payload, but the event handlers that act on the payload (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using a different, independently-attacker-controlled field, `repository.full_name`. The signature only proves "this request was signed with organization X's secret" — it never proves that the repository being synced actually belongs to organization X.

### Finding Description
`verify_signature` computes the organization to check against directly from the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This is HMAC-checked per-organization secret using `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Once verified, `Shipit::Webhooks.for_event(event)` dispatches handlers with the full raw payload: [4](#0-3) 

The handler base class resolves the acted-upon repository from a *different* payload field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

`PushHandler#process` then triggers `stack.sync_github(expected_head_sha: params.after)` for every stack matching that resolved repository: [6](#0-5) 

Shipit explicitly supports multiple GitHub Apps/organizations, each with its own (optionally blank) `webhook_secret`, as shown in the test fixture configuring two orgs (one of which has `webhook_secret: # nil`): [7](#0-6) 

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the target repository/stack) are two independent JSON fields inside the same attacker-supplied body, nothing enforces `repository.full_name` starts with `repository.owner.login`. An attacker who controls (or is an admin of) one onboarded GitHub organization — and therefore knows/controls that organization's `webhook_secret` (which can even be blank, as `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank: `return true unless webhook_secret` at line 77) — can sign (or trivially satisfy, if blank) a payload whose `repository.owner.login` is their own organization but whose `repository.full_name` names a victim organization's repository. The `verify_signature` check passes because it only validates against the attacker's own org's secret, yet the dispatched handler acts on the victim's repository name.

**Binding broken:** `organization authenticated (repository.owner.login, checked against GitHub App secret)` != `repository written (repository.full_name, used by Handler#stacks to resolve target Stack)`.

### Impact Explanation
An attacker with no privileges on the victim's Shipit stacks or GitHub organization — only control of their own onboarded organization/app installation — can forge a `push` webhook naming a victim repository's `full_name`. This triggers `GithubSyncJob` for every non-archived stack of that repository with an attacker-chosen `expected_head_sha`, causing the engine to sync/deploy state for a repository the attacker does not own. Depending on downstream trust in `sync_github`/`GithubSyncJob` (queuing deploys, updating commit state, refreshing statuses), this is an unauthorized cross-repository action triggered purely by an unprivileged actor who forged a webhook body — matching the "cross-repository writes / unauthorized deploy" impact class. Other handlers reachable the same way (`StatusHandler`, `CheckSuiteHandler`, PR handlers) are equally affected since they all inherit `Handler#repository_name`/`#stacks`.

### Likelihood Explanation
High for any Shipit installation configured with more than one GitHub organization/App (a documented and tested configuration, see `test/dummy/config/secrets_double_github_app.yml`), or where a webhook secret is left blank for any onboarded org. The attack requires only the ability to install/administer one legitimate GitHub App/org onboarded to the same Shipit instance and to send a crafted HTTP request to the public `/webhooks` endpoint — no Shipit session, API token, or GitHub write access to the victim repo is needed.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler#repository_name`), cross-check that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the owner portion of `repository.full_name` before dispatching to handlers, rejecting the request (e.g. `head(422)`) on mismatch — analogous to adding the missing secondary check `isERC721Approved(...)` alongside `_isApprovedOrOwner` in the referenced report.

### Proof of Concept
1. Shipit is configured with two onboarded GitHub organizations/Apps, `attacker-org` (attacker controls or knows its webhook secret, possibly blank) and `victim-org` (has stacks tracking `victim-org/victim-repo`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
signed (or left unsigned if blank) with `attacker-org`'s webhook secret via `X-Hub-Signature`.
3. `verify_signature` resolves `repository_owner` to `attacker-org`, validates the signature against `attacker-org`'s secret successfully.
4. `PushHandler#process` resolves the target repository via `payload.dig('repository', 'full_name')` = `victim-org/victim-repo`, finds `victim-org`'s stacks, and enqueues `GithubSyncJob` for the `victim-repo` stacks with the attacker-supplied `after` SHA — an action the attacker was never authorized to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
