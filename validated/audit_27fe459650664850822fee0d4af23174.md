### Title
`initialize_with_permission()` records an unverified, unchecked `creator` account as `pool_state.pool_creator`, permanently locking creator-fee accrual - (File: programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
`initialize_with_permission` accepts a `creator` field typed as a bare `UncheckedAccount` with only a `/// CHECK: creator of pool` comment and no signer, ownership, or address constraint. This value is stored verbatim into `PoolState.pool_creator` and becomes the permanent, immutable authority that all future creator-fee funds are routed to.

### Finding Description
In `InitializeWithPermission`, the `creator` account has no validation at all: [1](#0-0) 

It is passed straight into `pool_state.initialize(...)` and stored as `pool_creator`: [2](#0-1) [3](#0-2) 

This is analogous to the reported `registerWallet()` issue: an unprivileged/low-trust actor supplies an address that is later treated as a fully-trusted, capability-bearing identity (a "real Safe" in the original report, a fee-receiving `pool_creator` here) without verifying it is actually usable/controllable. Unlike the permissionless `initialize` instruction — where `creator` is forced to be the transaction `Signer` (`ctx.accounts.creator.key()`), guaranteeing a spendable key — `initialize_with_permission` lets the `payer` (who only needs a `permission` PDA, not ownership of the `creator` identity) set an arbitrary, non-signing `creator` pubkey, which can be any 32-byte value including an address with no known private key or an unrelated PDA: [4](#0-3) 

This `pool_creator` value later gates both fee-collection paths:
- `collect_creator_fee` requires the `creator` to be a `Signer` matching `pool_state.pool_creator`: [5](#0-4) 
- `collect_creator_fee_permissionless` allows *anyone* to trigger fee payout to whatever address is stored as `pool_creator`, creating an ATA owned by that address: [6](#0-5) [7](#0-6) 

Because `pool_creator` is immutable after initialization (there is no update/rotate instruction for it found in the codebase) and `creator_fees_token_0/1` accumulate from real swap volume (deducted from actual trader input during `swap_base_input`/`swap_base_output` via the `creator_fee_on` split configured at init), if `pool_creator` is set to an address with no corresponding private key (or a PDA nobody can sign for), all creator fees generated by the pool for its entire lifetime become permanently unclaimable — even though `collect_creator_fee_permissionless` will happily keep sweeping them into an unspendable ATA.

### Impact Explanation
This results in permanent freezing of real fee-ledger funds (the creator-fee portion of every swap routed through the pool), matching the "permanent freezing of user/LP funds" / "insolvent fee-ledger accounting" bar. While a self-inflicted misconfiguration by the pool creator is lower severity, the field is set by `payer` — not necessarily the actual `creator` — with zero verification, so a permission-holder acting as `payer` can silently misconfigure or grief the intended creator's fee stream, or set it to a garbage/unspendable pubkey, with no recourse since `pool_creator` cannot be changed later.

### Likelihood Explanation
Reaching this requires a single transaction with `attacker`/permission-holder-chosen accounts calling `initialize_with_permission`, and only needs the caller to already hold a `Permission` PDA (an intended, but easily obtainable in many deployments, precondition for this instruction). No other privileged signer or off-chain step is needed to set the malformed `creator` value.

### Recommendation
Constrain `creator` in `InitializeWithPermission` at minimum to be consistent with how `initialize` handles it (e.g., require it be a `Signer`, or otherwise validate it is a standard system-owned/wallet account capable of holding an ATA and producing a signature), and/or add an admin-gated instruction to rotate `pool_state.pool_creator` in case of misconfiguration, mirroring the recommendation in the original report to validate an untrusted-supplied identity before it is trusted for privileged, fund-bearing operations.

### Proof of Concept
1. Attacker (or any account already holding a `Permission` PDA) calls `initialize_with_permission` with `payer = attacker`, `creator = <pubkey with no known private key>` (e.g., a hash-derived address not on the ed25519 curve, or an arbitrary PDA of an unrelated program).
2. `pool_state.pool_creator` is set to this unspendable address per `PoolState::initialize` at `programs/cp-swap/src/states/pool.rs:139-152`.
3. Normal users perform swaps; `creator_fees_token_0/1` accumulate in `pool_state` as configured by `creator_fee_on`.
4. Anyone calls `collect_creator_fee_permissionless`; funds are moved into an ATA owned by the unspendable `creator` address per `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs:61-79`.
5. Because no private key exists for `creator`, and no instruction exists to change `pool_state.pool_creator`, these funds are permanently locked, and `collect_creator_fee` (the signer-gated path) can never be used to recover them either, since `address = pool_state.load()?.pool_creator` at `programs/cp-swap/src/instructions/collect_creator_fee.rs:12-13` can never be satisfied by a signature.
