Confirmed: `CCMenuUrlController#client` creates an `ApiClient` with `permissions: %w[read:stack]` but never sets `stack`/`stack_id` [1](#0-0) . `Api::CCMenuController#stack` fetches the stack directly via `Stack.from_param!(params[:stack_id])`, bypassing the scoped `stacks` helper entirely [2](#0-1) , and its permission check only verifies the generic `read:stack` permission via `require_permission :read, :stack` / `check_permissions!` with no stack-id comparison [3](#0-2) [4](#0-3) . Even `Api::BaseController#stacks` would scope by `current_api_client.stack_id?` (false here) to `Stack.all` if it were used [5](#0-4) , so the CCMenu token is unscoped by design/bug, valid for any `stack_id` param.

### Title
CCMenu token minted for one stack authorizes read access to every stack - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#client` creates an `ApiClient` with `read:stack` permission but never assigns `stack`/`stack_id`, and `Api::CCMenuController#show` resolves the target stack directly from `params[:stack_id]` without checking it against the token's (nonexistent) stack scope. As a result, a CCMenu URL minted for stack A's token works unmodified against any other stack B by simply editing the `stack_id` in the URL.

### Finding Description
The intended binding is: `token.stack_id == stack_id_the_token_was_issued_for` (single stack A). The actual binding is: `token.stack_id == nil`, which `Api::CCMenuController` never checks, so the token authorizes `stack_id ∈ Stack.all`.

Path: user with UI access to stack A calls `GET /ccmenu/<stack_A>`, hitting `CCMenuUrlController#fetch`, which builds `client` via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` [1](#0-0) . Note `find_or_create_by!` also means this same client/token is reused across *all* stacks that user calls `/ccmenu/<stack>` for, since it's keyed only by `creator` and `name`, not stack. The returned URL embeds `stack.to_param` and `client.authentication_token` [6](#0-5) . The attacker edits the `stack_id` segment to stack B and calls `GET /ccmenu/api/<stack_B>.xml?token=<token>` (or equivalent route), hitting `Api::CCMenuController#show`, whose `stack` method is `Stack.from_param!(params[:stack_id])` with no scoping by `current_api_client.stack_id` [2](#0-1) . Authorization is only `require_permission :read, :stack`, which calls `ApiClient#check_permissions!` checking only that `"read:stack"` is in the `permissions` array — it never compares `current_api_client.stack_id` to the requested stack [4](#0-3) . `Api::BaseController#stacks` does contain the scoping logic (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) [5](#0-4) , but `CCMenuController` overrides `stack` and never calls `stacks`, so this guard is never invoked — and even if it were, since `stack_id` is nil, it would resolve to `Stack.all` anyway, because `client` never had `stack`/`stack_id` set at creation time.

### Impact Explanation
Any user who can view one stack's CCMenu URL obtains a bearer token that grants read access (build/deploy status, latest deploy metadata) to every stack in the Shipit installation, not just the one they were authorized to view. This is a horizontal privilege escalation / broken object-level authorization: exposure of stack state across tenants that the attacker was never granted UI access to. This matches the "High - unauthenticated/unauthorized read of stack state" impact category for the CCMenu XML status endpoint (deploy id, timing, running state) across arbitrary stacks. It is fully repeatable — the same token works indefinitely against any `stack_id` since tokens are permanent (`SimpleMessageVerifier`-signed, no expiry) and the `ApiClient` permission set is static.

### Likelihood Explanation
Preconditions are trivial: this only requires normal Shipit UI/session access to a single stack (`ShipitController` before_action, not a privileged role) and the ability to call `GET /ccmenu/<stack_id>` for that stack, which the target stack's page exposes as a "CCMenu URL" link (see `app/views/shipit/stacks/settings.html.erb`). No secrets, GitHub credentials, or admin privileges are needed — the attacker only edits a URL query segment. Cost is a single HTTP request plus knowledge/guessing of another stack's `to_param` (which is derivable from repo owner/name/branch, all public-ish identifiers within the Shipit instance).

### Recommendation
Set `stack: stack` (and thus `stack_id`) when creating the `ApiClient` in `CCMenuUrlController#client`, keyed uniquely per stack (e.g. include stack in the `find_or_create_by!` lookup so distinct stacks get distinct tokens), and make `Api::CCMenuController#stack` use the scoped `stacks` helper from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!` directly, so a stack-scoped token cannot resolve an out-of-scope stack.

### Proof of Concept
Minitest plan for `test/controllers/ccmenu_url_controller_test.rb` combined with `test/controllers/api/ccmenu_controller_test.rb`:
1. Sign in as a user with access only to `stacks(:shipit)` (stack A). `GET :fetch, params: { stack_id: stacks(:shipit).to_param }`.
2. Assert `ApiClient.last.stack_id.present?` is `false` (binding LHS: token's stack scope is nil, not equal to stack A's id).
3. Extract `token` from the parsed `ccmenu_url` query string.
4. `GET :show` on `Api::CCMenuController` (or equivalent route) with `params: { stack_id: stacks(:cyclimse).to_param, token: token }` for an unrelated fixture stack B the user has no access to.
5. Assert response is `:ok` (rendering stack B's CCMenu XML) instead of the expected `:forbidden`/`:not_found`, proving the token issued for stack A is valid for stack B.
