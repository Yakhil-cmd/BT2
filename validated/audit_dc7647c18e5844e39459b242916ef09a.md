### Title
Webhook signature verification is keyed off an unverified `repository.owner.login`/`organization.login` field while all event handlers act on a different unverified field (`repository.full_name`), enabling cross-repository webhook forgery whenever any configured GitHub organization has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* `GitHubApp` (and therefore which `webhook_secret`) to validate a webhook against using `repository_owner`, a field read directly from the still-unverified JSON body [1](#0-0) . However, every event handler subsequently determines *which* `Repository`/`Stack` to act on using a completely different field of that same unverified body — `repository.full_name` [2](#0-1) . Because `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever `webhook_secret` is blank — an explicitly supported/documented configuration state [3](#0-2)  — an attacker who targets an organization with no configured secret can freely choose the `repository.full_name` value and forge webhook events against **any repository tracked by the same Shipit instance**, including ones belonging to organizations that do have a webhook secret configured.

### Finding Description
The authentication boundary and the write boundary are bound to two different, both attacker-controlled, fields of the same request body:

- Authentication is keyed on `repository_owner`: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, used to fetch the relevant `GitHubApp` and its `webhook_secret` [1](#0-0) [4](#0-3) .
- The actual write target is keyed on `repository.full_name`, used by the base `Handler` class (and every concrete handler such as `PushHandler`) to look up `Repository`/`Stack` records to mutate [2](#0-1) [5](#0-4) .

Shipit explicitly supports running with multiple GitHub App configurations, one per organization [6](#0-5) , and explicitly documents `webhook_secret` as *optional* per organization [7](#0-6) . The default/example secrets templates ship with `webhook_secret: null` [8](#0-7) , and `verify_webhook_signature` treats a blank secret as "always verified" [3](#0-2) .

Consequently, if even one organization managed by this Shipit instance has no `webhook_secret` set (a documented, supported configuration, not a misconfiguration outside the documented setup), an unauthenticated attacker can:
1. Send `POST /webhooks` with `X-Github-Event` set to any handled event.
2. Set `repository.owner.login` (or `organization.login`) to the secret-less organization, so `verify_signature` resolves to that org's `GitHubApp` and `verify_webhook_signature` returns `true` unconditionally — no valid `X-Hub-Signature` is required at all.
3. Set `repository.full_name` to any *other* repository tracked by Shipit — including one belonging to an organization that *does* enforce webhook signatures.

Because the handler layer never re-checks that `repository.full_name`'s organization matches the organization that was actually authenticated, the forged event is processed as if GitHub itself had sent it for the target repository.

### Impact Explanation
This breaks the equality binding "organization authenticated == repository written." An attacker can forge push, pull_request, status, check_suite, or membership events for any repository Shipit tracks, as long as any single configured organization lacks a webhook secret. Concretely this allows:
- Forged `push` events to trigger `GithubSyncJob` with an attacker-chosen `expected_head_sha` for an unrelated repository's stacks [9](#0-8) .
- Forged `pull_request` events to archive/unarchive review stacks, update PR metadata, or influence merge-queue-relevant records for repositories outside the attacker's own controlled organization [10](#0-9) [11](#0-10) .
- Forged `membership` events, which create/modify `Team`/`Membership` records used for authorization (`Shipit.github_teams`) purely from unverified payload data.

This is a cross-repository write achieved without any credential, satisfying the "Critical" impact bar (cross-repository writes / unauthorized state changes via forged GitHub events).

### Likelihood Explanation
Exploitation requires no session, no `ApiClient` token, and no knowledge of any secret — only that at least one configured GitHub organization on the instance has `webhook_secret` unset, which is the documented default/optional state and the value shipped in the example secrets templates. Given Shipit explicitly supports multi-organization deployments, an operator adding a new, less-critical organization without immediately configuring its webhook secret is a realistic and likely occurring scenario, and the resulting exposure silently extends to every other repository/organization managed by the same instance.

### Recommendation
Do not let an unverified field select the verification key that then gates writes to a different unverified field. Concretely:
- Bind signature verification to the same field used for locating the target repository (`repository.full_name`), or verify that `repository.full_name`'s organization matches `repository_owner` after selecting the `GitHubApp`.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in production; either require a secret for every configured organization or refuse to process events for organizations without one.
- Reject/log-and-drop events where the derived `repository_owner` does not match the organization portion of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `orgA` (no `webhook_secret` set) and `orgB` (secret `S` configured, and Shipit tracks `orgB/private-repo`).
2. As an unauthenticated attacker, POST to `/webhooks`:
```
POST /webhooks
X-Github-Event: push

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/private-repo"
  }
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` to `"orgA"`, fetches `orgA`'s `GitHubApp`, and calls `verify_webhook_signature` which returns `true` immediately because `orgA.webhook_secret` is blank [3](#0-2) .
4. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("orgB/private-repo")` [2](#0-1)  and enqueues `GithubSyncJob` for `orgB/private-repo`'s stacks with the attacker-supplied `expected_head_sha` — despite `orgB` having a properly configured webhook secret that was never checked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
