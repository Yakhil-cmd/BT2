### Title
Largest-remainder apportionment in `pox_5_make_signer_set` grants +1 weight per distinct signer key, letting an attacker inflate total signing weight by splitting one staker's STX across many self-controlled keys - ([File: stackslib/src/chainstate/nakamoto/signer_set.rs])

### Summary
`pox_5_make_signer_set` computes each signer's base weight as `stacked_amt / threshold` and then hands out any leftover reward slots one‑per‑entry in descending remainder order. Because the aggregation map is keyed by `signer_key` (not by underlying staker), an attacker who registers many distinct signer keys and splits the same aggregate STX across them (each above `SIGNER_SET_MIN_USTX` but below `threshold`) can collect multiple leftover "+1" awards instead of the single one a consolidated entry would compete for, inflating total weight relative to locked value. (Note: the question cites `stackslib/src/chainstate/stacks/db/snapshot/clarity.rs`, but that file does not contain this logic; the real code is in `stackslib/src/chainstate/nakamoto/signer_set.rs`.)

### Finding Description
The broken equality: for one staker's aggregate locked STX `S` behind a single signer key, `weight ∈ {floor(S/T), floor(S/T)+1}`. The claimed invariant is that splitting `S` across `N` self-controlled signer keys should not change this bound, i.e. `Σ weight_i <= ceil(S/T)`.

Code path: `pox_5_stake_entries`/`StakeEntryIteratorPox5::fallible_next` walks the per-cycle linked list, yielding one `RawPox5Entry{amount_ustx, signer_key}` per registered `signer_key` whose aggregate delegated STX has already crossed `SIGNER_SET_MIN_USTX` (comment at [1](#0-0) ). `pox_5_make_signer_set` then aggregates strictly `by signer_key` into a `HashMap`: [2](#0-1) 

`threshold = max(1, total_ustx_locked.div_ceil(reward_slots))` is computed over the *entire network's* locked STX for the cycle, not just the attacker's, so it can be far larger than the flat `SIGNER_SET_MIN_USTX` (50,000 STX) floor: [3](#0-2) 

Base weight and remainder are computed per signer_key, and any `leftover = reward_slots - Σ weight` is awarded one full unit per entry, sorted by descending remainder: [4](#0-3) 

Root cause: the leftover round's `+1` is a fixed per-entry bonus independent of the entry's stake size, and entries are never re-aggregated by the underlying staker/principal — only by `signer_key`. An attacker who is their own signer (via `register-signer`/`grant-signer-key`, reachable unprivileged as shown by `test-pox-5-signer.clar`'s `register-self`) can mint many distinct signer keys, each crossing the flat 50,000-STX `SIGNER_SET_MIN_USTX` floor to enter the linked list, but each kept below the *dynamic* `threshold`. Each such split entry then floors to weight 0 and enters the leftover lottery with its own remainder, so the attacker can win up to `N` leftover awards instead of the single one a consolidated stake would be limited to.

None of the existing guards address this: `verify-not-prepare-phase`, `check-pox-lock-period`, and `verify-signer-key-grant` only govern who may stake/register and when, not how many independent `signer_key`s one beneficiary may control or how their weights are aggregated for reward-slot apportionment.

### Impact Explanation
The attacker gains extra `weight` entries in the `.signers` reward-set/stackerdb assignment beyond what their locked STX would earn as a single signer, at the direct expense of the fixed, network-wide leftover-slot pool (`reward_slots - Σ floor(stacked/threshold)`). This is signing weight/reward-slot allocation exceeding locked value — the "High" impact category explicitly listed in scope. It also degrades honest signers' fair share of the largest-remainder round, since the pool of leftover slots is finite and shared across the whole network. This is repeatable every reward cycle in which the attacker restakes with freshly split keys.

### Likelihood Explanation
Preconditions are all attacker-controlled and require no privileged role: deploy a signer-manager contract (or several), self-grant multiple `signer-key`s via `grant-signer-key`/`register-signer`, and issue multiple `stake` calls each with an amount at or above `SIGNER_SET_MIN_USTX` (50,000 STX) but below the cycle's dynamic `threshold`. The attacker needs enough capital to fund each split above the 50,000-STX floor (cost scales with number of keys, not preventing the exploit, only its scale), and needs an estimate of `threshold`, which is computable from public on-chain data (total currently-locked STX and `reward_slots()`). The gain per cycle is bounded by `min(N, reward_slots - Σ assigned)`, so the practical benefit depends on how much "leftover" capacity exists network-wide, but the mechanism itself is deterministic and reproducible.

### Recommendation
Aggregate stake by the underlying staker principal (or by signer-manager identity, if that is the intended trust boundary) before running the largest-remainder apportionment, not solely by `signer_key`; alternatively, cap the number of leftover slots any single controlling principal can win, or make the leftover-round award proportional to remainder magnitude rather than a flat +1 per entry regardless of how many keys a beneficiary splits their stake across.

### Proof of Concept
Extend the existing `pox_5_make_signer_set_props` (referenced in `stackslib/src/chainstate/nakamoto/tests/signer_set.rs`) with a test that:
1. Builds a baseline set of honest `RawPox5Entry`s summing to some `total_ustx_locked` and computes `threshold` via `pox_constants.reward_slots()`.
2. Constructs entry set A: one entry with `stacked_amt = S` under a single `signer_key`.
3. Constructs entry set B: `N` entries under `N` distinct `signer_key`s, each `amount_ustx = S/N` (each `>= SIGNER_SET_MIN_USTX`, each `< threshold`), summing to the same `S`, mixed into the same honest background set so `total_ustx_locked` and `threshold` are identical between A and B.
4. Runs `NakamotoSigners::pox_5_make_signer_set` on both and asserts:
   - `Σ weight` over set-B's attacker keys `> ceil(S/threshold)` (demonstrating the break), and
   - specifically that it can exceed `floor(S/threshold)+1`, the maximum a single consolidated entry could achieve — for `N` chosen large enough relative to the available `leftover` pool.

            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
            })
            .collect();

        // Guaranteed `<= reward_slots` by the ceil quota, so leftover does not underflow.
        let assigned: u128 = apportioned.iter().map(|entry| entry.weight).sum();
        let mut leftover = reward_slots.saturating_sub(assigned);

        if leftover > 0 {
            // Largest fractional remainder wins the next slot; ties broken by signing_key
            // ascending so the apportionment is deterministic (and matches the final sort).
            apportioned.sort_by(|a, b| {
                b.remainder
                    .cmp(&a.remainder)
                    .then_with(|| a.signing_key.cmp(&b.signing_key))
            });
            for entry in apportioned.iter_mut() {
                if leftover == 0 {
                    break;
                }
                entry.weight += 1;
                leftover -= 1;
            }
        }
