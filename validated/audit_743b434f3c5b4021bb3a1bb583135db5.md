### Title
Webhook signature verification selects the GitHub App by an unverified `repository.owner.login` field, allowing signature bypass for a different (victim) repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) is used to validate the HMAC signature based on a value taken directly out of the still-unverified JSON body. The repository that is actually acted upon by the downstream handlers is taken from a *different* field of that same unverified body (`repository.full_name`). These two fields are never cross-checked, so an attacker can pick an organization whose app config has no `webhook_secret` set (verification trivially returns `true`) while making the payload's `repository.full_name` point at any other Stack tracked by the instance.

### Finding Description
`verify_signature` derives the organization used for verification purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a per-organization `GitHubApp` instance built from `Shipit.secrets.github`, and `verify_webhook_signature` short-circuits to `true` when that organization's `webhook_secret` is blank: [3](#0-2) 

Multi-organization configuration is an explicitly documented, first-class feature, and `webhook_secret` is documented as optional per organization: [4](#0-3) [5](#0-4) 

After (non-)verification, the controller dispatches the *entire raw, unvalidated* payload to the registered handlers: [6](#0-5) 

Nothing re-derives or re-checks `repository_owner` inside the handlers; they operate on whatever `repository`/`repository.full_name` value is embedded in the JSON body (confirmed by the push-event test asserting `GithubSyncJob` is enqueued for the stack matching the payload's `repository` data): [7](#0-6) 

The binding that should hold is:
`organization whose signature was cryptographically verified` == `organization/repository whose state is mutated by the handler`.

This binding is broken because the field used to select the verifying secret (`repository.owner.login` / `organization.login`) is independent of the field used by handlers to identify the target repository/stack (`repository.full_name`), and both live in the same unauthenticated request body.

### Impact Explanation
If any organization configured in `Shipit.secrets.github` has a blank/missing `webhook_secret` (which the documentation explicitly allows as "optional"), an unauthenticated attacker can craft a POST to `/webhooks` with:
- `X-Github-Event: push` (or `status`, `check_suite`, etc.)
- payload `repository.owner.login` (or `organization.login`) = the org with no secret
- payload `repository.full_name` = `victim-org/victim-repo`, a repository actually tracked by a Stack on the instance

`verify_signature` will pass unconditionally (`return true unless webhook_secret`), and the handlers will then act on the forged `victim-org/victim-repo` data — e.g. enqueueing `GithubSyncJob` with attacker-chosen commit SHAs, or forging `status`/`check_suite` results that satisfy deploy-gating checks (`deployable_status`, CI checks) for the victim stack. Depending on the target handler this enables forged commit statuses that unlock the merge/deploy queue, i.e. an unauthorized deploy — a Critical impact per the engine's own trust model, since it lets an external, unauthenticated party inject state into a repository/stack whose organization never signed the request.

### Likelihood Explanation
Requires only that the Shipit deployment configures more than one GitHub App/organization (a documented supported configuration) and that at least one configured organization lacks a `webhook_secret` — a state the setup docs list as acceptable/optional. No credentials, GitHub App keys, or prior authentication are needed; the request is a plain unauthenticated HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Bind the field used for verification to the field used for repository resolution: after selecting the `GitHubApp` config, verify that `repository.full_name`'s owner matches `repository_owner`/the app's configured organization, and reject organizations with no configured secret unless explicitly allowed with additional integrity checks (e.g., requiring a mandatory `webhook_secret` for every configured organization rather than making it optional).

### Proof of Concept
1. Configure Shipit with two organizations under `github:` in `secrets.yml`: `attacker-org` (no `webhook_secret`) and `victim-org` (tracked stack `victim-org/victim-repo`, has a `webhook_secret`).
2. Send:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-empty

{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
3. `repository_owner` resolves to `attacker-org`; `Shipit.github(organization: 'attacker-org').verify_webhook_signature` returns `true` because `webhook_secret` is blank for that org (`lib/shipit/github_app.rb:76-83`).
4. `Shipit::Webhooks.for_event('push')` handlers process the payload and act on `victim-org/victim-repo`, using the attacker-supplied `after` SHA, despite the request never being validated against `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

  github:
    somegithuborg:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
