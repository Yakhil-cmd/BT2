### Title
Cross-stack commit status forgery via unscoped SHA lookup in `StatusHandler#process`, amplified by `ignore_ci` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `Commit.where(sha: params.sha)` with no constraint tying the write to the repository/organization that authenticated the webhook, so a `status` event carrying a SHA that also exists as a `Commit` row in an unrelated stack will write a `Status` into that unrelated stack. Combined with `Commit#deployable?`'s `ignore_ci` short-circuit, this status write is capable of flipping deployability on a victim stack that never received CI signal from the actual authenticating repository.

### Finding Description
The broken binding is: **the `Status` written for a given `sha` should only be attributable to the repository whose GitHub App/organization signed the webhook** — i.e. `status.stack.github_repo_name == repository_owner/full_name from the verified payload` — but the code enforces no such equality.

Trace:
- `Shipit::WebhooksController#create` runs `before_action :verify_signature`, which validates the HMAC using `Shipit.github(organization: repository_owner)` [1](#0-0) . This only proves the payload came from GitHub for that organization/app installation — it does not bind the event to a specific stack or restrict which `Commit` rows may be touched.
- The controller then dispatches to `Shipit::Webhooks.for_event('status')` → `Handlers::StatusHandler` [2](#0-1) .
- `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
This query has **no repository/stack scoping** (no filter on `stack_id`, `stack.github_repo_name`, or the payload's `repository.full_name`) — every `Commit` record across every stack in the installation that shares that SHA gets a new `Status` row, each written into that commit's *own* `stack_id` via `create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) [5](#0-4) .
- On the victim side, `Commit#deployable?` is: `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [6](#0-5) . When `stack.ignore_ci?` is true, the injected status is irrelevant to `deployable?` directly (CI is already ignored) — however, the injection still: (a) fires `enable_ci_on_stack`/`schedule_continuous_delivery` side effects [7](#0-6) , and (b) can flip `blocked?`/`blocking?` state for *other* commits on the victim stack (via `stack.blocking_statuses`), and can be used to force `state`/`success?`/`failure?` transitions that drive `ProcessMergeRequestsJob` and continuous-delivery scheduling on a stack the attacker never authenticated against [8](#0-7) .

Existing guards checked and found insufficient: `verify_signature` only authenticates the *sender org*, not the target stack/commit [9](#0-8) ; `drop_unhandled_event` and the `ExplicitParameters` schema on `StatusHandler` only validate shape (`sha`, `state`, `context`, etc.), not repository ownership [10](#0-9) ; no `require_permission!`/`User#authorized?` check applies to webhook processing at all.

However, this depends on a real SHA collision between two `Commit` rows belonging to different stacks/repositories. Git SHAs are cryptographically derived from tree+parents+author+message+timestamp; an attacker cannot forge an arbitrary SHA to match an unrelated victim commit. The only realistic collision vector is when the **same underlying commit genuinely exists in both the attacker-controlled repo and the victim's tracked repo** (e.g., a fork sharing history, or multiple Shipit stacks configured against the same GitHub repo for different environments/branches that happen to import the same commit). In the fork case, the attacker's fork is a different GitHub repository (different `full_name`), but if the Shipit app is installed on the attacker's fork and a shared ancestor commit is also tracked as a `Commit` row on the victim's stack (upstream repo), the attacker can send a `status` webhook from their own fork/org (validly signed with their own repo's secret) referencing that shared SHA, and `StatusHandler` will apply it to the victim's `Commit` row too, because the lookup is by bare SHA with no cross-repo isolation.

### Impact Explanation
A record (a `Status`) is written for a stack that did not authenticate the event, satisfying the "payload for one repository mutating another's stack/commit" category (Critical) when the collision precondition is met — writes affect `Status.state/context`, drive `stack.enable_ci!`, `schedule_continuous_delivery`, and `ProcessMergeRequestsJob`, and influence `blocked?`/`state` computations that gate deploys and merges on the victim stack. The attack is repeatable per shared-SHA commit and scales to any number of victim stacks that happen to track a commit shared with an attacker-controlled repository.

### Likelihood Explanation
Preconditions are non-trivial: the attacker needs (1) a repository they control with the Shipit GitHub App/webhook installed (so their own signature verifies), and (2) a genuine SHA overlap with a `Commit` row belonging to a victim stack — this is not attacker-forgeable and only occurs in specific topologies (shared git history via forks, or multiple stacks tracking the same upstream repo/branches). The `ignore_ci true` amplification described in the question does not materially increase impact for the injected status itself, since `deployable?` bypasses CI entirely in that mode; the real exposure is the unscoped write itself (state/blocking effects), independent of `ignore_ci`.

### Recommendation
Scope `StatusHandler#process` (and analogously any handler resolving records by bare SHA) to the repository that authenticated the webhook: filter `Commit.where(sha: params.sha)` further by `stack.github_repo_name == repository_full_name` (or `repository_owner`/`repo_name` derived from the verified payload) before calling `create_status_from_github!`, so a status only ever mutates commits belonging to stacks tracking the exact repository that sent it.

### Proof of Concept
```ruby
test "status webhook for one repo does not mutate a commit belonging to a different stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit) # e.g. github_repo_name = 'shopify/shipit-engine'
  victim_stack.update!(ignore_ci: true)
  attacker_stack = shipit_stacks(:cyclimse) # e.g. github_repo_name = 'attacker/fork'

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit),
    committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now, message: 'shared')
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'shared')

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  payload = {
    'sha' => shared_sha, 'state' => 'success',
    'context' => 'continuous-integration/travis-ci',
    'repository' => { 'full_name' => attacker_stack.github_repo_name, 'owner' => { 'login' => 'attacker' } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body: payload.to_json, as: :json
  end
  # currently FAILS: victim_commit.statuses.count increases by 1, proving the unscoped write.
end
```
The equality that must hold both before and after processing: `victim_commit.statuses.count(before) == victim_commit.statuses.count(after)` when the webhook's authenticated repository (`attacker_stack.github_repo_name`) differs from `victim_commit.stack.github_repo_name`. Current code violates this equality because `StatusHandler#process` performs no repository check.
