Found the ccmenu_controller.rb match — that's the one binding worth flagging: the CCMenu endpoint authenticates via a query-string `token` rather than the standard `BasicAuth` scheme, and the token it accepts authorizes a `read:stack` scope on the stack whose `stack_id` is looked up independently of the token's own `stack_id` binding.

### Title
Query-string CCMenu token authorizes `read:stack` on any stack, not just the stack it was scoped to - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#authenticate_api_client` overrides the base authentication to accept a bare `params[:token]` and, on success, calls `super` only as a fallback. `Api::BaseController#stack` scopes lookups to `current_api_client.stack_id` when present [1](#0-0) , but `CCMenuController#stack` bypasses that scoping entirely and does a raw `Stack.from_param!(params[:stack_id])` [2](#0-1) .

### Finding Description
The binding that should hold is: `ApiClient#stack_id` (the stack the token was scoped to when created via `CCMenuUrlController#client`) `==` the stack actually rendered by `CCMenuController#show`. `CCMenuUrlController` creates a scoped `ApiClient` with `permissions: %w[read:stack]` and binds it to one specific stack via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, embedding its `authentication_token` in a URL for that stack [3](#0-2) . This token is designed to be handed to CI dashboard software (CCMenu clients) and is not treated as highly secret, since its permission is deliberately narrowed to a single stack.

However, `CCMenuController` does not go through `BaseController#stack`, which enforces the `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` restriction before locating a stack by param [1](#0-0) . Instead it defines its own `stack` method that resolves `params[:stack_id]` against the full `Stack` table regardless of which stack the authenticated `ApiClient` is bound to [2](#0-1) . The `require_permission :read, :stack` check only verifies that the token carries the `read:stack` permission string via `ApiClient#check_permissions!` [4](#0-3)  — it never checks `stack_id` equality to the requested `stack_id`.

So the equality that should be enforced (`current_api_client.stack_id == stack.id` whenever `current_api_client.stack_id?`) is never checked in this controller, even though it is exactly what `BaseController#stacks` was built to enforce for every other API endpoint.

### Impact Explanation
An attacker who obtains one team's CCMenu token URL (these URLs are routinely embedded in unauthenticated CI dashboard tools, shared over chat, or committed to config files, since they were only ever meant to grant read access to one stack) can request `CCMenuController#show` for an arbitrary `stack_id` and get an unauthenticated read of another stack's deploy state, output/build status, and lock status — the exact "unauthorized read of stack state, task streams or deploy output" scenario, achieved purely by an unprivileged party with any single CCMenu token, not the specific stack owner's.

### Likelihood Explanation
Likelihood is straightforward: obtaining any one CCMenu token (a low-privilege, narrowly-scoped credential intentionally shared for CI dashboard consumption) is sufficient; no repository write access, GitHub App key, or session is required. The only action needed is substituting a different `stack_id` in the request, which the code accepts unconditionally.

### Recommendation
Change `Api::CCMenuController#stack` to reuse `BaseController#stack`/`#stacks` (i.e., `stacks.from_param!(params[:stack_id])`) so the `current_api_client.stack_id` scoping is enforced identically to every other API endpoint, closing the gap between the stack the token authorizes and the stack it can actually read.

### Proof of Concept
1. Team A calls `GET /:stack_id/ccmenu_url` for `stack-A`, obtaining a URL of the form `.../ccmenu?token=<token-A>` where `token-A` is an `ApiClient` scoped with `stack_id = stack-A.id` and `permissions: ['read:stack']` [3](#0-2) .
2. An attacker who obtains `token-A` (e.g., from a public CI dashboard config) sends `GET /api/stacks/stack-B/ccmenu?token=token-A`.
3. `CCMenuController#authenticate_api_client` verifies `token-A` successfully (it is a valid, unexpired `ApiClient`) [5](#0-4) .
4. `require_permission :read, :stack` passes because `token-A`'s permissions include `read:stack` [6](#0-5) .
5. `CCMenuController#stack` resolves `stack-B` directly via `Stack.from_param!(params[:stack_id])`, ignoring that `token-A.stack_id == stack-A.id` [2](#0-1) .
6. The response renders `stack-B`'s deploy status, unauthorized cross-stack read achieved with a token that was never meant to authorize access to `stack-B`.
