### Title
Unsanitized certificate-derived repo/workflow strings printed to terminal in `gh attestation verify` - (File: pkg/cmd/attestation/verify/verify.go)

### Finding Description
`extractAttestationDetail` extracts `match[1]` verbatim from the Fulcio certificate's `BuildConfigURI`/`BuildSignerURI` extensions [1](#0-0) , and `runVerify` passes these raw strings directly to `opts.Logger.Printf` and `opts.Logger.PrintBulletPoints` without any escaping [2](#0-1) . `Handler.Printf` and `Handler.PrintBulletPoints` write these values with plain `fmt.Fprintf`/`fmt.Fprintln` to the TTY error stream with no control-character stripping [3](#0-2) [4](#0-3) .

Notably, the codebase already contains a purpose-built defense for exactly this class of bug: `pkg/iostreams/untrusted.go`'s `Untrusted` type sanitizes ANSI/control sequences from any string routed through it (verified by `TestUntrusted_String_sanitizes` and `TestUntrusted_fmt_paths_never_leak`) [5](#0-4) , and there is a dedicated acceptance test (`acceptance/testdata/workflow/run-view-log-escape-sequences.txtar`) confirming the project treats escape-sequence injection from remote-controlled data (e.g., Actions run logs) as a real concern that must be mitigated elsewhere in the CLI. However, `extractAttestationDetail`'s output in `verify.go` is never wrapped in `Untrusted` before being printed, so this specific attestation-verification code path bypasses the existing mitigation.

The certificate's `BuildConfigURI`/`BuildSignerURI` values are derived from the repository name, workflow file path, and git ref of the workflow that produced the attestation — values an attacker fully controls by owning the repo whose attestation the victim chooses to verify (`gh attestation verify --repo attacker/repo`).

### Impact Explanation
If an attacker can get any of the repository name, workflow file path, or job/ref components embedded in the OIDC-derived certificate extension to include ANSI/terminal control sequences, the victim's terminal could render spoofed prompts, hide/alter output, or (depending on terminal emulator) trigger other escape-sequence-driven behavior when running `gh attestation verify`. This maps to a terminal/output-injection impact class, moderate severity, contingent on the victim's terminal being vulnerable to escape sequence abuse and the actual character set permitted in the underlying GitHub identifiers.

### Likelihood Explanation
Feasibility is constrained by GitHub/git's own character restrictions, which I could not fully verify from this repository alone:
- Git ref names (branches) are restricted by `git check-ref-format`, which forbids ASCII control characters (including ESC, 0x1B) — this likely blocks the ref/ branch portion of the string.
- GitHub repository/owner names are restricted to a limited alphanumeric/hyphen/underscore/period charset, blocking that component too.
- The workflow **file path** component (e.g., `.github/workflows/<name>.yml`) is a git tree pathname; git tree entries generally only forbid NUL and `/` in path components, so it is less certain whether GitHub's repository/file-creation APIs and UI enforce a stricter allowlist that would also block control characters there. This is the most plausible injection vector but I cannot confirm from the codebase whether such characters are actually permitted end-to-end (repo creation, git commit, Fulcio certificate issuance).

Given this uncertainty on the exact allowed character set, the concrete exploitability of injecting `\x1b[` bytes specifically into the workflow path is not proven here, but the code path itself is a genuine gap: the output is not defensively sanitized even though the project already maintains an `Untrusted` sanitizer for this exact purpose.

### Recommendation
Wrap the extracted `sourceRepoAndOrg`, `sourceWorkflow`, `signerRepoAndOrg`, and `signerWorkflow` values (and any other certificate-derived strings that get printed) in `iostreams.NewUntrusted(...)` before passing them to `Logger.Printf` / `PrintBulletPoints`, consistent with how other untrusted, remote-controlled text (e.g., Actions run logs) is already handled in this codebase. Alternatively, apply a control-character/ANSI-stripping filter inside `Handler.Printf`/`Handler.PrintBulletPoints` for any values that originate from certificate extensions rather than static format strings.

### Proof of Concept
```go
// pkg/cmd/attestation/verify/verify_test.go
func TestExtractAttestationDetail_ControlCharsNotSanitized(t *testing.T) {
    malicious := "https://github.com/foo/bar/.github/workflows/\x1b[31mFAKE\x1b[0m.yml@refs/heads/main"
    orgAndRepo, workflow, err := extractAttestationDetail("", malicious)
    require.NoError(t, err)
    // Demonstrates the raw ANSI escape bytes survive extraction unmodified
    assert.Contains(t, workflow, "\x1b[31m")
    _ = orgAndRepo
}
```
Extend with an integration test that constructs a `verification.AttestationProcessingResult` whose `Signature.Certificate.Extensions.BuildSignerURI` contains the crafted string above, run it through `verifyAttestations`/`runVerify` against a test `io.Handler` backed by a TTY-simulated `iostreams.Test()`, and assert that the captured `ErrOut` buffer still contains raw `\x1b[` bytes — proving no sanitization occurs before terminal output, in contrast to `TestUntrusted_String_sanitizes` in `pkg/iostreams/untrusted_test.go` which shows the expected sanitized behavior once `Untrusted` is applied.

```go
func (h *Handler) PrintBulletPoints(rows [][]string) (int, error) {
	if !h.IO.IsStdoutTTY() {
		return 0, nil
	}
	maxColLen := 0
	for _, row := range rows {
		if len(row[0]) > maxColLen {
			maxColLen = len(row[0])
		}
	}

	info := ""
	for _, row := range rows {
		dots := strings.Repeat(".", maxColLen-len(row[0]))
		info += fmt.Sprintf("%s:%s %s\n", row[0], dots, row[1])
	}
	return fmt.Fprintln(h.IO.ErrOut, info)
}
```

```go
		"%v":     fmt.Sprintf("%v", u),

		"woven":  fmt.Sprintf("by %s here", u),
	}
	for name, out := range cases {
```
