### Title
RAY total-value integer overflow permanently freezes an oversized utilized market - (File: `common/src/rates/index.rs`)

### Summary
A market whose scaled debt multiplied by its updated borrow index exceeds `i128::MAX` cannot complete interest accrual. Because ordinary repayments, withdrawals, liquidations, and index updates all synchronize the market first, the first successful operation that pushes accrued value past that bound causes every later market operation to panic with `MathOverflow`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`update_borrow_index` computes `old_index * interest_factor` before checking `MAX_BORROW_INDEX_RAY`, and `calculate_supplier_rewards` then computes `borrowed * old_borrow_index` and `borrowed * new_borrow_index` in the fixed `i128`-backed RAY domain. [4](#0-3) [5](#0-4) 

The underlying `mul_div_half_up` widens the intermediate product to `I256`, but still requires the final quotient to fit `i128` and returns `MathOverflow` when it does not. [6](#0-5) 

`global_sync` invokes this accrual path before advancing market time, so a failed chunk leaves `last_timestamp` stale and the overflowing calculation remains reachable on every subsequent synchronization attempt. [7](#0-6) 

The controller exposes permissionless `update_indexes(caller, assets)`, plus caller-authorized `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, and `clean_bad_debt` entrypoints that reach the same pool market synchronization. [8](#0-7) [9](#0-8) 

The repository's regression test demonstrates a market with `1e9` eighteen-decimal whole tokens supplied and 98% borrowed reaching `MathOverflow` before `MAX_BORROW_INDEX_RAY`, after which both a one-unit withdrawal and a repayment panic. [10](#0-9) 

### Impact Explanation
Once the total scaled RAY value crosses the representable bound, suppliers cannot withdraw, borrowers cannot repay, liquidators cannot reduce risk, and `update_indexes` cannot advance the market past the failing timestamp. [2](#0-1) [11](#0-10) 

This permanently freezes the affected market's token funds and can leave debt insolvent because no normal repayment or liquidation path can run after the first overflowing accrual. [12](#0-11) [13](#0-12) 

A bad-debt write-down does not avoid the condition: `apply_bad_debt_to_supply_index` computes `supplied * supply_index` before writing down the index, so it hits the same RAY-value ceiling when total supplied value is the overflowing operand. [14](#0-13) 

### Likelihood Explanation
An unprivileged participant can create the required state by supplying an allowed market asset and another account can borrow it, subject only to the configured supply/borrow caps, available collateral, and ordinary solvency checks. [15](#0-14) [9](#0-8) 

The numeric bound is large but finite: the documented admitted cap is approximately 170.14 billion whole tokens at the relevant decimal scaling, while accrued market totals can still overflow independently before the index ceiling. [16](#0-15) 

The demonstrated scenario requires an oversized market and sustained high utilization for multiple years rather than a single small transaction, so practical likelihood depends on listing a sufficiently high-cap/high-supply token and keeping utilization on the steep part of its rate curve. [17](#0-16) [18](#0-17) 

### Recommendation
Prevent the total scaled RAY value from approaching `i128::MAX` by enforcing a market-level scaled supply/debt ceiling that includes projected index growth, or make accrual clamp debt value/index atomically before the final `i128` conversion can overflow. [4](#0-3) [12](#0-11) 

At minimum, cap usage in the same scaled domain before admitting supply or borrows and add an emergency accrual path that records the index ceiling without evaluating an unrepresentable total debt product. [19](#0-18) [2](#0-1) 

### Proof of Concept
1. Create an 18-decimal market, set its caps high enough to admit `1_000_000_000 * 10^18` base units, and supply that amount through `Controller::supply(caller, account_id, spoke_id, [(hub_asset, amount)])`. [20](#0-19) [21](#0-20) 
2. From a sufficiently collateralized account, borrow 98% of that market through `Controller::borrow(caller, account_id, [(hub_asset, debt)], to)`. [22](#0-21) [23](#0-22) 
3. Advance ledger time and call `Controller::update_indexes(caller, vec![hub_asset])` until the accrual returns `MathOverflow`; the test asserts this happens before `MAX_BORROW_INDEX_RAY`. [24](#0-23) [25](#0-24) 
4. Attempt `withdraw(account_id, vec![(hub_asset, 1)], None)` or `repay(account_id, vec![(hub_asset, amount)])`; both synchronize first and panic with the same `MathOverflow`, leaving the market unable to process normal recovery operations. [26](#0-25) [27](#0-26)

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);

/// Accrues borrow/supply indexes from `last_timestamp` to the cache's current time.
///
/// No-op when no time has elapsed. Splits long gaps into max-sized compound
/// windows, then sets `last_timestamp` to `current_timestamp`.
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Socializes `bad_debt` by reducing the supply index (capped at total supply value).
///
/// Used when seizing unpaid debt: remaining supplier claims shrink pro-rata.
/// No-op when total supplied value is zero. Floors the resulting index at
/// [`SUPPLY_INDEX_FLOOR_RAW`] to avoid a zero index.
pub(crate) fn apply_bad_debt_to_supply_index(cache: &mut Cache, bad_debt: Ray) {
    let total_supplied_value = cache.supplied().mul(cache.env(), cache.supply_index());

    if total_supplied_value == Ray::ZERO {
        return;
    }

    let capped = bad_debt.min(total_supplied_value);
    let remaining = total_supplied_value.checked_sub(cache.env(), capped);

    let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
    let new_supply_index = cache
        .supply_index()
        .mul_floor(cache.env(), reduction_factor);

    cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}

| Bound | Consequence |
|---|---|
| Asset decimals 0..=18 | Exact token-to-RAY upscaling. Below 3: collateral only, no flash loans, no liquidation fee, its account's only supply position, at least 2 whole units while in debt |
| Both indexes initially RAY; ceiling 10^36 | 10^9 times initial index; protocol constants |
| Supply-index floor 10^24 | At most 1,000 times the shares minted at index one for the same deposit |
| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.

/// Converts an asset-unit `cap` to a scaled `Ray` value, rounding down.
///
/// The division saturates at `i128::MAX` instead of panicking, so the cap check
/// fails open rather than trapping an entry path. The asset-to-RAY
/// rescale still panics on overflow; listings validate caps with
/// [`crate::validation::require_cap_within_asset_domain`]. Position accounting
/// uses [`calculate_scaled_supply`] and [`calculate_scaled_borrow`], which panic
/// on overflow.
pub fn calculate_scaled_cap(env: &Env, cap: i128, decimals: u32, index: Ray) -> Ray {
    Ray::from(fp_core::mul_div_floor_saturating(
        env,
        Ray::from_asset(env, cap, decimals).raw(),
        RAY,
        index.raw(),
    ))
}
