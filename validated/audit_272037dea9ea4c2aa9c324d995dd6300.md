### Title
Missing `return` after caught exception in `handleSavedPrivatePayments` causes duplicate/racing processing of a private-payment chain - ([File: network.js])

### Summary
In `network.js`, the inner `validateAndSave` function inside `handleSavedPrivatePayments` computes a hash of an attacker/counterparty-supplied private-payment payload inside a `try {} catch (e) {}` block. When the hash computation throws, the `catch` block sends an error result and calls `deleteHandledPrivateChain(..., cb)` (which will eventually invoke the `async.each` iteration callback `cb()`), but execution is **not stopped** — there is no `return` after the `catch` block. Control falls through to build `key` from the now-`undefined` `json_payload_hash` and then calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` a second time, whose own callbacks (`ifOk`/`ifError`/`ifWaitingForChain`) will *also* eventually call `cb()`.

This is the same bug class as the reported `_commitPrice` issue: an operation whose success/failure is not properly gated is allowed to continue executing further, unchecked, state-mutating logic — leading to double invocation of a callback and a second, concurrent validation/save attempt on the same private-payment chain.

### Finding Description
```javascript
// network.js:2467-2504
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); // <-- eventually calls cb()
        // MISSING return here
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { // <-- runs anyway, will also call cb() eventually
        ifOk: function(){ ... deleteHandledPrivateChain(..., cb); eventBus.emit(key, true); },
        ifError: function(error){ ... deleteHandledPrivateChain(..., cb); eventBus.emit(key, false); },
        ifWaitingForChain: function(){ ... cb(); }
    });
};
``` [1](#0-0) 

`getBase64Hash` can throw when `getJsonSourceString`/`getSourceString` encounters a value it cannot serialize (e.g. malformed types inside the attacker-controlled `payload` object of a private-payment element) [2](#0-1) . This payload originates from `arrPrivateElements[0].payload`, which is fully attacker-controlled data received from a peer or the hub via `handleOnlinePrivatePayment`/`handlePrivatePaymentChains`, stored verbatim in `unhandled_private_payments.json` [3](#0-2) , and later re-read and processed by `handleSavedPrivatePayments` without re-validating its shape before the hash call.

Because the `catch` block does not `return`, both:
1. `deleteHandledPrivateChain(...)` (from the catch branch), and
2. `privatePayment.validateAndSavePrivatePaymentChain(...)` (falling through)

run against the *same* `arrPrivateElements`/row. `deleteHandledPrivateChain` deletes the DB row and calls `cb()` immediately, while `validateAndSavePrivatePaymentChain` independently proceeds to open its own DB transaction (`BEGIN`/validate/`COMMIT`) via `private_payment.js`'s `validateAndSavePrivatePaymentChain` [4](#0-3)  and will call `cb()` a second time on completion. This double invocation of the `async.each` iteratee callback breaks the invariant that each row's callback fires exactly once, and it can also emit the `private_payment_validated-...` event a second time with a different outcome than the one already communicated to the peer/hub via `sendResult`.

### Impact Explanation
`async.each`'s iteratee callback being invoked twice for a single row is normally itself an async-control-flow bug (extra completion signal / undefined behavior in the `async` library), but here it also causes the private-payment validation/save path (`validateAndSavePrivatePaymentChain`) to run for a chain that the code already treated as failed and removed from the pending queue. Because this path performs `INSERT`/`UPDATE` on `outputs`/`inputs` tables (marking outputs spent, inserting new ones) inside its own DB transaction, running it a second, unintended time for a chain whose row was already deleted, concurrently with unrelated `async.each` iterations, risks node-local double-processing/inconsistent private-payment/private-asset bookkeeping (outputs marked spent or private-asset chain inserted a second time), and duplicate/contradictory `private_payment_validated-*` events being delivered to `wallet.js`'s waiting logic in `handlePrivatePaymentChains`, which relies on exactly one deterministic accept/reject signal per chain [5](#0-4) . This can desynchronize the local wallet's view of private-asset balances/spend-state from what was actually committed, a fund-accounting inconsistency for private/indivisible-asset payments.

### Likelihood Explanation
Reachable by any unprivileged private-payment counterparty who can craft a malformed `payload` (e.g. non-serializable value) in the head element of a private-payment chain they send to the victim (directly or via hub) — this is exactly the "private-payment counterparty" trust boundary called out as in-scope. No node/hub/peer privilege is required; only the ability to submit a private-payment message triggers the `getBase64Hash` throw and the downstream missing-return double execution. However, exploiting it into an actually attacker-favorable state (vs. merely a callback double-fire) would require a specific payload shape that both throws in `getBase64Hash` and is still processable enough by `validateAndSavePrivatePaymentChain`; this needs to be confirmed with a concrete PoC input, which could not be fully verified here without executing the code (`getJsonSourceString`/`getSourceString` throw conditions were only inspected, not exhaustively enumerated).

### Recommendation
Add a `return;` at the end of the `catch` block in `validateAndSave` (network.js, around line 2477) so execution does not fall through to compute `key` from an undefined hash and re-invoke `privatePayment.validateAndSavePrivatePaymentChain` after the row has already been deleted and `cb()` already scheduled:
```javascript
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```
Additionally, validate the shape of `objHeadPrivateElement.payload` before attempting to hash it, so malformed peer-supplied data is rejected earlier and deterministically.

### Proof of Concept
1. An unprivileged peer (or hub) sends a `private_payments`/`private_payment` message whose head element's `payload` contains a value that `getJsonSourceString`/`getSourceString` cannot serialize (throws inside `object_hash.getBase64Hash`), e.g. a payload field with an unsupported type/structure.
2. `handleOnlinePrivatePayment` stores it in `unhandled_private_payments` [3](#0-2)  because it cannot be immediately validated (light client / chain not linked, or `ifWaitingForChain`).
3. `handleSavedPrivatePayments` later re-reads the row and calls `validateAndSave()` [6](#0-5) ; `getBase64Hash` throws, the `catch` fires, `deleteHandledPrivateChain(..., cb)` runs (eventually calling `cb()`), but code falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` a second time, which will itself later call `cb()` again — observable as `cb` being invoked twice per `async.each` iteration, plus duplicate `private_payment_validated-*` events with potentially conflicting `true`/`false` values, and duplicate DB write attempts against the already-deleted row's chain data.

function getBase64Hash(obj, bJsonBased) {
	var sourceString = bJsonBased ? getJsonSourceString(obj) : getSourceString(obj)
	return crypto.createHash("sha256").update(sourceString, "utf8").digest("base64");
}
