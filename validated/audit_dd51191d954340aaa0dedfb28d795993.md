No further guard exists — `ReviewStackAdapter#create!` unconditionally creates the stack and queues provisioning once `provision?` returns true. This confirms the vulnerability.

### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` repos - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends to gate all review-stack auto-provisioning behind `repository.review_stacks_enabled`, but Ruby's `&&`/`||` precedence causes `review_stacks_enabled` to only be ANDed with the `allow_all?` branch. For repositories configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`), a stack is auto-created and queued for provisioning even when `review_stacks_enabled` is `false`.

### Finding Description
The broken binding: the code assumes `repository.review_stacks_enabled == <flag gating all provisioning behaviors>`, but in reality `review_stacks_enabled` is only combined with `provisioning_behavior_allow_all?`.

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && labeled?) || (prevent_with_label? && !labeled?)`

So when `provisioning_behavior == :allow_with_label` and the PR carries `provisioning_label_name`, `provision?` returns `true` regardless of `review_stacks_enabled`.

Contrast with `LabeledHandler#respond_to_label_change?`, which correctly ANDs `review_stacks_enabled` across the *entire* `archive?/unarchive?` disjunction:
```ruby
def respond_to_label_change?
  params.action == "labeled" &&
    pull_request_state == "open" &&
    repository.review_stacks_enabled &&
    (archive? || unarchive?)
end
``` [2](#0-1) 

This confirms the intended design (review_stacks_enabled must gate all behaviors) and that `OpenedHandler#provision?` diverges from it.

Call path: `OpenedHandler#process` → `respond_to_pull_request_opened?` → `provision?` (true) → `ReviewStackAdapter.new(...).find_or_create!` [3](#0-2)  → `create!` unconditionally builds the stack from `params.pull_request.head.ref` and queues `Shipit::ReviewStackProvisioningQueue.add(stack)` with no further `review_stacks_enabled` check [4](#0-3) . `ProvisioningHandler::Base#provision?` is a no-op guard defaulting to `true` [5](#0-4) , so nothing downstream re-checks the flag before the queued provisioning task runs `deploy_steps` from the fork's `shipit.yml` via `PTY.spawn`.

Attacker request: fork the target repo, push a branch with a `shipit.yml` containing a malicious `deploy.override` command, open a PR from that branch with the repository's configured `provisioning_label_name` attached, and let GitHub deliver the `pull_request` `opened` webhook (a standard, unauthenticated action from the attacker's perspective — GitHub, not the attacker, sends the webhook, but the attacker fully controls its content by controlling their own PR/fork).

Existing guards do not stop this: `verify_signature`/webhook auth only validates the payload came from GitHub, not that the *content* is safe; the `ExplicitParameters` schema only validates payload shape; nothing in `Repository`, `ReviewStackAdapter`, or `ProvisioningHandler::Base` re-checks `review_stacks_enabled` before creating/queueing the stack.

### Impact Explanation
For any repository an operator configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) but explicitly left `review_stacks_enabled: false` (i.e., opted out of review-stack auto-provisioning), an unprivileged forker who can open a PR and add/have the configured label can still trigger automatic stack creation and provisioning. Provisioning subsequently executes the fork's `shipit.yml` deploy steps on the deploy host via `Command`/`PTY.spawn`, i.e., RCE on the deploy host driven by content from an untrusted fork, for a repository whose operator never enabled this feature. This is repeatable per PR/branch and applies to every repository sharing this misconfiguration-adjacent combination, matching the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category.

### Likelihood Explanation
Preconditions: `repository.review_stacks_enabled == false` and `repository.provisioning_behavior` set to `allow_with_label` (label present on PR) or `prevent_with_label` (label absent) — both realistic configurations, e.g., an operator who toggled the behavior dropdown but didn't (or couldn't, if UI ties them) separately disable the enabled flag, or reduced review_stacks_enabled after initially configuring behavior. The attacker only needs fork+PR+label capability, all of which are attacker-controlled with no privileged access required. This is a straightforward, deterministic, and repeatable exploit given the misconfiguration exists.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire disjunction, matching `LabeledHandler`'s pattern:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks for repos with allow_with_label when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::ReviewStackProvisioningQueue.expects(:add).never

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Asserting `review_stacks_enabled == false` (left side of the binding) must equal "no provisioning occurs" (right side, what `provision?` should test) — currently this test fails because a stack is created and queued despite `review_stacks_enabled: false`.
