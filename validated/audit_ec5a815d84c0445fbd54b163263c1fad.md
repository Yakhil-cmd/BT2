### Title
Interest accrual overflows the RAY debt value and permanently freezes an oversized market - (File: common/src/rates/scaling.rs)

### Summary

A sufficiently large borrowed balance can make `borrowed * borrow_index` exceed the `i128` domain even though the borrow index remains below `MAX_BORROW_INDEX_RAY`. [1](#0-0) 

Every subsequent market operation must first synchronize interest, so the resulting `MathOverflow` prevents repayment, withdrawal, liquidation, recapitalization, revenue claims, and explicit index updates from completing. [2](#0-1) 

### Finding Description

`accrue_step` starts by converting stored scaled debt into its original value with `scaled_to_original`, and `scaled_to_original` performs `scaled.mul(index)`. [3](#0-2) 

`Ray::mul` delegates to `mul_div_half_up`, which returns `MathOverflow` when the exact result does not fit in `i128`. [4](#0-3) 

The widened `I256` intermediate protects only the multiplication; conversion of the final quotient still fails when the quotient exceeds `i128::MAX`. [5](#0-4) 

The borrow index is capped only after calculating the new index, and that cap does not bound the separate product `borrowed * borrow_index`. [6](#0-5) 

The configured ceiling is `10^36`, while a token position can already have a RAY-scaled value near the `i128` input limit, so an index substantially below the ceiling can still make the unscaled debt unrepresentable. [7](#0-6) 

### Impact Explanation

This is a permanent freezing of all funds represented by the affected market. Suppliers cannot withdraw because `withdraw::accounting` calls `load_leg`, which loads a synchronized market before burning shares or paying cash. [8](#0-7) 

Borrowers cannot repay because `repay::accounting` calls the same synchronized-market path before resolving or burning debt. [9](#0-8) 

New borrows and supplies are also unavailable because both operations call `load_leg`, and liquidation withdrawals and bad-debt operations use the pool mutation paths that synchronize the market cache. [10](#0-9) 

The public `Controller::update_indexes` path reaches `LiquidityPool::update_indexes`, which calls `ops::market::accrue`, so the unprivileged caller can trigger the poisoned accrual calculation directly. [11](#0-10) 

Because the panic occurs before `mark_accrued` or `commit`, no state transition can move the market past the overflowing accrual point, leaving stored cash and positions inaccessible absent a privileged code upgrade. [12](#0-11) 

### Likelihood Explanation

The attack requires a market whose configured caps admit an exceptionally large position and enough collateral to borrow a large fraction of it. [13](#0-12) 

An unprivileged user can create that condition through ordinary `Controller::supply` and `Controller::borrow` calls; the pool mints scaled supply and debt shares from the submitted asset amounts and enforces only the market's configured utilization and reserve gates. [14](#0-13) 

After enough interest has accrued, any caller can submit `Controller::update_indexes(caller, vec![hub_asset])`; the pool then evaluates `scaled_to_original(cache.borrowed(), cache.borrow_index())` and traps before any recovery action can execute. [15](#0-14) 

The condition is intentionally exercised by the repository's whale-market regression test, which observes `MathOverflow` before the borrow-index ceiling and confirms that withdrawal and repayment then fail with the same error. [16](#0-15) 

### Recommendation

Track or bound the RAY-valued market totals, not merely the indexes. Before accepting a supply or borrow, compute the post-operation maximum future value under the relevant index ceiling and reject exposure for which `scaled * MAX_*_INDEX / RAY` cannot fit in `i128`; alternatively store market totals in a wider fixed-point representation or split accrual so oversized totals cannot produce an unrecoverable trap. [17](#0-16) 

### Proof of Concept

1. Deploy a listed market whose configured caps admit approximately `1_000_000_000` whole units of an 18-decimal asset and whose curve permits sustained high utilization. [18](#0-17) 
2. Call `Controller::supply(attacker, 0, spoke_id, [(collateral_key, collateral_amount)])` with sufficient collateral in a separate listed asset. [19](#0-18) 
3. Arrange `1_000_000_000 * 10^18` base units of the debt asset in pool supply, either through the attacker's supply or existing suppliers, then call `Controller::borrow(attacker, account_id, [(debt_key, debt_amount)], None)` for roughly 98% of that supply. [20](#0-19) 
4. Let ledger time advance until `borrowed * borrow_index / RAY` exceeds `i128::MAX`; the repository's regression demonstrates this occurs before `borrow_index` reaches `MAX_BORROW_INDEX_RAY`. [21](#0-20) 
5. Call `Controller::update_indexes(attacker, [debt_key])`; `accrue_step` panics in `scaled_to_original`, and subsequent `withdraw`, `repay`, and liquidation attempts fail before reaching their settlement logic. [22](#0-21)

```rust
/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
```

```rust
/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
```
