Based on my investigation, I found a plausible analog: the `asset_attestors` (attestor-list) update mechanism in ocore is append-only, mirroring the "cannot shrink an array by resubmitting it" bug class from the original report. I was unable to view the exact SQL used to aggregate `arrAttestedAddresses` at spend-validation time (the `loadAssetWithListOfAttestedAuthors` function body did not surface in my searches), so that part of the chain is inferred from the absence of any `DELETE FROM asset_attestors` statement anywhere in the indexed code and from the INSERT-only write path shown below. ### Title
Attestor-list updates for spender-attested assets are append-only and cannot revoke previously granted attestors - (File: writer.js, validation.js)

### Summary
An asset definer who created a `spender_attested` asset can publish `asset` (initial) or `asset_attestors` (update) messages listing trusted attestor addresses. The write path only ever `INSERT`s attestor rows into `asset_attestors`; no code path ever deletes or supersedes previously inserted rows for that asset. This is the same "cannot reduce a set that was previously grown" defect described in the external report, applied to ocore's on-chain attestor list instead of a Solidity `payoutSchedule` array.

### Finding Description
When an asset is defined with `spender_attested: true`, its initial attestor set is inserted via: [1](#0-0) 
When the definer later wants to update (including shrink/replace) that list, `asset_attestors` messages are validated by `validateAttestorListUpdate`/`checkAttestorList`, which only check that the *new* list is well-formed, sorted, non-empty, and under `MAX_ATTESTORS_PER_ASSET`: [2](#0-1) 
The corresponding write path for this update simply appends the new attestors: [3](#0-2) 
No query in `writer.js`, `storage.js`, or the schema files removes prior `asset_attestors` rows for the asset; the table's schema likewise has no versioning/expiry column, only `(unit, message_index, attestor_address)` as key: [4](#0-3) 
This is architecturally identical to the reported bug: the definer publishes an updated ("shrunk") set intending to drop a previously trusted attestor, but the underlying storage only ever grows, never truncates, so old entries persist and remain effective unless the downstream query that computes `arrAttestedAddresses` explicitly filters to only the attestors from the most recent update unit (a detail I could not confirm from the indexed code, since the body of `loadAssetWithListOfAttestedAuthors` did not surface in search results).

### Impact Explanation
If validation at spend-time treats "is address X an attestor for asset A" as "does any row in `asset_attestors` for asset A name X" (rather than only the attestors named in the *latest* update unit), then an attestor address the definer intentionally revoked (e.g., because its key was compromised or the counterparty relationship ended) remains permanently able to attest spenders of the asset. Since `spender_attested` assets gate the ability to spend/transfer the asset on being attested by a trusted attestor (see `validatePayment`'s `objAsset.spender_attested` branch requiring `arrAttestedAddresses.indexOf(...) !== -1`), a revoked-but-still-effective attestor could authorize spending by addresses the definer no longer trusts — concrete unauthorized spending of the asset.

### Likelihood Explanation
Reaching this path requires only that an asset issuer (an ordinary, unprivileged asset definer — explicitly an in-scope actor) defines a `spender_attested` asset and later posts a normal `asset_attestors` message to shrink/replace the attestor set, which is a documented, single-authored, no-special-privilege operation (`objUnit.authors.length !== 1` is the only author restriction). No hub, peer, or node compromise is needed.

### Recommendation
Verify (and if confirmed, fix) that the code computing `arrAttestedAddresses` for `spender_attested` validation reads only the attestor set from the most recent `asset` or `asset_attestors` unit for that asset (e.g., by `mci`/`unit` ordering with a `LIMIT` per update boundary), rather than unioning all historically inserted `asset_attestors` rows. If it currently unions all rows, either (a) delete/mark-superseded prior rows when a new `asset_attestors` update is committed, or (b) change the read query to select only rows belonging to the latest update unit for that asset.

### Proof of Concept
1. Definer issues asset A with `spender_attested: true` and initial `attestors: [X]`.
2. Attestor X attests spender S (`attestation` message), enabling S to receive/spend asset A.
3. Definer later loses trust in X and posts `asset_attestors {asset: A, attestors: [Y]}` intending to replace X with Y.
4. Because `writer.js` only inserts the new row for Y and never removes the row for X (`asset_attestors` table, no DELETE path), a payment validated via `validatePayment` → `objAsset.arrAttestedAddresses` (if built by unioning all `asset_attestors` rows for asset A) still contains X.
5. S, still attested only by the revoked X, can continue spending asset A even though the definer explicitly attempted to revoke X's authority.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
