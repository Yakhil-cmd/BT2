### Title
Cross-organization webhook forgery via mismatched signature-verification key vs. target-repository resolution - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound webhook using `repository_owner`, i.e. `params.dig('repository', 'owner', 'login')` (or the `organization` sub-object). Every webhook `Handler`, however, resolves the *target* `Repository`/`Stack`/`Commit` using an entirely different, unauthenticated field: `payload.dig('repository', 'full_name')` (or, for `StatusHandler`, just the commit `sha` with no repository scoping at all). Because Shipit explicitly supports multi-organization deployments where each organization has its own `webhook_secret`, an attacker who legitimately controls one organization's GitHub App/webhook secret can sign a payload whose `repository.owner.login` matches their own organization (so the signature check passes) while `repository.full_name` (or `sha`) points at a stack belonging to a completely different, unrelated organization tracked by the same Shipit instance.

### Finding Description
The signature check is:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up the GitHub App config (and thus the `webhook_secret` used for HMAC verification) keyed by this attacker-controlled `repository.owner.login` string, per the documented multi-org configuration schema: [2](#0-1) [3](#0-2) 

Once the signature is accepted, the actual event handlers never re-check that the verified organization matches the repository being acted upon. `Handler#stacks`/`#repository_name` uses only `payload.dig('repository', 'full_name')`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler` inherits this and triggers a sync for whatever stack `full_name` resolves to: [5](#0-4) 

`StatusHandler` is even less scoped — it matches by commit `sha` globally, with no repository check whatsoever: [6](#0-5) 

This is the same trust-binding break described in the analog report: the field that gates verification (`repository.owner.login`, used to pick the HMAC secret) is never checked for equality against the field the application actually acts on (`repository.full_name` / commit `sha`, used to select the repository/stack/commit to mutate).

### Impact Explanation
A commit `status` transitioning to `success`/`pending` triggers `Commit#add_status` to call `stack.schedule_merges`: [7](#0-6) 

`ProcessMergeRequestsJob` then merges any pending PR whose required status checks now appear to pass: [8](#0-7) [9](#0-8) 

Therefore, an attacker who controls the webhook secret for one organization onboarded onto a shared Shipit instance can forge a `status` (or `push`/`check_suite`) webhook, get it accepted because the signature is validated against *their own* organization's secret, but have it act on a commit/stack belonging to a *different* organization's repository — triggering an unauthorized merge or an unwanted sync/deploy trigger on a repository they have no access to. This is a cross-repository/cross-organization write and an unauthorized merge, matching the Critical/High impact categories (cross-repository writes, unauthorized merge).

### Likelihood Explanation
Requires no Shipit session, `ApiClient` token, victim `webhook_secret`, GitHub App private key, or write access to the victim repository — only that the attacker legitimately controls (owns/administers) one GitHub organization/App that is also registered with the same multi-tenant Shipit deployment, which is an explicitly documented and supported configuration (`test/dummy/config/secrets_double_github_app.yml`, multi-org example in `config/secrets.development.example.yml`). The `/webhooks` endpoint accepts POSTs from anyone (it is not restricted to GitHub's IP ranges), so the attacker can send the forged, self-signed request directly.

### Recommendation
After signature verification, re-derive the organization from the resolved target repository (`repository.full_name`'s owner segment) and reject the webhook if it does not match the `repository_owner`/App used to verify the signature. Scope `StatusHandler` (and any other handler) lookups by repository, not just by `sha`, and verify that repository belongs to the authenticating organization before mutating any `Commit`/`Stack`/`MergeRequest` state.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `OrgA` and `OrgB`, each with its own GitHub App and distinct `webhook_secret` (supported per `config/secrets.development.example.yml`'s multi-org schema). Attacker administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`. `OrgB` has a tracked stack for `OrgB/victim-repo` with a pending merge-queued PR whose head commit sha is `deadbeef...`.
2. Attacker crafts:
   ```
   POST /webhooks
   X-Github-Event: status
   X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>
   body: {"sha":"deadbeef...","state":"success","context":"ci/required","repository":{"owner":{"login":"OrgA"}}}
   ```
3. `WebhooksController#verify_signature` computes `repository_owner` = `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and the signature verifies successfully (attacker knows this secret). [10](#0-9) 
4. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')`, matching the commit that actually belongs to `OrgB/victim-repo`, and calls `create_status_from_github!`, which schedules `ProcessMergeRequestsJob`. [6](#0-5) 
5. If all other required checks are (or were already) satisfied, `MergeRequest#merge!` executes against `OrgB/victim-repo`, an unauthorized cross-organization merge triggered purely by knowledge of `OrgA`'s webhook secret. [9](#0-8)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
