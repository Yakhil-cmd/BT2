### Title
`initialize_with_permission` binds the permission check to `payer` but assigns the permissioned `pool_creator` privilege to an unrelated, unchecked `creator` account - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
In `initialize_with_permission`, the `permission` PDA that gates access to the permissioned pool-creation flow is derived from `payer`'s key, but the privileged identity that is actually recorded on-chain and granted the ongoing creator-fee rights (`pool_creator`) is a completely separate, unchecked `creator` account. This mirrors the SmartSession "enable mode" bug class: the value used to authenticate the caller (`permission`, keyed by `payer`) is never checked against the value that actually receives the privilege (`creator`), so the identity that is authorized and the identity that benefits from the authorization are decoupled.

### Finding Description
`InitializeWithPermission` derives the gating PDA as: [1](#0-0) 

This account is only ever checked for existence via its Anchor seeds constraint (`[PERMISSION_SEED, payer.key()]`); its `authority` field (set at `create_permission_pda`) is never read or compared against anything in the instruction handler.

Meanwhile, `creator` is declared as an arbitrary, unchecked, non-signer account: [2](#0-1) 

and this `creator` key is what gets persisted into `PoolState.pool_creator`, the field that gates all future privileged creator-fee actions: [3](#0-2) 

`pool_creator` is later used as the sole authorization check for collecting the pool's accumulated creator fees: [4](#0-3) 
and even for the "permissionless" variant, the recipient of funds is still whatever `pool_creator` was set to at pool creation: [5](#0-4) 

So the sequence is:
1. The protocol gates `initialize_with_permission` by requiring the existence of a `Permission` PDA seeded on `payer`, implying only vetted/whitelisted `payer` addresses should be able to create permissioned pools.
2. However, the actual privileged, long-lived identity that is granted the pool's creator-fee income stream (`pool_creator`/`creator`) is never required to equal `payer`, `permission.authority`, or any value that was actually checked by the permission gate.
3. Consequently, the on-chain permission check (`permission` PDA existence for `payer`) verifies one identity, while the privilege that is durably persisted in `PoolState` (and used forever after for `collect_creator_fee`) is granted to a completely different, attacker-chosen identity (`creator`).

This is structurally identical to the reported bug class: a value used for authorization (`permissionID`/`permission`) is decoupled from the value that determines which entity actually receives the granted privilege (`enableData`'s session/`creator`), allowing the privileged effect to be redirected to an unintended identity within a single validated call.

### Impact Explanation
Any address that has been granted a `Permission` PDA (intended by the protocol operator to vet who may create permissioned pools) can create a pool and freely designate an arbitrary, unrelated `creator` account as `pool_creator`. That designated account then permanently owns the right to collect the pool's `creator_fees_token_0`/`creator_fees_token_1` via `collect_creator_fee`/`collect_creator_fee_permissionless`, indefinitely, for as long as the pool exists — without that account ever having been vetted, without it needing to sign anything, and without it being the entity whose permission was actually validated. This breaks the intended access-control invariant that only permissioned/vetted identities control creator-fee revenue, and can be used to grant ongoing fee-collection rights to an unauthorized party.

### Likelihood Explanation
This requires only a single, ordinary permissioned-pool-creation transaction from any address holding a `Permission` PDA — no privileged signer, leaked key, or malicious validator is needed, and the mismatch is directly reachable by any account within scope. The main uncertainty is intent: it's possible the protocol design deliberately allows the `payer`/permission-holder to designate a different `creator` (e.g., creating pools on behalf of clients). Without more context on the intended semantics of "permissioned" pool creation, it cannot be conclusively proven that `creator` must always equal the permissioned `payer`, but the complete absence of any constraint linking `creator` to `permission.authority` or `payer` is a clear analog of the reported bug: the privilege-granting field is never validated against the field used for authorization.

### Recommendation
Add an explicit constraint tying the privileged `creator`/`pool_creator` value to the identity that was actually checked by the `permission` account — e.g., require `creator.key() == ctx.accounts.permission.authority` (or require `creator` to be a signer equal to `payer`), analogous to the fix of always associating the enable-mode `permissionID` with the verified `enableData`.

### Proof of Concept
1. Protocol operator calls `create_permission_pda` to grant address `P` a `Permission` PDA (seed `[PERMISSION_SEED, P]`), intending `P` to be the only party allowed to create permissioned pools/receive creator fees.
2. `P` calls `initialize_with_permission` as `payer`, satisfying the `permission` seeds constraint (`[PERMISSION_SEED, payer.key()]`), but passes an arbitrary `creator` account `X` (any pubkey, not a signer, not `P`).
3. The instruction proceeds normally: `pool_state.initialize(...)` stores `ctx.accounts.creator.key()` (`X`) as `pool_creator`. [3](#0-2) 
4. From then on, `X` (never checked against the `Permission` PDA) can call `collect_creator_fee` as the sole authorized signer, or anyone can call `collect_creator_fee_permissionless` to route the pool's accumulated creator fees to `X`'s token accounts: [4](#0-3) 
5. The permission check verified `P`, but the durable, ongoing privilege belongs to `X` — an identity the permission system never vetted.
