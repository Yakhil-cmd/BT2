### Title
Unvalidated P2P Staking Info Accepted During Fast Sync Corrupts Reward-Distribution Database — (`datasync/downloader/queue.go`)

---

### Summary

During fast-sync, `P2PStakingInfo` objects received from a remote peer are written to the local database with **zero content validation**. The validate callback in `queue.DeliverStakingInfos` is an explicit no-op (marked `TODO`), while the analogous receipt delivery validates every receipt against the header's `ReceiptHash`. A malicious peer can therefore inject arbitrary staking amounts and reward addresses into the node's persistent staking-info database. Because `GetStakingInfo` prefers the database over re-deriving from state for all pre-Kaia-hardfork blocks, the corrupted entries become the authoritative source for reward distribution whenever those blocks are re-processed (state regeneration, archive queries, or any path that calls `FinalizeState` on a pre-Kaia block).

---

---

### Impact Explanation

A malicious peer that responds to a staking-info request during fast sync can supply a `P2PStakingInfo` with:

- **Inflated `CouncilStakingAmounts`** for attacker-controlled validators → those validators receive a disproportionate share of staking rewards when pre-Kaia blocks are re-processed.
- **Replaced `CouncilRewardAddrs`** → KAIA rewards are redirected to attacker addresses.
- **Replaced `KEFAddr` / `KIFAddr`** → treasury fund distributions are redirected.

The corrupted entries persist in the miscDB under key `"stakingInfo" || Uint64LE(sourceNum)` and are returned by `GetStakingInfo` in preference to the correct on-chain state for every pre-Kaia block. Any subsequent state-regeneration run, archive-node query, or `kaia_getReward` / `governance_getRewardsAccumulated` call that triggers `FinalizeState` on a pre-Kaia block will use the attacker-supplied figures.

---

### Likelihood Explanation

- **Trigger**: any peer connected during fast sync; no privileged access required.
- **Scope**: limited to pre-Kaia-hardfork blocks (after the Kaia hardfork, `GetStakingInfo` reads from state, not DB). Nodes that have already passed the Kaia hardfork are not affected for live block processing, but archive/state-regen paths remain vulnerable.
- **Detectability**: the corruption is silent — no error is logged, no hash mismatch is reported.

---

### Recommendation

Replace the no-op `validate` callback in `DeliverStakingInfos` with a content check analogous to receipt validation. The correct staking info for a block can be re-derived from the block's state root (via `getFromState`) and compared field-by-field (or via a deterministic hash) against the peer-supplied data before it is written to the database. At minimum, the `CouncilStakingAmounts` should be verified against the actual balances of the `CouncilStakingAddrs` at the claimed `BlockNum`.

---

### Proof of Concept

1. Operator node begins fast sync; it requests staking info for pre-Kaia interval blocks by sending block hashes to a connected peer.
2. Attacker peer intercepts the `StakingInfoRequestMsg` and responds with a crafted `P2PStakingInfo` where `CouncilStakingAmounts[0]` is set to `math.MaxUint64` and `CouncilRewardAddrs[0]` is the attacker's address.
3. `handleStakingInfoMsg` → `DeliverStakingInfos` → `queue.DeliverStakingInfos` accepts the payload (validate returns `nil`).
4. `commitFastSyncData` calls `PutStakingInfoToDB(blockNum, staking.ToStakingInfo(falsifiedInfo))`.
5. Later, any call to `GetStakingInfo(preKaiaBlockNum)` returns the falsified entry from DB.
6. `FinalizeState` calls `getDeferredRewardFull` → `assignStakingRewards` using the falsified `StakingAmounts`, computing an outsized reward for the attacker's reward address, and calls `state.AddBalance(attackerAddr, inflatedAmount)`. [8](#0-7) [9](#0-8) [5](#0-4) [6](#0-5)
