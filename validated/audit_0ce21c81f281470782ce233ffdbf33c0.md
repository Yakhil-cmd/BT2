### Title
Unauthorized destruction of a shared multi-signature wallet's cosigning data by an unapproved cosigner - (File: wallet_defined_by_keys.js)

### Summary
CVE-2016-2100 describes a Foreman flaw where a user holding a narrow, per-object permission (`edit_bookmarks`/`destroy_bookmarks`) could use it to modify or delete bookmarks belonging to *other* users, because the permission check validated only "does this user have the permission" rather than "does this user own this specific object." The analogous flaw in ocore is in the handling of the `cancel_new_wallet` device message: any cosigner who has been invited to (but has not yet approved) a shared multi-signature wallet can send a single message that deletes the wallet's bookkeeping rows for **all** cosigners, including those who already approved and may be relying on the wallet to spend funds.

### Finding Description
When a shared/multisig wallet is being set up, each invited device is added to the `extended_pubkeys` table for that `wallet` id, and to `wallet_signing_paths`/`wallets`. A cosigner can decline participation by sending a `cancel_new_wallet` justsaying message, handled in [1](#0-0) 
which calls `walletDefinedByKeys.deleteWallet(body.wallet, from_address, callbacks.ifOk)` with no check that `from_address` is the only member affected.

`deleteWallet` in `wallet_defined_by_keys.js` (lines 332-358, seen in earlier context) only checks that the sender is *some* member of the wallet who has not yet approved it:
```
db.query("SELECT approval_date FROM extended_pubkeys WHERE wallet=? AND device_address=?", [wallet, rejector_device_address], function(rows){
    if (rows.length === 0) return onDone();       // not a member
    if (rows[0].approval_date) return onDone();    // already approved, can't change mind
    ... DELETE FROM extended_pubkeys WHERE wallet=?
        DELETE FROM wallet_signing_paths WHERE wallet=?
        DELETE FROM wallets WHERE wallet=?
    ...
});
```
This deletes the *entire* wallet's rows — for every cosigner, not just the rejecting one. The scope of the permission check ("is this device a not-yet-approved member of the wallet") is correctly validated, but the action it authorizes (full deletion of shared wallet state) is not scoped to the caller's own membership record — exactly the bug class in CVE-2016-2100, where an operation legitimately available to a user for their own resource was applied without restricting its effect to that resource/owner.

Because wallet approval is asynchronous (`addWallet` / `checkAndFullyApproveWallet`, lines 140-166, 168-231), it is entirely possible for some cosigners to have already fully approved (`approval_date` set) and started deriving/using addresses from `arrWalletDefinitionTemplate` while a slower or malicious cosigner has not yet approved. That slow/malicious cosigner can send `cancel_new_wallet` at any time before their own approval and wipe the `wallets`, `extended_pubkeys`, and `wallet_signing_paths` records that the already-approved cosigners depend on to reconstruct the shared address definition and to know which signing paths/xpubkeys belong to which device when composing a multi-signature transaction.

### Impact Explanation
Deleting these bookkeeping tables does not delete previously derived/shared addresses (`shared_addresses`) directly, but it removes the wallet-level cosigner/xpubkey/signing-path records that the wallet software needs to locate cosigners, verify their extended public keys, and correctly build the definition used for co-signing future spends from addresses already created under that wallet. For the honest cosigners who already approved and may have received funds to addresses derived from this wallet, this constitutes a loss of the local state required to spend/cosign — a fund-freezing condition triggered entirely by a single low-privilege participant (an invited-but-not-approved device) acting outside the scope of their own approval decision. This matches the required impact class ("AA/wallet fund loss or freezing") the same way CVE-2016-2100 allowed a user with a narrow permission over their own resource to destroy resources belonging to other users.

### Likelihood Explanation
No signature or on-chain validation is required — this is purely a device-to-device (paired correspondent) protocol message, reachable by any device that has been invited into a multisig wallet-creation flow (a very early, low-trust stage of pairing). The check that gates the deletion only verifies wallet membership and non-approval status of the sender, not whether other members have progressed past dependency on this data, making the destructive action easy to trigger by simply waiting to approve, or never approving, and sending the message.

### Recommendation
Scope `deleteWallet`'s destructive effect to the rejecting device only: remove that device's own `extended_pubkeys` row and notify other members that this cosigner declined (as is already partially done via `wallet_declined` event), rather than deleting the shared `wallets` and `wallet_signing_paths` rows outright. Only fully tear down the wallet definition when no member has yet reached `approval_date`, or leave full teardown to the initiator/UI-driven flow with confirmation from all already-approved members.

### Proof of Concept
1. Device A initiates a 2-of-3 (or n-of-m) multisig wallet, inviting devices B and C via `create_new_wallet`.
2. Device B approves quickly (`addDeviceXPubKey` sets `approval_date`), and — depending on other approvals — the wallet may become fully approved for B's purposes; B may begin relying on the wallet (e.g., sharing addresses, receiving funds to an address derived from the template).
3. Device C, still an invited but unapproved cosigner, sends `cancel_new_wallet` with `{wallet: wallet_id}` to Device A (and to any of the other cosigners it can reach).
4. On the receiving device, `wallet.js` case `'cancel_new_wallet'` invokes `walletDefinedByKeys.deleteWallet(wallet_id, C_device_address, ...)`.
5. Because C is a member with no `approval_date`, `deleteWallet` deletes `wallets`, `extended_pubkeys`, and `wallet_signing_paths` rows for the entire `wallet_id` — including B's already-approved membership record — even though B never agreed to cancel and may already depend on this wallet for funds already received at a derived address. // called from network, without user interaction
// One of the proposed cosigners declined wallet creation
function deleteWallet(wallet, rejector_device_address, onDone){
	db.query("SELECT approval_date FROM extended_pubkeys WHERE wallet=? AND device_address=?", [wallet, rejector_device_address], function(rows){
		if (rows.length === 0) // you are not a member device
			return onDone();
		if (rows[0].approval_date) // you've already approved this wallet, you can't change your mind
			return onDone();
		db.query("SELECT device_address FROM extended_pubkeys WHERE wallet=?", [wallet], function(rows){
			var arrMemberAddresses = rows.map(function(row){ return row.device_address; });
			var arrQueries = [];
			db.addQuery(arrQueries, "DELETE FROM extended_pubkeys WHERE wallet=?", [wallet]);
			db.addQuery(arrQueries, "DELETE FROM wallet_signing_paths WHERE wallet=?", [wallet]);
			db.addQuery(arrQueries, "DELETE FROM wallets WHERE wallet=?", [wallet]);
			// delete unused indirect correspondents
			db.addQuery(
				arrQueries, 
				"DELETE FROM correspondent_devices WHERE is_indirect=1 AND device_address IN(?) AND NOT EXISTS ( \n\
					SELECT * FROM extended_pubkeys WHERE extended_pubkeys.device_address=correspondent_devices.device_address \n\
				)", 
				[arrMemberAddresses]
			);
			async.series(arrQueries, function(){
				eventBus.emit('wallet_declined', wallet, rejector_device_address);
				onDone();
			});
		});
	});
}
