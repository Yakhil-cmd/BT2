### Title
Insufficient validation of asset display names in `asset_metadata` enables homograph/confusable-character spoofing of asset identities - (File: wallet.js)

### Summary
CVE-2019-13718 describes Chrome's Omnibox failing to detect IDN homograph characters in a domain name, letting an attacker present a crafted string that is visually indistinguishable from a trusted identifier. The analogous surface in `ocore` is the asset-name registration/metadata mechanism: an asset's human-readable `name` is supplied as free-form data by a registry/asset-issuer unit and is accepted and displayed to wallet users with no charset, normalization, or confusable-character checks, allowing a malicious asset issuer to register a name that is visually identical to a well-known asset's name.

### Finding Description
Asset display names are not part of the core, hashed asset definition; they are attached out-of-band via ordinary `data` app messages posted by a "registry" address, and picked up by `fetchAssetMetadata`: [1](#0-0) 

The only checks performed on the payload are that `metadata_unit` and `registry_address` look structurally valid, and that `payload.name` is merely truthy: [2](#0-1) [3](#0-2) 

There is no restriction on the character set, no Unicode normalization (e.g., NFC/NFKC), and no confusable-skeleton comparison against existing registered names before the value is written into `asset_metadata` and later surfaced to the user via `readAssetMetadata`: [4](#0-3) 

The database schema backs this up: `name` is a plain `VARCHAR(20)` with a uniqueness constraint only on the *exact byte sequence* `(name, registry_address)`, and collisions between different registries are handled purely by appending a `suffix` (the registry's own name) — there is no mechanism to detect that two different byte sequences render as the same glyphs: [5](#0-4) 

`validation_utils.js`, the central place where all wire-format field validation is centralized, contains no helper for Unicode confusable/homograph detection or normalization at all (`isValidEmail`, `isValidAddress`, etc. are the closest string validators, none address confusables): [6](#0-5) 

As a result, a different registry address (reachable by any asset issuer who can get a registry to publish a `data` message about their asset, or a self-service/alternate registry) can register an asset whose `name` uses homoglyph characters (e.g., Cyrillic "а" vs Latin "a", or zero-width joiners) that is byte-for-byte different from, but visually identical to, an established asset's name such as a stablecoin or the network's own bytes/blackbytes-style trusted assets. `readAssetMetadata`/`fetchAssetMetadata` will happily store and surface this spoofed name to the wallet UI used for sending/receiving payments and viewing balances.

### Impact Explanation
Because wallets identify assets to users primarily by this `name` field (not by the 44-byte asset unit id, which users cannot practically distinguish visually), a spoofed asset with a homograph-identical name can trick a user into treating an attacker-issued asset as the legitimate one. A user could accept payment in, or send a payment intending to pay with, what they believe is the trusted asset but is actually the attacker's worthless one — leading to real economic loss (unauthorized transfer of value away from the intended counterparty) analogous to the domain-spoofing impact of the original CVE, mapped here onto asset issuance/transfer trust rather than URL trust. This is a Medium-severity spoofing bug: it does not directly forge signatures or break consensus, but it undermines the integrity guarantee that a displayed asset name reliably identifies a specific asset, which the payment/asset-transfer flow depends on for correct routing of funds.

### Likelihood Explanation
Any address capable of authoring a `data`-app unit that a registry recognizes (or an alternate/self-service registry address) can register asset metadata; no privileged network or hub access is required — this is reachable purely by posting ordinary units, matching the "asset issuer" persona explicitly in scope. The barrier is only social/registry-policy, not a technical validation gate, since the code performs no confusable-character screening.

### Recommendation
Before accepting/storing `payload.name` (and `suffix`) in `fetchAssetMetadata`/`asset_metadata`, apply Unicode normalization (NFKC) and a confusable-skeleton check (e.g., via `unicode-confusables`/UTS #39 skeleton) against all previously registered names for the same or well-known assets, rejecting or flagging registrations that produce colliding skeletons with different underlying code points. Additionally restrict `name`/`suffix` to a conservative allow-listed character set (ASCII alnum plus limited punctuation) unless a registry is explicitly marked as supporting extended Unicode, and surface the raw asset unit id alongside the name in any UI that displays asset identity for payment decisions.

### Proof of Concept
1. Attacker controls (or gets accepted by) a registry address `R2` distinct from the trusted registry `R1` that manages the real "USDC"-style asset name.
2. Attacker issues a new asset `A2` and has `R2` post a `data` message: `{app:"data", payload:{asset:"A2", name:"USDС", decimals:2}}` where the last character is Cyrillic "С" (U+0421) instead of Latin "C" (U+0043) — visually identical in most fonts, but a different byte sequence, so it passes the `UNIQUE(name, registry_address)` constraint without colliding with the real name.
3. `fetchAssetMetadata` (wallet.js:1427-1489) accepts and stores this row purely because `payload.name` is a truthy string and `registry_address`/`metadata_unit` pass structural checks — no comparison against existing names for confusability is performed.
4. Victims viewing balances/asset pickers via `readAssetMetadata` (wallet.js:1360-1425) see "USDС" rendered identically to "USDC" and send/accept payments in asset `A2` believing it is the trusted asset, resulting in loss of value to the attacker's spoofed asset.
