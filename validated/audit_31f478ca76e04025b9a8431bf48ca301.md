### Title
Cross-tenant team-ID collision in `MembershipHandler#find_or_create_team!` allows an org whose webhook is verified against its own `webhook_secret` to grant membership in another organization's team - (`app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` purely by the numeric `github_id` supplied in the webhook payload, with no check that the verifying organization actually owns that team. In a multi-organization Shipit deployment (`config/secrets.yml` with a top-level org key per GitHub App, as documented in `docs/setup.md`), a webhook whose signature is verified against organization A's `webhook_secret` can still add/remove members on a `Team` row that belongs to organization B, including a team listed in `Shipit.github_teams` (the authorization gate used by `User#authorized?`).

### Finding Description
The binding under test: `User#authorized?` (`app/models/shipit/user.rb:80-82`) should be true only if GitHub itself added the user to a team whose `id` is in `Shipit.github_teams.map(&:id)`. Those `Team` rows are populated either by `Team.fetch_and_create_from_github`/`refresh_members!` (real GitHub API data) or by `MembershipHandler`, which is supposed to reflect a genuine GitHub `membership` event *for the organization that signed the webhook*.

`app/controllers/shipit/webhooks_controller.rb#verify_signature` resolves the signing app via `Shipit.github(organization: repository_owner)`, where `repository_owner` falls back to `params.dig('organization', 'login')` for events (like `membership`) that carry no `repository` key (`app/controllers/shipit/webhooks_controller.rb:59-62`). In single-org mode this parameter is ignored (`Shipit.github_default_organization` is `nil`, so the one global secret is used regardless of the `organization` param — `lib/shipit.rb:170-181`), but in the documented multi-org configuration (`docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`), each org key has its own `webhook_secret`, and `Shipit.github(organization: X)` looks up and verifies against `X`'s own secret via `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`). Any org administrator who legitimately owns a Shipit-registered GitHub App tenant therefore knows a valid `webhook_secret` and can produce a correctly-signed `membership` payload for their own `organization.login`.

That verified payload is then dispatched to `Handlers::MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`), which calls:

```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```

`find_or_create_by!` looks up solely on `github_id`. If a `Team` row with that `github_id` already exists (e.g. it belongs to a different, victim organization and is one of `Shipit.github_teams`), the block is *not* executed — `team.organization` is left untouched — and the existing `Team` object is returned unchanged. `process` then does `team.add_member(member)` (`app/models/shipit/team.rb:41-43`), inserting a `Membership` row linking the attacker-chosen `member` (any GitHub login, e.g. the attacker's own account, resolved via `User.find_or_create_by_login!`) to that victim team, with no re-verification that `params.organization.login` matches `team.organization`.

Consequently: signature verification proves the payload came from organization A, but the mutation is applied to a `Team` that may belong to organization B, purely because GitHub team IDs form a single global integer namespace across all organizations and the code never checks `team.organization == params.organization.login` on the found-record path. This breaks the intended binding — `User#authorized?` can become true for a user GitHub never added to the relevant team, achieved entirely through this engine's own org-scoping gap in `find_or_create_by!`, not through a forged signature.

None of the existing guards catch this: `verify_signature` only proves *an* org's secret was used, not that it's the *right* org for the referenced `team.id`; `ExplicitParameters` schema on `MembershipHandler` only enforces types/presence, not organization/team ownership; and `Membership`'s `validates :user_id, uniqueness: { scope: :team_id }` only prevents duplicate rows, not unauthorized ones.

### Impact Explanation
A tenant organization that Shipit trusts (has a configured `webhook_secret`) can, with a single crafted `membership` webhook it can legitimately sign, add an arbitrary GitHub login (including an attacker-controlled account with no real GitHub relationship to the victim org) into any `Team` row whose `github_id` it can guess or observe — including a team inside `Shipit.github_teams`, the exact set gating `User#authorized?`. This is a High-severity escalation into `Shipit.github_teams` authorization per the stated impact categories: it is repeatable against any team ID the attacker can enumerate/guess, and it crosses tenant boundaries (one organization's traffic mutating another organization's authorization state), which is explicitly in-scope ("a payload for one repository mutating another's ... team"). Once the `Membership` row exists, `User#authorized?` returns true on the very next request through `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:25-30`), granting the attacker's session full operator access (deploys, rollbacks, secrets) without ever needing valid GitHub membership.

### Likelihood Explanation
This requires: (1) Shipit configured in multi-organization mode with at least two tenant orgs (a documented, supported configuration, not a misconfiguration), and (2) the attacker controls one legitimate tenant org's `webhook_secret` while targeting another tenant's `Team.github_id`. GitHub team IDs are sequential integers in a global namespace, not treated as secrets by GitHub, and may be discoverable through the team's public `api_url`/UI artifacts or brute-forced within a plausible range — making the numeric-ID precondition realistic though not guaranteed trivial. Given those preconditions, the attack costs a single unauthenticated-but-signed HTTP POST and is fully repeatable against any number of target teams/organizations, since no per-tenant scoping check exists in the code path.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` AND `organization` (and, on an existing record with a mismatched organization, reject the event instead of silently reusing it):
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login
    raise ArgumentError, "team #{params.team.id} does not belong to organization #{params.organization.login}"
  end
  Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |t|
    t.github_team = params.team
  end
end
```
Also consider validating a uniqueness constraint on `(organization, github_id)` at the model/DB level for `Team`.

### Proof of Concept

```ruby
test "membership webhook from org B cannot grant membership on org A's required team" do
  # Precondition: victim team belongs to org "shopify" and is part of Shipit.github_teams
  victim_team = shipit_teams(:shopify_developers) # organization: "shopify"
  Shipit.stubs(:github_teams).returns([victim_team])

  attacker_login = 'attacker'
  Shipit.github.api.stubs(:user).with(attacker_login).returns(george) # returns a stub github user

  # Attacker's own org "attacker-org" is a legitimately configured tenant with its own webhook_secret,
  # simulated by stubbing verify_webhook_signature to succeed only for that org's app instance.
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    mock(verify_webhook_signature: true)
  )

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' },      # signed by attacker-org's own secret
    member: { login: attacker_login }
  }.to_json

  assert_difference -> { Membership.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  attacker_user = User.find_by!(login: attacker_login)
  # BEFORE/AFTER binding check: GitHub never added attacker to victim_team, yet:
  assert victim_team.reload.members.include?(attacker_user),
    "expected engine-level Membership row despite no real GitHub membership"
  assert attacker_user.authorized?, "authorized? should be false absent real GitHub membership, but is true"
end
```

Followed by a session-level check that `GET /stacks` (a controller including `Shipit::Authentication`) returns `200` instead of `403` for `attacker_user` once `session[:user_id]` is set to their id, demonstrating `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:25-30`) now passes.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
