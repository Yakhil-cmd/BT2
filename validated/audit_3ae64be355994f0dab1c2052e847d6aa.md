Confirmed: `ERC20Matcher` accepts any local `AccountKey20` address as an asset ID with no allowlist [1](#0-0) , meaning any deployed ERC20 contract (including a fee-on-transfer / deflationary token deployed permissionlessly via `pallet-revive`) is a valid XCM asset ID once matched by `IsLocalAccountKey20`.

### Title
ERC20Transactor trusts nominal `transfer` amount instead of measured balance delta, breaking accounting for fee-on-transfer ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` execute an ERC20 `transfer(to, amount)` call and, upon a `true`/non-reverted return, unconditionally credit the XCM holding register (or consider the deposit complete) with the exact nominal `amount` requested by the XCM message, never checking the actual token balance change of the sender/receiver. This is the same root cause as the reported AlgebraPool issue: an amount is assumed to move 1:1 with what was requested, without verifying it via a before/after balance diff, which fails for fee-on-transfer (deflationary/tax) ERC20 tokens.

### Finding Description
`withdraw_asset_with_surplus` calls the ERC20 contract's `transfer` to move `amount` from `who` to the `ERC20TransfersCheckingAccount`, and on success mints an `Erc20Credit(amount)` into the XCM holding register regardless of what the checking account actually received: [2](#0-1) 

`deposit_asset_with_surplus` symmetrically calls `transfer(beneficiary, amount)` from the checking account and treats a `true` return as fully successful deposit of `amount`, again without verifying the beneficiary's actual received balance: [3](#0-2) 

The `Erc20Credit` imbalance type used to represent this asset in the XCM holding register is a bookkeeping-only abstraction with no runtime-enforced balance backing ("the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime") [4](#0-3) . This means the holding register's notion of "how much ERC20 X exists in holding" can silently diverge from what the `ERC20TransfersCheckingAccount` actually holds on-chain.

The `ERC20Matcher` used to recognize these assets accepts **any** local `AccountKey20` location with no allowlist of vetted/audited contracts [1](#0-0) , and this transactor is wired into Asset Hub Westend's `AssetTransactors` tuple, reachable from any `pallet_xcm::execute`/XCM program a signed user submits [5](#0-4) . A user with no privileged role can deploy an arbitrary ERC20 contract via `pallet-revive` (permissionless contract deployment) that implements a transfer fee/tax (a standard, well-known fee-on-transfer pattern), then reference that contract's address as an XCM asset and execute `WithdrawAsset`/`DepositAsset` instructions against it, exactly analogous to how `swapSupportingFeeOnInputTokens` in the referenced report assumed balance deltas equal requested amounts.

Consequences of the mismatch:
- On `withdraw_asset_with_surplus`: if the contract taxes transfers, the checking account receives less than `amount`, but holding is credited with the full nominal `amount`. Subsequent `DepositAsset` of that (over-stated) holding amount will attempt to transfer more than the checking account actually possesses, causing that deposit call to fail (transfer revert/return false) inside `deposit_asset_with_surplus`, which is handled gracefully as an XCM error — so this particular direction fails safely (denial of the specific XCM instruction, not loss of others' funds), but it does erode the checking account's real balance relative to what future users expect it to be able to deposit, since it was never topped up with the "missing" fee amount by anyone.
- More importantly, this creates a persistent asymmetry: any residual balance discrepancy accumulates in the `ERC20TransfersCheckingAccount`/contract without being reconciled by the runtime, silently breaking the checking-account invariant that "holding-register-claimed ERC20 balance == on-chain checking-account balance," which other flows (e.g., reserve-backed cross-chain ERC20 transfers noted in the PR history for "first step towards cross-chain transferring ERC20s") depend on [6](#0-5) .

### Impact Explanation
This is a Medium-severity accounting/DoS-adjacent issue rather than a direct fund-theft bug: it does not let an attacker mint XCM value out of thin air against tokens with real backing (Balances/pallet-assets are unaffected), and failed ERC20 deposits fail closed (return `Err`) rather than crediting wrong beneficiaries. However, it does violate the "amount transferred equals amount requested" invariant for arbitrary user-deployed ERC20 assets referenced via XCM, exactly mirroring the acknowledged (not fixed) AlgebraPool finding: no support for exact-amount semantics on tokens whose transfer behavior deducts a fee. It can cause XCM programs to fail non-deterministically for tokens the transactor was designed to generically support, and can leave the checking account's book-keeping out of sync with its true ERC20 balance over repeated operations, a form of state corruption/latent freezing for legitimate future ERC20 XCM flows using that same contract.

### Likelihood Explanation
High likelihood of triggering, since it requires no privileged access: any user can permissionlessly deploy a fee-on-transfer ERC20 via `pallet-revive` (a completely standard and common token pattern) and then submit a signed `pallet_xcm::execute` extrinsic referencing it, exactly as demonstrated by the existing test harness (`withdraw_and_deposit_erc20s`) that already exercises this exact withdraw/deposit path against arbitrary user-compiled contracts [7](#0-6) .

### Recommendation
Verify the real balance delta (`balance_before`/`balance_after` of `who`/checking-account and of checking-account/beneficiary) instead of trusting the nominal `amount` on both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, and credit the XCM holding register (and treat the deposit as fulfilled) only for the actually-observed delta — mirroring the report's own recommended mitigation of measuring balances rather than assuming full-amount transfer semantics, or explicitly document/gate this transactor to only whitelisted, audited, non-fee-on-transfer ERC20 contracts.

### Proof of Concept
Not independently executed against a live network; no test run was performed for this specific analog, so no pass/fail evidence is available. Reachability and mechanism are demonstrated by existing repository tests that exercise the identical `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` code path with an arbitrary user-deployed contract (`withdraw_and_deposit_erc20s`, `non_existent_erc20_will_error`) [7](#0-6) [8](#0-7) ; a minimal integration reproduction would replace the standard `MyToken` fixture with a fee-on-transfer variant (e.g., `transfer` deducting X% before crediting the recipient) and assert that `Revive::balance(erc20_address, &beneficiary)` after `withdraw_and_deposit_erc20s`-style execution is less than `erc20_transfer_amount`, while the transactor's logic still reports/attempts the full nominal amount — this was not actually executed here and should be run by a background engineer with Rust/cargo test access to confirm the discrepancy and its downstream failure mode.

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});

#[test]
fn non_existent_erc20_will_error() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 10_000_000_000_000u128;
	// We try to withdraw an ERC20 token but the address doesn't exist.
	let non_existent_contract_address = [1u8; 20];

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let wnd_amount_for_fees = 1_000_000_000_000u128;
		let erc20_transfer_amount = 100u128;
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((

	});
