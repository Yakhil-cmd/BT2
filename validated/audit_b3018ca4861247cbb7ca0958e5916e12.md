### Title
Cross-tenant Team membership injection via github_id-only lookup in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves a payload came from *some* configured GitHub App installation (matched by `repository_owner`/`organization.login`), not that the org owns the `Team` record being mutated. `MembershipHandler#find_or_create_team!` looks up `Team` solely by `github_id`, ignoring `params.organization.login`, so a webhook legitimately signed by an attacker's own org can mutate a `Team` row that belongs to a different, privileged organization, and add the attacker as a member.

### Finding Description
The binding that must hold is: `signing_organization (repository_owner used in Shipit.github(organization:).verify_webhook_signature) == team.organization (Shipit::Team#organization owning the github_id in the payload)`. This binding is never checked.

Path:
1. `WebhooksController#verify_signature` resolves `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and verifies the raw body against `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . For a `membership` event with `organization.login: 'attacker-org'`, this resolves to `attacker-org`'s own `webhook_secret` — which is legitimately configured (attacker owns/installed the app there), so `verify_signature` succeeds. This only proves provenance from `attacker-org`, nothing about the `team` payload's ownership.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... }` [3](#0-2) . The block (which sets `team.organization = params.organization.login`) only runs on **creation**. If a `Team` row with that `github_id` already exists (e.g. a legitimate, privileged team belonging to `victim-org`), `find_or_create_by!` simply returns the existing record — `organization` is never re-checked or re-validated against `params.organization.login`.
3. `process` then calls `team.add_member(member)` (for `action == 'added'`), which does `members.append(member) unless members.include?(member)` [4](#0-3) , inserting a `Membership` row linking the attacker's `User` to the victim's `Team`, with no organization check at all.
4. `Team.github_id` is only unique in combination with the real GitHub team ID space — there's no scoping by `organization` in the lookup key, and the `teams` table's only unique index is on `(organization, slug)`, not `(organization, github_id)` [5](#0-4) .
5. If the mutated `Team` is one of `Shipit.github_teams` (the configured authorization teams), `User#authorized?` becomes true for the attacker: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , which is exactly the gate enforced by `force_github_authentication` in `Shipit::Authentication` [7](#0-6) .

None of the existing guards catch this: `verify_signature` verifies provenance of the org named in the payload, not ownership of the specific `team.id`/`github_id` referenced; `drop_unhandled_event` doesn't apply (`membership` is handled); the `ExplicitParameters` schema on `MembershipHandler` only validates types/presence of `team.id`, `organization.login`, `member.login`, not cross-field consistency [8](#0-7) ; no model validation ties `Team#organization` to a re-checked value on lookup.

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: membership`, body `{"action":"added","team":{"id":<victim Team.github_id>,"name":"x","slug":"x","url":"x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker"}}`, signed with `X-Hub-Signature` computed using `attacker-org`'s own legitimate `webhook_secret`.

### Impact Explanation
The attacker causes a `Membership` row to be created linking their own GitHub login to a `Team` record that belongs to a victim organization, using only their own legitimate (but unrelated) GitHub App installation/webhook secret — a payload authenticated for `attacker-org` mutates a `Team` owned by `victim-org` (cross-tenant write). If that `Team` is one of `Shipit.github_teams`, the attacker's `User#authorized?` flips to `true`, granting them authenticated access to the whole Shipit application (deploys, stacks, tasks) gated by `force_github_authentication`. This matches the Critical category ("a payload for one repository mutating another's ... team") and also the High category (escalation into `Shipit.github_teams` authorization). It is repeatable against any `github_id` the attacker can guess/know (team IDs are sequential/enumerable, and org/team info is often visible via the GitHub API for any team the attacker can see), and against any number of victim orgs configured in the same Shipit instance.

### Likelihood Explanation
Preconditions required by the question (multiple `GithubApp`/organization webhook secrets configured, i.e., the "Using Multiple GitHub Applications" mode described in `docs/setup.md`) are a real, documented supported configuration [9](#0-8) . The attacker only needs: (a) their own legitimate GitHub App installation on an org they control (`attacker-org`) registered in the same Shipit instance's `secrets.github`, and (b) knowledge of the numeric `github_id` of a `Team` already present in the `teams` table (obtainable via GitHub's public team API for many orgs, or previously observed webhook traffic, or brute-force since GitHub team IDs are sequential integers). No Shipit session, token, or secret is required beyond the attacker's own installation credentials. This is a single HTTP POST, fully repeatable, and requires no live GitHub interaction to reproduce in tests.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (not just `github_id`), and reject/ignore the event if a `Team` already exists with that `github_id` but a different `organization` than `params.organization.login`. Consider adding a unique index on `(organization, github_id)` and treating an organization mismatch as an error to be logged and dropped rather than silently applied.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "cross-org membership event does not add member to a team owned by another organization" do
  victim_team = Shipit::Team.create!(
    github_id: 999, organization: 'victim-org', slug: 'admins', name: 'Admins', api_url: 'https://x'
  )

  payload = {
    action: 'added',
    team: { id: 999, name: 'Admins', slug: 'admins', url: 'https://x' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' }
  }.deep_stringify_keys

  before_org = victim_team.reload.organization
  member_created = -> { Shipit::User.find_by(login: 'attacker') }

  assert_no_difference -> { Shipit::Membership.count } do
    Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)
  end

  victim_team.reload
  assert_equal before_org, victim_team.organization
  attacker = member_created.call
  refute victim_team.members.include?(attacker) if attacker
end
```
This asserts both sides of the binding (`victim_team.organization` unchanged/mismatched from the signing org `attacker-org`) and that no `Membership` was created for the mismatched team — currently this test would fail on the current code, since `find_or_create_team!` returns the existing `victim_team` regardless of `organization`, and `team.add_member(member)` succeeds, making `attacker.authorized?` potentially true if `victim_team` is in `Shipit.github_teams`.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:
