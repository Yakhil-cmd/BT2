### Title
Attacker-chosen `receiver` receives the flash callback instead of the authenticated initiator, enabling forced execution of third-party `execute_flash_loan`/`execute_flash_position` callbacks - (File: contracts/pool/src/ops/flash.rs, contracts/controller/src/strategies/flash_position.rs)

### Summary
Both flash entrypoints let any unprivileged caller name an arbitrary `receiver` contract, and the protocol then invokes `execute_flash_loan` / `execute_flash_position` on that `receiver` — the exact `to.onFlashLoan()` pattern flagged in the Aloe report. The callback target is decoupled from the authenticated initiator, so an attacker can aim a protocol-initiated callback at any deployed contract that exposes the receiver interface without verifying the `initiator` argument.

### Finding Description
In `flash::apply`, the caller-supplied `receiver` is only required to be a WASM contract (`require_wasm_receiver`), after which the pool transfers `amount` to it and invokes `execute_flash_loan(initiator, asset, amount, fee, pool, data)` on it via `env.invoke_contract`. The `initiator` is passed only as a data argument — nothing binds the receiver to the initiator. [1](#0-0) [2](#0-1) 

`collect_repayment` then pulls `amount + fee` from the receiver via `transfer_from`, so a receiver whose callback approves repayment (the documented happy-path behavior) loses `fee` worth of its own token balance every time an attacker points a flash loan at it. [3](#0-2) 

The same shape exists in `process_flash_position`: the controller mints debt onto the *caller's* account, forwards the borrowed tokens to the caller-chosen `receiver`, and invokes `execute_flash_position` on it. Collateral pushed by the receiver is then deposited onto the attacker's account. [4](#0-3) [5](#0-4) [6](#0-5) 

The protocol's own integration docs acknowledge the trap: "Callbacks are public... bind the callback to an expected initiator/account/operation so a valid protocol caller cannot execute an unintended plan." Any existing receiver that omits the `initiator` check is a weaponizable target. [7](#0-6) 

### Impact Explanation
- **Theft of user funds (flash_position):** a deployed receiver holding tokens whose `execute_flash_position` doesn't check `initiator` will execute its stored plan and `transfer` collateral to the controller, which is deposited as collateral on the *attacker's* leveraged account — the attacker walks away with a collateralized borrow funded by the victim's tokens.
- **Theft of user funds (flash_loan):** a receiver that auto-approves repayment has `amount + fee` pulled from it while only `amount` was forwarded; each forced invocation drains `fee` from the victim.
- This mirrors the Primitive whitehack scenario cited in the report: the callback verifies it came from the protocol but not who initiated it.

### Likelihood Explanation
Medium. Exploitation requires a deployed receiver contract that implements the callback interface without an initiator gate — but the interface is public, the mocks explicitly ship ungated example code, and the docs concede receivers must add this check themselves. Any such contract deployed before or alongside the protocol is immediately targetable by any unprivileged address via `controller.flash_loan` / `controller.flash_position` (and `pool.flash_loan`), with no collateral or privilege required.

### Recommendation
Follow the Uniswap V3 model: invoke the callback on the authenticated initiator rather than a caller-supplied `receiver`. Concretely, in `process_flash_loan` and `process_flash_position`, either (a) drop the `receiver` parameter and invoke `execute_flash_loan`/`execute_flash_position` on `caller`, or (b) require `receiver == caller` (or `receiver.require_auth()`) so the callback target always consents to being invoked. Payouts can still go to a distinct `recipient` address if needed, as Uniswap V3 separates `recipient` from the `msg.sender` callback.

### Proof of Concept
1. Victim deploys a contract implementing `execute_flash_position` that, when invoked, transfers its stored collateral tokens to the `controller` argument (e.g., a receiver that only checks `controller == cfg.controller`, omitting the `initiator` check).
2. Attacker calls `controller.flash_position(caller=attacker, account_id=0, spoke_id, mode=Multiply, debt=(hub, USDC), amount=X, receiver=victim, data, collaterals=[(hub, COLL, min)], refund_assets=[])`.
3. Controller mints `X` USDC debt on the attacker's new account, forwards tokens to the victim, and invokes `victim.execute_flash_position(initiator=attacker, ...)`. The victim's ungated callback pushes its collateral to the controller. [5](#0-4) 
4. `collect_collateral_deposits` measures the inbound collateral and deposits it on the attacker's account; LTV/health checks pass and the position stays open — the attacker now holds a debt position collateralized by the victim's funds. [8](#0-7) 
5. Variant via `flash_loan`: attacker passes `receiver=victim` where the victim's ungated `execute_flash_loan` approves `amount + fee`; `collect_repayment` pulls `amount + fee` from the victim, net-draining `fee` per call, repeatable each transaction. [9](#0-8)

fn collect_repayment(
    env: &Env,
    asset: &token::Client,
    pool: &Address,
    receiver: &Address,
    terms: &FlashTerms,
) {
    assert_with_error!(
        env,
        asset.allowance(receiver, pool) >= terms.total_repayment,
        FlashLoanError::InvalidFlashloanRepay
    );
    asset.transfer_from(pool, receiver, pool, &terms.total_repayment);

fn collect_collateral_deposits(
    env: &Env,
    controller: &Address,
    collaterals: &Vec<(HubAssetKey, i128)>,
    before: &Map<Address, i128>,
) -> Vec<(HubAssetKey, i128)> {
    let mut deposits: Vec<(HubAssetKey, i128)> = Vec::new(env);
    for (hub_asset, min_amount) in collaterals.iter() {
        let baseline = before
            .get(hub_asset.asset.clone())
            .unwrap_or_else(|| panic_with_error!(env, GenericError::InternalError));
        let delta = balance_delta_since(env, &hub_asset.asset, controller, baseline);
        assert_with_error!(
            env,
            delta >= min_amount,
            StrategyError::CollateralMinimumNotMet
        );
        if delta > 0 {
            deposits.push_back((hub_asset, delta));
        }
    }
    assert_with_error!(
        env,
        !deposits.is_empty(),
        StrategyError::CollateralMinimumNotMet
    );
    deposits
}

## Callback gate and payload

Callbacks are public. Require auth from the configured pool/controller and
