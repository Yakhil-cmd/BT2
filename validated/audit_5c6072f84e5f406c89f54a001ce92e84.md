### Title
Cross-organization webhook forgery via owner/repository binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which configured GitHub organization's `webhook_secret` to validate a webhook against using `repository.owner.login` (or `organization.login`) from the raw JSON body, but the handlers that actually act on the payload (`PushHandler`, `CheckSuiteHandler`, and any handler inheriting `Handler#stacks`) resolve the target `Repository`/`Stack` using a *different* field of the same attacker-controlled body: `repository.full_name`. An attacker who legitimately administers one GitHub organization configured in a multi-tenant Shipit deployment can forge a signature that is valid for their own org while pointing the "acted upon" repository field at a completely different organization's stack.

### Finding Description
`verify_signature` computes the signing organization purely from body content, independent of the field the handler will use to select what gets mutated: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The signature check picks the HMAC secret for whichever organization is named in `repository.owner.login`. Once `verified` is true, the request body is dispatched unchanged to the registered handler: [3](#0-2) 

`PushHandler` and `CheckSuiteHandler` both inherit `Handler#stacks`, which resolves the affected `Repository`/`Stack` from a *different* field — `repository.full_name` — not `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

On genuine GitHub deliveries these two fields are always consistent (GitHub itself populates both from the same repository object), so the mismatch is unreachable through real webhook traffic. But this endpoint accepts raw, attacker-crafted JSON directly — it is not fetched from GitHub, it is POSTed by whoever knows a valid `webhook_secret`. In Shipit's documented multi-organization configuration, each configured GitHub organization has its own independent `webhook_secret`: [7](#0-6) 

An attacker who is the legitimate GitHub admin of one such configured organization ("OrgA") knows/controls OrgA's webhook secret (they configured it when wiring up their org's GitHub App/webhook). They can compute a valid `X-Hub-Signature` over an arbitrary payload where `repository.owner.login = "OrgA"` (so `verify_signature` selects and matches OrgA's secret) while `repository.full_name = "OrgB/victim-repo"` (a stack belonging to a different tenant, "OrgB", that the attacker has no relationship to). `verify_signature` passes because it only checks OrgA's secret against the body; the handler then acts on OrgB's stack because it reads `full_name` instead of `owner.login`.

This is exactly the class of binding break called out in scope: **the organization that authenticated (`repository.owner.login`) versus the repository that is written (`repository.full_name`)** are not the same field, and nothing enforces that they refer to the same repository.

### Impact Explanation
Using this mismatch with the `push` event, the attacker can force `stack.sync_github(expected_head_sha: params.after)` to run against any stack belonging to an organization/repository they do not control: [5](#0-4) 

This writes new commit/sync data into another tenant's `Stack` records purely on the strength of a signature computed with the attacker's own (unrelated) organization's secret — a cross-repository/cross-tenant write triggered without any authorization from the victim organization. The same primitive (`Handler#stacks` → `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) is reused by `CheckSuiteHandler`, extending the reach to forcing check-run refresh scheduling on arbitrary victim commits.

### Likelihood Explanation
Exploitation only requires: (1) Shipit configured for more than one GitHub organization (an explicitly supported and documented configuration), and (2) the attacker being a legitimate, unprivileged (from Shipit's perspective) administrator of any one of those organizations — a bar far lower than compromising the victim organization, obtaining a Shipit `ApiClient` token, or a GitHub App private key. No Shipit account, session, or API credential is needed at all; the request is sent directly to the public `WebhooksController#create` endpoint.

### Recommendation
Bind webhook signature verification and payload processing to the same identity field. Concretely, `WebhooksController` should derive the organization used for secret selection from the same value the handler will use to select the target repository (`repository.full_name`, parsed for the owner segment), and/or handlers should independently re-verify that the resolved `Repository`'s owning organization matches the organization whose secret validated the signature before performing any mutation.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `config/secrets.development.example.yml`'s documented multi-org format).
2. Attacker administers `OrgA` on GitHub and therefore knows `OrgA`'s `webhook_secret` (it was configured for their own GitHub App/webhook).
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` (or the mounted path) with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature.
6. `PushHandler#process` runs, resolving `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, and enqueues `GithubSyncJob`/`stack.sync_github` for a stack the attacker has no relationship to, despite the signature only proving control of `OrgA`.
