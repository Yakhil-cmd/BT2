### Title
Webhook Signature Verification Binds Only the Signing Organization, Not the Repository/Commit the Payload Mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` proves only that a request was signed by *some* configured organization's `webhook_secret`. It never checks that the `repository`/commit fields the handler subsequently mutates actually belong to that same organization/repository. `StatusHandler` in particular updates `Commit` rows by `sha` alone, with no repository scoping at all, so a validly-signed webhook from one (attacker-controlled) organization/repository can write CI status onto `Commit` records that belong to a different, unrelated stack whenever the two share a commit SHA (e.g. a fork sharing history with the upstream repo).

### Finding Description
`verify_signature` derives the signing organization strictly from the payload itself: [1](#0-0) [2](#0-1) 

This only establishes "this request was signed with organization X's `webhook_secret`". It does not establish that any other field in the same JSON body (e.g. `repository.full_name`, or a commit `sha`) actually belongs to organization X's repositories. The base `Handler` class does look up the target repository from `repository.full_name` for most events: [3](#0-2) 

but `StatusHandler` — the handler that writes commit CI status used for merge/deploy readiness — bypasses that scoping entirely and matches purely by SHA across the whole database: [4](#0-3) 

Because Git commit SHAs are content-addressed, any two repositories that share history (a fork and its upstream, or two stacks tracking the same repository) will have identical SHAs for their shared commits. An attacker who owns/administers a repository that is a fork of (or shares history with) a victim's Shipit-tracked repository can:
1. Configure that fork's webhook with their own `webhook_secret` value (which they legitimately know, since they own that repository/webhook — this is analogous to the never-set `firstApprovalBlock[to]` in the reported bug: the "authorization" the code checks — `firstApprovalBlock[to] > 0` / here, "signed by org X's secret" — is not actually bound to the entity the action is performed on).
2. Send a `status` event whose `sha` matches a shared ancestor commit that also exists in the victim's tracked repository/stack.
3. `verify_signature` succeeds (it only validates against the attacker's own organization's secret), and `StatusHandler#process` then creates/updates a `Status` on the victim's `Commit` row purely by SHA match, with no verification that the commit belongs to the signing organization's repository.

This breaks exactly the binding called out in the report’s bug class: the entity the code verifies (`repository_owner` → signing organization) is not the entity the code subsequently writes (`Commit` rows selected by bare `sha`, independent of repository/organization).

### Impact Explanation
Forged CI statuses on a victim's `Commit` can influence downstream merge/deploy-readiness logic that consumes `Status`/`create_status_from_github!` records (e.g. required-status gating used before merging or shipping). An attacker with no privileges on the victim's repository, but ordinary GitHub push/webhook-configuration rights on a forked/history-sharing repository, can inject arbitrary CI state into the victim's commit records — a cross-repository write achieved purely through the webhook trust boundary, matching the "cross-repository writes" / unauthorized-deploy-adjacent impact class.

### Likelihood Explanation
Requires the attacker to control a repository (e.g. a fork) sharing commit history with a Shipit-tracked repository, and to be able to configure/trigger a signed webhook against their own repository/org — both realistic for any public open-source project mirrored/forked on GitHub. No secret of the victim organization is needed.

### Recommendation
`StatusHandler` (and any other handler) must scope its lookups to the repository verified during signature validation, not just to a bare `sha`. Concretely, join through `stacks`/`Repository.from_github_repo_name(repository_name)` (as `Handler#stacks` already does for other events) before updating `Commit` records, and reject/ignore statuses for commits that don't belong to a stack under the verified repository/organization — mirroring the suggested fix in the analog report of asserting the checked property (`firstApprovalBlock[to] != 0`) is actually the one gating the action.

### Proof of Concept
1. Attacker forks victim's tracked repository (or otherwise shares a commit history with it) into `attacker/fork`, which Shipit is also configured to track (or simply has a webhook pointed at Shipit's `/github/webhooks` endpoint using the attacker's own organization's app/webhook secret).
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<sha shared with victim repo's HEAD commit>",
  "state": "success",
  "context": "ci/tests",
  "repository": {"full_name": "attacker/fork", "owner": {"login": "attacker"}}
}
```
3. Attacker signs it with `attacker`'s org `webhook_secret` and POSTs it to Shipit's webhook endpoint with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` succeeds (signature valid for `attacker`'s org) — [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every matching `Commit`, including the victim's, because the query never filters by repository/organization — [4](#0-3) .
