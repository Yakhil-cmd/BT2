## Title
`store()` for arbiter contracts trusts an untrusted cosigner-supplied `status`, letting a paired cosigner forge the initial contract state - ([File: arbiter_contract.js])

## Summary
The `initialize can be frontrun` bug class is about a state-initializing entry point that lacks proper authorization, so the *first* caller (rather than the intended owner) sets critical state. In `ocore`, the closest reachable analog is `arbiter_contract.store()`, invoked from the `arbiter_contract_shared` device-message handler. When the message is treated as coming from a cosigner (`bFromCosigner = true`), the function trusts the sender-supplied `status` value verbatim for the very first (and any subsequent, via `INSERT OR IGNORE`) local record of the contract, instead of forcing it to the safe default (`pending`) the way the `arbiter_contract_offer` path does.

## Finding Description
`arbiter_contract.store()`: [1](#0-0) 
computes `status = bFromCosigner ? (objContract.status || status_PENDING) : status_PENDING;` — i.e. only the non-cosigner path is forced to `pending`; when `bFromCosigner` is `true`, the attacker-controlled `objContract.status` field is stored as-is.

This function is called from the network message handler for `arbiter_contract_shared`: [2](#0-1) 
The handler validates only that `from_address` is a device associated with one of my wallet's `wallet_signing_paths` for `body.my_address` (i.e., that the sender is *some* cosigner of the multisig address involved in the contract) and that the `getHash()` matches. It does **not** validate that the `status` value is legitimate, sequenced, or consistent with any state-machine transition rules (those rules exist for `arbiter_contract_update` at lines 691-712, but are bypassed entirely on first ingestion via `arbiter_contract_shared`).

Because `store()` uses `INSERT OR IGNORE` semantics on this first receipt, whichever device message is processed first "wins" and establishes the local `wallet_arbiter_contracts.status` — directly analogous to the reported `initialize()` front-running pattern: an authorization-light state-setting function is reachable by an untrusted (or semi-trusted, in this case a cosigner) party, and whoever reaches it first fixes consequential state (here, the *initial* value of `status`) without going through the intended acceptance/response/dispute state machine.

## Impact Explanation
The `status` column drives contract-state logic used elsewhere in `arbiter_contract.js`/`wallet.js`, including transitions such as `paid` → `in_dispute`, `dispute_resolved` → `in_appeal`, and `in_appeal` → `appeal_approved`/`appeal_declined` (validated in `arbiter_contract_update` at lines 691-712). By forging an initial `status` (e.g., seeding a contract directly as `"paid"`, `"dispute_resolved"`, or `"completed"`) through the `arbiter_contract_shared` path — which is not subject to those transition checks — a malicious cosigner device could desynchronize a victim's local contract state from the true state, potentially causing incorrect UI/wallet decisions about whether/when to release funds tied to the arbiter multisig shared address, or to bypass the intended dispute/appeal workflow. This is a state-integrity/logic-bypass issue reachable purely from a paired-device message, matching the "reachable via paired device" category permitted by the validation rules.

## Likelihood Explanation
Requires the attacker to be a cosigner device already listed in `wallet_signing_paths` for the shared address referenced by the contract (a "paired device" role explicitly allowed as an attack surface in scope) — no additional privilege beyond normal peer/cosigner status is needed, and the race is trivially winnable since it only requires sending the `arbiter_contract_shared` message before/instead of any legitimate acceptance flow completes.

## Recommendation
In `store()`, always ignore attacker-supplied `status` on first creation and force it to `status_PENDING` regardless of `bFromCosigner`, allowing status changes only via the already-validated `arbiter_contract_update` transition-checking code path (lines 691-712 in `wallet.js`). If cosigners legitimately need to relay an already-agreed status, that status should be re-derived/re-validated against the same state-machine rules used for `arbiter_contract_update`, not accepted as an opaque field on first `store`.

## Proof of Concept
1. Attacker device `D` is added as a cosigner (`wallet_signing_paths`) for shared/multisig address `A` used in an arbiter contract between victim `V` and peer `P`.
2. Before `V` receives the legitimate `arbiter_contract_shared` message reflecting the true (`pending`/`accepted`) state, `D` crafts and sends its own `arbiter_contract_shared` message with the same `hash` (matching `getHash()`) but `status: "paid"` (or any other value from the allowed CHECK-constraint list). [3](#0-2) 
3. `V`'s node validates only cosigner membership and hash consistency, then calls `arbiter_contract.store(body, true)`. [4](#0-3) 
4. Because `bFromCosigner` is `true`, `status = objContract.status` (`"paid"`) is persisted directly into `wallet_arbiter_contracts`, bypassing all of the transition checks that normally gate `status` changes in `arbiter_contract_update`.

function store(objContract, bFromCosigner, cb) { // contracts shared by cosigners are trusted to reflect their true status
	const me_is_cosigner = bFromCosigner ? 1 : 0;
	const status = bFromCosigner ? (objContract.status || status_PENDING) : status_PENDING;
	var fields = "(hash, peer_address, peer_device_address, my_address, arbiter_address, me_is_payer, my_party_name, peer_party_name, amount, asset, is_incoming, creation_date, ttl, status, title, text, peer_pairing_code, peer_contact_info, my_pairing_code, my_contact_info, me_is_cosigner";
	var placeholders = "(?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?";
	var values = [objContract.hash, objContract.peer_address, objContract.peer_device_address, objContract.my_address, objContract.arbiter_address, objContract.me_is_payer ? 1 : 0, objContract.my_party_name, objContract.peer_party_name, objContract.amount, objContract.asset, 1, objContract.creation_date, objContract.ttl, status, objContract.title, objContract.text, objContract.peer_pairing_code, objContract.peer_contact_info, objContract.my_pairing_code, objContract.my_contact_info, me_is_cosigner];
	if (bFromCosigner) {
		if (objContract.shared_address) {
			fields += ", shared_address";
			placeholders += ", ?";
			values.push(objContract.shared_address);
		}
		if (objContract.unit) {
			fields += ", unit";
			placeholders += ", ?";
			values.push(objContract.unit);
		}
	}
	fields += ")";
	placeholders += ")";
	db.query("INSERT "+db.getIgnore()+" INTO wallet_arbiter_contracts "+fields+" VALUES "+placeholders, values, function(res) {
		if (cb) {
			cb(res);
		}
	});
}
