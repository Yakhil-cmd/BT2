### Title
Server-Side Request Forgery via unvalidated ArbStore URL in Arbiter Contract flow - (File: `arbiter_contract.js`, `arbiters.js`)

### Summary
The arbiter-contract feature lets any paired peer initiate a contract naming an arbitrary `arbiter_address`. When the local wallet later interacts with that arbiter (fetching arbiter info, opening a dispute, filing an appeal, or querying the appeal fee), it resolves the arbiter's ArbStore URL through the hub and then issues a raw HTTP(S) request to that URL with no validation of scheme, host, or destination (no protection against internal/private/link-local addresses). Because the `arbiter_address` used to look up the URL originates from data supplied by an untrusted peer (a private-payment counterparty in the contract), and any address owner can register itself as an "arbiter"/ArbStore for a hub, a malicious counterparty/arbiter can cause the victim's node to send authenticated, data-bearing HTTP requests to attacker-chosen internal or third-party endpoints — a classic SSRF.

### Finding Description
`wallet.js` handles the `arbiter_contract_offer` message from a paired peer and only checks that `arbiter_address` is a syntactically valid address, with no whitelist or provenance check: [1](#0-0) 

That address is persisted in `wallet_arbiter_contracts` and is later used by the wallet owner's own client to resolve where to send contract data. The resolution and request happen in two closely related modules:

1. `arbiters.js` resolves the ArbStore URL for an `arbiter_address` via the hub, then does a raw `https.get(url, ...)` with the response body parsed as JSON and trusted as arbiter/ArbStore info: [2](#0-1) 

2. `arbiter_contract.js` performs the same hub lookup pattern in `getArbstoreAddresses`, `openDispute`, `appeal`, and `getAppealFee`, and then POSTs the wallet's contract data (including an encrypted contract package with pairing codes and party names) to whatever host/path the resolved URL points to, via a hand-rolled `http.request` wrapper with no host/scheme allow-listing: [3](#0-2) [4](#0-3) [5](#0-4) 

The URL itself comes from `device.requestFromHub("hub/get_arbstore_url", arbiter_address, ...)`, i.e. whatever a hub returns for that `arbiter_address` is trusted verbatim and immediately dereferenced with `url.parse(host)` and passed to Node's `http.request`/`https.get` — there is no restriction preventing the URL from pointing at `127.0.0.1`, RFC1918 ranges, cloud metadata endpoints, or arbitrary third-party hosts.

The root problem is that the trust chain is: untrusted peer chooses `arbiter_address` in a message the wallet owner did not vet → hub-registered URL for that address is fetched unconditionally → victim's own node originates outbound HTTP(S) requests (carrying contract/dispute/appeal payloads including pairing codes and encrypted contract data) to that URL with no SSRF hardening.

### Impact Explanation
An attacker who controls (or colludes with) the arbiter identity referenced in a contract offer — or who tricks a user into accepting a contract naming a malicious/attacker-registered arbiter — can force the victim wallet to make outbound HTTP requests to arbitrary internal or external endpoints whenever the wallet interacts with that arbiter (fetching arbiter info, filing a dispute, appealing, or checking the appeal fee). This enables internal network/service enumeration reachable from the victim's node, potential interaction with internal-only APIs, and exfiltration of contract metadata (pairing codes, party names, encrypted contract blob, amounts, asset ids) to attacker-controlled hosts. This matches the CVE class (SSRF allowing an authenticated actor to send unauthorized requests from the system, aiding network enumeration or facilitating further attacks). It does not directly cause fund loss, double-spend, or consensus divergence, keeping it at Medium severity per the SSRF class definition.

### Likelihood Explanation
Reaching this code only requires a paired device to send an `arbiter_contract_offer` (or a party to be listed as an "arbiter" whose ArbStore is queried) — a normal, low-privilege wallet-to-wallet interaction that requires no special trust beyond pairing. The victim wallet automatically performs the follow-up hub lookups and HTTP requests as part of ordinary dispute/appeal/arbiter-info flows, with no host validation anywhere in the outbound request path, making exploitation straightforward once a victim engages with a malicious/arbiter-controlled contract.

### Recommendation
- Validate the URL returned by `hub/get_arbstore_url`/`hub/get_arbstore_url_by_address` before using it: enforce `https://` scheme, resolve and reject private/loopback/link-local/metadata IP ranges, and restrict to an operator-approved allowlist of ArbStore hosts.
- Apply the same validation in `arbiters.js` `requestInfoFromArbStore` and in `arbiter_contract.js` `httpRequest`.
- Consider requiring explicit user confirmation showing the resolved ArbStore host before any outbound request is made, and rate/size-limit responses.

### Proof of Concept
1. Attacker pairs with victim's device and sends `arbiter_contract_offer` naming `arbiter_address = X`, where the attacker (or a colluding hub registrant) has registered `X`'s ArbStore URL as `http://169.254.169.254/` (or an internal service URL) via the hub's arbstore registration mechanism.
2. Victim wallet stores the contract (validation only checks `isValidAddress` on `arbiter_address`) — see `wallet.js:617-627`.
3. Victim later calls `arbiters.getInfo(X, ...)` (e.g., to display arbiter details) or the wallet UI triggers `openDispute`/`appeal`/`getAppealFee` on the contract.
4. The wallet resolves the URL via `hub/get_arbstore_url` and issues `https.get(url + '/api/arbiter/' + address, ...)` (`arbiters.js:16-33`) or POSTs contract data via `httpRequest(url, "/api/dispute/new", dataJSON, ...)` (`arbiter_contract.js:296-313`) to the attacker-chosen host, with no SSRF protections in place.

function requestInfoFromArbStore(url, cb){
	http.get(url, function(resp){
		var data = '';
		resp.on('data', function(chunk){
			data += chunk;
		});
		resp.on('end', function(){
			try {
				cb(null, JSON.parse(data));
			} catch(ex) {
				cb(ex);
			}
		});
	}).on("error", cb);
}

function getAppealFee(hash, cb) {
	getByHash(hash, function(objContract){
		var command = "hub/get_arbstore_url";
		var address = objContract.arbiter_address;
		if (objContract.arbstore_address) {
			command = "hub/get_arbstore_url_by_address";
			address = objContract.arbstore_address;
		}
		device.requestFromHub(command, address, function(err, url){
			if (err)
				return cb("can't get arbstore url:", err);
			httpRequest(url, "/api/get_appeal_fee", "", function(err, resp) {
				if (err)
					return cb(err);
				cb(null, resp);
			});
		});
	});
}

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
