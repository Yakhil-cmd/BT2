## Analysis

The reported bug class is a **first‑depositor / donation‑based share‑price manipulation** vulnerability: a vault computes shares‑per‑deposit from the *current spot balance* of its reserve, so anyone can pre‑empt the intended depositor by manipulating that balance (via a small deposit plus a direct "donation" transfer) before the victim's transaction executes, skewing the price used for share issuance/redemption.

The ocore repository ships an in‑repo AA (Autonomous Agent) template that implements exactly this deposit/share‑issuance pattern, reachable by any unprivileged trigger sender or plain payment sender.

### Title
Reserve/Share-Price Manipulation via Unaccounted Direct-Balance Donation in the AA liquidity-pool template - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The bundled "Uniswap-like market maker" AA computes deposit shares, swap outputs, and divestment payouts directly from the AA's raw live balances (`balance[$asset]`, `balance[base]`) rather than from an internally tracked reserve variable. Because any unprivileged sender can transfer the pool's assets straight to the AA address outside of the defined `if` cases, they can alter these balances before a victim's deposit/swap/divest trigger is processed — the same "front‑run + balance donation" primitive described in the Gro/GSquared report against `GVault.deposit`.

All of these branches read `balance[$asset]` and `balance[base]` — the AA's *actual on-chain balance* at execution time — rather than a state variable that is exclusively updated through the defined deposit/withdraw logic. Since the `messages.cases` list only defines specific `if` conditions (invest, divest, swap-to-asset, swap-to-bytes), any unit that sends the pool's asset to the AA address but does not match one of those conditions (e.g., sending only `$asset` with no bytes while `var['mm_asset_outstanding']` is still unset) falls through with no matching case, and the AA silently absorbs the funds without minting `mm_asset` shares or updating `mm_asset_outstanding`. This lets an unprivileged sender inflate `$asset_balance` (or `$bytes_balance`) independent of the share-accounting logic.

Because the "initial deposit" condition is `$asset_balance == 0 OR $bytes_balance == 0` and issues `$issue_amount = balance[base]` — the *entire* current byte balance, not just the newly-deposited amount — an attacker who is first to trigger the AA (deterministically ordered by DAG unit stabilization, not wall-clock submission order, so any node broadcasting an earlier-processed unit can win this race) receives shares proportional to whatever balance happens to be present, and subsequent legitimate depositors/swappers have their share/price computations calculated against a balance that includes the attacker's unaccounted donation.

### Impact Explanation
Any unprivileged AA trigger sender (or plain payment sender) can:
1. Directly transfer the pool asset to the AA address to inflate `balance[$asset]` or `balance[base]` without going through the defined invest logic (bypassing all `if` cases).
2. Skew `$current_ratio`, `$p = $asset_balance * $bytes_balance`, and the initial-deposit branch's `$issue_amount` for the next legitimate participant.
3. Cause a legitimate depositor's shares to be miscalculated (via `round()` truncation against a manipulated ratio) or cause donated value to become permanently unattributed dead value inside the AA (no `mm_asset` corresponds to it), effectively locking/losing funds contributed by the pool's real users — the same class of fund loss described in the Gro report (shares redeemable for only a fraction of the true deposit).

### Likelihood Explanation
This requires no special privilege — only the ability to post a payment/trigger unit to the AA address, which is exactly the "unprivileged AA trigger sender" actor explicitly in scope. The manipulation window exists because AA execution reads live `balance[]` at trigger time rather than an isolated, exclusively-AA-updated reserve variable, and because the sample defines no catch-all/guard case rejecting unaccounted incoming transfers of the pool asset.

### Recommendation
- Track reserves in dedicated state variables (`var['reserve_asset']`, `var['reserve_bytes']`) updated only by the defined deposit/withdraw/swap logic, instead of reading `balance[$asset]`/`balance[base]` directly, so unsolicited direct transfers cannot influence share/price math.
- Add a default/catch-all case that bounces (rejects) any transfer of the pool's tracked asset that doesn't match one of the defined cases, preventing "silent donation" of funds outside the accounting model.
- Base the "initial deposit" condition on `!var['mm_asset_outstanding']` (i.e., zero shares outstanding) rather than `$asset_balance == 0 OR $bytes_balance == 0`, and require a minimum first-deposit size to reduce the value that can be captured/lost through balance manipulation at pool genesis.

### Proof of Concept
1. Deploy the AA from `test/samples/uniswap_like_market_maker.oscript`; call it once with `{data:{define:true}}` to create `$mm_asset`.
2. Before any legitimate `invest` deposit, Attacker sends a unit paying only `$asset` (no `base` beyond dust) to the AA. Since `var['mm_asset_outstanding']` is unset, this matches neither the "invest" case (`trigger.output[[asset=base]] > 1e5` fails) nor "exchange asset to bytes" (`var['mm_asset_outstanding']` falsy) — it falls through with no response, silently increasing `balance[$asset]` with no shares minted and no tracked reserve update.
3. Victim then submits the intended first "invest" deposit with `base` bytes. Because `$bytes_balance == 0` still holds (bytes were never deposited), the initial-deposit branch fires and mints `$issue_amount = balance[base]` (only the victim's bytes), while the attacker's earlier `$asset` donation is now permanently stranded in the pool, unaccounted for by any `mm_asset` shares, and inflates `$p = $asset_balance * $bytes_balance` used in every subsequent swap calculation — skewing exchange rates in later `exchange bytes to asset`/`exchange asset to bytes` trades to the detriment of legitimate counterparties.
