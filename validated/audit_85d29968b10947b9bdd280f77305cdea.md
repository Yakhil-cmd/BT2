### Title
Asset Definer Can Front-Run Pending Payments/AA Triggers by Racing an `asset_attestors` Update to Manipulate the Spender-Attestation Check - (File: `storage.js`, `validation.js`)

### Summary
The external report describes a privileged role (`restricted`) that can front-run a pending user transaction by changing a fee parameter (`performanceFee`) right before the user's transaction executes, since there is no restriction or grace period on the change. In ocore, an analogous privileged, unrestricted, and instantly-effective parameter exists for `spender_attested` assets: the **asset definer** can post an `asset_attestors` message at any time to change who counts as an "attested" spender, and — critically — when this list is resolved for AA processing, the protocol picks the *newest DAG-level* update rather than a stable, delay-protected one, letting the definer race and flip the outcome of an already-broadcast, in-flight payment/trigger.

### Finding Description
The asset definer of a `spender_attested` asset can freely update the attestor list via `composeAssetAttestorsJoint()` [1](#0-0)  and this is accepted with only a definer-address check, no timing/frequency restriction, no cooldown, and no grace period, mirroring the unrestricted `updatePerformanceFee` in the original report: [2](#0-1) .

The resolution of "which attestor list applies right now" is done in `readAsset`/`addAttestorsIfNecessary`. For non-AA callers it is constrained to stable data up to `last_ball_mci`, but for **AA execution** (`byAA=true`), the `before_last_ball_cond` filter is dropped entirely and the query instead just orders candidate `asset_attestors` units by `level DESC` and takes the top one — i.e., it accepts the newest, potentially-unconfirmed update: [3](#0-2) .

This resolved attestor list is what gates payment validity: only addresses in `arrAttestedAddresses` may issue/spend the asset when `spender_attested` is set [4](#0-3) . Because the definer can post a competing `asset_attestors` unit and have it win purely by achieving a higher `level` in the DAG (not by being first in time or already stable), the definer can watch a victim's in-flight payment or AA trigger that depends on the current attestor list, and then race it with an update that removes the victim (or adds/keeps only the definer), before the victim's unit's evaluation completes — exactly the "observe pending transaction, front-run a privileged parameter change, profit" pattern described in the original report.

### Impact Explanation
A definer who also runs (or colludes with) an AA that uses `spender_attested` assets as a gatekeeping/fee-extraction mechanism can:
- Deny a specific victim's already-submitted payment by removing them from the attestor list just before the AA evaluates the trigger, causing fund loss/bounce for the victim while the definer keeps the received bytes as bounce fee, or
- Insert themselves/a colluding address into the attestor list to redirect value that should have gone through a competing attested spender first.

This is a concrete unauthorized-advantage/fund-loss scenario reachable by an asset issuer against an ordinary AA trigger sender, matching the "AA fund loss" and "node disagreement on validity" impact classes.

### Likelihood Explanation
Medium. It requires the target asset to opt into `spender_attested` (a supported, documented feature — see `test/samples/*` and `divisible_asset.js`/`indivisible_asset.js` usages) and an AA (or protocol logic) that gates behavior on the attestation. No special network position is required beyond normal unit posting; the definer already has legitimate authority to update the list — the bug is that this authority has no delay or lock, so it can be exercised adversarially and reactively against in-flight transactions, identically to the reported `updatePerformanceFee` front-run.

### Recommendation
Apply the same remedy suggested in the original report: introduce a grace period before an `asset_attestors` update takes effect for AA-visible resolution (e.g., require `min_mci`/stability before a new list can be used by `addAttestorsIfNecessary(byAA=true)`), or drop the "latest by level, including unstable" resolution for AA contexts and instead use the last stable list only, consistent with the non-AA path. Alternatively, disallow attestor-list changes to affect an AA trigger/payment that references an earlier attestor snapshot already fixed at composition time.

### Proof of Concept
1. Definer issues asset `X` with `spender_attested: true` and an initial attestor list containing victim's address `V` via `composeAssetDefinitionJoint` (see fields validated in `validateAssetDefinition`) [5](#0-4) .
2. An AA gates a valuable payout on `trigger` payments of asset `X` being sent by an attested address (mirrors patterns like `test/samples/futures_contract.oscript`/`option_contract.oscript`, which use asset conditions and oracle-style gating).
3. Victim `V` broadcasts a trigger/payment spending asset `X`, currently valid because `V` is attested.
4. Before this unit is processed by the AA (or before it stabilizes), the definer calls `composeAssetAttestorsJoint(definer, X, [definer_or_other])` to exclude `V`, choosing parents that yield a higher DAG `level` than victim's unit.
5. When the AA composer resolves attestors via `readAsset(..., bAcceptUnconfirmedAA=true, ...)` → `addAttestorsIfNecessary(true)`, it selects the definer's newer, higher-level (possibly still-unstable) update [3](#0-2) , so `arrAttestedAddresses` no longer contains `V`.
6. `validatePayment` then rejects/treats differently `V`'s payment as "issuer is not attested" or the AA logic bounces/denies the trigger [4](#0-3) , letting the definer capture the economic benefit that should have gone to `V`, entirely analogous to the definer front-running `updatePerformanceFee` in the original report.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
