### Title
Caller-controlled flash receiver can execute hidden token transfers under the caller’s authorization - (contracts/pool/src/ops/flash.rs)

### Summary
`flash_loan` accepts an attacker-controlled Wasm `receiver` and opaque `data`, forwards them to the pool, and invokes `execute_flash_loan` on that contract while the caller’s authorization remains available to the transaction’s recorded authorization tree. A malicious receiver can therefore include an unrelated `token.transfer(caller, attacker, amount)` child invocation alongside the otherwise valid flash-loan authorization, stealing caller funds when that poisoned authorization tree is signed. The loan’s balance checks protect only pool funds; they do not constrain what the receiver asks the caller to authorize. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The controller entrypoint accepts `caller`, `asset`, `amount`, `receiver`, and `data`, requires only caller authorization and that `receiver` is a Wasm contract, then passes both attacker-controlled values to the configured pool. [4](#0-3) [5](#0-4) 

The pool transfers principal to the supplied receiver and invokes its `execute_flash_loan` function with `initiator` and opaque `data`. There is no receiver allowlist, callback-code restriction, or constraint on authorization children requested below the callback. [2](#0-1) [6](#0-5) 

After the callback, the pool only checks its own token balance and pulls `amount + fee` from the receiver. Those checks do not cover token transfers that the receiver induced from `initiator` to an unrelated attacker address. [7](#0-6) [8](#0-7) 

### Impact Explanation
A malicious receiver can steal arbitrary spendable token balances from the flash-loan caller by requesting a nested token transfer during the callback. The receiver must still satisfy principal-plus-fee repayment, but it already receives the principal and can be prefunded with the fee, so repayment does not prevent the theft. [9](#0-8) [8](#0-7) 

### Likelihood Explanation
Exploitation requires a victim to submit a flash loan naming the malicious receiver and sign an authorization tree containing the receiver’s additional token transfer. That makes this a user-authorization-scope attack rather than a fully unauthenticated exploit, but the `receiver` and `data` fields are intentionally opaque and unprivileged callers have no protocol-level indication of which child invocations the callback will request. [4](#0-3) [6](#0-5) 

### Recommendation
Do not expose unrestricted caller-selected callback contracts to account callers unless clients can prove and display the exact authorization tree before signing. Prefer a receiver registry or a fixed adapter contract for externally initiated flash loans, and require clients to reject any authorization child other than the expected repayment-related operations. At minimum, return or surface a deterministic authorization manifest for the expected callback so wallets can compare the signed tree against it.

### Proof of Concept
1. Deploy a Wasm receiver implementing `execute_flash_loan`.
2. Prefund it with the flash-loan fee.
3. In `execute_flash_loan`, call `token::Client::new(&env, &victim_token).transfer(&initiator, &attacker, &victim_balance)`.
4. Approve the pool for `amount + fee` so the normal repayment check succeeds.
5. Convince the victim to call `Controller::flash_loan(caller=victim, asset, amount, receiver=malicious_receiver, data)` and sign the authorization tree returned by simulation.
6. The callback steals `victim_token` into `attacker`, the receiver repays principal plus fee, and the transaction succeeds. [10](#0-9) [8](#0-7)
