### Title
`provision?` third disjunct bypasses `repository.review_stacks_enabled` due to operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends to gate all auto-provisioning behaviors behind `repository.review_stacks_enabled`, but Ruby's `&&`/`||` precedence causes only the first disjunct to be gated by that flag. This allows an attacker to trigger review-stack creation and provisioning on repositories where review stacks are explicitly disabled, as long as `provisioning_behavior == 'prevent_with_label'` and the PR simply omits an unrelated label.

### Finding Description
The broken binding: the code intends `repository.review_stacks_enabled == <gate for every provisioning behavior>`, but the actual binding enforced is `repository.review_stacks_enabled == <gate only for provisioning_behavior_allow_all?>`.

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`.

The second and third disjuncts never reference `review_stacks_enabled`. So with `repository.review_stacks_enabled == false`, `repository.provisioning_behavior == 'prevent_with_label'`, and `provisioning_label_name == 'skip-review'`, any PR whose labels array does not contain `'skip-review'` (i.e., any normal PR, since the label is unset by default) makes `!pull_request_has_provisioning_label?` true, and `provision?` returns `true` regardless of `review_stacks_enabled`.

`respond_to_pull_request_opened?` then permits `process` to call:
```ruby
Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter
  .new(params, scope: repository.review_stacks).find_or_create!
``` [2](#0-1) 

`ReviewStackAdapter#create!` builds a stack with `branch: params.pull_request.head.ref` (attacker-controlled branch name from their own fork) and enqueues it for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)`. [3](#0-2) 

No further gate re-checks `review_stacks_enabled` before provisioning proceeds through the task/command pipeline that reads `shipit.yml` from the attacker's branch and executes it via `Command`/`PTY.spawn`.

Existing guards do not catch this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and `provision?` itself (the buggy method) — there is no separate `review_stacks_enabled` check at the call site. [4](#0-3) 
The webhook payload itself only requires standard PR shape fields (`ExplicitParameters` schema), none of which constrain provisioning behavior. [5](#0-4) 

Notably, sibling handlers implement the intended, correct gating pattern — `LabeledHandler#respond_to_label_change?` explicitly ANDs `repository.review_stacks_enabled` as a top-level term applying to the whole "archive or unarchive" decision, before delegating to behavior-specific logic: [6](#0-5) 
This confirms `OpenedHandler#provision?`'s inline mixing of the flag into only one disjunct is the root-cause bug, not intentional design.

The existing test suite covers `prevent_with_label` + absent label only with `review_stacks_enabled` left at its (enabled) default, so this specific combination (disabled + prevent_with_label + absent label) is untested: [7](#0-6) 

### Impact Explanation
An attacker who can open a pull request against any repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (with any `provisioning_label_name` unrelated to their PR's labels) can force creation and provisioning of a `Shipit::ReviewStack` using a branch/`shipit.yml` they control. Provisioning executes deploy steps from that spec via the `Command`/`PTY.spawn` pipeline, i.e., attacker-controlled code execution on the deploy host — Critical RCE. This is repeatable against any repository sharing this configuration and does not require any Shipit credentials, session, or API token; only the ability to open a PR (fork + push + open PR), which is available to any GitHub user with read access sufficient to fork.

### Likelihood Explanation
Preconditions are a specific but plausible repository configuration: `review_stacks_enabled == false`, `provisioning_behavior == 'prevent_with_label'`, and a `provisioning_label_name` set to some label the attacker's PR doesn't carry (default state for most PRs, since the label is opt-in). Given that combination, exploitation costs the attacker nothing beyond opening a PR — no privileged role, no secret, and it's fully repeatable per PR/repository matching the configuration.

### Recommendation
Fix the operator grouping so `review_stacks_enabled` gates the entire expression, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same review to `ReopenedHandler#provision?` if it shares this pattern.

### Proof of Concept
minitest (in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style, not modifying out-of-scope files but describing the plan):
1. Configure repository: `review_stacks_enabled = false`, `provisioning_behavior = :prevent_with_label`, `provisioning_label_name = 'skip-review'`.
2. Build `payload_parsed(:pull_request_opened)` with `payload["pull_request"]["labels"] = []` (no `skip-review` label).
3. Assert binding before: `repository.review_stacks_enabled == false` and expected `provision? == false`.
4. Call `OpenedHandler.new(payload).process`.
5. Assert `assert_difference -> { Shipit::Stack.count }` — demonstrates a stack was created despite `review_stacks_enabled == false`, proving the binding is violated.
6. Optionally assert the created stack's `branch` equals `payload["pull_request"]["head"]["ref"]` and that `TaskCommands.new(task).perform` command line reflects the attacker-controlled `shipit.yml` fixture step, confirming the RCE path is reachable.
