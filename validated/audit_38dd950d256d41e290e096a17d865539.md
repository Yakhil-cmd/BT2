### Title
Unbounded submodule recursion in `configureWorktree` can cause persistent sync-timeout denial - (File: main.go)

### Summary
The TWAP oracle bug is a class of "unbounded iteration over attacker/owner-influenced state that runs on every update cycle, with no ability to cap or exclude items and no partial-progress mechanism." The closest reachable analog in `git-sync` is the submodule checkout step of the sync loop: `configureWorktree` unconditionally runs `git submodule update --init --recursive` over every submodule declared in the synced commit, with no limit on submodule count/depth and no way to skip/exclude individual submodules, on every single sync attempt bounded by `--sync-timeout`.

### Finding Description
Each sync pass calls `configureWorktree`, which — unless `--submodules=off` — always executes a full submodule initialization/update over *all* submodules recorded in `.gitmodules` at the synced ref: [1](#0-0) 

This work happens inside the single per-attempt operation that is bounded by `--sync-timeout` (default 120s), and there is no per-submodule progress checkpoint, no submodule allow/deny list, and no way to exclude a misbehaving/huge submodule tree — the only knobs are the global `--submodules` mode and `--depth` [2](#0-1) . Because the repository content (including `.gitmodules`) is exactly the untrusted input synced from the remote, whoever controls the tip of `--ref` on the source repo fully controls how many submodules (and how deeply nested, per the earlier e2e test showing recursive nested submodules) are enumerated on every future sync attempt: [3](#0-2) .

If a commit is pushed that declares an extremely large number of submodules (or deeply/recursively nested submodules, each requiring its own clone+checkout), the `git submodule update --init --recursive` invocation can be made to take arbitrarily long. Unlike `TwapOracle.update`, which has literally no timeout and would revert/run out of gas forever, git-sync's operation is bounded by `--sync-timeout`, but that only converts "runs forever" into "always exceeds the timeout and fails every single attempt" — functionally the same denial-of-service outcome: the sync can never complete, so `--link` is never advanced past the last good commit.

Additionally, `createWorktree`/`removeWorktree` unconditionally re-create the worktree directory each attempt (`git.removeWorktree` then `git worktree add`) [4](#0-3) , meaning every failed attempt re-does the expensive clone-and-discard cycle rather than resuming partial submodule progress, compounding the effect.

### Impact Explanation
This is a persistent sync denial: once such a commit becomes the resolved tip of `--ref`, every subsequent sync attempt in the loop will time out on the submodule step, the symlink will never be flipped to the new hash, and (depending on `--max-failures`) the process may eventually exit non-zero, taking down the sidecar and any consumer relying on fresh data. There is no operator recovery path other than out-of-band intervention (changing `--ref` back, raising `--sync-timeout` indefinitely, or forcing `--submodules=off`), which mirrors the original finding's "cannot recover" characteristic. This is weaker than the original in one respect: it requires push/commit access to the synced repository (an "attacker-pushed commit" per the analog rules), not a compromised operator of git-sync itself.

### Likelihood Explanation
Any user syncing a repository that accepts external contributions (or where an attacker has any write access, e.g. via a compromised dependency repo, a malicious PR merged by mistake, or a repo that mirrors third-party content) can trigger this with a single crafted commit adding many/deep submodules. `--submodules=recursive` is the default [2](#0-1) , so no special flags are required by the operator to be exposed; the operator only needs to not have set `--submodules=off`.

### Recommendation
- Add a submodule count/size safety limit (or a configurable timeout specifically for the submodule step, separate from `git worktree add`/checkout) so a pathological `.gitmodules` cannot consume the entire `--sync-timeout` budget silently.
- Consider adding an allow/deny mechanism (e.g., `--submodules-paths` include/exclude) so operators can exclude known-bad or oversized submodule paths without disabling submodules entirely.
- Surface a distinct error/metric when the submodule step itself times out, so operators can detect "stuck on submodules" versus a generic sync failure.

### Proof of Concept
1. Configure `git-sync` with default `--submodules=recursive` against a repository where an attacker/contributor can push commits.
2. Attacker pushes a commit that adds a very large number of submodules (or a deeply recursive chain of submodules, as exercised in the nested-submodule e2e test) to `.gitmodules` at the tracked `--ref`.
3. On the next sync attempt, `configureWorktree` runs `git submodule update --init --recursive` over the full set [1](#0-0) ; with a sufficiently large/deep submodule graph this exceeds `--sync-timeout` (default 120s).
4. Every subsequent sync attempt repeats the same expensive, timing-out work (worktree is recreated from scratch each time per `createWorktree`), so the `--link` symlink is never advanced — a persistent sync denial that only an out-of-band fix to `--ref`, `--sync-timeout`, or `--submodules` can resolve.

func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}
