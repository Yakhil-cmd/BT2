### Title
Clickjacking of `MergeStatusController#show` via `X-Frame-Options: ALLOWALL` enables unauthorized `enqueue`/`dequeue` of merge-queue actions - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`MergeStatusController#show` unconditionally sets `response.headers['X-Frame-Options'] = 'ALLOWALL'` and skips `force_github_authentication`, allowing any origin to embed the merge-status page (including its `enqueue`/`dequeue` forms) in a cross-origin `<iframe>`. Because the embedded forms are genuinely rendered by Shipit with a valid CSRF token and the victim's session cookie, an attacker can use UI-redressing (not CSRF forgery) to trick a logged-in victim into submitting the real `enqueue_merge_request`/`dequeue_merge_request` request, triggering `MergeRequest.request_merge!` without the victim's actual intent.

### Finding Description
The intended binding is: `user_intentional_click_on_enqueue_button == MergeRequest.request_merge!_invocation`. That is, `request_merge!` (called from `MergeStatusController#enqueue`, [1](#0-0) ) should only fire when the authenticated user deliberately clicked the "Add to merge queue" button rendered on Shipit's own page.

`show` explicitly disables frame protection for itself and `check` via `skip_authentication only: %i[check show]` plus `response.headers['X-Frame-Options'] = 'ALLOWALL'` [2](#0-1) . `enqueue` and `dequeue` are not in the `skip_authentication` list, so they still run `force_github_authentication` and rely on `current_user`'s session cookie [3](#0-2) . `ShipitController` (the parent class) applies `protect_from_forgery with: :exception` [4](#0-3) , so a naive cross-origin forged POST/PUT/DELETE without a valid CSRF token is rejected — this rules out the specific PoC framing in the question (a raw cross-site POST with a spoofed Origin/Referer would indeed be blocked by `protect_from_forgery`).

However, the actual exploitable path is clickjacking, not CSRF forgery: the `_merge_queue_button.html.erb` partial renders a genuine `form_tag` to `enqueue_merge_request_path`/`dequeue_merge_request_path` with an automatically-embedded, valid Rails CSRF token [5](#0-4) . Because `show` (the page containing this button) is served with `X-Frame-Options: ALLOWALL`, an attacker's page can iframe `merge_status?stack_id=...&referrer=https://github.com/owner/repo/pull/N` cross-origin, overlay decoy UI, and trick a logged-in victim into clicking through to the real, same-origin form submit button. The browser sends the victim's real session cookie and the real CSRF token (read from the DOM by the browser itself, not by attacker JS, so Same-Origin Policy does not block it), and `MergeRequest.request_merge!(stack, params[:number], current_user)` executes exactly as if the victim had visited Shipit directly and clicked "Add to merge queue" [1](#0-0) .

Existing guards do not stop this: `protect_from_forgery` stops token-less forged requests but not clickjacking of a genuine form; `force_github_authentication` still requires a real logged-in `current_user`, but the victim already has one; nothing in the codebase sets a `frame-ancestors` CSP or restricts `ALLOWALL` to a specific trusted origin (e.g. `github.com`, which is presumably the intended consumer via `contrib/browser-extension`). The routes comment "`# Browser extension`" above the `merge_status`/`enqueue_merge_request`/`dequeue_merge_request` routes confirms the intent was to allow embedding by a specific browser extension context on `github.com`, but `ALLOWALL` grants this to any origin, not just that one [6](#0-5) .

### Impact Explanation
A successful clickjack causes `MergeRequest.request_merge!` (enqueue) or `merge_request.cancel!` (dequeue) to run for a pull request the victim did not actually intend to act on, mutating the stack's merge queue on behalf of the victim's session for a repository/stack chosen entirely by the attacker (the `stack_id`/`referrer` are attacker-controlled request parameters, not restricted to any repo the attacker owns). This matches the "unauthorized merge" category in Critical impact, since it forces a privileged, authenticated user's session into performing a merge-queue mutation they didn't consciously authorize. It is repeatable against any stack/PR combination and against any authorized Shipit user who can be lured into visiting the attacker's page while logged in.

### Likelihood Explanation
Preconditions: the victim must have an active, authorized Shipit session (cookie) and must be enticed to visit an attacker-controlled page containing the disguised iframe/overlay while logged in — a purely client-side social-engineering step, no Shipit or GitHub secrets required. The attacker needs only to know or guess a `stack_id` and PR number (often public GitHub information) to target. This is feasible with standard clickjacking techniques (opacity-zero iframe positioning, drag-drop tricks) and does not require defeating CSRF or authentication.

### Recommendation
Restrict `X-Frame-Options` on `show`/`check` to the specific trusted origin needed by the browser extension instead of `ALLOWALL` (e.g., only allow framing from `https://github.com`, or use a `Content-Security-Policy: frame-ancestors` scoped to that origin), and avoid rendering state-changing forms (`enqueue`/`dequeue`) inside a frame-embeddable page — if the browser-extension use case needs live status only, remove the mutating buttons from the framed page or require a fresh, non-cookie-based confirmation (e.g., re-entry of a nonce not present in the framed DOM) for `enqueue`/`dequeue`.

### Proof of Concept
Minitest plan (`test/controllers/merge_status_controller_test.rb`), documenting the header-level root cause without needing live GitHub:
```ruby
test "#show sets X-Frame-Options to ALLOWALL enabling cross-origin framing" do
  sign_in(shipit_users(:walrus))
  get :show, params: { referrer: 'https://github.com/shipit/shipit-engine/pull/1' }
  assert_equal 'ALLOWALL', response.headers['X-Frame-Options']
  # binding check: an ALLOWALL page containing a genuine enqueue/dequeue form
  # can be embedded and clicked cross-origin, defeating the intended
  # "explicit same-origin user action" binding for merge-queue mutation,
  # even though a direct forged cross-site POST is still rejected by
  # ActionController::InvalidAuthenticityToken (protect_from_forgery).
end
```
Because the exploit's core mechanism is a client-side UI-redress (rendering a real page in an attacker-controlled iframe and manipulating clicks), it cannot be fully demonstrated end-to-end inside a Rails integration test without a browser automation harness (e.g., Capybara + a headless browser rendering an attacker HTML page with the iframe). The minitest-level proof is therefore limited to asserting the permissive header on `show`, which is the root-cause control that enables the clickjacking surface; full exploit demonstration requires browser-level tooling outside `test/` unit/integration scope.

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
