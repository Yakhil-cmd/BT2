### Title
API Client Token Scoped to One Stack Can Read CCMenu Status of Any Stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper to resolve `params[:stack_id]` against the entire `Stack` table instead of using the scoped lookup defined in `BaseController`, breaking the binding between the stack an `ApiClient` token is authorized for and the stack it can actually query.

### Finding Description
`Shipit::Api::BaseController` restricts an `ApiClient` to its assigned stack via the `stacks` scoping method: [1](#0-0) 

This scoping is what enforces that a stack-scoped `ApiClient` (one created with a `stack_id`, e.g. the `here_come_the_walrus` fixture) can only read/act on that single stack — confirmed by the test `"an api client scoped to a stack will only see that one stack"` for `StacksController#index`.

However, `CCMenuController` (which also declares `require_permission :read, :stack`, so it inherits the scoping-dependent authorization model) defines its own private `stack` method that bypasses the base class's scoped `stacks` accessor entirely: [2](#0-1) 

Instead of `stacks.from_param!(params[:stack_id])`, it calls `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` relation. `require_permission :read, :stack` only checks that the token carries the `read:stack` permission string (via `ApiClient#check_permissions!`), it never checks *which* stack the token is bound to: [3](#0-2) 

So the equality that should hold — `stack authorized by token == stack touched by the request` — fails: any token with `read:stack` and a `stack_id` restriction can supply an arbitrary `stack_id` in the `/api/stacks/:stack_id/ccmenu` route and get status data for a stack it was never granted access to.

### Impact Explanation
This is an unauthorized read of stack state: name, deploy activity, last build status/label/time, and web URL of a stack the caller's token was never scoped to. This matches the "High" impact category of "unauthenticated read of stack state" from a credential that should be confined to a single stack.

### Likelihood Explanation
Exploitation only requires possessing any valid `ApiClient` token that has `read:stack` permission and is restricted to a specific stack (a routine, low-privilege token type intentionally created to limit blast radius) and the target stack's identifier (`owner/repo/env`), which is often guessable/enumerable. No elevated privileges are required beyond having any such scoped token.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction from `BaseController#stacks` is honored consistently across all API controllers.

### Proof of Concept
1. Create/obtain an `ApiClient` token scoped to Stack A (`stack_id` set to A, permissions `['read:stack']`) — e.g. as with fixture `here_come_the_walrus`.
2. Send `GET /api/stacks/<owner>/<repo>/<env-of-Stack-B>/ccmenu` using that token's Basic Auth credentials, where Stack B is a different stack the token was never assigned to.
3. `require_permission :read, :stack` passes because the token has `read:stack`, and `CCMenuController#stack` resolves Stack B directly via `Stack.from_param!`, bypassing the `current_api_client.stack_id` restriction enforced elsewhere.
4. Response returns Stack B's CCMenu XML (name, activity, last build status/label/time, web URL) despite the token being authorized only for Stack A.
