I searched the repository for any FRAME/pallet-revive analog of the Astaria bug — a "vault" contract that must call `approve`/`transferFrom` on itself to move its own held asset tokens without ever setting a self-allowance. That specific footgun is an artifact of Solidity's ERC-20 `approve`/`transferFrom` idiom being misused for self-authorized withdrawal.

In this codebase, pallet-internal balance/asset movements never go through an ERC-20-style self-approval indirection: `pallet_assets::do_transfer_approved` [1](#0-0)  is driven by an explicit `Approvals` storage entry created by a separate `approve_transfer` call from the actual owner to a delegate [2](#0-1) , not by a contract approving itself. Likewise the `pallet-assets` ERC20 precompile's `transferFrom` dispatches straight into `do_transfer_approved` using the caller-as-spender and an existing allowance record [3](#0-2)  — there is no vault-like contract in this codebase that needs to pull tokens from its own balance via `transferFrom(self, ...)`. A `grep_search` for `ERC4626` across the whole indexed codebase returned no matches, and no Solidity vault/router fixture resembling Astaria's `Vault.withdraw` exists in `substrate/frame/revive/fixtures` .

Without a reachable entry point exhibiting the same "self-transfer via unset self-allowance" pattern, there is no demonstrable Polkadot SDK analog to this report.
