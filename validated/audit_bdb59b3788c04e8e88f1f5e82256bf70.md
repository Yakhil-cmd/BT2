### Title
Bond rollover can shrink custodied sBTC below the shares still credited for the closing bond's final cycle - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond` allows a staker rolling from bond `N` into bond `N+6` to specify a smaller `sats-total` than their existing bond membership, refund the difference via `roll-sbtc`, while leaving `protocol-bonds-total-staked`/`total-shares-staked-for-cycle` for bond `N`'s remaining/final cycle untouched. The staker keeps full `N`-th cycle reward-share credit on sats they no longer have custodied.

### Finding Description
The broken equality is: *sats credited toward bond N's final-cycle reward share* should equal *sats actually custodied by the contract for that cycle*. In `register-for-bond` [1](#0-0) , when `existing-membership` is `some` (a rollover), `old-sbtc` is computed from `get-staker-custodied-sbtc`, and the caller supplies a new `sats-total` for bond `N+6` via `amount-ustx`/`btc-lockup`. There is no assertion anywhere in this function requiring `sats-total >= (get amount-sats existing-membership)` on a rollover.

The rollover-specific code path explicitly states it does *not* tear down bond N's old per-cycle shares: [2](#0-1) 
Only the new bond's `add-staker-to-bond-cycles` is invoked (line 799-801); nothing calls `remove-staker-from-bond-cycles` for bond `N`, and `protocol-bonds-total-staked`/`total-shares-staked-for-cycle` for bond N's final cycle remain fixed at the original `S1` value set when the staker first joined bond `N`.

Meanwhile, `roll-sbtc(tx-sender, old-sbtc, new-sbtc)` is called at line 784 and — per the question's premise and the netting design implied by the "nets a larger sBTC amount" test — transfers back the excess (`old-sbtc - new-sbtc`) to the staker when the new position is smaller. This means the staker gets `S1 - S2` sats of sBTC returned to their wallet, while `staker-shares-staked-for-cycle` / `total-shares-staked-for-cycle` for bond N's still-open final cycle continue to reflect `S1`.

`verify-bond-rollover-window` only restricts *when* the rollover can occur (the last half-cycle / L1 unlock window of bond N), not the *amount*, so it does not prevent this divergence — it only bounds the exploit window.

### Impact Explanation
For the remainder of bond N's final reward cycle, the staker's reward-per-token accrual is computed against the stale `S1` share count even though only `S2` (or zero, if fully rolled to an L1 lock) sats back that share. This is an unbacked reward-share credit: the staker earns yield proportional to `S1` sats no longer under custody, diluting the reward pool relative to other bond-N participants who remain honestly custodied for the same cycle — a case of double-counting a commitment / theft of sBTC rewards, matching the Critical category (unbacked minting of reward entitlement).

### Likelihood Explanation
This requires only: (1) a staker already holding a legitimate bond `N` membership, (2) calling `register-for-bond` for `N+6` inside the L1 unlock window with a smaller `sats-total`/`amount-ustx` than their existing commitment, and (3) the L2/sBTC custody path (since the sBTC transfer-back only exists on the sBTC path via `roll-sbtc`, not the L1 lockup path). No privileged role is needed — this is directly reachable by any allow-listed staker with an active bond, which is a normal, expected precondition for this function. It is repeatable each time a staker has an eligible bond nearing rollover.

### Recommendation
When rolling over and `new-sbtc + new-l1-collateral < old amount-sats`, either (a) require `sats-total >= (get amount-sats existing-membership)` on rollovers (disallow shrinking), or (b) call `remove-staker-from-bond-cycles`/decrement `protocol-bonds-total-staked` and `total-shares-staked-for-cycle` for bond N's remaining cycle(s) by the shrunk amount before netting/refunding the sBTC, mirroring the remove-then-add pattern already used in `update-bond-registration`.

### Proof of Concept
Rust/Clarity integration test on local chainstate:
1. Set up bond `N` and `N+6`; allowlist staker for both with sufficient `max-sats`.
2. Staker registers for bond `N` with `sats-total = S1` via sBTC lockup; advance to bond N's L1 unlock window.
3. Staker calls `register-for-bond(bond-index=N+6, ..., btc-lockup=err(S2))` with `S2 < S1`.
4. Assert the sBTC transfer event moved `S1 - S2` back to the staker (confirms refund).
5. Assert `(get-total-sbtc-staked-for-bond N)` / `total-shares-staked-for-cycle {reward-cycle: <bond-N-final-cycle>, bond-index: (some N)}` is still `S1` (unchanged), while the contract's actual sBTC balance backing bond N dropped by `S1 - S2`.
6. Settle rewards for bond N's final cycle and assert the staker's computed reward share exceeds what `S2` sats would proportionally earn — demonstrating the unbacked credit.
