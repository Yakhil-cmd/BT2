### Title
Webhook signature verification is keyed to the "authenticating" organization in the payload, not to the repository the handlers actually mutate - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` picks a `GitHubApp` instance from `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and asks *that org's* app to verify the HMAC signature: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

The webhook event handlers, however, never re-check `repository.owner.login` (the field used to select which org "authenticated" the request). Instead they resolve the target `Repository`/`Stack` purely from `repository.full_name`, an independent field in the same attacker-controlled JSON body: [4](#0-3) [5](#0-4) [6](#0-5) 

This is exactly the reported bug class: the field the signature-verification logic binds to (`repository.owner.login`, used to pick the org whose secret gates the request) is never checked for equality against the field the write path actually acts on (`repository.full_name`). Nothing in `WebhooksController#create` re-validates that the two point at the same organization: [7](#0-6) 

The break becomes concretely exploitable, without any credential, whenever a configured GitHub organization has no `webhook_secret` set (a supported, documented configuration state, as shown in the sample secrets file): [8](#0-7) 

Equality that should hold but doesn't:
`organization that authenticated the request (repository.owner.login, gated by that org's webhook_secret)` == `repository the handlers write to (repository.full_name, used by Repository.from_github_repo_name)`

Before the attack: any inbound webhook can only affect stacks belonging to the repository that GitHub actually signed for.
After the attack: an unauthenticated caller sets `repository.owner.login` to any org configured in Shipit with a blank/unset `webhook_secret` (satisfying `verify_signature` for free) while setting `repository.full_name` to the full name of a different, sensitive org/repo that does have Stacks configured. `PushHandler`, `StatusHandler`, the `PullRequest` handlers, and `CheckSuiteHandler` all act on `repository.full_name` alone.

### Impact Explanation
This crosses the "unauthenticated read/write of stack state" and, via `StatusHandler#process`, can directly forge CI/commit statuses (`Commit#create_status_from_github!`) for arbitrary commits in a target stack the attacker doesn't own -- statuses that feed directly into `Commit#deployable?`/CI-gating decisions used by continuous deployment. Combined with continuous delivery, this can escalate to an **unauthorized deploy** of a commit that never actually passed CI, and it enables cross-repository writes (`GithubSyncJob`, pull-request/review-stack archival, membership state) triggered against a Stack the forged "authenticating" organization does not own. This satisfies the report's "High" bar (unauthenticated read/write of stack state) and potentially "Critical" (unauthorized deploy) depending on deployment configuration.

### Likelihood Explanation
Requires only that at least one GitHub organization configured on the Shipit instance has no `webhook_secret` set -- a state the codebase's own sample configuration treats as normal/expected. No GitHub App private key, webhook secret, API token, or session is needed by the attacker; they only need to know (a) the org name lacking a secret and (b) the `full_name` of the target repository/stack, both of which are typically public information (GitHub org/repo names). This is a plausible, low-effort attack path for any Shipit deployment onboarding multiple orgs where one hasn't finished webhook-secret setup.

### Recommendation
- Cross-validate that `repository.owner.login` (or `organization.login`) used to select the verifying `GitHubApp`/secret matches the `repository.full_name` owner actually used by the handlers, rejecting mismatches.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; instead require an explicit signed-off "no verification" mode, or refuse to process events for organizations without a configured secret.
- Alternatively/additionally, resolve the target `Repository`/`Stack` using the same organization identity that gated signature verification, rather than trusting `repository.full_name` from the unauthenticated JSON body independently.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `org-empty` (no `webhook_secret` set, per the documented pattern in `config/secrets.development.shopify.yml`) and `victim-org` (has Stacks configured, e.g. `victim-org/app`).
2. Send an unauthenticated `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "full_name": "victim-org/app", "owner": { "login": "org-empty" } }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "org-empty")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`), regardless of the (or absent) `X-Hub-Signature` header.
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on the commit belonging to `victim-org/app`, forging a successful CI status the attacker never earned -- with zero credentials of any kind.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
