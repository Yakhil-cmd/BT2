### Title
temp_data purge only patches the kvstore copy of a unit, not all locations where the unit's JSON is persisted, allowing supposedly-erased sensitive `temp_data` to remain retrievable after purge - (File: storage.js)

### Summary
The `temp_data` message app lets any single unit poster attach transient off-chain data to a unit that is meant to be automatically removed from storage once `constants.TEMP_DATA_PURGE_TIMEOUT` has elapsed, similar in spirit to disk-cleanup obligations in the CVE (Ironic not cleaning disk after use, leaking sensitive data to later, unauthorized readers). The purge routine `purgeTempData()` in `storage.js` only overwrites the `kvstore` object for a unit; it does not touch every code path that can serve or persist the full unit JSON, so a purged `data` field can still be reachable through other paths after the purge is supposed to have happened.

### Finding Description
`purgeTempData()` finds units with `app='temp_data'` whose ball is older than `TEMP_DATA_PURGE_TIMEOUT` and deletes `m.payload.data` from the in-memory `objJoint` before writing it back with `kvstore.put('j\n' + unit, JSON.stringify(objJoint), ...)`: [1](#0-0) 

This routine is only invoked from a `setInterval(purgeTempData, 3600 * 1000)` (i.e. hourly) call registered in `initCaches()`, and additionally opportunistically on devnet time leaps: [2](#0-1) [3](#0-2) 

The read path `readJointJsonFromStorage()` falls back to reading from the SQL `joints` table when running under Cordova (`bCordova`), a code path that `purgeTempData()` never updates: [4](#0-3) 

Because `purgeTempData()` unconditionally calls `kvstore.put(...)` and never issues an `UPDATE joints SET json=...` for that alternate storage backend, any deployment that persists joints into the SQL `joints` table (Cordova/light wallets, or any future/alternate storage backend using this table) keeps the original, unpurged `data` field of the `temp_data` message forever, even though the hourly purge job believes it has scrubbed it. The purge job's own success log (`` `purged temp data in`, unit ``) gives a false sense that the sensitive payload has actually been erased everywhere it is stored.

Separately, even on the primary (non-Cordova) kvstore path, the purge only happens on an hourly timer, so a poster who intends the data to expire "immediately" after `TEMP_DATA_PURGE_TIMEOUT` seconds is exposed to an up-to-one-hour window (plus the timeout) during which any node can freely fetch the unpurged `data` via `readJoint`/`storage.readJoint`, `formula/evaluation.js`'s `unit` opcode, or ordinary history/joint requests, before the scheduled purge finally runs.

### Impact Explanation
`temp_data` is explicitly designed as a mechanism for authors (including AA triggers and regular unit posters) to publish data that should not remain permanently retrievable, presumably because it may contain sensitive off-chain information tied to a unit (the price model even charges `constants.TEMP_DATA_PRICE` per byte, treating it as ephemeral, not permanent storage). Failure to erase this data from every persisted representation of the joint means a "sensitive information obtained by remote users" outcome directly analogous to CVE-2015-7514: any peer that can request the joint/unit (which any unprivileged network participant can normally do) can recover data the protocol advertises as purged, on any full node whose storage backend keeps the SQL `joints` table in sync (Cordova wallets acting as full/light nodes), or during the delay window before the hourly job runs on standard nodes.

### Likelihood Explanation
This is reachable by any ordinary, unprivileged unit poster who includes a `temp_data` message in their own unit — no special privilege beyond normal unit composition is needed, and the vulnerability manifests automatically as a normal consequence of the built-in purge design, not through malicious peer/hub behavior. The condition depends on operating a node/build in Cordova mode or otherwise relying on the SQL `joints` table, and on the inherent hourly-cadence gap of the scheduled purge, both of which are deterministic properties of the shipped code rather than a hypothetical attack precondition.

### Recommendation
Make `purgeTempData()` update every location where a joint's JSON may be persisted, not just the kvstore key: also patch/scrub the SQL `joints` table row (`UPDATE joints SET json=? WHERE unit=?`) when it is used as a joint-JSON source, and audit any other cache/table that might retain the unstripped payload (e.g., verify `assocUnstableMessages`, in-memory joint caches, and light/history response caches do not retain and re-serve `payload.data` after purge). Consider shortening or eliminating the fixed one-hour scheduling gap (e.g., trigger a purge pass immediately once a unit crosses `TEMP_DATA_PURGE_TIMEOUT`, or run the purge check more frequently) to reduce the exposure window between the promised timeout and actual deletion.

### Proof of Concept
1. Post a unit containing a `temp_data` message with an actual `data` field (as validated in `validateInlinePayload`'s `"temp_data"` case) from any unprivileged wallet: [5](#0-4) .
2. Configure/observe a node that serves joints via the SQL `joints` table fallback path (Cordova build) as in `readJointJsonFromStorage`: [4](#0-3) .
3. Wait past `constants.TEMP_DATA_PURGE_TIMEOUT` and let the hourly `purgeTempData()` run; observe the "purged temp data in <unit>" log line confirming the node believes the data is gone: [6](#0-5) .
4. Query that node for the joint (e.g. via the standard `readJoint`/history request path) and observe that `message.payload.data` for the `temp_data` message is still returned in full, because only the kvstore representation was overwritten while the SQL `joints` table copy (or any pre-purge cached response) retains the original payload.
