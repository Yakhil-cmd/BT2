### Title
ERC20Transactor credits/debits the XCM-requested amount regardless of actual ERC20 balance delta, allowing fee-on-transfer/rebasing tokens to create unbacked `AssetsInHolding` credit - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` move ERC20 tokens by invoking `IERC20::transferCall` on an arbitrary `pallet-revive` contract identified by an XCM `Asset` location, and then unconditionally credit/debit the XCM-requested `amount` into `AssetsInHolding` based only on the boolean return value of the contract call, never checking the real balance delta of the `TransfersCheckingAccount`. This is the exact fee-on-transfer/rebasing-ERC20 bug class from the Teller Protocol report, reproduced inside the Polkadot SDK's XCM↔pallet-revive ERC20 bridge.

### Finding Description
`ERC20Transactor` is registered as an `AssetTransactor` in `asset-hub-westend`'s XCM configuration [1](#0-0) , meaning it is reachable by any signed account issuing ordinary `pallet_xcm` calls (e.g. `transfer_assets`, `execute`, reserve/local-reserve transfers) whose `Asset.id` matches (via `Matcher: MatchesFungibles<H160, u128>`) an EVM-style contract address deployed under `pallet-revive`. Since any user can deploy an arbitrary `pallet-revive` contract implementing the `IERC20` interface, the attacker fully controls the token contract's `transfer()` semantics.

`withdraw_asset_with_surplus` calls `transfer(checking_address, amount)` on the asset contract from the withdrawing account, and if the call succeeds (`is_success == true`) it unconditionally constructs: [2](#0-1) 
i.e. it credits the *requested* `amount` into `AssetsInHolding` — not the amount that was actually received by `TransfersCheckingAccount`.

Symmetrically, `deposit_asset_with_surplus` calls `transfer(beneficiary, amount)` from `TransfersCheckingAccount`, and on success simply returns `Ok(surplus)` [3](#0-2)  without verifying that the beneficiary's balance actually increased by `amount`.

A fee-on-transfer or rebasing ERC20 contract can return `true` from `transfer()` while delivering strictly less than `amount` to the recipient (a well known ERC20 pattern, exactly what the referenced Teller Protocol issue calls out). Because `Erc20Credit(amount)` is constructed from the requested amount rather than a measured balance delta, the XCM executor's internal holding account is credited with tokens that were never actually received by `TransfersCheckingAccount`. This mismatch propagates into `AssetsInHolding`, which downstream XCM instructions (e.g. `DepositAsset`, `BuyExecution`/`Trader`, `AssetTransferFilter`) treat as backed value.

### Impact Explanation
Every `withdraw_asset_with_surplus` call for a fee-on-transfer/rebasing asset creates holding value greater than what `TransfersCheckingAccount`'s real ERC20 balance actually increased by. This is unbacked issuance inside the XCM executor's bookkeeping: subsequent `DepositAsset` operations (crediting other beneficiaries, or `BuyExecution`) will act on inflated `AssetsInHolding` amounts that the checking account cannot actually back. As more such deflationary-token deposits/withdrawals accumulate, `TransfersCheckingAccount`'s real balance is progressively drained relative to what the ledger believes it holds, so future legitimate `deposit_asset_with_surplus` calls for that asset will begin failing (funds effectively stuck / DoS for other users of the same asset), or — if the contract instead inflates on transfer — attacker-controlled ERC20 semantics can be used to extract more value out of the checking account than was ever deposited. This satisfies "unbacked issuance"/integrity-break criteria for the affected asset class.

### Likelihood Explanation
Any account can permissionlessly deploy a `pallet-revive` contract implementing `IERC20` with fee-on-transfer or rebasing semantics, then register/use that contract's address as an XCM-fungible asset matched by `Matcher`. No privileged role, governance action, or validator/collator collusion is required — the attacker only needs ordinary signed-extrinsic access to deploy a contract and issue XCM instructions referencing it (`transfer_assets`/`execute`), which is standard, enabled functionality on asset-hub-westend.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the actual balance delta of `TransfersCheckingAccount` (via `balanceOf` before/after the `transfer` call) rather than trusting the boolean return value plus the requested `amount`. Construct `Erc20Credit`/report success using the measured delta, and reject (or return the correct lesser amount as) any asset whose measured transferred amount differs from the requested amount, consistent with standard fee-on-transfer token handling recommendations.

### Proof of Concept
Not executed against a live network; this is a static-code/logic analysis based on reading `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` and confirming its wiring in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs` (grep-confirmed usage, 2 references) via the `Matcher: MatchesFungibles<H160, u128>` bound that maps arbitrary XCM `Location`s to `pallet-revive` contract addresses. A full reproduction would require: (1) deploying a fee-on-transfer `IERC20` contract via `pallet-revive`, (2) issuing `pallet_xcm::transfer_assets`/`execute` referencing that contract's `Location`, and (3) asserting `TransfersCheckingAccount`'s real ERC20 balance delta is less than the `amount` credited into `AssetsInHolding` as reported by `withdraw_asset_with_surplus`. This reproduction was not run; the finding is based on code inspection of the failed check (missing pre/post-balance verification in `withdraw_asset_with_surplus`/`deposit_asset_with_surplus`) and confirmed reachability through the asset-hub-westend XCM configuration.
