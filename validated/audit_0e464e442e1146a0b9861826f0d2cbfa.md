Based on the investigation, I found a strong logic analog to CVE-2019-13686 (a "use of freed/stale offline content" bug class) in ocore's locally-pruned-content recovery path.

### Title
Unauthenticated peer can substitute forged output data for a locally-pruned final-bad unit, bypassing per-message payload hash validation - ([File: network.js])

### Summary
`getUnitHash()`/`hasValidHashes()` only commits to the *stripped* unit skeleton (`content_hash`, parents, authors, `last_ball`) when a unit's messages have already been removed from local storage, never to the actual message/output content. When a node locally prunes a `final-bad` unit's messages (`storage.js` `updateMinRetrievableMciAfterStabilizingMci`), it keeps only `content_hash` on disk. Later, if a new unit references a previously-spent output of that pruned unit, ocore does not have the output data locally and instead asks any peer to resend the "full" joint and trusts it via `tryRecoverPrunedContentOfFinalBadUnit`, checking only `allHashesAreValid()` — which for a "final-bad" unit only validates `hasValidPayloadHashes` message-by-message but has no independent commitment tying that data back to what was originally validated/stored, because the original joint's message content was never itself hashed into `objUnit.unit` for content-hash-bearing (`bFinalBad`) units.

### Finding Description
When a unit is pruned (`storage.js:1725-1746`), its `content_hash` is computed once from the naked unit and messages are stripped from the DB; the only artifact retained for reconstruction from peers is the anonymous `content_hash`. When a subsequent spend references such a pruned output and the value is not in the short-lived `archiving.js` cache (`assocCachedPrunedJoints`, TTL 1h), validation returns `unresolved_dependency` with `bRequestPrunedContent: true` (`validation.js:2462-2471`). `network.js` `ifNeedParentUnits` (lines 1229-1254) then re-requests the unit's raw content from **any peer** (not necessarily the original submitter), and when a response arrives, `tryRecoverPrunedContentOfFinalBadUnit` (`network.js:1007-1033`) accepts it purely on `validation.allHashesAreValid(objJoint)` [1](#0-0) , then immediately caches it via `archiving.cachePrunedJoint(objJoint)` and treats it as ground truth to satisfy the pending spend, without recomputing/comparing the recovered content's hash against the *stored* `content_hash` of the pruned unit in the `units` table [2](#0-1) . `allHashesAreValid` reduces to `hasValidHashes` (checks `getUnitHash(objUnit) === objUnit.unit`, only over naked/stripped fields when `content_hash` exists) plus `hasValidPayloadHashes` (checks each message's own self-declared `payload_hash` matches its own payload) [3](#0-2)  — none of these actually recompute `getUnitContentHash()` and compare it to the `content_hash` value stored on disk for that unit, so a malicious peer supplying `objJoint.unit.messages` can forge arbitrary `payment` outputs/amounts/addresses (self-consistent `payload_hash`) while keeping `objUnit.unit` identical to the already-known unit id (since content_hash-mode `getUnitHash` only hashes the naked/stripped unit, not the messages) [4](#0-3) .

The recovered (forged) output is then read back via `archiving.getCachedOutput()` inside payment input validation and trusted for `address`, `amount`, `denomination`, `asset` used to validate the new spending unit's input [5](#0-4) .

### Impact Explanation
This is reachable purely by any node re-requesting a `get_joint` for a locally-pruned unit and any responding peer (untrusted, no reputation needed) supplying forged content — an unprivileged unit poster can trigger the situation by simply constructing a spend that references an already-pruned final-bad output, then colluding with/controlling the peer that answers the resulting `get_joint` request. If the forged `amount`/`address` is accepted as the recovered output for input validation, a node can be tricked into accepting a spending unit whose declared input amount does not match the real historical output, enabling acceptance of an invalid payment (double-spend/asset amount mismatch) that would diverge from what other honest nodes (which still have the real content or reject the forged content) would accept — a node-disagreement-on-validity condition, and potentially unauthorized spending if the forged amount is inflated.

### Likelihood Explanation
Exploitation requires: (1) the attacker's own unit was previously final-bad and pruned locally by the target node (attacker fully controls this by crafting a non-serial/double-spend unit that eventually gets voided and ages past `min_retrievable_mci`), and (2) the attacker (or a colluding relay) is selected to answer the resulting `get_joint` re-request for that unit. Because `handleResponseToJointRequest`/`requestJoints` reroutes to "any peer," and the attacker can also just directly connect as that peer or be positioned as an outbound/inbound peer of the target, this is achievable by a single malicious node without needing to compromise witnesses or use privileged APIs.

### Recommendation
In `tryRecoverPrunedContentOfFinalBadUnit`, before trusting recovered content, recompute `objectHash.getUnitContentHash(objJoint.unit)` over the (message-bearing) recovered unit and compare it to the `content_hash` already stored in the `units` table for that unit (the value recorded at prune time), rejecting the joint if they don't match, in addition to the existing `allHashesAreValid` check.

### Proof of Concept
1. Attacker crafts unit A with a real payment output O (e.g., 100 bytes to address X), gets it accepted, then submits a conflicting/double-spend unit that causes A to become `sequence='final-bad'`.
2. Time/height passes until A's MCI falls below `min_retrievable_mci` on the target node, so `updateMinRetrievableMciAfterStabilizingMci` strips A's messages, keeping only `content_hash` [6](#0-5) .
3. Attacker submits unit B that spends output O of A to the target. Since A's content isn't cached anymore (TTL expired) validation returns `unresolved_dependency` with `bRequestPrunedContent:true` [5](#0-4) , and the target requests A's content from any peer [7](#0-6) .
4. Attacker (or a peer they control) responds to the `get_joint` request for A with a forged `objJoint` in which the naked/stripped unit fields (parents, authors, last_ball, etc.) are unchanged (so `getUnitHash` still matches `objUnit.unit`) but the `payment` message's `payload` (output amount to X) is altered, with a matching self-consistent `payload_hash`.
5. `tryRecoverPrunedContentOfFinalBadUnit` accepts this via `allHashesAreValid`, caches it, and replays B, which is now validated against the attacker-forged output amount/address rather than the real original output [8](#0-7) . [9](#0-8) [10](#0-9)

function hasValidHashes(objJoint){
	var objUnit = objJoint.unit;
	try {
		if (objectHash.getUnitHash(objUnit) !== objUnit.unit)
			return false;
	}
	catch(e){
		console.log("failed to calc unit hash: "+e);
		return false;
	}
	return true;
}

function hasValidPayloadHashes(objJoint) {
	try {
		if (!("messages" in objJoint.unit)) return true; // final-bad
		if (!isNonemptyArray(objJoint.unit.messages)) return false;
		for (let m of objJoint.unit.messages) {
			if (m.payload_location !== "inline") {
				if ("payload" in m)
					return false;
				continue;
			}
			const expected_payload_hash = objectHash.getBase64Hash(getPayloadForHash(m), objJoint.unit.version !== constants.versionWithoutTimestamp);
			if (expected_payload_hash !== m.payload_hash)
				return false;
			if (m.app === "temp_data" && "data" in m.payload) {
				const hash = objectHash.getBase64Hash(m.payload.data, true);
				if (hash !== m.payload.data_hash)
					return false;
			}
		}
	}
	catch (e) {
		console.log("failed to calc payload hash: " + e);
		return false;
	}
	return true;
}

function allHashesAreValid(objJoint) {
	return hasValidHashes(objJoint) && hasValidPayloadHashes(objJoint);
}


function getPayloadForHash(objMessage) {
	if (objMessage.app !== "temp_data")
		return objMessage.payload;
	let p = _.cloneDeep(objMessage.payload);
	delete p.data;
	return p;
}

/*jslint node: true */
"use strict";
var db = require('./db.js');

// in-memory holdover of joints we just voided (stripped final-bad units), so that for a while after pruning
// we can still serve their full content to peers and recover from spends that raced the pruning locally
const PRUNED_JOINT_CACHE_TTL_ms = 60 * 60 * 1000;
let assocCachedPrunedJoints = {};

function cachePrunedJoint(objJoint){
	assocCachedPrunedJoints[objJoint.unit.unit] = { objJoint: objJoint, expiry_ts: Date.now() + PRUNED_JOINT_CACHE_TTL_ms };
}

function getCachedPrunedJoint(unit){
	const cached = assocCachedPrunedJoints[unit];
	if (!cached)
		return null;
	return cached.objJoint;
}

// looks up a specific output within a cached pruned joint, in the same shape as the outputs table columns we lost to stripping
function getCachedOutput(unit, message_index, output_index){
	const objJoint = getCachedPrunedJoint(unit);
	if (!objJoint)
		return null;
	const message = objJoint.unit.messages && objJoint.unit.messages[message_index];
	if (!message || message.app !== 'payment' || !message.payload)
		return null;
	const output = message.payload.outputs && message.payload.outputs[output_index];
	if (!output)
		return null;
	return {
		address: output.address,
		amount: output.amount,
		denomination: message.payload.denomination || 1,
		asset: message.payload.asset || null
	};
}

function purgeExpiredCachedPrunedJoints(){
	const now = Date.now();
	for (let unit in assocCachedPrunedJoints)
		if (assocCachedPrunedJoints[unit].expiry_ts < now)
			delete assocCachedPrunedJoints[unit];
}
setInterval(purgeExpiredCachedPrunedJoints, PRUNED_JOINT_CACHE_TTL_ms);
