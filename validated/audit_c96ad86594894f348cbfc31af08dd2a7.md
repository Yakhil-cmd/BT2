### Title
Cross-tenant Team/Membership mutation via `MembershipHandler#find_or_create_team!` matching on `github_id` alone - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook against the organization derived from the payload's own `organization.login` field, so a webhook signed with `attacker-org`'s own legitimate `webhook_secret` passes verification for `attacker-org`. `MembershipHandler#find_or_create_team!` then looks up (or creates) a `Team` solely by `github_id`, without ever checking that the pre-existing team's `organization` matches the authenticated organization, allowing an attacker who controls their own org's webhook to mutate a `Team`/`Membership` belonging to a different (victim) organization.

### Finding Description
The binding that must hold is: `organization authenticated by verify_signature` (`repository_owner`, resolved from the payload and checked against `Shipit.github(organization: repository_owner).verify_webhook_signature`) == `Team#organization` of the row mutated by the handler. This does not hold.

- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , and verifies the signature using `Shipit.github(organization: repository_owner).verify_webhook_signature` [2](#0-1) . For a `membership` event with no `repository` key, `repository_owner` is `organization.login` from the body, which the attacker controls, but it must correspond to an org whose `webhook_secret` the attacker knows — trivially true for the attacker's own org, since `Shipit.github` resolves per-organization config and validates the HMAC using that org's own `webhook_secret` [3](#0-2) .
- Once verified, `WebhooksController#create` dispatches the raw JSON body to `MembershipHandler.call` with no further tie to the authenticated organization [4](#0-3) .
- `MembershipHandler#find_or_create_team!` performs `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [5](#0-4) . The block that sets `organization` only executes on **creation**; if a `Team` row with that `github_id` already exists (e.g., owned by `shopify`), `find_or_create_by!` returns the existing record untouched, regardless of what `organization.login` the attacker put in the payload.
- `MembershipHandler#process` then calls `team.add_member(member)` for `action == 'added'`, appending the attacker-controlled `member.login` user to that pre-existing team's membership list [6](#0-5) , and `Team#add_member` performs the insert unconditionally if not already a member [7](#0-6) .

No code checks that `team.organization == repository_owner` (the authenticated org) before or after the `find_or_create_by!` lookup. The only guard is HMAC signature verification, which is scoped to the *requesting* organization, not to the *target team's* organization — these are conflated by the handler.

Attacker's request: attacker registers their own org `attacker-org` with Shipit's GitHub App and a webhook secret they know. They send `POST /webhooks` with header `X-Github-Event: membership`, signed with `attacker-org`'s `webhook_secret`, body:
```json
{"action":"added","team":{"id":<shopify_team_github_id>,"name":"x","slug":"x","url":"x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker-login"}}
```
This passes `verify_signature` (org = attacker-org, secret matches), reaches `MembershipHandler`, and since a `Team` with that `github_id` already exists (owned by `shopify`), it is mutated to add `attacker-login` as a member.

### Impact Explanation
An unprivileged attacker who merely operates their own GitHub org (with Shipit's app installed) can insert arbitrary GitHub logins as `Membership` rows into a `Team` belonging to a completely different tenant, without ever authenticating as, or being authorized by, that tenant. If the targeted team's `github_id` is one of the teams referenced by `Shipit.github_teams` (used for OAuth-team-based authorization, `github_teams` config option builds `Team` records from configured `oauth.teams` [8](#0-7) ), this becomes an authorization escalation: `attacker-login`'s corresponding `User` gains membership of a team that grants Shipit-side privileges via `User#authorized?`, i.e., cross-tenant privilege escalation. This matches the High severity category ("escalation into `Shipit.github_teams` authorization") and, given the arbitrary write into another tenant's data with no tie-back check, arguably data of Critical concern ("a payload for one repository/tenant mutating another's ... team").

### Likelihood Explanation
Preconditions: the attacker's org must be a legitimately configured GitHub organization within Shipit's multi-org config (i.e., Shipit's `github_app_config` must resolve a config for `attacker-org` with the attacker's own known `webhook_secret` and the app installed there) — this is the normal onboarding a self-serve Shipit deployment supports. The attacker needs only to know the `github_id` of the victim's `Team` (GitHub team IDs are visible via GitHub's API responses, e.g., team webhooks, org member listings, or team URLs, and are not secret in general). No Shipit session, API token, or GitHub App private key/secret of the victim org is required. The attack is repeatable at will and requires only a single crafted HTTP POST per membership change.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that any existing `Team` matched by `github_id` also has `organization == params.organization.login` (and that `params.organization.login` matches the organization that authenticated the webhook, i.e., `repository_owner`/`event.organization`) before mutating it; raise/reject (or create a new team scoped differently) on mismatch. More generally, the webhook processing pipeline should pass the authenticated organization down to handlers and have handlers assert scoping against it rather than trusting the unauthenticated payload fields to select records to mutate.

### Proof of Concept
```ruby
test ":membership webhook from attacker-org cannot mutate a team owned by shopify" do
  shopify_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: e.g. 42
  attacker_user = nil

  # attacker-org is configured in Shipit with its own webhook_secret known to the attacker
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', webhook_secret: 'attacker-secret')
  )

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: shopify_team.github_id, name: shopify_team.name, slug: shopify_team.slug, url: shopify_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-login' }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', payload)
  @request.headers['X-Hub-Signature'] = signature

  post :create, body: payload, as: :json
  assert_response :ok

  attacker_user = Shipit::User.find_by(login: 'attacker-login')
  # Binding check: organization that authenticated ('attacker-org') != Team#organization mutated ('shopify')
  assert_equal 'shopify', shopify_team.reload.organization
  assert Shipit::Membership.exists?(team_id: shopify_team.id, user: attacker_user),
    "attacker-controlled user was inserted into a team owned by a different, unauthenticated organization"
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
