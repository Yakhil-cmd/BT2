### Title
Webhook signature verification keys off `repository.owner.login`, not the `repository.full_name` the handlers act on, allowing cross-organization forgery of webhook events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a delivery against using the `repository.owner.login` (or `organization.login`) field of the JSON body, then, once "verified", dispatches the *same raw params* to the event handlers, which independently derive the repository to mutate from `repository.full_name` [1](#0-0) [2](#0-1) [3](#0-2) . Because Shipit explicitly supports hosting multiple, independently-secreted GitHub Apps for multiple organizations on one instance [4](#0-3) [5](#0-4) , the field used to pick the *verification secret* and the field used to pick the *repository/stack being written to* are never checked for consistency.

### Finding Description
`verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, uses it to fetch the corresponding `GitHubApp` config via `Shipit.github(organization: repository_owner)`, and verifies the HMAC signature with that org's `webhook_secret` [6](#0-5) . `verify_webhook_signature` only checks that the raw body's HMAC matches the secret configured for that one organization [7](#0-6) .

Once the signature is accepted, `create` parses the *same* raw body and fans it out unmodified to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) . Every handler resolves the repository/stack to act on from `payload.dig('repository', 'full_name')`, e.g. the base `Handler#stacks` helper [3](#0-2) , and the pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`) which look up `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive or create review stacks accordingly [8](#0-7) [9](#0-8) .

There is no code path anywhere in `verify_signature` or in `Handler` that cross-checks that the `repository.owner.login` used to select the verifying webhook secret matches the `repository.full_name`'s owner used by the handler. This is structurally the same class of bug as the NEAR report: two different fields of the same input are treated as equivalent/bound together (there, the shard a chunk belongs to vs. the shard actually tracked; here, the org whose secret signs the payload vs. the org/repo the payload claims to mutate), and only one of the two is actually validated.

Concretely, on a Shipit instance configured for multiple organizations (as documented and tested, e.g. `OrgOne`/`OrgTwo` each with their own `webhook_secret` [10](#0-9) [11](#0-10) ), an actor who legitimately controls `OrgTwo`'s GitHub App/webhook secret (the org they were granted onboarding for) can:
1. Set `repository.owner.login` = `OrgTwo` (or `organization.login` = `OrgTwo`) so `Shipit.github(organization: 'OrgTwo')` is used and the HMAC is computed/verified against the secret they know.
2. Set `repository.full_name` = `OrgOne/some-private-repo` (a repository belonging to a different, unrelated organization hosted on the same Shipit instance).
3. Send a `push`, `pull_request`, `status`, or `commit_status`/`merge_status` event; `verify_signature` passes because the signature matches OrgTwo's secret, and the handler acts on `OrgOne/some-private-repo` because it never reads `repository.owner.login` again.

### Impact Explanation
This breaks the trust binding `{organization that authenticated} == {repository the engine writes to}`. Handlers driven this way can, on a repository the attacker never had legitimate GitHub access to: enqueue a `GithubSyncJob` re-sync via the `push` handler, create fabricated commit statuses via the `status` handler, and archive/unarchive/provision review stacks via the pull_request handlers — i.e. cross-organization/cross-repository state writes on stacks the attacker does not own, satisfying the "Critical - cross-repository writes" bar in the rules.

### Likelihood Explanation
This requires the deployment to be configured with more than one GitHub organization/App under `secrets.yml` (an explicitly documented and tested supported configuration) and requires the attacker to be a legitimate operator of one of those onboarded orgs, but not of the victim org. No token, session, or admin credential of the Shipit app itself is needed — only the attacker's own org's webhook secret, which they already legitimately hold as part of normal onboarding. Given multi-tenant use is a first-class, documented feature, likelihood is realistic wherever it is enabled.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the signature, re-derive `repository_owner` from the *same* `repository.full_name` field the handlers use (or pass the verified organization down into the handler pipeline) and reject/short-circuit the request if the organization used to select the webhook secret does not match the owner portion of `repository.full_name` (and, for organization-scoped events, that `organization.login` matches). This restores the invariant that the entity whose secret signed the payload is the same entity whose resources the payload is allowed to mutate.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`, `OrgOne` (victim, secret unknown to attacker) and `OrgTwo` (attacker's own org, secret known to attacker), per the documented multi-org format [4](#0-3) .
2. Attacker builds a `pull_request`/`opened` (or `push`) JSON body with `repository.owner.login = "OrgTwo"` and `repository.full_name = "OrgOne/victim-repo"`.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgTwo_webhook_secret, raw_body)>` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgTwo').verify_webhook_signature(...)`, which succeeds because the attacker signed with `OrgTwo`'s secret [12](#0-11) [7](#0-6) .
5. `create` dispatches to `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler`, which resolves `Shipit::Repository.from_github_repo_name('OrgOne/victim-repo')` and creates/updates a review stack for the victim's repository [8](#0-7) , despite the attacker having no relationship to `OrgOne`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
