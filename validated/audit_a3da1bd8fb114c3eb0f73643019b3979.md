### Title
AddKey action fees (`add_full_access_key`/`add_function_call_key_*`) never charge for the actual `PublicKey` byte length, letting large ML-DSA-65 keys inflate `compute_receipt_size` for free - ([File: runtime/runtime/src/config.rs])

### Summary
`permission_send_fees` / `permission_exec_fees` in `runtime/runtime/src/config.rs` charge a flat base fee for `AddKeyAction::FullAccess` and a base+method-name-bytes fee for `FunctionCall` permission, but never look at `public_key.len()`/`trie_id_len()` to price the key bytes themselves. Since `PublicKey::MLDSA65` borsh-encodes to ~1953 bytes versus 33/65 bytes for classical keys, an `AddKey` action with an ML-DSA-65 key adds ~1900 extra bytes to the wire-serialized receipt (as measured by `compute_receipt_size`) at zero extra gas cost. This is unrelated to the `Delegate`/`signature_verification_cost` mechanism hypothesized in the question — that cost line only prices the delegate/tx signature's own verification and was never intended to cover inner-action byte costs.

### Finding Description
`exec_fee`/`total_send_fees` route `AddKey` actions through `permission_exec_fees`/`permission_send_fees` [1](#0-0) . Inside those helpers:
- `FullAccess`/`GasKeyFullAccess`: only the flat `ActionCosts::add_full_access_key` fee is charged - no per-byte term at all.
- `FunctionCall`/`GasKeyFunctionCall`: base fee plus `add_function_call_key_byte` scaled only by the `method_names` bytes; the `public_key` itself is never included in `num_bytes`. [2](#0-1) [3](#0-2) 

Separately, `signature_verification_cost` only charges for the *signer*/`Delegate` inner-signer's own signature scheme, and is documented as being unrelated to any other charge: "the extra verification cost of ML-DSA-65 ... in-contract cross-contract calls are unaffected" [4](#0-3) . So the premise that this cost is supposed to cover inner `AddKey` payload growth is incorrect by design — it never did, for delegated or non-delegated transactions alike.

The real gap is that `compute_receipt_size` (`borsh::object_length(&receipt)`) counts the full wire-encoded `PublicKey`, which for `MLDSA65` is ~1953 bytes per the documented borsh tag lengths (33/65/1953) [5](#0-4) , while the AddKey fee functions never multiply by that length. This receipt size feeds directly into congestion/bandwidth accounting (`ReceiptSinkV2::forward_or_buffer_receipt`, `ReceiptsStats::add_receipt`) which enforces `outgoing_receipts_usual_size_limit`/`outgoing_receipts_big_size_limit` and tracks `receipt_bytes` for congestion [6](#0-5) [7](#0-6) .

Note: the documented fix in the PQ feature only retrofitted `trie_id_len()` (33 bytes) into *storage-stake* and *gas-key* fee paths (`access_key_storage_usage`, `gas_key_*_fee` helpers) [5](#0-4) ; the ordinary (non-gas-key) `AddKey` send/exec fee functions were never wired to any key-length-based charge at all, before or after the PQ feature, so this is a pre-existing gap in the fee model rather than something introduced by, or exploitable specifically through, the `Delegate`-action signature-cost mechanism described in the question.

### Impact Explanation
An attacker (ordinary account holder) can submit `AddKey` actions (with `FullAccess` or `FunctionCall` permission) using an ML-DSA-65 public key, whether directly or wrapped in a `Delegate`/`DelegateV2` action, and pay the same gas as an ED25519/Secp256k1 `AddKey` despite the receipt being ~1900 bytes larger. Repeated at scale this inflates `compute_receipt_size`/`receipt_bytes` cheaply relative to intended per-byte pricing, contributing to congestion/bandwidth accounting (`outgoing_receipts_usual_size_limit`, `max_congestion_memory_consumption`) at below-cost gas price — a gas/storage metering-completeness gap (NEAR bounty class: gas/resource metering bypass / congestion accounting failure), not a signature-verification-cost bypass as the question's framing suggested.

### Likelihood Explanation
Feasible and repeatable by any account holder: create/queue many `AddKey` actions (direct or via `Delegate`) each carrying a fresh ML-DSA-65 public key. No special privileges or state are required beyond `PostQuantumSignatures` being enabled. However, note the magnitude is bounded (each action adds a fixed ~1900-byte "discount", not unboundedly scalable per action) and per-transaction/receipt size caps (`max_receipt_size`, `max_transaction_size`, action count limits) still bound the total achievable amplification per receipt/chunk.

### Recommendation
Add a per-byte charge to `permission_send_fees`/`permission_exec_fees` in `runtime/runtime/src/config.rs` (and the corresponding host-function paths in `runtime/near-vm-runner/src/logic/logic.rs` / `wasmtime_runner/logic.rs`) based on `public_key.len()` (wire/borsh size, matching what `compute_receipt_size` actually measures), for both `FullAccess` and `FunctionCall` permissions — not just `trie_id_len()` (which only reflects trie storage, not wire/receipt size). Introduce a new `ActionAddKeyPerByte`-style parameter if none exists, calibrated via the params estimator, and require a protocol-version gate since this changes gas costs.

### Proof of Concept
Unit test in `runtime/runtime/src/config.rs` (alongside existing `ml_dsa_65_*` tests), or an integration test in `test-loop-tests/src/tests/`:
1. Build two `AddKeyAction`s with `AccessKeyPermission::FullAccess`: one with an ED25519 public key, one with an `MLDSA65` public key.
2. Wrap each in a minimal `Receipt`/`ActionReceipt` (or `SignedTransaction`), compute `exec_fee`/`total_send_fees` gas via `tx_cost`, and separately compute `compute_receipt_size` on the resulting `Receipt`.
3. Assert: `gas_ed25519 == gas_mldsa65` (fee functions are indifferent to key type/size) while `size_mldsa65 - size_ed25519 ≈ 1920` bytes (matching the documented 33 vs 1953 byte encoding difference).
4. Repeat wrapping the `AddKey` inside a `Delegate`/`DelegateV2` action to confirm the gap persists identically regardless of delegation, demonstrating the fee omission is independent of `signature_verification_cost`.

fn permission_send_fees(
    permission: &AccessKeyPermission,
    fees: &RuntimeFeesConfig,
    sender_is_receiver: bool,
) -> ParameterCost {
    let key_fee = match permission {
        AccessKeyPermission::FunctionCall(perm)
        | AccessKeyPermission::GasKeyFunctionCall(_, perm) => {
            let num_bytes = perm
                .method_names
                .iter()
                // Account for null-terminating characters.
                .map(|name| name.as_bytes().len() as u64 + 1)
                .sum::<u64>();
            let base_fee =
                fees.fee(ActionCosts::add_function_call_key_base).send_fee(sender_is_receiver);
            let byte_fee =
                fees.fee(ActionCosts::add_function_call_key_byte).send_fee(sender_is_receiver);
            let all_bytes_fee = byte_fee.checked_mul(num_bytes).unwrap();
            base_fee.checked_add(all_bytes_fee).unwrap()
        }
        AccessKeyPermission::FullAccess | AccessKeyPermission::GasKeyFullAccess(_) => {
            fees.fee(ActionCosts::add_full_access_key).send_fee(sender_is_receiver)
        }
    };
    let gas_key_info_fee = match permission {
        AccessKeyPermission::GasKeyFunctionCall(..) | AccessKeyPermission::GasKeyFullAccess(_) => {
            gas_key_add_key_send_fee(fees, sender_is_receiver)
        }
        _ => ParameterCost::ZERO,
    };
    key_fee.checked_add(gas_key_info_fee).unwrap()
}

fn permission_exec_fees(
    permission: &AccessKeyPermission,
    config: &RuntimeConfig,
    account_id: &AccountId,
    public_key: &PublicKey,
) -> ParameterCost {
    let fees = &config.fees;
    let key_fee = match permission {
        AccessKeyPermission::FunctionCall(perm)
        | AccessKeyPermission::GasKeyFunctionCall(_, perm) => {
            let num_bytes = perm
                .method_names
                .iter()
                // Account for null-terminating characters.
                .map(|name| name.as_bytes().len() as u64 + 1)
                .sum::<u64>();
            let base_fee = fees.fee(ActionCosts::add_function_call_key_base).exec_fee();
            let byte_fee = fees.fee(ActionCosts::add_function_call_key_byte).exec_fee();
            let all_bytes_fee = byte_fee.checked_mul(num_bytes).unwrap();
            base_fee.checked_add(all_bytes_fee).unwrap()
        }
        AccessKeyPermission::FullAccess | AccessKeyPermission::GasKeyFullAccess(_) => {
            fees.fee(ActionCosts::add_full_access_key).exec_fee()
        }
    };
    // Additional costs for adding an access key with GasKeyFunctionCall or GasKeyFullAccess permissions.
    let gas_key_info = match permission {
        AccessKeyPermission::GasKeyFullAccess(info)
        | AccessKeyPermission::GasKeyFunctionCall(info, _) => info,
        _ => return key_fee,
    };
    let nonce_fee = gas_key_add_key_exec_fee(
        fees,
        account_id.len(),
        public_key.trie_id_len(),
        gas_key_info.num_nonces,
    );
    key_fee.checked_add(nonce_fee.total()).unwrap()
}

/// Extra cost burnt at conversion for the signature verifications this
/// transaction triggers: the signer's own signature plus each `Delegate`
/// action's inner signer, each looked up by scheme in
/// `signature_verification_costs`. The charge is the extra verification cost
/// relative to the classical schemes; only ML-DSA-65 is non-zero, while
/// ed25519/secp256k1 stay 0 for backwards compatibility. The compute cost
/// debits the chunk's wall-clock budget and may be set independently of the
/// gas cost.
fn signature_verification_cost(
    fees: &RuntimeFeesConfig,
    signer_public_key: &PublicKey,
    actions: &[Action],
) -> Result<ParameterCost, IntegerOverflowError> {
    let costs = &fees.signature_verification_costs;
    let mut total = costs[signature_kind(signer_public_key.key_type())];
    for action in actions {
        if let Some(delegate_action) = delegate_inner_action(action) {
            let kind = signature_kind(delegate_action.public_key().key_type());
            total = total.checked_add_result(costs[kind])?;
        }
    }
    Ok(total)
}

### 5. Storage usage and fee plumbing

The storage-stake calculation
(`runtime/runtime/src/access_keys.rs::access_key_storage_usage`) and the
gas-key fee helpers (`gas_key_*_fee` in `runtime/runtime/src/config.rs`) use
`PublicKey::trie_id_len()` rather than `PublicKey::len()`:

- `len()` reports the borsh-encoded length (33 / 65 / 1953 across the
  three `PublicKey` variants).
- `trie_id_len()` reports the on-trie length (33 / 65 / **33**).

The two diverge only for `PublicKey::MLDSA65`. Every storage-stake and
trie-byte-priced fee path was updated to call `trie_id_len()`.
