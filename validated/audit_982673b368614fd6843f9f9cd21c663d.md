### Title
Cross-repository forged CI status via unscoped `Commit.where(sha:)` lookup enables destructive sabotage of a victim stack's deploy/merge eligibility - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit for an incoming GitHub `status` webhook purely by `sha`, with no check that the webhook's originating repository matches the repository of the `Stack` that owns the matched `Commit`. Because a commit's `sha` is derived from Git content/history and is trivially reproduced by any fork or repository that shares that history, an attacker who owns an unrelated repository (with the Shipit GitHub App installed and thus a validly-signed webhook channel) can post a forged `state: 'error'`/`state: 'failure'` status for a sha that also exists in a victim's tracked stack, flipping the victim's already-`success` commit to non-deployable.

### Finding Description
The broken binding is:
`commit.stack.repository.full_name` (the repository whose deploy/merge eligibility is governed by the CI context) **==** the `repository`/`name` field of the incoming webhook payload that supplied the status (the repository whose CI actually produced that context).

Tracing the call path:
1. `WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event('status')` → `Handlers::StatusHandler`. [1](#0-0) 
2. `verify_signature` only checks that the HMAC signature matches the webhook secret configured for `Shipit.github(organization: repository_owner)` — i.e., it authenticates that *some* app installation belonging to that organization/app config sent the payload. It does **not** verify that the `sha`/`context` in the payload belongs to a commit that was ever part of that same repository. [2](#0-1) 
3. `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This query is global across the `commits` table — it is not scoped by `stack_id`, `repository_id`, or the payload's `repository`/`name` field. [3](#0-2) 
4. `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` creates a new `Status` row for **every** matching commit, regardless of stack/repository. [4](#0-3) [5](#0-4) 
5. `Commit#deployable?` and `Stack#branch_status`/`merge_status` are recomputed from the newly-inserted status via the `error > failure > pending > success` hierarchy implemented in `Status::Group#select_significant_status`. [6](#0-5) [7](#0-6) [8](#0-7) 

The `commits` table's uniqueness constraint is on `(sha, stack_id)`, not `(sha, repository)`, confirming that the same sha is expected/allowed to exist independently across many stacks. [9](#0-8) 

Exploit flow: an attacker forks or otherwise obtains a repository whose git history contains an identical commit sha to one tracked by a victim's Shipit stack (trivial for forks — the sha is deterministic from tree/parents/authorship and identical between upstream and fork). The attacker's repository has the Shipit GitHub App installed (a self-service action any GitHub user/org can perform on a public app, independent of the victim). The attacker then posts (or has their own CI post) a `status` API call on their own repo/commit with `state: 'error'`/`'failure'` and a `context` matching one the victim's stack considers meaningful (e.g., a common CI name like `ci/travis`). GitHub delivers a `status` webhook, correctly signed with the attacker's own app installation's secret, to Shipit. `verify_signature` passes because the signature is valid for that legitimate sender — but the sender's identity/repository is never checked against the target commit's owning stack. `StatusHandler#process` matches the victim's `Commit` row purely on `sha` and inserts the forged failing status, flipping `commit.state` to `error`/`failure` and `deployable?` to `false`.

None of the listed guards close this gap: `verify_signature` authenticates the org/app, not the repo-to-stack ownership; `ExplicitParameters` only validates payload shape (`sha`, `state`, `context`, etc.), not repository identity; there is no `require_permission!`/`User#authorized?` check because webhooks are unauthenticated-by-signature only; model validations on `Status`/`Commit` only check `state` inclusion and presence, not stack/repo cross-consistency.

### Impact Explanation
A payload signed by one repository's (attacker-controlled) GitHub App installation can mutate the `Status`/`Commit` state of a completely different, victim-owned `Stack`, blocking `deployable?` and merge eligibility (`Stack#merge_status`/`branch_status`) for a commit the victim never intended to be affected. This is a cross-tenant write: a request that authenticates repository A is used to write a durable record scoped to repository/stack B, matching the "Critical - unauthorized deploy, rollback or merge" / "payload for one repository mutating another's stack, commit" impact category, here exercised in the sabotage (denial) direction rather than the elevation direction. It is repeatable against any commit sha shared between an attacker-controlled repository and a victim's tracked stack (most straightforwardly, any fork of a victim's repository), and can be triggered indefinitely (repeated forged failing statuses re-block the commit each time it's recomputed).

### Likelihood Explanation
Preconditions: (1) the Shipit GitHub App (or an org-specific app in a multi-org config) must be installed on some repository the attacker controls — a low-cost, self-service step for a public app; (2) the attacker's repository must share a commit sha with the victim's tracked stack, trivially satisfied by forking the victim's repository (fork commits are byte-identical, hence sha-identical, to upstream until amended); (3) the attacker needs no Shipit session, API token, or GitHub App secret — only the ability to set a status on a commit in their own repository via their own valid GitHub credentials, which they inherently have as the repo owner. This makes the attack low-cost and fully repeatable by any GitHub user with a fork.

### Recommendation
In `StatusHandler#process` (and analogously in `CheckSuiteHandler`/other sha-keyed handlers), scope the `Commit` lookup to the repository identified in the webhook payload (`params.repository.full_name` / `params.name`) by joining through `Stack#repository` (e.g. `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_id: repository_from_payload.id })`), so a status can only ever be recorded against commits belonging to the stack whose backing repository actually produced it.

### Proof of Concept
Add a minitest to `test/models/commits_test.rb` (or a new webhook-level test) asserting the binding both before and after:

```ruby
test "create_status_from_github! does not let a status from an unrelated stack sabotage a deployable commit" do
  victim_commit = shipit_commits(:cyclimse_first) # belongs to victim stack, currently success
  assert_predicate victim_commit, :deployable?     # before: binding holds, commit is success/deployable

  # Simulate a cross-tenant commit with the SAME sha tracked under an unrelated attacker stack
  attacker_stack = shipit_stacks(:shipit)
  attacker_commit = attacker_stack.commits.create!(
    sha: victim_commit.sha, # shared sha (e.g. fork scenario)
    author: shipit_users(:walrus), committer: shipit_users(:walrus),
    authored_at: Time.now, committed_at: Time.now, message: "attacker's copy"
  )

  forged_status = OpenStruct.new(
    sha: victim_commit.sha,
    state: 'failure',
    context: 'ci/travis', # well-known context the victim relies on
    description: 'forged',
    created_at: 1.minute.ago.to_formatted_s(:db)
  )

  Shipit::Webhooks::Handlers::StatusHandler.new.call(forged_status.to_h.stringify_keys)

  victim_commit.reload
  refute_predicate victim_commit, :deployable?   # after: binding broken — victim sabotaged by attacker's own commit/webhook
end
```
This demonstrates that a status delivered against an attacker-owned `Commit` record sharing the victim's sha flips the unrelated victim commit's `deployable?` from `true` to `false`, with no relationship enforced between the webhook's originating repository and the victim's stack.

    def merge_status(backlog_leniency_factor: 2.0)
      return 'locked' if locked?
      return 'failure' if %w[failure error].freeze.include?(branch_status)
      return 'backlogged' if backlogged?(backlog_leniency_factor:)

      'success'
    end

    def backlogged?(backlog_leniency_factor: 2.0)
      maximum_commits_per_deploy && (undeployed_commits_count > maximum_commits_per_deploy * backlog_leniency_factor)
    end

    def branch_status
      undeployed_commits.each do |commit|
        state = commit.status.simple_state
        return state unless %w[pending unknown missing].freeze.include?(state)
      end
      'pending'
    end
