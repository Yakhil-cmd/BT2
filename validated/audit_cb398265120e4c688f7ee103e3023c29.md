### Title
Webhook signature verified against the org derived from `repository.owner.login`/`organization.login`, but handlers dispatch on the independently-controlled `repository.full_name` field, breaking the "organization authenticated == repository written" binding - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks the HMAC secret used to validate `X-Hub-Signature` based on a value extracted from the JSON body itself (`repository.owner.login`, falling back to `organization.login`), then, once "verified", the raw `params` hash is handed unmodified to every registered `Shipit::Webhooks::Handlers::Handler`. Those handlers resolve which `Repository`/`Stack` to mutate using a *different* field of the same payload: `payload.dig('repository', 'full_name')`. In a multi-organization deployment (each GitHub org has its own `webhook_secret` per `lib/shipit/github_app.rb` / `lib/shipit.rb#github_app_config`), nothing ties the org whose secret validated the signature to the org that is actually written to.

### Finding Description
- `verify_signature` computes `repository_owner` from the payload and fetches that organization's `GitHubApp` to verify the signature: [1](#0-0) [2](#0-1) 
- Multi-org configuration is explicitly supported, with one `webhook_secret` per organization: [3](#0-2)  and resolved via `Shipit.github_app_config`/`Shipit.github`: [4](#0-3) 
- Once verified, the entire raw payload (`params`) is dispatched, unfiltered, to every handler for the event: [5](#0-4) 
- All handlers (e.g. `PushHandler`, `StatusHandler`) resolve the target `Repository`/`Stack` via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a completely separate JSON key from the one used to pick the verifying org: [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository being written`. Because the controller derives the authenticating org from `repository.owner.login`/`organization.login` while the handler derives the target repo from the independent `repository.full_name` field, an attacker who legitimately controls (or knows the webhook secret for) Organization A can craft a payload where `repository.owner.login = "orgA"` (so the signature check uses, and passes against, Org A's secret) but `repository.full_name = "orgB/target-repo"`. The HMAC is computed over the raw JSON body as a whole, so the signature itself doesn't "cover" a semantic guarantee that owner and full_name agree — it only proves the body wasn't tampered with by someone who doesn't know Org A's secret. The attacker who does hold Org A's secret can freely set both fields to whatever they want in the same signed payload, including making `full_name` point at a repository belonging to Org B.

### Impact Explanation
This lets a party who legitimately has push/webhook-delivery capability into Organization A (e.g. because Org A installed its own GitHub App/webhook whose secret they can trigger from, or because Org A's secret leaked/was reused) forge `push`, `status`, `check_suite`, `pull_request`, or `membership` events that resolve against a stack belonging to a completely different, unrelated Organization B configured on the same Shipit instance. For `push` events this triggers `stack.sync_github(expected_head_sha: ...)` on Org B's stacks — an unauthorized cross-repository action driven by another organization's traffic. This matches the "Critical – cross-repository writes / unauthorized deploy" bucket, since it lets a signer for one tenant force GitHub-sync/status/membership actions against another tenant's stacks in a shared multi-org Shipit deployment.

### Likelihood Explanation
Exploitability is limited to genuinely multi-org Shipit deployments where more than one organization's GitHub App/webhook is configured (as explicitly documented and supported), and requires the attacker to be able to produce/trigger a validly signed webhook for at least one of the configured organizations (e.g. control of that org's GitHub App webhook delivery, which is the normal, intended way third parties interact with the engine — not a privileged Shipit account). Single-organization deployments (the common case, where `github_default_organization` is `nil`) are not affected because there's only one secret and it's implicitly self-consistent.

### Recommendation
After verifying the signature, re-derive the acting organization strictly from the same field the handlers will use (`repository.full_name`'s owner segment) rather than trusting a possibly-different field, and reject the webhook if `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`. Alternatively, verify the signature once using the correct app config keyed off `repository.full_name`, and refuse to process any event where the two fields disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` schema).
2. As a party with the ability to deliver a signed webhook for `orgA` (e.g. controlling `orgA`'s GitHub App webhook), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha that exists on orgB target repo>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
3. Sign the raw body with `orgA`'s `webhook_secret` and send it with header `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` (from `repository_owner`), successfully verifies the signature against `orgA`'s secret: [1](#0-0) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgB/target-repo")` and calls `stack.sync_github(...)` on `orgB`'s stack, even though the request was never signed by `orgB`: [6](#0-5) [7](#0-6)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
