### Title
Missing validation of `payload` field allows crash (uncaught TypeError) when processing an attacker-supplied private payment element - ([File: network.js])

### Summary
CVE-2018-14015 describes a crash in radare2's `sdb_set_internal`/`r_bin_dwarf_parse_comp_unit` caused by missing input validation on attacker-controlled data, leading to an invalid read and process crash. The analogous root cause pattern — dereferencing a nested field of an untrusted, attacker-supplied structure without first validating that the parent field exists — is present in ocore's private-payment handling path, which is directly reachable by a private-payment counterparty sending a device message.

### Finding Description
`handleOnlinePrivatePayment` in `network.js` validates only that `arrPrivateElements` is a non-empty array, but never validates that the first element actually contains a `payload` object before dereferencing it: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```

If a counterparty (a wallet peer sending `private_payment`/`private_payments` messages, reachable pre-authentication in the pairing/payment flow) sends `arrPrivateElements` where the first element has no `payload` field (or `payload: null`), the expression `arrPrivateElements[0].payload.denomination` throws `TypeError: Cannot read properties of undefined (reading 'denomination')`. This is exactly the same bug class as CVE-2018-14015: a nested field of attacker-supplied structured data is accessed without validating that its parent exists, causing an uncaught runtime exception (the JS analog of an "invalid read").

By contrast, other private-payment entry points in the codebase (e.g. `private_payment.js:validateAndSavePrivatePaymentChain`, `wallet.js:handlePrivatePaymentChains`) do explicitly check `isNonemptyObject(e.payload)` before further use: [2](#0-1) 

This confirms that `payload` presence is normally expected to be checked before use, but `handleOnlinePrivatePayment` (the network-message-driven private-payment entry point) omits this check for the very first field it touches.

### Impact Explanation
An uncaught `TypeError` thrown synchronously inside a message-handling callback in Node.js, if not caught by a surrounding `try/catch`, will propagate up and can crash the node process (uncaughtException), producing a denial of service against the receiving wallet/hub instance that is processing private payments. This matches the "network unable to confirm new units" / node-availability impact class permitted by the rules, triggered here by an unprivileged private-payment counterparty rather than a "malicious node/hub" p2p scenario.

### Likelihood Explanation
The private-payment message flow is reachable by any counterparty engaged in a private-asset transaction (a normal wallet-to-wallet interaction, not requiring special network privilege). Constructing `arrPrivateElements[0]` without a `payload` field is trivial for any sender controlling the JSON message content.

### Recommendation
Add an explicit validation step in `handleOnlinePrivatePayment` before accessing `arrPrivateElements[0].payload`:
```js
if (!ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("no payload in private element");
```
This should be inserted immediately after the `isNonemptyArray` check and before `unit`/`message_index`/`output_index` are read, mirroring the validation already present in `wallet.js:handlePrivatePaymentChains` and `private_payment.js`.

### Proof of Concept
1. As a counterparty/paired device, send a `private_payment` (or `private_payments`) network message whose body is `[{ unit: "<valid-looking-base64>", message_index: 0 }]` — i.e., omitting the `payload` field entirely, or setting `payload: null`.
2. `handleOnlinePrivatePayment` passes the `isNonemptyArray` check, then executes `arrPrivateElements[0].payload.denomination`, throwing a `TypeError` because `payload` is `undefined`.
3. If this exception is not caught by an enclosing handler, the Node.js process crashes/terminates on an unhandled exception, denying service to the wallet/hub node processing the message.

**Note on verification**: due to iteration limits, I was unable to fully trace every call site of `handleOnlinePrivatePayment` in `wallet.js` (5 references) and confirm whether all of them are wrapped in a try/catch that would downgrade this from a full process crash to a localized error; this should be verified by examining the exact invocation context in `wallet.js` before treating the impact as definitively "process crash" versus "unhandled promise/event rejection."

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
