### Title
API `X-Shipit-User` header lets any authenticated `ApiClient` impersonate an arbitrary `User` identity for privileged actions - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Shipit::Api::BaseController#current_user` derives the acting `User` from the client-supplied `X-Shipit-User` request header, with no verification that the request actually originates from that GitHub identity. Any request that is authenticated only via an `ApiClient` token (Basic Auth) can set this header to an arbitrary login and have privileged actions attributed to, and performed as, that impersonated `User`.

### Finding Description
`ApiClient` tokens authenticate the *caller* (an application/service), independent of any specific GitHub identity, via HMAC-signed token lookup: [1](#0-0) 

`current_user`/`identify_user`, however, is derived purely from an unauthenticated header: [2](#0-1) 

This breaks the intended binding: `ApiClient` (the credential that authenticates the request) == `User` (the identity acted-on-behalf-of and attributed in audit trails/authorization-sensitive calls). The `X-Shipit-User` header is never checked against any signature, GitHub OAuth session, or the `ApiClient#creator` association (`belongs_to :creator, class_name: 'User'` in `app/models/shipit/api_client.rb`). As long as the caller holds *any* valid `ApiClient` token with the relevant permission scope (e.g. `lock:stack`, `deploy:stack`), it can set `X-Shipit-User: <any-login>` and that arbitrary `User` record becomes `current_user` for the request.

This `current_user` is then passed directly into consequential actions across the API surface:
- `stack.lock(params.reason, current_user)` / lock update — [3](#0-2) 
- `deploy.trigger_rollback(current_user, ...)` and `active_task.abort!(aborted_by: current_user, ...)` — [4](#0-3) 
- `stack.trigger_task(params[:task_name], current_user, ...)` and `task.abort!(aborted_by: current_user)` — [5](#0-4) 
- `stack.trigger_deploy(commit, current_user, ...)` — [6](#0-5) 
- `MergeRequest.request_merge!(stack, params[:id], current_user)`, which sets `merge_requested_by` and is embedded verbatim into the eventual GitHub commit message (`Merge-Requested-By: <login>`) — [7](#0-6) [8](#0-7) [9](#0-8) 
- `deploy.report_healthy!(user: current_user)` / `report_faulty!` — [10](#0-9) 

Before the attacker's request: the actor recorded for a deploy/rollback/lock/merge is the entity that legitimately possesses the `X-Shipit-User` value's identity (or none/anonymous). After the attacker's request: identical privileged action executes attributed to and effectively "as" an arbitrary chosen `User`, breaking the equality `ApiClient-authenticated-caller == User-attributed-actor`.

### Impact Explanation
This directly maps to the review scope's "unauthorized deploy, rollback or merge" Critical bucket: a party holding only an `ApiClient` token (which is a separate, narrower trust boundary than a full GitHub-authenticated session) can force `trigger_deploy`, `trigger_rollback`, `request_merge!`, task triggers, and stack locks to be attributed to an arbitrary user of the operator's choosing. This corrupts audit trails/accountability for these ship/rollback/merge/lock actions and lets an attacker mask the true origin of an unauthorized action behind a legitimate-looking user identity (e.g., a team lead), which is exactly the kind of authorization/identity-binding violation the scope calls out ("a GitHub identity versus the `User` bound to the session").

### Likelihood Explanation
Exploitation only requires possessing any valid `ApiClient` token with the corresponding permission scope (`deploy:stack`, `lock:stack`, etc.) — the same prerequisite already needed to call these endpoints at all — plus setting one extra HTTP header, `X-Shipit-User`, to an arbitrary existing login. No cryptographic material, GitHub session, or elevated privilege is needed beyond what any legitimate integration already holds; the header lookup performs no correlation to the authenticated `ApiClient#creator` or its scope.

### Recommendation
Bind the acting user to the authenticated credential rather than an arbitrary client-supplied header: either drop `X-Shipit-User`-based impersonation entirely and use `@current_api_client.creator` (or a `System`/`ApiClient` actor) for attribution, or require that the header value match the `ApiClient`'s configured/creator identity (or be governed by its own permission), rejecting mismatches with 401/403 instead of silently trusting the header.

### Proof of Concept
1. Obtain a valid `ApiClient` token scoped only to `deploy:stack` for a given stack (e.g., a low-trust CI integration token).
2. Send `POST /api/stacks/:id/deploys` with `Authorization: Basic <token>` and header `X-Shipit-User: admin-login` (an arbitrary existing `User#login`).
3. `identify_user` resolves `current_user` to the `admin-login` `User` record purely from the header (`app/controllers/shipit/api/base_controller.rb:69-72`).
4. `DeploysController#create` calls `stack.trigger_deploy(commit, current_user, ...)`, creating/enqueuing the deploy attributed to `admin-login`, even though the request was never authenticated as that user — repeatable identically against `LocksController`, `RollbacksController`, `TasksController`, `MergeRequestsController`, and `ReleaseStatusesController`.
