### Title
Uncaught `Octokit::NotFound` from `User.find_or_create_by_login!` leaves a forged `Team` row permanently persisted - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` calls `find_or_create_team!` and commits a `Team` row before it calls `User.find_or_create_by_login!(params.member.login)`, which can raise an uncaught `Octokit::NotFound` if the attacker supplies a syntactically valid but non-existent GitHub login. Because the two calls are not wrapped in a shared transaction, the `Team` record created in step one survives even though the request as a whole fails with an unhandled exception.

### Finding Description
The binding that should hold is: `Team.exists?(github_id: params.team.id)` == `false` whenever the webhook request as a whole does not complete successfully. The code breaks this: [1](#0-0) 

`find_or_create_team!` uses `Team.find_or_create_by!`, which is its own implicit transaction that commits independently: [2](#0-1) 

The very next line calls `User.find_or_create_by_login!`, whose block invokes `Shipit.github.api.user(login)`: [3](#0-2) 

If the supplied `member.login` does not exist on GitHub, `Shipit.github.api.user(login)` raises `Octokit::NotFound`. This exception is not rescued anywhere in this path: not in `User.find_or_create_by_login!`, not in `MembershipHandler#process`, not in `Handler#call`/`Handler#initialize`, and not in `WebhooksController#create`: [4](#0-3) [5](#0-4) 

Since `Team.find_or_create_by!` already committed before the exception is raised, and there is no outer transaction spanning both statements, the `Team` row remains in the database even though the overall webhook request raises an unhandled exception (translating to a 500 response). Existing guards do not prevent this: `verify_signature` only authenticates that the request was signed with the secret associated with `repository_owner` (derived from the payload's own `organization.login`), it does not validate that `params.team.id` actually belongs to that organization, and no code re-checks or rolls back `Team` creation on later failure.

### Impact Explanation
An attacker who can produce a validly-signed webhook for an organization they control (or otherwise get a membership event delivered) can supply an arbitrary `team.id` while forcing the `member.login` lookup to fail, and still cause a permanent `Team` row to be created/attached with attacker-influenced `organization` value. Because the failure happens after the `Team` row is durably committed, every such probe permanently forges tenant state regardless of whether the rest of the handler (user creation, `Membership` row) ever completes. This is a repeatable write of a database row not properly scoped/validated to the requesting tenant, matching the "payload for one repository mutating another's stack/team" Critical impact category.

### Likelihood Explanation
The attacker only needs the ability to get a signed membership webhook delivered (e.g., control of an organization/installation whose webhook secret is verified by `verify_signature`) and no privileged Shipit role, session, or knowledge of Shipit-side secrets. Supplying a non-existent `member.login` costs nothing and is trivially repeatable against arbitrary `team.id` values, since `find_or_create_team!` runs and commits before the (deliberately) failing user lookup on every request.

### Recommendation
Wrap the entire `process` method (team lookup/creation, user lookup/creation, and the membership mutation) in a single `ActiveRecord::Base.transaction do ... end` block so that any exception, including `Octokit::NotFound` from the GitHub API call, rolls back the `Team` creation. Additionally, validate that `params.team`'s owning organization matches the organization the signature was verified against before creating any `Team` row.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
test "failed member lookup does not leave a persisted Team" do
  payload = {
    'action' => 'added',
    'team' => { 'id' => 999_999, 'name' => 'Victim Team', 'slug' => 'victim-team', 'url' => 'https://api.github.com/teams/999999' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'this-user-does-not-exist-xyz' },
  }

  Shipit.github.api.expects(:user).with('this-user-does-not-exist-xyz').raises(Octokit::NotFound)

  assert_raises(Octokit::NotFound) do
    Shipit::Webhooks::Handlers::MembershipHandler.call(payload)
  end

  # Binding check: no Team row should survive a failed request
  assert Shipit::Team.exists?(github_id: 999_999, organization: 'attacker-org'),
    "Team row persisted despite handler failing"
end
```
This demonstrates that `Team.find_or_create_by!(github_id: 999_999, organization: 'attacker-org')` commits before the uncaught `Octokit::NotFound` propagates, leaving the row in place.
