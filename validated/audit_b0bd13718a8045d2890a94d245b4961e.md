### Title
Internal consistency assertions in the in‑memory unit-cache TPS accounting (`getFinalTps`) can be crashed by an attacker-triggered AA response chain, causing full-node denial of service - (File: storage.js)

### Summary
`storage.js`’s `getFinalTps()` walks the in-memory unit caches (`assocStableUnits`, `assocStableUnitsByMci`) that are populated as units are validated, written and later stabilized, and re-derives a TPS (transactions-per-second) count from `count_aa_responses` fields that were previously written into those same cache objects by `aa_composer.js` while executing AA triggers. If the accumulated `count_aa_responses` recorded in the cache ever diverges from the actual response units reachable by walking parent links (e.g. because of interleaved/concurrent AA-trigger processing, or units being counted through more than one path), the function throws an uncaught `Error`, which is executed inside an `async` call chain (`updateTpsFees` → `stabilizeMci`) with no surrounding try/catch. This mirrors the PowerDNS pattern of "insert crafted data into a cache, then perform an operation that walks/aggregates the cache and asserts an invariant that can be violated," leading to a crash (assertion failure) rather than data corruption.

### Finding Description
`getFinalTps(objUnitProps)` recomputes a TPS estimate by:
1. Walking backward from the unit through `best_parent_unit`/`parent_units`, using cached `assocStableUnits[parent_unit]` entries, and summing `count_aa_responses` (`count` variable). [1](#0-0) 
2. Independently summing `count_aa_responses` for every stable unit stored in `assocStableUnitsByMci[i]` between `last_ball_mci` and the target `mci` (`countAll` variable). [2](#0-1) 
3. Asserting the two independently-computed counts agree, via a `throw Error` if they don't: [3](#0-2) 

`count_aa_responses` itself is mutated directly on the same cached object (`storage.assocStableUnits[unit]`) by `aa_composer.js` every time a primary AA trigger executes for that unit: [4](#0-3) 

This computation is not an optional debug check — it runs automatically for every stabilized unit after the v4 upgrade point, invoked from the main consensus/stabilization path: [5](#0-4) 
and from the writer’s post-commit path as well: [6](#0-5) 
via `updateTpsFees()` → `getFinalTpsFee()` → `getFinalTps()`: [7](#0-6) 

Because an ordinary user can trigger AA execution simply by sending a payment unit to any AA address (a primary AA trigger), and AAs can further chain to other AAs (secondary triggers) and to newly-defined AAs within the same trigger (as exercised by the test suite), a poster fully controls the shape and timing of the AA-response DAG that feeds these cached counters. Any accounting divergence between the "walk-up" count and the "scan-by-mci" count of `count_aa_responses` (e.g., due to units counted via multiple ancestor paths, forgotten/reverted response units in `revertResponsesInCaches`, or cache entries evicted by `shrinkCache` at inconvenient boundaries) throws inside an `async function` with no catch, producing an unhandled promise rejection that crashes the Node.js process on every full node that reaches that MCI — since the computation is part of consensus-critical, deterministic stabilization logic that every full node executes identically.

### Impact Explanation
Because `updateTpsFees`/`getFinalTps` runs on every full node as part of mandatory post-stabilization processing (not just the node that first sees the malicious unit), a crash here is a node-wide, then network-wide denial of service: once the offending unit becomes part of the DAG and reaches the relevant MCI, every full node that processes it hits the same assertion and crashes, stalling stabilization and halting confirmation of new units network-wide — matching the "network unable to confirm new units" impact class.

### Likelihood Explanation
Reaching this code path requires no special privilege: any address can post a payment to an AA, and any AA author can construct chains of AAs (including AAs that define and immediately trigger new child AAs, as already exercised in the test suite) that maximize the number of interacting response units and cached counters within one MCI. The exact conditions that produce a count mismatch depend on subtle cache bookkeeping (multi-path ancestor counting, cache eviction timing via `shrinkCache`, or reverted response units), so likelihood is Medium — it requires crafting a specific AA/DAG topology but does not require compromising a node, key material, or the network layer.

### Recommendation
- Replace the internal `throw Error` consistency checks in `getFinalTps` with a non-fatal defensive fallback (e.g., log the divergence via `eventBus.emit('nonfatal_error', ...)` similar to `throwError()` in the same file, and fall back to a conservative unstable/db-verified figure) so that a cache-accounting anomaly cannot crash the node. [3](#0-2) 
- Wrap `updateTpsFees`/`stabilizeMci` invocation in try/catch at the call sites so any residual invariant violation is caught, logged, and does not propagate to an unhandled promise rejection that terminates the process. [8](#0-7) 
- Audit `count_aa_responses` bookkeeping in `aa_composer.js` (`handlePrimaryAATrigger`, `revertResponsesInCaches`) and cache eviction in `storage.js` (`shrinkCache`) for scenarios where a unit’s `count_aa_responses` can be updated more than once, lost on revert, or evicted from `assocStableUnits`/`assocStableUnitsByMci` inconsistently relative to `last_ball_mci`. [9](#0-8) 

### Proof of Concept
1. Deploy a factory-style AA that, on trigger, defines a new child AA and immediately forwards funds to it in the same response unit (this pattern is already validated as functional in the test suite). [10](#0-9) 
2. Post multiple payment units in quick succession (before/around MCI stabilization) targeting the same AA and its dynamically generated children so that several primary/secondary AA triggers execute and update `count_aa_responses` on the same cached unit props concurrently via `handlePrimaryAATrigger`. [11](#0-10) 
3. Once the MCI stabilizes, `stabilizeMci` invokes `storage.updateTpsFees`, which calls `getFinalTps` for every stable unit in that MCI window; if the walk-up count and by-mci count of accumulated `count_aa_responses` diverge, the process throws inside the async chain and crashes. [3](#0-2) [12](#0-11)

function getFinalTpsFee(objUnitProps) {
	const mci = objUnitProps.main_chain_index;
	const base_tps_fee = getSystemVar('base_tps_fee', mci); // not at last_ball_mci
	const tps_interval = getSystemVar('tps_interval', mci);

// marks the MCI stable, executes triggers, and updates tps fees
async function stabilizeMci(mci) {
	const conn = await db.takeConnectionFromPool();
	await conn.query("BEGIN");
	const batch = kvstore.batch();
	const count_aa_triggers = await markMcIndexStable(conn, batch, mci);
	await util.promisify(batch.write.bind(batch))({ sync: true });
	await conn.query("COMMIT");
	conn.release();
	if (count_aa_triggers > 0) {
		console.log(`executing ${count_aa_triggers} AA triggers after stabilizing MCI ${mci}`);
		// every trigger takes its own db connection
		const aa_composer = require("./aa_composer.js");
		await aa_composer.handleAATriggers();
	}
	if (mci >= constants.v4UpgradeMci) {
		console.log(`updating tps fees after stabilizing MCI ${mci}`);
		// get a new connection to write tps fees
		const conn = await db.takeConnectionFromPool();
		await conn.query("BEGIN");
		await storage.updateTpsFees(conn, [mci]);
		await conn.query("COMMIT");
		conn.release();
	}
}
