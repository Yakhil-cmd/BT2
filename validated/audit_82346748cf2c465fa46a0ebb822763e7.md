### Title
Premature release of author-address mutex in AA-triggered unit validation allows a same-address double-spend race - ([File: aa_composer.js])

### Summary
CVE-2022-3566 is a Linux TCP race condition caused by a lock/refcount being dropped too early relative to the operation it was meant to protect (`tcp_getsockopt`/`tcp_setsockopt` racing on the same socket). The analogous bug class — a mutex being released before the state it guards is actually persisted — exists in `aa_composer.js`'s handling of AA-generated response units.

### Finding Description
`validation.validate()` serializes concurrent validation/spend-checking per author address by acquiring `mutex.lock(arrAuthorAddresses, ...)` before running double-spend and sequencing checks, and only calls the `unlock` callback (passed to `ifOk`) after the caller is done using the validated state [1](#0-0) .

Every legitimate caller of `validate()` respects this contract by holding the address lock until `writer.saveJoint()` (which actually commits the unit and updates the in-memory spend/sequence caches) has completed — see the pattern in `network.js`'s `handleJoint` [2](#0-1) , `composer.js`'s `getSavingCallbacks` [3](#0-2) , `divisible_asset.js` [4](#0-3) , and `indivisible_asset.js` [5](#0-4)  — all of which call `validation_unlock()` only inside the `onDone`/`save` callback of `writer.saveJoint`.

`aa_composer.js`'s `validateAndSaveUnit` breaks this pattern: it calls `validation_unlock()` immediately upon `ifOk`, **before** `writer.saveJoint()` is invoked: [6](#0-5) 

This releases the per-author-address mutex for the AA's own address while the response/bounce unit produced by the trigger is still unwritten (spends, `is_spent` flags, and unit caches in `writer.saveJoint` have not yet been applied). Because `objAAValidationState.bUnderWriteLock = true` is also set here, `writer.saveJoint` itself skips acquiring the `["write"]` mutex [7](#0-6) , relying entirely on the caller having already serialized writes — but the author-address lock that would have prevented a second validation pass for the same AA address from reading stale/uncommitted spend state has just been dropped.

### Impact Explanation
If any other unit or AA-response for the same AA address enters `validation.validate()` during the window between `validation_unlock()` and the completion of `writer.saveJoint()`, it will acquire the (now free) address mutex and run its double-spend/sequence checks against a database/cache state that does not yet reflect the first response's spends. This can result in two AA-authored outputs referencing the same input/balance being accepted as "sequence good," i.e., unauthorized double-spend of AA funds or divergent validity/sequence determination between nodes depending on timing — a node-disagreement / fund-loss class impact reachable purely by a trigger-sender causing overlapping AA responses (no privileged or malicious-peer role required).

### Likelihood Explanation
Exploitability depends on whether two `validateAndSaveUnit` calls for the *same* AA address can actually be scheduled concurrently in this codebase (e.g., via secondary triggers, bounce handling, or overlapping trigger executions within the same MCI). I could not fully confirm the enclosing concurrency guarantees of `handleTrigger`/`handleAATriggers` (i.e., whether some higher-level lock always serializes AA execution per address, which would neutralize this gap). Given the async, event-driven design of `aa_composer.js` and the explicit deviation from the safe unlock-after-save pattern used everywhere else in the codebase, this is a plausible, code-level race, but definitive confirmation of exploitability requires tracing all call paths into `validateAndSaveUnit` and verifying whether an outer lock (e.g., per-address AA execution lock) already prevents overlap.

### Recommendation
Move `validation_unlock()` in `aa_composer.js`'s `validateAndSaveUnit` (`ifOk` callback) to execute only after `writer.saveJoint()` completes (inside the callback passed to `writer.saveJoint`), matching the pattern used in `network.js`, `composer.js`, `divisible_asset.js`, and `indivisible_asset.js`. This ensures the per-author-address lock is held for the full duration during which the unit's spends are unwritten, preventing any concurrent validation for the same address from observing stale spend state.

### Proof of Concept
Not independently reproducible from static analysis alone — a concrete PoC would require confirming a code path (e.g., two triggers or a trigger plus a bounce/secondary response) that invokes `validateAndSaveUnit` twice for the same AA address without an intervening full serialization lock, then racing them so the second call's `validation.validate()` executes between the first's `validation_unlock()` (aa_composer.js:1825) and the completion of its `writer.saveJoint()` (aa_composer.js:1831-1835), causing both to pass sequence='good' against the same unspent output.
