### Title
Cross-organization Team hijack via `MembershipHandler#find_or_create_team!` ignoring organization scope, escalating into `Shipit.github_teams` authorization boundary - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::GitHubApp#verify_webhook_signature` legitimately returns `true` when an organization's `webhook_secret` is unset (a documented, supported configuration state), so any org with `webhook_secret: nil` accepts unsigned webhooks for itself. `MembershipHandler#find_or_create_team!` then looks up the mutated `Team` record solely by the attacker-supplied `github_id: params.team.id`, without verifying that this team's persisted `organization` matches the organization whose (absent) secret was used to accept the request, letting an attacker bind their own GitHub account to any pre-existing `Team` row, including one in `Shipit.github_teams`.

### Finding Description
The broken binding: **organization whose secret verified the webhook** (`Shipit.github(organization: repository_owner)` in [1](#0-0)  ) **==** **organization owning the `Team` row mutated** by `Team.find_or_create_by!(github_id: params.team.id)` in [2](#0-1) .

- `repository_owner` for a `membership` event (no `repository` key in the GitHub payload) resolves to `params.dig('organization', 'login')` — [3](#0-2) , i.e. exactly the same field `MembershipHandler` reads via `params.organization.login`.
- `Shipit::GitHubApp#verify_webhook_signature` short-circuits `return true unless webhook_secret` — [4](#0-3) . An operator with a valid, documented config where `github.<org>.webhook_secret` is left `nil` (shown as the default in `config/secrets.development.example.yml` and `docs/setup.md`) makes this branch reachable for that org with **any** body/signature.
- `find_or_create_team!` queries only by `github_id`; the `organization:` value from the payload is written **only inside the `find_or_create_by!` block**, which Rails only executes on record creation, not when an existing row is found — [2](#0-1) .
- `Team.add_member` unconditionally appends the member to whatever `Team` row was found — [5](#0-4) .
- `User.find_or_create_by_login!(params.member.login)` fetches the real GitHub user via `Shipit.github.api.user(login)` on creation, populating the **real** `github_id` for that login — [6](#0-5) . This is the same `github_id` used later by the legitimate OAuth callback path, `User.find_or_create_from_github` / `find_from_github(github_user)` which matches by `github_id` — [7](#0-6) , [8](#0-7) . So the membership row created by the forged webhook binds to the same `User` record the attacker controls when they later perform a real GitHub OAuth login.
- `User#authorized?` grants access purely based on team membership id intersection with `Shipit.github_teams`, with no organization cross-check — [9](#0-8) .

Exploit flow: attacker owns "attacker-org" (any real GitHub org they control) configured in Shipit with `webhook_secret: nil` (an in-scope, valid operator configuration for progressive onboarding). Attacker discovers or guesses the numeric GitHub `id` of a `Team` already present in Shipit's DB and referenced by `Shipit.github_teams` (e.g. "authorized-org/developers"). Attacker sends `POST /webhooks` with header `X-Github-Event: membership`, no `X-Hub-Signature` requirement satisfied since `attacker-org`'s secret is unset, and body:
```json
{"action":"added","team":{"id":<authorized_team_github_id>,"name":"x","slug":"x","url":"https://example.com"},
 "organization":{"login":"attacker-org"},"member":{"login":"<attacker_github_login>"}}
```
`verify_signature` passes trivially (webhook_secret nil for attacker-org). `MembershipHandler#process` finds the existing `Team` row by `github_id` (belonging to "authorized-org"), ignoring that the verified organization is "attacker-org", and adds the attacker's real GitHub account as a member of that authorized team. The attacker then logs into Shipit via the normal GitHub OAuth flow; `current_user.authorized?` now returns `true`.

None of the existing guards prevent this: `verify_signature`/`drop_unhandled_event` only gate on event name and per-organization secret presence, not on cross-referencing team ownership; the `ExplicitParameters` schema on `MembershipHandler` only type-checks fields (`Integer`/`String`), it does not bind `team.id` to `organization.login`; there is no model validation on `Team` enforcing `organization` immutability or uniqueness scoped by organization for `github_id` lookups.

### Impact Explanation
An attacker who controls an org with no configured `webhook_secret` can add their real GitHub account (via its correctly-resolved `github_id`) as a member of any pre-existing `Shipit::Team` row by guessing/enumerating its numeric GitHub team id, then complete a normal OAuth login to be treated as `authorized?`. This directly breaks the `Shipit.github_teams` authorization boundary gating access to the entire Shipit instance (stacks, deploys, tasks, secrets in env, etc.) — matching the High/Critical impact category "escalation into `Shipit.github_teams` authorization". It is repeatable against any team whose `github_id` the attacker can determine and is not limited to a single request (idempotent membership add).

### Likelihood Explanation
Requires: (1) the Shipit operator has at least one organization configured with `webhook_secret` unset — an explicitly documented, supported default configuration, not a misconfiguration outside scope; (2) the attacker knows or can enumerate the target `Team`'s GitHub numeric `id`, which is a plain integer, not a secret, and may be discoverable via public GitHub API team listings or historical exposure. No Shipit session, API token, or GitHub App secret is required, matching the unprivileged attacker model. Cost is a single crafted HTTP POST plus normal OAuth login.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify that the found record's `organization` matches `params.organization.login` before allowing membership mutations; reject (or no-op) the event otherwise. More fundamentally, avoid trusting an org's own "no secret configured" state to authorize mutations on teams belonging to a different organization.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":membership from an org with no webhook_secret cannot hijack another org's team" do
  attacker_org = 'attacker-org'
  authorized_team = shipit_teams(:shopify_developers) # belongs to organization 'shopify', id in Shipit.github_teams
  Shipit.stubs(:github_teams).returns([authorized_team])

  no_secret_app = Shipit::GitHubApp.new(attacker_org, webhook_secret: nil)
  Shipit.stubs(:github).with(organization: attacker_org).returns(no_secret_app)

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: authorized_team.github_id, name: 'x', slug: 'x', url: 'https://example.com' },
    organization: { login: attacker_org },
    member: { login: 'attacker_github_login' }
  }.to_json

  assert_no_difference -> { Team.count } do
    post :create, body: payload, as: :json
  end

  refute_includes authorized_team.reload.members.map(&:login), 'attacker_github_login'
end
```
This test asserts that, on the vulnerable code, the assertion FAILS (attacker is added), demonstrating that `organization` (`attacker-org`, verified) != `Team#organization` (`shopify`, mutated) — the broken binding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
