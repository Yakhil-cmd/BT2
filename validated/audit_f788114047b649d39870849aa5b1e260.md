### Title
RAY debt-value overflow permanently freezes an oversized market - (File: common/src/rates/index.rs)

### Summary
A sufficiently large, highly utilized market can reach a state where every subsequent interest accrual overflows `i128`, causing `update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, and liquidation-driven pool calls to revert before committing state. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`update_indexes` is callable by any signing address and forwards the supplied `Vec<HubAssetKey>` to the pool. [4](#0-3)  The pool then runs `interest::global_sync`, which invokes `accrue_step` for each elapsed chunk. [5](#0-4)  During accrual, `calculate_supplier_rewards` multiplies total scaled debt by both the new and old borrow indexes using `Ray::mul`, returning `MathOverflow` when either RAY product exceeds `i128`. [1](#0-0) [6](#0-5) 

The borrow-index ceiling bounds the index itself at `10^36`, but it does not bound `borrowed * borrow_index`; therefore, a large scaled-debt book overflows before the index cap becomes protective. [7](#0-6) [8](#0-7)  The repository’s own test demonstrates this state with a 1-billion-whole-token, 18-decimal market borrowed to 98% utilization: accrual returns `MATH_OVERFLOW`, while the committed borrow index remains below `MAX_BORROW_INDEX_RAY`. [9](#0-8) 

Once this condition exists, ordinary repayment also fails before debt can be reduced because `repay::accounting` calls `ops::load_leg`, which unconditionally calls `synced_market` and `global_sync` first. [10](#0-9) [11](#0-10)  Withdrawals have the same ordering: `withdraw::accounting` loads a synced market before resolving or burning the position. [12](#0-11)  The test confirms that both withdrawal and repayment revert with `MATH_OVERFLOW` after the cliff. [13](#0-12) 

### Impact Explanation
All supplier principal and outstanding borrower collateral/debt operations for the affected hub asset become inaccessible because no state transition can complete the mandatory accrual. [2](#0-1) [14](#0-13)  Borrowers cannot reduce debt, suppliers cannot exit, and liquidations cannot reach the pool’s repay or seize paths, so the market remains frozen absent a code-level fix or migration. [10](#0-9) [15](#0-14) 

### Likelihood Explanation
The attack requires supplying enough of the asset to create extremely large scaled totals and maintaining high utilization until the RAY-denominated debt value crosses `i128::MAX`. [16](#0-15)  This is capital-intensive and depends on a listed market being able to grow to that size, but it requires no privileged role, oracle manipulation, compromised key, or malformed protocol parameter. [17](#0-16) [4](#0-3) 

### Recommendation
Make accrual saturating at the RAY-value domain before multiplying `borrowed` by an index, or explicitly bound/reset scaled debt so `borrowed * MAX_BORROW_INDEX_RAY / RAY` remains representable. [1](#0-0) [7](#0-6)  At minimum, allow debt-reducing paths such as `repay` to use the last committed index when forward accrual is no longer representable, and add a market-level scaled-share ceiling derived from the maximum borrow index rather than relying on the index cap alone. [10](#0-9) [18](#0-17) 

### Proof of Concept
1. A user calls `supply` with `account_id = 0`, an active `spoke_id`, and a very large 18-decimal asset amount; `supply` is permissionless and only requires the caller’s authorization. [19](#0-18) 
2. The user supplies sufficient collateral and calls `borrow` to take the market to approximately 98% utilization; the test fixture uses `principal = 10^27` base units and `debt = principal * 98 / 100`. [20](#0-19) [21](#0-20) 
3. Once accrued interest makes `borrowed * borrow_index / RAY` exceed `i128::MAX`, any address calls `update_indexes(caller, vec![hub_asset])`; `calculate_supplier_rewards` overflows before `global_sync` can call `mark_accrued` or `commit`. [4](#0-3) [22](#0-21) [23](#0-22) 
4. Subsequent `repay(caller, account_id, payments)` and `withdraw(caller, account_id, withdrawals, to)` calls revert before debt or supply is reduced because both pool legs call `synced_market` first. [10](#0-9) [14](#0-13) [2](#0-1) 
5. The in-repository reproduction asserts `MATH_OVERFLOW` for `update_indexes`, `withdraw`, and `repay`, and asserts that the committed borrow index is still below `MAX_BORROW_INDEX_RAY`. [24](#0-23)

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }

    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
