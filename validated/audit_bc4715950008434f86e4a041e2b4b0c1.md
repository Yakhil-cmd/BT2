### Title
API token stack-scope bypass in CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports restricting a token to a single `Stack` via the `stack_id` association, and `Shipit::Api::BaseController` enforces that restriction through its `stacks`/`stack` helpers. `Shipit::Api::CCMenuController` overrides the `stack` method with a version that resolves the target stack directly from `params[:stack_id]`, bypassing the `current_api_client.stack_id` restriction entirely. This breaks the binding "stack a token authorises == stack it touches": a token scoped to (or intended for) one stack can be used to read CCTray/CCMenu status for any other stack.

### Finding Description
`Shipit::ApiClient` has `belongs_to :stack, optional: true` [1](#0-0) , and the base API controller enforces this scoping when resolving which stacks a client may act on:

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every controller inheriting from `BaseController` is expected to resolve `stack` through this scoped `stacks` relation, so that a token restricted to `stack_id: X` cannot be used against `stack_id: Y`. `Shipit::Api::CCMenuController`, however, defines its own `stack` method that ignores `stacks`/`current_api_client.stack_id` entirely and resolves the stack straight from request params:

```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

The controller only checks the coarse permission string via `require_permission :read, :stack` [4](#0-3) , which validates that `"read:stack"` is present in `current_api_client.permissions` [5](#0-4)  but never checks that the *specific* stack in the request matches the stack the token is authorised for. This is the same class of bug as the reported `ecrecover` issue: a verified/authenticated attribute of the credential (the token's `read:stack` permission plus its intended `stack_id` scope) is not actually compared against the value acted upon (`params[:stack_id]`); the check that exists elsewhere (`BaseController#stacks`) is silently skipped for this endpoint.

Any holder of a valid `read:stack`-permissioned `ApiClient` token — regardless of which stack it was created for/limited to — can authenticate to `GET /api/:stack_id/ccmenu.xml` (routed via `Shipit::Api::CCMenuController#show`) for an arbitrary `stack_id`, since `authenticate_api_client` in this controller also accepts the token via query string `params[:token]` [6](#0-5)  and `show` immediately calls the unscoped `stack` [7](#0-6) .

### Impact Explanation
This yields unauthenticated-relative-to-scope read of stack state for stacks the token was never authorised for: last deploy status, build label/time, and web URL of any stack in the installation, obtainable with a token meant to be limited to one stack. This matches the in-scope "High" impact category of "unauthenticated read of stack state, task streams or deploy output" via escalation past the token's intended stack-authorization boundary.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token carrying the `read:stack` permission (a low/read-only permission, plausibly widely distributed, e.g. embedded in CI dashboards or CCTray clients) and knowledge/guessing of another stack's `to_param` (owner/name/environment), which is often public information (repository owner/name). No privileged credentials, GitHub App keys, or session are required beyond a single low-privilege API token — which is consistent with the "unprivileged attacker" baseline since the attacker only needs *a* token, not *the specific* stack's token.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or make it delegate through the inherited `stacks` scoping) so that the CCMenu endpoint honors `current_api_client.stack_id` the same way every other `Api::BaseController` subclass does, ensuring the stack acted upon is always intersected with the stack(s) the authenticated token is authorised for.

### Proof of Concept
1. Create/obtain two stacks, `stack-a` and `stack-b`.
2. Create an `ApiClient` intended to be scoped to `stack-a` with permission `read:stack` (conceptually via `belongs_to :stack`; in this codebase the token-creation UI at `ApiClientsController#create_params` doesn't currently even expose `stack_id`, which independently means most `read:stack` tokens are effectively unscoped and could already read any stack through the properly-scoped `BaseController#stack`/`stacks`, but the point stands for any client whose `stack_id` is set, e.g. programmatically or in future UI additions).
3. As the holder of that token, send `GET /api/stack-b/ccmenu.xml?token=<token>` (or with `Authorization: Basic base64(token)`).
4. `authenticate_api_client` succeeds (`read:stack` present), and `CCMenuController#stack` resolves `stack-b` directly via `Stack.from_param!`, ignoring the token's `stack_id`, returning `stack-b`'s deploy status/XML even though the token is only meant to authorize `stack-a`.
