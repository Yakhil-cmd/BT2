### Title
Webhook signature verification is bound to `repository.owner.login` while all event handlers act on `repository.full_name`, allowing a legitimate webhook sender for one GitHub organization to forge Shipit events for any other organization's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate an incoming payload against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) . However, every event handler resolves the target `Stack`/`Repository` from a completely different field in the same payload: `repository.full_name`, via `Handler#repository_name` and `Repository.from_github_repo_name` [3](#0-2) [4](#0-3) . The HMAC check only proves the payload was signed with the secret of the organization named in `repository.owner.login`; it never proves that `repository.full_name`'s owner segment is the same organization. This is the same class of bug as the `WrappedIbbtcEth` finding: a value used for authorization/decision-making (`pricePerShare`) is decoupled from the value actually consumed for value transfer, letting an attacker exploit the gap between "the field that was checked" and "the field that was acted on."

### Finding Description
- `verify_signature` computes `repository_owner` from the payload and asks `Shipit.github(organization: repository_owner)` for that org's `GitHubApp`, then calls `verify_webhook_signature(signature, request.raw_post)` against that org's `webhook_secret` [1](#0-0) .
- `verify_webhook_signature` itself is a pure HMAC-SHA1 comparison keyed by whatever `webhook_secret` was fetched for that org - it says nothing about which repository the event concerns [5](#0-4) .
- After the signature step passes, `create` dispatches the *entire, attacker-controlled* JSON body to handlers, unmodified: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) .
- Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) locates the affected `Stack`(s) through `Handler#stacks`, which calls `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [3](#0-2) .
- `Repository.from_github_repo_name` simply splits `"owner/name"` from that field and looks up the DB row - it does not cross-check against `repository.owner.login` [4](#0-3) .

In a legitimate GitHub-issued webhook, `repository.owner.login` and the owner segment of `repository.full_name` are always the same value, so this gap is invisible under normal operation. But nothing in the engine enforces that equality server-side. In a multi-tenant Shipit installation (multiple organizations configured under `Shipit.github`, e.g. as shown in `config/secrets.development.shopify.yml` with `somegithuborg`/`someothergithuborg`) [7](#0-6) , any org that is a legitimate Shipit-configured tenant (and therefore knows/controls its own `webhook_secret`, e.g. because it operates the GitHub App or can trigger real deliveries to itself) can send a webhook to Shipit with:
- `repository.owner.login = "attacker-org"` (so the correct `webhook_secret` is used and signature validation passes), and
- `repository.full_name = "victim-org/victim-repo"` (so the handler resolves and acts on a stack belonging to an entirely different, unrelated organization).

The binding that should hold is:
```
organization whose webhook_secret authenticated the request == owner(repository.full_name) acted on by the handler
```
This equality is never checked; `verify_signature` checks the left side, handlers act on the right side, and the two are read from independent, attacker-controlled JSON fields in the same request body.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding explicitly called out as in-scope. Concretely, an org that is a legitimate (but otherwise unprivileged w.r.t. the victim) Shipit tenant can:
- Forge `push` events (`PushHandler`) causing `stack.sync_github(expected_head_sha: ...)` to run against a victim stack's branch, using the attacker's chosen `after` SHA [8](#0-7) .
- Forge `status`/`check_suite` events for a victim's commit, injecting fabricated commit statuses/check-run state that downstream deploy-readiness logic (deployable status, merge status, continuous delivery) consumes to decide whether a commit is safe to deploy.
- Forge `pull_request` lifecycle events (opened/closed/labeled/etc.) that drive `ReviewStackAdapter`/merge/label handlers for a victim repository.

Because `Repository#github_app` looks up the GitHub App by the *repository's own* configured `owner` (not the attacker's), any subsequent GitHub API call the engine makes as a result of this forged event (posting comments, updating deploy state, etc.) is performed with the legitimate GitHub App credentials of the victim organization - i.e., a completely unrelated tenant can trigger real state changes and real GitHub API side effects against a repository it has no relationship to, using only its own (valid) webhook secret. This satisfies "unauthorized deploy/rollback" / cross-tenant write impact.

### Likelihood Explanation
Exploitability requires:
1. A multi-tenant Shipit deployment with at least two organizations configured, each with its own `webhook_secret` (a documented, supported configuration - see `docs/setup.md` and the example `config/secrets.development.shopify.yml` listing multiple orgs) [9](#0-8) .
2. The attacker controls (or can trigger deliveries for) one such organization's webhook secret - which is exactly the "unprivileged w.r.t. other tenants" attacker model, not a privileged Shipit account or `ApiClient` token.
No repository write access, Shipit session, or `GITHUB_TOKEN` is needed - only the ability to send an HTTP POST to `/webhooks` with a body signed by any one configured org's secret and an arbitrary `repository.full_name`. This is a direct, low-effort forgery once an attacker organization is present in the multi-tenant configuration.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, enforce that the repository resolved for the event (`repository.full_name`'s owner segment, or the `Repository` row's `owner`) matches the organization (`repository.owner.login` / `organization.login`) whose secret validated the signature, and reject (422) the request if they diverge. Alternatively, always derive the repository lookup from a value that has been cross-validated against the authenticated organization, never trusting `repository.full_name` on its own once the org used for signature verification is known.

### Proof of Concept
1. Shipit is configured with two organizations, e.g. `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (a supported multi-tenant setup).
2. Attacker, who controls `attacker-org`'s webhook secret, computes `sha1=HMAC(attacker_secret, body)` over a crafted JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=...`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the HMAC check passes because the body was indeed signed with `attacker-org`'s secret [1](#0-0) .
5. `PushHandler` is invoked with the full `params`; `Handler#repository_name` reads `"victim-org/victim-repo"` from `repository.full_name`, resolves the real `victim-org/victim-repo` `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` [8](#0-7) [3](#0-2) , none of which validates that `victim-org` matches the `attacker-org` secret that authenticated the request.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
