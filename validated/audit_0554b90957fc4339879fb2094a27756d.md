### Title
Cross-organization webhook confusion allows deploy/rollback of a repository not owned by the authenticating organization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook against the GitHub App/webhook secret of the organization derived from `repository_owner` (payload `repository.owner.login`, falling back to `organization.login`), but the event handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#stacks`) resolve the target `Stack` purely from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`, with no cross-check that the resolved repository's owner matches the organization whose secret validated the signature. This breaks the binding "organization that authenticated == repository that is written," mirroring the referenced report's pattern where a value used to compute a result (the referrer/score) is not the same value that was actually verified.

### Finding Description
`verify_signature` computes `repository_owner` from the untrusted JSON body and looks up `Shipit.github(organization: repository_owner)` to obtain the secret used for HMAC verification: [1](#0-0) [2](#0-1) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full, still-untrusted JSON body to handlers: [3](#0-2) 

Handlers (e.g. `PushHandler`) resolve the affected stacks solely by `repository.full_name` from the same payload, independent of which organization key validated the signature: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` does a naive `owner/name` split-and-lookup with no relation to the verified organization: [6](#0-5) 

In a multi-organization Shipit deployment, `Shipit.github(organization:)` supports per-organization secrets keyed by organization name (`github_app_config`): [7](#0-6) 

Before/after the attack:
- **Before**: A webhook signed with `github["orgA"].webhook_secret` is only expected to affect stacks whose `Repository.owner == "orgA"`.
- **After**: An attacker who knows `orgA`'s webhook secret (e.g., an admin with legitimate configuration/webhook access for OrgA, but no privileges on OrgB) sets `repository.owner.login = "orgA"` (satisfying `verify_signature`) while setting `repository.full_name = "orgB/some-repo"` in the same JSON body. `verify_signature` passes using OrgA's secret, but `PushHandler#stacks` resolves and mutates OrgB's stack (triggering `stack.sync_github`, deploy pipelines, pull-request handling, etc.) — a cross-repository/cross-organization action that the verified signature never authorized for that repository.

This is the same root-cause shape as the referenced bug: a field consumed to produce an effect (the repository acted upon) is decoupled from the field that was actually authenticated (the organization/secret), letting an attacker substitute the acted-upon value while keeping the verified value pointed at their own controlled context.

### Impact Explanation
This crosses the "cross-repository writes" bucket: an entity that is only authenticated for organization A's webhook traffic can cause Shipit to process push/pull_request/status events (which schedule `GithubSyncJob`, update commit/CI status, and in the pull-request handlers can create or update `ReviewStack`s, close/label PRs, etc.) for a stack that belongs to organization B, entirely outside of A's authenticated scope. In multi-tenant/multi-org Shipit installations, this is an unauthorized cross-organization write against another team's deployment pipeline.

### Likelihood Explanation
Requires the attacker to already know one organization's real `webhook_secret` in a multi-org Shipit instance — that is a privileged-but-scoped credential (comparable to owning a GitHub App/webhook config for one org), not a Shipit session/API token/GITHUB_TOKEN. This matches the report's "medium likelihood" bar for the referenced arbitrage bug: exploitable only by someone who already holds a real, narrowly-scoped credential, but that credential grants far broader effect than intended because of the missing binding check.

### Recommendation
In `Handler#stacks` (and any handler resolving a `Repository`/`Stack` from the payload), enforce that the repository's owner matches the organization that was used to verify the webhook signature. Concretely, thread the verified `repository_owner`/organization through to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization: repository_owner) }`, and have `Repository.from_github_repo_name` (or the handler) reject/raise when `repo_owner.downcase != verified_organization.downcase`.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with its own `webhook_secret` (`secrets.github.orga.webhook_secret`, `secrets.github.orgb.webhook_secret`), and a `Stack` whose `Repository` has `owner: "orgb"`.
2. As someone who knows `orga`'s `webhook_secret` (e.g. has admin access to the GitHub App/webhook config for OrgA only), craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<sha>",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/some-repo" }
}
```
3. Compute `X-Hub-Signature` using OrgA's `webhook_secret` over the raw JSON body.
4. POST to the webhooks endpoint with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "orga")` and succeeds.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("orgb/some-repo")` and schedules `stack.sync_github` for OrgB's stack — an action outside OrgA's authenticated scope, confirmed via `assert_enqueued_with(job: GithubSyncJob, ...)` as demonstrated in the existing test suite pattern. **File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
