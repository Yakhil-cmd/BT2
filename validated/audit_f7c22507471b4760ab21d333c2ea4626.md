### Title
Missing worktree validity/existence check before symlink publish enables persistent-sync-denial / partial-content publish - (File: `main.go`)

### Summary
The report's core theme — a "destination" being used without first checking it actually exists / is valid before treating an operation on it as successful — has a direct functional analog in `git-sync`'s publish path. `publishSymlink` flips the public `--link` to point at a freshly-created worktree without ever calling the existence/validity check (`sanityCheckWorktree`) that the codebase itself defines and uses elsewhere for the *current* worktree.

### Finding Description
`repoSync.SyncRepo` only calls `sanityCheckWorktree` (which verifies the worktree directory is non-empty, has `HEAD` matching the intended hash, and passes `git fsck`) on the **existing** worktree when the hash hasn't changed: [1](#0-0) 

When a new hash is detected, the flow is `createWorktree` → `configureWorktree` → `publishSymlink`, with no call to `sanityCheckWorktree` on the *new* worktree before it is published: [2](#0-1) 

`createWorktree` explicitly defers checkout (`--no-checkout`), and the actual population of files happens later in `configureWorktree` via `git reset --hard`: [3](#0-2) [4](#0-3) 

`publishSymlink` itself performs no `os.Stat`/`sanityCheckWorktree` on `worktree.Path()` before atomically symlinking `--link` to it — it just trusts that the caller produced a valid worktree: [5](#0-4) 

This mirrors the report's root cause exactly: a "call" (here, publishing the symlink that consumers treat as the atomic, validated contract) succeeds without verifying that its "destination" (the worktree directory) truly contains the expected code/content, because the only existence/sanity check function that exists in the codebase (`sanityCheckWorktree`) is invoked for the old path but skipped for the new one.

### Impact Explanation
If `configureWorktree`'s `git reset --hard` or submodule step is interrupted (process kill/OOM/node reboot mid-sync — a realistic condition for a Kubernetes sidecar) or if filesystem state under `--root` is otherwise inconsistent (e.g., a concurrent/parallel writer, or a crashed prior run leaving a partially populated `.worktrees/<hash>` directory), `configureWorktree` can still return `nil` for parts of the sequence while the directory is not verified to be complete before `publishSymlink` flips `--link` to it. Consumers (per the README's stated "contract") treat the symlink target as reliable/complete/atomic. Publishing an unverified worktree can result in consumers reading a partial or stale checkout (violates the atomic-publish contract — "publishing wrong or partial content"), and because the same unchecked pattern applies across the sync loop, repeated failures of this kind can also produce persistent sync denial if downstream steps (submodule update, sparse-checkout config) fail non-fatally in edge cases while `changed` still causes a publish attempt.

### Likelihood Explanation
This requires no attacker-controlled remote content beyond ordinary operational conditions already anticipated by the project itself (crash-consistency comments exist throughout `createWorktree`/`initRepo`, e.g. "Avoid wedge cases where the worktree was created but this function error'd without cleaning up"). The missing check is a straightforward omission relative to the codebase's own established pattern (`sanityCheckWorktree` exists and is used for the old worktree), making the analog concrete and reachable via the normal, unprivileged sync loop rather than any privileged operator/node action.

### Recommendation
- Short term: Call `sanityCheckWorktree(ctx, newWorktree)` after `configureWorktree` succeeds and before `publishSymlink` is invoked; abort/retry the sync (without publishing) if it fails, mirroring the existing check used for the current worktree.
- Long term: Treat "worktree is fully and correctly checked out" as an explicit invariant enforced immediately before every symlink publish, not just opportunistically for pre-existing worktrees, consistent with the project's own atomic-publish contract described in `README.md`.

### Proof of Concept
Not independently reproducible from static analysis alone with full certainty — this requires inducing an interruption between `createWorktree` and the completion of `configureWorktree` (e.g., killing the container mid `git reset --hard` on a large repo, or simulating a submodule-update failure path) and then observing whether `publishSymlink` at `main.go:1960` still executes on the same sync pass with an incomplete worktree. Given the code path shown, no explicit guard prevents this sequence: `configureWorktree` returning `nil` is the sole gate before `publishSymlink` is called at `main.go:1955-1963`, and no `sanityCheckWorktree` call exists for the newly created worktree anywhere in `SyncRepo`.

// publishSymlink atomically sets link to point at the specified target.  If the
// link existed, this returns the previous target.
func (git *repoSync) publishSymlink(worktree worktree) error {
	targetPath := worktree.Path()
	linkDir, linkFile := git.link.Split()

	// Make sure the link directory exists.
	if err := os.MkdirAll(linkDir.String(), defaultDirMode); err != nil {
		return fmt.Errorf("error making symlink dir: %w", err)
	}

	// linkDir is absolute, so we need to change it to a relative path.  This is
	// so it can be volume-mounted at another path and the symlink still works.
	targetRelative, err := filepath.Rel(linkDir.String(), targetPath.String())
	if err != nil {
		return fmt.Errorf("error converting to relative path: %w", err)
	}

	const tmplink = "tmp-link"
	git.log.V(2).Info("creating tmp symlink", "dir", linkDir, "link", tmplink, "target", targetRelative)
	if err := os.Symlink(targetRelative, filepath.Join(linkDir.String(), tmplink)); err != nil {
		return fmt.Errorf("error creating symlink: %w", err)
	}

	git.log.V(2).Info("renaming symlink", "root", linkDir, "oldName", tmplink, "newName", linkFile)
	if err := os.Rename(filepath.Join(linkDir.String(), tmplink), git.link.String()); err != nil {
		return fmt.Errorf("error replacing symlink: %w", err)
	}

	return nil
}

// createWorktree creates a new worktree and checks out the given hash.  This
// returns the path to the new worktree.
func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}
