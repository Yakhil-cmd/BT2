This confirms the multi-organization setup: `Shipit.github(organization:)` looks up per-organization config (with distinct `webhook_secret`) via `github_app_config`, keyed by `secrets.github` entries (e.g., different GitHub orgs each with their own `app_id`, `webhook_secret`, etc.), as shown in [1](#0-0) .

### Title
Webhook signature verified against `repository.owner.login`'s org secret while the event is processed against an unrelated `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment, each GitHub organization has its own webhook secret. `WebhooksController#verify_signature` selects *which* secret to verify the HMAC against using `repository_owner`, a value taken from the untrusted JSON payload (`repository.owner.login`, or `organization.login` as fallback). Once the signature check passes, `WebhooksController#create` hands the *entire* parsed payload to the registered handlers, which independently derive the repository to act on from `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties the organization whose secret validated the signature to the organization implied by `full_name`.

### Finding Description
`verify_signature` is:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per configured GitHub organization via `github_app_config` [1](#0-0) .

Handlers, however, resolve the repository to operate on independently:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler#process` then updates stacks belonging to whatever repository `full_name` names, e.g. `stack.sync_github(expected_head_sha: params.after)` [4](#0-3) .

The equality that should hold but is not enforced:
`organization authenticated (repository.owner.login used to pick the HMAC secret)` == `organization implied by repository.full_name that is actually written/acted upon`.

Because both `repository.owner.login` and `repository.full_name` are attacker-supplied fields inside the same signed payload, an attacker who is an administrator of *any* one GitHub organization onboarded to this multi-tenant Shipit instance (and therefore knows/controls that organization's `webhook_secret`, e.g. by configuring their own GitHub App/webhook against the shared Shipit instance) can:
1. Set `repository.owner.login` = their own organization (so `Shipit.github(organization: repository_owner)` selects their own known secret).
2. Compute a valid HMAC-SHA1 signature of the full raw body using their own secret.
3. Set `repository.full_name` = a *different* organization's repository/stack tracked by the same Shipit instance.

`verify_signature` only checks that the signature matches under their own org's secret — it never checks that `repository.owner.login` matches `repository.full_name`'s owner. The request passes signature verification and is then dispatched to handlers that act on the victim organization's stack.

### Impact Explanation
This lets an administrator of one onboarded organization forge webhook events (`push`, `pull_request`, `status`, `check_suite`, `membership`, etc.) targeting stacks/repositories owned by a *different* onboarded organization, despite never possessing that organization's webhook secret. Concretely via `PushHandler`, an attacker can trigger `Stack#sync_github` with an attacker-chosen `expected_head_sha` against a victim stack; other handlers can add/modify commit statuses, capture PR labels, archive/unarchive review stacks, or provision teams/members for the victim's stacks — all without ever crossing the victim's own signature secret. This constitutes an authorization bypass across organizations reachable purely by a party who legitimately controls one tenant's secret, matching the "unauthorized deploy/write" class of impact defined for this engine (cross-tenant writes into stacks the attacker has no legitimate claim to).

### Likelihood Explanation
Requires the deployment to be configured with more than one GitHub organization in `secrets.github` (the intended, documented multi-tenant configuration schema per `github_app_config`/`TOP_LEVEL_GH_KEYS`), and requires the attacker to be a legitimate admin/webhook-secret-holder of at least one of the onboarded organizations — a party who is not privileged to affect other organizations' repositories. No GitHub App private key, Shipit session, or `ApiClient` token is needed; only crafting an HTTP POST with a matching HMAC computed from a secret they already legitimately hold.

### Recommendation
After computing `repository_owner` and verifying the signature, also verify that `repository.full_name`'s owner segment matches `repository_owner` (or, more robustly, verify the signature using the secret associated with the actual repository owner derived from `full_name`, and reject payloads where the two disagree) before dispatching to `Shipit::Webhooks.for_event(event)` handlers.

### Proof of Concept
1. Multi-org Shipit instance configured with orgs `attacker-org` (secret `S1`) and `victim-org` (secret `S2`), both with stacks tracked by Shipit.
2. Attacker crafts payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S1, raw_body)` using their own known secret `S1`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, verifies HMAC with `S1` — passes.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen sha>")` on victim's stack, despite the attacker never possessing `S2`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
