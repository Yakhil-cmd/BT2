### Title
Webhook signature verification keys on `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App / webhook secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), while every webhook handler determines which `Repository`/`Stack` to mutate using the separate `repository.full_name` field from the same JSON body. These two fields are never checked for consistency, so the "organization that authenticated" and the "repository that is written" are not the same equality the code implicitly assumes.

### Finding Description
`verify_signature` computes `repository_owner` and uses it purely to pick the `GitHubApp` config/secret to verify the raw body against: [1](#0-0) [2](#0-1) 

Once the signature is accepted, the controller hands the *entire raw payload* to the registered handlers unfiltered: [3](#0-2) 

Every handler, however, resolves the target `Repository`/`Stack` via `repository.full_name`, a field that is never cross-checked against `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

Shipit explicitly supports hosting multiple, independent GitHub organizations from a single deployment, each with its own `webhook_secret`, as documented for the `github` secrets-key layout: [8](#0-7) 

Because the HMAC-key selection binds only to `repository.owner.login` / `organization.login`, and the mutation logic binds only to `repository.full_name`, an operator who legitimately controls the webhook secret for **their own** organization (Org A, onboarded into this shared Shipit instance) can craft a signed payload whose `repository.owner.login` is `"OrgA"` (so the correct secret is selected and the signature check passes) while `repository.full_name` is set to `"OrgB/some-repo"` — a completely different, unrelated tenant's repository hosted on the same Shipit instance. The `equality binding` the code assumes — `organization that authenticated == repository that is written` — is broken.

### Impact Explanation
With a forged `repository.full_name` pointing at another organization's repository, an attacker can drive any webhook-triggered write path for a `Stack`/`Repository` they do not own:
- `PushHandler` calls `stack.sync_github(expected_head_sha:)` on victim stacks.
- `pull_request` handlers (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, etc.) can create, archive, or unarchive review stacks belonging to another org's repository.
- `StatusHandler`/`CheckSuiteHandler` (not fully inspected in this pass) can inject forged CI statuses/check-suite results against another tenant's commits, which the deploy pipeline uses to decide whether a commit is `deployable?` for gating deploys.

Falsifying CI status on someone else's repository to make an otherwise-failing commit appear green, and then having that commit auto-deployed via continuous delivery, escalates into an unauthorized deploy — this satisfies the "Critical" bar for "unauthorized deploy" in a multi-org Shipit deployment.

### Likelihood Explanation
This is exploitable by anyone who has legitimate admin control of the webhook configuration for *any* organization onboarded to the shared Shipit instance (a normal, non-privileged position relative to Shipit itself, and explicitly documented as a supported multi-org configuration). No Shipit session, `ApiClient` token, or leaked/privileged secret of the target org is required — only the attacker's own org's already-known webhook secret, which they legitimately possess by design.

### Recommendation
In `Shipit::WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler#repository_name`), enforce that the owner segment of `repository.full_name` matches `repository.owner.login` / `organization.login` used to select the signing secret, and reject the request (422) on mismatch. Alternatively, resolve the target `Repository` only within the scope of the authenticated organization, never trusting `full_name` alone across organization boundaries.

### Proof of Concept
1. Deploy Shipit configured with two organizations sharing one instance, as documented (`OrgA`, `OrgB`), each with its own `webhook_secret`.
2. As the (legitimate) admin of `OrgA`'s GitHub App/webhook, craft a `push` payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha-that-exists-in-OrgB-repo>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Sign the raw body with `OrgA`'s `webhook_secret` and send it to `POST /webhooks` with `X-Github-Event: push` and the resulting `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and verifies successfully.
5. `PushHandler#process` (via `Handler#repository_name` / `Repository.from_github_repo_name("OrgB/victim-repo")`) locates and mutates `OrgB`'s stack, even though `OrgA` never authenticated for `OrgB`.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
