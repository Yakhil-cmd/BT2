### Title
Unchecked `burn()` Return in `BridgeTransferERC20._requestERC20Transfer` Allows Silent Burn Failure Leading to Double-Spend of Bridged Assets — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

In `modeMintBurn` mode, `BridgeTransferERC20._requestERC20Transfer()` calls `ERC20Burnable(_tokenAddress).burn(_value)` without checking whether the burn actually succeeded. If a registered token implements `burn()` to return `false` instead of reverting on failure, the bridge silently skips the burn, emits `RequestValueTransfer`, and increments `requestNonce`. The counterpart bridge operators then mint the equivalent tokens on the destination chain, resulting in tokens existing on both chains simultaneously — an unauthorized inflation of bridged assets.

---

### Finding Description

`_requestERC20Transfer` in `BridgeTransferERC20.sol` handles the source-chain side of a cross-chain ERC20 transfer in `modeMintBurn` mode. The expected invariant is: tokens are burned on the source chain, then minted on the destination chain. The burn call is:

```solidity
if (modeMintBurn) {
    ERC20Burnable(_tokenAddress).burn(_value);
}

emit RequestValueTransfer(
    TokenType.ERC20,
    _from,
    _to,
    _tokenAddress,
    _value,
    requestNonce,
    fee,
    _extraData
);
requestNonce++;
``` [1](#0-0) 

The bridge casts `_tokenAddress` to `ERC20Burnable`, whose OZ v2 `burn()` is declared `void` and reverts on failure: [2](#0-1) 

However, the bridge only requires that the token is registered — it does not enforce that the token's `burn()` strictly matches the OZ implementation. A token that implements `burn(uint256) returns (bool)` and returns `false` on failure (e.g., due to a blocklist, pause, or custom access control) will not cause the bridge call to revert. In Solidity 0.5.x, when the callee returns extra data that the caller's ABI does not expect, the extra return data is silently discarded. The bridge proceeds to emit `RequestValueTransfer` and increment `requestNonce` as if the burn succeeded.

Contrast this with `handleERC20Transfer`, which correctly guards the mint path:

```solidity
require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
``` [3](#0-2) 

The same unchecked pattern exists in `BridgeTransferERC721._requestERC721Transfer`:

```solidity
if (modeMintBurn) {
    ERC721Burnable(_tokenAddress).burn(_tokenId);
}
emit RequestValueTransferEncoded(...);
requestNonce++;
``` [4](#0-3) 

---

### Impact Explanation

**Unauthorized minting of bridged assets / double-spend.**

Attack flow (ERC20, `modeMintBurn = true`):

1. A token with a non-reverting `burn()` that returns `false` is registered on the bridge.
2. User calls `requestERC20Transfer(tokenAddress, to, value, feeLimit, extraData)`.
3. `safeTransferFrom` moves `value + feeLimit` tokens from the user to the bridge — tokens are now in the bridge.
4. `_requestERC20Transfer` calls `ERC20Burnable(tokenAddress).burn(value)` — the token returns `false` silently; tokens remain in the bridge.
5. `RequestValueTransfer` is emitted and `requestNonce` is incremented.
6. Bridge operators on the counterpart chain observe the event and call `handleERC20Transfer`, which mints `value` tokens to the recipient on the destination chain.

Result: `value` tokens exist in the source-chain bridge contract AND `value` newly minted tokens exist on the destination chain. The total supply of the bridged asset is inflated by `value`. The tokens stranded in the bridge can be recovered by the attacker via a subsequent legitimate withdrawal or by exploiting any bridge liquidity mechanism.

The same inflation attack applies to ERC721 tokens via `BridgeTransferERC721._requestERC721Transfer`.

---

### Likelihood Explanation

- The token must be registered by the bridge owner (`onlyRegisteredToken` modifier), which is a semi-privileged precondition. However, bridge operators routinely register third-party tokens, and the interface contract only specifies that the token must implement `ERC20Burnable` — it does not mandate that `burn()` reverts on failure.
- Tokens with blocklists, pausable burn, or custom access control that return `false` instead of reverting are a realistic class of ERC20 implementations.
- The 1-step path (`onERC20Received`) is callable by any token that has already been transferred to the bridge, lowering the barrier further.
- The `handleERC20Transfer` path already demonstrates the correct pattern (`require(mint(...))`), confirming the asymmetry is an oversight rather than intentional design.

---

### Recommendation

Add a return-value check for the `burn()` call in both `_requestERC20Transfer` and `_requestERC721Transfer`. Since the OZ v2 `ERC20Burnable.burn()` is declared `void`, the safest approach is to use a low-level call and verify success, or to define a custom interface that returns `bool`:

**ERC20 fix:**
```solidity
if (modeMintBurn) {
    (bool ok,) = _tokenAddress.call(
        abi.encodeWithSignature("burn(uint256)", _value)
    );
    require(ok, "_requestERC20Transfer: burn failed");
}
```

**ERC721 fix:**
```solidity
if (modeMintBurn) {
    (bool ok,) = _tokenAddress.call(
        abi.encodeWithSignature("burn(uint256)", _tokenId)
    );
    require(ok, "_requestERC721Transfer: burn failed");
}
```

Alternatively, define a `IBurnable` interface with `burn(...) returns (bool)` and use `require(IBurnable(_tokenAddress).burn(_value))`.

### Proof of Concept

Deploy a mock ERC20 token that returns `false` from `burn()` instead of reverting:

```solidity
pragma solidity 0.5.6;

import "openzeppelin-contracts-v2/contracts/token/ERC20/ERC20.sol";

contract ERC20BurnNotReverting is ERC20 {
    // burn returns false instead of reverting when caller is not authorized
    function burn(uint256 amount) public returns (bool) {
        if (msg.sender != address(0xDEAD)) {
            return false; // silently fail
        }
        _burn(msg.sender, amount);
        return true;
    }
}
```

Test:
1. Deploy `ERC20BurnNotReverting` and register it on the bridge with `modeMintBurn = true`.
2. Mint 100 tokens to Alice.
3. Alice approves the bridge and calls `requestERC20Transfer(tokenAddr, Bob, 100, 0, "")`.
4. `safeTransferFrom` moves 100 tokens to the bridge.
5. `burn(100)` returns `false` — tokens remain in the bridge.
6. `RequestValueTransfer` event is emitted.
7. Bridge operators call `handleERC20Transfer` on the counterpart chain, minting 100 tokens to Bob.
8. Assert: bridge holds 100 tokens on source chain AND Bob holds 100 minted tokens on destination chain — total supply inflated by 100. [5](#0-4) [6](#0-5)
