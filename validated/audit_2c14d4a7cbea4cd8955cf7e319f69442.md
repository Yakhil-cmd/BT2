### Title
CCMenuController#stack bypasses ApiClient stack_id scoping, allowing cross-stack read via token replay - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` restricts an `ApiClient`'s visible stacks via the `stacks` scope (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), and the base `stack` method builds on that scope. `Shipit::Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, so a CCMenu token minted for stack A (with `stack_id` bound to A) can be replayed against any other `stack_id` in the URL and will resolve successfully.

### Finding Description
The intended binding is: `stack.id == current_api_client.stack_id` (when the client is stack-scoped), enforced by `BaseController#stacks`/`#stack`: [1](#0-0) 

`CCMenuUrlController#fetch` mints an `ApiClient` with `permissions: %w[read:stack]` and no `stack_id` restriction is even set on that client — it creates/reuses a single named client `"CCMenu Client"` per user: [2](#0-1) 

More critically, `CCMenuController` overrides `stack` to bypass the scope entirely: [3](#0-2) 

`require_permission :read, :stack` only checks that the string `"read:stack"` is present in `current_api_client.permissions` — it never compares against the resolved `stack` instance or `current_api_client.stack_id`: [4](#0-3) 

So even for a client that *does* have `stack_id` set, `CCMenuController#stack` resolves `params[:stack_id]` against the whole `Stack` table, ignoring `current_api_client.stack_id`. Contrast with `StacksController#stack`, which correctly uses the scoped `stacks.from_param!(params[:id])`: [5](#0-4) 

Exploit flow: attacker requests/obtains a CCMenu URL like `GET /api/stacks/A/ccmenu.xml?token=<T>` (e.g. shared by an operator for stack A). They then send `GET /api/stacks/B/ccmenu.xml?token=<T>` — `authenticate_api_client` in `CCMenuController` still authenticates via `ApiClient.authenticate(params[:token])`, and `stack` resolves stack B unconditionally via `Stack.from_param!`, returning stack B's deploy/task data with HTTP 200.

### Impact Explanation
This grants unauthorized read access to another stack's deploy status, last build label/status, and activity state (task streams / deploy state) via the CCMenu XML endpoint. It is repeatable against arbitrary stacks by simply changing the `stack_id` in the URL/query string, since the token itself carries no stack binding — the scoping is supposed to happen entirely in the controller and it doesn't. This matches the "High — unauthenticated/unauthorized read of stack state, task streams or deploy output" category (the attacker still needs *a* valid token, but that token was scoped/intended for a different, single stack).

### Likelihood Explanation
Precondition: the attacker must already possess a valid `token` for some stack (e.g., a CCMenu URL shared publicly by an operator for stack A, as the prompt states). This is a real-world pattern since CCMenu URLs are often embedded in build-status widgets or dashboards and considered "not secret" for a single stack's status. Once held, the attacker only needs to change `stack_id` in the query string — no additional secrets, sessions, or GitHub credentials required. This is low-cost and trivially repeatable.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to use the scoped `stacks` method from `BaseController` instead of `Stack.from_param!` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures the `current_api_client.stack_id` restriction (when present) is enforced, consistent with `StacksController` and other API controllers.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to stack A cannot be replayed against stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: "foo", name: "bar"), branch: 'main')

  scoped_client = ApiClient.create!(
    creator: @user, name: 'Scoped CCMenu Client',
    permissions: %w[read:stack], stack_id: stack_a.id
  )

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # Binding under test: stack.id must be ∈ Stack.where(id: current_api_client.stack_id)
  # i.e. stack_b.id != scoped_client.stack_id, so this must NOT return 200 with stack_b data.
  assert_response :not_found # or :forbidden — currently fails, returns 200 with stack_b's XML
end
```
Running this against current code demonstrates the request succeeds (200, returns stack B's `name`/`lastBuildStatus`) instead of being rejected, confirming the scope bypass caused by `CCMenuController#stack`'s direct `Stack.from_param!` call.
