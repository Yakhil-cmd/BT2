### Title
Stack-scoped API tokens bypass their stack authorization on the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via the `stack_id` column, and every API controller enforces that scope through `BaseController#stacks`/`#stack`. `Api::CCMenuController` overrides `#stack` to bypass that scoping entirely, so a token that is only supposed to authorize reading one stack's CCMenu status can be replayed to read the CCMenu status of any stack in the installation.

### Finding Description
`ApiClient` records can optionally `belongs_to :stack` [1](#0-0) , and the base API controller derives the authorized stack set from that binding:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This is the binding the rest of the API relies on: `token.stack_id == accessed_stack.id` (or the token is unscoped). It's exactly what the fixture `here_come_the_walrus` (permission `read:stack`, `stack: shipit`) and its test exercise, proving a stack-scoped token only ever sees its own stack through `Api::StacksController` [3](#0-2) [4](#0-3) .

`Api::CCMenuController`, however, re-implements both authentication and stack lookup and never consults `current_api_client.stack_id`:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [5](#0-4) 

`require_permission :read, :stack` only checks that the `permissions` array contains `read:stack` [6](#0-5) ; it never checks which stack the token is bound to. Because `#stack` here calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!`, any token carrying the `read:stack` permission — including one whose `stack_id` restricts it to a single stack — authorizes `stack_id` acted-on-by-the-request while the verified binding only ever covered `stack_id == token.stack_id`. This exactly matches the report's accounting pattern: enforcement ("this token is scoped to stack A") is asserted at issuance/other endpoints, but the actual value acted upon by this endpoint (`params[:stack_id]`) is never checked against that binding, so the same credential silently "spends" authorization it was never granted for other stacks.

### Impact Explanation
An attacker who legitimately possesses (or otherwise obtains, e.g. from a CCMenu monitoring tool config) a token scoped to Stack A can use it to read `deploy`/`lastBuildStatus`/lock state for any other stack in the same Shipit instance by simply changing `stack_id` in the URL `/api/stacks/*stack_id/ccmenu`. This is a cross-stack authorization escalation: `read:stack` bound to one repository/environment becomes `read:stack` for the entire fleet, exposing stack state (deploy status, lock reason) the token holder was never authorized to see. This matches the High-severity category "escalation into `Shipit.github_teams` authorization ... unauthenticated read of stack state, task streams or deploy output" relative to stacks outside the token's scope.

### Likelihood Explanation
Any holder of a valid, stack-scoped `read:stack` API token (the minimum, most restricted permission Shipit issues) can trigger this with a single unauthenticated GET request substituting an arbitrary `stack_id`; no privilege escalation, additional secrets, or session state is required beyond the token itself.

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so the `current_api_client.stack_id` binding is enforced identically to every other API controller.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to Stack A: `ApiClient.create!(creator: user, name: "CCMenu", stack: stack_a, permissions: ["read:stack"])`, and note its `authentication_token`.
2. Request `GET /api/stacks/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/ccmenu?token=<token>` for an unrelated Stack B.
3. Observe a `200 OK` response with Stack B's CCMenu XML (deploy status, lock state), even though the token's `stack_id` is Stack A — confirming the read succeeds outside the token's authorized stack, unlike `Api::StacksController#index`/`#show` which correctly restrict to `stacks.where(id: current_api_client.stack_id)` [7](#0-6) .
