### Title
RAY value overflow in interest accrual permanently freezes a market - (File: common/src/rates/simulate.rs)

### Summary
A market whose scaled supply or debt value exceeds `i128::MAX` can no longer complete `accrue_step`, so every operation that first synchronizes interest permanently reverts with `MathOverflow`, freezing supplier funds, borrower repayments, liquidations, flash loans, and index updates for that market. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller::update_indexes` is permissionless apart from caller authorization and forwards the selected `Vec<HubAssetKey>` to the pool. [3](#0-2) [4](#0-3) 

The pool's `accrue` operation loads each market and calls `interest::global_sync`, while every normal market leg also uses `synced_market`, which performs the same accrual before the requested mutation. [5](#0-4) [2](#0-1) 

`global_sync` chunks elapsed time and calls `accrue_step`, which first reconstructs total debt and total supply through `scaled_to_original`. [6](#0-5) [7](#0-6) 

`scaled_to_original` multiplies the stored scaled amount by the index, and `mul_div_half_up` panics with `MathOverflow` when the resulting RAY-denominated value does not fit in `i128`. [8](#0-7) [9](#0-8) 

The configured `MAX_BORROW_INDEX_RAY` ceiling does not prevent this failure because the overflow happens while reconstructing the current value, before the new index can be calculated and clamped. [10](#0-9) [11](#0-10) 

Because the panic occurs inside `accrue_chunk` before `mark_accrued`, `commit`, or the requested operation executes, Soroban rollback leaves `last_timestamp` and the market state unchanged, making every subsequent call repeat the same overflowing calculation. [6](#0-5) [5](#0-4) 

### Impact Explanation
This permanently freezes all funds and debt operations for the affected `(hub_id, asset)` book until the deployed code is changed. [12](#0-11) 

Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot reduce risk, `flash_loan` and `claim_revenue` cannot operate on the market, and even a governance-driven rate-model replacement cannot proceed because it calls `pool_update_indexes` before installing new parameters. [13](#0-12) [14](#0-13) 

The frozen state can also strand bad debt because liquidation and cleanup paths depend on the same interest-synchronized pool operations. [15](#0-14) 

### Likelihood Explanation
An unprivileged caller can trigger the final overflowing `update_indexes` call once a market's scaled debt or supply multiplied by its index approaches `i128::MAX`. [3](#0-2) [8](#0-7) 

The condition is economically expensive and ordinarily requires an extremely large book, high utilization, and substantial index growth, but it can arise from ordinary `supply` and `borrow` positions and does not require privileged calls or malformed inputs. [16](#0-15) [3](#0-2) 

A single funded attacker can create separate accounts for the market supply and collateralized borrow, maintain high utilization, and later submit `update_indexes`; alternatively, an unrelated keeper can trigger the freeze once an organically grown whale market crosses the representable-value boundary. [16](#0-15) [3](#0-2) 

### Recommendation
Use widened `I256` arithmetic for utilization inputs and other accrual intermediates, or explicitly enforce an invariant that `borrowed * borrow_index` and `supplied * supply_index` remain representable before admitting new shares or debt. [11](#0-10) [17](#0-16) 

Cap or reject operations at a market-value bound derived from the maximum reachable index rather than only limiting initial token-to-RAY scaling, and add a regression test that accrual, repayment, withdrawal, liquidation, and parameter replacement remain possible at that bound. [18](#0-17) [14](#0-13) 

### Proof of Concept
1. An attacker creates one account with `supply(caller=attacker, account_id=0, spoke_id=S, assets=[(BIG18, 1_000_000_000 * 10^18)])`, creating a large high-decimal supply position. [19](#0-18) 
2. The same attacker creates another account, supplies enough collateral to satisfy its risk limits, and calls `borrow(caller=attacker, account_id=B, borrows=[(BIG18, 980_000_000 * 10^18)], to=None)` to establish sustained high utilization. [20](#0-19) 
3. As the market accrues, the attacker periodically calls `update_indexes(caller=attacker, assets=[BIG18])` until `borrowed.mul(borrow_index)` or `supplied.mul(supply_index)` no longer fits in `i128`. [3](#0-2) [11](#0-10) 
4. The next `update_indexes`, `withdraw`, `repay`, `liquidate`, `flash_loan`, or `claim_revenue` touching `BIG18` reaches `global_sync` first, panics in `scaled_to_original`, and rolls back before updating `last_timestamp`, so the market remains frozen on every subsequent attempt. [6](#0-5) [2](#0-1)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```

```rust
/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
```

```rust
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

```rust
/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}
```
