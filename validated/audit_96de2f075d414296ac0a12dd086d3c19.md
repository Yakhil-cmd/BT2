`ValidatorInfo` is a struct describing a network validator's account, voting power, and config [1](#0-0) , constructed via `ValidatorInfo::new` only in test utilities, telemetry, discovery, and fuzzing code paths [2](#0-1) , not from any unprivileged transaction, authenticator, or API input path. In production, validator voting power reaching the quorum-checking code is materialized as `ValidatorConsensusInfo` inside `ValidatorVerifier`, which is built from the on-chain `ValidatorSet` reconfiguration output at epoch boundaries [3](#0-2)  — a result of privileged validator/staking-module operations (stake amounts, validator registration/rotation), not something an unprivileged transaction sender can directly stuff into an admission-time authenticator or proof.

The quorum computation itself (`sum_voting_power`, `check_voting_power`, `check_aggregated_voting_power`) sums voting power strictly from the validators registered in the `ValidatorVerifier`'s `validator_infos`, rejecting any unknown author entirely (`VerifyError::UnknownAuthor`) rather than trusting an attacker-supplied value out of thin air [4](#0-3) . An attacker cannot inject an arbitrary `ValidatorConsensusInfo`/voting-power entry through a transaction; that data only enters via the reconfiguration event driven by the Move staking/validator-set framework, which requires privileged validator-owner/operator transactions, not unprivileged sender authority.

Because the described exploit path requires manipulating validator-set configuration (a privileged, consensus/staking governance operation) rather than an unprivileged transaction/authenticator/API/proof input at the admission boundary (mempool → vm-validator → VM), it falls outside this review's boundary conditions ("must start from unprivileged transaction, authenticator, API, or proof input" and "reject anything that needs ... a pre-existing approval right"). No admission-boundary sender/signer/sequence/chain-id/domain binding defect was found.

    /// Sum voting power for valid accounts, exiting early for unknown authors
    pub fn sum_voting_power<'a>(
        &self,
        authors: impl Iterator<Item = &'a AccountAddress>,
    ) -> std::result::Result<u128, VerifyError> {
        let mut aggregated_voting_power = 0;
        for account_address in authors {
            match self.get_voting_power(account_address) {
                Some(voting_power) => aggregated_voting_power += voting_power as u128,
                None => return Err(VerifyError::UnknownAuthor),
            }
        }
        Ok(aggregated_voting_power)
    }

    /// Ensure there is at least quorum_voting_power in the provided signatures and there
    /// are only known authors. According to the threshold verification policy,
    /// invalid public keys are not allowed.
    pub fn check_voting_power<'a>(
        &self,
        authors: impl Iterator<Item = &'a AccountAddress>,
        check_super_majority: bool,
    ) -> std::result::Result<u128, VerifyError> {
        let aggregated_voting_power = self.sum_voting_power(authors)?;
        self.check_aggregated_voting_power(aggregated_voting_power, check_super_majority)
    }

    pub fn check_aggregated_voting_power(
        &self,
        aggregated_voting_power: u128,
        check_super_majority: bool,
    ) -> std::result::Result<u128, VerifyError> {
        let target = if check_super_majority {
            self.quorum_voting_power
        } else {
            self.total_voting_power - self.quorum_voting_power + 1
        };

        if aggregated_voting_power < target {
            return Err(VerifyError::TooLittleVotingPower {
                voting_power: aggregated_voting_power,
                expected_voting_power: target,
            });
        }
        Ok(aggregated_voting_power)
    }
