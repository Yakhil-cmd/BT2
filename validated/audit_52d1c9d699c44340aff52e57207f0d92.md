## Title
Unbounded synchronous scan of `storage.assocUnstableMessages` in `data_feed`/`in_data_feed` oscript ops can freeze AA trigger processing - (File: `data_feeds.js`, `formula/evaluation.js`)

### Summary
The Chainlink-Keeper report describes a bug class where a formula's *declared* gas cost does not reflect its *actual* execution cost, which instead scales with an external, attacker/usage-inflatable collection (number of connected vaults). In ocore, the analog is the `data_feed` and `in_data_feed` oscript operations used inside Autonomous Agent (AA) formulas: their *static* cost is a fixed `complexity`/`count_ops` increment charged by the validator, but their *actual* execution cost scales linearly with the number of currently-unstable AA-response units cached in memory (`storage.assocUnstableMessages`) — a quantity that is not bounded by, or reflected in, `constants.MAX_COMPLEXITY`/`MAX_OPS`, and that any unprivileged user can inflate simply by posting many AA-triggering units.

### Finding Description
When an AA formula uses `data_feed` or `in_data_feed`, evaluation calls into `dataFeeds.readDataFeedValue()` / `dataFeeds.dataFeedExists()` with `unstable_opts = bAA` (true whenever evaluated inside an AA context): [1](#0-0) [2](#0-1) 

Inside `dataFeedExists`, when `bAA` is true, the code performs a fully synchronous, in-memory scan over **every entry** of `storage.assocUnstableMessages` (i.e., every currently-unconfirmed unit's messages), filtering only by `objUnit.bAA` and address/mci range, before falling back to the on-disk KV scan: [3](#0-2) 

The equivalent unstable-inclusion branch in `readDataFeedValue` does the same full iteration over `storage.assocUnstableMessages`: [4](#0-3) 

Meanwhile, the *static* validator charges only a fixed cost for this op regardless of how large `storage.assocUnstableMessages` is at execution time: [5](#0-4) 
The `MAX_COMPLEXITY`/`MAX_OPS` bounds enforced during AA validation govern only the *shape* of the formula, not the size of the in-memory unstable-unit set that `data_feed`/`in_data_feed` traverses at run time: [6](#0-5) 

This is architecturally identical to the reported bug: a formula/upkeep whose declared cost estimate does not capture an externally-growable collection that the actual execution must fully traverse. Here the "vaults" are replaced by unstable AA-response units cached in `storage.assocUnstableMessages`, which any address can inflate by posting units that trigger AAs (each AA response unit stays "unstable" and in this cache until it reaches main-chain stability, which requires multiple witness levels of confirmation, i.e., time and further unit posting).

AA-trigger processing itself runs fully serially with a mutex lock and inside a DB transaction: [7](#0-6) [8](#0-7) 

Because Node.js is single-threaded, the synchronous `for (var unit in storage.assocUnstableMessages)` loop blocks the entire event loop for its duration — not just the specific trigger's transaction — while it runs.

### Impact Explanation
If an attacker inflates `storage.assocUnstableMessages` with a large number of unstable AA-response units (by rapidly posting many AA-triggering units faster than the DAG can stabilize them), then any subsequent AA trigger (their own or an unrelated victim AA) that evaluates `data_feed`/`in_data_feed` will force every full node to synchronously scan the entire unstable-message set in-process. Because this blocks Node's single event loop, it can stall unit validation, network message handling, and AA trigger processing across the whole node for the duration of the scan, directly risking delayed/failed confirmation of new units — the exact "network unable to confirm new units" outcome that this analog class of bug targets, reachable purely by an unprivileged unit/trigger poster and by anyone authoring an AA that calls `data_feed`/`in_data_feed`.

### Likelihood Explanation
Any user can post AA-triggering units and any AA author can include `data_feed`/`in_data_feed` in a formula (a very common, documented oscript primitive for oracle-based logic), so the reachable surface is broad and requires no special privilege — only volume of ordinary unit posting.

### Recommendation
Cap the number of unstable AA-response units scanned by `dataFeedExists`/`readDataFeedValue` (e.g., via an index keyed by `(address, feed_name)` instead of a full `for...in` over `assocUnstableMessages`), or charge `data_feed`/`in_data_feed` complexity proportionally to the current size of `storage.assocUnstableMessages` at evaluation time so that this externally-growable cost is reflected in `MAX_COMPLEXITY`/`MAX_OPS` enforcement, analogous to keeping keeper-callable state updates within a hard, pre-declared bound.

### Proof of Concept
1. Deploy/target an AA whose formula uses `data_feed(['ORACLE_ADDR'], 'x')` or `in_data_feed([...])` (a standard, common pattern).
2. From many addresses, post a large number of units that each trigger some AA (any AA, even trivial ones) so that their AA-response units accumulate in `storage.assocUnstableMessages` faster than the MC stabilizes them (`objUnit.bAA === true` entries).
3. Trigger the target AA that calls `data_feed`/`in_data_feed`; observe that `dataFeedExists`/`readDataFeedValue` (`data_feeds.js:34-94`, `205-241`) performs a full synchronous `for...in` scan over the inflated `storage.assocUnstableMessages`, blocking the node's event loop for the scan duration during AA-trigger processing that already holds the `aa_triggers` mutex and an open DB transaction.

					if (valueIsNumber()) {
						if (value.toString() !== feed_value.toString())
							bFound = true;
					}
					else {
						if (value !== feed_value)
							bFound = true;
					}
					return;
				}
				if (typeof value === 'number' && typeof feed_value === 'number') {
					if (relationSatisfied(feed_value, value))
						bFound = true;
					return;
				}
				var f_value = (typeof value === 'string') ? string_utils.toNumber(value, bLimitedPrecision) : value;
				var f_feed_value = (typeof feed_value === 'string') ? string_utils.toNumber(feed_value, bLimitedPrecision) : feed_value;
				if (f_value === null && f_feed_value === null) { // both are strings that don't look like numbers
					if (relationSatisfied(feed_value, value))
						bFound = true;
					return;
				}
				if (f_value !== null && f_feed_value !== null) { // both are either numbers or strings that look like numbers
					if (relationSatisfied(f_feed_value, f_value))
						bFound = true;
					return;
				}
				if (typeof value === 'string' && typeof feed_value === 'string') { // only one string looks like a number
					if (relationSatisfied(feed_value, value))
						bFound = true;
					return;
				}
				// else they are incomparable e.g. 'abc' > 123
			});
			if (bFound)
				break;
		}
		if (bFound)
			return handleResult(true);
