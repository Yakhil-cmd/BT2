### Title
Unbounded per-request event-listener leak in `handlePrivatePaymentChains` allows memory-exhaustion DoS - (File: wallet.js)

### Summary
CVE-2018-6554 is a kernel memory leak where an unprivileged caller can repeatedly invoke `irda_bind()` and never trigger the cleanup path, permanently growing kernel memory. The analog in ocore is `handlePrivatePaymentChains` in `wallet.js`, which registers a one-shot `eventBus` listener per submitted private-payment chain keyed by a hash of caller-supplied content, and only removes that listener if the chain is fully validated or explicitly fails. A private-payment counterparty (any paired device) can submit crafted chains whose completion event never fires, leaving the listener (and its closure state) permanently resident, growing without bound as more distinct chains are sent.

### Finding Description
`handlePrivatePaymentChains` computes, for every element of every submitted private-payment chain, a listener key derived from attacker-controlled content: [1](#0-0) 

For each key it calls `network.handleOnlinePrivatePayment`, and in the `ifQueued` branch (used whenever the payment cannot be validated immediately, e.g. because a referenced parent unit or private element is not yet known) it registers a **one-shot** `eventBus.once(key, ...)` listener that is only invoked once the corresponding unit/payload is later confirmed elsewhere in the codebase: [2](#0-1) 

There is a cleanup path (`cancelAllKeys`, using `eventBus.removeAllListeners(key)`), but it is only invoked from the `async.eachSeries` final callback when an earlier chain in the *same batch* fails validation: [3](#0-2) [4](#0-3) 

Because the listener `key` is derived from a hash of the caller-supplied `payload` (`objHeadPrivateElement.unit`, `json_payload_hash`, `output_index`), an attacker can trivially generate an unlimited number of distinct keys by varying payload contents slightly, each producing a *new* `eventBus.once(key, …)` registration. If the referenced dependency (the "missing" unit/private element that would normally trigger the corresponding `emit(key, …)` elsewhere in `network.js`) is never supplied by the attacker, the listener is **never invoked and never removed** — it remains registered on the shared, global `eventBus` singleton for the lifetime of the process. This mirrors the CVE-2018-6554 pattern: a locally-reachable, low-privilege operation (`bind`/here, "post an incomplete private payment chain") that allocates persistent kernel/process-wide state without a guaranteed release path, letting the caller drive unbounded memory growth purely through repetition.

Note: the top-level per-batch de-duplication cache `handledChainsCache` (`wallet.js:948`) only stores an entry *after* full successful validation of a batch, so it provides no protection against an attacker who never lets a batch fully validate — the exact scenario that produces orphaned listeners.

### Impact Explanation
Each orphaned `eventBus.once` registration retains references to its closure (`arrChains`, `assocValidatedByKey`, `from_address`, `body`, etc. captured indirectly through the outer scope), so memory consumption per leaked chain is non-trivial (proportional to submitted chain size, which can include payment payloads with inputs/outputs). Since `eventBus` is a process-wide singleton shared by all subsystems (`event_bus.js`), continual growth of registered listeners degrades and eventually exhausts process memory, causing the node (particularly light wallets/hub-facing wallet processes that handle `private_payment_chains` messages from paired devices) to crash or become unresponsive — a denial of service, consistent with the "Medium" severity and "local availability impact" class of the reference CVE.

### Likelihood Explanation
The trigger requires only that an already-paired device (a normal, low-privileged private-payment counterparty in the wallet's device-messaging trust model) send `private_payment_chains` messages whose chains reference dependencies that are deliberately never completed (e.g., referencing a fabricated or withheld ancestor unit). No special privileges, race conditions, or existing malicious infrastructure are required beyond the ability to exchange private-payment messages with the victim wallet, which is a normal part of asset/private-payment protocol usage. The attack can be repeated indefinitely and cheaply (each request costs only hashing/lightweight validation before entering the `ifQueued` branch).

### Recommendation
- Track all pending listener keys with an expiry timestamp (similar to `PRUNED_JOINT_CACHE_TTL_ms` in `archiving.js`) and periodically purge/`removeAllListeners` for keys whose corresponding chain never resolved within a bounded time window.
- Bound the total number of concurrently pending `assocValidatedByKey`/`eventBus.once` registrations per peer/device, rejecting or queuing further chains once the limit is reached.
- Ensure `cancelAllKeys()` (or an equivalent per-key cleanup) runs on a timeout even when no other chain in the batch fails, so a single incomplete chain cannot pin its listener forever.

### Proof of Concept
1. As a paired device (private-payment counterparty), repeatedly send `private_payment_chains` messages via the normal device-messaging protocol, each containing a single-element chain (`arrChains`) whose `payload` is syntactically valid (passes the `isNonemptyObject`/`isNonemptyArray` checks) but references a fabricated parent `unit` and unique random `inputs`/`outputs` so that each request computes a distinct `cache_key` (hash of `arrChains`) and thus a distinct `key` for `assocValidatedByKey`.
2. Ensure the referenced parent/ancestor is never actually delivered, so `network.handleOnlinePrivatePayment`'s `ifQueued` callback fires (dependency missing) and registers `eventBus.once(key, …)` at `wallet.js:1049-1062`, but the corresponding `emit(key, …)` that would normally fire on dependency arrival never occurs.
3. Repeat step 1 with new random payloads at high frequency.
4. Observe `eventBus`'s internal listener count (`eventEmitter.listenerCount`) and process RSS grow unboundedly over time, since `handledChainsCache` (only populated on full success) does not prevent repeated allocation, and no other cleanup path removes these orphaned listeners.
