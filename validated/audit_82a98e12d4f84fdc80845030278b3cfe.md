### Title
Cross-organization webhook forgery — a webhook's *verified* organization is never bound to the repository it actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using an organization value taken **from the unverified request body itself**, but the handlers that subsequently act on the payload identify the target `Repository`/`Stack` using a *different* field (`repository.full_name`) that is never cross-checked against the organization whose secret validated the signature. In a multi-organization Shipit deployment (`Shipit.github(organization:)`, `github_app_config`), this breaks the binding "organization that authenticated == repository that is written," letting a party who legitimately holds one tenant's webhook secret forge events that mutate a different tenant's stacks.

### Finding Description
`verify_signature` computes `repository_owner` straight from the JSON body and uses it to pick the `GitHubApp`/secret to verify against: [1](#0-0) [2](#0-1) [3](#0-2) 

Multi-org support means each organization has its own `webhook_secret`, looked up by this same attacker-supplied `repository_owner`/`organization.login` value: [4](#0-3) 

Once the HMAC check passes for *that* organization's secret, `create` dispatches the whole raw payload to handlers: [5](#0-4) 

But every handler resolves the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — a separate JSON field, not the `repository.owner.login` value used to pick the verifying secret: [6](#0-5) [7](#0-6) [8](#0-7) 

`Repository.from_github_repo_name` splits `full_name` purely by string and does a DB lookup with no ownership check tying it back to the verified org: [9](#0-8) 

Nothing in `WebhooksController`, `Webhooks::Handlers::Handler`, `PushHandler`, or `StatusHandler` asserts `repository.owner.login == repository.full_name.split('/').first`. Because HMAC-SHA1 is computed by the *sender*, whichever tenant's `webhook_secret` is used to sign a request fully determines what content is "authenticated" — but the field selecting *which secret to check against* and the field selecting *which tenant's data gets mutated* are independent, attacker-controlled JSON keys in the same unauthenticated request.

**Equality broken:** `organization authenticated by verify_signature (repository.owner.login / organization.login)` ≠ `organization whose repository/stack is written by the handler (repository.full_name)`.

### Impact Explanation
A party that legitimately controls the GitHub App / webhook secret for one organization configured in a shared, multi-org Shipit instance can sign a payload with their own valid secret while setting `repository.full_name` to `"other-org/other-repo"`. This is dispatched to handlers exactly as if it originated from the other organization:
- `PushHandler` will enqueue `GithubSyncJob` for the victim org's stack with an attacker-chosen `expected_head_sha`, causing Shipit to sync/append commits it believes came from GitHub for that repo.
- `StatusHandler` will create arbitrary commit statuses (`state`, `context`, `target_url`) for commits belonging to the victim org's repository, which can be leveraged to satisfy CI requirements gating the merge queue or deploy safety checks.
- `MembershipHandler`/`PullRequest` handlers similarly key off `repository.full_name`/`organization.login` payload fields independent of the verifying secret's organization.

This is a cross-tenant/cross-repository write achieved purely by crafting HTTP requests to the public `/webhooks` endpoint (no Shipit session, API token, or GitHub write access to the *target* repo required) — matching the Critical "cross-repository writes" / unauthorized deploy-influencing impact class.

### Likelihood Explanation
Exploitability depends entirely on the deployment running Shipit's multi-organization GitHub configuration (`secrets.github` keyed by multiple organizations, each with its own `webhook_secret`), which is a documented, supported configuration (`github_app_config`, `github_organizations`). Any tenant admin who legitimately possesses their own org's webhook secret can attempt this against any other org hosted on the same Shipit instance without needing credentials for that other org. Likelihood is moderate: it requires (a) a multi-org deployment and (b) the attacker to be an app admin for at least one of the configured orgs — but no privileged Shipit account, GitHub write access to the target repo, or session is needed.

### Recommendation
After `verify_signature` succeeds, bind the verified organization to every subsequent action: reject (or re-verify) any payload whose `repository.owner.login` / `organization.login` does not match `repository.full_name`'s owner segment, and pass the verified organization into `Webhooks::Handlers::Handler` so `stacks`/`repository` lookups are scoped to `Repository.where(owner: verified_organization)` rather than trusting the raw `full_name` string in isolation.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with a distinct `webhook_secret` (multi-org config per `lib/shipit.rb#github_app_config`).
2. As the holder of `org-b`'s webhook secret, build a `push` event payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "org-b" }, "full_name": "org-a/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1 of raw body using org-b's webhook_secret>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"org-b"`, verifies successfully using `org-b`'s secret.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("org-a/victim-repo")` and enqueues `GithubSyncJob` for `org-a`'s stack with the attacker-supplied `expected_head_sha`, despite the request never being authenticated by `org-a`'s secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
