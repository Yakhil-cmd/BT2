### Title
`in data feed` address/asset conditions check ever-existed history instead of the oracle's latest published value, so a revoked/updated attestation still authorizes spending forever - (File: definition.js, data_feeds.js)

### Summary
Address definitions and asset `issue_condition`/`transfer_condition` can gate spending on an oracle's data feed using `['in data feed', [oracles, feed_name, relation, value, min_mci]]`. Unlike the `data_feed` formula function used inside AAs (which reads only the *latest* value via `readDataFeedValue`/`ifseveral:'last'`), the authentifier-side `in data feed` condition is evaluated with `dataFeeds.dataFeedExists`, which merely checks whether the oracle *ever* posted a matching value in the queried MCI range. Once true, it stays true forever, even if the oracle later posts a contradicting/updating value meant to revoke the previous state (e.g., "kyc_status=approved" → later "kyc_status=revoked"). This is the same bug class as the referenced report: a status-changing update from a trusted party (the pause/oracle authority) is only forward-looking in appearance, while consumers of that status treat the old, now-invalid state as permanently valid.

### Finding Description
`in data feed` is a valid operator inside address definitions (spending/authorization conditions) as validated in `validateDefinition` [1](#0-0) , and it is also allowed as an asset `issue_condition`/`transfer_condition`, evaluated through the same authentifier evaluation path used for payments [2](#0-1) .

When actually authorizing a spend, `validateAuthentifiers`'s `in data feed` case calls `dataFeeds.dataFeedExists(arrAddresses, feed_name, relation, value, min_mci, objValidationState.last_ball_mci, false, cb2)` [3](#0-2) .

`dataFeedExists` (and its helper `dataFeedByAddressExists`) do not look for the most recent posted value — they scan the whole `[min_mci, max_mci]` window for **any** unit where the relation was ever satisfied, and return `true` as soon as one is found: [4](#0-3) [5](#0-4) 

This is fundamentally different from the "current state" semantics used elsewhere in the same file for reading a feed's value, e.g. `readDataFeedValue`, which explicitly sorts candidates and takes the *last* one when `ifseveral === 'last'` [6](#0-5) , and is exactly what the `data_feed` formula operator relies on inside AAs [7](#0-6) .

Because `in data feed` used as an authorization gate on address definitions or asset transfer/issue conditions uses the "existence" semantics rather than "latest value" semantics, an oracle that intends to revoke a previously-granted approval (analogous to `setPause` in the referenced report) by posting a new, contradicting data-feed value cannot actually revoke access: the old approving unit is still inside the `[min_mci, max_mci]` window and will still satisfy the `EXISTS` check, so the address/asset condition continues to evaluate to `true` indefinitely.

### Impact Explanation
Any wallet/business logic (e.g., KYC/AML gating, whitelisting, insurance eligibility, regulatory compliance conditions) built with `in data feed` as a spending authorization or asset-transfer condition can be permanently bypassed once a single qualifying value has ever been posted by the oracle — even after the oracle publishes a revocation. This defeats the entire purpose of using an oracle-controlled gate for compliance/asset-transfer restrictions, potentially enabling unauthorized transfers/spends of a restricted asset by an address that was only briefly, or is no longer, compliant. This is a Medium-severity condition-bypass/asset-transfer-restriction-bypass issue reachable by any ordinary unit poster who defines an address with such a definition, or by asset issuers using `issue_condition`/`transfer_condition`.

### Likelihood Explanation
`in data feed` is a documented, publicly usable primitive in oscript address definitions and asset conditions (demonstrated in tests as a `definition_template`, combined with `sig`, exactly for gating spending on oracle-posted attributes) [8](#0-7) . Any user/asset-issuer relying on it for revocable status checks is affected as soon as the oracle needs to change (revoke) a previously-true state — a normal, expected operational scenario (e.g., a KYC provider revoking a user's status), making this readily triggerable without any malicious peer/network behavior.

### Recommendation
Change the `in data feed` authentifier/condition semantics (or add a distinct new operator) to check the oracle's *current* (latest) value at `last_ball_mci`, using the same "last" logic as `readDataFeedValue`/`readDataFeedByAddress`, rather than an unbounded `EXISTS`-over-history query. At minimum, document clearly that `in data feed` is history-based and cannot be used for revocable conditions, and provide a "latest value" comparison primitive (e.g., extending `dataFeedExists` with an `ifseveral:'last'`-style mode, or exposing a boolean wrapper around `readDataFeedValue`) for developers who need genuinely revocable, pause-like gating in address definitions and asset conditions.

### Proof of Concept
1. Oracle address `O` posts a `data_feed` message `{"kyc": "approved"}` in unit `U1`, which stabilizes.
2. User defines address `A` (or an asset with `transfer_condition`) using:
   `['in data feed', [['O'], 'kyc', '=', 'approved']]`
   combined with `['sig', {...}]`. At this point `A` can spend/the asset can transfer because `dataFeedExists` finds `U1`.
3. Oracle `O` later posts `{"kyc": "revoked"}` in unit `U2` (intending to pause/revoke `A`'s eligibility), which stabilizes with `main_chain_index` still `<= last_ball_mci` used at spend time.
4. A subsequent unit spending from `A` (or transferring the asset) is validated: `validateAuthentifiers`/`evaluateAssetCondition` calls `dataFeedExists(['O'], 'kyc', '=', 'approved', min_mci, last_ball_mci, ...)`. Because `U1` (the old "approved" posting) is still within `[min_mci, last_ball_mci]`, the existence query returns `true` regardless of `U2`'s revocation, and the spend is authorized — demonstrating that the revocation in `U2` had no forward-blocking effect, unlike what the developer/oracle intended.
