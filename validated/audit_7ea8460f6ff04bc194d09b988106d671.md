### Title
Webhook signature scope confused with target repository scope enables cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's HMAC secret to validate a webhook against using a field taken from the *unauthenticated* JSON body, while the handlers that subsequently act on the payload use a *different* field of that same body to select the target repository/stack. Because these two fields are never cross-checked, a party who legitimately possesses the webhook secret for one organization configured on a shared Shipit instance can forge a signed request whose "authenticating" fields point at their own org while the "target" fields point at a different organization's repository, causing Shipit to act on a stack it was never authorized to touch.

### Finding Description
`verify_signature` derives the signing org from the payload itself, not from anything cryptographically bound yet: [1](#0-0) [2](#0-1) 

`repository_owner` is computed as `params.dig('repository','owner','login') || params.dig('organization','login')` and used only to pick which `github_app` (and therefore which `webhook_secret`) to validate the HMAC against via `github_app.verify_webhook_signature`.

Once the signature is accepted, `create` hands the *entire* raw JSON body to the registered handler for the event: [3](#0-2) 

Handlers, however, resolve the actual target repository/stack from a *different* field — `repository.full_name` — with no comparison back to `repository.owner.login`/`organization.login` that was used for signature verification: [4](#0-3) [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` blindly splits and looks up whatever owner/name pair is embedded in `full_name`: [7](#0-6) 

Because a legitimate GitHub-originated webhook would always have `repository.owner.login` match the owner portion of `repository.full_name`, this equality is implicitly assumed but never enforced in code. An attacker forging the request directly (not going through GitHub) can set them independently. This breaks the binding: *organization that authenticated (via `webhook_secret`/`repository_owner`) == repository actually written (via `repository.full_name`)*.

### Impact Explanation
On a multi-tenant Shipit deployment (the documented `config/secrets*.yml` pattern configures multiple independent GitHub orgs/apps, each with their own `webhook_secret`, in the same install — see `config/secrets.development.shopify.yml`), anyone holding the legitimate webhook secret for **their own** onboarded organization (e.g. because they configured their own GitHub App/webhook pointing at the shared Shipit URL, a normal, unprivileged action) can forge a `push`, `pull_request`, `status`, or `check_suite` event whose `repository.owner.login` matches their own org (satisfying `verify_signature`) but whose `repository.full_name` names a stack belonging to a completely different, unrelated organization hosted on the same instance. This lets the forger:
- Trigger `PushHandler#process` → `stack.sync_github(expected_head_sha: ...)` against another org's stack, injecting an attacker-chosen `after` SHA as the "expected head" for that stack's sync/deploy pipeline.
- Archive/unarchive another org's review stacks via the pull-request handlers.
- Post arbitrary commit statuses against another org's commits via `StatusHandler`.

This is a cross-repository / cross-organization write performed without any relationship to the target org's own credentials, matching the "cross-repository writes" / "unauthorized deploy or rollback" impact bar.

### Likelihood Explanation
Requires the attacker to control (not "steal") a `webhook_secret` for *some* organization already configured on the shared Shipit instance — a realistic scenario for any Shipit deployment onboarding multiple independent teams/orgs, since owning a webhook secret for your own org is a normal, unprivileged administrative action, not a compromise of the target's secrets. No GitHub App private key, `api_clients_secret`, or session token for the *victim* org is needed. The only barrier is direct-request forgery to the `/webhooks` endpoint with a crafted, internally-inconsistent JSON body, which is trivial once any org's secret is known.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Shipit::Webhooks::Handlers::Handler`, cross-validate that the organization/owner field used to select the signing secret (`repository.owner.login` / `organization.login`) matches the owner embedded in `repository.full_name` before dispatching to handlers; reject the request (422) on mismatch.

### Proof of Concept
1. Configure/own Organization A on a shared Shipit instance with `webhook_secret: "attacker-known-secret"`.
2. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Sign the exact raw body with `HMAC-SHA1(webhook_secret_of_OrgA, body)` and send it as `X-Hub-Signature`, `X-Github-Event: push`, to `POST /webhooks`.
4. `verify_signature` resolves `repository_owner = "OrgA"`, fetches OrgA's `github_app`, and the signature validates successfully.
5. `PushHandler#process` (via `Handler#repository_name` → `payload.dig('repository','full_name')`) resolves the stack for `OrgB/victim-repo` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on Organization B's stack despite the request only being authenticated against Organization A's secret.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
