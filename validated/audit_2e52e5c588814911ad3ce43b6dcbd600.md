### Title
Sustained high-utilization debt overflows the RAY value domain in accrual and permanently freezes the market before the borrow-index cap engages - (File: common/src/rates/scaling.rs)

### Summary
Analogous to the Envoy crash — a request path hits a numeric edge case the code does not handle and the component aborts — the pool's interest accrual panics with an untyped-arithmetic-style overflow (`MathOverflow`) when `borrowed * borrow_index` no longer fits the RAY fixed-point domain. Because every market verb calls `interest::global_sync` first, once the market reaches that state all subsequent `supply`, `withdraw`, `borrow`, `repay`, and liquidation-driven pool calls revert forever. The documented `MAX_BORROW_INDEX_RAY` ceiling never engages because the value product overflows one step earlier.

### Finding Description
`contracts/pool/src/interest.rs` runs `global_sync` at the top of every mutating entrypoint; it chunks elapsed time and calls `accrue_chunk`, which delegates to `common::rates::accrue_step` and writes the returned indexes unconditionally (`cache.set_borrow_index(step.borrow_index)`). Inside `accrue_step`/`scaled_to_original` (common/src/rates/index.rs, common/src/rates/scaling.rs), the ceiled debt value `borrowed * borrow_index` is computed with `mul_div_ceil`/`mul_ceil`, which panic with `GenericError::MathOverflow` when the product exceeds `i128` (common/src/math/fp_core.rs:164-175). The borrow index is monotone and only bounded by `MAX_BORROW_INDEX_RAY` (common/src/constants/pool.rs), but on a large-denomination market the *value* `borrowed * index` hits the `i128` ceiling while `borrow_index` is still below the cap — so the cap provides no protection and no clamping/saturation path exists.

The integration test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361) demonstrates this end-to-end: an 18-decimal market with ~1e30-token supply at 98% utilization on the steep XLM rate curve panics inside accrual after some number of `update_indexes` calls, with `borrow_index < MAX_BORROW_INDEX_RAY`, and the test confirms both `withdraw` and `repay` then revert with `MathOverflow`.

### Impact Explanation
Permanent freezing of funds for that market. Once the accrual overflows, every subsequent call re-enters `global_sync`, recomputes the same overflowing product, and aborts — suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot trigger the liquidation pool legs. Nothing in `apply_bad_debt_to_supply_index` or `recapitalize` can be reached because those paths also accrue first. This is a contract-level liveness failure directly parallel to the Envoy segfault: an unhandled edge case in a shared pre-processing step bricks the entire component.

### Likelihood Explanation
Medium-low but non-zero. Reaching the cliff requires a high-decimal market carrying very large aggregate debt (on the order of billions of whole units) sustained at high utilization on a steep rate curve for many compounding periods — an attacker with whale-scale capital can construct the position via `supply`/`borrow`, but the elapsed ledger time needed to grow the index is not attacker-accelerable, and governance caps ordinarily bound market size (caps can be lifted or set high for large-cap assets). The failure is deterministic once the domain boundary is crossed, and there is no recovery path.

### Recommendation
Enforce the index cap *before* the value multiplication can overflow: in `accrue_step`, clamp `borrow_index` to `MAX_BORROW_INDEX_RAY` (and `supply_index` symmetrically) each chunk, or compute the debt value with a saturating `mul_div_floor_saturating`-style path and short-circuit accrual when the index reaches the cap. At minimum, make `global_sync` treat "index at cap" as terminal accrual rather than recomputing an overflowing product, so exits and repayments remain possible.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`: build a market `BIG18` (18 decimals, XLM rate curve), supply `BILLION * 10^18` units, borrow 98% of it, advance ledger time in year steps calling `update_indexes` until it returns `MathOverflow` — then assert `try_withdraw_raw` and `try_repay` both fail with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`, confirming the freeze precedes the cap and is permanent.
