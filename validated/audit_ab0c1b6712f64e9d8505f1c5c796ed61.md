### Title
API-scoped ApiClient can read the CCMenu status of any stack, bypassing its `stack_id` authorization scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method to bypass the stack-scoping enforced by `Shipit::Api::BaseController`. An `ApiClient` created with `stack_id` set (meant to restrict the token to a single stack) can still be used to read build/deploy status (`CCMenu` XML) for *any* stack in the installation, breaking the binding between "the stack a token authorizes" and "the stack it actually touches" — directly analogous to the Treasury bug where a caller-supplied `initiator`/amount pair was trusted without checking it against the entity that should have been authorized.

### Finding Description
`Shipit::Api::BaseController` defines the authorization-scoping primitive: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to a stack, and `stack` resolves `params[:stack_id]` only within that restricted set — this is the mechanism that turns an `ApiClient` with a `stack_id` into a "single-stack" token (verified by the fixture `here_come_the_walrus`, which has `stack: shipit` and only `read:stack` permission, and the test asserting it only ever sees one stack in `#index`) [2](#0-1) [3](#0-2) .

However, `Api::CCMenuController` (which only checks `require_permission :read, :stack` — a permission check, not a scope check) overrides `stack` to bypass the scoped `stacks` collection entirely and resolve directly against the global `Stack` relation: [4](#0-3) 

`check_permissions!` only validates that `"read:stack"` is present in `current_api_client.permissions` — it never compares `current_api_client.stack_id` to the requested `stack_id`: [5](#0-4) 

So any token with `read:stack` permission — even one that was deliberately scoped to a single, low-sensitivity stack — can be replayed against `GET /api/stacks/:stack_id/ccmenu.xml` for a completely different `stack_id` and will successfully render that other stack's deploy/build status, name, last build status, etc. This is precisely the class of bug in the reported `calculateSetupRate()` issue: a caller-supplied identifier (`initiator` in Treasury, `stack_id` here) is acted upon without being checked against the value the caller was actually authorized for (the fee-receiver binding vs. the token's `stack_id` binding).

### Impact Explanation
This crosses the "stack a token authorizes vs. a stack it touches" trust boundary explicitly called out as in-scope. Impact is unauthenticated-scope read of stack state/deploy output for stacks the token holder was never granted access to — matching the High-severity category "unauthenticated read of stack state, task streams or deploy output" (here, "unauthenticated" in the sense of unauthorized-for-that-resource, since the credential presented is valid but scoped to a different stack). A token minted for one low-trust integration (e.g., a public CI dashboard widget for a non-sensitive stack) can be used to enumerate/observe the deploy status of sensitive/private stacks.

### Likelihood Explanation
High. Exploitation requires only possessing any valid `ApiClient` token with `read:stack` permission (these are routinely distributed for CCMenu integrations, exactly the kind of low-trust, externally-facing use case this controller exists for) and knowledge/guessing of another stack's `stack_id`/slug. No privileged access or additional secrets are needed beyond the token itself, which the CCMenu flow is explicitly designed to hand out via `CCMenuUrlController` for embedding in third-party tools.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited, scope-aware `stack` method from `BaseController` (i.e., resolve `params[:stack_id]` via `stacks.from_param!`, not `Stack.from_param!`), so a stack-scoped token can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_a` with only `read:stack` permission (as `CCMenuUrlController#client` does for any `current_user`) and obtain its `authentication_token`.
2. Send `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token_scoped_to_stack_a>` for an unrelated `stack_b`.
3. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (permission list includes `read:stack`), and `stack` resolves via `Stack.from_param!(params[:stack_id])` — returning `stack_b`'s data instead of being restricted to `stack_a`, confirmed by the absence of any scope assertion in the existing test suite for `CCMenuController` (`test/controllers/api/ccmenu_controller_test.rb`), which never exercises a client scoped to a *different* stack than the one requested.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
