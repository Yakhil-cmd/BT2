This confirms the vulnerability path: `WebhooksController#verify_signature` selects the GitHub App/secret to verify against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`), while every event `Handler` (e.g. `PushHandler`, `Handler#stacks`/`repository_name`) resolves the actual repository to act on from a **different** field in the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`.### Title
Webhook signature verification is keyed on `repository.owner.login` while every event handler acts on the independent, unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to check the `X-Hub-Signature` against using `repository_owner`, a value read directly out of the untrusted JSON body (`repository.owner.login` or `organization.login`). Every event handler, however, resolves the repository/stack to mutate using a completely different field of the same untrusted body: `repository.full_name`, via `Handler#repository_name` / `Repository.from_github_repo_name`. In a multi-organization deployment (the officially documented configuration schema in `config/secrets.development.example.yml`), these two fields are never cryptographically bound together, so an attacker can pick which organization's key checks the signature while causing a totally different organization's repository to be the one actually acted upon.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and uses it to pick the `GitHubApp` instance (and its `webhook_secret`) that verifies the raw HMAC signature: [1](#0-0) 

`GitHubApp#verify_webhook_signature` in `lib/shipit/github_app.rb` explicitly treats a missing secret as automatic success: [2](#0-1) 

Meanwhile, once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw JSON body* to handlers. Every handler resolves the repository/stack to act on via `payload.dig('repository', 'full_name')`, not `repository.owner.login`: [3](#0-2) [4](#0-3) 

`Repository.from_github_repo_name` splits `full_name` on `/` and does a case-insensitive lookup unrelated to `owner.login`: [5](#0-4) 

Shipit's documented multi-tenant configuration keys the GitHub App/secret per organization, and explicitly allows a per-organization `webhook_secret` to be left blank ("nil"): [6](#0-5) 

**Binding broken:** *the organization authenticated* (`repository.owner.login`, used only to pick the signing secret) **≠** *the repository that is written* (`repository.full_name`, used by all handlers to locate `Repository`/`Stack` records and perform DB writes/job dispatch). Because these two payload fields are read independently and never cross-checked against each other, and because a per-org secret can legitimately be absent, an attacker who knows (or guesses) that one configured organization in a multi-org install has no `webhook_secret` set can craft a single JSON body where:
- `repository.owner.login` = the org with no configured secret (or `organization.login` for `membership` events) → `verify_webhook_signature` returns `true` unconditionally, no signature needed.
- `repository.full_name` = `"other-org/other-repo"`, targeting a stack that belongs to a *different*, properly-secured organization.

The handler then acts on `other-org/other-repo` using data fully attacker-controlled (push SHAs, pull_request state/labels transitioning archive/unarchive, `status` context/state that feeds `deployable?` checks used to gate deploys, `membership` events that create/attach users and teams).

### Impact Explanation
This crosses a real trust boundary without needing any credential: an unauthenticated HTTP client can inject events attributed to a repository outside the organization whose secret was (deliberately or accidentally) bypassed. Concretely reachable, unprivileged-attacker-triggerable effects:
- `push` events invoke `stack.sync_github(expected_head_sha: ...)` for any not-archived stack matching the forged `full_name`/branch — forged head SHAs are queued for sync/deploy-eligibility state on a different org's stack.
- `status` events create fake commit statuses (`state`, `context`, `target_url`) on the target org's commits, directly influencing `Commit#deployable?`/CI-gating used before a human or continuous-delivery deploy is allowed to proceed — this is a step toward an unauthorized deploy.
- `pull_request` events (labeled/unlabeled/opened/closed/reopened) can archive/unarchive/create review stacks for the target org's repository.
- `membership` events create teams/users on the fly, affecting `Shipit.github_teams` authorization checks used by `Authentication#force_github_authentication` (`current_user.authorized?`), i.e. this can influence who is treated as authorized in the target org.

Given the report's classification of "escalation into `Shipit.github_teams` authorization" and "SSRF/unauthorized deploy" as High/Critical impacts, and that CI-status forgery is a documented lever toward an unauthorized deploy, this qualifies as High severity.

### Likelihood Explanation
Requires only that the operator use the (fully documented, supported) multi-organization `github:` config schema and leave any one organization's `webhook_secret` unset — an explicitly optional field per `docs/setup.md` ("Webhook secret (optional)") and the shipped example secrets file. No GitHub App credentials, session, or `ApiClient` token are needed; the endpoint (`/webhooks`) is intentionally public. The only "difficulty" is knowing/guessing which configured organization lacks a secret, which is discoverable by trial (a bypass attempt against `repository.owner.login = "orgX"` either succeeds or fails observably via the response headers/status and logged messages).

### Recommendation
- Bind the verified organization to the repository actually acted upon: reject/short-circuit processing if `repository.full_name`'s owner segment does not case-insensitively match the `repository_owner` value used to select the signing key (or simply always derive both from the same field, e.g. `repository.full_name`'s owner component, and require it for every handled event type).
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in a multi-organization configuration; either require a secret for every configured organization or make bypass explicit and logged as a security-relevant condition rather than transparent to downstream handlers.
- Consider making the webhook secret mandatory (non-optional) whenever more than one organization is configured, since the "optional" documentation was written for the single-org case.

### Proof of Concept
Preconditions: multi-org `github:` config with at least two orgs, e.g. `orgA` (no `webhook_secret` set) and `orgB` (has a stack for `orgB/secret-repo` and a configured `webhook_secret`).

```http
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json
# No X-Hub-Signature header needed

{
  "sha": "<target commit sha in orgB/secret-repo>",
  "state": "success",
  "context": "ci/tests",
  "target_url": "https://attacker.example/fake",
  "created_at": "2026-09-01T00:00:00Z",
  "branches": [{"name": "main"}],
  "repository": {
    "full_name": "orgB/secret-repo",
    "owner": { "login": "orgA" }
  }
}
```
- `repository_owner` resolves to `"orgA"`; `Shipit.github(organization: "orgA")` has `webhook_secret` unset, so `verify_webhook_signature` returns `true` unconditionally — request passes `verify_signature`.
- `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler`, which resolves the target commit/stack via `payload.dig('repository', 'full_name')` = `"orgB/secret-repo"`, and creates a forged commit status against `orgB`'s repository/commit, unrelated to the "orgA" identity used for the signature bypass.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
