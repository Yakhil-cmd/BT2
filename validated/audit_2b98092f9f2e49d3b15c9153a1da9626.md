### Title
Uncaught-exception fallthrough in `handleSavedPrivatePayments` causes double invocation of the async callback and continued processing of a private payment chain whose hash could not be computed - (File: network.js)

### Summary
In `handleSavedPrivatePayments` → `validateAndSave`, a `try/catch` around `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` catches failures but does not `return` from the `catch` block, so the function falls through and continues execution as if the hash succeeded, exactly analogous to the ERC-20 report's core issue of treating a failed operation as if it were successful because its outcome wasn't checked/enforced.

### Finding Description
`validateAndSave` computes `json_payload_hash` inside a `try` block. On exception, the `catch` block logs the error, optionally reports it to the peer via `sendResult`, and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — but does not `return` afterward: [2](#0-1) 
Because there is no `return`, execution continues past the `catch` block to build `key` using the now-`undefined` `json_payload_hash`, and then unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose `ifOk`/`ifError`/`ifWaitingForChain` handlers all eventually call `cb()` again: [3](#0-2) 
This means `cb` (the `async.each` iteratee callback) can be invoked twice for the same row — once from `deleteHandledPrivateChain` in the catch branch, and again from one of the `ifOk`/`ifError`/`ifWaitingForChain` branches after `validateAndSavePrivatePaymentChain` runs on data whose head element hash calculation had already failed. Calling `async.each`'s callback twice is undefined behavior in the `async` library and can cause the final completion callback (which calls `unlock()` and emits `"new_my_transactions"`) to fire prematurely or multiple times, and it processes `arrPrivateElements` through `validateAndSavePrivatePaymentChain` even though the head element's payload could not be hashed — the very code path that should have aborted.

### Impact Explanation
This is reachable by any private-payment counterparty who can cause `unhandled_private_payments.json` (attacker-supplied `payload`) to trigger a hash-computation exception (e.g., malformed/adversarial payload fields consumed by `objectHash.getBase64Hash`). The resulting double-callback/continued-processing behavior can corrupt the `mutex`-guarded processing pipeline for private payments (`["saved_private"]` lock unlocked out of turn, or the completion handler run twice), and it processes a private payment chain that was supposed to be rejected before further validation, undermining the integrity guarantee that malformed private elements are dropped before being handed to `validateAndSavePrivatePaymentChain`. Depending on downstream effects of double-unlocking the mutex and re-entrant chain handling, this can lead to inconsistent state for private (stable) outputs, which the audit scope treats as a stable-output double-spend/inconsistency class issue.

### Likelihood Explanation
Likelihood is moderate: it requires a peer to deliver a private-payment JSON via `unhandled_private_payments` whose payload triggers an exception in `objectHash.getBase64Hash` (a payload author or private-payment counterparty is in-scope per the task's reachability rules). No hub/network-level privilege is needed beyond sending a private payment/chain, which is a normal wallet interaction path.

### Recommendation
Add an explicit `return` in the `catch` block after `deleteHandledPrivateChain(...)` so the function does not fall through to compute `key` and invoke `validateAndSavePrivatePaymentChain` with corrupted state:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```

2. Deliver this as an unhandled private payment so it lands in the `unhandled_private_payments` table (via the normal private-payment relay path).
