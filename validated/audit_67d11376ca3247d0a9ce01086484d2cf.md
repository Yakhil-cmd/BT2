### Title
Asset definer can unilaterally rewrite the attestor list, permanently freezing balances of previously-attested holders - (File: validation.js / storage.js)

### Summary
The C4 report describes `Comptroller._setUniV3LpVault` letting an admin swap a mutable cross-contract reference (`uniV3LpVault`) at will, breaking downstream logic (`addNFTCollateral`, liquidation, withdrawal) that assumed the reference was stable, and permanently stranding NFTs that depended on the old reference. Ocore has a structurally identical pattern in the `spender_attested` asset feature: the asset **definer** can push an `asset_attestors` message at any time to fully replace the trusted attestor list (`validateAttestorListUpdate`, `validation.js:2829-2848`), and every subsequent spend check re-evaluates attestation status against only the *current* (latest) attestor list (`storage.readAsset`/`addAttestorsIfNecessary`, `storage.js:1911-1946`, and `filterAttestedAddresses`, `storage.js:1960-1974`). There is no requirement to preserve old attestors, migrate existing attestations, or grandfather already-attested holders.

### Finding Description
For `spender_attested` assets, holders must have an `attestation` message from an address currently listed in `asset_attestors` in order to spend. Validation of `spender_attested` assets pulls the attestor list at spend-time by finding the *latest* `asset_attestors` unit for the asset (`storage.js:1917-1946`, `addAttestorsIfNecessary`), not the list that existed when the holder was attested. The `filterAttestedAddresses` function (`storage.js:1960-1974`) checks `attestor_address IN(?)` against `objAsset.arrAttestorAddresses`, i.e., the *current* trusted attestor set. If the definer replaces the attestor list (removing an attestor whose attestation an existing holder relies on), that holder's previous `attestation` record no longer counts, and `arrAttestedAddresses.length === 0` will be returned for them going forward.

The only defender-side check enforced when publishing this list is that the message author equals `objAsset.definer_address` (`validation.js:2841-2842`, `validateAttestorListUpdate`) — no logic prevents the definer from unilaterally dropping all attestors that previously vouched for holders, or replacing them with attestors who refuse (or are unable) to re-attest those addresses.

Consequently, this exactly mirrors the C4 pattern: a single mutable pointer (`uniV3LpVault` ↔ `asset_attestors` list) that two pieces of logic (Comptroller/UniV3LpVault ↔ payment validation/attestation validation) must agree on, and changing that pointer via an ordinary admin/definer action strands assets that depended on the old state — in ocore's case, this affects `validatePayment` (`validation.js:2115-2122`) which requires `objAsset.arrAttestedAddresses.length` non-zero to allow a transfer/issue.

### Impact Explanation
Holders of a `spender_attested` asset who already hold a legitimate balance and were validly attested under the attestor list at the time of receipt can become permanently unable to move their funds if the definer later swaps the attestor list. This is a direct freezing-of-funds bug for asset holders — unauthorized by them, unilaterally triggered by the definer, with no on-chain mechanism to reverse or appeal it (the old attestor's attestation is silently invalidated). Because `assets` and `asset_attestors` participate in normal DAG unit validation reachable by any user composing a payment with such an asset, this is directly reachable by unprivileged asset holders being trapped, satisfying "AA/asset fund loss or freezing."

### Likelihood Explanation
Likelihood is limited by the fact that only the asset's own `definer_address` can push `asset_attestors` updates (`validation.js:2841-2842`), so this requires the definer to act (maliciously, carelessly, or under external pressure/compromise) after issuing tokens to attested holders. This is analogous to the C4 finding's own risk profile (Medium, since it requires an admin-controlled action), but the reachability for any spender_attested asset deployed on ocore (which is a standard, documented asset feature usable by any user issuing an asset) makes the precondition realistic and not contrived.

### Recommendation
- Preserve attestation validity for the attestor(s) who were on the list at the time attestation was recorded, e.g., validate attestation against the attestor list version in effect when the `attestation` unit was published, rather than always the latest list.
- Alternatively, disallow full replacement of the attestor list; only allow additive updates, or require a time-locked/notice period before removals take effect, giving holders a chance to re-attest under a still-recognized attestor before the change is finalized.
- At minimum, document/expose this risk clearly to asset issuers and integrators so wallets can warn holders when an asset's attestor list changes.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and publishes `asset_attestors` listing attestor `X` (`validateAssetDefinition`, `validation.js:2725-2827`; attestor rules enforced by `checkAttestorList`, `validation.js:2850-2864`).
2. Attestor `X` posts an `attestation` message for holder `H`'s address (`writer.js:205-217` persists into `attestations`).
3. `H` receives/holds asset `A` balance; `H` can spend because `filterAttestedAddresses` finds `H`'s address attested by `X`, who is in `objAsset.arrAttestorAddresses` (`storage.js:1960-1974`).
4. `D` (single author, as required by `validateAttestorListUpdate`, `validation.js:2829-2848`) publishes a new `asset_attestors` message for asset `A` replacing the attestor list with `Y` only (removing `X`). This passes validation because the only checks are: single-authored, author is definer, and the new list is well-formed (`checkAttestorList`).
5. `readAsset`'s `addAttestorsIfNecessary` (`storage.js:1911-1946`) now returns `arrAttestorAddresses = [Y]` as the latest list for asset `A`.
6. `H` attempts a payment with asset `A`. `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses` checks `attestor_address IN ([Y])` — `H`'s attestation by `X` no longer qualifies, so `arrAttestedAddresses` for `H` is empty.
7. `validatePayment` (`validation.js:2115-2122`) rejects the unit: `"none of the authors is attested"`. `H`'s balance is now unspendable unless `Y` also attests `H`, which is entirely outside `H`'s control and may never happen (analogous to the report's "NFT tokens becoming stuck"). function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
