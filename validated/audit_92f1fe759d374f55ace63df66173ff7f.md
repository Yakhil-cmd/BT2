### Title
`StatusHandler#process` writes GitHub status events to commits in any stack matching only by `sha`, ignoring the webhook's repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, with no check that the commit's `stack`/repository corresponds to the repository named in the webhook payload. Because git commit SHAs are content-addressed and identical across forks/clones of the same commit, a legitimately signed "status" webhook from an attacker-owned repository A can write a `Status` onto an identical-sha commit that actually belongs to victim stack B, flipping `Commit#deployable?` to `true` for B.

### Finding Description
The claimed binding is: `commit.stack.repository == payload.dig('repository', 'full_name')` for every `Status` created by a `status` webhook. This binding is enforced nowhere in the reachable code path.

`Shipit::Webhooks::Handlers::Handler` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) defines a `stacks` helper that scopes work to `Repository.from_github_repo_name(repository_name)&.stacks`, using `payload.dig('repository', 'full_name')`. `StatusHandler`, however, does not use this helper at all:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This looks up commits purely by `sha` across the entire `commits` table, regardless of which `stack_id`/repository they belong to, then calls `commit.create_status_from_github!(params)` [2](#0-1) , which writes a new `Status` row via `statuses.replicate_from_github!(stack_id, github_status)` and recomputes `status` from all statuses/check runs. `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) is gated by `stack.ignore_ci?` and `success?`, both evaluated on the commit that just received the injected status, i.e. victim stack B's commit.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only verifies that the HMAC signature matches the GitHub App/secret configured for `repository_owner` derived from the payload — it authenticates that the event genuinely came from GitHub for repository A's organization, but performs no check tying the event's repository to the specific commit/stack that ends up mutated. It therefore cannot prevent the divergence: the signature check operates on "which org sent this webhook," not "which commit/stack is allowed to be touched by it."

Exploit flow: Git commit hashes are SHA-1 content hashes of the same tree/parents/message/author/committer, so a commit that exists in victim stack B's repository (e.g. an open-source project Shipit tracks) also exists, byte-for-byte and hash-for-hash identical, in any fork or clone of that repository — including a fork owned by the attacker (repository A). The attacker (an unprivileged GitHub user who can push to/own a fork and trigger CI/status updates on their own repository) causes a commit `status` event to be created on repository A for that shared SHA (e.g. by pushing a tag/branch referencing that historical commit and letting CI or the GitHub Statuses API post a status). GitHub delivers a properly signed `status` webhook scoped to repository A. `StatusHandler#process` looks up `Commit.where(sha: <shared sha>)`, finds the victim's commit belonging to stack B, and writes a status derived from the attacker's event onto it. If the resulting state is `success` (or the relevant stack has `ignore_ci?`), `Commit#deployable?` for the victim's commit becomes `true`, and since `Commit#deployable?` also gates `schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`), this can trigger continuous deployment of stack B using a status the attacker fabricated.

### Impact Explanation
This is "a payload for one repository mutating another's stack, commit, task or team," meeting the Critical bar: an attacker-controlled webhook for repository A causes a `Status` record to be written on a commit belonging to an unrelated stack B, and can force `Commit#deployable?` to `true` for that commit without any action by stack B's owners. Combined with `schedule_continuous_delivery`, this can trigger an unauthorized deploy of stack B. The attack is repeatable against any commit whose SHA the attacker can reproduce in a repository they control (trivially true for any commit reachable via fork/clone of the same history), and is not limited to a single stack — any stack tracking a commit shared with an attacker-controlled fork is exposed.

### Likelihood Explanation
Preconditions: Shipit's GitHub App/webhook must be enrolled such that repository A (attacker-owned/forked repo) can legitimately emit `status` events that reach Shipit's `/webhooks` endpoint with a valid signature — a normal condition for any multi-repo/org-wide Shipit deployment where the attacker is an org member, contributor, or owner of a fork inside the monitored org/app installation. No Shipit secrets, sessions, or GitHub App keys are needed; the attacker only needs to legitimately trigger a status update (e.g., via a CI run or the Statuses API) on a repository they own for a SHA that coincides with a victim commit — which happens automatically for any commit shared via fork/clone. This makes the attack low-cost and repeatable per commit/stack.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed handler) to commits belonging to the repository named in the webhook payload, mirroring the `stacks`/`repository_name` scoping already implemented in the base `Handler` class, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` instead of `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook scoped to repository A does not mark a commit in unrelated stack B as deployable" do
  stack_b = shipit_stacks(:shipit) # belongs to repository "shopify/shipit-engine"
  commit_b = stack_b.commits.create!(sha: "a" * 40, message: "victim commit")
  assert_not commit_b.deployable?

  payload = {
    "sha" => commit_b.sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => "attacker/repo-a", "owner" => { "login" => "attacker" } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit_b.reload
  # Binding under test: commit.stack.repository == payload['repository']['full_name']
  assert_not_equal stack_b.repository.full_name, payload["repository"]["full_name"]
  assert commit_b.deployable?, "commit in stack B became deployable due to a status event scoped to repository A"
end
```
This demonstrates that a `status` payload whose `repository.full_name` never matches `stack_b.repository.full_name` nonetheless flips `commit_b.deployable?` to `true`, confirming the broken binding.
