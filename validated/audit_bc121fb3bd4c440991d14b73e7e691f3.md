Confirmed: both `create!` and `unarchive!` in `ReviewStackAdapter` call `Shipit::ReviewStackProvisioningQueue.add(stack)` unconditionally before any downstream provisioning task runs, with no re-check of `review_stacks_enabled`.### Title
`ReopenedHandler#unarchive?` replicates `opened_handler.rb`'s `&&`/`||` precedence bug, bypassing `review_stacks_enabled` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` mirrors `OpenedHandler#provision?`'s broken boolean precedence: `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (...) || (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)`. Because `&&` binds tighter than `||`, `review_stacks_enabled` only gates the `allow_all` branch, not the `prevent_with_label` branch, so a repository with `review_stacks_enabled: false` and `provisioning_behavior: :prevent_with_label` will still unarchive/provision a stack for a reopened PR that lacks the provisioning label. `UnlabeledHandler`, however, is not affected: its `respond_to_label_change?` gate applies `repository.review_stacks_enabled &&` as a top-level conjunction over `(archive? || unarchive?)`, so review-stacks-disabled repositories are always excluded regardless of the internal precedence inside `archive?`/`unarchive?`.

### Finding Description
Broken binding: `repository.review_stacks_enabled == true` is claimed to be the actual gate before `Command`/`PTY.spawn` is reached for any given repository's stacks. For `ReopenedHandler`, this binding is broken: [1](#0-0) 
`respond_to_pull_request_reopened?` calls `unarchive?`, whose expression `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)` parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label) || (prevent_with_label? && !label)`. When `review_stacks_enabled == false` and `provisioning_behavior == :prevent_with_label` and no provisioning label is present on the PR, the third disjunct alone evaluates `true`, so `unarchive?` returns `true` even though `review_stacks_enabled` is `false`.

Exploit flow: an attacker who owns/controls a PR on a repository configured with `review_stacks_enabled: false`, `provisioning_behavior: :prevent_with_label` simply ensures no provisioning label is attached and reopens a previously-closed PR (or the PR is already open with a label removed and then closed/reopened). GitHub emits a `pull_request` `reopened` webhook, handled by `ReopenedHandler#process` → `stack.unarchive!` on `ReviewStackAdapter`: [2](#0-1) 
If no stack exists yet, `unarchive!` calls `create!`, which unconditionally calls `Shipit::ReviewStackProvisioningQueue.add(stack)`: [3](#0-2) 
The queued stack is later provisioned by `ReviewStackProvisioningQueue#work`, which will eventually run a `Command`/`PTY.spawn`-based task against the attacker's branch/ref, with none of the intervening code re-checking `review_stacks_enabled`.

Why existing guards fail: `respond_to_pull_request_reopened?` only checks `params.action == "reopened"` and delegates entirely to `unarchive?`, which is the exact site of the precedence bug; there is no separate/explicit `repository.review_stacks_enabled` check ANDed over the whole expression the way `UnlabeledHandler#respond_to_label_change?` does it: [4](#0-3) 
No webhook signature check, `ExplicitParameters` schema, or model validation constrains `provisioning_behavior`/`review_stacks_enabled` combinations to prevent this — they are independent repository-level settings an operator can legitimately configure, and the bug is purely in the boolean logic of `unarchive?`.

### Impact Explanation
This lets an attacker on a repository configured with `review_stacks_enabled: false` + `provisioning_behavior: :prevent_with_label` force creation and provisioning of a review stack (running `shipit.yml`/`Command`/`PTY.spawn` from the attacker's controlled ref) purely by reopening their own PR without a label — a feature the operator explicitly disabled. This matches the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category, and since the trigger is the "reopened" event (not "opened"), it is a distinct call path from the previously known `opened_handler.rb` bug. It is repeatable against any repository sharing this specific configuration and is scoped to that repository's own stacks (not cross-tenant), but the attacker fully controls the ref/branch executed.

### Likelihood Explanation
Requires a specific but plausible repository configuration: `review_stacks_enabled: false` combined with `provisioning_behavior: :prevent_with_label`. This is a legitimate, likely-used configuration (operator disables review stacks broadly while defining a label policy for future/partial use, or toggles `review_stacks_enabled` off temporarily without changing `provisioning_behavior`). Attacker cost is trivial: open/close/reopen a PR they control, with no label attached — no privileges beyond standard GitHub PR authorship are needed. Fully repeatable.

### Recommendation
Add explicit parentheses to force `review_stacks_enabled` to gate the entire expression in `ReopenedHandler#unarchive?` (and audit `OpenedHandler#provision?` for the same issue):
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Alternatively, hoist `repository.review_stacks_enabled` into `respond_to_pull_request_reopened?` as a top-level AND (matching `UnlabeledHandler`'s pattern), so it always gates regardless of provisioning-behavior logic.

### Proof of Concept
minitest in `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` (extending the existing `configure_provisioning_behavior` helper already in that file):
```ruby
test "does not unarchive or provision stacks when review_stacks_enabled is false, even with prevent_with_label and no label" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = []

  Shipit::ReviewStackProvisioningQueue.expects(:add).never

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived since review_stacks_enabled is false"
end
```
Binding assertion (before/after equality check): assert `repository.review_stacks_enabled == false` while independently asserting `Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).send(:unarchive?) == false` — under current code this second assertion fails (`unarchive?` returns `true`), proving the divergence and that `ReviewStackProvisioningQueue.add` is reachable despite `review_stacks_enabled == false`.
