This confirms the analog. In multi-organization mode, `Shipit.github(organization:)` looks up a per-organization GitHub App config, each with its own `webhook_secret` [1](#0-0) . The webhook signature check in `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')` [2](#0-1) . However, the actual repository/stack acted upon by the event handlers (e.g. `PushHandler`) is resolved from a *different* field in the same unsigned-portion-independent JSON body: `payload.dig('repository', 'full_name')`, via `Repository.from_github_repo_name` [3](#0-2) [4](#0-3) .

### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while event handlers act on the independent `repository.full_name` field, allowing cross-organization webhook forgery in multi-GitHub-App deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
When Shipit is configured with multiple GitHub Apps (one per organization, as documented in `docs/setup.md`), the HMAC signature on an inbound webhook is verified against the secret belonging to the organization named in `repository.owner.login` (or `organization.login`). But the handler that actually performs the write — e.g. `PushHandler`, which triggers `stack.sync_github` — resolves the target repository from the completely separate `repository.full_name` field. Because the two fields are never cross-checked against each other, a webhook whose signature legitimately verifies for Organization A can carry a `repository.full_name` pointing at a repository owned by Organization B, and the push/sync will be processed as if it came from B's real GitHub App.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the raw JSON body and uses it purely to pick *which* `GitHubApp`/secret to validate the signature against: [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization in `secrets.github`: [1](#0-0) 

Once the signature check passes, `WebhooksController#create` dispatches the entire raw JSON payload to the registered handler(s) for the event, e.g. `Shipit::Webhooks::Handlers::PushHandler`: [5](#0-4) 

`PushHandler` (via the base `Handler` class) determines the target `Repository`/`Stack` set using `payload.dig('repository', 'full_name')` — not `repository.owner.login`: [3](#0-2) 

`Repository.from_github_repo_name` splits that string on `/` and looks the repository up purely by owner/name parsed from `full_name`: [4](#0-3) 

The binding that should hold is: **the organization whose secret authenticated the signature == the organization that owns the repository being acted upon**. Nothing enforces `repository.owner.login == repository.full_name.split('/').first`. GitHub's own webhook delivery would never produce such a payload, but the field is attacker-controlled from the perspective of Shipit's verification logic — an entity that can get GitHub to deliver *any* signed webhook for organization A (e.g. someone with push access to a repo in org A, which is unprivileged with respect to Shipit itself, or in a compromised/malicious app-installer scenario) can include an arbitrary `repository.full_name` value naming a repo belonging to org B in that same delivery by crafting a repo/webhook under org A that manipulates payload contents where possible, or more directly, this class of bug matters whenever the app owner mis-configures overlapping repo namespaces or whenever `repository_owner` (used for verification) diverges from `repository.full_name`'s owner segment (used for the write) within a single payload — e.g. a repo transferred/renamed between organizations, or a forked/mirrored payload replay across a differently-owned repository sharing the same webhook endpoint. Since verification and the acted-upon target are read from two independently-controlled JSON keys that GitHub does not cryptographically bind to each other beyond the overall payload signature (which Shipit does correctly check as a whole blob), the actual root issue is that `repository_owner` is *only* used to select the verification key and is never re-validated against `full_name` before the handler executes — i.e., Shipit never asserts `repository.owner.login == full_name.split('/').first` post-verification.

### Impact Explanation
If an attacker can obtain a validly-signed webhook body for one organization's GitHub App but influence `repository.full_name` to reference a repository/stack under a different organization (e.g. via a mis-scoped GitHub App shared across orgs, or a repository transfer edge case), the `PushHandler` will call `stack.sync_github(expected_head_sha:)` against a `Stack` belonging to the unrelated organization, causing unauthorized sync/deploy triggering — a cross-repository write not gated on that organization's own webhook secret. This matches the High-impact category of cross-repository writes / unauthorized deploy triggering through a credential-scope confusion.

### Likelihood Explanation
Likelihood is Low-to-Medium and configuration-dependent: it only manifests in the multi-GitHub-App deployment mode documented in `docs/setup.md` (`Using Multiple GitHub Applications`), where `repository_owner` genuinely determines a different signing secret per org. Under the more common single-app config (`github_default_organization.nil?`), all events use the same secret, and it does not affect stand-alone deployments where each org only manages its own repos.

### Recommendation
After signature verification succeeds, explicitly assert that `repository_owner` (used to select and verify the signing key) matches the owner segment of `repository.full_name` (used by handlers to select the target `Repository`/`Stack`) before dispatching to any `Shipit::Webhooks::Handlers`. Reject the webhook with `422` if they diverge.

### Proof of Concept
1. Configure Shipit in multi-org mode with two organizations, `org-a` and `org-b`, each with their own GitHub App and `webhook_secret` per `docs/setup.md`.
2. Craft (or obtain, via any legitimate delivery from `org-a`'s app) a `push` webhook payload where `repository.owner.login == "org-a"` but `repository.full_name == "org-b/some-repo"`.
3. Sign the payload with `org-a`'s `webhook_secret` and send it to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature.
5. `PushHandler` resolves `Repository.from_github_repo_name("org-b/some-repo")` and, if a matching stack exists, invokes `stack.sync_github(expected_head_sha:)`, triggering a sync/deploy for `org-b`'s stack despite the request never being authenticated by `org-b`'s own webhook secret.
