### Title
`in_data_feed`/`in data feed` trust unstable, not-yet-finalized (possibly non-serial) data feed units inside AA evaluation - ([File: data_feeds.js])

### Summary
The Rikkei Finance incident stemmed from the protocol trusting an oracle value that had been substituted/manipulated instead of the legitimate one. In `ocore`, the equivalent trust boundary is the `in data feed` / `in_data_feed` oscript primitive, which lets an AA or address definition make fund-release decisions based on whether a named oracle posted a given value. When this check is evaluated for an AA (`bAA=true`), `dataFeedExists()` scans `storage.assocUnstableMessages` — units that are posted but **not yet stable** — and does **not** verify `objUnit.sequence === 'good'` before accepting a data-feed message from them.

### Finding Description
`dataFeedExists()` in [1](#0-0)  iterates `storage.assocUnstableMessages` to let an AA react immediately to just-posted, not-yet-stable oracle values, without requiring `objUnit.sequence !== 'good'` to be filtered out.

By contrast, the sibling function `readDataFeedValue()`, which implements the value-returning `data_feed[[...]]` primitive, performs the same "fast unstable-oracle" optimization but explicitly requires `objUnit.sequence !== 'good'` to `continue` (skip) candidate units: [2](#0-1) .

`sequence` on a unit reflects whether the unit is a valid, "good" member of the DAG or a conflicting/double-spend loser that will end up `final-bad`/`temp-bad` once main-chain stability is determined (tracked in `main_chain.js`/`validation.js`). A unit that is currently unstable and destined to become non-serial (`final-bad`) is not something the protocol otherwise treats as authoritative, precisely because its data (in this case, the data-feed payload) can be reverted/invalidated once stability catches up.

`dataFeedExists()` backs the `in data feed` operator used in address/AA definitions (evaluated via `definition.js`, `validateAuthentifiers`, case `'in data feed'`) and the `in_data_feed()` oscript function used inside AA formulas (`formula/evaluation.js`, case `'in_data_feed'`), both of which call `dataFeeds.dataFeedExists(...)` with `bAA` set appropriately. Because the unstable-scan path omits the `sequence` filter, an AA that gates a payout, state transition, or fund release on `in_data_feed(...)` can be induced to see the condition as satisfied by an oracle-authored unit that is still unstable and might ultimately be excluded from the "good" sequence — i.e., the AA's decision is based on data that the protocol itself may later disown.

### Impact Explanation
An AA (e.g., a price-triggered vault, insurance payout, or prediction-market contract) that relies on `in data feed`/`in_data_feed` to gate a state change or fund transfer can execute that gate using a data-feed unit whose validity is not yet finalized and could resolve as non-serial. This mirrors the Rikkei Finance root cause: the receiving logic accepted an oracle signal it should not have fully trusted, resulting in funds being released against an unverified/soon-to-be-invalidated value. In AA contexts this can lead to AA fund loss/incorrect payout logic and to different nodes momentarily disagreeing on whether the `in_data_feed` condition held, since unstable, non-good-sequence data is transient state.

### Likelihood Explanation
Exploitation requires an attacker who controls (or colludes with) one of the oracle addresses referenced by the `in data feed`/`in_data_feed` condition to post a data-feed unit that conflicts with another of their own units (a double-spend/conflicting pair), so that the feed-bearing unit is temporarily unstable with an as-yet-undetermined sequence. This is a specific but realistic scenario for AAs whose definitions or trigger-supplied oracle lists allow a not-fully-trusted or self-referential oracle address (patterns supported by the language, as seen in the "oracle address from input"/`trigger.data.oracle` test cases). It requires more setup than a simple unprivileged spend, so it is placed at medium-to-high likelihood depending on how a given AA sources its oracle addresses.

### Recommendation
Add the same `objUnit.sequence !== 'good'` guard to the unstable-message scan in `dataFeedExists()` (data_feeds.js, the `bAA` branch) that already exists in `readDataFeedValue()`, so that `in data feed`/`in_data_feed` only treats unstable oracle units as authoritative when they are known-good in sequence, consistent with the value-reading code path.

### Proof of Concept
1. Deploy an AA whose bounce/state formula includes `in_data_feed[[oracles=<oracle_address>, feed_name="X", feed_value="Y"]]` guarding a fund release, where `<oracle_address>` is influenced by trigger data or is otherwise attacker-reachable, as demonstrated by ocore's own test patterns (`oracles=input[[asset=base]].address`, `oracles=trigger.data.oracle`) [3](#0-2)  and [4](#0-3) .
2. As the controller of that oracle address, post two conflicting (double-spending) units, one of which contains the `data_feed` message with `feed_name="X", value="Y"`.
3. While both units are unstable, trigger the AA; `dataFeedExists()`'s unstable-message loop (`data_feeds.js:34-43`) finds the data-feed message without checking `objUnit.sequence`, so `in_data_feed` returns `true` and the AA releases funds.
4. Once stability is determined, the data-feed-bearing unit may resolve to `sequence='final-bad'`, meaning the condition the AA acted on was never actually valid/final — yet the fund release already occurred.
