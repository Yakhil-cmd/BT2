## Title
Uncaught `throw Error("no src_coin")` reachable via a normally-posted unit crashes the validating node during payment validation - ([File: validation.js])

### Summary
`validation.js`'s `validatePaymentInputsAndOutputs` contains a code path that assumes `objValidationState.src_coin` was pre-populated by the private-payment machinery, and `throw`s a hard, uncaught exception if it wasn't. This assumption is not actually enforced for every code path that can reach that branch: any ordinary unit posted to the network that references a private, fixed-denomination asset with a `transfer` input goes through the same generic `validation.validate()` call used for normal (non-private-chain) unit processing, where `objValidationState.src_coin` is never set (it is only set by `indivisible_asset.js` when validating a private payment chain object, a different code path). This is analogous to CVE-2016-7052: a value the code assumes is always present (there, the CRL issuer's certificate; here, `objValidationState.src_coin`) is actually attacker-influenceable and can be missing, and the missing-value/NULL case is handled with an unconditional `throw`/crash instead of a graceful validation failure.

### Finding Description
`validatePaymentInputsAndOutputs()` handles the `"transfer"` input case for payment messages inside `validation.js`: [1](#0-0) 

```js
// for private fixed denominations assets, we can't look up src output in the database
// because we validate the entire chain before saving anything.
// Instead we prepopulate objValidationState with denomination and src_output
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    var src_coin = objValidationState.src_coin;
    if (!src_coin.src_output)
        throw Error("no src_output");
    ...
```

`objValidationState.src_coin` is populated only in one caller: `indivisible_asset.js`'s `validatePrivatePayment()`, which sets `objValidationState.src_coin` before invoking `validation.validatePayment(...)` as part of the *private-chain* validation flow: [2](#0-1) 

However, `validatePaymentInputsAndOutputs` (and the `case "transfer":` switch branch shown above) is also reached through the **generic, primary unit-validation path** (`validation.validate()` → `validateMessages` → `validateMessage` → `validatePayment` → `validatePaymentInputsAndOutputs`), which is invoked for every unit received from the network or posted by a light client, per `network.js`'s `handleJoint()`: [3](#0-2) 

In that generic path `objValidationState` is a bare object created at the top of `validate()`: [4](#0-3) 

It never gets a `src_coin` field. If an attacker crafts and posts an ordinary unit (not delivered through the private-payment-chain machinery) whose payment message references a private asset with `fixed_denominations: true` and includes a `"transfer"` type input, the validator will look up `objAsset` (correctly identifying it as private + fixed-denomination), enter the `if (objAsset && objAsset.is_private && objAsset.fixed_denominations)` branch, find `objValidationState.src_coin` undefined, and `throw Error("no src_coin")`.

This `throw` is not caught anywhere in the synchronous callback chain that leads here (`async.forEachOfSeries` callback inside `validatePaymentInputsAndOutputs`, called from `validateMessage`/`validateMessages`, invoked from inside `mutex.lock()`/`async.series()` in `validate()`). It therefore becomes an uncaught exception that propagates to Node's global handler: [5](#0-4) 

```js
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	console.error('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

By design the process is deliberately crashed rather than continuing in a possibly-inconsistent state. Every full node that receives and validates this single malicious unit will independently hit the same `throw` and crash, because the flaw is deterministic and depends only on the content of the posted unit (asset properties + a `"transfer"` input), not on any peer-specific or timing condition.

### Impact Explanation
This maps to the “network unable to confirm new units” outcome explicitly listed as acceptable impact: any node (hub, witness, or ordinary full node) that receives this single crafted unit crashes deterministically while validating it. Since the same unit will be relayed to and processed by every full node on the network, an attacker can use one crafted unit to knock full nodes/witnesses offline as they attempt to validate/relay it, disrupting the DAG's ability to progress and confirm new units until operators patch or filter the unit. This is a High-severity denial of validation availability triggered purely by a single unprivileged unit poster, directly analogous to a NULL/missing-field dereference crashing validation logic that processes attacker-supplied data (CVE-2016-7052 in x509_vfy.c during CRL processing).

### Likelihood Explanation
Likelihood is high: no special privileges, keys, or existing private-asset holdings are required to *construct* the malformed payment message; the attacker only needs to reference a real private, fixed-denomination asset that is already defined on the DAG (asset definitions are public) and add a `"transfer"` input claiming to spend from it in a normal, non-private-chain unit. The vulnerable code path is on validation code executed for every unit and does not require the unit to actually be accepted as valid to reach the crash — the `throw` occurs before double-spend/ownership checks resolve.

### Recommendation
Do not `throw` on missing `objValidationState.src_coin`/`src_coin.src_output` in `validatePaymentInputsAndOutputs`. Instead, return a normal validation error (`cb("no src_coin")` / `cb("no src_output")`), and additionally ensure that this code branch is only reachable from the private-payment-chain validation flow (e.g., by explicitly checking `objValidationState.bPrivate` or an equivalent flag before entering the `if (objAsset && objAsset.is_private && objAsset.fixed_denominations)` branch), so that a bare unit-level `transfer` input against a private fixed-denomination asset without a properly established `src_coin` is rejected as an ordinary unit error rather than crashing the process.

### Proof of Concept
1. Identify (or have the attacker previously define) an asset `A` with `is_private = true` and `fixed_denominations = true`.
2. Craft a unit `U` with a `payment` message whose `payload.asset = A` and whose `payload.inputs` contains one entry of the default `"transfer"` type (`{unit, message_index, output_index}`, no `type` field, defaults to `"transfer"`), referencing any existing unit/message_index/output_index (the exact target doesn't matter — the crash occurs before ownership/output existence is verified).
3. Post/broadcast `U` to a full node via normal unit submission (`network.js` `handleJoint`), just like any other unit.
4. During validation, `validatePaymentInputsAndOutputs` resolves `objAsset` for `A` (is_private && fixed_denominations = true), enters the branch at `validation.js:2415`, finds `objValidationState.src_coin` undefined (since this is the generic unit-validation path, not the private-chain-validation path that would have set it), and executes `throw Error("no src_coin")` at `validation.js:2416-2417`.
5. This exception is uncaught, triggers `process.on('uncaughtException')` in `network.js:4530-4543`, and crashes the node process.

Note: I was not able to execute this against a live node to confirm the crash empirically (no runtime access in this environment); the analysis is based on static tracing of the code paths shown above, and it should be verified in a controlled test/devnet before being treated as fully confirmed.
