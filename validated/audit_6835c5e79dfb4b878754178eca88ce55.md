### Title
Recipient Contract Revert in `handleKLAYTransfer` Permanently Locks Bridged KLAY and Freezes `lowerHandleNonce` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`BridgeTransferKLAY.handleKLAYTransfer` delivers KLAY to the destination address via a low-level call (`_to.call.value(_value)("")`) and then hard-reverts the entire transaction if that call fails. Because the nonce-accounting state (`handleNoncesToBlockNums`, `_updateHandleNonce`, `lowerHandleNonce`) is written **before** the delivery call, a revert rolls back all state changes. If `_to` is a contract whose fallback function always reverts, the bridge operators can never successfully execute this nonce, the KLAY is permanently locked inside the bridge contract, and `lowerHandleNonce` (and therefore `recoveryBlockNumber`) can never advance past the stuck nonce.

---

### Finding Description

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` executes in this order:

1. Nonce guard: `_lowerHandleNonceCheck(_requestedNonce)` [1](#0-0) 
2. Operator vote: `_voteValueTransfer(_requestedNonce)` [2](#0-1) 
3. State writes: `_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber`, `_updateHandleNonce(_requestedNonce)` [3](#0-2) 
4. Event emission [4](#0-3) 
5. **Asset delivery**: `(bool ok, ) = _to.call.value(_value)("")` followed by `require(ok, "handleKLAYTransfer: transfer failed")` [5](#0-4) 

If `_to` is a smart contract whose fallback function reverts (or consumes all forwarded gas), step 5 causes the entire transaction to revert. Because Solidity reverts are atomic, **all state writes from step 3 are also rolled back**. `handleNoncesToBlockNums[_requestedNonce]` is never set, so `_updateHandleNonce` can never advance `lowerHandleNonce` past this nonce:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [5](#0-4) [6](#0-5) 

The `recoveryBlockNumber` is used by the off-chain `valueTransferRecovery` subsystem as the starting block for re-scanning pending events:

```go
hint.blockNumber, err = to.bridge.RecoveryBlockNumber(nil)
``` [7](#0-6) 

A user who controls `_to` on the destination chain can make the fallback conditionally revert, holding the bridge nonce hostage indefinitely.

---

### Impact Explanation

- **Permanent KLAY lock**: The KLAY deposited into the bridge on the source chain can never be delivered to `_to` and cannot be reclaimed by the bridge operators (no refund path exists in the contract). The funds are frozen inside the bridge contract.
- **`lowerHandleNonce` freeze**: Because `handleNoncesToBlockNums[stuck_nonce]` is never written, the sequential scan in `_updateHandleNonce` halts at the stuck nonce. `lowerHandleNonce` and `recoveryBlockNumber` cannot advance past it.
- **Recovery subsystem degradation**: The off-chain recovery process reads `RecoveryBlockNumber` as its scan start. A frozen `recoveryBlockNumber` forces the recovery daemon to re-scan from an arbitrarily old block on every cycle, growing in cost as the chain grows.
- **Conditional-release griefing**: An attacker can deploy a contract that reverts only when a flag is set, then demand an out-of-band payment before enabling the transfer — analogous to the M-14 ransom scenario.

---

### Likelihood Explanation

Any user who initiates a bridge transfer on the source chain can freely specify any address as `_to`, including a contract they control. The bridge operators relay `_to` verbatim; they have no ability to substitute a safe address. The attack requires only deploying a contract with a reverting fallback and initiating one bridge transfer — no special privilege is needed.

---

### Recommendation

1. **Separate delivery from nonce accounting**: Mark the nonce as handled unconditionally, then allow the recipient to pull their KLAY in a separate `claim()` call. This is the pull-over-push pattern and eliminates the revert dependency entirely.
2. **Suppress delivery failure instead of reverting**: Replace `require(ok, ...)` with a conditional that emits a `DeliveryFailed` event and records the undelivered amount for a later claim, rather than reverting the whole transaction.
3. **Validate `_to` is not a contract, or use a try/catch**: At minimum, emit a failure event and skip delivery rather than reverting, so the nonce is still consumed and `lowerHandleNonce` can advance.

---

### Proof of Concept

```solidity
// Malicious recipient deployed on the destination chain
contract MaliciousRecipient {
    bool public block_ = true;
    address owner;
    constructor() { owner = msg.sender; }
    function setBlock(bool v) external { require(msg.sender == owner); block_ = v; }
    receive() external payable { require(!block_, "blocked"); }
}
```

1. Attacker deploys `MaliciousRecipient` on the destination chain with `block_ = true`.
2. Attacker calls `requestKLAYTransfer(address(maliciousRecipient), value, extraData)` on the source bridge, locking KLAY.
3. Bridge operators call `handleKLAYTransfer(..., address(maliciousRecipient), value, nonce, ...)` on the destination bridge.
4. `maliciousRecipient.receive()` reverts → `require(ok, ...)` reverts → entire tx reverts.
5. `handleNoncesToBlockNums[nonce]` is never set; `lowerHandleNonce` stays frozen.
6. Attacker calls `setBlock(false)` only after receiving an out-of-band payment, then operators retry and the transfer succeeds.
