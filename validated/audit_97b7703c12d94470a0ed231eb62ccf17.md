### Title
Cross-tenant `ReviewStack` creation with attacker-controlled `branch` via owner/full_name payload confusion - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify a webhook using `params.dig('repository','owner','login')`, but every pull-request handler (e.g. `OpenedHandler`) resolves the actual `Shipit::Repository` to act on using `params.repository.full_name` independently, with no check that the two agree. An attacker who owns organization A and can therefore produce a validly-signed webhook for A can put `repository.owner.login: "A"` (passes signature check) alongside `repository.full_name: "B/some-repo"` and an arbitrary `pull_request.head.ref`, causing a `ReviewStack` to be created under org B's real repository with `branch` set verbatim to the attacker's string.

### Finding Description
Binding claimed: `ReviewStack.branch (persisted) == a branch that exists/is authorized on the repository that the record is filed under (org B)`. This does not hold.

- `verify_signature` derives the signing organization solely from `params.dig('repository','owner','login')` (or `organization.login`) and validates the HMAC against that organization's `webhook_secret`: [1](#0-0) [2](#0-1) 
- `OpenedHandler#repository` independently resolves the target `Repository` from `params.repository.full_name` via `Repository.from_github_repo_name`, which just splits `"owner/name"` and does a DB lookup — it never compares this owner to the one used for signature verification: [3](#0-2) [4](#0-3) 
- If `repository.review_stacks_enabled` and the provisioning behavior permit it, `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` runs against org B's `review_stacks` scope: [5](#0-4) 
- `stack_attributes` takes `branch` verbatim from `params.pull_request.head.ref`, with no existence/authorization check against org B's GitHub branch protection or even that the branch exists in org B's repository: [6](#0-5) 

Exploit flow: attacker owns org A, configures its GitHub webhook to Shipit with a secret they know, and sends a `pull_request` `opened` event where `repository.owner.login = "A"` (so `verify_signature` succeeds using org A's secret) but `repository.full_name = "B/target-repo"` and `pull_request.head.ref = "<attacker-chosen-string>"`. `verify_signature` passes because it only checks org A's secret against org A's login field; the actual mutation target is picked from `repository.full_name`, which points at org B. This is the same repository/owner divergence documented for the push/opened-handler confusion (Q1/Q7); this question demonstrates its concrete consequence on `ReviewStack.branch`.

None of the existing guards catch this: `verify_signature` checks a signature, not owner/full_name consistency; `ExplicitParameters` schemas only enforce presence/type, not cross-field consistency; `Repository` model validations only constrain `owner`/`name` character sets, not that `full_name`'s owner matches the payload's `repository.owner.login`.

### Impact Explanation
A record is written into org B's `review_stacks` table (a database mutation for a repository/tenant that never authenticated this payload) with a fully attacker-controlled `branch` string and `environment` (`"pr#{params.number}"`). Downstream, `Stack#sync_github` and provisioning code treat `branch` as authoritative for fetching status/commits and driving CI-gated deploy behavior for that stack. This matches "a payload for one repository mutating another's stack" — Critical. It is repeatable against any repository that has `review_stacks_enabled` with `allow_all` (or a satisfiable label condition), for any PR number/environment slug the attacker chooses, as long as org B is configured that way.

### Likelihood Explanation
Preconditions: attacker must own/administer organization A within the same Shipit installation (to legitimately configure a webhook with a secret they know) — the rules state this is the assumed attacker capability. Target org B must have `review_stacks_enabled` and a provisioning behavior that the forged PR metadata satisfies (`allow_all`, or label-based if attacker also forges `labels`). No GitHub-side privilege on org B's repo is required, and no Shipit session/token is needed — only crafting a raw JSON POST to `/webhooks` with a valid signature computed with org A's own secret. This is a low-cost, fully repeatable HTTP-only attack.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler before acting), require that `params.dig('repository','owner','login')` (or `organization.login`) equals the owner segment parsed from `params.repository.full_name`; reject the webhook (422) on mismatch. Additionally, `Repository.from_github_repo_name` callers (or the model itself) should refuse to resolve/act on a repository whose owner differs from the webhook-verified organization, closing this class of tenant-confusion bugs across all handlers, not just `OpenedHandler`.

### Proof of Concept
Minitest plan (webhooks controller/integration test, no live GitHub):
1. Create `Shipit::Repository` for org B (`owner: "b", name: "target-repo"`) with `review_stacks_enabled: true`, `provisioning_behavior: "allow_all"`.
2. Configure `Shipit.github` so organization `"a"` has a known `webhook_secret`.
3. Build a `pull_request` `opened` JSON body with:
   - `repository: { owner: { login: "a" }, full_name: "b/target-repo" }`
   - `pull_request: { head: { ref: "attacker-controlled-branch" }, ... }`
4. Compute `X-Hub-Signature` using org A's `webhook_secret`.
5. POST to `/webhooks` with `X-Github-Event: pull_request`.
6. Assert response is `200`/`204` (accepted), and:
   ```ruby
   stack = Shipit::Repository.find_by(owner: "b", name: "target-repo").review_stacks.last
   assert_equal "attacker-controlled-branch", stack.branch
   ```
   This demonstrates `ReviewStack.branch == attacker-supplied head.ref` while verification occurred solely against org A's secret, for a stack persisted under org B's repository.
