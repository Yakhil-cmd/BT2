This confirms the vulnerability path: `WebhooksController#verify_signature` determines which GitHub App/secret to verify against using `repository_owner`, a value read directly from the unverified JSON payload (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), while the actual repository/stack acted upon by handlers such as `PushHandler` is resolved from a completely different, also-unverified payload field, `repository.full_name`, via `Handler#stacks` / `Repository.from_github_repo_name`.

### Title
Webhook signature verification keyed to a payload-controlled `repository.owner.login`, decoupled from the `repository.full_name` used to select the stack to act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The binding that should hold is: **organization whose secret authenticated the request == organization owning the repository the handler mutates**. This engine breaks that equality because the org used to pick the HMAC secret and the repository used to select the `Stack`/`Repository` to act on come from two independent, both attacker-controlled JSON fields in the same unsigned request.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the `webhook_secret`) using `repository_owner`, which is read straight out of the JSON body before any signature has been checked: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` only verifies the signature if `webhook_secret` is configured for that organization; if it is blank (a valid, documented configuration shown in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets.test.json`, where `webhook_secret: null`), verification is skipped entirely: [3](#0-2) 

Once past `verify_signature`, the actual event handlers (e.g. `PushHandler`) resolve the target `Stack` using a *different* payload field, `repository.full_name`, via `Handler#stacks` / `Repository.from_github_repo_name`, with no cross-check that this repository belongs to the organization that was used to authenticate the request: [4](#0-3) [5](#0-4) 

So an attacker who knows (or can cause) any organization in `Shipit.github` config to have no `webhook_secret` set — or who otherwise controls a signed webhook for one org — can submit an unsigned/mis-signed request with `repository.owner.login` set to that unsecured/attacker-controlled org (satisfying `verify_signature`) while `repository.full_name` names a completely different, victim-owned repository/stack tracked by Shipit. The handler then acts on the victim stack (e.g. enqueues `GithubSyncJob`, updates commit statuses, archives/unarchives review stacks, captures PR labels) as if it came from a verified source for that repository.

### Impact Explanation
This breaks the binding "organization that authenticated == repository being written," letting an attacker trigger unauthorized deploy-relevant side effects (sync, commit status writes, review-stack archive/unarchive, PR label capture/queue actions) against a stack/repository they do not control, purely by crafting the JSON body — no `webhook_secret`, no session, and no repository write access on the victim repo is needed if any configured org has no secret (a state the setup docs and test fixtures show is a normal/expected configuration for `webhook_secret`).

### Likelihood Explanation
Requires at least one configured GitHub organization in `Shipit.github` to have a blank `webhook_secret` (explicitly supported per `docs/setup.md` "Webhook secret (optional)"), which is realistic in multi-org Shipit deployments that only bother securing some apps. No other privilege is needed to exploit it once such an org exists.

### Recommendation
Bind the verified organization to the actually-mutated resource: after verifying the signature for `repository_owner`, re-derive/require that `repository.full_name`'s owner matches the same organization used for signature verification (or, better, always require `webhook_secret` to be present and reject requests when it is not configured), before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `attacker-org` (no `webhook_secret`) and `victim-org` (tracked stack, e.g. `victim-org/victim-repo`, branch `master`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No valid `X-Hub-Signature` needed, since `Shipit.github(organization: 'attacker-org').verify_webhook_signature` short-circuits to `true` per `lib/shipit/github_app.rb:77`.
3. `WebhooksController#create` proceeds and `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) resolves stacks via `repository.full_name = "victim-org/victim-repo"` and enqueues `sync_github` for that stack, despite the request only being "authenticated" against `attacker-org`.

      return true unless webhook_secret
