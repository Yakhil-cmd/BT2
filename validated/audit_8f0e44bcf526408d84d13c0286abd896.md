### Title
Opaque swap routes can hijack caller authorization to steal unrelated wallet tokens - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
A malicious or mutable route provider can return a poisoned `swap` payload for `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply`. The controller accepts the payload as opaque bytes and forwards it to the configured router, while the account owner’s root authorization remains active for downstream route-selected code. If simulation reveals and the user signs an added token-transfer child, arbitrary assets can be transferred from the user to an attacker while the lending operation still settles normally.

### Finding Description
`StrategySwap` is an uninterpreted `Bytes` value passed to the router’s `execute_strategy` interface. [1](#0-0) [2](#0-1) 

The strategy entrypoints authenticate only the account owner or delegate and accept the route from ordinary transaction arguments. [3](#0-2) [4](#0-3) 

For collateral-backed routes, `withdraw_and_swap_from_supply` withdraws the user’s supply into controller custody and passes the submitted bytes to `swap_tokens_or_passthrough`. [5](#0-4) 

`swap_tokens` requires only non-empty bytes, authorizes one controller-to-router transfer, and invokes `execute_strategy` with the opaque route. [6](#0-5) 

Its post-route checks bound only the controller’s input balance and require positive output; they do not authenticate, constrain, or inspect route-selected external calls made under the caller’s top-level authorization tree. [7](#0-6) [8](#0-7) 

### Impact Explanation
This enables theft of user funds outside the lending position. A poisoned route can invoke attacker-controlled code during the router call, and that code can request a token transfer from the user. Under Soroban authorization recording, that transfer can become a child of the user’s `swap_collateral` authorization; if the wallet signs the simulated tree, the host executes it. The route can still return a fair-looking swap output, leaving the account solvent and satisfying the controller’s measured-output and risk checks.

### Likelihood Explanation
The route is intended to be produced remotely and passed unchanged into the controller, matching the mutable specification trust boundary in the external report. A route provider that was previously benign can later serve a payload containing an attacker-controlled venue. The user does not need to intentionally authorize a separate transfer; the poisoned transfer is embedded in the authorization tree generated for the lending strategy. The controller’s checks do not prevent it because they measure only the configured router’s token effects and final account state.

### Recommendation
Do not rely on opaque route payloads beneath broad account-owner authorization. Restrict router-reachable venue/pool contracts to a governance-approved allowlist, or split route execution into a mode that cannot inherit the user’s root authorization. At minimum, reject any simulated authorization tree containing calls other than the exact expected token transfer, and surface that invariant in the controller-facing strategy contract. Prefer a router design where route payload addresses cannot introduce arbitrary contract calls under the caller’s authorization.

### Proof of Concept
1. Deploy an attacker-controlled contract exposing the call shape expected for a DEX venue. Its swap method calls `token.transfer(victim, attacker, amount)` on an unrelated token held by the victim, then allows the route to return a normal positive output.
2. Serve a mutable route specification that initially contains only normal DEX venues, then replace one venue address with the attacker contract while keeping the same requested input and output assets.
3. Have the victim invoke `swap_collateral(caller=victim, account_id, current, amount, new, swap=poisoned_route)`. The entrypoint authenticates the victim, verifies account ownership, withdraws the collateral to the controller, and forwards the opaque bytes to the configured router. [9](#0-8) [10](#0-9) 
4. During router execution, the attacker venue calls the unrelated token’s `transfer(victim, attacker, amount)`. The simulation records this as a child authorization beneath the victim’s `swap_collateral` call.
5. If the victim signs that tree, the unrelated wallet tokens move to the attacker while the swap can still return positive output, spend no more than the authorized route input, and pass the final account-risk checks. [7](#0-6) [11](#0-10)

pub(crate) fn swap_tokens(
    env: &Env,
    refund_to: &Address,
    token_in: &Address,
    amount_in: i128,
    token_out: &Address,
    swap: &StrategySwap,
) -> i128 {
    require_positive_amount(env, amount_in);
    assert_with_error!(env, !swap.is_empty(), GenericError::InvalidPayments);

    let controller = env.current_contract_address();
    let router_addr = storage::get_swap_aggregator(env);
    let router = SwapAggregatorClient::new(env, &router_addr);
    let token_in_client = token::Client::new(env, token_in);

    // Snapshot before router execution to measure its spend and output.
    let in_before = token_in_client.balance(&controller);
    let out_before = token::Client::new(env, token_out).balance(&controller);

    // Authorize only this token transfer to this router for this exact amount.
    authorize_transfer_as_current(env, token_in, &controller, &router_addr, amount_in);

    storage::with_flash_guard(env, || {
        let _ = router.execute_strategy(&controller, &amount_in, swap);
    });
