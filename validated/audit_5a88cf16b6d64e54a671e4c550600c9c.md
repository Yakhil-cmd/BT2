### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but every event handler resolves the target Stack/Repository from the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks *which* organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated JSON body, then calls `Shipit.github(organization: repository_owner)` to fetch that organization's `GitHubApp` and verify the signature with its secret. Once the signature check passes, every downstream `Shipit::Webhooks::Handlers::Handler` locates the `Repository`/`Stack` to act on using a *different* field of the same payload: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`). Nothing enforces that `repository.owner.login` and the owner segment of `repository.full_name` refer to the same GitHub org/repo.

### Finding Description
This is a "the organization that authenticated" vs. "the repository that is written" binding failure - the exact class of bug described in the report (a value that influences authorization/limits is read from an untrusted field with no cross-check against the field actually used to perform the privileged action).

Multi-organization Shipit deployments store one `webhook_secret` per organization (`Shipit.github_app_config`, `lib/shipit.rb:196-200`, `TOP_LEVEL_GH_KEYS`/`secrets.github` keyed by org). `WebhooksController#verify_signature`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

selects the secret to verify against using `repository.owner.login` taken from the request body itself. Handlers, however, never consult `repository.owner.login`; they resolve the actual `Repository`/`Stack` using `repository.full_name`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

Concretely, `PushHandler`, `StatusHandler`, and the `PullRequest` handlers (`ClosedHandler`, `EditedHandler`, `AssignedHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, etc.) all key off `repository.full_name` to find the `Repository`/`Stack`/`PullRequest` to mutate, e.g.: [3](#0-2) [4](#0-3) [5](#0-4) 

**Root cause**: the equality that should hold is `organization_that_signed_the_request == owner_of_repository_that_is_mutated`. The code instead enforces `organization_named_in_payload_field_A == organization_named_in_payload_field_A_by_construction` (i.e. it trivially reads back its own input) while acting on a completely independent field, `full_name`, whose owner segment is never compared to `repository.owner.login`. An attacker who legitimately controls Organization A within the same multi-tenant Shipit deployment (i.e., knows Org A's own `webhook_secret`, which they were given because they administer Org A's GitHub App installation - not a privileged Shipit account) can sign a payload where `repository.owner.login = "org-a"` (so `verify_webhook_signature` passes with Org A's secret) but `repository.full_name = "org-b/victim-repo"` (so the handler resolves and mutates Org B's `Repository`/`Stack`/`Commit` records).

### Impact Explanation
This crosses the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" bar: an actor who is only trusted for Organization A's webhooks can forge state changes against Organization B's stacks that they have no legitimate GitHub access to, e.g.:
- `PushHandler`: enqueue `GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha`, forcing a resync toward an arbitrary commit that Shipit will consider "the latest pushed commit" for a stack it doesn't own.
- `StatusHandler`: forge a passing/failing commit status (`Commit#create_status_from_github!`) on a victim commit sha, which can flip CI-gating (`ci.require`) decisions and unblock/block deploys.
- Pull request handlers: archive/unarchive review stacks, or mutate PR-derived metadata for a repository the attacker doesn't administer.

This is a cross-repository write achieved purely by having valid webhook credentials for a different, unrelated organization on the same instance - meeting the "cross-repository writes" critical-impact bar.

### Likelihood Explanation
Requires the instance to run in the multi-organization webhook-secret configuration (`secrets.github` keyed by multiple orgs) and requires the attacker to already legitimately control one onboarded organization's GitHub App/webhook secret - a normal, low-privilege administrative capability for their own org, not access to Shipit internals, `GITHUB_TOKEN`, or any Shipit account. Crafting the mismatched JSON body is trivial once the secret for org A is known. Likelihood is moderate: it depends on a specific deployment topology (multiple orgs sharing one Shipit instance) but requires no social engineering, no compromise of Shipit accounts, and no interception.

### Recommendation
In `WebhooksController#verify_signature` / `Handler#repository_name`, cross-validate that the organization used to select the signing secret matches the owner segment actually used to resolve the target repository (e.g., assert `repository.full_name.split('/').first.casecmp(repository_owner) == 0` before dispatching to handlers, or resolve the `Repository` via `(owner, full_name)` together rather than trusting `full_name` alone).

### Proof of Concept
1. Deploy Shipit with `secrets.github` configured for two organizations, `org-a` and `org-b`, each with its own `webhook_secret`, both with repositories onboarded as Shipit stacks.
2. As an administrator of `org-a`'s GitHub App installation (a normal, unprivileged-with-respect-to-Shipit capability), obtain `org-a`'s `webhook_secret`.
3. Craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
4. Sign the raw body with `org-a`'s `webhook_secret` using HMAC-SHA1 to produce `X-Hub-Signature`, set `X-Github-Event: push`, and POST to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature against `org-a`'s secret.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-b/victim-repo")` and enqueues `GithubSyncJob` for `org-b`'s stack with the attacker-supplied `expected_head_sha`, despite the request never having been authenticated by `org-b`.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
