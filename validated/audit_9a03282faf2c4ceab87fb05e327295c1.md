### Title
Bridge Relay Processes Stale Counterpart Token Cache Without Re-Validation, Bypassing Operator Emergency Stop — (`node/sc/bridge_manager.go`)

### Summary

`BridgeInfo.handleRequestValueTransferEvent` resolves the destination token address from a local in-memory cache (`bi.counterpartToken`) that is populated once and never invalidated. If an operator deregisters a token from the counterpart bridge contract (e.g., as an emergency stop), the relay continues to submit `handleERC20Transfer` / `handleERC721Transfer` transactions using the stale cached address. The on-chain handle functions contain no `onlyRegisteredToken` guard, so these transactions succeed, minting or transferring bridged assets to recipients after the operator intended to halt that token pair.

### Finding Description

`handleRequestValueTransferEvent` resolves the counterpart token address as follows:

```go
ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
    ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
    ...
    bi.RegisterToken(tokenAddr, ctTokenAddr)
    ctpartTokenAddr = ctTokenAddr
}
``` [1](#0-0) 

The on-chain query only happens when the local cache is empty. Once a token pair is cached, `GetCounterPartToken` returns the cached address unconditionally: [2](#0-1) 

The relay then calls `HandleERC20Transfer` with the cached (potentially stale) token address: [3](#0-2) 

The on-chain `handleERC20Transfer` has **no** `onlyRegisteredToken` modifier — it directly mints or transfers using the caller-supplied `_tokenAddress`: [4](#0-3) 

Compare with the request-side functions, which do enforce `onlyRegisteredToken` and `onlyUnlockedToken`: [5](#0-4) 

The `BridgeTokens.sol` `onlyRegisteredToken` modifier only guards request-side entry points, not handle-side: [6](#0-5) 

### Impact Explanation

In mint/burn mode, the bridge contract holds a minter role on the destination token. Deregistering the token from the bridge (via `deregisterToken`) does **not** revoke the minter role. If the relay has a cached counterpart token address and a pending event is in the queue, the relay will submit a `handleERC20Transfer` call that succeeds on-chain — minting tokens to the recipient — even though the operator intended to halt that token pair. In lock/unlock mode, the bridge transfers tokens from its own reserves, achieving the same unauthorized transfer.

The corrupted value is the recipient's token balance: it is increased by `valueOrTokenId` of a token the operator has explicitly deregistered, bypassing the emergency stop.

### Likelihood Explanation

The scenario requires: (1) a user submits a cross-chain request before the token is deregistered; (2) the operator deregisters the token (e.g., due to a security incident with that token contract); (3) the relay has already cached the counterpart token address. Steps 1 and 3 are the normal operating state of any active bridge pair. Step 2 is the exact emergency action an operator would take. The window between the request event being queued and the operator completing deregistration is realistic.

### Recommendation

1. **Re-validate the counterpart token on every handle attempt**, not just on cache miss. Before submitting a handle transaction, call `bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)` and abort if the result is `address(0)`.
2. **Add `onlyRegisteredToken` to `handleERC20Transfer` and `handleERC721Transfer`** in `BridgeTransferERC20.sol` and `BridgeTransferERC721.sol`, mirroring the guard already present on request-side functions.
3. **Invalidate the local cache** when `DeregisterToken` is called via the API, so the relay immediately reflects on-chain state.

### Proof of Concept

1. Deploy child bridge + parent bridge in mint/burn mode; register token pair `(childToken, parentToken)`.
2. User calls `requestERC20Transfer` on child bridge → relay caches `childToken → parentToken` and queues the event.
3. Operator calls `deregisterToken(parentToken)` on parent bridge (emergency stop).
4. Relay's `processingPendingRequestEvents` fires; `GetCounterPartToken(childToken)` returns the stale cached `parentToken`.
5. Relay submits `HandleERC20Transfer(..., parentToken, value, ...)` to parent bridge.
6. On-chain: `_lowerHandleNonceCheck` passes, `_voteValueTransfer` passes, `ERC20Mintable(parentToken).mint(to, value)` succeeds (bridge still holds minter role).
7. Recipient receives `value` tokens of `parentToken` after the operator intended to halt that token pair. [7](#0-6) [8](#0-7)

func (bi *BridgeInfo) GetCounterPartToken(token common.Address) common.Address {
	bi.ctTokenMu.RLock()
	defer bi.ctTokenMu.RUnlock()

	cpToken, exist := bi.counterpartToken[token]
	if !exist {
		return common.Address{}
	}
	return cpToken
}

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}
