### Title
Cross-organization webhook forgery — signature verified against the payload's `repository.owner.login`, but every handler acts on the unbound `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The DeFi bug class is a check that authenticates one identity but then acts on a different, un-validated identity (transfer-to-self double counting sender vs. receiver). The equivalent binding-break in `shipit-engine` is: `verify_signature` authenticates the webhook using the GitHub organization named in `repository.owner.login` (or `organization.login`), but every `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Stack`/`Repository` using the independent, uncorrelated `repository.full_name` field. Nothing ties these two fields together.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration (and thus the HMAC `webhook_secret`) to validate against, keyed purely by the organization name extracted from the payload: [1](#0-0) [2](#0-1) 

Shipit supports "Using Multiple GitHub Applications" where each GitHub organization has its own, independently configured `webhook_secret`: [3](#0-2) 

Once the signature check passes, `create` hands the *entire, untouched* JSON payload to every registered handler for the event, with no re-validation that the `repository` object is coherent with the org used for authentication: [4](#0-3) 

Every handler resolves its target purely from `payload.dig('repository', 'full_name')`, a field that is completely independent of `repository.owner.login`/`organization.login` used for signature verification: [5](#0-4) 

Concrete example — `PushHandler` looks up stacks by that unbound `full_name` and calls `stack.sync_github(expected_head_sha: params.after)`: [6](#0-5) 

Other handlers (`PullRequest::ClosedHandler`, `LabeledHandler`, `ReopenedHandler`, `AssignedHandler`, etc.) follow the exact same pattern, resolving `Repository.from_github_repo_name(params.repository.full_name)` with no cross-check against the org that authenticated the request: [7](#0-6) [8](#0-7) 

The equality that should hold and is broken:
`organization_that_signed(payload) == owner(repository.full_name_acted_on)`

Because signature verification only proves "this body was HMAC-signed with Org A's `webhook_secret`," and the body's `repository.owner.login` field used for the *secret lookup* is never cross-checked against `repository.full_name`, an operator/administrator of Org A's own GitHub App installation (who legitimately possesses or controls Org A's `webhook_secret`, since Shipit's multi-org model lets each onboarded organization supply/rotate its own App credentials — see `docs/setup.md`) can craft an arbitrary raw JSON body, set `repository.owner.login` to `"org-a"` (to pass the lookup/signature check) while setting `repository.full_name` to `"victim-org/victim-repo"`, sign it with Org A's known secret, and POST it to the shared `WebhooksController#create` endpoint.

### Impact Explanation
This crosses a repository-write trust boundary between organizations that are supposed to be isolated by per-organization GitHub App credentials. An attacker who legitimately controls one onboarded organization's webhook secret can:
- Force `PushHandler` to invoke `stack.sync_github(expected_head_sha:)` on a victim organization's stack, injecting an attacker-chosen `after` SHA that the victim's stack will treat as the new head to sync/deploy against.
- Manipulate `PullRequest` handlers to archive/unarchive review stacks, alter labels, or otherwise mutate state belonging to a repository the attacker has no legitimate access to.

This matches "cross-repository writes" / "unauthorized deploy" in the impact rubric, since it lets an attacker-controlled, cross-tenant webhook manipulate a victim stack's sync/deploy state without possessing that victim's own webhook secret or GitHub credentials.

### Likelihood Explanation
Requires only that Shipit is configured for multiple GitHub organizations (explicitly documented as a supported configuration) and that the attacker is the administrator of at least one onboarded organization — an "unprivileged attacker" relative to any other organization on the same Shipit instance. No GitHub App private key, `api_clients_secret`, or Shipit session/user account is needed; only knowledge of one's own organization's `webhook_secret`, which the organization owner controls/sets when installing the App.

### Recommendation
Bind the signature-verifying organization to every field the payload is subsequently allowed to act on: after computing `repository_owner`, require that `payload.dig('repository', 'full_name')` (and `organization.login` where relevant) belongs to that same organization (e.g., `full_name.split('/').first.casecmp(repository_owner) == 0`) before dispatching to handlers, rejecting the request with `422` otherwise.

### Proof of Concept
1. Configure Shipit with multiple GitHub organizations (`org-a`, `victim-org`), each with its own `webhook_secret`, per `docs/setup.md`.
2. As the administrator of `org-a`, construct a payload:
```json
{
  "ref": "refs/heads/master",
  "after": "attacker_chosen_sha",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=...` using `org-a`'s known `webhook_secret` over the raw JSON body.
4. POST to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: 'org-a')` and passes since the signature matches `org-a`'s secret.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: 'attacker_chosen_sha')` on the victim's stack — a stack the attacker has no legitimate access to.

**Uncertainty**: I could not fully trace `Shipit.github`/`GithubOrganizationUnknown` implementation or `Repository.from_github_repo_name` body within the tool budget (file reads failed due to missing parameters on the final iteration), so the exact lookup mechanics (e.g., whether organization names are case-normalized, or whether some `github_hooks` per-stack `secret` further gates dispatch for `Repo`-type hooks) are inferred from `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, and `docs/setup.md` rather than fully confirmed end-to-end. A Devin session with full repo access is recommended to verify `lib/shipit.rb#github` and `Shipit::GithubOrganizationUnknown` before treating this as conclusively exploitable.
