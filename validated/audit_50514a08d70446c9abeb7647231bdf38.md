### Title
Unconditional bypass of signature requirement for unresolved nested address definitions - (File: definition.js)

### Summary
`validateDefinition()` in `definition.js` structurally validates any address/asset-condition definition submitted by an unprivileged unit poster (via `objAuthor.definition`) or asset issuer (spending conditions). This validation determines, among other things, whether a definition actually contains a real authentication requirement (a `bHasSig`-style signal used by the `or`/`and`/`r of set`/`weighted and` combinators to enforce that at least one branch requires a real signature). The `case 'address':` branch, which evaluates a nested `['address', X]` reference to another (possibly not-yet-existing) address, is supposed to conditionally decide whether an unresolved inner definition should be trusted, gated by `objValidationState.bAllowUnresolvedInnerDefinitions`. Instead the code hardcodes this flag to `true` unconditionally, exactly mirroring the CORS bug class: a permissive wildcard default silently replaces what should be a narrowly scoped, context-checked trust decision.

### Finding Description
Inside `evaluate()`, the `'address'` operator handles a definition branch that references another address's definition: [1](#0-0) 

When the referenced address's definition is not yet found on-chain (`ifDefinitionNotFound`), the code first tries to find a matching co-author definition included in the same unit. If none is found (`arrDefiningAuthors.length === 0`), the outcome is decided by `bAllowUnresolvedInnerDefinitions`: [2](#0-1) 

The commented-out line 285–286 shows the original, intended logic: `if (objValidationState.bAllowUnresolvedInnerDefinitions) return cb(null, true);` — i.e., this permissive branch should only fire when the caller (e.g. local, non-authoritative pre-validation flows such as `wallet_defined_by_addresses.js`'s `validateAddressDefinition`, which explicitly sets `bAllowUnresolvedInnerDefinitions: true` on a fake validation state) explicitly opts into it. Instead, the flag is now hardcoded as a local `var bAllowUnresolvedInnerDefinitions = true;`, so it is **always true regardless of validation context**, including full on-chain `validateAuthor`/`validateDefinition` calls made from `validation.js` for units posted by any unprivileged party.

This means any unit poster can construct an address (or asset spending-condition) definition that references an address which has never posted a definition on-chain and is not co-signed in the same unit — and this branch will unconditionally report success (`cb(null, true)`), feeding a "true" signal into the `count_options_with_sig`/`bHasSig` bookkeeping that the combinator operators (`or`, `and`, `r of set`, `weighted and`) rely on to enforce that a definition actually requires a real signature check: [3](#0-2) 

By fabricating this "has signature" signal without any real authentication, an attacker can register address/asset definitions that pass structural policy checks meant to guarantee genuine spending authorization, when in fact no real signature or resolvable definition backs the relevant branch.

### Impact Explanation
`validateDefinition` is the exact security gate that ocore's `and`/`or`/`weighted and`/`r of set` combinators use to prevent authors from registering spending conditions that don't actually require a signature (analogous to CORS `allow_credentials` being trusted without verifying the origin). Bypassing it lets an unprivileged unit poster or asset issuer construct definitions/asset conditions that are structurally accepted as validly-authenticated even though they rely on a phantom, unresolved inner address. Depending on how such a definition is later used for spending authorization, this weakens the guarantee that funds controlled by that definition require real authentication — directly touching the "unauthorized spending" and "node disagreement on validity" categories called out as in-scope impact, since different nodes could reach different conclusions about whether an address definition legitimately requires a signature.

### Likelihood Explanation
This code path is reachable by any unprivileged actor who posts a unit containing a new address definition (`author.definition`) or defines an asset's spending conditions — no special privileges, hub role, or network position are required, matching the "unit validation, address definitions and authentifiers" scope. The trigger condition (referencing an address whose definition is not yet published and not co-authored) is trivial to construct.

### Recommendation
Restore the original conditional gate exactly as indicated by the commented-out code: only trust an unresolved inner address definition as satisfying an authentication branch when `objValidationState.bAllowUnresolvedInnerDefinitions` is explicitly set true by the calling context (e.g., local wallet pre-checks), and reject/require resolution otherwise during real on-chain `validateAuthor`/`validateDefinition` calls:
```js
ifDefinitionNotFound: function(definition_chash){
    if (objValidationState.bAllowUnresolvedInnerDefinitions)
        return cb(null, true);
    ...
}
```

### Proof of Concept
1. Attacker crafts a unit whose author definition is:
```json
["address", "SOME_ADDRESS_NEVER_USED_ON_CHAIN"]
```
2. During validation, `validation.js`'s `validateAuthor` invokes `Definition.validateDefinition`, which calls `evaluate` on this definition. [4](#0-3) 
3. `evaluate` hits `case 'address':`, calls `storage.readDefinitionByAddress`, which returns `ifDefinitionNotFound` since the referenced address has no definition on-chain and is not co-authored in the unit.
4. Because `bAllowUnresolvedInnerDefinitions` is hardcoded to `true`, `cb(null, true)` fires unconditionally, reporting the branch as satisfying the authentication requirement without any signature ever being checked. [2](#0-1)
