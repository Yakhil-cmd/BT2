### Title
Webhook signature verification selects the signing organization from `repository.owner.login`, but event handlers act on the independently attacker-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/webhook secret to validate a payload against using `repository.owner.login` (or `organization.login`), while the handlers that actually mutate state key off `repository.full_name` from the very same unauthenticated JSON body. These two fields are never cross-checked, and `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` resolves the signing app for a request like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from the untrusted, not-yet-verified request body (`params.dig('repository', 'owner', 'login')`), and `Shipit.github(organization: repository_owner)` resolves the per-organization config (multi-org support documented in `docs/setup.md`) [3](#0-2) .

`GitHubApp#verify_webhook_signature` then does: [4](#0-3) 

Note line 77: `return true unless webhook_secret` — if the organization picked via the attacker-controlled `repository.owner.login` has no `webhook_secret` configured (the setup docs explicitly mark it "optional": [5](#0-4) ), signature verification is bypassed entirely and the request is treated as verified regardless of the actual `X-Hub-Signature` header.

Once `verify_signature` passes, `WebhooksController#create` dispatches the *entire* raw payload to handlers unmodified: [6](#0-5) 

But every handler resolves the target `Repository`/`Stack` using a *different* field of the same payload — `repository.full_name`, not `repository.owner.login`: [7](#0-6) [8](#0-7) 

Because `repository.owner.login` (used to pick the authenticating org/secret) and `repository.full_name` (used to pick the acted-upon repository) are two independent keys inside the same unauthenticated JSON body, an attacker can set them to different values. Concretely: pick any configured organization `orgA` that has no `webhook_secret` set (blank/omitted, an explicitly supported configuration per the setup docs), put `repository.owner.login = "orgA"` (or `organization.login = "orgA"`) to trip the `return true unless webhook_secret` bypass, while setting `repository.full_name = "victim-org/victim-repo"` — a repository belonging to a completely different, secret-protected organization managed by the same Shipit instance. `Handler#repository_name` / `Repository.from_github_repo_name` will happily resolve and act on `victim-org/victim-repo` [9](#0-8) , even though the request was never authenticated for that organization at all.

This lets an unauthenticated network attacker forge:
- `push` events, driving `PushHandler#process` to call `stack.sync_github(expected_head_sha:)` on victim stacks [10](#0-9) .
- `status` events, driving `Commit#create_status_from_github!` to inject fabricated CI/CD statuses on victim commits [11](#0-10) .
- Similarly `check_suite`, `pull_request`, and `membership` events for the victim repository/org, since none of these handlers re-validate that `repository.full_name`'s owner matches the org that was actually used for signature verification.

### Impact Explanation
This breaks the authentication boundary the whole `verify_signature` filter is meant to enforce: a webhook is supposed to be provably from GitHub for the specific organization/repository it claims to describe. Here, the org used to *select the trust anchor* (secret) and the repository that is *actually mutated* are decoupled, so an attacker who only knows (or exploits) one loosely-configured/secret-less organization in a multi-org Shipit deployment can forge webhook events against every other organization/repository hosted on the same instance — including ones with correctly configured, secret-protected webhooks. This can falsify commit statuses that gate merges/deploys and drive `sync_github`, i.e., influence deploy/merge state without any GitHub-issued signature for the targeted repository — matching the High-impact criteria (unauthenticated write into stack/task state that should require GitHub-authenticated webhook delivery).

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (explicitly documented/supported feature), and (2) at least one configured organization lacking a `webhook_secret` (explicitly documented as "optional"). Given both are legitimate, documented configurations, the attack requires no credentials, no session, and no knowledge of any secret — a bare unauthenticated HTTP POST to `/webhooks` suffices, making likelihood high wherever such a deployment exists.

### Recommendation
Bind the "authenticated organization" to the "repository acted upon" as an equality check before dispatching to handlers: after resolving `github_app` for `repository_owner`, verify that `repository.full_name`'s owner segment equals `repository_owner` (case-insensitively) and reject (422) on mismatch. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for organizations that are not the sole/default org — either require a secret for every configured organization in multi-org mode, or fail closed instead of returning `true`.

### Proof of Concept
1. Configure Shipit in multi-org mode with two organizations: `orgA` (no `webhook_secret` set) and `orgB` (has a `webhook_secret`, hosting `orgB/victim-repo` with an active stack).
2. POST to `/webhooks` with header `X-Github-Event: status` and any/garbage `X-Hub-Signature`, and body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "organization": { "login": "orgA" },
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank), so `head(422)` is never called.
4. `create` dispatches the payload; `StatusHandler` looks up commits by `sha` and calls `create_status_from_github!`, injecting a forged, "successful" status on `orgB/victim-repo`'s commit — despite the request never being validated against `orgB`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
