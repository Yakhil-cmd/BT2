### Title
Webhook signature verified against `repository.owner.login`'s secret while provisioning acts on a different, attacker-chosen `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate the request using `params.dig('repository', 'owner', 'login')`, while `OpenedHandler#repository` resolves the actual `Shipit::Repository` to provision against using the independent field `params.repository.full_name`. Because both fields live in the same attacker-supplied JSON body and GitHub's signature only proves byte-for-byte integrity relative to whichever secret is looked up, an attacker who controls their own org's webhook secret can desynchronize these two fields to make Shipit provision a review stack under a repository they do not own or control.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`params.dig('repository','owner','login')` (used in `verify_signature` to pick `Shipit.github(organization: ...)` and thus the `webhook_secret`) `==` the owner implied by `params.repository.full_name` (used in `OpenedHandler#repository` via `Shipit::Repository.from_github_repo_name`).

Code path:
- `WebhooksController` runs `before_action ... :verify_signature` [1](#0-0) , which computes `repository_owner` strictly from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) [2](#0-1) , then fetches the org-specific `GitHubApp` and validates the raw body against that org's `webhook_secret` via HMAC-SHA1 [3](#0-2)  and [4](#0-3) .
- After signature verification succeeds, `create` dispatches the parsed body to handlers [5](#0-4) .
- `OpenedHandler#process` calls `provision?` then constructs `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [6](#0-5) .
- `repository` is resolved independently, from `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name` [7](#0-6) .

Root cause: the signature-selection field (`repository.owner.login`) and the provisioning-target field (`repository.full_name`) are two separate leaves of the same attacker-supplied JSON. GitHub itself keeps these consistent for genuine webhooks, but nothing in this engine enforces that `repository.full_name` starts with `repository.owner.login` before trusting it for repository resolution. An attacker who owns/administers their own GitHub org "org-a" (and has therefore configured Shipit's webhook + `webhook_secret` for org-a legitimately, or otherwise knows it because it's their own org) can hand-craft the POST body so `repository.owner.login = "org-a"` while `repository.full_name = "org-b/victim-repo"`. `verify_signature` looks up `Shipit.github(organization: "org-a")`, computes the HMAC using org-a's `webhook_secret` (known to attacker), and it matches because the attacker signed the exact raw bytes they are sending. The signature check therefore passes despite the payload targeting an unrelated org's repository.

None of the existing guards catch this: `verify_signature` doesn't cross-check `owner.login` against `full_name`; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `OpenedHandler` only requires `repository.full_name` be a String, with no ownership constraint [8](#0-7) ; and `provision?`/`respond_to_pull_request_opened?` only gate on org B's own `review_stacks_enabled`/`provisioning_behavior_allow_all?` flags, which is precisely the condition the attacker is depending on and does not re-validate the requesting org.

### Impact Explanation
If exploited against a target org B configured with `review_stacks_enabled: true` and `provisioning_behavior_allow_all?`, the attacker causes `ReviewStackAdapter#find_or_create!` to create a new `Stack` scoped to B's repository, using entirely attacker-controlled `pull_request.head.sha`, `head.ref`, and `title`. This is a cross-tenant forgery: a payload authenticated under org A's credentials mutates state (creates a stack, and downstream, potentially triggers deploy of the attacker's `head.sha`) that should require org B's authorization. This matches the Critical category "a payload for one repository mutating another's stack" / "unauthorized deploy" since review stack creation is a precursor to deployment of attacker-supplied code. It is repeatable against any Shipit-hosted org that has permissive review-stack provisioning, using only the attacker's own org's webhook secret, and scales to any number of target repositories/orgs configured similarly.

### Likelihood Explanation
Preconditions: the attacker needs their own GitHub org/webhook configured in Shipit (or any org whose `webhook_secret` they know — which they trivially do for their own org), and the victim org B must have `review_stacks_enabled: true` and permissive provisioning behavior (`allow_all`, or satisfy the label conditions, which the attacker fully controls anyway on their own crafted PR body). No GitHub API call is needed — the attacker crafts and POSTs raw JSON directly to `/webhooks` with a valid HMAC computed against their own secret. This requires no Shipit session, API token, or GitHub credentials beyond the attacker's own org's webhook secret, matching the allowed attacker capability set. Cost is a single crafted HTTP POST; it is fully repeatable.

### Recommendation
In `WebhooksController#verify_signature` or `OpenedHandler#repository`, enforce that the org used to select the webhook secret matches the org embedded in `repository.full_name` — e.g., reject the request (or refuse to resolve a `Repository`) unless `params.dig('repository','full_name').to_s.split('/').first.casecmp?(repository_owner)`. More robustly, resolve the target `Shipit::Repository` first, verify that the repository's owning organization's `GitHubApp` (not `repository_owner`'s) is the one whose secret validated the signature, and only then run handlers.

### Proof of Concept
Minitest (`test/controllers/webhooks_controller_test.rb`, no live GitHub):
1. Fixtures: create/stub Shipit config so org `"org-a"` has `webhook_secret = "secret-a"`; ensure `Shipit::Repository` fixture for `"org-b/victim-repo"` exists with `review_stacks_enabled: true` and `provisioning_behavior: allow_all` (or equivalent fixture already provided per the prompt).
2. Build `pull_request` `opened` payload body with:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/victim-repo"`
   - `pull_request.head.sha`, `head.ref`, `title` set to attacker-controlled values.
3. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', "secret-a", raw_body)`.
4. POST to `/webhooks` with header `X-Github-Event: pull_request` and the computed signature; assert response is `200`/`204` (not `422`).
5. Assert equality check both sides: before request, `repository_owner_used_for_signature = "org-a"` and `repository_targeted_for_provisioning = "org-b"` are unequal; assert a new `Shipit::Stack` row now exists scoped to the `"org-b/victim-repo"` `Repository` fixture (`Shipit::Repository.from_github_repo_name("org-b/victim-repo").review_stacks.count` increased), proving org A's signed request mutated org B's data.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
