### Title
Webhook signature verification is keyed to the attacker-controlled `repository_owner`/organization while handlers act on an unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify a webhook against using an **unverified** field taken straight out of the incoming payload (`repository.owner.login` / `organization.login`). Once verification "passes," the very same raw payload is handed to event handlers that resolve the target `Stack`/`Repository` from a completely different, equally unverified field (`repository.full_name`), with no requirement that the two correspond to the same organization. If any configured GitHub App organization has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` trivially returns `true`, letting an unprivileged attacker forge a webhook "from" that organization while making it operate on any repository/stack tracked by Shipit, including ones belonging to a completely different, properly-secured organization.

### Finding Description
- `WebhooksController#verify_signature` computes `repository_owner` from the raw, unauthenticated JSON body and uses it to pick the GitHub App config to verify against: [1](#0-0) [2](#0-1) 

- `Shipit.github(organization:)` only actually uses that caller-supplied `organization` when the installation is running in the documented "multiple GitHub Applications" mode (`github_default_organization` present); it looks up the org-specific config purely by the org name string coming from the payload: [3](#0-2) 

- `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's config has no `webhook_secret` configured: [4](#0-3) 

- The multi-org setup documented for this engine explicitly allows a `webhook_secret` to be left blank per organization: [5](#0-4) 

- After the (bypassable) signature check, `WebhooksController#create` re-parses the raw body and dispatches it, unmodified, to registered handlers: [6](#0-5) 

- Handlers determine which `Stack`s to mutate using `repository.full_name` from that same payload - a field wholly independent from the `repository_owner` used for signature selection, and never checked for organization consistency: [7](#0-6) [8](#0-7) 

- Concretely, `StatusHandler` writes a commit status for any commit matching `params.sha` across the whole install, with no repository/org scoping at all: [9](#0-8) 

- `PushHandler` triggers a full `GithubSyncJob` resync for any stack whose repository matches `repository.full_name`: [10](#0-9) 

**The broken binding, stated as an equality that the engine assumes but never enforces:**
`organization used to select the verifying webhook_secret (repository_owner)` == `organization owning the repository the handler actually mutates (repository.full_name)`.

Before the attack: a legitimately configured org's App verifies its own webhooks and handlers only ever see payloads whose `repository.full_name` genuinely belongs to that org, because GitHub itself only sends real webhooks for repos it manages.

After the attack: an attacker POSTs directly to `/webhooks` (no GitHub involved) with `repository.owner.login` (or `organization.login`) set to any org name configured in `secrets.yml` that happens to have `webhook_secret` unset/blank, and `repository.full_name` (and any other handler-parsed fields, e.g. `sha`, `state`, `ref`, `after`) set to target an arbitrary tracked repository belonging to a *different*, properly-secured organization. `verify_signature` passes unconditionally (because the selected org has no secret), and the handler acts on the attacker-chosen repository.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary called out in the analog rules, and rises to a **Critical** impact under the stated criteria (unauthorized deploy/merge / cross-repository writes):
- `StatusHandler` lets the attacker fabricate a passing (`state: "success"`) commit status on any commit of any tracked repository. If that stack's `ci.require`/merge-queue configuration gates deploys or the merge queue on that status context, this can unblock an otherwise-blocked deploy or auto-merge - an unauthorized deploy/merge.
- `PushHandler`/`GithubSyncJob` can be forced against an arbitrary stack, causing Shipit to resync/append attacker-asserted commit metadata for a repository outside the "authenticated" organization's scope - a cross-repository write not authorized by that organization's credentials.
- The root cause is purely in this engine's own code path (`WebhooksController`, `GitHubApp#verify_webhook_signature`, `Shipit.github`, `Handler#stacks`), not a third-party gem defect, and requires no session, API token, or GitHub App private key - only knowledge of an org name present in `secrets.yml` (often visible in setup docs/config templates) that has no `webhook_secret` configured, which the engine's own documented multi-org setup permits.

### Likelihood Explanation
Exploitability is conditional on deployment configuration: the installation must use the multi-org GitHub App configuration format (`github_default_organization` non-nil) with at least one configured organization lacking a `webhook_secret`. This is an explicitly documented, supported configuration state (see `docs/setup.md` "Using Multiple Github Applications" and the shipped `config/secrets.development.shopify.yml` fixture, which sets `webhook_secret: # nil` for both sample orgs), so it is a realistic operational state during onboarding of a new organization before its webhook secret is set, not a purely theoretical one. Single-org installations (the common case, where `github_default_organization` is `nil`) are not affected because `Shipit.github` ignores the payload-derived `organization:` argument entirely in that mode.

### Recommendation
- Never select the verification secret using data taken from the unauthenticated request body; verification must be tied to a secret that is not itself chosen by the same payload it is meant to validate.
- Change `GitHubApp#verify_webhook_signature` to fail closed (return `false`/reject) when `webhook_secret` is blank, rather than treating an absent secret as "always verified."
- After signature verification succeeds for organization `O`, enforce that every handler only mutates repositories/stacks whose `Repository#owner` equals `O` (or otherwise scope handler payload parsing to repositories that are actually installed under the authenticated GitHub App), instead of trusting `repository.full_name` independently.

### Proof of Concept
Preconditions: engine deployed with multi-org config, e.g.:
```yaml
production:
  github:
    orgWithNoSecret:
      app_id: 1
      installation_id: 1
      webhook_secret:      # left blank
    victimOrg:
      app_id: 2
      installation_id: 2
      webhook_secret: real-secret-value
```
And a stack tracked under `victimOrg/victim-repo`.

Attacker request (no GitHub, no valid signature needed):
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": { "owner": { "login": "orgWithNoSecret" }, "full_name": "victimOrg/victim-repo" },
  "sha": "<sha of a real commit on victimOrg/victim-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
Trace:
1. `repository_owner` resolves to `"orgWithNoSecret"` (`app/controllers/shipit/webhooks_controller.rb:59-62`).
2. `Shipit.github(organization: "orgWithNoSecret")` returns the `GitHubApp` for that org, whose `webhook_secret` is blank (`lib/shipit.rb:170-200`).
3. `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`); `head(422)` is never called.
4. `create` re-parses the body and dispatches it to `StatusHandler` (`app/controllers/shipit/webhooks_controller.rb:10-15`).
5. `StatusHandler#process` finds the commit by `sha` (regardless of repository) and calls `create_status_from_github!`, writing a forged `"success"` status onto the `victimOrg/victim-repo` commit (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).

If `victimOrg/victim-repo`'s stack requires that status context for deploy/merge, this forged status can unblock deployment or the merge queue despite the attacker having no credentials for `victimOrg`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
