### Title
Membership-webhook authorization escalation into `Shipit.github_teams` via unauthenticated signature bypass - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit.github_teams` (used by `User#authorized?` to gate access to the entire application) is populated purely from `Team` rows that any `membership` webhook can mutate [1](#0-0) , and the webhook's authenticity check silently no-ops whenever the target organization has no `webhook_secret` configured — a state the docs explicitly present as an optional, supported configuration [2](#0-1) [3](#0-2) . This breaks the binding "organization that authenticated the webhook" = "team/membership state that is written," letting an unprivileged network attacker add themselves to any GitHub team, including one listed in `Shipit.github_teams`.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App config for the org named in the attacker-supplied JSON body (`repository_owner`, itself just `params.dig('organization','login')` when no `repository` key is present) and calls `verify_webhook_signature` [4](#0-3) . That method is a deliberate bypass when no secret is set:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

`webhook_secret` is documented as optional in both the setup guide and the example secrets file [5](#0-4) [6](#0-5) , so a compliant, documented deployment can legitimately have it unset for one or more configured organizations.

When verification is bypassed this way, `create` dispatches the raw, fully attacker-controlled JSON straight to handlers [7](#0-6) . The `membership` event is handled by `MembershipHandler#process`, which creates/looks up a `Team` purely from payload fields and adds the attacker-named `member` to it with no further verification against real GitHub state:

```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'added'
    team.add_member(member)
  ...
``` [8](#0-7) 

`Shipit.github_teams` — the authorization gate checked on every request via `User#authorized?` and `Authentication#force_github_authentication` — is derived directly from these `Team` records by handle (`organization/slug`) [1](#0-0) [9](#0-8) [10](#0-9) . If the organization/slug named in the forged webhook matches (or is created to match, via `find_or_create_team!`) one of the org's configured `oauth.teams` handles, the forged `Membership` row makes `authorized?` return true for that attacker-controlled `User#login` — even though GitHub itself never granted that membership.

This is the direct analog of the reported bug class: a field is acted upon (`team`/`member`/`organization` in the webhook payload) that is never actually covered by any verified signature (because none is required when `webhook_secret` is blank), producing a state (team membership) that diverges from and overrides the real, GitHub-verified source of truth, exactly as the report's unclaimed-fee portion diverged from the real reserve state.

### Impact Explanation
This directly matches the specified High-severity impact class: "escalation into `Shipit.github_teams` authorization." Because `authorized?` is the sole application-wide access gate for the Rails engine's UI/API session flow, an attacker who forges a `membership` `added` webhook for an org with no configured `webhook_secret` can grant themselves (or any GitHub login they choose to pre-provision a `User` for) membership in a team that `Shipit.github_teams` trusts, bypassing the "must be a member of X" restriction entirely without ever authenticating through GitHub OAuth.

### Likelihood Explanation
No credential, session, `ApiClient` token, or repository access is required — only knowledge that a target org has no `webhook_secret` configured (a documented, legitimate, and reasonably common configuration, especially for single-org/simple installs) and the org handle/team slug names listed in `Shipit.github_teams`, which are visible in the forbidden-access error message itself: `render(plain: "You must be a member of #{team_list} ...")` [11](#0-10) . This makes the attack straightforward to mount for anyone who can reach the `/webhooks` endpoint.

### Recommendation
Require `webhook_secret` to be present for every configured organization (fail closed rather than fail open when it is blank), or, independent of that, have `MembershipHandler` re-verify the claimed team/membership state against the live GitHub API (or restrict `Team`/`Membership` mutation to trusted, GitHub-confirmed data) rather than trusting the webhook payload verbatim for authorization-relevant records.

### Proof of Concept
1. Deploy Shipit with an organization config where `github.webhook_secret` is left blank (a supported, documented configuration) and `oauth.teams` includes `"acme/admins"`.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "admins", "slug": "admins", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "acme"},
  "member": {"login": "attacker-login"}
}
```
No `X-Hub-Signature` needs to be valid because `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is nil.
3. `MembershipHandler#process` creates/finds `Team(organization: "acme", slug: "admins")` and adds `User(login: "attacker-login")` as a member.
4. Attacker completes normal GitHub OAuth login as `attacker-login`; `authorized?` now returns `true` because `attacker-login` is a member of the `Team` matching `Shipit.github_teams`, granting full application access despite never having real GitHub membership in `acme/admins`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
