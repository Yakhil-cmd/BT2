## Finding

### Title
Missing length validation before `address::from_bytes` on Ethereum→Sui bridge claim causes permanent fund lock - (File: `crates/sui-framework/packages/bridge/sources/bridge.move`)

### Summary
The external report's root cause is a missing structural/length check before a fixed-size decode (`abi.decode(modifiedPacket, (address, bytes))`) that reverts when the input isn't shaped as expected. The Sui bridge has a structurally analogous pattern: on the EVM→Sui claim path, the `target_address` field of a `TokenTransferPayload` is converted directly into a Sui `address` via `address::from_bytes` without any length assertion at that call site, even though the field is carried through the wire format as an arbitrary-length, attacker/user-influenced byte vector.

### Finding Description
`claim_token_internal` extracts the payload and derives the recipient directly: [1](#0-0) 

The `target_address` bytes originate from `extract_token_bridge_payload`/`extract_token_bridge_payload_v2`, which peel it with `bcs::peel_vec_u8()` — an arbitrary-length vector, not a fixed 32-byte value: [2](#0-1) 

Unlike the Sui→Ethereum direction, which explicitly enforces `target_address.length() == EVM_ADDRESS_LENGTH` before constructing the outbound message: [3](#0-2) 

there is no equivalent assertion anywhere in the `approve_token_transfer` / `claim_token_internal` path (bridge.move lines 301-408) that the `target_address` extracted from an EVM-originated message is exactly 32 bytes (the required length for a Sui `address`) before it is passed to `address::from_bytes`. The comment in `message.move` even acknowledges the assumption is fragile: *"Note: `bcs::peel_vec_u8` happens to work here because `sender_address` and `target_address` are no longer than 255 bytes"* — it only guarantees the length fits in a `u8`, not that it equals 32.

### Impact Explanation
If the Ethereum-side deposit call (`bridgeERC20`/`bridgeETH` on `SuiBridge.sol`) does not itself enforce that the Sui recipient bytes are exactly 32 bytes long before emitting the deposit event, a malformed `target_address` becomes baked into the immutable on-chain event, gets validated and quorum-signed by the bridge committee (since nothing in the Move approval/claim path checks the length), and then permanently fails at `address::from_bytes` inside `claim_token_internal` every time a claim is attempted. Because the underlying asset is already locked/escrowed in the Ethereum vault at deposit time, this would result in a **permanent fund lock** — no path exists to ever produce a valid `owner` address to complete the mint/transfer, and the record can never be marked claimed. This maps to the explicitly allowed "permanent fund lock" High/Medium impact category.

### Likelihood Explanation
I was not able to fully verify, within the available indexed context, whether `SuiBridge.sol`'s deposit functions (`bridgeERC20`/`bridgeETH`) independently validate that the caller-supplied Sui target address is exactly 32 bytes before emitting the `TokensDeposited` event that the bridge committee signs. If such a check exists on the Solidity side, this finding is fully mitigated at the source and would not be reachable in practice. The Move-side code alone shows no defense-in-depth length check at the `address::from_bytes` call site, so this represents a real gap in layered validation, but I could not confirm definitively whether it is currently exploitable end-to-end without inspecting the exact `SuiBridge.sol` deposit implementation (not available in the retrieved snippets). This uncertainty should be resolved with a Devin session that reads the full `bridge/evm/contracts/SuiBridge.sol` deposit functions and the bridge client's construction of `MoveTypeBridgeMessage`/`BridgeAction::EthToSui*` before treating this as confirmed.

### Recommendation
Add an explicit assertion in `bridge.move`'s `approve_token_transfer` or `claim_token_internal` (and/or in `extract_token_bridge_payload`/`_v2` in `message.move`) that `token_target_address().length() == 32` whenever the target chain is Sui, mirroring the existing `EVM_ADDRESS_LENGTH` check used for the reverse direction. This closes the gap regardless of what the Ethereum contract does, and converts any malformed message into an immediate, informative abort at `approve_token_transfer` time rather than a silent permanent lock discovered only at claim time.

### Proof of Concept
Conceptual (not independently executed): construct/relay an EVM `TokensDeposited` event (or a `SuiToEthOnChainBcsPayload`-equivalent for the Eth→Sui direction) where `eth_address`/`target_address` is not exactly 32 bytes. If `SuiBridge.sol` does not reject this at deposit time, the committee will sign and `approve_token_transfer` will accept it (no length check exists in `bridge.move`/`message.move`). Any subsequent call to `claim_token`/`claim_and_transfer_token` will abort inside `address::from_bytes(token_payload.token_target_address())` (bridge.move line 560) forever, while the deposited funds remain locked in the Ethereum vault.

// Note: `bcs::peel_vec_u8` *happens* to work here because
// `sender_address` and `target_address` are no longer than 255 bytes.
// Therefore their length can be represented by a single byte.
// See `create_token_bridge_message` for the actual encoding rule.
public fun extract_token_bridge_payload(message: &BridgeMessage): TokenTransferPayload {
    assert!(message.message_version() == 1, EInvalidMessageVersion);
    let mut bcs = bcs::new(message.payload);
    let sender_address = bcs.peel_vec_u8();
    let target_chain = bcs.peel_u8();
    let target_address = bcs.peel_vec_u8();
    let token_type = bcs.peel_u8();
    let amount = peel_u64_be(&mut bcs);

    chain_ids::assert_valid_chain_id(target_chain);

    assert!(bcs.into_remainder_bytes().is_empty(), ETrailingBytes);

    TokenTransferPayload {
        sender_address,
        target_chain,
        target_address,
        token_type,
        amount,
    }
}
