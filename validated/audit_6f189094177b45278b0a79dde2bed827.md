### Title
Double-completion of async iteration callback in private payment chain handling due to missing `return` after error path - ([File: network.js])

### Summary
`handleSavedPrivatePayments()`'s inner `validateAndSave()` closure in `network.js` fails to `return` after handling an exception from `objectHash.getBase64Hash()`, causing the shared `async.each` iterator callback `cb` (via `deleteHandledPrivateChain`) to be invoked twice for the same row — once from the `catch` block and once again from the fall-through call to `privatePayment.validateAndSavePrivatePaymentChain()`. This mirrors the CVE-2021-47589 root cause: two independent error/cleanup paths that converge and act on the same resource because an early exit was omitted, resulting in the same "free"/cleanup routine (here, `deleteHandledPrivateChain` and the `async.each` completion callback) being invoked more than once.

### Finding Description
In `handleSavedPrivatePayments()`: [1](#0-0) 

```
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }

    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
        ifOk: function(){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifError: function(error){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifWaitingForChain: function(){ ... cb(); }
    });

```

`deleteHandledPrivateChain(unit, message_index, output_index, cb)` deletes the `unhandled_private_payments` row and then invokes `cb()`: [2](#0-1) 

If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (e.g. on a malformed/unserializable `payload` sent as part of a private payment element), the `catch` block calls `deleteHandledPrivateChain(...)`, which itself invokes `cb()` — the `async.each` per-item completion callback. Execution does not stop there: control falls through to the code after the `try/catch`, where `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` is still called with the same row, and each of its outcome branches (`ifOk`, `ifError`) also calls `deleteHandledPrivateChain(..., cb)`, invoking `cb()` a second time for the same `async.each` item.

This is invoked from `handleOnlinePrivatePayment` -> `savePrivatePayment` (`unhandled_private_payments` insert path) whenever a peer/cosigner/hub sends a private payment chain, and periodically via `findAndHandleJointsThatAreReady`/timers that call `handleSavedPrivatePayments`: [3](#0-2) [4](#0-3) 

The `saved_private` mutex lock guards this whole batch of chains: [5](#0-4) 

`async` invokes the outer completion function once the internal counter reaches the number of items; calling one item's `cb` twice decrements/settles that counter early, causing the batch-completion callback (which calls `unlock()` on `saved_private` and emits `new_my_transactions`) to fire before other private-payment chains queued in the same batch have actually finished being validated and saved: [6](#0-5) 

Because `saved_private` unlocks prematurely relative to the true completion of all chains in the batch, `handleSavedPrivatePayments` can be invoked concurrently against the same or overlapping private payment elements before the previous run has fully persisted them, undermining the serialization that this lock exists to guarantee for private (indivisible/divisible) asset chains.

### Impact Explanation
The mutex `saved_private` exists specifically to serialize the validation/saving of privately-transmitted asset payment chains so that concurrent processing of the same unhandled private payment rows cannot occur. Prematurely releasing this lock (via the double-`cb()` bug) reintroduces the race the lock was meant to prevent: a second `handleSavedPrivatePayments` pass (e.g., triggered by another `findAndHandleJointsThatAreReady` call or manual re-check) could begin operating on private payment chains that are still mid-validation/mid-save, which for indivisible-asset private chains (see `validateAndSavePrivatePaymentChain`) directly risks state corruption of the wallet's private-chain bookkeeping — potentially permitting the same private output to be accepted/spent through two overlapping code paths (double-spend of a private, unconfirmed output) or causing the wallet to silently drop/lose track of a legitimately received private payment (fund loss/freezing from the recipient's perspective).

### Likelihood Explanation
The trigger condition — `objectHash.getBase64Hash()` throwing on `objHeadPrivateElement.payload` — is reachable by any private-payment counterparty or hub relaying a private payment chain to a wallet, since `payload` originates from attacker-controlled JSON deserialized from the network message (`JSON.parse(row.json)`), and `getSourceString`/`getJsonSourceString` can throw on certain malformed/edge-case structures (e.g., unexpected types not handled by the source-string serializer). No privileged access is required: any device paired with the victim wallet, or any hub relaying private payments, can supply a payload of this kind. However, exploiting the resulting race into a concrete double-spend requires additional timing coordination (a second concurrent trigger of `handleSavedPrivatePayments`) which is plausible but not guaranteed on every occurrence, so likelihood is assessed as moderate rather than trivial.

### Recommendation
Add a `return` statement immediately after the `catch` block's `deleteHandledPrivateChain(...)` call in `validateAndSave()` so that `privatePayment.validateAndSavePrivatePaymentChain(...)` is never invoked when `getBase64Hash` has already failed and `cb()` has already been called:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```
Additionally, consider hardening `deleteHandledPrivateChain`/the `async.each` iteratee to guard against double invocation (e.g., an idempotency flag) as defense-in-depth against future similar mistakes.

### Proof of Concept
1. A paired device or hub sends a private payment (`private_payment` message) whose head chain element's `payload` is crafted to make `getSourceString`/`getJsonSourceString` throw when hashed (e.g., a payload field of an unsupported type that the source-string serializer cannot handle).
2. `handleOnlinePrivatePayment` stores it via `savePrivatePayment`, inserting a row into `unhandled_private_payments`. [3](#0-2) 
3. When `handleSavedPrivatePayments` next processes this row, `validateAndSave()` executes; `objectHash.getBase64Hash` throws, hitting the `catch` block, which calls `deleteHandledPrivateChain(...)` → `cb()` (iteration 1 complete).
4. Execution falls through (no `return`) to call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`; whichever outcome fires (`ifOk`/`ifError`) calls `deleteHandledPrivateChain(...)` again → `cb()` a second time for the same item.
5. `async.each`'s internal completion counter is decremented twice for one item, causing the outer completion callback (which calls `unlock()` on the `saved_private` mutex) to fire prematurely relative to the true number of outstanding chains in the batch, opening a window for concurrent/overlapping processing of private payment chains that the mutex was meant to prevent.

Note: I was not able to execute this in a live environment; the analysis is based on static code review of the cited files. The exact conditions under which `getSourceString`/`getJsonSourceString` throw on adversarial input were not fully enumerated within available context — a Devin session with full repository access could construct and verify a concrete crashing payload.
