### Title
API impersonation of arbitrary Shipit users via unauthenticated `X-Shipit-User` header - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Shipit::Api::BaseController#identify_user` derives `current_user` purely from the client-supplied `X-Shipit-User` request header, performing a case-insensitive `login` lookup with no cryptographic binding to the authenticated `ApiClient`. Any holder of a valid, low-privilege `ApiClient` token can set this header to an arbitrary existing user's login and have their mutating action (lock, comment, rollback, deploy trigger) attributed to that victim.

### Finding Description
The claimed binding is: `current_user == identity of the ApiClient that authenticated this request` (or at minimum, an identity the requester actually controls). In the actual code:

```ruby
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
``` [1](#0-0) 

`authenticate_api_client` only verifies the HTTP Basic token against `ApiClient.authenticate`; it establishes no relationship between the `ApiClient` and any `User` account:

```ruby
def authenticate_api_client
  @current_api_client = if Shipit.disable_api_authentication
                          UnlimitedApiClient.new
                        else
                          BasicAuth.authenticate(request) do |*parts|
                            token = parts.select(&:present?).join('--')
                            ApiClient.authenticate(token)
                          end
                        end
  ...
end
``` [2](#0-1) 

`current_user` is then consumed directly by mutation endpoints (locks, rollbacks, tasks, deploys, merge requests, release statuses) to attribute the actor of the action, e.g. `Shipit::Api::LocksController`, `Shipit::Api::RollbacksController`, `Shipit::Api::TasksController`, `Shipit::Api::DeploysController`, `Shipit::Api::MergeRequestsController`. None of these controllers, nor `require_permission!`/`check_permissions!` on `ApiClient`, verify that the `X-Shipit-User` value corresponds to any identity actually proven by the request — `check_permissions!` only checks operation/scope permissions of the `ApiClient` token itself, not the impersonated user. Since `identify_user` does a straight `User.where(...)` lookup keyed only on attacker-controlled header content, and any legitimately-scoped `ApiClient` token (even one with minimal permissions) passes `authenticate_api_client`, an attacker can set `X-Shipit-User: <victim-login>` on any mutating request to have the resulting record (lock, comment, deploy trigger, rollback) permanently attributed to the victim instead of themselves.

### Impact Explanation
This is a scoped identity/attribution forgery: an attacker holding any valid `ApiClient` token can cause database records (`Lock#user`, `Task#user` triggering a deploy/rollback, `Comment#user`, etc.) to name an arbitrary existing Shipit user as the actor, without that user's knowledge or consent. This lets an attacker frame another Shipit user for a deploy, lock, or rollback, and could subvert any downstream logic that trusts `current_user` for audit trails or additional authorization decisions. It does not, by itself, grant the attacker permissions beyond what their own `ApiClient` token already has (permission checks are still gated by `current_api_client.check_permissions!`), so it is an attribution/impersonation issue rather than a full authentication bypass or privilege escalation into `Shipit.github_teams`.

### Likelihood Explanation
Preconditions are minimal: attacker needs only a legitimately issued, low-privilege `ApiClient` token (which per the threat model here is assumed available/in-scope for the "attacker action") and knowledge of any existing victim `User#login` (logins are often public, e.g., GitHub usernames). No GitHub secrets, webhook secrets, or session access are required. The attack is trivially repeatable against any endpoint that reads `current_user`, for every request, against any existing user.

### Recommendation
Remove header-based user impersonation entirely, or bind it cryptographically: require `ApiClient` records to be associated with a specific `User` (creator) and derive `current_user` from that association instead of trusting `X-Shipit-User`; if header-based attribution must remain for trusted internal integrations, restrict it to `ApiClient`s explicitly flagged as trusted/service accounts and audit-log the override, and require out-of-band verification (e.g., a signed assertion) rather than a plain header value.

### Proof of Concept
Minitest integration test outline under `test/controllers/api/locks_controller_test.rb` (or similar mutation endpoint):
1. Create `victim = shipit_users(:walrus)` (or any fixture user) and a separate `api_client` with minimal/no relation to `victim`, authenticated via its own token.
2. `authenticated_post stack_lock_path(stack), params: { description: 'x' }, headers: { 'X-Shipit-User' => victim.login }`.
3. Assert `Lock.last.user == victim` even though the request was authenticated by `api_client`, which is not associated with `victim` in any way — i.e., assert `binding_before` (`current_user` should equal the identity that authenticated the request, e.g. `nil`/`AnonymousUser` or the `ApiClient`'s own associated user) diverges from `binding_after` (`current_user == victim`), demonstrating the forgeable equality `identify_user(header) == User.find_by(login: attacker_supplied_value)` regardless of the authenticating `ApiClient`.
