### Title
Webhook signature verification uses `repository.owner.login` to select the GitHub App secret, but handlers act on the independent `repository.full_name` field, allowing an org-A webhook-secret holder to forge events for org B's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks *which* organization's `webhook_secret` to validate a request against using `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`). The handlers that actually act on the payload (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, pull-request handlers, etc.) resolve the target `Repository`/`Stack` from a *different* field of the same body: `repository.full_name` (see `Shipit::Webhooks::Handlers::Handler#repository_name`). Because Shipit explicitly supports hosting multiple, independently trusted GitHub organizations in one instance (`docs/setup.md`, "Using Multiple Github Applications"), each with its own `webhook_secret`, the field used to select the verifying secret and the field used to select the acted-upon repository are not bound together by the verification.

### Finding Description
`verify_signature` in [1](#0-0)  does:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

`repository_owner` is computed from the same request body being verified: [2](#0-1) .

Downstream, every handler resolves its target stacks from `repository.full_name`, a sibling field of the payload, independent of `repository.owner.login`: [3](#0-2) .

`Shipit.github_app.rb#verify_webhook_signature` only proves that the sender knows the secret associated with the organization named in the payload's `owner.login`/`organization.login` field — it proves nothing about consistency between that org and the `full_name` repository the handlers subsequently mutate: [4](#0-3) .

In a multi-org deployment (explicitly documented and supported, see `docs/setup.md` lines 182-209), each organization owner independently knows its own `webhook_secret` (it is generated when creating that org's GitHub App/webhook, per `docs/setup.md` lines 30 and 119). An admin of org A can therefore craft an arbitrary JSON body directly to `/webhooks` (not proxied through GitHub) with:
- `repository.owner.login` (or `organization.login`) = `"orgA"` — so `verify_signature` selects org A's `github_app` and validates successfully because the attacker computed the HMAC with org A's own secret.
- `repository.full_name` = `"orgB/some-repo"` — a repository belonging to a different, unrelated organization hosted on the same Shipit instance.

This breaks the binding "organization that authenticated == repository that is written": the signature only authenticates possession of org A's secret, but the handler acts on org B's repository/stacks.

### Impact Explanation
Depending on event type, this allows an org-A secret holder to affect org B's stacks without any authorization from org B:
- `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb`) triggers `stack.sync_github(expected_head_sha:)` on arbitrary org B stacks matched by branch name.
- `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb`) creates a commit status (`commit.create_status_from_github!`) for any commit sha across the instance — this can forge a "success" CI status on an org B commit, which can make that commit appear deployable.
- `CheckSuiteHandler` schedules check-run refreshes on org B stacks.
- `MembershipHandler`-style handlers can create/modify teams/memberships tied to org B.

Forged deployable-status/commit-status events can influence which commits are presented as safe to deploy on another organization's stack, and push/check-suite forgery can trigger unwanted internal state syncs on repositories the attacker does not own — an unauthorized cross-organization write into another tenant's deployment state. This satisfies the "cross-repository writes" / "unauthorized deploy" bar, though the most severe outcome (a forced deploy) still requires a human or automated policy on org B's side to act on the forged status.

### Likelihood Explanation
Requires the attacker to be an administrator/owner of *any one* organization/repository already onboarded to the shared Shipit instance (i.e., they legitimately know their own org's `webhook_secret`), and requires the deployment to host multiple orgs (an explicitly documented, supported configuration). No GitHub App private key, `api_clients_secret`, or Shipit session/API token is needed — only knowledge of a webhook secret the attacker was given for their own organization's webhook, plus the ability to POST directly to the shared `/webhooks` endpoint.

### Recommendation
Bind the field used to select the verifying secret to the field used to resolve the acted-upon repository: after selecting `github_app` via `repository_owner`, verify that `repository.full_name`'s owner segment equals `repository_owner` (or, better, resolve the target `Repository`/`Stack` first and confirm it belongs to the same organization/GitHub App installation that signed the payload) before dispatching to any handler.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `orgA` and `orgB`, each with distinct `webhook_secret` values, per `docs/setup.md`'s multi-org configuration.
2. As the administrator of `orgA` (who legitimately knows `orgA`'s `webhook_secret`), craft a JSON body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" },
  "sha": "<commit sha belonging to orgB stack>",
  "state": "success"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and set `X-Github-Event: status`.
4. POST directly to `https://<shipit-host>/webhooks`. `verify_signature` resolves `Shipit.github(organization: "orgA")` and validates successfully.
5. `StatusHandler` executes `Commit.where(sha: params.sha)` (matching the `orgB` commit) and calls `create_status_from_github!`, forging a status on `orgB`'s commit despite the request never being authenticated by `orgB`'s GitHub App/secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
