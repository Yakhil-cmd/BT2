## Title
Webhook signature verification is bound to `repository.owner.login`, but the resulting event handlers act on the `repository.full_name` field — allowing cross-organization/cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The reported bug class is a mismatch between the field a signature actually covers/authorizes and the field the code subsequently *acts on*. In this engine, `WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login`, while every webhook handler that resolves the target `Stack`/`Repository` uses the unrelated `repository.full_name` field from the same JSON body. In a multi-organization Shipit deployment, this breaks the binding `verified_organization == repository_acted_upon`.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config (and therefore the `webhook_secret` used for HMAC verification) using: [1](#0-0) 

and it derives that organization from: [2](#0-1) 

`Shipit.github(organization:)` supports per-organization GitHub App configs, each with its own independent `webhook_secret`: [3](#0-2) 

However, once the signature is accepted, the base `Handler` class (used by `PushHandler`, the `PullRequest` handlers, etc.) resolves which `Stack`/`Repository` to act on using a *different* field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

`PushHandler` then triggers a real write — a GitHub sync job — against whatever stacks match that `full_name`: [5](#0-4) 

`StatusHandler` is even less scoped: it doesn't call `stacks`/`repository_name` at all, and instead updates any `Commit` row whose `sha` matches, with no repository binding: [6](#0-5) 

Because verification authorizes based on `repository.owner.login` (mapped to a specific organization's secret) while the mutation is keyed on the independent `repository.full_name` value, an attacker who legitimately controls one organization's GitHub App/webhook secret in a multi-org Shipit instance (`github_app_config` keyed by org name) can:
1. Craft an arbitrary JSON body with `repository.owner.login` = their own org (so their own known `webhook_secret` verifies it), and
2. Set `repository.full_name` = `victim-org/victim-repo`.

The signature check passes using the attacker's own secret, and the handler then executes writes (`stack.sync_github`, commit status updates, PR label/state mutations) against the victim organization's `Stack`, which the attacker has no privilege over in Shipit (no `ApiClient` token, no repository write access, no membership).

Before vs after:
- Before (expected binding): `verified_organization(secret_used) == organization_owning(repository_acted_upon)`.
- After (attacker's crafted payload): `verified_organization = attacker_org`, but `repository_acted_upon = victim_org/victim_repo`.

### Impact Explanation
This is a cross-repository/cross-organization write performed by an unprivileged party with respect to the victim repository: they hold no Shipit `ApiClient` token, no GitHub write access to the victim repo, and no Shipit account for that stack — only their own, unrelated org's webhook secret. Depending on which handler is exercised this can force `GithubSyncJob` runs and commit records to be written for a victim `Stack` (`PushHandler`), or forge/alter CI status objects consumed by Shipit's deploy-safety checks (`StatusHandler`, unscoped by repository), or mutate pull-request/label state used to drive `ReviewStack` creation and merge-queue behavior (`PullRequest` handlers). This matches the "cross-repository writes" / "unauthorized deploy" impact bar for this engine.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration via `github_app_config`/`TOP_LEVEL_GH_KEYS`), and requires the attacker to control at least one organization's own GitHub App webhook secret registered on that shared instance — a realistic scenario for shared/multi-tenant Shipit deployments. No repository collaborator access, no `ApiClient` token, and no session are needed for the target repository.

### Recommendation
Bind the two fields together before trusting the payload: after verifying the signature with the organization's secret, re-validate that `repository.full_name`'s owner segment matches the `repository.owner.login`/`organization.login` that was used to select the verification secret, rejecting the webhook otherwise. Additionally, scope `StatusHandler`'s `Commit.where(sha:)` lookup by the repository resolved from the verified organization, rather than performing an unscoped global sha lookup.

### Proof of Concept
1. Configure Shipit with two organizations in `github_app_config`, e.g. `org-a` (attacker-controlled GitHub App, known `webhook_secret`) and `org-b` (victim, has a `Stack` in Shipit).
2. Attacker (who only administers `org-a`'s GitHub App) crafts:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. POST it to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature` computed with `org-a`'s webhook secret (which the attacker legitimately knows).
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s `webhook_secret`, and the HMAC check succeeds (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `PushHandler#process` resolves `stacks` via `repository.full_name` = `"org-b/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` against `org-b`'s real `Stack` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), even though the attacker has no relationship to `org-b` in Shipit.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
