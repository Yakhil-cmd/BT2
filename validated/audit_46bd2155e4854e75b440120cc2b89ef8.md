### Title
Webhook signature verification org can be spoofed independently of the repository the event mutates - (File: app/controllers/shipit/webhooks_controller.rb + app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to check the signature against using `repository_owner`, which is read from the raw, unvalidated JSON body (`params.dig('repository','owner','login')`). `ClosedHandler#repository` separately reads `params.repository.full_name` from the same body to resolve the actual `Shipit::Repository`/`ReviewStack` to mutate. Because these are two independent, attacker-controlled fields in one payload, there is no binding forcing them to refer to the same repository/org.

### Finding Description
The claimed binding should be: `organization_used_for(signature) == organization_owning(review_stack_being_archived)`. Tracing the code:

- `verify_signature` picks the signing org from the raw request body: [1](#0-0)  using `repository_owner` defined at [2](#0-1) .
- In a multi-org deployment, `Shipit.github(organization:)` uses that attacker-supplied `organization` value to pick the `webhook_secret` to verify against: [3](#0-2) .
- `ClosedHandler#repository` resolves the record that will actually be mutated from a *different* field, `params.repository.full_name`: [4](#0-3) .
- `ClosedHandler#process` then calls `review_stack.archive!` on the `ReviewStack` scoped to that resolved repository, with no re-check that the resolved repository's owner matches `repository_owner` used for signing: [5](#0-4) .

Since `repository.owner.login` (used only for signature-org selection) and `repository.full_name` (used to look up the real `Repository`/`ReviewStack`) are both plain, unrelated fields of one attacker-supplied JSON body, and the `ExplicitParameters` schema for `ClosedHandler` never requires or validates `repository.owner.login` against `repository.full_name`, an attacker who legitimately controls a GitHub org/app registered with this Shipit instance (and thus knows that org's `webhook_secret`) can set `repository.owner.login` to their own org (so the signature check passes) while setting `repository.full_name` to `victim-org/victim-repo`. `Repository.from_github_repo_name` performs a plain DB lookup on `owner`/`name` split out of `full_name` with no relation to the verified signature: [6](#0-5) .

Existing guards do not stop this: `verify_signature` only proves the request was signed by *some* org's known secret, not that it was signed by the secret of the org named in `full_name`; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `ClosedHandler` only requires the presence/type of `repository.full_name`, not its correlation to `repository.owner.login`; there is no `Repository`-level or handler-level check re-deriving `repository_owner` from `full_name` and comparing it to the header-selected org.

### Impact Explanation
A successful request causes `review_stack.archive!` to run against a victim org's live `ReviewStack` for `pr#{number}`, triggering `stack.deprovision` and `stack.archive!(user)` under the Shipit app's own GitHub/infra credentials, against a repository/org the attacker never authenticated for. This is a "payload for one repository mutating another's stack" — the impact category explicitly called Critical in the rules. It is repeatable against any victim repo/PR number for which the attacker can guess or observe an active review stack, as long as the attacker controls at least one org onboarded to the same Shipit instance (multi-org `github:` config) and knows that org's webhook secret (which they legitimately possess as that org's integrator/admin).

### Likelihood Explanation
This requires a multi-org Shipit deployment (`config/secrets.yml` using the per-organization `github:` schema, as documented) where the attacker controls one onboarded org's GitHub App/webhook secret and can craft raw JSON to `POST /webhooks` with a valid `X-Hub-Signature` for that secret. It does not require any Shipit session, API token, GitHub team membership, or victim-org credentials — only that the attacker knows the target victim repository name and an active PR/ReviewStack environment name (`pr#{number}`), both of which are typically public/observable on GitHub. This is realistic in any Shipit instance serving multiple independent GitHub orgs (the documented "Using Multiple Github Applications" setup).

### Recommendation
Bind the signature-verification organization to the same repository identity the handler will act on: after JSON-parsing the body, derive `repository_owner` from the same `repository.full_name` used by handlers (e.g. `full_name.split('/').first`) rather than from the separate `repository.owner.login` field, or explicitly verify `params.dig('repository','owner','login')&.downcase == params.dig('repository','full_name')&.split('/')&.first&.downcase` before dispatching to handlers. Additionally, each handler resolving a `Repository`/`ReviewStack` from `full_name` should assert that the resolved repository's `owner` matches the org whose secret validated the signature, rejecting (422) otherwise.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or a new `pull_request_closed_handler_test.rb`), using the existing multi-org test fixtures (`test/dummy/config/secrets_double_github_app.yml`, orgs `OrgOne`/`OrgTwo`):

1. Configure Shipit with the double-github-app secrets so `OrgOne` and `OrgTwo` have distinct known `webhook_secret`s (attacker controls `OrgOne`'s secret; `OrgTwo` is the "victim").
2. Seed `victim_repo = Shipit::Repository.create!(owner: 'orgtwo', name: 'victim-repo', ...)` and a `Shipit::ReviewStack`/underlying `Shipit::Stack` scoped to `victim_repo` with `environment: "pr42"`, and stub/mock `stack.expects(:deprovision)` plus spy on `archive!`.
3. Build a `pull_request` `closed` webhook JSON body with:
   - `action: "closed"`, `number: 42`, `pull_request.number: 42`
   - `repository.full_name: "OrgTwo/victim-repo"`
   - `repository.owner.login: "OrgOne"` (or omit `full_name.owner`, only set the top-level `owner.login` used by `repository_owner`)
4. Sign the raw body with `OrgOne`'s `webhook_secret` and send `POST /webhooks` with `X-Github-Event: pull_request` and the computed `X-Hub-Signature`.
5. Assert response is `200`/`:ok` (not `422`), then assert `stack.reload.archived?` is `true` and that `deprovision` was invoked — proving `OrgOne`'s signature authorized a mutation on `OrgTwo`'s (`victim_repo`'s) review stack.
6. Negative control: repeat with `repository.owner.login: "OrgTwo"` and a signature made with `OrgOne`'s secret — expect `422` and no archive, confirming the divergence only exists when `owner.login` and `full_name`'s owner disagree.
