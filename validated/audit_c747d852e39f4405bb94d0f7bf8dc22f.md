This confirms the finding decisively: `PushHandler` and `CheckSuiteHandler` both scope their queries through `stacks` (which is derived from `Repository.from_github_repo_name(repository_name)` in `Handler#stacks`, tying all effects to the webhook's own repository), but `StatusHandler#process` uniquely bypasses this scoping entirely, querying `Commit.where(sha: params.sha)` globally across the whole `commits` table with no repository/stack filter.

### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up target commits with `Commit.where(sha: params.sha)`, a global query unscoped to the webhook's own repository, then calls `commit.create_status_from_github!(params)` on every match. Any repository whose organization has a validly-signed GitHub App installation on this Shipit instance can therefore write an attacker-controlled `description`/`target_url`/`context` onto a `Status` row attached to a commit belonging to a completely different, uninvolved stack/repository, as long as the `sha` values collide.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`Status#target_url` displayed on victim_stack's commit == a value that was submitted through a webhook whose `repository.full_name` equals victim_stack's own repository.

In this codebase that equality is not enforced. The code path is:
1. `WebhooksController#verify_signature` at [1](#0-0)  only checks that the raw body is HMAC-signed by the GitHub App config keyed on `repository_owner` (the org in the payload). It says nothing about which repository within that org, nor does it constrain which commits the payload may target.
2. `Handler#stacks` at [2](#0-1)  exists specifically to scope handler effects to the stacks of `Repository.from_github_repo_name(repository_name)` — i.e., the repository named in the webhook's own payload. `PushHandler#process` [3](#0-2)  and `CheckSuiteHandler#process` [4](#0-3)  both use this `stacks` scope before touching any commit.
3. `StatusHandler#process`, however, does not use `stacks` at all: it runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . This is a table-wide lookup across every stack/repository registered in the Shipit instance.
4. `create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` [6](#0-5) , and `Status.replicate_from_github!` persists `state`, `description`, `target_url`, `context`, `created_at` verbatim from the webhook params with no validation tying them to the authenticating repository [7](#0-6) .
5. `StatusHandler`'s param schema accepts `description`, `target_url`, `context` as free strings with no format constraint [8](#0-7) .

Given a `sha` collision between a commit tracked by an attacker-controlled stack and a commit tracked by an unrelated victim stack, a real (or replayed) GitHub `status` webhook — validly signed for the attacker's own organization/app installation — will match and mutate the victim's `Commit#statuses` because the query has no `WHERE stack_id = ...` or repository join at all. None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) address this because they only validate the request's authenticity for its own organization/repository, not whether the `sha` inside the payload belongs to that same repository.

### Impact Explanation
An attacker who controls (or merely triggers status events on) any repository connected to this Shipit instance can, for a colliding `sha`, write arbitrary `target_url`/`description`/`context`/`state` into a `Status` record attached to a victim commit in an unrelated stack — a cross-repository record mutation. This is displayed in victim_stack's UI as if it were a status check on the victim's own commit, and (per `Status#after_create`) also triggers `enable_ci_on_stack` and `schedule_continuous_delivery` side effects on the victim stack [9](#0-8) . It is repeatable for every colliding sha the attacker can produce/replay, and the blast radius is every stack across every tenant/org configured in this Shipit installation, since the lookup is completely global.

### Likelihood Explanation
The attacker must own or control a repository already connected to Shipit (self-service stack creation exists via `StacksController#create`/`Api::StacksController#create`) so that their `status` webhook is validly signed for their own org. They then need a `sha` that also appears in `Commit` for a victim stack — this is the stated precondition of the question (sha collision), not something this finding needs to newly establish. Given that precondition, exploitation costs the attacker nothing beyond emitting one legitimate webhook for their own repository; there is no rate limiting or additional secret needed.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: restrict the commit lookup to `stacks` derived from the webhook's own `repository.full_name`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`-style):
```ruby
test "status webhook cannot mutate a commit belonging to a different repository" do
  victim_commit = shipit_commits(:first) # belongs to stack :shipit / repo shopify/shipit
  colliding_sha = victim_commit.sha

  # simulate an attacker-owned repo/stack with a commit sharing the same sha
  attacker_stack = shipit_stacks(:cyclimse) # different repository than :shipit
  attacker_stack.commits.create!(sha: colliding_sha, author: shipit_users(:walrus),
                                  committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => colliding_sha,
    'state' => 'success',
    'target_url' => 'http://evil',
    'description' => 'evil',
    'context' => 'evil/ci',
    'repository' => { 'full_name' => attacker_stack.repository.full_name, 'owner' => { 'login' => attacker_stack.repository.owner } }
  }.to_json

  post :create, body:, as: :json

  victim_status = victim_commit.reload.statuses.last
  # Binding under test: victim_status.target_url == 'http://evil' should be FALSE
  assert_not_equal 'http://evil', victim_status&.target_url
end
```
With the current `Commit.where(sha: params.sha)` implementation this assertion fails (the victim's `Status#target_url` becomes `'http://evil'`), demonstrating the cross-repository write.
