### Title
ERC20Transactor assumes fee-on-transfer/deflationary ERC20 tokens move the exact requested `amount` - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` bridge XCM's `AssetsInHolding` accounting to a real ERC20 contract deployed under `pallet_revive`, by calling `IERC20::transferCall` for a fixed `amount` and then crediting/debiting the XCM holding register with exactly that same `amount` on success, never checking the actual balance delta of the checking account. This is the same class of bug described in the source report ("Deflationary tokens are not supported"): the code assumes `transfer()`/`transferFrom()` moves precisely `amount`, which is false for fee-on-transfer/rebasing ERC20 tokens.

### Finding Description
In `withdraw_asset_with_surplus`, the transactor transfers `amount` from the user to `TransfersCheckingAccount` via a raw Solidity `transfer` call, and on a truthy return value unconditionally mints an `Erc20Credit(amount)` into `AssetsInHolding`: [1](#0-0) [2](#0-1) 

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary and, on success, simply returns `Ok(surplus)` with no verification that the beneficiary's balance actually increased by `amount`: [3](#0-2) 

Neither function reads the ERC20 balance of the checking account (or the counterparty) before and after the call to derive the real transferred amount; they trust the `bool` return of `transfer()` alone. If the underlying ERC20 contract charges a transfer fee/burn (deflationary token) or rebases, the actual increase/decrease in on-chain balance is less than `amount`, while the XCM executor's internal `AssetsInHolding` ledger (and therefore cross-chain/cross-instruction accounting, refunds, and subsequent `DepositAsset`/`InitiateTransfer` legs) continues to operate on the nominal `amount`. This creates a persistent divergence between the pallet_revive-tracked real balance of `TransfersCheckingAccount` and the XCM-internal accounting that references this transactor.

### Impact Explanation
Because `TransfersCheckingAccount` is a single shared account used across all withdrawals/deposits routed through this transactor, an accounting drift accumulates: every deflationary-token withdrawal credits holding with more than what the checking account actually received. Eventually a later legitimate `deposit_asset_with_surplus` call for that asset can fail (the checking account lacks the ERC20 balance the ledger believes it has), causing genuine user assets to be trapped/lost in that XCM leg, or - depending on how holdings are further routed through `InitiateTransfer`/reserve-transfer logic - allows the ledger-recorded amount to exceed the backing reserve, undermining the "asset is fully backed 1:1 by the checking account" invariant this transactor is meant to preserve. This matches a Medium-severity impact (accounting mismatch/possible fund loss), analogous to the original Knox report.

### Likelihood Explanation
Reachability depends on whether an arbitrary attacker can register/use a deflationary ERC20 contract with this transactor without any privileged action. `pallet_revive` allows any signed user to deploy a Solidity contract (including a custom fee-on-transfer ERC20), and the transactor's `Matcher: MatchesFungibles<H160, u128>` decides which contract addresses are treated as valid fungible asset IDs for XCM purposes. I was not able to fully confirm, within the available tool budget, whether the `Matcher` configured in `asset-hub-westend`'s `xcm_config.rs` restricts eligible ERC20 contract addresses to an admin-curated allow-list or permits any deployed contract address to be used as an XCM asset once minimally registered/foreign-asset-mapped. If registration is permissionless (or only requires a standard "register foreign asset" call available to ordinary users), the likelihood is High since any user could deploy a deflationary ERC20 and drive the accounting mismatch themselves; if registration requires governance/admin approval, likelihood drops to Low/Medium since it depends on an approved token later turning out to have deflationary transfer semantics (e.g., in future or misconfigured deployments).

### Recommendation
Measure the ERC20 balance of the relevant account (checking account or beneficiary) immediately before and after the `transferCall`, and use the actual observed delta - not the requested `amount` - when constructing/consuming `AssetsInHolding` credits in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`. Alternatively, restrict `Matcher` to only accept ERC20 contracts that are verified (e.g., via a governance-gated registry) to implement standard, non-fee, non-rebasing transfer semantics, and document this as a hard requirement rejected at registration time.

### Proof of Concept
I could not execute a concrete Rust/FRAME reproduction within the available tool budget. A full PoC would require: (1) confirming the exact `Matcher`/registration path wired in `asset-hub-westend/src/xcm_config.rs` to determine whether a permissionless user can register an arbitrary deployed ERC20 contract address for use with `ERC20Transactor`; (2) deploying a minimal fee-on-transfer ERC20 contract via `pallet_revive`; (3) driving an XCM `WithdrawAsset`/`DepositAsset` program through `ERC20Transactor` for that asset and asserting that `Erc20Credit`'s tracked amount diverges from the checking account's actual on-chain balance delta, then showing a subsequent legitimate deposit for a different user fails due to insufficient real balance in the checking account. This last verification step (the registration/permission model) is the main open uncertainty in this report; without it, likelihood cannot be pinned to a specific severity band with full confidence.
