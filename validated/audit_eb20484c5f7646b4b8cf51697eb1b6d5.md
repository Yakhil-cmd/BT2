### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends to gate all provisioning on `repository.review_stacks_enabled`, but Ruby's `&&`/`||` precedence causes `review_stacks_enabled` to be ANDed only with the first disjunct (`provisioning_behavior_allow_all?`), not with the `allow_with_label` or `prevent_with_label` disjuncts. As a result, when `review_stacks_enabled` is `false` and `provisioning_behavior` is `allow_with_label`, an attacker who labels their own PR with the exact `provisioning_label_name` still causes `provision?` to return `true` and a `Shipit::ReviewStack` to be created and queued for provisioning.

### Finding Description
The broken invariant: `provision?` should equal `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && label) || (prevent_with_label? && !label))`, i.e., no disjunct should fire unless `review_stacks_enabled == true`.

The actual code is:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && label) || (prevent_with_label? && !label)`

So `review_stacks_enabled` is only checked in the first clause. The second and third clauses never reference `review_stacks_enabled` at all.

Path: `OpenedHandler#process` → `respond_to_pull_request_opened?` → `provision?` → if true, `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` runs, which calls `create!`, persisting a `Shipit::ReviewStack` (with `branch` set to the attacker's PR head ref) and enqueuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)`. [2](#0-1) [3](#0-2) 

The scenario per the given threat model: repository has `review_stacks_enabled = false` and `provisioning_behavior = :allow_with_label`. The attacker's PR carries a label whose name matches `repository.provisioning_label_name` (labeling one's own PR is an explicitly granted attacker capability under the stated rules). `pull_request_has_provisioning_label?` returns `true`. [4](#0-3) 
`provision?`'s second disjunct evaluates to `true` regardless of `review_stacks_enabled`, so `respond_to_pull_request_opened?` returns `true` and stack creation proceeds — despite the feature being disabled at the repository level.

Existing guards do not catch this: `params` schema validation only enforces payload shape, not label semantics [5](#0-4) ; `Repository#from_github_repo_name` only ensures the repo is tracked [6](#0-5) ; and there is no other check on `review_stacks_enabled` before `ReviewStackAdapter.find_or_create!` is invoked. The identical bug pattern also exists in `ReopenedHandler#unarchive?` [7](#0-6) , though the question is scoped to `OpenedHandler`.

The existing test suite does not exercise the combination of `review_stacks_enabled: false` with `allow_with_label`/`prevent_with_label`; the only "disabled" test uses `behavior: :allow_all` [8](#0-7) , which is why this precedence bug is not caught by current tests.

### Impact Explanation
When a repository maintainer disables review-stack provisioning (`review_stacks_enabled = false`) but leaves `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (the enum default/non-`allow_all` state), any user who can open a PR against that repo and get the matching label attached can force Shipit to create and provision a `Shipit::ReviewStack` for their PR branch — bypassing the disabled feature flag. This results in unauthorized stack creation and triggers the provisioning pipeline (`ReviewStackProvisioningQueue`), which downstream can run deploy/provisioning tasks (command execution) for a branch the attacker controls. This is repeatable for every PR against the affected repository and matches the Critical category: "a record written for a repository that did not authenticate it" plus provisioning leading to task/command execution.

### Likelihood Explanation
Preconditions: repository has `review_stacks_enabled = false` and `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`) — plausible/likely configuration since operators may set a behavior mode while intending the master toggle to fully disable review stacks. Attacker cost is low: open a PR and get the specific label attached (a capability explicitly granted to the attacker under the stated threat model). No secrets, tokens, or elevated permissions are required. Fully repeatable against any repository in this misconfiguration state.

### Recommendation
Fix operator precedence in `provision?` (and the identical `unarchive?` in `reopened_handler.rb`) by explicitly gating the whole expression on `review_stacks_enabled`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does not create stacks when review_stacks_enabled is false, even with allow_with_label and matching label" do
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false
  repository.provisioning_behavior = :allow_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  # Binding under test: review_stacks_enabled (false) must equal the actual gating applied to provision?
  assert_equal false, repository.review_stacks_enabled

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, `Shipit::Stack.count` increases despite `review_stacks_enabled == false`, proving the divergence; after the fix, no stack is created.
