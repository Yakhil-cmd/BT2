### Title
First-depositor share-price manipulation via front-running the "initial deposit" branch of the market-maker AA cookbook pattern - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The `H-29` bug is a "lazy initialization / uninitialized cycle" issue: a reward-tracking variable (`endCycle`) is left at its default zero value until the owner's setup call, and an attacker front-runs that setup call to seize funds that were meant to be distributed only after proper initialization. The closest structurally-equivalent, reachable pattern inside ocore's own AA scripting layer is the "initial deposit" branch of the Uniswap-like market-maker AA sample shipped with the repo's cookbook. This branch uses `balance[$asset] == 0 OR balance[base] == 0` as its "not yet initialized" signal and, once it is true, unconditionally mints share tokens equal to the entire current `balance[base]`. An attacker can front-run the legitimate first depositor (or immediately follow the `mm_asset` definition trigger) to become the very first depositor with a minimal amount, then directly inflate the AA's real token/byte balances outside of the tracked `mm_asset_outstanding` accounting, diluting later depositors' share price — the same "seize control of state before it is properly initialized/accounted" root cause as the C4 report.

### Finding Description
Autonomous Agents (AAs) in Obyte execute automatically whenever a unit sends funds to their address, and any of the AA's balances (`balance[asset]`, `balance[base]`) reflect **all** coins ever received by the address, not just the coins that arrived via a tracked/"official" case [1](#0-0) . The market-maker sample computes whether a deposit is the very first one purely from the raw balances:

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
``` [2](#0-1) 

There is no state variable that independently tracks whether the pool has already been seeded (analogous to `endCycle` being left at its zero/default value in the Solidity report). The "has anyone deposited yet" check is inferred solely from the mutable, attacker-influenceable `balance[...]` values, exactly like the C4 finding where `endCycle == 0` was used (implicitly, by omission) as the "not yet started" signal and an attacker could manipulate the surrounding state (`incrementGauge`) before the owner's real initialization (`addBribeFlywheel`) fired.

An attacker who observes the `define share asset` trigger (which sets `var['mm_asset']`) can immediately submit their own minimal "invest in MM" trigger before the intended first liquidity provider's transaction is included, becoming the first depositor and setting `mm_asset_outstanding` from an artificially small `balance[base]`. The attacker can then send further raw payments (of `$asset` and/or `base`) directly to the AA address — these are simply accepted by AAs whose case list has no `if` match (or match the exchange cases) without updating `mm_asset_outstanding` — inflating the true pool balance while the accounting variable used for pro-rata payouts on divestment (`var['mm_asset_outstanding']`) stays disproportionately small relative to the attacker's minted shares [3](#0-2) . Later depositors that use the intended "invest" path get their `$issue_amount` computed only against the artificially skewed `$bytes_balance`/`$current_ratio`, so their real contribution is diluted relative to the attacker's already-outstanding shares, letting the attacker capture a disproportionate fraction of the pool upon divestment — the same "front-run an uninitialized/loosely-guarded state transition to steal funds meant for legitimate later participants" root cause as the external report.

### Impact Explanation
An attacker who wins the front-run controls the exchange rate used for all subsequent depositors and can subsequently divest to withdraw a disproportionate share of bytes/asset balance that legitimate depositors contributed, i.e. concrete unauthorized fund extraction from the AA (asset issuance and transfer conditions / AA definitions and triggers category). Because this is a documented cookbook pattern in the "Sample Agents Cookbook" that AA authors are expected to copy and adapt, any AA deployed from this template inherits the vulnerability, and exploitation only requires posting ordinary triggers/units — no special privilege.

### Likelihood Explanation
Front-running a specific AA's first-use trigger only requires broadcasting a competing unit with a higher/earlier tip inclusion, which is achievable by any DAG participant; the "am I the first depositor" check relying purely on raw balances rather than an explicit initialization flag makes the race trivially exploitable whenever the pool is newly created and has zero balance.

### Recommendation
Use an explicit, monotonic state flag (e.g., `var['initialized']` set exactly once inside the same state-update message that also fixes the initial exchange rate/mm_asset_outstanding) instead of inferring "not yet initialized" from `balance[...]==0`, and reconcile `mm_asset_outstanding` against `balance[...]` on every deposit/exchange so that externally-donated funds cannot be excluded from share accounting (i.e., always price shares from the state variable, never from raw, donation-manipulable `balance[]`).

### Proof of Concept
1. Owner posts `{trigger.data.define: true}` to the market-maker AA; `var['mm_asset']` is set.
2. Attacker immediately posts an "invest in MM" trigger with `trigger.output[[asset=base]] = 100001` and `trigger.output[[asset=$asset]] = 1`, front-running the legitimate LP's larger deposit. Since `balance[$asset]` and `balance[base]` were 0 before this trigger, the "initial deposit" branch fires and the attacker receives `mm_asset` shares equal to `balance[base]` (≈100001) while `var['mm_asset_outstanding']` is set to the same small number [4](#0-3) .
3. Attacker sends a large "donation" of raw `$asset` and `base` bytes directly to the AA address via a trigger that matches the "exchange" cases or otherwise leaves `mm_asset_outstanding` unmodified relative to the injected size, inflating `balance[base]`/`balance[$asset]` without minting corresponding shares.
4. The legitimate LP now deposits; `$bytes_balance` used to price their shares is calculated from the inflated `balance[base]`, so `$issue_amount` mints them a tiny fraction of `mm_asset_outstanding` relative to their real contribution.
5. Attacker calls "divest MM shares", redeeming their `mm_asset` for `round($investor_share * balance[$asset])` and `round($investor_share * balance[base])`, capturing a disproportionate share of the pool that includes the legitimate LP's later deposit [5](#0-4) .
