### Title
Webhook signature is verified against the payload's `repository.owner.login` while every event handler dispatches on `repository.full_name` — an attacker holding one organization's `webhook_secret` can forge events that mutate a *different* organization's stacks (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-suppliable JSON body. Every downstream `Webhooks::Handlers::Handler` subclass, however, determines *which repository/stack to act on* using a completely different field of the same payload: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`, and every pull-request handler’s `repository.full_name` lookup). Nothing ties these two fields together, so the org whose secret authenticated the request is never checked against the org that is actually written to.

### Finding Description
`Shipit.github(organization:)` (`lib/shipit.rb`) supports a per-organization configuration map (documented in `config/secrets.development.example.yml:18-38` and `docs/setup.md`), each org having its own independent `webhook_secret`. The controller's `verify_signature` uses that attacker-controlled org name to pick which secret to verify against: [1](#0-0) 

`repository_owner` is derived purely from the JSON payload: [2](#0-1) 

Once the signature check passes, `create` hands the *entire* parsed payload to the registered handlers: [3](#0-2) 

But the base `Handler` class (used by `PushHandler`, all `PullRequest::*Handler`s, etc.) resolves the target `Repository`/`Stack` from a *different* field, `repository.full_name`, never cross-checked against `repository.owner.login`: [4](#0-3) 

`PushHandler` then syncs the resolved stack using attacker-controlled `ref`/`after` values: [5](#0-4) 

Pull-request handlers similarly resolve the repository from `params.repository.full_name` independent of the org used for signature verification, e.g.: [6](#0-5) 

Binding that should hold: `organization authenticated by verify_signature (repository.owner.login) == organization that owns the repository whose Stack is mutated (repository.full_name)`. The code enforces neither field's consistency with the other — it never asserts `repository.full_name.split('/').first == repository.owner.login`. An attacker who has learned or been issued the `webhook_secret` for a low-trust organization "OrgA" (any org configured in a multi-org Shipit `secrets.yml`) can build a payload where:
- `repository.owner.login = "OrgA"` → makes `verify_signature` pick the GitHub App/secret the attacker actually possesses, so the HMAC check passes.
- `repository.full_name = "OrgB/private-repo"` → is what every handler (`PushHandler`, PR handlers) actually acts on, targeting a stack belonging to a completely different, higher-trust organization "OrgB" that the attacker has no credentials for.

This is the structural analogue of the H-03 finding: a field that is acted upon downstream (`repository.full_name` → which repo/stack is mutated) is never covered by the check that is supposed to authorize the whole operation (`repository.owner.login` → which secret validates the signature).

### Impact Explanation
This lets an attacker who only controls the webhook secret of one configured GitHub organization forge `push`/`pull_request` events that are processed as belonging to any other organization's repository/stack known to this Shipit instance, as long as that repository name is guessable (repo full names are public). Concretely:
- Forged `push` events invoke `stack.sync_github(expected_head_sha: ...)` for an arbitrary target stack (`PushHandler#process`), which can trigger unwanted syncs/continuous-deployment behavior on a stack the attacker has no authorization over.
- Forged `pull_request` events can create/unarchive/label/close review stacks belonging to another organization (`OpenedHandler`, `ReopenedHandler`, `ClosedHandler`, etc.), causing unauthorized state changes (provisioning, deprovisioning/archival) on cross-organization resources.

This crosses the "cross-repository writes" / "unauthorized deploy" bar defined in scope, since the mutation is performed on a stack/repository outside the organization whose credential actually authenticated the request.

### Likelihood Explanation
Exploitability strictly requires a real deployment to be configured with **more than one GitHub organization** in `secrets.yml` (the documented multi-org schema), and the attacker must possess the `webhook_secret` for at least one of those configured orgs (e.g., because they administer or have compromised the GitHub App for a lower-trust org integrated into the same Shipit instance). Given that requirement, forging the payload is trivial (it's just JSON with a mismatched `owner.login` vs `full_name`), and no session, `ApiClient` token, or GitHub push access to the target repo is needed to affect that repo's Shipit-side sync/review-stack state.

### Recommendation
In `WebhooksController`, or in the base `Webhooks::Handlers::Handler`, assert that the organization that authenticated the signature equals the owner segment of `repository.full_name` before dispatching to handlers — e.g., derive `repository_owner` and the acting repository consistently from the same field, and reject the webhook (422) if `repository.full_name.split('/', 2).first.casecmp?(repository_owner)` is false. More robustly, resolve the webhook secret from the `Stack`/`Repository`/`GithubHook` record matching `repository.full_name` rather than from an org name taken directly out of the unauthenticated JSON body.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`, `OrgA` (attacker-controlled webhook secret) and `OrgB` (victim org, has a Stack for `OrgB/private-repo`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "OrgB/private-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Attacker computes `X-Hub-Signature` using OrgA's `webhook_secret` over the raw JSON body and POSTs to `/github_webhooks` (or the mounted webhooks path) with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature using OrgA's secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgB/private-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on OrgB's stack — an operation the attacker was never authorized to trigger.
