### Title
Webhook signature verification authenticates `repository.owner.login`, but the handler dispatches on `repository.full_name` from the same unverified body — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the signature against using `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON body, while the event handlers resolve the target `Repository`/`Stack` using a *different* field from that same unverified body: `repository.full_name`. In a multi-organization Shipit deployment (an officially documented configuration), these two fields are never checked for consistency, so an attacker can pick an organization whose app has no `webhook_secret` configured to sail through signature verification, while pointing the payload's `full_name` at a completely different, victim organization's repository.

### Finding Description
Signature verification: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')`) before any authentication has taken place, and is used only to pick which `GitHubApp` config (and thus which `webhook_secret`) to check the signature against: [3](#0-2) 

Note that `verify_webhook_signature` returns `true` unconditionally when the selected app has no `webhook_secret` configured (`return true unless webhook_secret`). A `nil` `webhook_secret` is an explicitly supported, documented configuration option per organization: [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature`, `create` re-parses the same raw body and dispatches it to handlers unchanged: [6](#0-5) 

Handlers, however, locate the target `Repository`/`Stack` using a *different* key from the very same body — `repository.full_name` — not `repository.owner.login`: [7](#0-6) 

and `PushHandler#process` uses that lookup to trigger a real GitHub sync against whatever `Stack`s belong to that resolved repository: [8](#0-7) 

Because `repository.owner.login` (used to pick the verification context) and `repository.full_name` (used to pick the acted-upon repository) are two independent, fully attacker-controlled fields in the same unverified JSON body, the equality the system implicitly relies on — **organization authenticated == repository/stack written** — does not hold and is never enforced. An attacker can set `repository.owner.login` to an organization configured with `webhook_secret: nil` (satisfying `verify_signature`) while setting `repository.full_name` to `"victim-org/victim-repo"` (satisfying the handler's repository lookup), causing the request to be treated as an authentic webhook for the victim's stack.

### Impact Explanation
This lets an unauthenticated external attacker forge `push` (and similarly `status`/`check_suite`) webhook events for any repository/stack hosted on the Shipit instance, as long as any organization configured on that instance has no `webhook_secret` set (an explicitly supported, documented configuration for per-org GitHub Apps). The forged event causes `Stack#sync_github` to run for the victim stack on attacker-chosen timing/`expected_head_sha`, which can trigger continuous-delivery auto-deploys for stacks with `continuous_deployment` enabled — an unauthorized deploy trigger that the deployment-trust model (a webhook is only supposed to be actionable if genuinely signed for that repository's org) is meant to prevent.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub App/organization (a documented, supported setup) and that at least one of those organizations has no `webhook_secret` configured. No credentials, GitHub App private key, or repository write access are needed by the attacker — only knowledge of the org name lacking a secret and the victim repository's `full_name`, both of which are discoverable/public information.

### Recommendation
Bind the authentication context to the same identifier used for authorization/dispatch: require that `repository.owner.login` used to select the webhook secret matches (case-insensitively) the owner segment of `repository.full_name` before processing, or resolve the target `Repository` via the same organization that was cryptographically verified, rejecting the event otherwise.

### Proof of Concept
1. Deploy Shipit with two organizations configured under `config/secrets.yml`, e.g. `AttackerOrg` (no `webhook_secret`) and `VictimOrg` (has a `webhook_secret` and a stack tracking `VictimOrg/app`).
2. POST to `/webhooks` with header `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already present on GitHub>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/app"
  }
}
```
No `X-Hub-Signature` needed (or any garbage value), since `Shipit.github(organization: "AttackerOrg")` has no `webhook_secret` and `verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb` lines 24-30, `lib/shipit/github_app.rb` lines 76-83).
3. `verify_signature` passes, `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("VictimOrg/app")` via `repository_name` (`app/models/shipit/webhooks/handlers/handler.rb` lines 36-38) and calls `stack.sync_github(expected_head_sha: ...)` for the victim's stack (`app/models/shipit/webhooks/handlers/push_handler.rb` lines 12-17), despite the request never having been authenticated for `VictimOrg`.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
