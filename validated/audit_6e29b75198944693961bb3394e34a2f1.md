### Title
Checks-Effects-Interactions Violation in `_requestERC721Transfer` Allows Reentrancy to Emit Duplicate Bridge Request Events with Distinct Nonces — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`_requestERC721Transfer` in `BridgeTransferERC721.sol` makes an external low-level call to the token contract (`tokenURI`) **before** incrementing `requestNonce`. A malicious registered ERC721 token can re-enter `onERC721Received` during that call, causing two `RequestValueTransferEncoded` events with **different** nonces to be emitted for a single user deposit. In `modeMintBurn` on the destination bridge, both nonces are processed independently, resulting in an unauthorized mint of a bridged ERC721 asset the user never deposited.

---

### Finding Description

In `_requestERC721Transfer`:

```solidity
// BridgeTransferERC721.sol lines 85-105
require(isRunning, "stopped bridge");
(bool success, bytes memory uri) = _tokenAddress.call(          // ← External call #1
    abi.encodePacked(ERC721Metadata(_tokenAddress).tokenURI.selector,
                     abi.encode(_tokenId)));
if (!success) { uri = ""; }
if (modeMintBurn) {
    ERC721Burnable(_tokenAddress).burn(_tokenId);               // ← External call #2
}
emit RequestValueTransferEncoded(..., requestNonce, ...);
requestNonce++;                                                  // ← State change LAST
```

The `requestNonce` counter — the bridge's authoritative sequencing state — is updated **after** two external calls into the token contract. There is no `nonReentrant` guard on this path (unlike `handleKLAYTransfer` and `_requestKLAYTransfer` which carry `nonReentrant`).

The entry points that reach `_requestERC721Transfer` without reentrancy protection:

```solidity
// BridgeTransferERC721.sol line 117
function onERC721Received(address _from, uint256 _tokenId, address _to, bytes memory _extraData) public {
    _requestERC721Transfer(msg.sender, _from, _to, _tokenId, _extraData);
}

// BridgeTransferERC721.sol lines 129-131
function requestERC721Transfer(address _tokenAddress, address _to, uint256 _tokenId, bytes memory _extraData) public {
    IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
    _requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
}
```

`onERC721Received` passes `msg.sender` as `_tokenAddress` and is gated only by `onlyRegisteredToken(_tokenAddress)` — any registered token can call it.

The same pattern exists in `_requestERC20Transfer` (`BridgeTransferERC20.sol` lines 91–107): `_payERC20FeeAndRefundChange` makes external `safeTransfer` calls before `requestNonce++`.

---

### Impact Explanation

**Exact corrupted value**: `requestNonce` on the source bridge is consumed twice (values N and N+1) for a single user deposit of one NFT. The destination bridge receives two valid `RequestValueTransferEncoded` events with distinct nonces and distinct `_tokenId` values.

**Unauthorized mint**: In `modeMintBurn` mode on the destination bridge, `handleERC721Transfer` processes each nonce independently. Nonce N mints `tokenId=2` (the attacker-chosen phantom token) and nonce N+1 mints `tokenId=1` (the legitimately deposited token). The user deposited one NFT but receives two on the destination chain — one of which was never locked on the source chain.

**Broken bridge invariant**: The bridge's core invariant is `tokens_locked_on_source == tokens_minted_on_destination`. This is violated: one token locked, two tokens minted.

---

### Likelihood Explanation

**Trigger**: A registered ERC721 token whose `tokenURI` function re-enters `bridge.onERC721Received`. Token registration is an owner-only operation (`BridgeTokens.sol`), making this a semi-trusted trigger. However:
- The token contract could be an upgradeable proxy registered legitimately and later upgraded to be malicious.
- The bridge owner may register a token without auditing its `tokenURI` implementation.
- Service-chain bridge deployments are permissioned environments where the token registry is managed by a small set of operators, making a compromised or malicious token a realistic scenario.

---

### Recommendation

1. **Increment `requestNonce` before any external call** in both `_requestERC721Transfer` and `_requestERC20Transfer`, following the Checks-Effects-Interactions pattern:

```solidity
// Correct order
uint64 currentNonce = requestNonce;
requestNonce++;                          // Effect first
emit RequestValueTransferEncoded(..., currentNonce, ...);
// Then external calls (burn, tokenURI)
```

2. **Add `nonReentrant`** to `_requestERC721Transfer`, `_requestERC20Transfer`, `handleERC20Transfer`, and `handleERC721Transfer` — consistent with the guard already applied to the KLAY variants.

---

### Proof of Concept

```
Source chain (non-mintBurn or mintBurn):

1. Attacker deploys MaliciousNFT (registered by bridge owner).
   MaliciousNFT.tokenURI(tokenId) calls bridge.onERC721Received(attacker, 999, victim, "").

2. Attacker calls bridge.requestERC721Transfer(MaliciousNFT, victim, 1, ""):
   a. transferFrom(attacker, bridge, tokenId=1)          // bridge holds tokenId=1
   b. _requestERC721Transfer(MaliciousNFT, attacker, victim, 1, ""):
      i.  tokenURI(1) → MaliciousNFT re-enters bridge.onERC721Received(attacker, 999, victim, "")
          → _requestERC721Transfer(MaliciousNFT, attacker, victim, 999, ""):
              tokenURI(999) → no re-entry
              emit RequestValueTransferEncoded(..., tokenId=999, requestNonce=0)
              requestNonce++ → 1
      ii. (returns to outer call)
      iii. emit RequestValueTransferEncoded(..., tokenId=1, requestNonce=1)
      iv. requestNonce++ → 2

3. Destination bridge operators process:
   - Nonce 0: handleERC721Transfer → mintWithTokenURI(victim, 999, ...)  ✓ free mint
   - Nonce 1: handleERC721Transfer → mintWithTokenURI(victim, 1, ...)    ✓ legitimate mint

Result: attacker deposited 1 NFT (tokenId=1), victim receives 2 NFTs (tokenId=1 and tokenId=999).
Bridge invariant violated: 1 token locked, 2 tokens minted.
