### Title
Cross-repository status forgery: `StatusHandler#process` mutates commits without verifying repository ownership - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook body using the `organization` derived from the *attacker's own* `payload['repository']['owner']['login']`, which only proves the signature belongs to that org's `webhook_secret`. `StatusHandler#process` then looks up commits purely `by sha` globally (`Commit.where(sha: params.sha)`), with no re-check that the authenticated organization owns the repository/stack that the matched commit(s) belong to.

### Finding Description
The broken binding is: authenticated_org (org whose `webhook_secret` verified the raw POST body, derived from `payload['repository']['owner']['login']`) == owning_org(commit matched by `params.sha`). These are never compared.

- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository', 'owner', 'login')` straight from the attacker-controlled payload [1](#0-0) [2](#0-1) . This only proves the request was signed by *some* known org's secret matching the org named in the payload's own `repository.owner.login` field — it never binds that org to any specific commit or stack.
- `StatusHandler` is dispatched generically via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) , and `Handler.call` simply instantiates and calls `#process` [4](#0-3) .
- `StatusHandler`'s params schema does not even `require :repository` (unlike every `PullRequest::*Handler`, which requires `repository.full_name` and scopes lookups through `Repository.from_github_repo_name(params.repository.full_name)`) [5](#0-4) . Compare with `OpenedHandler#repository` which enforces repo scoping [6](#0-5) .
- `StatusHandler#process` matches commits **only by `sha`**, globally across all stacks/repositories, and mutates every match: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [7](#0-6) . `Handler#repository_name`/`#stacks` exist in the base class [8](#0-7)  but `StatusHandler` never calls them, so no repository-ownership filter is applied at all.
- The `commits` table has a **composite unique index on `(sha, stack_id)`**, not a global unique index on `sha` alone [9](#0-8) . This confirms the schema explicitly anticipates the *same* SHA existing under multiple stacks (e.g., forks, mirrors, or reused commit SHAs across independent repositories tracked by different Shipit stacks), and `StatusHandler` deliberately/negligently ignores that scoping when applying incoming statuses.

Exploit flow: attacker owns org `attacker-org` with a repo registered in Shipit and a valid GitHub App/`webhook_secret` for that org. They POST to `/webhooks` with `X-Github-Event: status`, a body whose `repository.owner.login` is `attacker-org` (so `verify_signature` resolves and validates the correct secret), but `sha` set to the SHA of a commit that also exists under a *victim* org's stack (same SHA value, different `stack_id` row — feasible whenever a SHA is shared across mirrored/forked repos, or simply if an attacker can get some SHA value onto their own tracked stack that coincides with a victim's tracked commit). `StatusHandler#process` finds and mutates **all** `Commit` rows with that SHA, including the victim's, calling `create_status_from_github!` which creates a `Status`, which can flip `deployable?`/`state`, trigger `Hook.emit(:deployable_status, ...)`, and schedule `ContinuousDeliveryJob`/`ProcessMergeRequestsJob` on the victim's stack [10](#0-9) [11](#0-10) [12](#0-11) .

Existing guards do not catch this: `verify_signature` only validates that the body's own declared owner matches a known org's secret — it is self-referential and doesn't constrain which commits get touched. `drop_unhandled_event` only checks the event type is registered. `ExplicitParameters` schema for `StatusHandler` doesn't require or validate `repository` at all. No `force_github_authentication`, `User#authorized?`, or `require_permission!` check applies to webhook processing (webhooks are inherently unauthenticated as a user context).

### Impact Explanation
A payload authenticated only for the attacker's own org can create/mutate `Status` rows on **any commit anywhere in the Shipit instance that shares the same SHA**, regardless of which stack/repository owns it. This can flip a victim commit's deployability, trigger `deployable_status` hooks, and schedule continuous-delivery/merge jobs for the victim's stack — i.e., "a payload for one repository mutating another's stack, commit, task" — matching the **Critical** impact category. The blast radius spans all tenants/orgs configured under the same Shipit instance sharing `Shipit.github_apps`, and the attack is repeatable per request (no rate limiting relevant here, ignored per rules) as long as the attacker can produce a colliding SHA under their own controlled stack.

### Likelihood Explanation
Preconditions: attacker needs (a) a GitHub org with a Shipit-configured app/webhook secret (i.e., their own onboarded org — "unprivileged" in the sense of no special Shipit role, but must control an org that Shipit trusts to sign for itself), and (b) a commit SHA collision between their own tracked stack and the victim's tracked stack. SHA collision is trivially achievable when the victim repository is public and forked/mirrored (attacker can add the exact victim commit to their own fork/stack, giving it the identical SHA), which is a normal, low-cost, non-secret-requiring action for any GitHub user. Given that, forging the status webhook requires zero secrets beyond the attacker's own (self-issued) webhook secret. This makes the attack highly feasible and repeatable.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository/organization that was authenticated in `verify_signature`, mirroring what `PullRequest::*Handler`s do: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and constrain the `Commit` query to that repository's stacks (e.g., `Commit.joins(stack: :repository).where(sha: params.sha, stacks: { repository_id: repository.id })`). Additionally, `WebhooksController#verify_signature` should be reviewed so any downstream handler can access/trust the authenticated organization, not just the payload's self-declared owner.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook authenticated for org A mutates a commit belonging to org B's stack" do
          org_a_stack = shipit_stacks(:shipit) # e.g. repository owned by 'shopify'/org A
          org_b_stack = shipit_stacks(:cyclimse) # different org/repository, org B

          shared_sha = 'deadbeef' * 5

          commit_a = org_a_stack.commits.create!(sha: shared_sha, message: 'a')
          commit_b = org_b_stack.commits.create!(sha: shared_sha, message: 'b')

          # Payload signed and verified as belonging to org A's OWN repository only.
          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'repository' => { 'full_name' => org_a_stack.repository.full_name,
                               'owner' => { 'login' => org_a_stack.repository.owner } }
          }

          assert_difference -> { commit_b.statuses.count }, 1 do
            StatusHandler.call(payload)
          end

          # Equality check that SHOULD hold but does not:
          # authenticated_org (org A) != owning_org(commit_b's stack) (org B)
          refute_equal org_a_stack.repository.owner, org_b_stack.repository.owner
          assert commit_b.reload.statuses.exists?, "org B's commit was mutated by a payload authenticated only for org A"
        end
      end
    end
  end
end
```
