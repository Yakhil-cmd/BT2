### Title
AA formula cost model does not charge the real cost of `data_feed`/`in_data_feed` when AA is unstable (`bAA=true`), letting an attacker-defined AA turn a single trigger into an O(size of unstable DAG) synchronous scan that stalls the node - ([File: data_feeds.js])

### Summary
`fulfillRandomWords()` in the original report failed because the VRF callback's fixed gas budget did not match the true cost of the work performed inside it. Ocore has an analogous fixed-budget mechanism for AA execution: `constants.MAX_COMPLEXITY` / `constants.MAX_OPS`, enforced in `definition.js` and `formula/validation.js`, are meant to bound the real computational cost of evaluating an AA/oscript formula so that a single trigger can never make node processing unbounded. `data_feed` / `in_data_feed` are charged a flat, small complexity cost (`complexity = 1`, see `formula/validation.js:26-83` `validateDataFeed()` and `formula/validation.js:381-395`), regardless of how expensive the underlying lookup actually is.

### Finding Description
When a data-feed lookup covers not-yet-stable data (the common `bAA` path used for oracle checks inside an AA formula), `dataFeedExists()` does not use an indexed key-value scan; instead it iterates the entire in-memory `storage.assocUnstableMessages` map — i.e., every currently-unstable unit in the DAG cache — for every single `data_feed`/`in_data_feed` call: [1](#0-0) 

This scan cost is proportional to the size of the unstable/unconfirmed portion of the DAG at call time, which is influenced by overall network load and can be driven up by an attacker flooding the network with many still-unstable units before triggering the AA. The formula-evaluation cost accounting, however, treats this call as constant cost: [2](#0-1) [3](#0-2) 

Because the cost model is a flat "1" per call rather than proportional to `|assocUnstableMessages|`, an attacker can post/trigger an AA whose formula invokes `data_feed`/`in_data_feed` repeatedly (bounded only by `MAX_OPS`/`MAX_COMPLEXITY`, which is a fixed, small budget unrelated to the real per-call cost) inside a single AA response. Each such call re-walks the full unstable-unit cache. `evaluate()` in `formula/evaluation.js` only yields the event loop every 100 evaluation steps via `setImmediate`, so most of this work executes synchronously on Node's single-threaded event loop: [4](#0-3) 

AA triggers themselves are processed strictly sequentially, one at a time, by `handleAATriggers()`/`handleTrigger()`, which run as part of main-chain stabilization (`main_chain.js` calls `handleAATriggers()` after computing commissions, and `writer.js` calls `aa_composer.handleAATriggers()` after every additional stabilization): [5](#0-4) [6](#0-5) 

Just as the VRF `fulfillRandomWords()` callback had a fixed 2.5M gas cap that did not scale with the actual on-chain work performed (healing/wounding/killing loops over many agents), ocore's `MAX_OPS`/`MAX_COMPLEXITY` budget for AA formula execution does not scale with the actual cost of `data_feed`/`in_data_feed` lookups against the unstable-unit cache. The budget was designed as a "gas limit" surrogate to keep AA execution time bounded and predictable, but it under-charges this specific primitive, breaking that guarantee exactly the way the reported bug broke the VRF gas guarantee.

### Impact Explanation
Unlike a value-losing bug, this is a computational DoS: while it is processing a trigger whose formula performs many `data_feed`/`in_data_feed` calls against a large unstable-message cache, the node's main event loop is dominated by this scan. Since stabilization (`markMcIndexStable` → `handleAATriggers`) and AA trigger processing happen serially and inline with the writer's commit path (`writer.js` `saveJoint()`), a sufficiently expensive trigger delays the processing of all subsequent joints, catch-up, and network messages on that node while the trigger executes — i.e., the node becomes temporarily unable to confirm/process new units, mirroring the reported "DoS of the entire contract" until the cause resolves. Because every node must independently execute the same AA trigger deterministically to reach consensus on AA state, this affects the whole network's processing rate for that MCI, not just a single actor's local view.

### Likelihood Explanation
Any user can post a new AA definition (`app: 'definition'`), which is immediately usable, and then trigger it with a normal payment — no special privilege is required (analogous to the "unprivileged unit poster"/"AA trigger sender" class explicitly in scope). The attacker only needs to write a formula that loops `data_feed`/`in_data_feed` calls up to the `MAX_OPS` budget while the network's unstable-DAG cache is reasonably large (which naturally grows under normal transaction load, and can be artificially inflated by the same attacker flooding low-fee/legit-looking units beforehand). No race condition or timing dependency beyond normal usage is required, making this readily reachable, though the magnitude of the resulting delay depends on how large `assocUnstableMessages` is at execution time.

### Recommendation
- Charge `data_feed`/`in_data_feed` complexity proportional to the real cost of the lookup when `bAA` triggers the `assocUnstableMessages` scan path (e.g., proportional to `Object.keys(storage.assocUnstableMessages).length`, or cap/short-circuit the scan and charge accordingly), rather than a flat `1`.
- Alternatively, avoid the O(unstable-units) full scan entirely by indexing unstable data-feed messages by author address (as is already done for stable data via key-prefixed streams in `dataFeedByAddressExists`), so a data-feed lookup against unconfirmed data costs O(matching messages) rather than O(all unstable units).
- Add a hard ceiling on `storage.assocUnstableMessages` size influencing this code path, or make the loop yield periodically (similar to the `count % 100` `setImmediate` pattern already used in `evaluate()`), so a single expensive AA trigger cannot starve the node's event loop for the duration of one huge scan.

### Proof of Concept
Conceptual PoC (cannot be executed without a running network, but the mechanism is directly derivable from the cited code):
1. Attacker posts many small, valid, but not-yet-stable units so that `storage.assocUnstableMessages` grows large (feasible during normal network load, or accelerated by the attacker).
2. Attacker defines an AA whose response formula contains a sequence of `in_data_feed`/`data_feed` calls (up to the `MAX_OPS`/`MAX_COMPLEXITY` ceiling), each querying some oracle address/feed name, e.g.:
   ```
   {
     $x = in_data_feed[[oracles="SOME_ORACLE", feed_name="f1", feed_value=1]];
     $x = in_data_feed[[oracles="SOME_ORACLE", feed_name="f2", feed_value=1]];
     ... (repeated many times up to MAX_OPS)
   }
   ```
3. Attacker sends a payment to this AA to trigger it (`getTrigger`/`handleTrigger` in `aa_composer.js`).
4. During trigger execution, `formula/evaluation.js`'s `data_feed`/`in_data_feed` case repeatedly invokes `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists`, each of which — because `bAA=true` — walks the entire `storage.assocUnstableMessages` map (`data_feeds.js:34-94`), multiplying the real cost by the number of calls, while the flat complexity accounting (`formula/validation.js:26-83`) never reflects this and lets the formula pass validation.
