### Title
Team.find_or_create_by! in MembershipHandler#find_or_create_team! binds membership mutations to a stale `organization` on team_id collision - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` uses `Team.find_or_create_by!(github_id: params.team.id)`, and the `do |team|` block that sets `team.organization = params.organization.login` only runs on record creation, not on find. Because `WebhooksController#verify_signature` derives the org used for HMAC verification independently from `params.organization.login` (via `repository_owner`), a second, genuinely-signed request from a different org for the same `team.id` is accepted and mutates the existing Team's roster without ever re-checking that the verifying org matches the Team's recorded `organization`.

### Finding Description
The broken binding as an equality: `verified_org` (the organization whose webhook secret produced a valid `X-Hub-Signature` for this request, computed in `WebhooksController#verify_signature` as `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`) must equal `team.organization` (the org value stored on the `Team` record being mutated by `MembershipHandler#process`).

Code path:
- `app/controllers/shipit/webhooks_controller.rb:24-49` verifies the signature using `Shipit.github(organization: repository_owner)`, where for a `membership` event `repository_owner` falls back to `params.organization.login` [1](#0-0) . This confirms *only* that org-B (the attacker-controlled org) genuinely signed *this* request; it says nothing about whether org-B is authoritative for `team.id`.
- `MembershipHandler#process` then calls `find_or_create_team!`, and:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [2](#0-1) 
`find_or_create_by!` only yields the block to the initializer when a **new** record is being created; on the first request (org-a) it creates `Team(github_id: X, organization: 'org-a')`. On the attacker's later request (org-b, same `team.id == X`), `find_or_create_by!` finds the existing row and returns it untouched — `team.organization` stays `'org-a'` even though the request that unlocked this code path was verified against org-b's secret.
- `process` then unconditionally does `team.add_member(member)` (for `action == 'added'`) [3](#0-2)  and `Team#add_member` appends to `members` with no organization check [4](#0-3) .

No other guard closes this gap: `drop_unhandled_event` and `verify_signature` only validate event type and signature per-org, not per-`team.id` ownership; the `ExplicitParameters` schema for `MembershipHandler` only enforces types/presence, not organization consistency [5](#0-4) ; `User#authorized?` trusts `teams` membership (`Membership` rows) without re-validating the owning org [6](#0-5) .

Attacker exploit flow: attacker owns/administers GitHub org `org-b` (or any org for which they can genuinely emit signed webhooks) that is configured in this Shipit instance's `secrets.github`. They discover (or guess/enumerate) the numeric GitHub team id `X` of a Team that is a member of `Shipit.github_teams` (an authorization team) and currently owned by `org-a`. From `org-b`, they trigger (or forge, since they control that org's webhook delivery) a `membership` event with `team: { id: X, ... }`, `organization: { login: 'org-b' }`, `member: { login: '<any-github-login>' }`, `action: 'added'`. The request is correctly signed with `org-b`'s webhook secret, so `verify_signature` passes. `find_or_create_team!` finds the pre-existing Team row (created originally under `org-a`) by `github_id: X` and does not update `organization`. `team.add_member(member)` runs, adding an arbitrary GitHub user as a member of that Team in Shipit's database.

### Impact Explanation
If the targeted Team is referenced by `Shipit.github_teams` (used in `User#authorized?` to gate access to the Shipit instance), this bug lets an attacker who controls an unrelated, legitimately-configured GitHub org add arbitrary GitHub users (including themselves) to that authorization team's roster in Shipit's database, without any relationship to `org-a` or its real GitHub team membership. This is an escalation into Shipit's authorization mechanism (`Shipit.github_teams`) for a repository/tenant the attacker does not own, matching the "High - escalation into `Shipit.github_teams` authorization" category. It is repeatable for every Team id known to the attacker, and works even against Teams unrelated to the attacker's own org, as long as attacker's org is a legitimately configured Shipit-integrated org and the attacker knows/guesses the target's numeric `team.id`.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured with multiple GitHub organizations (`secrets.github` with multiple orgs) since a single-org Shipit installs typically share one webhook secret/org and this scenario collapses; (2) the target Team must already exist (created via a prior legitimate membership event from `org-a`) with a `github_id` known to the attacker — GitHub team ids are sequential/enumerable but not public by default, so the attacker needs some information leak or brute force to learn `X`; (3) the attacker's own org (`org-b`) must be a genuinely configured Shipit-integrated GitHub org, i.e. they must be an org owner/admin of an org that this Shipit instance trusts — this is a real but non-trivial precondition (multi-tenant Shipit deployments where multiple independent orgs are configured, e.g. hosted/shared Shipit instances). Attacker cost is low once these are met: no secrets are needed, only the ability to trigger a webhook delivery from their own org (e.g., via the GitHub UI, adding/removing a member from a team in their own org, which GitHub itself sends signed).

### Recommendation
In `MembershipHandler#find_or_create_team!`, always re-validate/update team identity fields against the verified request instead of relying on `find_or_create_by!`'s create-only block: after finding (or creating) the Team, assert `team.organization == params.organization.login` (or update it transactionally with an audit trail) and raise/reject the webhook if the verified org does not match the Team's recorded owning org. Alternatively, scope the lookup by both `github_id` and `organization` (`find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and treat any `github_id` collision under a different org as an error/log-worthy anomaly rather than silently succeeding.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual, minitest)
module Shipit
  module Webhooks
    module Handlers
      class MembershipHandlerTest < ActiveSupport::TestCase
        test "does not add a member when the verified org differs from the team's stored organization" do
          team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 1
          assert_equal 'shopify', team.organization

          payload = {
            'action' => 'added',
            'team' => { 'id' => team.github_id, 'name' => team.name, 'slug' => team.slug, 'url' => team.api_url },
            'organization' => { 'login' => 'attacker-org' }, # verified org != team.organization
            'member' => { 'login' => 'walrus' }
          }

          # Simulate that request was already signature-verified for 'attacker-org'
          MembershipHandler.call(payload)

          team.reload
          # Binding under test: verified_org ('attacker-org') != team.organization ('shopify')
          refute_equal 'attacker-org', team.organization
          # Vulnerable behavior: member gets added despite the mismatch
          refute team.members.map(&:login).include?('walrus'),
                 "expected membership NOT to be added when webhook org does not match team's owning org"
        end
      end
    end
  end
end
```
This test creates the pre-existing `shipit_teams(:shopify_developers)` fixture (org `shopify`), then calls the handler with `organization.login == 'attacker-org'` for the same `team.id`, asserting (post-fix) that the mismatch is rejected — currently (pre-fix) the assertion fails because `team.add_member(member)` proceeds and `'walrus'` is added despite the organization mismatch.
