### Title
Independent per-recipient rounding of `earned_headers_commission_share` can inflate or leak headers-commission payouts - ([File: headers_commission.js])

### Summary
`headers_commission.js` splits a header-commission amount (`full_amount`) among multiple `earned_headers_commission_recipients` by computing each recipient's share independently with `Math.round(full_amount * share / 100.0)`, exactly like the DODO `_multiSwap` bug where `curAmount = curTotalAmount * weight / totalWeight` is computed per-pool without tracking the cumulative remainder. Because each recipient is rounded in isolation instead of using an accumulator that assigns the last recipient "whatever remains," the sum of the rounded payouts can differ from `full_amount`. [1](#0-0) [2](#0-1) 

### Finding Description
Any unit poster with more than one author must supply `earned_headers_commission_recipients`, and `validation.js` only enforces that the declared integer shares sum to exactly 100 - it does not constrain how many recipients there are or their individual share sizes. [3](#0-2) 

When that unit later wins a headers commission, `calcHeadersCommissions` computes `full_amount` (an integer amount of bytes) and then, for each recipient, computes `amount = Math.round(full_amount * share / 100.0)` independently: [4](#0-3) [5](#0-4) 

This is structurally identical to the DODO bug: a total amount is divided into proportional shares via `total * weight / totalWeight` for each participant without an accumulator to correct for the accumulated rounding error on the last participant. Because JavaScript's `Math.round` rounds .5 up independently for each recipient, it is straightforward to choose two or more integer shares (e.g., 50/50, or any split summing to 100) and a `full_amount` such that the sum of the independently rounded amounts exceeds `full_amount` (over-payment / inflation) or falls short of it (dust loss). For example, with shares `50` and `50` and `full_amount = 3`: `round(3*50/100) = round(1.5) = 2` for each recipient, so `2 + 2 = 4 > 3` — the two recipients are jointly credited 4 bytes of headers commission even though only 3 bytes were actually earned/available from the payer unit.

These per-recipient amounts are inserted verbatim into `headers_commission_contributions` and subsequently aggregated into `headers_commission_outputs`, which become real spendable balances credited to addresses: [6](#0-5) [7](#0-6) 

There is no reconciliation step anywhere in `calcHeadersCommissions` that checks `SUM(amount)` per `child_unit`/`payer_unit` against `full_amount` before insertion — the DODO report's exact recommended fix (accumulate distributed amount and give the remainder to the last recipient) is absent here as well.

### Impact Explanation
Because the resulting per-address amounts are written into `headers_commission_contributions`/`headers_commission_outputs`, which directly determine spendable balances (per `balances.js` usage of that table), a rounding-favorable split allows the sum of credited headers commission to exceed the actual `headers_commission` amount recorded on the payer unit. This is a form of supply inflation reachable by any user who authors a multi-author unit with a crafted `earned_headers_commission_recipients` list and later wins headers commission on a subsequent child unit — no privileged role is required. Conversely, unfavorable splits silently burn a small amount of commission (dust loss), which is a lesser, but still incorrect, accounting bug affecting fund distribution fairness/finality of state committed by `calcHeadersCommissions`, a process every full node runs identically, so all nodes would agree on the (subtly wrong) result — meaning this manifests as a consistent but incorrect application-level inflation rather than a node-disagreement/fork issue.

### Likelihood Explanation
Likelihood is straightforward: the attacker only needs to define a multi-authored unit (or reuse an existing valid multi-author flow) with `earned_headers_commission_recipients` shares chosen (e.g., 50/50, or any combination where fractional halves align) so that per-recipient rounding pushes the sum above `full_amount`. Winning a headers commission for such a unit is a normal part of protocol operation (`getWinnerInfo` in `headers_commission.js`) and does not require any special privilege, network position, or race condition beyond normal unit posting and standard chain progression. [8](#0-7) 

### Recommendation
In `headers_commission.js`, when distributing `full_amount` (or the header-commission `hc` amount) across `earned_headers_commission_recipients` (both the in-memory `arrValuesRAM` path and the SQL/`profit_distribution_rows` path), maintain a running total of already-distributed amount. For all but the last recipient, use `Math.round(full_amount * share / 100.0)` as today, but for the last recipient in the sorted list, assign `full_amount - runningTotal` instead of an independently rounded value, guaranteeing the sum of distributed amounts always equals `full_amount` exactly. Apply the same fix to the SQL `ROUND(...)` computation path in the MySQL branch and to any other independent per-recipient share splitting of a fixed total (e.g., the analogous `tps_fees_delta` split in `storage.js`'s `updateTpsFees`, which uses `Math.floor(total_tps_fees_delta * share / 100)` per recipient with the same unaccounted-remainder pattern) should also be reviewed for the same class of drift. [9](#0-8) 

### Proof of Concept
1. Author a multi-signed unit `U1` (2 authors, A and B) with `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]`. `validation.js` accepts this since `50 + 50 = 100`. [10](#0-9) 
2. Ensure `U1` is chosen as the winning child (`getWinnerInfo`) for a parent unit `P` whose `headers_commission` is an odd number, e.g. `3` bytes, so that `full_amount = 3`. [11](#0-10) 
3. `calcHeadersCommissions` computes, for each recipient: `amount = Math.round(3 * 50 / 100.0) = Math.round(1.5) = 2` for A and 2 for B. [1](#0-0) 
4. Total inserted into `headers_commission_contributions` for payer unit `P` is `2 + 2 = 4`, one byte more than the actual `headers_commission` of `3` recorded on `P`. This extra byte becomes spendable balance for A and B combined, i.e., commission payout exceeds the amount actually assessed/available — a concrete instance of unauthorized fund creation via rounding, reachable purely by an unprivileged unit author choosing recipient shares and relying on normal network processing.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
