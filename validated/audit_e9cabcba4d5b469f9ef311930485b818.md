### Title
Improper Privilege Management in `handleNewSharedAddress` allows a paired device to hijack cosigner routing for addresses it does not control - (File: wallet_defined_by_addresses.js)

### Summary
`handleNewSharedAddress()` in `wallet_defined_by_addresses.js` accepts a `"new_shared_address"` message from any paired correspondent device and persists the `signers` map — including the attacker-supplied `device_address` for every signing path — into `shared_address_signing_paths` almost verbatim. The only self-protective check performed is `determineIfIncludesMeAndRewriteDeviceAddress()`, which rewrites `device_address` **only** for paths whose `address` is one of the local wallet's own `my_addresses`. For every other signing path (addresses belonging to third parties, e.g. genuine cosigners), the claimed `device_address` is trusted unconditionally and written into the database, even though nothing proves that this device actually controls the corresponding key/address.

### Finding Description
The message handler chain is:
- `wallet.js` `case "new_shared_address"` dispatches directly to `walletDefinedByAddresses.handleNewSharedAddress(body, ...)` [1](#0-0) 
- `handleNewSharedAddress` validates only structural properties: definition shape, chash(`body.definition`) === `body.address`, that each `signerInfo.address` is a syntactically valid address, and that the addresses embedded in `body.signers` match the `["address", ...]` leaves extracted from the definition via `extractAddressPathsFromDefinition` [2](#0-1) . None of these checks verify that the `device_address` field of a `signerInfo` corresponds to a device that actually possesses the signing key for that `address`.
- `determineIfIncludesMeAndRewriteDeviceAddress` only fixes up `device_address` for paths whose `address` is in the *local* wallet's `my_addresses`/`shared_addresses`; it does not validate `device_address` for any other party's address [3](#0-2) .
- The unmodified `body.signers` (attacker controlled for all non-local paths) is then persisted by `addNewSharedAddress`, inserting `(shared_address, address, signing_path, member_signing_path, device_address)` rows straight from the message [4](#0-3) .

`shared_address_signing_paths.device_address` is later trusted as authoritative for two privileged operations that should only be available to the real key holder of that path:
1. **Signing routing** — `findAddress()` looks up `device_address` for a signing path of a shared address and, if it's not the local device, treats it as `ifRemote` and forwards the entire unsigned unit (including private-payload metadata) to that device for signing [5](#0-4) . An attacker who registered themselves as `device_address` for a third party's signing path will now receive genuine signing requests intended for that party.
2. **Private-payment chain forwarding** — `forwardPrivateChainsToOtherMembersOfAddresses()` selects `device_address` from `shared_address_signing_paths` (joined with `correspondent_devices`) for the shared address and forwards full private payment chains to it via `walletGeneral.forwardPrivateChainsToDevices` [6](#0-5) [7](#0-6) .

This is directly analogous to CVE-2021-45230: a party that only has permission to perform one action ("create"/introduce a shared-address record it participates in) is able to silently grant itself a different, higher privilege (acting as signer/cosigner-of-record for an address it does not control) because the authorization check validates the wrong scope (structural consistency of the definition) instead of verifying that the claimant is actually entitled to be registered as the controller of that signing path.

### Impact Explanation
A malicious paired device can:
- Intercept unsigned units (and their `private_payloads`, including recipient addresses, blinding factors and amounts of otherwise-private outputs) sent by the victim for a shared/multisig address, by claiming to be the `device_address` for a cosigner path it does not actually control — enabling the attacker to eavesdrop on genuinely private transaction data ("private-payment counterparty" attack surface explicitly in scope).
- Cause denial of cosigning / freezing of funds: because the real cosigner never receives the signing request (it goes to the attacker instead), a wallet composing a payment from that shared address may never obtain the necessary cosignature, effectively freezing spending from the multisig address.
- Receive forwarded private payment chains destined for legitimate cosigners, an unauthorized disclosure of sensitive private-payment data that only the actual cosigner device should be able to receive.

This satisfies the required impact bar ("AA fund loss or freezing" analog / concrete unauthorized access to private-payment chain data) rather than being a mere information-only or resource-exhaustion issue.

### Likelihood Explanation
The attack requires only that the victim be paired with the malicious device (a normal, low-privilege trust relationship established for any wallet cosigning scenario, exactly matching the "paired device" actor explicitly allowed in scope) and that the victim's wallet is later asked to compose/sign a transaction from, or route private payments through, a shared address that includes an address controlled by another (non-attacker) party alongside the attacker's spoofed entry. No cryptographic forgery, hub compromise, or network-level attack is needed — a single crafted `"new_shared_address"` message suffices, making this readily reachable and moderate-to-high likelihood in any multisig/shared-address wallet workflow.

### Recommendation
- In `handleNewSharedAddress`, do not blindly trust `signerInfo.device_address` for third-party addresses. At minimum:
  - Reject/flag registrations where `device_address` for a path does not match a device already known to control that `address` (e.g. via prior legitimate introduction from the address owner, or a signed attestation from the claimed device/address).
  - Require that entries for non-local addresses only be accepted/updated when they originate from the correspondent device that is itself listed as the owner of that address (`from_address === signerInfo.address`'s known device), or from the address owner directly, rather than from an arbitrary third device claiming knowledge of the mapping.
- Add a conflict-detection mechanism: if a `shared_address_signing_paths` row for `(shared_address, signing_path)` already exists with a different `device_address` than what's being proposed, do not silently overwrite it — surface the conflict to the user rather than trusting the newest message (`db.getIgnore()` in the current `INSERT` silently no-ops rather than resolving a mismatch, which is also risky if the row already existed with correct data, but does nothing to stop a first-write hijack).
- Consider requiring an explicit signed confirmation/handshake from the device that will act as the actual signer for a given `address`, before wiring up `sign`/private-payment routing to it.

### Proof of Concept
1. Attacker pairs their device with the victim's wallet (a normal, unprivileged pairing relationship).
2. The victim participates (or will participate) in a legitimate multisig/shared address with a third cosigner "C" whose address is `ADDR_C`.
3. Attacker crafts and sends a `"new_shared_address"` device message to the victim:
   ```json
   {
     "subject": "new_shared_address",
     "body": {
       "address": "<chash of arrDefinition>",
       "definition": ["and", [["address","ADDR_VICTIM"], ["address","ADDR_C"]]],
       "signers": {
         "r.0": { "address": "ADDR_VICTIM" },
         "r.1": { "address": "ADDR_C", "device_address": "<ATTACKER_DEVICE_ADDRESS>" }
       }
     }
   }
   ```
4. `handleNewSharedAddress` passes structural validation (definition hashes to `body.address`; `signerInfo.address` at each path matches definition leaves; every leaf has a signer). `determineIfIncludesMeAndRewriteDeviceAddress` finds the victim owns `ADDR_VICTIM` (rewriting only that path) but leaves `r.1`'s `device_address` as the attacker's, since `ADDR_C` is not one of the victim's own addresses.
5. `addNewSharedAddress` inserts `shared_address_signing_paths` with `(shared_address, ADDR_C, r.1, ..., ATTACKER_DEVICE_ADDRESS)`.
6. When the victim later composes a spend from the shared address, `findAddress()` resolves the cosigner slot for `ADDR_C` to the attacker's device and sends it the unsigned unit (and any `private_payloads`) for "signing" — the attacker now sees the private transaction data and can simply refuse to sign, blocking the spend, or forward it while probing the victim for information.

Note: full confirmation that no independent server-side or hub-side check re-validates `device_address` ownership before message delivery was not verified beyond the code paths shown (i.e., `device.sendMessageToDevice` and hub relay logic were not inspected in depth); this determination is based on the client-side (`ocore`) logic reviewed above, which is the code intended to enforce this authorization.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
