### Title
Webhook signature is verified against `repository.owner.login`'s org secret but the acted-upon repository is resolved from the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate the HMAC against using `repository_owner`, which is read from `payload.dig('repository','owner','login')` (or `organization.login`). All downstream event handlers, however, resolve the repository/stack to actually act on using a completely different payload field, `repository.full_name`, via `Handler#repository_name` and `Repository.from_github_repo_name`. Nothing enforces that these two fields agree, so the field that gates "whose secret authenticates this request" is decoupled from the field that determines "which repository gets acted on" — the same class of defect as the DKIM report, where the field used to prove authenticity differs from the field actually consumed.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
selects the app config via `Shipit.github(organization: repository_owner)`, and [2](#0-1) 
derives `repository_owner` solely from `repository.owner.login` (or `organization.login`) in the JSON body.

`Shipit.github` looks up the per-organization `webhook_secret` from `secrets.github[organization]`: [3](#0-2) 
This confirms the engine's documented multi-tenant model: a single Shipit instance can host multiple GitHub organizations, each with its own independent `webhook_secret` (see `config/secrets.development.shopify.yml` listing `somegithuborg`/`someothergithuborg`).

Once the signature check passes, `create` dispatches the same raw JSON body to handlers: [4](#0-3) 
Every handler resolves the target repository/stack from an entirely different field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

Since `repository.owner.login` (used to select the trusted secret) and `repository.full_name` (used to select the acted-upon repository) are two independent, attacker-controlled JSON fields with no cross-check that they refer to the same repository/owner, an event whose signature was validated against organization A's secret can carry a `repository.full_name` pointing into organization B's repository/stack. The equality that must hold — *organization whose secret authenticated the request* == *organization that owns the repository being written to* — is not enforced anywhere in `verify_signature`, `Handler#repository_name`, or `Repository.from_github_repo_name`.

### Impact Explanation
An attacker who can produce a validly-signed webhook body for any one organization configured in this Shipit instance (e.g. because they administer/own a GitHub App installation for organization A that is also configured in this multi-tenant Shipit deployment) can forge `repository.full_name` = `"victim-org/victim-repo"` while keeping `repository.owner.login` = `"attacker-org"` so the HMAC check runs against attacker-org's own known secret. This lets the attacker trigger cross-repository/cross-organization state changes — e.g. `PushHandler` calling `stack.sync_github(expected_head_sha: params.after)` against a victim stack for a fabricated `after` SHA, `PullRequest`-family handlers creating/archiving review stacks for a victim's repository, or membership/team handlers manipulating access data — none of which the attacker is authorized to write to. This is a cross-repository-write class issue.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured for more than one GitHub organization sharing infrastructure but with a distinct `webhook_secret` per org (a documented, supported configuration), and the attacker must control (or already have legitimate delivery rights for) one of those organizations' webhook secrets. Given that constraint, forging the mismatched JSON payload requires no special access — a plain crafted `X-Hub-Signature` computed with the attacker's own known secret over an attacker-authored JSON body suffices; no session, API token, or GitHub write access to the victim org is needed.

### Recommendation
In `verify_signature`, after computing the HMAC-authenticated organization, cross-validate that the same organization is what every downstream handler will act on: require `repository.owner.login` == the owner segment of `repository.full_name` before dispatching (or better, derive the sole source of truth for "target repository" once in the controller and pass it down, rather than letting each handler independently re-parse `full_name`). At minimum, reject webhooks where `params.dig('repository','full_name')&.split('/')&.first` disagrees with `repository_owner`.

### Proof of Concept
1. Shipit is configured with two orgs in `secrets.github`: `attacker-org` (attacker knows/controls its `webhook_secret`) and `victim-org` (hosts a tracked `Stack`/`Repository` in this Shipit instance).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully because the HMAC matches attacker-org's secret [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack [7](#0-6) [5](#0-4) , despite the request never being authenticated with `victim-org`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
