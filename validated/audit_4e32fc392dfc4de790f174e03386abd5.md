## Analog Found

The Zivoe report describes a Synthetix-style rewards accounting bug: the "last update time" clock advances even when there are zero stakers, so reward tokens meant for that period are treated as already distributed, yet nobody receives them — and the funds become stuck. This exact bug-class is reproduced in the Polkadot SDK's `pallet-asset-rewards`, which is itself a Substrate port of the same Synthetix `StakingRewards` design.

### Title
Reward accrual clock advances while `total_tokens_staked == 0`, silently forfeiting reward-period funds to a stuck pool account - (`substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` computes rewards using a `reward_per_token_stored` accumulator and a `last_update_block` checkpoint, mirroring Synthetix's `rewardPerTokenStored`/`lastUpdateTime` pattern. `reward_per_token()` correctly skips accrual when `total_tokens_staked` is zero, but `update_pool_rewards()` unconditionally advances `last_update_block` to the current block regardless of whether anyone was staked. Any signed account can permissionlessly fund a pool via `deposit_reward_tokens`. When a pool has no stakers (e.g., before the first `stake`, or after all stakers fully `unstake`), the reward amount implied by `reward_rate_per_block × elapsed_blocks` for that dead window is neither accrued to any staker nor preserved for future ones — it is simply skipped and the underlying tokens sit unclaimed in the pool's pot account, recoverable only by the pool `admin` via `cleanup_pool`, and only while the pool currently has zero active stakers.

### Finding Description
The reward math lives in: [1](#0-0) 

`reward_per_token()` returns the stored value unchanged when `total_tokens_staked.is_zero()`, i.e. it deliberately does not accrue reward during zero-stake periods. However, `update_pool_rewards()`, which is always called right after `reward_per_token()` in `update_pool_and_staker_rewards`, `set_pool_reward_rate_per_block`, and `set_pool_expiry_block`, unconditionally moves the checkpoint forward: [2](#0-1) 

Because `last_update_block` is advanced to "now" every time these functions run — even while `total_tokens_staked == 0` — the elapsed-block window during which nobody was staked is permanently excised from the accrual timeline. When a new staker later joins via `stake()`: [3](#0-2) 

`update_pool_and_staker_rewards` is invoked before the new stake is applied, so `reward_per_token` reflects zero growth for the dead window; the new staker's `reward_per_token_paid` is set to the (unchanged) stored value, and rewards for that window are never assigned to anyone — not the previous stakers who already unstaked, not the new one.

Meanwhile, `deposit_reward_tokens` is a completely permissionless entry point (any signed account, no admin check) that transfers reward-asset tokens into the pool's pot account ahead of time: [4](#0-3) 

Those tokens, once in the pot, can only leave via `harvest_rewards` (paying out a staker's `rewards` field, which never includes the skipped-window amount) or via `cleanup_pool`: [5](#0-4) 

`cleanup_pool` requires `origin == pool_info.admin` and that `PoolStakers` for the pool is currently empty. This means the tokens corresponding to any zero-stake window are:
1. Never credited to any staker's claimable `rewards`.
2. Only retrievable by the pool `admin` (a privileged role distinct from whoever called `deposit_reward_tokens`), and only at a moment when the pool happens to have zero active stakers.
3. If the pool never returns to a fully-empty `PoolStakers` state (e.g., stakers keep rotating in/out, or nobody ever calls `cleanup_pool`), the funds remain stuck in the pot account indefinitely, unreachable by anyone.

This is the same root cause as the Zivoe finding: the reward "clock" (`last_update_block` / `lastUpdateTime`) advances during no-staker windows even though the corresponding per-token accumulator does not, so the pallet's internal accounting believes those rewards were already distributed, when in fact they were distributed to nobody.

### Impact Explanation
Any reward tokens funded (via the permissionless `deposit_reward_tokens` call, or pre-funded before creation) that correspond to a window where `total_tokens_staked == 0` are permanently excluded from any staker's payout and become effectively unrecoverable except through a privileged admin action requiring a specific pool state (zero current stakers). In common lifecycle patterns — pool created before first staker joins, or all stakers exit and re-enter later — this can lock a portion of reward-asset funds in the pallet's pot account, unavailable to depositors, stakers, or (until the exact zero-staker condition is met) even the admin. This matches a Medium-severity fund-lock/misallocation class, not a critical fund-theft, since no attacker directly extracts value; value is simply misplaced/stuck.

### Likelihood Explanation
Reaching the zero-staker window requires no privileged action: `create_pool` is gated by `CreatePoolOrigin` (a runtime-configured, potentially permissioned origin), but ordinary events like "no one has staked yet" or "every staker fully unstakes at some point during a long-lived pool" are completely ordinary, non-adversarial scenarios. `deposit_reward_tokens` itself is fully permissionless and requires no special role, so any user pre-funding a pool, or a natural lull in staking participation, triggers the loss. This is a design/accounting flaw, not something requiring an attacker with elevated privileges, matching the "no privileged role" requirement of the scan.

### Recommendation
When `total_tokens_staked` is zero, do not advance `last_update_block` in `update_pool_rewards` (or equivalently, track a separate "reward start" checkpoint that only advances once stakers exist), so unearned reward-per-block amounts accumulate against `reward_rate_per_block` for the *next* staker rather than being silently discarded. Alternatively, allow the admin (or a permissionless sweep function) to reclaim/redirect stranded reward-window funds without requiring the `PoolStakers` map to be fully empty at the time of reclaim.

### Proof of Concept
No executable PoC was run against a live node in this session; the finding is based on static analysis of the accrual logic cited above (`reward_per_token`, `update_pool_rewards`, `stake`, `deposit_reward_tokens`, `cleanup_pool`) together with the pallet's existing test suite pattern, e.g. `create_sets_recorded_data`/`join_updates_recorded_data`-style tests in `substrate/frame/asset-rewards/src/tests.rs`, which exercise pool creation and staking sequencing but do not appear to specifically test the "reward accrued while `total_tokens_staked == 0`, later diluted/lost" scenario: [6](#0-5) 
A minimal integration reproduction would: (1) call `create_pool` with a nonzero `reward_rate_per_block`, (2) advance several blocks with `total_tokens_staked == 0`, (3) call `deposit_reward_tokens` to fund the pot for the intended duration, (4) call `stake` from a first staker, and (5) assert that `Pools::<T>::get(pool_id).reward_per_token_stored` and the staker's eventual `harvest_rewards` payout do not include the reward amount implied by `reward_rate_per_block × blocks elapsed before staking`, while confirming those tokens remain in the pool's `account` balance and are inaccessible except via `cleanup_pool` under the admin's exclusive control.

		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
