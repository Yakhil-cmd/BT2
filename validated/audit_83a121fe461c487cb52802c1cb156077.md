### Title
Unauthenticated P2PStakingInfo Accepted During FastSync Corrupts Persisted Reward Distribution State — (`datasync/downloader/downloader.go`, `kaiax/staking/impl/schema.go`)

### Summary

During FastSync, a malicious peer can serve fabricated `P2PStakingInfo` (with attacker-chosen `CouncilStakingAmounts`, `CouncilNodeAddrs`, `CouncilRewardAddrs`) for blocks at `stakingUpdateInterval` boundaries. This data flows through `queue.DeliverStakingInfos` → `commitFastSyncData` → `PutStakingInfoToDB` and is written to the chain database with no content validation. The persisted staking info is subsequently used by the reward module for all reward distribution calculations, directing block rewards to attacker-controlled addresses.

### Finding Description

The `P2PStakingInfo` struct carries all fields that govern reward distribution: [1](#0-0) 

These fields are **not cryptographically bound to the block headers**. During FastSync, headers are validated via consensus signatures, but the staking info is a separate data item fetched from the peer and delivered via `queue.DeliverStakingInfos`. The `fetchResult` struct holds both independently: [2](#0-1) 

The persistence path `PutStakingInfoToDB` simply marshals and writes to the DB with zero validation: [3](#0-2) 

The `WriteStakingInfo` function it calls also performs no cross-validation against the state trie: [4](#0-3) 

The comment on `GetStakingInfoFromDB` confirms this DB path is specifically the one used for P2P sync, not a re-derived path: [5](#0-4) 

The `ToStakingInfo` conversion from `P2PStakingInfo` to `StakingInfo` is a direct field copy with no invariant checks: [6](#0-5) 

### Impact Explanation

A victim node completing FastSync will have its `stakingInfo` DB entries for all synced `stakingUpdateInterval` boundary blocks replaced with attacker-chosen values. The reward module reads these DB entries to determine:
- Which addresses receive block proposer/staking rewards (`CouncilRewardAddrs`)
- How rewards are proportionally split (`CouncilStakingAmounts`)
- KEF/KIF fund addresses

This constitutes unauthorized redirection of KAIA block rewards to attacker-controlled addresses, meeting the "Unauthorized transfer... reward distribution... affecting KAIA... system-managed funds" impact gate.

### Likelihood Explanation

- **Attacker entry point is permissionless P2P**: any node can connect as a FastSync peer.
- **Headers are independently validated** (consensus signatures), but staking info is not bound to them — the attacker can serve real canonical headers obtained from the network while fabricating the staking info payload.
- **No authentication or content validation** exists at any point in the `DeliverStakingInfos` → `commitFastSyncData` → `PutStakingInfoToDB` path.
- Nodes performing initial sync (a common operational state) are fully exposed.

### Recommendation

1. After FastSync completes (or during pivot block processing), re-derive staking info from the canonical state trie for all `stakingUpdateInterval` boundary blocks and compare against the peer-delivered values; reject or overwrite on mismatch.
2. Implement the `validate` stub (noted as TODO) to verify that `P2PStakingInfo.CouncilStakingAmounts` matches the on-chain balances of `CouncilStakingAddrs` at the claimed `BlockNum`.
3. Treat peer-delivered staking info as untrusted input that must be verified against the authenticated state root before persistence.

### Proof of Concept

Integration test outline:
1. Start a "malicious" peer serving a valid canonical header chain but with `P2PStakingInfo` where `CouncilRewardAddrs` are replaced with attacker addresses and `CouncilStakingAmounts` are doubled.
2. Have a victim node FastSync from this peer.
3. After sync, call `ReadStakingInfo` for a `stakingUpdateInterval` boundary block — assert it returns the fabricated values.
4. Trigger reward distribution for a block in the post-sync range — assert rewards are sent to the attacker's addresses rather than the legitimate validator reward addresses. [7](#0-6)

func ReadStakingInfo(db database.Database, num uint64) *staking.StakingInfo {
	b, err := db.Get(stakingInfoKey(num))
	if err != nil || len(b) == 0 {
		return nil
	}

	var sl staking.StakingInfoLegacy
	if err := json.Unmarshal(b, &sl); err != nil {
		logger.Error("Malformed staking info", "num", num, "err", err)
		return nil
	}
	return sl.ToStakingInfo()
}

	b, err := json.Marshal(si)
	if err != nil {
		logger.Error("Failed to marshal StakingInfo", "num", num, "err", err)
		return
	}

	if err := db.Put(stakingInfoKey(num), b); err != nil {
		logger.Crit("Failed to write StakingInfo", "num", num, "err", err)
	}
}
