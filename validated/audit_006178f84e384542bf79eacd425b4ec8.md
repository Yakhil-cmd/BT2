### Title
Cross-repository Status webhook forgery lets an attacker mark a victim stack's commit deployable, triggering an unauthorized `Shipit.user` deploy - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the commit to update by SHA alone (`Commit.where(sha: params.sha)`), with no check that the webhook's originating `repository.full_name` matches the `stack.repository` that owns that commit. Because git commit SHAs are content-addressed, an attacker who owns any GitHub repository legitimately onboarded to Shipit can produce (via forking/cherry-picking) a commit whose SHA collides with a commit that also exists in an unrelated victim stack, then use their own, real GitHub credentials to post a status for that SHA. The resulting genuine, correctly-signed webhook is applied to every `Shipit::Commit` row sharing that SHA across the whole installation, including the victim's, making it `deployable?` and letting `Stack#trigger_continuous_delivery` fire `trigger_deploy(commit, Shipit.user, ...)`.

### Finding Description
Binding claimed to hold: `webhook_signing_repository.full_name == commit.stack.repository.full_name` (the entity certifying CI state for a commit must be the same entity that owns the stack/repo the commit belongs to).

Code path:
1. `WebhooksController#verify_signature` only validates that the payload is signed by the secret configured for `repository_owner` (`params.dig('repository','owner','login')`), i.e., it proves "this webhook really came from GitHub for *some* org/repo that owns a configured secret" [1](#0-0) , [2](#0-1) . It does **not** prove the webhook is authorized for any particular commit or stack.
2. `StatusHandler#process` takes the attacker-controlled `sha`, `state`, `context`, `description`, `target_url` fields and applies them to **every** `Commit` row with a matching `sha`, regardless of which stack/repository that commit belongs to: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .
3. `Commit#create_status_from_github!` → `statuses.replicate_from_github!` records the forged status with no cross-check against `stack.repository` [4](#0-3) .
4. `Stack#next_commit_to_deploy` selects the newest `reachable` commit for which `deployable_commits` finds `commit.deployable?` true [5](#0-4) , [6](#0-5) . `deployable?` is driven by the commit's status/check-run state, which the forged Status now satisfies (attacker fully controls `context`, so they can match whatever `required_statuses`/`ci/travis`-style context the victim stack expects).
5. `Stack#trigger_continuous_delivery` then calls `trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)` [7](#0-6) , which builds and runs a real `Deploy` as the privileged `Shipit.user`, entering the `Command`/`PTY.spawn` pipeline.

Root cause: the webhook layer authenticates *who sent the request* (an org/repo owner with a valid app secret) but the domain handler (`StatusHandler`) never re-checks that the sender's repository is the one that actually owns the target commit before mutating that commit's CI state. `Commit.reachable`/`Stack.commits` scoping is bypassed entirely because the lookup is a bare `Commit.where(sha:)` across the whole table.

Attacker's exact request: attacker owns (or forks) a GitHub repository that is (or can be) onboarded as a Shipit stack, ensuring at least one commit shares an identical SHA with a commit in the victim stack (trivial via fork, since fork commits keep identical SHAs, or via `git commit-tree`/cherry-pick reproducing author/committer/timestamp/tree). Attacker then uses their own (legitimate) GitHub token to `POST /repos/{attacker}/{repo}/statuses/{sha}` with `state=success` and `context` matching the victim stack's required context. GitHub delivers a real, correctly-signed `status` webhook to Shipit's `/webhooks` endpoint for the attacker's own org — this passes `verify_signature` — and `StatusHandler#process` then updates the victim's commit as well.

Existing guards checked and found insufficient: `verify_signature`/`GitHubApp#verify_webhook_signature` only proves the message is from a legitimate GitHub org configured in Shipit — it says nothing about which commit/stack the payload may affect [8](#0-7) . `drop_unhandled_event` doesn't apply (status is a handled event). The `StatusHandler` `ExplicitParameters` schema has no repository field to validate against [9](#0-8) .

### Impact Explanation
A commit belonging to a victim stack can be marked "CI green" and deployed by the trusted `Shipit.user` identity through the `Command`/`PTY.spawn` deploy pipeline (carrying `GITHUB_TOKEN`) without that repository's real CI ever certifying it — this is an unauthorized deploy triggered by a payload originating from an unrelated repository, i.e., "a payload for one repository mutating another's stack/commit" per the Critical impact category. This is repeatable against any stack whose commits happen to share a SHA with a repository the attacker controls (forks of public repos being the trivial case), and it works across organizational boundaries since the SHA-based lookup has no tenant scoping.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true`, a `cached_deploy_spec`, and no active task (all stated as scenario preconditions) [7](#0-6) . The attacker needs (a) a repository they legitimately own/control that is or becomes onboarded to Shipit (giving them a real, valid webhook signature path), and (b) a commit SHA collision with a commit already present in the victim stack — trivially achieved by forking a public repo the victim also builds from, since fork commits preserve their original SHA. No secrets, sessions, or privileged roles are required; cost is essentially "own or fork a repo and hit GitHub's own status API," fully within the declared attacker capabilities.

### Recommendation
In `StatusHandler#process` (and the analogous check-run/commit-status paths), scope the commit lookup to commits whose `stack.repository` matches the webhook's `repository.full_name` (or `organization.login`) instead of matching by bare `sha`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: payload_repository_full_name }).each { ... }`. Reject/ignore the event if the derived repository doesn't match any commit's owning stack.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (StackTest-style)
test ":status webhook from an unrelated repository should not make a foreign stack's commit deployable" do
  victim_stack = shipit_stacks(:shipit) # e.g. repo shopify/shipit-engine
  victim_commit = shipit_commits(:second) # belongs to victim_stack, not yet deployable

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => victim_stack.required_statuses.first, # attacker sets whatever context is required
    'branches' => [{ 'name' => victim_stack.branch }],
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }.to_json

  refute_predicate victim_commit, :deployable?

  post :create, body: forged_payload, as: :json

  victim_commit.reload
  # binding check: webhook repository ('attacker/unrelated-repo') != victim_commit.stack.repository.full_name
  refute_equal 'attacker/unrelated-repo', victim_commit.stack.repository.full_name
  assert_predicate victim_commit, :deployable?, "unrelated repo's status should not have made this commit deployable"

  assert_difference -> { Deploy.count }, 0 do
    victim_stack.trigger_continuous_delivery
  end
  # currently FAILS: Deploy.count increments because next_commit_to_deploy picks up victim_commit
  # and trigger_deploy(commit, Shipit.user, ...) runs it.
end
```
Both sides of the binding (`'attacker/unrelated-repo'` vs `victim_commit.stack.repository.full_name`) diverge, yet the status is applied and the deploy triggers — confirming the vulnerability.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
