### Title
Hookify's own guardrail rules can be self-modified and take effect immediately, letting an agent disable its own safety block and act under the weakened rule in the same turn - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The `hookify` plugin implements a PreToolUse/PostToolUse/Stop/UserPromptSubmit guardrail system that is entirely driven by `.claude/hookify.*.local.md` rule files, re-read fresh on every single tool call with no caching, session lock, or restart requirement. The same agent session that is constrained by these rules is also given, via the `/hookify` command, unrestricted `Write` access to create or edit those exact rule files, and the plugin explicitly advertises that "no restart needed - rules take effect on the very next tool use." This mirrors the reported multisig bug class: a privileged execution flow can rewrite the parameters that govern its own future authorization decisions and then immediately benefit from the weakened parameters within the same execution context, before any independent review takes place.

### Finding Description
The hookify hooks (`plugins/hookify/hooks/pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) all follow the same pattern: on every tool invocation they call `load_rules(...)` [1](#0-0)  which globs and re-parses `.claude/hookify.*.local.md` from disk with no caching between calls [2](#0-1) . The evaluated rules directly determine whether a subsequent `Bash`/`Write`/`Edit` action is denied via `permissionDecision: "deny"` or merely warned about, based on the `action` field of the rule [3](#0-2) .

The `/hookify` command itself is granted `allowed-tools: ["Read", "Write", "AskUserQuestion", "Task", "Grep", "TodoWrite", "Skill"]` [4](#0-3)  and its documented workflow is to use the `Write` tool to create/overwrite `.claude/hookify.{name}.local.md` files, explicitly setting `action: warn` or `action: block` [5](#0-4) , and the command finishes by telling the user/agent: "Rules are active immediately - no restart needed! The hookify hooks are already loaded and will read your new rules on the next tool use." [6](#0-5)  The README reiterates this "no restart needed" / "active immediately" property as a headline feature [7](#0-6) , and the `writing-rules` skill confirms disabling a rule (`enabled: false`) "take[s] effect on next tool use" [8](#0-7) .

This is structurally the same pattern flagged in the multisig report: an actor with the ability to trigger one privileged flow (an "order"/`/hookify` invocation) can use it to rewrite the trust parameters that govern subsequent authorization decisions (the signer/threshold dictionary / the hookify block rules), and the rewritten parameters are honored immediately for the very next action in the same session, with no independent re-validation gate analogous to the multisig's "second initialisation" guard.

### Impact Explanation
If an agent is manipulated (e.g., via prompt injection from a file, tool output, or a crafted `$ARGUMENTS` to `/hookify`) into writing or editing a `hookify.*.local.md` file that flips an existing `action: block` rule to `action: warn` (or `enabled: false`), the very next tool call in the same turn is evaluated against the weakened rule set and the previously-blocked dangerous command (e.g. `rm -rf`, editing `.env`/credentials) will be allowed to execute, with only a warning message shown instead of a hard deny. Because hookify is meant to be the last line of defense against exactly these dangerous operations, an actor able to self-modify its own configuration effectively neutralizes the guardrail it is supposed to be bound by, within the same session and without any restart, human settings review, or additional approval step.

### Likelihood Explanation
Exploitation requires the agent to invoke `/hookify` (or directly use `Write`) to modify its own `.local.md` rule files - something the plugin's design explicitly permits and even encourages ("no restart needed", "active immediately"). No additional access is required beyond what any ordinary session with the hookify plugin installed and the `Write` tool available already grants. The main constraint is that this generally requires the agent (not a human) to decide to weaken its own rule, which could arise from prompt injection, confused/careless editing of the wrong rule name, or an attacker steering the `/hookify` conversation-analyzer agent's proposed rule content. This is a plausible but not fully "unattended" attack path, so likelihood is moderate rather than high.

### Recommendation
- Treat guardrail/block-type hookify rules as a protected configuration surface: require an explicit user (not agent) confirmation step before any `Write`/`Edit` to an existing `action: block` rule file is applied, separate from normal file-write approval.
- Add a PreToolUse check specifically for edits to `.claude/hookify.*.local.md` that would downgrade an `action: block` rule to `warn` or set `enabled: false`, and force this through the standard permission-prompt flow rather than the plugin's own hook logic (which cannot review changes to itself).
- Consider caching the effective, security-relevant rule set at session start (or requiring a `/hookify:reload` confirmation) so that a rule weakening cannot silently take effect on the very next tool call within the same turn that created it.
- Document in `hookify`'s README/skill files that self-modifying block-type rules mid-session is a trust boundary and should be flagged for user review, mirroring the long-term recommendation from the referenced report to document privileged roles and avoid invalid self-authorization.

### Proof of Concept
1. Install the `hookify` plugin and create a blocking rule: `.claude/hookify.dangerous-rm.local.md` with `action: block`, `pattern: rm\s+-rf` (as shown in the plugin's own quick-start example) [9](#0-8) .
2. Confirm `rm -rf /tmp/test` is denied by `PreToolUse` via `pretooluse.py` → `RuleEngine.evaluate_rules` returning `permissionDecision: "deny"` [10](#0-9) .
3. Within the same session, have the agent (e.g., driven by an injected instruction in a file it reads) invoke `/hookify` or directly use `Write` to overwrite `.claude/hookify.dangerous-rm.local.md`, changing `action: block` to `action: warn` (or `enabled: false`), following the documented, sanctioned workflow [11](#0-10) .
4. Immediately re-run `rm -rf /tmp/test` in the same turn/session — per the plugin's own documented behavior ("no restart needed... active immediately") [6](#0-5) , the weakened rule is loaded fresh by `load_rules()` and the command is now only warned about (or not flagged at all), executing successfully where it was previously blocked.

            # Use appropriate blocking format based on event type
            if hook_event == 'Stop':

                return {
                    "hookSpecificOutput": {
                        "hookEventName": hook_event,
                        "permissionDecision": "deny"
                    },
                    "systemMessage": combined_message
                }
            else:
                # For other events, just show message
                return {
                    "systemMessage": combined_message
                }

        # If only warnings, show them but allow operation
