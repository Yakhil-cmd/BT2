### Title
No User or Admin Withdrawal Mechanism for Stuck Funds in Service Chain Bridge — (`contracts/service_chain/bridge/Bridge.sol`)

---

### Summary

The Kaia service chain `Bridge` contract and its entire inheritance chain contain no withdrawal, refund, or rescue function. When a user deposits KLAY or ERC20/ERC721 tokens into the source-side bridge via `requestKLAYTransfer`, `requestERC20Transfer`, or the KLAY fallback, those assets are held in the bridge contract. If the SubBridge operator is offline, censoring specific nonces, or misconfigured, the deposited assets are permanently locked with no on-chain path for the user or the owner to recover them.

---

### Finding Description

The `Bridge` contract is the composition of `BridgeTransferKLAY`, `BridgeTransferERC20`, `BridgeTransferERC721`, and `BridgeCounterPart`. [1](#0-0) 

**KLAY deposit path** — `requestKLAYTransfer` (and the fallback `()`) collect `msg.value` into the contract, pay the fee, and emit `RequestValueTransfer`. The KLAY principal stays in the bridge: [2](#0-1) 

**ERC20 deposit path (non-mintBurn mode)** — `requestERC20Transfer` pulls `_value + _feeLimit` from the caller into the bridge via `safeTransferFrom`. In non-mintBurn mode the `_value` portion is **not** burned; it sits in the bridge contract awaiting the operator's `handleERC20Transfer` call on the counterpart chain: [3](#0-2) [4](#0-3) 

The operator is the sole entity authorised to call `handleKLAYTransfer` / `handleERC20Transfer` on the destination bridge: [5](#0-4) 

A grep across the entire `contracts/service_chain/` tree returns **zero** results for any `withdraw`, `rescue`, or `emergencyWithdraw` function. The only owner-callable functions are administrative (`setRunningStatus`, `lockKLAY`, `setFeeReceiver`, `registerToken`, `setCounterPartBridge`) — none move funds back to users: [6](#0-5) [7](#0-6) 

The off-chain Value Transfer Recovery (`vt_recovery.go`) only **re-submits** the pending `handleValueTransfer` call to the destination chain; it provides no on-chain refund path on the source chain and requires the SubBridge process itself to be running: [8](#0-7) 

---

### Impact Explanation

Any KLAY sent via `requestKLAYTransfer` / the fallback, and any ERC20/ERC721 tokens sent via `requestERC20Transfer` / `onERC20Received` in lock-mode, are held exclusively by the bridge contract. If the SubBridge operator never calls the corresponding `handle*Transfer` on the counterpart chain, those assets are irrecoverably locked. Neither the user nor the bridge owner has any on-chain mechanism to retrieve them. The corrupted state is the bridge's native-token balance and ERC20 balances, which grow without a corresponding release path.

---

### Likelihood Explanation

The SubBridge operator is a single semi-trusted account registered by the bridge owner. A single point of failure (operator key loss, node crash, RPC outage, or deliberate censorship of specific request nonces) is sufficient to trigger the lock. The `_lowerHandleNonceCheck` enforces strict ordering: if the operator skips a nonce, `lowerHandleNonce` stalls at that nonce and all subsequent handle calls for higher nonces still succeed, but the skipped nonce's corresponding source-chain funds remain locked indefinitely: [9](#0-8) 

---

### Recommendation

1. Add a time-locked user-initiated refund function: after a configurable timeout (e.g., 7 days) with no corresponding `HandleValueTransfer` event for a given `requestNonce`, allow the original depositor to reclaim their KLAY or ERC20 tokens from the source bridge.
2. At minimum, add an `onlyOwner` emergency-rescue function that can transfer arbitrary ERC20 balances or KLAY back to a specified address, so an admin can manually refund affected users.
3. Decentralise the operator set (increase `operatorThresholds` and register multiple independent operators) to reduce the single-point-of-failure risk.

---

### Proof of Concept

1. Deploy `Bridge` in non-mintBurn mode with a single operator.
2. User calls `requestKLAYTransfer(user, 1 ether, "")` with `msg.value = 1.4 ether` (0.4 ether fee). Bridge holds 1 ether; `requestNonce` becomes 1.
3. Operator goes offline (or is deregistered). `handleKLAYTransfer` is never called on the counterpart chain.
4. Call every function in the bridge as the owner: `setRunningStatus`, `lockKLAY`, `setFeeReceiver`, `setCounterPartBridge` — none return the 1 ether to the user.
5. The 1 ether remains in `address(bridge).balance` with no callable path to retrieve it, confirming permanent asset lock. [10](#0-9) [11](#0-10)

    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }

// recoverPendingEvents recovers all pending events by resending them.
func (vtr *valueTransferRecovery) recoverPendingEvents() error {
	defer func() {
		vtr.childEvents = []IRequestValueTransferEvent{}
		vtr.parentEvents = []IRequestValueTransferEvent{}
	}()

	if len(vtr.childEvents) > 0 {
		logger.Warn("VT Recovery : Child -> Parent Chain", "cBridge", vtr.cBridgeInfo.address.String(), "events", len(vtr.childEvents))
	}

	vtRequestEventMeter.Mark(int64(len(vtr.childEvents)))
	vtRecoveredRequestEventMeter.Mark(int64(len(vtr.childEvents)))

	events := make([]IRequestValueTransferEvent, len(vtr.childEvents))
	for i, event := range vtr.childEvents {
		events[i] = event
	}
	vtr.pBridgeInfo.AddRequestValueTransferEvents(events)

	if len(vtr.parentEvents) > 0 {
		logger.Warn("VT Recovery : Parent -> Child Chain", "pBridge", vtr.pBridgeInfo.address.String(), "events", len(vtr.parentEvents))
	}

	vtHandleEventMeter.Mark(int64(len(vtr.parentEvents)))
	events = make([]IRequestValueTransferEvent, len(vtr.parentEvents))
	for i, event := range vtr.parentEvents {
		events[i] = event
	}
	vtr.cBridgeInfo.AddRequestValueTransferEvents(events)

	return nil
}
