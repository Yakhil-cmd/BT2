### Title
Webhook event-type header is not covered by the GitHub HMAC signature, allowing event-type confusion on an otherwise validly-signed payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` authenticates only the raw request body (`request.raw_post`) against the `X-Hub-Signature` header, while the value that actually decides which handler processes that body — `X-Github-Event` — is read separately from an unsigned header and is never included in the HMAC input. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

This mirrors the reported bug class exactly: a field that governs how a payload is interpreted (there: `tokenType`; here: `event`) is never bound by the verification mechanism (there: the currency whitelist check; here: the HMAC signature), so the same "verified" payload can be reinterpreted under a different, unverified classification.

### Finding Description
The equality that should hold is:
`event type covered by the verified signature == event type used to select the handler`

What actually holds is:
`sha1(body, webhook_secret) verifies body` while `event = header("X-Github-Event")` is used, unauthenticated, to pick `Shipit::Webhooks.for_event(event)`. [1](#0-0) 

Because the signature is computed only over the JSON body, any request whose body was legitimately signed by GitHub for one event (e.g. `push`, `status`, `check_suite`, `pull_request`) can be resubmitted with the `X-Github-Event` header swapped to a different value (e.g. `membership`), and `verify_signature` will still return `true`, since it never inspects or covers the event header. The dispatch that follows (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) then runs the handler registered for the attacker-chosen event name against the (legitimately signed but differently-typed) body. [5](#0-4) 

`MembershipHandler` is the highest-value target reachable this way because it directly mutates the `Shipit.github_teams` authorization model — it creates/looks up `Team` records and adds/removes `User` memberships based on `params.action`, `params.team`, `params.organization`, and `params.member`, and team membership is exactly what `Authentication#force_github_authentication` / `User#authorized?` use to gate access to the whole application. [6](#0-5) [7](#0-6) 

### Impact Explanation
If an attacker can obtain (or induce) any legitimately GitHub-signed webhook body whose JSON happens to satisfy `MembershipHandler`'s required shape (`action`, `team.{id,name,slug,url}`, `organization.login`, `member.login`), replaying it with `X-Github-Event: membership` bypasses the intended per-event authenticity binding and lets the attacker add an arbitrary GitHub login to a `Team` that gates access via `Shipit.github_teams`, i.e. an escalation into `Shipit.github_teams` authorization — one of the explicitly listed High-impact outcomes for this engine. Even absent a body that satisfies `MembershipHandler`'s strict params, the underlying root cause — the signature not binding the event type — is a genuine violation of the verified-payload/acted-upon-field equality analogous to the source finding, and is exploitable against any current or future handler with looser input requirements than `MembershipHandler`.

### Likelihood Explanation
Exploitation requires the attacker to possess a validly-signed webhook body for the configured GitHub App/organization. Bodies for many event types (issues, pushes to branches, comments, etc.) are producible by any GitHub user with ordinary, unprivileged interaction with a public repository monitored by the Shipit instance (opening an issue, commenting, pushing to a branch they have access to, etc. — no Shipit credentials, no `webhook_secret`, and no privileged account are required). The main constraint is finding/crafting a body whose JSON shape coincidentally satisfies a more sensitive handler's required params. This is a real but non-trivial precondition (as opposed to a directly triggerable exploit), which is why the report from the source scan was rated a structural/systemic weakness rather than a guaranteed one-shot exploit — but the missing binding itself is definite and independently verifiable from the code shown above.

### Recommendation
Bind the `X-Github-Event` header into the HMAC input verified by `verify_webhook_signature`, or otherwise cryptographically tie the declared event type to the signed body (e.g. mirroring GitHub's own recommended practice of only trusting `X-Github-Event` in combination with signature verification that covers it, or re-deriving/validating the event type strictly from body content rather than the header alone). At minimum, per-handler schemas should be event-exclusive (reject payloads containing fields characteristic of another event) so a body signed for one event cannot satisfy another handler's `params` block.

### Proof of Concept
Conceptual replay (cannot be executed without network/GitHub access in this environment):
1. Capture any request Shipit legitimately receives from GitHub for the configured org, e.g. an `issues` event body `B` with valid `X-Hub-Signature: S` (computed by GitHub over `B` using `webhook_secret`).
2. Resend `POST /github/webhooks` with the exact same body `B` and signature header `S`, but set `X-Github-Event: membership` instead of `issues`.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner).verify_webhook_signature(S, B)`, which only HMACs `B` — it returns `true` regardless of the `X-Github-Event` header value. [4](#0-3) 
4. Dispatch proceeds via `Shipit::Webhooks.for_event('membership')`, invoking `MembershipHandler#process` on body `B` — if `B`'s JSON structure happens to satisfy the handler's `params` schema (`action`, `team`, `organization`, `member`), a `Team`/`Membership` mutation occurs despite the body never having been signed by GitHub as a `membership` event. [8](#0-7)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
