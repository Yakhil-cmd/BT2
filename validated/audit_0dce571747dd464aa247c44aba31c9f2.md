### Title
Stack-scoped API tokens can read the deploy/build status of any stack via `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via `stack_id`, and every other API controller enforces that scope by resolving the target stack through `BaseController#stack`/`#stacks`, which filters by `current_api_client.stack_id`. `Api::CCMenuController` overrides `#stack` to resolve the stack directly from the URL parameter without consulting the token's `stack_id`, breaking the equality "stack a token authorizes == stack it touches."

### Finding Description
`ApiClient` supports being scoped to one stack: `belongs_to :stack, optional: true` [1](#0-0) . `Api::BaseController` enforces this scope uniformly for every other resource controller:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::TasksController`, `Api::DeploysController`, `Api::RollbacksController`, `Api::LocksController`, and `Api::HooksController` all inherit and rely on this `stack` method, so a token scoped to stack A cannot touch stack B, even though `require_permission :read, :stack` only checks the permission *name*, not the stack identity, in `ApiClient#check_permissions!` [3](#0-2) .

`Api::CCMenuController` breaks this pattern by redefining `stack` to bypass the scoped `stacks` collection:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

This method resolves the stack from the raw path parameter against the entire `Stack` table, ignoring `current_api_client.stack_id` entirely. Since `require_permission :read, :stack` only validates that the token has the `read:stack` permission string [5](#0-4) , any token carrying that permission — even one deliberately scoped to a single stack when it was created — can be replayed against `/api/stacks/*stack_id/ccmenu` for any other stack in the installation.

### Impact Explanation
This is an unauthorized cross-stack information disclosure: a token that was explicitly restricted to one stack (`ApiClient.stack_id`) can be used to read the CI/deploy status (name, last build status/label, last build time, web URL) of every other stack managed by the Shipit instance, via `Api::CCMenuController#show` [6](#0-5) . This directly violates the trust boundary that the rest of the API enforces (stack the token authorizes vs. stack it touches), and matches the "unauthenticated/unauthorized read of stack state" high-impact category, since the intended per-stack restriction is silently ignored for this one endpoint.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token that has the `read:stack` permission, regardless of whether it was minted with a `stack_id` restriction. Because the whole feature (`ccmenu`) is designed around embeddable, semi-public CI status badges (see `CCMenuUrlController#fetch` generating shareable URLs) [7](#0-6) , such tokens are more likely to circulate outside tightly controlled contexts, making the scope bypass practically reachable once a scoped token is exposed for its intended single stack.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack through the inherited, scope-aware `stacks` collection (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that stack-scoped tokens cannot address any stack outside their configured `stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A with permission `read:stack` (as done via the `api_clients` UI/API, e.g. fixture `here_come_the_walrus` scoped to `stack: shipit`) [8](#0-7) .
2. Using that token's Basic Auth credentials (or `?token=`), issue `GET /api/stacks/<owner>/<repo-of-stack-B>/<env>/ccmenu` for a different Stack B that the token was never scoped to.
3. `authenticate_api_client` succeeds because the token is valid and carries `read:stack` [9](#0-8) ; `stack` resolves Stack B directly via `Stack.from_param!` [4](#0-3) , bypassing the `current_api_client.stack_id` restriction enforced everywhere else, and the response discloses Stack B's build/deploy status despite the token being scoped only to Stack A.
