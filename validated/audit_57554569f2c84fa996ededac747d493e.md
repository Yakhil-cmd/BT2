## Title
Webhook signature is verified against an organization chosen from the payload, but the write target (repository/commit) is taken from a different, unvalidated payload field — cross-tenant status and stack forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate a request against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body, then hands the *entire, unmodified* payload to event handlers that determine what gets written using an entirely separate field (`repository.full_name`) or, in one handler, no repository scoping at all. Because these two things — "whose secret authenticated this request" and "what resource gets mutated" — are never cross-checked against each other, any tenant/organization holding its own legitimately-configured webhook secret can forge events that mutate another organization's data.

### Finding Description
`Shipit` supports multi-tenant GitHub App configuration, keyed per organization, each with its own `webhook_secret` [1](#0-0) . The webhook signature check picks the app/secret to verify against using a payload-controlled field: [2](#0-1) [3](#0-2) 

Once `verified` is (correctly) computed with *some* organization's secret, `create` blindly dispatches the full JSON body to handlers [4](#0-3) . Handlers resolve the resource to write using a *different* field of the same attacker-controlled payload: [5](#0-4) [6](#0-5) 

Nothing ties `repository.owner.login` (used to pick the signing secret) to `repository.full_name` (used to pick the `Repository`/`Stack` that gets mutated). Worse, `StatusHandler` doesn't even use repository scoping — it looks up commits **globally by SHA**, across every stack in the installation: [7](#0-6) 

`PushHandler` and `CheckSuiteHandler` scope to `Repository.from_github_repo_name(payload['repository']['full_name'])`, which is likewise never cross-validated against the organization used for signature verification: [8](#0-7) [9](#0-8) 

**Binding broken:** `organization that authenticated the request (via its own webhook_secret)` ≠ `repository/commit that is actually written to`.

### Impact Explanation
An organization ("Org A") legitimately onboarded to a shared, multi-org Shipit instance knows its own GitHub App webhook secret (it configured that secret both on its GitHub App and in Shipit's `secrets.github[org_a]`). Using that secret, Org A's operator can:
- Sign a `status` event with `repository.owner.login = "org-a"` (so `verify_signature` succeeds using Org A's own secret) while setting `sha` to a commit SHA belonging to Org B's stack. `StatusHandler` has no repository scoping at all, so it will happily attach an attacker-chosen CI status (`state: "success"`, arbitrary `context`/`description`/`target_url`) to Org B's commit [7](#0-6) . Because deploy safety/gating in Shipit relies on commit `Status`/`deployable?`, this can be used to fake a green CI status on a victim commit and unblock/trigger deploys the victim did not authorize.
- Sign a `push`/`check_suite` event with `repository.owner.login = "org-a"` but `repository.full_name = "org-b/victim-repo"`, causing `GithubSyncJob` to run against Org B's stack or forcing check-run refreshes on Org B's commits [10](#0-9) .

This is a cross-repository/cross-tenant write achieved without possessing the victim organization's webhook secret, an `ApiClient` token, or `GITHUB_TOKEN` — only the attacker's own, legitimately-held secret for their own tenant.

### Likelihood Explanation
Requires a Shipit deployment configured for multiple GitHub organizations (explicitly supported via `github_app_config`/`github_organizations` [11](#0-10) ). Any one of the onboarded, unprivileged tenant organizations can mount this attack against any other tenant, using only its own webhook secret and knowledge of a target commit SHA (public on GitHub) or repository full name (also public). No special access to Shipit itself, no GitHub App private key, and no compromised credentials beyond what the attacking tenant already legitimately possesses are needed.

### Recommendation
Cross-validate the organization used to select/verify the webhook signature against the resource the handler is about to mutate:
- After deriving `repository_owner` for signature verification, also parse `repository.full_name`/`organization.login` and reject the request (422) if the owner segment of `full_name` doesn't match `repository_owner`.
- In `Repository.from_github_repo_name` lookups performed by handlers (`Handler#stacks`, `PushHandler`, `CheckSuiteHandler`), assert the resolved `Repository#owner` equals the organization whose secret validated the request.
- Fix `StatusHandler` to scope `Commit.where(sha: ...)` to commits whose stack's repository owner matches the verified organization, instead of a global SHA lookup.

### Proof of Concept
1. Org A operator obtains Org A's webhook secret (`secrets.github["org-a"].webhook_secret`), which they legitimately configured.
2. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<sha-of-org-b-victim-commit>",
  "state": "success",
  "context": "ci/tests",
  "description": "forced pass",
  "repository": { "owner": { "login": "org-a" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org_a_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and validates successfully using Org A's own secret [2](#0-1) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` globally and calls `create_status_from_github!`, writing a forged "success" status onto Org B's commit — despite the request only ever having been authenticated as Org A [7](#0-6) .

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
