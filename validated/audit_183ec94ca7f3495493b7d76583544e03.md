### Title
Caller-controlled swap routes can redirect signed authorization into unrelated token transfers - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy entrypoints accept opaque route payloads and execute them through the configured aggregator while the caller’s authorization is active. A malicious route can place attacker-controlled contract code on the call stack and add an unrelated `token.transfer(caller, attacker, amount)` as a child authorization. If the victim signs the authorization tree produced by simulation without decoding every child invocation, the route both completes a plausible swap and transfers unrelated wallet assets to the attacker.

### Finding Description
The vulnerable shape is analogous to Phoenix’s external-URL redirect: input presented as an internal route can redirect execution to an external destination. `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` all accept caller-provided `swap: Bytes`, and `swap_collateral` forwards that value into `SwapCollateralParams` without validating its destination semantics [1](#0-0) .

The shared strategy helper loads the configured router, authorizes only the controller’s exact input transfer, and passes the opaque `swap` payload to `router.execute_strategy` [2](#0-1) . Its post-call checks only bound controller input spend, refund controller-held leftovers, and require positive output [3](#0-2) . They do not prevent route-selected code from requesting additional authorization from the original caller.

The repository’s authorization-tree test demonstrates the concrete behavior: a router-selected hop invokes a rogue pool, and that pool calls `token.transfer(victim, attacker, amount)` [4](#0-3) . Simulation records that transfer as a child of the victim’s `swap_collateral` authorization [5](#0-4) ; signing the returned tree executes the theft [6](#0-5) .

### Impact Explanation
An attacker can steal unrelated wallet tokens from a user who signs a poisoned authorization tree. The stolen amount is not limited to the strategy’s `amount_in`: it can target any token held by the victim, subject to the victim signing the corresponding child authorization. The swap can still return plausible output and pass the controller’s measured-output and account-risk checks, making the malicious operation resemble a normal strategy transaction.

### Likelihood Explanation
This requires social engineering or a malicious/compromised route-generation client. The victim must sign an authorization tree containing the unexpected transfer; an unsigned rogue transfer is rejected. That user-interaction requirement and the visibility of the authorization tree lower likelihood, consistent with a Medium severity analog rather than a direct protocol-accounting flaw.

### Recommendation
Treat swap route payloads and simulated authorization trees as untrusted. Wallets and route builders should decode every route and reject any `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or direct router authorization tree containing children beyond the expected controller input-token transfer. Prefer a route format whose execution cannot request arbitrary caller authorization, or constrain venue execution so nested contracts cannot attach unrelated `require_auth` operations under the caller’s root invocation.

### Proof of Concept
1. Alice owns a funded lending account and an unrelated wallet token.
2. Attacker provides Alice a `swap_collateral` route that nominally swaps USDC to ETH but names an attacker-controlled hop pool.
3. Alice calls:

   `swap_collateral(caller=alice, account_id, current=USDC, amount, new=ETH, swap=malicious_route)`

4. The controller forwards `malicious_route` through `execute_strategy`; during route execution the attacker-controlled hop calls:

   `wallet_token.transfer(alice, attacker, alice_wallet_balance)`

5. Simulation records the wallet transfer as a child authorization under Alice’s `swap_collateral` root.
6. If Alice signs the returned tree, the swap can return fair ETH output while the unrelated wallet-token balance moves to the attacker.

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),

        sub_invocations: std::vec![stolen_transfer],
