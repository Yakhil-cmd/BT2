### Title
CCMenu API token scoped to one stack can read the build status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack directly from `Stack.from_param!(params[:stack_id])` instead of using the stack-scoped `stacks` helper that every other stack-scoped API endpoint relies on. This breaks the binding "stack a token authorises == stack it touches": an `ApiClient` created with a `stack_id` restriction (e.g. the CCMenu client created per-stack by `CCMenuUrlController`, or any stack-scoped token an operator issues) can be replayed with a different `stack_id` parameter to read another stack's deploy state.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` (`app/models/shipit/api_client.rb:8`). `Api::BaseController` enforces this scoping through its `stacks` helper: [1](#0-0) 
which is consumed by `stack` in `StacksController`: [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [3](#0-2) 

`require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which checks that the permission string `"read:stack"` is present in `permissions` — it never checks `stack_id` equality: [4](#0-3) 

So any client holding a token with `read:stack` permission — even one explicitly created bound to a single stack, such as the one generated by `CCMenuUrlController`: [5](#0-4) 
— can call `GET /api/stacks/:stack_id/ccmenu` with an arbitrary `stack_id` and successfully read that other stack's latest deploy/rollback status, lock state, and build result, because `CCMenuController#stack` never checks whether the authenticated `ApiClient#stack_id` matches the requested stack.

This is the same class of bug as the Swivel finding: a verification/authorization step (checking the permission bit) is performed, but a second value that should also be bound by that same authorization (which specific stack the token is limited to) is taken from unchecked, attacker-controlled input instead of the verified/authorized value — "a stack a token authorises versus a stack it touches."

### Impact Explanation
This grants unauthenticated-in-effect (relative to the intended scope) read access to another stack's state: deploy status, lock status, last build label/time, which corresponds to the engine's "High" bucket — unauthenticated read of stack state via an authorization scope bypass. A token meant to be limited to a single low-sensitivity stack can be used to enumerate/monitor CI/deploy status of any stack in the installation, including stacks the token holder was never granted access to.

### Likelihood Explanation
Any holder of a stack-scoped API token with `read:stack` permission (the exact kind of token this engine issues for the CCMenu integration, or that operators can issue via the `ApiClients` admin UI limited to a `stack`) can trivially trigger this by changing the `stack_id` path parameter in the request; no privilege escalation, signature forgery, or additional credentials are required beyond possessing one valid, narrowly-scoped token.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the same scoped helper used elsewhere, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a client whose `ApiClient#stack_id` is set can only ever resolve to that stack, consistent with `StacksController` and `HooksController`.

### Proof of Concept
1. Create (or use the existing) stack-scoped `ApiClient`, e.g. fixture `here_come_the_walrus` bound to `stack: shipit` with `permissions: ['read:stack']` (`test/fixtures/shipit/api_clients.yml:12-17`).
2. Authenticate as that client (Basic Auth with its `authentication_token`, or via `?token=`).
3. Request `GET /api/stacks/<some-other-stack-id-or-slug>/ccmenu` (a stack this client is not scoped to).
4. `require_permission :read, :stack` passes because the client's `permissions` includes `read:stack`.
5. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly (bypassing the `stacks` scope check that `StacksController#stack` uses), returning the other stack, and its deploy/build status is rendered in the XML response — despite the token being authorized only for the `shipit` stack.
