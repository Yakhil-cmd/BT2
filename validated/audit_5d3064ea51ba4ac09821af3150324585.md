### Title
Crafted unit triggers unhandled `throw Error()` invariant violation in validation, crashing the node process - ([File: validation.js])

### Summary
CVE-2019-2486 describes a MySQL bug where a supposedly safe/expected internal state assumption is violated by an attacker-supplied operation, causing the server to hang or crash (complete DoS) rather than fail gracefully. `ocore`'s unit validation pipeline contains an analogous pattern: several code paths that process attacker-controlled unit content are guarded not with graceful `callback(error)` rejection but with hard `throw Error(...)` statements documented as "should never happen" / "unreachable code" invariants. Because these throws happen inside asynchronous callbacks fired while processing a *newly received, unprivileged, remotely-posted unit*, they escape the calling `validate()`'s callback contract and surface as Node.js `uncaughtException`, which `network.js` deliberately converts into a full process crash.

### Finding Description
`validation.js`'s `checkForDoublespends()` function, used to detect conflicting payment inputs and asset issuance serial numbers, contains invariant assertions that assume no attacker can produce certain states, e.g.: [1](#0-0) 

These `throw Error(...)` calls (`"conflicting "+type+" spent from another address?"`, `"double spending "+type+" without double spending address?"`, `"unreachable code, conflicting "+type+" in unit "+...`) assume `arrAuthorAddresses` and `objValidationState.arrAddressesWithForkedPath` are always consistent with what is found in the `outputs`/issuance tables for a crafted unit. Similarly, `validateAuthor()` and other authorship/definition-resolution code paths use hard throws for conditions such as `"AA definition not found "` and `"more than one poll?"` in reachable, attacker-influenced contexts: [2](#0-1) [3](#0-2) 

Rather than propagating these as `ifUnitError`/`ifJointError` results (which the validation callback contract in `network.js`'s `handleJoint` is designed to handle gracefully), a thrown `Error` bypasses all of `validate()`'s `async.series` error handling in `validation.js`:354-496 and becomes an uncaught exception. `network.js`'s own inline comment acknowledges this exact risk when processing a peer-submitted joint: [4](#0-3) 

And the top-level handler for such exceptions is designed to crash the whole node process rather than recover: [5](#0-4) 

The same unguarded-`throw` pattern is reused in the AA trigger execution path (`aa_composer.js`) and in wallet-side saving callbacks (`indivisible_asset.js`, `divisible_asset.js`), meaning any of: an unprivileged unit poster (broadcasting a unit directly), an AA trigger sender (whose trigger is processed via `aa_composer.js`'s `validateAndSaveUnit`), or a private-payment counterparty (via `getSavingCallbacks` in the asset modules) can potentially reach one of these invariant-violation throws with attacker-shaped input.

### Impact Explanation
If a crafted unit/trigger/private-payment payload can violate one of these "should never happen" invariants, the resulting uncaught exception is intentionally re-thrown by `network.js`'s `process.on('uncaughtException', ...)` handler to crash the Node.js process (`network.js:4542`, "crash the process to avoid ending up in an inconsistent state"). This means a single unprivileged actor — anyone able to post/broadcast a unit, submit an AA trigger, or negotiate a private payment — can remotely crash a full/hub node, matching CVE-2019-2486's impact category: unauthorized ability to cause a hang or a repeatable crash (complete DoS) via a normally-restricted internal operation, without any data corruption. Repeated crashes across the network could degrade the ability of nodes to confirm new units.

### Likelihood Explanation
Exploitability depends on whether an attacker can actually construct unit content or a sequence of prior units that puts `objValidationState`/database state into one of the specific inconsistent configurations guarded by these throws (e.g., a double-spend record whose address isn't among the unit's authors, or a "forked path" address list that disagrees with query results). I was not able to fully trace, within the available tool budget, the exact conditions under which `objValidationState.arrAddressesWithForkedPath` is populated relative to attacker-controlled parent/unit selection, so I cannot confirm a concrete, minimal proof-of-concept unit that reaches one of these throws. This is a genuine gap in verification, not an assumption resolved in the attacker's favor.

### Recommendation
- Audit every `throw Error(...)` inside `validation.js`, `aa_composer.js`'s trigger validation, and the asset-saving callbacks (`indivisible_asset.js`, `divisible_asset.js`) that executes during processing of attacker-supplied units/triggers/private payments, and confirm each is truly unreachable under adversarial input (including replays, reorgs, and private/asset edge cases).
- Where reachability cannot be conclusively ruled out, convert the `throw` into a graceful `callback("...")`/`ifUnitError` rejection so malformed-but-crafted units are rejected rather than crashing the process.
- Consider hardening `network.js`'s `uncaughtException` handler so that exceptions originating specifically from per-unit/per-trigger validation logic (as opposed to genuine internal inconsistency) do not necessarily terminate the entire process, reducing the blast radius of any single crafted input.

### Proof of Concept
Not constructed — reaching a concrete crash requires proving a specific sequence of units/database state that violates one of the identified invariants (e.g., in `checkForDoublespends`), which I could not fully verify with the tool calls available in this session. The finding is based on: (1) confirmed unguarded `throw Error()` invariants in attacker-reachable validation code paths (`validation.js:1671-1693`, `1149-1173`, `1826-1841`), and (2) confirmed process-crashing `uncaughtException` handling in `network.js:4530-4543`, combined with `network.js`'s own comment (`network.js:1169`) acknowledging that validation of peer-supplied joints can crash the process.
