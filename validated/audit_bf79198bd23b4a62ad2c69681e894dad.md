### Title
Webhook signature is validated against the payload's `repository.owner.login`, but every event handler routes and mutates state using the unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against by reading `params.dig('repository', 'owner', 'login')` (or `organization.login`) straight out of the still-unverified JSON body. [1](#0-0) [2](#0-1)  Once the signature check passes, every downstream `Shipit::Webhooks::Handlers::Handler` subclass (push, status, pull_request, membership, etc.) resolves the target `Repository`/`Stack` using a *different* field of the same payload: `payload.dig('repository', 'full_name')`. [3](#0-2) [4](#0-3) 

The binding the system relies on is: `organization that authenticated (repository.owner.login checked against webhook_secret) == owner of the repository being written to (repository.full_name)`. Nothing enforces this equality; the two fields are independent, attacker-controlled strings inside the same signed JSON body.

### Finding Description
`Shipit.github(organization: repository_owner)` picks the `GitHubApp` instance (and thus the HMAC `webhook_secret`) using `repository_owner`, which is derived purely from the JSON body before any cryptographic check occurs. [5](#0-4)  `verify_webhook_signature` then simply checks that the raw body is signed with *that organization's* secret. [6](#0-5)  This is sound as far as it goes: it proves the payload was signed by the holder of `OrgA`'s webhook secret.

The problem is that the signature only proves "OrgA signed this JSON blob" - it says nothing about which repository the blob is supposed to describe. Every handler ignores `repository.owner.login` entirely and instead does:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 
and
```ruby
def repository
  @repository ||= Shipit::Repository.from_github_repo_name(params.repository.full_name) ||
                  Shipit::NullRepository.new
end
``` [4](#0-3) 

Since anyone can install the Shipit GitHub App on their own personal organization/repo (this is the documented, intended install flow: "Install the GitHub App on your organization"), an attacker legitimately obtains a valid `webhook_secret` for `attacker-org`. Nothing stops them from then hand-crafting a webhook POST body where `repository.owner.login = "attacker-org"` (so signature verification passes using the attacker's own known secret) while `repository.full_name = "victim-org/tracked-repo"` (an arbitrary repository/stack already registered in the target Shipit instance). The controller's signature check is happy - it's a valid signature for `attacker-org` - but the JSON content it accepted claims to describe an entirely different, victim-owned repository, and every handler will act on that claim.

This exactly matches the discrepancy pattern in the source report: the "verified" quantity (organization tied to the signing secret) and the quantity actually *acted upon* (repository the event is applied to) are computed from different, uncorrelated inputs, and the code never checks they agree.

### Impact Explanation
Handlers keyed off `repository.full_name` include, among others, the `status` handler (creates a `Status`/commit CI status for a specific commit+repo) and the `push` handler (queues `GithubSyncJob` for the resolved stack). Commit statuses are the exact signal Shipit's continuous-delivery/merge logic consumes to decide whether a commit is deployable/mergeable (via `Stack#continuous_deployment`, required/blocking status lists in `deploy_spec`, etc.). An attacker who only controls a webhook secret for their own, unrelated org can therefore forge a passing CI status (or arbitrary status state) against a victim repository/commit that Shipit tracks, which can push a stack with `continuous_deployment: true` into triggering an **unauthorized deploy** - this satisfies the "unauthorized deploy" High-impact criterion. It can also desynchronize/spam `GithubSyncJob`s or pollute `Team`/`User`/`PullRequest` state tied to the victim repository/organization via the `membership`/`pull_request` handlers, none of which the attacker is authorized to touch.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install a GitHub App on an org the attacker controls (documented, unprivileged, self-service flow for anyone who can create their own GitHub org/repo), which yields a webhook secret they legitimately know; and (2) sending a single crafted HTTP POST to the shared `/webhooks` endpoint with a correctly-signed body whose `repository.owner.login` names their own org while `repository.full_name` names the victim stack. No GitHub write access, Shipit session, `ApiClient` token, or `webhook_secret` of the *target* org is needed - only knowledge of the attacker's own webhook secret, which they inherently possess. This requires no social engineering or interception, matching the "unprivileged attacker breaks a deployment-trust binding" criterion in scope.

### Recommendation
- Short term: after signature verification, re-derive `repository_owner`/`organization` and cross-check it against `repository.full_name`'s owner segment (or `organization.login`) before dispatching to any handler; reject the webhook if they disagree.
- Long term: bind webhook secrets to specific repositories (not just organizations) where possible, and have `Handler#repository_name` consume a value that was itself validated as belonging to the authenticated organization, rather than trusting an independent field from the same unauthenticated JSON body.

### Proof of Concept
1. Attacker creates a public GitHub organization `attacker-org` and a throwaway repo inside it, then installs the target Shipit instance's GitHub App on that org, obtaining/setting a `webhook_secret` (`S_attacker`) they know.
2. Attacker crafts a push (or status) webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already known to exist on victim repo>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/tracked-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_attacker, body)`.
4. POST to `https://<shipit-host>/webhooks` with `X-Github-Event: push` (or `status`) and the signature header.
5. `verify_signature` resolves `repository_owner => "attacker-org"`, loads `attacker-org`'s `GitHubApp`, and successfully verifies the signature (it was legitimately produced with `S_attacker`). [1](#0-0) 
6. `Shipit::Webhooks.for_event('push')` handlers run and resolve the repository via `payload.dig('repository', 'full_name')` = `"victim-org/tracked-repo"`, acting on the victim's real, unrelated stack. [3](#0-2)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
