### Title
Webhook signature verified against the organization named in the unverified payload, while handlers act on the repository named in the same unverified payload — allowing cross-organization forged events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using an **unverified** field of the incoming JSON body (`repository.owner.login`), but the event handlers that subsequently act on the payload identify the target `Stack`/`Repository` using a **different, independently-controlled** field of the same unverified body (`repository.full_name`). Because nothing binds these two fields together, an attacker who legitimately administers a GitHub organization configured on this Shipit instance (and therefore knows that organization's `webhook_secret`) can forge a valid signature for a payload that names their own org as the signing owner while pointing `repository.full_name` at a stack belonging to a completely different organization also hosted on the same instance.

### Finding Description
Signature verification is done here: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the un-authenticated raw body, and is used to pick which `GitHubApp` config (and thus which `webhook_secret`) will be used to check the HMAC: [3](#0-2) 

`Shipit.github(organization:)` supports exactly this multi-tenant scheme, keying distinct configs (and distinct `webhook_secret`s) per GitHub organization name found in `secrets.github`: [4](#0-3) 

This is a documented, supported deployment mode (multiple orgs sharing one Shipit instance), shown in the example secrets file and the installer template: [5](#0-4) 

Once the signature passes, `create` dispatches the full JSON payload to handlers: [6](#0-5) 

Handlers determine which `Stack` to mutate using a **different** JSON key — `repository.full_name` — with no cross-check against `repository.owner.login`: [7](#0-6) 

For example, `PushHandler` uses this lookup to force a stack to sync to an attacker-chosen SHA: [8](#0-7) 

The equality that should hold, but is not enforced, is:
`organization whose secret authenticated the HMAC (repository.owner.login) == organization that owns the repository the handler mutates (repository.full_name)`

Since the HMAC only guarantees "this exact byte sequence was produced by someone who knows Org A's secret," and Org A's secret owner fully controls every byte of that sequence including the unrelated `repository.full_name` field, they can freely set `full_name` to `OrgB/some-repo` while keeping `owner.login` set to `OrgA`.

### Impact Explanation
This breaks the deployment-trust binding between "the organization that authenticated the webhook" and "the repository that is written," permitting cross-repository/cross-organization writes and unauthorized deploy triggers on a multi-tenant Shipit instance — a specifically accepted analog impact category (cross-repository writes / unauthorized deploy). A tenant organization admin who only owns credentials for their own GitHub org can forge events (`push`, `status`, `pull_request`, `check_suite`, etc.) that are processed as if they originated from a completely different tenant's repository, e.g.:
- `PushHandler` forcing `stack.sync_github(expected_head_sha:)` on someone else's stack.
- Commit-status/check-suite handlers injecting forged statuses that can satisfy deploy safety checks on someone else's stack, enabling deploys to proceed.
- `pull_request` handlers mutating another org's review stacks (archive, label, etc.).

### Likelihood Explanation
Requires the Shipit instance to be configured in the documented multi-organization mode (multiple keys under `github:` in secrets), and requires the attacker to be a legitimate administrator of at least one of the organizations configured on that shared instance (i.e., knows that organization's `webhook_secret` because they set up its GitHub webhook). No GitHub App private key, no Shipit session, and no `ApiClient` token are needed — only knowledge of one tenant's own webhook secret, which by design that tenant possesses.

### Recommendation
After verifying the signature, validate that the organization actually used to select the signing secret matches the owner of `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to handlers, e.g. reject the request if `repository.owner.login`/`organization.login` used for secret selection does not match the owner portion of `repository.full_name`.

### Proof of Concept
1. Shipit is configured with two tenant orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `secrets.github.orgA` / `secrets.github.orgB`), both hosting stacks on the same Shipit instance.
2. Attacker administers `OrgA`'s GitHub webhook configuration and thus knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha-existing-in-OrgB-repo>",
     "repository": {
       "full_name": "OrgB/private-repo",
       "owner": { "login": "OrgA" }
     }
   }
   ```
4. Attacker computes `sha1=HMAC(OrgA_webhook_secret, body)` and sends it as `X-Hub-Signature`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")`, matches the HMAC successfully (`lib/shipit/github_app.rb:76-83`), and the request proceeds.
6. `PushHandler` resolves the target stacks via `Repository.from_github_repo_name("OrgB/private-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack — despite the request never being signed by anyone with access to `OrgB`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
