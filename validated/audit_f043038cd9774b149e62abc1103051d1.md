### Title
Cross-repository stack read via unscoped `Stack.from_param!` in CCMenu controller - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` overrides the base controller's tenant-scoped stack lookup with an unscoped `Stack.from_param!(params[:stack_id])`, while `require_permission :read, :stack` only validates that the token's `permissions` array contains the string `"read:stack"` and never compares it to the resolved stack's identity. Any `ApiClient` token holding the generic `read:stack` permission — even one created and scoped to a stack in a completely different repository — can fetch CCMenu XML (build status/last deploy) for any stack in the system by guessing/enumerating `stack_id`.

### Finding Description
The broken binding, stated as an equality that the code implies but never enforces:
`current_api_client.permissions.include?("read:stack")` == `current_api_client authorized to read *this* stack (params[:stack_id])`.

In `app/controllers/shipit/api/base_controller.rb`, the generic `stack` helper is properly scoped: [1](#0-0) 
`stacks` restricts to `current_api_client.stack_id` when the token has one, and `stack` resolves via that scoped relation.

However, `CCMenuController` redefines `stack` to bypass this scoping entirely: [2](#0-1) 
`Stack.from_param!(params[:stack_id])` is called directly on the unscoped model class, ignoring `current_api_client.stack_id`.

`require_permission!` (used via the class-level `require_permission :read, :stack` declaration) only checks the permission string, in `app/models/shipit/api_client.rb`: [3](#0-2) 
`check_permissions!` never receives or checks the target stack — it only checks `permissions.include?("read:stack")`.

Root cause: the authorization check (`read:stack` permission) and the resource resolution (`stack` lookup) are decoupled, and `CCMenuController` reintroduces an unscoped lookup that undoes the tenant isolation the base controller otherwise provides via `stacks`.

Exploit flow: an attacker who legitimately holds (or is issued) an `ApiClient` token scoped to `stack_id` = S1 in repository A, with `read:stack` permission, sends `GET /api/stacks/:stack_id/ccmenu.xml` (or the query-string-token variant) with `stack_id` set to a stack S2 belonging to unrelated repository B. `authenticate_api_client` succeeds (valid token), `require_permission!(:read, :stack)` passes (token has `read:stack`), and `stack` resolves S2 unscoped, returning B's build status/deploy output in the XML response.

Existing guards that fail to prevent this: `authenticate_api_client` only validates token signature/existence, not stack scope; `require_permission!`/`check_permissions!` only checks the permission string; the `stacks` scoping mechanism exists in `BaseController` but is dead code for this controller because `CCMenuController#stack` shadows it.

### Impact Explanation
An attacker holding any `read:stack`-scoped `ApiClient` token (scoped to one specific stack) can read the CCMenu status (activity, last build status/label/time, web URL) of any other stack/repository in the Shipit instance by varying `stack_id`, without holding rights to that repository. This is a cross-tenant unauthorized read of stack/build state, matching the High severity category ("unauthenticated/unauthorized read of stack state, task streams or deploy output"). It is fully repeatable against arbitrary stacks by enumerating `stack_id` values (stack `to_param` values are often predictable, e.g., `owner/repo/branch`-derived slugs).

### Likelihood Explanation
Preconditions: attacker needs *some* valid `ApiClient` token with `read:stack` permission (even one deliberately scoped to only a single unrelated stack) — this is a normal, low-privilege credential type in Shipit, often issued to CI/monitoring integrations for a single repo. No GitHub secrets, session, or admin role needed. Given such a token, the attack is a single unauthenticated-relative-to-target HTTP GET with a different `stack_id`; cost is trivial and fully repeatable.

### Recommendation
Remove the `stack` override in `CCMenuController`, or change it to use the scoped `stacks.from_param!(params[:stack_id])` from `BaseController` so the token's `stack_id` restriction is honored. Alternatively, have `require_permission!` check the resolved stack against `current_api_client.stack_id` explicitly when the token is stack-scoped.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a read:stack token scoped to one stack cannot read a different stack's ccmenu xml" do
  stack_a = shipit_stacks(:shipit) # repo A
  stack_b = Stack.create!(repository: Repository.new(owner: "other-org", name: "other-repo"), branch: "main")

  scoped_client = ApiClient.create!(
    creator: @user, name: "scoped", permissions: ['read:stack'], stack: stack_a
  )

  request.headers['Authorization'] = nil
  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # Binding under test: permission check (read:stack) vs stack identity check (stack_id == stack_b.id)
  assert_response :forbidden # currently fails: returns 200 with stack_b's data
end
```
This demonstrates the divergence: `scoped_client.check_permissions!(:read, :stack)` passes because it only checks the permissions array, while `stack` (overridden in `CCMenuController`) resolves `stack_b` regardless of `scoped_client.stack_id == stack_a.id`.
