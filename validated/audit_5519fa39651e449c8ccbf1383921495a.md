### Title
CCMenu API scope-bypass: `ApiClient#stack_id` binding vs. `CCMenuController#stack` lookup - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` scopes stack access to the stack bound to the authenticated `ApiClient` (`stack_id`), but `Shipit::Api::CCMenuController` overrides the `stack` lookup with an unscoped query, letting any authenticated `ApiClient` (even one restricted to a single stack) read the CI/deploy state of an arbitrary other stack just by changing a request parameter — the same "unvalidated parameter breaks an intended binding" class described in the external report, applied to the stack-authorization boundary instead of token/amount parameters.

### Finding Description
`ApiClient` can be scoped to a single stack via its `stack_id` association, and `Shipit::Api::BaseController` enforces this scope for every normal API controller through the `stacks`/`stack` helper methods: [1](#0-0) 

This means for controllers like `CommitsController` or `LocksController`, a scoped client's `stack` lookup is constrained to `Stack.where(id: current_api_client.stack_id)`, so a request for a foreign stack simply 404s. [2](#0-1) 

`CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving the stack directly from the request parameter with no reference to `current_api_client.stack_id`: [3](#0-2) 

It also accepts authentication both via query-string `token` and via the normal Basic-Auth path (`super` from `BaseController#authenticate_api_client`), so any valid `ApiClient` credential — including one deliberately scoped to a single stack (as created for `here_come_the_walrus` in fixtures) — is accepted here: [4](#0-3) 

`require_permission :read, :stack` only checks that the client's permission list contains `read:stack`; it never checks which stack the client is scoped to: [5](#0-4) 

So the equality binding the system is supposed to enforce — *"stack a token authorizes" == "stack it touches"* — holds in every other API controller (via `stacks.from_param!`) but is broken specifically in `CCMenuController#stack`, which resolves `params[:stack_id]` against the full, unscoped `Stack` relation.

### Impact Explanation
Before the attacker's request: a client scoped to stack A (`stack_id` set to A) can only read/act on stack A through the API. After hitting `CCMenuController#show` with `stack_id` set to stack B: the same credential returns stack B's CCMenu XML, which includes build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, etc.) for a stack the client was never authorized to see. This is an authorization-scope escape leading to unauthenticated-relative-to-that-resource read of stack state/deploy output for an arbitrary stack — matching the High-severity bucket "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
This requires only possession of any valid, low-privilege `ApiClient` credential scoped to one stack (something routinely handed out, e.g. via the CCMenu URL feature or the api_clients UI) and knowledge/guessing of another stack's `to_param` (a predictable `owner/name/env`-style slug, not a secret). No GitHub App keys, session cookie, or elevated permission are needed — only the documented `CCMenuController` route and the client's own credentials.

### Recommendation
Make `CCMenuController#stack` go through the same scoped `stacks` collection used by `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `ApiClient#stack_id` binding is enforced consistently across all API controllers.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to stack A only, e.g. `ApiClient.create!(creator: user, name: 'x', permissions: %w[read:stack], stack: stack_a)`, and get its `authentication_token`.
2. As this client, request:
   ```
   GET /api/stacks/<owner>/<stack_b_name>/<env>/ccmenu.xml?token=<stack_a_scoped_token>
   ```
   (or via Basic Auth using the client's `id`/token pair, per `CCMenuControllerTest#"can authenticate with query string token"`) [6](#0-5) 
3. The response returns stack B's `NoDeploy`/last deploy XML successfully, even though the client's `stack_id` is bound to stack A, because `CCMenuController#stack` never consults `current_api_client.stack_id`. [7](#0-6)

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
```
