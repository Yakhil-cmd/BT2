### Title
Webhook signature verification key is selected from unverified, attacker-controlled JSON, allowing forged `membership`/`push`/`status` events to bypass authentication when any onboarded organization has no `webhook_secret` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the GitHub organization used to look up the HMAC secret from the **same unverified JSON body** that the handlers subsequently act on, and `verify_webhook_signature` returns `true` unconditionally when that organization has no configured `webhook_secret`. Because `webhook_secret` is documented and templated as *optional*, and the organization used for secret lookup is never cross-checked against the actual data being written (`repository.full_name`, `member.login`, `team.slug`, `sha`, etc.), an attacker can pick any organization value that maps to a blank secret and have Shipit process a completely unauthenticated event — including `membership` events that directly grant `Shipit.github_teams` authorization.

### Finding Description
The signature check binds only on the value it itself derives from the untrusted body: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of `JSON.parse(request.raw_post)` — fully attacker-controlled — before any cryptographic check occurs. It is then used to select which `GithubApp` instance (and thus which `webhook_secret`) validates the signature: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` **unconditionally** when `webhook_secret` is blank for the resolved organization (line 77). `webhook_secret` is explicitly documented as optional: [4](#0-3) 

This creates a broken binding: *the organization whose secret gated the signature check* ≠ *the organization/repository/team actually written by the handler*, because `create` re-parses and dispatches the whole body to handlers using fields (`repository.full_name`, `organization.login`, `member.login`, `team`) that were never covered by the (bypassed) signature: [5](#0-4) 

The `membership` event handler creates/removes `Team` and `Membership` rows purely from payload data, as confirmed by test coverage: [6](#0-5) 

Those `Membership` rows are exactly what gates authorization for OAuth-authenticated sessions: [7](#0-6) 

So an attacker who can get one unauthenticated `membership` webhook accepted (either because the target org never set `webhook_secret`, or — in a multi-organization deployment — by supplying an `organization.login`/`repository.owner.login` value belonging to a *different*, secret-less organization while the rest of the payload still names the victim's team) can insert an arbitrary GitHub login into a `Team` that is present in `Shipit.github_teams`. When that GitHub account subsequently completes the real OAuth flow, `User#authorized?` succeeds and the session is granted full application access.

### Impact Explanation
This breaks the equality "GitHub organization that authenticates the webhook = organization/team whose state is mutated by the webhook," letting an unauthenticated network attacker escalate into `Shipit.github_teams` authorization — one of the explicitly listed High-impact outcomes. Depending on team‑to‑repository mapping this can cascade to unauthorized triggering of `GithubSyncJob`, forged commit `Status` rows (`ci.require` checks), and `check_suite` refreshes for any tracked stack, since these handlers are likewise reachable once the same secret-less-organization bypass fires.

### Likelihood Explanation
Requires no credentials, no session, and no GitHub write access — only knowledge that some onboarded organization on the Shipit instance has an unset `webhook_secret`, which the setup docs and template treat as a normal, supported configuration (`webhook_secret: # nil` in `test/dummy/config/secrets.yml`, "(optional)" in `docs/setup.md`). Any operator following the documented setup without filling in the optional secret is exposed by default; multi-tenant deployments are additionally exposed even when *some* orgs do set a secret, because the attacker simply names a different, secret-less org in the JSON body.

### Recommendation
- Never resolve the verification key from attacker-supplied JSON before the signature is validated; require `X-Hub-Signature` verification against a secret that is bound to the actual delivery (GitHub signs per-installation, so the installation/App-level secret should be used, not one derived from body content).
- Fail closed instead of returning `true` when `webhook_secret` is blank; require a `webhook_secret` to be present for every onboarded organization/installation.
- Re-validate that the `organization`/`repository` field used to select the secret matches the `organization`/`repository` field acted upon by the handler before dispatching (`Shipit::Webhooks.for_event`).

### Proof of Concept
1. Onboard/target a Shipit deployment where organization `no-secret-org` has `webhook_secret: nil` (a documented, valid configuration) while victim organization `victim-org` has `Shipit.github_teams` referencing `victim-org/some-team`.
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "no-secret-org" },
  "team": { "id": 1, "name": "some-team", "slug": "some-team", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
No valid `X-Hub-Signature` is required because `verify_webhook_signature` short-circuits to `true` for `no-secret-org`.
3. `MembershipHandler` creates a `Membership` for `attacker-github-login` in team `some-team` (as shown in the existing test `":membership can append an user membership"`).
4. Attacker completes real GitHub OAuth as `attacker-github-login`; `User#authorized?` now returns `true` because a `Membership` row exists for a team present in `Shipit.github_teams`, granting full access to the Shipit instance.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
