### Title
Unrestricted `BlockRevenue` commission updates (SIMD-0291) retroactively alter already-earned block-reward splits for the current epoch - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`GovSettings::editSettings`'s flaw is that a single global parameter (`voteRewardsCoefficient`) can be changed mid-flight and is then applied uniformly to reward calculations for value that voters already earned in the past, so payouts differ depending only on *when* they are claimed rather than on the terms in effect when the work was done. Agave has an almost identical parameter-retroactivity hazard in vote-account commission handling for block-revenue rewards.

### Finding Description
Agave already recognizes and mitigates this exact bug class for **inflation-rewards** commission: the `delay_commission_updates` feature forces the epoch-rewards calculator to use a commission value captured a full epoch *before* the rewarded epoch (`snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts`), specifically "to prevent last-minute commission rugs" [1](#0-0) , and this delayed value is what is actually used to compute `commission_bps` for `redeem_rewards` [2](#0-1) .

However, the newer `BlockRevenue` commission (SIMD-0291/SIMD-0123, `block_revenue_commission_bps`) is updated with **no timing restriction whatsoever**: `update_commission_bps` explicitly documents "No commission update rule, per SIMD-0249 and SIMD-0291" and lets the authorized withdrawer set the new rate at any slot, unlike the legacy `update_commission` path which enforces `is_commission_update_allowed` in the first half of the epoch [3](#0-2) , contrasted with the legacy rule enforcement [4](#0-3) .

When `block_revenue_sharing` is active, `calculate_block_reward` is invoked using `cached_vote_accounts.distribution_epoch_vote_accounts` [5](#0-4) , which is documented as "Vote account state from the end of the rewarded epoch / beginning of the distribution epoch" — i.e., the *final* commission value observed at epoch end, not the delayed snapshot used for inflation-rewards commission [6](#0-5) . Because block revenue for the whole epoch is computed once, in bulk, at epoch boundary (analogous to the DAO computing rewards for the whole proposal using a single coefficient), a validator can leave `block_revenue_commission_bps` low throughout the epoch to attract stake/attention, then raise it (up to 100%, i.e., 10000 bps) in the final slots before the epoch-end snapshot is taken by the reward calculator. Because there is no delay mechanism analogous to `delay_commission_updates` protecting this field, the new, higher commission is applied retroactively to *all* block rewards accrued by delegators for the entire already-completed epoch, not just prospectively.

This mirrors the reported bug precisely: a governance/commission parameter is voted/changed after value has already accrued under a previously communicated rate, and the change is unexpectedly applied to that already-earned reward period rather than being frozen for it.

### Impact Explanation
Stakers delegated to a vote account can have their promised share of block-revenue rewards silently reduced for an entire epoch's worth of already-produced blocks, with no forewarning and no epoch-boundary delay to protect them (unlike the analogous inflation-commission path). This is a misattribution/reduction of rewards that stakers were led to expect based on the commission rate observed during the epoch, functioning as a "commission rug" specifically for the block-revenue-sharing reward stream that SIMD-0291 intentionally exempted from the anti-rug delay rule.

### Likelihood Explanation
Any vote-account withdraw authority can trigger this unilaterally and immediately — no consensus change, feature-gate race, or unusual conditions are required beyond `block_revenue_sharing` being active. The only precondition is that the validator (or a compromised/malicious withdrawer key) waits until near end-of-epoch to raise `block_revenue_commission_bps`.

### Recommendation
Apply the same anti-rug delay used for inflation-rewards commission (`delay_commission_updates`) to `block_revenue_commission_bps` as well — i.e., derive the commission used in `calculate_block_reward` from a snapshot taken a full epoch prior to the rewarded epoch (or otherwise freeze the rate in effect for the duration of the epoch being rewarded), rather than from the end-of-epoch `distribution_epoch_vote_accounts` snapshot.

### Proof of Concept
Not applicable/available from static analysis alone; the exact numerical effect depends on `calculate_block_reward`'s internal implementation, which could not be located/read within the available tool budget (grep for `fn calculate_block_reward` only returned its call sites in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, not its definition). The structural evidence above — unrestricted `update_commission_bps` for `BlockRevenue` plus use of the end-of-epoch (undelayed) vote-account snapshot in the block-reward calculation call site — supports the finding, but confirming the exact commission field read inside `calculate_block_reward` would require reviewing its full body, which was not retrievable in this session.

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
