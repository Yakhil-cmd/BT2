### Title
Authorization Bypass Through User-Controlled `address`/`signing_path` in Device "sign" Request Handler - ([File: wallet.js])

### Summary
The `"sign"` message handler in `handleMessageFromHub` accepts a caller-supplied `body.address` / `body.signing_path` pair from any correspondent device and, when the address is locally controlled (`ifLocal`), immediately emits a `signing_request` event asking the wallet owner to approve signing an arbitrary attacker-supplied `unsigned_unit`. The code explicitly disables the check that would verify the sending device is actually a legitimate cosigner/session participant for that address, so the "session" (the address + signing path being signed) is not bound to any verified relationship between the sender and that address — the same bug class as the DeepSeek MCP report, where a caller-controlled `session_id` is accepted without binding it to an authenticated principal.

### Finding Description
In `wallet.js`, the `case "sign":` branch parses `body.address`, `body.signing_path`, and `body.unsigned_unit` from a decrypted device message and, after checking only that `body.address` appears among the authors of the (attacker-supplied) `unsigned_unit`, calls `findAddress` to resolve it: [1](#0-0) 

When the address is locally hosted, `ifLocal` is invoked, and the ownership/cosigner check is explicitly commented out: [2](#0-1)

Because this check is disabled, the `address` value supplied in the message — analogous to the `session_id` in the CVE — is used to select which local signing session/UI confirmation to trigger, but it is never verified to belong to a wallet relationship (shared address / wallet cosigner set) that includes `from_address`. Any paired correspondent device (not necessarily a cosigner of that specific address) can therefore submit a `sign` request naming ANY address the victim wallet locally controls, along with a crafted `unsigned_unit`, and the wallet will proceed straight to `eventBus.emit("signing_request", ...)`, prompting the user to approve a transaction whose legitimacy context (who is really asking, and why) is not authenticated against the target address: [3](#0-2) 

The only structural defenses are (1) the UI confirmation dialog, and (2) heuristics in `getSigner().sign`'s `ifRemote` path that try to detect prosaic/arbiter contract deposits to adjust the displayed message — none of which authenticate that `from_address` is authorized to request signing for `body.address`.

### Impact Explanation
A paired-but-unauthorized device correspondent can trigger signing prompts for units it fully controls the content of (arbitrary outputs/amounts) against any address the victim's wallet locally hosts, including shared/multisig addresses the sender is not a cosigner of. If the wallet UI does not sufficiently distinguish "signing request from a legitimate cosigner of address X" from "signing request from any correspondent naming address X", a user can be tricked into authorizing unauthorized spends from a shared address — i.e., unauthorized spending / fund loss, matching the required impact bar (concrete unauthorized spending).

### Likelihood Explanation
Exploitation only requires being a paired correspondent device of the victim (a normal, low-privilege relationship established via pairing, not requiring being a cosigner of any specific address), and crafting a `sign` device message with an arbitrary `unsigned_unit` naming a locally-controlled address. No special network position or hub compromise is needed — this is reachable purely through the encrypted device-message channel that any correspondent can use.

### Recommendation
Restore (and make mandatory) verification in the `ifLocal` branch that `from_address` is a genuine cosigner of `body.address` (e.g., via `extended_pubkeys`/`wallet_signing_paths` or `shared_address_signing_paths`) before emitting `signing_request`, or otherwise clearly bind and surface the requester's authorization context to the UI before any signature can be produced.

### Proof of Concept
1. Pair device B with victim device A (normal pairing, no special privilege).
2. From B, send a `hub/message` with `subject: "sign"`, `body.address` = one of A's locally-controlled (e.g., shared multisig) addresses that B is not a cosigner of, `body.signing_path` = a valid path for that address, and `body.unsigned_unit` = a crafted unit whose `authors` include `body.address` and whose payment outputs send funds to an address controlled by B.
3. A's `handleMessageFromHub` reaches `case "sign"` → `findAddress` → `ifLocal`, skips the disabled cosigner check, and emits `signing_request` to A's UI.
4. If A approves (believing it's a legitimate cosign request), the malicious unit is signed and funds move to B despite B never being a party to `body.address`.
