### Title
Double-crediting of Bitcoin L1 lockup amounts via outpoint replay across separate `register-for-bond`-style calls - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s L1-lockup verification path (`verify-l1-lockups` / `validate-l1-lockup`) sums the sats credited from a list of Bitcoin UTXOs and only de-duplicates outpoints **within a single call**, via a `seen-outpoints` accumulator that is freshly initialized to `(list)` on every invocation of `verify-l1-lockups`. [1](#0-0) [2](#0-1) 

### Finding Description
`validate-l1-lockup` checks, for each supplied Bitcoin output: that the unlock height is valid, that the output script matches the expected timelock script for the staker/bond, that the claimed amount matches the on-chain output, that the Merkle proof/header are valid, and — critically — that the `(txid, output-index)` outpoint has not already appeared in `seen-outpoints` for *this call*: [3](#0-2) 

The accumulator that carries `seen-outpoints` is constructed fresh inside `verify-l1-lockups` each time it is invoked, seeded with an empty list: [1](#0-0) 

The docstring for `validate-l1-lockup` itself states the scoping explicitly: "`seen-outpoints` tracks every (txid, output-index) pair already credited **in this call**", implying no persistent, contract-wide ledger of previously-credited outpoints is consulted by this function. [2](#0-1) 

This breaks the intended equality: "sats credited via L1 proof == sats actually locked on Bitcoin for that staker/bond." If nothing outside `verify-l1-lockups`/`validate-l1-lockup` maintains a persistent set of already-credited outpoints (checked and marked as used across separate transactions), the same Bitcoin UTXO lockup proof could be resubmitted in a subsequent, independent call (e.g., to register for a different bond, or to re-register/renew the same bond) and be credited again, since the local `seen-outpoints` list is reset every time. This would let a staker (or their signer/counterparty) inflate their credited/staked sats total without ever locking additional BTC — a double-counting of a commitment.

### Impact Explanation
If exploitable, this allows a staker to be credited with sats-backed stake weight multiple times from a single Bitcoin lockup, i.e., unbacked "locked" collateral is recognized in the reward/weight accounting without corresponding BTC ever being locked again. Per the impact classification, this is a double-counting of a commitment, mapping to a Critical/High severity issue (double-counting a commitment or reward, or signing weight/reward slots exceeding locked value).

### Likelihood Explanation
The likelihood depends entirely on whether some other, currently-unverified part of the contract (e.g., the caller of `verify-l1-lockups`, such as `register-for-bond`) maintains and checks a **persistent, cross-call** map of already-used outpoints before invoking this verification. I was not able to locate such a map within the code paths I reviewed, and the function's own documentation explicitly limits de-duplication to "in this call," which is a strong signal that no such global check exists in this function. However, I was unable to fully inspect the complete `register-for-bond`/renewal call graph in `pox-5.clar` before running out of investigation budget, so I cannot rule out that a persistent outpoint ledger exists elsewhere in the contract (e.g., a `used-lockup-outpoints` map checked prior to calling `verify-l1-lockups`). This uncertainty should be resolved by a follow-up review of every call site of `verify-l1-lockups` in `pox-5.clar`.

### Recommendation
- Maintain a persistent, contract-level map (e.g., `used-lockup-outpoints: {txid, output-index} -> bool`) that is checked and updated (via `map-insert`, failing on duplicate) for every outpoint credited through `validate-l1-lockup`/`verify-l1-lockups`, not just within a single call's local accumulator.
- Audit all callers of `verify-l1-lockups` (e.g., `register-for-bond` and any renewal/rollover functions) to confirm they cannot re-submit previously-credited outpoints in later, independent transactions.
- Add regression/unit tests that attempt to replay the same Bitcoin lockup proof across two separate `register-for-bond`-style calls (different bonds, or a second call to the same bond) and assert the second call is rejected.

### Proof of Concept
1. Staker locks BTC on L1 to the timelock script for `bond-index = A`, producing outpoint `O = (txid, output-index)`.
2. Staker calls `register-for-bond` (or equivalent) for bond `A` supplying `O` in the `outputs` list; `verify-l1-lockups` validates it and credits `amount` sats to the staker's stake for bond `A`. `seen-outpoints` inside this call now contains `O`, but this list is discarded once the call returns.
3. Staker calls the registration/renewal flow again — either for a different `bond-index = B`, or in a later separate transaction for the same bond — re-submitting the same `O` in `outputs`.
4. Because `verify-l1-lockups` reinitializes `seen-outpoints` to `(list)` on every call [1](#0-0) , and no other check observed in the reviewed code marks `O` as globally consumed, `validate-l1-lockup` passes all its checks again (script, amount, Merkle proof, height are all still valid for the same on-chain output) and the sats are credited a second time — without any additional BTC being locked.

**Caveat:** This PoC assumes no external, persistent outpoint-tracking mechanism exists in the parts of `pox-5.clar` I was unable to fully review (particularly the full `register-for-bond` implementation and any state map it consults before calling `verify-l1-lockups`). This should be confirmed before treating the finding as fully validated.
