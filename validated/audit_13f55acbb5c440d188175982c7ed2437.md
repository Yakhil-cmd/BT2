### Title
Stale collateral/debt bitmask entry can panic `get-position`, blocking liquidation of an under-collateralized account - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
`get-collateral` and `get-debt` in `v0-market-vault.clar` are implemented with `unwrap-panic (map-get? ...)`, and are only supposed to be called for asset bits that are set in an account's `mask`. `iter-lookup-collateral`/`iter-lookup-debt` fold over the bits from the account's own `mask` and call these panicking getters for every set bit, and `get-position` (used by liquidation/health-check paths and by `protocol-data.clar` aggregation) calls into this fold.

### Finding Description [1](#0-0) 
`get-collateral` and `get-debt` both use `unwrap-panic` on a `map-get?` lookup keyed by `{ id, asset }`, i.e. they assume an entry always exists whenever they are called. `remove-user-collateral` and `remove-user-scaled-debt` [2](#0-1)  delete the corresponding map entry entirely once the balance/scaled-debt reaches `u0`. The account-level `mask` bitmap is the sole index consumed by `lookup-collateral`/`lookup-debt` via `mask-to-list-collateral`/`mask-to-list-debt` and `iter-lookup-collateral`/`iter-lookup-debt` [3](#0-2)  to decide which asset ids to fetch — and `get-position` [4](#0-3)  is the function relied on across the protocol (health checks, liquidation, `protocol-data.clar`'s `get-supplies-user`/`get-market-vault-balances-user`) to read an account's full position. If the public entry points that manage collateral/debt (in `market.clar`) can leave the `mask` bit set for an asset whose backing `collateral`/`debt` map row was deleted (analogous to the NEAR bug where the genesis chunk header stores an empty/never-computed root that the verification code unconditionally assumes is present), any subsequent call to `get-position` for that account aborts the whole transaction instead of returning a graceful error — exactly the panic-vs-error class in the cited NEAR fix.

### Impact Explanation
This lands in the "permanent freezing of funds" / protocol-insolvency class: if an account's position becomes permanently un-queryable through `get-position`, no liquidator (an unprivileged third party) can compute its health factor or execute a liquidation against it, and any DAO/keeper flow that depends on `get-position` also reverts. An account that accumulates bad debt while un-liquidatable directly socializes losses across all suppliers in the affected vaults, since the debt can never be repaid or the collateral seized. The victims here are the liquidators (denied fees) and the pool's other suppliers (bearing the bad debt), not just the position owner — satisfying the "one unprivileged principal harms another via shared state" bar.

### Likelihood Explanation
I could not confirm, within the available tool budget, that the public collateral/debt-removal entry points in `market.clar`/`market-vault.clar` actually fail to clear the `mask` bit in every removal path (full withdrawal, full repayment, forced liquidation-partial-seizure edge cases, rounding-to-zero edge cases). This is the crux fact needed to prove reachability, and it remains unverified.

### Recommendation
Audit every code path in `market.clar`/`market-vault.clar` that deletes a `collateral` or `debt` map row (i.e., balance/scaled-debt hits `u0`) and confirm the corresponding `mask` bit is always cleared for that account in the same transaction. Additionally, harden `get-collateral`/`get-debt` to use `default-to u0` (as `add-user-collateral`/`remove-user-collateral` already do) instead of `unwrap-panic`, so a missing entry degrades gracefully instead of aborting the whole call — directly mirroring the NEAR fix of returning an error instead of asserting/panicking on an absent value.
