### Title
Unfiltered pull request label names injected into deploy/task process environment allow attacker-controlled variables (e.g. `DYLD_INSERT_LIBRARIES`) to reach `Command#start`/`PTY.spawn` - ([File: app/models/shipit/review_stack.rb], [File: lib/shipit/task_commands.rb], [File: lib/shipit/command.rb])

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) as an environment key with value `"true"` into the stack's env, with no allowlist. `TaskCommands#env` (used by `DeployCommands`/`RollbackCommands`) merges this raw `@stack.env` directly into the command environment, bypassing `EnvironmentVariables#permit`/`filter_deploy_envs`, which is only applied to the operator/API-supplied `deploy.variables` env. That merged hash is passed to `Command.new(..., env:)` and ultimately to `PTY.spawn(unbundled_env, ...)`.

### Finding Description
The broken binding: the invariant should be `keys(process_env_passed_to_PTY.spawn) ⊆ keys(deploy_variables) ∪ fixed_internal_keys`. In practice, `keys(process_env) ⊇ pull_request.labels.map(&:upcase)`, which is attacker-controlled with no allowlist.

Path:
1. `ReviewStack#env` (app/models/shipit/review_stack.rb:84-93) does:
```ruby
super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
```
This has no key filter — any label name becomes an env key. `LabelCapturingHandler#capture_labels` (app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102) persists `pull_request.update!(labels: params.pull_request.labels.map(&:name))` directly from the incoming webhook payload's `pull_request.labels[].name` field, which any GitHub user can set by naming a label on their own fork PR (labels are per-repository/org objects the PR author can typically create/apply on their own fork, and label names are attacker-supplied strings in the webhook body).
2. `TaskCommands#env` (lib/shipit/task_commands.rb:33-48) does `super.merge(@stack.env).merge({...fixed keys...}).merge(deploy_spec.machine_env).merge(@task.env)`. Since `@task.env` (the actual deploy_variables-filtered env, set at trigger time via `Stack#build_deploy` → `filter_deploy_envs` → `EnvironmentVariables#permit`) only contains keys explicitly declared in `deploy.variables`, it never overrides or strips label-derived keys such as `DYLD_INSERT_LIBRARIES` that aren't declared in the shipit.yml `deploy.variables` schema.
3. This merged hash is passed into `Command.new(*args, chdir:, env:)` (lib/shipit/command.rb:31-37), stored in `@env`, and used in `unbundled_env` (lib/shipit/command.rb:103-105): `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)`.
4. `Command#start` (lib/shipit/command.rb:85-101) calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, so the label-derived `DYLD_INSERT_LIBRARIES=true` key reaches the spawned child process environment on the deploy host.

Existing guards checked and found insufficient: `EnvironmentVariables#permit`/`filter_deploy_envs` (app/models/shipit/deploy_spec.rb:174-176, lib/shipit/environment_variables.rb) enforce an allowlist only against the `env` hash supplied at deploy-trigger time (`params[:deploy][:env]` in `DeploysController#deploy_params`), not against `Stack#env`/`ReviewStack#env`. The webhook signature verification (`verify_signature`/`GitHubApp#verify_webhook_signature`) authenticates that the payload came from GitHub for the configured repo, but does not restrict the *content* of label names, and label creation/application on a PR author's own fork is not a privileged action gated by `Shipit.github_teams` or repository maintainer status.

Existing tests (`test/models/shipit/review_stack_test.rb:59-65`, `test/lib/shipit/task_commands_test.rb`, `test/lib/shipit/deploy_commands_test.rb`) already demonstrate that arbitrary uppercased label names (`WIP`, `BUG`) flow unfiltered into `stack.env`/`TaskCommands#env`, confirming the mechanism; only the specific `DYLD_INSERT_LIBRARIES` key value needs to be substituted to demonstrate the security-relevant instance of this general pattern.

### Impact Explanation
On macOS deploy hosts, `DYLD_INSERT_LIBRARIES` set in a spawned process's environment causes the dynamic linker to preload the named shared library into every dynamically-linked Mach-O executable invoked by the deploy/rollback steps (subject to standard macOS restrictions, e.g. SIP-hardened runtime binaries ignoring it, but many deploy toolchain binaries such as shell, ruby, git are not hardened-runtime and are affected). Combined with the deploy step's shell execution of the repo's own `deploy.override`/`deploy.pre`/`deploy.post` commands, an attacker who also supplies (or has supplied) a dylib path reachable during the deploy (e.g. via files checked into their own fork or a path they control on the shared deploy host cache) can achieve code execution in the context of every process the deploy step spawns — this is Remote Code Execution on the Shipit deploy host, matching the Critical impact category for `Command`/`PTY.spawn`. This is scoped to `ReviewStack`s belonging to the affected repository/fork (PR-triggered continuous delivery), not stacks of arbitrary unrelated repositories, but is repeatable on every PR-triggered deploy/task/rollback for that stack as long as the label remains applied.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and `provisioning_behavior` in `allow_with_label`/`allow_all` so that a `ReviewStack` exists and is deployed/continuously delivered for the fork PR; the attacker needs the ability to apply a label to their own PR (label creation ability on a fork/repo they control, or use of an existing label name they can apply) and to trigger a deploy or task run (e.g. via continuous delivery on push, or a `/shipit` style comment mechanism depending on configuration) — no Shipit session, API token or GitHub team membership is required beyond normal fork-PR-and-webhook interaction, which matches the described unprivileged attacker. Attacker cost is low (create/apply one label on their own fork PR); feasibility is high because the vulnerable merge (`ReviewStack#env`) applies unconditionally to every PR label with no allowlist, and it is fully repeatable across every deploy/rollback/task for that review stack.

### Recommendation
Filter pull-request-label-derived environment keys through the same allowlist mechanism used for user-supplied deploy variables (`EnvironmentVariables#permit`) before merging them into `ReviewStack#env`/`TaskCommands#env`, or namespace/prefix label-derived keys (e.g. `LABEL_<NAME>`) and explicitly exclude any key colliding with sensitive process-environment variable names (`DYLD_INSERT_LIBRARIES`, `LD_PRELOAD`, `PATH`, `BUNDLE_*`, etc.) so that PR label names can never set arbitrary/dangerous environment variable names on the deploy host.

### Proof of Concept
minitest plan (add to `test/models/shipit/review_stack_test.rb` or `test/lib/shipit/task_commands_test.rb`):
```ruby
test "#env does not allow a PR label to inject dangerous variables such as DYLD_INSERT_LIBRARIES" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["dyld_insert_libraries"]

  env = Shipit::TaskCommands.new(stack.trigger_continuous_delivery).env

  # Binding under test: env passed to Command/PTY.spawn must not contain
  # keys outside deploy.variables ∪ fixed internal keys.
  refute env.key?("DYLD_INSERT_LIBRARIES"), "PR label leaked into process env reaching PTY.spawn"
end
```
Expected result before fix: `env["DYLD_INSERT_LIBRARIES"] == "true"`, demonstrating the key reaches `Command#env`/`unbundled_env` and would be passed to `PTY.spawn`. After remediation (allowlisting/prefixing label-derived keys), the assertion `refute env.key?("DYLD_INSERT_LIBRARIES")` should pass.
