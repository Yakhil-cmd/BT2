### Title
`status` webhook binds signature verification to attacker-controlled `repository.owner.login` but the handler resolves and mutates commits with no repository scoping at all - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted JSON body. `StatusHandler#process`, however, resolves the target `Commit` purely by SHA across the whole installation (`Commit.where(sha: params.sha)`), with zero binding to the repository/organization that was used to authenticate the request. This breaks the equality "organization that authenticated the webhook == repository the webhook is allowed to act on," letting an attacker who legitimately controls the webhook secret of *any* organization configured in this Shipit instance forge CI status updates for commits belonging to *any other* stack/organization.

### Finding Description
`verify_signature` picks the HMAC secret using a field the attacker fully controls in the raw JSON body: [1](#0-0) 

The `status` event is then dispatched to `StatusHandler`, whose `params` schema only requires `sha`, `state`, and optional `description`/`target_url`/`context`/`created_at`/`branches` — there is no `repository` requirement at all: [2](#0-1) 

`process` looks up commits globally by SHA, independent of any organization/repository:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

`create_status_from_github!` builds a `Status` record directly from attacker-supplied fields (`state`, `description`, `target_url`, `context`, `created_at`): [4](#0-3) [5](#0-4) 

Creating a `Status` has real side effects unrelated to the organization that signed the request: it enables CI on the target stack and schedules continuous delivery: [6](#0-5) 

If the affected stack has `continuous_deployment: true`, `ContinuousDeliveryJob` will trigger an actual deploy once the stack is unoccupied and the commit's status/state is deployable: [7](#0-6) 

**Binding broken:** the organization whose `webhook_secret` authenticated the request (`repository.owner.login` used only for signature selection) is not equal to the repository/stack whose commit state (`Commit.where(sha: ...)`) is actually mutated. Because commit SHAs are 40-hex-character values that can collide across unrelated repositories only by chance, but more importantly a real, disclosed SHA belonging to a *known* target stack can simply be reused by the attacker in a forged payload signed with their own org's secret.

### Impact Explanation
This crosses an authentication boundary between tenants of a shared/multi-org Shipit deployment (a case explicitly supported by `Shipit.github(organization: ...)` and `config/secrets*.yml` holding one `webhook_secret` per organization). An attacker who is a legitimate customer of the Shipit instance for organization A (and thus knows organization A's webhook secret and can produce a validly signed `X-Hub-Signature`) can forge a `status` event whose `repository.owner.login` is `A` (so the signature check passes) but whose `sha` is a commit belonging to organization B's stack. This allows: (1) injecting fabricated CI status entries for arbitrary commits it does not control, and (2) if the target stack is continuous-deployment enabled, triggering an unauthorized deploy of organization B's code by supplying a forged "success" status for a not-yet-deployed commit. This satisfies the "unauthorized deploy" High-impact criterion.

### Likelihood Explanation
Requires the attacker to already hold a valid webhook secret for at least one organization configured on the shared Shipit instance (a realistic scenario in any multi-tenant/multi-org deployment, since each org's secret is independent and no cross-check to the target repository exists). No repository write access, no GitHub App private key, and no Shipit session/API token is required — only knowledge of one org's `webhook_secret`, which is a lower-privilege credential than the ones excluded by the rules. The target commit SHA is typically discoverable (commits/output are often publicly visible or leaked via other stacks' public pages), making this practically exploitable.

### Recommendation
Scope `StatusHandler` (and ideally `Handler#stacks`/`repository_name` overall) so it only updates commits belonging to the repository named in the payload's `repository.full_name`, and additionally verify that this `repository.full_name`'s owner matches the organization that was actually used to validate the webhook signature in `WebhooksController#verify_signature`. Reject events where the two do not match.

### Proof of Concept
1. Attacker is a customer of the Shipit instance and legitimately owns organization `attacker-org`, configured in Shipit with its own `webhook_secret`.
2. Attacker discovers (e.g., from the public commit history of a victim stack in organization `victim-org`) the SHA of a not-yet-deployed commit on a continuous-deployment-enabled stack.
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-context",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
4. Attacker signs this payload with their own `attacker-org` `webhook_secret` and sends it with header `X-Github-Event: status` to `/webhooks`.
5. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and successfully verifies the signature. [8](#0-7) 
6. `StatusHandler#process` finds the victim's `Commit` purely by SHA (ignoring the `repository` field entirely) and creates a forged `success` `Status` on it. [3](#0-2) 
7. `Status#after_create` callbacks enable CI and schedule continuous delivery for `victim-org`'s stack, potentially causing `ContinuousDeliveryJob` to deploy that commit without any authorization from `victim-org`. [6](#0-5) [7](#0-6)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
