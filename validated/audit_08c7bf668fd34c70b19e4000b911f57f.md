### Title
`StatusHandler#process` mutates `Commit`/`Status` records for any stack sharing a `sha`, bypassing repository scoping used by `PushHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::Handler` defines a `stacks` helper that scopes all mutation to `Repository.from_github_repo_name(repository_name)` derived from the verified payload's own `repository.full_name` [1](#0-0) . `PushHandler#process` and `CheckSuiteHandler#process` both honor this by mutating only `stacks.not_archived.where(branch:)` / `stacks.where(branch:)` [2](#0-1) [3](#0-2) . `StatusHandler#process`, however, resolves the target purely via `Commit.where(sha: params.sha)`, never calling `stacks`, `repository_name`, or `Repository.from_github_repo_name` at all [4](#0-3) .

### Finding Description
Broken binding: `StatusHandler#process`'s mutation target should equal `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })` (repository-scoped, as in `PushHandler`), but it actually equals `Commit.where(sha: params.sha)` (global, unscoped) [4](#0-3) . These two sets are not equal whenever a `Commit` row with the same `sha` exists under a different `Repository`/`Stack` than the one that sent the webhook — which happens routinely for forks, since fork histories share commit SHAs with their upstream.

Path: a `status` webhook hits `WebhooksController#create`, which after `verify_signature` (using `Shipit.github(organization: repository_owner)` and the org's configured `webhook_secret`) dispatches to `Shipit::Webhooks.for_event('status')` handlers, i.e. `StatusHandler.call(params)` [5](#0-4) . `verify_signature` authenticates that the payload really came from the organization named in `payload['repository']['owner']['login']` — it does **not** verify that the `sha` the payload references belongs to that same organization's repository. `StatusHandler#process` then calls `commit.create_status_from_github!(params)` on every `Commit` row anywhere in the database whose `sha` matches, regardless of which `Stack`/`Repository` it belongs to.

An attacker who owns (or forks) a repository that is legitimately onboarded to Shipit can:
1. Fork a repository whose commit history is shared with (or push a branch containing) a commit sha that is also tracked by a victim stack (a `Commit` row already exists for that sha under the victim's stack, created when the victim's push/pull events ingested it).
2. Trigger a real, validly-signed `status` webhook from their own repo/org (this passes `verify_signature` because it's actually signed by GitHub using the attacker's own org's configured webhook secret — no secret theft required).
3. `StatusHandler#process` finds the victim's pre-existing `Commit` row (same `sha`, different `Repository`) via the unscoped `Commit.where(sha: ...)` query and calls `create_status_from_github!` on it, writing an attacker-controlled `state`/`context`/`description`/`target_url` onto a commit belonging to a repository the attacker never authenticated against.

Existing guards do not stop this: `verify_signature` only authenticates the sender's organization, not the `sha` ownership; the `ExplicitParameters` schema only validates types/presence, not repository ownership; there is no model-level constraint tying a `Status` write back to the repository named in the payload.

### Impact Explanation
This lets a payload legitimately signed for repository/org A mutate `Commit`/`Status` records belonging to a stack under an entirely different repository/org B, satisfying the "payload for one repository mutating another's stack, commit ... " Critical category. `create_status_from_github!` fires `commit_status` and potentially `deployable_status` webhooks/state transitions on the victim commit [6](#0-5) , which can affect deploy-readiness gating (`required_statuses`/`blocking_statuses`) on the victim's stack — i.e., an attacker can flip a victim commit's CI status to `success` to unblock/allow a deploy, or to `failure`/`error` to block one, entirely from outside that repository's trust boundary. This is repeatable against any stack whose tracked commit history overlaps (via fork or shared history) with a repository the attacker controls.

### Likelihood Explanation
Preconditions: the attacker needs (a) a GitHub repository they administer, onboarded to the same Shipit instance (self-service repo/stack creation is a normal, unprivileged Shipit workflow), and (b) a shared commit `sha` between their repo and the victim's tracked stack — trivially achieved by forking a public repository that a victim also tracks in Shipit, or by the victim commit being a widely-shared open-source commit. No secrets, tokens, or GitHub App credentials are required; the webhook signature is genuinely valid because it is signed by GitHub for the attacker's own org. This makes the attack cheap, repeatable, and requires no elevated GitHub or Shipit privileges.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: resolve commits only through `stacks` (i.e. `Repository.from_github_repo_name(repository_name)`'s stacks), e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha)).each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }`, ensuring the mutation is confined to the repository named in the payload's own `repository.full_name`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual file may need creating):
```ruby
test "#process does not mutate commits belonging to other repositories" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, message: "shared history")

  attacker_repo = Repository.create!(owner: "attacker-org", name: "attacker-repo")
  payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => attacker_repo.full_name, "owner" => { "login" => "attacker-org" } }
  }

  handler = Shipit::Webhooks::Handlers::StatusHandler.new(payload)

  # Binding under test: mutation target should equal stacks scoped to attacker_repo (empty),
  # not Commit.where(sha:) unscoped (which matches victim_commit).
  assert_equal Stack.none.to_a, handler.send(:stacks).to_a  # attacker_repo has no stacks/commits

  assert_no_difference -> { victim_commit.reload.statuses.count } do
    handler.process
  end
end
```
Running this against the current code fails: `victim_commit.statuses.count` increases even though `handler.send(:stacks)` (scoped to `attacker_repo`) never contains `victim_commit`, proving `StatusHandler#process` bypasses the `stacks` scoping used elsewhere in the codebase.

      head(422) unless verified
