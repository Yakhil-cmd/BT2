### Title
Cross-organization webhook trust confusion – signature verification org ≠ repository written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization secret to validate a webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`). However, every event handler (`Handler#repository_name`, and each handler's `params.repository.full_name` usage) resolves the actual `Repository`/`Stack` to mutate using the independent `repository.full_name` field from the same JSON body. These two fields are never cross-checked against each other.

### Finding Description
`Shipit.github(organization: repository_owner)` in `app/controllers/shipit/webhooks_controller.rb:24-30` looks up the `GitHubApp` config (and its `webhook_secret`) for the organization named in `repository.owner.login`. The HMAC signature is verified only against *that* org's secret: [1](#0-0) 

Critically, `GitHubApp#verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that organization: [2](#0-1) 

Per the setup docs, the webhook secret is explicitly **optional**: [3](#0-2) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the *raw, attacker-controlled* JSON body to the registered handlers unmodified: [4](#0-3) 

Every handler then independently determines the repository to act on using `repository.full_name`, a completely different payload field than the one used for authentication: [5](#0-4) [6](#0-5) 

This breaks the binding: `organization-that-authenticated == repository-that-is-written`. In a multi-organization Shipit deployment (`Shipit.github_organizations`, `github_app_config`), each org has its own independent `GitHubApp` and `webhook_secret`: [7](#0-6) 

If any one onboarded organization ("Org-Low") has no `webhook_secret` configured (or a weaker/known one), an attacker can send a single POST to the shared `/webhooks` endpoint with `repository.owner.login = "Org-Low"` (satisfying signature verification trivially since `webhook_secret` is blank) while setting `repository.full_name = "Org-High/protected-repo"` — a repository belonging to a *different*, properly-secured organization. Because the handlers never verify that `full_name`'s owner matches the org whose secret authenticated the request, the forged event is processed against `Org-High`'s repository/stack.

### Impact Explanation
Depending on the event type, this allows an attacker with no credentials for the target organization to:
- Trigger `PushHandler` → `stack.sync_github(expected_head_sha:)` for an arbitrary tracked stack, forcing Shipit to treat an attacker-chosen SHA as the head of the branch, which can advance `undeployed_commits` state used by later legitimate deploys.
- Trigger `PullRequest::OpenedHandler`/`LabeledHandler`/`UnlabeledHandler` to create, archive, or unarchive Review Stacks for the victim repository via `ReviewStackAdapter`.
- Trigger `StatusHandler` to write forged CI/commit statuses (`Commit#create_status_from_github!`) against real commits, which Shipit's `ci.require`/merge-queue logic consults before allowing a merge or deploy — effectively laundering a fake "green" status into a protected repository's merge/deploy gate.

This is a cross-repository/cross-organization write achieved purely by exploiting the mismatch between the field used for authentication and the field used for target resolution — no `webhook_secret`, private key, or repository access for the target org is required, only knowledge that some other onboarded org lacks (or has a weak) webhook secret. This matches the High-severity category of "escalation into authorization" / effectively an unauthorized state mutation of stack/commit-status data that gates deploys, without the app's actual GitHub credentials.

### Likelihood Explanation
Likelihood is moderate-to-high in any Shipit instance onboarding more than one GitHub organization: the webhook secret is documented as optional per app, so it is plausible for at least one lower-priority/test organization to be configured without one while a security-sensitive organization has one configured. Since the webhook endpoint is shared and unauthenticated by IP/org scoping, any internet client can attempt this with zero prior access.

### Recommendation
- After signature verification, assert that `repository_owner` (the organization the signature was verified against) equals the owner embedded in `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to handlers; reject on mismatch.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in a multi-org configuration — either require a secret for every configured organization or bind verified organization identity explicitly to the repository object passed to handlers instead of re-parsing it from the untrusted payload.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `OrgLow` (no `webhook_secret`) and `OrgHigh` (with `webhook_secret` set), each tracking their respective repositories as Shipit stacks — a realistic multi-tenant setup as shown in `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: push` and no/incorrect `X-Hub-Signature`, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker_chosen_sha>",
  "repository": {
    "owner": { "login": "OrgLow" },
    "full_name": "OrgHigh/protected-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgLow")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/garbage) signature header.
4. `PushHandler#process` calls `Repository.from_github_repo_name("OrgHigh/protected-repo")` (via `Handler#repository_name`) and invokes `stack.sync_github(expected_head_sha: "<attacker_chosen_sha>")` on `OrgHigh`'s protected stack — despite the request never being authenticated by `OrgHigh`'s webhook secret.

Note: I was unable to execute this end-to-end in a live Shipit instance to confirm runtime behavior beyond static code review; the analysis is based on the code paths cited above (`app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/push_handler.rb`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
