### Title
Unfiltered PR label names reach the OS process environment of `ruby`/`bundle` dependency install commands, allowing `GEM_PATH` (and any other loader variable) injection - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) directly into the stack environment hash with no allow-list, unlike every other env source in this codebase which goes through `EnvironmentVariables#permit`. That hash flows unfiltered through `TaskCommands#env` into `Command#env`/`Command#unbundled_env`, which is passed straight to `PTY.spawn` for the `bundle install`/`ruby` dependency step generated by `TaskCommands#install_dependencies`. An attacker who can label their own PR (e.g. add label `gem_path`) with `provisioning_behavior=prevent_with_label` can therefore set `GEM_PATH` in the environment of the review-stack's dependency install command.

### Finding Description
The broken binding: the code assumes `stack.env.keys ⊆ deploy_variable_names ∪ fixed_internal_keys`, i.e. every key injected into the task/command environment is either a hardcoded Shipit key or has passed `EnvironmentVariables#permit(variable_definitions)` (as enforced for `Task#env`, `Deploy#env`, `Rollback#env` via `TaskDefinition#filter_envs` / `DeploySpec#filter_deploy_envs`, `app/models/shipit/task_definition.rb:63-65`, `app/models/shipit/deploy_spec.rb:174-180`). That invariant is broken for `ReviewStack#env`:

```
app/models/shipit/review_stack.rb:84-93
def env
  return super unless pull_request.present?
  super
    .merge(
      pull_request
        .labels
        .each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
    )
end
```

No call to `EnvironmentVariables.with(...).permit(...)` is made here — every label name becomes a raw environment key with value `"true"`.

Path from attacker to execution:
1. Attacker opens/labels a PR with a label literally named `gem_path` (case-insensitive, since it's `.upcase`d) on a repo configured with `review_stacks_enabled` and `provisioning_behavior: prevent_with_label`.
2. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim into `PullRequest#labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) — no allow-list, straight from the webhook JSON body.
3. When any task runs on that review stack (e.g. the PR's CD deploy, or a triggered custom task), `TaskCommands#env` calls `.merge(@stack.env)` (`lib/shipit/task_commands.rb:33-48`), pulling in `ReviewStack#env`'s unfiltered `GEM_PATH=true`.
4. `TaskCommands#install_dependencies` builds a `Command.new(command_line, env:, chdir: steps_directory)` for the `bundle install` (or other ruby) step discovered by `DeploySpec::BundlerDiscovery#discover_bundler` (`lib/shipit/task_commands.rb:17-21`, `app/models/shipit/deploy_spec/bundler_discovery.rb`).
5. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, where `unbundled_env` is `BASE_ENV.merge(...).merge(@env.stringify_keys)` (`lib/shipit/command.rb:85-105`) — `@env` (containing attacker-controlled `GEM_PATH`) overrides `BASE_ENV`/`ENV` with no filtering at all at this layer.

Because Ruby's `RubyGems`/`Bundler` toolchain honors `GEM_PATH` to locate gems consulted by `require`, an attacker-writable path placed there (e.g. pointing at a directory the attacker also controls inside the checked-out working tree, or a shared/writable location) can be consulted during `bundle install`/`bundle exec`, enabling arbitrary code execution during that dependency step.

Existing guards do not stop this: `EnvironmentVariables#permit` is only invoked for task/deploy/rollback custom `env` params supplied via API (`TaskDefinition#filter_envs`, `DeploySpec#filter_deploy_envs`) — never for `ReviewStack#env`'s label-derived hash. `LabelCapturingHandler`'s `ExplicitParameters` schema only validates types/presence of `labels[].name` (`String`), not the content or an allow-list of names. There is no `require_permission!`/authorization gate relevant here since the actor is an unprivileged PR author acting on their own fork/PR.

### Impact Explanation
An attacker who can open/label a PR on any repository with review stacks enabled (`provisioning_behavior=prevent_with_label` or `allow_with_label`/`allow_all`, since `ReviewStack#env` merges labels unconditionally regardless of behavior) can inject arbitrary environment variable keys (uppercased label names) with value `"true"` into the exact process environment used to execute the `bundle install`/`ruby` dependency step run by Shipit on the deploy host for that stack. Depending on toolchain behavior and file-system layout, this can escalate to code execution during dependency installation (Critical — RCE class per the rules), and at minimum represents an unauthorized/unintended environment perturbation of a privileged Shipit-invoked process, which is out of the intended trust boundary (fixed hardcoded keys / allow-listed variables only). The blast radius is limited to that one review stack's dependency install command, but is repeatable per PR/per label, and any repository with review stacks enabled is affected — not cross-tenant beyond the affected repository's own review stack.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with any provisioning behavior (`prevent_with_label`, `allow_with_label`, or `allow_all`), and use a `ruby`/`Gemfile`-based dependency step (auto-detected by `DeploySpec::BundlerDiscovery#bundler?`). The attacker only needs the ability to open a pull request and add a label to it on a repository they control (fork), or push code plus label their own PR — no Shipit credentials, GitHub App keys, or maintainer status required. This is low-cost and fully repeatable (relabel/unlabel/relabel, or open new PRs) as confirmed by the existing test coverage that labels flow straight into `stack.env` (`test/models/shipit/review_stack_test.rb:59-65`, `test/lib/shipit/task_commands_test.rb`).

### Recommendation
Do not merge raw pull-request label names into the process environment. Either:
1. Remove the label→env merge in `ReviewStack#env`, or
2. Route it through `EnvironmentVariables#permit` against an explicit allow-list (e.g. only labels matching a safe pattern and not colliding with sensitive/loader-related variable names such as `GEM_PATH`, `GEM_HOME`, `RUBYOPT`, `RUBYLIB`, `LD_PRELOAD`, `BUNDLE_*`, `PATH`), and additionally deny-list keys that could influence the ruby/bundler toolchain or process loader regardless of source.
3. As defense in depth, make `Command#unbundled_env` strip/deny known loader-sensitive keys before merging `@env`, so no per-task environment source (label-derived or otherwise) can override them.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (add)
test "#env allows a pull request label to inject GEM_PATH into command env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["gem_path"]

  assert_equal "true", stack.env["GEM_PATH"]

  task = shipit_tasks(:shipit_restart)
  task.stack = stack
  command_env = Shipit::TaskCommands.new(task).install_dependencies.first&.env || Shipit::TaskCommands.new(task).env

  assert_equal "true", command_env["GEM_PATH"],
    "expected GEM_PATH from PR label to reach the ruby/bundle dependency step's process env"
end
```
Binding under test (both sides should be equal only if the invariant holds — it doesn't):
- Expected (invariant): `TaskCommands.new(task).env.keys - FIXED_INTERNAL_KEYS ⊆ allowed_variable_names` (i.e., no key present unless whitelisted)
- Actual: `TaskCommands.new(task).env["GEM_PATH"] == "true"` after merely labeling the PR "gem_path" — demonstrating the divergence and confirming the vulnerable path from `ReviewStack#env` → `TaskCommands#env`/`#install_dependencies` → `Command#env`/`#unbundled_env` → `PTY.spawn`.
