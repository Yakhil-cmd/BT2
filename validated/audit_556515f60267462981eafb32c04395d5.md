**Analysis:**

The premise conflates two unrelated concerns. `AggregatorSnapshotResource<T>` in `types/src/account_config/resources/aggregator.rs` is a plain Rust struct mirroring a Move `AggregatorSnapshot<IntElement>`, used to represent parallel-aggregator snapshot values (e.g., for supply/counter tracking) [1](#0-0) . It is not returned by the account balance REST endpoint, which instead reads `CoinStoreResourceUntyped`, `FungibleStoreResource`, or `ConcurrentFungibleBalanceResource` state directly from the DB at the requested ledger version [2](#0-1) . There is no code path where a client-supplied or attacker-controlled `AggregatorSnapshotResource<T>` value feeds into `fee_payer_prologue`'s auth-key check.

The actual on-chain authenticity check for a fee-payer transaction is performed inside `prologue_common`/`unified_prologue_fee_payer_v2`/`versioned_prologue` in `transaction_validation.move`, which reads the fee payer's authentication key fresh from account state at execution time via `account::get_authentication_key(fee_payer_address)` and compares it against the authenticator-derived key hash, aborting with `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY` on mismatch [3](#0-2) . This check is re-evaluated at actual on-chain execution time against the live account state, not against any REST API response the client may have cached earlier [4](#0-3) . Any client-side balance snapshot becoming stale due to an auth-key rotation between a REST read and submission is a client-side staleness/UX concern, not an admission-boundary defect: the VM re-derives and re-checks the fee payer's current auth key at validation/execution time regardless of what the client previously observed via the API, so rotation cannot cause bypass of sequence, expiry, chain-id, or auth-key checks, nor rebind/replay a transaction.

There is no unprivileged input path here that gets a transaction admitted incorrectly — the described scenario does not correspond to any actual code interaction in this repository.
