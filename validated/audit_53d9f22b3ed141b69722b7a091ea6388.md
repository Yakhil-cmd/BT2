### Title
Symlinked `.claude` directory causes `setup-ralph-loop.sh` to write state file outside workspace - ([File: plugins/ralph-wiggum/scripts/setup-ralph-loop.sh])

### Summary
`setup-ralph-loop.sh` runs `mkdir -p .claude` followed by `cat > .claude/ralph-loop.local.md` relative to the current working directory without verifying that `.claude` is a real directory confined to the workspace. If a malicious repository ships `.claude` as a committed symlink (git supports symlink blobs, mode `120000`) pointing outside the workspace (e.g. to `$HOME/.ssh` or another absolute/relative escape path), `mkdir -p` succeeds silently because the target already resolves to an existing directory, and the subsequent heredoc write follows the symlink, writing attacker-influenced content to a location outside the intended workspace boundary.

### Finding Description
The command is invoked via `plugins/ralph-wiggum/commands/ralph-loop.md`, which runs `"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" $ARGUMENTS` from the user's current session working directory (the checked-out repo). In `setup-ralph-loop.sh`: [1](#0-0) 
`mkdir -p .claude` does not fail or warn if `.claude` already exists as a symlink to an existing directory — POSIX `mkdir -p` treats an existing (non-regular-file) path satisfying the name as success. [2](#0-1) 
The heredoc write `cat > .claude/ralph-loop.local.md <<EOF ... EOF` then resolves `.claude` through the filesystem, following the symlink, and creates/overwrites `ralph-loop.local.md` inside whatever directory the symlink points to, with contents including `$MAX_ITERATIONS`, `$COMPLETION_PROMISE_YAML`, a timestamp, and the attacker-influenceable `$PROMPT` (user-supplied slash-command arguments, but the file content and location are still redirected outside the sandboxed workspace by attacker-controlled repository state). Git natively supports committing symlinks (`120000` mode blobs); cloning such a repository recreates the symlink on disk exactly as specified by the blob target, including relative escape sequences like `../../../../.ssh`. No check in the script (`-L`, `readlink`, or realpath containment check) exists to detect or reject `.claude` being a symlink before writing.

### Impact Explanation
This allows a repository under attacker control to redirect writes performed by a legitimate slash command (`/ralph-loop`) to an arbitrary filesystem location reachable by the victim's user account, outside the intended project/workspace directory. This is a workspace confinement violation — an arbitrary file write/creation outside the intended workspace boundary, matching a scoped "workspace escape via file write" bounty impact. The severity is bounded by the fact that the written filename is fixed (`ralph-loop.local.md`) and cannot overwrite arbitrary existing filenames, but it can create new files, and if the symlink target is a directory such as `~/.ssh` or a directory that is watched/parsed by other tooling, this still represents a boundary violation with potential for follow-on effects (e.g., directory pollution, disk exhaustion, or interaction with tools that scan such directories).

### Likelihood Explanation
Preconditions: the victim must clone/checkout an attacker-controlled repository containing a committed `.claude` symlink and then run `/ralph-loop` inside that repository. This is a normal, expected workflow (cloning third-party repos and using Claude Code plugins on them), and requires no special privileges, leaked credentials, or social engineering beyond the routine act of running the ralph-loop command in an untrusted checkout. The behavior is deterministic and repeatable — `mkdir -p` and `cat >` will always follow the pre-existing symlink.

### Recommendation
Before writing, verify `.claude` is a real directory owned by/contained within the workspace and not a symlink: use `[[ -L .claude ]]` (or `[[ -L .claude ]] && ! [[ -d .claude ]]`) to detect a symlink and abort with an error, or resolve `.claude` with `realpath` and confirm the resolved path is a descendant of `$(pwd)` (workspace root) before performing `mkdir -p` / writing. Consider using `mkdir -p` with `O_NOFOLLOW`-safe semantics (e.g., write to a temp file and `mv` only after confirming the target directory's realpath is inside the workspace), and apply the same guard consistently to other scripts that do `mkdir -p .claude` (e.g., `plugins/hookify/commands/hookify.md`).

### Proof of Concept
Integration test plan:
1. Create a fixture git repository. In it, commit a symlink named `.claude` pointing to a directory outside the repo (e.g., `ln -s /tmp/attacker-target .claude`, `git add .claude`, commit — git will store this as a `120000` mode blob).
2. Clone this fixture repository to a fresh directory (`git clone fixture-repo victim-workspace`), confirming `victim-workspace/.claude` is recreated as a symlink pointing to `/tmp/attacker-target`.
3. From within `victim-workspace`, run `bash plugins/ralph-wiggum/scripts/setup-ralph-loop.sh "test prompt"`.
4. Assert that `/tmp/attacker-target/ralph-loop.local.md` now exists and contains the expected YAML frontmatter/prompt content — proving the write escaped `victim-workspace`.
5. Assert (as the intended fix) that after patching the script with a symlink/containment guard, the script instead exits non-zero with an error and no file is created at `/tmp/attacker-target/ralph-loop.local.md`, and/or that `realpath("victim-workspace/.claude")` is verified to start with `realpath("victim-workspace")` before any write occurs.
