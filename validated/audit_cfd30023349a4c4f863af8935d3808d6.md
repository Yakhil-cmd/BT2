### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only authenticates that the request body's HMAC matches the `webhook_secret` configured for the organization named in `params.dig('repository','owner','login')`, proving nothing about which `Stack`/`Commit` rows the payload is entitled to touch. `StatusHandler#process` then queries `Commit.where(sha: params.sha)` with no join or filter on repository/stack, so any commit anywhere in the database sharing that SHA gets its status mutated, regardless of which org's secret signed the request.

### Finding Description
The claimed binding is: `organization that produced a validly-signed request (WebhooksController#repository_owner, i.e. params['repository']['owner']['login'])` **==** `organization owning every Commit row that StatusHandler#process mutates`.

Tracing the code:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and fetches `Shipit.github(organization: repository_owner)`, then verifies the HMAC signature against that org's `webhook_secret`. This only proves "attacker controls a repo/webhook under `repository_owner`'s GitHub org, and knows that org's secret" (trivially true for the attacker's own fork/org). It says nothing about the `sha` field's ownership.
- `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `#create` (line 12) dispatches the raw, unscoped `params` hash to every registered handler for the event type — `repository_owner`/`repository.full_name` is never passed along or re-checked by the handler layer.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
`Commit` (`app/models/shipit/commit.rb:11`) `belongs_to :stack`, and `Stack` belongs to a `Repository`/organization, but `StatusHandler` never joins to `stacks`/`repositories` nor compares `commit.stack.repository.owner` (or similar) against `repository_owner`. It matches purely on the git SHA string, which is a content-addressed hash — identical across any repositories/forks that share the same commit object (same parents/tree/author/committer/timestamp/message).

Attack: an attacker creates their own GitHub organization/repo (or forks the victim's public repo, which shares commit objects with the victim's Stack until history diverges), registers/points a webhook at the Shipit host, and POSTs a `status` event whose `repository.owner.login` is the attacker's own org (so `verify_signature` passes using the attacker's own legitimately-known secret) but whose `sha` is a commit that is also imported into a victim organization's `Stack#commits` table (e.g., a shared upstream commit, or a commit the attacker learned the SHA of from the victim's public commit history/CI logs). `StatusHandler#process` finds and mutates the victim's `Commit` row via `create_status_from_github!`, which ultimately calls `statuses.replicate_from_github!` and can flip the commit's aggregate CI status (`success`/`failure`/`pending`), affecting `deployable?`, `blocked?`, `schedule_continuous_delivery`, and Hook emission for the victim's stack — all without the attacker ever authenticating against the victim's org's webhook secret.

None of the listed guards prevent this: `verify_signature` only checks HMAC per `repository_owner`, not per-commit ownership; `drop_unhandled_event` only filters unknown event types; there is no `ExplicitParameters` constraint tying `sha` to `repository`; `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant (this is an unauthenticated webhook endpoint by design); `Repository`/`Stack` validations don't prevent duplicate SHAs across stacks (git SHAs are legitimately shared across forks/mirrors and Shipit's schema has no uniqueness constraint scoping `sha` to `repository_owner`).

### Impact Explanation
An attacker who owns any GitHub org/repo (trivial, free) can forge commit-status webhooks that mutate `Commit`/`Status` records belonging to a completely unrelated organization's `Stack`, as long as they know or can guess a SHA that also exists in the victim's stack (straightforward for shared upstream history via forks, or for any commit whose SHA leaked via public GitHub UI/API/CI logs — SHAs are not secret). This can flip a commit from failing to "success", unblocking `deployable?`/`blocked?` checks and triggering `schedule_continuous_delivery`, i.e., causing an unauthorized deploy decision for a stack the attacker never authenticated against — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy". It's repeatable against any organization/stack whose commits share a SHA reachable by the attacker, and the blast radius spans all tenants hosted by the same Shipit instance.

### Likelihood Explanation
Preconditions: attacker needs (1) their own GitHub org/repo with a working webhook secret pointed at the Shipit host (self-service, no privilege needed), and (2) a SHA that is also present in a target stack's `commits` table — trivially satisfiable for public forks sharing history, or for any commit SHA the attacker can observe on the target's public GitHub repo/PRs/CI. No Shipit session, API token, or GitHub App secret is required. Cost is a single crafted HTTP POST to `/webhooks` per attempt, fully repeatable and scriptable.

### Recommendation
Scope `StatusHandler#process` (and other SHA-keyed handlers like `CheckRunHandler`/similar) to the repository that was authenticated by `verify_signature`. E.g., pass `repository_owner`/`repository.full_name` from the controller through the handler dispatch, and filter: `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: repository_owner, ... })` (or join via `Stack#repository_name`/`Stack#repository_owner` matching the verified `repository.full_name`), so only commits belonging to stacks whose repository matches the webhook's authenticated repository are mutated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "process does not mutate commits belonging to a different org's stack" do
  victim_stack = shipit_stacks(:shipit) # owned by org "victim-org"
  attacker_repo_owner = "attacker-org"

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared upstream commit")

  # Binding under test:
  #   repository_owner_that_signed_request == "attacker-org"
  #   commit.stack.repository.owner (victim_commit.stack) == "victim-org"
  # These must NOT be equal for the mutation to be rejected.
  assert_not_equal attacker_repo_owner, victim_commit.stack.repository.owner

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "repository" => { "owner" => { "login" => attacker_repo_owner } }
  }

  handler_params = Shipit::Webhooks::Handlers::StatusHandler.new.send(:build_params, payload) # or via .call(payload)
  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)

  victim_commit.reload
  # EXPECTED (secure): victim_commit's status is unchanged because attacker-org never
  # authenticated against victim-org's webhook_secret.
  assert_not_equal "success", victim_commit.status.state,
    "commit belonging to a different, unauthenticated org's stack was mutated"
end
```
This test constructs a `status` payload where `repository.owner.login` is the attacker's own verified org while `sha` collides with a commit under `victim_stack` (a different org), and asserts the victim's `Commit#status` should remain unchanged — demonstrating that current `StatusHandler#process` code (`Commit.where(sha: params.sha)`) fails this assertion because it has no repository/org scoping.
