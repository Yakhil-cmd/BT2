The key code is in `handleParentChainInfoResponseMsg`. Let me trace the exact logic:

### Title
Malicious P2P Bridge Peer Can Reset Parent Operator Nonce to Zero, Permanently Halting Bridge Settlement — (`node/sc/sub_bridge_handler.go`)

---

### Summary

`handleParentChainInfoResponseMsg` unconditionally overwrites the parent operator nonce with the peer-supplied value even when that value is *lower* than the current nonce. When the `BridgeTxPool` is empty, a single crafted `ServiceChainParentChainInfoResponseMsg` with `Nonce=0` from any connected bridge peer resets the operator nonce to 0, causing every subsequent bridge transaction to be submitted with nonce 0 and rejected by the parent chain as "nonce too low," permanently halting bridge asset settlement.

---

### Finding Description

The nonce-sync logic in `handleParentChainInfoResponseMsg` has three branches gated on `GetMaxTxNonce`: [1](#0-0) 

```
poolNonce = GetMaxTxNonce(operatorAddr)   // returns 0 when pool is empty

if poolNonce > 0 {          // branch A – pool has txs
    ...
} else if getParentOperatorNonce() > pcInfo.Nonce {   // branch B
    logger.Error(...)
    setParentOperatorNonce(pcInfo.Nonce)   // ← unconditional downgrade
} else {                    // branch C
    setParentOperatorNonce(pcInfo.Nonce)
}
```

**Branch B** is reached when the pool is empty (`poolNonce == 0`) **and** the local nonce is already higher than the peer-supplied nonce. The code logs an error but still calls `setParentOperatorNonce(pcInfo.Nonce)`, blindly trusting the peer-supplied value. There is no lower-bound guard, no cross-check against the on-chain confirmed nonce, and no authentication of the responding peer beyond chain-ID matching.

`GetMaxTxNonce` returns `0` both when the pool is empty and when the highest queued nonce is literally 0: [2](#0-1) 

The P2P handshake only validates `NetworkId` and `ProtocolVersion`; the `ChainID` field is self-reported by the peer and never cryptographically verified: [3](#0-2) 

`RegisterNewPeer` rejects peers whose self-reported chain ID does not match, but any node that knows the public parent chain ID passes this check: [4](#0-3) 

After the nonce is corrupted, `setParentOperatorNonceSynced(true)` is called unconditionally: [5](#0-4) 

This means the bridge immediately begins generating and submitting transactions with nonce 0 without triggering a re-sync.

---

### Impact Explanation

Every bridge value-transfer and anchoring transaction generated after the attack uses nonce 0: [6](#0-5) 

The parent chain rejects all of them with "nonce too low" because the on-chain confirmed nonce is already N > 0. The `BridgeTxPool` accumulates failed transactions; no receipts are ever returned; bridge asset settlement is permanently halted for as long as the attacker continues sending crafted messages. Recovery requires operator intervention to manually resync the nonce, which is not automatic.

---

### Likelihood Explanation

- The sub-bridge P2P listener accepts any inbound connection that presents the correct (public) `NetworkId` and `ProtocolVersion`.
- The attacker only needs to know the parent chain ID (public) and send one RLP-encoded message.
- The pool-empty condition is a normal operational state (e.g., after all pending txs are confirmed).
- No privileged key, governance role, or validator collusion is required.

---

### Recommendation

In branch B, never allow the nonce to decrease. Replace the unconditional overwrite with a max-guard:

```go
} else if sbh.getParentOperatorNonce() > pcInfo.Nonce {
    // Do NOT downgrade; keep the higher local nonce.
    // Log the discrepancy for diagnostics only.
    logger.Error("received nonce lower than local nonce; keeping local nonce",
        "local", sbh.getParentOperatorNonce(), "received", pcInfo.Nonce)
    // setParentOperatorNonce intentionally omitted
}
```

Additionally, consider authenticating the responding peer (e.g., verifying the response comes from the same peer that received the request, or requiring a signed nonce response).

### Proof of Concept

1. Start a sub-bridge with operator nonce set to 10 (simulate N confirmed txs).
2. Drain the `BridgeTxPool` so `GetMaxTxNonce` returns 0.
3. Connect a malicious P2P node presenting the correct `NetworkId`/`ProtocolVersion`/`ChainID`.
4. Send a raw `ServiceChainParentChainInfoResponseMsg` with `parentChainInfo{Nonce: 0, GasPrice: 1}`.
5. Assert: `getParentOperatorNonce()` is now 0 (branch B executed).
6. Trigger `generateAndAddAnchoringTxIntoTxPool`; observe the generated tx has `Nonce=0`.
7. Submit to a parent-chain node; observe rejection with "nonce too low".

func (pool *BridgeTxPool) GetMaxTxNonce(from *common.Address) uint64 {
	pool.mu.RLock()
	defer pool.mu.RUnlock()

	maxNonce := uint64(0)
	if list, exist := pool.queue[*from]; exist {
		for _, t := range list.items {
			if maxNonce < t.Nonce() {
				maxNonce = t.Nonce()
			}
		}
	}
	return maxNonce
}

	}
	if int(status.ProtocolVersion) != p.version {
		return errResp(ErrProtocolVersionMismatch, "%d (!= %d)", status.ProtocolVersion, p.version)
	}
	return nil
}
