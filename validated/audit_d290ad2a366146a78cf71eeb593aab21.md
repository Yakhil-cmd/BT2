### Title
`pool_creator` set from an unvalidated, non-signing account in `initialize_with_permission` permanently freezes creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`InitializeWithPermission::creator` is declared as an `UncheckedAccount<'info>` with no address, ownership, or non-default constraint, and its key is written directly into `PoolState.pool_creator` during pool creation with `enable_creator_fee = true`. If the transaction's caller (or any front-runner/attacker with a valid `permission` PDA) supplies `Pubkey::default()` (the all-zero address, which is also the System Program's ID) as the `creator` account, the pool is initialized with `pool_creator == Pubkey::default()` and creator-fee accrual enabled, permanently freezing the resulting fee.

### Finding Description
In `InitializeWithPermission`, the `creator` account has no validation at all: [1](#0-0) 

Its raw key is then stored as `pool_creator` on `PoolState` when the pool is initialized, with `enable_creator_fee` forced to `true`: [2](#0-1) 

`PoolState::initialize` performs no zero-address check either: [3](#0-2) 

Once `pool_creator` is `Pubkey::default()`, the two instructions that are the only way to withdraw accrued creator fees both become permanently unusable for a legitimate party:

- `CollectCreatorFee` requires a `Signer` whose address equals `pool_state.pool_creator`: [4](#0-3) 
Since `Pubkey::default()` has no corresponding private key, no one can ever produce a valid signature for this account, so `collect_creator_fee` can never succeed for this pool.

- `CollectCreatorFeePermissionless` uses `pool_state.pool_creator` as the ATA authority for the fee-receiving accounts: [5](#0-4) 
Any tokens routed here end up in associated token accounts owned by the System Program address, which can never sign a transfer, so the funds are permanently locked.

Meanwhile, every swap on the pool continues to accrue and lock funds into `creator_fees_token_0`/`creator_fees_token_1`, as seen in the curve fee split logic used by `swap_base_input`/`swap_base_output`: [6](#0-5) 

This is directly analogous to the reported class of bug: an address field that gates privileged/critical logic (here, the right to withdraw creator fees) is populated without a non-zero check, and once it is zero, dependent functionality is permanently disabled.

### Impact Explanation
Creator fees accrued on every swap through this pool become permanently unrecoverable — a real, concrete freezing of funds that keeps growing with every trade as long as the pool is used, with no admin or emergency recovery path in `collect_creator_fee`/`collect_creator_fee_permissionless`. This meets the "permanent freezing of user funds" bar.

### Likelihood Explanation
The `creator` account has zero on-chain constraints (no `address`, `has_one`, or `require_keys_neq` check), so any caller who can obtain a valid `permission` PDA (via `create_permission_pda`) can trivially pass `Pubkey::default()` (or the System Program account, which trivially satisfies this key) as `creator` in a single transaction with attacker-chosen accounts and data. No special privilege beyond being a permitted pool creator is required, and the mistake could also happen accidentally through tooling that fails to fill in the field.

### Recommendation
Add an explicit non-default check on the `creator` account, mirroring the pattern already used elsewhere in the codebase for owner-type fields, e.g. in `update_config.rs`: [7](#0-6) 
Either add `constraint = creator.key() != Pubkey::default() @ ErrorCode::InvalidInput` to the `creator` account in `InitializeWithPermission`, or add the same `require_keys_neq!` check inside `PoolState::initialize` before writing `pool_creator`.

### Proof of Concept
1. Attacker/caller with a valid `permission` PDA calls `initialize_with_permission`, supplying `creator = Pubkey::default()` (the System Program address) as the `creator` account (it is an `UncheckedAccount`, so it can be any account, including one with no matching keypair).
2. `pool_state.initialize(...)` is called with `pool_creator = ctx.accounts.creator.key() == Pubkey::default()` and `enable_creator_fee = true`. [2](#0-1) 
3. Users swap against the pool; `creator_fee` accrues into `pool_state.creator_fees_token_0/1` per the fee-split logic in `curve/calculator.rs`.
4. Any attempt to call `collect_creator_fee` fails because no signer can ever match `pool_state.pool_creator == Pubkey::default()`. [4](#0-3) 
5. Calling `collect_creator_fee_permissionless` succeeds in creating ATAs owned by the System Program address and transferring the accrued fees there, but those tokens can never be moved again since the System Program address cannot sign token transfers — the funds are permanently frozen. [5](#0-4)
