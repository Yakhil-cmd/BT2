### Title
Assets with `auto_destroy: true` are irrevocably burned by unit validation the instant they are sent to their AA (definer), completely bypassing the AA's own pause/rejection (bounce) logic — ([File: validation.js])

### Summary
An asset can be defined with `auto_destroy: true`, in which case any output sent to the asset's `definer_address` is treated as permanently destroyed/burned by the base-layer unit-validation rules, independent of any application-level (AA) logic that is supposed to gate the operation. When an autonomous agent (AA) is the definer of such a "share"/"LP-token"-like asset (a very common Obyte AA pattern for pools, market makers, and fundraising proxies), a user can send the shares straight to the AA. Destruction of that output is enforced unconditionally at the DAG/consensus level as soon as the triggering unit becomes stable — this happens *before and independent of* whatever the AA's own oscript logic decides to do with the trigger (accept, pay out, or bounce/pause). If the AA implements a "pause" style guard (e.g. a `var['paused']` check that bounces redemption requests), the shares sent by the user are still destroyed by consensus rules even though the AA bounced and refused to process the redemption, resulting in an unrecoverable loss of the user's tokens.

This mirrors the reported Arrakis issue's core defect: a "burn" pathway (here, the protocol-level `auto_destroy` semantic) that operates completely outside of, and is unreachable by, the higher-level pause/restriction mechanism (here, the AA's own bounce/if-condition logic), so the pause can be silently defeated — except in ocore the effect is worse, since it is the *victim*'s own funds that vanish with no possibility of AA-side recovery.

### Finding Description
The `auto_destroy` semantics are enforced purely in the general unit-validation code path, not in the AA response/bounce machinery:

- Asset definitions accept a boolean `auto_destroy` field, validated generically for both ordinary and AA-defined assets. [1](#0-0) [2](#0-1) 

- When validating a payment that spends (or, in the input-side check, references) an output belonging to an `auto_destroy` asset whose owner is the asset's `definer_address`, the network permanently disallows any further spend of that value — this is the "burn" mechanic, and it is a pure consensus rule with no AA hook: [3](#0-2) [4](#0-3) 

- The AA composer itself acknowledges and relies on this consensus-level effect: when the AA is the `definer` of an `auto_destroy` asset, the composer explicitly excludes those outputs from ever being considered "spendable" by the AA again, confirming the destruction is unconditional and outside the AA's control: [5](#0-4) 

Critically, the trigger unit carrying the payment to the AA becomes stable and final through ordinary DAG consensus, regardless of how (or whether) the AA subsequently processes/bounces the trigger. The AA's `if`/`bounce()` guards (the natural place to implement a "pause" or emergency stop, analogous to the router's `pause()` in the reported issue) run only in `aa_composer.js`'s `handleTrigger`, strictly after the triggering payment (and its `auto_destroy` burn) is already consensus-final: [6](#0-5) 

This is precisely the same class of bug as the reported Arrakis issue: a "burn" style operation (there, `ArrakisV2.burn()`; here, the `auto_destroy` consensus rule) is reachable through a path that is completely independent of, and therefore cannot be gated by, the higher-level pause/authorization mechanism (there, `ArrakisV2Router.pause()`; here, the AA's own `if`/`bounce` guard logic).

Notably, the ocore reference AA templates shipped in the test suite implement exactly this share/LP-token pattern (mint on deposit, redeem by sending shares back to the AA) and deliberately set `auto_destroy: false` for these share assets, e.g. the Uniswap-like market maker and fundraising proxy templates: [7](#0-6) [8](#0-7) 

This shows the risk is real and already implicitly known/avoided in the reference examples, but nothing in the AA validation layer prevents an AA author from choosing `auto_destroy: true` for a similar share/LP-token asset, in which case the vulnerability becomes exploitable.

### Impact Explanation
If an AA author defines a share/LP-token-style asset with `auto_destroy: true` and implements any pause/guard condition intended to block redemption (a natural and expected safety mechanism, analogous to the router's `pause()`), that guard can be silently defeated: a user's redemption payment still burns their shares through the base-layer consensus rule the instant the unit stabilizes, before the AA's bounce logic even executes. The AA cannot compensate the user for the destroyed shares because the destruction is not reflected in any state the AA controls — it is a property of the DAG itself. This causes concrete, irreversible fund loss for the token holder and defeats the intended protective purpose of the pause mechanism, matching the "AA fund loss or freezing" impact category.

### Likelihood Explanation
The pattern of AA-defined share/LP tokens combined with a pause/guard condition is a standard, expected design pattern for pools, vaults, and market-maker AAs on Obyte (as shown by the shipped reference templates). Any AA author who chooses `auto_destroy: true` for such an asset (a legitimate, validator-accepted configuration) instead of `false` (as the reference templates use) would be immediately exposed, and any unprivileged user could trigger the loss simply by sending a normal payment to the AA — no special privileges, race conditions, or network assumptions are required.

### Recommendation
- Warn against or disallow `auto_destroy: true` for assets defined by an AA definer in `aa_validation.js`'s asset-message validation, since the semantics make the burn unconditional and unreachable by the AA's own logic.
- Alternatively, change the consensus semantics so that an `auto_destroy` output sent to an AA definer is only considered destroyed after the AA's response for that trigger has been computed (i.e., tie the burn to the AA's acceptance rather than to unconditional unit stabilization), allowing the AA to bounce and effectively "un-burn" (refuse) the operation.
- At minimum, document this behavior prominently so AA authors relying on a pause/guard pattern for share redemption are aware that `auto_destroy: true` bypasses any such guard.

### Proof of Concept
1. Deploy an AA that defines a share asset with `auto_destroy: true`, `issued_by_definer_only: true`, and a redemption branch guarded by `if: "{!var['paused']}"` (bounces when paused), mirroring the Uniswap-like market maker template at [9](#0-8)  but with `auto_destroy: true` instead of `false`.
2. Set `var['paused'] = 1` (e.g., via an admin trigger) to simulate an emergency stop.
3. A user sends a payment message with an output carrying their shares to the AA address, attempting to redeem.
4. The triggering unit stabilizes normally through DAG consensus; per `validation.js:2504` / `2430`, that output (owned by the AA/definer of an `auto_destroy` asset) is permanently unspendable — i.e., burned — regardless of the AA's processing outcome.
5. The AA's trigger handler runs afterward, sees `var['paused']` is set, and bounces the trigger, refunding only bytes (no share-equivalent value), per the guard logic executed in `aa_composer.js` (`handleTrigger`/`bounce` path, lines 1841-1863).
6. Net result: the user's shares are gone (burned by consensus rule) with no compensation, even though the AA "paused" and refused to process the redemption — demonstrating the pause was bypassed by the auto-destroy burn path.
