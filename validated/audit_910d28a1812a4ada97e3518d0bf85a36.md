### Title
Webhook signature verification binds to `repository.owner.login`/`organization.login` while all state-changing handlers act on `repository.full_name` — cross-organization webhook forgery in multi-tenant Shipit - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the incoming signature against using `repository_owner`, derived from `repository.owner.login` or `organization.login` in the JSON body. Every webhook handler that actually mutates state, however, resolves the target `Stack`/`Repository` using a *different* field of the same payload: `repository.full_name` (`Handler#repository_name`). In a multi-tenant Shipit install (explicitly supported and documented) these two fields are never cross-checked against each other, so a party who legitimately possesses the `webhook_secret` for one configured organization can forge a payload whose `full_name` names a repository belonging to a different organization and have it accepted and processed.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) [2](#0-1) 

`verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies the HMAC over the raw body against that organization's configured `webhook_secret`. `repository_owner` is read from `params.dig('repository','owner','login')` (fallback `organization.login`).

Every handler that then does actual work resolves the affected repository via a **different** JSON field: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

e.g. `PushHandler#process`: [4](#0-3) 

Shipit explicitly supports multiple, independently-secreted GitHub Apps in a single install (one per organization), each with its own `webhook_secret`: [5](#0-4) [6](#0-5) 

**Binding that should hold, expressed as an equality:**
`organization whose secret authenticated the request` == `organization that owns the repository the handler will act on`

**What actually holds:** `verify_signature` authenticates against `payload['repository']['owner']['login']` (or `payload['organization']['login']`), while `Handler#repository_name` (and thus `Repository.from_github_repo_name`, and thus which `Stack` gets acted on) is driven by the independent, attacker-controlled field `payload['repository']['full_name']`. Because the whole HTTP body is attacker-supplied and the signature is a raw HMAC over that entire body, an attacker who holds the `webhook_secret` for **OrgOne only** can construct:

```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```

`verify_signature` resolves `Shipit.github(organization: "OrgOne")` and succeeds (the attacker legitimately knows OrgOne's secret), but `PushHandler` (and every other handler, since `repository_name`/`stacks` is shared logic in the base `Handler`) will look up and act on stacks belonging to `OrgTwo/victim-repo` — an organization/tenant the attacker has no relationship to and for which they hold no secret, token, or repository access.

This is exactly the reported bug class: a guard checks one value (`amount` / `repository.owner.login`) while the state actually mutated depends on a related-but-different value that isn't included in the check (`balanceOf(msg.sender)+amount` / `repository.full_name`).

### Impact Explanation
Once the forged webhook is accepted, `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching `OrgTwo/victim-repo` and the pushed branch, enqueuing `GithubSyncJob` against a stack outside the attacker's own tenant/organization. This is a cross-tenant, cross-repository write path reachable purely from having a webhook secret scoped to a *different* organization — the exact "cross-repository writes" / "unauthorized deploy" impact category, since `sync_github` feeds directly into commit ingestion and (depending on the target stack's `continuous_deployment` configuration) deploy triggering, without the attacker ever needing a Shipit `ApiClient` token, GitHub App private key, or write access to the victim organization's repository.

### Likelihood Explanation
This requires the deployer to run Shipit in the documented multi-organization configuration (one Shipit instance serving several GitHub organizations/tenants, each with its own `webhook_secret`), which is an explicitly supported, documented deployment mode (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`). Any tenant/organization admin who is handed their own `webhook_secret` for their own app installation — an "unprivileged" party with respect to *other* tenants on the same Shipit instance — can exploit this without any additional privilege escalation.

### Recommendation
In `verify_signature`, after signature verification succeeds, assert that the organization used to select the signing secret (`repository_owner`) actually matches the owner portion of `repository.full_name` (and/or `organization.login`) before dispatching to handlers; alternatively, have every `Handler` re-derive the acting organization exclusively from the already-authenticated `repository_owner` rather than trusting `repository.full_name` independently, mirroring the fix pattern of including the already-verified state (locked balance / authenticated org) in the check that gates the action.

### Proof of Concept
1. Deploy Shipit configured for two tenants as in `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`), each with its own `webhook_secret`, and a Stack tracking `OrgTwo/victim-repo`.
2. As the legitimate owner/operator of `OrgOne`'s GitHub App (who only knows OrgOne's `webhook_secret`), build the payload:
```json
{"ref":"refs/heads/main","after":"<sha>","repository":{"owner":{"login":"OrgOne"},"full_name":"OrgTwo/victim-repo"}}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgOne_webhook_secret, raw_body)>` and `X-Github-Event: push`, then `POST /webhooks`.
4. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves `Shipit.github(organization: "OrgOne")` and the signature verifies successfully.
5. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) resolves stacks via `repository_name` = `"OrgTwo/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for the `OrgTwo` stack with the attacker-supplied `expected_head_sha`, despite the attacker never having authenticated as, or held any credential for, `OrgTwo`.

Note: I was unable to fully inspect `status_handler.rb` and `lib/shipit.rb`'s `github`/`github_organizations` lookup helpers before the tool budget ran out, so I cannot confirm whether the `status`/`check_suite` event handlers could be similarly abused to forge CI status and trigger an unauthorized merge/deploy in the merge queue for a foreign stack — this would strengthen the impact further but is not verified here.
