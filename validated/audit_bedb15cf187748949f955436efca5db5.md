### Title
Malicious `_to` Recipient Can Permanently Brick Bridge KLAY Handle Nonce via Reverting Fallback — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` pushes KLAY to a user-controlled `_to` address via a low-level call and then hard-`require`s success. Because `_to` is chosen by the original requester on the source chain, a malicious user can deploy a contract whose fallback always reverts, causing every operator attempt to handle that nonce to revert. All state written before the call (nonce bookkeeping) is rolled back, so `lowerHandleNonce` is permanently stuck and the VT-recovery daemon retries the same nonce forever, wasting operator gas and locking the source-chain KLAY with no refund path.

---

### Finding Description

`handleKLAYTransfer` executes the following sequence:

```
_setHandledRequestTxHash(_requestTxHash);          // state write
handleNoncesToBlockNums[_requestedNonce] = ...;    // state write
_updateHandleNonce(_requestedNonce);               // state write

(bool ok, ) = _to.call.value(_value)("");          // external call to user-controlled address
require(ok, "handleKLAYTransfer: transfer failed");// reverts entire tx on failure
``` [1](#0-0) 

If `_to` is a contract whose `fallback` reverts (or consumes all forwarded gas), the `require` on line 99 reverts the entire transaction. Because Solidity reverts roll back all state changes in the same call frame, the three state writes above are also undone. In particular, `handleNoncesToBlockNums[_requestedNonce]` is never set.

`_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive `i` starting from `lowerHandleNonce`:

```go
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) { ... }
lowerHandleNonce = i;
``` [2](#0-1) 

Because the stuck nonce's entry is never written, `lowerHandleNonce` never advances past it. The VT-recovery daemon (`vt_recovery.go`) uses `lowerHandleNonce` as its `handleNonce` hint and continuously re-queues the same pending event: [3](#0-2) [4](#0-3) 

The `_to` address is fully user-controlled: the requester on the source chain passes it to `requestKLAYTransfer`, which emits it in the `RequestValueTransfer` event, and the bridge operator faithfully forwards it to `handleKLAYTransfer` on the destination chain. [5](#0-4) 

---

### Impact Explanation

- **KAIA locked permanently**: The source-chain bridge holds the user's KLAY with no refund or cancellation mechanism. The destination-chain bridge also holds its KLAY reserve but can never deliver it for this nonce.
- **Bridge nonce permanently stuck**: `lowerHandleNonce` is frozen at the attacker's nonce. `recoveryBlockNumber` never advances past the corresponding block, so the recovery system scans the same block range on every interval.
- **Operator gas drain**: Every recovery cycle re-submits the doomed `handleKLAYTransfer` transaction, which reverts and burns operator gas indefinitely.
- **Scope**: Affects the Kaia service-chain bridge's KLAY transfer path — a direct unauthorized lock of bridged KAIA assets and corruption of bridge nonce state.

---

### Likelihood Explanation

- Any user with a small amount of KLAY can trigger this: deploy a reverting contract on the destination chain, then call `requestKLAYTransfer` on the source chain with that address as `_to`.
- No special role, operator access, or majority-validator collusion is required.
- The attack is cheap (one source-chain tx + one contract deployment) and permanent.

---

### Recommendation

Replace the push-transfer pattern with a pull-payment (escrow) pattern, analogous to the fix recommended in H-3:

```diff
- (bool ok, ) = _to.call.value(_value)("");
- require(ok, "handleKLAYTransfer: transfer failed");
+ (bool ok, ) = _to.call.value(_value)("");
+ if (!ok) {
+     // Store for later withdrawal; do NOT revert so the nonce is committed
+     withdrawableKLAY[_to] = withdrawableKLAY[_to].add(_value);
+ }
```

The nonce state (`_setHandledRequestTxHash`, `handleNoncesToBlockNums`, `_updateHandleNonce`) must be committed regardless of whether the push succeeds. The recipient can then call a separate `withdrawKLAY()` function to claim their funds.

---

### Proof of Concept

1. **Deploy a griefing contract** on the destination chain:
   ```solidity
   contract GriefRecipient {
       fallback() external payable { revert("blocked"); }
   }
   ```

2. **Request a KLAY bridge transfer** on the source chain, setting `_to = address(GriefRecipient)`:
   ```solidity
   bridge.requestKLAYTransfer{value: 1 ether}(address(griefRecipient), 1 ether, "");
   // emits RequestValueTransfer with requestNonce = N
   ```

3. **Bridge operators call `handleKLAYTransfer`** on the destination chain for nonce `N`. The call to `griefRecipient.call.value(1 ether)("")` triggers the reverting fallback. `require(ok, ...)` reverts the entire transaction. `handleNoncesToBlockNums[N]` is never written.

4. **Observe `lowerHandleNonce` is stuck at `N`**: subsequent nonces `N+1`, `N+2`, … can be processed but `lowerHandleNonce` never advances past `N` because the loop in `_updateHandleNonce` stops at the first gap. [6](#0-5) 

5. **VT-recovery daemon** (`vtr.Recover()`) detects `requestNonce > handleNonce`, re-queues nonce `N`, and operators re-submit — all reverts, indefinitely. [7](#0-6)
