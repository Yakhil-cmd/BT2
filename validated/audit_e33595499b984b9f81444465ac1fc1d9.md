This confirms the vulnerability. `Handler#stacks` (used by `PushHandler`, `CheckSuiteHandler`, etc.) scopes lookups via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, meaning the payload's `full_name` is the authorization boundary for those handlers. [1](#0-0)  `StatusHandler`, by contrast, never calls `stacks` or reads `full_name` at all — it queries `Commit.where(sha: params.sha)` globally across the entire `commits` table, with no scoping to any repository or stack. [2](#0-1) 

### Title
Cross-tenant commit-status forgery via unscoped `sha` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates the request against the GitHub App/org identified by `payload.dig('repository','owner','login')` [3](#0-2) , but `StatusHandler#process` never checks that `full_name`/owner against the `Commit` rows it mutates — it matches purely on `sha` across all stacks. [2](#0-1)  Any attacker who legitimately controls a Shipit-configured GitHub App/webhook secret for their own repository can therefore forge `status` events that mutate commit statuses belonging to any other tenant's stack, as long as the `sha` happens to collide with a commit tracked in another stack.

### Finding Description
The broken binding is: `Shipit.github(organization: repository_owner)` (used to verify the HMAC signature) should equal the organization/repository that owns the `Commit` rows being mutated, i.e. `verified_owner == commit.stack.repository.owner`. In `WebhooksController`, `repository_owner` is read from the untrusted payload itself (`params.dig('repository','owner','login')`) purely to select which app's `webhook_secret` to verify against [4](#0-3) . Once the signature check passes, `WebhooksController#create` dispatches the parsed JSON straight to `StatusHandler.call(params)` [5](#0-4) .

`StatusHandler` only requires `sha`, `state`, and optional fields in its `params` schema — it does not require or read `repository`/`full_name` at all [6](#0-5) , and its `process` method runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` unscoped by stack or repository [2](#0-1) . This is inconsistent with the base `Handler` class's own `stacks` helper, which other handlers (e.g. `PushHandler`) use to scope operations to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [1](#0-0)  — `StatusHandler` simply never applies this scoping.

Exploit flow: attacker registers/controls a GitHub App or org config for their own repository (`repository_owner = attacker-org`), obtaining a legitimate `webhook_secret` for that org. They send a `status` payload HMAC-signed with that secret, with `repository.owner.login` = their own org (so `verify_signature` passes), but with `sha` set to a value matching a `Commit` row that actually belongs to a different tenant's `Stack`. `Commit.where(sha: ...)` finds that commit regardless of which stack/org it belongs to, and `create_status_from_github!` mutates it — including potentially triggering deploy-relevant transitions (`deployable_status`, `ProcessMergeRequestsJob`, continuous-deployment triggers) as shown in `commits_test.rb`.

Existing guards do not close this gap: `verify_signature` only authenticates *who signed the request*, not *which commits the payload is allowed to affect*; `drop_unhandled_event`/`check_if_ping` are unrelated; the `ExplicitParameters` schema for `StatusHandler` doesn't require or validate `repository`; and there is no model-level uniqueness constraint tying `sha` to a specific owner/organization visible in `Commit`.

### Impact Explanation
An attacker who legitimately owns a Shipit-registered repository/app can mutate `Commit`/`Status` records belonging to unrelated stacks by supplying a matching `sha`, purely because `StatusHandler` performs a global, unscoped `Commit.where(sha:)` lookup. This can flip a commit's state (e.g. to `success`), which per `commits_test.rb` can trigger `deployable_status` hooks and `ProcessMergeRequestsJob`/continuous-deployment scheduling for a stack the attacker does not own [7](#0-6) . This is a cross-tenant "payload for one repository mutating another's stack/commit" scenario, matching the Critical impact category defined in the rules. The blast radius depends on `sha` collision — while a truly random SHA1 collision is infeasible to engineer directly, this is realistically triggerable whenever the same commit (or content) is legitimately shared across multiple Shipit-tracked stacks/forks (a common Shipit pattern, e.g. mirrored/forked repos, monorepo forks, or shared upstream commits merged into multiple downstream repos) — the attacker only needs knowledge of a target `sha`, which is often public.

### Likelihood Explanation
Preconditions: the attacker needs their own legitimately-configured GitHub App/webhook and its `webhook_secret` (readily available to anyone who can set up a Shipit-tracked repo or webhook for a repo they control) and knowledge of a target commit's `sha` in another Shipit stack (often public/discoverable). No privileged Shipit role, session, or victim's secret is required. The attack is fully repeatable and can be aimed at any other stack whose commit shas the attacker can learn.

### Recommendation
Scope `StatusHandler#process` to the repository/stack identified by the payload, mirroring the base `Handler#stacks` pattern: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(...)`/`stacks`, and constrain the `Commit` lookup to `stacks.commits.where(sha: params.sha)` instead of a global `Commit.where(sha:)`. Additionally, verify that the payload's `repository.owner.login` matches the organization whose `webhook_secret` verified the signature, to prevent an app for org A from asserting facts about org B's repos even when `full_name` is present but forged.
