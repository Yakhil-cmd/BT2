### Title
Webhook signature verified against organization derived from an attacker-controlled field that is decoupled from the repository the event actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub organization's webhook secret to check the HMAC signature against by reading `repository.owner.login` out of the still-unverified request body. Once the signature check passes (because it matched *that* organization's own secret), the actual event-processing code picks the `Repository`/`Stack` to mutate using a completely different, unconstrained field: `repository.full_name`. Nothing in the request ties `repository.owner.login` (the field used to select the verifying secret) to `repository.full_name` (the field used to select the target repository). This reproduces the report's core bug class: a value used for an authorization/verification decision (`operator` in the original report; `repository.owner.login` here) is decoupled from the value that state-changing logic actually operates on (`owner`'s shares in the report; `repository.full_name` here).

The equality that should hold but does not:
`organization whose secret authenticated the request (repository.owner.login)` == `organization/repository whose Stack state is mutated (repository.full_name)`

Before an attacker's forged request: only genuine GitHub deliveries for organization X (signed with X's registered secret) can act on stacks belonging to repositories under X.
After the attacker's forged request: anyone who knows (or controls, e.g., as an admin of their own onboarded organization/repo, since Shipit's `webhook_secret` is configured per-organization and known to whoever set up that org's webhook) the webhook secret of *any one* organization tracked by this Shipit instance can craft a payload with `repository.owner.login` set to their own organization (to pass signature verification) while setting `repository.full_name` to any other tracked repository's full name. The forged event is then dispatched to handlers that mutate state for the victim repository's `Stack` (e.g., enqueue `GithubSyncJob`, create commit `Status` rows, enqueue `RefreshCheckRunsJob`, create `Team`/`User` records via the membership handler) — none of which the attacker has any GitHub-side permission over.

### Impact Explanation
This is a cross-repository write: an actor who legitimately controls one onboarded organization's webhook secret can inject fabricated GitHub events (pushes, commit statuses, check-suite completions, membership changes) that are applied to a *different* organization/repository's `Stack` records inside Shipit, without ever having write access to that other repository on GitHub. Because commit statuses and check-suite refreshes are inputs that Shipit's deploy-gating logic consults, this lets an attacker corrupt or manipulate the state Shipit uses to decide whether a victim stack's revisions are deployable, which is a cross-tenant integrity break in a multi-organization Shipit deployment.

### Likelihood Explanation
Any actor with legitimate administrative control of one organization/repository tracked in a shared Shipit instance (and therefore knowledge of that organization's webhook secret, which they configured on GitHub's side themselves) can exploit this with a single crafted HTTP POST to `/github/webhooks`, with no additional privilege, session, or token needed for the victim organization.

### Recommendation
Bind the two fields together before dispatching to handlers: after `verify_signature` succeeds for organization X, reject (or re-scope) any event whose `repository.full_name`'s owner does not equal X (`repository_owner`). Concretely, validate in `WebhooksController#create` (or in `Handlers::Handler#initialize`) that `payload.dig('repository', 'full_name')` begins with `"#{repository_owner}/"` before invoking handlers, rejecting mismatched payloads with `422`.

### Proof of Concept
1. Attacker administers `attacker-org/some-repo`, which is tracked by the shared Shipit instance, and knows `attacker-org`'s configured webhook secret (they set it up on GitHub themselves).
2. Attacker computes a valid `X-Hub-Signature` HMAC over a crafted JSON body using `attacker-org`'s secret, where the body sets:
   - `repository.owner.login = "attacker-org"` (so `WebhooksController#verify_signature` looks up and validates against `attacker-org`'s secret) — [2](#0-1) 
   - `repository.full_name = "victim-org/victim-repo"` (the repo whose `Stack` will actually be acted on) — [6](#0-5) 
   - `ref = "refs/heads/main"`, `after = "<arbitrary sha>"` for a `push` event.
3. `X-Github-Event: push` header is set; the POST is sent to the webhooks endpoint.
4. `verify_signature` passes because the signature matches `attacker-org`'s own secret.
5. `PushHandler#process` looks up stacks for `victim-org/victim-repo` via `Repository.from_github_repo_name(repository_name)` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — [5](#0-4) , even though the attacker has no GitHub permissions on `victim-org/victim-repo`.
