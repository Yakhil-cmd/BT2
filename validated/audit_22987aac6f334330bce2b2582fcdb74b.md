### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets a status webhook from any authenticated repository mutate commit state on unrelated stacks sharing the same SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA with `Commit.where(sha: params.sha).each`, with no scoping to the repository that authenticated the webhook via `verify_signature`. Because `Commit#deployable?` treats `stack.ignore_ci?` as an unconditional bypass of CI success (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`), any commit whose SHA coincides with a commit on a victim stack (e.g. a shared ancestor commit from a shared git history/fork) can have its status/CI state manipulated by a webhook that only ever proved authorization for a *different* repository.

### Finding Description
The broken binding the question implies is: `status.context == 'ci/coverage'` for `sha` should only ever affect `Commit` records belonging to `stack.repository == repository_that_authenticated_the_webhook`. In `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24), the query `Commit.where(sha: params.sha)` is not filtered by repository at all — it matches every `Commit` row across every `Stack` in the installation that happens to share that SHA, then calls `commit.create_status_from_github!(params)` on each.

`WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, i.e. it only proves that the payload was legitimately signed for the *organization/repository that sent it* — it says nothing about which `Commit` rows in the database should be affected. The authorization boundary the signature enforces is "this payload came from GitHub for org X", but the handler's data-access boundary is "any row with this SHA, anywhere," which is a strictly broader set. There is no `repository_id`/`stack_id` filter, no `github_repo_name` check, nothing in `ExplicitParameters` schema (`requires :sha`, `requires :state`, `accepts :context`) that constrains scope either.

Because git commit SHAs are content-addressed, two different `Stack`s (backed by different GitHub repositories, potentially owned by different organizations/users) can contain `Commit` rows with an identical SHA whenever they share history — for example a fork of a victim's repository, a common upstream commit merged into both, or a shared library commit. An attacker who owns such a fork (or any repo containing a commit that is also present, byte-identical, in the victim stack) can cause GitHub to send a genuinely signed `status` webhook for that SHA from their own repository (their own CI reporting `context: ci/coverage`, `state: success` or `state: failure`). `verify_signature` passes because the signature is valid for the attacker's own organization. `StatusHandler#process` then updates the status of **every** `Commit` row with that SHA, including the one belonging to the victim's stack.

If the victim stack has `ignore_ci: true`, `Commit#deployable?` (app/models/shipit/commit.rb:227-229) short-circuits to `!locked? && true`, meaning CI status is irrelevant to deployability — but the status write itself still triggers `add_status` side effects: `Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and critically `stack.schedule_merges` (app/models/shipit/commit.rb:379-384) when the new status is `pending?` or `success?`. This can trigger merge-queue processing / continuous delivery scheduling (`schedule_continuous_delivery`, app/models/shipit/commit.rb:281-287) on the victim stack from a payload that was never authenticated for that stack's repository — the injected status is exactly what flips the pending/success transition that fires `schedule_merges` and continuous deployment eligibility checks.

None of the existing guards prevent this: `verify_signature` authenticates the sender's own repo, not the target rows; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema only validates payload shape, not scope; there is no `Stack`/`Repository` correlation check anywhere in `StatusHandler`.

### Impact Explanation
A `status` webhook, signed and legitimate for the attacker's own repository, causes `Commit#create_status_from_github!` to execute against `Commit` rows on stacks the attacker does not control, as long as a SHA collision exists across repos (which is a routine, attacker-inducible occurrence via forking/shared history). This is a payload for one repository mutating another repository's commit/stack state, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." On stacks with `ignore_ci: true`, this can directly trigger `schedule_merges`/continuous deployment scheduling for a commit the attacker does not own, moving the victim stack toward an unauthorized deploy. The blast radius is any stack across any tenant sharing an installation whose repo history overlaps with an attacker-controlled repo.

### Likelihood Explanation
Preconditions: attacker needs a repository (which they can freely create/fork) that (a) has the app installed so GitHub will sign webhooks for it, and (b) contains at least one commit with a SHA identical to a commit already present in the victim's `Stack#commits`. Forking a public repo guarantees SHA-identical history for all pre-fork commits, so this is close to universally satisfiable for public/forkable target stacks, and the attacker's cost is a normal GitHub commit-status API call or CI run on their own fork — no secrets, no privileged role, no session required. It is trivially repeatable against any number of stacks that share history with attacker-controlled forks.

### Recommendation
Scope the `StatusHandler` (and equivalently `check_run` handlers, if similarly unscoped) query by the repository that authenticated the webhook: join/filter `Commit` through `Stack` on `stack.repository_id`/`github_repo_name` matching `params.dig('repository', 'full_name')` (or organization/owner+name) before calling `create_status_from_github!`, so a status can only update commits belonging to stacks whose repository matches the webhook's authenticated repository.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` conceptually):
1. Create two stacks, `victim_stack` (repository `victim/repo`, `ignore_ci: true`, required status `ci/coverage`) and `attacker_stack` (repository `attacker/fork`).
2. Create two `Commit` rows with the identical `sha: 'deadbeef' * 5` — one on `victim_stack`, one on `attacker_stack` — simulating shared git history.
3. Build a `status` webhook payload: `{ sha: <shared_sha>, context: 'ci/coverage', state: 'success', repository: { full_name: 'attacker/fork', owner: { login: 'attacker' } } }`.
4. Assert binding before: `victim_commit.statuses.count == 0` and `victim_commit.status.state != 'success'`.
5. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new(...).call(payload)` (bypassing controller-level signature check, which is orthogonal — it only authenticates `attacker/fork`).
6. Assert binding after: `victim_commit.reload.statuses.count == 1` and `victim_commit.status.state == 'success'`, proving a payload authenticated only for `attacker/fork` mutated a `Commit` belonging to `victim/repo`'s stack — violating the invariant "A status for `ci/coverage` only affects the repository that authenticated it."

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
