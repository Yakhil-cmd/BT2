### Title
`OpenedHandler#provision?` operator precedence bypasses `review_stacks_enabled`, allowing unauthorized ReviewStack creation - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` uses `&&`/`||` in a way where `repository.review_stacks_enabled` only gates the `provisioning_behavior_allow_all?` clause, not the `allow_with_label?` or `prevent_with_label?` clauses. Any unprivileged GitHub user who opens a pull request against a repository with `review_stacks_enabled=false` and `provisioning_behavior='prevent_with_label'` (while omitting the label) triggers `ReviewStackAdapter#create!`, writing a `Shipit::ReviewStack` and enqueueing provisioning work for a repository that never opted into review stacks.

### Finding Description
The broken binding: the code intends `repository.review_stacks_enabled == true` to gate all provisioning paths, but due to Ruby operator precedence (`&&` binds tighter than `||`) the actual evaluated expression is:

```ruby
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
``` [1](#0-0) 

`review_stacks_enabled` is textually written before `&&`, but it only actually short-circuits the `allow_all?` disjunct; the second and third disjuncts (`allow_with_label?` / `prevent_with_label?`) are entirely independent of `review_stacks_enabled`. This is confirmed by contrast with `LabeledHandler`, which correctly gates all behavior with a standalone `repository.review_stacks_enabled` check in `respond_to_label_change?` before ever evaluating `archive?`/`unarchive?`: [2](#0-1) 

Call path: `process` → `respond_to_pull_request_opened?` → `provision?` → `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` → `create!`, which persists a `Shipit::ReviewStack` row via `scope.create!(stack_attributes)` and immediately enqueues `Shipit::ReviewStackProvisioningQueue.add(stack)`: [3](#0-2) [4](#0-3) 

Attacker request: open a pull request (`action: "opened"`) on a repository configured with `review_stacks_enabled=false` and `provisioning_behavior='prevent_with_label'`, with an empty `labels` array. `provisioning_behavior_prevent_with_label?` is true and `pull_request_has_provisioning_label?` is false (no labels present), so the third disjunct evaluates true regardless of `review_stacks_enabled`, and `provision?` returns true.

No existing guard intercepts this: the `params` schema (`ExplicitParameters`) only validates payload shape, not authorization; there is no separate `review_stacks_enabled` check in `respond_to_pull_request_opened?` unlike `LabeledHandler`; and webhook signature verification (out of scope here) only authenticates that GitHub sent the payload — it does not enforce the repository's opt-in configuration. This is a genuine logic defect in the engine's own authorization gating, not a webhook forgery issue: the attacker only needs to control the content of their own pull request (no label, or presence of label depending on the misconfigured mode), which is already an action available to any unprivileged user who can open PRs.

### Impact Explanation
For any repository with `review_stacks_enabled=false` and `provisioning_behavior` set to `prevent_with_label` (or `allow_with_label`), an unprivileged pull-request author causes the engine to create a `Shipit::ReviewStack` and enqueue it for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)`, despite the repository administrator never having enabled review stacks. This is an unauthorized deploy/provisioning action taken against a repository that opted out, matching the "unauthorized deploy" Critical impact category. The bug is repeatable against any repository in this specific configuration (`review_stacks_enabled=false` + `prevent_with_label`/`allow_with_label`) and requires no special per-repository knowledge beyond opening a PR with/without a label.

### Likelihood Explanation
Requires the target repository to be configured with `review_stacks_enabled=false` and `provisioning_behavior` set to `prevent_with_label` (or `allow_with_label`) — `provisioning_behavior` defaults are defined via the `PROVISIONING_BEHAVIORS` enum and depend on operator setup [5](#0-4) ; the question's precondition already fixes this configuration. Given that configuration, exploitation cost is zero beyond opening a normal pull request (with or without a label, matching the mode) — an action any GitHub user with push access to a fork can perform without needing any Shipit credentials.

### Recommendation
Fix operator precedence in `provision?` by explicitly parenthesizing the `review_stacks_enabled` gate around the entire expression, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In a minitest for `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler`:
1. Create/stub a `Shipit::Repository` with `review_stacks_enabled: false`, `provisioning_behavior: 'prevent_with_label'`.
2. Build `payload_parsed(:pull_request_opened)` with `pull_request.labels = []` (no provisioning label) and `repository.full_name` matching the above repository.
3. POST the payload through the webhook handler (`process`).
4. Assert `Shipit::ReviewStack.count` (or `Shipit::Stack.count` depending on fixture setup) does **not** change, i.e. `assert_no_difference('Shipit::ReviewStack.count') { ... }`.
5. Currently this assertion fails because `provision?` returns `true` due to the precedence bug — demonstrating that `repository.review_stacks_enabled == false` is not honored by the third disjunct of `provision?`, and a stack is created/enqueued despite the binding stating it should not be.
