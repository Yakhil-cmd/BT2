### Title
Webhook signature is verified against the organization in `repository.owner.login`, but downstream handlers act on the unrelated `repository.full_name` and `organization.login` fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to verify the HMAC signature with based on `repository_owner`, a value read out of the JSON body itself. Once the signature check passes, the entire raw payload is handed to `Shipit::Webhooks.for_event(event)` handlers, which independently derive the actual repository/organization to write to from other fields of the same attacker-controlled JSON (`repository.full_name`, `organization.login`). These two lookups are never cross-checked, so a payload that is legitimately signed for organization A can carry business data pointing at organization B, and Shipit will act on B.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

**Binding broken:** `authenticated_organization (repository_owner used to select the webhook secret) == organization/repository actually written by the handler (repository.full_name / organization.login)`. Nothing enforces this equality; the two lookups read different, independently attacker-controlled JSON keys from the same payload.

### Impact Explanation
In a multi-organization Shipit deployment (explicitly supported, cf. `secrets_double_github_app.yml`), an attacker who legitimately controls their own GitHub organization/App installation (Org A, with a known `webhook_secret`) can sign a webhook payload correctly for Org A while filling the business fields with data pointing at a completely different, unrelated organization/repository (Org B) that they do not control:
- A forged `membership` event: `organization.login` = victim's org name (whose `Team` is in `Shipit.github_teams`), `member.login` = attacker's own already-registered Shipit login. This calls `team.add_member(member)`, silently adding the attacker to a privileged GitHub team record inside Shipit — bypassing `User#authorized?` and thus bypassing the entire team-based authorization gate (`Shipit::Authentication#force_github_authentication`). This is a direct escalation into `Shipit.github_teams` authorization.
- A forged `push`/`pull_request` event with `repository.full_name` pointing at a victim repository triggers `sync_github`, review-stack creation/archival, or label-driven provisioning on a stack/repository outside the signing organization's ownership — a cross-repository write triggered purely by request forgery once one org's secret is possessed.

### Likelihood Explanation
Requires the attacker to legitimately control at least one organization/app installation configured in the same multi-tenant Shipit instance (a supported, documented configuration), and knowledge of that org's own `webhook_secret` — which they possess by definition since they configured it. No compromise of the victim org's credentials, no GITHUB_TOKEN, and no privileged Shipit account are needed; only a normal, low-privilege attacker who is a legitimate customer/org owner on the same Shipit install.

### Recommendation
Bind signature verification to the exact same repository/organization identifiers that handlers use to select records to mutate. At minimum:
- Verify the signature using the org derived consistently (e.g., always `repository.full_name`'s owner segment, never falling back to a different top-level `organization.login` field for signature routing vs. business logic), and re-check that value again inside `Handler#process` before mutating any record.
- Reject webhooks whose `repository.owner.login` disagrees with `repository.full_name`'s owner, and reject `membership` events whose `organization.login` doesn't match the org whose webhook secret verified the request.

### Proof of Concept
1. Shipit configured with two orgs: `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim, has a `Team` referenced in `Shipit.github_teams`).
2. Attacker computes `X-Hub-Signature` for the following payload using `OrgA`'s `webhook_secret`:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Victim Team", "slug": "victim-team", "url": "https://github.com/orgs/OrgB/teams/victim-team"},
  "organization": {"login": "OrgB"},
  "member": {"login": "attacker-shipit-login"}
}
```
3. POST to `/webhooks` with `X-Github-Event: membership` and the computed signature header. `repository_owner` resolves via `params.dig('organization','login')` fallback → but for signature selection this only matters if attacker sets it to match an org they control instead; regardless, `verify_signature` selects the app config for whichever org string is present, verified with the attacker's own known secret, while `find_or_create_team!`/`team.add_member(member)` operate against whatever `organization.login`/`team.id` values are embedded — allowing the attacker's own user to be added to `OrgB`'s team.
4. `User#authorized?` for the attacker's account now returns true because `teams.where(id: Shipit.github_teams.map(&:id)).exists?` matches the forged membership, bypassing `Shipit::Authentication#force_github_authentication`.

Note: full end-to-end confirmation (e.g., whether `repository_owner`'s fallback to `organization.login` always coincides with the `membership` handler's own `organization.login` read in a way that fully decouples signature-org from mutated-org in every code path) would benefit from running the existing `test/controllers/webhooks_controller_test.rb` suite and the multi-org fixtures interactively, which was not executed here.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
