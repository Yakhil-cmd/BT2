Confirmed: `GET /api/stacks/*stack_id/ccmenu` routes to `Api::CCMenuController#show`, and the controller's own `stack` method reads the `stack_id` param directly from `Stack.from_param!`, completely bypassing the scoping mechanism used everywhere else in the API (`Api::BaseController#stacks`/`#stack`, e.g. `Api::StacksController#stack` at [1](#0-0)  which correctly filters through `stacks.from_param!`).

### Title
API token scoped to one stack can read CI/build status of any other stack via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::ApiClient` records can be scoped to a single `stack_id`, and this scope is meant to be the boundary of what that token can read or write, enforced by `Api::BaseController#stacks`/`#stack` which restrict lookups to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped. `Api::CCMenuController` overrides `#stack` to bypass that scoping entirely, so a stack-scoped token can query any stack's build/merge status regardless of the stack it was authorized for.

### Finding Description
`ApiClient#check_permissions!` only checks whether the operation/scope string (e.g. `"read:stack"`) is present in the client's `permissions` array; it never checks which stack the client is bound to [2](#0-1) . The actual stack-scoping restriction is implemented separately, in `Api::BaseController#stacks`, which narrows the queryable set of stacks to `current_api_client.stack_id` when the client is stack-scoped, and `#stack`, which resolves the requested stack through that filtered `stacks` relation [3](#0-2) . `Api::StacksController` relies on this correctly by inheriting `#stack` unchanged except to call `stacks.from_param!(params[:id])` [1](#0-0) .

`Api::CCMenuController`, however, defines its own `#stack` that resolves the stack directly from `Stack.from_param!(params[:stack_id])`, without going through the api-client-scoped `stacks` relation at all [4](#0-3) . `#show` renders that unscoped `stack`'s CI/merge status, last build result, and web URL [5](#0-4) .

This is exactly the "stack a token authorises versus a stack it touches" binding: the token is authorized (scoped) for stack A only, but the code that actually serves the request touches whichever stack ID appears in the URL, with no equality check between the two.

### Impact Explanation
This is an unauthenticated-for-that-resource read of stack state: any holder of a `read:stack`-permissioned `ApiClient` token scoped to stack A (e.g. a CCMenu token generated by `CCMenuUrlController` at [6](#0-5) , which is deliberately created with minimal `read:stack`-only permission scoped to one stack) can substitute any other stack's identifier in the URL path and receive that stack's build status, lock state, and last deploy id — data intended to be gated behind that other stack's own tokens/session. This matches the High-impact category "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
High likelihood: no special privileges are needed beyond possessing any single valid stack-scoped API token (which is routinely distributed, e.g. embedded in CCMenu tray-tool URLs per `CCMenuUrlController`). The attacker only needs to know or guess another stack's `owner/repo/environment` identifier, which is often predictable or discoverable (repository names are public, environments are conventional like `production`/`staging`).

### Recommendation
Make `Api::CCMenuController#stack` resolve through the scoped `stacks` relation from `Api::BaseController`, e.g. remove the override and let it inherit `stacks.from_param!(params[:stack_id])`, or explicitly reimplement it as `stacks.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` can only ever resolve the stack it was created for.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']` (this is exactly what `CCMenuUrlController#client` does for a given stack, see `app/controllers/shipit/ccmenu_url_controller.rb`).
2. Obtain its `authentication_token`.
3. Send `GET /api/stacks/other-owner/other-repo/production/ccmenu` using that token as HTTP Basic auth.
4. `authenticate_api_client` succeeds (valid signed token) and `require_permission :read, :stack` passes because the token has `read:stack` in `permissions`.
5. `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing the `stack_id`-scoped `stacks` relation), returning the unrelated stack B.
6. The response renders stack B's `merge_status`, `lastBuildStatus`, `lastBuildLabel`, and `webUrl` — data the token was never authorized to see.
