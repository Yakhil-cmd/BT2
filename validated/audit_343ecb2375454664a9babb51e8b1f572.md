### Title
Unvalidated `P2PStakingInfo.BlockNum` in FastSync Allows Malicious Peer to Corrupt Staking Info DB at Attacker-Chosen Epoch Key — (`datasync/downloader/queue.go`)

---

### Summary

The `validate` callback inside `queue.DeliverStakingInfos` is a deliberate no-op (marked `TODO-Kaia-Snapsync`). It never checks that `P2PStakingInfo.BlockNum` matches the block number of the header that triggered the request. Because `commitFastSyncData` and `commitPivotBlock` both use `result.StakingInfo.BlockNum` — not `result.Header.Number.Uint64()` — as the key passed to `PutStakingInfoToDB`, a malicious sync peer can write an arbitrary staking-info record to any pre-Kaia epoch key in the persistent DB.

---

### Finding Description

**Entrypoint — P2P message handler**

Any connected peer can send a `StakingInfoMsg`. `handleStakingInfoMsg` decodes the raw `[]*staking.P2PStakingInfo` slice and forwards it directly to the downloader with no content checks beyond RLP decoding. [1](#0-0) 

**Missing validation in `queue.DeliverStakingInfos`**

Every other `Deliver*` method performs cryptographic binding to the requested header. `DeliverReceipts` checks `DeriveReceiptsRoot` against `header.ReceiptHash`; `DeliverBodies` checks `DeriveTransactionsRoot` against `header.TxHash`. The staking-info counterpart has a no-op stub:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
``` [2](#0-1) 

The `reconstruct` closure stores the raw, peer-supplied `P2PStakingInfo` (including its `BlockNum` field) directly into `result.StakingInfo` without any cross-check against `header.Number`.

**DB write uses attacker-controlled key**

Both `commitFastSyncData` and `commitPivotBlock` call:

```go
d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
``` [3](#0-2) [4](#0-3) 

The key is `result.StakingInfo.BlockNum` — the value the peer sent — not `result.Header.Number.Uint64()`. A peer that responds to a request for block 1000 with a `P2PStakingInfo{BlockNum: 999, RewardAddrs: [attacker...], KEFAddr: attacker, KIFAddr: attacker}` causes the DB to be written at key 999 with attacker-controlled content, while key 1000 receives nothing.

**DB entry is authoritative for pre-Kaia blocks**

`GetStakingInfo` reads the DB first for pre-Kaia blocks and returns immediately if the entry is non-nil — it does **not** fall back to state when a record exists:

```go
if !isKaia {
    if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {
        s.stakingInfoCache.Add(sourceNum, si)
        return si, nil   // ← no state fallback
    }
}
``` [5](#0-4) 

A corrupted non-nil entry at key 999 is therefore used verbatim for every block in the epoch that draws its staking info from source block 999.

**Contrast with the `SyncStakingInfo` path**

The separate staking-info recovery path explicitly validates `BlockNum`:

```go
if d.stakingInfoRecoveryBlocks[0] != stakingInfo.BlockNum {
    logger.Error("failed to receive expected block", ...)
    return
}
``` [6](#0-5) 

The FastSync path has no equivalent guard.

---

### Impact Explanation

`StakingInfo` controls `RewardAddrs` (per-validator reward destinations), `KEFAddr`/`KIFAddr` (treasury fund addresses), and `StakingAmounts` (validator selection weights). [7](#0-6) 

For pre-Kaia epochs, the DB record is the authoritative source. A corrupted record at key K causes every block in the epoch `[K+StakingInterval, K+2*StakingInterval)` to use attacker-supplied `RewardAddrs` and treasury addresses when the node computes reward distribution and validator set selection. If the victim node is a validator, it will propose blocks with wrong reward payouts; if it is an RPC node, `kaia_getStakingInfo` / `governance_getStakingInfo` return attacker-controlled data. The corruption is durable — it persists in the key-value DB and is served from cache on subsequent reads. [8](#0-7) 

---

### Likelihood Explanation

- The attacker only needs to be a connected P2P peer during FastSync — no privileged role required.
- The victim node must be running FastSync (common during initial sync or re-sync after a crash).
- The attack requires sending a single crafted `StakingInfoMsg` response; no cryptographic material is needed.
- The `TODO` comment confirms the missing check is a known gap, not an intentional design choice.

---

### Recommendation

In `queue.DeliverStakingInfos`, replace the no-op `validate` with a check that binds the delivered record to the requested header:

```go
validate := func(index int, header *types.Header) error {
    if stakingInfoList[index].BlockNum != header.Number.Uint64() {
        return errInvalidStakingInfo
    }
    return nil
}
```

Additionally, in `commitFastSyncData` and `commitPivotBlock`, use `result.Header.Number.Uint64()` as the DB key rather than `result.StakingInfo.BlockNum`, so the key is always derived from the locally-verified header, not from peer-supplied data.

---

### Proof of Concept

1. Victim node starts FastSync against a malicious peer.
2. Victim requests staking info for block 1000 (hash H1000).
3. Malicious peer responds with `P2PStakingInfo{BlockNum: 999, CouncilRewardAddrs: [attacker_addr], KEFAddr: attacker_addr, KIFAddr: attacker_addr}`.
4. `queue.DeliverStakingInfos` calls `validate(0, header_1000)` → returns nil (no-op).
5. `reconstruct` stores the record in `result.StakingInfo`.
6. `commitFastSyncData` calls `PutStakingInfoToDB(999, ...)` → DB key 999 is overwritten with attacker-controlled addresses.
7. DB key 1000 is never written.
8. Any subsequent `GetStakingInfo(num)` where `sourceBlockNum(num) == 999` reads the corrupted record and returns attacker-controlled `RewardAddrs`/`KEFAddr`/`KIFAddr`.
