### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but the repository/stack actually acted upon is selected from the independent `repository.full_name` field — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and thus which `webhook_secret`) to validate a webhook's HMAC signature against based on `repository.owner.login` in the JSON body, while every event `Handler` resolves the target `Stack`/`Repository` to act on using the separate `repository.full_name` field from the same body. Because both values are attacker-supplied fields inside the same payload the attacker fully controls, an admin of any single GitHub organization onboarded to a shared Shipit instance can sign a payload with their own (known) webhook secret while pointing `repository.full_name` at a completely different organization's repository, causing Shipit to act on a repo/stack the signer does not own.

### Finding Description
`Shipit::WebhooksController#verify_signature` selects the signing/verification context per-organization: [1](#0-0) 
`repository_owner` is read straight from the untrusted body: [2](#0-1) 

The `GithubOrganizationUnknown` rescue path confirms the engine is designed for multiple, independently configured GitHub organizations/Apps (each with its own `webhook_secret`), any one of which an outside admin can legitimately control and configure themselves: [3](#0-2) 

Once the signature check passes (using the secret belonging to the organization named in `repository.owner.login`), the raw body is handed unmodified to the registered event handlers: [4](#0-3) 

Every handler resolves the repository/stack to operate on independently, using `repository.full_name` — not `repository.owner.login`: [5](#0-4) [6](#0-5) 

Nothing ties `full_name`'s owner segment back to the `repository_owner`/organization whose secret was used for verification — they are read from two different fields of an entirely attacker-authored body. `PushHandler`, for example, uses this repository lookup to sync a stack to an attacker-chosen SHA: [7](#0-6) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by the verified HMAC (repository.owner.login)` == `organization/repository actually written to (repository.full_name)`.

Concretely: an attacker who administers *any* GitHub organization/App connected to a shared Shipit instance knows that org's `webhook_secret` (they configured it themselves per `docs/setup.md`). They can:
1. Build a JSON body with `repository.owner.login = "attacker-org"` (so `verify_signature` selects `Shipit.github(organization: "attacker-org")`) but `repository.full_name = "victim-org/victim-repo"`.
2. Sign the whole raw body with `attacker-org`'s known `webhook_secret` using `Hook::DeliverySigner`-equivalent HMAC-SHA1 logic mirrored in `GitHubApp#verify_webhook_signature`: [8](#0-7) 
3. POST it to `/webhooks`. Signature verification succeeds (it only checks the secret matches `attacker-org`'s), and the handler dispatched for the event then loads `victim-org/victim-repo`'s stacks via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and acts on them — e.g. `stack.sync_github(expected_head_sha: params.after)` for a `push` event.

### Impact Explanation
This crosses an authentication boundary from one organization into another organization's repositories/stacks tracked by the same Shipit deployment — a cross-repository write. Depending on the event/handler exercised, this can force a victim stack to sync to an attacker-chosen commit SHA (potentially triggering an unauthorized deploy if continuous deployment is enabled), forge CI/commit statuses, or manipulate pull-request/merge-queue state (`pull_request/*` handlers, `status_handler.rb`, `check_suite_handler.rb`) for repositories the attacker has no legitimate access to. This matches the specified High/Critical impact categories (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization/App (a documented, supported configuration per `docs/setup.md`), and that the attacker controls one of those organizations (i.e., knows its `webhook_secret`) — no privileged Shipit account, session, or API token is needed, only network access to the public `/webhooks` endpoint.

### Recommendation
After signature verification, re-derive the organization strictly from the same trusted context used to select the verification secret, and reject (or restrict) any handler action where `repository.full_name`'s owner segment does not match the `repository_owner`/organization that authenticated the request. Alternatively, verify that the resolved `Repository#owner` used by handlers equals the organization whose secret validated the HMAC before dispatching any handler logic.

### Proof of Concept
1. Attacker registers/controls GitHub organization `attacker-org`, which is a legitimate, separate organization already onboarded to a shared Shipit instance (each org has its own `github.webhook_secret` per `docs/setup.md`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<victim-repo-old-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC_SHA1(attacker-org_webhook_secret, raw_body)` and sends it as `X-Hub-Signature`, with `X-Github-Event: push`, to the Shipit `/webhooks` endpoint.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository_owner`), verifies successfully against the attacker's own secret.
5. `Shipit::Webhooks.for_event('push')` dispatches `PushHandler`, which resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: 'victim-repo-old-sha')` on the victim's stack — an action fully controlled by an attacker who authenticated only as `attacker-org`.

*(Note: I could not directly inspect `lib/shipit.rb`'s exact multi-organization `github` configuration lookup within the available iterations to fully confirm that each organization is guaranteed a distinct `webhook_secret` in every deployment; this is inferred from the `GithubOrganizationUnknown` handling and the documented per-org `github:` config block in `docs/setup.md`. If a Shipit instance is single-tenant with only one configured organization, this specific analog does not apply.)*

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
