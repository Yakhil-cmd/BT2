### Title
Webhook signature verification is bound to an attacker-chosen `repository.owner.login`/`organization.login` field, while the events themselves act on an unrelated repository/commit — allowing cross-organization webhook forgery (`WebhooksController#verify_signature`)

### Summary
`Shipit::WebhooksController` selects which GitHub App's `webhook_secret` to verify a webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the **unauthenticated JSON body**, but the handlers that actually mutate state key off a *different* field of the same body — `repository.full_name` for most handlers, or, in `StatusHandler`, no repository scoping at all. This breaks the binding "organization that authenticated == repository/commit that is written," which is the same class of flaw as the CNote report (a value that gates authorization is not the value that is actually acted upon).

### Finding Description
`verify_signature` picks the verifying `GitHubApp` config purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

That `github_app` (chosen by the attacker-controlled `repository_owner`) is used only to fetch a `webhook_secret` used to `verify_webhook_signature`: [3](#0-2) 

Note that if a configured organization has no `webhook_secret` set (documented as *optional*), `verify_webhook_signature` unconditionally returns `true`: [4](#0-3) [5](#0-4) 

Once verification passes, `create` dispatches the same raw params to the event handler: [6](#0-5) 

But the generic `Handler#stacks` (used by `PushHandler`, `CheckSuiteHandler`, etc.) resolves the target repository from `repository.full_name`, a field that was never part of the value checked to select the verifying secret: [7](#0-6) 

Worse, `StatusHandler` performs no repository binding check at all — it looks up commits globally by `sha` across the entire Shipit installation and writes an attacker-supplied status (`state`, `description`, `target_url`, `context`) onto it: [8](#0-7) 

So the equality that should hold — *"the organization whose secret authenticated this request" == "the repository/commit the event is allowed to modify"* — is never enforced. An attacker only needs to control (or find one configured org with a blank) `webhook_secret` for *any* organization known to this multi-tenant Shipit instance (multiple GitHub Apps/orgs are an explicitly supported, documented configuration): [9](#0-8) 

and can then set `repository.owner.login` to that organization (to pass signature verification) while setting `repository.full_name` (for push/check_suite/etc.) or simply `sha` (for status events) to point at an entirely different, victim stack.

### Impact Explanation
This is an unauthenticated (no Shipit session, no `ApiClient` token) forgery path against the public `/webhooks` endpoint (`WebhooksController` does not include the `Authentication` concern used elsewhere):
- `StatusHandler` lets an attacker mark an arbitrary, cross-organization commit's CI/status check as `"success"` with a forged `context`/`target_url`, independent of which repository/organization the commit belongs to. Since commit statuses gate mergeability and deploy readiness in Shipit's UI/merge-queue logic, this can enable an unauthorized merge/deploy of a commit that never actually passed CI.
- `PushHandler`/`CheckSuiteHandler` let an attacker trigger `GithubSyncJob`/check-run refresh for any victim repository/stack configured in the instance, by presenting a `repository.owner.login` the attacker controls the secret for, while pointing `repository.full_name` at the victim repository.

This matches the required Critical impact category (unauthorized deploy/merge) since a forged "success" status can be a direct precondition for auto-merge/deploy gating.

### Likelihood Explanation
Requires the attacker to control (or discover a blank) `webhook_secret` for **any** organization configured in the target's multi-org Shipit setup — not the victim organization's secret. Since `webhook_secret` is documented as optional and Shipit explicitly supports multiple orgs sharing one instance, an attacker who is a legitimate collaborator/admin on one low-trust org (or who deploys their own GitHub App pointed at the shared `/webhooks` URL) can forge signatures accepted for any other org's repositories/commits. No repository write access, GitHub App private key, or Shipit session/token is required — only knowledge of one configured org's HMAC secret (which the attacker may legitimately possess for their own, unrelated org).

### Recommendation
Do not let the value used to select the verifying secret diverge from the value the handler acts on:
- After verifying with `Shipit.github(organization: repository_owner)`, re-derive the repository/organization to act on strictly from `repository_owner` (or verify that `repository.full_name`'s owner segment equals `repository_owner`) before dispatching to handlers.
- Reject requests where `webhook_secret` is blank rather than treating them as automatically verified, or explicitly require `webhook_secret` for every configured organization.
- In `StatusHandler`, scope `Commit.where(sha: ...)` to commits belonging to stacks under the authenticated `repository_owner`/organization rather than performing a global, unscoped lookup.

### Proof of Concept
1. Configure/assume the target Shipit instance manages multiple GitHub orgs (a documented supported setup), e.g. `attacker-org` (attacker knows/controls its `webhook_secret`, or it is left blank) and `victim-org/victim-repo` (a real, sensitive stack).
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha the attacker wants marked green>",
  "state": "success",
  "context": "ci/forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` (known to them) over the raw body, sets `X-Github-Event: status`, and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and successfully verifies the signature, because the attacker signed the body with the secret for `attacker-org`.
5. `create` dispatches to `Shipit::Webhooks::Handlers::StatusHandler`, which runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — writing a forged "success" status onto the victim commit, in `victim-org/victim-repo`, with no relation to `attacker-org` ever checked.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
