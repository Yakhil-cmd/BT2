### Title
Misplaced EIP-3541 Validation Permanently Stores 0xEF Contract Code in State Despite Reported Failure — (`blockchain/vm/evm.go`)

---

### Summary

In `blockchain/vm/evm.go`, the `create()` function's EIP-3541 guard for the Kore hardfork (rejecting runtime code starting with `0xEF`) is placed **after** the code has already been written to the state DB and **after** the snapshot-revert decision block. As a result, a contract deployer can cause 0xEF-prefixed bytecode to be permanently committed to the state trie while the transaction receipt reports failure. The code comment in the repository explicitly acknowledges this ordering error.

---

### Finding Description

The `create()` function in `blockchain/vm/evm.go` executes the following sequence when `chainRules.IsKore && !chainRules.IsPrague`:

1. **Snapshot taken** at line 566.
2. **Init code runs** at line 584; returns 0xEF-prefixed runtime bytes in `ret`.
3. **Max-code-size check** (lines 588–590): passes — `err` remains `nil`.
4. **Prague 0xEF check** (lines 592–595): skipped — `IsPrague` is false.
5. **`evm.StateDB.SetCode(address, ret)`** called at line 604 — **0xEF code is written to state**.
6. **Revert block** (lines 620–625): `err == nil`, so `RevertToSnapshot` is **never called**.
7. **Kore 0xEF check** (lines 631–633): `err` is now set to `ErrInvalidCode` — but the code is already committed and the snapshot was not reverted.
8. Function returns `err = ErrInvalidCode`.

Back in `TransitionDb()`, `vmerr = ErrInvalidCode`. Because `ErrInvalidCode` is absent from the `errTxFailed2receiptstatus` map (lines 667–697 of `blockchain/state_transition.go`), `getReceiptStatusFromErrTxFailed` falls through to `ReceiptStatusErrDefault` (0x02). The receipt is written as a failure, but the state trie permanently contains the 0xEF bytecode at the contract address.

The repository itself documents this as a known misplacement:

> *"This validation was incorrectly placed after the code was already stored in state DB, which should have been prevented. This is kept for backwards compatibility and will be properly handled after Prague hardfork."* [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

---

### Impact Explanation

**Broken invariant**: A failed contract deployment must leave no code at the target address. Here, the state trie contains live 0xEF bytecode at the address while the receipt signals failure.

**Concrete consequences**:
- The "failed" contract address has non-empty code in state; `state.GetCode(addr)` returns the 0xEF bytes.
- Any KAIA or tokens sent to that address are controlled by the deployed (but receipt-failed) contract.
- Other contracts that call `EXTCODESIZE` or `EXTCODEHASH` on the address will observe non-zero values, contradicting the receipt.
- The state root diverges from what the receipt implies, corrupting canonical execution for any system that relies on receipt status to determine deployment success.
- `ErrInvalidCode` is not in `errTxFailed2receiptstatus`, so the receipt status is the generic `ReceiptStatusErrDefault` (0x02), giving no signal that code was actually stored. [5](#0-4) [6](#0-5) 

---

### Likelihood Explanation

- **Trigger**: Any unprivileged user can submit a contract-creation transaction whose init code returns a single byte `0xEF` (or any 0xEF-prefixed sequence ≤ 24 576 bytes).
- **Window**: Active on any Kaia node running Kore-compatible hardfork without Prague enabled. Kairos testnet and any private network in this hardfork range are affected.
- **No special privilege required**: standard `TxTypeSmartContractDeploy` or Ethereum-compatible `CREATE`/`CREATE2`.

---

### Recommendation

Move the Kore-era 0xEF rejection to **before** `SetCode` is called, mirroring the Prague guard at lines 592–595:

```go
// Reject code starting with 0xEF (EIP-3541) for Kore hardfork.
if err == nil && len(ret) >= 1 && ret[0] == 0xEF && evm.chainRules.IsKore {
    err = ErrInvalidCode
}

// Only store code if no error.
if err == nil {
    createDataGas := uint64(len(ret)) * params.CreateDataGas
    ...
}
```

This ensures the snapshot revert at lines 620–625 fires before any state write occurs, matching the Prague path. [7](#0-6) 

---

### Proof of Concept

**Init bytecode** that returns a single `0xEF` byte as runtime code:
```
60EF  // PUSH1 0xEF
6000  // PUSH1 0x00
53    // MSTORE8  (mem[0] = 0xEF)
6001  // PUSH1 0x01  (size = 1)
6000  // PUSH1 0x00  (offset = 0)
F3    // RETURN
```

**Steps**:
1. Submit a `TxTypeSmartContractDeploy` (or Ethereum `CREATE`) with the above init code on a Kore-active, Prague-inactive chain.
2. Observe receipt: `status = 0x02` (`ReceiptStatusErrDefault`) — deployment appears failed.
3. Query `kaia_getCode(contractAddress, "latest")` — returns `0xEF`, confirming code is in state.
4. Send KAIA to `contractAddress`; the balance is now controlled by the 0xEF contract, not an EOA.

**Corrupted value**: `state.GetCode(contractAddress)` returns `[0xEF, ...]` while the receipt `Status` field is `0x02` (failure). The state root includes this code, creating a permanent divergence between on-chain state and receipt-derived expectations. [8](#0-7) [9](#0-8)
