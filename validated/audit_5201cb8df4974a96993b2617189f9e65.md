### Title
`OpenedHandler#provision?` skips `review_stacks_enabled` for the `allow_with_label`/`prevent_with_label` branches, letting a PR author on a repo with review stacks disabled trigger provisioning by self-applying a label - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`provision?` is written as `A && B || (C && D) || (E && F)`; due to Ruby's `&&`/`||` precedence, `review_stacks_enabled` (`A`) is only ANDed into the first disjunct (`allow_all?`). The second and third disjuncts (`allow_with_label?`/`prevent_with_label?`) are evaluated independently of `review_stacks_enabled`, so on a repository with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label`, a PR author who applies the configured label to their own PR can still trigger `ReviewStackAdapter#create!` and provisioning.

### Finding Description
The claimed broken binding: `repository.review_stacks_enabled == false` should imply "no review stack is ever provisioned for this repository," but the actual code guarantees only `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? == true` implies provisioning is gated — the other two behaviors are gated purely by label state, independent of `review_stacks_enabled`.

Code path, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

`respond_to_pull_request_opened?` gates `process` purely on `params.action == "opened" && provision?`, and `process` then unconditionally calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which calls `create!` and persists a `ReviewStack`/`Stack` record and adds it to `ReviewStackProvisioningQueue`: [2](#0-1) [3](#0-2) 

`pull_request_has_provisioning_label?` reads label names straight from the webhook payload (`pull_request.labels[].name`), which is attacker-writable metadata on the attacker's own PR: [4](#0-3) 

Exploit: attacker opens a PR on a repo configured with `review_stacks_enabled: false`, `provisioning_behavior: allow_with_label`, `provisioning_label_name: <guessable default>`. Attacker adds that label to their own PR before/at open time (labels are part of the `pull_request.labels` array in the `pull_request` webhook, which the attacker fully controls on their own repo/PR). When the "opened" webhook fires, `provision?` evaluates the second disjunct `(allow_with_label? && has_label)` = true regardless of `review_stacks_enabled`, so `respond_to_pull_request_opened?` returns true and a `ReviewStack` is created and queued for provisioning.

Existing guards do not prevent this: webhook signature verification (`GitHubApp#verify_webhook_signature`) only proves the event genuinely originates from the attacker's own repo/PR — it says nothing about whether the *business rule* "review stacks disabled" is honored, and `ExplicitParameters` schema only validates payload shape, not the provisioning-behavior guard, which is exactly the buggy boolean expression above. `NullRepository` (untracked repos) is unaffected since its behavior predicates always return `false`, but this is irrelevant once the repo is tracked with the vulnerable config. [5](#0-4) 

The identical precedence bug is also present in `ReopenedHandler#unarchive?`, which uses the exact same expression shape: [6](#0-5) . Note that `LabeledHandler#respond_to_label_change?` correctly ANDs `repository.review_stacks_enabled` across the whole `archive?`/`unarchive?` disjunction, confirming the intended invariant was "review_stacks_enabled must gate every provisioning behavior," not just `allow_all`: [7](#0-6) .

### Impact Explanation
On a repository that has explicitly opted out of review-stack automation (`review_stacks_enabled: false`), an unprivileged PR author (who is not a repository maintainer, has no Shipit session, and controls only their own PR/labels) can still cause a `Stack`/`ReviewStack` record to be created and queued for provisioning, and the resulting stack execution will run the attacker-supplied `shipit.yml` from their branch (per `stack_attributes`, `branch: params.pull_request.head.ref`). This is a repository-owner-authorization bypass: the repo owner deliberately disabled review-stack provisioning, but the label-based behaviors ignore that setting entirely. It is repeatable against any repository configured with `review_stacks_enabled: false` + `provisioning_behavior: allow_with_label` (or `prevent_with_label`, where it is trivially always true unless the attacker deliberately adds the label) and a guessable/default `provisioning_label_name`. This matches "Critical: a payload for one repository mutating another's stack" in spirit — more precisely, it is an unauthorized-provisioning/config-bypass leading to arbitrary attacker-controlled `shipit.yml` execution on that repo's review-stack infrastructure, which the maintainer explicitly opted out of.

### Likelihood Explanation
Requires the target repository to have `review_stacks_enabled: false` combined with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) and a `provisioning_label_name` the attacker can guess or discover (e.g., a common default like `"ship-it"`, `"review-app"`, visible in repo settings UI/docs, or brute-forceable since label names are typically short and conventional). Attacker cost is a single PR open with a self-applied label on their own fork/branch — no privileged access required. This is a plausible but not universal configuration combination; likelihood depends on how many operators actually pair `review_stacks_enabled: false` with `allow_with_label`/`prevent_with_label` (an unusual but valid combination since the enum/boolean are independent columns with no DB-level constraint preventing it).

### Recommendation
Rewrite `provision?` (and the analogous `unarchive?` in `ReopenedHandler`) so `review_stacks_enabled` gates all three disjuncts, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` add:
```ruby
test "does not create stacks for allow_with_label when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding to assert both sides of:
- Before fix: `repository.review_stacks_enabled == false` but `Shipit::Stack.count` still increases by 1 (test fails, proving the bypass).
- After fix: `repository.review_stacks_enabled == false` implies `Shipit::Stack.count` unchanged (test passes).
