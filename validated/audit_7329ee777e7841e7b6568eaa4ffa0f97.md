### Title
`Commit.where(sha:)` unscoped by repository lets a `status` webhook mutate another repository's commit statuses - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha`, without ever calling `Repository.from_github_repo_name` or scoping to the payload's `repository.full_name`, and calls `commit.create_status_from_github!(params)` on every match. Since git SHAs are content-addressed and can trivially collide across unrelated forks/orgs sharing history (or be brute-guessed/observed via public commit history), an attacker who owns a repository can send a signed `status` webhook naming their own repo but referencing a SHA belonging to a commit tracked by an unrelated stack, mutating that unrelated stack's commit status/CI state.

### Finding Description
The broken binding: for every `Handler` subclass, `repository resolved from payload == repository actually mutated`. In `OpenedHandler#process` this holds: `repository.review_stacks` is derived from `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [1](#0-0) , and the base `Handler#stacks` helper used by `PushHandler` similarly scopes via `Repository.from_github_repo_name(repository_name)&.stacks` before filtering by branch [2](#0-1) [3](#0-2) .

`StatusHandler#process`, however, does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository/stack filter at all [4](#0-3) . Its `params` schema doesn't even require a `repository` field [5](#0-4) . `Commit#create_status_from_github!` writes a new `Status` record tied to the commit's actual `stack_id` and emits `commit_status`/`deployable_status` hooks scoped to that stack [6](#0-5) [7](#0-6) , and can flip `deployable?`/trigger `schedule_continuous_delivery`, potentially unblocking a deploy on a stack the attacker never authenticated against.

Exploit: attacker signs a `status` event webhook (valid signature for their own repo's registered secret) with `sha` equal to a commit SHA that also exists in an unrelated stack's `commits` table (via shared git history — forks, cherry-picks, or coincidentally identical commits are realistic; the DB `Commit#sha` column has no repository uniqueness constraint enforced at the handler level). Every `Commit` row across all repositories matching that SHA gets a forged status written, regardless of which repository's webhook secret validated the request.

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only proves *some* repository's secret matches, not that the sha belongs to that repository; `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha`, `requires :state`) never enforce a repository check; there is no `require_permission!` or repository-comparison step anywhere in `StatusHandler`.

### Impact Explanation
A successful `status` webhook write injects an attacker-controlled CI status (`success`/`failure`/`pending`, `description`, `target_url`) onto a commit belonging to a stack/repository the attacker does not own, which can influence `blocked?`/`deployable?` and `schedule_continuous_delivery`, i.e., a payload for one repository mutating another's commit/stack state — this matches the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It is repeatable against any commit whose SHA the attacker can discover and match to an owned/forked repo's history.

### Likelihood Explanation
Preconditions: the attacker needs a registered Shipit repository (owning webhook secret) and knowledge of a target SHA that also exists as a `Commit` row elsewhere (achievable via forks sharing history, or any commit that has been mirrored/cherry-picked, both common on GitHub). No special Shipit role or GitHub team membership is required — cost is a single signed HTTP POST. Feasibility depends on SHA collision across repos' commit tables, which is realistic in forked/mirrored-repo ecosystems, making this moderately but not universally exploitable.

### Recommendation
Scope `StatusHandler#process` to the payload's repository, matching the pattern used elsewhere: require `repository.full_name` in the params schema, resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit` lookup to that repository's stacks (e.g. `repository.stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent scoped query) instead of a global `Commit.where(sha:)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, out-of-scope directory per rules but described conceptually):
1. Create `stack_a` (repo `attacker/repo`) and `stack_b` (repo `victim/repo`), each with a `Commit` sharing the same `sha` value.
2. Build a `status` payload naming `repository.full_name = "attacker/repo"` and `sha` equal to the shared value.
3. Assert, before invoking `StatusHandler.call(payload)`, that `Shipit::Repository.from_github_repo_name` is never invoked inside `StatusHandler#process` (`Shipit::Repository.expects(:from_github_repo_name).never`), contrasted with `OpenedHandler`, where the same expectation is set to be called once with `params.repository.full_name`.
4. Call `StatusHandler.call(payload)` and assert that `stack_b`'s commit (`victim/repo`) received a new `Status` row / `create_status_from_github!` was invoked on it, proving cross-repository mutation, while only `stack_a`'s webhook secret was used to pass signature verification.
