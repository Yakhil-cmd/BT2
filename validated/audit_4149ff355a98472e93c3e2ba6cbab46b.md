### Title
Webhook signature key selection is bound to `repository.owner.login` while stack lookup is bound to `repository.full_name`, allowing cross-organization webhook forgery — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) from the untrusted JSON body, while the event handlers that act on the payload (`PushHandler`, and the `PullRequest::*Handler` family) resolve the target `Stack`/`Repository` using a completely different field of the same body: `repository.full_name`. The signature therefore never binds "the organization whose secret authenticated the request" to "the repository the request is allowed to act on." In a multi-organization Shipit installation, anyone who controls one configured organization's GitHub App secret can forge a syntactically valid, correctly-signed webhook body that targets a different organization's repository/stack.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This selects the `webhook_secret` used for HMAC verification purely from `repository.owner.login` inside the attacker-controlled JSON body (Shipit supports multiple configured GitHub organizations, each with its own `webhook_secret`, per `docs/setup.md`). Once the signature check passes, the raw params (including `repository.full_name`) are forwarded unchanged to the registered handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [2](#0-1) 

Handlers then resolve the target repository/stack using a *different* field, `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` uses this to trigger a sync on any matching stack:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

The pull-request handlers do the same, resolving the acted-upon repository from `params.repository.full_name`, independent of which org's secret signed the request, e.g.:
```ruby
def repository
  @repository ||=
    Shipit::Repository.from_github_repo_name(params.repository.full_name) ||
    Shipit::NullRepository.new
end
``` [5](#0-4) 

**Binding broken (as an equality):**
`organization_that_authenticated (params.repository.owner.login, used to pick the HMAC key)` should equal `repository_that_is_written (params.repository.full_name, used to select the Stack/Repository that gets mutated)`. Nothing in `verify_signature` or in the handler chain enforces this equality — an attacker can set these two fields independently in the same JSON body they sign.

### Impact Explanation
In a multi-org Shipit deployment (`config/secrets.yml` with a per-organization `github:` map, as documented in `docs/setup.md:182-209`), each organization administrator only receives/controls their *own* organization's `webhook_secret`. An attacker who legitimately owns/administers "Org A" and its GitHub App (and therefore knows Org A's `webhook_secret`) can craft an HTTP POST directly to `/webhooks` (bypassing GitHub entirely) with:
- `repository.owner.login` = `"org-a"` (so `verify_signature` picks Org A's `webhook_secret`, which the attacker knows and can correctly HMAC-sign), and
- `repository.full_name` = `"org-b/victim-repo"` (an unrelated, already-registered Shipit repository/stack belonging to a different organization the attacker has no access to).

Because the two checks use disjoint fields, the forged, correctly-signed request is accepted and dispatched to handlers acting on Org B's stack:
- Via `PushHandler`, the attacker can force `Stack#sync_github` on Org B's stack with an attacker-chosen `expected_head_sha`, an unauthorized cross-organization action against a stack the attacker was never granted webhook trust for.
- Via the `PullRequest::*Handler` family, the attacker can create/archive/unarchive review stacks and manipulate labels/pull-request state on Org B's repository's review stacks.

This is a genuine authentication/trust-boundary bypass: possession of one organization's webhook credential is treated by the engine as sufficient authorization to act on any other configured organization's repository, which is the deployment-trust binding shipit.yml/config expects to be organization-scoped. This matches the "cross-repository writes" impact category.

### Likelihood Explanation
Exploitability requires: (1) a Shipit instance configured with multiple GitHub organizations (a documented, supported configuration), and (2) the attacker being a legitimate, non-privileged controller of just one of those organizations' GitHub App webhook secrets — no access to the victim organization, no `ApiClient` token, no repository write access on the victim repo, and no interaction with Shipit's session/auth system is needed. The request can be crafted and sent directly via HTTP, entirely bypassing GitHub. This is a realistic configuration and a straightforward exploitation path once multi-org support is in use.

### Recommendation
Bind the field used to select the verification key to the same field used to resolve the acted-upon repository/stack. Concretely:
- In `verify_signature`, after verifying the HMAC using the org derived from `repository.owner.login`, additionally verify that `repository.owner.login` matches the owner segment of `repository.full_name` (or store/compare a canonical "organization" derived once and reused consistently by all handlers).
- Alternatively, have `Repository.from_github_repo_name` / handler lookups also filter by the verified `repository_owner` organization, rejecting payloads whose `full_name` owner doesn't match the organization whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` multi-org setup), and register a Shipit `Repository`/`Stack` for `org-b/victim-repo`.
2. As the administrator of `org-a`'s GitHub App (an "unprivileged" attacker with respect to `org-b`), construct a push webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `org-a`'s known `webhook_secret` over the raw JSON body (per `GitHubApp#verify_webhook_signature` and `app/controllers/shipit/webhooks_controller.rb:24-30`).
4. POST this body with header `X-Github-Event: push` directly to `/webhooks`. `verify_signature` resolves `Shipit.github(organization: "org-a")`, verifies successfully, and `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) resolves the stack via `repository.full_name = "org-b/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on Org B's stack — despite the attacker never having any credential or access tied to Org B.
