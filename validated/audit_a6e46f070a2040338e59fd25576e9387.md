### Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, letting a stack-restricted token read any stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via its `stack_id` column, enforced by `Shipit::Api::BaseController#stacks`/`#stack`. The CCMenu API endpoint, however, overrides `#stack` to bypass this scoping entirely, so a token that is authorized only for stack A can be used to read the build/deploy status of any stack B.

### Finding Description
`Shipit::Api::BaseController` defines the scoping contract that every other API controller relies on: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves the requested `params[:stack_id]` against that restricted set — this is the binding: *token authorizes stack X* ⇒ *only stack X can be touched*. This scoping is real and used in practice, e.g. the `here_come_the_walrus` fixture client is created with `stack: shipit` and only the `read:stack` permission: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, does not use the inherited scoped `stack` method. It overrides it to look the stack up directly and unconditionally: [3](#0-2) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

This calls `Stack.from_param!` directly instead of `stacks.from_param!`, so `current_api_client.stack_id` is never consulted. The only permission gate is the class-level `require_permission :read, :stack` declaration (a permission-string check, not a stack-identity check): [4](#0-3) 

`ApiClient#check_permissions!` only verifies the client has the `read:stack` permission string — it never compares `stack_id` to the requested resource: [5](#0-4) 

Equality that should hold but does not:
`token.stack_id (authorized stack)` == `stack_id in ccmenu request (stack actually touched)` — this equality is enforced by `BaseController#stack` for every other API resource, but the `CCMenuController` override breaks it.

### Impact Explanation
Any holder of a valid, stack-scoped, read-only `ApiClient` token (e.g. a CCMenu/CCTray monitoring URL generated by `CCMenuUrlController` and meant to be embedded in a public build-status dashboard/widget) can use that exact token to query `GET /api/:owner/:repo/:stack/ccmenu.xml` for *any other stack in the installation*, obtaining `merge_status`, deploy activity, last build time/label, and stack URL for stacks the token was never meant to see. This is an unauthorized cross-stack read of stack state (merge/deploy status), matching the "High — unauthenticated/unauthorized read of stack state" impact class: a credential legitimately scoped to one deployable stack is usable to read every other stack's status in the Shipit instance.

### Likelihood Explanation
Likelihood is high for anyone who already possesses one legitimately-issued CCMenu token (these tokens are explicitly designed to be embedded in third-party CI dashboard tools and are not treated as highly sensitive, since they are meant to be stack-scoped and read-only). No additional privileges, session, or GitHub identity are required — only the token value and knowledge/guessing of another stack's `stack_id`/param format, which is derivable from any visible stack URL (`stack.to_param`).

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to use the scoped lookup consistent with the rest of the API surface:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the `current_api_client.stack_id` restriction so a stack-scoped token can only retrieve CCMenu data for the stack it was issued for.

### Proof of Concept
1. As a legitimate user, generate a CCMenu URL for stack `shipit` via `CCMenuUrlController#fetch`, which creates/reuses an `ApiClient` (in general such a client could be created with `stack: shipit` scoping and `read:stack` permission only, e.g. akin to the `here_come_the_walrus` fixture) and returns a token embedded in the CCMenu URL: [6](#0-5) 
2. Take the resulting `token` query parameter and issue a request against a *different* stack's CCMenu endpoint:
`GET /api/other-owner/other-repo/other-stack/ccmenu.xml?token=<token>`
3. Because `CCMenuController#stack` calls `Stack.from_param!` directly rather than the client-scoped `stacks.from_param!`, the request succeeds and returns the other stack's `merge_status`/deploy info, even though the token was only ever authorized (or intended) for the original stack.
