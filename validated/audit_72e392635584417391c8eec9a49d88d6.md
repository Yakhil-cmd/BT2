### Title
GitHub webhook signature is checked against the organization named in an untrusted payload field, while the commit/repository actually written comes from a *different*, uncorrelated payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is the same root-cause bug class as the yAxis `inCaseStrategyGetStuck` finding: an action is performed against one piece of tracked state (`_vaultDetails[_vault].balances[_strategy]`) while the "authorization" check (the pre-recorded balance) is derived from a different, stale source. In Shipit, `WebhooksController#verify_signature` decides whether a webhook is "authenticated" using the organization/owner name taken from the untrusted payload itself, but the handlers that actually mutate state (create commit statuses, sync stacks, trigger merges) key off *other*, independent fields of that same untrusted payload. Nothing binds "the organization whose secret validated this request" to "the repository/commit that gets written."

### Finding Description
`WebhooksController#verify_signature` computes which GitHub App config to check against purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the unverified body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), and `Shipit.github(organization: repository_owner)` selects that organization's `GitHubApp` instance. Verification itself is a short-circuit when that org has no configured `webhook_secret`: [3](#0-2) 

`webhook_secret` is an optional, documented setting (`docs/setup.md`, and multi-org config samples show an org intentionally left with `webhook_secret: # nil`), so on any multi-organization Shipit instance where at least one configured organization has no secret, `verified` is unconditionally `true` for a request whose `repository.owner.login` names that org — regardless of the `X-Hub-Signature` header's validity.

Once past `verify_signature`, the handler that actually performs the write does **not** re-derive the target from `repository_owner`. `StatusHandler` matches purely by commit SHA, globally, with no repository scoping at all: [4](#0-3) 

Other handlers (`PushHandler`, pull-request handlers) scope by `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks`, which is again an independent field of the same attacker-supplied body: [5](#0-4) [6](#0-5) 

So the equality that should hold — `organization used to pick the verification secret == organization/repository actually written to` — is never enforced anywhere in the request lifecycle.

### Impact Explanation
An unprivileged, unauthenticated caller who only needs to know that *some* org configured on the instance has no `webhook_secret` (an intentionally supported, documented configuration, not a misuse of the engine) can forge a `status` event naming that org as `repository.owner.login` to sail through `verify_signature`, while setting `sha` to a real commit SHA belonging to a completely unrelated stack/repository on the same instance. `StatusHandler#process` then calls `Commit#create_status_from_github!` on that victim commit: [7](#0-6) 

which runs `add_status`, and if the forged state flips the commit to `success`, unconditionally schedules the merge queue for the *victim* stack: [8](#0-7) 

This lets an attacker with no Shipit session, no `ApiClient` token, and no knowledge of the victim's real webhook secret force a forged "CI success" onto an arbitrary commit and trigger an unauthorized merge/deploy — squarely within the Critical impact bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Likelihood is realistic wherever a Shipit deployment hosts multiple GitHub organizations (a documented, first-class configuration — see `test/dummy/config/secrets_double_github_app.yml`) and at least one of them has not set `webhook_secret` (also explicitly documented as optional in `docs/setup.md`). No credentials, tokens, or privileged access are required — only knowledge of that org's name/login and a target commit SHA, both discoverable via the public GitHub repo/PR UI.

### Recommendation
Bind verification to the entity actually acted upon: after computing which org's secret validated the signature, re-derive/require that the payload's `repository.full_name` (and, for `StatusHandler`, the commit's owning stack) belongs to that same verified organization before any handler runs, rejecting the request otherwise. Additionally, `StatusHandler` should scope its `Commit` lookup by the verified repository rather than matching bare SHA across the entire instance.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgTrusted` (has commits deployed by real victim project) and `OrgUnsecured` (installed but `webhook_secret` left blank, per documented optional config).
2. As an anonymous attacker, `POST /github/webhooks` with header `X-Github-Event: status` and any/garbage `X-Hub-Signature`:
```json
{
  "repository": {"owner": {"login": "OrgUnsecured"}, "full_name": "OrgUnsecured/anything"},
  "sha": "<victim commit sha in OrgTrusted's stack>",
  "state": "success",
  "context": "ci/forged",
  "branches": [{"name": "master"}]
}
```
3. `verify_signature` resolves `repository_owner` to `OrgUnsecured`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the forged signature is accepted.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit belonging to `OrgTrusted`'s stack, and calls `create_status_from_github!`, injecting a fabricated "success" status.
5. If this flips the commit's `simple_state` to success, `stack.schedule_merges` fires on the victim stack, potentially merging/deploying code without any genuine CI signal — achieved entirely without credentials for `OrgTrusted`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
