## Confirmed root cause and binding break

`WebhooksController#verify_signature` selects **which GitHub App/organization secret** to validate the HMAC signature with by reading a field from the **unauthenticated, attacker-supplied JSON body itself**: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Then `Shipit.github(organization: repository_owner)` looks up per-org config, and `verify_webhook_signature` is applied: [3](#0-2) . Critically, `return true unless webhook_secret` means **any organization configured without a `webhook_secret` (nil is the documented default in `secrets.development.example.yml`) causes signature verification to unconditionally pass**, regardless of the actual `X-Hub-Signature` header.

Meanwhile, the actual object that gets written/acted upon by the event handler is resolved from a **different, independently-controlled field of the same JSON body**: `payload.dig('repository', 'full_name')`, used to look up the `Repository`/`Stack` that the handler mutates: [4](#0-3) 

So the equality that should hold is:
`organization authenticated via repository.owner.login/organization.login` == `organization implied by repository.full_name that the handler writes to`

In a legitimate GitHub-originated payload these two fields are consistent by construction (GitHub itself fills both from the same repo). But since the webhook endpoint is unauthenticated public HTTP and the entire JSON body is attacker-controlled, nothing in Shipit enforces this equality — an attacker can submit `repository.owner.login` = an organization Shipit has configured *without a webhook_secret* (a supported, documented configuration per `test/dummy/config/secrets_double_github_app.yml` and `secrets.development.example.yml`, where `webhook_secret:` is explicitly commented as `# nil`), while setting `repository.full_name` to point at a **completely different repository/organization** that Shipit also tracks (with its own, secret-protected GitHub App).

This lets an unprivileged network attacker with no token, no `webhook_secret`, and no repository access forge events (`status`, `push`, `check_suite`, etc.) against a stack belonging to an entirely different, secured organization, because verification is keyed on the wrong field.

### Concrete high-impact instance: forged `status` events

`StatusHandler` directly updates any `Commit` matching an attacker-chosen `sha` with an attacker-chosen `state`/`context`, with zero relation to which org's secret was checked: [5](#0-4) . If the attacker sets `repository.owner.login` to the no-secret org while providing the sha of a commit belonging to the secret-protected stack, they can mark that commit "success" for the CI context Shipit expects, i.e., make it `deployable?`. Combined with `continuous_deployment` (`Stack.schedule_continuous_delivery`), this can trigger an **unauthorized deploy** of a commit whose CI status was never actually verified by the real GitHub App — a Critical-tier impact per the given rules.

### Title
Webhook signature verification keyed on `repository.owner.login`/`organization.login` from the unauthenticated payload, while handlers act on the independently-controlled `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/org whose secret is used to validate `X-Hub-Signature` based on `repository.owner.login` (or `organization.login`) taken straight from the unauthenticated JSON body. All webhook handlers, however, resolve the repository/stack they mutate from `repository.full_name`, a separate field of that same attacker-controlled body. No code enforces that these two fields refer to the same organization/repository.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` purely from request JSON and uses it to fetch the corresponding `GitHubApp` (`Shipit.github(organization: repository_owner)`), then checks the signature against that org's `webhook_secret`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) trivially returns `true` when the resolved org has no `webhook_secret` configured — a supported/documented state (see `config/secrets.development.example.yml:11`, `test/dummy/config/secrets_double_github_app.yml:7,46`).
- `Shipit::Webhooks::Handlers::Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and all handlers (`PushHandler`, `StatusHandler`, etc.) resolve the target `Repository`/`Stack`/`Commit` from `repository.full_name` — a value never checked against `repository_owner`.
- Because the whole HTTP body is fully attacker-controlled (no header/URL-bound org, no signature yet at the time these values are read), an attacker can decouple "the org whose secret authorizes this request" from "the repository/stack actually mutated."

### Impact Explanation
An unprivileged, unauthenticated network attacker can spoof high-trust GitHub webhook events (e.g., commit `status`) for stacks belonging to organizations that are otherwise properly protected by a `webhook_secret`, by borrowing the identity of any other organization configured in the same Shipit instance that lacks a secret. This can force arbitrary commits to appear CI-green (`deployable?`), enabling continuous-delivery pipelines to perform an unauthorized deploy of unverified code — meeting the "unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Requires: (1) the target Shipit instance hosts multiple GitHub organizations (a documented, supported multi-org configuration), and (2) at least one configured organization lacking a `webhook_secret`. Both conditions are explicitly supported/documented defaults (`webhook_secret: # nil`), making this a realistic misconfiguration rather than a theoretical one. No credentials, tokens, or repository access are needed by the attacker — only knowledge of a shipit instance's public webhook endpoint and any org name it manages without a secret.

### Recommendation
Verify the signature using the webhook secret associated with the repository that will actually be acted upon (derived consistently from `repository.full_name`, matched against the `Repository` record's known owner/org), not a value read independently from the request body. Additionally, do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for multi-org configurations — require every configured organization to have a `webhook_secret`, and reject events whose claimed owner does not match the actual owner encoded by `repository.full_name`.

### Proof of Concept
1. Shipit is configured with two orgs: `no-secret-org` (no `webhook_secret`) and `secured-org` (has `webhook_secret`), both tracked (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker (no credentials) POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {"owner": {"login": "no-secret-org"}, "full_name": "secured-org/victim-repo"},
  "sha": "<victim commit sha under secured-org>",
  "state": "success",
  "context": "<ci context expected by secured-org stack>"
}
```
No valid `X-Hub-Signature` is required, because `Shipit.github(organization: "no-secret-org")` has `webhook_secret` nil, so `verify_webhook_signature` returns `true` unconditionally.
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) finds the `Commit` by `sha` (belonging to `secured-org`'s stack) and calls `create_status_from_github!`, marking it green.
4. If `secured-org`'s stack has `continuous_deployment: true`, this can trigger an automatic, unauthorized deploy of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
