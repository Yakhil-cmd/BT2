### Title
`MembershipHandler#find_or_create_team!` matches teams by `github_id` alone, letting membership webhooks from any Shipit-configured organization mutate a team owned by a different organization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Team.find_or_create_by!(github_id: params.team.id)` in `find_or_create_team!` only sets `team.organization`/`github_team=` inside the `find_or_create_by!` block, which runs only on creation. If a `Shipit::Team` with that `github_id` already exists, the existing record (belonging to whatever organization originally created it) is returned unmodified, and `process` then calls `team.add_member(User.find_or_create_by_login!(params.member.login))` without ever comparing `params.organization.login` to `team.organization`. Any organization the operator has configured with a `webhook_secret` in `Shipit.github` can therefore add arbitrary GitHub logins to a team that belongs to a completely different organization, as long as it guesses/knows that team's numeric `github_id`.

### Finding Description
The intended binding is: `Membership` row exists for `Team` T ⇔ GitHub actually reports T's own organization added that member to T, i.e. `params.organization.login == team.organization`. That equality is never checked.

Path traced:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` from `params.dig('organization','login')` for membership events (no `repository` key present) and calls `Shipit.github(organization: repository_owner)`. This only proves the payload was signed with the secret configured for whatever organization name the attacker put in `organization.login` — it does not tie that organization to any specific `Team`. [1](#0-0) 
2. `MembershipHandler#process` calls `find_or_create_team!`, then unconditionally `team.add_member(member)` for `action == 'added'`. [2](#0-1) 
3. `find_or_create_team!` uses `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }`. The block only executes on **creation**. If a `Team` row with that `github_id` already exists (created originally by a different organization via `Team.find_or_create_by_handle`/`fetch_and_create_from_github`, app/models/shipit/team.rb:17-27), it is returned as-is, and the attacker's `organization.login` is discarded. [3](#0-2) 
4. `Team#add_member` unconditionally appends the member. [4](#0-3) 
5. `User#authorized?` grants access based purely on membership rows for teams in `Shipit.github_teams`, with no re-validation against GitHub. [5](#0-4) 

Root cause: `find_or_create_by!` is keyed only on `github_id`, and no post-lookup guard re-asserts `team.organization == params.organization.login` before mutating membership. None of the existing guards (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema) check this cross-field consistency — they validate signature-of-payload and payload shape, not organization/team ownership.

Precondition required for this to be exploitable: the attacker must control (own, or have been granted webhook credentials for) a GitHub organization that the Shipit operator has already configured in `secrets.github` with its own `webhook_secret`/app entry (`Shipit.github_app_config`), and must know/guess the target `github_id` of a `Team` already registered under a different organization (the question posits this is discoverable via the `team_handles` list rendered in the 403 message from `force_github_authentication`, though that message discloses `handle` strings like `org/slug`, not the internal numeric `github_id` — the numeric id is not directly exposed there, so the attacker would need to independently learn or brute-force the `github_id`, which is a real but non-trivial precondition).

### Impact Explanation
If exploited, an attacker with access to any second, lower-trust GitHub organization configured in Shipit gains a `Shipit::Membership` row on a privileged `Team` they were never actually added to on GitHub, which flips `current_user.authorized?` to `true` in `Authentication#force_github_authentication`, bypassing Shipit's authorization gate entirely. This is a genuine authentication/authorization-bypass path (matches the "escalation into `Shipit.github_teams` authorization" / "authentication bypass" categories) and is repeatable per webhook, for any team whose `github_id` the attacker can obtain, across the whole Shipit instance (not scoped to one repository/stack).

### Likelihood Explanation
Exploitability is gated by two non-trivial preconditions: (1) the operator must have configured a second organization in `Shipit.github` (multi-org Shipit deployments with per-org webhook secrets are a supported but non-default configuration — `github_default_organization`/`github_app_config` in lib/shipit.rb), and (2) the attacker must obtain the target team's numeric `github_id`, which is not directly leaked by the cited 403 message (that only lists `team_handles`, i.e., `organization/slug` strings, via `Shipit.github_teams.map(&:handle)`). Given precondition (1), which the question stipulates as given ("even a throwaway org set up by an operator for testing"), the core code defect — matching solely on `github_id` with no organization cross-check on update — is real and directly reachable once the id is known.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify organization ownership on every event, not just at creation: look up the team by `github_id`, and if it exists, assert `team.organization == params.organization.login` (case/downcase-normalized) before proceeding, raising/dropping the event otherwise (mirroring how `Team.find_or_create_by_handle` scopes by `organization` and `slug` together). Alternatively, scope the `find_or_create_by!` query itself on both `github_id` and `organization`.

### Proof of Concept
Minitest plan (test/models/shipit/webhooks/handlers/membership_handler_test.rb — illustrative, not part of this engine's shipped tests):
```ruby
test "membership webhook from foreign organization mutates existing team's membership" do
  team = shipit_teams(:shipit) # existing team, e.g. organization: "shopify"
  attacker = shipit_users(:walrus) # unprivileged, not a member of `team`

  payload = {
    action: 'added',
    team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url },
    organization: { login: 'attacker-org' }, # differs from team.organization ("shopify")
    member: { login: attacker.login }
  }

  assert_not_equal 'attacker-org', team.organization

  assert_difference('Shipit::Membership.count') do
    Shipit::Webhooks::Handlers::MembershipHandler.new(payload).call
  end

  assert team.reload.members.include?(attacker)
  assert attacker.authorized? if Shipit.github_teams.include?(team)
end
```
Both sides of the equality (`params.organization.login` = `"attacker-org"` vs `team.organization` = `"shopify"`) diverge and remain unreconciled after the handler runs, confirming the missing check.
