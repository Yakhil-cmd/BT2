## Analysis

The `[M-07]` report is about a guard/state binding that is checked using one identity (`lastTokeCycleIndex`/`currentCycleIndex`) while the actual amount that gets acted upon (`requestWithdrawalAmount`) is bound to a different, broader scope — so the check that's supposed to gate an action doesn't actually cover everything the action later touches. The reusable bug class is: **the entity that authorizes an action is not the same entity the action is actually scoped/applied to.**

The strongest analog in this engine is in the CCMenu API endpoint, where the entity that *authorizes* the request (the `ApiClient`'s own `stack_id` scope) is never the entity the controller action actually *touches* (`params[:stack_id]`).

### Root cause

`Shipit::Api::BaseController` defines the correct, scoped lookup: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to a single stack, and `stack` resolves `params[:stack_id]` only within that restricted relation — this is how every other stack-scoped API controller (`StacksController`, `DeploysController`, `TasksController`, etc.) enforces the binding "token’s authorized stack == stack touched".

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass that scoping entirely: [2](#0-1) 

`require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which checks the operation/scope string, never the specific stack ID: [3](#0-2) 

So the binding that should hold is:
`ApiClient.stack_id (the stack the token authorizes) == stack (the stack the request touches)`

But `CCMenuController#stack` resolves directly via `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks` relation, breaking that equality. Any client token that has `read:stack` permission — including one legitimately created and scoped to a single stack (e.g. via `CCMenuUrlController#client`, which mints a `stack_id`-scoped, `read:stack`-only client) — can supply an arbitrary `stack_id` and read that stack's status instead of its own: [4](#0-3) 

### Title
Stack-scoped API token can read the CCMenu status of any stack, bypassing its `stack_id` authorization scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` resolver used by every other stack-scoped API endpoint, and looks up `params[:stack_id]` directly against `Stack.from_param!` instead of the client's authorized `stacks` relation. This lets a token that is deliberately restricted to a single stack read the build/lock/deploy status of any other stack in the installation.

### Finding Description
`Shipit::Api::BaseController#stacks` computes the set of stacks an `ApiClient` may act on: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [5](#0-4) , and `#stack` resolves the `stack_id` request param only inside that set [6](#0-5) . This is the mechanism that binds "the stack a token authorizes" to "the stack the request touches" across all stack-scoped API controllers.

`CCMenuController` opts out of this binding by redefining `stack`:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [7](#0-6) 

`require_permission :read, :stack` only enforces that the token carries the `read:stack` permission string via `ApiClient#check_permissions!` [3](#0-2) ; it never verifies that the resolved `stack` matches `current_api_client.stack_id`. Consequently, a token that was minted scoped to Stack A (e.g. the "CCMenu Client" created per-stack by `CCMenuUrlController#client` [8](#0-7) ) is fully valid for `GET /api/:stack_id/ccmenu` requests for Stack B, C, D, … — anything reachable via `Stack.from_param!`.

### Impact Explanation
This is an authorization-scope bypass: an attacker who obtains one legitimate, narrowly-scoped `read:stack` CCMenu token (which are handed out fairly liberally, e.g. embedded in CI dashboard integration URLs) can enumerate `stack_id` params and read `lastBuildStatus`, `lastBuildLabel` (commit SHA), `activity`, lock status, and stack `name`/`webUrl` for every stack in the Shipit instance, not just the one the token was issued for. This matches the "unauthenticated [into a scope the client does not hold] read of stack state" class of High severity issue: the read is authenticated, but not authorized for the target stack, which is exactly the equality the rules call out — "a stack a token authorises versus a stack it touches."

### Likelihood Explanation
Any holder of a valid, stack-scoped API token (which by design is meant to be safely embeddable in CI dashboards per `CCMenuUrlController`) can trivially exploit this by changing the `stack_id` path/query parameter — no privileged access, no additional credentials, and no interaction with a maintainer is required beyond possessing one legitimate token.

### Recommendation
Have `CCMenuController#stack` reuse the base `stacks` scoping (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the resolved stack is restricted to `current_api_client.stack_id` exactly like every other stack-scoped API controller.

### Proof of Concept
1. Create Stack A and Stack B in the same Shipit instance.
2. As a logged-in user with access only to Stack A, visit its CCMenu integration page to mint a scoped token: `GET /stacks/:owner/:repo-a/:env/ccmenu_url` → returns `ccmenu_url` containing `token=<TOKEN_A>`, where `TOKEN_A`'s underlying `ApiClient` has `stack_id = StackA.id` and permissions `['read:stack']` (see `CCMenuUrlController#client` [8](#0-7) ).
3. Using `TOKEN_A`, request `GET /api/:owner/:repo-b/:env/ccmenu.xml?token=TOKEN_A` (Stack B's id/param, not Stack A's).
4. `CCMenuController#authenticate_api_client` authenticates `TOKEN_A` successfully [9](#0-8) ; `require_permission :read, :stack` passes because `TOKEN_A` does have `read:stack` [3](#0-2) ; `#stack` resolves Stack B directly via `Stack.from_param!` [7](#0-6) , and Stack B's build status/commit/lock info is rendered to the requester, who was never granted access to Stack B.

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
