### Title
Signature-authenticating `repository.owner.login` is decoupled from the target-selecting `repository.full_name`, letting a no-secret-org attacker forge `pull_request` events that mutate another repository's review stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates the request using `Shipit.github(organization: repository_owner)` where `repository_owner` is `params.dig('repository','owner','login')`, but returns `true` unconditionally when that organization's `GitHubApp` config has a blank `webhook_secret` [1](#0-0) [2](#0-1) . Every downstream `PullRequest` handler, including `LabelCapturingHandler`, resolves the *target* repository independently via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , a field the ExplicitParameters schema requires but never cross-checks against `repository.owner.login` [4](#0-3) . This lets an attacker who controls (or names) a GitHub organization configured in Shipit without a `webhook_secret` forge a request whose `repository.owner.login` matches that unauthenticated org, while `repository.full_name` names an arbitrary victim repository/stack.

### Finding Description
The broken binding: the code implicitly assumes `authenticated_organization == target_repository.owner`, i.e. that the organization used to verify the signature (`repository.owner.login`) is the same organization that owns the repository the handler mutates (`repository.full_name`'s owner segment). This is never enforced.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)` [5](#0-4) .
2. `GitHubApp#verify_webhook_signature` returns `true unless webhook_secret` — i.e. if the org configured under `repository_owner` has no `webhook_secret`, the raw body is accepted with no HMAC check whatsoever [2](#0-1) .
3. `WebhooksController#create` parses the body and dispatches it to all handlers for the event, unconditionally passing the full `params` hash (including whatever `repository.full_name` the attacker chose) [6](#0-5) .
4. `LabelCapturingHandler#repository` and `#review_stack` look up the target repository/stack purely from `params.repository.full_name`, completely independent of the `repository.owner.login` value used in step 1 [7](#0-6) .
5. For `action == "reopened"` on a non-archived stack, `reopened_active_stack?` is satisfied and `capture_labels` runs `pull_request.update!(labels: params.pull_request.labels.map(&:name))` on the victim stack's `PullRequest` record [8](#0-7) [9](#0-8) .
6. `ReviewStack#env` uppercases each captured label name into an environment variable set to `"true"` merged into the stack's deploy environment [10](#0-9) , and this attacker-controlled label set is what an operator's `blocking_statuses` configuration (via `Status`/`Commit#blocked?`-style checks) can be made to key off of, or otherwise poison the state consumed at deploy time.

Exploit flow: attacker registers/owns a GitHub organization `attacker-org` that a Shipit operator has configured in `Shipit.github_organizations` (or similar) without a `webhook_secret` (a legitimately supported but insecure configuration state — the "no-secret organization" gap). Attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, body `{"action":"reopened","number":N,"pull_request":{...,"labels":[{"name":"ATTACKER_LABEL"}]},"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`. Because `attacker-org` has no `webhook_secret`, `verify_signature` passes with zero signature validation. `LabelCapturingHandler` then resolves `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` and, if a matching open review-stack `PullRequest` with number `N` exists and is not archived, overwrites its `labels` column with attacker-chosen values.

Why existing guards fail: `drop_unhandled_event` only checks the event type is registered, not the payload's internal consistency [11](#0-10) . The `ExplicitParameters` schema for `LabelCapturingHandler` requires `repository.full_name` as a `String` but does not require or validate `repository.owner.login` at all, nor cross-check it against the value used for signature verification [4](#0-3) . `Repository.from_github_repo_name` performs a plain DB lookup with no ownership/authentication check tied to the request's authenticated organization [12](#0-11) .

### Impact Explanation
An unauthenticated/unprivileged attacker can write to another organization's `PullRequest.labels` record purely by controlling an unrelated, no-secret-configured GitHub organization — a payload for one repository mutates another repository's stack/record. Because `ReviewStack#env` maps these attacker-controlled labels directly into uppercased environment variables merged into the deploy environment, and the victim stack has `blocking_statuses` configured, this state can influence which statuses/environment flags gate `blocked?`/deploy behavior for the victim's review stack. This is a cross-tenant state manipulation matching the "Critical - a payload for one repository mutating another's stack" category. It is repeatable against any victim repository/PR number as long as the attacker can identify or open a PR whose associated `ReviewStack`/`PullRequest` record exists, and as long as at least one Shipit-configured GitHub organization lacks a `webhook_secret`.

### Likelihood Explanation
Preconditions: (1) Shipit operator has configured at least one GitHub organization without a `webhook_secret` (a real, documented misconfiguration risk given the code explicitly special-cases "no secret" as "verified"), (2) the victim repository has review stacks enabled with an open, non-archived PR/stack matching the forged `number`, and (3) `blocking_statuses` is configured on that stack for amplification. Attacker cost is a single unauthenticated HTTP POST with no GitHub secrets, no session, no API token — fully within the stated unprivileged attacker capabilities. It is trivially repeatable.

### Recommendation
Verify that the organization used to authenticate the webhook (`repository.owner.login` used in `verify_signature`) matches the organization segment of `repository.full_name` used by every handler before dispatching, or better, pass the authenticated organization into the handler context and require the resolved `Repository`'s `owner` to equal it. Additionally, treat a missing `webhook_secret` as "reject" (or require secret configuration) rather than "auto-verified", since `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` effectively disables authentication for any org lacking a secret.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure two orgs in `Shipit.github_organizations` (or stub `Shipit.github`): `"attacker-org"` with `webhook_secret: nil`, and `"victim-org"` with a real `webhook_secret`.
2. Create `victim_repo = Repository.create!(owner: "victim-org", name: "victim-repo")`, a `ReviewStack` for it with `provisioning_behavior_allow_all` (or matching config so it's not archived), and an associated `PullRequest` with `number: 42`, `labels: []`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request` and no/garbage `X-Hub-Signature`, body:
```json
{
  "action": "reopened",
  "number": 42,
  "pull_request": { "...": "...", "labels": [{"name": "malicious_flag"}] },
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "sender": {"login": "attacker"}
}
```
4. Assert response is `200 OK` (not `422`), proving signature verification was bypassed.
5. Assert `PullRequest.find_by(stack: victim_stack).reload.labels == ["malicious_flag"]` — the equality `authenticated_organization ("attacker-org") == target_repository.owner ("victim-org")` is false, yet the write to `victim-org/victim-repo`'s `PullRequest` succeeded, proving the binding is broken and cross-tenant mutation occurred.
6. Optionally assert `victim_stack.env["MALICIOUS_FLAG"] == "true"` to demonstrate downstream environment/deploy-gating impact.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
