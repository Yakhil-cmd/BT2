### Title
Cross-organization commit-status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary

### Finding Description
The reported bug class is a binding break: a value that is *used* to decide something is not the same value that is *verified*. In `Vault.sol` the interest computation used raw TCAP/collateral amounts without applying the decimals verified/expected by the oracle, breaking the equality between "amount charged" and "amount actually owed."

The same class of bug exists in shipit-engine's webhook trust model. `WebhooksController#verify_signature` selects which GitHub App (and therefore which HMAC `webhook_secret`) to use for verifying a payload based on the organization named *inside the untrusted payload itself*: [1](#0-0) [2](#0-1) 

This only proves that *the payload was signed by the organization named in `repository.owner.login`/`organization.login`*. It says nothing about which repository/commit the payload's other fields will actually cause Shipit to mutate.

`Shipit::Webhooks::Handlers::StatusHandler`, which processes the `status` event, never re-derives or checks the organization/repository that was used for signature verification. It looks up commits **globally by `sha`**, with no scoping to the repository/stack that the signed payload's `repository` object refers to: [3](#0-2) 

Compare this to `Handler#stacks`, which *is* scoped to `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`, and is used by `PushHandler`: [4](#0-3) [5](#0-4) 

`StatusHandler` skips this scoping entirely — the `sha` from the payload is matched against **every `Commit` row in the database**, across every stack, repository, and organization tenant Shipit is configured for (Shipit explicitly supports multiple GitHub organizations sharing one instance, each with its own `webhook_secret`, per `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`):


The equality that should hold is:
`organization whose webhook_secret verified the signature == organization owning the repository/commit that create_status_from_github! mutates`

`StatusHandler` breaks this: it only guarantees the former, but acts on *any* commit sha it's told about, regardless of which org/repo it belongs to.

### Impact Explanation
An entity that legitimately administers **any one** GitHub organization connected to a shared Shipit instance (and therefore knows that org's `webhook_secret`, since GitHub App owners set/see it themselves) can:
1. Sign an arbitrary JSON body with their own org's `webhook_secret`.
2. Set `repository.owner.login` to their own org, so `WebhooksController#verify_signature` selects and passes with their own secret.
3. Set `event: status` with a `sha` equal to a real commit SHA belonging to a **completely different organization's stack** hosted on the same Shipit instance (git SHAs are public/knowable via GitHub).

`StatusHandler#process` will then call `commit.create_status_from_github!` on that foreign commit, forging any `state`/`context`/`target_url`/`description` for it — including `state: "success"`.

This directly feeds `Commit#deployable?` and the merge-queue/CD gating logic: [6](#0-5) 
and triggers `stack.schedule_merges`/`ProcessMergeRequestsJob` on state transitions: [7](#0-6) 

A forged `success` status on a victim org's commit can make that commit `deployable?` and eligible for the merge queue (`allows_merges?`) even though the real CI never passed, resulting in an **unauthorized deploy or merge** on a repository/organization the attacker does not control — satisfying the Critical "unauthorized deploy, rollback or merge" criterion.

### Likelihood Explanation
This requires only an unprivileged-relative-to-victim attacker: legitimate admin access to *any single* org onboarded to a shared Shipit instance (a normal, expected actor, not a Shipit session, `ApiClient` token, or GitHub App private key holder for the victim org). No cross-tenant credential or privilege escalation on GitHub itself is needed — the flaw is entirely in Shipit's own webhook-to-commit binding.

### Recommendation
In `StatusHandler` (and any other handler that doesn't already scope through `Handler#stacks`), restrict the `Commit` lookup to commits belonging to the repository named in the verified payload, e.g. `Commit.where(sha: params.sha, stack_id: stacks.pluck(:id))`, or alternatively have `WebhooksController` resolve and pass the authenticated `Repository`/org down to handlers so no handler can act outside the org whose signature was verified.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as supported by `config/secrets.yml`'s multi-org format).
2. As the legitimate owner/admin of `OrgA`'s GitHub App, obtain `OrgA`'s `webhook_secret`.
3. Find a public commit SHA that exists in `OrgB`'s tracked repository/stack (e.g. from GitHub's public commit history).
4. Craft:
```json
{
  "sha": "<OrgB's real commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/whatever" }
}
```
5. Sign the raw body with `OrgA`'s webhook secret, POST to `/webhooks` with `X-Github-Event: status` and the resulting `X-Hub-Signature`.
6. `verify_signature` selects `Shipit.github(organization: "OrgA")` and passes. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — finds and updates OrgB's commit — creating a forged success status that can trigger `OrgB`'s merge queue/deploy eligibility despite the attacker never having access to OrgB.
