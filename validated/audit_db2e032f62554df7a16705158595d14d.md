### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook from one repository mutate commit status on another tenant's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire `commits` table and calls `create_status_from_github!` on every match, without ever checking that the matched commit's `stack.repository` corresponds to the `repository` named in the webhook payload. Because the base `Handler` class already provides a repository-scoped `stacks` helper (used by other handlers such as push/pull-request handlers) but `StatusHandler` never calls it, a correctly signed status webhook for one repository (public repo C) can flip the CI status of an identical-SHA commit that also exists in an unrelated stack (private repo D), regardless of ownership.

### Finding Description
The binding that should hold is: `payload.dig('repository', 'full_name') == commit.stack.repository.full_name` for every `commit` whose status is mutated by a status webhook. In `StatusHandler#process`: [1](#0-0) 

the code does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. It never calls `repository_name` / `stacks` (defined in the base class specifically for this purpose): [2](#0-1) 

so the equality above is never checked — the actual predicate applied is only `commit.sha == params.sha`, which is a strictly weaker condition than the intended repository-bound one.

`WebhooksController#verify_signature` only verifies that the request was signed with the webhook secret configured for `repository_owner` (`params.dig('repository','owner','login')`): [3](#0-2) [4](#0-3) 

This confirms the *identity* of the sending org (org C, the attacker's own onboarded org/repo), but does nothing to constrain which `Commit` rows the handler is allowed to touch — that constraint is supposed to live in the handler itself via `stacks`/`repository_name`, and `StatusHandler` omits it.

**Exploit flow:**
1. Attacker owns/controls repository C (any GitHub org/repo already integrated with this Shipit instance, e.g. a public fork or upstream of the victim's private repository D). Private stack D contains a `Commit` row with `sha = X` (e.g., a shared history/fork-point commit, or a cherry-picked commit that is byte-identical, hence same SHA, in both repos).
2. Attacker uses GitHub's own Status API (or simply triggers CI) on repository C for commit `X` with `state: success`. GitHub sends a `status` webhook to Shipit, correctly signed with org C's `webhook_secret`, naming `repository.full_name = "attacker/C"`.
3. `verify_signature` passes (org C's secret matches). `StatusHandler.call(payload)` runs.
4. `StatusHandler#process` executes `Commit.where(sha: "X")`, which returns **both** the commit row belonging to repo C's stack **and** the row belonging to private stack D, because the query is unscoped by repository/stack.
5. `commit.create_status_from_github!(params)` is invoked on the stack-D commit too, writing a forged `success` status onto a private stack the attacker has no relationship with.

No existing guard prevents this: `verify_signature` authenticates the sender org, not the target stack; `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not their relationship to any stack; there is no `require_permission!`/`stacks` scoping call anywhere in this handler.

### Impact Explanation
A forged `success` status on a private stack's commit is a real, security-relevant write: `Commit#status` feeds `deployable?`, and `add_status` explicitly triggers `stack.schedule_merges` and the `deployable_status`/`commit_status` hooks when status changes: [5](#0-4) 

If the victim stack has `continuous_deployment?` enabled, `schedule_continuous_delivery` can fire off an actual deploy/merge for a commit whose real CI never passed, purely because an unrelated, attacker-controlled repository claimed success for a colliding SHA. This is a cross-tenant write — "a payload for one repository mutating another's stack/commit" — matching the Critical severity bucket (unauthorized deploy/merge triggered from a forged webhook belonging to a different repository). It is repeatable against any stack/commit whose SHA the attacker can reproduce or already knows (shared history between a public upstream and a private fork is common and easy to enumerate via `git log`).

### Likelihood Explanation
Preconditions: the attacker's own repository/org must already be integrated with the Shipit instance (a normal, unprivileged onboarding state for any org using this Shipit deployment — not a Shipit secret or elevated role), and the attacker needs a commit SHA that is present in both their own repo and the victim's private stack. This is realistic for fork-based workflows: private forks share commit history with the public upstream by construction, and attackers can also craft byte-identical commits (same tree/parent/author/committer timestamps/message) to force an arbitrary SHA collision with a specific target commit if they can inspect it (e.g., leaked via other tooling) or simply rely on shared ancestor commits. No GitHub/Shipit secret, session, or API token is required — only the ability to make GitHub emit a legitimately signed status webhook for a repo the attacker already controls.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository that sent the webhook, mirroring the `stacks` pattern used elsewhere in the codebase, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently join through `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_id: stacks.pluck(:repository_id) })`, ensuring only commits belonging to the repository named in `payload['repository']['full_name']` (already verified against the signing org) can have their status mutated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook for repo C cannot mutate a commit belonging to a different repository's stack" do
  attacker_stack = shipit_stacks(:shipit) # belongs to repository "attacker/C"
  victim_stack   = Shipit::Stack.create!(repository: shipit_repositories(:victim_private_repo)) # "victim/D"

  shared_sha = "a" * 40
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus))
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus))

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/C', 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding under test: only the commit belonging to the payload's repository should be updated.
  assert_equal 'success', attacker_commit.reload.status.state  # expected to pass
  refute_equal 'success', victim_commit.reload.status.state    # FAILS on current code: victim_commit also becomes "success"
end
```
This demonstrates that a webhook payload naming `attacker/C` mutates `victim_commit`, which belongs to stack `victim/D`, proving the binding `payload.repository.full_name == commit.stack.repository.full_name` is not enforced by `StatusHandler#process`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret
