### Title
Webhook signature verification keys off `repository.owner.login` while event handlers act on the unrelated `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the inbound HMAC against using `repository.owner.login` (or `organization.login`), while every event handler (`Shipit::Webhooks::Handlers::Handler#stacks`) resolves the repository/stack to mutate using the completely independent `repository.full_name` field from the same JSON body. [1](#0-0) [2](#0-1)  Because these two fields are never checked for consistency, and because `verify_webhook_signature` unconditionally returns `true` whenever the selected app's `webhook_secret` is blank (a documented "optional" configuration value), an unauthenticated caller can pick an organization with no configured secret to short-circuit signature verification, then point `repository.full_name` at a completely different, secret-protected repository/stack to drive its webhook side effects. [3](#0-2) 

### Finding Description
This mirrors the audited bug class: a field that gates a security check (`repository.owner.login`, analogous to the "founder" check) versus the field the resulting logic actually operates on (`repository.full_name`, analogous to unchecked "non-founder" state) — the check and the effect are bound to different, independently attacker-controlled inputs.

1. `WebhooksController#verify_signature` computes `repository_owner` from the untrusted, unsigned JSON body:
   ```ruby
   def repository_owner
     params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
   end
   ```
   and uses it purely to pick the `GitHubApp` instance (and hence the `webhook_secret`) used to validate `X-Hub-Signature`. [4](#0-3) [5](#0-4) 

2. `GitHubApp#verify_webhook_signature` treats a blank/unset `webhook_secret` as automatic success:
   ```ruby
   def verify_webhook_signature(signature, message)
     return true unless webhook_secret
     ...
   end
   ```
   `webhook_secret` is explicitly documented as optional per-organization configuration. [3](#0-2) [6](#0-5) 

3. Once verification "passes" (trivially, because the *selected* org has no secret), `Shipit::Webhooks.for_event(event)` runs the corresponding handler on the *raw, unmodified* `params`, i.e., the exact same body the attacker crafted. [7](#0-6) 

4. Every handler resolves the target `Stack`/`Repository` using `repository.full_name`, a field never compared against `repository.owner.login`:
   ```ruby
   def stacks
     @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
   end

   def repository_name
     payload.dig('repository', 'full_name')
   end
   ``` [2](#0-1) 

   `PushHandler#process` will then enqueue `GithubSyncJob` for any stack matching that `full_name`/branch, causing Shipit to re-fetch commits and cache deploy specs for a target repository whose real webhook secret the attacker never had to know. [8](#0-7)  `StatusHandler` similarly writes commit statuses using unrelated repository fields keyed by `full_name`.

Concretely: an attacker with zero credentials sends one POST to the public `/webhooks` endpoint (no session, no `ApiClient`, no GitHub App key required) with:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-with-no-webhook-secret" },
    "full_name": "victim-org/protected-repo"
  }
}
```
and header `X-Github-Event: push`. `repository_owner` resolves to `org-with-no-webhook-secret`, whose `GitHubApp#verify_webhook_signature` returns `true` unconditionally (no secret configured), so `head(422)` is never sent. The `PushHandler` then acts on `victim-org/protected-repo` (a fully different, secret-protected organization's tracked stack), triggering `GithubSyncJob` and downstream deploy-spec caching/re-sync for a stack the attacker has no legitimate relationship to. [9](#0-8) [10](#0-9) 

This is exactly the class of binding break called out in scope: "an organization that authenticated versus the repository that is written."

### Impact Explanation
This grants an unauthenticated attacker the ability to forge arbitrary GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against any stack/repository tracked by the Shipit instance, as long as at least one configured GitHub App/organization omits `webhook_secret` (a supported, documented configuration). Reachable consequences include: forcing unscheduled `GithubSyncJob` runs and cache invalidation on arbitrary stacks, injecting forged commit statuses via `StatusHandler`, and forging `membership` events that call `Team#add_member`/`members.delete` on arbitrary teams — which, combined with `User#authorized?`'s reliance on `teams.where(id: Shipit.github_teams...)`, can escalate an attacker-controlled `User` record into a team gating access to the whole Shipit UI. [11](#0-10) [12](#0-11)  This meets the "High" bar: escalation into `Shipit.github_teams` authorization and unauthenticated forcing of stack state changes.

### Likelihood Explanation
Requires only that the deployment configures at least two GitHub organizations (a documented, supported "Using Multiple GitHub Applications" setup) where at least one has `webhook_secret` left blank (explicitly documented as optional). Given the endpoint is public and unauthenticated by design (it must accept GitHub's webhooks), and no credential or session is needed, exploitation is straightforward once that configuration condition holds.

### Recommendation
Bind the field used to select/validate the signing secret to the same field used for downstream processing: derive both the "authenticating organization" and the "acted-upon repository" from a single, consistently-verified source (e.g., always use `repository.full_name`'s owner segment for secret selection, or vice versa), and reject requests where `repository.owner.login` and the owner segment of `repository.full_name` diverge. Additionally, do not treat a blank `webhook_secret` as an automatic pass in `GitHubApp#verify_webhook_signature`; require explicit opt-in (e.g., a `Shipit.allow_unsigned_webhooks` flag) rather than silent bypass.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (no `webhook_secret`) and `OrgB` (with a `webhook_secret`), each with tracked stacks (per `docs/setup.md`'s multi-org example). [6](#0-5) 
2. As an unauthenticated attacker, POST to `/webhooks` with `X-Github-Event: push` and body:
   ```json
   {"ref":"refs/heads/master","after":"deadbeef","repository":{"owner":{"login":"OrgA"},"full_name":"OrgB/protected-repo"}}
   ```
   without any valid `X-Hub-Signature` header value matching OrgB's secret.
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` and the request is not rejected. [3](#0-2) 
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/protected-repo")` and enqueues `GithubSyncJob`, mutating OrgB's protected stack state despite never presenting a valid signature for OrgB. [10](#0-9)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
