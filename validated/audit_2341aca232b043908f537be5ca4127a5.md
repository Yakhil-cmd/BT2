### Title
CCMenu API token is never bound to the stack it was issued for, allowing it to read any stack's state - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#client` mints an `ApiClient` with `read:stack` permission but never sets its `stack` association, and `Api::CCMenuController` never checks that a token is scoped to the stack being requested. The result is the exact "stack a token authorises versus a stack it touches" mismatch described in the C4-style bug class: a credential generated for stack A can be replayed to read the state of any stack B in the installation.

### Finding Description
When a user requests a CCMenu URL for a stack, `CCMenuUrlController#client` builds the backing `ApiClient` like this: [1](#0-0) 

Note that `stack:` is never passed to `create_with`/`find_or_create_by!` — only `creator:` and a fixed `name: 'CCMenu Client'`. Because the lookup key is `(creator, name)` and not `(creator, name, stack)`, a single user only ever has **one** "CCMenu Client" `ApiClient` record for their whole account, shared across every stack they generate a CCMenu URL for. That record's `stack_id` column is left `nil`.

`ApiClient#stack` is `belongs_to :stack, optional: true` [2](#0-1) , and the intended scoping mechanism lives in `Api::BaseController`: [3](#0-2) 

`stacks` only restricts the accessible set when `current_api_client.stack_id?` is true. Since the CCMenu client's `stack_id` is `nil`, this scoping never activates for it — the token behaves as unscoped ("global") the moment it is created.

This is compounded by `Api::CCMenuController`, which doesn't even use the scoped `stack` helper from the base controller — it overrides it to look up any stack directly from the request parameter, with no relationship to the authenticated `current_api_client` at all: [4](#0-3) 

`require_permission :read, :stack` [5](#0-4)  only checks the client's `permissions` array (`check_permissions!` in `ApiClient`) [6](#0-5) ; it never compares `current_api_client.stack_id` to `params[:stack_id]`.

**Binding that should hold:** `token.authorized_stack == stack_being_read`.
**Binding that actually holds:** `token.authorized_stack == nil` (unscoped) `≠ stack_being_read` (attacker-controlled request parameter), so any stack in the installation satisfies `show`.

### Impact Explanation
A CCMenu URL is designed to be handed to third-party CI dashboard/status-monitor tooling for a single stack, and is treated as a narrowly-scoped, low-trust credential (it's embedded in a plain URL query string, often stored in less-secured monitoring tools). Because the underlying `ApiClient` is never bound to that stack, possession of one CCMenu token for stack A is sufficient to query `/api/*/ccmenu` for any other stack B by simply changing `stack_id` in the URL — this discloses `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` for stacks the token was never meant to see. This matches the "unauthenticated/unauthorized read of stack state" High-impact category: the credential grants read access far beyond the single stack it was provisioned for.

### Likelihood Explanation
Any authenticated Shipit user who is entitled to fetch a CCMenu URL for one stack (a normal, low-privilege action available from the stack page) automatically receives this over-scoped token — no special permission or race condition is needed. Exploitation is a single authenticated HTTP GET with a different `stack_id` using the token already in hand; the bug is deterministic, not timing-dependent.

### Recommendation
- Persist the `stack` on the `ApiClient` created in `CCMenuUrlController#client` (`ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')`), and include `stack` in the `find_or_create_by!` lookup key so each stack gets its own token.
- In `Api::CCMenuController`, use the scoped `stacks`/`stack` helpers from `Api::BaseController` (or explicitly verify `current_api_client.stack_id == stack.id` when `current_api_client.stack_id?`) instead of resolving the stack directly from `params[:stack_id]`.

### Proof of Concept
1. As an authenticated Shipit user, request the CCMenu URL for stack `org/repoA/production`: `GET /ccmenu/org/repoA/production` → returns `https://.../api/org/repoA/production/ccmenu?token=<TOKEN>`.
2. Inspect the `ApiClient` created: `ApiClient.find_by(name: 'CCMenu Client', creator: current_user).stack_id` is `nil`.
3. Reuse the same `<TOKEN>` against a different, unrelated stack the requester never asked a URL for: `GET /api/org/repoB/staging/ccmenu?token=<TOKEN>`.
4. The request succeeds (HTTP 200) and returns `repoB`'s CI/build status XML, even though the token was only ever issued in the context of `repoA`.
