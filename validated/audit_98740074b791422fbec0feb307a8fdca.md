### Title
Unbounded permanent disk storage of unvalidated joints via `known_bad_joints` (no size cap, no purge) - ([File: joint_storage.js])

### Summary
`CVE-2018-19157` describes a chain-based PoS node that stores attacker-supplied invalid headers/blocks on disk before they are fully validated, letting a low-cost attacker exhaust victim disk space. `ocore` has an analogous pattern: `validation.validate()` performs the unit-hash check *before* any size/complexity limits are enforced, and any joint that fails this early check is persisted forever in the `known_bad_joints` table with no expiry or purge routine, unlike the `unhandled_joints` table which is cleaned up after an hour.

### Finding Description
In `validation.js`, `validate()` checks the unit length and unit hash very early: [1](#0-0) 

Only *after* this hash check does the code apply size/complexity limits (`isTooDeeplyNestedOrHasTooManyNodes`, `isObjectWellFormed`): [2](#0-1) 

This means an attacker can submit a joint whose `unit` field is any 44-character base64 string (passes the length check) but whose content does not hash to that value, and pack the joint with an arbitrarily large/complex `messages`/payload structure. This fails at the "wrong unit hash" check, which calls `callbacks.ifJointError(...)` before the size/nesting guard has a chance to reject the oversized object.

Any `ifJointError` result — reached through `handleJoint()` in `network.js`, which is used uniformly for online joints, saved joints, and **posted joints** — results in the full JSON being written permanently to disk: [3](#0-2) [4](#0-3) 

`handlePostedJoint()` (reachable by any unprivileged unit poster, e.g. a light-wallet client submitting a transaction to a hub) drives the exact same `handleJoint()` path with `bPosted=true`, so this is not limited to “malicious peer” gossip — a normal unit-posting client can trigger it directly: [5](#0-4) 

Crucially, while `unhandled_joints` (used for joints missing parents) is purged after one hour via `purgeOldUnhandledJoints()`: [6](#0-5) 

there is no equivalent purge routine anywhere in the codebase for `known_bad_joints` — every row inserted via `saveKnownBadJoint` is retained indefinitely (only an in-memory cache `assocKnownBadJoints` is populated on startup, but the DB table itself is never trimmed).

### Impact Explanation
Since each malformed joint requires no valid signature, no proof-of-work, no fee payment, and no relationship to the DAG (the hash mismatch is caught before authors/parents/signatures are ever checked), an attacker can repeatedly post syntactically-plausible-but-hash-mismatched joints with large payloads. Each one is written permanently to `known_bad_joints` (`json` column stores the entire joint). Because there is no cleanup, disk usage grows monotonically with attacker-controlled input, eventually exhausting the victim node's storage — a denial of service consistent with the "unable to confirm new units" criterion (a node whose disk fills up can no longer accept/process new units).

### Likelihood Explanation
Likelihood is high: the code path is reachable by any unit poster with no special privileges (light wallet users posting to a hub, or any node accepting units), requires no computational cost to the attacker (no signature or PoW needed to reach the early `ifJointError` branch), and can be repeated indefinitely with unique random 44-character strings as the `unit` field to avoid duplicate-key collisions in `known_bad_joints`.

### Recommendation
- Enforce joint size/complexity limits (`isTooDeeplyNestedOrHasTooManyNodes`, overall JSON size cap) *before* the unit-hash comparison in `validation.js`, so oversized/malformed joints are rejected without ever reaching a persistence path.
- Add a purge/retention policy for `known_bad_joints` similar to `purgeOldUnhandledJoints()` for `unhandled_joints`, or cap the number/size of rows retained (e.g., LRU eviction, TTL, or storing only a hash + truncated snippet instead of the full JSON).
- Consider rate-limiting or requiring minimal proof-of-work/anti-spam cost per posted joint before persisting a copy of a rejected joint's payload.

### Proof of Concept
1. Construct a `joint` object where `unit.unit` is a random 44-character base64 string (satisfies `isStringOfLength(objUnit.unit, constants.HASH_LENGTH)`).
2. Populate `unit.messages` with a very large, deeply-nested-but-not-*too*-deep payload (under the eventual nesting limit, but large in raw byte size) so that `objectHash.getUnitHash(objUnit)` computes without throwing but does not equal `objUnit.unit`.
3. Submit this joint repeatedly via the light-client "post joint" flow handled by `handlePostedJoint()` in `network.js`, or via a `'joint'` justsaying message, each time with a new random `unit` value.
4. Each submission reaches `validate()` in `validation.js`, fails at the "wrong unit hash" check (`validation.js:133-134`), and is written to `known_bad_joints` by `joint_storage.saveKnownBadJoint()` (`joint_storage.js:330-341`) with no expiry.
5. Repeat at scale to grow `known_bad_joints` disk usage without bound, since no purge mechanism exists for that table.

function saveKnownBadJoint(objJoint, error, onDone){
	var joint_hash = objectHash.getJointHash(objJoint);
	const truncatedError = truncate(error);
	assocKnownBadJoints[joint_hash] = truncatedError;
	db.query(
		"INSERT "+db.getIgnore()+" INTO known_bad_joints (joint, json, error) VALUES (?,?,?)",
		[joint_hash, JSON.stringify(objJoint), truncatedError],
		function(){
			onDone();
		}
	);
}
