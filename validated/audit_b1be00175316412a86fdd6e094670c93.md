### Title
Unbounded in-memory growth of `assocKnownBadUnits`/`assocKnownBadJoints` via posted invalid units causes node OOM crash - ([File: joint_storage.js])

### Summary
Any unauthenticated unit poster can cause a full/hub node to permanently retain an entry in an in-process, never-evicted JavaScript object for every syntactically-parseable-but-invalid unit or joint it submits. Because these objects are keyed by attacker-derived, effectively unlimited-cardinality strings (unit hashes / joint hashes) and are never pruned, an attacker can grow them without bound simply by repeatedly posting cheap, distinct invalid units, eventually exhausting process memory and crashing the node — the same class of unbounded, reachable resource exhaustion (CWE-770) as the reported `Plug.Cowboy` atom-table exhaustion, where an unauthenticated remote input drives permanent growth of a global, unbounded in-memory table until the runtime crashes.

### Finding Description
`joint_storage.js` maintains three in-memory associative caches that are populated purely from unit-validation outcomes, reachable from ordinary "post a unit" flows (no special peer/hub/catchup privilege required): [1](#0-0) 

- `saveKnownBadJoint` inserts into `assocKnownBadJoints` for every joint whose *joint-level* structure fails validation (`ifJointError` path): [2](#0-1) 

- `purgeJointAndDependencies` inserts into `assocKnownBadUnits` for every *unit-level* validation failure (`ifUnitError` path): [3](#0-2) 

- `collectQueriesToPurgeDependentJoints` also adds entries to `assocKnownBadUnits` for every dependent unit that is transitively purged: [4](#0-3) 

These insertions are driven directly by `network.js`'s `handleJoint`, the normal entry point for any unit a peer (including a light client, wallet, or unauthenticated poster over `post_joint`) submits: on `ifUnitError`/`ifJointError` it calls `purgeJointAndDependenciesAndNotifyPeers` / `joint_storage.saveKnownBadJoint`, which in turn populate the caches above: [5](#0-4) 

Unlike the other in-memory caches in the codebase (e.g. `storage.js`'s `assocCachedUnits`/`assocCachedAssetInfos`, which are bounded by `MAX_ITEMS_IN_CACHE` and periodically shrunk via `shrinkCache()`, or `archiving.js`'s `assocCachedPrunedJoints`, which is TTL-purged via `purgeExpiredCachedPrunedJoints()`), there is no code path anywhere in `joint_storage.js` that ever calls `delete assocKnownBadUnits[...]` or `delete assocKnownBadJoints[...]`. The only other place these maps are touched is at startup (`initUnhandledAndKnownBad`), which explicitly says "ignore old known-bads" and never even repopulates them from disk: [6](#0-5) 

So each new distinct invalid unit/joint permanently adds one entry to these process-lifetime maps, with the error string value additionally embedding attacker-influenced content (bounded by `truncate()` to 200 chars, but the object itself grows one key per invalid unit regardless): [7](#0-6) 

This is structurally identical to the reported bug class: an unauthenticated, remotely reachable input (there: an HTTP/2 `:scheme` value converted to a permanent BEAM atom; here: a unit/joint hash inserted as a permanent JS object key) drives unbounded growth of a global, non-evicted table until the process runs out of memory.

### Impact Explanation
Any unprivileged party able to post units to a full node or hub (a completely normal, unauthenticated capability of the protocol — light clients and wallets constantly post units) can, at negligible cost (each invalid unit only needs to be syntactically valid JSON with a unique hash, e.g. a bad signature or malformed field that fails a cheap check early in `validation.js`), force the node to retain one permanent object key per submission. Sustained submission of cheap distinct invalid units will grow `assocKnownBadUnits`/`assocKnownBadJoints` without bound, eventually exhausting the Node.js process heap and crashing the node/hub — a denial of service that prevents the affected node from validating/confirming further units, i.e., "a network unable to confirm new units" for the affected node(s), matching the required impact bar of an unauthenticated, reachable DoS.

### Likelihood Explanation
High. No authentication, special network position, or privileged role is required — posting a unit that fails validation is a core, always-reachable capability of the protocol (`network.js` `handleJoint`, invoked for any submitted joint). Generating a fresh invalid unit with a unique hash each time is trivial and cheap (e.g. varying a payload field to change the hash while still failing a signature/authentifier check), so an attacker can automate mass submission at high rate with minimal computational cost per submission, unlike the victim node's permanent per-entry memory cost.

### Recommendation
Bound and periodically evict `assocKnownBadUnits` and `assocKnownBadJoints` the same way `storage.js`'s `shrinkCache()`/`MAX_ITEMS_IN_CACHE` and `archiving.js`'s TTL-based `assocCachedPrunedJoints` are handled: impose a maximum size (or TTL with periodic sweep via `setInterval`) and evict oldest/expired entries once the limit is exceeded, falling back to the `known_bad_joints` DB table (which already persists this information) for authoritative lookups instead of keeping an unbounded in-memory mirror.

### Proof of Concept
1. Start a full node/hub that accepts posted joints from unauthenticated peers/wallets.
2. Repeatedly construct minimal well-formed-but-invalid units (e.g., a payment unit with a bad/garbage signature so it always fails `ifUnitError`, varying an arbitrary field such as `timestamp`/nonce data each iteration so each unit has a unique hash).
3. Submit these units via the normal joint-posting path (`network.js` `handleJoint`) in a tight loop from one or more unauthenticated connections.
4. Observe `joint_storage.assocKnownBadUnits` (and/or `assocKnownBadJoints` for joint-structure failures) growing by one entry per submission with no eviction, tracked via heap snapshots or `process.memoryUsage()`, until the Node.js process exhausts available memory and crashes.

*Note: I was unable to find any additional cleanup logic for these two maps elsewhere in the indexed codebase; given index size limits, it is possible some cleanup exists in a file not surfaced by search — this should be verified directly in a full checkout before treating the maps as entirely unbounded in all code paths.*

function purgeJointAndDependencies(objJoint, error, onPurgedDependentJoint, onDone){
	var unit = objJoint.unit.unit;
	const truncatedError = truncate(error);
	assocKnownBadUnits[unit] = truncatedError;
	db.takeConnectionFromPool(function(conn){
		var arrQueries = [];
		conn.addQuery(arrQueries, "BEGIN");
		conn.addQuery(arrQueries, "INSERT "+conn.getIgnore()+" INTO known_bad_joints (unit, json, error) VALUES (?,?,?)", [unit, JSON.stringify(objJoint), truncatedError]);
		conn.addQuery(arrQueries, "DELETE FROM unhandled_joints WHERE unit=?", [unit]); // if any
		conn.addQuery(arrQueries, "DELETE FROM dependencies WHERE unit=?", [unit]);
		collectQueriesToPurgeDependentJoints(conn, arrQueries, unit, truncatedError, onPurgedDependentJoint, function(){
			conn.addQuery(arrQueries, "COMMIT");
			async.series(arrQueries, function(){
				delete assocUnhandledUnits[unit];
				conn.release();
				if (onDone)
					onDone();
			})
		});
	});
}

function collectQueriesToPurgeDependentJoints(conn, arrQueries, unit, error, onPurgedDependentJoint, onDone){
	conn.query("SELECT unit, peer FROM dependencies JOIN unhandled_joints USING(unit) WHERE depends_on_unit=?", [unit], function(rows){
		if (rows.length === 0)
			return onDone();
		const truncatedError = truncate(error);
		//conn.addQuery(arrQueries, "DELETE FROM dependencies WHERE depends_on_unit=?", [unit]);
		var arrUnits = rows.map(function(row) { return row.unit; });
		arrUnits.forEach(function(dep_unit){
			assocKnownBadUnits[dep_unit] = truncatedError;
			delete assocUnhandledUnits[dep_unit];
		});
		conn.addQuery(arrQueries, "INSERT "+conn.getIgnore()+" INTO known_bad_joints (unit, json, error) \n\
			SELECT unit, json, ? FROM unhandled_joints WHERE unit IN(?)", [truncatedError, arrUnits]);
		conn.addQuery(arrQueries, "DELETE FROM unhandled_joints WHERE unit IN(?)", [arrUnits]);
		conn.addQuery(arrQueries, "DELETE FROM dependencies WHERE unit IN(?)", [arrUnits]);
		async.eachSeries(
			rows,
			function(row, cb){
				if (onPurgedDependentJoint)
					onPurgedDependentJoint(row.unit, row.peer);
				collectQueriesToPurgeDependentJoints(conn, arrQueries, row.unit, error, onPurgedDependentJoint, cb);
			},
			onDone
		);
	});

function initUnhandledAndKnownBad(){
	db.query("SELECT unit FROM unhandled_joints", function(rows){
		rows.forEach(function(row){
			assocUnhandledUnits[row.unit] = true;
		});
		return; // ignore old known-bads
		db.query("SELECT unit, joint, error FROM known_bad_joints ORDER BY creation_date DESC LIMIT 1000", function(rows){
			rows.forEach(function(row){
				if (row.unit)
					assocKnownBadUnits[row.unit] = row.error;
				if (row.joint)
					assocKnownBadJoints[row.joint] = row.error;
			});
		});
	});
}
