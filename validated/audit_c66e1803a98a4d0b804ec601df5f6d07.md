### Title
`StatusHandler#process` updates commit statuses without scoping by the webhook's repository, enabling cross-repository status forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Handler#stacks` correctly scopes queries to the repository named in the webhook payload via `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [1](#0-0) , but `StatusHandler#process` never invokes this scoping method. Instead it runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) , which matches commits by SHA across the entire `commits` table regardless of which repository/stack the commit belongs to.

### Finding Description
The invariant that should hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` mutated by a given webhook. `Handler#stacks` enforces exactly this by resolving `Repository.from_github_repo_name(repository_name)` before touching any stack-scoped data [1](#0-0) . Several sibling handlers (`PullRequest::*Handler`, etc.) call `stacks` before mutating anything scoped to a repository.

`StatusHandler#process`, however, looks up commits purely `Commit.where(sha: params.sha)` [3](#0-2)  with no reference to `repository_name` or `stacks` at all — the equality above is never checked, so the binding is broken specifically in this handler.

`Commit` is `belongs_to :stack`, and `stack.repository` is what actually determines ownership [4](#0-3) . Because `sha` is a raw git content hash with no repository namespace attached at the DB level, whenever two different Shipit-registered repositories happen to share commit history (the canonical case: repo `A` is public and repo `B` is a fork of `A`, both configured as separate Shipit stacks), a `Commit` row with the same `sha` can exist for both stacks.

Exploit flow:
1. Attacker forks a target repository that is registered as a Shipit stack (public repos are forkable by any GitHub user) and has the Shipit GitHub App/webhook installed on their own fork.
2. Attacker triggers (or fabricates, since they own the fork) a `status` event for a commit `sha` that is shared with the upstream/target repository (any commit predating the fork, which is any commit at all, satisfies this).
3. GitHub signs and delivers the webhook to `POST /webhooks` with `X-Hub-Signature` computed using the webhook/App secret; this passes `verify_signature`, because it validates only that the payload is signed by a real GitHub delivery for an installation the attacker legitimately controls (their own fork) — it does not verify that the `repository.full_name` in the JSON body matches any particular target [5](#0-4) .
4. `StatusHandler#process` ignores `payload['repository']` entirely and updates `Commit.where(sha: attacker_controlled_sha)`, which resolves to the row belonging to the *target* stack, applying `params.state`/`description`/`target_url` supplied by the attacker via `create_status_from_github!` [6](#0-5) .

`create_status_from_github!` → `add_status` recomputes `status`, emits `Hook.emit(:deployable_status, ...)`, and calls `stack.schedule_merges if new_status.pending? || new_status.success?` [7](#0-6) . If the target stack has continuous deployment/merge-on-green enabled and is otherwise gated on this status context, a forged `success` status can trigger an unauthorized deploy or merge on a repository the attacker never authenticated against.

None of the existing guards close this gap: `verify_signature` authenticates the webhook sender/installation, not the semantic repository field inside the JSON body; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema in `StatusHandler` only validates the shape of `sha`/`state`/etc., not which repository they apply to; and `Handler#stacks`/`repository_name` — the only mechanism designed to enforce this equality — is simply never called by this subclass.

### Impact Explanation
An attacker who controls any repository with the same commit history as a Shipit-managed target repository (trivially achieved by forking a public repo) can forge arbitrary commit statuses (`state`, `description`, `target_url`) onto the target stack's commits, without any Shipit session, API token, or membership in `Shipit.github_teams`. This is a cross-tenant write: "a payload for one repository mutating another's stack/commit," and if the affected stack relies on that status context for continuous deployment gating, it can produce an unauthorized deploy — matching the Critical impact category.

### Likelihood Explanation
Preconditions: (1) the target repository must be registered as a Shipit `Repository`/`Stack`; (2) the attacker's own repository (e.g. a fork) must be reachable by the same GitHub App/webhook configuration so that `verify_signature` passes for a legitimately-signed delivery from the attacker's own repo; (3) the forged commit `sha` must exist as a `Commit` row on the target stack, which is guaranteed for any commit that predates the fork (i.e., essentially all history). This requires no secrets, no privileged role, and is repeatable for any public repository the attacker chooses to fork, making it feasible and repeatable at low cost.

### Recommendation
Make `StatusHandler#process` scope the commit lookup through `stacks` (mirroring `Handler#stacks`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so that a status webhook can only mutate commits belonging to stacks tied to the `Repository` resolved from `payload.dig('repository', 'full_name')`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, minitest)
test "Handler#stacks correctly scopes to Stack.none for unmatched repository" do
  handler = Shipit::Webhooks::Handlers::StatusHandler.new(
    'repository' => { 'full_name' => 'nonexistent-owner/nonexistent-repo' },
    'sha' => 'deadbeef', 'state' => 'success'
  )
  assert_equal Shipit::Stack.none, handler.send(:stacks)
end

test "StatusHandler#process ignores repository scoping and mutates a commit belonging to a different stack" do
  stack_a = shipit_stacks(:shipit) # repository "foo/bar"
  stack_b = create_stack!(repository: create_repository!(owner: 'attacker', name: 'fork-of-bar'))
  commit = stack_a.commits.create!(sha: 'sharedsha1', message: 'shared commit', ...)

  payload = {
    'repository' => { 'full_name' => 'attacker/fork-of-bar' }, # attacker's own repo
    'sha' => 'sharedsha1', 'state' => 'success'
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit.reload
  assert_equal 'success', commit.status.state
  # proves the mutation happened even though payload['repository'] never
  # resolved to stack_a's Repository, i.e. stacks scoping was bypassed
end
```
This contrasts a unit test proving `Handler#stacks` correctly returns `Stack.none` for an unmatched repository, with an integration test proving `StatusHandler#process` never consults that scoping and mutates a commit on an unrelated stack — isolating the defect to `StatusHandler#process`.
