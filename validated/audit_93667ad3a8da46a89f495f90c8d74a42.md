### Title
Instant, unilateral asset-attestor list changes let the asset definer freeze or reroute holder funds without any grace period - ([File: validation.js])

### Summary
The externally reported bug class is "a privileged owner/admin role can unilaterally and instantly change a critical permission set (admins), with no timelock/grace period, so a malicious or compromised owner can immediately strip protections." The reachable ocore analog is the `spender_attested` asset's attestor list: the asset **definer** (an unprivileged, self-selected asset issuer role, reachable by any unit poster who defines an asset) can post an `asset_attestors` message at any time to replace the entire attestor list, and this change takes effect for the very next stable unit — with no delay, cooldown, or grace period for existing coin holders to react.

### Finding Description
When an asset is defined with `spender_attested: true`, the definer publishes an attestor list that determines who is allowed to hold/spend the asset [1](#0-0) . The definer can update this list later via an `asset_attestors` message, validated by `validateAttestorListUpdate`, whose *only* authorization check is that the sending address equals `objAsset.definer_address` — there is no delay, timelock, or notice period before the new list becomes effective: [2](#0-1) 

Once such a unit becomes stable, `storage.readAsset` picks the attestor list from the single latest stable `asset_attestors` unit (ordered by `level DESC LIMIT 1`), completely replacing the previous list with no transition window: [3](#0-2) 

This new list is then enforced immediately against holders' existing (already-owned) coins. Spending an input of a `spender_attested` asset requires the *current* owner address to be in the *current* attestor-derived attested-address set, checked directly during payment validation: [4](#0-3) [5](#0-4) 

Because the check is evaluated at spend time against whatever the latest stable attestor list happens to be, a definer can:
- Remove an attestor (or replace the whole list) so that addresses previously attested by it instantly lose the ability to spend outputs they already hold, freezing their funds with no warning or grace window, or
- Add new attestors so that new addresses can immediately be treated as attested and receive/spend restricted asset outputs.

There is no analog of the "grace period" recommended in the report (i.e., no mandatory delay between the definer proposing an attestor-list change and it taking effect), so a malicious or compromised definer key can weaponize this instantly, exactly mirroring the reported owner/admin centralization issue.

### Impact Explanation
This directly enables **freezing of holder funds** or **unauthorized restriction/loosening of who may spend a shared asset**, both of which are concrete fund-loss/freezing impacts within scope. Any attested holder's spendable balance can be rendered permanently unspendable at the definer's sole discretion and with no time to react, and this applies to every unit already broadcast to the network (not just future transactions).

### Likelihood Explanation
Likelihood is high in practice for any asset that opts into `spender_attested`: the action requires only a single self-authored `asset_attestors` message from the definer address, no cosigners, no other approvals, and takes effect as soon as the unit is stable (a matter of a few main-chain confirmations). A compromised or malicious definer key can execute this at any time.

### Recommendation
Introduce a mandatory delay (grace period) between when an `asset_attestors` update is posted and when it becomes enforceable against already-existing outputs, analogous to a timelock: e.g., only apply attestor-list updates for main_chain_index a fixed number of MCIs after the change's stabilization, or grandfather in already-attested holders' existing balances for a cooldown window before requiring re-attestation. This gives holders time to move funds before losing spend rights, mirroring the timelock pattern from the referenced Solidity example.

### Proof of Concept
1. Definer address `D` issues asset `A` with `spender_attested: true` and initial `attestors: [X]` via the `asset` message [6](#0-5) .
2. Address `X` receives and holds asset `A` output; validation confirms `X` is attested via `arrAttestedAddresses` at spend time [5](#0-4) .
3. `D` posts a single-authored `asset_attestors` message for asset `A` with a new attestor list that excludes `X`, requiring only that `D` is the definer (`validateAttestorListUpdate`) [2](#0-1) .
4. Once this unit stabilizes, `storage.readAsset`'s `addAttestorsIfNecessary` picks this newest stable `asset_attestors` unit as the sole source of truth for the attestor list [3](#0-2) .
5. `X` now attempts to spend its previously-received, already-owned output of asset `A`. `filterAttestedAddresses`/`arrAttestedAddresses` no longer includes `X`, so `validatePaymentInputsAndOutputs` rejects the spend with "owner address is not attested" [4](#0-3) , permanently freezing `X`'s funds with no advance notice or grace period.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
