Found the analog: the **CCMenuController** breaks the exact "stack a token authorises versus stack it touches" binding that the DebtRegistry report is analogous to.

### Title
API client scoped to a single stack can read any stack's CCTray status via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
Shipit's API authorization model assumes that an `ApiClient` restricted to a `stack_id` can only act on that one `Stack`. This invariant is enforced through `Api::BaseController#stacks`, which every other API controller (`Api::StacksController`, `Api::DeploysController`, `Api::TasksController`, `Api::CommitsController`, `Api::RollbacksController`, `Api::HooksController`) uses to resolve `stack`/`stacks`. `Api::CCMenuController`, however, resolves the stack directly from `Stack.from_param!(params[:stack_id])`, bypassing the scoping method entirely, breaking the binding `token.authorized_stack == stack_touched_by_request`.

### Finding Description
`Api::BaseController` defines the scoping used everywhere else: [1](#0-0) 

Every other stack-scoped controller resolves the target stack through this `stack`/`stacks` helper, which restricts lookups to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` has a `stack_id` set (e.g. `Api::CommitsController#index`, `Api::RollbacksController#create`, `Api::TasksController`, `Api::HooksController#hooks`): [2](#0-1) [3](#0-2) 

`Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping and resolves the stack directly from the raw request parameter: [4](#0-3) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string; it never checks that the referenced `stack` matches `current_api_client.stack_id`: [5](#0-4) [6](#0-5) 

As a result, an `ApiClient` created with a `stack_id` restriction (e.g. the fixture `here_come_the_walrus`, scoped to the `shipit` stack, confirmed elsewhere to only see that one stack via the `stacks` helper) can nonetheless authenticate to `Api::CCMenuController#show` and supply an arbitrary `stack_id` in the URL, retrieving deploy/rollback status (including deploy timing, running state, and stack identity) for a stack it was never granted access to. The `stacks` fixture test explicitly demonstrates the intended restriction is honored elsewhere: [7](#0-6) 

The binding broken:
`token.stack_id == request.stack_id` (enforced in every other controller via `Api::BaseController#stacks`) is bypassed in `Api::CCMenuController`, which uses `token.stack_id == ANY` (unenforced) while still touching `request.stack_id`.

### Impact Explanation
This grants unauthenticated read of stack state to a caller who only holds credentials for a different stack — matching the "High: unauthenticated read of stack state, task streams or deploy output" impact bucket. The leaked data includes deploy IDs, timestamps, and running/success state for any stack in the Shipit instance, regardless of the `stack_id` restriction placed on the client's token when it was created.

### Likelihood Explanation
High likelihood: exploitation requires only a valid `ApiClient` token restricted to one stack (a normal, low-privilege credential explicitly designed to be scoped-down) and knowledge/guessing of another stack's `owner/repo/environment` param (which is not secret — stack identifiers are visible throughout the UI, git remotes, and CI logs). No elevated access is required beyond holding any single-stack-scoped API token.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the inherited, permission-aware `stacks` scope instead of `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This mirrors the pattern already used correctly in `Api::StacksController`, `Api::HooksController`, and all other stack-scoped API controllers, restoring the `token.stack_id == stack.id` invariant.

### Proof of Concept
1. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id (mirrors fixture `here_come_the_walrus`).
2. Authenticate to `GET /api/:stack_id_of_stack_B/cc.xml` (or equivalent CCMenu route) using Stack A's token but supplying Stack B's `stack_id` param.
3. `authenticate_api_client` succeeds (token is valid); `require_permission :read, :stack` passes (token has `read:stack`); `stack` resolves via `Stack.from_param!(params[:stack_id])` to Stack B, bypassing the `current_api_client.stack_id` restriction that every sibling controller enforces via `Api::BaseController#stacks`.
4. Response renders Stack B's latest deploy/rollback status XML, which the token was never authorized to view.
