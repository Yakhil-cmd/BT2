### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized continuous-delivery deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the commit to update purely by `sha`, with no check that the webhook's `repository`/`organization` actually owns that commit. Because GitHub's Statuses API does not require the `:sha` argument to belong to the repository the status is posted against, any GitHub user who owns (or has push access to) a single repository sharing the same GitHub App/webhook secret as the victim's organization can post a status for an arbitrary victim commit SHA, causing Shipit to record a forged `success` status on the victim's commit and — if the victim stack has `continuous_deployment: true` — trigger a real deploy using the victim's credentials.

### Finding Description
The broken binding: the code assumes `commit.stack == webhook_payload.repository`, i.e. "the CI state recorded for commit X was produced by the repository that owns X." In reality the handler only checks `commit.sha == params.sha`; it never validates `params` against the `stack`/`repository` that the commit belongs to.

Path:
- `WebhooksController#verify_signature` only checks that the raw body's HMAC matches the webhook secret configured for `repository_owner` (`params.dig('repository','owner','login')`) [1](#0-0) . This proves the request came from GitHub for *some* repo in that organization/app — it says nothing about which SHA the status applies to.
- `StatusHandler#process` then does a completely global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This query is not scoped by stack, repository, or organization — any `Commit` record anywhere in the Shipit database with a matching `sha` gets a new `Status` created against it, attributed to its own (`commit.stack_id`), not the sender's repository.
- `Status` model fires `after_commit :schedule_continuous_delivery` on create, which calls `commit.schedule_continuous_delivery`, eventually enqueuing `ContinuousDeliveryJob` for the victim's stack [3](#0-2) .
- `ContinuousDeliveryJob#perform` only checks `stack.continuous_deployment?`, the deploy schedule window, and `stack.occupied?` — none of which validate the origin of the status that triggered it [4](#0-3) .
- `Stack#trigger_continuous_delivery` computes `next_commit_to_deploy` (which becomes non-nil once the forged `success` status exists) and calls `trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)` [5](#0-4) , which builds and enqueues a real `Deploy`/`Task` that spawns the deploy `Command` with the victim stack's GitHub token/env.

Why existing guards fail: `verify_signature` authenticates the *sender's organization/app*, not the *SHA-to-repository ownership*. GitHub's real Statuses API (`POST /repos/:owner/:repo/statuses/:sha`) is known to accept arbitrary SHA values not necessarily present in `:repo`'s history, as long as the caller has push access to `:repo`. Consequently an attacker who owns any repository under an org sharing the same GitHub App/webhook_secret as the victim's org can legitimately trigger GitHub to send a signed `status` webhook whose `sha` field is the victim's undeployed commit SHA. Since `StatusHandler` never cross-checks `params['repository']` against `commit.stack.repository`, the forged status lands on the victim's commit.

### Impact Explanation
A forged status write on a commit that does not belong to the sender's repository is exactly the "payload for one repository mutating another's stack/commit" critical category. When the target stack has `continuous_deployment: true` and no other deployable commit exists (`next_commit_to_deploy` is `nil`), the forged status is sufficient to make it non-nil, causing `Stack#trigger_continuous_delivery` to invoke `trigger_deploy` as `Shipit.user`, spawning the victim's deploy `Command` with the victim's real `GITHUB_TOKEN`/`GIT_ASKPASS` environment — an unauthorized deploy executed with the victim's credentials, triggered entirely from a webhook the attacker caused via their own (unrelated) repository. This is repeatable against any commit/stack sharing the same GitHub App/organization webhook secret as the attacker's own repo, and blast radius extends to every stack tracked by Shipit under that GitHub App installation, not just the attacker's own repo's stack.

### Likelihood Explanation
Preconditions: the attacker needs push/admin access to at least one repository whose webhooks are verified with the same GitHub App/organization webhook secret Shipit trusts (e.g., a low-privilege repo in the same GitHub org/installation as the victim's tracked repository) — a realistic condition in any multi-repo/multi-team organization using a single shared GitHub App installation, which is the common Shipit deployment pattern. The attacker must also know or guess the target's undeployed commit SHA, which is generally public (commit shas are visible on GitHub, in PRs, in CI logs, etc.) rather than secret. No Shipit session, API token, or GitHub secret is required beyond ordinary push access to their own repo. This is a low-cost, repeatable attack once those conditions hold.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository identified in the webhook payload, e.g., resolve the `Stack`/`Repository` from `params['repository']['full_name']` first, then find commits only within that stack's commit set (`stack.commits.where(sha: params.sha)`), rejecting or ignoring status updates whose payload repository does not match the commit's actual stack/repository.

### Proof of Concept
```ruby
# test/models/shipit/continuous_delivery_cross_repo_forgery_test.rb
require 'test_helper'

module Shipit
  class ContinuousDeliveryCrossRepoForgeryTest < ActiveSupport::TestCase
    test "forged status for another repo's commit triggers unauthorized CD deploy" do
      victim_stack = shipit_stacks(:shipit)
      victim_stack.update!(continuous_deployment: true)
      victim_stack.tasks.delete_all
      victim_stack.deploys_and_rollbacks.destroy_all

      # No deployable commit currently
      assert_nil victim_stack.next_commit_to_deploy

      target_commit = victim_stack.undeployed_commits.first
      assert_not_nil target_commit

      # Attacker's own repo/org webhook payload, signature verified for attacker's org,
      # but sha belongs to victim_stack's commit.
      forged_params = OpenStruct.new(
        sha: target_commit.sha,
        state: 'success',
        description: 'forged',
        context: 'ci/attacker',
        target_url: nil,
        created_at: Time.now.to_s
      )

      assert_difference -> { target_commit.statuses.count }, 1 do
        Commit.where(sha: forged_params.sha).each do |commit|
          commit.create_status_from_github!(forged_params)
        end
      end

      assert_equal target_commit, victim_stack.reload.next_commit_to_deploy

      assert_difference -> { Deploy.count }, 1 do
        ContinuousDeliveryJob.new.perform(victim_stack)
      end

      deploy = victim_stack.deploys.last
      assert_equal Shipit.user, deploy.user
      assert_equal target_commit, deploy.until_commit
    end
  end
end
```
This demonstrates that a status record created for a commit — using data that never referenced `victim_stack`'s own repository — is sufficient to flip `next_commit_to_deploy` from `nil` to the target commit and cause `ContinuousDeliveryJob` to create and enqueue a real `Deploy` as `Shipit.user`, with no verification tying the status's origin to the stack being deployed.

      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy
