### Title
Front-running an AA-based liquidity pool's first deposit lets an attacker set an unfair exchange rate and drain the honest depositor - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The bundled `uniswap_like_market_maker.oscript` AA template implements a constant-product liquidity pool between `base` bytes and an asset. Its "invest in MM" branch has a special, unchecked code path for the very first deposit that lets whoever triggers it first fix the pool's asset/bytes ratio arbitrarily, exactly mirroring the reported "front-run pool's `initialize`" issue: no access control and no price/ratio validation exist for the operation that establishes the pool's initial price.

### Finding Description
In the "invest in MM" case, the `init` formula computes: [1](#0-0) 
```
if: `{$mm_asset AND trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0}`,
init: `{
    $asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
    $bytes_balance = balance[base] - trigger.output[[asset=base]];
    if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
        $issue_amount = balance[base];
        return;
    }
```
When the pool holds no prior asset or bytes balance (i.e., the first-ever deposit), the AA mints `mm_asset` shares equal to `balance[base]` (the depositor's own byte contribution) with **no check whatsoever on `trigger.output[[asset=$asset]]`**, the amount of the paired asset sent in the same trigger. Any address can be the first to trigger this branch and choose an arbitrary, non-market ratio between the two assets deposited (e.g., 1 byte-worth of shares backed by a huge amount of the asset, or vice versa), fixing `$current_ratio` used by all subsequent operations.

Every later interaction — the ratio-checked deposit path, and especially the unrestricted swap paths — is anchored to this attacker-chosen ratio: [2](#0-1) 
```
$current_ratio = $asset_balance / $bytes_balance;
$expected_asset_amount = round($current_ratio * trigger.output[[asset=base]]);
if ($expected_asset_amount != trigger.output[[asset=$asset]])
    bounce('wrong ratio of amounts, expected ' || $expected_asset_amount || ' of asset');
``` [3](#0-2) 
```
{ // exchange bytes to asset
    if: `{trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] == 0 AND var['mm_asset_outstanding']}`,
    init: `{
        $asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
        $bytes_balance = balance[base] - trigger.output[[asset=base]];
        $p = $asset_balance * $bytes_balance;
        $new_asset_balance = round($p / balance[base]);
        $amount = $asset_balance - $new_asset_balance;
    }`,
```
Because the constant-product invariant `$p` is derived directly from the manipulated initial reserves, an attacker who set an extreme ratio at initialization can later swap at that skewed rate, extracting value from any counterparty who deposits or swaps at the AA's address, unaware the pool's price was rigged from the start. This is structurally identical to the Trail of Bits finding for Uniswap V3's `initialize`: no access control on the state-setting operation, no sanity check tying the deposited amounts to any external price reference, and the first caller unilaterally determines the reference price used by everyone thereafter.

### Impact Explanation
Because the AA has no owner/whitelist restriction on who may trigger it, and the OScript engine itself imposes no requirement that the "initial deposit" reflect a fair market ratio, a malicious actor can front-run the intended first liquidity provider's transaction (visible pre-stabilization in the DAG) and lock in an arbitrary asset/bytes ratio. Once the legitimate provider's larger deposit follows (either bounced for wrong ratio, or, if instead a plain swap is used, executed at the corrupted price), the attacker can drain the honest party's funds by swapping against the AA at the skewed constant-product price. This is a direct fund-loss / drain scenario for AA users following this widely referenced example pattern, matching the "Medium" severity classification of the original report.

### Likelihood Explanation
Any address can post a trigger unit to the AA; there is no cap, whitelist, or minimum-liquidity mechanism preventing the first "invest" call from being made with a deliberately skewed pair of amounts. Because Obyte units are broadcast before finality, an attacker monitoring the DAG for a pending "define"/first "invest" transaction targeting this AA can trivially post their own trigger with higher fee/priority parents to land first, exactly as in the original Uniswap front-running scenario. The only precondition is that the AA is deployed using (a close variant of) this documented pattern, which is precisely why it is shipped as a canonical example in `test/samples/`.

### Recommendation
- Require a minimum, non-zero initial liquidity contribution to be permanently locked (analogous to Uniswap V2's minimum liquidity burn) so the first depositor cannot pick an arbitrarily thin/skewed ratio.
- Have the AA definer (not an arbitrary trigger sender) supply or attest to the initial ratio, or seed the pool atomically with the `define` message rather than allowing any later, independent "first investor" trigger to set the price.
- Add a sanity bound / oracle check comparing the implied initial price against an expected range before accepting the "initial deposit" branch.
- Document prominently, wherever this example is referenced, that the first deposit is a privileged, price-setting operation and must not be left open to arbitrary callers.

### Proof of Concept
1. AA is deployed; `mm_asset` is defined via the "define share asset" case.
2. Attacker sends a single trigger to the AA with `trigger.output[[asset=base]] = 100001` (just above the `1e5` threshold) and `trigger.output[[asset=$asset]] = 1` (or, conversely, a huge amount, depending on which side the attacker wants overpriced), landing in the "invest in MM" case before the intended first liquidity provider's unit stabilizes: [4](#0-3) 
3. Because `$asset_balance == 0 OR $bytes_balance == 0` is true, `issue_amount = balance[base]` is minted to the attacker with no relation to the 1 unit of asset supplied — the pool's reserve ratio is now `asset:bytes = 1:100001` (or whatever the attacker chose).
4. The legitimate provider's later, market-priced deposit is bounced by the ratio check, or, if they instead perform an "exchange bytes to asset"/"exchange asset to bytes" swap trusting real market price, the constant-product formula computed from the corrupted `$asset_balance`/`$bytes_balance` pays them out (or takes from them) at the attacker's rigged rate.
5. The attacker then swaps back through the pool to realize a profit extracted from the honest party's funds, at no meaningful capital cost of their own (their initial 1-unit contribution was negligible).
