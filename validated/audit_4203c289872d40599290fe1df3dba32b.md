### Title
Uncaught synchronous `throw Error` in oscript formula evaluator can crash the node process (unhandled exception DoS) - ([File: formula/evaluation.js])

### Summary
The CEL-rust advisory describes a parser/evaluator that panics (aborts the whole process) when fed a malformed-but-syntactically-acceptable expression, because a "should never happen" code path is actually reachable from untrusted input. The oscript formula engine in ocore has the same structural risk: `formula/evaluation.js`'s `evaluate()` function is riddled with `throw Error(...)` calls used as "this should never happen" assertions on AST shapes produced by the successfully-parsed, attacker/AA-author-controlled formula (e.g. lines around 1472 `throw Error("test evaluated to object " + res)`, 2051 `throw Error("unknown op: " + op)`, 3131 `throw Error("neither local nor remote: " + funcInfo)` / `unrecognized function argument`, 3341 `throw Error("args is not an array")`). Unlike the parser feed itself (which is wrapped in `try/catch` in both `formula/validation.js:250-266` and `formula/evaluation.js:108-120`), these `throw`s happen **inside the asynchronous, callback-driven `evaluate()` recursion**, which is not inside any `try/catch` in the calling chain (`aa_composer.js`, `network.js` `light/execute_getter` handler, etc.). Because they are thrown asynchronously via `async.eachSeries`/`setImmediate` callbacks rather than returned to the outer `try` block, they surface as Node.js uncaught exceptions, which by default terminate the process (or trigger the `uncaughtException` handler with an unrecoverable state), exactly mirroring the Rust panic → process abort behavior described in the CEL advisory.

### Finding Description
`formula/validation.js` and `formula/evaluation.js` only guard the initial `nearley` parse step with `try { ... } catch (e) { return callback(...) }` [1](#0-0) . Once parsing succeeds, the resulting AST is walked by the deeply recursive, callback-based `evaluate()` function. Validation (`formula/validation.js`) is supposed to reject any formula whose AST could trigger these "impossible" branches before the AA is even installed/executed, but validation and evaluation are two independently-maintained code paths that must stay in perfect sync on every accepted grammar production; any gap between what the grammar can produce, what `validation.js`'s `evaluate()` accepts, and what `evaluation.js`'s `evaluate()` handles turns into a reachable `throw Error(...)` deep inside `evaluate()`, e.g.:
- `throw Error("test evaluated to object " + res)` in the `ifelse` handler [2](#0-1) 
- `throw Error("unknown op: " + op)` in string-op handling [3](#0-2) 
- `throw Error("neither local nor remote: " + funcInfo)` and `throw Error("unrecognized function argument: " + func_expr)` in function-argument resolution [4](#0-3) [5](#0-4) 
- `throw Error("args is not an array")` in `callGetter` [6](#0-5) 

These `throw` statements execute inside nested callbacks fired by `async.eachSeries`, `evaluate(...)`, or `setImmediate`, i.e. **outside** the stack frame of the `try/catch` that wraps only the `parser.feed()` call at the top of `exports.evaluate`. A synchronous throw from inside an async callback in Node.js is not caught by any ancestor `try/catch` — it propagates up through the event loop as an uncaught exception.

This code is reachable by an unprivileged actor in several ways without any special privilege:
- Posting a unit whose payload references an AA's `init`/`messages` formulas that are evaluated during `aa_composer.js` trigger handling (`handleTrigger` → `formulaParser.evaluate`) for **any** AA a user can send a trigger to.
- Sending `light/execute_getter` network requests, which directly call `formulaEvaluation.executeGetter` → `callGetter` → `exports.evaluate` with attacker-supplied getter name/args [7](#0-6) .
- AA-to-AA remote getter calls (`remote_func_call`), where a malicious AA author can craft formulas designed to hit one of these "impossible" AST shapes in a way validation.js fails to reject, causing the calling node to crash while evaluating a getter on behalf of another AA (`callGetter`, `evaluateFunctionExpression`) [8](#0-7) .

### Impact Explanation
If any of these `throw Error` sites are reachable from an AST that both parses successfully and passes `formula/validation.js`'s independent `evaluate()` walk (a plausible scenario given the size and duplicated logic of both files, and the fact that the grammar and evaluator are maintained in parallel across many op-codes), the result is an unhandled exception that crashes the full-node process handling unit validation / AA execution — a network-wide denial of service, since every full node processing that unit or AA trigger would independently crash on the same input, potentially halting confirmation of new units network-wide until nodes are patched or restarted. This matches the CVSS "Availability: High" characterization of the CEL-rust advisory.

### Likelihood Explanation
Likelihood is **conditional but non-trivial**: it requires finding at least one oscript formula string that (a) is accepted by the `nearley` grammar, (b) passes `formula/validation.js`'s independent complexity/type-checking `evaluate()` pass, and (c) still lands on one of the many "should never happen" `throw Error(...)` branches in `formula/evaluation.js`'s `evaluate()`. Given the sheer number of duplicated assumption points between the two ~3000+ line files (validation.js and evaluation.js each re-implement checks for every op-code independently), and the demonstrated CEL-rust precedent that "unreachable" parser/evaluator branches are frequently reachable in practice via edge-case grammar productions, this is a realistic class of bug rather than a purely theoretical one. I was not able to construct or verify a concrete PoC formula string within this session that reaches one of these throws while passing validation — that requires deeper cross-referencing of `formula/grammars/oscript.ne` productions against every corresponding case in `formula/validation.js`, which is a large manual/fuzzing effort beyond what could be completed here.

### Recommendation
- Wrap every asynchronous recursive `evaluate()` invocation chain in `formula/evaluation.js` (and `formula/validation.js`) with a top-level safety net, e.g. a `try/catch` around each `evaluate` callback body or a global `domain`/`process.on('uncaughtException')`-style guard specifically scoped to AA/formula execution, converting internal assertion failures into a graceful `setFatalError`/bounce rather than an uncaught throw.
- Replace all internal "should never happen" `throw Error(...)` calls inside `evaluate()` with calls to `setFatalError(...)` (the existing graceful-failure mechanism already used pervasively in this file) so that any assumption violation results in formula/AA failure instead of a process crash.
- Add fuzz/differential testing between `formula/grammars/oscript.ne`, `formula/validation.js`, and `formula/evaluation.js` to find AST shapes accepted by the grammar/validator but mishandled by the evaluator, analogous to how the CEL-rust fix hardened the parser/visitor against malformed-but-parseable inputs.

### Proof of Concept
A concrete triggering formula was not identified in this session (would require systematic differential fuzzing of the `oscript` grammar against `validation.js` and `evaluation.js` to find a specific AST that reaches one of the identified `throw Error(...)` sites while surviving validation). The structural PoC is the code pattern itself: any oscript formula whose AST, after passing `formula/validation.js`, causes `formula/evaluation.js`'s `evaluate()` to execute one of:
```
throw Error("test evaluated to object " + res);          // formula/evaluation.js:1472
throw Error("unknown op: " + op);                          // formula/evaluation.js:2051
throw Error("neither local nor remote: " + funcInfo);       // formula/evaluation.js:2425
throw Error("unrecognized function argument: " + func_expr);// formula/evaluation.js:3132
throw Error("args is not an array");                        // formula/evaluation.js:3341
```
will crash the node process via an uncaught exception, since these throws occur inside async callback chains outside the `try/catch` that only guards `parser.feed()`.
