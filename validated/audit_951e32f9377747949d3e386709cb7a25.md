### Title
Cross-tenant commit status forgery via unscoped `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Commit#refresh_statuses!` correctly scopes every GitHub status pull to the owning stack's own repository via `stack.github_api.statuses(github_repo_name, sha, ...)`, but the webhook-driven `StatusHandler#process` looks up commits by `sha` alone across the entire `commits` table with no repository/stack scoping before calling `commit.create_status_from_github!(params)`. An attacker who controls a repository wired to Shipit (their own repo/stack) can send a legitimately-signed `status` webhook whose `sha` collides with a commit that also exists in a victim stack (e.g., a shared/forked commit history), causing their attacker-controlled `state`/`description`/`target_url`/`context` to be written onto the victim's commit, potentially flipping it to `success` and unblocking deploy/merge/continuous-delivery logic for that unrelated stack.

### Finding Description
The broken binding: **the repository context bound to `stack.github_api.statuses(github_repo_name, sha)` in `refresh_statuses!`** MUST equal **the repository context used before `StatusHandler#process` calls `commit.create_status_from_github!(params)`**, but the latter has none.

- `Commit#refresh_statuses!` and `Commit#create_status_from_github!` at [3](#0-2)  — the pull path always fetches statuses via the commit's own `stack.github_api`, scoped to `github_repo_name` (delegated to `stack`, see [4](#0-3) ). `create_status_from_github!` itself does no scoping — it trusts its caller to have already bound the correct commit/stack.
- Every other webhook handler scopes to a specific repository before acting: `Handler#stacks` resolves `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) , and handlers like `PushHandler#process` use `stacks.not_archived.where(branch:)` [5](#0-4) , or `PullRequestClosedHandler` resolves `repository` from `params.repository.full_name` before touching any stack [6](#0-5) .
- `StatusHandler#process`, uniquely, ignores `repository_name`/`stacks` entirely and does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) . The `params` schema for `StatusHandler` doesn't even require a `repository` field [7](#0-6) .
- `WebhooksController#verify_signature` only authenticates that the payload came from the GitHub App registered for `repository_owner` (`params.dig('repository','owner','login')`) [8](#0-7) . It proves the sender legitimately controls *some* repository owned by that org/owner — it does **not** prove that the `sha` in the payload belongs to that repository, nor does it constrain which `Commit` rows (from any stack, any repo) get matched downstream. Because Shipit is multi-tenant (many stacks/repos share one Shipit install), this signature check does not bind the webhook to the specific victim stack at all.

Exploit flow: attacker configures/owns a repository integrated with Shipit (a legitimate, low-privilege action — e.g., a public fork of the same upstream as the victim's repo, so they naturally share commit SHAs from common history). Attacker triggers (or directly POSTs, since they control their own repo's real webhook secret) a `status` event with `sha` equal to a commit that also exists in the victim's stack's `commits` table, and arbitrary `state`/`context`/`description`/`target_url`. `StatusHandler#process` matches by `sha` alone and calls `create_status_from_github!` on every matching `Commit` row regardless of which stack/repo it belongs to, mutating the victim commit's status.

### Impact Explanation
A cross-tenant write: an attacker-controlled webhook payload can create a `Status` record on a commit belonging to a stack/repository the attacker does not control, potentially setting `state: 'success'` on a `deployable?`/`blocking?` context. Per `Commit#deployable?` and `Stack` continuous-delivery scheduling (`schedule_continuous_delivery`), this can affect deploy-readiness decisions and merge-queue processing (`ProcessMergeRequestsJob`) for the victim stack. This matches "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy, rollback or merge" — Critical, cross-tenant.

### Likelihood Explanation
Requires: (1) attacker owns/controls a repository that is itself onboarded as a Shipit stack (so they can send a validly-signed webhook), and (2) a commit `sha` collision between attacker's repo and the victim's stack's commits table — realistic for forks of the same upstream project or repositories sharing history, as called out in the preconditions ("shared-sha commit in victim stack"). No secrets, sessions, or privileged roles are needed beyond controlling one's own onboarded repository's webhook, matching the unprivileged-attacker threat model. Repeatable per matching commit/stack pair.

### Recommendation
Scope `StatusHandler#process` the same way every other handler does: resolve `repository = Repository.from_github_repo_name(params.repository.full_name)` (require `repository.full_name` in the `params` schema) and only update commits belonging to `repository.stacks` (e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { id: repository.id })`), mirroring the scoping already used in `Handler#stacks`.

### Proof of Concept

```ruby
test "does not mutate a commit belonging to a different repository/stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit) # repo shopify/shipit-engine
  attacker_stack = shipit_stacks(:cyclimse) # different repo/owner
  shared_sha = "cafebabe" * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => attacker_stack.repository.full_name,
                       "owner" => { "login" => attacker_stack.repository.owner } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Compare against `refresh_statuses!`, which is always properly scoped:
```ruby
test "refresh_statuses! only ever queries github_api scoped to the commit's own stack" do

```
Run the first test against current code: it fails (the victim commit gains a status), proving `StatusHandler#process` breaks the repository-scoping invariant that `refresh_statuses!` upholds.
