### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository scoping, letting a legitimately-signed webhook for an attacker's own repo mutate a victim stack's commit and flip `blocked?`/`deployable?` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no repository or stack scoping, unlike every other handler in this engine which resolves `stacks` via `Repository.from_github_repo_name(repository_name)`. Because a git SHA1 is a function of commit content (tree, parents, author/committer, message, timestamps) and not of the remote repository, an attacker who owns/controls their own GitHub repository can craft a commit whose SHA collides with a commit that already exists in a victim's Shipit stack, then send a genuinely-signed `status` webhook for their own repo that gets applied to the victim's `Commit` record.

### Finding Description
The broken invariant, stated as an equality that should hold but doesn't:

`StatusHandler#process` should only mutate commits where `commit.stack.repository.full_name == payload['repository']['full_name']`, but instead it mutates every `Commit` where `commit.sha == params.sha`, regardless of `stack_id`/repository: [1](#0-0) 

Contrast with the pattern used elsewhere in the same handler hierarchy, which correctly scopes to the authenticated repository via `Handler#stacks`: [2](#0-1) 

`WebhooksController#verify_signature` only proves the payload is genuinely signed for the *organization named in the payload's own `repository.owner.login`* — it does not, and cannot, constrain which `Commit` rows the handler is allowed to touch: [3](#0-2) 

Exploit flow:
1. Attacker owns/controls a GitHub repository (e.g. a public fork or a throwaway repo) that is registered under `Shipit.github_teams`'s organization app (any org Shipit is configured for) or under an org Shipit already trusts — signature verification is per-organization via `Shipit.github(organization: repository_owner)`, so the attacker only needs a repo whose owning org has a Shipit GitHub App installed, which is common for any public/organization repo Shipit already watches.
2. Attacker crafts (or locates) a commit in their own repository whose SHA1 is identical to a commit that already exists in a victim stack's `commits` table — e.g. an empty/well-known commit, a cherry-picked/rebased commit that is bit-for-bit identical (same tree, parents, author, committer, timestamps, message), or simply reusing a SHA the attacker already knows is shared (mirrors, forks, vendored history).
3. Attacker triggers GitHub to send a `status` event for that commit with `context: "ci/lint"` and an attacker-chosen `state` (`success` or `failure`). GitHub signs this webhook correctly because it's a real event for the attacker's own repo.
4. `WebhooksController#verify_signature` passes (real signature, real org).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this returns **every** `Commit` row across **every** stack with that SHA, including the victim's, and writes a `Shipit::Status` against it via `statuses.replicate_from_github!(stack_id, github_status)`: [4](#0-3) 
6. If the victim stack has `blocking_statuses` configured to include `ci/lint`, `Commit#blocked?` re-evaluates using the forged status: `blocking?` is `!success? && commit.blocking_statuses.include?(context)`: [5](#0-4) [6](#0-5) 
   - Setting `state: success` clears the block, unblocking deploys/merges on the victim stack.
   - Setting `state: failure`/`error` sets the block, halting the victim's legitimate deploy pipeline.
7. `add_status` in `Commit` additionally triggers `stack.schedule_merges` when the new status is `pending?`/`success?`, and can fire `deployable_status`/`commit_status` hooks, further propagating the forged state into the victim's continuous-delivery flow: [7](#0-6) 

No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) prevents this because none of them look at, or constrain, which repository's commits the handler is permitted to write — they only validate that the JSON is well-formed and the *sender's own* organization signature is valid.

### Impact Explanation
A fully valid, GitHub-signed webhook for a repository the attacker controls can write `Shipit::Status` rows against commits belonging to an unrelated victim stack/repository, as long as a SHA collision (which the attacker can deliberately construct via identical commit content) exists. This directly matches the Critical category "a payload for one repository mutating another's stack, commit, task or task or team, or an unauthorized deploy, rollback or merge": it can force `Commit#blocked?` to flip, gating or releasing deploys on a stack the attacker never authenticated against. It's repeatable against any stack/repository as long as the attacker can produce or find a colliding SHA and knows (or guesses) a `context` value present in the victim's `blocking_statuses`/`required_statuses` configuration.

### Likelihood Explanation
Preconditions: the victim stack must have `blocking_statuses` (or `required_statuses`) configured for a `context` the attacker uses, and a SHA collision must exist between the attacker's own commit and a commit already tracked in the victim stack. Producing an exact SHA1 collision (not just "same content by chance", but a deliberately identical commit — same tree, parents, author, committer, timestamps, message) is feasible when the attacker can observe the victim's commit history (e.g., public/open-source repositories, forks, mirrors, or shared history via merges/rebases) and reproduce a commit with byte-identical content in a repo they control. This is not a brute-force SHA1 collision attack; it only requires duplicating already-known commit content, which is straightforward for any commit whose full metadata is public. Attacker cost is low (own a GitHub repo, push/label a matching commit, wait for GitHub to fire the `status` webhook or send one via an authorized integration on their own repo) and the attack is repeatable per SHA/context pair.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the pattern used in `Handler#stacks`/other handlers, e.g. resolve the stacks for `repository_name` first and then restrict the `Commit` lookup to `commit.stack_id` within those stacks (`Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), so a status can never be applied to a commit belonging to a stack outside the authenticated repository.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` conceptually):
1. Create `repository_a` ("attacker/repo") and `repository_b` ("victim/repo") with distinct `Stack`s, `stack_a` and `stack_b`.
2. Create `commit_b = Commit.create!(stack: stack_b, sha: "deadbeef" * 5)` (40-hex) with no statuses yet. Configure `stack_b`'s deploy spec/`blocking_statuses` to include `"ci/lint"`.
3. Assert precondition: `commit_b.blocked?` is `false` before any status exists (no blocking commit yet is a separate case — instead seed a *newer* blocking commit and confirm `stack_b.commits.reachable...any?(&:blocking?)` becomes true only after the forged status).
4. Build a payload shaped as if it came from `repository_a` (`payload['repository']['full_name'] == "attacker/repo"`) but with `sha: commit_b.sha`, `context: "ci/lint"`, `state: "success"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check, since the finding is that signature verification is orthogonal to the scoping bug).
6. Assert: `commit_b.reload.statuses.last.context == "ci/lint"` and `commit_b.blocked?` (or `stack_b.commits...blocked?`) changed state — i.e., a status was written to `stack_b`/`commit_b` even though the payload's `repository.full_name` was `"attacker/repo"`, proving `commit.stack_id != Repository.from_github_repo_name("attacker/repo")&.stacks&.pluck(:id)&.include?(commit.stack_id)` yet the write still succeeded — violating the stated invariant that "a status for `ci/lint` only affects the repository that authenticated it."
