## Analysis

The audited pattern (splitting a total amount proportionally across multiple recipients with `amount = total * share / total_share`, causing dust to be gained or lost to rounding) has a direct analog in `ocore`'s headers-commission distribution logic, and it is reachable by any ordinary user who authors a multi-author unit.

### Root cause

When a child unit has more than one author (or explicitly redistributes its commission), the unit itself specifies how the earned headers commission is split via `earned_headers_commission_recipients`. Validation only requires the shares to be positive integers summing to exactly 100 — it does not constrain how the rounding of `headers_commission * share / 100` behaves: [1](#0-0) 

The actual split is computed with simple rounding, once in SQL for MySQL and once in JS for SQLite, with no compensating "remainder to last recipient" step: [2](#0-1) [3](#0-2) 

The resulting per-recipient rows are inserted into `headers_commission_contributions` and later simply summed per `(main_chain_index, address)` into the spendable `headers_commission_outputs` table — again, with no cross-check against the original `headers_commission` amount actually earned by the payer unit: [4](#0-3) 

### Why this differs from the report (and is worse)

In the Sherlock report, `Math.round`-style rounding of a proportional split can only ever **lose** dust (sum of parts ≤ total, when using floor-like truncation). Here, standard "round half up" is used for **each independent recipient share**, which means the sum of the rounded parts can be *either* less than *or greater than* the original `headers_commission`. For example, with two recipients at 50%/50% and an odd `headers_commission` of `7`: `round(7*0.5)=4` for each, summing to `8` instead of `7`.

Since `headers_commission_outputs` becomes real spendable base-currency (bytes) balance later spendable via `headers_commission` type inputs, this discrepancy is not merely "dust stuck in a contract" — it is new base currency created (or destroyed) that was never actually paid by the parent unit(s).

### Reachability

Any unpriviledged unit poster can:
1. Post a multi-authored unit (or a single-authored unit that explicitly redistributes its commission) naming `earned_headers_commission_recipients` with addresses they control and share percentages chosen to maximize positive rounding drift (e.g., all shares at `x.5%` boundaries relative to typical `headers_commission` values).
2. Get that unit accepted as the "winning child" for headers commission from one or more parent units in the normal DAG-growth process (no special privilege needed — winning is essentially a hash-based lottery among candidate children, so an attacker can also try repeatedly / use many addresses to increase odds over time).
3. Each time this happens, the attacker's chosen recipients collectively receive slightly more bytes than the parent unit(s) actually paid, which get aggregated unconditionally into `headers_commission_outputs` — spendable balance.

Repeated over many units/main-chain indices, this is a systematic (if small-scale per event) inflation of the byte supply beyond what miners'/authors' units actually paid in commissions, which violates the invariant that total headers commission distributed must equal total headers commission collected.

### Title
Rounding drift in `earned_headers_commission_recipients` split can mint extra bytes (supply inflation) - (File: `headers_commission.js`)

### Summary
`calcHeadersCommissions` splits a payer unit's `headers_commission` across `earned_headers_commission_recipients` using independent `ROUND()`/`Math.round()` calls per recipient share, then sums these rounded contributions unconditionally into the spendable `headers_commission_outputs` table, with no reconciliation against the actual `headers_commission` amount owed.

### Finding Description
For a winning child unit that declares `earned_headers_commission_recipients` (attacker-controlled, required only to sum to 100 as validated in `validateHeadersCommissionRecipients`), each recipient's share of the commission is computed independently:
- MySQL path: `ROUND(punits.headers_commission*earned_headers_commission_share/100.0)` [5](#0-4) 
- SQLite/JS path: `Math.round(full_amount * share / 100.0)` [6](#0-5)  and [7](#0-6) 

Because rounding is applied per-recipient rather than to a running remainder, the sum of rounded shares can exceed the original `headers_commission` amount (e.g., two 50% shares of an odd total each round up). These per-recipient amounts are inserted into `headers_commission_contributions` and then aggregated with a plain `SUM()` into `headers_commission_outputs` with no cap or correction: [4](#0-3) . `headers_commission_outputs` rows directly become spendable base-currency balance (see its use in `balances.js` and as a spendable `headers_commission`-type input), so any positive rounding drift is minted bytes that were never actually paid by any parent unit.

### Impact Explanation
This breaks the invariant that the total headers commission paid out must equal the total headers commission collected from parent units — i.e., it is a (small but systematic) inflation of the base currency supply. An attacker who controls both the child unit's authors and the recipient addresses can deliberately choose share percentages that maximize positive rounding drift, and can repeat this over many qualifying units/main-chain indices to accumulate free bytes over time.

### Likelihood Explanation
Likelihood is moderate: crafting a multi-author unit with adversarial `earned_headers_commission_recipients` shares requires no special privilege — any wallet can author such a unit. The main constraint is that the unit must actually be selected as the DAG's "winning child" for headers commission (a hash-based selection among candidate children), which an attacker can influence probabilistically by posting many candidate units, and the per-event gain is small (bounded by number of recipients), but it is fully attacker-triggerable and repeatable indefinitely.

### Recommendation
Compute recipient shares using an integer proportional-allocation scheme that guarantees the sum of parts equals the original `headers_commission` exactly — e.g., round all but the last recipient normally and assign the last recipient `full_amount - sum_of_previous_amounts`, analogous to the audit's suggested fix. Apply this fix consistently in both the MySQL SQL-based path and the SQLite JS-based path in `headers_commission.js`.

### Proof of Concept
1. Author a 2-of-2 unit (or otherwise multi-authored unit) with `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]`, where `A` and `B` are both attacker-controlled.
2. Get this unit accepted as the DAG's winning child for a parent unit whose `headers_commission` is an odd number (e.g. `7`).
3. `calcHeadersCommissions` computes `round(7*0.5)=4` for both `A` and `B`, inserting `4+4=8` total into `headers_commission_contributions` instead of `7`.
4. This `8` is summed unconditionally into `headers_commission_outputs`, becoming `8` bytes of real spendable balance for the attacker's addresses A/B — 1 byte more than the parent unit actually paid, with no corresponding burn elsewhere.
5. Repeating this across many stable units cumulatively inflates the byte supply.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
