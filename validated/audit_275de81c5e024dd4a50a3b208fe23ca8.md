### Title
Asset holders can permanently lose transferable balance if the asset's attestor list changes after they received coins - (File: `validation.js`, `storage.js`)

### Summary
Obyte's `spender_attested` asset type mirrors the PayoutManager eligibility-gate pattern: a payment output can only be spent by its holder if, at the moment of the *spend*, the holder is on the asset's *current* list of attested addresses. That list is entirely mutable by the asset definer via an `asset_attestors` message. If the definer rotates the attestor list (e.g., replaces attestor A with attestor B) after a holder received coins while attested by A, and the holder is never re-attested by B, the holder's coins become permanently unspendable — with no protocol-level mechanism to recover or redirect them, exactly like the PayoutManager bug where a post-deposit AML score change locked both investor and admin out of the funds.

### Finding Description
When an asset is defined with `spender_attested: true`, every payment spending or receiving that asset must satisfy the attestation check at validation time, not at issuance time: [1](#0-0) 

For outputs (i.e., who is *allowed to receive/later spend* the coin), the check re-runs against the attestor list that is current as of `last_ball_mci` of the spending unit: [2](#0-1) 

and again at spend time for the specific input owner address: [3](#0-2) 

The attestor list used for this check is always the *single latest* list published by the definer, not the list that was active when the holder originally received the coins: [4](#0-3) 

`filterAttestedAddresses` only counts an attestation as valid if it comes from an address in that current list and was issued after the address's last definition change — it does not consider whether the attestation was valid under a *previous* attestor list at the time the coins were received: [5](#0-4) 

The asset definer can freely update this attestor list at any time via an `asset_attestors` message, restricted only to the definer: [6](#0-5) 

Consequently: Alice receives `spender_attested` asset coins while attestor A vouches for her. Later, the definer legitimately rotates attestors (removes A, adds B) for business reasons unrelated to Alice. If B never attests Alice, her existing balance — which passed all checks when received — can never again satisfy `objAsset.arrAttestedAddresses.indexOf(owner_address) === -1` in `validation.js:2506` or `storage.js` `filterAttestedAddresses`, so any future payment message spending that output is rejected. Neither Alice nor the definer nor any protocol function can move or reclaim that specific balance; it is permanently stuck, functionally destroying part of the asset's supply that was previously spendable.

This is the direct structural analog of the reported PayoutManager bug: an eligibility condition (`isEligibleAccount`/`checkAccountEligibility` there, `spender_attested` attestor-membership here) is re-evaluated against present-day state at withdrawal/spend time rather than fixed at deposit/receipt time, and no fallback/recovery path (like the report's `revokePayout` fix that returns funds to `capitalRecipient`) exists in ocore for spender-attested assets.

### Impact Explanation
Funds (any `spender_attested` asset balance) become permanently frozen for legitimate former-eligible holders through no fault of their own, purely as a side effect of the definer performing an ordinary attestor-list update. Because `spender_attested` also gates transfers between addresses (`some output addresses are not attested` check in `validation.js:2637`), the coins cannot be sent to a fallback attested address, cannot be returned to the definer for manual handling, and cannot be reissued. This is a permanent loss of access to funds — a Medium-severity fund-freezing issue, matching the severity of the original report.

### Likelihood Explanation
Attestor list rotation is an expected, documented feature (`must subsequently publish and update the list of trusted attestors` per the `assets` table schema) — definers are expected to use it over an asset's lifetime (e.g., to add/replace KYC providers). Any coin holder whose sole attestation came from a since-removed attestor is affected as soon as the list changes, with no action required by the holder. This makes the scenario realistically and repeatably triggerable in normal asset-lifecycle operation, not merely a theoretical edge case.

### Recommendation
Consider one of:
1. Snapshot/grandfather validity: allow spending if the holder was attested under *any* attestor list that was current at the time they received the output, rather than requiring attestation under only the current list.
2. Add a definer-restricted recovery message (analogous to `revokePayout`) that lets the definer reclaim/redirect balances stuck due to attestor-list changes, with funds routed back to the holder once re-attested or to a defined fallback address.
3. Require that attestor-list updates cannot retroactively invalidate already-attested holders, e.g., by only affecting future issuances/attestations rather than a global "current list" applied to historical balances.

### Proof of Concept
1. Definer issues asset X with `spender_attested: true`, `attestors: [A]`.
2. Attestor A attests Alice's address; Alice receives an output of asset X (passes checks in `validation.js:2115-2122` and `2630-2642`).
3. Definer publishes `asset_attestors` message changing the attestor list to `[B]` (`validateAttestorListUpdate`, `validation.js:2829-2848`; storage lookup always takes the latest list, `storage.js:1917-1946`).
4. Alice (or anyone) attempts to spend/transfer Alice's previously-received output of asset X.
5. `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses` computes `arrAttestedAddresses` using only attestor `B`; Alice, attested only by the now-removed `A`, is excluded (`storage.js:1959-1974`).
6. `validatePaymentInputsAndOutputs`/`validatePayment` reject the spend with `"owner address is not attested"` (`validation.js:2506`) or `"none of the authors is attested"` (`validation.js:2118`), permanently blocking Alice's access to that balance with no recovery path in the codebase.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
