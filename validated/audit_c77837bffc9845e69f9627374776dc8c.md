### Title
Hand-rolled hookify frontmatter parser silently drops mis-indented `action`/`event` keys, downgrading `block` rules to default `warn` - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter` in `config_loader.py` uses a hand-rolled line-based state machine that only recognizes a top-level key when `indent == 0`, and only recognizes a dict-continuation field when `indent > 2` **and** `in_dict_item` is already `True`. Any line with `indent` in `{1, 2}` (or `indent > 2` while not inside an open list dict item) matches none of the parser's branches and is silently dropped with no error, warning, or fallback. If the dropped line is `action: block`, `Rule.from_dict` falls back to its default `action = "warn"`, silently downgrading an intended blocking rule.

### Finding Description
`extract_frontmatter` (`plugins/hookify/core/config_loader.py:87-195`) processes frontmatter line by line using three mutually exclusive branches:
- `indent == 0` and not a list item → top-level key [1](#0-0) 
- `stripped.startswith('-') and in_list` → new list item (plain, or inline comma dict) [2](#0-1) 
- `indent > 2 and in_dict_item and ':' in line` → continuation field of an already-open list-item dict [3](#0-2) 

There is no `else` branch, so a line that is indented (e.g. 1-3 spaces) but does not satisfy the exact conditions of branch 2 or 3 is silently ignored — no key is ever written to `frontmatter`. Concretely, a rule file like:
```
---
name: block-env-writes
enabled: true
event: file
conditions:
  - field: file_path
    operator: regex_match
    pattern: \.env$
  action: block
---
Blocked: attempt to write .env file
```
has `action: block` at indent=2, immediately after a still-open list-item dict (`in_dict_item=True` from the preceding `pattern:` line). This line hits none of the three branches: `indent==0` fails, it doesn't start with `-`, and `indent > 2` fails (indent is 2). The line is dropped with zero diagnostics. `frontmatter` never gets an `action` key, so `Rule.from_dict` (`config_loader.py:75-84`) applies its default: `action=frontmatter.get('action', 'warn')` → `"warn"` [4](#0-3) .

The rule then flows unchanged through `load_rule_file` → `load_rules` (no validation that a rule with intended block semantics actually parsed as `block`) into `RuleEngine.evaluate_rules`, which strictly separates `blocking_rules` from `warning_rules` based on `rule.action == 'block'` [5](#0-4) . A rule that matches but is bucketed as a warning only emits `systemMessage` and returns `{}`/no deny decision, while `PreToolUse`/`PostToolUse` blocking rules emit `permissionDecision: "deny"` [6](#0-5) . So the silently-downgraded rule allows the exact operation (e.g., writing/editing `.env`, or a dangerous `rm -rf`) that the file's plain-text content clearly intends to block, with the file itself looking correct to a human reviewer since 1-3 space indentation differences are visually easy to miss in a markdown diff.

There is no reference-YAML cross-check, no lint step, and no runtime assertion that a `block`-looking rule parsed as `block`; `load_rules` only catches I/O/parsing exceptions, not semantic silent-drop cases [7](#0-6) .

### Impact Explanation
Any actor who can get a `.claude/hookify.*.local.md` rule file merged or written into a project (e.g., via a PR, a generated rule file, or content that an agent is instructed to author) can produce a rule that visually reads as `action: block` for a sensitive target (e.g. `.env`, credentials, `rm -rf`) but is actually enforced as `warn`. This defeats the DENY_MEANS_DENY invariant for hookify-based confinement: the operation is not blocked, only a warning message is shown while the write/bash/stop operation proceeds. This is a scoped confinement/enforcement bypass for whatever guard the rule was meant to provide (file write confinement, dangerous-command blocking, stop-prevention), matching an "unauthorized file action / guard bypass" class of impact rather than a core Claude Code sandbox escape, since hookify is a project-configured plugin, not the platform's built-in permission system.

### Likelihood Explanation
Preconditions are just attacker-controlled content of a rule `.md` file (no execution rights needed), consistent with the stated precondition. The trigger is a very plausible authoring mistake (1-3 space indentation instead of 0), which is easy to introduce deliberately while looking benign in review, and easy to reproduce deterministically — the parser has no randomness and the branch logic is fixed. Because the failure is a silent drop (no error), it is unlikely to be caught by manual review or existing error handling, increasing real-world feasibility.

### Recommendation
Replace the hand-rolled frontmatter parser with a real YAML parser (e.g. `yaml.safe_load`) for the frontmatter block, or, if a custom parser must be kept, add an `else` branch in `extract_frontmatter` that raises/logs on any non-empty, non-comment line that doesn't match a known state, so malformed indentation fails loudly instead of silently dropping keys. Additionally, add a post-parse invariant check in `load_rule_file`/`Rule.from_dict` that rejects (or warns loudly and disables) any rule whose message body or historical intent implies blocking but whose parsed `action` differs from what a reference YAML parse would produce, and validate `action` is only ever `"warn"` or `"block"` in the top-level dict via a strict schema check.

### Proof of Concept
Differential/unit test in `plugins/hookify/core/config_loader.py` (or a new test module):
```python
import yaml
from hookify.core.config_loader import extract_frontmatter

CONTENT = """---
name: block-env-writes
enabled: true
event: file
conditions:
  - field: file_path
    operator: regex_match
    pattern: \\.env$
  action: block
---
Blocked: attempt to write .env file
"""

def test_action_not_silently_dropped():
    fm, _ = extract_frontmatter(CONTENT)
    ref = yaml.safe_load(CONTENT.split('---')[1])
    # Reference parser sees action: block at top level (or at least somewhere non-default)
    assert 'action' in fm, "action key silently dropped by hand-rolled parser"
    assert fm.get('action') == 'block', f"action downgraded to {fm.get('action')!r} instead of 'block'"
```
Expected current behavior: `fm` has no `action` key (assertion fails), demonstrating `Rule.from_dict` will default to `action="warn"` for a file whose author/reviewer intended `block`. A broader fuzz test should generate frontmatter permutations varying indentation of `action`/`event` (0, 1, 2, 3, 4 spaces) both inside and outside an open `conditions` list-item context, parse with `extract_frontmatter`, and assert the resulting `action`/`event` never differs from a `yaml.safe_load` baseline in a `block → warn` (or specified-event → `all`) direction.
