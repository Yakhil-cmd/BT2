## Analysis

I found a concrete analog. The bug class in the report is a TOCTOU/binding mismatch: a check is performed against one scope (the "authorized" balance/org) while the actual privileged action is executed using a different, unchecked value from the same request/session context — i.e., "a stack a token authorises vs a stack it touches."

`Shipit::Api::BaseController` establishes the authorization scoping contract for every API endpoint: a token created with a `stack_id` is meant to be restricted to that one stack, enforced by scoping lookups through `stacks` before resolving `params[:stack_id]`: [1](#0-0) 

`Shipit::Api::CCMenuController` inherits this authorization model (`require_permission :read, :stack`), but overrides the private `stack` helper to resolve `params[:stack_id]` directly against the global `Stack` scope, completely bypassing the `stacks` (i.e., `current_api_client.stack_id?`) restriction that every other controller relies on: [2](#0-1) 

### Title
Stack-scoped API tokens can read any stack's build status via CCMenuController - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` tokens can be scoped to a single stack via `stack_id`, and `Api::BaseController#stack` is supposed to enforce that scoping by resolving `params[:stack_id]` through the `stacks` relation, which is filtered to `current_api_client.stack_id` when present. `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, never checking whether the authenticated token is scoped to a different stack. `#show` only checks `read:stack` permission (a boolean capability, not a per-resource check), so any token with `read:stack` — even one deliberately restricted to a single, low-sensitivity stack — can enumerate and read the build/deploy status of every stack in the Shipit instance.

### Finding Description
The binding that must hold is: `stack a token authorizes == stack the controller action touches`. `Api::BaseController#stacks`/`#stack` implement that binding for the rest of the API surface: [3](#0-2) 

`require_permission :read, :stack` only verifies the client has the `read:stack` capability string in its `permissions` array via `ApiClient#check_permissions!`, it does not verify which stack that permission applies to: [4](#0-3) 

`CCMenuController` re-defines `stack` to look up any stack in the system by the request-supplied `stack_id`, ignoring the client's `stack_id` scope entirely: [2](#0-1) 

Before the request: token `T` is bound to `stack_id = A` (e.g. created via `CCMenuUrlController#client`, which creates an `ApiClient` scoped only by `permissions: %w[read:stack]` with no `stack_id` set at all in that flow, or via a manually scoped client such as fixture `here_come_the_walrus`) — after the request: an attacker holding `T` supplies `stack_id: B` and receives stack `B`'s deploy status, name, and lock state, even though `T` was never authorized for `B`. This is the same class of bug as the report: a value checked at authorization time (`current_api_client.stack_id`) is silently not the value acted upon (`params[:stack_id]` resolved against the unscoped `Stack` table).

### Impact Explanation
This grants unauthenticated-relative-to-scope read access to `Stack` state (name, activity, last build status/label/time, web URL, lock state) for stacks the token was never granted access to. This matches the in-scope High-impact category: "unauthenticated read of stack state, task streams, or deploy output." Any consumer holding a `read:stack`-scoped token for one stack (which is the normal, least-privilege pattern encouraged by `ApiClient.belongs_to :stack, optional: true` and by `CCMenuUrlController`, which mints tokens for exactly this endpoint) can pivot to reading every other stack's build status.

### Likelihood Explanation
High. No special conditions are required beyond possessing any valid API token with the `read:stack` permission (the minimal permission set, and the one `CCMenuUrlController` itself provisions). The attacker only needs to change the `stack_id` route/query parameter to a different stack's `owner/name/environment` param — no signature, secret, or additional credential is needed.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the same authorization-scoped relation as `BaseController`, e.g. `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`, so that stack-scoped tokens cannot escape their `stack_id` boundary.

### Proof of Concept
1. Create (or obtain) an `ApiClient` with only `permissions: ['read:stack']`, either unscoped or explicitly scoped to `stack_id: A` (mirrors `here_come_the_walrus` fixture / the token minted by `CCMenuUrlController#client`).
2. As that client, call `GET /api/stacks/:owner/:repo/:env/ccmenu.xml` (routed to `Api::CCMenuController#show`) using the `stack_id` of a different stack `B` that the token was never granted access to.
3. `require_permission :read, :stack` passes because it only checks the capability string, not the specific stack.
4. `stack` resolves `Stack.from_param!(params[:stack_id])` against the full `Stack` table (bypassing `stacks`/`current_api_client.stack_id` filtering used elsewhere), returning stack `B`.
5. The response renders `B`'s name, lock status, and last build status/label/time — data the token was not authorized to read.
