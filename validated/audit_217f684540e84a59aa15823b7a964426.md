### Title
Single asset with a blacklist-style `transfer_condition` can permanently deny an AA's ability to send a combined multi-asset/multi-recipient response, bouncing the entire response and reverting state - ([File: aa_composer.js])

### Summary
The Sherlock finding describes OpenQ's `ClaimManagerV1` looping over multiple bounty tokens and sending them one-by-one to a winner; if any single token is paused/blacklisted for that winner, the whole transfer loop reverts and the entire claim fails. The analogous ocore mechanism is an Autonomous Agent (AA) response unit that bundles a base-currency payment together with one or more custom-asset payments (each asset can carry an arbitrary `transfer_condition` oscript formula, functioning like a "blacklist/pause" check). When the AA composes and validates its response unit in `aa_composer.js`, all payment messages (base + every asset) are part of one atomic unit; if the `transfer_condition` of just one asset rejects the recipient (or any other participant) for that unit, the entire unit fails validation and the AA `bounce()`s, undoing all balance/state changes for every output in that response — not just the one asset whose condition failed.

### Finding Description
When an AA trigger produces payment messages, `sendUnit()` in `aa_composer.js` assembles all payment messages (base asset + custom assets) into a single unit and attempts to validate and save it: [1](#0-0) 

Each asset payment message is validated through `validatePaymentInputsAndOutputs`, which — for assets that define a `transfer_condition` — evaluates that formula via `Definition.evaluateAssetCondition` and fails the whole payment (and therefore the whole unit) if the condition is not satisfied: [2](#0-1) 

Asset definitions (which anyone — including an AA itself via an `asset` message — can create) allow an arbitrary `transfer_condition` oscript formula, validated at definition time: [3](#0-2) [4](#0-3) 

Because `transfer_condition` is an arbitrary boolean oscript formula (can reference `data_feed`, output addresses, timestamps, etc.), it can be crafted to systematically reject transfers to specific addresses — functioning exactly like a blacklist/pause mechanism on an ERC20 token. If an AA response bundles a payment in that asset together with payments in other assets/base currency to the same or other addresses (a very common pattern, e.g., the option/futures-contract patterns shown in `test/samples/option_contract.oscript` and `test/samples/futures_contract.oscript`, and the merge logic in `mergeMessagesAndOutputs`): [5](#0-4) 

...then a single blacklisted/failing asset condition causes `validateAndSaveUnit` to fail, and the AA calls `bounce(err)`, reverting all balance updates and state changes for the entire response, including the unrelated, otherwise-valid asset/base payments: [6](#0-5) 

This is analogous to the OpenQ bug: the "all-or-nothing" nature of a single unit containing many independent payments means one poisoned/blacklisted asset denies delivery of everything else bundled with it.

### Impact Explanation
Any AA that distributes multiple assets (e.g., reward/prize distribution, DEX/AMM payouts, futures/options settlement as seen in the option/futures oscript samples) in the same response unit is exposed: if one of the assets involved has a `transfer_condition` that can reject a specific recipient (a condition an asset issuer — an ordinary, unprivileged user — controls when defining the asset), then every trigger that would produce a combined payment including that asset to that recipient permanently bounces. This causes denial of service for the entire response (loss of funds/rewards to legitimate other recipients bundled in the same unit, and repeated wasted bounce fees for the triggering user), and can be a persistent/permanent block if the condition is deterministic (e.g., checks a fixed address or an oracle-controlled blacklist feed), which is exactly the "no partial send" problem described in the source report.

### Likelihood Explanation
This requires: (1) an AA that pays multiple assets/parties in a single response, and (2) at least one of those assets having a `transfer_condition` that can fail for a specific address. Both conditions are entirely under the control of unprivileged actors — anyone can issue a custom asset with a `transfer_condition` formula, and AA authors commonly combine several asset payments per trigger (as shown in the test samples). Given ocore's atomic-unit design, this is a natural consequence of the protocol architecture rather than an edge case, making likelihood moderate-to-high wherever AAs bundle third-party-defined assets with attacker-influenceable conditions into a single response with base-currency or other-asset outputs.

### Recommendation
- Document/require AA developers to isolate risky, condition-bearing asset payments (assets with `transfer_condition`/`spender_attested` they do not control) into separate, dedicated response units/messages rather than merging them with other guaranteed payments, so a failure in one does not block the rest.
- Consider adding an AA-facing primitive to "try" a payment and catch/ignore its failure without bouncing the whole trigger (e.g., an oscript function that pre-checks `transfer_condition`/`spender_attested` before including the output), or evaluate feasibility of splitting a trigger's response into independent sub-units per asset so a `transfer_condition` failure on one asset does not revert unrelated outputs.
- At minimum, warn AA authors in documentation that mixing externally-defined, condition-bearing assets with other payments in a single AA response creates an atomic all-or-nothing dependency that untrusted asset issuers can exploit to block legitimate distributions.

### Proof of Concept
1. Attacker (or any user) issues a custom asset `X` with a `transfer_condition` oscript formula that evaluates false whenever the output address equals `victim_address` (functionally a blacklist), as permitted by asset definition validation: [7](#0-6)  and evaluated per-payment in [2](#0-1) .
2. `victim_address` participates as a counterparty in an AA (e.g., a market-maker/AMM/option contract like `test/samples/option_contract.oscript`) that, on a given trigger, must pay out both asset `X` and base bytes (or another asset) to `victim_address` in the same response unit, as illustrated by the combined payment messages in that sample.
3. When the trigger fires, `sendUnit()` bundles the base and asset `X` payment messages into one unit and calls `validateAndSaveUnit`: [6](#0-5) .
4. Validation of the asset `X` payment fails the `transfer_condition` check for `victim_address`, causing the whole unit (including the unrelated base-currency payout) to fail and the AA to `bounce()`, reverting all balance/state changes for that trigger.
5. Every subsequent attempt by `victim_address` (or anyone whose payout is bundled with asset `X` to that address) to trigger this AA fails identically, permanently denying the payout — mirroring the "no partial send" failure mode from the referenced OpenQ report.

			let objMergedMessage = assocMergedMessagesByAsset[asset];
			if (!objMergedMessage) {
				objMergedMessage = { app: 'payment', payload: { outputs: [] } };
				if (payload.asset)
					objMergedMessage.payload.asset = payload.asset;
				assocMergedMessagesByAsset[asset] = objMergedMessage;
				arrMergedMessages.push(objMergedMessage);
			}
			for (let output of payload.outputs) {
				if (output.amount === undefined) { // send-all output, don't merge with anything
					objMergedMessage.payload.outputs.push(output);
					continue;
				}
				const existing_output = objMergedMessage.payload.outputs.find(o => o.address === output.address && o.amount !== undefined);
				if (existing_output)
					existing_output.amount += output.amount;
				else
					objMergedMessage.payload.outputs.push(output);
			}
		}
		return arrMergedMessages;
	}
