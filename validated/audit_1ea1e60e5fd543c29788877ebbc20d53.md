### Title
Nested contract instantiation bypasses `InstantiateOrigin`/`UploadOrigin` permission checks - ([File: substrate/frame/contracts/src/lib.rs])

### Summary
`pallet-contracts` exposes `Config::UploadOrigin` and `Config::InstantiateOrigin` to let a chain restrict *who* is allowed to deploy or instantiate contract code [1](#0-0) . These checks are only performed inside the top-level dispatchables `instantiate_with_code`/`instantiate` [2](#0-1) . The project's own prdoc for this feature explicitly documents that the restriction "is not enforced when a contract instantiates another contract" [3](#0-2) .

### Finding Description
`InstantiateOrigin::ensure_origin` is only invoked when a *signed extrinsic* directly calls `Pallet::instantiate`/`instantiate_with_code` [2](#0-1) . When a contract itself calls the `seal_instantiate` host function (`ctx.ext.instantiate(...)` in `exec.rs`, reached via the wasm/pvm runtime shims) to spin up a nested contract, that call path resolves the target executable purely from an attacker-supplied `code_hash` and never re-checks `InstantiateOrigin` — the origin used for storage/deposit accounting is the calling contract's account, not a re-validated `Signed` origin subject to `T::InstantiateOrigin`. This is analogous to the LDAP Account Manager bug class: a privileged "who may construct this object" gate exists at one entry point (the top-level dispatchable / LAM's controlled instantiation flow) but a second, less-scrutinized code path (nested contract-to-contract instantiate / LAM's other instantiation site) allows an attacker to drive instantiation of an arbitrary, otherwise-restricted "class" (contract code) without going through the gate.

Concretely: any already-deployed, publicly callable contract (deployed once by a permissioned account, or any contract with unrestricted `call` access) can, in its `call`/`deploy` body, invoke `seal_instantiate`/`instantiate_v2` with an attacker-chosen `code_hash` argument that is fully attacker-controlled input data passed through the contract's own call parameters. This lets an unprivileged, non-permissioned caller cause instantiation of contract code that the chain's `InstantiateOrigin` policy intended to restrict to a permissioned allow-list, as long as that code was previously uploaded (uploads are separately gated by `UploadOrigin`, but any code uploaded by a legitimate permissioned party — or itself reachable through the same nested-instantiate bypass if `UploadOrigin`/`Contains` filters are similarly scoped only at top level — becomes instantiable by anyone via this path).

### Impact Explanation
On any chain that configures `pallet-contracts` with a restrictive `InstantiateOrigin` (e.g., permissioned/compliance parachains that intend "only allow-listed accounts may deploy new contract instances"), this gap lets non-allow-listed users spin up new instances of restricted code through an intermediary public contract, defeating the governance/compliance control the runtime configured. This is a genuine integrity break of an explicit access-control primitive exposed by FRAME, though it does not directly cause loss of funds, unbacked issuance, or code execution outside the sandbox — the "code execution" is still confined to the deterministic Wasm/PVM contract sandbox, unlike the referenced CVE's native RCE.

### Likelihood Explanation
Requires a chain to (a) actually configure non-default `InstantiateOrigin` (default is `EnsureSigned`, i.e., no restriction, so most chains are unaffected), and (b) have at least one publicly-callable contract already deployed that can be induced to call `seal_instantiate` with attacker-supplied `code_hash`. The Polkadot SDK itself already documents this as a known, accepted limitation of the feature (via the prdoc) rather than a silent defect, which weighs against classifying it as a new, undisclosed vulnerability.

### Recommendation
If bounty scope treats "known/documented limitations" as out of scope, this finding should be downgraded/rejected — the maintainers already disclosed the gap in the PR's own documentation. If it is to be treated as a defect, the fix would be to propagate/re-check `InstantiateOrigin` (or an equivalent nested-instantiation policy) inside `Exec::instantiate` in `exec.rs`, not only in the pallet's dispatchable entry points, or to clearly document that `InstantiateOrigin` only governs top-level, not contract-to-contract, instantiation so runtime designers do not rely on it as a strong isolation guarantee.

### Proof of Concept
Not executed. The prdoc text itself is the primary evidence of the documented gap [3](#0-2) ; a full runtime-level reproduction (custom `InstantiateOrigin` filter + a deployed "proxy" contract calling `seal_instantiate` with an attacker-chosen `code_hash` from an unprivileged signed origin) was not built or run in this session due to tool/iteration limits. This should be treated as **unverified/likely a known, already-disclosed limitation** rather than a novel critical vulnerability; I could not confirm any bounty-eligible live chain actually enables a restrictive `InstantiateOrigin` in a way that this bypass would matter.
