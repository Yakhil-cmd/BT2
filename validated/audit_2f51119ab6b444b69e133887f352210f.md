### Title
`Commit.where(sha: params.sha)` has no repository/stack scoping, letting a signed webhook from one repository set commit status on identical-sha commits in unrelated stacks - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` [1](#0-0)  without any repository or stack filter, unlike `PushHandler`, which explicitly scopes to `stacks` derived from `payload['repository']['full_name']` before acting [2](#0-1) . The `where(sha:)` clause is a strict equality (no SQL injection), but because `sha` is not unique across repositories (fork networks, mirrors, and any repos that share commit history produce identical SHA-1 objects), one legitimately-signed `status` webhook from an attacker-controlled repository can update the commit status of every `Commit` record across every stack that happens to share that sha.

### Finding Description
The claimed broken binding, verified as an equality: `Commit.where(sha: params.sha)` == `Commit.where(sha: params.sha)` with **no** `stack_id`/repository predicate, versus the correctly scoped `stacks.not_archived.where(branch:)` used by `PushHandler`. Both sides of the "binding" (the sha value and the actual row set touched) diverge as soon as more than one stack contains a `Commit` with the same `sha`, because nothing in `Handler#stacks`/`repository_name` is consulted inside `StatusHandler#process` even though the base `Handler` class already exposes a `stacks` helper scoped by `Repository.from_github_repo_name(repository_name)` [3](#0-2)  — `StatusHandler` simply never calls it.

`ExplicitParameters` for this handler only requires `sha`/`state` as plain strings with no format or repository binding [4](#0-3) , and `WebhooksController#verify_signature` authenticates the webhook only against the **sending repository's organization** (`Shipit.github(organization: repository_owner)`) [5](#0-4)  — it never validates that the `sha` in the payload actually belongs to a commit reachable from that same repository. So an attacker who owns/controls a repository that is legitimately wired to Shipit (i.e., under an org Shipit already trusts) can emit a real, correctly-signed `status` event naming a `sha` value that is byte-identical to a commit that also exists in a completely different stack (trivially achievable via a fork sharing history with the target's tracked repo, since Git commit ids are content-addressed and identical across forks that share that commit). `Commit#create_status_from_github!` then writes a new `Status` and, if it flips `deployable?`/`blocked?`, triggers `stack.schedule_merges` and `schedule_continuous_delivery` [6](#0-5)  for a stack the attacker never authenticated against.

None of the existing guards prevent this: `verify_signature` only proves "this org sent it," not "this sha belongs to this repo"; the `ExplicitParameters` schema imposes no sha/repo binding; and there is no `stacks`/repository filter anywhere in `StatusHandler#process`.

### Impact Explanation
A single forged-but-validly-signed status webhook can mutate `Status` records for commits belonging to stacks/repositories the attacker does not control, and because status changes can flip a commit's `deployable?` state, this can trigger `stack.schedule_merges` and continuous-delivery deploy scheduling for an unrelated stack — i.e., a payload for one repository mutating another repository's stack/commit and potentially causing an unauthorized deploy, matching the "Critical" category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). It is repeatable against any stack whose tracked commits share a sha with a commit reachable by the attacker's own repository (fork-sharing scenario), and blast radius spans every stack in the Shipit instance that has ever recorded that sha.

### Likelihood Explanation
Exploitability requires: (1) the attacker owns/controls a repository under a GitHub organization that Shipit already trusts (so `verify_signature` passes for a webhook the attacker can trigger, e.g. by setting a commit status via the GitHub API on their own repo), and (2) a genuine sha collision — practically, forking or sharing history with a repo tracked by the target stack so an identical commit object exists in both. This is a real but conditional precondition (not a hash-forgery, just fork-sharing of commit objects), making it feasible in any Shipit deployment where a GitHub App/organization webhook secret is shared across multiple repositories the attacker can influence, but not universally trivial since it depends on actual sha overlap rather than attacker-chosen arbitrary shas matching arbitrary victims.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` does: resolve the target commits via `stacks.joins(...).where(sha: params.sha)` (i.e., restrict to `Commit`s belonging to stacks under `Repository.from_github_repo_name(repository_name)`) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (illustrative)
test "sha equality has no repository scope" do
  sql = Shipit::Commit.where(sha: 'x').to_sql
  assert_match(/WHERE .*"sha" = 'x'/, sql)
  refute_match(/stack_id/, sql)
  refute_match(/repository/, sql)
end

test "a status webhook updates commits across unrelated stacks sharing the same sha" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclone) # a different, unrelated stack/repository

  commit_a = stack_a.commits.create!(sha: 'deadbeef', author: nil)
  commit_b = stack_b.commits.create!(sha: 'deadbeef', author: nil)

  payload = { 'sha' => 'deadbeef', 'state' => 'success', 'context' => 'ci' }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert commit_a.reload.statuses.exists?(state: 'success')
  assert commit_b.reload.statuses.exists?(state: 'success')
  # both stacks' commits mutated by one webhook payload naming only a sha, with no repository scoping
end
```
