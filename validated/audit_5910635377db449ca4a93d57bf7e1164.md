## Title
`Api::CCMenuController` bypasses `ApiClient` stack scoping, allowing a scoped token to read state of stacks it was not authorized for - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The reported bug class is a reentrancy issue that breaks the binding between "what the relayer intends to execute" and "what actually executes," letting an attacker desynchronize authorization from execution. The equivalent binding in this Rails engine is the one explicitly called out in the rules: **the stack a token authorizes vs. the stack it touches**. `Shipit::Api::BaseController` establishes this binding via a scoped `stacks` relation, but `Shipit::Api::CCMenuController` overrides `#stack` and looks the stack up directly from `Stack`, skipping the scoping relation entirely.

### Finding Description
`Shipit::Api::BaseController` is the base for all API controllers and defines the authorization binding for a scoped `ApiClient`: [1](#0-0) 

`stacks` restricts the accessible set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a specific stack, and `stack` looks up `params[:stack_id]` **within that scoped relation** (`stacks.from_param!`). This is the binding: `ApiClient#stack_id` (what the token authorizes) == the stack acted upon.

`Shipit::Api::CCMenuController` inherits from `BaseController` and also declares `require_permission :read, :stack`, relying on the same authorization framework: [2](#0-1) 

However, it defines its own private `stack` method that does **not** go through the scoped `stacks` relation:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This looks up any stack in the entire application directly from `Stack`, not from `current_api_client`'s scoped `stacks`. `require_permission!(:read, :stack)` (from `BaseController`) only checks that the client's `permissions` array includes `'read:stack'`, it does not verify that the `stack_id` in the URL matches the client's `stack_id`: [3](#0-2) [4](#0-3) 

Contrast this with `Shipit::Api::StacksController` / other API controllers that rely on the inherited `stack` from `BaseController`, correctly scoping lookups through `stacks.from_param!`, as exercised in tests like "an api client scoped to a stack will only see that one stack": [5](#0-4) 

So an `ApiClient` created with a `stack_id` (i.e., intentionally restricted to one stack, per `ApiClient` model: `belongs_to :stack, optional: true`) and only the `read:stack` permission — the least-privileged, "safe" configuration an operator can hand out (e.g., for embedding a CI status badge/CCMenu widget for one specific project) — can use its valid, unmodified authentication token against the `ccmenu#show` route for **any** `stack_id` in the deployment, because `CCMenuController#stack` bypasses the intended scoping.

### Impact Explanation
This matches the in-scope "High" impact category: "unauthenticated read of stack state, task streams or deploy output" — more precisely here, authenticated-but-under-scoped read of stack state (build/deploy status, environment name, last build label) for stacks outside the token's authorized scope. It is a direct violation of the stack-authorization binding the rules call out. While the CCMenu feed exposes summarized build status (not secrets), it is still a cross-stack information disclosure across an authorization boundary the operator explicitly configured via `ApiClient#stack_id`.

### Likelihood Explanation
Any holder of a scoped `ApiClient` token (a common, low-privilege token type used for public status badges) can trivially trigger this by changing the `stack_id` segment of the URL — no additional exploitation complexity, front-running, or race condition is required, unlike the original reentrancy report. This makes it more directly and reliably reachable than the original xsubmit() reentrancy bug.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to use the inherited, scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so that scoped `ApiClient` tokens cannot read state for stacks outside their authorized `stack_id`.

### Proof of Concept
1. Operator creates an `ApiClient` scoped to `stack_id: <stack A>` with only the `read:stack` permission (a normal "badge/status" token, e.g. fixture `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml`).
2. Using that client's valid `authentication_token`, issue: `GET /api/stacks/<any-other-org>/<any-other-repo>/<any-env>/ccmenu?token=<token>` (or via Basic Auth header).
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (it is valid), and `#stack` resolves `params[:stack_id]` via unscoped `Stack.from_param!`, returning the unrelated stack.
4. The controller renders that unrelated stack's build/deploy status XML, even though the `ApiClient` is scoped to stack A only — demonstrating the authorization-scope bypass.

Note: I could not find an automated test in `test/controllers/api/ccmenu_controller_test.rb` that exercises the scoped-client-vs-different-stack case (the existing tests use an unscoped `spy` client), so this specific bypass path is not covered by the current test suite; verification of a live deployment would confirm it end-to-end.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
