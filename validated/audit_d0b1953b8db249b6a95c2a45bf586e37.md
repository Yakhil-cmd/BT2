## Analog Found: DB connection leak in AA trigger dry-run/estimation path leading to management-node DoS

### Title
Unreleased database connection during AA trigger dry-run/estimation causes connection-pool exhaustion DoS - (File: `aa_composer.js`)

### Summary
`aa_composer.js` exposes `dryRunPrimaryAATrigger()` and `estimatePrimaryAATrigger()`, both of which take a DB connection with `db.takeConnectionFromPool()` and only release it from inside the `onDone` success callback of `handleTrigger()`. The comment on `estimatePrimaryAATrigger` explicitly documents that "unit validation errors are not caught" during this call. [1](#0-0)  Because `handleTrigger()` and the AA/oscript evaluation it drives contain numerous synchronous `throw Error(...)` statements reachable from attacker-influenced trigger/AA state, an exception can propagate out of the call chain before `conn.release()` is ever reached, permanently leaking the pooled connection.

### Finding Description
`dryRunPrimaryAATrigger()` takes a connection, begins a transaction, and only calls `conn.release()` inside the `onDone` callback passed to `handleTrigger()`: [2](#0-1) . Likewise `estimatePrimaryAATrigger()` only releases the connection in its own `onDone` handler after a `ROLLBACK`: [3](#0-2) .

`handleTrigger()` contains multiple unconditional `throw Error(...)` statements that are reachable depending on the supplied trigger/AA-definition content, e.g. mismatched `bAir`/`assocBalances` options, malformed AA definitions, or missing base-AA definitions during template redirection: [4](#0-3) . None of these throw paths lead back into the `onDone`/release logic — they are simply thrown up the call stack.

This is reachable by an unprivileged network peer via the `light/dry_run_aa` WebSocket command, which accepts an arbitrary user-supplied `trigger` object and the address of *any* existing AA (not necessarily one owned by the caller), performs only shallow shape/size validation via `validateAATriggerObject()`, and then calls `dryRunPrimaryAATrigger()`: [5](#0-4) . `validateAATriggerObject()` checks structural constraints (address validity, output positivity, size limits) but does not perform full oscript/formula-level validation of `trigger.data` against the target AA's logic: [6](#0-5) .

The underlying pool implementations confirm the leak has cumulative effect rather than resetting itself: in `sqlite_pool.js`, once `MAX_CONNECTIONS` in-use connections exist, subsequent `takeConnectionFromPool()` calls are queued indefinitely in `arrQueue` rather than failing fast: [7](#0-6) ; the MySQL pool similarly hands out a bounded number of connections per `conf.database.max_connections`: [8](#0-7) . A connection whose `bInUse` flag/pool slot is never released is never returned to `arrConnections`/the MySQL pool and is unusable for the lifetime of the process.

### Impact Explanation
Every crafted `light/dry_run_aa` request that hits one of the un-caught `throw` paths in `handleTrigger()`/AA evaluation permanently consumes one pooled DB connection. Because the connection pool size is fixed (`conf.database.max_connections` / `MAX_CONNECTIONS`), an attacker who is any connected peer (no special privileges, no valid trigger unit needs to be posted on-chain — it's a pure dry-run RPC) can repeat this a bounded number of times to exhaust the entire pool. Once exhausted, all other database-dependent operations across the node — unit validation (`validation.js`'s `db.takeConnectionFromPool` in `validate()`), AA trigger execution (`handlePrimaryAATrigger`), MC stabilization (`stabilizeMci`), and joint writing (`writer.saveJoint`) — will queue forever waiting for a connection, and the management node effectively stops confirming new units: a full denial of service, matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
The `light/dry_run_aa` command is intentionally exposed to unauthenticated light clients/peers and requires no on-chain unit to be posted — it is a lightweight RPC callable repeatedly and cheaply. `validateAATriggerObject()` only validates shape/size, not deep formula compatibility, so finding an AA (any AA already deployed on the network, which an attacker doesn't need to own) whose oscript logic throws on some crafted `trigger.data`/`trigger.outputs` combination is a realistic, low-cost search for an attacker, especially given the code's own acknowledgment that "unit validation errors are not caught" in this path.

### Recommendation
Wrap the connection lifecycle in `dryRunPrimaryAATrigger()` and `estimatePrimaryAATrigger()` (and any other `handleTrigger()` callers) in a `try/finally`-equivalent pattern so that `conn.release()` is guaranteed to execute even if `handleTrigger()`/`evaluateAA()` throws synchronously. Additionally, ensure the top-level exception handler used for WS command processing (the one preventing full process crashes) also actively cleans up/releases any DB connections associated with the failed request context, rather than allowing them to remain marked in-use indefinitely.

### Proof of Concept
1. Attacker connects as a normal peer/light client and identifies any deployed AA address `A`.
2. Attacker repeatedly sends `light/dry_run_aa` WS requests with `params = { address: A, trigger: {...crafted...} }`, varying `trigger.data`/`trigger.outputs` to search for inputs that satisfy `validateAATriggerObject()`'s shallow checks but trigger one of the internal `throw Error(...)` statements inside `handleTrigger()` (e.g., base-AA redirection failure, `bAir`/`assocBalances` mismatch, or an oscript evaluation edge case).
3. Each successful throw leaks one pooled connection because `dryRunPrimaryAATrigger()`'s `conn.release()` (in `aa_composer.js` lines 296-298) is never reached.
4. After repeating step 2 up to `conf.database.max_connections` (MySQL) or `MAX_CONNECTIONS` (SQLite) times, the connection pool is fully exhausted.
5. All subsequent DB-dependent operations (unit validation, AA trigger execution, MC stabilization) block indefinitely in the pool's queue, halting the node's ability to process and confirm new units. [2](#0-1) [4](#0-3) [5](#0-4) [7](#0-6)

	try {
		if (trigger.data)

	}
	catch (e) {

	var arrAssets = Object.keys(trigger.outputs).filter(function(asset) {return asset !== 'base'});

		return handle("too many assets");
	if (!ValidationUtils.isPositiveInteger(trigger.outputs.base))
		return handle("no base payment");

	function checkAddressIsNotAA() {
		db.query("SELECT 1 FROM aa_addresses WHERE address=?", [trigger.address], rows => {
			if (rows.length)

	});
