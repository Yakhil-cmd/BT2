### Title
Webhook signature verified against `repository.owner.login` while handlers act on `repository.full_name` — cross-organization status/stack forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against using `repository.owner.login` (or `organization.login`) from the payload, but all downstream `Shipit::Webhooks::Handlers::Handler` subclasses (e.g. `StatusHandler`, `PushHandler`, pull-request handlers) resolve the target `Stack`/`Repository` using a *different* field, `repository.full_name`. Because both fields live inside the same signed body, the "organization that authenticated" is not equal to "the repository that is written," which is exactly the trust-binding class described in the report (a value used for one authorization decision differs from the value used to perform the write).

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used to validate the HMAC) via: [1](#0-0) [2](#0-1) 

Meanwhile, every handler resolves the *actual* repository/stack acted upon from a completely different payload key: [3](#0-2) 

Shipit explicitly supports hosting multiple GitHub organizations (each with its own `webhook_secret`) behind one instance: [4](#0-3) 

Because a legitimate installer of the app in *their own* organization ("OrgA") genuinely knows/receives their own `webhook_secret` (delivered by GitHub when they install the app), they can compute a valid HMAC signature over an arbitrary JSON body using OrgA's secret. Nothing stops them from setting `repository.owner.login` = `"OrgA"` (so `verify_signature` picks OrgA's secret and the signature checks out) while simultaneously setting `repository.full_name` = `"OrgB/some-other-repo"` — a repository belonging to a completely different, unrelated organization tracked by the same Shipit instance. `Repository.from_github_repo_name` performs a straight DB lookup with no ownership/secret binding check: [5](#0-4) 

The equality the code should enforce but does not is:
`organization_that_authenticated (repository.owner.login used to pick the webhook secret) == organization_that_is_written (owner segment of repository.full_name used to resolve the Stack/Repository)`

Since this equality is never checked, an attacker who legitimately controls one org's webhook secret can forge events that are routed to any other org's `Stack` tracked by the instance.

### Impact Explanation
The most damaging outcome is via `StatusHandler`, which writes arbitrary GitHub commit statuses onto any `Commit` matching a forged `sha`, regardless of which org actually owns that commit: [6](#0-5) 
Commit statuses are used by Shipit to determine whether a commit is "deployable" (CI green). An attacker can forge a `success` status for a specific `sha` belonging to a totally different, victim organization's stack, potentially satisfying deploy-readiness checks and leading to an unauthorized deploy of that victim stack — this crosses the "unauthorized deploy" impact bar. `PushHandler` similarly lets the attacker trigger `stack.sync_github` on an arbitrary victim `Stack` chosen purely from the forged `repository.full_name`: [7](#0-6) 

### Likelihood Explanation
Exploitation requires only that the attacker legitimately controls (and can install the Shipit GitHub App on) at least one organization that this Shipit instance also serves — a configuration explicitly documented and supported ("Using Multiple Github Applications"). No repository write access, GITHUB_TOKEN, or API-client secret is needed; only the attacker's own legitimate webhook secret, which they are handed as part of normal app installation. This is a realistic misconfiguration/multi-tenancy scenario the engine's own code fails to defend against.

### Recommendation
In `WebhooksController#verify_signature`, after determining `repository_owner` and verifying the signature, additionally assert that `repository_owner` matches the owner segment of `repository.full_name` (and of `organization.login` when present) before dispatching to handlers; reject with `422` on mismatch. Alternatively, have `Shipit::Webhooks::Handlers::Handler#repository_name` cross-check that the resolved `Repository#owner` equals the authenticated `repository_owner`, refusing to process events where they diverge.

### Proof of Concept
1. Attacker legitimately installs the Shipit GitHub App on their own org `attacker-org`, obtaining that org's real `webhook_secret`.
2. Attacker crafts a `status` (or `push`) event payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/tests"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates the HMAC successfully (it is a valid signature for that secret over that exact body). [8](#0-7) 
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` — a commit belonging to `victim-org/victim-repo` — and creates a forged success status on it, with no re-validation that `victim-org` matches the org whose secret authenticated the request. [6](#0-5)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
