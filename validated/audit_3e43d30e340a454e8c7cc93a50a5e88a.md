### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler resolves the affected `Stack` from the independent, unverified `repository.full_name` field, letting one configured GitHub organization forge events for another organization's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the `X-Hub-Signature` against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

Once the HMAC check passes, `Shipit::Webhooks.for_event(event)` dispatches the raw parsed JSON to the matching handler(s) with no re-validation: [3](#0-2) 

Every handler that resolves *which* `Stack`/`Repository` the event applies to does so via the base `Handler#stacks`/`#repository_name`, which reads a **different** JSON field — `payload.dig('repository', 'full_name')`: [4](#0-3) 

This is used directly by, e.g., `PushHandler#process` (triggers `stack.sync_github`) and by `StatusHandler#process` (creates a `Status` for a commit from the `sha`/`state` in the payload, with no repository ownership check at all): [5](#0-4) [6](#0-5) 

Shipit explicitly supports configuring **multiple independent GitHub organizations against a single engine instance**, each with its own `webhook_secret`: [7](#0-6) 

Nothing in the code enforces that `repository.owner.login` (the field used to pick the verifying secret) and `repository.full_name` (the field used to pick the acted-upon repository/stack) agree. An attacker who legitimately controls one configured organization's GitHub App (and therefore knows that org's `webhook_secret`, which they set themselves in GitHub's App settings) can:
1. Compute a valid `X-Hub-Signature` HMAC over a payload where `repository.owner.login` = their own org (so `verify_signature` selects their own org's secret and passes),
2. While setting `repository.full_name` = `"other-org/other-repo"`, a **different**, unrelated organization/repository also hosted on the same Shipit instance.

This breaks the trust binding: **organization that authenticated (via valid HMAC) ≠ repository that is actually written to** by the dispatched handler.

### Impact Explanation
Because `StatusHandler` and `PushHandler` (and similarly, pull-request handlers keyed off `params.repository.full_name`) act on whatever repository the payload names, an attacker who is a legitimate GitHub App owner for Organization A — but has no access to Organization B's repository or GitHub App — can forge commit statuses and push/sync events for Organization B's stacks:
- Forged `status` events via `commit.create_status_from_github!(params)` can mark a commit's CI/required status as `success`, which is exactly the mechanism Shipit's continuous-delivery gating (`ci.require`, merge-queue `all_status_checks_passed?`) relies on to decide whether to auto-deploy or auto-merge. This can lead to an **unauthorized deploy or merge** of a commit that never actually passed CI on the real repository, satisfying the report's "Critical" impact bucket (unauthorized deploy/rollback/merge).
- Forged `push` events can trigger `stack.sync_github` for a repository the attacker doesn't otherwise control.

This is a direct structural analog of the flash-loan finding: the code verifies one entity (the fee/signature is checked against the caller/organization) but then acts on a different entity (the receiver/repository), silently assuming the two match.

### Likelihood Explanation
Requires that the Shipit operator has configured more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml`) and that the attacker is a legitimate installer/owner of at least one of those organizations' GitHub Apps (so they know that org's `webhook_secret`) but not of the target organization. No Shipit session, `ApiClient` token, `api_clients_secret`, or GitHub App private key for the *target* org is required — only knowledge of the attacker's own org's webhook secret, which they inherently possess. This is a realistic multi-tenant misconfiguration risk whenever one Shipit deployment serves several orgs.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, ensure the organization used to select the verifying secret is the same one that owns the repository the handler will act on. Concretely: derive the acted-upon repository consistently from the same trusted source used for signature selection (e.g., verify that `repository.full_name.split('/').first == repository_owner`, case-insensitively) before dispatching to handlers, and reject the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `org-a` and `org-b` (as in `config/secrets.development.shopify.yml`), each with its own `webhook_secret`.
2. As the owner of `org-a`'s GitHub App, craft a `status` webhook payload:
```json
{
  "sha": "<commit-sha-belonging-to-org-b/some-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/some-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC(org-a-webhook-secret, raw_body)` and `X-Github-Event: status`.
4. POST to `/webhooks`. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: "org-a")` and the signature validates successfully. [1](#0-0) 
5. `StatusHandler#process` runs unconditionally against `Commit.where(sha: params.sha)`, updating status for the commit that actually belongs to `org-b/some-repo`, with no check that `org-a` was the verified organization for that repository. [6](#0-5)
