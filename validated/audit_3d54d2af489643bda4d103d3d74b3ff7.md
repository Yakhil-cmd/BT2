### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` renders `require_ci` meaningless - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` attaches an incoming GitHub `status` webhook to **every** `Commit` row in the database that shares the same `sha`, without checking that the webhook's `repository`/`repository_owner` actually corresponds to that commit's stack. Because git commit SHAs are content-addressed and are shared across forks/mirrors of the same history, an attacker who owns any repository that has Shipit's webhook installed can cause a legitimately-signed `status` event from *their own* repo to write a `Status` row against a commit that also belongs to an unrelated victim stack, corrupting `Commit#deployable?` and defeating the `require_ci` safety check in `Shipit::Api::DeploysController#create`.

### Finding Description
The broken binding, stated as an equality that must hold but does not:

`stack_id(s) whose commits may be mutated by a "status" webhook == stack_id(s) of the repository that GitHub authenticated the webhook for (payload.repository.full_name / repository_owner)`

Code path:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON payload (`params.dig('repository','owner','login')`, line 59-61). This only proves the payload was signed by *some* org's webhook secret known to Shipit — it does **not** prove the `sha`/commit in the payload belongs to that org's repository.
2. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This is a **global, unscoped** lookup by raw `sha` across the entire `commits` table, spanning all stacks/repositories. No comparison is made against `params.dig('repository','full_name')` or the commit's own `stack.repository`.
3. `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (app/models/shipit/commit.rb:165-169, app/models/shipit/status.rb:24-33) creates a `Status` scoped to the **victim commit's own `stack_id`**, so it is indistinguishable from a real CI status originating on victim/prod's own repository.
4. `Commit#deployable?` (app/models/shipit/commit.rb:227-229) delegates `success?`/`state` to `status`, which now includes the forged, victim-stack-scoped `Status` row.
5. `Shipit::Api::DeploysController#create` (app/controllers/shipit/api/deploys_controller.rb:22) checks `param_error!(:require_ci, ...) if params.require_ci && !commit.deployable?` — since `commit.deployable?` is now poisoned, this check passes even though victim/prod's own CI never ran or failed.

Exploit flow: attacker forks (or otherwise obtains) a public repository whose git history overlaps with victim/prod's tracked commits (a very common situation — a fork shares identical SHAs for all commits prior to divergence, and any shared ancestor commit is present as a `Commit` row in both stacks once each has been synced by Shipit). Attacker configures Shipit's webhook on their own repository (an action explicitly listed as available to the unprivileged attacker: "emit webhooks from a repository they own"). GitHub genuinely and correctly signs a `status` event for that shared SHA on the attacker's repo. `verify_signature` passes because the signature is valid for the attacker's own org. `StatusHandler#process` then writes a `success` `Status` for that SHA against **every** `Commit` row sharing that SHA, including the one belonging to victim/prod's stack. A legitimate `ApiClient` with deploy permission on victim/prod later calls `POST /api/stacks/:id/deploys` with `require_ci: true`; the check that should block a not-actually-CI-passed commit is bypassed.

Existing guards do not prevent this: `verify_signature` only authenticates the *sender org*, not the *scope of the sha being mutated*; there is no model validation tying a `Status` write to the correct repository; `require_permission!`/`ApiClient` scoping is irrelevant here since the corruption happens in the webhook path, upstream of the deploy request. ### Impact Explanation
A payload genuinely originating from and authenticated for one repository can mutate CI state (and therefore deployability) of a commit belonging to an unrelated stack/repository/tenant — this matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" and directly enables "an unauthorized deploy" by nullifying the `require_ci` safety gate. It is repeatable against any victim stack that shares any commit SHA with a repository the attacker controls (trivially achievable via forking public repos, or via any repo with overlapping history). Blast radius extends to every stack in the Shipit instance whose tracked commit history overlaps with an attacker-controlled repository, i.e., potentially many tenants in a multi-tenant Shipit deployment.

### Likelihood Explanation
Preconditions are modest and within the declared attacker capability set: attacker needs (a) a GitHub repository they control that shares at least one commit SHA with the victim stack (common for forks of public repos, or repos onboarded from the same upstream), and (b) that repository has Shipit's webhook configured (self-service in typical Shipit deployments; explicitly enumerated as an available attacker action — "emit webhooks from a repository they own"). No secrets, no privileged Shipit role, and no signature forgery are required — GitHub itself produces a validly signed event. The only additional requirement for full exploitation of `require_ci` bypass is that some legitimate operator issues a deploy with `require_ci: true` on the affected sha, which is an ordinary, expected action for any responsible deploy pipeline.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogously in `PushHandler`/`CheckSuiteHandler` if similarly unscoped) to the repository that the webhook was verified against, e.g., resolve the target `Stack`(s) via `params.dig('repository','full_name')` (or `repository_owner`/`repository_name` matched against `Stack#repository`) and restrict `Commit.where(sha: ..., stack_id: matching_stack_ids)` before applying the status. Never trust bare `sha` equality across tenants as an authorization boundary.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (new/extended test)
test "process does not attach a status to a commit belonging to an unrelated repository/stack" do
  shared_sha = 'deadbeefcafefeed0000000000000000000000'

  attacker_stack = shipit_stacks(:shipit) # repo the attacker owns/controls webhooks for
  victim_stack   = shipit_stacks(:cyclimse) # unrelated victim/prod stack

  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit),
                                                     committer: shipit_users(:shipit),
                                                     authored_at: Time.now, committed_at: Time.now,
                                                     message: 'shared ancestor')
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit),
                                                 committer: shipit_users(:shipit),
                                                 authored_at: Time.now, committed_at: Time.now,
                                                 message: 'shared ancestor')

  # LHS of binding: victim_commit.deployable? computed strictly from victim_stack's own CI
  refute_predicate victim_commit.reload, :deployable? # no status yet -> not deployable

  # Attacker-controlled webhook, correctly signed for the attacker's own org
  Shipit::Webhooks::Handlers::StatusHandler.new.call(
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => 'master' }]
  )

  # RHS: the source of victim_commit.deployable? is now partially attacker-forged
  assert_predicate victim_commit.reload, :deployable?, "victim commit incorrectly became deployable via cross-repo status"
end
```
