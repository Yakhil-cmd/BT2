## Finding

CVE-2022-0635 is a BIND crash caused by an internal assertion failing on attacker-supplied, malformed but superficially valid input, terminating the daemon (DoS). `ocore` has an analogous pattern: hard `throw Error(...)` "invariant" checks embedded deep in async validation code paths that are reachable with attacker-controlled data, and — unlike the `callback(err)` error path used everywhere else in `validation.js` — these throws are not converted into a soft validation error; they propagate as uncaught exceptions and crash the process.

### Title
Malicious private-payment chain crashes wallet/hub node via uncaught `throw Error("no src coin amount")` in payment validation - (File: validation.js)

### Summary
When validating a *private* (fixed-denomination / "blackbyte") payment chain, `indivisible_asset.js`'s `validatePrivatePayment` builds `objValidationState.src_coin` from the **previous** (ancestor) private-chain element's hidden output before that ancestor element has itself been validated. The `amount` field of that ancestor output is never type/range-checked at this point. It later reaches `validatePaymentInputsAndOutputs` in `validation.js`, which asserts `isPositiveInteger(src_coin.amount)` and, on failure, executes `throw Error("no src coin amount")` instead of returning a normal validation error. Because this is a synchronous `throw` inside a deeply nested async callback, it is not caught by any `try/catch` and crashes the node process that receives the crafted chain.

### Finding Description
`private_payment.js` → `network.js:handleOnlinePrivatePayment` accepts private payment chains sent by any counterparty (a private-payment sender/device) [1](#0-0) , which calls into `indivisible_asset.js`'s chain parser.

In `parsePrivatePaymentChain`, elements are iterated **in the order supplied by the sender** (`arrPrivateElements` is "reverse chronological order", so element `0` — the head — is validated before element `1`, its ancestor, is validated) [2](#0-1) .

When validating the head element (`i=0`), its own fields are checked (asset, denomination, output shape, output hash) [3](#0-2) , but the code then pulls the **ancestor's** hidden output straight from attacker-supplied JSON with only an existence check, not a type/amount check: [4](#0-3) 

Specifically, `prev_hidden_output = objPrevPrivateElement.payload.outputs[input.output_index]` is only checked for truthiness (`"no prev hidden output"`), and its `amount` is copied verbatim into `objValidationState.src_coin.amount` — with no `isPositiveInteger` or even `typeof === 'number'` check.

This `src_coin` object is then consumed in `validation.js`'s payment-input validator for private fixed-denomination transfers: [5](#0-4) 

Here, if `src_coin.amount` (attacker-controlled, unvalidated) is not a positive integer, the code does not return a normal validation error via `cb(...)`; it does:
```js
if (!isPositiveInteger(src_coin.amount))
    throw Error("no src coin amount");
```
This `throw` executes inside the `ifOk` callback chain rooted in `validatePrivatePayment`'s nested `async.series`/`conn.query` callbacks, several levels away from any enclosing `try/catch`. In Node.js, an exception thrown from inside an async callback with no surrounding `try/catch` becomes an uncaught exception, which by default terminates the process.

The `denomination` check cannot be abused this way because `payload.denomination` is validated as a positive integer on the *current* element before being copied into `src_coin.denomination` [6](#0-5) , but no equivalent validation exists for the *ancestor* element's `amount` field, since that ancestor element is validated only *after* the head element that references it.

### Impact Explanation
Any peer or device that a wallet/hub exchanges private payments with (a normal, unprivileged "private-payment counterparty") can send a specially crafted private payment chain in which the ancestor element's hidden output `amount` is a non-integer (string, negative number, float, or `NaN`). When the victim node validates the chain, `validatePaymentInputsAndOutputs` throws an uncaught `Error`, crashing the wallet or hub process. This is a remote, unauthenticated (from the perspective of the counterparty role) denial-of-service against nodes that process private asset payments — directly matching the "network unable to confirm new units" / node-crash impact class called out in the report's Validate criteria.

### Likelihood Explanation
The sender fully controls both the on-chain unit (including the `spend_proofs` hash committed on the DAG) and the off-chain private-element JSON delivered to the recipient, so they can freely choose the ancestor output's `amount` value while still producing a `spend_proof` hash that matches what is checked in `validateSpendProof` [7](#0-6) . No special privileges, mining power, or witness status are required — only the ability to be a private-payment counterparty, which is a normal wallet-to-wallet interaction. This makes the bug straightforward to trigger for anyone able to send a private payment.

### Recommendation
In `indivisible_asset.js:validatePrivatePayment`, validate `prev_hidden_output.amount` (and generally all fields consumed from `objPrevPrivateElement`) with `ValidationUtils.isPositiveInteger` before building `objValidationState.src_coin`, returning `callbacks.ifError(...)` on failure instead of allowing invalid data to reach the `throw Error` invariant checks in `validation.js`. Additionally, convert the "invariant" throws in `validatePaymentInputsAndOutputs` (`"no src_coin"`, `"no src_output"`, `"no denomination in src coin"`, `"no src coin amount"`) into soft validation errors (`return cb(...)`) so that any residual malformed input results in a rejected/bad unit rather than a process crash — consistent with the defense-in-depth principle of never trusting attacker-reachable state to satisfy internal invariants.

### Proof of Concept
1. Attacker (device B) initiates a chain of private (fixed-denomination/blackbyte) asset payments to victim (device A), e.g. issue → transfer1 (ancestor) → transfer2 (head), as normally composed by `indivisible_asset.js:buildPrivateElementsChain`.
2. Attacker tampers with the resulting `arrPrivateElements` JSON before sending it via `handleOnlinePrivatePayment`/`private_payment.js`: in `arrPrivateElements[1].payload.outputs[output_index]` (the ancestor referenced by the head element's `input.unit/message_index/output_index`), set `amount` to a non-integer value (e.g. `"1e9"`, `-1`, or `1.5`) while keeping `output_hash` consistent with a matching spend-proof hash that the attacker also embeds in the actually-broadcast unit's `spend_proofs`.
3. Attacker sends this chain to the victim node (as a normal recipient/cosigner private-payment delivery).
4. Victim's `parsePrivatePaymentChain` validates the head element (`i=0`) first: `validateSpendProof` succeeds (attacker crafted matching hash), `src_coin.amount` is set to the tampered value from the unvalidated ancestor element [8](#0-7) .
5. `validation.validatePayment` → `validatePaymentInputsAndOutputs` reaches the fixed-denomination private-transfer branch and executes `throw Error("no src coin amount")` [5](#0-4) , which is uncaught and crashes the victim's node process.

function parsePrivatePaymentChain(conn, arrPrivateElements, callbacks){
	var bAllStable = true;
	var issuePrivateElement = arrPrivateElements[arrPrivateElements.length-1];
	if (!issuePrivateElement.payload || !issuePrivateElement.payload.inputs || !issuePrivateElement.payload.inputs[0])
		return callbacks.ifError("invalid issue private element");
	var asset = issuePrivateElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in issue private element");
	var denomination = issuePrivateElement.payload.denomination;
	if (!denomination)
		return callbacks.ifError("no denomination in issue private element");
	async.forEachOfSeries(
		arrPrivateElements,
		function(objPrivateElement, i, cb){
			if (!objPrivateElement.payload || !objPrivateElement.payload.inputs || !objPrivateElement.payload.inputs[0])
				return cb("invalid payload");
			if (!objPrivateElement.output)
				return cb("no output in private element");
			if (objPrivateElement.payload.asset !== asset)
				return cb("private element has a different asset");
			if (objPrivateElement.payload.denomination !== denomination)
				return cb("private element has a different denomination");
			var prevElement = null; 
			if (i+1 < arrPrivateElements.length){ // excluding issue transaction
				var prevElement = arrPrivateElements[i+1];
				if (prevElement.unit !== objPrivateElement.payload.inputs[0].unit)
					return cb("not referencing previous element unit");
				if (prevElement.message_index !== objPrivateElement.payload.inputs[0].message_index)
					return cb("not referencing previous element message index");
				if (prevElement.output_index !== objPrivateElement.payload.inputs[0].output_index)
					return cb("not referencing previous element output index");
			}
			validatePrivatePayment(conn, objPrivateElement, prevElement, {
				ifError: cb,
				ifOk: function(bStable, input_address){
					objPrivateElement.bStable = bStable;
					objPrivateElement.input_address = input_address;
					if (!bStable)
						bAllStable = false;
					cb();
				}
			});
		},
		function(err){
			if (err)
				return callbacks.ifError(err);
			callbacks.ifOk(bAllStable);
