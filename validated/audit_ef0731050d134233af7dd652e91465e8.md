### Title
Cross-organization webhook status injection via mismatched signature-verification field and status-write field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login` (or `organization.login`), but `Shipit::Webhooks::Handlers::StatusHandler#process` writes commit status using only `sha`, with no repository/organization scoping at all. In a multi-GitHub-App Shipit deployment, this breaks the intended binding "organization whose secret authenticated the request == repository/commit that is written."

### Finding Description
Shipit supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret`, as documented in `docs/setup.md` ("Using Multiple Github Applications") and shown in `test/dummy/config/secrets_double_github_app.yml`. [1](#0-0) [2](#0-1) 

The webhook signature check picks the secret to verify against based solely on `repository.owner.login` from the JSON body: [3](#0-2) [4](#0-3) 

Once the signature passes (using organization A's secret), the raw JSON body is dispatched to handlers with no further binding to organization A. `Shipit::Webhooks::Handlers::Handler#stacks` scopes most handlers by `repository.full_name` (a separate field from `repository.owner.login`), but `StatusHandler` does not use `stacks`/repository scoping at all — it looks up commits by `sha` across the *entire* database: [5](#0-4) 

`Commit#create_status_from_github!` then records the injected status and, if the resulting aggregate status changes, emits `deployable_status` hooks and can trigger `stack.schedule_merges` for continuous delivery: [6](#0-5) [7](#0-6) 

Deployability itself is directly derived from `status`/`success?`: [8](#0-7) 

**The broken binding:** the organization whose `webhook_secret` authenticated the HTTP request (`repository.owner.login`) is never checked to equal the organization/repository whose commit status is mutated (looked up purely by `sha`, global across all stacks/orgs). Because git commit SHAs are content-addressed, an attacker who controls (or forks) a repository whose commit history overlaps with a victim stack's repository (e.g., a public upstream repo mirrored/forked into the attacker's own onboarded organization) can produce commits with identical SHAs to the victim's commits, then send a `status` webhook signed with their **own** organization's legitimate webhook secret, but referencing the victim's commit `sha`. Shipit will locate and update that commit belonging to a completely different organization/stack.

### Impact Explanation
This allows an attacker who is a legitimate but low-privilege customer/organization onboarded into a shared multi-tenant Shipit instance to forge a passing CI status (or otherwise manipulate `deployable_status`) on a commit belonging to a different organization's stack that they do not control on GitHub. Since `Commit#deployable?` and continuous-deployment scheduling (`schedule_continuous_delivery`, `stack.schedule_merges`) are driven directly by this status, this can result in an unauthorized deploy being triggered for another organization's stack — matching the "unauthorized deploy" Critical-impact category, achieved purely by crossing an organization/repository trust boundary that the signature check was supposed to enforce.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with multiple GitHub organizations (a documented, supported configuration), (2) attacker control of one onboarded, lower-trust organization with a known/legitimate webhook secret for their own app installation, and (3) a commit SHA collision with the target stack's repository, which is trivially achievable by forking/mirroring a public target repository (SHAs are identical since they are computed from commit content, not location). No GitHub write access, Shipit session, or ApiClient token is required — only the ability to deliver an HTTP request with a valid signature for the attacker's own organization.

### Recommendation
Bind the status/commit lookup to the same organization/repository that was used to select the verification secret. Concretely, `StatusHandler` (and any other handler that doesn't already use the repository-scoped `stacks` helper) should scope its `Commit` lookup through `stacks` (i.e., via `Repository.from_github_repo_name(repository_name)`), and/or the controller should pass the authenticated organization down to handlers and verify that `repository.full_name`'s owner matches `repository.owner.login`/the authenticated organization before dispatch.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim), per `docs/setup.md`'s multi-app configuration.
2. Attacker forks/mirrors OrgB's public target repository into `OrgA`, obtaining identical commit SHAs to commits already tracked by a Shipit stack for `OrgB`.
3. Attacker crafts a `status` webhook payload: `{"sha": "<victim_commit_sha>", "state": "success", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/forked-repo"}, ...}` and signs it with `OrgA`'s legitimate `webhook_secret` in the `X-Hub-Signature` header.
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — matching OrgB's real commit — and calls `create_status_from_github!`, injecting a fabricated "success" status onto OrgB's commit, potentially flipping `deployable?` to true and triggering continuous deployment for OrgB's stack, without any credential or access to OrgB's GitHub organization.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
