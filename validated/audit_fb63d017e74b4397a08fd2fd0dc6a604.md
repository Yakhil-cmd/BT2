### Title
Disabled indirect-correspondent subject allowlist lets introduced (non-paired) devices send any wallet command - ([File: wallet.js])

### Summary
`wallet.js`'s `handleMessageFromHub` used to restrict which message `subject`s an "indirect correspondent" (a device added via `addIndirectCorrespondents`, i.e. introduced as a cosigner but never directly paired/trusted) was allowed to send. That allowlist check is commented out, so an indirect correspondent can now send any subject at all, exactly mirroring the OpenClaw bug class where ingress is accepted before the channel/member-level allowlist gate is enforced.

### Finding Description
When a device is a member of a shared/multisig address introduced through another cosigner, it is added to `correspondent_devices` with `is_indirect=1` via `addIndirectCorrespondents` [1](#0-0) , without ever completing the normal pairing handshake that establishes trust (`handlePairingMessage`) [2](#0-1) .

At the hub-relay layer (`device.js` `handleJustsaying` case `'hub/message'`), once the sender is found in `correspondent_devices` (which includes indirect ones), the message is unconditionally forwarded to the wallet layer regardless of `is_indirect`: `handleMessage(rows[0].is_indirect)` [3](#0-2) . The `bIndirectCorrespondent` flag is passed all the way into `wallet.js`'s `handleMessageFromHub`, where a dedicated check was supposed to restrict indirect correspondents to only wallet-setup subjects:

```
//if (bIndirectCorrespondent && ["cancel_new_wallet", "my_xpubkey", "new_wallet_address"].indexOf(subject) === -1)
//    return callbacks.ifError("you're indirect correspondent, cannot trust "+subject+" from you");
``` [4](#0-3) 

This check is commented out, so `bIndirectCorrespondent` is received but never enforced. As a result the full `switch(subject)` dispatcher in `doHandle()` [5](#0-4)  treats an indirect (merely-introduced, never directly paired) device exactly like a fully-trusted correspondent for every subject, including `"sign"` (multisig signing requests) [6](#0-5) , `"new_shared_address"` [7](#0-6) , `"arbiter_contract_update"` / `"arbiter_contract_response"` [8](#0-7) [9](#0-8) , and `"removed_paired_device"` [10](#0-9) .

This is the same bug class as the OpenClaw advisory: a per-member/per-channel access allowlist exists in the code but the gate that should reject unauthorized senders before further processing is not actually enforced, so unauthorized parties reach privileged handlers.

### Impact Explanation
An indirect correspondent — a device that a legitimate cosigner introduced to the user's wallet (e.g., as part of setting up a shared/multisig address) but that the user never directly paired with or vetted — can now send arbitrary wallet-protocol messages that the user's device will process with the same trust level as a directly-paired correspondent. Concretely, such a device can:
- Send `"sign"` requests for units it has crafted, triggering `signing_request` UI prompts on the victim's device using addresses the victim controls [11](#0-10) , increasing the chance a user is socially engineered into approving payments.
- Send `"new_shared_address"` to register a shared/multisig address whose participant list (`signers`) can be forged, since sender identity is never cross-checked against the definition's signer addresses at the wallet-message layer [12](#0-11) .
- Manipulate arbiter/prosaic contract state machines (accept/decline/dispute) if a matching contract hash exists, since the primary authorization gate the code relies on is "you must be a known correspondent," not "you must be a directly-trusted correspondent."

This constitutes an authorization gap reachable from an already-paired (but supposed to be only partially trusted) device, matching the "paired device" actor class in scope, and can lead to unauthorized wallet/contract state manipulation and AA-fund-loss-adjacent scenarios (fraudulent multisig setup, unauthorized signing prompts) without requiring full correspondent trust.

### Likelihood Explanation
Likelihood is significant: any legitimate cosigner in a shared-address setup can cause `addIndirectCorrespondents` to add a third party as an indirect correspondent of the victim device with zero further verification (no direct pairing needed) [1](#0-0) . From that point, the disabled check means the attacker-controlled device has unrestricted access to the same subject space as a normal correspondent, requiring no additional interaction with the hub's own authorization (the hub only requires a valid ECDSA signature and a `to` device that's registered) [13](#0-12) .

### Recommendation
Re-enable and correctly enforce the indirect-correspondent subject allowlist in `wallet.js`'s `doHandle()`, ideally expanding/auditing the allowed subject list to match what indirect (untrusted) correspondents legitimately need (e.g., wallet-bootstrap subjects) and rejecting all other subjects with `callbacks.ifError(...)` before any subject-specific processing occurs. Additionally, consider tightening `handleNewSharedAddress` to verify the message sender's device address is actually referenced among `body.signers` device addresses, similar to the check already done in `validateAddressDefinitionTemplate` [14](#0-13) .

### Proof of Concept
1. Attacker device D is introduced as a cosigner of a shared address the victim is also part of (e.g., via a normal multisig wallet setup flow among cosigners C1, C2, D). During this flow, `addIndirectCorrespondents` inserts D into the victim's `correspondent_devices` table with `is_indirect=1`, without D ever completing a `"pairing"` handshake with the victim [1](#0-0) .
2. D crafts and sends a `hub/message` justsaying to the victim's hub with `subject: "sign"` (or `"new_shared_address"`, `"arbiter_contract_update"`, etc.) and a valid signature over its own permanent device key, addressed (`to`) to the victim's device address, following the wire format checked in `device.js` `handleJustsaying` case `'hub/message'` [15](#0-14) .
3. On the victim's device, `correspondent_devices` lookup finds D (`is_indirect=1`), and `handleMessage(true)` is invoked regardless, emitting `handle_message_from_hub` with `bIndirectCorrespondent=true` [16](#0-15) .
4. In `wallet.js`, `handleMessageFromHub` receives `bIndirectCorrespondent=true`, but because the restricting check is commented out [4](#0-3) , execution falls straight into the `switch(subject)` and processes the `"sign"` (or other) request exactly as if D were a fully-trusted, directly-paired correspondent [5](#0-4) .
