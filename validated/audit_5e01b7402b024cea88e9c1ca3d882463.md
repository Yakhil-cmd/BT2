### Title
Webhook signature verification is keyed off an attacker-controlled organization field decoupled from the repository/team that the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret) to validate a webhook against using `repository_owner`, a value read directly out of the unauthenticated JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The handlers that subsequently act on the request (`MembershipHandler`, `PushHandler`, pull-request handlers, etc.) use *other* fields of that same unauthenticated body (`repository.full_name`, `team.id`, `organization.login`) to decide which `Stack`/`Team`/`Membership` record to mutate. There is no requirement that the organization used to pick the verifying secret be the same organization that owns the entity being modified. Combined with the fact that `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank/unset (a state the shipped config templates present as the default), this breaks the trust binding: `organization that authenticated == repository/team that is written`. ### Finding Description
`verify_signature` derives `repository_owner` purely from the request body and uses it to look up the `GitHubApp` config to validate the signature against: [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` unconditionally accepts the request when no `webhook_secret` is configured for that organization: [4](#0-3) 

The default/example secrets templates ship `webhook_secret` as blank/optional, and Shipit explicitly supports configuring multiple, independently-secreted GitHub organizations in `secrets.yml`: [5](#0-4) [6](#0-5) 

Once the (possibly trivially-bypassed) signature check passes, `create` dispatches the entire attacker-supplied JSON to registered handlers with no re-validation that the entity acted upon belongs to the organization that "authenticated" the request: [7](#0-6) 

`Handler#stacks` resolves the target purely from `repository.full_name` in the body: [8](#0-7) 

Most critically, `MembershipHandler#process` creates/finds a `Team` by `params.team.id` and `params.organization.login` (both attacker-supplied) and adds/removes a `User` from that team's `Membership` list based on `params.member.login` and `params.action`: [9](#0-8) 

`Membership`/`Team` records are exactly what `User#authorized?` checks to gate access to the whole Shipit application: [10](#0-9) 

Attack path: an unprivileged external attacker (no Shipit session, no ApiClient token, no GitHub push access) sends `POST /webhooks` with header `X-Github-Event: membership` and a body such as `{"repository":{"owner":{"login":"<org-with-no-webhook-secret>"}}, "organization":{"login":"<victim-org>"}, "team":{"id":<attacker-chosen>,"name":"x","slug":"x","url":"x"}, "member":{"login":"<attacker-github-login>"}, "action":"added"}`. `verify_signature` looks up the GitHub App for `<org-with-no-webhook-secret>`; since that org has no `webhook_secret` configured, `verify_webhook_signature` returns `true` for any (or missing) `X-Hub-Signature` header. The request then reaches `MembershipHandler`, which creates a `Team` scoped to `<victim-org>` and inserts a `Membership` linking the attacker's own (self-created) `User` record to that team — directly forging membership in whatever team is configured under `Shipit.github_teams`, bypassing GitHub-side team membership entirely.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization (an explicitly listed High-impact class): an attacker with zero legitimate GitHub or Shipit privileges can grant themselves (or any GitHub login they choose) membership in the team(s) gating `force_github_authentication`/`current_user.authorized?`, thereby obtaining full authenticated access to the Shipit UI (stacks, deploys, task triggers, hooks, API client creation, etc.). The same authentication-decoupling flaw also lets the same unprivileged sender forge `push`, `status`, `check_suite`, and `pull_request` events against arbitrary stacks/repositories tracked by the engine, since `Stack`/`Repository` resolution in every handler trusts `repository.full_name` from the same unauthenticated body.

### Likelihood Explanation
Likelihood depends entirely on whether the deployment has at least one configured organization (in single- or multi-org `secrets.yml` mode) with a blank `webhook_secret` — which is the value shown as the default/optional setting in every shipped configuration template (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `template.rb`) and is explicitly documented as "optional." Any installation that has not manually filled in `webhook_secret` for every configured organization is exploitable by a completely anonymous internet attacker who only needs to know the public `/webhooks` endpoint URL — no GitHub credentials, no repository access, and no Shipit account are required.

### Recommendation
- Do not silently accept unsigned webhooks: `GitHubApp#verify_webhook_signature` should fail (or the engine should refuse to boot / log a hard warning) when `webhook_secret` is blank, rather than treating it as "always verified."
- Bind the authenticated organization to the entity being mutated: after selecting the `GitHubApp` via `repository_owner`, re-validate that the `Team`/`Stack`/`Repository` actually targeted by the handler (`repository.full_name`, `team.*`, `organization.login`) belongs to that same, already-authenticated organization before making any writes.
- In `MembershipHandler`, verify `params.organization.login` matches the organization whose secret validated the request before creating/mutating `Team`/`Membership` records.

### Proof of Concept
Given a Shipit deployment configured with (at least) organization `weakorg` whose `webhook_secret` is left blank, and `Shipit.github_teams` containing team `victimorg/admins`:

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 999999, "name": "admins", "slug": "admins", "url": "https://github.com/x" },
  "organization": { "login": "victimorg" },
  "member": { "login": "attacker-controlled-login" },
  "repository": { "owner": { "login": "weakorg" }, "full_name": "weakorg/whatever" }
}
```
- `repository_owner` resolves to `weakorg`; `Shipit.github(organization: 'weakorg').verify_webhook_signature` returns `true` unconditionally (no `webhook_secret` configured), so `verify_signature` passes with no valid `X-Hub-Signature` header at all.
- `MembershipHandler#process` finds/creates `Team(organization: "victimorg", github_id: 999999)` and adds `User(login: "attacker-controlled-login")` as a member via `Membership`.
- If `victimorg/admins` (or a team with the same `github_id`) is present in `Shipit.github_teams`, the attacker's `User` record now satisfies `User#authorized?`, and once they complete the normal (unprivileged) GitHub OAuth login flow as `attacker-controlled-login`, `force_github_authentication` grants them full access to the Shipit instance.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
