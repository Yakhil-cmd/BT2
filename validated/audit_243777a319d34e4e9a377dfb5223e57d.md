## Finding

### Title
Unauthenticated Webhook Forgery Bypasses `Shipit.github_teams` Authorization When `webhook_secret` Is Unset - (File: `lib/shipit/github_app.rb`)

### Summary
`Shipit::GitHubApp#verify_webhook_signature` silently treats every inbound webhook as valid when no `webhook_secret` is configured for the organization, exactly like the reported `swap()` bug where a required check (deadline / signature) is skipped instead of enforced. This lets an unauthenticated attacker forge GitHub webhook payloads (e.g. `membership` events) and have `WebhooksController` process them as authentic, ultimately allowing them to be added to a `Team` that grants `Shipit.github_teams` authorization.

### Finding Description
`WebhooksController#verify_signature` is the sole gate protecting `/webhooks` before any handler mutates state: [1](#0-0) 

It delegates the actual cryptographic check to `GitHubApp#verify_webhook_signature`: [2](#0-1) 

The very first line, `return true unless webhook_secret`, means that whenever the configured GitHub App for an organization has no `webhook_secret` set, **the signature is never actually checked** — the `X-Hub-Signature` header can be missing or garbage and the request is still marked "verified". The setup documentation explicitly lists this field as optional, not a misconfiguration: [3](#0-2) 

Once `verify_signature` passes, `WebhooksController#create` blindly dispatches the attacker-controlled JSON to registered handlers: [4](#0-3) 

The `membership` event handler trusts the payload completely to mutate `Team`/`Membership` records: [5](#0-4) 

`Team` membership is the exact mechanism gating application-wide authorization: `Shipit.github_teams` and `User#authorized?` check membership in these `Team` records, independent of any real GitHub team state: [6](#0-5) [7](#0-6) 

**Binding broken:** `signature verified == true` should equal `HMAC(webhook_secret, raw_body) matches X-Hub-Signature`. When `webhook_secret` is blank, the left side is forced to `true` unconditionally, decoupling it from the right side entirely — the same class of defect as a deadline field the documentation requires but the code never enforces.

### Impact Explanation
An attacker who has (or creates) an ordinary GitHub account and completes the normal OAuth login (creating an unauthorized `Shipit::User` row) can, in parallel, POST a forged `membership` webhook naming their own GitHub login as `added` to a `Team` whose `github_id`/`organization` correspond to one of `Shipit.github_teams`. Because signature verification is a no-op in this configuration, the forged request is processed identically to a legitimate GitHub-originated one, and `Team#add_member` grants the attacker `authorized?` status without any real organizational team membership. This is a direct escalation into `Shipit.github_teams` authorization — enumerated as a High-impact outcome in scope — and from there the attacker has full authenticated access to trigger deploys, rollbacks, and task execution across every stack mounted on the instance.

### Likelihood Explanation
Any Shipit deployment that leaves `webhook_secret` empty (a state the official setup guide presents as an accepted, "optional" configuration rather than a misuse of the engine) is exploitable by a single unauthenticated HTTP POST to the public `/webhooks` endpoint — no GitHub App private key, `ApiClient` token, or session is required, satisfying the rules' "unprivileged attacker" and "no host misconfiguration" constraints.

### Recommendation
Do not treat an absent `webhook_secret` as an implicit bypass. Require a configured secret and always perform constant-time HMAC verification (`verify_webhook_signature` should return `false`/raise when `webhook_secret` is blank, or the engine should refuse to boot/mount webhooks without one), mirroring the report's fix of adding the missing enforcement instead of silently accepting the unchecked path.

### Proof of Concept
1. Configure Shipit (or use an installation) with `github.webhook_secret` left blank, as permitted by `docs/setup.md`.
2. Attacker performs the standard OAuth login flow with their own GitHub account, creating an unauthorized `User` row via `GithubAuthenticationController#callback`.
3. Attacker sends:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": <id of an authorized Shipit::Team>, "name": "...", "slug": "...", "url": "..."},
  "organization": {"login": "<org>"},
  "member": {"login": "<attacker-github-login>"}
}
```
No `X-Hub-Signature` header, or an arbitrary one, is required.
4. `verify_signature` calls `GitHubApp#verify_webhook_signature`, which returns `true` immediately since `webhook_secret` is nil.
5. `MembershipHandler#process` adds the attacker's `User` to the authorized `Team`.
6. Attacker's existing session now satisfies `current_user.authorized?`, granting full deploy/rollback access across the instance.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
