This confirms it: `Shipit.github(organization:)` supports a **multi-tenant** configuration where each key under `secrets.github` is a distinct organization, each with its own `webhook_secret`, `app_id`, `installation_id`, and `private_key` [1](#0-0) . This is exactly the scenario needed to make the analog concrete: multiple organizations can be configured, each with an independently-known webhook secret, but the field used to select which secret verifies the request is not the same field used to decide which repository's stacks get acted upon.

### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the unbound `repository.full_name` — cross-repository writes across GitHub organizations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Finding Description
`WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification from the payload field `repository.owner.login` (falling back to `organization.login`): [2](#0-1) [3](#0-2) 

Once the signature check passes, `create` re-parses the exact same raw body and dispatches it to the registered handler for the event type: [4](#0-3) 

However, `Handler#stacks`/`#repository_name` — used by every handler including `PushHandler` to decide which `Stack`/`Repository` records are mutated — reads a *different* field of the same payload, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

The signature verification only proves "this raw body was signed with organization X's secret" (where X = `repository.owner.login`). It does not prove or constrain that `repository.full_name` (used for actual DB lookups and, in `PushHandler`, `stack.sync_github`, i.e., triggering a sync/fetch of a specific repo) belongs to that same organization X. Since `Shipit.github(organization:)` supports independent per-organization webhook secrets configured under `secrets.github` [1](#0-0) , this is a genuine multi-tenant boundary: an attacker who administers Organization A (with a Shipit-configured webhook secret they can compute, e.g. because they configured the webhook themselves when onboarding their own org to this Shipit instance) can POST directly to `/webhooks` (this endpoint has no session/API-client requirement — only the HMAC check) with:
- `repository.owner.login = "org-a"` (so `Shipit.github(organization: "org-a")` resolves and the HMAC, computed with `org-a`'s secret, validates), and
- `repository.full_name = "org-b/some-repo"` (an unrelated, already-onboarded stack in the same Shipit instance).

The equality that should hold is: `organization authenticated by verify_signature == organization owning the repository the handler mutates`. This binding is broken because one side is `repository.owner.login` and the other is `repository.full_name`'s owner segment, and nothing in the code enforces they match.

### Impact Explanation
`PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every stack matching the forged `repository.full_name` and branch [6](#0-5) . This lets an attacker who only controls one onboarded organization/repo (org A) force a sync/fetch cycle — and depending on downstream deploy triggers/CI-status handlers reachable via the same class of mismatch (`StatusHandler`, `CheckSuiteHandler`, `MembershipHandler` all resolve repository/team state purely from unverified payload fields) — trigger unauthorized state changes scoped to a different organization's repository (org B) that the attacker was never granted access to. This is a cross-organization/cross-repository write achieved purely by crafting a payload whose "owning organization" and "acted-upon repository" disagree, satisfying the "unauthorized deploy"/"cross-repository writes" bar.

### Likelihood Explanation
Requires the target Shipit deployment to run in the multi-organization configuration (`secrets.github` keyed by org) and requires the attacker to control at least one onboarded organization's legitimate webhook secret (i.e., they administer/onboarded org A with Shipit). This is a realistic tenant-isolation failure for any Shipit instance serving multiple GitHub organizations, since org admins are expected to be mutually untrusted.

### Recommendation
In `WebhooksController#verify_signature` and in `Handler#repository_name`/`#stacks`, enforce that the organization used to resolve the webhook secret is the same organization embedded in `repository.full_name` (i.e. split `full_name` and compare the owner segment against `repository_owner`), rejecting the request with 422 if they disagree.

### Proof of Concept
1. Deploy Shipit with `secrets.github` containing two orgs, `org-a` and `org-b`, each with a distinct `webhook_secret`, both with stacks/repositories already onboarded.
2. As an attacker who is an admin of `org-a` (and thus knows/controls `org-a`'s configured webhook secret because they set it up when onboarding), craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and the signature validates.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-b/target-repo")` and calls `sync_github`, acting on org B's repository despite the signature only proving org A authorized the request. [7](#0-6) [8](#0-7)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end
