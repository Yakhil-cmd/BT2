### Title
API-scoped `ApiClient` tokens read CCMenu build status for stacks outside their authorized scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The external report's bug class is "no de-duplication check lets one authorization slot silently cover more state than intended, breaking a 1:1 trust binding." In this engine the closest reachable analog is the binding "a stack a token authorizes == a stack it touches," which is enforced everywhere except in `Shipit::Api::CCMenuController`.

### Finding Description
`Shipit::Api::BaseController` defines the canonical stack-scoping mechanism for `ApiClient` tokens: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to a single stack, and `stack` resolves `params[:stack_id]` through that scoped relation. Every other API resource controller (e.g. `Shipit::Api::StacksController`) relies on this `stack`/`stacks` helper to bind the token's authorized stack to the stack actually acted upon.

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

It resolves `params[:stack_id]` via `Stack.from_param!`, a global unscoped lookup, instead of `stacks.from_param!`. It only calls `require_permission :read, :stack`, which checks the *permission* (`read:stack`) but never checks that `current_api_client.stack_id` (if set) matches the requested `stack_id`.

Compounding this, the primary producer of CCMenu tokens, `Shipit::CCMenuUrlController`, creates the `ApiClient` without any `stack_id` at all: [3](#0-2) 

so by default the token is globally scoped (`stack_id` nil → `stacks` resolves to `Stack.all` per the `BaseController#stacks` logic), even though the feature's intent — a per-stack "CCMenu URL" for CI status widgets — is that the token should only reveal the one stack it was generated for.

### Impact Explanation
Any valid `read:stack`-permissioned `ApiClient` token (whether globally scoped by default, as `CCMenuUrlController` creates, or explicitly stack-scoped by an admin through `Shipit::ApiClientsController`) can be replayed against `Shipit::Api::CCMenuController#show` with an arbitrary `stack_id` and will return that other stack's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, etc.), because the controller never re-applies the `current_api_client.stack_id` restriction that the rest of the API enforces. This is an unauthorized cross-stack read of stack state — matching the "unauthenticated/unauthorized read of stack state" High-impact category, since a token meant to authorize disclosure for stack A discloses state for stack B.

### Likelihood Explanation
Likelihood is high for any holder of a valid API token (even one intentionally scoped to a single stack via the admin UI, or the CCMenu-specific token that is embedded directly in a CI-status-widget URL and thus more likely to leak/be shared): they need only issue a GET to `/api/stacks/:other_stack_id/ccmenu.xml` with their own token, which is precisely the same request shape already exercised by `test/controllers/api/ccmenu_controller_test.rb`, just substituting a different `stack_id`.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and use the inherited scoped `stack` method from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) so the `current_api_client.stack_id` restriction is enforced consistently. Additionally, have `Shipit::CCMenuUrlController#client` create/find the `ApiClient` with `stack: stack` so CCMenu tokens are stack-scoped by construction, not just by convention.

### Proof of Concept
1. User has a valid `read:stack` API token `T` (e.g., obtained via `Shipit::CCMenuUrlController#fetch` for `stack_id: A`, or an admin-issued token explicitly scoped with `stack: A`).
2. Attacker (or the same user) sends `GET /api/stacks/B/ccmenu.xml?token=T` where `B` is a different, unrelated stack.
3. `Shipit::Api::BaseController#authenticate_api_client` accepts `T` and sets `current_api_client`.
4. `Shipit::Api::CCMenuController#stack` resolves `B` via `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id`.
5. `require_permission :read, :stack` only checks `T.permissions.include?('read:stack')`, which is true, so the request succeeds and returns stack `B`'s build status/lock state — data the token was never meant to authorize.
