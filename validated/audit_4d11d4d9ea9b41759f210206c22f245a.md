### Title
Webhook signature verification is bound to the attacker-controlled `repository.owner.login`/`organization.login` field while event handlers act on unrelated fields (`repository.full_name`, or nothing at all) - forged cross-organization commit statuses can trigger unauthorized deploys - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an inbound webhook against using the payload field `repository.owner.login` (with a fallback to `organization.login`), both of which are attacker-supplied JSON fields inside the very body being verified. None of the event handlers re-check that this "authenticated organization" actually owns the resource the handler subsequently mutates. `Webhooks::Handlers::StatusHandler`, in particular, performs no repository scoping whatsoever - it looks up commits system-wide by SHA (`Commit.where(sha: params.sha)`) and writes a `Status` for every match, regardless of which organization the signature was verified for. This breaks the binding "organization that authenticated == repository/commit that is written," identical in shape to the reported Convex bug where a call path skips the check that should scope the action.

### Finding Description
Shipit explicitly supports multiple GitHub organizations configured on a single instance, each with its own `app_id`/`installation_id`/`webhook_secret` (see `config/secrets.development.shopify.yml` listing `somegithuborg` and `someothergithuborg`, and `docs/setup.md` explaining that the `webhook_secret` is an operator-chosen string typed in during GitHub App creation - i.e., an org admin plainly knows their own org's secret).

The webhook signature check is: [1](#0-0) 

`repository_owner` used to pick the verifying `github_app` comes straight from the JSON body: [2](#0-1) 

Once the signature is accepted (valid for *some* configured organization), the event is dispatched generically: [3](#0-2) 

`StatusHandler` then processes the payload with **no organization or repository check at all**: [4](#0-3) 

Contrast this with the base `Handler` class, which does have a repository-scoping helper (`repository_name`/`stacks`) used by other handlers such as `PushHandler`: [5](#0-4) [6](#0-5) 

`StatusHandler` does not call `stacks`/`repository_name` at all - it matches commits purely by SHA across every stack of every organization tracked by the Shipit instance.

The binding that should hold and is never enforced:
`organization_that_signed(request) == owner_of(repository containing Commit#sha targeted by the handler)`

Since an org admin legitimately knows their *own* org's `webhook_secret` (it's a value they typed in themselves, not a GitHub-issued secret), they can compute a fully valid `X-Hub-Signature` for a payload whose `repository.owner.login`/`organization.login` is set to their own org (satisfying `verify_signature`), while the `sha`, `state`, `context`, `description` fields target a commit belonging to a completely different, unrelated stack/organization hosted on the same Shipit instance.

### Impact Explanation
A forged `status` webhook lets the attacker set an arbitrary CI status (`success`) on any commit SHA in any stack tracked by the instance: [7](#0-6) 

`Commit#deployable?` depends directly on this forged status: [8](#0-7) 

And `add_status` schedules continuous delivery automatically once the commit becomes deployable for stacks with continuous deployment enabled: [9](#0-8) [10](#0-9) 

This can cause an **unauthorized deploy** of a commit belonging to a repository/organization the attacker has no legitimate access to, purely by forging a webhook signed with credentials for an unrelated organization hosted on the same multi-tenant Shipit instance.

### Likelihood Explanation
Any organization onboarded onto a shared/multi-tenant Shipit instance (a configuration explicitly supported and documented, e.g. `config/secrets.development.shopify.yml`) trivially knows its own `webhook_secret` and can send this forged request at will; no interaction with the victim organization is required, and the flaw is hit on every `status` webhook delivery since `StatusHandler` never scopes by repository.

### Recommendation
- In `WebhooksController`, after resolving the payload's declared repository/organization and verifying the signature, cross-check that the same organization actually owns every resource the dispatched handler will touch.
- In `Webhooks::Handlers::StatusHandler` (and any other handler that doesn't already do so), scope the lookup through `stacks`/`repository_name` (as `PushHandler` does) instead of querying `Commit` globally by SHA, ensuring the commit's stack's repository owner matches the organization whose secret validated the signature.

### Proof of Concept
1. Attacker is an administrator of `orgA`, which is one of several organizations configured on a shared Shipit instance (per `config/secrets.*.yml` supporting multiple `github:` orgs). Attacker knows `orgA`'s `webhook_secret` because they typed it in themselves when creating the GitHub App (per `docs/setup.md`).
2. Attacker crafts a JSON body:
```json
{
  "sha": "<sha-of-a-real-commit-on-orgB/private-repo-stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(orgA_webhook_secret, body)` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `"orgA"`, fetches `orgA`'s `github_app`, and the signature validates successfully (app/controllers/shipit/webhooks_controller.rb:24-30).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit belonging to `orgB`'s stack (never checking that it belongs to `orgA`), and calls `create_status_from_github!`, marking it `success`.
6. If `orgB`'s stack has continuous deployment enabled, `schedule_continuous_delivery` triggers `ContinuousDeliveryJob`, resulting in an unauthorized deploy of a commit the attacker never had legitimate access to.
