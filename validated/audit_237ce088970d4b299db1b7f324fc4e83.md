### Title
Unfiltered `ReviewStack#env` merge of PR label names allows fork PR authors to inject arbitrary environment variables (e.g. `BASH_ENV`) into task/deploy step processes - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the stack's environment hash with a fixed value of `"true"` and no allowlist, unlike every other user-influenced env path in the codebase (`Stack#trigger_task`, `Stack#build_deploy`, `RollbacksController`, `TasksController`) which all route through `EnvironmentVariables#permit`. This unfiltered hash flows into `TaskCommands#env` → `Command#unbundled_env` → `PTY.spawn`, letting a PR author who can label their own PR (or any actor able to trigger `LabelCapturingHandler#capture_labels` with a crafted webhook body) set arbitrary env var names such as `BASH_ENV` for every `tasks.<name>.steps` and deploy/rollback step the review stack runs.

### Finding Description
The broken binding: the set of environment variable keys reaching `Command#start`/`PTY.spawn` for a review stack's task/deploy steps should equal `deploy_variables ∪ rollback_variables ∪ task.variables` (the shipit.yml-declared allowlists enforced by `EnvironmentVariables#permit`, see `app/models/shipit/task_definition.rb:63-65`, `app/models/shipit/deploy_spec.rb:174-180`). Instead it equals that set **plus every PR label name, uppercased, attacker-controlled and unfiltered**: [1](#0-0) 

`LabelCapturingHandler#capture_labels` persists label names straight from the webhook payload into `pull_request.labels`: [2](#0-1) 

`TaskCommands#env` merges `@stack.env` (which for a `ReviewStack` includes the label-derived keys) directly, with no `EnvironmentVariables#permit` call anywhere in the chain: [3](#0-2) 

That hash is passed into `Command.new(command_line, env:, chdir:)` for every step (`perform`, `install_dependencies`): [4](#0-3) 

`Command#unbundled_env` merges `@env.stringify_keys` (i.e. the attacker-supplied `BASH_ENV=true`) on top of `BASE_ENV`, and this exact hash is handed to `PTY.spawn`: [5](#0-4) 

Root cause: `EnvironmentVariables#permit` (the only sanitizer in the codebase) is applied to controller-submitted `env` params (`app/controllers/shipit/rollbacks_controller.rb:29-31`, `app/controllers/shipit/api/rollbacks_controller.rb`, `app/controllers/shipit/tasks_controller.rb:77-82`) and to `Stack#build_deploy`/`Stack#trigger_task` (`app/models/shipit/stack.rb:139-172`), but it is never applied to `Stack#env`/`ReviewStack#env` itself before it is merged into `TaskCommands#env`. `ReviewStack#env` is a self-inflicted bypass of that allowlist mechanism.

Existing guards that fail to catch this: `EnvironmentVariables#permit` exists but is not invoked on this path; `force_github_authentication`/`verify_signature` authenticate the webhook sender/repository but do not constrain the *content* of `labels`; there is no `Repository`/`Stack` validation restricting label name characters.

Attacker flow: attacker opens (or already has) a fork PR against a repo configured with `provisioning_behavior=prevent_with_label`; a review stack is provisioned for that PR; attacker adds a label named `bash_env` (case-insensitive, becomes `BASH_ENV` after `.upcase`) to their PR, which is captured via `capture_labels`; attacker also commits a file literally named `true` at the working-directory root of their branch (the review stack's checked-out code, which is what the step's `chdir` points to). When a `tasks.<name>.steps` command (or deploy step) subsequently runs for that review stack, `BASH_ENV=true` is present in the child process env; if the step is invoked through a bash-compatible non-interactive shell, bash sources the relative file `true` from the step's working directory before running the intended command — the attacker's committed content executes with the deploy host's privileges.

### Impact Explanation
An unprivileged fork PR author gains code execution in the environment of every `tasks.<name>.steps`/deploy/rollback/dependency-install step executed for their own review stack, on the Shipit deploy host, using only PR-label control and their own repository's file content — no Shipit credentials, GitHub App key, or maintainer role required. This matches the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" impact category. The blast radius is scoped to the review stack tied to that PR/repo (the working directory and steps run for that stack), but the deploy host and its stored secrets (`GITHUB_TOKEN`, deploy credentials, etc. present in the process environment or reachable from the host) are within reach of an attacker-controlled process.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` with `provisioning_behavior=prevent_with_label` (or `allow_with_label`/`allow_all`, since `ReviewStack#env` unconditionally merges labels regardless of provisioning behavior) and must run steps for the review stack (default `tasks.*.steps`, deploy/rollback steps). Attacker cost is minimal: open a PR from a fork, add a label to it (label creation/attachment permission model is repository-dependent, but per the stated attacker capabilities this is assumed feasible), and commit a file named `true`. This is fully repeatable per PR/label change and does not require any secret. The main uncertainty is whether the deploy host's step-invocation shell honors `BASH_ENV` (depends on `/bin/sh` → bash vs dash), but the unfiltered env-injection itself (the core defect: PR labels reaching `Command`'s spawned environment with no allowlist) is unconditionally reproducible and independent of that shell detail.

### Recommendation
Do not let `ReviewStack#env` merge raw, attacker-controlled label names as environment variable keys. At minimum:
1. Route `ReviewStack#env`'s label-derived hash through `EnvironmentVariables#permit` against an explicit, repository/shipit.yml-declared allowlist of permitted label-derived variable names, mirroring how `deploy_variables`/`rollback_variables`/`task.variables` are enforced elsewhere.
2. Alternatively/additionally, deny-list known-dangerous variable names (`BASH_ENV`, `LD_PRELOAD`, `PATH`, `IFS`, `ENV`, `PROMPT_COMMAND`, etc.) centrally in `Command#unbundled_env` or `TaskCommands#env` so no caller can override them regardless of source.
3. Namespace/prefix label-derived variables (e.g. `LABEL_<NAME>`) instead of exposing raw uppercased label text as a bare environment variable key.

### Proof of Concept
minitest plan (`test/lib/shipit/task_commands_test.rb` or `test/models/shipit/review_stack_test.rb`):
```ruby
test "[prevent_with_label] BASH_ENV injected via a PR label reaches the tasks.<name>.steps process env" do
  stack = shipit_stacks(:review_stack) # a ReviewStack fixture
  configure_provisioning_behavior(repository: stack.repository, behavior: :prevent_with_label, label: "deploy-me")
  stack.pull_request.update!(labels: ["bash_env"]) # simulates LabelCapturingHandler#capture_labels persisting an attacker-chosen label name

  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  # Binding under test: BASH_ENV must NOT be attacker-reachable via a PR label.
  assert_nil env["BASH_ENV"], "expected BASH_ENV to be absent, but PR label injected it"
  # Before fix, this fails because:
  # assert_equal "true", env["BASH_ENV"]

  command = Shipit::TaskCommands.new(task).perform.first
  assert_nil command.env["BASH_ENV"] # confirms the value reaching Command#unbundled_env / PTY.spawn
end
```
This demonstrates the exact equality violated: `command.env.keys` should equal the shipit.yml-declared `task.variables` names (plus fixed internal keys), but instead includes attacker-chosen PR label names such as `BASH_ENV`.
