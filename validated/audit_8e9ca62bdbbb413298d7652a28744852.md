This is confirmed. The equality that should hold is: **organization authenticated by the HMAC check == organization that owns the repository the webhook handler acts on**. That equality is not enforced.

### Title
Webhook signature-selection field is not bound to the repository field handlers act on, allowing cross-organization/repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to validate a webhook against using `repository_owner`, taken from the **unverified** JSON body (`repository.owner.login`, or `organization.login` fallback). Once the signature check passes, every event handler (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, etc.) independently reads a *different* field of the same unverified body, `repository.full_name`, to resolve the `Shipit::Repository`/`Stack` it operates on. Nothing ties these two fields together, so a payload can be crafted where the "owner" used for signature verification and the "full_name" used to select the target repository name different organizations.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Every handler bases its target resolution on a separate field, `repository.full_name`, via the shared base class:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler` (triggers `sync_github`, which drives commit tracking and continuous-deployment triggers) and `PullRequest::*Handler`s (which resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`) both use `full_name`, not the `owner.login` field used for signature routing. [3](#0-2) [4](#0-3) 

Shipit explicitly supports hosting multiple GitHub organizations behind one instance, each with its own independent `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.shopify.yml`), each looked up via `Shipit.github(organization: repository_owner)`. [5](#0-4) 

**Binding that should hold:** `organization authenticated by verify_signature(repository_owner) == organization owning repository.full_name acted on by the handler`. This binding is never checked — an attacker who can produce a validly-signed payload for **Org A** (e.g. because Org A's `webhook_secret` was leaked, is weak/misconfigured, or is left blank as the docs describe it being "optional") can set `repository.owner.login = "OrgA"` (so `verify_signature` selects and validates against Org A's app/secret) while setting `repository.full_name = "OrgB/victim-repo"` (a completely different organization's stack hosted on the same Shipit instance). The signature check passes, and the handler acts on `OrgB/victim-repo` regardless.

### Impact Explanation
This breaks Shipit's multi-tenant isolation between organizations/repositories hosted on the same instance. Concretely, an attacker with a valid signature for one onboarded, lower-trust organization can:
- Inject fabricated `push` events for another org's stack, forcing `GithubSyncJob`/`sync_github`, which can advance `last_deployed_commit`/undeployed-commit tracking and, combined with `continuous_deployment`, trigger unauthorized deploys on a stack belonging to an organization they have no legitimate relationship with (`Repository.from_github_repo_name` → `PushHandler#process` → `stack.sync_github`).
- Inject fabricated `status`/`check_suite` events that flip a foreign stack's commit CI state, unblocking deploys or the merge queue for repositories they don't control.
- Manipulate `pull_request` events (`opened`, `labeled`, `closed`, etc.) against foreign review-stacks, causing archive/unarchive/provisioning actions cross-organization.

This is a cross-repository/cross-organization write achieved purely by exploiting an unchecked binding between the field used for cryptographic authentication and the field used for authorization/targeting — the same class of confusion as the reported `assignRole` bug (a privilege check that validates one identity but lets an unrelated field determine the actual effect).

### Likelihood Explanation
Likelihood is Low/conditional: it requires the attacker to already possess a valid HMAC signature for *some* organization onboarded to the same Shipit instance (e.g. a leaked/blank `webhook_secret` for one org, or control of a GitHub App webhook delivery for one tenant). This is realistic in genuinely multi-tenant deployments (the codebase explicitly supports and tests multiple orgs sharing one instance, and documents `webhook_secret` as "optional"), where trust levels differ between onboarded organizations. It does not require a Shipit session, API token, or any credential belonging to the *targeted* organization/repository — only to some other tenant on the same instance, which is exactly the boundary this endpoint is supposed to enforce.

### Recommendation
After successfully verifying the signature for the organization identified by `repository_owner`, re-derive the repository owner used by handlers (`repository.full_name`'s owner segment, or a dedicated verified field) and assert it matches the `repository_owner` that was cryptographically authenticated before dispatching to any handler. Reject the webhook (422) on mismatch. Consider also normalizing/duplicating this check inside `Handler#repository_name`/`#stacks` so any future handler cannot bypass it.

### Proof of Concept
1. Shipit instance hosts two organizations, `OrgA` (attacker has/derives a valid `webhook_secret`, e.g. blank/leaked) and `OrgB` (victim, unrelated organization with stacks configured).
2. Attacker crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefcafefeed",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `OrgA`'s `webhook_secret` and `X-Github-Event: push`, and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` computes `repository_owner == "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and verifies successfully since the signature was generated with `OrgA`'s secret. [6](#0-5) 
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name('OrgB/victim-repo')` and calls `stack.sync_github` on OrgB's stack — an action never authenticated for OrgB. [7](#0-6)
