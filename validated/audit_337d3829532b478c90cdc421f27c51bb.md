### Title
CCMenu API endpoint bypasses `ApiClient` stack scoping, allowing a token authorized for one stack to read another stack's build/deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` can be scoped to a single `stack_id`, meaning the token is only supposed to authorize `read:stack`/etc. operations against that one stack [1](#0-0) . `Shipit::Api::BaseController` enforces this binding by having `stacks` return only the client's assigned stack when `stack_id?` is set, and `stack` resolves via that scoped relation: `@stack ||= stacks.from_param!(params[:stack_id])` [2](#0-1) . `Shipit::Api::CCMenuController`, however, overrides `stack` to resolve directly against the unscoped `Stack` model: `@stack ||= Stack.from_param!(params[:stack_id])` [3](#0-2) , entirely bypassing the `current_api_client.stack_id` restriction that every other API controller relies on.

### Finding Description
This is an analog of the mitigation gap described in the report: a binding ("the stack a token authorizes" == "the stack the token's request actually touches") that is supposed to be enforced uniformly is silently skipped in one code path.

- `ApiClient#stack_id` scopes a token to a single stack via `belongs_to :stack, optional: true` [4](#0-3) .
- `BaseController#stacks` is the single chokepoint meant to enforce this: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [5](#0-4) , and `#stack` derives from it via `stacks.from_param!(params[:stack_id])` [6](#0-5) .
- `CCMenuController` requires only `read:stack` permission (`require_permission :read, :stack`) [7](#0-6)  and then defines its own `stack` method that queries `Stack.from_param!(params[:stack_id])` directly, never consulting `current_api_client.stack_id` [3](#0-2) .
- The controller also allows authenticating via a plain query-string `token` param (`ApiClient.authenticate(params[:token])`) rather than requiring HTTP Basic auth [8](#0-7) , which is how CCMenu URLs are normally distributed per-stack via `ccmenu_url_controller.rb` (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)`) [9](#0-8) .

Before the fix that introduced per-stack scoped `ApiClient`s, "authorized for `read:stack`" implicitly meant "authorized for all stacks." With scoped clients, an operator can legitimately hand out a stack-specific CCMenu token expecting it to only ever return status for that one stack (as seen in the fixture `here_come_the_walrus`, scoped to the `shipit` stack, and exercised in `test "an api client scoped to a stack will only see that one stack"` for the JSON stacks API) [10](#0-9) [11](#0-10) . But `CCMenuController#stack` never applies this scoping, so any holder of a scoped, `read:stack`-permitted CCMenu token/URL can substitute an arbitrary `stack_id` in the request path and receive that other stack's CI/deploy status (name, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) — data belonging to stacks the token was never authorized for.

### Impact Explanation
This crosses the "stack a token authorises" vs "stack it touches" trust boundary called out in scope: a token minted and distributed for one stack (e.g. embedded in a CI dashboard URL, which is inherently less protected than a Basic-Auth header since it is a bare query-string value) can be used to enumerate/read build and deploy status of any other stack in the installation, an unauthorized read of stack state that maps to the "unauthenticated/unauthorized read of stack state, task streams or deploy output" High-impact category defined by scope.

### Likelihood Explanation
Likelihood is significant because: (1) CCMenu tokens are specifically designed to be embedded in plain URLs (`ccmenu_url_controller.rb` builds `token` as a query param, not sent over Basic Auth) [12](#0-11) , making them more exposure-prone (browser history, logs, shared dashboards); (2) exploitation requires nothing more than changing `stack_id` in the URL path — no privilege escalation, no secret, no session; (3) the bypass is a straightforward method override that is easy to miss in review since every sibling controller (`StacksController`, etc.) correctly uses the scoped `stack`/`stacks` helpers from `BaseController`.

### Recommendation
Remove `CCMenuController`'s private `stack` override and instead rely on `BaseController#stack` (i.e., `stacks.from_param!(params[:stack_id])`), so CCMenu lookups are constrained the same way as every other API endpoint by `current_api_client.stack_id`. If query-string authentication must be preserved for CI tool compatibility, that override should only affect `authenticate_api_client`, not the stack resolution logic.

### Proof of Concept
1. Admin creates a CCMenu URL for `stack A` via `CCMenuUrlController#fetch`, producing `ApiClient` scoped to `stack: A`, `permissions: [read:stack]`, and a token embedded as `?token=...` [13](#0-12) .
2. Attacker obtains this URL (e.g., from an internal dashboard, browser history, or shared chat) and requests:
   `GET /api/stacks/<B_owner>/<B_repo>/<B_env>/ccmenu.xml?token=<A's token>`
3. `authenticate_api_client` succeeds because the token is valid for `ApiClient` A [8](#0-7) .
4. `require_permission :read, :stack` passes since client A has `read:stack` permission (checked without stack context) [14](#0-13) .
5. `stack` resolves `Stack.from_param!(params[:stack_id])` against stack B directly, ignoring that client A is scoped to stack A [3](#0-2) .
6. `show` renders stack B's `lastBuildStatus`/`lastBuildLabel`/etc. to the attacker, who was never authorized for stack B [15](#0-14) .
