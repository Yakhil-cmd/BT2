### Title
Signature verification keyed off `repository.owner.login` while event routing keyed off `repository.full_name` allows cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate `X-Hub-Signature` based on `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON body, while `Shipit::Webhooks::Handlers::Handler#repository_name` — which decides which `Repository`/`Stack` the event actually acts on — reads `repository.full_name` from that same unverified body. [1](#0-0) [2](#0-1)  These two fields are never required to be consistent, so an attacker can pick which org's secret is used for verification independently of which repo's stacks get processed.

### Finding Description
In a multi-organization Shipit deployment (`config/secrets.yml` keyed by organization, as documented) [3](#0-2) , each organization has its own `github_app`/`webhook_secret` looked up via `Shipit.github(organization: repository_owner)`. `verify_webhook_signature` explicitly treats a blank/unset `webhook_secret` as automatically valid: `return true unless webhook_secret`. [4](#0-3)  A blank `webhook_secret` is a documented, non-privileged configuration state (`webhook_secret: # nil` appears as the example/default in both the example and Shopify secrets templates). [5](#0-4) [6](#0-5) 

The controller determines *which* organization's secret to check against purely from the attacker-controlled payload:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [7](#0-6) 

But once verification passes (or is skipped because that org has no secret), the actual handler dispatch resolves the target `Stack` using a **different field** from the same payload:
```
def repository_name
  payload.dig('repository', 'full_name')
end
...
Repository.from_github_repo_name(repository_name)&.stacks
``` [2](#0-1) 

Nothing enforces `repository.full_name.split('/').first == repository.owner.login`. An attacker can therefore submit a single forged webhook body where `repository.owner.login` names an organization configured with no `webhook_secret` (satisfying/bypassing `verify_signature`), while `repository.full_name` names `victim-org/victim-repo`, a fully-secured organization's tracked repository. `PushHandler#process`, for example, will then call `stack.sync_github(expected_head_sha: params.after)` for stacks belonging to `victim-org/victim-repo` using attacker-supplied `ref`/`after` values, with no valid signature from `victim-org` ever having been checked. [8](#0-7) 

This is the direct analog of the report's bug class: the entity that is cryptographically "authenticated" (the organization whose secret gates `verify_signature`) is not bound to the entity that is actually "written to" (the repository/stack resolved by `repository.full_name`), exactly the "organization authenticated versus the repository that is written" binding called out in scope.

### Impact Explanation
An unauthenticated network attacker (no Shipit session, no API token, no GitHub write access) can forge webhook deliveries that are accepted as authentic for any tracked stack, as long as any single organization configured on the instance has a blank `webhook_secret` (a documented, easy-to-reach misconfiguration, and arguably the *default* state per the shipped example secrets files). Depending on which webhook handler is invoked, this can trigger unauthorized `GithubSyncJob`s, forged commit statuses, spoofed `pull_request`/`merge_status`/`check_run` events, or other state changes against a stack that belongs to an entirely different, properly-secured GitHub organization — an unauthorized state change bypassing the intended per-organization authentication boundary. This maps to "unauthorized deploy/rollback"-adjacent impact since `sync_github` and status-driven automation (merge, continuous deployment) can be triggered by spoofed push/status events without ever presenting a valid signature for the targeted org.

### Likelihood Explanation
Likelihood is moderate-to-high in any real multi-org deployment: the vulnerable condition (one org with `webhook_secret` unset) is exactly what the shipped `secrets.development.example.yml` and `secrets.development.shopify.yml` templates show as the baseline/example value, so it's plausible in staging/test orgs coexisting with production orgs on the same Shipit instance. No credentials, no signature forgery, and no insider access are required — only knowledge that such an org exists (discoverable via `422`/`GithubOrganizationUnknown` probing of the `/webhooks` endpoint, which logs and differentiates "unknown organization" from other failure modes).

### Recommendation
Bind the signature-verification identity to the same value used for handler dispatch: after resolving `repository_owner`, verify that `payload.dig('repository', 'full_name')` (and `organization.login`) actually belongs to that same owner before invoking any handler, or better, resolve the target `Repository`/`Stack` first and use *its* configured organization/`webhook_secret` to verify the signature, rejecting the payload if the two are inconsistent. Additionally, stop treating a blank `webhook_secret` as an automatic pass — require an explicit `Shipit.webhook_validation_disabled?`-style opt-in rather than silently accepting unsigned payloads.

### Proof of Concept
1. Configure `config/secrets.yml` with two orgs: `victim-org` (has `webhook_secret: <strong-secret>`, tracks stack `victim-org/victim-repo`) and `test-org` (per the shipped example template, `webhook_secret:` left blank).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "test-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
No `X-Hub-Signature` header is required.
3. `WebhooksController#verify_signature` computes `repository_owner = "test-org"`, loads `test-org`'s `github_app`, and `verify_webhook_signature` returns `true` immediately because `test-org.webhook_secret` is blank. [9](#0-8) 
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, matches `victim-org`'s real, secured stack, and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — a `victim-org` state change triggered without ever satisfying `victim-org`'s webhook secret. [10](#0-9)

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
