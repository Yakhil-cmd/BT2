`StatusHandler#process` writes commit statuses by global SHA lookup, unscoped by the webhook's verified repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the request was signed with `Shipit.github(organization: repository_owner).webhook_secret` for the claimed org (org B) in the payload's `repository.owner.login`. `StatusHandler#process` then looks up commits by `Commit.where(sha: params.sha)` with no relation whatsoever to that verified repository, so any commit sharing that SHA in any stack/org gets a new `Status` written from attacker-controlled data.

### Finding Description
The broken binding: `verify_signature` proves `signing_org == payload.dig('repository','owner','login')` (org B), but the record mutated is scoped by `identity_of(commit) == org_that_owns(sha)`, which can be org A. These are asserted to be the same identity but nothing in the code enforces it for the `status` event.

Code path:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and verifies the HMAC using `Shipit.github(organization: repository_owner).webhook_secret` [1](#0-0) [2](#0-1) .
- `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the entire parsed JSON body [3](#0-2) .
- The base `Handler` class does expose a `stacks`/`repository_name` helper that scopes lookups to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [4](#0-3) , and other handlers (e.g. `CheckSuiteHandler`, the `PullRequest::*Handler`s) use this `stacks`/`repository` scoping before writing anything [5](#0-4) [6](#0-5) .
- `StatusHandler`, however, does not require or use `repository` at all in its `params` schema, and `#process` does an unscoped, global `Commit.where(sha: params.sha)` lookup, writing a `Status` on every matching commit regardless of which stack/repository/org it belongs to [7](#0-6) .
- `Commit#sha` is a per-stack column (`belongs_to :stack`) but is not globally unique across stacks/orgs in the schema as used here [8](#0-7) .

Exploit flow: The attacker owns org B and has a real, legitimately configured GitHub App/webhook for org B, so they know or can trigger deliveries signed with org B's `webhook_secret` (this is normal, expected access for any repo owner using Shipit — not a secret leak). They send `POST /webhooks` with `X-Github-Event: status`, `repository.owner.login` / `repository.full_name` set to org B (so `verify_signature` passes against org B's real secret), but `sha` set to a SHA value belonging to a commit tracked under org A's stack (SHA values are not secrets — they are visible in git history, PRs, CI logs, and Shipit's own public stack pages). Because `StatusHandler#process` never checks `repository`/`full_name` against the commit's actual stack, the status is written onto org A's commit.

Existing guards examined and found insufficient for this handler: `verify_signature` only binds signature validity to org B, never to which commit gets mutated [9](#0-8) ; `drop_unhandled_event` and `ExplicitParameters` schema in `StatusHandler` do not require/validate `repository` [10](#0-9) ; the base `Handler#stacks` scoping mechanism exists but is simply unused by `StatusHandler`.

### Impact Explanation
An attacker who legitimately controls only org B's webhook can inject arbitrary CI status records (`state`, `description`, `target_url`, `context`, `created_at`) onto any commit in any other tenant's (org A's) stack, as long as they know that commit's SHA — which is not secret information. This is a cross-tenant write (`Status` record creation) achieved despite correct signature verification for the attacker's own org, matching the "payload for one repository mutating another's stack/commit" Critical category. It is repeatable against any known SHA and any number of times, and can corrupt CI/status gating used to allow or block deploys in org A's pipeline (e.g., faking a `success` status for a required check), potentially unlocking a deploy that shouldn't be allowed. Blast radius spans all Shipit-tracked orgs sharing the same Shipit installation, since the lookup is global (`Commit.where(sha:)` with no stack/org scope).

### Likelihood Explanation
Preconditions are low-cost and match the threat model exactly: the attacker needs only their own legitimately-configured org B (any GitHub App owner can obtain this) and knowledge of a target commit SHA belonging to org A's stack, which is typically discoverable through public git history, GitHub UI, CI logs, or even the target Shipit instance's own stack pages. No Shipit session, API token, or org A secret is required. The attack is fully repeatable — one POST per forged status per SHA — using only standard HTTP tooling.

### Recommendation
Require and validate `repository.full_name` in `StatusHandler`'s params, and scope the commit lookup through the base `Handler#stacks` (or an equivalent `Repository.from_github_repo_name(...).stacks.commits`) instead of the bare `Commit.where(sha: params.sha)`, mirroring the pattern already used in `CheckSuiteHandler` and the `PullRequest::*` handlers.
