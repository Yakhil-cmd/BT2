### Title
Oracle last-update timestamp shared cache can be poisoned by one caller to freeze price resolution for all other users - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The `price-resolve` function stores the freshest observed oracle timestamp per `{type, ident}` key in the shared `last-update` map, and every subsequent call anywhere in the protocol enforces `(>= ts prev)` against this shared, global watermark [1](#0-0) . Any unprivileged caller who supplies a valid, signed Pyth (or DIA) feed with the largest available future timestamp permanently raises this shared watermark for that asset, since the map is written unconditionally whenever a newer timestamp is observed with no per-user scoping.

### Finding Description
`last-update` is declared as a protocol-wide map keyed only by `{ type, ident }`, i.e. by asset identity, not by caller [2](#0-1) . Every public entry point that resolves a price for an asset (borrow, withdraw, liquidate, collateral-add, etc., via `write-feeds`/`price-multi-resolve`/`price-resolve`) shares this same map. `price-resolve` computes `oracle-timestamp-fresh` by checking `ts <= now` and `ts >= prev`, then unconditionally does `(map-set last-update key timestamp)` if the new timestamp exceeds the stored one [3](#0-2) . Because Pyth/DIA feeds are permissionlessly relayed (any caller can submit any valid, correctly-signed price update they can obtain, including one whose `publish-time` is close to `stacks-block-time`), a caller who is first to submit a feed with the maximum currently valid timestamp for an asset raises the global watermark to that value. Any other user's subsequent transaction in the same or a later block that carries a feed with an equal-or-earlier timestamp for that same asset (e.g., because their price relay source lags, or because network latency causes them to fetch a feed update published slightly earlier) will fail `(>= ts prev)` and revert with `ERR-ORACLE-INVARIANT`, even though their price data is otherwise fresh and legitimate.

### Impact Explanation
This is a shared, global cache primed by one caller and consumed by another: attacker (or even an ordinary, fast user) primes `last-update[asset]` to a high value; victim's otherwise-valid transaction on the same asset is rejected because the shared watermark was raised out from under them. Because price resolution gates borrow, withdraw, repay-triggered health checks, and liquidation, an attacker can use this to block a specific victim's time-sensitive action (e.g., prevent a victim from repaying/adding collateral before a liquidation window, or block a liquidator's liquidation tx) by front-running with a feed timestamp that the victim's already-fetched feed cannot exceed. This lands in the temporary freezing of funds impact class, since the victim cannot execute transactions involving that asset until a fresher feed timestamp than the poisoned watermark becomes available.

### Likelihood Explanation
Likelihood is moderate: no privileged role or oracle compromise is required, only the ability to relay a legitimately signed Pyth/DIA update (a normal, permissionless action already supported by the protocol's `price-feeds` parameter). The main constraint is that the attacker's feed timestamp must be `<=` current block time and pass confidence checks, but attackers can simply wait for/select the newest available valid feed and submit ahead of the victim in the same block via mempool ordering/MEV, which is feasible on most chains supporting Pyth pull-oracle updates.

### Recommendation
Do not use a single global monotonic watermark shared across all callers to gate price freshness. Either (a) remove the `>= ts prev` monotonicity requirement entirely and rely solely on the absolute staleness check against `stacks-block-time` (`delta <= max-staleness`), since Pyth/DIA already guarantee authenticity and recency via signatures, or (b) scope monotonicity tracking so it cannot be weaponized to reject a different, independently-valid fresher-than-staleness-bound update (e.g., only reject if the new timestamp is stale relative to `now`, not relative to another caller's previously submitted timestamp).

### Proof of Concept
1. Victim intends to call `borrow`/`collateral-add` for asset X in block N, holding a valid Pyth update with `publish-time = T1` (fresh, within `max-staleness`).
2. Attacker observes victim's pending transaction (or simply races ahead) and submits any transaction touching asset X with a valid Pyth update `publish-time = T2 > T1` (also fresh and legitimately signed) in an earlier position in block N (or block N-1).
3. `price-resolve` sets `last-update[{type, ident}] = T2` [4](#0-3) .
4. Victim's transaction executes afterward with `T1 < T2`; `oracle-timestamp-fresh` evaluates `(>= ts prev)` as `(>= T1 T2)` = false, so `price-resolve` asserts `ERR-ORACLE-INVARIANT` and the victim's transaction reverts [5](#0-4) , even though `T1` independently satisfies the staleness bound and would have been accepted absent the attacker's prior call.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
