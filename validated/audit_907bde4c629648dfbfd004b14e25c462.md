### Title
Webhook signature verification is scoped to the wrong organization, allowing cross-repository status/push forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the inbound signature against based on `repository_owner`, which is read straight out of the unauthenticated JSON body (`repository.owner.login` or `organization.login`). All downstream event handlers, however, resolve the target `Repository`/`Stack` using a *different* field of that same unauthenticated body: `repository.full_name`. Nothing ties the two together, so in a multi-organization Shipit install the field that decides "which secret proves authenticity" and the field that decides "which repository gets acted upon" are never checked for consistency.

### Finding Description
`Shipit.github` supports a per-organization configuration map (`TOP_LEVEL_GH_KEYS`, `github_app_config`), each with its own independent `webhook_secret`: [1](#0-0) 

`WebhooksController#verify_signature` picks the app/secret to verify against using `repository_owner`, which is attacker-controlled JSON, not anything cryptographically bound yet: [2](#0-1) [3](#0-2) 

Once `verify_signature` passes (using organization A's `webhook_secret`), `create` dispatches the *entire raw payload* to every registered handler for the event, unmodified: [4](#0-3) 

Every handler, however, resolves its target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — a completely separate field from the one used for signature-org selection: [5](#0-4) 

For example `PushHandler` forces a resync of any stack matching `repository.full_name` + branch to an attacker-chosen `after` SHA: [6](#0-5) 

And `StatusHandler` writes a forged commit status (state/description/context/target_url) for any commit matching `sha`, with no cross-check against `repository.full_name`/owner at all: [7](#0-6) 

**The broken binding**: "organization that authenticated the request" (`repository_owner` used in `verify_signature`) ≠ "repository that gets written to" (`repository.full_name` used by every `Handler`). In a single-organization install this is not exploitable because there is only one possible signer. But `docs/setup.md` and `template.rb` explicitly document and support configuring multiple GitHub organizations under one Shipit instance, each with its own webhook secret — this is a first-class, documented deployment mode, not a misconfiguration: [8](#0-7) 

In that documented multi-org mode, anyone who can produce a validly-signed payload for *any one* of the configured organizations (e.g. because they control that org's GitHub App/webhook settings — a valid GitHub identity for org A, not a Shipit credential) can set `repository.owner.login` to org A (to pass `verify_signature`) while setting `repository.full_name`/`sha` to point at a completely different, unrelated organization's (org B's) repository. Shipit will process the event as if it legitimately came from org B.

### Impact Explanation
Falls under the "unauthorized deploy" bucket: `StatusHandler` lets the attacker forge arbitrary commit statuses for any commit SHA in a target repository they do not control, which is precisely the mechanism Shipit uses to gate deployability (`Commit#create_status_from_github!`, consumed by `Stack`/`MergeRequest`/`DeploySpec` "required status" logic). Forging a passing status for a malicious or unreviewed commit can make it appear deployable through Shipit's UI/API, enabling a deploy of code that never actually passed the real CI/review process on the target repository — without the attacker ever holding a Shipit session, API token, or write access to the victim GitHub repository. `PushHandler` similarly lets the attacker trigger `sync_github` with an arbitrary `expected_head_sha` against a stack belonging to an org unrelated to the one that signed the request.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured for more than one GitHub organization (a supported, documented configuration), and (b) the attacker to be able to produce a validly HMAC-signed payload for at least one of the configured organizations (e.g., because they control that org's GitHub App webhook secret, are that org's admin, or that org's secret has otherwise leaked) — none of which require any Shipit credential or access to the victim organization/repository. This is a realistic path for any multi-tenant/multi-org Shipit deployment where the configured organizations do not fully trust each other.

### Recommendation
After signature verification succeeds, `verify_signature`/`create` should re-derive the organization from `repository.owner.login` and require that the *same* organization owns `repository.full_name` used by the handlers (i.e., verify `repository.full_name.split('/').first == repository_owner`, case-insensitively), rejecting the request otherwise. Alternatively, pass the verified `repository_owner` into each `Handler` and have `Handler#stacks`/`#repository` scope lookups to `Repository` records whose owner matches the verified organization, not just the raw `full_name` from the payload.

### Proof of Concept
1. Configure Shipit for two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s (per `docs/setup.md`'s "Using Multiple Github Applications" section).
2. As an actor who controls `org-a`'s GitHub App webhook secret (e.g. an `org-a` admin, with no access to `org-b` or any Shipit credential), craft a `status` event payload:
   ```json
   {
     "sha": "<sha-of-a-commit-in-org-b/target-repo>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "org-a" } }
   }
   ```
3. Compute `X-Hub-Signature` using `org-a`'s `webhook_secret` over the raw body.
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `Shipit.github(organization: "org-a")` and succeeds.
5. `StatusHandler#process` finds `Commit.where(sha: params.sha)` — which belongs to `org-b/target-repo` — and calls `create_status_from_github!`, writing a forged "success" status for that commit, independent of which organization actually signed the request.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
