### Title
Reentrancy in `liquidate` via caller-supplied `debt-ft`/`collateral-ft` traits allows collateral seizure to exceed its bound - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate` accepts `collateral-ft` and `debt-ft` as caller-controlled `<ft-trait>` parameters rather than hardcoded, vetted token principals [1](#0-0) . It computes the liquidation amounts and health status, then calls `vault-system-repay` (which triggers `contract-call?` on the liquidator-supplied `debt-ft`) *before* the borrower's on-chain debt is decremented via `debt-remove-scaled` [2](#0-1) . Because the token contract executing the transfer is chosen by the caller, a malicious `debt-ft`/`collateral-ft` implementation can re-enter `liquidate` on the same borrower during that transfer, before the first call's debt/collateral state mutations are committed.

### Finding Description
In `liquidate`, the health check, liquidation-amount calculation (`scale-debt-for-liquidation`, `coll-final`), and the `same-block-check` are all derived from state read at the top of the function (`get-liquidation-position`, `get-full-position`) [3](#0-2) [4](#0-3) . The debt repayment transfer happens via `vault-system-repay debt-aid debt-to-repay debt-ft debt-address`, which internally invokes `contract-call?` on the caller-supplied `debt-ft` trait principal to pull tokens from the liquidator into the vault [5](#0-4) . Only *after* this external call does the function persist the effects of the liquidation: `debt-remove-scaled` on `.v0-market-vault` and `collateral-remove` [6](#0-5) .

Because `debt-ft` (and `collateral-ft`) are trait-typed parameters supplied by `contract-caller` rather than fixed, whitelisted token contracts, the liquidator can pass a token contract they control. When the market calls `transfer` on that contract during `vault-system-repay`, the attacker's contract can execute arbitrary logic — including calling `liquidate` again on the same `borrower` — before the first invocation's `debt-remove-scaled`/`collateral-remove` state updates have been written. The re-entrant call reads the borrower's still-unmodified debt/collateral state (the registry updates in `.v0-market-vault` have not yet happened), so the health check, LTV, and liquidation-amount calculations are computed against stale (pre-liquidation) figures. This lets the liquidator repeat the liquidation-amount computation and seize collateral for what is effectively the same underlying debt reduction multiple times within one outer transaction, exceeding the collateral seizure that a single, correctly-ordered liquidation of that debt amount would allow. This is analogous to the C4 VTVL finding's core defect — a state-mutating external call (`safeTransfer`/token `transfer`) occurring before the internal accounting it depends on is updated, letting the caller re-enter and exploit the stale check — except here the "malicious token" role is filled by the caller-chosen `<ft-trait>` implementation, and the harmed party is the borrower/position being liquidated (an unprivileged third party), not the caller themselves.

### Impact Explanation
The borrower whose position is liquidated has more collateral seized (and/or has the same debt slice used to justify multiple penalty-bearing seizures) than the single, correctly-computed liquidation of `debt-amount` would produce. This is a seizure exceeding its intended bound at the expense of an unprivileged borrower — a form of direct theft of user funds (collateral) at rest, since the excess collateral is transferred out to the liquidator/`collateral-receiver` beyond what the liquidation logic and liquidation-penalty caps intend.

### Likelihood Explanation
Exploitation requires the attacker to supply their own contract as the `debt-ft` (or `collateral-ft`) trait argument, which `liquidate` freely accepts as long as `contract-of` resolves to a registered asset address matching an enabled asset in `get-asset` [7](#0-6) . If asset registration strictly binds `debt-address`/`coll-address` to one fixed, non-reentrant token principal per asset ID (as appears to be the intent given the registry design), the attacker cannot substitute an arbitrary reentrant contract for those specific assets, which would sharply limit or eliminate practical exploitability. I was not able to fully verify from the available context whether `get-asset` enforces a strict one-to-one mapping preventing any attacker-supplied contract from masquerading as a legitimate `debt-ft`/`collateral-ft`, nor whether the registered token contracts themselves (e.g., `sbtc`, `usdc`) contain any callback/hook surface reachable during `transfer`. Based on the token contracts I could inspect (e.g., `sbtc.clar`), transfers are simple `ft-transfer?` calls with no callback hooks, which would make classic reentrancy unreachable through those specific assets. Likelihood therefore hinges on registry/asset-trait enforcement details not fully confirmed in the indexed code.

### Recommendation
- Update all borrower/position state (`debt-remove-scaled`, `collateral-remove`) before performing the external token transfer in `vault-system-repay`/`liquidate`, following strict checks-effects-interactions ordering.
- Add a reentrancy guard (mirroring the `in-flashloan` pattern already used elsewhere) around `liquidate`/`liquidate-multi`/`liquidate-redeem` to prevent nested re-entry into liquidation logic for the same borrower within one transaction.
- Verify that `get-asset`/asset registry strictly pins each `aid` to one canonical, audited token contract, and reject `liquidate` calls where the supplied `<ft-trait>` principal does not exactly match that pinned contract.

### Proof of Concept
1. Liquidator identifies a liquidatable `borrower` position with debt asset `debt-aid`.
2. Liquidator deploys/uses a malicious contract `EvilToken` that implements the `ft-trait` and, inside its `transfer` function, calls back into `market.liquidate` for the same `borrower` before returning.
3. Liquidator calls `liquidate(borrower, collateral-ft, EvilToken, debt-amount, min-collateral-expected, none, none)`.
4. Execution reaches `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` [5](#0-4) , which calls `EvilToken`'s `transfer`.
5. Inside that callback, `EvilToken` re-enters `liquidate(borrower, ...)`. Because `debt-remove-scaled`/`collateral-remove` from step 3 have not yet executed, `get-full-position`/`get-liquidation-position` for `borrower` still show the pre-liquidation debt/collateral, so the health check and liquidation-amount math run again on the same (stale) figures.
6. The re-entrant call completes its own `debt-remove-scaled`/`collateral-remove`, seizing collateral a second time; control returns to the outer call, which then also completes its own `debt-remove-scaled`/`collateral-remove` [6](#0-5) , seizing collateral again for effectively the same debt reduction.
7. Net effect: the borrower's collateral is seized more than once for what should be a single bounded liquidation of `debt-amount`.

Note: This PoC's practical feasibility depends on whether the asset registry (`get-asset`) permits an attacker-chosen contract to be accepted as `debt-ft` for a real, enabled debt asset — a detail not fully confirmed from the indexed code, and which the recommendation above targets directly.
