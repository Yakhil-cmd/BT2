### Title
Address chash equivalence allows multiple case-variant string representations of the same address, bypassing case-sensitive uniqueness/order checks in payment/output validation - ([File: validation.js])

### Summary
CVE-2019-9855 is a "path equivalence" bug: a filename could be represented in multiple textual forms (canonical vs. Windows 8.3 short name) that resolve to the same file, letting an attacker bypass a security check that only looked at one textual form. `ocore` has a structurally identical equivalence problem in its address-checksum (chash) validation: `chash.isChashValid()` and `isValidAddressAnyCase()` decode base32 without enforcing canonical case, so a single 32-byte chash/address can be represented by multiple distinct strings (case variants), while all other logic (sorting, `indexOf` de-duplication, `===` comparisons) treats addresses as opaque, case-sensitive strings.

### Finding Description
`chash.js` computes the canonical address string with `base32.encode(chash).toString()` [1](#0-0)  — the canonical/output form is uppercase. However, validation of a *supplied* string only checks that decoding succeeds and the embedded checksum matches; it does not require the exact canonical case: [2](#0-1) 

`validation_utils.js` exposes two validators built on this: the strict `isValidAddress` requires the regex `/^[A-Z2-7]{32}$/` (canonical, uppercase-only) in addition to `isValidChash`, while `isValidAddressAnyCase` only requires `isValidChash`, with no case restriction at all: [3](#0-2) 

`validation.js`'s `validatePaymentInputsAndOutputs` explicitly chooses between these two functions based on `last_ball_mci`: [4](#0-3) 

For units whose `last_ball_mci` is below `constants.timestampUpgradeMci`, `isValidAddressWithCase` resolves to `isValidAddressAnyCase`, meaning a lower-case (or mixed-case) string that decodes to the same chash as an existing uppercase address is accepted as a *valid* address string for a payment output — but it is a *different* string. The output-address ordering/uniqueness logic in the very same function works purely on string comparison and does not canonicalize case before comparing: [5](#0-4) 

The same case-sensitive/opaque-string assumption is used pervasively elsewhere for addresses that participate in ordering or exact-match checks that must guarantee "one authoritative representation per underlying address" — e.g., sorted, non-duplicated author addresses: [6](#0-5) 

and sorted, checksum-validated `earned_headers_commission_recipients` whose shares must sum to 100 and whose addresses must be unique/sorted: [7](#0-6) 

Both of these use the strict `isValidAddress`, so they are not directly reachable with case-variant addresses today. The demonstrably reachable analog is the private/blinded-payment output path in `validatePaymentInputsAndOutputs`, gated purely by the historical `last_ball_mci` threshold rather than being uniformly enforced everywhere `isValidAddressAnyCase` might still be reachable via old/replayable logic paths (`bAA`-triggered replays, catchup of historical units, or any code path that constructs `objValidationState.last_ball_mci` from attacker-influenced/legacy state). This is exactly the CVE-2019-9855 bug class: a security-relevant identity check (chash/address) accepts multiple non-canonical textual encodings of one underlying value, and downstream logic that assumes a single canonical string representation (sorting, uniqueness, output aggregation) can be confused by supplying an alternate-case "pseudonym" of an address.

### Impact Explanation
If an alternate-case string for a valid chash can be pushed through `isValidAddressWithCase` for units still evaluated under the legacy (`isValidAddressAnyCase`) branch, an attacker could craft payment outputs whose `address` field is a differently-cased pseudonym of a legitimate address. Since output aggregation/sorting checks (`prev_address`, `arrOutputAddresses.indexOf`) work on raw string equality, two payload outputs that are semantically "the same address" in two different cases would not be recognized as duplicates/violate the required sort order, and the case-varied output would not be recognized as belonging to the real owner by any code that queries balances/outputs by the canonical uppercase address string. Depending on where downstream code (wallet balance readers, AA state, commission distribution) performs case-sensitive lookups, this can lead to: (a) funds becoming permanently unspendable/frozen (sent to a chash-valid but non-canonical string nobody's wallet is watching), or (b) validation-order bypass allowing multiple outputs to what should be treated as a single recipient to slip past "sorted, no duplicate address" invariants relied upon elsewhere in the codebase for consensus determinism. Because different nodes could, in principle, treat case differently in edge/legacy code paths, this also creates a node-disagreement-on-validity risk for units near the `timestampUpgradeMci` boundary.

### Likelihood Explanation
The strict `isValidAddress` (canonical uppercase only) is applied almost everywhere addresses are validated in current code, and the only found location that still branches to the lenient `isValidAddressAnyCase` is explicitly protected by an MCI upgrade gate (`constants.timestampUpgradeMci`), i.e., it is intended to be legacy-only behavior for units already stabilized before the upgrade activated. I was not able to fully verify, within the available index, whether the gate is unreachable for any new unit an attacker can post today, or whether other legacy compatibility paths (e.g., proof-serving for light clients, historical replays, or older stored `objValidationState.last_ball_mci` values in specific chain states) could still route a newly-crafted unit through the lenient branch. This uncertainty should be treated as a concrete engineering task: confirm whether `timestampUpgradeMci` has been activated on all live networks and whether any live consensus path can still compute a `last_ball_mci` below that threshold for a unit an attacker fully controls.

### Recommendation
- Audit every remaining call site of `isValidAddressAnyCase` (and any other case-insensitive chash check) to confirm none are reachable by a newly attacker-posted unit under current/live MCI values; if any are reachable, remove the legacy branch or gate it strictly server-side rather than trusting unit-embedded MCI-derived state.
- Canonicalize address strings (e.g., force-uppercase) before any string-equality, sort, or `indexOf`-based de-duplication logic, rather than relying on callers to have already validated canonical case.
- Add explicit regression tests that submit chash-valid but non-canonical-case address strings through `validatePaymentInputsAndOutputs`, author sorting, and commission-recipient sorting to confirm they are rejected uniformly regardless of `last_ball_mci`.

### Proof of Concept
Conceptual PoC (not fully verified against live MCI gating, see Likelihood):
1. Take a valid address `ADDR` (32 chars, `[A-Z2-7]{32}`, valid chash).
2. Compute `lower(ADDR)` — since `chash.isChashValid` decodes base32 without enforcing case, `isValidAddressAnyCase(lower(ADDR))` returns `true` even though `isValidAddress(lower(ADDR))` returns `false`.
3. Craft a private-payment unit whose `last_ball_mci` places it on the legacy side of `constants.timestampUpgradeMci` (or find any other reachable path still using `isValidAddressAnyCase`), with a payment output `{address: lower(ADDR), blinding: ..., amount: ...}`.
4. Submit the unit; `validatePaymentInputsAndOutputs` accepts `lower(ADDR)` as valid, but any wallet/query logic that looks up outputs by the canonical uppercase `ADDR` string will not find/credit this output, effectively freezing/misdirecting funds — or, if a second output uses the canonical-case `ADDR`, the "outputs must be sorted / no duplicate address+amount" invariant can be bypassed since the two strings differ.
