### Title
Stack-scoped ApiClient tokens bypass their stack restriction on the CCMenu API endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to resolve the target stack via `Stack.from_param!(params[:stack_id])` instead of using the stack-scoping helper (`stacks.from_param!`) inherited from `Shipit::Api::BaseController`. This breaks the binding between "the stack a token authorizes" (`ApiClient#stack_id`) and "the stack the request actually touches" (`params[:stack_id]`), letting a stack-scoped token read CI/build state for any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` implements stack scoping centrally: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a specific stack (`stack_id` present), and `stack` resolves `params[:stack_id]` only within that restricted relation.

`Shipit::Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 
It resolves `params[:stack_id]` against the unscoped `Stack` model (`Stack.from_param!`), and its `authenticate_api_client` override only changes how the token is read (from `params[:token]` instead of the `Authorization` header) — it does not restore the stack-scope check that `BaseController#stack` normally provides.

The only authorization gate that remains is `require_permission :read, :stack`, which is enforced via `ApiClient#check_permissions!`: [3](#0-2) 
This only checks whether the string `"read:stack"` is present in `permissions` — it says nothing about *which* stack. The actual per-stack restriction lives exclusively in `BaseController#stacks`/`#stack`, which `CCMenuController` bypasses.

Before vs after the trust boundary:
- Intended binding: `ApiClient.stack_id == requested Stack.id` (enforced in every other API controller through `stacks.from_param!`).
- Actual binding in `CCMenuController`: `ApiClient.permissions.include?("read:stack")` (any stack), with `requested Stack.id` taken unchecked from client-supplied `params[:stack_id]`.

This is a direct analog to the CLOB report's class of bug: a value that is checked/authorized under one scope (lot-size-rounded amount / here, the client's `stack_id`) is not what is actually acted upon (raw unmatched amount / here, an arbitrary attacker-supplied `stack_id`), because the enforcement point (`FOKOrderNotFilled` check / here, stack scoping) was implemented inconsistently between code paths.

### Impact Explanation
An `ApiClient` token deliberately scoped to a single stack (e.g. via `Stack#api_clients` or the `here_come_the_walrus` fixture pattern shown in the tests, `stack: shipit`) is meant to only read/write that one stack's data. Via `CCMenuController#show`, that token can instead read the CI/build status, last deploy id, running/failure state, and other CCMenu-exposed metadata (`app/views/shipit/ccmenu/project`) of **any** stack in the Shipit installation by simply substituting `params[:stack_id]`. This is an unauthenticated-for-that-resource read of stack state/deploy output across a repository-authorization boundary that the rest of the API deliberately enforces — matching the "High" impact class: "escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
No special privilege is required beyond possessing any valid stack-scoped `ApiClient` token with `read:stack` permission (a routine, low-privilege credential meant to be scoped to one stack, e.g. issued via `CCMenuUrlController` itself, which creates such tokens: `app/controllers/shipit/ccmenu_url_controller.rb` lines 15-18). The attacker only needs to change the `stack_id` route/query parameter — no signature, secret, or additional credential is needed, and the flaw is triggered on every request to this controller, making it consistently and trivially reachable.

### Recommendation
Make `CCMenuController#stack` honor the inherited scoping instead of querying the global `Stack` model directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the `stacks` scoping defined in `BaseController` (`app/controllers/shipit/api/base_controller.rb:74-80`), ensuring `ApiClient#stack_id`-scoped tokens cannot resolve stacks outside their authorized scope.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to Stack A, with `permissions` including `read:stack` (e.g., as `CCMenuUrlController#client` does for any `current_user`, tied to a specific `stack_id`).
2. Send `GET /api/stacks/:stack_id_of_stack_B/ccmenu.xml?token=<stack_A_token>` where `stack_id_of_stack_B` is any other stack's identifier.
3. `authenticate_api_client` succeeds because the token is valid (`ApiClient.authenticate`), and `require_permission :read, :stack` passes because the token has `read:stack` in its permission list.
4. `stack` resolves via `Stack.from_param!(params[:stack_id])` — unscoped — returning Stack B, not Stack A.
5. The response renders Stack B's CI/build/deploy status, even though the token was only meant to authorize access to Stack A, confirmed by contrast with `BaseController#stack`'s scoping logic that every other `Api::*Controller` relies on (e.g., `test/controllers/api/stacks_controller_test.rb` "an api client scoped to a stack will only see that one stack").
