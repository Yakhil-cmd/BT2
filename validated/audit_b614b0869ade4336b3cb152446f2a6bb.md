### Title
Crash of the whole node (DoS) via oversized SQL built from AA `attestation()` `attestors` string - ([File: formula/evaluation.js])

### Summary
The oscript/AA formula function `attestation()` builds the `attestor_address IN(...)` clause by manually string-concatenating an attacker-influenced list of addresses instead of using a bound parameter, and the underlying SQLite driver wrapper crashes the entire process on any query error. This mirrors the CVE-2021-35607 bug class: a DML statement built from attacker-influenced input that can crash/hang the server.

### Finding Description
`attestation()` in the formula evaluator derives `arrAttestorAddresses` by splitting the `attestors` parameter string on `:`, validating only that every resulting token is a syntactically valid address: [1](#0-0) 

It then embeds every element directly into the SQL text via `conn.escape` and string concatenation (not as a single bound array parameter), twice — once for the "unstable AA units" lookup and once for the "stable units" lookup: [2](#0-1) 

Because the `attestors` value is evaluated from an arbitrary formula expression (`evaluate(params[param_name].value, ...)`), an AA author can wire it to trigger-supplied data (e.g. `trigger.data.attestors`), meaning an unprivileged trigger sender fully controls the string content and length. There is no upper bound enforced on the number of `:`-separated addresses (only per-address format validation), so a trigger sender can supply a string containing an extremely large number of valid-looking addresses, producing a SQL statement of unbounded size.

When the resulting SQL exceeds SQLite's internal limits (e.g. `SQLITE_MAX_SQL_LENGTH`/too many terms in compound statement) or otherwise errors, the driver wrapper in `sqlite_pool.js` does not handle the error gracefully — it synchronously `throw`s, which is not caught anywhere in the call chain (AA execution during MCI stabilization), crashing the node process: [3](#0-2) 

Because AA trigger execution happens deterministically for every full node processing that unit during stabilization (`handleAATriggers` / `markMcIndexStable` in `main_chain.js`), a single such trigger unit reaching consensus stabilization will be evaluated — and crash — on every full node in the network simultaneously, not just the sender's own node.

### Impact Explanation
This is a network-wide, unauthenticated availability attack: any trigger sender interacting with an AA that forwards trigger data into `attestation({attestors: ...})` can craft a single unit whose AA response evaluation deterministically crashes every full node that processes and stabilizes that unit. This satisfies the "network unable to confirm new units" bar — a synchronized crash of full nodes during MC stabilization halts progress until nodes are manually restarted/patched, directly analogous to the MySQL DML crash/hang described in CVE-2021-35607.

### Likelihood Explanation
Exploitation requires an existing (or attacker-deployed) AA that passes trigger-controlled data into the `attestors` parameter of `attestation()` — a plausible and unremarkable oscript pattern (e.g., delegated/oracle-configurable attestor lists). Once such an AA exists, any address can send a trigger with a sufficiently long `data.attestors` string; no special privilege, key compromise, or hub/peer position is needed — only the ability to post a unit that triggers the AA, which is within the threat model (AA trigger sender is explicitly in-scope).

### Recommendation
- Bind `arrAttestorAddresses` as a single array-typed query parameter (`attestor_address IN(?)`) instead of manually concatenating `conn.escape` results, letting the driver's placeholder-expansion logic manage size instead of building a raw SQL string.
- Enforce a hard cap on the number of attestor addresses accepted by `attestation()` (and any other formula function performing similar address-list SQL construction) before evaluation reaches the SQL layer.
- Wrap/guard `sqlite_pool.js` query error handling so a query error (oversized statement, syntax error, etc.) returns a controlled error to the caller / marks the AA response as bounced, instead of throwing synchronously and crashing the whole process.

### Proof of Concept
1. Deploy (or use an existing) AA whose bytecode includes something like:
   `attestation({attestors: trigger.data.attestors, address: trigger.data.address})`
2. As an ordinary user, send a trigger unit to that AA with `data.attestors` set to a string of tens of thousands of colon-separated, syntactically valid Obyte addresses (cheap to generate offline, since only format/checksum validity is required, not real ownership).
3. When the unit's MCI becomes stable, `handleAATriggers` invokes the AA, which evaluates `attestation()`, builds the oversized `IN(...)` SQL string in `formula/evaluation.js` lines 966-992, and the query fails/overflows in the SQLite driver.
4. `sqlite_pool.js`'s query callback (`formula/evaluation.js` lines 111-116 area) `throw`s the error synchronously, crashing the node process on every full node that stabilizes this MCI — producing a synchronized network-wide crash.
