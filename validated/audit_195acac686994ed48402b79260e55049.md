Confirmed: `callback` in `app/controllers/shipit/github_authentication_controller.rb` sets `session[:user_id]` and `session[:authenticated]` directly after a successful OmniAuth GitHub round-trip, without ever calling `reset_session`. `reset_session` is only invoked from `logout` and from `force_github_authentication` when a stale token is detected. This is a session-fixation pattern: whatever session identifier existed before the OAuth callback (including one an attacker could have planted, e.g. via a session-store cookie set before the user authenticates) remains valid and becomes privileged the moment `session[:user_id]` is written to it.

### Title
Session Fixation on GitHub OAuth Login - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
The Wormhole report describes a trust binding (the address the contract calls) that was set incorrectly/left unmigrated between environments, silently breaking authorization. The reachable analog in this engine is a trust-binding break between "the session identifier that existed before login" and "the `User` bound to the session after login": `GithubAuthenticationController#callback` assigns `session[:user_id]` without rotating the session, so a pre-existing (potentially attacker-supplied) session becomes authenticated as the victim.

### Finding Description
`GithubAuthenticationController#callback` [1](#0-0)  performs:
```
session[:user_id] = sign_in_github(auth)
session[:authenticated] = true
redirect_to(return_url)
```
No `reset_session` call precedes this write. Compare with `logout`, which does call `reset_session` [2](#0-1) , and with `Authentication#force_github_authentication`, which only resets the session on a stale/legacy-token condition, not on every successful login [3](#0-2) . `current_user` is derived purely from `session[:user_id]` [4](#0-3) .

Before vs after the login request:
- Before: `session[<sid>]` → anonymous/unauthenticated (or attacker-controlled placeholder).
- After: `session[<sid>]` → `{user_id: victim.id, authenticated: true}`, same `<sid>`.

The binding that should hold — "session identifier issued before authentication" ≠ "session identifier trusted after authentication" — is violated: the identifier is reused unchanged.

### Impact Explanation
If the host application's session store allows a session identifier to be fixed in the victim's browser prior to login (a supported, non-exotic scenario for server-side session stores, e.g. `ActiveRecord::SessionStore`/Redis-backed session stores, or any subdomain/network position allowing a `Set-Cookie` for the session cookie name before the login flow), an attacker who knows/fixes that identifier gains full authenticated access as the victim once the victim completes the GitHub OAuth flow — including access to `api_clients`, deploys, rollbacks, and merges gated behind `current_user`. This maps to the explicitly allowed High-impact class: "session fixation / forced OAuth completion."

### Likelihood Explanation
Requires the attacker to plant/know a session identifier and get the victim to complete the OAuth login while using it — a known, practical attack pattern against applications lacking session-ID rotation on login, independent of any credential the attacker themselves would need to possess. No `ApiClient` token, GitHub App secret, or existing privileged account is required by the attacker.

### Recommendation
Call `reset_session` immediately before assigning `session[:user_id]`/`session[:authenticated]` in `GithubAuthenticationController#callback`, so a fresh session identifier is issued on every successful authentication, mirroring the existing `logout` behavior.

### Proof of Concept
1. Attacker obtains/fixes a session identifier `S` for the victim's browser (e.g., by planting a `Set-Cookie` for the session cookie name via any mechanism the host's session-store configuration permits before authentication).
2. Victim, using session `S`, completes the GitHub OAuth flow at `/github/auth/github/callback`.
3. `callback` sets `session[:user_id] = victim.id` on session `S` without rotating it [5](#0-4) .
4. Attacker, still holding session identifier `S`, is now recognized as the authenticated victim by `current_user` [4](#0-3)  and can create `ApiClient`s, trigger deploys, or approve merges as the victim.

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end

        end
      else

      end
    end
