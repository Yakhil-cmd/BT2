### Title
CCMenu API leaks stack existence across the entire Stack table via unscoped `stack` resolution - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` overrides the base class's scoped `stack` resolution with `Stack.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id` restriction entirely, and combined with `NoDeploy#id` returning `0` for deploy-less stacks, a holder of any single valid CCMenu token can enumerate the existence of arbitrary stacks by observing 200-vs-404 responses.

### Finding Description
The broken binding: information disclosed should satisfy `stacks_readable_by_token ⊆ {stack | stack.id == current_api_client.stack_id}` (or `Stack.all` only for unscoped clients), but the actual code path makes `stacks_readable_by_token == Stack.all` for every CCMenu token regardless of scoping.

`Shipit::Api::BaseController` defines a scoped accessor: [1](#0-0) 
which restricts lookups to `current_api_client.stack_id` when the token is stack-scoped. However, `CCMenuController` redefines `stack` without using this scope: [2](#0-1) 
This directly calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model, so the `current_api_client.stack_id` restriction that the rest of the API enforces is never applied here.

Combined with: [3](#0-2) 
a request to `GET /api/stacks/:stack_id/ccmenu?token=...` for an **existing** stack (even with zero deploys) returns `200 OK` with `NoDeploy.new` (`id` 0, `lastBuildStatus` "Success"), confirmed by the existing test: [4](#0-3) 
while a request for a **nonexistent** `stack_id` raises `ActiveRecord::RecordNotFound` from `from_param!`, producing a `404`.

Attacker flow: the `CCMenuUrlController#client` creates a CCMenu `ApiClient` scoped only by `permissions: %w[read:stack]`, with no `stack_id` set: [5](#0-4) 
Any user who legitimately obtains one CCMenu token this way (or any leaked/shared CCMenu token) can call `GET /api/stacks/*any_owner/any_repo/any_env/ccmenu?token=<their_token>` for arbitrary `stack_id` values and distinguish "exists, no deploys" (200, `lastBuildStatus=Success`) from "does not exist" (404), fingerprinting every `owner/repo/environment` combination on the instance — including private repositories the attacker has no access to.

Why guards fail: `require_permission :read, :stack` only checks that the token has the `read:stack` permission bit, not which stack it's scoped to; the actual scope check exists only in `BaseController#stack`/`#stacks`, which this controller does not use. No `verify_signature`, `force_github_authentication`, or model validation intervenes because this is a same-engine authorization scoping bug, not an authentication bug.

### Impact Explanation
Any valid CCMenu token (read:stack scoped or not) can be used to enumerate the existence of every `Stack` record in the instance — an unauthenticated (relative to the target stack) disclosure of stack existence, name, activity, and lock status for repositories/environments the token was never authorized for. This matches the High-severity category "unauthenticated read of stack state... for repositories/environments the client is not authorized for," since scoped tokens (intended to be limited to one stack) instead read state for any stack. It is fully repeatable — every request with a distinct `stack_id` param yields another oracle result, allowing systematic enumeration across all tenants sharing the instance.

### Likelihood Explanation
Preconditions are minimal: attacker only needs one legitimately obtained (or leaked) CCMenu token for any single stack — no elevated privileges, no `api_clients_secret`, and no GitHub secrets are required. The `stack_id` values (`owner/name/environment`) are often guessable/known (public repo names), making enumeration cheap and reliable. This is a straightforward, no-cost, and fully repeatable attack once one token is held.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to use the inherited scoped resolver instead of the raw model:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the local override entirely (relying on `BaseController#stack`) is the simplest fix, ensuring `current_api_client.stack_id` scoping is enforced consistently with every other API controller.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped token cannot read ccmenu status for a different stack" do
  scoped_client = ApiClient.create!(
    creator: @user, name: 'scoped', permissions: %w[read:stack], stack: @stack
  )
  other_stack = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

  get :show, params: { stack_id: other_stack.to_param, token: scoped_client.authentication_token }

  # Binding under test: stacks readable by a stack-scoped token should equal {@stack},
  # so other_stack must NOT be readable -> expect 404/forbidden, not 200.
  assert_response :not_found # currently fails: actual response is 200 OK with lastBuildStatus=Success
end

test "an unscoped token can distinguish existing-empty stack from nonexistent stack id" do
  existing_empty = Stack.create!(repository: Repository.new(owner: "foo", name: "baz"), branch: 'main')

  get :show, params: { stack_id: existing_empty.to_param, token: @client.authentication_token }
  existing_status = response.status

  get :show, params: { stack_id: "nope/nope/production", token: @client.authentication_token }
  nonexistent_status = response.status

  assert_equal 200, existing_status
  assert_equal 404, nonexistent_status
  refute_equal existing_status, nonexistent_status # existence oracle confirmed
end
```
