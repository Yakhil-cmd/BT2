### Title
Webhook signature verification key selection is not bound to the payload's actual repository/organization, allowing forged `membership` events to grant unauthorized `Shipit.github_teams` access - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` derives *which* GitHub App configuration (and therefore *which* `webhook_secret`) to validate a delivery against purely from an attacker-controlled JSON field (`repository.owner.login` / `organization.login`), and then hands the *entire* raw, parsed payload to the event handler unchanged. Nothing binds the organization whose secret validated the delivery to the organization/team that the handler subsequently mutates. Combined with the fact that `webhook_secret` is documented as optional and `GithubApp#verify_webhook_signature` returns `true` unconditionally when no secret is configured, an attacker who can get *any* payload accepted (e.g., because one configured org has no secret, mirroring the multi-org example in `docs/setup.md`) can submit a forged `membership` webhook that creates a `Team`/`Membership` mapping an arbitrary GitHub login (their own) into any `Shipit.github_teams` entry, bypassing the app's authorization check entirely.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes the “authorizing” organization straight from the untrusted body: [1](#0-0) [2](#0-1) 

The selected `GithubApp` instance's `verify_webhook_signature` is used only to authenticate that *some* known org's secret matches the raw body: [3](#0-2) 

Critically, `return true unless webhook_secret` means verification is a no-op for any org configured *without* a secret — and `webhook_secret` is presented throughout the documentation and templates as optional (`webhook_secret: # nil`), including in the natively-supported multi-org configuration: [4](#0-3) [5](#0-4) 

Once `verify_signature` "passes" (either because it is genuinely signed by an org with a secret, or trivially because the selected org has none), `WebhooksController#create` dispatches the entire payload — including fields never cross-checked against `repository_owner` — to the registered handler: [6](#0-5) 

The `membership` handler trusts the `organization.login`, `team`, and `member.login` fields of that same payload to create/update a `Team` and add a `User` (looked up or *created* by GitHub login) as a member: [7](#0-6) 

That `Team` is the exact model checked during authorization: [8](#0-7) [9](#0-8) 

**Broken binding (equality that should hold but doesn't):**
`organization/repository whose secret authenticated the delivery` ≠ `organization/team/member the handler is permitted to mutate`.

Before the attacker's request: signature verification is scoped per-org via `Shipit.github(organization: repository_owner)`, implicitly assumed to also scope *what the payload is allowed to claim*.
After the attacker's request: the handler blindly trusts `params.team`, `params.organization.login`, and `params.member.login` — none of which were checked to belong to the org that was actually used to validate the signature (or, in the no-secret case, were checked at all).

### Impact Explanation
This directly maps to the report's bug class ("value acted upon does not correspond to the value that was actually verified/authorized"): here, the *identity binding* (which org authorizes writing this membership record) is never enforced — only the raw byte signature (or nothing, if no secret) is checked, independent of which team/org/user the payload claims to describe.

Impact reaches the explicitly listed High-severity criterion: **escalation into `Shipit.github_teams` authorization**. A forged `membership` `added` event creates a `Membership` row associating an arbitrary attacker-chosen GitHub login with any `Team`/`github_id` the attacker names in the payload; `Team#organization`/`slug` become attacker-controlled strings that can collide with, or be crafted to match, an org/team listed in `Shipit.github_teams`. When that attacker's real GitHub account subsequently completes the normal OAuth login flow, `User#authorized?` finds the forged `Membership` and grants full application access, and `find_or_create_by_login!` even auto-vivifies a `User` row for the attacker's login via the GitHub API if it does not exist yet.

### Likelihood Explanation
Likelihood depends on deployment specifics I could not fully verify from the index:
- It requires the `/webhooks` endpoint to accept a delivery whose selected org key (`repository_owner`) resolves to a configured GitHub App entry with no `webhook_secret` set, or otherwise requires possession of a valid `webhook_secret` for at least one configured org. Multi-org configuration and unset `webhook_secret` are both documented/first-class options in this engine (`docs/setup.md`, `config/secrets.development.example.yml`), so this is not a "misuse" scenario outside the documented deployment model, but I could not confirm from the index whether Shipit's own recommended production template enforces a non-blank secret.
- Given the rules exclude findings that depend on possessing a `webhook_secret`, the concretely reachable unprivileged path is the "no secret configured for at least one org" case, which is an explicit, documented configuration knob rather than a misconfiguration outside the engine's control — I flag this as the key point of uncertainty for triage.

### Recommendation
Cross-validate that `repository.owner.login` (or `organization.login`) used to select the verifying `GithubApp`/secret is the *same* organization the payload's business object (`team.organization`, `membership.organization`, `repository.full_name` owner, etc.) claims to mutate before invoking any handler. Additionally, make `webhook_secret` mandatory (fail closed) rather than allowing `verify_webhook_signature` to return `true` when unset, and reject `membership` events whose `organization.login` does not match a `Shipit.github_teams` entry's configured organization prior to creating/updating `Team`/`Membership` records.

### Proof of Concept
1. Deploy Shipit with two configured GitHub Apps (multi-org mode, as documented in `docs/setup.md`): `OrgKnown` (no `webhook_secret` configured — a supported, documented option) and `OrgTarget` (the org actually referenced by `Shipit.github_teams`).
2. As an anonymous, unauthenticated attacker, `POST /webhooks` directly (no GitHub involved) with:
   - Header `X-Github-Event: membership`
   - Body:
     ```json
     {
       "action": "added",
       "team": { "id": 999, "name": "Developers", "slug": "developers", "url": "https://example.com" },
       "organization": { "login": "OrgKnown" },
       "member": { "login": "attacker-github-login" }
     }
     ```
   No `X-Hub-Signature` header is required to matter, because `repository_owner` resolves via `params.dig('organization','login')` → `OrgKnown`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. `MembershipHandler#process` creates `Team.find_or_create_by!(github_id: 999)` with `organization: "OrgKnown"` and adds `User.find_or_create_by_login!("attacker-github-login")` as a member.
4. If `Shipit.github_teams` is configured to include a team whose `github_id`/slug the attacker can also predict/target (or if the attacker iterates ids to match any existing tracked team), the attacker's real GitHub account, after a normal OAuth login, is now recognized as authorized by `User#authorized?` (`app/models/shipit/user.rb:80-82`), granting full application access without ever needing credentials for `OrgTarget` or the real webhook secret.

*Note: I was not able to fully confirm within the indexed code whether `Shipit.github_teams` matching is keyed by `github_id` alone or requires additional fields, nor whether the engine's official production templates forbid blank `webhook_secret`; a Devin session with full repository access would be needed to verify these remaining details precisely.*

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```
