## Confirmation

Important scope-limiting fact I confirmed: `assocUnstableMessages[unit]` only gets an entry when the unit contains a message with `app` in `['data_feed', 'definition', 'system_vote', 'system_vote_count']` [1](#0-0)  — not for every unstable unit on the DAG. This significantly narrows (but does not eliminate) the attack surface described in the report, since an attacker must post many `data_feed`/`definition`/`system_vote` messages that remain unstable, rather than any arbitrary unit.

### Title
Unbounded iteration over `storage.assocUnstableMessages` in `dataFeedExists`/`readDataFeedValue` allows AA-formula execution cost to grow with attacker-controlled unstable data-feed/definition/vote message count - (File: data_feeds.js)

### Summary
`dataFeedExists()` and `readDataFeedValue()` in `data_feeds.js`, when invoked in AA context (`bAA` true, which is always the case for the `data_feed`/`in_data_feed` oscript operators evaluated during AA trigger processing), perform a `for (var unit in storage.assocUnstableMessages)` loop over the *entire* global in-memory map of not-yet-stable messages before doing any relevance filtering [2](#0-1) [3](#0-2) . This map is populated, one entry per unit, whenever a unit carries a `data_feed`, `definition`, `system_vote`, or `system_vote_count` message [1](#0-0) , and entries are only removed once that unit's MCI stabilizes [4](#0-3) . This is structurally analogous to the `coolersFor` mapping in the reported Factory.sol bug: a data structure that only grows as a side effect of ordinary, permissionless user actions (posting messages), with no cap, that is later iterated in full by a hot code path.

### Finding Description
Any user can post units containing `data_feed` (or `definition`/`system_vote`) messages — this requires no special privilege beyond being able to post any unit. Each such unit, while unstable, adds one key to the global `storage.assocUnstableMessages` object [1](#0-0) .

Whenever *any* AA on the network evaluates an oscript formula using `data_feed[...]` or `in_data_feed[...]` with "unstable" oracle lookups, `evaluation.js` calls into `dataFeeds.readDataFeedValue(...)` / `dataFeeds.dataFeedExists(...)` with `bAA` (an AA-context flag) set [5](#0-4) [6](#0-5) . Inside these functions, before any address/feed-name/mci filter is applied, the code unconditionally iterates `for (var unit in storage.assocUnstableMessages)` over *every* unstable unit that has a tracked message anywhere on the network — not just units relevant to the specific oracle addresses or feed name being queried [7](#0-6) [8](#0-7) . The relevance filters (`objUnit.latest_included_mc_index` range check, `_.intersection(arrAddresses, objUnit.author_addresses)`) are applied per-iteration, so the O(n) cost of the scan is paid regardless of how few matches exist.

Because there is no upper bound on how many unstable `data_feed`/`definition`/`system_vote` units can exist simultaneously (bounded only by how fast the DAG stabilizes and by how many such messages users choose to post), an attacker can inflate `storage.assocUnstableMessages` by repeatedly posting cheap `data_feed` messages (posting a data feed message requires no special role — any address can post a `data_feed` app message) faster than they stabilize, or targeting periods/situations where stabilization lags. Every subsequent `data_feed`/`in_data_feed` formula evaluation by *any* AA on the node — not just the attacker's own AA — then pays the cost of scanning the whole inflated map.

### Impact Explanation
This is a network-wide computational-DoS analog to the Factory.sol issue: instead of a Solidity function hitting the block gas limit, ocore full/AA-processing nodes incur increasingly large per-evaluation CPU/time cost for a very common oscript primitive (`data_feed`/`in_data_feed`) used across many AAs (e.g., price oracles, prediction markets). Since every full node must independently execute AA triggers to agree on validity/state, a sufficiently inflated `assocUnstableMessages` map degrades AA-trigger processing throughput for the whole network, risking triggers not completing before required deadlines, slower stabilization/consensus on AA outputs, or nodes falling behind — i.e., a node/network unable to process new AA triggers/units in a timely fashion. This meets the "network unable to confirm new units" / node disagreement risk bar, though the severity is bounded by how fast units stabilize on `ocore`'s DAG and by the cost of posting the qualifying messages, so it is a resource-exhaustion-style degradation rather than an instant hard failure.

### Likelihood Explanation
Likelihood is moderate: reaching the vulnerable code only requires (a) posting ordinary `data_feed` messages (no special role) faster than the DAG stabilizes them, and (b) some AA on the network invoking `data_feed[...]`/`in_data_feed[...]` (a widely-used, ordinary oscript feature, not requiring cooperation with the attacker). The attacker does not need to control the AA being harmed — they merely need to bloat the shared global cache that all such formula evaluations consult. The main mitigating factor is that stabilization continuously prunes the map [4](#0-3) , so sustaining a large map requires sustained spam and/or exploiting periods of slow stabilization.

### Recommendation
- Index `storage.assocUnstableMessages` (or a derived structure) by `(feed_name, address)` / by app type so lookups in `dataFeedExists`/`readDataFeedValue` can filter without a full linear scan of all unstable messages.
- Alternatively, maintain a secondary map keyed by author address (or by feed_name) pointing to the relevant unstable units, populated at the same time as `assocUnstableMessages`, and use it in `data_feeds.js` instead of iterating the full map.
- Consider capping/rate-limiting how many pending (unstable) `data_feed`/`system_vote`/`definition` messages a single address can have outstanding at once, or deprioritizing their relay/inclusion once a threshold is exceeded, to bound worst-case map size.

### Proof of Concept
1. From an unprivileged address, repeatedly compose and broadcast units each containing an `app: "data_feed"` message, at a rate exceeding the network's normal MCI-stabilization pace (or during a period of slow stabilization) — see `writer.js` lines populating `storage.assocUnstableMessages[objUnit.unit]` for every such unit [1](#0-0) .
2. As units accumulate unstable, `Object.keys(storage.assocUnstableMessages).length` grows proportionally to the number of outstanding spam units (confirmed by the log line at initialization time reporting this count, e.g. `initUnstableMessages done, N messages found` [9](#0-8) ).
3. Trigger (or wait for) any AA that evaluates a `data_feed[[...]]` or `in_data_feed[[...]]` formula referencing "unstable" data (this is normal AA behavior, e.g. oracle-consuming AAs) — this calls `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists` with `bAA=true` [5](#0-4) .
4. Observe (e.g., via the function's own timing log `'df took '+(Date.now()-start_time)+'ms'` [10](#0-9) ) that evaluation time scales with the number of spammed unstable units, since the `for (var unit in storage.assocUnstableMessages)` loop [11](#0-10)  is O(size of the map) regardless of relevance to the queried oracle/feed.
