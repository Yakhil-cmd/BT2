### Title
Cross-tenant `pull_request` webhook forgery via mismatched `repository.owner.login` and `repository.full_name` combined with secret-less org bypass in `verify_webhook_signature` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to validate against using `params.dig('repository', 'owner', 'login')`, while the actual repository/stack that handlers mutate (e.g. `LabelCapturingHandler`) is resolved from the independent `params.repository.full_name` field. Because the attacker fully controls the JSON body and these two fields are never checked for consistency, and because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved organization has no `webhook_secret` configured, an attacker can forge a `pull_request` webhook that verifies against a secret-less organization while writing into a completely different organization's repository/stack.

### Finding Description
The invariant that should hold is: `organization_that_verified_signature == organization_that_owns_the_mutated_repository`, i.e. `params.dig('repository','owner','login') == Repository.from_github_repo_name(params.repository.full_name).owner`.

In `Shipit::WebhooksController#verify_signature` [1](#0-0) , the organization used to pick the `GitHubApp` (and thus the `webhook_secret` to verify against) comes from `repository_owner`, defined as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) .

`GitHubApp#verify_webhook_signature` short-circuits to `true` when the resolved org has no configured secret: `return true unless webhook_secret` [3](#0-2) .

Meanwhile, `LabelCapturingHandler#repository` resolves the repository to mutate purely from a *different* JSON field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name` [4](#0-3) , which simply splits the string on `/` with no cross-check against `repository.owner.login` [5](#0-4) . The handler then persists attacker-controlled label names onto that repository's stack's `PullRequest` via `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [6](#0-5) .

Exploit flow: the attacker crafts a `pull_request`/`opened` body where `repository.owner.login = "org-with-no-secret"` (any org configured in this Shipit instance's `Shipit.github` registry without a `webhook_secret`) and `repository.full_name = "victim-org/victim-repo"` (an arbitrary target repository, potentially belonging to an org that *does* have a secret). `verify_signature` looks up `Shipit.github(organization: "org-with-no-secret")`, finds no secret, and returns `true` unconditionally regardless of the supplied `X-Hub-Signature` value — the attacker never needs to know any real secret. The request passes `verify_signature` and is dispatched to `LabelCapturingHandler`, which resolves the repository/stack from `full_name` ("victim-org/victim-repo") and writes labels into that stack's `PullRequest`, independent of which org's secret (or lack thereof) authenticated the request.

Existing guards do not catch this: `drop_unhandled_event` only checks the event name; the `ExplicitParameters` schema (`params do ... end`) only validates types/presence, not cross-field consistency between `repository.owner.login` and `repository.full_name`; and no model validation in `Repository`, `Stack`, or `ReviewStackAdapter` re-derives or checks the owner against the verified organization.

### Impact Explanation
An attacker can make Shipit write attacker-chosen `labels` (which become uppercased environment variable keys via `ReviewStack#env`) onto the `PullRequest` record of any repository/stack tracked by the Shipit instance, as long as some other organization registered in the instance's GitHub App configuration has no `webhook_secret` set. This is a cross-tenant integrity violation: a payload that authenticates as belonging to org A ends up mutating org B's stack state. This matches the "payload for one repository mutating another's stack/commit/task" Critical impact category. The attack is repeatable against any repository/stack as long as the attacker knows (or can enumerate) one secret-less organization configured on the instance, and any full_name of a target repo/stack.

### Likelihood Explanation
Preconditions: the Shipit instance must have at least one organization configured without a `webhook_secret` in `Shipit.github` (a plausible real-world misconfiguration, e.g. for internal/low-risk orgs) — the attacker only needs to know or guess that org's login, not any secret. No authentication, session, API token, or webhook_secret is required from the attacker. The attacker only crafts an HTTP POST to `/webhooks` with a `X-Github-Event: pull_request` header and a JSON body they fully control. This is straightforward, low-cost, and repeatable against arbitrary target repositories.

### Recommendation
Derive the organization used for signature verification and the organization used for repository resolution from the same, single source of truth, and reject requests where `repository.owner.login` does not match the owner parsed from `repository.full_name`. Additionally, treat organizations without a configured `webhook_secret` as requiring verification failure (or at minimum, restrict/disable webhook processing) rather than defaulting to `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Minitest (`ActionDispatch::IntegrationTest` or `ActionController::TestCase` style, matching existing `test/controllers/webhooks_controller_test.rb` conventions):
1. Configure `Shipit.github(organization: 'secretless-org')` with no `webhook_secret`, and `Shipit.github(organization: 'victim-org')` with a secret set (representing the real owner of the target stack).
2. Create a `victim-org/victim-repo` `Repository`/`ReviewStack`/`PullRequest` fixture.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or an arbitrary bogus `sha1=...` value), and a body where `repository.owner.login == "secretless-org"` but `repository.full_name == "victim-org/victim-repo"`, `action: "opened"`, and `pull_request.labels` containing an attacker-chosen label name.
4. Assert `response.status == 200` (request accepted, not 422).
5. Assert equality check before: `params.dig('repository','owner','login') != Repository.from_github_repo_name(params.dig('repository','full_name')).owner` (i.e., `"secretless-org" != "victim-org"`).
6. Assert that `victim_pull_request.reload.labels` now contains the attacker-supplied label — proving org `secretless-org`'s (non-)verification mutated `victim-org`'s `PullRequest` record.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
