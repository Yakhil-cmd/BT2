### Title
Webhook signature verified against `repository.owner.login`'s organization while the acted-upon repository is taken from the unchecked `repository.full_name` field, enabling cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the `X-Hub-Signature` HMAC against using `repository_owner`, computed solely from `params.dig('repository','owner','login')` (falling back to `organization.login`). Every actual webhook `Handler` (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) instead resolves the target `Stack`/`Repository` from the sibling, independently-controlled field `payload.dig('repository','full_name')`. Because these two fields live in the same attacker-supplied JSON body and are never cross-validated against each other, an entity that can obtain a valid `webhook_secret` for *any* one configured organization (a legitimate use case for Shipit deployments serving multiple GitHub orgs, as shown in `config/secrets.development.shopify.yml`) can forge a signed payload whose `repository.owner.login` matches their own organization (so the HMAC check passes) but whose `repository.full_name` names a stack belonging to a completely different, victim organization.

### Finding Description
The binding that should hold is: *organization whose secret authenticated the payload* == *organization owning the repository the handler writes to*. Since `Shipit.github(organization:)` (`lib/shipit.rb:170-200`) keys webhook secrets per-organization and `Repository#from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) trusts `full_name` verbatim to look up any repository/stack in the entire Shipit instance, the two fields are never forced to agree. `verify_signature` only checks `repository.owner.login` (or `organization.login`) against a configured org's secret; it never confirms that this same login is the owner segment of `repository.full_name`, nor that `full_name`'s owner matches the org whose secret validated the request.

An attacker who administers (or has convinced the Shipit operator to onboard) any one GitHub organization present in `secrets.github` knows that organization's `webhook_secret` (it is chosen at GitHub App creation time by the org owner). They can then POST directly to the shared `/webhooks` endpoint with a manually crafted JSON body and HMAC signature computed with their own org's secret, setting `repository.owner.login` to their own org (to pass `verify_signature`) but `repository.full_name` to `"victim-org/victim-repo"`. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb`) will then locate the victim's `Stack` via `Handler#stacks`/`#repository_name` and invoke `stack.sync_github(expected_head_sha: params.after)`, triggering `GithubSyncJob` against a stack that belongs to an organization the attacker was never authenticated for.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope: an attacker authenticated (via a valid HMAC) as organization A can drive webhook-triggered state changes (sync, forced re-sync with an attacker-chosen `expected_head_sha`, status/check-run updates, or pull-request/merge-related bookkeeping depending on handler) against organization B's stacks, without ever having credentials, GitHub App installation, or Shipit account access to organization B. This is a cross-organization write triggered purely by controlling a valid signature for a different, unrelated tenant.

### Likelihood Explanation
Likelihood is high in any multi-organization Shipit deployment (a documented, supported configuration, e.g. `config/secrets.development.shopify.yml`). Any unprivileged actor who is an admin of just one onboarded organization — including one they set up themselves if self-service onboarding is allowed, or one they compromise — can trivially compute the HMAC for their own org's secret and free-form the rest of the JSON body, since none of the code cross-checks `repository.owner.login` against `repository.full_name`.

### Recommendation
In `WebhooksController#verify_signature`, or in `Shipit::Webhooks::Handlers::Handler`, enforce that the organization used to select/verify the webhook secret is derived from (or validated against) the exact same `repository.full_name`/owner segment that handlers use to resolve the target repository — e.g., verify `repository_owner == repository.full_name.split('/').first` (or normalize `repository_owner` to be parsed from `full_name` rather than the separate `owner.login` object) before dispatching to any handler.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.github`: `attacker-org` (attacker is the GitHub App owner/admin, chose its `webhook_secret`) and `victim-org` (unrelated tenant with stack `victim-org/victim-repo`).
2. Attacker computes `sha1=` HMAC over a crafted JSON body using `attacker-org`'s `webhook_secret`:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. POST this body to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed hmac>`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully since the signature matches `attacker-org`'s secret.
5. `PushHandler#process` resolves `repository_name` = `"victim-org/victim-repo"`, finds the corresponding `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, causing `GithubSyncJob` to run against the victim's stack — a cross-organization action the attacker was never authorized to trigger.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end
