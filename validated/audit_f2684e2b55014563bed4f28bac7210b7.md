## Title
Market-maker AA share/reserve desync at zero-reserve edge enables share dilution and fund extraction - (File: `test/samples/uniswap_like_market_maker.oscript`)

## Summary
The bundled Uniswap-like market-maker AA template tracks LP-style shares in a state variable (`var['mm_asset_outstanding']`) that is meant to represent a claim proportional to the AA's *real* on-chain balances (`balance[$asset]`, `balance[base]`). The "initial deposit" fallback branch re-prices new deposits as if the pool were empty whenever *either* reserve balance is zero, without checking whether outstanding shares are also zero. Because reserves and share supply can become desynchronized (one reserve fully drained while shares and the other reserve remain nonzero), a trigger sender can exploit this branch to mint shares that are disproportionate to the value actually contributed, diluting existing share holders and extracting a disproportionate amount of the remaining reserve — the same class of "internal accounting vs. real pooled balance" mismatch described in the referenced report.

## Finding Description
The relevant logic lives in the "invest in MM" case: [1](#0-0) 

```
{ // invest in MM
    if: `{$mm_asset AND trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0}`,
    init: `{
        $asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
        $bytes_balance = balance[base] - trigger.output[[asset=base]];
        if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
            $issue_amount = balance[base];
            return;
        }
        ...
        $issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
    }`,
```

`$asset_balance` and `$bytes_balance` are computed from the AA's *live* balances via the `balance[]` built-in (read directly from `aa_balances`/on-chain outputs, see `formula/evaluation.js` `readBalance()`), not from any separately tracked deposit ledger: [2](#0-1) 

The bug is that the "initial deposit" special case is triggered whenever **either** reserve is exactly zero, and in that branch the code mints `$issue_amount = balance[base]` (the entire incoming/base balance) as new shares, completely ignoring the current value of `var['mm_asset_outstanding']`. This is only safe if the share supply is also zero at that point. But the two reserves and the share supply are three independently-evolving quantities:
- Reserves are moved by `payment` messages (subject to integer `round()` in both the invest and divest branches, and by the constant-product swap branches).
- `mm_asset_outstanding` is moved by `state` updates in the invest/divest branches.

Because withdrawals pay out `round($investor_share * balance[$asset])` and `round($investor_share * balance[base])` independently for each asset (see divest branch), it is possible — by choosing the divesting share amount and by the accumulated effect of swap fees/rounding — to fully zero out one reserve (e.g. `balance[base]` rounds down to 0 on the last unit of precision) while `balance[$asset]` and `var['mm_asset_outstanding']` remain nonzero. The very next "invest" trigger then satisfies `$bytes_balance == 0` and takes the "initial deposit" branch, minting `$issue_amount = balance[base]` shares (the attacker's own full incoming base amount) while completely disregarding the pre-existing `mm_asset_outstanding` supply and the pre-existing nonzero `$asset` reserve still sitting in the AA. This lets the attacker's newly minted shares represent an outsized fraction of total supply relative to the value they actually contributed, and a subsequent divest by the attacker extracts value (asset-side reserve) that was contributed by earlier depositors.

This mirrors exactly the class of bug in the external report: the contract's internal accounting (`mm_asset_outstanding`) can silently diverge from the real, live balances backing it, and the code path that is supposed to "reset" pricing when the pool is empty does not verify that *all three* invariants (both reserves and the share supply) are simultaneously zero.

## Impact Explanation
Any address that can post a trigger to a deployed instance of this market-maker AA (an ordinary, unprivileged transaction sender) can exploit the reserve/share desync to mint shares out of proportion to their contribution and later redeem them for a disproportionate share of the AA's real balance — a direct AA fund loss for other liquidity providers. Because AA fund balances are Obyte assets locked in the AA's address and can only move via correctly-computed `payment` messages emitted by the AA's own formula logic, this is a real, irreversible loss of funds for other participants, matching the "AA fund loss" impact category.

## Likelihood Explanation
The template is shipped in-repo as a reference/example AA pattern (`test/samples/uniswap_like_market_maker.oscript`, exercised by `test/ojson.test.js`), so any AA author who copies or is inspired by this pattern (a very natural and expected use of `balance[]` + a share-count `var[]`) inherits the flaw. Reaching the zero-reserve edge condition only requires ordinary sequences of deposit/withdraw/swap operations — no privileged access, no malicious peer/hub — driven purely by ordinary trigger senders performing valid trigger sequences, and integer rounding in `round()` makes hitting an exact zero reserve on one side plausible over the AA's lifetime, especially by an attacker deliberately structuring divest amounts to hit the zero boundary.

## Recommendation
The "initial deposit" reset logic should require that the share supply is also zero (`var['mm_asset_outstanding']` is unset/zero) before re-pricing as an empty pool, e.g.:
```
if (($asset_balance == 0 OR $bytes_balance == 0) AND !var['mm_asset_outstanding']){
    $issue_amount = balance[base];
    return;
}
```
More robustly, the AA should bounce (rather than silently re-price) if it detects a reserve of zero while shares are still outstanding, since that state indicates an accounting invariant violation that needs remediation rather than being treated as a legitimate "fresh pool" state. It is also advisable to enforce a minimum reserve floor (as real Uniswap does with `MINIMUM_LIQUIDITY`) so that reserves can never round down to exactly zero while shares remain outstanding.

## Proof of Concept
1. Attacker (or any user) performs the "define share asset" and an initial "invest" trigger, establishing `$asset` and `base` reserves and `mm_asset_outstanding` shares.
2. Attacker repeatedly triggers "divest MM shares" with carefully chosen `$mm_asset_amount` such that `round($investor_share * balance[base])` rounds down to consume the *entire remaining* base reserve to 0, while `round($investor_share * balance[$asset])` leaves a nonzero `$asset` reserve (due to different magnitudes/rounding on each asset) and leaves `mm_asset_outstanding` nonzero (not fully divested).
3. Attacker now sends a new "invest" trigger with `trigger.output[[asset=base]] > 1e5` and `trigger.output[[asset=$asset]] > 0`. Since `$bytes_balance == 0` (pre-trigger real base balance), the code takes the "initial deposit" branch and sets `$issue_amount = balance[base]` (attacker's own contributed base amount) — completely ignoring the pre-existing nonzero `mm_asset_outstanding` and nonzero `$asset` reserve still held in the AA from earlier depositors.
4. Attacker's shares are now minted independent of, and disproportionately large relative to, the true pool value (which still contains the pre-existing `$asset` reserve). Attacker triggers "divest MM shares" for their newly minted shares and receives a payout of `$asset` reserve value that rightfully belonged to earlier depositors, at their expense.
