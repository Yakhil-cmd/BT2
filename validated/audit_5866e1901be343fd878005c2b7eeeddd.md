### Title
Cross-organization webhook trust bypass: signature verified against `repository.owner.login`, but the mutated Stack/Repository is selected from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` selects which organization's `GitHubApp` (and thus which `webhook_secret`) is used to verify an inbound webhook's HMAC signature by reading `repository.owner.login` (or `organization.login`) from the JSON body. The handler dispatch that actually mutates application state (finds the `Repository`/`Stack` and applies the event) reads a *different* field from the same JSON body — `repository.full_name` — with no check that it belongs to the organization that was used to authenticate the request. In a multi-organization deployment this breaks the equality `organization used to verify signature == organization whose repository is written`.

### Finding Description
`verify_signature` picks the org-specific `GitHubApp` purely from `repository_owner`: [1](#0-0) [2](#0-1) 

That app config is resolved per-organization via `Shipit.github(organization:)` / `github_app_config`, which supports multiple independently configured GitHub Apps/webhook secrets in the same Shipit instance: [3](#0-2) 

Signature verification (`GitHubApp#verify_webhook_signature`) only checks the HMAC against the raw body using that one organization's secret: [4](#0-3) 

Once verified, `create` hands the *entire* raw JSON straight to the event handlers with no re-validation that the payload's target repository belongs to the organization that authenticated it: [5](#0-4) 

Every handler then resolves the `Stack`/`Repository` to mutate using `repository.full_name` — a field wholly independent from `repository.owner.login`: [6](#0-5) 

The same pattern (resolving the acted-upon repository from `params.repository.full_name`) repeats across concrete handlers (push/status/pull_request/etc.), e.g.: [7](#0-6) [8](#0-7) 

In a legitimate GitHub webhook delivery, `repository.owner.login` and the owner segment of `repository.full_name` are always identical because GitHub itself populates and signs both fields consistently for the repository that generated the event. `WebhooksController`, however, never enforces this equality itself — it trusts that GitHub always sends consistent payloads, and does not defend against a payload where the two fields diverge.

### Impact Explanation
This engine supports multiple organizations with independently configured GitHub Apps and distinct `webhook_secret`s (confirmed by the multi-app fixture `test/dummy/config/secrets_double_github_app.yml` and `Shipit.github_organizations`). An entity that legitimately controls the webhook secret for one configured organization (Org X) — e.g. an Org X administrator who can view/rotate Org X's own GitHub App webhook secret, a level of access far below possessing Shipit's Rails credentials, `GITHUB_TOKEN`, or an `ApiClient` token — can forge a correctly-signed webhook whose `repository.owner.login`/`organization.login` is `"OrgX"` (satisfying `verify_signature`) but whose `repository.full_name` is `"OrgY/some-repo"`, a repository belonging to a completely unrelated organization also hosted on the same Shipit instance. Because handler dispatch resolves the target `Stack` solely from `repository.full_name`, this forged event is processed as if it legitimately originated from Org Y: it can trigger `GithubSyncJob` deploy-branch syncs, mutate `MergeRequest`/status state, or archive/unarchive `ReviewStack`s belonging to Org Y — a cross-organization state mutation using credentials scoped to a different organization. This falls under "cross-repository writes," a Critical-severity impact per the engine's own webhook authentication model.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that configures more than one organization/GitHub App (a documented, supported configuration, see `secrets.github` multi-org schema and `github_app_config`). No Shipit session, `ApiClient` token, or Shipit-privileged account is required — only possession of one configured organization's own webhook secret, which is routinely accessible to that organization's own GitHub App administrators. The bug is purely in engine code (`WebhooksController#repository_owner` vs. `Handlers::Handler#repository_name`), not a third-party gem defect or a misconfiguration of the host app.

### Recommendation
After signature verification succeeds, `WebhooksController#create` (or `Handlers::Handler`) should assert that the organization derived from `repository.full_name`'s owner segment matches the `repository_owner` used to select the verifying `GitHubApp`, rejecting (422) any payload where they diverge. Alternatively, thread the verified organization through to handler dispatch and have `stacks`/`repository_name` resolution scope lookups to that verified organization instead of trusting the unauthenticated `repository.full_name` field in isolation.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgX` and `OrgY`, each with its own GitHub App and `webhook_secret` (as supported by `secrets.github` schema, cf. `test/dummy/config/secrets_double_github_app.yml`).
2. As an administrator of `OrgX`'s GitHub App, obtain `OrgX`'s `webhook_secret` (a credential scoped only to `OrgX`).
3. Craft a `push` (or `pull_request`) webhook JSON body where:
   - `repository.owner.login` = `"OrgX"` and `organization.login` = `"OrgX"` (used by `verify_signature`/`repository_owner`)
   - `repository.full_name` = `"OrgY/private-repo"` (used by `Handlers::Handler#repository_name` and every event handler)
4. Sign the raw JSON body with `OrgX`'s `webhook_secret` using HMAC-SHA1, and POST it to `/webhooks` with `X-Hub-Signature` set to that signature and `X-Github-Event: push`.
5. `verify_signature` succeeds (it only checks the signature against `OrgX`'s secret and the raw body). `create` dispatches the payload to `Shipit::Webhooks.for_event('push')`, which resolves the target `Stack` via `Repository.from_github_repo_name("OrgY/private-repo")` and performs the corresponding side effects (e.g. enqueues `GithubSyncJob` for `OrgY`'s stack) — despite the request never being authenticated by `OrgY`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
