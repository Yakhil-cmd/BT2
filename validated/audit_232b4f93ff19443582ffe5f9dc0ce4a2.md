### Title
Missing upper-bound validation on `threshold_size` system vote allows unit poster to set unbounded stability threshold - (File: validation.js)

### Summary
`validation.js`'s `system_vote` handler validates the `threshold_size` subject with only a lower bound (`>= 1000`) and a positive-integer check, but never enforces an upper bound, unlike the sibling `base_tps_fee`/`tps_interval`/`tps_fee_multiplier` votes which were explicitly given both lower *and* upper bounds. This mirrors the reported `_setTranches` bug class: a monotonic/one-sided bound check ("must increase" / "must be at least X") without the complementary upper-bound check that the value is later assumed to respect.

### Finding Description
In `validation.js`, the `system_vote` case dispatches on `payload.subject`. For `threshold_size` the only constraints applied are that the value is a positive integer and, conditionally, at least 1000 [1](#0-0) . Compare this to the `base_tps_fee`/`tps_interval`/`tps_fee_multiplier` branch immediately below it, where the developers explicitly added upper bounds (`<= 1e8`, `< 0.1` reject, `> 1000` reject) in addition to lower bounds after recognizing that a one-sided check is insufficient [2](#0-1) . `threshold_size` was left without the same treatment, so any unit author (not just witnesses/OPs — the only restriction present is `objValidationState.bAA` cannot cast a system vote) can post a `system_vote` unit with an arbitrarily large `threshold_size` value, which is a governance parameter consumed by `main_chain.js` to determine the witness support threshold needed to advance the stable main chain [3](#0-2) .

This is structurally the same defect as the `TrancheVesting._setTranches` issue: the code checks that a value satisfies one directional bound ("increasing" / "at least") but omits the corresponding upper-bound `require`, letting an attacker push the parameter to an extreme that breaks the invariant the rest of the system depends on (there, `vestedFraction` exceeding 10000 causes over-vesting; here, `threshold_size` growing unboundedly can make the required witness-support threshold unreachable).

### Impact Explanation
`threshold_size` is a network-wide parameter tallied via `system_vote`/`system_vote_count` and consumed in main-chain stability calculations. If an attacker can push this value arbitrarily high with a single vote unit (subject to normal vote-counting/superseding rules, but with no ceiling ever enforced), the effective threshold used to certify stability could become unreachable, preventing the network from advancing the stable main-chain index — i.e., the network becomes unable to confirm/finalize new units, one of the explicitly accepted high-impact outcomes for this class of bug.

### Likelihood Explanation
Casting a `system_vote` requires only posting a normal, non-AA unit — this is reachable by any unpriviledged unit poster, matching the required "unauthorized/unprivileged" analog criteria. The bug is a pure validation omission (no upper bound), so exploitation requires no special timing or race condition, only that the attacker's vote unit becomes part of the vote tally used to compute the active parameter.

### Recommendation
Add an explicit, sane upper bound to the `threshold_size` system-vote validation, consistent with how `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` were bounded, e.g.:

```javascript
case "threshold_size":
    if (!isPositiveInteger(payload.value))
        return callback(payload.subject + " must be a positive integer");
    if (!constants.bTestnet || objValidationState.last_ball_mci > 3543000) {
        if (payload.value < 1000)
            return callback(payload.subject + " must be at least 1000");
        if (payload.value > MAX_THRESHOLD_SIZE) // define a sensible cap
            return callback(payload.subject + " must be at most " + MAX_THRESHOLD_SIZE);
    }
    callback();
    break;
```

### Proof of Concept
1. Craft and broadcast a unit (any non-AA, single-authored unit is sufficient) with message `app: "system_vote"`, `payload: { subject: "threshold_size", value: <extremely large integer> }`.
2. Validation in `validation.js` accepts it because only the lower bound (`>= 1000`) and positive-integer checks are enforced; no upper bound exists [1](#0-0) .
3. Once enough such votes are counted via `system_vote_count`, the network-wide `threshold_size` parameter used by `main_chain.js` for stability determination is updated to the attacker-supplied extreme value.
4. With an unreachable threshold, the network cannot certify further units as stable, halting confirmation of new units.

Note: I was not able to fully trace, within the available search budget, the exact formula in `main_chain.js` that consumes `threshold_size` to confirm the precise numeric consequence of an extreme value (e.g., whether vote-count safeguards elsewhere might partially mitigate this). This should be verified against `main_chain.js`'s stability-threshold computation before treating the impact as fully confirmed.
