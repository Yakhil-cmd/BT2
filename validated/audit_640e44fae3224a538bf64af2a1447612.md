This confirms the multi-tenant GitHub configuration model: `Shipit.github(organization:)` looks up a separate `GitHubApp` (with its own `webhook_secret`) per organization key in `secrets.github` [1](#0-0) , and `webhook_secret` is explicitly documented as optional per app/org [2](#0-1) .

### Title
Cross-organization webhook forgery via organization/repository binding mismatch in `WebhooksController` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the HMAC secret) used to validate an inbound webhook based on `repository.owner.login` (or `organization.login`) taken from the **unverified** request body, while the handlers that actually mutate state select the target `Repository`/`Stack` using `repository.full_name`, also taken from the same unverified body [3](#0-2) . These two fields are never checked for consistency, and if any one configured organization in a multi-tenant Shipit install has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` unconditionally returns `true` for it [4](#0-3) .

### Finding Description
This is the same class of bug as the `LineOfCredit` report: a value that is trusted and acted upon (`repository.full_name`, used by `Handler#repository_name` to resolve the stack to write to [5](#0-4) ) is never covered by the same verification that is performed on a *different* field (`repository.owner.login`, used only to pick which app's secret validates the signature) [6](#0-5) .

The equality that should hold is:
`organization authenticated by verify_signature == organization owning the repository that handlers write to`

Before the attack: for a legitimate webhook, GitHub sets both `repository.owner.login` and `repository.full_name` consistently, and signs the payload with the secret for that same organization.

After the attacker's forged request: an attacker who knows (or is a member of) any organization `org-A` configured in Shipit with **no** `webhook_secret` set can send a raw POST to `/webhooks` with:
- `X-Github-Event` set to `push` (or another handled event),
- `repository.owner.login = "org-A"` (so `verify_signature` calls `Shipit.github(organization: "org-A")`, whose `verify_webhook_signature` returns `true` unconditionally because no secret is configured) [4](#0-3) ,
- `repository.full_name = "org-B/victim-repo"` — any other tracked repository in the Shipit instance.

`PushHandler` will then resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (i.e. `org-B/victim-repo`) and call `stack.sync_github(expected_head_sha: params.after)` on it [7](#0-6) , forcing a GitHub sync on a target stack the attacker does not own, using a forged `after` SHA. Similarly `ClosedHandler` can archive an arbitrary tracked pull-request stack based only on the forged `repository.full_name` [8](#0-7) .

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding named in the rules. In a Shipit install serving several GitHub organizations, one org's lax/absent webhook secret becomes an authentication bypass that lets that org's members forge webhook events attributed to any other organization's repositories/stacks, triggering `sync_github`, stack archival, or merge-queue processing for repos they have no access to. This can escalate to unauthorized deploy triggers if commit statuses are also spoofable through the same path.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment with `secrets.github` containing more than one organization, and (2) at least one of those organizations configured without a `webhook_secret` (documented as optional, so realistic in practice) [2](#0-1) . Given that, any unprivileged actor able to reach the public `/webhooks` endpoint (no Shipit session or token needed) can exploit it — likelihood is moderate-to-high depending on deployment configuration, but not universal since it needs the multi-org + missing-secret precondition.

### Recommendation
Bind the field used for signature-selection to the field used for stack resolution: after `verify_webhook_signature` succeeds, re-derive/verify that `repository.full_name`'s owner matches the organization whose secret validated the request (or vice-versa), and reject events where they diverge. Additionally, consider treating a missing `webhook_secret` as "require an X-Hub-Signature that still cannot pass" rather than an implicit bypass, or require configuring a secret per organization when multiple organizations are configured.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `org-A` (no `webhook_secret`) and `org-B` (has a stack tracking `org-B/victim-repo`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/victim-repo" }
}
```
No `X-Hub-Signature` header (or any garbage value) is required.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-A")` and `verify_webhook_signature` returns `true` (no secret configured for `org-A`) — see `app/controllers/shipit/webhooks_controller.rb:24-30` and `lib/shipit/github_app.rb:76-83`.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("org-B/victim-repo")` and its stacks, then calls `stack.sync_github(expected_head_sha: "deadbeef...")` on `org-B`'s stack — see `app/models/shipit/webhooks/handlers/handler.rb:36-38` and `app/models/shipit/webhooks/handlers/push_handler.rb:12-17` — despite the request never being signed by, or originating from, `org-B`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
