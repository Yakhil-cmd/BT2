### Title
Staking reward `cnAmount` silently lost when validator `CLPoolAddr` equals `RewardAddr` — (File: `kaiax/reward/impl/getter.go`)

---

### Summary

In `assignStakingRewards` and `assignStakingRewardsFlex`, the Prague-era CL reward split uses bare map **assignment** (`alloc[addr] = value`) rather than addition. If a validator's consensus-liquidity pool address (`CLPoolAddr`) equals their AddressBook reward address (`RewardAddr`), the second assignment silently overwrites the first, causing the `cnAmount` portion of that validator's staking reward to be permanently unallocated — neither credited to the validator nor returned to the proposer as a remainder.

---

### Finding Description

Both `assignStakingRewards` and `assignStakingRewardsFlex` contain the following pattern for Prague-era validators that have a `CLStakingInfo`:

```go
// assignStakingRewards  (lines 521-525)
cnAmount, clAmount := cn.Split(reward)
alloc[cn.RewardAddr] = cnAmount                    // assignment #1
alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount      // assignment #2
```

`cn.Split(reward)` partitions `reward` proportionally between `cn.StakingAmount` (CNStaking) and `cn.CLStakingInfo.CLStakingAmount` (CLStaking), so `cnAmount + clAmount ≈ reward`.

When `cn.CLStakingInfo.CLPoolAddr == cn.RewardAddr`:

1. Assignment #1 writes `alloc[R] = cnAmount`.
2. Assignment #2 **overwrites** `alloc[R] = clAmount`.
3. `remaining` is still decremented by the full `reward = cnAmount + clAmount`.

After the loop, `alloc` contains only `clAmount` for address `R`, while `remaining` has been reduced by `cnAmount + clAmount`. The caller (`getDeferredRewardFullKore` / `getDeferredRewardFullFlex`) adds `remaining` (as `kip82Remainder`) to the proposer and iterates `alloc` to credit recipients:

```go
stakersAlloc, kip82Remainder := assignStakingRewards(config, stakers, si)
proposer.Add(proposer, kip82Remainder)          // kip82Remainder already short by cnAmount
for addr, amount := range stakersAlloc {
    spec.IncRecipient(addr, amount)             // only clAmount credited to R
}
```

Net accounting:

| Recipient | Receives | Should receive |
|-----------|----------|----------------|
| Validator `R` | `clAmount` | `cnAmount + clAmount` |
| Proposer | `proposer + (stakers − cnAmount − clAmount − …)` | `proposer + (stakers − cnAmount − clAmount − …)` ← same |
| **Lost** | **`cnAmount`** | **0** |

`cnAmount` is permanently unallocated. Because `spec.Stakers` is set to `stakers − kip82Remainder = cnAmount + clAmount + …` (the full intended staker budget), but `spec.Rewards` sums to `stakers − cnAmount + …`, the `spec.Validate()` consistency check (`sumParts == sumRewards`) will detect the discrepancy and cause `FinalizeState` to return an error, halting block finalization for every block where this validator is eligible for staking rewards.

The identical pattern exists in `assignStakingRewardsFlex` at lines 474–477.

---

### Impact Explanation

- **Primary**: Every block in which the affected validator is staking-reward-eligible, `FinalizeState` returns a validation error, preventing the block from being written. This is a **consensus-halting** condition for any node that processes a block proposed while this validator configuration is active.
- **Secondary** (if `Validate()` is lenient): `cnAmount` of KAIA staking rewards is permanently lost per block — neither credited to the validator nor redistributed to the proposer.

Both outcomes fall within the allowed impact gate: *invalid state transition / consensus divergence on honest nodes* and *incorrect reward distribution affecting KAIA*.

---

### Likelihood Explanation

The trigger requires `cn.CLStakingInfo.CLPoolAddr == cn.RewardAddr`. There is **no validation** in the Go staking/reward pipeline that enforces these two addresses to be distinct. The `CLPoolAddr` is sourced from the CLRegistry contract and the `RewardAddr` from the AddressBook contract; they are parsed independently in `parseCallResult` / `parsePermissionlessCallResult` with no cross-check. A validator who deploys a smart contract and registers it as both their AddressBook reward address and their CLRegistry pool address — whether accidentally or deliberately — triggers the bug. The Aleo report's sponsor explicitly acknowledged the analogous scenario ("a validator operator will want to withdraw rewards … it's possible that a validator tries to use the same withdrawal address for both validator and delegator") as a legitimate use-case; the same reasoning applies here.

---

### Recommendation

Replace bare map assignment with additive helpers in both functions:

```go
// Instead of:
alloc[cn.RewardAddr] = cnAmount
alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount

// Use (mirrors specWithProposerAndFunds which already uses IncRecipient correctly):
addToAlloc(alloc, cn.RewardAddr, cnAmount)
addToAlloc(alloc, cn.CLStakingInfo.CLPoolAddr, clAmount)

// helper:
func addToAlloc(m map[common.Address]*big.Int, addr common.Address, v *big.Int) {
    if cur, ok := m[addr]; ok {
        cur.Add(cur, v)
    } else {
        m[addr] = new(big.Int).Set(v)
    }
}
```

Additionally, add a guard in `consolidateNodes` or `parseCallResult` / `parsePermissionlessCallResult` that rejects (or logs and skips) any `CLStakingInfo` whose `CLPoolAddr` equals the corresponding `RewardAddr`.

---

### Proof of Concept

**Setup (Prague hardfork active, `WeightedRandom` policy, `deferredTxFee = true`):**

1. Validator V registers reward address `R` in AddressBook (`CN_REWARD_ADDRESS_TYPE`).
2. Validator V registers CL pool address `R` (same address) in CLRegistry.
3. V's CNStaking = 6 000 000 KAIA, CLStaking = 2 000 000 KAIA; `minStake` = 5 000 000 KAIA.

**Execution trace in `assignStakingRewards`:**

```
cn.RewardAddr          = R
cn.StakingAmount       = 6_000_000
cn.CLStakingInfo.CLPoolAddr    = R   ← same as RewardAddr
cn.CLStakingInfo.CLStakingAmount = 2_000_000

reward = proportional share of stakersReward
cn.Split(reward):
  cnAmount = reward * 6_000_000 / 8_000_000 = 0.75 * reward
  clAmount = reward * 2_000_000 / 8_000_000 = 0.25 * reward

alloc[R] = cnAmount          // 0.75 * reward
alloc[R] = clAmount          // OVERWRITES → 0.25 * reward
remaining -= reward          // decremented by full reward

returned alloc[R] = 0.25 * reward   (0.75 * reward lost)
```

**Result:** `spec.Stakers` accounts for the full `reward`, but `spec.Rewards` is short by `0.75 * reward`. `spec.Validate()` fails → `FinalizeState` returns error → block cannot be committed. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

func (si *StakingInfo) consolidateNodes() *[]consolidatedNode {
	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))
	nToR := make(map[common.Address]common.Address)

	for i, n := range si.NodeIds {
		r := si.RewardAddrs[i]
		// Unique nodeId is guaranteed by AddressBook.
		nToR[n] = r
		if cn, ok := cmap[r]; ok {
			cn.NodeIds = append(cn.NodeIds, n)
			cn.StakingContracts = append(cn.StakingContracts, si.StakingContracts[i])
			cn.StakingAmount += si.StakingAmounts[i]
		} else {
			cmap[r] = &consolidatedNode{
				NodeIds:          []common.Address{n},
				StakingContracts: []common.Address{si.StakingContracts[i]},
				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}

	// CLStakingInfo can only exist after Prague HF.
	if len(si.CLStakingInfos) > 0 {
		for _, clsi := range si.CLStakingInfos {
			// If the nodeId of CLStakingInfo is not found in nToR, it means the validator is not in the AddressBook.
			// So we skip it.
			if r, ok := nToR[clsi.CLNodeId]; ok {
				// One CLStakingInfo per validator is guaranteed by CLRegistry.
				cmap[r].CLStakingInfo = clsi
			}
		}
	}
