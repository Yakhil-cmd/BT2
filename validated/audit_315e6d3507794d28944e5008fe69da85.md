### Title
KAIA Permanently Frozen in Service-Chain Bridge When `_to` Recipient Cannot Receive Native KAIA — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`BridgeTransferKLAY.handleKLAYTransfer` delivers bridged KAIA to a fixed `_to` address recorded at request time. If `_to` is a contract that cannot receive native KAIA (no `receive()` / `fallback()`), the low-level call returns `false`, the `require` reverts the entire handle transaction, and the KAIA is permanently locked inside the bridge contract. There is no alternative-recipient parameter, no emergency-sweep function, and no way for the original sender to redirect the funds.

---

### Finding Description

When a user initiates a cross-chain KAIA transfer on the source chain they call:

```solidity
// BridgeTransferKLAY.sol line 132
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
```

The `_to` address is emitted in a `RequestValueTransfer` event and relayed by bridge operators to the destination chain via:

```solidity
// BridgeTransferKLAY.sol lines 62-100
function handleKLAYTransfer(
    bytes32 _requestTxHash,
    address _from,
    address payable _to,   // fixed at request time, cannot be changed
    uint256 _value,
    ...
) public onlyOperators nonReentrant {
    ...
    (bool ok, ) = _to.call.value(_value)("");
    require(ok, "handleKLAYTransfer: transfer failed");
}
``` [1](#0-0) 

If `_to` is a contract that does not implement `receive()` or a payable `fallback()`, the low-level call returns `ok = false`. The `require` reverts the entire `handleKLAYTransfer` transaction. Because the nonce is only advanced inside the same transaction (after the `require`), the handle record for this nonce is never written, and operators must keep retrying — always reverting. The KAIA value remains locked in the bridge contract with no on-chain path to recover it.

The `_requestKLAYTransfer` internal function also hardcodes `msg.sender` as the source address in the event:

```solidity
// BridgeTransferKLAY.sol lines 113-123
emit RequestValueTransfer(
    TokenType.KLAY,
    msg.sender,   // source is fixed
    _to,          // destination is fixed
    ...
);
requestNonce++;
``` [2](#0-1) 

Neither the source sender nor the bridge owner has any function to redirect the stuck KAIA to an alternative address. No `emergencyWithdraw`, `sweep`, or recipient-override function exists in the bridge contract hierarchy (`BridgeTransfer`, `BridgeTransferKLAY`).

The Go-layer bridge manager unconditionally calls `HandleKLAYTransfer` with the original `to` address from the event, providing no fallback path:

```go
// node/sc/bridge_manager.go line 333
handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
``` [3](#0-2) 

---

### Impact Explanation

Bridged KAIA is permanently frozen inside the destination bridge contract. The original sender loses the full transferred value with no on-chain recovery path. This matches the "bridged assets permanently frozen" category in the Kaia Allowed Impact Gate.

---

### Likelihood Explanation

Low. The trigger requires `_to` to be a contract address that cannot receive native KAIA. This can occur when:
- A user mistakenly specifies a contract address (e.g., a multisig, DAO, or protocol contract) that lacks a `receive()` function.
- A contract at `_to` is upgraded or self-destructed between the request and the handle.

The scenario is low-probability but fully reachable by any unprivileged user without operator collusion.

---

### Recommendation

Add an `alternativeRecipient` parameter to `handleKLAYTransfer` (analogous to the Ajna recommendation), or implement a pull-payment pattern: on transfer failure, credit the value to a claimable balance keyed by `_requestTxHash` that the original sender can redirect to a new address. At minimum, add an owner-callable `recoverStuckTransfer(bytes32 requestTxHash, address newRecipient)` function.

---

### Proof of Concept

1. On the source chain, a contract `VaultContract` (no `receive()`) calls `requestKLAYTransfer(address(VaultContract), 100 ether, "")` sending 100 KAIA.
2. Bridge operators observe the `RequestValueTransfer` event with `_to = address(VaultContract)`.
3. Operators call `handleKLAYTransfer(..., address(VaultContract), 100 ether, ...)` on the destination bridge.
4. `(bool ok,) = address(VaultContract).call{value: 100 ether}("")` returns `ok = false` because `VaultContract` has no `receive()`.
5. `require(ok, "handleKLAYTransfer: transfer failed")` reverts.
6. The nonce is never advanced; every subsequent retry reverts identically.
7. 100 KAIA remains locked in the bridge contract permanently with no recovery function available. [4](#0-3)
