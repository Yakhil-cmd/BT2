### Title
Cross-organization webhook forgery — `WebhooksController#verify_signature` authenticates the wrong organization, letting one org's GitHub App secret forge events (deploys, statuses, and DAO-authorization team membership) for any other org's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit supports one GitHub App configuration *per organization*, each with its own `webhook_secret`. `WebhooksController#verify_signature` picks which organization's secret to verify the HMAC against using a field taken from the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`), then hands the *same* raw, unvalidated body to event handlers that act on a completely different field (`repository.full_name`, or `organization.login` for `membership`) without ever checking that it is consistent with the organization whose secret validated the signature.

### Finding Description
`verify_signature` resolves the signing organization purely from attacker-controlled payload content: [1](#0-0) [2](#0-1) 

The webhook secret used for that HMAC check is looked up per-organization from `secrets.github[organization]`: [3](#0-2) 

Because the HMAC covers the raw body, an attacker cannot forge a signature without *knowing some org's webhook secret*. However, any GitHub organization admin who installs Shipit's GitHub App on their own org (or otherwise legitimately obtains their org's `webhook_secret`, e.g. via GitHub's UI/App settings) can compute a fully valid signature for **any JSON body they like**, as long as `repository.owner.login` (or `organization.login`) in that body names their own org. Nothing forces the rest of the payload — in particular `repository.full_name`, or the `organization` object used by the membership handler — to actually belong to that org.

Downstream handlers trust these unverified fields to select what gets mutated:
- `PushHandler` resolves the target `Repository`/`Stack` via `payload.dig('repository','full_name')` in the shared `Handler` base class, entirely independent of the org used for signature verification: [4](#0-3) [5](#0-4) 
- `StatusHandler` doesn't even scope by repository — it matches purely on commit SHA across the entire installation: [6](#0-5) 
- `MembershipHandler` uses `params.organization.login` (a distinct field from what's used for signature-org selection when `repository` is absent) to find-or-create a `Team` and add/remove arbitrary GitHub logins as members: [7](#0-6) 

Team membership feeds directly into authorization: `User#authorized?` checks membership in `Shipit.github_teams`, which are org/team handles from server config: [8](#0-7) [9](#0-8) 

**Binding broken:** `organization authenticated by verify_signature (repository.owner.login / organization.login used to select webhook_secret) ≠ organization/repository actually written by the handler (repository.full_name resolved independently, or a same-named `organization.login` field never cross-checked against the verified org)`.

### Impact Explanation
An attacker who controls (or is an admin of) any single organization onboarded to a shared Shipit instance — a routine, low-privilege action (installing a GitHub App and reading its own webhook secret from GitHub's UI, or configuring their own repo's per-repo `GithubHook` secret) — can forge signed webhook deliveries whose signature validates under their own org, but whose `repository.full_name`/`organization.login` payload fields point at a victim org's stack or team:
- Forge a `push` event for a victim's `Stack` → triggers `GithubSyncJob`/`sync_github`, potentially cascading into continuous-deployment auto-deploys of arbitrary commit SHAs — an unauthorized deploy.
- Forge a `status` event for any commit SHA in the entire installation (not scoped to any repository at all) → poison CI/deployability gating for any stack.
- Forge a `membership` event naming an authorized org/team → add an arbitrary GitHub login to a `Team` that is part of `Shipit.github_teams`, granting that login authenticated/authorized access to the whole Shipit instance — an authentication/authorization bypass, matching the "escalation into `Shipit.github_teams` authorization" High-impact category.

This satisfies the required impact bar: unauthorized deploy and escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
Requires possessing one legitimate GitHub App/organization webhook secret already known to the attacker for an org they administer on a multi-tenant Shipit deployment (or a hooked repository's `GithubHook#secret`) — a routine setup action, not a privileged Shipit credential, GitHub write access to the victim repo, or social engineering. No other authentication boundary needs to be crossed.

### Recommendation
After signature verification, re-derive and enforce that every payload field used by handlers to select a target (`repository.full_name`'s owner segment, or `organization.login` for organization-level events) matches exactly the organization whose secret validated the signature. Reject the webhook if these disagree, rather than trusting `repository.owner.login`/`organization.login` merely to pick a key and then trusting other payload fields independently for routing.

### Proof of Concept
1. Admin of `attacker-org` installs Shipit's GitHub App on their own organization, obtaining their organization's `webhook_secret` (a normal, expected action for onboarding).
2. Craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `webhook_secret`, and the signature validates (see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `PushHandler` resolves the target via `repository.full_name` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `push_handler.rb:12-17`) and enqueues `GithubSyncJob` for the victim's stack — a stack the attacker never authenticated against.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
