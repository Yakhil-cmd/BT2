### Title
Cross-user DoS via `reject_new_shared_address` device message – missing membership check allows any correspondent to delete another user's pending multi-signature address setup - ([File: wallet.js])

### Summary
The `reject_new_shared_address` device-message handler deletes a `pending_shared_addresses` record identified solely by an attacker-supplied `address_definition_template_chash`, without verifying that the sending device (`from_address`) is actually one of the invited co-signers for that specific pending shared address. This mirrors the Hatchet pattern: a caller-supplied resource identifier (`worker_id` in Hatchet, `address_definition_template_chash` here) is used to perform a state-changing/DoS operation while the code never checks that the identifier belongs to the caller's own relationship/session.

### Finding Description
In `wallet.js`, the `handleMessageFromHub` switch handles the `reject_new_shared_address` subject: [1](#0-0) 

```js
case "reject_new_shared_address":
    // {address_definition_template_chash: "BASE32"}
    if (!ValidationUtils.isValidAddress(body.address_definition_template_chash))
        return callbacks.ifError("invalid addr def c-hash");
    walletDefinedByAddresses.deletePendingSharedAddress(body.address_definition_template_chash);
    callbacks.ifOk();
    break;
```

The only validation performed is that the field is syntactically a valid address/chash — there is no check binding `from_address` (the authenticated sender, derived from the verified device-message signature) to the `definition_template_chash` being deleted. Compare this with the sibling handler `approve_new_shared_address`, whose downstream function `approvePendingSharedAddress` correctly scopes its `UPDATE` with `WHERE definition_template_chash=? AND device_address=?` using `from_address`: [2](#0-1) 

`deletePendingSharedAddress`, by contrast, performs an unscoped delete keyed only by the chash: [3](#0-2) 

```js
function deletePendingSharedAddress(address_definition_template_chash){
	db.query("DELETE FROM pending_shared_address_signing_paths WHERE definition_template_chash=?", [address_definition_template_chash], function(){
		db.query("DELETE FROM pending_shared_addresses WHERE definition_template_chash=?", [address_definition_template_chash], function(){});
	});
}
```

Any correspondent (paired device) that is able to send a `reject_new_shared_address` message — including one who is not a member of the specific multi-address definition template in question — can wipe out the `pending_shared_addresses` and `pending_shared_address_signing_paths` rows for that template, aborting the in-progress shared/multisig address creation for the actual intended participants. As in the Hatchet advisory, the `from_address` is derived and authenticated from the message signature but is used only incidentally (nowhere in the delete path), never to authorize the operation against the referenced resource.

### Impact Explanation
This allows a low-privilege paired correspondent to disrupt the shared-address (multisig) setup process of other users on the same node/hub relationship graph, deleting legitimate in-progress `pending_shared_addresses`/`pending_shared_address_signing_paths` records they are not a party to. This is a denial-of-service against another party's wallet-setup workflow: the victim's multi-signature address creation silently fails/needs to be restarted, and could be repeated to indefinitely block a targeted user's shared-address (and thus a shared/multisig funds address) from ever completing, which can delay or prevent access to funds meant to be secured by that pending shared address.

### Likelihood Explanation
Exploitation requires the attacker to be a paired correspondent capable of sending encrypted device messages to the victim device (this messaging path is only reachable between paired devices, consistent with the allowed "paired device" actor class) and to know or guess the `address_definition_template_chash` of the target's pending shared address, which is a 160-bit c-hash of the address definition template. This significantly limits opportunistic attackers, but any device that legitimately received the `create_new_shared_address` offer for a group (e.g. one member of a 3+-party template) can trivially compute/observe the correct chash and then attack the other, non-consented member's flow, or a malicious/misbehaving correspondent already in the pairing/cosigner group can grief the wallet setup of others outside their own device-address scope, since the delete is not restricted to rows involving `from_address`.

### Recommendation
Scope the deletion of `pending_shared_addresses`/`pending_shared_address_signing_paths` by the authenticated `from_address`, mirroring the pattern already used in `approvePendingSharedAddress`. For example, only delete `pending_shared_address_signing_paths` rows `WHERE definition_template_chash=? AND device_address=?` for the sender, and only cascade-delete the parent `pending_shared_addresses` row once no signing-path rows for other devices remain unaffected by an unauthorized party, or require confirmation that `from_address` is present among the expected `device_address`es for that `definition_template_chash` before allowing deletion.

### Proof of Concept
1. Device A initiates `createNewSharedAddressByTemplate` including devices A, B, C, generating `address_definition_template_chash = objectHash.getChash160(arrAddressDefinitionTemplate)`.
2. Device C (a paired but non-consenting/malicious correspondent of A or B, or a member of the group acting maliciously toward a sibling flow) obtains this chash (e.g., by being CC'd into the flow or via a leaked/logged value) and sends the `reject_new_shared_address` device message to Device A with `{address_definition_template_chash: <chash>}`, using its own valid signed device message (its own `from_address` need not match any row for that chash).
3. `wallet.js`'s handler calls `walletDefinedByAddresses.deletePendingSharedAddress(chash)` unconditionally, deleting the `pending_shared_addresses` and `pending_shared_address_signing_paths` rows for the entire A/B/C group.
4. Devices A and B's legitimate multisig/shared-address setup silently disappears, forcing them to restart the process — demonstrating a DoS triggered by an unauthorized paired device referencing another party's resource identifier.
