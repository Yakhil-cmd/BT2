### Title
Unauthenticated, front-runnable `BridgeCommittee.initializeConfig` allows hijacking bridge stake-threshold verification - (File: `bridge/evm/contracts/BridgeCommittee.sol`)

### Summary
`BridgeCommittee` splits its initialization into two functions: `initialize(...)` (guarded by OpenZeppelin's `initializer` modifier) and `initializeConfig(address _config)`, which is a completely separate, unprotected `external` call. This mirrors the root cause of the EIP712 report: a contract that inherits/depends on a piece of state that is normally expected to be set during "initialization" but whose setting is not enforced atomically or access-controlled, leaving a window where the security-critical state can be bound to attacker-controlled data instead of the legitimate value.

### Finding Description [1](#0-0) 

```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

Unlike `initialize()`, this function has no `onlyOwner`, `initializer`, or any caller restriction — the only guard is that `config` must still be the zero address. `config` is later relied on by `verifySignatures` (via `BridgeUtils.requiredStake(message)`) to decide how much aggregate committee stake is required to approve a message: [2](#0-1) 

Because committee membership/stake is populated in `initialize()` but the `config` contract that determines `requiredStake` is populated in a *separate, unguarded* transaction, there is a window between the two deployment steps (which necessarily happen in different transactions, since `BridgeConfig` cannot be deployed before `BridgeCommittee` exists and needs its address) during which any unprivileged account can call `initializeConfig` on the freshly-deployed `BridgeCommittee` proxy and bind it to an attacker-controlled `IBridgeConfig` implementation before the legitimate deployer does. This is directly analogous to the audited bug pattern: state that should be set as part of a single, protected initialization sequence is instead left to be filled in later without proper access control/atomicity, and downstream logic (`castVoteBySig`-style signature/threshold checks in the original bug; `verifySignatures` here) silently operates against attacker-influenced values instead of the intended ones.

### Impact Explanation
If an attacker wins the race and sets `config` to a malicious contract, `BridgeUtils.requiredStake(message)` can be made to return `0` (or any arbitrarily low value) for `TOKEN_TRANSFER` messages. In `verifySignatures`, `require(approvalStake >= requiredStake, ...)` would then pass trivially — even with zero or arbitrarily few valid committee signatures — allowing an attacker to push through fabricated bridge messages such as token transfer approvals, ultimately enabling illegitimate unlocking/minting of bridged assets from the vault. This matches the Critical allowed-impact class "bridge message forgery or bridge governance/upgrade bypass that enables illegitimate mint or unlock."

### Likelihood Explanation
Exploitability depends entirely on deployment procedure: if `BridgeCommittee.initializeConfig` and `BridgeConfig` deployment/wiring are not performed atomically within the same transaction (e.g., via a deployer/multicall contract that deploys and wires everything in one call), the window is real and can be front-run by any unprivileged address monitoring the mempool for the legitimate `initializeConfig` call. I was not able to fully confirm from the deployment scripts in this repository whether the production deployment flow performs this wiring atomically (the tool budget ran out before I could inspect `bridge/evm/script/` deployment scripts in detail) — the test harness (`BridgeBaseTest.t.sol`) calls `initialize` and `initializeConfig` in sequential but separate calls from the same `deployer` account, which is consistent with a real two-transaction deployment flow in production as well. This uncertainty about actual production deploy atomicity is the main caveat on likelihood.

### Recommendation
- Merge `initializeConfig` into the `initializer`-gated `initialize()` function so `config` is set atomically with the rest of the committee state in a single, unforgeable transaction, or
- Add access control (e.g., restrict to the deployer/owner or use a factory/multicall pattern with `CREATE2`) so `initializeConfig` cannot be called by an arbitrary address, and
- Emit an event on `initializeConfig` so any front-run attempt is immediately observable, and add a check requiring `_config != address(0)` before accepting it.

### Proof of Concept
1. Deployer publishes `BridgeCommittee` proxy and calls `initialize(committee, stake, minStakeRequired)` in transaction T1 — committee membership/stake is now live, but `config == address(0)`.
2. Attacker observes T1 is mined and, before the deployer's follow-up `initializeConfig(realConfigAddress)` transaction is mined, submits `initializeConfig(maliciousConfigAddress)` with higher gas.
3. Because `initializeConfig` has no caller restriction, attacker's transaction succeeds and `config` is permanently locked to `maliciousConfigAddress` (guarded only by the "already initialized" check, which now blocks the legitimate deployer's call).
4. `maliciousConfigAddress` implements `IBridgeConfig` to return `requiredStake == 0` for `TOKEN_TRANSFER` (or any) message type.
5. Attacker (or a colluding minimal-stake signer) calls `updateBlocklistWithSignatures`/token transfer approval flow through `SuiBridge`, which calls `BridgeCommittee.verifySignatures`; with `requiredStake == 0`, `approvalStake >= requiredStake` is trivially true even with zero valid signatures, allowing forged bridge messages to be accepted.

    function verifySignatures(bytes[] memory signatures, BridgeUtils.Message memory message)
        external
        view
        override
    {
        uint32 requiredStake = BridgeUtils.requiredStake(message);

        uint16 approvalStake;
        address signer;
        uint256 bitmap;

        // Check validity of each signature and aggregate the approval stake
        for (uint16 i; i < signatures.length; i++) {
            bytes memory signature = signatures[i];
            // recover the signer from the signature
            (bytes32 r, bytes32 s, uint8 v) = splitSignature(signature);

            (signer,,) = ECDSA.tryRecover(BridgeUtils.computeHash(message), v, r, s);

            require(!blocklist[signer], "BridgeCommittee: Signer is blocklisted");
            require(committeeStake[signer] > 0, "BridgeCommittee: Signer has no stake");

            uint8 index = committeeIndex[signer];
            uint256 mask = 1 << index;
            require(bitmap & mask == 0, "BridgeCommittee: Duplicate signature provided");
            bitmap |= mask;

            approvalStake += committeeStake[signer];
        }

        require(approvalStake >= requiredStake, "BridgeCommittee: Insufficient stake amount");
