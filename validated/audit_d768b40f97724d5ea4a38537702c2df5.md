### Title
Architecture-Gated G2 Subgroup Check Divergence in BN256 Pairing Precompile — (`crypto/bn256/bn256_fast.go`, `crypto/bn256/bn256_slow.go`, `crypto/bn256/gnark/g2.go`, `crypto/bn256/cloudflare/bn256.go`)

---

### Summary

The `bn256` package selects its implementation via build tags: `amd64 || arm64` uses gnark, while `!amd64 && !arm64` uses cloudflare. The gnark `G2.Unmarshal` performs both an on-curve check and a prime-order subgroup check; the cloudflare `G2.Unmarshal` performs only an on-curve check. A raw 192-byte input to precompile `0x08` containing a G2 point that is on the twist curve but outside the prime-order subgroup (a cofactor element) will be rejected with an error on gnark nodes and silently accepted on cloudflare nodes. Because the cloudflare `PairingCheck` applies `finalExponentiation` — which annihilates cofactor-order elements for BN254 — the cloudflare path returns `true32Byte`, while the gnark path causes the precompile call to revert. This produces divergent EVM execution results and divergent state roots between the two node populations.

---

### Finding Description

**Build-tag split:**

`bn256_fast.go` (build tag `amd64 || arm64`) aliases `G2` and `PairingCheck` to the gnark package. [1](#0-0) 

`bn256_slow.go` (build tag `!amd64 && !arm64`) aliases them to the cloudflare package. [2](#0-1)

``` [4](#0-3) 

**cloudflare `PairingCheck` — proceeds directly to `finalExponentiation`:**

```go
func PairingCheck(a []*G1, b []*G2) bool {
    acc := new(gfP12)
    acc.SetOne()
    for i := range a {
        if a[i].p.IsInfinity() || b[i].p.IsInfinity() { continue }
        acc.Mul(acc, miller(b[i].p, a[i].p))
    }
    return finalExponentiation(acc).IsOne()
}
``` [5](#0-4)

### Impact Explanation

For BN254, the G2 twist curve has order `r · h₂` where `h₂` is the cofactor. A cofactor element `T` (order dividing `h₂`, on the curve, not in the prime-order subgroup) satisfies `e(P, T) = 1` after `finalExponentiation` because `h₂ | (p¹²−1)/r` for BN254. Therefore:

| Node type | `G2.Unmarshal(T)` | Precompile result |
|---|---|---|
| amd64 / arm64 (gnark) | error — `IsInSubGroup()` fails | CALL reverts (returns 0, empty data) |
| non-amd64 / non-arm64 (cloudflare) | success — only `IsOnCurve()` checked | CALL succeeds, returns `true32Byte` |

Any contract that branches on the return value of `call(gas, 0x08, ...)` will execute a different code path on the two node populations, producing different storage writes and different state roots. This is a consensus split.

---

### Likelihood Explanation

The cloudflare path is gated behind `!amd64 && !arm64`. Production Kaia validators almost universally run on amd64 or arm64, so the divergence requires at least one non-amd64/non-arm64 validator to be present in the active set. This makes the practical likelihood low. However:

- The code explicitly ships and maintains the cloudflare path for these architectures.
- The attacker input is a single valid-looking 192-byte transaction payload — no privileged access, no key compromise, no validator collusion required.
- If any non-amd64/non-arm64 node participates in consensus, the split is deterministic and repeatable.

---

### Recommendation

Add a subgroup check to the cloudflare `G2.Unmarshal`, mirroring the gnark path:

```go
// After IsOnCurve() check in cloudflare/bn256.go G2.Unmarshal:
if !e.p.IsInSubGroup() {
    return nil, errors.New("bn256: point not in correct subgroup")
}
```

`twistPoint` in the cloudflare library already exposes the group order, so a scalar-multiplication check (`r·Q == ∞`) is straightforward. Alternatively, unify both paths to use gnark on all architectures and remove the cloudflare fallback entirely.

---

### Proof of Concept

1. Compute a BN254 G2 cofactor element `T`: pick any twist-curve point `Q` in the prime-order subgroup and compute `T = h₂ · Q_random − (h₂ · Q_random projected to subgroup)`, or directly use a known cofactor-order test vector.
2. Serialize `T` as 128 bytes (EVM G2 encoding).
3. Prepend a valid G1 generator point (64 bytes) to form a 192-byte pairing input.
4. Submit a transaction calling address `0x08` with this input.
5. On an amd64/arm64 node: `newTwistPoint` → `gnark.G2.Unmarshal` → `IsInSubGroup()` fails → precompile returns error → CALL returns `(0, "")`.
6. On a non-amd64/non-arm64 node: `newTwistPoint` → `cloudflare.G2.Unmarshal` → only `IsOnCurve()` checked → passes → `PairingCheck` → `finalExponentiation(miller(T,P)).IsOne()` → `true` → CALL returns `(1, true32Byte)`.
7. Assert that the two nodes produce different transaction receipts and state roots for the same transaction.
