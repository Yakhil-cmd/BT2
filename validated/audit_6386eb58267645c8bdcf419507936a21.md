### Title
Double-counting of Bitcoin L1 lockup outputs across multiple `register-for-bond` calls due to per-call-only outpoint deduplication - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`verify-l1-lockups`/`validate-l1-lockup` in `pox-5.clar` only deduplicates Bitcoin lockup outpoints within the single list submitted in one call (via a local `seen-outpoints` accumulator capped at 10 entries), rather than against a persistent, contract-wide record of previously-consumed outpoints.

### Finding Description
`validate-l1-lockup` builds up `seen-outpoints` purely as an in-memory fold accumulator that starts empty on every invocation of `verify-l1-lockups`: [1](#0-0) 
and the duplicate check only looks at that same call's accumulator: [2](#0-1) 

The proof verifies that a Bitcoin output (script, amount, unlock height, header, merkle inclusion) is a genuine on-chain lockup output paying the staker's timelock script, and sums `amount` across all outputs supplied in the call to produce the sats credited toward the bond: [3](#0-2) 

Nothing in the reviewed code persists which outpoints have already been credited across separate `register-for-bond` invocations (no map keyed on `{txid, output-index}` marking an outpoint as consumed was found anywhere in `pox-5.clar`). Because the same Bitcoin lockup transaction/output remains spendable-looking on L1 (it is never actually spent by this call — this is a *proof of lockup*, not a UTXO consumption), a staker (or, via `register-for-bond`'s allowed-contract-caller path, another wallet acting for them) can submit the exact same lockup proof in multiple separate `register-for-bond` calls — e.g. registering for two different `bond-index` values, or re-registering after a rollover — and have the same underlying sats counted as backing collateral for more than one bond position simultaneously.

### Impact Explanation
This breaks the equality "sats credited by an L1 proof == sats actually locked on Bitcoin for that specific bond." A single BTC lockup can be double-counted to inflate the staker's/bond's `amount-sats`, which feeds directly into shares (`total-shares-staked-for-cycle`, `signer-shares-staked-for-cycle`, `staker-shares-staked-for-cycle`) and hence into reward distribution (`calculate-rewards`) and signer-set weight. That is unbacked minting of stacking weight/reward entitlement — Critical per the rules ("sats credited by an L1 proof that were never locked on Bitcoin" / "double-counting a commitment").

### Likelihood Explanation
I could not fully trace `register-for-bond`'s complete body (map writes, per-bond-index restrictions, or any global outpoint-tracking map) within the available context/iterations, so I cannot rule out that some other part of the contract enforces global uniqueness of the outpoint (e.g., a `define-map` I did not locate). The dedup logic that *is* visible (`seen-outpoints`) is explicitly scoped to a single call, and no cross-call persistence mechanism for outpoints was found via targeted searches (`consumed-l1-lockups`, `l1-lockup-consumed`, `define-map.*lockup`) across the repo. This leaves meaningful uncertainty about whether a global check exists elsewhere in the ~2100+ line contract that I was not able to inspect in full.

### Recommendation
Add a persistent `define-map` keyed by `{txid, output-index}` (or the full outpoint) recording that an L1 lockup has been consumed by a specific bond/staker, and check+set that map inside `validate-l1-lockup` (or immediately after `verify-l1-lockups` succeeds in `register-for-bond`), rejecting with a new error if the outpoint was already claimed in any prior call.

### Proof of Concept
1. Staker creates one Bitcoin lockup output `O` to their timelock script per `construct-lockup-output-script`, sized to satisfy the bond minimum.
2. Staker calls `register-for-bond` for `bond-index = A`, submitting `O` in `outputs`; `validate-l1-lockup` verifies it and credits `amount-sats` toward bond `A`.
3. Staker (or an allowed contract-caller) calls `register-for-bond` again for `bond-index = B` (or re-registers/rolls over), submitting the same `O` again. Because `seen-outpoints` resets per call and no global map is checked, `validate-l1-lockup` re-verifies the same proof and credits the same sats again toward bond `B`.
4. The staker now has sats-backed shares counted in two bonds' reward/signer-weight accounting from a single real BTC lockup.
