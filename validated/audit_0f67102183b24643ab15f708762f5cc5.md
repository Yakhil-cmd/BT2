## Title
Stack-scoped API tokens can read CCMenu status of any stack — `stack` authorization scope bypassed in `Api::CCMenuController` (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController` enforces that a stack-scoped `ApiClient` (an `ApiClient` record with `stack_id` set) can only touch the specific `Stack` it was created for, by resolving the target stack through a scoped `stacks` relation. `Api::CCMenuController` overrides the `stack` accessor and resolves the target directly from `Stack.from_param!(params[:stack_id])`, bypassing that scoping entirely, so a stack-scoped token authorized for one stack can be replayed against the CCMenu endpoint with a different `stack_id` to read another stack's build/deploy status.

### Finding Description
`Api::BaseController` defines the authorization-scoping binding that every other API controller (`CommitsController`, `Api::StacksController`, etc.) relies on: [1](#0-0) 

`stacks` restricts the queryable set to the client's own `stack_id` when the `ApiClient` is stack-scoped, and `stack` resolves the requested `params[:stack_id]` only within that restricted set — this is the intended equality: `token.stack_id == stack.id` (or the token is unscoped/global).

`Api::CCMenuController`, however, redefines `stack` to bypass this scoping and resolve directly against the whole `Stack` table: [2](#0-1) 

The permission check performed by `require_permission :read, :stack` only validates that the token carries the `read:stack` permission string; it never validates which stack the token is scoped to: [3](#0-2) 

Because `CCMenuController#stack` never goes through `stacks` (the `current_api_client.stack_id?`-gated relation), the binding "the stack a token authorizes" vs. "the stack the request actually touches" is broken: any valid `read:stack` token — even one deliberately scoped to a single stack via `CCMenuUrlController`/`ApiClient#stack` — can be replayed with an arbitrary `stack_id` in the URL to read another stack's CI status. [4](#0-3) 

The rendered response (`shipit/ccmenu/project.xml.builder`) discloses stack name, merge/lock status, last deploy activity, timing, build label, and a link to the stack page — deploy/task state that the token holder was never granted access to: [5](#0-4) 

Compare with the correctly-scoped sibling controller, which resolves `stack` through the inherited, client-scoped method: [6](#0-5) 

### Impact Explanation
This is an authorization-scope escape: a credential intentionally minted for read access to a single stack (e.g. the "CCMenu Client" token users embed in CI dashboard tools, per `CCMenuUrlController`) can be used to read build/deploy status for every other stack hosted on the same Shipit instance, simply by changing the `stack_id` path segment. This matches the High-impact category of unauthenticated/unauthorized read of stack state and deploy output, since the token was never authorized for the stacks it can now read.

### Likelihood Explanation
Likelihood is meaningful: any holder of a legitimately-issued, stack-scoped `read:stack` API token (which is routinely embedded in CI status URLs, e.g. CCTray/CCMenu dashboard configs, and is not treated as highly sensitive since it's "read only" for one project) can trivially exploit this by editing the `stack_id` in the request URL — no additional credentials, signature, or privilege are required.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (and the `authenticate_api_client` override's interaction with it), and instead resolve the target stack through the inherited, client-scoped `stacks`/`stack` methods from `Api::BaseController`, so a stack-scoped token can never resolve a stack outside its `stack_id`. If `Stack.from_param!(params[:stack_id])` must be kept for URL compatibility, explicitly verify `current_api_client.stack_id.blank? || current_api_client.stack_id == resolved_stack.id` before rendering.

### Proof of Concept
1. As a Shipit user, visit a stack's settings and fetch its CCMenu URL via `CCMenuUrlController#fetch` for `stack A`. This mints (or reuses) an `ApiClient` scoped only to `stack A` with `permissions: ['read:stack']`.
2. Take the returned `token` query parameter from that URL.
3. Issue `GET /api/stacks/<owner>/<repo-B>/<environment-B>/ccmenu?token=<token from step 2>` for an unrelated `stack B`.
4. Observe `200 OK` with `stack B`'s build status/label/activity in the XML body, even though the token's `ApiClient#stack_id` is scoped to `stack A` only — demonstrating the broken `token.stack_id == requested_stack.id` binding enforced everywhere else in `Api::BaseController` but bypassed here.

# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
