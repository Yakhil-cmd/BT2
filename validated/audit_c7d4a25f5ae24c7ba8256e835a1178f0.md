### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while every event handler resolves and mutates state using the attacker-controlled `repository.full_name` field, allowing a legitimate multi-tenant organization to forge writes against another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate the HMAC signature against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . Every event handler, however, resolves the target `Repository`/`Stack` from a *different* field in the same JSON body: `payload.dig('repository', 'full_name')` [3](#0-2) , used by `Repository.from_github_repo_name` [4](#0-3)  and by all `PullRequest` handlers (`OpenedHandler`, `ReopenedHandler`, `ClosedHandler`, `LabelCapturingHandler`, etc.) [5](#0-4)  and by `PushHandler` (via `Handler#stacks`) [6](#0-5) .

### Finding Description
Shipit supports true multi-tenant configuration: `Shipit.github(organization:)` looks up a distinct GitHub App config (its own `app_id`, `installation_id`, and — critically — its own `webhook_secret`) per organization key in `secrets.github` [7](#0-6) . This means org "A" and org "B" can be onboarded onto the same Shipit instance with two independently-created GitHub Apps and two independently-known `webhook_secret` values.

The webhook endpoint is unauthenticated by session/CSRF (`skip_before_action :verify_authenticity_token`) and only gated by the HMAC check [8](#0-7) . The organization used to pick which secret verifies that HMAC is taken from `repository.owner.login`/`organization.login` in the *request body itself* [2](#0-1) . Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the *entire, still attacker-controlled* body to the handler [9](#0-8) . Handlers never re-check that `repository.full_name`'s owner matches the organization whose secret was used to authenticate the request — they independently look up `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [4](#0-3)  and act on whatever `Stack`/`Repository` that resolves to.

This breaks the intended equality: `organization-that-authenticated == organization-owning-the-repository-being-written`. An org that legitimately owns a GitHub App configured in Shipit (and therefore knows/can generate a valid signature with *its own* `webhook_secret`) can POST directly to `/webhooks` with `repository.owner.login` (or `organization.login`) set to itself (so the correct secret is selected and the signature passes) while setting `repository.full_name` to `victim-org/victim-repo`, causing handlers to act on a completely unrelated tenant's stack.

### Impact Explanation
Concretely reachable cross-repository writes:
- `PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` on any non-archived stack under the forged `full_name` matching the forged `ref` branch [6](#0-5) , letting a foreign tenant force resynchronization/queue jobs against a victim stack it has no relationship with.
- `PullRequest::OpenedHandler#process` / `ReopenedHandler#process` will create or unarchive a victim `ReviewStack` via `ReviewStackAdapter.find_or_create!` / `stack.unarchive!` [10](#0-9) [11](#0-10) , and `ClosedHandler#process` will archive one [12](#0-11) .
- `LabelCapturingHandler`/`UnlabeledHandler` will archive/unarchive victim stacks and overwrite `pull_request.labels`/state with attacker-chosen values [13](#0-12) .

This satisfies the "cross-repository writes" Critical-impact criterion: an org whose signature validated is able to trigger writes/state transitions against a different organization's stacks that it has no authorization over.

### Likelihood Explanation
No session, `ApiClient` token, or GitHub App private key is required — only knowledge of a `webhook_secret` for *any one* organization onboarded onto the shared Shipit instance, which that organization's own operator legitimately possesses (they created that GitHub App and configured the secret). This is realistic in any deployment supporting more than one organization via the per-organization `github_app_config` mechanism [14](#0-13) . The `/webhooks` endpoint accepts arbitrary raw POST bodies with attacker-chosen headers, so crafting the forged request is trivial once one valid secret is known.

### Recommendation
After signature verification, re-derive the organization used for authentication and enforce that it matches the owner encoded in `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to handlers; reject the request otherwise. Alternatively, look up the `Repository`/`Stack` strictly within the scope of the authenticated organization rather than trusting `full_name` globally.

### Proof of Concept
1. Onboard/attacker-control organization `attacker-org` on the shared Shipit instance with its own GitHub App and known `webhook_secret_A`.
2. Craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` [1](#0-0)  and the signature validates successfully because it was computed with that org's real secret.
5. `PushHandler` resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` [6](#0-5)  and triggers `sync_github` on the victim's stack — a write the attacker's own organization never authenticated for.

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
