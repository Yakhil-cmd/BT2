### Title
`Api::CCMenuController#stack` bypasses `current_api_client.stack_id` scoping by calling `Stack.from_param!` instead of `stacks.from_param!` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` scopes all `stack`/`stacks` resolution to the authenticated `ApiClient`'s `stack_id` via the `stacks` method, but `Api::CCMenuController` overrides `stack` and calls `Stack.from_param!` directly on the unscoped `Stack` model, allowing a token scoped to one stack to read deploy/task status of any other stack.

### Finding Description
The intended binding is: for every scoped `ApiClient` (`current_api_client.stack_id?` is true), `resolved_stack.id == current_api_client.stack_id`. This is enforced generically in `Api::BaseController#stacks`/`#stack`: [1](#0-0) 

which restricts resolution to `Stack.where(id: current_api_client.stack_id)` before calling `.from_param!`.

However, `Api::CCMenuController` redefines `stack` and bypasses this scope entirely, resolving against the global `Stack` relation: [2](#0-1) 

`Stack.from_param!` itself performs no client/tenant filtering — it only matches on repository owner/name/environment parsed from `params[:stack_id]`: [3](#0-2) 

The only authorization check applied is `require_permission :read, :stack`, which just checks that the permissions array on the `ApiClient` record contains the string `"read:stack"` — it performs no comparison against `stack_id`: [4](#0-3) [5](#0-4) 

So an `ApiClient` scoped to stack A, with `read:stack` permission and a valid token, can request `GET /api/stacks/<owner>/<repo>/<env-of-stack-B>/ccmenu.xml?token=<tokenA>` (the controller even overrides `authenticate_api_client` to accept the token via query param instead of Basic Auth) and successfully resolve and render stack B's latest deploy/rollback status, bypassing the `stack_id` restriction entirely.

`verify_signature`, `force_github_authentication`, and the `stacks` scope in `BaseController` do not help here because this controller action never calls the scoped `stacks` method — it defines its own `stack` method that shadows the parent's.

### Impact Explanation
An attacker holding any token scoped to one stack (which they could legitimately be issued, e.g. as a low-privilege integration for a single repository) can read the deploy/task state (`show` action renders `deploys_and_rollbacks.last`, exposing deploy id and status in CCMenu XML format) of **any** other stack in the Shipit instance, including stacks belonging to other repositories/tenants they have no permission for. This is an unauthenticated-relative-to-target read of stack state, matching the High severity bucket ("unauthenticated read of stack state, task streams or deploy output") — arguably Critical-adjacent since it is a direct authorization bypass of a `current_api_client.stack_id` scope, letting one repository's payload/token read another repository's stack status. It is trivially repeatable against any stack in the instance since `stack_id` in the URL can be any owner/repo/environment string.

### Likelihood Explanation
Preconditions: `Shipit.disable_api_authentication` is false (default), and the attacker possesses a valid, legitimately-scoped `ApiClient` token with `read:stack` permission (a realistic and common configuration for CI integrations). No GitHub secrets, session, or elevated role is required. The attacker only needs to know or guess the target's `owner/repo/environment` path segment, which is commonly discoverable (public repo names). This makes the attack cheap, deterministic, and fully repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection instead of the unscoped `Stack` model:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Audit all other `BaseController` subclasses for similar direct `Stack.from_param!`/`Stack.find` calls that bypass `stacks`.

### Proof of Concept
Minitest plan (functional test) under `test/controllers/api/ccmenu_controller_test.rb`:
1. Create `stack_a` and `stack_b` (different repositories/environments).
2. Create `api_client = shipit_api_clients(:scoped_to_stack_a)` (or build one) with `stack_id: stack_a.id`, `permissions: ['read:stack']`.
3. Assert the binding before tracing: `api_client.stack_id == stack_a.id` and `api_client.stack_id != stack_b.id`.
4. Create a deploy on `stack_b` so it has distinguishable state.
5. `get ccmenu_api_stack_url(stack_b), params: { token: api_client.authentication_token }`.
6. Assert `response.status == 200` and response body contains `stack_b`'s deploy id/status — proving cross-stack read succeeded despite `api_client.stack_id == stack_a.id`.
7. Contrast with `Api::StacksController#show` (uses inherited `stack`/`stacks`) where the same request against `stack_b` correctly raises `ActiveRecord::RecordNotFound` (404), demonstrating the divergence is specific to `CCMenuController`'s override.
