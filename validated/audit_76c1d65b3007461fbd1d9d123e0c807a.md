### Title
TOCTOU race in private-payment doublespend/duplicate check allows double-spend of a private output - ([File: private_payment.js])

### Summary
Validation of a privately-transferred (blackbytes-style) payment chain checks the source output for duplicates/spend-proofs and then writes the spend in a single DB transaction, but this transaction is opened per-request on its own pooled connection without any address- or output-level mutex being held, unlike the public unit-validation path which serializes on `mutex.lock(arrAuthorAddresses, ...)`.

### Finding Description
The public/joint validation path in `validation.js` serializes every check-then-write sequence for a given set of author addresses behind `mutex.lock(arrAuthorAddresses, ...)` [1](#0-0) , so no two units by the same author(s) can be concurrently validated and see stale double-spend/duplicate state.

The private-payment path does not use this mechanism. `validateAndSavePrivatePaymentChain` in `private_payment.js` takes a fresh connection from the pool, issues `BEGIN`, performs a duplicate-output check (`SELECT ... FROM outputs WHERE unit=? AND asset=? AND message_index=?`), and only afterward calls into `divisibleAsset`/`indivisibleAsset` `validateAndSavePrivatePaymentChain`, which further validates spend proofs against the `spend_proofs` table and then inserts inputs/outputs and marks the source output `is_spent=1` — all inside that same open transaction [2](#0-1) . No `mutex.lock` on the author address(es) or on the spent output is acquired before or during this check-then-write window (the `mutex.lock(["private_write"])` in `validatePaymentInputsAndOutputs`/`checkInputDoubleSpend` is only taken in the branch that "accepts" an already-detected doublespend, i.e., after a conflicting unit was found on a different unstable path — it does not protect the ordinary duplicate/spend-proof read-then-insert sequence) [3](#0-2) .

Because two private-payment chains that spend the very same source output can be submitted concurrently (e.g., by an unprivileged wallet counterparty replaying/duplicating a received private chain, or an attacker racing two chain deliveries against the node's private-payment handler), each request opens its own connection/transaction, performs its own `SELECT` (finding the output not yet marked spent and no conflicting `spend_proofs` row), and only commits afterward. Depending on the storage engine's transaction isolation (this is exploited in a race window rather than depending on a specific isolation level), both transactions can pass the "not yet spent" check before either commits its `INSERT ... is_spent=1` write, analogous to the screen TOCTOU where the check (owner PID) and the privileged action (signal) are separated by a window in which the state can change.

This mirrors the CVE's bug class: a check ("is this output/PID still valid to act on") is performed, but the actual privileged action (mark spent / send signal) happens later without holding the lock that would make the check atomic with the action.

### Impact Explanation
If the race succeeds, the same private output can be accepted as an input in two independent private-payment chains, each of which is written to the local database as valid ("double-spend of a stable/serial output"). This directly allows unauthorized double-spending of a private asset, since the two receiving counterparties would each hold a locally-validated, saved payment chain for the same funds — an outcome the double-spend protection in the public path (protected by `mutex.lock`) is designed to prevent.

### Likelihood Explanation
Exploitability requires the attacker (a private-payment counterparty who controls when and how many chains they submit) to fire the same private chain, or two conflicting chains spending the same output, concurrently at the node's private-payment handling entry point so that both requests are validated before either commits. This is plausible for a local wallet-to-wallet or hub relaying private payments to a light node, since nothing in `private_payment.js`/`divisible_asset.js`/`indivisible_asset.js` prevents concurrent invocations for the same output, in contrast to the explicit mutex used for regular units.

### Recommendation
Serialize private-payment validation-and-save the same way ordinary units are: acquire a `mutex.lock` keyed by the spent output(s) (e.g., `unit-message_index-output_index` or the author addresses) before performing the duplicate/spend-proof checks in `private_payment.js`, and release it only after the transaction commits/rolls back — mirroring the pattern already used for regular joints in `validation.js`.

### Proof of Concept
Not executable from static analysis alone; conceptually: submit the same signed private divisible/indivisible payment chain (or two different chains referencing the same `{unit, message_index, output_index}` source output) to `private_payment.validateAndSavePrivatePaymentChain` twice in rapid succession/concurrently. Each call opens its own connection, runs the duplicate-output/spend-proof `SELECT`s in `private_payment.js:62-107` and `divisible_asset.js:118-165` before either has committed its `INSERT ... is_spent=1`, so both can reach `callbacks.ifOk()` and be persisted, producing two valid spends of the same source output.

*Note: I was unable to fully confirm the exact isolation-level behavior of the specific SQL backend (SQLite vs MySQL) in this deployment, which affects how wide the race window is in practice; this would need to be verified in a running environment.*
