## Title
Asset issuer can permanently freeze every holder's funds by rotating the attestor list of a `spender_attested` asset - ([File: validation.js])

## Summary
Any user can issue an asset in ocore with `spender_attested: true`. This asset type gates every payment (and even a sender's own change output) on the counterparty address holding a currently valid attestation from one of the asset's registered attestors. The list of attestors is fully and unilaterally controlled by the asset's `definer_address` via the single-authored `asset_attestors` message, at any time after issuance, with no minimum attestor requirements, no timelock, and no way for anyone else to intervene. This mirrors the Napier `M-8` pattern precisely: a single privileged party (there, the rebalancer/admin; here, the asset definer) controls a parameter that gates users' ability to move their own funds, and can flip it to an unreachable value at will, permanently bricking withdrawals/transfers for every legitimate holder.

## Finding Description
When an asset is defined with `spender_attested: true`, the definer supplies an initial, non-empty, sorted list of `attestors` [1](#0-0) . The definer can subsequently replace this list at will by broadcasting a single-authored `asset_attestors` message; the only requirement is `objUnit.authors[0].address === objAsset.definer_address` and that the new list is non-empty and passes `checkAttestorList` [2](#0-1) .

At payment-validation time, for `spender_attested` assets, **every output address of the payment** (not just the recipient - also the sender's own change output) must appear in the currently attested set, or the whole payment is rejected: [3](#0-2) 

The issuer/spender-side check is enforced similarly for issuance and multi-author inputs: [4](#0-3) 

`filterAttestedAddresses` determines "attested" purely by whether an attestation from a *currently listed* attestor exists for that address, after the most recent `address_definition_changes` — so attestations issued under a previous attestor list, or attestations that will never come because the new attestor set is composed of addresses that never attest anyone, simply do not count anymore: [5](#0-4) 

Because the check applies to the sender's own change output as well, once the definer swaps the attestor list to attestors that will never attest any address, **no holder of the asset can construct a valid spend at all** — not even to send it back to themselves or to the definer's own address (unless the entire coin is sent in one output straight to the definer without change, which is not always possible or desired, and does not restore normal usability). There is no permissionless path to re-attest, no fallback attestor set, and no expiry/failsafe in the protocol: the definer's single message is instantly and unconditionally binding on all current and future holders' spendability.

## Impact Explanation
This lets a malicious or compromised asset issuer permanently freeze the funds of every current holder of a `spender_attested` asset, at zero cost, with a single low-fee unit (`asset_attestors`). Unlike a poorly designed but bounded parameter, there is no way for holders, other attestors, or the network to recover: the check is baked into core payment validation (`validation.js`) and evaluated freshly against the live attestor list on every subsequent attempt to spend. This is a direct analog to the Napier `M-8` finding, which was ruled Medium severity specifically because a role able to reconfigure a live parameter (there, rebalancer/buffer) could, without stealing funds, indefinitely deny users the ability to withdraw/transfer their own assets. Here, the "asset issuer" role (explicitly one of the reachable, non-privileged on-chain actors) can achieve the same DoS-of-withdrawal outcome against holders of any asset they define, via a documented but unrestricted protocol feature with no rate-limit, quorum, or recovery mechanism.

## Likelihood Explanation
Any full or light wallet user can issue a `spender_attested` asset and later publish an `asset_attestors` update — this requires only a single signature from the definer address and a single confirmed unit; no special permissions, additional consensus, or high cost are needed. Any protocol/dApp that distributes attestation-gated assets to third parties (e.g., regulated/KYC-style tokens) is exposed the moment holders acquire the asset and the definer decides (maliciously, or is compromised) to swap attestors.

## Recommendation
- Require that attestor-list changes cannot instantly invalidate the attestations of addresses that were validly attested at the time they received the asset (e.g., grandfather existing attested addresses until they explicitly opt out, or require a timelock/delay before a new attestor list becomes binding on already-issued outputs).
- Do not require the sender's own change output to satisfy the attestor check — only the actual transfer recipient(s) should need attestation, so a holder can always at least consolidate/return funds to themselves.
- Consider allowing multiple independent attestors to be "sufficient" (any one valid attestation) rather than requiring the currently configured, definer-controlled set, and/or provide a permissionless/no-definer fallback attestor path analogous to the "make `requestWithdrawal` permissionless" recommendation from the referenced report.

## Proof of Concept
1. Issuer creates asset `A` with `spender_attested: true` and `attestors: [X]`, where `X` is an attestor the issuer controls [1](#0-0) .
2. `X` attests several holder addresses (`H1`, `H2`, ...), who then legitimately acquire and hold asset `A`.
3. Issuer (the `definer_address`) broadcasts an `asset_attestors` message replacing the attestor list with `[Y]`, where `Y` is an address that will never attest anyone (validated solely by `checkAttestorList`, single signature from definer) [6](#0-5) .
4. Any `H_i` attempts to spend asset `A` (even a self-payment to consolidate change). `filterAttestedAddresses` checks the output addresses against attestations issued by `Y` — none exist and none will ever be created — so `validatePaymentInputsAndOutputs` rejects the payment with "some output addresses are not attested" [3](#0-2) .
5. All existing holders' balances of asset `A` are now permanently unspendable; there is no on-chain path to restore attestation without the definer's cooperation.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
