### Title
API token stack-scope bypass in CCMenu endpoint allows cross-stack unauthorized read - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::ApiClient` tokens can be scoped to a single stack via `stack_id` (see fixture `here_come_the_walrus`, scoped to stack `shipit`, with permission `read:stack` only). This binding — "the stack a token authorizes" must equal "the stack the request touches" — is enforced in `Shipit::Api::BaseController#stack`/`#stacks`, but `Shipit::Api::CCMenuController` completely overrides the `stack` method and re-implements authentication without ever applying that scoping check, allowing any holder of a stack-scoped token to read CCMenu status for **any** stack in the installation, not just the one the token was issued for.

### Finding Description
`BaseController` defines the binding between an authenticated `ApiClient` and the stacks it may touch: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the token is scoped, and `stack` resolves `params[:stack_id]` only within that restricted scope. Every controller inheriting this default `stack` method (e.g. `Shipit::Api::DeploysController`, `Shipit::Api::StacksController`) is therefore bound by: `token.stack_id == nil || token.stack_id == requested_stack.id`.

`CCMenuController`, however, overrides both `authenticate_api_client` (to allow a `?token=` query param, for legacy CCMenu clients) and `stack` itself: [2](#0-1) 

Its `stack` implementation calls `Stack.from_param!(params[:stack_id])` directly — bypassing `stacks`/`current_api_client.stack_id` entirely. The only remaining check is `require_permission :read, :stack`, which is enforced via `ApiClient#check_permissions!`: [3](#0-2) 

This check is purely permission-string based (`"read:stack"` present in `permissions`) and carries no notion of *which* stack. So a token that is scoped to stack A but still carries `read:stack` in its `permissions` array is fully capable, at the `CCMenuController` level, of reading stack B, C, etc., because the stack-binding equality that `BaseController#stack` enforces for every other endpoint is silently dropped here.

Before the flaw is exploited: `token.stack_id == A`, and per the documented intent (and the `here_come_the_walrus` fixture, `stack: shipit`) the token should only ever resolve `stack` to `A`.
After exploitation: the same token, sent to `GET /api/:stack_id/cc.xml?token=<token>` with `stack_id = B`, resolves `@stack` to `B`, breaking `token.stack_id == request.stack.id`.

### Impact Explanation
This is an authenticated-but-unauthorized cross-stack information disclosure: a token holder restricted to one stack can enumerate/read `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` for every other stack managed by the Shipit instance, including locked/private stacks, via the CCMenu XML feed rendered in `show`: [4](#0-3) 

This matches the "unauthenticated/unauthorized read of stack state" High-impact category: the attacker did not receive an increase in raw permissions, but the scope binding meant to constrain a legitimately-issued, narrowly-scoped credential is bypassed for this specific controller.

### Likelihood Explanation
Requires possession of any valid `ApiClient` token that includes `read:stack` in its permission list and is stack-scoped (a normal, supportable configuration per the `stack:` column and the `here_come_the_walrus` fixture) — no privileged account or session is needed beyond that token, which is a routine, low-privilege credential intentionally distributed to CI/monitoring tools. The bypass is a simple `stack_id` URL parameter substitution.

### Recommendation
Remove the custom `stack` override in `CCMenuController`, or reintroduce the same scoping check used in `BaseController#stacks` (i.e., resolve the stack from `current_api_client.stack_id`-restricted collection rather than an unrestricted `Stack.from_param!`), so that a stack-scoped token can never resolve a stack outside its `stack_id`.

### Proof of Concept
1. Create `ApiClient` `token_A` with `stack_id = stack_A.id`, `permissions = ['read:stack']` (mirrors fixture `here_come_the_walrus`).
2. Confirm scoping works elsewhere: `GET /api/stack_A/deploys` succeeds; `GET /api/stack_B/deploys` with `token_A` returns 404 via `stacks.from_param!` (because `stacks` is `Stack.where(id: stack_A.id)`).
3. Call the CCMenu endpoint for a *different* stack with the same token:
   `GET /api/stack_B/cc.xml?token=<token_A.authentication_token>`
4. Observe HTTP 200 with `stack_B`'s CCMenu XML (`name`, `lastBuildStatus`, etc.) returned, because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!`, and `authenticate_api_client`/`require_permission :read, :stack` never re-validate that `stack_B.id == token_A.stack_id`.
