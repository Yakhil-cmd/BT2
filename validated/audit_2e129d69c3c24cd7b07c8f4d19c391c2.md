### Title
Unbounded, unpriced `changes` / `EXPERIMENTAL_changes` RPC allows free multi-account state-change disk scans - ([File: chain/chain/src/store/mod.rs])

### Summary
The `changes` RPC method accepts a `StateChangesRequestView` containing an arbitrary-length `account_ids: Vec<AccountId>` (or `keys: Vec<AccountWithPublicKey>`), which is parsed with no size cap and then used to perform one RocksDB prefix/range scan per account/key in `ChainStore::get_state_changes`. This mirrors the reported in3-server bug class: an unauthenticated client sends a single request containing an array of items, each of which triggers an independent, uncapped unit of server-side work, for zero cost.

### Finding Description
`RpcStateChangesInBlockByTypeRequest::parse` simply forwards to `Params::parse(value)` with no validation of the number of `account_ids`/`keys` in the request: [1](#0-0) 

The request type itself imposes no bound: [2](#0-1) [3](#0-2) 

Once parsed, `ChainStore::get_state_changes` iterates the entire `account_ids`/`keys` list and, for each entry, performs a RocksDB prefix scan (`find_iter`/`find_exact_iter`) over the state-changes column for the requested block: [4](#0-3) 

Only the *empty* case is short-circuited before hitting the view client / disk; a non-empty request of any size proceeds to resolve the block and scan storage once per account/key: [5](#0-4) 

By contrast, other array-shaped RPC inputs in the same codebase are explicitly bounded — e.g. `BlockHeadersRequest` is capped via `sync::header::MAX_BLOCK_HEADERS`, and `EXPERIMENTAL_view_state` pagination is capped via `MAX_VIEW_STATE_PAGE_ITEMS` / `MAX_VIEW_STATE_PAGE_BYTES`: [6](#0-5) [7](#0-6) 

`changes`/`EXPERIMENTAL_changes` has no analogous cap on the `account_ids`/`keys` array length. This is precisely the bug class described in the external report: a free-to-send request whose array input controls the amount of internal server work performed (one internal storage scan per array element), with no limit on array size and no cost to the requester — analogous to `in3.sign([{blockNumber:i} for i in range(200)])` triggering 200 unpriced internal operations.

### Impact Explanation
Any unauthenticated RPC client can submit a single `changes` request with a very large `account_ids` array (bounded only by the 10MB JSON body limit, which still permits hundreds of thousands of short account IDs), causing the RPC/view-client node to perform a correspondingly large number of RocksDB prefix scans for a single incoming request. Because there is no per-item cost, gas charge, or rate limit tied to array length, a small number of requests can consume disproportionate CPU/I/O on the node, degrading RPC availability for legitimate users (denial of service on the RPC/view-client path). This does not directly cause token theft or state divergence, but it is a concrete "free or underpriced execution" / "unbounded resource use" condition reachable directly from an RPC request.

### Likelihood Explanation
High likelihood of triggerability: the `changes` endpoint is a standard, publicly documented JSON-RPC method with no authentication, and constructing a request with thousands of account IDs is trivial for any client. The only practical constraints are the JSON payload size limit (default 10MB) and network bandwidth, both of which still permit large enough arrays to cause many storage scans per request, and the request can be repeated at will.

### Recommendation
Enforce an explicit maximum on the number of `account_ids` / `keys` entries accepted in `StateChangesRequestView` at parse time (in `RpcStateChangesInBlockByTypeRequest::parse` / `chain/jsonrpc/src/api/changes.rs`), analogous to `MAX_BLOCK_HEADERS` and `MAX_VIEW_STATE_PAGE_ITEMS`, rejecting oversized requests with a validation error before any block resolution or storage scan occurs. Consider also bounding total scanned changes returned per request/page.

### Proof of Concept
Send a single `changes` JSON-RPC request such as:
```
POST /
{
  "jsonrpc": "2.0",
  "id": "dontcare",
  "method": "changes",
  "params": {
    "block_id": <recent_block_hash>,
    "changes_type": "account_changes",
    "account_ids": ["acc0.test","acc1.test", ... /* tens of thousands of entries */]
  }
}
```
Per `get_state_changes`, this causes the node to perform one `find_exact_iter` RocksDB scan per listed account_id for the given block, all within a single unauthenticated, unpriced request, as shown in `chain/chain/src/store/mod.rs` lines 690-699 and reachable via the "changes"/"EXPERIMENTAL_changes" route documented in `chain/jsonrpc/RPC_ARCHITECTURE.md` lines 139-141.
