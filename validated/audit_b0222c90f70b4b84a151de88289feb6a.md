### Title
Fork-controlled `SHELL` env var reaches `Command#unbundled_env`/`PTY.spawn` via unfiltered `ReviewStack#env` labels and `DeploySpec#machine_env` - ([File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb])

### Summary
`ReviewStack#env` merges every PR label name, upcased, directly into the stack's environment hash with no allow-list, and `TaskCommands#env` further merges `deploy_spec.machine_env` (sourced from the fork's own `shipit.yml`) with no allow-list either. Both paths bypass `EnvironmentVariables#permit`, which is only ever applied to `@task.env` via `filter_deploy_envs`/`filter_rollback_envs`, not to labels or `machine_env`. The resulting hash is passed to `Command.new(env: ...)`, and `Command#unbundled_env` merges `@env` last, so any attacker-supplied key — including `SHELL` — overrides the base environment used by `PTY.spawn`.

### Finding Description
The broken binding is: the set of keys reaching `Command#unbundled_env` should equal the whitelisted set returned by `EnvironmentVariables#permit(variable_definitions)`, i.e. `unbundled_env.keys ⊆ allowed_variables`. In practice this does not hold for two merge points.

1. `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
```
super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
```
Every label on the PR becomes an env key with no filtering. If a PR label is `shell`, the stack env gains `"SHELL" => "true"`.

2. `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) builds the deploy/task environment as:
```
super.merge(@stack.env).merge({...}).merge(deploy_spec.machine_env).merge(@task.env)
```
`@stack.env` (containing the label-derived keys) and `deploy_spec.machine_env` (`app/models/shipit/deploy_spec.rb:69-71`, sourced from the checked-out `shipit.yml`'s `machine.environment` key) are merged with no call to `EnvironmentVariables.with(...).permit(...)`. Only `filter_deploy_envs`/`filter_rollback_envs` (`app/models/shipit/deploy_spec.rb:174-180`) apply `permit`, and they are used elsewhere for `@task.env`, not for `@stack.env` or `machine_env`.

This merged hash is passed as `env:` into `Command.new` (used by `perform`/`install_dependencies`), stored as `@env` (`lib/shipit/command.rb:31-37`). `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) computes:
```
BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
```
`@env` is merged last, so any attacker-controlled key — `SHELL`, `PATH`, etc. — overrides the base/sanitized environment. This hash is fed directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (`lib/shipit/command.rb:92`), which uses `SHELL`/`PATH` to resolve how the step's command line is interpreted/located.

For a repository with `provisioning_behavior = allow_all`, an unprivileged fork PR is provisioned into a `ReviewStack` regardless of labels (per the settings help text, "the provisioning label has no effect... ALL Pull Requests dynamically provision stacks" - `app/views/shipit/repositories/settings.html.erb:22-24`), so no special permission is needed for the stack to be created and deployed. The attacker then needs a PR label named `shell` (or `path`) applied to their PR, or simply ships a `shipit.yml` under their fork with `machine: { environment: { SHELL: "/tmp/attacker" } }` — the latter requires no elevated GitHub permission at all, since the fork's own `shipit.yml` is read from the checked-out commit.

None of the existing guards intercept this: `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb`) is never invoked on `@stack.env` or `deploy_spec.machine_env`; there is no repository/stack validation restricting `machine.environment` keys; and `provision?` precedence under `allow_all` does not gate on label content at all.

### Impact Explanation
An attacker who can get a PR opened (or merely pushes a fork branch containing a crafted `shipit.yml`) against a repository configured with `provisioning_behavior: allow_all` and `review_stacks_enabled: true` can inject `SHELL` (and other env vars) into the deploy/task command execution environment for the review stack. Since `PTY.spawn` uses this environment, redirecting `SHELL` (or manipulating `PATH`) changes how each deploy step is interpreted, allowing arbitrary command execution on the Shipit deploy host under the Shipit service account. This matches the Critical RCE-on-deploy-host impact category. The blast radius is scoped to the repository whose review stack is provisioned, but is repeatable for every PR against any `allow_all` repository.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled: true` and `provisioning_behavior: allow_all`, and the attacker must be able to open a PR from a fork containing a `shipit.yml` with `machine.environment.SHELL` set (fully within an unprivileged contributor's control — no maintainer action or secret required), OR get a `shell`-named label applied to the PR. The `machine_env` route requires zero privilege beyond opening a PR, making this highly feasible and repeatable at will.

### Recommendation
- In `ReviewStack#env`, do not merge raw label names as arbitrary env keys; use a fixed, prefixed, or explicitly allow-listed representation (e.g., `LABEL_<name>`) and never allow it to collide with reserved/sensitive variable names like `SHELL`, `PATH`, `IFS`, `LD_PRELOAD`, etc.
- In `DeploySpec#machine_env` / `TaskCommands#env`, run `machine_env` and `@stack.env` through `EnvironmentVariables#permit` (or an explicit deny-list of dangerous keys such as `SHELL`, `PATH`, `IFS`, `BASH_ENV`, `LD_PRELOAD`) before merging into the command environment.
- In `Command#unbundled_env`, explicitly strip/pin dangerous keys (`SHELL`, `PATH`) from `@env` so they cannot be overridden by any caller-supplied hash, merging them last instead of first.

### Proof of Concept
```ruby
# test/unit/task_commands_env_test.rb (conceptual, no live GitHub)
test "fork-controlled SHELL reaches Command#unbundled_env via ReviewStack env/machine_env" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  review_stack = shipit_review_stacks(:review_stack) # or build one via factory
  pull_request = review_stack.pull_request
  pull_request.update!(labels: ["shell"]) # attacker-added label -> env["SHELL"]

  # LHS: expected safe binding
  allowed_keys = review_stack.cached_deploy_spec.deploy_variables.map(&:name)

  # RHS: actual keys reaching the spawned process
  task = shipit_deploys(:review_stack_deploy) # deploy/task belonging to review_stack
  commands = TaskCommands.new(task)
  command = commands.perform.first

  assert_includes command.env.keys, "SHELL"          # fails the intended invariant
  refute_includes allowed_keys, "SHELL"               # SHELL was never whitelisted
  assert_equal "true", command.unbundled_env["SHELL"] # attacker value present in spawn env
end
```
This demonstrates that `SHELL` (attacker-controlled via PR label or fork `shipit.yml` `machine.environment`) is present in `Command#unbundled_env`, contradicting the intended invariant that only `EnvironmentVariables#permit`-whitelisted keys should reach the spawned process environment.
