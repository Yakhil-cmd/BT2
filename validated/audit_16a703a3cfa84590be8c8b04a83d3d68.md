Based on my research, I found a structurally analogous pattern in the newly added `pallet-assets-precompiles` EIP-2612 `permit` implementation, where the domain separator binds to a static pallet-config constant instead of any value that actually distinguishes forked/duplicated chains.

### Title
EIP-2612 `permit()` domain separator binds to a static `ChainId` constant instead of genesis/fork-derived identity, enabling signature replay across chains/forks sharing the same runtime constant - (File: `substrate/frame/assets/precompiles/src/permit.rs`)

### Summary
The `permit` pallet added to `pallet-assets-precompiles` implements EIP-2612 gasless approvals for ERC20 asset precompiles. The EIP-712 domain separator is computed with a `chainId` field sourced from `T::ChainId: Get<u64>`, a compile-time pallet configuration constant, rather than any runtime value that is uniquely re-derived per genesis/fork (e.g. `frame_system::block_hash(0)` / genesis hash). [1](#0-0) [2](#0-1) 

### Finding Description
`compute_domain_separator` builds the EIP-712 `DOMAIN_SEPARATOR` as `keccak256(DOMAIN_TYPEHASH, name_hash, version_hash, chain_id, verifying_contract)`, where `chain_id = T::ChainId::get()`. [3](#0-2) 
`permit_digest` then wraps this domain separator with the struct hash to produce the digest that the owner signs off-chain and which `use_permit`/`do_verify_permit` verify on-chain against the current stored nonce. [4](#0-3) [5](#0-4) 

`T::ChainId` is a `#[pallet::constant]` fixed in the runtime's `impl permit::Config` — it is baked into the compiled runtime and does not change if the same runtime (same constant) is instantiated on a different chain with a different genesis, and it does not change across a chain split where both branches continue running the identical runtime code. This mirrors exactly the root cause in the referenced report: `constructMsg` binds the signed payload to inputs that are stable across a chain divergence, omitting any value (like `block.chainid` in the original report, or a genesis-hash-based chain identifier here) that would differ between the two post-fork/duplicated chains. Because the nonce state (`Nonces` storage) is identical on both branches immediately after a fork/duplication, and the domain separator is also identical (same `ChainId` constant, same verifying contract, same token name), a permit signature valid on one branch is valid, unconsumed, and immediately replayable on the other branch.

This differs from ordinary Substrate extrinsic replay protection: normal signed extrinsics are protected against fork replay by `CheckGenesis`/`CheckMortality`-style `SignedExtension`s that embed the genesis hash into the extrinsic's signed payload. The `permit` mechanism operates entirely outside that protection layer — it is a self-contained EIP-712 signature scheme reachable through the `pallet-revive` ERC20 precompile's `permit()` call, with its own ad hoc "chain id" binding that is not tied to genesis/fork identity at all. [6](#0-5) 

### Impact Explanation
If the same compiled runtime constant (`T::ChainId`) is shared by two distinct chain instances — either through a contentious chain split that keeps the runtime code unchanged, or through reuse of the same EVM-style chain-id constant across separate networks derived from the same runtime template — a permit signed by a token owner intending to authorize a spender on one chain can be replayed verbatim on the other chain (same domain separator, same starting nonce), granting the spender an ERC20 allowance and enabling a subsequent `transferFrom` without the owner's consent on that other chain. This is a theft-of-allowance / unauthorized-approval impact matching the "High" impact class of the original report.

### Likelihood Explanation
Exploitation requires either (a) an actual, low-probability contentious runtime/chain fork of a parachain that preserves identical runtime code and thus identical `ChainId`/nonce state on both branches, or (b) the runtime's `ChainId` constant being reused verbatim across genuinely distinct networks (a known real-world EVM anti-pattern of chain-id collisions). Parachains under a shared relay chain governance model rarely undergo contentious forks, which reduces likelihood relative to a general-purpose EVM chain, but the code itself provides no independent binding (e.g., genesis hash) that would prevent replay if such duplication occurs — the safeguard the report calls out is simply absent here as well.

### Recommendation
Derive the EIP-712 `chainId` (or an additional domain field) from a value that is unique per genesis/fork, such as `frame_system::Pallet::<T>::block_hash(BlockNumberFor::<T>::zero())`, rather than solely from a static `Get<u64>` pallet constant, and consider adding an explicit `salt` field bound to the genesis hash in the domain separator, mirroring OpenZeppelin's `EIP712.sol` cached-domain-separator/genesis-fork-detection pattern referenced in the original report.

### Proof of Concept
No executable PoC was run. The analysis is based on static code inspection of `substrate/frame/assets/precompiles/src/permit.rs` and its tests (`permit_tests.rs`, `permit_precompile_tests.rs`), which confirm: (1) the domain separator is a pure function of `(name, "1", T::ChainId::get(), verifying_contract)` with no genesis/fork-dependent input; (2) `T::ChainId` is a compile-time `#[pallet::constant]`; (3) existing tests only verify determinism and per-verifying-contract domain separation, not resistance to cross-chain/fork constant reuse. [7](#0-6) [8](#0-7) 
I was unable to fully verify, within the available tool budget, the exact literal value assigned to `permit::Config::ChainId` in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs` (grep found 2 matches there but I could not read the surrounding lines before the session ended), so I cannot confirm whether that specific value is currently reused by another live network — this would need to be checked in a follow-up session before treating this as a confirmed cross-network collision rather than a structural weakness.

		/// Compute the EIP-712 domain separator for a given verifying contract.
		///
		/// DOMAIN_SEPARATOR = keccak256(abi.encode(
		///   keccak256("EIP712Domain(string name,string version,uint256 chainId,address
		/// verifyingContract)"),
		///   keccak256(name),
		///   keccak256("1"),
		///   chainId,
		///   verifyingContract
		/// ))
		///
		/// The `name` parameter should be the token name per EIP-2612 specification.
		pub fn compute_domain_separator(verifying_contract: &H160, name: &[u8]) -> H256 {
			let name_hash = keccak_256(name);
			let version_hash = keccak_256(b"1");
			let chain_id = T::ChainId::get();

			// Encode: typehash || name_hash || version_hash || chainId || verifyingContract
			let mut data = Vec::with_capacity(DOMAIN_SEPARATOR_ENCODED_LEN);
			data.extend_from_slice(&DOMAIN_TYPEHASH);
			data.extend_from_slice(&name_hash);
			data.extend_from_slice(&version_hash);
			// Pad chain_id to 32 bytes (big-endian)
			data.extend_from_slice(&[0u8; 24]);
			data.extend_from_slice(&chain_id.to_be_bytes());
			// Pad address to 32 bytes
			data.extend_from_slice(&[0u8; 12]);
			data.extend_from_slice(verifying_contract.as_bytes());

			H256(keccak_256(&data))

		fn do_verify_permit(
			verifying_contract: &H160,
			name: &[u8],
			owner: &H160,
			spender: &H160,
			value: &[u8; 32],
			deadline: &[u8; 32],
			v: u8,
			r: &[u8; 32],
			s: &[u8; 32],
		) -> Result<(), Error<T>> {
			// EIP-2612: owner and spender cannot be the zero address
			if owner.is_zero() {
				return Err(Error::<T>::InvalidOwner);
			}
			if spender.is_zero() {
				return Err(Error::<T>::InvalidSpender);
			}

			// Validate deadline against current timestamp.
			// EIP-2612 specifies deadlines in UNIX seconds. We use the `UnixTime`
			// trait which returns a `core::time::Duration` — its `as_secs()` method
			// gives us seconds regardless of pallet_timestamp's internal resolution
			// (which stores milliseconds, converted via `Duration::from_millis` in
			// pallet_timestamp's `UnixTime` implementation).
			let now_seconds = <pallet_timestamp::Pallet<T> as UnixTime>::now().as_secs();
			let deadline_u256 = U256::from_big_endian(deadline);
			let now_u256 = U256::from(now_seconds);

			if deadline_u256 < now_u256 {
				return Err(Error::<T>::PermitExpired);
			}

			let nonce = Self::nonce(verifying_contract, owner);
			let digest = Self::permit_digest(
				verifying_contract,
				name,
				owner,
				spender,
				value,
				&nonce,
				deadline,
			);

			let recovered = Self::ecrecover(&digest, v, r, s)?;

			if &recovered != owner {
				return Err(Error::<T>::SignerMismatch);
			}

			Ok(())
		}

/// Sign an EIP-2612 permit digest with Hardhat #0's key. Reads the
/// current on-chain nonce so the digest is valid for an immediate
/// `permit()` call. Returns `(v, r, s)` in Ethereum format
/// (v ∈ {27, 28}).
fn sign_permit(
	asset_addr: H160,
	spender: H160,
	value: AlloyU256,
	deadline: AlloyU256,
) -> (u8, [u8; 32], [u8; 32]) {
	let nonce = permit::Pallet::<Test>::nonce(&asset_addr, &HARDHAT_ACCOUNT_0);
	let value_bytes: [u8; 32] = value.to_be_bytes();
	let deadline_bytes: [u8; 32] = deadline.to_be_bytes();

	let digest = permit::Pallet::<Test>::permit_digest(
		&asset_addr,
		PERMIT_TOKEN_NAME,
		&HARDHAT_ACCOUNT_0,
		&spender,
		&value_bytes,
		&nonce,
		&deadline_bytes,
	);

	// Sign via the keystore — works in both native and WASM, mirroring
	// the approach used in benchmarking.rs.
	let key_type = sp_core::crypto::KeyTypeId(*b"prmt");
	let pub_key = sp_io::crypto::ecdsa_generate(key_type, Some(HARDHAT_ACCOUNT_0_SEED.to_vec()));
	let sig = sp_io::crypto::ecdsa_sign_prehashed(key_type, &pub_key, &digest)
		.expect("signing with Hardhat #0 must succeed; qed");
	let sig_bytes: &[u8; 65] = sig.as_ref();
	let r: [u8; 32] = sig_bytes[0..32].try_into().expect("r is 32 bytes");
	let s: [u8; 32] = sig_bytes[32..64].try_into().expect("s is 32 bytes");
	let v: u8 = sig_bytes[64] + 27;
	(v, r, s)
}
