### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status to using a global, repository-unscoped query (`Commit.where(sha: params.sha)`), while every sibling handler (`CheckSuiteHandler`, pull-request handlers) resolves the target stacks through `Repository.from_github_repo_name(repository_name)` first. Any commit row anywhere in the database that happens to share a SHA with the SHA named in an incoming, validly-signed `status` webhook gets a new `Status` created against *its own* stack, letting a legitimately-owned repository's CI event mutate another tenant's commit/stack state.

### Finding Description
The broken binding: the code implicitly assumes `commit.sha == params.sha ⇒ commit.stack.repository == payload.repository`. This is false — `Commit.where(sha: params.sha)` at [1](#0-0)  performs no join or filter on `repository`/`stack`, unlike the base `Handler#stacks` helper used elsewhere, which does scope by `Repository.from_github_repo_name(repository_name)` [2](#0-1) , and unlike `CheckSuiteHandler`, which correctly restricts to `stacks.where(branch: ...)` before touching commits [3](#0-2) .

`verify_signature` only proves the webhook was genuinely emitted for the `repository_owner`/organization named in the payload [4](#0-3)  — it says nothing about which `Commit` rows the handler is allowed to touch. So an attacker who legitimately owns a GitHub repository that has the Shipit GitHub App installed (a normal onboarding step requiring no stolen secret) can push a commit, and cause a genuinely-signed `status` event for that commit's SHA. Because `StatusHandler` never checks that the SHA belongs to a commit tracked by the *same* repository as `payload['repository']['full_name']`, any other stack whose commit table has an identical SHA — most realistically a fork or a second stack/branch that shares git ancestry with the attacker's repo — will also receive a new `Status` row: `commit.create_status_from_github!(params)` → `statuses.replicate_from_github!(stack_id, github_status)` uses the *victim* commit's own `stack_id` [5](#0-4) [6](#0-5) .

`Commit#blocked?` then re-evaluates over the victim stack's own reachable/undeployed range and calls `blocking?` on each commit, which derives purely from `status.state` [7](#0-6) [8](#0-7) . If the forged status flips the blocking commit from pending/failure to success, every later undeployed commit in that chain (e.g. `soc_third`) becomes deployable, as demonstrated by the existing test pattern for this exact fixture chain [9](#0-8) .

None of the listed guards catch this: `verify_signature` authenticates the *sender org*, not the *target commit/stack*; the `ExplicitParameters` schema for `StatusHandler` only validates shape (`sha`, `state`, etc.) [10](#0-9) , not cross-repo binding; there is no `stacks`/`repository` scoping applied at all in this handler.

### Impact Explanation
A payload legitimately signed for repository A causes state mutation (`Status` creation) against a commit that belongs to repository B's stack, exactly matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." This can unblock a chain of undeployed commits in the victim stack and enable unauthorized continuous deployment of commits the victim's own CI never approved. It is repeatable against any stack whose commit table contains a SHA also present in a repository the attacker legitimately controls (forks, mirrors, or repositories sharing initial commit history are the realistic vector), and it does not require breaking SHA-1 collision resistance in general — only a shared/duplicated commit SHA across tracked repositories.

### Likelihood Explanation
Preconditions: (1) attacker owns/administers a GitHub repository with the Shipit GitHub App installed (ordinary product usage, not a privileged Shipit role); (2) a target commit SHA exists in another Shipit-tracked stack's `commits` table (realistic via forks/shared history, or any repo re-onboarded/mirrored into Shipit); (3) that target stack has `blocking_statuses` configured and an undeployed chain, matching the `soc` stack fixture pattern already in the test suite. Attacker cost is a single legitimate commit + a GitHub status update on their own repo — no secrets, no privileged role required.

### Recommendation
Scope `StatusHandler#process` through the same repository-aware path as other handlers: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` and only update commits belonging to those stacks, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { ... })`, mirroring `CheckSuiteHandler`'s `stacks.where(...).commits.where(sha: ...)` pattern.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status event for a SHA shared with another repository's commit does not mutate the other stack" do
  victim_commit = shipit_commits(:soc_second)          # stack: soc, currently success
  victim_next   = shipit_commits(:soc_third)

  # Attacker-owned repo/stack, distinct from :soc, sharing the SHA (fork / shared history)
  attacker_stack = shipit_stacks(:shipit) # different repository than :soc
  attacker_stack.commits.create!(sha: victim_commit.sha, message: "attacker copy",
                                  author: shipit_users(:walrus), committer: shipit_users(:walrus),
                                  authored_at: Time.now, committed_at: Time.now)

  # Precondition: bindings differ
  assert_not_equal attacker_stack.repository, victim_commit.stack.repository

  victim_commit.statuses.delete_all # make it pending/blocking
  assert_predicate victim_commit.reload, :blocking?
  refute_predicate victim_next, :deployable?

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'soc/compliance',
    'repository' => { 'full_name' => attacker_stack.repository.github_repo_name,
                       'owner' => { 'login' => attacker_stack.repository.owner } }
  }

  assert_difference 'victim_commit.reload.statuses.count', 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  assert_predicate victim_commit.reload, :success?
  assert victim_next.reload.deployable? # forged event from attacker's repo unblocked victim's chain
end
```
This proof relies on the exact code paths cited above and existing fixtures (`soc_second`/`soc_third`); no live GitHub or secret material is used.
