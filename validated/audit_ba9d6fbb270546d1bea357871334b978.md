### Title
Path traversal in `writeToOutput` via unsanitized `file.Name` from Contents API response - ([File: pkg/cmd/repo/read-file/read_file.go])

### Summary
`writeToOutput` joins the API-reported `file.Name` directly onto the user-supplied `--output` directory with `filepath.Join(dest, file.Name)` without ever validating that the resulting path stays within `dest`. If the JSON response returned by the Contents API endpoint (or a host the victim's `gh` is configured to talk to) contains a `name` field with `../` sequences, the file is written outside the directory the user intended to confine it to.

### Finding Description
In `pkg/cmd/repo/read-file/http.go`, `fetchFile` populates `repoFile.Name` straight from the server-supplied `content.Name` field of the Contents API JSON response, with no validation: [1](#0-0) 

That value flows unchanged into `writeToOutput`, which — when the output path is (or resolves to) a directory — does: [2](#0-1) 

`filepath.Join` calls `filepath.Clean`, which collapses `..` segments against the preceding path component rather than rejecting them. There is no `filepath.Base(file.Name)` call, no check that the cleaned `dest` still has `output` as a prefix, and no rejection of `..` components anywhere in `writeToOutput` or its callers. The existing lstat-based checks in the function only guard against symlinks and pre-existing files at the *final* computed path — after the traversal has already been applied — so they do nothing to stop the escape.

For file names to escape the output directory, the `name` field of the Contents API JSON response must contain path separators/`..`. On real github.com this can't happen for an actual git blob, since a git tree entry's name is a path segment and cannot itself contain `/`. The realistic trigger is a scenario where `gh` is pointed at a non-github.com host (e.g. via `--hostname`/GHES config) that is attacker-controlled or compromised, and that host serves a crafted Contents API response with an arbitrary `name` field (e.g. `"name": "../../evil.md"`).

### Impact Explanation
This is a scoped `PATH_CONFINEMENT` violation: the `--output dir/` flag is meant to confine written content to `dir/`, but a malicious/compromised API host can cause `gh repo read-file --output dir/` to write attacker-controlled bytes to a location outside `dir/`, e.g. into a parent directory the victim did not intend to touch. This matches GitHub's "file write outside the intended path" bounty impact class.

### Likelihood Explanation
Exploitation requires the victim to run `gh repo read-file` against a host whose Contents API responses the attacker fully controls (a malicious/compromised GitHub Enterprise-style host the victim has pointed `gh` at) and to pass `--output` with a directory target. It is not exploitable against genuine github.com-hosted repositories because GitHub's real Contents API cannot emit a `name` field containing `/`. Given that constraint, likelihood against the primary github.com attack surface is low, but the code path itself has no defense-in-depth against a malicious/compromised host doing this.

### Recommendation
In `writeToOutput`, sanitize `file.Name` before joining: reject any name containing path separators or `..`, or explicitly use `filepath.Base(file.Name)` and verify the cleaned result is a direct child of `dest` (e.g., compare `filepath.Clean(dest)` as a prefix of the joined, cleaned path) before writing.

### Proof of Concept
Extend `Test_writeToOutput` in `pkg/cmd/repo/read-file/read_file_test.go`:
```go
{
    name:   "directory target rejects traversal in remote name",
    file:   &repoFile{Name: "../evil.md", Content: []byte("pwned")},
    output: "out/",
    lstat: func(path string) (*lstatResult, error) {
        if path == "out/" {
            return &lstatResult{isDir: true}, nil
        }
        return nil, fs.ErrNotExist
    },
    wantErr: "invalid remote file name", // expected after fix
},
```
Currently, running this against the unpatched `writeToOutput` yields `dest == "evil.md"` (outside `out/`) instead of an error, confirming the traversal.
