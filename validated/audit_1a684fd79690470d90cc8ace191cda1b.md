### Title
Bridge `processingPendingRequestEvents` Loop Permanently Blocks All Subsequent Cross-Chain Transfers on Per-Event Error — (`node/sc/bridge_manager.go`)

### Summary

`BridgeInfo.processingPendingRequestEvents` iterates over a batch of ordered pending `RequestValueTransfer` events and, on the first error from `handleRequestValueTransferEvent`, re-queues the failing event **and every event behind it** before returning. Because the sorted pending queue is nonce-ordered and the failing event is always re-inserted at the front, every subsequent bridge transfer with a higher nonce is permanently frozen until the root cause of the failure is resolved externally — with no in-protocol mechanism to skip or bypass the stuck entry.

### Finding Description

`processingPendingRequestEvents` in `node/sc/bridge_manager.go` drives the off-chain relay loop that submits `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` transactions to the destination bridge contract: [1](#0-0) 

```go
for idx, ev := range ReadyEvent {
    if ev.GetRequestNonce() < bi.lowerHandleNonce || bi.handledEvent.Exist(ev.GetRequestNonce()) {
        continue
    }
    if err := bi.handleRequestValueTransferEvent(ev); err != nil {
        bi.AddRequestValueTransferEvents(ReadyEvent[idx:])   // re-queues failing + all later events
        logger.Error("Failed handle request value transfer event", ...)
        return
    }
}
```

`handleRequestValueTransferEvent` returns a hard Go-level error (not an on-chain revert) in at least two reachable paths:

1. **Unregistered counterpart token** — if the token is registered on the source bridge but absent from the destination bridge's `RegisteredTokens` mapping, the function returns `errors.New("can't get counterpart token from bridge")`: [2](#0-1) 

2. **RPC / submission failure** — any network error from `bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)` or from the `HandleKLAYTransfer` / `HandleERC20Transfer` / `HandleERC721Transfer` Go-binding call propagates as a non-nil error: [3](#0-2) 

When either path fires, `ReadyEvent[idx:]` — which includes the failing event itself — is pushed back into `pendingRequestEvent`. The next ticker or `newEvent` signal calls `processingPendingRequestEvents` again, pops the same batch, hits the same event, fails again, and re-queues again. The loop is infinite and no event with `requestNonce > N` (the stuck nonce) is ever processed.

The `valueTransferRecovery` subsystem re-fetches missed events from logs and re-adds them to the same pending queue: [4](#0-3) 

It does not skip or bypass stuck entries, so recovery does not resolve the blockage.

### Impact Explanation

Every cross-chain value transfer whose `requestNonce` is greater than the stuck nonce is permanently frozen on the relay side. The destination bridge never receives the corresponding `handle*Transfer` transaction, so the recipient never receives KAIA, ERC-20, or ERC-721 assets. Funds are locked in the source bridge contract with no on-chain path to release them until the operator manually resolves the root cause and restarts the relay — an operation with no guaranteed SLA.

### Likelihood Explanation

The trigger is reachable through semi-trusted operator actions that are part of normal bridge administration:

- A token is deregistered from the destination bridge (`DeregisterToken`, `onlyOwner`) while one or more `RequestValueTransfer` events for that token are already in the pending queue. The relay immediately enters the permanent-failure loop for those events and all events behind them.
- Alternatively, a transient RPC outage to the counterpart chain causes the same re-queue loop; if the outage is prolonged, the backlog grows and ordering guarantees mean no later event is processed even after connectivity is restored.

The bridge's `onlyRegisteredToken` guard on the *source* side does not prevent this: a token can be registered on the source bridge, a user can legitimately request a transfer, and the token can be deregistered on the destination side before the relay processes the event. [5](#0-4) 

### Recommendation

Change `processingPendingRequestEvents` to **skip** (not re-queue) events that fail with a persistent error, and only re-queue on transient errors (e.g., RPC timeouts). Concretely:

- Distinguish error categories: return a typed sentinel (e.g., `ErrSkippableEvent`) from `handleRequestValueTransferEvent` when the token is permanently unresolvable.
- On a skippable error, log the event, drop it from the queue (or move it to a dead-letter store), and **continue** the loop rather than returning.
- On a transient error, retain the current re-queue-and-return behaviour.
- Expose an operator API to inspect and manually drain the dead-letter store.

### Proof of Concept

1. Deploy source bridge `S` and destination bridge `D`; register token `T` on both.
2. User calls `S.requestERC20Transfer(T, …)` → event with `requestNonce = 5` is emitted and enters the relay's pending queue alongside later events (nonces 6, 7, …).
3. Operator calls `D.deregisterToken(T, …)` before the relay processes nonce 5.
4. Relay calls `processingPendingRequestEvents`:
   - Nonces 0–4 succeed normally.
   - Nonce 5: `handleRequestValueTransferEvent` calls `D.RegisteredTokens(nil, T)` → returns `address(0)` → returns `errors.New("can't get counterpart token from bridge")`.
   - `ReadyEvent[5:]` (nonces 5, 6, 7, …) is re-queued; function returns.
5. Next ticker fires → same result. Nonces 6, 7, … are never processed.
6. Users whose transfers correspond to nonces 6, 7, … never receive their assets on the destination chain. [6](#0-5) [7](#0-6)

// processingPendingRequestEvents handles pending request value transfer events of the bridge.
func (bi *BridgeInfo) processingPendingRequestEvents() {
	ReadyEvent := bi.GetReadyRequestValueTransferEvents()
	if ReadyEvent == nil {
		return
	}

	logger.Trace("Get ready request value transfer event", "len(readyEvent)", len(ReadyEvent), "len(pendingEvent)", bi.pendingRequestEvent.Len())

	for idx, ev := range ReadyEvent {
		if ev.GetRequestNonce() < bi.lowerHandleNonce || bi.handledEvent.Exist(ev.GetRequestNonce()) {
			logger.Trace("handled requests can be ignored", "RequestNonce", ev.GetRequestNonce(), "lowerHandleNonce", bi.lowerHandleNonce)
			continue
		}

		if err := bi.handleRequestValueTransferEvent(ev); err != nil {
			bi.AddRequestValueTransferEvents(ReadyEvent[idx:])
			logger.Error("Failed handle request value transfer event", "err", err, "len(RePutEvent)", len(ReadyEvent[idx:]))
			return
		}
	}

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}
