### Title
Webhook signature verification is bound to `repository.owner.login`, not the `repository.full_name` actually acted upon, allowing cross-organization stack tampering in multi-org Shipit deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the HMAC signature against using `repository_owner`, a value read from the unauthenticated JSON body itself. The event handlers that subsequently act on the payload (e.g. `PushHandler`, the `PullRequest::*` handlers) resolve the actual `Repository`/`Stack` to mutate using a *different* field of the same body, `repository.full_name`. Because Shipit explicitly supports configuring one GitHub App per organization (multi-tenant setup), these two fields are never cross-checked against each other, breaking the equality `organization that authenticated == repository/stack that is written`.

### Finding Description
The controller derives the signing organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`repository_owner` (`repository.owner.login` or `organization.login`) is used only to select which configured GitHub App's `webhook_secret` is used to verify the HMAC over the raw body: [3](#0-2) 

However, once the signature check passes, every default handler determines *which* `Repository`/`Stack` to act on using the unrelated `repository.full_name` field of the very same JSON body: [4](#0-3) [5](#0-4) [6](#0-5) 

Shipit's own setup documentation confirms that separate GitHub Apps/secrets are configured per organization, each organization owner independently knowing (and legitimately possessing) their own `webhook_secret`: [7](#0-6) 

The `repository.owner.login` field (used for signature-organization selection) and `repository.full_name` (used to select the acted-upon `Repository`) are independent, attacker-suppliable strings within the same JSON object — nothing enforces `full_name.split('/').first == repository_owner`. An entity that legitimately owns *any one* of the configured organizations (and therefore legitimately knows that organization's `webhook_secret`, e.g. an org admin who created the GitHub App per `docs/setup.md`) can craft an arbitrary payload, set `repository.owner.login` to their own org (so `verify_signature` picks their own, valid secret and passes), while setting `repository.full_name` to `victim-org/victim-repo` (a stack belonging to a completely different tenant tracked by the same Shipit instance).

Before the attacker's request: `verified-organization == acted-upon-repository-owner` holds only because legitimate GitHub always sends both fields consistent with the actual repository. After the attacker's crafted request: `verified-organization (attacker-org)` ≠ `acted-upon-repository (victim-org/victim-repo)`, yet the handler proceeds because there is no equality check between them — the deployment-trust binding is broken.

### Impact Explanation
This is a cross-organization confused-deputy vulnerability affecting a self-hosted, multi-tenant Shipit instance:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for a victim's stack the attacker does not control [8](#0-7) .
- `PullRequest::OpenedHandler`/`LabeledHandler` can create or archive/unarchive review stacks belonging to the victim repository [9](#0-8) [10](#0-9) .
- `StatusHandler` and `CheckSuiteHandler` (not fully re-inspected here but wired the same way through `Handler#repository_name`) can inject fabricated commit statuses/check-run refreshes onto a victim's commits, which `Commit#add_status` uses to trigger `stack.schedule_merges` and downstream automatic merges via `ProcessMergeRequestsJob#perform` → `MergeRequest#merge!`, which calls `stack.github_api.merge_pull_request` using the app's own `GITHUB_TOKEN`-equivalent installation token for the *victim* repository [11](#0-10) [12](#0-11) [13](#0-12) .

This reaches the required Critical bar: an unauthorized deploy/merge can be induced against a repository/organization the attacker does not administer, using the app's legitimate GitHub credentials, satisfying "cross-repository writes" / "unauthorized deploy, rollback or merge."

### Likelihood Explanation
Requires the target Shipit instance to be configured in the documented multi-organization mode (`github: { orgA: {...}, orgB: {...} }`), and requires the attacker to control at least one of the configured GitHub organizations (i.e., they legitimately know that org's own `webhook_secret`, which they themselves provisioned when creating their GitHub App as instructed in `docs/setup.md`). This is a realistic scenario for shared/hosted Shipit deployments serving multiple, mutually-untrusting organizations, since no repository/organization ownership cross-check exists anywhere between `verify_signature` and the handler dispatch pipeline.

### Recommendation
In `WebhooksController#create`/`verify_signature`, after selecting the GitHub App by `repository_owner`, validate that the organization portion of `repository.full_name` (and `organization.login`, if used as fallback) exactly matches `repository_owner` before dispatching to handlers, rejecting the request (422) on mismatch. Alternatively, resolve the target `Repository` via `Repository.from_github_repo_name` and assert `repository.owner == repository_owner` before invoking any `Webhooks::Handlers::Handler`.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, per the documented multi-org `github:` config; the attacker legitimately knows `attacker-org`'s `webhook_secret` because they created that GitHub App.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker's own secret [1](#0-0) .
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `repository.full_name` = `"victim-org/victim-repo"` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [8](#0-7) , despite the attacker having no relationship to `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
