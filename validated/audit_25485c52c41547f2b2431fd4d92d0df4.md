## Title
Cross-organization forged commit status enables unauthorized merges/deploys — signature verified against the payload's `repository.owner`/`organization` field while `StatusHandler` writes to a globally-scoped `Commit` table with no organization/repository check ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on a field read straight out of the untrusted request body (`repository.owner.login` or `organization.login`), then dispatches the *entire* payload to handlers that are trusted to act only within that organization's scope. [1](#0-0) [2](#0-1)  `StatusHandler`, however, never checks the `repository` field at all — it looks up commits globally by `sha` across the entire `Commit` table and writes a GitHub status to whatever commit matches, regardless of which stack/organization that commit belongs to. [3](#0-2)  This breaks the binding "organization that authenticated == repository that is written," matching the analog bug class in the report (a value used for a security decision — inside-fee/authorization scope — that doesn't match the value that is actually acted upon).

### Finding Description
Shipit supports multiple GitHub organizations, each with its own independently configured `webhook_secret` in `secrets.yml`. [4](#0-3)  `Shipit.github(organization:)` resolves the app/secret purely by the `organization` string passed in. [5](#0-4)  The webhook controller picks that `organization` value straight from the untrusted JSON body:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

and uses it only to select which secret to verify the HMAC with:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end
``` [6](#0-5) 

Once verification succeeds, the *entire* raw payload is forwarded unmodified to every registered handler for the event type: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [7](#0-6) 

For most handlers (e.g. `PushHandler`, the `PullRequest::*Handler`s), the actual target repository is derived from `repository.full_name` via `Handler#repository_name`/`#stacks`, which is a *different* field than the one used for signature-org selection, but that is at least still scoped to the repository named in the payload. [8](#0-7) 

`StatusHandler` is worse — it does not use `repository`/`stacks` scoping at all:
```ruby
class StatusHandler < Handler
  params do
    requires :sha, String
    requires :state, String
    ...
  end

  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
``` [9](#0-8) 

`Commit.where(sha: params.sha)` queries across **all stacks and all organizations** configured on the Shipit instance, so a `status` payload only needs to carry a `sha` value and an `organization`/`repository.owner.login` that resolves to *any* configured secret the attacker knows — it does not need to match the organization that actually owns the target commit/stack.

An unprivileged actor who legitimately administers their own GitHub organization ("Org A") that has been onboarded to a shared multi-org Shipit instance (per the documented multi-org setup) knows Org A's `webhook_secret` (they configured/rotated it themselves when creating the GitHub App). They can:
1. Take the `sha` of a real, pending commit belonging to an unrelated Org B stack on the same Shipit instance.
2. Craft a `status` webhook body: `{"sha": "<Org B commit sha>", "state": "success", "context": "<Org B's required CI context>", "organization": {"login": "Org A"}}`.
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(body, OrgA_webhook_secret)>` themselves and POST directly to `/webhooks`.
4. `verify_signature` resolves the Org A app via `repository_owner` → verifies successfully against Org A's real secret. [6](#0-5) 
5. `StatusHandler` finds the Org B commit by `sha` (global lookup) and creates a fabricated `success` status on it via `commit.create_status_from_github!`. [10](#0-9) 

The injected status flows into `Commit#add_status`, which schedules merges/continuous delivery whenever the commit becomes `pending` or `success`: `stack.schedule_merges if new_status.pending? || new_status.success?`. [11](#0-10)  If Org B's stack has the merge queue or continuous deployment enabled, `ProcessMergeRequestsJob` will then see `all_status_checks_passed?` return true (based on the forged status) and call `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request` using **Shipit's own GitHub App credentials for Org B** — an unauthorized merge triggered purely by a cross-organization forged status. [12](#0-11) [13](#0-12) 

### Impact Explanation
This is a cross-repository/cross-organization write and can directly produce an unauthorized merge or deploy: an actor who is only authenticated as one onboarded GitHub organization can forge CI status data for a commit belonging to a *different* onboarded organization's stack, using Shipit's own valid GitHub credentials to actually execute the merge on GitHub. This matches the "Critical: cross-repository writes / an unauthorized deploy, rollback or merge" bar.

### Likelihood Explanation
Requires only knowledge of a legitimately-configured organization's `webhook_secret` (something any of that org's admins can obtain by design, without any Shipit account, session, or repository write access) plus the target commit sha (visible in Shipit's own UI/API for any stack, or guessable/observable from the target repo's public commit history). No Shipit credentials, GitHub App private key, or `api_clients_secret` are needed — only a plain HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Scope every webhook handler's actions by the repository/organization actually asserted in the signed payload and validated against the record it is about to mutate — e.g. `StatusHandler` should restrict `Commit.where(sha: ...)` to `stacks`/`repository_name`-scoped commits (as `Handler#stacks` already does for other handlers), and additionally cross-check that `repository_owner` used for signature verification matches the repository owner of the target stack/commit before applying any mutation.

### Proof of Concept
1. Assume a shared Shipit instance configured with two organizations in `secrets.yml`: `orga` (attacker-controlled) and `orgb` (victim, whose stack has continuous deployment / merge queue enabled) — per the documented multi-org config format. [4](#0-3) 
2. Attacker (an admin of `orga`'s real GitHub org) knows `orga`'s `webhook_secret`.
3. Attacker identifies a pending commit `sha` on an `orgb` stack (e.g. from the public Shipit UI or GitHub) that is awaiting a required CI status.
4. Attacker builds JSON body:
```json
{"sha": "<orgb_commit_sha>", "state": "success", "context": "<orgb_required_context>", "organization": {"login": "orga"}}
```
5. Attacker computes `sig = sha1=HMAC_SHA1(body, orga_webhook_secret)` locally and sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<sig>
Content-Type: application/json

<body>
```
6. `verify_signature` succeeds (verified against `orga`'s real secret). [1](#0-0) 
7. `StatusHandler#process` finds the `orgb` commit purely by `sha` and creates the forged `success` status on it. [10](#0-9) 
8. If the affected `orgb` stack has continuous deployment/merge queue enabled, the forged status can trigger `ProcessMergeRequestsJob` to merge or a deploy to be scheduled for the `orgb` commit, using Shipit's own GitHub credentials. [12](#0-11)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
