### Title
Hash Collision in `arbiter_contract.getHashSrc` Enables Contract Forgery with Colliding Hash - (File: `arbiter_contract.js`)

### Summary
`arbiter_contract.js` computes a contract's identifying `hash` from several free-form string and numeric fields. For contracts created before `exports.NEW_HASH_DATE`, the fields are concatenated with `join("")` (no delimiter at all), which is exactly the "same-datatype fields hashed adjacent without separation" collision pattern described in the reference report, only worse (no delimiter vs. same-type grouping).

### Finding Description
`getHashSrc()` builds the hash pre-image differently depending on the contract's `creation_date`: [1](#0-0) 

For the "old" branch (`creation_date <= NEW_HASH_DATE`) the fields `payer_name`, `contract.arbiter_address`, `payee_name`, `contract.amount`, `contract.asset` (plus `title`, `text`, `creation_date`) are joined with the empty string `""` — i.e., no separator whatsoever between adjacent free-text/numeric fields. This is a direct instance of the reported bug class: variable-length string fields placed next to each other in a hash pre-image without a delimiter allow different sets of field values to serialize to the identical byte string, and therefore to the identical SHA-256 hash produced by `getHash()`: [2](#0-1) 

For example, `title="AB", text="C"` and `title="A", text="BC"` (with all other fields identical) concatenate to the same string `"ABC..."`, producing the same `hash`. The same ambiguity applies to `payer_name`/`payee_name` boundaries versus `arbiter_address`.

Critically, `exports.NEW_HASH_DATE = '2026-11-01'` is a future date relative to today (2026-09-15): [3](#0-2) 

Since `contract.creation_date > exports.NEW_HASH_DATE` is false for all contracts created today, **every contract currently created goes through the vulnerable, delimiter-less branch** — the newer, safer branch (which at least uses `exports.DELIMITER = "[|#|]"`) is not yet active in practice.

The `hash` computed this way is used as the primary identifier for the whole arbitrated-contract lifecycle: it is stored as the contract's `hash` in `createAndSend()`, used to key it in `wallet_arbiter_contracts`, sent to the counterparty device as `arbiter_contract_offer`/`arbiter_contract_response`/`arbiter_contract_update` messages, and embedded into on-DAG `data_feed` payloads as `"CONTRACT_" + contract.hash` (arbiter's dispute verdict) and `"CONTRACT_DONE_" + contract.hash` (private-asset completion marker), consumed later by `parseWinnerFromUnit()`: [4](#0-3) [5](#0-4) 

### Impact Explanation
Because the hash is the sole binding identifier tying together the off-band contract text (title/parties/amount) with the on-DAG dispute-resolution data feed, a hash collision lets a malicious payer or payee construct two distinct contract bodies (e.g., different `title`/`text`, or shifted boundaries between `payer_name`/`arbiter_address`/`payee_name`) that hash to the same value. This can be used to:
- Present one version of the contract terms to the counterparty (for acceptance/signature) while a different, colliding version is used with the arbiter/arbstore or stored locally, since all lookups (`getByHash`, `parseWinnerFromUnit`, dispute keys `CONTRACT_<hash>`) key strictly off the hash rather than the full content.
- Cause the arbiter's or a party's local `wallet_arbiter_contracts` state to reference terms that were never mutually agreed, since `handleDuplicateAddressDefinition`-style trust in `hash` equality is misplaced when content differs.

This is a private, off-DAG-payment-adjacent contract mechanism (arbiter-mediated escrow) whose fund-moving conclusion (`complete()`) depends on the previously agreed `objContract.amount`/`peer_address`, so a successful collision attack can lead to loss/misdirection of escrowed funds or an arbiter deciding a dispute based on terms that differ from what the counterparty actually saw and agreed to.

### Likelihood Explanation
Exploitation requires only that one of the (already semi-trusted but adversarial) contract participants control the free-text fields (`title`, `text`, `my_party_name`/`peer_party_name`) — which is normal for this feature, since both counterparties supply their own text. No special network position, hub compromise, or leaked keys are needed; a single unprivileged AA/contract author acting as payer or payee is sufficient. The bug is also currently "live" for every contract created today because the safer delimiter-based branch is gated behind a future date (`2026-11-01`) that hasn't arrived yet.

### Recommendation
- Do not gate the fix behind a future `creation_date` threshold; apply a proper collision-resistant encoding (e.g., length-prefixed fields or `ocore`'s own `getSourceString`/`getJsonSourceString` from `string_utils.js`, which already tags each field with a type prefix and a `\x00` join character specifically to prevent this ambiguity) to **all** contracts, retroactively if needed.
- Replace `getHashSrc`'s `join("")` (old branch) and `join(exports.DELIMITER)` (new branch, which is still theoretically breakable if a field can contain the delimiter string) with `object_hash.getBase64Hash({...fields}, true)`, mirroring how the rest of the codebase (e.g., `indivisible_asset.js` spend proofs, unit/definition hashing) avoids exactly this class of bug by using `string_utils.getSourceString`/`getJsonSourceString`.

### Proof of Concept
1. Construct `contractA` with `title="AB"`, `text="C"`, and all other fields fixed (`creation_date`, `payer_address`, `payer_name`, `arbiter_address`, `payee_address`, `payee_name`, `amount`, `asset`).
2. Construct `contractB` identical except `title="A"`, `text="BC"`.
3. Call `getHashSrc(contractA)` and `getHashSrc(contractB)` — because `creation_date <= NEW_HASH_DATE` (true for any date before 2026-11-01), both use the `join("")` branch:
   `[title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset].join("")`
   Wait — verify against actual field order in code: the "old" (pre-`NEW_HASH_DATE`) branch is `[title, text, creation_date, payer_name, arbiter_address, payee_name, amount, asset].join("")`.
4. Both `contractA` and `contractB` pre-image strings resolve to the identical concatenated string `"ABC" + rest`, so `getHash(contractA) === getHash(contractB)` even though the contracts have different `title`/`text`.
5. Any code path treating `hash` as a unique identifier for contract content (device messaging, `CONTRACT_<hash>` data-feed dispute key, `getByHash` lookups) can be confused by presenting one party with `contractA` and using `contractB`'s hash-keyed dispute/completion messages, or vice versa.

```javascript
function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
```

```javascript
function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
```
