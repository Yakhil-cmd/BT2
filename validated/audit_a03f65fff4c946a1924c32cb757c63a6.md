### Title
`note_author` reward payout ignores `Currency::transfer` failure, letting a collator advance `LastAuthoredBlock` without receiving payment - ([File: cumulus/pallets/collator-selection/src/lib.rs])

### Summary
`pallet_collator_selection`'s `EventHandler::note_author` pays half of the `StakingPot` balance to the block author via `T::Currency::transfer(&pot, &author, reward, KeepAlive)`, but discards the `Result` behind a `debug_assert!`, which is compiled to a no-op in release/production builds. Regardless of whether the transfer succeeds, `LastAuthoredBlock` is unconditionally updated. This is the same bug class as the reported `VaultV3::custodyFunds`/`returnFunds` issue: state mutation proceeds without validating the token-transfer outcome.

### Finding Description
`note_author` is the `pallet_authorship::EventHandler` implementation invoked whenever a block author (or uncle) is recorded: [1](#0-0) 

```rust
fn note_author(author: T::AccountId) {
    let pot = Self::account_id();
    let reward = T::Currency::free_balance(&pot)
        .checked_sub(&T::Currency::minimum_balance())
        .unwrap_or_else(Zero::zero)
        .div(2u32.into());
    // `reward` is half of pot account minus ED, this should never fail.
    let _success = T::Currency::transfer(&pot, &author, reward, KeepAlive);
    debug_assert!(_success.is_ok());
    LastAuthoredBlock::<T>::insert(author, frame_system::Pallet::<T>::block_number());
    ...
}
```

The `_success` result is never propagated or checked with a real guard — only `debug_assert!`, which is stripped out entirely in non-debug (production) builds. `LastAuthoredBlock` is written unconditionally right after, regardless of whether the payout actually landed.

Reachability from an unprivileged user:
- `register_as_candidate` is a permissionless signed extrinsic; any account with the `CandidacyBond` and registered session keys can become a collator candidate: [2](#0-1) 
- Test/benchmark code confirms this is fully attacker-reachable with zero privileges beyond a bond deposit: [3](#0-2) 
- Once selected into the active collator set (via `assemble_collators`/`new_session`), authoring a block triggers `note_author` through the `pallet_authorship::EventHandler` wiring: [4](#0-3) 

`T::Currency::transfer` with `Preservation::KeepAlive` can fail on the *deposit* side when the receiving account does not already exist and the computed `reward` is below the existential deposit — a condition an attacker can force by controlling a freshly-created collator `AccountId` with zero prior balance, combined with a `StakingPot` balance that yields a sub-ED reward (e.g., a pot that is thin after being drained, or shortly after collator-set churn). In that scenario the transfer errors out silently, but `LastAuthoredBlock` still advances.

### Impact Explanation
The consequence mirrors the report's "state inconsistency" class, but manifests in the collator-eviction (`kick_stale_candidates`) logic rather than a vault:
- `kick_stale_candidates` relies on `LastAuthoredBlock` to determine if a collator is "lazy" and should be evicted: [5](#0-4) 
- Because `LastAuthoredBlock` is updated even when the reward transfer fails, a collator can be treated as active/non-lazy while never actually being paid, permanently occupying a slot that should be reclaimed and distorting the incentive/eligibility bookkeeping the pallet is meant to enforce.
- Unlike the report's severity (direct fund custody/lock), this does not enable direct theft or unbacked issuance — the pot funds simply remain undistributed rather than being lost or double-spent — so it is best classified as a state-integrity/Low-to-Medium griefing issue rather than Critical/High.

### Likelihood Explanation
Reaching `register_as_candidate` requires no privileged role — only a signed account and the bond, matching the mandated "no privileged role/governance/stolen keys" attacker model. Actually forcing the *specific* transfer-failure condition (fresh zero-balance author account + sub-ED reward from the pot) is a narrower, timing-dependent scenario dependent on `StakingPot` balance state and session selection, which the attacker does not fully control deterministically on-chain (selection into the active set is not solely attacker-controlled). This keeps likelihood moderate rather than trivial.

### Recommendation
Propagate the transfer error instead of masking it with `debug_assert!`, and avoid mutating `LastAuthoredBlock` (or gate the "active/non-lazy" credit) unless the reward transfer actually succeeded — e.g., log/emit a distinguishable event on failure similar to `pallet-staking-async`'s `Unexpected::ValidatorIncentiveTransferFailed` handling pattern already present elsewhere in this codebase: [6](#0-5) 

### Proof of Concept
Not executed against a live network. A minimal FRAME test-harness repro would:
1. Register account `A` as a candidate via `CollatorSelection::register_as_candidate(RuntimeOrigin::signed(A))` (permissionless, matches existing test pattern at `cumulus/pallets/collator-selection/src/tests.rs:606-627`).
2. Drain/configure `StakingPot`'s balance so `reward = (free_balance(pot) - ED) / 2` is below the pallet's existential deposit, and ensure account `A` has zero prior balance (so the deposit side of `KeepAlive` transfer fails at the ED boundary).
3. Call `<CollatorSelection as pallet_authorship::EventHandler<_,_>>::note_author(A)` directly (as done in benchmarking/test code).
4. Assert: `T::Currency::transfer` returns `Err(_)` (no balance moved to `A`), yet `LastAuthoredBlock::<T>::get(A)` is still updated to the current block — demonstrating the state mutation proceeds despite the failed, unchecked transfer.

This was reasoned from static code inspection of the pallet's current logic; the described test was not run against the repository, so execution status/output is unverified — this should be validated by actually running the above scenario in the pallet's `mock.rs`/`tests.rs` harness before filing as a confirmed bounty submission.

		/// registered session keys and (b) be able to reserve the `CandidacyBond`.
		///
		/// This call is not available to `Invulnerable` collators.
		#[pallet::call_index(3)]
		#[pallet::weight(T::WeightInfo::register_as_candidate(T::MaxCandidates::get()))]
		pub fn register_as_candidate(origin: OriginFor<T>) -> DispatchResultWithPostInfo {
			let who = ensure_signed(origin)?;

			// ensure we are below limit.
			let length: u32 = CandidateList::<T>::decode_len()
				.unwrap_or_default()
				.try_into()
				.unwrap_or_default();
			ensure!(length < T::MaxCandidates::get(), Error::<T>::TooManyCandidates);
			ensure!(!Invulnerables::<T>::get().contains(&who), Error::<T>::AlreadyInvulnerable);

			let validator_key = T::ValidatorIdOf::convert(who.clone())
				.ok_or(Error::<T>::NoAssociatedValidatorId)?;
			ensure!(
				T::ValidatorRegistration::is_registered(&validator_key),
				Error::<T>::ValidatorNotRegistered
			);

			let deposit = CandidacyBond::<T>::get();
			// First authored block is current block plus kick threshold to handle session delay
			CandidateList::<T>::try_mutate(|candidates| -> Result<(), DispatchError> {
				ensure!(
					!candidates.iter().any(|candidate_info| candidate_info.who == who),
					Error::<T>::AlreadyCandidate
				);
				T::Currency::reserve(&who, deposit)?;
				LastAuthoredBlock::<T>::insert(
					who.clone(),
					frame_system::Pallet::<T>::block_number() + T::KickThreshold::get(),
				);
				candidates
					.try_insert(0, CandidateInfo { who: who.clone(), deposit })
					.map_err(|_| Error::<T>::InsertToCandidateListFailed)?;
				Ok(())
			})?;

			Self::deposit_event(Event::CandidateAdded { account_id: who, deposit });
			// Safe to do unchecked add here because we ensure above that `length <
			// T::MaxCandidates::get()`, and since `T::MaxCandidates` is `u32` it can be at most
			// `u32::MAX`, therefore `length + 1` cannot overflow.
			Ok(Some(T::WeightInfo::register_as_candidate(length + 1)).into())
		}

		/// Kicks out candidates that did not produce a block in the kick threshold and refunds
		/// their deposits.
		///
		/// Return value is the number of candidates left in the list.
		pub fn kick_stale_candidates(candidates: impl IntoIterator<Item = T::AccountId>) -> u32 {
			let now = frame_system::Pallet::<T>::block_number();
			let kick_threshold = T::KickThreshold::get();
			let min_collators = T::MinEligibleCollators::get();
			candidates
				.into_iter()
				.filter_map(|c| {
					let last_block = LastAuthoredBlock::<T>::get(c.clone());
					let since_last = now.saturating_sub(last_block);

					let is_invulnerable = Invulnerables::<T>::get().contains(&c);
					let is_lazy = since_last >= kick_threshold;

					if is_invulnerable {
						// They are invulnerable. No reason for them to be in `CandidateList` also.
						// We don't even care about the min collators here, because an Account
						// should not be a collator twice.
						let _ = Self::try_remove_candidate(&c, false);
						None
					} else {
						if Self::eligible_collators() <= min_collators || !is_lazy {
							// Either this is a good collator (not lazy) or we are at the minimum
							// that the system needs. They get to stay.
							Some(c)
						} else {
							// This collator has not produced a block recently enough. Bye bye.
							let _ = Self::try_remove_candidate(&c, true);
							None
						}
					}
				})
				.count()
				.try_into()
				.expect("filter_map operation can't result in a bounded vec larger than its original; qed")
		}
