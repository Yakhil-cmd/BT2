### Title
Malformed `conditions:` YAML block in a hookify rule file silently parses to an empty list, causing block rules to never fire with zero warning - (File: plugins/hookify/core/config_loader.py)

### Summary
The hand-rolled YAML parser in `extract_frontmatter` (plugins/hookify/core/config_loader.py:87-195) silently drops any indented line under a list key (like `conditions:`) that does not start with `-`, producing an empty list with **no exception and no warning**. When this happens, `Rule.from_dict` sets `conditions=[]` [1](#0-0) , and `RuleEngine._rule_matches` then unconditionally returns `False` for that rule because "Rules must have at least one condition to be valid" [2](#0-1) . This differs from the specific "missing `:` and `,`" example in the prompt (that case actually raises `AttributeError` and gets rejected with a printed error), but the same code path does contain a genuine silent-empty-conditions bug via a different, equally plausible authoring mistake.

### Finding Description
`extract_frontmatter` processes `.claude/hookify.*.local.md` frontmatter line-by-line with only three recognized branches: a top-level `key: value` line (`indent == 0`), a list item starting with `-` while `in_list` is set [3](#0-2) , and a dict-item continuation line requiring `in_dict_item` to already be `True` [4](#0-3) . Any line that is indented (`indent > 0`), does not start with `-`, and is encountered while `in_dict_item` is still `False` (i.e. the very first line describing a condition's fields, if the rule author omits the leading `-`) matches **none** of the `if/elif` branches and is silently skipped — there is no `else` clause.

Example attacker/author-authored rule frontmatter that triggers this:
```
---
name: block-secrets
enabled: true
event: bash
action: block
conditions:
  field: command
  operator: regex_match
  pattern: "curl .*api.internal"
---
```
Here `conditions:` sets `in_list = True`, `current_key = 'conditions'`, `current_list = []` [5](#0-4) . None of the following three lines start with `-`, so each falls through every `if/elif` and is discarded. At end of parsing, `frontmatter['conditions'] = []` is saved [6](#0-5) . `load_rule_file` succeeds without raising any exception, so **no warning is printed anywhere** (unlike the malformed-inline-dict case, which does hit the `AttributeError` handler and prints "Error: Malformed rule file...") [7](#0-6) . `Rule.from_dict` yields `conditions=[]`, `enabled=True`, `action='block'` [8](#0-7) , so `load_rules` includes it as an active rule [9](#0-8) . At evaluation time, `RuleEngine._rule_matches` hits `if not rule.conditions: return False` [2](#0-1)  for every input, so the rule can never enter `blocking_rules` in `evaluate_rules` [10](#0-9) . The hook script (`plugins/hookify/hooks/pretooluse.py`) only forwards the JSON result of `evaluate_rules` on stdout [11](#0-10) ; any `print(..., file=sys.stderr)` diagnostics from `config_loader` are not part of that JSON and are not surfaced to the Claude Code user/session, so the rule silently appears "enabled" while functioning as a permanent no-op.

### Impact Explanation
A `block`-action hookify rule intended to prevent dangerous commands or file edits (e.g. blocking `rm -rf`, secret exfiltration commands, etc.) can be rendered completely inert by an innocuous-looking YAML authoring mistake in the `conditions:` block, with zero diagnostic surfaced to the operator/user. This defeats the stated invariant that "block hooks must not be bypassable through parsing tricks / silent misconfiguration," undermining the plugin's core safety guarantee without any attacker interaction beyond shipping/committing a subtly malformed rule file — a realistic supply-chain or accidental-misconfiguration scenario for repo-shipped hookify rules.

### Likelihood Explanation
No special privileges are required beyond being able to place or modify a `.claude/hookify.*.local.md` file (e.g., a repo-shipped rule reviewed and merged by a maintainer who doesn't notice the missing `-` prefixes, or a rule generated by a non-YAML-aware tool/script). The mistake (indented mapping fields without a leading dash under a list key) is a common and easy-to-make YAML authoring error, and because the custom parser has no catch-all/else branch and never raises, the bug is 100% silent and reliably reproducible for any rule authored this way.

### Recommendation
Add an explicit "unrecognized line" branch in `extract_frontmatter` that raises a `ValueError` (or logs a hard, propagated warning) for any line inside an active list context that matches none of the expected patterns, instead of silently dropping it. Additionally, `Rule.from_dict`/`load_rule_file` should treat a rule with `action == 'block'` and an empty `conditions` list as a load-time error (raise/reject) rather than silently constructing a Rule object that can never match, and this rejection should be surfaced to the user (not only to stderr, which is not included in the hook's JSON output).

### Proof of Concept
Unit test in `plugins/hookify/core` test suite:
```python
from hookify.core.config_loader import extract_frontmatter, Rule
from hookify.core.rule_engine import RuleEngine

def test_dashless_conditions_silently_empty():
    content = '''---
name: block-secrets
enabled: true
event: bash
action: block
conditions:
  field: command
  operator: regex_match
  pattern: "curl .*api.internal"
---
Blocked!
'''
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # This currently fails: conditions ends up [] with no error raised anywhere
    assert rule.conditions != [], "conditions silently dropped by parser"

    engine = RuleEngine()
    input_data = {
        "tool_name": "Bash",
        "tool_input": {"command": "curl https://api.internal/secret"}
    }
    result = engine.evaluate_rules([rule], input_data)
    # Block rule should fire but currently returns {} (no block), proving silent bypass
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
```
Expected current (buggy) behavior: `rule.conditions == []` and `evaluate_rules` returns `{}` (operation allowed) with no warning surfaced anywhere in the hook's stdout JSON, confirming the silent block-rule bypass.
