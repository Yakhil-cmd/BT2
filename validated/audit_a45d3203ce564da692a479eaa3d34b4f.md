### Title
Webhook Signature Verification Is Not Bound to the Repository the Payload Actually Writes To — Cross-Organization/Cross-Repository Writes ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate the incoming HMAC signature based on an attacker-influenced field inside the very payload being verified (`repository.owner.login`, falling back to `organization.login`), but nothing in the engine subsequently confirms that this same organization matches the repository that the downstream webhook handlers actually act upon (looked up via `repository.full_name`/similar payload fields). This is the same class of bug as the reported "slippage limits are not enforced on-chain" finding: a value that gates a state-changing action (which secret authorizes the request) is decoupled from the value that determines what is actually written (which repository/stack is mutated), and the binding between the two is never checked.

### Finding Description
`verify_signature` resolves which organization's webhook secret to verify against purely from payload content: [1](#0-0) [2](#0-1) 

The HMAC check itself only proves the payload was produced by someone who holds `Org_X`'s `webhook_secret` — it says nothing about which repository the payload content describes elsewhere: [3](#0-2) 

Once the signature is accepted, `WebhooksController#create` hands the raw, attacker-controlled JSON straight to the registered handlers with no further validation of internal consistency between `repository.owner.login`/`organization.login` (the field used to select and validate against the secret) and the repository/stack the handler resolves and mutates: [4](#0-3) 

Because `Shipit` supports multiple organizations, each configured with its own independent `webhook_secret` (`config/secrets.development.shopify.yml` shows this per-org structure), and each Stack maps 1:1 to a `repository.full_name`, a request signed with Org A's secret can carry a `repository`/`full_name` payload field pointing at an entirely different Stack belonging to Org B. Nothing in `verify_signature` or `Hook`/handler dispatch cross-checks that the two must match. [5](#0-4) 

This mirrors exactly the bug class in the report: the value used to gate/authorize the operation (`repository_owner` chosen for signature verification) is not the same value enforced when the state-changing action is actually carried out (the repository/stack a handler mutates), so the "authorization" and the "effect" can silently diverge.

### Impact Explanation
An attacker who legitimately controls (or has compromised) the webhook configuration for any single organization onboarded to a shared, multi-tenant Shipit instance can forge a webhook body whose `repository.owner.login`/`organization.login` matches their own org (so it passes `verify_webhook_signature` using their own known secret) while its `repository.full_name` (or other payload identifiers consumed by handlers such as push/status/check_suite/membership handlers) references a Stack belonging to a completely unrelated organization/repository. Depending on which event/handler is targeted, this can drive unauthorized state changes for a Stack the attacker has no legitimate relationship with — e.g., forcing a `GithubSyncJob`, injecting fabricated commit statuses, or manipulating membership/team records tied to another organization's Stack — constituting a cross-repository write performed with credentials scoped to a different, unrelated repository.

### Likelihood Explanation
Exploitability requires only knowledge of one organization's `webhook_secret` in a multi-org deployment (i.e., being an onboarded/legitimate tenant of the Shipit instance for *some* organization), not any privilege over the victim organization/repository. This satisfies an "organization that authenticated versus the repository that is written" boundary crossing. Note: I was unable to directly inspect the internals of `push_handler.rb`, `membership_handler.rb`, `handler.rb`, and `repository.rb` in this session (tool errors on the final call prevented reading them), so I cannot cite the exact field names each handler uses to resolve the target Stack/repository beyond what is visible in `webhooks_controller.rb`. This should be verified against those handler implementations before treating this as fully confirmed.

### Recommendation
After `verify_signature` succeeds, explicitly re-derive the organization/owner from the same trusted field the handler will use to resolve the Stack/Repository (e.g., `repository.full_name`'s owner segment), and reject the request (422) if it does not match the organization whose secret validated the signature. This closes the gap between "who authorized this payload" and "what this payload is allowed to modify."

### Proof of Concept
Conceptual (unverified end-to-end due to missing handler inspection):
1. Attacker administers Org A's GitHub App integration in a multi-tenant Shipit deployment and knows Org A's `webhook_secret`.
2. Attacker crafts a JSON body where `repository.owner.login` (or `organization.login`) = `"org-a"`, but `repository.full_name` = `"org-b/victim-repo"` (a Stack belonging to an unrelated org).
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(org_a_secret, body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and `verify_webhook_signature` succeeds because the signature was computed correctly with `org-a`'s real secret.
5. `Shipit::Webhooks.for_event(event)` handlers process the body and resolve/mutate the Stack for `org-b/victim-repo` based on `repository.full_name`, without any check that `org-b` matches the `org-a` identity that authorized the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
