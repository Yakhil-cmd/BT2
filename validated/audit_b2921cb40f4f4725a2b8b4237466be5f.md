### Title
Webhook organization used for signature verification is never bound to the repository/commit actually written - forged CI status and cross-stack sync in `WebhooksController` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is the same trust-binding defect as the RocketNodeDistributor `extcodesize` bug: a value that is "verified" (the GitHub App/organization whose secret authenticates the request) is not the same value that is actually acted upon (the repository/commit that gets written to). In Shipit's webhook pipeline, the organization used to select the HMAC secret for signature verification is read from an attacker-controlled JSON body, but the code path that decides *which repository or commit* to mutate reads a *different* field from that same attacker-controlled body, with no cross-check that the two agree.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration (and therefore the `webhook_secret` used for HMAC verification) using `repository_owner`, which is read straight out of the unauthenticated JSON payload: [1](#0-0) [2](#0-1) 

Once verification passes (using whatever org's secret matched `repository_owner`), the event is dispatched to handlers that determine what to write from a *different* field of the same body:
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')`, independent of `repository_owner`: [3](#0-2) 
- `StatusHandler#process` doesn't scope by repository at all — it looks up **any** commit in the entire instance by `sha` and writes a CI status to it: [4](#0-3) 
- `PushHandler#process` resolves the stack to resync via `stacks` (built from `repository_name`, i.e. `full_name`), not from `repository_owner`: [5](#0-4) 

Because Shipit supports multiple onboarded GitHub organizations, each with its own App installation/`webhook_secret` (`Shipit.github(organization: ...)`, documented per-org config): [6](#0-5)  a party that legitimately controls one onboarded organization's installation (and therefore knows that org's `webhook_secret`) can craft a payload where:
- `repository.owner.login` / `organization.login` = **their own org** (so `verify_signature` picks their own known secret and the HMAC check passes), while
- `sha` (for `status` events) or `repository.full_name` (for `push` events) references a **different, victim org/repository's** commit or stack.

Nothing ties the org whose secret authenticated the request to the repository/commit that the handler subsequently mutates.

### Impact Explanation
For `status` events this is the most severe: `Commit.where(sha:)` has no repository scoping, so an attacker who runs their own onboarded GitHub org can forge a passing (`success`) commit status for an arbitrary commit sha belonging to a victim stack they have no access to. Shipit's deploy spec uses commit statuses to gate whether a commit is deployable/mergeable (`required_statuses`, `blocking_statuses`): [7](#0-6) . A forged passing status can satisfy CI gating and enable an **unauthorized deploy or merge** on a repository the attacker does not control — this matches the "unauthorized deploy, rollback or merge" Critical-tier impact category. The `push` case additionally lets a foreign org trigger `stack.sync_github` on a victim stack it doesn't own, an unauthorized cross-repository interaction.

### Likelihood Explanation
Requires only that the attacker legitimately control one onboarded GitHub organization/App installation in a multi-organization Shipit deployment (no Shipit session, API token, or GitHub Team membership needed) — a realistic scenario for a shared multi-tenant Shipit instance, and does not require any host misconfiguration beyond the documented multi-org support.

### Recommendation
Bind verification and action to the same field: derive the authenticating organization identically to the field the handlers use to select the target repository/commit (e.g. always resolve from `repository.full_name`'s owner segment), and additionally re-check, inside each `Handler`, that the resolved repository/commit genuinely belongs to the organization whose secret verified the request before performing any write (especially in `StatusHandler`, which currently performs no repository scoping check at all).

### Proof of Concept
1. Attacker onboards/controls GitHub org `attacker-org` in the shared Shipit instance and knows its `webhook_secret`.
2. Attacker sends a `status` webhook with body `{"repository": {"owner": {"login": "attacker-org"}, "full_name":"attacker-org/repo"}, "sha": "<victim-commit-sha>", "state": "success", ...}`, HMAC-signed with `attacker-org`'s `webhook_secret` in `X-Hub-Signature`.
3. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s app, and the signature check passes.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and writes a `success` status for the victim commit, with no ownership check against `attacker-org`.
