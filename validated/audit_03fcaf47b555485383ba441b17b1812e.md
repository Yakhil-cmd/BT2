### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone with no repository/stack scoping, unlike `PushHandler` which correctly restricts its query to `stacks.not_archived.where(branch:)`. An attacker who controls any repository registered in the same multi-tenant Shipit instance can send a validly-signed `status` webhook naming a sha that also exists in a victim's unrelated stack, and Shipit will write a status onto the victim's commit.

### Finding Description
The broken binding is: `Commit.where(sha: params.sha)` should be equivalent to `stacks.joins(...).where(sha: params.sha)` (i.e. scoped to `Handler#stacks`, which is derived from `payload.dig('repository', 'full_name')`), but it is not — it is a global, unscoped ActiveRecord query across the entire `commits` table: [1](#0-0) 

Compare with `PushHandler`, which correctly scopes to the authenticated repository's stacks before mutating anything: [2](#0-1) 

`Handler#stacks` exists precisely for this purpose but `StatusHandler` never calls it: [3](#0-2) 

The webhook signature check in `WebhooksController#verify_signature` only proves that the payload genuinely came from GitHub for the *attacker's own* `repository_owner`/organization — it does not, and cannot, restrict which rows `StatusHandler` is allowed to mutate: [4](#0-3) 

Exploit flow: the attacker owns/controls a repository that is legitimately registered as a tenant in the shared Shipit instance (or otherwise able to get a validly signed `status` event, e.g. via a fork with the GitHub App/webhook installed on their own org). They identify a victim's public commit sha from GitHub, then send a `status` webhook payload whose `repository.full_name` is their own repo but whose `sha` matches the victim's commit. `StatusHandler#process` calls `Commit.where(sha: params.sha)`, which returns every `Commit` row across all stacks/tenants sharing that sha (trivially true if the attacker names an existing victim sha, and specifically demonstrable when both stacks hold a commit with the identical sha), and calls `commit.create_status_from_github!(params)` on all of them — including the victim's commit belonging to a stack the attacker's webhook never authenticated for. This directly matches the listed Critical impact: "a payload for one repository mutating another's stack, commit, task or team."

None of the existing guards prevent this: `verify_signature` authenticates the sender's own organization, not the target row; `drop_unhandled_event` and `ExplicitParameters` only validate presence/shape of `sha`/`state`, not ownership; there is no `force_github_authentication`, `require_permission!`, or `stacks` scoping applied in `StatusHandler#process`.

### Impact Explanation
A `create_status_from_github!` call mutates the victim commit's CI status (`Shipit::Status`), which feeds `Commit#deployable?`, `Commit#blocked?`, and `Stack#schedule_merges`/continuous-delivery scheduling. An attacker can therefore force a victim's commit to appear "success" (unblocking deploys/merges it should not unblock) or "failure" (blocking legitimate deploys), for a stack they never authenticated against, using only a webhook against their own, unrelated repository. This is repeatable against any commit sha they can predict/observe, across arbitrary stacks in the same multi-tenant install, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the attacker needs some repository registered with valid Shipit/GitHub App webhook signing (i.e., a tenant repo they legitimately control, or the app installed on their own org/fork) — no session, API token, or `Shipit.github_teams` membership is required. Sha collision across repositories is exact-match only, so realistically the attacker needs to either predict/reuse a sha (as described, e.g. reproducing an identical commit object) or target a scenario where the same commit is legitimately pushed/mirrored into multiple stacks (common in Shipit setups where one physical commit is deployed via multiple stacks/environments) — in that ordinary case, this bug already fires with a naturally-shared sha without needing sha-forgery tricks at all. Attacker cost is a single crafted webhook POST.

### Recommendation
Scope the lookup in `StatusHandler#process` to `stacks` (as `PushHandler` does), e.g. `Commit.where(stack_id: stacks.select(:id), sha: params.sha)`, so only commits belonging to the authenticated `repository.full_name`'s stacks can be affected.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `repository_a` / `stack_a` and `repository_b` / `stack_b`.
2. Create `commit_a = create(:commit, stack: stack_a, sha: "deadbeef...")` and `commit_b = create(:commit, stack: stack_b, sha: "deadbeef...")` — same sha, different stacks/tenants.
3. Assert `Shipit::Commit.where(sha: "deadbeef...").count == 2` (both sides of the binding: unscoped query returns rows from both tenants).
4. Build a payload with `repository.full_name = repository_a.full_name`, `sha: "deadbeef..."`, `state: "success"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert `commit_b.reload.status.state == "success"` even though the payload's `repository.full_name` only authenticated `repository_a`/`stack_a`, proving cross-tenant mutation.
