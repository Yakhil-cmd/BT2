### Title
L1 BTC Lockup Outpoints Are Never Persistently Marked as Spent, Allowing the Same Bitcoin Lockup to Be Counted Multiple Times Toward `pox-5` Bond Sats Commitments - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond` in `pox-5.clar` accepts an L1 Bitcoin lockup proof (`btc-lockup`) and, via `verify-l1-lockups`/`validate-l1-lockup`, credits the staker with `sats-total` uSTX-equivalent sBTC weight for the bond, based on Bitcoin-chain proofs of locked outputs. The duplicate-outpoint protection (`seen-outpoints`) is scoped only to the single call's fold accumulator and is never persisted to contract storage. There is no map recording which `(txid, output-index)` pairs have already been used to credit a bond. As a result, the exact same, still-unspent Bitcoin lockup output can be submitted again in a later `register-for-bond` call (e.g., for a different `bond-index` whose `early-unlock-bytes` happen to match) to be credited a second time, double-counting the same locked BTC as backing for two separate protocol-bond commitments.

### Finding Description
`register-for-bond` computes `sats-total` from the caller-supplied lockup proof: [1](#0-0) 

This is delegated to `verify-l1-lockups`, which folds over the supplied `outputs` with a **freshly-initialized** `seen-outpoints: (list)` accumulator: [2](#0-1) 

`validate-l1-lockup` only checks each outpoint against the `seen-outpoints` accumulated *within this single call* (`is-none (index-of? seen-outpoints outpoint)`), then appends it, verifies the script/merkle proof, and adds `(get amount output)` to `sum`: [3](#0-2) 

There is no persistent, contract-level map (e.g. a `used-l1-outpoints` map keyed on `txid`/`output-index`) anywhere in the reviewed `pox-5.clar` code that records outpoints once they are credited. The dedup is transient — it exists only for the duration of one `fold` call. Consequently, once `register-for-bond` returns successfully for `bond-index` A using outpoint `O`, nothing stops the same staker from calling `register-for-bond` again later for a different `bond-index` B (as long as `B`'s `early-unlock-bytes` bond parameter matches what was actually embedded in `O`'s Bitcoin output script — a condition that can arise from ordinary, non-malicious bond configuration reuse by the deployer, not requiring any privileged/colluding admin action) and resubmit the identical outpoint `O` to be credited `amount-sats` a second time.

Because the Bitcoin UTXO underlying `O` is never spent or otherwise marked used by this contract-side verification (it only checks a CLTV/hashlock script commitment and a merkle inclusion proof against the Bitcoin header, not that the output is "fresh" or previously unclaimed), the same locked BTC can back multiple `protocol-bond-memberships` entries simultaneously (for different `bond-index` values across time, since `bond-overlaps-new-position?` only prevents *overlapping* bond terms for the *same* staker, not reuse of the underlying Bitcoin collateral across non-overlapping bond terms).

This breaks the equality that `sum(amount-sats credited across all active bond memberships backed by L1 proofs) == sum(actual distinct locked BTC outputs)`. The same BTC lock is double-counted as two separate, valid stacking commitments.

### Impact Explanation
Per the rules, double-counting a commitment corresponds to a Critical/High-impact issue. Concretely:
- `amount-sats` feeds directly into `protocol-bonds-total-staked`, per-cycle bond/signer/staker shares (`add-staker-to-bond-cycles`), and ultimately reward computation (`bondRewardsPerToken`) and signing-weight bookkeeping.
- A staker who has locked BTC once could re-present the same lockup proof to register for a second (later, non-overlapping) bond period, receiving reward-earning stake weight and/or signer-eligibility credit twice for a single real BTC commitment, without additional BTC ever being locked.
- This inflates the "commitment" side of the pox-5 protocol's accounting relative to what is actually secured on Bitcoin L1, i.e., reward slots / signing weight exceeding the actual locked value — one of the explicitly listed High-impact equality breaks.

### Likelihood Explanation
Exploitation requires only an unprivileged staker: they need one real (or even an already-used) L1 BTC lockup transaction whose script parameters (`staker`, `staker-unlock-bytes`, `unlock-burn-height`, and the target bond's `early-unlock-bytes`) validate against a *different* bond period than the one it was first used for. Because `early-unlock-bytes` is a bond-wide configuration value (not staker/lockup-specific), it is plausible for multiple bonds set up over time by the deployer to share identical `early-unlock-bytes` (e.g., an empty/default early-exit script), in which case reuse across bonds is trivial and requires no colluding admin action — just calling `register-for-bond` twice with the same `btc-lockup` proof for two different `bond-index` values whose terms don't overlap for that staker.

### Recommendation
Persist a contract-level map (e.g., `used-l1-lockup-outpoints: {txid: (buff 32), output-index: uint} -> bool`) and have `validate-l1-lockup` (or `verify-l1-lockups`) `map-insert` each outpoint into this durable map, asserting the insert succeeds (i.e., the outpoint was not already used in any prior call, not just within the current fold), before returning the accumulated `sum`. This should be scoped independent of `bond-index` so the same real-world BTC lock cannot ever back more than one protocol-bond membership.

### Proof of Concept
1. Staker `S` locks BTC in a Bitcoin transaction using a P2WSH output constructed via `construct-lockup-output-script` for `staker = S`, some `unlock-burn-height`, `staker-unlock-bytes`, and `early-unlock-bytes = E` (matching a bond configuration `E`).
2. Deployer sets up `bond-index = 0` with `early-unlock-bytes = E`. `S` calls `register-for-bond(bond-index: 0, ..., btc-lockup: ok({outputs: [O], staker-unlock-bytes: ...}))`. This succeeds, crediting `amount-sats` for bond 0, and the bond term eventually ends (unlock cycle passes, `S`'s membership is settled/rolled or the bond simply completes).
3. Deployer later sets up `bond-index = 6` with the same `early-unlock-bytes = E` (a very plausible, non-malicious configuration reuse).
4. After bond 0's term has ended for `S` (so `bond-overlaps-new-position?` does not block it), `S` calls `register-for-bond(bond-index: 6, ..., btc-lockup: ok({outputs: [O], ...}))` again, submitting the **same** outpoint `O`.
5. `validate-l1-lockup`'s `seen-outpoints` check only guards against duplicates *within this second call's* `outputs` list; it has no memory of `O` having been used in step 2. The merkle/script/CLTV checks pass again (the Bitcoin output and header are unchanged and still valid), so `sats-total` for bond 6 is credited again using the same underlying locked BTC.
6. `S` now holds `amount-sats` credit in both bond 0's historical accounting and bond 6's live accounting from a single real BTC lock, inflating cumulative reward/signing-weight bookkeeping relative to actual BTC locked.

Note: I could not fully confirm the absence of a persistent "used outpoints" map across every part of `pox-5.clar` due to index size limits on this codebase snapshot — a background Devin session with full file access should verify by grepping the complete `pox-5.clar` (and any related migration/state maps) for a persistent outpoint-tracking map before treating this as fully proven.

        (staker principal)
        (bond-index uint)

            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        })
    )
    (let (
            (bond (unwrap! (get-protocol-bond bond-index) ERR_BOND_NOT_FOUND))
            (accumulation (try! (fold validate-l1-lockup (get outputs lockups)
                (ok {
                    sum: u0,
                    staker: staker,
                    minimum-unlock-height: (get-bond-l1-unlock-height bond-index),
                    staker-unlock-bytes: (get staker-unlock-bytes lockups),
                    early-unlock-bytes: (get early-unlock-bytes bond),
                    seen-outpoints: (list),
                })
            )))
        )
        (ok (get sum accumulation))
    )
