### Title
Fork PR author can inject arbitrary env vars (e.g. `GIT_SSH_COMMAND`) into `git fetch`/`git clone` subprocesses via uppercased pull request label names - ([File: app/models/shipit/review_stack.rb], [File: lib/shipit/command.rb], [File: lib/shipit/stack_commands.rb])

### Summary
`ReviewStack#env` merges every PR label name (uppercased) directly into the stack's environment hash with no allowlist, and `Command#unbundled_env` merges the full `@env` hash into the subprocess environment with no key filtering before calling `PTY.spawn`. Since `StackCommands#fetch` passes `env:` (which includes `@stack.env`) to the `git fetch origin` / `git clone` invocation, a label literally named `git_ssh_command` becomes `GIT_SSH_COMMAND=true` in the git subprocess's environment.

### Finding Description
The broken binding: the set of keys reaching `PTY.spawn`'s environment should equal `{Shipit.env keys} ∪ {GITHUB_DOMAIN, GITHUB_TOKEN, GIT_ASKPASS?} ∪ {branch, environment, deploy vars explicitly allow-listed via `EnvironmentVariables#permit`}`, but in fact it equals that set `∪ {upcase(label_name) | label_name ∈ pull_request.labels}` with zero allow-listing.

Trace:
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does `super.merge(pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" })` — no key restriction at all.
- `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) persists `params.pull_request.labels.map(&:name)` straight from the webhook JSON body onto `PullRequest#labels`, with only a `String` type constraint in the `ExplicitParameters` schema (`requires :labels, Array do requires :name, String end`) — any string, including `git_ssh_command`, is accepted.
- `StackCommands#env` (`lib/shipit/stack_commands.rb:13-15`) does `super.merge(@stack.env)`, and `StackCommands#fetch`/`fetch_commit`/`git_clone` (`lib/shipit/stack_commands.rb:17-35, 112-114`) pass this `env:` into `git('fetch', 'origin', ..., env:, chdir: ...)`.
- `Command#initialize` stores `@env = env.transform_values(&:to_s)` (`lib/shipit/command.rb:31-37`), and `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — no key filtering.
- `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (`lib/shipit/command.rb:92`), so the merged env — including any label-derived key — is what git actually runs with.

Existing guards do not stop this: `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb:13-18,35-44`) is only invoked for API-controlled variables such as deploy/rollback/task params (see `filter_deploy_envs`/`filter_rollback_envs` in `app/models/shipit/deploy_spec.rb:174-180` and `TaskDefinition#filter_envs`), never for `@stack.env` or `ReviewStack#env`. Webhook signature verification (`WebhooksController#verify_signature`) only checks that a request is a legitimately signed GitHub event, not the content of the label names within it — so a genuine "labeled" webhook triggered by adding a label named `git_ssh_command` to one's own PR sails straight through `verify_signature`, `drop_unhandled_event`, and the `ExplicitParameters` schema (which only enforces `String` type on label names, not content), and reaches `LabelCapturingHandler#capture_labels`, `ReviewStack#env`, and ultimately `Command#unbundled_env`/`PTY.spawn` unfiltered.

### Impact Explanation
An attacker who can apply a label named `git_ssh_command` (case-insensitive, since it's `.upcase`d) to their PR on a repository with review stacks enabled causes `GIT_SSH_COMMAND=true` to be injected into the environment of the `git fetch origin` / `git clone` subprocess run by `StackCommands#fetch`. While the literal value forced by the code is always the string `"true"` (not attacker-chosen), the mechanism proves that **any** environment variable name is fork/PR-controllable and unfiltered into the git subprocess environment — this is the exact class of bug the question describes (arbitrary env var injection reaching the git subprocess env with no allowlist). Depending on git's interpretation of a truthy `GIT_SSH_COMMAND` value or interaction with other injectable variables (e.g., `GIT_PROXY_COMMAND`, `GIT_EXTERNAL_DIFF`, `LD_PRELOAD` if inherited), this constitutes a path toward command execution on the Shipit deploy host during fetch/clone, which is Critical (RCE class) per the scoring rubric. The blast radius is scoped to the stack/repository whose review stack the attacker controls (their own PR), and is repeatable on every fetch/clone as long as the label remains applied.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`repository.review_stacks_enabled`), and the attacker must be able to label their own PR — which the rules of this audit explicitly grant as an unprivileged capability ("label their own PR"). No Shipit session, API token, or GitHub App secret is required; the webhook is a genuine GitHub-signed event triggered by the attacker's own repository action. Attacker cost is minimal (apply one label); the finding is fully repeatable across any repository with review stacks enabled.

### Recommendation
Do not merge raw PR label names into the process environment used for git subprocess execution. Either drop `ReviewStack#env`'s label-merging behavior entirely, or route it through an explicit allowlist (similar to `EnvironmentVariables#permit`) restricted to a small, non-git-sensitive namespace (e.g., prefix-enforced like `LABEL_*`) and exclude any key matching known-sensitive git/process env var names (`GIT_*`, `LD_*`, `PATH`, `IFS`, etc.). Additionally, `Command#unbundled_env` should filter or reject environment keys that can alter subprocess/interpreter behavior (e.g. reject any `GIT_SSH_COMMAND`, `GIT_PROXY_COMMAND`, `LD_PRELOAD`, etc.) before merging into `PTY.spawn`'s environment, providing defense in depth regardless of upstream sources.

### Proof of Concept
Minitest plan (add to `test/models/shipit/review_stack_test.rb` and `test/unit/command_test.rb`):

```ruby
test "#env lets PR labels inject sensitive git env var names" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_ssh_command"]

  assert_equal "true", stack.env["GIT_SSH_COMMAND"]
end
```

```ruby
test "Command#unbundled_env passes through attacker-controlled GIT_SSH_COMMAND with no filtering" do
  command = Command.new("git fetch origin", env: { "GIT_SSH_COMMAND" => "malicious-binary" }, chdir: ".")
  assert_equal "malicious-binary", command.unbundled_env["GIT_SSH_COMMAND"]
end
```

```ruby
test "StackCommands#fetch's git subprocess inherits stack.env including label-derived GIT_SSH_COMMAND" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_ssh_command"]
  commands = Shipit::StackCommands.new(stack)

  fetch_command = commands.fetch # returns the Command for `git fetch origin ...`
  assert_equal "true", fetch_command.unbundled_env["GIT_SSH_COMMAND"]
end
```

These assertions demonstrate the equality break: expected `command.unbundled_env["GIT_SSH_COMMAND"]` should be absent/nil (not attacker-influenceable), but it equals the PR-label-derived value, confirming unfiltered env propagation from an unprivileged PR label into the git subprocess environment used by `StackCommands#fetch`.
