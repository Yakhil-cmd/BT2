### Title
Unrecoverable RAY accrual overflow permanently freezes a saturated lending market - ([File: common/src/rates/index.rs])

### Summary
A market whose scaled balances approach the `i128` RAY-value ceiling can be pushed into a state where every subsequent operation that touches the market panics during interest accrual. Once the next interest factor makes `borrowed * borrow_index` exceed `i128::MAX`, `accrue_step` fails before it can commit the advanced timestamp or indexes. [1](#0-0) [2](#0-1) 

### Finding Description
Every pool mutation loads the market and calls `global_sync` before applying the operation. [3](#0-2)  The controller exposes ordinary supply, borrow, withdraw, repay, liquidation, and bad-debt paths that all reach these pool operations. [4](#0-3) 

During accrual, `accrue_step` first converts scaled debt and supply back to RAY values, then updates the borrow index and multiplies `borrowed` by both the old and new indexes. [1](#0-0) [5](#0-4)  `update_borrow_index` caps only the index itself; it does not account for whether the implied debt value still fits in `i128`. [6](#0-5)  The fixed-point multiplication panics with `MathOverflow` when the widened result cannot be represented as `i128`. [7](#0-6) [8](#0-7) 

Because the panic occurs in `accrue_chunk` before `mark_accrued` and before `Cache::commit`, the transaction rolls back without advancing `last_timestamp`; the next call attempts the same overflowing accrual again. [9](#0-8) [10](#0-9) 

The repository contains a deterministic reproduction: an 18-decimal market holding one billion whole tokens at 98% utilization eventually returns `MathOverflow` from `update_indexes`, after which even a one-unit withdrawal and a repayment fail with the same error. [11](#0-10) 

### Impact Explanation
This permanently freezes all funds in the affected `(hub, asset)` market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot settle positions touching the market, and bad-debt cleanup cannot burn the debt because those paths all synchronize the same market first. [12](#0-11) [13](#0-12) [14](#0-13) [15](#0-14) [16](#0-15) 

The failure is not a temporary price outage or paused-market condition: it is a deterministic arithmetic state reached through ordinary market growth. Once the next accrual crosses the `i128` value ceiling, there is no valid state transition that commits a lower index and restores operation. [9](#0-8) 

### Likelihood Explanation
An unprivileged account can establish the prerequisite book using only `supply` and `borrow`, subject to the listed market's caps and collateral requirements. [17](#0-16)  The borrow cap does not prevent the condition by itself because `MAX_BORROW_INDEX_RAY` bounds the index, not the product `scaled_debt * index` used to calculate accrued debt. [6](#0-5) [5](#0-4) 

The attack requires a very large token book and sustained high-utilization accrual, so its practical feasibility depends on the market's token supply and configured caps. However, the repository's own numeric limits acknowledge that admitted caps and bounded indexes do not ensure accrued market totals fit the RAY domain. [18](#0-17)  This is therefore a conditional but reachable **Medium** availability issue rather than a hypothetical host-budget denial of service.

### Recommendation
Make index updates headroom-aware before multiplying scaled balances:

1. In `update_borrow_index` and `update_supply_index`, calculate the largest index for which `scaled_balance * index / RAY <= i128::MAX` using `I256`.
2. Clamp the new index to the minimum of that headroom and the existing protocol index cap.
3. Recompute accrued debt and supplier rewards from the clamped indexes, allowing the accrual to commit and advance `last_timestamp` instead of panicking.
4. Alternatively, represent intermediate and stored market totals in a wider type, with explicit saturation and accounting rules at the protocol boundary.
5. Independently enforce listing caps that leave room for the configured market to reach `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY` without exceeding `i128`.

The key requirement is that the first accrual crossing the representable boundary must commit a safe bounded state; it must not repeatedly trap before `mark_accrued` and `commit`. [19](#0-18)

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
