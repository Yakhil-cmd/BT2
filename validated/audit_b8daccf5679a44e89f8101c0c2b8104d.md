Confirmed: `CCMenuController` (`app/controllers/shipit/api/ccmenu_controller.rb`) overrides `stack` to bypass the scoping that `BaseController` normally enforces. [1](#0-0) [2](#0-1) 

### Title
Stack-scoped `ApiClient` token authorizes reading any stack's CI status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuController#stack` overrides the base controller's stack lookup and resolves the target stack directly from `params[:stack_id]` via `Stack.from_param!`, bypassing the `stacks` scoping that every other API controller relies on to restrict a stack-scoped `ApiClient` to only its assigned stack.

### Finding Description
Shipit's API authorization model binds a token to at most one stack: `ApiClient#stack_id` and the `BaseController#stacks` helper enforce that a client is limited to `Stack.where(id: current_api_client.stack_id)` when `stack_id` is set, and only falls back to `Stack.all` for unscoped clients. [1](#0-0) 

`CCMenuUrlController` creates exactly this kind of scoped client for the CCMenu integration, minting a token scoped with `read:stack` permission for one specific stack: [3](#0-2) 

However, `CCMenuController` (which serves that CCMenu XML feed) defines its own private `stack` method that resolves `Stack.from_param!(params[:stack_id])` directly, without going through `stacks`/`current_api_client.stack_id?` scoping: [4](#0-3) 

The only authorization check applied is `require_permission :read, :stack`, which validates the permission *type* (`read:stack`) on the token but never checks whether the requested `stack_id` matches the scope the token was minted for: [5](#0-4) [6](#0-5) 

This breaks the binding: `stack a token authorizes == stack it touches`. Before the exploit, a scoped token is only supposed to read the one `Stack` it was created for. After an attacker simply changes the `stack_id` param on their request while authenticating with their own valid, narrowly-scoped token, they can read CCMenu XML for any stack in the installation — a cross-stack authorization boundary is crossed with a legitimately-issued but narrowly-scoped credential.

### Impact Explanation
This is an authenticated but unauthorized cross-stack read: any holder of a stack-scoped `ApiClient` token (e.g. a CCMenu integration token meant for one stack) can enumerate build/deploy state (`lastBuildStatus`, `activity`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of every other stack in the Shipit instance, including stacks belonging to unrelated repositories/teams they were never granted access to. This matches the documented High-impact class "unauthenticated read of stack state" in spirit — here it is a case of authorization-scope bypass rather than fully unauthenticated access, but it crosses the same trust boundary the `stacks` scoping exists to protect, using only a legitimately-issued low-privilege credential.

### Likelihood Explanation
High likelihood: exploitation requires only a valid stack-scoped API token (which any user with API-client creation rights, or anyone handed a CCMenu URL, already possesses) and changing the `stack_id` route parameter. No additional privileges, secrets, or session access are required beyond what's needed to obtain any single scoped token.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited `stack` (or `stacks`) method from `BaseController` instead of querying `Stack.from_param!` directly, so scoped tokens are restricted to their assigned stack:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. Create (or obtain) a stack-scoped `ApiClient` for `stack_a` with `read:stack` permission, e.g. via `CCMenuUrlController#fetch`, obtaining `token_a` and its `authentication_token`.
2. Send a request to another stack's CCMenu endpoint using `token_a`:
```
GET /api/1/stacks/<owner>/<repo>/<env_b>/ccmenu?token=<token_a>
```
where `env_b` belongs to `stack_b`, a stack `token_a` was never scoped to.
3. Observe the response renders `stack_b`'s CCMenu XML (`lastBuildStatus`, `activity`, etc.) successfully, instead of being rejected because `token_a.stack_id != stack_b.id`.
