### Title
Whale-scale market permanently freezes when `scaled_to_original` overflows `i128` before the borrow-index cap can engage - (File: common/src/rates/index.rs)

### Summary
The bug class from the external report — a multiply that is only checked against an outer bound (`u256`/`i128` max of the raw product) instead of the semantically bounded value, so the intermediate product reverts where the clamped result would have been fine — exists verbatim in XOXNO Lending's accrual path. `calculate_supplier_rewards` multiplies the full scaled `borrowed` balance by `new_borrow_index` via `Ray::mul` before any clamping is applied to the index. When `borrowed * new_borrow_index` exceeds `i128::MAX`, `mul_div_half_up` panics with `MathOverflow` even though `update_borrow_index` would have simply clamped the index to `MAX_BORROW_INDEX_RAY`. Every controller verb accrues first, so once the product crosses the cliff the market is permanently frozen: no `repay`, `withdraw`, `liquidate`, `supply`, `borrow`, or `update_indexes` call on that book can ever succeed again.

### Finding Description
In `common/src/rates/index.rs`, `calculate_supplier_rewards` computes:

```rust
let old_total_debt = borrowed.mul(env, old_borrow_index);
let new_total_debt = borrowed.mul(env, new_borrow_index);
```

where `borrowed` is the scaled debt shares (`Ray`) of the market and `borrow_index` is a RAY-scaled multiplier. `Ray::mul` delegates to `fp_core::mul_div_half_up`, which computes `borrowed * index / RAY` and panics with `GenericError::MathOverflow` if the result does not fit `i128` — even after widening the intermediate to `I256`, the *result* `borrowed * index / RAY` itself exceeds `i128::MAX` once `borrowed_raw * index_raw > i128::MAX * RAY`.

Separately, `update_borrow_index` clamps the index to `MAX_BORROW_INDEX_RAY`, but that cap is about the index's own magnitude, not the debt valuation — the test `test_borrow_index_at_the_ceiling_multiplies_without_overflow` only proves `ceiling * factor` fits, not `borrowed * index`. The overflow check is therefore placed on the wrong quantity, exactly like the external report: the guard (index cap at `MAX_BORROW_INDEX_RAY`) does not protect the multiplication that actually panics (`borrowed * index`). The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates this end-to-end: the panic surfaces inside `scaled_to_original` while `borrow_index < MAX_BORROW_INDEX_RAY`, i.e. "the index cap did not engage before the value overflow."

Because accrual is invoked unconditionally at the top of every state-changing entrypoint (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_*`, `multiply`, swaps, `update_indexes`, `recapitalize`), the first panic bricks the entire market. The test confirms both `try_withdraw_raw` and `try_repay` revert with `MATH_OVERFLOW` after the cliff.

### Impact Explanation
Permanent freezing of funds: once `borrowed * borrow_index` crosses `i128::MAX`, every user action on that market reverts forever. Suppliers cannot withdraw, borrowers cannot repay or be liquidated, and the protocol cannot even mark the bad debt or recapitalize the book. A billion-whole-token market (e.g. an 18-decimal asset) at sustained high utilization on the steep XLM rate curve reaches this cliff within a small number of accrual years, well below the 40-year documented bound, and the index cap never protects it.

### Likelihood Explanation
Reachable by an unprivileged address: `supply` a large token amount into a high-decimals market, `borrow` to high utilization, then let interest accrue via `update_indexes` (permissionless). The only requirement is market scale — the scaled `borrowed` must be large enough that a sub-`MAX_BORROW_INDEX_RAY` index multiplication overflows. For an 18-decimal token with 1e9 whole tokens supplied at ~98% utilization, the reproduction already exists in-tree and deterministically hits `MATH_OVERFLOW`. It requires a whale-scale deposit rather than any privileged action.

### Recommendation
Do not let the accrual path panic on `borrowed * new_borrow_index` when the only economically meaningful bound is the capped index. Options:
- Compute the debt valuation with `mul_div_floor_saturating`/`mul_div_ceil`-style saturating semantics (as `calculate_scaled_cap` and `protocol_fee_shares` already do) so `new_total_debt` saturates instead of trapping, letting accrual commit and the index cap engage.
- Alternatively, detect that `new_index` would drive `borrowed * new_index` over `i128::MAX` and clamp `new_index` to `i128::MAX * RAY / borrowed` before computing the totals, so the post-clamp accrual still commits.
- Apply the same treatment to the supply-side valuation `supplied.mul(old_index)` in `update_supply_index` and `supply_index_reward_shortfall`, which share the identical unchecked-product shape.

### Proof of Concept
Already implemented as an in-tree harness test at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs` (the `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` case):

```rust
t.supply_raw(BOB, "BIG18", BILLION * 10i128.pow(18));   // 18-decimal market
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);     // 98% utilization
loop { t.advance_time(YEAR_SECS); t.try_update_indexes_for(&["BIG18"])?; }
// → Err(MATH_OVERFLOW) while book.borrow_index < MAX_BORROW_INDEX_RAY
// → t.try_withdraw_raw(BOB, "BIG18", 1) = MATH_OVERFLOW
// → t.try_repay(ALICE, "BIG18", 1.0)    = MATH_OVERFLOW  (permanent freeze)
```

The overflow originates at `borrowed.mul(env, new_borrow_index)` inside `calculate_supplier_rewards` (`common/src/rates/index.rs:80-81`), reached via `scaled_to_original` (`common/src/rates/scaling.rs:14-16`), propagating `MathOverflow` from `fp_core::mul_div_half_up` — while `update_borrow_index` (`common/src/rates/index.rs:13-19`) clamps only the index, leaving the product unguarded.
