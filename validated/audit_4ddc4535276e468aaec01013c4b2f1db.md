### Title
ERC20Transactor withdraw commits real token transfer to checking account even when the XCM instruction returns an error, permanently stranding funds - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` executes an on-chain ERC20 `transfer` via `pallet_revive::Pallet::<T>::bare_call` to move tokens from the user to a `TransfersCheckingAccount`, then attempts to ABI-decode the boolean return value to decide whether to mint an `AssetsInHolding` credit for the XCM executor. If the underlying ERC20 contract does not return a value (or an unexpected value) on a successful, non-reverting `transfer` — the same class of non-standard-ERC20 behavior described in the reference report (e.g. legacy BNB/USDT-style tokens that omit the boolean return) — `abi_decode_returns_validate` fails and the function returns `Err(XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode"))` without producing any `AssetsInHolding` credit, even though the token transfer to the checking account has already been committed on-chain.

### Finding Description
`withdraw_asset_with_surplus` calls `bare_call` to invoke `IERC20::transferCall` on the registered ERC20 contract [1](#0-0) . Inside `pallet_revive`, a contract call's storage effects are committed as soon as the call itself does not revert, independent of what the caller of `bare_call` subsequently does with the result: `with_transaction` only rolls back on revert/error at the contract execution layer, and commits otherwise [2](#0-1) . This means once `bare_call` returns `Ok(return_value)` with `!return_value.did_revert()`, the ERC20 `transfer` from the user to `TransfersCheckingAccount` is already final in pallet_revive's own storage transaction scope.

`withdraw_asset_with_surplus` then tries to decode `return_value.data` as a `bool` via `IERC20::transferCall::abi_decode_returns_validate` [3](#0-2) . If the ERC20 token's `transfer` implementation returns no data (or malformed data) on success — the exact non-standard-ERC20 pattern flagged in the reference report — this decode fails and the function returns `Err(XcmError::FailedToTransactAsset(...))` without constructing any `AssetsInHolding::new_from_fungible_credit` [4](#0-3) . The XCM executor therefore treats the withdrawal as having failed and gives the caller no credit representing the tokens, while the tokens have physically already moved into `TransfersCheckingAccount` inside pallet_revive's committed state.

I was not able to fully verify within the available context whether the enclosing XCM instruction execution (`polkadot/xcm/xcm-executor/src/lib.rs`) or `pallet-xcm`'s `execute`/message-queue dispatch path wraps the whole instruction in an additional outer `with_transaction` that would independently roll back the `bare_call`'s already-committed inner transaction on `WithdrawAsset` failure. My searches did not find `with_transaction` usage in `polkadot/xcm/xcm-executor/src/lib.rs`, suggesting each `TransactAsset` call's storage effects are not further wrapped by the executor itself, but I could not exhaustively trace the full extrinsic/message-queue call chain (e.g. `pallet-xcm::execute`, `pallet_message_queue`, or Cumulus's inbound XCMP processing) to confirm whether any outer transactional boundary exists that would undo the pallet_revive-level commit.

### Impact Explanation
If the enclosing execution path does not fully roll back the inner `bare_call` commit on `WithdrawAsset` failure, user ERC20 tokens registered via `ERC20Matcher`/`ERC20Transactor` that don't strictly return a `bool` on `transfer` (matching the exact bug class in the reference report) would be irreversibly transferred into `TransfersCheckingAccount` with no corresponding `AssetsInHolding` credit ever created, and no path in this code to reclaim them — a direct fund loss for the token holder, analogous to "certain ERC20 tokens can get locked" in the reference report, but manifesting via a Substrate contracts-pallet/XCM boundary instead of a plain Solidity pool contract.

### Likelihood Explanation
Requires: (1) an ERC20 contract deployed on the parachain (via `pallet_revive`) whose `transfer` function does not return a `bool` on success (a known, real-world pattern, e.g. legacy USDT/BNB-style tokens); (2) that token being registered as a recognized fungible under `ERC20Matcher`; and (3) a normal signed user performing an ordinary XCM asset withdrawal/transfer of that token. No privileged role or malicious actor is needed — this is triggerable by any holder of such a token attempting a standard transfer.

### Recommendation
- Do not treat a decode failure of the ERC20 return value as unconditional proof that no state change occurred; instead, either (a) explicitly check the ERC20 contract's actual balance delta before/after the call rather than relying solely on the ABI-decoded return value, or (b) ensure the outer transactional boundary (executor/XCM instruction processing) fully and provably reverts the `bare_call`'s committed storage effects whenever `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` return an `Err`.
- Treat "call succeeded, but return data missing/malformed" as a success case (matching common non-standard ERC20 handling, similar to how OpenZeppelin's `SafeERC20` accepts empty return data) rather than as an unrecoverable failure, since the transfer already executed.

### Proof of Concept
No executable PoC was produced. Reproducing this requires deploying a `pallet_revive` contract whose `transfer` returns no data (or invalid data) on success, registering it through `ERC20Matcher` in an asset-hub-style runtime configuration, and running an integration test invoking `ERC20Transactor::withdraw_asset_with_surplus` (or a full XCM `WithdrawAsset` instruction) to confirm: (1) the ERC20 contract's internal balance/storage shows the transfer to `TransfersCheckingAccount` completed, (2) `withdraw_asset_with_surplus` returns `Err`, and (3) after the surrounding extrinsic/XCM message completes, no rollback restores the user's original ERC20 balance. This last step — confirming whether an outer transactional layer in `pallet-xcm`/message-queue processing masks or fails to mask the inner commit — was not verified against actual execution and remains the key open question determining whether this is a real, exploitable fund-loss condition or is neutralized by an outer rollback boundary I could not locate in the indexed code.
