Based on the code I was able to verify directly, this describes a real and serious authorization gap in the legacy burnchain PoX stacking path.

### Title
StackStxOp sender is copied from an unauthenticated PreStxOp output address, allowing an attacker to lock a victim's STX without their signature - (File: `stackslib/src/chainstate/burn/operations/stack_stx.rs`)

### Summary
`PreStxOp::parse_from_tx` sets `output` to whatever address appears in output index 0 of a Bitcoin transaction, with no requirement that the transaction's signer control that address [1](#0-0) . `StackStxOp::get_sender_txid` only validates that the StackStxOp's first input spends vout 1 of the referenced PreStxOp tx, with no check binding that spend to the address in vout 0 [2](#0-1) . The resulting `sender` (taken from the PreStxOp's `output` field, i.e. vout 0) is then used verbatim as the stacking principal in `StackStxOp::parse_from_tx` [3](#0-2) .

### Finding Description
The broken equality: **the principal whose STX gets locked by `stack-stx` == the principal that cryptographically authorized the lock**. Here, `sender` is derived purely from an arbitrary Bitcoin output address (`PreStxOp.output`, vout 0), which requires no signature or spend to create — any attacker can put any victim's Stacks-derived Bitcoin address into vout 0 of a self-funded PreStxOp transaction [4](#0-3) .

The only cryptographic requirement enforced by the protocol is that the follow-up StackStxOp transaction's first input spends vout 1 of that PreStxOp tx [2](#0-1) . Since vout 1 is an output the attacker created and funded themselves, the attacker fully controls it — there is no check tying the public key/signature used to spend vout 1 to the address named in vout 0. `StackStxOp::parse_from_tx` then unconditionally assigns `sender: sender.clone()` from this unauthenticated value into the op that is applied against the victim's on-chain STX balance [3](#0-2) .

Exploit flow:
1. Attacker builds a PreStxOp Bitcoin transaction with output 0 = victim's Stacks-derived BTC address, output 1 = an address the attacker controls, funded entirely from attacker's own BTC inputs.
2. Attacker broadcasts and confirms it; `classify_transaction`/burnchain indexing records it into the `pre_stx_op_map` keyed by its txid, with `output` = victim address.
3. Attacker spends output 1 (their own UTXO) in a new transaction carrying the `StackStx` opcode. `get_sender_txid` accepts this because vout==1 is satisfied.
4. The op is parsed with `sender` = victim's address, `reward_addr` = attacker's chosen PoX reward address (from the StackStxOp tx's own output 0), and whatever `stacked_ustx`/`num_cycles` the attacker encodes.
5. This op is applied to pox-4, locking the victim's STX balance for stacking while directing BTC rewards to the attacker's `reward_addr`.

No signature check from the victim's Stacks key is performed anywhere in this path — the entire chain of trust rests on the (false) assumption that whoever creates a PreStxOp naming an address as vout 0 is that same address's owner.

### Impact Explanation
An unprivileged attacker can force-lock an arbitrary victim's STX balance for one or more reward cycles without the victim's consent or signature, and can direct the resulting PoX BTC rewards to an attacker-controlled reward address. This matches the Critical bucket: theft of locked STX/sBTC rewards and locking of STX that was never authorized by its owner. The attack is repeatable against any victim address whose STX is unlocked and spendable, each time costing the attacker only Bitcoin transaction fees for a PreStx + StackStx op pair.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only their own BTC UTXOs (to fund the two-output PreStxOp transaction and later spend its second output) and knowledge of the victim's Stacks-derived Bitcoin address (public information). No privileged role, no signer key, no bond/pause admin access, and no victim cooperation is required. This is feasible in any reward cycle in which burnchain-based stacking ops are accepted (pre-sunset epochs) and the victim's targeted STX balance is unlocked at the time the op is applied.

### Recommendation
Require that the address in `PreStxOp.output` (vout 0) be provably controlled by the same party who later spends vout 1 — e.g., derive `sender` from the public key(s)/scriptSig actually used to spend vout 1 of the PreStxOp transaction, rather than trusting an unauthenticated output address field. Alternatively, disable/deprecate the legacy PreStxOp/StackStxOp burnchain path in favor of signed Clarity `stack-stx` contract calls (pox-4), which correctly require the stacker's Stacks-level signature.

### Proof of Concept
Rust integration test outline (booted chainstate, mirroring existing tests in `stackslib/src/chainstate/burn/operations/stack_stx.rs` and `stackslib/src/chainstate/coordinator/tests.rs`):
1. Create `victim_addr` (a `StacksAddress`) with a known STX balance and no signing key available to the test's "attacker" context.
2. Construct a `BitcoinTransaction` with opcode `PreStx`, funded from attacker's own inputs, `outputs[0].address` = `victim_addr`-derived Bitcoin address, `outputs[1].address` = attacker's own key.
3. Call `PreStxOp::parse_from_tx(...)` and assert `op.output == victim_addr` (equality #1: unauthenticated field == victim identity — already true by construction, showing no check exists).
4. Construct a second `BitcoinTransaction` with opcode `StackStx`, whose first input's `tx_ref` = `(prestx_txid, 1)`, signed only with the attacker's key (never the victim's).
5. Call `StackStxOp::get_sender_txid` and confirm it returns `Ok` (accepts the attacker-signed spend).
6. Call `StackStxOp::parse_from_tx(..., sender = victim_addr, ...)` and assert `op.sender == victim_addr`.
7. Feed the op through the burnchain-to-Clarity apply path (as in `coordinator/tests.rs`) and assert that `victim_addr`'s STX balance becomes locked (`STXBalance` locked amount increases) despite no Stacks transaction ever being signed by `victim_addr`'s key — this is the second half of the broken equality (STX locked belongs to victim; authorization belongs to attacker only).

Note: I was not able to fully trace `burnchains/burnchain.rs`'s `classify_transaction`/`pre_stx_op_map` construction and the exact point where op.sender-derived locking is applied into pox-4 within the available tool budget, so the final Clarity-side balance-locking step of the PoC should be validated against that code before treating this as fully confirmed.

    pub fn get_sender_txid(tx: &BurnchainTransaction) -> Result<&Txid, op_error> {
        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!("Invalid tx: StackStxOp must spend the second output of the PreStxOp");
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }
