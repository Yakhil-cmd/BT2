### Title
Prototype-Polluted Formula Cache Causes Permanent Evaluation Hang - ([File: formula/evaluation.js])

### Summary
`formula/evaluation.js` and `formula/validation.js` memoize parsed oscript ASTs in a plain JavaScript object `cache = {}` (defined in `formula/common.js`) keyed directly by the raw formula source string, with no `Object.create(null)` and no `hasOwnProperty` check [1](#0-0) . Any AA author, asset issuer, or oscript author fully controls the formula text embedded in `{...}` blocks throughout unit/AA definitions (init, getters, message templates, state formulas, asset conditions, data-feed conditions, etc). This is structurally the same bug class as CVE-2021-32773: a shared, improperly-scoped name→object resolution table lets attacker-supplied "module names" (here, formula-cache keys) collide with names the trusted runtime implicitly resolves through the prototype chain (`toString`, `constructor`, `hasOwnProperty`, `valueOf`, `__proto__`, `isPrototypeOf`, `propertyIsEnumerable`), causing the trusted evaluator to use the wrong "module" (an inherited `Object.prototype` function) instead of the intended freshly-parsed AST.

### Finding Description
In `evaluate()`:
```
var parser = {};
if(cache[formula]){
    parser.results = cache[formula];
}else {
    ... parser.feed(formula); cache[formula] = parser.results; ...
}
``` [2](#0-1) 

Because `cache` is a plain object literal, `cache[formula]` performs prototype-chain lookup. If an attacker crafts a formula whose exact text equals an inherited `Object.prototype` member name (e.g. `toString`, `constructor`, `hasOwnProperty`), the lookup returns the *inherited function*, which is truthy, **before any parsing is attempted**. `parser.results` is then set to that function object rather than to a parse-tree array.

At the end of `evaluate()`:
```
if (parser.results && parser.results.length === 1 && parser.results[0]) {
    evaluate(parser.results[0], res => {...}, true);
} else {
    if (parser.results.length > 1) { ... callback('ambiguous grammar', null); }
}
``` [3](#0-2) 

For `formula === "toString"`, `cache["toString"]` is `Object.prototype.toString`, whose `.length` is `0`. Neither branch's conditions are satisfied (`.length === 1` is false, and `.length > 1` is false), so **`callback` is never invoked** — the evaluation call hangs forever without ever resolving or rejecting. The same `cache` object and the same unguarded `if(cache[formula])` pattern is used identically in `formula/validation.js` [4](#0-3) , so the same collision can also stall AA-definition/formula validation.

### Impact Explanation
`evaluate()` is invoked from `aa_composer.js`'s `handleTrigger`/`replace()` for every AA message field, formula-valued key, and state-update formula reachable from a posted trigger unit [5](#0-4) , and from `callGetter()` for remote-AA getter calls that any AA's oscript can invoke on any address [6](#0-5) . If the callback for one of these formula evaluations is never invoked, the surrounding `async` control flow that drives AA-trigger response composition never completes for that trigger. AA-trigger processing is executed synchronously as part of stabilizing/writing units to the DAG; a trigger whose processing chain never completes prevents the writer from finishing that unit's post-stabilization work, which can stall the node's ability to progress to processing and confirming subsequent units — matching the "network unable to confirm new units" impact category. This is reachable by any unprivileged AA author who defines an AA with a formula field equal to a reserved `Object.prototype` name, or by any unprivileged trigger sender who feeds attacker-controlled data into a template evaluated as a formula.

### Likelihood Explanation
Trivial to trigger: an attacker only needs to author (or get someone to interact with) an AA whose definition contains, e.g., `init: "{toString}"` or a message field `"{constructor}"`, or otherwise cause a formula string exactly equal to `toString`/`constructor`/`hasOwnProperty`/`valueOf` to reach `evaluate()`/`validate()`. No special privileges beyond posting an ordinary AA-defining unit or trigger are required. The only constraint is that the collision word must reach `evaluate()` as the literal formula string (post `getFormula`/`fixFormula` extraction) which is straightforward given AA definitions are fully attacker-authored JSON/oscript.

### Recommendation
- Change `cache` in `formula/common.js` to `Object.create(null)` so it has no prototype chain, and/or replace the plain-object cache with a `Map`.
- Guard every `cache[formula]` lookup with `Object.prototype.hasOwnProperty.call(cache, formula)` in both `formula/evaluation.js` and `formula/validation.js`.
- Add a defensive `else` branch that always calls `callback`/`cb` with an error when `parser.results` is not a proper array, instead of silently falling through without invoking the callback.

### Proof of Concept
1. Post an AA definition containing a formula field whose extracted text equals an `Object.prototype` member name, e.g.:
```
['autonomous agent', {
  init: `{toString}`,
  messages: [ { app: 'data', payload: { x: 1 } } ]
}]
```
2. Have any user send a trigger payment to this AA address.
3. `aa_composer.js` calls into `formulaParser.evaluate` for the `init` formula with `opts.formula === "toString"` [7](#0-6) .
4. `cache["toString"]` resolves via the prototype chain to `Object.prototype.toString` (truthy), bypassing the nearley parser entirely [2](#0-1) .
5. At the end of `evaluate`, `parser.results.length` is `0`, so neither branch fires and `callback` is never called [3](#0-2) , leaving the AA-trigger handling for that unit permanently pending.
