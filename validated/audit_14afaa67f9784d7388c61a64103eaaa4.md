### Title
Attacker-controlled `Merge-Requested-By` commit-message field lets any pusher forge commit authorship to an arbitrary Shipit user - ([File: app/models/shipit/user.rb])

### Summary
`User.find_or_create_author_from_github_commit` blindly trusts a `Merge-Requested-By: <login>` line embedded in the raw commit message text and attributes authorship of the commit to that GitHub login, without verifying that the commit is actually the output of Shipit's own merge queue. Any commit synced from GitHub — whether reached via a normal push to the tracked branch or via a pull request head/base commit sync — passes through this same code path, so an attacker who can push a commit or open a PR containing this crafted message can bind an arbitrary existing user as the commit's author.

### Finding Description
The broken binding: the code assumes `commit.commit.message` containing `Merge-Requested-By: X` implies `X == the user who requested/authored this merge via Shipit's merge queue`. In reality, `commit.commit.message` is fully attacker-controlled free text, so the equality `attributed_author == actual_committer_identity` does not hold.

Code path:
- `GithubSyncJob#perform` → `append_commit` → `stack.commits.create_from_github!(gh_commit)` [1](#0-0)  is invoked for every new commit fetched from the stack's tracked branch (`stack.github_commits`), with no filtering for "merge-queue-produced" commits only.
- `Commit.create_from_github!` → `Commit.from_github` calls `User.find_or_create_author_from_github_commit(commit)` [2](#0-1) .
- `User.find_or_create_author_from_github_commit` regex-matches `github_commit.commit.message` against `/^Merge-Requested-By: ([\w\-.]+)$/` and, on match, returns `find_or_create_by_login!(match_info[1])` as the commit's `author` — completely bypassing `github_commit.author`/`github_commit.commit.author` (the actual GitHub identity) [3](#0-2) .
- The `MERGE_REQUEST_FIELD` string (`'Merge-Requested-By'`) is the same marker Shipit itself writes into merge commits it produces via the merge queue (`MergeRequest#merge_message`) [4](#0-3) , but nothing at the point of parsing verifies the commit actually originated from that trusted flow (e.g., checking `merge_request.merge_requested_by` on the associated `MergeRequest` record). The existing test `self.find_or_create_author_from_github_commit handles missing users on github` even demonstrates the field is parsed straight from an arbitrary `commit.message` string with no signature or provenance check [5](#0-4) .
- Separately, `identify_merge_request` (a `before_create` callback on `Commit`) does perform the authoritative check by looking up the stack's `MergeRequest` and using `merge_request.merge_requested_by` [6](#0-5) , but this callback fires **after** `author` has already been set by the untrusted regex match in `from_github`, and only overrides it when a matching `MergeRequest` row exists for that PR number in the message — it does not invalidate the initial untrusted assignment for ordinary pushes that don't correspond to a tracked pull request.

Attacker's exact action: push (or land, via a PR merged by GitHub directly rather than Shipit's merge queue) a commit whose message is:
```
ship it

Merge-Requested-By: victim-login
```
to the branch tracked by an onboarded Shipit Stack. The webhook signature check (`verify_signature`) only authenticates that the *payload* came from GitHub for *that repository* — it does not, and cannot, validate the semantic content of the commit message the repository owner (who may be the attacker's own fork/repo, or any contributor with push access) wrote. `Repository`/branch validators and `ExplicitParameters` schemas govern structural payload shape, not commit message content, so none of the listed guards intervene.

### Impact Explanation
Successful exploitation writes a `Shipit::Commit` row whose `author_id` points to `victim-login`'s `Shipit::User` record even though `victim-login` never touched the code, is not the GitHub committer, and may have no relationship to the pushing party. This is an authorization/identity-binding violation: commit attribution feeds `stacks_contributed_to`/`repositories_contributed_to`, task/commit UI display, and (per the report) downstream `SHIPIT_USER`/`GIT_COMMITTER_*` environment values used during task/deploy execution. An attacker can repeat this against any onboarded repository they can push to or PR against, for any victim login that resolves via `Shipit.github.api.user`, without needing any Shipit credential. This matches the "Critical" bucket's "attribution ... to a user who never pushed it" / identity-binding violation described in the question, though it is bounded by needing push/PR access to *some* onboarded repo — it does not directly enable an unauthorized deploy/rollback/merge by itself.

### Likelihood Explanation
Preconditions are modest: the attacker needs the ability to push a commit (or open a PR) to a repository already onboarded as a Shipit Stack — explicitly listed as in-scope "unprivileged" attacker capability — and the target login must resolve via GitHub's API. No Shipit secret, session, or team membership is required. The mechanism is deterministic and trivially repeatable across any number of commits/stacks/victim logins.

### Recommendation
In `User.find_or_create_author_from_github_commit`, do not trust the `Merge-Requested-By` text from an arbitrary commit message. Only apply the override when the commit is verified to be the actual merge commit tied to a `Shipit::MergeRequest` record whose `merge_requested_by` was set by Shipit's own trusted merge flow (i.e., rely on `Commit#identify_merge_request` / `MergeRequest#merge_requested_by` exclusively, and remove or gate the regex-based lookup in `User.find_or_create_author_from_github_commit` behind that same check), and always fall back to `github_commit.author`/`commit.author` for any commit not originating from a matched `MergeRequest`.

### Proof of Concept
```ruby
# test/models/users_test.rb (new test)
test "find_or_create_author_from_github_commit does not trust arbitrary Merge-Requested-By text" do
  victim = shipit_users(:walrus)
  attacker_github_identity = stub(id: 999_999, name: 'Attacker', login: 'attacker', email: 'attacker@evil.example', date: Time.now.utc)

  github_commit = resource(
    sha: 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef',
    author: attacker_github_identity,
    commit: {
      author: attacker_github_identity,
      committer: attacker_github_identity,
      message: "ship it\n\nMerge-Requested-By: #{victim.login}\n"
    }
  )

  author = Shipit::User.find_or_create_author_from_github_commit(github_commit)

  # Binding under test: author == actual committer identity (attacker), not the forged login.
  refute_equal victim, author
  assert_equal 'attacker', author.login
end
```
This assertion currently fails: `author` resolves to `victim` (via `find_or_create_by_login!('walrus')`) instead of the actual GitHub committer `attacker`, proving the misattribution.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
