### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but event handlers act on the independently-controlled `repository.full_name` field, allowing cross-organization/cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook's HMAC signature against using `repository_owner`, a value pulled from the JSON body itself (`repository.owner.login`, falling back to `organization.login`). Once the signature check passes, the `create` action re-parses the *same raw body* and dispatches it to event handlers that determine the target `Repository`/`Stack` using a **different** field of that same JSON body: `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`). Because the entire raw body is attacker-supplied and only its *bytes* (not its semantic consistency) are covered by the signature, an actor who legitimately controls one organization's webhook secret can craft a payload whose `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name` points at a completely different, unrelated organization/repository tracked by the same Shipit instance.

**Equality that should hold but doesn't:** `organization whose secret authenticated the request` == `organization/repository whose Stack is acted upon by the handler`.

**Before the attack:** `repository_owner` (`repository.owner.login`) is used both to select the verifying secret and (implicitly, in a legitimate GitHub-originated payload) matches `repository.full_name`'s owner, since both fields come from the same real GitHub event.

**After the attack:** An attacker who is an authorized member/admin of `OrgA` (and therefore legitimately knows `OrgA`'s configured `webhook_secret`, e.g., because they set up `OrgA`'s GitHub App integration in this multi-org Shipit deployment) can POST an arbitrary JSON body to `/webhooks` with:
- `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) — makes `verify_signature` pick `OrgA`'s `GitHubApp` and its secret.
- HMAC signature computed with `OrgA`'s known secret over the crafted raw body — passes `verify_webhook_signature`.
- `repository.full_name = "OrgB/victim-repo"` and other event-specific fields (e.g., `after`, `ref`) of the attacker's choosing.

Because `Handler#repository_name` and every handler's repository-lookup logic reads `repository.full_name`, not `repository.owner.login`/`organization.login`, the event is processed against `OrgB`'s stack even though the cryptographic authentication only proved knowledge of `OrgA`'s secret. This is the direct analog of the reported bug class: the field that was checked/authorized (`repository.owner.login`) is not the field that is actually acted upon (`repository.full_name`).

### Impact Explanation
This breaks the tenant/organization isolation boundary the multi-org webhook_secret design is meant to provide. Concretely, with a forged `push` event, an attacker controlling only `OrgA`'s secret can trigger `GithubSyncJob` for any stack under `OrgB`: [8](#0-7) 
This causes Shipit to sync git history/commits for `OrgB`'s stack using `OrgB`'s own GitHub credentials, and — because continuous-deployment/merge-queue stacks can automatically schedule deploys once new commits are synced — can lead to an unauthorized deploy pipeline action being kicked off for a repository the attacker has no legitimate relationship with. Other handlers (`status`, `check_suite`, `pull_request/*`) exhibit the same `repository.full_name`-based lookup and are equally susceptible to being invoked against an arbitrary tracked repository/stack, e.g. forging commit statuses or manipulating review-stack archival/unarchival for repos outside the attacker's own organization. This qualifies as a cross-organization/cross-repository write and a potential unauthorized deploy trigger — matching the Critical impact bucket ("cross-repository writes" / "an unauthorized deploy").

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate, unprivileged (with respect to the victim org) party who possesses a valid webhook secret for *any one* organization configured on the shared Shipit instance — which is exactly the multi-org deployment model the codebase documents and tests (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`). No GitHub App private key, Shipit session, `ApiClient` token, or repository write access to the victim org is needed; the attacker never needs to compromise `OrgB` at all. `/webhooks` is a public, unauthenticated (aside from HMAC) endpoint, and constructing an HMAC-SHA1 signature over an arbitrary payload with a secret the attacker already knows is trivial.

### Recommendation
Do not let handlers resolve the target repository/stack from a field (`repository.full_name`) that is disjoint from the field used to select/authenticate the signing organization (`repository.owner.login`/`organization.login`). Concretely:
- After signature verification succeeds for `repository_owner`, validate that `repository.full_name`'s owner segment matches `repository_owner` before dispatching to handlers, rejecting (422) any mismatch.
- Alternatively, thread the authenticated `repository_owner`/`github_app` context into each handler and have `Handler#stacks`/`#repository_name` scope lookups to repositories belonging to that authenticated organization only, rather than trusting the raw payload's `repository.full_name` unconditionally.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `OrgA` and `OrgB`, each with its own `github.webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), both tracking repositories/stacks in the same Shipit instance.
2. As an attacker who administers `OrgA`'s GitHub App (and thus knows `OrgA`'s `webhook_secret`), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(OrgA_webhook_secret, raw_body)>`.
4. POST to `/webhooks` with `X-Github-Event: push` and the header above.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully (per `app/controllers/shipit/webhooks_controller.rb#L24-30`).
6. `create` dispatches to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` (per `app/models/shipit/webhooks/handlers/handler.rb#L32-38` and `push_handler.rb#L12-17`) and enqueues `GithubSyncJob` for `OrgB`'s stack — despite the request only proving possession of `OrgA`'s secret.
