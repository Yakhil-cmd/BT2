### Title
Unauthenticated SSE access to `/events` leaks stack update notifications for arbitrary stacks - (File: config/routes.rb)

### Summary
`Shipit::Engine.routes.draw` mounts `Pubsubstub::StreamAction.new` at `/events` with no `Shipit::Authentication` concern or `before_action` in front of it, unlike every other route which is served by a `ShipitController` subclass that enforces `force_github_authentication`. Any unauthenticated caller can subscribe to `stack.<id>` channels and receive the `{id:, updated_at:}` payloads that `Stack#broadcast_update` publishes for that stack, regardless of the caller's authorization to that stack's repository.

### Finding Description
The binding the application implicitly relies on is: *"a caller subscribed to `stack.<id>` == a caller for which `User#authorized?`/`require_permission!` passed for that stack's repository."* This binding never holds for `/events`, because the mount: [1](#0-0) 

places `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` directly on `Shipit::Engine.routes.draw`, outside of any controller and thus outside of `ApplicationController`/`ShipitController`'s `include Shipit::Authentication` and `force_github_authentication` before-action machinery that every other route (e.g. `stacks#show`) goes through. `Pubsubstub::StreamAction` is a Rack endpoint from the `pubsubstub` gem, not a `ShipitController`, so it has no way to inherit those filters.

Every stack broadcasts its updates unconditionally on every `after_commit :broadcast_update, on: :update`: [2](#0-1) 

and the channel name used both to publish and to subscribe is just `"stack.#{id}"`, a sequential, guessable numeric primary key, as seen in the view that legitimately subscribes to it: [3](#0-2) 

Because `/events` has no authentication concern in front of it, any internet client can `GET /events?channels[]=stack.<id>` for any numeric `<id>` — including stacks belonging to private/other-tenant repositories the caller was never authorized to view — and receive that stack's live `update` events over SSE. No session cookie, `ApiClient` token, or GitHub OAuth completion is required. `verify_signature`, `force_github_authentication`, and `User#authorized?` are all bypassed simply because none of them are ever invoked for this route.

### Impact Explanation
The attacker obtains real-time confirmation that a specific stack ID exists and is currently being updated (its `updated_at` timestamp changes), without needing any credentials, for any tenant's private stack. This is a low-information leak (only `id` and `updated_at`, not deploy output/task logs/commit content), but it is an unauthenticated read of live stack-update events tied to a per-tenant resource that should require authorization, matching the "unauthenticated read of stack state" High-severity category in the rubric. It is trivially repeatable against every stack ID by iterating the numeric space, and requires no interaction with GitHub, webhooks, or victim behavior.

### Likelihood Explanation
No special Shipit or repository configuration is required beyond the engine being mounted as documented, which is assumed per the rules. The attacker only needs network access to the Shipit host and knowledge/guessing of a numeric stack ID (which are sequential and enumerable). Cost is a single unauthenticated HTTP request; the attack is fully repeatable and requires no secrets, sessions, or privileged roles.

### Recommendation
Wrap `/events` behind an authenticated controller action that validates the caller is authorized for every channel/stack ID requested before establishing the SSE stream (e.g., replace the bare `mount` with a controller action that includes `Shipit::Authentication`, parses `params[:channels]`, and calls `require_permission!`/`current_user.authorized?(stack.repository)` per channel before delegating to `Pubsubstub::StreamAction`), or otherwise validate/authorize each channel argument before calling `Pubsubstub.subscribe`.

### Proof of Concept
Minitest (`ActionDispatch::IntegrationTest`) plan:
1. Create a `Shipit::Stack` (`victim_stack`) belonging to a repository the test session is never authorized for.
2. Do not log in / set no session cookie and send no `Authorization` header.
3. `get "/events", params: { channels: ["stack.#{victim_stack.id}"] }` and assert the response is `200`/streaming (not a redirect to `/github/auth/github` or a `401`/`403`), contrasting with the same unauthenticated client hitting `stack_path(victim_stack)` which is redirected by `force_github_authentication`.
4. Stub/spy `Pubsubstub.publish` (or trigger `victim_stack.update!(...)` to invoke `broadcast_update`) and assert the SSE body received by the unauthenticated connection contains the published `{id:, updated_at:}` JSON for `stack.#{victim_stack.id}`.
5. Assert both sides of the binding explicitly: `current_user.authorized?(victim_stack.repository)` is `false`/`nil` (no session), yet the channel data was delivered anyway — proving the equality claimed by the finding is broken.
