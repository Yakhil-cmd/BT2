### Title
Premature division before multiplication causes rounding-down loss of stake rewards during Alpenglow migration epoch - ([File: runtime/src/inflation_rewards/mod.rs])

### Summary
In the `MigrationEpoch` branch of `calculate_stake_rewards`, the tower-portion of a stake account's inflation reward is computed by dividing before multiplying twice in sequence, instead of grouping all multiplications before the final division. This is the same rounding-down bug class described in the external report (multiplication performed on the result of a division), and it causes lamports that a delegator is entitled to for the migration epoch to be permanently lost.

### Finding Description
`calculate_stake_rewards` computes stake rewards for the special one-time epoch in which the cluster migrates from Tower BFT consensus to Alpenglow. For that epoch, the reward is split proportionally between the "tower" portion of the epoch and the "Alpenglow" portion of the epoch: [1](#0-0) 

The tower portion is computed as:
```
tower_points = (tower_points * point_value.rewards / point_value.points) * num_tower_slots / total_slots
```
instead of the mathematically equivalent, precision-preserving form:
```
tower_points = (tower_points * point_value.rewards * num_tower_slots) / (point_value.points * total_slots)
```
The intermediate `.checked_div(point_value.points)` truncates a fractional lamport amount before it is subsequently multiplied by `num_tower_slots` and divided again by `total_slots` (line 319-328) [2](#0-1) . This exactly mirrors the reported anti-pattern of "multiplication on the result of division," which discards precision that would otherwise be preserved if all multiplications were grouped before any division.

This result feeds directly into the stake/voter reward split and is ultimately paid out to the delegator's stake account via `redeem_stake_rewards`/`redeem_rewards`, which increments `stake.delegation.stake` by `staker_rewards` [3](#0-2) . Since `calculate_stake_rewards` is called for every stake delegation during normal epoch-boundary reward redemption (an unprivileged-user-facing accounting path, not a validator/operator-only code path), any lamports lost to this early truncation are never recovered — they are effectively dropped from what is minted/distributed to the staker for that epoch.

### Impact Explanation
During the single Alpenglow migration epoch, delegators receive slightly less than their mathematically correct tower-portion reward because of the compounded truncation from dividing twice instead of once. The truncated fractional lamports are not tracked or re-credited anywhere else in the reward pipeline, so they are permanently unclaimable by the affected stakers — consistent with the "permanent freezing of unclaimed yield" impact class from the analog report, applied here to a real, reachable Agave stake/reward accounting path.

### Likelihood Explanation
This code path executes unconditionally for every stake delegation whose reward is calculated during the migration epoch (`AlpenglowEpochType::MigrationEpoch`), which is a real, scheduled, one-time epoch transition in the protocol's consensus migration — not a contrived or validator-role-only scenario. No special privileges or malicious input are required; the truncation occurs purely as a function of normal `tower_points`, `point_value`, `num_tower_slots`, and `total_slots` values.

### Recommendation
Reorder the arithmetic so that all multiplications occur before any division, matching the pattern already used correctly for `earned_points` in `calculate_alpenglow_points` (single division after all multiplications) [4](#0-3) :
```rust
let tower_points = tower_points
    .checked_mul(u128::from(point_value.rewards))
    .and_then(|v| v.checked_mul(*num_tower_slots as u128))
    .expect("Rewards intermediate calculation should fit within u128")
    .checked_div(point_value.points.checked_mul(total_slots).unwrap())
    .unwrap();
```
This groups both multiplications ahead of the single combined division, eliminating the intermediate truncation while remaining within `u128` bounds (verify overflow headroom given realistic `rewards`, `num_tower_slots`, and `points` magnitudes).

### Proof of Concept
Using the values from the external report's PoC style, substituting the Agave migration-epoch formula:
```
tower_points = 1_000_000_000_000u128;   // representative points
rewards      = 999_999u64;              // representative per-epoch inflation reward
points       = 7_000_000_000_000u128;   // representative total points
num_tower_slots = 333u128;
total_slots     = 432_000u128;

// current (buggy) order:
current = (tower_points * rewards as u128 / points) * num_tower_slots / total_slots;

// corrected order:
fixed = (tower_points * rewards as u128 * num_tower_slots) / (points * total_slots);
```
With representative epoch-scale magnitudes, `current < fixed` whenever `(tower_points * rewards) % points != 0`, demonstrating the same class of lamport loss shown in the original report's Solidity PoC, now reproduced against the concrete `runtime/src/inflation_rewards/mod.rs` migration-epoch reward formula.
