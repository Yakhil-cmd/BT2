## Analysis

The Beedle report describes a bug where reward eligibility is based on an instantaneous balance snapshot taken at distribution time, rather than a time-weighted measure of participation — letting an attacker front-run the distribution, capture the full reward, and immediately exit with no real staking commitment.

The analogous pattern exists in ocore's **system-parameter voting** mechanism (governance voting for the witness/OP list and network TPS parameters), implemented in `countVotes()`.

### Root cause

When votes for a subject (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) are tallied, the voting weight of each address is computed from its **current stable balance at count time**, not a time-weighted or vote-time balance: [1](#0-0) 

The eligible voter set is any address that has *ever* cast a `system_vote` for the subject (`SELECT DISTINCT address FROM system_votes WHERE subject=?`), and the "recency" filter only checks that the *vote itself* (not the balance) falls inside the lookback window: [2](#0-1) [3](#0-2) 

The final tally joins the latest recorded vote (`op_votes` / `numerical_votes`) with `voter_balances`, which holds only the momentary balance read at count time: [4](#0-3) [5](#0-4) 

`system_vote` and `system_vote_count` are ordinary messages that any unprivileged unit author can post (only AAs are barred), so anyone can trigger this path: [6](#0-5) [7](#0-6) 

### Attack pattern

1. Attacker casts a cheap `system_vote` (e.g., for `op_list` or `threshold_size`) from an address with near-zero balance — this only needs to happen once, any time within the lookback window (up to a year, expanding further if turnout is low).
2. Just before the MCI that will trigger vote counting stabilizes, the attacker moves a large balance into that voting address (a single payment unit).
3. `countVotes()` reads the balance at that moment and assigns it full voting weight, even though the funds were never actually "staked"/held for governance purposes — they can be withdrawn again immediately after the count.
4. The attacker's vote (e.g., for a malicious/compromised witness in `op_list`, or extreme values for `threshold_size`/`tps_*` params) is weighted with a balance that existed for only a few seconds around the counting event, exactly analogous to the front-run staking reward from the report (deposit right before distribution → get proportional share → withdraw immediately after).

### Impact

`op_list` votes determine the network's order-providers (witnesses), and `threshold_size`/`tps_*` votes determine core validity/consensus economics parameters. Because the weight-determining balance can be transient and unrelated to actual long-term economic commitment, a well-funded but non-committed actor can repeatedly "flash" balance into pre-registered voting addresses at count time to swing witness-list or TPS-parameter outcomes, undermining the stake-weighted governance model and potentially pushing the network toward witness sets or parameters that cause validity/stability disagreement among nodes.

### Note on confidence

This is a governance-weighting design characteristic rather than a memory-corruption/direct-fund-theft bug, and it is plausible the ocore team considers "vote once, then balance-weighted at count time" to be intentional (similar to some snapshot-voting systems). I was not able to find any explicit time-weighting or minimum-holding-period safeguard in the code, so from a pure code-reachability standpoint the pattern matches the report's bug class (reward/weight granted based on point-in-time balance, no holding-duration requirement), but its severity classification (whether it's considered a "vulnerability" versus expected governance semantics) would need confirmation from the ocore maintainers/design docs, which are not in the indexed code.

### Title
Governance vote weight uses instantaneous balance at count time, allowing front-run "flash-balance" manipulation of `op_list`/TPS parameter votes - (File: `main_chain.js`)

### Summary
`countVotes()` in `main_chain.js` computes each voter's weight from their *current* stable balance at the moment vote-counting executes, not from balance held during the actual voting period. An address only needs a single historical `system_vote` message to remain eligible; an attacker can move a large balance into that address immediately before the counting MCI stabilizes and withdraw it right after, gaining outsized governance influence without any real economic commitment — mirroring the reported Beedle staking bug where reward eligibility depended on an instantaneous deposit rather than time-weighted stake.

### Finding Description
`system_vote` messages are validated and accepted from any unprivileged unit author (`validation.js` lines 1844-1851), and voter eligibility is determined purely by having *ever* cast a vote for the subject (`main_chain.js` line 1741). The recency filter (`since_timestamp` loop, lines 1807-1821) only checks vote timestamps, not balance history. The actual weight comes from `voter_balances`, populated from a live balance query at count time (lines 1757-1777), then joined with the latest vote per address to tally `op_list` (lines 1850-1863) or numerical parameters (lines 1882-1900). There is no mechanism ensuring the counted balance was held throughout the voting window.

### Impact Explanation
`op_list` controls the network's witness/order-provider set, and `threshold_size`/`tps_*` control core consensus fee/timing parameters. Manipulating these via transient balance injection could bias witness selection toward attacker-controlled or malicious addresses, or push TPS/fee parameters to attacker-favorable extremes, risking node disagreement on validity/stability of subsequent units.

### Likelihood Explanation
Requires only the ability to post ordinary units (payment + `system_vote`), no special privilege, and only needs a large balance for a brief window around the periodic vote-counting event (main-chain stabilization), which is a comparatively low-cost, repeatable attack for anyone with temporary access to significant funds (e.g., via a large loan/transfer round-tripped through the account).

### Recommendation
Weight votes by a time-integrated/time-weighted balance measure (e.g., average balance held over the voting window, or balance at multiple sampled checkpoints) rather than a single point-in-time balance read at count time, consistent with the report's recommendation to use a time-weighted reward/weight allocation algorithm.

### Proof of Concept
1. From address A (balance ≈ 0), post a unit with a `system_vote` message for `subject: "threshold_size"` (or `op_list`) with the attacker's preferred value.
2. Wait until close to the point where `main_chain.updateMainChain` → `countVotes` will next execute for that subject (triggered by stabilization following a `system_vote_count` message).
3. Immediately before that MCI stabilizes, send a large payment into address A.
4. After counting, `voter_balances` reflects A's large momentary balance, giving A's vote outsized weight in the tally (`main_chain.js` lines 1850-1900).
5. Immediately spend the funds out of A to another address, restoring A to near-zero balance — the vote's influence has already been "locked in" without any real holding period.
