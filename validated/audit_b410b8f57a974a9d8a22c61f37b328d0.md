## Title
Stack-scoped ApiClient token can read the CI/deploy status of any stack, not just the one it was scoped to - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces per-token stack scoping by routing all stack lookups through the `stacks`/`stack` helpers, which filter by `current_api_client.stack_id` when the token is stack-scoped. `Shipit::Api::CCMenuController` overrides `#stack` to resolve directly against `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks` collection, breaking the "stack a token authorizes" vs. "stack it touches" binding.

### Finding Description
`BaseController` defines the token-to-stack authorization binding as: [1](#0-0) 
`current_api_client.stack_id?` restricts the token to a single `Stack`; `stack` is resolved only from that restricted collection. All standard API resource controllers (e.g. `Api::StacksController`) rely on this `stack`/`stacks` helper for authorization.

`Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely, resolving the target stack directly from the unscoped `Stack` model using the client-supplied `params[:stack_id]`: [2](#0-1) 

The controller still declares `require_permission :read, :stack` [3](#0-2)  — this only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!` [4](#0-3) , it does not verify which stack the token is scoped to. Because `#stack` no longer routes through `stacks` (the `stack_id`-filtered scope), the `current_api_client.stack_id` restriction that the token owner/creator intended is never applied in this controller.

The `show` action then discloses per-stack CI/deploy state using this unauthorized `stack`: [5](#0-4) 

By contrast, the equivalent stack lookup in `Api::StacksController` correctly goes through the scoped helper: [1](#0-0) .

### Impact Explanation
A stack-scoped `ApiClient` token (an `ApiClient` record with `stack_id` set and only the `read:stack` permission — the minimal, deliberately-limited grant, e.g. as created automatically for the CCMenu URL feature itself: [6](#0-5) ) can be replayed against any other stack's `stack_id` in the `/api/stacks/:stack_id/ccmenu.xml` endpoint. This discloses that other stack's name, deploy activity, last build status, last build label (deploy id) and last build time — an unauthenticated-scope read of stack state beyond what the token was authorized for. This matches the "High - unauthenticated read of stack state" impact category, since the token's authorized boundary (one stack) is broken for a resource the same token was never meant to see.

### Likelihood Explanation
Any legitimate holder of a stack-scoped, read-only `ApiClient` token (a routine, low-privilege credential intentionally issued to restrict scope, and automatically generated for CCMenu integration by `CCMenuUrlController`) can trivially exploit this by changing the `stack_id` route parameter — no additional secrets, elevated permissions, or session are required beyond the token itself. Existing tests only exercise the "happy path" for the token's own stack and never assert scope enforcement here: [7](#0-6) , unlike `Api::StacksController`'s tests which explicitly verify stack scoping: [8](#0-7) .

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection inherited from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that stack-scoped tokens cannot read data for stacks outside their `stack_id`.

### Proof of Concept
1. As a legitimate low-privilege user, obtain a stack-scoped `ApiClient` token for Stack A with only `read:stack` (e.g. via the CCMenu URL feature, which auto-creates such a token: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, stack: stack_a, name: 'CCMenu Client')`).
2. Send `GET /api/stacks/<stack_B_id>/ccmenu.xml?token=<token_for_stack_A>` for an arbitrary Stack B the token was never scoped to.
3. Observe that `CCMenuController#stack` resolves Stack B via `Stack.from_param!(params[:stack_id])` (bypassing `stack_id?` scoping in `BaseController#stacks`), and the response renders Stack B's deploy/build status — data the token was never authorized to access.

Note: I could not locate a `Stack.from_param!`/`from_param` class-method definition in the indexed portion of `app/models/shipit/stack.rb` (it is inherited via a shared concern not fully surfaced by search); this does not affect the finding, since the scoping bypass is evident from the divergent code paths (`stacks.from_param!` vs. `Stack.from_param!`) regardless of `from_param!`'s exact implementation.
