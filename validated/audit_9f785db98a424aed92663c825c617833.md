### Title
Unbounded recursive query in `light/get_aa_response_chain` allows DoS of a full node/hub - (File: network.js)

### Summary
The `light/get_aa_response_chain` WebSocket API handler in [1](#0-0)  walks a chain of AA responses starting from an attacker-supplied `trigger_unit`, recursively issuing one DB query per hop (`addAAResponse`) with no cap on the number of hops, no cap on the number of rows accumulated in `all_rows`, and no pagination — unlike the sibling endpoint `light/get_aa_responses`, which explicitly caps results with `LIMIT 100` [2](#0-1) , or `light/get_history`, which enforces `MAX_HISTORY_ITEMS = 2000` and rejects oversized requests via `constants.lightHistoryTooLargeErrorMessage` [3](#0-2) [4](#0-3) , or `light/get_aa_state_vars`, which caps `limit` at `MAX_STATE_VARS` [5](#0-4) .

### Finding Description
`addAAResponse(trigger_unit, onDone)` queries `aa_responses` for all rows whose `trigger_unit` matches, then for every row whose `response_unit` is set, recursively calls itself using that `response_unit` as the next `trigger_unit`, chaining through `async.eachSeries`: [6](#0-5) 

There is no limit on:
- the total number of hops walked,
- the total number of rows pushed into `all_rows`,
- the time spent doing this recursive DB traversal.

This is reachable by any unprivileged light client simply by sending a `light/get_aa_response_chain` request with a `trigger_unit` of their choosing over the WebSocket JSON-RPC interface, requiring no authentication and no fee. If a chain of AA-to-AA responses exists that is long (built up organically over time by any AA whose response payments continue to feed further AA triggers, e.g. AAs that call each other or bounce/re-trigger over many separate top-level units posted over the network's lifetime), a single request forces the server to perform an unbounded, purely sequential series of DB round-trips synchronously inside `handleRequest`.

ocore's networking layer is effectively single-threaded per Node.js event loop (like the reported Aim web server), so a request that triggers thousands of sequential DB queries and pushes an unbounded response array blocks that event loop / connection-handling logic for an extended period, delaying processing of new unit gossip, validation, and other peer requests — matching the CVE-2024-12778 bug class exactly: "lack of a limit on the number of [items] that can be requested per call... leading to excessive resource consumption and blocking of the server."

### Impact Explanation
A malicious light client can force a full node or hub to perform an unbounded, synchronous DB-query chain and build an unbounded in-memory array, tying up the node's single-threaded event loop. Because ocore nodes multiplex unit propagation/validation and light-client servicing on the same event loop, this can delay the node's confirmation and forwarding of new units to the network, i.e., "a network unable to confirm new units" in the terms specified by the validation rules, and can also be used to exhaust node memory/CPU. This is a High-severity availability issue on any full node/hub serving `light/*` requests.

### Likelihood Explanation
Likelihood is moderate to high: no privilege is required beyond an open WebSocket connection to a hub/full node (the same posture as any light wallet), and the attacker fully controls the `trigger_unit` parameter used to start the walk. The chain length that can be exploited depends on the existence of a naturally long or attacker-constructed chain of AA-to-AA/response-to-trigger links, which sophisticated AA authors can deliberately build (e.g., an AA designed to have its response continually re-trigger further AA calls across many top-level posted units over time), making a long, exploitable chain readily obtainable without needing any special privilege beyond posting ordinary units/AA triggers.

### Recommendation
Add explicit bounds to `light/get_aa_response_chain` symmetric to the other `light/*` handlers:
- Cap the maximum number of hops/rows traversed (e.g., mirror the `LIMIT 100` used in `light/get_aa_responses`), returning an error such as "chain too large" once the cap is exceeded, similar to `constants.lightHistoryTooLargeErrorMessage` handling in `light/get_history`.
- Consider adding a request-level timeout/abort if traversal takes too long.
- Optionally support pagination (continue token) instead of returning the full chain in one response.

### Proof of Concept
1. As an AA author, publish a chain of AAs whose responses continually feed further AA triggers (each response's payment output targets another AA address), repeated across many separately-posted top-level trigger units over time, to build an `aa_responses` chain of substantial length (thousands of linked `trigger_unit -> response_unit` hops).
2. As an unprivileged light client, connect to the target hub/full node over its WebSocket API and send:
   ```json
   { "command": "light/get_aa_response_chain", "params": { "trigger_unit": "<unit that starts the long chain>" } }
   ```
   corresponding to the handler at [1](#0-0) .
3. Observe that the server performs one sequential DB query per hop with no limit, delaying its response and blocking further request/message handling on the same event loop, degrading availability for all connected peers/clients during the traversal.
