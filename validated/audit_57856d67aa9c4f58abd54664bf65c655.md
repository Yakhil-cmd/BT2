### Title
Cross-repository status webhook forgery via unscoped `Commit.where(sha:)` lookup triggers unauthorized continuous deployment - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by SHA (`Commit.where(sha: params.sha)`), unlike every other webhook handler which scopes work through `Handler#stacks` (filtered by the webhook's `repository.full_name`). Because git commit SHAs are content-addressed and identical across forks/mirrors of a repository, an attacker who owns or forks a repository can emit a legitimately-signed status webhook for a SHA that also exists as a `Commit` record belonging to an unrelated tenant's stack, injecting a fabricated `success` status that flips `Commit#deployable?` and triggers `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` for that unrelated stack.

### Finding Description
The broken binding is: `payload.dig('repository', 'full_name')` (the repository that actually sent the webhook) **should equal** `commit.stack.repository.full_name` (the repository that owns the targeted `Commit`) before that commit's state is mutated. `Handler#stacks` enforces exactly this equality for every other handler by resolving `Repository.from_github_repo_name(repository_name)&.stacks` first [1](#0-0) . `StatusHandler#process`, however, never calls `stacks` and instead does a global lookup:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This means any inbound, properly-signed `status` webhook — regardless of which repository sent it — is applied to **every** `Commit` row in the database whose `sha` matches, including commits belonging to stacks for entirely different repositories/tenants.

Exploit flow:
1. Attacker forks (or otherwise reproduces) tenant A's public repository. Git commit hashes are content-addressed, so commits shared with the upstream history keep identical SHAs in the fork.
2. Attacker installs/configures the Shipit GitHub App or webhook on their own repository (a repo they own — within their allowed capability) and pushes/creates a commit status (`success`) for one of those shared SHAs. GitHub sends a real, correctly-signed `status` event with `repository.full_name` = attacker's own repo.
3. `POST /webhooks` verifies the signature successfully (it is a genuine GitHub webhook for the attacker's own installation) and dispatches to `StatusHandler`.
4. `StatusHandler#process` ignores `repository_name` and finds the `Commit` record belonging to tenant A's stack that has the same `sha`, then calls `commit.create_status_from_github!(params)` [3](#0-2) , creating a `Status` row on tenant A's commit with the attacker-supplied `state: "success"`.
5. `Status`'s `after_commit :schedule_continuous_delivery` calls `commit.schedule_continuous_delivery` [4](#0-3) , which checks `deployable? && stack.continuous_deployment? && stack.deployable?` [5](#0-4) . `deployable?` is now true because of the forged `success` status [6](#0-5) .
6. `ContinuousDeliveryJob.perform_later(stack)` is enqueued for tenant A's stack; on execution it calls `stack.trigger_continuous_delivery` if the stack is not occupied and within schedule [7](#0-6) , ultimately spawning a deploy `Task`/`Command` using tenant A's `deploy_spec`/environment (including its `GITHUB_TOKEN`) — with zero involvement or approval from tenant A.

Existing guards do not stop this: webhook signature verification only proves the request came from GitHub for *some* installation the attacker legitimately controls (their own repo) — it says nothing about which `Commit`/`Stack` the payload is allowed to affect. The `ExplicitParameters` schema only validates field types/shapes, not repository ownership. `Repository.from_github_repo_name` / the `stacks` scoping method exists precisely to enforce this and is used everywhere except in `StatusHandler`.

### Impact Explanation
A payload originating from repository B (attacker-controlled) mutates state (`Status`, and transitively a `Deploy`/`Task`) belonging to repository A's stack, and can trigger an unauthorized deploy that executes `Command`/`PTY.spawn` with tenant A's deploy environment and `GITHUB_TOKEN`. This is a cross-tenant confused-deputy leading to unauthorized deploy execution on tenant A's host, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). It is repeatable against any stack/repository whose commits share SHAs reachable by an attacker-controlled fork (a very common scenario for any public repository), and is not limited to a single stack — any `Commit` row anywhere in the Shipit database with a matching SHA is affected by a single crafted webhook.

### Likelihood Explanation
Preconditions: (a) the target repository is public or otherwise forkable so the attacker can reproduce identical commit SHAs, (b) the attacker can get the Shipit GitHub App/webhook installed on a repository they own (a normal, low-privilege GitHub action), (c) the target stack has continuous deployment enabled and relies on CI status (`success?`) rather than `ignore_ci?` for deployability, and (d) the specific commit SHA is not yet deployed and not blocked by an intervening blocking status. Attacker cost is low — forking a repo and configuring a webhook/app installation requires no Shipit credentials, session, or secrets. It is fully repeatable across any commit/stack combination sharing SHAs.

### Recommendation
Scope `StatusHandler#process` the same way as all other handlers: resolve the commit only within the repository's own stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join `Commit` through `stack_id` restricted to `stacks` (as computed from `repository_name`), rejecting/ignoring status updates whose payload repository does not own the target commit's stack.

### Proof of Concept
Minitest plan under `test/`, mocking `Command`/`PTY` similar to existing continuous-delivery tests:

1. Create `stack_a` for repository `"tenant/a"` with `continuous_deployment: true` and CI-based deployability (not `ignore_ci?`).
2. Create `commit` under `stack_a` with a known `sha` (e.g. `"deadbeef" * 5`), not yet deployed.
3. Simulate the forged webhook: build a `status` payload with `repository.full_name = "attacker/fork"` and `sha` equal to `commit.sha`, `state: "success"`, and invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing only signature verification, which is out of scope of this bug).
4. Assert `commit.reload.status.state == "success"` even though the webhook's `repository.full_name` never matched `stack_a`'s repository — this is the broken equality (`repository_name != commit.stack.repository.full_name` yet the write still happened).
5. Assert `ContinuousDeliveryJob` was enqueued with `stack_a`; run `ContinuousDeliveryJob.perform_now(stack_a)` with `Command`/`PTY.spawn` mocked/stubbed, and assert a `Deploy`/`Task` record is created for `stack_a` and that the mocked spawn was invoked with `stack_a`'s environment — proving execution occurred for tenant A purely from tenant B's webhook.
