### Title

`withdraw` and `borrow` allow the all-zero account recipient - ([File: `contracts/controller/src/positions/supply.rs`])

### Summary

The controller accepts an optional recipient for collateral withdrawals and borrows, but only rejects the controller and pool addresses. An unprivileged owner or delegate can therefore pass an all-zero Stellar account address and have the pool transfer real assets to an account for which no corresponding signer can recover them.

### Finding Description

`Controller::withdraw` forwards `to: Option<Address>` into `process_withdraw`. [1](#0-0)   
`process_withdraw` defaults `None` to `caller`, but otherwise uses the supplied `to` verbatim after calling `require_external_recipient`. [2](#0-1)   
That guard checks only the controller and pool addresses, not the all-zero account address. [3](#0-2)   
The pool then debits cash and transfers the withdrawal amount to that recipient through the token contract. [4](#0-3) [5](#0-4)   
`Controller::borrow` has the same recipient-selection shape and applies the same incomplete guard before borrowing to `recipient`. [6](#0-5) 

### Impact Explanation

A successful withdrawal to the all-zero account burns the user's supply shares while sending the underlying assets to an address with no practical recovery path. A successful borrow likewise creates protocol debt while placing the borrowed assets outside the borrower's control. The result is permanent loss of the transferred assets, while the user's accounting position has still been consumed or the borrower's debt has still been created.

### Likelihood Explanation

The vulnerable path is directly reachable by the account owner or an authorized delegate through public `withdraw(caller, account_id, withdrawals, to)` or `borrow(caller, account_id, borrows, to)` calls. It requires the caller to supply the zero-account `Address` as `to`; the protocol performs the value transfer after accepting that recipient. This is primarily a severe user-input footgun rather than a third-party theft path, so the practical severity is medium.

### Recommendation

Reject the canonical all-zero account address in `require_external_recipient`, before any supply shares are burned or debt is created. Apply the check to every user-selected payout address, including `withdraw` and `borrow`; keep the existing controller and pool rejections.

Conceptually:

```rust
assert_with_error!(
    env,
    !is_zero_account_address(recipient),
    FlashLoanError::InvalidFlashloanReceiver
);
```

The check belongs in `contracts/controller/src/positions/mod.rs` inside `require_external_recipient`, so all current and future controller flows using that helper inherit it.

### Proof of Concept

A Soroban invocation can construct an account address whose Ed25519 public key is `[0; 32]` and pass it as `to`:

```rust
use soroban_sdk::{xdr, TryIntoVal, Vec};
use common::types::HubAssetKey;

let zero_recipient: soroban_sdk::Address = xdr::ScAddress::Account(
    xdr::AccountId(xdr::PublicKey::PublicKeyTypeEd25519(
        xdr::Uint256([0; 32]),
    )),
)
.try_into_val(&env)
.unwrap();

let withdrawals = Vec::from_array(
    &env,
    [(HubAssetKey { hub_id, asset }, amount)],
);

controller_client.withdraw(
    &caller,
    &account_id,
    &withdrawals,
    &Some(zero_recipient),
);
```

The controller maps `Some(zero_recipient)` directly to `recipient` and accepts it because `require_external_recipient` compares only against the controller and pool. [7](#0-6) [8](#0-7)   
The pool consequently performs `token.transfer(pool -> zero_recipient, net_transfer)` after debiting cash. [9](#0-8)

```rust
/// Rejects pool and controller recipients with `InvalidFlashloanReceiver`.
/// Pool self-transfers debit cash without moving tokens; controller receipts
/// would remain unclaimed by balance-delta accounting.
pub(crate) fn require_external_recipient(env: &Env, cache: &mut Context, recipient: &Address) {
    let pool = cache.cached_pool_address();
    assert_with_error!(
        env,
        *recipient != env.current_contract_address() && *recipient != pool,
        FlashLoanError::InvalidFlashloanReceiver
    );
```
