No vulnerability found for this question.

**Reasoning:**

The `ecdsa_recover_internal` native does have the length-related quirk implied by the question: the underlying `libsecp256k1::Message::parse_slice` only rejects messages longer than 32 bytes and zero-pads shorter ones (including empty vectors) rather than requiring exactly 32 bytes, despite the doc comment on `ecdsa_recover` in `secp256k1.move` implying a well-formed 32-byte digest. [1](#0-0) [2](#0-1) 

However, this only matters if reachable from an unprivileged, non-excluded transaction-admission path with attacker-controlled message length. The only place in the framework that calls `secp256k1::ecdsa_recover` with a message derived from external/attacker input is `ethereum_derivable_account::recover_public_key`, which is part of the domain/derivable account-abstraction authentication flow (`authenticate_auth_data` → `daa_authenticate`), i.e. AIP-104 Account Abstraction, which is explicitly excluded from scope. [3](#0-2) [4](#0-3) 

Moreover, even within that excluded flow, the `message` passed into `secp256k1::ecdsa_recover` is always `aptos_hash::keccak256(message)`, i.e. a fixed 32-byte hash output — never an attacker-supplied empty vector — so the zero-padding quirk in the native isn't actually reachable with a variable-length attacker input even in that (out-of-scope) path. [5](#0-4) 

No other production transaction-admission code (mempool, vm-validator, authenticator parsing, multisig/secondary-signer handling, or REST/BCS transaction ingestion) invokes `secp256k1::ecdsa_recover` with attacker-controlled variable-length data, so there is no path where this behavior could admit an otherwise-invalid transaction under the wrong sender/signer/fee-payer binding.

```text
    fun recover_public_key(signature_bytes: &vector<u8>, message: &vector<u8>): vector<u8> {
        let rs = signature_bytes.slice(0, 64);
        let v = signature_bytes[64];
        assert!(v == 27 || v == 28, EUNEXPECTED_V);
        let signature = secp256k1::ecdsa_signature_from_bytes(rs);

        let maybe_recovered = secp256k1::ecdsa_recover(*message, v - 27, &signature);

        assert!(
            maybe_recovered.is_some(),
            EINVALID_SIGNATURE
        );
```
