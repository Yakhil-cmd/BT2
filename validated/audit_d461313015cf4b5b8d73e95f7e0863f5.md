### Title
Cross-repository status webhook injection triggers merge-queue processing for unrelated stacks - ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/commit.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits with a global, unscoped `Commit.where(sha: params.sha)` query that never checks the webhook payload's `repository` against the `stack` that owns the matched `Commit` record. Because `Commit#add_status` unconditionally calls `stack.schedule_merges` on a pending/success transition, a validly-signed webhook originating from a repository the attacker controls can update the status of, and trigger merge-queue processing for, a completely different (victim) stack whenever a `sha` collision exists between the two repositories' commit graphs.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `webhook.payload.repository.full_name == commit.stack.repository.full_name` for every `Commit` mutated by the handler. In fact this equality is never checked.

Code path:
1. `StatusHandler#process` [1](#0-0)  looks up commits purely `Commit.where(sha: params.sha)` — with no filter on repository, org, or stack. `params` only requires `sha`, `state`, and optional descriptive fields [2](#0-1) ; nothing ties the resolved `Commit` back to the `repository` field of the payload that GitHub actually delivered.
2. For every matching `Commit` (there can be more than one across different stacks if the same git commit object exists in more than one repository, e.g., a shared upstream ancestor, a fork, or a manually re-pushed identical commit object), `commit.create_status_from_github!(params)` runs and internally calls `add_status`.
3. `add_status` compares `previous_status`/`new_status` and, on a state-class transition, unconditionally calls `stack.schedule_merges if new_status.pending? || new_status.success?` [3](#0-2) , where `stack` is `commit.stack` — i.e., whatever stack happens to own the row that matched on `sha`, not necessarily the repository named in the webhook payload.
4. `schedule_merges` fans out to `ProcessMergeRequestsJob`, which evaluates `MergeRequest#reject_unless_mergeable!`/`all_status_checks_passed?` against the queued merge requests of stack A.

Root cause: the handler trusts webhook signature validity (which only proves "this request came from GitHub for *some* app installation") as a proxy for "this request is authoritative for the commit I'm about to mutate." It never re-derives or checks the owning repository/stack from `params.repository` before mutating `Commit`/`Stack` state. `Commit` rows are also not uniquely scoped by `(stack_id, sha)` enforcement at the query layer used here — the handler intentionally iterates *all* stacks sharing that sha, which is fine for legitimate mirrored/forked history but becomes a cross-tenant primitive once an attacker can get GitHub to deliver a signed status event for an arbitrary sha they don't need write access to the victim's repo for.

Exploit flow: an attacker who owns/controls a public GitHub repository B, and who can get a webhook delivered to the Shipit host for B (e.g. via the Shipit GitHub App installed on their own repo, or their own configured webhook), pushes/imports the exact git commit object with sha `S` that is already present as a `Commit` row for victim stack A (e.g., the head commit of a currently queued `MergeRequest`, whose `Commit` row was created when the PR was synced against A). The attacker then sets a commit status (`state: success`) on sha `S` in repo B via the standard GitHub Statuses API, causing GitHub to emit a `status` webhook naming repository B. `StatusHandler#process` matches the `Commit` row belonging to stack A solely by `sha`, updates its status, and fires `stack.schedule_merges` for A — all without the attacker ever touching stack A's repository, session, or API token.

Why existing guards don't stop it: webhook signature verification (`verify_signature`/GitHub App signature check) only proves the request came from GitHub for a legitimate installation — it says nothing about which repository/stack the payload is entitled to mutate. `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape (`sha`, `state`, etc.), not repository ownership. No `stacks` scope, `require_permission!`, or model validation in `Commit`/`Stack` cross-checks `params.repository` against `commit.stack`.

### Impact Explanation
A payload authenticated for repository B causes a state mutation (`Status` creation) and a merge-queue evaluation (`schedule_merges` → `ProcessMergeRequestsJob`) for unrelated stack A, which the attacker does not own or control. This is a payload-for-one-repository-mutating-another's-commit/stack scenario — an unauthorized trigger of stack A's merge queue processing, matching the "Critical" impact category (payload for one repository mutating another's stack/commit, unauthorized merge). The blast radius spans every stack hosted on the same Shipit instance whose commit history can share a sha with an attacker-controlled repository (public forks, shared upstream history, or manually replayed git objects), i.e., cross-tenant on any multi-org Shipit deployment.

### Likelihood Explanation
Preconditions: (1) stack A has `merge_queue_enabled` and a queued `MergeRequest` whose head commit's sha is known to the attacker (visible on the public PR); (2) that sha must actually exist as a git object reachable to the attacker so they can push/import it into a repository they control and legitimately call the GitHub Statuses API on it (feasible for public forks/shared history, harder for genuinely private, isolated commits); (3) the attacker needs some Shipit-recognized repository (their own) able to deliver validly-signed webhooks (e.g., installing the same GitHub App used by Shipit on their own public repo, which any GitHub user can normally do). No Shipit session, API token, or secret is required. This is repeatable per request/per sha and requires no privileged role.

### Recommendation
In `StatusHandler#process` (and equivalent handlers that resolve `Commit`/`Stack` by `sha` alone), scope the lookup by the repository identified in the webhook payload, e.g. `Commit.joins(:stack).merge(Stack.where(repository: repo_from_payload)).where(sha: params.sha)`, rejecting/ignoring commits whose owning stack's repository does not match `params.repository.full_name`/`owner`. Alternatively, require the webhook's app installation/repository context to be resolved to a specific `Stack`/`Repository` record before any `Commit` mutation, mirroring the provenance check the push/pull_request handlers already rely on.

### Proof of Concept
Minitest outline (`test/models/shipit/webhooks/handlers/status_handler_test.rb` — to be added by engineering, illustrating the missing check):
```ruby
test "status webhook for repository B does not mutate commits/stacks belonging to repository A" do
  stack_a = shipit_stacks(:shipit)               # victim stack, owns repo "org-a/repo-a"
  commit_a = shipit_commits(:first)               # belongs to stack_a, sha: "aaaa...", queued MergeRequest head
  stack_a.update!(merge_queue_enabled: true)

  payload = {
    sha: commit_a.sha,
    state: "success",
    repository: { full_name: "attacker/repo-b" }, # attacker-owned repo named in payload
  }

  stack_a.expects(:schedule_merges).never

  Shipit::Webhooks::Handlers::StatusHandler.new(payload: payload, delivery: SecureRandom.uuid).process

  assert_equal "unknown", commit_a.reload.state # unchanged, since payload.repository != stack_a.repository
end
```
Both sides of the binding before the fix: `payload.repository.full_name == "attacker/repo-b"` while `commit_a.stack.repository.full_name == "org-a/repo-a"` — they diverge, yet `stack.schedule_merges` still fires because `StatusHandler#process` never compares them. After the recommended fix, the handler should skip `commit_a` because its stack's repository does not match `payload.repository`.
