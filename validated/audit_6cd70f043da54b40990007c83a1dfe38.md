### Title
Reused L1 Bitcoin lockup outpoint across sequential `register-for-bond` calls double-counts a single BTC timelock - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`verify-l1-lockups` / `validate-l1-lockup` in `pox-5.clar` only deduplicate Bitcoin outpoints *within the current call's* proof list via a freshly-initialized `seen-outpoints` accumulator. There is no persistent, cross-call map recording Bitcoin outpoints that were already credited by a prior successful `register-for-bond`, so the same confirmed L1 lockup transaction can be presented again in a later, non-overlapping `register-for-bond` call to mint a second bond membership and STX lock off the same never-re-spent Bitcoin UTXO.

### Finding Description
The invariant that should hold is: `sum(sats-total credited across all successful register-for-bond calls for a staker's L1 lockups) == sats locked ONCE by a confirmed Bitcoin timelock transaction`.

In `register-for-bond` [1](#0-0) , the L1 branch computes `sats-total` via `verify-l1-lockups`, which seeds a fresh `seen-outpoints: (list)` accumulator for every invocation [2](#0-1) . The fold function `validate-l1-lockup` rejects an outpoint only if it repeats *inside this same fold* via `(asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT)` [3](#0-2) . Nothing here — nor anywhere else in `register-for-bond` — checks the outpoint against outpoints already credited by a *previous* successful call (there is no map such as `used-l1-outpoints`; `grep` confirms `protocol-bond-memberships` and other maps track staker/bond state, not spent Bitcoin outpoints).

The remaining guards in `register-for-bond` (`verify-not-prepare-phase`, `bond-overlaps-new-position?` guarding `ERR_ALREADY_REGISTERED`, `verify-bond-rollover-window`) [4](#0-3)  only enforce that the staker's bond *terms* don't overlap in time — they say nothing about Bitcoin-outpoint reuse. Since the Bitcoin script committed to in the lockup (`construct-lockup-output-script`) bakes in a single `unlock-burn-height` [5](#0-4) , a staker who initially locks BTC with a sufficiently distant `unlock-burn-height` can satisfy `>= (get-bond-l1-unlock-height bond-index)` for many successive bonds' minimum-unlock checks [6](#0-5) . Because the UTXO is never actually re-spent on Bitcoin between calls (the "proof" is just a Merkle inclusion proof of the original confirmed transaction, not a proof of continued non-spend at present time — pox-5 has no mechanism to check the current UTXO set), the same confirmed transaction/output can be replayed as proof in a second, later, non-overlapping bond registration once the first bond's term has fully ended and the staker's STX has auto-unlocked.

Exploit flow:
1. Attacker locks BTC once in the canonical timelock script with an `unlock-burn-height` far enough in the future to satisfy several bond periods' `get-bond-l1-unlock-height`.
2. Attacker calls `register-for-bond(bond A, ..., ok {outputs: [proof], ...})`. `verify-l1-lockups` validates and returns `sats-total`; `register-for-bond` locks STX and records `protocol-bond-memberships` for bond A.
3. Bond A's term ends (STX auto-unlocks via `pox-locking`'s `handle_lockup_pox_v5`).
4. Attacker calls `register-for-bond(bond B, ...)` reusing the identical `proof` (same txid/output-index/merkle proof) for a non-overlapping later bond period. `verify-l1-lockups` re-validates the same outpoint from scratch (fresh `seen-outpoints`), succeeds, and a brand-new `sats-total`/STX lock/bond membership is created — all backed by the same, single, real BTC lockup.

### Impact Explanation
Each replay lets the attacker obtain a fresh bond membership, a fresh STX lock, and a fresh share of the bond's reward-slot/signer weight (proportional to `sats-total`) — all attributed to a single Bitcoin timelock that was only ever created once. This is a double-counting (in fact N-counting, repeatable every bond period until the BTC timelock's own CLTV height is reached) of a Bitcoin-side commitment, matching the Critical category ("double-counting a commitment or reward"). It also lets the attacker occupy allowlist `max-sats` slots repeatedly for the same nominal BTC collateral, distorting `get-total-shares-staked-for-cycle` and downstream reward distribution across multiple cycles from one real lockup.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: they only need one real confirmed L1 lockup with a generously far `unlock-burn-height`, be allowlisted for the target bonds (attacker-controlled bond config aside, allowlisting is typically bond-admin controlled, but the flaw is exploitable as soon as the staker is allowlisted for two non-overlapping bond periods, e.g., via legitimate onboarding for both). No signer or admin privilege is needed, no reentrancy, no chain-consensus assumption beyond the already-confirmed original transaction. The attack is fully repeatable every bond period until `unlock-burn-height` matures on Bitcoin.

### Recommendation
Add a persistent map (e.g., `l1-lockup-outpoints-used: {txid, output-index} -> bool` or `-> staker/bond-index`) that `validate-l1-lockup` checks and inserts into (via `map-insert`, asserting `ERR_DUPLICATE_LOCKUP_OUTPOINT` on failure) so an outpoint already credited in any prior successful `register-for-bond` call can never be credited again, in addition to the existing intra-call `seen-outpoints` check.

### Proof of Concept
Rust integration test extending `check_pox_5_register_for_bond_l1_lockup_lifecycle` in `stacks-node/src/tests/pox_5_integrations.rs`:
1. Set up bond 0 and bond 6 (non-overlapping), allowlist the staker for both, and create one real Bitcoin lockup with `unlock-burn-height` satisfying both bonds' `get-bond-l1-unlock-height`.
2. Call `register-for-bond(bond 0, proof)`, assert `ok`, capture `STXBalance.amount_locked()` == bond 0's expected sats-derived amount.
3. Mine past bond 0's unlock height so STX auto-unlocks (`amount_locked() == 0`).
4. Call `register-for-bond(bond 6, same proof)` and assert the current code returns `ok` (reproducing the bug) with a *second* `amount_locked()` equal to the same sats-derived amount — i.e., two locks from one BTC output.
5. Fixed test (after the recommended fix) should assert the second call reverts with `ERR_DUPLICATE_LOCKUP_OUTPOINT` (or a new dedicated error) and that `amount_locked()` remains unaffected by the second call.
