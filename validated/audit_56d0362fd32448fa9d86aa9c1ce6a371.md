### Title
Membership webhook lets an attacker join their own org's Team record to an existing privileged Team by `github_id`, or forge `params.organization.login` independent of the org whose secret signed the request - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the webhook secret using `repository_owner`, which is read from `params.dig('repository','owner','login')` with a fallback to `params.dig('organization','login')` — both attacker-supplied JSON fields with no cross-check against each other. `MembershipHandler#find_or_create_team!` then trusts a *separate* attacker-controlled field, `params.organization.login`, to set `team.organization`, and matches/creates the `Team` row purely by `params.team.id` (`github_id`), a value the attacker also fully controls in the JSON body. This breaks the binding "the org that signed the payload equals the org whose Team gains a member."

### Finding Description
Binding claimed: `signing_org(webhook_secret used in verify_signature) == params.organization.login (org written to team.organization / used to resolve team membership)`.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) does `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(signature, raw_post)`, where `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) is `params.dig('repository','owner','login') || params.dig('organization','login')`. Both are plain JSON fields inside the body the attacker fully constructs and signs with their own org's `webhook_secret`. [1](#0-0) 
- Nothing in `verify_signature`, `Handler`, or `MembershipHandler` enforces that `repository.owner.login` (used to select the HMAC secret) equals `organization.login` (used later to attribute the created team). The two are independent keys in the same attacker-crafted JSON document.
- `MembershipHandler#find_or_create_team!` resolves the Team purely by GitHub's numeric `team.id`: `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`). If a `Team` row with that `github_id` already exists (e.g., a privileged team referenced by `Shipit.github_teams`, itself created via `Team.find_or_create_by_handle`/`fetch_and_create_from_github`, `app/models/shipit/team.rb:17-27`), the block is **not** executed — `find_or_create_by!` just returns the existing record, ignoring `params.organization.login` entirely. `team.add_member(member)` (`app/models/shipit/team.rb:41-43`) is then called on that pre-existing, possibly privileged, `Team`.
- `User#authorized?` grants access solely via `teams.where(id: Shipit.github_teams.map(&:id)).exists?` (`app/models/shipit/user.rb:80-82`) — by primary key `id`, so any membership row attached to that exact `Team` record (regardless of which org's secret was used to add it) satisfies authorization.

Exploit flow:
1. Attacker owns/administers `attacker-org`, which is configured in Shipit and thus has a known `webhook_secret` they control (they set it on their own org's GitHub webhook config, or it's whatever secret Shipit is configured with for that org — the attacker only needs an org for which they know the secret Shipit uses, i.e., their own).
2. Attacker crafts a `membership` webhook JSON body: `{"action":"added","team":{"id":<privileged_team_github_id>,"name":"x","slug":"x","url":"x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker-user"},"repository":{"owner":{"login":"attacker-org"}}}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC verifies successfully — attacker's own secret over attacker's own body.
5. `MembershipHandler#process` runs `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: <privileged_team_github_id>)`. If that `github_id` matches an existing privileged `Team` (one already resolved into `Shipit.github_teams`), the existing record is returned untouched by the block, and `team.add_member(attacker_user)` adds the attacker directly to that privileged team's `memberships`.
6. Attacker is now authorized per `User#authorized?`, without ever having been added to the real GitHub team and without any secret beyond their own org's.

Why guards fail: `verify_signature` only proves the *body* was signed with *some* org's secret it can resolve from a field the attacker also controls; it never re-validates that the org used to pick the secret matches the org field used downstream in the handler, nor that the target `Team`'s `organization` matches the verified org. `find_or_create_team!` keys off `github_id` alone with no organization ownership check on the found record.

### Impact Explanation
This lets an unprivileged attacker escalate into `Shipit.github_teams` authorization (High/Critical category "escalation into `Shipit.github_teams` authorization") by adding themselves (or any GitHub login) as a member of a privileged Shipit `Team` row, using only their own org's webhook secret. The precondition of knowing the target's `github_id` (GitHub team IDs are opaque integers, but often discoverable via GitHub's public API for teams visible to the attacker, or via the org's public team listing) narrows likelihood but not exploitability once known. This is a genuine cross-tenant write: a payload "signed" for `attacker-org` mutates a `Team` row that is not scoped to `attacker-org`, contradicting the intended repository/org-scope binding. Blast radius: any org whose secret an attacker knows (including their own) can be used to add members to any `Team` row already in the database, regardless of that team's `organization`.

### Likelihood Explanation
Requires: (1) Shipit configured with at least one org for which the attacker knows/controls the `webhook_secret` (trivially true for the attacker's own org if the deployment is multi-tenant, or if the "org" concept maps to something the attacker can register), (2) the numeric `github_id` of the target privileged Team already existing as a row in Shipit's DB (created once via `Team.find_or_create_by_handle` at startup through `Shipit.github_teams`, or from prior legitimate membership events), (3) knowledge/guessing of that `github_id`. Cost is a single crafted HTTP POST with a valid HMAC computed from a secret the attacker legitimately possesses. No GitHub-side action or live GitHub API call is required to reach `find_or_create_by!`. Repeatable for `action: 'removed'` too, letting an attacker actively evict legitimate members from a privileged team.

### Recommendation
- In `MembershipHandler#find_or_create_team!`, require that a found (pre-existing) `Team`'s `organization` matches the verified `repository_owner`/organization used to authenticate the webhook, and raise/reject if they differ, instead of silently reusing the existing record.
- In `WebhooksController#verify_signature`, thread the resolved `repository_owner` through to handlers (or re-derive `params.organization.login` from the same verified field) rather than trusting a second, independently attacker-controlled JSON key for org attribution.
- Consider scoping `Team.find_or_create_by!` lookups to `(github_id:, organization:)` rather than `github_id` alone.

### Proof of Concept
```ruby
test "membership webhook cannot add member to a team owned by a different org than the one whose secret signed it" do
  privileged = Team.create!(github_id: 999, organization: "victim-org", slug: "developers", name: "Developers", api_url: "https://example.com")
  Shipit.stubs(:github_teams).returns([privileged])

  @request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'added',
    team: { id: 999, name: 'Developers', slug: 'developers', url: 'https://example.com' },
    organization: { login: 'attacker-org' },
    member: { login: 'mallory' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, body)
  @request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { Team.count } do
    post :create, body: body, as: :json
  end

  privileged.reload
  refute_includes privileged.members.map(&:login), 'mallory'
end
```
If the assertion fails (i.e., `mallory` is added to `privileged.members`), the vulnerability is confirmed as described.
