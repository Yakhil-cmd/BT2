### Title
Multi-org webhook signature-org selection lets a repository owner with their own Shipit-registered GitHub App forge webhooks written against a repository in a different organization — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a direct analog of the "depositor can spend funds of another depositor" pattern from the report: a caller-supplied identifier (`briber`/`bribeIdentifier`) is used to *authorize* an action, but a different, independently-controlled identifier is used to *execute* it, with no equality check binding the two. In `WebhooksController`, the organization used to select the webhook secret for signature verification is not the same field the event handlers use to decide which repository/stack gets written to.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration — and therefore the HMAC secret used to validate `X-Hub-Signature` — from the request body itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')`, and `Shipit.github(organization: repository_owner)` resolves to a *per-organization* config entry when Shipit is deployed with the multi-org secrets schema (`github: { orgA: {...}, orgB: {...} }`), as documented in `config/secrets.development.shopify.yml` and `lib/shipit.rb#github`/`#github_app_config`: [3](#0-2) 

Once the signature check passes, `create` hands the *entire raw payload* to every handler registered for the event, and the handler decides which `Repository`/`Stack` to mutate using a completely separate field, `payload.dig('repository', 'full_name')`: [4](#0-3) [5](#0-4) [6](#0-5) 

There is no check anywhere in the controller or in `Handler#stacks`/`#repository_name` that `repository.owner.login` (the field used to select the verifying secret) equals the owner segment of `repository.full_name` (the field used to locate the `Repository`/`Stack` to act on). The equality that should hold — "organization whose secret authenticated this request" == "organization of the repository actually written" — is never enforced.

Concretely, this breaks the binding: `verified_org(repository.owner.login) == written_repo_org(repository.full_name.split('/').first)`. GitHub itself always keeps these fields consistent for its own webhook deliveries, but the vulnerability is that Shipit's own code never re-validates this invariant — it trusts the payload to be internally consistent once *any* valid signature (from *any* configured org) is found.

### Impact Explanation
An organization that operates its own GitHub App entry in Shipit's multi-org `secrets.github` config (and therefore knows/controls its own `webhook_secret`, a routine, low-privilege administrative task for that org's own integration) can craft and correctly sign a payload where `repository.owner.login` is their own org (so the signature validates against their own secret) but `repository.full_name` names a repository belonging to a *different* organization hosted on the same Shipit instance. This is a cross-repository write: it can trigger `PushHandler` to enqueue `sync_github` against a victim org's stack, `commit_status`/`check_suite`/`pull_request` handlers to mutate statuses, labels, or archive/unarchive review stacks for a repository the attacker's org has no legitimate authority over. Per the stated impact criteria, cross-repository writes are Critical.

### Likelihood Explanation
This is only exploitable on deployments using the multi-organization `secrets.github` schema with more than one org configured, where each org's webhook secret is managed independently (documented and supported per `docs/setup.md`/`config/secrets.development.shopify.yml`). Given that setup, the attack requires no privileged Shipit account, no `ApiClient` token, and no compromise of the victim org — only the ability to send a signed POST to `/webhooks` using the attacker's own org's webhook secret, which the attacker is expected to possess for their own integration. Likelihood is therefore moderate-to-high specifically for multi-tenant Shipit deployments.

### Recommendation
In `Handler#stacks` (and any handler resolving a repository from the payload), verify that the organization segment of `repository.full_name` matches the `repository.owner.login`/`organization.login` that was used to select and validate the webhook signature, rejecting the event if they diverge. Alternatively, pass the verified organization from `WebhooksController` into each handler and require handlers to scope repository lookups to `Repository.where(owner: verified_organization)` rather than trusting `full_name` alone.

### Proof of Concept
1. Shipit is deployed with `secrets.github` containing two orgs, `orgA` and `orgB`, each with its own `webhook_secret`.
2. Attacker controls `orgA`'s GitHub App/webhook secret (legitimately, as the org's own admin).
3. Attacker POSTs to `/webhooks` with body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
   signed with `orgA`'s `webhook_secret` via `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "orgA")`, verifies the signature successfully (it was signed with `orgA`'s secret over this exact body).
5. `PushHandler#stacks` (via `Handler#repository_name`) looks up `Repository.from_github_repo_name("orgB/victim-repo")` and enqueues `sync_github(expected_head_sha: "<attacker-controlled sha>")` against `orgB`'s stack — a write against a repository/organization the attacker's credentials never authenticated for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
