### Title
CCMenu API endpoint bypasses stack-scoped `ApiClient` authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` establishes the authorization invariant that a stack-scoped `ApiClient` token may only touch the single `Stack` it is bound to: `current_api_client.stack_id?` gates whether `stacks` returns `Stack.where(id: current_api_client.stack_id)` or `Stack.all`. [1](#0-0) 
`Shipit::Api::CCMenuController` overrides `stack` to look up `Stack.from_param!(params[:stack_id])` directly, skipping the scoped `stacks` helper entirely, while still declaring `require_permission :read, :stack`. [2](#0-1) 

### Finding Description
`ApiClient` records optionally `belongs_to :stack` and are meant to be restricted to that stack when set, as demonstrated by the fixture `here_come_the_walrus` (`stack: shipit`, `permissions: [read:stack]`) and the corresponding test asserting a stack-scoped client "will only see that one stack" for the index endpoint. [3](#0-2) [4](#0-3) 

`ApiClient#check_permissions!` only checks whether the client's `permissions` array contains `"read:stack"` — it never checks which stack is being requested: [5](#0-4) 
The stack-binding is enforced purely at the controller layer via `stacks`/`stack` in `BaseController`. `CCMenuController` re-implements `stack` and drops that scoping, calling `Stack.from_param!` unconditionally: [6](#0-5) 

The equality that should hold is:
`current_api_client.stack_id == requested_stack.id` (or `stack_id` unset ⇒ global token)

Before the attacker's action: a stack-scoped token (e.g. `stack_id = A`, permission `read:stack`) can only fetch data for stack A through every other `Api::BaseController` subclass (`Api::StacksController`, `Api::DeploysController`, etc.), because they all resolve `stack` via the scoped `stacks` method.

After: the same token, presented to `GET /api/<stack_id=B>/ccmenu`, passes `require_permission :read, :stack` (permission string match only) and then `stack` resolves stack B unconditionally via `Stack.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id` check — breaking the binding.

### Impact Explanation
This lets the holder of a legitimately-issued, narrowly-scoped API token (issued for one stack, e.g., generated by `CCMenuUrlController#client` or created through any process that sets `ApiClient#stack`) read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`) for **any** stack in the Shipit instance, not just the one it was authorized for. This matches the "unauthorized read of stack state" High-impact category in scope, since it is an authorization-scope escalation reachable by an attacker who only possesses a low-privilege, single-stack token rather than a global one.

### Likelihood Explanation
High likelihood: stack-scoped tokens are a supported, intended use case of `ApiClient` (see the `stack_id?` scoping logic and its dedicated test coverage), and the only thing an attacker needs is possession of such a token (no need for a global API secret, GitHub credentials, or session). Exploitation is a single unauthenticated-style GET request substituting a different `stack_id` in the URL; `CCMenuController` is the sole controller under `Api::BaseController` that fails to route through the scoped `stacks` accessor.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to reuse the inherited scoping instead of bypassing it, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the custom override so that stack-scoped tokens can no longer resolve stacks outside their `stack_id`.

### Proof of Concept
1. Admin issues a stack-scoped `ApiClient` for stack A, e.g. via the CCMenu flow (`GET /ccmenu/*stack_A` → `CCMenuUrlController#fetch`) or any process that persists `ApiClient.create!(stack: stack_A, permissions: ["read:stack"], creator: user)`. [7](#0-6) 
2. Attacker obtains this token (`client.authentication_token`), scoped only to stack A.
3. Attacker requests `GET /api/<stack_B_owner>/<stack_B_name>/<stack_B_env>/ccmenu.xml?token=<token>` for an unrelated stack B.
4. `authenticate_api_client` succeeds via `ApiClient.authenticate(params[:token])`. [8](#0-7) 
5. `require_permission :read, :stack` passes because the token has `"read:stack"` in `permissions`, regardless of target stack. [5](#0-4) 
6. `stack` resolves stack B via `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id == stack_A.id`, and the controller renders stack B's build/deploy status — a stack the token was never authorized to touch. [9](#0-8)
