### Title
Webhook Handlers Trust `repository.full_name` From the Signed Payload Without Binding It to the Organization That Actually Verified the Signature - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The bug class in the external report (a value taken from attacker-influenced input is used to gate a security-relevant decision without validating it against the boundary that is supposed to constrain it) has an analog in `shipit-engine`'s webhook pipeline: the field used to pick *which organization's secret verifies the signature* (`repository.owner.login`) is never bound to the field used to *decide which repository/stack the event acts on* (`repository.full_name`). Any organization with a legitimately configured `webhook_secret` in a multi-org Shipit deployment can therefore sign a payload with its own secret while making the payload's `repository.full_name` point at a completely different, unrelated tracked repository.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to check the HMAC against using `repository_owner`, derived straight from the JSON body: [1](#0-0) [2](#0-1) 

Once the signature check passes, `WebhooksController#create` hands the *entire parsed payload* to the registered handlers with no further scoping: [3](#0-2) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) determines which `Stack`/`Repository` to operate on purely from `payload.dig('repository', 'full_name')`, via the shared base class: [4](#0-3) 

For example, `PushHandler#process` looks up stacks solely off that field and triggers a GitHub sync job for them: [5](#0-4) 

Nowhere is `repository.full_name`'s owner cross-checked against `repository_owner` (the organization whose secret actually validated the HMAC). Shipit explicitly supports configuring independent `webhook_secret`s per GitHub organization (see the multi-org config example), so the "authenticating organization" and the "repository being acted upon" are two different trust domains that this code silently conflates: [6](#0-5) 

This is the same class of defect as `_getBonusRewards()`: a value that determines a privileged outcome (which repo/stack gets acted on) is taken from data that was validated for a different, narrower purpose (that *some* org's secret matches *some* signature) rather than being properly bound/limited to that same scope.

### Impact Explanation
Any organization onboarded onto a multi-org Shipit instance (i.e., any org whose admin can install the Shipit GitHub App and thus knows its own `webhook_secret`) can send a validly-signed webhook to `/webhooks` while forging `repository.full_name`/`repository.owner.login` fields for the tracked-stack lookup to reference a repository belonging to an entirely different organization. This lets that org's holder trigger `GithubSyncJob` (`PushHandler`), `RefreshCheckRunsJob` (`CheckSuiteHandler`), commit-status writes (`StatusHandler`), and review-stack archive/unarchive/PR-label mutations (`PullRequest::*` handlers) on stacks it has no relationship to and no `ApiClient`/permission grant for. Because `sync_github` can feed into a stack's continuous-deployment pipeline, this crosses the "unauthorized deploy" bar for stacks with `continuous_deployment` enabled, since it lets an unrelated organization's credentials force sync/deploy-triggering behavior on someone else's repository — an authorization-boundary violation ("organization that authenticated" ≠ "repository that is written").

### Likelihood Explanation
Exploitation requires only that the attacker controls a legitimately configured GitHub organization/webhook secret on the same multi-tenant Shipit instance — not any Shipit session, `ApiClient` token, or the victim organization's secret. This is a realistic tenancy-isolation failure for any Shipit deployment serving more than one organization, which the codebase explicitly documents as a supported configuration.

### Recommendation
In `Handler#stacks`/`#repository_name`, or in `WebhooksController`, validate that the resolved `repository.owner.login` (used for stack/repository lookup) matches the `repository_owner` that was actually used to select and verify the webhook signature before dispatching to handlers. Reject events where the two diverge.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per the documented multi-org config).
2. As the admin of `attacker-org` (who legitimately knows `attacker-org`'s `webhook_secret`), craft a `push` event JSON body where `repository.full_name` = `"victim-org/victim-repo"` and `repository.owner.login` = `"attacker-org"`.
3. Sign the raw body with `attacker-org`'s `webhook_secret` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature. `PushHandler` then resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github`, acting on a stack the attacker's organization has no authorization over.
