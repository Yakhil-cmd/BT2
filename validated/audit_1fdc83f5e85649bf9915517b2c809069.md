### Title
Missing protocol-level check for AA bounce-fee compliance leads to irrecoverable loss of funds sent to Autonomous Agents - ([File: composer.js], [File: aa_addresses.js], [File: aa_composer.js])

### Summary
Just as `FootiumClub.safeMint()` transferred NFTs without verifying the receiver could handle them (missing `_checkOnERC721Received`), ocore's core unit-composition layer (`composer.js`) allows any single-authored unit to send bytes/assets to an Autonomous Agent (AA) address without ever verifying that the payment meets the AA's `bounce_fees` requirement. The only place this "receiver-compatibility" check (`aa_addresses.checkAAOutputs`) is performed is in the high-level wallet convenience function `wallet.sendMultiPayment()`. Any other path that composes and posts a payment — headless wallets, custom bots/bridges, exchanges, or any code calling `composer.composePaymentJoint`/`composeJoint` directly — can send an amount below an AA's configured `bounce_fees` and the funds become permanently stuck at the AA address with no path to recovery.

### Finding Description
When a unit posts a payment whose output goes to an AA address, `aa_composer.handleTrigger()` first credits the AA's balance with the received amount via `updateInitialAABalances()` [1](#0-0) , and only afterwards checks whether the trigger paid enough to cover `bounce_fees`: [2](#0-1) 

If the received `base` amount is less than `bounce_fees.base`, `bounce()` is invoked, but because the trigger itself doesn't carry enough bytes to pay for a bounce response, `bounce()` silently gives up and calls `finish(null)` without sending any refund: [3](#0-2) 

The result: the sender's coins are already merged into `aa_balances` for that AA address (an address with no private key — pure script logic), the AA's `messages` template never executes for this trigger, and no response/refund unit is produced. If the AA's own logic has no code path that later sweeps such below-threshold deposits (many simple AAs don't), the funds are irrecoverably locked forever, mirroring an NFT permanently stuck in a contract that never implements `onERC721Received`.

The protocol ships a "receiver check" analogous to OpenZeppelin's `_checkOnERC721Received`, but it is implemented only as an optional pre-flight advisory in `aa_addresses.checkAAOutputs()`, invoked exclusively from `wallet.sendMultiPayment()`: [4](#0-3) [5](#0-4) 

Crucially, this check is not enforced in the core unit composer used by every other sending path in the codebase (`composer.composePaymentJoint` / `composeJoint`, used by `indivisible_asset.js`, `arbiter_contract.js`, textcoin generation, and any external tool that talks to ocore's composer API directly): [6](#0-5) [7](#0-6) 

Nor is it enforced at unit-validation time in `validation.js`, so a network node has no way to reject or warn about such a payment — it is fully valid and gets stably confirmed, at which point the coins are gone.

### Impact Explanation
Unlike the Solidity bug (loss of a single NFT), here every payment sent to any AA address that doesn't reach the AA's `bounce_fees` threshold is silently absorbed with zero recourse for the sender. Because AA addresses have no private key, there is no way for anyone — including the AA's author — to manually rescue the coins; they can only be recovered if the specific AA's `messages`/`init` formulas explicitly account for previously-accumulated sub-threshold balances on a later, properly funded trigger. Many simple/common AA definitions (see `test/samples/simple_aa.oscript`, `bounce_half_of_balance.oscript`, etc.) do not do this. This is a direct, unauthorized-in-effect loss of user funds reachable by any unprivileged unit poster who is not using the reference wallet's `sendMultiPayment` wrapper (e.g., headless wallets, custom bridges/bots, DEX/exchange integrations, or direct use of `composer.js`).

### Likelihood Explanation
Likelihood is high: `bounce_fees` is a normal, commonly-used AA definition field (validated and required to be ≥ `MIN_BYTES_BOUNCE_FEE` in `aa_validation.js`), so essentially every deployed AA has a minimum threshold. Any sender that composes a unit without going through `wallet.sendMultiPayment()`'s advisory check (which is the norm for many integrations that use `composer.js` directly, or wallets/services with their own composition logic) can trivially underpay this threshold, especially in scripted/automated flows where the exact bounce fee of an arbitrary AA isn't known in advance.

### Recommendation
Move the bounce-fee sufficiency check out of the optional wallet convenience layer and into the shared, mandatory code path:
- Enforce the `aa_addresses.checkAAOutputs` (or equivalent) check inside `composer.composeJoint`/`composePaymentJoint` itself, so every caller of the composer benefits automatically, not just `wallet.sendMultiPayment`.
- Alternatively/additionally, have `aa_composer.handleTrigger()`'s underfunded-trigger path (`bounce()` when `trigger.outputs.base < bounce_fees.base`) still return the received coins to `trigger.address` instead of merely calling `finish(null)`, so an underfunded payment is refunded rather than silently swallowed even when no separate check was performed upstream.

### Proof of Concept
1. Deploy an AA with `bounce_fees: { base: 10000 }` (e.g., `test/samples/simple_aa.oscript`).
2. Using any tool that calls `composer.composePaymentJoint`/`composeJoint` directly (bypassing `wallet.sendMultiPayment`), send `9000` bytes to the AA address.
3. The unit is validated and confirmed normally by the network (`validation.js` has no bounce-fee check).
4. `aa_composer.handleTrigger()` credits the AA's `aa_balances` with 9000 bytes (`updateInitialAABalances`), then hits `trigger.outputs.base (9000) < bounce_fees.base (10000)` and calls `bounce()`, which calls `finish(null)` with no refund message (see `test/aa_composer.test.js` "less than bounce fees" test, which confirms `bounced: true` and `response_unit: null` — i.e., no unit is ever sent back) [8](#0-7) .
5. The 9000 bytes remain permanently in the AA's balance with no way for the sender to reclaim them unless the specific AA logic happens to sweep accumulated sub-threshold balances on a future trigger.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
}
