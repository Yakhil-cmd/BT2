### Title
CCMenu API bypasses stack-scoping, letting a stack-scoped `ApiClient` token read the deploy/build status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack with `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!` used by every other API controller, breaking the binding "stack a token authorizes == stack it touches."

### Finding Description
`Shipit::Api::BaseController` establishes the authorization invariant that when an `ApiClient` is scoped to a single stack (`current_api_client.stack_id?` true), only that stack is reachable: `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` and the generic `stack` helper resolves through that scoped relation. [1](#0-0) 

Every other API resource controller (stacks, deploys, tasks, hooks, locks, etc.) relies on this scoped `stack`/`stacks` helper, so a token created with `stack: some_stack` can only ever resolve that one stack, as verified in the stacks controller test suite (`"an api client scoped to a stack will only see that one stack"`). [2](#0-1) 

`CCMenuController`, however, overrides the private `stack` method to bypass the scoping entirely, resolving directly against the unscoped `Stack` model using an attacker-supplied `params[:stack_id]`: [3](#0-2) 

The only check performed before rendering is a *permission-class* check (`require_permission :read, :stack`), which merely verifies the token carries the generic `read:stack` permission string on `ApiClient#check_permissions!`; it does not verify that the requested `stack_id` matches the stack the token was scoped to. [4](#0-3) 

So the equality that should hold — `stack the token authorizes == stack the controller acts on` — is enforced everywhere except here, where `stack` is resolved unscoped from user input while authentication only checks the permission name, not the stack identity.

### Impact Explanation
This is a High-severity issue under the "unauthenticated/unauthorized read of stack state, task streams or deploy output" bucket. A holder of any valid, unprivileged `read:stack`-scoped `ApiClient` token — including a token deliberately minted to be scoped to a *single, specific* stack via the normal `ApiClientsController`/`CCMenuUrlController` flows — can supply a different `stack_id` in the `show` request and receive that other stack's build/deploy status (lock state, last build result, last deploy id/time, web URL) even though the token was never authorized for that stack. This defeats the entire purpose of per-stack token scoping (`stack_id` column on `ApiClient`), which other endpoints correctly honor.

### Likelihood Explanation
Likelihood is high for anyone who already possesses a legitimately-issued, stack-scoped read-only token (e.g., a CCMenu URL/token generated for one project) since only a single unauthenticated-content GET request with a different `stack_id` parameter is required — no additional credentials, signature, or privilege escalation is needed. The requirement is only holding a token scoped to *any* stack; the exploit crosses into every other stack in the installation.

### Recommendation
In `Shipit::Api::CCMenuController`, replace the private `stack` method with the inherited scoped implementation from `BaseController` (i.e., resolve via `stacks.from_param!(params[:stack_id])` rather than `Stack.from_param!(params[:stack_id])`), so stack-scoped tokens cannot read cross-stack state. If the override exists purely for pre-authentication routing reasons (token comes from the query string before `current_api_client` is set), reorder so the stack lookup uses `stacks` after authentication is resolved, mirroring the pattern in every other API controller.

### Proof of Concept
1. Via the normal UI/API, create (or have) an `ApiClient` scoped to `stack_id = A` with `permissions: ['read:stack']` (e.g., through `CCMenuUrlController#fetch`, which mints such read-only clients, or via `ApiClientsController#create` plus manual `stack_id` assignment).
2. Using that token's `authentication_token`, issue:
   `GET /api/stacks/:stack_B_id/ccmenu.xml?token=<token>` where `stack_B_id` belongs to a different, unrelated stack `B` that the token was never scoped to.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully via `ApiClient.authenticate(params[:token])`. [5](#0-4) 
4. `require_permission :read, :stack` passes because the token does carry `read:stack`.
5. `stack` resolves `Stack.from_param!(params[:stack_id])` against the unscoped `Stack` model, returning stack `B`, whose deploy/build status is rendered in the XML response — despite the token only ever having been authorized for stack `A`. [6](#0-5)
