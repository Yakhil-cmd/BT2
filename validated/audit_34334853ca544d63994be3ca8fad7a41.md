### Title
Insufficient policy enforcement in address-definition validation lets an unresolved inner "address" branch satisfy the "has signature" requirement - ([File: definition.js])

### Summary
`Definition.validateDefinition()` structurally validates an address (or asset-condition) definition before it is accepted, enforcing that "each branch must have a signature" (`definition.js:626-627`). For the `'address'` operator, when the referenced inner address's definition cannot be resolved on-chain and is not supplied by a co-author in the same unit, the code unconditionally treats the branch as satisfied (`cb(null, true)`), regardless of the caller's actual policy intent. [1](#0-0) 

### Finding Description
Inside `evaluate()` of `validateDefinition()`, the `'address'` case resolves an inner address via `storage.readDefinitionByAddress`. When the inner definition is not found on-chain and no co-author of the unit supplies a matching definition, the correct policy check should be gated on the caller-supplied `objValidationState.bAllowUnresolvedInnerDefinitions` flag — this flag is explicitly set to `true` only by internal, non-authoritative "fake validation" call sites such as `wallet_defined_by_addresses.js:validateAddressDefinition` (`objFakeValidationState = {last_ball_mci: MAX_INT32, bAllowUnresolvedInnerDefinitions: true}`), used purely for local UI-side sanity checks with an empty `authors` array. [2](#0-1) 

However, in the real code path that is reached, the flag check is commented out and replaced by a hardcoded local variable:
```
ifDefinitionNotFound: function(definition_chash){
//	if (objValidationState.bAllowUnresolvedInnerDefinitions)
//		return cb(null, true);
var bAllowUnresolvedInnerDefinitions = true;
...
if (arrDefiningAuthors.length === 0) // no address definition in the current unit
    return bAllowUnresolvedInnerDefinitions ? cb(null, true) : cb("definition of inner address "+other_address+" not found");
``` [3](#0-2) 

This means that for **every** call to `validateDefinition` — including the authoritative path used when a brand-new address definition is posted on-chain by an ordinary unit author (`validateAuthor` → `validateAuthentifiers` → `validateDefinition`, where `objValidationState.bAllowUnresolvedInnerDefinitions` is never set) — an `'address'` branch pointing at any never-used, unresolvable address is treated as if it "has a signature," satisfying the policy check at `definition.js:626-627` (`if (!bHasSig && !bAssetCondition) return handleResult("each branch must have a signature");`) without actually requiring any cryptographic authorization for that branch. [4](#0-3) 

Note that the *actual* authentication check in `validateAuthentifiers`'s own `evaluate()` (used when the unit is really spending funds) independently re-resolves the referenced address and requires a matching authentifier path, correctly returning `false` if the address is still unresolved (`definition.js:774-800`). This means the bug does not directly enable unauthorized spending through this exact branch alone, but it does relax a structural safety gate that is meant to prevent posting definitions where a branch can never be authorized ("dead"/spoofable branches), and it silently disables an intended caller-controlled policy switch (`bAllowUnresolvedInnerDefinitions`) that other code paths rely on to distinguish "trusted local fake validation" from "real on-chain validation." [5](#0-4) 

### Impact Explanation
This is a policy-enforcement defect (matching CVE-2021-21117's class: insufficient enforcement of an intended access/validation policy) rather than a direct fund-theft primitive as currently observed, because the true authorization gate in `validateAuthentifiers` still independently re-verifies each `'address'` branch at spend time. The risk is that the safety net meant to reject definitions with branches referencing indefinitely-unresolvable/unauthorizable code paths is bypassed for every unit — not just for the intended "fake/local" validation call sites — undermining the assumed invariant that `bAllowUnresolvedInnerDefinitions=false` (the default for real on-chain validation) rejects such branches. Because the flag is unconditionally overridden, any future/related logic relying on the original flag semantics (e.g., additional or future spending-condition checks that only rely on `validateDefinition`'s structural verdict rather than re-deriving live definitions) would be silently exposed to acceptance of always-true "has signature" branches with no real cryptographic backing.

### Likelihood Explanation
Any user can trivially craft an address definition (a "crafted file"/unit analog) containing `['address', '<never-used-address>']` and post it on-chain as a new address definition; this path is reached on every definition validation, not only the intended internal call sites, so the likelihood of the code path being triggered is high. However, because the redundant, authoritative check in `validateAuthentifiers` still blocks actual spending through such an unresolved branch, exploitation into a concrete fund-loss/double-spend requires an additional accompanying vulnerability (or future logic that trusts `validateDefinition`'s "has signature" verdict without live re-verification), which was not found in this scan.

### Recommendation
Restore the intended conditional check so the "unresolved inner address" leniency is applied only when explicitly authorized by the caller:
```js
ifDefinitionNotFound: function(definition_chash){
    if (objValidationState.bAllowUnresolvedInnerDefinitions)
        return cb(null, true);
    ...
    if (arrDefiningAuthors.length === 0)
        return cb("definition of inner address "+other_address+" not found");
    ...
}
```
This restores parity with the design comment at `definition.js:646` ("also validates address definition") and the intended narrow scope of `bAllowUnresolvedInnerDefinitions`, ensuring on-chain definitions cannot include branches that are structurally treated as authorized without ever being resolvable/verifiable.

### Proof of Concept
1. Construct `arrDefinition = ['address', 'UNUSED32CHARBASE32ADDRESSXXXXXXXX']` (a syntactically valid, never-before-used address) as the entire definition for a new address, or as one OR-branch alongside a real `sig` clause.
2. Compute the address chash and post a unit defining this address (`author.definition = arrDefinition`), with no co-author supplying `UNUSED...`'s definition.
3. Observe that `Definition.validateDefinition()` accepts it (`bHasSig=true` for that branch, via the hardcoded `bAllowUnresolvedInnerDefinitions = true` at `definition.js:287`), even though `objValidationState.bAllowUnresolvedInnerDefinitions` was never set for this real validation path — demonstrating the policy check is unconditionally bypassed rather than gated as originally intended.
