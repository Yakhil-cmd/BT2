### Title
Cross-organization webhook forgery via organization/repository binding mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a payload against based on `repository_owner` (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), but the handlers that subsequently act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolve the target repository from a *different* field, `payload.dig('repository', 'full_name')`. Nothing enforces that the owner used to pick the verifying secret is the same owner encoded in `full_name`, so a payload can be legitimately signed under one organization's webhook secret while acting on a stack belonging to a completely different organization's repository.

### Finding Description
`verify_signature` picks the GitHub App/org config used to validate the HMAC signature: [1](#0-0) [2](#0-1) 

The org used here is `repository.owner.login`, and `Shipit.github(organization: repository_owner)` resolves a specific `GitHubApp` instance whose `verify_webhook_signature` uses that org's own `webhook_secret`: [3](#0-2) 

Once the signature is accepted, the actual event dispatch and repository resolution use a *different* field of the same JSON body — `repository.full_name` — via `Handler#repository_name` / `Handler#stacks`: [4](#0-3) 

For example `PushHandler` uses `stacks` (derived from `repository.full_name`) to look up and sync/deploy stacks: [5](#0-4) 

`Repository.from_github_repo_name` splits `full_name` on `/` to find `owner`/`name` independent of `repository.owner.login`: [6](#0-5) 

The binding being broken is: *the organization whose webhook secret authenticated the request* should equal *the organization owning the repository the handler actually writes to*. Because the signature only proves "someone who knows organization A's webhook secret sent this exact byte string," and the code lets `repository.owner.login = A` (used only for signature-secret selection) diverge from `repository.full_name = B/some-repo` (used for all downstream stack lookup/sync/deploy actions), a party with legitimate access to organization A's webhook secret can craft a signed payload that drives Shipit to act on organization B's stacks.

### Impact Explanation
This breaks a deployment-trust binding equivalent to "an organization that authenticated versus the repository that is written" described in the rules. On a multi-tenant Shipit instance managing several GitHub organizations/apps with distinct `webhook_secret`s, an actor who is entitled to trigger webhooks for their own organization (A) — e.g. by having admin rights over their org's GitHub App/webhook configuration, which does not require any Shipit credentials — could forge a `push` (or other handled event) payload that is validly signed by A's secret but whose `repository.full_name` names a repository under organization B. This can enqueue `GithubSyncJob`, trigger stack lookups, or drive other handler logic (`membership`, `pull_request`, `status`, `check_suite`) against stacks that belong to a different organization than the one whose credential was used to authenticate the request, i.e., an unauthorized cross-organization action on Shipit stacks.

### Likelihood Explanation
This requires no Shipit session, API token, or GitHub write access to the victim organization's repository — only control of a webhook secret for some organization configured in the same Shipit deployment (a normal, low-privilege capability for any onboarded tenant). Because `verify_signature` never cross-checks that `repository.owner.login`/`organization.login` matches `repository.full_name`'s owner, the attack surface is entirely within the already-reachable, unauthenticated-to-Shipit `/github/webhooks` (or equivalent) endpoint.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to select/verify the webhook secret is the same organization encoded in `repository.full_name` (and `organization.login`, when present) before dispatching to handlers. Reject the webhook (422) if these do not match, rather than only validating the signature against a single owner field while letting handlers key off an independent field of the same payload.

### Proof of Concept
1. Shipit is configured with two GitHub App/org entries, e.g. `orgA` (attacker-administered) and `orgB` (victim), each with its own `github.webhook_secret`.
2. Attacker crafts a `push` JSON payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "orgA" },
       "full_name": "orgB/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` using the webhook secret they legitimately control for `orgA`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and validates the signature successfully (rule at `app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which computes `repository_name` from `payload.dig('repository','full_name')` = `"orgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), looks up `orgB`'s repository/stacks, and enqueues a sync (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — acting on organization B's stack using a signature that only proves knowledge of organization A's secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
