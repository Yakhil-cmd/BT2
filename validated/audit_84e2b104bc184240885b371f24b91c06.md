### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` lookup and unrestricted `context` in `StatusHandler` bypasses a victim stack's `blocking_statuses`/`required_statuses` gating - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire `Commit` table, with no check that the webhook's `repository.full_name` matches the commit's stack/repository, and `context` is an unconstrained, attacker-supplied string. An attacker who owns any repository connected to Shipit (and thus possesses that repository's own valid webhook secret) can send a signed "status" webhook naming a `sha` that also exists in a victim stack, spoofing `context` to match the victim's `ci.blocking`/`ci.require` context, forcing `Commit#blocked?`/`deployable?` to miscompute for the victim stack.

### Finding Description
The broken binding: the code implicitly assumes `payload.repository.full_name == stack.repository.full_name` for the commit being updated, but this is never checked.

- `WebhooksController#verify_signature` derives the GitHub App/org to verify against from `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . An attacker who legitimately owns a repository wired into Shipit possesses that repository's real `webhook_secret` and can produce a validly signed payload naming their *own* `repository.owner.login`.
- `StatusHandler.params` only requires `sha` and `state`; `context`, `target_url`, `description` are freely attacker-supplied strings with no validation tying them to any repository [3](#0-2) .
- Crucially, `StatusHandler#process` ignores the `Handler` base class's repository-scoped `stacks` helper entirely and instead does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . Compare with `Handler#stacks`, which does scope by `Repository.from_github_repo_name(repository_name)` but is unused here [5](#0-4) .
- `Commit#create_status_from_github!` then writes the status using the *commit's own* `stack_id` [6](#0-5) , so the forged status attaches correctly to whichever stack the matched `Commit` row belongs to — it is the *lookup*, not the write, that ignores tenant boundaries.
- `Status::Common#blocking?`/`#required?` compare the status's `context` string directly against `commit.blocking_statuses`/`commit.required_statuses`, which come from the victim stack's own `shipit.yml` (`ci.blocking`, `ci.require`) [7](#0-6) [8](#0-7) .
- `Commit#blocked?` walks `stack.commits.reachable...older_than(self).any?(&:blocking?)` [9](#0-8) . If a previously-blocking commit in the victim stack receives a forged `success` status for its blocking context (via a shared `sha` match), that commit's `blocking?` flips to false, and `blocked?`/`deployable?` for later commits changes accordingly.

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: status`, a valid `X-Hub-Signature` computed with their own repo's webhook secret, and a body `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/attacker-repo"}, "sha": "<victim_sha>", "state": "success", "context": "ci/build"}`. `verify_signature` passes (attacker's own valid secret/org), `StatusHandler` matches any `Commit` row with that `sha` — including one belonging to the victim stack — and writes a forged `success` status with `context: "ci/build"` on it.

Existing guards fail here because: `verify_signature` authenticates the *sender's own organization*, not the *target stack/repository* being mutated; `ExplicitParameters` validates only shape/presence of fields, not ownership; and `StatusHandler#process`'s `Commit.where(sha:)` query has no repository/stack filter at all.

### Impact Explanation
A cross-tenant write: a payload authenticated for repository A mutates commit/status state belonging to stack B, which the attacker does not control and did not authenticate for. This directly matches the "payload for one repository mutating another's stack, commit" Critical category. The practical exploitability depends on the attacker being able to name a `sha` that exists as a `Commit` row in the victim's stack — feasible for forked repositories, cherry-picked/rebased commits, or any commit whose sha the attacker can learn (e.g. a public repository's commit history) since git SHAs are content-derived and can be reused/synced across repos when history is shared. The forged status can flip `Status::Common#blocking?`/`#required?` for that context, changing `Commit#blocked?`/`#deployable?` results and potentially permitting a deploy that should have been withheld.

### Likelihood Explanation
Preconditions: the attacker must control at least one repository already integrated with Shipit (own webhook secret, no Shipit session or privileged role needed) and must know/produce a `sha` that also exists as a `Commit` record in the victim stack (achievable via shared history/forks/cherry-picks). No knowledge of the victim's webhook secret, `secret_key_base`, or GitHub App private key is required. This is a repeatable, unauthenticated-per-victim attack: a single unprivileged repository owner can forge status webhooks against any stack whose commits share a sha with theirs.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository that actually sent the webhook (mirroring `Handler#stacks`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining `Commit` through `Stack`/`Repository` matched against `payload.dig('repository','full_name')`, instead of a bare `Commit.where(sha: params.sha)` across the entire table.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_status_cross_tenant_test.rb
require 'test_helper'

module Shipit
  class WebhooksControllerStatusCrossTenantTest < ActionController::TestCase
    tests Shipit::WebhooksController

    setup do
      GithubHook.any_instance.stubs(:verify_signature).returns(true)

      @victim_repo  = Repository.create!(owner: 'victim-org', name: 'victim-repo')
      @victim_stack = Stack.create!(repository: @victim_repo, environment: 'production', branch: 'master')
      @victim_stack.stubs(:blocking_statuses).returns(['ci/build'])
      @victim_stack.stubs(:required_statuses).returns(['ci/build'])

      @shared_sha = 'deadbeef' * 5
      @blocking_commit = @victim_stack.commits.create!(sha: @shared_sha, message: 'shared', authored_at: Time.now, committed_at: Time.now)
      @later_commit = @victim_stack.commits.create!(sha: 'a' * 40, message: 'later', authored_at: Time.now, committed_at: Time.now)

      # sanity: victim commit is currently blocking (no success status for ci/build)
      assert @later_commit.blocked?
    end

    test "status webhook signed for attacker's own org forges a status on a victim stack's commit with matching sha" do
      request.headers['X-Github-Event'] = 'status'

      forged_payload = {
        'sha' => @shared_sha,
        'state' => 'success',
        'context' => 'ci/build',
        'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
      }.to_json

      post :create, body: forged_payload, as: :json
      assert_response :ok

      @blocking_commit.reload
      status = @blocking_commit.statuses.last
      assert_equal 'ci/build', status.context
      assert_equal 'success', status.state
      assert_equal @victim_stack.id, status.stack_id # written into victim stack despite attacker payload

      refute @later_commit.reload.blocked? # gating bypassed for the victim stack
    end
  end
end
```
Both sides of the binding before/after: before the forged webhook, `payload.repository.full_name == 'attacker-org/attacker-repo'` while the mutated `commit.stack.repository.full_name == 'victim-org/victim-repo'` — they diverge, and no code path enforces equality, so the write proceeds and `blocked?` flips from `true` to `false`.
