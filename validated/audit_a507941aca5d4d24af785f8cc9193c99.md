### Title
Cross-organization webhook forgery via `repository.owner.login`/`organization.login` divergence lets an unprivileged attacker use a secret-less org to bypass signature verification while `MembershipHandler` mutates a different organization's team - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus which `webhook_secret` to check) using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` first and falls back to `params.dig('organization', 'login')` only if `repository` is absent [1](#0-0) . `MembershipHandler`, however, uses the independent `params.organization.login` field to set the created `Team#organization` [2](#0-1) . Because the attacker controls the raw JSON body, they can populate a fabricated `repository.owner.login` pointing at an organization configured with no `webhook_secret` (which unconditionally verifies as `true`) while pointing `organization.login`/`team.id`/`member.login` at an entirely different organization's team, causing the handler to add/remove memberships for a tenant whose secret never validated the request.

### Finding Description
The invariant that should hold is: `organization_that_verified_signature == organization.login used by the handler to mutate Team/Membership`. Tracing the code:

1. `verify_signature` computes `repository_owner` from the payload and looks up `Shipit.github(organization: repository_owner)` [3](#0-2) .
2. `verify_webhook_signature` returns `true` unconditionally when the resolved `GitHubApp`'s `webhook_secret` is blank — this is intentional behavior for orgs that opted out of webhook secrets, but it is scoped only by whatever value `repository_owner` produced [4](#0-3) .
3. Multi-org installations are supported and looked up by the payload-controlled organization string via `Shipit.github_app_config` [5](#0-4) .
4. Once the request passes `verify_signature`, `WebhooksController#create` parses `request.raw_post` again and dispatches the *entire* attacker-controlled body to `MembershipHandler.call(params)` [6](#0-5) .
5. `MembershipHandler#find_or_create_team!` uses `params.team.id` to find/create a `Team` and sets `team.organization = params.organization.login`, then `process` adds or removes the `member` (`params.member.login`) from that team [7](#0-6) .

Because `repository_owner` (used to select the verifying secret) and `organization.login` (used to attribute the mutated `Team`) are two **independently attacker-supplied JSON fields**, an attacker can supply:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "org-with-no-secret"}},
  "organization": {"login": "victim-org"},
  "team": {"id": 12345, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "member": {"login": "attacker-login"}
}
```
with header `X-Github-Event: membership` and any/no `X-Hub-Signature` value (since the no-secret org bypasses verification regardless of the signature format supplied). `verify_signature` resolves `repository_owner` → `"org-with-no-secret"` (since `repository.owner.login` is present, it wins over `organization.login`), whose `GitHubApp` has no `webhook_secret`, so `verify_webhook_signature` returns `true` and the request is accepted. `MembershipHandler` then finds/creates the `Team` keyed by `team.id` and attributes it to `organization: "victim-org"`, adding `attacker-login` to it — a membership record for `victim-org`'s team, despite the fact that `victim-org`'s webhook_secret never validated any part of this request.

None of the existing guards catch this: `drop_unhandled_event` only checks the event is handled, `ExplicitParameters` schema in `MembershipHandler` only validates types/presence (not that `organization.login == repository_owner`) [8](#0-7) , and `verify_signature` never cross-checks that the field it used for org resolution matches the field the handler later uses for org attribution.

### Impact Explanation
If the resulting `Team` (identified by `github_id`) is one referenced by `Shipit.github_teams` (the set of teams used for authorization), an attacker can add their own GitHub login as a member without ever being a real member of that GitHub organization/team, escalating into `User#authorized?` which checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [9](#0-8) . This satisfies the "escalation into `Shipit.github_teams` authorization" High-severity category. The precondition is that the Shipit deployment uses multi-org configuration with at least one configured organization lacking a `webhook_secret` — a documented, supported configuration [10](#0-9)  — after which the attack is repeatable against any organization/team whose `github_id`/`login` the attacker knows or guesses, entirely from an unauthenticated `POST /webhooks`.

### Likelihood Explanation
Requires: (a) a multi-org Shipit configuration, and (b) at least one configured organization with no `webhook_secret` set (a state explicitly supported/documented, and easy to overlook operationally). Given that, the attacker needs no secrets, sessions, or GitHub org membership — only knowledge of a target team's `github_id`/organization login, both of which can often be discovered from public GitHub data. This is a single unauthenticated HTTP POST, fully repeatable.

### Recommendation
In `WebhooksController#verify_signature`, ensure the organization used to select the verifying `GitHubApp`/secret is derived consistently and validated against the organization actually used by the dispatched handler (e.g., reject payloads where `repository.owner.login` and `organization.login` disagree, or have `verify_signature` re-derive `repository_owner` the same way each handler derives its organization/team ownership). Additionally, consider making a missing `webhook_secret` fail closed (reject unsigned/no-secret orgs) rather than default to accepting all such requests, and have `MembershipHandler` validate `params.organization.login` matches the same organization resolved during signature verification before mutating `Team`/`Membership` records.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":membership from a no-secret org can forge membership for a different org's team" do
  Shipit.stubs(:secrets).returns(
    ActiveSupport::OrderedOptions.new.tap do |s|
      s.github = {
        "org-with-no-secret" => { app_id: 1, installation_id: 1 }, # no webhook_secret
        "victim-org" => { app_id: 2, installation_id: 2, webhook_secret: "victim-secret" }
      }
    end
  )

  victim_team = shipit_teams(:shopify_developers) # organization: "victim-org" in fixture, or set explicitly

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # irrelevant, no secret configured for repository.owner

  body = {
    action: 'added',
    repository: { owner: { login: 'org-with-no-secret' } }, # picked for signature verification
    organization: { login: 'victim-org' },                  # actually attributed by handler
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: 'https://example.com' },
    member: { login: 'attacker-login' }
  }.to_json

  assert_difference -> { victim_team.reload.members.count }, 1 do
    post :create, body: body, as: :json
  end

  assert_response :ok
  assert_includes victim_team.members.map(&:login), 'attacker-login'
end
```
Both sides of the invariant (`repository_owner` resolved for signature verification vs. `organization.login` used by `MembershipHandler`) diverge in this request, and the assertion proves the handler mutated `victim-org`'s team despite `victim-org`'s secret never validating the request.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
