## Title
Cross-Stack Information Disclosure via CCMenu API Token — Stack a Token Authorizes vs. Stack it Touches ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to bypass `BaseController`'s stack-scoping logic, so any `read:stack` API token can be used to fetch deploy/build status for **any** stack in the Shipit instance, not just the stack the token was issued for. This breaks the binding "the stack an `ApiClient` is scoped/authorized for" == "the stack the request actually touches" — directly analogous to the referenced bug class where a party in the trust relationship (here, an `ApiClient` token) can act on a target it was never actually granted rights over, simply because the check applied is a coarse permission string rather than the specific resource binding.

### Finding Description
`Shipit::ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true`. `BaseController` enforces this scoping generically: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]` only from within that restricted set. `require_permission :read, :stack` only checks that the token carries the string `read:stack` in its `permissions` list — it never checks whether the specific `stack_id` in the request matches the token's bound `stack_id`; that check is delegated entirely to the `stacks`/`stack` helper.

`CCMenuController`, however, overrides both `authenticate_api_client` (fine — supports query-string tokens) **and** `stack`, resolving the target directly against the full `Stack` table instead of the scoped `stacks` relation: [2](#0-1) 

Because `require_permission :read, :stack` (declared class-side, see `Api::BaseController.require_permission`) only calls `current_api_client.check_permissions!(:read, :stack)`, and `check_permissions!` merely checks the permission string: [3](#0-2) 

the per-stack binding is silently dropped for this controller. Compounding this, the token-issuance flow (`CCMenuUrlController`) itself creates a client with **no `stack:` association at all** — it's keyed only by `creator` and a fixed name, so a single global, unscoped `read:stack` token is minted (or reused) for a user regardless of which stack's CCMenu URL they requested: [4](#0-3) 

So the equality that should hold — `token.stack_id == request.stack_id` (or `token.stack_id.nil?` meaning "admin/global scope", intentionally) — is broken in two ways: (1) tokens minted for CCMenu are never stack-scoped to begin with, and (2) even a stack-scoped `read:stack` `ApiClient` (e.g., built via `Api::BaseController`/settings UI with an explicit `stack:` value, as in the `here_come_the_walrus` fixture) is not respected by `CCMenuController`, because its `stack` method ignores `current_api_client.stack_id`.

### Impact Explanation
This is an unauthenticated-relative-to-target-stack read of stack state and deploy output: possession of any `read:stack` token (which may be embedded in a public CI-badge URL, e.g. a README or dashboard, since CCMenu URLs are designed for external polling) allows enumeration of build status, last deploy time, and deploy/rollback history (`stack.deploys_and_rollbacks.last`) for **every** stack managed by the Shipit instance, including stacks the token holder has no legitimate access to. This matches the High-severity category "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Any authenticated Shipit user can obtain a `read:stack` CCMenu token for a stack they can see via `CCMenuUrlController#fetch`, then simply swap `stack_id` in the returned URL to read any other stack's status — no privilege escalation, no additional secrets, and no interaction with GitHub credentials required. The only prerequisite is holding one valid `read:stack` token, which is the intended baseline capability of the CCMenu feature itself.

### Recommendation
Remove `CCMenuController`'s `stack` override and instead reuse `BaseController#stack` (i.e., resolve via the scoped `stacks` relation) so that stack-scoped tokens are enforced consistently across all API controllers. Additionally, scope the `ApiClient` created in `CCMenuUrlController#client` to the specific `stack` being requested (pass `stack:` into `create_with`/`find_or_create_by!`), so CCMenu tokens are never implicitly global.

### Proof of Concept
1. As User A, visit stack `shipit/prod`'s CCMenu URL endpoint: `GET /stacks/shipit/prod/ccmenu.xml` → `CCMenuUrlController#fetch` mints (or reuses) an `ApiClient` named "CCMenu Client" for User A with `permissions: ['read:stack']` and no `stack_id`, returning `.../api/stacks/prod/ccmenu.xml?token=<T>`.
2. Using the same token `T`, request a different stack's status: `GET /api/stacks/<other_stack_id>/ccmenu.xml?token=<T>`.
3. `CCMenuController#authenticate_api_client` authenticates `T` successfully; `require_permission :read, :stack` passes because `T` carries `read:stack`; `stack` resolves `<other_stack_id>` directly via `Stack.from_param!`, bypassing any per-stack restriction.
4. The response discloses `<other_stack_id>`'s latest deploy/rollback status and timing, even though `T` was never granted access to that stack.
