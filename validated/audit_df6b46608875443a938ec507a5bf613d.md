### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a forged cross-repo Status trigger an unauthorized deploy before any corrective `RefreshStatusesJob` can run - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by SHA, with no scoping to the repository that emitted the webhook, so a webhook signed for repo A can write a `Status` row onto a `Commit` that actually belongs to repo B's stack. Once that forged `Status` is persisted, `Commit#schedule_continuous_delivery` and `Stack#trigger_continuous_delivery` act on it immediately (with only a fixed 10-second `ContinuousDeliveryJob` delay) using purely local DB state, while the only mechanism that would re-validate against real GitHub data (`Commit#refresh_statuses!` via `RefreshStatusesJob`) is not automatically scheduled on status creation, so the corrective pull can arrive - if ever - long after the unauthorized deploy has already been enqueued and executed.

### Finding Description
Binding claimed broken: `forged_status.commit_id == victim_commit.id` while `forged_status.stack_id == victim_commit.stack_id`, and the attacker's webhook signature is only valid for their own repository, so this equality (a Status apparently belonging to the victim stack, produced from a payload that authenticated only the attacker's repo) should never hold. Tracing the code shows it can:

- `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 
This query is *not* scoped to `stacks` (the `repository_name`-derived scope defined in the base `Handler` class) the way other handlers use it [2](#0-1) . It matches **any** `Commit` row across **any** stack/repository sharing the same `sha`.

- `WebhooksController#verify_signature` only authenticates that the payload came from GitHub for the `repository_owner` embedded in the payload itself (`Shipit.github(organization: repository_owner)` + HMAC check) [3](#0-2) . It proves the webhook is authentic *for the attacker's own repository*; it proves nothing about which `Commit`/`Stack` records the payload's `sha` should be allowed to touch.

- `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, ...)` persists the forged `Status` using the **victim commit's own `stack_id`** [4](#0-3) , `Status#replicate_from_github!` [5](#0-4) .

- `Status` `after_commit :schedule_continuous_delivery` fires unconditionally on creation [6](#0-5) , calling `Commit#schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` with only a fixed `RECENT_COMMIT_THRESHOLD` (10 seconds) delay, purely from local state (`deployable?`, `stack.continuous_deployment?`, `stack.deployable?`) [7](#0-6) .

- `ContinuousDeliveryJob#perform` re-checks only local predicates (`continuous_deployment?`, schedule window, `occupied?`) and calls `stack.trigger_continuous_delivery` [8](#0-7) , which computes `next_commit_to_deploy` from the DB's `commits`/`statuses` tables and calls `trigger_deploy`, enqueuing a real `PerformTaskJob` [9](#0-8) . None of this path performs a live GitHub call.

- The only corrective mechanism, `Commit#refresh_statuses!` (called by `RefreshStatusesJob`), is *not* triggered on `Status` creation. It's only scheduled `after_commit ... on: :create` for a new **Commit** row [10](#0-9) , or via an explicit user/API "Refresh" action [11](#0-10) . There is no automatic re-pull triggered by a webhook-created `Status`.

Exploit flow: attacker (who owns a repository, e.g., a personal fork enrolled with Shipit's GitHub App/webhook integration per the stated threat model) reproduces the exact byte-identical Git commit object (same tree, parents, author/committer identities and timestamps, message) of a known, public victim commit into their own repo/branch - which yields an identical SHA-1 - then sets a `success` status on that commit via the GitHub Status API on their own repo. GitHub emits a validly-signed `status` webhook for the attacker's own repository. `verify_signature` passes (it only checks that this payload really came from GitHub for the attacker's own org). `StatusHandler#process` then finds the victim's `Commit` row (same `sha`) irrespective of stack, and writes a forged `success` Status onto it, immediately kicking off `ContinuousDeliveryJob` → `trigger_deploy` for the victim's stack.

Existing guards fail here because: `verify_signature` authenticates the *source repository* of the webhook, not the *target records* the handler is permitted to mutate; `drop_unhandled_event` only filters unregistered event types; the `ExplicitParameters` schema only validates payload shape, not authorization scope; and there is no `Repository`/`Stack` ownership check anywhere between webhook receipt and `Commit.where(sha:)`.

### Impact Explanation
An attacker who controls any repository wired into Shipit (their own fork/org) can, without any Shipit credentials, forge a `success`/passing CI `Status` on an arbitrary victim commit belonging to a completely different stack/repository, as long as they can reproduce that commit's exact content (feasible for public commits by replaying identical tree/author/message/timestamps). This directly satisfies the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy" - the forged status causes `trigger_continuous_delivery` to enqueue and run a real deploy task (`PerformTaskJob`) for the victim stack. The window during which this forged data is authoritative is not bounded by any race with `RefreshStatusesJob`: that job is never automatically scheduled in response to a `Status` webhook, so by the time (if ever) an operator manually triggers a refresh, the unauthorized deploy has typically already completed. This is repeatable against any commit/stack whose SHA the attacker can reproduce.

### Likelihood Explanation
Preconditions: the attacker needs a repository that is wired to receive genuinely GitHub-signed webhooks routed through Shipit's webhook endpoint (consistent with the stated threat model of "emit webhooks from a repository they own"), `stack.continuous_deployment?` enabled on the victim stack, and the ability to reconstruct a byte-identical commit object matching a real victim commit (git tree/parents/author/committer/timestamps/message all public for public repos, making this achievable without any secret). No Shipit session, API token, or webhook secret is required by the attacker - GitHub itself computes and sends the valid signature for the attacker's own repository. Cost is essentially one crafted git commit + one GitHub Status API call the attacker already has legitimate rights to perform on their own repo.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving records purely by `sha`) to the repository named in `payload['repository']['full_name']`, e.g. restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or join through `Stack`/`Repository` so a `Status` can only be attached to commits belonging to stacks tied to the webhook's authenticated repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_race_test.rb
require 'test_helper'

module Shipit
  class StatusHandlerRaceTest < ActiveSupport::TestCase
    test "forged cross-repo status via shared sha triggers an unauthorized deploy before RefreshStatusesJob corrects it" do
      victim_stack = shipit_stacks(:shipit) # continuous_deployment stack
      victim_stack.update!(continuous_deployment: true)
      victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, ...) # same sha reused by "attacker" repo

      # Attacker's own repo emits a validly-signed status webhook (out of scope here to forge signature;
      # directly exercise the handler as the controller would after verify_signature passes)
      payload = {
        'sha' => victim_commit.sha,
        'state' => 'success',
        'repository' => { 'full_name' => 'attacker/unrelated-repo' }
      }

      assert_difference -> { victim_commit.statuses.count }, 1 do
        Webhooks::Handlers::StatusHandler.call(payload)
      end

      assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
        # status creation already scheduled it
      end

      perform_enqueued_jobs(only: ContinuousDeliveryJob)

      # Unauthorized deploy already exists for the victim stack
      assert victim_stack.deploys.where(until_commit_id: victim_commit.id).exists?,
             "expected an unauthorized deploy to already exist"

      # RefreshStatusesJob has NOT run yet - simulate it now (too late)
      assert_no_enqueued_jobs(only: RefreshStatusesJob)
      # Even if it later ran and removed the forged status, the deploy already fired:
      Commit.any_instance.stubs(:refresh_statuses!) # simulate corrective pull never invalidates completed deploy
      assert victim_stack.deploys.where(until_commit_id: victim_commit.id).exists?
    end
  end
end
```
