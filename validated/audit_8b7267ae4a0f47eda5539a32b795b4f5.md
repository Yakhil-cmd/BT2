### Title
CCMenuController bypasses ApiClient stack scoping, letting a stack-scoped token read status for any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The generic Shipit API scopes every `ApiClient` (token) to the stack it was granted against: when `stack_id` is set, `Shipit::Api::BaseController#stacks`/`#stack` restrict lookups to `Stack.where(id: current_api_client.stack_id)`. `Shipit::Api::CCMenuController` overrides `#stack` and looks the stack up unscoped via `Stack.from_param!(params[:stack_id])`, so the stack-scoping binding enforced everywhere else in the API is silently dropped for this one endpoint.

### Finding Description
`Shipit::Api::BaseController` defines the trust binding "a stack a token authorizes == a stack it touches": [1](#0-0) 

Any endpoint that inherits `stack` from `BaseController` (e.g. `OutputsController`, `MergeRequestsController`, `StacksController`) respects this binding, so an `ApiClient` created with a specific `stack` (as in the `here_come_the_walrus` fixture, scoped to the `shipit` stack with only `read:stack`) can only ever resolve `stack` to that one row: [2](#0-1) 

`CCMenuController`, however, overrides `#stack` to bypass this scoping entirely and resolve directly against the unscoped `Stack` model: [3](#0-2) 

It still declares `require_permission :read, :stack`, which only checks that the string `read:stack` is present in `current_api_client.permissions` — it never checks `current_api_client.stack_id`: [4](#0-3) [5](#0-4) 

So the check that is verified ("does this token have `read:stack` permission at all") is not the same as the check that is actually needed ("is this token authorized for *this* stack"), breaking the equality `token.authorized_stack == stack_touched_by_request`.

### Impact Explanation
A caller holding a token that was deliberately scoped to a single, presumably lower-sensitivity stack (e.g. a CI badge/CCMenu integration token for stack A) can supply any other `stack_id` in the URL and read that other stack's CCMenu project status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`), as rendered by: [6](#0-5) 

This is an unauthorized read of stack state (lock status, last deploy result) for a stack the token was never granted access to — matching the "unauthenticated/unauthorized read of stack state" High-impact category, since the credential's authorization boundary (its `stack_id`) is bypassed for this specific route.

### Likelihood Explanation
Likelihood is limited by the precondition that an operator has actually issued a stack-scoped `ApiClient` (non-null `stack_id`) with `read:stack` permission — which is exactly the intended, documented use case for CCMenu-style integrations (see `CCMenuUrlController`, which mints such a token). Any holder of that legitimately-scoped token can immediately probe other `stack_id` values with no additional privilege, since the endpoint's only authentication requirement is `authenticate_api_client` and the only authorization requirement is the un-scoped `read:stack` permission string.

### Recommendation
Make `CCMenuController#stack` reuse the scoped lookup from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens cannot resolve stacks outside their `stack_id`.

### Proof of Concept
1. Create/observe an `ApiClient` scoped to stack A with only `read:stack` permission (as in fixture `here_come_the_walrus`, scoped to stack `shipit`).
2. Authenticate to `GET /api/:stack_b_id/ccmenu.xml` (routed to `Shipit::Api::CCMenuController#show`) using stack A's token, where `stack_b` is a different stack the token was never granted.
3. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` (unscoped), resolves stack B, and `check_permissions!(:read, :stack)` only checks the permission string, not `stack_id` — the response renders stack B's CCMenu project XML (name, lastBuildStatus, etc.), even though the token is only authorized for stack A.
