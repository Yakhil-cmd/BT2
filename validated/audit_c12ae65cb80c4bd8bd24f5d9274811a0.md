### Title
Webhook organization used for signature verification is not bound to the `repository.full_name` used for stack dispatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC against using `repository.owner.login` (falling back to `organization.login`), while every event handler that actually mutates state (`PushHandler`, `PullRequest::ClosedHandler`, `PullRequest::ReopenedHandler`, `ReviewStackAdapter`, etc.) resolves the target `Stack`/`Repository` using the unrelated `repository.full_name` field via `Repository.from_github_repo_name`.

### Finding Description
The HMAC signature is computed over the raw JSON body, so it does technically "cover" every byte of the payload including `repository.full_name`. However, `Shipit.github(organization: repository_owner)` picks the *secret* to validate against based solely on `repository.owner.login`/`organization.login`. In a shared/multi-tenant Shipit instance configured with multiple `Shipit.github` app secrets (one per GitHub organization, per `config/secrets.*.yml`), an attacker who legitimately controls (or has compromised) a repository in Organization A can:

1. Configure a GitHub webhook on their own OrgA repository, so GitHub signs deliveries with OrgA's genuine `webhook_secret`.
2. Trigger a `push`/`pull_request` event whose top-level `repository.owner.login` is `"OrgA"` (satisfying signature verification against OrgA's secret) but whose `repository.full_name` is forged to reference a repository/stack belonging to a *different* organization/team (e.g. `"OrgB/critical-app"`).
3. Because the signature check only binds the *organization secret* to `repository.owner.login`, and never cross-validates that `repository.full_name`'s owner matches `repository.owner.login`, the request passes `verify_signature` even though its `full_name` targets a stack the attacker has no legitimate relationship with.
4. `Handler#stacks` / `PushHandler#process` then look up and act on `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, which is OrgB's stack — outside the trust boundary the signature was supposed to establish.

This breaks the intended equality: `organization whose secret authenticated the request == organization owning the repository the handler writes to`. The verified field (`repository.owner.login`) and the acted-upon field (`repository.full_name`) are independent, attacker-controlled JSON keys within the same signed body — nothing forces them to agree.

### Impact Explanation
Depending on the event/handler, this allows an attacker who legitimately owns a webhook secret for one organization to trigger `GithubSyncJob` syncs, archive/unarchive review stacks (`PullRequest::ClosedHandler#process`, `ReopenedHandler#process`), or otherwise cause state changes against stacks belonging to unrelated repositories/organizations tracked by the same Shipit instance — an unauthorized cross-repository write, matching the Critical impact bar ("cross-repository writes").

### Likelihood Explanation
Exploitability requires: (a) a Shipit deployment configured with more than one GitHub organization/app (the multi-org `github:` secrets schema shown in `config/secrets.development.shopify.yml`), and (b) the attacker already holding a valid webhook secret for at least one of those organizations (i.e., they have configured a webhook on a repo in that org — this is a normal, low-privilege GitHub repo admin action, not an ApiClient token, GitHub App key, or Shipit session). Given that, forging the `repository.full_name` field in a signed delivery is trivial since GitHub webhook payloads are attacker/repo-owner-authored JSON that Shipit simply relays verbatim from `request.raw_post`.

### Recommendation
In `WebhooksController#verify_signature` / `Shipit::Webhooks::Handlers::Handler`, cross-validate that the organization used to select the webhook secret (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, or resolve the target `Repository`/`Stack` using the same verified `owner.login` field rather than the independent `full_name` field.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `secrets.*.yml` multi-org schema).
2. Attacker controls a repo in `OrgA` and creates a webhook there, receiving `OrgA`'s real `webhook_secret` from GitHub delivery signing.
3. Attacker crafts and self-delivers (or replays) a `push` payload with:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/target-repo"`
   - `ref = "refs/heads/master"`, `after = "<attacker-chosen-sha>"`
   and signs it with OrgA's `webhook_secret` (`X-Hub-Signature`).
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which succeeds because the signature was computed with the correct OrgA secret over this exact body.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `#stacks` resolves `Repository.from_github_repo_name("OrgB/target-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on OrgB's stack — an action the attacker was never authorized to trigger.
