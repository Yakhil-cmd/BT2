### Title
Webhook signature verified against attacker-controlled `repository.owner.login`, not the `repository.full_name` acted on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against using a field taken from the *unverified* JSON body (`repository.owner.login`), while every event handler subsequently resolves and mutates state using a *different* field from the same unverified body (`repository.full_name`). Nothing ties these two fields together, so the organization whose secret authenticates the request is not guaranteed to be the organization whose repository/stack is actually written to.

### Finding Description
`before_action :verify_signature` computes the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (or `organization.login`), and `Shipit.github(organization: repository_owner)` is used to pick the `GitHubApp` instance (and thus the `webhook_secret`) that `verify_webhook_signature` checks the raw body against.

Once the signature passes, `create` dispatches the same raw `params` to handlers: [3](#0-2) 

Handlers resolve the target repository from a *different* JSON field, `repository.full_name`: [4](#0-3) 

and `Repository.from_github_repo_name` looks up the local `Repository`/`Stack` purely by parsing that string, independent of `repository.owner.login`: [5](#0-4) 

`PushHandler` (and similarly `StatusHandler`, `CheckSuiteHandler`, membership/pull_request handlers) then act on whatever stacks match that `full_name`, e.g. triggering `stack.sync_github`: [6](#0-5) 

Shipit explicitly supports configuring one distinct GitHub App (and thus one distinct `webhook_secret`) per organization, precisely so that different tenant organizations are isolated from one another: [7](#0-6) 

Because `verify_signature` derives the signing app from `repository.owner.login`/`organization.login` while the handlers act on `repository.full_name`, these two values are never cross-checked. An attacker who legitimately controls (or has been granted webhook delivery/signing capability for) one configured organization, say `OrgA` with `webhook_secret_A`, can POST directly to the public `/webhooks` endpoint with:
- `X-Hub-Signature` computed with `webhook_secret_A`
- JSON body: `repository.owner.login = "OrgA"` (so `verify_signature` selects and validates against `webhook_secret_A`, which succeeds)
- JSON body: `repository.full_name = "OrgB/private-repo"` (so the handler resolves and mutates `OrgB`'s `Repository`/`Stack`)

This breaks the binding "organization that authenticated" == "repository that is written", exactly the isolation the multi-app configuration is meant to guarantee.

### Impact Explanation
This allows a low-privilege actor - who is only trusted with one organization's webhook secret - to forge arbitrary webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) against stacks/repositories belonging to a completely different, unrelated organization configured on the same Shipit instance. Concretely this enables cross-repository/cross-organization writes: e.g. forged `push` events trigger `GithubSyncJob`/`stack.sync_github` for another org's stack, forged `status`/`check_suite` events falsify CI state used to gate `deployable?`, and forged `membership` events create/delete `Team`/`Membership` records for another organization's `oauth_teams`, which feed into `Shipit.github_teams` authorization. This matches the Critical "cross-repository writes" / High "escalation into `Shipit.github_teams` authorization" impact categories.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate holder of the webhook secret for *any one* organization configured on the shared Shipit instance (a normal, low-privilege condition for a multi-tenant deployment that intentionally isolates organizations via separate GitHub Apps, per `docs/setup.md`). No GitHub App private key, `api_clients_secret`, or Shipit session is required — only a raw HTTP POST to the public webhook endpoint. Given that the documented purpose of per-organization apps/secrets is isolation between tenants, this is a realistic misconfiguration-independent flaw in the engine's own verification logic.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification succeeds, cross-check that the same organization identity used to select the signing `GitHubApp` (`repository_owner`) matches the owner embedded in `repository.full_name` (and any other repository/organization references in the payload) before dispatching to handlers. Reject (422) any request where these do not match. More robustly, handlers should receive the already-authenticated organization/owner from the controller rather than re-deriving repository/owner identity from unauthenticated payload fields.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`'s multi-app example: `OrgA` (`webhook_secret_A`) and `OrgB` (`webhook_secret_B`), each with a `Repository`/`Stack`.
2. As an entity that only knows `webhook_secret_A` (e.g., an admin of `OrgA`'s installed GitHub App), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/private-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, raw_body)>` and set `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and validates the signature successfully against `webhook_secret_A`.
5. `create` invokes `PushHandler`, whose `repository_name` (from `Handler#repository_name`) resolves to `"OrgB/private-repo"`, looking up and mutating `OrgB`'s `Stack` (e.g. enqueuing `GithubSyncJob`) — despite the request never being authenticated by `OrgB`'s secret.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
