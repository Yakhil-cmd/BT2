### Title
Api::CCMenuController lets a stack-scoped ApiClient token read CCMenu status for any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` tokens can be scoped to a single `stack_id`, and `Api::BaseController#stack` enforces that scope by resolving the requested stack through `stacks`, which filters to `Stack.where(id: current_api_client.stack_id)` when the token is scoped. [1](#0-0)  `Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving the stack directly from the request parameter instead of from the scoped `stacks` relation. [2](#0-1) 

### Finding Description
The binding that is broken is: **the stack a token authorizes == the stack it touches**.

- `ApiClient#check_permissions!` only validates the coarse `operation:scope` string (e.g. `read:stack`); it has no notion of which specific stack the token is allowed to touch. [3](#0-2) 
- The actual per-stack restriction is implemented purely in `BaseController#stacks`/`#stack`: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, then `stacks.from_param!(params[:stack_id])`. [1](#0-0) 
- `CCMenuController` redefines `stack` as `Stack.from_param!(params[:stack_id])`, which resolves *any* stack by param, never consulting `current_api_client.stack_id`. [2](#0-1) 
- `CCMenuController#authenticate_api_client` also authenticates via `ApiClient.authenticate(params[:token])` (a GET query-string token, as used by `CCMenuUrlController`), independent of the standard Basic-Auth flow, but this only affects the authentication method, not the missing scope check. [4](#0-3) 

Consequently, an attacker holding *any* valid `ApiClient` token that has the `read:stack` permission — even one deliberately scoped by the operator to a single, low-sensitivity stack (e.g. tokens minted by `CCMenuUrlController#client`, which are `read:stack`-only and tied to one stack) — can query `GET /api/stacks/<other-owner>/<other-repo>/ccmenu?token=<token>` and receive build/deploy status for a stack the token was never meant to access. [5](#0-4)  The response leaks `lastBuildStatus`, `activity`, `lastBuildTime`, `lastBuildLabel`, and `webUrl` for the target stack's latest deploy/rollback. [6](#0-5) 

### Impact Explanation
This matches the in-scope High-severity bucket "unauthenticated read of stack state, task streams or deploy output": a credential explicitly scoped by design to one stack (`ApiClient#stack_id`) is silently honored for every other stack in the installation because `CCMenuController` does not reuse the scoping logic from `BaseController#stack`. This is a cross-repository information disclosure of deployment state — analogous to the OpenZeppelin advisory's core defect where a check performed at one point (quorum snapshot / stack authorization) is not re-validated at the point where the privileged action actually occurs (proposal execution / stack read).

### Likelihood Explanation
Any party who can obtain a legitimately-issued, narrowly-scoped `ApiClient` token (e.g., a stack-scoped CCMenu token shared with a low-trust CI dashboard/tool, as generated by `CCMenuUrlController`) can immediately exploit this without any additional privilege, by simply changing the `stack_id` in the request URL. No signature or secret needs to be forged; the existing valid token is reused as-is.

### Recommendation
Make `Api::CCMenuController#stack` reuse the inherited `stacks` scoping (i.e., call `stacks.from_param!(params[:stack_id])` as `BaseController` does) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped token cannot resolve stacks outside its authorized `stack_id`.

### Proof of Concept
1. Operator calls `GET /ccmenu/*stack_id` for `stack A`, which creates/reuses an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to stack A's id, returning a CCMenu URL containing `?token=<tokenA>`. [7](#0-6) 
2. Attacker who obtains `tokenA` (e.g., from a shared CI dashboard configuration) issues:
   `GET /api/stacks/other-owner/other-repo/ccmenu?token=<tokenA>`
3. `CCMenuController#authenticate_api_client` authenticates the token successfully via `ApiClient.authenticate(params[:token])`. [4](#0-3) 
4. `require_permission :read, :stack` passes because the token does have `read:stack` in its permission list, regardless of the target stack. [8](#0-7) 
5. `stack` resolves `other-owner/other-repo` directly via `Stack.from_param!`, ignoring that the token's `stack_id` points to stack A, and the XML response reveals `other-owner/other-repo`'s latest deploy status. [9](#0-8)
