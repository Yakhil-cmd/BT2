### Title
Missing minimum key-strength check for RSA keys in `is_valid_sig`/`vrf_verify` allows AAs to be gated by a practically-breakable signature scheme - (File: `signature.js`)

### Summary
The external advisory concerns liboqs continuing to accept the Rainbow Level I signature scheme after a practical key-recovery attack made it breakable — i.e., a verifier trusting a signature scheme whose private key can be recovered by an attacker. ocore's oscript formula engine exposes `is_valid_sig()` and `vrf_verify()`, which use `signature.validateAndFormatPemPubKey()` to accept PEM-encoded public keys before verifying a signature/proof against them. For RSA keys, that function never enforces a minimum modulus size, so an RSA key of essentially any (small) length is accepted as a "valid" key to authenticate against, even though small RSA moduli are practically factorable (analogous to a "broken parameter set" being accepted as secure).

### Finding Description
`validateAndFormatPemPubKey()` performs an ASN.1/DER structural parse of the PEM key and only checks:
- a maximum overall size (736 base64 chars, "largest is RSA 4096 bits") [1](#0-0) 
- for ECDSA curves only, that the key's byte length matches the expected size for the named curve [2](#0-1) 

For the RSA entry in `objSupportedPemTypes`, there is no `hex_pub_key_length` field and thus no length/strength validation at all — any RSA `SubjectPublicKeyInfo` matching the PKCS#1 RSA OID passes, regardless of modulus size: [3](#0-2) 

This function is invoked directly from the oscript formula evaluator for two operators reachable by an AA trigger sender / defined by an AA author:
- `is_valid_sig(message, pem_key, sig)` with `algo = "any"`, so an RSA key of any size satisfies the "any" filter [4](#0-3) 
- `vrf_verify(seed, proof, pem_key)` with `algo = "RSA"` explicitly [5](#0-4) 

Verification itself falls back to Node's `crypto.createVerify('SHA256').verify()` for non-secp256k1 keys, which does not itself reject undersized RSA keys: [6](#0-5) 

By contrast, note that the core protocol's mandatory address-authorization mechanism (`['sig', {pubkey}]` in address definitions) is hard restricted to `secp256k1` only, explicitly rejecting any other algorithm — this is the correct pattern the RSA path fails to follow: [7](#0-6) [8](#0-7) 

The `objSafePemTypes` allowlist added by the "pem curves fix" only restricts weak *elliptic curves*, and does not add any RSA-size floor — RSA remains unconditionally allowed regardless of `bPostPemCurvesFix`: [9](#0-8) 

### Impact Explanation
If an AA author relies on `is_valid_sig`/`vrf_verify` with an RSA public key (e.g., to gate a payout, order settlement, or state transition on possession of a private key belonging to a specific off-chain identity/oracle), the protocol provides no minimum-strength enforcement, so a small/weak RSA modulus can be silently accepted as equivalent to a strong one. Because small RSA moduli (e.g., 512-bit and smaller) are practically factorable, anyone who is not the legitimate key holder can recover the private key and forge signatures/VRF proofs that the AA's oscript will treat as authentic. This can be exploited by an AA trigger sender to satisfy conditions intended to require a legitimate signer's authorization, leading to unauthorized release of AA funds or acceptance of forged oracle attestations that drive fund-moving logic — a concrete AA fund-loss scenario reachable purely through posted triggers/oscript evaluation.

### Likelihood Explanation
Exploitability depends on an AA actually using a weak/small RSA key with `is_valid_sig`/`vrf_verify` (either by author mistake, dynamically-constructed keys, or any code path where the RSA key's provenance isn't independently strength-audited). The protocol gives no signal, warning, or enforcement to prevent this, unlike the ECDSA curve path where the "pem curves fix" explicitly disallowed weak curves. This is a real gap in defense-in-depth for a documented, user-reachable cryptographic primitive of the oscript language, though it requires a specific AA design choice to become directly exploitable against funds.

### Recommendation
Add an explicit minimum RSA modulus size (e.g., ≥2048 bits) check in `validateAndFormatPemPubKey()` for the `06092a864886f70d0101010500` (RSA) entry, mirroring the length check already done for ECDSA curves, and gate it behind `bPostPemCurvesFix`/a new upgrade MCI consistent with how the elliptic-curve allowlist was introduced.

### Proof of Concept
1. An AA author (or any user constructing oscript logic) writes an AA branch: `if (vrf_verify(seed, trigger.data.proof, trigger.data.pem_key)) { ... payout ... }` intending `pem_key` to identify a trusted oracle by its RSA public key.
2. An attacker crafts a PEM `SubjectPublicKeyInfo` with a small (e.g., 256–512 bit) RSA modulus that structurally satisfies the OID/ASN.1 checks in `validateAndFormatPemPubKey()` (`signature.js:117-188`) — no size floor rejects it.
3. The attacker factors the small modulus offline (trivial with modern tooling) and forges a valid RSA-SHA256 signature/proof for an arbitrary message.
4. The attacker submits a trigger with this `pem_key`/forged `proof`; `vrf_verify()`/`is_valid_sig()` (`formula/evaluation.js:1704-1766`) return `true`, and the AA proceeds to release funds or accept the forged data as if it came from a legitimate, strong key holder.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}
