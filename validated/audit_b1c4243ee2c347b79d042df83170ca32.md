### Title
Session fixation on GitHub OAuth callback — authenticated identity is bound to a pre-existing, non-rotated session — (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` writes the freshly authenticated GitHub identity directly into the *existing* Rails session (`session[:user_id] = sign_in_github(auth)`) without ever calling `reset_session`. The session container that receives the privileged identity is therefore never rotated at the point authentication succeeds, breaking the intended binding between "the GitHub identity that just completed OAuth" and "the session that must be freshly minted for that identity."

### Finding Description
The OAuth callback is: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

No `reset_session` is invoked before `session[:user_id]` is assigned. Contrast this with the only other place `reset_session` is called in the engine, `force_github_authentication`, which only resets the session on a *stale-credentials* logout path, never on a fresh login: [2](#0-1) 

The consequence is the classic session-fixation binding break: the equality the app should enforce is

`session_id(before OAuth completes, anonymous) != session_id(after OAuth completes, authenticated)`

but the code guarantees the opposite — the session container (and therefore its ID/cookie) is identical before and after privilege escalation. If an attacker can plant/share a session cookie with the victim before the OAuth dance starts (e.g. cookie tossing from a sibling subdomain sharing the cookie domain, a response that sets a cookie, or any mechanism that causes the victim's browser to carry an attacker-known session value into the flow), then once the victim completes the real GitHub OAuth handshake, the *same* session — now holding `session[:user_id]` for the victim — remains valid for the attacker too, because it was never rotated. This is precisely the "GitHub identity vs. the `User` bound to the session" binding named in scope: the GitHub identity that authenticates is supposed to be bound 1:1 to a newly issued session, but the code instead binds it to whatever session container already existed.

This requires none of the explicitly excluded prerequisites (no Shipit session pre-existing with privilege, no `ApiClient` token, no `webhook_secret`, no `api_clients_secret`, no GitHub App key, no repository write access) — it only requires the standard unprivileged-attacker session-fixation primitive of getting a session identifier into the victim's browser prior to their real OAuth login, which is exactly the "session fixation / forced OAuth completion" impact class explicitly called out as in-scope.

### Impact Explanation
If exploited, an attacker gains an authenticated session as the victim after the victim completes a legitimate GitHub OAuth login, without ever needing the victim's credentials. Once fixated, the attacker inherits `session[:user_id]` for the victim and can act as that user throughout the Shipit UI — this maps to the explicitly listed High-impact category "session fixation / forced OAuth completion."

### Likelihood Explanation
Likelihood depends on the attacker's ability to seed a session cookie into the victim's browser before the OAuth callback fires (e.g., cookie tossing across a shared parent domain, or any mechanism that lets a cookie be set for the app's domain without needing XSS on the app itself). The engine's `SameSiteCookieMiddleware` and default Rails encrypted-cookie session store make some fixation vectors harder, but the root cause — never regenerating the session at the moment of privilege escalation — is present and unconditional in this code path regardless of transport-level mitigations. I could not fully verify from the indexed files whether any additional session-store or cookie-scoping configuration (outside the excluded `config/**`/`test/dummy` boundaries) further constrains or blocks this vector; that residual uncertainty should be resolved by review of the deployed session-store configuration.

### Recommendation
Call `reset_session` at the start of `callback`, before assigning `session[:user_id]`, so a fresh session (and cookie) is always issued at the moment a GitHub identity is bound to the session:

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?

  reset_session
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

### Proof of Concept
1. Attacker obtains any session cookie value for the Shipit host (e.g., by visiting the app anonymously, or via a cookie-tossing vector on a shared parent domain) and gets the victim's browser to carry that same cookie (e.g., via a crafted link or cross-subdomain cookie write) before the victim authenticates.
2. Victim clicks the normal "Login with GitHub" link and completes the real GitHub OAuth flow.
3. `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` on the *existing* (attacker-known) session, per [3](#0-2) , without rotating the session.
4. The attacker's browser, holding the same session cookie, is now authenticated as the victim on subsequent requests, since `find_current_user` in [4](#0-3)  trusts `session[:user_id]` unconditionally.
