### Title
`StatusHandler#process` applies forged CI statuses to commits in unrelated stacks by matching only `sha`, ignoring the verified repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the *entire* `commits` table, without restricting to the stacks that belong to the repository named in the verified webhook payload. Because the `commits` table only enforces uniqueness of `sha` per `stack_id` (not globally), an attacker who can legitimately emit a signed `status` webhook from a repository they own can inject a forged status onto a same-SHA commit that belongs to a completely different stack/repository — including a victim stack that has `ignore_ci: true`, whose sibling-commit `blocked?`/`blocking?` computation never consults `ignore_ci` at all.

### Finding Description
The binding that should hold is: `payload.dig('repository', 'full_name') == commit.stack.repository.full_name` for every `Commit` mutated by a given webhook. `WebhooksController#verify_signature` correctly verifies the signature against the organization derived from the payload's own repository/organization (`repository_owner`), and the attacker is explicitly permitted to "emit webhooks from a repository they own" per the threat model, so this side of the check is legitimately satisfied for the attacker's own repository.

However, `Handler` defines a repository-scoped helper specifically for this purpose: [1](#0-0) 

`PushHandler` and `CheckSuiteHandler` both correctly use it to scope their side effects to stacks tied to the payload's own repository: [2](#0-1) [3](#0-2) 

`StatusHandler#process` does not use `stacks` at all — it queries `Commit` globally by `sha`: [4](#0-3) 

The `commits` table enforces `sha` uniqueness only per `stack_id`, not globally: [5](#0-4) 

This means any two stacks (backed by any repositories, e.g. a victim's private repo and a public fork of it that the attacker owns) that happen to share a commit with the same SHA — a routine occurrence for forks, since git SHAs are deterministic and preserved for unmodified history — will both have that `Commit` row updated by a single forged status webhook.

Root cause: `StatusHandler` fails to intersect the looked-up commits with `stacks` (i.e., repositories authenticated by the verified payload), unlike its sibling handlers.

Effect on the victim: the forged status is persisted via `create_status_from_github!` → `add_status`, updating `Commit#status`/`state`, which is what `blocking?`/`blocked?` consult: [6](#0-5) 

Crucially, `blocked?` never checks `stack.ignore_ci?` — it is purely a function of `blocking_statuses` and sibling commits' `blocking?` state: [7](#0-6) 

So even a victim stack configured with `ignore_ci: true` (which only affects `Commit#deployable?` at line 228) will still have its sibling commits' `blocked?`/UI/hook state corrupted by the attacker's forged status, because `blocked?` is reached independently of `ignore_ci` and the commit lookup itself is not scoped to the correct repository in the first place.

Existing guards that fail to stop this: `verify_signature` only proves the payload's repository/organization is legitimate for *that* repository — it says nothing about which `Commit` rows get mutated, since `StatusHandler#process` never checks that the matched `Commit`'s `stack` belongs to the verified repository. `ExplicitParameters` schema only validates the shape of `sha`/`state`/etc., not repository ownership.

### Impact Explanation
An attacker who owns any repository with a legitimately signed webhook integration (e.g., a public fork of a victim project, or any repo sharing commit history with a victim stack) can post a forged `status` event for a shared SHA and have it written as a `Status` on the victim's `Commit` row in an entirely different stack/repository they do not control. This can: falsely mark a blocking status as failing (corrupting `blocked?`, UI badges, `Hook.emit(:commit_status/:deployable_status, ...)` for the victim stack) or falsely mark it as `success` (potentially clearing a legitimate block and enabling `schedule_continuous_delivery`/auto-merge/deploy eligibility for a commit that never actually passed CI in the victim repo). This is a cross-tenant, one-payload-for-one-repository-mutates-another's-commit/stack scenario, matching the Critical impact category (payload for one repository mutating another's stack/commit, or enabling an unauthorized deploy). It is repeatable against any stack whose commit history overlaps (forks, shared upstream, monorepo splits) with a repository the attacker controls.

### Likelihood Explanation
Preconditions: the attacker must control/own a repository with a working (legitimately signed) webhook integration into the same Shipit instance, and that repository must share at least one commit SHA with the victim's stack — trivially true for any fork relationship, which is extremely common on GitHub. No secrets, sessions, or elevated GitHub permissions are required beyond what the Rules already grant the attacker ("emit webhooks from a repository they own"). Cost is a single crafted `status` webhook POST; the exploit is deterministic and repeatable against any shared-history commit.

### Recommendation
Scope `StatusHandler#process` to the repository authenticated by the verified payload, mirroring `PushHandler`/`CheckSuiteHandler`, e.g. restrict the lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) so only commits belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')` can be mutated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook from an unrelated repository cannot corrupt a different stack's blocked? state" do
  victim_stack = shipit_stacks(:shipit) # some_owner/some_repo
  victim_stack.update!(ignore_ci: true)
  victim_stack.cached_deploy_spec.stubs(:blocking_statuses).returns(['ci/build'])

  shared_sha = 'deadbeef' * 5
  blocked_sibling = victim_stack.commits.create!(sha: 'aaaa', ...)
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, ...) # newer than blocked_sibling, older than sibling under test

  # Equality that should hold: payload repository == commit.stack.repository
  assert_not_equal 'attacker/fork', victim_stack.repository.full_name

  # sibling commit not blocked before the forged webhook
  refute victim_commit.blocked?

  # Attacker posts a legitimately-signed status webhook for THEIR OWN repo, referencing the shared sha
  payload = {
    'repository' => { 'full_name' => 'attacker/fork', 'owner' => { 'login' => 'attacker' } },
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'ci/build'
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  assert_equal 'failure', victim_commit.state, "commit belonging to a different repository's stack was mutated"
  assert victim_commit.blocked?, "ignore_ci: true did not prevent blocked? from being corrupted by a foreign payload"
end
```
This demonstrates that even with `ignore_ci: true` on the victim stack, a forged status from an unrelated, attacker-owned repository corrupts `Commit#state`/`blocked?` for the victim's commit, because `StatusHandler#process` never checks the binding `payload.repository.full_name == commit.stack.repository.full_name`.
