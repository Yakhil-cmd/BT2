### Title
AA can receive indivisible (NFT-like) public assets but can never send them out - permanent fund lock ([File: aa_composer.js])

### Summary
Autonomous Agents (AAs) in ocore accept payments in any public asset, including `fixed_denominations` assets (ocore's indivisible/NFT-like asset type), as trigger inputs with no restriction. However, when an AA composes its response unit to send funds out, `aa_composer.js` explicitly skips any payment message that uses a `fixed_denominations` asset, silently dropping such outputs. As a result, any indivisible asset sent to an AA is permanently trapped in the AA's balance with no code path able to move it back out.

### Finding Description
`validateAATrigger` in `validation.js` only checks that outputs to an AA address are not duplicated per asset; it does not exclude `fixed_denominations` (indivisible) assets from being valid trigger payments to an AA address [1](#0-0) . Any unprivileged unit poster can therefore send an indivisible/NFT-like asset as a trigger payment to any AA.

When the AA later tries to respond and send a payment message denominated in that same asset, `aa_composer.js`'s `sendUnit` function loads the asset info and explicitly bails out for `fixed_denominations` assets with the comment "will skip it later": [2](#0-1) 

Then, in the second pass, any payment message referencing a `fixed_denominations` asset is filtered out of the messages array entirely before the response unit is built: [3](#0-2) 

This means an AA formula that attempts to forward an indivisible asset it holds to a user (e.g., `["payment", {asset: "...", outputs: [...]}]` for an indivisible asset) will have that message silently stripped, and if that was the only response message, the AA falls back to `handleSuccessfulEmptyResponseUnit`. The AA's on-chain `aa_balances` table still records the incoming indivisible-asset balance (added in `updateFinalAABalances` when processing the trigger's inbound payment) [4](#0-3) , but there is no mechanism in `aa_composer.js` anywhere else that composes an outgoing indivisible-asset payment message, so this balance is permanently unspendable by the AA.

### Impact Explanation
Any indivisible/NFT-like asset (`fixed_denominations: true`) sent to any AA address, whether accidentally by a user or intentionally as part of a bounty/marketplace/vault-style AA design, becomes permanently and irrecoverably stuck. This is a direct fund-loss/freezing condition reachable by any unprivileged unit poster who sends such an asset to an AA, or by an AA author who designs an AA intending to receive and later distribute indivisible assets (e.g., an NFT escrow, ongoing-bounty-like AA, or auction AA) — the AA can never fulfill its intended payout in that asset, and the value is permanently frozen at the AA's address.

### Likelihood Explanation
Likelihood is high for any AA use case that legitimately wants to handle indivisible assets (tickets, certificates, NFTs) since nothing in trigger/payment validation prevents funding an AA with such assets, and no AA developer-facing error/warning exists at composition time beyond a bounce with a generic empty-response message. Any user can trivially trigger this by sending a `fixed_denominations` asset payment to an AA address.

### Recommendation
Either:
1. Reject trigger payments of `fixed_denominations` assets to AA addresses in `validateAATrigger`/payment validation so such assets can never be sent to an AA in the first place, or
2. Implement proper composition support for indivisible-asset outputs in `aa_composer.js`'s `sendUnit` (analogous to the divisible/base-asset logic) so that AAs can actually forward `fixed_denominations` assets they hold, instead of silently discarding these payment messages.

### Proof of Concept
1. Deploy any AA whose formula, upon a certain trigger, attempts to respond with `["payment", {asset: "<indivisible_asset>", outputs: [{address: "$trigger.address", amount: 1}]}]` for some pre-existing `fixed_denominations` asset.
2. From any unprivileged address, send a unit carrying an indivisible-asset payment (`fixed_denominations: true`) whose output funds the AA address — this passes `validateAATrigger`/`validatePayment` with no restriction on asset type [5](#0-4) .
3. The AA's balance for that asset increases via `updateFinalAABalances` [4](#0-3) .
4. Trigger the AA logic that should send the indivisible asset back out. In `sendUnit`, the payment message for that asset is skipped (`objAsset.fixed_denominations // will skip it later`) and later filtered from `messages` entirely [6](#0-5) [7](#0-6) .
5. Observe that no payment for the indivisible asset is ever produced; the AA's `aa_balances` entry for that asset remains nonzero forever, with no way to spend it.
