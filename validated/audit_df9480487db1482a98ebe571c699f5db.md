### Title
Webhook signature is verified against `repository.owner.login`, but events are applied to whatever repository is named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::Webhook`s verifies the HMAC signature using the GitHub App/organization resolved from `repository.owner.login`, but the handlers that actually act on the payload locate the target `Stack`/`Commit` using the unrelated `repository.full_name` field from the very same, attacker-controlled JSON body. When Shipit is configured with multiple GitHub organizations and any one organization has no `webhook_secret` (documented as "optional" in `docs/setup.md`), an unauthenticated caller can produce a validly "verified" webhook for the secret-less organization while pointing `repository.full_name` at a completely different, protected repository/stack, causing the handler to write state (commit statuses, check runs, stack syncs) for that other repository without ever knowing its secret.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp`/secret to validate against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is blank for that resolved organization: [3](#0-2) 

Multi-org configuration is a supported schema (`Shipit.github(organization:)`, `github_app_config`), and `webhook_secret` is explicitly documented as optional per organization/app: [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature`, `WebhooksController#create` dispatches the *entire raw payload* to handlers: [6](#0-5) 

But `Handler#repository_name` — used by every push/status/check_suite/pull_request handler to select the `stacks` to mutate — reads a *different* field, `repository.full_name`, not `repository.owner.login`: [7](#0-6) 

This breaks the intended binding `verified_organization == acted_repository_owner`. Concretely:
- `StatusHandler#process` looks up commits purely `by sha` (global, not scoped to organization/owner) and calls `commit.create_status_from_github!`, which can flip a commit's CI status to `success`: [8](#0-7) 
- `Commit#deployable?` and `Commit#add_status` treat a `success` status as making the commit deployable and can trigger `stack.schedule_merges`/continuous delivery: [9](#0-8) [10](#0-9) 
- `PushHandler#process` resolves `stacks` from `repository_name` (`full_name`) and force-syncs them from GitHub regardless of which org's secret was checked: [11](#0-10) 

So an attacker who knows (or is themselves) the owner of any Shipit-configured organization that has no `webhook_secret` set can send `POST /webhooks` with `repository.owner.login` set to that secret-less org (making `verify_webhook_signature` return `true` unconditionally) while setting `repository.full_name` to any other tracked repository, e.g. `victim-org/victim-repo`, and forging `status`/`push`/`check_suite`/`pull_request` events against it.

### Impact Explanation
This is an authentication-bypass on a trust boundary that Shipit is supposed to enforce per-organization: the webhook signature check is meant to prove "this event genuinely came from GitHub for this org's repositories," but it is checked against a field that is disjoint from the field actually used to pick the mutated resource. The most severe consequence is forging a `success` commit status for an arbitrary tracked repository, making a normally CI-gated commit `deployable?` and, with continuous deployment enabled, triggering an unauthorized deploy via `schedule_continuous_delivery`/`schedule_merges` — squarely matching the in-scope "unauthorized deploy" impact. It also allows forcing `GithubSyncJob`s (`push`) and check-run refreshes (`check_suite`) on repositories the caller has no legitimate relationship to.

### Likelihood Explanation
This requires a deployment where Shipit is configured for multiple GitHub organizations and at least one of them has an empty/unset `webhook_secret` — a state the documentation and example secrets file explicitly present as a normal, supported ("optional") configuration, not a misconfiguration. Given that, the exploit requires no session, no `ApiClient` token, and no secret knowledge whatsoever: a bare unauthenticated HTTP POST to the public `/webhooks` endpoint with a crafted body and mismatched `X-Github-Event` header/owner/full_name fields is sufficient.

### Recommendation
Verify the webhook signature using the same field(s) the handlers use to locate the target resource (`repository.full_name`, not `repository.owner.login`/`organization.login`), or, at minimum, cross-check that `repository.full_name`'s owner segment matches the `repository_owner` used to select the signing secret before dispatching to handlers. Additionally, consider disallowing `webhook_secret` to be blank when more than one organization is configured, since a single secret-less org currently downgrades signature verification to a no-op for the entire multi-tenant deployment.

### Proof of Concept
Preconditions: Shipit configured with two orgs in `secrets.yml`, e.g. `orgA` (no `webhook_secret`) and `orgB` (protected repo `orgB/prod-app` tracked as a Stack with a commit `abc123` pending CI).

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "sha": "abc123",
  "state": "success",
  "context": "ci/forged",
  "repository": {
    "full_name": "orgB/prod-app",
    "owner": { "login": "orgA" }
  }
}
```

- `WebhooksController#repository_owner` resolves to `"orgA"`; `Shipit.github(organization: "orgA")` returns a `GitHubApp` with `webhook_secret` blank.
- `verify_webhook_signature` returns `true` unconditionally (no `X-Hub-Signature` header even required).
- `StatusHandler#process` runs and finds `Commit.where(sha: "abc123")` — which belongs to `orgB/prod-app` — and calls `create_status_from_github!`, marking it `success`, potentially making it `deployable?` and triggering continuous delivery for `orgB`'s stack, despite the request never being signed by `orgB`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
