### Title
CCMenu API endpoint bypasses per-stack ApiClient scoping, allowing an unauthorized read of any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a specific stack (`ApiClient#stack_id`) can only ever resolve `params[:stack_id]` against that one stack, via the `stacks`/`stack` helper methods. [1](#0-0)  `Shipit::Api::CCMenuController`, however, overrides `stack` to look the record up directly with `Stack.from_param!(params[:stack_id])` against the entire `Stack` table, completely bypassing that scoping check, while still only gating access with the generic `require_permission :read, :stack` declaration. [2](#0-1) 

### Finding Description
`ApiClient` records may optionally be bound to a single `Stack` (`belongs_to :stack, optional: true`). [3](#0-2)  `BaseController#stacks` is the mechanism that enforces this binding for every other API controller: if the authenticated client is scoped (`current_api_client.stack_id?`), only that one stack is visible; otherwise all stacks are visible. [1](#0-0)  `StacksController`, `TasksController`, `DeploysController`, etc. all resolve the requested stack through this `stacks`/`stack` helper, so a stack-scoped token cannot touch a stack it wasn't issued for (confirmed by `test/controllers/api/stacks_controller_test.rb`'s "an api client scoped to a stack will only see that one stack" test). [4](#0-3) 

`CCMenuController` breaks this equality. Instead of using `stacks.from_param!`, it defines its own `stack` method that queries `Stack.from_param!(params[:stack_id])` unconditionally, and only checks the coarse-grained `read:stack` permission (`require_permission :read, :stack`), never verifying that `current_api_client.stack_id` (if set) matches the requested `stack_id`. [5](#0-4) 

This is the exact bug-class analog described in the reference report: a value that is supposed to be checked/derived from a scoped, "current" context (the total supply cached at checkpoint time vs. re-derived at distribution time) is instead taken from an unchecked, attacker-supplied input. Here, the binding that should hold is:

`stack the ApiClient token authorizes == stack the CCMenuController action touches`

Before the pull request/behavior in question, this equality holds everywhere except `CCMenuController`. In `CCMenuController`, the right-hand side is replaced with whatever `params[:stack_id]` the caller supplies, independent of the left-hand side (`current_api_client.stack_id`).

### Impact Explanation
An attacker who possesses one legitimately-issued, stack-scoped `ApiClient` token (e.g., a "CCMenu Client" token intentionally scoped to a single, low-sensitivity stack, or any token created via the `api_clients` UI and manually bound to one stack) can supply a different `stack_id` in the request to `GET /api/:stack_id.xml` and read that other stack's build/deploy status (`stack.deploys_and_rollbacks.last`, lock state, activity, last build label, etc.), even though the token was never authorized for that stack. [6](#0-5)  This is an unauthenticated-for-that-resource read of stack state/deploy output across a security boundary that every other API controller enforces, matching the "unauthenticated read of stack state, task streams or deploy output" High-impact category.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with `read:stack` permission (the lowest, most commonly granted permission) — no elevated privileges, no GitHub write access, and no knowledge of internal secrets are needed. The only extra step is guessing/knowing the `owner/repo/environment` triple of the target stack (which is often predictable or discoverable, e.g., from public repository names). The existing test suite (`test/controllers/api/ccmenu_controller_test.rb`) never exercises the cross-stack scoping case, indicating this gap is untested and easy to miss. [7](#0-6) 

### Recommendation
Remove the `stack` override in `CCMenuController` and use the inherited, scope-aware `stacks.from_param!(params[:stack_id])` (or equivalently check `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`) so the CCMenu endpoint respects the same per-client stack scoping enforced by `BaseController`.

### Proof of Concept
1. Create two stacks, `org/repo-a/production` and `org/repo-b/production`.
2. Create an `ApiClient` scoped to `repo-a` only (`stack_id` set to repo-a's stack, `permissions: ['read:stack']`).
3. Using that client's `authentication_token`, request:
   `GET /api/org/repo-b/production.xml` with HTTP Basic auth using the token.
4. Expected (per other controllers' scoping): 404/`RecordNotFound`, since the token is not scoped to `repo-b`.
5. Actual: `CCMenuController#stack` resolves `repo-b` via unscoped `Stack.from_param!`, and `require_permission :read, :stack` passes because the client does hold `read:stack` — the response renders `repo-b`'s deploy/build status XML, confirming the cross-stack authorization bypass.

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }
