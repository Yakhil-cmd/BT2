### Title
AA "owner" state-var updates can front-run already-broadcast triggers because trigger execution order is decided at stabilization, not at broadcast time - (File: aa_composer.js, main_chain.js)

### Summary
The reported Yieldy bug lets an admin change a fee variable that governs a payout calculation, and front-run a user's already-submitted transaction by getting the fee change mined first. In ocore the analogous primitive is any Autonomous Agent (AA) that stores a mutable governance parameter (e.g. a fee, price, or rate) in a state var settable by a privileged trigger sender defined inside the AA's own oscript (any wallet can author such an AA, so this role is unprivileged at protocol level). Because ocore executes AA triggers only after the triggering unit becomes stable, and the execution order across triggers sharing an MCI is fixed only at stabilization time by `(mci, level, unit, address)` rather than by broadcast time, a user who broadcasts a trigger that depends on today's fee/price has no guarantee that their unit will be processed before a competing state-changing unit that is broadcast later but ends up with a smaller `level`/earlier `mci`.

### Finding Description
AA triggers are queued in `aa_triggers` and executed strictly in the order `ORDER BY aa_triggers.mci, level, aa_triggers.unit, address` [1](#0-0) , and this queue itself is populated only after an MCI is marked stable, using the deterministic ordering `ORDER BY units.level, units.unit, address` [2](#0-1) . Because `level` is computed from the DAG parents chosen at composition time (not from wall-clock broadcast order), an attacker who observes a victim's pending (not-yet-stable) trigger unit can compose and broadcast their own unit selecting parents that give it a lower `level` (or land it in an earlier `main_chain_index`), causing it to execute before the victim's trigger once both become stable — even though it was broadcast after the victim's transaction.

Inside an AA, a party the author designates as "owner"/governance (e.g. `if (trigger.address == params.owner_address) var['fee'] = trigger.data.fee`) can use `state_var_assignment` to mutate any state var read by subsequent formulas [3](#0-2) . If the victim's trigger computes a payout using `var['fee']` (or any price/rate variable) without an explicit slippage/maximum-fee bound, the owner can broadcast a fee-changing trigger designed to land earlier in the deterministic execution order than the victim's, exactly mirroring `setFee()` front-running `instantUnstake()` in the original report — except here the "mempool ordering" that is gamed is the DAG level/MCI ordering rather than a miner's transaction pool.

### Impact Explanation
Any AA that stores a mutable fee/price/rate state var controlled by a designated address, and lets ordinary trigger senders compute payouts based on that var without a caller-specified acceptable bound, is exposed to loss of funds: the sender can receive a worse-than-expected payout (or pay a higher-than-expected fee) because the parameter changed between the time they composed their unit and the time their trigger actually executes. Because ocore guarantees deterministic ordering only after stabilization, and never guarantees that "broadcast first" implies "executes first," any AA is inherently exposed to this ordering-manipulation risk unless the author defends against it in oscript.

### Likelihood Explanation
Exploitation requires: (1) an AA whose oscript defines a privileged trigger sender able to mutate a fee/price state var, and (2) that AA's payout logic omitting caller-supplied min/max bounds. Both are common, unenforced design choices left entirely to AA authors; ocore itself provides no protocol-level protection (no "as-of" locking of state read at broadcast time, no deadline/slippage primitives). Composing a unit with parents chosen to obtain a favorable `level` is straightforward and requires no special permission — any node can pick its own tips when building its message.

### Recommendation
- Document and, where feasible, provide oscript-level primitives/best-practice patterns (e.g. built-in `min_amount`/`max_fee`/deadline checks) so AA authors can let callers specify acceptable bounds and have the AA `bounce` if the state var changed beyond the caller's tolerance since the trigger was composed.
- Consider exposing to formulas a way to reference the state var value "as observed at composition time" versus "current," so AAs can implement commit-reveal or deadline-based protections without relying on external oracles.
- Emphasize in developer guidance that mutable governance parameters read inside payout formulas must always be paired with a caller-provided tolerance/slippage bound, since ocore does not guarantee execution order matches broadcast order.

### Proof of Concept
1. AA author deploys an AA with `var['fee']` settable by `params.owner_address` via a `state_var_assignment` formula, and a payout formula `payout = trigger_amount * (1 - var['fee'])` sent to any trigger sender, with no caller-specified minimum payout.
2. Victim composes and broadcasts trigger unit `U1` expecting `fee = 1%`, referencing current tips.
3. Owner observes `U1` in the unstable DAG (`storage.assocUnstableUnits`) before it stabilizes, and broadcasts trigger unit `U2` (`var['fee'] = 100%`) using earlier/independent tips so that `U2` obtains a smaller `level` (or lands in an earlier `main_chain_index`) than `U1`.
4. When the shared MCI stabilizes, `handleAATriggers` inserts and executes triggers ordered by `(mci, level, unit, address)` [2](#0-1) , so `U2`'s fee change executes before `U1`.
5. `U1`'s payout is computed with `fee = 100%`, and the victim receives (near) nothing instead of the expected 99% payout — reproducing the "malicious admin frontruns instantUnstake with fee increase" scenario entirely within ocore's own deterministic-but-composition-order-dependent trigger execution model.
