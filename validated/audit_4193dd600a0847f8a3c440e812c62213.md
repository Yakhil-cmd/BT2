### Title
`RollbackCommands#env` inherits unfiltered `@stack.env` (PR-label-derived) injection, unfiltered by `filter_rollback_envs`/`rollback_variables` - ([File: lib/shipit/rollback_commands.rb])

### Summary
`RollbackCommands#env` calls `super` (through `DeployCommands` → `TaskCommands#env`), which unconditionally merges `@stack.env` into the process environment before adding `ROLLBACK=1`. For a `ReviewStack`, `env` is overridden to merge every PR label name (uppercased) as an environment key with value `"true"`, and this merge happens identically whether the task is a `Deploy` or a `Rollback`. `filter_rollback_envs`/`rollback_variables` only ever scope the user-supplied `env` parameter passed through the rollback controllers, never `@stack.env`, so the label-injected keys reach `PTY.spawn` for `rollback_steps` completely unfiltered — the same way they do for `deploy_steps`.

### Finding Description
Binding claimed: `keys(Command#unbundled_env during rollback) == keys(deploy_spec.rollback_variables ∪ deploy_spec.machine_env)`. This is false; the actual set is a strict superset that also includes every uppercased PR label name.

Path:
1. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` directly from attacker-controlled webhook payload with no interpolation/whitelist check [1](#0-0) .
2. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the stack's env hash unconditionally, with no filtering against `deploy_variables`/`rollback_variables` [2](#0-1) .
3. `TaskCommands#env` merges `@stack.env` into the task environment before task/deploy-specific overrides [3](#0-2) .
4. `RollbackCommands#env` simply calls `super` and appends `'ROLLBACK' => '1'`, inheriting the same `@stack.env` merge unchanged [4](#0-3) .
5. `filter_rollback_envs`/`rollback_variables` (`deploy_spec.rb`) are only invoked on the `env` parameter accepted by `RollbacksController`/`Api::RollbacksController` — that filtered hash becomes `@task.env`, a value merged much later and never intersects with or restricts `@stack.env` [5](#0-4) [6](#0-5) .

Attacker request: open/label a PR on a repository they own with review-stacks enabled, using an interpreter-honoured label name (e.g., a shell/tool-recognized variable name). No Shipit session or credentials are needed — this is the standard unauthenticated webhook flow already gated only by webhook signature verification, which does not restrict label content. This is the exact same root cause already established for the deploy path, and it is confirmed to also affect the rollback execution path because `RollbackCommands` does not override or re-filter `env` beyond adding `ROLLBACK=1`.

### Impact Explanation
Any environment variable value settable via a label name (value fixed at `"true"`) is injected into the shell environment of `rollback_steps` commands executed via `Command`/`PTY.spawn` for the affected review stack — mirroring the deploy-path exposure and extending the attack window to a second execution path (rollback) for the same stack. Whether this reaches Critical (RCE) depends on whether `rollback_steps`/`deploy_steps` scripts consume unvalidated env-var names in a way that allows command execution (e.g., via `$VARNAME` interpolation in scripts using attacker-controlled variable names) — this is bounded by the same conditions as the already-established deploy finding. Blast radius is limited to review stacks of repositories with a supported rollback and where the attacker can label their own PR; it is repeatable per label change and does not cross into other repositories' stacks.

### Likelihood Explanation
Preconditions: review stack feature enabled, `deploy_spec.supports_rollback?` true (i.e., `rollback_steps` configured), and a PR the attacker controls/labels on their own repository. Attacker cost is minimal — labeling a PR requires only standard GitHub permissions on their own repo/fork and no Shipit credentials. This is deterministic and repeatable on every rollback of that stack as long as the label remains applied.

### Recommendation
Filter `@stack.env`'s label-derived keys the same way task/deploy/rollback variables are filtered — e.g., restrict `ReviewStack#env`'s label merge to an explicit allow-list, or run it through `deploy_spec.filter_deploy_envs`/`filter_rollback_envs` (or a dedicated `filter_label_envs`) using a stack/spec-defined set of permitted label-derived variable names before merging into the process environment used by both `DeployCommands#env` and `RollbackCommands#env`.

### Proof of Concept
```ruby
# test/unit/rollback_commands_test.rb (extension)
test "#env exposes unfiltered PR label as environment variable during rollback" do
  stack = shipit_review_stacks(:some_review_stack) # ReviewStack with rollback supported
  pull_request = stack.pull_request
  pull_request.update!(labels: ['DANGEROUS_VAR'])

  rollback = shipit_rollbacks(:shipit_rollback)
  rollback.stubs(:stack).returns(stack)

  commands = Shipit::RollbackCommands.new(rollback)
  env = commands.env

  assert_equal 'true', env['DANGEROUS_VAR']
  refute_includes stack.rollback_variables.map(&:name), 'DANGEROUS_VAR'
end
```
Binding assertion: `env.keys` (actual) is a strict superset of `stack.rollback_variables.map(&:name) ∪ deploy_spec.machine_env.keys` (expected per `filter_rollback_envs`), proving the label key `'DANGEROUS_VAR'` bypasses the intended whitelist during rollback execution.
