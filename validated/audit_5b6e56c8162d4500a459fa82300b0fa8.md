### Title
Webhook signature verification is bound to the payload's `repository.owner`/`organization` field, not to the repository/stack that is actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to check the HMAC against using an attacker-controlled field of the very same JSON body it is trying to authenticate, while every `Webhooks::Handlers::Handler` subclass locates and mutates the target `Stack`/`Repository`/`Team` using a *different* attacker-controlled field of that same body. The engine never checks that these two fields describe the same organization/repository, so the "organization that authenticated" and "the repository that is written" are only nominally the same value and are never cryptographically bound together.

### Finding Description
`verify_signature` picks the `GitHubApp` (and therefore the webhook secret) to validate against like this: [1](#0-0) 

```
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` is read directly from the untrusted, unsigned-at-this-point request body. `GitHubApp#verify_webhook_signature` then does:

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

i.e. if the org resolved from the payload has no `webhook_secret` configured, verification is a no-op and **any** payload is accepted, regardless of the `X-Hub-Signature` header.

Every event handler, however, resolves the actual `Stack`/`Repository`/`Team` that gets mutated from a *different* field of the same body:

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler#process` then acts on whatever stacks match that `full_name`:
```
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

Shipit explicitly supports multiple GitHub Apps/organizations in one installation, each with its own optional `webhook_secret`: [6](#0-5) 
and the webhook secret is documented as optional in the single-org setup as well: [7](#0-6) 

Because `repository.owner.login`/`organization.login` (used to pick the secret) and `repository.full_name` (used to pick the record to mutate) are two independent, unauthenticated fields of the same attacker-supplied JSON body, an attacker only needs the signature check to trivially pass for *any one* configured organization (i.e. that organization has no `webhook_secret` set, which is a documented, supported configuration) in order to forge events that are attributed to and mutate `Stack`/`Repository`/`Team` records belonging to any *other*, fully-secured organization tracked by the same Shipit instance. Nothing in `Handler`, `PushHandler`, `StatusHandler`, `MembershipHandler`, or the `PullRequest::*Handler`s cross-checks that the org used for signature verification matches the owner embedded in `repository.full_name` / `organization.login` used for the actual write.

### Impact Explanation
An attacker who knows that at least one org configured in a multi-tenant Shipit deployment has no `webhook_secret` (a documented/allowed configuration, not a leaked secret) can forge webhook requests naming that org for authentication while pointing `repository.full_name` at a `Stack` belonging to a different, secured organization. This lets them:
- Inject fabricated commits/`expected_head_sha` into another org's `Stack` via `PushHandler` → `Stack#sync_github`.
- Inject fabricated commit statuses via `StatusHandler`, which drives `Commit#add_status` and can trigger `stack.schedule_merges` for a repository they don't control.
- Create/mutate `Team`/`Membership` records via `MembershipHandler` for an org they don't own.
- Archive/unarchive review stacks and manipulate PR state via the `PullRequest::*Handler`s for repositories under a different org.

These are writes into Shipit's persisted state for a repository/organization whose trust boundary was never actually authenticated - a cross-repository/cross-organization write performed without possessing any of the excluded credentials (no session, no `ApiClient` token, no actual `webhook_secret` value, no GitHub App key).

### Likelihood Explanation
Requires: (1) the target Shipit deployment tracks stacks across more than one GitHub organization (an explicitly documented, supported feature), and (2) at least one of those organizations is configured, per the docs, without a `webhook_secret`. Given `webhook_secret` is documented as optional and many simple/legacy setups omit it, this is a realistic deployment state rather than a theoretical one; no secret knowledge, session, or privileged credential is required from the attacker.

### Recommendation
- Make `webhook_secret` mandatory (or at minimum warn/refuse to boot when any configured GitHub org lacks one), removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`.
- Cross-validate, inside `WebhooksController#verify_signature`/`Handler`, that the organization used to resolve the signing app (`repository.owner.login` / `organization.login`) matches the owner embedded in `repository.full_name` before dispatching to any handler, rejecting mismatches with `422`.
- Consider binding verification not just to "an org that has *a* valid secret" but to "the specific org that owns the specific repository being mutated."

### Proof of Concept
Preconditions: multi-org Shipit config (`config/secrets.yml`) with `orgA` (no `webhook_secret`) and `orgB` (has `webhook_secret`, tracks the target `Stack`).

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # ignored, orgA has no secret

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },      // used only to pick verifying secret
    "full_name": "orgB/victim-repo"    // used to pick the Stack that gets mutated
  }
}
```
`verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally. `PushHandler` then resolves `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on a `Stack` belonging to the fully-secured `orgB`, without ever possessing `orgB`'s secret.

      return true unless webhook_secret

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
