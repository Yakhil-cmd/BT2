### Title
Caller authorization remains live during arbitrary flash-position callbacks, allowing nested wallet or account theft - ([File: contracts/controller/src/strategies/flash_position.rs])

### Summary
`flash_position` authenticates `caller`, validates a caller-selected Wasm receiver, mints debt, and then invokes that receiver inside the same authorized invocation tree. [1](#0-0)  The callback receives both `caller` and `account_id`, while the account owner check was performed before the callback and is not repeated afterward. [2](#0-1) [3](#0-2)  A malicious receiver can therefore add a nested `caller`-authorized token transfer or position-NFT transfer to the transaction authorization tree.

### Finding Description
`process_flash_position` calls `require_authorized_caller`, which performs `caller.require_auth()` before the external callback. [4](#0-3) [5](#0-4)  The receiver is selected entirely through the `receiver` argument and is only checked to be a Wasm contract distinct from the controller and pool, not an allowlisted or protocol-trusted contract. [6](#0-5) 

For an existing account, `AccountGuard::Multiply` verifies that `caller` is the owner or an active delegate before the callback runs. [2](#0-1) [7](#0-6)  The callback is invoked with `caller`, `account_id`, the debt asset, amounts, and arbitrary `data` after debt has been minted and forwarded. [3](#0-2) 

That ordering leaves the caller's authorization available to descendant calls made by attacker-controlled code. A malicious callback can request a `caller` token transfer unrelated to the flash position, or transfer the `account_id` position NFT because account ownership is resolved through the NFT owner record. [8](#0-7)  Transaction simulation can include that malicious transfer as a sub-invocation beneath the victim's `flash_position` authorization; if the victim signs the prepared tree, the callback can satisfy the nested authorization.

The callback can still satisfy the declared collateral minimum by transferring sufficient listed collateral to the controller. [9](#0-8)  The controller then performs normal supply crediting and risk finalization without re-resolving the NFT owner, so an NFT transfer performed by the callback is not detected before success. [10](#0-9) 

### Impact Explanation
The impact is theft of user funds and potentially theft of the complete lending account. An unrelated wallet token stolen by the callback is transferred directly to the attacker, while a stolen position NFT gives the attacker control of the account's supplied collateral and debt obligations. [11](#0-10)  The attack is not bounded by the flash-position collateral minimum or final solvency checks because those checks measure the account and controller balances, not unrelated assets removed from the victim's wallet. [9](#0-8) 

### Likelihood Explanation
An unprivileged attacker can deploy the receiver and construct the malicious `flash_position` call; no privileged role, leaked key, oracle manipulation, upgrade, or protocol parameter is required. [12](#0-11)  The attack requires the victim to sign a prepared authorization tree containing the malicious sub-invocation, consistent with a crafted transaction or malicious interface rather than an unauthenticated direct theft. This matches a Medium-severity user-interaction authorization flaw rather than a purely passive exploit.

### Recommendation
Do not invoke arbitrary caller-selected contracts while the caller's authorization is live for `flash_position`. [3](#0-2)  Prefer a governance-approved receiver allowlist or a fixed protocol-owned callback adapter whose code cannot request unrelated `caller` authorization.

If arbitrary receivers remain supported, re-resolve the NFT owner after the callback and revert if ownership changed, and require integrations to reject any signed authorization tree containing descendants beyond the explicitly expected token movements. [8](#0-7)  The post-callback owner check prevents account theft but does not prevent unrelated wallet-token theft, so it is not sufficient by itself.

### Proof of Concept
1. The victim owns a healthy `Multiply`, `Long`, or `Short` account whose position can support a small additional borrow, and the selected debt market has `is_flashloanable` enabled. [13](#0-12) 
2. The attacker deploys a Wasm receiver whose `execute_flash_position` sends enough of a listed collateral asset to the controller to satisfy `collaterals`, then invokes `token.transfer(caller, attacker, victim_wallet_balance)` for an unrelated victim token or invokes the position NFT transfer for `account_id`. [14](#0-13) [3](#0-2) 
3. The attacker prepares `flash_position(caller = victim, account_id = victim_id, spoke_id = victim_spoke, mode = victim_mode, debt = enabled_debt_market, amount > 0, receiver = malicious_receiver, data = arbitrary, collaterals = [(listed_collateral, minimum)], refund_assets = [])`. [15](#0-14) 
4. Simulation returns a victim authorization rooted at `flash_position` with the malicious token or NFT transfer included as a child invocation.
5. The victim signs the prepared tree; `require_auth` succeeds, ownership is checked once, debt is forwarded, and the malicious callback executes. [16](#0-15) [7](#0-6) 
6. The receiver supplies the minimum collateral, so post-callback deposit and finalization succeed while the malicious transfer remains part of the committed transaction. [10](#0-9)

```rust
pub(crate) fn process_flash_position(
    env: &Env,
    caller: &Address,
    params: FlashPositionParams<'_>,
) -> u64 {
    require_authorized_caller(env, caller);

    let FlashPositionParams {
        account_id,
        spoke_id,
        mode,
        debt,
        amount,
        receiver,
        data,
        collaterals,
        refund_assets,
    } = params;

    require_positive_amount(env, amount);
    config::require_hub_active(env, debt.hub_id);
    assert_with_error!(
        env,
        matches!(
            mode,
            PositionMode::Multiply | PositionMode::Long | PositionMode::Short
        ),
        CollateralError::InvalidPositionMode
    );
    require_wasm_receiver(env, receiver);

    let controller = env.current_contract_address();
    assert_with_error!(
        env,
        *receiver != controller,
        FlashLoanError::InvalidFlashloanReceiver
    );

    let mut cache = Context::new(env);
    let pool_addr = cache.cached_pool_address();
    assert_with_error!(
        env,
        *receiver != pool_addr,
        FlashLoanError::InvalidFlashloanReceiver
    );
    // Caller-selected receivers require flash loans enabled; multiply uses
    // the configured router and does not require this flag.
    assert_with_error!(
        env,
        cache.cached_pool_sync_data(debt).params.is_flashloanable,
        FlashLoanError::FlashloanNotEnabled
    );
```

```rust
    /// Mints `amount` of `debt` without a flash fee, forwards measured receipts
    /// and invokes the Wasm receiver's `execute_flash_position` callback.
    /// `collaterals` sets minimum controller-balance increases to deposit;
    /// listed `refund_assets` balance increases return to the caller.
    /// Returns the solvent account's id; `account_id = 0` creates it. An existing
    /// account requires owner or delegate authorization and a matching mode.
    #[when_not_paused]
    fn flash_position(
        env: Env,
        caller: Address,
        account_id: u64,
        spoke_id: u32,
        mode: PositionMode,
        debt: HubAssetKey,
        amount: i128,
        receiver: Address,
        data: Bytes,
        collaterals: Vec<(HubAssetKey, i128)>,
        refund_assets: Vec<Address>,
    ) -> u64 {
        strategies::flash_position::process_flash_position(
            &env,
            &caller,
            FlashPositionParams {
                account_id,
                spoke_id,
                mode,
                debt: &debt,
                amount,
                receiver: &receiver,
                data: &data,
                collaterals: &collaterals,
                refund_assets: &refund_assets,
            },
        )
    }
```
