## #Vulnerability found for this question.

### Title
Non-deterministic OpenSSL-backed `is_valid_sig`/PEM signature verification in oscript can cause node disagreement on AA validity - (File: signature.js)

### Summary
The oscript function `is_valid_sig` (and `vrf_verify`) delegates ECDSA/RSA signature verification for a large, attacker-selectable set of curves to Node.js's `crypto.createVerify('SHA256').verify(...)`, which is backed by the host's OpenSSL library [1](#0-0) . Unlike the deterministic in-repo `secp256k1` verification path, correctness of `crypto.verify()` for edge-case inputs (malformed/non-canonical DER points, invalid or degenerate EC public-key points, signature malleability) is determined by the underlying OpenSSL version bundled with each node's Node.js runtime, not by ocore's own code. This is the same class of bug as EL-2025-24: a cryptographic edge case (there, "point at infinity" in EIP-2537 BLS12-381) is handled ambiguously by the underlying implementation, so different client/runtime versions can reach different accept/reject verdicts for the same input, which is unacceptable in a consensus-critical validation path.

### Finding Description
`validateAndFormatPemPubKey` accepts dozens of ECDSA curves (brainpool, prime, secp, sect, wap-wsg families) via `objSupportedPemTypes`, restricting only to a smaller "safe" set (`objSafePemTypes`) after `pemCurvesFixMci` [2](#0-1) [3](#0-2) . For any accepted PEM key/curve other than `secp256k1` (which is separately verified deterministically via the `secp256k1` npm package, see `verifyMessageWithSecp256k1PemPubKey`), the actual signature check falls through to `crypto.createVerify('SHA256').verify({key: pem_key}, signature, encoding)` [4](#0-3) .

This function is directly reachable by any unprivileged unit poster or AA trigger sender through the `is_valid_sig(message, pem_key, signature)` oscript primitive, which is evaluated during AA response computation and during unit validation via `Definition.evaluate`/`validateAuthentifiers` paths that use `signature.verifyMessageWithPemPubKey` [5](#0-4) . It is also reachable via `vrf_verify` for RSA keys [6](#0-5) .

Because oscript/AA evaluation results (and thus unit/AA-response validity, DAG stability determination, and state-vars/fund movements) must be bit-for-bit identical across all full nodes, any verification path whose accept/reject outcome depends on the specific OpenSSL build/version linked into a given node's Node.js binary breaks this determinism guarantee. OpenSSL implementations have historically differed in behavior for degenerate EC public-key encodings, points not strictly on the curve, or signatures with non-canonical/extra-length DER encoding — exactly the same "spec vs. implementation ambiguity" class flagged in EL-2025-24 for BLS12-381 infinity-point handling.

### Impact Explanation
If a crafted `pem_key`/`signature`/`message` triplet is judged valid by one node's OpenSSL and invalid by another's, an AA using `is_valid_sig` in a condition guarding fund transfers, or a `sig`/definition path relying on non-secp256k1 PEM verification, will produce divergent unit/AA-response validity outcomes across the network. This causes nodes to disagree on unit or AA-trigger validity and, if such a unit becomes part of the main chain on some nodes but not others, on stability of the DAG — a Medium/High consensus-splitting condition affecting the network's ability to reach agreement on validity, structurally analogous to the impact described in EL-2025-24 (network split / stability disagreement).

### Likelihood Explanation
Exploitation requires finding an edge-case PEM public key/signature pair whose OpenSSL-verification result differs across the OpenSSL versions actually deployed among ocore full nodes. This requires nontrivial cryptographic research to construct a concrete divergent input, and the practical likelihood depends on how much OpenSSL version diversity exists across deployed nodes. Given that many non-secp256k1 curves are still accepted (pre-`pemCurvesFixMci`, and even a reduced "safe" set post-fix) and none of them are verified deterministically like secp256k1, the attack surface is present in production oscript code today, not merely legacy/deprecated code, and any single crafted trigger unit can attempt to exploit it.

### Recommendation
Replace the OpenSSL-`crypto.verify` fallback in `verifyMessageWithPemPubKey` with a fully deterministic, in-repo (or vetted, version-pinned) ECDSA/RSA implementation for every curve in `objSupportedPemTypes`, the same way `secp256k1` is already handled via the `secp256k1` npm package rather than OpenSSL. At minimum, restrict `objSafePemTypes` to curves/algorithms verified with pure-JS or otherwise deterministic libraries, and add explicit point-validity/canonical-encoding checks (reject points at infinity, reject non-canonical DER) before calling into any OpenSSL-backed primitive so that behavior cannot vary by node OpenSSL version.

### Proof of Concept
Conceptual PoC path (requires constructing an actual divergent input via curve-specific research):
1. Author an AA (or plain unit `sig`/`hash`-style definition path) that evaluates `is_valid_sig(message, pem_key, signature)` where `pem_key` uses a non-`secp256k1` curve accepted by `objSupportedPemTypes`/`objSafePemTypes`.
2. Craft `signature`/`pem_key` bytes representing a degenerate case (e.g., public key encoding that different OpenSSL versions parse/validate inconsistently, or a DER signature with non-canonical/extra padding) — see the verification call site: [4](#0-3) .
3. Post the resulting unit/AA trigger to the network. Nodes running different OpenSSL versions bundled with their Node.js runtime evaluate `crypto.verify(...)` differently, causing some nodes to accept the unit/AA response as valid and others to reject it, producing disagreement on unit/AA validity — an ocore-specific analog of EL-2025-24's ambiguous point-at-infinity handling causing implementation divergence.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}

function validateAndFormatPemPubKey(pem_key, algo, handle, bPostPemCurvesFix) {

	if (!ValidationUtils.isNonemptyString(pem_key))
		return handle("pem key should be a non empty string");

	//we remove header and footer if present
	var contentAloneB64 = pem_key.replace("-----BEGIN PUBLIC KEY-----", "").replace("-----END PUBLIC KEY-----", ""); 
	
	//we remove space, tab space or carriage returns
	contentAloneB64 = contentAloneB64.replace(/\s/g, "");

	if (contentAloneB64.length > 736) // largest is RSA 4096 bits
		return handle("pem content is too large");

	if (!ValidationUtils.isValidBase64(contentAloneB64))
		return handle("not valid base64 encoding" + contentAloneB64);

	var contentAloneBuffer = Buffer.from(contentAloneB64, 'base64');

	if (contentAloneBuffer[0] != 0x30)
		return handle("pem key doesn't start with a sequence");

//we determine start and length of algo/curve identifiers
	if (contentAloneBuffer[1] <= 0x7F){
		if (contentAloneBuffer[2] != 0x30)
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 4;
		var identifiersLength = contentAloneBuffer[3];
	} else if (contentAloneBuffer[1] == 0x81){
		if (contentAloneBuffer[3] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 5;
		var identifiersLength = contentAloneBuffer[4];
	} else if (contentAloneBuffer[1] == 0x82){
		if (contentAloneBuffer[4] != 0x30) 
			return handle("pem key doesn't have a second sequence");
		var identifiersStart = 6;
		var identifiersLength = contentAloneBuffer[5];
	} else {
		return handle("wrong length tag");
	}

	//we decode the length of identifiers
	if (identifiersLength != 13 && identifiersLength != 16 && identifiersLength != 19 && identifiersLength != 20)
		return handle("wrong identifiers length" + identifiersLength);

	//we isolate the identifiers
	var contentAloneHex = contentAloneBuffer.toString('hex')
	var typeIdentifiersHex = contentAloneHex.slice(identifiersStart * 2, identifiersStart *2 + identifiersLength *2);

	if (!objSupportedPemTypes[typeIdentifiersHex])
		return handle("unsupported algo or curve in pem key");

	if (bPostPemCurvesFix && !objSafePemTypes.has(typeIdentifiersHex))
		return handle("unsupported curve after pem curves fix MCI");

	if (algo != "any"){
		if (algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "ECDSA")
			return handle("PEM key is not ECDSA type");
		if (algo == "RSA" && objSupportedPemTypes[typeIdentifiersHex].algo != "RSA")
			return handle("PEM key is not RSA type");
	}

	if (objSupportedPemTypes[typeIdentifiersHex].algo == "ECDSA" && objSupportedPemTypes[typeIdentifiersHex].hex_pub_key_length != (contentAloneHex.length - identifiersStart * 2 - identifiersLength *2 - 8))
		return handle("wrong key length");

	//we add back header and footer
	pem_key =	"-----BEGIN PUBLIC KEY-----" + "\n";
	pem_key += contentAloneB64+"\n";
	pem_key += "-----END PUBLIC KEY-----";
	return handle(null,pem_key);
}
