Confirmed: `StatusHandler#process` at [1](#0-0)  creates a commit status purely based on `Commit.where(sha: params.sha)` **globally across all stacks/repositories** — it does not scope by `repository_name`/organization at all, unlike `CheckSuiteHandler` and `Handler#stacks`. ## Title
Cross-organization webhook forgery via secret-less GitHub App bypasses signature verification for all repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting multiple GitHub organizations, each with its own `GitHubApp` configuration and optional `webhook_secret`. The webhook signature check in `WebhooksController#verify_signature` selects which organization's secret to validate against using `repository_owner`, a field taken from the attacker-supplied payload, while the actual repository whose state gets mutated is selected independently, by `Handler#repository_name`/`StatusHandler#process`, using a different field (`repository.full_name`/global `sha` lookup) from the same payload. Because `GitHubApp#verify_webhook_signature` treats an unset `webhook_secret` as "always verified" [2](#0-1) , any organization configured without a webhook secret becomes a skeleton key: an attacker can claim that organization for signature purposes while forging events for a completely different, secured repository.

### Finding Description
`WebhooksController#verify_signature` computes the signing organization solely from the payload: [3](#0-2) [4](#0-3) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` — fully attacker-controlled JSON, not yet authenticated at this point. `Shipit.github(organization: repository_owner)` looks up a per-organization `GitHubApp` (documented multi-org support in `docs/setup.md`, lines 182-209, and `lib/shipit.rb` `github`/`github_app_config`), and `verify_webhook_signature` is called against that org's `webhook_secret`: [2](#0-1) 
Note `return true unless webhook_secret` — a documented "optional" setting (`docs/setup.md` line 30, `config/secrets.development.example.yml` lines 11/24/33). Once verification "passes" for that (secret-less) org, the actual event processing binds to a repository/commit using a **separate, unauthenticated field** from the same payload:
- `Handler#repository_name` uses `payload.dig('repository', 'full_name')` [5](#0-4) , which is never cross-checked against `repository.owner.login` used for the signature lookup.
- `StatusHandler#process` doesn't even scope by repository at all — it matches by raw commit `sha` globally: [1](#0-0) .

This breaks the binding: `organization authenticated (via webhook signature) == repository/commit actually written`. Since the whole JSON body is attacker-controlled prior to verification, an attacker who knows (or is themselves) the owner of any org configured on the Shipit instance without a `webhook_secret` can send a webhook whose `repository.owner.login` names that unsecured org, while `repository.full_name` (or, for `status` events, just a known `sha`) targets an arbitrary other repository/stack managed by the same Shipit instance.

### Impact Explanation
Exploiting this lets an unauthenticated attacker forge GitHub webhook events for stacks belonging to organizations they do not control:
- `status` events let an attacker inject arbitrary/forged commit statuses for any commit whose SHA they can guess or discover (e.g., via GitHub's public API) via `commit.create_status_from_github!` [6](#0-5) . These forged "success" statuses feed directly into `MergeRequest#all_status_checks_passed?` [7](#0-6) , which the merge queue (`ProcessMergeRequestsJob`) uses to decide whether to auto-merge a pull request [8](#0-7) . A pull request can thus be tricked into merging without real CI passing — an unauthorized merge — satisfying the Critical impact bar ("unauthorized deploy, rollback or merge").
- `push` events targeting a victim stack trigger `GithubSyncJob`, and `check_suite`/`membership` events allow further state manipulation for repositories outside the attacker's actual org.

### Likelihood Explanation
Requires only that at least one GitHub organization configured on the Shipit instance has no `webhook_secret` set — an explicitly supported/optional configuration per `docs/setup.md` and the example secrets files — and that the attacker knows that organization's login and a target commit SHA/repository full name, both public information on GitHub. No GitHub App private key, session, or `ApiClient` token is required; the request is a plain unauthenticated POST to `/webhooks`.

### Recommendation
Bind the signature-verifying organization to the same repository identity used for processing: after selecting `github_app` for `repository_owner`, verify that `payload.dig('repository', 'full_name')`'s owner segment (and any handler-level repository/commit lookup) matches `repository_owner`/the actual `Repository#owner` for the resolved stack before applying any state change, or resolve the repository/stack first and derive the signing organization from the resolved `Repository#owner` (a trusted, DB-backed value) rather than from the raw untrusted payload. Additionally, `GitHubApp#verify_webhook_signature` should not silently accept unsigned/any-signature requests when `webhook_secret` is blank in a multi-organization configuration — a secret should be mandatory for any organization if any other organization in the same instance is configured with one.

### Proof of Concept
Assume a Shipit instance configured for two organizations per `docs/setup.md`'s multi-org format: `OrgA` (attacker-controlled or with no webhook secret set) and `OrgB` (secured, hosts the victim stack `OrgB/prod-app`).

1. Attacker finds a currently pending/failing pull request in `OrgB/prod-app` with head commit `abc123...`.
2. Attacker sends:
```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=anything-or-omitted

{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/prod-app" }
}
```
3. `verify_signature` resolves `repository_owner = "OrgA"`, loads `Shipit.github(organization: "OrgA")`; since `OrgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the signature header.
4. `StatusHandler#process` executes `Commit.where(sha: "abc123...")` and creates a `success` status on the real `OrgB/prod-app` commit, with no cross-check against `OrgA`.
5. On the next `ProcessMergeRequestsJob` run, `all_status_checks_passed?` is satisfied by the forged status, and the PR is merged to `OrgB/prod-app` without genuine CI approval.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
