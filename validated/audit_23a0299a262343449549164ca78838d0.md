### Title
Missing device-ownership check lets any paired correspondent delete another user's pending shared-address proposal - ([File: wallet.js])

### Summary
The `reject_new_shared_address` message handler in `wallet.js` deletes rows from `pending_shared_addresses` / `pending_shared_address_signing_paths` keyed solely by `address_definition_template_chash`, a value supplied by the sender, with no check that `from_address` (the device that sent the message) is actually a participant in that pending shared-address proposal.

### Finding Description
`wallet.js` routes the `reject_new_shared_address` message straight to `walletDefinedByAddresses.deletePendingSharedAddress`, validating only that the payload is a syntactically valid address: [1](#0-0) 

`deletePendingSharedAddress` performs unconditional `DELETE` statements filtered only by `definition_template_chash`, never checking `device_address` or any relationship between the caller and the proposal: [2](#0-1) 

Any device that has previously paired with the victim (a normal, low-privilege pairing relationship — no special trust required) and that can compute or guess/observe the `definition_template_chash` (which is derived deterministically via `objectHash.getChash160(arrAddressDefinitionTemplate)` from data that is broadcast to all members of the proposed shared address, see `createNewSharedAddressByTemplate`) can send a forged `reject_new_shared_address` message and delete the pending multi-signature address proposal that legitimately belongs to other cosigners, even though the attacker is not one of the cosigners referenced by `pending_shared_address_signing_paths.device_address` for that chash. [3](#0-2) 

This mirrors the CVE-2025-52670 bug class: an authenticated, low-privilege actor can delete a resource (here, a pending shared-address approval workflow) belonging to a different account, because the deletion routine only checks the *identity* of the target resource, not the caller's *relationship/ownership* of it.

### Impact Explanation
An attacker who is merely a paired correspondent of one of the cosigners (or who otherwise learns/derives the `definition_template_chash`) can silently abort in-flight creation of shared (multisig) addresses belonging to other users by deleting their pending approval state. This can be used to griefing/denial-of-service the address-creation workflow for other users' multisig setups, causing loss of already-collected approvals and forcing victims to restart the process, which can disrupt fund custody arrangements built around that shared address (e.g., a payment or escrow the victim expected to complete via the pending multisig address).

### Likelihood Explanation
Reachable by any device that is a correspondent of the wallet (a low-privilege, easily obtained trust relationship via pairing) sending a single crafted `reject_new_shared_address` message; no signature over the target resource ownership is required, and the `chash` is not secret — it is transmitted to every party in `sendOfferToCreateNewSharedAddress`/`create_new_shared_address` messages during proposal setup. [4](#0-3) 

### Recommendation
In `deletePendingSharedAddress` (or its caller in `wallet.js`), verify that `from_address` is present in `pending_shared_address_signing_paths` for the given `definition_template_chash` (i.e., is actually one of the invited cosigner devices) before performing the delete, mirroring the ownership check pattern already used elsewhere (e.g., `prosaic_contract_update`'s `objContract.peer_device_address !== from_address` check). [5](#0-4) 

### Proof of Concept
1. Device A initiates a shared-address proposal with cosigners B and C via `create_new_shared_address` / `createNewSharedAddressByTemplate`, producing `address_definition_template_chash = X`, which is sent to B and C in the `create_new_shared_address` offer. [6](#0-5) 
2. Attacker device M, who is merely a paired correspondent of B (not a cosigner in the proposal, or even a wholly unrelated device that observed/derived chash X), sends `{"subject":"reject_new_shared_address","body":{"address_definition_template_chash":"X"}}` to A.
3. `wallet.js`'s handler only validates that `X` looks like a valid address string, then calls `deletePendingSharedAddress(X)` without checking `from_address`. [1](#0-0) 
4. `deletePendingSharedAddress` deletes all `pending_shared_addresses` and `pending_shared_address_signing_paths` rows for chash `X`, destroying the pending proposal and any approvals already collected from B and C, even though M was never a party to it. [2](#0-1)

function createNewSharedAddressByTemplate(arrAddressDefinitionTemplate, my_address, assocMyDeviceAddressesByRelativeSigningPaths){
	validateAddressDefinitionTemplate(arrAddressDefinitionTemplate, device.getMyDeviceAddress(), function(err, assocMemberDeviceAddressesBySigningPaths){
		if(err) {
			throw Error(err);
		}

		// assocMemberDeviceAddressesBySigningPaths are keyed by paths from root to member addresses (not all the way to signing keys)
		var arrMemberSigningPaths = Object.keys(assocMemberDeviceAddressesBySigningPaths);
		var address_definition_template_chash = objectHash.getChash160(arrAddressDefinitionTemplate);
		db.query(
			"INSERT INTO pending_shared_addresses (definition_template_chash, definition_template) VALUES(?,?)", 
			[address_definition_template_chash, JSON.stringify(arrAddressDefinitionTemplate)],
			function(){
				async.eachSeries(
					arrMemberSigningPaths, 
					function(signing_path, cb){
						var device_address = assocMemberDeviceAddressesBySigningPaths[signing_path];
						var fields = "definition_template_chash, device_address, signing_path";
						var values = "?,?,?";
						var arrParams = [address_definition_template_chash, device_address, signing_path];
						if (device_address === device.getMyDeviceAddress()){
							fields += ", address, device_addresses_by_relative_signing_paths, approval_date";
							values += ",?,?,"+db.getNow();
							arrParams.push(my_address, JSON.stringify(assocMyDeviceAddressesByRelativeSigningPaths));
						}
						db.query("INSERT INTO pending_shared_address_signing_paths ("+fields+") VALUES("+values+")", arrParams, function(){
							cb();
						});
					},
					function(){
						var arrMemberDeviceAddresses = _.uniq(_.values(assocMemberDeviceAddressesBySigningPaths));
						arrMemberDeviceAddresses.forEach(function(device_address){
							if (device_address !== device.getMyDeviceAddress())
								sendOfferToCreateNewSharedAddress(device_address, arrAddressDefinitionTemplate);
						})
					}
				);
			}
		);
	});
}
