### Title
Repository-preferred `repository_owner` webhook auth (`WebhooksController#verify_signature`) allows a payload verified against one org's (nil/weak) secret to mutate another org's `Team` via `MembershipHandler` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#repository_owner` picks `params.dig('repository','owner','login')` over `params.dig('organization','login')` to select which `GitHubApp` (and thus which `webhook_secret`) verifies the signature, but `MembershipHandler` uses `params.organization.login` (not `repository.owner.login`) to identify which `Team` row to create/mutate. `GitHubApp#verify_webhook_signature` also unconditionally returns `true` when the resolved org's `webhook_secret` is blank/nil. Combining these, a forged payload naming a `repository.owner.login` for an org with a nil/weak secret, alongside an unrelated `organization.login`, is authenticated using the weak-secret org's (non-)check while mutating the unrelated org's `Team`/membership rows.

### Finding Description
The broken binding: **the org whose secret authenticates the request (`repository_owner` = `params.dig('repository','owner','login')`) must equal the org whose `Team` row is mutated (`params.dig('organization','login')` used by `MembershipHandler#find_or_create_team!`)**. Nothing in the code enforces this equality.

- `WebhooksController#repository_owner` prefers the `repository.owner.login` field: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) .
- `verify_signature` resolves the `GitHubApp` for that `repository_owner` and calls `verify_webhook_signature` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank: `return true unless webhook_secret` [3](#0-2) .
- `MembershipHandler` never reads `repository.owner.login`; it derives the `Team.organization` strictly from `params.organization.login`: [4](#0-3) .

Exploit flow: attacker POSTs to `/webhooks` with header `X-Github-Event: membership`, a body containing `"repository": {"owner": {"login": "weak-secret-org"}}` (an org configured in Shipit but with `webhook_secret` nil/blank) and `"organization": {"login": "victim-org"}`, plus `team`/`member`/`action` fields satisfying `MembershipHandler`'s `ExplicitParameters` schema. `verify_signature` resolves `repository_owner` to `"weak-secret-org"`, and because that org's secret is blank, the signature check passes regardless of the `X-Hub-Signature` header content (or its absence). `MembershipHandler#process` then runs using `params.organization.login == "victim-org"`, creating/mutating a `Team` row scoped to `victim-org` and adding/removing members from `Shipit.github_teams` for that team - despite the request never being authenticated against `victim-org`'s secret. No code in `WebhooksController` or `MembershipHandler` cross-checks that `repository.owner.login` (or its absence) matches `organization.login`.

### Impact Explanation
This yields a cross-tenant write matching the Critical category "a payload for one repository mutating another's ... team," and also constitutes an authentication-bypass-adjacent issue since a request nominally verified for org A actually authorizes mutation of org B's authorization data (`Team`/`Membership`, which feeds `Shipit.github_teams` authorization checks elsewhere in the app). Repeated `added`/`removed` actions let the attacker manipulate arbitrary organizations' team membership records as long as any configured org exists with a nil/weak secret to anchor the signature check.

### Likelihood Explanation
This requires a genuine precondition: at least one org configured in `Shipit.github_teams`/`GithubHook`-style config with a blank/nil `webhook_secret` (the `return true unless webhook_secret` fallback in `GitHubApp#verify_webhook_signature`). If that precondition holds, the attacker cost is a single unauthenticated HTTP POST with no valid signature required, fully repeatable and scriptable against any organization named in the `organization.login` field.

### Recommendation
- Do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is unset; treat missing secret as a hard configuration/verification failure.
- Have `WebhooksController#repository_owner` and `MembershipHandler` (and other org-scoped handlers) agree on a single canonical source of "owning org" for a given event type, and reject payloads where `repository.owner.login` and `organization.login` diverge instead of independently trusting each field for different purposes.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two orgs in test config: `weak-secret-org` (`webhook_secret: nil`) and `victim-org` (any secret).
2. Stub `Shipit.github(organization: 'weak-secret-org')` to return a `GitHubApp` with nil secret (so `verify_webhook_signature` returns `true`).
3. POST to `/webhooks` with `X-Github-Event: membership`, no/garbage `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "T", "slug": "t", "url": "https://api.github.com/teams/1"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker"},
  "repository": {"owner": {"login": "weak-secret-org"}}
}
```
4. Assert response is `200 OK` (signature check passed via `weak-secret-org`'s nil secret): `assert_response :ok`.
5. Assert `Team.find_by(github_id: 1).organization == "victim-org"` — i.e., the mutated Team's org equals the divergent `organization.login`, not the `repository_owner` (`weak-secret-org`) that authenticated the request, proving the binding `repository_owner (auth) == organization.login (mutated)` is broken.
