### Title
Cross-organization webhook signature confusion allows forcing writes to a victim stack via a valid but wrongly-scoped signature - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound webhook using the `repository.owner.login` (or `organization.login`) field of the JSON body, while every downstream `Handler` resolves the repository/stack to act on using the entirely separate `repository.full_name` field. No code enforces that these two fields refer to the same organization/repository. An attacker who legitimately controls one org onboarded to this (multi-tenant) Shipit instance — and therefore knows that org's own `webhook_secret` — can sign a payload with their own secret while setting `repository.full_name` to a *different*, victim repository already tracked by the same instance. The signature verifies (it was correctly computed with a known, valid secret), yet the handler acts on the victim's stack.

### Finding Description
Signature verification only proves "this body was signed by organization X's webhook secret" — it never proves "the data inside this body belongs to organization X":

```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` is a pure HMAC check against whatever secret is loaded for `repository_owner`: [3](#0-2) 

Every handler, however, resolves the target repository/stacks using a *different* field of the same payload:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Because the app supports multiple independently-configured GitHub Apps/orgs, each with its own `webhook_secret` (as documented in the dummy multi-org secrets fixture with `OrgOne`/`OrgTwo` entries), an org that is legitimately onboarded to a shared Shipit instance knows its own secret but has no privilege over any other org's repositories: [5](#0-4) 

**Before the attack:** `repository.owner.login == attacker-org` and `repository.full_name == attacker-org/some-repo` — the org that authenticates equals the repo that is written.
**After the attacker's crafted request:** the attacker sets `repository.owner.login = attacker-org` (so the lookup in `verify_signature` still resolves to a secret they know) but `repository.full_name = victim-org/victim-repo`. The HMAC is computed over the full raw body with the attacker's own known secret, so `verify_webhook_signature` returns `true`, yet the handler that runs afterward operates on `victim-org/victim-repo`'s stacks — breaking the equality `organization-that-authenticated == repository-that-is-acted-upon`.

This is the same class of bug as the reported issue: a value used to gate a privileged transition (`VotesGCByVault` / the verified signature) is not properly re-validated/bound to the value that is actually acted upon (`NewGovernance` / `repository.full_name`), letting an entity with only narrow, self-scoped legitimacy reach outside its own scope.

### Impact Explanation
Concretely reachable handlers that act on the mismatched `repository.full_name`:
- `PushHandler` forces `Stack#sync_github(expected_head_sha: params.after)` on the victim stack with an attacker-chosen SHA [6](#0-5) .
- `StatusHandler` creates arbitrary commit statuses (`create_status_from_github!`) on the victim's commits, which can influence a commit's "deployable" status/CI gating [7](#0-6) .
- `CheckSuiteHandler` schedules check-run refresh jobs against the victim stack's commits [8](#0-7) .

This amounts to a cross-repository write into a stack the attacker does not control, and can be used to manipulate commit deployability/status data that gates real deploys — matching the Critical bucket ("cross-repository writes, or an unauthorized deploy").

### Likelihood Explanation
Requires the attacker to be a legitimate, low-privilege participant on a single org already onboarded to a Shipit instance that hosts multiple orgs/apps (the codebase explicitly supports this multi-tenant configuration). No GitHub App private key, `api_clients_secret`, or Shipit session is needed — only knowledge of the attacker's own org's `webhook_secret`, which they inherently possess as the owner of that GitHub App installation. Likelihood is Medium: it depends on the deployment hosting more than one organization/secret, which the code's design explicitly anticipates and documents.

### Recommendation
In `WebhooksController#verify_signature` (and/or in `Handler#repository_name`), after resolving the signing organization, verify that `repository.full_name`'s owner segment matches `repository_owner` (or, more robustly, that the resolved `Repository` belongs to the same organization whose secret validated the signature) before dispatching to any handler. Reject the payload (422) on mismatch, analogous to resetting `VotesGCByVault` — the derived state (`repository_name`) must be revalidated against the value that established trust (`repository_owner`) rather than trusted independently.

### Proof of Concept
1. Attacker registers/owns GitHub org `attacker-org`, installs the Shipit GitHub App on it, and thus knows `attacker-org`'s `webhook_secret` from their own app settings.
2. Victim org `victim-org/victim-repo` is already tracked as a `Stack` on the same shared Shipit instance.
3. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org's webhook_secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `attacker-org`, loads `attacker-org`'s secret, and the HMAC checks out → request proceeds.
6. `PushHandler` resolves `stacks` via `repository.full_name` = `victim-org/victim-repo`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack, despite the attacker having no relationship to `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
