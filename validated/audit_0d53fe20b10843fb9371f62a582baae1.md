### Title
Coarse (filePath, category) dedup key in commit-review lets an attacker suppress warnings for a genuinely new, dangerous vulnerability in an already-flagged file - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
`handle_commit_review_posttooluse` records and deduplicates LLM findings using only the tuple `(filePath, category)`, explicitly ignoring `vulnerableCode` content [1](#0-0) . Because an attacker fully controls the diff content (and therefore the file touched and the likely LLM-assigned category) across a sequence of ordinary commits, a first, low-value finding in a file can pre-populate `previous_findings` for `(file, category)`, so a later, genuinely dangerous vulnerability introduced into the same file under the same coarse category is treated as "already known" and silently dropped from the commit-review output.

### Finding Description
`handle_commit_review_posttooluse` runs analysis via `analyze_code_security`/agentic review, then narrows the LLM's `vulns` to `new_vulns` using `_dedup_against_state`, which only filters a narrow race-condition delta [2](#0-1) . Separately, and more importantly, the persistent cross-commit dedup state (`previous_findings`, shared with the Stop hook) is keyed solely by `(filePath, category)`:
```
existing = [...]
seen = {(f.get("filePath", ""), f.get("category", "")) for f in existing}
for f in finding_snapshots:
    key = (f["filePath"], f["category"])
    if key not in seen:
        ...
``` [3](#0-2) 

The comment in the code acknowledges the tradeoff explicitly: `vulnerableCode` is intentionally excluded from the key because diff-context lines drift between LLM calls, so matching by content "under-dedupes" [4](#0-3) . However, this means the key space is coarse enough that a second, unrelated (and more severe) vulnerability of the same LLM-assigned `category` in the same `filePath` will match an already-recorded key and be considered "already known," never being appended as a *new* finding to trigger stderr/exit(2) rewake behavior at `sys.exit(2)` [5](#0-4) .

Exploit flow:
1. Attacker (an unprivileged contributor operating the normal edit/commit workflow that Claude Code drives) commits a file with a trivial/benign finding that the LLM classifies under some category, e.g. `"Injection"` on `foo.py`. This gets recorded into `previous_findings` as `(foo.py, "Injection")` via `handle_commit_review_posttooluse`.
2. In the same or a later commit touching the same file, the attacker introduces a genuinely dangerous new vulnerability (e.g., a critical SQL injection or command injection) that the reviewer also classifies as `"Injection"` for `foo.py`.
3. When `handle_commit_review_posttooluse` fires again, `vulns` returned from `analyze_code_security`/agentic review may contain this new critical finding, but `_dedup_against_state` only removes items in the concurrent-write race delta (not the persisted state), so it should normally survive that filter [6](#0-5) . But once it does survive, when it is merged into `previous_findings` at record time, if the key `(foo.py, "Injection")` is already `seen`, the new finding is not distinguished from the old — but more critically, this same shared `previous_findings` state is consumed by other surfaces (Stop hook, push-sweep) as the "already known, don't re-flag" set fed into `analyze_code_security(..., previous_findings=...)`, which explicitly instructs the LLM to only re-flag `previous_findings` entries "if the attempted fix is incomplete" [7](#0-6) . Since the prompt only carries category-level context (not the specific vulnerable code), the LLM reviewing a *later* Bash call (e.g., `git push`) is told the file/category pair was already surfaced and may decline to re-flag the new, unrelated issue, or the local key-based bookkeeping treats it as duplicate before display.
4. The net effect across retries/amends/pushes is that a dangerous, novel vulnerability sharing a file and coarse category with an earlier, already-acknowledged (or trivial) finding can be silently absorbed into the "already known" set and never surfaces via stderr/exit(2), defeating the intended invariant that dangerous edits/commands remain reviewable and blockable across the commit/amend/push lifecycle.

I could not fully verify the exact list of category strings the LLM prompt uses (the `analyze_code_security` prompt-construction and category taxonomy in `llm.py` was not fully retrievable via search in this pass), nor could I locate and confirm the Stop-hook's own dedup function (`_record_fire`) to verify whether it applies the identical `(filePath, category)` keying and is equally exploitable via the same shared `previous_findings` state. These would need direct file inspection to fully confirm severity and to rule out an additional severity- or vulnerableCode-based safety net elsewhere in the pipeline (e.g., `_format_vulns_summary`, `_format_vulns_guidance`, or the severity filter mentioned in comments at lines ~1268-1277).

### Impact Explanation
If confirmed, this allows a security-control bypass: a dangerous code change (e.g., new injection, authz bypass, secret leak) can be silently excluded from the commit-review/Stop/push-sweep warning and rewake mechanism simply because an earlier, unrelated or intentionally-planted finding of the same broad category exists for the same file. This routes around the review/blocking boundary that the plugin is designed to enforce on every dangerous commit, matching "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries."

### Likelihood Explanation
Preconditions are low: the attacker only needs the ability to author two ordinary commits into the same file where the second introduces a more severe issue that an LLM reviewer classifies under the same coarse category as a prior, already-recorded finding in that file. This is plausible given that categories are broad LLM-assigned labels, and repeatable because the state persists per-session and is explicitly designed to accumulate across commits/amends/pushes. However, actual triggerability depends on the LLM's category-assignment behavior being coarse/predictable enough for an attacker to engineer the collision reliably, which is probabilistic rather than deterministic, and I was unable to confirm exact category granularity from the available context.

### Recommendation
Strengthen the dedup key so that distinct vulnerable code/root causes in the same file and category are not conflated — e.g., include a stable normalized hash of the vulnerable code's semantic location (function name, line-range bucket, or a fuzzy/normalized content hash) in the key rather than relying purely on `(filePath, category)`. At minimum, ensure the LLM prompt in `analyze_code_security`/`_dedup_against_state` never treats "already known" file+category entries as a reason to suppress newly-introduced, structurally different vulnerabilities, and require content-similarity confirmation before deduping across commits/amends/pushes.

```python
def _dedup_against_state(session_id: str, vulns: List[Dict[str, Any]],
                         prompted: set) -> Tuple[List[Dict[str, Any]], int]:
    """Drop vulns that a CONCURRENT asyncRewake hook wrote to
    previous_findings while this hook's LLM was running.

    `prompted` is the (filePath, category) set the LLM was already told about
    via the prev_section prompt block. The LLM is instructed to only re-flag
    those if the attempted fix is incomplete, so a re-flag of a `prompted`
    entry is an intentional "fix didn't work" verdict and MUST pass through.
    We therefore re-read state now and only filter the race delta —
    (seen_now − prompted) — i.e. findings the LLM was never told about
    because they were written mid-review by the other hook.
    Returns (surviving_vulns, n_dropped).
    """
    if not vulns:
        return vulns, 0
    fresh = with_locked_state(
        session_id, lambda s: list(s.get("previous_findings", []))
    ) or []
    race_delta = _finding_keys(fresh) - prompted
    kept = [v for v in vulns
            if (v.get("filePath", ""), v.get("category", "")) not in race_delta]
    return kept, len(vulns) - len(kept)
```
