### Title
Webhook signature verification selects the signing organization from an unverified payload field decoupled from the repository field that handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to validate the HMAC against using `repository_owner`, a value read straight out of the still-unauthenticated request body. The handler that subsequently executes (`PushHandler`, `ClosedHandler`, etc.) instead acts on `payload.dig('repository', 'full_name')` — a different field in the same attacker-controlled JSON. These two fields are never bound to each other, so the "organization that authenticated" and "the repository that is written" can be made to diverge.

### Finding Description
`verify_signature` computes the signing org from the raw payload before any authenticity check occurs: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) — both fully attacker-supplied since the JSON body is parsed before signature verification. `Shipit.github(organization: repository_owner)` is then used purely to look up which `webhook_secret` to check against, and `verify_webhook_signature` trivially returns `true` when no secret is configured for that org: [3](#0-2) 

Once `verify_signature` passes, `create` re-parses the same raw body and dispatches it to handlers unmodified: [4](#0-3) 

Handlers, however, resolve the target repository/stack from a *different* field of the same payload — `repository.full_name` — with no re-check that it belongs to the organization that was used for signature verification: [5](#0-4) [6](#0-5) [7](#0-6) 

This is structurally identical to the Curve-pool analog category "an organization that authenticated versus the repository that is written": the equality the code implicitly assumes — `organization used to pick the verification secret == organization owning repository.full_name that gets acted on` — is never enforced. In a Shipit deployment configured for multiple GitHub organizations, if any one configured organization has no `webhook_secret` set (an explicitly supported, non-error configuration per `@webhook_secret = @config[:webhook_secret].presence`), an unprivileged attacker can set `repository.owner.login`/`organization.login` to that unsecured org while pointing `repository.full_name` at a stack belonging to a different, properly-secured organization. Signature verification passes trivially (no secret to check), yet the handler still acts on the secured org's repository.

### Impact Explanation
`PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack whose branch matches the forged `ref`, using an attacker-chosen `after` SHA: [6](#0-5) 
This lets an attacker who never possesses the target organization's real `webhook_secret` inject a forged push event that drives the stack's head-tracking and downstream sync/deploy pipeline for a repository they do not control the webhook for — matching the "unauthorized deploy" impact bucket. `ClosedHandler` similarly lets the attacker archive a review stack belonging to the secured org without ever satisfying that org's signature check.

### Likelihood Explanation
Requires only: (a) the Shipit instance being configured for more than one GitHub organization, and (b) at least one of those configured organizations having no `webhook_secret` set — a state the code explicitly tolerates rather than rejects (`return true unless webhook_secret`). No credentials, sessions, or GitHub App keys are needed; the attacker only needs to POST a crafted JSON body to the public `/webhooks` endpoint.

### Recommendation
Bind the two fields together: derive the organization used for signature verification from the same repository record that the handler will subsequently act on (e.g., verify against `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner`), or refuse verification entirely when the resolved organization has no configured `webhook_secret`, rather than treating an absent secret as an implicit pass.

### Proof of Concept
1. Configure Shipit with two organizations: `secured-org` (has `webhook_secret`) and `open-org` (no `webhook_secret` configured).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "full_name": "secured-org/target-repo",
    "owner": { "login": "open-org" }
  }
}
```
3. `verify_signature` computes `repository_owner = "open-org"`, loads `Shipit.github(organization: "open-org")`, and `verify_webhook_signature` returns `true` because that org has no secret — the request is accepted despite never being signed by `secured-org`.
4. `create` dispatches the same payload to `PushHandler`, which resolves the stack via `repository.full_name = "secured-org/target-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker chosen sha>")` on that stack, affecting a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
