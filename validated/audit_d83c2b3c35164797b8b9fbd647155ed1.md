### Title
Webhook signature verification is scoped to the payload's claimed organization while event processing trusts the payload's `repository.full_name`, letting a signature valid for one configured GitHub org authorize writes against any stack in the Shipit instance - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the `X-Hub-Signature` against based on `repository_owner`, a field read from the same untrusted JSON body (`repository.owner.login` or `organization.login`). Once verification "succeeds" (including the case where that organization has no `webhook_secret` configured, in which case `verify_webhook_signature` unconditionally returns `true`), the event is dispatched to handlers that resolve the target stack/repository/commit from a *different, unrelated* field of the same payload: `repository.full_name`. Nothing ties the organization whose secret validated the signature to the repository that the handler subsequently mutates.

### Finding Description
The verification step: [1](#0-0) [2](#0-1) 

selects the org config via `Shipit.github(organization: repository_owner)`, and the underlying check is: [3](#0-2) 

Critically, `return true unless webhook_secret` means that for any GitHub organization configured in `secrets.github` **without** a `webhook_secret` set (documented as optional: "Webhook secret (optional)"), signature verification is bypassed entirely regardless of the actual `X-Hub-Signature` header value.

Meanwhile, the actual write target is picked independently, from `repository.full_name` in the very same JSON body, by the base `Handler` and every concrete handler: [4](#0-3) [5](#0-4) [6](#0-5) 

Nothing in `StatusHandler#process`, `PushHandler#process`, or `Handler#stacks`/`#repository_name` restricts the targeted repository to the organization identified by `repository_owner` (the field consulted for signature verification). An attacker who can produce a payload whose `repository.owner.login` (or `organization.login`) names any org configured in this Shipit instance's `secrets.github` with no `webhook_secret` set, but whose `repository.full_name` points at a different, secret-protected organization's repository, will have that payload accepted and processed against the victim organization's stacks.

This is the same class of bug as the external report: a value is trusted/acted upon (`repository.full_name`, used to select which record is mutated) that is never actually bound to what was verified (the signature check binds only to `repository_owner`, and in the no-secret-org case, to nothing at all).

### Impact Explanation
Depending on which webhook event/handler is exercised, this can produce a High-severity unauthenticated write against arbitrary stacks:
- `StatusHandler` lets an attacker post arbitrary commit statuses for any commit SHA already known to Shipit (`commit.create_status_from_github!`), which can be used to fabricate a passing CI status on a targeted stack's commit, potentially unblocking automatic/continuous deployment or the merge queue (`MergeRequest#all_status_checks_passed?` relies on the `Status` records) - i.e., contributing to an unauthorized deploy or merge.
- `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` for any stack matching the forged `repository.full_name`/branch, letting an attacker force a resync/job queue against a stack it does not control.
- `MembershipHandler` allows arbitrary team membership manipulation (`team.add_member`/`team.members.delete`) tied to an `organization.login` value that also isn't validated against the org that actually authenticated the request.

This satisfies "escalation into `Shipit.github_teams` authorization" and "an unauthorized deploy, rollback or merge" impact categories, without requiring any Shipit session, ApiClient token, or knowledge of any *other* organization's `webhook_secret`.

### Likelihood Explanation
Requires only that the Shipit instance is configured with the documented multi-organization GitHub App schema (`secrets.github` keyed by org, per `lib/shipit.rb#github_app_config`/`#github_organizations`) and that at least one configured organization has no `webhook_secret` set - an explicitly supported, documented ("optional") configuration, not a deployment error out of scope. No secrets, sessions, or GitHub write access are required to reach `POST /webhooks`, which is unauthenticated by design (`WebhooksController` skips CSRF and has no other auth). This is a realistic misconfiguration surface for Shipit installations onboarding a new org before wiring up its webhook secret, or intentionally leaving an internal/low-risk org's secret blank.

### Recommendation
Bind the value used for signature verification to the value used for locating the target stack: derive `repository_owner`/organization strictly from the `repository.full_name`/`repository.owner.login` that the handlers will actually act on (single source of truth), and refuse to process the event if that derived organization has no `webhook_secret` configured (treat missing secret as "deny", not "allow"), rather than defaulting to `true` in `GitHubApp#verify_webhook_signature`. At minimum, remove the `return true unless webhook_secret` short-circuit for multi-org deployments and require every configured organization to have a webhook secret, or explicitly reject payloads for orgs lacking one.

### Proof of Concept
Preconditions: Shipit configured with multi-org GitHub Apps, e.g. `secrets.github = { "org-a" => { webhook_secret: nil, ... }, "org-b" => { webhook_secret: "s3cret", ... } }`, and Shipit hosts a stack for `org-b/victim-repo`.

1. Attacker crafts a `status` (or `push`) webhook JSON body:
```json
{
  "sha": "<known deployed commit sha on org-b/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "org-b/victim-repo", "owner": { "login": "org-a" } }
}
```
2. Attacker sends `POST /webhooks` with `X-Github-Event: status` and any (or no) `X-Hub-Signature` header.
3. `WebhooksController#repository_owner` returns `"org-a"` (from `repository.owner.login`); `verify_webhook_signature` is invoked against `org-a`'s config, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally - the request passes verification.
4. `StatusHandler#process` is invoked with the full payload and looks up `Commit.where(sha: params.sha)` - resolving to the commit on `org-b/victim-repo`, whose organization (`org-b`) actually has a secret configured and was never involved in the verification - and creates a forged successful status on it, independent of `org-a`.
5. If `org-b/victim-repo`'s stack has continuous deployment or a merge queue relying on that status context, the forged status can unblock an unauthorized deploy or merge.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
