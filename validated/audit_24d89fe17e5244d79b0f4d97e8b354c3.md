### Title
Operator-precedence bug in `ReopenedHandler#unarchive?` allows unauthorized review-stack provisioning/unarchival on repos with `review_stacks_enabled == false` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` has the same operator-precedence defect described for `lib/shipit/review_stack_commands.rb`: `&&` binds tighter than `||`, so `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?` is only one disjunct of three, and the last two disjuncts never check `review_stacks_enabled` at all. A repository with `review_stacks_enabled == false` but `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`) still evaluates `unarchive?` to `true` on a `reopened` webhook, causing `ReviewStackAdapter#unarchive!` to run and, since no stack has ever been provisioned (`stack.blank?`), fall into `create!`, which builds a new `ReviewStack` and enqueues it via `Shipit::ReviewStackProvisioningQueue.add`.

### Finding Description
The intended binding is: *a ref approved to run `shipit.yml` steps via `Command#start` must be approved because `repository.review_stacks_enabled == true`*. The code instead computes:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Due to Ruby precedence this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label) || (prevent_with_label? && !label)`. The last two disjuncts are independent of `review_stacks_enabled`. Compare with the sibling `LabeledHandler`, which correctly ANDs `repository.review_stacks_enabled` at the top level, outside of `archive?`/`unarchive?`: `params.action == "labeled" && pull_request_state == "open" && repository.review_stacks_enabled && (archive? || unarchive?)` [2](#0-1)  — this shows the correct pattern that `ReopenedHandler` and `OpenedHandler` fail to replicate.

`respond_to_pull_request_reopened?` gates only on `params.action == "reopened" && unarchive?` [3](#0-2) , so once `unarchive?` mis-evaluates to `true`, `process` calls `stack.unarchive!` [4](#0-3) .

In `ReviewStackAdapter#unarchive!`, since the PR was never provisioned before (attacker's own PR, freshly opened and closed/reopened), `scope.find_by(environment:)` returns nil, so `stack.blank?` is true and the code calls `create!` [5](#0-4) . `create!` builds a `ReviewStack` from `params.pull_request.head.ref` as the deploy branch and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [6](#0-5) .

Attacker's exact request: any GitHub user opens a PR against a target repository configured with `review_stacks_enabled: false, provisioning_behavior: allow_with_label` (or `prevent_with_label`), applies (or omits) the provisioning label they control on their own PR, closes the PR, then reopens it — a `pull_request` webhook with `action: "reopened"` is emitted automatically by GitHub for any PR state transition the PR author performs, requiring no repository write access beyond opening/labeling/closing/reopening their own PR.

Existing guards do not stop this: webhook signature verification only authenticates that GitHub sent the payload, not that the *content* satisfies the intended stack-provisioning policy; `ExplicitParameters` validates payload shape, not the boolean logic; no `review_stacks_enabled` check gates the label-based branches, unlike the correctly-written `LabeledHandler`.

### Impact Explanation
This causes creation and enqueuing for provisioning of a `ReviewStack` for a repository whose administrator explicitly disabled review stacks (`review_stacks_enabled == false`). The new stack's `branch` is fully attacker-controlled (`params.pull_request.head.ref`, the attacker's own fork branch) [7](#0-6) . If that branch's `shipit.yml` defines deployment steps, they will eventually be picked up and executed as shell commands on the deploy host via the stack's task pipeline (`Command#start`/`PTY.spawn` in `lib/shipit/command.rb`), matching the Critical-severity "RCE on the deploy host" / "unauthorized deploy" category. This is repeatable against any repository with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (both are non-default but valid, operator-settable configurations), and the attack requires only actions on the attacker's own PR.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`. This is a plausible admin configuration (e.g., an operator disabling review stacks generally while leaving a stale/opt-in label policy set, or toggling the enabled flag off without resetting the behavior enum). Given that configuration, the attacker's cost is trivial: open, label/unlabel, close, and reopen a PR they control — all standard, unprivileged GitHub actions. No secrets, tokens, or elevated roles are needed. The existing test suite (`test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`) never exercises `review_stacks_enabled: false` combined with `allow_with_label`/`prevent_with_label`, so this gap is not caught by current tests (`configure_provisioning_behavior` defaults `provisioning_enabled: true` in every test) [8](#0-7) .

### Recommendation
Fix `unarchive?` (and the analogous `provision?` in `OpenedHandler`) to require `review_stacks_enabled` across all branches, e.g.:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same parenthesization fix to `OpenedHandler#provision?`, which contains the identical defect.

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`:
```ruby
test "does not unarchive or provision stacks for repos with review_stacks_enabled=false, even with allow_with_label + label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::ReviewStack.count } do
    Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process
  end
end
```
Binding under test: LHS = `repository.review_stacks_enabled` (`false`), RHS = whether `ReviewStackProvisioningQueue.add`/`ReviewStack.create!` is invoked. Currently these diverge (stack is created despite `review_stacks_enabled == false`), which the assertion `assert_no_difference` will catch as a failure against the current code, proving the vulnerability.
