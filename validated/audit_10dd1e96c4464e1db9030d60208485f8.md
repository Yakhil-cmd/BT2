### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, while the repository actually written to is looked up via the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a structural analog of the reported bug class: a field that is trusted and acted upon (`repository.full_name`, used to select which `Stack`/`Repository` gets synced) is never bound to the field that was actually authenticated by the HMAC signature check (`repository.owner.login`, used only to select *which webhook secret* to verify against). Just like the Move contract accepted a `_value` parameter but never used it for the recorded value, `WebhooksController` accepts a `repository.owner.login` for authentication purposes but never cross-checks it against the `repository.full_name` that downstream handlers actually operate on.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App / webhook secret to validate the HMAC signature against using `repository_owner`, which is read straight out of the untrusted JSON body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once the signature is confirmed valid for that organization's secret, `create` dispatches the entire raw payload to handlers: [3](#0-2) 

Handlers, however, never use `repository_owner`. Instead they resolve the target `Repository`/`Stack` from a **different** field of the same payload, `repository.full_name`: [4](#0-3) [5](#0-4) 

Shipit explicitly supports hosting multiple GitHub organizations behind one instance, each with its own `webhook_secret`: [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the acted-upon repository) live in the same attacker-controlled JSON body and are never cross-validated, the "organization authenticated" and "repository written" values are not bound to each other. An entity that legitimately controls a webhook for Organization A can send a request whose `repository.owner.login` is `"OrgA"` (so it authenticates fine against `OrgA`'s secret) but whose `repository.full_name` is `"OrgB/some-repo"`. `verify_signature` passes because it only checked that the raw body is HMAC-signed by `OrgA`'s secret; it never checked that the body's content is actually about `OrgA`. The `PushHandler` then resolves `Repository.from_github_repo_name("OrgB/some-repo")` and, for every matching, non-archived stack on that branch, enqueues `stack.sync_github(expected_head_sha: params.after)` — a job belonging to `OrgB`, not `OrgA`.

`GithubSyncJob` (enqueued by `sync_github`) fetches commits using the target stack's own configured GitHub API/credentials and appends them to the stack: [8](#0-7) 

If the target stack has `continuous_deployment` enabled, appending new commits via a forced/faked sync can trigger continuous delivery, i.e., an unauthorized deploy on a stack belonging to an organization the attacker does not control.

### Impact Explanation
This breaks the binding "organization that authenticated versus the repository that is written," which is explicitly called out as a valid analog class. The practical impact is a cross-tenant/cross-organization action: an attacker who only holds a valid webhook secret for Org A (their own legitimately configured organization) can cause writes/syncs and potentially unauthorized deploys against stacks belonging to Org B, whose secret they never had. This matches the Critical bar for "cross-repository writes" / "an unauthorized deploy."

### Likelihood Explanation
The likelihood of this exact analog is **moderate but non-trivial to weaponize under the stated scope**: exploitation genuinely requires possession of a valid webhook secret for at least one organization configured in the Shipit instance (multi-tenant deployment), which the rules generally treat as an unprivileged-attacker-reachable boundary only insofar as the attacker's own organization's webhook is "unprivileged" relative to *other* organizations' stacks. In a single-organization deployment (the common case, and what most `secrets.yml` examples show), `repository_owner` and `repository.full_name`'s owner will always match the same single configured secret, so there's nothing to desynchronize and the bug is not exploitable. The vulnerability is only live in the documented multi-org configuration (`docs/setup.md`), which is an explicitly supported feature of this engine, not a misconfiguration.

### Recommendation
In `WebhooksController#create`/`#verify_signature`, cross-validate that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, or have handlers resolve/enforce the repository strictly from the same field used to select the verifying webhook secret, so the two are never allowed to diverge within a single request.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org config), and a stack for `OrgB/some-repo` with `continuous_deployment: true`.
2. As an entity holding only `OrgA`'s `webhook_secret` (e.g., someone with admin on an `OrgA` repo/webhook config), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-or-real-sha>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/some-repo"
     }
   }
   ```
3. Sign the raw body with `OrgA`'s `webhook_secret` (`sha1=` HMAC) and send it as `X-Hub-Signature` to `POST /github/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and verifies successfully against `OrgA`'s secret.
5. `PushHandler#process` resolves the target via `payload.dig('repository', 'full_name')` = `"OrgB/some-repo"`, and enqueues `stack.sync_github` for `OrgB`'s stack, triggering a sync (and potentially a continuous deploy) the attacker had no credentials to authorize directly.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
