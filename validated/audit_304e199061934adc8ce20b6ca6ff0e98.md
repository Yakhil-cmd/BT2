### Title
`Api::CCMenuController#stack` bypasses the `ApiClient#stack_id` scope, allowing a token minted for stack A to read any stack B's CCMenu status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` scopes stack lookups to `current_api_client.stack_id` via its `stacks`/`stack` helpers, but `Api::CCMenuController` overrides `stack` with its own unscoped implementation that calls `Stack.from_param!` directly on all stacks. Since permission checking (`check_permissions!`) only validates the permission name (`read:stack`) and never compares `client.stack_id` to the resolved stack, a stack-A-scoped token can be replayed against `/api/stacks/:B/ccmenu.xml?token=...` to read stack B's deploy status.

### Finding Description
The broken binding: `token's ApiClient#stack_id == stack_id param resolved` is expected but never enforced for `CCMenuController`.

`ApiClient.authenticate(token)` only decrypts/verifies the signed id and does `find_by(id: ...)` with no stack comparison: [1](#0-0) .

`Api::BaseController` defines the intended scoping mechanism: `stacks` restricts to `current_api_client.stack_id` when present, and `stack` resolves `params[:stack_id]` against that scoped relation: [2](#0-1) .

However, `Api::CCMenuController` redefines `stack` to bypass this scope entirely, resolving directly against all stacks: [3](#0-2) . It also overrides `authenticate_api_client` to accept the token via `params[:token]` (query string, as intended for CCMenu clients) but this override only changes how the token is read, not the stack scoping: [4](#0-3) .

`require_permission :read, :stack` only checks that the client's `permissions` array contains `"read:stack"` via `check_permissions!`, with no comparison to `stack_id`: [5](#0-4) .

Attack: an attacker who has obtained (via legitimate sharing, e.g. a CI dashboard) a CCMenu URL like `/api/stacks/owner-a/repo-a/branch/ccmenu.xml?token=<A-scoped-token>` can instead request `/api/stacks/owner-b/repo-b/branch/ccmenu.xml?token=<A-scoped-token>`. Because `CCMenuController#stack` uses `Stack.from_param!` unscoped, it resolves stack B regardless of the token's `stack_id`, and `check_permissions!(:read, :stack)` passes since the permission name matches, disclosing stack B's build/deploy status.

This diverges from the general API base behavior (`stacks`/`stack` in `BaseController`) precisely because `CCMenuController` reimplements `stack` without the scope guard, indicating the omission is specific to this controller and not a global authorization gap.

### Impact Explanation
An attacker with any legitimately-obtained CCMenu token (scoped to one stack, e.g. a public read-only token shared for CI dashboards) can enumerate and read the CCMenu status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state) of any other stack in the same Shipit deployment, including private/internal repositories' stacks, by simply changing the `stack_id` path segment. This is an unauthenticated-for-that-resource read of stack state across tenants, matching the "unauthorized read of stack state" High-severity category. It is fully repeatable against arbitrary stacks known to the attacker (stack identifiers are typically `owner/repo/branch`, often guessable/public on GitHub).

### Likelihood Explanation
Preconditions: attacker needs one valid `ApiClient` token with `read:stack` permission scoped to any stack (these tokens are routinely embedded in plaintext CCMenu URLs shared with CI dashboard tools, so leakage/possession is a normal and expected occurrence, not a secret compromise). No Shipit secrets, session, or GitHub credentials are required. The attacker only needs to know or guess the target stack's `owner/repo/branch` identifier used in the URL. This makes exploitation cheap and repeatable.

### Recommendation
In `Api::CCMenuController`, remove the local `stack` override and use the inherited scoped `stack`/`stacks` helpers from `Api::BaseController` (or explicitly verify `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id` before rendering).

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to stack A cannot read stack B's ccmenu status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

  scoped_client = ApiClient.create!(
    creator: @user, name: 'scoped', stack: stack_a, permissions: ['read:stack']
  )

  # Binding under test: token's ApiClient#stack_id == stack_id param resolved
  assert_equal stack_a.id, scoped_client.stack_id
  refute_equal stack_a.id, stack_b.id

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # Expected (secure) behavior: request should be rejected/forbidden because
  # scoped_client.stack_id (stack_a.id) != resolved stack (stack_b.id)
  assert_response :forbidden # currently fails: controller returns 200 with stack_b's data
end
```
This demonstrates that `check_permissions!(:read, :stack)` passes (permission name matches) while the served record (`stack_b`) is unrelated to `scoped_client.stack_id` (`stack_a.id`), confirming the cross-stack information leak in `Api::CCMenuController#stack`.
