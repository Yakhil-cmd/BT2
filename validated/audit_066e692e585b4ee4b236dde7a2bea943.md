### Title
Anyone can lower a victim's cached liquidation threshold and raise their liquidation bonus via a permissionless dust `supply` - (contracts/controller/src/positions/supply.rs)

### Summary
`supply` is permissionless for third parties as long as they only top up a hub asset the target account already holds a supply position in. Every supply leg unconditionally runs `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, which restamps the position's `liquidation_threshold`, `liquidation_bonus` and `liquidation_fees` to the current listing config. When governance has tightened a listing (lower liquidation threshold, higher bonus), any unprivileged address can force-apply the worse parameters onto a victim's collateral with a dust deposit, degrading the victim's health factor down to the 1.05 gate without the victim's consent — the same bug class as "anyone can lower another user's voting power."

### Finding Description
`process_supply` in `contracts/controller/src/positions/supply.rs:40-74` only requires `caller` auth. The third-party restriction `require_third_party_existing_supply` (lines 78-97) merely checks that each supplied asset already exists in the victim's `supply_positions`; it does not restrict amounts, so a single smallest-unit deposit qualifies.

Each supply leg goes through `merge_supply_leg` (lines 275-324), which calls `refresh_supply_risk_params(..., RiskRefreshScope::FullTuple)` at line 288. In `contracts/controller/src/risk/params.rs:25-40`, `FullTuple` invokes `apply_gated_liquidation_params` (lines 68-93), which overwrites `position.liquidation_threshold`, `position.liquidation_bonus` and `position.liquidation_fees` with `effective_config` values. The only protection is `clears_min_hf` (lines 103-119): if the change "favors the liquidator" and the account has debt, the restamp is silently skipped unless the resulting HF is ≥ `THRESHOLD_UPDATE_MIN_HF_RAW` (1.05). It does **not** revert and does **not** require the account owner's consent — the supply proceeds and the downgrade is applied.

The dedicated keeper path `update_account_threshold` (`params.rs:124-144`, reachable via `controller::update_account_threshold` in `lib.rs:386`) is equally permissionless and performs the same restamp.

Attack sequence:
1. Governance timelocks a listing update that lowers `liquidation_threshold` (and/or raises `liquidation_bonus`) for an asset — a routine, legitimate parameter change (the `liqvid-listing-params` runbook documents exactly such a 6000→5300 LT cut).
2. A victim account holding that asset as collateral keeps the old, more favorable cached tuple indefinitely because restamps are lazy (INV design: params refresh on touch).
3. Any attacker calls `supply(caller, victim_account_id, victim_spoke_id, [(asset, dust)])`. Since the victim already holds that supply position, `require_third_party_existing_supply` passes.
4. `merge_supply_leg` restamps the victim's tuple to the new worse values, provided the victim's HF stays ≥ 1.05 under the new LT — i.e., the attacker can drive the victim's HF arbitrarily close to 1.05 from wherever it was.

### Impact Explanation
The victim's liquidation safety buffer is destroyed by a stranger for the cost of a dust deposit. An account that would have remained safely above liquidation under its grandfathered threshold becomes liquidatable after a much smaller price move (or becomes liquidatable to interest accrual sooner), and a raised `liquidation_bonus`/`liquidation_fees` makes any subsequent liquidation strictly more expensive to the victim. This is a forced, irreversible degradation of another user's financial position by an unprivileged address, enabling indirect theft via earlier/more profitable liquidation — the accepted impact category "theft of user funds" via loss of grandfathered liquidation terms.

### Likelihood Explanation
Likelihood is conditional on a risk-parameter tightening ever occurring, which is a normal and documented governance operation for this protocol (see `docs/reference/runbooks/liqvid-listing-params.md`, which explicitly walks through lowering LT from 6000 to 5300). Every listed market eventually gets retuned; every borrower with a stale tuple in that market is a target. The attack requires no capital beyond a dust deposit and gas, and can be executed atomically in the same transaction as a liquidation cascade attempt once price moves below the new-threshold liquidation point but above the old one.

### Recommendation
Gate the risk-parameter restamp on `merge_supply_leg` for third-party callers: only apply `RiskRefreshScope::FullTuple` when `caller` is the account owner or an active delegate; for foreign suppliers use `RiskRefreshScope::LtvOnly` or skip the tuple refresh entirely, mirroring how `liquidation`-mode withdrawals already skip restamping via `leg_may_restamp_risk_params`. Similarly, `update_account_threshold` should either require owner/delegate auth per `account_id`, or apply `favors_liquidator` restamps only when invoked by the account owner, so a stranger can never choose *when* a victim absorbs tightened liquidation terms.

### Proof of Concept
1. Account A (victim) supplies `X` and borrows, holding cached `liquidation_threshold = 6000`, `liquidation_bonus = B0`; HF = 1.20.
2. Governance executes `edit_asset_in_spoke` setting `liquidation_threshold = 5300`, `liquidation_bonus = B1 > B0` (as in the runbook).
3. Attacker (any address) calls `supply(caller=attacker, account_id=A, spoke_id, assets=[(X, 1)])`. `require_third_party_existing_supply` passes because A already supplies `X`.
4. `merge_supply_leg` → `refresh_supply_risk_params(FullTuple)` → `apply_gated_liquidation_params`: `favors_liquidator` is true; `clears_min_hf` checks HF under LT 5300 = 1.06 ≥ 1.05 → restamp applied. A now stores LT 5300, bonus B1.
5. A's HF drops from 1.20 to ~1.06 without A ever signing a transaction; A is now liquidatable after a ~6% price/interest move instead of ~17%, and pays bonus B1 on liquidation.
