### Title
Attacker-controlled PR label overwrites `PATH` env var reaching `PTY.spawn` - (File: app/models/shipit/review_stack.rb)

### Summary
`Shipit::ReviewStack#env` merges every PR label name (uppercased) as an environment variable key with the value `"true"` into the stack's environment with no filtering. Because this stack env flows unfiltered into `TaskCommands#env` and then into `Command#unbundled_env`, which merges `@env.stringify_keys` last, any label named case-insensitively `path` overwrites the `PATH` variable used by `PTY.spawn` to resolve commands.

### Finding Description
The broken binding: the set of keys that reach `Command#unbundled_env`'s final `@env` merge is claimed to equal the set defined by `deploy_spec.machine_env`/`VariableDefinition`, but in fact `ReviewStack#env`'s label-derived keys reach that merge with zero relation to those whitelists.

Code path:
- `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` on top of `super` (i.e., `Stack#env`), with no key allow-list. [1](#0-0) 
- `pull_request.labels` is attacker-controlled: `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` directly from the webhook payload with no name filtering. [2](#0-1) 
- `TaskCommands#env` merges `@stack.env` (which for a `ReviewStack` includes the label-derived keys) *before* `deploy_spec.machine_env` and `@task.env`: `super.merge(@stack.env).merge({...}).merge(deploy_spec.machine_env).merge(@task.env)`. [3](#0-2) 
- If the repo's `deploy_spec` doesn't define a `machine.environment.PATH` entry (the normal case), nothing overrides the label-injected `PATH` key at this stage.
- `Command#unbundled_env` builds `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)` — `@env` is the final `TaskCommands#env` hash, applied **last**, so a `PATH` key surviving from the label overwrites Shipit's constructed `PATH`. [4](#0-3) 
- This env is what's passed to `PTY.spawn(unbundled_env, *interpolated_arguments, ...)`. [5](#0-4) 

Attacker action: open/label a PR against a repo with a provisioned `ReviewStack`, adding a label named `path` (or `PATH`, case-insensitive) via GitHub UI, which GitHub relays to Shipit's `POST /webhooks` as a `pull_request` event with `action: labeled`. No Shipit credentials are required — this is a standard GitHub webhook signed by GitHub itself in response to the attacker's own PR/label action on a repo they can label (their own fork or, if they have write access to a monitored repo, that repo). `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticates that the payload came from GitHub for that repository; they do not filter which label names GitHub is allowed to relay, so they don't stop this. `ExplicitParameters` in `LabelCapturingHandler` validates the payload shape (`requires :labels, Array do requires :name, String end`) but not label name content. [6](#0-5) 

Filtering that exists elsewhere but doesn't apply here: `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` use `EnvironmentVariables#permit` against `deploy_variables`, but these are only applied to `@task.env` (deploy-request-time envs submitted by a human deployer, e.g. via `RollbacksController`), not to `Stack#env`/`ReviewStack#env`. [7](#0-6) 

### Impact Explanation
An attacker who can label their own PR against a repo with an active `ReviewStack` can force the deploy host's shell command resolution (`PTY.spawn`) to use `PATH=true` for every subsequent deploy/task/step of that review stack, causing all step commands (git, bundler, rake, etc.) to fail to resolve ("command not found"), and if the attacker can also influence any earlier-resolved directory literally named `true` on disk (unlikely but not provably impossible depending on host layout), potentially achieve command hijacking. At minimum this is a reliable, repeatable denial of a review stack's task execution triggered purely from an unprivileged GitHub PR interaction, and it demonstrates that arbitrary attacker-chosen label text becomes an environment variable available to the shell process spawned on the deploy host — the binding between "keys reaching `PTY.spawn`'s env" and "keys sanctioned by `deploy_spec`" is broken. This matches the Critical category ("RCE on the deploy host via `Command`/`PTY.spawn`") in spirit — the exploit path reaches the exact env-merge site feeding `PTY.spawn`, though full arbitrary binary execution depends on additional host-specific conditions (a writable/attacker-controlled directory named `true` earlier in resolution, or other label names colliding with security-relevant env vars like `LD_PRELOAD`, `BUNDLE_GEMFILE`, `GIT_SSH_COMMAND`, etc. — labels are attacker's free-text choice, so this is not limited to `PATH`).

### Likelihood Explanation
Preconditions: repository must have an active `ReviewStack` (i.e., review-stack provisioning enabled for that repo) and `deploy_spec` must not define `machine.environment.PATH` (or the specific env var name matching the chosen label) to override the injected value. Attacker cost is trivial — open a PR against such a repo and add any label to it; no Shipit credentials, GitHub App keys, or secrets are needed, only ordinary label-adding permission on the PR (which any contributor to their own PR effectively controls, and maintainers/bots can also be tricked by mirroring labels). This is fully repeatable per PR/per review stack.

### Recommendation
In `ReviewStack#env`, restrict label-derived keys to an explicit allow-list (e.g., only labels matching a configured `deploy_spec` variable name, or prefix all label-derived keys with a fixed, reserved namespace like `LABEL_` that cannot collide with `PATH`/other sensitive names), and/or filter the merged result through `deploy_spec.filter_deploy_envs`-style permit logic before it reaches `Stack#env`/`TaskCommands#env`. Additionally, `Command#unbundled_env` should not allow `@env` to redefine `PATH` (or other Shipit-controlled critical vars) unconditionally last; consider merging `@env` before, not after, the constructed `PATH`, or explicitly excluding reserved keys from `@env` before merge.

### Proof of Concept
Minitest plan (no live GitHub, using existing fixtures/factories):
1. Create a `ReviewStack` fixture with an associated `PullRequest` whose `labels` is set to `["path"]` (simulating what `LabelCapturingHandler#capture_labels` would persist).
2. Assert `Shipit::ReviewStack#env['PATH'] == 'true'` (demonstrates the merge is unfiltered at the model level):
   ```ruby
   assert_equal 'true', review_stack.env['PATH']
   ```
3. Build `Shipit::TaskCommands.new(task)` where `task.stack == review_stack` and a `deploy_spec` with no `machine.environment.PATH` entry; assert:
   ```ruby
   assert_equal 'true', task_commands.env['PATH']
   refute_equal task_commands.env['PATH'], "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
   ```
4. Construct `Shipit::Command.new('true', env: task_commands.env, chdir: Dir.tmpdir)` and assert `command.unbundled_env['PATH'] == 'true'`, proving the value that reaches `PTY.spawn` differs from the intended shell path and instead equals the label-derived string, i.e. asserting the binding `Command#unbundled_env['PATH'] != Shipit.shell_paths.join(':') + ':' + ENV['PATH']` fails to hold once a `path` label is present.
5. (Optional, webhook-level) Post a `pull_request` `action: labeled` payload with `labels: [{name: "PATH"}]` to `LabelCapturingHandler` directly (bypassing signature verification since that's tested elsewhere) and assert the persisted `PullRequest#labels` includes `"PATH"`, closing the loop from webhook input to the env merge.

      @out = @pid = nil

      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)

      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
