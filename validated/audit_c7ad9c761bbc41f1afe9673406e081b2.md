### Title
Webhook signature is verified against an attacker-chosen organization while handlers act on an unrelated, unverified `repository.full_name` / commit `sha` - cross-repository writes ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate a webhook's HMAC using `repository_owner`, a value pulled straight out of the still-unauthenticated JSON body (`params.dig('repository','owner','login')` or the `organization.login` fallback). [1](#0-0)  Once the signature check passes, the very same raw body is dispatched to event handlers that key their side effects off a *different* body field, `repository.full_name`, via `Handler#repository_name`/`Repository.from_github_repo_name`. [2](#0-1)  Nothing enforces that `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the Stack/Repository/Commit that gets written to) refer to the same repository. Some handlers go even further: `StatusHandler` doesn't consult the repository at all — it loads `Commit.where(sha: params.sha)` globally and writes a CI status onto every matching commit across every stack. [3](#0-2) 

### Finding Description
The trust binding the engine relies on is: *"the organization whose webhook secret authenticated this HTTP request" == "the repository/commit that the handler is about to mutate."* This binding is never enforced.

- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and then calls `github_app.verify_webhook_signature(header, raw_post)`, where `repository_owner` is read from the unauthenticated JSON body itself. [1](#0-0) 
- `verify_webhook_signature` just HMACs the raw body with whatever secret belongs to that organization and compares it to `X-Hub-Signature`. [4](#0-3) 
- After the check passes, `WebhooksController#create` dispatches the parsed body to every handler for the event, with no re-derivation or cross-check of organization: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [5](#0-4) 
- Handlers resolve the target repository from `payload.dig('repository', 'full_name')`, a field completely independent of `repository.owner.login`. [6](#0-5) 
- `StatusHandler` doesn't even use the repository field — it matches purely on commit `sha` across the whole install and writes a new `Status` for every matching commit, regardless of which stack/organization it belongs to. [3](#0-2) 

In a Shipit deployment configured for multiple GitHub organizations (each with its own `webhook_secret` under `Shipit.secrets.github`, as documented for multi-org installs) [7](#0-6) , any party who legitimately controls (or can obtain the webhook secret of) *one* of those organizations can sign an arbitrary JSON body with that org's secret while setting the payload's other fields — `repository.full_name`, `sha`, `ref`, `after`, pull-request fields, etc. — to target a completely different, victim organization/repository/stack hosted on the same instance. The controller will accept the signature (it matches the attacker's own org's secret) and then execute handler logic against the victim's data.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding and enables genuine cross-repository writes without any compromise of the victim's credentials:
- `PushHandler` can trigger `stack.sync_github(expected_head_sha:)` for a victim stack chosen purely from the attacker-controlled `repository.full_name`, causing GitHub sync jobs to run against a repository the attacker doesn't own. [8](#0-7) 
- `StatusHandler` can forge a passing (or failing) CI status on any commit in any stack in the system merely by knowing/guessing its `sha`, independent of repository ownership, which can influence merge/deploy gating decisions that consult commit statuses. [3](#0-2) 
- The `PullRequest` handlers (`opened`, `closed`, `labeled`, `unlabeled`, `reopened`) resolve their target repository the same way, from `params.repository.full_name`, allowing forged provisioning/archival/unarchival of review stacks belonging to a different organization. [9](#0-8) [10](#0-9) 

This meets the Critical bar of "cross-repository writes."

### Likelihood Explanation
Exploitability requires that the deployed Shipit instance be configured with more than one GitHub organization (multi-tenant secrets configuration, as documented in `docs/setup.md` and `config/secrets.development.shopify.yml`), and that the attacker controls or can obtain the webhook secret for at least one of the configured organizations — a realistic scenario for a shared/multi-org Shipit deployment where different teams manage their own organizations independently but share the same Shipit host. Given that, forging the payload only requires basic HTTP tooling; no GitHub credentials, session, or `ApiClient` token for the victim organization are needed.

### Recommendation
After verifying the HMAC signature, re-derive the repository/organization the handler will act on strictly from data already tied to the verified organization (or reject the request if `repository.owner.login`/`organization.login` does not match `repository.full_name`'s owner segment). `StatusHandler` should additionally scope its `Commit` lookup by the repository resolved from the verified payload rather than matching `sha` globally.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` (attacker controls the webhook secret) and `victim-org` (unrelated, victim-owned stack `victim-org/victim-repo`), per the multi-org `github:` secrets schema. [7](#0-6) 
2. Attacker crafts a `status` event JSON body:
   ```json
   {
     "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/attacker-repo"},
     "sha": "<sha of a commit belonging to victim-org/victim-repo>",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(webhook_secret(attacker-org), raw_body)` — a secret the attacker legitimately possesses for their own org — and sends it as `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and validates the signature successfully. [1](#0-0) 
5. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, writing a forged `success` status onto the victim's commit, even though the signature was only ever proven valid for `attacker-org`. [3](#0-2)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
