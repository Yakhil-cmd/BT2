### Title
Pull-request labels are injected into deploy/task shell command environment without whitelist filtering, enabling shell-variable-substitution tampering - (File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` unconditionally merges every attacker-controlled pull-request label into the environment hash used to run deploy/task shell commands, with no whitelist check, unlike `@task.env` which is passed through `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` (backed by `EnvironmentVariables#permit`). Any `$VARNAME` referenced in a trusted `shipit.yml` step is substituted via `Command#interpolate_environment_variables`/`EnvironmentVariables#interpolate` with the label-derived value before `PTY.spawn`, so an unauthenticated PR author can control the value bound to that variable simply by naming a label.

### Finding Description
The broken binding is: the value substituted for `$X` in a deploy/rollback/task step string should equal a value that originated from `deploy_spec` variable defaults, `@task.env` (filtered through `EnvironmentVariables#permit`), or trusted stack metadata — but for review stacks it can instead equal `"true"` derived from an arbitrary, attacker-chosen PR label name.

Path:
1. `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` onto `pull_request.labels` on `labeled`/`unlabeled`/`opened`/`reopened` events, with no whitelist on label names (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`). This webhook fires for events on any repository/PR the attacker controls (their own fork/PR), with no signature or permission relevant to the *content* of the label.
2. `ReviewStack#env` merges those raw labels directly into the stack's environment: `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` (`app/models/shipit/review_stack.rb:84-93`). No `permit`/whitelist call exists on this path.
3. `TaskCommands#env` (and `DeployCommands#env`) merges `@stack.env` directly into the environment used for every deploy/task command (`lib/shipit/task_commands.rb:33-48`), and `perform`/`install_dependencies` build `Command.new(command_line, env:, chdir: ...)` from `deploy_spec.deploy_steps!`, i.e. the trusted step strings from the repo's own `shipit.yml` (`lib/shipit/task_commands.rb:17-27`).
4. `Command#interpolate_environment_variables` calls `EnvironmentVariables.with(env).interpolate(argument)`, which does a raw regex substitution of `$VARNAME` in the step string with `Shellwords.escape(@env.fetch(variable) { ENV[variable] })`, with no whitelist check at all (`lib/shipit/command.rb:51-55`, `lib/shipit/environment_variables.rb:20-27`). This runs immediately before `PTY.spawn` in `Command#start` (`lib/shipit/command.rb:85-101`).

Contrast: `@task.env` (explicit user-supplied deploy variables) *is* filtered through `filter_deploy_envs`/`filter_rollback_envs`/`filter_envs`, which call `EnvironmentVariables#permit` and raise `NotPermitted` for unlisted variables (`app/models/shipit/deploy_spec.rb:174-180`, `app/models/shipit/task_definition.rb:63-65`, `lib/shipit/environment_variables.rb:13-18`). Labels bypass this permit mechanism entirely because they are merged in at the `ReviewStack#env`/`Stack#env` layer, not through `@task.env`.

Attack: attacker forks/owns a repo with review stacks enabled, whose `shipit.yml` deploy/rollback/task step contains a `$SOME_VAR` reference (this is visible to the attacker since `shipit.yml` lives in the repository, which they can read, or in a public repo). Attacker opens a PR and adds a label named `SOME_VAR` (case-insensitive, since it's upcased). On any subsequent deploy/task run against the review stack, that step's `$SOME_VAR` is substituted with `"true"` instead of whatever value the deploy_spec author intended (default value, or none). Existing guards (`force_github_authentication`, `verify_signature`, `ExplicitParameters` schema, `EnvironmentVariables#permit`) do not apply to this path: the `LabelCapturingHandler` schema only validates label field shape/type, not content, and `permit` is simply never invoked for the label-derived env.

### Impact Explanation
This is a real command-string tampering primitive against the review-stack owning repository's own deploy/rollback/task execution — the attacker's PR labels are folded into shell commands that already run with `GITHUB_TOKEN` and deploy credentials in `Command#unbundled_env` (`lib/shipit/command.rb:103-105`). If the repository's own `shipit.yml` (author-controlled, trusted) references any variable by name that is not in that step's explicit `deploy_variables`/`task_definition` whitelist (i.e., relies on the general "labels become env vars" convention, or any name collision with a label), the attacker chooses the substituted value. Whether this reaches "RCE" depends on how the *repository owner's own* `shipit.yml` uses that variable (e.g., as a path, flag, or command fragment vs. pure data echoed to logs) — this is a config-dependent amplifier, not an unconditional RCE by itself. It is repeatable on every deploy/task run for that stack and scoped to the repository whose PR the attacker opened (their own repo/fork triggering their own review stack); it does not cross-tenant to unrelated repositories' stacks, since `ReviewStack` scoping is per-repository (`review_stack_adapter.rb` scopes by `repository.review_stacks`).

### Likelihood Explanation
Preconditions: review stacks feature enabled for the repository (`repository.review_stacks_enabled`), and the repository's `shipit.yml` on the base branch (trusted, authored by a maintainer) must reference `$VARNAME` in a deploy/rollback/task step where `VARNAME` is not already defined by a higher-precedence merge (`@task.env`/`deploy_spec.machine_env` override later in the merge chain in `TaskCommands#env`, so a maintainer-supplied variable of the same name would win). The attacker needs only to be able to open/label a PR on a repository where they can create review stacks (their own fork or a repo where they have write access sufficient to label a PR) — this is a low-cost, fully automatable action requiring no secrets. The main gating factor is discovering (or guessing common names like `DEBUG`, `SKIP_TESTS`, `FORCE`, `PUBLIC`) a variable name actually referenced in that repo's `shipit.yml`, which is often visible since `shipit.yml` lives in the repo itself.

### Recommendation
Filter pull-request-label-derived environment variables through the same `EnvironmentVariables#permit` whitelist mechanism used for `@task.env`/`deploy_variables`, or namespace them (e.g. prefix with `LABEL_`) so they cannot silently override or spoof variables referenced by trusted `shipit.yml` steps unless explicitly whitelisted. At minimum, `ReviewStack#env`'s label merge should be constrained to a name pattern that cannot collide with deploy_spec-defined variables, or gated behind an explicit opt-in list in `shipit.yml`.

# frozen_string_literal: true

module Shipit
  class EnvironmentVariables
    NotPermitted = Class.new(StandardError)

    class << self
      def with(env)
        EnvironmentVariables.new(env)
      end
    end

    def permit(variable_definitions)
      return {} unless @env
      raise "A whitelist is required to sanitize environment variables" unless variable_definitions

      sanitize_env_vars(variable_definitions)
    end

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end

    private

    def initialize(env)
      @env = env
    end

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
  end
end
