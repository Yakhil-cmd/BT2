### Title
API client stack-scope bypass in CCMenu endpoint discloses build status of unauthorized stacks - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single `Stack` via the optional `stack_id` association [1](#0-0) . The generic API base controller enforces this scope by restricting the queryable `stacks` relation to `Stack.where(id: current_api_client.stack_id)` whenever `stack_id` is present [2](#0-1) . However, `Api::CCMenuController` (the CCTray/CCMenu status-widget endpoint) overrides `#stack` to bypass that scoped relation entirely, resolving the stack directly from `Stack.from_param!(params[:stack_id])` [3](#0-2) .

### Finding Description
The trust binding that should hold is: `ApiClient#stack_id` (the stack the token authorizes) == the stack whose data is rendered by the request. `BaseController#stacks`/`#stack` correctly enforce this equality for every other API controller (`app/controllers/shipit/api/base_controller.rb:74-80`). `CCMenuController` only checks the coarse-grained `read:stack` permission via `require_permission :read, :stack` [4](#0-3) , which is satisfied by any client that has the `read:stack` permission string regardless of its `stack_id` scope (`ApiClient#check_permissions!` only inspects the `permissions` array, not `stack_id`) [5](#0-4) . Because `CCMenuController#stack` re-implements the lookup as `Stack.from_param!(params[:stack_id])` instead of calling the inherited `stacks.from_param!`, a token that was deliberately scoped to a single stack (e.g., issued for a public build-status badge on stack A) can be used to query the CCMenu XML for any other stack B by simply changing the `stack_id` URL parameter, since `authenticate_api_client` in this controller also accepts the token via a public query-string parameter (`params[:token]`) rather than only header-based Basic Auth [6](#0-5) .

### Impact Explanation
This is an authorization-scope bypass: a token holder with a deliberately narrow, single-stack grant (the common intended use case for CCMenu tokens embedded in public build-status widgets) can read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, lock state, activity) for every stack in the Shipit instance, not just the one it was scoped to. This matches the report's "stack a token authorises versus a stack it touches" binding failure and results in unauthorized read of stack state across the deployment, which the scoping mechanism was specifically designed to prevent.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token that has the `read:stack` permission — including a token intentionally issued with a `stack_id` restriction (the exact scenario `stack_id` scoping exists to contain). No repository write access, GitHub credentials, or session is needed; only the token string, which per the CCMenu design is meant to be embeddable in public URLs/badges, needs to be known.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited, scope-respecting lookup (`stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the `current_api_client.stack_id` restriction is honored exactly as it is in `BaseController`.

### Proof of Concept
1. Create two stacks, A and B.
2. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id: A.id` (intended to only expose stack A's CI status via a public badge URL).
3. Request `GET /api/*A/ccmenu?token=<client_token>` — succeeds as intended.
4. Request `GET /api/*B/ccmenu?token=<client_token>` (same token, different `stack_id` in the path) — `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), bypassing the `stack_id` scope check that would have been applied by `BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-80`), and returns stack B's build status even though the token was only meant to authorize stack A.
