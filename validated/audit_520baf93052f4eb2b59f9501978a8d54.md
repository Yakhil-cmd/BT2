### Title
Cross-tenant webhook forgery via `repository_owner` organization fallback selecting the wrong signing secret while `ClosedHandler` mutates a different, attacker-named repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb`)

### Summary
`Shipit::WebhooksController#repository_owner` selects which organization's `webhook_secret` verifies the HMAC signature by reading `params.dig('repository','owner','login')` and falling back to `params.dig('organization','login')`, while `ClosedHandler` independently determines the target repository/stack from `params.repository.full_name`. In multi-organization Shipit deployments these two attacker-controlled fields are never checked for consistency, so an attacker who is an admin of their own onboarded GitHub organization (and thus knows that organization's `webhook_secret`) can sign a payload with their own secret while naming a victim organization's repository in `repository.full_name`, causing `ClosedHandler` to archive that victim's `ReviewStack`.

### Finding Description
The broken binding: `repository_owner` (used to pick the verifying `GitHubApp`/secret) is claimed to equal the repository/organization that the handler actually mutates (`params.repository.full_name`'s owner), but nothing enforces `params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`, nor `params.dig('organization','login') == that owner`.

Path:
1. `Shipit::WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` [1](#0-0) , where `repository_owner` falls back from `repository.owner.login` to `organization.login` [2](#0-1) .
2. `Shipit.github(organization:)` in multi-org configs (`github_default_organization` non-nil) uses `github_app_config(organization)` to fetch the config/secret keyed by exactly the passed-in `organization` argument [3](#0-2) , so the secret used to verify the HMAC is determined solely by the attacker-controlled `organization.login`/`repository.owner.login` field.
3. `GitHubApp#verify_webhook_signature` just HMAC-verifies the raw body against that selected secret [4](#0-3) . If the attacker knows that secret (because it belongs to an organization they legitimately administer within the same multi-tenant Shipit instance), they can sign any raw body they want, including one that names a different repository.
4. Once verified, `ClosedHandler` requires `repository.full_name` but not `repository.owner.login` [5](#0-4) , and resolves the target repository purely from that field: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) , then archives the matching `ReviewStack` for the PR number: `review_stack.archive!` [7](#0-6) .

Attacker request: `POST /webhooks` with `X-Github-Event: pull_request`, body `{"action":"closed","number":N,"pull_request":{...},"repository":{"full_name":"victim-org/victim-repo"},"organization":{"login":"attacker-org"},"sender":{"login":"attacker"}}` and `X-Hub-Signature` computed with the attacker's own `attacker-org` webhook secret. Note the payload deliberately omits `repository.owner.login` so the fallback path selects `attacker-org`, while `repository.full_name` names an unrelated victim repo.

Existing guards do not stop this: `verify_signature` only checks that the signature matches *some* configured org's secret, not that the org matches the repository being mutated; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema on `ClosedHandler` only requires `repository.full_name` to be a String, it does not require or cross-check `repository.owner.login`; there is no code anywhere in the request path that compares the verifying organization to the repository named in the payload.

### Impact Explanation
An attacker who administers one organization onboarded to a multi-tenant Shipit instance can archive the `ReviewStack` of any other onboarded organization's pull request by number, without any credential belonging to that victim organization. This is a write against a repository/stack that did not authenticate the request — matching the Critical category "a payload for one repository mutating another's stack." The attack is repeatable against arbitrary victim repositories/PR numbers as long as the attacker can compute a valid signature with a secret they legitimately possess for their own tenant. Note: this specific handler (`ClosedHandler`) only archives the review stack; it does not itself trigger `ContinuousDeliveryJob` or a deploy/rollback, so the "auto-ships newly-green commits via `ContinuousDeliveryJob`" amplification claimed in the question is not substantiated by code in `ClosedHandler` — that job is driven by commit status changes on `Stack`/`Commit`, not by pull-request-closed events. The confirmed impact is limited to unauthorized archival of a victim's `ReviewStack` via cross-tenant signature confusion, not an unauthorized deploy.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (`secrets.github` keyed by org names, i.e., `github_default_organization` non-nil) where the attacker is a legitimate administrator of at least one onboarded organization (and thus knows that org's `webhook_secret`) while a different, victim organization is also onboarded to the same Shipit instance. In a single-org deployment, `Shipit.github` ignores the passed `organization` argument entirely and always uses the one configured secret [8](#0-7) , so the divergence has no effect there. Given the multi-tenant precondition, the attack cost is low (one crafted HTTP POST) and fully repeatable.

### Recommendation
In `ClosedHandler` (and other webhook handlers), require and validate `repository.owner.login`, and in `WebhooksController#verify_signature`/`repository_owner`, derive the verifying organization strictly from `repository.owner.login` (do not fall back to the independent `organization.login` field), and additionally assert that the organization used to select the signing secret matches the owner of `repository.full_name` before dispatching to any handler.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or a new test), no live GitHub:
1. Configure `Rails.application.credentials.github` as a multi-org hash with two orgs: `attacker-org` (webhook_secret `"attacker-secret"`) and `victim-org` (webhook_secret `"victim-secret"`).
2. Create a `Stack`/`ReviewStack` fixture under repository `victim-org/victim-repo` bound to PR number `42`, `continuous_deployment: true`.
3. Build payload: `{"action":"closed","number":42,"pull_request":{...minimal valid fields, head.ref/sha...},"repository":{"full_name":"victim-org/victim-repo"},"organization":{"login":"attacker-org"},"sender":{"login":"attacker"}}` (no `repository.owner.login`).
4. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', "attacker-secret", body)`.
5. POST to `/webhooks` with `X-Github-Event: pull_request`.
6. Assert response is `200 OK` (i.e., verification passed using `attacker-org`'s secret: `repository_owner` == `"attacker-org"` even though the mutated repo's true owner is `"victim-org"` — the equality `repository_owner == repository.full_name.split('/').first` is false yet the request still succeeds).
7. Assert the victim's `ReviewStack` for PR 42 is now archived (`review_stack.reload.archived?` is `true`), proving a payload authenticated by `attacker-org`'s secret mutated `victim-org`'s stack.

```ruby
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)

    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
