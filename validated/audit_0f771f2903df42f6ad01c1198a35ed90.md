### Title
Config-blind Team/Membership persistence lets a webhook-planted membership become authoritative on a future `Shipit.github_teams` change - ([File: app/models/shipit/team.rb])

### Summary
`MembershipHandler#find_or_create_team!` and `Team.add_member` persist a `Team` and `Membership` row purely from webhook payload data, with no relationship at all to whether that team is (or will ever be) part of `Shipit.github_teams`. Because `Shipit.github_teams` resolves configured team handles via a DB-first lookup (`Team.find_or_create_by_handle` → `find_by(organization:, slug:)`) that only hits GitHub when the row is *absent*, a pre-existing row created from an attacker-controlled webhook is adopted as-is, without any live GitHub validation, the instant an operator adds the matching `"org/slug"` string to config.

### Finding Description
The binding that is supposed to hold is: *a `Membership` row for a team in `Shipit.github_teams` == a membership GitHub currently reports for that team*. The code breaks this binding as follows:

- `MembershipHandler#process` and `#find_or_create_team!` build a `Team` from attacker-suppliable payload fields (`params.team.id/name/slug/url`, `params.organization.login`) with `Team.find_or_create_by!(github_id: params.team.id)`, then calls `team.add_member(member)` to insert a `Membership`, all with zero cross-check against `Shipit.github_teams`. [1](#0-0) 
- `Team#add_member` inserts the membership unconditionally if not already present. [2](#0-1) 
- Later, `Shipit.github_teams` resolves each configured `"org/slug"` string with `Team.find_or_create_by_handle`, which does a **DB lookup first** and only calls GitHub (`fetch_and_create_from_github`) if no row is found. If a row with the matching `organization`/`slug` already exists (planted earlier by the webhook), it is returned as-is - no GitHub call is ever made. [3](#0-2) 
- `User#authorized?` and `force_github_authentication` then trust this Membership directly, with no live validation. [4](#0-3) [5](#0-4) 
- The only place GitHub membership is ever actually verified is `Team#refresh_members!`, invoked manually via `bin/rake teams:fetch`, which the docs instruct operators to run only "after you change the list of teams." Until that rake task runs, the stale/fabricated row stands. [6](#0-5) [7](#0-6) 

The webhook path itself is guarded by `verify_signature`/`drop_unhandled_event`, and in the fully multi-tenant configuration (`github_default_organization` present, `secrets.github` keyed per organization) an unregistered organization would be rejected with `GithubOrganizationUnknown` before any handler runs. [8](#0-7) [9](#0-8) 
However, in the legacy/single-app configuration (`github_default_organization` is `nil`, which is the schema shown throughout `docs/setup.md` and `test/dummy/config/secrets.yml`), `Shipit.github(organization: repository_owner)` ignores the `organization` argument entirely and always returns the one globally configured `GitHubApp`/secret regardless of which organization's login appears in the payload — there is no registration list to check against. In that mode, signature verification does not bind the event to a "known" organization at all; it only proves the request was signed by the single shared webhook secret associated with the one GitHub App install, and does not prevent processing of a `membership` event whose `organization.login`/`team.id` values are attacker-influenced. [10](#0-9) 

Given a signed `membership` webhook is delivered (as the question stipulates), the exploit flow is:
1. Attacker's org (never configured in Shipit) fires (or attacker otherwise causes delivery of) a `membership` "added" event with an arbitrary, non-colliding `team.id`, `organization.login = "attacker-org"`, `team.slug = "team"`, `member.login = <attacker's Shipit user login>`.
2. `find_or_create_team!` creates `Team(github_id: <arbitrary>, organization: "attacker-org", slug: "team")`, and `team.add_member(member)` creates the `Membership` row — both persisted with no relation to `Shipit.github_teams`.
3. Weeks/months later, an operator adds `"attacker-org/team"` to `github.oauth.teams`. `Shipit.github_teams` calls `Team.find_or_create_by_handle('attacker-org/team')`, which `find_by(organization: 'attacker-org', slug: 'team')` returns the attacker's pre-planted row — no GitHub call, no revalidation.
4. `User#authorized?` for the attacker's account now returns `true` immediately, purely from the stale row, until (if ever) an operator runs `rake teams:fetch`.

### Impact Explanation
This is a High-severity escalation into `Shipit.github_teams` authorization: an unprivileged party can pre-plant a `Team`/`Membership` pair that later, upon an unrelated operator configuration change, silently grants that party authenticated access to the whole Shipit instance (viewing stack state, task streams, triggering deploys/rollbacks depending on further authorization checks) without ever having been validated as an actual GitHub team member. The blast radius is scoped to installations using the legacy single-app webhook configuration (the configuration shown in this engine's own docs and test fixtures), and to the window between the config change and the next `rake teams:fetch` run — which the docs suggest is not automatic.

### Likelihood Explanation
Preconditions: (1) Shipit is running the legacy single-GitHub-App config (`github_default_organization` nil), so webhook signature verification doesn't bind to a specific registered organization; (2) the attacker can get a genuinely signed `membership` webhook delivered for a `team.id` value that doesn't collide with any existing `Shipit.github_teams` entry; (3) an operator later adds that exact `"org/slug"` string to `github.oauth.teams` without immediately running `rake teams:fetch`. Conditions (1) and (3) are configuration/operational choices outside the attacker's control, and the exact reachability of (2) — how a real, validly-signed webhook for an attacker-chosen org reaches the single shared endpoint — depends on GitHub App installation settings not fully verifiable from this codebase alone. Given the multi-step, config-change-dependent nature, this is a real design flaw in the code (DB-first, GitHub-second team resolution combined with unauthenticated webhook-driven Team/Membership creation) but not a single-request, fully attacker-controlled exploit.

### Recommendation
- Do not create/trust `Team`/`Membership` rows for organizations/teams that are not already part of `Shipit.github_teams` at webhook-processing time; restrict `MembershipHandler` to organizations whose teams are currently configured, or validate `params.team.id`/`slug` against a live GitHub lookup before persisting.
- Make `Team.find_or_create_by_handle` always revalidate against GitHub (or at least verify `github_id` still matches the live team) instead of trusting an existing DB row unconditionally.
- Automatically invoke `refresh_members!` for any team newly added to `Shipit.github_teams` (e.g., on config load, not only via manual `rake teams:fetch`), so stale/fabricated memberships cannot become authoritative without a live GitHub check.

```ruby
# test/models/team_test.rb (conceptual addition, no live GitHub)
test "a membership row planted before a team is configured becomes authoritative without any GitHub check" do
  # 1. Simulate a membership webhook for a brand-new, unconfigured org/team.
  post_data = {
    action: 'added',
    team: { id: 999_999, name: 'Attacker Team', slug: 'team', url: 'https://example.com/attacker' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(post_data.deep_stringify_keys)

  team = Shipit::Team.find_by(organization: 'attacker-org', slug: 'team')
  user = Shipit::User.find_by(login: 'attacker')
  assert team.present?
  assert Shipit::Membership.exists?(team_id: team.id, user_id: user.id)

  # 2. Operator later adds "attacker-org/team" to Shipit.github_teams, with NO refresh_members! call.
  Shipit.stubs(:github_teams).returns([team])

  # 3. Binding under test: Membership row == live GitHub fact. It is not -- no GitHub call ever happened.
  assert user.authorized?, "attacker gained authorization purely from a pre-planted webhook row"
end
```

```ruby
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
