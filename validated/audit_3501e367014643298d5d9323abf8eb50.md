### Title
Webhook Signature Verified Against `repository.owner.login` While Downstream Handlers Act on Attacker-Controlled `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment, the HMAC signature check binds trust to the organization taken from `repository.owner.login` (or `organization.login`) in the JSON payload, but every event handler subsequently resolves the *repository/stack to act on* using a completely separate field, `repository.full_name`, taken from the same attacker-supplied JSON body. Because the signature only proves the raw bytes were signed by *some* configured org's webhook secret — not that a specific field within the JSON is authentic — a party who knows one organization's webhook secret can forge a validly-signed webhook whose `repository.owner.login` matches their own org (satisfying `verify_signature`) while `repository.full_name` points at a completely different repository/stack tracked by another team's Shipit configuration.

### Finding Description
`WebhooksController#verify_signature` selects the signing secret using only the organization owner login from the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization config block (including its own `webhook_secret`) from `secrets.github`, a scheme explicitly documented for multi-org installations: [3](#0-2) [4](#0-3) 

Once the signature check passes, `Shipit::Webhooks.for_event(event)` dispatches to handlers that resolve the target repository/stack from a *different* JSON field — `repository.full_name` — via `Handler#stacks`/`#repository_name`, completely independent of the `repository.owner.login` value used earlier for authentication: [5](#0-4) 

This same pattern repeats in the push handler and every PR-related handler (`opened_handler.rb`, `labeled_handler.rb`, `reopened_handler.rb`, `unlabeled_handler.rb`, `label_capturing_handler.rb`), all of which call `Repository.from_github_repo_name(params.repository.full_name)`: [6](#0-5) [7](#0-6) 

The binding that should hold is: **organization whose secret signed the request == organization that owns the repository being acted upon**. Because `repository.owner.login` (checked) and `repository.full_name` (acted upon) are two independent, attacker-controlled fields inside the same signed JSON blob, this equality is never actually enforced — only "some field in the payload matches a known org" is checked, not "the org that signed this payload owns the repo being mutated."

### Impact Explanation
In a shared/multi-tenant Shipit instance (the documented multi-org `secrets.github` layout), any party who possesses (or can obtain, e.g., as an org owner/admin of their own onboarded organization) the webhook secret for *one* configured organization can forge `push`, `status`, `check_suite`, and `pull_request` events that are accepted as authentic for a *different* organization's repository/stack. Depending on which handler is targeted this can:
- Trigger `GithubSyncJob`/forced resync of an unrelated stack (`push_handler.rb`).
- Inject fabricated commit statuses (`status_handler.rb`) that can satisfy `MergeRequest#any_status_checks_failed?`/`any_status_checks_missing?`, feeding into `MergeRequest#merge!`, which calls `stack.github_api.merge_pull_request` — i.e., contributing toward an **unauthorized merge/deploy decision** on a repository the attacker does not otherwise control: [8](#0-7) 
- Archive/unarchive or spuriously provision/deprovision review stacks belonging to another org's repository via the PR label/opened/reopened handlers.

This crosses the "an organization that authenticated versus the repository that is written" boundary called out in scope, and can culminate in state changes (unauthorized merges, forced syncs) on repositories outside the attacker's authorization domain — a high-severity escalation across the multi-tenant trust boundary, without requiring a Shipit session, API token, or GitHub write access to the victim repository.

### Likelihood Explanation
Exploitability requires the target Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to know/control a webhook secret for at least one of those organizations (e.g., because they administer that org's GitHub App installation). This is a realistic scenario for shared internal deployment platforms serving multiple business units/teams, each with legitimate access to their own org's webhook secret but no authorization over other orgs' repositories. No GitHub write access, Shipit session, or API token is needed to forge the cross-org event.

### Recommendation
Bind the verified signature to the exact repository/organization the handler will act on: derive both the signature-selection key and the repository lookup key from the same, single trusted field (e.g., always use `repository.full_name`'s owner segment, or explicitly re-validate that `repository.owner.login == repository.full_name.split('/').first` before dispatch), and reject the webhook if they diverge. Alternatively, verify the signature per-repository (resolve the `Stack`/`Repository` first, then verify with that repository's associated org secret) rather than trusting an org name pulled from an unauthenticated JSON body prior to signature verification.

### Proof of Concept
Preconditions: Shipit configured with `secrets.github` containing two organizations, `org-a` (attacker-administered, webhook secret known to attacker) and `org-b` (victim, has a stack tracking `org-b/victim-repo`).

1. Attacker crafts a `push` (or `status`) webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a webhook_secret, body)` — a signature they can legitimately produce because they know `org-a`'s secret.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'org-a')` (from `repository.owner.login`), successfully verifies the signature against `org-a`'s secret, and allows the request through.
4. `PushHandler#stacks` resolves `Repository.from_github_repo_name('org-b/victim-repo')` (from `repository.full_name`) and processes the forged push/status event against `org-b`'s stack — despite the signature never having been checked against `org-b`'s secret.

Note: full confirmation that `Repository.from_github_repo_name` and `Stack` do not perform any additional cross-check against the verified organization would benefit from reviewing `app/models/shipit/repository.rb`, which was not directly inspected in this session; the index did not surface its full contents, and a Devin session with full repo access would be needed to confirm there is no compensating check there.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
