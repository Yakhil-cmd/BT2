### Title
Cross-organization commit-status forgery via unscoped `StatusHandler` webhook processing - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub organization/App derived from the payload's `repository.owner.login` (or `organization.login`) field, using that organization's configured `webhook_secret`. [1](#0-0) [2](#0-1)  This authenticates *who sent the request*, but `StatusHandler`, one of the registered event handlers invoked immediately after verification, never checks the repository at all: it looks up commits globally by SHA and writes a forged status onto them. [3](#0-2)  Shipit explicitly supports hosting multiple GitHub organizations, each with its own independent `webhook_secret`, on a single instance. [4](#0-3)  This breaks the equality "organization that authenticated == repository that is written": a valid signature for org A does not bind the payload's `sha`/status contents to any repository owned by org A.

### Finding Description
The webhook signature is verified per-organization: `Shipit.github(organization: repository_owner)` selects the `GitHubApp` (and therefore the `webhook_secret`) to check the `X-Hub-Signature` against, where `repository_owner` is read straight out of the attacker-supplied JSON body. [5](#0-4) [2](#0-1)  HMAC verification only proves the raw bytes were signed by whoever holds that organization's `webhook_secret`; it says nothing about which repository's data the attacker is allowed to write to.

Most webhook handlers re-derive scope from `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks`, which restricts writes to `Repository`/`Stack` rows matching that name (e.g. `PushHandler`, `CheckSuiteHandler`). [6](#0-5) [7](#0-6)  `StatusHandler`, however, ignores repository scoping entirely — it looks up *any* `Commit` row in the whole instance by raw SHA and writes the attacker-controlled status fields onto it:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2)  Because a `status` event payload requires only `sha`, `state`, and optional `description`/`target_url`/`context`/`created_at`, all fully attacker-controlled, [8](#0-7)  an attacker who legitimately administers a GitHub App/org configured in the same multi-org Shipit deployment (and thus knows that org's own `webhook_secret`) can sign a payload that passes `verify_signature` for their own org, while `sha` names a commit that belongs to a completely different organization's `Stack`/`Repository`.

### Impact Explanation
This is a cross-repository/cross-organization write: an attacker who controls only their own low-privilege organization's webhook secret can inject a fabricated CI status (e.g. `"success"`, arbitrary `context`/`description`/`target_url`) onto commits belonging to a victim organization's repositories with no relationship enforced between the authenticating organization and the affected repository. Because commit statuses feed into Shipit's CI-gating logic used to decide whether a commit is deployable, this can be leveraged to make an otherwise-blocked commit appear green, contributing to an unauthorized deploy of that victim stack.

### Likelihood Explanation
Requires the attacker to control (administer) at least one GitHub organization/App that is legitimately configured as a secondary org in the same shared Shipit instance's multi-org `github:` config — this is a supported and documented deployment topology, not merely theoretical. [4](#0-3)  No repository write access, GitHub App private key, or Shipit `ApiClient`/session is needed — only that organization's own `webhook_secret`, which the attacker legitimately owns for their own org. Guessing/knowing a victim commit SHA is straightforward since SHAs are frequently public (commit hashes appear in PRs, CI logs, public repos, etc.).

### Recommendation
`StatusHandler#process` must scope its `Commit` lookup to the repository indicated by the verified webhook's organization/repository, e.g. joining through `stacks`/`Repository.from_github_repo_name(payload.dig('repository','full_name'))` (as `Handler#stacks` already does for other handlers) before matching by SHA, rejecting or ignoring statuses whose `repository.full_name` does not belong to the organization that was actually used to verify the signature.

### Proof of Concept
1. Shipit is configured for two GitHub organizations, `attacker-org` and `victim-org`, each with its own App/`webhook_secret` (documented supported setup).
2. Attacker knows `attacker-org`'s `webhook_secret` (they legitimately administer that GitHub App/org) and knows the SHA of a commit belonging to a `victim-org` repository/stack tracked by the same Shipit instance (e.g. from a public PR).
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"},
     "sha": "<victim-org commit sha>",
     "state": "success",
     "context": "ci/checks",
     "description": "forged"
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org webhook_secret, raw_body)` and `X-Github-Event: status`, and POSTs to `/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` → `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and successfully verifies the signature using the attacker's own valid secret. [5](#0-4) 
6. `StatusHandler.call(params)` runs `Commit.where(sha: params.sha)` and finds the victim commit belonging to `victim-org`, then calls `commit.create_status_from_github!(params)`, persisting the forged `"success"` status onto it — with no check that this commit belongs to `attacker-org`. [3](#0-2)

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
