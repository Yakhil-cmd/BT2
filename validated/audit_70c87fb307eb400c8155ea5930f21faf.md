### Title
Pre-Publish Exechook Failure Does Not Block Symlink Publication - (File: main.go)

### Summary
`git-sync` allows a `--pre-publish-exechook-command` to run "validation" logic against a newly-fetched worktree before it is published via the atomic symlink swap. However, the `beforePublish` hook is invoked asynchronously and always reports success to the caller regardless of the actual hook outcome, so `publishSymlink` proceeds immediately without waiting for (or checking) the pre-publish hook's result — analogous to the reported bug class where an action is executed without validating that the precondition still holds/succeeded at execution time.

### Finding Description
In the sync loop, `syncHooks.beforePublish` is defined as: [1](#0-0) 

```go
syncHooks := syncHooks{
    ...
    beforePublish: func(hash string) error {
        if prePubExechookRunner != nil {
            prePubExechookRunner.Send(hash)
        }
        return nil
    },
    ...
}
```

`prePubExechookRunner.Send(hash)` only pushes the hash into a buffered channel consumed by a separate goroutine (`HookRunner.Run`); it does not block on, wait for, or propagate the result of the pre-publish command's execution: [2](#0-1) 

Because `beforePublish` unconditionally `return nil`s, `SyncRepo` treats the pre-publish check as having "passed" and immediately calls `git.publishSymlink(newWorktree)`: [3](#0-2) 

This mirrors the reported bug's root cause: an operation (symlink publish) that should be gated on a freshly-evaluated precondition (successful pre-publish validation) is instead executed based on stale/optimistic assumptions, because there is no synchronous check or deadline/verification tying the publish step to the actual hook outcome.

### Impact Explanation
If a user relies on `--pre-publish-exechook-command` to reject bad content (e.g., signature verification, linting, running tests, or "does this commit look legitimate" checks) before it becomes visible to the consuming application via `--link`, that content is published to the `--link` path regardless of whether the check ultimately fails. Downstream consumer pods can therefore begin consuming a worktree that the operator intended to gate on validation, resulting in "publishing wrong or partial content" to the application. In `--one-time` mode, the final exit code does reflect pre-publish failure via `WaitForCompletion` (fixed by `os.Exit(exitCode)` after the fact), but this happens *after* the symlink has already been swapped, so the incorrect content has already been exposed. [4](#0-3) 

### Likelihood Explanation
This triggers on every sync cycle where `--pre-publish-exechook-command` is configured and `changed` is true — no special attacker action beyond causing a new commit to be fetched (which is the normal, always-reachable trigger of the sync loop) is required to reach the flawed ordering. It requires the operator to have configured `--pre-publish-exechook-command`/`GITSYNC_PRE_PUBLISH_EXECHOOK_COMMAND` for it to matter, but this is a documented, first-class feature.

### Recommendation
Make `beforePublish` synchronous with respect to the pre-publish hook outcome: run (or wait on) the pre-publish exechook and propagate its error before calling `publishSymlink`, e.g. by having `HookRunner` expose a blocking `RunOnce(ctx, hash) error` (or reusing the `oneTimeResult` channel path unconditionally) so `SyncRepo` can abort publication when the hook fails, instead of firing-and-forgetting via the async `Send` channel.

### Proof of Concept
1. Configure git-sync with `--pre-publish-exechook-command=/bin/false --link=link --root=$ROOT --repo=file://$REPO`.
2. Push a new commit to `$REPO`.
3. Observe that `$ROOT/link` is updated to point at the new worktree hash immediately (verifiable via `readlink`/`assert_link_exists` as done in the e2e harness) even though the pre-publish exechook (`/bin/false`) always fails — the failure is only reflected in `git_sync_hook_run_count_total{status="error"}` metrics/logs and (in `--one-time` mode) the process exit code, not in whether the symlink was flipped. [5](#0-4)

```go
// Send sends hash to hookdata.
func (r *HookRunner) Send(hash string) {
	r.data.send(hash)
}

// Run waits for trigger events from the channel, and run hook when triggered.
func (r *HookRunner) Run(ctx context.Context) {
	var lastHash string

	// Wait for trigger from hookData.Send
	for range r.data.events() {
		// Retry in case of error
		for {
			// Always get the latest value, in case we fail-and-retry and the
			// value changed in the meantime.  This means that we might not send
			// every single hash.
			hash := r.data.get()
			if hash == lastHash {
				break
			}

			if err := r.hook.Do(ctx, hash); err != nil {
				r.log.Error(err, "hook failed", "hash", hash, "retry", r.backoff)
				updateHookRunCountMetric(r.hook.Name(), "error")
				// don't want to sleep unnecessarily terminating anyways
				r.sendOneTimeResultAndTerminate(false)
				time.Sleep(r.backoff)
			} else {
				updateHookRunCountMetric(r.hook.Name(), "success")
				lastHash = hash
				r.sendOneTimeResultAndTerminate(true)
				break
			}
		}
	}
}
```
