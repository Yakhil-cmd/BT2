### Title
Webhook signature verification selects the GitHub App/secret from an unverified `organization`/`repository.owner` field, decoupling the authenticated organization from the repository actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the HMAC secret) used to validate `X-Hub-Signature` from `repository_owner`, a value read straight out of the still-unauthenticated JSON body [1](#0-0) . The same raw, unauthenticated body is then handed unchanged to every registered `Shipit::Webhooks` handler in `create`, which independently derives the actual `repository`/`organization`/`team` records it mutates from the same JSON fields [2](#0-1) . Because the field used to choose *which secret validates the signature* (`repository.owner.login`, or `organization.login` when `repository` is absent) is read from the request body before any cryptographic check occurs, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that organization's `webhook_secret` is blank [3](#0-2) , an attacker who knows of any Shipit-configured GitHub organization with no `webhook_secret` set can forge a signature-less webhook whose `organization`/`repository.owner` claims that unsecured org while other payload data is processed by handlers exactly as sent.

### Finding Description
The binding that should hold is: **the organization whose credentials authenticate the request == the organization/repository whose state is written by the request**. In `verify_signature`, the organization used to select the verifying `GitHubApp` is taken from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [4](#0-3) . This lookup happens *before* signature verification succeeds — the value is attacker-controlled at this point. `Shipit.github(organization: repository_owner)` resolves per-org config (`webhook_secret`, `private_key`, etc.) from `config/secrets.yml`, supporting multiple GitHub organizations with independent secrets, as documented in `docs/setup.md` ("Using Multiple Github Applications") [5](#0-4) . `GitHubApp#verify_webhook_signature` treats an absent secret as automatic success: `return true unless webhook_secret` [6](#0-5) .

Membership/team webhook handling is a concrete example of the resulting decoupling: `MembershipHandler` finds or creates the `Team` using `params.team.id` and binds it to `params.organization.login` as the team's `organization`, and mutates `Membership` records for whatever `member.login` is supplied [7](#0-6) . `Team#github_hooks` scopes membership hooks by `organization` [8](#0-7) , and `Shipit.github_teams` (backed by `Team`) directly controls `current_user.authorized?` — the authorization gate for the entire UI [9](#0-8) , [10](#0-9) . Because `verify_signature`'s organization selection and the handler's own repository/organization extraction both read the same untrusted body fields independently, there is no requirement that "the org whose secret validated this request" equals "the org/repo the handler subsequently writes to" — only that a payload be crafted so the *verification* path resolves to an organization with a blank/no `webhook_secret` while other fields drive the actual write.

### Impact Explanation
If any GitHub organization configured in Shipit's `github` secrets section lacks a `webhook_secret` (explicitly supported — see the example `secrets.development.shopify.yml` showing `webhook_secret: # nil` [11](#0-10)  and the "unknown organization" handling path built for multi-org configs [12](#0-11) ), an unauthenticated attacker can send arbitrary, unsigned webhook bodies that Shipit will fully process (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) as long as `organization.login`/`repository.owner.login` names that unsecured org. Depending on which handler runs, this can: forge commit `status`/`check_run` results that feed into `Commit#deployable?` and the merge queue's `merge_status` (both of which gate deploys/merges) [13](#0-12) , [14](#0-13) ; inject arbitrary team membership, which alters `Shipit.github_teams`-based authorization used to gate application access [9](#0-8) ; or trigger `GithubSyncJob` fetches. This crosses the authentication boundary the webhook signature is meant to enforce, matching the "authentication bypass" / "escalation into `Shipit.github_teams` authorization" impact tiers.

### Likelihood Explanation
Exploitation requires: (1) Shipit configured with at least one GitHub organization whose `webhook_secret` is blank — a state the codebase explicitly tolerates (`return true unless webhook_secret`) and that the multi-org documentation shows as a normal per-org setting, and (2) no other network-level restriction on the `/webhooks` endpoint (it is a public, unauthenticated Rails controller with CSRF protection explicitly disabled: `skip_before_action :verify_authenticity_token` [15](#0-14) ). This is entirely configuration-dependent rather than universally exploitable, which limits likelihood, but the vulnerable code path itself requires no privileged credential, session, or repository access to trigger.

### Recommendation
Do not select the verifying `GitHubApp`/secret from an unauthenticated body field that the handler will later reuse to determine the mutated resource. Options: require `webhook_secret` to be present for every configured organization (fail closed instead of returning `true` on a blank secret), or verify the signature against every configured organization's secret and only accept the request if at least one matches, then use *that* organization (not the body-derived one) to authorize/scope which repositories the handlers may touch.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `secured-org` (real, `webhook_secret` set) and `unsecured-org` (any org name Shipit is configured to recognize with `webhook_secret` blank/nil, per the documented multi-org format [16](#0-15) ).
2. POST to `/webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature` (or any garbage value), body:
```json
{
  "action": "added",
  "team": {"id": 48, "name": "Ouiche Cooks", "slug": "ouiche-cooks", "url": "https://example.com"},
  "organization": {"login": "unsecured-org"},
  "member": {"login": "attacker-controlled-existing-github-login"}
}
```
3. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (invalid) signature header [3](#0-2) .
4. `create` then runs `MembershipHandler`, which creates/updates a `Team` scoped to `organization: "unsecured-org"` and adds the named member to it [7](#0-6) . If `Shipit.github_teams` includes a team with that handle (matching org "unsecured-org"), the attacker has forged their own authorization membership without ever presenting a valid signature for any organization that actually has a secret configured.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
