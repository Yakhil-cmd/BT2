### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` bypasses `blocking_statuses` gate - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit purely by `sha`, querying the entire `commits` table with no constraint that the commit's `stack`/`repository` matches the repository whose webhook signature was verified. An attacker who controls a repository containing a commit with the same SHA as a victim stack's blocking commit (e.g., a fork sharing history, or a repository seeded with identical commit content) can push a `state: success` status webhook from their own, legitimately-verified org and flip `Commit#blocking?` for the victim's commit, unblocking downstream victim commits they never authenticated against.

### Finding Description
The broken binding is: `webhook_repository_owner (params.dig('repository','owner','login'), verified via github_app.verify_webhook_signature)` should equal `victim_commit.stack.repository.owner`, but it does not — `StatusHandler#process` never checks it.

Code path:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the *attacker's own* payload (`params.dig('repository','owner','login')`). This only proves the request came from that org's webhook secret — it says nothing about which commits/stacks may be touched.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha` with no join/filter on `stack`/`repository`. Note the base `Handler` class even defines a `stacks` helper scoped by `repository_name` (app/models/shipit/webhooks/handlers/handler.rb:32-38) for exactly this purpose, but `StatusHandler` does not use it.
- `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!` writes a new `Status` row, changing `Commit#status`/`Commit#blocking?` (app/models/shipit/commit.rb:165-169, 219).
- `Commit#blocked?` (app/models/shipit/commit.rb:231-237) recomputes over `stack.commits.reachable.newer_than(last_deployed_commit).older_than(self).any?(&:blocking?)`. Once the blocking commit's status becomes non-blocking, later commits in the *same victim stack* become `blocked? == false` and thus `deployable? == true` (app/models/shipit/commit.rb:227-229).

Exploit flow: attacker identifies a victim stack whose `stack.blocking_statuses` is non-empty and locates a commit with matching `sha` in that stack that is currently blocking deploys. Because SHA-1 commit hashes are deterministic content hashes, an attacker who forks/shares history with the victim repo (or otherwise reproduces the exact commit object) can have a commit of identical `sha` in their own, attacker-owned GitHub repository. The attacker then sends a normal, correctly-signed GitHub status webhook (`POST /webhooks`) from their own repository with `sha: <victim-blocking-sha>`, `state: success`. `verify_signature` passes because it only validates against the attacker's own org secret. `StatusHandler#process` finds the `Commit` row by sha regardless of which stack/repository it belongs to and writes the forged success status onto it, clearing the block for the victim stack.

None of the existing guards catch this: `verify_signature` validates sender authenticity for a *repository*, not target-commit ownership; `ExplicitParameters` only validates payload shape; there is no `stacks`/`repository_name` filter applied in `StatusHandler#process` unlike what the `Handler` base class provides for other handlers.

### Impact Explanation
A record (a `Status`) is written for a stack/repository that never authenticated the request, directly removing a deploy safety gate (`blocking_statuses`) on a victim stack. This can lead to an unauthorized/unsafe deploy proceeding on the victim stack — matching "a payload for one repository mutating another's stack, commit... or an unauthorized deploy" (Critical). The attack is repeatable against any victim stack for which the attacker can obtain a commit with a matching SHA, and does not require any privilege on the victim repository, stack, or Shipit instance — only ability to send a normal, self-signed GitHub webhook from an owned repo.

### Likelihood Explanation
Preconditions: victim stack has `blocking_statuses` configured and has an undeployed commit queued behind a "blocking" commit; the attacker must reproduce an identical SHA-1 commit object in a repository they control (feasible via forks/mirrors sharing history, or manufactured commits with identical tree/parent/author/committer/message/timestamps — non-trivial for arbitrary content, but low-cost when the attacker forks the victim repo, which is the common case that gives identical SHAs for shared commits). No Shipit secrets, sessions, or GitHub App credentials are needed — only a normal GitHub webhook triggered from the attacker's own repository, which is signed correctly with the attacker's own webhook secret. This is a realistic, repeatable, low-cost attack for any attacker who forks or previously shared history with the target repository.

### Recommendation
Scope `StatusHandler#process` (and any other handler doing lookups purely by `sha`) to only affect commits belonging to stacks of the repository that authenticated the webhook, e.g. via the existing `stacks` helper on `Handler`:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring the commit's stack repository matches `payload.dig('repository','full_name')` before mutating any status.

### Proof of Concept
Add a minitest test under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or extend an existing status handler test):
1. Create two stacks: `victim_stack` (repository `victim/repo`) and `attacker_stack` (repository `attacker/repo`), both with `stack.blocking_statuses` containing e.g. `"ci/build"`.
2. Create `blocking_commit` on `victim_stack` with `sha: "abc123..."`, and add a status making it blocking (`state: "pending"` under a required/blocking context).
3. Create `downstream_commit` on `victim_stack` newer than `blocking_commit`; assert `downstream_commit.blocked?` is `true`.
4. Create an unrelated `Commit` with the **same sha** `"abc123..."` on `attacker_stack` (representing the attacker's own repo/commit with identical SHA).
5. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or POST to `/webhooks` with a valid signature computed using `attacker/repo`'s org secret) with `repository.full_name = "attacker/repo"`, `sha: "abc123..."`, `state: "success"`.
6. Assert: `blocking_commit.reload.blocking?` becomes `false` (status changed via the attacker-scoped webhook even though it targets `victim_stack`'s commit), and `downstream_commit.reload.blocked?` transitions from `true` to `false` — demonstrating the victim stack's safety gate was removed by a request authenticated only against `attacker/repo`.
