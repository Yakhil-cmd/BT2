### Title
Cross-tenant `Team` membership forgery via `github_id`-only lookup in `MembershipHandler#process` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#process` resolves the target `Team` solely by `github_id` via `find_or_create_team!`, without ever validating that the webhook's authenticated `organization.login` matches the existing record's `organization` column. Because the GitHub webhook signature is verified per-organization using that same organization's own `webhook_secret`, an attacker who controls (and can sign for) their own configured organization can forge a `membership` event whose `team.id` collides with a pre-existing `Team` belonging to a different organization, causing `team.add_member(member)` to attach an attacker-controlled user to that foreign team.

### Finding Description
The broken binding: the write is legitimate only if `params.organization.login == team.organization` for the `Team` row being mutated. In `find_or_create_team!`: [1](#0-0) 

the lookup key is exclusively `github_id`; the `organization.login` value from the payload is only used inside the `create` block, which is skipped entirely when a `Team` with that `github_id` already exists. `process` then calls: [2](#0-1) 

and `Team#add_member` performs the mutation unconditionally: [3](#0-2) 

Signature verification in `WebhooksController#verify_signature` derives the signing organization from the payload itself, falling back to `organization.login` when no `repository` key is present (which is the case for `membership` events): [4](#0-3) 

`GitHubApp#verify_webhook_signature` only proves that the request was HMAC-signed with the `webhook_secret` configured for the organization named in the payload — it proves nothing about the `team.id` value inside the same payload: [5](#0-4) 

Attack flow: the attacker administers (or is otherwise able to configure/know the `webhook_secret` for) an organization `attacker-org` that Shipit is configured to trust. They POST to `/webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `attacker-org`'s `webhook_secret`, `organization.login: 'attacker-org'`, but `team.id` set to the numeric `github_id` of a genuine `Shipit::Team` belonging to a different organization (a team in `Shipit.github_teams`). Signature verification succeeds because it only checks that the body was signed by `attacker-org`'s secret — it never cross-checks that `team.id` actually belongs to `attacker-org`. `Team.find_or_create_by!(github_id: ...)` finds the existing victim-org `Team` and skips the create block (so `team.organization` stays as the victim org's), and `team.add_member(member)` appends `attacker` as a member of that team.

Existing guards do not catch this: `drop_unhandled_event`/`check_if_ping` are irrelevant; `ExplicitParameters` schema only validates types/presence, not cross-field consistency; there is no `require_permission!`/`User#authorized?` check inside `MembershipHandler`; and `find_or_create_team!` never compares `params.organization.login` against `team.organization` on the existing-record path.

### Impact Explanation
The attacker forges a `Membership` write that links an attacker-controlled GitHub login to a `Shipit::Team` belonging to an organization they do not control. If that team is one of the teams listed in `Shipit.github_teams` (used for authorization elsewhere, e.g., granting elevated Shipit privileges/operator status), this is a direct escalation into `Shipit.github_teams` authorization for a victim organization's team — an authentication/authorization bypass with cross-tenant blast radius. This is repeatable for any `github_id` the attacker can guess or observe (team IDs are often discoverable), and works against arbitrary teams/organizations configured in the Shipit instance, as long as the attacker controls one trusted organization's webhook secret.

### Likelihood Explanation
Preconditions: (1) `Shipit.github_teams` is non-empty and includes the targeted team; (2) the targeted `Team` row already exists in the DB with a known `github_id`; (3) the attacker controls an organization that Shipit is configured to trust and knows/can obtain that organization's `webhook_secret` (e.g., they are an admin of their own onboarded org in a multi-tenant Shipit deployment). Given those, the attack is a single crafted HTTP POST with no GitHub interaction required — fully repeatable and low-cost. The main constraint is that the attacker must legitimately hold a `webhook_secret` for some trusted org, which is a real, if narrower, unprivileged-attacker scenario in multi-org Shipit deployments (the attacker is not "in `Shipit.github_teams`," not a Shipit operator, and holds no `secret_key_base`/API tokens — only their own org's webhook secret, which they legitimately possess as that org's GitHub App/webhook owner).

### Recommendation
In `find_or_create_team!`, always verify (and if necessary correct or reject) that `params.organization.login` matches the existing `team.organization` before performing any membership mutation; e.g., raise/drop the event if `team.organization != params.organization.login` instead of silently proceeding to `add_member`/`members.delete`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`-style):
1. Create `victim_team = Shipit::Team.create!(github_id: 4242, organization: 'victim-org', slug: 'victim-team', name: 'Victim Team', api_url: 'https://api.github.com/teams/4242')`.
2. Stub `Shipit.github(organization: 'attacker-org')` to a `GitHubApp` configured with a known `webhook_secret`.
3. Build a `membership` payload: `{ action: 'added', team: { id: 4242, name: 'x', slug: 'x', url: 'x' }, organization: { login: 'attacker-org' }, member: { login: 'attacker' } }`, and compute `X-Hub-Signature` using `attacker-org`'s `webhook_secret`.
4. POST to `/webhooks` with `X-Github-Event: membership` and that signature.
5. Assert `Shipit::Team.find_by(github_id: 4242).organization == 'victim-org'` (still equal — record untouched by identity) **and** `Shipit::Membership.exists?(team: victim_team, user: Shipit::User.find_by(login: 'attacker'))` is `true` — proving a cross-tenant write occurred despite `params.organization.login ('attacker-org') != team.organization ('victim-org')`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
