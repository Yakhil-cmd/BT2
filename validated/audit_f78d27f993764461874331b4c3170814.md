### Title
Uncaught exception in c-hash decoding causes crash / validation DoS - ([File: chash.js])

### Summary
`isChashValid()` in `chash.js` only wraps the base32/base64 decoding step in a `try/catch`; the subsequent bit-splitting and buffer reconstruction is unprotected and can throw on malformed but same-length input, propagating an uncaught exception into the validation pipeline. This is analogous to the GhostScript CVE-2020-16288 pattern where insufficiently bounds-checked parsing of attacker-supplied structured data leads to a crash/DoS when processing untrusted input.

### Finding Description
`isChashValid()` decodes an externally supplied encoded c-hash string and then unconditionally calls `buffer2bin()`, `separateIntoCleanDataAndChecksum()`, and `bin2buffer()` on the result: [1](#0-0) 

`separateIntoCleanDataAndChecksum()` throws a hard `Error` (`"bad length="...`) whenever the decoded buffer's bit-length isn't exactly 160 or 288 bits: [2](#0-1) 

The `try/catch` in `isChashValid()` covers only the `base32.decode` / `Buffer.from` call, not this later step, so any length mismatch propagates as an uncaught exception rather than returning `false`: [3](#0-2) 

The normal entry point `isValidAddress()` mitigates this risk by first enforcing a strict base32-alphabet regex (`/^[A-Z2-7]{32}$/`) before calling into `chash.isChashValid`, which for a well-formed 32-character base32 string always decodes to exactly 20 bytes (160 bits), so the length check can never fail: [4](#0-3) 

However, `isValidChash()` / `isValidAddressAnyCase()`, exposed from the same module, skip that charset restriction and only check string length before calling `chash.isChashValid`: [5](#0-4) 

`isValidAddressAnyCase` is referenced from `validation.js`, meaning it is reachable during unit/message validation of attacker-controlled data. Because the base32 decode library (`thirty-two`) can silently produce a decoded buffer whose bit length isn't a clean multiple matching 160/288 for certain malformed-but-correctly-sized inputs (e.g., strings mixing case, padding characters, or symbols the library tolerates without throwing), the length check inside `separateIntoCleanDataAndChecksum` can fail and throw, uncaught, out of `isChashValid`.

### Impact Explanation
An uncaught exception thrown deep inside address/c-hash validation, if it escapes the calling async/validation chain (rather than being caught by the immediate caller), can crash the Node.js process handling unit or message validation. Since this code path can be reached from unit content or wallet/AA messages carrying loosely-cased or malformed address-like strings, a remote unprivileged unit poster could potentially trigger a validation-node crash, resulting in a node being unable to process further units — mapping to "a network unable to confirm new units" if this affects widely-deployed validating nodes.

### Likelihood Explanation
Exploitability is uncertain and could not be fully confirmed: I could not verify from the index alone (a) the exact call site and surrounding error-handling in `validation.js` where `isValidAddressAnyCase` is used, and (b) whether the `thirty-two` base32 decoder can actually be coerced into producing an unexpected-length buffer without throwing itself. Both conditions are necessary for the uncaught exception to be reachable from attacker-controlled input, and I was not able to trace them to completion within available tool calls.

### Recommendation
Wrap the entire body of `isChashValid()` (not just the initial decode) in the `try/catch`, and have `separateIntoCleanDataAndChecksum`/`mixChecksumIntoCleanData` return an error indicator instead of throwing on the hot validation path, so malformed but same-length-string input is rejected as invalid rather than crashing the caller. Additionally, restrict `isValidChash`/`isValidAddressAnyCase` to the same base32 alphabet check used by `isValidAddress` before decoding.

### Proof of Concept
Not confirmed — reproducing this requires exercising the `thirty-two` decoder with an internally malformed string that passes `isStringOfLength(str, 32)` yet decodes to a byte buffer whose length isn't 20 bytes, and demonstrating that `chash.isChashValid` is called on such a string via `isValidAddressAnyCase` from a network-reachable validation path. I was unable to verify these two conditions with the tools available in this session.
