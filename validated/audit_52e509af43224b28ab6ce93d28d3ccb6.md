### Title
Webhook authentication fails open when a configured organization has no `webhook_secret`, breaking the binding between the authenticating organization and the repository/commit acted upon - ([File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using an attacker-controlled payload field (`repository.owner.login` / `organization.login`), and `GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever that organization has no `webhook_secret` configured. Because the handlers that actually mutate state (`PushHandler`, `StatusHandler`) trust a *different* payload field (`repository.full_name`, commit `sha`) with no further authentication, an unauthenticated attacker who knows that at least one organization configured on the Shipit instance has a blank `webhook_secret` can submit a completely forged webhook and have it accepted as genuine for any repository/commit tracked by that instance.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to check against based on `repository_owner`, which is read directly from the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` fails open — it treats an unset secret as "trust everything": [3](#0-2) 

This is a documented, reachable configuration state, not an unsupported deployment: both the example and Shopify secrets templates ship with `webhook_secret: # nil` as the default value for an organization entry: [4](#0-3) [5](#0-4) 

Once verification is bypassed (because the attacker-chosen `repository_owner` maps to an org with no secret), the handlers that actually act on the payload use a *separate, still-unverified* field of the same forged body to decide what to mutate. `Handler#repository_name`/`#stacks` resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`: [6](#0-5) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack: [7](#0-6) 

`StatusHandler#process` is even weaker: it never consults `repository_name`/`stacks` at all, and matches purely by commit `sha` across the whole database: [8](#0-7) 

The binding broken is: **organization that authenticated the request (`repository_owner`, checked against a per-org secret) ≠ repository/commit that is written (`repository.full_name` / `sha`, taken from the same unauthenticated body)**. Nothing ties the two together once the selected organization's secret is blank; the "verified" signature check never actually covers the fields the handlers use to select the mutated record.

### Impact Explanation
An attacker who knows (or discovers, e.g., by observing that a secondary/legacy org in a multi-org Shipit deployment was never given a secret) that some configured organization has `webhook_secret` unset can:
- Forge `push` events with an arbitrary `repository.full_name` and `after` SHA, invoking `Stack#sync_github` on any tracked stack belonging to a completely different, properly-secured organization — app/models/shipit/webhooks/handlers/push_handler.rb.
- Forge `status` events for any commit `sha` tracked anywhere in the instance, since `StatusHandler` performs no repository-scoping check at all, potentially satisfying `ci.require` and unblocking continuous deployment of a commit — app/models/shipit/webhooks/handlers/status_handler.rb.

This can lead to an unauthorized deploy/rollback being unblocked by forged CI state, or repositories being resynchronized with attacker-chosen commit SHAs, without ever needing the actual per-organization webhook secret, an `ApiClient` token, a session, or any privileged credential — only the public `/webhooks` HTTP endpoint. This matches the "unauthorized deploy" / "unauthenticated write" impact tier.

### Likelihood Explanation
Requires only that one organization entry in the running Shipit instance's `github:` secrets config has a blank `webhook_secret` — an explicitly documented, non-exotic configuration state shown as the default in the shipped example/secrets templates for both single- and multi-organization setups. No credentials, sessions, or privileged access are needed; the request is a single unauthenticated POST to the public webhooks endpoint.

### Recommendation
- Make `GitHubApp#verify_webhook_signature` fail closed (reject) when `webhook_secret` is blank instead of returning `true`, or require `webhook_secret` presence as a hard startup/config validation for every configured organization.
- Stop selecting the verifying organization/secret from unauthenticated payload content; if multiple organizations must share the endpoint, bind the verified secret to the same repository/organization values consumed by the handlers (e.g., verify against `repository.full_name`'s owner and re-validate handler lookups use the identical, already-verified owner).
- Add explicit repository/organization scoping to `StatusHandler#process` so a verified webhook cannot mutate commit status for a repository other than the one it was verified for.

### Proof of Concept
1. Deploy Shipit with a multi-organization `github:` config where org `LegacyOrg` (tracked previously but no longer receiving real webhooks) has `webhook_secret: nil`, while `RealOrg` is Shipit's actively used, properly-secured organization with tracked stacks.
2. POST to `/webhooks` with header `X-Github-Event: status` and any/garbage `X-Hub-Signature`, and body:
```json
{
  "organization": { "login": "LegacyOrg" },
  "sha": "<sha of a commit already tracked under a RealOrg stack>",
  "state": "success"
}
```
3. `verify_signature` resolves `repository_owner` = `LegacyOrg`, `Shipit.github(organization: "LegacyOrg").verify_webhook_signature` returns `true` unconditionally (lib/shipit/github_app.rb:76-77) because `webhook_secret` is blank.
4. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) matches the commit purely by `sha`, ignoring that the forged payload's claimed organization is unrelated, and creates a forged successful CI status on a `RealOrg` commit — potentially unblocking a deploy gated on `ci.require`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
