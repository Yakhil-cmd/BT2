### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook by matching the payload's `repository.owner.login` (or `organization.login`) to a specific GitHub App/organization config and validating the HMAC signature against that organization's `webhook_secret`. That verification proves only "this payload was signed by organization X's installed app." The `status` event handler, however, never re-checks that the commit it mutates actually belongs to a stack under organization X — it looks up commits by `sha` alone, globally, across every stack in the installation.

### Finding Description
`WebhooksController#verify_signature` resolves the app used for signature checking purely from the payload-declared owner: [1](#0-0) [2](#0-1) 

This is the equality the app relies on: `organization authenticated == organization whose stacks the handler may mutate`. Once the signature is valid for organization X, `Shipit::Webhooks.for_event('status')` dispatches the entire payload to `StatusHandler`: [3](#0-2) 

`StatusHandler#process` breaks that equality: it queries commits by `sha` only, with no scoping to the repository/organization that was authenticated, unlike the base `Handler` class's `stacks`/`repository_name` helpers (which scope by `payload.dig('repository', 'full_name')` but are never used here): [4](#0-3) [5](#0-4) 

`Commit` records are indexed on `(stack_id, sha)`, not on `sha` alone, meaning `sha` is not required to be globally unique — the schema explicitly supports multiple stacks (i.e., multiple repositories/organizations) sharing the same `sha` value:

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` will therefore match and update every commit across every stack/organization that happens to share that sha — a trivial condition to produce by forking a victim repository (a git fork reproduces identical commit objects/shas for any commit it hasn't rewritten).

`create_status_from_github!` writes a `Status` on the found commit using attacker-controlled `state`, `context`, `target_url`, and `description` fields from the payload: [6](#0-5) 

### Impact Explanation
An attacker who owns/controls any GitHub organization (or a repo) that has legitimately installed a Shipit-configured GitHub App instance — a routine, unprivileged action available to anyone in a multi-org `secrets.yml` deployment — can sign an arbitrary `status` webhook with their own organization's `webhook_secret`. By setting `sha` to a commit that also exists in a victim stack (obtained by forking the victim's public/private-but-forkable repository), the attacker forges a passing (`state: success`) CI status for that commit in the *victim's* stack, despite never having write/status access on the victim's actual GitHub repository. Because commit status/`deployable_status` directly gates `deployable?`, the merge queue, and `continuous_deployment` in `Commit#schedule_continuous_delivery` / `Stack`, this can result in an unauthorized deploy being triggered on a repository the attacker has no legitimate access to — this is the "unauthorized deploy" outcome explicitly listed as Critical impact.

### Likelihood Explanation
This requires only: (1) the ability to install (or already having installed) a self-controlled GitHub organization's app config in Shipit's multi-org setup — a normal, documented, unprivileged workflow — and (2) forking the target repository to reproduce a matching commit sha, which is possible for any commit the attacker hasn't needed to modify. No Shipit session, `ApiClient` token, or repository write access on the victim repo is required, satisfying the engine's unprivileged-attacker threat model.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving objects purely from a global identifier such as `sha`) to the repository/organization that was cryptographically verified for that request — i.e., intersect `Commit.where(sha: params.sha)` with `stacks` (repository-derived) as the base `Handler` class already does for `PushHandler`, rather than trusting a bare `sha` match across all stacks.

### Proof of Concept
1. Configure Shipit with two GitHub organizations in `config/secrets.yml` (`victim-org` and `attacker-org`), each with its own `webhook_secret`, as documented for multi-app installs.
2. Attacker forks `victim-org/target-repo` into `attacker-org/target-repo` (or otherwise obtains a commit sha shared with a real commit tracked by a Shipit stack for `victim-org`).
3. Attacker's GitHub App (installed on `attacker-org`) fires (or attacker crafts and signs, using `attacker-org`'s known `webhook_secret`) a `status` webhook payload:
   ```json
   {
     "sha": "<victim-org commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/target-repo"}
   }
   ```
4. `WebhooksController#verify_signature` validates the signature using `attacker-org`'s `webhook_secret` — succeeds, because the org referenced in the payload legitimately matches the signer.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which returns the commit belonging to the victim's stack, and writes a forged `success` status to it, unblocking deploy/merge gating on `victim-org/target-repo`.
