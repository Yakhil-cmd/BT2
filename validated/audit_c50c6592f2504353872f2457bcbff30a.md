### Title
Unbounded user-chosen book size overflows RAY fixed-point value math in `scaled_to_original` during accrual, permanently freezing the market - (File: contracts/pool/src/cache/scale.rs)

### Summary
The vault-module bug class — a user-provided magnitude multiplied against a fixed-point factor with no upper bound, aborting on overflow and disabling a core function — maps onto XOXNO Lending's share/index accounting. Any user sets the market's scaled debt book via `borrow`/`supply` with arbitrary `amount`s; accrual then computes `borrowed * borrow_index` inside `scaled_to_original`. When the scaled book is large (a high-decimal whale market) and the borrow index grows, the RAY-scaled product exceeds `i128::MAX` and panics with `MathOverflow`. Because every verb accrues first, the market freezes permanently — and the `MAX_BORROW_INDEX_RAY` cap never engages before the value ceiling is hit.

### Finding Description
`Cache::calculate_utilization` in `contracts/pool/src/cache/scale.rs:19-27` calls `scaled_to_original(env, self.borrowed, self.borrow_index)`, multiplying a RAY-scaled debt book by a RAY index. The same unscale path runs inside accrual (`unscale_borrow_ceil_ray` at `scale.rs:90-92` uses `scaled.mul_ceil(env, self.borrow_index)`), and accrual runs at the top of every market verb: `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `update_indexes`, `clean_bad_debt`, `recapitalize`.

The only bound on book size is the decimal-domain supply cap (rejects `i128` overflow on the raw amount, per `extreme_amount_inputs.rs:58-95`), and the index has a nominal cap `MAX_BORROW_INDEX_RAY`. Neither bound constrains the *product* `scaled_book * index`. A market holding ~1e9 whole tokens at 18 decimals is a scaled book of ~1e36 RAY; `i128::MAX ≈ 1.7e38`, so an index of ~170x — reachable in a few years at ~98% utilization on the steep segment of the XLM interest-rate curve — overflows the multiply. The repository's own harness test proves this end to end (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-360`): after the cliff, `update_indexes`, `withdraw`, and `repay` all fail with `MATH_OVERFLOW`, and `last.borrow_index < MAX_BORROW_INDEX_RAY`, i.e., the index cap is unreachable before the value overflow. The test comment notes the documented bound in `docs/reference/formulas.md` is wrong, so this is a genuine defect, not an ADR-documented choice.

### Impact Explanation
Permanent freezing of funds. Once the product overflows, every entrypoint that touches the market aborts in accrual: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and governance cannot `clean_bad_debt` or `recapitalize` (accrual precedes the write-down). All supplied liquidity and collateral in the market is permanently bricked — a contract unable to operate.

### Likelihood Explanation
A single unprivileged address can construct the precondition: `lift_caps`-equivalent governance caps aside, supplying a large principal and borrowing it at high utilization requires only the standard `supply`/`borrow` verbs. The requirements are (a) a high-decimal market where the cap domain admits a book near the ceiling, (b) a whale-scale position or aggregate market of that size, and (c) sustained high utilization on a steep rate curve so the index compounds ~170x before the index cap fires. This is a medium-likelihood tail risk rather than a cheap attack — it requires capital and time — but it is fully permissionless and irreversible once reached.

### Recommendation
Bound the product, not just the operands: either enforce `scaled_to_original(borrowed, borrow_index)` fits `i128` by capping accrual when `borrowed > i128::MAX / borrow_index`, or engage `MAX_BORROW_INDEX_RAY` strictly below the value ceiling derived from the decimal-domain maximum book, and clamp new supply/borrow so the scaled book times the maximum reachable index stays under `i128::MAX`.

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );

pub(crate) fn process_borrow(
    env: &Env,
    caller: &Address,
    account_id: u64,
    borrows: &Vec<HubPayment>,
    to: Option<Address>,
) {
    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);
    require_owner_or_delegate(env, account_id, caller, &account.owner);

    let recipient = to.unwrap_or_else(|| caller.clone());
    let mut cache = Context::new(env);
    require_external_recipient(env, &mut cache, &recipient);
    let aggregated = payments::aggregate_positive_payments(env, borrows);

    validate_position_entry_gates(
        env,
        &account,
        &aggregated,
        &mut cache,
        AccountPositionType::Borrow,
    );
    settle_borrow(env, &mut account, &recipient, &aggregated, &mut cache);
