### Title
Predictable/grindable "randomness" via `number_from_seed` allows AA trigger senders to bias on-chain lottery/gambling outcomes - (File: formula/evaluation.js)

### Summary
`ojson`/oscript AAs (Autonomous Agents) can implement pseudo-randomness with the `number_from_seed(seed[, min, max])` function, which deterministically maps a `sha256` of a caller-supplied seed to a number in a range. Unlike the properly designed `vrf_verify` primitive, `number_from_seed` provides no guarantee that the seed is unpredictable to the party constructing the triggering unit. If an AA author seeds it with any value that is fully known or fully controlled by the trigger sender before broadcast (e.g. `trigger.unit`, `trigger.data.*`, `timestamp`, or other fields the sender freely chooses), the sender can grind: compute the AA's response for arbitrarily many candidate trigger units off-chain (using `dryRunPrimaryAATrigger` or manual replication of the deterministic formula engine), and only broadcast the candidate that resolves in their favor. This is the exact bug class described in the report — a "random" outcome that is fully knowable/selectable in advance by the party submitting the transaction that consumes it — mapped onto AA execution instead of `block.difficulty`.

### Finding Description
`number_from_seed` is implemented in [1](#0-0)  as a pure hash function: it evaluates its arguments, hashes the seed with SHA-256, and derives a float/integer deterministically from the hash — there is no entropy source outside of what is passed in as `seed`. The grammar exposes this to any AA author as a first-class construct [2](#0-1) , and it is validated only for argument count/type, not for the unpredictability of its input [3](#0-2) .

Because AA execution in Obyte is fully deterministic given the trigger unit content and the current stable DAG state, and because `aa_composer.dryRunPrimaryAATrigger` lets anyone locally simulate AA responses for arbitrary candidate triggers before posting [4](#0-3) , a trigger sender who fully controls the content of their own unit (its `data` payload, and thus its hash `trigger.unit`, as well as `timestamp`) can iterate offline over many candidate messages, compute `number_from_seed(...)` for each, and submit only the unit that yields the favorable random outcome. The engine offers no built-in unpredictable entropy comparable to a delayed randomness beacon; the only unbiased mechanism ocore ships is `vrf_verify`, which requires an external oracle-held RSA private key to produce a VRF proof [5](#0-4)  and [6](#0-5) . If AA authors instead rely on `number_from_seed` with a self-supplied or trigger-derived seed (which is a documented, tested, unrestricted usage pattern, see [7](#0-6) ), the resulting "randomness" is exactly as grindable as the `block.difficulty`-derived hash described in the report.

### Impact Explanation
Any gambling/lottery/loot-box style AA that determines payouts, item rarity, or winner selection via `number_from_seed` fed by trigger-controllable data is exploitable: an attacker never loses and only submits triggers guaranteed to win, draining the AA's balance (fund loss to the AA and to honest participants) or unfairly capturing scarce, one-of-a-kind resources analogous to the reported settlement-type/location exploit. This matches the "AA fund loss" impact category, and is systemic to the oscript language rather than to a single deployed AA, since ocore ships and documents `number_from_seed` as the primary numeric-randomness primitive without pairing it with guidance/enforcement that its seed must originate from unpredictable, externally-attested data such as a `vrf_verify`-checked proof.

### Likelihood Explanation
Likelihood is high for any AA developer who reaches for `number_from_seed` as "the" randomness function without realizing that trigger-controlled inputs (or even `trigger.unit`/`timestamp`) are grindable by the trigger sender via free, unlimited off-chain dry-runs (`dryRunPrimaryAATrigger`). No special privileges are required — this is directly reachable by any ordinary unit poster acting as an AA trigger sender.

### Recommendation
- Document loudly (and where possible enforce) that `number_from_seed` must never be seeded with data controllable or fully known to the account triggering the AA (trigger fields, timestamp, own address) when the outcome affects value transfer; require seeds to originate from `vrf_verify`-validated oracle proofs or other externally-committed unpredictable data.
- Consider adding a commit-reveal or delayed-seed pattern at the language level (e.g., a builtin that references a future MC unit's data feed / oracle-signed value) so AA authors have a safe default without needing an RSA-VRF oracle for every game.
- Add static/dynamic validation warnings when `number_from_seed`'s seed argument is derived solely from `trigger.*` or `timestamp`/`mci` with no oracle-signed component.

### Proof of Concept
1. Deploy an AA whose payout logic includes: `messages: [{app:'state', state: "{ $r = number_from_seed(trigger.unit, 0, 99); if ($r >= 90) { ... pay attacker a jackpot ... } }"}]`.
2. As the attacker, before broadcasting, iterate over an unused `trigger.data` field (nonce) locally, computing candidate `trigger.unit` hashes and running `aa_composer.dryRunPrimaryAATrigger` (or replicating `number_from_seed`'s SHA-256-based formula from [8](#0-7) ) for each candidate to find one where `$r >= 90`.
3. Broadcast only the winning unit; the AA deterministically pays the jackpot every time, since the "randomness" was known before submission — mirroring the report's mining-then-selecting-favorable-location attack.
