### Title
Permanent freezing of accrued creator fees when the pool creator's token account becomes frozen/blocklisted - (File: `programs/cp-swap/src/instructions/collect_creator_fee.rs`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
`collect_creator_fee` and its permissionless variant always transfer the accrued `creator_fees_token_0`/`creator_fees_token_1` to a token account whose owner is hard-constrained to `pool_state.pool_creator`, with no alternate recipient or admin override path. If the underlying mint is a blocklist/freeze-capable token (e.g. USDC/USDT via freeze authority, or Token-2022 with a transfer-hook blocklist) and the creator's account becomes frozen or blocklisted, the fee transfer permanently reverts, and because the accounting fields are only zeroed *after* a successful transfer, the fees remain stuck in the vault indefinitely with no way to ever be withdrawn.

### Finding Description
The account constraint pins the fee recipient to the pool creator's address recorded at pool creation: [1](#0-0) 

Both instructions call `transfer_from_pool_vault_to_user`, which performs a plain `transfer_checked` CPI with no fallback recipient: [2](#0-1) [3](#0-2) 

The accumulated fee counters are only reset to zero after the transfer succeeds: [4](#0-3) 

If the token mint enforces a blocklist (freeze authority on SPL Token, or a Token-2022 transfer-hook/permanent-delegate enforcing a blocklist) and the `pool_creator`'s associated token account is or becomes frozen/blocklisted, every call to `transfer_checked` for that leg will fail. Since `pool_creator` is fixed in `PoolState` and no instruction updates it, and there is no alternate collection path, the fees keep accruing on every swap but can never be extracted — mirroring the referenced UMA disputer-blocklist pattern where a fixed, attacker/issuer-influenced recipient address permanently blocks a state-transition.

### Impact Explanation
This results in permanent freezing of the accrued creator fee funds for the affected token leg. Unlike the original UMA report (which DoSed the entire module), here the blast radius is narrower: swaps, deposits, and withdrawals for other users are unaffected, since fee accounting (`creator_fees_token_0/1`) is independent of swap execution. Only the creator's own accrued and future fees for the frozen leg become permanently unrecoverable, which still constitutes a real, permanent loss of the creator's rightful funds with no recovery mechanism in the program.

### Likelihood Explanation
Likelihood depends on the pool being created with a token that supports freezing/blocklisting (USDC/USDT-style freeze authority, or Token-2022 blocklist hooks) and on the creator's specific token account being frozen by the token issuer (regulatory action, compliance freeze, sanctions, etc.), which is outside the pool's control. This is a plausible but issuer-dependent scenario rather than something an ordinary unprivileged swapper can trigger unilaterally.

### Recommendation
Allow the fee to be redirected or claimable to a different, program-verifiable destination if the primary transfer fails (e.g., support specifying/updating an alternate creator-fee-recipient address, or add an escrow/claim mechanism keyed by `pool_creator` rather than a rigid `TransferChecked` to a single, unchangeable ATA), so that a frozen or blocklisted recipient account cannot permanently strand the accrued fees.

### Proof of Concept
1. Create a pool where `token_0_mint` (or `token_1_mint`) is an SPL/Token-2022 mint with freeze authority or a blocklist transfer-hook.
2. Let swaps occur so `creator_fees_token_0`/`creator_fees_token_1` accrue in `pool_state` (`programs/cp-swap/src/states/pool.rs` fields at lines 107-111 nearby "creator_fees_token" — confirmed present via grep, though exact accrual site in swap instructions not fully traced in this session).
3. The mint's freeze authority freezes the pool creator's associated token account for that mint (or a blocklist hook denies the creator's address).
4. Call `collect_creator_fee` or `collect_creator_fee_permissionless`; the `transfer_checked` CPI in `transfer_from_pool_vault_to_user` reverts every time, and `creator_fees_token_0/1` are never zeroed, permanently trapping the accrued value in the vault with no alternate withdrawal path.

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```
