### Title
`StatusHandler#process` mutates commit statuses matched only by SHA with no repository authorization check, allowing cross-repository status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely via `Commit.where(sha: params.sha)` and never calls the inherited `Handler#stacks`/`repository_name` helpers to confirm that the webhook's `repository.full_name` matches the commit's own stack's repository. This means a valid, signed webhook from an attacker's own registered repository can create/replace a `Status` on a commit belonging to an entirely different stack/repository, as long as the attacker knows or guesses the victim commit's SHA.

### Finding Description
The binding that should hold is: `commit.stack.repository == Repository.from_github_repo_name(params.repository.full_name)` before any `commit.create_status_from_github!` write occurs. Tracing the code shows this binding is never established:

- `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` — `process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. It never references `stacks`, `repository_name`, or any `Repository` lookup.
- `app/models/shipit/webhooks/handlers/handler.rb:32-38` — the base `Handler` class defines `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`) precisely so that sibling handlers (e.g. `PullRequest::LabeledHandler`) scope their mutations to stacks belonging to the repository named in the webhook payload — but `StatusHandler` doesn't use it.
- `Commit.where(sha: ...)` in `app/models/shipit/commit.rb` has no `stack_id`/repository scoping; SHAs are matched globally across all stacks in the Shipit instance.
- `commit.create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) unconditionally writes a new `Status` row (`statuses.replicate_from_github!`) for whatever commit was found.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves the webhook was signed by the GitHub App installation for `repository_owner` (the org named in the payload) — it says nothing about whether that repository's SHA space overlaps with another stack's commits. An attacker who owns/controls any repository connected to Shipit (their own fork, or any repo they can push commits/webhooks to) can send a legitimately signed `status` event where `payload['sha']` equals a SHA that also exists in a victim's stack (SHAs are 40-hex-char git hashes tied to content, and many organizations share commits via forks/cherry-picks/rebases, or an attacker can simply create a commit in their own throwaway repo with a colliding short-known SHA of a victim's public commit, e.g. a public open-source repository mirrored into two different Shipit stacks). The handler then finds and mutates the victim commit's status without ever checking that `payload['repository']['full_name']` corresponds to that commit's own stack.

### Impact Explanation
An attacker who controls any repository onboarded into the Shipit instance (their own fork/org) can inject or overwrite CI status on commits belonging to a completely different repository/stack that they do not control. Since statuses feed directly into deploy-gating logic (`Commit#deployable?`, `Stack#schedule_merges`, `ContinuousDeliveryJob` scheduling in `add_status`), this can trick a victim stack's continuous-deployment pipeline into treating a commit as green/CI-passed and trigger an unauthorized deploy or merge — this is a cross-tenant "payload for one repository mutating another's stack/commit" scenario, matching the Critical severity bucket. It is fully repeatable against any known SHA in any stack.

### Likelihood Explanation
The attacker needs: (1) a repository connected to Shipit with a working GitHub App/webhook installation they legitimately own (a normal, unprivileged capability — any GitHub user can create/register such a repo if Shipit is configured to accept it), and (2) knowledge of a target commit SHA in the victim's stack (commonly discoverable via public GitHub history, shared upstream commits, mirrored/forked repos, or simply by having pushed the same commit content to their own repo, since Git SHAs are content-derived and identical commits from a shared history produce identical SHAs across forks). No secrets, sessions, or team memberships are needed. This is a realistic and low-cost attack path.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to stacks belonging to the reporting repository, mirroring the pattern used elsewhere in the codebase, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, using the existing `Handler#stacks`/`repository_name` helper so that only commits belonging to the repository that signed the webhook can be mutated.

### Proof of Concept
```ruby
test "StatusHandler mutates a commit without any repository resolution" do
  victim_stack = shipit_stacks(:shipit)
  commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  Shipit::Repository.expects(:from_github_repo_name).never

  payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'context' => 'attacker-ci',
    'description' => 'forged',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' },
  }

  assert_difference -> { commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.new(payload).process
  end
end
```
This demonstrates that `Repository.from_github_repo_name` is never invoked (the equality `commit.stack.repository == Repository.from_github_repo_name(payload['repository']['full_name'])` is never checked) and the commit belonging to `victim_stack`, unrelated to `attacker/unrelated-repo`, is still mutated.
