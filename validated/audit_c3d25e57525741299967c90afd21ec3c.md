## Finding: `contains_duplicate_signers()` omits the fee-payer address from its duplicate-signer check

### Summary
`SignedTransaction::contains_duplicate_signers()` — the guard used by `AptosVM::validate_signed_transaction` to reject transactions with colliding signer addresses — only checks the sender against the secondary signers. It never includes the fee-payer address in the de-duplication set, even though `TransactionAuthenticator::FeePayer` carries a separate `fee_payer_address` field that is passed into the Move prologue/session as its own signer slot. [1](#0-0) 

```
pub fn contains_duplicate_signers(&self) -> bool {
    let mut all_signer_addresses = self.authenticator.secondary_signer_addresses();
    all_signer_addresses.push(self.sender());
    let mut s = BTreeSet::new();
    all_signer_addresses.iter().any(|a| !s.insert(*a))
}
```

`secondary_signer_addresses()` for the `FeePayer` variant returns only `secondary_signer_addresses`, not `fee_payer_address`: [2](#0-1) 

This check is invoked unconditionally at the very start of prologue validation: [3](#0-2) 

```
// Check transaction format.
if transaction.contains_duplicate_signers() {
    return Err(VMStatus::error(
        StatusCode::SIGNERS_CONTAIN_DUPLICATES,
        None,
    ));
}
```

### Finding Description
For `TransactionAuthenticator::FeePayer` and multi-agent transactions, the intent of `contains_duplicate_signers` is clearly to reject any transaction where the same account address appears more than once among the set of parties treated as independent "signers" for the Move VM session (sender, secondary signers, fee payer). However, the fee-payer address is structurally excluded from the address list being deduplicated. As a result, a transaction whose `fee_payer_address` collides with a secondary signer address (or, in principle, with the sender address, though that specific case is also independently guarded in the Move prologue via `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY`) is **not rejected** by this generic guard, unlike the analogous secondary-signer/secondary-signer or secondary-signer/sender collisions, which are rejected.

Since the fee payer's `AccountAuthenticator` is verified independently and does not have to be cryptographically identical to the secondary signer's authenticator, this creates an inconsistency window: `all_signers()` on `TransactionAuthenticator` pushes `sender`, then `secondary_signers`, then `fee_payer_signer` as separate signer entries (used to build the Move `signer` values passed into the prologue/session) — see `all_signers()`: [4](#0-3) 

Because address-level duplication among (secondary signer, fee payer) is not rejected at the format-check stage, the same address can be presented to the Move layer simultaneously as a "secondary signer" (authenticated with one key/authenticator) and as the fee payer (potentially authenticated by a different, attacker-controlled authenticator, subject only to the deferred, address-specific auth-key check inside `multi_agent_common_prologue`/`unified_prologue_fee_payer_v2`). This diverges from the explicit intent encoded by the existing e2e test suite (`verify_multi_agent_duplicate_secondary_signer`), which shows this exact class of check is meant to be comprehensive over all signer roles.

### Impact Explanation
This is a boundary/consistency defect in the transaction-admission format check rather than a demonstrated full compromise: each individual signer role (secondary signer, fee payer) still undergoes independent authentication-key verification later in the Move prologue (`multi_agent_common_prologue`, `unified_prologue_fee_payer_v2`), so a straightforward "wrong signer accepted" bypass is not immediately evident from this code alone. I was not able to fully trace, within the available context, whether any downstream Move/VM logic (e.g., session signer list construction, gas/fee attribution, or account-creation logic for `sponsored_automatic_account_creation`) relies on the invariant that signer addresses in a transaction are pairwise-unique, and would misbehave (e.g., double gas credit/debit, or an account being erroneously treated as both an existing signer and an auto-created sponsored account) when the fee payer's address duplicates a secondary signer's address. Given this uncertainty, I can state with confidence the code path is inconsistent with its own stated intent, but I cannot fully substantiate a concrete "wrong sender/signer executes and commits" impact chain purely from local code in the areas indexed.

### Likelihood Explanation
Triggering this requires crafting a `FeePayer`-authenticator transaction where `fee_payer_address` is set equal to one of the `secondary_signer_addresses`, each with independently valid signatures over their respective signing messages (`RawTransactionWithData::MultiAgentWithFeePayer`). This is fully within the reach of any unprivileged transaction submitter (no special permissions needed) and does not require any leaked keys — it only requires control of, or collusion between, the accounts used as secondary signer and fee payer, which is themselves attacker-controlled entities. The signature-verification logic (`TransactionAuthenticator::verify`) does not prevent the same address from acting in both roles.

### Recommendation
Update `contains_duplicate_signers()` to include `fee_payer_address()` (when present) in the set of addresses being checked for uniqueness, mirroring the address collection performed by `all_signers()`/`all_signer_auth_keys()`. This restores the original apparent invariant — that every signer role in a `FeePayer`/multi-agent transaction refers to a distinct account address — and removes the discrepancy between the documented intent (per the existing duplicate-secondary-signer e2e test) and the actual implementation.

### Proof of Concept
Conceptual PoC (not executed, due to tool limitations in ask-only mode):
1. Create three funded accounts: `sender`, `secondary`, and set `fee_payer_address == secondary`'s address.
2. Build a `RawTransaction` with `sender` as the sender and `secondary` as the sole secondary signer.
3. Sign it via `TransactionAuthenticator::fee_payer(sender_auth, vec![secondary_addr], vec![secondary_auth], secondary_addr /* fee_payer_address */, fee_payer_auth)`, where `fee_payer_auth` is signed by `secondary`'s key over the fee-payer message (address = `secondary_addr`) and `secondary_auth` is signed by `secondary`'s key over the same message.
4. Submit through mempool → `validate_transaction` → `AptosVM::validate_signed_transaction`. Observe that `contains_duplicate_signers()` returns `false` (no rejection) despite `secondary_addr` appearing as both a secondary signer and the fee-payer, which is inconsistent with the rejection that would occur if two *secondary* signer addresses collided instead (as covered by `verify_multi_agent_duplicate_secondary_signer`, at `aptos-move/e2e-testsuite/src/tests/verify_txn.rs`).

I was unable to further confirm (due to reaching the tool-call limit) whether this admission inconsistency propagates into an actual state-transition/gas-accounting fault inside the Move prologue/epilogue or session-signer construction; a background Devin session with full build/test access would be needed to execute the PoC end-to-end and confirm whether it produces any observable incorrect state transition beyond the missed format-level rejection.

    pub fn all_signers(&self) -> Vec<AccountAuthenticator> {
        match self {
            // This is to ensure that any new TransactionAuthenticator variant must update this function.
            Self::Ed25519 { .. }
            | Self::MultiEd25519 { .. }
            | Self::MultiAgent { .. }
            | Self::FeePayer { .. }
            | Self::SingleSender { .. } => {
                let mut account_authenticators: Vec<AccountAuthenticator> = vec![];
                account_authenticators.push(self.sender());
                account_authenticators.extend(self.secondary_signers());
                if let Some(fee_payer_signer) = self.fee_payer_signer() {
                    account_authenticators.push(fee_payer_signer);
                }
                account_authenticators
            },
        }
    }
