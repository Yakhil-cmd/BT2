### Title
Cross-repository commit status injection bypasses CI/deploy gating due to unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook by picking the `GithubApp`/secret for a specific **organization**, derived from `params.dig('repository','owner','login')`, and validating the HMAC signature against that organization's `webhook_secret`. However, the `status` event handler that consumes the verified payload never re-checks that the commit it mutates actually belongs to a repository owned by that same, authenticated organization. This breaks the binding: `organization whose secret verified the signature == repository/stack that gets written`.

### Finding Description
The webhook entrypoint selects which organization's secret to verify against using only the `repository.owner.login` field of the untrusted payload: [1](#0-0) 

Once the HMAC check passes, `WebhooksController#create` dispatches the entire raw JSON `params` to the registered handler for the event type with no further repository-ownership check: [2](#0-1) 

The base `Handler` class *does* provide a repository-scoped `stacks` helper that resolves `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository','full_name')`: [3](#0-2) 

Other handlers such as `PushHandler` correctly use this scoped `stacks` accessor before touching any records: [4](#0-3) 

But `StatusHandler#process` does **not** use `stacks` at all. It looks up commits **globally, across every repository/stack in the Shipit instance**, keyed only by `sha`, and then writes a GitHub-supplied status onto whichever commit(s) match: [5](#0-4) 

`Commit#create_status_from_github!` persists this attacker-influenced status (`state`, `context`, `target_url`, `description`) directly from the webhook payload, with no cross-check against the commit's actual `stack`/repository: [6](#0-5) 

**The equality that should hold, and is broken:**
`organization authenticated by verify_signature (payload.repository.owner.login)` == `repository/stack whose commit is mutated (commit.stack, resolved purely by matching sha)`

Before the flaw: an operator assumes a webhook's HMAC signature from Org A's GitHub App can only affect data belonging to repositories owned by Org A.
After: Org A's (or any onboarded, unprivileged GitHub organization's/repo's) legitimately signed `status` webhook can write a status onto a commit belonging to a completely different stack/repository/organization B tracked by the same Shipit instance, as long as the git SHA happens to match — which is trivial via a GitHub fork (forks retain identical SHAs for shared history) or any repository that has cherry-picked/rebased the same commit.

### Impact Explanation
Commit statuses directly gate both deploy safety checks and the merge queue: `Commit#deployable?` requires `success?` (derived from `status`, which is built from `statuses`), and blocking/required statuses (`ci.require`, `merge.require`) are enforced from this same data: [7](#0-6) 

An attacker who controls (or forks) any GitHub repository that is independently onboarded into the same Shipit instance can:
1. Fork/obtain a repository sharing a commit SHA with a victim stack's current HEAD (or an unmerged/pending commit awaiting CI).
2. Send a `status` GitHub API call from their own repo/organization for that SHA with `state: success` and a `context` matching one of the victim stack's `ci.require`/`merge.require` contexts.
3. GitHub delivers the resulting `status` webhook, correctly signed by the attacker's own organization's webhook secret.
4. `WebhooksController#verify_signature` validates the signature (correctly, for the attacker's org) and forwards the payload.
5. `StatusHandler#process` finds the victim's `Commit` by SHA alone (ignoring which org/repo actually authenticated) and marks it `success`, potentially satisfying required CI checks and unblocking an unauthorized deploy or merge-queue merge on a repository the attacker has no legitimate access to.

This maps to the "unauthorized deploy or merge" Critical/High impact category, since it lets an attacker forge CI signal on a repository/stack outside their authorization scope purely by controlling an unrelated, low-privilege GitHub repository.

### Likelihood Explanation
Requires only that: (a) two distinct repositories tracked as separate Shipit stacks share a commit SHA (trivially achievable via a public fork of the victim repo, which anyone can create without any privileged access to the victim), and (b) the attacker can set a commit status on their own fork via the standard GitHub API (a normal, unprivileged repo-owner capability, not requiring victim-side access, Shipit sessions, or API client tokens). No secrets, sessions, or admin access to the target stack are required — only ordinary GitHub write access to an attacker-owned repository.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through the same repository-derived `stacks` relation used elsewhere (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack: stacks)`), so a status can only be applied to commits belonging to the repository that was actually authenticated via the webhook signature. Apply the same repository-scoping audit to any other handler that queries `Commit`/`Stack` without going through `Handler#stacks`.

### Proof of Concept
1. Register two unrelated Shipit stacks: Stack V (victim, org `victim-org/app`) and Stack A (attacker-controlled, org `attacker-org/app-fork`, a public fork of Stack V's repo so it shares commit history/SHAs), each with distinct GitHub App webhook secrets.
2. Identify a commit SHA `S` present in both `victim-org/app` (as an undeployed/pending commit awaiting a required CI context, e.g. `ci/required-check`) and in `attacker-org/app-fork` (inherited from the fork).
3. As the owner of `attacker-org/app-fork`, call the GitHub Statuses API to set `state=success`, `context=ci/required-check` on commit `S` in the attacker's own fork.
4. GitHub sends a `status` webhook to Shipit, signed with `attacker-org`'s webhook secret.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and validates the signature successfully (it's genuinely attacker-org's signed payload).
6. `StatusHandler#process` executes `Commit.where(sha: 'S')`, which matches the commit in **Stack V** (victim), and calls `create_status_from_github!`, marking it `success` for `ci/required-check` — even though `attacker-org` has no relationship to `victim-org/app`.
7. If this satisfies Stack V's `ci.require`/`merge.require` configuration, `Commit#deployable?` becomes true and/or the merge queue considers the PR mergeable, enabling an unauthorized deploy/merge on a stack the attacker never had access to.
