### Title
Signature verification is a silent no-op when `webhook_secret` is unset, allowing unauthenticated forgery of GitHub webhooks that escalate into `Shipit.github_teams` authorization - (File: lib/shipit/github_app.rb)

### Summary
`GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the organization, so `WebhooksController` accepts and processes arbitrary, unauthenticated JSON payloads on the public `/webhooks` endpoint. Because the `membership` webhook handler mutates `Team`/`Membership` records that directly gate `User#authorized?`, an anonymous attacker can forge a `membership` event to add an arbitrary Shipit user (including themselves, once they've completed the normal OAuth login) to a team listed in `Shipit.github_teams`, bypassing the GitHub-team authorization check entirely.

### Finding Description
The webhook signature check is:
```ruby
# lib/shipit/github_app.rb
def verify_webhook_signature(signature, message)
  return true unless webhook_secret

  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'

  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [1](#0-0) 

`webhook_secret` is explicitly documented as **optional** (`docs/setup.md`: "Webhook secret (optional): Fill it with some randomly generated string...") [2](#0-1)  and the example secrets file ships with `webhook_secret: # nil` [3](#0-2) . This is a supported, documented deployment configuration, not a misuse of the engine.

`WebhooksController` is mounted at `/webhooks` with no session, API-client, or other authentication requirement — the only gate is `verify_signature`:
```ruby
before_action :check_if_ping, :drop_unhandled_event, :verify_signature
...
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
``` [4](#0-3) 
Note also that `verify_signature` never actually halts the request when verification fails — it calls `head(422)` but does not `return`, so the `create` action still runs regardless of the signature outcome. Combined with an unset `webhook_secret`, or even independent of it, `create` unconditionally dispatches the raw parsed body to registered handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [5](#0-4) 

The `membership` event is routed to `Handlers::MembershipHandler` [6](#0-5) , which (per `test/controllers/webhooks_controller_test.rb`) creates/removes `Team` and `Membership` records based on payload-supplied `team`/`member`/`action` fields [7](#0-6) .

Authorization to use the entire Shipit UI is gated purely on team membership:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [8](#0-7) 
and this is enforced in `Authentication#force_github_authentication`, which renders a 403 for logged-in-but-unauthorized users [9](#0-8) .

**The broken binding**: "an organization/request that authenticates as GitHub" (via `X-Hub-Signature`) versus "the `Team`/`Membership` state that is actually written and later trusted for authorization." When `webhook_secret` is absent, the left side of that equality is vacuously true for any payload, so the two sides diverge completely — anyone can write membership state without ever being GitHub.

### Impact Explanation
This maps to the listed High-impact criterion: "escalation into `Shipit.github_teams` authorization." An attacker who has completed a normal (unprivileged) GitHub OAuth login to Shipit — thereby obtaining a `User` record but failing the `authorized?` check — can forge a `membership` webhook adding their own `login` to a `Team` whose `organization/slug` matches one of `Shipit.github_teams`. Their next request will pass `authorized?` and gain full access to stacks, tasks, deploys, and rollbacks. This is a genuine authentication/authorization bypass reachable by any unprivileged attacker who can send an HTTP request, with no GitHub App credentials, webhook secret, ApiClient token, or session required beforehand (aside from a self-service OAuth login, which is intentionally open to any GitHub user under this authorization model).

### Likelihood Explanation
Likelihood is high wherever an operator has not configured `webhook_secret`, a state explicitly presented as optional/acceptable in the project's own setup documentation. No timing, race condition, or privileged credential is needed — a single unauthenticated POST to `/webhooks` with `X-Github-Event: membership` and a fabricated body is sufficient.

### Recommendation
- Make `webhook_secret` mandatory (fail closed) rather than treating its absence as "signature verified." At minimum, `verify_webhook_signature` should return `false`, not `true`, when no secret is configured, unless webhooks are being deliberately and explicitly disabled.
- Fix `WebhooksController#verify_signature` to actually halt the filter chain (`head(422) and return` / `render` then stop) so that a failed or skipped verification cannot fall through to `create`.
- Do not derive authorization-critical state (`Team`/`Membership`) purely from unauthenticated webhook content; consider requiring the GitHub App installation context (verified via signature) to match the team's `organization` before mutating membership.

### Proof of Concept
1. Deploy Shipit without setting `github.webhook_secret` (a documented, supported configuration).
2. As any GitHub user, complete OAuth login to Shipit to create a `User` record; note `authorized?` is `false` because the user is not on an approved team.
3. Send an unauthenticated request:
```
POST /webhooks
X-Github-Event: membership

{
  "action": "added",
  "organization": {"login": "<org-in-Shipit.github_teams>"},
  "team": {"id": 1, "name": "Approved Team", "slug": "<approved-slug>", "url": "https://example.com"},
  "member": {"login": "<attacker-github-login>"},
  "repository": {"owner": {"login": "<org-in-Shipit.github_teams>"}}
}
```
4. `verify_signature` calls `Shipit.github(organization: "<org-in-Shipit.github_teams>").verify_webhook_signature(...)`, which returns `true` unconditionally because `webhook_secret` is `nil`.
5. `Handlers::MembershipHandler` creates the `Membership` linking the attacker's `User` to the approved `Team`.
6. The attacker reloads the Shipit UI; `User#authorized?` now returns `true`, granting full access without ever proving GitHub App/organization ownership.
