### Title
Receipt size limit bypass via `promise_return`/`value_return` after `output_data_receivers` are appended post-validation - ([File: runtime/runtime/src/verifier.rs])

### Summary
`validate_receipt` only enforces `max_receipt_size` when `mode == ValidateReceiptMode::NewReceipt`, and this check runs *before* `output_data_receivers` are appended to a receipt created via `promise_return`/`value_return`. The resulting oversized receipt is later handled under `ValidateReceiptMode::ExistingReceipt`, which intentionally skips the size check, so the receipt is accepted into delayed/incoming receipt queues and buffers despite exceeding `max_receipt_size`.

### Finding Description
`validate_receipt` in [1](#0-0)  only checks `borsh::object_length(receipt) > limit_config.max_receipt_size` when `mode == ValidateReceiptMode::NewReceipt`. This check is invoked from `apply_action_receipt` right after actions execute and new receipts are produced [2](#0-1) , i.e., *before* `output_data_receivers` from the calling receipt are merged into the promise-returned receipt.

The merge happens afterward in the "Generating outgoing data" step: if a `FunctionCall` result is `ReturnData::ReceiptIndex` (which is what `promise_return` produces), the caller's `output_data_receivers` are appended in-place to the already-validated new receipt's `output_data_receivers` [3](#0-2) . This append happens strictly after the `NewReceipt`-mode size check already ran, so a receipt that was exactly at (or just under) `max_receipt_size` at validation time can grow past the limit afterward and is never re-validated as `NewReceipt`.

This exact mechanism is documented in-repo as a known, tracked issue: the `ValidateReceiptMode::ExistingReceipt` variant explicitly notes "There is a bug which allows to create receipts that are above the size limit... See https://github.com/near/nearcore/issues/12606" [4](#0-3) . Once persisted, the oversized receipt is processed via `ValidateReceiptMode::ExistingReceipt` both for delayed receipts [5](#0-4)  and incoming receipts [6](#0-5) , both of which skip the size gate entirely, so it is never rejected on reprocessing.

The scenario is directly reproduced by the test-loop test `test_max_receipt_size_promise_return`, whose comment states: "Size of this receipt will be equal to `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and the receipt's size will go above max_receipt_size. The receipt should be rejected, but currently isn't because of a bug" [7](#0-6) , and its companion `max_receipt_size_promise_return_method2`/`promise_return` contract code [8](#0-7) .

### Impact Explanation
An unprivileged account can, via ordinary `FunctionCall` actions using `promise_return`, cause an oversized `ActionReceipt` (above `max_receipt_size`, e.g. `4_194_304` bytes) to be committed to state/queues. This breaks the invariant relied upon elsewhere in the runtime that all receipts are bounded by `max_receipt_size` — for example the bandwidth scheduler's outgoing-buffer accounting assumes "all receipts are smaller than `max_receipt_size`" when metadata isn't fully initialized [9](#0-8) . This is a receipt/congestion accounting failure-boundedness violation (resource/limit-bypass), matching the "receipt or congestion accounting failures" and "unbounded resource use" impact classes. Because the size check is skipped identically by `ValidateReceiptMode::ExistingReceipt` on every node (deterministic code path), this does not by itself cause state/consensus divergence between honest nodes — all nodes tolerate the oversized receipt the same way — but it does allow bypassing the `max_receipt_size` protocol limit indefinitely.

### Likelihood Explanation
Fully reachable by any unprivileged account: deploy any contract, call a method that builds a promise DAG and uses `promise_return` on a promise whose base receipt size is close to `max_receipt_size`, then let the caller's `output_data_receivers` be appended. This is deterministic and repeatable, and is already exercised by the existing test-loop test `test_max_receipt_size_promise_return` (and its analogue `test_max_receipt_size_value_return`), both of which explicitly assert the oversized receipt occurs (`assert_oversized_receipt_occurred`) [10](#0-9) .

### Recommendation
Re-validate the size of promise-returned/value-returned receipts under `ValidateReceiptMode::NewReceipt` after `output_data_receivers` are appended in the "Generating outgoing data" step in `runtime/runtime/src/lib.rs` (around lines 1019-1037), before the receipt is added to `new_receipts`/persisted, so the `ReceiptSizeExceeded` error is surfaced at receipt-creation time rather than being silently tolerated later. Alternatively, bound the maximum receipt size at creation time to account for the maximum possible `output_data_receivers` growth so the post-append size can never exceed `max_receipt_size`. This should resolve the underlying tracked issue near/nearcore#12606 rather than merely tolerating it via `ExistingReceipt`.

### Proof of Concept
Use the existing `test_max_receipt_size_promise_return` integration test in `test-loop-tests/src/tests/max_receipt_size.rs` (lines 129-208) as the PoC: it deploys `rs_contract()`, calls `max_receipt_size_promise_return_method1` with `args_size` computed so the base receipt is exactly `max_receipt_size`, triggers the promise DAG rewrite via `promise_return` (in `max_receipt_size_promise_return_method2`), and then calls `assert_test_completed`. The test currently asserts `assert_oversized_receipt_occurred`, confirming an oversized receipt is persisted. To strictly demonstrate the fix is needed, add an assertion that re-running `validate_receipt` with `ValidateReceiptMode::NewReceipt` on the persisted oversized receipt (obtained from `get_incoming_receipts_for_shard`/chain store as in `assert_oversized_receipt_occurred`) returns `Err(ReceiptValidationError::ReceiptSizeExceeded { .. })`, proving the receipt would fail strict re-validation yet was accepted and persisted under `ExistingReceipt` mode.

pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    /// More strict than `OldReceipt` mode, which has to handle older receipts.

    ExistingReceipt,
