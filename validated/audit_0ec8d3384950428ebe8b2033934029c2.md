## Title
Cross-organization team-membership forgery via the GitHub `membership` webhook escalates a user into `Shipit.github_teams` authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler` resolves the `Team` record to mutate using only the GitHub-assigned numeric `team.id` from the webhook payload, without ever checking that the payload's `organization.login` (the organization whose webhook secret was actually used to authenticate the request) matches the `organization` already stored on that `Team`. This breaks the binding "organization authenticated by the webhook signature" == "organization that owns the team being written to," the exact class of bug highlighted in the rules (an org authenticated vs. a different resource being written).

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against based on `repository_owner` (derived from the payload's `organization.login` for membership events), and only proves that the request truly came from *that* organization's GitHub App: [1](#0-0) [2](#0-1) 

That authentication only proves *which organization* sent the event — it says nothing about which `Team` row the payload is allowed to mutate. `MembershipHandler#process` then resolves the target team purely by GitHub's global numeric `team.id`: [3](#0-2) 

`Team.find_or_create_by!(github_id: params.team.id)` performs no scoping by `organization` — the `organization = params.organization.login` assignment only runs inside the `find_or_create_by!` block, i.e. only on *creation*. If a `Team` row with that `github_id` already exists (e.g. the authorization team configured via `Shipit.github_teams`), the existing row is looked up and reused as-is, and `team.add_member(member)` is called on it regardless of which organization actually sent the webhook.

`Shipit.github_teams` — the list of teams that gate access to the whole application — is built from a single, specific organization's OAuth config: [4](#0-3) 

and a user's authorization is a direct membership check against those teams: [5](#0-4) 

which gates access at the controller layer: [6](#0-5) 

In a multi-organization Shipit deployment (explicitly supported, see `docs/setup.md` "Using Multiple Github Applications"), each connected organization has its own webhook secret, and `Shipit.github(organization:)` correctly verifies each organization's own signature: [7](#0-6) 

An unprivileged Shipit user who is merely an owner/admin of one of these *other*, less-trusted connected organizations can trigger a genuine, correctly-signed `membership` webhook from *their own* organization whose `team.id` collides with the `github_id` of the privileged authorization `Team` already registered from the primary organization. Because `find_or_create_team!` never re-validates `params.organization.login` against the existing row's `organization`, `MembershipHandler` will add that attacker-controlled `member.login` as a member of the privileged team.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization (an explicitly listed High-severity impact): an identity that is authenticated only as a member of an unrelated, lower-trust GitHub organization ends up being recorded as a member of the team that `User#authorized?` checks, granting full authenticated access to the Shipit UI/deploy application meant to be restricted to the primary organization's team.

### Likelihood Explanation
Exploitation requires (a) a multi-organization Shipit deployment where the attacker legitimately administers one of the connected-but-untrusted organizations, and (b) the numeric `team.id` of a newly created team in that organization to match the `github_id` of the target privileged team (GitHub team ids are sequential/global, making this a matter of enumeration/timing rather than a hard cryptographic barrier). This is a real code defect independent of the ID-collision difficulty — the missing organization check applies to every existing `Team` row, not just the authorization team — but the practical difficulty of engineering an exact `github_id` match makes likelihood moderate rather than trivial.

### Recommendation
When handling the `membership` webhook, resolve/update the `Team` scoped by both `github_id` and `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and treat a `github_id` match with a different stored `organization` as an error/no-op rather than silently reusing the existing row.

### Proof of Concept
1. Deploy Shipit with `github.oauth.teams: ["primaryorg/security-team"]`, using the multi-organization `github:` config (`docs/setup.md`), plus a second connected organization `otherorg` (webhook + app configured, e.g. for a different internal team's stacks).
2. `Shipit.github_teams` creates a `Team` row for `primaryorg/security-team` with its real GitHub `github_id` (e.g. `555`).
3. Attacker, an owner of `otherorg` (no privileges in `primaryorg` or Shipit), repeatedly creates/deletes teams in `otherorg` until GitHub assigns a new team the numeric id `555` (sequential id collision), then adds themself to that team.
4. GitHub sends a legitimately-signed `membership` (`action: added`) webhook for `otherorg`; `WebhooksController#verify_signature` validates it correctly against `otherorg`'s own webhook secret.
5. `MembershipHandler#process` calls `Team.find_or_create_by!(github_id: 555)`, finds the existing `primaryorg/security-team` row, and calls `team.add_member(attacker_user)`.
6. Attacker logs into Shipit via normal GitHub OAuth; `User#authorized?` now returns true because they are a member of a team in `Shipit.github_teams`, granting full access to `primaryorg`'s Shipit instance.

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
