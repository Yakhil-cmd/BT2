### Title
Webhook signature scope confused with acted-upon repository field allows forged GitHub events to be accepted for another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The vulnerability class in the reference finding is a delegation binding that is never fully cleared/validated, letting an attacker present one identity to authorization logic while a different identity is actually acted upon, multiplying trust. The same class of bug appears in Shipit's webhook trust boundary: the field used to select *which* organization's secret verifies the HMAC signature is not the same field used to select *which repository/stack* the verified webhook is applied to, even though both come from the same attacker-supplied, unauthenticated JSON body.

### Finding Description
`WebhooksController#verify_signature` derives the organization used for signature verification exclusively from the payload itself: [1](#0-0) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

It then fetches `Shipit.github(organization: repository_owner)` and verifies the raw body against **that org's** `webhook_secret`: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when the resolved organization has no `webhook_secret` configured — a state explicitly documented as optional/`nil` by default (`docs/setup.md` and `config/secrets.development.example.yml`), and used in Shipit's supported multi-organization configuration schema (`config/secrets.development.shopify.yml`, `Shipit.github_app_config`).

Downstream, once `verified` is truthy, the raw, still-attacker-controlled `params` are dispatched to handlers, which resolve the actual repository/stack from a **different** field of the same payload: [4](#0-3) 

```
def repository_name
  payload.dig('repository', 'full_name')
end
```

Nothing in the request enforces that `repository.owner.login` (used to pick the verifying secret) matches the owner segment of `repository.full_name` (used to pick the actually-affected `Repository`/`Stack` via `Repository.from_github_repo_name`). Both are independent, attacker-controlled keys inside the same unauthenticated JSON body.

The binding that should hold is:
```
organization used to verify signature == organization that owns the repository the handler mutates
```
Before the attack this equality is assumed to hold because GitHub always produces internally-consistent payloads. After a forged request, an attacker can set them to different organizations, breaking the binding while the request still passes `verify_signature`.

### Impact Explanation
In any Shipit deployment using the documented multi-organization `github:` config (`docs/setup.md` "Using Multiple Github Applications"), if even one configured organization is left with `webhook_secret: nil` (explicitly presented as optional in the docs and templates), an attacker can:
1. Set `repository.owner.login` (or `organization.login`) to the name of the organization that has no `webhook_secret` configured, causing `verify_webhook_signature` to short-circuit to `true` with no signature required at all.
2. Set `repository.full_name` in the same JSON body to `<protected-org>/<target-repo>`, i.e. a real repository under a different, secret-protected organization.
3. Send this as an unauthenticated POST to `/webhooks` with an arbitrary `X-Github-Event` header (e.g. `push`, `status`, `check_suite`).

Because the handler dispatch uses only `repository.full_name` (via `Repository.from_github_repo_name`) to resolve the target `Stack`, the forged, unsigned event is processed as if it legitimately originated from GitHub for the protected repository — e.g. queuing `GithubSyncJob` for that stack, injecting fabricated commit `Status` records, or manipulating check-run/merge state that gates automatic deploys and the merge queue. This is a genuine authentication-bypass on the webhook trust boundary and can be leveraged into an unauthorized deploy/merge by faking passing CI/status signals for a target repository's stack, without ever possessing that organization's webhook secret.

### Likelihood Explanation
This requires the operator to run the documented multi-org configuration and to have at least one org without a `webhook_secret` (explicitly allowed/optional per `docs/setup.md` and the config templates), which is a realistic, documented deployment shape rather than a hypothetical misconfiguration invented by the attacker. No credentials, GitHub access, or Shipit session are required — the endpoint is `ActionController::Base` with authenticity token verification skipped and reachable pre-authentication.

### Recommendation
Bind the organization used to verify the signature to the same repository object that is subsequently acted upon, e.g. derive both the verifying organization and the acted-upon repository from a single, unambiguous canonical field (or re-derive `repository_owner` after verification from the exact same nested object used by `Handler#repository_name`, and reject if they diverge). Additionally, do not treat "no `webhook_secret` configured" as "signature verification passes" — instead reject (422) webhooks for repositories whose resolved owner has no secret configured, or require all organizations in a multi-org config to have a secret set.

### Proof of Concept
1. Deploy Shipit with a multi-org `github:` config where `orgWithoutSecret` has `webhook_secret: nil` and `orgWithSecret` has a real repository/stack tracked in Shipit.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {
    "owner": { "login": "orgWithoutSecret" },
    "full_name": "orgWithSecret/target-repo"
  },
  "sha": "<commit-sha-of-target-stack>",
  "state": "success",
  "context": "ci/required-check",
  "branches": [{"name": "master"}]
}
```
No `X-Hub-Signature` header is required. `verify_signature` resolves `Shipit.github(organization: "orgWithoutSecret")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally.
3. `StatusHandler` (invoked via `Shipit::Webhooks.for_event('status')`) resolves the stack from `repository.full_name` = `orgWithSecret/target-repo` and creates/updates a `Status` for the given `sha`, as confirmed by the existing test pattern in [5](#0-4) , which shows a forged `status` payload directly creating a `Status` on a real commit once signature verification passes.

*(Note: exact contents of `status_handler.rb`/`push_handler.rb`/`repository.rb` could not be retrieved due to a tool error in the final iteration; the causal chain is reconstructed from `handler.rb`'s `repository_name` method and the corroborating webhook controller test, which is sufficient to establish the root cause but should be re-verified by reading those files directly.)*

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
