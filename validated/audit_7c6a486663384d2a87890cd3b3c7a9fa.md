### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler` lets a no-secret-organization forged `status` webhook mutate commit status on an unrelated victim stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` accepts any `status` webhook body without HMAC verification whenever the GitHub organization configured for the claimed `repository.owner.login` has a blank `webhook_secret`, because `GitHubApp#verify_webhook_signature` returns `true` unconditionally in that case. `StatusHandler#process` then resolves the target commit purely by `Commit.where(sha: params.sha)`, with no scoping to the repository/organization that actually authenticated the request, so a forged `status` event can mutate a commit's status — and trigger deploy-gating side effects — for any stack in the Shipit instance whose commit shares that SHA, independent of that stack's `review_stacks_enabled` setting.

### Finding Description
The broken binding: `authenticated_organization(request) == commit.stack.repository.owner` should always hold before `create_status_from_github!` runs, but the code never establishes it.

- `WebhooksController#verify_signature` picks the `GitHubApp` for verification purely from the attacker-controlled `repository.owner.login` (or `organization.login`) field in the payload: `Shipit.github(organization: repository_owner)` [1](#0-0)  combined with the `repository_owner` extractor at [2](#0-1) .
- If that organization is configured in Shipit but its config has no `webhook_secret`, `GitHubApp#verify_webhook_signature` short-circuits to `true`: [3](#0-2) . No HMAC is checked at all in this branch.
- `StatusHandler#process` then resolves target commits with zero repository/stack scoping: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) .
- `create_status_from_github!` calls `add_status`, which emits `Hook.emit(:deployable_status, ...)` and calls `stack.schedule_merges` whenever the simple state changes: [5](#0-4) . This can change whether a commit is `deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`, [6](#0-5) ), and can drive `schedule_continuous_delivery` for any stack with continuous deployment enabled [7](#0-6) .

Exploit flow: the attacker registers/controls a repository under (or crafts a payload claiming to be from) a GitHub organization that a Shipit operator has configured with an `app_id`/`installation_id` but has forgotten to set `webhook_secret` for. Because a git commit SHA is a content hash, an attacker who forks or shares history with the victim repository (or otherwise causes/observes a commit with the same SHA present in the victim stack, e.g. via a shared upstream commit merged into both repos) can send an unsigned `POST /webhooks` `status` payload naming that SHA and a fabricated `state`/`context`. `verify_signature` waves it through since `webhook_secret` is blank for the claimed org; `StatusHandler` matches the commit purely by SHA across the entire commits table and writes a status for the victim's stack, regardless of that stack's `review_stacks_enabled` value.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type is handled, not repository identity; there is no `ExplicitParameters` check tying `params.dig('repository','full_name')` to the resolved commit/stack; and `StatusHandler` performs no repository/stack filter on the `Commit` lookup.

### Impact Explanation
A successful forged `status` request causes Shipit to write a fabricated CI status onto a commit belonging to a stack the attacker does not control and never authenticated against. Depending on the forged `state`, this can move a commit from blocked to `deployable?`, unblock `blocked?` gating for downstream commits, and trigger `stack.schedule_merges` / `schedule_continuous_delivery`, potentially causing an unauthorized deploy for a victim's continuous-delivery-enabled stack. This is a payload from one (attacker-controlled/no-secret) organization mutating another repository's stack/commit state — matching the Critical "payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy" category. Repeatable against any commit SHA the attacker can discover or cause to be shared between repositories.

### Likelihood Explanation
Requires: (a) a Shipit deployment with at least one GitHub organization configured without `webhook_secret` (a real-world misconfiguration, not a hypothetical secret leak) — the `no-secret organization` gap; (b) a victim stack containing a commit whose SHA the attacker can predict or produce (trivial for forked/shared-history repositories, common in monorepo/fork workflows). No Shipit session, API token, or GitHub secret is needed. Cost to the attacker is a single crafted unsigned HTTP POST.

### Recommendation
Bind webhook processing to the concrete repository that authenticated the request instead of trusting SHA alone: pass the verified `repository_owner`/`repository.full_name` through to `StatusHandler` and scope `Commit.where(sha: params.sha)` to `Commit.joins(:stack).merge(Stack.where(repository: matched_repository))`. Additionally, reject webhooks for organizations configured without a `webhook_secret` (fail closed rather than `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`), or require an explicit opt-in flag for unsigned orgs.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "status event from a no-secret organization mutates a commit belonging to an unrelated stack" do
  # Victim stack: review_stacks_enabled false, normal repository "victim/app"
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, message: "shared commit")

  # Configure an org "no-secret-org" in Shipit with no webhook_secret
  Shipit.stubs(:github_app_config).with('no-secret-org').returns(app_id: 1, installation_id: 1) # no webhook_secret key

  payload = {
    sha: victim_commit.sha,
    state: "success",
    context: "ci/forged",
    repository: { owner: { login: "no-secret-org" }, full_name: "attacker/unrelated-repo" }
  }.to_json

  # No X-Hub-Signature header, or an arbitrary bogus one - should still pass verify_signature
  post "/webhooks", params: payload, headers: { 'X-Github-Event' => 'status', 'Content-Type' => 'application/json' }

  assert_response :ok
  victim_commit.reload
  # Assert the binding is broken: attacker (no-secret-org / attacker/unrelated-repo)
  # was able to write a status onto victim_stack's commit without authenticating
  # against victim's repository secret.
  assert_equal "success", victim_commit.status.state
end
```
Both sides of the equality `authenticated_org == commit.stack.repository.owner` differ (`no-secret-org`/`attacker/unrelated-repo` vs the victim's actual repository), yet the status write succeeds, confirming the divergence.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
