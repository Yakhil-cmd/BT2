This confirms the multi-organization deployment mode: `Shipit.github(organization:)` supports per-organization config with distinct `webhook_secret` values keyed by GitHub org name in `secrets.github` [1](#0-0) . This is the analog to the Solana rent-misallocation bug: one field (`repository.owner.login`) is used to select and authenticate *which* secret validates the signature, while a *different* field (`repository.full_name`) determines what gets written — and nothing binds the two together beyond both appearing in the same signed byte string.

### Title
Webhook organization-selected signing secret is not bound to the repository field that handlers act on, allowing cross-organization stack forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate the raw payload against based on `repository.owner.login` (falling back to `organization.login`) via `Shipit.github(organization: repository_owner)` [2](#0-1) . Each onboarded GitHub organization can have its own independent `webhook_secret` in `secrets.github`, resolved by `Shipit.github_app_config(organization)` [3](#0-2) . Once the signature check passes, every webhook handler (e.g. `PushHandler`) resolves the actual repository/stack to mutate using a *separate* field, `payload.dig('repository', 'full_name')`, via `Handler#repository_name` and `Handler#stacks` [4](#0-3) .

### Finding Description
The equality that should hold is:
`organization whose secret authenticated the request == owner of the repository the handler writes to`

Both `repository.owner.login` and `repository.full_name` live inside the same JSON body, but they are independent, attacker-controllable strings inside that body. The HMAC only proves "whoever holds organization X's `webhook_secret` produced this exact byte string" — it does not constrain which repository name appears inside that byte string. In a multi-tenant Shipit deployment (the `github_app_config(organization)` / `secrets.github` keyed-by-org mode [3](#0-2) ), any actor who legitimately controls a repository/organization onboarded to Shipit — and can therefore get GitHub to deliver (or replay) a webhook signed with *their own* organization's `webhook_secret` — can set `repository.full_name` inside that same delivery to point at a *different* onboarded repository/stack. `verify_signature` will validate successfully because it only checks the org derived from `repository.owner.login`/`organization.login` against its own secret [5](#0-4) , while `PushHandler#process` and `Handler#stacks` resolve and mutate the stack belonging to whatever `repository.full_name` says [6](#0-5) [4](#0-3) .

This is exactly analogous to the reported bug class: a field that is acted upon (`close`/here `repository.full_name`) is never checked against the field that was actually verified/authorized (the signer/here `repository.owner.login` used for secret selection).

### Impact Explanation
This crosses the "cross-repository writes" boundary listed as Critical impact. An organization admin/repo owner in org A (with a legitimate, low-privilege Shipit onboarding of their own repo) could forge `push`/`status`/`check_suite` events that are validated with org A's secret but whose `repository.full_name` claims to be a stack belonging to org B, causing `GithubSyncJob`/`sync_github` to run against org B's stack, corrupt commit/status state, or influence deploy eligibility for a repository the attacker does not control — without ever needing org B's webhook secret.

### Likelihood Explanation
Requires the deployment to run in the multi-organization config mode (`secrets.github` keyed by organization) and requires the attacker to control at least one legitimately onboarded organization/repository so GitHub will sign a webhook with a secret the attacker can leverage (either by controlling delivery content directly through GitHub's UI features like custom payloads/replays, or by any mechanism that lets them influence the `repository` sub-object of an event fired for their own repo). This is plausible but conditional on the multi-tenant configuration and on the attacker being able to shape the `repository` payload fields independently of GitHub's normal repo-name population — which I could not fully verify from the in-scope code alone (GitHub controls webhook payload construction; the risk is highest for custom/internal event replays or a compromised/renamed-repo scenario feeding `refresh_repository!`-style resyncs). This uncertainty should be validated further, ideally with a live Devin session able to trace how GitHub populates `repository.full_name` vs `repository.owner.login` in delivered payloads and whether any of the in-scope handlers or `GithubSyncJob` allow the two to diverge in practice.

### Recommendation
In `WebhooksController#verify_signature`, and/or in `Handler#stacks`/`Handler#repository_name`, enforce that the organization used to select/verify the signing secret matches the owner segment of `repository.full_name` (i.e., derive both values from the same, single trusted field, or explicitly assert `repository.full_name.split('/').first.casecmp(repository_owner) == 0` before dispatching to handlers). Reject the webhook if they diverge.

### Proof of Concept
1. Deploy Shipit in multi-org mode with `secrets.github` containing separate entries (and `webhook_secret`s) for `org-a` and `org-b`, each with a stack onboarded (`org-a/repo-a`, `org-b/repo-b`).
2. As an attacker who controls `org-a/repo-a`, arrange for (or replay) a webhook event whose JSON body has `organization.login`/`repository.owner.login = "org-a"` but `repository.full_name = "org-b/repo-b"`, signed with `org-a`'s `webhook_secret`.
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "org-a")` and validates the HMAC successfully [5](#0-4) .
4. `PushHandler#process` (or other handlers) resolve `Repository.from_github_repo_name("org-b/repo-b")` via `Handler#stacks` and act on `org-b`'s stack [4](#0-3) [6](#0-5) , despite the request never being authenticated against `org-b`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
