### Title
Indirect (introduced) correspondents are treated as fully-paired devices — commented-out trust check lets an unpaired cosigner reach signing/wallet operations - ([File: wallet.js])

### Summary
The OpenClaw bug class is: a weak, cheaply-forgeable trust signal (network locality during Control UI pairing) was accepted as if it conferred full pairing trust, letting an attacker mint a durable admin device token. The direct analog in ocore's wallet/device layer is that a weak trust signal — being merely *introduced* as an "indirect correspondent" by a legitimate correspondent (never having actually completed device pairing) — is treated by `handleMessageFromHub` as fully equivalent to a directly paired device, because the restriction meant to limit indirect correspondents to a safe subset of message subjects is commented out.

### Finding Description
`device.js` maintains two correspondent trust levels: directly paired devices (`is_indirect=0`, added only through `handlePairingMessage` after a real pairing-secret exchange) and indirectly known devices (`is_indirect=1`, added via `addIndirectCorrespondents`) [1](#0-0) . Indirect correspondents are added purely from data supplied by *another* correspondent (`arrOtherCosigners`, containing `device_address`, `hub`, `pubkey`, `name` for cosigners of a shared address) — the introduced device itself never proves possession of its permanent key to us via pairing.

In `wallet.js`, `handleMessageFromHub` receives a `bIndirectCorrespondent` flag (set by `device.js`'s `hub/message` handler at [2](#0-1)  based on `correspondent_devices.is_indirect`), and the code that was supposed to restrict indirect correspondents to only a small safe set of subjects is disabled:

```
//if (bIndirectCorrespondent && ["cancel_new_wallet", "my_xpubkey", "new_wallet_address"].indexOf(subject) === -1)
//    return callbacks.ifError("you're indirect correspondent, cannot trust "+subject+" from you");
``` [3](#0-2) 

Because this check is commented out, any subject in the large `switch(subject)` block — `sign`, `new_shared_address`, `approve_new_shared_address`, `create_new_shared_address`, `removed_paired_device`, etc. — is dispatched identically regardless of whether the sender is a directly-paired device or merely an indirectly-introduced one [4](#0-3) .

The `sign` handler in particular only checks that the claimed signer address is among `other_device_addresses` for a shared address, and that the `from_address` is listed as a cosigner — it does not require that the requester be a directly paired (trust-verified) device: [5](#0-4) 

Thus, an entity that a legitimate correspondent introduces as a cosigner (e.g. as part of `new_shared_address` propagation) becomes a persistent row in `correspondent_devices` with `is_indirect=1`, and from then on can send this node `sign` requests, shared-address approval/creation/rejection messages, and other wallet-management subjects exactly as if it had gone through genuine pairing — mirroring the OpenClaw flaw where a locality signal was accepted as equivalent to a pairing-verified identity, producing a durable elevated trust relationship (the `correspondent_devices` row persists like a "device token" until manually removed).

### Impact Explanation
An indirect correspondent that was never actually paired can:
- Send `sign` requests for a shared/multisig address it is (or claims via cosigner data introduced by another party) associated with, triggering local signing UI/flows on the victim's wallet for shared addresses, potentially leading the victim to co-sign fraudulent transactions/spend from a shared address.
- Send `new_shared_address`, `approve_new_shared_address`, `create_new_shared_address` and other structural messages that affect what addresses the wallet considers as shared/multisig, affecting fund custody logic.
- Send `removed_paired_device` (subject to the `determineIfDeviceCanBeRemoved` gate) and other operational subjects that were intentionally excluded from the trusted subset for indirect peers.

This elevates an introduction-only relationship into full wallet-message trust, which can contribute to unauthorized signing requests / manipulation of shared-address bookkeeping — a concrete path toward unauthorized-spending-adjacent behavior in multisig/shared-address flows, matching this program's required "concrete unauthorized spending ... AA fund loss" bar when the victim is coaxed into co-signing.

### Likelihood Explanation
Reaching this requires that the victim already has at least one legitimate correspondent who introduces the attacker as a co-signer of a shared address (a normal, expected step in ocore's shared-address workflow) — i.e., reachable by a paired device or an AA/shared-address counterparty, not an arbitrary unauthenticated party. This matches the "paired device" reachability class permitted by the rules. Given that shared-address setups routinely exchange cosigner lists, the introduction step is not adversarial by itself; the vulnerability is that this weak, one-sided introduction is enough, since the intended stronger check was disabled.

### Recommendation
Re-enable and correctly enforce the indirect-correspondent subject whitelist in `handleMessageFromHub`, ensuring subjects such as `sign`, `new_shared_address`, `approve_new_shared_address`, `create_new_shared_address`, and `removed_paired_device` are rejected (or require additional verification) from correspondents with `is_indirect=1`, restoring the original intent expressed by the commented-out check at `wallet.js:92-93`.

### Proof of Concept
1. Victim device V is a genuine correspondent of device A (paired normally).
2. A creates or forwards a shared-address setup listing device B (attacker) as a cosigner via `new_shared_address`/cosigner metadata; V calls `device.addIndirectCorrespondents`, inserting B into `correspondent_devices` with `is_indirect=1` and B's self-reported `pubkey`/`hub` [1](#0-0) .
3. B (never having paired with V) now sends V a `hub/message` with `subject: "sign"` for the shared address, using its own permanent device key to sign the message (satisfying `hub/message`'s signature checks in `device.js`).
4. `device.js`'s `correspondent_devices` lookup finds B known (`is_indirect=1`) and calls `handleMessage(rows[0].is_indirect)` → `bIndirectCorrespondent=true` [2](#0-1) .
5. `wallet.js handleMessageFromHub` receives `bIndirectCorrespondent=true` but the whitelist check is commented out, so the `sign` case is processed identically to a fully-paired cosigner, prompting V with a signing request as if B were a trusted party [3](#0-2) [5](#0-4) .
