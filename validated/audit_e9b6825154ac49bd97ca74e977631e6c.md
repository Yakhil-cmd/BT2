### Title
Webhook signature is verified against `repository.owner.login` while all event handlers act on the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `params.dig('repository','owner','login')`, but every webhook handler (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, `Handler#repository_name`) resolves the target `Stack`/`Repository` from the independent `repository.full_name` field of the same payload. Nothing ties these two fields together, so a payload can be "authenticated" for one organization while acting on a repository belonging to a different organization.

### Finding Description
`verify_signature` picks the GitHub App config to validate the signature using only the `owner.login` sub-field: [1](#0-0) [2](#0-1) 

Every downstream handler, however, resolves the actual repository/stack to mutate using a completely different field, `repository.full_name`: [3](#0-2) [4](#0-3) [5](#0-4) 

Crucially, `GitHubApp#verify_webhook_signature` short-circuits to `true` when the selected organization's `webhook_secret` is blank/unconfigured (an explicitly documented "optional" setting): [6](#0-5) [7](#0-6) 

In a multi-organization Shipit deployment (supported per `Shipit.github_app_config`/`Shipit.github_organizations`, exercised in `test/dummy/config/secrets_double_github_app.yml`), it is entirely possible for one configured organization to have no `webhook_secret` set while another (the "victim" org) does. An unprivileged attacker who knows (or guesses) the name of the no-secret organization can POST directly to `/webhooks` with:
- `repository.owner.login` = the no-secret organization (so `verify_signature` looks up that org's `GitHubApp`, whose `verify_webhook_signature` trivially returns `true` regardless of the `X-Hub-Signature` header),
- `repository.full_name` = `victim-org/victim-repo` (so the handler locates and mutates the victim org's `Stack`).

This breaks the equality the deployment implicitly relies on: *the organization whose credentials authenticated the request* must equal *the organization whose repository is acted upon*. Here, the "authenticated" org (no-secret org) and the "written" repository's org (victim org, protected by its own real webhook secret) are never checked against each other.

### Impact Explanation
Depending on event type, this allows an attacker with no session, no API token, and no repository access to:
- Force `PushHandler` to enqueue `GithubSyncJob` for the victim's stack with an attacker-chosen `expected_head_sha`, triggering re-fetch/sync of the victim's deploy pipeline: [8](#0-7) [9](#0-8) 
- Inject arbitrary commit statuses via `StatusHandler#process` on the victim's commits: [10](#0-9) 
- Archive/unarchive review stacks belonging to the victim's repository via `PullRequest::*Handler` / `ReviewStackAdapter`, including re-provisioning: [11](#0-10) 

This effectively grants cross-organization/cross-repository write access to Shipit's internal state for the victim repository/stack without possessing the victim's webhook secret — matching the "cross-repository writes" Critical-impact category, since the trust boundary broken is precisely "organization authenticated" vs. "repository written."

### Likelihood Explanation
Requires: (a) the Shipit instance to host more than one GitHub organization (a documented, supported configuration), and (b) at least one configured organization to have no `webhook_secret` set (explicitly documented as "optional"). Both are realistic operational states, not implementation bugs unique to a single misconfiguration; the vulnerability is that the code never cross-validates `owner.login` against `full_name`'s owner segment, so this condition is directly exploitable by an unauthenticated network attacker who can enumerate/guess the no-secret org's name (e.g., via public GitHub App installation lists) and knows/guesses a victim repo's `full_name` in the same Shipit instance.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), validate that `repository.full_name`'s owner segment matches `repository.owner.login` (or `organization.login`) before dispatching to any handler, and reject the payload if they differ. Additionally, consider requiring `webhook_secret` to be mandatory for all configured GitHub organizations, removing the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, e.g. `OrgA` (no `webhook_secret`) and `OrgB` (has a real `webhook_secret`), similar to `test/dummy/config/secrets_double_github_app.yml`.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefattackerchosen",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
No valid `X-Hub-Signature` is required because `Shipit.github(organization: "OrgA").verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank) at [12](#0-11) .
3. `WebhooksController#create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` (from `repository.full_name`) at [3](#0-2)  and enqueues `GithubSyncJob` for the victim's stack with the attacker-supplied `expected_head_sha`, despite the request never having been authenticated for `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
