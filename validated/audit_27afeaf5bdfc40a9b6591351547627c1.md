### Title
Attacker-pinned utilization permanently blocks all supplier withdrawals in a market - (File: contracts/pool/src/guards.rs)

### Summary
The pool applies `require_utilization_below_max` as a post-state guard to non-liquidation withdrawals in `contracts/pool/src/ops/withdraw.rs::gate_and_debit` [1](#0-0) . Burning supply shares lowers the denominator, so the check uses the post-burn state: once `borrowed / supplied` reaches `max_utilization`, every withdrawal of any size reverts with `UtilizationAboveMax` (127) [2](#0-1) . An unprivileged borrower can push utilization exactly to the cap with `borrow` (the guard admits `<=`), and then millisecond interest accrual in `global_sync` pushes `borrowed` above the cap on every subsequent touch, so the freeze persists and deepens without further attacker action [3](#0-2) .

### Finding Description
The bug class from CVE-2020-14765 is a low-privilege, network-reachable denial of service. The analog here is a single unprivileged address freezing an entire market's exits:

1. Attacker supplies collateral and calls controller `borrow` repeatedly until `borrowed.div_ceil(supplied) == max_utilization`. The check `borrowed.div_ceil(env, supplied) <= max_utilization` admits equality [4](#0-3) .
2. Every later `withdraw` first runs `interest::global_sync`, which grows `borrowed` via the borrow index, so utilization lands strictly above the cap.
3. `gate_and_debit` runs `require_utilization_below_max` after `burn_supply`, which only decreases `supplied`, so no withdrawal size can ever satisfy the guard — it reverts for dust and full withdrawals alike.
4. The freeze releases only if (a) someone repays the attacker's debt, (b) liquidation consumes the leftover (but liquidation withdraws skip the guard only for the seized leg and require the attacker's HF < 1, which the attacker avoids by keeping the position healthy), or (c) the attacker chooses to repay.

Note the docs describe this guard as an "absolute post-state test" and acknowledge "once utilization reaches the cap no withdrawal of any size passes, and interest accrual alone pushes it there" [5](#0-4)  — but the documented text describes it as a passive consequence, whereas an attacker can deliberately induce and indefinitely maintain this state against other users' funds.

### Impact Explanation
Temporary freezing of funds: all suppliers in the affected (hub, token) market are unable to withdraw any amount while utilization is pinned at or above the cap. The attacker controls duration by maintaining a healthy borrow and never repaying; accrual keeps utilization above the cap even as positions are liquidated elsewhere. Suppliers' funds are not stolen but are locked for an attacker-controlled duration.

### Likelihood Explanation
Reachable by any unprivileged address via ordinary `supply` + `borrow` calls; requires enough capital to borrow the market up to `max_utilization` on the attacker's own collateral, and the attacker pays borrow interest for the duration. No oracle manipulation, no privileged role, no timing requirement beyond reaching the cap boundary. Medium: capital cost and interest expense bound the griefing duration, and repayment or liquidation of the attacker's debt ends the state.

### Recommendation
Do not apply the utilization ceiling to exits, or apply it only to the pre-burn state with a strictly-greater comparison so that a withdrawal that reduces utilization is always admitted. Alternatively, exempt withdrawals that reduce utilization (compare post-burn utilization against pre-burn utilization rather than against `max_utilization`) in `gate_and_debit`.

### Proof of Concept
1. Attacker supplies large collateral in market A, borrows token B via controller `borrow` until `borrowed_B / supplied_B == max_utilization_B` exactly.
2. Any supplier's `withdraw` on market B reverts `UtilizationAboveMax` after `global_sync` accrues interest and `burn_supply` shrinks `supplied`.
3. Attacker tops up collateral to keep HF ≥ 1 so no liquidation can consume the debt; every subsequent withdrawal attempt reverts until the attacker repays.

```rust
pub(crate) fn require_utilization_below_max(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO || cache.params().max_utilization >= Ray::ONE {
        return;
    }

    let borrowed = cache.borrowed().mul_ceil(env, cache.borrow_index());
    if borrowed == Ray::ZERO {
        return;
    }
    let supplied = cache.supplied().mul_floor(env, cache.supply_index());
    assert_with_error!(
        env,
        supplied > Ray::ZERO && borrowed.div_ceil(env, supplied) <= cache.params().max_utilization,
        CollateralError::UtilizationAboveMax
    );
}
```
