### Title
Per-delegator clamp in `calculate_block_reward` fails to enforce a shared vote-account budget, allowing sum of block rewards to exceed `pending_delegator_rewards` - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`calculate_block_reward` computes each stake account's share of a vote account's `pending_delegator_rewards` proportionally to `stake / total_active_stake`, then clamps the *individual* result to `pending_delegator_rewards`. Because this clamp is applied independently per stake account rather than against a shared, decreasing budget for the vote account, multiple delegators of the same vote account can each be clamped up to the full `pending_delegator_rewards`, letting the sum distributed across all of a vote account's delegators exceed the vote account's actual pending pool.

### Finding Description
`calculate_block_reward` looks up `total_active_stake` from `reward_epoch_delegated_stakes` (a snapshot fixed at the end of the reward epoch) and computes `stake` via `delegation_effective_stake` at `rewarded_epoch` [1](#0-0) . The code's own comment acknowledges the exact scenario in the question: during recalculation, a stake account that already received rewards can end up with `stake > total_active_stake`, and the resulting `u128` product `pending_delegator_rewards * stake / total_active_stake` can exceed `pending_delegator_rewards` [2](#0-1) .

The mitigation is `.min(pending_delegator_rewards)` applied to a *single* delegator's computed reward. This function is invoked independently, in parallel, once per stake delegation via `calculate_stake_rewards_and_commissions`'s `par_iter()` over `stake_delegations`, with no shared/mutable running total subtracted from `pending_delegator_rewards` as rewards are assigned to earlier delegators [3](#0-2) . Consequently, if the `stake > total_active_stake` condition is triggered for two or more distinct stake accounts delegated to the same vote account (e.g., because the attacker controls multiple stake accounts delegated to the same vote pubkey, and a recalculation event causes each of their `delegation_effective_stake` values to appear inflated relative to the frozen `total_active_stake` snapshot), each independent computation can be clamped up to the *full* `pending_delegator_rewards` value. The sum of `block_reward` fields written into `PartitionedStakeReward` for that vote account's delegators can therefore exceed the vote account's single `pending_delegator_rewards` pool, violating value conservation.

The existing per-entry `.min(pending_delegator_rewards)` clamp only prevents a single delegator's reward from exceeding the total pool; it does not prevent multiple delegators from each independently claiming up to that same total, because there is no cross-delegator accounting or reduction of the pool as it's consumed within this parallel computation.

### Impact Explanation
This falls under lamport minting / reward over-distribution: if multiple `PartitionedStakeReward.block_reward` values for delegators of the same vote account each approach `pending_delegator_rewards`, the sum distributed and later deducted from the vote account's balance can exceed what the vote account actually holds/was allotted, resulting in minted lamports beyond the intended inflation/reward schedule for that vote account. This matches the "value-conservation" invariant explicitly named in the audit question.

### Likelihood Explanation
This requires the recalculation path where `stake` (delegation effective stake at `rewarded_epoch`) diverges from the frozen `total_active_stake` snapshot — a condition the source code comments describe as a real occurrence during recalculation (e.g. after skip-slot/reorg driven reward recomputation), not a purely hypothetical one [4](#0-3) . An attacker only needs ordinary permissions to create and delegate multiple stake accounts to the same (their own or a victim's) vote account, requiring no validator/leader control. However, triggering the specific recalculation divergence deterministically (exact reorg/skip-slot timing) requires precise control over epoch-boundary reprocessing, which is a cluster-level condition rather than something achievable via a single instruction; this reduces — but does not eliminate — practical repeatability.

### Recommendation
Track a shared, mutable remaining-budget for `pending_delegator_rewards` per vote account across all its delegators within `calculate_stake_rewards_and_commissions` (e.g., group stake delegations by vote account first, or use an atomic/synchronized remaining-budget counter that is fetched-and-subtracted for each computed `block_reward` before it is finalized), so that the sum of all `block_reward` values for a given vote account never exceeds that vote account's `pending_delegator_rewards`, rather than clamping each delegator's value independently against the full, un-decremented pool.

### Proof of Concept
```rust
// runtime/src/bank/partitioned_epoch_rewards/calculation.rs (test module)
//
// Simulate two delegations to the same vote account where
// delegation_effective_stake(rewarded_epoch) > total_active_stake for BOTH,
// as can occur post-recalculation, and assert value conservation fails.
#[test]
fn block_reward_sum_can_exceed_pending_delegator_rewards() {
    let pending_delegator_rewards: u64 = 1_000_000;
    let total_active_stake: u64 = 100; // frozen snapshot from end of reward epoch
    // Two delegators, each with effective stake > total_active_stake
    // (simulating post-recalculation inflated `stake` values)
    let stake_a: u64 = 1_000; // 10x total_active_stake
    let stake_b: u64 = 1_000;

    let reward_a = (pending_delegator_rewards as u128 * stake_a as u128
        / total_active_stake as u128)
        .try_into()
        .unwrap_or(u64::MAX)
        .min(pending_delegator_rewards);
    let reward_b = (pending_delegator_rewards as u128 * stake_b as u128
        / total_active_stake as u128)
        .try_into()
        .unwrap_or(u64::MAX)
        .min(pending_delegator_rewards);

    // Each individual reward is correctly clamped to pending_delegator_rewards...
    assert_eq!(reward_a, pending_delegator_rewards);
    assert_eq!(reward_b, pending_delegator_rewards);

    // ...but the sum across the vote account's delegators violates conservation.
    let total_distributed = reward_a as u128 + reward_b as u128;
    assert!(
        total_distributed > pending_delegator_rewards as u128,
        "value-conservation invariant violated: sum(block_reward) ({total_distributed}) > \
         pending_delegator_rewards ({pending_delegator_rewards})"
    );
}
```
Full integration-level PoC: construct a `Bank` with `block_revenue_sharing` and Alpenglow/MigrationEpoch active, create a victim vote account with a known `pending_delegator_rewards`, delegate two attacker-owned stake accounts to it, force a stake-rewards recalculation path (matching the one that produces the `stake > total_active_stake` comment) so both delegations report `delegation_effective_stake(rewarded_epoch) > total_active_stake`, then call `calculate_stake_rewards_and_commissions` and assert `sum(PartitionedStakeReward.block_reward for that vote account) <= pending_delegator_rewards`.
