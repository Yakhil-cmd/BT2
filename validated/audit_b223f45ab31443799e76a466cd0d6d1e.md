### Title
`register-for-bond`'s L1 path credits sats from a Bitcoin inclusion proof with no check that the timelock output is still unspent - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`verify-l1-lockups` / `validate-l1-lockup` in `pox-5.clar` credit `sats-total` purely from a Merkle-inclusion proof of a Bitcoin transaction output that matches the expected timelock script, amount, and unlock height. Nothing in the validation checks that the referenced UTXO is still unspent, nor does it check that the current burn height is still before `unlock-burn-height`. A staker can spend their matured BTC timelock on L1 and still submit the (still cryptographically valid) old inclusion proof to `register-for-bond`, getting STX-lock/bond-membership credit for sats that are no longer actually locked on Bitcoin.

### Finding Description
The claimed equality is: sats credited by `verify-l1-lockups` == sats currently locked in a confirmed, unspent Bitcoin timelock committed to `tx-sender`. Tracing `validate-l1-lockup` [1](#0-0) , the checks performed are: `unlock-burn-height >= minimum-unlock-height` (a bond parameter, not the *current* chain height), `unlock-burn-height < BITCOIN_LOCKTIME_THRESHOLD`, the output script matches `construct-lockup-output-script`, the amount matches the claimed `amount`, the outpoint is not a duplicate within the same call (`seen-outpoints`), the 80-byte header is valid (`verify-block-header`), and the Merkle proof of inclusion is valid. None of these checks queries current UTXO spend status, and none of them checks that "now" (the current burn height at the time of `register-for-bond`) is still before `unlock-burn-height`.

`register-for-bond` computes `sats-total` from this and uses it directly to determine the STX amount required and the bond membership recorded [2](#0-1) . Clarity-Bitcoin-style Merkle proofs only prove that a transaction was included in a block with a given header — they say nothing about whether the referenced output has since been spent on Bitcoin L1. Root cause: `verify-l1-lockups` treats "proof of past inclusion in a matured timelock output" as equivalent to "sats are currently locked", which is false once the timelock has matured and the owner has swept the BTC.

Attacker's exact call: an unprivileged staker who owns the Bitcoin timelock UTXO (1) waits for `unlock-burn-height` to mature, (2) spends/reclaims the BTC on Bitcoin L1 back to themselves (they are within their rights, since it's their own timelock), (3) calls `register-for-bond(bond-index, signer-manager, amount-ustx, (ok {outputs: [{...old proof...}], staker-unlock-bytes: ...}), signer-calldata)` using the original (still Merkle-valid) inclusion proof of the now-spent output. `verify-l1-lockups` returns the full `sats-total` for that already-reclaimed output, `register-for-bond` locks the corresponding STX and creates a bond membership with `is-l1-lock: true`, crediting weight for BTC that is no longer locked.

Existing guards (`verify-not-prepare-phase`, `ERR_DUPLICATE_LOCKUP_OUTPOINT` dedup, `verify-block-header`, the Merkle-proof check) only defend against duplicate submissions within a single call and forged/altered headers/tx bytes — they do not defend against a legitimately-once-locked, now-spent output being replayed as proof.

### Impact Explanation
The attacker gains STX-lock/bond-membership/reward-weight credit that is sats-based (`min-ustx-for-sats-amount sats-total ...`) without maintaining any actual BTC lock, i.e. weight/allowance exceeding real locked value. This is repeatable across multiple bonds/allowlist slots as long as the attacker (or a colluding party) has previously-matured timelock outputs and their proofs. This matches the "signing weight or reward slots exceeding locked value" High-severity category (and arguably crosses into Critical if this weight directly drives reward-sats distribution without any real backing BTC).

### Likelihood Explanation
Preconditions: the attacker must have set up a real Bitcoin timelock output matching pox-5's expected script and have it mature past `unlock-burn-height`, then be allowlisted for a bond (`protocol-bond-allowances`) — a normal precondition for using `register-for-bond` at all, not a privileged role. No prepare-phase, coordinator, or cycle-state check depends on real-time UTXO spentness. Attacker cost is just BTC transaction fees to sweep the output before registering with the stale proof. This is straightforward and fully reproducible by any staker with sBTC/STX and access to their own Bitcoin UTXOs.

### Recommendation
Require an additional, freshness-bound proof that the UTXO is still unspent at (or very near) the time of `register-for-bond` — e.g., require the burn height at proof submission to be strictly before `unlock-burn-height` (so the lock cannot have matured yet), or require a fresh SPV proof anchored close to the current burn tip plus a mechanism (e.g., a bonded challenge period or an oracle/relayer-free UTXO-set check) that can detect a spend. At minimum, enforce `current-burn-height < unlock-burn-height` at registration time so a matured (and therefore spendable) timelock cannot be used to back a bond, closing the "mature, spend, then register" window entirely.

### Proof of Concept
Rust integration test plan (extending `check_pox_5_register_for_bond_l1_lockup_lifecycle` in `stacks-node/src/tests/pox_5_integrations.rs`):
1. Fund a bondholder wallet, compute the expected P2WSH via `construct-lockup-output-script`, and send `BTC_LOCKUP_SATS` to it with `unlock-burn-height = minimum-unlock-height + 1`.
2. Mine blocks past `unlock-burn-height` so the timelock output is spendable.
3. From the bondholder wallet, spend the timelock output back to a fresh address on Bitcoin L1 (confirm the spend).
4. Using the original tx bytes/header/merkle-proof (captured before step 3), call `register-for-bond` with `(ok {outputs: [lockup], staker-unlock-bytes: ...})`.
5. Assert: the call succeeds (`is-ok` receipt), `get-bond-membership` shows `is-l1-lock: true` with the full `sats-total` credited, and the staker's STX gets locked per `min-ustx-for-sats-amount` — despite the referenced BTC output having zero balance on L1 at call time (query bitcoind UTXO set to confirm output is spent). This demonstrates `sats-total credited` != `sats currently locked and unspent on Bitcoin`, violating the stated equality.
