### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha` with no repository/stack scoping, unlike every other handler which uses `Handler#stacks` (scoped via `Repository.from_github_repo_name`). A GitHub `status` webhook that is correctly signed for repository B's organization can therefore write a `Status` onto a `Commit` belonging to stack A, as long as the SHA values collide, breaking the binding that the org verified by `verify_signature` must equal the org owning the mutated data.

### Finding Description
The broken binding, stated explicitly: `repository_owner_of(signed_payload)` (verified in `WebhooksController#verify_signature`, using `Shipit.github(organization: repository_owner)` at [1](#0-0)  ) must equal `stack.repository.owner` for every `Commit` row mutated by the request, but the code never checks this for status events.

`StatusHandler#process` does: [2](#0-1) 
`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this queries across **all stacks/repositories in the database**, not filtered by `payload['repository']['full_name']`. Contrast this with the base `Handler` class, which provides a `stacks` helper explicitly scoped by repository: [3](#0-2) 
`StatusHandler` does not use this helper at all.

`create_status_from_github!` and `add_status` then mutate the found commit regardless of which org it belongs to: [4](#0-3) [5](#0-4) 
This can flip `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`, [6](#0-5) ) for stack A purely from a signature verified against repo B's organization, and unconditionally fires `Hook.emit(:deployable_status, stack, ...)` and `stack.schedule_merges` for stack A.

**Important caveat on the deploy-trigger portion of the chain**: `schedule_continuous_delivery` is registered as `after_commit ..., on: :create` on the `Commit` model: [7](#0-6) 
This callback fires only when a `Commit` row is *created*, not when a `Status` is added to an already-existing commit via `add_status`. `add_status`/`create_status_from_github!` never call `schedule_continuous_delivery` directly. So the specific synchronous call graph claimed in the question ("`Commit#add_status` → ... → `schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later`") is **not** supported by the code as a direct chain from processing a status webhook on an existing commit — this part of the proof idea would not reproduce as literally stated in a minitest that just asserts an immediate job enqueue from `StatusHandler#process`.

What *is* fully supported and independently satisfies the Critical impact bar ("a payload for one repository mutating another's stack, commit, task or team") is that repo B's signed webhook can create a `Status` row against, and mutate the `deployable?`/`schedule_merges` state of, a `Commit` that belongs to stack A/org A, without any check that A == B.

### Impact Explanation
An attacker who controls repository B can, by crafting a commit whose SHA collides with a commit already tracked in victim stack A (feasible for shared history, cherry-picks, forks, or mirrored repositories — not requiring a cryptographic SHA-1 break), POST a `status` webhook signed with B's own valid webhook secret and have Shipit write a `Status` record onto stack A's commit, flip `deployable?` for stack A, and trigger `stack.schedule_merges` for stack A — none of which the attacker is authorized to affect. This is a cross-tenant data-integrity violation (Critical category: "a payload for one repository mutating another's stack, commit"). It is repeatable against any stack whose tracked commit SHA the attacker can reproduce in a repository they control. Whether this reliably cascades into an unauthorized `ContinuousDeliveryJob`/deploy specifically through the `after_commit on: :create` hook is not established by the traced code path; that portion of the claim is unconfirmed.

### Likelihood Explanation
Requires only: (1) an unprivileged GitHub account able to push commits to an attacker-owned repository and receive its own webhook events (default for any repo), and (2) a SHA collision between a commit the attacker controls and a commit tracked by the victim stack — achievable via forks/mirrors/shared history without needing a hash break. No Shipit credentials, session, or org membership are needed. The signature check in `verify_signature` only proves the payload came from *some* valid GitHub org, not that it's authorized for the specific commit/stack being mutated, so the check provides no protection against this specific divergence.

### Recommendation
Scope `StatusHandler#process` (and `CheckRunHandler` if it has the same pattern) to only update commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')`, mirroring the `Handler#stacks` helper, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` under `repository_owner: "victim-org"` with a `commit` of `sha: "abc123...".
2. Build a status webhook `payload` with `repository.full_name == "attacker/other-repo"`, `sha: "abc123..."`, `state: "success"`.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
4. Assert: `stack_a.commits.find_by(sha: "abc123...").statuses.exists?` is `true` and `commit.reload.deployable?` changed — i.e., a payload whose repository field is `"attacker/other-repo"` mutated a commit belonging to `"victim-org"`'s stack, proving `repository_owner_of(signed_payload) != stack.repository.owner` yet the write succeeded.
5. (Separately, and noted as unconfirmed) attempting to assert `ContinuousDeliveryJob` was enqueued directly from this call would currently fail, since `schedule_continuous_delivery` only runs on `Commit` creation, not on status addition to an existing commit — this part of the original proof idea needs revision to target the cross-tenant `Status` write itself rather than an immediate job enqueue.
