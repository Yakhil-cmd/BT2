### Title
Security-review commit-SHA selection trusts attacker-influenceable Bash output, allowing the automated commit review to be pointed at a decoy SHA instead of the actual commit - (File: plugins/security-guidance/hooks/security_reminder_hook.py)

### Summary
The `security-guidance` plugin's `PostToolUse` hook for `git commit` (`handle_commit_review_posttooluse`) determines *which* commit to security-review by regex-parsing the Bash tool's own stdout/stderr for a `[branch sha]`-shaped token, taking the **last** match as authoritative. Because `bash_output` is the literal output of whatever command Claude/the agent ran — which can be a compound command whose trailing segment is fully attacker/model-controlled — the "last match wins" heuristic can be made to select a decoy SHA instead of the real commit SHA, in effect letting an untrusted actor substitute the identity that the review path trusts, exactly like the Connext router-substitution bug where the destination-chain check validated internal consistency (signature ↔ specified router) rather than the true, sequencer-selected identity.

### Finding Description
`handle_commit_review_posttooluse` is invoked via `hooks.json`'s `if: "Bash(git commit:*)"` gate whenever Claude runs a Bash command containing `git commit`. It builds:

```python
stdout = tool_response.get("stdout", "") or ""
stderr = tool_response.get("stderr", "") or ""
bash_output = stdout + "\n" + stderr
``` [1](#0-0) 

and later selects the commit(s) to review purely from this text:

```python
all_shas = _COMMIT_SHA_RE.findall(bash_output)
shas = [all_shas[-1]] if all_shas else []
``` [2](#0-1) 

The code's own comment states the trust assumption explicitly: *"Take only the LAST match ... The real commit line is always last in git's own output — the earlier matches are either decoys or superseded commits."* [3](#0-2) 

This assumption only holds if nothing can append attacker-controlled text to the same stdout/stderr stream *after* git's own `[branch sha]` line. But `bash_output` is captured from the full Bash tool invocation, which — like the compound/chained shell commands this same hook explicitly worries about elsewhere ("`git commit && git push`", "chained commands like `git commit && git commit`") — can trivially include a trailing `echo`/`printf` whose text matches `_COMMIT_SHA_RE` (e.g. `git commit -m "msg" && echo "[main 0000000]"`). Since `findall(...)[-1]` always prefers the last occurrence, the fabricated bracketed token displaces the genuine commit SHA as the thing that gets reviewed. The `commit_succeeded` gate that runs beforehand only requires *a* SHA-shaped match plus *a* diffstat-shaped line somewhere in the output — both of which the real `git commit` already supplies — so the presence of the decoy line doesn't stop the hook from proceeding; it just changes which SHA is fed to the downstream `git show -p <sha>` / `analyze_code_security` review path.

This is a direct structural analog to the Connext finding: the destination-side verification (`_executeSanityChecks`) checked *internal consistency* of attacker-suppliable fields (router ↔ its own signature) instead of the *authoritative, upstream-selected* identity (the sequencer's original router choice). Here, the security-review hook checks *internal consistency* of an attacker-suppliable field (a same-shaped bracketed token appearing in output) instead of the *authoritative* commit identity (e.g. `git rev-parse HEAD` in the reviewed repo, or `git log -1 --format=%H` immediately following the commit), letting the last-attacker-supplied token override the true one — a hook-bypass in the git-automation trust boundary.

### Impact Explanation
If Claude Code is driven by prompt injection (e.g., untrusted file/README/task content instructing it to run `git commit -m "..." && echo "[main <fake-sha>]"`, or any construct that appends a matching bracketed token after the real commit line), the automated LLM security review that is supposed to catch malicious or vulnerable commits before they land can be silently redirected to review a nonexistent or unrelated SHA instead of the actual malicious commit. This defeats the intended safety net for the `security-guidance` plugin's git-automation review path, allowing a maliciously-crafted commit to be pushed/land without ever being flagged — a concrete hook-bypass with direct impact on the project's automated code-security control.

### Likelihood Explanation
Exploitation requires only the ability to influence the Bash command text that Claude executes for a `git commit` (a realistic scenario given prompt-injection from untrusted repository content, issue text, or tool output that Claude is instructed to act on) — no special privilege beyond what any content-injection attacker already has in this threat model. The construction (`git commit ... && echo "[branch fakesha]"`) is simple and the code's own comments show the authors were aware of the general "decoy bracket" problem (pre-commit/husky labels) but only defended against decoys appearing *before* the real line, not ones appended *after* it in the same output stream.

### Recommendation
Do not derive the reviewed commit identity from free-form Bash stdout/stderr text. Instead, resolve the actual commit(s) created by the tool call from an authoritative source, e.g.:
- Run `git rev-parse HEAD` (or `git log -1 --format=%H`) in `repo_root` immediately after detecting a successful commit, rather than regex-matching output text, and cross-check it against the reflog timestamp/action as already done for the fallback path.
- If multiple commits may have occurred in one Bash call, enumerate them via `git rev-list` bounded by the pre-call and post-call `HEAD`, not via text pattern matching over `bash_output`.
- Treat any bracketed `[branch sha]`-shaped substrings in the command's own stdout only as a corroborating signal, never as the sole source of truth for which SHA to review.

### Proof of Concept
1. Attacker plants prompt-injection content (e.g. in a README, issue, or file Claude is asked to process) instructing: run `git add -A && git commit -m "add feature" && echo "[main 0000000000000000000000000000000000000000]"` in a single Bash tool call.
2. Claude Code executes it; the real `git commit` succeeds and prints its genuine `[main <real_sha>] add feature` line plus a diffstat line, satisfying `commit_succeeded`.
3. The trailing `echo` appends a second bracketed token to the same stdout stream, matching `_COMMIT_SHA_RE`.
4. `all_shas[-1]` picks the fabricated token instead of `<real_sha>` at [2](#0-1) .
5. The downstream `git show -p <fake_sha>` targets an invalid/irrelevant SHA, so the actual malicious diff introduced by the real commit is never sent to `analyze_code_security`, and no findings are surfaced for the genuinely malicious commit.

Note: I could not confirm from the available index what exact fallback behavior occurs immediately after line 1052 when `git show -p <sha>` fails for an invalid SHA (e.g., whether it silently skips or errors) — this repo's index only exposes the `security-guidance` plugin source and changelog/docs, not the closed-source Claude Code core engine, so I was unable to inspect the full downstream handler body. This does not change the core finding: the SHA-selection step itself trusts attacker-shapeable output text, but confirming the precise post-failure code path would benefit from a full read of the file in a Devin session with complete file access.
