### Title
Cross-tenant CI status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, globally across all stacks/repositories, and writes a `Status` onto every matching `Commit` regardless of which repository/organization the verified webhook signature belongs to. Because Shipit's `commits` table only enforces uniqueness on `[sha, stack_id]` (not a global uniqueness on `sha`), the same sha can legitimately exist under multiple stacks belonging to different repositories/organizations (e.g. forks sharing ancestor commit history), so a validly-signed webhook from OrgA can mutate a commit's CI status in OrgB's stack.

### Finding Description
The broken binding: `repository_owner` (verified via `Shipit.github(organization: repository_owner).verify_webhook_signature`, in `app/controllers/shipit/webhooks_controller.rb:24-30`) must equal `commit.stack.repository.owner` for every `Commit` mutated by the handler — but this equality is never checked.

`StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
Unlike other handlers such as `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler`/`LabeledHandler`/`ClosedHandler`, which resolve `Repository.from_github_repo_name(params.repository.full_name)` and scope all lookups to that repository [1](#0-0) , `StatusHandler`'s `params` schema does not even require a `repository` object [2](#0-1) , and its `process` method queries `Commit` directly with no stack/repository scoping [3](#0-2) .

`WebhooksController#verify_signature` only verifies the HMAC signature against the GitHub App registered for `repository_owner` taken from the payload [4](#0-3) ; it never restricts which `Commit` rows the resulting handler is allowed to touch. The `commits` table's only uniqueness constraint is `["sha", "stack_id"]` (unique), not global on `sha` [5](#0-4) , confirmed by the dedicated migration `IndexCommitsOnStackIdAndSha` [6](#0-5) . This means the same 40-character sha can be stored under multiple `stack_id`s belonging to different `Repository` rows (e.g. two Shipit-tracked stacks for a fork and its upstream, which share ancestor commit shas by construction of git; `GithubSyncJob` imports whatever commits are reachable per stack, so a shared ancestor sha ends up duplicated across stacks with different owners).

Exploit flow:
1. Attacker owns and controls "OrgA" repository/organization, which is legitimately configured in Shipit with its own GitHub App installation and `webhook_secret` (satisfies "real webhook_secret" per the question).
2. Attacker's OrgA repository shares a common ancestor commit (same `sha`) with a repository tracked as a stack under "OrgB" (e.g., because OrgA's tracked repo is a fork of, or shares history with, OrgB's tracked repo) — `Commit` rows for that shared sha exist under both stacks (`stack_id` differing, `sha` identical, permitted by the schema).
3. Attacker triggers a real GitHub `status` event on their own OrgA repository at that shared sha (e.g., by pushing a commit or using GitHub Actions/any CI integration they control to post a status). GitHub signs and delivers this webhook using OrgA's `webhook_secret`, which is correctly verified by `verify_signature`.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which returns **all** `Commit` rows across **all** stacks matching that sha, including the one under OrgB's stack, and calls `create_status_from_github!` on each, writing an OrgA-controlled status (`pending`/`success`/`failure`) onto OrgB's commit.
5. `Commit#create_status_from_github!` → `Status.replicate_from_github!` → `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` fire on OrgB's stack/commit, and depending on state transition this can trigger `stack.schedule_merges`/`ProcessMergeRequestsJob` enqueuing for OrgB's stack (per the `commit_status`/`deployable_status` transition logic exercised in `test/models/commits_test.rb:763-777`, which shows `create_status_from_github!` enqueuing `ProcessMergeRequestsJob` for the commit's `stack`).

No existing guard closes this gap: `verify_signature` only authenticates the org that sent the request, not which commits the handler is permitted to write; `drop_unhandled_event` and the `ExplicitParameters` schema for `status` don't require/validate a `repository` field at all.

### Impact Explanation
Impact: an unauthorized write to another organization's `Commit`/`Status` — matching "Critical: a payload for one repository mutating another's stack, commit, task, or team," and potentially "an unauthorized merge" if the forged `success`/`pending` status causes `ProcessMergeRequestsJob` to advance OrgB's merge queue on a commit that never actually passed CI in OrgB's context. This is repeatable against any sha that the attacker can arrange to be shared between a repo they control and any other Shipit-tracked stack (most practically via forks, which routinely share ancestor commit shas exactly). The blast radius spans any number of tenants sharing commit ancestry with the attacker's controlled repository.

### Likelihood Explanation
Preconditions: attacker needs (a) a Shipit-tracked repository/org they legitimately own and control, with a working GitHub App installation (this is a normal, low-cost setup any GitHub org owner can obtain if Shipit is multi-tenant), and (b) a target commit sha that also exists in another org's Shipit-tracked stack — most naturally satisfied via forks/shared git history, which is common in real-world usage of GitHub. No Shipit secrets, sessions, or privileged roles are required beyond normal GitHub App installation on the attacker's own org, which is explicitly in-scope per the question's framing ("attacker owns OrgA with a real webhook_secret"). The attack is cheap and repeatable (one webhook per target sha).

### Recommendation
Scope `StatusHandler#process` to only commits belonging to stacks under the repository identified in the verified webhook payload — mirroring the pattern used by `Shipit::Webhooks::Handlers::Handler#stacks`/`Repository.from_github_repo_name`. E.g., require `repository.full_name` in the `status` params schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the query to `Commit.where(sha: params.sha, stack: repository.stacks)` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (model/controller test, no live GitHub):
```ruby
test "status webhook signed for OrgA does not mutate commits belonging to OrgB's stack with the same sha" do
  shared_sha = '6d9278037b872fd9a6690523e411ecb3aa181355'

  org_b_repo = Repository.create!(owner: 'orgb', name: 'repo')
  org_b_stack = Stack.create!(repository: org_b_repo, environment: 'production')
  org_b_commit = org_b_stack.commits.create!(sha: shared_sha, message: 'x',
    author: shipit_users(:walrus), committer: shipit_users(:walrus),
    authored_at: Time.now, committed_at: Time.now)

  org_a_repo = Repository.create!(owner: 'orga', name: 'repo')
  org_a_stack = Stack.create!(repository: org_a_repo, environment: 'production')
  org_a_stack.commits.create!(sha: shared_sha, message: 'x',
    author: shipit_users(:walrus), committer: shipit_users(:walrus),
    authored_at: Time.now, committed_at: Time.now)

  payload = {
    'sha' => shared_sha, 'state' => 'success',
    'repository' => { 'full_name' => 'orga/repo', 'owner' => { 'login' => 'orga' } }
  }

  GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true) # OrgA's real, valid signature

  assert_no_difference -> { org_b_commit.statuses.count } do
    request.headers['X-Github-Event'] = 'status'
    post :create, body: payload.to_json, as: :json
  end
end
```
Binding assertion: `repository_owner` from the verified payload (`'orga'`) must equal `org_b_commit.stack.repository.owner` (`'orgb'`) before any `Status` is created for `org_b_commit`; today `StatusHandler#process` creates the `Status` regardless, proving the gap. This can be extended with `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [org_b_stack])` to demonstrate the merge-queue side effect on OrgB's stack, matching the pattern already exercised in `test/models/commits_test.rb:763-777`.
