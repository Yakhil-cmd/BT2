### Title
Zero-Value Handle Calls Permanently Consume Bridge Nonces Without Delivering Assets — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleERC20Transfer` and `handleKLAYTransfer` in the Kaia service-chain bridge contracts accept `_value = 0` without any guard. A registered bridge operator can call either function with a valid pending nonce but with `_value = 0`, which permanently marks that nonce as handled and advances `lowerHandleNonce` — without delivering any tokens or KAIA to the recipient. The user's assets on the source chain are already locked or burned; they are never recoverable.

---

### Finding Description

The request-side functions correctly reject zero-value transfers:

```solidity
// BridgeTransferERC20.sol line 89
require(_value > 0, "zero ERC20 token amount");
```

```solidity
// BridgeTransferKLAY.sol line 109
require(msg.value > _feeLimit, "insufficient amount");
```

But the handle-side functions have no equivalent guard:

**`handleERC20Transfer`** (lines 32–73):
```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash, address _from, address _to,
    address _tokenAddress, uint256 _value,          // ← no zero check
    uint64 _requestedNonce, uint64 _requestedBlockNumber,
    bytes memory _extraData
) public onlyOperators {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }   // closes nonce
    _setHandledRequestTxHash(_requestTxHash);
    handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
    _updateHandleNonce(_requestedNonce);                     // advances lowerHandleNonce
    emit HandleValueTransfer(..., _value, ...);
    if (modeMintBurn) {
        require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...); // mint(to, 0) succeeds
    } else {
        IERC20(_tokenAddress).safeTransfer(_to, _value);              // transfer(to, 0) succeeds
    }
}
```

**`handleKLAYTransfer`** (lines 62–100):
```solidity
function handleKLAYTransfer(
    bytes32 _requestTxHash, address _from, address payable _to,
    uint256 _value,                                 // ← no zero check
    uint64 _requestedNonce, uint64 _requestedBlockNumber,
    bytes memory _extraData
) public onlyOperators nonReentrant {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }   // closes nonce
    ...
    _updateHandleNonce(_requestedNonce);                     // advances lowerHandleNonce
    (bool ok, ) = _to.call.value(_value)("");               // call.value(0) succeeds
    require(ok, "handleKLAYTransfer: transfer failed");
}
```

The voting mechanism in `_voteValueTransfer` uses `keccak256(msg.data)` as the vote key:

```solidity
// BridgeOperator.sol line 109
bytes32 voteKey = keccak256(msg.data);
```

With the **default threshold of 1** (set in the constructor), a single operator's call with `_value = 0` immediately satisfies the threshold, sets `closedValueTransferVotes[_requestedNonce] = true`, and executes the rest of the handle function — delivering nothing.

After this call:
- `closedValueTransferVotes[nonce]` is `true` → any subsequent call with the correct `_value` reverts with `"closed vote"`
- `lowerHandleNonce` may advance past the nonce → `_lowerHandleNonceCheck` would also reject retries
- The value transfer recovery system (`ValueTransferRecovery`) reads `lowerHandleNonce` and `upperHandleNonce` to determine pending events; once the nonce is consumed, recovery considers it handled

---

### Impact Explanation

A user initiates a bridge transfer on the source chain. Their tokens are either burned (mint-burn mode) or locked in the source bridge contract. On the destination chain, a malicious operator calls `handleERC20Transfer` or `handleKLAYTransfer` with the correct nonce but `_value = 0`. The nonce is permanently consumed. The user receives nothing. Their source-chain assets are permanently lost — burned or locked forever with no recovery path.

This satisfies the allowed impact: **unauthorized nonce consumption affecting bridged assets**, resulting in permanent loss of user funds.

---

### Likelihood Explanation

The default operator threshold is 1 (constructor sets `operatorThresholds[i] = 1` for all vote types). In a single-operator deployment — the most common service-chain configuration — one operator can execute this unilaterally. Even with threshold > 1, colluding operators can agree to submit identical zero-value calldata. The attack is cheap (one on-chain transaction per nonce) and irreversible. The off-chain bridge manager (`handleRequestValueTransferEvent` in `node/sc/bridge_manager.go`) passes `valueOrTokenId` directly from the source-chain event without any zero-value filter, so a compromised or buggy operator node could trigger this inadvertently or deliberately.

---

### Recommendation

Add a zero-value guard at the top of both handle functions, mirroring the guard already present on the request side:

```solidity
// BridgeTransferERC20.sol — handleERC20Transfer
require(_value > 0, "zero ERC20 token amount");

// BridgeTransferKLAY.sol — handleKLAYTransfer
require(_value > 0, "zero KLAY amount");
```

These checks must be placed **before** `_voteValueTransfer` is called so that a zero-value call cannot consume the nonce at all.

---

### Proof of Concept

1. User calls `requestERC20Transfer` on the source bridge with `_value = 100e18`. Source bridge locks 100e18 tokens. `requestNonce` increments to `N`.
2. Malicious operator observes the `RequestValueTransfer` event for nonce `N`.
3. Operator calls on the destination bridge:
   ```solidity
   handleERC20Transfer(
       txHash, from, to, tokenAddr,
       0,          // _value = 0 instead of 100e18
       N,          // _requestedNonce
       blockNum, extraData
   );
   ```
4. With threshold = 1: `_voteValueTransfer(N)` returns `true`, sets `closedValueTransferVotes[N] = true`.
5. `_updateHandleNonce(N)` advances `lowerHandleNonce`.
6. `mint(to, 0)` or `safeTransfer(to, 0)` succeeds silently.
7. Any subsequent call with `_value = 100e18` and nonce `N` reverts: `"closed vote"`.
8. The value transfer recovery system sees nonce `N` as handled and skips it.
9. User's 100e18 tokens are permanently lost. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6)

        internal
        returns(bool)
    {
        require(!closedValueTransferVotes[_requestNonce], "closed vote");

        bytes32 voteKey = keccak256(msg.data);
        if (_voteCommon(VoteType.ValueTransfer, _requestNonce, voteKey)) {
            closedValueTransferVotes[_requestNonce] = true;
            return true;
        }

        return false;

    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}
