### Title
Interest accrual `scaled_to_original` overflow permanently bricks a whale-sized market — no repay, withdraw, or liquidation — ([File: common/src/rates/scaling.rs])

### Summary
The vLLM report's bug class is "an unhandled exception on attacker-influenced input kills the whole engine," not just the failing request. The analog in XOXNO Lending is the RAY-value ceiling in the shared accrual step: `accrue_step` computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` — a plain `Ray::mul` that panics with `GenericError::MathOverflow` on i128 overflow (`common/src/rates/scaling.rs:14-16`, `common/src/rates/simulate.rs:60-61`). The `MAX_BORROW_INDEX_RAY` clamp is applied to the *index* only, after the multiply, so it never protects the *value* product (`common/src/rates/index.rs:13-19`). Because `contracts/pool/src/interest.rs::global_sync` runs `accrue_chunk` before every state-changing verb, once `borrowed × borrow_index` crosses the i128 ceiling every subsequent call on that market — `update_indexes`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan` — panics inside the same accrual, permanently freezing all supplier and borrower funds in the market.

### Finding Description
- Root cause: `scaled_to_original` at `common/src/rates/scaling.rs:14-16` delegates to `Ray::mul`, which panics on overflow (`common/tests/math/fp.rs:368-371` asserts `Ray::from(i128::MAX).mul(i128::MAX)` panics). It is invoked at the top of every `accrue_step` (`common/src/rates/simulate.rs:60-61`) and again inside `calculate_supplier_rewards` (`borrowed × new_borrow_index`).
- The borrow index is clamped at `MAX_BORROW_INDEX_RAY = 1e36` (`common/src/rates/index.rs:13-19`), but `supplied`/`borrowed` scaled shares are unbounded beyond asset caps, so `borrowed × borrow_index` can exceed `i128::MAX` *before* the index cap engages — the test at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:349-353` asserts exactly that ordering.
- The panic is sticky: `global_sync` (`contracts/pool/src/interest.rs:20-33`) loops `accrue_chunk` over elapsed chunks and is invoked by every controller verb first, so the failure is hit identically by `try_update_indexes`, `try_withdraw_raw`, and `try_repay`, all reverting with `MATH_OVERFLOW` (test lines 343-356).
- Attacker path: an unprivileged address calls controller `supply` and `borrow` to build a whale-scale position on a market whose configured caps admit it (caps are a per-market listing parameter, not a per-call privilege; the test uses `lift_caps` only because the harness seeds restrictive defaults). Sustained high utilization on a steep rate curve then grows `borrow_index` until the product overflows — no privileged or malformed-input step is needed after the position is planted.

### Impact Explanation
Permanent freezing of funds and a market unable to operate: once the accrual panics, no supplier can withdraw, no borrower can repay, no liquidator can close positions, and bad debt cannot be cleaned or recapitalized in that market, because every entry point accrues first. All tokens physically held in the pool for that (hub, token) book are permanently locked. This matches the accepted impact classes "permanent freezing of funds" and "contract unable to operate" for the affected market.

### Likelihood Explanation
Medium. The trigger requires (a) a market configured with caps large enough to admit ~170× the i128 RAY-value bound in scaled terms, and (b) sustained high utilization long enough for the index to grow into the overflow — the harness shows this occurring within the index's pre-cap lifetime on the steep segment of an XLM-style curve. It is not instant and demands whale-scale capital, but it needs no privilege, no oracle manipulation, and no cooperation; the failure is deterministic arithmetic, confirmed by an in-repo test, and is irreversible once reached.

### Recommendation
Saturate rather than panic at the RAY-value ceiling inside accrual: make `scaled_to_original` (or the `borrowed × borrow_index` products in `accrue_step`/`calculate_supplier_rewards`) use a saturating `mul_div` so the accrual clamps to `i128::MAX` value the same way `update_borrow_index` clamps the index — mirroring the existing fail-open precedent in `calculate_scaled_cap` (`common/src/rates/scaling.rs:26-33`). Alternatively, enforce at listing time a supply/borrow cap bound that guarantees `cap_scaled × MAX_BORROW_INDEX_RAY` stays within i128, analogous to `require_cap_within_asset_domain`. Position-level unscale paths (`unscale_*`) can keep panicking since they only affect the caller's own transaction.

### Proof of Concept
The repository already encodes the PoC as `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`):

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);              // unprivileged supply
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);                 // unprivileged borrow, ~98% util
// ... advance time until accrual panics:
assert_contract_error(Err(failure), errors::MATH_OVERFLOW);          // update_indexes dies
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW); // withdraw dies
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);    // repay dies
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY);  // cap never engaged
```

The only non-attacker steps in the test are `lift_caps`/`with_max_utilization_disabled_all_markets`, which set market configuration; on any live market whose listing parameters permit whale-scale supply and near-full utilization, a single unprivileged address planting the position plus ordinary passage of time produces the same permanent freeze.
