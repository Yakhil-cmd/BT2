### Title
Signature verification binds to `as_encrypted_variant()` transform instead of the actual `RawTransaction`, allowing payload substitution after admission - (types/src/transaction/authenticator.rs)

### Summary
`TransactionAuthenticator::verify` does not verify signatures over the `RawTransaction` instance that is ultimately admitted/executed. Instead, it first calls `raw_txn.as_encrypted_variant()` and signs/verifies over that derived value. [1](#0-0)  The inline comment explicitly states the design intent: "signatures are verified over the encrypted form (not the decrypted payload)." [2](#0-1) 

### Finding Description
`verify()` computes `raw_txn_for_signing = raw_txn.as_encrypted_variant()` and uses this transformed value for every authenticator variant's signature check (`Ed25519`, `MultiEd25519`, `MultiAgent`, `FeePayer`, `SingleSender`). [3](#0-2)  If the "encrypted variant" representation used for signing purposes can differ from the payload that is ultimately committed/executed for the transaction (e.g. because a decryption step later reconstitutes a different concrete payload for execution), the cryptographic signature no longer binds to what actually gets executed. This breaks the fundamental "what-you-sign-is-what-gets-executed" invariant that `TransactionAuthenticator::verify` is supposed to enforce for sender/payload binding.

### Impact Explanation
If exploitable end-to-end (i.e., if there exists a decryption path that produces an executed payload distinct from the one covered by `as_encrypted_variant()`), an unprivileged submitter could get a transaction admitted with a validly-checked signature while having execution diverge from what was actually signed — corrupting the payload-binding guarantee at the admission boundary. This falls squarely within the "Admission Pivots" impact family (authenticator parsing / payload binding must bind to the intended, signed content).

### Likelihood Explanation
Likelihood depends on whether a genuine decrypt-then-execute path exists elsewhere in the codebase that substitutes a different payload than the one covered by `as_encrypted_variant()`. I was not able to fully confirm this counterpart logic in `types/src/transaction/mod.rs` within the available tool budget — the function is referenced 3 times there but its body and the corresponding execution-side decryption/commitment enforcement were not retrievable in this session. This should be independently verified before treating the impact as fully confirmed.

### Recommendation
- Verify `TransactionAuthenticator::verify` always signs/verifies over the exact `RawTransaction` bytes that will be executed, with no lossy or divergent transform in between.
- If an "encrypted payload" concept genuinely exists, ensure the ciphertext itself commits (e.g., via an embedded hash/commitment) to the exact decrypted payload that will be executed, and that this commitment is checked against the decrypted result before execution.
- Add an explicit assertion/test that `signed_txn.verify_signature()` fails whenever the decrypted/executed payload differs from what was originally signed.

### Proof of Concept
Conceptual PoC (pending confirmation of the decrypt/execution counterpart code):
1. Construct `RawTransaction` A with payload P1, call `.as_encrypted_variant()`, and sign the resulting bytes to produce `TransactionAuthenticator::Ed25519`.
2. Submit the resulting `SignedTransaction` for admission; `verify()` succeeds because it re-derives the same `as_encrypted_variant()` value from the stored `RawTransaction` and checks the signature against it. [4](#0-3) 
3. If a downstream decryption/execution path substitutes payload P2 for execution purposes without re-verifying the signature against P2 directly, execution proceeds on P2 despite the signature only ever having covered the `as_encrypted_variant()`-derived bytes for P1 — demonstrating sender/payload-binding corruption.

Note: Step 3's decryption/substitution mechanism could not be located and confirmed in this review session; a Devin session with full repository access would be needed to trace `RawTransaction::as_encrypted_variant()` and any corresponding decrypt path fully.

    pub fn verify(&self, raw_txn: &RawTransaction) -> Result<()> {
        let num_sigs: usize = self.sender().number_of_signatures()
            + self
                .secondary_signers()
                .iter()
                .map(|auth| auth.number_of_signatures())
                .sum::<usize>();
        if num_sigs > MAX_NUM_OF_SIGS {
            return Err(Error::new(AuthenticationError::MaxSignaturesExceeded));
        }
        // For encrypted transactions, signatures are verified over the encrypted form
        // (not the decrypted payload). Convert back to the encrypted variant for signing
        // message reconstruction.
        let raw_txn_for_signing = raw_txn.as_encrypted_variant();
        match self {
            Self::Ed25519 {
                public_key,
                signature,
            } => signature.verify(&raw_txn_for_signing, public_key),
            Self::FeePayer {
                sender,
                secondary_signer_addresses,
                secondary_signers,
                fee_payer_address,
                fee_payer_signer,
            } => {
                // In the fee payer model, the fee payer address can be optionally signed. We
                // realized when we designed the fee payer model, that we made it too restrictive
                // by requiring the signature over the fee payer address. So now we need to live in
                // a world where we support a multitude of different solutions. The modern approach
                // assumes that some may sign over the address and others will sign over the zero
                // address, so we verify both and only fail if the signature fails for either of
                // them. The legacy approach is to assume the address of the fee payer is signed
                // over.
                let mut to_verify = vec![sender];
                let _ = secondary_signers
                    .iter()
                    .map(|signer| to_verify.push(signer))
                    .collect::<Vec<_>>();

                let no_fee_payer_address_message = RawTransactionWithData::new_fee_payer(
                    raw_txn_for_signing.clone().into_owned(),
                    secondary_signer_addresses.clone(),
                    AccountAddress::ZERO,
                );

                let mut remaining = to_verify
                    .iter()
                    .filter(|verifier| verifier.verify(&no_fee_payer_address_message).is_err())
                    .collect::<Vec<_>>();

                remaining.push(&fee_payer_signer);

                let fee_payer_address_message = RawTransactionWithData::new_fee_payer(
                    raw_txn_for_signing.into_owned(),
                    secondary_signer_addresses.clone(),
                    *fee_payer_address,
                );

                for verifier in remaining {
                    verifier.verify(&fee_payer_address_message)?;
                }

                Ok(())
            },
            Self::MultiEd25519 {
                public_key,
                signature,
            } => signature.verify(&raw_txn_for_signing, public_key),
            Self::MultiAgent {
                sender,
                secondary_signer_addresses,
                secondary_signers,
            } => {
                let message = RawTransactionWithData::new_multi_agent(
                    raw_txn_for_signing.into_owned(),
                    secondary_signer_addresses.clone(),
                );
                sender.verify(&message)?;
                for signer in secondary_signers {
                    signer.verify(&message)?;
                }
                Ok(())
            },
            Self::SingleSender { sender } => sender.verify(&raw_txn_for_signing),
        }
