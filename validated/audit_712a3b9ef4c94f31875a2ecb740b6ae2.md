### Title
Signature verification is keyed by an attacker-controlled `repository.owner.login` that need not match the `repository.full_name` acted on, allowing HMAC-signature bypass for one org's repositories using another (unsecured) org's config - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to validate the request signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body. The event handlers, however, resolve the repository that is actually written to independently, from `repository.full_name` in the same body. These two payload fields are never cross-checked, so the "organization whose secret authenticated the request" is not bound to the "repository the handler acts on."

### Finding Description
`verify_signature` computes:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`GitHubApp#verify_webhook_signature` explicitly no-ops when the resolved org has no configured `webhook_secret`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

`webhook_secret` is explicitly documented as optional per-organization configuration (`docs/setup.md`), and the repo's own multi-org fixture shows two distinct orgs each with independently nil/blank `webhook_secret` possible: [3](#0-2) 

Meanwhile, the actual repository acted on by every handler is resolved from a **different** field of the same JSON body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the target repository/stack) are independent, attacker-controlled fields inside the same unauthenticated JSON body, an attacker can:
1. Set `repository.owner.login` (or `organization.login`) to any organization configured on the Shipit instance whose `webhook_secret` is blank/unset.
2. Set `repository.full_name` to `TargetOrg/target-repo`, a *different*, properly-secured organization/repository actually deployed through Shipit.
3. Send the webhook with any garbage/empty `X-Hub-Signature` header (or omit it).

`verify_signature` resolves the GitHub App config for the attacker-chosen owner, finds no `webhook_secret`, and returns `true` unconditionally — the signature is never actually checked against the real target org's secret. The request then proceeds to `Shipit::Webhooks.for_event(event)`, whose handlers key entirely off `repository.full_name`, so the forged event is applied to the real target repository's stacks.

This breaks exactly the trust binding: `organization authenticated == repository written`.

### Impact Explanation
Depending on event type, this enables:
- `push`: forging a `GithubSyncJob` sync with an attacker-chosen `expected_head_sha` for a target stack the attacker has no access to [5](#0-4) .
- `status`: injecting a fabricated CI status (`success`, arbitrary `context`/`description`/`target_url`) onto an existing commit of the target repository via `Commit#create_status_from_github!`, without ever having push/write access to that repository or its CI [6](#0-5) . Since Shipit's deploy gating relies on aggregated commit statuses to decide whether a commit is "deployable," this can be used to force a stack's deploy-safety checks to pass for a commit that never actually passed real CI, enabling an unauthorized/unsafe deploy to proceed.
- `check_suite`: forging a `RefreshCheckRunsJob` trigger for the target repository [7](#0-6) .

The precondition (at least one onboarded organization with no `webhook_secret` configured) is realistic and explicitly supported by the documented setup flow, which marks `webhook_secret` as optional. This crosses the "unauthenticated read/write of stack state" and potentially "unauthorized deploy" impact bar defined in the rules, without requiring any Shipit session, API token, or GitHub repository write access — only unauthenticated POSTs to the public `/webhooks` endpoint.

### Likelihood Explanation
Any unprivileged, unauthenticated network attacker who can reach the `/webhooks` endpoint can attempt this; the only requirement is that *some* organization on the Shipit instance (not necessarily the target) has a blank `webhook_secret`, which the setup docs present as an acceptable/optional configuration choice, making this realistically reachable in multi-org deployments.

### Recommendation
Bind signature verification to the same repository/organization the handler will act on: resolve `repository.full_name` (and derive its owner from that, not from a separately attacker-controlled field/`organization.login` fallback), and require a non-empty configured `webhook_secret` for that specific repository's owner before accepting the event — never silently treat "no secret configured" as "verified." Additionally, reject events whose `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
Given a Shipit instance configured with two orgs, `UnsecuredOrg` (no `webhook_secret`) and `TargetOrg` (with `webhook_secret` and a real stack deployed for `TargetOrg/prod-repo`):

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=deadbeef   (garbage, no valid secret known)

{
  "sha": "<existing commit sha of TargetOrg/prod-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": {
    "owner": { "login": "UnsecuredOrg" },
    "full_name": "TargetOrg/prod-repo"
  }
}
```
`verify_signature` looks up `Shipit.github(organization: "UnsecuredOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the bogus signature [2](#0-1) . `StatusHandler` then resolves `Commit.where(sha: ...)` against the real commit belonging to `TargetOrg/prod-repo` (via `repository.full_name`) and records a forged `success` status [6](#0-5) , despite the attacker never possessing `TargetOrg`'s `webhook_secret` or any GitHub credentials for that repository.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
