### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup — (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` only proves that the request was signed with the `webhook_secret` of the organization named in the payload's `repository.owner.login`; it never proves that the `sha` field in a `status` payload actually belongs to a commit in that same repository. `StatusHandler#process` then does a global, un-scoped `Commit.where(sha: params.sha)` lookup and calls `create_status_from_github!` on every match, regardless of which stack/organization owns that commit row.

### Finding Description
The binding that must hold is: `organization_that_signed(payload) == organization_owning(Commit.find_by(sha: params.sha).stack)`. The code never enforces this equality.

- `WebhooksController#verify_signature` derives the signing organization solely from `params.dig('repository','owner','login')` (or `organization.login`) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, i.e. it authenticates "this payload came from organization X's webhook secret" — nothing about the `sha` itself. [1](#0-0) [2](#0-1) 

- `StatusHandler#process` ignores `payload.dig('repository', ...)` entirely for the lookup and instead resolves target commits purely by `sha`, with no join/filter on stack, repository, or organization: [3](#0-2) 

The base `Handler` class does define a `stacks`/`repository_name` helper scoped from `payload.dig('repository','full_name')`, but `StatusHandler` doesn't use it for the DB lookup — it only relies on `params.sha`. [4](#0-3) 

- `Commit#create_status_from_github!` writes a `Status` row for whatever commit was matched, without re-checking that the commit's `stack.repository` corresponds to the organization that authenticated the request: [5](#0-4) 

- That `Status` creation, via `add_status`/`after_commit`, triggers `Commit#schedule_continuous_delivery`, which checks `deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) purely against the matched commit/stack, and if the victim stack has `continuous_deployment?` enabled, enqueues `ContinuousDeliveryJob` for the victim's stack: [6](#0-5) [7](#0-6) 

**Exploit flow:** git commit SHAs are content-addressed, and forks of a public repository share identical commit objects/SHAs for shared history. An attacker who owns a repository/organization already onboarded to Shipit (with its own valid `webhook_secret`) — e.g. a fork or a repo that shares commits with the victim's repository (vendored code, cherry-picks, shared history) — can send a legitimately-signed `status` webhook (`state: success`, `sha: <victim's pending commit sha>`, `repository.full_name: <attacker's own repo>`). `verify_signature` succeeds because the signature matches the attacker's own organization's secret. `StatusHandler#process` then finds and mutates the **victim's** `Commit` row purely by `sha`, flips it to `success`, and — if the victim stack has continuous deployment enabled — schedules and executes an unauthorized deploy of a commit that never actually passed CI on the victim's own repository.

None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) check that the resolved `Commit#stack`'s repository matches `repository_owner`/`repository_name` from the payload, so the divergence is real.

### Impact Explanation
This allows one Shipit tenant (an organization/repository onboarded with its own webhook secret) to write a forged `Status` (`success`) onto another tenant's `Commit` and, if continuous deployment is enabled on the victim stack, trigger an unauthorized deploy of that commit. This is a payload for one repository mutating another's commit/stack state and can lead to an unauthorized deploy — matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The attack is repeatable against any commit sha shared between the attacker's onboarded repository and any victim stack's undeployed commits, and blast radius spans all stacks/organizations onboarded to the same Shipit instance whose commit history overlaps (forks, shared libraries, cherry-picks, monorepo splits, etc.) with an attacker-controlled repository.

### Likelihood Explanation
Preconditions: (1) attacker must control (or push to) a repository/organization that is already onboarded to the target Shipit instance with a valid `webhook_secret` (this is a normal, unprivileged capability for any team member with a repo on the Shipit deployment — not a Shipit operator role); (2) the attacker's repo must share a commit SHA with the victim stack's pending commit — trivially achievable via forking a public repo, since forks preserve identical commit SHAs for shared history, or via any shared/cherry-picked commit; (3) the victim stack must have `continuous_deployment?` enabled and an undeployed commit whose CI is pending/failing. Given these are common configurations (forked/mirrored repos, CD-enabled stacks), the attack requires no secrets and only a legitimately-signed webhook from the attacker's own onboarded repository, making it low-cost and repeatable.

### Recommendation
In `StatusHandler#process` (and analogous handlers doing sha-based lookups), scope the `Commit` lookup to the repository that authenticated the webhook, e.g. join through `stack.repository` and require it match `payload.dig('repository', 'full_name')` (reusing the `stacks`/`repository_name` helper already defined on `Handler`), rejecting/ignoring statuses for commits belonging to a different repository than the one that signed the payload.

### Proof of Concept
Minitest plan (no live GitHub, using existing fixtures):
1. Set up `shipit_stacks(:victim)` with `continuous_deployment: true`, and an undeployed `Commit` (`victim_commit`) whose current status is not success (pending/failed), belonging to repository `victim/repo`.
2. Create an `attacker_commit` fixture/record with the **same `sha`** as `victim_commit.sha`, but attached to `shipit_stacks(:attacker)` belonging to `attacker/repo`, whose organization has a real, distinct `webhook_secret` configured in `Shipit.github`.
3. POST to `/webhooks` with header `X-Github-Event: status`, a valid `X-Hub-Signature` computed using `attacker/repo`'s organization webhook secret, and a JSON body: `{ "sha": <shared_sha>, "state": "success", "repository": { "full_name": "attacker/repo", "owner": { "login": "attacker" } } }`.
4. Assert before: `victim_commit.reload.status.state != 'success'` and `Deploy.count` unchanged for `shipit_stacks(:victim)`.
5. Assert after: `victim_commit.reload.status.state == 'success'`, and (after running `ContinuousDeliveryJob` inline / `perform_enqueued_jobs`) `Deploy.where(stack: shipit_stacks(:victim)).count` increments — proving the attacker's own-repo, correctly-signed webhook caused a deploy/status mutation on `shipit_stacks(:victim)`'s commit, which it never authenticated.
