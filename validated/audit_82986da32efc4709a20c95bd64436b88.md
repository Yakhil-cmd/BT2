### Title
Inconsistent signature checking in `validateSignedMessageSync` for multisig/complex address definitions - (File: signed_message.js)

### Summary
`signed_message.js` exposes two entry points for verifying an off-chain signed message against an address definition: the asynchronous `validateSignedMessage()` and a synchronous wrapper `validateSignedMessageSync()`. The wrapper is explicitly documented in the code as "inconsistent for multisig addresses" [1](#0-0) , because it assumes the underlying async validation completes synchronously and throws if it does not. This mirrors the Across `SpokePool` bug class: two verification call sites for the same signed message/definition can diverge in behavior — one path (async, DB-aware) fully evaluates definitions that require DB lookups (e.g. `and`/`or` combos, `address` references to other definitions, `definition template`), while the sync path silently mis-evaluates or throws for any definition whose evaluation is not purely synchronous.

### Finding Description
`Definition.validateAuthentifiers()` evaluates arbitrary address-definition trees, including ops like `sig`, `hash`, nested `address` (pointing at another on-chain definition, requiring a DB read), and `definition template` (requiring a DB read of a template unit) [2](#0-1) . These evaluations are inherently asynchronous because they call `storage.readDefinitionByAddress` / `conn.query`.

`validateSignedMessage()` in `signed_message.js` correctly performs this evaluation asynchronously and feeds the result through `Definition.validateAuthentifiers` with a real `conn` [3](#0-2) . However, `validateSignedMessageSync()` calls the same function but expects it to call back before the function returns, throwing `"validateSignedMessage is not sync"` if it doesn't [4](#0-3) . For simple single-key `sig` definitions the callback chain happens to be synchronous (since `ecdsaSig.verify` is synchronous and no DB query is needed), so the sync wrapper "works" only for that narrow case — exactly the class of bug described in the report, where a signature-verification abstraction silently behaves correctly for the simple ECDSA case but diverges for the more complex (multisig/EIP‑1271-analogous) case.

This is functionally identical to the reported issue: a message/signature verification helper that is expected to give the same answer regardless of caller, but actually gives different (or broken/exception) results depending on whether the underlying address definition is a plain single-key signature or a more complex definition (multisig, nested `address`, `definition template`) requiring asynchronous resolution.

### Impact Explanation
Any caller of `validateSignedMessageSync()` for an address whose definition is not a trivial single `sig` node (e.g., a multisig `and`/`or` combination, or a definition referencing another on-chain address) will either:
- Get an exception (`"validateSignedMessage is not sync"`), causing a denial of legitimate signed messages/authorizations, or
- Depending on timing, potentially proceed with an incomplete/uninitialized `err` value if the exception is not properly caught by all call sites, leading a caller to treat an unverified signature as valid.

Because `is_valid_signed_package()` in AA formula evaluation and payment-channel oscript templates (see `test/samples/payment_channels.oscript`) rely on signed-package verification for off-chain relay/dispute mechanics (fraud proofs, channel closure, peer signature checks) [5](#0-4) , an inconsistency between the sync and async verification paths for multisig-controlled channel addresses could let an AA (or any code depending on this synchronous path) accept a bad signed package or reject a valid one, potentially resulting in incorrect fund distribution in payment-channel-style AAs that use signed off-chain state.

### Likelihood Explanation
The AA-facing production path (`is_valid_signed_package`) uses the async `validateSignedMessage()` exclusively [6](#0-5) , so the most severe AA-level consequence is not directly reachable through that path. The risk is specifically confined to any code path in the codebase that calls the documented-as-broken `validateSignedMessageSync()` with a non-trivial (multisig or address-referencing) definition — a real but narrower attack surface than the original report, since the comment itself flags the danger and most callers appear to use the async version.

### Recommendation
- Remove or deprecate `validateSignedMessageSync()` entirely, since asynchronous DB lookups can occur for any address definition beyond a bare `sig`, making "sync" validation fundamentally unsound.
- If a synchronous convenience wrapper is needed, restrict it explicitly to a whitelist of definition shapes that are provably synchronous (single `sig`/`hash` at root, no `address`, no `definition template`), and reject/throw clearly for any other shape *before* attempting evaluation, rather than after an async call unexpectedly resolves asynchronously.
- Audit all call sites of `validateSignedMessageSync()` (and `validation.js`'s re-exported version) to ensure none of them are reachable with attacker-supplied or multisig-controlled address definitions.

### Proof of Concept
1. Create an address definition using `['and', [['sig', {...}], ['sig', {...}]]]` for a 2-of-2 multisig, or a definition of the form `['address', otherAddress]` referencing another on-chain address.
2. Construct a `signed_message` object authored by this address with valid authentifiers for both keys.
3. Call `signed_message.validateSignedMessageSync(objSignedMessage)`.
4. Because `Definition.validateAuthentifiers` must perform `storage.readDefinitionByAddress`/`conn.query` for the `address` op (or async iteration over multiple `sig` children in `and`), the callback in `validateSignedMessage` will not fire before `validateSignedMessageSync` checks `bCalledBack`, causing it to throw `"validateSignedMessage is not sync"` — demonstrating the divergence in behavior between simple and multisig/complex definitions that the code itself flags as "inconsistent for multisig addresses" [1](#0-0) .
