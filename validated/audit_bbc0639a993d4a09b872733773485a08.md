### Title
Cross-organization forgery of GitHub webhooks (push/status/check_suite) due to unauthenticated repository binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate an inbound webhook against using `repository_owner`, a value read directly out of the *unverified* JSON body. Once the signature check passes with that org's secret, the entire raw payload — including the `repository.full_name` field actually used by the event handlers to pick which `Stack`/`Commit` to mutate — is dispatched unmodified. Nothing re-checks that the organization whose secret validated the signature is the same organization named in the fields the handlers act on. This breaks the binding `organization that authenticated == repository that is written`.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) [2](#0-1) 

`repository_owner` is computed from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) — both attacker-controlled fields inside the same JSON body being verified. This value is used only to pick which configured `GitHubApp`/secret (`Shipit.github(organization: repository_owner)`) to check the HMAC against — see `lib/shipit.rb` `#github`/`#github_app_config` and the documented multi-org configuration: [3](#0-2) [4](#0-3) 

Shipit explicitly supports one distinct GitHub App (and thus one distinct `webhook_secret`) per organization, each normally created/owned by that organization's own admin. Signature verification itself is a correct HMAC-SHA1 comparison: [5](#0-4) 

However, after verification succeeds using OrgA's secret, `create` dispatches the *unmodified* payload to handlers: [6](#0-5) 

Handlers resolve the target `Stack`/`Commit` purely from payload content, with no re-validation that it belongs to the organization that authenticated:

- `PushHandler` resolves stacks via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — an independent, attacker-settable field from the one used for signature-org selection: [7](#0-6) [8](#0-7) 

- `StatusHandler` is worse: it doesn't scope by repository/stack at all, it matches **any** commit sha in the entire Shipit database: [9](#0-8) 

- `CheckSuiteHandler` similarly resolves stacks from `repository_name`, independent from the org used to authenticate: [10](#0-9) 

Concretely, before/after the attacker's request:
- Before: signature must be valid for organization X (`repository.owner.login == "X"`), and events for stack/commit belonging to X are the only ones expected to be triggered by X's webhook deliveries.
- After: an attacker who holds OrgA's `webhook_secret` (a value known to OrgA's own GitHub App admin, an unprivileged actor from Shipit's perspective relative to any other tracked organization/repo) can post directly to the webhooks endpoint with `repository.owner.login = "OrgA"` (so `verify_signature` picks and passes OrgA's secret) while setting `repository.full_name` (for push/check_suite) or `sha`(for status) to reference a *different* organization's/repository's stack or an arbitrary commit anywhere in the instance. The equality `authenticated org == repository being written` is broken.

### Impact Explanation
This lets an organization admin who legitimately controls only their own GitHub App/webhook secret forge events against stacks and commits belonging to any other organization tracked by the same Shipit instance:
- Via `status` events, they can fabricate arbitrary CI status (`state`, `context`, `description`) for any commit sha in the instance, which feeds `Commit#create_status_from_github!` and directly affects whether commits are treated as deployable/mergeable by the merge queue and deploy gating (`required_statuses`/`blocking_statuses` on `Stack`, delegated from `Commit`) — see `app/models/shipit/commit.rb` lines 57-58 for the delegation to stack-level deploy-gating checks. Forcing a "success" status on a malicious commit in a victim repository can enable that commit to pass CI gating and be shipped/merged through Shipit's normal flows, i.e., an unauthorized deploy/merge outcome.
- Via `push`/`check_suite` events, they can trigger `stack.sync_github` or `schedule_refresh_check_runs!` against another organization's stack using an attacker-chosen `after`/`head_sha`, causing cross-tenant side effects and resource use tied to a repository the attacker does not administer.

This matches the report's "Critical: cross-repository writes / unauthorized deploy" bar since it lets one tenant's credentials affect another tenant's deploy-gating state.

### Likelihood Explanation
Requires the instance to be configured with the documented multi-org GitHub App setup (explicitly supported and documented) and requires the attacker to be the admin/owner of at least one such configured organization (an otherwise unprivileged actor with respect to every other org/repo tracked by that Shipit deployment). No Shipit session, `ApiClient` token, or the victim organization's secret is needed — only knowledge of the attacker's own org's `webhook_secret`, which such an org admin legitimately possesses when they created their own GitHub App integration. The request is a direct unauthenticated HTTP POST to `/github/webhooks` (or equivalent mounted route), fully scriptable.

### Recommendation
After signature verification succeeds for organization X, enforce that every repository/organization reference used by the dispatched handlers (`repository.full_name`, `repository.owner.login`, and any commit lookup) actually belongs to organization X before processing. For `StatusHandler` specifically, scope the `Commit` lookup to commits under stacks belonging to the authenticated organization rather than a global, unscoped `Commit.where(sha:)`.

### Proof of Concept
1. Configure Shipit with the documented multi-org setup, e.g. `test/dummy/config/secrets_double_github_app.yml`, with `OrgOne` and `OrgTwo`. [11](#0-10) 
2. Attacker is the legitimate admin of `OrgOne`'s GitHub App and knows `OrgOne`'s `webhook_secret`.
3. Attacker POSTs to `/github/webhooks` with:
   - `X-Github-Event: status`
   - Body: `{"repository": {"owner": {"login": "OrgOne"}}, "sha": "<victim-org-two-commit-sha>", "state": "success", "context": "ci/attacker-forged"}`
   - `X-Hub-Signature: sha1=<HMAC-SHA1 of the raw body using OrgOne's webhook_secret>`
4. `verify_signature` computes `repository_owner == "OrgOne"`, fetches OrgOne's `GitHubApp`, and the HMAC check succeeds (attacker controls this secret).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the commit even though it belongs to `OrgTwo`'s stack — and calls `commit.create_status_from_github!(params)`, injecting a forged "success" status for a commit the attacker does not own, potentially unblocking it for deploy/merge in `OrgTwo`'s stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
