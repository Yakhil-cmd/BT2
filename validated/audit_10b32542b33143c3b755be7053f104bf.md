## Analog Found: Fee-on-transfer / rebasing ERC20 tokens break `ERC20Transactor`'s checking-account accounting on Asset Hub

### Title
XCM `ERC20Transactor` credits the nominal (requested) amount into the holding register instead of the amount actually received by the checking account, letting fee-on-transfer/deflationary ERC20 tokens under-fund `ERC20TransfersCheckingAccount` and break later legitimate withdrawals - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` moves an asset out of a user's account by calling the Solidity `IERC20::transfer(checking_account, amount)` on an arbitrary pallet-revive contract, then unconditionally credits the XCM holding register with the *requested* `amount` as soon as the call returns `true` [1](#0-0) . `deposit_asset_with_surplus` performs the mirror operation, transferring the recorded `amount` out of the shared `TransfersCheckingAccount` to the beneficiary, again trusting the boolean return value only [2](#0-1) . Neither function checks the checking account's actual `balanceOf` before and after the call. Any ERC20 contract matched by `Matcher`/`ERC20Matcher` (via `AccountKey20` locations) can therefore be a standard fee-on-transfer/deflationary token whose `transfer()` moves less than `amount` while still returning `true` - exactly the class of token targeted by the referenced report.

### Finding Description
`pallet-revive` allows any signed account to deploy arbitrary contracts, and `assets_common::ERC20Matcher`/`ERC20Transactor` treats any `AccountKey20`-keyed location as a valid fungible "ERC20" asset for XCM purposes, with no registration or vetting step - confirmed by the existing test that deploys a fresh contract and immediately uses it as an XCM asset [3](#0-2) . `pallet_xcm::execute`, wired into `AssetHubWestend`'s `AssetTransactors` tuple together with `ERC20Transactor` [4](#0-3) , is a real, permissionless, signed-extrinsic entry point.

For any such ERC20 asset, `withdraw_asset_with_surplus`:
- calls `transfer(checking_account, amount)` on the token contract from the origin,
- checks only that the call didn't revert and that the ABI-decoded return value is `true`,
- then creates `AssetsInHolding::new_from_fungible_credit(what.id, Erc20Credit(amount))` using the *nominal* `amount`, not any measured delta of the checking account's balance.

A fee-on-transfer ERC20 (a common, legitimate token pattern - e.g. transfers taxed by 1% to a fee sink) will move only `amount - fee` into the checking account while still returning `true`. The transactor has no way to detect this and simply asserts the checking account now backs `amount` of "ERC20 credit" in the XCM holding register.

Symmetrically, `deposit_asset_with_surplus` later debits the checking account by the *recorded* `amount` (not by what is actually needed/available), again trusting only the boolean return. Over repeated withdraw/deposit cycles of the same fee-on-transfer token by different, non-malicious users, the checking account's *real* on-chain balance in that ERC20 contract falls behind the sum of amounts the XCM executor believes it is holding on the chain's behalf. Once the deficit exceeds the checking account's real balance, a legitimate user's `deposit_asset_with_surplus` call will hit an ERC20 `transfer` that reverts for insufficient balance (or, for tokens that clamp/truncate instead of reverting, silently pays out less than intended) - this is precisely the "last person to withdraw can't" failure mode from the report, translated to Polkadot SDK's XCM/pallet-revive ERC20 bridging path, with the violated invariant being "checking account real balance == sum of currently-held nominal ERC20 credits in the XCM holding registers for that asset."

### Impact Explanation
This breaks fungibility/availability guarantees for any ERC20 asset with fee-on-transfer or otherwise non-1:1 transfer semantics that is bridged through the shared `ERC20TransfersCheckingAccount`. Legitimate holders of such a token can have their `DepositAsset`/withdraw XCM instructions fail (funds trapped, requiring manual `ClaimAsset` recovery, or in truncating-token designs, silent underpayment to beneficiaries) purely because of a deficit created by other, unrelated users' prior transfers of the same token. This is a fund-availability/integrity issue reachable by ordinary signed users with no privileged role, matching the Medium-severity classification of the analogous report (accounting desync from a non-standard-but-lawful token behavior causing operational failure for other users, not an unbacked-issuance/critical loss).

### Likelihood Explanation
Fee-on-transfer/deflationary ERC20 contracts are a very common, well-known token pattern (tax tokens, reflection tokens, burn-on-transfer tokens) that require no special exploit code - any user can legitimately deploy one via `pallet_revive::instantiate`/`instantiate_with_code` and register/use it as an XCM asset without any admin approval, since the `ERC20Matcher` accepts any `AccountKey20` location. Triggering the underlying accounting mismatch only requires performing ordinary `pallet_xcm::execute` withdraw/deposit operations with such a token - no forged proofs, no governance, and no race condition are needed.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the checking account's (or beneficiary's) actual `balanceOf` before and after the `transfer` call and use that delta - not the nominal `amount` - to construct/consume the `Erc20Credit` in the XCM holding register. This mirrors how native FRAME token traits (`fungible`/`fungibles::Mutate::transfer`) always return the *actual* transferred amount rather than assuming the requested one [5](#0-4) [6](#0-5) .

### Proof of Concept
- Reachable boundary: confirmed via the existing integration test that deploys an arbitrary pallet-revive contract and drives it through `pallet_xcm::execute`'s `withdraw_asset`/`deposit_asset` using `ERC20Transactor` [3](#0-2) .
- Failed guard: `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` check only `did_revert()` and the ABI-decoded boolean return of `IERC20::transfer`, never comparing `balanceOf` before/after [7](#0-6) [8](#0-7) .
- No local execution was run against this repository as part of this analysis; this is a static-analysis-derived analog requiring a background engineering session to write and run a concrete integration reproduction (deploy a minimal fee-on-transfer PVM/EVM ERC20 contract, execute repeated `withdraw_asset`/`deposit_asset` XCM programs through `pallet_xcm::execute` on `AssetHubWestend`'s test runtime, and assert that the checking account's real ERC20 balance falls below the sum of nominal amounts credited, causing a subsequent legitimate `deposit_asset` to fail).

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});

	fn transfer(
		asset: Self::AssetId,
		source: &AccountId,
		dest: &AccountId,
		amount: Self::Balance,
		preservation: Preservation,
	) -> Result<Self::Balance, DispatchError> {
		let _extra = Self::can_withdraw(asset.clone(), source, amount)
			.into_result(preservation != Expendable)?;
		Self::can_deposit(asset.clone(), dest, amount, Extant).into_result()?;
		if source == dest {
			return Ok(amount);
		}

		Self::decrease_balance(asset.clone(), source, amount, BestEffort, preservation, Polite)?;
		// This should never fail as we checked `can_deposit` earlier. But we do a best-effort
		// anyway.
		let _ = Self::increase_balance(asset.clone(), dest, amount, BestEffort);
		Self::done_transfer(asset, source, dest, amount);
		Ok(amount)
	}
