### Title
Route-selected contracts can execute arbitrary token transfers under the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller’s swap strategies authenticate the account owner or delegate, then pass attacker-influenced opaque `swap` bytes to the configured router inside the same authorization context. Because routes can name arbitrary venue contract addresses, a malicious venue can request authorization for unrelated operations—such as transferring any token held by the caller—to the attacker. Transaction simulation records that transfer as a child of the caller’s controller authorization; if the caller signs the generated tree, the malicious transfer executes even though the user intended to authorize only the lending strategy.

### Finding Description
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and the conversion path of `multiply` all funnel user-controlled route bytes into `swap_tokens_or_passthrough()` or `swap_tokens()`. Each strategy first calls `require_authorized_caller()`, which invokes `caller.require_auth()` [1](#0-0) . For example, `process_swap_collateral` authenticates `caller`, verifies account ownership, then passes the caller’s `swap` bytes to `withdraw_and_swap_from_supply()` [2](#0-1) .

`swap_tokens()` snapshots only the controller’s input and output token balances, authorizes the controller’s exact input transfer to the router, and invokes `router.execute_strategy(&controller, &amount_in, swap)` [3](#0-2) . Those checks constrain the controller’s token balance, but they do not constrain which contracts the route causes the router to invoke or which `require_auth` calls those contracts issue against the original caller. The authorization helper only bounds the controller-to-router input transfer; it does not sandbox the authorization tree for other calls made below the user-authorized controller invocation [4](#0-3) .

The regression test demonstrates the resulting boundary violation: a router route invokes an attacker-selected hop contract, and that contract calls `token.transfer(victim, attacker, amount)` for a token unrelated to the lending markets [5](#0-4) . Simulation records the theft as a child invocation under Alice’s `swap_collateral` authorization [6](#0-5) . With an honest tree containing no child transfer, enforcing authorization rejects it; with the simulated poisoned tree, the victim’s unrelated token balance is transferred to the attacker [7](#0-6) .

### Impact Explanation
An attacker can steal arbitrary token balances from a user who signs a malicious strategy authorization tree. The stolen assets need not be supplied collateral, borrowed assets, or even assets listed by the lending protocol. The lending operation itself can complete normally—the test receives the expected collateral output—so the user may see a successful collateral swap while unrelated wallet funds are drained [8](#0-7) .

This maps directly to the missing userspace-boundary check class: the strategy grants a caller’s privileged authorization to route-selected code without an `access_ok`-style restriction that confines it to the intended token pull and position operation. The monetary damage is theft of user funds.

### Likelihood Explanation
Exploitation requires a malicious route to reach a victim and the victim to sign the simulated authorization tree containing the extra transfer. Attackers commonly control route construction through malicious frontends, compromised route providers, phishing payloads, or manipulated transaction builders. The extra authorization is included in the tree by honest simulation rather than hidden by protocol validation, but users and integrations may not inspect every child invocation before signing.

The vulnerable entrypoints are normal unprivileged user paths, including `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`. No administrator, oracle manipulation, leaked key, or protocol account compromise is required once the victim signs the route-specific transaction.

### Recommendation
Do not execute arbitrary route-selected contracts inside a caller-authorized account operation. Require the swap router to invoke only governance- or router-allowlisted venue implementations and pool contracts, and reject route hops whose resolved venue addresses are not admitted. The allowlist must cover the addresses actually invoked, not merely the token whitelist used for fee placement.

Additionally, define and enforce a maximum authorization shape for every strategy. Clients should reject any `multiply`, `swap_debt`, `swap_collateral`, or `repay_debt_with_collateral` simulation containing child invocations outside the documented token pulls. The controller should reject opaque strategy payloads unless the configured router provides this venue isolation, since controller-side balance deltas cannot bound authorization-tree misuse.

### Proof of Concept
1. Alice owns a lending account holding USDC collateral and also holds `WALLET_BALANCE` units of an unrelated token.
2. The attacker deploys a route-compatible contract whose `swap()` method calls `token.transfer(alice, attacker, WALLET_BALANCE)` on that unrelated token.
3. The attacker supplies Alice a `swap_collateral` route whose hop pool address is the malicious contract.
4. Alice simulates `swap_collateral(caller=alice, account_id=alice_id, current=USDC, amount=SWAP_IN_USDC, new=ETH, swap=route)`.
5. Simulation records a root authorization for controller `swap_collateral` containing a child `unrelated_token.transfer(alice, attacker, WALLET_BALANCE)` invocation.
6. Alice signs the returned authorization tree. The venue’s transfer is accepted, Alice’s unrelated wallet token balance becomes zero, and the attacker receives it, while the expected ETH collateral output is still credited.

The repository’s regression test implements this exact sequence: it registers a router that invokes the route’s hop address, deploys a `RogueHopPool` that transfers the victim’s unrelated wallet token, records the poisoned authorization tree, and confirms the transfer succeeds only when that child invocation is signed [9](#0-8) [7](#0-6) .

    });

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();

    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),

            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),

        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
