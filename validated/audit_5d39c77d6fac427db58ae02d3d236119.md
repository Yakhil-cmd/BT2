### Title
Webhook signature verification keyed on attacker-controlled `repository.owner.login` is decoupled from the `repository.full_name` used to select the target repository/organization scope - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the HMAC signature against by reading `repository_owner`, derived from the **unauthenticated** JSON body (`params.dig('repository', 'owner', 'login')`), before the signature has been verified. Every webhook handler that actually resolves the target `Repository`/`Stack` (e.g. `PushHandler`, `MembershipHandler`'s `Team#organization`, the `PullRequest` handlers) instead uses a *different* attacker-controlled field, `repository.full_name` (or `organization.login` for membership events). Nothing in the engine enforces that the organization used to pick the verification secret is the same organization/repository that the payload is actually applied to. ### Finding Description
This is the direct analog of the reported `LockPositionService::increaseLockTime` bug: the report's root cause is that the value **used to compute an effect** (`block.timestamp`, i.e. current unaligned time) is not the same value that the system **conceptually commits to** (the cycle-aligned start time), so an attacker/user can get a materially different, unintended outcome purely by timing their action near a boundary. Here, the value used to select the **trust anchor** (which org's `webhook_secret` legitimizes the request) is not the same value used to determine **what gets mutated** (which repository/stack/team the payload acts on):

- `verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner)` to fetch that org's `GitHubApp`, whose `verify_webhook_signature` is then checked against the raw body using that org's `webhook_secret`.
- Crucially, `verify_webhook_signature` short-circuits to `true` if the target organization's `webhook_secret` is blank/unset: `return true unless webhook_secret`. Multi-tenant Shipit deployments (as documented in the shipped sample, `config/secrets.development.shopify.yml`, which shows `webhook_secret: # nil` as a valid/expected state per organization) can have one organization configured without a webhook secret while others have one.
- Once `verify_signature` passes (via the no-secret organization), `WebhooksController#create` dispatches `params` unchanged to the event handlers, none of which re-derive or check `repository_owner`. They instead resolve the actual target repository via `Handler#repository_name` (`payload.dig('repository', 'full_name')`) or, for the `membership` event, via `params.organization.login` directly (`MembershipHandler#find_or_create_team!`).

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` / `organization.login` (used to determine what is actually mutated) are two independent, fully attacker-controlled JSON fields with no cross-check, an attacker can craft a single JSON body where:
- `repository.owner.login` = an organization configured in this Shipit instance with no `webhook_secret` (satisfies signature check trivially), while
- `repository.full_name` / `organization.login` = a **different**, victim organization/repository actually configured with a real stack and a real `webhook_secret`.

The binding that should hold is: `organization whose secret authenticated the request == organization/repository the payload is applied to`. This engine breaks that equality because the two are read from independent, unauthenticated fields before any signature check occurs.

### Impact Explanation
This crosses directly into the specified High-impact categories:
- **Escalation into `Shipit.github_teams` authorization**: `membership` events reach `MembershipHandler`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` and then `team.add_member(member)` for an arbitrary GitHub login supplied in `params.member.login`. Since `User#authorized?` gates application access purely on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, an attacker who can forge a `membership` webhook (by piggybacking on a no-secret organization's identity while naming a privileged team/organization in the body) can add an arbitrary user to a `Shipit.github_teams` team record, bypassing GitHub-side team membership entirely.
- **Unauthenticated write of stack state**: `push` events reach `PushHandler`, which resolves stacks via `full_name` and calls `stack.sync_github(expected_head_sha: params.after)` — this can be triggered against any configured stack under the victim org/repo despite the request never being validated with that org's real secret.

### Likelihood Explanation
Requires only that at least one organization configured on the Shipit instance has no `webhook_secret` set — an explicitly supported and documented configuration state (see the shipped sample secrets file), not a hypothetical misconfiguration outside the engine's own code. No GitHub credentials, API tokens, or authenticated Shipit session are needed; the attacker only needs the engine's public `/webhooks` endpoint and knowledge of another tenant organization/repository name configured on the same instance, which is typically discoverable (Shipit stack pages, repo slugs in URLs, etc.).

### Recommendation
`verify_signature` must not use an unauthenticated, attacker-supplied field to choose the trust anchor unless it is exactly the same field the handlers subsequently use to resolve targets. Concretely:
- Derive `repository_owner` from the same canonical field the handlers use (`repository.full_name`'s owner segment, or `organization.login` for membership), and require the two to be textually the same value the handlers will read — ideally by binding it once and passing it explicitly into the handler dispatch rather than re-parsing `params` independently.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank in production; treat a missing secret for a configured organization as a hard misconfiguration (fail closed, not open), or require a global default secret with no fallback bypass.
- After signature verification, re-validate that `repository.owner.login` (or `organization.login`) matches the actual repository found via `repository.full_name` before dispatching to handlers, and reject mismatches with 422.

### Proof of Concept
1. Configure Shipit (as in the shipped sample `config/secrets.development.shopify.yml`) with two organizations: `attacker-org` (no `webhook_secret`) and `victim-org` (real `webhook_secret`, real stacks, and a `Shipit.github_teams` team used for authorization).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "Victim Admins", "slug": "victim-admins", "url": "https://github.com/..." },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-handle" },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. `verify_signature` computes `repository_owner = "attacker-org"`, loads `attacker-org`'s `GitHubApp` (no `webhook_secret`), and `verify_webhook_signature` returns `true` unconditionally — no valid `X-Hub-Signature` is even required.
4. `MembershipHandler#process` runs using `params.organization.login == "victim-org"` and adds `attacker-github-handle` to (or creates) team id `1` under `victim-org`, potentially satisfying `Shipit.github_teams` membership checks in `User#authorized?` and granting the attacker access to `victim-org`'s Shipit instance.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
