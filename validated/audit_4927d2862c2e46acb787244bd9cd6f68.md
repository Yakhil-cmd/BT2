### Title
Unfiltered PR-label-derived environment variables reach `PTY.spawn` via `Command#unbundled_env`, enabling generalized interpreter-hijack RCE (not limited to `RUBYOPT`) - ([File: app/models/shipit/review_stack.rb])

### Summary
`Shipit::ReviewStack#env` converts every GitHub pull-request label name into an environment-variable key with value `"true"` and merges it into the stack's environment with no whitelist. That environment flows unfiltered through `TaskCommands#env` / `DeployCommands#env` into `Command#unbundled_env`, which is exactly what `PTY.spawn` executes with. Any interpreter-hijack variable name usable as an env var — `RUBYOPT`, `PYTHONPATH`, `PERL5LIB`, `DYLD_INSERT_LIBRARIES`, `LD_PRELOAD`, etc. — can be injected this way if the corresponding interpreter is invoked by any `deploy_spec.yml` step.

### Finding Description
Binding claimed and verified broken: `set(Command#unbundled_env.keys)` is **not** a subset of any operator-approved key list; it equals `BASE_ENV.keys ∪ {'PATH'} ∪ @env.keys`, and `@env` includes every upcased PR label name with no filter.

Code path:
- `Shipit::ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into `super` with no whitelist check at [1](#0-0) .
- Labels are attacker-controlled: `LabelCapturingHandler#capture_labels` does `pull_request.update!(labels: params.pull_request.labels.map(&:name))` directly from the webhook payload's `pull_request.labels[].name` field, with no format/length/charset validation on label names [2](#0-1) .
- `TaskCommands#env` merges `@stack.env` (i.e., `ReviewStack#env`) directly into the hash passed to `Command.new` for every deploy/task step, with no call to `EnvironmentVariables#permit` [3](#0-2) .
- `Command#unbundled_env` merges `BASE_ENV` with `PATH` and then `@env.stringify_keys` — the full stack/task env, unfiltered — and this exact hash is what's passed to `PTY.spawn` in `Command#start` [4](#0-3) .
- `EnvironmentVariables#permit`/`sanitize_env_vars` does exist as a whitelist mechanism, but it is only invoked via `Stack#build_deploy` (`filter_deploy_envs`) and `Stack#trigger_task` (`definition.filter_envs`) on the **user-supplied deploy/task env parameter**, not on `stack.env`/`ReviewStack#env` [5](#0-4) . It never touches label-derived keys, so it provides no protection here.

Exploit flow: An attacker who can open a PR against a repo with review stacks enabled (or push a label to their own fork's PR, which is entirely self-owned) applies a label named e.g. `pythonpath` (or `perl5lib`, `dyld_insert_libraries`, `ld_preload`). GitHub sends a `labeled` webhook; `LabelCapturingHandler` persists the label name verbatim; on next task/deploy run `ReviewStack#env` uppercases it to `PYTHONPATH` (etc.) and value `"true"`, this merges unfiltered into `Command`'s env, and if any `deploy_spec.yml` step in that repo's config invokes `python3` (or perl, or a dynamic-loader-honoring binary on macOS), the attacker's env var influences that interpreter's module/library search path — the same interpreter-hijack pattern as `RUBYOPT`, generalized to any interpreter honored by the deploy host.

### Impact Explanation
If the injected variable is honored by whatever binary the deploy steps invoke (Ruby via `RUBYOPT`, Python via `PYTHONPATH`, Perl via `PERL5LIB`, or dynamic loader variables like `LD_PRELOAD`/`DYLD_INSERT_LIBRARIES` on the relevant OS), this is Critical: arbitrary code execution on the deploy host under the Shipit worker's privileges, executed via `Command`/`PTY.spawn`. Because the label is attacker-controlled per-PR, it's repeatable against any repository that has review stacks enabled and whose deploy steps shell out to an interpreter honoring one of these variables. This is a generalization of an already-present unwhitelisted-env-key defect in `ReviewStack#env`, not a distinct new bug — the root cause (no key whitelist on label-derived env) is identical regardless of which downstream interpreter variable is targeted.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled, and its `shipit.yml` deploy/task/dependencies steps must invoke an interpreter or loader that honors an environment variable an attacker can inject via a label name (e.g. `python3`, `perl`, or any dynamically-linked binary). Attacker cost is trivial — labeling one's own PR requires no special privilege beyond being able to open a PR/label it, which is explicitly in the unprivileged threat model. No Shipit or GitHub secret is needed. Feasibility depends entirely on the operator's `shipit.yml` content; it is not universal to every Shipit install, but wherever such a step exists, the exploit is deterministic and repeatable on every task/deploy run.

### Recommendation
Whitelist or reject the environment keys derived from PR labels in `Shipit::ReviewStack#env` (e.g., only allow keys matching an explicit prefix such as `LABEL_<name>`, or run them through `EnvironmentVariables#permit` against an operator-defined list) instead of merging raw uppercased label names directly into the process environment reaching `Command`/`PTY.spawn`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (conceptual addition)
test "#env does not allow interpreter-hijack variable names via labels" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["pythonpath", "perl5lib", "dyld_insert_libraries"]

  env = stack.env

  # Binding under test: keys derived from PR labels must be a subset of an
  # operator-approved whitelist, not blindly merged into the process env.
  dangerous_keys = %w[PYTHONPATH PERL5LIB DYLD_INSERT_LIBRARIES LD_PRELOAD RUBYOPT]
  assert_empty(env.keys & dangerous_keys,
    "PR label names must not be able to set interpreter/loader env vars, " \
    "but got: #{(env.keys & dangerous_keys)}")
end
```
This assertion currently fails: `env["PYTHONPATH"]`, `env["PERL5LIB"]`, and `env["DYLD_INSERT_LIBRARIES"]` are all `"true"` because `ReviewStack#env` performs no key filtering, demonstrating the absence of any whitelist for label-derived environment keys.
