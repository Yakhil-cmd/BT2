### Title
Cross-repository SHA collision in `StatusHandler` lets an attacker-controlled repository's `status` webhook forge `commit_status` hook deliveries for an unrelated stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/commit.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` with no scoping to the repository that actually sent the webhook, unlike every other handler (`PushHandler`, `CheckSuiteHandler`) which use the repository-scoped `stacks` helper. A GitHub `status` event that is legitimately signed for repository B (attacker-controlled) can therefore update the status of, and trigger `Hook.emit(:commit_status, ...)`/`DeliverHookJob` for, an unrelated stack A's commit whenever a byte-identical commit (same sha) exists in both repositories.

### Finding Description
The broken binding the question assumes: `commit_status hook emitted for stack A ⇒ status verified via stack A's own repository/webhook`. In code this should mean `handler scoped to repository_owner/full_name of the incoming payload == stack.repository of the commit being updated`.

Tracing the path:
1. `WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which validates the signature only against `Shipit.github(organization: repository_owner)` — i.e. it proves the payload really came from GitHub for repo B's organization, not that repo B is related to any particular stack. [1](#0-0) 
2. `StatusHandler#process` then runs:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no repository filter at all. [2](#0-1) 
3. Contrast with the base `Handler#stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)` from the payload's `repository.full_name` and scopes queries to that repository's stacks — used correctly by `PushHandler` and `CheckSuiteHandler` but never by `StatusHandler`. [3](#0-2) [4](#0-3) 
4. `Commit#create_status_from_github!` → `add_status` computes the new aggregate `status`, and if it changed, calls `Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status))` where `stack` is whatever stack owns the matched `Commit` row (stack A), independent of which repository's webhook triggered the update. [5](#0-4) 
5. `Hook.emit`/`Hook.deliver` enqueue `DeliverHookJob`, which POSTs to stack A's operator-configured `delivery_url`, signed with stack A's own `webhook_secret` (`Hook::DeliverySigner`), so the receiving system has no way to know the trigger actually originated from an unrelated repository.

Exploit flow: an attacker (any GitHub user) forks/clones stack A's public repository, obtaining a commit with sha `S` that is identical (parents, tree, author/committer, timestamps, message) to a commit already ingested into Shipit for stack A. They push that byte-identical commit into a repository B they own (any account/org, no special privilege). Because git commit ids are content-addressed, pushing the identical content to a different repository yields the same sha `S`. The attacker then uses the ordinary GitHub Statuses API on repo B (standard write access to their own repo) to set `state: success` on sha `S`. GitHub emits a real, correctly-signed `status` webhook for repo B (signed by GitHub itself if repo B's owner org has the Shipit GitHub App installed - the attacker never needs to know any Shipit secret). `verify_signature` passes because the payload genuinely came from GitHub for repo B's owner. `StatusHandler#process` then matches `Commit.where(sha: S)` across the whole database, including stack A's row, and calls `commit.create_status_from_github!`, which fires `Hook.emit(:commit_status, stack_A, ...)` and enqueues `DeliverHookJob` to stack A's hook URL, claiming success for stack A's commit — entirely as a side effect of repo B's unrelated status event.

Existing guards fail to prevent this because: `verify_signature` only authenticates "this payload is really from GitHub for org/owner X," never "commit X belongs to a stack backed by that same repository"; `drop_unhandled_event` only checks the event type has a registered handler; the `StatusHandler`'s `ExplicitParameters` schema validates payload shape, not repository identity; and there is no `stacks`/repository filter applied before the `Commit.where(sha:)` lookup, unlike `PushHandler`/`CheckSuiteHandler`.

### Impact Explanation
A payload legitimately originating from repository B causes a database write (`Status` record) and an outbound webhook delivery (`DeliverHookJob`) attributed to stack A's commit and repository, without any authentication tying B to A. This is "a payload for one repository mutating another's stack/commit," matching the Critical category. Any third-party system that treats Shipit's `commit_status` hook payload (with stack A's own webhook secret) as authoritative proof that CI passed for stack A can be tricked into authorizing a downstream action (e.g., unlocking a deployment gate) based on an event that never happened on stack A's own CI. The attack is repeatable against any stack whose commit history overlaps (via fork, mirror, subtree copy, or attacker-reconstructed identical commit) with a repository the attacker controls, and requires no privilege on stack A, its repository, or Shipit itself.

### Likelihood Explanation
Preconditions: (1) the attacker must be able to produce a commit with an identical sha to one already synced into Shipit for stack A — trivial via forking/cloning a public (or attacker-accessible) repository and pushing to their own repo, since git commit hashes are pure content hashes independent of the hosting repository; (2) the attacker's repository must belong to an account/org where GitHub can generate a validly signed webhook that passes `Shipit.github(organization: repository_owner)` — i.e., the Shipit GitHub App/webhook integration must be reachable for that owner (this is normally true for any GitHub App installed broadly, or any org the attacker is a member of that already onboarded Shipit). No Shipit secrets, sessions, or tokens are needed; the attacker only needs ordinary GitHub write access to a repository they control, which is explicitly in scope for "unprivileged" attackers per the rules.

### Recommendation
Scope `StatusHandler#process` to the repository that sent the webhook, mirroring `PushHandler`/`CheckSuiteHandler`, e.g. resolve commits through `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` (using the base `Handler#stacks` helper keyed off `repository.full_name`) instead of the global `Commit.where(sha: params.sha)`, so a matched commit's stack must belong to the repository identified in the payload.

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/status_handler_test.rb` (new file) or `test/controllers/webhooks_controller_test.rb`:

```ruby
test "a status webhook for repository B does not fire commit_status hooks for stack A's identical-sha commit" do
  stack_a = shipit_stacks(:shipit) # backed by repository "shopify/shipit-engine" (repo A)
  commit_a = stack_a.commits.create!(sha: 'deadbeef' * 5, ...) # existing commit tracked for stack A

  hook = Hook.create!(stack: stack_a, delivery_url: 'https://internal-gate.example.com/hooks',
                       events: ['commit_status'], secret: 'stack-a-secret')

  # Forged/foreign payload: repository field points at repo B, owned by the attacker,
  # but sha matches commit_a (content-identical commit pushed to repo B).
  payload = {
    'sha' => commit_a.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate a genuinely GitHub-signed event for repo B

  assert_no_enqueued_jobs only: DeliverHookJob do
    @request.headers['X-Github-Event'] = 'status'
    post :create, body: payload.to_json, as: :json
  end

  # Binding under test:
  #   before: commit_a.state == 'unknown/pending' AND hook not delivered for repo B's event
  #   after:  commit_a.state must remain unchanged, no DeliverHookJob referencing stack_a enqueued
  commit_a.reload
  refute_equal 'success', commit_a.state
end
```

With the current implementation (`Commit.where(sha: params.sha)` unscoped by repository in `app/models/shipit/webhooks/handlers/status_handler.rb`), this test fails: `DeliverHookJob` is enqueued and `commit_a.state` becomes `'success'`, proving stack A's `commit_status` hook fires as a side effect of repository B's webhook.
