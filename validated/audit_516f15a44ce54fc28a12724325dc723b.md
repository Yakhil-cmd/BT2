### Title
Missing `return` after caught exception causes double execution and double callback in private-payment handling - (File: network.js)

### Summary
In `handleSavedPrivatePayments()`, the inner `validateAndSave` function computes `json_payload_hash` inside a `try/catch`. When `objectHash.getBase64Hash()` throws, the `catch` block logs the error, notifies the peer, and calls `deleteHandledPrivateChain(..., cb)` — but it never `return`s. Execution falls through to the code after the `try/catch`, which builds `key` using the now-undefined `json_payload_hash` and calls `privatePayment.validateAndSavePrivatePaymentChain(...)` again, whose callbacks (`ifOk`/`ifError`/`ifWaitingForChain`) also eventually call `cb` a second time. This mirrors the CVE-2021-38114 pattern: a failure signal from a called function (`init_vlc`'s return value / here, the thrown exception path) is not properly acted upon, so processing continues on invalid/incomplete state instead of aborting.

### Finding Description
The relevant code: [1](#0-0) 

```
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

`getBase64Hash` internally calls `getJsonSourceString`/`getSourceString` on the untrusted `objHeadPrivateElement.payload` that came from an attacker-controlled, stored `unhandled_private_payments.json` row (populated from a private payment received from any peer/private-payment counterparty) [2](#0-1) . `getSourceString`/`getJsonSourceString` can throw for malformed/unexpected payload shapes (e.g., unsupported types, structural issues), which is exactly the kind of "similar issue" class the CVE describes: a called routine's failure indication is not checked/handled correctly, and execution proceeds using an invalid/uninitialized result.

Because the `catch` block does not `return` after calling `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`:
1. `deleteHandledPrivateChain` asynchronously deletes the row and, on completion, calls `cb()` — advancing `async.each`'s iterator once.
2. Execution simultaneously continues synchronously to build `key` (with `json_payload_hash === undefined`) and invoke `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the same, now-deleted-from-queue private element.
3. That second call's callbacks (`ifOk`, `ifError`, or `ifWaitingForChain`) each also call `cb()` (directly or via `deleteHandledPrivateChain`), and on the `ifOk` path additionally emit `"new_direct_private_chains"`/`"new_my_transactions"` and populate `assocNewUnits`.

This produces two independent completions of the same `async.each` iteration item (calling `cb` twice), which can corrupt the `async.each` control flow (double invocation of the final callback, `unlock()` potentially called out of turn, or the whole `handleSavedPrivatePayments` mutex getting unlocked/relocked incorrectly), and lets a private-payment chain be processed and potentially accepted/saved via `validateAndSavePrivatePaymentChain` even though the head element already failed integrity hashing and its DB row was deleted. This is reachable purely by any private-payment counterparty sending a malformed/crafted private payment chain to the victim's wallet.

### Impact Explanation
Double-invocation of `cb` inside `async.each` and out-of-order/duplicate calls to `deleteHandledPrivateChain` and `privatePayment.validateAndSavePrivatePaymentChain` on the same private-chain entry can lead to inconsistent processing state in the receiving wallet: private payments accepted/emitted (`new_my_transactions`, `new_direct_private_chains`) despite a hashing failure on the head element, or duplicate/racy database operations on `unhandled_private_payments`. This can cause the wallet to disagree on the validity of a private payment or process malformed private-payment data it should have rejected outright, which falls within the "node disagreement on validity" / "private-payment counterparty" reachable impact categories.

### Likelihood Explanation
Reaching this path requires only that a private-payment counterparty send a private-payment chain whose head element's `payload` triggers an exception in `getSourceString`/`getJsonSourceString` (e.g., malformed structure that isn't rejected earlier by chain validation before this hashing step). Since `handleSavedPrivatePayments` operates on payloads already stored to `unhandled_private_payments` (received directly, not necessarily fully validated yet at this stage), a crafted payload from any device/peer sending private payments could exercise this bug.

### Recommendation
Add a `return` statement after the calls inside the `catch` block in `network.js`'s `validateAndSave` function so execution does not fall through to use the undefined `json_payload_hash` or make a second, redundant call to `privatePayment.validateAndSavePrivatePaymentChain`:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```

### Proof of Concept
1. As a private-payment counterparty, send/deliver a private-payment chain whose head element's `payload` field is a value that causes `string_utils.getSourceString`/`getJsonSourceString` to throw (e.g., a payload shape not covered by the source-string serializer) while still passing earlier syntactic checks that allow it to be persisted in `unhandled_private_payments`.
2. Wait for/trigger `handleSavedPrivatePayments()` to process the row (called from multiple internal locations, e.g. `network.js:2443`).
3. Inside `validateAndSave`, `objectHash.getBase64Hash` throws, entering the `catch` block, which calls `deleteHandledPrivateChain(..., cb)` (async DB delete + `cb()`), but execution also falls through synchronously to invoke `privatePayment.validateAndSavePrivatePaymentChain` again on the same `arrPrivateElements`.
4. Observe `cb` invoked twice for the same `async.each` item and/or a second, unintended validation/save attempt proceeding on payload data that already failed hash computation, and confirm via debug logging or by observing `assocNewUnits`/`new_my_transactions` events firing inconsistently with the deleted `unhandled_private_payments` row. function getBase64Hash(obj, bJsonBased) {
	var sourceString = bJsonBased ? getJsonSourceString(obj) : getSourceString(obj)
	return crypto.createHash("sha256").update(sourceString, "utf8").digest("base64");
}
