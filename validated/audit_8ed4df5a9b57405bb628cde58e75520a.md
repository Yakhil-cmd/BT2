## Title
Cross-Stack Authorization Bypass in CCMenu API — CCMenuController#stack Ignores ApiClient Stack Scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The Ammplify bug describes tokens whose declared behavior (safe ERC-20 semantics) is never actually enforced by the code path that trusts it, letting a token silently violate the contract's assumptions. The equivalent binding-break in shipit-engine is that an `ApiClient` token's declared authorization scope (`stack_id`) is enforced everywhere in the API *except* in `Shipit::Api::CCMenuController`, which resolves the target `Stack` directly from request params instead of going through the scoped `stacks` relation, breaking the equality "a stack a token authorises == a stack it touches."

### Finding Description
Every other API controller resolves the target stack through `Shipit::Api::BaseController#stack`, which is scoped to the client's authorized stack: [1](#0-0) 

`current_api_client.stack_id?` restricts the queryable stacks to only the one stack the client is scoped to (when scoped at all). This is the intended authorization binding: a stack token can only touch the stack it authorizes.

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model rather than through `stacks.from_param!`. The controller still enforces `require_permission :read, :stack`: [3](#0-2) 

so any valid `ApiClient` token that merely holds the `read:stack` permission — including one deliberately scoped to a single stack via `belongs_to :stack, optional: true` and `stacks.from_param!` elsewhere — can request `stack_id` for **any** other stack in the installation and the check silently succeeds because `Stack.from_param!` is queried on the full `Stack` table, not the client's authorized subset.

Existing tests confirm the intended scoping semantics hold for other endpoints (e.g. `"an api client scoped to a stack will only see that one stack"` in the stacks controller tests), while the CCMenu controller test suite exercises only the unscoped case: [4](#0-3) 

There is no test verifying that a stack-scoped client is rejected when requesting a *different* `stack_id` via CCMenu, because the code path never checks it.

### Impact Explanation
`CCMenuController#show` renders the target stack's `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` — deploy/build state for the stack: [5](#0-4) 

A token that is supposed to be restricted to a single stack (`current_api_client.stack_id`) can be used to read deploy/build status of any other stack in the Shipit installation, which is an authorization escalation beyond the scope the token was granted — matching the "escalation into authorization" / "unauthenticated read of stack state" impact class, since the requester is effectively unauthorized for the stack whose state is disclosed.

### Likelihood Explanation
Any holder of a valid, stack-scoped `ApiClient` token with `read:stack` permission can exploit this with a single unmodified HTTP request by simply changing the `stack_id` path segment — no privileged access, signature forgery, or additional credentials are required beyond the token they already legitimately possess.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (`stacks.from_param!(params[:stack_id])`) as `BaseController` does, instead of querying the unscoped `Stack` model, so the client's `stack_id` authorization binding is enforced consistently across all API controllers. The same should be verified for `Shipit::CCMenuUrlController#stack`, which has the identical unscoped pattern.

### Proof of Concept
1. Create (or use an existing) `ApiClient` scoped to `stack_id: A` (`belongs_to :stack`) with `permissions: ['read:stack']`.
2. Authenticate as that client and call `GET /api/stacks/*stack_id/ccmenu` with `stack_id` set to a *different* stack `B`'s param (`owner/repo/environment`).
3. Observe the response returns HTTP 200 with stack `B`'s build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.), even though the client's token is only authorized for stack `A`. [6](#0-5)
