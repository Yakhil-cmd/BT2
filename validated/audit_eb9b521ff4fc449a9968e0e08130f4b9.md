### Title
Webhook signature is verified against the organization named in `repository_owner`, but handlers act on unrelated `organization.login`/`repository.full_name`/`team.id` fields from the same unverified body — allowing cross-organization writes via any org with a weak/unset `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which HMAC secret) to check against solely from `repository_owner` (`repository.owner.login` or `organization.login`), and only proves that whoever crafted the raw body knows the secret configured for *that* organization key. It never revalidates that the other identity-bearing fields consumed later by handlers — `repository.full_name` (used to select the target `Stack`/`Repository`) and `organization.login`/`team.id` (used by `MembershipHandler` to create/modify `Team` membership) — actually belong to the same organization that was authenticated. This mirrors the ERC-4626 report's root cause: a check performed against one entity/field (`yieldVault.maxDeposit`) while the actual state-changing action is driven by a different, unchecked entity/field (`yieldVault.mint`).

### Finding Description [1](#0-0)  shows `verify_signature` picks `Shipit.github(organization: repository_owner)` and validates the raw POST body's HMAC against that single organization's `webhook_secret`. `repository_owner` is itself just JSON taken from the unauthenticated payload: [2](#0-1) 

`verify_webhook_signature` explicitly treats a missing secret as automatic success: [3](#0-2) 

Once verification passes for *whichever* organization was named in `repository_owner`, `create` blindly dispatches the entire body to handlers: [4](#0-3) 

Handlers then derive the actual target from *different* fields of the same body, which are never cross-checked against `repository_owner`:
- `Handler#repository_name` reads `repository.full_name` to select the `Stack` to sync/deploy against: [5](#0-4) 
- `MembershipHandler` reads `organization.login` and `team.id`/`team.slug` — fields totally independent of `repository_owner` — to create/find a `Team` and add an arbitrary `member.login` to it: [6](#0-5) 

Because GitHub itself always emits internally-consistent payloads (an event's `repository.owner.login`/`organization.login` always matches the actual `repository.full_name`/team being described), the engine never needed to enforce that consistency itself. But nothing stops an attacker who can get *any one* configured organization's webhook accepted (trivially, one with no `webhook_secret` set, per `return true unless webhook_secret`) from submitting a hand-crafted body where `organization.login`/`repository.owner.login` says one org (to satisfy `verify_signature`/`Shipit.github(organization:)` lookup) while `repository.full_name`, `team.id`, and `member.login` describe a completely different organization's stack or authorization team.

This directly parallels the report's binding break pattern "an organization that authenticated versus the repository that is written": the signature only authenticates *an* organization identifier, not the specific repository/team object that ends up mutated.

### Impact Explanation
The most severe consequence is via `MembershipHandler`: an attacker can forge a `membership` webhook naming a weakly-configured organization (satisfying signature verification), but set `team.id` to the GitHub team ID backing `Shipit.github_teams` and `member.login` to their own GitHub login. `MembershipHandler#process` looks the team up purely by `github_id` (no live GitHub API call is required if the team already exists) and calls `team.add_member(member)`, `User.find_or_create_by_login!` creating/mapping the attacker's `User` row. `authorized?` in `app/controllers/concerns/shipit/authentication.rb` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) then grants full authenticated access to the entire Shipit application — an escalation into `Shipit.github_teams` authorization (explicitly listed High-severity impact). Similarly, forging `push`/`status`/`check_suite` events with a `repository.full_name` pointing at a different org's stack can inject fake commit statuses/checks or trigger `GithubSyncJob`, undermining CI-gating used before deploys, and can constitute cross-repository writes into another organization's tracked stack data.

### Likelihood Explanation
Exploitation requires no privileged credentials, no `ApiClient` token, and no knowledge of any secret — only that the Shipit instance is configured with (or can be made to resolve) at least one organization entry whose `webhook_secret` is left blank (explicitly documented as optional: "If you've set a webhook secret during the App creation, you should copy it here"). Multi-organization installs are a first-class, documented configuration (`config/secrets.development.shopify.yml`), making this a realistic deployment shape rather than a contrived edge case.

### Recommendation
After `verify_signature` succeeds, re-derive and enforce that every organization/repository identifier consumed downstream (`repository.full_name`'s owner segment, `organization.login`, and any `team`/`repository` object referenced by a handler) is equal to the exact `repository_owner`/organization that was cryptographically verified for this request, rejecting the webhook otherwise. Additionally, require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), and for `MembershipHandler`, validate `team`/`organization` membership against the live GitHub API (or at minimum bind team lookups to the organization that was actually authenticated) rather than trusting `team.id`/`organization.login` from the payload verbatim.

### Proof of Concept
1. Configure (or find) a Shipit instance with multiple GitHub organizations where one, e.g. `low-sec-org`, has no `webhook_secret` set (a documented-valid configuration).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": {"login": "victim-org"},
  "team": {"id": <TEAM_ID_BACKING_SHIPIT_GITHUB_TEAMS>, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "member": {"login": "attacker-github-login"},
  "repository": {"owner": {"login": "low-sec-org"}, "full_name": "low-sec-org/whatever"}
}
```
3. `verify_signature` resolves `Shipit.github(organization: 'low-sec-org')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the (even absent) `X-Hub-Signature` header.
4. `MembershipHandler#process` runs using `params.organization.login` (`victim-org`) and `params.team.id`, adding the `attacker-github-login` user to the real authorization team, granting `Shipit.github_teams` access despite the attacker never authenticating with `victim-org`'s credentials.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```
