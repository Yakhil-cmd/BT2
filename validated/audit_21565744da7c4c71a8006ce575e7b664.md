### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App / `webhook_secret` to validate a webhook against using one payload field (`repository.owner.login` or `organization.login`), while every `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Stack`/`Repository` using a **different** payload field (`repository.full_name`). Nothing binds these two fields together, so in a multi-organization Shipit deployment an actor who controls the webhook secret for *one* configured GitHub organization can forge a signed payload whose `repository.owner.login` matches their own org (passing signature verification) while `repository.full_name` names a repository belonging to a completely different, unrelated org/stack hosted on the same Shipit instance.

### Finding Description
Signature verification: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `repository.owner.login`/`organization.login` and used solely to pick which org's `Shipit.github(organization:)` config (and thus which `webhook_secret`) verifies the HMAC signature.

Every handler, however, resolves the acted-upon repository from a different field, `repository.full_name`, completely independent of `repository.owner.login`: [3](#0-2) 

For example `PushHandler` looks up stacks by `repository_name` (i.e. `full_name`) and triggers `stack.sync_github`: [4](#0-3) 

and `CheckSuiteHandler` matches stacks by branch/SHA and schedules a check-run refresh, which feeds continuous-deployment gating: [5](#0-4) 

Multi-org support is a documented, first-class configuration (`config/secrets.development.shopify.yml`, `docs/setup.md:182-209`), where each org has its own independent `webhook_secret`: [6](#0-5) 

The binding that is broken is: `organization whose webhook_secret authenticated the request == organization owning the repository the handlers act on`. Because `verify_signature` checks the former from `repository.owner.login` and the handlers act on the latter from `repository.full_name`, these two are never cross-checked against each other. An attacker who is a legitimate GitHub org admin for **Org A** (with its own GitHub App installed on the same Shipit instance) can compute a valid `X-Hub-Signature` using Org A's `webhook_secret`, set `repository.owner.login = "OrgA"` (so verification passes) but set `repository.full_name = "OrgB/target-repo"` (a stack they do not control), and have it processed by every handler as if it legitimately originated from OrgB.

### Impact Explanation
This crosses a trust boundary between organizations that are supposed to be isolated by separate GitHub Apps/webhook secrets in a multi-tenant Shipit deployment. Concretely:
- `PushHandler` lets the attacker enqueue `GithubSyncJob` for any stack under any full_name with an attacker-chosen `expected_head_sha`, forcing a resync of a foreign stack.
- `CheckSuiteHandler` lets the attacker inject fabricated `head_sha`/`head_branch` check-suite completions for a foreign stack's commits, feeding `schedule_refresh_check_runs!` and the CI-status pipeline that continuous delivery relies on to decide whether a commit is ready to deploy — this can push an unrelated stack's continuous-deployment gate toward "ready", contributing to an unauthorized deploy on a repository the attacker does not own.
- `MembershipHandler` and `PullRequest::*` handlers similarly act on organization/repository identifiers taken from unverified payload fields once the (mismatched) signature check passes.

This is a cross-tenant authorization break reachable by anyone who legitimately administers one org's GitHub App webhook config on a shared Shipit instance, but who has no rights over other orgs' stacks — satisfying the "cross-repository writes / unauthorized deploy" impact bar for High severity in a multi-org setup.

### Likelihood Explanation
Requires the target Shipit instance to be configured with multiple GitHub organizations (a documented, supported configuration), and requires the attacker to control (or be a legitimate integrator for) at least one of those organizations' GitHub Apps in order to know/generate a valid webhook signature for that org. Given multi-org support exists specifically to let independent orgs share one Shipit instance without trusting each other, this is a realistic configuration where the trust break directly matters.

### Recommendation
- Bind signature verification to the same repository identity the handlers use: verify the signature using the org derived from `repository.full_name` (or verify that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name`) before dispatching to handlers.
- Alternatively, reject the payload if `repository.owner.login` does not match the owner segment of `repository.full_name`.
- Add a regression test asserting that a webhook signed by Org A's secret but referencing an Org B repository is rejected.

### Proof of Concept
1. Deploy Shipit with two GitHub orgs configured (`OrgA`, `OrgB`), each with a distinct `webhook_secret`, both hosting stacks on the same instance (per `docs/setup.md` multi-org setup).
2. As an administrator of `OrgA`'s GitHub App, compute `X-Hub-Signature = sha1=HMAC(OrgA_webhook_secret, body)` for a crafted `push` payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
   }
   ```
3. POST to `/webhooks` with header `X-Github-Event: push` and the computed signature.
4. `verify_signature` looks up `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret [1](#0-0) .
5. `PushHandler` resolves stacks via `repository.full_name == "OrgB/target-repo"` [3](#0-2)  and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` for a stack the attacker does not own.
