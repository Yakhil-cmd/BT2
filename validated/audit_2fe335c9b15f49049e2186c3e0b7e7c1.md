### Title
Missing `webhook_secret` for any configured GitHub organization globally disables `X-Hub-Signature` verification for that org's `/webhooks` traffic - ([File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` delegates verification to `GitHubApp#verify_webhook_signature`, which explicitly returns `true` when the resolved organization's `webhook_secret` is blank, regardless of the `X-Hub-Signature` header. Because `Shipit.github(organization: repository_owner)` is selected purely from the attacker-controlled `organization.login` (or `repository.owner.login`) field in the POST body, any request whose org field matches a configured org that lacks a `webhook_secret` is accepted unauthenticated, letting `MembershipHandler#process` create/mutate `Team`/`Membership` rows for that org with no valid signature at all.

### Finding Description
The broken binding: the app assumes `verified == true` implies `HMAC-SHA1(webhook_secret, raw_post) == X-Hub-Signature`, but `GitHubApp#verify_webhook_signature` short-circuits: [1](#0-0) 
`return true unless webhook_secret` means when `@webhook_secret` is nil/blank for the resolved org config, the method returns `true` unconditionally — the header is never inspected.

The org used to pick the `GitHubApp` instance is taken straight from request JSON: [2](#0-1) [3](#0-2) 
and resolution is case-insensitive because `github_app_config` downcases both the stored keys and the supplied organization name: [4](#0-3) 

Exploit flow: an attacker with no Shipit credentials POSTs to `/webhooks` with `X-Github-Event: membership` and a body whose `organization.login` matches (case-insensitively) any org configured in `secrets.github` that has no `webhook_secret` set — no `X-Hub-Signature` header (or a garbage one) is required. `verify_signature` calls `verify_webhook_signature` which returns `true`, so the request proceeds to `create`, which dispatches to `MembershipHandler#process`, creating/mutating a `Team` and `User`/membership row: [5](#0-4) 
None of `drop_unhandled_event`, the `ExplicitParameters` schema, or `check_if_ping` perform any authentication check — they only gate on event type/params shape, not on signature.

### Impact Explanation
Per configured organization lacking a `webhook_secret`, an unauthenticated attacker can forge arbitrary `membership`/other webhook events (`push`, `status`, `check_suite`, etc., since the same `verify_signature` gate covers all events) and have them processed as if GitHub sent them — this is an authentication bypass on the entire webhook ingestion pipeline for that org, matching the Critical "forged webhook accepted" category. Blast radius is scoped to organizations whose config omits `webhook_secret`; orgs with a secret configured are unaffected because `verify_webhook_signature` performs the real HMAC/`secure_compare` check for them.

### Likelihood Explanation
This requires a real precondition: the deployed Shipit instance must have at least one entry in `secrets.github` (single- or multi-org) with `webhook_secret` unset/blank — this is a legitimate, documented configuration state (`config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`/`secrets_double_github_app.yml` all show `webhook_secret: # nil` as an accepted value). Given that precondition, exploitation cost is a single unauthenticated HTTP POST with no secrets needed, and it is fully repeatable against any event type for that org.

### Recommendation
Do not treat a missing `webhook_secret` as "verification passed." Either require `webhook_secret` to be present for every configured organization at boot (fail fast / refuse to start), or make `verify_webhook_signature` reject (return `false`)/require operators to opt into an explicit "unsigned webhooks allowed" flag rather than defaulting to a silent bypass. At minimum, log/alert loudly when a webhook is accepted purely because no secret was configured, and document that omitting `webhook_secret` disables authentication for that org's entire webhook surface.

### Proof of Concept
Minitest plan (mirrors existing `test/controllers/webhooks_controller_test.rb` membership tests, e.g. lines 129-140):
1. Configure the test dummy app's `Shipit.github(organization: 'target-org')` (or reuse `secrets_double_github_app.yml`'s `OrgTwo`, which already has `webhook_secret: # nil`) with no `webhook_secret`.
2. `post :create` with `request.headers['X-Github-Event'] = 'membership'` and no `X-Hub-Signature` header (or an arbitrary bogus value), body = `membership_params.merge(organization: { login: 'OrgTwo' }, team: {...}, member: { login: 'attacker' })`.
3. Assert `response.status == 200` and `assert_difference('Team.count', 1)` / a `Membership`/`User` row is persisted for `attacker`, proving the equality `verified == (valid HMAC signature present)` is false: `verified` is `true` even though no valid signature (or none at all) was supplied, because `Shipit.github(organization: 'orgtwo').webhook_secret` is `nil`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
