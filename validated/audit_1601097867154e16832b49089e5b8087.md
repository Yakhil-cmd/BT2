### Title
Stale delegate grants silently re-arm when a position NFT returns to the previous owner, restoring full manager authority without any fresh authorization - (File: contracts/controller/src/account.rs)

### Summary
CVE-2008-7320 describes Seahorse exposing plaintext secrets through the `quickAllow` dialog at an unlocked workstation — a previously satisfied authorization state is treated as standing consent for a sensitive action, with no re-verification. XOXNO Lending's delegate mechanism has the same shape: a `DelegateGrant` is stamped with `granted_by` and is keyed against the *current* NFT owner, so a grant that became inactive on transfer is not deleted — it goes dormant and **re-activates automatically if the position NFT ever returns to the address that created it**, with no new `require_auth` from the re-armed owner. The regained authority is then usable in any owner-or-delegate-gated flow such as `multiply` and `migrate_from_blend`.

### Finding Description
Authority over a lending account is resolved by `is_owner_or_delegate` in `contracts/controller/src/account.rs:115-127`:

```rust
let active_manager =
    storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
```

`get_delegates(env, account_id, owner)` filters stored `DelegateGrant`s by `granted_by == owner`, where `owner` is the live NFT holder. The position-nft README documents the consequence verbatim (`contracts/position-nft/README.md:174-179`): "Delegates lapse on transfer... The stale grant stays in storage and **re-arms if the token returns to `granted_by`**." The transfer path itself performs no grant cleanup — the NFT's `transfer`/`transfer_from` move only the `Owner(token_id)` record, and the controller stores account metadata keyed by `account_id`, not holder.

So the lifecycle is:

1. Alice calls `controller::add_delegate(account_id, M)`; `set_account_delegate` stores `DelegateGrant { granted_by: alice, delegate: M }` (`account.rs:229-275`, `storage::add_delegate`).
2. Alice transfers the position NFT to Bob. `is_owner_or_delegate(..., M, owner=bob)` fails because `granted_by != bob` — the grant is inert.
3. The NFT returns to Alice — she buys back her own leveraged position, settles a private OTC deal, or receives it back from any counterparty. She is never asked to re-confirm anything.
4. `is_owner_or_delegate(..., M, owner=alice)` now passes again because `granted_by == alice`. `M` is an active `PositionManager`, so `require_owner_or_delegate` succeeds for `M` in `load_or_create_account` with `AccountGuard::Migrate` and `AccountGuard::Multiply` (`account.rs:101-108`), gating `migrate_from_blend` and `multiply`, which let the manager reshape the account's collateral/debt composition against routes and parameters Alice never re-authorized.

This is the exact Seahorse pattern: a one-time unlock event (the original `add_delegate` signature) is replayed as standing consent for a later sensitive action that the current owner never saw or signed.

### Impact Explanation
The delegate is a position manager contract/address with owner-equivalent power inside owner-or-delegate flows. Once re-armed it can drive leverage-changing operations (`multiply` borrows against collateral and swaps through caller-supplied routes; `migrate_from_blend` rewrites the debt structure of the account). Because `multiply`/`migrate` execute caller-provided swap routes and strategy parameters, a stale manager can push the account into unfavorable routes, extractable positions, or forced-liquidation territory — theft of user funds / loss of position value by an address the current owner reasonably believes has no authority. Severity: Medium (real value at risk, but requires the NFT to return to the grantor and the manager to still be `is_active`).

### Likelihood Explanation
Medium. Preconditions: (a) the victim previously granted a delegate, (b) the position NFT is transferred away and later returns to the victim — plausible in secondary-market trading of leveraged positions, custody handoffs, or accidental round-trips — and (c) the delegate's `PositionManagerConfig` is still `is_active`. No privileged role, leaked key, or off-chain component is needed; the manager is an ordinary registered address. The protocol even documents the re-arming behavior, meaning it is deterministic whenever the preconditions hold rather than an edge case.

### Recommendation
Invalidate grants permanently instead of keying them on a mutable `granted_by`. Concretely:

- In `controller` transfer handling (or via a hook the position-nft `transfer`/`transfer_from` invokes), iterate and delete all `DelegateGrant` entries for the `account_id`, mirroring how the NFT clears `Approval(token_id)` on transfer, or
- stamp each grant with a monotonically increasing `ownership_epoch` that increments on every NFT transfer, and have `is_owner_or_delegate` reject grants from a stale epoch.

Either approach makes re-acquisition of the position require a fresh `add_delegate` signature, restoring the consent check the current scheme skips.

### Proof of Concept
1. Alice supplies and receives `account_id = 5` (token id 5).
2. Alice calls `controller::add_delegate(caller=alice, account_id=5, delegate=M)` where `M` is an active position manager. `DelegateGrant{granted_by=alice, delegate=M}` is stored.
3. Alice calls `position_nft::transfer(alice → bob, 5)`. The grant goes dormant (`granted_by=alice ≠ bob`).
4. Bob later calls `position_nft::transfer(bob → alice, 5)` — e.g., after Alice repurchases the position. No authorization prompt of any kind touches the delegate state.
5. `M` now calls `controller::multiply(caller=M, account_id=5, ...)` or `controller::migrate_from_blend(...)`. `require_owner_or_delegate(env, 5, M, owner=alice)` succeeds because `get_delegates(env, 5, alice).contains(M)` — the dormant grant re-armed silently.
6. `M` executes leverage/migration flows over Alice's collateral and debt with parameters and routes of its choosing, which Alice never authorized under her current ownership.

Caveat noted during review: I confirmed the re-arming semantics and the Migrate/Multiply delegate gates from source and documentation; I did not fully enumerate every owner-or-delegate entrypoint (e.g., whether `withdraw`/`borrow` also accept delegates versus `require_account_owner`), so the exact maximum extractable value depends on that full surface, which should be audited alongside the fix.
