### Title
Repository-less membership webhook can write Team membership for an organization that never signed the request - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#params` never requires `repository`, and `WebhooksController#repository_owner` falls back to `params.dig('organization','login')` when `repository` is absent, so a fully repository-less membership payload still passes signature verification scoped to the attacker's own organization. Because `find_or_create_team!` keys the mutated row purely on `params.team.id` and only assigns `organization` inside the `find_or_create_by!` creation block, a pre-existing `Team` row whose `github_id` happens to collide with the attacker-supplied `team.id` is mutated (`add_member`/`members.delete`) without re-validating that its `organization` matches the organization that produced a valid signature.

### Finding Description
The binding claimed to hold is: `verified_organization = params.dig('organization','login')` (used in `Shipit.github(organization: repository_owner)` at [1](#0-0)  and `repository_owner` at [2](#0-1) ) `== mutated_team.organization` (the `Team` row actually written by `find_or_create_team!`).

The `params` schema for `MembershipHandler` only requires `action`, `team`, `organization`, and `member` — `repository` is never required [3](#0-2) , so a payload with no `repository` key at all is schema-valid. `repository_owner` explicitly falls back to the `organization` sub-object when `repository` is missing [2](#0-1) , so signature verification is performed against `Shipit.github(organization: params.dig('organization','login'))` — i.e., against the *attacker's own organization's* configured webhook secret (in a multi-org deployment, per `github_app_config`) [4](#0-3) .

The mutation path is `find_or_create_team!`:
```
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [5](#0-4) 
The `organization` assignment only executes inside the block passed to `find_or_create_by!`, which ActiveRecord only invokes on the **create** branch. If a `Team` row already exists with `github_id == params.team.id` (belonging to a different, victim organization), the **find** branch returns that existing row untouched — `organization` is never re-checked or re-assigned. `process` then calls `team.add_member(member)` or `team.members.delete(member)` [6](#0-5)  on that victim-owned `Team`, using a `member` the attacker also fully controls via `User.find_or_create_by_login!(params.member.login)`.

Root cause: the record used for authorization scoping (`Team#organization`) is decoupled from the record used to key the write (`Team#github_id`), and the webhook's only organization-binding check (`verify_signature`) validates the *sender's* organization, not the *target row's* organization. The `repository`-omission detail confirms this divergence is reachable with the minimal membership payload (`organization` + `team.id` + `member` only) — no `repository` object, and thus no repository-level authorization signal, is ever consulted for this event type.

None of the existing guards close this gap: `verify_signature` only proves the attacker legitimately administers organization A's webhook secret (a precondition, not evidence about organization B's Team rows); `drop_unhandled_event` and `ExplicitParameters` schema validation only check payload shape, not cross-organization ownership of the `team.id` being referenced; `force_github_authentication`/`User#authorized?`/`require_permission!` are not invoked anywhere in this webhook path.

### Impact Explanation
A successful collision lets the attacker call `team.add_member(member)` or `team.members.delete(member)` on a `Team` row that belongs to a different tenant/organization than the one whose secret signed the request. Since `Team` records back `Shipit.github_teams`-style authorization gating (`oauth.teams` in `github_app.rb`, `oauth_teams`) [7](#0-6) , this is an escalation into another organization's team-membership state — matching the High-severity category "escalation into `Shipit.github_teams` authorization." The blast radius is bounded by whether an attacker can find/guess a `github_id` for a privileged `Team` belonging to a different organization already present in this Shipit instance's database (GitHub team IDs are global, sequential integers, not secrets, so this is enumerable in principle though not attacker-chosen at will). Repeatable per request; no rate limiting relevant.

### Likelihood Explanation
Preconditions: (1) the Shipit deployment must be configured for multiple organizations (`github_app_config`), with the attacker being a legitimate admin/owner of at least one onboarded organization (so they possess that organization's real `webhook_secret`, which is chosen by whoever creates the GitHub App, per `docs/setup.md`); (2) a `Team` row for a *different* onboarded organization must already exist in the database with a `github_id` the attacker can supply/guess. Given (1) and (2), the attacker's cost is a single crafted HTTP POST to `/webhooks` with a valid HMAC-SHA1 signature computed from a secret they legitimately hold for their own org — no Shipit session or `ApiClient` token required. Feasibility of guessing another org's specific privileged `Team`'s `github_id` is the main limiting factor and is not demonstrated as trivial in this codebase (GitHub team IDs are not exposed anywhere in this engine to an outside attacker as far as located).

### Recommendation
In `find_or_create_team!`, verify that the found (not just newly-created) `Team#organization` equals `params.organization.login` before performing `add_member`/`members.delete`, and raise/drop the event on mismatch. Additionally, consider requiring `repository` in `MembershipHandler#params` and cross-checking `repository.owner.login == organization.login` to remove the reliance on the fallback branch for this event type.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual, minitest)
test "membership webhook without repository key cannot mutate a team from a different organization" do
  victim_team = Shipit::Team.create!(github_id: 999, organization: 'victim-org', slug: 'admins', name: 'Admins')
  payload = {
    'action' => 'added',
    'team' => { 'id' => 999, 'name' => 'Admins', 'slug' => 'admins', 'url' => 'https://x' },
    'organization' => { 'login' => 'attacker-org' }, # no 'repository' key at all
    'member' => { 'login' => 'attacker' }
  }

  # sanity: verified org (signature) vs mutated row's org — assert they differ before the call
  assert_equal 'attacker-org', payload.dig('organization', 'login')
  assert_equal 'victim-org', victim_team.organization
  refute_equal payload.dig('organization', 'login'), victim_team.organization

  Shipit::Webhooks::Handlers::MembershipHandler.call(payload)

  victim_team.reload
  # BUG: victim_team.organization is still 'victim-org' (untouched) but it now has the attacker's member
  assert_includes victim_team.members.map(&:login), 'attacker'
  assert_equal 'victim-org', victim_team.organization # confirms find-branch performed no re-check/re-assignment
end
```
This demonstrates the payload needs no `repository` key, passes `MembershipHandler`'s `ExplicitParameters` schema, and — given a pre-existing `Team` collision on `github_id` — mutates a row whose `organization` never matches the organization used to compute/verify the webhook signature.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
