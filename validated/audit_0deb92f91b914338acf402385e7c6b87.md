### Title
Webhook signature verification binds to `repository.owner.login`/`organization.login` while the acted-upon repository/commit is taken from unrelated payload fields, enabling cross-organization forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against based on `params.dig('repository','owner','login')` (or `organization.login`), then hands the *same raw payload* to event handlers that resolve the target repository/stack/commit from a completely different, uncorrelated field (`repository.full_name`, or in `StatusHandler`, no repository scoping at all — just `sha`). Nothing ties the field used to select the signing secret to the field(s) used to determine what gets mutated, so a payload can validly authenticate as organization A while writing to a stack/commit that belongs to organization B.

### Finding Description
Shipit supports a multi-tenant GitHub configuration where each organization has its own `webhook_secret`: [1](#0-0) 

The webhook signature check selects which organization's secret to verify against using `repository_owner`, derived purely from JSON payload fields: [2](#0-1) 

Once `verify_signature` passes, `create` dispatches the *entire raw payload* to registered handlers: [3](#0-2) 

Handlers, however, resolve their target scope from a different field than the one used for signature/secret selection. The base `Handler` class scopes stacks by `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

`PushHandler` uses this base `stacks` scope to sync arbitrary tracked stacks: [5](#0-4) 

`StatusHandler` is worse still — it does not scope by repository at all, only by commit SHA, which is a value entirely controlled by the attacker in the payload and can match a real SHA belonging to any tracked repository: [6](#0-5) 

`CheckSuiteHandler` similarly resolves stacks via the base `Handler#stacks` (i.e. `repository.full_name`), independent of the signature-selecting `repository.owner.login`: [7](#0-6) 

**Binding violated:** the engine implicitly assumes `organization authenticated by verify_signature` == `organization that owns the repository/stack/commit actually written by the handler`. Nothing in the code enforces `payload['repository']['owner']['login'] == owner_of(payload['repository']['full_name'])`, nor does any handler re-derive the acting organization from the *same* field that was cryptographically verified. Since `repository.owner.login` and `repository.full_name` are two independent strings inside one attacker-controlled JSON body, an attacker who can produce a valid signature for *any one* configured organization (e.g. because they administer that org's GitHub App/webhook, or because that org's config in `secrets.github` has no `webhook_secret` set — in which case `verify_webhook_signature` unconditionally returns `true`) can set `repository.full_name` (or, for `StatusHandler`, just `sha`) to point at a stack/commit belonging to a *different* organization tracked by the same Shipit instance.

### Impact Explanation
This breaks the confused-deputy boundary between tenants of a multi-org Shipit deployment: an attacker with legitimate control of one configured organization's webhook secret (or exploiting an org with no secret configured) can inject forged `push`, `status`, or `check_suite` events that mutate state belonging to a different organization's stacks — most notably forging a successful commit `status` (`StatusHandler`) for a real commit SHA of a victim repository, which can mark that commit deployable and, in a continuous-delivery configuration, trigger an unauthorized deploy. This matches the "unauthorized deploy" High/Critical impact category.

### Likelihood Explanation
Requires the Shipit instance to be configured in multi-tenant GitHub mode (`secrets.github` keyed by organization) with at least one organization either lacking a `webhook_secret` or whose secret is known to the attacker (e.g. an org admin who legitimately manages that org's GitHub App integration but should not be able to affect other orgs' stacks). No GitHub write access, Shipit session, or API token is required — only the ability to send an HTTP POST to `/webhooks` with a payload signed for one of the configured organizations.

### Recommendation
Cross-validate that the organization used to select/verify the webhook secret is the same organization that owns the repository referenced by the fields the handler will act on (i.e. require `repository.full_name`'s owner segment to match `repository_owner`/`organization.login` before dispatching), and scope `StatusHandler`'s commit lookup by repository as well as SHA rather than searching commits globally.

### Proof of Concept
1. Shipit is configured with `secrets.github` containing two orgs, e.g. `orgA` (attacker-administered GitHub App, known `webhook_secret`) and `victimOrg` (tracked stacks, e.g. a production repo), per `Shipit.github_app_config`.
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<real sha of a victimOrg commit currently tracked by Shipit>",
  "state": "success",
  "context": "ci/attacker-forced",
  "repository": { "owner": { "login": "orgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `orgA`'s known `webhook_secret` over the raw body.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` (from `repository_owner`) and successfully verifies the signature. [8](#0-7) 
5. `create` dispatches the payload to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` — matching the victim's commit regardless of `orgA` having no relationship to it — and records a forged successful status. [6](#0-5) 
6. If `victimOrg`'s stack is configured for continuous deployment gated on commit status, this forged status can contribute to an unauthorized deploy of that stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
