### Title
PR label named `github_repo_owner`/`github_repo_name`/`deploy_url` overrides trusted `Stack#env` values in `ReviewStack#env` - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges attacker-controlled PR label names (upcased, value `"true"`) over the base `Stack#env` hash using `.merge`, so a label wins over `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `ENVIRONMENT`, `BRANCH`, or `LAST_DEPLOYED_SHA`. This corrupted value is then propagated through `TaskCommands#env` into `Command#unbundled_env`/`PTY.spawn`, and can be interpolated into deploy step arguments via `EnvironmentVariables#interpolate` (`$GITHUB_REPO_OWNER` etc.) if a `deploy_spec` step references those variables.

### Finding Description
Binding claimed broken: `stack.env['GITHUB_REPO_OWNER'] == repository.owner` for a `ReviewStack`. Trace:

- Base binding is set in `Stack#env`: [1](#0-0) 
- `ReviewStack#env` overrides it: `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` — labels win because `.merge` takes the argument hash's values on key conflict: [2](#0-1) 
- Labels are written verbatim from the webhook payload with no filtering of reserved names: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` in `LabelCapturingHandler#capture_labels`: [3](#0-2) 
- This handler runs on `opened`, `labeled`, `unlabeled`, `reopened` PR events for any `ReviewStack` tied to that PR's `environment` (`pr<number>`), created automatically via `ReviewStackAdapter#create!`/`stack_attributes`: [4](#0-3) 
- The corrupted `@stack.env` value flows into task/deploy execution: `TaskCommands#env` does `super.merge(@stack.env).merge(...)` — nothing downstream restores `GITHUB_REPO_OWNER`/`GITHUB_REPO_NAME`/`DEPLOY_URL`: [5](#0-4) 
- Final env reaches `PTY.spawn` via `Command#unbundled_env`/`#start`: [6](#0-5) 
- If a deploy step references `$GITHUB_REPO_OWNER`/`$GITHUB_REPO_NAME`/`$DEPLOY_URL` (custom `deploy_spec` step, similar to the documented `$ENVIRONMENT` capistrano usage), `EnvironmentVariables#interpolate` substitutes the corrupted value: [7](#0-6) [8](#0-7) 

None of the guardrails in scope block this: `verify_signature`/webhook auth only validates the request came from GitHub, not the label content; the `LabelCapturingHandler` params schema only requires `labels[].name` be a `String` with no value restriction; there is no reserved-word check against `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `ENVIRONMENT`, `BRANCH`, or `LAST_DEPLOYED_SHA`; `EnvironmentVariables#permit` is not applied to `Stack#env`/`TaskCommands#env` (it's used elsewhere for a different whitelist purpose).

### Impact Explanation
For a specific `ReviewStack`, an attacker able to label their own PR (per this exercise's threat model) can silently overwrite `GITHUB_REPO_OWNER` (or `GITHUB_REPO_NAME`/`DEPLOY_URL`/`ENVIRONMENT`/`BRANCH`) with the literal string `"true"` for that PR's review deploys. This corrupts the values passed to any deploy/custom step that interpolates those variables, i.e. commands run during a deploy could target the wrong owner/repo/URL argument. This affects only the attacker's own `ReviewStack`/PR (same repository, same PR-scoped environment) — I could not confirm from the code that this crosses tenant/repository boundaries, since `ReviewStackAdapter#stack` scopes lookup to `repository.review_stacks` and `environment: "pr<number>"`. Whether this reaches the "Critical: RCE via `Command`/`PTY.spawn`" bar depends entirely on whether the target repository's `shipit.yml`/`deploy_spec` actually references `$GITHUB_REPO_OWNER`/`$GITHUB_REPO_NAME`/`$DEPLOY_URL` in a deploy step — this is not guaranteed by the engine itself and is configuration-dependent (out of this engine's control). Absent such a step, the practical impact is limited to corrupting env values that a deploy script may or may not consume; it is not a self-contained RCE demonstrable purely within this engine.

### Likelihood Explanation
Requires: (1) review stacks enabled for the repository, (2) the attacker's PR already has (or gets) a `ReviewStack`, (3) attacker can attach a label with a reserved name to their PR — on real GitHub this normally requires `triage`/`write` access to the repo, which contradicts "unprivileged PR author" in practice, though the prompt's stated threat model asserts this is achievable, (4) the repository's `deploy_spec` must reference the shadowed variable in an executed step for there to be observable impact. Given (3) and (4) are both external/configuration preconditions not controlled by this engine's code, exploitability solely through this engine, for an attacker with no elevated GitHub permissions and no cooperating deploy_spec, is low.

### Recommendation
In `ReviewStack#env` (app/models/shipit/review_stack.rb), reject or filter label-derived keys against a reserved set (`GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `ENVIRONMENT`, `BRANCH`, `LAST_DEPLOYED_SHA`, and any other core `Stack#env` key), or invert the merge precedence so the base `Stack#env`/reserved keys always win over label-derived entries, e.g. `pull_request_env.merge(super)` with an explicit denylist, rather than `super.merge(pull_request_env)`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (new test)
test "#env: label named github_repo_owner overrides the real repository owner" do
  repository = shipit_repositories(:shipit)
  stack = ReviewStack.create!(
    repository: repository,
    environment: "pr999",
    branch: "some-branch"
  )
  stack.build_pull_request.save!(validate: false)
  stack.pull_request.update_column(:labels, ["github_repo_owner"])

  # Binding under test:
  assert_equal repository.owner, stack.repository.owner # sanity: real owner value
  assert_equal "true", stack.env["GITHUB_REPO_OWNER"]    # actual (corrupted) behavior
  refute_equal repository.owner, stack.env["GITHUB_REPO_OWNER"]
end
```
This confirms `env['GITHUB_REPO_OWNER']` becomes `"true"` rather than `repository.owner`, matching the broken binding described in the question. Whether this corrupted value is ever executed by `PTY.spawn` in a way that constitutes RCE could not be confirmed from this engine's code alone, since it depends on repository-supplied `deploy_spec` content, which is out of scope/unverifiable here.

      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
