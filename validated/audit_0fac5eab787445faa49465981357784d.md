### Title
Cross-repository CI-status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits with a global `Commit.where(sha: params.sha)` query instead of scoping the lookup to the repository that sent the webhook. Any GitHub organization/repo that is onboarded to this Shipit instance (i.e., can legitimately send GitHub‑signed `status` webhooks) can attach a forged CI status to a commit belonging to a completely unrelated stack, as long as that other stack contains a commit with the identical `sha` string.

### Finding Description
The broken binding: the code treats `commit.sha == params.sha` as sufficient identity to authorize writing a status onto a commit's stack, when the correct binding should be `commit.sha == params.sha AND commit.stack.repository == payload.repository`.

Code path:
- `Shipit::WebhooksController#create` dispatches the parsed payload to `Shipit::Webhooks.for_event(event)`, which for `"status"` is `[Handlers::StatusHandler]` [1](#0-0) [2](#0-1) .
- `verify_signature` only checks that the payload is validly signed by GitHub for the organization named in `payload.repository.owner.login`; it never checks that the `sha` in the payload belongs to that same repository's commit graph [3](#0-2) .
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [4](#0-3) 
This query is **global** across the `commits` table — it is not scoped to `stacks` (i.e. to the repository that emitted the webhook), unlike the sibling `CheckSuiteHandler`, which correctly narrows to the emitting repository first: `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` [5](#0-4) . `stacks` is defined in the base `Handler` as `Repository.from_github_repo_name(repository_name)&.stacks`, i.e. properly scoped by the webhook's own `repository.full_name` [6](#0-5) . `StatusHandler` simply never applies this scoping.
- `Commit#create_status_from_github!` writes the status keyed by the *commit's own* `stack_id`, not the webhook's originating stack, so a matched row belonging to a victim stack gets a real, persisted `CommitStatus` for that victim stack [7](#0-6) .

The unique index `commits(sha, stack_id)` [8](#0-7)  confirms `sha` is only unique *per stack*, not globally — `sha` alone is not a valid cross-tenant identity key, which is exactly what `StatusHandler` implicitly assumes.

Exploit flow: the attacker (per the stated threat model, someone who can "emit webhooks from a repository they own") arranges for a commit with an identical `sha` to exist in both their own onboarded repository and the victim stack's git history (e.g., by forking a shared/public upstream so the git object is byte-for-byte identical and therefore has the same SHA-1 — no cryptographic collision is required, only that both repos legitimately contain the same commit object). The attacker then creates a commit status on that commit via GitHub's own Statuses API against their own repo. GitHub emits a validly signed `status` webhook to Shipit. `verify_signature` passes because the signature is genuine for the attacker's own organization. `StatusHandler` then matches and mutates every `Commit` row across every stack sharing that `sha`, including the victim's, writing an attacker-controlled `state`/`description`/`context` onto the victim commit's status list.

None of the existing guards catch this: `verify_signature` validates signer identity, not sha ownership; `ExplicitParameters` only validates the shape of `sha`/`state`, not repository ownership; `drop_unhandled_event` is irrelevant to a handled `status` event; there is no `stacks`/repository scoping anywhere in `StatusHandler`.

### Impact Explanation
A single, correctly-signed webhook from an attacker-controlled repository can write a forged `CommitStatus` (arbitrary `state`, `context`, `description`, `target_url`) onto an arbitrary victim stack's commit, as long as a matching `sha` string exists there. If that context is one of the stack's `required_statuses`, this can flip a commit from blocked to deployable, enabling an unauthorized deploy — this is a cross-tenant "payload for one repository mutating another's stack/commit" scenario, matching the Critical impact category. The attack is repeatable against any stack/commit whose `sha` the attacker can reproduce (most easily via shared/forked history), and scales to any number of victim tenants sharing this Shipit instance.

### Likelihood Explanation
Preconditions: the attacker must control (or be onboarded to) a GitHub org/repo that this Shipit instance accepts webhooks from, and must be able to produce a commit with a `sha` matching one present in the target stack — trivial if the victim's stack contains history shared with a public/forked upstream, harder (though not impossible for old/short-lived, low-entropy commits) otherwise. No Shipit secrets, sessions, or tokens are needed; only genuine GitHub webhook delivery from an org the attacker legitimately controls. This is a low-cost, repeatable attack once a matching sha is identified.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, mirroring `CheckSuiteHandler`/`PushHandler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `commit.stack.repository == payload.repository` before writing any status.

### Proof of Concept
Minitest (`test/models/shipit/webhooks/handlers/status_handler_test.rb`), no live GitHub:
```ruby
test "does not create a status for a commit belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit) # repo: "shopify/shipit-engine"
  attacker_stack = shipit_stacks(:cyclimse) # different repo/org

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared")

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "forged/context",
    "repository" => { "full_name" => attacker_stack.repository.full_name }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_empty victim_commit.reload.statuses.where(context: "forged/context"),
    "victim commit must not receive a status from a webhook for a different repository"
  assert_not_empty attacker_commit.reload.statuses.where(context: "forged/context")
end
```
Before the fix, `Commit.where(sha: shared_sha)` matches both rows and both assertions on the two sides of the binding (`commit.stack.repository == payload.repository`) diverge, proving the vulnerability; after applying the recommended scoping, only `attacker_commit` receives the status.
