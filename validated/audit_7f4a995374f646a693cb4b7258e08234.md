## Analysis

CVE-2021-30851 is a WebKit memory-corruption bug fixed by *"improved locking"* around a race condition. The strongest reachable analog in `ocore--014` is a missing-lock / TOCTOU race in the **private-payment chain validation-and-save path**, which is exercised directly by a private-payment counterparty (no node/peer trust required) and can be reached whenever a wallet receives a private (hidden) payment chain.

### Title
Missing mutex serialization in private payment chain validate-and-save allows a private output to be accepted as spent by two conflicting chains (double-spend / inconsistent state) - (File: private_payment.js)

### Summary
The on-chain unit validation path in `validation.js` serializes all validation+write work per author address with `mutex.lock(arrAuthorAddresses, …)` [1](#0-0) , and double-spend "ununiquing" of private inputs is additionally serialized with a dedicated `mutex.lock(["private_write"], …)` [2](#0-1) . However, the separate flow used to validate and persist standalone **private payment chains** (`private_payment.js:validateAndSavePrivatePaymentChain`) takes **no mutex lock at all** before reading the "duplicate" state and writing the chain to the database.

### Finding Description
`private_payment.js` checks for a duplicate output and then calls into `indivisible_asset.js`/`divisible_asset.js` to validate and save the chain, all without ever calling `mutex.lock`: [3](#0-2) [4](#0-3) 

The actual DB write in `indivisible_asset.js:validateAndSavePrivatePaymentChain` inserts the spending `input` row with `INSERT ... IGNORE` (`db.getIgnore()`), relying purely on the DB-level unique key `bySrcOutput(src_unit, src_message_index, src_output_index, is_unique)` to reject a second spend of the same source output, and separately updates the `outputs.is_spent` flag with a plain `UPDATE`: [5](#0-4) 

Because there is no JS-level mutex serializing concurrent invocations for the same source output/asset (unlike the on-chain path's `mutex.lock(arrAuthorAddresses, …)` and `mutex.lock(["private_write"], …)`), this whole check-then-write sequence is a classic time-of-check/time-of-use race: two different private-payment chains claiming the same source output can both pass the "check if duplicate" read in `private_payment.js` and both proceed to `validateAndSavePrivatePaymentChain` concurrently on independent DB connections/transactions (`db.takeConnectionFromPool` + `BEGIN`/`COMMIT`). Both `async.series` write batches run to completion and both call `transaction_callbacks.ifOk()` regardless of whether their `INSERT IGNORE` for the `inputs` row actually succeeded, because `INSERT ... IGNORE` does not report a conflict as an error the caller checks. This is reachable directly by a **private-payment counterparty**: an attacker can craft two conflicting private payment chains spending the same hidden output and deliver both to a victim wallet/hub concurrently (e.g. via direct device message and via the hub's `unhandled_private_payments` queue, both funneled into `network.js:handleSavedPrivatePayments`, which processes multiple rows in parallel with `async.each`): [6](#0-5) 

### Impact Explanation
A successful race causes the wallet/hub to acknowledge (`ifOk`) two conflicting private spends of the same hidden output to two different recipients, while only one of the two `inputs` rows can ultimately exist due to the DB unique key. This creates node disagreement about which private payment is valid, and a recipient who received a false "accepted" acknowledgment may treat a non-existent payment as final/confirmed — a private-payment double-spend/fund-loss scenario for the counterparty who is defrauded.

### Likelihood Explanation
This requires no privileged network position — a normal user acting as a private-payment counterparty (or a device/hub relay) can trigger two chains for the same source output at once. The race window exists because the `private_payment.js` entry point performs no serialization at all, unlike every other write path in the codebase (`validation.js`, `writer.js`) which is consistently protected by `mutex.lock`.

### Recommendation
Acquire a `mutex.lock` keyed by the source output identity (e.g. `asset + src_unit + src_message_index + src_output_index`, or by output address) around the duplicate-check-and-save sequence in `private_payment.js:validateAndSavePrivatePaymentChain`, mirroring the `["private_write"]` locking already used in `validation.js`'s double-spend handling, so that concurrent chains spending the same private output are serialized and only one can be accepted.

### Proof of Concept
1. Attacker crafts two valid-looking private payment chains, `chainA` and `chainB`, both spending the same private output (`src_unit`, `src_message_index`, `src_output_index`) of a private asset, but paying two different destination addresses/amounts.
2. Attacker submits `chainA` directly to the victim's device (`new_direct_private_chains`) and near-simultaneously submits `chainB` through the hub's `unhandled_private_payments` queue so both reach `network.js:handleSavedPrivatePayments`, which invokes `privatePayment.validateAndSavePrivatePaymentChain` for each row in parallel via `async.each`.
3. Both invocations execute `private_payment.js`'s duplicate check on separate DB connections before either commits, both see "not a duplicate," and both proceed to `assetModule.validateAndSavePrivatePaymentChain`, each running its own `BEGIN…COMMIT` transaction.
4. Because there is no mutex serializing the two invocations, both report `ifOk()` to their respective callers/recipients even though the underlying `inputs` unique key silently drops one of the two conflicting `INSERT IGNORE` rows, leaving one recipient believing they received a valid, accepted private payment that does not actually exist in the ledger.

function handleSavedPrivatePayments(unit){
	//if (unit && assocUnitsInWork[unit])
	//    return;
	if (!my_device_address) return; // skip if we don't have a wallet
	if (!unit && mutex.isAnyOfKeysLocked(["private_chains"])) // we are still downloading the history (light)
		return console.log("skipping handleSavedPrivatePayments because history download is still under way");
	var lock = unit ? mutex.lock : mutex.lockOrSkip;
	lock(["saved_private"], function(unlock){
		var sql = unit
			? "SELECT json, peer, unit, message_index, output_index, linked FROM unhandled_private_payments WHERE unit="+db.escape(unit)
			: "SELECT json, peer, unit, message_index, output_index, linked FROM unhandled_private_payments CROSS JOIN units USING(unit)";
		db.query(sql, function(rows){
			if (rows.length === 0)
				return unlock();
			var assocNewUnits = {};
			async.each( // handle different chains in parallel
				rows,
				function(row, cb){
					var arrPrivateElements = JSON.parse(row.json);
					var ws = getPeerWebSocket(row.peer);
					if (ws && ws.readyState !== ws.OPEN)
						ws = null;
					
					var validateAndSave = function(){
						var objHeadPrivateElement = arrPrivateElements[0];
						try {
							var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
						}

							console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
							if (ws)
								sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
							deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
