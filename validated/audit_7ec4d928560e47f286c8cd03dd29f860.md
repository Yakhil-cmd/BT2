### Title
Webhook signature verification is keyed by `repository.owner.login`, but handlers act on the unauthenticated `repository.full_name` — allowing cross-organization forged webhooks in multi-tenant deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-tenant configuration where each GitHub organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC against using a field read out of the *same* attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`), then all downstream handlers independently re-read a *different* field of that same body (`repository.full_name`) to decide which `Repository`/`Stack` to actually mutate. Nothing ties these two lookups together beyond "both come from the signed bytes" — the signature only proves the sender knows *some* organization's secret, not that `repository.full_name` is consistent with `repository.owner.login`.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the HMAC secret) to validate against based on the payload itself: [2](#0-1) [3](#0-2) 

Separately, every webhook `Handler` resolves the target `Repository` (and thus the `Stack`s that get mutated) from `payload.dig('repository', 'full_name')`: [4](#0-3) 

`Repository.from_github_repo_name` splits `full_name` on `/` and looks up `owner`/`name` independently of anything checked during signature verification: [5](#0-4) 

In a single-organization Shipit deployment this is not exploitable, because there is only one `webhook_secret` and any holder of it already has full write access to every repository configured there. However, Shipit explicitly documents and supports a multi-tenant mode where distinct GitHub organizations, each with their own separately-configured `webhook_secret`, share one Shipit instance: [1](#0-0) [6](#0-5) 

In that mode, an operator/administrator of one onboarded organization ("Org A") — an attacker who is unprivileged with respect to every *other* tenant's repositories — legitimately knows Org A's `webhook_secret` (they configured their own GitHub App). They can POST directly to `/webhooks` with:
- `X-Github-Event: pull_request` (or `push`, etc.)
- a body where `repository.owner.login == "OrgA"` and `organization.login == "OrgA"` (so `verify_signature` selects Org A's `GitHubApp` and its secret matches the HMAC),
- but `repository.full_name == "OrgB/victim-repo"` (a repository belonging to a completely different tenant, "Org B", configured elsewhere in the same Shipit instance),
- signed with Org A's own `webhook_secret`.

`verify_signature` succeeds because it only checks that the HMAC matches Org A's secret over the raw bytes; it never validates that `repository.owner.login` matches `repository.full_name`'s owner segment, nor that Org A's `GitHubApp` has any relationship to Org B. The equality that should hold — "the organization whose secret authenticated this payload == the organization that owns the repository being written to" — is broken:
`repository_owner (verified) == repository.owner.login` but `repository (mutated) == Repository.from_github_repo_name(repository.full_name)`, and these two are never cross-checked.

### Impact Explanation
With a forged `full_name` targeting Org B, several handlers act on Org B's stacks/pull requests without any legitimate GitHub-originated event:
- `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` for Org B's stacks matching the forged branch [7](#0-6) .
- `PullRequest::EditedHandler` / `OpenedHandler` / `ClosedHandler` etc. update `PullRequest` records for Org B using attacker-controlled JSON (`title`, `state`, `additions`, `deletions`, `assignees`, `labels`, `head.sha`) via `github_pull_request=`, which is populated straight from the untrusted payload rather than a fresh GitHub API fetch: [8](#0-7) . `head.sha` is then resolved through `find_or_create_commit_from_github_by_sha!`, which fetches commit data from *Org B's* GitHub API using *Org B's* own installation token [9](#0-8) , and `LabeledHandler`/`OpenedHandler` can trigger `stack.archive!`/`unarchive!`/provisioning of Org B's review stacks based on attacker-forged labels [10](#0-9) .

This is a cross-tenant write into another organization's Shipit-managed state (PullRequest metadata, review-stack archive/provision actions, forced GitHub syncs) triggered purely by an operator of an unrelated, lower-privileged tenant — satisfying the "cross-repository writes" bar, though it does not directly exfiltrate `GITHUB_TOKEN`/`github_access_token` and does not perform an unauthorized deploy/merge (deploy/merge actions require a matching `Stack` and additional state such as CI/mergeable status obtained via real GitHub API calls scoped to the correct app credentials, which the attacker cannot forge).

### Likelihood Explanation
Requires: (1) the target Shipit instance be configured in the documented multi-org mode with more than one organization's `webhook_secret`, and (2) the attacker control at least one legitimately onboarded organization in that same instance (e.g., a low-trust customer/team boarded onto a shared internal Shipit deployment). This is a plausible but non-default configuration; most Shopify/OSS deployments run single-organization Shipit. Likelihood is therefore **Low-to-Medium** and configuration-dependent, though the code path itself has no defense-in-depth check even when this mode is used.

### Recommendation
In `WebhooksController`, after `verify_signature` succeeds, re-derive and enforce that `repository.owner.login` (the field used to select the verifying `GitHubApp`) is consistent with the `full_name` field(s) any handler will use to resolve organizations/repositories — e.g., compare `repository_owner` against `params.dig('repository', 'full_name')&.split('/')&.first` and reject (422) on mismatch. Alternatively, pass the already-verified `repository_owner` into handlers and have `Handler#stacks`/`Repository.from_github_repo_name` require it to match rather than blindly trusting `full_name` from the raw payload.

### Proof of Concept
1. Deploy Shipit with multi-org config containing `OrgA` (attacker-controlled) and `OrgB` (victim), each with distinct `webhook_secret`s, per `docs/setup.md`'s "Using Multiple Github Applications" section.
2. As the operator of OrgA, compute `sig = HMAC-SHA1(OrgA_webhook_secret, body)` where `body` is:
```json
{
  "action": "edited",
  "number": 1,
  "pull_request": {
    "id": 1, "number": 1, "url": "https://api.github.com/x",
    "title": "pwned", "state": "open", "additions": 0, "deletions": 0,
    "head": {"sha": "<victim-commit-sha>", "ref": "feature"},
    "user": {"login": "attacker"}, "assignees": [], "labels": []
  },
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"},
  "sender": {"login": "attacker"}
}
```
3. `POST /webhooks` with header `X-Hub-Signature: sha1=<sig>` and `X-Github-Event: pull_request`.
4. `verify_signature` looks up `Shipit.github(organization: "OrgA")` and validates successfully against OrgA's secret.
5. `EditedHandler` resolves `Shipit::Repository.from_github_repo_name("OrgB/victim-repo")` and updates the matching `PullRequest` under `OrgB`'s stack using attacker-supplied fields, despite the request never having been signed by OrgB's GitHub App.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

          def stack
            @stack ||=

            params.pull_request
          end

            pull_request.state
          end

          def respond_to_label_change?
            params.action == "labeled" &&
              pull_request_state == "open" &&
              repository.review_stacks_enabled &&
              (archive? || unarchive?)
          end

          def archive?
            (repository.provisioning_behavior_allow_with_label? && !pull_request_has_provisioning_label?) ||
              (repository.provisioning_behavior_prevent_with_label? && pull_request_has_provisioning_label?)
          end

          def unarchive?
            (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
              (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
          end
