### Title
`StatusHandler#process` writes GitHub statuses by bare SHA with no repository scoping, letting a status from one repo mutate a commit belonging to another stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` — a global, unscoped query against the entire `commits` table — instead of using the `stacks`/`repository_name` scoping helper already provided by the base `Handler` class. Since the `commits` table's uniqueness constraint is only `[sha, stack_id]` (not `sha` alone), a webhook the attacker legitimately and validly signs for their own repository can create/update a status on a completely different stack's commit that happens to share the same SHA, flipping a `release/gate` context to `failure` and affecting deployability.

### Finding Description
The broken binding: the code assumes `commit.stack_id == repository_that_authenticated_this_webhook`, but the actual code never checks this — the equality `params.dig('repository','full_name') == commit.stack.repository.full_name` is never enforced in `StatusHandler#process`.

Path:
1. Attacker owns a GitHub repository and can freely trigger `status` webhook deliveries against it (e.g., via GitHub Actions, GitHub API, or any integration on their own repo) — these are legitimately signed by GitHub using the attacker's own app installation.
2. `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) dispatches the parsed payload to `Shipit::Webhooks.for_event(event)`, but before that `verify_signature` (line 24-49) validates the HMAC using `Shipit.github(organization: repository_owner)` derived from the attacker's own `payload['repository']['owner']['login']`. This check only proves the webhook genuinely originated from GitHub for the attacker's own repo/org — it says nothing about which Shipit stack the SHA belongs to. [1](#0-0) 
3. `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that correctly scopes lookups to the repository named in the payload, via `Repository.from_github_repo_name(repository_name)&.stacks`. [2](#0-1) 
4. `StatusHandler#process` does **not** use this scoping. It directly does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [3](#0-2) 
5. The `commits` table has a unique index on `[sha, stack_id]`, not on `sha` alone, so the same SHA can legitimately exist as separate rows for different stacks (e.g., forks tracking the same upstream history, or multiple Shipit stacks pointed at repositories that share commit ancestry). [4](#0-3) [5](#0-4) 
6. When the attacker's webhook payload carries a `sha` that collides with a commit row belonging to the victim's stack, `Commit.where(sha: ...)` returns both rows, and `commit.create_status_from_github!(params)` is invoked on the victim's commit too, writing a `Status` with `context: 'release/gate'`, `state: 'failure'` under the victim's `stack_id` via `statuses.replicate_from_github!(stack_id, github_status)`. [6](#0-5) 
7. Because `release/gate` is treated as a required/blocking status context for the victim stack's deploy/merge gating (`required_statuses`/`blocking_statuses`, referenced from `Commit`/`Stack`/`DeploySpec`), this write can flip the victim commit's aggregate `state` and block or unblock deploys/merges without any interaction with the victim's own repository or credentials.

Existing guards do not prevent this: `verify_signature` only authenticates that the payload came from GitHub for the *attacker's own* organization/repo — it has no notion of "this status may only apply to commits under repository X." The `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/`context`, not repository ownership. No `stacks`/`repository_name` filter is applied in this handler, unlike what the base `Handler` class provides for that exact purpose.

### Impact Explanation
An attacker who controls only their own repository can write to `Status` records (and thus commit aggregate `state`) belonging to an unrelated victim stack whenever a SHA they control (or that legitimately collides across forked/shared histories) matches a commit already tracked by the victim. This can force a `release/gate` (or any other) status to `failure`, blocking a deploy or merge on a stack the attacker has no access to — a cross-tenant/cross-repository state write matching the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Exploitation requires the attacker's SHA to collide with a SHA already present as a commit for the victim's stack. This is realistic in common scenarios: forked repositories tracked as separate Shipit stacks sharing history, monorepos split into multiple Shipit-tracked repositories with shared commits, or repositories that were renamed/migrated where old SHAs persist. In all such cases the attacker's own, legitimately-signed webhook is sufficient — no victim secrets, no privileged role, and it is repeatable against any stack sharing a SHA with an attacker-controlled repository.

### Recommendation
Scope `StatusHandler#process` the same way other handlers are scoped: resolve commits only within `stacks` (derived from `payload.dig('repository', 'full_name')`), e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, instead of a bare `Commit.where(sha: params.sha)` query against the entire table.

### Proof of Concept
```ruby
test "StatusHandler does not create a status for a commit belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit) # repo: "shipit-engine/shipit-engine" (example)
  attacker_stack = shipit_stacks(:cyclimse) # unrelated repo owned by attacker

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'release/gate',
    'repository' => { 'full_name' => attacker_stack.github_repo_name, 'owner' => { 'login' => attacker_stack.repo_owner } }
  }

  before_state = victim_commit.reload.state # e.g. "success" or "unknown"

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  after_state = victim_commit.reload.state

  # Binding under test: attacker's payload for their own repo must not change the victim's commit state
  assert_equal before_state, after_state, "release/gate status leaked across repositories via unscoped Commit.where(sha:)"
end
```
Running this against the current code fails the assertion because `StatusHandler#process` matches the victim's commit purely by SHA and calls `create_status_from_github!`, changing `victim_commit`'s aggregate state.
