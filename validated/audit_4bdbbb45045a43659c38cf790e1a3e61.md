### Title
Webhook signature verification keyed on `repository.owner.login` while handlers act on `repository.full_name` allows cross-repository status/push forgery to trigger unauthorized deploys - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`) field [3](#0-2) . However, the actual event handlers that mutate application state select the target `Repository`/`Stack` using a **different** field from the same attacker-controlled payload: `repository.full_name`, via `Handler#repository_name` and `Handler#stacks` [4](#0-3) .

### Finding Description
The binding the engine implicitly relies on is:
`organization authenticated by verify_signature (repository.owner.login)` == `repository whose Stack is written by the handler (repository.full_name)`

This equality is never enforced. In a multi-organization Shipit deployment (a documented, supported configuration — see `docs/setup.md`'s "Using Multiple GitHub Applications" section and `config/secrets.development.shopify.yml`), each configured GitHub organization has its own `webhook_secret`, known to that organization's own GitHub App administrator (they set it when creating their App) [5](#0-4) .

An attacker who legitimately controls org A's GitHub App webhook secret can send a forged webhook request where:
- `repository.owner.login` = `"org-a"` (their own org) — so `Shipit.github(organization: repository_owner)` resolves to their own `GithubApp` instance, and they can correctly compute the HMAC signature with their own real secret, passing `verify_webhook_signature` [6](#0-5) .
- `repository.full_name` = `"org-b/victim-repo"` — an arbitrary repository tracked by the Shipit instance, belonging to a different, unrelated organization.

Because `verify_signature` only checks the raw body against org A's secret and never cross-checks `repository.full_name`'s owner against `repository_owner`, the request is accepted, and `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full attacker-controlled JSON to handlers that resolve the stack via `Repository.from_github_repo_name(repository_name)` using `repository.full_name` [7](#0-6) .

For the `status` event, `StatusHandler#process` looks up any `Commit` by raw `sha` (no repository/stack scoping in the lookup itself) and calls `commit.create_status_from_github!(params)` with an attacker-chosen `state` (e.g. `success`) [8](#0-7) . This flows into `Commit#add_status`, which updates the commit's CI status and calls `stack.schedule_merges if new_status.pending? || new_status.success?` [1](#0-0) . A commit forced to `success` becomes `deployable?` and can satisfy `Stack#deployable?` / `next_expected_commit_to_deploy`, which `trigger_continuous_delivery` uses to enqueue a real deploy task when continuous deployment is enabled [2](#0-1) .

### Impact Explanation
This breaks the deployment-trust boundary between organizations sharing one Shipit instance: an org that only owns its own GitHub App/webhook secret can forge CI status for a commit belonging to a repository/stack it does not own, and drive that stack's commit to a `deployable`/`success` state, causing an unauthorized deploy to be triggered on victim's stack when continuous deployment is enabled — satisfying the "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires the attacker to legitimately control at least one configured GitHub organization/App on a multi-tenant Shipit instance (a supported, documented configuration), and requires the target stack to have continuous deployment enabled and rely on forgeable status contexts as its CI gate. No GITHUB_TOKEN, session, or `ApiClient` credentials are required — only knowledge of the attacker's own already-provisioned webhook secret, which is inherent to how the multi-org feature works.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`/`stacks`), enforce that the owner used to select the verifying GitHub App/secret matches the owner encoded in `repository.full_name` (and, ideally, also validate that the `sha` in a `status` event belongs to a commit whose stack's repository owner matches `repository_owner`) before dispatching to handlers, e.g. reject when `repository.full_name.split('/').first != repository_owner`.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` (attacker-controlled App/secret) and `org-b` (victim, tracked stack `org-b/victim-repo`).
2. Attacker crafts payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required",
  "repository": { "full_name": "org-b/victim-repo", "owner": { "login": "org-a" } }
}
```
3. Attacker computes `X-Hub-Signature` using org A's own webhook secret over the raw body and sets `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: 'org-a')` and validates successfully against the attacker's own secret [9](#0-8) .
5. `StatusHandler#process` updates the victim's commit status to `success`, which can trigger `schedule_merges`/continuous deployment on `org-b/victim-repo` [8](#0-7) .

      return true unless webhook_secret
