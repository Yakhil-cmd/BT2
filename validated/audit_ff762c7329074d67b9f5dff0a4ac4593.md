This confirms the binding break: the webhook signature is verified against the GitHub App config selected by `params.dig('repository','owner','login')` (or `organization.login`) [1](#0-0) , while the actual write target (which `Stack`/`Repository` receives the event) is resolved from a completely different field, `payload.dig('repository','full_name')` [2](#0-1) . These two fields are never cross-checked against each other.

### Title
Webhook signature is verified against `repository.owner.login`'s GitHub App while the event is applied to `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to use for HMAC verification based on `repository.owner.login`/`organization.login` in the *unverified* JSON body [3](#0-2) . But once the request passes verification, `Handlers::Handler#stacks` looks up the target `Repository`/`Stack` using `repository.full_name`, an entirely separate field of the same unverified body, with no assertion that its owner matches the organization whose secret authenticated the request [2](#0-1) .

### Finding Description
The equality that should hold is: `organization whose webhook_secret verified the HMAC == owner(repository.full_name) that the handler writes to`. Both sides are read from the same POST body, so this is only meaningfully enforced if the app hard-fails when they diverge — it doesn't.

- `Shipit.github(organization: repository_owner)` looks up per-organization config via `github_app_config` in a hash keyed by org name [4](#0-3) .
- `verify_webhook_signature` compares the request's `X-Hub-Signature` against an HMAC computed with that organization's `webhook_secret` — but if `webhook_secret` is blank/absent for that config entry, verification is bypassed entirely (`return true unless webhook_secret`) [5](#0-4) . The multi-org example fixture explicitly shows an org (`OrgTwo`) configured with `webhook_secret: # nil` [6](#0-5) .
- After `verify_signature` passes (using `repository.owner.login`'s app/secret), `create` dispatches to handlers with the *raw, unauthenticated* `params` [7](#0-6) .
- Handlers such as `PushHandler` and `StatusHandler` resolve the target `Repository` purely from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name` [2](#0-1) [8](#0-7) , and then act on any matching `Stack` (e.g., triggering `sync_github`) [9](#0-8) .

This mirrors the Astaria bug class precisely: the check that provides trust (`liquidationInitialAsk` / here, HMAC verification) is bound to one identifier (`stack[j]` / here, `repository.owner.login`), but the value actually acted upon in practice belongs to a different identifier (`stack[0]` / here, `repository.full_name`). An attacker who controls (or is a legitimate low-privilege member of) any one organization configured in `secrets.github` with either a known/leaked `webhook_secret` or — more critically — an org entry with `webhook_secret` unset, can send a webhook where `repository.owner.login`/`organization.login` names that (weak) org, while `repository.full_name` names a repository belonging to an entirely different, victim organization/stack.

### Impact Explanation
If exploitable, this allows cross-repository/cross-organization forged webhook events (e.g., forcing `sync_github` on an arbitrary victim stack, injecting fake commit statuses via `StatusHandler`, or manipulating team membership via `MembershipHandler`) without possessing that victim organization's real `webhook_secret`. This matches the "cross-repository writes" Critical-impact category defined by the rules, since the write target repository is decoupled from the verified sender identity.

### Likelihood Explanation
Exploitability strictly depends on deployment configuration: it requires (a) the multi-organization GitHub config schema being used (`secrets.github` keyed by org) and (b) at least one configured organization having no `webhook_secret` set (or a leaked/guessable one). Single-org deployments are not affected because there is only one app/secret and no `repository_owner`-keyed selection ambiguity relative to the deployed data set. The rules explicitly reject "analogs that depend on the host application not mounting the engine as documented" — a documented, intentional deployment choice (multiple GitHub Apps, one intentionally left secret-less, as literally demonstrated in the repo's own multi-app test fixture) is a supported configuration, not a misuse of the engine, so this scenario is in-scope, but its likelihood is gated by that specific, non-default multi-org + blank-secret configuration.

### Recommendation
After signature verification succeeds, re-derive the expected organization from the same trusted binding used for verification and assert that `repository.full_name`'s owner (or `organization.login`) matches the `repository_owner` that selected the verifying `webhook_secret`, rejecting the request (422) on mismatch. Additionally, consider requiring `webhook_secret` to be mandatory per configured organization (removing the `return true unless webhook_secret` bypass in `GithubApp#verify_webhook_signature`), since an organization entry without a secret provides no protection at all for its own namespace, let alone for others when full_name diverges from the verified owner.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub config schema: `OrgWeak` (attacker-controlled or misconfigured with `webhook_secret: nil`) and `OrgVictim` (has a real Stack, e.g. `orgvictim/app`), matching the documented schema in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker POSTs to `/webhooks` (or the engine's mounted webhook path) with:
   - `X-Github-Event: push`
   - Body: `{"repository": {"owner": {"login": "OrgWeak"}, "full_name": "orgvictim/app"}, "ref": "refs/heads/main", "after": "<attacker-chosen sha>"}`
   - No/garbage `X-Hub-Signature` header.
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgWeak"`, calls `Shipit.github(organization: "OrgWeak")`, and `verify_webhook_signature` returns `true` immediately because `OrgWeak`'s `webhook_secret` is blank [10](#0-9) .
4. `create` proceeds and dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("orgvictim/app")` from `full_name` [2](#0-1)  and triggers `sync_github` on that victim stack — despite the request never being authenticated by `OrgVictim`'s secret.

**Caveat:** I could not verify from the index whether any additional owner/organization consistency check exists elsewhere in the request pipeline (e.g., in `Shipit::Webhooks.for_event` or a before_action not indexed) that might block this divergence; the controller, handler, and `GitHubApp` code reviewed show no such check. If the user needs full confidence, a Devin session with complete repository access should trace the full webhook dispatch path to confirm no such cross-check exists elsewhere.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end
