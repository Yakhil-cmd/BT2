### Title
Future-dated oracle price poisons the shared `last-update` monotonic cache, freezing price-dependent operations for all users of that asset - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`price-resolve` in `v0-4-market.clar` accepts any oracle price whose timestamp is greater than the current `stacks-block-time` as fully "fresh" (it just clamps the staleness delta to `u0` instead of rejecting it), and then unconditionally stores that future timestamp into the shared, per-feed `last-update` map. Because every subsequent price resolution for that feed enforces `(>= ts prev)`, a single accepted future-dated update poisons the monotonic ordering for the feed and blocks every legitimate follow-up price update (and therefore every borrow/withdraw/repay/liquidation touching that asset) until real chain time catches up to the poisoned value.

### Finding Description
`oracle-timestamp-fresh` computes: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

This is exactly the class of fix from the external report (avoiding `(- stacks-block-time ts)` underflow when `ts > stacks-block-time`), but Zest only neutralizes the *arithmetic* problem — it does not reject the future timestamp itself. When `ts > stacks-block-time`, `delta` is forced to `u0`, so the staleness bound is trivially satisfied and the price is treated as maximally fresh, regardless of how far in the future `ts` is.

`price-resolve` then persists that value into the shared per-feed cache unconditionally whenever it's newer than the stored one: [2](#0-1) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let (...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

`last-update` is a single map keyed only by `{type, ident}` (the price feed), shared by *every* user's transaction that needs a price for that asset: [3](#0-2) 

Once a price with `timestamp = T_future` (ahead of the real `stacks-block-time`) is accepted and stored as `last-update`, every subsequent legitimate price update for that feed with a correct (lower) timestamp fails the monotonicity check `(>= ts prev)` in `oracle-timestamp-fresh`, causing `ERR-ORACLE-INVARIANT` on every call that resolves that asset's price — borrows, withdrawals, repayments, liquidations, health checks — until real block time advances past `T_future`.

The upstream oracles feeding this path (Pyth via `pyth-storage-v4.clar`, DIA) themselves only enforce a *lower* staleness bound and never an upper one: [4](#0-3) 

so a signed, legitimate off-chain price update whose `publish-time` is slightly ahead of the Stacks chain's block time (ordinary cross-chain clock drift/latency — the exact scenario in the referenced Synthetix incident) can be permissionlessly relayed (`verify-and-update-price-feeds`/`get-price` are public, callable by anyone) at the moment it becomes advantageous to poison the cache.

### Impact Explanation
The `last-update` cache is shared state: one unprivileged caller (whoever triggers price resolution while a future-dated update is available) can plant a future timestamp that then blocks every other unprivileged user's operations relying on that asset's price — this is not a self-harm scenario, the attacker/triggerer's own transaction is unaffected while every other borrower/lender/liquidator using that asset is frozen out. This lands on **temporary freezing of funds**: users cannot borrow, withdraw, repay, or be liquidated for the affected asset while `last-update` remains stuck in the future.

### Likelihood Explanation
Likelihood is driven by ordinary cross-chain time skew between the off-chain price publisher (Pyth guardians / DIA) and Stacks block time, not by forging any data — the signed price payload is legitimate, only its relay timing matters, and both `get-price`/`verify-and-update-price-feeds` (Pyth) and the underlying DIA feed lookup are permissionlessly callable. No privileged access or governance compromise is required, satisfying the "unprivileged principal harms another via shared cache" pattern the scope explicitly allows.

### Recommendation
Add an explicit upper bound (max acceptable future skew) in `oracle-timestamp-fresh` instead of silently clamping `delta` to `u0`, e.g. `(asserts! (<= ts (+ stacks-block-time MAX_FUTURE_SKEW)) ERR-ORACLE-INVARIANT)`, and when persisting `last-update`, cap the stored value with `(min timestamp stacks-block-time)` so a single out-of-bounds submission cannot poison the monotonic ordering consumed by all subsequent callers.

### Proof of Concept
1. An off-chain Pyth-signed VAA carries `publish-time = T+30` for asset feed `F` (30s ahead of current `stacks-block-time` due to normal relay latency/clock drift).
2. Any unprivileged relayer submits/triggers this price (e.g., calls a market function requiring `F`'s price, going through `resolve-pyth` → `price-resolve`).
3. `oracle-timestamp-fresh(T+30, prev, max-staleness)` computes `delta = u0` (since `ts > stacks-block-time`) and passes; `last-update[F]` is set to `T+30` per [5](#0-4) .
4. Shortly after, a legitimate user B calls any market function needing `F`'s price with the next real (correct, lower) publish-time `T+1`. `oracle-timestamp-fresh(T+1, T+30, max-staleness)` fails the `(>= ts prev)` check, and `price-resolve` reverts with `ERR-ORACLE-INVARIANT`.
5. Every operation depending on `F`'s price (borrow, withdraw, repay, liquidate) reverts for all users until real `stacks-block-time` reaches `T+30`, freezing funds/positions tied to that asset.
