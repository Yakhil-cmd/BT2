### Title
Webhook signature verification is bound to `repository.owner.login`, not to the repository actually mutated — cross-tenant/cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), but every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, pull-request handlers) resolves the target `Stack`/`Repository`/`Team` using a *different*, independently attacker-controlled field: `payload.dig('repository', 'full_name')` (or `organization.login` for membership). Since both fields live in the same unsigned-until-verified JSON body, whoever controls the `webhook_secret` for *any one* configured GitHub organization can forge a payload where `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name` (or team `organization`) names a completely different, unrelated repository/org also configured on the same Shipit instance.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This selects the HMAC secret to check against based on `repository.owner.login` (the same untrusted, attacker-supplied JSON body). `verify_webhook_signature` (in `lib/shipit/github_app.rb`) does a byte-for-byte HMAC check of the *entire* raw body against that org's `webhook_secret`: [2](#0-1) 

Once signature verification passes, `create` dispatches the *entire same payload* to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

But every handler determines *what to mutate* using a different field of the payload:
- `Handler#stacks` / `#repository_name` uses `payload.dig('repository', 'full_name')`: [4](#0-3) 
- `PushHandler#process` calls `stack.sync_github` for every stack matching that `full_name` + branch: [5](#0-4) 
- `StatusHandler#process` writes a `Status` on any `Commit` matching the attacker-supplied `sha`, without checking repository ownership at all: [6](#0-5) 
- `MembershipHandler#process` creates/updates `Team` and adds/removes members based on `params.organization.login`, a field entirely independent of `repository.owner.login`: [7](#0-6) 

The engine explicitly supports multiple, independently administered GitHub App installations, each with its own `webhook_secret` set by whoever installed that GitHub App for their org (see `test/dummy/config/secrets_double_github_app.yml`, defining `OrgOne` and `OrgTwo` each with their own `webhook_secret`/`private_key`): [8](#0-7) 

The broken binding, stated as an equality that should hold but doesn't:
`organization whose webhook_secret authenticated the request` == `repository/org actually written to by the handler`

Before the attacker's request: only GitHub (or whoever legitimately controls OrgTwo's GitHub App settings) can produce a valid signature for OrgTwo, and that signature is only ever expected to describe events belonging to OrgTwo's repositories.
After the attacker's request: the administrator of OrgTwo's GitHub App (unprivileged with respect to OrgOne) can sign a payload with OrgTwo's `webhook_secret` while setting `repository.full_name` to `OrgOne/some-repo` (or `organization.login` to any team's org for membership events), and Shipit will process it as if it were a legitimate event about OrgOne's stack/team, because the code never checks that the field used for signature-org-selection matches the field used for the actual mutation.

### Impact Explanation
This lets an attacker who controls one organization's GitHub App webhook secret (a routine, low-privilege capability if Shipit serves multiple independently-administered GitHub orgs, as the codebase's own multi-org fixtures demonstrate) forge fully valid, signed webhook events targeting **any other org/repository configured in the same Shipit instance**. Concrete cross-repository writes achievable:
- Force `PushHandler` to trigger `stack.sync_github(expected_head_sha: ...)` on arbitrary stacks belonging to a different repo/org.
- Inject fake commit `Status` records (`StatusHandler`) on arbitrary commits by SHA, potentially unblocking CI gating for deploys on stacks unrelated to the attacker's own org.
- Manipulate `Team` membership (`MembershipHandler`) for teams tied to `organization.login` values fully independent from the org whose secret signed the request, which can affect `Shipit.github_teams` based authorization checks used elsewhere (`app/controllers/concerns/shipit/authentication.rb`) — i.e., escalation into `Shipit.github_teams` authorization.

This satisfies the "Critical: cross-repository writes" / "High: escalation into `Shipit.github_teams` authorization" impact bar defined by the rules.

### Likelihood Explanation
Any deployment of this engine that federates multiple GitHub organizations/apps under one Shipit instance (explicitly supported and exercised by the repo's own `secrets_double_github_app.yml` fixture) is affected. The only requirement is that the attacker legitimately controls (or has been handed) the `webhook_secret` for at least one configured org's GitHub App — which is routine for any org admin who installed their own GitHub App, and does not require any Shipit session, API token, or GitHub repository write access to the *target* org.

### Recommendation
After signature verification succeeds, re-derive (or verify) that the organization used to select the `webhook_secret` (`repository_owner`) matches the organization actually referenced by the field the handler will act on (`repository.full_name`'s owner, or `organization.login` for membership events) before dispatching to handlers. Alternatively, resolve the target `Stack`/`Repository`/`Team` strictly from the same `repository_owner` value used for signature verification, rejecting any event where the acted-upon repository's owner differs from the authenticating organization.

### Proof of Concept
1. Shipit is configured with two GitHub App installations, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately administers OrgTwo's GitHub App and thus knows `OrgTwo`'s `webhook_secret`.
3. Attacker crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/private-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgTwo_webhook_secret, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: 'OrgTwo')` (from `repository.owner.login`), validates the HMAC using `OrgTwo`'s secret — passes.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('OrgOne/private-repo')` and calls `sync_github(expected_head_sha: ...)` on OrgOne's stack, even though the attacker never controlled OrgOne's app or secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
