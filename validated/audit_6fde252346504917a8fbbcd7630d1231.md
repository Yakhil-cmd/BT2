## Analysis

I found a concrete binding-break analog: the webhook signature verification in `WebhooksController` selects which GitHub App/secret to verify against using `repository.owner.login` from the unauthenticated payload body, while the actual event handlers (e.g. `StatusHandler`, `PushHandler`) act on data keyed by `sha` / `repository.full_name` that is never cross-checked against that same `owner.login`. Combined with `verify_webhook_signature` returning `true` unconditionally whenever no `webhook_secret` is configured for the selected organization [1](#0-0) , this breaks the equality: `organization verified == organization whose repository is acted upon`.

### Title
Webhook signature verification keyed to attacker-controlled `repository.owner.login` allows forging events for any tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the HMAC secret) to validate a webhook against using `repository_owner`, a value taken directly from the unauthenticated JSON body (`params.dig('repository','owner','login')`), before any signature has been validated [2](#0-1) . The handlers that subsequently act on the payload (e.g. `StatusHandler`, matching commits purely by `sha`, or `Handler#stacks` matching `repository.full_name`) never re-verify that this owner matches the repository that was actually targeted [3](#0-2) [4](#0-3) .

### Finding Description
Shipit supports multiple GitHub App configurations, one per organization, selected by `Shipit.github(organization:)` [5](#0-4) . Setup docs explicitly document that some orgs may have `webhook_secret` left blank ("`webhook_secret: # nil`") [6](#0-5) . In `GitHubApp#verify_webhook_signature`, when no secret is configured for the selected organization, verification is bypassed entirely: `return true unless webhook_secret` [1](#0-0) .

Crucially, the organization used to pick the verifying `GitHubApp` is read straight out of the same untrusted JSON body being verified: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [7](#0-6) . Nothing enforces that this `owner.login` is consistent with the `repository.full_name` (or the `sha`) that the downstream handler actually acts on — these are two independent JSON fields supplied by the same anonymous POST body.

Concretely: if Shipit is multi-org configured and any one configured organization has no `webhook_secret` set, an unauthenticated attacker can submit a `status` (or `push`, `pull_request`, etc.) webhook where `repository.owner.login` is set to that secret-less organization (so `verify_webhook_signature` trivially returns `true`), while the rest of the payload (`sha`, `repository.full_name`, `state`, etc.) targets a *different*, fully-protected organization's repository/stack. `StatusHandler#process` looks up commits purely by `sha` across the whole install, with no organization or repository check at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [8](#0-7) . `Commit#create_status_from_github!` creates a `Status` record, and `Status#state == 'success'` for a required CI context transitions the commit to `deployable?` and schedules continuous delivery via `stack.schedule_merges` / `commit.schedule_continuous_delivery` [9](#0-8) [10](#0-9) . This equals crafting a fake "CI passed" signal for a target commit that then gets auto-deployed by any stack configured for continuous deployment — i.e., an unauthorized deploy triggered purely from a forged, effectively-unauthenticated webhook whose signature check was satisfied against an unrelated organization.

### Impact Explanation
This breaks "an organization that authenticated versus the repository that is written": the app authenticates the *webhook sender* against organization A's (missing) secret, but the payload writes CI/status state for a commit that lives in organization B's repository/stack, with no code path re-validating that A == B. The consequence is a forged CI-status webhook that can flip a commit to `deployable?` and trigger continuous deployment (`schedule_continuous_delivery`) for any stack with `continuous_deployment: true`, i.e., an unauthorized deploy, which is explicitly listed as a Critical-severity impact for this scope.

### Likelihood Explanation
Requires that the Shipit instance is configured with multiple GitHub organizations (a documented supported configuration) and that at least one configured organization has no `webhook_secret` set (also explicitly shown as a valid/blank config in the shipped example secrets files). Given that combination — which the docs themselves suggest as acceptable ("webhook_secret: # nil") — exploitation requires no credentials at all: a single unauthenticated POST to `/webhooks` with a crafted JSON body and no valid `X-Hub-Signature` needed for the chosen org. This makes likelihood Medium: it hinges on operator configuration (multi-org + at least one org without a secret), which is a realistic and explicitly documented deployment pattern.

### Recommendation
- Verify the webhook signature against the actual repository/organization the event's handler will act upon, not a value pulled from the same unauthenticated body used only for App/secret selection.
- Do not allow signature verification to unconditionally pass when `webhook_secret` is blank for a *specific* organization in a multi-org configuration; either require all configured organizations to set a secret, or refuse events whose derived organization has no configured secret.
- In `StatusHandler` (and other handlers), scope lookups (e.g. `Commit.where(sha: ...)`) to the repository/stack whose owner matches the organization that was actually cryptographically verified, rather than matching globally by `sha`/`full_name` alone.

### Proof of Concept
1. Operator configures Shipit with two organizations, e.g. `OrgSecure` (secret set, hosts the real target stack/commit) and `OrgOpen` (no `webhook_secret` set) — matching the documented multi-app pattern in `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and a JSON body:
```json
{
  "sha": "<sha-of-target-commit-in-OrgSecure/target-repo>",
  "state": "success",
  "context": "<required-ci-context>",
  "repository": { "owner": { "login": "OrgOpen" }, "full_name": "OrgOpen/decoy" }
}
```
No valid `X-Hub-Signature` header is required, since `verify_signature` selects `Shipit.github(organization: 'OrgOpen')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [1](#0-0) .
3. `StatusHandler#process` matches the commit purely by `sha` (ignoring `repository`), creating a `success` `Status` on the target commit in `OrgSecure`'s stack [11](#0-10) .
4. If that stack has `continuous_deployment: true` and the forged context satisfies `required_statuses`, the commit becomes `deployable?` and continuous delivery is scheduled, resulting in an unauthorized deploy — without ever presenting a valid signature for `OrgSecure`.

**Uncertainty**: I could not directly execute this end-to-end in this environment (no filesystem/terminal access here), so this is based on static code tracing of `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, and `app/models/shipit/commit.rb`. Whether a real-world deployment actually leaves one organization's `webhook_secret` blank while running multi-org is an operational assumption; if all configured organizations always have a secret set, this specific path is not exploitable, though the underlying design flaw (verification-selector field not bound to the acted-upon repository) remains.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
