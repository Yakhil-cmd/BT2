### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler acts on the unrelated `repository.full_name` field, letting any org that legitimately possesses one GitHub App's `webhook_secret` forge CI statuses / provisioning / sync events for a completely different tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . Every actual `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the repository/stack to act on using a **different** payload field, `repository.full_name` [2](#0-1) [3](#0-2) [4](#0-3) . Nothing in the controller or handlers checks that the owner encoded in `full_name` matches `repository.owner.login`/`organization.login` used to pick the signing secret. In Shipit's supported multi-organization configuration (`Shipit.github_app_config`, one `app_id`/`webhook_secret` per org) [5](#0-4) , this breaks the binding "organization whose secret authenticated the request == repository that is actually written to."

### Finding Description
The webhook endpoint is a plain, unauthenticated HTTP `POST /webhooks` route (only `X-Hub-Signature` is checked) [6](#0-5) . `verify_signature` computes:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

with `repository_owner` sourced purely from the JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [7](#0-6) . `Shipit.github(organization:)` looks up that organization's own `webhook_secret` from `secrets.github` [8](#0-7) [9](#0-8) , and `verify_webhook_signature` HMACs the *entire raw body* with that org's secret [10](#0-9) .

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw JSON to handlers [11](#0-10) . Handlers universally locate the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')` [2](#0-1) , e.g. `PushHandler#process` [12](#0-11) , `PullRequest::OpenedHandler#repository` [3](#0-2) , and `StatusHandler#process`, which creates a `Status` for any commit matching the attacker-supplied `sha`, regardless of which org that commit's stack belongs to [4](#0-3) .

Since `repository.owner.login` (used only to pick the verifying secret) and `repository.full_name` (used to select the target `Repository`/`Stack`/commit) are independent strings inside the same JSON body, and the org whose secret was used for verification is never required to be the owner of that `full_name`, an entity that legitimately knows one organization's `webhook_secret` (e.g., the admin of Org A's own GitHub App, who chose that secret when creating the App per `docs/setup.md`) can forge a body where `repository.owner.login = "org-a"` but `repository.full_name = "org-b/victim-repo"`, sign it with Org A's secret, and have it accepted and dispatched against Org B's stacks.

### Impact Explanation
This breaks the equality "the organization that authenticated (owns the verifying secret) == the repository that gets written." Concretely, `StatusHandler` lets the forger inject arbitrary `state`/`context`/`description` `Status` rows onto any commit sha existing under Shipit, in any org's stack, which feeds directly into `Commit#deployable?` / continuous-delivery decisioning and can flip a stack from blocked to deployable (`stack.schedule_merges`/`schedule_continuous_delivery` fire on status changes) [13](#0-12) [14](#0-13) . Combined with `PushHandler` (forces `sync_github`/re-check of arbitrary tracked repos) and `PullRequest` handlers (provisioning/archiving review stacks of arbitrary repos) [15](#0-14) , this is an unauthorized cross-organization write to another repository's deployability state — an unauthorized-deploy-adjacent primitive matching the "cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
Low-to-moderate: it requires the attacker to operate a GitHub organization that itself has a legitimately configured GitHub App on this Shipit instance (i.e., they know that org's own `webhook_secret`, which they picked when registering the App per `docs/setup.md`), and it only applies when Shipit is run with the multi-org config schema. No GitHub-side signature key, `GITHUB_TOKEN`, `api_clients_secret`, or Shipit session is needed — the forged HTTP request is sent directly to the public `/webhooks` endpoint.

### Recommendation
Cross-check that the organization embedded in `repository.full_name` (or resolved `Repository#owner`) matches the organization whose secret verified the signature (`repository_owner`) before dispatching handlers, and reject the request otherwise.

### Proof of Concept
1. Attacker registers/administers their own GitHub App for `org-a` on the shared Shipit instance and knows `org-a`'s `webhook_secret` (self-chosen at App creation time, per `docs/setup.md`).
2. Attacker crafts a `status` event JSON body with `repository.owner.login = "org-a"` and `sha`/`state`/`context` targeting a commit that belongs to a stack under `org-b` (a different tracked org/repo).
3. Attacker computes `sha1=HMAC(org-a-secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status` and that `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and successfully verifies the signature against `org-a`'s secret [16](#0-15) .
5. `StatusHandler#process` matches the commit by `sha` alone and creates the forged `Status`, regardless of which org/stack owns that commit [17](#0-16) , potentially unblocking a deploy for `org-b`'s stack.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
