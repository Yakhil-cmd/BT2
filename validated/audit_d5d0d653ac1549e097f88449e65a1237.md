### Title
Cross-tenant CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler`, escalated to unauthorized merge when `merge_queue_enabled` is true - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits by bare SHA across the entire `commits` table with no repository/stack scoping, unlike every other webhook handler which scopes lookups through `Handler#stacks` (which filters by `Repository.from_github_repo_name(repository_name)`). An attacker who legitimately owns/onboards one repository into Shipit can send a properly signed `status` webhook whose `sha` matches an identical commit that also exists under a completely unrelated victim stack (e.g. via forking a public repo tracked by the victim stack), writing a forged `Status` row onto the victim's `Commit` and triggering `stack.schedule_merges`, which — combined with `merge_queue_enabled: true` — can complete `MergeRequest#merge!` on the victim stack.

### Finding Description
The broken binding: the code should enforce `commit.stack.repository.full_name == payload.dig('repository','full_name')` (i.e., a status only touches commits belonging to the repository that authenticated the webhook), but `StatusHandler#process` never checks this at all: [1](#0-0) 

Compare this to the base class helper used by every other handler (`PushHandler`, `PullRequest::*Handler`), which explicitly resolves the acting repository first: [2](#0-1) 

`StatusHandler` bypasses `stacks`/`repository_name` entirely and queries `Commit.where(sha: params.sha)` directly, matching every `Commit` row in the database that shares that SHA string, irrespective of which `stack_id`/repository it belongs to.

`Commit` has no global or cross-stack uniqueness constraint on `sha`: [3](#0-2) 

so identical commits (e.g., produced by forking a public upstream repo that a victim Shipit stack tracks, or any two repos sharing history) legitimately create two separate `Commit` rows with the same `sha` under two different `stack_id`s.

Signature verification (`WebhooksController#verify_signature`) only proves the request came from an org/app installation configured in Shipit, using the webhook_secret scoped by `repository_owner` in the payload: [4](#0-3) 
It does not, and cannot, constrain which `sha` values the sender is allowed to reference — an attacker who owns a repository onboarded into Shipit (their own account/org, with a webhook_secret they configured themselves) can sign an arbitrary `sha`/`context`/`state` payload for **their own** repository, and `StatusHandler` will apply it to any commit in the system sharing that `sha`, including one belonging to a victim stack in a different organization.

Exploit flow:
1. Victim stack `V` tracks public repo `upstream/repo`, has `merge_queue_enabled: true`, requires context `continuous-integration/travis-ci`, and has a pending `MergeRequest` whose head commit SHA is `S` (already imported into Shipit as `Commit(stack_id: V.id, sha: S)`).
2. Attacker forks `upstream/repo` into their own account, which is separately onboarded into Shipit as stack `A` (owned by attacker, legitimate webhook secret known to attacker). Because Git commit hashes are content-addressed, `S` is identical in the fork, and Shipit imports `Commit(stack_id: A.id, sha: S)`.
3. Attacker POSTs `/webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with their own `webhook_secret`, `repository.full_name = "attacker/repo"`, `sha: S`, `context: "continuous-integration/travis-ci"`, `state: "success"`.
4. `verify_signature` passes (valid signature for attacker's own org). `StatusHandler#process` runs `Commit.where(sha: S)`, which returns **both** `Commit(stack_id: A.id)` and `Commit(stack_id: V.id)`, and calls `create_status_from_github!` on each — writing a forged success `Status` scoped to `V.id` on the victim's stack.
5. `Commit#add_status` runs `stack.schedule_merges if new_status.pending? || new_status.success?` → `ProcessMergeRequestsJob.perform_later(V)`. [5](#0-4) 
6. In the job, since `V.allows_merges?` is true (`merge_queue_enabled? && !locked? && merge_status == 'success'`), and `merge_request.all_status_checks_passed?` now returns true because of the forged status, `merge_request.merge!` executes against GitHub, merging attacker-influenced/unauthorized state into the victim repository. [6](#0-5) [7](#0-6) [8](#0-7) 

No existing guard prevents this: `verify_signature` authenticates the sender's own organization, not the target commit's ownership; `StatusHandler` performs no `repository_name`/`stacks` check at all (unlike its siblings); and there is no DB constraint tying `sha` uniqueness to a single stack.

### Impact Explanation
A payload authenticated for one repository (the attacker's own) mutates the CI/status state of another, unrelated repository/stack's commit, and — when `merge_queue_enabled` is true — that forged status can be the deciding factor that causes `MergeRequest#merge!` to execute against the victim's actual GitHub repository, i.e., an unauthorized merge. This matches the Critical impact category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge." It is repeatable against any victim stack/commit whose SHA the attacker can reproduce (trivial for public/forkable repositories) and does not require any Shipit session, API token, or GitHub secret belonging to the victim.

### Likelihood Explanation
Preconditions: the attacker needs (a) to legitimately own/onboard some repository into the same Shipit instance (self-service in many Shipit deployments), which gives them a valid signing secret for their own org; (b) a victim stack with `merge_queue_enabled: true` tracking a repo whose commit the attacker can reproduce byte-for-byte (trivial via fork, since git SHAs are content hashes, not repo-scoped). No live GitHub interaction, no privileged role, and no secret of the victim's is needed. Cost is low (one fork + one signed HTTP POST); the attack is repeatable against any stack sharing a SHA with an attacker-controlled repo.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: resolve the acting repository via `repository_name`/`stacks` from the payload and restrict the `Commit` lookup to `stack_id IN (stacks.ids)` (or otherwise verify `commit.stack.repository.full_name == repository_name`) before calling `create_status_from_github!`, mirroring `Handler#stacks`.

5. Assert after: a `Status` row now exists with `stack_id: stack_v.id` for that commit, `merge_request.all_status_checks_passed?` flips to `true`, and `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [stack_v])`; simulate job run and assert `merge_request.reload.merged?` (with `github_api.merge_pull_request` stubbed) to demonstrate the unauthorized merge on the victim stack triggered entirely by a payload signed for `repository_a`.
