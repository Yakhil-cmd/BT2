### Title
Webhook signature verification is keyed on an attacker-controlled organization field that is disconnected from the repository the event handlers act on, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`). Once verification "succeeds," the raw `params` (including a completely independent `repository.full_name` field) is handed to the registered `Shipit::Webhooks` handlers, which resolve the target `Stack`/`Repository` from `repository.full_name` alone. Because the two fields are never cross-checked, an attacker who knows (or can obtain) the webhook secret for *any one* configured GitHub organization can forge webhook events that are processed against a *different* organization's stacks.

### Finding Description
`verify_signature` computes the verifying app from a payload field: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` config for that org (Shipit explicitly supports multiple independently-configured GitHub organizations, each with its own `webhook_secret`, as documented in `docs/setup.md`), and `verify_webhook_signature` is checked against that org's secret alone: [3](#0-2) 

Critically, if that organization has no `webhook_secret` configured (documented as "optional"), verification unconditionally returns `true`:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Once verification passes, the entire raw `params` object is dispatched to handlers: [4](#0-3) 

Every handler resolves the affected `Stack`/`Repository` from a *different* field, `repository.full_name`, with no relationship enforced to the `repository.owner.login`/`organization.login` value used for signature verification: [5](#0-4) 

For example `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for any stack matching `repository.full_name`+branch: [6](#0-5) 

The equality this breaks: `organization used to authenticate the webhook` should equal `organization that owns the repository the handler mutates`, but nothing in the code enforces `params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`.

### Impact Explanation
An attacker who has legitimate admin access to their own GitHub organization/repository (`OrgA`, tracked by the same multi-tenant Shipit instance as an unrelated `OrgB`) knows `OrgA`'s webhook secret (they configured it, or it may be left blank as documented "optional"). They can sign (or, if blank, submit unsigned) a POST to the public, unauthenticated `/webhooks` endpoint with `repository.owner.login = "OrgA"` (satisfies signature check) but `repository.full_name = "OrgB/target-repo"` (drives the actual handler logic). This lets them:
- Forge `push` events to force `GithubSyncJob`/`stack.sync_github` to run against `OrgB`'s stack with an attacker-chosen `expected_head_sha`.
- Forge `status`/`check_suite`/`commit_status` events to mark commits on `OrgB`'s repository as passing, which feeds into `MergeRequest`/merge-queue gating and continuous-deployment eligibility checks — enabling an unauthorized merge or deploy on a repository the attacker has no access to.

This is a cross-repository/cross-organization boundary violation reachable by an unprivileged external attacker, matching the Critical impact category "unauthorized deploy, rollback or merge" / "cross-repository writes."

### Likelihood Explanation
Requires a multi-organization Shipit deployment (a documented, supported configuration) where the attacker controls or knows the webhook secret (or lack thereof) for at least one configured organization, distinct from the organization they wish to affect. No GitHub App private key, `ApiClient` token, or Shipit session is required — only an HTTP POST to the public `/webhooks` route.

### Recommendation
Derive the organization used for signature verification and the repository acted upon from the same trusted source, and reject requests where `repository.full_name`'s owner does not match the organization whose secret was used to verify the signature. Alternatively, verify the signature against every configured organization's app associated with the actually-targeted repository (looked up via `repository.full_name`), not an attacker-suppliable `owner.login`/`organization.login` field.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` (attacker-controlled, blank/known `webhook_secret`) and `OrgB` (victim org, tracked stack `OrgB/target-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Sign with `OrgA`'s secret (or omit `X-Hub-Signature` if `OrgA` has none configured) — `verify_signature` passes because it only checks against `OrgA`'s `GitHubApp`.
4. `PushHandler` runs against the `Stack` matching `OrgB/target-repo`, invoking `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on a stack the attacker does not control.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
