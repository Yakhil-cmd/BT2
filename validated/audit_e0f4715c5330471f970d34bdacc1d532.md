### Title
CCMenuController leaks build status of any stack to an ApiClient token that is scoped to a single stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` implements per-token stack scoping: when an `ApiClient` has a `stack_id` set, the `stacks`/`stack` helpers restrict resource lookup to that one `Stack` [1](#0-0) . `Shipit::Api::CCMenuController`, however, overrides `stack` to bypass that scoping entirely, loading any stack directly by its param regardless of which stack the authenticated token is bound to [2](#0-1) .

### Finding Description
The equality that should hold is: `stack a token authorizes == stack a token touches`. `BaseController#stacks` enforces this by scoping to `Stack.where(id: current_api_client.stack_id)` whenever `current_api_client.stack_id?` is true, and `BaseController#stack` resolves the requested resource through that scoped relation: [1](#0-0) 

`CCMenuController` is a subclass of `BaseController` and inherits `require_permission :read, :stack`, which only checks that the token's `permissions` array contains `read:stack` — it performs no per-stack scoping check [3](#0-2) . The actual per-stack authorization boundary lives exclusively in `BaseController#stack`/`#stacks`. `CCMenuController` redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` relation, entirely skipping the `stacks` scoping helper: [4](#0-3) 

This is confirmed by the same test suite that documents the intended scoping behavior for other stack-scoped endpoints (e.g. `StacksController#index`), where `here_come_the_walrus` (a fixture `ApiClient` bound to a single stack) is asserted to only see one stack via the `stacks` helper [5](#0-4) . `CCMenuController`'s own test suite never exercises a stack-scoped client against a *different* stack's id, so the missing check went unverified [6](#0-5) .

Before the request: the token authorizes reads on stack A only (`current_api_client.stack_id == A.id`).
After the request: `GET /api/A_or_any_id/ccmenu.xml?token=<A's token>` for `stack_id=B` succeeds because `stack` resolves `B` directly from `Stack.from_param!`, never consulting `current_api_client.stack_id`.

### Impact Explanation
A stack-scoped `ApiClient` credential — deliberately restricted at issuance to a single stack/repository (e.g. a CCMenu client meant to expose only one team's build status) — can be used to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state) for every other stack in the Shipit instance, including stacks belonging to different repositories/teams. This is an unauthorized cross-stack read of stack state, matching the High-impact category "unauthenticated read of stack state, task streams or deploy output" relative to what the credential was scoped to authorize.

### Likelihood Explanation
Exploitation only requires possession of any valid `read:stack`-permissioned `ApiClient` token that is scoped to a single stack (such tokens are handed out for limited integrations, e.g. via `CCMenuUrlController`, and are lower-privilege than an unscoped token) [7](#0-6) . No additional secrets, signatures, or elevated access are needed — just changing the `stack_id` route/query parameter to a target stack's identifier.

### Recommendation
Remove the `stack` override in `CCMenuController`, or reimplement it to go through the inherited `stacks` scoping relation (`stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens cannot read stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` with `permissions: ["read:stack"]` and `stack_id` set to stack A's id (mirrors the `here_come_the_walrus` fixture pattern used elsewhere in the test suite).
2. Send `GET /api/<stack_B_param>/ccmenu.xml?token=<clientA.authentication_token>` where stack B is a different stack.
3. Observe HTTP 200 with stack B's build status rendered, despite the token being scoped only to stack A — because `CCMenuController#stack` calls `Stack.from_param!` directly instead of `stacks.from_param!`.
