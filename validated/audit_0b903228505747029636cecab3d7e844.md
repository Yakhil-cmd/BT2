### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but `StatusHandler`/`PushHandler` act on targets selected from other unauthenticated payload fields (`sha`, `repository.full_name`) with no cross-check - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/org config (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, a value taken straight out of the same untrusted JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`). Nothing then re-validates that the *acted-upon* target (the commit SHA for `status` events, or `repository.full_name` for `push`/PR events) actually belongs to that authenticated organization. `StatusHandler#process` is the worst offender: it resolves target commits with a completely global, unscoped query `Commit.where(sha: params.sha)` — it never even looks at `repository.full_name` or the org. This breaks the trust binding "organization that authenticated == repository/commit that is written."

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` is derived from the payload itself: [2](#0-1) . In a multi-org deployment (documented and supported, see `docs/setup.md` "Using Multiple Github Applications"), each org has its *own*, independently configured, *optional* `webhook_secret` [3](#0-2) . Per `verify_webhook_signature`, `return true unless webhook_secret` — i.e. any org configured **without** a webhook secret accepts *any* signature (or none) unconditionally.

The signature check is therefore only bound to whichever organization login string appears in the payload's `repository.owner.login`/`organization.login` field — it is never cross-checked against the field the handlers actually use to select the object being mutated:
- `PushHandler`/other handlers resolve the target `Stack` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [4](#0-3)  — a *different* JSON field than the one used for auth-org selection.
- `StatusHandler#process` doesn't even use the repository at all: it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) , which is completely unscoped to any stack/repo/organization.

Combined, this means: if *any single* GitHub org configured in the multi-org `github:` secrets block has no `webhook_secret` set (explicitly documented as optional, [6](#0-5) ), an unprivileged party can POST a self-crafted JSON body directly to `/webhooks` with `repository.owner.login` (or `organization.login`) set to that unsecured org — passing `verify_signature` trivially — while the actually-affected object (`sha` for status events, or `repository.full_name` for push/PR events) is chosen freely and can reference a commit/repository belonging to a completely different, properly-secured organization/App.

`create_status_from_github!` then persists an attacker-chosen `state`/`context`/`target_url`/`description` as a real `Status` on that arbitrary commit [7](#0-6) . Status changes feed directly into deploy/merge gating: `deployable?` depends on `success?` [8](#0-7) , and `add_status` triggers `stack.schedule_merges if new_status.pending? || new_status.success?` [9](#0-8) , i.e. forging a green status can unblock the automatic merge queue and continuous-deployment pipeline for a commit/repo the attacker never authenticated for.

### Impact Explanation
This crosses exactly the boundary called out as in-scope: an organization/App credential that authenticated (whichever org's config was selected via the unauthenticated `repository_owner` field, possibly one with no secret at all) is not the same as the repository/commit that is actually written (chosen via `sha`/`repository.full_name`, completely uncorrelated fields). The practical outcome is forging commit statuses on arbitrary commits tracked by the Shipit instance, which can flip `deployable?`/merge-queue gating and trigger an unauthorized deploy or merge — matching the High/Critical criteria ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only: (1) the target Shipit instance be configured for multiple GitHub organizations (a documented, supported configuration) where at least one configured org has no `webhook_secret` set (also documented as "optional"), and (2) knowledge of a target commit SHA and repository full name, both of which are typically public GitHub information. No GitHub App private key, session, or `ApiClient` token is required — the request goes straight to the public `/webhooks` endpoint. This is a config-dependent but realistic and unprivileged path, not requiring social engineering, TLS interception, or host misconfiguration outside documented options.

### Recommendation
- Bind the webhook-authenticity check to the *same* identifier the handler will act on: after selecting the org/app for signature verification, re-derive and enforce that `repository.full_name`'s owner (and, for `status`/`check_run`/`check_suite` events, the commit's owning stack/repository) matches the org whose secret validated the signature.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank in a multi-org configuration; either require a secret for every configured org or reject/flag such configurations.
- In `StatusHandler` (and any handler using `Commit.where(sha: ...)`), scope the lookup to the stack resolved from `repository.full_name` of the *verified* payload, not a bare global SHA search.

### Proof of Concept
Given a multi-org `secrets.yml` where org `unsecured-org` has `webhook_secret: nil` and org `victim-org` has a real App/secret and a tracked stack for `victim-org/victim-repo` with an undeployed commit `abc123...`:

```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=anything-or-omit

{
  "sha": "abc123def4567890abc123def4567890abc1234",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example.com",
  "repository": { "owner": { "login": "unsecured-org" } }
}
```
`verify_signature` looks up `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the header. `StatusHandler#process` then runs `Commit.where(sha: "abc123...")`, finds the commit belonging to the unrelated `victim-org/victim-repo` stack, and records a forged successful status — potentially unblocking that stack's merge queue/continuous deployment, even though `victim-org`'s webhook secret was never satisfied.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
