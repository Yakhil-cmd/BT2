### Title
Webhook signature is verified against `repository.owner.login`, but the repository/stack that gets acted upon is resolved from the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization whose `webhook_secret` will validate the HMAC signature using `repository.owner.login` (falling back to `organization.login`), while every webhook `Handler` resolves the target `Stack`/`Repository` to mutate using the unrelated `repository.full_name` field of the same JSON body. Because these two attacker-controlled fields are never cross-checked against each other, a party who legitimately knows the `webhook_secret` for one organization configured on a multi-tenant Shipit instance can forge a signature that Shipit accepts as "authenticated for OrgA", while pointing `repository.full_name` at a stack belonging to a different, unrelated repository/organization.

### Finding Description
`WebhooksController#verify_signature` computes the org used for signature verification like this: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) purely to look up which `Shipit.github(organization: ...)` app config's `webhook_secret` should validate `X-Hub-Signature`.

Once the signature is accepted, `create` dispatches the full, attacker-controlled `params` hash to the registered handler(s): [3](#0-2) 

Every `Handler` then determines *which* `Stack`/`Repository` to operate on using a completely different field of the same payload: [4](#0-3) 

For example `PushHandler` uses this to trigger `stack.sync_github`: [5](#0-4) 

Nothing in the request pipeline enforces the invariant `repository.owner.login == repository.full_name.split('/').first`. `verify_signature` only proves that the raw body was signed with the secret belonging to whatever organization `repository.owner.login` (or `organization.login`) names — it says nothing about which repository the handler will actually act on, because `repository_name` is read independently from `repository.full_name`.

This is the same bug class as the reported `swapOn1INCH` issue: a value that is trusted and acted upon (`repository.full_name`, "the repository that is written") is never actually checked against the value that was validated to establish trust (`repository.owner.login`, "the organization that authenticated"). The low-level check in the Solidity report ("was the call successful") is analogous here to "does the authenticated organization actually match the repository being modified" — both are missing bindings between an action and the thing that was supposed to authorize it.

### Impact Explanation
On a multi-tenant Shipit deployment (multiple GitHub Apps/organizations configured in `secrets.yml`, each with its own `webhook_secret` — a supported and documented configuration, see `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), any party who is a legitimate holder of one organization's `webhook_secret` can forge a signed payload whose `repository.owner.login`/`organization.login` names their own org (so signature verification passes) but whose `repository.full_name` names a stack belonging to a completely different, unrelated organization configured on the same Shipit instance. The handler dispatched from `create` will then resolve and mutate that unrelated stack (e.g., trigger `sync_github`, or other handlers that record statuses/check-suite state/lock changes keyed only off `repository.full_name`), a cross-repository/cross-tenant write performed without ever possessing that victim organization's `webhook_secret`.

### Likelihood Explanation
Requires the attacker to already legitimately hold a `webhook_secret` for at least one organization configured on a shared/multi-tenant Shipit install — this is not a random unauthenticated internet attacker, but it is not a privileged Shipit account either; it is an unprivileged-relative-to-the-victim-org GitHub App/webhook credential holder. Given that `secrets.yml` explicitly supports registering multiple independent organizations (`test/dummy/config/secrets_double_github_app.yml`), this is a realistic configuration, and no additional guessing or race condition is needed — the mismatch is directly exploitable by crafting one HTTP request with a valid HMAC for the attacker's own org.

### Recommendation
After `verify_signature` succeeds, re-derive the organization/owner actually referenced in `repository.full_name` (or `organization.login` used for dispatch) and require it to match `repository_owner` used for signature selection before invoking any handler. Concretely, in `WebhooksController`, reject the request (e.g. `head(422)`) unless `params.dig('repository', 'full_name')&.split('/', 2)&.first == repository_owner`, or have `Handler#repository_name`/`stacks` re-validate ownership against the verified organization rather than trusting `repository.full_name` in isolation.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own `github.webhook_secret` (as supported by `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately controls `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies the signature successfully against `OrgA`'s secret [1](#0-0) .
6. `create` dispatches to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` = `"OrgB/victim-repo"` [6](#0-5) , and calls `stack.sync_github(expected_head_sha: params.after)` on the `OrgB` stack [5](#0-4)  — a write performed on `OrgB`'s stack despite the request only being authenticated against `OrgA`'s secret.
