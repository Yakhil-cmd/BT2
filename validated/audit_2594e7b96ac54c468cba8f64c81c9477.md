### Title
`EnvironmentVariables#permit` ignores `VariableDefinition#select`, allowing values outside declared whitelist for select-constrained variables - ([File: lib/shipit/environment_variables.rb])

### Summary
`EnvironmentVariables#sanitize_env_vars` only checks that the submitted env var *name* is in the list of permitted names (`variable_definitions.map(&:name)`) and never checks the submitted *value* against `VariableDefinition#select` when a `select` whitelist is declared for that variable. This means a `select`-constrained variable (e.g. `ENVIRONMENT: [production, canary]`) can be given any arbitrary string value by whoever supplies the `env` params, and that value passes `permit` unchanged.

### Finding Description
The broken binding: for any `VariableDefinition` `vd` where `vd.select.present?`, it should hold that `permit(env)[vd.name] ∈ vd.select`. In the actual code: [1](#0-0) 

`sanitize_env_vars` computes `allowed_variables = variable_definitions.map(&:name)` and partitions `@env` purely by key membership in that name list — the `select` attribute of `VariableDefinition` is never read here. `VariableDefinition#initialize` does parse and store `@select`, [2](#0-1)  but nothing in `EnvironmentVariables#permit` consults it, and the accompanying test suite only exercises name-based filtering, never a `select` violation. [3](#0-2) 

However, tracing the reachable attacker path shows this is **not exploitable by an unprivileged, unauthenticated attacker** as defined in scope. The only concrete caller found, `DeploysController#create`, requires a loaded, existing `@stack` and passes `deploy_params[:env]` — and `deploy_params` itself is filtered through Rails strong-parameters using `@stack.deploy_variables.map(&:name)` before ever reaching `trigger_deploy`/`permit`: [4](#0-3) [5](#0-4) 

Triggering a deploy through this controller requires an authenticated Shipit session (this is gated by the base `ShipitController`, which was not present in the index to fully confirm the exact filter name, but the codebase's routing/controllers for deploys are documented elsewhere as session-protected, and the attacker model explicitly states the attacker holds "no Shipit session, no `ApiClient` token"). There is no route reachable via unauthenticated webhook (`POST /webhooks`) that lets an outside GitHub user or anonymous HTTP client supply arbitrary `env` values into a deploy — webhook payloads drive commit/status/PR bookkeeping, not deploy env vars.

Because the attacker model here excludes any authenticated Shipit user (maintainer or otherwise), and no unauthenticated code path was found that lets `env` params reach `permit`, the described bug — while real as a logic defect in `EnvironmentVariables#permit` — does not have a demonstrated reachable path satisfying the "unprivileged, unauthenticated" attacker constraints of this audit. Exploiting it would require an authenticated Shipit user with deploy trigger permission on the stack, i.e., a privileged actor already trusted to run deploys and choose `env` values — at which point the missing `select` check is a reduction of operator-configured guardrails, not a boundary an outside attacker can cross.

### Impact Explanation
If exploited by an authenticated user who already has permission to trigger deploys on a stack, the missing `select` validation lets them bypass an operator's intended value whitelist for an env var (e.g. `ENVIRONMENT: [production, canary]`), and if that variable is later interpolated into a shell command via `Command#interpolate_environment_variables`/`Shellwords`, unexpected values could reach the deploy host's command execution. This matches the Critical RCE category *in principle*, but the actor able to trigger it must already be a stack deploy operator — not the internet-facing/unauthenticated attacker defined in scope.

### Likelihood Explanation
Requires an authenticated Shipit user with deploy permission on the target stack and the stack's `shipit.yml` to declare a `select`-constrained env var. Under the stated threat model (unprivileged, no Shipit session, no API token, no team membership), no reachable path from an anonymous HTTP request or an attacker-controlled webhook payload was found that supplies `env` values to `permit`.

### Recommendation
Not applicable under the stated attacker model since no unauthenticated/unprivileged reachable path exists. (For completeness, as a defense-in-depth improvement even for authenticated deploy triggers, `EnvironmentVariables#sanitize_env_vars` should validate `@env[vd.name]` against `vd.select` when `vd.select.present?` and raise `NotPermitted` for out-of-set values.)

### Proof of Concept
Not applicable — no minitest reproduction satisfies the required unprivileged/unauthenticated attacker precondition, since the only identified caller of `permit` with externally-supplied `env` (`DeploysController#create`) is gated behind stack-scoped, session-authenticated strong parameters (`deploy_params`) filtered by variable name via Rails `permit`, and no unauthenticated webhook or public endpoint was found that forwards arbitrary `env` values into `Stack#trigger_deploy` → `EnvironmentVariables#permit`.

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
