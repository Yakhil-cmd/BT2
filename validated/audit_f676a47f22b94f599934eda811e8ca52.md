### Title
Cross-tenant webhook forgery: authenticated organization is never bound to the acted-upon repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook against using `repository.owner.login` (falling back to `organization.login`) taken from the attacker-supplied JSON body, while every event handler that subsequently runs operates on `repository.full_name`, a different field of the same body that is never cross-checked against the field used for authentication.

### Finding Description
Shipit is multi-tenant: each configured GitHub organization has its own independent `webhook_secret` (see `config/secrets.development.shopify.yml` listing `somegithuborg`/`someothergithuborg`, each with its own `webhook_secret`) [1](#0-0) .

The controller picks which organization's secret to verify against like this: [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` then HMACs the raw payload with the secret selected purely from that `repository_owner`/`organization.login` value: [4](#0-3) 

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire* body to handlers, none of which re-derive or validate the owner used for auth. Every handler resolves the target stack(s) from a different field, `repository.full_name`: [5](#0-4) 

`PushHandler`, for example, uses that `stacks` scope to trigger a sync job for whatever repository `repository.full_name` names, using attacker-supplied `ref`/`after` values: [6](#0-5) 

Because HMAC verification only depends on which org name appears in `repository.owner.login`/`organization.login`, and no code checks that this owner actually matches the owner embedded in `repository.full_name`, an attacker who legitimately administers **one** onboarded GitHub organization (and therefore genuinely knows that organization's `webhook_secret`) can build a raw POST body where:
- `repository.owner.login` = `"attacker-org"` (their own org, used only to pick the verification key)
- `repository.full_name` = `"victim-org/victim-repo"` (an unrelated, unowned stack hosted on the same Shipit instance)

then sign the whole body with their own org's `webhook_secret`. `verify_signature` succeeds (it only ever checks the secret belonging to `attacker-org`), and the handler layer then acts on `victim-org/victim-repo` entirely on the attacker's terms.

This is exactly the binding break described in scope: **an organization that authenticated ≠ the repository that is written**. The signature proves "this came from someone who knows attacker-org's secret," but the code executes as if it were an authenticated webhook for `victim-org/victim-repo`.

### Impact Explanation
Using `PushHandler`, the attacker can force `GithubSyncJob` to run against any stack tracked by the Shipit instance, with an attacker-chosen `expected_head_sha` [7](#0-6) , injecting `Commit` rows and mutating the accessibility state (`mark_as_accessible!`/`mark_as_inaccessible!`) of a stack the attacker does not own — a cross-repository write into another tenant's Shipit data using only the attacker's own tenant credentials. The same authentication-binding gap applies uniformly to every other registered handler (`status`, `pull_request`, `membership`, `check_suite`), since none of them re-validate the owner used in `verify_signature` against `repository.full_name` used for dispatch, so the same forgery technique lets an attacker inject arbitrary, falsely-"authenticated" webhook events (e.g. forged commit statuses, forged PR events) against repositories/stacks belonging to other organizations hosted on the same multi-tenant Shipit deployment.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate administrator of at least one GitHub organization already onboarded to the shared Shipit instance (i.e., they know their own org's `webhook_secret`, which is a normal, expected credential for that org — not privileged access to the victim org, Shipit itself, or any GitHub App private key). Crafting the JSON body with mismatched `repository.owner.login` vs `repository.full_name` and computing an HMAC-SHA1 over it is trivial; there is no server-side check preventing the mismatch.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), require that the organization/owner used to select the verification secret is identical to the owner embedded in `repository.full_name` (and in `organization.login` when present), rejecting the webhook with `422` on any mismatch, so a valid signature for one organization can never be replayed to act on another organization's repositories/stacks.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, which is configured in Shipit with `webhook_secret: S`.
2. Attacker builds a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...attacker-chosen-sha",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC-SHA1(S, body)` and sends `POST /webhooks` with header `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"` (`app/controllers/shipit/webhooks_controller.rb:59-62`), fetches `Shipit.github(organization: "attacker-org")`, and verifies successfully because the attacker used that org's own real secret (`lib/shipit/github_app.rb:76-83`).
5. `Shipit::Webhooks.for_event("push")` dispatches the full body to `PushHandler`, which resolves stacks via `repository.full_name` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for the victim's stack with the attacker-chosen `expected_head_sha` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), even though the request was never signed by `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
