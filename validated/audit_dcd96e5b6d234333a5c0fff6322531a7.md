### Title
Cross-Stack Authorization Bypass in CCMenu API Endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController` overrides the `stack` lookup method to bypass the stack-scoping enforcement that `Api::BaseController` applies to every other API client. As a result, an `ApiClient` token that is bound to a single stack (`stack_id`) — and is therefore only supposed to read that one stack's data — can be used to read the deploy/task status of **any** stack in the installation by simply supplying a different `stack_id` in the request path.

### Finding Description
`Api::BaseController` implements a scoping model for `ApiClient` tokens: [1](#0-0) 

`stacks` restricts the queryable relation to the single stack the client is bound to (`current_api_client.stack_id?`), and `stack` (used by most API controllers, e.g. `Api::CommitsController`, `Api::DeploysController`, `Api::TasksController`) resolves the requested stack **through that scoped relation** — so a request for a `stack_id` outside the client's bound stack raises `RecordNotFound` and is rejected.

`Api::CCMenuController` does not use this inherited `stack` method. It defines its own: [2](#0-1) 

`stack` here calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` class, completely bypassing the `stacks` scoping helper (and thus the `current_api_client.stack_id` binding). The only check that remains is the permission-scope check: [3](#0-2) 

`require_permission :read, :stack` only verifies that the token carries the `read:stack` permission string — it never verifies that the specific stack referenced in `params[:stack_id]` is the stack the token was scoped to.

This is the same class of bug as the report's `previousPrices` issue: a security-relevant binding (`ApiClient#stack_id`, the "authorized" stack) is established once (at client creation / in the base scoping logic) but is never consulted at the point where the actual resource access happens (`CCMenuController#stack`). The binding that should be enforced —

```
stack the token authorizes == stack the token touches
```

— is broken specifically in this controller, while it holds everywhere else in the API namespace.

### Impact Explanation
Any holder of a valid `ApiClient` token with `read:stack` permission — even one deliberately scoped to a single, low-sensitivity stack (e.g., a CCMenu client created via `CCMenuUrlController` for one project) — can enumerate `stack_id` values and retrieve the CI/CD status (`running?`, `ended_at`, latest deploy/rollback state) of every other stack managed by the Shipit instance, including stacks the token was never meant to access. This is an unauthenticated-in-effect cross-tenant read of stack/task state, matching the High-impact category "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state, task streams or deploy output" since it defeats the per-client stack scoping that the rest of the API enforces.

### Likelihood Explanation
Exploitation requires only possession of any valid, low-privilege `ApiClient` token that has `read:stack` permission (such tokens are routinely generated and distributed as CCMenu URLs via `CCMenuUrlController#fetch`, embedded in query strings that can leak through logs, browser history, or referrers). No GitHub credentials, session, or elevated permissions are needed — only substituting a different `stack_id` in an otherwise legitimate, authenticated request. This makes the likelihood high once any such token is obtained.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack through the inherited, scoped `stacks` relation instead of the unscoped `Stack` model, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

removing the private override entirely so the base controller's scoping logic (`current_api_client.stack_id?`) is enforced consistently.

### Proof of Concept
1. Obtain a CCMenu `ApiClient` token scoped to Stack A, e.g. via `GET /stacks/:stack_a/ccmenu_url`, which returns a URL like `.../api/stacks/stack_a/ccmenu.xml?token=<token>` (created by `CCMenuUrlController#client`, an `ApiClient` scoped to a specific `stack`).
2. Send `GET /api/stacks/<stack_a>/ccmenu.xml?token=<token>` — succeeds as intended.
3. Send `GET /api/stacks/<stack_b>/ccmenu.xml?token=<token>` for an arbitrary, unrelated Stack B.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than `stacks.from_param!(params[:stack_id])`, the `current_api_client.stack_id` binding (Stack A) is never checked, and the request returns Stack B's deploy/rollback status — confirming the cross-stack authorization bypass.
