### Title
API-client stack scope is ignored by the CCMenu endpoint, allowing a token issued for one stack to read any stack's deploy state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces per-client stack scoping through the `stacks`/`stack` helper pair, but `Shipit::Api::CCMenuController` overrides `stack` to bypass that scoping entirely, binding the authorization check (`read:stack` permission) to an attacker-controlled `params[:stack_id]` instead of the stack the authenticated `ApiClient` was actually scoped/issued for.

### Finding Description
The base API controller correctly binds visibility to the client's own `stack_id`: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a stack, and `stack` resolves `params[:stack_id]` only within that restricted scope. This is the binding: "stack a token authorizes == stack it touches."

`CCMenuController`, however, defines its own `stack` method that ignores `stacks` and the client's scope completely: [2](#0-1) 

It only declares `require_permission :read, :stack` (a permission-string check, `ApiClient#check_permissions!`) with no stack-identity check: [3](#0-2) 

Because `stack` resolves via `Stack.from_param!(params[:stack_id])` directly on the global `Stack` relation, any `ApiClient` holding `read:stack` — whether globally scoped or scoped to a *specific* stack via `belongs_to :stack, optional: true` — can fetch and render deploy status for **any** stack by supplying a different `stack_id` in the query string.

This is compounded by how these tokens are minted. `CCMenuUrlController#client` finds-or-creates a single, stack-unscoped `ApiClient` per user (`find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, no `stack:` attribute set) with permission `read:stack`, then embeds its token in a URL for one particular stack: [4](#0-3) 

The token the user is handed (and may paste into an external, less-trusted CI status widget/CCMenu client) is not bound to the stack it was generated for; it authorizes reading `read:stack` in the abstract, and `CCMenuController#stack` happily substitutes any `stack_id` the requester supplies. Even for the general-purpose, explicitly stack-scoped `ApiClient` records used elsewhere in the API (`belongs_to :stack, optional: true`, as exercised by the `here_come_the_walrus` fixture scoped to a single stack for `index`/`show`), the same override means the CCMenu endpoint alone does not respect that scoping, unlike every other `Api::BaseController` subclass.

### Impact Explanation
An attacker in possession of any `read:stack`-permissioned CCMenu token (e.g., leaked from a CI dashboard/IRC bot/build-status widget where such tokens are commonly embedded in plaintext URLs) can enumerate and read deploy/task status (`stack.deploys_and_rollbacks.last`, revision info rendered by the CCMenu XML view) for every stack in the Shipit instance, not just the one the token was minted for. This is an unauthorized read of stack/task state across repository boundaries, matching the High-severity bucket for "unauthenticated/unauthorized read of stack state, task streams or deploy output."

### Likelihood Explanation
CCMenu tokens are designed to be embedded in third-party tooling (CI dashboards, status trays) via a bare query-string token, exactly the kind of low-trust distribution channel where leakage is likely. Exploitation requires only a valid CCMenu token (which the requesting user already possesses for their own stack) and knowledge/enumeration of another stack's numeric/slug identifier — no privileged account, no signature forgery, and no session is needed beyond the token itself.

### Recommendation
Make `Api::CCMenuController#stack` resolve through the scoped `stacks` helper from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, and/or scope the `ApiClient` created in `CCMenuUrlController#client` to the specific stack (`stack:` attribute) rather than sharing one global per-user client across all stacks.

### Proof of Concept
1. User Alice visits Stack A's settings page and clicks "CCMenu URL," receiving `.../api/stacks/A/ccmenu.xml?token=<sig(client_id)>`, where `client_id` refers to a globally-scoped `ApiClient` with only `permissions: ["read:stack"]`. [4](#0-3) 
2. Alice (or anyone who obtains this token, e.g., from a public CI dashboard) requests `.../api/stacks/B/ccmenu.xml?token=<same token>` for Stack B, which she has no declared access to.
3. `authenticate_api_client` authenticates the token successfully; `require_permission :read, :stack` passes because the permission string is present; `stack` resolves `Stack.from_param!('B')` on the unscoped `Stack` relation. [5](#0-4) 
4. The response renders Stack B's latest deploy/rollback status, disclosing deploy state Alice was never authorized to view.
