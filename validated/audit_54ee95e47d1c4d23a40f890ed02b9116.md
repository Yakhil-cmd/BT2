### Title
Assertion-style `throw Error("no src coin amount")` in private indivisible-asset payment validation crashes the node - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` contains hard `throw Error(...)` assertions that are meant to catch "impossible" internal-consistency violations when validating a **private, fixed-denomination (indivisible) asset transfer**. These assertions are reachable with attacker-controlled data supplied by a private-payment counterparty, because the `src_coin` object they check is built directly from the *previous* element of an attacker-supplied private-payment chain **before** that previous element's payload has been cross-checked against the actual on-chain payload hash. A crafted chain can therefore trigger an uncaught synchronous `throw` deep inside a DB-callback, which is not caught anywhere and is turned into a fatal `uncaughtException` that intentionally crashes the whole node process — the same bug class as CVE-2021-20217 (crafted request → assertion failure → DoS).

### Finding Description
For fixed-denomination private assets, `validatePrivatePayment()` builds `objValidationState.src_coin` straight from the **previous chain element supplied by the peer** (`objPrevPrivateElement`), without validating that element's `amount` value yet: [1](#0-0) 

Specifically, `prev_hidden_output = objPrevPrivateElement.payload.outputs[input.output_index]` is only checked for existence (`if (!prev_hidden_output) return callbacks.ifError(...)`), not for the amount being a valid positive integer, and its `.amount` is copied verbatim into `src_coin.amount`.

The chain is processed element-by-element in order by `parsePrivatePaymentChain`: [2](#0-1) 
When processing `arrPrivateElements[i]`, its `prevElement` is `arrPrivateElements[i+1]` — but that next element's own `payload_hash` (the check that ties it back to the genuine on-chain unit) is only verified when it becomes the "current" element on the *following* iteration, inside `initPrivatePaymentValidationState`: [3](#0-2) 
i.e. at the moment `src_coin` is built for element `i`, element `i+1`'s `amount` has not been authenticated against the ledger at all — it is fully attacker-controlled JSON sent over the wire in the `private_payment` message.

That unauthenticated `amount` later reaches this assertion in `validatePaymentInputsAndOutputs()`: [4](#0-3) 
If the peer sets the amount of the referenced previous output to `0`, a negative number, a float, or a non-numeric value, `isPositiveInteger(src_coin.amount)` fails and the code executes `throw Error("no src coin amount")` — a synchronous `throw` instead of routing the error through the `cb()`/`callbacks.ifError()` chain used everywhere else in this function.

This validation path is entered by `handleOnlinePrivatePayment` when a device/peer sends the recipient a `private_payment` message for a known unit: [5](#0-4) 
via `private_payment.js` → `indivisible_asset.js` `validateAndSavePrivatePaymentChain` → `parsePrivatePaymentChain` → `validatePrivatePayment`.

Because the throw fires inside a `conn.query` callback (asynchronous, detached from any enclosing `try/catch`), there is no handler on the call stack to catch it. It propagates as a Node.js `uncaughtException`, and ocore's global handler deliberately re-throws to crash the process "to avoid ending up in an inconsistent state": [6](#0-5) 

### Impact Explanation
Any private-payment counterparty (a wallet/device that a victim has ever transacted a private, fixed-denomination asset with, or is willing to accept a payment notification from) can send a single crafted `private_payment` chat message that crashes the victim's full node process. This is a remotely triggerable denial of service on wallets/hubs that process private payments (e.g., blackbytes-style indivisible private assets), matching the "no impact except availability" profile of CVE-2021-20217, but reachable purely through the wallet-message protocol rather than any network/p2p sync path.

### Likelihood Explanation
High: the attacker only needs to be an existing or plausible private-payment counterparty (no privileged position, no key compromise) and can construct the `arrPrivateElements` array and its `payload.outputs[i].amount` field arbitrarily, since it is not validated against on-chain data at the point it is consumed to build `src_coin`.

### Recommendation
Replace the `throw Error("no src_coin")/"no src_output"/"no denomination in src coin"/"no src coin amount"` assertions in `validatePaymentInputsAndOutputs()` (`validation.js:2415-2424`) with normal `cb("...")` error returns, consistent with the rest of the function. Additionally, validate `prev_hidden_output.amount` (and other fields copied into `src_coin`) for correct type/positivity in `validatePrivatePayment()` (`indivisible_asset.js`) immediately when reading `objPrevPrivateElement`, before trusting it, rather than deferring authentication of that element to a later loop iteration.

### Proof of Concept
1. Attacker and victim share a device pairing and have previously (or nominally) transacted a private, fixed-denomination custom asset.
2. Attacker crafts a `private_payment` chain (`arrPrivateElements`) with two elements: element `[0]` is a normal-looking "transfer" referencing output_index `k` of element `[1]`; element `[1]`'s `payload.outputs[k].amount` is set to `0` (or a negative number).
3. Attacker sends this chain to the victim as a device message handled by `handleOnlinePrivatePayment` (`network.js:2376`).
4. `parsePrivatePaymentChain` processes element `[0]` first, calling `validatePrivatePayment(conn, element[0], element[1], ...)`. `src_coin.amount` is set to the tampered `0` from element `[1]` (`indivisible_asset.js:135-139`) — element `[1]`'s payload hash has not yet been checked.
5. `validation.validatePayment` → `validatePaymentInputsAndOutputs` hits the "transfer" branch for a private fixed-denomination asset and executes `if (!isPositiveInteger(src_coin.amount)) throw Error("no src coin amount");` (`validation.js:2423-2424`).
6. The uncaught throw bubbles up through the async DB callback, is caught by `process.on('uncaughtException')`, which re-throws and crashes the victim's node (`network.js:4530-4543`).
