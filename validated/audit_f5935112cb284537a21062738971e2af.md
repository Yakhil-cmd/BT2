### Title
Cross-repository CI status forgery via organization-scoped webhook authentication combined with sha-only commit lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects *which organization's* `webhook_secret` to validate a webhook against using an attacker-influenced field of the (not-yet-verified) payload, and then only proves that the payload came from *some* organization configured in Shipit. `Shipit::Webhooks::Handlers::StatusHandler#process`, unlike other handlers, never re-checks that the commit it mutates belongs to a repository owned by that authenticated organization — it looks the commit up by `sha` alone, globally, across every stack in the installation.

### Finding Description
The webhook signature check picks the `GitHubApp`/`webhook_secret` to verify against from `repository_owner`, itself derived from the untrusted payload body before verification: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` proves only that the raw body was HMAC-signed with *that organization's* secret (and, per the documented multi-org setup, `webhook_secret` is explicitly optional/nilable, in which case it returns `true` unconditionally): [3](#0-2) [4](#0-3) 

This establishes a binding: *organization O authenticated* == *webhook_secret(O) matches request body*. However, `StatusHandler`, which processes GitHub `status` events, never checks that the commit it updates belongs to a repository owned by `O`. It resolves the target purely by commit `sha`, globally across the whole database: [5](#0-4) 

Contrast this with the base `Handler` class, which provides a `stacks`/`repository_name` scoping mechanism keyed off `payload.dig('repository', 'full_name')` that other handlers (e.g. `PushHandler`) correctly use to scope their side effects to the repository named in the payload: [6](#0-5) [7](#0-6) 

`StatusHandler` never calls `stacks`/`repository_name` at all — it is the one handler where "the organization that authenticated" (via `repository_owner` used to pick the webhook secret) and "the repository that is written" (any stack anywhere whose `Commit.sha` happens to match) are never bound together, breaking the equality the rules describe: `organization_authenticated == repository_written`.

### Impact Explanation
Because `Commit.where(sha: params.sha)` is unscoped by repository, a correctly-signed `status` webhook for organization O's app installation can write a status (including `state: "success"`) onto *any* `Commit` row in the Shipit database that happens to share that sha, regardless of which organization/repository that commit's stack belongs to. Commit shas are not organization-secret; they are widely visible (mirrors, forks, template repositories, vendored/shared monorepo commits, or simply an attacker with any push/webhook-triggering access to one org-A repository that shares history with an org-B repository tracked by a different Shipit stack). If a targeted stack's `shipit.yml` declares `ci.require`, a forged "success" status can satisfy the CI gate for a commit the attacker never had CI/merge rights over, enabling an **unauthorized deploy** (e.g. via `continuous_deployment`) on a stack outside the authenticating organization's control. This matches the Critical "unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitation requires the attacker to be able to trigger a legitimately-signed `status` webhook for some organization configured in the target Shipit instance (e.g. controlling/triggering CI on any repository under an org whose GitHub App is installed, or exploiting the documented optional/nil `webhook_secret` configuration) and to know or guess a `sha` that also exists as a `Commit` under a different stack/organization. This is a narrower precondition than a full authentication bypass, but the binding failure is concrete and reachable purely through the public `/webhooks` endpoint with no repository write access or Shipit session required, matching the required "unprivileged-attacker" bar.

### Recommendation
Scope `StatusHandler#process` (and any other handler that does not currently use `Handler#stacks`/`repository_name`) to the repository named in the payload, e.g. restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, so the organization proven by the signature check and the repository whose commit is mutated are always the same entity.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App/`webhook_secret` (per the documented multi-org config), and separate `Stack`s tracking repositories in each org.
2. A commit with sha `S` exists in a `Commit` row belonging to a stack under `OrgB` (e.g. because `OrgB`'s repo forked/mirrors a commit also present in `OrgA`'s repo, or shares a vendored history).
3. Attacker triggers (or is otherwise able to produce) a validly HMAC-signed `status` webhook for `OrgA` (whose secret they can compute/trigger through normal GitHub status-check integration on an `OrgA` repo they control) with body:
   `{"sha": "S", "state": "success", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/some-repo"}}`
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates the HMAC against `OrgA`'s secret — which succeeds because the attacker legitimately produced this signature for `OrgA`.
5. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the `OrgB` commit (unscoped by repository), and calls `commit.create_status_from_github!(params)`, writing a forged `"success"` status onto `OrgB`'s commit — satisfying `ci.require` for a stack the attacker has no access to, in an organization whose webhook secret they never possessed.

Note: I was not able to inspect `Commit#create_status_from_github!` directly (index truncation), so the exact downstream field handling of that status write could not be fully verified in-repo; the unscoped `Commit.where(sha:)` lookup itself is confirmed directly from `status_handler.rb`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
