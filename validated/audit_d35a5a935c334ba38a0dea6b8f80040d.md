Confirmed: `Shipit::Api::CCMenuController` (`app/controllers/shipit/api/ccmenu_controller.rb`) overrides the base `stack` accessor to bypass the per-token stack scoping that every other API controller relies on.

### Title
Stack-scoped API token can read any stack's build status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` tokens can be scoped to a single `stack_id`, which `Shipit::Api::BaseController#stacks`/`#stack` enforces by intersecting the requested stack with `Stack.where(id: current_api_client.stack_id)` [1](#0-0)  . `Shipit::Api::CCMenuController` overrides `stack` to instead call `Stack.from_param!(params[:stack_id])` directly, entirely skipping the `stacks` scoping method [2](#0-1)  .

### Finding Description
The binding the engine intends to enforce is: `token.authorised_stack == stack.acted_on`. `BaseController#stack` implements this by first narrowing to `stacks` (which is `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped) before resolving the param [1](#0-0)  . Every other API controller relies on this inherited `stack`/`stacks` method.

`CCMenuController`, however, defines its own private `stack` method that resolves `params[:stack_id]` against the full `Stack` relation, ignoring `current_api_client.stack_id` entirely [3](#0-2)  . The only authorization check that remains is `require_permission :read, :stack`, which validates the *permission bit* on the token (`read:stack`) but not the *stack scope* [4](#0-3)  , [5](#0-4)  .

This is precisely the class of bug hinted by the report: a value (here, `stack_id` scope) that is meant to bound what an actor can act on is silently not enforced on one code path, while it is enforced everywhere else — an "owner may claim 99.9%" analog where a narrowly-scoped credential ends up acting outside its intended boundary. Any stack-scoped token (for example, the read-only, single-stack tokens auto-created by `CCMenuUrlController#client` for embedding a CI status badge, `permissions: %w[read:stack]`, scoped to one stack [6](#0-5)  ) can be replayed against `/api/*/ccmenu/:stack_id` with an arbitrary `stack_id` to read another stack's latest deploy/rollback status, lock state, and deploy metadata, which `CCMenuController#show` renders as XML [7](#0-6)  .

### Impact Explanation
This matches the High-severity bucket defined in scope: "unauthenticated read of stack state, task streams or deploy output" via escalation past the token's authorized scope — a token meant to read one stack's status can read the status of every stack in the installation (deploy/rollback status, lock reason, timestamps), regardless of which stack it was issued for.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped tokens (the built-in CCMenu flow does this automatically for any logged-in user via `CCMenuUrlController`), since the attacker only needs any single valid stack-scoped token (which they can legitimately obtain for a stack they do have access to) and can then enumerate other `stack_id` values against the same endpoint without further authorization checks.

### Recommendation
Have `CCMenuController#stack` reuse the inherited, scope-aware `stacks`/`stack` resolution from `BaseController` (i.e., resolve `params[:stack_id]` against `stacks`, not `Stack` directly), so that stack-scoped tokens cannot be used to query stacks outside their authorized `stack_id`.

### Proof of Concept
1. As a legitimate user with access to `stack_A`, visit any page that triggers `CCMenuUrlController#fetch` for `stack_A`; this creates/reuses an `ApiClient` scoped to `stack_A` with `permissions: ['read:stack']` and returns a CCMenu URL containing its `authentication_token` [8](#0-7)  .
2. Take that token and issue `GET /api/<stack_A_id>/ccmenu` replaced with an arbitrary `stack_id` belonging to `stack_B` (a stack the attacker was never authorized for): `GET /api/<stack_B_id>/ccmenu?token=<token>`.
3. `authenticate_api_client` on `CCMenuController` accepts the token via `ApiClient.authenticate(params[:token])` [9](#0-8)  ; `require_permission :read, :stack` passes because the token has `read:stack` [5](#0-4)  ; `stack` resolves `stack_B` directly via `Stack.from_param!` without checking `current_api_client.stack_id` [3](#0-2)  .
4. The response renders `stack_B`'s latest deploy/rollback status and lock state, which the token was never authorized to view.
