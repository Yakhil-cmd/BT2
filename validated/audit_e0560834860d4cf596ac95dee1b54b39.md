### Title
Webhook signature is verified against the payload's `repository.owner`/`organization` login, but event handlers act on the `repository.full_name` (or, for statuses, on no repository scope at all) — allowing a legitimately onboarded organization to forge webhooks that mutate another organization's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-tenant Shipit deployment (the documented "Using Multiple Github Applications" setup, where each GitHub organization has its own GitHub App and its own `webhook_secret`), `WebhooksController#verify_signature` selects which secret to HMAC-verify the incoming webhook against using `repository_owner`, derived from the payload itself (`repository.owner.login`, falling back to `organization.login`). Once verified, the raw, attacker-supplied `params` hash is passed unmodified to the registered handlers, which independently determine which `Repository`/`Stack`/`Commit` to mutate — using `repository.full_name` (`Handler#repository_name`) for push/check-suite events, and using no repository scope whatsoever for status events. Because the field used to pick the verification key is never bound to the field(s) used to select the mutated resource, an organization that legitimately owns one GitHub App installation (and therefore knows its own `webhook_secret`) can sign a payload with its own secret while setting `repository.full_name` (or just `sha`, for status events) to reference a completely different organization's repository/commit tracked by the same Shipit instance.

### Finding Description
- `verify_signature` computes the verification key from attacker-controlled JSON:
`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

- After a `head(422) unless verified` check that does **not halt the filter chain** (no `return`/`throw` — it just sets the response status), `create` still dispatches the full payload to all registered handlers for the event:
`app/controllers/shipit/webhooks_controller.rb:10-15` [3](#0-2) 

- Handlers resolve the target `Repository`/`Stack` using `repository.full_name`, a field that is not part of what was checked to select the verification secret:
`app/models/shipit/webhooks/handlers/handler.rb:32-38` [4](#0-3) 

- `StatusHandler` is worse: it never scopes by repository at all, it matches any `Commit` in the entire database by `sha` and writes a GitHub status onto it:
`app/models/shipit/webhooks/handlers/status_handler.rb:20-24` [5](#0-4) 

The binding that should hold is: `organization authenticated by verify_webhook_signature == organization/repository whose state the handler mutates`. This equality is never enforced. Before the attack: OrgA's webhook secret can only affect OrgA's own stacks. After a forged request with `repository.owner.login = "OrgA"` (used only for signature lookup) and `repository.full_name = "OrgB/target"` / `sha = "<OrgB commit sha>"` (used by the handler), OrgA's credential mutates OrgB's tracked stack/commit state.

### Impact Explanation
This crosses the required credential/repository binding ("an organization that authenticated versus the repository that is written") for a High-severity outcome:
- Via `StatusHandler`, any onboarded organization can forge a passing (or failing) CI status for an arbitrary commit sha belonging to a different organization's stack. Since Shipit gates deploys and the merge queue on required commit statuses (`ci.require`), this enables **unauthorized deploy/merge** unlocking on a repository the attacker organization does not own or have write access to — this satisfies the "unauthorized deploy, rollback or merge" Critical impact bucket.
- Via `PushHandler`/`CheckSuiteHandler`, an attacker organization can trigger `GithubSyncJob`/check-run refresh cycles against another organization's stack, causing unsolicited GitHub-side actions (and, when combined with the status abuse and continuous delivery configuration, deploy triggering) using only credentials belonging to the attacker's own org.

### Likelihood Explanation
Exploitability requires only that the attacker organization is one of several legitimately configured GitHub App installations in a multi-org Shipit deployment (a documented, supported configuration) — no session, `ApiClient` token, or the victim's `webhook_secret`/private key is required. Any organization admin who owns their own App installation's webhook secret can craft this payload directly against the public `/webhooks` endpoint.

### Recommendation
Bind the authenticated organization to the resource the handler is allowed to touch: after `verify_webhook_signature` succeeds for `repository_owner`, require handlers to only operate on `Repository` records whose owner matches the exact `repository_owner`/`organization.login` used for verification (e.g., pass the verified owner into `Handler.call` and assert `repository_name.split('/').first == verified_owner` before any lookup, and add repository scoping to `StatusHandler`'s `Commit` lookup instead of matching by bare `sha`). Additionally, make `verify_signature` actually halt the filter chain (`head(422) and return`) instead of merely setting the response status while allowing `create` to still execute.

### Proof of Concept
1. Shipit is configured with two GitHub Apps, one per org, per the documented multi-org setup (`test/dummy/config/secrets_double_github_app.yml`), tracking stacks for `OrgA/repoA` and `OrgB/repoB`.
2. Attacker controls `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/repoA"},
  "sha": "<sha of a commit tracked under OrgB/repoB's stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
signed with `OrgA`'s webhook secret via `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and successfully verifies the signature using OrgA's own secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `OrgB/repoB` commit regardless of the `repository` field in the payload — and calls `commit.create_status_from_github!(params)`, marking OrgB's commit as CI-passing.
6. If `OrgB/repoB`'s stack has continuous delivery enabled and requires that status context, this can unlock an unauthorized deploy on `OrgB/repoB` using only `OrgA`'s credentials.
