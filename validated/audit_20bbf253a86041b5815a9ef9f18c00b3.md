### Title
Vote account withdraw authority can spike `commission` mid-epoch and capture stakers' entire inflation reward for that epoch - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
This is a direct analog of the `BoostAggregator` bug: an account authority that unstaked/unprivileged depositors must trust can unilaterally raise a reward-split "fee" parameter and redirect the depositors' yield to itself. In Agave, the analogous authority is the vote account's `authorized_withdrawer`, the "fee" parameter is the vote account `commission`, and the unprivileged depositors are the stake accounts delegated to that vote account.

### Finding Description
`VoteInstruction::UpdateCommission` lets the `authorized_withdrawer` unilaterally set the vote account's commission up to 100 (i.e., 100% via the legacy percentage scale), gated only by `verify_authorized_signer` — no consent or notice to delegators is required: [1](#0-0) 

The only guardrail against a "last-minute rug" is `enforce_commission_update_rule`, which disallows commission *increases* in the second half of an epoch, but only when the `delay_commission_updates` feature is not active, and it imposes no restriction at all in the first half of an epoch: [2](#0-1) 

At reward-calculation time, `redeem_delegation_rewards` decides whether to use a delayed (snapshot) commission value or the vote account's *current* commission, based on the `delay_commission_updates` feature flag: [3](#0-2) 

When `delay_commission_updates` is not active for the relevant epoch, the commission used to split rewards between the validator (commission collector) and the stake delegators is read directly from the vote account's live state at distribution time rather than from a value snapshotted before the epoch began — the same class of flaw described in the `BoostAggregator` report where the fee used for payout is read at payout time instead of being locked in when the user "deposited."

The separate `UpdateCommissionBps` instruction (SIMD-0291) is documented to explicitly have "No commission update rule" at the instruction level: [4](#0-3) [5](#0-4) 

### Impact Explanation
If a vote account's withdraw authority increases `commission` (or `inflation_rewards_commission_bps`) to its maximum near/at the start of an epoch (or at any point, for the bps path) while `delay_commission_updates` is not effectively protecting that epoch's calculation, every stake account delegated to that vote account loses its entire inflation reward for that epoch to the commission collector — a concrete misattribution/theft of lamports analogous to the `BoostAggregator` `protocolFee` exploit, except here the victims are stake-account owners (delegators), an unprivileged class relative to the vote account withdraw authority.

### Likelihood Explanation
Exploitability is conditioned on the state of the `delay_commission_updates` feature activation for the epoch(s) in question and on the legacy first-half-of-epoch commission-increase window, which the current code explicitly still permits: [6](#0-5) 

I could not fully verify from the index whether `delay_commission_updates` and `commission_rate_in_basis_points` are activated cluster-wide on mainnet-beta today (their activation status is external cluster state, not code); the feature-set definitions exist in `feature-set/src/lib.rs` but I was unable to retrieve the exact file contents to confirm current activation status due to result truncation.

### Recommendation
Ensure `delay_commission_updates` (and `commission_rate_in_basis_points`) are unconditionally enforced (not feature-gated / never disabled) so that the commission used for an epoch's reward split is always locked in at least one full epoch ahead, closing the window where `update_commission`/`update_commission_bps` can be used to reallocate an already-earned epoch's rewards. Continue applying the existing snapshot-based `snapshot_epoch_vote_accounts` lookback ( [7](#0-6) ) as the single source of truth regardless of feature-gate state.

### Proof of Concept
1. Delegate stake to vote account `V` with `commission = 0`.
2. Near the start of an epoch where `delay_commission_updates` is not protecting that epoch's calculation, `V`'s `authorized_withdrawer` submits `VoteInstruction::UpdateCommission(100)` — allowed by `update_commission` since it's in the first half of the epoch and only requires the withdrawer's signature ( [8](#0-7) ).
3. At epoch-end reward calculation, `redeem_delegation_rewards` reads the *current* (100%) commission because `delay_commission_updates` did not force use of the pre-epoch snapshot ( [9](#0-8) ).
4. All stake delegated to `V` receives zero reward for the epoch; the full inflation reward is paid to the commission account, mirroring the `BoostAggregator.setProtocolFee(10_000)` theft pattern.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;
