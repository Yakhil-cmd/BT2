### Title
CCMenu API tokens grant unauthenticated cross-stack read access instead of being scoped to the stack they were issued for - (File: `app/controllers/shipit/ccmenu_url_controller.rb`)

### Summary
`CCMenuUrlController#client` mints a single, reusable `ApiClient` per Shipit user that is never bound to any particular `Stack`, yet `Api::CCMenuController` — an endpoint that is reachable with **no Shipit session at all**, purely via a `token` query parameter — only checks that the token carries the `read:stack` permission, never that the token's authorized stack matches the stack path segment being requested. The equality the design implies is `token.stack == requested_stack_id`; the code never enforces it, so a token minted for stack A ends up valid for every stack in the installation.

### Finding Description
When a user opens the CCMenu settings for a stack, `CCMenuUrlController#fetch` builds a URL containing an `ApiClient` token: [1](#0-0) 

The `client` method does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — note that `stack:` is never passed, even though `ApiClient` explicitly supports a `belongs_to :stack, optional: true` association meant for this exact purpose: [2](#0-1) 

Because `stack_id` is left `nil`, the intended per-stack scoping mechanism in `Api::BaseController#stacks` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) would resolve to *every* stack even if it were consulted: [3](#0-2) 

`Api::CCMenuController` doesn't even go through that scoping helper — it overrides `#stack` to look up `Stack.from_param!(params[:stack_id])` directly, and authenticates solely via the raw token, bypassing the normal Basic-Auth/session-based `authenticate_api_client`: [4](#0-3) 

The only authorization check performed is `require_permission :read, :stack`, which merely verifies the client's `permissions` array contains `read:stack` — it never compares the client's (non-existent) stack scope to the `stack_id` in the request: [5](#0-4) 

Also note the same single client/token is reused for **every** stack a given creator ever fetches a CCMenu URL for (`find_or_create_by!(creator:, name:)` has no `stack` key), reinforcing that the token was never designed to carry per-stack scope in practice, and the missing check in `CCMenuController#stack` means it works for stacks the creator never even visited.

### Impact Explanation
This breaks the "stack a token authorises versus a stack it touches" binding: a token generated to expose one stack's CI badge to an external, unauthenticated CCMenu widget (`GET /api/stacks/*stack_id/ccmenu?token=...`, which requires no `X-Shipit-User`, no Basic-Auth secret, no Shipit session) is valid to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, etc., see `test/controllers/api/ccmenu_controller_test.rb`) for **any stack in the entire installation**, simply by substituting a different `stack_id` in the path. Any party who obtains one such URL/token (which by design is meant to be embedded in third-party, non-Shipit-authenticated CI dashboards) gains unauthenticated read access to the state of every stack, matching the "High — unauthenticated read of stack state ... or deploy output" impact bucket.

### Likelihood Explanation
The precondition — a Shipit user fetching a CCMenu URL for at least one stack they can see — is routine, expected usage of this exact feature (settings page has a "Fetch URL" button for CCMenu), not a privilege abuse. The exploitation step itself (swapping the `stack_id` in the URL) requires no authentication, no secret beyond the already-obtained token, and no additional access — it is a trivial, unprivileged action once any single CCMenu token is known to an attacker (e.g., leaked from a public CI status page, log, or screenshot, which is a realistic exposure vector for this exact class of "CI badge" token).

### Recommendation
Persist the target `stack` on the `ApiClient` created in `CCMenuUrlController#client` (include `stack:` in the `find_or_create_by!`/`create_with` call, and make the token per-stack rather than per-creator), and make `Api::CCMenuController#stack` route through the scoped `stacks` helper (or explicitly assert `current_api_client.stack_id == stack.id`) instead of resolving `Stack.from_param!(params[:stack_id])` unconditionally.

### Proof of Concept
1. User Alice, who has access to `owner/repoA`, visits its Settings page and clicks "Fetch URL"; this calls `CCMenuUrlController#fetch`, creating/reusing an `ApiClient` named `"CCMenu Client"` for Alice with `permissions: ['read:stack']` and `stack_id: nil`, and returns `GET /api/stacks/owner/repoA/production/ccmenu?token=<T>`.
2. Anyone obtaining `<T>` (e.g., it was pasted into a public CI dashboard) can then request `GET /api/stacks/owner/repoB/production/ccmenu?token=<T>` for a completely unrelated stack `repoB` that Alice may or may not even have looked at.
3. `Api::CCMenuController#authenticate_api_client` accepts `<T>` (it's a valid, non-expired `ApiClient` token), `require_permission :read, :stack` passes because the client's `permissions` includes `read:stack`, and `#stack` resolves `repoB` directly via `Stack.from_param!`, returning `repoB`'s build/deploy status with no Shipit login, no Basic-Auth secret, and no relationship whatsoever between the token and `repoB`.

  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end
