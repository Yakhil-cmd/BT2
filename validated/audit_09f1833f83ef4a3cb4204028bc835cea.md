### Title
Webhook signature verification org and `Team.organization` write org can diverge via mismatched `repository`/`organization` payload keys - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `Shipit.github(organization:)` app (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, which prefers `params.dig('repository','owner','login')` over `params.dig('organization','login')`. `MembershipHandler#find_or_create_team!` instead unconditionally uses `params.organization.login` to set the `Team#organization` on creation. Because these two fields are read independently from the same JSON body with no cross-check, an attacker who owns a legitimate GitHub App installation on their own org can forge a `membership` webhook whose `repository.owner.login` points to their own org (verified with their own known `webhook_secret`) while `organization.login` points to a victim org, causing a `Team` row to be created/attributed to the victim organization.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`organization_whose_secret_verified_signature (repository_owner => Shipit.github(organization: repository_owner))` == `organization_written_to_Team (params.organization.login)`.

Code path:
- `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and verifies HMAC with that app's `webhook_secret`: [1](#0-0) 
- `repository_owner` prefers `repository.owner.login`, only falling back to `organization.login` if `repository` is absent: [2](#0-1) 
- `MembershipHandler` requires both a `team`/`organization`/`member` block, and separately, the base `Handler#initialize` only parses the declared schema — `repository` is not part of `MembershipHandler`'s schema and is not cross-validated against `organization`: [3](#0-2) 
- `find_or_create_team!` writes `team.organization = params.organization.login` unconditionally, with no reference to `repository_owner` or the app used to verify the signature: [4](#0-3) 

Exploit flow: attacker installs a Shipit-compatible GitHub App on their own org (`attacker-org`), and knows/controls that org's `webhook_secret` (a legitimate credential for their own org, satisfying the stated precondition). They POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{"repository":{"owner":{"login":"attacker-org"}},"organization":{"login":"victim-org"},"team":{"id":1,"name":"x","slug":"x","url":"http://x"},"member":{"login":"attacker"},"action":"added"}
```
signed with `attacker-org`'s webhook secret. `verify_signature` resolves `repository_owner` → `"attacker-org"` → verifies successfully using the attacker's own secret. `MembershipHandler#process` then creates a `Team` with `organization: "victim-org"` and adds the attacker as a member of that team.

Existing guards do not close this: `drop_unhandled_event` only checks event type; `verify_signature`'s `GithubOrganizationUnknown` rescue only fires if `repository_owner` resolves to an org with no configured app — the attacker's own org is a known, configured org, so this rescue never triggers. `ExplicitParameters` schema in `MembershipHandler` validates presence/types only, not cross-field consistency between `repository` and `organization`. No model validation ties `Team#organization` to the verifying app.

### Impact Explanation
A `Team` record scoped to `victim-org` (and its `Membership` rows) can be created or mutated by an attacker who never authenticated against `victim-org`'s webhook secret and holds no privilege there. If `victim-org`'s legitimate team of that `github_id` doesn't yet exist in Shipit's DB, this plants an attacker-controlled `Team`/`Membership` under the victim's `organization` field; if `Shipit.github_teams` authorization is later consulted against `Team#organization`/`slug` combinations, this could let the attacker's added member gain authorization tied to `victim-org`'s namespace — an escalation path into `Shipit.github_teams`. This is repeatable against any organization name the attacker chooses for the `organization.login` field, for every `membership` event they choose to forge, as long as they control at least one org with an installed app.

### Likelihood Explanation
Preconditions: attacker must have their own GitHub org with a Shipit App installation configured in `Shipit.github` (giving them a legitimate `webhook_secret` for the `Shipit.github(organization: 'attacker-org')` lookup) — this matches the stated precondition and is achievable by any external party who can set up their own org's app integration. No knowledge of the victim org's secret, no Shipit session, and no privileged role is required. The attacker only needs to craft one JSON POST with mismatched `repository`/`organization` fields and a valid HMAC signature computed with their own known secret. This is low-cost and fully repeatable/scriptable.

### Recommendation
Bind webhook signature verification org to the same field used for record attribution. Concretely: use `params.dig('organization','login')` (or whichever field is authoritative for the handler) consistently in both `WebhooksController#repository_owner`/`verify_signature` and `MembershipHandler#find_or_create_team!`, or, safer, have `MembershipHandler` cross-validate that `payload.dig('organization','login')` matches the `repository_owner` value that was used for signature verification, rejecting the webhook (422) on mismatch.

### Proof of Concept
```ruby
test "membership handler team.organization diverges from webhook-verified org" do
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  request.headers['X-Github-Event'] = 'membership'
  body = {
    repository: { owner: { login: 'attacker-org' } },
    organization: { login: 'victim-org' },
    team: { id: 999, name: 'Evil', slug: 'evil', url: 'http://example.com' },
    member: { login: 'attacker' },
    action: 'added'
  }.to_json

  assert_difference -> { Team.count }, 1 do
    post :create, body:, as: :json
  end

  team = Team.find_by(github_id: 999)
  # Binding check: signature-verifying org ('attacker-org') != Team.organization ('victim-org')
  assert_equal 'victim-org', team.organization
  refute_equal 'attacker-org', team.organization
end
```
