### Title
Unbounded key-range scan in `in data feed` / data-feed getters lets a single cheap unit trigger disproportionate I/O on every validating node - ([File: data_feeds.js])

### Summary
An unprivileged unit poster can embed an `['in data feed', ...]` clause (via an address definition/authentifier, or via an AA getter such as `data_feed[...]`) with a relational operator (`>`, `>=`, `<`, `<=`, `!=`) against a long-lived oracle feed. The complexity/op-counting model in `definition.js`/`formula/validation.js` charges this operation a flat cost of `complexity++`/`count_ops++` (effectively O(1)), but the actual implementation in `data_feeds.js` performs an **unbounded LevelDB key-stream scan** with no `limit` for these relations, so the real cost is O(number of matching feed records), which grows unboundedly as an oracle keeps posting over the network's lifetime. This mismatch lets a spammer buy near-unlimited validator CPU/I/O for a fixed, tiny declared "complexity," analogous to the Jupiter incident where cheap spam requests disproportionately loaded backend infrastructure.

### Finding Description
`validateAuthentifiers` in `definition.js` evaluates the `in data feed` operator by calling `dataFeeds.dataFeedExists`, which for non-`=` relations delegates to `dataFeedByAddressExists`: [1](#0-0) 

In `dataFeedByAddressExists`, only the `=` relation sets `options.limit = 1`. All other relations (`>`, `>=`, `<`, `<=`, and the `!=` case which recurses into `>`/`<`) open a `kvstore.createReadStream`/`createKeyStream` with **no limit**, and iterate every matching key until a match is found or the stream ends: [2](#0-1) 

The same unbounded-scan pattern is used by `readDataFeedByAddress`/`readDataFeedValue`, reachable from oscript's `data_feed[...]` getter used inside AA definitions: [3](#0-2) [4](#0-3) 

Meanwhile, the static complexity/op-counter that is supposed to bound the cost of evaluating a definition or AA formula treats every operator, including `in data feed`, as a fixed unit of work: [5](#0-4) 

There is no accounting for the size of the oracle's historical feed range, the number of records to scan, or the min/max MCI window width supplied by the attacker (`min_mci` defaults to 0, i.e., "scan since genesis" is allowed). Because feeds accumulate over the life of the network (e.g., long-running price oracles posting every few seconds/minutes for years), the achievable scan size is attacker-uncontrolled but grows monotonically with chain age, while the "price" the attacker pays (fixed complexity=1, one op) does not.

### Impact Explanation
Every full node (and every validating/witness node) must independently evaluate this operator when validating the unit (address-definition based) or when executing the AA trigger, so a single cheap unit can force every validating node to perform a large, unindexed range scan of the `df`/`dfv` keyspace for a chosen long-history oracle address/feed name. Repeating this in a burst of cheap units (each paying the same minimal declared complexity/fee) lets an attacker impose asymmetric CPU/I/O load on the whole validating network, slowing down validation and delaying confirmation of legitimate units network-wide — matching the "network unable to confirm new units" impact category. This is reachable purely by an unprivileged unit poster (crafting an address whose definition contains `in data feed`) or by anyone triggering an AA that reads such a data feed, with no special privilege required.

### Likelihood Explanation
The building blocks are all directly reachable from unprivileged inputs: any address can adopt a spending condition containing `in data feed` with a non-equality relation and `min_mci: 0` targeting any long-running oracle (e.g., a well-known price feed), and any user can send a trivial payment from that address (satisfying the condition cheaply, since a scan simply returning `false`/`true` still completes the full traversal in the worst case for `!=`/no-match cases). Similarly, any AA can call `data_feed[oracles=...][...]` in a getter/trigger execution. No coordination with witnesses/hubs, no privileged keys, and no protocol upgrade gating prevents this today, though the actual amount of achievable I/O amplification depends on how large existing oracle feed histories are, which grows over time.

### Recommendation
- Bound the LevelDB scan the same way `=` is bounded: add a sane `limit` (and/or require callers to supply a maximum scan depth) for `>`, `>=`, `<`, `<=`, and `!=` data-feed lookups in `dataFeedByAddressExists`/`readDataFeedByAddress`.
- Charge complexity/op cost proportional to actual work performed (e.g., increment `count_ops` per record inspected, similar to the `count`/`count_before_found` counters already collected in `data_feeds.js`), or enforce a hard cap on `max_mci - min_mci` / number of records scanned and fail validation if exceeded.
- Consider requiring `min_mci` to be non-zero / bounded relative to `last_ball_mci` by protocol default to prevent full-history scans, or maintain a secondary index that supports efficient range queries independent of feed volume.

### Proof of Concept
1. Identify (or create) an oracle address/feed with a long posting history (e.g., a price feed posted every few minutes since genesis).
2. Define a new address whose spending condition is `['in data feed', [[oracle_address], 'feed_name', '!=', 'some_value_never_posted']]` with `min_mci` omitted (defaults to 0).
3. Fund the address and post payment units repeatedly using it as an authentifier path; each validating node, on receipt, calls `dataFeedExists` → `dataFeedByAddressExists('!=', ...)`, which internally issues unbounded `>` and `<` range streams over the oracle's entire feed history in `kvstore`.
4. Repeat with multiple units/parallel senders; because the declared complexity/ops charged for this operator is fixed (`complexity++`/`count_ops++` = 1) regardless of feed size, the attacker's cost stays flat while imposed validator I/O grows with feed history size, illustrating the amplification.
