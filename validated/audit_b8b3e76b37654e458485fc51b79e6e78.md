### Title
Webhook organization used to select the signing secret is not the repository the payload acts on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App config (and thus which `webhook_secret`) to use for HMAC verification based on an **unauthenticated** field of the same JSON body it is about to verify, while every event handler acts on a **different, independently-controlled** field of that same unverified body to decide which repository/stack to mutate. If any configured GitHub organization in a multi-org Shipit deployment has no `webhook_secret` set, signature verification is skipped entirely for payloads claiming that organization, yet the payload can still name any other tracked repository to act on.

### Finding Description
`verify_signature` resolves the GitHub App instance via: [1](#0-0) 
using [2](#0-1) 
i.e. `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` — both read from `request.raw_post` **before** the signature has been checked.

`Shipit.github(organization:)` looks up per-organization config and instantiates a `GitHubApp` whose `webhook_secret` is optional: [3](#0-2) [4](#0-3) 

Verification itself trivially passes when no secret is configured for the resolved organization: [5](#0-4) 
`return true unless webhook_secret`.

Meanwhile, every webhook handler resolves the **repository actually acted on** from a separate JSON field, `repository.full_name`, not from `repository.owner.login`/`organization.login`: [6](#0-5) 

The binding the system implicitly relies on is:
`verified_organization (repository.owner.login / organization.login) == acted_on_repository_owner (repository.full_name)`

Nothing enforces this equality. The dispatch loop in `create` simply calls every handler registered for the event type with the raw, verified-only-by-HMAC-of-bytes `params`: [7](#0-6) 
The HMAC only proves the bytes were signed with *some* secret matching whichever organization the attacker put in `repository.owner.login`; it says nothing about which repository the rest of the payload (`repository.full_name`, `sha`, `state`, `member`, `team`, etc.) claims to touch.

### Impact Explanation
In a multi-organization deployment (`Shipit.github_default_organization` non-nil, keyed config as documented in `docs/setup.md`), if even one onboarded organization is configured without a `webhook_secret` (an allowed, documented-optional setting), an attacker who can reach the `/webhooks` endpoint can craft a JSON body with:
- `organization.login` / `repository.owner.login` = the org with no secret (bypasses `verify_signature` entirely, since `webhook_secret` is blank → `verify_webhook_signature` returns `true` unconditionally), and
- `repository.full_name` = any *other* tracked repository belonging to a fully-protected organization.

This lets the attacker forge events processed by `Shipit::Webhooks` handlers against a repository they have no relationship to, e.g.:
- `push` → enqueues `GithubSyncJob` for an arbitrary stack.
- `status`/`check_suite` → injects fake CI status/check results (`StatusHandler`, `CheckSuiteHandler`), which the merge queue and continuous-deployment gating in `deploy_spec` and `ci.require` rely on to trigger unattended deploys/merges.
- `membership` → creates `Team`/`User`/`Membership` records, as exercised in `test/controllers/webhooks_controller_test.rb` (`:membership creates the mentioned team on the fly`, `:membership can append an user membership`), directly manipulating `Shipit.github_teams`-based authorization data.

This crosses the "organization that authenticated versus the repository that is written" binding and can escalate into `Shipit.github_teams` authorization or trigger an unauthorized deploy/merge — both explicitly in-scope High/Critical impacts.

### Likelihood Explanation
Requires: (a) the operator to run a multi-organization Shipit configuration, and (b) at least one configured organization with no `webhook_secret` set — both are supported, documented configurations rather than misuse, and the endpoint is unauthenticated by design (it's the GitHub webhook receiver). No GitHub App private key, `ApiClient` token, or session is needed by the attacker; they only need network access to the public webhook endpoint. Likelihood is therefore conditional on this specific but legitimate configuration pattern, which I could not verify against a specific deployment — this is a configuration-dependent, not universal, vulnerability in the engine's own logic.

### Recommendation
Do not use an unauthenticated payload field to select the verification secret independent from the field the handlers use to determine the acted-on resource. Concretely:
- After computing `repository_owner`, verify that it matches the owner embedded in `repository.full_name` before proceeding (reject on mismatch), and/or
- Refuse to short-circuit `verify_webhook_signature` to `true` when `webhook_secret` is blank for a resolved organization in multi-org mode — instead reject the request (fail closed) unless the deployment explicitly opts into the legacy single-app, no-secret mode.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub config: `orgA` (no `webhook_secret` set) and `orgB` (has `webhook_secret` set, hosts a real tracked stack `orgB/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "organization": { "login": "orgA" },
  "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "branches": [{ "name": "master" }]
}
```
No `X-Hub-Signature` needed (or an arbitrary value), since `verify_signature` resolves `Shipit.github(organization: 'orgA')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-83`.
3. `StatusHandler` processes the forged status against `orgB/victim-repo`'s commit, satisfying CI-required checks and potentially unblocking continuous deployment/merge for a repository the attacker does not control.

Note: I was unable to open `app/models/shipit/webhooks/handlers/status_handler.rb`, `push_handler.rb`, and `membership_handler.rb` in full within the remaining budget to confirm every field consumed by each handler beyond what test assertions show; the root-cause binding break in `webhooks_controller.rb` and `handler.rb` is confirmed directly from source.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
