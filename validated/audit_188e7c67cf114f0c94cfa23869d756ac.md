I have enough evidence to confirm this is a genuine bug in `OpenedHandler#provision?`.### Title
`OpenedHandler#provision?` operator precedence bypasses `review_stacks_enabled` for `prevent_with_label` behavior - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb#provision?])

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with `provisioning_behavior_allow_all?` using `&&`, but the third disjunct for `prevent_with_label` never re-checks `review_stacks_enabled` due to Ruby operator precedence, so an unprivileged PR author can force creation and provisioning of a `Shipit::ReviewStack` on a repository that has explicitly disabled review stacks.

### Finding Description
The claimed binding is: `(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?) ⊆ (repository.review_stacks_enabled == true)`.

`provision?` is written as:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

In Ruby, `&&` binds tighter than `||`, so this parses as three independent disjuncts:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`.

The third disjunct — the `prevent_with_label` path — never references `review_stacks_enabled`. With `review_stacks_enabled == false` and `provisioning_behavior == :prevent_with_label`, an "opened" webhook payload with no matching label satisfies `prevent_with_label? && !has_label?` = `true`, making `provision?` return `true` regardless of the disabled flag. This is confirmed by the equivalent, symmetric bug in `ArchiveHandler`/`LabeledHandler`/`ReopenedHandler` all sharing the same broken pattern [2](#0-1) , and by the existing test suite, which never exercises `review_stacks_enabled: false` combined with `prevent_with_label` [3](#0-2) .

`respond_to_pull_request_opened?` calls `provision?` directly, and on true, `process` calls `ReviewStackAdapter#find_or_create!`, which builds a `ReviewStack` from attacker-controlled `pull_request.head.ref` (branch) and PR number (environment), then enqueues it for provisioning via `ReviewStackProvisioningQueue.add`, which will later invoke the repository's `ProvisioningHandler#up` against that branch [4](#0-3) [5](#0-4) [6](#0-5) .

Attacker request: open a pull request (no label) against a repository whose Shipit admin has set "Dynamically provision stacks for Pull Requests?" unchecked (`review_stacks_enabled = false`) but left `provisioning_behavior = prevent_with_label`. GitHub emits the `pull_request` `opened` webhook to `POST /webhooks`, which `OpenedHandler` processes.

Existing guards that fail to catch this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that GitHub sent the payload — they don't validate business logic; `respond_to_pull_request_opened?` delegates entirely to the broken `provision?`; the `ExplicitParameters` schema only validates payload shape, not the disabled flag; there is no model validation preventing `Stack` creation when `review_stacks_enabled` is false, because that check lives only in the handler.

### Impact Explanation
This produces a `Shipit::ReviewStack` (a `Shipit::Stack` subtype) record and an associated `Shipit::PullRequest` record for a repository whose administrator explicitly disabled dynamic review-stack provisioning, with `branch` set to the attacker's fork/branch ref. The record is then enqueued and, subject to the host's `ProvisioningHandler#provision?`/`#up`, provisioned — running host-defined provisioning logic against attacker-supplied branch content. This is a write to a repository's stack set that bypasses the repository owner's explicit configuration decision (`review_stacks_enabled = false`), i.e., an unauthorized record/stack mutation for that repository driven purely by an unprivileged PR author. It does not, by itself, trigger `DeploysController#create`/`TaskCommands#perform` — the created stack has `continuous_deployment: false` and any actual deploy execution still requires an authenticated user (`session[:user_id]`) via `DeploysController#create` or an API client via `Api::DeploysController#create`. The exploit is repeatable per repository configured this way and per new PR (each opened PR is an independent trigger).

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled = false` and `provisioning_behavior = prevent_with_label` — a plausible, documented configuration (an admin turning off the feature while a `prevent_with_label` behavior remains selected from a prior setup). No Shipit session, API token, or GitHub secret is required; the attacker only needs to be able to open a PR (fork + push access), which is available to any GitHub user. Cost is a single PR open with no label. Feasible and deterministic, but requires the specific admin misconfiguration (disabled flag with `prevent_with_label` behavior) to be present.

### Recommendation
Fix operator precedence and explicitly gate all three disjuncts on `review_stacks_enabled` in `OpenedHandler#provision?` (and the equivalent methods in `ReopenedHandler#unarchive?`, `LabeledHandler#archive?`/`#unarchive?`, `UnlabeledHandler#archive?`/`#unarchive?`), e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does NOT create stacks when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false      # binding LHS: review_stacks_enabled == false
  repository.provisioning_behavior = :prevent_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []        # no provisioning label

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails: `Shipit::Stack.count` increases by 1 because `provision?` evaluates to `true` despite `review_stacks_enabled == false`, demonstrating that `(prevent_with_label? && !label)` is not a subset of `(review_stacks_enabled == true)` as the code currently stands. After applying the recommended fix, the test passes with `assert_no_difference`.
