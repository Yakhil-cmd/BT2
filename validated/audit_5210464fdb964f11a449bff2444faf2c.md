### Title
Webhook signature verification is silently skipped when `webhook_secret` is unset, allowing forged `membership` events to escalate into `Shipit.github_teams` authorization - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) returns `true` unconditionally when no `webhook_secret` is configured for the organization: `return true unless webhook_secret`. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) selects which `GitHubApp` (and thus which secret) to check against using `repository_owner`, a value read straight out of the still-unverified JSON body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, line 61). Since the webhook secret is documented as optional (docs/setup.md:30, "Webhook secret (optional)"), an operator can have a fully functional GitHub App integration with no secret set, in which case the entire webhook trust boundary collapses to nothing: any POST to `/webhooks` with the right `X-Github-Event` header is treated as an authenticated GitHub event for whatever organization/login the attacker names in the JSON body. [1](#0-0) [2](#0-1) 

### Finding Description
The binding this breaks is: *the organization that authenticated the webhook* should equal *the identity acted upon by the handler*. Concretely:

1. `WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) dispatches the raw, attacker-controlled JSON `params` to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature` "passes."
2. When `webhook_secret` is blank for the targeted organization, `verify_signature` never actually checks anything cryptographic — it trivially returns `true` for any payload (lib/shipit/github_app.rb:76-77).
3. `MembershitpHandler#process` (app/models/shipit/webhooks/handlers/membership_handler.rb:22-34) then executes: `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` followed by `team.add_member(member)` where `member = User.find_or_create_by_login!(params.member.login)` — all values taken from the unverified body.
4. `Team#add_member` (app/models/shipit/team.rb:41-43) simply appends the member to `Team#members` with no additional GitHub-side verification.
5. `User#authorized?` (app/models/shipit/user.rb:80-82) — the single gate used by `Authentication#force_github_authentication` (app/controllers/concerns/shipit/authentication.rb:20-34) to decide whether *any* logged-in GitHub user may use the whole Shipit UI — is satisfied purely by DB team membership: `teams.where(id: Shipit.github_teams.map(&:id)).exists?`.

So an attacker who can reach `/webhooks` (no session, no `ApiClient` token, no GitHub credentials) can forge a `membership` event naming one of `Shipit.github_teams`' `github_id`/`organization` values and any GitHub login (including their own, if they have any GitHub account and can authenticate to Shipit's OAuth flow), and that login is granted a `Membership` row. On next request, `authorized?` returns `true` for that login, bypassing the team-authorization control entirely.

### Impact Explanation
This directly matches the High-severity impact class "escalation into `Shipit.github_teams` authorization." Membership in `Shipit.github_teams` is Shipit's sole authorization mechanism gating the entire authenticated UI (deploys, rollbacks, custom tasks, stack management) once a user has completed any GitHub OAuth login — it is not scoped to a specific repository's collaborators. An attacker who is unauthorized (not on the configured team) can grant themselves membership via a forged webhook and subsequently perform privileged actions (deploys, rollbacks, task triggers) as an "authorized" identity.

### Likelihood Explanation
This is only exploitable when an operator has not configured `github.webhook_secret` for the organization in question — an explicitly supported ("optional") configuration per docs/setup.md. It requires no privileged credential (no `ApiClient` token, no session, no GitHub App private key, no `webhook_secret`), satisfying the analog rule's requirement that the exploit not depend on any excluded credential. It does require the attacker to know (a) a `Shipit.github_teams` entry's `github_id`, which is discoverable via GitHub's public team APIs for teams the attacker can see, and (b) to complete Shipit's normal GitHub OAuth login with any GitHub account to obtain a session — this is the ordinary, unprivileged login path, not a bypass of OAuth itself.

### Recommendation
Reject webhook delivery entirely (fail closed, not open) whenever `webhook_secret` is not configured, or refuse to process privilege-sensitive events (`membership`) without secret verification. Alternatively, corroborate `membership` events against a live GitHub API call (verifying the member is actually part of the named team/org) before mutating `Team`/`Membership` records, rather than trusting the webhook payload as sole authority.

### Proof of Concept
1. Operator configures a GitHub App for org `acme` in `secrets.yml` without setting `github.webhook_secret` (permitted per setup docs).
2. `Shipit.github_teams` includes team `acme/deployers` with `github_id: 555`.
3. Attacker (with a personal GitHub account, having completed normal Shipit OAuth login, thus currently unauthorized) sends:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": 555, "name": "deployers", "slug": "deployers", "url": "https://api.github.com/teams/555"},
  "organization": {"login": "acme"},
  "member": {"login": "attacker-github-login"}
}
```
4. `verify_signature` calls `Shipit.github(organization: "acme").verify_webhook_signature(...)`, which returns `true` immediately since `webhook_secret` is blank (lib/shipit/github_app.rb:76-77) — no signature is actually checked.
5. `MembershipHandler#process` creates/reuses `Team` `acme/deployers` and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`.
6. On the attacker's next request, `current_user.authorized?` (app/models/shipit/user.rb:80-82) returns `true`, granting full access to the Shipit UI as an "authorized" user.

      return true unless webhook_secret
