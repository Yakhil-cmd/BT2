### Title
`StatusHandler#process` writes CI status to every stack sharing a commit SHA, not just the repository that authenticated the webhook - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, which is scoped by SHA alone with no repository/stack filter. Because `shipit_commits` has a unique index on `(sha, stack_id)` rather than `sha` alone, the same commit (a shared ancestor between a review-stack branch and a protected branch, e.g. `main`) can legitimately have one `Commit` row per stack, and a single incoming `status` webhook updates all of them at once.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack == repository_that_authenticated(payload)`, but the actual invariant enforced is only `commit.sha == params.sha`, for any stack in the database.

Path: `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) dispatches the `status` event to `StatusHandler`, whose `process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

`Commit` `belongs_to :stack` [2](#0-1) , and the DB schema enforces uniqueness on `(sha, stack_id)`, not on `sha` alone: [3](#0-2) . This means the same content-addressed commit can exist as separate `Commit` rows under multiple stacks belonging to the same repository (e.g. a production stack tracking `main` and a review stack auto-provisioned for a pull request whose branch shares history/commits with `main`).

`Repository#review_stacks_enabled` with `provisioning_behavior_allow_all?` causes `PullRequest::OpenedHandler` to auto-provision a review stack for *any* opened pull request without maintainer approval: [4](#0-3) . An unprivileged contributor who can open a PR can cause a review stack to track a commit whose SHA is shared with, or an ancestor of, the victim's protected stack.

When GitHub genuinely relays a `status` event (e.g., CircleCI reporting `success` for `ci/circleci` on that SHA because CI ran for the PR), the webhook is correctly signed by the real GitHub App secret for that organization/repository — `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) passes as designed, since this is a legitimate GitHub-forwarded event, not a forged one. `StatusHandler#process` then updates `create_status_from_github!` on every `Commit` row matching that SHA, including the row belonging to the victim's protected/production stack, via `Commit#add_status` which can flip `deployable?`/`blocked?` state and calls `stack.schedule_merges` when the new status becomes `success`/`pending`: [5](#0-4) , [6](#0-5) .

None of the existing guards prevent this: `verify_signature` only checks the webhook came from a legitimate GitHub organization, not that the SHA belongs to the stack being modified; the `ExplicitParameters` schema in `StatusHandler` only validates presence/type of `sha`/`state`/`context`, not ownership; and there is no `stacks`/repository scope applied to the `Commit.where(sha:)` lookup.

### Impact Explanation
A CI status event authenticated for one context (a review stack / PR branch) can mutate the deploy-readiness state (`deployable?`, blocking status, merge scheduling) of a *different* stack (e.g. a production stack) that happens to share a commit SHA — most plausibly a shared ancestor commit between the PR branch and the target branch. This is a cross-tenant/cross-stack write not authorized by the repository that legitimately sent the status, matching the "payload for one repository mutating another's stack/commit" Critical impact category, since it can trigger `stack.schedule_merges` and influence deploy/merge decisions on a stack the attacker does not control.

### Likelihood Explanation
Requires: (1) `review_stacks_enabled` with `allow_all` (or a labeling policy the attacker can satisfy) on the victim repository so external PRs auto-provision review stacks; (2) the attacker's PR branch sharing a commit SHA with the protected stack's branch — trivially achievable since a PR branch typically shares the target branch's full history up to the fork point, so any ancestor commit already tracked by the target stack is also tracked by the newly created review stack; (3) CI (or any status-posting integration) reporting a status for that shared SHA, which GitHub relays as a normal, validly signed webhook. No secrets, tokens, or privileged roles are needed by the attacker — only the ability to open a PR, which is the baseline attacker capability defined in this audit's rules. This is repeatable per PR/status event.

### Recommendation
Scope the `StatusHandler#process` (and `create_or_update_check_run_from_github!` / check-run handler, which has the analogous issue) lookup to only the `Commit` rows belonging to stacks/repository that the webhook payload's `repository.full_name` actually authenticates, e.g. `Commit.joins(:stack).merge(Stack.where(repository: repository_from_payload)).where(sha: params.sha)`, instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "a status for a shared SHA updates an unrelated stack's commit" do
  shared_sha = "a" * 40

  production_stack = shipit_stacks(:shipit) # review_stacks_enabled true, allow_all, requires ci/circleci
  production_commit = production_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  review_stack = Shipit::Stack.create!(
    repository: production_stack.repository,
    environment: "pr123",
    branch: "pr-branch"
  )
  review_commit = review_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  # Binding under test: commit.stack == authenticating_repository(payload)
  assert_not_equal production_commit.stack_id, review_commit.stack_id
  assert_equal production_commit.sha, review_commit.sha

  refute production_commit.reload.deployable?

  params = ExplicitParameters::Params.new(
    sha: shared_sha, state: "success", context: "ci/circleci"
  )
  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  # Assert the production stack's commit was mutated by a status event
  # that only the review stack's branch/PR authenticated.
  assert production_commit.reload.deployable?, "unrelated stack's commit was flipped to deployable"
end
```
This demonstrates that a single `status` webhook processed by `StatusHandler#process` mutates `Commit` rows across stacks solely by SHA match, violating "a `ci/circleci` status affects only the repository/stack that authenticated it."
