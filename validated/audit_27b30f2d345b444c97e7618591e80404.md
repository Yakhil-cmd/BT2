### Title
Cross-tenant Team membership forgery via GitHub team-ID collision in membership webhook - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to verify a payload against using `repository_owner` (`organization.login` for `membership` events), but `MembershipHandler#find_or_create_team!` looks up the target `Team` row using only the GitHub-global `team.id`, with no check that the team's `organization` matches the org whose secret verified the request. An attacker who controls their own GitHub org's webhook can forge a `membership` payload naming a victim org's team ID, causing their own GitHub user to be granted membership in the victim's `Team` record.

### Finding Description
The broken binding: `organization_whose_secret_verified_signature (repository_owner == params.organization.login)` should equal `organization_owning_the_mutated_team_record (team.organization)`, but nothing in the code enforces this.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [3](#0-2) , then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [4](#0-3) . For an attacker-controlled org (`attacker-org`), this passes because the request is legitimately signed with `attacker-org`'s own `webhook_secret`.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { ... }` [5](#0-4) . Since GitHub team IDs are globally unique but Shipit indexes teams only by `github_id` (not scoped by `organization`), supplying a `team.id` that matches an existing victim `Team` row (belonging to a different org) causes `find_or_create_by!` to find and reuse that existing row instead of creating a new one scoped to `attacker-org`.
3. `team.add_member(member)` is then called with `member = User.find_or_create_by_login!(params.member.login)` (the attacker's own GitHub login) [6](#0-5) , appending a `Membership` linking the attacker's `User` to the victim `Team` [7](#0-6) .
4. If that victim `Team` is one of `Shipit.github_teams` (i.e., an authorization-granting team, resolved via `oauth_teams`) [2](#0-1) , the attacker's `User#authorized?` now returns true via `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [1](#0-0) , granting them full Shipit session access enforced by `force_github_authentication` [8](#0-7) .

No existing guard catches this: `verify_signature` only proves the payload was signed by *some* known org, not that the org matches the mutated record's owner; `find_or_create_by!` has no scoping by `organization`; `ExplicitParameters` schema only validates types/presence, not ownership.

### Impact Explanation
An unprivileged attacker who registers/owns any GitHub organization configured in Shipit (with its own `webhook_secret`) can grant themselves membership in an arbitrary pre-existing `Team` belonging to a different, victim organization, without any GitHub-side team invitation. If that victim team is used in `Shipit.github_teams`, this is a direct authentication/authorization bypass, granting the attacker full logged-in access to the Shipit deployment UI (deploys, rollbacks, task streams) — matching "escalation into `Shipit.github_teams` authorization" (High) and arguably "unauthorized deploy" territory (Critical) once inside, since a logged-in authorized user can trigger deploys/rollbacks on stacks. This is repeatable against any victim `Team` row whose numeric GitHub `github_id` is known or guessable, and is cross-tenant (attacker-org payload mutates a record belonging to a completely different org).

### Likelihood Explanation
Preconditions: Shipit configured with multiple GitHub orgs each having their own `webhook_secret` (explicitly stated as multi-tenant in this question) [9](#0-8) ; a `Team` row for the victim org already exists (created automatically the first time any legitimate `membership` webhook fires for that org, or via `Shipit.github_teams` bootstrap at startup) [2](#0-1) . Attacker cost is low: create/own a GitHub org, register it (or have it already registered) as a Shipit-integrated org with its own webhook, and know/guess the victim team's numeric GitHub team ID (discoverable via public GitHub API for public orgs/teams, or via `GET /orgs/{org}/teams` if the victim org is public). The attack is a single crafted HTTP POST, fully repeatable.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization`, and verify that `params.organization.login` matches `repository_owner` (the org whose secret was verified) before trusting it:
```ruby
def find_or_create_team!
  raise ArgumentError, 'organization mismatch' unless params.organization.login == repository_owner_from_signature
  Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```
More generally, `find_or_create_by!` should never match an existing row across a different `organization` than the one that authenticated the webhook; add a uniqueness validation/index on `(github_id, organization)` and refuse to reuse a `Team` row whose `organization` differs from the verified org.
