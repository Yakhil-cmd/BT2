### Title
Webhook signature verification is keyed off `repository.owner.login`/`organization.login` while the acted-upon repository is looked up via `repository.full_name`, letting a webhook sender for one organization spoof events for another organization's stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using `repository.owner.login` (or `organization.login`), but the handler that actually acts on the payload (`Handler#stacks`/`#repository_name`) resolves the target `Repository`/`Stack` using `repository.full_name`. These two fields are never checked for consistency, and both live inside the same signed JSON body that an app owner fully controls when crafting their own webhook secret. An attacker who legitimately administers a Shipit-connected GitHub App for *any* configured organization (i.e., knows that organization's `webhook_secret`) can forge a payload whose `repository.owner.login` matches their own organization (so the correct/known secret is used and the HMAC check passes) while `repository.full_name` points at a victim organization's repository/stack.

### Finding Description
`WebhooksController#verify_signature` computes: [1](#0-0) 
using `repository_owner`, defined as: [2](#0-1) 

Once the HMAC check passes, `create` dispatches the *same raw payload* to registered handlers: [3](#0-2) 

Handlers resolve which `Stack`(s) to act on independently, via `Handler#stacks`/`#repository_name`, which reads a *different* field of the payload: [4](#0-3) 

`repository.owner.login` (used for signature/secret selection) and `repository.full_name` (used for stack resolution) are two independent, attacker-controlled fields within the same JSON body. Since HMAC verification only proves "this body was signed with the secret belonging to the organization named in `repository.owner.login`," it proves nothing about which organization's repository `full_name` actually names. An attacker who owns/administers a GitHub App on some low-value organization `attacker-org` (and therefore knows `attacker-org`'s `webhook_secret`) can construct:
```json
{ "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }, "ref": "refs/heads/main", "after": "<attacker-chosen-sha>" }
```
sign it with `attacker-org`'s known secret, and POST it to `/webhooks`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the signature validates successfully. `PushHandler#process` then resolves stacks via `full_name = "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: params.after)`: [5](#0-4) 

This breaks the intended binding "the organization whose secret authenticated the request == the repository/organization being written to by the handler," an exact analog of the report's "amount contributed == price paid" binding being broken because two independently-attacker-controlled values are compared to two different verified/unverified fields.

### Impact Explanation
An attacker with legitimate control of a single organization's webhook secret in a multi-tenant Shipit install can trigger `sync_github`/actions against an arbitrary other organization's stack that they have no authorization over. Depending on the target stack's configuration (e.g., `continuous_deployment: true`, as seen in test fixtures), this can drive an unauthorized sync/deploy pointing at an attacker-chosen commit SHA on a repository the attacker does not control — an unauthorized deploy/cross-repository write, matching the Critical impact bar ("cross-repository writes... or an unauthorized deploy").

### Likelihood Explanation
Requires the attacker to control (own the GitHub App/webhook secret for) at least one organization configured in a shared, multi-organization Shipit instance — a realistic scenario for any Shipit deployment serving multiple orgs/teams, and does not require any Shipit session, API token, or privileged account, satisfying the "unprivileged attacker" bar.

### Recommendation
After verifying the HMAC, re-derive the organization strictly from the same field used for repository/stack resolution (`repository.full_name`'s owner segment) and require it to equal the organization whose secret validated the signature; reject the request otherwise.

### Proof of Concept
1. Attacker registers/owns a Shipit-connected GitHub App on `attacker-org` and knows its `webhook_secret`.
2. Attacker crafts a `push` payload: `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, `ref = "refs/heads/main"`, `after = "<attacker-chosen-sha>"`.
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known secret and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and passes.
5. `PushHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on the victim's stack despite the request only ever being authenticated for `attacker-org`.
