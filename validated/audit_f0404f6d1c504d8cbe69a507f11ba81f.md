### Title
Unchecked `receive-tokens` result in `collateral-add` allows crediting collateral without a real token transfer - (File: `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`v0-market-vault.clar` defines a helper `receive-tokens` that pulls the underlying `ft-trait` token into the contract, but — unlike its sibling `send-tokens` — it does **not** wrap the `contract-call? ... transfer` in `try!`, so its `response` result is not enforced to be `ok` before the caller proceeds.

### Finding Description
The private helper is defined as a bare `contract-call?` with no `try!`/`asserts!`: [1](#0-0) 

Compare this to the outbound helper `send-tokens`, defined immediately below it, which explicitly wraps every `transfer` call in `try!` so a failing transfer aborts the transaction: [2](#0-1) 

This asymmetry is the direct Clarity analog of the Solidity `MerkleVesting.withdraw()` bug: a token `transfer` whose boolean/response result is not checked, so an unsuccessful transfer is treated as if it succeeded by the rest of the function. `receive-tokens` is the only entry point through which the market-vault registers that a user has actually deposited underlying tokens as collateral (it is invoked by `collateral-add` in the calling market contract before the collateral map is incremented). If the calling code that invokes `receive-tokens` does not itself re-wrap the returned response in `try!`/`asserts!` (which is the pattern the codebase relies on everywhere else, e.g. `send-tokens`, `dao-treasury.clar` `withdraw`), a malicious or non-conforming `ft-trait` implementation supplied by the caller can return `(err ...)` from `transfer` while the collateral map is still updated as if tokens were received.

### Impact Explanation
Because the market/vault collateral and debt accounting is a shared pool (`total-assets`, `total-supply`, LTV/health calculations use the recorded collateral map, not the real token balance), an attacker who can get "phantom" collateral registered without actually transferring tokens can then borrow real underlying assets against that phantom collateral. Every other depositor sharing the vault absorbs this shortfall — the vault becomes under-collateralized relative to its real token holdings, i.e. protocol insolvency / loss to other lenders/suppliers, not just the attacker's own funds. This matches the "socialization charged to all suppliers" / "shared pool" harm class explicitly listed as in-scope.

### Likelihood Explanation
Exploitability depends on whether a caller can register a collateral asset backed by a token contract that is attacker-influenced (e.g., an `ft-trait`-conforming token whose `transfer` returns `(err ...)` under certain conditions instead of aborting) and on whether the call site of `receive-tokens` fails to re-check the response. This could not be fully confirmed within the available tooling because the exact call site (`collateral-add` in the market contract) that invokes `receive-tokens` was not retrieved before the tool budget was exhausted — I was only able to confirm the definition of `receive-tokens` itself lacks the `try!` guard present in the symmetric `send-tokens` helper, which is the root-cause evidence for this class of bug. This should be verified against the actual call site to confirm whether it re-wraps the call in `try!`.

### Recommendation
Wrap the `contract-call? asset transfer amount account current-contract none` in `receive-tokens` with `try!` (or `asserts!`) exactly as done in `send-tokens`, so that a failed/erroring `transfer` response aborts the entire `collateral-add` transaction instead of allowing collateral bookkeeping to be updated without a corresponding real token inflow.

### Proof of Concept
1. Register (or already support) an `ft-trait` token whose `transfer` implementation can return `(err ...)` without reverting the Clarity transaction (e.g., a permissioned/pausable token, or one with an allowance/blacklist check that returns an error response).
2. Call the market's `collateral-add`/`supply-collateral-add` flow with that token while the transfer is set up to fail (e.g., attacker is blacklisted at the token level, or token has insufficient balance check that returns `(err ...)` instead of aborting).
3. If `receive-tokens`'s un-checked response is not re-validated by the caller, `v0-market-vault`'s collateral map is incremented for the attacker's account despite no tokens having moved into the vault.
4. The attacker then borrows real underlying assets from the shared vault against this phantom collateral, extracting value that other depositors funded, leaving the vault's real assets insufficient to honor all obligations.
