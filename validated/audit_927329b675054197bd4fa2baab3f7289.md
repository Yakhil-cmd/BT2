### Title
Cross-organization `pull_request` `closed` webhook allows attacker-signed payload to archive/deprovision a victim organization's ReviewStack - (File: `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb`)

### Finding Description
The claimed broken binding: `repository_owner` (used to select the webhook secret / GitHub App config for signature verification, from `params.dig('repository','owner','login')`) `==` the organization that actually owns the `ReviewStack` being archived (derived from `params.repository.full_name` inside `ClosedHandler`/`ReviewStackAdapter`).

Tracing the code: `WebhooksController#verify_signature` resolves the signing app via `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` [1](#0-0) , and verifies the HMAC using `Shipit.github(organization: repository_owner)` [2](#0-1) . `ClosedHandler#process` and `ReviewStackAdapter` never re-read `repository.owner.login` — they resolve the target repository purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [3](#0-2)  and `Repository.from_github_repo_name` splits `full_name` on `/` to find owner+name [4](#0-3) .

For this attack to work, the equality must actually be checkable: `Shipit.github(organization:)` looks up `secrets.github` — in the single-org config schema (`github_default_organization` is `nil`, the default/documented setup per `docs/setup.md` and `config/secrets.development.example.yml`), there is exactly **one** `webhook_secret` for the whole Shipit instance, used for every organization/repository regardless of what `repository_owner` string is present in the payload [5](#0-4) . `verify_webhook_signature` computes `OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message)` and does a `secure_compare` against the signature header, entirely independent of the `repository_owner` value [6](#0-5) . This means:

- In the (documented default) single-org configuration, `repository_owner` in the payload is not cryptographically bound to the secret at all — any repository owner string in the JSON body passes as long as the single shared `webhook_secret` matches. Since the attacker does not know that secret either, they cannot forge a valid signature in this mode — this is not exploitable in single-org mode because the secret itself is unknown to the attacker.
- In the **multi-org** configuration (`github: { org_a: {...}, org_b: {...} }`), each organization has its own distinct `webhook_secret` looked up via `github_app_config(organization)` [7](#0-6) . An attacker who owns/administers `org_a` in this multi-tenant Shipit deployment (and thus legitimately knows `org_a`'s webhook secret because they configured that GitHub App/organization) can sign a payload with `repository.owner.login = "org_a"` (so `verify_signature` passes using `org_a`'s secret) while setting `repository.full_name = "victim-org/victim-repo"` and `number = N` to target a completely different, victim-owned `ReviewStack`.

The critical missing guard is that no code anywhere re-validates that `params.repository.owner.login` (the authenticating org) matches the owner portion of `params.repository.full_name` (the org whose data is mutated). `ClosedHandler`'s `params` schema only requires `repository.full_name` [8](#0-7)  and never touches `repository.owner`. `ReviewStackAdapter#archive!` then unconditionally calls `stack.remove_from_provisioning_queue`, `stack.deprovision`, and `stack.archive!(user, ...)` on whatever stack `from_github_repo_name(full_name)` resolves to [9](#0-8) , with `user` resolved via `User.find_or_create_by_login!(params.sender['login'])` — an attacker-controlled string [10](#0-9) .

### Impact Explanation
This is exploitable **only** in a multi-organization Shipit deployment where the attacker legitimately controls at least one of the configured GitHub organizations/webhook secrets in that same Shipit instance (a genuine multi-tenant setup, e.g. an internal platform team onboarding many orgs). Within that scope, a malicious org owner can archive, deprovision, and mark as closed any other tenant's live ReviewStack by guessing/observing a valid `repository.full_name` and PR `number`. This is a real cross-tenant write: a payload authenticated for org A mutates org B's stack state — matching the "payload for one repository mutating another's stack" Critical category. It does not enable code execution or credential exfiltration, but it is an unauthorized deprovision/archive (denial of a legitimate deploy) driven by a payload signed by a different organization than the one whose data is affected.

### Likelihood Explanation
Requires: (1) Shipit configured with the multi-org `github:` schema (not the default single-secret schema most documented setups use), (2) the attacker legitimately administers at least one org already onboarded to that same Shipit instance and thus knows that org's real `webhook_secret`, and (3) the attacker knows or can guess the victim's `repository.full_name` and an active PR `number` with a live ReviewStack. This is not exploitable by a fully anonymous/unprivileged internet attacker with no Shipit relationship at all — under the single-secret default configuration described in `docs/setup.md`/`config/secrets.development.example.yml`, the attacker cannot forge a valid `X-Hub-Signature` without knowing the one shared secret. The realistic threat model is therefore a semi-trusted party (one legitimate tenant org attacking another tenant) rather than a fully external unprivileged attacker, which is a narrower precondition than the question's stated attacker model ("no Shipit secrets, not a maintainer") strictly allows.

### Recommendation
In `ClosedHandler` (and the other `pull_request` handlers using `ReviewStackAdapter`/`Repository.from_github_repo_name`), validate that `params.repository.owner.login` (or the owner segment of `full_name`) matches the `repository_owner` that was used to authenticate the webhook signature, e.g. by having the controller pass the verified organization into the handler and asserting `repository.owner == verified_organization` before performing any archive/deprovision mutation; reject the event otherwise.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual, multi-org secrets fixture required)
test "closed pull_request webhook signed by org_a cannot archive org_b's review stack" do
  # Setup: Shipit configured with multi-org secrets: org_a (attacker-owned) and org_b (victim)
  victim_stack = create_review_stack(owner: "org_b", name: "victim-repo", pr_number: 7)

  body = {
    action: "closed",
    number: 7,
    pull_request: { id: 1, number: 7, url: "u", title: "t", state: "closed",
                     additions: 1, deletions: 1,
                     head: { sha: "sha", ref: "ref" },
                     user: { login: "attacker" }, assignees: [], labels: [] },
    repository: { owner: { login: "org_a" }, full_name: "org_b/victim-repo" },
    sender: { login: "attacker" }
  }.to_json

  signature = sign_with_org_a_secret(body) # attacker legitimately knows org_a's secret

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  assert_no_changes -> { victim_stack.reload.archived? } do
    post :create, body: body, as: :json
  end
end
```
Assert both sides of the binding: `repository_owner` used in `verify_signature` == `"org_a"`, while the owner implied by `params.repository.full_name` == `"org_b"`; the test should assert the request is either rejected (fixed behavior) or, absent a fix, that `victim_stack.reload.archived?` becomes `true` and `provision_status` becomes `deprovisioning`/`deprovisioned` (demonstrating the vulnerability).

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
