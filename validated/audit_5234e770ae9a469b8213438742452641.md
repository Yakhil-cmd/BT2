### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enables attacker-controlled batch deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the commit(s) to update purely by SHA, with no scoping to the repository that authenticated the webhook. Because `Stack#next_commit_to_deploy` and `trigger_continuous_delivery` trust any `success` `Status` row on a commit regardless of which repository's CI produced it, a webhook validly signed for one repository/organization can write statuses onto commits belonging to a completely unrelated stack whose SHA happens to match (trivial for forks of a public repo, since git SHAs are content-addressed and identical across forks).

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`{Commit rows a status webhook is allowed to mutate} == {Commits belonging to Stack(s) of Repository.from_github_repo_name(payload.repository.full_name)}`

In reality the code implements:

`{Commit rows mutated} == Commit.where(sha: params.sha)` (system-wide, unscoped) [1](#0-0) 

Compare this to the sibling handlers, which correctly scope to the repository resolved from the payload via the `Handler#stacks` helper: [2](#0-1) [3](#0-2) 

`StatusHandler` is the only "status" handler; it never calls `stacks` or checks `payload.dig('repository','full_name')` — it queries `Commit` globally by `sha` and calls `commit.create_status_from_github!` on every match, in every stack, in every repository configured on the Shipit instance.

**Signature check does not bind repo identity to content.** `WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification purely from the payload's own JSON field `repository.owner.login`: [4](#0-3) 
This only proves the payload was signed with *some* organization's configured `webhook_secret` — it says nothing about which SHAs the payload may reference. In a multi-tenant Shipit instance (explicitly a supported configuration, see `docs/setup.md` "Using Multiple Github Applications"), an attacker who legitimately owns/administers Org A's GitHub App installation (and therefore knows Org A's `webhook_secret`) can produce a validly-signed `status` webhook whose `repository` field names Org A, but whose `sha` values are copied from a victim's public repository in unrelated Org B. Because forking a public GitHub repo preserves the exact git commit objects, the SHAs are byte-identical, and `Commit.where(sha: params.sha)` will match the victim's real `Shipit::Commit` rows in Stack B.

**Exploit flow:**
1. Attacker forks victim's public repository (byte-identical commit objects/SHAs to several consecutive pending victim commits).
2. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a body whose `repository` object identifies Attacker's own onboarded org/repo (so `verify_signature` succeeds using a secret the attacker legitimately knows), and `sha` set to each of the victim's consecutive pending commit SHAs, `state: success`.
3. `StatusHandler#process` finds each matching `Commit` (belonging to the victim's Stack) purely by SHA and calls `commit.create_status_from_github!`, creating real `Shipit::Status` rows with `state: 'success'` against the victim's stack, and firing `stack.schedule_merges`/continuous-delivery scheduling side effects.
4. `Stack#next_commit_to_deploy` reads these forged statuses via `deployable_commits`, which relies on `Commit#deployable?`/`status`, and picks the furthest commit that now looks CI-green: [5](#0-4) [6](#0-5) 
5. `trigger_continuous_delivery` deploys through that commit: [7](#0-6) 

The attacker thereby chooses exactly how many consecutive victim commits are marked "CI-passed" (bounded only by `maximum_commits_per_deploy`), controlling the scope of an unauthorized deploy of the victim's own code — none of this CI ever ran against the victim's authenticated repository.

**Why existing guards don't stop this:** `verify_signature` authenticates "a request signed by some org's secret," not "a request about this repository's own commits." `drop_unhandled_event`/`check_if_ping` are irrelevant. `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not repository ownership. Nothing in `Commit`, `Status`, or `StatusHandler` cross-checks the payload's `repository.full_name` against the `stack.repository` that owns the matched `Commit`.

### Impact Explanation
An attacker who controls (or merely administers the GitHub App integration for) any single repository/org onboarded to a shared Shipit instance can write `Status` rows — and thereby trigger real deploys — against any *other* tenant's stack, as long as they can reproduce (or already know) target commit SHAs, which is trivial for any public fork. This is a "payload for one repository mutating another's stack/commit" and an "unauthorized deploy" — both listed as Critical impact categories. The attacker fully controls which and how many consecutive victim commits are deployed, exceeding what the victim's real CI ever approved. This is repeatable against arbitrary stacks/repositories hosted on the same Shipit instance and requires no victim-side interaction.

### Likelihood Explanation
Preconditions: (1) the Shipit instance hosts more than one GitHub App/organization (a documented, supported configuration), and the attacker legitimately controls one of them (or knows its `webhook_secret`); (2) the victim stack has pending commits and `continuous_deployment`/CD scheduling enabled, and the target commit SHAs are known/reproducible (trivial for public repos via fork). Attacker cost is a handful of crafted HTTP POSTs with correct HMAC signatures they can legitimately compute for their own org. No Shipit session, API token, or victim secret is required. This is repeatable at will against any stack whose commit SHAs are known.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, matching the pattern used by `PushHandler`/`CheckSuiteHandler`: resolve `stacks` (via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) first, then only update `Commit` rows whose `stack_id` is in that scoped set (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent `Commit.where(sha: params.sha, stack: stacks)`), rejecting/ignoring any SHA match belonging to a different repository's stack.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
1. Create two stacks backed by two different `Repository` records (`repo_a` "attacker/app", `repo_b` "victim/app"), each in its own fixture-based `GithubHook`.
2. Create 3 consecutive `Commit` rows under `repo_b`'s stack with identical, attacker-known SHAs (`sha_1..sha_3`), currently `pending`.
3. Build a `status` webhook payload whose `repository.full_name == "attacker/app"` but `sha` set to `sha_1`, `sha_2`, `sha_3` in turn, `state: "success"`, and call `Shipit::Webhooks::Handlers::StatusHandler.call(params)` directly (bypassing controller-level signing, since the point under test is the handler's missing repo scoping).
4. Assert (broken binding, before fix): `Shipit::Commit.find_by(sha: sha_3, stack: victim_stack).statuses.last.state == 'success'` even though the payload's `repository.full_name` was `"attacker/app"`.
5. Assert `victim_stack.next_commit_to_deploy == victim_commit_3` (the furthest forged commit).
6. Assert `victim_stack.trigger_continuous_delivery` creates a `Deploy` with `until_commit == victim_commit_3`.
7. After applying the recommended fix (scope by `stacks`), re-run and assert no `Status` is created on `repo_b`'s commits, `next_commit_to_deploy` is unchanged, and no `Deploy` is created.
