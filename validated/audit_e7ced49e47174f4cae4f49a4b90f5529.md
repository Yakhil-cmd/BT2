### Title
Route-supplied venue addresses let attacker contract code execute under the caller's signed authorization and transfer arbitrary wallet tokens - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The Chrome CVE class — attacker-supplied code (a malicious extension) running in a trusted context to inject unauthorized actions — maps onto the controller's strategy-swap path: `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` forward user-supplied `swap` bytes to the swap aggregator, which invokes whatever pool/token addresses the payload names with no venue allowlist. A malicious "hop pool" contract inside that call stack can issue `token.transfer(caller, attacker, amount)` for any token the caller holds, and Soroban records it as a child of the caller's own authorization entry — executing if the caller signs the simulated tree. This is the on-chain analog of injected script running with the victim's privileges.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:34-38` grants the router one exact input-transfer authorization and calls `router.execute_strategy(&controller, &amount_in, swap)` where `swap` is raw caller-provided bytes. The controller never decodes or validates the route contents. The aggregator dispatches hops to venue pool addresses named in the payload and "keeps no allowlist of them" (`docs/explanation/threat-model.md:154-165`). The in-repo proof test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:39-71` shows a router/hop-pool pair where the pool's `swap()` performs `token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount)` — draining an unrelated token the protocol never listed — and the recorded authorization tree attaches that theft as a child of the caller's `swap_collateral` entry (lines 194-227). Neither the payload `min_out`, the measured-output check in `verify_router_output` (swap.rs:75-83), nor the final account risk gate bounds this loss, because the stolen transfer is the caller's wallet funds, not routed funds.

### Impact Explanation
Theft of user funds beyond the swapped amount: any token balance in the victim's wallet (not just the swap input) can be transferred to the attacker inside the victim's own signed authorization tree. In the test, Alice loses her entire `WALLET_BALANCE` of an unrelated token while her position still passes all risk checks and receives fair swap output.

### Likelihood Explanation
Requires user interaction (UI:R analog of the CVE): the victim must submit a strategy call carrying an attacker-crafted route — e.g., a poisoned route served by a compromised/malicious quote source or a phishing interface — and sign the auth tree a wallet presents. The attacker needs no privilege and no on-chain footprint beforehand. The protocol provides no on-chain mitigation: venue addresses are unallowlisted by design, and the defense ("a client must decode the route it signs") is pushed entirely to off-chain client hygiene, which fails exactly when the quoting/signing path is malicious — the same trust failure as the CVE.

### Recommendation
Enforce a venue/pool allowlist on-chain in the swap aggregator: maintain an owner-gated registry of approved venue contract addresses (per `SwapVenue`) and reject hops whose pool address is not registered, so payload bytes can only reach audited adapter targets. Alternatively or additionally, have the aggregator execute venue calls with router-scoped auth only and verify post-hop that no caller-authorized sub-invocation beyond the exact input pull was requested — though the allowlist is the robust fix since Soroban auth trees cannot be inspected on-chain. Front-end/wallet validation remains defense-in-depth, not a substitute.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

- `UnlistedPoolRouter::execute_strategy` (lines 39-47) pulls `total_in`, invokes `route.hop_pool` — an address taken straight from the caller's `swap` bytes — and pays a fair `min_out` so all controller checks pass.
- `RogueHopPool::swap` (lines 62-71) calls `token.transfer(victim, attacker, amount)` on a wallet token the protocol never listed.
- The test (lines 194-227) asserts simulation records the stolen `transfer` as a child invocation under Alice's `swap_collateral` auth entry, and that enforcing mode executes it once signed: `assert_eq!(s.wallet(&s.alice), 0)` and `assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE)` while `supply_balance_raw(ALICE, "ETH") == FAIR_OUT_ETH`.

In production the same primitive holds via `swap_debt`, `multiply`, or `repay_debt_with_collateral`, since all funnel through the same unvalidated `swap` bytes.
