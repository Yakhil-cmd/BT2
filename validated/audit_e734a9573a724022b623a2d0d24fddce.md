### Title
Cross-repository Status forgery via `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup and missing repository check in `Status.replicate_from_github!` - (File: app/models/shipit/webhooks/handlers/status_handler.rb, app/models/shipit/status.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone, across **all** stacks in the database, instead of using the repository-scoped `stacks` helper that `Handler` provides and that other handlers use. Because `Status.replicate_from_github!(stack_id, github_status)` and `Commit#create_status_from_github!` never compare the webhook's `repository.full_name` against the target `Stack`'s `Repository`, a validly-signed webhook from an attacker-controlled repository can write a `Status` (e.g. a required CI context marked `success`) onto a completely different victim `Stack`, as long as a `Commit` record with the same `sha` exists under the victim stack.

### Finding Description
The broken binding, stated explicitly: the code should enforce `Commit#stack.repository.full_name == payload['repository']['full_name']` before creating a `Status`, but this equality is never checked anywhere in the call chain.

Path:
- `Shipit::WebhooksController#create` verifies the HMAC signature against the GitHub App configured for `repository_owner` [1](#0-0) , but this only proves the payload genuinely came from GitHub for *some* repository owned by that organization — it says nothing about which `Stack`/`Commit` rows the payload is allowed to affect.
- `Shipit::Webhooks::Handlers::Handler` exposes a repository-scoped helper, `stacks`, built from `Repository.from_github_repo_name(repository_name)` [2](#0-1) , which is the mechanism other handlers (e.g. pull-request handlers) rely on to scope their side effects to the correct repository.
- `StatusHandler#process`, however, ignores this scoping entirely and does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This matches every `Commit` row in the whole database with that `sha`, regardless of which `Stack`/`Repository` it belongs to.
- `Commit#create_status_from_github!` forwards `stack_id` (the *matched commit's own* stack id) with no repository comparison: `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) .
- `Status.replicate_from_github!` performs `find_or_create_by!(stack_id:, state:, description:, target_url:, context:, created_at:)` with zero repository/ownership validation [5](#0-4) .

Exploit flow: an attacker owns (or forks) a repository that is configured as a Shipit stack. If any commit sha exists identically in both the attacker's stack's `commits` table and a victim stack's `commits` table (a routine occurrence for forks/shared-history repos, or any commit the victim project shares with the attacker's own repo/branch history), the attacker triggers a genuine, correctly-signed GitHub `status` webhook from their own repository with `context` equal to the victim's `ci.require` entry (public in the victim's `shipit.yml`) and `state: success`. `verify_signature` passes because the payload is legitimately signed for the attacker's own org/repo. `StatusHandler#process` then matches **every** `Commit` row with that sha — including the victim's — and writes a `success` `Status` onto the victim stack's commit, potentially making it `deployable?` and triggering `schedule_continuous_delivery` / merges.

Existing guards do not stop this: `verify_signature` only authenticates "this payload came from GitHub for this org," not "this commit/stack belongs to this repository." `drop_unhandled_event`, `ExplicitParameters` schema validation, and model validations on `Status`/`Stack` do not check cross-repository ownership either.

### Impact Explanation
A payload originating from the attacker's own (unprivileged) repository directly mutates another tenant's `Stack`/`Commit` by forging a required CI `Status` (`state: success`) that the victim did not authorize. This can flip `Commit#deployable?` to `true` and trigger continuous delivery / merge scheduling on the victim stack (`app/models/shipit/commit.rb` `deployable?`, `schedule_continuous_delivery`). This is a cross-tenant write that can enable an unauthorized deploy — matching the "Critical: a payload for one repository mutating another's stack/commit ... an unauthorized deploy" category. It is repeatable against any victim stack for which the attacker can find/produce a matching commit sha, and scales across all repositories hosted by the same Shipit instance.

### Likelihood Explanation
Requires: (1) attacker controls a repository configured as (or able to trigger events for) a Shipit stack, so they can emit a validly-signed `status` webhook; (2) a `Commit` row with an identical `sha` exists in both the attacker's and victim's stacks — realistic for forks or repositories sharing git history/common ancestor commits, which is common in open-source ecosystems; (3) knowledge of the victim's `ci.require` context name, which is public via the victim's `shipit.yml`. No Shipit credentials, session, API token, or GitHub secrets are needed. The attack is cheap and repeatable (one webhook per attempt).

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository derived from the payload, using the same `stacks`/`Repository.from_github_repo_name` mechanism the base `Handler` already provides, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each { ... }`. Additionally, harden `Status.replicate_from_github!` (or `Commit#create_status_from_github!`) to assert that the target `Stack`'s `Repository.full_name` matches the webhook's `repository.full_name` before writing, so a mismatch raises rather than silently succeeding.

### Proof of Concept
Minitest plan (no live GitHub, matches the described "Attacker action"):
1. Create two `Repository`/`Stack` pairs: `victim_stack` (`full_name: "victim/repo"`, `ci.require` includes `"ci/travis"`) and `attacker_stack` (`full_name: "attacker/repo"`).
2. Create `Commit.create!(stack: victim_stack, sha: "deadbeef...")` and `Commit.create!(stack: attacker_stack, sha: "deadbeef...")` (same sha, simulating shared git history).
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha: "deadbeef..."`, `context: "ci/travis"`, `state: "success"`.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature verification, as permitted by "no live GitHub").
5. Assert: `victim_stack.commits.find_by(sha: "deadbeef...").statuses.where(context: "ci/travis", state: "success").exists?` is `true`, and `victim_stack.commits.find_by(sha: "deadbeef...").deployable?` is `true` — i.e., before the fix the equality `commit.stack.repository.full_name == payload['repository']['full_name']` (`"victim/repo" == "attacker/repo"`) is false yet the write still occurs, proving the missing binding check.
6. After applying the recommended fix, re-run and assert no `Status` is created on `victim_stack`'s commit (the equality is now enforced and the webhook is a no-op for that stack).
