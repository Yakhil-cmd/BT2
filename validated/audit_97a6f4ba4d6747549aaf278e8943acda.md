### Title
Unvalidated, non-signer `creator` account in `initialize_with_permission` allows setting `pool_creator` to an uncontrollable/zero address, permanently freezing accrued creator fees - (File: programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
`initialize_with_permission` accepts an arbitrary `creator` account with no `Signer` requirement and no address constraint, and stores it directly as `PoolState.pool_creator`. This value later gates both fee-collection instructions, so if it is set to `Pubkey::default()` (or any other address nobody controls), the accrued creator fees for that pool become permanently unclaimable while swaps keep accruing them.

### Finding Description
In `Initialize` (permissionless pool creation) the pool creator is a `Signer`, guaranteeing it is a real, controllable key: [1](#0-0) 

But in `InitializeWithPermission`, the analogous field is only an `UncheckedAccount` with no signer check and no `address =` constraint — the caller (`payer`) fully controls what value is used: [2](#0-1) 

The only gating check in this instruction is a `permission` PDA keyed to `payer`, not to `creator`: [3](#0-2) 

This `creator` key (whatever it is) is written straight into `PoolState.pool_creator` on initialization, with `enable_creator_fee = true`: [4](#0-3) [5](#0-4) 

Both fee-collection paths are then permanently gated by this stored value:
- `collect_creator_fee` requires the `creator` account to literally sign as `pool_state.pool_creator`: [6](#0-5) 
- `collect_creator_fee_permissionless` sends fees to an ATA whose authority is `pool_state.pool_creator`, with no signature required from that account: [7](#0-6) [8](#0-7) 

If `pool_creator` is set to `Pubkey::default()` (or any key for which no one holds the private key/authority), `collect_creator_fee` can never be signed for (impossible to produce a valid signature for the all-zero pubkey), and `collect_creator_fee_permissionless` will happily create an ATA owned by that unreachable address and route fees into it forever, with nobody able to move them out (spending from a token account requires the owner authority's signature). This mirrors the Lens bug class: an entity able to reach a "set config/module" path can supply a degenerate/zero value that is never validated, silently breaking a dependent code path (`collect`) for the lifetime of the object (post/pool).

### Impact Explanation
Every swap on such a pool continues to accrue `creator_fees_token_0`/`creator_fees_token_1` in `PoolState` (confirmed accrual logic exists in `swap_base_input.rs`/`swap_base_output.rs`/`curve/calculator.rs`), but those fees can never be withdrawn — this is a permanent freezing of protocol/creator funds inside the pool's vaults, satisfying the "permanent freezing of user or LP funds" bar. Unlike the Lens finding (loss of read/collect functionality on a single post), here real token value is locked indefinitely in on-chain vaults with no recovery path, since neither `collect_creator_fee` (needs an impossible signature) nor `collect_creator_fee_permissionless` (sends to an unspendable ATA) can retrieve it.

### Likelihood Explanation
Reaching `initialize_with_permission` requires only holding a `permission` PDA for the caller's own key (created once by an admin-controlled `create_permission_pda`), but once granted, the permissioned caller fully controls the `creator` field with zero additional validation — they can pass `Pubkey::default()`, a random unrelated pubkey, or an account with no known signer, either by mistake or deliberately. No admin action or extra validation intervenes at pool-creation time, and the freeze only becomes apparent after fees have already accrued via swaps, matching the External report's "acceptable but should be validated" risk profile (Medium).

### Recommendation
Constrain `creator` in `InitializeWithPermission` the same way as in `Initialize` (require it to be a `Signer`, or at minimum add `require_keys_neq!(creator.key(), Pubkey::default())`), and/or reject `Pubkey::default()` when writing `pool_creator` inside `PoolState::initialize`. Consider also validating that `creator` is not an account provably unable to sign (e.g., a PDA of another program) if that is a supported deployment target.

### Proof of Concept
1. Admin calls `create_permission_pda` for `payer` (the pool creator), granting it a `Permission` PDA.
2. `payer` calls `initialize_with_permission`, passing `creator = Pubkey::default()` (system-owned, no init needed since `creator` is just `UncheckedAccount`, not required to exist or sign) — the instruction succeeds, `pool_state.pool_creator = Pubkey::default()`, `enable_creator_fee = true`.
3. Users swap against the pool; `creator_fees_token_0`/`creator_fees_token_1` accumulate in `PoolState` per the fee-split logic in `curve/calculator.rs` and `swap_base_input.rs`/`swap_base_output.rs`.
4. Anyone calls `collect_creator_fee_permissionless`; it succeeds, creating an ATA with `authority = Pubkey::default()` and transferring the accrued fees into it.
5. No one can ever call `collect_creator_fee` (cannot sign as `Pubkey::default()`) nor spend from the ATA created in step 4 (its authority can't sign), so the transferred fees are permanently frozen.
