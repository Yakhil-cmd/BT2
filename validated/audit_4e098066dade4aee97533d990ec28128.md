### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but every handler acts on the (different) repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which configured GitHub organization's `webhook_secret` to HMAC-verify a webhook against using one JSON field of the payload (`repository.owner.login`, or `organization.login`), while every `Shipit::Webhooks::Handlers::Handler` subclass resolves which `Repository`/`Stack` to mutate using a *different* field of the very same payload (`repository.full_name`). Nothing ties these two fields together, so a party who legitimately controls the webhook secret for one Shipit-configured organization can forge a validly-signed payload that claims to originate from their own org while pointing the `repository.full_name` at a stack belonging to a completely different, unrelated organization also hosted on the same Shipit instance.

### Finding Description
`before_action :verify_signature` runs before the payload is dispatched to handlers: [1](#0-0) 

The organization used to select the verifying secret comes straight from the JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `GitHubApp`, each with its own independently configured `webhook_secret` (multiple orgs can be registered in the same Shipit instance): [3](#0-2) 

`GitHubApp#verify_webhook_signature` only proves that the raw body was signed with *that org's* secret - it makes no assertion about which repository inside the body the signer is authorized to speak for: [4](#0-3) 

Once the signature passes, `Shipit::Webhooks.for_event(event)` dispatches to handlers that all inherit the same repository-resolution logic, which uses a *separate* payload field: [5](#0-4) 

For example, `StatusHandler` writes a commit status directly from attacker-supplied fields with no additional authorization check tying the acted-upon repository back to the organization whose secret validated the request: [6](#0-5) 

`PushHandler` similarly resolves stacks purely from `repository.full_name` and triggers a sync: [7](#0-6) 

Both `repository.owner.login` (used for signature-secret selection) and `repository.full_name` (used for target-stack resolution) are ordinary, independently-settable keys inside the same signed JSON body - the HMAC only proves "this body was produced by someone holding org A's secret," not "the repository named inside this body belongs to org A." This is exactly the class of bug described in the referenced report: a value that determines *which principal's authority is checked* (deposit's slip adjustment / share basis) is decoupled from the value that determines *what the authority is spent on* (asset released), letting an attacker split the two so the check passes but the effect lands somewhere else.

### Impact Explanation
Any principal who can obtain (or is handed) a valid `webhook_secret` for **one** organization configured in this Shipit instance can forge events for **any other repository/stack** tracked by the same instance, regardless of organization:
- `StatusHandler` lets them write arbitrary `create_status_from_github!` commit statuses (state/description/context/target_url) for any commit sha in the victim organization's repositories. Since Shipit's `ci.require` deploy-gating relies on these `Status` rows, an attacker can forge a passing status to satisfy CI requirements and enable an otherwise-blocked deploy on a stack they have no legitimate access to.
- `PushHandler` lets them trigger `stack.sync_github` for a victim stack.
- The `PullRequest::*` handlers let them create/archive/unarchive review stacks belonging to a victim repository.

This is a cross-organization/cross-repository authorization bypass reachable purely by crafting a webhook payload with a mismatched `repository.owner.login` vs `repository.full_name`, satisfying the "unauthorized deploy" / "cross-repository writes" impact bar.

### Likelihood Explanation
Exploitation requires only knowledge of one org's `webhook_secret` already configured in the Shipit deployment - it does not require a Shipit session, an `ApiClient` token, or GitHub write access to the *target* repository. Multi-organization Shipit deployments (as shown by the sample secrets file listing `somegithuborg`/`someothergithuborg`) are an explicitly supported configuration, so the cross-org confusion is directly reachable in the documented deployment model, not a hypothetical misconfiguration.

### Recommendation
After verifying the HMAC signature, re-derive the organization the request is authorized for and require that `repository.full_name`'s owner segment (or `organization.login`) matches `repository_owner` exactly before dispatching to any handler; reject the webhook otherwise. Handlers should also independently confirm the resolved `Repository`'s owner matches the authenticated organization rather than trusting `full_name` unconditionally.

### Proof of Concept
1. Attacker legitimately administers `orgA`, one of several GitHub organizations configured in this Shipit instance, and thus knows/controls `orgA`'s `webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "sha": "<victim commit sha in orgB/target-repo>",
  "state": "success",
  "context": "required-ci-check",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `orgA`'s known `webhook_secret` over this exact raw body and POSTs it to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` computes `repository_owner == "orgA"`, fetches `orgA`'s `GitHubApp`, and the signature verifies successfully (attacker legitimately holds that secret).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!` for the commit belonging to `orgB/target-repo`, forging a passing CI status for a repository/organization the attacker does not control, potentially satisfying `ci.require` and enabling an unauthorized deploy on `orgB`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
