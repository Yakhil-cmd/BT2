Confirmed: `creator_fees_token_0`/`creator_fees_token_1` in `PoolState` accumulate on every swap via `update_fees` [1](#0-0) , are excluded from the tradable vault balance in `vault_amount_without_fee` [2](#0-1) , and are only zeroed out inside `collect_creator_fee`/`collect_creator_fee_permissionless` after the `transfer_from_pool_vault_to_user` CPIs succeed [3](#0-2) . The mint-extension allow-list in `is_supported_mint` only restricts extension types (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`) [4](#0-3)  but does not check or forbid a standard SPL/Token-2022 `freeze_authority` on the mint, which can freeze any token account for that mint (including the creator's ATA) independent of extensions.

### Title
Permissionless creator-fee collection can be permanently DoS'd by a frozen/blacklisted creator token account - (File: `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`)

### Summary
`collect_creator_fee_permissionless` is designed so "anyone can trigger the collection since the fee is always sent to the pool creator" [5](#0-4) , mirroring Notional's permissionless `settleVaultAccount` design. If the creator's destination token account (`creator_token_0`/`creator_token_1`) is or becomes frozen — via the mint's standard `freeze_authority` (not covered by the extension allow-list in `is_supported_mint`) — every call to this function reverts, permanently blocking fee collection.

### Finding Description
`transfer_from_pool_vault_to_user` performs a `token_2022::transfer_checked` CPI to the creator's ATA [6](#0-5) . Token-2022 (and legacy SPL Token) accounts can be frozen by the mint's `freeze_authority`, an account-state field independent of the extension list validated in `is_supported_mint` [4](#0-3) . Any transfer into a frozen account reverts unconditionally at the token-program level. Because `collect_creator_fee_permissionless`'s `creator_token_0`/`creator_token_1` accounts are pinned to the `pool_creator` recorded in `pool_state` [7](#0-6) , there is no way for a caller (or the creator) to redirect the payout to an unfrozen account, and there is no admin bypass path. `pool_state.creator_fees_token_0`/`creator_fees_token_1` are only reset to zero after the transfers succeed [8](#0-7) , so a persistently frozen creator account leaves these accrued fees stuck in the vault forever, with the instruction failing on every future invocation (both the permissioned `collect_creator_fee` and the permissionless variant share the identical failure mode).

### Impact Explanation
Accrued creator fees (which grow continuously from every swap through `update_fees`, and are excluded from swappable/withdrawable vault liquidity via `vault_amount_without_fee`) become permanently unclaimable once the creator's token account is frozen for either token. This is a permanent freeze of funds legitimately owed to the pool creator, with no recovery path in the program (no force-settle/bypass instruction exists).

### Likelihood Explanation
Requires only that the mint of token_0 or token_1 has (or later sets) a `freeze_authority` and that authority freezes the creator's associated token account — a routine capability of many real-world Token-2022/SPL tokens (e.g., regulated stablecoins) and not filtered by `is_supported_mint`'s extension check. No privileged action against the pool program itself is required; the freeze happens entirely at the token-program level and is outside the AMM's control once the pool exists.

### Recommendation
Add an admin/permissionless-safe fallback path that can credit stuck creator fees (e.g., write off to protocol fees, allow updating a destination account controlled by the creator with re-authentication, or wrap the transfer CPI so partial success doesn't block state reset), or explicitly document/reject mints with a set `freeze_authority` at `initialize`/`initialize_with_permission` time, similar to the existing extension allow-list in `is_supported_mint`.

### Proof of Concept
1. Create a pool with token_0 being a Token-2022 mint that has a `freeze_authority` set (this passes `is_supported_mint` since freeze authority isn't an extension type).
2. Perform swaps so that `creator_fees_token_0` accrues in `pool_state`.
3. Freeze the pool creator's ATA for token_0 using the mint's freeze authority.
4. Call `collect_creator_fee_permissionless` (or `collect_creator_fee`) — `transfer_from_pool_vault_to_user` reverts on the frozen destination, the instruction fails, and `creator_fees_token_0` is never reset; every subsequent call fails identically, permanently locking the creator's fees in the vault.

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```

```rust
pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
```
