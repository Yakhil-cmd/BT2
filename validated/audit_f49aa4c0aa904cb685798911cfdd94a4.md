Confirmed: this is a genuine authentication-binding break, matching exactly what the question describes.

### Title
`current_user` is derived from an unauthenticated `X-Shipit-User` request header, letting any authenticated API client (or unauthenticated caller under `disable_api_authentication`) impersonate an arbitrary Shipit user for Task/Deploy creation - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Shipit::Api::BaseController#identify_user` trusts the client-supplied `X-Shipit-User` header to resolve `current_user`, with no cryptographic binding between that header and the `ApiClient` token (or GitHub identity) that authenticated the request. Any caller possessing a valid `ApiClient` token for a stack (even one issued for an unrelated automation/bot with only `deploy:stack` scope) can set this header to a victim's login and have `Deploy`/`Task` objects created and attributed to that victim.

### Finding Description
The intended binding is: `current_user == identity of the caller who supplied the credential authenticating this request` (i.e., `current_user == ApiClient#creator` or equivalent verified GitHub identity). In the actual code: [1](#0-0) 

`authenticate_api_client` only verifies possession of an `ApiClient` token (via `ApiClient.authenticate`/`SimpleMessageVerifier`) or, when `Shipit.disable_api_authentication` is true, skips authentication entirely by issuing an `UnlimitedApiClient`. That authentication result is stored in `@current_api_client`, which is used only for permission scoping (`stack_id`, `check_permissions!`). Separately, `identify_user` reads `request.headers['X-Shipit-User']` verbatim and does `User.where('lower(login) = ?', user_login.downcase).first` — there is no signature, no check that this login corresponds to the token's `creator`, and no restriction requiring elevated privilege to set the header.

`current_user` (backed by `identify_user`) is then passed directly into task/deploy creation: [2](#0-1) [3](#0-2) 

`require_permission!`/`check_permissions!` in `ApiClient` only checks scope strings like `deploy:stack` against the token's `permissions` array — it never checks identity of the acting user: [4](#0-3) 

**Attack**: An attacker holding any valid `ApiClient` token with `deploy:stack` permission for a given stack (their own low-privilege bot token, or, in a misconfigured deployment, no token at all if `disable_api_authentication` is set) sends `POST /stacks/:id/deploys` with header `X-Shipit-User: victim-login` and a valid `sha`. `stack.trigger_deploy(commit, current_user, ...)` records the deploy as created/authorized by `victim-login`'s `User` record, with no proof that the victim initiated or approved it.

None of the listed guards intercept this: `verify_signature`/webhook signature checks are irrelevant (this is the API controller, not webhooks); `ExplicitParameters` only validates `sha`/`force`/`env` types, not the identity header; `force_github_authentication` and OAuth session flows govern the browser UI's `current_user`, not the API's; `User#authorized?`/`require_permission!` check GitHub team membership and scope strings respectively, but never validate that `X-Shipit-User` matches the authenticated principal.

### Impact Explanation
Any request authenticated merely by a low-privilege `ApiClient` token (or, in `disable_api_authentication` mode, any unauthenticated caller who can reach the host) can cause `Deploy`/`Task` records to be created and attributed to an arbitrary existing Shipit user by name, spoofing the acting identity used for deploy authorization and audit trail. This is repeatable per-request against any stack the token has `deploy:stack` permission for, and the spoofed identity can be any login present in the `User` table (e.g., an admin or team lead), effectively forging authorization provenance for deploys/rollbacks. This matches "Critical - unauthorized deploy" / identity-spoofing driving deploy authorization.

### Likelihood Explanation
Preconditions: attacker needs any valid `ApiClient` token scoped to `deploy:stack` (or `write:stack`) for a target stack — these are commonly issued to CI/bot integrations with lower trust than the humans they impersonate — or the host must run with `Shipit.disable_api_authentication = true` (documented as a footgun for `PUBLIC_API`/dev use, but present in `lib/shipit.rb` and referenced in `test/dummy/config/environments/development.rb`, showing it's a real supported configuration path). No secrets, signatures, or GitHub credentials are required beyond the low-privilege token already held. Cost is a single crafted HTTP header on an otherwise-legitimate authenticated request.

### Recommendation
Remove `identify_user`'s trust in the raw `X-Shipit-User` header. Bind `current_user` to the authenticated principal instead: derive it from `current_api_client.creator` (or a verified GitHub-authenticated session), or, if a client-supplied "acting user" is a required feature, require the `ApiClient` to carry an explicit, admin-provisioned mapping/allowlist of logins it's permitted to act as, and reject headers naming anyone else.

### Proof of Concept
```ruby
# test/controllers/api/deploys_controller_test.rb (conceptual addition)
test "X-Shipit-User header lets a low-privilege ApiClient impersonate an arbitrary victim user" do
  victim = shipit_users(:walrus) # some other, unrelated user record
  low_priv_client = shipit_api_clients(:some_bot_token_scoped_only_to_this_stack)

  authenticated_as(low_priv_client) do
    @request.headers['X-Shipit-User'] = victim.login
    post :create, params: { stack_id: @stack.to_param, sha: @commit.sha }
  end

  deploy = Shipit::Deploy.last
  # Broken binding demonstrated: current_user (== deploy.user) resolves to the
  # victim, despite the victim never authenticating this request.
  assert_equal victim, deploy.user
  refute_equal low_priv_client.creator, deploy.user
end
```
This demonstrates `current_user == victim` even though the only verified identity for the request is `low_priv_client` (and, transitively, `low_priv_client.creator`), proving the equality `current_user == authenticated request identity` is broken.

        @current_api_client = if Shipit.disable_api_authentication
                                UnlimitedApiClient.new

                                BasicAuth.authenticate(request) do |*parts|
                                  token = parts.select(&:present?).join('--')
                                  ApiClient.authenticate(token)

        headers['WWW-Authenticate'] = 'Basic realm="Authentication token"'

      def current_user

      end

      def identify_user

        User.where('lower(login) = ?', user_login.downcase).first if user_login
      end
