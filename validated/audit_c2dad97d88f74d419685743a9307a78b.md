### Title
CCMenu API token confused for scope — a token authorized for one `Stack` reads any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The external report describes a class of bug where a cryptographic authorization artifact (a signature/token) is checked for validity but the binding between "what the artifact authorizes" and "what it is actually used against" is broken, allowing the artifact to be reused outside its intended scope. In `shipit-engine`, `Shipit::Api::CCMenuController` reproduces this bug class: an `ApiClient` token that is scoped to a single `Stack` (via `ApiClient#stack_id`) is accepted by `CCMenuController`, but the controller resolves the target `Stack` directly from the request parameter instead of through the scoped lookup used everywhere else in the API, so the token's stack binding is never enforced.

### Finding Description
`Shipit::ApiClient` supports scoping a token to a single stack via the optional `stack` association [1](#0-0) . The base API controller enforces this scope by resolving stacks through a helper that filters by `current_api_client.stack_id`:

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This is the mechanism that binds "the stack(s) a token authorizes" to "the stack a request touches". Every other API controller inherits this `stack`/`stacks` method unmodified (e.g. `Shipit::Api::StacksController`, which is explicitly tested to enforce this scoping: "an api client scoped to a stack will only see that one stack") [3](#0-2) .

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoped lookup entirely, resolving the stack directly from the class:

```
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

The controller only checks `require_permission :read, :stack`, which validates the operation/scope string pair (`"read:stack"` is in `permissions`) but never checks the specific stack instance:

```
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [5](#0-4) 

So the only place that would have prevented cross-stack access — the `stacks` scoping in `#stack` — is exactly the method `CCMenuController` overrides. Because `authenticate_api_client` is also overridden to accept the token from a query-string `token` parameter (as designed for CCMenu clients embedded in URLs) [6](#0-5) , any holder of a stack-scoped `read:stack` token — for example a token deliberately minted for one stack via `CCMenuUrlController`/`ApiClientsController` — can pass a different `stack_id` in the URL and receive build/deploy status for a stack the token was never authorized for.

**Binding broken (equality that should hold but doesn't):**
`stack(s) authorized by ApiClient token` == `stack acted on by the request`

Before the fix path exists elsewhere (`StacksController`, `TasksController`, etc.) this equality holds because they all use `stacks.from_param!`. In `CCMenuController` it does not hold, because `stack` resolves via the unscoped `Stack.from_param!`.

### Impact Explanation
This lets a party holding a legitimately-issued, stack-scoped read token silently read the deploy/build status (name, activity, last build status/label/time, web URL) of any other stack on the Shipit instance, not just the one it was authorized for. This is a cross-tenant/cross-repository unauthorized read of stack state — matching the in-scope "High" impact category "unauthenticated [i.e., authorization-scope-violating] read of stack state, task streams or deploy output." No repository write access, session, or privileged account is required beyond possessing one legitimately-scoped `read:stack` token, which multiple stacks/teams on a shared Shipit instance may independently possess (e.g. via the self-service `CCMenuUrlController#fetch` endpoint that any authenticated Shipit user can trigger for a stack they can view) [7](#0-6) .

### Likelihood Explanation
High. `CCMenuController#stack` is reachable directly via the public `api/ccmenu` route with only `token` and `stack_id` as parameters, requires no prior privileged action beyond having one valid `read:stack`-scoped token (a routine, low-privilege artifact intentionally distributed for CI-status widgets), and the fix (`stacks.from_param!`) is a one-line divergence from the pattern used by every sibling controller, making this an easy-to-miss regression that is trivial to exploit once noticed.

### Recommendation
Remove the `stack` override in `CCMenuController`, or change it to resolve through the scoped `stacks` helper (`stacks.from_param!(params[:stack_id])`) exactly as `BaseController` and its other subclasses do, so the `ApiClient#stack_id` scope is enforced consistently for every endpoint, including CCMenu.

### Proof of Concept
1. Create two stacks, `stack_a` and `stack_b`.
2. Mint (or have minted, e.g. via `CCMenuUrlController#fetch`) an `ApiClient` token scoped to `stack_a` with permission `read:stack` (see fixture `here_come_the_walrus`, which is `stack: shipit`, `permissions: [read:stack]`) [8](#0-7) .
3. Call `GET /api/stack_b/ccmenu.xml?token=<stack_a's token>` (or the equivalent `Api::CCMenuController#show` route with `stack_id=stack_b`).
4. Observe the request succeeds and returns `stack_b`'s CI/build status, even though the token's `ApiClient.stack_id` is `stack_a`'s id and `check_permissions!` never inspects which stack is being accessed — contrast with the equivalent call against `Api::StacksController#show` for `stack_b`, which is correctly rejected because it resolves through `stacks.from_param!` and returns nothing for a stack outside the client's scope, as validated in `test/controllers/api/stacks_controller_test.rb:217-223`.
