### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while the acted-upon repository is selected from the independent `repository.full_name` field, enabling cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit supports per-organization GitHub App configuration, where `Shipit.github(organization:)` resolves a distinct webhook secret for each configured organization [1](#0-0) . The webhook controller selects *which* organization's secret to verify the HMAC signature against using `repository.owner.login` (falling back to `organization.login`) pulled straight out of the unauthenticated JSON body, before the signature has been checked [2](#0-1) [3](#0-2) . Once verification succeeds, every handler resolves the target `Stack`/`Repository` to act on using a *different* field of the same payload: `repository.full_name` [4](#0-3) . Nothing ties `repository.owner.login` to `repository.full_name`, so the field whose organization authenticates the request is not the field that determines which repository's stacks get written to.

### Finding Description
The binding that should hold is:
`organization that authenticated the webhook (repository.owner.login / organization.login used to pick the HMAC secret)` == `repository whose stacks are looked up and mutated (repository.full_name)`

Before the pull request/attack sequence (legitimate flow): a GitHub webhook for `acme-org/app` has `repository.owner.login == "acme-org"` and `repository.full_name == "acme-org/app"`. `verify_signature` selects `acme-org`'s configured webhook secret and validates the HMAC over the raw body [5](#0-4) . `Handler#repository_name` independently reads `repository.full_name` to find matching stacks [6](#0-5) . In the legitimate case both fields agree, so the check appears to authorize acting on that repository.

After the attack: an attacker who controls (or is a member of) any organization onboarded to this multi-tenant Shipit instance — call it `attacker-org` — knows `attacker-org`'s legitimate webhook secret (or can trigger a real webhook delivery for one of their own repos and replay/modify it before delivery is verified, since the signature covers only the raw bytes, not a semantic binding between `owner.login` and `full_name`). They construct/forge a `push` (or `status`, `check_suite`) payload where:
- `repository.owner.login` = `"attacker-org"` (or `organization.login` = `"attacker-org"`) → selects `attacker-org`'s secret, so `verify_webhook_signature` returns `true` since they computed the HMAC with a secret they know [7](#0-6) .
- `repository.full_name` = `"victim-org/victim-repo"` → an entirely different, unrelated repository they do not own.

`WebhooksController#create` dispatches this payload to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack/branch [8](#0-7) . This forges a GitHub-authenticated push notification for `victim-org/victim-repo` despite the cryptographic signature only proving control of `attacker-org`'s secret, not of `victim-org`'s repository.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding explicitly called out as in-scope. A tenant of a multi-organization Shipit deployment can forge sync/status/check-suite events for stacks belonging to repositories under a completely different organization they do not control — a cross-repository write of GitHub-derived state (last deployed SHA tracking, commit statuses, check-suite refreshes, PR merge-queue state) driven by attacker-supplied data instead of the real owning organization's GitHub App. This matches the Critical impact category "cross-repository writes."

### Likelihood Explanation
Requires the attacker to be onboarded as (or compromise) any single organization configured in the Shipit instance with a known/derivable webhook secret for that organization — an "unprivileged attacker" relative to the victim organization's repositories, satisfying the required boundary crossing. No `ApiClient` token, GitHub App private key, or repository write access to the victim repo is needed; only knowledge of one's own org's webhook secret, which by design an org admin can see/regenerate.

### Recommendation
Bind the two fields together before trusting the payload: after `verify_webhook_signature` succeeds using `repository_owner`, assert that `repository.full_name`'s owner segment equals the same `repository_owner`/`organization.login` value used for verification, rejecting the request (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the same organization identity that was used to select the signing secret rather than an independently-trusted `full_name` field.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` and `victim-org`, each with its own `github_apps`/`webhook_secret` entry.
2. As a member of `attacker-org`, retrieve/know `attacker-org`'s webhook secret (or observe a real delivery to compute `sha1=`).
3. Build a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac(attacker-org secret, body)>`.
5. `POST /github/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and passes [5](#0-4) .
6. `PushHandler.process` runs against stacks of `victim-org/victim-repo` [8](#0-7) , triggering `sync_github(expected_head_sha: "<attacker chosen sha>")` on a repository the attacker never had signature-verified authority over.

Note: I could not fully confirm within the available context how `github_apps`/multi-organization secrets are declared in `lib/shipit.rb` (the file's full contents were not indexed), so the exact configuration keys for per-org webhook secrets are inferred from `GitHubApp.new(organization, config)` and `Shipit.github(organization:)` usage in `lib/shipit/github_app.rb` and `app/controllers/shipit/webhooks_controller.rb`. If a given deployment only configures a single global GitHub App/secret (no per-organization secrets), this specific cross-organization signature-selection weakness would not be exploitable, though the underlying lack of binding between `repository.owner.login`/`organization.login` and `repository.full_name` would remain a latent design flaw activated as soon as multi-org support is used.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** app/controllers/shipit/webhooks_controller.rb (L24-49)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
