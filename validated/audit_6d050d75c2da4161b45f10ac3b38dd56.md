No vulnerability found for this question.

The external report concerns application-level Solidity coding practice (using `transfer()`/`send()` with the EVM's 2300-gas stipend vs. `call()`), which is a guideline for smart-contract authors, not a protocol-level defect. Investigating `pallet-revive`, the runtime already implements and deliberately tests this exact EVM semantic: the 2300-gas stipend is detected via a heuristic and enforced with `ReentrancyProtection::AllowNext` in `run_call` in [1](#0-0) , and the same handling is applied for host-function calls in `call_evm` in [2](#0-1) . This preserves Ethereum's stipend-based reentrancy guarantee even though revive's gas scale differs from Ethereum's, as documented in [3](#0-2) .

Dedicated test fixtures (`Stipends.sol`) and Rust tests (`stipends.rs`) explicitly verify that `transfer()`/`send()` calls to complex/reentrant receivers correctly fail or are blocked, matching real Solidity/EVM behavior: [4](#0-3)  and [5](#0-4) . This is the opposite of the reported issue — the underlying platform correctly and intentionally reproduces the stipend/reentrancy protection semantics rather than exposing a broken analog. There is no FRAME pallet, XCM, or Substrate primitive path where a `transfer()`-vs-`call()` pattern maps to a genuine unauthorized dispatch, fund loss, or DoS through the required entry points (signed extrinsic, permitted XCM execute, or public proof submission). The finding is scoped to Solidity contract-author guidance, not to `polkadot-sdk` production/runtime code, so no analog vulnerability applies.
