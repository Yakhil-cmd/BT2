### Title
Unlocked "ununique" of private-asset conflicting inputs races with the global write lock, enabling a stable-output double-spend - ([File: validation.js])

### Summary
The CVE describes `unix_stream_sendpage()` mutating a peer's `recv` skb queue without taking the queue lock that protects the same structure elsewhere, so a concurrently running garbage-collection path can free the skb while it is being accessed, corrupting shared state. The reachable ocore analog is `validatePaymentInputsAndOutputs()`'s double-spend acceptance branch in `validation.js`, which mutates the shared `inputs`/`units` rows for private-asset conflicts under a *different*, narrower mutex (`"private_write"`) than the one (`"write"`) that guards all other unit persistence and stability transitions in `writer.js`.

### Finding Description
When a double-spend is detected for a **public** asset input, the "ununique" SQL is deferred and queued into `objValidationState.arrAdditionalQueries`, to be executed later inside `writer.saveJoint()` under the global `"write"` mutex lock: [1](#0-0) 

But for **private** assets, the code takes a *separate* lock, `mutex.lock(["private_write"], ...)`, and runs the `UPDATE inputs SET is_unique=NULL ...` query immediately, independent of whatever unit is currently being written under the `"write"` lock: [2](#0-1) 

`writer.saveJoint()` — the function responsible for actually persisting units, computing `sequence`, updating `is_stable`/`is_free`, and mutating the in-memory caches (`storage.assocUnstableUnits`, `assocStableUnits`, `assocBestChildren`, etc.) — acquires the `"write"` mutex key, not `"private_write"`: [3](#0-2) [4](#0-3) 

Because `"private_write"` and `"write"` are disjoint mutex keys (`mutex.js` locks only serialize callers holding the *same* key set), a private-asset double-spend "ununique" UPDATE against the `inputs`/`units` tables can execute concurrently with a `writer.saveJoint()` transaction that is simultaneously reading or writing the very same rows (e.g. while determining `sequence`, `is_stable`, or while another unit's `checkForDoublespends()` is evaluating the current `is_unique` state of competing inputs for the same asset). This is structurally the same class of bug as CVE-2023-4622: a shared, spend-uniqueness-critical resource is mutated outside the lock that other code paths rely on to treat it as consistent, opening a window where one path observes a transitional/inconsistent state of `inputs.is_unique` / `units.sequence`.

### Impact Explanation
`inputs.is_unique` and `units.sequence` are the fields that ocore uses to decide whether a unit's spend is the "good" (final) branch of a double-spend or a "final-bad" loser. A race here can let two conflicting private-asset spends be evaluated using stale/interleaved uniqueness data across concurrently-running validations, so both units can transiently be accepted as sequence `good`, or a unit's sequence can be resolved inconsistently between the in-memory validation state and the persisted DB state for the input it consumes. Since `checkForDoublespends`'s query (`sequence!='final-bad'`) is precisely the read that decides whether a competing spend is treated as live, a race window here maps directly to acceptance of a second, conflicting spend of the same private-asset output before/while the correct loser is marked `final-bad` — i.e. a double-spend of what should become a stable output, which is one of the explicitly listed unauthorized-impact outcomes.

### Likelihood Explanation
Reachability requires only two ordinary asset transactions on the same private asset, from a single unprivileged unit poster or a private-payment counterparty, that spend conflicting inputs and arrive to the node close together in time — no privileged or peer-trust position is needed, matching the CVSS local/no-privilege character of the original bug. The trigger condition (two overlapping validations of the same asset's conflicting inputs) is exactly the kind of concurrency the original code comment ("`--- will ununique the conflicts of unit`") is trying to serialize, but does so on the wrong lock key, so the race is a direct byproduct of the existing code path rather than a hypothetical scenario.

### Recommendation
Serialize the private-asset double-spend "ununique" UPDATE under the same `"write"` mutex key used by `writer.saveJoint()` (or otherwise make it part of the same critical section/transaction as unit persistence), instead of the disjoint `"private_write"` key, so that no other writer/validator can observe or mutate `inputs.is_unique` / `units.sequence` for the same rows concurrently.

### Proof of Concept
1. Post two units, `U1` and `U2`, from a wallet holding a private asset, each spending the same private-asset output (a genuine double-spend pair), to two different full nodes or via two rapid successive submissions to the same node.
2. Node processes `U1`: `validatePaymentInputsAndOutputs()` detects a private-asset doublespend candidate, acquires `mutex.lock(["private_write"])`, and issues the `UPDATE inputs SET is_unique=NULL ...` for the conflicting older input rows, then releases the lock immediately (line 2283-2296 of `validation.js`) — independent of whether `writer.saveJoint()` for some other unit currently holds the `"write"` lock.
3. Concurrently, `writer.saveJoint()` for a different unit that reads/writes the same `inputs`/`units` rows (e.g. computing `sequence` for a unit sharing an author/asset) is mid-transaction under `"write"`.
4. Because the two operations use different mutex keys, they can interleave: the `UPDATE` from step 2 can commit between reads performed inside the `"write"`-locked transaction, producing an inconsistent view of which spend is unique, allowing the node to record `sequence='good'` for both `U1` and `U2` in different code paths before consistency is restored.
