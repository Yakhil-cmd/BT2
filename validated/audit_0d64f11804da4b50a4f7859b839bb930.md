The reported bug concerns `RoyaltyModule.sol`/`IpNFT.sol` — Solidity contracts for an NFT royalty/derivative-minting system that do not exist in this repository. The only royalty-related code found is the OpenZeppelin `ERC2981` fixture used as a test contract for `pallet-revive`, which is a static per-token royalty registry with no parent-token minting, no royalty-share summation, and no "terms update" call that could be frontrun. [1](#0-0) 

The closest FRAME analog, `pallet-nfts`'s `mint`/`do_mint` and `update_mint_settings`, has no cross-token royalty-splitting logic and no parent/derivative revenue-sharing model at all. [2](#0-1) [3](#0-2) 

Even setting aside the missing analog, the report describes a pure front-running/economic manipulation scenario (an owner changing terms before a pending transaction executes), which the scan method explicitly instructs to reject regardless of domain. There is no comparable "terms" mutable-before-inclusion primitive combined with a revenue-split invariant in this codebase to map the root cause onto, and no signed-extrinsic/XCM/contract entry point in scope exhibits the same missing check (accepting stale/frontrun-able parameters without binding them to the transaction).

			item: T::ItemId,
