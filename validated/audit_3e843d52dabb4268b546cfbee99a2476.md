### Title
Webhook event authenticated against attacker-chosen organization can write to any repository's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify a webhook against using an attacker-controlled field from the *unauthenticated* request body, while the event handlers that actually mutate state (create commits/statuses, sync branches, archive/unarchive review stacks, create teams/users) key off a *different* attacker-controlled field from the same body. These two fields are never checked for consistency, and `verify_webhook_signature` trivially returns `true` whenever the selected organization has no `webhook_secret` configured.

### Finding Description
`verify_signature` resolves the organization used for signature verification purely from the JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository','owner','login')` (falling back to `organization.login`) — both are plain fields inside the raw, unauthenticated JSON POST body. This value picks which `GitHubApp` config (and thus which `webhook_secret`) is used to verify the `X-Hub-Signature` header: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when the resolved organization's `webhook_secret` is blank — i.e. no cryptographic check occurs at all for that org:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
In multi-organization deployments (a documented, supported configuration — see `secrets.development.example.yml` / `secrets.development.shopify.yml`, both of which ship `webhook_secret: # nil` as example values), `Shipit.github_app_config(organization)` looks up a *per-organization* config by name taken straight from the payload: [4](#0-3) 

Meanwhile, every event handler resolves the repository/stack to mutate using a *separate* field, `repository.full_name`, from the same untrusted body — with no cross-check against `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

The equality that should hold but doesn't: `organization used to authenticate the payload == owner of the repository whose stack is written`. An attacker can submit `repository.owner.login = "org-with-no-webhook-secret"` (bypassing the HMAC check entirely, since `verify_webhook_signature` short-circuits to `true`) while setting `repository.full_name = "victim-org/victim-repo"` to target any repository/stack actually tracked by the Shipit instance — for any of the built-in handlers (`push`, `pull_request` open/close/label, `status`, `check_suite`, `membership`): [8](#0-7) 

This exactly mirrors the reported smart-contract bug class: a counter/authorization is scoped to one identity (`ethWithdrawn`/org secret) while the mutating operation is applied to a different, unaccounted pool (shares/another repository) because the two were never bound together.

### Impact Explanation
This breaks the deployment-trust binding "organization authenticated versus the repository that is written" with no credentials, session, or webhook secret required for the "unset-secret" organization slot. Concretely an unauthenticated attacker can, for any repository tracked by the instance:
- Forge `push` events to trigger `stack.sync_github(expected_head_sha: ...)`, spoofing what Shipit believes is the current HEAD of the branch (feeding into deploy eligibility decisions).
- Forge `pull_request` `closed`/`opened`/`labeled` events to archive/unarchive/create review stacks for repositories they don't control.
- Forge `status`/`check_suite` events to inject fake CI statuses, which stacks use to gate `deployable?`/merge-queue decisions (`allows_merges?`), potentially enabling an unauthorized deploy or merge on the real repository.
- Forge `membership` events to create arbitrary GitHub teams/users records inside Shipit.

Because CI status / check-suite spoofing directly feeds `Stack#deployable?` and `#allows_merges?`, this can escalate to an unauthorized deploy or merge, matching the "High" impact bar in scope (escalation into authorization state / unauthenticated read-write of stack state).

### Likelihood Explanation
High, but conditioned on deployment configuration: it requires the multi-organization GitHub App configuration mode (`Shipit.github_default_organization` present) and at least one configured organization with a blank/unset `webhook_secret`. The example configuration files shipped in this repository (`secrets.development.example.yml`, `secrets.development.shopify.yml`) explicitly model `webhook_secret: # nil` as a normal/expected value per organization, indicating this is not a contrived misconfiguration but a documented default state operators are likely to leave for at least one org while other orgs are protected. No GitHub session, `ApiClient` token, or `webhook_secret` knowledge is needed by the attacker — only the ability to send an arbitrary HTTP POST to the public `/github/webhooks` endpoint.

### Recommendation
- Require `webhook_secret` to be present and enforce signature verification for every configured organization; refuse (422) instead of allow-through when `webhook_secret` is blank in multi-org mode.
- Bind the field used to select the verification key to the field used to resolve the target repository: verify that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting mismatches.
- Consider deriving the target repository strictly from the same verified identity used for signature selection, rather than trusting a second, independently-supplied JSON field.

### Proof of Concept
1. Configure Shipit in multi-org mode with two orgs: `victim-org` (has `webhook_secret` set) and `empty-org` (no `webhook_secret`, e.g. left as the documented `webhook_secret: # nil`).
2. `victim-org/victim-repo` is a tracked Shipit stack.
3. Attacker, with no credentials, POSTs to the webhooks endpoint (`config/routes.rb` mounts `Shipit::WebhooksController#create`) with:
   - Header `X-Github-Event: pull_request`
   - Header `X-Hub-Signature: sha1=anything` (arbitrary, unverifiable)
   - Body: `{"action":"closed", "number":1, "pull_request": {...}, "repository": {"owner": {"login": "empty-org"}, "full_name": "victim-org/victim-repo"}, "sender": {"login":"attacker"}}`
4. `verify_signature` resolves `repository_owner` = `"empty-org"`, loads its `GitHubApp` config, finds `webhook_secret` blank, and `verify_webhook_signature` returns `true` unconditionally — request proceeds.
5. `ClosedHandler#process` resolves `repository` via `params.repository.full_name = "victim-org/victim-repo"` and calls `review_stack.archive!`, mutating the victim's actual tracked repository/stack despite the request never having been authenticated by `victim-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
