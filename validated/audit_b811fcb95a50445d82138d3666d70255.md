### Title
Webhook signature verified against `repository.owner.login`'s org while the acted-upon repository is read from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` picks which GitHub App/organization's webhook secret to verify a signature against using one field of the JSON body, but every handler that actually mutates state resolves the target `Repository`/`Stack` from a *different* field of the same attacker-controlled body. In a multi-organization deployment these two fields are never cross-checked, so a forged payload can authenticate as an organization with no (or a weaker) webhook secret while writing to a stack that belongs to a completely different, protected organization.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` instance — and therefore the HMAC secret used to validate `X-Hub-Signature` — via `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`): [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank: [3](#0-2) 

This is a documented, supported configuration: the setup docs and fixtures explicitly show `webhook_secret` left empty per-organization in a multi-app config (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`), and Shipit natively supports many organizations sharing one instance via `Shipit.github(organization:)`: [4](#0-3) [5](#0-4) 

However, once the request passes (or is exempted from) that check, `WebhooksController#create` hands the *entire* parsed body to every registered handler for the event, unfiltered by organization: [6](#0-5) 

Every handler resolves the `Repository`/`Stack` it will act on from `payload.dig('repository', 'full_name')`, a field never compared against the `repository.owner.login` used for signature verification: [7](#0-6) 

For example, `PushHandler` looks up matching, not-archived stacks purely from that `repository_name` and immediately calls `stack.sync_github`: [8](#0-7) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the mutated repository) are read independently from the same attacker-supplied JSON, an attacker can set them to different values. This breaks the trust binding: `organization authenticated by signature == organization of the repository being written`.

### Impact Explanation
An attacker who knows (or can determine, e.g. from `docs/setup.md` defaults or an intentionally-unconfigured secondary org) that at least one configured GitHub organization has no `webhook_secret` set can craft a webhook body where `repository.owner.login` = that unsecured org (so `verify_webhook_signature` auto-passes) and `repository.full_name` = `"<protected-org>/<real-stack-repo>"`. The forged, unsigned request is then processed by handlers exactly as if it originated from the protected organization's GitHub App: `PushHandler` triggers `sync_github` for that stack, `commit_status`/`check_suite` handlers can flip commit status/CI state used to gate deploys, and `pull_request` handlers can drive merge-queue behaviour — all for a repository outside the organization whose signature was actually checked. This crosses the "organization that authenticated versus the repository that is written" boundary called out in scope and can lead to spoofed CI status enabling an unauthorized deploy/merge on a stack the attacker does not control.

### Likelihood Explanation
Exploitability requires only an unauthenticated HTTP POST to the public `/webhooks` endpoint (no session, API token, or GitHub write access needed) and knowledge that at least one configured organization in the multi-app setup has `webhook_secret` unset — a state the project's own example configs and docs show as normal/supported. Single-organization Shipit deployments (the common case) are not affected, since there `repository_owner` and the acted-upon repository are inherently the same org; this is specific to the documented multi-organization configuration.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), require that the organization used to select the verifying `GitHubApp`/secret matches the owner embedded in `repository.full_name`; reject the webhook (422) on mismatch. Alternatively, have handlers derive the repository strictly from the same `repository.owner.login` value already validated for signing, rather than independently trusting `repository.full_name`.

### Proof of Concept
1. Deploy Shipit with a multi-org GitHub App config where `OrgA.webhook_secret` is unset and `OrgB` (containing a real, tracked stack, e.g. `orgb/prod-app`) has a strong secret — mirroring the shipped example in `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or any garbage signature), body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "orgb/prod-app" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (absent/invalid) signature — see `lib/shipit/github_app.rb:76-83`.
4. `WebhooksController#create` dispatches to `PushHandler`, which resolves the stack via `repository.full_name = "orgb/prod-app"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and triggers `stack.sync_github` for OrgB's stack, despite the request never being validated against OrgB's secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
