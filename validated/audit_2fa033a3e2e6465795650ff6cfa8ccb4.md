### Title
Membership webhook privilege-escalation via organization/team binding never revalidated - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to check the HMAC against based on an **attacker-controlled, pre-verification** field of the JSON body (`repository.owner.login` / `organization.login`), while the actual state-mutating handler (`MembershipHandler`) trusts a *different* field of the same unverified body (`team.id`) to look up and mutate an **existing** `Team` record without ever re-checking that the team truly belongs to the organization whose secret validated the request.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and its `webhook_secret`) to validate against using a value taken straight from the still-unverified JSON payload: [1](#0-0) [2](#0-1) 

Per Shipit's own multi-org config schema, `webhook_secret` is an **optional** field — nil/blank is valid and, when unset, `verify_webhook_signature` short-circuits to `true` for *any* signature (including none at all): [3](#0-2) [4](#0-3) 

This means any organization configured in `secrets.github` without a `webhook_secret` becomes a fully unauthenticated entry point into `/webhooks`: an attacker only needs to set `organization.login`/`repository.owner.login` in the payload to that unsecured org's name to sail through `verify_signature` — no `webhook_secret`, `api_clients_secret`, session, or GitHub App key required.

Once past that gate, `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler`, which never re-derives or re-checks the organization used for verification. It trusts `params.team.id` (attacker-supplied) to find/mutate a `Team`, and `params.member.login` (attacker-supplied, can be the attacker's own GitHub login) to add that user as a member: [5](#0-4) 

`Team.find_or_create_by!(github_id: params.team.id)` only assigns `team.organization = params.organization.login` inside the creation block — if a `Team` row with that `github_id` **already exists** (which it will for any real, currently-authorized team), the existing record is fetched as-is and `team.add_member(member)` runs unconditionally: [6](#0-5) 

Team membership is exactly what gates application authorization: [7](#0-6) [8](#0-7) 

This is the same bug class as the OS-SYM-ADV-01/OS-SYM-ADV-02 report: a value that gates a validation decision (`repository_owner` used to pick the signing secret) diverges from the value the downstream instruction actually mutates state on/with (`team.id`/`organization.login` used by `MembershipHandler` to write a `Membership` row), with no cross-check binding the two. The equality that should hold — "organization whose secret authenticated the request == organization the write actually affects" — is never enforced.

### Impact Explanation
An attacker who can name any Shipit-configured organization that lacks a `webhook_secret` (a documented, valid configuration state, not a misconfiguration bug) can add themselves — or anyone — to any existing authorized `Team`, satisfying `User#authorized?` and `Shipit.github_teams`. This is a full authentication-bypass/privilege-escalation into the deployment app: the resulting authorized session lets the attacker trigger deploys, rollbacks, and merges. This matches the "escalation into `Shipit.github_teams` authorization" High-impact category, and arguably rises to unauthorized-deploy territory once inside.

### Likelihood Explanation
`/webhooks` is a public, unauthenticated endpoint by design (it must accept unauthenticated GitHub deliveries). The only gate is `verify_signature`, and the org-selection logic reads from unverified payload content before any cryptographic check occurs. Multi-org Shipit deployments where at least one configured org intentionally omits `webhook_secret` (explicitly supported per the example config) make this trivially exploitable with a single crafted POST; no credentials, GitHub App key, or session are needed.

### Recommendation
- Never let attacker-controlled payload fields determine which `webhook_secret`/organization is used to verify the signature; the organization context should come from an authenticated/route-bound source, not `params.dig('repository', 'owner', 'login')` picked up before verification.
- Make `webhook_secret` mandatory (fail closed) rather than allowing `verify_webhook_signature` to return `true` when absent.
- In `MembershipHandler#find_or_create_team!`, always validate that an existing `Team`'s `organization` matches `params.organization.login` (and that this organization matches the one that authenticated the webhook) before performing `add_member`/`delete` mutations; reject if they diverge.

### Proof of Concept
1. Operator configures Shipit with two orgs in `secrets.github`: `org-a` (no `webhook_secret` set) and `org-b` (properly secured, and whose team `T` with `github_id: 999` is listed in `Shipit.github_teams`, granting deploy access to `org-b`'s Shipit stacks).
2. Attacker (no credentials at all) POSTs directly to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Deployers", "slug": "deployers", "url": "https://x" },
  "organization": { "login": "org-a" },
  "member": { "login": "attacker-github-handle" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "org-a")`; since `org-a` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally — request passes with no valid `X-Hub-Signature` needed.
4. `MembershipHandler#process` runs: `Team.find_or_create_by!(github_id: 999)` finds the existing `org-b` team `T` (ignoring that the request "authenticated" as `org-a`), and calls `team.add_member(User.find_or_create_by_login!("attacker-github-handle"))`.
5. Attacker logs into Shipit via normal GitHub OAuth as `attacker-github-handle`; `current_user.authorized?` now returns `true` because they belong to `T`, one of `Shipit.github_teams` — full access to `org-b`'s stacks, deploys, and rollbacks granted, despite never authenticating against `org-b`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
