## Analysis

Root cause found: `Shipit::Api::CCMenuController` re-implements stack lookup in a way that breaks the "stack a token authorizes" vs. "stack it touches" binding that `BaseController` otherwise enforces.

`Api::BaseController` scopes every stack lookup to the current `ApiClient`'s authorized stack when one is set: [1](#0-0) 

But `Api::CCMenuController` overrides `#stack` to bypass that scoping entirely, resolving the stack straight from the request param against the whole `Stack` table: [2](#0-1) 

`ApiClient` supports being scoped to a single stack via its `stack_id` column, and `BaseController#stacks` is the only place enforcing that scope: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. `CCMenuController#stack` never consults `stacks`/`current_api_client.stack_id`, so any valid `read:stack` token — even one deliberately scoped to a single stack (`stack_id` set, as in fixture `here_come_the_walrus`) — can hit `/api/stacks/:stack_id/cc.xml` with a different `stack_id` and read that unrelated stack's deploy/build status. [3](#0-2) 

### Title
Stack-scoped API tokens can read the CI/deploy status of any stack via CCMenu, bypassing per-stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` resolves the target stack via `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!(params[:stack_id])` used everywhere else in `Api::BaseController`. This breaks the binding "stack a token authorizes == stack it touches": an `ApiClient` created with `stack_id` set (i.e., authorized to touch only that one stack) is still permitted, by `require_permission :read, :stack`, to fetch `#show` for any other stack in the installation simply by changing the `stack_id` route/query parameter.

### Finding Description
`Api::BaseController#stacks` is the mechanism the engine relies on to enforce that a stack-scoped `ApiClient` can only see its own stack:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
`CCMenuController` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) shadows this with:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This resolves against the unscoped `Stack` relation, so `current_api_client.stack_id` is never consulted. The only guard left is `require_permission :read, :stack`, which just checks the token has the string permission `read:stack` — it says nothing about which stack. The controller also supports authenticating via a bare `?token=` query parameter (`authenticate_api_client` override), which is how such tokens are normally distributed for CI-status widgets, making this endpoint the most exposed one for this class of token.

### Impact Explanation
A token minted for one stack (e.g. via `CCMenuUrlController#client`, which creates an `ApiClient` scoped to a specific stack with only `read:stack` permission — `app/controllers/shipit/ccmenu_url_controller.rb:15-18`) can be replayed against `/api/stacks/:owner/:repo/:env/cc.xml` for any other stack in the Shipit installation, returning that stack's build/deploy status (last build result, lock state, running deploy) — data the token was never authorized to see. This is an unauthorized read of stack state that crosses the token's authorization boundary, matching the "unauthenticated/unauthorized read of stack state" class of impact.

### Likelihood Explanation
CCMenu tokens are specifically designed to be shared/embedded (CI dashboard widgets, IDE plugins) since they're passed as a plain URL query parameter rather than via `Authorization` headers, so they are the token type most likely to leak or be observed. Exploiting the gap only requires knowing/guessing another stack's `stack_id` param (owner/repo/environment path segments), which are non-secret identifiers visible in the UI/URLs.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `Api::BaseController` (i.e., call `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so a stack-scoped `ApiClient` cannot resolve stacks outside `current_api_client.stack_id`.

### Proof of Concept
1. Create/obtain a CCMenu `ApiClient` scoped to Stack A (`stack_id: A.id`, permissions `['read:stack']`) — this is exactly what `CCMenuUrlController#client` does per-stack.
2. Call `GET /api/stacks/:owner_b/:repo_b/:env_b/cc.xml?token=<stack-A-token>` using Stack B's path params instead of Stack A's.
3. `authenticate_api_client` accepts the token (valid signature via `ApiClient.authenticate`); `require_permission :read, :stack` passes (`read:stack` is present); `stack` resolves Stack B via unscoped `Stack.from_param!`, and Stack B's build/deploy status is rendered — despite the token being authorized only for Stack A.
