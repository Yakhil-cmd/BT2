### Title
Webhook signature verification keys off `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` / bare commit `sha` — allowing an attacker with valid webhook credentials for *any* onboarded GitHub organization to inject fabricated commit statuses (and other webhook effects) into *any other org's* stacks — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using the payload field `repository.owner.login` (or `organization.login`) [1](#0-0) [2](#0-1) . However, the event handlers that subsequently act on the same payload look up the *actual* repository/commit to mutate using a completely different, unverified field — `repository.full_name` in `Handler#repository_name`/`#stacks` [3](#0-2) , or, in the case of `StatusHandler`, a bare `sha` with **no repository scoping at all** [4](#0-3) . Because Shipit supports multiple independently configured GitHub organizations, each with its own `webhook_secret` [5](#0-4) , the "organization whose secret authenticated the request" and "the repository/commit that is actually written to" are never checked for equality.

### Finding Description
The binding that should hold is:
`organization authenticated by verify_signature == owner of the repository/commit acted upon by the handler`

`verify_signature` computes `repository_owner` from the payload and fetches the corresponding `GithubApp` instance solely to validate the signature:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event)` dispatches the *entire raw payload* to handlers, which never re-derive or cross-check `repository.owner.login` — they instead use `repository.full_name` (`Handler#repository_name`) [3](#0-2)  to resolve the `Repository`/`Stack`. Nothing forces `full_name.split('/').first == repository.owner.login`.

Worse, `StatusHandler` — which materializes CI status information used for deploy/merge gating — does not consult the repository at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 
It matches by SHA globally across the entire Shipit installation's `commits` table, regardless of which org's webhook secret validated the request.

An attacker who legitimately controls (or has compromised) the webhook secret for **one** organization configured on the Shipit instance (e.g., they are the GitHub org admin who installed the App for Org A, granted per `docs/setup.md`) can craft a signed `status` webhook whose `repository.owner.login = "orgA"` (so it passes `verify_signature`) but whose `sha` matches a commit belonging to `orgB`'s stack, or whose `repository.full_name = "orgB/some-repo"` for push/pull_request-class events. The verified organization (Org A) and the organization/repository actually mutated (Org B) are never checked to be equal.

### Impact Explanation
This breaks the deployment-trust boundary between tenants of a single Shipit instance: an org that is legitimately onboarded (and thus possesses a valid `webhook_secret`) can forge webhook effects against repositories belonging to a *different, unrelated* organization also hosted on the same instance. Concretely:
- Fabricate a passing/failing commit status on an arbitrary commit SHA in another org's stack via `StatusHandler`, which feeds into deployability/merge-queue gating decisions (`Commit#create_status_from_github!`) [4](#0-3) .
- Force `GithubSyncJob`/check-run refresh cycles on another org's stack via `PushHandler`/`CheckSuiteHandler` by supplying a `repository.full_name` pointing at that org's stack while authenticating with the attacker's own org's secret [7](#0-6) [8](#0-7) .
- Manipulate another org's `PullRequest`/review-stack state (archive/unarchive, label capture) via the `pull_request` handlers, which likewise trust `params.repository.full_name` without checking it against the org that authenticated the request [9](#0-8) [10](#0-9) .

This constitutes a cross-organization/cross-repository write in a multi-tenant Shipit deployment — one org's authenticated identity is used to mutate another org's tracked state, potentially influencing merge/deploy readiness signals for repositories the attacker does not control.

### Likelihood Explanation
Requires only that the attacker already holds (or can obtain) a valid `webhook_secret` for *some* organization onboarded to the shared Shipit instance — a normal, expected credential for any org admin who installs the Shipit GitHub App, not a privileged Shipit account, `ApiClient` token, or `GITHUB_TOKEN`. In any deployment where Shipit is shared across multiple independent GitHub organizations (as explicitly supported by the multi-org secrets format), this is directly reachable by any of those orgs against any of the others.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after determining `repository_owner` from the payload, enforce that every handler's target repository (`repository.full_name`'s owner segment, or the resolved `Commit`'s stack's repository owner in `StatusHandler`/`CheckSuiteHandler`) matches the authenticated `repository_owner`. Reject (422) any payload where these disagree, and update `StatusHandler` to scope its `Commit` lookup by repository rather than a bare, installation-wide `sha` match.

### Proof of Concept
Conceptual (multi-org Shipit instance with `orgA` and `orgB` both configured, each with distinct `webhook_secret`, `orgB` having a tracked stack/commit with sha `S`):
1. Attacker controls the GitHub App installation/webhook secret for `orgA` only.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
   ```json
   { "sha": "S", "state": "success", "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/whatever" } }
   ```
   signed with `orgA`'s `webhook_secret`.
3. `verify_signature` resolves `Shipit.github(organization: "orgA")` and accepts the signature (valid for `orgA`) [1](#0-0) .
4. `StatusHandler#process` runs `Commit.where(sha: "S")` — matching the commit that actually belongs to `orgB`'s stack — and creates a fabricated status on it [4](#0-3) , despite the request never being authenticated for `orgB`.

Note: I could not fully trace how `Commit#create_status_from_github!` feeds into `Stack#mergeable?`/merge-queue automatic merge logic within this scan (that logic lives largely in `app/models/shipit/commit.rb`, `app/models/shipit/stack.rb`, and `app/jobs/shipit/process_merge_requests_job.rb`, which I only located by filename and did not read in full) — I recommend a follow-up review of those files to confirm the exact downstream consequence of an injected cross-org commit status (e.g., whether it can directly trigger an unauthorized merge/deploy) before finalizing severity.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```

module Shipit
  module Webhooks
    module Handlers
      class CheckSuiteHandler < Handler
        params do
          requires :check_suite do
            requires :head_sha, String
            requires :head_branch, String
          end

        def process
          stacks.where(branch: params.check_suite.head_branch).each do |stack|

          end
        end
      end
    end
  end
