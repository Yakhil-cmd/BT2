#No Vulnerability found for this question.

**Why the claimed exploit path does not work:**

1. **A `FunctionCallPermission` key can never authorize a `Transfer` action.** `verify_function_call_permission` (in `runtime/runtime/src/verifier.rs`) requires the transaction to contain exactly one action and that action must be `Action::FunctionCall`; any other action type (including `Transfer`) is rejected with `InvalidAccessKeyError::RequiresFullAccess` before any fee/allowance logic runs. [1](#0-0) 

2. **The malformed `receiver_id` produced under `AccountIdValidityRulesVersion::V0` cannot be exploited via receiver mismatch either.** Under V0, `read_and_parse_account_id` accepts an unvalidated string via `AccountId::new_unvalidated`, which is stored verbatim in `FunctionCallPermission.receiver_id` when the AddKey action is executed. [2](#0-1) [3](#0-2) 
But when the access key is later used to sign a transaction, `verify_function_call_permission` does an **exact string comparison** between `tx.receiver_id()` (which is always a validly-parsed `AccountId`) and `function_call_permission.receiver_id`. A malformed string (containing characters that can never appear in a valid `AccountId`) can never equal a legitimate `tx_receiver`, so any attempt to use the key against a real account fails with `ReceiverMismatch` before any allowance is charged or gas/fee computation for the target receiver occurs. [4](#0-3) 

3. **Fee computation for the AddKey action itself does not depend on `fc.receiver_id` at all.** The exec/send fee for `add_function_call_key_base`/`add_function_call_key_byte` is computed from `method_names` byte length only (see `promise_batch_action_add_key_with_function_call` in `logic.rs`), not from the (possibly malformed) `receiver_id` string. For the related gas-key variant, the byte-fee even explicitly uses `self.ext.get_receipt_receiver(receipt_idx)` (the real, validated receiver of the enclosing receipt), never `fc.receiver_id`. [5](#0-4) [6](#0-5) 

4. **`Transfer` fee computation (`transfer_exec_fee`/`transfer_send_fee`) is keyed off the receipt's actual (validated) receiver's account type**, obtained via `self.ext.get_receipt_receiver(receipt_idx)` in `promise_batch_action_transfer`, entirely independent of any `FunctionCallPermission.receiver_id` string — so there is no code path where a Transfer's gas/fee accounting is computed "against a different (attacker-normalized) receiver" derived from the AddKey permission. [7](#0-6) 

Given (1) Transfer actions are categorically rejected for function-call-permission-signed transactions, and (2)/(3)/(4) there is no code path linking the (possibly malformed) `FunctionCallPermission.receiver_id` string to any fee/allowance computation for a Transfer, the described metering-bypass/under-charging scenario is not reachable. The only real consequence of the V0 unvalidated-receiver behavior (which is intentionally preserved for legacy compatibility and tightened via V1/V2, per the comment in `validate_access_key_permission`) is that such a key becomes practically unusable — it cannot match any valid `receiver_id` in future transactions. [8](#0-7)

    tx: &Transaction,

    let Some(Action::FunctionCall(function_call)) = tx.actions().get(0) else {

    fn read_and_parse_account_id(&mut self, ptr: u64, len: u64) -> Result<AccountId> {
        let buf = get_memory_or_register!(self, ptr, len)?;
        self.result_state.gas_counter.pay_base(utf8_decoding_base)?;
        self.result_state.gas_counter.pay_per(utf8_decoding_byte, buf.len() as u64)?;

        let account_id_str = String::from_utf8(buf.into_owned()).map_err(|_| HostError::BadUTF8)?;

        match self.config.limit_config.account_id_validity_rules_version {
            near_primitives_core::config::AccountIdValidityRulesVersion::V0
            | near_primitives_core::config::AccountIdValidityRulesVersion::V1 =>
            {
                #[allow(deprecated)]
                Ok(AccountId::new_unvalidated(account_id_str))

            near_primitives_core::config::AccountIdValidityRulesVersion::V2 => account_id_str
                .parse()
                .map_err(|_| VMLogicError::HostError(HostError::InvalidAccountId)),
