### Title
Cross-org webhook signature verification bypass via `repository.owner.login`/`repository.full_name` mismatch reaching `AssignedHandler` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used for HMAC verification solely from `params.dig('repository','owner','login')`, while `AssignedHandler` (and other handlers) resolve the target `Repository`/`Stack`/`PullRequest` solely from `params.repository.full_name`. Because these two fields are independently attacker-controlled in the same JSON body and are never cross-checked, an attacker can pick a "no-secret" org for signature verification while pointing `full_name` at a repository belonging to a completely different, secret-protected org.

### Finding Description
The broken binding: the equality that should hold is `org_used_for_signature(repository.owner.login) == org_that_owns(repository.full_name)`. The code never enforces this.

- `repository_owner` is read as `params.dig('repository', 'owner', 'login')` [1](#0-0) .
- `verify_signature` fetches the `GitHubApp` for that owner and checks the signature against it: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)` [2](#0-1) .
- Critically, `GitHubApp#verify_webhook_signature` returns `true unless webhook_secret` — i.e., if the selected organization has no `webhook_secret` configured, signature verification is skipped entirely and any payload is accepted: [3](#0-2) .
- Once verification passes, `create` dispatches the raw JSON body to all handlers for the event, with no re-derivation of the owner: [4](#0-3) .
- `AssignedHandler#repository` resolves the target repo using `params.repository.full_name` only — completely independent of `repository.owner.login`: [5](#0-4) .
- `AssignedHandler#pull_request` then looks up a persisted `Shipit::PullRequest` joined through `stack -> repository` matching that `repository.id`, and `process` updates it: [6](#0-5) .

Exploit flow: attacker crafts a `pull_request` webhook body with `action: "unassigned"`, `repository.owner.login: "no-secret-org"` (an org configured in Shipit with no `webhook_secret`, e.g. a personal/free-tier org), and `repository.full_name: "victim-org/victim-repo"` (a repository actually tracked by Shipit under a different, secret-protected org). They send it to `POST /webhooks` with `X-Github-Event: pull_request` and any `X-Hub-Signature` value (or omit it) — since `no-secret-org` has no secret, `verify_webhook_signature` returns `true` unconditionally regardless of the signature header. The request passes `verify_signature`, then `AssignedHandler` resolves `victim-org/victim-repo`'s `Repository` record by `full_name` and updates the matching `PullRequest`'s `github_pull_request` JSON blob.

Existing guards fail because: `verify_signature` and the handler's repository resolution use two different, uncorrelated fields from the same payload; there is no check anywhere in this path that the org used for signature verification matches the org that owns the `full_name` repository. `GithubOrganizationUnknown` handling only protects against unknown/unconfigured owners, not against an owner that legitimately has no secret. `ExplicitParameters` schema for `AssignedHandler` only requires `repository.full_name` to be a `String`, with no ownership cross-validation [7](#0-6) .

### Impact Explanation
An attacker who controls (or registers) any GitHub org with no `webhook_secret` configured in Shipit can forge webhook events that mutate `PullRequest` records belonging to any other tracked repository/org, without ever possessing that other org's secret. This is a cross-tenant state manipulation: one org's (attacker's) unauthenticated payload writes another org's persisted records. While `AssignedHandler` only mutates `github_pull_request` metadata (not deploy actions), the same signature-selection flaw generically applies to any handler that trusts `repository.full_name` independently of `repository.owner.login` (e.g., push/status handlers), making the blast radius broader than just PR assignee metadata — the root cause is an authentication-bypass class issue at the controller level, matching "forged webhook accepted" and "payload for one repository mutating another's record" in the Critical impact category.

### Likelihood Explanation
Preconditions: Shipit must have at least one configured GitHub org/app with no `webhook_secret` set (this is a supported, documented configuration state, not a misconfiguration Shipit rejects), and the victim org's repository must be tracked in Shipit under a different org. The attacker needs zero credentials — no Shipit session, no API token, no webhook secret for any org — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted JSON body. This is trivially repeatable against any tracked repository as long as one no-secret org exists in the Shipit deployment.

### Recommendation
In `WebhooksController`, verify that the organization used to validate the signature is the same organization that owns the resolved `repository.full_name` (or, more robustly, resolve the target `Repository`/`Stack` first and use its bound org/secret for verification, rejecting payloads where `full_name`'s owner differs from `repository.owner.login`). Additionally, do not treat a missing `webhook_secret` as an automatic verification pass for organizations that own repositories tracked elsewhere; require an explicit secret for every configured org, or fail closed if `full_name`'s namespace doesn't match `repository_owner`.

### Proof of Concept
minitest (integration or controller test), no live GitHub:

```ruby
test "cross-org owner/full_name mismatch lets no-secret org forge writes to another org's PullRequest" do
  # Setup: configure "no-secret-org" with no webhook_secret, and "victim-org" with a secret.
  # victim_repo belongs to victim-org and has a tracked Stack + persisted PullRequest (number: 42).

  no_secret_org_app = Shipit::GitHubApp.new('no-secret-org', {}) # no webhook_secret
  Shipit.stubs(:github).with(organization: 'no-secret-org').returns(no_secret_org_app)

  body = {
    action: 'unassigned',
    number: 42,
    pull_request: {
      id: 1, number: 42, url: 'https://api.github.com/...', title: 't',
      state: 'open', additions: 1, deletions: 1,
      head: { sha: 'abc', ref: 'feature' },
      user: { login: 'attacker' },
      assignees: [],
      labels: []
    },
    repository: {
      full_name: 'victim-org/victim-repo', # points at the OTHER org's tracked repo
      owner: { login: 'no-secret-org' }    # used ONLY for signature verification
    },
    sender: { login: 'attacker' }
  }.to_json

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # arbitrary/invalid, irrelevant since no secret

  pr = shipit_pull_requests(:victim_pr) # belongs to victim-org's stack/repository

  assert_changes -> { pr.reload.updated_at } do
    post :create, body:, as: :json
  end

  assert_response :ok
  # Assert the binding is broken: verification org != mutated record's owning org
  assert_equal 'no-secret-org', JSON.parse(body).dig('repository', 'owner', 'login')
  assert_equal 'victim-org', pr.stack.repository.owner
end
```

Both sides of the equality (`no-secret-org` used for verification vs `victim-org` whose record was mutated) diverge, confirming the invariant is broken.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
