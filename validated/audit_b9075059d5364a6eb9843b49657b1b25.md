### Title
Forged `pull_request:assigned` webhook verified against a no-secret organization's config lets an attacker mutate an unrelated repository's `PullRequest` record - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used to authenticate a webhook based solely on the attacker-controlled `repository.owner.login` field, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's config has a blank `webhook_secret`. Because the handler that actually mutates state (`AssignedHandler`) resolves its target repository/stack from the same JSON body's `repository.full_name` field — with no requirement that it match the org used for verification — an attacker can pick a "no-secret" org purely to bypass HMAC verification while pointing the payload at a completely different, unrelated, and normally-protected repository's `PullRequest`.

### Finding Description
The broken binding: the code assumes `verifying_org(repository.owner.login) == target_repository_org(repository.full_name)`, but nothing enforces this equality.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and fetches `Shipit.github(organization: repository_owner)` to verify the signature [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` returns `true` immediately if that org's `@webhook_secret` is blank [3](#0-2) , and `@webhook_secret` is set from `@config[:webhook_secret].presence` at construction [4](#0-3) . Test fixtures show this is a realistic configuration (`"webhook_secret": null`) [5](#0-4) .
3. Once verification passes, `Shipit::Webhooks.for_event(event)` handlers are invoked with the raw, attacker-controlled `params` [6](#0-5) .
4. `AssignedHandler#process` looks up the `PullRequest` to mutate using `params.repository.full_name` via `Repository.from_github_repo_name` [7](#0-6)  — an entirely separate JSON field from `repository.owner.login` used in step 1, with no cross-check between the two.
5. `Repository.from_github_repo_name` simply splits the string and does a DB lookup by owner/name [8](#0-7) , so it will happily resolve to any repository/stack configured in Shipit, regardless of which org's secret was used to authenticate the request.
6. `AssignedHandler#process` then calls `pull_request.update(github_pull_request: params.pull_request)` [9](#0-8) , persisting attacker-supplied data (title, state, additions/deletions, assignees, labels, head sha/ref) onto a `PullRequest` record belonging to a repository/stack the attacker never authenticated against.

Exploit: attacker crafts a `pull_request` webhook body with `X-Github-Event: pull_request`, `action: "assigned"`, `repository.owner.login = "no-secret-org"` (an org present in Shipit's `secrets.github` config but with `webhook_secret` unset/blank), and `repository.full_name = "victim-org/victim-repo"` (an unrelated, real, protected stack in Shipit). No `X-Hub-Signature` is required since `webhook_secret` is blank for `no-secret-org`. `verify_signature` passes; `AssignedHandler` then finds and updates the `PullRequest` for `victim-org/victim-repo` using entirely attacker-controlled JSON.

None of the existing guards stop this: `drop_unhandled_event` only checks the event type exists, `ExplicitParameters` only validates field presence/types (not cross-field consistency), and there is no code anywhere that asserts `repository.owner.login` (used for signature selection) matches the org embedded in `repository.full_name` (used for the actual mutation).

### Impact Explanation
An attacker with no Shipit credentials can write/overwrite fields of a `PullRequest` record (title, state, additions/deletions, head SHA/ref, assignees, labels) belonging to any repository/stack configured in Shipit, as long as any single org anywhere in the Shipit deployment is misconfigured without a `webhook_secret`. This is a "payload for one repository mutating another's stack" scenario — a cross-tenant authentication/authorization bypass. Because `PullRequest#github_pull_request` data can influence downstream stack behavior (merge/PR status display, potentially affecting deploy eligibility logic depending on integration), this is repeatable indefinitely and affects every repository/stack in the Shipit instance, not just the misconfigured org's own repositories. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the Shipit deployment must have at least one org entry in `secrets.github` with a blank/missing `webhook_secret` (a real, documented, and seen-in-fixtures misconfiguration state, not a contrived one), and the endpoint `POST /webhooks` must be internet-reachable (standard for GitHub webhook receivers). No authentication, tokens, or knowledge of any secret is required — the attacker only needs to know (a) that such an org exists in the multi-org config and (b) the `owner/name` of the victim repository, both of which are typically public/discoverable (GitHub org/repo names are public). Cost is a single unauthenticated HTTP POST, fully repeatable.

### Recommendation
Enforce that the organization used to select/verify the webhook signature is the same organization embedded in the payload's `repository.full_name` (and `organization.login`), rejecting the request (422) on mismatch, before dispatching to handlers. Additionally, treat a blank/missing `webhook_secret` as a hard configuration error (fail closed, e.g. raise or reject all webhooks for that org) rather than silently accepting any payload unconditionally in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
minitest plan (under `test/controllers/webhooks_controller_test.rb`, no live GitHub required):
1. Configure the dummy secrets so `Shipit.github(organization: 'no-secret-org')` config has `webhook_secret: nil` (mirrors `test/dummy/config/secrets.test.json`).
2. Create a victim `Shipit::Repository` (`owner: 'victim-org', name: 'victim-repo'`), a `Shipit::Stack` on it, and a `Shipit::PullRequest` with `number: 42`, `title: 'original title'`.
3. Assert binding before: `pull_request.reload.title == 'original title'`.
4. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and JSON body:
   ```json
   {
     "action": "assigned",
     "number": 42,
     "pull_request": {
       "id": 1, "number": 42, "url": "...", "title": "PWNED",
       "state": "open", "additions": 1, "deletions": 1,
       "head": {"sha": "abc", "ref": "abc"},
       "user": {"login": "attacker"},
       "assignees": [{"login": "attacker"}],
       "labels": []
     },
     "repository": {"owner": {"login": "no-secret-org"}, "full_name": "victim-org/victim-repo"},
     "sender": {"login": "attacker"}
   }
   ```
5. Assert response is `200 OK` (verification passed, not `422`).
6. Assert binding after: `pull_request.reload.title == 'PWNED'` — proving the record for `victim-org/victim-repo`, never authenticated by any secret belonging to `victim-org`, was mutated using the `no-secret-org` config's unconditional `true` signature verification.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
