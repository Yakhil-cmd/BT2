### Title
Webhook signature check is keyed by an attacker-controlled organization field while the write path is keyed by a different, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` picks the GitHub App/secret used to verify the HMAC signature using `repository_owner`, a value read straight out of the *unauthenticated* JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The event handlers, however, resolve the actual `Repository`/`Stack` to mutate using a *different* field from that same unauthenticated body: `payload.dig('repository','full_name')`. Because multi-org Shipit deployments allow some organizations to have no `webhook_secret` configured, and `GitHubApp#verify_webhook_signature` treats a blank secret as "verification not required," an attacker can pick an org with no secret for the verification step while pointing `repository.full_name` at any other, fully-protected repository/stack, causing the signature check to succeed for content it never actually authenticated.

### Finding Description
The binding that is broken is: **organization that authenticated == repository that is written**.

- `verify_signature` derives the app/secret to check against from a field taken directly from the raw JSON payload before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` intentionally bypasses the HMAC check entirely when the resolved app has no `webhook_secret` configured: [3](#0-2) 

- Multi-org configuration explicitly supports organizations without a secret (`github_app_config`/`github_organizations` allow per-org configs, and nothing forces every org to define `webhook_secret`): [4](#0-3) 

- After "verification" passes (or is skipped), the actual event handler resolves which `Repository`/`Stack` to write to using a *separate* field of the same untrusted payload, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

Because `repository_owner` (used to select the signing organization) and `repository.full_name` (used to select the repository actually acted upon) are two independent, attacker-supplied fields of the same unsigned JSON body, nothing enforces that they refer to the same GitHub repository/organization. An attacker who knows (or guesses) that org `X` in the Shipit deployment has no `webhook_secret` configured (this is visible/discoverable, e.g., via the "unknown organization" 422 log message pattern, or simply by trial) can submit a forged webhook where `repository.owner.login` / `organization.login` = `X` (secret-less org, so `verify_webhook_signature` returns `true` unconditionally) while `repository.full_name` = `owner-with-secret/protected-repo`. The signature check "succeeds" (because it was never performed), and the handler proceeds to act on `protected-repo`'s `Stack` — e.g., enqueuing a `GithubSyncJob`, updating commit statuses, closing/merging pull requests via the `PullRequest::ClosedHandler`, or archiving review stacks — for a repository the attacker never had any GitHub credential for.

### Impact Explanation
This crosses the "unauthorized deploy/rollback/merge" boundary called out in scope: forged `pull_request` closed events can trigger `review_stack.archive!` for a real, unrelated stack; forged `status`/`check_suite`/`push` events can force `GithubSyncJob`/`RefreshCheckRunsJob` runs or manipulate commit statuses that gate the merge queue and continuous deployment (`schedule_merges_if_necessary`), indirectly enabling unauthorized deploys on stacks belonging to organizations the attacker never proved control over. No `ApiClient` token, GitHub App private key, or repository write access is required — the attacker only needs to know that at least one configured Shipit organization has no `webhook_secret`.

### Likelihood Explanation
Requires a specific misconfiguration precondition (at least one org configured without `webhook_secret` while others are protected), which is plausible in real multi-tenant Shipit deployments incrementally onboarding organizations, and the vulnerable code path (`repository_owner` vs `repository.full_name` divergence) is unconditionally reachable by any unauthenticated POST to the webhooks endpoint.

### Recommendation
Verify the webhook signature using the same repository/organization identity that the handler subsequently uses to select the `Stack` (i.e., derive both from `repository.full_name`, not independently from `repository.owner.login`/`organization.login`), and require that every configured organization define a non-blank `webhook_secret` — remove or make configurable-but-opt-in the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature` so a missing secret cannot silently authorize other organizations' payloads.

### Proof of Concept
1. Configure Shipit with two orgs: `secured-org` (has `webhook_secret` set, owns stack `secured-org/prod-app`) and `open-org` (no `webhook_secret` configured, e.g. left blank during onboarding).
2. POST to `/webhooks` with header `X-Github-Event: pull_request` and body:
```json
{
  "action": "closed",
  "number": 1,
  "pull_request": { "id": 1, "number": 1, "url": "...", "title": "x", "state": "closed",
    "additions": 0, "deletions": 0,
    "head": { "sha": "deadbeef", "ref": "feature" },
    "user": { "login": "attacker" }, "assignees": [], "labels": [] },
  "repository": { "full_name": "secured-org/prod-app", "owner": { "login": "open-org" } },
  "sender": { "login": "attacker" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "open-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` without checking any HMAC.
4. `Shipit::Webhooks.for_event('pull_request')` handlers run, resolving `repository` via `params.repository.full_name = "secured-org/prod-app"` and calling `review_stack.archive!` on the real, secured stack — despite the attacker never possessing `secured-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
