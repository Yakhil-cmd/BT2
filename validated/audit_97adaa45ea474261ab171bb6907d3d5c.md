### Title
Webhook signature verification selects the trust anchor from attacker-controlled payload fields, allowing cross-organization forgery of GitHub events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body. The handlers that then act on the request (`Webhooks::Handlers::Handler#repository_name`, `PushHandler`, and especially `StatusHandler`) read *other* fields from that same body (`repository.full_name`, `sha`) to decide what to write, without ever checking that those fields belong to the organization whose secret validated the signature. This reproduces the audited bug class exactly: the signature is valid for the bytes it covers, but a value that materially changes the meaning/target of the action ("which org/repo this event is about") is not bound by that signature and can be swapped by anyone who legitimately controls one tenant's secret.

### Finding Description
The verification flow is:

```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0)

**The broken binding, as an equality that fails:**
`organization whose webhook_secret authenticated the request` ≠ `repository/commit that the handler actually mutates`.

Nothing ties `repository.owner.login` (used to pick the HMAC key) to `repository.full_name`/`sha` (used to select what gets written). Both are attacker-supplied JSON fields inside the same signed payload, so a signer for Org A can freely set the "acted-upon" fields to point at Org B's tracked repository/commit, exactly as the RFX report describes fields (`nonce`, `expiry`) that are not covered by the signature and can be freely substituted.

### Impact Explanation
Any party who legitimately possesses the `webhook_secret` for **one** GitHub organization configured on a shared, multi-tenant Shipit deployment (`docs/setup.md`'s "Using Multiple Github Applications" section, `Shipit.github_organizations`) [8](#0-7)  can:

1. Craft a JSON body with `repository.owner.login = "OrgA"` (so `verify_signature` uses OrgA's `webhook_secret`, which the attacker knows) while setting `repository.full_name` / `sha` to point at a repository or commit belonging to `OrgB`, an unrelated tenant on the same instance.
2. Sign the raw body with OrgA's secret — a fully valid `X-Hub-Signature`.
3. POST it to `/webhooks`. `verify_signature` passes because the HMAC does match OrgA's key over the raw bytes.
4. The dispatched handler acts on OrgB's data: `StatusHandler` writes an arbitrary commit status (`create_status_from_github!`) on any matching commit in the entire instance, and/or `PushHandler` triggers `GithubSyncJob`/`sync_github` on OrgB's stacks.

This is a cross-repository write across an organizational trust boundary that the multi-org webhook design is supposed to enforce (each org's App/secret is meant to only speak for its own repos). Since Shipit stacks commonly gate deploys on commit status checks, forging a passing status for a target commit in another tenant's repository can influence deploy-safety checks for that tenant — a concrete cross-tenant integrity break reachable by an unprivileged party who only has legitimate access to a different org's webhook configuration.

### Likelihood Explanation
Requires Shipit to be configured with more than one GitHub organization sharing the instance (an explicitly documented and supported configuration, `docs/setup.md`), and requires the attacker to know a `webhook_secret` for at least one of the configured organizations (a secret they may legitimately hold as an admin of that org's GitHub App, without any privilege inside the target org). No GitHub App private key, no `GITHUB_TOKEN`, no Shipit session or API token is needed — only crafting an HTTP POST with a correct HMAC for a secret the attacker already has.

### Recommendation
After selecting the `webhook_secret` by `repository_owner`, verify that every organization-identifying field used later by handlers (`repository.full_name` owner segment, `organization.login`, etc.) is consistent with the same `repository_owner`/organization that validated the signature, and reject the webhook otherwise. Alternatively, scope `Commit`/`Repository`/`Stack` lookups in every handler by the authenticated organization instead of trusting `repository.full_name` unconditionally, and change `StatusHandler` to filter `Commit.where(sha:)` further by the commit's repository owner matching the verified organization.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org schema). Track a repo/stack for `OrgB` (e.g. `OrgB/secret-repo`) and a commit with `sha = S` that some deploy depends on for its status checks.
2. As an attacker who only administers `OrgA`'s GitHub App (and thus knows OrgA's `webhook_secret`), build a `status` event body:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/secret-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and validates successfully against OrgA's secret [9](#0-8) .
5. `StatusHandler#process` then runs `Commit.where(sha: "S").each { |c| c.create_status_from_github!(params) }` [6](#0-5) , writing a forged "success" status on `OrgB`'s commit `S`, despite the attacker never having had any credential tied to `OrgB`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
