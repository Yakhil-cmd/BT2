### Title
Content-Type-based JSON trust bypasses escape-sequence guarding in `gh api`, allowing raw non-JSON bytes to reach the terminal unsanitized - ([File: pkg/cmd/api/api.go])

### Summary
`processResponse` classifies a response as JSON solely by matching the `Content-Type` header against `jsonContentTypeRE`, without ever validating that the body is actually well-formed JSON. When `isJSON` is true and color output is not active, the body is streamed via a plain `io.Copy` (bypassing `iostreams.CopyGuardedContent` and its own `SetContentSanitization(false)` call), so an attacker-controlled host that labels an arbitrary raw body as JSON can smuggle terminal escape/OSC sequences straight to the victim's terminal.

### Finding Description
`apiRun` disables the `ContentOut` sanitizer for the whole command with a comment asserting "JSON is sanitized by the transport, ... only a raw non-JSON body needs neutralizing": [1](#0-0) 

In `processResponse`, the JSON/non-JSON decision is made purely from the response header: [2](#0-1) 

The guarding logic only runs `CopyGuardedContent` when `!isJSON`; whenever `isJSON` is true (and neither `--jq`/`--template` nor color output applies), the body is copied verbatim with a bare `io.Copy`, with no escape-sequence or binary check at all: [3](#0-2) 

Because `jsonContentTypeRE` (`[/+]json(;|$)`) only inspects the `Content-Type` string and never parses the body, a host the victim points `gh api` at (custom `--hostname`/`GH_HOST`, or any endpoint under attacker control) can return a response whose `Content-Type` matches this regex (e.g. `application/json`) while the body is arbitrary bytes containing raw ANSI/OSC escape sequences instead of valid JSON. This reaches the `io.Copy(bodyWriter, responseBody)` branch untouched: `SetContentSanitization(false)` means `ContentOut` also performs no sanitization, and `CopyGuardedContent`'s `ContainsEscapeSequence`/binary checks are never invoked for this branch. Only when output is colorized does `jsoncolor.Write` attempt to tokenize the body as JSON, and even that path is not exercised when color is disabled (e.g. `NO_COLOR`, `--color=never`, non-color terminal) or output isn't a TTY combined with color settings that keep `ColorEnabled()` false.

### Impact Explanation
An attacker who controls the responses of a host the victim explicitly points `gh api` at can inject arbitrary terminal escape/OSC sequences into the victim's terminal on an ordinary `gh api` GET, despite the tool's explicit intent (via `CopyGuardedContent`) to guard all raw, non-color-rendered response bodies against exactly this. This can be used to forge fake gh prompts, manipulate terminal title/state, or attempt OSC52 clipboard/exfiltration primitives supported by the victim's terminal emulator — matching GitHub's "terminal/output injection leading to spoofing or data exfiltration" bounty class. Impact is bounded by requiring color output to be disabled and by dependence on the victim's terminal emulator supporting the injected OSC sequence.

### Likelihood Explanation
Requires the victim to run `gh api` against a host or endpoint the attacker controls (custom `GH_HOST`/`--hostname`, self-hosted GHE the attacker operates, or any URL-controlled backend) and to have color output disabled at the time (`NO_COLOR` env var, `--color=never`, or non-color-capable terminal) — a realistic but non-default configuration. No token, MITM, or elevated privilege is needed beyond controlling the target host's HTTP responses, which is explicitly in-scope per the rules ("controls responses from a host the victim points gh at").

### Recommendation
Do not trust the `Content-Type` header alone to exempt a response body from `CopyGuardedContent`. Either (a) validate that the body actually decodes as JSON before treating it as trusted/sanitized, falling back to `CopyGuardedContent` on parse failure, or (b) always route the raw (non-jq/non-template/non-jsoncolor) body through `CopyGuardedContent` regardless of the declared `isJSON` classification, only skipping the guard for output that has been re-serialized through a JSON encoder (which cannot carry raw control bytes outside escaped string literals).

### Proof of Concept
Go test using `httptest`/`httpmock` in `pkg/cmd/api/api_test.go` style:
```go
func TestProcessResponse_SpoofedJSONContentTypeBypassesGuard(t *testing.T) {
    ios, _, out, _ := iostreams.Test()
    ios.SetStdoutTTY(true)
    ios.SetColorEnabled(false) // e.g. NO_COLOR

    body := "\x1b]52;c;ZXZpbCBjb250ZW50\x07plain text, not JSON"
    resp := &http.Response{
        StatusCode: 200,
        Header:     http.Header{"Content-Type": []string{"application/json"}},
        Body:       io.NopCloser(strings.NewReader(body)),
    }
    opts := &ApiOptions{IO: ios}
    _, err := processResponse(resp, opts, ios.ContentOut, ios.Out, template.New(ios.ContentOut, 80, false), true, true)

    require.NoError(t, err)
    // Assert the OSC52 payload reached the terminal-bound writer unmodified,
    // i.e. CopyGuardedContent/ErrEscapeSequence was never triggered.
    require.Contains(t, out.String(), "\x1b]52;")
}
```
Fuzz plan: generate `Content-Type` strings matching `jsonContentTypeRE` paired with non-JSON bodies containing `0x1B` (ESC) bytes and OSC52 sequences; assert that for every case where `jsonContentTypeRE` matches but `json.Valid(body)` is false, the code path currently used by `processResponse` still performs raw `io.Copy`, confirming the guard bypass.
