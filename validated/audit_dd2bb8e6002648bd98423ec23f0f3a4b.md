### Title
Cross-stack unauthorized read via `CCMenuController#stack` bypassing the `stacks` permission scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides both `authenticate_api_client` and `stack` from `Api::BaseController`. Its `stack` method resolves `Stack.from_param!(params[:stack_id])` against **all** stacks instead of the scoped `stacks` collection, so a `read:stack` token minted for one stack can be used to read the CCMenu deploy/build status of any other stack.

### Finding Description
The intended binding is: the stack an API request may touch must be an element of `current_api_client`'s authorized scope, i.e. `stack ∈ stacks` where `stacks` is defined in `Api::BaseController#stacks` as: [1](#0-0) 
`stacks` filters to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and the default `stack` method correctly calls `stacks.from_param!`.

`Api::CCMenuController`, however, redefines `stack` to bypass this scope entirely: [2](#0-1) 
This calls `Stack.from_param!` on the unscoped `Stack` relation, so any authenticated `ApiClient` — regardless of its `stack_id` — can resolve any stack by path.

The only permission check performed is `require_permission :read, :stack`, which is enforced by `ApiClient#check_permissions!`: [3](#0-2) 
This method only checks the `permissions` array (e.g. `"read:stack"`) and never inspects `stack_id`. The scoping to a single stack is enforced *only* by the `stacks` method in `BaseController`, which `CCMenuController#stack` deliberately does not use.

Exploit flow:
1. Attacker has (or obtains) a `read:stack`-scoped `ApiClient` token for stack A — e.g. legitimately minted via `CCMenuUrlController#fetch`, which creates a `read:stack` client per-user (not even per-stack, since `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` ignores `stack`), and returns the token embedded in a shareable CCMenu URL: [4](#0-3) 
2. Attacker sends `GET /api/stacks/OWNER/REPO/ENV/ccmenu?token=<token-for-A>` where the path segment names stack B.
3. `authenticate_api_client` in `CCMenuController` authenticates the client via `ApiClient.authenticate(params[:token])`, ignoring `stack_id` scoping entirely (it doesn't even use HTTP basic auth like the base controller): [5](#0-4) 
4. `require_permission :read, :stack` (declared at class level) passes because the client has `"read:stack"` in its permissions, irrespective of which stack is targeted.
5. `#show` calls `stack`, which resolves stack B via unscoped `Stack.from_param!`, and renders B's latest deploy/rollback status.

Existing guards do not prevent this: `check_permissions!` is scope-blind by design (it's `stacks`, not `check_permissions!`, that enforces per-stack authorization elsewhere in the API), and `CCMenuController` simply never calls `stacks`.

### Impact Explanation
An attacker holding any `read:stack` token — even one they legitimately obtained for a stack they have access to — can read the deploy/build status (via the rendered CCMenu XML in `#show`) of any other stack in the Shipit instance, across repository/tenant boundaries. This is a repeatable, unauthenticated-relative-to-target-stack read of stack state, matching the "High - unauthenticated read of stack state" impact category. The information disclosed (last deploy/rollback status, running state) is limited to what the CCMenu XML exposes, but it is fully repeatable against arbitrary stack IDs without any additional privilege.

### Likelihood Explanation
The attacker needs any valid `read:stack`-scoped API token. This is a low bar: `CCMenuUrlController#fetch` is reachable by any authenticated Shipit web user (`current_user`) and mints such a token bound to the user (not the stack) with `read:stack` permission for whichever stack they viewed, and that token/URL is designed to be shared externally (that's the entire purpose of the CCMenu integration with CI dashboard tools). Once such a token leaks or is obtained, forging the request against a different `stack_id` in the path requires no further secrets. This is highly feasible and fully repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped `stacks` collection instead of the unscoped `Stack.from_param!`, mirroring `Api::BaseController`'s own `stack` method, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`. Additionally consider removing the custom `authenticate_api_client` override or ensuring it still respects `stack_id` scoping consistently with the base controller.

### Proof of Concept
minitest plan (`test/controllers/api/ccmenu_controller_test.rb` style, using `ApiControllerTestCase`):
1. Create `stack_a = shipit_stacks(:shipit)` (or `Stack.create!`) and `stack_b = Stack.create!(...)` with distinct repository/environment.
2. Create `client = ApiClient.create!(creator: users(:walrus), name: 'test', stack_id: stack_a.id, permissions: ['read:stack'])`.
3. Assert binding before: `client.stack_id == stack_a.id` and stack B is not in `Stack.where(id: client.stack_id)`.
4. `get "/api/stacks/#{stack_b.repository.owner}/#{stack_b.repository.name}/#{stack_b.environment}/ccmenu", params: { token: client.authentication_token }`.
5. Assert `response.status` is NOT `200` (e.g. `assert_response :not_found` after the fix, since `stacks.from_param!` would raise `RecordNotFound` for stack B when scoped to stack A) — currently it returns `:ok` with stack B's data, demonstrating the vulnerability.
6. Additionally assert `response.body` does not include stack B's deploy data pre-fix vs. post-fix to make the divergence explicit.
