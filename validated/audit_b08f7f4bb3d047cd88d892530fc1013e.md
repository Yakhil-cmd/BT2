### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but handlers act on the repository derived from `repository.full_name`/global commit SHA lookup - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret used for HMAC verification using `repository_owner`, which is read from the still-unverified JSON body (`repository.owner.login`, falling back to `organization.login`). Every webhook handler that actually mutates state, however, resolves the target `Stack`/`Repository`/`Commit` from a *different* field of the same unverified body: `repository.full_name` (`Handler#repository_name`), or, in the case of `StatusHandler`, from a raw commit SHA with no repository scoping at all. Nothing enforces that the organization whose secret validated the signature is the same organization/repository that the handler subsequently writes to.

### Finding Description
`verify_signature` looks up the app config by `repository_owner`: [1](#0-0) 
and `repository_owner` is taken straight from the unauthenticated payload: [2](#0-1) 

Once the signature validates (using the secret belonging to *that* organization), `WebhooksController#create` dispatches the full payload to handlers: [3](#0-2) 

Every generic `Handler` resolves the target repository from a *different* payload field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

`PushHandler` uses this to enqueue a resync of whatever stack matches `full_name`: [5](#0-4) 

`StatusHandler` is even less scoped: it looks up commits **only by SHA**, with no repository check at all, and writes a GitHub commit status onto whatever commit matches, across the entire instance: [6](#0-5) 

In a multi-tenant Shipit deployment, each organization has its own `github_app` config entry with its own `webhook_secret`, which the org's own GitHub admin configures and therefore knows: [7](#0-6) 

Because the entire raw body is HMAC-signed, an attacker who legitimately administers Org A's webhook integration (and therefore knows Org A's `webhook_secret`) can construct an arbitrary JSON payload where `repository.owner.login` (or `organization.login`) is set to `"Org A"` (so `verify_signature` selects Org A's app/secret and the HMAC matches), while `repository.full_name` names Org B's real, unrelated repository, or the `sha` field names an arbitrary commit belonging to Org B's stack. `Shipit.github(organization:)` raising `GithubOrganizationUnknown` only guards against unknown orgs, not against an org/repo mismatch inside a request whose HMAC is otherwise valid: [8](#0-7) 

This breaks exactly the binding the analysis targets: `organization that authenticated the request` != `repository the handler actually writes to`, mirroring the Morpho bug class where a validated quantity (APR) is silently substituted for a different, unchecked quantity (APY) used by the compounding computation.

### Impact Explanation
Via `StatusHandler`, the forging org can inject a fabricated `"state": "success"` GitHub status for any commit SHA that happens to exist on a victim stack. `Stack#deployment_checks_passed?`/CI status gating (`ci.require`) relies on `Commit#statuses` populated from these webhook-sourced records, so a forged success status can satisfy the CI requirement gate that Shipit uses to allow deploys/merges, i.e. it can defeat the deploy-gating control and enable an unauthorized deploy. Via `PushHandler`, the forging org can also force-enqueue `GithubSyncJob` for a victim stack. This crosses an organizational trust boundary (Org A's webhook credential is used to affect Org B's repository state) even though neither org has any legitimate relationship or access to the other's stack.

### Likelihood Explanation
Likelihood is high in any multi-organization Shipit deployment (the shape explicitly supported by `config/secrets*.yml`, which keys `github:` config per-organization). Any org onboarded to the instance already knows its own `webhook_secret` (they configured it on GitHub's webhook settings page), and nothing prevents them from sending a raw signed POST to the shared `/webhooks` endpoint with mismatched `owner.login` / `full_name` fields — GitHub itself always keeps these fields consistent, but the endpoint doesn't enforce that, so a hand-crafted request bypasses the assumption entirely.

### Recommendation
After verifying the signature for `repository_owner`, re-derive the acting organization/repository strictly from the same field used for verification (or verify signature per-repository rather than per-org, and enforce that `repository.full_name`'s owner segment equals the field used to select the verifying secret). For `StatusHandler`, scope the `Commit` lookup by the repository resolved from the verified organization, not by a bare SHA query across all stacks.

### Proof of Concept
1. Configure two orgs in `secrets.yml`, `org-a` (attacker-administered, known `webhook_secret_a`) and `org-b` (victim, tracked stack `org-b/victim-repo`).
2. Attacker crafts payload:
```json
{
  "sha": "<victim-repo commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/whatever" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_a, body)` and POSTs with `X-Github-Event: status`.
4. `verify_signature` selects `org-a`'s app via `repository_owner` ("org-a") and the signature validates.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — which matches the victim commit regardless of `repository.full_name` — and creates a forged `success` status on it, potentially clearing `ci.require` for a deploy the attacker has no access to trigger directly.
