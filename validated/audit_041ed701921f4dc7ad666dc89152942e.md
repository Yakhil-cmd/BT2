## Title
Webhook signature verification authenticates the *organization*, but `StatusHandler` writes commit status to *any* repository's commit by SHA, unscoped — cross-tenant CI-status forgery enabling an unauthorized deploy - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken directly from the untrusted JSON body, and only proves the payload was signed by *some* known organization's `webhook_secret` in this Shipit install. [1](#0-0)  Nothing subsequently ties that authenticated organization to the repository the event handler actually mutates. `StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` — a global, unscoped query across every stack/repository in the database — and calls `commit.create_status_from_github!(params)` on whatever it finds. [2](#0-1) 

### Finding Description
Shipit supports hosting multiple GitHub organizations from one instance, each configured with its own `webhook_secret` in `secrets.yml` (see the documented multi-org config schema). [3](#0-2)  The webhook endpoint is shared: `WebhooksController#verify_signature` derives `repository_owner` from the attacker-controlled JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), fetches `Shipit.github(organization: repository_owner)`, and verifies the `X-Hub-Signature` against that org's `webhook_secret`. [1](#0-0)  This only proves "signed with organization X's secret" — it establishes no binding between organization X and the actual repository/commit fields the handler will act on.

`StatusHandler` then processes the `status` event using only `params.sha`, `params.state`, `params.context`, etc., with **no repository/stack scoping at all**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [4](#0-3)  The equality that should hold — `organization authenticated == organization owning the commit's repository` — is never checked; only `organization authenticated ∈ {known orgs}` is checked.

An attacker who legitimately administers a GitHub App/webhook for **their own** tenant organization on this shared Shipit instance (org A) knows org A's `webhook_secret` (they configured it when creating their GitHub App, per the setup docs). [5](#0-4)  They can craft an arbitrary "status" webhook payload with `repository.owner.login = "org-A"` (so `verify_signature` selects and matches org A's secret) but with `sha` set to a commit SHA that belongs to a *different tenant's* repository/stack (org B) hosted on the same Shipit instance, and `state: "success"` with the `context` value org B's stack requires. Because `Commit.where(sha:)` is global, this forges a passing CI status on org B's commit.

### Impact Explanation
`Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, driven directly by the statuses attached via `create_status_from_github!`. [6](#0-5)  By forging a successful status for a required CI context on a victim organization's commit, an attacker outside that organization's authorization boundary can make an otherwise CI-blocked, non-deployable commit appear deployable, enabling an **unauthorized deploy** on a stack/repository they have no legitimate access to — this matches the Critical-severity impact category (unauthorized deploy) defined by the scope rules. It also lets an attacker interfere with the merge queue (`ProcessMergeRequestsJob` is triggered on status transitions) for a repository they don't own. [7](#0-6) 

### Likelihood Explanation
Requires the attacker to control (or be an administrator of) at least one GitHub App/org tenant already configured on a shared, multi-organization Shipit deployment — a realistic scenario since Shipit explicitly documents and supports hosting several unrelated organizations from a single instance/secrets file. [8](#0-7)  No Shipit session, `ApiClient` token, or GitHub credentials for the victim org are needed — only the attacker's own, already-issued webhook secret and knowledge/guessability of a target commit SHA in another tenant's repository (commit SHAs are frequently public/discoverable via GitHub itself).

### Recommendation
In `Handler#stacks`/`StatusHandler#process` (and any other handler that resolves records purely by attacker-supplied identifiers such as SHA), scope the lookup to the repository identified in `payload['repository']['full_name']`, and additionally verify that the authenticated organization (`repository_owner` used in `verify_signature`) matches the owner segment of that `full_name` before processing. Concretely, `StatusHandler` should resolve the target `Repository`/`Stack` via `Repository.from_github_repo_name(repository_name)` (as other handlers already do) and scope `Commit.where(stack: stacks, sha: params.sha)` instead of a global, cross-tenant `Commit.where(sha:)` lookup.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (as documented multi-org config).
2. As the operator of `org-a`'s GitHub App, compute `sha256=...` HMAC over a crafted JSON body using `org-a`'s known `webhook_secret`:
   ```json
   {
     "sha": "<sha-of-a-commit-belonging-to-org-b's-stack>",
     "state": "success",
     "context": "<the-context-required-by-org-b's-shipit.yml ci.require>",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
   }
   ```
3. `POST /webhooks` with `X-Github-Event: status` and `X-Hub-Signature: sha256=<computed>`.
4. `WebhooksController#verify_signature` resolves `repository_owner == "org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature matches — request is accepted. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — since this is unscoped, it finds the commit belonging to `org-b`'s stack and calls `create_status_from_github!`, recording a forged "success" status on it. [4](#0-3) 
6. If that context was the last missing/blocking required status for `org-b`'s stack, `Commit#deployable?` now returns true, and a deploy against `org-b`'s stack can proceed without any legitimate CI success or credentials from `org-b`.

Note: I was unable to execute this against a live instance to confirm end-to-end behavior (e.g., interaction with `ignore_ci`, `blocking_statuses`, or additional hidden validations in `DeploySpec`); the analysis is based on the exact, unscoped query in `StatusHandler` and the organization-only binding in `WebhooksController#verify_signature` as read from the indexed source.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post
      )
      head(422) unless verified
