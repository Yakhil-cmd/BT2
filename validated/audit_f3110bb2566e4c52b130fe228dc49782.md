### Title
Status webhooks are matched globally by SHA, so a spoofed/nonexistent `repository.full_name` still writes a status onto a victim stack's commit - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the entire `commits` table, with no scoping by the payload's `repository.full_name`, then calls `commit.create_status_from_github!(params)`, which writes to `commit.stack_id` — the real, matched stack's id, not anything derived from the payload. Unlike `PushHandler`, which resolves the target stacks via the inherited `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`), `StatusHandler` never calls `stacks` or reads `repository_name` at all, so the repository field in the payload is purely decorative for this handler.

### Finding Description
Binding claimed broken: `repository.full_name` (attacker-supplied) == `Repository.from_github_repo_name(repository.full_name)` consulted before the write. Trace:

- `app/controllers/shipit/webhooks_controller.rb:24-30` (`verify_signature`) resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and validates the HMAC signature using that organization's `webhook_secret`. This only requires the attacker to control (own) *some* organization already onboarded to this Shipit instance and know its `webhook_secret` — it does not bind the signature to any specific target repository name or to the `full_name` field. [1](#0-0) 
- `Handler#stacks`/`#repository_name` would normally scope a handler's effect to `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`, but `StatusHandler#process` never calls this helper. [2](#0-1) 
- `StatusHandler#process` instead does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup by `sha` alone. [3](#0-2) 
- `Commit#create_status_from_github!` writes using `statuses.replicate_from_github!(stack_id, github_status)`, where `stack_id` comes from the matched `Commit` record's own association, entirely independent of the payload. [4](#0-3) 

Contrast with `PushHandler`, which correctly scopes its side effects to the repository resolved from the payload: [5](#0-4) 

Exploit flow: attacker owns/controls Org A already connected to this Shipit instance (has that org's `webhook_secret`, e.g. as a normal legitimate onboarding customer — not a privileged Shipit role). They send `POST /webhooks` with `X-Github-Event: status`, `repository.owner.login = "org-a"` (so `verify_signature` passes using Org A's secret), but `repository.full_name = "nonexistent/nowhere"` (or any repo they don't control) and `sha` equal to a real commit sha belonging to victim Stack B (an unrelated org/repo entirely). `verify_signature` succeeds because it only checks the owner login against a known configured org, not `full_name` against the resolved repository. `StatusHandler` then finds the victim's `Commit` row purely by sha match and creates a `Status` on it, using the victim stack's real `stack_id`. `Repository.from_github_repo_name('nonexistent/nowhere')` is never even queried by this handler, confirming the repository field is decorative.

Existing guards do not catch this: `verify_signature` authenticates *an* organization the attacker legitimately controls, not the *target* repository; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` only requires `sha`/`state`/etc., not a valid/matching `repository`; there is no `stacks`/`Repository.from_github_repo_name` check anywhere in this handler.

### Impact Explanation
An attacker who legitimately controls any one org/repo connected to the Shipit instance can inject fabricated CI statuses (`state`, `description`, `target_url`, `context`) onto any other tenant's commit, as long as they can guess or observe that commit's SHA (SHAs are often public via GitHub, PRs, or CI logs). This is exactly the "payload for one repository mutating another's stack/commit" Critical category: statuses affect `deployable?`/`blocked?` gating and can be used to force-green or force-red a victim's commit, influencing deploys/merges (`schedule_merges`, `ContinuousDeliveryJob`) on a stack the attacker never authenticated against. It is trivially repeatable against any commit sha and any stack, blast radius spans all tenants sharing the Shipit instance.

### Likelihood Explanation
Preconditions: attacker needs one legitimate org connected to Shipit (a normal state for any onboarded customer) and the victim commit's SHA (public in most GitHub workflows: forks, PRs, commit URLs, CI badges). No Shipit session, API token, or victim's webhook secret is needed. Cost is a single signed HTTP POST. This is fully repeatable and requires no race conditions or timing tricks.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository resolved from the payload, mirroring `PushHandler`, e.g. `stacks.joins(:commits...)` or restrict via `Repository.from_github_repo_name(repository_name)` before touching `Commit.where(sha:)`, rejecting/ignoring the event when the resolved repository does not own a matching commit/stack.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "does not create a status when repository.full_name does not resolve to any Repository" do
          victim_commit = shipit_commits(:first) # belongs to a real, existing stack/repo

          assert_nil Shipit::Repository.from_github_repo_name('nonexistent/nowhere')

          payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'context' => 'attacker-forged',
            'repository' => { 'full_name' => 'nonexistent/nowhere', 'owner' => { 'login' => 'attacker-org' } }
          }

          assert_difference -> { victim_commit.statuses.count }, 1 do
            StatusHandler.new(payload).process
          end

          assert_equal 'attacker-forged', victim_commit.statuses.last.context
        end
      end
    end
  end
end
```
This demonstrates both sides of the binding diverge: `Repository.from_github_repo_name('nonexistent/nowhere')` is `nil` (left side), yet a `Status` is still written against the victim's real `stack_id` (right side), proving the repository field is never consulted before the write.
