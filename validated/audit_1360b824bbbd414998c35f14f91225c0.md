### Title
Stack-scope binding on `ApiClient` tokens is bypassed by `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` records can be scoped to a single `Stack` via `belongs_to :stack, optional: true`, and this scope is meant to restrict which stacks a token holder can query. `Api::BaseController` enforces this binding centrally, but `Api::CCMenuController` overrides the stack-resolution method with an unscoped lookup, so a stack-scoped `read:stack` token can be used to read the CI/build status of any stack, not just the one it is bound to.

### Finding Description
`Api::BaseController` defines the canonical binding between an authenticated `ApiClient` and the stacks it may touch: [1](#0-0) 

This means `stack` (and therefore any controller action gated by `require_permission :read, :stack`) is supposed to be limited to `Stack.where(id: current_api_client.stack_id)` whenever the client is stack-scoped. This is exactly the mechanism validated by the test suite: `"an api client scoped to a stack will only see that one stack"` in `test/controllers/api/stacks_controller_test.rb`, and the fixture `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml` demonstrates a real stack-scoped client used in production-style tests.

`Api::CCMenuController`, however, redefines `stack` to bypass the scope entirely: [2](#0-1) 

`stack` here resolves via `Stack.from_param!(params[:stack_id])` directly against the global `Stack` table, ignoring `current_api_client.stack_id`. The `require_permission :read, :stack` before_action only calls `current_api_client.check_permissions!(operation, scope)`: [3](#0-2) 

`check_permissions!` only checks the string permission list (`read:stack`), not the `stack_id` binding. Consequently, the equality that should hold — `stack the token authorizes == stack the token can touch` — is broken specifically inside `CCMenuController#show`. Any client holding a `read:stack` permission, even one explicitly scoped to a single stack, can pass an arbitrary `stack_id` in the URL and retrieve build status data for stacks outside its authorized scope.

### Impact Explanation
This is a High-severity authorization escalation: it grants a token holder unauthenticated-for-that-resource read access to task/deploy state (`stack.deploys_and_rollbacks`, lock status, build status/label) of *any* stack in the installation, despite the token being deliberately restricted to a single stack via `ApiClient#stack_id`. This matches the rules' listed analog category — "a stack a token authorises versus a stack it touches" — and falls under the accepted High-impact class "escalation into...unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Exploitation requires only possession of a valid, stack-scoped `ApiClient` token with `read:stack` permission (a normal, unprivileged capability any integration/CI tool may hold) and knowledge/guessing of another stack's identifier (`owner/repo/env-branch`), which is not secret information. No privileged account or additional credential is needed beyond the token itself, which is a legitimately issued, narrowly-scoped credential — this is a genuine boundary break, not a scenario requiring a privileged account.

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the `current_api_client.stack_id` binding is enforced consistently across all API controllers.

### Proof of Concept
1. Create an `ApiClient` scoped to `Stack A` (`stack_id` set) with `permissions: ['read:stack']`, and obtain its `authentication_token`.
2. As the CCMenu integration would, call:
   `GET /api/<STACK_B_ID>/ccmenu.xml?token=<STACK_A_SCOPED_TOKEN>`
   (or via Basic auth per `CCMenuController#authenticate_api_client`).
3. `require_permission :read, :stack` passes because the client has the `read:stack` permission string.
4. `stack` resolves via `Stack.from_param!(params[:stack_id])` (unscoped), returning `Stack B` even though the client's `stack_id` is `Stack A`.
5. The response renders `Stack B`'s deploy/lock/build status — data the token was never authorized to see.
