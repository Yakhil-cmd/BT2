### Title
Unvalidated `burnt_gas_reward` fraction can be configured ≥ 1, causing a consensus-critical panic on every function-call receipt - ([File: runtime/runtime/src/lib.rs])

### Summary
`RuntimeFeesConfig::burnt_gas_reward` is a `Rational32` fraction that determines what portion of the gas burnt during a function call is credited back to the contract account. Unlike other fraction-typed genesis/runtime parameters (`online_max_threshold`, `online_min_threshold`, `gas_price_adjustment_rate`), there is no validation anywhere in the codebase enforcing `burnt_gas_reward < 1` (i.e., numerator < denominator). If a chain is configured with `burnt_gas_reward >= 1`, every function-call receipt that burns gas will deterministically panic all validating nodes via an `unwrap()` on a balance subtraction, halting the chain.

### Finding Description
When a receipt finishes executing, the runtime computes the contract's gas reward directly from the configured fraction with no bound check: [1](#0-0) 

```
let receiver_gas_reward = result
    .gas_burnt_for_function_call
    .checked_mul(*apply_state.config.fees.burnt_gas_reward.numer() as u64)
    .unwrap()
    .checked_div(*apply_state.config.fees.burnt_gas_reward.denom() as u64)
    .unwrap();
...
```

Immediately afterwards, this `receiver_reward` is subtracted from `tx_burnt_amount` using an unchecked `.unwrap()`: [2](#0-1) 

The reward is, by design, supposed to be a fraction (currently 30%, i.e. `3/10`) of `gas_burnt_for_function_call` [3](#0-2)  — strictly smaller than the burnt amount it is deducted from. If `burnt_gas_reward.numer() >= burnt_gas_reward.denom()` (i.e., the fraction is ≥ 1, analogous to `s_defaultClientBasisPoints >= 10_000` in the reported bug), `receiver_reward` can exceed `tx_burnt_amount`, and `tx_burnt_amount.checked_sub(receiver_reward).unwrap()` panics.

Genesis/runtime-config validation (`GenesisValidator::validate_processed_records`) explicitly checks other fraction fields for the `<1` invariant — `online_max_threshold`, `online_min_threshold`, and `gas_price_adjustment_rate` — but conspicuously omits `burnt_gas_reward` and other `RuntimeFeesConfig` fractions (`pessimistic_gas_price_inflation`, `gas_refund_penalty`): [4](#0-3) 

There is no analogous check inside `core/parameters` (`cost.rs`, `view.rs`, `parameter_table.rs`) for `burnt_gas_reward` either — it is deserialized straight from the runtime-config YAML/genesis JSON files with no bounds enforcement.

### Impact Explanation
This directly matches the "balance and gas accounting" category: `burnt_gas_reward` feeds into the per-receipt balance ledger used by every validating node applying a chunk. Because the computation and the resulting panic occur deterministically in `Runtime::apply`/`process_receipt` for any function-call receipt with `gas_burnt_for_function_call > 0`, a misconfigured `burnt_gas_reward >= 1` in a chain's genesis/runtime-config would cause **every single validator processing any function-call transaction to panic**, i.e., a full chain halt (a genuine "node panic / chain stall" outcome per the validation criteria) triggered by an ordinary, unprivileged account submitting a normal `FunctionCall` transaction — not by any malicious/validator-only action.

### Likelihood Explanation
The likelihood depends entirely on `burnt_gas_reward` being misconfigured to `>= 1` at genesis or via a runtime-config parameter change (this value lives in the runtime-config table which is part of the genesis records for custom/private chains, and is also expressed via `parameters.yaml`/diff files used for protocol-version parameter transitions on mainnet/testnet). For mainnet/testnet this value is a hardcoded protocol constant (`3/10`) reviewed through the standard NEP/parameter-diff process, so accidental misconfiguration there is unlikely. However, for any custom/private nearcore deployment (a common use case, as evidenced by the extensive genesis-validation infrastructure covering exactly this class of fraction fields), there is no safeguard preventing an operator from setting an invalid `burnt_gas_reward`, and the resulting failure mode is a full deterministic chain panic rather than a graceful rejection at genesis-validation time — the same "revert on initialization" failure mode described in the analogous report, except manifesting as a live-network panic instead of a deploy-time revert.

### Recommendation
Add an explicit check in `GenesisValidator::validate_processed_records` (and/or wherever `RuntimeConfig`/`RuntimeFeesConfig` is loaded/validated) enforcing:
```
burnt_gas_reward < Rational32::from_integer(1)
```
mirroring the existing check for `gas_price_adjustment_rate`. Consider adding the same `< 1` bound validation for the other unguarded fee fractions (`pessimistic_gas_price_inflation`, `gas_refund_penalty`) for consistency, and replace the unchecked `.unwrap()` in `runtime/runtime/src/lib.rs` (line ~999) with a `checked_sub` that returns a `RuntimeError`/`StorageError` instead of panicking, as defense in depth.

### Proof of Concept
1. Configure a custom nearcore genesis/runtime-config with `fees.burnt_gas_reward = { numerator: 1, denominator: 1 }` (or any value with `numerator >= denominator`).
2. Start the chain; `validate_genesis` passes because `burnt_gas_reward` is never checked.
3. Submit any `FunctionCall` transaction that burns non-zero gas during execution (e.g., a simple contract method call with `gas > 0`).
4. During receipt application, `receiver_gas_reward` computed from `burnt_gas_reward` equals or exceeds `tx_burnt_amount`.
5. `tx_burnt_amount.checked_sub(receiver_reward).unwrap()` in `runtime/runtime/src/lib.rs` returns `None` and the `.unwrap()` panics, crashing every node applying this receipt deterministically — halting the chain.

Note: I could not find any additional runtime-side validation (e.g. in `core/parameters`) for `burnt_gas_reward` beyond what is shown in `genesis_validate.rs`; if such validation exists elsewhere and was not indexed, this would need confirming with a full repository search (index size limits may have excluded some files).
