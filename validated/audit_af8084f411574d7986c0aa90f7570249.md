### Title
Cross-repo Status webhook forgery flips victim commit to `success` and triggers unauthorized `ContinuousDeliveryJob` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha` (`Commit.where(sha: params.sha)`), ignoring the `repository_name`-scoped `stacks` helper that the base `Handler` class exposes for exactly this purpose. [1](#0-0) [2](#0-1)  Because a legitimately-signed "status" webhook from an attacker-owned repository is authenticated only against that repository's own signing secret, and not against the sha's ownership, the attacker can write a `Status(state: 'success')` row onto a victim stack's commit and trigger its `after_commit :schedule_continuous_delivery` callback, which walks into `Commit#schedule_continuous_delivery` and, if the victim stack has `continuous_deployment?` enabled, enqueues `ContinuousDeliveryJob` for that victim stack. [3](#0-2) [4](#0-3) 

### Finding Description
The broken binding is: **authenticated_repository(webhook) == owning_repository(commit_written)**. `verify_signature` only proves the payload was legitimately signed for the `repository_owner`/org named in the payload — it says nothing about which commits that payload is allowed to mutate. [5](#0-4)  The `Handler` base class anticipates this and provides a `stacks` helper scoped to `Repository.from_github_repo_name(repository_name)` (i.e., the repository named in the *authenticated* payload), specifically so handlers can restrict their writes to stacks belonging to that repository. [2](#0-1) 

`StatusHandler#process`, however, never calls `stacks`. It does a bare, global lookup:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 
This matches **any** `Commit` row in the entire installation whose `sha` equals the attacker-supplied `params.sha`, regardless of which repository/stack it belongs to, then calls `create_status_from_github!` which creates a `Status` scoped to `stack_id` derived from the matched (victim) commit, not the attacker's repository. [6](#0-5) 

Exploit flow:
1. Attacker owns/controls a repository `attacker/attacker-repo` that is onboarded into Shipit (or any repo Shipit tracks) and can therefore cause GitHub to emit a genuinely-signed `status` webhook for that repo (e.g., via GitHub's Statuses API using a token scoped to their own repo — GitHub's Statuses API does not require the `sha` to belong to that repository's commit graph).
2. Attacker discovers a victim commit's `sha` (commit SHAs are public information — visible on GitHub, in PRs, in Shipit's own UI).
3. Attacker POSTs/triggers a status update for `sha = <victim_sha>`, `state = success` against their own repo. GitHub relays this as an authentically signed webhook to Shipit's `/webhooks` endpoint with `repository.full_name = attacker/attacker-repo` but `sha = <victim_sha>`.
4. `verify_signature` succeeds — the signature is real and matches the attacker's own org's app secret. [5](#0-4) 
5. `StatusHandler#process` ignores the (attacker's) `repository_name` entirely and matches the victim's `Commit` by `sha`, writing a new `success` `Status` scoped to the victim's `stack_id`. [1](#0-0) 
6. `Status`'s `after_commit :schedule_continuous_delivery` fires, delegating to `commit.schedule_continuous_delivery`, which (per the question's stated logic, `deployable? = stack.ignore_ci? || (success? && !blocked?)`) now evaluates `success?` true for the victim commit. [4](#0-3) 
7. If the victim stack has `continuous_deployment?` enabled (an admin-set flag on the *victim's own stack*, untouched by the attacker), `ContinuousDeliveryJob` is enqueued for the victim stack — an unauthorized deploy trigger caused entirely by a payload authenticated for a different repository.

None of the existing guards prevent this: `verify_signature` authenticates repo ownership of the *webhook*, not of the *commit sha* being mutated; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape (`sha`, `state`, etc.), not sha ownership; there is no `require_permission!`/`stacks`-scoping check in `StatusHandler` as there is a `stacks` helper available but unused.

### Impact Explanation
An attacker who controls or can push signed status events for any single Shipit-tracked repository can write forged CI state onto any other tenant's commit purely by knowing its SHA, and — combined with an admin's pre-existing `continuous_deployment?` setting on the victim stack — cause an unauthorized deploy to be scheduled for that victim stack (`ContinuousDeliveryJob.perform_later`/enqueue for the victim `Stack`). This is a "payload for one repository mutating another's stack/commit" leading to an unauthorized deploy, matching the Critical severity bucket. The attack is repeatable against any commit sha the attacker can learn, across arbitrary victim stacks in the same Shipit installation, and also silently corrupts victim CI status/`enable_ci_on_stack` state even when `continuous_deployment?` is off.

### Likelihood Explanation
Preconditions: attacker needs (a) any Shipit-tracked repository they control to legitimately emit signed `status` webhooks (cheap — create/own a public repo and add it to Shipit, or use one already tracked), and (b) knowledge of a victim commit's SHA (trivially public). No Shipit session, API token, or secret is required — only the ability to cause GitHub to sign and deliver a `status` event for their own repo, which is normal, unprivileged GitHub functionality. The victim's stack requires `continuous_deployment?` to be true for the deploy-trigger impact (a common, intentional configuration for CD-enabled stacks), but the underlying cross-tenant Status write happens regardless of that flag. This is low-cost and repeatable at will.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the requesting repository, e.g. use the existing `stacks` helper: `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status payload can only mutate commits belonging to stacks tied to the authenticated `repository.full_name`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status webhook from another repository cannot mutate a victim commit and trigger CD" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_deployment: true, ignore_ci: false)
  victim_commit = shipit_commits(:first) # belongs to victim_stack, currently not success

  attacker_repository_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'branches' => [{ 'name' => victim_stack.branch }],
    'repository' => { 'full_name' => 'attacker/attacker-repo' } # authenticated, but NOT victim's repo
  }.to_json

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulates a genuinely signed attacker webhook

  assert_no_enqueued_jobs(only: ContinuousDeliveryJob) do
    post :create, body: attacker_repository_payload, as: :json
  end

  victim_commit.reload
  refute_equal 'success', victim_commit.state # EXPECTED after fix; currently FAILS (forged success write + job enqueued)
end
```
Both sides of the binding — `authenticated_repository == 'attacker/attacker-repo'` vs `owning_repository(victim_commit) == victim_stack.repository` — must be equal for the write/job-enqueue to be legitimate; the test demonstrates they diverge under current code (`StatusHandler#process` ignoring `stacks`), and the assertion should pass once the lookup is scoped as recommended.
