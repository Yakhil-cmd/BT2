### Title
Webhook signature is verified against an organization derived from the payload, but the repository actually written to is taken from a different, unverified payload field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), but every event `Handler` (used to actually mutate state — sync a stack, archive/create a review stack, post a commit status, etc.) resolves the target repository from a completely different field, `payload.dig('repository','full_name')`, with no cross-check that the two agree.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where `repository_owner` is read straight from the JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This binds the *signature check* to one field of the payload (`repository.owner.login`). However, the code that actually performs writes uses a *different* field for the repository lookup:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 
`PushHandler`, for example, uses this to trigger a resync of a `Stack`:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 
and the `pull_request/*` handlers likewise resolve `repository` via `params.repository.full_name` (a distinct field from `repository.owner.login`) to archive/unarchive/provision review stacks. [5](#0-4) 

Shipit explicitly supports **multiple GitHub Apps for multiple organizations**, each with its own independently-configured `webhook_secret`:
```yaml
github:
  somegithuborg:
    webhook_secret: ...
  someothergithuborg:
    webhook_secret: ...
``` [6](#0-5) 
This is a first-class, documented deployment topology (also reflected in `test/dummy/config/secrets_double_github_app.yml`) [7](#0-6)  intended to isolate organizations from each other on a shared Shipit instance.

**Binding that should hold (equality):**
`organization_whose_secret_signed_the_request == organization_owning_repository.full_name_used_by_the_handler`

**What actually holds:** the controller only guarantees `organization_whose_secret_signed_the_request == payload['repository']['owner']['login']`. Nothing ties `payload['repository']['owner']['login']` to `payload['repository']['full_name']` — they are two independent, attacker-controlled strings inside the same signed JSON body. Since the entire raw POST body (`request.raw_post`) is signed as one opaque blob with whatever secret the *attacker's own organization* possesses, the attacker (who legitimately administers "org‑A", one of the multiple GitHub App installations configured on the shared Shipit instance) can freely choose the JSON content, including setting `repository.owner.login` to `"org-A"` (to select the secret they know) while setting `repository.full_name` to `"org-B/victim-repo"` — a stack that belongs to a different, unrelated organization on the same shared instance.

### Impact Explanation
By computing a valid HMAC-SHA1 signature over a hand-crafted JSON body using org‑A's own `webhook_secret` (which org‑A administrators legitimately possess for their own GitHub App installation), and setting `repository.full_name` to point at a stack belonging to org‑B, the attacker can invoke any webhook handler against org‑B's stacks without ever going through GitHub or possessing org‑B's secret:
- `push` → forces `GithubSyncJob` to run against org‑B's stack with an attacker-chosen `expected_head_sha`, causing the stack to resync/refetch commits and potentially feed continuous-deployment/auto-deploy logic with attacker-influenced state [8](#0-7) [9](#0-8) .
- `pull_request` (`opened`/`labeled`/`closed`/etc.) → creates, archives, or unarchives org‑B's review stacks. [10](#0-9) 

This is a cross-organization write on a multi-tenant Shipit deployment: an entity authenticated only as org‑A is able to mutate state belonging to org‑B, which the multi-org webhook-secret feature is specifically designed to prevent. This matches the "Critical — cross‑repository writes / unauthorized deploy" impact class.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization (a documented, supported configuration) and that the attacker controls one such organization's GitHub App (i.e., is a legitimate but semi-trusted org admin on a shared instance) — no theft of another org's secret, no privileged Shipit account, and no `ApiClient` token is needed. This is a realistic scenario for any SaaS-style or multi-team deployment of Shipit that onboards several GitHub organizations onto one instance.

### Recommendation
Make the field used to select the verifying secret and the field used to resolve the target repository the same, and enforce that the resolved `Repository`'s `owner` matches the organization whose secret validated the signature. Concretely:
- In `Handler#repository_name` (and every place a handler independently parses `repository.full_name`), also verify that `Repository.from_github_repo_name(repository_name).owner` equals the organization identified by `WebhooksController#repository_owner`, rejecting the event otherwise.
- Alternatively, pass the verified organization down from the controller into `Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization: repository_owner) }` and have `Handler#stacks` scope `Repository.from_github_repo_name` results to `where(owner: verified_organization)`.

### Proof of Concept
1. Attacker administers `org-A`'s GitHub App installation on a shared Shipit instance that also serves `org-B` (per `docs/setup.md`'s multi-org config), and thus knows `org-A`'s `webhook_secret`.
2. Attacker crafts a raw JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-A" },
    "full_name": "org-B/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC_SHA1(org-A_webhook_secret, raw_body)` and POSTs directly to the Shipit webhooks endpoint with `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner` = `"org-A"`, fetches `Shipit.github(organization: "org-A")`, and the signature validates (attacker used the correct secret for that org). [1](#0-0) 
5. `create` dispatches to `PushHandler`, whose `stacks` method resolves the target via `payload.dig('repository','full_name')` = `"org-B/victim-repo"`, entirely bypassing any relation to `org-A`, and triggers `stack.sync_github(expected_head_sha: ...)` on `org-B`'s stack. [3](#0-2) [4](#0-3) 

Note: I was unable to locate/inspect the exact implementation of `Shipit.github(organization:)` and `GithubOrganizationUnknown` in `lib/shipit.rb` within the indexed content (only match locations were found, not the source lines), so the precise mechanics of multi-org secret lookup are inferred from `docs/setup.md`, the `test/dummy/config/secrets_double_github_app.yml` fixture, and the controller/test code shown above rather than from reading that file directly.

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
