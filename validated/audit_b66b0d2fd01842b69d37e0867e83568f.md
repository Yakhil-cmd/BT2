### Title
Reentrant callback in `register-for-bond` lets a staker double-count bond stake/signing-weight using collateral validated only once - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond` in pox-5 reads the staker's balance, existing membership, and allowance into `let`-bound locals, then calls out to an attacker-chosen contract (`signer-manager-validate-stake`, a `<signer-manager-trait>` implementation supplied by the caller) *before* it commits any state. Because the pre-callback locals (`existing-membership`, `total-balance`, `current-total-staked`) are snapshotted before the callback and never re-checked afterward, a malicious `signer-manager` contract can re-enter `register-for-bond` for a second bond during the callback. Both the inner and outer calls pass all guards using the same collateral/allowance, and each independently increments per-bond/per-cycle accounting (`protocol-bonds-total-staked`, `add-staker-to-bond-cycles`, `add-staker-to-signer-cycles`), even though only one `protocol-bond-memberships` record (last writer wins) and one real STX lock ultimately exist. This is the Clarity analog of the reported "double order via callback" bug: a stale pre-callback check is used to authorize state changes made after an attacker-controlled call-out.

### Finding Description
In `register-for-bond` [1](#0-0) , key values are bound once at function entry:
- `existing-membership` via `(map-get? protocol-bond-memberships tx-sender)`
- `total-balance` via `(stx-account tx-sender)`
- `current-total-staked` via `(get-total-shares-staked-for-cycle first-reward-cycle (some bond-index))`

These are checked with `asserts!` (`total-balance >= amount-ustx`, no overlapping `existing-membership`) at lines 751 and 767-770 [2](#0-1) .

Between these checks, the contract calls into caller-supplied code:
```
(try! (signer-manager-validate-stake signer-manager tx-sender bond-index u1
    amount-ustx sats-total true signer-calldata
))
``` [3](#0-2) 

`signer-manager` is a `<signer-manager-trait>` value fully controlled by `tx-sender` (the caller picks which contract to pass in as the trait implementation), so this call-out executes arbitrary attacker code with `tx-sender` unchanged (Clarity preserves `tx-sender` across nested `contract-call?`s; only `contract-caller` changes). That attacker code can call `register-for-bond` again for a different `bond-index` before the outer call has written anything.

Because the *inner* reentrant call independently re-reads `protocol-bond-memberships`/`stx-account`/`get-total-shares-staked-for-cycle` fresh (all still unmodified, since the outer call hasn't performed any `map-set` yet), the inner call passes its own checks and completes: it writes `protocol-bond-memberships`, bumps `protocol-bonds-total-staked` for bond B, calls `add-staker-to-bond-cycles`/`add-staker-to-signer-cycles` for bond B's signer/cycles, and (via the node's post-call special-case handler in `pox_5.rs`) locks the staker's STX [4](#0-3) .

Execution then returns to the *outer* call, whose `existing-membership`/`total-balance`/`current-total-staked` locals are the stale, pre-callback snapshots (Clarity evaluates `let` bindings once, at function entry, not lazily). The outer call's `bond-overlaps-new-position?` check at line 767 still sees `existing-membership` as it was before the inner call ran (i.e. still passes), and its `total-balance` check at line 751 already succeeded before the callback. The outer call then proceeds to also finalize: `roll-sbtc`, `map-set protocol-bond-memberships` (overwriting bond B's record with bond A's — `protocol-bond-memberships` is keyed only by staker principal, not bond-index), `protocol-bonds-total-staked` for bond A (`+ current-total-staked sats-total`), and `add-staker-to-bond-cycles`/`add-staker-to-signer-cycles` for bond A's signer/cycles [5](#0-4) .

Net effect: the single staker's stake/collateral is checked and authorized only once (pre-callback), but per-bond/per-cycle accounting used for reward and signing-weight calculation (`protocol-bonds-total-staked`, `add-staker-to-bond-cycles`, `add-staker-to-signer-cycles`) is incremented **twice**, for two different bonds/signers, while the durable per-staker membership record and the actual STX lock reflect only one bond. This double-counts a commitment that was backed by a single balance check, breaking the equality "sum of per-bond/per-signer recorded stake == actual locked collateral of the staker."

### Impact Explanation
This falls under the rubric's Critical/High bucket: "double-counting a commitment or reward" and "signing weight or reward slots exceeding locked value." A signer's aggregate weight (`add-staker-to-signer-cycles`) and a bond's total staked sats (`protocol-bonds-total-staked`) — both used downstream for reward distribution and possibly quorum/voting weight — can be inflated for two bonds/signers using collateral that is fully backed by only one real lock, since the second bond's `protocol-bond-memberships` entry is silently clobbered by the first's `map-set`.

### Likelihood Explanation
Exploitation requires the attacker to author their own `<signer-manager-trait>` contract (a normal, permissionless action — anyone can implement this trait and pass it as `signer-manager`) and craft it to re-enter `register-for-bond` for a second bond during `signer-manager-validate-stake`. No privileged role, miner cooperation, or other party's key is needed — only the attacker's own transaction and their own signer-manager contract. This matches the "unprivileged-account analog" requirement in the rules.

### Recommendation
Re-validate all pre-callback state (existing membership, unlocked/available balance, per-bond/per-cycle staked totals) *after* `signer-manager-validate-stake` returns, immediately before the `map-set`/accounting-update calls, or move the callback to occur strictly after all state has been committed (mirroring the report's recommendation to perform the untrusted call-out only after balances are finalized). Alternatively, add a reentrancy guard (e.g., a data-var flag checked/set at function entry and cleared at exit) around `register-for-bond`/`update-bond-registration`/`stake`/`stake-update` so that no nested call into these functions can succeed while an outer call is still executing.

### Proof of Concept
1. Attacker deploys `evil-signer-manager.clar` implementing `<signer-manager-trait>`. Its `validate-stake` function, when invoked by pox-5, issues a `contract-call?` back into `pox-5.register-for-bond`, targeting a second `bond-index` (say bond B) with the same `tx-sender`-owned collateral parameters.
2. Attacker calls `pox-5.register-for-bond` for bond A, passing `evil-signer-manager` as `signer-manager`.
3. Inside pox-5's evaluation of bond A: after `total-balance`/`existing-membership` are captured (none/enough), execution reaches `signer-manager-validate-stake`, which re-enters `register-for-bond` for bond B using the same attacker principal.
4. The inner (bond B) call sees the same unmodified state, passes all its checks, writes `protocol-bond-memberships` (bond B), bumps `protocol-bonds-total-staked` for bond B, and adds staker/signer-cycle entries for bond B; the underlying STX lock is applied.
5. Control returns to the outer (bond A) call, which — using its stale, already-passed checks — also writes `protocol-bond-memberships` (bond A, overwriting bond B's record), bumps `protocol-bonds-total-staked` for bond A, and adds staker/signer-cycle entries for bond A.
6. Result: `protocol-bonds-total-staked` for *both* bond A and bond B, and the per-cycle signer/bond weight maps for *both* signers, reflect the attacker's stake — even though only one `protocol-bond-memberships` record and one STX lock exist, corresponding to a single real deposit of collateral. [6](#0-5)

(define-public (register-for-bond
        (bond-index uint)
        (signer-manager <signer-manager-trait>)
        (amount-ustx uint)
        ;; Their BTC lockup info. If the response is `ok`, then
        ;; this is a list of outputs corresponding to their timelocks.
        ;; If the response is `err`, this is the amount of sBTC (in sats)
        ;; that they want to lock.
        (btc-lockup (response {
            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        }
            uint
        ))
        (signer-calldata (optional (buff 500)))
    )
    (let (
            (signer (contract-of signer-manager))
            ;; Compute the sats being staked for this bond.
            (sats-total (try! (match btc-lockup
                l1-lockups (verify-l1-lockups tx-sender bond-index l1-lockups)
                sbtc-amount (ok sbtc-amount)
            )))
            ;; Any bond the staker is currently a member of. Some value here
            ;; means this is a roll-over from an ending bond into a later one.
            (existing-membership (map-get? protocol-bond-memberships tx-sender))
            ;; sBTC currently custodied for the staker's existing bond (0 if
            ;; they have none, or if the existing bond is an L1 lock).
            (old-sbtc (get-staker-custodied-sbtc tx-sender))
            ;; sBTC this new bond needs custodied (0 on the L1 path).
            (new-sbtc (if (is-ok btc-lockup)
                u0
                sats-total
            ))
            ;; Any STX-only stake the staker has. Present means this
            ;; `register-for-bond` is a roll-over from an ending stx-only
            ;; stake into a bond.
            (existing-stake (map-get? staker-info tx-sender))
            (bond (unwrap! (map-get? protocol-bonds bond-index) ERR_BOND_NOT_FOUND))
            (allowance (unwrap!
                (map-get? protocol-bond-allowances {
                    staker: tx-sender,
                    bond-index: bond-index,
                })
                ERR_NOT_ALLOWLISTED
            ))
            (first-reward-cycle (bond-period-to-reward-cycle bond-index))
            (bond-start-height (bond-period-to-burn-height bond-index))
            ;; the first cycle in which their stx are unlocked
            (unlock-cycle (+ first-reward-cycle BOND_LENGTH_CYCLES))
            (current-total-staked (get-total-shares-staked-for-cycle first-reward-cycle
                (some bond-index)
            ))
            (stx-balance (stx-account tx-sender))
            (total-balance (+ (get locked stx-balance) (get unlocked stx-balance)))
        )
        ;; Reject during the prepare phase since next-cycle data is mutated
        (try! (verify-not-prepare-phase))
        ;; Verify that they're sending enough STX
        (asserts!
            (>= amount-ustx
                (min-ustx-for-sats-amount sats-total (get stx-value-ratio bond)
                    (get min-ustx-ratio bond)
                ))
            ERR_INSUFFICIENT_STX
        )

        ;; Verify that the bond hasn't started
        (asserts! (< burn-block-height bond-start-height)
            ERR_BOND_ALREADY_STARTED
        )

        ;; An existing STX-only stake is allowed only if its term ends no
        ;; later than this bond's first reward cycle (no overlap). A stx-only
        ;; stake has no L1 collateral, so there's no L1-unlock-window gate
        ;; here -- the lock just extends forward via the node-side handler.
        (asserts!
            (match existing-stake
                stake-info (<=
                    (+ (get first-reward-cycle stake-info)
                        (get num-cycles stake-info)
                    )
                    first-reward-cycle
                )
                true
            )
            ERR_ALREADY_STAKED
        )

        ;; Cannot stake more sats than their allowance
        (asserts! (<= sats-total allowance) ERR_TOO_MUCH_SATS)

        ;; Must have enough unlocked STX
        ;;  the Staker must have sufficient total funds (locked + unlocked).
        ;;  On a roll-over the staker's STX is still locked by the ending
        ;;  bond; the node-side handler extends that lock to the new amount,
        ;;  so checking only `stx-get-balance` (unlocked) would falsely fail.
        (asserts! (>= total-balance amount-ustx) ERR_INSUFFICIENT_STX)

        ;; Validate that the staker can join this signer
        (try! (signer-manager-validate-stake signer-manager tx-sender bond-index u1
            amount-ustx sats-total true signer-calldata
        ))

        ;; The signer must have been registered already, and its signer key
        ;; grant must still be active.
        (try! (verify-signer-key-grant signer
            (unwrap! (get-signer-info signer) ERR_SIGNER_NOT_FOUND)
        ))

        ;; Reject if an existing membership *overlaps* this bond. An existing
        ;; bond whose staking term ends no later than this bond's first cycle
        ;; (e.g. rolling from bond N into bond N+6) is allowed.
        (asserts!
            (not (bond-overlaps-new-position? existing-membership first-reward-cycle))
            ERR_ALREADY_REGISTERED
        )

        ;; Settle rewards before updating state
        (settle-rewards signer first-reward-cycle (some bond-index))
        (settle-staker-rewards signer first-reward-cycle (some bond-index)
            tx-sender
        )

        ;; A rollover from a non-overlapping existing bond may only happen in
        ;; that bond's L1 unlock window, the last 1/2 cycle.
        (try! (verify-bond-rollover-window existing-membership))

        ;; Move the staker's custodied sBTC into this bond, transferring only the
        ;; net difference vs. any bond they're rolling over from.
        (try! (roll-sbtc tx-sender old-sbtc new-sbtc))

        (map-set protocol-bond-memberships tx-sender {
            bond-index: bond-index,
            amount-ustx: amount-ustx,
            signer: signer,
            is-l1-lock: (is-ok btc-lockup),
            amount-sats: sats-total,
        })
        (map-set protocol-bonds-total-staked bond-index
            (+ current-total-staked sats-total)
        )
        ;; A roll-over from an ending bond ADDS the new bond's shares but does
        ;; NOT tear down the old bond's per-cycle shares/delegation (unlike
        ;; `update-bond-registration`, which removes then re-adds).
        (try! (add-staker-to-bond-cycles tx-sender signer bond-index first-reward-cycle
            BOND_LENGTH_CYCLES sats-total
        ))

        (try! (add-staker-to-signer-cycles tx-sender signer first-reward-cycle
            BOND_LENGTH_CYCLES amount-ustx false
        ))

        ;; If this was a roll-over from an STX-only stake, clear the
        ;; staker-info entry so `stake-update` / `unstake` can no longer
        ;; reach the now-stale stake. The stake's signer-cycle memberships
        ;; through its original term stay intact (the staker keeps
        ;; participating and earning through that term).
        (if (is-some existing-stake)
            (map-delete staker-info tx-sender)
            true
        )

        (let ((result {
                signer: signer,
                staker: tx-sender,
                amount-ustx: amount-ustx,
                sats-total: sats-total,
                bond-index: bond-index,
                first-reward-cycle: first-reward-cycle,
                unlock-burn-height: (reward-cycle-to-burn-height unlock-cycle),
                unlock-cycle: unlock-cycle,
                is-l1-lock: (is-ok btc-lockup),
                btc-lockup: (match btc-lockup
                    l1-info {
                        type: "l1",
                        txs: (some (map get-l1-lockup-summary (get outputs l1-info))),
                    }
                    sbtc-amount {
                        type: "l2",
                        txs: none,
                    }
                ),
            }))
            (print (merge { topic: "register-for-bond" } result))
            (ok result)
        )
    )
)
