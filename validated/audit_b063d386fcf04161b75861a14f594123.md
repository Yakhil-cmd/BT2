### Title
Cross-organization webhook confusion: signature verified against the payload's `repository.owner.login`, but stack lookup uses the unbound `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a webhook's HMAC against based on `params.dig('repository','owner','login')` (or `organization.login`), while every event handler (`PushHandler`, the `PullRequest::*Handler`s, `MembershipHandler`, etc.) resolves the actual `Repository`/`Stack`/`Team` to mutate using a *different, unbound* field of the same JSON body (`repository.full_name`, `organization.login`, `team.id`). Because the field used to pick the verifying secret is never checked for consistency against the field(s) used to decide what gets written, the "organization that authenticated" and "the repository that is written" are two independently attacker-influenced values inside a single payload whose integrity is only checked as a whole blob, not field-by-field-bound.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is derived purely from the payload body: [2](#0-1) .

`Shipit.github(organization:)` looks up per-organization app configuration and, critically, falls back to a single shared config (`secrets.github`) whenever `github_default_organization` is `nil` (single-app deployments, the documented default setup): [3](#0-2) . In this (most common, documented) single-GitHub-App configuration, *every* organization/repository routes to the exact same `GitHubApp` instance and the exact same `webhook_secret`, so the value of `repository_owner` has no effect on which secret is used to verify the signature — it is purely decorative for logging, yet the code still treats verification as if it were organization-scoped.

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3)  hands the raw, HMAC-verified JSON to handlers that independently resolve the target repository/organization from *other* fields in the same body:
- `PushHandler` resolves stacks via `Handler#stacks` → `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository','full_name')` [5](#0-4) , then syncs any matching stack's branch: [6](#0-5) .
- `PullRequest::OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc. resolve `repository` the same way via `params.repository.full_name`, then archive/unarchive/create review stacks: [7](#0-6) .
- `MembershipHandler` creates/updates `Team`s and adds/removes `User` memberships keyed on `params.organization.login` and `params.team.id`, unrelated to `repository.owner.login`: [8](#0-7) .

No code path cross-checks that the organization used to select the verifying secret (`repository.owner.login`/`organization.login`) is the same organization that owns the repository actually being written to (`repository.full_name`, `organization.login` used by handlers). In the shared single-app configuration this discrepancy is invisible because there is only one secret anyway; but the controller's own logic (`Shipit.github(organization: repository_owner)`, the `GithubOrganizationUnknown` rescue, and the `secrets_double_github_app.yml`-documented multi-org feature) demonstrates that Shipit explicitly supports and documents a mode where *different organizations use different webhook secrets*, i.e. where `repository_owner` is meant to be an authorization-relevant credential-selection input. In that supported multi-org mode, the signature is verified strictly against the App belonging to the org named in `repository.owner.login`/`organization.login`, but the record actually mutated (which `Stack`, which `Repository`, which `Team`, which `PullRequest`) is driven by the unrelated `repository.full_name` / `team.id` fields, which are not required to belong to the same organization and are not re-validated against the verified org.

### Impact Explanation
Where Shipit is configured with multiple GitHub Apps (multi-org mode, as in `test/dummy/config/secrets_double_github_app.yml`), an attacker who can produce a validly-signed webhook body for one configured organization (e.g. because they administer a repository/App installation under Org A, which is a legitimate, unprivileged-relative-to-Org-B position) can set `repository.full_name` (or `organization.login` for membership events) to point at a *different* organization's (Org B's) repository/team while keeping `repository.owner.login` set to Org A so the signature validates with Org A's secret. This lets an attacker with standing under Org A trigger `GithubSyncJob`/`sync_github`, archive or create Review Stacks, or mutate `Team`/`Membership` records that belong to Org B's stacks — i.e. cross-organization writes to state that should only be reachable by Org B's own authenticated webhooks. This directly matches the report's "impact bucket": cross-repository writes achieved by breaking the binding between the entity whose credential authenticated the request and the entity whose data gets written.

### Likelihood Explanation
Exploitability depends entirely on the deployment topology:
- In the default single-GitHub-App configuration (the vast majority of deployments per `docs/setup.md`), the vulnerability is not observable as a *cross-organization* issue because there is only one secret/org scope to begin with — though it does show the code's authorization model is purely payload-derived and non-binding by design.
- In the documented multi-org configuration, exploitation requires the attacker to already be able to produce a validly-signed webhook payload for at least one configured organization (e.g., by being an admin of a repository under that org whose GitHub App can emit real webhooks). That is a real but non-trivial precondition, and I was unable to fully verify (given tool/iteration limits) whether GitHub App webhook secrets are per-installation or per-App-globally-shared in this codebase's model, which affects how "unprivileged" the precondition truly is. This uncertainty should be resolved by a maintainer/deep session before assigning a severity.

### Recommendation
After signature verification, re-derive the authorized organization from the verified request and require that every entity resolved by handlers (`Repository.from_github_repo_name`, `Team`/`organization.login` in `MembershipHandler`, etc.) belongs to that same, cryptographically-verified organization before performing any writes. Do not treat `repository.owner.login`/`organization.login` as sufficient proof of scope unless it is checked against the resource the handler is about to mutate.

### Proof of Concept
Not independently executable within the scope of this review (requires standing up a multi-GitHub-App Shipit instance with two configured organizations and a legitimately-obtainable signed webhook for one of them); the code paths cited above show mismatched binding between the field used for signature-org selection (`app/controllers/shipit/webhooks_controller.rb:59-62`) and the fields used for record resolution in every handler (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `push_handler.rb:12-17`, `pull_request/opened_handler.rb:50-54`, `membership_handler.rb:22-43`).

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end
```
