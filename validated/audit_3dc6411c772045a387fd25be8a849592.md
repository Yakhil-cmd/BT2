### Title
Ruby operator precedence bug in `OpenedHandler#provision?` bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` repos - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`review_stacks_enabled` defaults to `false` and is documented/intended as the operator's master opt-in switch for review-stack provisioning. Due to Ruby's `&&`/`||` precedence in `OpenedHandler#provision?`, that flag is only actually applied to the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches are unconditionally evaluated regardless of `review_stacks_enabled`, so an attacker who can attach a matching label to their own PR can trigger stack creation and provisioning even when review stacks are disabled.

### Finding Description
The claimed binding is: `review_stacks_enabled == true` should be a necessary precondition for provisioning under any provisioning behavior. The code: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

`&&` has higher precedence than `||` in Ruby, so this parses as:

```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
```

`review_stacks_enabled` is only ANDed into the first disjunct. The second and third disjuncts — which cover `allow_with_label` and `prevent_with_label` — are evaluated independent of `review_stacks_enabled`. So if a repository has `provisioning_behavior = :allow_with_label` (or `:prevent_with_label`) but `review_stacks_enabled = false` (the column default per [2](#0-1) ), `provision?` still returns `true` whenever the PR label condition matches.

`process` calls this directly on the `opened` webhook with no authentication other than the payload matching a tracked repository name: [3](#0-2) 

An attacker who opens a PR against a tracked repository configured with `provisioning_behavior: allow_with_label` and any `provisioning_label_name` (label names are visible on GitHub's public UI) and attaches that label to their own PR causes `ReviewStackAdapter#create!` to run, creating a `Stack`/`ReviewStack` row and queuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [4](#0-3) 

This eventually results in the queued provisioning task executing `shipit.yml` steps for that stack/environment — the intended `review_stacks_enabled` gate never engaged.

None of the existing guards prevent this: the webhook signature check (out of scope for this trace) only verifies the request came from GitHub for *some* repository, `respond_to_pull_request_opened?` merely checks `action == "opened"` then defers entirely to the broken `provision?`, and there is no separate check of `review_stacks_enabled` anywhere else in the call chain. The `ExplicitParameters` schema validates payload shape only, not authorization. Existing tests never exercise `provisioning_enabled: false` combined with `allow_with_label`/`prevent_with_label` — every test that sets `provisioning_enabled: false` uses `behavior: :allow_all` ( [5](#0-4) ), so the gap is untested and unnoticed. The analogous handlers (`LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`) correctly AND `review_stacks_enabled` as a separate top-level condition (`respond_to_label_change?`/`respond_to_pull_request_reopened?`), confirming `OpenedHandler#provision?` is the outlier with the precedence defect.

### Impact Explanation
Any unauthenticated PR-opener on a tracked GitHub repository can force Shipit to create a `Stack` row and enqueue a provisioning task for a repository that explicitly has review-stack auto-provisioning turned off (`review_stacks_enabled: false`), purely by naming/guessing the configured label and attaching it to their own PR. The queued provisioning task runs `Command`/shell steps defined in the repo's `shipit.yml` for the review-stack provisioning handler — an unauthorized deploy/execution triggered without the operator's intended opt-in. This is repeatable against any repository configured with `allow_with_label` or `prevent_with_label` behavior (the default `provisioning_behavior` is `allow_all`, but any repo that has been explicitly configured with the label-based behaviors while leaving `review_stacks_enabled` at its default `false` is exposed). Impact matches "Critical: unauthorized deploy triggered."

### Likelihood Explanation
Preconditions are narrow but plausible: the repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (not the `allow_all` default) while `review_stacks_enabled` remains `false` — i.e., an operator partially configured provisioning behavior without flipping the enable switch, or intentionally disabled review stacks after having set a label-based behavior. `provisioning_label_name` is attacker-discoverable via the repo's public label list on GitHub. Attacker cost is a single PR open + one label add (or two near-simultaneous webhook deliveries), fully unauthenticated relative to Shipit. The bug is code-level (Ruby operator precedence), deterministic, and repeatable on every matching repository/PR.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three behavior branches:

```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:

```ruby
test "does not create stacks for repos with allow_with_label when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```

Assert both sides of the binding: `repository.review_stacks_enabled == false` and expected provisioning outcome `Shipit::Stack.count` unchanged / no `Shipit::ReviewStackProvisioningQueue.add` call. Against current code this test fails (a Stack row is created and queued), demonstrating the divergence; after applying the recommended fix it passes.
