### Title
CheckSuiteHandler cross-tenant job scheduling via mismatched `repository.owner.login` and `repository.full_name` in webhook payload - (File: app/models/shipit/webhooks/handlers/check_suite_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC-verifying organization from `payload.dig('repository','owner','login')`, while `CheckSuiteHandler`/`Handler#stacks` resolves the target `Stack`/`Commit` from the separate, unvalidated field `payload.dig('repository','full_name')`. Because nothing ties these two fields together, an attacker who can produce a valid signature for their own (or secret-less) organization can name an arbitrary victim `repository.full_name`, causing `Commit#schedule_refresh_check_runs!` to run for a commit belonging to an organization that never authenticated the request.

### Finding Description
Binding claimed: `verifying_org (from repository.owner.login) == owning_org (from repository.full_name)`. Tracing the code shows these are two independent reads of the same top-level `params`/`payload` hash with no cross-check:

- `app/controllers/shipit/webhooks_controller.rb:24-30,59-62` — `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)` to verify `X-Hub-Signature` against `request.raw_post`. [1](#0-0) [2](#0-1) 

- `app/models/shipit/webhooks/handlers/handler.rb:32-38` — `stacks` resolves via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, a completely different key path from the same JSON body. [3](#0-2) 

- `app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17` — `process` uses `stacks.where(branch: params.check_suite.head_branch)` and, within it, `stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)`, with no re-derivation or verification of ownership beyond that already-decoupled `stacks` scope. [4](#0-3) 

- `app/models/shipit/repository.rb:53-56` — `from_github_repo_name` simply splits `full_name` on `/` and does a `find_by(owner:, name:)`, with no comparison to the org that satisfied signature verification. [5](#0-4) 

Exploit flow: attacker administers (or has legitimate access to configure) their own org in Shipit and therefore knows their own `webhook_secret` (or the org has none, per the question's premise). They POST directly to `/webhooks` with `X-Github-Event: check_suite`, a signature computed with their known secret, and a JSON body where `repository.owner.login = "attacker-org"` (so `verify_signature` succeeds against the attacker's own secret) but `repository.full_name = "victim-org/victim-repo"` and `check_suite.head_sha`/`head_branch` set to a real victim commit/branch. `verify_signature` passes because it only checks the attacker's own org's HMAC; `CheckSuiteHandler#process` then resolves the real victim `Repository`/`Stack`/`Commit` from `full_name` and calls `schedule_refresh_check_runs!` on it. No code path re-derives or asserts that the verified org equals the owner encoded in `full_name`.

### Impact Explanation
The attacker can force `RefreshCheckRunsJob.perform_later(commit_id:)` to be enqueued and run against any victim commit whose repo `full_name`, branch, and sha they can name (often discoverable via the victim's public GitHub repo). This is unauthorized cross-tenant job scheduling: a request that authenticated as tenant A causes work item creation scoped to tenant B's `Stack`/`Commit`, directly matching the Critical category "a payload for one repository mutating another's stack, commit, task or team". It is repeatable per request against any Shipit-tracked repository and requires no privileges beyond control of one legitimate (or secret-less) tenant.

### Likelihood Explanation
Requires the attacker to control (or know the secret of) at least one organization onboarded into Shipit, or to target an org configured with no `webhook_secret` — both scenarios explicitly allowed by the question's threat framing. Crafting the payload is trivial (direct HTTP POST with attacker-chosen JSON body), and the victim's branch/sha values are typically public GitHub information. No GitHub-side webhook needs to actually fire; the attacker sends the HTTP request directly to the Shipit host.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, derive the organization used for signature verification and the organization used to resolve `stacks`/`Repository` from the same trusted value, and explicitly assert they match before processing (e.g., have `Handler#stacks` verify that `Repository.from_github_repo_name(repository_name).owner` equals the `repository_owner` that satisfied signature verification, rejecting the event otherwise).

### Proof of Concept
Minitest plan (e.g., extending `test/controllers/webhooks_controller_test.rb`, no live GitHub):
1. Create two fixtures: `attacker_org` with a known `webhook_secret` configured via `Shipit.github(organization: 'attacker-org')`, and `victim_org` owning `shipit_stacks(:shipit)`/`shipit_commits(:first)` with branch `master` and a known `sha`.
2. Build a `check_suite` JSON body: `{"repository" => {"owner" => {"login" => "attacker-org"}, "full_name" => "victim-org/victim-repo"}, "check_suite" => {"head_sha" => victim_commit.sha, "head_branch" => "master"}}`.
3. Compute `X-Hub-Signature` using `attacker-org`'s secret over the raw JSON body; set `X-Github-Event: check_suite`.
4. POST to `/webhooks` and assert `response.status == 200` (signature accepted for `attacker-org`).
5. Assert equality-before: `verifying_org = "attacker-org"`, `owning_org = victim_commit.stack.repository.owner # => "victim-org"` — these differ.
6. Assert `RefreshCheckRunsJob` was enqueued with `commit_id: victim_commit.id` (e.g., via `assert_enqueued_with(job: RefreshCheckRunsJob, args: [commit_id: victim_commit.id])`), proving `schedule_refresh_check_runs!` executed on the victim's `Commit` despite verification against the attacker's org.
