### Title
Missing length validation on ephemeral pubkeys before native ECDH allows malformed-buffer input in device message decryption - (File: device.js)

### Summary
`decryptPackage()` in `device.js` derives a shared secret from an attacker-controlled `sender_ephemeral_pubkey`/`recipient_ephemeral_pubkey` field taken from a device message, but never validates the decoded buffer's length before handing it to the native `secp256k1` ECDH binding, mirroring the PJSIP root cause of trusting a size formula that does not bound the actual attacker-supplied data before a native/low-level buffer operation.

### Finding Description
In the PJSIP CVE, `dec_frame[].buf` was sized using a fixed PCM-derived formula, but `codec_parse()` could hand back encoded data up to `MAX_ENCODED_PACKET_SIZE`, and `pj_memcpy()` copied `input->size` bytes without checking it against the allocated buffer — a mismatch between the assumed/allocated size and the actual attacker-influenced size that feeds directly into a raw memory copy.

The analogous pattern in `ocore` is in the end-to-end device-message decryption path:

- `network.js` "hub/deliver" only checks that `objDeviceMessage.encrypted_package.dh.sender_ephemeral_pubkey` and `.recipient_ephemeral_pubkey` are present and are strings; it never checks their decoded byte length. [1](#0-0) 
- `device.js`'s `decryptPackage()` again only checks `typeof ... !== 'string'` for `dh.sender_ephemeral_pubkey`/`dh.recipient_ephemeral_pubkey` before matching them against known key strings (`objMyTempDeviceKey.pub_b64`, etc.) and, on match, calls `deriveSharedSecret(objEncryptedPackage.dh.sender_ephemeral_pubkey, priv_key)`. [2](#0-1) [3](#0-2) 
- `deriveSharedSecret()` decodes the attacker-supplied base64 string into a `Buffer` with no length check and passes it straight into the native `secp256k1` module's `ecdh()` call: `new Buffer(peer_b64_pubkey, 'base64')` → `ecdsa.ecdh(pubkey, privKey, {hashfn:(x,y)=>x}, Buffer.alloc(32))`. [4](#0-3) 

Elsewhere in the codebase, every other place that accepts a public key enforces `isStringOfLength(pubkey, constants.PUBKEY_LENGTH)` before doing anything cryptographic with it (e.g., `hub/get_temp_pubkey`, `hub/temp_pubkey`, `sig` authentifier checks). [5](#0-4) [6](#0-5)  The `dh.sender_ephemeral_pubkey`/`recipient_ephemeral_pubkey` path is a rare place where this normal invariant is skipped, and the value goes straight into a native compiled binding rather than a pure-JS crypto primitive. This is structurally the same defect class as the PJSIP bug: a value whose size is assumed/expected to conform to a fixed cryptographic format is passed to a lower-level (here, native) routine without confirming the actual byte length matches that assumption.

### Impact Explanation
`secp256k1`'s native binding is expected to validate public key encodings internally and reject malformed lengths; if that validation is bypassed or incomplete in the specific version/binding bundled with this build, an out-of-bounds read/crash in the native addon is possible from a value fully controlled by any paired device or by a hub relaying a `hub/deliver` message — i.e., reachable by any unprivileged party able to send a device message. Because this is normal device-messaging traffic, exploitation does not require operator privileges, a malicious peer/hub/node role, or network-level access beyond what a legitimate correspondent already has.

### Likelihood Explanation
Exploitability depends entirely on whether the underlying native `secp256k1` binding performs strict length/format checks before touching its internal buffers; well-maintained builds of this library generally do validate and throw a JS exception rather than corrupt memory, which is the deciding factor and could not be confirmed from the JS-level code alone (the native module source is outside the indexed JS codebase). Absent that guarantee, the missing application-level length check is a clear defect that removes a defense-in-depth layer that exists everywhere else pubkeys are handled in this codebase.

### Recommendation
Add an explicit `ValidationUtils.isStringOfLength(dh.sender_ephemeral_pubkey, constants.PUBKEY_LENGTH)` / `isStringOfLength(dh.recipient_ephemeral_pubkey, constants.PUBKEY_LENGTH)` check in both `network.js`'s `hub/deliver` handler and `device.js`'s `decryptPackage()`/`deriveSharedSecret()` before any base64 decode or ECDH call, matching the validation pattern already used for every other pubkey field in the codebase.

### Proof of Concept
1. A paired device (or hub acting on a peer's behalf) crafts a `hub/deliver` (or direct `hub/message`) payload where `encrypted_package.dh.sender_ephemeral_pubkey` is a base64 string decoding to a buffer shorter or longer than the expected 33-byte compressed pubkey (e.g., 1 byte or 200 bytes), while `recipient_ephemeral_pubkey` matches the victim's known temp/permanent key so `decryptPackage()` selects a `priv_key` and proceeds.
2. The message passes the `typeof ... === 'string'` check in both `network.js` (`hub/deliver`) and `device.js` (`decryptPackage`), since no length constraint is applied. [7](#0-6) [8](#0-7) 
3. `deriveSharedSecret()` decodes this malformed value into a `Buffer` and passes it directly to `ecdsa.ecdh(...)`, the native `secp256k1` binding, with no application-level bounds check beforehand. [9](#0-8) 
4. Whether this yields a crash, undefined behavior, or a safely-thrown error depends on the native binding's own validation, which was not verifiable from the indexed JS sources — flagged here as a defect (missing defense-in-depth) rather than a confirmed memory-corruption proof.
