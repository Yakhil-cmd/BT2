### Title
Multisig transaction executor can execute a different payload than the one approved by owners when `abort_if_multisig_payload_mismatch` is disabled - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`validate_multisig_transaction`, the Move function invoked by the VM prologue during mempool admission and execution of a multisig transaction, is supposed to bind the number of collected owner approvals to the *specific payload* that will actually be executed. When a multisig transaction is created via `create_transaction` (full payload stored on-chain, no hash), the code that verifies the payload submitted at execution time matches the payload that owners voted on is gated entirely behind the `abort_if_multisig_payload_mismatch` feature flag.

### Finding Description
`create_transaction` stores the full approved payload on-chain and leaves `payload_hash` as `None`: [1](#0-0) 

`validate_multisig_transaction` is the function the VM calls (via `run_multisig_prologue`) both during mempool admission and as the first execution step: [2](#0-1) 

The quorum/timelock checks (lines 1335–1359) only verify that *enough owners approved the pending transaction at this sequence number* — they never look at the `payload` argument that the executor (any owner) supplies to the entry function being run. The only code that ties the supplied `payload` back to what was actually approved is:
- Lines 1365–1371: only runs when `transaction.payload_hash.is_some()`, i.e. only for transactions created via `create_transaction_with_hash`.
- Lines 1375–1384: only runs when `features::abort_if_multisig_payload_mismatch_enabled()` is true **and** `transaction.payload.is_some()` **and** the supplied `payload` is non-empty.

For a transaction created with `create_transaction` (the common/default path, `payload_hash` is `None`), if the `abort_if_multisig_payload_mismatch` feature is not enabled, **no comparison between the supplied execution payload and the on-chain stored/approved payload is performed at all**. The quorum check only validates that N owners approved *a* transaction at that sequence number — not that they approved *this exact payload*.

On the Rust/VM side, `run_multisig_prologue` derives `provided_payload` directly from the caller-supplied `TransactionExecutableRef` of the signed transaction (i.e., attacker-controlled), not from the on-chain approved payload: [3](#0-2) 

This confirms the "provided_payload" is fully under the control of whichever owner submits the execution transaction, and is passed straight into `validate_multisig_transaction` where — absent the feature flag — it is never checked against the payload that was actually voted upon.

### Impact Explanation
This breaks the core multisig authorization invariant: approvals collected for payload A can be spent to execute payload B. Any single owner who is one of the multisig's authorized executors (needs no special privilege beyond being an owner) can submit a multisig-execution transaction whose actual entry-function call differs from what the other owners approved, while quorum/timelock checks still pass because they only key off the transaction's sequence number, not its content. This is a classic pre-admission "approval-set confusion" — the wrong signer/approval set is treated as authorizing the executed call — which can lead to unauthorized state transitions/fund transfers being committed under the guise of a legitimately-approved multisig transaction.

### Likelihood Explanation
Likelihood depends entirely on whether the `abort_if_multisig_payload_mismatch` feature flag is enabled on-chain. I was not able to conclusively determine its default/rollout status from the indexed code (only the `features.move`/`features.spec.move` definitions and flag-check call sites were found, not a definitive "default enabled on mainnet" confirmation). If the flag is disabled or not yet fully rolled out on any given network instance using this framework snapshot, this issue is directly and trivially exploitable by any account owner of an affected multisig, with no other preconditions.

### Recommendation
- Make payload-vs-approval binding unconditional (not feature-gated) for the `create_transaction` (full on-chain payload) path: always assert `payload == *stored_payload` when `transaction.payload.is_some()`, regardless of `abort_if_multisig_payload_mismatch_enabled()`.
- Audit why this check was ever made optional via a feature flag, and if it must remain gated for migration purposes, ensure the flag is enabled by default before any multisig accounts using `create_transaction` are reachable.

### Proof of Concept
1. Multisig account `M` requires 2-of-3 approvals.
2. Owner A calls `create_transaction(M, payload_A)` where `payload_A` calls `transfer(recipient_A, 100)`. Owner B approves. Quorum (2) is met for sequence number `N`.
3. Instead of executing `payload_A`, owner A (or any owner who is an authorized executor) submits a signed transaction whose actual `TransactionExecutableRef` is `payload_B` = `transfer(recipient_attacker, 100000)`.
4. `run_multisig_prologue` computes `provided_payload` from this attacker-chosen executable and passes it to `validate_multisig_transaction`.
5. Because `transaction.payload_hash` is `None` (created via `create_transaction`) and `abort_if_multisig_payload_mismatch_enabled()` is false, no comparison between `payload_B` and the stored `payload_A` occurs; the quorum/timelock checks pass since they only check sequence number `N`.
6. `payload_B` executes and commits with the multisig account's authority, despite never having been approved by owner B.

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }

    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },

            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
