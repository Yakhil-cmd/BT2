### Title
Malicious Bridge Operator Can Front-Run `requestKLAYTransfer`/Fallback to Drain User KLAY via Uncapped Fee Manipulation — (`contracts/service_chain/bridge/BridgeFee.sol`, `BridgeTransferKLAY.sol`, `BridgeOperator.sol`)

---

### Summary

The Kaia service-chain bridge reads `feeOfKLAY` at transaction execution time rather than at submission time, and a single bridge operator (default `operatorThresholds[Configuration] = 1`) can change that fee instantly with no timelock. A malicious operator can front-run any pending user bridge request, raise the fee to just below `msg.value`, and redirect nearly all of the user's KLAY to the `feeReceiver`.

---

### Finding Description

**Root cause — `BridgeOperator.sol` constructor, line 56:**

```solidity
constructor() internal {
    for (uint8 i = 0; i < uint8(VoteType.Max); i++) {
        operatorThresholds[uint8(i)] = 1;   // single operator suffices
    }
    ...
}
```

The default `Configuration` vote threshold is **1**, so a single operator can call `setKLAYFee` and have it take effect immediately in the same block. [1](#0-0) 

**Root cause — `BridgeFee.sol` `_payKLAYFeeAndRefundChange`, line 44:**

```solidity
function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
    uint256 fee = feeOfKLAY;   // reads live storage at execution time
    ...
    require(_feeLimit >= fee, "insufficient feeLimit");
    (bool ok, ) = feeReceiver.call.value(fee)("");
    ...
}
```

The fee is read from storage at execution time, not captured at submission time. [2](#0-1) 

**Root cause — `BridgeTransferKLAY.sol` fallback, line 128:**

```solidity
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
```

The fallback passes the **current** `feeOfKLAY` as `_feeLimit`. If the fee has been raised between submission and execution, the user's entire `msg.value` minus a tiny epsilon is consumed as fee, and only epsilon is bridged. [3](#0-2) 

The amount bridged is computed as `msg.value.sub(_feeLimit)`: [4](#0-3) 

`setKLAYFee` has no cap and no timelock: [5](#0-4) 

---

### Impact Explanation

A malicious operator observes a pending fallback transaction with `msg.value = V` in the mempool. The operator submits `setKLAYFee(V − ε, configNonce)` with higher gas to front-run it.

When the user's fallback executes:
- `_feeLimit = feeOfKLAY = V − ε`
- `require(msg.value > _feeLimit)` → `V > V − ε` → **passes**
- Fee paid to `feeReceiver` = `V − ε`
- Amount bridged = `msg.value − _feeLimit = ε` (near zero)

The user loses `V − ε − F_original` KLAY to the fee receiver — an **unauthorized transfer of bridged KLAY assets** to the operator-controlled `feeReceiver`.

---

### Likelihood Explanation

- Default `operatorThresholds[Configuration] = 1` means **any single operator** can execute this attack unilaterally without collusion.
- The attack is executable on any EVM-compatible chain where transaction ordering is observable (mempool visibility), which applies to Kaia service chains.
- The `feeReceiver` is set by the bridge owner and can be the operator's own address.

---

### Recommendation

1. **Add a user-specified max-fee parameter** to `requestKLAYTransfer` and the fallback so the transaction reverts if `feeOfKLAY` exceeds the user's tolerance (analogous to the Teller fix of allowing lenders to specify a max fee).
2. **Enforce a timelock** on `setKLAYFee` / `setERC20Fee` so fee changes cannot take effect in the same block they are voted on.
3. **Raise the default `Configuration` threshold** to require multi-operator consensus before any fee change is applied.

---

### Proof of Concept

```
State before:
  feeOfKLAY = 0.4 KLAY
  feeReceiver = operator's address

1. User submits: bridge.fallback{value: 1.4 ether}()
   (expecting to bridge 1.0 KLAY, pay 0.4 KLAY fee)

2. Operator front-runs (higher gas):
   bridge.setKLAYFee(1.39 ether, configNonce)
   → feeOfKLAY = 1.39 KLAY (takes effect immediately, threshold=1)

3. User's fallback executes:
   _requestKLAYTransfer(user, feeOfKLAY=1.39e18, "")
   require(1.4e18 > 1.39e18)  ✓
   _payKLAYFeeAndRefundChange(1.39e18):
     fee = feeOfKLAY = 1.39e18
     require(1.39e18 >= 1.39e18)  ✓
     feeReceiver.call{value: 1.39e18}()  ← operator receives 1.39 KLAY
     refund = 0
   amount bridged = msg.value - _feeLimit = 1.4e18 - 1.39e18 = 0.01 KLAY

Result:
  User intended: bridge 1.0 KLAY, pay 0.4 KLAY fee
  Actual:        bridge 0.01 KLAY, pay 1.39 KLAY fee
  Stolen:        0.99 KLAY transferred to operator-controlled feeReceiver
```

```text
    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }
```
