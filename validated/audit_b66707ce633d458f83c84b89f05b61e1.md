### Title
Webhook signature verification is bound to an attacker-chosen organization, not to the repository/commit actually mutated - enabling authentication bypass and unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against using an organization name taken directly from the attacker-controlled JSON body, not from any authenticated GitHub metadata. Handlers such as `StatusHandler` then mutate data (commit statuses, which can trigger continuous deployment) by looking the commit up **globally by SHA**, with no check that the commit's repository/organization matches the organization whose secret validated the request. This breaks the intended binding "organization that authenticated == repository/commit that is written."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to validate against like this: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is derived from the **request body itself**: [2](#0-1) 

The engine explicitly supports multiple GitHub App configurations (one per organization), and per-organization `webhook_secret` is optional. When it is blank, `GitHubApp#verify_webhook_signature` **short-circuits to `true` with no verification at all**: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```

This multi-org, optional-secret setup is a first-class, documented configuration (see `test/dummy/config/secrets_double_github_app.yml`, where `OrgTwo` has `webhook_secret: # nil`, and `docs/setup.md` describing `github.webhook_secret` as something you copy in "if you've set" one).

Once signature verification passes (trivially, for the org with no secret), the event is dispatched to handlers keyed only by `X-Github-Event`. `StatusHandler` looks up the target commit **globally by SHA, with no repository/organization scoping whatsoever**: [4](#0-3) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

So an attacker who knows (a) that some organization configured in this Shipit instance has no `webhook_secret`, and (b) the SHA of a commit tracked under a *completely different, properly-secured* organization/repository, can send a forged `status` event claiming to be from the unsecured organization. The signature check passes unconditionally, and `StatusHandler` will still create a `Status` for the targeted commit, because the lookup by SHA never verifies which repository/organization the commit belongs to.

### Impact Explanation
Creating a `Status` record drives `Commit#add_status`, which — when the new state is `success` — calls `stack.schedule_merges` and, via `Status#schedule_continuous_delivery` / `Deploy` state machine hooks, can trigger `ContinuousDeliveryJob` for stacks with `continuous_deployment: true`: [5](#0-4) [6](#0-5) 

This means an attacker with no Shipit session, no `ApiClient` token, and no knowledge of the target organization's real webhook secret can forge a "CI success" status for an arbitrary tracked commit, causing an unauthorized deploy to be scheduled — meeting the "unauthorized deploy" Critical impact bar.

### Likelihood Explanation
Exploitation requires: (1) the Shipit instance to be configured for more than one GitHub organization where at least one has no `webhook_secret` set (a supported, documented configuration, not a misconfiguration against docs), and (2) knowledge of a target commit SHA (commit SHAs are typically public on GitHub). Both conditions are plausible in real multi-tenant Shipit deployments and require no privileged credentials.

### Recommendation
- Never derive the "identity" used for signature verification from the same untrusted payload that is later used to select which data to mutate. At minimum, cross-check that `repository.full_name` / `repository.owner.login` used by handlers matches the `repository_owner` that successfully authenticated the request.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank; either require a secret for every configured organization or explicitly disable webhook processing for organizations without one.
- Scope `StatusHandler` (and other handlers that look up by SHA only) to the repository named in the payload, verified against the authenticating organization, rather than a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Configure Shipit with two GitHub App orgs, e.g. `OrgA` (real secret) and `OrgB` (no `webhook_secret`), as already exercised in `test/dummy/config/secrets_double_github_app.yml`.
2. Obtain the SHA of a tracked commit belonging to a stack under `OrgA` (public on GitHub).
3. POST to `/github/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature` (or any bogus value), and body:
```json
{
  "organization": { "login": "OrgB" },
  "sha": "<sha-of-OrgA-tracked-commit>",
  "state": "success",
  "context": "ci/forged"
}
```
4. `verify_signature` calls `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
5. `StatusHandler#process` finds the commit by SHA (no org check) and creates a `success` `Status`, potentially triggering `ContinuousDeliveryJob` for the `OrgA` stack — an unauthorized deploy triggered without ever knowing `OrgA`'s webhook secret.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
