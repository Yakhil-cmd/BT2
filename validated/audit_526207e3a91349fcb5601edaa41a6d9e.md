### Title
Attacker-controlled swap routes can invoke unauthorized token transfers under the caller's authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` and the other router-backed strategy entrypoints accept opaque, caller-controlled route bytes and forward them to the configured router without constraining which contracts the route may invoke. A malicious route can therefore place attacker-deployed contract code inside the caller-authorized invocation tree and cause an unrelated token transfer from the caller if the caller signs the simulation-produced authorization tree.

### Finding Description
`process_swap_collateral` authenticates the caller and verifies ownership or delegation for `account_id`, but it passes the unvalidated `swap` bytes into `withdraw_and_swap_from_supply`. [1](#0-0) [2](#0-1) 

`swap_tokens` snapshots balances, authorizes only the exact input transfer from the controller to the router, and invokes `execute_strategy` with the caller-controlled route. [3](#0-2) 

That narrowly scoped controller authorization protects the controller's input token, but it does not constrain arbitrary child calls that the route makes under the original caller's authorization. [4](#0-3) 

The security test demonstrates the resulting authorization-tree injection: a route-selected hop contract is invoked, calls `token.transfer(victim, attacker, amount)`, and the unauthorized-wallet transfer appears as a child of the victim's `swap_collateral` authorization during simulation. [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
A malicious route can steal tokens unrelated to the lending position rather than merely returning a poor swap price. [8](#0-7) 

The theft is not bounded by the collateral amount, controller input authorization, output minimum, or final account-risk check because the malicious token call uses a separate caller-authorized child invocation. [9](#0-8) [10](#0-9) 

This is analogous to the Xen issue's arbitrary pointer dereference: an opaque route-supplied contract address is treated as executable code and reaches operations outside the intended swap boundary. [11](#0-10) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious route contract and supply the poisoned route through any path used to generate `swap` bytes. [12](#0-11) 

The victim must initiate or sign the affected strategy call, and enforcement rejects the malicious transfer if the signed authorization tree omits the injected child. [13](#0-12) 

However, simulation records the malicious transfer under the victim's root invocation, so a client that signs the returned authorization tree without independently validating every child enables the theft. [14](#0-13) 

The same pattern is reachable through the other router-backed unprivileged strategy entrypoints, including `multiply`, `swap_debt`, and `repay_debt_with_collateral`, whenever they use a non-empty route. [15](#0-14) 

### Recommendation
Do not allow route payloads to name arbitrary executable venue contracts. Decode or reference only a governance-controlled venue registry, or require the router to maintain an explicit venue allowlist and reject any hop whose pool/venue address is not registered. [11](#0-10) 

Clients should also reject authorization trees containing any child invocation other than the expected input-token transfer and must not blindly sign simulation-produced trees. This is defense-in-depth rather than a substitute for venue validation. [4](#0-3) 

### Proof of Concept
1. The victim owns a debt-free account holding listed collateral, plus an unrelated wallet token that the lending protocol never listed. [16](#0-15) 
2. The attacker deploys a contract whose route handler calls `wallet_token.transfer(victim, attacker, victim_balance)` and embeds that contract address in the route bytes. [17](#0-16) [18](#0-17) 
3. The victim invokes `swap_collateral(caller=victim, account_id, current=USDC, amount=5_000_USDC, new=ETH, swap=poisoned_route)`. [12](#0-11) 
4. The controller forwards the route to the configured router; the router invokes the route-selected malicious pool, which performs the unrelated wallet-token transfer. [11](#0-10) [5](#0-4) 
5. Simulation records the wallet-token transfer as a child of the victim's `swap_collateral` authorization and empties the victim's unrelated wallet-token balance. [19](#0-18) 
6. Under enforcement, the same malicious route succeeds when that injected child is included in the signed authorization tree, while an honest tree without it reverts. [20](#0-19)
