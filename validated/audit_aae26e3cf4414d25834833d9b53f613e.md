### Title
Embedded literal `---` in a hookify frontmatter value truncates parsing and silently downgrades `action: block` to default `warn` - (File: plugins/hookify/core/config_loader.py)

### Finding Description
`extract_frontmatter` naively splits the raw file text on the literal substring `---` with `content.split('---', 2)` [5](#0-4) . This is a substring search over the whole content, not a line-anchored delimiter match (unlike the bash helpers elsewhere in the repo, which use `sed -n '/^---$/,/^---$/'` or `awk '/^---$/{...}'` that only match lines that are exactly `---` [6](#0-5) ).

If any frontmatter field value (most plausibly `pattern`, since it is free-form regex text and typically appears before `action:` in every documented rule template) contains the literal three-character sequence `---` anywhere in it, `split('---', 2)` treats that occurrence as the second delimiter. `parts[1]` (the parsed `frontmatter_text`) then ends right there, cutting off every field that appears later in the file — including `action: block` — and dumps the remaining real content (the actual closing `---`, and any subsequent fields) into `parts[2]`, which becomes the free-text `message` body instead of parsed YAML.

`Rule.from_dict` then falls back to the default `action = frontmatter.get('action', 'warn')` [7](#0-6) , silently turning an intended blocking rule into a warning rule. `RuleEngine.evaluate_rules` routes non-`'block'` rules into `warning_rules`, which only emits a `systemMessage` and allows the tool call to proceed for `PreToolUse` events [8](#0-7) .

This is reachable both via a checked-in `.claude/hookify.*.local.md` file in a cloned repo (rule files are not scoped or validated beyond `content.startswith('---')` in `load_rule_file` [9](#0-8) ) and via `/hookify` writing attacker-influenced text into the pattern field, since the command explicitly instructs the model to place `action: {warn|block}` after `pattern: {regex pattern}` [4](#0-3) . Existing checks (only `startswith('---')` and `len(parts) < 3`) do not detect or reject embedded `---` substrings inside values, so nothing stops the truncation.

### Impact Explanation
A rule file that is explicitly intended to `block` a dangerous `Bash`/`Edit`/`Write` operation (e.g., `rm -rf`, `chmod 777`, destructive `dd`) can silently degrade to `warn`-only enforcement because `action: block` never reaches the parsed dict. `RuleEngine.evaluate_rules` will then only attach a `systemMessage` and allow the operation to execute (`PreToolUse`/`PostToolUse` return no `permissionDecision: deny`), and for `Stop` events it will not block session termination either. This breaks the "deny means deny" guarantee of a security guardrail plugin, letting an operation that a project explicitly configured to be blocked execute anyway.

### Likelihood Explanation
This requires only that an unprivileged party control the raw text of a `.claude/hookify.*.local.md` file — either by committing it to a cloned repository or by having `/hookify` generate a rule from attacker-influenced conversation/instruction text containing a `pattern` value with a literal `---` substring (e.g. a regex alternation such as `rm\s+-rf|---|dd`, or any pattern text that happens to include three consecutive hyphens). No special privileges, admin access, or social engineering of the victim beyond normal repo/plugin usage is needed, and the bug is 100% deterministic given such input — this makes it readily discoverable and reproducible.

### Recommendation
Fix `extract_frontmatter` to split on the frontmatter delimiter using line-anchored matching (e.g. `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or splitting on `'\n---\n'`/scanning line-by-line for lines that are exactly `---`), rather than a raw substring split. This mirrors the safer approach already used by the shell-based frontmatter parsers in the repo (`sed -n '/^---$/,/^---$/'`) and prevents any field value from being misinterpreted as a delimiter.

### Proof of Concept
