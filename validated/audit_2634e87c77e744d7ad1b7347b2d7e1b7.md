## Title
Unhandled `throw Error` in AA-trigger construction crashes the node on a malformed payment to an AA - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `getTrigger()` builds the `trigger` object that is passed into AA execution whenever a unit's `payment` message sends funds to an autonomous agent address. If the computed `trigger.outputs` map ends up empty, the function does not return an error to the caller — it synchronously `throw`s a JS `Error`, exactly the crash-on-malformed-input pattern described in CVE-2023-37007 (a required field missing from an attacker-supplied message causes an unhandled assertion/throw that kills the process). [1](#0-0) 

### Finding Description
`getTrigger(objUnit, receiving_address)` iterates the unit's payment messages, sums outputs addressed to `receiving_address` into `trigger.outputs[asset]`, and then asserts:
```
if (Object.keys(trigger.outputs).length === 0)
    throw Error("no outputs to " + receiving_address);
``` [2](#0-1) 

This is a raw `throw`, not a callback-style validation error (`ifUnitError`/`ifJointError`) used consistently everywhere else in `validation.js`. Every other malformed-field case in the unit/message/AA-trigger validation pipeline is funneled through `callback()`/`callbacks.ifUnitError()` so that a bad unit is rejected gracefully: [3](#0-2) 

`getTrigger` is invoked from the AA-trigger handling path (`validateAATrigger` in `validation.js`, called unconditionally for every unit passing through `validate()`), as well as from `network.js`. Because `getTrigger` throws synchronously instead of going through the async callback chain, this exception is not caught by the `async.series`/callback error-handling machinery that wraps the rest of unit validation, and propagates up as an uncaught exception in whatever code path invoked the trigger evaluation.

The precondition — an attacker producing a unit where `trigger.outputs` is empty despite the code believing it should reach `getTrigger` for AA processing — is reachable by any unprivileged unit poster: a party can construct a unit whose only payment message targeting the AA is filtered out (e.g., an asset payment whose `payload.asset` field/matching logic leaves `trigger.outputs` empty after the `forEach`, e.g., zero-length or improperly typed `payload.outputs`), yet the code has already decided the unit needs AA processing (an output exists in the `outputs` table crediting the AA address from an earlier stage), producing the mismatch that trips the assertion instead of a normal validation error.

### Impact Explanation
An uncaught exception thrown from `getTrigger` during unit validation/AA-trigger processing crashes the Node.js process on every full node/witness/hub that processes the malicious unit (Node.js default behavior for an uncaught synchronous exception is process termination unless a domain/global handler intercepts it). Since AA-trigger handling occurs as part of ordinary unit validation for any unit that touches an AA address, a single crafted unit broadcast to the network can repeatedly crash nodes that attempt to validate/process it — a network-wide denial of service preventing confirmation of new units, analogous to the Open5GS S1AP assertion crash in the CVE.

### Likelihood Explanation
Reaching this code requires posting a unit that appears (from the DB/`outputs`-table perspective) to pay an AA but for which `trigger.outputs` computation from the message list ends up empty — for example a mismatch between the recorded output address/asset and what the `messages.forEach` scan recomputes. This is a corner case that depends on how/when `getTrigger` is invoked relative to unit acceptance, and I was not able to fully trace, within the available tool budget, every exact call site and precondition in `network.js`/`aa_composer.js` that guarantees this state is externally reachable without any privileged/internal precondition. This should be verified with the full codebase before treating it as fully confirmed.

### Recommendation
Replace the `throw Error(...)` in `getTrigger()` with a validation-style error propagated through the normal callback chain (returning `ifUnitError`/an explicit error to the caller) so a malformed/inconsistent unit is rejected as invalid rather than crashing the process. Audit all other `throw Error("no ...")`/`throw Error("unknown ...")` assertions reachable from externally-supplied unit/message data (e.g., `validation.js` lines flagged during this scan, such as the `src_coin`/`src_output`/`denomination` assertions in `validatePaymentInputsAndOutputs`) and convert genuinely attacker-reachable ones to graceful validation errors, reserving `throw` only for states provably unreachable from untrusted input.

### Proof of Concept
Not fully constructible without further verification of the exact caller context (`network.js` call sites) that determines when `getTrigger` is invoked relative to unit acceptance; a concrete PoC unit would need to reproduce a state where the AA address is recorded as a payment recipient but the `messages.forEach` output-summation in `getTrigger` yields an empty `trigger.outputs` map (e.g., via an asset/base mismatch or malformed `payload.outputs` array that bypasses upstream `payment` message validation while still crediting the AA in the outputs table). This gap should be closed by a follow-up code review of `network.js`'s two `getTrigger` call sites before this is treated as fully proven.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
```
