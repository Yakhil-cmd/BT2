### Title
Webhook signature verification is keyed by an attacker-controlled organization field, decoupling authentication from the repository actually written - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC validation based on `repository_owner`, a value read directly out of the unauthenticated JSON body. `GithubApp#verify_webhook_signature` treats a missing `webhook_secret` as an automatic pass. Because the organization used to select the verification secret is not cryptographically bound to the repository that the event handlers subsequently act on (`repository.full_name`), an attacker can pick an organization whose config has no `webhook_secret` to short-circuit verification, then supply a `repository.full_name` belonging to any other, real, fully-configured stack to drive its handlers (push sync, status, check_suite, membership, pull_request/review-stack handlers).

### Finding Description
`verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and uses it to fetch the app config: `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(header, raw_post)`. [2](#0-1) 

`verify_webhook_signature` is:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Shipit explicitly supports per-organization GitHub App configuration, each with its own optional `webhook_secret` (per `docs/setup.md` and the example secrets files, `webhook_secret` is documented as optional/nilable): [4](#0-3) [5](#0-4) [6](#0-5) 

`repository_owner` and `repository.full_name` are two independent fields inside the same attacker-supplied JSON body — nothing ties the `owner.login` used for secret lookup to the `full_name` that handlers subsequently act on:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 

Equality that should hold but doesn't: `organization authenticated (repository.owner.login used to pick webhook_secret) == organization/repository whose state the handler mutates (repository.full_name)`. An attacker can set `repository.owner.login` to an org with no configured `webhook_secret` (bypassing HMAC verification entirely) while setting `repository.full_name` to any other tracked repository/stack, breaking that equality.

### Impact Explanation
If any organization configured in `Shipit.github` (a realistic, documented, in-scope configuration state — `webhook_secret` is optional per setup docs) lacks a `webhook_secret`, an unauthenticated attacker can forge fully arbitrary webhook events for *any other* tracked repository/stack:
- `push` events trigger `GithubSyncJob` via `PushHandler#process` for arbitrary stacks [8](#0-7) 
- `status`/`check_suite`/`membership`/`pull_request` events mutate commit statuses, review-stack provisioning, team/user membership, etc., all keyed off attacker-supplied `repository.full_name`.

This can influence continuous-delivery triggers (auto-deploys keyed on commit-status/statuses of a real target stack) and review-stack provisioning/archival for a real repository — an authentication bypass into event-processing logic that the deployment expects to be GitHub-signed.

### Likelihood Explanation
Requires no credentials: the webhook endpoint skips CSRF and is reachable by anyone who can POST to it; the only precondition is that at least one configured GitHub organization in the Shipit instance has no `webhook_secret` set — a state explicitly supported and shown as the default/example in the shipped configuration templates and test fixtures. In any multi-organization Shipit deployment where even one org's webhook secret is unset (e.g., left blank during onboarding), every other configured stack becomes forgeable via this endpoint.

### Recommendation
Do not allow signature verification to succeed based on an org config with a blank `webhook_secret` unless verification is globally/explicitly disabled for the whole installation. At minimum:
1. Fail closed (422) when `webhook_secret` is unset for the given organization, unless a global, admin-controlled flag intentionally disables all signature verification.
2. Bind the organization used for secret lookup to the repository the payload claims to act on — e.g., after locating the `Stack`/`Repository` by `full_name`, verify that its owning organization matches `repository_owner`, and reject if they differ.

### Proof of Concept
1. Configure `Shipit.github` with two organizations: `victim-org` (fully configured with a strong `webhook_secret`, owns a tracked stack `victim-org/prod-app`) and `attacker-org` (registered but with `webhook_secret` left blank, as the docs/templates show is valid).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/prod-app" }
}
```
No `X-Hub-Signature` needs to be valid — `repository_owner` resolves to `attacker-org`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally. [3](#0-2) 
3. The request proceeds to `create`, and `PushHandler` resolves `stacks` via `repository.full_name = "victim-org/prod-app"`, enqueuing `GithubSyncJob` for the real, unrelated `victim-org` stack with an attacker-chosen `expected_head_sha`. [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
