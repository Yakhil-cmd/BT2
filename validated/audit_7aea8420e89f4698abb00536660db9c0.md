### Title
Asset definer can instantly and unlimitedly rewrite the `spender_attested` attestor list, freezing already-held coins of previously-attested holders with no limit or delay - (File: validation.js)

### Summary
An asset created with `spender_attested: true` gives its definer perpetual, unbounded, timelock-free control over the list of trusted attestors via the `asset_attestors` message. Because every payment involving such an asset requires **both** the input owner and all output addresses to be currently attested, a definer can at any moment replace the attestor list, instantly de-attesting addresses that already hold coins. Those holders can no longer move (or even self-send change for) their existing balance, since any output to a now-unattested address fails validation. There is no limit on how drastically the list can change and no delay before the change takes effect for previously issued coins, mirroring the reported bug class where a semi-trusted coordinating role has unchecked, non-timelocked control over a parameter that determines whether existing users' positions/funds remain valid.

### Finding Description
When an asset is defined with `spender_attested = true`, the asset definer is the only party allowed to update the attestor list, via the `asset_attestors` message: [1](#0-0) 

The only checks performed are that the message is single-authored by the definer and that the new list is well-formed (sorted, valid addresses, not exceeding `MAX_ATTESTORS_PER_ASSET`): [2](#0-1) 

There is no restriction preventing the definer from wholesale-replacing the attestor list (e.g., removing all previously-trusted attestors and adding entirely new ones), no rate limit on how often this can be updated, and no timelock delaying when the new list takes effect.

`storage.readAsset` always resolves to the **most recently stabilized** attestor list for the asset, with no grace period for older holders: [3](#0-2) 

Every payment of the asset re-checks attestation status of both the spending address (owner of the input) and every output address against the *current* attestor list, not the list that was in effect when the coins were received: [4](#0-3) [5](#0-4) 

Consequently, an address that legitimately received asset coins while attested can be later excluded by the definer, and from that point on:
- It cannot spend the coins as an input (`"owner address is not attested"`).
- It cannot even receive its own change output when transferring (`"some output addresses are not attested"`).

This effectively **freezes** the holder's funds with a single, unilateral, non-timelocked action by the definer — the same failure mode described in the reported bug class: a role with broad but "reasonable-looking" control over a market/asset parameter can unilaterally and immediately change it in a way that harms existing, honest participants, with no limit or advance notice built into protocol validation.

### Impact Explanation
Any holder of a `spender_attested` asset can have their already-acquired balance permanently frozen at the sole discretion of the asset definer, with no cap on how much of the attestor list can change at once and no delay for holders to react (e.g., to move funds out beforehand). This is a fund-freezing impact reachable by any unprivileged party who chooses to accept and hold such an asset, triggered entirely by the definer's unilateral, unbounded control — directly analogous to the reported issue where an insufficiently constrained privileged role can unilaterally harm existing users without limits or timelocks.

### Likelihood Explanation
Likelihood depends on a user holding an asset with `spender_attested: true` from a definer who later becomes malicious or compromised, or who simply changes attestation policy. Since nothing in `validateAttestorListUpdate` or `checkAttestorList` restricts the scope or frequency of changes, and the effect is immediate for all future spends (including self-change), a malicious or coerced definer can trigger the freeze at will as soon as their `asset_attestors` unit stabilizes.

### Recommendation
- Add a timelock (minimum MCI/time delay) between an `asset_attestors` update and when it becomes effective for existing token holders, so holders have a window to move funds under the previous attestation rules.
- Consider "grandfathering" already-held balances: check attestation status as of the time coins were received (or last spent) rather than the very latest attestor list, at least for input ownership.
- Optionally cap how much of the attestor list can change in a single update (e.g., require a minimum overlap with the previous list), similar to the recommended sanity limits in the referenced report.

### Proof of Concept
1. Definer issues an asset `A` with `spender_attested: true` and an initial attestor list `[Attestor1]` (`validateAssetDefinition`, `validation.js:2725-2827`).
2. `Attestor1` attests `Alice`'s address; Alice receives coins of asset `A` in a payment (validated via `objAsset.arrAttestedAddresses`, `validation.js:2115-2122`).
3. Definer posts an `asset_attestors` message setting attestors to `[Attestor2]` only (`validation.js:2829-2848`); this passes validation because it only checks sender==definer and list well-formedness.
4. Once this unit stabilizes, `storage.readAsset` now returns `[Attestor2]` as the active attestor list (`storage.js:1917-1946`).
5. Alice, still attested only by `Attestor1`, attempts to spend her coins (even just to send change back to herself): validation fails with `"owner address is not attested"` / `"some output addresses are not attested"` (`validation.js:2499-2507`, `2630-2641`), permanently freezing her balance.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
