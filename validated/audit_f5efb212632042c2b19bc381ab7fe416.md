### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) purely by bare SHA (`Commit.where(sha: params.sha)`) with no repository filter, unlike other handlers that scope lookups to the originating repository via `Handler#stacks`. Because git commit SHAs are shared across forks/mirrors of the same history, an attacker who owns a fork under a GitHub organization/owner already trusted by Shipit's GitHub App can emit a `status` webhook (`context: deploy/production`, `state: success`) for a SHA that also exists in a victim stack, writing a status record onto the victim's commit and (if `merge_queue_enabled` is true) triggering `stack.schedule_merges`.

### Finding Description
The broken binding: the code should guarantee `commit.stack.repository.full_name == payload.repository.full_name` for every `Commit` touched by a webhook, but `StatusHandler` never checks this.

Path:
- `Shipit::WebhooksController#create` verifies only that the payload is signed by the GitHub App registered for `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:24-49`), i.e. it authenticates *who sent the event*, not *which stack the event may mutate*.
- `Handler#stacks` (the pattern used by properly-scoped handlers such as `push_handler.rb` and `check_suite_handler.rb`) restricts writes to `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) .
- `StatusHandler#process` bypasses that scoping entirely and does a bare, global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) .
- `Commit#create_status_from_github!` → `add_status` writes the status, and if the new state is `success` (and the simple state changed), it calls `stack.schedule_merges` unconditionally, regardless of which repository actually authenticated the webhook [3](#0-2) . `Stack#schedule_merges` enqueues `ProcessMergeRequestsJob`, which advances the merge queue for stacks where `merge_queue_enabled` is true [4](#0-3) .

Exploit flow: an attacker who has push/collaborator access to a repository under a GitHub owner/org already onboarded to Shipit (so `Shipit.github(organization: repository_owner)` resolves and `verify_webhook_signature` succeeds) forks or otherwise shares commit history with the victim repository, so a commit's SHA exists identically in both repos' Shipit `Commit` records. The attacker (or any CI integration they control on their own repo) issues `POST /repos/<attacker>/<repo>/statuses/<shared-sha>` with `context: deploy/production`, `state: success`. GitHub relays this as a genuine, correctly-signed `status` webhook to Shipit. `StatusHandler` matches the shared SHA across *all* stacks in the database — including the victim's — and writes the `deploy/production` success status onto the victim's commit, flipping its required-context state and (with `merge_queue_enabled: true`) firing `schedule_merges`/`merge!` machinery for a commit the victim's own CI never validated.

Existing guards do not stop this: `verify_signature` only proves the event came from GitHub for the claimed `repository_owner`, it never constrains which `Commit` rows the handler is allowed to touch; `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not repository ownership; and unlike other handlers, `StatusHandler` never calls `stacks`/`Repository.from_github_repo_name`.

### Impact Explanation
A payload authenticated for one repository can flip the `deploy/production` status and, with the merge queue enabled, force merge-queue progression (`merge!`) for a stack belonging to a different repository that merely happens to share a commit SHA. This is a write for a repository that did not authenticate it, matching the "Critical - a payload for one repository mutating another's stack/commit" and "unauthorized deploy/rollback/merge" categories. The blast radius is any stack whose commit history overlaps with a repository the attacker can post statuses to (most commonly forks of the victim repo), and the action is repeatable for every subsequent shared commit/status write.

### Likelihood Explanation
Preconditions: (1) the attacker needs push/write access to some repository/fork under a GitHub owner already configured in Shipit (so webhook signature verification succeeds) — this is a low bar for any org member or anyone who forks a repo owned by a Shipit-registered org; (2) the target commit SHA must exist in both the attacker's repo and the victim stack's `commits` table, which is trivially true for any commit inherited from the shared upstream history before the fork diverged; (3) the victim stack must have `merge_queue_enabled: true` and require `deploy/production` as (part of) its status set for the queue-advancing effect to manifest. Cost to the attacker is a single authenticated GitHub API call to set a commit status on their own repository — no Shipit credentials, sessions, or secrets are needed.

### Recommendation
Scope `StatusHandler#process` (and any other handler doing bare `Commit`/SHA lookups) to the repository that authenticated the webhook, mirroring `Handler#stacks`: e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Stack -> Repository` using `payload.dig('repository', 'full_name')`, so a status can only be applied to commits belonging to stacks of the repository that sent it.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual file is out of scope for authoring under audit rules but describes the reproducible assertion):
```ruby
test "status webhook for a shared SHA mutates a stack of a different repository" do
  victim_repo  = shipit_repositories(:shipit)              # e.g. "shopify/shipit-engine"
  attacker_repo_payload = { 'repository' => { 'full_name' => 'attacker/fork' } }

  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(merge_queue_enabled: true)
  shared_sha = shipit_commits(:first).sha
  shipit_commits(:first).update!(stack: victim_stack)

  before_deployable = shipit_commits(:first).reload.deployable?

  Shipit::Webhooks::Handlers::StatusHandler.call(
    attacker_repo_payload.merge(
      'sha' => shared_sha,
      'state' => 'success',
      'context' => 'deploy/production'
    )
  )

  after_deployable = shipit_commits(:first).reload.deployable?

  # Binding under test: commit.stack.repository.full_name == payload['repository']['full_name']
  refute_equal victim_repo.full_name, attacker_repo_payload['repository']['full_name']
  refute_equal before_deployable, after_deployable # status/merge state changed for a repo that never authenticated the request
  assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack])
end
```
This demonstrates that a webhook signed and authenticated for `attacker/fork` mutates `shipit_stacks(:shipit)`'s commit state and triggers merge-queue processing, confirming the cross-tenant write.
