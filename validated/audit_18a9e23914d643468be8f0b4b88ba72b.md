### Title
Webhook signature verification silently no-ops when an organization's `webhook_secret` is blank, letting unauthenticated requests drive stack sync/deploy state - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` treats a missing/blank `webhook_secret` as "verification passed" instead of rejecting the request. This mirrors the reported bug class (a critical trust parameter that can be left at its zero/unset value with no guard, silently disabling the check it is supposed to enforce), and here it disables the entire GitHub-webhook HMAC authentication boundary for that organization.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App config for the organization named in the payload and calls into it to check the `X-Hub-Signature` header: [1](#0-0) 

The actual check is: [2](#0-1) 

`return true unless webhook_secret` means: if the `webhook_secret` field for that organization's config is nil/blank, **any** request — with **any** body, **any** or no `X-Hub-Signature` header — is treated as validly signed. There is no separate authentication mechanism at this layer; `verify_signature` is the entire HMAC gate protecting `create`, which dispatches every registered handler (`push`, `status`, `check_suite`, `membership`, `pull_request`, `merge`, `deployable_status`, …) against attacker-supplied JSON.

`webhook_secret` is a value the operator can leave unset — the shipped example templates literally show it blank: [3](#0-2) [4](#0-3) 

and the multi-organization setup doc (`docs/setup.md`, "Using Multiple Github Applications") shows each org configured independently with its own `webhook_secret`, so a single blank value in a multi-org deployment disables verification only for that one organization, without affecting others — an easy, non-obvious misconfiguration to introduce incrementally as orgs are onboarded.

This breaks the binding the report's bug class targets: *the GitHub organization that is supposed to be cryptographically authenticated versus the events actually acted upon for the repositories under it*. With verification silently short-circuited, the equality "organization proven by valid HMAC signature == organization whose repositories/stacks get mutated" collapses to "any request claiming that organization name."

Downstream, a `push` webhook for that organization is processed with zero authentication: [5](#0-4) 

which resolves the target repository purely from the JSON payload: [6](#0-5) 

and enqueues `GithubSyncJob`, which fetches commits via `stack.github_api` and appends them to the stack, potentially unlocking deploys/toggling `mark_as_accessible!`/`mark_as_inaccessible!` state: [7](#0-6) 

Other handlers (status, check_suite, deployable_status, merge, membership) are equally reachable and equally unauthenticated once `webhook_secret` is blank for the targeted organization, allowing forged CI/check statuses, forged deployable-status transitions, or fabricated team/membership objects.

### Impact Explanation
For any organization whose `webhook_secret` is unset in `Shipit.github`, an unauthenticated remote attacker can POST arbitrary JSON to the webhooks endpoint and have it processed as a genuine GitHub event: syncing arbitrary commit history into a stack, forging commit/check/deployable statuses that gate whether a commit is "deployable," and manipulating merge-related state. Because Shipit's automatic/continuous-deployment and merge-gating logic consumes these statuses, this can lead to an unauthorized deploy of attacker-influenced state — matching the Critical bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires no credential, session, or knowledge of any secret — it is exploitable precisely because no secret is configured for the targeted organization. Given multi-org configs are documented as a supported pattern (`docs/setup.md`) and per-org `webhook_secret` is optional/independently settable, this is a realistic operational state, not a contrived one; the shipped example config files even ship with blank `webhook_secret` values.

### Recommendation
Change `verify_webhook_signature` to fail closed when `webhook_secret` is blank (reject the request / require an explicit "auth disabled" opt-in flag instead of implicit bypass), and add a startup/config validation that surfaces a warning or refuses to boot when an organization is configured without a `webhook_secret`.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`, where `org-b.webhook_secret` is left blank/nil (as shown in the shipped `config/secrets.development.shopify.yml` template).
2. As an unauthenticated attacker, POST to `/github/webhooks` with header `X-Github-Event: push` and a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha of an existing commit in org-b's repo>",
  "repository": { "full_name": "org-b/some-repo", "owner": { "login": "org-b" } }
}
```
No `X-Hub-Signature` header, or any arbitrary value, is required.
3. `verify_signature` resolves `Shipit.github(organization: "org-b")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`), and `PushHandler#process` enqueues `GithubSyncJob` for the matched stack — all without the attacker ever knowing a secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def append_commit(gh_commit)
      stack.commits.create_from_github!(gh_commit)
    end
