Cross-repository status injection via unscoped `Commit.where(sha:)` in `StatusHandler#process` bypasses `blocking_statuses` gating - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository/stack scoping, unlike every other webhook handler (e.g. `PushHandler`, `PullRequest::*Handler`) which route through the `Handler#stacks` helper scoped to `Repository.from_github_repo_name(repository_name)`. Because GitHub webhook signature verification is keyed only to the payload's `repository.owner.login`/`organization.login` (an attacker-controlled field, verified against that org's own secret), an attacker who owns any GitHub org/repo wired into this Shipit instance can send a validly-signed `status` webhook whose `sha` matches a commit tracked under a completely different (victim) stack, injecting a `Status` row on that foreign commit and flipping `blocked?`/`deployable?`/CD scheduling for the victim stack.

### Finding Description
The broken binding: the handler should enforce `commit.stack.repository == payload.repository`, but it does not — it enforces nothing: [1](#0-0) 

Compare with the base `Handler` class, which every scoped handler is expected to use: [2](#0-1) 

`PushHandler`, the sibling handler, correctly filters through `stacks` (repository-scoped): [3](#0-2) 

`StatusHandler` never calls `stacks`/`repository_name` at all; it queries the global `Commit` table by `sha` only, then for every match (regardless of which stack/repository the commit belongs to) calls `commit.create_status_from_github!(params)`, creating a `Status` row scoped to `commit.stack_id` — a stack the attacker's payload never named: [4](#0-3) 

Signature verification does not close this gap because it is keyed off the same attacker-controlled `repository`/`organization` field in the payload, not the target commit's actual owning repository: [5](#0-4) [6](#0-5) 

An attacker who owns/operates any repository configured under `Shipit.github_teams`/`Shipit.github(organization:)` (i.e., any org for which this Shipit instance holds credentials — this could be the attacker's own onboarded fork/org if the instance is multi-tenant, or any org they can trigger a webhook from) can send:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: <valid signature for attacker's own org secret>
{
  "repository": {"full_name": "attacker/decoy", "owner": {"login": "attacker-org"}},
  "sha": "<victim commit sha>",
  "context": "ci/coverage",
  "state": "success"
}
```
Because `Commit.where(sha:)` matches by SHA alone, and 40-character git SHAs frequently collide across forks/mirrors sharing history, or are simply known/public for the victim's tracked commits, this payload creates a `Status(context: "ci/coverage", state: "success")` on the victim's commit. `Status::Common#blocking?` and `Commit#blocked?`/`#deployable?` then evaluate this attacker-injected status against the victim stack's own `blocking_statuses`/`required_statuses` config: [7](#0-6) [8](#0-7) 

`add_status` then reacts to the state transition by scheduling merges/continuous delivery on the victim stack: [9](#0-8) 

None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `require_permission!`, `stacks` scope) prevent this, because `verify_signature` only authenticates *that the payload's named org* sent it, and `StatusHandler` never checks that the named org/repository actually owns the target commit's stack.

### Impact Explanation
A payload from one repository/org mutates state (`Status` rows, `blocked?`, `deployable?`, scheduled continuous delivery / merges) belonging to a stack tied to a different, unauthenticated repository. This is a cross-tenant/cross-repository state manipulation matching the "Critical" category (payload for one repository mutating another's stack/commit) — it can force a ship (by injecting a passing required status) or force a block (by injecting a failing/blocking status) on a victim stack the attacker does not control. It is repeatable against any commit SHA the attacker can learn or predict, across every stack sharing that SHA.

### Likelihood Explanation
Preconditions: the attacker needs a valid webhook signature for *some* org known to this Shipit instance (their own onboarded repo/org) and knowledge of a target SHA tracked by the victim stack (commit SHAs are typically public/derivable from GitHub, shared forks, or PR history). No Shipit session, API token, or GitHub-team membership is required — only the ability to compute an HMAC with a secret the attacker legitimately possesses for their own repo. This is low-cost and fully repeatable/scriptable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the stacks belonging to the payload's own repository, mirroring `PushHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `Handler#stacks`/`repository_name` helpers so a status can only ever be applied to commits belonging to the repository that authenticated the webhook.

### Proof of Concept
minitest plan (controller or handler-level test, no live GitHub):
1. Create two repositories/stacks: `victim/repo` (stack A, `blocking_statuses` includes `ci/coverage`) and `attacker/repo` (stack B).
2. Create `commit = Commit.create!(stack: stack_a, sha: "deadbeef"*5)` (or shared SHA) with `blocking_statuses` satisfied only by a pending/failing status so `commit.blocked?` is currently `true` (assert this before).
3. Post a `status` webhook with `X-Github-Event: status`, body `repository.full_name = "attacker/repo"`, `sha = commit.sha`, `context: "ci/coverage"`, `state: "success"`, stubbing `verify_signature`/`GithubHook#verify_signature` to simulate a valid signature for `attacker/repo`'s org (as existing tests do: `GithubHook.any_instance.stubs(:verify_signature).returns(true)`).
4. Assert: `commit.reload.blocked?` changed from `true` to `false` (or `commit.statuses.last.context == "ci/coverage"` and `commit.stack_id == stack_a.id` even though the payload named `attacker/repo`), proving stack A's state was mutated by a payload authenticated only for `attacker/repo`.
5. Binding check: before, `commit.stack.repository.full_name != payload["repository"]["full_name"]` (i.e. `"victim/repo" != "attacker/repo"`) yet after processing `commit.statuses.count` increased — demonstrating the missing equality check that should have rejected the write.
