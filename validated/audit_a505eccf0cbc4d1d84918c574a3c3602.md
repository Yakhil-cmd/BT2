## Analysis

The reported bug class is: **a validation performed against one identifier is used to authorize an action that is actually applied to a different, attacker-controlled identifier from the same payload.** In `PythPriceOracle`, the index used for the disabling check (`_priceFeedIds[0]`) was decoupled from the index actually mutated (`i`).

The closest analog in this engine breaks the binding required by the rules: *"an organization that authenticated versus the repository that is written."*

### Root cause

`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, computed as: [1](#0-0) [2](#0-1) 

This value comes from the JSON body field `repository.owner.login` (or `organization.login` as fallback) — fields the requester fully controls in the raw POST body, since this is an unauthenticated, publicly reachable endpoint (`resources :webhooks, only: :create`) whose only gate is the HMAC signature.

However, the event handlers that actually mutate state (creating commits, updating CI statuses, processing `check_suite`/`check_run`, closing/labeling PRs, etc.) resolve the target repository from a **different, independent field**: `repository.full_name`: [3](#0-2) 

Nothing in `verify_signature` checks that `repository.owner.login` (used to pick the verifying secret) is consistent with the owner segment of `repository.full_name` (used by every handler to look up the `Repository`/`Stack` to write to).

Shipit explicitly supports multi-tenant, multi-organization deployments where each organization has its own independent GitHub App and `webhook_secret`: [4](#0-3) [5](#0-4) [6](#0-5) 

### Title
Webhook signature verification authenticates against `repository.owner.login` but event handlers act on the independent `repository.full_name` field, enabling cross-organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the verifying `webhook_secret` using `repository.owner.login`/`organization.login`, while every `Webhooks::Handlers::Handler` subclass resolves the repository/stack to mutate using the unrelated `repository.full_name` field of the same attacker-supplied JSON body. Because these two fields are never cross-checked, on a multi-organization Shipit instance a party who legitimately possesses the `webhook_secret` for *their own* configured organization (OrgA) can forge a payload whose `repository.owner.login` is `OrgA` (so signature verification passes) but whose `repository.full_name` is `OrgB/some-repo`, causing GitHub push/status/check_run/pull_request events to be processed against OrgB's stacks without ever having proven possession of OrgB's secret.

### Finding Description
- Verification org selection: [1](#0-0)  uses `repository_owner`, sourced purely from the request body.
- The org lookup uses per-organization secrets: [7](#0-6)  and [8](#0-7)  compare the signature only against the `webhook_secret` configured for the organization named in `repository.owner.login`.
- Action target selection: every handler resolves stacks via `payload.dig('repository', 'full_name')` [3](#0-2) , and this same disconnect exists in `pull_request` handlers, which independently trust `params.repository.full_name` [9](#0-8) .
- These two fields (`repository.owner.login` and `repository.full_name`) are never asserted to be consistent, so the "organization that authenticated" is not bound to the "repository that is written."

### Impact Explanation
This is Critical: an attacker who administers *any one* organization onboarded to a shared, multi-tenant Shipit instance can forge webhook events that write into a completely different organization's stacks/commits/CI status/pull-request/merge-queue state — a cross-repository write achieved without possessing that victim organization's credentials. Depending on which event type is forged (`push`, `status`, `check_suite`/`check_run`, `pull_request`), this can inject fabricated commits, flip CI statuses to "success" (enabling unauthorized deploys via continuous delivery / merge queue), or manipulate merge-queue/review-stack state for a repository the attacker has no legitimate relationship with.

### Likelihood Explanation
Requires that the Shipit instance is configured for multiple GitHub organizations (`Shipit.github_organizations` returning more than one org — documented and supported: [10](#0-9) ) and that the attacker controls (as an org admin) one of the onboarded orgs' webhook secret while targeting a stack belonging to a different onboarded org. This is a realistic deployment pattern explicitly documented and tested (`test/dummy/config/secrets_double_github_app.yml`).

### Recommendation
- **Short term:** In `verify_signature`, after signature verification succeeds, assert that the owner segment of `repository.full_name` matches `repository.owner.login` (or `organization.login`) used to select the verifying app; reject the request (422) on mismatch.
- **Long term:** Have handlers resolve the organization from the already-verified `repository_owner` used during signature verification (pass it through the pipeline) rather than re-deriving it independently from `repository.full_name`, so a single verified field drives both authentication and authorization decisions.

### Proof of Concept
Conceptual request (not run, no infra access):
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(body, OrgA_webhook_secret)>

{
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  },
  "ref": "refs/heads/main",
  "commits": [ ... attacker-controlled forged commits ... ]
}
```
`verify_signature` computes `repository_owner = "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and verifies the HMAC using OrgA's secret — which the attacker legitimately possesses. The signature check passes. `PushHandler` (subclass of `Handler`) then resolves `repository_name = "OrgB/victim-repo"` and looks up `Repository.from_github_repo_name("OrgB/victim-repo")`, ingesting the forged commits into OrgB's stacks even though the attacker never proved knowledge of OrgB's `webhook_secret`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
