### Title
A borrower can DoS their own liquidation by mutating debt/collateral so the liquidator's signed transfer authorization no longer matches the pulled amount - (File: contracts/controller/src/positions/liquidation/apply.rs)

### Summary
Symmio's liquidation required a Muon signature over an on-chain nonce, which the target could bump at every block to invalidate any liquidation in flight. XOXNO Lending has no oracle-signed nonces, but it has an equivalent signed artifact: the liquidator's Soroban authorization tree pins the exact `transfer(liquidator, pool, amount)` sub-invocation amount, while the controller computes the pull amount from live account state at execution. Whenever the pull is quote-bound rather than offer-bound, the account owner can cheaply perturb their own position (a dust `repay`, or a dust `supply` that shifts the collateral-backed trim) so the executed pull differs from the signed amount, and the host rejects the liquidation transaction with an auth failure.

### Finding Description
`liquidate(liquidator, account_id, debt_payments, seize_mode)` builds a `LiquidationPlan` from account state at execution (`build_liquidation_plan`, `plan.rs`), then pulls repayment tokens via `apply_liquidation_repayments`. The pull per leg is:

- the merged **offered** amount only when the plan is a full close (`offered` is `Some`), or
- the **planned** amount otherwise (`apply.rs:54-56`, `pull = offered.map_or(entry.amount, ...)`).

The planned amount is state-dependent: in the collateral-backed (insolvent) regime the quote is `floor(C / (1 + base))` trimmed per leg to whole units, and in the solvent partial regime the kept amount is bounded by the HF-derived bonus curve over live debt/collateral values (`math.rs`, `curve.rs`).

Because repayment and seizure legs are settled by `transfer_amount_measured`, the token `transfer` call executes with the *planned* amount. Soroban authorization requires the signed auth tree to match the invoked arguments exactly. The protocol's own tests document this: `tests/test-harness/tests/controller/liquidation_band_signed_auth.rs` shows that when the plan trims an over-offer, "the capped pull no longer matches the signed transfer" and the call fails with an `Auth`/`Context` host error ("Unauthorized function call for address"), leaving the debt untouched. The liquidation runbook similarly warns that "a transfer signed for more fails authorization."

An unprivileged borrower controls the inputs to the plan:

- `repay(caller, account_id, payments)` is permissionless for any account; repaying 1 base unit of a debt leg reduces the debt the quote is computed over.
- `supply(caller, account_id, spoke_id, assets)` lets the owner add dust collateral (or a new collateral leg), which changes `total_collateral` and therefore the collateral-backed trim and per-leg rounding.

Either action, performed before the liquidator's transaction executes (and repeatable every ledger for near-zero cost — repay amounts are in base units, and supply dust is retained as collateral), changes the planned pull relative to what the liquidator simulated and signed. The liquidation then reverts on authorization instead of executing.

### Impact Explanation
A liquidatable borrower can indefinitely prevent any pre-signed liquidation of their account by mutating their position once per ledger, mirroring the original nonce-bump DoS. Every liquidation attempt authored from a simulation fails at the auth layer, so the position accrues interest and price risk while remaining unclosable, increasing protocol deficit/bad-debt exposure. The escape hatches are partial: in the whole-debt full-close band an over-offer is pull-stable, but outside that band (partial closes on large accounts, insolvent trims) the pull is quote-bound and manipulable; a liquidator cannot simply "sign more" because the signed amount must equal the executed amount exactly.

### Likelihood Explanation
- Reachable by the account owner alone via `repay`/`supply` — both unprivileged entrypoints.
- Cost per ledger is negligible (1 base unit of debt token, or dust collateral that remains the borrower's own collateral).
- No mempool race is required: the borrower simply keeps perturbing the position each ledger; any liquidation signed against a stale plan reverts, and on-chain simulation→submission latency makes the signature stale by construction.
- Limitation: the attack only breaks the auth when the submitted offer is trimmable (offer > computed quote) or the quote itself shifts; a liquidation whose pull equals the offered amount (the whole-debt band with a full over-offer) is immune. This lowers reliability versus the original, supporting High→Medium severity.

### Recommendation
Decouple the signed authorization amount from the mutable plan amount, so small state deltas cannot invalidate a signed liquidation:

- Pull a fixed, liquidator-chosen amount (the offered leg amounts) and let the pool/controller refund unaccepted excess — the same mechanism already used in the full-close path — for *all* liquidation plans, not only whole-debt quotes; or
- Round the pull to a coarse unit (e.g., whole-token granularity) and require the account's mutation to exceed that granularity to matter, so dust repay/supply cannot shift the pull; or
- Accept a signed upper bound: authorize `transfer` of the offered amount and pull `min(offered, quote)`, crediting the difference as a refund, which makes any borrower mutation shrink the fill rather than break the signature.

### Proof of Concept
1. Borrower opens an account, supplies collateral, borrows; the price moves so HF < 1 and the account sits where the quote is not the whole debt (e.g., insolvent, or solvent with a partial close-factor cap).
2. Liquidator simulates `get_liquidation_estimate`/`liquidate` with `debt_payments = [(asset, X)]` and signs the auth tree containing `transfer(liquidator, pool, P)` where `P` is the planned pull.
3. Before the liquidation executes, the borrower calls `repay` with a 1-base-unit payment on that debt leg (or `supply` a dust amount that changes the collateral-backed cap). The quote/planned pull becomes `P' ≠ P`.
4. At execution, `apply_liquidation_repayments` computes `pull = P'` (planned amount since `offered` is `None` outside full close) and invokes `transfer(..., P')`, which does not match the signed `transfer(..., P)` sub-invocation; the host raises an authorization error and the entire liquidation reverts — exactly as demonstrated for over-offers in `liquidation_band_signed_auth.rs`.
5. The borrower repeats step 3 each ledger, keeping the account unliquidatable indefinitely.
