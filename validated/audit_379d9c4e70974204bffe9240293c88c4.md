## Analysis

The external report is about mismatched docstrings/comments vs. implementation in a Solidity contract. Mapped into this Ruby engine's in-scope trust boundaries, the closest real analog is a **mismatch between which payload field is covered by webhook signature verification and which field is actually acted upon** — i.e., the binding "an organization that authenticated versus the repository/target that is written" required by the rules.

### Root cause

`WebhooksController#verify_signature` selects the GitHub App/org configuration — and therefore the secret used to validate `X-Hub-Signature` — using an attacker-controlled payload field: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login`, falling back to `organization.login` — both are ordinary JSON fields inside the same request body being signed, chosen entirely by the client.

`GitHubApp#verify_webhook_signature` unconditionally passes verification whenever the selected org config has no `webhook_secret` configured: [3](#0-2) 

The setup docs explicitly describe `webhook_secret` as **optional**, and every example/template config ships with it blank/`nil`: [4](#0-3) [5](#0-4) 

Meanwhile, the field actually used to select the *target* of the webhook's effect (which stacks get synced, which commit gets a status, which team a member is added to) is a **different** field of the same payload — `repository.full_name` for `Handler#stacks`, or `organization.login` for `MembershipHandler`: [6](#0-5) [7](#0-6) 

### The binding that breaks

`organization authenticated (repository_owner, used to pick webhook_secret) == organization/repository written (repository.full_name / organization.login, used by handlers)`

Because `repository_owner` and the fields consumed by the handlers are independent, an unprivileged attacker who can reach `POST /webhooks` (an unauthenticated, public endpoint — no session, no `ApiClient` token, no GitHub App key required) can craft a payload where `repository.owner.login` names *any* organization configured in Shipit that happens to have no `webhook_secret` set (verification then returns `true` regardless of the `X-Hub-Signature` header supplied), while `repository.full_name` or `organization.login` names a completely different, legitimate stack/organization/team. This lets the attacker:

- Trigger `PushHandler` → `stack.sync_github(...)` for arbitrary tracked stacks belonging to any organization, spoofing pushes.
- Inject fabricated commit statuses via `StatusHandler#process` → `commit.create_status_from_github!` for arbitrary commits.
- Auto-archive/unarchive review stacks via `LabeledHandler`/`UnlabeledHandler`.
- Create `Team`/`Membership` records via `MembershipHandler`, potentially interacting with the `Shipit.github_teams` authorization check (`User#authorized?`): [8](#0-7) 

I was not able to fully verify within the remaining tool budget whether `MembershipHandler` can be chained into a full authentication bypass (this depends on `User.find_or_create_by_login!` semantics and how `github_id` matching interacts with the real OAuth login flow, which I didn't get to inspect) — that part remains an open question. The push/status/stack-sync forgery path, however, is directly confirmed by the code above.

This satisfies the required impact bar (unauthorized deploy trigger / cross-repository writes) since it lets an attacker cause `GithubSyncJob` to run for stacks it does not control, and spoof commit statuses that other automated merge/deploy tooling may rely on.

### Title
Cross-Organization Webhook Forgery via Mismatched Signature-Selection Field and Optional Per-Org `webhook_secret` — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and thus which HMAC secret) to validate a webhook against using the attacker-supplied `repository.owner.login`/`organization.login` field. Because `webhook_secret` is documented and shipped as optional, an org with no secret configured causes `verify_webhook_signature` to return `true` unconditionally. Handlers then act on a *different* payload field (`repository.full_name`, `organization.login`) to decide which stack/commit/team to mutate.

### Finding Description
- `repository_owner` (used only for secret selection) and the fields consumed downstream by `Handler#stacks`/`MembershipHandler` are independent values inside the same attacker-controlled JSON body.
- `verify_webhook_signature` short-circuits to `true` when no secret is configured for the selected org (`lib/shipit/github_app.rb:76-77`).
- An attacker can name `repository.owner.login` as an org with no `webhook_secret`, satisfying signature "verification" trivially, while populating `repository.full_name`/`organization.login`/`sha` with values referencing a different, targeted organization's resources.

### Impact Explanation
This breaks the deployment-trust binding "organization authenticated == organization/repository acted upon", allowing an unauthenticated external attacker to trigger sync jobs, forge commit statuses, and archive/unarchive review stacks for stacks/organizations they have no relationship to — a cross-organization write achieved without any credential.

### Likelihood Explanation
Requires only that at least one org configured in the Shipit instance has an unset `webhook_secret` — the documented, template-shipped default — and the `/webhooks` endpoint is publicly reachable by design (it must accept unauthenticated GitHub deliveries).

### Recommendation
Do not derive the org used for signature-secret selection from unauthenticated payload content without cross-checking it against the field(s) the handler will actually act on; reject/require `webhook_secret` for all configured orgs; fail closed (422) rather than defaulting to "verified" when no secret is configured.

### Proof of Concept
1. Configure two orgs in `secrets.yml`: `orgA` (no `webhook_secret`) and `orgB` (tracked stack `orgB/target-repo`, real secret unknown to attacker).
2. POST to `/webhooks` with header `X-Github-Event: push`, any/garbage `X-Hub-Signature`, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" }
}
```
3. `repository_owner` resolves to `orgA`; `Shipit.github(organization: "orgA").verify_webhook_signature` returns `true` (no secret configured) regardless of the bogus signature.
4. `PushHandler` uses `repository.full_name` = `orgB/target-repo` to look up and sync `orgB`'s stack, which the attacker never authenticated against. [9](#0-8)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
