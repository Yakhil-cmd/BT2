### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, while the Stack that actually gets written is selected independently from `repository.full_name` in the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization config (and therefore the `webhook_secret` used for HMAC verification) using one field of the untrusted JSON body (`repository.owner.login` / `organization.login`), while the code path that actually mutates state (`PushHandler`, `StatusHandler`, PR handlers, etc.) selects the target `Stack`/`Repository` using a different field of the same body (`repository.full_name`). Nothing cross-checks that these two fields refer to the same repository/organization, so the field that is authenticated is not the field that is acted upon — the same class of binding break described in the report, where the value checked (`voteStartBlock_`/eligibility block) diverges from the value actually used to compute the effect (`_getVotesAtSnapshotBlocks` snapshot).

### Finding Description
`verify_signature` resolves the signing secret this way: [1](#0-0) 

`repository_owner` is read straight from the untrusted body: [2](#0-1) 

Once the signature check passes, the very same raw JSON is dispatched to per-event handlers, which independently derive the `Stack`/`Repository` to act on using `repository.full_name`, a completely different field of the payload: [3](#0-2) [4](#0-3) 

`Shipit.github(organization:)` is explicitly organization-scoped (multiple orgs/apps can be configured, each with its own `webhook_secret`), which is why the controller has a dedicated `Shipit::GithubOrganizationUnknown` rescue path: [5](#0-4) 

Because `repository.owner.login`/`organization.login` (used to select *which* secret verifies the signature) and `repository.full_name` (used to select *which* Stack is written to) are two independent, attacker-controllable fields of the same JSON body, and neither is cross-validated against the other, the trust binding "organization that authenticated == repository that is written" does not hold. An attacker who knows/controls the `webhook_secret` for one organization configured in this Shipit instance (e.g., because they own a low-value org/app registered on the instance) can HMAC-sign a payload with `repository.owner.login` set to that org, while setting `repository.full_name` to a Stack belonging to a completely different, higher-value organization tracked by the same instance. `verify_signature` succeeds because it only checks the low-value org's secret against the raw body; the handler then happily updates commits/statuses/PR state for the unrelated target repository.

### Impact Explanation
This breaks a repository-authorization boundary: signature validated for org A is treated as authorization to write into any Stack whose `repository.full_name` claims to belong to org B. Concretely:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for the target Stack chosen via `repository.full_name`, independent of which org's secret validated the request — [6](#0-5) .
- `StatusHandler`/other handlers similarly resolve `stacks` from `repository.full_name` via the shared `Handler#stacks` helper — [3](#0-2) .
- Forged/incorrect CI status updates for arbitrary tracked commits can flip `deployable?`/`blocked?` state used by continuous delivery to auto-trigger deploys — [7](#0-6) , [8](#0-7) .

This is a cross-repository/cross-organization write using credentials that were never issued for the target organization, matching the "cross-repository writes" / "unauthorized deploy" impact criteria.

### Likelihood Explanation
Requires that the Shipit instance is configured to serve multiple organizations/GitHub Apps (the codebase explicitly supports and expects this via `Shipit.github(organization:)` and `GithubOrganizationUnknown`), and that the attacker controls or can obtain the webhook secret for at least one such organization while targeting a Stack belonging to a different, better-protected organization on the same instance. This is a realistic multi-tenant deployment scenario but its exact prevalence depends on how many organizations a given Shipit instance is configured to serve — an aspect not fully verifiable from static index inspection alone (would need to see the actual multi-organization config loader in `lib/shipit.rb`, which the index did not surface in full before this turn ended).

### Recommendation
In `WebhooksController#verify_signature` / `Handler#stacks`, require that the organization/owner used to select the verification secret matches the owner embedded in `repository.full_name` (or better, verify the signature using the specific `Repository`/`Stack` resolved from `repository.full_name`, then confirm that repository's registered org matches the secret that validated it) before dispatching to any handler. Reject the webhook if the two do not match.

### Proof of Concept
1. Configure/control the `webhook_secret` for organization `attacker-org` on a shared Shipit instance that also tracks a Stack for `victim-org/critical-repo`.
2. Build a webhook JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/critical-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen-sha>"}` (or a `status` payload for an arbitrary tracked commit).
3. Sign the raw body with `attacker-org`'s `webhook_secret` and send it as `X-Hub-Signature` with `X-Github-Event: push` (or `status`).
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and succeeds because the signature matches `attacker-org`'s secret.
5. `PushHandler`/`StatusHandler` resolve the Stack via `repository.full_name = "victim-org/critical-repo"`, and update/queue `GithubSyncJob` or create a `Status` for `victim-org`'s Stack despite the request never being authenticated against `victim-org`'s webhook secret.
