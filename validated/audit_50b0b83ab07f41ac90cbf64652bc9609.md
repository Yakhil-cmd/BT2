### Title
Webhook authentication is bound to the wrong entity: organization-scoped signature verification is decoupled from the repository/commit the payload actually writes to - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` resolves *which* GitHub App/organization secret to check against using a value pulled straight out of the untrusted, unverified payload (`repository.owner.login`, falling back to `organization.login`), and `GithubApp#verify_webhook_signature` silently returns `true` whenever that resolved organization has no `webhook_secret` configured. Once inside `create`, every registered handler (e.g. the status handler) resolves the *repository/stack/commit it writes to* from a completely different payload field (`repository.full_name`), with no check that this repository belongs to the organization that was actually authenticated. This breaks the equality "organization that authenticated == repository that is written," letting an attacker who controls (or targets) an organization with no `webhook_secret` configured forge events that are applied to any other tracked stack's commits.

### Finding Description
`before_action :verify_signature` computes the signing organization purely from the JSON body: [1](#0-0) [2](#0-1) 

It then asks `Shipit.github(organization: repository_owner)` for that org's `GithubApp` and calls `verify_webhook_signature`: [3](#0-2) 

Note line 77: `return true unless webhook_secret`. Shipit explicitly supports multiple GitHub App configurations per instance (one per organization), and `webhook_secret` is a documented, optional key per organization — the test fixtures demonstrate a two-org setup where one org has a real secret and the other has `webhook_secret: # nil`: [4](#0-3) 

Once `verify_signature` passes (trivially, for any org with no secret configured), `create` dispatches the *entire, attacker-chosen* JSON body to event handlers: [5](#0-4) 

Handlers, however, do not reuse `repository_owner` — they resolve the target repository/stack from a different field, `repository.full_name`: [6](#0-5) 

Nothing ties `repository.full_name`'s owner back to `repository_owner`/`organization.login`, the value that was actually used to select (or bypass) the authenticating secret. For the `status` event, the handler writes a `Status` record directly from unverified payload fields (`sha`, `state`, `description`, `target_url`, `context`), with no round-trip to GitHub's API to confirm the status is genuine — confirmed by the existing test asserting an exact 1:1 mapping from payload to persisted `Status`: [7](#0-6) 

These forged commit statuses are exactly what `ci.require` uses to gate deploys: [8](#0-7) 

**Binding broken:** `organization authenticated by verify_signature (derived from payload.repository.owner.login)` ≠ `organization/repository whose commit/stack state is mutated (derived from payload.repository.full_name)`.

Before the attack: for a properly configured org, forging events for repo R requires knowing R's org's `webhook_secret`.
After the attack: an attacker crafts a single payload where `repository.owner.login` is set to *any* organization configured in this Shipit instance that has no `webhook_secret` set (a documented, supported configuration state — not a deployment error), while `repository.full_name`/`sha` point at a commit belonging to a *different*, secret-protected stack. `verify_signature` authenticates the request against the no-secret org (trivially true), and the handler then writes state for the unrelated target repository's commit.

### Impact Explanation
A forged `status` event lets an unauthenticated attacker mark arbitrary commits on any tracked stack as passing required CI checks (`ci.require`), which is exactly the safety gate Shipit uses before permitting a deploy. This can unblock or facilitate an **unauthorized deploy** of a stack the attacker has no legitimate access to, without needing a Shipit session, API token, or the target org's webhook secret — matching the Critical impact bucket ("an unauthorized deploy"). A forged `push` event similarly lets the attacker trigger `GithubSyncJob` against an arbitrary tracked stack.

### Likelihood Explanation
Exploitability depends on at least one organization configured in the Shipit instance lacking a `webhook_secret` — a state the codebase explicitly supports and treats as "trusted by default" (`return true unless webhook_secret`) rather than rejecting outright. Any multi-tenant Shipit deployment tracking repositories across several GitHub orgs/apps (the exact shape the test fixtures model) is at risk if even one of those orgs was configured without a secret (e.g., during onboarding, or an internal/sandbox org). No credentials, sessions, or write access to GitHub are required — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted `X-Github-Event` header and JSON body.

### Recommendation
1. Do not fail open when `webhook_secret` is blank; require a secret to be configured for every organization or reject unsigned/unsigned-org webhooks outright.
2. Cryptographically/structurally bind the organization used for signature verification to the repository the handler mutates: after verifying the signature, re-derive `repository_owner` from the same payload field the handlers use (`repository.full_name`'s owner segment) and reject the request if it doesn't match the organization whose secret validated the signature.
3. Consider validating GitHub-signaled repository/commit state (e.g., commit statuses) against GitHub's API rather than trusting the webhook payload verbatim for security-sensitive gating logic like `ci.require`.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs: `no-secret-org` (no `webhook_secret`) and `victim-org` (secret configured, has a tracked stack with `ci.require: ["ci/tests"]`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "no-secret-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha awaiting required CI status>",
  "state": "success",
  "context": "ci/tests",
  "description": "forged",
  "target_url": "https://attacker.example"
}
```
3. `verify_signature` resolves `repository_owner` = `no-secret-org`, calls `verify_webhook_signature` which returns `true` unconditionally (`lib/shipit/github_app.rb:77`) regardless of any/no `X-Hub-Signature` header.
4. `StatusHandler` processes the payload using `repository.full_name` = `victim-org/victim-repo`, creating a `Status` record for the victim commit with `state: success`, satisfying `ci.require` and clearing the deploy gate without ever touching GitHub's real CI status for that commit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
