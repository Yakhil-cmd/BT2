### Title
Cross-organization webhook forgery via `repository.owner.login` / `repository.full_name` binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate an inbound webhook using `repository.owner.login` (or `organization.login`), while every downstream `Shipit::Webhooks` handler acts on `repository.full_name` to locate/create the `Repository`, `Stack`, and `Commit` records that are actually mutated. Because these two payload fields are never cross-validated, and because Shipit explicitly supports per-organization configs where `webhook_secret` can be left `nil` (documented in `docs/setup.md` and `config/secrets.development.example.yml`), an attacker who knows of any configured organization with no `webhook_secret` can send an unsigned/forged webhook whose `owner.login` matches that unprotected org while `repository.full_name` points at a completely different, protected stack tracked by Shipit.

### Finding Description
`verify_signature` derives the authenticating organization exclusively from `repository.owner.login`: [1](#0-0) [2](#0-1) 

This value picks a `GitHubApp` instance via `Shipit.github(organization:)`, which looks up the org config case-insensitively: [3](#0-2) 

If that org's `webhook_secret` is unset (a supported configuration, e.g. `webhook_secret: # nil` in `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.example.yml`), `verify_webhook_signature` unconditionally accepts the request: [4](#0-3) 

Once `verify_signature` passes, `create` dispatches the raw, attacker-controlled `params` to every registered handler for the event with no further authenticity check: [5](#0-4) 

Handlers such as `Handlers::PushHandler` and `Handlers::StatusHandler` do not use `repository.owner.login` to locate the target — they resolve the repository/stack by `repository.full_name` (as exercised by `test/controllers/webhooks_controller_test.rb`, which forges a push payload by only editing `unknown_repo_payload["repository"]["full_name"]`): [6](#0-5) 

Because the value used for **authentication** (`owner.login`) and the value used for **the write target** (`full_name`) are independent JSON fields in the same attacker-supplied body, and the signature check for the "authenticating" org is entirely skipped when that org has no secret, the attacker can freely set `full_name` to any other tracked stack's `owner/repo`, breaking the equality:
`organization whose secret authenticated the request == organization of the repository actually written to`.

### Impact Explanation
This lets an unauthenticated, unprivileged network attacker (no Shipit session, no `ApiClient` token, no webhook secret for the *target* org) inject forged GitHub events — fake `push`, `status`, `check_suite`, and `pull_request` events — against any stack tracked by the Shipit instance, as long as the instance has at least one configured organization without a `webhook_secret`. Concretely this can:
- Spoof a "success" commit status (`Handlers::StatusHandler`) for an attacker-chosen SHA on a victim's repository, which Shipit's continuous-deployment/merge-queue logic treats as a genuine CI signal, potentially triggering an unauthorized deploy or merge.
- Enqueue `GithubSyncJob` for a victim stack's branch (`Handlers::PushHandler`) to force synchronization of fabricated commit metadata.
- Manipulate pull-request/merge-queue state handlers for repositories the attacker does not control.

This matches the "unauthorized deploy, rollback or merge" / authentication-bypass impact tier, since the webhook authentication boundary meant to scope trust to a specific GitHub organization is bypassed for repositories outside that organization.

### Likelihood Explanation
Likelihood depends on the deployment having more than one GitHub organization configured with at least one of them lacking a `webhook_secret` — a configuration explicitly documented and shown in the codebase's own examples/fixtures as valid (`webhook_secret: # nil`). Any Shipit operator running the documented multi-org configuration without setting a secret on every organization is exposed. No credentials, session, or prior access are required, only knowledge/guessing of an unprotected organization's login and the target's `repository.full_name`.

### Recommendation
- Validate that `repository.owner.login` (or `organization.login`) used for signature-based authentication matches the `repository.full_name` prefix actually acted upon by every handler, rejecting mismatches.
- Do not implicitly trust `full_name` derived from the payload to resolve/create/mutate `Repository`/`Stack` records when the request was authenticated as "no signature required" for an unrelated org; require signature verification to always be organization/repository-scoped, and disallow silently accepting requests when `webhook_secret` is blank unless explicitly opted-in per repository, not per organization.

### Proof of Concept
1. Operator configures `secrets.github` with two orgs: `OrgWithSecret` (real target, has `webhook_secret`) and `OrgOpen` (has `webhook_secret: nil`, per supported config in `config/secrets.development.example.yml`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {
    "owner": { "login": "OrgOpen" },
    "full_name": "OrgWithSecret/victim-repo"
  },
  "sha": "<attacker-chosen-sha>",
  "state": "success",
  "context": "ci/required-check",
  "branches": [{ "name": "main" }]
}
```
3. `verify_signature` resolves `repository_owner` = `"OrgOpen"`, fetches `Shipit.github(organization: "OrgOpen")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`) — no valid signature is required.
4. `Handlers::StatusHandler` processes the payload using `repository.full_name` ("OrgWithSecret/victim-repo") and records a spoofed successful CI status for the attacker's SHA on the victim's tracked stack, which can feed into continuous-deployment/merge-queue automation without ever validating against `OrgWithSecret`'s real webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
