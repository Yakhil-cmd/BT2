## Title
Reward Commission Misattribution via Undelayed `UpdateCommissionCollector` in Partitioned Epoch Rewards - (File: `programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The vote program's custom commission collector feature (SIMD-0232) lets the withdraw authority redirect commission payouts to a different account via `update_commission_collector`. Unlike commission-*rate* changes (`update_commission` / `update_commission_bps`), which are deliberately delayed by up to a full epoch to prevent "last-minute commission rugs," the commission *collector* address has no such delay. During epoch-reward calculation, the collector address used to route commission lamports is read from the "current" vote account state rather than a state snapshot recorded during the epoch in which the rewards were actually earned. This mirrors the DeliHook bug class: the entity that receives accrued rewards is resolved using post-change state instead of the state that was in effect while the rewards accrued, producing misattributed rewards.

### Finding Description
`update_commission` enforces `is_commission_update_allowed`, restricting rate increases to the first half of an epoch, specifically to prevent commission changes from unfairly affecting already-accrued rewards: [1](#0-0) 

`update_commission_bps` (SIMD-0291) explicitly notes it has "no timing restrictions... per SIMD-0249": [2](#0-1) 

However `update_commission_collector` (SIMD-0232), which changes *where* commission lamports are sent, has no timing gate at all — only a withdrawer-signature check and account validation: [3](#0-2) 

During epoch reward calculation, `redeem_delegation_rewards` deliberately delays the *commission rate* (`commission_bps`) by pulling it from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` when `delay_commission_updates` is enabled, to avoid "last minute commission rugs": [4](#0-3) 

But the *commission collector* (`commission_pubkey`) — i.e., who actually receives the commission lamports — is resolved from `vote_state`, which comes from `distribution_epoch_vote_accounts` (the current/live vote account view), with no equivalent delay: [5](#0-4) 

So while the *rate* used to compute commission is locked in based on state from before the rewarded epoch, the *recipient* of that commission is whoever is configured as collector at reward-distribution time — which can be changed by the withdraw authority at any point up until distribution, including after all the reward-generating activity for the epoch has already occurred. This is the same root-cause pattern as the reported bug: the payout recipient is bound at settlement time to "current" state instead of to the state that was authoritative during the period the reward was earned.

### Impact Explanation
An operator (or a party who newly acquires withdraw authority over a vote account, e.g., via a business/vote-account sale) can call `UpdateCommissionCollector` at any time before partitioned reward distribution for a completed epoch, causing the entire epoch's commission — which economically accrued to whoever held the collector role throughout that epoch — to be paid to a different, newly-designated address instead. This is a misattributed-rewards condition directly analogous to the reported DeliHook issue: the party that earned/held the role during the accrual period is deprived of the reward, which is instead credited to the new/current holder. This is listed among the explicitly accepted impact classes (misattributed or duplicated rewards) and occurs in the reward distribution path.

### Likelihood Explanation
The action requires only a withdraw-authority signature — an unprivileged, permission-normal operation available to any vote account's withdrawer, not a validator/peer/operator-role capability restricted by SECURITY.md scope exclusions. It requires no crafted snapshot, no external process, and no multi-client coordination — a single `UpdateCommissionCollector` transaction issued near the end of an epoch (or between epoch end and reward distribution) is sufficient. The asymmetry with the intentionally-delayed commission-rate logic (which the codebase itself documents as guarding against "commission rugs") strongly suggests the collector-address path was not given equivalent protection.

### Recommendation
Apply the same delay semantics used for `commission_bps` (via `snapshot_epoch_vote_accounts` / `rewarded_epoch_vote_accounts`) to the commission collector lookup in `redeem_delegation_rewards`, so that `commission_pubkey` is resolved from the vote account state recorded during (or before) the rewarded epoch rather than from the live `distribution_epoch_vote_accounts` state. This ensures the party who is the "current" collector at distribution time cannot receive rewards that accrued while a different collector was configured.

### Proof of Concept
1. Vote account V has `inflation_rewards_collector = A`, with `custom_commission_collector` and `block_revenue_sharing`/`delay_commission_updates` features active.
2. Throughout rewarded epoch N, stake delegated to V earns commission that should economically accrue to collector A.
3. Near the end of epoch N (or during the gap before reward calculation/distribution for epoch N happens in epoch N+1), the withdraw authority calls `UpdateCommissionCollector` to set the collector to B — no timing restriction blocks this, per `update_commission_collector` in `programs/vote/src/vote_state/mod.rs`.
4. When `redeem_delegation_rewards` runs (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs`), `commission_bps` correctly reflects the rate from the snapshot/rewarded epoch (delayed), but `commission_pubkey` is computed from the current `vote_state` (i.e., collector B), so all of epoch N's commission lamports — earned while A was collector — are paid to B instead of A.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
