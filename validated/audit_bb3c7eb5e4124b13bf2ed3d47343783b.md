## Binding claimed vs. actual

Claimed binding: `webhook_secret(org owning attacker's repo) verified body` == `org owning the Repository/Stack whose row is mutated`.

- `CheckSuiteHandler#process` enforces this: it scopes through `stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` — i.e., only stacks belonging to the exact repository named in the (signature-verified) payload are touched. [1](#0-0) [2](#0-1) 

- `StatusHandler#process` does **not** call `stacks` or `repository_name` at all. It runs a global, unscoped query `Commit.where(sha: params.sha)` across the entire `commits` table (all stacks, all repositories, all organizations) and calls `commit.create_status_from_github!(params)` on every match. [3](#0-2) [4](#0-3) 

`verify_signature` in `WebhooksController` only checks that the payload's `repository.owner.login`/`organization.login` matches an org with a known `webhook_secret` via `Shipit.github(organization:)` — it never checks that the named repository is one the attacker is authorized for beyond "this org's secret signed it," and it never scopes what the handler is allowed to mutate. [5](#0-4) 

## Root cause

`Commit#sha` is not unique across the `commits` table; each `Stack`/`Repository` gets its own `Commit` row per pushed sha (`belongs_to :stack`), so identical SHAs can legitimately exist in unrelated stacks (forks, mirrors, cherry-picks, shared vendor/base commits, or simply an attacker who forces their fork's HEAD to match a known public SHA of the victim repo before pushing/tagging it). `StatusHandler` was written under the (false) assumption that a `sha` uniquely identifies a Shipit-tracked commit, so it never re-derives or checks `repository_name`/`stacks` the way every other handler (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`) does. [6](#0-5) [7](#0-6) 

## Exploit flow

1. Attacker owns/controls a repository under an org whose GitHub App installation and `webhook_secret` are configured in Shipit (a normal, unprivileged precondition — they just need a repo in that org, e.g. a personal fork granted org membership, or any org that installs the same Shipit GitHub App broadly).
2. Attacker observes (via public GitHub, no secrets needed) a commit SHA that exists in a victim `Stack`'s `Commit` table — e.g. a shared base commit, a commit cherry-picked/rebased identically into both repos, or by forcing their own branch HEAD to an SHA that also matches content in the victim repo.
3. Attacker sends `POST /webhooks` with `X-Github-Event: status` and a body naming *their own* repository (so `verify_signature` passes using their org's legitimately-known `webhook_secret`) but with `sha` set to the shared/victim SHA, and `state: success` (or any other state).
4. `WebhooksController#create` dispatches to `Handlers::StatusHandler`, which runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this matches the victim's `Commit` row too, regardless of `stack_id`/`repository`, and creates a `Status` row on the victim stack via `Status.replicate_from_github!`. [8](#0-7) 
5. That forged status flows through `Commit#add_status`, which can flip `Commit#state`, trigger `stack.schedule_merges`, fire `deployable_status`/`commit_status` hooks, and (via `Commit#schedule_continuous_delivery`) enqueue continuous delivery on the victim stack if it becomes "deployable." [9](#0-8) [10](#0-9) 

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) do not prevent this because they validate *that a known org signed the body*, not *that the handler only mutates rows belonging to the repository named in that body*. `CheckSuiteHandler` independently enforces the latter via `stacks`; `StatusHandler` does not.

### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a signed webhook from one repository mutate another repository's `Commit`/`Status` state - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike every other webhook handler (`PushHandler`, `CheckSuiteHandler`, all PR handlers) which resolve `stacks`/`repository` from the signed payload's `repository.full_name`. Because `Commit#sha` is not globally unique (each `Stack` has its own `Commit` rows), a `status` webhook whose signature is validated for the attacker's own repository/org can still write a `Status` onto a `Commit` belonging to a completely different `Stack`/`Repository`/organization if the SHAs coincide.

### Finding Description
Broken binding: `organization verified via webhook_secret for repository named in payload` should equal `organization owning the Stack/Commit row that gets mutated`. This holds for `CheckSuiteHandler`, which filters via `stacks` (itself derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`), but not for `StatusHandler`, whose `process` method never touches `repository_name`/`stacks` and instead does a table-wide `Commit.where(sha:)` lookup, then calls `create_status_from_github!` on every matching commit across every stack. Root cause: SHAs are only unique per-`Stack` (`belongs_to :stack` on `Commit`), so an attacker who controls any repository under a validly-configured GitHub App installation can forge a `status` event naming their own repo (passing `verify_signature`) with a `sha` that also happens to exist in a victim stack, causing a `Status` row (and downstream `commit_status`/`deployable_status` hooks, continuous-delivery scheduling) to be created against the victim's commit/stack.

### Impact Explanation
A payload authenticated for one repository mutates another repository's stack/commit state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attacker can flip a victim commit's CI state to `success`, which can cascade into `stack.schedule_merges` and, if `continuous_deployment` is enabled on the victim stack, into an automatic deploy via `Commit#schedule_continuous_delivery`. This is repeatable against any repository/stack whose `Commit#sha` the attacker can predict or reproduce, and the blast radius spans any Shipit-tracked stacks sharing SHAs, not limited to the attacker's own tenant.

### Likelihood Explanation
Preconditions: attacker needs a repository under an org/installation whose `webhook_secret` is configured in Shipit (a low bar — many orgs configure one GitHub App broadly across all their repos), and needs a target commit SHA that also exists as a `Commit` row in a victim stack (achievable via shared history, cherry-picks/rebases producing identical trees+metadata, or vendored/mirrored commits — SHAs are public information on GitHub). No Shipit credentials, session, or GitHub secrets are required beyond sending an HTTP POST with a body whose repository field matches an org the attacker legitimately belongs to.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: resolve the repository from the signed payload (`stacks`/`Repository.from_github_repo_name(repository_name)`) and restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalently join through `stack_id in stacks`), rejecting/ignoring matches on commits belonging to stacks outside that repository's own stacks.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (illustrative)
test "status handler does not cross tenant boundary for a shared sha" do
  attacker_repo = shipit_repositories(:attacker_org_repo)
  victim_stack  = shipit_stacks(:shipit) # belongs to a different repository/org
  shared_sha    = "6d9278037b872fd9a6690523e411ecb3aa181355"

  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)

  forged_payload = {
    "sha" => shared_sha,
    "state" => "success",
    "repository" => { "full_name" => attacker_repo.github_repo_name, "owner" => { "login" => attacker_repo.owner } },
    "branches" => [{ "name" => victim_stack.branch }]
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)
  end
end

test "check_suite handler correctly scopes to the named repository (control)" do
  attacker_repo = shipit_repositories(:attacker_org_repo)
  victim_stack  = shipit_stacks(:shipit)

  forged_payload = {
    "repository" => { "full_name" => attacker_repo.github_repo_name },
    "check_suite" => { "head_sha" => victim_stack.commits.last.sha, "head_branch" => victim_stack.branch }
  }

  assert_no_enqueued_jobs(only: RefreshCheckRunsJob) do
    Shipit::Webhooks::Handlers::CheckSuiteHandler.call(forged_payload)
  end
end
```
The first assertion currently fails (a `Status` is created on `victim_commit`), demonstrating the tenant-boundary violation unique to `StatusHandler`; the second passes, confirming `CheckSuiteHandler` is correctly scoped via `stacks` and ruling out a systemic `Handler#call`/`WebhooksController` defect.
