### Title
Unchecked i128 ray-value overflow during interest accrual permanently freezes an entire market — all verbs panic before any state can change - ([File: contracts/pool/src/interest.rs])

### Summary
The WebKit CVE is a missing-metadata-validation bug that turns attacker-shaped input into a release assertion crashing the host process. The analog in XOXNO Lending is the missing bound between scaled position size (RAY-scale `i128`) and borrow-index growth: when `scaled_borrowed * borrow_index` no longer fits in `i128`, accrual panics, and because every pool verb accrues first, the market is permanently frozen — no repay, withdraw, or liquidation can ever execute again. The protocol's own stress test proves the cliff is reachable and that the `MAX_BORROW_INDEX_RAY` cap never engages in time.

### Finding Description
`global_sync` in `contracts/pool/src/interest.rs:20-33` runs before every state-changing operation and calls `accrue_chunk`, which delegates to `accrue_step` (`common/src/rates`). Inside the step, the ray value of total debt (`scaled_to_original` / `mul_div_half_up` in `common/src/math/fp.rs:50-52` via `fp_core`) is computed as an `i128` multiply. A ray value is `amount * index`; with an 18-decimal asset, a billion-token position is already ~10^54 in scaled terms, so an index of ~x170 overflows `i128::MAX` (~1.7e38). The panicking path is `panic_with_error!(env, GenericError::MathOverflow)` (`common/src/math/fp.rs:13-16`).

There is no validation linking supply/borrow caps to the index ceiling: a user can `supply` and `borrow` a whale-sized book (unprivileged `supply`/`borrow` entrypoints), let utilization sit near the steep end of the rate curve (e.g., the 175% max-rate XLM-style curve), and permissionless `update_indexes` calls plus ordinary verb-triggered accrual advance the index. The test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`) demonstrates: `try_update_indexes_for` fails with `MATH_OVERFLOW`, `borrow_index < MAX_BORROW_INDEX_RAY` (the safety cap never engages), and both `try_withdraw_raw` and `try_repay` revert with the same panic — permanently, since rollback preserves the over-cliff state and the index is monotonically non-decreasing.

### Impact Explanation
Permanent freezing of user funds for the entire affected (hub, token) book: suppliers can never withdraw, borrowers can never repay, liquidators can never liquidate — every path panics inside `global_sync` before touching state. The pool's `cash`/`supplied` books are intact but unreachable, matching the "release assertion kills the UI process" shape of the CVE: a malformed scale relationship (unvalidated "metadata" — scaled amount vs index magnitude) crashes the coordinator on every subsequent message.

### Likelihood Explanation
Medium. It requires whale-scale positions (caps must admit them — the test uses lifted caps and `max_utilization` disabled) plus years at high utilization on a steep curve, but no privileged action: a single well-funded address supplies a huge principal, borrows near full utilization, and waits/pings `update_indexes`. Notably the attacker loses nothing extra — the freeze also bricks honest suppliers' exits, making it a griefing/insolvency-latency weapon rather than a self-harm edge case.

### Recommendation
Enforce the ray-value ceiling where accrual actually computes it: in `accrue_step` (or `accrue_chunk` call site), clamp or cap the borrow index so `scaled_borrowed * borrow_index` stays within `i128` — i.e., make the existing `MAX_BORROW_INDEX_RAY` check the tighter of `MAX_BORROW_INDEX_RAY` and `i128::MAX / scaled_borrowed`. Alternatively, reject `supply`/`borrow` amounts whose ray-scaled value exceeds `i128::MAX / MAX_BORROW_INDEX_RAY` at entry, so the product can never overflow regardless of index growth.

### Proof of Concept
`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361` — supplies 1e9 18-decimal tokens, borrows 98% of it, advances ledger time in a loop calling `update_indexes` until it reverts with `MATH_OVERFLOW`, then asserts `withdraw` and `repay` also revert with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.
