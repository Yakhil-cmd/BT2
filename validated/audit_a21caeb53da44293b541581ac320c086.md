### Title
Liquidation risk parameters can only be updated as an atomic tuple, so a permissionless keeper can force an adverse bonus/fee onto a healthy account to update a single parameter — (File: contracts/controller/src/risk/params.rs)

### Summary
`update_account_threshold` refreshes a supply position's `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees` only as a single atomic write in `apply_gated_liquidation_params`. There is no path to update one field independently. Any authenticated caller can invoke this on arbitrary `account_ids`, and for accounts that clear the `THRESHOLD_UPDATE_MIN_HF_RAW` (HF ≥ 1.05) gate, the entire tuple — including changes that favor the liquidator (higher bonus, lower fee, lower threshold) — is stamped onto the position. The result mirrors the Gitcoin `updateStartAndEndTimes` flaw: a caller cannot propagate a single desired parameter without also ingesting every other pending config delta.

### Finding Description
In `contracts/controller/src/risk/params.rs`:

- `update_account_threshold(env, caller, has_risks, account_ids)` is callable by any authenticated caller and iterates over arbitrary account IDs, calling `sync_account_thresholds` with `RiskRefreshScope::FullTuple` when `has_risks = true` (lines 124–144).
- `sync_account_thresholds` restamps every listed supply asset of the target account (lines 182–215), then only enforces a post-refresh `health_factor >= 1.05` (lines 221–234).
- The actual write is `apply_gated_liquidation_params` (lines 68–93): if the pending config change "favors the liquidator" and the hypothetical HF clears 1.05, it assigns `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees` together. No selective update exists.

The same tuple coupling exists on the user paths `merge_supply_leg` and `merge_withdraw_leg`, so even the account owner cannot refresh a favorable field without also accepting an adverse one.

The harness test `test_update_account_threshold_propagates_adverse_tuple_to_healthy_account` (`tests/test-harness/tests/controller/keeper.rs:268-299`) proves a healthy account takes the whole tuple — including `liquidation_bonus + 500` — in one permissionless keeper call.

### Impact Explanation
Like the round operator who could not extend `roundEndTime` without also re-supplying unrelated timestamps, here neither the account owner nor a keeper can restamp a single parameter. Concretely, if governance changes multiple fields (e.g., lowers `liquidation_threshold` for safety while raising `liquidation_bonus`), a keeper calling `update_account_threshold(caller, true, [victim_id])` forces the higher bonus onto the victim's stored position while its HF ≥ 1.05. The stored `liquidation_bonus` later determines the seized-collateral premium in the liquidation bonus curve (`get_account_bonus_params` reads stored values), so future liquidations transfer more of the user's collateral to liquidators — a direct theft of user funds enabled by a permissionless call. The gate protects only accounts near the liquidation boundary; well-collateralized accounts have no defense.

### Likelihood Explanation
Likelihood is moderate: it requires a governance listing edit that leaves a liquidator-favoring delta pending (e.g., a raised bonus or cut fee combined with another change the user wants). Such mixed edits are realistic, and once pending, any address can execute `update_account_threshold` against any healthy account ID — no timing race or privileged role needed.

### Recommendation
Allow independent updates of `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees` — e.g., gate each field separately: always apply changes that favor the borrower, and apply liquidator-favoring fields individually under the HF ≥ 1.05 check, rather than coupling all three in `apply_gated_liquidation_params`. Alternatively, require the account owner's auth to stamp liquidator-favoring changes onto their own position.

### Proof of Concept
1. Governance edits an asset config: `loan_to_value = 5000`, `liquidation_bonus = bonus + 500`, `liquidation_fees = fee - 50` (mixed, liquidator-favoring delta pending).
2. Victim holds a supplied position with HF ≥ 1.05.
3. Any caller executes `controller.update_account_threshold(caller, true, vec![victim_account_id])`.
4. `apply_gated_liquidation_params` writes the whole tuple; the victim's stored `liquidation_bonus` increases without consent.
5. On any later liquidation, the bonus curve computes a larger seizure premium against the victim's collateral — quantified in `keeper.rs:288-298` where the tuple `(6100, bonus+500, fee-50)` lands atomically on a healthy account.
