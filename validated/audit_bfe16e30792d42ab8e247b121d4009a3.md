### Title
AA responses silently drop payment messages for fixed-denomination (NFT-like) assets, permanently trapping deposited funds - (File: aa_composer.js)

### Summary
When an AA's oscript composes a response containing a `payment` message for an asset with `fixed_denominations: true` (ocore's indivisible-coin asset type — the closest analog to an ERC-721 NFT, since these coins exist in specific fixed amounts/denominations similar to unique tokens), the AA composer silently discards that payment message instead of sending it or bouncing the trigger. The AA balance is never debited for it either, so the payout is simply never delivered, exactly mirroring the OpenQ bug where NFT payout logic was entirely missing from the claim path.

### Finding Description
In `handleTrigger`'s `sendUnit` function, each `payment` message's asset is loaded and inspected: [1](#0-0) 

For assets with `fixed_denominations` (indivisible/NFT-like assets), the code explicitly skips processing "will skip it later" and does not raise an error. Later, these messages are filtered out entirely: [2](#0-1) 

If this filtering empties out all messages, the trigger is treated as a "successful empty response" rather than a bounce, meaning the deposit that triggered the AA is accepted and consumed but no error is surfaced to the AA author or the recipient: [3](#0-2) 

Critically, `updateFinalAABalances` computes balance deltas strictly from `objUnit.messages` of the unit that is actually sent: [4](#0-3) 

Since the fixed-denomination payment message was removed before `objUnit` was built, it never appears in `objUnit.messages`, so the AA's balance for that indivisible asset is never decremented. The asset remains logically "in the AA" per `aa_balances`, but there is no code path by which the AA can ever pay it out — the composer will always strip these messages on every subsequent invocation too.

Nothing in AA-definition-time validation (`aa_validation.js`, `case 'payment'`) rejects or warns about targeting a fixed-denomination asset in a payment message, so an AA author can freely write oscript that appears to pay out an indivisible/NFT-like asset, but that payout will never execute: [5](#0-4) 

This matches the reported bug class precisely: the payout code path for one category of asset (NFT-equivalent) is missing from the composer, while divisible/base-asset payments work correctly.

### Impact Explanation
Any AA designed to receive an indivisible (fixed-denomination) asset deposit and later pay it back out (e.g., an escrow, marketplace, or auction AA holding NFT-like collectibles) will permanently trap that asset. Users who send such assets to the AA, expecting a contractual payout, will never receive it, and the AA has no means to release it — this is an AA fund loss/freezing condition reachable by any ordinary asset issuer or AA trigger sender who deposits a fixed-denomination asset into an AA that attempts to forward it.

### Likelihood Explanation
This triggers deterministically any time an AA's response messages include a `payment` for a `fixed_denominations` asset — no attacker collusion or special conditions are required. It will affect every AA author who (reasonably, given no validation-time rejection) writes oscript assuming indivisible assets can be paid out, and every user who deposits such an asset expecting a response payout.

### Recommendation
Either (a) reject AA definitions at validation time (`aa_validation.js`) that reference a payment message whose asset could resolve to `fixed_denominations: true`, forcing authors to avoid this asset type entirely, or (b) implement proper indivisible-asset payout support in `aa_composer.js`'s `sendUnit`, analogous to `indivisible_asset.js`'s coin-picking logic, so that AAs can actually compose valid multi-denomination payment messages for indivisible assets instead of silently dropping them. At minimum, the trigger should bounce with an explicit error (as done for `is_private` assets at `aa_composer.js:1329`) rather than silently succeeding with an empty response, so the loss becomes visible to the AA author.

### Proof of Concept
1. Define an asset `A` with `fixed_denominations: true` (e.g., unique NFT-like collectible denominations) and `issued_by_definer_only: true`.
2. Deploy an AA whose oscript, upon receiving a trigger, responds with a `payment` message paying asset `A` to `trigger.address` (e.g., an escrow that returns the deposited collectible).
3. Send asset `A` to the AA together with a triggering payment.
4. Observe: `aa_composer.js` loads `objAsset.fixed_denominations === true` at line 1327, skips completing that payment message, then filters it out at line 1356; if no other messages remain, `handleSuccessfulEmptyResponseUnit(null)` is invoked at line 1354/1360 — the trigger is accepted as successful, no bounce occurs, and no unit paying out asset `A` is ever produced.
5. Confirm via `aa_balances` that the AA's balance for asset `A` is unchanged (still holds the deposited amount) but no mechanism exists to withdraw it, since every future invocation repeats the same silent filtering.
