### Title
Webhook signature is verified against the GitHub App bound to `repository.owner.login` / `organization.login`, but handlers act on the independent `repository.full_name` field, letting an org that legitimately owns one GitHub App forge cross-repository writes against a different org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository_owner`, extracted from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves the repository/stack to *act on* using a completely different, independently-controlled field: `payload.dig('repository', 'full_name')` [1](#0-0) . Nothing ties the value used for signature-selection to the value used for target-resolution, so a request signed by one GitHub organization's webhook secret can carry a forged `repository.full_name` pointing at a stack owned by a different organization.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 

`repository_owner` is read from the payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

This chooses which multi-tenant GitHub App config (and thus which `webhook_secret`) is used to validate the HMAC — Shipit explicitly documents multi-organization support where each organization key in `secrets.yml` has its own `webhook_secret` [4](#0-3) .

Once the signature is accepted, the actual event handler resolves the target repository independently via `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 

`PushHandler` uses this to find stacks and trigger `stack.sync_github(expected_head_sha: params.after)` [5](#0-4) , and the pull-request handlers (`OpenedHandler`, `LabeledHandler`, `ReopenedHandler`, `LabelCapturingHandler`) resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to archive/unarchive/create review stacks [6](#0-5) , [7](#0-6) . `Repository#owner` (used only for `Shipit.github(organization: owner)` when the repository record itself needs GitHub API access) is a stored DB column set from `full_name`'s owner segment at repository-creation time, not from the webhook payload's `repository.owner.login` used for signature validation [8](#0-7) .

The equality the code implicitly relies on but never enforces is:
```
organization authenticated by verify_signature (repository.owner.login / organization.login)
   ==
organization/repository actually written by the handler (repository.full_name)
```
Because the HMAC is verified using the secret keyed by `repository.owner.login`, and `repository.full_name` is a sibling field in the same JSON body that is *never cross-checked* against `repository.owner.login`, an actor who controls (or is a legitimate GitHub App installer for) one organization configured in Shipit's multi-org `secrets.yml` can compute a valid signature with their own org's `webhook_secret` while setting `repository.full_name` to point at a stack belonging to a different, victim organization also configured on the same Shipit instance. The signature check passes (their own secret, correctly computed), yet the handler that runs afterwards operates on the victim's stack.

### Impact Explanation
In a multi-org Shipit deployment (explicitly supported and documented), this breaks the binding between "which organization's webhook secret authenticated this request" and "which repository's stack gets written to." Concretely:
- `PushHandler` can force `stack.sync_github(expected_head_sha: ...)` on a victim organization's stack using an attacker-forged `after` SHA and `ref`, manipulating recorded commit/branch state for a repository the attacker's org has no legitimate relationship to.
- `MembershipHandler` creates/updates `Team` records and adds/removes arbitrary GitHub logins as team members based on `params.organization.login` taken from the *unverified-against-owner* payload field, `Team#organization` being set directly from it [9](#0-8) . Team membership drives `Shipit.github_teams` authorization elsewhere in the app, so a forged/mismatched organization value here escalates into cross-org team/authorization state.
- Pull request handlers can archive/unarchive or create review stacks for a victim repository based on a forged `repository.full_name`.

This matches the "organization that authenticated versus the repository that is written" analog and crosses a repository/authorization boundary without requiring any Shipit session or API token — only the ability to be a legitimate webhook sender for *any one* of the organizations configured on the instance. Given the write is a cross-repository write into stack/team state, this rises to the High/Critical band defined by the rules (cross-repository writes / escalation into `Shipit.github_teams` authorization).

### Likelihood Explanation
Exploitability is contingent on the deployment actually configuring more than one GitHub organization in `secrets.yml` (explicitly a supported, documented configuration) and both attacker-controlled and victim repositories/organizations coexisting on the same Shipit instance. Under that documented configuration, the attacker needs no elevated Shipit credentials at all — only control of their own org's legitimate webhook delivery (i.e., they can trigger any GitHub event, e.g. via their own repo, and edit/replay/proxy the delivery body before it reaches Shipit, since GitHub webhook deliveries are attacker-observable/replayable by whoever administers that org's webhook endpoint settings). This is a realistic but deployment-dependent condition, so likelihood is Medium-to-High specifically for multi-tenant Shipit installations.

### Recommendation
Bind the field used for signature-app-selection to the field used for target resolution: after selecting `github_app` via `repository_owner`, validate that `repository_owner` matches the owner segment parsed from `payload.dig('repository', 'full_name')` (and, for `organization`/`membership` events, that `organization.login` matches the resolved `Repository#owner` for any repository ultimately touched) before invoking any handler. Reject the webhook with 422 on mismatch.

### Proof of Concept
1. Deploy Shipit with two organizations configured under `github:` in `secrets.yml`: `attacker-org` (attacker has legitimate control/installation) and `victim-org` (hosts the target stack), per the documented multi-org format [10](#0-9) .
2. Craft a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body (`OpenSSL::HMAC.hexdigest('sha1', webhook_secret, body)`), as done by `GitHubApp#verify_webhook_signature` [11](#0-10) .
4. POST to `/github/webhooks` with `X-Github-Event: push` and the computed signature.
5. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature with the attacker's own secret [12](#0-11) .
6. `PushHandler#process` resolves stacks via `repository_name = "victim-org/victim-repo"` and calls `sync_github(expected_head_sha: params.after)` on the victim's stack [5](#0-4) , mutating victim-owned stack state despite the request never being authenticated against `victim-org`.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
