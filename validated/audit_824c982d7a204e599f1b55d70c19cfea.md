### Title
Cross-tenant `Team`/`Membership` write via `membership` webhook signed by an attacker's own organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the signing `GitHubApp` (and thus the HMAC secret to verify against) solely from `params.dig('repository','owner','login')`, while `MembershipHandler#process` mutates a `Team`/`Membership` located purely by `params.team.id` (an attacker-supplied integer), never checking that the org whose secret signed the request actually owns that team. An attacker who controls any organization configured on the Shipit instance (with its own `webhook_secret`) can therefore sign a `membership` event with their own secret and use it to add/remove members on a `Team` belonging to a different, victim organization.

### Finding Description
Binding claimed by the code (but not enforced): `repository_owner` (the org whose secret is used in `verify_signature`) == the org that owns the `Team` row mutated by `MembershipHandler#process`.

- `verify_signature` in [1](#0-0)  picks the `GitHubApp` with `Shipit.github(organization: repository_owner)` and checks the HMAC only against that org's `webhook_secret`. `repository_owner` is read directly from attacker-controlled payload: [2](#0-1) .
- Shipit supports multiple orgs, each with its own independent `webhook_secret`, selected via `Shipit.github(organization:)` / `github_app_config` [3](#0-2) , and the actual comparison is a plain HMAC-SHA1 compare in `GitHubApp#verify_webhook_signature` [4](#0-3) , scoped only to the org named in the request itself.
- Once signature verification passes for *any* configured org, `MembershipHandler#process` runs and never re-checks `repository_owner` or cross-validates the org against the team being mutated: [5](#0-4) .
- The team lookup is keyed purely on the numeric `github_id`: `Team.find_or_create_by!(github_id: params.team.id)`. If a `Team` with that `github_id` already exists (e.g. a real Shopify team synced previously), the block that would set `team.organization = params.organization.login` is skipped entirely, and the pre-existing team (whatever real org it belongs to) is fetched and then mutated by `team.add_member(member)` / `team.members.delete(member)`: [6](#0-5) .

Exploit flow: the attacker registers/controls organization `attacker-org` on the Shipit instance (a legitimately configured tenant with its own `webhook_secret`). They send `POST /webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `attacker-org`'s secret, `repository.owner.login = "attacker-org"` (so `verify_signature` passes), but `team.id` set to a known/guessable `github_id` of a victim org's team (e.g. Shopify's), and `member.login` set to their own GitHub handle. `verify_signature` only checks that the request was signed by *some* org's secret it happens to own — it never checks that this org is the one whose team is being modified. `MembershipHandler#process` then finds the victim's pre-existing `Team` by `github_id` and adds the attacker as a member, or removes an existing member.

None of the existing guards catch this: `verify_signature` only authenticates "a request signed by org X was received", not "org X may modify team Y"; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not cross-tenant ownership; there is no `require_permission!`/org-matching check inside `MembershipHandler`.

### Impact Explanation
A successful request lets an attacker who owns any configured org on a multi-tenant Shipit instance add themselves (or remove a legitimate member) to/from another organization's `Shipit::Team` row, purely by guessing/enumerating the numeric GitHub team `github_id` (these are visible via public GitHub API team lookups) — no privileged Shipit credentials needed. Since `Shipit.github_teams` drives OAuth-team-based authorization [7](#0-6) , and `Team`/`Membership` rows back that mechanism, this is an escalation into `Shipit.github_teams` authorization for a different tenant/org than the one that authenticated the request — matching the High severity bucket ("escalation into `Shipit.github_teams` authorization"). It is repeatable against any team `github_id` the attacker can enumerate and against any number of other configured organizations.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations, each with its own `webhook_secret` (a documented, supported configuration per `Shipit.github_app_config`); (2) attacker controls one such configured org (owns/administers it, so they legitimately know its `webhook_secret` and can trigger/replay a `membership` webhook, or simply POST directly to `/webhooks` with a self-computed signature since they know their own org's secret); (3) the victim's `Team` row must already exist in Shipit's DB (true for any org that has previously synced OAuth teams or received a legitimate `membership` webhook) so the `find_or_create_by!` block is skipped and the existing team's identity is preserved while membership is still mutated. Attacker cost is low — one crafted HTTP POST, no browser session, no GitHub App private key needed.

### Recommendation
In `MembershipHandler#process`/`#find_or_create_team!`, validate that `params.organization.login` (and/or `repository_owner`) matches the `Team#organization` of any pre-existing record before mutating membership, and reject/log mismatches instead of silently operating on the found team. Additionally, `WebhooksController#verify_signature` should be verified alongside a check that the event payload's `organization.login`/`team` ownership is consistent with `repository_owner` before dispatch.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership from attacker org can mutate a team belonging to another org" do
  victim_team = shipit_teams(:shopify_developers) # pre-existing Team, organization: 'shopify'

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-login' },
    repository: { owner: { login: 'attacker-org' } } # signs with attacker-org's own webhook_secret
  }

  assert_difference -> { victim_team.memberships.count }, 1 do
    post :create, body: payload.to_json, as: :json
    assert_response :ok
  end
  assert victim_team.reload.members.exists?(login: 'attacker-login')
  assert_equal 'shopify', victim_team.organization # team org unchanged, yet its membership was still mutated
end
```
Both sides of the claimed binding (`repository_owner == 'attacker-org'` used for signing vs. `victim_team.organization == 'shopify'` being the org actually mutated) diverge, confirming the cross-tenant write.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
