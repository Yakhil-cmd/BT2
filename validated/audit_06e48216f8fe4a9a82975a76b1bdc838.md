### Title
Session Fixation on GitHub OAuth Login — Session ID Not Rotated on Authentication — ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`Shipit::GithubAuthenticationController#callback` authenticates a user after a successful GitHub OAuth handshake and immediately writes the resulting identity into the *existing* Rack session (`session[:user_id]`, `session[:authenticated]`) without ever calling `reset_session`. [1](#0-0)  This breaks the intended binding "GitHub identity that completed OAuth == the `User` that should be bound to *a fresh* session," because the pre-existing session identifier is preserved across the trust boundary crossing (anonymous → authenticated).

### Finding Description
The external report's root cause is that a security-relevant value (the unlock timestamp) is trusted without validating it is fresh/current, allowing an attacker to bind a favorable-but-stale state to a privileged action. The structural analog here is that the *session identifier* — not a signed/verified artifact of the OAuth exchange — is implicitly trusted to represent "this browser's own, fresh session," and Shipit never re-validates or refreshes it at the moment authentication state changes.

Concretely:
- `callback` reads `request.env['omniauth.auth']` (the verified GitHub identity) and calls `sign_in_github(auth)`, which resolves/creates a `Shipit::User` and returns its `id`. [2](#0-1) 
- It then does `session[:user_id] = sign_in_github(auth)` and `session[:authenticated] = true` on the *same* session object that existed before authentication — it never calls `reset_session`. [3](#0-2) 
- By contrast, `#logout` does correctly call `reset_session` when tearing down a session, showing the pattern is known but not applied at the point of privilege elevation. [4](#0-3) 
- `current_user` is derived purely from `session[:user_id]` for every subsequent request, so whoever holds the session cookie is treated as that authenticated `User`. [5](#0-4) 

Because the session ID is not rotated at the authentication boundary, any actor who can get a victim's browser to reuse an attacker-known session ID (a classic session-fixation precondition — e.g. an attacker-controlled sibling subdomain sharing the cookie domain, or any mechanism that plants/reuses a session cookie in the victim's browser) can pre-establish a session, have the victim complete the real GitHub OAuth flow on that fixed session, and then use the same known session ID to inherit the victim's now-authenticated `Shipit::User` session — without ever knowing the victim's GitHub credentials.

### Impact Explanation
This matches the "session fixation / forced OAuth completion" High-impact category explicitly listed in scope: an attacker who successfully fixates a session and gets the victim to complete OAuth ends up with an authenticated session bound to the victim's `Shipit::User` identity, granting them the victim's authorization level (including any Shipit team-based authorization checked via `current_user.authorized?`). [6](#0-5) 

### Likelihood Explanation
Exploitation requires the attacker to have some means of fixing the session cookie value in the victim's browser before the victim completes OAuth (e.g., shared cookie domain/subdomain, or another mechanism to plant a cookie), plus getting the victim to click through the login flow. This is a standard, well-understood attack pattern (CWE-384) and does not require compromising GitHub, the webhook secret, or any Shipit credential — the only missing control is `reset_session` at the authentication callback.

### Recommendation
Call `reset_session` (or otherwise regenerate the session ID, e.g. via `request.session_options[:renew] = true` / `session.clear` before writing new keys) in `GithubAuthenticationController#callback` immediately before establishing the authenticated session (`session[:user_id]`, `session[:authenticated]`), mirroring the existing pattern already used in `#logout`.

### Proof of Concept
1. Attacker obtains/plants a known session identifier in the victim's browser cookie jar for the Shipit host (precondition: shared cookie domain/subdomain or other cookie-planting primitive).
2. Victim visits Shipit, is redirected to `/github/auth/github`, and completes the GitHub OAuth authorization dialog legitimately.
3. GitHub redirects back to `GithubAuthenticationController#callback`; the controller sets `session[:user_id] = victim_user.id` on the *same, attacker-known* session rather than issuing a new session ID. [3](#0-2) 
4. Attacker sends a request to Shipit using the same known session cookie and is now treated as `current_user == victim_user` by `Authentication#current_user`. [5](#0-4)

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```
