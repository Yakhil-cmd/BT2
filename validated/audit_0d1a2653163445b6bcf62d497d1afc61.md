## Title
Asset Definer Can Instantly Freeze Attested-Asset Holders by Updating the Attestor List - (File: `validation.js`)

## Summary
For any asset created with `spender_attested: true`, the asset definer can send an `asset_attestors` message at any time to replace the list of trusted attestors. This change takes effect immediately for **every existing holder** of the asset. A user (or an AA) who legitimately received and holds an attested-asset output — and was attested by an attestor that is subsequently removed from the list — becomes unable to spend that output, even though the funds were valid and spendable at the time they were received. This is the same bug class as the reported `perpetual::set_maintenance_margin_required()` issue: a privileged party unilaterally changes a global condition that retroactively converts previously-safe positions/holdings into unusable/liquidatable ones, with no grace period, timelock, or grandfathering for existing balances.

## Finding Description
When an asset is defined with `spender_attested = true`, spending/receiving it requires that the owner address currently appear in the asset's attestor-derived `arrAttestedAddresses` list, computed by `storage.filterAttestedAddresses()`: [1](#0-0) 

This list is filtered using `objAsset.arrAttestorAddresses`, which is always the **latest** attestor list for the asset, resolved in `storage.readAsset()`/`addAttestorsIfNecessary()` by picking the most recent `asset_attestors` unit: [2](#0-1) 

The attestor list can be changed at any time by the asset definer via `validateAttestorListUpdate()`, with no restriction other than authorship by the definer: [3](#0-2) 

Both spending (input) and receiving (output) checks reference this current, mutable attestor-derived list, not the list that was in effect when the output was created: [4](#0-3) [5](#0-4) 

Consequently, an output that was perfectly valid and spendable when received becomes permanently unspendable the moment the definer swaps out the attestor whose attestation qualified the owner — exactly analogous to the reported MMR issue where a global risk parameter change retroactively turns a previously-safe position into a liquidatable one, with immediate effect and no opportunity for the affected party to react.

## Impact Explanation
Any holder (user address or an AA) of a `spender_attested` asset can have their existing, previously valid balance instantly frozen by a unilateral, single-message action of the asset definer (`asset_attestors`), with no timelock, no grandfathering of already-attested holders, and no on-chain announcement delay. This is a concrete, immediate freezing of already-issued funds triggered purely by a definer-side configuration change — not by any action, mistake, or market movement of the holder. If the asset is held by an AA (e.g., a DEX, escrow, or vault AA that accepts an attested asset as collateral or trading pair), the AA's funds in that asset become frozen, blocking the AA's normal operation for all its users, not just one.

## Likelihood Explanation
Reachable by an unprivileged actor in the role explicitly permitted by the rules: the **asset issuer**. The issuer only needs to post a single, ordinary `asset_attestors` unit (`validateAttestorListUpdate`, `validation.js:2829`) referencing an asset they defined — no witness collusion, no hub/peer compromise, no timelock bypass. Any asset with `spender_attested: true` deployed today is subject to this at the sole discretion of its definer, and nothing in validation prevents a definer from removing an attestor that currently backs a large share of outstanding balances.

## Recommendation
Do not apply attestor-list changes retroactively to already-attested holders/outputs:
- Grandfather addresses that were attested under a previous attestor list at least until they get a chance to move funds, or
- Only apply new attestor lists to attestations created after the update (checking the union of historical attestor lists rather than only the latest one in `readAsset()`/`filterAttestedAddresses()`), or
- Introduce a delay/timelock (measured in MCI) before a new `asset_attestors` list takes effect for spend/receive validation, giving holders time to move funds attested under the old list.

## Proof of Concept
1. Definer `D` creates asset `X` with `spender_attested: true` and initial `attestors = [A]`.
2. Attestor `A` posts an `attestation` for user address `U`.
3. `U` receives a payment in asset `X` (valid: `filterAttestedAddresses` finds `U` attested by `A`, per `storage.js:1959-1974`).
4. `D` posts `asset_attestors` for asset `X` with `attestors = [B]` (removing `A`) — accepted per `validateAttestorListUpdate`, `validation.js:2829-2848`, since `D` is the definer and the new list passes `checkAttestorList`.
5. `readAsset()`/`addAttestorsIfNecessary()` (`storage.js:1917-1946`) now resolves `arrAttestorAddresses = [B]` for asset `X`.
6. `U` attempts to spend the previously received output. `filterAttestedAddresses` no longer returns `U` (attested only by removed `A`), so `validatePaymentInputsAndOutputs` rejects the spend with `"owner address is not attested"` (`validation.js:2506-2507`), even though the funds were validly received and unchanged.
7. `U`'s balance in asset `X` is now permanently frozen unless/until `D` chooses to re-add `A` (entirely at `D`'s discretion).

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
