### Title
Broken Access Control in Multisig "sign" Request Handler Leaks Private Payment Data to Non-Cosigner Correspondents - (File: wallet.js)

### Summary
The `"sign"` device-message handler in `wallet.js` builds a signing request for any local wallet address without verifying that the sender (`from_address`) is actually a registered cosigner of that address/wallet. The check that would enforce this is explicitly commented out, allowing any paired correspondent to trigger disclosure of private payment details for wallets/addresses it does not co-own.

### Finding Description
In the `"sign"` case of `handleMessageFromHub` (`wallet.js:251-404`), when `findAddress` resolves the requested `body.address`/`body.signing_path` to a **local** address (`ifLocal` callback, `wallet.js:334-372`), the code immediately proceeds to process the request and emit a `"signing_request"` event carrying `assocPrivatePayloads` (decrypted private payment outputs/inputs, including addresses, blinding factors, and amounts, see `wallet.js:278-314`) to the wallet UI — without ever validating that `from_address` (the sender) is actually one of the cosigners registered for that wallet.

The intended check is present in the code but disabled:
```

//    if (sender_rows.length !== 1)
//        return callbacks.ifError("sender is not cosigner of this address");
``` [1](#0-0) 

`findAddress` (`wallet.js:1233-1259`) itself performs no sender-authorization check either — it only resolves which local wallet a given address/signing_path belongs to: [2](#0-1) 

Because any device that has merely paired as a correspondent (not necessarily a cosigner of any shared wallet) can send a `"sign"` message referencing an address it does not co-sign, and because the `address`/`signing_path` values are attacker-supplied and only checked for format validity (`wallet.js:253-256`), an attacker who has paired with the victim (or is any correspondent, including one added for an unrelated purpose) can:
1. Guess or learn a victim's wallet address and a plausible signing path (paths are low-entropy, e.g. `r`, `r.0`, `r.1`, discoverable from public unit structure).
2. Send a crafted `"sign"` request for that `address`/`signing_path` together with an `unsigned_unit` containing `payload_location: "none"` payment messages and matching `private_payloads`.
3. The victim's wallet, upon reaching `ifLocal`, immediately calls `callbacks.ifOk()` and fires `signing_request`, surfacing the (attacker's own, but potentially also correlated) private payload data and prompting the victim UI, or in the `signed_message` branch bypasses the confirmation entirely and directly returns/validates.

More critically, the same missing-cosigner check means an attacker device that is a correspondent of the victim (e.g., a previously removed or otherwise weakly-trusted contact, or an indirect correspondent) can submit sign requests for shared/multisig addresses that legitimately belong to *other* devices' wallets, causing the local device to treat itself as a party to signing flows and reveal wallet/account/address-index (`objAddress` in `ifLocal`) and payment details it has no business relationship with. This is directly analogous to the OpenEMR issue: the server resolves and exposes a resource (address/wallet signing context and private payment payload) tied to another authorized user without validating that the requester is actually permitted to act on/view it.

### Impact Explanation
This breaks confidentiality guarantees of the private-payment / multisig-wallet subsystem: an unprivileged correspondent can cause disclosure of private payment payloads (addresses, amounts, blinding factors) and wallet/cosigner structural information (wallet id, account, address_index) belonging to addresses it is not authorized to sign for, and can trigger spurious signing-confirmation prompts on victim devices, potentially leading a user to sign/approve something they shouldn't (fund loss risk) if combined with social engineering, since the disabled check was specifically there to gate "who is allowed to request a signature for this address."

### Likelihood Explanation
Any paired correspondent device can send arbitrary `"sign"` messages; no cosigner relationship needs to be established beforehand, and the vulnerable code path is reached as soon as `findAddress` resolves to a locally-known address, which requires no additional secret beyond the address and its signing path (both often derivable/guessable in shared-address/multisig contexts). The removed check's absence is explicit and intentional-looking in the code (commented out with a rationale note), making this a straightforward, high-likelihood trigger for any correspondent, not just genuine cosigners.

### Recommendation
Re-enable (or otherwise reinstate a functionally-equivalent) authorization check in the `ifLocal` branch of the `"sign"` handler that verifies `from_address` is a legitimate cosigner/party for `body.address` (e.g., checking `extended_pubkeys`/`wallet_signing_paths` for wallet addresses, and `shared_address_signing_paths` for shared addresses) before emitting `signing_request` or processing `assocPrivatePayloads`, while still allowing legitimate multilateral-signing/contract use cases (e.g., by checking cosigner-or-contract-counterparty status rather than wallet-cosigner-only).

### Proof of Concept
1. Pair device B with victim device A as an ordinary correspondent (no shared wallet).
2. From B, learn/guess one of A's wallet addresses `ADDR` and a signing path such as `r` (single-sig) or `r.0`/`r.1` (common multisig paths).
3. B sends A a device message:
```json
{
  "subject": "sign",
  "body": {
    "address": "ADDR",
    "signing_path": "r",
    "unsigned_unit": { "version": "...", "authors": [{"address": "ADDR", "authentifiers": {"r": "sig"}}], "messages": [ ... payment message with payload_location: "none", payload_hash matching a crafted private_payloads entry ... ] },
    "private_payloads": { "<hash>": { "inputs": [...], "outputs": [{"address": "...", "blinding": "...", "amount": 1} ...] } }
  }
}
```
4. On A, `handleMessageFromHub` → `case "sign"` → `findAddress(ADDR, "r", ...)` resolves `ifLocal` (since `ADDR` is A's own wallet address) and, since the cosigner check is commented out, immediately calls `callbacks.ifOk()` and emits `"signing_request"` with the private payload contents and wallet/account metadata, regardless of whether B is actually a cosigner of `ADDR`.
