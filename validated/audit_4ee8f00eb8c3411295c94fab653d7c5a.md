### Title
Webhook signature authenticates `repository.owner.login`, but `EditedHandler` mutates the repository named by the independent, unverified `repository.full_name` field, letting a payload signed by one org write to another org's `PullRequest` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to validate the HMAC using `repository_owner`, i.e. `params.dig('repository','owner','login')`. `PullRequest::EditedHandler` never consults `repository_owner`; instead it independently derives the target repository from `params.repository.full_name` and updates that repository's `PullRequest` row. The two fields are never checked for equality, so a signature computed against one org's secret can be replayed with a payload whose `repository.full_name` names a different org's repo.

### Finding Description
The binding the code implicitly assumes is:
`repository_owner (used to select webhook_secret) == owner_segment(params.repository.full_name) (used to select the row to mutate)`

This equality is never asserted anywhere in the request path.

- `verify_signature` picks the app config via `Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(sig, raw_post)` [1](#0-0) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the configured org has no `webhook_secret` set: `return true unless webhook_secret` [2](#0-1) .
- `EditedHandler` builds its own `repository` from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`, completely independent of `repository_owner`, and then finds and updates the matching `PullRequest`: `pull_request.update(github_pull_request: params.pull_request) if pull_request.present?` [3](#0-2) .
- The `ExplicitParameters` schema for this handler only requires `repository.full_name` — it never requires or cross-checks `repository.owner.login` [4](#0-3) .

Exploit flow: an attacker who controls (or is onboarded as) an org in Shipit knows that org's own `webhook_secret` (they configured the webhook using it) or targets an org configured with no `webhook_secret` at all. They POST to `/webhooks` with `X-Github-Event: pull_request`, a valid (or trivially satisfied, if secret is nil) signature for `repository.owner.login = attacker-org`, but `repository.full_name = "victim-org/victim-repo"` and `number` matching a real victim PR. `verify_signature` authenticates against `attacker-org`'s config and passes. `EditedHandler` then resolves `repository` from `victim-org/victim-repo` and updates that PR's `github_pull_request` JSON (title, labels, assignees, state, head sha) — a write to a repository/org that never authenticated this specific payload.

No other guard intervenes: `drop_unhandled_event` only checks the event is registered, `check_if_ping` is irrelevant, and there's no `force_github_authentication`/`current_user` check on this unauthenticated webhook endpoint by design (webhooks are meant to authenticate solely via signature) — but that signature check does not bind to the payload's actual target repository.

### Impact Explanation
The attacker causes a persistent mutation of another organization's `PullRequest` record's stored GitHub metadata (title, state, labels, assignees, head SHA) — a payload for one repository mutating another's stack/PR data, satisfying the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any PR number in any repository tracked by Shipit and is not limited to a single victim; blast radius spans every tenant/org configured on the same Shipit instance, since the divergence exists regardless of which org is used to authenticate.

### Likelihood Explanation
Preconditions: the attacker needs a valid HMAC for *some* org configured in the Shipit instance — either (a) an org with `webhook_secret` unset/nil (trivial, since `verify_webhook_signature` returns `true` unconditionally in that case), or (b) any org for which the attacker legitimately knows the webhook secret (e.g., their own onboarded org in a multi-tenant Shipit deployment, which is a normal, unprivileged position per the threat model). Given either condition, forging the cross-org payload requires no Shipit session, API token, or GitHub secret beyond the signing key for their own/an unsecured org. This is highly feasible and fully repeatable.

### Recommendation
In `verify_signature`, extract the target repository's owner from `params.repository.full_name` (not just `repository.owner.login`) and require it to equal `repository_owner` before proceeding; alternatively, have each handler validate that the repository it resolves from `params.repository.full_name` belongs to the same owner used to select the `GitHubApp`/secret in `verify_signature`, rejecting the webhook (422) on mismatch. Additionally, do not treat a missing `webhook_secret` as automatic success — require an explicitly-configured secret per org, or bind the signature check to the exact repository being mutated.

### Proof of Concept
1. Configure two orgs in `Shipit.github_apps`/secrets: `attacker-org` with `webhook_secret: nil` (or a known secret used to sign the request), and `victim-org` with a *different* configured `webhook_secret` and an existing `Shipit::Repository`/`Stack`/`PullRequest` (number `42`).
2. POST to `/webhooks` with header `X-Github-Event: pull_request`, body:
   ```json
   {
     "action": "edited",
     "number": 42,
     "pull_request": { ...valid pull_request fields with a new "title": "PWNED"... },
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sender": { "login": "attacker" }
   }
   ```
   with `X-Hub-Signature` omitted/invalid (works because `attacker-org` has no secret) or correctly HMAC-signed with `attacker-org`'s secret.
3. Assert response is `200 OK` (not `422`).
4. Assert `Shipit::PullRequest.find_by(number: 42, ...).title` (or `github_pull_request['title']`) in `victim-org/victim-repo`'s stack now equals `"PWNED"`, proving a payload authenticated under `attacker-org`'s signature mutated `victim-org`'s row.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
