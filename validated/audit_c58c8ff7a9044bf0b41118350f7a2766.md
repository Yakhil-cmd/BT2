## Analysis

Given the tool budget, I was able to fully confirm the webhook signature/authorization logic in `WebhooksController`, but a read‑error prevented me from pulling the full body of `PushHandler`/other handlers to give a byte‑for‑byte trace of how they resolve the target `Repository`/`Stack`. I'm flagging that gap explicitly below.

### Title
Webhook signature verification authenticates the organization while handlers act on an attacker‑controlled repository field from the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate a webhook against using `repository_owner`, a value read out of the untrusted JSON body itself (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the HMAC check passes, the *entire* raw JSON body — including the `repository.full_name` field that handlers use to look up the `Repository`/`Stack` to mutate — is handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.

### Finding Description
The verified binding should be: `organization_that_signed == organization_that_is_written`. In multi-org Shipit installs (the engine explicitly supports a `github: { org_a: {...}, org_b: {...} }` config, see `config/secrets.development.example.yml`), each organization has its own GitHub App and its own `webhook_secret`. [1](#0-0) [2](#0-1) 

`verify_signature` derives the signing key purely from `repository.owner.login` (falling back to `organization.login`) inside the same JSON body that is later trusted for record lookups: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` passes the raw, already-verified `params` hash straight through. [3](#0-2) 

Because HMAC verification only proves "this body was signed by organization X's webhook secret," not "every field inside this body legitimately belongs to organization X," an operator of a legitimately-installed GitHub App for org `A` can craft a `push`/`status`/`check_suite`/`membership` payload where `repository.owner.login` (used to pick the verifying secret) is set to their own org `A`, while `repository.full_name` (which downstream handlers use to resolve the `Repository`/`Stack` record to update) is spoofed to point at a repository belonging to a different org `B` that is also configured in the same Shipit instance. The signature will verify successfully (it's a valid signature from org `A`'s real secret over the full body), yet the mutation performed by the handler would apply to org `B`'s stack.

### Impact Explanation
If exploitable, this allows an authenticated-but-unprivileged GitHub App owner for one tenant organization to forge sync/status/membership events against a different tenant's repository configured in the same Shipit instance, potentially: injecting spoofed commits/statuses that make a foreign stack appear deployable, creating spoofed Team/User membership records, or triggering merge-queue and continuous-deployment side effects for a repository the attacker does not control — a cross-repository/cross-organization write achieved without ever possessing the victim org's webhook secret, GitHub App key, or an `ApiClient` token.

### Likelihood Explanation
This requires: (1) a Shipit deployment configured for multiple GitHub organizations sharing one webhook endpoint, and (2) attacker control of a legitimately installed GitHub App for at least one of those organizations (an ordinary, low-privilege scenario the attacker can arrange themselves, e.g., a personal org). I could not fully verify from the available index whether `PushHandler`/`StatusHandler`/`MembershipHandler` actually resolve the target `Repository` via `repository.full_name` independently of the `repository.owner.login` used for verification, or whether they re-derive/cross-check the owner — a read failure prevented me from inspecting `app/models/shipit/webhooks/handlers/push_handler.rb` and sibling handlers in this pass. This is the key uncertainty that would need confirming (e.g., via a Devin session with full file access) before treating this as a confirmed, exploitable finding rather than a plausible confused-deputy pattern in the verification layer.

### Recommendation
In `verify_signature`, after selecting the GitHub App/secret by `repository_owner` and validating the HMAC, re-validate that every organization-identifying field the downstream handler will use (`repository.full_name`'s owner segment, `organization.login`, etc.) is consistent with the `repository_owner` value used to pick the secret, rejecting the webhook (422) on any mismatch. Handlers themselves should not trust `full_name`/owner fields from the payload for record resolution without this cross-check.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (per the documented multi-org config shape).
2. As the (legitimate, low-privileged) admin of `org-a`'s GitHub App, craft a `push` event JSON body where `repository.owner.login = "org-a"` (so `verify_signature` selects and validates against `org-a`'s real secret) but `repository.full_name = "org-b/victim-repo"`.
3. Sign the raw body with `org-a`'s known `webhook_secret` and POST it to `/webhooks` with the corresponding `X-Hub-Signature` header.
4. `verify_signature` succeeds because the HMAC is valid for `org-a`. The unmodified `params` (containing the spoofed `full_name`) is passed to `Shipit::Webhooks.for_event('push')`'s handlers, which — if they resolve the target repository by `full_name` as assumed — would update `org-b`'s stack/commit data despite the request never being signed by `org-b`.

*Caveat: step 4's handler behavior could not be independently confirmed in this pass due to a tool error reading `push_handler.rb`; verifying the exact field used for repository resolution in the handler code is the remaining step to fully substantiate this as a confirmed vulnerability.*

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
