### Title
Fee-on-Transfer ERC20 Token Inflates Bridge Transfer Amount — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`BridgeTransferERC20.requestERC20Transfer` uses the caller-supplied `_value` directly in the `RequestValueTransfer` event without verifying the actual amount received by the bridge. If the registered ERC20 token charges an internal transfer fee, the bridge receives less than `_value`, but the counterpart bridge operator mints or unlocks the full `_value` on the other chain, draining the bridge's reserves or inflating the bridged token supply.

---

### Finding Description

`requestERC20Transfer` pulls `_value + _feeLimit` from the caller via `safeTransferFrom`, then immediately passes the caller-supplied `_value` to `_requestERC20Transfer`, which emits it verbatim in the `RequestValueTransfer` event: [1](#0-0) 

```solidity
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

Inside `_requestERC20Transfer`, `_value` is emitted without any balance check: [2](#0-1) 

The bridge operator on the counterpart chain reads `valueOrTokenId` from this event and calls `handleERC20Transfer` with that exact value: [3](#0-2) 

`handleERC20Transfer` then mints or transfers the full `_value` to the recipient: [4](#0-3) 

If the token deducts a fee during `transferFrom` (e.g., a USDT-style fee mechanism), the bridge receives `_value + _feeLimit - tokenFee` instead of `_value + _feeLimit`. The emitted event still carries `_value`, so the counterpart bridge mints/unlocks the full `_value` — more than was actually deposited.

---

### Impact Explanation

**Lock/Unlock mode (`modeMintBurn = false`):** The source bridge holds `_value - tokenFee` (net of the token's internal fee), but the counterpart bridge releases `_value`. Each transfer drains `tokenFee` from the counterpart bridge's reserves. Repeated transfers exhaust the counterpart bridge's liquidity, blocking legitimate withdrawals.

**Mint/Burn mode (`modeMintBurn = true`):** The source bridge burns `_value` tokens but only received `_value - tokenFee`. The counterpart bridge mints `_value`. This inflates the circulating supply of the bridged token by `tokenFee` per transfer, constituting unauthorized minting of bridged assets.

This matches the allowed impact gate: **unauthorized mint/unlock of bridged assets affecting system-managed funds**.

---

### Likelihood Explanation

Any ERC20 token registered with the bridge that has a fee-on-transfer mechanism triggers this. The trigger is a normal, unprivileged user call to `requestERC20Transfer`. No special role is required. The USDT contract already contains the fee mechanism (currently set to zero), and other fee-on-transfer tokens exist. The bridge has no whitelist enforcement preventing such tokens from being registered.

---

### Recommendation

Use a balance-before / balance-after pattern to determine the actual amount received, and use that as the bridged value:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    uint256 actualValue = actualReceived > _feeLimit ? actualReceived.sub(_feeLimit) : 0;
    require(actualValue > 0, "zero ERC20 token amount after fee");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualValue, _feeLimit, _extraData);
}
```

Alternatively, restrict bridge token registration to tokens that are verified to have no transfer fee.

---

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token `FeeToken` that deducts 1% on every `transferFrom`.
2. Register `FeeToken` with the bridge (lock/unlock mode).
3. Alice calls `requestERC20Transfer(feeToken, bob, 1000, 0, "0x")`.
4. Bridge receives `990` tokens (1% fee deducted by the token contract).
5. `RequestValueTransfer` event is emitted with `valueOrTokenId = 1000`.
6. Bridge operator reads the event and calls `handleERC20Transfer(..., 1000, ...)` on the counterpart bridge.
7. Counterpart bridge transfers `1000` tokens to Bob.
8. Net loss to the bridge system: `10` tokens per transfer.
9. After 100 such transfers, the counterpart bridge's reserves are fully drained by `1000` tokens while only `990 × 100 = 99000` were ever deposited. [5](#0-4) [4](#0-3) [6](#0-5)

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}
