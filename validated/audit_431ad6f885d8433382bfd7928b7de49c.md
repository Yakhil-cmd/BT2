### Title
Custom Task triggering bypasses the deploy/rollback environment-variable whitelist, letting an unprivileged task-triggering user override reserved runtime flags (e.g. `IGNORED_SAFETIES`) on the deploy host - (File: `app/models/shipit/stack.rb`)

### Summary
The reported bug class is "a value the system trusts because it went through one code path is instead used unchecked through a second path" (WETH deposit path skips the ETH-safe deposit path). The same class of "permitted set vs. actually spawned set" mismatch exists in Shipit for environment variables: Deploys and Rollbacks pass user-supplied `env` through an explicit whitelist (`DeploySpec#filter_deploy_envs` / `#filter_rollback_envs`), but generic Task triggering (`Stack#trigger_task`) merges the caller-supplied `env` hash directly into the task without ever checking it against the task definition's declared variables, and that unfiltered hash is later merged **last** (i.e. with highest priority) into the actual process environment used to spawn shell commands on the deploy host.

### Finding Description
For deploys/rollbacks, Shipit enforces an equality: `permitted keys (deploy_variables/rollback_variables from shipit.yml) == keys allowed into task.env`. This is implemented via `DeploySpec#filter_deploy_envs` / `#filter_rollback_envs`: [1](#0-0) 
and is enforced at the API boundary, rejecting non-whitelisted variables with a 422 (demonstrated by the existing test suite): [2](#0-1) 

However, `Stack#trigger_task`, the method used to create arbitrary custom Tasks (as opposed to deploys/rollbacks), never applies an equivalent permit/whitelist check. It only fills in *missing* keys with their declared defaults and otherwise merges the raw, caller-supplied `env` hash verbatim: [3](#0-2) 

That unfiltered `task.env` is subsequently merged as the **last** (highest-priority) step when building the actual OS-level environment for the spawned shell command: [4](#0-3) 

Because the merge order places `@task.env` after the system-reserved keys (`SHIPIT_USER`, `EMAIL`, `TASK_ID`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`), any key supplied in the caller's `env` payload silently overrides these reserved values in the process actually spawned by `Command`/`PTY.spawn`: [5](#0-4) 

This breaks the intended binding "environment key permitted (by `deploy_variables`/task definition variables) == environment key spawned (in the OS process env)" that is explicitly enforced for the deploy/rollback code paths but absent for the generic task-trigger path.

### Impact Explanation
An authenticated caller who is only authorized to trigger a specific custom Task (via `Stack#trigger_task`, reachable from `Api::TasksController`) can supply an `env` hash containing keys that were never declared by that Task's definition. Because that hash is merged last, it can override safety-relevant reserved variables such as `IGNORED_SAFETIES`, independent of the actual `Task#ignored_safeties?` flag/authorization that is supposed to gate that value, and it can inject arbitrary environment variables consumed by the shell commands the Task executes on the deploy host. Depending on what the deployed `shipit.yml` task steps do with their environment (a very common pattern, since `machine.environment` and custom `deploy.variables` are explicitly designed to be interpolated into shell commands per `Command#interpolate_environment_variables`), this can escalate to executing unintended commands or bypassing safety checks on the deploy host — i.e., an unauthorized deploy-host action performed with elevated effect relative to what the caller's task-trigger privilege was meant to allow.

### Likelihood Explanation
Medium: it requires the caller to already have permission to trigger *some* Task on the stack (an authenticated Shipit user with task-trigger rights, not necessarily deploy/rollback rights), which is a materially different privilege boundary than deploy/rollback triggering. Given that Shipit deliberately whitelists env for deploy/rollback but not for generic tasks, this looks like an oversight rather than a defense-in-depth omission, making exploitation straightforward for any user who can already call the task-trigger endpoint.

### Recommendation
Apply the same whitelist enforcement used for deploys/rollbacks to `Stack#trigger_task`: filter the caller-supplied `env` through the Task definition's declared `variables` (analogous to `filter_deploy_envs`/`filter_rollback_envs`) before persisting/merging it into `task.env`, and reject requests containing keys outside that whitelist. Additionally, do not let user-supplied env silently shadow reserved/system keys (`IGNORED_SAFETIES`, `GIT_COMMITTER_*`, `SHIPIT_USER`, `TASK_ID`) — merge those after, not before, arbitrary task env.

### Proof of Concept
1. As a user with permission to trigger a Task (but not IGNORED_SAFETIES override rights), call the task-trigger endpoint with `env: { "IGNORED_SAFETIES": "1", "ARBITRARY_VAR": "payload" }`, where `ARBITRARY_VAR`/`IGNORED_SAFETIES` are not declared in the task's `variables` in `shipit.yml`.
2. `Stack#trigger_task` (`app/models/shipit/stack.rb:139-150`) stores this hash verbatim as `task.env` with no whitelist check.
3. When the task executes, `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) merges `@task.env` last, so `IGNORED_SAFETIES=1` and `ARBITRARY_VAR=payload` end up in the actual spawned process environment (`lib/shipit/command.rb:92-105`), overriding the intended `IGNORED_SAFETIES` value and introducing an unvetted variable into the task's shell execution context — despite the caller never being whitelisted for either variable.

Note: I was not able to inspect the full contents of `app/controllers/shipit/api/tasks_controller.rb` before the iteration limit was reached, so I cannot rule out an additional filtering step at the controller layer that might mitigate this. The core gap — `Stack#trigger_task` lacking the `filter_deploy_envs`/`filter_rollback_envs`-style whitelist that deploys/rollbacks explicitly have — is confirmed directly in the model code cited above.
