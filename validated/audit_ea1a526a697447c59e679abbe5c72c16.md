## Vulnerability Analog Found

### Title
Stack-Scoped API Tokens Can Read Any Stack via CCMenu Endpoint's Unscoped Lookup - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method to resolve stacks directly from the URL parameter instead of using the stack-scoped collection enforced everywhere else in the API, breaking the binding between "the stack a token authorizes" and "the stack a request actually touches."

### Finding Description
Every other API controller resolves the target stack through `Shipit::Api::BaseController#stack`, which restricts the lookup to the caller's authorized stacks: [1](#0-0) 

`current_api_client.stack_id?` is true whenever an `ApiClient` was created scoped to one particular stack (e.g. the `here_come_the_walrus` fixture, or any client created via `ApiClient.create_with(stack: some_stack)`), and in that case `stacks` is deliberately narrowed to `Stack.where(id: current_api_client.stack_id)`, so `from_param!` will raise/404 for any other stack.

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 

It resolves the stack directly with `Stack.from_param!(params[:stack_id])`, with no reference to `current_api_client.stack_id`. The controller still calls `require_permission :read, :stack`, but that check only tests whether the token carries the `read:stack` permission string, not whether the token is scoped to *this* stack: [3](#0-2) 

This mirrors the reported bug class exactly: one code path (`userDeposit`/generic `BaseController#stack`) enforces an accounting/scoping invariant, while a second code path (`processWithdrawDeposit`/`CCMenuController#stack`) mutates state (here, the effective authorization scope) without going through the same check, producing a `client.stack_id == authorized stack` vs `stack_id param == stack actually read` mismatch.

Compounding this, `CCMenuUrlController#client` (used to mint these tokens for end-users) does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — note it never sets `stack:`, so any token minted this way is **already globally scoped** (`stack_id` nil) even before considering the controller bug: [4](#0-3) 

So there are two independent ways the "stack a token authorizes" vs "stack a token touches" binding is broken:
1. Tokens minted via `CCMenuUrlController` for "stack A's CCMenu badge" are not actually scoped to stack A at the model level (`stack_id` is nil), so they already work against `Stack.all` through the generic `BaseController#stack`.
2. Even a deliberately stack-scoped `ApiClient` (created directly with a `stack_id`, e.g. via the `/api/clients` management UI/API) can still read any other stack's status through `CCMenuController`, because that controller never consults `current_api_client.stack_id`.

### Impact Explanation
Any bearer of a `read:stack`-permissioned token — including a token that an operator intentionally scoped to a single, low-sensitivity stack, or a CCMenu badge URL meant only to expose one stack's build status — can enumerate `stack_id` values and read the deploy/status XML for *every* stack in the Shipit instance via `GET /api/:stack_id/ccmenu.xml?token=...`. This is an unauthorized/unintended read of stack state for stacks the token holder was never granted access to, satisfying the "unauthenticated read of stack state" high-impact criterion (the attacker needs only the narrowly-scoped token, not any credential valid for the target stack).

### Likelihood Explanation
CCMenu tokens are explicitly designed to be embedded in external CI-monitoring tools/URLs and are lower-trust by design (self-service, non-expiring, created without any additional authorization check beyond an existing login session). Any holder of such a URL — or any legitimate stack-scoped `ApiClient` credential issued by an operator for a single project — can trivially pivot to reading all stacks by changing the `stack_id` path segment, requiring no privilege beyond possessing one valid, narrowly-scoped token.

### Recommendation
Make `CCMenuController#stack` reuse the scoped `stacks` collection from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so `current_api_client.stack_id` scoping is enforced consistently. Additionally, `CCMenuUrlController#client` should create/find the `ApiClient` scoped to the specific `stack` being requested (`stack:`) rather than a single global "CCMenu Client" shared across all stacks for a user.

### Proof of Concept
1. An operator creates (or a user self-service creates via the UI, `CCMenuUrlController#fetch`) a `read:stack`-scoped token intended only for `stack-a`'s CCMenu badge: `GET /stack-a/ccmenu_url` → returns `ccmenu_url` containing `token=T`.
2. An attacker (or the CI tool the badge URL was shared with) requests a different, unrelated stack's status using the same token: `GET /api/stack-b/ccmenu.xml?token=T`.
3. `CCMenuController#authenticate_api_client` authenticates `T` successfully (`ApiClient.authenticate` only validates the signature/id, not any stack binding).
4. `CCMenuController#stack` resolves `stack-b` via `Stack.from_param!(params[:stack_id])`, ignoring that the token (whether globally-scoped as minted today, or even if fixed to be stack-scoped to `stack-a` at the model level) has no relation to `stack-b`.
5. `require_permission :read, :stack` only checks that `T`'s permissions array includes `"read:stack"`, which it does, so the request succeeds and returns `stack-b`'s deploy/build status XML — a stack the token was never meant to expose.
