### Title
Silent CLStakingInfo Overwrite in `consolidateNodes()` Causes Incorrect CL Reward Distribution for Multi-Node Validators — (`kaiax/staking/staking_info.go`)

---

### Summary

When a validator registers multiple node IDs sharing the same reward address in AddressBook, and each node ID has a separate CL pool registered in CLRegistry, the `consolidateNodes()` function silently overwrites earlier `CLStakingInfo` entries with later ones. Only the last CL pool's staking amount is used for reward calculation, causing the validator's CL staking rewards to be undercounted and the remainder to flow to the proposer.

---

### Finding Description

The external bug's class is **"first/forced-index selection from a registry when multiple valid entries exist"** — the system picks one entry from a list without considering all of them, causing incorrect asset accounting.

The native analog lives in `consolidateNodes()` in `kaiax/staking/staking_info.go`. The function builds a map from reward address → `consolidatedNode`. It then iterates over `CLStakingInfos` and assigns each entry to its reward address via `nToR`:

```go
// kaiax/staking/staking_info.go lines 151-159
if len(si.CLStakingInfos) > 0 {
    for _, clsi := range si.CLStakingInfos {
        if r, ok := nToR[clsi.CLNodeId]; ok {
            // One CLStakingInfo per validator is guaranteed by CLRegistry.
            cmap[r].CLStakingInfo = clsi   // ← unconditional overwrite
        }
    }
}
``` [1](#0-0) 

The assignment `cmap[r].CLStakingInfo = clsi` is unconditional. When two node IDs (`n1`, `n3`) share the same reward address `r1`, and both have separate CL pools registered in CLRegistry, the second iteration silently overwrites the first. The test case **"4 nodes consolidated to 2 nodes and one node has two CLs"** in `staking_info_test.go` confirms this exact behavior — only `n3`'s CL entry survives:

```go
// kaiax/staking/staking_info_test.go lines 243-271
// CL1 will be ignored when being consolidated since it has duplicate CL (not feasible in real)
expectedConsolidated: []consolidatedNode{
    {[]common.Address{n1, n3}, ..., r1, a1+a3, &CLStakingInfo{n3, clPool2, clStakingAmount2}},
``` [2](#0-1) 

The developer comment "not feasible in real" is an assumption, not a code-enforced invariant. The CLRegistry guarantees **one CL per node ID**, but multiple node IDs can legitimately share the same reward address (this is the explicit purpose of the `consolidatedNode` design). [3](#0-2) 

The corrupted value then propagates into `Split()`, which uses `c.CLStakingInfo.CLStakingAmount` to divide the proposer reward between the CN staking contract and the CL pool:

```go
// kaiax/staking/staking_info.go lines 169-187
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
    totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)
    cnAmount := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
``` [4](#0-3) 

`Split()` is called in `specWithProposerAndFundsFlex()` and `specWithProposerAndFunds()` in `kaiax/reward/impl/getter.go` to distribute the proposer's block reward: [5](#0-4) 

With only one CL pool's amount instead of the sum of all CL pools for the consolidated node, the split ratio is wrong. The CL pool receives less than it should, and the remainder stays with the CN reward address (proposer).

---

### Impact Explanation

The exact corrupted value is `cn.CLStakingInfo.CLStakingAmount` inside the `consolidatedNode` struct — it holds only the last CL pool's staking amount instead of the aggregate of all CL pools belonging to node IDs that share the same reward address. This causes:

- The validator's CL pool(s) to receive less KAIA block reward than their staking proportion entitles them to.
- The underpaid amount flows to the CN reward address (proposer) instead of the CL pool.

This is an incorrect redistribution of KAIA block rewards — a protected-state asset impact.

---

### Likelihood Explanation

The scenario requires a validator to:

1. Register multiple node IDs (`n1`, `n3`) with the **same reward address** in AddressBook — this is a supported, documented feature (the entire `consolidatedNode` mechanism exists for this).
2. Register separate CL pools for each of those node IDs in CLRegistry — each node ID is independently eligible for a CL pool.

Neither step requires special privileges or majority-validator collusion. The CLRegistry guarantees one CL per **node ID**, not one CL per **reward address**. The developer comment "not feasible in real" is an unverified assumption that is not enforced anywhere in the Go code.

---

### Recommendation

In `consolidateNodes()`, instead of unconditionally overwriting `CLStakingInfo`, accumulate the CL staking amounts when multiple CL entries map to the same reward address:

```go
if r, ok := nToR[clsi.CLNodeId]; ok {
    if existing := cmap[r].CLStakingInfo; existing != nil {
        // Accumulate: multiple node IDs sharing a reward address may each have a CL pool.
        existing.CLStakingAmount += clsi.CLStakingAmount
    } else {
        cmap[r].CLStakingInfo = clsi
    }
}
```

Alternatively, the `consolidatedNode` struct should hold a slice of `CLStakingInfo` entries and `Split()` should sum them before computing the ratio.

---

### Proof of Concept

1. Validator registers `n1` and `n3` with reward address `r1` in AddressBook; staking amounts 10 M and 5 M KAIA.
2. Validator registers CL pool `P1` for `n1` (CL amount: 8 M KAIA) and CL pool `P2` for `n3` (CL amount: 3 M KAIA) in CLRegistry.
3. CLRegistry returns `CLStakingInfos = [{n1, P1, 8M}, {n3, P2, 3M}]`.
4. `consolidateNodes()` processes them:
   - Iteration 1: `cmap[r1].CLStakingInfo = {n1, P1, 8M}`
   - Iteration 2: `cmap[r1].CLStakingInfo = {n3, P2, 3M}` ← **overwrites**
5. `Split()` is called with `CLStakingAmount = 3M` instead of `11M`.
   - Correct CL fraction: `11M / (15M + 11M) ≈ 42%`
   - Actual CL fraction: `3M / (15M + 3M) ≈ 17%`
6. For a 6.4 KAIA block reward allocated to this validator, the CL pools receive ~1.1 KAIA instead of ~2.7 KAIA. The difference (~1.6 KAIA per block) accumulates to the CN reward address instead of the CL pools. [6](#0-5) [7](#0-6)

func (si *StakingInfo) consolidateNodes() *[]consolidatedNode {
	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))
	nToR := make(map[common.Address]common.Address)

	for i, n := range si.NodeIds {
		r := si.RewardAddrs[i]
		// Unique nodeId is guaranteed by AddressBook.
		nToR[n] = r
		if cn, ok := cmap[r]; ok {
			cn.NodeIds = append(cn.NodeIds, n)
			cn.StakingContracts = append(cn.StakingContracts, si.StakingContracts[i])
			cn.StakingAmount += si.StakingAmounts[i]
		} else {
			cmap[r] = &consolidatedNode{
				NodeIds:          []common.Address{n},
				StakingContracts: []common.Address{si.StakingContracts[i]},
				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}

	// CLStakingInfo can only exist after Prague HF.
	if len(si.CLStakingInfos) > 0 {
		for _, clsi := range si.CLStakingInfos {
			// If the nodeId of CLStakingInfo is not found in nToR, it means the validator is not in the AddressBook.
			// So we skip it.
			if r, ok := nToR[clsi.CLNodeId]; ok {
				// One CLStakingInfo per validator is guaranteed by CLRegistry.
				cmap[r].CLStakingInfo = clsi
			}
		}
	}

	carr := make([]consolidatedNode, 0, len(cmap))
	for _, r := range rList {
		carr = append(carr, *cmap[r])
	}
	return &carr
}

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

// specWithProposerAndFundsFlex assigns proposer, kif, kef, kpf to the reward spec.
// This must be the last step of building the RewardSpec as it finalizes the Proposer, KEF, KIF fields.
func specWithProposerAndFundsFlex(spec *reward.RewardSpec, config *reward.RewardConfig, proposer, kif, kef, kpf *big.Int, si *staking.StakingInfo) *reward.RewardSpec {
	newSpec := spec.Copy()

	// If KIF, KEF, or KPF address is not set, proposer takes it.
	if common.EmptyAddress(si.KIFAddr) {
		newSpec.KIF = common.Big0
		proposer.Add(proposer, kif)
	} else {
		newSpec.KIF = kif
		newSpec.IncRecipient(si.KIFAddr, kif)
	}

	if common.EmptyAddress(si.KEFAddr) {
		newSpec.KEF = common.Big0
		proposer.Add(proposer, kef)
	} else {
		newSpec.KEF = kef
		newSpec.IncRecipient(si.KEFAddr, kef)
	}

	if common.EmptyAddress(si.KPFAddr) {
		newSpec.KPF = common.Big0
		proposer.Add(proposer, kpf)
	} else {
		newSpec.KPF = kpf
		newSpec.IncRecipient(si.KPFAddr, kpf)
	}

	newSpec.Proposer = proposer
	if !config.Rules.IsPrague || si.CLStakingInfos == nil {
		newSpec.IncRecipient(config.Rewardbase, proposer)
		return newSpec
	}

	// Handle CLStakingInfo for proposer after Prague
	cns := si.ConsolidatedNodes()
	for _, cn := range cns {
		if cn.RewardAddr != config.Rewardbase {
			continue
		}
		if cn.CLStakingInfo == nil {
			// Early exit if there's no CL for proposer
			break
		}

		cnAmount, clAmount := cn.Split(proposer)

		newSpec.IncRecipient(cn.RewardAddr, cnAmount)
		newSpec.IncRecipient(cn.CLStakingInfo.CLPoolAddr, clAmount)
		return newSpec
	}

	newSpec.IncRecipient(config.Rewardbase, proposer)
	return newSpec
}
