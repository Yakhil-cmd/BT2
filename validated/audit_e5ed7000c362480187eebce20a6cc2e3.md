### Title
Webhook payload fields used to select the HMAC verification org differ from those used to target the affected repository/stack, allowing cross-tenant webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting webhooks for multiple GitHub organizations from a single instance, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to validate the `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) directly out of the **unverified** raw JSON body [2](#0-1) [3](#0-2) . Downstream handlers, however, select the repository/stack that will actually be acted on using a *different* field of the same unverified body: `repository.full_name`, read by `Shipit::Webhooks::Handlers::Handler#repository_name` [4](#0-3) , or `organization.login` combined with `team.id`/`team.slug` in `MembershipHandler` [5](#0-4) .

This is the same bug class as the reported liquidity-manager overflow: two related quantities (`node.available` used to check availability, `node.pending` added on restore) are treated as coupled but are independently attacker-influenced, breaking an invariant that the code implicitly assumes holds. Here, the analogous invariant is: *"the organization whose secret authenticated this webhook" == "the organization/repository the handler will act on."* Because both values are sourced from the same attacker-authored JSON body but are never cross-checked against each other, an attacker who legitimately controls the webhook secret for **one** configured organization can supply a payload where the signing-org field points to their own org (so signature verification passes) while the acting-target field (`repository.full_name`, or `organization.login`/`team`) points at an entirely different, victim tenant's repository/team/stack hosted on the same Shipit instance.

### Finding Description
- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and uses it to fetch the corresponding `GitHubApp` (and thus `webhook_secret`) via `Shipit.github(organization: repository_owner)` [2](#0-1) . This lookup happens **before** the body has been authenticated — the attacker fully controls which org's secret is used to check the signature.
- `Shipit.github_app_config` resolves this organization key against `secrets.github`, confirming multi-tenant configuration is a first-class, supported deployment shape (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md#Using-Multiple-Github-Applications`) [6](#0-5) .
- Once the signature is confirmed as valid *for the org named in `repository.owner.login`*, `Shipit::Webhooks.for_event(event)` dispatches the same raw `params` hash to handlers [7](#0-6) .
- `PushHandler` and other handlers resolve the target repository purely from `repository.full_name` [4](#0-3) [8](#0-7) , a field that is completely independent of `repository.owner.login` used above — nothing forces `full_name`'s owner segment to match `owner.login`.
- `MembershipHandler` similarly trusts `organization.login` (used to attribute a newly created `Team#organization`) and `team.id`/`team.slug`, `member.login`, and directly calls `team.add_member(member)` / deletes membership based on `params.action` [5](#0-4) , with no re-validation tying `organization.login` back to the org whose secret validated the signature.

**Equality that should hold, but doesn't:**
`organization_that_authenticated(secret used in verify_signature)` **==** `organization/repository/team that the handler subsequently mutates`.

Before the attacker's request: for a legitimate webhook, GitHub itself guarantees `repository.owner.login` and `repository.full_name`'s owner segment are the same, because GitHub generates and signs the whole payload consistently for a single repo/org.

After the attacker's request: the attacker (who administers a Shipit-configured org, e.g. `OrgTwo`, and thus knows `OrgTwo`'s `webhook_secret`) crafts a raw JSON body where:
```
repository.owner.login = "OrgTwo"       # used only for signature-org lookup
repository.full_name   = "OrgOne/victim-repo"  # used by handlers to pick the actual stack
```
and signs the exact raw body with `OrgTwo`'s secret. `verify_signature` succeeds because it validates against `OrgTwo`'s secret over the exact bytes sent. The `PushHandler`/`StatusHandler`/`MembershipHandler` then act on `OrgOne`'s repository, team, or commit — a tenant the attacker has no legitimate relationship with — using the trust conferred by having merely proven control of a *different* org's secret.

### Impact Explanation
This breaks the cross-tenant isolation Shipit's multi-org webhook feature is meant to provide. Concretely reachable, unprivileged-attacker outcomes on a multi-org Shipit deployment:
- **Forged `status` events** for arbitrary commits/repos not owned by the attacker's org, which can be used to falsely mark required CI checks as `success` on a victim's commit, defeating `ci.require` gating and enabling continuous delivery to deploy that commit — an unauthorized deploy.
- **Forged `membership` events**, letting the attacker create/populate `Team` records and add/remove arbitrary users to/from teams keyed by `organization.login`, which can influence `Shipit.github_teams` authorization checks (`User#authorized?`) if that organization's team is used for access control.
- **Forged `push` events** targeting a victim repository's stacks, triggering `GithubSyncJob`/`sync_github` against a repo the attacker has no legitimate access to.

This satisfies the required High/Critical bar (escalation into `Shipit.github_teams` authorization, or an unauthorized deploy) because the attacker crosses a tenant/organization boundary using only their own legitimately-provisioned webhook secret — no `ApiClient` token, session, or GitHub App private key theft is required.

### Likelihood Explanation
Requires a Shipit deployment configured for multiple GitHub organizations (explicitly documented and supported, `docs/setup.md`), and the attacker must be an admin/maintainer of at least one of those configured organizations (able to view that org's own Shipit GitHub App webhook secret) — a low bar relative to compromising the victim org. The webhook endpoint (`/webhooks`) is unauthenticated by design (`skip_before_action :verify_authenticity_token`), reachable by anyone able to send an HTTP POST with a forged `X-Hub-Signature`, once the correct secret is known.

### Recommendation
After `verify_signature` succeeds, re-derive the "authenticated organization" and enforce that every organization-identifying field used by the dispatched handler (`repository.full_name`'s owner segment, `organization.login`, `team` ownership) matches the organization resolved during signature verification, rejecting the webhook (HTTP 422) on mismatch. Alternatively, key `verify_signature`'s org lookup and the handler's target-resolution logic off the identical single field, so there is no independent, attacker-controllable pair of values.

### Proof of Concept
Not independently executable from static review — this requires a running multi-org Shipit instance plus knowledge of one configured org's `webhook_secret` (Cantina-report equivalent: no exploit was executed against this codebase; this write-up maps the invariant break to exact code locations per the confirmed control flow in `app/controllers/shipit/webhooks_controller.rb` and `app/models/shipit/webhooks/handlers/handler.rb`/`membership_handler.rb`). Conceptual request:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(raw_body, OrgTwo_webhook_secret)>
Body:
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "full_name": "OrgOne/victim-repo",
    "owner": { "login": "OrgTwo" }
  }
}
```
`verify_signature` resolves `repository_owner = "OrgTwo"`, validates against `OrgTwo`'s known secret, passes; `PushHandler` then acts on `OrgOne/victim-repo`'s stacks using `repository.full_name`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
