### Title
Pre-permissionless `verifySeals` accepts blocks with 1 committed seal for N≤3 validators due to `F(N,N)=0` — (`blockchain/block_validator.go`)

### Summary

In the pre-permissionless branch of `verifySeals`, the quorum threshold is computed as `2*sealer.F(blockNum, qualifiedLen, committeeSize)+1`. For any network with N≤3 qualified validators and committeeSize=N, `F` returns 0, making the threshold 1. This contradicts the live consensus engine (`calcQuorumSize`), which requires all N validators to commit when N<4. A single malicious council member can craft a block with only their own committed seal and have it accepted by any syncing node.

### Finding Description

`IstanbulSealer.F` is defined as:

```go
func (m *IstanbulSealer) F(_ uint64, qualifiedLen, committeeSize int) int {
    if qualifiedLen > int(committeeSize) {
        return int(math.Ceil(float64(committeeSize)/3)) - 1
    }
    return int(math.Ceil(float64(qualifiedLen)/3)) - 1
}
``` [1](#0-0) 

For `qualifiedLen=3, committeeSize=3`: `ceil(3/3) - 1 = 1 - 1 = 0`. So `2*F+1 = 1`.

The pre-permissionless branch of `verifySeals` uses this directly:

```go
if validSeal < 2*v.sealer.F(blockNum, qualifiedLen, committeeSize)+1 {
    return istanbul.ErrInvalidCommittedSeals
}
``` [2](#0-1) 

The live consensus engine uses `calcQuorumSize`, which explicitly returns N (everyone) for N<4:

```go
func calcQuorumSize(qualifiedLen int, committeeSize uint64) int {
    size := min(qualifiedLen, int(committeeSize))
    if size < 4 {
        return size  // quorum = 3 for N=3
    }
    ...
}
``` [3](#0-2) 

`IstanbulSealer.Quorum` also returns N for N<4 (matching `calcQuorumSize`), but the pre-permissionless path deliberately bypasses `Quorum` and uses `2*F+1` instead, as noted in the comment at line 312–313. The bug is that `2*F+1` and `Quorum` are inconsistent for N<4: `Quorum(3,3)=3` but `2*F(3,3)+1=1`. [4](#0-3) 

The pre-permissionless path only checks that the author is in the qualified set (line 290) and that committed seals come from the council (line 300–302). It does **not** check that the author is the designated proposer (unlike the permissionless branch at line 261). So the attacker does not need to be the scheduled proposer. [5](#0-4) 

### Impact Explanation

A single malicious council member in a pre-permissionless network with N=2 or N=3 qualified validators can:

1. Craft a block with any state root they choose.
2. Sign it as proposer (their own key, they are qualified).
3. Attach only their own committed seal (1 seal satisfies `validSeal >= 1`).
4. Broadcast it via P2P.

Any honest node that is syncing (not participating in live consensus) will call `validateHeader` → `verifySeals`, which passes. The node inserts the block into its canonical chain, accepting an invalid state root. This is a consensus divergence between live-consensus nodes (which require quorum=3) and syncing nodes (which accept quorum=1), and constitutes invalid block acceptance with corrupted canonical state.

The affected network sizes are N=2 (F=0, threshold=1) and N=3 (F=0, threshold=1). N=1 is unaffected since 1 seal is the correct quorum.

### Likelihood Explanation

Pre-permissionless Kaia networks with exactly 2 or 3 validators are a realistic deployment configuration (e.g., service chains, testnets, early-stage networks). The attack requires only one malicious council member using their own legitimate key — not key compromise, not majority collusion. The P2P sync path is a standard public entry point.

### Recommendation

Replace the `2*F+1` formula in the pre-permissionless branch with `sealer.Quorum(blockNum, qualifiedLen, committeeSize)`, which already returns N for N<4 and `ceil(2N/3)` otherwise — matching `calcQuorumSize` used by the live consensus. This eliminates the inconsistency for small committees while preserving historical validity for larger ones.

Alternatively, add a special case in `F` or in `verifySeals` to enforce a minimum quorum of N when N<4, mirroring the `calcQuorumSize` guard.
