### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` makes `Commit#deployable?` trust another repository's CI result - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub `status` webhook to using only `Commit.where(sha: params.sha)`, with no filter on the repository that sent the webhook. If a commit with the same SHA exists in another stack (tracking a different repository), that unrelated stack's commit silently receives the `Status`, which then flows into `Commit#deployable?` and can trigger an unauthorized deploy.

### Finding Description
The broken binding: `Commit#deployable?` for `victim/repoB`'s commit is defined as `!locked? && (stack.ignore_ci? || (success? && !blocked?))` at [1](#0-0) , and `success?` is delegated to `status`, which is derived from `commit.statuses` (rows in the `Status` table) — i.e. the intended equality is `Commit#deployable? == GitHub's real CI result for victim/repoB's own SHA, verified through victim/repoB's own webhook`.

This breaks because `StatusHandler#process` resolves target commits purely by SHA, regardless of which repository's webhook delivered the event: [2](#0-1) 

Contrast this with the base `Handler` class, which the other handlers (`OpenedHandler`, `LabeledHandler`, `ClosedHandler`, etc.) use to scope by `Repository.from_github_repo_name(repository_name)` before acting: [3](#0-2) . `StatusHandler` does not use this `stacks`/`repository_name` scoping at all — it queries `Commit` globally by `sha`.

`create_status_from_github!` then creates the `Status` scoped to whichever stack the matched commit belongs to: [4](#0-3) [5](#0-4) 

**Exploit flow:**
1. `victim/repoB` is a public (or attacker-forkable) repository tracked by a Shipit stack with `continuous_deployment? == true` and `ignore_ci? == false`.
2. Attacker forks or otherwise obtains the exact git object of a victim commit (SHA is content-addressed, so cloning the object reproduces the identical SHA byte-for-byte) and pushes it into `attacker/repoA`, a repository they own that is also tracked by a Shipit stack on the same multi-tenant Shipit instance (per documented multi-org support: [6](#0-5) ).
3. Attacker's own CI (fully under their control) reports `success` for that SHA on `attacker/repoA`. GitHub sends a legitimately-signed `status` webhook for `attacker/repoA` (signature verifies correctly via `Shipit.github(organization: repository_owner)` because it genuinely is `attacker`'s org/app installation — no secrets are stolen: [7](#0-6) ).
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which also matches the `victim/repoB` commit row (already present in Shipit's `commits` table for that SHA), and calls `commit.create_status_from_github!(params)` on it — writing a `success` `Status` scoped to `victim/repoB`'s own stack.
5. `victim/repoB`'s commit is now `success?`, and if not `locked?`/`blocked?`, `Commit#deployable?` returns `true`, and continuous deployment (`schedule_continuous_delivery`/`ProcessMergeRequestsJob`, see `after_create`/`after_commit` callbacks in `Status`) can trigger an unauthorized deploy of that commit in `victim/repoB`'s stack — despite `victim/repoB` never having received any real CI signal for that SHA from its own configured CI/repository.

Existing guards do not prevent this: `verify_signature` only proves the webhook came from a legitimately configured org (here, the attacker's own org), it says nothing about which stack/repository the payload should affect; `drop_unhandled_event` and `ExplicitParameters` schema validate shape, not repository ownership; there is no `repository`/`full_name` check anywhere in `StatusHandler`.

### Impact Explanation
An attacker who controls any repository tracked by the same (possibly multi-tenant) Shipit instance can cause a `Status` record — and consequently a `deployable?` transition and unauthorized deploy — to be written against an unrelated stack/repository/commit they do not control, by reusing an identical SHA. This is a "payload for one repository mutating another's stack/commit" — Critical severity per the stated impact categories. It is repeatable against any commit SHA the attacker can reproduce (any public repo, or any repo whose commits leak through PRs opened against it), across every stack on the instance.

### Likelihood Explanation
Preconditions: (a) the victim stack has `continuous_deployment?` true and `ignore_ci?` false, (b) the victim commit is not `locked?` and the stack is not `blocked?`, (c) the attacker controls a repository/org that is itself a legitimate, configured Shipit tenant (own org/app installation) — no theft of `webhook_secret`, `GITHUB_TOKEN`, or any Shipit secret is required, and (d) the attacker can reproduce the exact victim commit's SHA (trivial for public repositories via forking/cloning the git object). Cost is low and the exploit is fully repeatable per target SHA.

### Recommendation
Scope `StatusHandler#process` to the repository that sent the webhook, mirroring the base `Handler#stacks`/`repository_name` pattern — e.g. restrict the `Commit` lookup to commits belonging to stacks of `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, instead of a bare `Commit.where(sha: params.sha)` across all repositories.

### Proof of Concept
minitest plan (model-level, no live GitHub, mirrors existing suite style):
```ruby
test "cross-repository status payload leaks Status into unrelated stack's commit" do
  sha = "deadbeef" * 5

  repo_victim = shipit_repositories(:shipit) # or a second fixture repo
  stack_victim = repo_victim.stacks.create!(environment: "production", continuous_deployment: true, ignore_ci: false)
  commit_victim = stack_victim.commits.create!(sha:, author: shipit_users(:shipit), authored_at: Time.now,
                                                committer: shipit_users(:shipit), committed_at: Time.now,
                                                message: "victim commit")

  repo_attacker = Shipit::Repository.create!(owner: "attacker", name: "repoA")
  stack_attacker = repo_attacker.stacks.create!(environment: "production")
  commit_attacker = stack_attacker.commits.create!(sha:, author: shipit_users(:shipit), authored_at: Time.now,
                                                     committer: shipit_users(:shipit), committed_at: Time.now,
                                                     message: "attacker commit, same sha")

  refute_predicate commit_victim, :deployable? # before: no real CI success on victim's own stack

  payload = {
    "sha" => sha, "state" => "success", "context" => "ci/attacker",
    "repository" => { "full_name" => "attacker/repoA" }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_predicate commit_victim.reload, :deployable?, # BROKEN: attacker's own CI result now deploys victim's stack
    "victim commit became deployable from a status attached via attacker/repoA's webhook"
end
```
This demonstrates `Commit#deployable?` diverging from GitHub's real CI result for `victim/repoB`'s own SHA/repository binding.

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",

      ].join(' '))
