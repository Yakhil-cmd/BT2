### Title
Unvalidated peer-supplied StakingInfo written to DB before `FastSyncCommitHead` with no rollback on failure, enabling permanent reward-address corruption — (`datasync/downloader/downloader.go`)

### Summary
During fast sync, `commitPivotBlock` writes peer-supplied `StakingInfo` (containing `CouncilRewardAddrs` and `CouncilStakingAmounts`) to the key-value DB before calling `FastSyncCommitHead`. If `FastSyncCommitHead` fails, the fabricated staking info is left permanently in the DB at the pivot block number with no cleanup. Even on success, the content is never validated against the block's state root.

### Finding Description
`commitPivotBlock` calls `d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))` at line 1897, then calls `d.blockchain.FastSyncCommitHead(block.Hash())` at line 1903. If `FastSyncCommitHead` returns an error (e.g., the state root is unavailable), the function returns that error without deleting the already-written staking info. `WriteStakingInfo` performs a plain `db.Put` with no transaction; there is no compensating `DeleteStakingInfo` call in any error branch of `commitPivotBlock`.

The same write-without-validation pattern also appears in the non-pivot fast-sync batch path at lines 1881–1884, where `PutStakingInfoToDB` is called for every result whose `StakingInfo != nil`, again with no content validation. [6](#0-5) 

### Impact Explanation
`StakingInfo` stored at a given block number is the authoritative source for epoch reward distribution — it determines which addresses receive block rewards (`CouncilRewardAddrs`) and in what proportion (`CouncilStakingAmounts`). A malicious sync peer that fabricates these fields can redirect KAIA block rewards to attacker-controlled addresses for the affected epoch. This meets the "unauthorized reward distribution affecting KAIA" impact gate.

### Likelihood Explanation
Any node performing fast sync is exposed. The attacker only needs to be a reachable P2P peer that the syncing node selects as a sync source. No privileged access, governance keys, or validator-majority collusion is required. The `FastSyncCommitHead` failure condition (e.g., incomplete state download, disk error) is a realistic transient condition that makes the corruption permanent, but the content-validation gap exists even on the success path.

### Recommendation
1. **Rollback on failure**: In `commitPivotBlock`, if `InsertReceiptChain` or `FastSyncCommitHead` returns an error, call `d.stakingModule.DeleteStakingInfo(result.StakingInfo.BlockNum)` before returning.
2. **Content validation**: Before writing peer-supplied `StakingInfo`, re-derive it from the committed state (via the staking contract) and reject or overwrite any peer-supplied value that does not match.
3. **Atomic write**: Wrap the `PutStakingInfoToDB` + `InsertReceiptChain` + `FastSyncCommitHead` sequence in a single DB batch/transaction so that a partial failure leaves no orphaned data.

### Proof of Concept
Unit test outline:
1. Mock `blockchain.FastSyncCommitHead` to return `errors.New("missing state root")`.
2. Construct a `fetchResult` with a `StakingInfo` containing fabricated `CouncilRewardAddrs = [attacker_address]`.
3. Call `commitPivotBlock(result)` — it returns the mocked error.
4. Call `ReadStakingInfo(db, pivotBlockNum)` — assert it returns the fabricated entry with `attacker_address`, confirming the orphaned write. [7](#0-6)

func (d *Downloader) commitPivotBlock(result *fetchResult) error {
	block := types.NewBlockWithHeader(result.Header).WithBody(result.Transactions)
	logger.Debug("Committing fast sync pivot as new head", "number", block.Number(), "hash", block.Hash())
	if result.StakingInfo != nil {
		d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
		logger.Info("Imported new staking information on pivot block", "number", result.StakingInfo.BlockNum, "pivot", block.Number())
	}
	if _, err := d.blockchain.InsertReceiptChain([]*types.Block{block}, []types.Receipts{result.Receipts}); err != nil {
		return err
	}
	if err := d.blockchain.FastSyncCommitHead(block.Hash()); err != nil {
		return err
	}
	atomic.StoreInt32(&d.committed, 1)

	// If we had a bloom filter for the state sync, deallocate it now. Note, we only
	// deallocate internally, but keep the empty wrapper. This ensures that if we do
	// a rollback after committing the pivot and restarting fast sync, we don't end
	// up using a nil bloom. Empty bloom is fine, it just returns that it does not
	// have the info we need, so reach down to the database instead.
	if d.stateBloom != nil {
		d.stateBloom.Close()
	}
	return nil
}
