### Title
Webhook signature verification keys on `repository.owner.login` while handlers act on the independent `repository.full_name` field, enabling cross-organization forged writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-org Shipit deployments, `WebhooksController#verify_signature` picks the HMAC secret to validate an inbound GitHub webhook using `repository.owner.login` (or `organization.login`), a value read straight out of the untrusted JSON body [1](#0-0) . But the handlers that actually mutate state look up the target `Stack`/`Repository` using a *different* field in the same payload, `repository.full_name` [2](#0-1) . Because these two fields are never cross-checked, whichever GitHub organization's secret was used to authenticate the request does not have to be the organization whose repository/stack ends up being written to.

### Finding Description
`Shipit.github(organization: repository_owner)` selects the `GitHubApp`/webhook secret keyed by `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, and the signature is checked against that secret [3](#0-2) . This is the multi-org configuration explicitly documented and supported by the engine, where each GitHub organization has its own `app_id`/`webhook_secret` [4](#0-3) .

Once the signature passes, `WebhooksController#create` dispatches the entire raw payload to the registered handlers for the event [5](#0-4) . Every handler (`PushHandler`, the `pull_request` handlers, `StatusHandler`, `CheckSuiteHandler`) resolves the target `Repository`/`Stack` via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a completely separate key from the one used for authentication [2](#0-1) . `PushHandler`, for example, uses this to select stacks and enqueue `sync_github` for them [6](#0-5) .

The equality that should hold but doesn't:
`organization authenticated (repository.owner.login used to pick the webhook_secret)` == `organization whose repository is written (repository.full_name used to resolve the Stack)`.

Before the attack: an organization admin of `OrgA` (who legitimately configured and knows `OrgA`'s `webhook_secret` because they installed Shipit's GitHub App for their own org, per `docs/setup.md`) can only forge webhooks whose HMAC validates against `OrgA`'s secret. Legitimate GitHub-delivered webhooks always have `repository.owner.login` consistent with `repository.full_name`, so this alone isn't exploitable through GitHub itself.

After the attack: nothing stops that same admin from POSTing directly to `/webhooks` a JSON body where `repository.owner.login = "OrgA"` (so `verify_signature` selects and validates against the secret they know) but `repository.full_name = "OrgB/some-tracked-repo"` (a repository belonging to a completely different organization configured in the same Shipit instance). Because the HMAC is computed over the raw body with a secret the attacker legitimately possesses, the signature check passes, and the handler then acts on `OrgB`'s repository using the `full_name` field, which was never covered by any org-scoped trust check beyond "the body's signature matched *some* org's secret."

### Impact Explanation
This crosses a repository-ownership trust boundary: an actor who is only entitled to control webhooks for their own GitHub organization can trigger writes against `Stack`s belonging to a different organization's repositories tracked by the same Shipit instance. Depending on handler, this includes forcing `sync_github`/commit ingestion (`PushHandler`), archiving/unarchiving or creating review stacks for another org's PRs (`PullRequest` handlers), and injecting fabricated commit statuses (`StatusHandler`) — this matches the "cross-repository writes" High/Critical impact bucket.

### Likelihood Explanation
Requires only that the attacker administers (or has webhook-secret knowledge for) any single GitHub organization configured in a Shipit multi-org deployment — no privileged Shipit account, `ApiClient` token, or access to the victim org is needed. This is a realistic, low-privilege position for many real deployments that federate several orgs behind one Shipit instance, as explicitly supported by `docs/setup.md`.

### Recommendation
In `WebhooksController#verify_signature`/`create`, bind the organization used to select the webhook secret to the same value used by handlers to resolve the target repository — e.g., derive both from `repository.full_name` (or validate that `repository.owner.login` matches the owner segment of `repository.full_name`) before dispatching to any handler, rejecting the request if they diverge.

### Proof of Concept
1. Configure Shipit in multi-org mode with `OrgA` and `OrgB`, each with their own `webhook_secret` (per `docs/setup.md`), and a tracked stack for `OrgB/victim-repo`.
2. As an admin of `OrgA` (who knows `OrgA`'s `webhook_secret`), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC_SHA1(OrgA_webhook_secret, raw_body)` and POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` to `"OrgA"`, validates successfully against `OrgA`'s secret [1](#0-0) , then `PushHandler` resolves stacks via `repository.full_name = "OrgB/victim-repo"` [2](#0-1)  and enqueues `GithubSyncJob` against `OrgB`'s stack [7](#0-6) , despite the attacker having no relationship to `OrgB`.

      verified = github_app.verify_webhook_signature(

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
