### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled=false` for `prevent_with_label` repositories - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`Repository#review_stacks_enabled` is meant to be a global gate that disables all automatic review-stack provisioning for a repository, but in `OpenedHandler#provision?` the `&&` only binds to the `provisioning_behavior_allow_all?` clause, not to the two other `||` branches. As a result, a repository configured with `review_stacks_enabled = false` and `provisioning_behavior = :prevent_with_label` will still auto-create a `Shipit::Stack` for any PR that lacks the provisioning label.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == false` ⇒ `provision? == false` for every provisioning behavior. The actual code is: [1](#0-0) 

Because Ruby's `&&` has higher precedence than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is not distributed across the OR'd terms, so when `provisioning_behavior_prevent_with_label?` is true and the PR carries no label, `provision?` returns `true` regardless of `review_stacks_enabled`.

`respond_to_pull_request_opened?` gates only on `action == "opened"` and `provision?`, with no additional check of `review_stacks_enabled`: [2](#0-1) . `process` then unconditionally calls `ReviewStackAdapter#find_or_create!`, which creates a `Shipit::Stack`, attaches the pull request, and immediately enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`: [3](#0-2) . The queue later calls `stack.provision`, which runs the repository's shipit.yml provisioning steps: [4](#0-3) .

No other guard intervenes: `Repository#review_stacks_enabled` is a plain boolean column with no model-level enforcement (`app/models/shipit/repository.rb`), and none of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema check the review-stacks toggle. This is a genuine precedence defect, distinct from and analogous to the same pattern that reportedly exists in `LabeledHandler`/`UnlabeledHandler`.

Attack: an attacker who owns/controls a repository configured this way opens a PR with no labels (labels are attacker-controlled — the attacker opening the PR chooses not to add any label, and can even open PRs from their own fork/branch on a repo they administer, or simply rely on how any external contributor's PR is treated) via the standard `pull_request` "opened" webhook. Since webhook signature verification is a separate, orthogonal control (it authenticates that GitHub sent the payload, not that the *content* obeys the operator's `review_stacks_enabled` intent), a legitimately-signed webhook for an unlabeled PR is sufficient to trigger stack creation despite the operator having disabled review stacks.

### Impact Explanation
The gap causes a `Shipit::Stack` (review stack) to be created and queued for provisioning even though the repository operator explicitly disabled review-stack auto-provisioning (`review_stacks_enabled = false`). Once provisioned, the stack runs the repository's `shipit.yml` deploy/provision steps on the Shipit deploy host, i.e. attacker-influenced (PR branch) commands execute where the operator believed no such automation was possible. This is scoped to the specific repository (not cross-tenant), but it violates the operator's explicit provisioning policy and results in code/commands executing on the deploy host that should not have run — matching the Critical impact category ("a command running that should not, a record written for a repository that did not authenticate it, or a credential leaving the host") in the sense of unauthorized command execution against the operator's intended configuration.

### Likelihood Explanation
Preconditions: repository configured with `provisioning_behavior = :prevent_with_label` and `review_stacks_enabled = false` (a plausible, even encouraged configuration for a repo that wants labels to gate stacks with review stacks otherwise "off"). Attacker cost is trivial: open a PR without the provisioning label (the default state of any new PR). No secrets, sessions, or privileged roles required — this is triggered purely by the natural webhook flow from opening a PR. Fully repeatable for every PR opened against the misconfigured repository.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates all three behavior branches:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the same fix to the analogous methods in `LabeledHandler`, `UnlabeledHandler`, and `ReopenedHandler` if they share this pattern.

### Proof of Concept
Minitest, in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  Shipit::ReviewStackProvisioningQueue.expects(:add).never

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix: `Shipit::Stack.count` increases by 1 and `ReviewStackProvisioningQueue.add` is invoked, even though `review_stacks_enabled == false`. After applying the recommended fix, both assertions pass.
