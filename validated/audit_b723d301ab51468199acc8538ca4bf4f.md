## Finding

The strongest verifiable analog to the Jenkins Mac Plugin missing-permission-check bug (CVE-2020-2148) in this codebase is a deliberately disabled permission check in the wallet's `"sign"` device-message handler in `wallet.js`.

### Title
Missing cosigner authorization check allows any paired device to trigger local signing requests for wallet addresses it does not co-own - (File: wallet.js)

### Summary
`wallet.js`'s `handleMessageFromHub` processes the `"sign"` subject sent by any already-paired correspondent device [1](#0-0) . After parsing and hash-checking the unsigned unit, it calls `findAddress()` to resolve where the address's signing key lives, and in the `ifLocal` callback — reached when the requested address's private key exists on the receiving device — it accepts the request and fires the `signing_request` UI event / begins validating the unit, with the actual cosigner-membership check commented out [2](#0-1) .

### Finding Description
The code explicitly shows what the check *should* be:
```

    //    if (sender_rows.length !== 1)
    //        return callbacks.ifError("sender is not cosigner of this address");
        callbacks.ifOk();

``` [3](#0-2) 

Contrast this with the `ifRemote` branch of the very same handler, which *does* enforce that the sender is a listed cosigner of the address before proxying the request: `if (!other_device_addresses.includes(from_address)) return callbacks.ifError("you are not listed as a cosigner for this address ...")` [4](#0-3) . The `ifLocal` path lacks the equivalent authorization check against `extended_pubkeys`/`wallet_signing_paths`, which is the table used elsewhere in the very same file to authorize cosigners (e.g. for `arbiter_contract_shared` and `prosaic_contract_shared`) [5](#0-4) [6](#0-5) .

`findAddress()` only confirms that the address+signing_path pair is hosted locally in `my_addresses`/`wallet_signing_paths`; it does not verify that the message's `from_address` (the paired device that sent the `"sign"` request) is actually one of the wallet's registered cosigners in `extended_pubkeys` [7](#0-6) . As a result, any device that has been paired with the victim (a "correspondent"), even one with zero legitimate participation in a particular multi-device wallet or shared address, can send a crafted `"sign"` request for any local address it knows about, and the receiving node will proceed to validate/emit a signing prompt for it. This is exactly the "missing permission check by a lesser-privileged, already-connected principal" bug class described in the Jenkins advisory (a peer that has some access — Overall/Read there, "paired correspondent" here — reaching functionality that should be restricted to a more privileged principal — SSH-credential use there, cosigner authorization here).

### Impact Explanation
This allows an unauthorized paired device (not a cosigner) to:
- Force local unit validation (`network.handleOnlineJoint`) of attacker-supplied unsigned units for the victim's local addresses [8](#0-7) .
- Spam/trigger the `signing_request` event that surfaces a signing confirmation dialog in the wallet UI, for a payment the attacker fully constructed (recipient/amount encoded in `objUnit.messages`), potentially inducing the user to approve unintended outgoing payments (unauthorized spending) if they are not carefully scrutinizing the popup, since the request appears to legitimately involve their own address.
- Because there is no authorization gate before this occurs, any paired chat contact — not just genuine multisig/multi-device wallet cosigners — can reach this code path.

### Likelihood Explanation
The prerequisite is only that the attacker's device is a paired correspondent of the victim (`correspondent_devices` entry) — a low bar, since pairing is initiated via widely shared pairing codes/QR codes and bot pairing flows [9](#0-8) . No cosigner relationship on the specific wallet/address is required, only knowledge of a valid local address and signing path of the victim, both of which can be observed from prior interactions (chat, shared addresses, contract flows).

### Recommendation
Restore (rather than comment out) an authorization check in the `ifLocal` branch of the `"sign"` handler, verifying that `from_address` is a legitimate cosigner for `body.address`'s wallet (via `extended_pubkeys`/`wallet_signing_paths`) before accepting the request and emitting `signing_request`/validating the unit — mirroring the check already implemented in the `ifRemote` branch. If multilateral (cross-address, cross-wallet) signing must remain supported, that use case should be explicitly authorized via its own permission model (e.g., checking that `from_address` corresponds to a declared multilateral signer for that specific `signing_path`), rather than disabling the cosigner check entirely.

### Proof of Concept
1. Pair a device D2 with the victim's wallet device D1 (ordinary chat pairing, no wallet cosigner relationship required).
2. D2 learns one of D1's local payment addresses `A` (e.g., from a prior chat/shared-address interaction) and its default signing path `r`.
3. D2 sends a `"sign"` device message to D1 via the hub with `body = {address: A, signing_path: "r", unsigned_unit: <attacker-crafted unit paying attacker's address from A's funds>}`.
4. D1's `wallet.js` `handleMessageFromHub` resolves `A` as local via `findAddress`, and because the cosigner check in `ifLocal` is commented out, it validates the unit and emits `signing_request`, causing D1's wallet UI to prompt for a signature for a transaction it never initiated. [10](#0-9)

	db.query(
		"SELECT wallet, account, is_change, address_index, full_approval_date, device_address \n\
		FROM my_addresses JOIN wallets USING(wallet) JOIN wallet_signing_paths USING(wallet) \n\
		WHERE address=? AND signing_path=?",
		[address, signing_path],
		async function(rows){
			if (rows.length > 1)
				throw Error("more than 1 address found");
			if (rows.length === 1){
				var row = rows[0];
				if (!row.full_approval_date)
					return callbacks.ifError("wallet of address "+address+" not approved");
				if (row.device_address !== device.getMyDeviceAddress()) {
					const other_rows = await db.query("SELECT DISTINCT device_address FROM wallet_signing_paths WHERE wallet=? AND device_address!=?", [row.wallet, row.device_address]);

					wallet: row.wallet,
					account: row.account,
					is_change: row.is_change,
					address_index: row.address_index
				};
