### Title
Webhook `status` events write commit statuses without repository scoping, allowing any org with a valid signing secret to forge CI status for commits in unrelated repositories - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook by looking up the GitHub App secret for the **organization** named in the payload (`repository.owner.login`), but the handler that actually performs the write — `StatusHandler` — resolves the target purely by commit **sha**, with no check that the commit belongs to a stack/repository under the organization whose secret validated the request.

### Finding Description
`WebhooksController#verify_signature` selects which secret to check against using only the organization login from the payload: [1](#0-0) 

That binds "signature verified" to "organization X's App secret matches," nothing more. But `StatusHandler#process`, unlike `PushHandler`/`CheckSuiteHandler` (which use `Handler#stacks`, itself scoped by `repository.full_name` via `Repository.from_github_repo_name`), performs a completely unscoped lookup: [2](#0-1) 

It queries `Commit.where(sha: params.sha)` across the **entire** Shipit installation and calls `create_status_from_github!` on every match, regardless of which repository/organization that commit belongs to.

The base `Handler` class does define a repository-scoped `stacks` helper keyed off `payload.dig('repository', 'full_name')`: [3](#0-2) 

but `StatusHandler` simply never uses it, so the "org authenticated" (`repository.owner.login`, checked against a specific App's `webhook_secret`) and "repository/commit written" (`sha`, resolved globally) are two entirely disjoint fields of the same JSON body — exactly the kind of deployment-trust binding break in scope here: **organization that authenticated ≠ repository (commit) that is written**.

Shipit explicitly supports multiple independent GitHub Apps/organizations sharing one instance, each with its own `webhook_secret` that the owning organization itself provisions: [4](#0-3) 

So an org (call it `OrgA`) that is a legitimate, but otherwise unprivileged, tenant of the shared Shipit instance knows its own valid webhook secret and can produce a validly-HMAC-signed `status` event where `repository.owner.login = "OrgA"` (making `verify_signature` succeed) while the `sha` field is copied to match a commit that actually belongs to `OrgB`'s stack.

### Impact Explanation
Because `Commit#create_status_from_github!` is invoked with attacker-controlled `state`/`context`/`target_url`/`description` for any sha that happens to exist in the datastore, `OrgA` can inject a fabricated passing CI status (e.g. `context: "ci/tests"`, `state: "success"`) onto a commit belonging to `OrgB`, a repository/organization it has no access to. Shipit's deploy-gating and merge-queue logic rely on `Commit#deployable?`/status checks derived from these `Status` records, so this is a genuine cross-repository/cross-tenant write that can unblock or spoof the CI prerequisite for an otherwise-blocked deploy or merge in a repository the attacker does not own — satisfying the "cross-repository writes" / "unauthorized deploy or merge" bar.

### Likelihood Explanation
Requires only that the attacker control (or be an admin of) any one organization/App already legitimately configured on the shared Shipit instance (a normal, documented multi-tenant setup) and know/guess a target commit sha in another tenant's repository (commit shas are frequently public/knowable via GitHub itself). No Shipit session, `ApiClient` token, or privileged account is required — only the webhook endpoint, which is unauthenticated by design apart from the per-organization HMAC check that this bug fails to actually scope.

### Recommendation
Scope `StatusHandler#process` (and any other handler that writes model state) to the repository resolved from the same trust boundary used for signature verification — i.e., only update `Status` for commits that belong to a stack under `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, and additionally assert that this repository's `owner` matches the organization whose secret validated the webhook.

### Proof of Concept
1. Shipit instance is configured with two GitHub Apps for `OrgA` and `OrgB` per the documented "Using Multiple GitHub Applications" setup, each with its own `webhook_secret`.
2. `OrgA`'s administrator (who legitimately owns `OrgA`'s App and its `webhook_secret`) computes `sha1=HMAC(webhook_secret_OrgA, body)` over a forged JSON body:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/some-repo"},
  "sha": "<commit sha belonging to OrgB/victim-repo>",
  "state": "success",
  "context": "ci/tests"
}
```
3. POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=...`.
4. `verify_signature` succeeds because it only checks the signature against `OrgA`'s own secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit under `OrgB/victim-repo`, and writes a fabricated "success" status to it — with no verification that the commit belongs to `OrgA`.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
