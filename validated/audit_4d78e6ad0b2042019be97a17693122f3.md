### Title
Routed-swap authorization leaks to route-named code: a malicious hop pool can spend any of the caller's tokens inside the signed auth tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The `.npmrc` bug class is credentials scoped to one authority (the registry) being replayed against a different host (the tarball URL). The on-chain analog exists here: a `swap_collateral` / `swap_debt` / `repay_debt_with_collateral` / `multiply` caller signs an authorization tree intended to cover one exact input-token transfer to the router, but the swap-aggregator executes venue calls against pool and token addresses named by the caller-supplied payload with no allowlist. A route that names attacker-controlled code puts `token.transfer(victim, attacker, amount)` below the caller's auth entry; simulation records it as a child of the caller's `swap_*` entry, and if the caller signs that tree the transfer executes — draining wallet balances of any token, including tokens the protocol never listed. The repo documents this exposure in `docs/explanation/threat-model.md` and proves it in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

### Finding Description
`swap_tokens` in the controller authorizes exactly one invocation: `token_in.transfer(controller, router, amount_in)` via `authorize_transfer_as_current`, with no token allowance [1](#0-0) . That correctly scopes the *controller's* grant (INV-STRAT-01) [2](#0-1) .

The scope break happens one level down. `execute_strategy` calls `sender.require_auth()` and then walks the payload's instruction stream, calling whatever pool/token addresses the `assets` registry names — the router "keeps no allowlist of them" [3](#0-2) . Venue adapters self-authorize with invoker-contract auth (`authorize_as_current_contract`), so no extra entries appear for honest hops, but arbitrary third-party code placed on the call stack by the route runs *below the caller's `require_auth` entry* [4](#0-3) . In recording mode the host attaches any `token.transfer(caller, …)` issued by that code as a child of the caller's authorization entry, and in enforcing mode it executes if the caller signed it [5](#0-4) .

This is the CVE-2024-37150 shape exactly: an authorization credential granted for host A (the router hop) is silently extended to host B (whatever contract the payload names), because the consumer of the credential does not pin the recipient domain.

The harness test demonstrates the full chain end to end: a `RogueHopPool` named as the hop venue calls `token::Client::new(&wallet_token).transfer(&victim, &attacker, &amount)` inside its `swap` [6](#0-5) ; simulation records the theft as a `sub_invocations` child under Alice's `swap_collateral` entry [7](#0-6) ; and in enforced mode the same route with the simulation-produced tree succeeds and moves her entire wallet balance to the attacker [8](#0-7) .

Note the honest-tree test also shows the mitigation ceiling: signing only the root makes the host reject the rogue transfer [9](#0-8) . The vulnerability is that neither the controller nor the router prevents route-named code from injecting such children into the recorded tree — the defense is delegated entirely to the client decoding the route it signs [10](#0-9) , which is precisely the "documented boundary" caveat: this finding stands only insofar as the protocol is expected to bound what routes can do on-chain, not relying on every signer auditing XDR auth trees.

### Impact Explanation
Theft of user funds. A victim running `swap_collateral` (or `multiply`, `swap_debt`, `repay_debt_with_collateral`, `flash_position`'s inner swap, or a direct `execute_strategy`) with a crafted route loses any token balance in their wallet — the loss is "the caller's wallet, not the routed amount" [11](#0-10) . In the proof test Alice loses `WALLET_BALANCE` of an unlisted token while the swap itself completes normally and credits a fair `token_out` [12](#0-11) .

### Likelihood Explanation
Reachable by a single unprivileged address: the attacker deploys a contract exposing the hop-venue ABI, embeds its address in the `assets` registry of a route, and gets a victim to submit that route (the quote/route is built off-chain and passed as opaque XDR; users do not decode hop addresses before signing). The attacker's only cost is contract deployment. The exploit requires the victim to sign the recorded tree — the same signature the honest flow already needs, so no extra user interaction is required beyond choosing the poisoned route. Severity is bounded by the documented client-side mitigation; on-chain the protocol deliberately admits unallowlisted venues per ADR-0018 [13](#0-12) .

### Recommendation
Constrain what a route can place beneath the caller's authorization on-chain rather than relying on client-side XDR decoding:

- Maintain a governance-managed venue/pool allowlist in the swap-aggregator (analogous to the existing Blend-pool approval list enforced by INV-STRAT-03 [14](#0-13) ) and reject hops whose `assets[idx]` pool is not listed.
- Alternatively, have the controller pin the expected token set for each strategy call and post-check that the signed invocation tree contains no children other than the single authorized `token_in` transfer — i.e., enforce at the contract level the same rule the threat model asks clients to apply manually.
- At minimum, emit an event or return metadata listing every distinct external contract invoked during `execute_strategy` so callers/wallets can flag unexpected domains before signing.

### Proof of Concept
Already implemented as a harness test: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

```rust
// Attacker-deployed "pool" named in the route's assets registry.
pub fn swap(env: Env) {
    let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = /* ... */;
    if amount > 0 {
        // Runs below the caller's swap_collateral auth entry.
        token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
    }
}
```

1. Attacker deploys `RogueHopPool` with `PLAN = (alice, wallet_token, attacker, WALLET_BALANCE)`.
2. Attacker supplies a `swap_collateral` route whose hop names `RogueHopPool`; the router double pays fair output so the swap looks legitimate.
3. `simulateTransaction` records `token.transfer(alice → attacker, WALLET_BALANCE)` as a child of Alice's `swap_collateral` entry — asserted in `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` [15](#0-14) .
4. Alice signs the simulated tree; `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the theft executes: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while her protocol position still receives the fair swap output [16](#0-15) .

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
