### Title
Structural definition validation treats unresolved nested `address` references as satisfying the "must have signature" requirement, bypassing the anti-sig-free-definition check - (File: definition.js)

### Summary
`validateDefinition()` enforces the invariant that every logical branch of an address (or asset-issuer) spending condition must resolve to `bHasSig = true`, i.e., every branch must ultimately require some authentifier (signature/hash) at runtime [1](#0-0) . The `'address'` op, used to nest another address's definition inside a definition, computes `bHasSig` for that branch by looking up the referenced address's current definition. When the referenced address has never posted a definition yet (`ifDefinitionNotFound`), and it is not co-defined by an author in the same unit, the code should have deferred/failed this determination, but instead a variable `bAllowUnresolvedInnerDefinitions` is hardcoded to `true` (the actual guarding check, `objValidationState.bAllowUnresolvedInnerDefinitions`, is commented out immediately above it) [3](#0-2) . As a result the branch is unconditionally reported back as `cb(null, true)` — "this branch has a signature" — even though nothing has actually been checked or resolved, analogous to the reported bug class where a call to a non-existent/self-destructed contract is treated as a successful call.

### Finding Description
This is precisely the "missing existence check treated as success" pattern from the external report, transplanted to definition/address validation instead of contract calls. The `'address'` op is meant to defer part of a spending condition to another address's own definition (e.g., `['address', 'SOME_ADDRESS']` inside an `or`/`and`/`r of set`). During structural validation of a *new* definition (`validateDefinition`), the code must determine whether that nested branch structurally guarantees a signature requirement, which is used purely to satisfy the global "each branch must have a signature" rule at [4](#0-3) . But when `SOME_ADDRESS` does not yet have a definition on the DAG (`ifDefinitionNotFound`) and is not being defined in the current unit by a co-author, the correct behavior would be to either reject the branch (fail validation, forcing the author to add a real signature requirement) or defer judgment — instead the code always answers "yes, has a signature" via the hardcoded `true`, letting the branch through as if it were adequately secured [3](#0-2) .

By contrast, the actual runtime authorization evaluator (`validateAuthentifiers`, used to check real signatures when spending), correctly returns `cb2(false)` in the equivalent case when the referenced address's definition cannot be resolved [5](#0-4) . This asymmetry is exactly the bug: the *structural* check that gates whether a definition is even accepted onto the DAG treats an "address existence" lookup failure as success, while the runtime check treats the same failure as failure.

### Impact Explanation
An attacker (unprivileged author of a new address/asset-condition unit) can craft a definition such as:
```
['or', [ ['address', 'FRESH_UNUSED_ADDRESS'], ['sig', {pubkey: attacker_pubkey}] ]]
```
or more subtly hide a no-signature-required branch behind nested `'address'` references to never-used addresses, so that the top-level `bHasSig` check at line 626 is satisfied by the phantom `true` returned for the unresolved `'address'` branch, without that branch truly enforcing any authentifier. This is a validation-time false-positive: it does not immediately let funds move without a signature (because runtime `validateAuthentifiers` for that same op does properly fail-closed at line 792/793), but it means the "each branch must have a signature" defense-in-depth invariant enforced by `validateDefinition` can be defeated for the specific branch, silently allowing definitions to be accepted into the DAG that the design intended to reject at creation time. Because address definitions can be changed later (`seen definition change`), and other constructs elsewhere in oscript rely on this same structural signature-requirement guarantee being sound (e.g., asset issuer/definer conditions, AA-adjacent address definitions used to gate payments), the false "has signature" result undermines a foundational safety check that other code paths (including wallet, AA payment routing, and asset-issuance definer checks) rely on to assume that any accepted address definition genuinely enforces authorization somewhere in every branch.

### Likelihood Explanation
High reachability: any unprivileged party can post a unit that defines a new address (or defines an asset's spending condition) containing a `'address'` reference to an address that has no prior definition, which is a completely ordinary, low-cost, single-unit action. No special privileges, no waiting for network state beyond "address never posted a definition," are required to trigger the `ifDefinitionNotFound` branch and the hardcoded bypass.

### Recommendation
Remove the hardcoded `var bAllowUnresolvedInnerDefinitions = true;` and restore the real check against `objValidationState.bAllowUnresolvedInnerDefinitions` (or explicitly fail closed, returning `cb("definition of inner address "+other_address+" not found")`, matching the fail-closed behavior of the runtime `validateAuthentifiers` evaluator) at [3](#0-2) . At minimum, an unresolved nested `'address'` reference must not be treated as automatically satisfying the "has signature" structural requirement.

### Proof of Concept
1. Attacker composes a unit defining address `A` with definition:
   `['or', [ ['address', 'B'], ['sig', {pubkey: attacker_pubkey}] ]]` where `B` is a fresh address that has never posted any unit/definition and is not co-authoring this unit.
2. During validation of this new definition, `evaluate()` reaches the `'address'` case for `B`; `storage.readDefinitionByAddress` calls `ifDefinitionNotFound`; since `B` isn't a co-author in this unit, `arrDefiningAuthors.length === 0`, and the hardcoded `bAllowUnresolvedInnerDefinitions = true` causes `cb(null, true)` to be returned for this branch [6](#0-5) .
3. The `'or'` aggregation at [7](#0-6)  counts this branch as `bHasSig = true`, satisfying `count_options_with_sig === args.length` is not even required since `or` only needs one option — meaning the definition passes the "each branch must have a signature" gate at line 626 based purely on the phantom result from the unresolved `'address'` op, rather than on a genuine verified requirement.
