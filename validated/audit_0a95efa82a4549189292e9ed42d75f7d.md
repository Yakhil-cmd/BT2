### Title
Attacker-triggered assert_eq! panic in `build_updated_stake_reward` via same-block Split/Withdraw on own stake account halts the cluster - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
An unprivileged staker who is the sole stake/withdraw authority of their own stake account can submit a `Split` or `Withdraw` instruction that lands in the same block (or any block after the last recalculation) that triggers reward distribution for their delegation. Because `build_updated_stake_reward` reads the *current* `StakesCache` entry at distribution time and compares it against a reward delta computed earlier from a now-stale delegation value, the `assert_eq!` at [1](#0-0)  can fail deterministically on every honest validator, causing a cluster-wide panic.

### Finding Description
`store_stake_accounts_in_partition` snapshots the live `stakes_cache` at the moment of distribution: [2](#0-1) . For each reward it calls `Bank::build_updated_stake_reward`, which fetches the *current* stake account for the pubkey from that live cache: [3](#0-2) .

When the `relax_post_exec_min_balance_check` (SIMD‑0392 "adjust delegations for rent") feature is not active, the code takes the `else` branch and asserts that the *current* on-chain `stake.delegation.stake` plus the previously computed `inflation.stake_reward` equals the previously computed `new_stake.delegation.stake` (the value baked into the `PartitionedStakeReward` at calculation time): [4](#0-3) 

`PartitionedStakeReward::inflation.stake` is derived once, either during the epoch-boundary `calculate_stake_rewards_and_commissions` pass [5](#0-4) , or refreshed once per new block via `recalculate_partitioned_rewards_if_active`/`recalculate_stake_rewards`, which itself reads the stakes cache *as it existed at the start of that block* (i.e., the parent's state, before that block's transactions execute) [6](#0-5) .

Distribution (`distribute_partitioned_epoch_rewards` → `store_stake_accounts_in_partition`) happens after that same block's transactions have been executed and applied to the `StakesCache` (at freeze time), so any stake-authority-signed `Split` or `Withdraw` instruction that lands in that block will mutate `delegation.stake` (and/or lamports) between the reward calculation/recalculation step and the distribution step for that block. There is no code found in this repository that blocks ordinary `Split`/`Withdraw` stake instructions while `EpochRewards.active == true`: the only `RewardInterval` type that models "inside/outside the reward interval" is defined entirely inside the `#[cfg(test)]` module of `partitioned_epoch_rewards/mod.rs` [7](#0-6)  and is never referenced from production transaction-processing code. The doc comment on `store_stake_accounts_in_partition` claims "further state mutation prevents by stake-program restrictions" [8](#0-7) , but no such restriction was found guarding `Split`/`Withdraw`; a test elsewhere even confirms that ordinary transfers to stake accounts (a lamport-mutating operation) are explicitly allowed "regardless of rewards period" [9](#0-8) , and `test_delegation_adjustment_at_distribution` demonstrates the bank tolerating a lamport mismatch only through the rent-adjustment path, not through the assert path used when that feature is inactive.

Because block execution is deterministic and every validator replays the same transaction set at the same block height, the assertion fires identically on every honest node that processes the block, producing a synchronized, cluster-wide panic rather than a fork.

### Impact Explanation
This is a consensus-halting bug: a single unprivileged user, using only their own stake account and authority, can panic every validator process at a deterministic point during epoch-boundary reward distribution, corresponding to the "epoch-boundary halt / cluster-wide panic" bounty category. No validator/leader control, no other users' accounts, and no external state are required — only a well-timed `Split` or `Withdraw` submitted by the stake authority.

### Likelihood Explanation
Preconditions: the attacker must have a stake account with an active/earning delegation that is due a nonzero reward at the epoch boundary, and must be its sole stake/withdraw authority (ordinary staker setup). They must land a `Split` or `Withdraw` transaction in the block that processes their reward's partition (or after the reward's last recalculation and before that partition's distribution). This is timing-sensitive but reproducible: the attacker can observe blockhash progression, epoch schedule, and partition hashing (`hash_rewards_into_partitions`) to predict which block distributes their reward, then submit the mutating instruction in/just before that block. This is fully repeatable in a local test harness. The exploit is gated on the `relax_post_exec_min_balance_check` feature being inactive for the assert-based (rather than min()-based) code path to execute; if that feature is active on the target cluster, the panic path is not reached (though other, non-panicking inconsistencies could still occur through the `adjust_delegation_for_rent` path, which is out of scope for this question).

### Recommendation
`build_updated_stake_reward` should not assert equality against a possibly-stale reward computation. Instead:
- Recompute (or re-validate) the stake reward against the *current* on-chain delegation right before applying it, replacing the `assert_eq!` with a graceful `DistributionError` (e.g., a new `DistributionError::DelegationChanged` variant) that causes the reward to be safely dropped/burned like `AccountNotFound`/`ArithmeticOverflow` are already handled, rather than panicking.
- Alternatively, ensure `recalculate_partitioned_rewards_if_active` is invoked, and the resulting rewards frozen, strictly after all transactions for a given block have been applied and immediately before that block's `distribute_epoch_rewards_in_partition` call, closing the window where a same-block Split/Withdraw can outrun the calculation.

### Proof of Concept
Integration test plan (extending the existing `create_reward_bank`/`create_reward_bank_with_specific_stakes` test harness in `runtime/src/bank/partitioned_epoch_rewards/mod.rs`):
