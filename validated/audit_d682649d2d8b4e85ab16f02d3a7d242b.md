### Title
Cross-repository CI-status forgery via organization-agnostic `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a payload against using `repository_owner`, a value read straight out of the unverified JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')` as fallback) [1](#0-0) [2](#0-1) . This organization is only used to pick the correct HMAC secret via `Shipit.github(organization: repository_owner).verify_webhook_signature` [3](#0-2) . Nothing ties the *authenticated organization* to the *repository/commit the handler actually writes to*.

`Handlers::Handler` (the base class most handlers use) does scope work by the payload's `repository.full_name` via `stacks`/`repository_name` [4](#0-3) , but `Handlers::StatusHandler` bypasses that entirely: it resolves the target purely by commit SHA, with no repository or organization check at all: [5](#0-4) 

Because the HMAC signature only proves "this request was signed by *some* org's registered GitHub App secret," and `StatusHandler` never checks that the signing org owns the commit it's about to write a status for, any organization configured in Shipit (the app explicly supports "multiple GitHub organisations", per `CHANGELOG.md:132`) can forge a `status` webhook that attaches an arbitrary CI status to a commit belonging to a completely different repository/stack, as long as it knows a valid SHA — which is trivial since git commit SHAs are public, content-addressed identifiers visible in any clone or GitHub UI of the target repo.

### Finding Description
The binding broken is: **organization that authenticated (payload `repository.owner.login`, used to select the verifying secret) ≠ the repository/commit whose state is written (looked up solely by `sha`)**.

Flow:
1. Attacker controls (or is invited to) organization `attacker-org`, which is one of the organizations configured in this Shipit instance (multi-org support, `CHANGELOG.md:132`), and therefore knows/derives `attacker-org`'s legitimate webhook secret through normal use of their own app installation.
2. Attacker sends a `status` webhook with `repository.owner.login = "attacker-org"` (so `verify_signature` fetches and validates against `attacker-org`'s secret) but with `sha` set to a real commit SHA belonging to `victim-org/victim-repo`, and `state: "success"`.
3. `WebhooksController#verify_signature` passes because the signature is valid for `attacker-org`'s secret and the raw body [1](#0-0) .
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — globally, across all stacks/repositories — and calls `commit.create_status_from_github!(params)` for every match, regardless of which org "authenticated" the request [5](#0-4) .

This lets a party with legitimate but unrelated org-level trust in Shipit inject a forged commit status (e.g. a fabricated "success" for a required CI check) into an entirely different tenant's repository, without any repository or organization membership check enforcing that they may only report statuses for commits under their own org.

### Impact Explanation
Commit statuses gate deployability in Shipit (required checks must pass before a commit can be deployed). Forging a passing status for a commit in a repository/stack outside the attacker's authorization scope can make an otherwise-blocked, unreviewed, or CI-failing commit appear deployable, enabling an **unauthorized deploy** of that commit for a stack the attacker has no legitimate access to — this meets the Critical impact bar ("unauthorized deploy"). It is also a **cross-repository/cross-tenant write** primitive: an org-scoped credential is used to write into another org's commit records.

### Likelihood Explanation
Any Shipit installation configured with more than one GitHub organization (a documented, supported configuration, see `CHANGELOG.md` "Support multiple GitHub organisations (#1151)") is affected. No repository write access, no `ApiClient` token, and no privileged Shipit account are needed — only possession of a *valid webhook secret for any one of the configured organizations* (which any admin/maintainer of that org's GitHub App already legitimately has) plus knowledge of a target commit SHA, which is public information for any cloned/visible repository. The `StatusHandler` code path performs no additional authorization check, so exploitation is a single crafted HTTP request.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stack/repository whose owner matches the organization that produced a valid signature (i.e., join through `Repository`/`Stack` and require `commit.stack.repository.owner == repository_owner`, mirroring the approach already used by `Handlers::Handler#stacks`/`repository_name`), rather than resolving purely by `sha`.

### Proof of Concept
1. Register (or already control) organization `attacker-org` in the Shipit instance's multi-org GitHub config, with its own webhook secret.
2. Obtain the SHA of any commit tracked by Shipit under `victim-org/victim-repo` (public repo history, or Shipit's own commit list).
3. POST to `/webhooks` with header `X-Github-Event: status`, `X-Hub-Signature` computed with `attacker-org`'s secret over the raw body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"}
}
```
4. `verify_signature` validates against `attacker-org`'s secret and passes [1](#0-0) .
5. `StatusHandler#process` finds the commit purely by SHA and writes the forged status onto the victim's commit [5](#0-4) , regardless of `attacker-org` having no relation to `victim-org/victim-repo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
