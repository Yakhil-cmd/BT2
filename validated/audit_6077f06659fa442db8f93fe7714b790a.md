### Title
Untrusted route code can inject wallet-draining token transfers into a caller’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller forwards caller-supplied opaque `swap` bytes to the configured router. A malicious route can place attacker-controlled venue code below the caller’s root `swap_collateral` authorization. That code can call `token.transfer(caller, attacker, amount)` for any unrelated wallet token; simulation records the call as a required child authorization, and if the caller signs the generated tree, the transfer executes even though the intended swap still succeeds. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` accepts the route as unrestricted `Bytes` and passes it to the strategy implementation. [3](#0-2)  `swap_tokens` forwards those bytes to `execute_strategy` and only constrains the controller’s own exact input-token transfer. [4](#0-3)  The helper authorizes one `transfer(controller, router, amount)` with no further sub-invocations, but this protects only the controller grant—not invocations that attacker-controlled route code requests from the human caller. [5](#0-4) 

Route venues are not allowlisted, so attacker-controlled code can execute below the caller-authorized controller call and request an unrelated token transfer from the caller. [6](#0-5)  The regression test demonstrates a router double invoking a payload-selected pool, and that pool calling `token::Client::transfer(victim, attacker, amount)`. [7](#0-6) [8](#0-7) 

The same class reaches every route-taking controller strategy, including `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`, because each accepts opaque route bytes. [9](#0-8) [10](#0-9) [11](#0-10) 

### Impact Explanation
A caller can lose any token held in their wallet, including assets unrelated to the lending position and not limited by the routed input amount. The theft is bounded only by wallet balances and the authorization tree the caller signs; the protocol’s measured input/output checks and final solvency checks do not detect or bound the extra child transfer. [12](#0-11)  The harness proves a malicious route can transfer an unrelated wallet token while the expected collateral swap output is still credited. [13](#0-12) 

### Likelihood Explanation
Exploitation requires the victim to sign a poisoned authorization tree produced from simulation, so it is not a fully unauthenticated theft. However, the malicious invocation is embedded inside a valid route execution, and the protocol accepts opaque bytes rather than exposing a bounded venue allowlist or predictable authorization surface. [14](#0-13)  The test shows enforced authentication rejects the rogue transfer only when the signed tree omits it, and executes it when the caller signs the simulation-produced child. [15](#0-14) 

### Recommendation
Constrain route execution so route-selected venue code cannot introduce caller-spending child invocations. Prefer a protocol-controlled venue registry or an authorization architecture in which only the controller contract’s scoped transfer authorization is used and route code cannot request separate end-user authorization. At minimum, treat any additional child authorization under a lending strategy root as invalid and enforce this invariant in transaction construction and contract-facing route validation.

### Proof of Concept
1. Deploy a malicious venue whose `swap` function transfers an unrelated victim token to the attacker. [16](#0-15) 
2. Encode a route whose selected hop address is that venue, while configuring a fair `min_out`. [17](#0-16) 
3. Have the victim invoke `swap_collateral` with the malicious route and simulate it. Simulation records the attacker’s token transfer as a child beneath the victim’s `swap_collateral` root. [18](#0-17) 
4. If the victim signs that tree, the unrelated wallet-token balance moves to the attacker while the normal swap output is deposited. [19](#0-18)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
