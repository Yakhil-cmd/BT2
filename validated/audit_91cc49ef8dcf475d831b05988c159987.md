### Title
Divisible private-asset payments leak the sender's change address and balance to the payment counterparty - ([File: divisible_asset.js])

### Summary
When composing and forwarding a **divisible** private-asset payment, ocore does not redact non-relevant outputs from the private payload that is handed to the payment counterparty. Every output of the payment message — including the sender's own change output (address + amount + blinding) — is included, in the clear, in the single `arrPrivateElements` chain that is forwarded to the recipient. This is the opposite of the behavior implemented for **indivisible** private assets, where `buildPrivateElementsChain` explicitly strips `address`/`blinding` from outputs that don't belong to the recipient of that particular chain element.

### Finding Description
For private assets, ocore is designed so that each participant in a private payment only learns what is strictly necessary about the transaction (amount and address of the output that concerns them, plus enough hashed/blinded data to validate the chain). This is implemented for indivisible assets in `buildPrivateElementsChain`: [1](#0-0) 

which deliberately deletes `address` and `blinding` from all outputs except the one belonging to the current chain element, leaving only `{amount, output_hash}` for the others.

No equivalent redaction exists for divisible private assets. In `composeDivisibleAssetPaymentJoint`, the change output is appended to the very same `outputs` array as the recipient's output, and the resulting `payload` (containing all outputs with full address/amount/blinding) becomes the `private_payload` that is stored as the single message payload: [2](#0-1) 

When this payment is saved, `getSavingCallbacks`'s `ifOk` builds the private-element chain directly from this un-redacted `payload` and returns the *same* chain object both as the "recipient chain" and the "cosigner chain": [3](#0-2) 

Because divisible payments consist of exactly one `objPrivateElement` per message (`validateAndSavePrivatePaymentChain` in `divisible_asset.js:17-20` — "we always have only one element"), there is no per-output filtering step analogous to indivisible assets' `hidden_payload`. As confirmed in `private_payment.js`, the code explicitly notes divisible outputs "are never hidden individually": [4](#0-3) 

This full, unredacted chain is what gets sent to the recipient device via `forwardPrivateChainsToOtherMembersOfOutputAddresses` / `sendPrivatePayments` (see the `sendToRecipients` callback in `wallet.js`): [5](#0-4) 

The recipient (an unprivileged private-payment counterparty) therefore receives the sender's change address, the exact change amount, and the blinding factor for that change output — none of which are needed to validate their own payment and none of which they are otherwise entitled to know. This is a direct information-disclosure defect in the "sync"/handoff step of private-payment chain construction, structurally analogous to CVE-2020-25459 (FATE's `sync_tree` leaking sensitive intermediate data to an unauthorized party during processing of a joint/collaborative computation).

### Impact Explanation
An ordinary payment counterparty — someone who is simply paid a private/divisible asset — learns:
- The sender's other address used for change (which, combined with public-chain data, may deanonymize the sender's holdings),
- The exact remaining balance of the sender's spent coin,
- The blinding factor of that change output, which can later be used to link/verify further transactions from that change address.

This breaks the confidentiality guarantee that private/divisible assets are supposed to provide to the paying party, i.e., an authorized recipient obtains privacy-sensitive financial information about the payer beyond what is required to receive/verify their own payment. This is a High-severity confidentiality issue for any use of divisible private assets (e.g., blackbytes-style assets configured as divisible and private), reachable purely by being on the receiving end of a normal, otherwise-legitimate private payment.

### Likelihood Explanation
High. This triggers on every ordinary divisible private-asset payment; no attacker action, malicious peer, or malicious hub is required — the counterparty is simply the intended, legitimate recipient of the payment and receives more data than intended as part of standard wallet flow (`sendMultiPayment` → `composeDivisibleAssetPaymentJoint` → `getSavingCallbacks` → `forwardPrivateChainsToOtherMembersOfOutputAddresses`).

### Recommendation
Mirror the indivisible-asset redaction logic for divisible private assets: when constructing the chain element(s) to forward to a given recipient, clone the payload and strip `address`/`blinding` (retaining only `amount`/`output_hash` where needed for validation) from every output that does not belong to that recipient, analogous to `buildPrivateElementsChain`'s `hidden_payload` handling in `indivisible_asset.js:623-638`. The sender/cosigner-facing chain can retain the full detail, but the object sent to the external counterparty via `sendPrivatePayments`/`forwardPrivateChainsToOtherMembersOfOutputAddresses` should be redacted per-recipient before transmission.

### Proof of Concept
1. Define a divisible private asset (`is_private: true`, `fixed_denominations: false`).
2. Wallet A holds funds of that asset on address `A1` and sends a partial amount to Wallet B's address `B1`, causing a change output back to `A1` (or another owned address) to be created — see `divisible_asset.js:259-266`.
3. `composeDivisibleAssetPaymentJoint` builds one `payload.outputs` array containing both the `B1` output and the `A1` change output, each with full `address`, `amount`, `blinding` (`divisible_asset.js:268-272`).
4. On save, `getSavingCallbacks.ifOk` (`divisible_asset.js:395-404`) builds `arrChains` from this same un-redacted payload and calls `callbacks.ifOk(objJoint, arrChains, arrChains)`.
5. `wallet.js:sendMultiPayment`'s `preCommitCb` forwards `arrChainsOfRecipientPrivateElements` (== `arrChains`) to Wallet B via `walletGeneral.sendPrivatePayments` (`wallet.js:2405-2429`).
6. Wallet B, upon receiving/parsing the private-payment chain, has full visibility of `A1`'s change address, exact remaining balance, and blinding factor — information it was never supposed to learn, in contrast to the redaction Wallet B would experience on the equivalent indivisible-asset flow.
