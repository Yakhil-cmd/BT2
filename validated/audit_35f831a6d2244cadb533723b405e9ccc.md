### Title
`gh skill update` re-binds an installed skill's trusted source to attacker-controlled `SKILL.md` frontmatter metadata - (File: pkg/cmd/skills/update/update.go)

### Summary
This is analogous in *shape* to the reported bug class (state/consistency signal that never fires, and a trust anchor that can be rewritten by the very entity it's supposed to constrain), but I could not confirm a concrete, currently-exploitable vulnerability in this codebase within the scope of this investigation.

### Finding Description
`gh skill update` treats the `metadata.github-repo` (and related `github-tree-sha`/`github-ref`) fields found in the *installed* `SKILL.md` file as the ground truth for where future updates come from [1](#0-0) . These fields are written by the installer as part of the previously-installed content, which itself originates from whatever repository the user pointed `gh skill install` at [2](#0-1) . If a skill's `SKILL.md` embeds forged `github-repo`/`github-path` metadata pointing at a different, more "trusted"-looking repository than the one it actually came from, `gh skill update` would poll and pull future content from that forged source rather than the repo the user actually installed from — the equivalent of the `OnChainLab` account's own state being used to silently redirect trust (the "self-rotatable attester" pattern) rather than an independently verified anchor set at install time.

However, I was not able to fully verify within this session whether:
- the frontmatter fields are sanitized/overwritten at install time to always reflect the actual resolved `opts.Owner`/`opts.Repo` (which would neutralize this), or
- there is a cross-check between the lockfile's `RecordInstall` entry (which does use the real install-time `owner`/`repo`, not the SKILL.md's self-declared metadata) and the values `scanInstalledSkills` later parses from disk.

The presence of the `lockfile` package (which independently records `owner`/`repo` from `opts.Owner`/`opts.Repo` at install time — the trusted parameters, not skill-supplied ones) suggests the maintainers may have already built the correct binding, and that `update.go`'s reliance on on-disk frontmatter could be a fallback path only used when the lockfile entry is absent or when `--dir` is used to scan skills installed by another tool.

### Impact Explanation
If unmitigated, this would let a malicious skill instruct `gh skill update` to silently redirect its own future updates to a different repository than the one actually vetted/installed by the user, without any visible signal to the user (similar to the report's "state doesn't move" problem) — enabling supply-chain style content substitution on subsequent `gh skill update` runs. I cannot state a concrete confirmed impact without further verification of the fallback/precedence logic between `lockfile.go`'s install-time record and `update.go`'s disk-scan parsing.

### Likelihood Explanation
Unconfirmed. Requires establishing that `scanInstalledSkills`/`scanAllAgents` prefer or fall back to skill-supplied frontmatter over the lockfile's install-time-recorded `owner`/`repo`, and that a user would actually run `gh skill update` against a maliciously-crafted, previously-installed skill.

### Recommendation
Given the significant uncertainty here, I recommend this be investigated further with full repository access (a background Devin session) rather than asserting a vulnerability from index-only evidence: specifically, tracing `scanInstalledSkills`/`scanAllAgents` in `pkg/cmd/skills/update/update.go` and comparing it against `internal/skills/lockfile/lockfile.go`'s `RecordInstall`/read path to determine precedence, and confirming whether the update flow ever trusts skill-embedded `github-repo` metadata over the lockfile's install-time-verified source.

### Proof of Concept
Not constructed — insufficient certainty in the precedence between lockfile-recorded and frontmatter-embedded source metadata to produce a concrete PoC without further code access.

```go
// RecordInstall adds or updates a skill entry in the lock file.
// It uses a file-based lock to prevent concurrent read-modify-write races
// when multiple install processes run simultaneously.
func RecordInstall(host, skillName, owner, repo, skillPath, treeSHA, pinnedRef string) error {
	lockPath, err := lockfilePath()
	if err != nil {
		return err
	}
	if err := os.MkdirAll(filepath.Dir(lockPath), 0o755); err != nil {
		return fmt.Errorf("could not create lock directory: %w", err)
	}

	lockedFile, unlock, err := acquireFLock()
	if err != nil {
		return err
	}
	defer unlock()

	f, err := readFrom(lockedFile)
	if err != nil {
		return err
	}

	now := time.Now().UTC().Format(time.RFC3339)

	existing, exists := f.Skills[skillName]
	installedAt := now
	if exists {
		installedAt = existing.InstalledAt
	}

	f.Skills[skillName] = entry{
		Source:          owner + "/" + repo,
		SourceType:      "github",
		SourceURL:       ghinstance.HostPrefix(host) + owner + "/" + repo + ".git",
		SkillPath:       skillPath,
		SkillFolderHash: treeSHA,
		InstalledAt:     installedAt,
		UpdatedAt:       now,
		PinnedRef:       pinnedRef,
	}

	return writeTo(lockedFile, f)
```
