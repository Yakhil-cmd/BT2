### Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a signature based on the *organization* embedded in the payload (`repository.owner.login` / `organization.login`), but the `status` event handler that subsequently runs never re-checks that the commit it mutates actually belongs to that organization's repository. `StatusHandler#process` looks up commits globally by `sha` alone, so an org that legitimately controls its own repository (and can therefore fire a genuinely-signed `status` webhook for it) can write a commit status onto any `Commit` row that happens to share that `sha` — including one that belongs to a completely different stack/repository/organization tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization from the payload and validates the signature using that organization's own `webhook_secret`: [1](#0-0) [2](#0-1) 

Once the signature passes, `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler`: [3](#0-2) 

`StatusHandler#process` performs a **global** `Commit.where(sha: params.sha)` lookup — with no filter on `repository` or `stack` — and writes the status to every matching commit: [4](#0-3) 

Contrast this with `Handler#stacks`, which *does* scope lookups by `repository.full_name` from the same payload and is used by other handlers such as `PushHandler`: [5](#0-4) [6](#0-5) 

The binding that should hold is:
`organization_that_signed_the_webhook == organization_owning_the_repository_whose_commit_is_written`

`StatusHandler` breaks this equality: the signature/organization check happens on `repository.owner.login`, but the actual mutation target (`Commit` row) is selected purely by `sha`, a field that is part of the payload body but is never cross-checked against the `repository` field that was used for authentication. Any tenant repository legitimately onboarded to the same shared Shipit instance can trigger a real `status` webhook (verified with its own valid `webhook_secret`) for a `sha` value it names — commit SHAs are public, git-content-derived identifiers, and are legitimately shared across forks, mirrors, and commits cherry-picked/duplicated between repositories tracked on the same Shipit deployment. If a target stack owned by a different organization has a `Commit` with that same `sha` (a realistic occurrence for forked/mirrored repositories or shared upstream history — a common Shipit multi-tenant setup), the attacker's org can create/overwrite a `Status` on that foreign commit via `Commit#create_status_from_github!`.

### Impact Explanation
Commit statuses feed directly into Shipit's deploy-gating logic (`required_statuses` / `blocking_statuses` evaluated through `CommitChecks`/`Status::Group`, wired from `deploy_spec.rb` and `stack.rb`). An attacker who controls an onboarded but unrelated repository can forge a `success` status on a commit belonging to a victim stack they have no authorization over, potentially satisfying that victim's CI gating requirements and enabling an unauthorized deploy to proceed on the victim's stack — this is a cross-repository write that breaks a deployment-trust boundary and escalates to an unauthorized deploy, matching the required High/Critical impact bar.

### Likelihood Explanation
The attacker only needs to be an authenticated, legitimate owner/CI operator of *any* repository/organization already onboarded to the shared Shipit instance — no privileged access to the victim's org, no knowledge of the victim's `webhook_secret`, and no `ApiClient` token is required. The only non-trivial requirement is producing a `status` payload whose `sha` matches an existing `Commit.sha` in the victim stack, which is realistic in shared/forked/mirrored-history scenarios common to organizations using a shared internal Shipit deployment.

### Recommendation
In `StatusHandler#process` (and any other handler that trusts a payload field without re-deriving it from the authenticated `repository`), scope the `Commit` lookup by the repository asserted in the same payload that was used to select the signing secret, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, mirroring the scoping already used in `Handler#stacks`.

### Proof of Concept
1. Onboard `attacker-org/attacker-repo` to the shared Shipit instance (legitimate, unprivileged tenant onboarding).
2. Identify (via public GitHub data) a commit `sha` that exists both in `attacker-org/attacker-repo`'s history and in `victim-org/victim-repo` (e.g. `victim-repo` is a fork of, or shares upstream history with, `attacker-repo`).
3. Trigger a genuine `status` webhook from `attacker-org`'s installation (e.g., have CI post a status for that `sha`), which GitHub signs with `attacker-org`'s webhook secret.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org`, fetches `Shipit.github(organization: 'attacker-org')`, and successfully verifies the signature.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matches the commit belonging to `victim-org/victim-repo`'s stack, and calls `create_status_from_github!`, writing a status (e.g. `success`) onto the victim's commit — without any authorization from `victim-org`.
