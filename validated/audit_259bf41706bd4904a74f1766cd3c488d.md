### Title
Webhook signature verification keyed on attacker-controlled `repository.owner.login`/`organization.login` while events are routed by a separate, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
The firedancer bug used the wrong index (`largest_ack - 1` wrapping) to select a lookup key, causing the treap to be walked from the wrong side and validating the wrong data. The equivalent trust-binding break in Shipit is that the webhook signature check and the event-routing lookup are computed from two different attacker-controlled fields of the same unauthenticated JSON body, so the "organization whose secret is verified" is not bound to the "repository the payload is applied to."

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository_owner`, which is read directly from the unverified request body: [1](#0-0) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank: [3](#0-2) 

Meanwhile, once the request passes the `verify_signature` filter, `create` dispatches the raw, still-unverified-for-content JSON body to handlers: [4](#0-3) 

Every handler determines which `Stack`/`Repository` the event applies to via a *different* field of the same body, `repository.full_name`, which is never checked against `repository.owner.login`: [5](#0-4) 

So the equality the deployment model is supposed to enforce is:
`organization authenticated by HMAC (repository.owner.login / organization.login)` == `repository actually mutated (repository.full_name)`

Because both fields live in the same unsigned JSON body and the code never cross-checks them, an attacker who can produce a request that authenticates against org A (e.g., an org configured in `Shipit.secrets.github` with no `webhook_secret` set, for which `verify_webhook_signature` short-circuits to `true`) can set `repository.full_name` to point at a repository owned by a completely different, properly-secured org B. The signature filter passes (org A requires no secret), but the handler acts on org B's repository/stack.

### Impact Explanation
This breaks the "organization authenticated versus repository written" binding the ruleset defines as a valid analog target. A successful forgery lets an unauthenticated attacker inject arbitrary `push`, `status`, `check_suite`, `deployable_status`, `pull_request`, or `membership` events for a target stack they do not control, e.g., triggering `GithubSyncJob` for a forged `push` payload, or fabricating commit statuses that `Shipit`'s deploy gating relies on — potentially leading to unauthorized deploys/merges being unblocked. Whether this reaches "Critical/High" per the rubric depends on the deployment actually having at least one multi-org entry with a blank `webhook_secret`, which is a documented, legitimate configuration in `github_app_config`/`github_organizations` (multi-org secrets schema), not a misconfiguration outside the engine's own code path.

### Likelihood Explanation
This requires the operator to run Shipit in the multi-organization GitHub Apps mode (`secrets.github` keyed by org) with at least one configured organization that has no `webhook_secret` — the code explicitly supports and does not warn against this (`@webhook_secret = @config[:webhook_secret].presence` then `return true unless webhook_secret`). I could not verify from the indexed docs/config whether omitting `webhook_secret` per-org is flagged as unsupported/insecure by the maintainers, so likelihood depends on real-world deployment topology that I cannot confirm is common. Given the rules state third-party/deployment-topology-dependent issues are out of scope unless the binding break is in the engine's own code, and here the missing binding check genuinely lives in `WebhooksController`/`Handler` (not the host app), I present this as the strongest reachable analog but flag the pre-condition (an org configured without a secret) as unverified in this codebase snapshot.

### Recommendation
Bind the two identities: after selecting the GitHub App/secret via `repository_owner`, verify that `payload.dig('repository', 'owner', 'login')` matches the owner segment of `payload.dig('repository', 'full_name')`, and reject (422) if they diverge or if the resolved app's `webhook_secret` is blank in a multi-org configuration (require a secret per org rather than silently accepting unsigned traffic). Alternatively, resolve the app to verify against using the same `full_name`-derived repository/org, not a separate top-level `owner`/`organization` field.

### Proof of Concept
1. Configure `Shipit.secrets.github` with two orgs: `org-a` (no `webhook_secret`) and `org-b` (has `webhook_secret`, owns the real target stack).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" },
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-a")`; since `org-a` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (absent/garbage) `X-Hub-Signature` header.
4. `create` dispatches the payload to the `push` handler, which resolves the stack via `repository.full_name` = `"org-b/target-repo"`, enqueuing `GithubSyncJob` for `org-b`'s real stack without ever validating a signature against `org-b`'s secret.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
