### Title
Cross-repository commit status forgery via unscoped `StatusHandler#process` sha lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with zero repository/stack scoping, unlike every other webhook handler which filters through the `Repository.from_github_repo_name(repository_name)`-scoped `stacks` helper. Any `status` webhook whose payload names repository R will update `commit.state` (and persist a `Status` row) for every `Commit` record in the database that happens to share that sha, including commits that belong to a completely unrelated stack/repository S.

### Finding Description
The broken binding: the code should guarantee
`commit.status(after webhook) changed ⇒ payload['repository']['full_name'] == commit.stack.repository.full_name`.

In reality:
```ruby
# app/models/shipit/webhooks/handlers/status_handler.rb
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit.where(sha: params.sha)` is a global, unscoped query across all stacks/repositories — it never consults `payload.dig('repository', 'full_name')`. Contrast with the base `Handler` class, which every other handler is expected to use to scope by repository:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`StatusHandler` does not call `stacks`/`repository_name` at all — it bypasses this scoping entirely.

Once a matching `Commit` row is found (matched purely on `sha`, a value that is a property of the git object, not of any particular repository), `create_status_from_github!` writes a new `Status` under that commit's own (real, victim) `stack_id`:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [3](#0-2) 

`Commit#state` is delegated straight to the recomputed `status`:
```ruby
delegate :pending?, :success?, :error?, :failure?, :blocking?, :state, to: :status
...
def status
  @status ||= Status::Group.compact(self, statuses_and_check_runs)
end
``` [4](#0-3) [5](#0-4) 

Exploit flow: an attacker who owns/controls a GitHub repository R (per the stated attacker capabilities, they can emit signed webhooks from a repo they own) reproduces a commit with an identical sha to a commit already tracked under victim stack S — trivially achievable by forking/cherry-picking so the git object (tree, parents, author/committer identity and timestamps, message) is byte-identical, since SHA-1 commit ids are content-derived and not repository-scoped. The attacker then triggers (or sends) a `status` event for repository R with that sha and `state: success` (or `failure`). `StatusHandler#process` matches the victim's `Commit` row purely by sha, ignoring that the payload names R not S, and calls `commit.create_status_from_github!`, writing a new `Status` tied to the victim stack's `stack_id`. `Commit#state`, shown on stack S's dashboard, now reflects a status the attacker authored under repository R's context.

None of the existing guards prevent this: `verify_signature`/webhook signature validation only proves the payload came from a legitimately configured webhook source (which the threat model grants the attacker for their own repo R), it says nothing about which commit/stack the payload is allowed to affect. `ExplicitParameters` (the `params do ... end` schema) only validates the shape of the payload (sha/state/description present), not repository ownership of the sha. `drop_unhandled_event` and `force_github_authentication` are irrelevant to record-level scoping. There is no `Repository`/`Stack` validation performed anywhere in this call path that ties the found `Commit` to the incoming `repository.full_name`.

### Impact Explanation
A payload naming repository R causes a `Status` row to be created, and `Commit#state`/`Stack` dashboard state to change, for a `Commit`/`Stack` belonging to a different, unrelated tenant repository S — this is a direct instance of "a payload for one repository mutating another's stack [or] commit" (Critical). It lets an attacker falsely mark a competitor's commit green (potentially influencing `deployable?`/`schedule_continuous_delivery` and thus real deploy decisions) or mark it red to grief CI/CD. It is repeatable against any sha the attacker can reproduce and requires no privilege on stack S, no session, and no knowledge of S's secrets.

### Likelihood Explanation
The precondition is that the attacker must reproduce an existing sha of a real commit under the victim stack — feasible when the victim project is open-source/forked (shared git history, identical commit objects across the origin repo and any fork), which is a very common scenario for Shipit-managed repositories. The attacker also needs the capability to emit a genuinely-signed `status` webhook from a repository they control, which is explicitly granted in the threat model's attacker capability list. No Shipit credentials, sessions, or API tokens are required. This is straightforward and repeatable per target sha.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by `sha`/global identifiers) through the same repository-derived `stacks` helper used elsewhere, e.g. restrict the commit lookup to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring the payload's `repository.full_name` matches the commit's own stack's repository before applying any status mutation.

### Proof of Concept
```ruby
# minitest plan (no live GitHub required)
test "status webhook for repository R does not mutate commit state for unrelated stack S" do
  stack_s = shipit_stacks(:shipit)              # repository "shopify/shipit-engine" e.g.
  commit_s = stack_s.commits.create!(sha: "deadbeef" * 5, ...)

  other_repo_payload = {
    'sha' => commit_s.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' }
  }

  before_state = commit_s.reload.state
  Shipit::Webhooks::Handlers::StatusHandler.call(other_repo_payload)
  after_state = commit_s.reload.state

  assert_equal before_state, after_state,
    "commit.state for stack S must not change from a status payload naming a different repository"
end
```
This test demonstrates the equality `payload['repository']['full_name'] == commit.stack.repository.full_name` is never checked, and `commit.reload.state` changes despite the payload naming an unrelated repository.
