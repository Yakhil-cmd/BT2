### Title
Unvalidated, unsigned `creator` account in `initialize_with_permission` permanently misassigns pool-creator fee rights - (File: programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
The `initialize_with_permission` instruction records an arbitrary, attacker-supplied `creator` public key into the pool's permanent on-chain state without requiring that address to sign or otherwise prove consent, similarly to how tSQD's `registerTokenOnL2` allowed an unauthorized caller to permanently set a critical bridge address with no access control.

### Finding Description
In `InitializeWithPermission`, the `creator` account is declared as an `UncheckedAccount` with no signer requirement and no constraint tying it to `payer`: [1](#0-0) 

The value is then written permanently into `pool_state.pool_creator` via `pool_state.initialize(...)`: [2](#0-1) 

Compare this to the sibling instruction `Initialize`, where `creator` is required to be a `Signer`: [3](#0-2) 

This `pool_creator` field is later used as the sole authorization check for withdrawing accumulated creator fees, both in the permissioned collection path (`address = pool_state.load()?.pool_creator` on a `Signer`): [4](#0-3) 

and in the permissionless collection path, where fees are forcibly routed to whatever `pool_creator` value was recorded at pool creation: [5](#0-4) 

Because `initialize_with_permission` allows any `payer` (an unprivileged, permissionless signer) to submit an arbitrary `creator` pubkey without that pubkey's consent, and because this value can never be updated after pool creation (no update/reassign instruction exists for `pool_creator`), a party funding a "permissioned" pool on behalf of a project can silently substitute their own address (or any address) as the permanent fee-rights holder—exactly the "set once, unauthorized, unfixable" pattern described in the analog report.

### Impact Explanation
All ongoing creator-fee revenue collected via `creator_fees_token_0`/`creator_fees_token_1` for the life of the pool is permanently and irrevocably directed to whichever address the transaction submitter chose, regardless of who the legitimate project/creator is supposed to be. This is a permanent misappropriation of protocol/creator fee funds with no recovery path, matching the "permanent freezing/misdirection of funds due to an unauthorized privileged effect" impact bar.

### Likelihood Explanation
Medium: exploitation requires that some other party (e.g., a relayer, bot, or intermediary) is expected to call `initialize_with_permission` on behalf of a real project/creator without that creator co-signing the transaction. Given `creator` is not a `Signer`, any submitter of this transaction can unilaterally choose the value, so the likelihood is entirely dependent on operational trust assumptions rather than any cryptographic protection at the protocol layer.

### Recommendation
Require `creator` to be a `Signer` in `InitializeWithPermission` (consistent with `Initialize`), or add an explicit constraint that ties the recorded `pool_creator` to a value that cannot be unilaterally chosen by the transaction submitter alone (e.g., require a signature or pre-registered creator record). At minimum, add access control so only an authorized party (e.g., the `payer` themselves, or an on-chain allow-listed admin) can set the `pool_creator` field, preventing an unrelated submitter from claiming fee rights over a pool they do not own.

### Proof of Concept
1. Attacker (or any unprivileged actor) calls `initialize_with_permission` supplying legitimate mints/`amm_config` for a pool a project intends to launch, and sets `creator = attacker_pubkey` in the accounts list; `payer` funds the initial liquidity as required.
2. Because `creator` has no `Signer` constraint (`programs/cp-swap/src/instructions/initialize_with_permission.rs:26-27`), the transaction succeeds and `pool_state.pool_creator` is permanently set to `attacker_pubkey` (`programs/cp-swap/src/instructions/initialize_with_permission.rs:357-372`).
3. From then on, every call to `collect_creator_fee` or `collect_creator_fee_permissionless` validates against `pool_state.pool_creator` and routes all accumulated creator fees to `attacker_pubkey` (`programs/cp-swap/src/instructions/collect_creator_fee.rs:10-13`, `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs:17-20`), with no instruction available to change `pool_creator` afterward.
