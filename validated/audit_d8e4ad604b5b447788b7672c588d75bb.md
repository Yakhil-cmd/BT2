### Title
Webhook signature is verified against an organization derived from the payload, but the repository/stack actually acted upon is never checked to belong to that verified organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate a webhook against using the payload's own `repository.owner.login` field, but the code that later dispatches side effects (`Webhooks::Handlers::Handler#repository_name` / `PushHandler#process`) looks up the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`. Nothing enforces that the organization whose secret was used to authenticate the request is the same organization that owns the repository being acted upon. This is the same class of bug as the reported finding: a check ("is this signed by org X") is performed on one representation of the resource, while the operation that follows is performed on a second, independently-controlled representation of the "same" resource, without re-validating the invariant that they match.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` used for verification like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the untrusted JSON body (`repository.owner.login` or fallback `organization.login`) and used to pick `Shipit.github(organization: repository_owner)`, i.e. a specific `GitHubApp` instance with its own `webhook_secret`. `GitHubApp#verify_webhook_signature` then does: [3](#0-2) 

Note the `return true unless webhook_secret` — if the selected organization has no secret configured, verification is a no-op that always succeeds. The example/default configs ship with `webhook_secret` unset: [4](#0-3) 

After `verify_signature` passes, `WebhooksController#create` dispatches the *same raw payload* to handlers: [5](#0-4) 

Handlers determine the target repository/stack from a completely different field of the same payload: [6](#0-5) [7](#0-6) 

Nothing ties `repository.full_name` back to `repository_owner`/the verified organization — they are two independent JSON fields an attacker fully controls in a forged request to the unauthenticated `/webhooks` endpoint (this controller has no session/authentication requirement, unlike `Shipit::Authentication`-protected controllers). In a multi-organization deployment (`Shipit.github_organizations`, `TOP_LEVEL_GH_KEYS` schema in `lib/shipit.rb`), each org can have its own, independently configured `webhook_secret`: [8](#0-7) 

This breaks the required equality: `verified_organization(payload) == owning_organization(target_repository_acted_upon)`.

### Impact Explanation
An attacker who knows (or who administers) one org configured in Shipit with a blank/known `webhook_secret` can forge a payload where `repository.owner.login` names that weakly-secured org (to pass `verify_signature`) while `repository.full_name` names a target `Stack` belonging to an entirely different, properly-secured organization/repository. The forged `push` event is then dispatched to `PushHandler`, which enqueues `GithubSyncJob` for the *target* stack — a stack whose real organization's webhook secret was never checked at all. `GithubSyncJob` fetches real commits via `stack.github_api` and, for stacks with continuous deployment enabled, this results in an automatically triggered deploy of newly-synced commits, i.e., an unauthorized deploy trigger on a repository/organization the attacker does not control and whose signing secret was never validated. This crosses the "unauthorized deploy" Critical-impact bar defined by the rules.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment, and (2) at least one configured organization with no `webhook_secret` set (the documented/example default) or a leaked/guessable one. Both are plausible operational configurations shown in the repo's own example secrets files. No GitHub session, `ApiClient` token, or repository write access is needed — the endpoint is unauthenticated by design (it must be, to receive GitHub webhooks), so this is exploitable by an unprivileged network attacker who can reach the `/webhooks` route.

### Recommendation
After selecting the organization used for signature verification, validate that the same organization owns the repository referenced by `repository.full_name` (and any other repository/organization fields consumed downstream by handlers) before dispatching to `Shipit::Webhooks.for_event`. Reject the payload if `repository.full_name`'s owner segment does not match the verified `repository_owner`. Additionally, treat a missing/blank `webhook_secret` as a hard configuration warning rather than an implicit signature-verification bypass.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `orgA` (no `webhook_secret` set) and `orgB` (properly configured, `orgB/victim-repo` has a `Stack` with `continuous_deployment: true`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-hint>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")`; since `orgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally regardless of the (even absent) `X-Hub-Signature` header — see `app/controllers/shipit/webhooks_controller.rb:24-30` and `lib/shipit/github_app.rb:76-83`.
4. `create` dispatches to `PushHandler`, whose `stacks` lookup resolves `orgB/victim-repo` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), and `stack.sync_github(expected_head_sha: ...)` is invoked (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), enqueuing `GithubSyncJob` for `orgB`'s stack even though `orgB`'s webhook secret was never verified.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
