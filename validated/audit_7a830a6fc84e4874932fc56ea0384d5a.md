### Title
Missing `return` after caught hashing error causes duplicate/undefined processing of untrusted private-payment payload - (File: network.js)

### Summary
`handleSavedPrivatePayments()`'s inner `validateAndSave` function in `network.js` hashes an attacker-supplied private-payment payload with `objectHash.getBase64Hash()`. If hashing throws (e.g. because the payload contains a `null` value or another shape rejected by `string_utils.getJsonSourceString`/`getSourceString`), the `catch` block logs the error and calls `deleteHandledPrivateChain(...)`, but does **not** `return`. Execution falls through to build `key` with an `undefined` `json_payload_hash` and unconditionally invokes `privatePayment.validateAndSavePrivatePaymentChain()` a second time on the same malformed payload. [1](#0-0) 

### Finding Description
This mirrors the OpenSSL `X509_issuer_and_serial_hash()` bug class: a function that computes a hash over externally supplied, potentially malformed data fails to properly stop processing when the hashing/parsing step throws, so a partially-initialized value is used afterwards.

`objectHash.getBase64Hash(obj, true)` calls `string_utils.getJsonSourceString`, which throws `Error` on a `null` value, an unfinite number, or unknown types found anywhere inside the object graph: [2](#0-1) 

In `validateAndSave`, when this throw happens: [3](#0-2) 
the `catch` block calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which asynchronously invokes `cb()` once the DB delete completes — but code execution does not stop there. It falls through to compute `key` (using `undefined` for `json_payload_hash`) and synchronously calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again with the very same (unhashable) `arrPrivateElements`. Every one of that call's outcome branches (`ifOk`, `ifError`, `ifWaitingForChain`) also calls `cb()` (directly or via a second `deleteHandledPrivateChain`): [4](#0-3) 

The net effect is that the `cb` supplied by `async.each` for this row can be invoked twice. `async`'s iteratee callbacks are not designed to be called more than once; a duplicate invocation throws an uncaught "Callback was already called" style error inside the async iterator, propagating out of the `db.query`/mutex callback chain in `handleSavedPrivatePayments`. Because this happens inside a bare callback (not wrapped in try/catch) invoked from the event loop, Node treats it as an uncaught exception, which by default terminates the process.

`objectHash.getChash160`/`getBase64Hash` calls are also used elsewhere on the same kind of untrusted payload, e.g. in `object_hash.js`: [5](#0-4) 

### Impact Explanation
`handleSavedPrivatePayments()` runs whenever a private-payment chain that was previously queued into `unhandled_private_payments` is (re)processed — data written there originates from a private-payment counterparty or paired device, not from a trusted operator. `handleOnlinePrivatePayment()` in the same file stores the raw JSON of `arrPrivateElements` into `unhandled_private_payments` in several branches (`ifNew`, `ifKnownUnverified`, the light-client "wait for chain" branch) without first validating that the payload can be hashed: [6](#0-5) [7](#0-6) 

A counterparty who controls the content of a private-payment chain (e.g. by embedding a `null` somewhere inside `payload`) can therefore get a payload queued that will later crash the receiving light wallet/full node process in `handleSavedPrivatePayments`, when the malformed chain is dequeued and hashed a second time. This is a denial-of-service against the recipient's ocore process (wallet or hub-connected node), preventing it from continuing to process/confirm any further private payments or other queued work handled on the same event loop until restarted — consistent with the "network unable to confirm new units" class of impact for that node.

### Likelihood Explanation
Reaching `validateAndSave` requires only that a private-payment chain accepted by `handleOnlinePrivatePayment` (with a payload not previously hash-validated) end up in `unhandled_private_payments` and later be reprocessed by `handleSavedPrivatePayments`. Some ingestion paths (e.g. `wallet.js`'s `handlePrivatePaymentChains`, used for the hub-relayed `private_payments` device message) already perform a `getBase64Hash` check with a correct `return` before calling `network.handleOnlinePrivatePayment`, which would filter out this specific malformed shape before it is ever queued via that path. However, `handleOnlinePrivatePayment`'s own queuing branches (`ifNew`, `ifKnownUnverified`, and the light `bLight && length>1` branch) commit the raw JSON to the DB unconditionally, without first calling any hash function, meaning any code path that reaches `handleOnlinePrivatePayment` directly (rather than exclusively through the pre-checked `wallet.js` gate) can plant an unhashable payload. I was not able to fully trace every caller of `handleOnlinePrivatePayment` (e.g. a direct peer-to-peer "private_payment" websocket handler) within this analysis due to tool-call limits, so exploitability specifically depends on whether such a path exists that bypasses the `wallet.js` pre-check.

### Recommendation
Add a `return` after the error-handling branch in the `catch` block of `validateAndSave` in `network.js` so that a hashing failure terminates that call path (calling `cb()` exactly once) instead of falling through to re-invoke `privatePayment.validateAndSavePrivatePaymentChain` with a payload known to be unprocessable: [8](#0-7) 
Additionally, validate/sanitize `arrPrivateElements` payloads (rejecting `null`/unsupported types) at the point they are first queued in `handleOnlinePrivatePayment`'s `savePrivatePayment`, so malformed payloads never enter `unhandled_private_payments` in the first place.

### Proof of Concept
1. As a private-payment counterparty (or via a paired device), craft a private-payment chain whose head element's `payload` object (which otherwise satisfies the shallow checks in `wallet.js:handlePrivatePaymentChains`, i.e. non-empty `inputs`/`outputs` arrays of non-empty objects) contains a `null` value nested in a field not covered by those checks (e.g. inside an output/input sub-field).
2. Deliver it through a code path that reaches `network.handleOnlinePrivatePayment` and results in it being written to `unhandled_private_payments` without first calling `objectHash.getBase64Hash` on the payload (e.g. the light-client `ifNew`/`ifKnownUnverified`/chain-wait branches in `handleOnlinePrivatePayment`).
3. Trigger reprocessing of the queue, e.g. via `network.handleSavedPrivatePayments()` (invoked periodically/on new unit events).
4. In `validateAndSave`, `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws because of the embedded `null`; the `catch` block runs `deleteHandledPrivateChain(...)` (which will eventually call `cb()`), but code falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(...)` again, whose callbacks also call `cb()` — resulting in `cb` being invoked twice for the same `async.each` iteration, throwing an uncaught error and crashing the process.

function getJsonSourceString(obj, bAllowEmpty) {
	let cache = new WeakMap();  // object to stringified result
	function stringify(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				return toWellFormedJsonStringify(variable);
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
			case "boolean":
				return variable.toString();
			case "object":
				// return cached result if already processed
				if (cache.has(variable))
					return cache.get(variable);
				let result;
				if (Array.isArray(variable)){
					if (variable.length === 0 && !bAllowEmpty)
						throw Error("empty array in "+JSON.stringify(obj));
					result = '[' + variable.map(stringify).join(',') + ']';
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0 && !bAllowEmpty)
						throw Error("empty object in "+JSON.stringify(obj));
					result = '{' + keys.map(function(key){ return toWellFormedJsonStringify(key)+':'+stringify(variable[key]) }).join(',') + '}';
				}
				cache.set(variable, result);  // memoize for future references
				return result;
			default:
				throw Error("getJsonSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}

function getBase64Hash(obj, bJsonBased) {
	var sourceString = bJsonBased ? getJsonSourceString(obj) : getSourceString(obj)
	return crypto.createHash("sha256").update(sourceString, "utf8").digest("base64");
}
