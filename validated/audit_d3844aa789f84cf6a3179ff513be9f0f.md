Based on my investigation, the block-reward pool is a pre-funded lamport reserve (`create_epoch_rewards_sysvar` holds `block_rewards` in the `EpochRewards` sysvar account, debited via `update_epoch_rewards_sysvar`'s `checked_sub_lamports(debit_block_reward_lamports)` without touching capitalization), not directly the vote account's `pending_delegator_rewards` field being decremented per-distribution. The clamp `.min(pending_delegator_rewards)` in `calculate_block_reward` only bounds a *single* delegator's share to the full pool size — it provides no cross-delegator invariant.

### Title
Split/Merge-induced stake inflation during reward recalculation lets a delegator's `block_reward` exceed its fair share, over-crediting the vote account's `pending_delegator_rewards` pool - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`calculate_block_reward` computes a delegator's share of a vote account's `pending_delegator_rewards` as `pending_delegator_rewards * stake / total_active_stake`, where `total_active_stake` is a frozen snapshot (`RewardEpochDelegatedStakes`) taken at the rewarded epoch boundary, but `stake` (`delegation_effective_stake`) is derived from the delegation's *current* `stake` field read from the live `StakesCache` at recalculation time [1](#0-0) . A comment in the code explicitly acknowledges that `stake > total_active_stake` is possible during recalculation and is "harmless in practice" because of a `.min(pending_delegator_rewards)` clamp, but that clamp only bounds one delegator's reward to the whole pool — it does not enforce that the sum across all delegators stays within `pending_delegator_rewards` [2](#0-1) .

### Finding Description
`recalculate_stake_rewards` is triggered on fork switches while `EpochRewards.active` is true, and recomputes `PartitionedStakeReward`s (including `block_reward`) using the *live* `StakesCache` state for delegation stake amounts, while using the frozen `RewardEpochDelegatedStakes` snapshot as the denominator [3](#0-2) . Because `delegation_effective_stake` for a fully-activated delegation simply returns the delegation's current `stake` field (there is no further warmup once fully active) [4](#0-3) , an attacker who legitimately increases their `Delegation.stake` via a `Merge` (merging a second, fully-owned stake account into their delegated stake) between the epoch-boundary reward calculation and a later recalculation trigger can cause `delegation_effective_stake(...)` computed at recalculation to exceed the value that was captured in `total_active_stake` at epoch-boundary time.

The resulting numerator/denominator mismatch means `pending_delegator_rewards * stake / total_active_stake` can legitimately compute a value greater than 100% of `pending_delegator_rewards` for that single delegator, which is clamped down to exactly `pending_delegator_rewards` — i.e., the attacker's single stake reward entry can claim the vote account's *entire* remaining pool, on top of whatever partial distribution to other delegators has already occurred or will subsequently occur based on the original (smaller, correct) stake proportions calculated before the Merge. There is no code that re-normalizes or re-derives everyone else's shares to sum to `pending_delegator_rewards`; each `PartitionedStakeReward.block_reward` is computed independently per stake account and stored/distributed independently in `store_stake_accounts_in_partition`/`build_updated_stake_reward`, which simply add `block_reward` lamports to each stake account and debit that same total from the `EpochRewards` sysvar via `update_epoch_rewards_sysvar`'s `checked_sub_lamports` [5](#0-4) .

The only invariant enforced at distribution time is that the sysvar has enough lamports to be debited (an `expect`/assert on `checked_sub_lamports`), which only guarantees that cumulative debits across the whole epoch don't exceed the epoch's *total* pre-funded `block_rewards` figure recorded when `create_epoch_rewards_sysvar` was called — it does not enforce a *per-vote-account* cap that sum(block_reward across delegators of vote X) ≤ vote X's `pending_delegator_rewards`. If recalculation only affects the not-yet-distributed remainder of partitions, and if partitions already distributed used the pre-Merge (correct) stake proportions, the total block reward eventually paid out for that vote account across the whole epoch can exceed the vote account's actual `pending_delegator_rewards` for that epoch, at the expense of that discrepancy being paid from the shared epoch-wide `EpochRewards` sysvar pool (funded across all vote accounts), effectively transferring value from other validators'/delegators' block-reward allocations to the attacker.

### Impact Explanation
This falls under "misattributed or duplicated rewards" in the partitioned reward distribution path. The unfair over-payment is sourced from the shared `EpochRewards` sysvar block-reward pool (funded once per epoch, decremented per distribution without capitalization change), so lamports aren't newly minted into the total supply, but the attacker receives lamports that either (a) should have gone to other delegators of the same vote account, or (b) are drawn from the epoch-wide block-reward reserve beyond what was allocated to that specific vote account, silently mis-crediting funds across vote accounts within the same epoch's distribution pool.

### Likelihood Explanation
This requires: (1) attacker controls two of their own stake accounts delegated to the same vote account, one of which is used to legitimately `Merge` into the other after the epoch-boundary calculation but before a later recalculation is triggered by a fork switch, and (2) `recalculate_stake_rewards` must actually be invoked mid-epoch (which happens naturally whenever a validator switches forks while `EpochRewards.active`), and (3) `block_revenue_sharing` feature (SIMD-0123 / SIMD-0185) must be active. All of these preconditions rely only on standard system/stake-program instructions available to an unprivileged user and naturally-occurring fork switches; no privileged validator behavior is required to trigger the recalculation path itself. However, whether the resulting overpayment is realized depends on partition scheduling (which stake accounts are in already-distributed vs. not-yet-distributed partitions) and is bounded per-epoch by the size of `pending_delegator_rewards`, making the magnitude of exploitable value proportional to the vote account's accumulated block revenue in that epoch, not to total inflation supply.

### Recommendation
Track and enforce a per-vote-account remaining `pending_delegator_rewards` budget during recalculation (decrementing it by amounts already distributed in earlier partitions) rather than recomputing each delegator's `block_reward` independently against a static `pending_delegator_rewards` figure and a potentially stale `total_active_stake` denominator; alternatively, disallow Merge/Split operations affecting a delegation's effective stake for the currently rewarded epoch until after reward distribution completes for that vote account, or clamp `total_active_stake` at recalculation time to be at least `delegation_effective_stake` summed over all remaining delegations so proportions can't exceed 100% cumulatively.

    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // On recalculation, only the `StakeRewardCalculation::stake_rewards`
        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while
        // `StakeRewardCalculation::total_rewards` only reflects rewards that
        // have not yet been distributed.
        //
        // NOTE: the `RewardCommissionAccounts` will NOT have a correct
        // post_lamport amount if the commission account is NOT the vote account,
        // because the commission account is loaded from the current bank, and
        // not the start of the epoch. We don't have a snapshot of all commission
        // accounts from the start of the epoch. For this reason, the
        // `RewardCommissionAccounts` calculated in this function call should
        // NOT be used ever.
        let (_, StakeRewardCalculation { stake_rewards, .. }) = self
            .calculate_stake_rewards_and_commissions(
                &stake_history,
                stake_delegations,
                cached_vote_accounts,
                rewarded_epoch,
                point_value,
                &ag_epoch_type,
                thread_pool,
                null_tracer(),
                &mut RewardsMetrics::default(), // This is required, but not reporting anything at the moment
            );
