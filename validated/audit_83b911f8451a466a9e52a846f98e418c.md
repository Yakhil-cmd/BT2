Confirmed: no filtering exists on `machine.environment` keys anywhere in `DeploySpec#machine_env` or `EnvironmentVariables`, and `Command#unbundled_env` merges `@env` last, letting a fork-controlled `PATH` win.

### Title
Fork-controlled `PATH` via `machine.environment` in `shipit.yml` overrides `Command#unbundled_env`, enabling RCE on `allow_with_label` review stacks - (File: lib/shipit/command.rb)

### Summary
`DeploySpec#machine_env` reads `config('machine', 'environment')` verbatim from the checked-out branch's `shipit.yml`, and `TaskCommands#env` merges it into the hash passed to `Command.new`. `Command#unbundled_env` then merges `@env.stringify_keys` last, after the safe `PATH` (built from `Shipit.shell_paths` + `ENV['PATH']`), so a `PATH` key supplied via `machine.environment` silently overrides the deploy host's safe `PATH` for every step, including `deploy.override`, and `PTY.spawn` resolves bare command names against the attacker-controlled directory.

### Finding Description
The broken binding is: the equality `unbundled_env['PATH'] == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` is expected to always hold, but it does not when `@env` contains a `PATH` key.

Code path:
- `DeploySpec#machine_env` returns `config('machine', 'environment') || {}` unfiltered [1](#0-0) .
- `DeploySpec::FileSystem#config`/`load_config` read this straight from the `shipit.yml` found in the task's working directory checkout, i.e., the review-stack branch content that is checked out from the fork PR [2](#0-1) .
- `TaskCommands#env` merges `deploy_spec.machine_env` into the environment hash used for every `Command.new(..., env:, ...)` call, including `DeployCommands#env` used for `deploy.override` steps [3](#0-2) [4](#0-3) .
- `Command#unbundled_env` builds `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)` — `@env` is merged **last**, so any `PATH` key in it wins over the intended safe `PATH` [5](#0-4) .
- `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, so the overridden `PATH` governs resolution of any bare command name in the spawned process [6](#0-5) .

Attacker's exact action: on a repository configured with `provisioning_behavior = allow_with_label`, the attacker opens a PR from their fork whose branch contains a `shipit.yml` with:
```yaml
machine:
  environment:
    PATH: /tmp/evil:/usr/bin:/bin
deploy:
  override:
    - some-bare-command
```
and applies the provisioning label to their own PR — an action the threat model explicitly grants to the unprivileged attacker (`label their own PR`). This is handled by `LabeledHandler`/`OpenedHandler`, which check only `provisioning_behavior_allow_with_label?` and label presence, not repo ownership of the shipit.yml content [7](#0-6) . Shipit then provisions/deploys the review stack, checking out the fork branch and reading its `shipit.yml`, and the injected `PATH` reaches the spawned `deploy.override` command.

No existing guard filters `machine.environment` keys: `DeploySpec#machine_env` (`app/models/shipit/deploy_spec.rb:69-71`) performs no denylist/allowlist on keys such as `PATH`, `LD_PRELOAD`, `RUBYOPT`, etc. `EnvironmentVariables` (`lib/shipit/environment_variables.rb`) is used only for `${VAR}` interpolation inside command strings, not for filtering the env hash passed to `Command.new`. `verify_signature`/webhook signature checks only gate whether the webhook is accepted, not the content of the checked-out `shipit.yml`.

### Impact Explanation
An unprivileged fork PR author achieves arbitrary code execution on the Shipit deploy host, because a bare command name in the `deploy.override` (or any other) step resolves through an attacker-controlled `PATH` directory populated by files checked out from the same fork branch. This is Critical — RCE on the deploy host via `Command`/`PTY.spawn`, matching the specified impact category. The blast radius is scoped to repositories with `provisioning_behavior = allow_with_label` (or `allow_all`, which needs no label) and review stacks enabled, but is fully repeatable per PR/per repository under that configuration, and the compromised host process runs with the Shipit deploy host's credentials (e.g., `GITHUB_TOKEN`), so it can pivot into other repositories/stacks.

### Likelihood Explanation
Preconditions: `review_stacks_enabled = true` and `provisioning_behavior = allow_with_label` (or `allow_all`) on the target repository; the attacker needs no Shipit session, API token, or GitHub org membership — only the ability to open a PR from a fork and label it (assumed available per the threat model). No secrets are required, and the `shipit.yml` in question is entirely attacker-authored on their own fork branch. This is a low-cost, fully repeatable attack requiring only standard GitHub PR mechanics.

### Recommendation
In `Command#unbundled_env`, strip or explicitly disallow the `PATH` key (and other sensitive interpreter/loader variables such as `LD_PRELOAD`, `RUBYOPT`, `DYLD_*`) from `@env` before merging, or merge `@env` first and force the safe `PATH` last: `BASE_ENV.merge(@env.stringify_keys).merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}")`. Additionally, consider denylisting dangerous keys in `DeploySpec#machine_env` so `machine.environment` from `shipit.yml` cannot set `PATH` at all.

### Proof of Concept
Minitest plan (`test/unit/command_test.rb` or `test/unit/deploy_commands_test.rb`):
1. Build a `DeployCommands`/`Command` instance the same way the review-stack `deploy.override` step is built, stubbing `deploy_spec.machine_env` to return `{ 'PATH' => '/tmp/evil:/usr/bin:/bin' }` (simulating a fork branch's `shipit.yml` with a `machine.environment.PATH` entry).
2. Assert on both sides of the binding:
   - Expected (safe) value: `"#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"`.
   - Actual value observed: `command.env['PATH']` and `command.unbundled_env['PATH']`.
3. Assert `command.unbundled_env['PATH'] == '/tmp/evil:/usr/bin:/bin'` (not the safe value), proving the override reaches the hash passed to `PTY.spawn`.
4. Optionally run `Command.new('some-bare-command', env: { 'PATH' => '/tmp/evil_bin' }, chdir: '.').start` with `/tmp/evil_bin/some-bare-command` present, and confirm the attacker binary executes instead of raising `Command::NotFound`.
