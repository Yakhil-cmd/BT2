### Title
No slippage protection on `SwapFirstAssetTrader::refund_weight` swap-back — attacker can sandwich XCM fee refunds - ([File: cumulus/primitives/utility/src/lib.rs])

### Summary
`SwapFirstAssetTrader::refund_weight` swaps unused `Target` fee credit back into the user's original fee-paying asset by calling `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min = None`, i.e. with no minimum-output check [1](#0-0) . This mirrors the reported IchiVaultSpell pattern: when the token obtained from a swap is not being checked against a hard downstream constraint (there, "repay debt"; here, "receive back into holding for the user"), the swap itself has zero slippage protection and its output can be minimized by a pool-price manipulation executed around the victim's operation.

### Finding Description
`SwapFirstAssetTrader` is a `WeightTrader` used to let a user pay XCM execution fees in an asset different from the runtime's `Target` fee asset, swapping through `pallet_asset_conversion`'s `SwapCredit` trait (or any equivalent AMM-backed implementation) [2](#0-1) .

- `buy_weight` swaps the user's asset into `Target` using `swap_tokens_for_exact_tokens`, which does enforce a bound (the exact `fee` amount needed) [3](#0-2) .
- When the XCM message finishes and unused weight is refunded (triggered by `RefundSurplus`/end-of-execution processing in the XCM executor), `refund_weight` swaps the leftover `Target` credit back into the asset the user originally paid with, via `swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` — passing `None` as `amount_out_min` [4](#0-3) .

Because `amount_out_min` is `None`, `pallet_asset_conversion::do_swap_exact_tokens_for_tokens` skips the `ensure!(amount_out >= amount_out_min, ...)` check entirely (that check is conditional on `Some(...)`) [5](#0-4) . The swap will execute at whatever price the pool reserves reflect at that moment, with the standard constant-product AMM slippage — there is no floor on how little the user gets back.

This is the direct analog of the reported bug: in IchiVaultSpell, the swap output is only implicitly checked when the user chooses to repay debt (transfer to bank fails if insufficient); if the user opts out of repayment, there's no explicit slippage bound and the swap is unprotected. In `SwapFirstAssetTrader::refund_weight`, the swapped-back "refund" credit similarly has no explicit slippage bound because the value simply flows back into the XCM holding register with no invariant enforcing a minimum receivable amount.

### Impact Explanation
An attacker who can observe a pending XCM message that will trigger `PayFees`/`BuyExecution` with a non-`Target` asset (e.g. any parachain-to-AssetHub message, or a `pallet_xcm::execute` call by a victim) can, within the same block (front-running via priority/tip, or as a block-producing collator/validator with no special permission beyond ordinary transaction submission), execute a swap on the same AMM pool (`Target` -> `refund_swap_asset`) to skew reserves right before the victim's XCM executes, then reverse it immediately after. The victim's `refund_weight` call executes at the manipulated price and returns them significantly less than the fair-value refund; the attacker profits from the price reversion (a classic sandwich against an unprotected swap).

### Likelihood Explanation
- The `SwapFirstAssetTrader` refund path executes automatically as part of normal XCM message finalization whenever leftover fee credit exists and `last_fee_asset` differs from `Target` — no privileged action or malicious peer/collator/relayer role is required beyond ordinary block-inclusion ordering, which any user or MEV searcher can influence via normal transaction submission/fees.
- The `None` argument is hardcoded in this trait implementation, so every runtime configuring `SwapFirstAssetTrader` with an AMM-backed `SwapCredit` (e.g. `pallet_asset_conversion`) inherits this gap unconditionally; it does not depend on a specific runtime bug, only on using this documented, shipped utility.
- Actual exploitability/profitability depends on refund amounts being economically significant relative to sandwich costs (gas/tip + pool depth), which can be marginal for typical XCM fee refunds — this bounds severity to Medium/Low rather than a large, deterministic loss.

### Recommendation
Pass a computed `amount_out_min` (e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` before swapping, discounted by an acceptable slippage tolerance) instead of `None` in `SwapFirstAssetTrader::refund_weight`, mirroring the bound already used in `buy_weight`. Alternatively, skip the swap-back and return the refund in the `Target` asset (avoiding the reverse swap) if the loss from an unprotected swap is deemed unacceptable.

### Proof of Concept
No executable PoC was run; this is a code-level analysis based on static tracing. Evidence supporting exploitability:
- `refund_weight`'s call site with `None` for `amount_out_min`: [4](#0-3) .
- Confirmed that `pallet_asset_conversion`'s check is only applied `if let Some(amount_out_min) = amount_out_min`, meaning `None` truly disables the floor: [5](#0-4) .
- Existing unit tests (`cumulus/primitives/utility/src/tests/swap_first.rs`) exercise `buy_weight`/`refund_weight` with a 1:1 mock swap and do not test adversarial reserve manipulation between `buy_weight` and `refund_weight`, so no existing harness proves or disproves the sandwich scenario [6](#0-5) .
- I was not able to fully verify, within available tool budget, the precise call-order guarantee from the XCM executor's `RefundSurplus`/message-completion path back into `refund_weight` (i.e., confirming there is always an intervening block boundary that allows front-run + back-run order, versus purely intra-message execution with no interleaving opportunity). This would need to be confirmed via a live integration test (e.g. `cumulus/parachains/integration-tests`) simulating two competing extrinsics/XCM messages in the same block to demonstrate actual value extraction, which was not executed here.

#[test]
fn buy_and_refund_twice_for_target() {
	let client_asset_total = 15;
	let fee = 5;
	let refund1 = 4;
	let refund2 = 2;

	setup_pool(CLIENT_ASSET, 1000, TARGET_ASSET, 1000);
	// create pool for refund swap.
	setup_pool(TARGET_ASSET, 1000, CLIENT_ASSET, 1000);

	let holding_asset = create_holding_asset(CLIENT_ASSET, client_asset_total);
	let holding_change = create_holding_asset(CLIENT_ASSET, client_asset_total - fee);
	let refund_asset = create_holding_asset(CLIENT_ASSET, refund1);

	let target_total = Fungibles::total_issuance(TARGET_ASSET);
	let client_total = Fungibles::total_issuance(CLIENT_ASSET);

	let mut trader = Trader::new();
	let change = trader.buy_weight(weight_worth_of(fee), holding_asset, &xcm_context()).unwrap();
	assert_eq!(&change, &holding_change);

	assert_eq!(trader.total_fee.peek(), fee);
	assert_eq!(trader.last_fee_asset, Some(create_asset_id(CLIENT_ASSET)));

	let refund = trader.refund_weight(weight_worth_of(refund1), &xcm_context());
	assert_eq!(refund.as_ref(), Some(&refund_asset));

	assert_eq!(trader.total_fee.peek(), fee - refund1);
	assert_eq!(trader.last_fee_asset, Some(create_asset_id(CLIENT_ASSET)));

	assert_eq!(trader.refund_weight(weight_worth_of(refund2), &xcm_context()), None);

	assert_eq!(trader.total_fee.peek(), fee - refund1);
	assert_eq!(trader.last_fee_asset, Some(create_asset_id(CLIENT_ASSET)));

	assert_eq!(Fungibles::total_issuance(TARGET_ASSET), target_total);
	assert_eq!(Fungibles::total_issuance(CLIENT_ASSET), client_total);
}
