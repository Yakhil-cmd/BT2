### Title
Webhook signature is bound to the payload's declared organization, not the repository being written — allows cross-tenant push spoofing and unauthorized syncs/deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a delivery against using an **attacker-controlled JSON field** (`repository.owner.login`, falling back to `organization.login`), while the actual event handlers act on a **different, independently-controlled JSON field** (`repository.full_name`). Because the HMAC only proves "this body was signed with organization X's secret," and X is picked from inside that same body, an operator of any organization onboarded to a multi-tenant Shipit instance can forge a payload that verifies against their own organization's secret but drives Shipit to mutate a stack belonging to a completely different, victim organization.

### Finding Description
`Shipit.github(organization: repository_owner)` looks up the per-organization webhook secret to use for HMAC verification, and `repository_owner` is computed purely from request body content: [1](#0-0) [2](#0-1) 

In a multi-tenant deployment, each organization has its own config/secret keyed by org name, selected via `github_app_config`/`github_default_organization`: [3](#0-2) 

The `create` action then dispatches the *entire raw payload* to handlers: [4](#0-3) 

Every handler resolves the target `Repository`/`Stack` using `repository.full_name` from the same payload — a field that is never cross-checked against `repository.owner.login`/`organization.login` (the field used to pick the verifying secret): [5](#0-4) [6](#0-5) [7](#0-6) 

The broken binding, as an equality that the code fails to enforce:

```
organization used to select/verify the webhook secret (repository.owner.login / organization.login)
        ≠
organization that actually owns the repository being acted on (repository.full_name)
```

Since the HMAC signature only proves knowledge of the secret belonging to whichever organization name is embedded in the very same payload, an attacker who legitimately administers **their own** onboarded GitHub organization (and therefore possesses its GitHub App/webhook secret, as configured for their org's installation) can sign a synthetic payload with:
- `repository.owner.login` = `"attacker-org"` (or `organization.login` = `"attacker-org"`) — so signature verification succeeds using the attacker's own valid secret, and
- `repository.full_name` = `"victim-org/victim-repo"` — an arbitrary repository tracked by a different tenant of the same Shipit instance.

`verify_signature` passes because it only checks that the body was signed with attacker-org's secret; nothing re-validates that `repository.full_name` belongs to `attacker-org`. Downstream, `Repository.from_github_repo_name("victim-org/victim-repo")` resolves to the victim's real `Repository`/`Stack` record, and handlers such as `PushHandler` act on it as if GitHub had genuinely reported activity on that repository.

### Impact Explanation
`PushHandler#process` enqueues `GithubSyncJob` for every matching, non-archived `Stack` on the (spoofed) branch, using an attacker-supplied `after` SHA as the "expected head": [8](#0-7) [9](#0-8) 

`GithubSyncJob` re-fetches the real commit history from GitHub for the victim stack via `stack.github_api`/`FirstParentCommitsIterator`, then appends new commits and (through `CacheDeploySpecJob`) triggers stack state recomputation; if `continuous_deployment` is enabled on the victim stack this results in an **unauthorized deploy trigger** originating entirely from a cross-tenant forged webhook. Other handlers keyed the same way (`pull_request` opened/labeled/closed/edited, `check_suite`, `status`, `commit_status`) similarly resolve their target via `repository.full_name` and can be pointed at any tracked repository regardless of which organization's secret signed the request — a cross-repository write/action across tenant boundaries, matching the "organization that authenticated versus the repository that is written" binding called out as in-scope.

This requires the Shipit instance to be configured in the multi-organization mode (`secrets.github` keyed by org names, exercised by `github_app_config`/`github_organizations`), and requires the attacker to control (administer) at least one organization already onboarded to that same Shipit instance so they possess a valid webhook secret to sign with — no `ApiClient` token, session, or GitHub App private key of Shipit itself is needed.

### Likelihood Explanation
Any organization admin already onboarded as a legitimate tenant can trivially craft this request with `curl`/a script — no special access to the victim org, no GitHub UI interaction, and no timing race is needed; only knowledge of their own webhook secret (which they configured) and the target's `owner/repo` name (often public knowledge) is required.

### Recommendation
After signature verification succeeds, independently derive the organization from the field(s) actually consumed by handlers (`repository.full_name`'s owner segment, or `organization.login`) and require it to equal the organization whose secret verified the signature. Reject the delivery (422) on mismatch, rather than trusting `repository.owner.login` alone as both the authentication key and treating `repository.full_name` as unrelated, independently-trusted data.

### Proof of Concept
1. Onboard/administer `attacker-org` on the target multi-tenant Shipit instance (legitimate tenant with a real webhook secret `S_attacker`).
2. Identify `victim-org/victim-repo`, a repository/stack already tracked by the same Shipit instance under a different organization.
3. Build a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, raw_body)>`.
5. POST to the webhooks endpoint with `X-Github-Event: push`.
6. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully against `S_attacker`.
7. `PushHandler` resolves the stack via `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` for the victim's stack, causing Shipit to sync (and, if continuous deployment is enabled, deploy) commits for a repository the attacker does not own or have webhook access to.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
