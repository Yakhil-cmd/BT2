### Title
CCMenu API endpoint bypasses per-token stack scoping, letting a stack-scoped API token read any stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces a binding between an `ApiClient`'s `stack_id` and the stacks it is allowed to touch: `stack_id == stack.id` for any client that is scoped to a single stack. `Shipit::Api::CCMenuController` overrides the `stack` lookup and breaks this binding, so a token scoped to one stack can read the CI status of every other stack.

### Finding Description
`BaseController#stacks` restricts the queryable set of stacks to the one referenced by `current_api_client.stack_id` when the client is scoped, falling back to `Stack.all` only for unscoped clients, and `BaseController#stack` resolves the requested stack through that scoped relation: [1](#0-0) 

`CCMenuController` inherits from `BaseController` and requires the generic `read:stack` permission, but it privately redefines `stack` to resolve directly against the unscoped `Stack` model instead of the scoped `stacks` relation: [2](#0-1) 

The binding that should hold for a scoped `ApiClient` is: `current_api_client.stack_id == params[:stack_id]-resolved-stack.id`. `BaseController#stack` enforces this by scoping the lookup through `stacks`; `CCMenuController#stack` (`Stack.from_param!(params[:stack_id])`) does not, so any `params[:stack_id]` value is resolved regardless of the authenticated client's `stack_id`.

### Impact Explanation
Any request bearing a valid (even narrowly stack-scoped) API token can request `GET /api/stacks/:stack_id/ccmenu` for an arbitrary `stack_id` and receive that other stack's latest deploy/rollback status (`deploys_and_rollbacks.last`), rendered via `shipit/ccmenu/project`. This is an authorization-boundary break: it converts a token that was explicitly restricted to one stack into a global reader of any stack's build/deploy state, matching the "unauthenticated/unauthorized read of stack state" impact class.

### Likelihood Explanation
The only requirement is possession of any valid API token that authenticates through `ApiClient.authenticate` and holds `read:stack` — including a token deliberately provisioned by an operator to be limited to a single stack (via `ApiClient#stack_id`). No privileged account, GitHub credentials, or webhook secret is needed; only substitution of the `stack_id` path/query parameter is required.

### Recommendation
Remove the `stack` override in `CCMenuController`, or reimplement it using the inherited scoped `stacks` relation (`stacks.from_param!(params[:stack_id])`) so the `current_api_client.stack_id` restriction is honored consistently with every other API endpoint in `Shipit::Api::BaseController`.

### Proof of Concept
1. Provision (or have provisioned) an `ApiClient` scoped to `Stack#1` (`stack_id = 1`, `permissions = ['read:stack']`), e.g. via the flow used by `CCMenuUrlController`: [3](#0-2) 
2. Using that token's Basic-Auth credentials, request `GET /api/stacks/2/ccmenu` where stack `#2` is a different, unrelated stack.
3. `BaseController#authenticate_api_client` succeeds and `require_permission :read, :stack` passes because the client holds `read:stack` generically.
4. `CCMenuController#stack` resolves `Stack.from_param!(2)` directly (bypassing `stacks.from_param!`), returning stack `#2` even though `current_api_client.stack_id == 1`.
5. The response renders stack `#2`'s latest deploy/rollback state, which the token was never authorized to see.
