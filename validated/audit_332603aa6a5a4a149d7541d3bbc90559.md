### Title
Cross-repository `Commit`/`Status` mutation via unscoped `Commit.where(sha:)` in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits globally by SHA with `Commit.where(sha: params.sha)` instead of scoping through the webhook's own verified `stacks` (as `PushHandler` and `CheckSuiteHandler` correctly do). Since GitHub commit `sha` values are only unique within a repository and the `commits` table index is `[stack_id, sha]` (not a global unique index on `sha`), any GitHub user who owns a repository can trigger a validly-signed `status` webhook for their own repo but with an arbitrary `sha` string, and the handler will mutate the `Commit`/`Status` rows of any other stack/repository whose commit happens to share that SHA.

### Finding Description
The broken binding is: `repository named in verified payload (payload.dig('repository','full_name'))` should equal `repository owning the Commit row(s) mutated by process`. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) only verifies that the raw body was signed by the GitHub App/webhook secret configured for `repository_owner` (`payload.dig('repository','owner','login')`), i.e. it authenticates "this payload legitimately originates from a status event on repo X owned by org O" — it does **not** constrain which `Commit` rows the handler is allowed to touch.

`Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) exists precisely to derive that authorized scope: `Repository.from_github_repo_name(repository_name)&.stacks`. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:14-16`) both correctly restrict their mutations to `stacks.where(...)`. `StatusHandler#process`, however, does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This query is completely unscoped by `stacks`/repository — it searches the entire `commits` table across every stack in the Shipit install.

Exploit flow: an attacker owns (or has push access to) any GitHub repository connected to the same Shipit instance (this is trivially satisfiable — Shipit is typically open to any repo an org onboards, and the attacker only needs *a* repo with a webhook, not the victim's). The attacker sets a commit status via the GitHub Statuses API (`POST /repos/:owner/:attacker_repo/statuses/:sha`) using an arbitrary `sha` value equal to a known commit SHA belonging to a victim's stack (git SHAs are content hashes and often observable — e.g., via the victim's public repo, PR, or Shipit stack UI). GitHub will legitimately sign and deliver this `status` webhook (since the event genuinely originates from the attacker's own, properly configured repo), so `verify_signature` passes. `StatusHandler#process` then runs `Commit.where(sha: attacker_chosen_sha)`, matches the victim's `Commit` row (because `sha` is not globally unique — only indexed as `[stack_id, sha]`, per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), and calls `commit.create_status_from_github!(params)` with attacker-controlled `state`/`context`/`description`/`target_url`. This flows into `Commit#add_status` (`app/models/shipit/commit.rb:366-386`), which emits `Hook.emit(:commit_status, ...)` and, critically, calls `stack.schedule_merges if new_status.pending? || new_status.success?` — letting an attacker inject a fabricated "success" CI status onto a victim's commit and trigger that victim stack's auto-merge logic, entirely from a webhook the attacker legitimately owns.

None of the existing guards close this gap: `verify_signature` only authenticates the origin org/repo of the payload, not the target of the mutation; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema for `StatusHandler` only validates types/presence of `sha`/`state`/etc., not their relationship to any repository; there is no `require_permission!`/`stacks` scoping check inside `StatusHandler#process` itself.

### Impact Explanation
An unprivileged attacker can inject a forged CI/status update onto a `Commit` belonging to an arbitrary victim repository/stack managed by the same Shipit instance, from a webhook triggered on a repository the attacker controls. This can flip the victim commit's simple status state and trigger `stack.schedule_merges`, i.e. cause the victim's merge queue to consider that commit deployable/mergeable based on a fabricated status — "a payload for one repository mutating another's stack, commit ... an unauthorized deploy, rollback or merge" (Critical). It is fully repeatable against any commit SHA the attacker can learn, across any number of tenants sharing the Shipit instance.

### Likelihood Explanation
Preconditions are minimal: the attacker needs (a) any GitHub repository with a `status` webhook wired to the target Shipit instance (a normal, unprivileged onboarding action many Shipit installs allow), and (b) knowledge of a target commit SHA in the victim stack (typically discoverable from public repos, PRs, or the Shipit UI itself). No Shipit session, API token, or GitHub secret is required — the attacker only ever authenticates their own repo's webhook, which GitHub signs for them legitimately. Cost is a single `POST` to GitHub's public Statuses API. This is trivially repeatable and requires no timing/race conditions.

### Recommendation
Scope the lookup in `StatusHandler#process` through the handler's own verified `stacks`, mirroring `PushHandler`/`CheckSuiteHandler`, e.g. `Commit.where(sha: params.sha, stack: stacks)` (or `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` via a join), so only commits belonging to the repository named in the verified payload can be mutated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub needed):

1. Create two stacks/repositories, `stack_a` (attacker-connected repo, e.g. `"attacker/repo"`) and `stack_b` (victim repo, e.g. `"victim/repo"`), each with a `Commit` sharing the same `sha` value (`"deadbeef" * 5`).
2. Build a `status` payload whose `repository.full_name` is `"attacker/repo"` (i.e., it would pass `verify_signature` in a real controller flow) but whose `sha` matches `stack_b`'s commit.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
4. Assert the binding is broken: `stack_b.commits.reload.find_by(sha: sha).status.state` changed to the attacker-supplied `state`, and `stack_b`'s commit's statuses now include the attacker's `context`/`description` — even though the verified payload only ever named `"attacker/repo"`, never `"victim/repo"`.
5. Contrast with `Commit.where(sha: sha, stack: Repository.from_github_repo_name("attacker/repo").stacks)` returning zero rows for `stack_b`'s commit, proving the unscoped query in production code is the exploitable primitive and that a `stacks`-scoped query would have returned no match, i.e. would not have mutated `stack_b`.
