### Title
`attestation[[...]]` formula getter in AA scripts returns attestation data without checking that it postdates the address's last definition change - (File: formula/evaluation.js)

### Summary
The `attestation[[attestors=..., address=...]]` getter used inside AA (Autonomous Agent) oscript formulas retrieves the most recent attestation matching an attestor/address pair without any check on whether the attested address's controlling definition (keys) has changed since the attestation was issued. This mirrors the reported CRL bug pattern: data that is meant to vouch for the current state of an identity/credential is consumed without validating that it is still relevant to the current holder of that credential, while a parallel, more careful code path in the same codebase (`storage.filterAttestedAddresses`, used by the `attested` definition operator and by asset issuer/spender attestation checks) explicitly filters out attestations made before the address's last key rotation.

### Finding Description
When validating address definitions/authentifiers, the `attested` opcode resolves via `storage.filterAttestedAddresses`, which only counts an attestation if it was made *after* the address's most recent `address_definition_changes` entry: [1](#0-0) 

This same freshness filter (`main_chain_index > IFNULL(last address_definition_change mci, 0)`) is applied for asset issuer/spender attestation checks: [2](#0-1) [3](#0-2) 

However, the `attestation[[...]]` getter available to AA formulas (a distinct, commonly-used mechanism for AAs to read attestation data, e.g. KYC/verification status, from oracle-style attestors) queries the `attestations`/`attested_fields` tables directly and returns the newest matching row, with no comparison against `address_definition_changes`: [4](#0-3) 

The SQL only filters by `attestor_address`, `address`, `field`, and `main_chain_index`/stability — there is no join or subquery against `address_definition_changes` the way `filterAttestedAddresses` has: [5](#0-4) 

This is the same root-cause pattern as the reported issue: one path (`getCrl`/`X509ChainBase.verifyCertChain`) trusts stored authorization/verification data without checking it is still tied to the current credential holder, while a "correct" validation pattern exists elsewhere in the same system (checking against the issuing/definition state) but is not applied consistently.

### Impact Explanation
AA authors routinely use `attestation[[...]]` to gate value transfers or state changes on identity/verification attestations (e.g., "release funds only if `attestation[[attestors=KYC_PROVIDER,address=trigger.address]].verified == 'yes'`"). Because the AA-formula getter does not exclude attestations that predate the address's most recent key rotation, an attestation issued while one key controlled the address remains usable by the AA logic after the address's definition (keys) has since changed — for example after the original key holder rotates away from a compromised or previously-attested key, or after a shared/multisig address's cosigner set is redefined. This can let an AA release or lock funds based on stale/irrelevant attestation state, i.e., it enables incorrect AA fund release decisions (fund loss to the AA or wrong beneficiary) whenever the AA's business logic relies on attestations remaining tied to the specific key material that was attested.

### Likelihood Explanation
Any AA author using `attestation[[...]]` for identity/verification gating is affected, and this is a documented, commonly used oscript feature, making the reach broad (any AA trigger sender interacting with such an AA). No special privilege is needed beyond triggering the AA after the address in question has undergone an ordinary `address_definition_change` — a normal, unprivileged action any address owner can perform. The fact that the codebase already implements the correct filter in a sibling code path (`filterAttestedAddresses`) confirms the developers recognize the risk of stale attestations surviving key rotation, but the AA-formula getter was not updated to apply the same protection.

### Recommendation
- Short term: Add the same `address_definition_changes` freshness filter used in `storage.filterAttestedAddresses` (main_chain_index of the attestation must exceed the main_chain_index of the address's most recent stable definition change) to the SQL queries in the `attestation` case of `formula/evaluation.js`.
- Long term: Consolidate the attestation-freshness logic into a single shared helper used by all three call sites (`definition.js` "attested" opcode, `validation.js` asset attestation checks, and `formula/evaluation.js` "attestation" getter) to prevent this kind of check from being missed in future additions, and document for AA authors that attestations are tied to a specific definition epoch of the attested address.

### Proof of Concept
1. Address `A` is controlled by key `K1`. An attestor `T` posts an attestation for `A` with field `verified=yes` (e.g. after KYC).
2. An AA `X` is deployed with logic such as: `if (attestation[[attestors=T, address=trigger.address]].verified == 'yes') { send funds to trigger.address }`.
3. The owner of `A` posts an `address_definition_change` message rotating control of `A` from `K1` to a new key `K2` (e.g., because `K1` was compromised, or ownership is effectively transferred through cooperative multisig/key handoff outside the attestor's knowledge).
4. A trigger unit signed by `K2` is sent to AA `X` from address `A`.
5. `attestation[[attestors=T, address=A]].verified` still evaluates to `yes` because `formula/evaluation.js` does not check that the attestation predates the definition change, even though the entity now controlling `A` was never verified by `T`.
6. AA `X` releases funds to `A` based on a verification claim that no longer reflects who currently controls the address — contrasted with the `attested` oscript operator/`filterAttestedAddresses`, which would correctly reject this same stale attestation in an address-definition context.
