### Title
Webhook signature verified against `repository.owner.login`'s app, but handlers act on the unrelated `repository.full_name` field, breaking the org-authentication↔repo-written binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once the signature passes, `Shipit::Webhooks::Handlers::Handler#repository_name` (and its subclasses) instead resolve the target `Repository`/`Stack` using a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`. Nothing enforces that these two fields refer to the same organization/repository, i.e. the field covered by the "authorization" decision (`repository.owner.login`) is not the field the rest of the pipeline trusts and acts on (`repository.full_name`).

### Finding Description [1](#0-0) 

`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 
`verify_webhook_signature` only checks that the raw body's HMAC matches the secret configured for that one organization — it says nothing about which repository the payload's other fields describe.

Downstream, every handler resolves the acted-upon repository from a **separate** field: [3](#0-2) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`Repository.from_github_repo_name` splits this string on `/` to get `owner`/`name` and looks the repo up purely by that string: [4](#0-3) 

In multi-organization deployments (documented feature, `config/secrets.yml` keyed per org, see `Shipit.github_app_config`), each org has its own GitHub App and `webhook_secret`: [5](#0-4) 

The binding that should hold is:
`organization used to select the verifying webhook_secret (repository.owner.login) == organization of the repository actually acted upon (repository.full_name)`

The code never checks this equality. Anyone who knows (or controls) the `webhook_secret` for **one** configured organization ("OrgA") can sign an arbitrary JSON body with that secret while setting `repository.owner.login = "OrgA"` (so `verify_signature` picks OrgA's app and passes) but `repository.full_name = "OrgB/some-repo"` (a completely different, unrelated org/stack managed by the same Shipit instance). `verify_signature` never inspects `full_name`, and the handlers never inspect `owner.login`, so the forged event is processed as if it legitimately originated from OrgB's repository.

### Impact Explanation
This is a cross-organization authorization boundary break equivalent to the underlying report's "verified field vs. acted-upon field" mismatch. Concretely:
- `StatusHandler#process` ( [6](#0-5) ) looks up commits purely `by sha`, globally, and calls `commit.create_status_from_github!(params)`; this can mark an arbitrary commit belonging to `OrgB`'s repo (any commit whose sha collides globally across the instance) as CI-`success`, influencing `deployable?`/continuous-deployment decisions for `OrgB`'s stacks despite the attacker only possessing `OrgA`'s webhook secret.
- `PushHandler#process` ( [7](#0-6) ) triggers `stack.sync_github` for whatever stacks match `repository_name`/`branch`, letting a holder of OrgA's secret force GitHub syncs on OrgB's stacks.
- `MembershipHandler` creates/manages `Team`/`Membership` records keyed by `params.organization.login`, which is not cross-checked against the org that authenticated the webhook either, potentially letting an OrgA-secret holder manipulate `Team`/`Membership` records claimed to belong to a different org string, indirectly affecting `Shipit.github_teams` authorization data.

This satisfies the required High-severity class ("escalation into `Shipit.github_teams` authorization" / unauthorized actions on stacks belonging to a repository never verified by the signature check) because the boundary crossed is exactly the credential-binding described in the rules: an organization that authenticated (via its own `webhook_secret`) versus the repository that is actually written/acted upon.

### Likelihood Explanation
Exploitability is gated by the attacker possessing at least one org's `webhook_secret` in a multi-org Shipit deployment (e.g., an org admin of a smaller/less-trusted org onboarded onto a shared Shipit instance who provisioned their own GitHub App webhook secret). This is a realistic scenario in the documented "Using Multiple Github Applications" setup, where distinct GitHub orgs are onboarded to a single shared Shipit instance with differing trust levels — precisely the setup this feature exists for. Given only the secret of one's own org, this bug lets that org forge events attributed to any other org's repository on the same instance.

### Recommendation
In `WebhooksController#verify_signature`, verify that the organization derived from `repository.owner.login` (or `organization.login`) matches the organization portion of `repository.full_name` (and any other org-identifying field used downstream) before dispatching to handlers, e.g.:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  verified &&= repository_owner.to_s.casecmp(repository_full_name_owner.to_s).zero?
  head(422) unless verified
end
```
Alternatively, have every `Handler` derive the repository/organization solely from the same field that was authenticated (`repository.owner.login`), and reject any event where `repository.full_name`'s owner segment disagrees with it. Add regression tests asserting that a valid signature from Org A cannot be used to process a payload whose `repository.full_name` belongs to Org B.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. As someone who knows `OrgA`'s `webhook_secret` (e.g., an OrgA admin who configured the GitHub App), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/private-stack" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and set `X-Github-Event: push`.
4. POST to `/github/webhooks`. `verify_signature` selects `Shipit.github(organization: "OrgA")`, validates successfully against the forged HMAC, and the request proceeds.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/private-stack")` and calls `stack.sync_github(expected_head_sha: ...)` on OrgB's stack — an action never authorized by OrgB's own webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
