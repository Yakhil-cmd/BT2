### Title
Cross-repository status forgery via unscoped commit lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to update by `sha` alone (`Commit.where(sha: params.sha)`) with no filtering by the repository that authenticated the webhook, unlike other handlers which scope through the `stacks` helper (`Repository.from_github_repo_name(repository_name)`). Because git commit SHAs are content-addressed and identical commits (e.g., shared/forked history) can exist verbatim in an attacker-owned repository and a victim's repository, an attacker who owns any repo connected to the Shipit instance can forge a `status` webhook, signed only with their own org's `webhook_secret`, that mutates the state of a commit belonging to a completely different, victim-owned stack.

### Finding Description
The broken binding: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` authenticates only that the payload was signed for `repository_owner` (attacker's org) [1](#0-0)  — the code assumes `repository_owner == owner of every record subsequently mutated by the handler`, but this equality is never enforced downstream.

`WebhooksController#create` dispatches the raw payload to all applicable handlers with no additional repository scoping [2](#0-1) . Most handlers scope their work through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository', 'full_name')` before touching any records [3](#0-2) . `StatusHandler#process`, however, bypasses this scoping entirely and queries commits globally:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

`Commit#create_status_from_github!` then unconditionally replicates the state into `statuses` and calls `add_status`, which — on a state transition to pending/success — invokes `stack.schedule_merges` and, via the `after_commit` callback chain on create/transition, drives `schedule_continuous_delivery` [5](#0-4) [6](#0-5) . `Commit#deployable?` only checks `!locked? && (stack.ignore_ci? || (success? && !blocked?))` — it has no notion of which repository authenticated the status [7](#0-6) , and `schedule_continuous_delivery` only checks `deployable? && stack.continuous_deployment? && stack.deployable?` before enqueuing `ContinuousDeliveryJob.perform_later(stack)` for the **victim's** stack [8](#0-7) .

Exploit flow: attacker owns/administers a repository (and its GitHub webhook secret) connected to the same Shipit instance. Attacker forks or otherwise obtains a commit whose SHA is identical to a commit sitting in a victim stack that is `continuous_deployment: true` and currently blocked by a pending/failing status on that shared commit. Attacker POSTs to `/webhooks` a `status` event body containing `sha: <shared_sha>, state: 'success', repository: {full_name: attacker/repo, owner: {login: attacker_org}}`, signed with the attacker org's own webhook secret. `verify_signature` succeeds (it only checks the attacker's own org secret). `StatusHandler#process` finds the commit row purely by `sha`, which matches the victim's stored commit, and flips its status to success, unblocking `next_commit_to_deploy` and triggering an unauthorized deploy of the victim's stack.

Existing guards do not stop this: `verify_signature` only checks the signature belongs to `repository_owner`, it never checks that `repository_owner` matches the owner of the `Stack`/`Commit` being mutated; `ExplicitParameters` only validates the shape of the payload, not repository ownership; `drop_unhandled_event` is irrelevant here since `status` is a handled event.

### Impact Explanation
An attacker with control of any repository/org onboarded onto the same Shipit instance can force a status transition — and consequently an unauthorized deploy — on a stack belonging to an unrelated repository/org, without ever authenticating for that repository. This is a payload-for-one-repository-mutates-another's-stack/commit case, and directly enables an unauthorized deploy, matching the **Critical** impact category. It is repeatable against any victim stack for which the attacker can obtain (or predict/reuse) a matching commit SHA, and the blast radius spans all tenants sharing the Shipit instance.

### Likelihood Explanation
Preconditions: (1) attacker owns a repository/org already connected to the target Shipit instance with a valid webhook secret (a realistic scenario for any multi-tenant/shared Shipit deployment); (2) attacker can produce or already has a commit whose SHA is identical to one sitting in the victim's stack — trivially achievable if the attacker forks the victim's public repository, since git commit SHAs are content-addressed and identical across forks; (3) the victim stack has `continuous_deployment: true` with a deploy currently blocked by that exact commit's status. Given these are all attacker-controllable or commonly-true conditions in shared instances, the attack is inexpensive and fully repeatable via ordinary `POST /webhooks` requests.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by `sha`/global identifiers) to the repository that authenticated the webhook, mirroring the `stacks`/`Repository.from_github_repo_name(repository_name)` pattern used elsewhere, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Commit.joins(:stack).merge(stacks)`, so a commit can only be mutated by a webhook whose signature was verified for the owning repository.

### Proof of Concept
Minitest under `test/models/shipit/webhooks/handlers/status_handler_test.rb` style (illustrative, not a literal existing test — reproduce logic locally):

```ruby
test "status event scoped to attacker repo does not mutate victim stack's commit/deploy" do
  victim_stack = shipit_stacks(:shipit)  # continuous_deployment: true, cached_deploy_spec present
  shared_sha = victim_stack.commits.last.sha
  victim_commit = victim_stack.commits.find_by(sha: shared_sha)
  victim_commit.statuses.create!(stack: victim_stack, state: 'pending')

  attacker_payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/other-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  before_deploy_count = Deploy.count

  # Simulate verify_signature succeeding for attacker-org (their own secret authenticated their own payload)
  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  victim_commit.reload
  assert_not_equal 'success', victim_commit.state,
    "commit belonging to victim stack must not transition on a payload authenticated only for attacker-org"
  assert_equal before_deploy_count, Deploy.count,
    "no deploy should be triggered on victim stack by attacker-authenticated payload"
end
```

Binding under test (before/after):
- Before: `repository_owner (attacker-org)` authenticates request == `owner(victim_stack.repository)` — **false**.
- Expected (fixed) behavior: `StatusHandler#process` only mutates commits where `commit.stack.repository == Repository.from_github_repo_name('attacker/other-repo')`, so `victim_commit.state` remains unchanged and `Deploy.count` remains unchanged.
- Actual (current) behavior: `Commit.where(sha: shared_sha)` matches `victim_commit` regardless of `repository_owner`, `victim_commit.state` becomes `'success'`, and `schedule_continuous_delivery`/`Stack#trigger_continuous_delivery` can enqueue/execute a deploy on `victim_stack` — confirming the vulnerability.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state

      end
      new_status
    end
