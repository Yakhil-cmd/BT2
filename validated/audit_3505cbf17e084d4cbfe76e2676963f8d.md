### Title
Cross-Organization Webhook Forgery via Unbound `repository_owner` Signature Check — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify a signature against by reading an untrusted field straight out of the *unverified* JSON payload (`repository.owner.login`, or `organization.login`), while every downstream `Webhooks::Handlers::Handler` subclass identifies the target repository/stack from a *different* payload field (`repository.full_name`). In a multi-organization deployment, any organization configured without a `webhook_secret` causes signature verification to be unconditionally bypassed, letting an attacker forge a webhook body whose "authenticated organization" field points at the secret-less org while its "acted-upon repository" field points at an arbitrary, unrelated stack.

### Finding Description
`verify_signature` derives the org used for the HMAC check from the raw payload before any cryptographic validation has occurred: [1](#0-0) [2](#0-1) 

That organization name is used to fetch the matching `GitHubApp` config and check the signature: [3](#0-2) 

Critically, `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the resolved organization has no `webhook_secret` configured: [4](#0-3) 

This is a supported, documented multi-org configuration (each org's app config, including an optionally blank `webhook_secret`, is set independently — see the fixture used for this exact scenario in `test/dummy/config/secrets_double_github_app.yml`, where `OrgTwo` has `webhook_secret: # nil`).

Once `verify_signature` passes (trivially, for the secret-less org), the actual event handlers never re-check that the "authenticated" organization matches the repository being mutated. They instead resolve the target purely from `repository.full_name`: [5](#0-4) [6](#0-5) [7](#0-6) 

This is exactly the binding break the report's bug class describes, translated to this engine: the report's `withdrawInterest` checks a *combined* balance (`totalInterest + totalInterestFromLiquidation`) but mutates only one bucket (`totalInterest`), letting the check and the effect diverge. Here, the *check* (signature verification) is scoped to `repository_owner`/`organization.login`, while the *effect* (which stack/commit gets mutated) is scoped to `repository.full_name` — an entirely independent field with no cross-validation that they refer to the same repository/org.

Concretely: `organization authenticated (repository_owner)` ≠ `repository written (repository.full_name)`.

### Impact Explanation
An unauthenticated, unprivileged internet attacker (no Shipit session, no `ApiClient` token, no GitHub App private key, no webhook secret) who merely knows the name of one organization in the deployment that has no `webhook_secret` set can:

- Send a forged `X-Github-Event: status` webhook with `organization.login`/`repository.owner.login` set to the secret-less org, but `sha` and `state: "success"` targeting a commit belonging to a *different, security-critical* stack. `StatusHandler#process` will call `commit.create_status_from_github!(params)` for any `Commit` matching that SHA anywhere in the install, forging a green CI status on a commit that never actually passed CI. If that stack gates deploys on `ci.require` checks, this can enable an **unauthorized deploy** of unreviewed code.
- Send a forged `push` event the same way to force `stacks.sync_github(expected_head_sha: ...)` against an arbitrary stack's branch, influencing which commits are considered "head" for deploy purposes.

This satisfies the "High" impact bar (escalation past an authorization/authentication boundary enabling unauthorized deploy actions) with a very low likelihood barrier, since the attacker doesn't need any credentials — only knowledge/discovery of one secret-less org name, which is itself discoverable via a signature-check oracle (payloads with different `organization.login` guesses return 422 vs 200/204).

### Likelihood Explanation
Requires: (1) the deployment runs a multi-organization GitHub App configuration (a documented, supported feature — `secrets.github` keyed by org, per `github_app_config`), and (2) at least one configured organization has a blank `webhook_secret`. This is plausible in real deployments (e.g., staging/onboarding orgs, or orgs added without yet wiring a secret) and is directly exercised in the engine's own test fixtures (`test/dummy/config/secrets_double_github_app.yml`), confirming the code path is real and reachable, not merely theoretical. The webhook endpoint is public and unauthenticated by design (`skip_before_action :verify_authenticity_token`), so no other barrier stands in the way once the secret-less org is identified.

### Recommendation
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in a multi-organization configuration; either require a secret for every configured organization or fail closed.
- Cross-validate that the organization used to select the verification secret matches the owner embedded in `repository.full_name` (and any other repository-identifying fields the handlers use) before dispatching to handlers.
- Consider deriving the "trusted organization" for a request from the same field that handlers use to select the target stack, so the same untrusted payload segment cannot be split between the "checked" side and the "acted upon" side.

### Proof of Concept
1. Deploy Shipit with a multi-org GitHub App config where `OrgTwo` has `webhook_secret: nil` (mirrors `test/dummy/config/secrets_double_github_app.yml`) and `OrgOne` (or any other org) has a real stack/commit that gates deploys on CI (`ci.require`).
2. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
   ```json
   {
     "sha": "<target commit sha belonging to OrgOne's stack>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "full_name": "OrgOne/production-app", "owner": { "login": "OrgTwo" } }
   }
   ```
   No `X-Hub-Signature` header value is required to be valid — `repository_owner` resolves to `"OrgTwo"`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`).
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) looks up `Commit.where(sha: params.sha)` — matching the OrgOne commit — and calls `create_status_from_github!`, forging a passing CI status unrelated to `OrgTwo`.
4. If OrgOne's stack requires that CI context to deploy, the forged status can unblock/trigger an unauthorized deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
