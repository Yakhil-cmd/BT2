### Title
Cross-organization signing binding is not enforced against `organization.login`/`team.id` in `membership` webhooks - MembershipHandler mutates Team/Membership state signed by a different organization ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the signing `GitHubApp` solely from `params.dig('repository','owner','login')` (falling back to `organization.login`), but for `membership` events these two fields can diverge because `repository` is attacker-controlled while `Shipit::Webhooks::Handlers::MembershipHandler` trusts `params.organization.login` and `params.team.id` independently to create/select `Team` records and add/remove `Membership` rows. An attacker who controls a repository/org with its own configured `webhook_secret` on the same Shipit instance can sign a `membership` payload with `repository.owner.login` set to their own org (so the signature check passes against their own `GitHubApp`/secret), while setting `organization.login` and `team.id` to values belonging to a completely different, victim organization.

### Finding Description
The intended binding is: **organization verifying the HMAC (`repository_owner`, i.e. `params.dig('repository','owner','login')`) == organization whose `Team`/`Membership` state is mutated (`params.organization.login` / `Team#organization` for the `github_id` referenced by `params.team.id`)**.

Tracing the code:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) fetches `github_app = Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` using that app's `webhook_secret` (`lib/shipit/github_app.rb:76-83`). `repository_owner` is defined as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`).
- Once signature verification passes, `WebhooksController#create` parses the raw body again and dispatches to `Shipit::Webhooks::Handlers::MembershipHandler.call(params)` (`app/controllers/shipit/webhooks_controller.rb:10-15`, `app/models/shipit/webhooks.rb:20`).
- `MembershipHandler#process` and `#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`) use `params.team.id` (as `github_id`) and `params.organization.login` (as `Team#organization`) — completely independent fields from `repository.owner.login` — to locate/create the `Team` and then call `team.add_member(member)` / `team.members.delete(member)`.
- Because `repository.owner.login` is present in the payload, the fallback to `organization.login` in `repository_owner` is never triggered when `repository` is included, so nothing forces `repository.owner.login == organization.login`. The controller and `MembershipHandler` schema (`ExplicitParameters`) never cross-check these two identifiers.

Attack: attacker owns/controls an org (`attacker-org`) whose `webhook_secret` is configured in this Shipit instance (a legitimate, if unprivileged, tenant on a multi-org Shipit deployment). They compute a valid `X-Hub-Signature` using `attacker-org`'s secret over a body where `repository.owner.login = "attacker-org"` but `organization.login = "shopify"` and `team.id = <victim's real Team#github_id>`. `verify_signature` resolves and validates against `attacker-org`'s `GitHubApp`, succeeds, and the request proceeds to `MembershipHandler`, which finds the existing victim `Team` by `github_id` and adds the attacker-chosen `member.login` as a member — or, if the team doesn't yet exist, creates a `Team` row with `organization: "shopify"` under an ID chosen by the attacker.

Existing guards do not prevent this: `verify_signature` only checks that *some* known org's secret was used, not that the org verifying matches the org referenced inside the payload for team/membership mutation; `find_or_create_team!`'s `ExplicitParameters` schema (`app/models/shipit/webhooks/handlers/membership_handler.rb:7-21`) only validates types/presence, not cross-consistency with `repository_owner`.

### Impact Explanation
A successful request lets an unprivileged attacker who merely controls their own onboarded org/webhook_secret write into another organization's `Team`/`Membership` authorization state (`Shipit::Team`, `Shipit::Membership`), potentially adding a user (including the attacker's own GitHub login) to a victim team. If that team is referenced by `Shipit.github_teams` for authorization purposes, this becomes escalation into privileged Shipit roles for a different tenant — matching "High: escalation into `Shipit.github_teams` authorization" or, if it enables an unauthorized deploy/merge via team-based ACL, "Critical: unauthorized deploy". The attack is repeatable against any org/team whose numeric `github_id` the attacker can guess or learn, and the blast radius spans every organization configured on the shared Shipit instance, since the trust boundary between tenants (`GitHubApp` webhook secrets) is not honored by the handler's write path.

### Likelihood Explanation
This requires the Shipit instance to host multiple orgs (multi-tenant `Shipit.github` configuration) and the attacker to control at least one org that is a legitimate registered tenant with its own `webhook_secret` — a precondition explicitly allowed by the threat model here (attacker is "any GitHub user" controlling their own repo, not necessarily a Shipit operator). No Shipit secrets are required: the attacker uses their own legitimate secret to sign, and only needs to know or guess the victim's numeric `Team#github_id` (an easily discoverable GitHub team ID) and org login (public). Cost is a single crafted HTTP POST to `/webhooks`; it is trivially repeatable.

### Recommendation
In `WebhooksController#verify_signature` (or in `MembershipHandler`), enforce that the organization used to select/verify the signing `GitHubApp` matches the organization referenced by the event body being mutated — e.g., require `params.dig('repository','owner','login') == params.dig('organization','login')` for `membership` events, and additionally validate that any `Team` found by `github_id` belongs to the same `organization` as the verified signer before mutating membership. Reject the webhook (422) on mismatch.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":membership signed by attacker org mutates a different organization's team" do
  attacker_org = 'attacker-org'
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: X

  Shipit.stubs(:github).with(organization: attacker_org).returns(
    Shipit::GitHubApp.new(attacker_org, webhook_secret: 'attacker-secret')
  )

  body = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: 'https://example.com' },
    organization: { login: 'shopify' },      # victim org, mismatched vs repository.owner.login
    member: { login: 'mallory' },
    repository: { owner: { login: attacker_org } } # used only for signature verification
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', body)}"

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  assert_difference -> { victim_team.memberships.count }, 1 do
    post :create, body:, as: :json
    assert_response :ok
  end
  # Binding violated: repository_owner == 'attacker-org' (signer), but Team#organization == 'shopify' was mutated.
end
```
This demonstrates the signer (`attacker-org`) and the mutated organization (`shopify`) diverge, and the write succeeds despite the mismatch.
