### Title
Cross-repository forgery of GitHub `status` webhooks writes commit statuses onto arbitrary stacks - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table instead of scoping the lookup to the repository that authenticated the webhook, unlike other handlers which use the `Handler#stacks` helper. An attacker who owns any GitHub repository/organization can send a validly-signed `status` webhook for their own repo but with a `sha` that also exists as a commit row in a victim's stack (e.g. a shared ancestor commit from a fork, or any stack that happens to contain that SHA), causing a `Status` record (with attacker-chosen `context`/`state`, e.g. `context: review/approved`, `state: success`) to be written against the victim's commit/stack.

### Finding Description
The broken binding: the code assumes `signature_valid_for(repository_owner) == commit_belongs_to(repository_owner)`, i.e., that a webhook whose signature is verified for organization `X` can only affect commits/stacks belonging to repositories owned by `X`. In fact these are not equal.

- `WebhooksController#verify_signature` only checks that the payload signature matches the GitHub App/organization identified by `params.dig('repository','owner','login')` [1](#0-0) . It does not constrain which `sha` or which stacks the handler may touch.
- The base `Handler` class provides a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, i.e., only stacks belonging to the repository named in the payload [2](#0-1) .
- `StatusHandler#process`, however, does **not** use this `stacks` scope. It queries `Commit.where(sha: params.sha)` directly, across the whole `commits` table (all repositories/stacks), and calls `commit.create_status_from_github!(params)` on every match: [3](#0-2) .
- `Commit#create_status_from_github!` creates a `Status` scoped to `commit.stack_id` (the commit's actual owning stack, not the requester's), and that write can flip `state`/`simple_state` and trigger merge scheduling: [4](#0-3)  and [5](#0-4) .

Exploit flow: attacker sends `POST /webhooks` with `X-Github-Event: status`, a body whose `repository.full_name`/`repository.owner.login` is the attacker's own repo (so `verify_signature` passes using the attacker's own valid app credentials/signature for their own org), and `sha` set to a commit hash that is also present as a `Commit` row in a victim stack (commits table is keyed unique on `(sha, stack_id)`, so the same SHA can legitimately exist in multiple stacks, e.g. shared ancestor commits between a fork and upstream, or monorepo/mirrored repos tracked by multiple Shipit stacks). Because `StatusHandler` does not scope by repository, `Commit.where(sha: params.sha)` returns the victim's commit row too, and a `Status` with `context: review/approved`, `state: success` gets created against the victim stack's commit — regardless of the fact that the attacker's signature only authenticated their own, unrelated repository.

None of the existing guards catch this: `verify_signature`/`GithubApp#verify_webhook_signature` only validate that the payload came from the org named inside the payload itself (which the attacker controls and owns) [6](#0-5) ; `drop_unhandled_event` and the `ExplicitParameters` schema only validate presence/type of `sha`/`state`/`context`, not repository ownership [7](#0-6) ; and the `stacks` scoping helper that would prevent this is simply unused by this handler.

### Impact Explanation
A successful exploit lets an attacker write a `Status` row (arbitrary `context`, `state`, `description`, `target_url`) onto a commit belonging to a stack/repository they do not own and never authenticated a webhook for. If the victim stack requires a `review/approved`-style status as part of its `required_statuses`/CI gating, injecting `state: success` for that context can flip the commit's simple state to "success", which per `Commit#add_status` schedules merge processing (`stack.schedule_merges`) and fires `deployable_status` hooks — i.e., it can make an otherwise-blocked commit appear deployable/mergeable, or conversely inject a `failure`/`error` to block a legitimate deploy. This is a payload for one repository mutating another repository's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Preconditions: the attacker needs (a) a GitHub repository/org they control (to pass `verify_signature`, which is trivial — any GitHub user can create a repo and install/trigger a status webhook, or directly POST a crafted payload if they can produce a signature valid for their own org's configured secret), and (b) a `sha` value that also exists as a `Commit` record in the victim stack. The latter is realistic in common topologies: forks of a shared upstream, mirrored/multiple-stack tracking of the same repository, or monorepos — all commonly produce identical SHAs recorded across multiple `Stack`/`Repository` rows. No Shipit session, API token, or GitHub team membership is required, making this reachable by a fully unprivileged internet attacker, and it is repeatable against any stack sharing a SHA with the attacker's repo.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring other handlers: replace `Commit.where(sha: params.sha)` with a lookup restricted to `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }` (using the inherited `stacks` helper), so a `status` webhook can only ever create/update `Status` rows for commits belonging to stacks of the repository named (and cryptographically authenticated) in that same payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook for repo A cannot write a status onto a commit belonging to repo B's stack" do
  victim_stack = shipit_stacks(:shipit) # belongs to repository "shopify/shipit-engine" (repo B)
  shared_sha = "deadbeefcafebabefeed1234567890abcdef1234"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                                committer: shipit_users(:walrus),
                                                authored_at: Time.now, committed_at: Time.now,
                                                message: "shared ancestor")

  attacker_payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'review/approved',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  # BEFORE: victim_commit has no review/approved status
  assert_nil victim_commit.statuses.find_by(context: 'review/approved')

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  # AFTER: assert the equality "authenticated repo == affected stack's repo" is violated
  forged_status = victim_commit.reload.statuses.find_by(context: 'review/approved')
  assert_not_nil forged_status, "expected no cross-repo write, but attacker's webhook created a status"
  assert_equal 'success', forged_status.state
end
```
Expected (buggy) result: the test shows the forged `review/approved` `success` status is created on `victim_stack`'s commit even though the webhook payload's `repository.full_name` was `attacker/unrelated-repo`, proving the cross-repository write. After applying the recommended fix (scoping via `stacks`), the assertion `assert_not_nil forged_status` would fail, confirming the vulnerability is closed.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      end
      new_status
    end
