### Title
Forged `membership` webhook verified by a no-secret organization mutates an arbitrary org's `Team`/`User` membership - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` to validate a webhook's signature by looking at `repository.owner.login` (falling back to `organization.login`), and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's configured `webhook_secret` is blank. `Shipit::Webhooks::Handlers::MembershipHandler`, however, does not use `repository.owner.login` at all — it creates/finds the `Team` and mutates membership using `params.organization.login` and `params.team.id`, fields fully controlled by the attacker inside the same JSON body. This lets an attacker who knows only that some configured org has no `webhook_secret` forge a `membership` event that is "verified" against that org but writes team membership for a completely different org.

### Finding Description
The broken binding: the organization whose `webhook_secret` authenticated the request should equal the organization whose `Team`/membership records are mutated by the handler. Concretely, `repository_owner` (used to pick the `GitHubApp` for signature verification in `verify_signature`) should equal `params.organization.login` (used by `MembershipHandler#find_or_create_team!` to set `team.organization` and to look up `github_id`).

Code path:
- `app/controllers/shipit/webhooks_controller.rb:24-30` — `verify_signature` calls `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) 
- `repository_owner` is derived purely from attacker-controlled JSON: `params.dig('repository','owner','login') || params.dig('organization','login')`. [2](#0-1) 
- `lib/shipit/github_app.rb:76-83` — `verify_webhook_signature` short-circuits: `return true unless webhook_secret`. If the org picked by `repository_owner` has no `webhook_secret` configured, **any** body/signature pair is accepted. [3](#0-2) 
- `app/models/shipit/webhooks/handlers/membership_handler.rb:22-43` — once accepted, the handler uses `params.team.id` to find/create a `Team`, sets `team.organization = params.organization.login`, resolves `User.find_or_create_by_login!(params.member.login)`, and then calls `team.add_member(member)` or `team.members.delete(member)` depending on `params.action`. [4](#0-3) 
- `app/models/shipit/team.rb:41-43` — `add_member` appends the member to `members` unconditionally. [5](#0-4) 
- `app/models/shipit/user.rb:80-82` — `User#authorized?` is gated by `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, i.e., exactly the membership rows the handler just wrote/deleted. [6](#0-5) 

Root cause: `repository_owner` (verification key) and `params.organization.login`/`params.team.id` (mutation key) are two independent, attacker-supplied fields with no cross-check that they refer to the same organization. Because signature verification for the no-secret org is a no-op, an attacker needs no secret at all to pass `verify_signature`, then can point the rest of the payload at any other configured org's team.

Existing guards do not prevent this:
- `drop_unhandled_event` only checks that a handler exists for the `X-Github-Event` header; it does not validate payload consistency.
- `ExplicitParameters` schema in `MembershipHandler.params` only validates types/presence of `action`, `team.id/name/slug/url`, `organization.login`, `member.login` — it does not cross-check against `repository.owner.login` or the org used for verification.
- `verify_signature` rescues `Shipit::GithubOrganizationUnknown` (unknown org → 422), but a **known, configured-but-secretless** org passes cleanly with `verified = true`.

Attacker request: `POST /webhooks` with `X-Github-Event: membership`, any `X-Hub-Signature` value (ignored because `webhook_secret` is blank), and a JSON body where `repository.owner.login` (or `organization.login` used as the verification fallback) is set to the no-secret org, while the body's `organization.login` and `team.id` reference a different, secret-protected org's real team, and `member.login` is the attacker's own GitHub login with `action: "added"`.

### Impact Explanation
A successful forgery adds (or removes) a `Membership` row linking an arbitrary GitHub login to an arbitrary `Team` belonging to a different, secured organization — without ever presenting that organization's `webhook_secret`. If that team's `github_id` is among `Shipit.github_teams`, the attacker (or anyone they add) satisfies `User#authorized?` and gains whatever permissions Shipit grants to authorized users (e.g., deploy/rollback approval gates depending on `require_permission!` usage elsewhere). This is a cross-tenant authorization bypass: a payload nominally scoped to one (unprotected) organization mutates state for a completely different, protected organization's team — matching the Critical category "a payload for one repository mutating another's stack, commit, task, or team" / authentication-authorization bypass. It is repeatable against any org's team as long as the attacker knows (a) any configured org with a blank `webhook_secret`, and (b) the target team's `github_id`.

### Likelihood Explanation
Preconditions: Shipit must have at least one configured GitHub organization (`Shipit.github(organization: ...)` config) whose `webhook_secret` is blank/unset — a realistic misconfiguration since `docs/setup.md`/`template.rb` show `webhook_secret` as an optional field per-org, and multi-org Shipit deployments are supported (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`). The attacker needs no credentials, only knowledge that such an org exists (observable from public webhook endpoint behavior/error codes, or just guessing common org setups) and the target team's `github_id` (obtainable via public GitHub API for the target org's teams, if the org/teams are public, or brute force since `github_id` is a small integer). Cost is a single crafted HTTP POST with no cryptographic material required. This is fully repeatable and requires no privileged access.

### Recommendation
- In `Shipit::WebhooksController#verify_signature`, do not treat a blank `webhook_secret` as automatically verified; either require every configured organization to have a `webhook_secret`, or explicitly reject/flag webhooks for orgs without one instead of silently trusting them.
- Cross-check that the organization used to select the verifying `GitHubApp` (`repository_owner`) matches the organization referenced by the payload processed by the handler (`params.organization.login` in `MembershipHandler`, and analogous fields in other handlers) before allowing any writes.
- In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` equals the org whose secret validated the webhook (pass the verified org down from the controller) before creating/updating a `Team` or adding/removing `Membership` rows.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_membership_forgery_test.rb
require 'test_helper'

module Shipit
  class WebhooksControllerMembershipForgeryTest < ActionDispatch::IntegrationTest
    setup do
      # Org A: configured with NO webhook_secret (misconfiguration under test)
      Shipit.stubs(:github).with(organization: 'org-a').returns(
        Shipit::GitHubApp.new('org-a', {}) # no webhook_secret key
      )
      # Real protected team belonging to a different org, "org-b"
      @team = Team.create!(organization: 'org-b', slug: 'secure-team', name: 'Secure Team',
                            github_id: 4242, api_url: 'https://api.github.com/teams/4242')
      Shipit.stubs(:github_teams).returns([@team])
    end

    test 'membership event verified against org-a mutates org-b team membership' do
      body = {
        action: 'added',
        team: { id: @team.github_id, name: @team.name, slug: @team.slug, url: @team.api_url },
        organization: { login: 'org-b' },       # actual org being mutated
        member: { login: 'attacker' },
        repository: { owner: { login: 'org-a' } } # org used for signature verification (no secret)
      }.to_json

      post '/webhooks', params: body,
           headers: { 'X-Github-Event' => 'membership', 'X-Hub-Signature' => 'sha1=deadbeef',
                      'Content-Type' => 'application/json' }

      assert_response :ok
      attacker = User.find_by(login: 'attacker')
      assert attacker.present?
      assert @team.members.reload.include?(attacker),
             "attacker should NOT be added to org-b's team via a webhook verified under org-a's (secretless) config"
      assert attacker.authorized?, 'attacker gained authorization via forged cross-org membership webhook'
    end
  end
end
```
Both sides of the binding: `repository_owner` (`"org-a"`, unauthenticated/no-secret) vs. `params.organization.login`/`team.organization` (`"org-b"`, the org actually mutated) diverge after the request — proving the vulnerability.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
