### Title
Unchecked `os.RemoveAll` return value on legacy worktree cleanup allows attacker-controlled file permissions to cause silent, persistent disk leak / sync denial - (File: main.go)

### Summary
The upstream report is about a Solidity `payable(msg.sender).call{value:wad}("")` whose boolean success return is discarded, silently swallowing a failure and leaving funds stuck. The structural analog in `git-sync` is the discarded error return of `os.RemoveAll(currentWorktree.Path().String())` in `repoSync.SyncRepo`, a low-level OS operation whose failure is never checked, silently swallowing a failure and leaving stale, undeletable worktree data on disk.

### Finding Description
In `SyncRepo`, after a successful publish, git-sync attempts a best-effort cleanup of an old (pre-migration) worktree path: [1](#0-0) 
The call `os.RemoveAll(currentWorktree.Path().String())` at line 1992 does not check or capture the returned `error`. This is functionally identical to the reported pattern: a low-level, potentially-failing system call (`call{value}` in Solidity, `os.RemoveAll` here) whose failure signal is discarded, letting execution continue as if the operation had succeeded.

By contrast, the dedicated `removeWorktree` helper used elsewhere in the same file *does* check this error and propagates it: [2](#0-1) 

Because the checked-out worktree content originates from the remote repository, an attacker who can push a commit (the untrusted-content threat model for this scan) can commit files/directories with restrictive permissions (e.g., a subdirectory with mode `0000`, or a file marked read-only in a way that prevents unlink within its parent) that get materialized into the worktree via `git worktree add`. If such a tree later becomes the "old" worktree that this code path attempts to delete, `os.RemoveAll` can partially fail (some children may resist removal due to permission bits), and that failure is dropped on the floor at line 1992 — the sync loop proceeds as if cleanup succeeded.

### Impact Explanation
Because the error is discarded, the directory (or remnants of it) is left behind under `--root` outside of any further remediation attempt, and no failure is logged or surfaced to the operator/metrics. Repeated occurrences (e.g., a repeatedly-updated malicious ref, or repeated crash/upgrade cycles hitting this legacy-path branch) accumulate un-removable directories under `--root`, consuming disk space over time. Since `--root` must remain usable for git operations, unbounded disk growth from stuck worktree remnants can eventually degrade or deny the sync loop (disk exhaustion), satisfying the "persistent sync denial" impact class. This is a lower-severity analog than the original funds-locking bug (no code execution or credential exposure), but it is a genuine unprivileged-attacker-reachable, silently-swallowed low-level call failure in a security-relevant code path (filesystem cleanup under `--root`).

### Likelihood Explanation
This path is only reached in a narrow migration scenario — `currentHash != "" && currentWorktree != git.worktreeFor(currentHash)` — i.e., when git-sync detects it is dealing with a worktree path from a prior version's naming scheme. It requires: (1) the operator to be running/upgrading from a legacy layout, and (2) the attacker to have pushed a commit containing hard-to-delete file permissions before that worktree became "current". This makes the likelihood low-to-moderate: it is not triggered on every sync, and the impact (disk growth) is gradual, not immediate.

### Recommendation
Check and handle the error from `os.RemoveAll` at main.go:1992, e.g.:
```go
if err := os.RemoveAll(currentWorktree.Path().String()); err != nil {
    git.log.Error(err, "can't remove legacy worktree", "path", currentWorktree.Path())
}
```
At minimum, log the failure (as is done elsewhere, e.g. the `touch` error handling immediately above at lines 1966-1969) so operators have visibility into stuck directories, and consider making this fatal or metric-tracked so persistent cleanup failures are observable rather than silently ignored, consistent with how `removeWorktree` already treats `os.RemoveAll` errors as first-class.

### Proof of Concept
Not independently executable from static review alone; the sequence of conditions is: (1) attacker pushes a commit containing a subtree with permissions that resist deletion (e.g., a directory chmod'd to `0000` before adding children, so `os.RemoveAll` cannot list/unlink it) via a ref git-sync tracks, (2) the worktree gets synced and later superseded, (3) the migration-cleanup branch at main.go:1989-1993 is hit for that worktree, and (4) `os.RemoveAll`'s failure is dropped, leaving orphaned directories under `--root` indefinitely. Full confirmation would require running `git-sync` against a crafted repo and a legacy on-disk layout to trigger the exact branch condition at line 1989; this was not runnable in this read-only review, so likelihood/precise reachability of the "legacy path mismatch" branch under current versions is an area of residual uncertainty.

```go
// removeWorktree is used to remove a worktree and its folder.
func (git *repoSync) removeWorktree(ctx context.Context, worktree worktree) error {
	// Clean up worktree, if needed.
	_, err := os.Stat(worktree.Path().String())
	switch {
	case os.IsNotExist(err):
		return nil
	case err != nil:
		return err
	}
	git.log.V(1).Info("removing worktree", "path", worktree.Path())
	if err := os.RemoveAll(worktree.Path().String()); err != nil {
		return fmt.Errorf("error removing directory: %w", err)
	}
	if _, _, err := git.Run(ctx, git.root, "worktree", "prune", "--verbose"); err != nil {
		return err
	}
	return nil
}
```
