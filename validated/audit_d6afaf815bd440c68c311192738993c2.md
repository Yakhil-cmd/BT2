The CVE-2021-21415 pattern requires an unprivileged, remote-triggerable configuration value (a binary path) to be executed by client tooling. Searching the Polkadot SDK for analogous "execute configured binary path" logic only surfaces node-operator-controlled paths: PVF worker binary discovery in `polkadot/node/service/src/workers.rs` (`determine_workers_paths`, `list_workers_paths`) [1](#0-0) , the worker spawning code in `polkadot/node/core/pvf/src/worker_interface.rs` (`spawn_with_program_path`, `WorkerHandle::spawn`) [2](#0-1) , the security-check process spawning in `polkadot/node/core/pvf/src/security.rs` (`spawn_process_for_security_check`) [3](#0-2) , and build-fixture compiler invocation in `substrate/frame/revive/fixtures/src/builder.rs` (`compile_with_standard_json`) [4](#0-3) .

All of these paths are set via CLI flags, environment variables, or local build configuration chosen by the node operator or developer at startup/build time — none are reachable through a signed extrinsic, an enabled contract call, an XCM message, or any other unprivileged on-chain entry point as required by the threat model. There is no equivalent to the VSCode `.vscode/settings.json`-driven, per-project, attacker-supplied binary path that gets auto-executed on a benign user action; nothing in the runtime/PVF/executor code path allows an on-chain caller to influence which executable is spawned by a node. Since the required "real user entry" (signed extrinsic / contract call / XCM) reaching an attacker-influenced binary execution does not exist, this bug class does not have a demonstrable analog in the scanned production code.
