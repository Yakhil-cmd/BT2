This confirms the write path: `ReviewStackAdapter#create!` calls `scope.create!(stack_attributes)` where `scope` is `repository.review_stacks` — i.e., an association scoped to whatever `Repository` row `from_github_repo_name(params.repository.full_name)` returned [1](#0-0) . That repository lookup is driven entirely by the `repository.full_name` string, independent of the `repository.owner.login`/`organization.login` field used by `verify_signature` to pick which org's `webhook_secret` to check against [2](#0-1) [3](#0-2) .

### Title
Signature-authenticated organization is decoupled from the repository actually mutated, allowing cross-tenant ReviewStack creation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/org config (and thus which `webhook_secret`) to validate the request against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Every `PullRequest` handler (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`) instead resolves the `Repository` acted upon via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, a completely separate JSON field. Because these two fields are independently attacker-controlled in the raw JSON body, and because the signature check only fails to protect requests when the resolved org has no `webhook_secret` configured (`return true unless webhook_secret`), an attacker can pick an org with no secret for `repository.owner.login`/`organization.login` while setting `repository.full_name` to an existing repository owned by a different, real (victim) organization, causing a `ReviewStack` (and its `Stack`/`PullRequest` records) to be created under the victim organization's real `Repository`.

### Finding Description
The intended (but unenforced) binding is:
`repository_owner (used in verify_signature)` == `Repository#owner` of the record loaded by `from_github_repo_name(params.repository.full_name)`.

Tracing the code:
- `WebhooksController#repository_owner` reads `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [4](#0-3) .
- `verify_signature` calls `Shipit.github(organization: repository_owner)` and then `verify_webhook_signature`, which is a no-op returning `true` whenever that org's config has no `webhook_secret` set: `return true unless webhook_secret` [5](#0-4) .
- After signature "verification" passes, every `pull_request.*` handler resolves the repository purely from `params.repository.full_name`, splitting on `/` and doing `find_by(owner:, name:)` — with no reference at all to `repository.owner.login`/`organization.login` used above: `def self.from_github_repo_name(github_repo_name); repo_owner, repo_name = github_repo_name.downcase.split('/'); find_by(owner: repo_owner, name: repo_name); end` [2](#0-1) .
- `OpenedHandler#repository` (and the closed/reopened/labeled/unlabeled/label-capturing handlers) use that lookup result to scope `ReviewStackAdapter`, e.g. `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [6](#0-5) .
- `ReviewStackAdapter#create!` writes `scope.create!(stack_attributes)` — i.e. `repository.review_stacks.create!`, tying the new `Stack`/`ReviewStack` row to whichever `Repository` `from_github_repo_name` returned [1](#0-0) .

Exploit flow (given a multi-org Shipit deployment, or a single-org deployment, where at least one configured org has no `webhook_secret` — a state the shipped example configs explicitly show as the default, `webhook_secret: # nil` [7](#0-6) ):
1. Attacker POSTs directly to `/webhooks` (`repository_owner authenticated`) with `X-Github-Event: pull_request`, no valid `X-Hub-Signature` needed.
2. Body sets `repository.owner.login` (or `organization.login`) to `attacker-controlled-org-with-no-secret`, but `repository.full_name` to `"victim-org/victim-repo"` — an existing `Shipit::Repository` row that is fully provisioned (`review_stacks_enabled`, `provisioning_behavior_allow_all?`).
3. `verify_signature` resolves `Shipit.github(organization: "attacker-controlled-org-with-no-secret")`; since that org's `webhook_secret` is unset, `verify_webhook_signature` returns `true` unconditionally, regardless of the actual header value.
4. `OpenedHandler#repository` loads the real `victim-org/victim-repo` `Repository` row via `from_github_repo_name`, completely ignoring the org used for signature verification.
5. `provision?` evaluates true against the victim repo's real provisioning settings, and `find_or_create!` writes a new `Stack`/`ReviewStack`/`PullRequest` under the victim's `Repository`.

No existing guard closes this gap: `verify_signature` never compares its chosen org to the owner encoded in `full_name`; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `OpenedHandler` only requires `repository.full_name` be a `String` with no consistency check against `repository.owner.login` [8](#0-7) ; and `Repository` model validations only constrain format/uniqueness of `owner`/`name` on write, not cross-request consistency [9](#0-8) .

### Impact Explanation
An attacker who can only reach `POST /webhooks` (no Shipit session, no API token, no webhook secret) can create arbitrary `ReviewStack`/`Stack`/`PullRequest` records against any tracked `Repository` belonging to any tenant, as long as one org in the Shipit config has no `webhook_secret`. This is a cross-tenant write bypassing the intended per-org authentication binding, matching "Critical — a payload for one repository mutating another's stack." The same decoupling affects `ClosedHandler#archive!`, `ReopenedHandler#unarchive!`, `LabeledHandler`/`UnlabeledHandler` archive/unarchive logic, all scoped by the same mismatched `repository`, so the attacker can also archive/unarchive victim review stacks. This is repeatable against any repository whose `owner/name` the attacker can guess or discover (e.g., via public repo listings), for every affected org combination.

### Likelihood Explanation
Requires: (a) a Shipit deployment with at least one configured GitHub org lacking a `webhook_secret` (explicitly the documented/shipped default in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`), and (b) knowledge of a target repository's `owner/name` that already has a tracked `Shipit::Repository` row with review stacks enabled. Neither requires any Shipit secret, session, or privileged role — only a raw HTTP POST with a crafted JSON body and the correct `X-Github-Event` header. This is low-cost and fully repeatable.

### Recommendation
Enforce the binding explicitly: after resolving `repository` via `from_github_repo_name(params.repository.full_name)`, verify that the resolved `Repository#owner` matches `repository_owner`/`organization.login` used for signature verification, and reject the request (422) on mismatch. Additionally, treat a missing `webhook_secret` as a deployment misconfiguration warning rather than a silent bypass, or require it to be present for any org with tracked repositories.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` (or a new handler test), simulate two orgs configured in `Shipit.github_organizations`, one (`"org-y"`) with `webhook_secret: nil` and one (`"org-x"`) with a repository record `shipit_repositories(:org_x_repo)` (owner: `"org-x"`, review_stacks_enabled: true, provisioning_behavior: allow_all):

```ruby
test "cross-tenant review stack creation via org/full_name mismatch" do
  repository = shipit_repositories(:org_x_repo) # owned by "org-x"
  payload = payload_parsed(:pull_request_opened)
  payload["repository"]["full_name"] = repository.github_repo_name # "org-x/repo"
  payload["repository"]["owner"] = { "login" => "org-y" } # org-y has no webhook_secret

  request.headers["X-Github-Event"] = "pull_request"
  # no valid X-Hub-Signature required since org-y has no secret

  assert_difference -> { repository.review_stacks.count }, 1 do
    post :create, body: payload.to_json, as: :json
  end

  stack = repository.review_stacks.last
  assert_equal repository.id, stack.repository_id # binding broken: created under org-x, authenticated as org-y
end
```
This demonstrates that `repository_owner` (`"org-y"`, used for signature verification) does not equal the owner of the `Repository` row that actually received the write (`"org-x"`), confirming the cross-tenant bypass.
