### Title
Any signed account can permanently freeze part of an arbitrary victim's balance via `pallet_vesting::vested_transfer` with an unreachable `starting_block` - ([File: substrate/frame/vesting/src/lib.rs])

### Summary
`pallet-vesting`'s `vested_transfer` extrinsic lets **any signed account** create a vesting schedule on **any target account** (no consent from the target is required) with an attacker-chosen `starting_block`. The only validation performed on the schedule is that `locked != 0` and `per_block != 0` [1](#0-0) . There is no upper bound on `starting_block`. If `starting_block` is set to (or near) `BlockNumberFor<T>::max_value()`, `locked_at()` will return the full `locked` amount for the entire practical lifetime of the chain, because the vesting math saturates to zero elapsed blocks whenever `now < starting_block` [2](#0-1) . This mirrors the reported OpenQ pattern: an attacker-controlled, unbounded "time-until-unlock" parameter that gates the only self-service path to reclaim/rescue funds, with no automatic recovery.

### Finding Description
`vested_transfer` is a plain signed extrinsic — the caller supplies `target`, and the schedule (`locked`, `per_block`, `starting_block`) is entirely attacker-controlled: [3](#0-2) 

The only input validation is in `do_vested_transfer`, which checks `locked >= MinVestedTransfer` and `schedule.is_valid()` (non-zero `locked`/`per_block`) — nothing bounds `starting_block`: [4](#0-3) 

After the currency transfer succeeds, the schedule is stored via `add_vesting_schedule`, and the pallet computes `locked_now` and calls `write_lock`, which places a `LockableCurrency` lock (`VESTING_ID`) on the **target** for the total unvested amount, using `WithdrawReasons::except(UnvestedFundsAllowedWithdrawReasons)`: [5](#0-4) 

Because `VestingInfo::locked_at` computes `vested_block_count = n.saturating_sub(starting_block)`, setting `starting_block` to `BlockNumberFor::<T>::max_value()` (or any block number that will not realistically be reached) makes `vested_block_count` permanently `0`, so `locked_at()` always returns the full `locked` amount: [2](#0-1) 

The only way an ordinary account can reduce this lock is by calling `vest`/`vest_other`, both of which just recompute `locked_at()` at the current block — which will stay at the full amount forever for such a schedule: [6](#0-5) [7](#0-6) 

The victim has no self-service escape: `merge_schedules` is signed by the victim but only recombines existing schedules using their `locked_at` values (still fully locked, so merging does not help) [8](#0-7) , and there is no signed-origin call to cancel/reject an unwanted incoming schedule. The only removal path is `force_remove_vesting_schedule`, gated by `ensure_root` [9](#0-8)  — i.e., recovery requires governance/root intervention, not the account owner.

This is a direct analog of the reported bug class: a permissionless, attacker-supplied "expiration"/"unlock-time" parameter (`starting_block`) with no sane upper bound, whose only mitigation ("wait for it to expire" / call the standard unlock function) can never succeed once the parameter is pushed far enough into the future, and for which the protocol provides no non-privileged rescue mechanism — only a root-only override exists, analogous to the audit's recommendation of an "emergency function."

### Impact Explanation
Any account can grief an arbitrary victim by transferring `MinVestedTransfer` (chain-configured, can be small) tokens to the victim with `starting_block = max_value()`, `per_block = 1`. This permanently locks that amount of the victim's total spendable balance (their fungible balance, not tagged coins) until governance intervenes via `force_remove_vesting_schedule`. Repeating the attack up to `MAX_VESTING_SCHEDULES` times can also fill the victim's vesting-schedule slots, blocking legitimate future vested transfers to that account (`AtMaxVestingSchedules` error) [10](#0-9) . This is an irreversible (without governance) freezing/DoS condition imposed on a non-consenting third party, at a cost to the attacker equal only to `MinVestedTransfer` per schedule slot consumed.

### Likelihood Explanation
High likelihood of reachability: `vested_transfer` is a standard signed extrinsic exposed wherever `pallet-vesting` is deployed (Polkadot/Kusama/Westend relay chains, asset-hub runtimes, `substrate/bin/node`), requires no special origin, and the attack costs only `MinVestedTransfer` in the target chain's native currency. No wrapped/failure path removes the schedule automatically; only manual root action (`force_remove_vesting_schedule`) resolves it.

### Recommendation
- Bound `starting_block` in `VestingInfo::is_valid()` (or in `do_vested_transfer`/`add_vesting_schedule`) to a reasonable maximum offset from the current block (e.g., reject schedules whose `starting_block` is further than some configurable `MaxVestingHorizon` in the future).
- Consider requiring recipient consent (e.g., an opt-in/claim step) before an incoming vesting schedule is applied and a lock placed on a non-consenting account, similar to how some pallets require target acknowledgement for balance-affecting third-party actions.
- Alternatively, expose a non-root, rate-limited self-service mechanism (e.g., `vest`-callable garbage collection for schedules whose `starting_block` is unreasonably far, or a `reject_vesting_schedule` call before the sender's schedule "settles") so victims are not solely dependent on governance/root to recover liquidity.

### Proof of Concept
Not executed against a live network. Reasoning is based on static code tracing of `pallet-vesting` in this repository:
1. Attacker (any signed, unprivileged account) calls `Vesting::vested_transfer(origin=attacker, target=victim, schedule=VestingInfo::new(MinVestedTransfer, 1, BlockNumberFor::<T>::max_value()))`.
2. `do_vested_transfer` checks pass (`locked >= MinVestedTransfer` ✓, `is_valid()` ✓ since `locked!=0`, `per_block!=0`); no bound on `starting_block` is enforced [11](#0-10) .
3. Currency transfer moves `MinVestedTransfer` from attacker to victim; `add_vesting_schedule` stores the schedule and calls `write_lock`, placing a currency lock of `MinVestedTransfer` on victim under `VESTING_ID` [5](#0-4) .
4. Victim calls `vest(origin=victim)`; `do_vest` recomputes `locked_at(now)` which is still `locked` in full because `now < starting_block` (saturating to 0 elapsed blocks) [2](#0-1) ; the lock is rewritten unchanged. This holds for every future block until the chain's block number would (impractically) reach `max_value()`.
5. Only `force_remove_vesting_schedule` (root-gated) can free the lock [9](#0-8) .

This trace was derived purely from static inspection of the indexed source; no test harness or on-chain execution was run, so runtime-specific values of `MinVestedTransfer`/`MAX_VESTING_SCHEDULES` for the affected production runtimes (e.g., exact Westend/Polkadot constants) were not confirmed from the index within the available search scope. A Devin session with full repository/runtime access would be needed to pull exact constant values and run an integration test (`ExtBuilder`-based, similar to existing tests in `substrate/frame/vesting/src/tests.rs`) confirming the lock persists indefinitely across many blocks.

	pub fn locked_at<BlockNumberToBalance: Convert<BlockNumber, Balance>>(
		&self,
		n: BlockNumber,
	) -> Balance {
		// Number of blocks that count toward vesting;
		// saturating to 0 when n < starting_block.
		let vested_block_count = n.saturating_sub(self.starting_block);
		let vested_block_count = BlockNumberToBalance::convert(vested_block_count);
		// Return amount that is still locked in vesting.
		vested_block_count
			.checked_mul(&self.per_block()) // `per_block` accessor guarantees at least 1.
			.map(|to_unlock| self.locked.saturating_sub(to_unlock))
			.unwrap_or(Zero::zero())
	}

	fn do_vested_transfer(
		source: &T::AccountId,
		target: &T::AccountId,
		schedule: VestingInfo<BalanceOf<T>, BlockNumberFor<T>>,
	) -> DispatchResult {
		// Validate user inputs.
		ensure!(schedule.locked() >= T::MinVestedTransfer::get(), Error::<T>::AmountLow);
		if !schedule.is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		};

		// Check we can add to this account prior to any storage writes.
		Self::can_add_vesting_schedule(
			target,
			schedule.locked(),
			schedule.per_block(),
			schedule.starting_block(),
		)?;

		T::Currency::transfer(source, target, schedule.locked(), ExistenceRequirement::AllowDeath)?;

		// We can't let this fail because the currency transfer has already happened.
		// Must be successful as it has been checked before.
		// Better to return error on failure anyway.
		let res = Self::add_vesting_schedule(
			target,
			schedule.locked(),
			schedule.per_block(),
			schedule.starting_block(),
		);
		debug_assert!(res.is_ok(), "Failed to add a schedule when we had to succeed.");

		Ok(())
	}

	/// Write an accounts updated vesting lock to storage.
	fn write_lock(who: &T::AccountId, total_locked_now: BalanceOf<T>) {
		if total_locked_now.is_zero() {
			T::Currency::remove_lock(VESTING_ID, who);
			Self::deposit_event(Event::<T>::VestingCompleted { account: who.clone() });
		} else {
			let reasons = WithdrawReasons::except(T::UnvestedFundsAllowedWithdrawReasons::get());
			T::Currency::set_lock(VESTING_ID, who, total_locked_now, reasons);
			Self::deposit_event(Event::<T>::VestingUpdated {
				account: who.clone(),
				unvested: total_locked_now,
			});
		};
	}

	/// Ensure we can call `add_vesting_schedule` without error. This should always
	/// be called prior to `add_vesting_schedule`.
	fn can_add_vesting_schedule(
		who: &T::AccountId,
		locked: BalanceOf<T>,
		per_block: BalanceOf<T>,
		starting_block: BlockNumberFor<T>,
	) -> DispatchResult {
		// Check for `per_block` or `locked` of 0.
		if !VestingInfo::new(locked, per_block, starting_block).is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		}

		ensure!(
			(Vesting::<T>::decode_len(who).unwrap_or_default() as u32) < T::MAX_VESTING_SCHEDULES,
			Error::<T>::AtMaxVestingSchedules
		);

		Ok(())
	}
