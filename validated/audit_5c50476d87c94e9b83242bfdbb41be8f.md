### Title
Webhook event handlers act on `repository.full_name` from the payload while `WebhooksController#verify_signature` authenticates only against the GitHub App keyed by `repository.owner.login` (or `organization.login`) — a per-organization signature-selection binding that can be broken in multi-org installs - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / webhook secret to verify the HMAC against using `repository_owner` (derived from `params.dig('repository','owner','login')` or `params.dig('organization','login')`), [1](#0-0) [2](#0-1) . In multi-org configurations, each organization has its own independent `webhook_secret` [3](#0-2) , and `GithubApp#verify_webhook_signature` trivially returns `true` if that organization's `webhook_secret` is blank/unset [4](#0-3) . Meanwhile, every webhook handler (`Handler#stacks`, `PushHandler`, `OpenedHandler`, etc.) resolves the target `Repository`/`Stack` using `payload.dig('repository','full_name')` — a completely separate field from the one used to pick the verifying app [5](#0-4) [6](#0-5) .

### Finding Description
This is the same class of trust-binding break as the `confirmBaseInterestAllocator()` finding: the report's bug is that one field (the newly-confirmed allocator) is acted upon without being bound to the check that was actually performed (the pending-allocator approval), so the "thing verified" and "thing executed" diverge. Here the equality that should hold is:

`organization used to select/verify the webhook signature == organization that owns the repository the handlers write to`

but the code enforces:
- Signature selection: `Shipit.github(organization: repository_owner)` where `repository_owner = payload.dig('repository','owner','login') || payload.dig('organization','login')` [1](#0-0) .
- Actual write target: `Repository.from_github_repo_name(payload.dig('repository','full_name'))` inside every handler, with no cross-check against `repository_owner` [5](#0-4) .

Because `verify_webhook_signature` short-circuits to `true` whenever the selected organization's `webhook_secret` config value is blank [4](#0-3)  — and `webhook_secret` is explicitly documented as optional, with example/default configs shipping it as nil [7](#0-6) [8](#0-7)  — an unprivileged attacker who knows (or controls a webhook installation for) any configured organization lacking a `webhook_secret` can submit an entirely forged POST to `/webhooks` where:
- `repository.owner.login` (or `organization.login`) = the org whose GitHub App has no `webhook_secret` configured (verification auto-passes), and
- `repository.full_name` = any other tracked `owner/repo`, including repos belonging to organizations that *do* have a strict `webhook_secret` configured.

The signature check never inspects `full_name`; it only decides which app config to use for HMAC verification based on `repository_owner`. Since that check passes unconditionally (secret is blank), the forged payload is accepted, and `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs handlers that act on the attacker-chosen `full_name` target [9](#0-8) .

### Impact Explanation
Via the `pull_request` `opened` event handler, this reaches an unauthorized-deploy-class primitive: `OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!`, which creates a `Stack` whose `branch` is taken directly from the forged `pull_request.head.ref` [10](#0-9) , and enqueues it for provisioning [11](#0-10) . Because the repository resolved is looked up purely from `full_name` (not tied to the org that was actually authenticated), an attacker can provision/unarchive review stacks — and reach the deploy pipeline — for a repository under an organization other than the one whose (missing) secret satisfied the signature check. This lands in the report's "Critical: unauthorized deploy" bucket. Push events (`PushHandler`) similarly resync arbitrary tracked stacks based on the forged `full_name`, and `status`/`check_suite` handlers can inject forged CI/check state for arbitrary tracked commits.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (supported and documented) [12](#0-11) , (2) at least one configured organization without a `webhook_secret` — a state the official setup docs call "optional" and ship as nil by default [7](#0-6) . No GitHub App private key, session, or `ApiClient` token is needed — the attacker only needs to know the name of an org configured on the instance (visible in Shipit's own stack/URL naming) and craft a POST body; the `X-Hub-Signature` header value is irrelevant when the secret is blank.

### Recommendation
Bind the two checks together: after selecting the GitHub App/organization used to verify the signature, require that `payload.dig('repository','full_name')` (and `organization.login`, if present) actually belongs to that same organization before dispatching to handlers — i.e., derive `repository_owner` and cross-validate it equals the owner segment of `repository.full_name`, rejecting the request otherwise. Additionally, treat a blank `webhook_secret` for any configured organization as a hard misconfiguration (or at minimum, never allow signature bypass to authorize writes to repositories under a *different* organization's namespace) — the invariant "verified organization == acted-upon repository owner" must hold unconditionally, mirroring the recommended fix for the reported bug (never allow an action authorized under one binding to be executed against a target from a different, unverified binding).

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` (no `webhook_secret` set) and `OrgB` (strict `webhook_secret` set), as shown in the multi-org config format [13](#0-12) . `OrgB` has a stack/repository tracked in Shipit with review-stacks provisioning enabled (`allow_all`).
2. POST to `/webhooks` with header `X-Github-Event: pull_request` and any (or no) `X-Hub-Signature` value, with a JSON body:
```json
{
  "action": "opened",
  "number": 999,
  "pull_request": {
    "id": 1, "number": 999, "url": "https://x", "title": "x", "state": "open",
    "additions": 0, "deletions": 0,
    "head": { "sha": "deadbeef", "ref": "attacker-branch" },
    "user": { "login": "attacker" }, "assignees": [], "labels": []
  },
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" },
  "organization": { "login": "OrgA" },
  "sender": { "login": "attacker" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (even absent/garbage) signature header [4](#0-3) .
4. `create` dispatches to `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler`, which resolves `repository` via `Repository.from_github_repo_name("OrgB/target-repo")` — a real, strictly-secured org — and, if provisioning is enabled, creates/provisions a review stack on branch `attacker-branch` [6](#0-5) [10](#0-9) , despite the request never being validated against `OrgB`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
