## StatusHandler's `Commit.where(sha:)` lookup is not scoped to any repository — even more critical than the routing mismatch

### Summary
The webhook signature-verification path in `WebhooksController` selects *which* GitHub App/organization secret to check against using an attacker-influenced field (`repository.owner.login` / `organization.login`) taken from the unauthenticated request body, while several downstream event handlers resolve the *repository/commit to mutate* using a different field from the same body (`repository.full_name`, or for `status` events, nothing at all). This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to validate the HMAC against by parsing the payload itself, before the signature has been proven authentic: [1](#0-0) [2](#0-1) 

In a multi-organization deployment (`docs/setup.md` "Using Multiple Github Applications"), each org has its own `webhook_secret` that its own admins configure and know: [3](#0-2) 

`Shipit.github(organization:)` looks up the app config keyed by that attacker-controlled `repository_owner`/`organization` string, so any org onboarded into the shared instance can compute a *valid* signature over a *crafted* body using its own known secret.

Once the signature check passes, handlers resolve what to act on from a **different, independently-parsed field**:
- Generic handlers use `payload.dig('repository', 'full_name')`, unrelated to `repository_owner`: [4](#0-3) 
- `StatusHandler` doesn't even check the repository at all — it matches purely by commit SHA across the entire `commits` table: [5](#0-4) 
- `CheckSuiteHandler` scopes by `stacks` (repo-derived) + branch + sha: [6](#0-5) 
- `PushHandler` similarly triggers a sync against `stacks` resolved from `repository.full_name`, gated only by branch: [7](#0-6) 

**Equality broken:** `verify_signature`'s trust anchor = `Shipit.github(organization: payload['repository']['owner']['login'])`, but the entity actually mutated = `Repository.from_github_repo_name(payload['repository']['full_name'])` (or, worse, an unscoped `Commit.where(sha:)` for `status` events). These two payload-derived values are never cross-checked against each other, and the HMAC only proves "signed by whichever org's secret was looked up," not "signed by the org that owns the repository named in the payload."

### Impact Explanation
An org admin who has legitimately onboarded their own organization into a shared/multi-tenant Shipit instance (and thus knows their own `webhook_secret`) can forge a webhook body that:
1. Sets `repository.owner.login` / `organization.login` to their own org (so `verify_signature` selects their own known secret and passes), and
2. Sets `repository.full_name` / `sha` to point at a **victim repository/commit tracked under a different organization** in the same Shipit instance.

Most severe path: forging a `status` event for a victim's commit SHA (guessable/observable from GitHub UI) with `state: "success"` and a matching `context`. `StatusHandler#process` writes this status onto the matching `Commit` record with no ownership check at all, since it queries the global `commits` table by SHA only. Because Shipit gates deploys/merges on required CI statuses, this can flip a victim commit's status to green and lead to an **unauthorized deploy or merge** — matching the Critical impact bar. Even the `full_name`-scoped handlers (`push`, `check_suite`, `pull_request`) allow forcing spurious syncs/refreshes or manipulating review-stack lifecycle (archive/unarchive) for repositories the forging org has no relationship to.

### Likelihood Explanation
Requires the instance to be configured for multiple GitHub organizations (a documented, supported feature) and requires the attacker to control one legitimate tenant org's own webhook secret — not the victim's. No `ApiClient` token, session, or GitHub App private key theft is needed; the `/webhooks` endpoint is unauthenticated by design and only distinguishes senders via this signature scheme. This is a realistic configuration for any SaaS-style shared Shipit deployment serving multiple orgs/customers.

### Recommendation
- Verify that `repository.owner.login` (used to select the signing secret) matches the owner embedded in `repository.full_name` before trusting the payload.
- After signature verification, re-derive the acted-upon repository strictly from the verified organization identity, not from an independently-parsed field of the same untrusted body.
- Scope `StatusHandler#process` to commits belonging to stacks/repositories owned by the verified organization instead of a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Attacker's organization `attacker-org` is legitimately configured in Shipit's multi-org `github:` secrets with a `webhook_secret` the attacker knows.
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim-org/repo commit sha under CI review>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org's webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner => "attacker-org"`, fetches `attacker-org`'s config, verifies the HMAC — passes, per [1](#0-0) .
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` — the victim's commit — and calls `create_status_from_github!`, per [5](#0-4) , marking the victim's commit "success" regardless of which org actually owns it, potentially unblocking an unauthorized deploy/merge in `victim-org`.
