Based on my analysis, I found a plausible analog: the PEM-key validation used by `is_valid_sig`/`vrf_verify` (and by extension address definitions containing `sig`-over-PEM checks) accepts weak/small RSA keys and a large family of legacy/weak ECDSA curves without any strength enforcement, letting an attacker satisfy an "unlockable" authentication check with a key an attacker can practically break.

### Title
Weak Key-Strength Requirements in PEM Public-Key Validation Allow Forgeable Signature Conditions - (File: signature.js)

### Summary
`validateAndFormatPemPubKey` in `signature.js`, used by the `is_valid_sig` and `vrf_verify` oscript functions [1](#0-0) , only checks structural/format validity of a supplied PEM public key (SEQUENCE tag, algorithm OID whitelist, and an overall byte-length cap of 736 bytes) — it never enforces a minimum key strength. For RSA (`objSupportedPemTypes['06092a864886f70d0101010500']`) there is no `hex_pub_key_length` check at all, meaning an attacker-supplied RSA key of any size (e.g. 512-bit) passes validation [2](#0-1) . This is directly analogous to the "weak password requirements" bug class: the value that's supposed to gate authorization (here, a cryptographic key/signature check embedded in an oscript formula or asset/definition condition) is accepted even when trivially weak, enabling forgery with realistic computational effort.

### Finding Description
`is_valid_sig` and `vrf_verify` in `formula/evaluation.js` let any AA trigger sender, address-definition author, or asset-condition author embed an arbitrary PEM public key that is later used to "prove" authorization of a payload via signature [3](#0-2) . Before verifying the signature, the key is passed through `signature.validateAndFormatPemPubKey(evaluated_pem_key, "any", ..., bPostPemCurvesFix)` [4](#0-3) .

That validator:
- Rejects keys larger than 736 bytes (an RSA-4096 sized upper bound) [5](#0-4) .
- Whitelists an algorithm OID against `objSupportedPemTypes`, which includes numerous historically weak/deprecated ECDSA curves (`secp112r1/r2`, `secp128r1/r2`, `sect113r1/r2`, `wap-wsg-idm-ecid-wtls*`, etc., all with sub-160-bit key sizes) as well as plain RSA (PKCS #1) with **no minimum modulus length check** [6](#0-5) .
- Only for `ECDSA` keys does it check that the encoded public-key length matches the expected curve size [7](#0-6) ; for RSA there is no equivalent enforcement of modulus size — a 512-bit or 384-bit RSA key (a handful of hex-encoded bytes) is structurally valid and accepted.
- The `bPostPemCurvesFix` gate (`objSafePemTypes`) narrows accepted curves for *new* AAs only to a small safe set (P-256, P-224, P-384, secp256k1, RSA/PKCS#1) [8](#0-7) [9](#0-8)  — but RSA is still accepted in that safe set without any modulus-size floor, so the "fix" does not close the RSA weak-key gap, and pre-fix units/older AAs remain exposed to the full weak-curve list.

An attacker who controls the key (e.g., because they are the AA author, or because the `pem_key` argument is derived from unit/trigger data they control) can pick a deliberately weak key (small RSA modulus, or one of the sub-112-bit ECDSA curves) that they can factor/break within realistic computational effort, then forge a signature that satisfies `is_valid_sig`/`vrf_verify`. If AA logic uses this as an authorization gate (e.g., "only pay out if `is_valid_sig` succeeds for a specific key" pattern, or `vrf_verify` used to gate reveal/settlement logic), the "authentication" is illusory and can be satisfied without the true secret, once the weak key's private counterpart is broken.

### Impact Explanation
Any AA that relies on `is_valid_sig`/`vrf_verify` (or on an oracle-style "prove-you-know-the-secret" pattern embedded via PEM keys) for gating fund release, data-feed authorization, or VRF-based randomness can have its "signature" check bypassed by an attacker who deliberately registers/uses a weak key and breaks it offline, then forges the corresponding signature/proof. This can lead to unauthorized AA fund release or manipulation of VRF-driven logic — an impact category explicitly in scope (AA fund loss). Because the check is embedded inside oscript formulas that are validated the same way regardless of author, the weak-key acceptance is reachable by any unprivileged AA trigger sender or address/asset-condition author who controls the relevant PEM key argument.

### Likelihood Explanation
Likelihood is moderate: exploitation requires (1) an AA (or address/asset definition) design that uses `is_valid_sig`/`vrf_verify` with a PEM key that is attacker-influenceable, and (2) the attacker to actually break a small RSA modulus or a low-security ECDSA curve, which is computationally feasible for the smallest curves/RSA sizes listed (e.g. `secp112r1`, sub-1024-bit RSA) but not for the "safe" set. The validator's structural nature (no modulus/curve-strength floor) means the vulnerability exists independent of any specific AA, so the risk surface grows as more AAs adopt this oscript feature.

### Recommendation
- Enforce a minimum key-strength floor in `validateAndFormatPemPubKey`: reject RSA keys below a safe modulus size (e.g., 2048 bits) by decoding and checking the modulus length, not just overall PEM byte length.
- Remove (or gate behind `bPostPemCurvesFix`-style deny-list, consistent with `objSafePemTypes`) all sub-160-bit and generally weak ECDSA curves from `objSupportedPemTypes` for all consensus paths, not only post-fix AAs.
- Apply the same minimum-strength requirement retroactively is not possible for already-stable units, but new units/AAs going forward should be blocked from using unsafe curves/RSA sizes regardless of `bPostPemCurvesFix` legacy compatibility windows.

### Proof of Concept
1. Construct a PEM public key using the `sect113r1` curve OID (`06072a8648ce3d020106052b81040004`, ~113-bit security) or a 512-bit RSA key in PKCS#1/SubjectPublicKeyInfo form.
2. Embed this key as the `pem_key` argument of `is_valid_sig(message, pem_key, sig)` (or `vrf_verify`) inside an AA's formula, or as part of an address/asset spending condition that uses a formula referencing this op.
3. Confirm `validateAndFormatPemPubKey` accepts the key (structural checks pass; no modulus/curve-strength check blocks it) — see `signature.js` lines 117-188.
4. Off-chain, factor the RSA modulus or solve the ECDLP for the weak curve to recover the private key (feasible for these small key sizes with commodity resources).
5. Sign the required message with the recovered private key and submit it as the `sig` argument in a trigger/unit; `is_valid_sig` returns `true`, satisfying whatever fund-release or logic gate the AA/definition built around it, without ever having had the legitimate secret.
