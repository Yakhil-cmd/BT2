### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but events are applied to stacks/commits resolved from unrelated payload fields — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify the raw webhook body against by reading `repository.owner.login` (or `organization.login`) out of the **unverified, attacker-controlled JSON body**. [1](#0-0) [2](#0-1)  Once verification passes, the actual side effects performed by the event handlers are computed from *different* fields of the same payload — `repository.full_name` for `Handler#stacks`/`#repository_name` [3](#0-2) , and, more critically, a bare commit `sha` with no repository scoping at all in `StatusHandler#process`. [4](#0-3) 

### Finding Description
In the multi-org GitHub App configuration (documented in `docs/setup.md` and `lib/shipit.rb#github`/`#github_app_config`), each organization has its own `webhook_secret` entry in `secrets.github`. `Shipit.github(organization: repository_owner)` looks up that organization's config and `GitHubApp#verify_webhook_signature` HMAC-verifies the signature — but if that organization's `webhook_secret` is unset/nil (a documented, valid configuration shown literally as `webhook_secret: # nil` in `config/secrets.development.shopify.yml` and `docs/setup.md`), verification is skipped entirely:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [5](#0-4) 

This creates the binding break: **authenticated_organization (`repository.owner.login`) ≠ acted_upon_repository/commit (derived from `repository.full_name` or bare `sha`)**. Because the org used for verification and the resource that is subsequently mutated are two independent, attacker-controlled fields of the same unauthenticated JSON body, an attacker who can produce *any* payload accepted by `verify_signature` (either because the resolved org has no `webhook_secret` configured, or because they hold that org's secret) can set `repository.full_name`/`sha` to point at an entirely different stack/commit belonging to a different, victim organization tracked by the same Shipit instance.

The most severe manifestation is `StatusHandler`, which does not even use `Handler#stacks`/`repository_name` scoping — it resolves target records purely by `Commit.where(sha: params.sha)` [4](#0-3) , with no repository/organization check whatsoever. Commit SHAs are non-secret (visible on GitHub, in PR links, CI logs, etc.), so knowledge of a target commit's SHA is trivial for a public repo.

### Impact Explanation
An attacker who can get any organization entry accepted by `verify_signature` (e.g. one configured with no `webhook_secret`, a legitimate and documented setup) can forge `status` webhook events for **any commit SHA tracked by any stack in the instance**, independent of which organization "authenticated" the request. Because Shipit's autodeploy/merge-status/deploy-gating machinery consumes `Status` records to decide whether a commit is "green"/deployable (`Commit#create_status_from_github!`, `Status::Group`, `merge_status`), this allows an attacker to inject fabricated passing CI statuses onto commits in stacks they do not own, potentially unlocking auto-merge/auto-deploy gating for a victim's stack — an unauthorized-deploy-adjacent authorization bypass. It can also drive `PushHandler`/`CheckSuiteHandler` to trigger `GithubSyncJob`/`schedule_refresh_check_runs!` against a victim's stack, since those handlers only trust `repository.full_name`, not the org used for signature selection. [6](#0-5) [7](#0-6) 

### Likelihood Explanation
Exploitability depends entirely on the deployment's `secrets.github` configuration containing at least one organization entry with no `webhook_secret` set (or one whose secret the attacker otherwise knows) — this is a documented, supported configuration shape (see `config/secrets.development.shopify.yml` and `docs/setup.md`'s multi-org example, both showing `webhook_secret: # nil`). Given that, no session, API token, or repository write access is required — only the ability to send an HTTP POST to the public `/github/webhooks` endpoint with a crafted JSON body and matching `X-Github-Event`/`X-Hub-Signature` headers. The remaining requirement — knowing a target commit SHA — is trivially satisfiable for any public repository.

### Recommendation
Bind the verification identity to the resource being mutated: derive `repository_owner` and the acted-upon repository/stack from the *same*, single source of truth, and additionally have each handler validate that the record it mutates (`Commit`, `Stack`) actually belongs to the repository/organization that was cryptographically verified for this request, rather than trusting `repository.full_name` or a bare `sha` independently. In particular, `StatusHandler` should scope `Commit.where(sha: params.sha)` to commits whose `stack.repository` matches the verified `repository_owner`/`repository.full_name`, not process a global `sha` match.

### Proof of Concept
1. Deploy Shipit with a multi-org `github` config where organization `attacker-org` has `webhook_secret` unset (a valid, documented configuration) and organization `victim-org` (with its own configured stacks) has a `webhook_secret` set.
2. Find a public commit SHA `deadbeef...` belonging to a stack tracked under `victim-org/some-repo`.
3. POST to `/github/webhooks` with:
   - `X-Github-Event: status`
   - Body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"}, "sha": "deadbeef...", "state": "success", "context": "ci/attacker", ...}`
   - Any/garbage `X-Hub-Signature` value.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, calls `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally — the request is accepted regardless of the (invalid) signature header.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on the matching commit, which belongs to `victim-org/some-repo`, injecting a forged status despite the request never having been authenticated for `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
