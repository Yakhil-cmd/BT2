### Title
Plaintext contents of every decrypted paired-device message are written to console/log output - (File: device.js)

### Summary
`decryptPackage()` in `device.js` unconditionally logs the full plaintext of every decrypted device-to-device message to `console.log`, regardless of message type or sensitivity. In typical ocore/headless-wallet deployments, `console.log` output is redirected to a log file (start scripts / process managers commonly do `node start.js >> log.txt 2>&1`), so this plaintext ends up persisted on disk in a file that is frequently group/world-readable, exactly the same bug class as CVE-2021-3429 (secret material written by design into an insufficiently protected log sink).

### Finding Description
When a device message arrives from a hub, `device.js` decrypts it and immediately logs the decoded JSON: [1](#0-0) 
```
	breadcrumbs.add("decrypted lengths: "+decrypted1.length+" + "+decrypted2.length);
	var decrypted_message_buf = Buffer.concat([decrypted1, decrypted2]);
	var decrypted_message = decrypted_message_buf.toString("utf8");
	console.log("decrypted: "+decrypted_message);
```
This happens for **every** decrypted device message with no filtering by `subject`/type, before the payload is even JSON-parsed or validated [2](#0-1) . Device messages are the transport used for pairing, wallet co-signing key exchange, shared/multisig wallet address definitions, private payment chains (private asset transfer proofs, blinding factors, addresses), private profile attestations, and textcoin claim data — all of which routinely flow through this exact code path. Any paired correspondent (including a maliciously-added or compromised correspondent device) can trigger this logging simply by sending an encrypted message that successfully decrypts with the recipient's temp/prev-temp/permanent device key.

Similar unconditional/insufficiently-guarded logging of sensitive material recurs elsewhere in the private-payment and message-relay code paths, e.g. logging full private payment chains and blinding factors: [3](#0-2) [4](#0-3) 
and forwarded private chain contents in `wallet.js`: [5](#0-4) 

All of these `console.log` calls write to the process's standard log stream, which ocore-based nodes/wallets typically persist to a log file on disk.

### Impact Explanation
Device messages and private payment chains can carry secrets such as blinding factors for hidden outputs, shared/multisig wallet key material exchanged during pairing, and private payment proofs that establish ownership and spendability of coins. Persisting this plaintext to an on-disk log file that is not access-restricted to the exact same degree as the wallet/keystore itself creates a local-information-disclosure vector: any local unprivileged user or process with read access to the log directory (a common misconfiguration, mirroring the cloud-init CVE) can recover data that should only be known to the paired parties. This can enable unauthorized reconstruction of private payment chains, disclosure of shared-wallet composition data, or replay/verification of information that was intended to remain confidential between correspondents — undermining the confidentiality guarantees of ocore's private-payment and secure pairing design.

### Likelihood Explanation
Reaching the vulnerable code requires nothing more than being (or becoming) a paired correspondent device and sending any well-formed encrypted device message — no special privilege on the hub or network is needed, and the log statement fires unconditionally on every successful decryption. Because this is a normal, expected part of routine wallet operation (pairing, private payment forwarding, textcoin exchange), the sensitive data is logged continuously in real operation, not only in an edge case.

### Recommendation
- Remove or gate the `console.log("decrypted: "+decrypted_message)` statement in `device.js` behind an explicit debug flag that is off by default, and never log full decrypted payloads in production.
- Redact/omit sensitive fields (`blinding`, private payment `outputs`, key material, mnemonics) before any logging in `indivisible_asset.js`, `divisible_asset.js`, `private_payment.js`, and `wallet.js`'s private-chain forwarding code.
- Apply restrictive file permissions (e.g., `0600`) to log files created by node/headless-wallet start scripts, consistent with the fix applied for cloud-init (writing password/secret data only to permission-restricted files).

### Proof of Concept
1. Pair two ocore-based wallets/devices (attacker device B pairs with victim device A).
2. From device B, send any encrypted device message to A (e.g., a legitimate pairing/chat message, or trigger any flow that forwards a private payment chain to A, such as sending a private asset payment).
3. On device A's host, inspect the log file that the node/wallet process's stdout is redirected to (commonly configured via pm2/systemd/`> log.txt`).
4. Observe the full plaintext of the decrypted device message — including any private payment chain contents, blinding factors, or wallet-key-exchange payloads — appearing in the `"decrypted: ..."` log line at `device.js:466`, now readable by any local user/process with access to that log file.
