## Title
Uncaught Exception in AA Data-Feed Candidate Sorting Crashes the Whole Node — Denial of Service ([File: data_feeds.js])

### Summary
`CVE-2024-51179` describes an Open5GS crash caused by an unhandled fault while processing a PDU session establishment message: a message that reaches deep application logic without full defensive validation triggers an unrecoverable crash of a core network function (UPF/SMF), denying service to the whole network. The `ocore` analog is a synchronous, uncaught `throw Error(...)` inside `Array.prototype.sort`'s comparator in `readDataFeedValue()`, reachable from an AA's `data_feed()`/`in_data_feed()` formula evaluation during ordinary trigger processing. Because `ocore`'s top-level `uncaughtException` handler deliberately re-throws to crash the process, any attacker able to trigger this code path can crash the entire node — the same "unhandled fault → process crash" bug class as the CVE.

### Finding Description
When an autonomous agent (AA) formula calls `data_feed(...)` (or `in_data_feed(...)`), evaluation reaches `dataFeeds.readDataFeedValue()` with `unstable_opts` set to the boolean `bAA` (i.e., `true`, not the string `'all_unstable'`): [1](#0-0) 

Inside `readDataFeedValue`, `bIncludeUnstableAAs = !!unstable_opts` becomes `true`, but `bIncludeAllUnstable = (unstable_opts === 'all_unstable')` is `false`: [2](#0-1) 

The function then collects all unstable AA-authored `data_feed` messages from the requested oracle addresses into `arrCandidates` and, if more than one candidate exists, sorts them by `latest_included_mc_index` then by `level`: [3](#0-2) 

If two distinct unstable AA units posting the same `feed_name` (from oracle addresses referenced by the calling AA's formula) end up with an **identical `latest_included_mc_index` and identical `level`**, the comparator falls through to:
```
throw Error("can't sort candidates "+a+" and "+b);
```
because `bIncludeAllUnstable` is `false` in this call path. This is a synchronous `throw` inside `Array.prototype.sort`, which is not guarded by any `try/catch` along the call chain from `formula/evaluation.js` → AA trigger handling (`aa_composer.js`) → `validation.validate()` → `network.js`'s `handleJoint`/mutex-protected validation flow. The exception therefore escapes as a Node.js `uncaughtException`.

`network.js` explicitly re-throws on `uncaughtException` in order to force-restart in a clean state: [4](#0-3) 

This means the entire node process crashes and must restart, rather than simply rejecting the offending unit.

### Impact Explanation
A crash of the process is a concrete network-unable-to-confirm-new-units condition per the DoS class in scope: any node (including witnesses, hubs, or ordinary full nodes) that evaluates the crafted AA trigger goes down. Because AA triggers are automatically executed by every full node that processes the triggering unit (not merely the poster), a single malicious but validly-formed unit can be broadcast and crash every full node in the network that reaches this code path — a straightforward, low-cost, repeatable DoS, exactly analogous to how a single malformed PDU Session Establishment Request could down Open5GS's UPF/SMF.

### Likelihood Explanation
The trigger conditions are reachable by an ordinary AA author and AA trigger sender, both explicitly in scope:
- An attacker deploys an AA (or uses `data_feed()`/`in_data_feed()` in an existing AA) that reads a data feed from two or more oracle addresses under the attacker's control.
- The attacker deploys two (or more) AAs (also attacker-controlled) at those "oracle" addresses that each post `data_feed` messages with the same `feed_name` in units that are secondary/child triggers of the very same primary trigger, so they end up with equal `latest_included_mc_index` (same main-chain reference) and equal graph `level` (a very achievable condition for AA response units spawned in the same processing round, since their level is derived from a common ancestor structure).
- The attacker sends one trigger unit to the primary AA; ocore synchronously fans out to the secondary AAs (writing the data feeds) and then evaluates the `data_feed()` call, hitting the ambiguous-sort branch.

No special privileges are required — only the ability to define AAs and post ordinary triggering units, which is unrestricted in `ocore`.

### Recommendation
- In `data_feeds.js`, replace the `throw Error("can't sort candidates ...")` fallback with a deterministic, total-order tie-breaker (e.g., compare by unit hash) so the sort never throws.
- More generally, wrap the AA formula evaluation / data-feed lookup pipeline so that any synchronous exception is converted into a formula evaluation error (bounced trigger) instead of propagating to `uncaughtException`.
- Audit other `throw Error(...)` statements reachable from formula evaluation and payment/asset validation paths (e.g., `validation.js` `"no src_coin"`, `"spend proof didn't help"`) for similar unguarded reachability from attacker-controlled unit/trigger content, since the process-level `uncaughtException` handler turns any of them into a full-node DoS.

### Proof of Concept
1. Attacker controls addresses `Oracle1` and `Oracle2`, each defined as an AA (`AA_O1`, `AA_O2`).
2. Attacker deploys `AA_Main`, whose bound formula contains `data_feed({oracles: 'Oracle1:Oracle2', feed_name: 'x'})` (equivalently `in_data_feed`), evaluated as part of handling its own trigger.
3. Attacker crafts `AA_Main` so that, upon being triggered, it sends secondary triggers to `AA_O1` and `AA_O2` in the same response round (or engineers unrelated units from `Oracle1`/`Oracle2` that land at the same MC index/level), each of which posts a `data_feed` message for feed name `x`.
4. Attacker posts the primary trigger unit to `AA_Main`.
5. During the same trigger-handling cycle, `AA_Main`'s formula calls `data_feed(...)`, which invokes `readDataFeedValue` with `unstable_opts = true` (`bAA`). Both `AA_O1` and `AA_O2`'s just-written `data_feed` messages become candidates with identical `latest_included_mc_index` and `level`.
6. The sort comparator in `data_feeds.js` throws `Error("can't sort candidates ...")`, which is uncaught, triggers `process.on('uncaughtException', ...)` in `network.js`, and the node process crashes (`throw err` at network.js:4542).
