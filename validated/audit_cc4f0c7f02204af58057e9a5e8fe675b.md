### Title
Uncaught exception in AA trigger evaluation crashes the full node - ([File: aa_composer.js])

### Summary
CVE-2019-12974 is a NULL-pointer-dereference DoS in ImageMagick coders that crashes the process when a crafted, structurally-unexpected image is parsed and an unchecked assumption fails. The reachable analog in `ocore` is a JavaScript equivalent: unexpected/invariant-violation code paths inside the AA trigger execution engine (`aa_composer.js` / `formula/evaluation.js`) use bare `throw Error(...)` on conditions that are assumed impossible but are in fact reachable with attacker-crafted trigger data or AA definitions, and this exception is never caught. Because `network.js` installs a global `process.on('uncaughtException', ...)` handler that deliberately re-throws to crash the whole daemon [1](#0-0) , any single unprivileged unit poster who can cause one of these "impossible" branches to execute can bring down the entire node process — a full denial of service, not just a rejected unit.

### Finding Description
Any address can become an AA trigger sender simply by sending a payment to an AA address; the AA logic and its trigger's `data` payload are both attacker-influenced. When a new unit is accepted, `handleJoint`'s `ifOk` handler synchronously executes a "dry run" of any AA triggers contained in the unit before saving it: [2](#0-1) 

`dryRunPrimaryAATrigger` builds a real trigger object from attacker data and immediately calls `handleTrigger`, which parses the AA definition and evaluates its formulas against the attacker-supplied trigger: [3](#0-2) [4](#0-3) 

Both `aa_composer.js`'s `handleTrigger` and `formula/evaluation.js`'s `evaluate()` are littered with bare `throw Error(...)` statements guarding conditions the authors believed to be unreachable invariants (e.g. "unknown type of arr", "unrecognized function argument", "test evaluated to object", "unit AA with more than 2 parents", "base AA not found", "no messages", cache/lookup misses such as `storage.assocStableUnits[trigger.unit]` being undefined). Representative examples: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

Unlike the many `setFatalError(...)` paths that gracefully bounce the AA response, these `throw Error` statements propagate as JavaScript exceptions with no surrounding `try/catch` in the async call chain (`handleTrigger` → `evaluateAA`/formula evaluation → `dryRunPrimaryAATrigger`'s executor → the `await` in `ifOk`). This mirrors the ImageMagick bug class: a code path assumes well-formed/expected internal state (e.g. an image header field being present) and dereferences/uses it without a defensive check, and a maliciously crafted input reaches that assumption and crashes the whole process instead of being safely rejected.

### Impact Explanation
Because `network.js` intentionally converts any uncaught exception into a full process crash (`throw err; // crash the process to avoid ending up in an inconsistent state`) [1](#0-0) , triggering one of these unguarded `throw` branches from a posted unit takes down the entire node — full nodes, hubs, and witnesses alike — rather than just failing validation of one unit. Repeated broadcast of such a unit can be used to repeatedly crash restarted nodes across the network, preventing confirmation of new units (a network-wide denial of service), which satisfies the "network unable to confirm new units" impact bar.

### Likelihood Explanation
Reaching this code path requires only sending a normal payment to any AA address with a payload designed to hit one of the un-caught invariant violations in formula evaluation or AA composition — no special privileges, keys, or trusted role are needed; a single ordinary wallet suffices to post the triggering unit. The specific triggering condition is currently unverified against a concrete PoC (the repository does not expose an obvious attacker-controlled path that trivially satisfies one of the listed `throw Error` conditions without deeper live-testing of the formula engine and `assocStableUnits`/`assocUnstableUnits` cache-consistency invariants), so likelihood is assessed as **Medium**: the bug-class (unguarded "impossible" throws in an attacker-reachable interpreter) is clearly present and structurally analogous to the CVE, but exact reachability of a specific throw site would need to be confirmed with live fuzzing of formula/trigger inputs.

### Recommendation
- Wrap all invocations of AA trigger execution and formula evaluation (`handleTrigger`, `evaluateAA`, `formula/evaluation.js`'s `evaluate`) in `try/catch` at every asynchronous boundary that lies on a path reachable from unit acceptance (`dryRunPrimaryAATrigger`, `handlePrimaryAATrigger`, `network.js`'s `ifOk`), converting any thrown "invariant violation" error into a bounced AA response or unit-validation error instead of letting it escape as an uncaught exception.
- Replace remaining bare `throw Error(...)` invariant checks inside the formula evaluator and AA composer with `setFatalError(...)`/`callback(err)` patterns already used elsewhere in the same files, so malformed-but-reachable inputs fail gracefully.
- Add defensive `if (!x) return cb(error)` guards before any array/object indexing derived from attacker-controlled trigger `data`, AA `params`, or cache lookups keyed by attacker-influenced identifiers (e.g. `storage.assocStableUnits[trigger.unit]`).
- Consider making the global `uncaughtException`/`unhandledRejection` handlers isolate and reject the offending unit/trigger rather than unconditionally crashing the whole process, at least for errors that originate from AA/formula evaluation of untrusted data.

### Proof of Concept
Not concretely constructed — the repository index does not let me trivially prove a single crafted trigger payload that reaches one of the specific `throw Error(...)` sites (e.g. `formula/evaluation.js:3131`, `aa_composer.js:1862`) end-to-end without live execution/fuzzing of the formula parser and AA state machine. A background engineering effort with runtime access should fuzz AA trigger `data` payloads and AA definitions containing edge-case formulas (malformed function calls, ternaries returning objects, remote-AA calls with crafted params, assets/units referencing cache-inconsistent state) against `aa_composer.dryRunPrimaryAATrigger` with `conf.bDryRunNewTriggers` enabled to confirm which specific throw site is reachable and produces the uncaught crash.
