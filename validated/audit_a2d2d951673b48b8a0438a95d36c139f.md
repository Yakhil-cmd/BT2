### Title
Commit status webhooks are applied by bare `sha` lookup with no binding to the verified repository, allowing cross-repository CI status forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App configuration selected by the payload's own `repository.owner.login` (or `organization.login`) field [1](#0-0) [2](#0-1) . That verification only proves the event legitimately came from GitHub for *some* repository whose owning organization's `webhook_secret` matches. However, `StatusHandler#process`, which persists commit CI statuses, never re-derives or checks which repository/stack the event belongs to — it looks up commits by a bare, globally-unscoped `sha` string and writes the status to every matching `Commit` row in the entire database [3](#0-2) . This breaks the equality that should hold: `organization/repository whose signature was verified == repository whose Commit record is mutated`.

### Finding Description
Every other webhook handler in this engine resolves the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')`, using `Shipit::Webhooks::Handlers::Handler#repository_name` / `#stacks` [4](#0-3) , e.g. `PushHandler#process` scopes its write to `stacks.not_archived.where(branch:)` [5](#0-4) .

`StatusHandler` does not follow this pattern. Its `process` method is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

`Commit.where(sha: params.sha)` is a global, unscoped ActiveRecord query across the entire `commits` table — it is not filtered by `repository_id`, `stack_id`, or anything derived from `payload['repository']`. The `params` schema for this handler doesn't even require the `repository` key [6](#0-5) , confirming the repository context is deliberately (or accidentally) not used to constrain which commit rows are updated.

The signature verification upstream in `WebhooksController` is scoped to "does this webhook_secret match for this claimed organization" — it says nothing about which specific `Commit` records may be mutated. Any Shipit installation tracking more than one stack/repository (the common case — Shipit is designed to manage many stacks) is exposed: a genuinely GitHub-signed `status` event for repository A (one that an attacker can trigger, e.g., by having push/CI access to their own tracked repository/fork) can carry an arbitrary `sha`. If that `sha` string coincidentally (or intentionally, e.g. by re-uploading/duplicating an existing commit object byte-for-byte into a repo the attacker controls) matches a `Commit` row belonging to an unrelated stack B, the forged `state`/`context`/`target_url`/`description` is written onto stack B's commit via `commit.create_status_from_github!(params)`, with no cross-check that commit B's repository is the one whose signature was verified.

### Impact Explanation
Commit statuses gate deploy safety in Shipit: the README documents `ci.require`, which blocks deploys unless the listed status contexts are present and successful, and `Commit`/`Stack` deployability checks (`deployable?`, undeployed-commit gating) rely on these `Status` records [7](#0-6) . Because `StatusHandler` writes a forged status onto any commit sharing the same `sha` regardless of which repository actually owns that webhook's signature, an attacker who can trigger genuine `status` webhooks from a repository they control (their own tracked stack, or CI they operate) can inject a fabricated `state: "success"` for a required check context on a commit belonging to a victim stack, if that commit's SHA is shared/duplicated across the two repositories. This can satisfy `ci.require` and other CI-derived deployability gates for a victim stack, contributing to an unauthorized deploy — matching this program's "unauthorized deploy" Critical impact criterion.

### Likelihood Explanation
The precondition (a matching `sha` existing in two `Commit` rows belonging to different repositories/stacks tracked by the same Shipit instance) is not guaranteed for arbitrary repositories, but is realistic in common real-world setups this engine explicitly supports: multiple stacks/environments per repository, forked/mirrored/vendored repositories, monorepo splits, or an attacker with legitimate push access to one tracked repository deliberately re-creating (cherry-picking / re-uploading identical tree+parents+commit metadata) a commit that already exists in a victim's tracked repository, then using their own real CI/webhook to post an arbitrary status for that identical SHA. No special secret, GitHub App key, or privileged Shipit account is required beyond ordinary contributor/push access to some repository already tracked by the Shipit instance — squarely within the "unprivileged attacker" scope of this program, since the code path is reachable purely by triggering a normal, correctly-signed `status` webhook from an attacker-controlled repository.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, mirroring every other handler: resolve `stacks`/`repository_name` from `payload.dig('repository', 'full_name')`, and restrict the `Commit` lookup to commits belonging to that repository's stacks (e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or equivalent), rejecting/ignoring the event if the commit's owning repository does not match the authenticated repository from the payload.

### Proof of Concept
1. Attacker has ordinary push/CI access to `attacker-org/attacker-repo`, which is tracked as a Shipit stack (Shipit App installed there with its own `webhook_secret`).
2. Attacker creates a commit whose SHA is identical to a commit already present in `victim-org/victim-repo` (e.g. by re-uploading the exact same commit object — same tree, parent, author/committer timestamps and message — into `attacker-repo`, which is possible because git commit hashes depend only on content, not on which repository stores them).
3. Attacker's own genuine CI (or a manually issued `POST /repos/attacker-org/attacker-repo/statuses/:sha` call using their own repo's credentials) causes GitHub to deliver a `status` webhook to Shipit, correctly signed with `attacker-org`'s real `webhook_secret`, with `state: "success"`, `context: "<required-check-name>"`, and `sha: "<the shared sha>"`.
4. `WebhooksController#verify_signature` passes because the signature is valid for `attacker-org`.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which matches the `Commit` row for `victim-org/victim-repo`, and calls `create_status_from_github!`, writing a forged `success` status for the required check context onto the victim stack's commit — potentially unblocking `ci.require` gating for a deploy of that commit in `victim-org/victim-repo`'s stack, with the attacker never having had any access to `victim-org` or its `webhook_secret`.
