### Title
Unallowlisted route venues ride on the caller's signed authorization tree to steal arbitrary wallet tokens — (File: contracts/controller/src/strategies/swap.rs)

### Summary
The cookie-sharing class maps onto Soroban invoker auth: in Contao, a privileged crawler forwarded the user's session cookie to attacker-chosen external URLs; here, controller strategy entrypoints forward the caller's *signed authorization* to attacker-chosen external contracts. `swap_collateral`, `swap_debt`, `multiply` and `repay_debt_with_collateral` accept caller-supplied `swap: Bytes` route data and pass it to the swap router, which invokes whatever pool and token addresses the payload names with no allowlist. A malicious venue contract invoked under this flow can issue `token.transfer(victim, attacker, amount)`; because the caller's `require_auth` root is on the stack, simulation records that transfer as a child of the caller's authorization entry, and it executes once the caller signs the tree. The repository's own harness proves the drain: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` empties the victim's entire wallet balance of an unrelated token.

### Finding Description
- Strategy entrypoints route swaps through the aggregator using untrusted route bytes; the router keeps no allowlist of pools or tokens (`docs/explanation/threat-model.md:154-165`).
- A route-named pool executes arbitrary code inside the caller's authorization scope. Any `transfer` it makes from the caller is recorded as a sub-invocation of the caller's `swap_collateral`/`execute_strategy` auth entry (`rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227`, where the recorded tree contains `transfer(alice → attacker, WALLET_BALANCE)`).
- Neither the payload's `min_out` check nor the controller's final health-factor gate bounds this loss — the stolen transfer is orthogonal to the swap's measured input/output.

### Impact Explanation
Theft of user funds: the full balance of any wallet token can be transferred to the attacker, far exceeding the routed amount, in a single signed transaction.

### Likelihood Explanation
Requires the victim to sign a poisoned transaction (UI:R, matching the original advisory's interaction requirement). An attacker distributes a crafted route/quote; wallet UX that does not decode and diff the simulated auth tree will present it as a normal swap. The protocol documents this as a client responsibility (`threat-model.md:161-164`), so exploitability hinges entirely on front-end validation rather than on-chain enforcement — hence Medium rather than High.

### Recommendation
Enforce on-chain what is currently left to clients: pin the set of pool/token addresses a strategy route may invoke (governance-managed venue allowlist), or have the controller authorize the router call through a scoped invoker-auth entry that permits only the exact input transfer, so a rogue venue's extra `transfer` has no authorized parent to attach to.

### Proof of Concept
1. Attacker deploys `RogueHopPool` whose `swap()` calls `token.transfer(victim, attacker, victim_balance)` on a wallet token (`rogue_hop_pool_transfer_joins_caller_auth_tree.rs:62-71`).
2. Attacker serves the victim a route that names that pool for `swap_collateral(account_id, current, amount, new, swap)` or router `execute_strategy`.
3. Simulation records the theft as a child of the victim's auth entry; on signing, the token move executes and the swap still settles fairly, satisfying all risk gates (test asserts `balance(attacker) == WALLET_BALANCE`, `balance(alice) == 0`).
