### Title
Cross-Organization Webhook Spoofing via Repository-Owner/Repository-Name Mismatch - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/secret to validate a webhook's HMAC signature against using one payload field (`repository.owner.login`), while the webhook handlers that actually mutate state use a *different* payload field (`repository.full_name`) to resolve the `Repository`/`Stack` to act on. Because Shipit is multi-tenant (one `GitHubApp` config, and one `webhook_secret`, per organization), an attacker who legitimately controls the webhook secret for their own org's GitHub App can craft a payload whose `repository.owner.login` matches their own org (so it passes signature verification) while `repository.full_name` points at a repository belonging to a completely different organization tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization exclusively from the `owner.login` sub-field: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` instance configured for that organization and calls `verify_webhook_signature`, which HMACs the *entire* raw body against that organization's own `webhook_secret`: [3](#0-2) 

Once the signature is accepted, `Handler#stacks`/`#repository_name` use a *different* field of the same JSON body — `repository.full_name` — to find the `Repository` (and its `Stack`s) that the handler will mutate: [4](#0-3) 

Both `push_handler.rb`, `status_handler.rb`, and `check_suite_handler.rb` inherit this and act on whatever `Repository`/`Stack`/`Commit` the crafted `full_name`/`sha` resolves to: [5](#0-4) [6](#0-5) 

Nothing enforces that `repository.owner.login` (the field that selects the verifying secret) and `repository.full_name` (the field that selects the object being written to) refer to the same repository/organization. Since the attacker controls the raw JSON body and only needs a secret for *their own* organization's app to produce a valid signature over that body, they can set `owner.login` to their own org (satisfying `verify_signature`) and `full_name` to `"other-org/victim-repo"` (driving the actual state change) in the very same signed payload.

This is the same trust-binding break as the reported Dutch-auction bug: one field of an approved/verified payload is checked, while a *different* field of that same payload is the one actually acted upon, letting the value that "moves value" diverge from the value that was "authorized."

### Impact Explanation
An attacker who administers their own GitHub organization/App installed against a shared multi-tenant Shipit instance can forge `push`, `status`, or `check_suite` events attributed to a victim organization's repository:
- A forged `push` event triggers `Stack#sync_github(expected_head_sha:)` on the victim's stacks, altering deploy state for a repository the attacker doesn't own — a cross-repository write.
- A forged `check_suite`/`status` event can mark commits with fabricated CI state (`Commit#create_status_from_github!`) or trigger `RefreshCheckRunsJob`, potentially bypassing CI gating relied upon by the merge queue/deploy flow for the victim repository, enabling an unauthorized deploy/merge decision to be influenced.

This satisfies the "Critical: cross-repository writes / unauthorized deploy" bar, since the attacker never needed any credential belonging to the victim organization.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where the attacker legitimately administers at least one tracked GitHub App/organization (and thus knows its `webhook_secret`), and knowledge that another org's repository is tracked by the same instance (discoverable via Shipit's public stack listing UI). No access to the victim's secret, session, or `ApiClient` token is needed — only the ability to POST a self-signed JSON body to the shared `/webhooks` endpoint. This is a realistic scenario in shared/hosted Shipit deployments serving multiple organizations.

### Recommendation
Bind signature verification and object resolution to the *same* payload field. Either:
- Derive both the verifying organization and the acted-upon repository from the same authenticated field (e.g., verify against `repository.full_name`'s owner, and reject if `repository.owner.login` disagrees with it), or
- After computing `repository_name` in `Handler`, assert that the resolved `Repository#owner` matches the `organization` whose secret validated the signature, rejecting the event otherwise.

### Proof of Concept
1. Attacker controls GitHub org `attacker-org`, which has its own GitHub App installed on the shared Shipit instance with webhook secret `S_attacker`.
2. Victim org `victim-org/prod-repo` is also tracked by the same Shipit instance (different secret `S_victim`, unknown to attacker).
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/prod-repo"
  }
}
```
4. Attacker signs the raw body with `S_attacker` and sets `X-Hub-Signature`/`X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature against `S_attacker`.
6. `PushHandler#process` (via `Handler#repository_name`) resolves `full_name` = `"victim-org/prod-repo"`, finds that `Repository`'s stacks, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` — mutating victim state despite the request never being signed by `victim-org`'s real webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
