### Title
Unhandled exception / node crash from malformed address checksum causes length mismatch in `isChashValid` - (File: chash.js)

### Summary
`CVE-2015-9274` describes HarfBuzz crashing because `GPOS`/`GSUB` table offsets were read and used to index sub-tables without validating that the resulting offsets/lengths matched the expected table size, causing an out-of-bounds read and application crash. `ocore`'s address-checksum ("c-hash") decoder in [1](#0-0)  has the same root-cause shape: it decodes an attacker-supplied string into a binary buffer and then walks a **precomputed fixed offset table** (`arrOffsets160`/`arrOffsets288`) assuming the decoded buffer is *exactly* 160 or 288 bits long, without re-validating the actual decoded length before indexing into it.

### Finding Description
`isChashValid(encoded)` first checks that the encoded string is 32 or 48 characters [2](#0-1) , but the string-length check does **not** guarantee that the *decoded* binary length will be exactly 160 or 288 bits:
- For 48-character input, `Buffer.from(encoded, 'base64')` is used [3](#0-2) . Node's base64 decoder silently skips characters outside the base64 alphabet rather than throwing, so a 48-character string containing invalid characters can decode to a buffer whose byte length is not 36 (288 bits).
- The `try/catch` in `isChashValid` wraps only the decode call [4](#0-3) ; the subsequent processing (`buffer2bin`, `separateIntoCleanDataAndChecksum`) is executed **outside** that try/catch.
- `separateIntoCleanDataAndChecksum(bin)` then throws an uncaught `Error("bad length=...")` if `bin.length` is not exactly 160 or 288 [5](#0-4) , exactly analogous to HarfBuzz reading a GPOS/GSUB offset table entry that doesn't match the actual table bounds and crashing.

This is reachable from `isValidChash` → `isValidAddress`/`isValidAddressAnyCase` [6](#0-5) , which are called throughout unit/definition/authentifier validation (`validation.js`, `definition.js`, `formula/evaluation.js`, `aa_validation.js`) whenever an address string supplied by a unit author, AA trigger, or asset definition is checked.

### Impact Explanation
If any of these call paths invoke `isValidAddress`/`isValidChash` without an enclosing try/catch (multiple call sites exist across `validation.js`, `definition.js`, `formula/evaluation.js`, `aa_validation.js`), a single crafted address string embedded in a posted unit, AA trigger, or definition can throw an uncaught exception during validation of an unprivileged unit, potentially crashing the validating process (denial of service, "network unable to confirm new units" if it affects hub/node validation flow uniformly). I was not able to confirm within the available iterations whether every call site wraps this in a try/catch (the top-level `validate()` in `validation.js` may catch some exceptions), so the actual reachability of an unhandled crash versus a caught validation failure is **unverified**.

### Likelihood Explanation
Medium: constructing a 48-character string with invalid base64 characters that still parses without throwing in `Buffer.from(str, 'base64')` is straightforward and requires no privileges — any address field in a unit, AA definition, or payment output is a candidate. The main uncertainty is whether upstream callers already wrap definition/authentifier evaluation in a try/catch that converts this into a normal validation error rather than a crash.

### Recommendation
- In `chash.js`, validate that the decoded buffer's bit-length strictly equals 160 or 288 immediately after decoding, inside the same try/catch, and return `false` (not throw) if not.
- Wrap the entire body of `isChashValid` in a single try/catch and return `false` on any exception, so malformed encodings never propagate as unhandled exceptions to unit/AA validation code paths.

### Proof of Concept
1. Construct a 48-character string that is a mix of valid base64 characters and characters outside the base64 alphabet (e.g., `!`, `*`) such that `Buffer.from(str, 'base64')` returns a buffer whose length isn't 36 bytes.
2. Pass this string as an address (e.g., in a unit's `authors[].address`, an AA trigger address, or a `definition` authentifier) so that `isValidAddress`/`isValidChash` → `chash.isChashValid` is invoked [6](#0-5) .
3. `separateIntoCleanDataAndChecksum` receives a `bin` whose length is neither 160 nor 288 and throws `Error("bad length=...")` outside of any try/catch in `isChashValid` [5](#0-4) [7](#0-6) , propagating as an unhandled exception to whichever validation routine called it.
