### Title
Webhook signature is verified against `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` field, allowing cross-organization payload forgery - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to check the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')`. Once the signature is accepted, every `Shipit::Webhooks::Handlers::Handler` subclass resolves the actual `Repository`/`Stack` to mutate using a *different* JSON field, `payload.dig('repository', 'full_name')`, which is never checked against the organization whose secret validated the request. Because both fields live in the same attacker-controlled JSON body, an operator who legitimately owns a webhook secret for one configured organization can forge a payload whose `repository.owner.login` matches their own org (so the HMAC check passes) while `repository.full_name` names a stack belonging to an entirely different organization on the same multi-tenant Shipit instance.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` picks the signing secret this way: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), and `Shipit.github(organization: repository_owner)` looks up that organization's `webhook_secret` from `Shipit.github_apps` config to verify the HMAC. This only proves the sender knows the secret for the organization named in that specific sub-field.

Every downstream handler, however, resolves which `Repository`/`Stack` record to operate on from a *different* field, `repository.full_name`, via the shared base class: [3](#0-2) 

`PushHandler` uses this to find stacks and trigger a GitHub sync: [4](#0-3) 

`StatusHandler` uses `sha` alone (no repo/owner check at all) to write commit statuses that feed CI/merge-queue gating: [5](#0-4) 

`PullRequest::ClosedHandler` independently re-reads `params.repository.full_name` to locate the repository and archive its review stack: [6](#0-5) 

Nothing in this chain re-derives `repository.full_name`'s owner and compares it to `repository_owner`/`organization.login`, the value that was actually authenticated. The equality the code implicitly assumes but never enforces is:

`organization authenticated by verify_signature (repository.owner.login) == organization that owns the repository.full_name acted upon by the handler`

Before the attack: for a legitimate webhook, GitHub itself guarantees `repository.owner.login` and `repository.full_name`'s owner segment refer to the same repository, so this equality always holds naturally.

After the attack: an entity holding a valid `webhook_secret` for `org-A` (i.e., anyone who administers a GitHub App/webhook config for one org hosted on a shared, multi-tenant Shipit instance) can POST to `/webhooks` with `repository.owner.login = "org-A"` (or `organization.login = "org-A"`) so the signature check passes against `org-A`'s secret, while setting `repository.full_name = "org-B/victim-repo"`. The handler layer then acts on `org-B`'s stack using data the attacker fully controls (fake commit SHAs, fake CI `state`/`context`, fake `push.after` head SHAs, fake pull-request `closed` events), even though the attacker has no webhook credential for `org-B` at all.

### Impact Explanation
This breaks the trust boundary between "organization that authenticated" and "repository that is written," which is explicitly one of the impact classes this analysis is scoped to protect. Concretely, on a multi-tenant Shipit deployment (multiple orgs configured in `Shipit.github_apps`), an attacker who legitimately controls only their own org's webhook secret can:
- Inject arbitrary GitHub commit statuses via `StatusHandler` for `org-B`'s commits, directly manipulating `all_status_checks_passed?` used by `MergeRequest#merge!` and the merge queue (`ProcessMergeRequestsJob`), which can push a merge queue toward an unauthorized merge in a repository they don't control.
- Force `sync_github` on `org-B` stacks (`PushHandler`), or archive `org-B` review stacks (`ClosedHandler`), causing cross-repository writes to state the attacker has no legitimate access to.

This satisfies the "unauthorized deploy/rollback/merge" and "cross-repository writes" impact bar, crossing an authentication boundary without needing a Shipit session, `ApiClient` token, or repository write access to `org-B` — only a webhook secret for any one configured org.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with more than one GitHub organization/app entry (as `test/dummy/config/secrets_double_github_app.yml` demonstrates is a supported configuration) and requires the attacker to possess a valid webhook secret for at least one of them — which is a much lower bar than compromising `org-B`'s own credentials, GitHub App private key, or a Shipit session/API token. The `WebhooksController` performs no additional cross-field consistency check, so the forged payload is accepted as-is by `verify_signature` before being routed to handlers that trust `repository.full_name` unconditionally.

### Recommendation
After computing `repository_owner` for signature verification, re-validate that it matches the owner segment parsed from `params.dig('repository', 'full_name')` (and `organization.login` when present) before dispatching to any handler; reject the request (422) on mismatch. Alternatively, have `Handler#repository_name` receive the already-authenticated organization as a required argument and assert it against the owner segment of `full_name` rather than trusting the raw payload field in isolation.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `org-A` (`webhook_secret: secretA`) and `org-B` (`webhook_secret: secretB`), both with existing stacks in the DB (mirrors `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who only knows `secretA`, craft a `status` (or `push`) webhook body:
```json
{
  "sha": "<commit sha belonging to org-B/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/victim-repo" }
}
```
3. Sign the raw body with `secretA` using GitHub's standard `sha1=HMAC` scheme and set it as `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` calls `Shipit.github(organization: 'org-A').verify_webhook_signature(...)`, which succeeds because the signature was computed with `secretA`. `StatusHandler#process` then finds `Commit.where(sha: ...)` for `org-B/victim-repo` (no owner cross-check) and records the forged `success` status, exactly as if `org-B`'s own webhook had reported it — despite the attacker never possessing `secretB`.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
