### Title
Bridge `handle*Transfer` Functions Bypass `isRunning` Emergency Stop — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

### Summary

The Kaia service-chain bridge has an `isRunning` flag that the owner can set to `false` to halt all value transfers in an emergency. The three `request*Transfer` entry-points correctly enforce this flag, but the three `handle*Transfer` functions — which actually release or mint assets on the destination chain — contain no `isRunning` check. Automated bridge operators will therefore continue to settle pending cross-chain requests and release/mint KLAY, ERC-20, and ERC-721 tokens even after the bridge has been stopped, defeating the emergency-stop mechanism entirely.

### Finding Description

`BridgeTransfer` stores the bridge's running state: [1](#0-0) 

`setRunningStatus` / `start` let the owner flip it to `false`: [2](#0-1) 

Every `request*Transfer` path enforces the flag before accepting a new cross-chain request:

- `_requestKLAYTransfer`: [3](#0-2) 
- `_requestERC20Transfer`: [4](#0-3) 
- `_requestERC721Transfer`: [5](#0-4) 

The three `handle*Transfer` functions, however, contain **no** `isRunning` check. They proceed directly to asset release/mint after only a nonce check and operator vote:

- `handleKLAYTransfer` (releases KLAY via `.call.value`): [6](#0-5) 
- `handleERC20Transfer` (mints or transfers ERC-20): [7](#0-6) 
- `handleERC721Transfer` (mints or transfers ERC-721): [8](#0-7) 

The same asymmetry exists for the per-token lock flags (`isLockedKLAY`, `lockedTokens`): `_requestKLAYTransfer` applies the `unlockedKLAY` modifier and `_requestERC20/721Transfer` applies `onlyUnlockedToken`, but none of the `handle*Transfer` functions check the corresponding lock state.

### Impact Explanation

When the bridge owner calls `setRunningStatus(false)` (or `start(false)`) to halt the bridge — for example, because a bug or insolvency has been detected — the automated operator relayers have a backlog of already-observed `RequestValueTransfer` events queued in `processingPendingRequestEvents`. Those relayers will continue to call `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` on the destination bridge, releasing or minting real assets to recipients. The emergency stop is therefore ineffective: assets continue to flow out of the bridge contract after the owner has explicitly ordered a halt.

In `modeMintBurn` mode the impact is direct token inflation — the destination bridge mints new ERC-20/ERC-721 tokens for every pending request regardless of the stopped state. In lock/unlock mode the bridge's own token reserves are drained.

### Likelihood Explanation

Bridge operators are automated off-chain relayers (`handleRequestValueTransferEvent` in `node/sc/bridge_manager.go`): [9](#0-8) 

They process every event in their pending queue without consulting `isRunning`. An emergency stop is most likely to be triggered precisely when there is a large backlog of pending requests (e.g., during an exploit), so the window during which `handle*Transfer` continues to execute after the stop is widest exactly when the damage is greatest.

### Recommendation

Add an `isRunning` guard to all three `handle*Transfer` functions, mirroring the check already present in the `request*Transfer` paths:

```solidity
require(isRunning, "stopped bridge");
```

Similarly, `handleKLAYTransfer` should check `!isLockedKLAY`, and `handleERC20Transfer` / `handleERC721Transfer` should check `!lockedTokens[_tokenAddress]`, so that per-asset locks are also respected on the settlement side.

### Proof of Concept

1. Bridge owner detects an exploit and calls `bridge.start(false)` on the destination bridge, setting `isRunning = false`.
2. The automated operator relayer has 50 `RequestValueTransfer` events already queued from the source chain.
3. The relayer calls `handleERC20Transfer(...)` for each queued event. Because `handleERC20Transfer` contains no `isRunning` check, all 50 calls succeed.
4. In `modeMintBurn` mode, `ERC20Mintable(_tokenAddress).mint(_to, _value)` is executed 50 times, minting tokens to recipients even though the bridge was stopped. [10](#0-9) 
5. The emergency stop has been completely bypassed; the bridge continues to issue assets after the owner's halt command.

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}
