### Title
Unpinned route-pool addresses let route-selected third-party code drain the caller's wallet under the signed auth tree — ([File: contracts/swap-aggregator/src/execute/mod.rs])

### Summary
The bug class is "an external action is referenced by a mutable/unsigned identifier (version tag) instead of a pinned digest." On-chain, the equivalent is a contract invoking third-party code at an address that is not pinned or allowlisted. XOXNO's swap flow has exactly this shape: the `swap: Bytes` payload names the pool and token addresses for each hop, the router invokes whatever the payload names ("The router calls the pool and token addresses its payload names and keeps no allowlist of them"), and the controller executes that route under the caller's authorization. A rogue hop pool can call `token.transfer(victim, attacker, amount)` for any token the victim owns; Soroban records that call as a child of the victim's `swap_collateral`/`execute_strategy` auth entry, and it executes once the victim signs the simulated tree — identical in effect to a swapped-out GitHub Action stealing the job's credentials.

### Finding Description
`swap_collateral` (and `swap_debt`, `repay_debt_with_collateral`, `multiply`) accept attacker-influenced route bytes and forward them to the configured router ( [1](#0-0) ). The controller binds only one exact input transfer via `authorize_transfer_as_current` ( [2](#0-1) ), and its measured-delta checks bound only the controller's own balances ( [3](#0-2) ). Nothing bounds what route-selected code does under the *caller's* `require_auth` entry. The threat model concedes the bound "covers the controller's own grant only" and that a route "can put third-party code on the call stack below the caller's authorization," where "the loss is then the caller's wallet, not the routed amount" ( [4](#0-3) ).

The harness test proves the mechanics end-to-end: a router double invokes the pool address the payload names ( [5](#0-4) ); the rogue pool transfers the victim's entire balance of an unrelated wallet token ( [6](#0-5) ); simulation records the theft as a child of the victim's `swap_collateral` entry ( [7](#0-6) ); and in enforcing mode the signed poisoned tree moves the funds ( [8](#0-7) ). Source-account credentials (single-signature flow without an entry signature) are equally affected ( [9](#0-8) ).

### Impact Explanation
Theft of user funds. A user who signs a route containing a malicious hop loses any token balance in their wallet — the loss is unbounded by `amount_in`, the route `min_out`, or the controller's risk gates, which are the quantities a user reasonably believes they are risking.

### Likelihood Explanation
One unprivileged attacker deploys a rogue "pool" contract and gets a victim to submit a route referencing it — e.g., by serving the poisoned `routeXdr` through a compromised or look-alike quote path, or by inducing `execute_strategy` directly on the router. The victim's signing UX shows an ordinary simulated auth tree; the extra child transfer is a nested detail most wallets do not surface. Medium likelihood.

### Recommendation
Pin the external code the route can reach: maintain an on-chain allowlist of vetted pool/token contract addresses (or wasm hashes) in the router and reject hops naming unlisted contracts — the on-chain analog of pinning actions to a SHA. Until then, clients must decode `routeXdr` and reject any simulated authorization tree with children beyond the single expected input `transfer` ( [10](#0-9) ).

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows simulation silently folding `transfer(alice → attacker, WALLET_BALANCE)` into Alice's auth root, and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the signed tree executes the theft while the honest route passes cleanly.
