**Why the premise is false:** `v1::Message.lifetime_specifier` is not a distinct "nonce-derived encoding" — it is the exact same `Hash` type serving the identical semantic role as `recent_blockhash` in legacy/v0 messages (just renamed in the v1 format). This is confirmed by:

- The `RuntimeTransaction` view conversion, which builds a `v1::Message` directly from `recent_blockhash: Hash` and assigns it to `lifetime_specifier`: [1](#0-0) 
- A test constructing a `v1::Message` with `lifetime_specifier: Hash::new_unique()`, showing the field is typed and populated exactly like a blockhash: [2](#0-1) 
- The UI encoding path treating `lifetime_specifier.to_string()` as the `recent_blockhash` string for both raw and parsed message views, confirming semantic equivalence: [3](#0-2) 
- Nonce validation (`verify_nonce_account`) operates on `message.recent_blockhash()`, and the durable-nonce value stored on-chain is itself a `Hash`, so whichever message version supplies it, the comparison is a `Hash == Hash` check: [4](#0-3) 

Given `lifetime_specifier` and `recent_blockhash` are the same `Hash`-typed value with the same meaning (the durable-nonce hash or recent blockhash used for transaction lifetime/replay protection), the conversion in `storage-proto/src/convert.rs` at lines 342-393 (`impl From<v0::Message>` and `impl From<v1::Message>`) is a straightforward field rename mapping, not a semantic collision or misrepresentation: [5](#0-4) . There is no "distinct encoding" that gets flattened into a `Hash` incorrectly — it already is a `Hash`, and the archived `generated::Message.recent_blockhash` accurately preserves the durable-nonce value used to authorize the transaction, exactly as it does for v0. No unprivileged attacker action can create a divergence here since the value transformation is a lossless, type-preserving field copy.
