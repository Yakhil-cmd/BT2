### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login`, but event processing acts on the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the request against using `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). [1](#0-0) [2](#0-1)  But the actual event handlers that mutate state resolve the target repository/stack from a **different, unrelated payload field**: `payload.dig('repository', 'full_name')`, used both in `Handler#repository_name`/`#stacks` and in each handler (`PushHandler`, `label_capturing_handler`, `review_stack_adapter`, etc.). [3](#0-2) [4](#0-3) 

### Finding Description
The signature check only proves that the request was signed with the webhook secret configured for the organization named in `repository.owner.login` (or `organization.login`). It does not verify any relationship between that value and `repository.full_name`, which is a completely separate, attacker-controlled JSON field in the same payload. Because Shipit supports multi-org configuration (`Shipit.github(organization:)`, keyed per-org secrets in `config/secrets.yml`), a party who legitimately controls the webhook secret for **Org A** can craft a payload where `repository.owner.login = "OrgA"` (so it passes `verify_webhook_signature` using OrgA's secret) while `repository.full_name = "OrgB/some-repo"`. Handlers never re-check that `full_name`'s owner matches the organization whose secret authenticated the request; they simply do `Repository.from_github_repo_name(repository_name)` and act on whatever stack that resolves to. [5](#0-4)  This is exactly the analog of the CLOB bug class: a validation performed on one representation of the data (`baseTokenAmountReceived & quoteTokenAmountSent`, here `repository.owner.login`) doesn't actually constrain the value that is later acted upon (`quoteTokenAmountSent`/`baseTokenAmountSent`, here `repository.full_name`), because the two are only loosely related and never cross-checked.

### Impact Explanation
An attacker who controls (or has compromised) the webhook delivery for one onboarded GitHub organization/repository can produce validly-signed payloads that reference and mutate a **different** repository's stack (e.g., trigger `GithubSyncJob`, create commits/statuses, provision/deprovision review stacks, or manipulate pull-request-driven review stack lifecycle for a repo they do not own) — as long as any stack for that `full_name` exists in Shipit. This crosses the "cross-repository writes" impact bucket defined in scope.

### Likelihood Explanation
Low-to-moderate. Requires: (1) the engine configured with multiple GitHub organizations/apps (a documented, supported configuration — see `config/secrets.development.example.yml` showing the multi-org schema), and (2) attacker control of a legitimate webhook secret for at least one onboarded org (e.g., a malicious/compromised repo admin in Org A). Given those preconditions, forging the mismatched payload is trivial since `repository.full_name` and `repository.owner.login` are independent JSON fields with no cross-field validation.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handlers::Handler`), assert that the organization portion of `repository.full_name` matches `repository.owner.login`/`organization.login` used for signature selection, rejecting (422) any payload where they diverge, before dispatching to handlers.

### Proof of Concept
1. Onboard two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` in `secrets.yml`, and a stack for `OrgB/target-repo`.
2. As a holder of `OrgA`'s webhook secret, POST to `/webhooks` a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Sign the raw body with `OrgA`'s `webhook_secret` and set `X-Hub-Signature` accordingly.
4. `verify_signature` resolves `repository_owner == "OrgA"`, validates successfully against OrgA's secret. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `repository.full_name == "OrgB/target-repo"` and triggers `stack.sync_github` for OrgB's stack — despite the request never being authenticated by OrgB's secret. [4](#0-3)
