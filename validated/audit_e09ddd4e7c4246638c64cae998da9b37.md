Confirmed: multi-organization Shipit deployments configure per-organization `webhook_secret` values under distinct keys in `secrets.github` [1](#0-0) . The organization used to select which secret verifies a webhook is derived from the still-unauthenticated payload before the signature check runs.

### Title
Webhook signature is verified against an organization key chosen from the same untrusted payload used for repository targeting, allowing cross-organization webhook forgery in multi-org deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to validate the HMAC signature against by reading `repository_owner` straight out of the unauthenticated JSON body, then hands the very same body to the event handlers, which independently re-read `repository.full_name` to decide which `Repository`/`Stack` to mutate [2](#0-1) .

### Finding Description
The binding the engine relies on is: *the organization whose secret validated the signature* == *the organization whose repository the handler acts on*. In a single-org deployment this holds trivially because there is one secret. But `Shipit.github` supports a per-organization config keyed by organization login, with `github_app_config(organization)` doing a simple hash lookup on the organization name pulled out of the payload [3](#0-2) .

`verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` — fields controlled entirely by whoever sends the HTTP POST, before any cryptographic check has happened — and uses that value to select which `GitHubApp`/secret verifies `request.headers['X-Hub-Signature']` against `request.raw_post` [4](#0-3) . Once `verify_webhook_signature` returns true, `create` re-parses the same raw body and dispatches it to handlers keyed only by `X-Github-Event` [5](#0-4) . Handlers such as `Handler#repository_name` / `stacks` derive the target repository from `payload.dig('repository','full_name')` — a *different* field of the same JSON body, never covered by the org-selection logic and never re-checked against `repository_owner` [6](#0-5) .

An attacker who legitimately controls a GitHub App installation on **their own** organization (`attacker-org`) knows that organization's `webhook_secret` (it's visible in their own GitHub App settings). They can craft a payload where `repository.owner.login` = `"attacker-org"` (so `verify_signature` looks up and validates against the attacker's own known secret) but `repository.full_name` = `"victim-org/victim-repo"` (so the dispatched handler operates on the victim's tracked repository/stack). Because the two fields are read independently and neither the controller nor `Handler` cross-checks them, a validly-signed-but-crafted webhook from one tenant's org can trigger sync/status/check-run/pull-request mutations against another tenant's `Stack` in the same Shipit instance — this mirrors the `benRevocable` bug class: a value acted upon (`repository.full_name`) is never covered by the check that is supposed to gate the action (the signature verification keyed on `repository.owner.login`).

### Impact Explanation
This crosses the "cross-repository writes" bar: a party in control of one organization's webhook secret can inject synthetic `push`, `status`, `check_suite`, or `pull_request` events for repositories belonging to a different organization hosted on the same Shipit instance, causing `GithubSyncJob` enqueues, spurious commit statuses, check-run state changes, and PR metadata updates for a repo/stack they don't own [7](#0-6) [8](#0-7) . Depending on downstream automation gated on commit status/check-run state (e.g., merge or deploy gating), this can influence deploy/merge decisions on the victim's stack.

### Likelihood Explanation
Requires: (1) the Shipit instance is configured for multiple organizations via the keyed `secrets.github` schema (opt-in, but documented/supported) [9](#0-8) , and (2) attacker legitimately controls one of those configured organizations/apps and thus its `webhook_secret`. No repository write access or Shipit account is needed — only knowledge of one's own configured org's webhook secret plus network access to the public webhook endpoint. This is realistic for shared multi-tenant Shipit deployments.

### Recommendation
After signature verification succeeds, re-validate that the organization implied by every payload field the handlers actually consume (`repository.full_name`'s owner segment) matches the `repository_owner` value that selected the verifying secret, rejecting (422) on mismatch. Alternatively, resolve `Repository`/`Stack` from `full_name` first and derive the webhook-secret lookup from the *resolved* Repository's stored owner rather than from unauthenticated payload fields, or pin one canonical field to be the sole source of truth for both the secret lookup and the handler dispatch.

### Proof of Concept
1. Attacker configures a GitHub App on `attacker-org`, obtaining `webhook_secret_A` per the multi-org `secrets.github` schema [3](#0-2) .
2. Attacker crafts JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "after": "<sha>", ...}` for a `push` event.
3. Attacker computes `X-Hub-Signature` using `webhook_secret_A` over the exact raw body and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature [10](#0-9) .
5. `create` dispatches to the `push` handler, which resolves the target stack from `repository.full_name` = `"victim-org/victim-repo"` and enqueues `GithubSyncJob` for the victim's stack — an event the attacker had no authorization to originate.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
