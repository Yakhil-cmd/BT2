### Title
Missing sequence/validity check in `dataFeedExists` allows a doomed (final-bad) unit's data feed to satisfy oracle checks in AA formulas - (File: data_feeds.js)

### Summary
`dataFeedExists()` in [1](#0-0)  scans `storage.assocUnstableMessages` for unstable AA-authored `data_feed` messages to answer `data_feed[[...]]` "exists" queries used by AA oscript formulas. Unlike the sibling function `readDataFeedValue()`, which explicitly filters out invalid units with `if (objUnit.sequence !== 'good') continue;` at [2](#0-1) , `dataFeedExists` performs no such check on `objUnit.sequence` before scanning its messages for a match, as seen at [3](#0-2) .

### Finding Description
This mirrors the reported SDK bug class: a state/event is consumed from a unit without first checking whether that unit is a valid, "good"-sequence unit (the ocore analog of Solana tx `is_err`). In ocore, a unit can be marked `sequence = 'final-bad'` (e.g., loser of a double-spend, or an equivalent invalidity condition) while it is still unstable and present in `storage.assocUnstableMessages` — the deletion/exclusion of a final-bad unit's messages from that map only happens later, at stabilization time in `main_chain.js`'s `saveUnstablePayloads()` (`if (objUnitProps.sequence === 'final-bad'){ delete storage.assocUnstableMessages[unit]; return cb(); }`, as observed in [4](#0-3) ). Between the time a unit's sequence becomes `final-bad` and the time it stabilizes, `dataFeedExists` will still iterate over and match its `data_feed` message, because it only checks `!objUnit.bAA`, MCI range, and author intersection — never `objUnit.sequence` — at [3](#0-2) .

`readDataFeedValue`, used for the same purpose (unstable AA data feed lookups) elsewhere, correctly filters this window out: [5](#0-4)  shows the `if (objUnit.sequence !== 'good') continue;` guard that `dataFeedExists` lacks. This asymmetry is the exact root cause pattern flagged in the external report: failing to check the finalized error/validity state of a unit/transaction before consuming its emitted data for downstream logic.

### Impact Explanation
`dataFeedExists` backs the `data_feed[[...]]` "exists" check used inside AA oscript formulas (posted by any user triggering an AA, or embedded in an AA's own logic when it reads unstable oracle data). If a malicious poster crafts a double-spend where one of the conflicting units carries a spoofed `data_feed` message, that unit will be flagged `sequence='final-bad'` yet can remain visible to `dataFeedExists` while unstable. An AA relying on `data_feed_exists`-style checks against unstable feeds (`unstable_opts`) could then branch on the presence of a feed value that will never actually be confirmed/valid, since the underlying unit is guaranteed to be excluded at stabilization. Depending on the AA's logic, this can cause it to release funds, mint/burn balances, or otherwise finalize state transitions based on a condition that should never have been true — a concrete AA fund-loss/inconsistent-state scenario, and a source of node disagreement about a triggered response if nodes evaluate the check at different points relative to sequence determination vs. stabilization.

### Likelihood Explanation
Reaching this path requires only posting a self-authored double-spending pair of units where one of them carries the spoofed `data_feed` message and is destined to lose sequencing — something any ordinary unprivileged unit poster can construct. No special network position, hub/peer compromise, or leaked keys are required, and the trigger is a single posted unit pair plus an AA that consults `data_feed_exists` against unstable data feeds.

### Recommendation
Add the same validity guard used in `readDataFeedValue` to `dataFeedExists`'s scan of `storage.assocUnstableMessages`: skip units whose `objUnit.sequence !== 'good'` before evaluating their `data_feed` messages, i.e. mirror the check at [2](#0-1)  inside the loop at [3](#0-2) .

### Proof of Concept
1. Attacker crafts unit A and unit B that double-spend the same input, with unit B (or A) carrying a `data_feed` message with a payload the attacker wants an AA to "see" as existing (e.g., `{ "PRICE_FEED_EXISTS": "1" }`).
2. Both units are broadcast; the node determines `sequence` for the loser (e.g., `final-bad`) as soon as the conflict is detected, prior to MC stabilization, while both units remain in `storage.assocUnstableMessages`.
3. Before stabilization completes, a unit triggers an AA whose oscript formula calls the `data_feed_exists`-backed check against unstable data feeds for the attacker's authoring address/feed name.
4. `dataFeedExists` iterates `storage.assocUnstableMessages`, finds the `final-bad` unit's `data_feed` message (no `sequence` filter applied), and reports the feed as existing — even though this unit's data feed will be dropped once it stabilizes and will never be included by `readDataFeedValue`'s "good"-sequence-only search.
5. The AA acts on the false-positive existence check (e.g., releasing funds or updating state), producing an outcome inconsistent with what will actually be confirmed on-chain.

*(Note: I was unable to directly confirm the exact oscript keyword mapping to `dataFeedExists` in `formula/evaluation.js` beyond seeing it referenced 3 times there and in `definition.js`; a full trace of the formula opcode name was not completed due to the iteration limit. This does not affect the validity of the root-cause finding in `data_feeds.js`, but confirming the exact caller/opcode name would strengthen the PoC.)*
