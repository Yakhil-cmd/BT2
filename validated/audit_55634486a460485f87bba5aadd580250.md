### Title
Cross-repository status forgery enables unauthorized PR merge via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to update purely by git `sha`, with no repository or stack scoping, even though `Shipit::WebhooksController#verify_signature` only proves that the *payload's named repository/organization* legitimately sent the webhook — not that the sha belongs to that repository. Because git commit shas are shared across forks/clones, an attacker who controls (or has legitimate write access to) any repository tracked by the same Shipit instance can cause a forged/real "success" `Status` row to be attached to a commit that actually belongs to an unrelated victim repository, unblocking `ProcessMergeRequestsJob` to merge a victim PR that never had real CI results.

### Finding Description
The claimed binding is: `repository_that_authenticated_the_webhook == repository_owning_the_commit_being_mutated`. Tracing the code shows this binding is never enforced.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) resolves `github_app = Shipit.github(organization: repository_owner)` from the payload's own `repository.owner.login`/`organization.login`, and verifies the HMAC signature against that org's `webhook_secret`. This only proves the request came from GitHub for *some* org/repo the instance trusts — it says nothing about which `Commit`/`Stack` the payload's `sha` should apply to.
- `Shipit::Webhooks::Handlers::StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` **globally by `sha` only**, with no filter on `repository_name`/`stack`, even though the base `Handler` class already provides a `repository_name`/`stacks` helper (app/models/shipit/webhooks/handlers/handler.rb:32-38) that other handlers could use to scope by repository — `StatusHandler` does not use it.
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (app/models/shipit/commit.rb:165-169, app/models/shipit/status.rb:23-33) creates the `Status` using the **commit's own `stack_id`** (the victim's), not any stack derived from the attacker's payload. So the forged status is fully "legitimate-looking" from the victim stack's perspective.
- `MergeRequest#any_status_checks_missing?` / `#all_status_checks_passed?` (app/models/shipit/merge_request.rb:193-206) build a `StatusChecker` from `head.statuses_and_check_runs`, which now includes the forged `success` Status, making `missing?` false and `success?` true.
- `ProcessMergeRequestsJob#perform` (app/jobs/shipit/process_merge_requests_job.rb:10-32) calls `reject_unless_mergeable!` (passes, since `any_status_checks_missing?` is now false) then `all_status_checks_passed?` (true) then `merge_request.merge!`, which calls `stack.github_api.merge_pull_request(...)` (app/models/shipit/merge_request.rb:169-176) using the app's own `GITHUB_TOKEN`.

Exploit flow: attacker opens PR #N on `victim/prod` (head sha `S`). Because `S` is a normal git commit object, it is trivially reproducible/obtainable by forking `victim/prod` (fork shares identical git objects/shas) into `attacker/evil`, a repository also tracked by the same Shipit instance (or any other repo tracked by the same instance where the attacker can push that exact commit object). The attacker then triggers a `status` event for sha `S` in `attacker/evil` (either via GitHub's real Status API on their own repo — producing a *validly signed* webhook when the instance uses a single shared GitHub App/webhook secret for the org, or by directly posting to `POST /webhooks` if they can produce a valid signature for their own org). `verify_signature` passes because the payload correctly identifies `attacker/evil`'s owner. `StatusHandler#process` then finds **every** `Commit` row (across all stacks/orgs) with `sha == S`, including the victim's PR head commit, and writes a `success` Status scoped to the victim's stack. This defeats `any_status_checks_missing?`, allowing `reject_unless_mergeable!` to fall through and the merge queue to merge the victim's unreviewed PR.

Existing guards do not catch this: `verify_signature` checks org-level authenticity, not sha-to-repo ownership; `ExplicitParameters` only validates the shape/types of the status payload (`sha`, `state`, etc.), not its origin; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
This allows an unauthorized merge of a pull request into the victim's default branch (Critical category: "a payload for one repository mutating another's stack, commit, task, or team" / "an unauthorized deploy, rollback or merge"), executed via the app's own `GITHUB_TOKEN`/GitHub App installation token. The attack is repeatable against any repository/stack tracked by the same Shipit instance that shares (or can be made to share) commit shas with a repository the attacker controls — most straightforwardly via a fork, which by git's nature preserves identical commit objects/shas for unmodified history. Blast radius: any multi-tenant Shipit deployment tracking more than one repository/stack is affected, since `Commit.where(sha:)` has zero tenant isolation.

### Likelihood Explanation
Preconditions: (1) the Shipit instance must track at least one repository/stack the attacker can influence (push access to a fork, or being an unprivileged contributor able to trigger `status` events, e.g. via their own CI/webhook on a repo they control that's also onboarded to Shipit); (2) the target PR's head commit must have no real CI status yet (`ci_missing` window) — a normal, common race window right after a PR is opened; (3) if the instance uses per-organization GitHub Apps, the attacker's controlled repo must belong to the same org as the victim (single shared `webhook_secret`) for a "real" GitHub-signed status to work without needing to forge HMAC; cross-org exploitation would additionally require guessing/leaking the victim org's `webhook_secret`. Given a very common single-org, multi-repo Shipit deployment (the default/simple configuration documented in `docs/setup.md`), attacker cost is very low: fork the target repo, add it as (or reuse) a Shipit-tracked repo/stack, and post a real GitHub status on that sha. No Shipit credentials, sessions, or webhook secrets are required in the common single-org case.

### Recommendation
Scope `StatusHandler#process` (and any other webhook handler that resolves records purely by `sha`) to the repository named in the payload, mirroring the `stacks`/`repository_name` helper already defined in `Shipit::Webhooks::Handlers::Handler`. E.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status webhook can only affect commits belonging to stacks whose `Repository` matches `payload.repository.full_name`, restoring the binding between the authenticated repository and the mutated record.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or a new job/model test):
1. Seed two stacks: `victim_stack` for `victim/prod` and `evil_stack` for `attacker/evil`.
2. Create a `MergeRequest`/PR fixture on `victim_stack` whose `head` commit has `sha = "deadbeef..."` and **no** `Status` rows (so `any_status_checks_missing?` is true, `ci_missing` would normally reject).
3. Also create a `Commit` with the same `sha = "deadbeef..."` belonging to `evil_stack` (simulating the shared-object fork).
4. Stub `GithubHook`/`verify_signature` (or `GitHubApp#verify_webhook_signature`) to return true for `attacker/evil`'s org (simulating a validly signed webhook from the attacker's own repository).
5. POST to `/webhooks` with `X-Github-Event: status` and a body whose `repository.full_name == "attacker/evil"`, `sha == "deadbeef..."`, `state == "success"`.
6. Assert: `victim_pr.head.reload.statuses.count == 1` and `victim_pr.head.statuses.first.stack_id == victim_stack.id` (the equality `repository_that_authenticated == repository_owning_commit` is violated — attacker authenticated `evil_stack`'s repo but wrote a Status onto `victim_stack`'s commit).
7. Then call `Shipit.github.api.expects(:merge_pull_request)` and run `ProcessMergeRequestsJob.perform_now(victim_stack)`; assert the expectation is satisfied, proving the forged cross-repo status caused an unauthorized merge of `victim/prod`'s PR.     def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

      false
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    def any_status_checks_missing?
      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).missing?
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
