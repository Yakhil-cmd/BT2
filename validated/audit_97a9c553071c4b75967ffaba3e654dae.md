## Analysis

I traced the reward-accounting pattern in `pallet-asset-rewards` (`substrate/frame/asset-rewards/src/lib.rs`), which is architecturally the closest FRAME analog to the reported Stargate/Arcadia bug: both use a Synthetix-style "reward-per-token accumulator" that is updated JIT on every user interaction, and the accumulator's incremental math depends on a stored "last update" checkpoint being properly bounded relative to a data source (`pendingEmissionToken` in Solidity vs. `expiry_block` in FRAME).

The underflow itself is not silent in Rust (`ensure_sub` returns `Result`, it doesn't wrap), but the consequence is functionally identical to the Solidity report: the computation errors out and the dispatchable reverts — and I found a path where this is **permanent** rather than transient, because the offending state (`last_update_block`) is never corrected once broken. ### Title
Un-capped `last_update_block` past pool expiry causes permanent `ArithmeticError` underflow in `reward_per_token`, freezing all staked funds and rewards in `pallet-asset-rewards` - (File: substrate/frame/asset-rewards/src/lib.rs)

### Summary
`Pallet::<T>::update_pool_rewards` unconditionally sets `PoolInfo::last_update_block` to the current block number, even when the pool has already passed `expiry_block`. Once `last_update_block` exceeds `expiry_block`, every future call to `reward_per_token` computes `expiry_block.ensure_sub(last_update_block)`, which underflows and returns `Err`. Since `reward_per_token` is invoked by `stake`, `unstake`, and `harvest_rewards` via `update_pool_and_staker_rewards`, every subsequent dispatch on that pool fails permanently as long as `total_tokens_staked` is non-zero — which can never be reduced to zero because `unstake` itself is blocked by the same error. This permanently freezes all staked tokens and pending rewards in the pool.

### Finding Description
`reward_per_token` computes the elapsed "rewardable" blocks as: [2](#0-1) 

`last_block_reward_applicable` caps the reference point at `expiry_block`: [3](#0-2) 

But `update_pool_rewards`, called right after `reward_per_token` on every interaction, stores the *actual* current block number into `last_update_block`, without capping it at `expiry_block`: [4](#0-3) 

`unstake` and `harvest_rewards` are permissionless for *any* signed caller once the pool has expired (`now > pool_info.expiry_block`), which is the real, unprivileged user entry point that triggers the first "poisoning" write: [5](#0-4) [6](#0-5) 

Sequence:
1. Pool created with `expiry_block = E`. A staker stakes at block `B1 <= E`, setting `last_update_block = B1`.
2. Time passes to block `B2 > E`. Any signed account calls `unstake` (partial amount) or `harvest_rewards` for the staker (permitted per the `now > expiry_block || caller == staker` check). This is the *first* post-expiry interaction. Inside it, `reward_per_token` computes fine because `last_update_block (B1) <= E`. But `update_pool_rewards` then sets `last_update_block = B2` (which is `> E`), and this is persisted via `Pools::<T>::insert`.
3. As long as `total_tokens_staked > 0` after this call (e.g., a partial unstake, or a `harvest_rewards` call that doesn't touch stake), any further call to `stake`, `unstake`, or `harvest_rewards` on this pool computes `last_block_reward_applicable(E) = E` (since current block is still `> E`) and then `E.ensure_sub(last_update_block=B2)`, which underflows since `B2 > E`. `ensure_sub` returns `Err(ArithmeticError::Underflow)`, which propagates through `update_pool_and_staker_rewards` and aborts the dispatch.
4. Because `unstake` itself needs to pass through `update_pool_and_staker_rewards` before it can decrement `total_tokens_staked`, **no staker can ever unstake again**, and `total_tokens_staked` can never be driven back to zero to bypass the buggy branch (`if pool_info.total_tokens_staked.is_zero() { return Ok(...) }`). The pool is permanently bricked: all remaining staked tokens are frozen and all unharvested rewards become unclaimable.

This is the FRAME analog of the reported issue: an accumulator ("reward-per-token") delta computed from a "last recorded" checkpoint against a bounded/capped reference value, where the checkpoint update logic does not respect the same cap the read-path uses, causing every future JIT reward recomputation triggered by ordinary user extrinsics to fail.

### Impact Explanation
This is an irreversible freezing-of-funds bug reachable by any account with no privileges: it locks all staked assets and unclaimed reward assets of the affected pool once triggered, with no recovery path in the pallet's public API (there is no root/admin `force_unstake` or reset of `last_update_block`). This qualifies as High/Critical per the criteria valuing "irreversible freezing."

### Likelihood Explanation
The trigger requires only: (a) a pool reaching its `expiry_block` (a normal, expected lifecycle event, not an edge case), and (b) one ordinary post-expiry `unstake` or `harvest_rewards` call that doesn't fully drain `total_tokens_staked` to zero — both extremely likely in normal usage of a pool with multiple stakers, since the permissionless post-expiry access pattern is explicitly designed to let *anyone* clean up a stale pool on behalf of a staker. No governance, malicious collator, or privileged role is needed.

### Recommendation
In `update_pool_rewards`, cap the persisted `last_update_block` the same way `last_block_reward_applicable` caps the reward computation, e.g.:
```rust
new_pool_info.last_update_block = Self::last_block_reward_applicable(pool_info.expiry_block);
```
instead of unconditionally using `T::BlockNumberProvider::current_block_number()`. This keeps `last_update_block <= expiry_block` for all time once expired, matching the invariant `reward_per_token` already assumes, and prevents the underflow entirely.

### Proof of Concept
Not executed against a live node/CI — this is a manual trace of `substrate/frame/asset-rewards/src/lib.rs` and its existing test harness (`substrate/frame/asset-rewards/src/tests.rs`). A concrete reproduction would extend the existing `integration` test pattern as follows (conceptually, using the pallet's own mock runtime and existing test helpers `create_default_pool`, `System::set_block_number`, `StakingRewards::stake/unstake/harvest_rewards`):

1. Create a pool with a short `expiry_block` (e.g., via `DispatchTime::After(lifetime)`), two stakers `staker1`, `staker2` stake at blocks before expiry.
2. Advance the block number past `expiry_block`.
3. Have `staker2` (any account) call `harvest_rewards` for `staker1` (permitted since `now > expiry_block`), or have anyone call `unstake` with a partial amount for `staker1`, leaving `total_tokens_staked > 0`.
4. Advance the block number further (still `> expiry_block`).
5. Attempt any of `stake`, `unstake`, or `harvest_rewards` on the same pool — expect `Err(ArithmeticError::Underflow)` (or equivalent `DispatchError`) instead of `Ok(())`, and expect this failure to persist on all further attempts, with the previously staked balance permanently un-withdrawable.

I did not run this test; it is provided as the minimal reproduction path derived directly from the code paths cited above (`reward_per_token`, `update_pool_rewards`, `unstake`, `harvest_rewards`). A background engineer with repo access should implement and run this as an integration test in `substrate/frame/asset-rewards/src/tests.rs` to confirm the `Err` is returned and that the pool becomes permanently locked.

```rust
		pub fn update_pool_rewards(
			pool_info: &PoolInfoFor<T>,
			reward_per_token: T::Balance,
		) -> Result<PoolInfoFor<T>, DispatchError> {
			let mut new_pool_info = pool_info.clone();
			new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
			new_pool_info.reward_per_token_stored = reward_per_token;

			Ok(new_pool_info)
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
```
