### Title
Accrued debt-value overflow permanently freezes a market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
The accrual engine converts scaled supply and debt shares into unscaled RAY values before computing utilization, rate, and interest-index deltas. A sufficiently large borrowed position can make `borrowed * borrow_index` exceed `i128::MAX` before the borrow-index cap is reached. Because every pool mutation accrues first, the resulting `MathOverflow` permanently blocks repayment, withdrawal, liquidation, and later index updates for that market.

### Finding Description
`accrue_step` computes `borrowed_original` and `supplied_original` through `scaled_to_original`, then derives utilization, borrow rate, and a new borrow index. [1](#0-0)  `scaled_to_original` delegates to `Ray::mul`, whose result is converted back to `i128`; an unrepresentable result returns `None` and is converted into `GenericError::MathOverflow`. [2](#0-1) [3](#0-2) [4](#0-3) 

The index cap does not prevent this condition: `update_borrow_index` caps only the returned index at `MAX_BORROW_INDEX_RAY`, while the debt valuation is the product of stored shares and the index and can cross `i128::MAX` earlier. [5](#0-4) 

`global_sync` always runs the accrual step whenever time has elapsed. [6](#0-5)  The shared `synced_market` helper loads the market and calls `global_sync` before mutation-specific logic. [7](#0-6)  The permissionless controller entrypoint `update_indexes(caller, assets)` also reaches this path through `pool.update_indexes`. [8](#0-7) [9](#0-8) 

### Impact Explanation
Once the RAY-valued debt or supply calculation overflows, the market cannot perform any state-changing operation that accrues interest. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot reduce the position, and `update_indexes` cannot advance the market timestamp. The existing harness test demonstrates this end state: `update_indexes` fails with `MathOverflow`, and subsequent withdrawal and repayment attempts fail with the same error. [10](#0-9) 

This is permanent freezing of user funds in the affected market: waiting longer does not remove the overflow, and the failed accrual prevents the position from being reduced through the normal user paths.

### Likelihood Explanation
The condition requires an exceptionally large market and sustained high utilization, so it is not reachable with ordinary balances. It is nevertheless reachable by unprivileged users through normal `supply`, collateralized `borrow`, and later `update_indexes` calls; the test constructs a one-billion-token market, borrows 98% of it, and advances time until the next accrual crosses the `i128` value ceiling. [11](#0-10)  The test expects the cliff within 40 years and confirms that it occurs below `MAX_BORROW_INDEX_RAY`. [12](#0-11) 

### Recommendation
Add an explicit representable-value bound before accrual mutates or rejects market operations. In particular:

- Bound admitted scaled supply/debt totals by `i128::MAX / MAX_SUPPLY_INDEX_RAY` and `i128::MAX / MAX_BORROW_INDEX_RAY`, rather than only bounding token input amounts.
- Keep sufficient headroom below those bounds so each chunk’s new index valuation remains representable.
- Consider tracking utilization from values that cannot overflow, such as widened `I256` calculations, or fail new borrows before the market reaches the accrual cliff.
- Add an explicit protocol error for the value-domain ceiling, with a tested boundary just below it, instead of allowing the market to discover an unrecoverable `MathOverflow` after time passes.

### Proof of Concept
The repository already contains a regression test proving the reachable failure:

1. Create an 18-decimal market using the steep XLM stress curve and a collateral market.
2. Supply `1_000_000_000 * 10^18` units of the debt asset and borrow 98% of that principal.
3. Advance ledger time in one-year intervals while calling `update_indexes`.
4. Once `borrowed * borrow_index` can no longer fit into `i128`, `update_indexes` returns `MathOverflow`.
5. The stored borrow index remains below `MAX_BORROW_INDEX_RAY`, showing the index cap did not prevent the failure.
6. Subsequent `withdraw` and `repay` calls both fail because they accrue first. [13](#0-12) [14](#0-13)

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
