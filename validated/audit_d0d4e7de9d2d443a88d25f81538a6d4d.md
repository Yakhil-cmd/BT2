### Title
CCMenuController bypasses the ApiClient's stack scoping, letting a stack-scoped API token read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` scopes which `Stack` an `ApiClient` may act on by intersecting the requested `stack_id` param with the stacks the client is authorized for. `Shipit::Api::CCMenuController` overrides this scoping method and resolves the stack directly against the entire `Stack` table, breaking the binding between "the stack(s) an ApiClient token is authorized for" and "the stack the request actually touches" — the exact class of bug described in the reference report (a value used for one purpose diverging from the value used for the guarding check).

### Finding Description
`Api::BaseController` defines the authorization-scoped stack lookup: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` has a `stack_id` set (i.e., it's a stack-scoped token), and `stack` (used by every other controller such as `DeploysController`, `LocksController`, `TasksController`, `MergeRequestsController`) resolves `params[:stack_id]` only within that authorized scope.

`Api::CCMenuController`, however, redefines `stack` to bypass this scope entirely: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

This calls `Stack.from_param!` directly on the full `Stack` relation instead of the client-scoped `stacks` relation from the parent class. The controller still enforces `require_permission :read, :stack` (a *permission* check, i.e. "does this client have the `read:stack` capability at all"), but never re-checks that the specific `stack_id` in the URL is one the client's `stack_id` scoping actually grants.

The binding that should hold is:
`current_api_client.stack_id (the stack the token is authorized for) == params[:stack_id] resolved via BaseController#stacks (the stack actually touched)`

For `CCMenuController#show`, this equality is never enforced — `stack` resolves against `Stack.from_param!` unconditionally, for any `stack_id`.

### Impact Explanation
An `ApiClient` created with a narrow scope (a specific `stack_id`, e.g. issued by `CCMenuUrlController#client` with `permissions: %w[read:stack]` scoped to one stack — see [3](#0-2) ) is expected to only be able to read the CI/build status of the stack it was minted for. Because `CCMenuController#stack` ignores the scope, the holder of that legitimately-issued, narrowly-scoped token can supply an arbitrary `stack_id` in the request path and read the latest deploy/build status (`deploys_and_rollbacks.last`, lock state, last build label, etc.) of any other stack in the installation — an unauthorized cross-stack read of deploy/build state, exactly the "unauthenticated/unauthorized read of stack state" impact category for this engine.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped API tokens (this is the built-in, documented mechanism via `CCMenuUrlController`, which auto-creates a `read:stack`-scoped `ApiClient` per stack). Any holder of one such token — which by design is meant to be embeddable in third-party CI dashboard tools and is therefore lower-trust than a full-access client — can trivially enumerate other `stack_id`s (stack ids/params are not secret; they appear in the UI/URLs) and pull their CI status. No additional privilege beyond possessing one legitimately-scoped read token is required.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction is honored the same way it is for every other API controller.

### Proof of Concept
1. Create two stacks, A and B.
2. Via `CCMenuUrlController#fetch` (or directly), obtain a `read:stack` `ApiClient` scoped to `stack_id: A` (`ApiClient.stack_id = A.id`).
3. Authenticate as that client and request `GET /api/stacks/:stack_id/cc_menu.xml` with `stack_id` set to `B.to_param` instead of `A.to_param`.
4. `authenticate_api_client` succeeds (valid token), `require_permission :read, :stack` succeeds (client has `read:stack` permission), and `stack` resolves to `Stack.from_param!(B.to_param)` — bypassing the `stacks` scoping that would otherwise raise a not-found for any stack other than A. The response reveals B's latest deploy/build status even though the token was only ever authorized for A. [4](#0-3) [5](#0-4)

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
