### Title
ECDSA signature malleability via unenforced canonical low-S in `signature.js` allows unit-hash malleation - (File: signature.js)

### Summary
`signature.verify()` in [1](#0-0)  validates authentifiers/authentications for units, device messages, and signed packages using `secp256k1.ecdsaVerify()` from the npm `secp256k1` package (backed by libsecp256k1), without any additional check that `S` is in the canonical "low-S" half of the curve order. Unlike the reported gnark bug, libsecp256k1's compact-signature parser does reject `r`/`s` values `>= order`, so the specific `S >= order` overflow forgery from the report does not apply verbatim. However, the underlying bug *class*—insufficient scalar constraints in a signature-verification circuit/routine allowing multiple distinct `(R,S)` witnesses to validate against the same public inputs—has a direct, reachable analog here: standard ECDSA is symmetric under `S → n−S` (both values are `< n` and both pass the identical verification equation, since only the x‑coordinate of the recovered point is checked). Because `signature.verify()` never calls `ecdsa.signatureNormalize()` (as is done for the PEM/secp256k1 path in [2](#0-1) ) before verifying, both the original `S` and its negation `n−S` are accepted as valid signatures over the exact same message hash and public key.

### Finding Description
The `sig` authentifier evaluator directly calls `ecdsaSig.verify()` on the raw base64 signature supplied in the unit, with no low-S canonicalization step: [3](#0-2) 

The same unconstrained `verify()` is reused for device pairing/login messages and hub temp-pubkey packages: [4](#0-3) [5](#0-4) 

Critically, `object_hash.getUnitHash()`—which computes the canonical unit ID used everywhere as `unit` (parent references, spend references, DAG storage key)—hashes the *stripped* unit including its content hash derived from the full unit body, while only `getUnitHashToSign()` strips out `authentifiers` before hashing for signing purposes: [6](#0-5) [7](#0-6) 

Because the message that gets signed (`unit_hash_to_sign`) excludes the `authentifiers` field, but the authentifiers (containing the signature) are part of the unit content that feeds into `getUnitContentHash()`/`getUnitHash()`, flipping any author's signature `S` component to `n−S` produces a byte-for-byte semantically-identical unit (same inputs, outputs, messages, definitions, parents) that still satisfies `validateAuthentifiers()` (via `ecdsaSig.verify()`), yet hashes to a **different unit ID**.

### Impact Explanation
Any party who observes a broadcast-but-not-yet-stable unit (the original poster themselves, a paired device, or any counterparty that has visibility of the raw signed unit before it reaches finality, e.g. in a private-payment chain handoff) can re-derive an alternate, equally valid unit with a different `unit` hash. This breaks the implicit assumption that a specific `unit` hash uniquely and durably identifies a given signed transaction before stabilization:
- Children units or private-payment chain units that reference a parent by its `unit` hash (`parent_units`, or chained private-payment `unit` references) can be invalidated/orphaned if the malleated variant instead becomes part of the DAG, causing loss of access to funds the recipient believed were committed (fund freezing) for a private-payment counterparty.
- Any off-band commitment, notification, or nonce/idempotency logic keyed on `unit` hash (e.g., device-to-device confirmations referencing a specific `unit`) can be desynchronized between honest counterparties, since two functionally identical but hash-distinct units exist and only one may ultimately stabilize.
- This does not, by itself, defeat the double-spend/sequence conflict resolution for the *same* input (both malleated variants still compete as "same address double-spend" and only one can go `sequence='good'`), so it stops short of a stable-output double-spend by itself. This limits the severity relative to the classic Bitcoin malleability finding but the finding itself (missing scalar canonicalization in `signature.verify()`) is a concrete instance of the same "missing scalar checks → multiple valid witnesses for one message" bug class as the reported gnark advisory.

### Likelihood Explanation
Exploitation requires no special privilege beyond being the unit's own author, a paired device, or any entity that legitimately has access to a not-yet-stable signed unit (e.g. a private-payment recipient who is handed the raw joint before it propagates/stabilizes)—well within the "unprivileged unit poster / private-payment counterparty" reachability the analog rules require. Computing `n−S` and re-forming the base64 signature is trivial and does not require breaking the underlying cryptography.

### Recommendation
Enforce canonical low-S signatures in `signature.js`'s `verify()` (mirroring what is already done for the PEM secp256k1 path), e.g. reject or normalize any signature whose `S > n/2` before calling `ecdsa.ecdsaVerify()`, consistent with `ecdsa.signatureNormalize()` usage already present in `verifyMessageWithSecp256k1PemPubKey()`: [8](#0-7) . This closes the multiple-valid-witness gap for the same message/pubkey pair and removes signature-based unit-hash malleability.

### Proof of Concept
1. Sign a normal unit/authentifier using `ecdsaSig.sign()` [9](#0-8) , obtaining a compact 64-byte `(R,S)` signature.
2. Compute `S' = n - S` (mod the secp256k1 group order `n`), and rebuild a 64-byte `(R,S')` signature, base64-encoding it as the new authentifier value.
3. Both the original and the `S'`-modified unit pass `definition.js`'s `sig` evaluator via `ecdsaSig.verify()` [3](#0-2)  because libsecp256k1's verification is symmetric in `S ↔ n−S`.
4. Because `authentifiers` differ between the two units while all other content is identical, `object_hash.getUnitHash()` [6](#0-5)  yields two different `unit` hashes for what `object_hash.getUnitHashToSign()` treats as the same signed message [7](#0-6) , demonstrating the malleability.

```javascript
function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
```
