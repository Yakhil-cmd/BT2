### Title
Missing duplicate-attestation check in `gh release verify-asset` allows silent selection of the wrong attestation - (File: pkg/cmd/release/verify-asset/verify_asset.go)

### Summary
`gh release verify-asset` fetches all attestations for a release-tag digest, filters them by tag name and then by the asset's file digest, and finally verifies only `filteredAttestations[0]` — without ever checking that exactly one attestation survived filtering. The sibling command `gh release verify` performs the equivalent filtering but explicitly rejects the case where more than one attestation matches. `verify-asset` has no such guard, so when multiple attestations match the filters, the tool silently verifies an arbitrary one and reports success for the wrong subject/predicate. This mirrors the report's root cause: an aggregate "does a match exist" check (`len(filteredAttestations) == 0` → error) is used in place of a per-item uniqueness check, letting an unrelated/duplicated match stand in for the intended one.

### Finding Description
In `verifyAssetRun` [1](#0-0) , attestations for the release ref digest are fetched with `Limit: 100` (the code comment even notes "multiple attestations can exist for a single SHA"), then filtered:

1. `shared.FilterAttestationsByTag(attestations, tagName)` — keeps attestations whose predicate `tag` field equals the target tag.
2. `shared.FilterAttestationsByFileDigest(filteredAttestations, fileDigest.Digest())` — keeps attestations whose DSSE statement contains a subject digest matching the computed file digest.

After both filters, the code only checks `len(filteredAttestations) == 0` (returns "no attestations found") but never checks `len(filteredAttestations) > 1`. It then unconditionally verifies `filteredAttestations[0]`:
```
verified, err := config.AttVerifier.VerifyAttestation(releaseRefDigest, filteredAttestations[0])
```
`FilterAttestationsByFileDigest` also appends the same attestation once per matching subject in the loop (no `break`/dedup), which can multiply entries for a single attestation. In contrast, the near-identical `gh release verify` command explicitly guards this exact scenario:
```go
if len(filteredAttestations) > 1 {
    return fmt.Errorf("duplicate attestations found for release %s in %s", tagName, baseRepo.RepoName())
}
```
found in `verifyRun` [2](#0-1) . `verify-asset` lacks this check entirely, meaning ambiguity between multiple candidate attestations (e.g., a release with several assets sharing overlapping tag/predicate metadata, or a repo where more than one workflow run produced a "release" predicate for the same tag) is resolved by picking index `0` rather than failing safe.

This is the same bug class as the reported Infinity Exchange issue: a validation routine checks that "a match exists" (count ≥ 1) without checking "the match is unique/unambiguous," so the code proceeds to act on an item that may not correspond to what the caller actually intended, silently substituting one signed statement for another.

### Impact Explanation
If `verifyAssetRun` selects the wrong attestation among several matching candidates, the command can report `Verification succeeded!` for an asset while having actually validated a *different* attestation's cryptographic bundle than the one truly describing the presented file/tag combination. Since `gh release verify-asset` exists specifically to let users assert supply-chain trust in a downloaded asset before use, a false-positive "verified" result undermines the entire purpose of the command and could lead a user to trust/execute an asset that was not actually covered by the attestation they believe was checked.

### Likelihood Explanation
Exploitability depends on how attestations for a release/tag/digest are actually structured; multiple genuine attestations for the same tag are explicitly called out as a real possibility in the code's own comments ("multiple attestations can exist for a single SHA"). The bug requires no local/admin privileges and is reachable by any user running `gh release verify-asset` against a repository containing more than one attestation matching the tag+digest filters — a condition that can arise from normal repository activity (e.g., re-releases, multiple build/attestation workflows) rather than requiring a sophisticated attack, making it moderately likely to occur in practice even without malicious intent, and a genuine correctness/security-relevant bug regardless.

### Recommendation
Add the same guard used in `pkg/cmd/release/verify/verify.go` to `verifyAssetRun`: after filtering by tag and by file digest, if `len(filteredAttestations) > 1`, return an explicit "duplicate/ambiguous attestations found" error instead of silently using `filteredAttestations[0]`. Additionally, fix `FilterAttestationsByFileDigest` to append an attestation at most once (e.g., `break` after the first matching subject) so a single attestation is never counted multiple times toward the "how many matched" determination.

### Proof of Concept
Not independently reproducible from static analysis alone — reproducing this requires a live GitHub repository/release where two or more real attestations exist for the same tag and the asset's digest is present as a subject in more than one of them (or crafting a bundle with multiple subjects sharing the target digest), then running `gh release verify-asset <file> --repo <owner/repo> <tag>` and observing that verification is performed only against `filteredAttestations[0]` with no duplicate-count error, unlike `gh release verify` which fails with "duplicate attestations found" under the analogous condition.
