### Title
API scope bypass in CCMenu endpoint allows a stack-scoped ApiClient token to read any other stack's build/deploy status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The `Shipit::Api::CCMenuController` overrides the stack-resolution method inherited from `BaseController` in a way that drops the per-`ApiClient` stack scoping enforced everywhere else in the API, letting a token that was only authorized for one stack read CI/deploy status of any other stack in the installation.

### Finding Description
`ApiClient` records can be scoped to a single stack via the `stack_id` column (e.g. fixture `here_come_the_walrus` has `stack: shipit, permissions: [read:stack]` [1](#0-0)  ). Every other API controller resolves the target stack through `Shipit::Api::BaseController#stack`, which is deliberately restricted to the client's authorized stack set:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely and resolve directly from the global `Stack` model using the client-supplied `params[:stack_id]`:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [3](#0-2) 

The only permission check performed is `check_permissions!`, which is purely capability-based and stack-agnostic:

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
``` [4](#0-3) 

Because `CCMenuController#stack` never consults `current_api_client.stack_id`, any token that carries the `read:stack` permission string — including one whose `stack_id` column scopes it to exactly one stack — can be replayed against `GET /api/:stack_id/cc.xml` (or equivalent CCMenu route) with an arbitrary `stack_id` for a *different* stack and still succeed, since `require_permission :read, :stack` only checks the permission name, not the stack binding.

**Binding broken:** stack a token authorizes (`current_api_client.stack_id`) vs. stack it touches (`params[:stack_id]` resolved unscoped in `CCMenuController#stack`).

### Impact Explanation
An entity holding a legitimately-issued, narrowly-scoped `ApiClient` token (e.g., a CI dashboard integration granted `read:stack` for a single stack) can escalate that token to read the build/deploy status — name, lock status, `lastBuildStatus`, `lastBuildLabel` (deployed SHA), `lastBuildTime`, `webUrl` — of every other stack in the Shipit instance, including stacks belonging to other teams/projects the token holder was never authorized to see. This is an unauthorized cross-stack read of deploy state, matching the High-impact category of "escalation into authorization... unauthenticated read of stack state... deploy output."

### Likelihood Explanation
Likelihood is high in any deployment where per-stack scoped `ApiClient`s are issued to third parties (which the product explicitly supports via the `stack` column on `ApiClient` and the API client creation UI). No secret material beyond a token the attacker legitimately possesses is required, and the request is a single unauthenticated (session-free) GET with a different `stack_id` query/path parameter.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped `stacks` accessor from `BaseController` (i.e., remove the override, or replace `Stack.from_param!(params[:stack_id])` with `stacks.from_param!(params[:stack_id])`) so that stack-scoped `ApiClient`s cannot resolve stacks outside their authorized `stack_id`.

### Proof of Concept
1. Admin creates two stacks, `stack-a` and `stack-b`.
2. Admin issues an `ApiClient` scoped to `stack-a` only, with permission `read:stack` (as done via the `ApiClient` `stack` column, mirrored by fixture `here_come_the_walrus`) [1](#0-0) .
3. Using that client's `authentication_token`, request `GET /api/stack-b/cc.xml?token=<token>` (or via Basic auth), i.e. `stack_id` set to `stack-b` instead of `stack-a`.
4. `authenticate_api_client` in `CCMenuController` accepts the token [5](#0-4) ; `require_permission :read, :stack` passes because the token has `read:stack` [6](#0-5) ; `stack` resolves `stack-b` directly via `Stack.from_param!`, bypassing the `stacks` scoping filter [7](#0-6) .
5. Response returns `stack-b`'s CCMenu XML (deploy status/SHA/lock state), even though the token was only ever authorized for `stack-a`.
