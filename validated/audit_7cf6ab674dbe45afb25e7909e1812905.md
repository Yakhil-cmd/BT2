Confirmed: `has_many :review_stacks` is not scoped by `review_stacks_enabled` [1](#0-0) , so nothing at the association/scope level compensates for the `provision?` logic bug.

### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled=false`, auto-provisioning and executing an attacker-controlled fork branch's `shipit.yml` - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` is written so that `repository.review_stacks_enabled` only gates the `allow_all` clause; because Ruby's `&&` binds tighter than `||`, the `allow_with_label` and `prevent_with_label` clauses are evaluated independently of `review_stacks_enabled`. Consequently, a repository with review stacks explicitly turned off (`review_stacks_enabled=false`) but configured with `provisioning_behavior=:prevent_with_label` will still auto-create and auto-provision a review stack for any `opened` PR that omits the label, and that stack's task execution reads `shipit.yml`/steps from the attacker-controlled PR branch.

### Finding Description
The broken binding as an equality: the intended invariant is `provision? == (review_stacks_enabled && behavior_matches?)`; the actual code computes `provision? == (review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`, i.e. `review_stacks_enabled` is not distributed over the last two disjuncts: [2](#0-1) 

Trace:
- `respond_to_pull_request_opened?` gates only on `params.action == "opened" && provision?` [3](#0-2) .
- With `review_stacks_enabled=false`, `provisioning_behavior_prevent_with_label? = true`, and the PR omitting the `provisioning_label_name` label, the third clause `(prevent_with_label? && !has_label)` evaluates to `true` regardless of the first clause's `review_stacks_enabled` term, so `provision?` returns `true`.
- `process` then calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which calls `create!`, building `stack_attributes` with `branch: params.pull_request.head.ref` (the attacker's fork branch) [4](#0-3) .
- `create!` enqueues the stack via `ReviewStackProvisioningQueue.add(stack)` [5](#0-4) .
- Provisioning subsequently drives `TaskCommands#perform`, which builds `Command.new(command_line, ...)` for each step read from `@task.definition.steps`, sourced from `DeploySpec::FileSystem` checked out against the stack's `branch` (the fork ref) [6](#0-5) .
- `Repository#review_stacks` is a plain `has_many`, not filtered by `review_stacks_enabled` [7](#0-6) , so no downstream guard compensates for the precedence bug.

Existing guards do not catch this: `verify_signature`/webhook signature checks only authenticate that GitHub sent the payload, they don't validate `review_stacks_enabled` semantics; `ExplicitParameters` schema only validates payload shape, not business logic; there is no `User#authorized?`/`require_permission!` check in this handler chain since webhooks are unauthenticated by design and rely on signature verification, which is orthogonal to this bug. The test suite's `configure_provisioning_behavior` helper defaults `provisioning_enabled: true` in every `prevent_with_label`/`allow_with_label` test [8](#0-7) , so the combination `review_stacks_enabled=false` + `prevent_with_label` + no label is never exercised, leaving the regression undetected.

Note: the framing in the question that "the ref supplying `shipit.yml` is an unapproved fork ref, EXECUTION TRUST fails" describes the *intended* design of review stacks when `review_stacks_enabled=true`/`allow_all` — review stacks are documented to build and deploy the PR's own branch for preview purposes [9](#0-8) , so that part alone is not a bug. The demonstrable, reproducible bug is narrower: the `review_stacks_enabled` toggle is silently ignored for two of the three provisioning-behavior modes, letting attackers trigger provisioning (and thus fork-branch `shipit.yml` execution) on repositories where the maintainer explicitly disabled the feature.

### Impact Explanation
On any repository configured with `provisioning_behavior=:prevent_with_label` (or `:allow_with_label`) but `review_stacks_enabled=false`, an unprivileged PR author can force creation and provisioning of a `Shipit::ReviewStack` bound to their own fork branch, whose `shipit.yml`-defined steps are subsequently executed via `Command`/`PTY.spawn` on the deploy host with the environment merged in `TaskCommands#env` (including `GITHUB_TOKEN`-bearing credentials and other stack env) [10](#0-9) . This is repeatable against any repository misconfigured this way (or any repo where a maintainer believed disabling the toggle fully disabled auto-provisioning), matching the Critical RCE category for "a command running that should not."

### Likelihood Explanation
Requires the specific repository configuration `review_stacks_enabled=false` with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible, documented, non-default combination a maintainer might set while transitioning away from review stacks). Attacker cost is trivial: open a PR from a fork with (for `prevent_with_label`) no label, or with the label (for `allow_with_label`). No secrets or elevated privileges are needed.

### Recommendation
Fix operator precedence/logic in `provision?` so `review_stacks_enabled` gates every clause, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Add regression tests covering `review_stacks_enabled: false` combined with `allow_with_label` and `prevent_with_label` behaviors to prevent recurrence.

### Proof of Concept
minitest plan in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:

Assert both sides of the binding: before fix, `repository.review_stacks_enabled == false` yet `Shipit::Stack.count` still increments (bug present); after fix, `Shipit::Stack.count` stays unchanged, matching `review_stacks_enabled == false`.

**File:** docs/review_stacks.md (L17-21)
```markdown
shipit-engine support three distinct behaviors for determining which Pull Requests should be considered for Review Stack creation.

1. "Allow All" - shipit-engine will create a Review Stack for every new Pull Requests.
1. "Allow With Label" - when creating or updating a Pull Request, the user must add a label matching the `Shipit::Repository`'s "provisioning_label" attribute in order for shipit-engine to dynamically create/manage a Review Stack - an opt-in strategy.
1. "Prevent With Label" - when creating or updating a Pull Request, the user must add a label matching the `Shipit::Repository`'s "provisoining_label" attribute in order to **prevent** shipit-engine from dynamically creating/managing a Review Stack - an opt-out strategy.
```
