### Title
Double completion of the per-chain callback in `handleSavedPrivatePayments` due to a missing `return` after a hashing exception - ([File: network.js])

### Summary
`network.js`'s `handleSavedPrivatePayments()` re-processes private-payment chains that a peer or hub previously sent and that were queued in the `unhandled_private_payments` table by `handleOnlinePrivatePayment()`. For each queued chain it calls the inner `validateAndSave()` closure, which computes a hash of the head element's payload and then unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(...)`. If the hash computation throws, the `catch` block already finalizes the row (via `deleteHandledPrivateChain(..., cb)`, which itself invokes `cb`) but execution falls through to the code below the `try/catch` and invokes `validateAndSavePrivatePaymentChain` anyway, which asynchronously calls `cb` (or `deleteHandledPrivateChain(...,cb)`) a second time. [1](#0-0) 

### Finding Description
The relevant code path is: [2](#0-1) 

`validateAndSave()` wraps `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` in a `try/catch`. On exception it logs the error, optionally sends an error result to the peer, and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which deletes the DB row and then calls `cb()`, the completion callback handed to this iteration by `async.each`. Critically, there is **no `return`/`throw` after this call**, so control flow continues past the `catch` block into the line that builds `key` and then unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`. That call always resolves asynchronously via one of `ifOk`, `ifError`, or `ifWaitingForChain`, each of which itself calls `cb()` again (`ifOk`/`ifError` do so via a second `deleteHandledPrivateChain(...)` call, `ifWaitingForChain` calls `cb()` directly): [3](#0-2) 

This is the JS/async analogue of a double-free: the same completion handle (`cb`, the per-item finalizer of `async.each`) is "released" (invoked) twice for one logical resource (one queued private-payment chain row). `deleteHandledPrivateChain` (analogous to freeing a decoded attribute buffer) also fires twice: [4](#0-3) 

`objHeadPrivateElement.payload` is fully attacker-controlled: `handleOnlinePrivatePayment` only validates the outer `unit`, `message_index`, and `output_index` before persisting the raw JSON blob to `unhandled_private_payments` — it performs no structural validation of `payload` itself: [5](#0-4) 

so a private-payment counterparty (or hub-relayed private payment) can submit a payload whose shape causes `getBase64Hash`/`getJsonSourceString` to throw (e.g. unsupported value types, since `getSourceString`/`getJsonSourceString` in `string_utils.js` enforce strict type rules and throw on anything they don't recognize), triggering the double-free-like double completion once the wallet later replays it from `unhandled_private_payments` via `handleSavedPrivatePayments`.

### Impact Explanation
Calling `async.each`'s per-item `cb` twice corrupts the control-flow bookkeeping of the `async` library for that batch: it can cause the final callback (`unlock()`, i.e., releasing the `saved_private` mutex key) to fire prematurely or more than once, and/or throw internally. Because `handleSavedPrivatePayments` also emits `eventBus` events and issues a second DB `DELETE` for the same row, an attacker who repeatedly triggers this path can destabilize wallet-side processing of private/asset payments (mutex desynchronization, duplicate event emission, or an uncaught exception that crashes the process) — a denial-of-service against the wallet/light client that consumes private payments, matching the CVE's "double-free causing DoS" bug class.

### Likelihood Explanation
The trigger only requires sending a private-payment chain (over p2p or via a hub) whose head payload cannot be hashed by `getJsonSourceString`/`getSourceString` — no authentication or special privilege beyond being a private-payment counterparty is required, and the malformed payload passes all checks performed before being queued in `unhandled_private_payments`. The bug fires deterministically (missing `return` after `catch`), so the double-callback happens every time the hashing throws for a queued chain.

### Recommendation
Add a `return` (or restructure to an `if/else`) after the `deleteHandledPrivateChain(..., cb)` call inside the `catch` block in `validateAndSave()` in `network.js`, so that `privatePayment.validateAndSavePrivatePaymentChain` is never invoked once the row has already been finalized. Additionally, validate `payload` structurally (types compatible with `getSourceString`/`getJsonSourceString`) before persisting it to `unhandled_private_payments` in `handleOnlinePrivatePayment`, to fail fast instead of deferring the crash to replay time.

### Proof of Concept
1. As a paired device / private-payment counterparty, send (directly or via hub) a `private_payment_chain`/private-payment message whose head element's `payload` contains a value type that `getJsonSourceString`/`getSourceString` rejects (per `string_utils.js`, these functions throw on values outside their accepted type set), while still satisfying the loose checks in `handleOnlinePrivatePayment` (valid `unit`/`message_index`/`output_index`, non-empty objects/arrays).
2. The payment is queued into `unhandled_private_payments` unvalidated.
3. When the wallet later calls `handleSavedPrivatePayments()` (on startup, on new unit notification, or periodically) to process the queue, `validateAndSave()` throws inside the `try`, calls `deleteHandledPrivateChain(...,cb)` (1st `cb()`), then falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose `ifOk`/`ifError`/`ifWaitingForChain` handler invokes `cb()` a second time.
4. Observe the double invocation of `cb` inside `async.each`, the duplicate `DELETE FROM unhandled_private_payments` execution, and/or a mutex/eventBus state anomaly for the `saved_private` lock.

Note: I could not directly inspect `getSourceString`/`getJsonSourceString` in `string_utils.js` in this session (only a peripheral snippet was retrieved) to enumerate every exact input that throws; the exploitability hinges on confirming a concrete "throwing" payload shape reachable through the loose validation in `handleOnlinePrivatePayment`. This should be verified by reading `string_utils.js`'s `getSourceString`/`getJsonSourceString` in full before finalizing a fix or exploit payload.
