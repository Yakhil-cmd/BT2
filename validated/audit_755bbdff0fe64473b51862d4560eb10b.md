### Title
`TaskCommands#env` merges `@task.env` last, letting a whitelisted-by-name attacker variable override host-authoritative audit env keys - ([File: lib/shipit/task_commands.rb])

### Summary
`TaskCommands#env` builds the process environment by merging `@stack.env`, then host-set audit/identity keys (`TASK_ID`, `SHIPIT_LINK`, `SHIPIT_USER`, `GIT_COMMITTER_EMAIL`, etc.), then `deploy_spec.machine_env`, and finally `@task.env` last [1](#0-0) . Because the set of allowed keys in `@task.env` is derived from `variables:` names declared in the same repository's `shipit.yml` (via `TaskDefinition#filter_envs`), a review-stack attacker who controls that file can declare a variable literally named `TASK_ID` or `GIT_COMMITTER_EMAIL`, causing their value to win the final merge and overwrite the host-computed value.

### Finding Description
The broken binding: for any key `k` in the host-set hash at task_commands.rb:37-44 (e.g. `k = 'TASK_ID'`), the intended invariant is `TaskCommands#env['TASK_ID'] == @task.id.to_s` regardless of `@task.env`. This invariant is violated whenever `@task.env.key?('TASK_ID')`, because `.merge(@task.env)` is the last call in the chain and Ruby `Hash#merge` lets the right-hand operand's keys win [2](#0-1) .

`@task.env` is populated from `Stack#trigger_task`/`Stack#trigger_deploy`, which whitelist incoming `env` params strictly against `variables:`/`deploy_variables` declared in the repository's own `shipit.yml`: `definition.filter_envs(env)` calls `EnvironmentVariables.with(env).permit(variables)` where `variables` come from `TaskDefinition#initialize`, parsed directly from the repo's `config['variables']` [3](#0-2) [4](#0-3) . Since this whitelist is sourced from the untrusted branch's `shipit.yml` (for a review stack, attacker-controlled), the attacker can simply add a `variables:` entry named `TASK_ID` (or `SHIPIT_LINK`, `GIT_COMMITTER_EMAIL`) to make that name pass the permit-filter for their own task/deploy. Additionally, `Stack#trigger_task` auto-fills unset keys from the variable's declared `default:` (`env[variable.name] ||= variable.default`) [5](#0-4) , so the attacker does not even need control over request parameters — an attacker-declared `default:` value in `shipit.yml` is sufficient to poison `@task.env['TASK_ID']`.

The resulting `@task.env` value then flows unfiltered into `TaskCommands#env`'s final `.merge(@task.env)`, overriding the host-authoritative `TASK_ID`/`SHIPIT_LINK`/`GIT_COMMITTER_EMAIL` used for audit trail, permalinks and git commit metadata, and is exposed to subsequent step commands via `Command#interpolate_environment_variables`/`EnvironmentVariables#interpolate` for `$VAR`-style expansion in later hard-coded `shipit.yml` steps [6](#0-5) .

None of the existing guards prevent this: `filter_envs`/`EnvironmentVariables#permit` only restrict *which names* may be set by the caller — they do not exclude reserved/host-authoritative key names, and the variable name list itself is attacker-controlled through the same `shipit.yml` under review.

### Impact Explanation
An attacker who controls a review-stack branch's `shipit.yml` can forge audit-trail fields (`TASK_ID`, `SHIPIT_LINK`, `GIT_COMMITTER_NAME`/`EMAIL`, `SHIPIT_USER`) that are meant to be host-computed and trustworthy. Because these values are later interpolated with `$VAR` into subsequent steps' shell command lines via `EnvironmentVariables#interpolate`, an attacker-supplied value containing shell metacharacters can inject additional commands into a later step's shell invocation, running on the deploy host — a Critical-severity outcome. This affects only the attacker's own repository/stack (review stack scoped to their branch), so blast radius is confined to that tenant/stack, but is fully repeatable per PR.

### Likelihood Explanation
Requires: (1) a review stack (or any stack) configuration that runs task/deploy steps derived from an attacker-controlled `shipit.yml` (satisfied per the stated precondition that "review stack executes attacker steps"), and (2) the attacker naming a `variables:` entry identically to one of the host-injected keys and (optionally) supplying a malicious `default:`. This costs the attacker nothing beyond writing a `shipit.yml` in their own PR/branch — no secrets, sessions, or elevated permissions are needed for the `shipit.yml` authorship itself. The remaining question is whether the deploy/task trigger step (which is gated by `require_permission :deploy, :stack` in the controllers) is itself reachable without privilege in the review-stack flow; this is assumed true per the stated precondition (Q3) but was not independently re-verified in this pass.

### Recommendation
In `TaskCommands#env`, do not let `@task.env` override host-authoritative keys. Merge `@task.env` before the host-set block (or explicitly re-apply the host-set hash after merging `@task.env`), and/or reject `variables:` declarations in `shipit.yml`/`TaskDefinition` whose names collide with reserved keys (`TASK_ID`, `SHIPIT_LINK`, `SHIPIT_USER`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `EMAIL`, `BUNDLE_PATH`, `IGNORED_SAFETIES`).

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb
test "@task.env cannot override host-computed TASK_ID" do
  task = shipit_tasks(:restart)
  task.update!(env: { 'TASK_ID' => 'attacker-value; rm -rf /' })
  commands = TaskCommands.new(task)

  assert_equal task.id.to_s, commands.env['TASK_ID'],
    "attacker-controlled task.env['TASK_ID'] overrode the host-computed TASK_ID"
end
```
Before the fix: `commands.env['TASK_ID']` equals the attacker's string (last merge wins). After the fix: it must equal `task.id.to_s`.
