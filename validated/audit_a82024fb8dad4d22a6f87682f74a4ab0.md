## Analysis

The reported Code4rena finding is about a **binding break between an operator that authenticated an action and the on-chain effect it is allowed to trigger** (gas price at job selection vs. gas price at execution). The structurally analogous class explicitly permitted by the rules is: *"an organization that authenticated versus the repository that is written."* Shipit-engine's inbound webhook pipeline exhibits exactly this class of binding break.

`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository_owner`, which is read straight out of the **unauthenticated JSON body**: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The HMAC check itself only proves the raw body was signed with whichever organization's `webhook_secret` corresponds to `repository_owner`: [3](#0-2) 

However, once the signature is accepted, the actual event handlers (e.g. `PushHandler`) never re-check `repository_owner` — they independently resolve the target `Stack`/`Repository` from a **separate, unchecked field of the same body**: `repository.full_name`. [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because `verify_webhook_signature` is computed over `request.raw_post` (the entire attacker-supplied body, not a canonical/parsed subset), anyone who legitimately possesses the `webhook_secret` configured for **any one** organization tracked by this Shipit instance (multi-org config is a supported and documented setup: [5](#0-4) ) can freely construct the JSON body themselves. They set `repository.owner.login` to their own org (so `Shipit.github(organization: ...)` picks the secret they know) but set `repository.full_name` to point at a *different* organization/repository's stack. The signature will validate, yet the handler will act on the attacker-chosen `full_name`.

### Title
Webhook signature is verified against `repository.owner.login`, but handlers dispatch on the unrelated `repository.full_name` field, enabling cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate against using `repository.owner.login` from the untrusted JSON payload, then blindly trusts the same payload's `repository.full_name` for routing the event to a `Stack`/`Repository` in `Handler#stacks`. These two fields are never cross-validated.

### Finding Description
Any actor who is a legitimate GitHub App/webhook administrator for **one** organization configured in this Shipit instance's `github:` secrets (a normal, self-service, unprivileged action — configuring the "Authorization callback URL"/webhook secret for their own org's GitHub App per `docs/setup.md`) knows that organization's `webhook_secret`. Because `verify_signature` computes the HMAC over the full raw POST body supplied by the caller, and derives which secret to check against from a body field the caller also controls, this actor can:

1. Craft an arbitrary JSON payload with `repository.owner.login = "their-own-org"` (so `Shipit.github(organization: repository_owner)` resolves to the secret they know) — [6](#0-5) 
2. Set `repository.full_name = "victim-org/victim-repo"` — the field actually used to resolve the target stack — [7](#0-6) 
3. Sign the whole body with the known secret and POST it directly to the public `/webhooks` endpoint.

The equality that should hold — `organization that authenticated the request == organization owning the repository the handler mutates` — is broken; the code only verifies `organization that authenticated == organization named in an attacker-controlled field`, decoupled entirely from `repository.full_name`.

### Impact Explanation
A successful forgery lets the attacker inject fabricated `push` events for any repository/stack hosted on the same Shipit instance, regardless of organization. `PushHandler#process` calls `stack.sync_github(expected_head_sha:)` for matching branches: [8](#0-7) . If the targeted stack has `continuous_deployment` enabled, a forged/synced commit reaching a passing/pending status can trigger `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → `trigger_deploy`, i.e. an **unauthorized deploy** of a repository the attacker does not own: [9](#0-8) [10](#0-9) . Other webhook handlers (`status`, `pull_request` labeled/opened/reopened) similarly key off `repository.full_name` and can archive/unarchive review stacks or record forged commit statuses cross-tenant. This satisfies the "unauthorized deploy" / "cross-repository writes" High-impact bar.

### Likelihood Explanation
Requires only that the attacker legitimately administers the GitHub App/webhook configuration for at least one organization already onboarded to the shared Shipit instance — a normal, unprivileged setup action documented in `docs/setup.md`, not requiring any Shipit session, `ApiClient` token, or GitHub org membership on the victim side. This is realistic wherever a single Shipit deployment serves multiple organizations/tenants (as the multi-org config format explicitly supports).

### Recommendation
Bind signature verification to the same field used for routing: derive `repository_owner` for secret selection from `repository.full_name`'s owner segment (or vice versa), and reject the request if `repository.owner.login` does not match the owner segment of `repository.full_name`. Alternatively, verify against every configured organization's secret and only accept the match whose organization equals the owner parsed out of `full_name`.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` (webhook secret known to the attacker, who administers that org's App) and `victim-org` (contains a stack with `continuous_deployment: true`).
2. Attacker builds JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already present as a commit on victim stack, or benign>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully because the attacker knows that secret. [11](#0-10) 
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and dispatches `sync_github` against `victim-org`'s stack, potentially cascading into an unauthorized continuous-delivery deploy. [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
