### Title
`status` webhook events update commit CI state by SHA alone, with no binding to the repository that authenticated the webhook - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` GitHub webhook handler resolves target commits purely by matching `sha` across the *entire* `commits` table, without ever checking that the `sha` belongs to the `repository` covered by the verified webhook signature. This breaks the equality that should hold: `organization/repository that authenticated the webhook == repository whose commit-status (CI gate) is written`.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization strictly from the payload's `repository.owner.login` (or `organization.login`) and validates the HMAC signature using that organization's `webhook_secret` via `Shipit.github(organization: repository_owner)`, then dispatches the entire raw JSON payload to the registered handler for the event type. [1](#0-0) 

Every other handler in the engine scopes its database writes to the repository referenced in the payload via `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` before touching any records (e.g. `PushHandler#process`, `CheckSuiteHandler#process`). [2](#0-1) [3](#0-2) 

`StatusHandler`, however, does not use `stacks`/`repository_name` at all — it looks up commits globally by `sha`: [4](#0-3) 

Because a Git commit's SHA is a pure content hash (tree, parents, author/committer, timestamps, message) and not tied to which repository stores it, any two repositories — even ones belonging to different organizations/installations, as long as one of them has a webhook signing secret an attacker can produce a valid signature for (i.e., any repository whose org's GitHub App is configured in this Shipit instance and where the attacker can push commits, such as a repo they legitimately control within that org) — can contain an object with an identical SHA to a commit tracked by a completely unrelated Shipit stack. Sending (or naturally triggering, e.g. via a CI system configured on the attacker's own repo) a `status` event for that SHA, signed correctly with the attacker-controlled repository's/organization's webhook secret, will match `Commit.where(sha: params.sha)` against **any** stack in the Shipit instance whose tracked commit happens to share that SHA, and call `commit.create_status_from_github!(params)` on it — writing a fabricated CI status (e.g. `success`) onto a commit that belongs to a different, unrelated stack/repository. [5](#0-4) 

This is precisely the "organization that authenticated versus the repository that is written" binding break: `verify_signature` binds trust to `repository_owner` derived from the payload, but `StatusHandler#process` never re-checks that the commit being mutated belongs to the repository/stack implied by that same payload.

### Impact Explanation
`Commit#deployable?` and the CI/merge gating logic depend directly on `status`/`success?` derived from `Status::Group.compact(self, statuses_and_check_runs)`, which is populated by `create_status_from_github!`. [6](#0-5) [7](#0-6) 

A forged `success` status on a commit that never actually built/tested successfully allows that commit to become `deployable?`, satisfy `required_statuses`, and be picked up by continuous delivery (`schedule_continuous_delivery`) — resulting in an unauthorized deploy of a commit that bypassed CI. This matches the required "unauthorized deploy" impact class.

### Likelihood Explanation
Exploitation requires: (1) the attacker to have push/commit-creation access to some repository under an organization for which this Shipit instance has a configured GitHub App/webhook (not necessarily the target stack's own repository — any onboarded org/repo suffices, since signature verification is keyed on the sending organization only), and (2) the ability to engineer a commit object whose SHA matches a real commit SHA of the target stack (feasible because commit SHA generation is deterministic from tree+parents+author/committer identity+timestamps+message, all of which an attacker who can see the target's public commit metadata, e.g. via the target repo's public GitHub history, can reproduce byte-for-byte in a different repository they control). No Shipit session, API token, or webhook secret needs to be stolen — the attacker uses their own legitimately signed webhook traffic. This is a real, concrete boundary crossing (repository/organization isolation), not a theoretical one, though it does require the attacker to already be a trusted contributor of some onboarded GitHub org.

### Recommendation
In `StatusHandler#process` (and any other handler that resolves records purely by content-derived keys such as `sha`), scope the query to the repository/stack implied by the verified webhook payload, mirroring the pattern used by `Handler#stacks` (i.e., `stacks.commits.where(sha: params.sha)` instead of `Commit.where(sha: params.sha)`), so a commit status can only be written for a commit belonging to the same repository that authenticated the webhook.

### Proof of Concept
1. Shipit is configured with two onboarded GitHub organizations/apps, `org-trusted` (whose repo `org-trusted/app` is deployed by Shipit stack `S`) and `org-attacker` (any org the attacker can push to, configured with its own `webhook_secret`).
2. Attacker observes the tree, parent SHA, author/committer name+email+timestamp, and commit message of a real pending/failing commit `C` (sha `abc123`) in `org-trusted/app` (public commit metadata).
3. Attacker reproduces an identical commit object (same tree, parents, author/committer, timestamps, message) inside `org-attacker/scratch`, producing the exact same SHA `abc123` via `git commit-tree`/`git hash-object` replication.
4. Attacker's own CI (or a manually crafted webhook, signed with `org-attacker`'s legitimate `webhook_secret`) posts a GitHub `status` event: `{"sha": "abc123", "state": "success", "repository": {"owner": {"login": "org-attacker"}, "full_name": "org-attacker/scratch"}, ...}`.
5. `WebhooksController#verify_signature` validates the signature against `org-attacker`'s secret and passes it through.
6. `StatusHandler#process` executes `Commit.where(sha: 'abc123')`, matches commit `C` in stack `S` (belonging to `org-trusted`), and calls `commit.create_status_from_github!(params)`, marking `C` as `success` in Shipit even though `org-trusted`'s real CI never reported success — enabling `C` to become `deployable?` and be auto-deployed if `continuous_deployment` is enabled.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
