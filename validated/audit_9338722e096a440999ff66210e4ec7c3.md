## Analog Found: Asset attestor list can be changed by the definer at any time, retroactively freezing already-issued/held coins of a `spender_attested` asset

### Title
Unrestricted mid-lifecycle change of asset attestor list can freeze counterparties' already-issued/held coins - (File: validation.js)

### Summary
The reported bug class is "a privileged party changes global settings after a deal is already committed, breaking the payment process for the counterparty." The closest reachable analog in `ocore` is the `spender_attested` asset mechanism: the asset **definer** can post an `asset_attestors` message at any time to change the list of attestors, and this list is later re-evaluated against the *current* (latest, pre-last-ball) attestor list rather than the list that was in effect when a holder received/issued the asset.

### Finding Description
An asset with `spender_attested: true` restricts who may hold/spend the asset to addresses attested by one of the attestors in `attestors`. This list is not fixed at asset-creation time — the definer can update it later via the `asset_attestors` app, validated by `validateAttestorListUpdate`, which only checks that the sender is the definer and that the new list is well-formed: [1](#0-0) 

When any later payment involving this asset is validated, the current attestor list (the most recent one stable before `last_ball_mci`) is looked up fresh via `readAsset`/`readAssetInfo`, and spendability of the payment's output addresses is re-checked against that *latest* list: [2](#0-1) [3](#0-2) 

The payment validator enforces this at spend time: [4](#0-3) 
and again inside `validatePaymentInputsAndOutputs` for output addresses: [5](#0-4) 

Because the attestor list is a live, mutable global setting rather than something snapshotted at the time a specific deal/coin was created, the definer (the "market owner" analog) can change it — e.g. remove the attestor that certified a given holder — strictly after that holder has already received/is holding units of the asset. Any output the holder later tries to spend, or that is in flight, will then fail `spender_attested` validation ("some output addresses are not attested" / "none of the authors is attested"), even though the holder legitimately obtained the asset under the previously valid attestor list.

This exactly parallels the reported pattern: a privileged actor (asset definer / market owner) can unilaterally change a setting (`attestors` / `setPaymentDefaultDuration`) that governs an already-in-progress obligation (an asset transfer already issued to a counterparty), breaking the payment/spend process for a party who did nothing wrong.

### Impact Explanation
- Funds (units of the affected asset) held by a counterparty can become permanently unspendable ("frozen") the moment the definer updates the attestor list to exclude the attestor that vouched for that holder.
- A pending/in-flight payment from an already-attested holder can be invalidated retroactively by a definer action that lands before the payment's `last_ball_mci`, causing the payment to fail validation network-wide (nodes will reject it), even though it was valid when composed.
- This is a fund-freezing issue reachable by any asset definer against holders of their own `spender_attested` asset — no special network position needed, matching the Medium severity of the source report (settings change after commitment breaking payment processing).

### Likelihood Explanation
Any asset definer of a `spender_attested` asset can trigger this simply by posting a normal `asset_attestors` message at any time — this is a standard, unrestricted operation with no cooldown, no timelock, and no check for outstanding balances/holders under the old list. It requires no cooperation from anyone else and no unusual timing beyond ordinary unit composition/inclusion, making it straightforward to trigger, whether accidentally (definer rotates attestors for legitimate reasons) or maliciously.

### Recommendation
- Snapshot the attestor list (or its chash) that authorized a specific holder's acquisition of the asset, and allow spending as long as it satisfies the list valid at receipt time, not the very latest list.
- Alternatively, require a lock/grace period before an attestor-list change becomes effective for already-issued outputs, or explicitly document/restrict this as intended behavior with off-chain safeguards, and provide an on-chain path for a removed holder to migrate/redeem funds before the change takes effect.

### Proof of Concept
1. Definer `D` creates asset `A` with `spender_attested: true`, `attestors: [X]`.
2. `X` attests address `H` (holder). `D` sends units of `A` to `H`; validated fine because `H` is attested by `X`, current member of `attestors`.
3. Before `H` spends further, `D` posts an `asset_attestors` message removing `X` from the attestor list (validated only by `validateAttestorListUpdate`, no reference to outstanding holders): [1](#0-0) 
4. `H` now tries to send a payment of `A`. `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses` recomputes attestation against the *new* attestor list (no longer including `X`), and the payment fails validation: [6](#0-5) 
5. `H`'s previously legitimately-acquired coins are now stuck/frozen, purely due to a unilateral setting change by `D` after the transfer was already committed.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
