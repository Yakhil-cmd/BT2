### Title
Cross-organization webhook forgery via signature verification bound to `repository.owner.login` while handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook with based on `repository.owner.login` (a field inside the untrusted JSON body), but the event handlers that actually act on the payload key off `repository.full_name`, a *different* field in the same untrusted body. Because GitHub App webhook secrets are configured per-organization and are documented as *optional*, an attacker who knows (or has none configured for) any one organization's webhook secret can forge a signature that is accepted for that org, while setting `repository.full_name` to point at any other organization/repository tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` computes which app config to use for HMAC verification purely from an attacker-controlled field: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` and `verify_webhook_signature` then load that organization's own webhook secret and validate the HMAC over the raw body: [3](#0-2) [4](#0-3) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Note that if an organization has no `webhook_secret` configured (explicitly documented as optional in `docs/setup.md`), signature verification for a payload claiming that org's ownership succeeds unconditionally.

After this check, the controller re-parses the *same* raw body and dispatches to handlers, which resolve the repository/stack using a completely different field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because the entire request body is a single JSON blob fully controlled by the attacker prior to signing, nothing forces `repository.owner.login` (used to pick/verify the secret) to be consistent with `repository.full_name` (used to pick the stack that gets acted upon). This breaks the intended binding: *the organization whose secret authenticated the request* == *the repository the handlers actually write to*.

`StatusHandler` is a concrete example of impactful acted-upon logic: it creates a `Status` record for any commit matching an attacker-supplied `sha`, regardless of which organization the signature was checked against: [7](#0-6) 

A forged `success` status on a required CI check can make a commit `deployable?` and, combined with continuous deployment, trigger an unauthorized deploy: `Commit#deployable?` and the CD scheduling path react directly to newly created statuses: [8](#0-7) [9](#0-8) 

### Impact Explanation
This crosses a genuine authentication boundary: it lets a webhook signed for org A (whose secret is known/absent) forge events attributed to any repository/stack belonging to org B tracked by the same Shipit instance. Depending on the handler triggered, the impact ranges from spoofing CI status (`StatusHandler`) — which can make an otherwise non-deployable commit appear `deployable?` and enable an unauthorized continuous deployment — to triggering `GithubSyncJob` for arbitrary tracked stacks, or manipulating `membership`/`pull_request` handlers for repositories the attacker does not control. The most severe realistic outcome is an **unauthorized deploy** triggered via forged CI success statuses on a stack with continuous delivery enabled.

### Likelihood Explanation
This requires the deployment to be configured with multiple GitHub organizations (the multi-org `secrets.github` schema shown in `docs/setup.md` and `config/secrets.development.example.yml`), and at least one organization either having no `webhook_secret` configured (explicitly presented as "optional") or having a secret known to the attacker (e.g., the attacker's own org/repo where the GitHub App is also installed). Given webhook secrets are optional per the documented setup, and Shipit explicitly supports many orgs sharing one instance, this is a realistic configuration for organizations onboarding multiple teams/orgs onto a shared Shipit deployment.

### Recommendation
Bind webhook signature verification to the same repository identity the handlers act on. Concretely:
- Derive the organization used for secret selection consistently from `repository.full_name` (e.g., the owner segment of `full_name`) rather than from the independent `repository.owner.login`/`organization.login` fields, or
- After selecting the app/secret and verifying the signature, re-validate that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting mismatches.
- Consider requiring `webhook_secret` to be mandatory (not optional) for every configured organization to remove the unauthenticated bypass path entirely.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two organizations in `secrets.github`: `orgA` (no `webhook_secret` set) and `orgB` (has a stack tracked, e.g. `orgB/victim-repo`, with CI required for deploys).
2. Craft a JSON body for a `status` event:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "sha": "<sha of an undeployed commit on orgB/victim-repo>",
  "state": "success",
  "context": "required-ci-check"
}
```
3. POST this body to `/webhooks` with header `X-Github-Event: status` and any `X-Hub-Signature` value (or omit — `verify_webhook_signature` returns `true` unconditionally for `orgA` because it has no secret, per `lib/shipit/github_app.rb#L76-77`).
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'orgA')`, whose `verify_webhook_signature` short-circuits to `true`.
5. `StatusHandler#process` then matches the commit by `sha` regardless of organization and creates a `success` `Status` for it on `orgB/victim-repo`, potentially making the commit `deployable?` and triggering continuous deployment for a repository the attacker has no legitimate access to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
