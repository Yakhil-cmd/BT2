## Title
Shared-address device-controller spoofing bypasses cosigner authorization and leaks private-payment metadata - (File: wallet_defined_by_addresses.js)

### Summary
The `new_shared_address` device-message handler (`handleNewSharedAddress`) accepts a fully attacker-supplied `signers` map that binds arbitrary `device_address` values to member addresses of a shared address, and only "self-heals" the mapping for addresses that are the recipient's own plain (`my_addresses`) addresses. Addresses that correspond to an *existing shared address* the recipient already belongs to are never re-validated, so a paired-but-unauthorized correspondent can claim to be the controlling device for that nested shared address. This mirrors CVE-2021-35949's root cause: a permission check exists for one access class (plain "my" addresses) but is silently skipped for another class (nested shared addresses), letting an unauthorized party register itself as a legitimate recipient of share metadata.

### Finding Description
`handleNewSharedAddress` (`wallet_defined_by_addresses.js:378-415`) validates only structural consistency of the message (definition hash, signer/definition address matching), then calls `determineIfIncludesMeAndRewriteDeviceAddress`: [1](#0-0) 

This function looks up which member addresses belong to `my_addresses` (`type: 'my'`) vs `shared_addresses` (`type: 'shared'`), but the device-address rewrite loop only fixes up entries whose `address` is in `arrMyMemberAddresses` (plain addresses):

```
if (!bHasMyDeviceAddress){
    for (var signing_path in assocSignersByPath){
        var signerInfo = assocSignersByPath[signing_path];
        if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
            signerInfo.device_address = device.getMyDeviceAddress();
    }
}
```

If the attacker's crafted definition instead references an address the victim already recognizes as a *shared* address (`type === 'shared'`, e.g. an existing multisig wallet address the victim co-manages with real cosigners), the corresponding `signerInfo.device_address` is never rewritten — it remains whatever the attacker supplied. `addNewSharedAddress` then persists this unverified mapping directly into `shared_address_signing_paths`: [2](#0-1) 

This table is later trusted, without any additional authorization check, to decide who receives private-payment metadata. `readAllControlAddresses` recursively expands "control addresses/devices" of any address, including through nested shared addresses: [3](#0-2) 

and `forwardPrivateChainsToOtherMembersOfSharedAddresses` (wallet.js) uses that expansion to push full private-payment chains — addresses, amounts, blinding factors — to every resolved device that is already a correspondent: [4](#0-3) 

Because the attacker's poisoned `device_address` entry is folded into `arrControlDeviceAddresses` during this recursive resolution, the attacker's device (already a correspondent, hence able to send `new_shared_address` at all per the correspondent gate in `device.js:204-221`) ends up on the forwarding list for private payments sent to the newly crafted (attacker-defined) address — even though the attacker was never actually approved as a signer/cosigner of the victim's real shared address relationships. There is no confirmation step tying receipt of `new_shared_address` back to a prior `create_new_shared_address`/`approve_new_shared_address` handshake (`approvePendingSharedAddress`/`deletePendingSharedAddress` are marked "unused"), so this direct handler is the sole trust boundary and it is insufficient for the nested-shared-address case.

### Impact Explanation
An already-paired correspondent (not a legitimate cosigner of any of the victim's shared addresses) can inject a crafted shared-address definition that nests one of the victim's real existing shared addresses, causing the victim's wallet to silently register the attacker's device as a "control device" for that relationship. Subsequent private-asset payments routed through the crafted address are forwarded — with full metadata (address, amount, blinding) — to the attacker's device without the victim's consent. This is unauthorized disclosure of private payment/share metadata, analogous to the CVE's bypass of read-permission checks on "upload-only" shares.

### Likelihood Explanation
Requires the attacker to already be a correspondent (paired device) of the victim — a common state in ocore-based wallets (contacts, bots, exchanges). No cryptographic break is needed: the attacker only needs to craft a definition that legally references the victim's already-known shared address (public chash) and control the private payment routing to trigger forwarding, e.g., by paying privately into the newly crafted address themselves.

### Recommendation
In `determineIfIncludesMeAndRewriteDeviceAddress`, also validate/rewrite `signerInfo.device_address` for signing paths whose `address` matches an existing `shared_addresses` entry — the only devices that should be trusted to control such a path are those already recorded in `shared_address_signing_paths` for that address, not whatever the incoming message claims. Reject the whole `new_shared_address` message if a claimed device_address for a nested shared-address path doesn't match the locally-known cosigner records.

### Proof of Concept
1. Attacker `D_att` is already a correspondent of victim `D_vic`.
2. Attacker learns `SA_real`, an existing shared (multisig) address of the victim (public on-chain data).
3. Attacker builds `arrDefinition = ["or", [["address", SA_real], ["address", D_att_owned_address]]]`, computes `new_addr = chash160(arrDefinition)`.
4. Attacker sends device message `{subject: "new_shared_address", body: {address: new_addr, definition: arrDefinition, signers: {"r.0": {address: SA_real, device_address: D_att}, "r.1": {address: D_att_owned_address, device_address: D_att}}}}`.
5. Victim's `handleNewSharedAddress` accepts it: hash matches, `SA_real` is found as `type:'shared'` in `determineIfIncludesMeAndRewriteDeviceAddress`, but its `device_address` is **not** rewritten (only `my_addresses` entries are). `addNewSharedAddress` stores `shared_address_signing_paths(new_addr, SA_real, ..., D_att)`.
6. Attacker (or a colluding third party) sends a private-asset payment to `new_addr`.
7. Victim's node, while forwarding the private chain, resolves `readAllControlAddresses` for `new_addr`, which recurses into `SA_real`'s real cosigner devices, and also directly emits `D_att` as a control device for `new_addr` — sending the private payment payload (amount/address/blinding) to `D_att`.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function readAllControlAddresses(conn, arrAddresses, handleLists){
	conn = conn || db;
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, (correspondent_devices.device_address IS NOT NULL) AS have_correspondent \n\
		FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?)", 
		[arrAddresses], 
		function(rows){
			if (rows.length === 0)
				return handleLists([], []);
			var arrControlAddresses = rows.map(function(row){ return row.address; });
			var arrControlDeviceAddresses = rows.filter(function(row){ return row.have_correspondent; }).map(function(row){ return row.device_address; });
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
