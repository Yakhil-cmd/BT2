### Title
Single failed sync (e.g. from attacker-controlled remote content) permanently halts the entire sync engine instead of being isolated — analogous to Broker-wide disablement - (File: main.go)

### Summary
`git-sync`'s default failure policy treats *any* single sync error the same way, regardless of its cause or scope: it terminates the whole sync engine (`os.Exit(1)`) rather than isolating/skipping the offending update. This mirrors the referenced Reserve Protocol bug class, where a fault in one narrow subsystem (`GnosisTrade`) was allowed to disable the entire shared mechanism (`Broker`, covering both `GnosisTrade` and `DutchTrade`) instead of being scoped to the failing component, requiring external (governance) intervention to recover.

### Finding Description
The main sync loop increments a global `failCount` on every `SyncRepo` error and aborts the whole process once `failCount >= maxFails`, where `maxFails` defaults to `0` — i.e., "any sync failure will terminate git-sync": [1](#0-0) [2](#0-1) 

`SyncRepo` performs fetch, worktree creation, submodule update, and symlink publish as one atomic-looking sequence; any failure anywhere in that chain (fetch, `reset`, `createWorktree`, `configureWorktree` including submodule init, `publishSymlink`, or hook execution) is surfaced identically as a generic error to the outer loop: [3](#0-2) 

Because remote content (a new commit, tag, or submodule reference) is attacker-influenced whenever `git-sync` tracks a branch controlled by an untrusted contributor/CI pipeline, a single malformed or broken update — e.g., a commit adding a submodule pointing at an unreachable/invalid URL, an oversized object, or any condition that makes `configureWorktree`'s `submodule update --init` or `reset --hard` fail — causes `SyncRepo` to return an error on the very first attempt. With the default `--max-failures=0`, this single failure immediately exceeds the threshold and the whole process exits: [4](#0-3) 

Unlike a scoped failure (skip this ref, keep serving/retrying), the entire git-sync process — including future syncs of any future, unrelated commits — is torn down. On restart (whether via Kubernetes `restartPolicy` or manual operator action), `currentWorktree()`/`fetch` will still observe the same bad `remoteHash` (since the symlink/worktree was never advanced past the last good state, and the ref hasn't moved), so `configureWorktree` fails identically again, immediately exhausting `--init-max-failures` (which defaults to `--max-failures`, i.e., `0`) and exiting again — producing a persistent crash loop that never recovers without manual repo history editing or reconfiguration of the deployment (raising `--max-failures`, changing `--submodules`, etc.). This external, out-of-band remediation step is the functional analog of the "governance" resolution required in the Broker report.

### Impact Explanation
- **Persistent sync denial**: once the tracked ref advances to a commit that trips any transient/one-off failure in the sync pipeline, the entire git-sync sidecar can enter an unrecoverable crash loop, and no further updates (even unrelated, later-fixed commits accessible only after fetching past the bad one) are applied until an operator manually intervenes (e.g., editing the flag configuration or the upstream history).
- The currently published symlink target is not corrupted (last-known-good content remains served), so this is not data corruption, but it is a genuine, code-path-provable denial-of-sync condition triggerable purely by remote repository content that git-sync is designed to track, without any operator misconfiguration beyond using the documented defaults.

### Likelihood Explanation
This requires no special git-sync configuration beyond defaults (`--max-failures` unset ⇒ `0`), which the documentation itself states is the default behavior. Any environment where the synced ref/branch can receive contributions from a party who is not fully trusted (a common CI/CD or GitOps pattern that `git-sync` is built for) can trigger this via an innocuous mistake or a deliberately crafted commit (e.g. malformed `.gitmodules`, an inaccessible submodule URL, or any condition causing `git reset --hard`/`submodule update --init` to fail).

### Recommendation
- Do not treat every sync error identically; distinguish between transient/infrastructure errors (network, timeout) and errors traceable to the specific fetched ref/commit content (e.g., submodule resolution failures, checkout failures).
- For ref/content-specific failures, avoid permanently exiting the process; instead, keep serving the last good state, keep retrying at `--period`, and surface metrics/log alerts, without counting toward a global process-terminating failure budget that can be exhausted by a single occurrence.
- Consider changing the default so that a single, isolated content failure does not immediately terminate the whole daemon (e.g., only apply `--max-failures` semantics after distinguishing "poison-ref" failures from generic ones), aligning with the referenced report's guidance of scoping the failure response to the actually-affected component rather than the whole system.

### Proof of Concept
1. Deploy `git-sync` with defaults (`--max-failures` unset ⇒ `0`) tracking a branch that receives pushes from a less-trusted contributor:
   ```
   git-sync --repo=https://example.com/repo.git --ref=main --root=/tmp/root --link=current
   ```
2. Attacker pushes a commit to `main` that adds a submodule with an unreachable/invalid URL (or any change that causes `configureWorktree`'s `submodule update --init` step to fail), e.g.:
   ```
   git submodule add https://invalid.invalid/nonexistent.git broken-sub
   git commit -am "poison commit"
   git push origin main
   ```
3. On the next sync attempt, `SyncRepo` fetches the new commit, then fails inside `configureWorktree` (submodule update failure) — see [5](#0-4) .
4. The outer loop increments `failCount` to `1`, which already meets/exceeds the default `maxFails=0`, and the process calls `os.Exit(1)` — see [4](#0-3) .
5. Because the ref still points at the poisoned commit, any restart of the process (by Kubernetes or an operator) repeats steps 3–4 indefinitely, producing a permanent sync-denial crash loop until the offending commit/config is fixed or `--max-failures`/`--submodules` flags are changed out-of-band.
