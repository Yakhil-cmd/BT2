### Title
Front-running of permissionless `initialize` permanently blocks the deterministic canonical pool PDA for a token pair - ([File: programs/cp-swap/src/instructions/initialize.rs])

### Summary
`initialize` (and its sibling `initialize_with_permission`) is callable by anyone and creates the pool's `PoolState` account at a deterministic PDA derived only from `amm_config`, `token_0_mint`, and `token_1_mint` <cite repo="hirayap/raydium-cp-swap--018" path="programs/cp-swap/src/instructions/initialize.rs" start="376="384" /> [1](#0-0) . Because the caller fully controls `init_amount_0`, `init_amount_1`, `open_time`, and the depositing token accounts, an attacker can observe a legitimate creator's pending `initialize` transaction (same token pair / config) and land their own transaction first, permanently occupying the canonical PDA with attacker-chosen pricing/parameters before the legitimate transaction executes — analogous to the front-running DDOS described in the referenced report where a deterministic `bountyIdToAddress[_bountyId]` key let an attacker preempt a legitimate creation with different init parameters.

### Finding Description
`create_pool` computes `expect_pda_address` solely from `(amm_config, token_0_mint, token_1_mint)` and only requires the caller to be a signer when passing a *different* ("random") pool account; for the canonical PDA path no signature or authorization is required beyond the deterministic seeds [2](#0-1) . The very first check is `if pool_account_info.owner != &system_program::ID { return err!(ErrorCode::NotApproved); }` [3](#0-2) , meaning once any transaction succeeds in creating (allocating+assigning) the PDA to the program, all subsequent `initialize` calls for that exact `(amm_config, token_0_mint, token_1_mint)` triple permanently fail with `NotApproved`. There is no per-creator scoping or nonce in the seed — the identity of the pool is exactly the token-pair/config tuple, just like the vulnerable `bountyIdToAddress[_bountyId]` mapping in the referenced report keyed only by `_bountyId`.

Since `initialize` is `nonReentrant`-equivalent but fully permissionless (`creator: Signer<'info>` can be any wallet) [4](#0-3) , and the only economic cost to the attacker is supplying enough liquidity so that `liquidity > lock_lp_amount (100)` [5](#0-4) , an attacker can cheaply front-run the intended pool creator's transaction with minimal token amounts and/or a manipulated `open_time`, claiming the canonical PDA before the legitimate transaction lands.

### Impact Explanation
Once the attacker's `initialize` transaction succeeds, `pool_account_info.owner` is no longer `system_program::ID`, so the legitimate project's intended `initialize` transaction for that exact token pair + `amm_config` permanently reverts with `ErrorCode::NotApproved` [3](#0-2) . This is a permanent denial-of-service on the canonical pool address for that token pair/config combination: the legitimate deployer can never recreate the pool at the expected deterministic address with their intended initial price/liquidity. In addition, unsuspecting users or integrators who look up the pool via the deterministic PDA (as the client SDK does via `Pubkey::find_program_address` with the same seeds [6](#0-5) ) could be routed to the attacker-seeded pool with a skewed initial price, leading to economic loss when depositing or swapping against it.

### Likelihood Explanation
The attack requires only observing an upcoming `initialize` call for a token pair of interest (e.g., a new/anticipated token launch) and submitting a competing transaction with higher priority fee before it lands — a standard and cheap front-running technique on Solana, requiring no special privileges, and costing the attacker only a small amount of both tokens (enough to clear the `lock_lp_amount` threshold of 100).

### Recommendation
Do not rely purely on `(amm_config, token_0_mint, token_1_mint)` as the sole identity/authorization for canonical pool creation. Options include: requiring the intended creator to pre-register or reserve the pool (e.g., via a signed/whitelisted `initialize_with_permission`-style flow for canonical pools), incorporating a creator-controlled component into the PDA seeds so squatting a pair does not block the intended party, or adding a config-level allowlist/creator check so `create_pool` rejects unauthorized first-callers for permissioned token pairs, mirroring the recommendation to avoid using a purely user-guessable/collision-prone identifier as the sole existence check.

### Proof of Concept
1. Attacker monitors for a forthcoming `initialize` transaction for `token_0_mint`/`token_1_mint` under `amm_config` index 0 (addresses are fully derivable off-chain via the same seeds used in `initialize_pool_instr` [6](#0-5) ).
2. Attacker submits their own `initialize` transaction for the identical `(amm_config, token_0_mint, token_1_mint)` with a trivial `init_amount_0`/`init_amount_1` (just above the `lock_lp_amount` threshold) and a favorable/malicious `open_time`, with a higher priority fee so it lands first.
3. `create_pool` succeeds for the attacker: `pool_account_info.owner` becomes the program ID after `create_or_allocate_account` [7](#0-6) , and `pool_state.initialize(...)` finalizes it with attacker-controlled reserves/price [8](#0-7) .
4. The legitimate creator's `initialize` transaction for the same pair now fails at the very first check in `create_pool` (`pool_account_info.owner != &system_program::ID`) with `ErrorCode::NotApproved`, permanently unable to create the intended canonical pool [3](#0-2) .

pub fn create_pool<'info>(
    payer: &AccountInfo<'info>,
    pool_account_info: &AccountInfo<'info>,
    amm_config: &AccountInfo<'info>,
    token_0_mint: &AccountInfo<'info>,
    token_1_mint: &AccountInfo<'info>,
    system_program: &AccountInfo<'info>,
) -> Result<AccountLoad<'info, PoolState>> {
    if pool_account_info.owner != &system_program::ID {
        return err!(ErrorCode::NotApproved);
    }

    let (expect_pda_address, bump) = Pubkey::find_program_address(
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
        ],
        &crate::id(),
    );

    if pool_account_info.key() != expect_pda_address {
        require_eq!(pool_account_info.is_signer, true);
    }

pub fn create_or_allocate_account<'a>(
    program_id: &Pubkey,
    payer: AccountInfo<'a>,
    system_program: AccountInfo<'a>,
    target_account: AccountInfo<'a>,
    siger_seed: &[&[u8]],
    space: usize,
) -> Result<()> {
    let rent = Rent::get()?;
    let current_lamports = target_account.lamports();

    if current_lamports == 0 {
        let lamports = rent.minimum_balance(space);
        let cpi_accounts = system_program::CreateAccount {
            from: payer,
            to: target_account.clone(),
        };
        let cpi_context = CpiContext::new(*system_program.key, cpi_accounts);
        system_program::create_account(
            cpi_context.with_signer(&[siger_seed]),
            lamports,
            u64::try_from(space).unwrap(),
            program_id,
        )?;
    } else {
        let required_lamports = rent
            .minimum_balance(space)
            .max(1)
            .saturating_sub(current_lamports);
        if required_lamports > 0 {
            let cpi_accounts = system_program::Transfer {
                from: payer.to_account_info(),
                to: target_account.clone(),
            };
            let cpi_context = CpiContext::new(*system_program.key, cpi_accounts);
            system_program::transfer(cpi_context, required_lamports)?;
        }
        let cpi_accounts = system_program::Allocate {
            account_to_allocate: target_account.clone(),
        };
        let cpi_context = CpiContext::new(*system_program.key, cpi_accounts);
        system_program::allocate(
            cpi_context.with_signer(&[siger_seed]),
            u64::try_from(space).unwrap(),
        )?;

        let cpi_accounts = system_program::Assign {
            account_to_assign: target_account.clone(),
        };
        let cpi_context = CpiContext::new(*system_program.key, cpi_accounts);
        system_program::assign(cpi_context.with_signer(&[siger_seed]), program_id)?;
    }
