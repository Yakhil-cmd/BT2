### Title
AA "air" (dry-run) unit sending path (`sendDummyUnit`) skips transfer_condition/issue_condition, is_transferrable, spender_attested, and cosigned_by_definer checks that the real unit path enforces - ([File: aa_composer.js])

### Summary
When an autonomous agent sends outgoing asset payments, the normal path builds a real unit via `sendUnit()` and passes it through `validateAndSaveUnit`, which triggers the full `validatePaymentInputsAndOutputs` checks in `validation.js` (transfer/issue conditions, `is_transferrable`, `spender_attested`, `cosigned_by_definer`, `auto_destroy`). However, when `trigger_opts.bAir` is set, the AA engine instead calls `sendDummyUnit()`, which updates the AA's internal asset balances directly and only checks `issued_by_definer_only` before allowing a negative balance (i.e., issuing new units of an asset) — it never re-checks `is_transferrable`, `spender_attested`, `cosigned_by_definer`, or the asset's `transfer_condition`/`issue_condition`.

### Finding Description
`sendUnit()` in `aa_composer.js` builds a real payment unit and calls `validateAndSaveUnit`, which funnels into `validation.js`'s `validatePaymentInputsAndOutputs` (validation.js:2606-2659). That function enforces, for every asset payment:
- `is_transferrable` [1](#0-0) 
- `spender_attested` on output addresses [2](#0-1) 
- `issue_condition` / `transfer_condition` evaluation [3](#0-2) 
- `cosigned_by_definer` and `issued_by_definer_only` in `validatePayment` [4](#0-3) 

In contrast, `sendDummyUnit()` — used when `trigger_opts.bAir` is set (an "air"/dry-run execution mode for AA triggers that doesn't create or persist a real unit) — updates `trigger_opts.assocBalances` directly from the messages, and for assets whose resulting balance goes negative (i.e., the AA is effectively issuing/spending beyond what it holds) it performs only one check: whether `objAsset.issued_by_definer_only` is true and the AA is not the definer. [5](#0-4) 

None of the other asset-level restrictions enforced on the real-unit path — `is_transferrable`, `spender_attested`, `cosigned_by_definer`, or `issue_condition`/`transfer_condition` — are re-checked in this "air" balance-update path. This mirrors the JOJO bug pattern exactly: one code path (external/primary "deposit"-equivalent, here the real on-chain payment path) enforces the permission flags, while an alternate internal path that achieves the equivalent economic effect (crediting/debiting an AA's asset balance) bypasses those same flags.

### Impact Explanation
If an attacker can arrange for an "air"/dry-run AA trigger chain to move a restricted asset (e.g., an asset marked `is_transferrable: false`, `spender_attested: true`, `cosigned_by_definer: true`, or with a `transfer_condition`/`issue_condition` that should reject the transfer) through `sendDummyUnit`, the transfer would be accepted and the AA balance would be updated as if the conditions were satisfied, even though they were not. This could allow unauthorized asset transfers, bypass of attestation requirements, or effectively "printing" balance for a capped/definer-restricted asset within the AA's internal balance bookkeeping (`trigger_opts.assocBalances`), leading to AA fund loss/inflation of tracked balances that later get paid out through subsequent, legitimately-validated units.

### Likelihood Explanation
This requires the `bAir` code path to be reachable with attacker-influenced trigger data that produces a payment message referencing a restricted asset. The `bAir`/dry-run mechanism exists specifically for evaluating AA logic without creating real units (as seen from the mirrored logic in `sendUnit`/`sendDummyUnit` and the restore-on-bounce logic keyed on `trigger_opts.bAir`), so any legitimate invocation of that mode (e.g., chained/simulated secondary triggers or getters) could hit this gap. I could not fully trace every caller of `handleTrigger` with `bAir: true` within the available indexed context to confirm end-to-end attacker reachability and whether the resulting balance divergence can ever be exfiltrated into a real, validated unit — this remains unverified due to index/context limits.

### Recommendation
In `sendDummyUnit()` (aa_composer.js), before applying negative-balance deltas for an asset, replicate the same checks performed in `validatePaymentInputsAndOutputs`/`validatePayment`: verify `is_transferrable`, `spender_attested` (attested output addresses), `cosigned_by_definer`, and evaluate the asset's `issue_condition`/`transfer_condition` via `Definition.evaluateAssetCondition`, bouncing the trigger if any check fails, exactly as the real-unit path does.

### Proof of Concept
1. Define an asset with `is_transferrable: false` (or `spender_attested: true` with a restrictive attestor list, or a `transfer_condition` that always evaluates false).
2. Craft an AA (or a chain of AA triggers) that is invoked in "air"/dry-run mode (`trigger_opts.bAir = true`) and sends a payment message transferring that asset to an address that does not satisfy the restriction.
3. Because `sendDummyUnit()` only checks `issued_by_definer_only` (aa_composer.js:989-990) before allowing the balance-affecting transfer, the transfer is accepted and `trigger_opts.assocBalances` is updated as if it were valid, whereas the same transfer attempted via a real unit (`sendUnit` → `validateAndSaveUnit` → `validatePaymentInputsAndOutputs`) would be rejected with "the asset is not transferrable" / "some output addresses are not attested" / "transfer or issue condition not satisfied".

	// with bAir option, we don't send or save a real unit
	function sendDummyUnit(messages) {
		console.log('AA ' + address + ': send dummy unit with messages', util.inspect(messages, { depth: 6 }));
		var objUnit = messages.length ? {
			unit: 'dummy' + Date.now(),
			authors: [{ address: address }],
			messages: messages,
		} : null;
		executeStateUpdateFormula(objUnit, function (err) {
			if (err)
				return bounce(err);
			// update balances
			var arrOutputAddresses = [];
			messages.forEach(message => {
				if (message.app !== 'payment')
					return;
				var asset = message.payload.asset || 'base';
				message.payload.outputs.forEach(output => {
					if (output.amount !== 0 && arrOutputAddresses.indexOf(output.address) === -1)
						arrOutputAddresses.push(output.address);
					if (!trigger_opts.assocBalances[address][asset])
						trigger_opts.assocBalances[address][asset] = 0;
					if (output.amount === undefined) // send all
						output.amount = trigger_opts.assocBalances[address][asset];
					// deduct from this AA's balance. It can get negative if we are issuing coins but in this case balance[] is probably meaningless
					trigger_opts.assocBalances[address][asset] -= output.amount;
				});
			});
			if (arrOutputAddresses.length === 0)
				return finish(objUnit);
			if (trigger_opts.assocBalances[address].base < 0)
				return bounce("not enough balance in base");
			let arrAssetsWithNegativeBalances = [];
			for (let asset in trigger_opts.assocBalances[address])
				if (asset !== 'base' && trigger_opts.assocBalances[address][asset] < 0)
					arrAssetsWithNegativeBalances.push(asset);
			async.eachSeries(
				arrAssetsWithNegativeBalances,
				function (asset, cb) {
					storage.loadAssetWithListOfAttestedAuthors(conn, asset, mci, [address], true, function (err, objAsset) {
						if (err)
							return cb(err);
						if (objAsset.issued_by_definer_only && address !== objAsset.definer_address)
							return cb("not enough balance in " + asset); // and we are not the issuer
						cb();
					});
				},
				function (err) {
					if (err)
						return bounce(err);
					fixStateVars();
					addResponse(objUnit, function () {
						handleSecondaryTriggers(objUnit, arrOutputAddresses);
					});
				}
			);
		});
	}
