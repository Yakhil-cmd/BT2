### Title
AA payments to `spender_attested` assets can be silently dropped/DoSed, letting stale (de-attested) recipients keep funds meant to be refunded/paid — analogous to blacklist/ERC777-recipient auction lock in the report ([File: aa_composer.js])

### Summary
The Venus report describes a "push" refund pattern that can be permanently blocked when the refund recipient becomes un-receivable (blacklisted address / reverting ERC777 hook), letting a stale participant keep funds/priority forever. Ocore's Autonomous Agents (AAs) have a structurally identical push-payment pattern: an AA response unit contains `payment` messages with `outputs` addressed to state-tracked participants (e.g., "current highest bidder", "previous depositor", "counter-party to refund"). For assets defined with `spender_attested: true`, whether an output address can legally receive funds depends on a **mutable, off-chain-controlled condition** — the current attestor-issued attestation status of that address — exactly like a blacklist flag can be toggled by a third party after the fact.

### Finding Description
When validating a payment of a `spender_attested` asset, `validatePaymentInputsAndOutputs` requires that **all** output addresses currently be attested: [1](#0-0) 

Attestation status is not fixed at the time funds were deposited; it is re-evaluated at validation time based on the current DAG state (`filterAttestedAddresses` queries `attestations` as of `last_ball_mci`): [2](#0-1) 

The AA composer (`aa_composer.js`), which builds AA response units carrying refund/payout `payment` messages to addresses recorded in AA state (`trigger.address`, or an address saved in `var[...]` from an earlier trigger, e.g. as in `fundraising_proxy.oscript`'s refund case), does **not** pre-check `spender_attested`/attestation status of output addresses before composing and broadcasting the response unit — no reference to `spender_attested` or `arrAttestedAddresses` exists anywhere in `aa_composer.js`. It only pre-checks other asset restrictions such as `issued_by_definer_only` for negative balances: [3](#0-2) 

This mirrors the Shortfall.sol pattern: a "push" transfer to a previously-recorded recipient (`trigger.address` / saved bidder/participant address) is attempted without verifying, at composition time, that the transfer will actually be accepted by the receiving-side rule engine (attestation requirement / blacklist). If the attestor de-attests the address (analogous to being blacklisted) after the AA recorded it as the rightful recipient, the resulting response unit's `payment` message will fail the network-wide validation check "some output addresses are not attested" once the address's attestation is later revoked or was revoked between deposit and payout.

Concretely, using an auction/refund-style AA (structurally like `fundraising_proxy.oscript`'s "refund" case) built on a `spender_attested` asset: [4](#0-3) 

1. Participant A deposits/bids while attested, and the AA records A's address as the current "winner"/entitled recipient in a state var.
2. A's attestor revokes A's attestation (equivalent to being "blacklisted") — a normal, permitted, externally-triggered action outside the AA's control.
3. Participant B posts a higher/valid trigger that should cause the AA to refund/replace A by sending A the asset back.
4. The AA composes a response unit whose `payment` output goes to A. Because A is no longer attested, this payment message fails `validatePaymentInputsAndOutputs`'s attestation check for **all** nodes (this is a protocol-level, node-agreement rule, not merely A's own wallet rejecting it).
5. Depending on how deep in the AA logic the payment sits relative to state updates, this can either (a) cause the whole trigger response to be rejected as invalid at the network level (the unit can never be validly composed/broadcast — DoS of the auction/settlement step for the AA), or (b) if the AA doesn't detect the failure ahead of time and there is no fallback, funds directed at A become permanently unpayable through the intended code path, and A retains whatever privileged state (e.g., "current winner") the AA had already granted it, while other participants can never dislodge A because the required refund/settlement payment can never validate.

### Impact Explanation
This breaks the same invariant flagged in the Venus finding: a state-machine that grants a privileged position (highest bidder/holder of funds) based on a "we will pay them back later" promise can be permanently deadlocked, and the "malicious"/uncooperative party can retain funds or a privileged role indefinitely because the protocol-level refund transaction can never be validly constructed for their (now unattested) address. In Obyte terms this is worse than Solidity's local revert: attestation is a network-consensus-checked condition (`validatePaymentInputsAndOutputs`), so it isn't just "recipient rejects transfer" — the payment is objectively unfundable while the condition persists, for any node, forever. This can result in AA fund lock/freezing and node disagreement between users expecting the AA to progress (settle) and the actual state where it cannot, matching the required "AA fund loss or freezing" / "network unable to confirm new units" impact classes.

### Likelihood Explanation
Requires the AA author to build a payout/refund pattern on a `spender_attested` asset and for one of the tracked recipients to lose attestation between being recorded and being paid — a scenario entirely plausible for AAs that integrate with real-world identity/KYC-gated assets (the whole purpose of `spender_attested`), and the attestor (a legitimate, expected actor, not an attacker) can trigger this simply by updating attestation state, which is a normal, permitted, unprivileged-observable action for third parties in the ocore protocol.

### Recommendation
- In `aa_composer.js`, before finalizing an AA response unit's `payment` messages for `spender_attested` assets, pre-check (similar to the existing `issued_by_definer_only` check at `aa_composer.js:986-991`) that every output address is currently attested, and `bounce()` gracefully (with a clear error and full state/balance rollback) instead of allowing an unvalidatable unit to be attempted.
- AA authors using `spender_attested` assets in "record recipient now, pay later" patterns (auctions, refund queues, etc.) should implement a pull-based claim mechanism instead of push payments to a previously-stored address, so that a temporarily-unattested recipient cannot block state progression for other participants — mirroring the report's "pull over push" recommendation.
- Document this hazard prominently for AA developers, since the `spender_attested` restriction is otherwise easy to treat as a simple output filter rather than a dynamic condition that can revoke previously-valid recipients.

### Proof of Concept
Conceptual (network-validation) PoC, based on existing AA/validation code paths:
1. Define asset `X` with `spender_attested: true` and attestor `Z` (per `validateAssetDefinition`, `validation.js:2725-2755`).
2. Deploy an auction/refund AA analogous to `fundraising_proxy.oscript`'s "refund" branch, which on a later trigger sends `X` (or the asset it tracks) back to the address stored from an earlier trigger (`trigger.address` recorded via `var[...]`).
3. Address `A` (attested by `Z`) triggers the AA, gets recorded as current entitled recipient.
4. `Z` posts an `asset_attestors`/de-attestation update revoking `A`'s attestation (`storage.filterAttestedAddresses`, `storage.js:1959-1974`, reflects this at the next `last_ball_mci`).
5. Address `B` triggers the AA to supersede `A`, causing the AA to compose a `payment` message with output to `A`.
6. Because `aa_composer.js` performs no attestation pre-check (confirmed absent by search of `spender_attested`/`arrAttestedAddresses` in that file), the response unit is composed and broadcast with an output to now-unattested `A`.
7. Any node validating the response unit hits `validatePaymentInputsAndOutputs`'s check at `validation.js:2630-2642` ("some output addresses are not attested") and rejects it — the intended settlement/refund can never be validly completed while `A` remains unattested, freezing the AA's progression for this and dependent triggers.

		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\

			0)",
