## Title
Unvalidated field access in `handleOnlinePrivatePayment` crashes the node on malformed private-payment chain - (File: network.js)

### Summary
`network.js`'s `handleOnlinePrivatePayment` dereferences `arrPrivateElements[0].payload.denomination` before validating that `.payload` exists, meaning a private-payment counterparty (or a paired device/hub relay) can send a head element with a missing/malformed `payload` and trigger an unhandled `TypeError`. Because this codebase re-throws inside `process.on('uncaughtException')` to intentionally crash the process, this reachable, attacker-controlled exception is a concrete denial-of-service, structurally analogous to the qtdemux OOB-read DoS in ALPINE-CVE-2017-5840 (an unvalidated index/field is dereferenced before the bounds/structure check that comes later in the same function).

### Finding Description
`handleOnlinePrivatePayment` is the entry point for processing an incoming private-payment chain (`arrPrivateElements`), reachable from a private-payment counterparty sending a `private_payment` justsaying message, or via a paired device forwarding through a hub (see `sendPrivatePaymentToWs`/`sendJustsaying(ws, 'private_payment', ...)` and `wallet.js` callers of `handleOnlinePrivatePayment`).

The function performs only one shallow check before doing unchecked property access: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");

	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	if (!ValidationUtils.isValidBase64(unit, constants.HASH_LENGTH))
		return callbacks.ifError("invalid unit");
	...
```

`arrPrivateElements[0]` is only checked to exist as a non-empty array element (`isNonemptyArray` only guarantees the array is non-empty, not that its elements are well-formed objects). The `.payload` field of that first element is never checked before `.denomination` is read from it. If the sender omits `payload` entirely (or sends `payload: null`), `arrPrivateElements[0].payload.denomination` throws `TypeError: Cannot read properties of undefined (reading 'denomination')`.

This mirrors the CVE's root cause: an index/field taken from attacker-supplied data structure is dereferenced without validating the structure is well formed first, causing an out-of-bounds/invalid-memory-shaped access (here, a property access on `undefined`) that the code's own later checks (`isValidBase64`, `isNonnegativeInteger`, etc.) would have caught had they run first.

Unlike normal validation errors in this codebase (which are wrapped in callbacks and reported gracefully), an unhandled `TypeError` thrown synchronously inside a network message handler is not caught anywhere in the call chain up to `onWebsocketMessage`. It propagates to Node's `uncaughtException` handler, which this codebase deliberately re-throws to crash the process: [2](#0-1) 

```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	console.error('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

### Impact Explanation
A single malformed private-payment message from any private-payment counterparty (or a compromised/misbehaving paired device relayed through a hub) can crash the receiving full node or hub process. This is a network-reachable, unauthenticated (relative to the victim) denial-of-service that can be repeated at will, matching the "network unable to confirm new units" / DoS class explicitly in scope, since a crashed node stops processing/relaying units until restarted. Multiple peers exploiting this simultaneously against hub or witness nodes would degrade network availability.

### Likelihood Explanation
High likelihood: the trigger requires only sending a `private_payment` message (or forwarding one as a paired device) with `arrPrivateElements[0].payload` unset — no cryptographic material, valid unit, or prior relationship is required to reach the vulnerable line, since the crash happens before any of the unit/base64/index validations run.

### Recommendation
Validate that `arrPrivateElements[0]` is a non-empty object and that `.payload` is present and is itself a non-empty object before accessing `.payload.denomination`, e.g. using `ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload)` prior to line 2382, returning `callbacks.ifError(...)` on failure instead of throwing.

### Proof of Concept
1. As a device paired with the victim (or a peer capable of sending `justsaying` messages), send:
```
["justsaying", {"subject": "private_payment", "body": [ { "unit": "AAAA...==", "message_index": 0 } ]}]
```
i.e. an `arrPrivateElements` array whose first element has no `payload` field.
2. `handleOnlinePrivatePayment` executes `arrPrivateElements[0].payload.denomination`, throwing `TypeError`.
3. The exception is uncaught, hits `process.on('uncaughtException')`, and the process re-throws and crashes, per network.js:4530-4543.

Note: I could not fully trace every possible caller path invoking `handleOnlinePrivatePayment` with hub-relay semantics (e.g., whether the hub itself sanitizes `body` before relaying) due to index coverage limits on `wallet.js`'s five call sites; if a Devin session with full file access is desired to confirm all reachable paths, that would clarify whether hub-side pre-filtering mitigates any specific route.
