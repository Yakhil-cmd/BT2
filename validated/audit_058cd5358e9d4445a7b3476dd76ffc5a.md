### Title
API Client stack-scoped token can read CCMenu build/deploy status of any stack, bypassing the token's stack scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` records can be created with an optional `stack_id`, which is meant to restrict the token to a single stack. `Api::BaseController#stack` enforces this by resolving stacks through `stacks` (`current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`). `Api::CCMenuController` overrides the private `stack` method and resolves it directly via `Stack.from_param!(params[:stack_id])`, completely bypassing that scoping check, so a token scoped to stack A can retrieve CCMenu status for any other stack B.

### Finding Description
`Api::BaseController` defines the scoping contract that every API endpoint is expected to respect: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the token is scoped, and `stack` (used by e.g. `TasksController`, `MergeRequestsController`) always resolves through that scoped `stacks` relation, enforcing the binding: `token.stack_id == accessed_stack.id` (or "token unscoped").

`Api::CCMenuController`, however, overrides `stack` to bypass this relation entirely: [2](#0-1) 

Only `require_permission :read, :stack` is enforced, which is an operation-type check (`ApiClient#check_permissions!`) unrelated to which specific stack record is being fetched: [3](#0-2) 

Because `stack` in `CCMenuController` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`, the scope granted to the token (`stack_id` on `ApiClient`) is never checked against the actual stack being rendered. This breaks exactly the "a stack a token authorises versus a stack it touches" binding: the token authorizes stack A, but the CCMenu action touches whatever stack the caller names in the URL.

The route confirms `stack_id` is a free-form path segment supplied by the caller: [4](#0-3) 

### Impact Explanation
Any valid `ApiClient` token that has the `read:stack` permission — including one deliberately scoped to a single stack (as documented and tested for `StacksController#index`, e.g. `here_come_the_walrus` fixture) — can be used to query the CCMenu XML (`/api/stacks/*stack_id/ccmenu`) of every other stack in the Shipit installation, exposing build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`) for stacks it is not authorized to see: [5](#0-4) 

This is an authorization scope escalation resulting in unauthenticated (from the perspective of that specific stack) read of stack state/build status for stacks outside the token's intended scope, matching the High-severity bucket "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Exploitation only requires possession of any valid `read:stack` API client token (even a narrowly-scoped one issued for a single low-trust integration, e.g. a CI status badge) and knowledge/guessing of another stack's `to_param` (`owner/repo/environment`, which is often predictable or discoverable). No privilege beyond having any token is required to read cross-stack data via this endpoint, making this straightforward to exploit once any scoped token is obtained.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (as `BaseController#stack` does), e.g. `stacks.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` scope is enforced consistently across all API endpoints, including CCMenu.

### Proof of Concept
1. Create two stacks, `stack_a` (`owner/repo-a/production`) and `stack_b` (`owner/repo-b/production`).
2. Create an `ApiClient` scoped to `stack_a` only (`stack_id: stack_a.id`) with `read:stack` permission, and obtain its `authentication_token`.
3. Request `GET /api/stacks/owner/repo-a/production/ccmenu` with that token → succeeds (expected).
4. Request `GET /api/stacks/owner/repo-b/production/ccmenu` with the same token → also succeeds and returns `stack_b`'s build status, even though the token is scoped only to `stack_a`. This contradicts the scoping behavior verified for other endpoints, e.g.: [6](#0-5) 

which shows a scoped token ("an api client scoped to a stack will only see that one stack") is expected to be restricted — a guarantee `CCMenuController` fails to uphold.
