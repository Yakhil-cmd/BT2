### Title
Webhook signature verified against attacker's own organization while stack-mutating repository is chosen from a different, unverified field, allowing cross-tenant `ReviewStack` creation with attacker-controlled `branch` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the HMAC-verification organization from `params.dig('repository','owner','login')`, while every pull-request handler (e.g. `OpenedHandler`) resolves the repository to mutate from the independent field `params.repository.full_name`. Because these two string fields are never checked for consistency, an attacker who owns organization A (and thus knows A's `webhook_secret`) can forge a payload whose `repository.owner.login` is `"A"` but whose `repository.full_name` is `"B/repo"`, producing a validly-signed webhook that creates a `ReviewStack` on org B's real repository with `branch: params.pull_request.head.ref` taken verbatim from the forged body.

### Finding Description
The broken binding: `repository_owner_used_for_signature == repository_owner_of_the_repository_actually_mutated` is assumed but never enforced.

- `verify_signature` computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` and asks `Shipit.github(organization: repository_owner)` to verify the HMAC signature against that organization's `webhook_secret`: [1](#0-0) [2](#0-1) 

- Separately, `Handler#repository_name` / each pull-request handler resolves the target repository from `payload.dig('repository', 'full_name')` (or `params.repository.full_name` in `OpenedHandler`), a wholly independent string field in the same JSON body: [3](#0-2) [4](#0-3) 

- `Repository.from_github_repo_name` does a direct DB lookup by `owner/name` parsed from that `full_name` field with no relation back to the signature-verification owner: [5](#0-4) 

- `ReviewStackAdapter#stack_attributes` then takes `branch` verbatim from `params.pull_request.head.ref`, with no cross-check against org B's actual GitHub branch protection or against `repository.owner.login`: [6](#0-5) 

Exploit flow: attacker owns organization `A` in a Shipit install serving multiple organizations (each with its own `webhook_secret` via `Shipit.github(organization:)`). Attacker crafts a `pull_request` `opened` event payload:
```json
{
  "action": "opened",
  "number": 999,
  "repository": { "owner": { "login": "A" }, "full_name": "B/protected-repo" },
  "pull_request": { "head": { "ref": "attacker-controlled-branch" }, ... },
  "sender": { "login": "attacker" }
}
```
computes `X-Hub-Signature` using org A's known `webhook_secret`, and POSTs it to `/webhooks`. `verify_signature` reads `repository.owner.login == "A"`, fetches org A's GitHub app config, and successfully verifies the signature (attacker legitimately knows this secret). Processing proceeds; `OpenedHandler` resolves `Shipit::Repository.from_github_repo_name("B/protected-repo")` — org B's real repository — and (subject to `provision?` gating on B's repository settings, e.g. `allow_all` provisioning behavior) calls `ReviewStackAdapter#find_or_create!`, persisting a `ReviewStack` under org B with `branch` equal to the attacker's forged `head.ref`, unrelated to any real, authorized branch on B's GitHub repository.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type header; `verify_signature` checks a signature computed against the field the attacker controls and legitimately owns; `ExplicitParameters` schema only validates types/presence, not cross-field/tenant consistency; `Repository` model validators only constrain owner/name character sets, not that the record matches the org that signed the request.

### Impact Explanation
A crafted payload for one repository (nominally org A, whose secret authenticated the request) mutates another organization's data (org B) — creating a `ReviewStack` record with an attacker-chosen `branch` value under B's repository. Because `sync_github`/deploy pipelines treat `ReviewStack.branch` as authoritative, this seeds a stack pointed at a branch string the attacker fully controls, which can be leveraged for subsequent provisioning/deploy actions scoped to org B. This matches the Critical category: "a payload for one repository mutating another's stack." It is repeatable against any target repository (`org B`) as long as the attacker can compute a valid signature for some organization served by the same Shipit instance and that target repository's `provisioning_behavior` allows automatic review-stack creation (`allow_all`, or label-gated behaviors bypassed via `pull_request.labels` also attacker-controlled in the same forged payload).

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment serving at least two GitHub organizations with independent `webhook_secret`s (a supported and documented configuration, since `Shipit.github(organization:)` is keyed per org); (2) attacker owns/administers organization A within that same Shipit install (unprivileged relative to org B, consistent with the threat model — they only control their own org's secret); (3) target repository B has `review_stacks_enabled` with a permissive `provisioning_behavior`. No Shipit session, API token, or org B secret is needed — only knowledge of org A's own `webhook_secret`, which the attacker legitimately possesses. Cost is a single crafted HTTP POST; fully repeatable/scriptable against any repository in the install.

### Recommendation
Bind webhook signature verification to the same repository/organization actually acted upon: after `verify_signature` succeeds, re-derive and enforce that the organization used to fetch the `webhook_secret` matches the owner segment of `params.repository.full_name` (and reject if they differ) before dispatching to any handler; alternatively, resolve the target `Repository` first and verify the signature using that repository's associated organization's secret rather than a raw, independently-controlled `repository.owner.login` field.

### Proof of Concept
Under `test/controllers/webhooks_controller_test.rb` (or a new test), add a multi-org secrets fixture (e.g. reuse pattern from `test/dummy/config/secrets_double_github_app.yml`) with distinct `webhook_secret`s for org `A` and org `B`, and a real `Shipit::Repository` owned by `B`. Then:
```ruby
test "signature verified against org A allows forging a ReviewStack under org B with attacker branch" do
  repo_b = shipit_repositories(:B) # owner: 'b', name: 'protected-repo'
  payload = {
    action: 'opened',
    number: 999,
    repository: { owner: { login: 'A' }, full_name: 'b/protected-repo' },
    pull_request: {
      id: 1, number: 999, url: 'x', title: 'x', state: 'open', additions: 1, deletions: 0,
      head: { sha: 'a' * 40, ref: 'attacker-controlled-branch' },
      user: { login: 'attacker' }, assignees: [], labels: []
    },
    sender: { login: 'attacker' }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', ORG_A_WEBHOOK_SECRET, payload)

  post shipit.github_webhooks_path,
       params: payload,
       headers: { 'X-Github-Event' => 'pull_request', 'X-Hub-Signature' => signature, 'Content-Type' => 'application/json' }

  assert_response :ok
  stack = repo_b.review_stacks.find_by(environment: 'pr999')
  refute_nil stack
  assert_equal 'attacker-controlled-branch', stack.branch # violated equality: branch was never authorized against org B's repo
end
```
Both sides of the binding: `repository owner authenticated by signature ("A")` vs `repository actually mutated ("b/protected-repo")` — they differ, and the created `ReviewStack.branch` equals the attacker-forged `head.ref`, proving the divergence.
