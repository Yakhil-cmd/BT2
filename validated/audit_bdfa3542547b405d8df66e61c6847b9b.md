### Title
RAY-value `i128` overflow permanently freezes a large accrued market - (common/src/rates/scaling.rs)

### Summary
A market whose scaled debt times its borrow index exceeds the `i128` RAY-value domain causes every accrual to revert before the borrow-index cap can engage. Because all pool mutations call `global_sync` before repayment, withdrawal, liquidation, or further index updates, the affected market becomes permanently unusable and supplier funds remain locked.

### Finding Description
`scaled_to_original` computes `scaled.mul(index)`, where `Ray::mul` evaluates `scaled * index / RAY` and panics with `MathOverflow` when the exact quotient cannot fit `i128`. [1](#0-0) [2](#0-1) [3](#0-2) 

Accrual calls this conversion for both borrowed and supplied values before updating indexes, so an oversized debt value aborts `accrue_step` before `update_borrow_index` can clamp the index. [4](#0-3) 

Every existing-market mutation loads the cache and runs `global_sync`; therefore the same overflowing multiplication runs before `borrow`, `withdraw`, `repay`, `net_settle`, seizure, flash loans, strategies, and revenue claims. [5](#0-4) [6](#0-5) 

The protocol itself documents that valid caps and bounded indexes do not guarantee accrued values fit the RAY domain, and that value overflow can block repayment and withdrawal because those operations accrue first. [7](#0-6) 

### Impact Explanation
Once `borrowed * borrow_index / RAY` crosses `i128::MAX`, no operation that accrues the market can complete. Borrowers cannot repay, suppliers cannot withdraw, liquidators cannot reduce risk, and `update_indexes` cannot advance the stored timestamp because the panic occurs before the borrow index is capped. [4](#0-3) [8](#0-7) 

The project's harness confirms this end state: a sufficiently large market under sustained utilization reaches `MathOverflow`, after which withdrawal and repayment both revert. [9](#0-8) 

### Likelihood Explanation
The trigger requires a very large book and sustained accrued growth, but it is reachable through ordinary unprivileged `supply`, `borrow`, and later `update_indexes` calls when configured caps and token liquidity admit the required exposure. Supply and borrow caps limit entry size but do not prevent later index growth from pushing accrued RAY value beyond `i128`. [10](#0-9) [7](#0-6) 

The condition is not transient: once the book is in the overflowing domain, every mutation re-enters the same overflow before state can change. The index ceiling does not rescue the market because the unbounded scaled-value multiplication precedes the capped index update. [11](#0-10) 

### Recommendation
Bound stored share totals and accrued values so `scaled * index / RAY` remains representable before accrual can proceed, or make the value calculation saturate at the market-index ceiling rather than panic. Enforce entry caps in projected accrued-value units, not merely admitted asset units, and add an emergency path that can clamp indexes or settle positions without first evaluating an overflowing total. [12](#0-11) [8](#0-7) 

### Proof of Concept
1. An attacker supplies a very large amount of an 18-decimal asset through controller `supply` and borrows a large fraction of it through `borrow`, within the configured spoke caps.
2. The market remains at high utilization while ordinary `update_indexes` calls accrue interest. Each step computes `scaled_to_original(borrowed, borrow_index)` before `update_borrow_index` can clamp at `MAX_BORROW_INDEX_RAY`. [4](#0-3) 
3. When `borrowed * borrow_index / RAY > i128::MAX`, `Ray::mul` resolves through the widened exact path and then fails `to_i128`, producing `MathOverflow`. [13](#0-12) 
4. The repository's harness demonstrates the resulting state: `try_update_indexes_for(["BIG18"])` fails with `MATH_OVERFLOW`, the borrow index remains below its cap, and subsequent `withdraw` and `repay` calls fail with the same error because they accrue first. [14](#0-13) 
5. The result is permanent freezing of the market's supplier collateral and borrower repayment path rather than a bounded-index transition. [6](#0-5)

```rust
/// The division saturates at `i128::MAX` instead of panicking, so the cap check
```

```rust
/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```markdown
## Caps, fees, and numeric limits

A cap is in native token units. Entry compares stored scaled usage plus the
new scaled amount with the cap floor-converted at the current index. Zero cap
allows no positive exposure. Exits subtract usage without checking caps;
missing usage rows and zero exit deltas are no-ops. Cap→scaled conversion
saturates at `i128::MAX` (`calculate_scaled_cap`), so the entry check fails
open instead of trapping. A saturated scaled cap does not enforce the
configured asset-unit limit. An admitted cap saturates only at an index below
one RAY. Only a bad-debt write-down moves the supply index below one RAY; at
its floor (`RAY / 1000`), a supply cap above 1/1000 of the admitted maximum
saturates. The borrow index never falls below one RAY, so an admitted borrow
cap cannot saturate. Position conversion still rejects overflow.
```

```rust
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
