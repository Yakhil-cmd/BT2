## Title
Cross-tenant repository impersonation via decoupled webhook signature-org selection and payload `repository.full_name` resolution — ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC using `repository_owner`, which is read from `params.dig('repository','owner','login')` (or `organization.login`). `OpenedHandler` (and every other PR handler) instead resolves the target `Shipit::Repository` using a *different* field of the same untrusted JSON body, `params.repository.full_name`. Because these two fields are never cross-validated, an entity that legitimately knows the webhook secret for one Shipit-tracked organization can forge a signed payload whose `repository.full_name` names a repository belonging to a *different* tracked organization, causing Shipit to create/archive/unarchive a `ReviewStack` for a repository that never actually sent the event.

### Finding Description
The claimed provenance binding is: `Shipit.github(organization: repository_owner from params.repository.owner.login)` (secret used to authenticate the request) **must equal** `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (repository the handler mutates). Tracing the code shows these are independent reads of the same attacker-supplied JSON body with no equality check between them:

- Signature verification selects the app/secret purely from `repository.owner.login` / `organization.login`: [1](#0-0) [2](#0-1) 
- `Shipit.github` in multi-tenant mode looks up a per-organization config (distinct `app_id`/`webhook_secret` per org) keyed by that same string: [3](#0-2) 
- `OpenedHandler` never reads `repository.owner.login`; it resolves the acted-upon repository solely from `params.repository.full_name`, and its `ExplicitParameters` schema doesn't even require `owner.login` to be present: [4](#0-3) 
- `provision?`/`ReviewStackAdapter` then operate on whatever repository `from_github_repo_name` returns, creating/mutating its `ReviewStack`: [5](#0-4) [6](#0-5) 

Exploit flow (multi-org/multi-tenant Shipit deployment, i.e., `secrets.github` keyed by organization — see `github_default_organization`/`github_app_config`): an attacker who legitimately administers the Shipit↔GitHub App integration for their own organization `attacker-org` knows `attacker-org`'s `webhook_secret` (they configured it when wiring up the App/webhook). They POST to `/webhooks` with `X-Github-Event: pull_request`, a body where `repository.owner.login = "attacker-org"` (so `verify_signature` picks `attacker-org`'s secret, which they hold, and the HMAC validates) but `repository.full_name = "victim-org/victim-repo"` (a repository tracked under a different, victim organization in the same Shipit instance). `drop_unhandled_event`/`check_if_ping` pass, `verify_signature` passes because the attacker computed a correct HMAC with the secret it actually selected, and `OpenedHandler` then resolves and mutates `victim-org/victim-repo`'s review stacks — a payload for one repository (as authenticated) mutating another repository's stack.

None of the existing guards close this gap: `verify_signature` only proves the request was signed by *some* org's configured secret, not that the org whose secret was used matches the repository named in the payload body used by the handler; the `ExplicitParameters` schema on `OpenedHandler` only validates presence/types, not cross-field consistency with `repository.owner.login`; there is no `require_permission!`/`User#authorized?` check in this webhook path since GitHub webhooks are not user-session-authenticated.

### Impact Explanation
This is Critical impact: "a payload for one repository mutating another's stack." In a multi-tenant Shipit deployment (multiple orgs configured under `secrets.github`), any org that is a legitimate but low-trust tenant can forge PR-opened/labeled/closed/reopened events for any *other* tracked repository, causing unauthorized `ReviewStack` creation, provisioning-queue enqueue, archive/unarchive actions, and `PullRequest` record writes against a victim repository the attacker does not control — repeatable at will for any repository name resolvable via `Repository.from_github_repo_name`.

### Likelihood Explanation
Exploitability is conditional on the deployment running Shipit in multi-organization mode with per-org webhook secrets (`github_default_organization` non-nil, i.e., `secrets.github` keyed by org) and the attacker being a legitimate administrator/holder of the webhook secret for at least one tracked organization. If Shipit is configured in single-app/global-secret mode, `Shipit.github(organization: ...)` always returns the same global config regardless of `repository_owner`, so the divergence described here has no additional effect (the secret used for verification doesn't vary with the payload's claimed owner) — in that mode this specific cross-tenant vector does not apply, though it still doesn't verify the resolved repository matches the actually-configured tenant of the secret used. Given the explicit multi-tenant support in `lib/shipit.rb` (`github_app_config`, `github_organizations`), this is a realistic configuration.

### Recommendation
In `WebhooksController` or `Handler`, after selecting the GitHub App via `repository_owner`, enforce that the owner segment of `params.repository.full_name` (as read by the handler) matches `repository_owner` used to select/verify the signature; reject (422) any payload where these diverge before dispatching to handlers.

### Proof of Concept
Minitest plan (add to `test/controllers/webhooks_controller_test.rb`), assuming a multi-org fixture setup with two orgs `attacker-org` and `victim-org` each with distinct `webhook_secret`s configured under `secrets.github`:
1. Configure `Shipit.stubs(:github_app_config)` (or credentials fixture) so `attacker-org` and `victim-org` have different `webhook_secret`s, and create a tracked `Shipit::Repository` for `victim-org/victim-repo` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`.
2. Build a `pull_request` `opened` payload with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"`.
3. Sign the raw body with `attacker-org`'s `webhook_secret` and set `X-Hub-Signature` accordingly.
4. `assert_difference -> { Shipit::ReviewStack.count }, 1 do post :create, body: payload, as: :json end` — asserting the victim's stack count increased, i.e., `repository_owner` used for signature selection (`attacker-org`) does NOT equal the owner of the repository actually mutated (`victim-org`), proving the provenance binding is broken. Assert `response` is `:ok` (not `422`), confirming signature verification passed despite the mismatch.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
