### Title
Asset definer can unilaterally rewrite the `spender_attested` attestor list at any time, freezing already-issued coins held by existing holders - (File: `validation.js`)

### Summary
For any asset created with `spender_attested: true`, the asset definer can post an `asset_attestors` message at any later time to replace the entire list of trusted attestors, with no restriction on frequency, timing, or prior notice. Because payment validation checks attestation against the *current* attestor list rather than the list in effect when a holder acquired the coins, the definer can instantly invalidate all previously valid attestations for existing coin holders, freezing their funds. This mirrors the External Report's `updateArtSettings` issue: a privileged party (the asset issuer, analogous to the "artist") can change critical enforcement parameters of an already-issued token/asset after the fact, harming holders who transacted under the original rules.

### Finding Description
When an asset is defined with `spender_attested: true`, every payment (issue, transfer, or output) involving that asset must have its input/output addresses attested by one of the asset's registered attestors [1](#0-0) , and again for outputs at spend time [2](#0-1) , and for private fixed-denomination inputs [3](#0-2)  and public divisible inputs [4](#0-3) .

The attestor list is not fixed at asset creation. The definer can post an `asset_attestors` message at any time to completely replace it: [5](#0-4) 

The only checks are that the message is single-authored, that the sender is the asset's `definer_address`, and that the new list is well-formed (sorted, valid addresses, under `MAX_ATTESTORS_PER_ASSET`) [6](#0-5) . There is no limitation on:
- How often the list can be changed,
- Overlap with the previous list,
- Or any grace period for addresses already holding coins under the old list.

Critically, when resolving which addresses are currently "attested," the code always looks up the *latest* attestor list for the asset and only counts attestations issued by addresses in that latest list: [7](#0-6) [8](#0-7) 

If the definer swaps out the attestor set for a completely new set of addresses (who have not yet attested anyone), every previously-attested holder immediately loses the ability to spend or receive the asset — `arrAttestedAddresses` becomes empty for them until the new attestors re-attest them.

### Impact Explanation
This lets the asset issuer/definer freeze the funds of any or all existing holders of a `spender_attested` asset at will, at any point after issuance, without the holders' consent or any advance notice — directly analogous to the reported `updateArtSettings` bug where the artist could toggle `soulBounded` to trap already-minted NFT holders. Holders who acquired the asset trusting the attestor set at time of purchase can find their coins permanently unspendable if the definer changes attestors and the new attestors never attest them (maliciously or through simple non-cooperation). This is a fund-freezing vulnerability reachable by a single privileged but otherwise unprivileged-from-the-protocol's-perspective party (the asset definer address), acting through a normal, validly-signed unit.

### Likelihood Explanation
Likelihood is high: any user can define an asset with `spender_attested: true` (this is a completely permissionless, standard asset feature, not an admin-only capability), acquire trust from token holders, and later post a single `asset_attestors` unit to swap in attestors under the definer's own control (or attestors who simply refuse to attest anyone), instantly freezing all previously circulating coins. No special privileges beyond being the asset's own definer are required, and the change takes effect as soon as the unit becomes stable — no cooldown, timelock, or opt-in mechanism exists.

### Recommendation
- Require that any attestor-list update for an already-circulating asset preserve attestations issued under previous attestor lists for a grace period, or
- Cache/anchor the attestor list validity to the MCI at issuance/last transfer of each specific output rather than always using the latest list, or
- Add a minimum delay (timelock) between successive `asset_attestors` updates and require it be announced ahead of effect, giving holders time to react, similar to the fix direction taken in the referenced report (removing/limiting unrestricted post-issuance changes to critical enforcement settings).

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and an initial attestor list `[X]` (validated per `validateAssetDefinition`, `validation.js:2725-2827`).
2. `X` attests holder `H`'s address. `H` receives coins of asset `A` in a payment that passes the `spender_attested` check at `validation.js:2115-2122`/`2630-2641` because `H` is in `arrAttestedAddresses` (attested by `X`, currently the sole attestor).
3. At any later time, `D` posts an `asset_attestors` message for asset `A` with a brand-new attestor list `[Y]` where `Y ≠ X` and `Y` has never attested anyone. This passes validation solely because `D` is `objAsset.definer_address` (`validation.js:2829-2848`); there is no cooldown or holder consent check.
4. `storage.readAsset`/`filterAttestedAddresses` now resolve the "latest" attestor list to `[Y]` (`storage.js:1917-1946`, `1960-1974`). Since `Y` never attested `H`, `H`'s address no longer appears in `arrAttestedAddresses`.
5. `H` attempts to spend or transfer the previously received asset `A` coins. `validatePaymentInputsAndOutputs` rejects it with "owner address is not attested" (`validation.js:2506-2507`) or "some output addresses are not attested" (`validation.js:2637-2638`), permanently freezing `H`'s funds unless `D`/`Y` chooses to re-attest `H`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
