### Title
Webhook signature verified against `repository.owner.login`'s org secret while stack-matching handlers act on the unrelated `repository.full_name` field - cross-organization stack sync ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify the raw payload against using `repository.owner.login` (falling back to `organization.login`). Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers whose `stacks`/`repository` lookup uses an entirely different field of the same attacker-controlled JSON body: `repository.full_name`. No code enforces that `repository.owner.login` and `repository.full_name`'s owner segment refer to the same organization.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
selects the verifying `GithubApp` via `repository_owner`: [2](#0-1) 

`Shipit.github(organization:)` looks up a **per-organization** `webhook_secret` when the engine is configured for multiple GitHub Apps (documented and tested multi-tenant configuration): [3](#0-2) [4](#0-3) 

Once `verify_signature` passes, `create` dispatches the same raw payload to registered handlers: [5](#0-4) 

`Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` resolves the target repository/stack using a **different** JSON field — `repository.full_name` — not `repository.owner.login`: [6](#0-5) 

`PushHandler#process` then matches stacks by branch and directly triggers a GitHub sync with an attacker-supplied `expected_head_sha`: [7](#0-6) 

Because the HMAC in `verify_webhook_signature` only proves the payload was signed with the secret belonging to the org named in `repository.owner.login`, and that field is never cross-checked against `repository.full_name`, an attacker who legitimately controls one organization's webhook secret (`OrgA`) can craft a payload where `repository.owner.login == "OrgA"` (so the signature check passes using OrgA's secret) but `repository.full_name == "OrgB/target-repo"` (so the handler resolves and acts on a stack belonging to `OrgB`, an organization the attacker has no credentials for). This breaks the equality that should hold: `organization whose secret authenticated the request == organization that owns the repository/stack being acted upon`.

### Impact Explanation
This allows an attacker with only their own organization's webhook secret (no privileged access to the target org/repo) to trigger `Shipit::GithubSyncJob` on a `Stack` belonging to a completely different, unrelated organization hosted on the same Shipit instance, with an attacker-chosen `expected_head_sha`. This is an unauthorized cross-organization write into the target stack's commit history/state (`stack.commits.create_from_github!`, `CacheDeploySpecJob`), potentially enabling a spoofed "new commit landed" signal that can influence deploy eligibility for a repository the attacker does not control. This matches the "cross-repository writes" / "unauthorized deploy" impact category, since it can drive an unauthorized stack synchronization step that downstream deploy logic and status checks rely on.

### Likelihood Explanation
Requires Shipit to be configured for multiple GitHub organizations (explicitly documented and supported feature, `docs/setup.md` "Using Multiple Github Applications", and covered by `test/dummy/config/secrets_double_github_app.yml`). Any attacker who is an admin of one org's onboarded GitHub App (and therefore knows that org's `webhook_secret`) can exploit this without needing access to the victim org at all — a low bar in genuinely multi-tenant deployments.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the organization used to select/verify the webhook secret matches the owner segment of `repository.full_name` (and `organization.login` if present) before dispatching to handlers. Reject the webhook (422) if these fields disagree.

### Proof of Concept
Assume Shipit is configured with two orgs, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (multi-org config as in `test/dummy/config/secrets_double_github_app.yml`). Attacker is an admin of `OrgA`'s GitHub App and knows `OrgA`'s `webhook_secret`.

1. Attacker crafts a `push` event payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `OrgA`'s known `webhook_secret` over this raw body.
3. POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies the HMAC successfully (attacker owns this secret).
5. `create` dispatches to `PushHandler`, whose `repository_name` reads `repository.full_name == "OrgB/target-repo"`, resolves `OrgB`'s stacks, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — a write triggered on `OrgB`'s stack despite the signature only proving control of `OrgA`.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
