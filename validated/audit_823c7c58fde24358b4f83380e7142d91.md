### Title
Cross-organization team hijack via unscoped `github_id` lookup in `MembershipHandler#process` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Shipit::Team` purely by the numeric `github_id` supplied in the webhook body, with no check that the team's `organization` matches the organization whose webhook secret actually verified the request. An attacker who owns any GitHub organization with a registered `membership` webhook can sign a payload with their own legitimate secret, but reference an arbitrary pre-existing team's `github_id`, and get added as a member of that team via `Team#add_member`.

### Finding Description
The broken binding is: `team.organization == params.organization.login` (the organization whose `webhook_secret` verified the request) should hold whenever the handler mutates membership of an existing `Team` row, but this is never enforced.

Trace:
- `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` where `repository_owner` falls back to `params.dig('organization', 'login')` for events without a `repository` key [1](#0-0) . The attacker legitimately owns this organization and its `webhook_secret`, so `verify_webhook_signature` succeeds — signature verification is correct for the attacker's own org, but says nothing about the `team.id` field inside the payload.
- `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [2](#0-1) . Since GitHub team IDs are global, this lookup is not scoped to `params.organization.login` at all — it only initializes `team.organization` inside the create block, which never runs if a row with that `github_id` already exists.
- `Team#add_member` then unconditionally appends the payload's `member` (also attacker-controlled) to `members` [3](#0-2) .
- `Team.github_hooks` is scoped by `organization` [4](#0-3) , but this association is never consulted during webhook processing — it exists for other purposes (e.g. refresh jobs), not for authorizing which org's webhook may mutate which team's membership.
- If the targeted team is one of `Shipit.github_teams`, `User#authorized?` grants the attacker access to Shipit itself: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [5](#0-4) .

Exploit: attacker owns org `evil-corp` with a registered `membership` webhook. They POST to `/webhooks` with `X-Github-Event: membership`, `action: 'added'`, `organization: {login: 'evil-corp'}`, `team: {id: <victim's real numeric team id>}`, `member: {login: 'attacker'}`, signed with `evil-corp`'s real secret. `verify_signature` passes (correct secret for `evil-corp`). `find_or_create_team!` returns the pre-existing victim `Team` row matching that `github_id` (created earlier from the victim org's real membership events), completely ignoring that the request came from `evil-corp`. `team.add_member(attacker_user)` adds the attacker to the victim's team.

None of the existing guards catch this: `verify_signature` only checks the payload was signed by *some* registered org, not that it's authoritative for the referenced `team.id`; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of fields, not cross-org ownership.

### Impact Explanation
The attacker gains membership in an arbitrary pre-existing `Shipit::Team` record by guessing/knowing its numeric GitHub team ID, without ever being a real member of that team's organization. If that team is configured in `Shipit.github_teams`, this is a direct authorization-bypass escalation into Shipit's own permission model (`User#authorized?`), granting access to protected stacks/deploys the attacker has no legitimate right to. This is repeatable against any team whose numeric `github_id` is known or discoverable, and the only precondition is that the attacker's own org has a `membership` webhook registered — which is trivially something any GitHub org owner can do to their own org. This matches the "escalation into `Shipit.github_teams` authorization" High-severity category, and can reach Critical if `Shipit.github_teams` gates deploy/merge/rollback authorization.

### Likelihood Explanation
Preconditions: attacker needs a `GithubHook::Organization` row for an org they own with `event: 'membership'` — feasible since Shipit registers hooks for orgs the operator connects, and the attacker only needs to be an owner/admin of some org that has been onboarded to Shipit (a common self-service flow for GitHub App/OAuth integrations). They need the victim team's numeric `github_id`, which may be predictable/enumerable (sequential IDs, or discoverable via public GitHub API `GET /orgs/{org}/teams`, which does not require special access for many orgs). No Shipit session, token, or secret of the victim org is required. This is a single crafted HTTP POST, fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization: params.organization.login`, and refuse to mutate membership (`add_member`/`members.delete`) on an existing `Team` row whose `organization` does not match the verified `params.organization.login`. Additionally consider validating a uniqueness constraint on `(github_id, organization)` rather than `github_id` alone, and explicitly rejecting/logging membership events where the target team's stored `organization` differs from the webhook's authenticated organization.

### Proof of Concept
```ruby
test "membership webhook from a different organization cannot add a member to an existing team" do
  victim_org = GithubHook::Organization.create!(organization: 'victim-org', webhook_secret: 'victimsecret', event: 'membership')
  attacker_org = GithubHook::Organization.create!(organization: 'evil-corp', webhook_secret: 'attackersecret', event: 'membership')

  victim_team = Team.create!(github_id: 999, organization: 'victim-org', slug: 'admins', name: 'Admins', api_url: 'https://api.github.com/teams/999')

  payload = {
    action: 'added',
    team: { id: 999, name: 'Admins', slug: 'admins', url: 'https://api.github.com/teams/999' },
    organization: { login: 'evil-corp' }, # attacker's own org
    member: { login: 'attacker' }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'attackersecret', payload)

  request.headers['X-Github-Event'] = 'membership'
  request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { Membership.where(team: victim_team).count } do
    post :create, body: payload, as: :json
  end
  # Expect: attacker is NOT added to victim_team.
  # Currently fails because Team.find_or_create_by!(github_id: 999) matches victim_team
  # regardless of organization: 'evil-corp' in the verified payload.
end
```
This demonstrates that `team.organization` ('victim-org') and `params.organization.login` ('evil-corp') diverge yet `find_or_create_team!` still returns/mutates the victim team, proving the broken binding.

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

            team.add_member(member)
          when 'removed'

          end
        end
