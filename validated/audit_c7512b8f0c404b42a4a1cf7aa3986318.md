### Title
Asset ticker names are not normalized for Unicode confusables, enabling IDN-homograph-style asset spoofing - (File: wallet.js)

### Summary
Any address can act as a "registry" and post a `data` message defining `asset_metadata` (`asset`, `name`, `suffix`, `decimals`) for an asset it controls. Wallets fetch and cache this metadata via `fetchAssetMetadata` and display `payload.name` (optionally with `.suffix`) as the asset's ticker to the user, exactly like Keycloak displayed a username string without homograph protection.

### Finding Description
`fetchAssetMetadata` in [1](#0-0)  takes `payload.name` straight from an untrusted `data` message and only checks that it's non-empty (`if (!payload.name) return handleMetadata(...)`), with no normalization (NFC/NFKC) and no restriction to a "confusable-safe" character set (e.g. ASCII-only). It is then inserted into `asset_metadata` keyed by `UNIQUE(name, registry_address)` as defined in [2](#0-1) , and surfaced to the user in `readAssetMetadata` as the asset's display name: [3](#0-2) .

Because uniqueness/equality is purely byte-for-byte string comparison (both in the SQL `UNIQUE` index and in the JS name-change check at `assocAssetMetadata[asset].name === name`, [4](#0-3) ), an attacker who controls a different "registry" address (any single-authored address can define asset metadata for its own asset) can register a ticker that is visually indistinguishable from an existing legitimate asset's ticker by substituting Unicode homoglyphs (e.g. Cyrillic "а" for Latin "a", or other confusable code points). Since the uniqueness constraint is scoped to `(name, registry_address)`, this doesn't even collide with the real entry — a spoofed name simply coexists as a distinct row that renders identically to the user in wallet UI (asset pickers, balances, payment confirmation dialogs).

This mirrors CVE-2021-3424: Keycloak trusted an unnormalized/unrestricted identity string for uniqueness and display, letting an attacker register a homoglyph-confusable identity and trick a privileged party (the admin) into treating it as the real one.

### Impact Explanation
A user (or an operator approving a payment/AA interaction) who visually selects an asset by its displayed ticker/name can be tricked into sending funds under, or trusting, a spoofed asset that looks identical to a well-known one but is actually controlled by an attacker. In payment/AA contexts where the ticker is used as a human decision point (e.g., choosing which asset to send in a wallet dialog, or configuring an AA/oracle deal off-chain based on displayed names), this can lead to funds being sent to the wrong (malicious) asset instance, i.e., concrete unauthorized spending. This satisfies the Medium-severity classification of the original advisory.

### Likelihood Explanation
Likelihood is moderate: any address can post a `data` message defining metadata for an asset it authored, at ordinary DAG-posting cost, and craft `payload.name` using Unicode homoglyphs freely since there is no character-set restriction. The most likely trigger is social engineering combined with wallet UI display rather than a purely on-chain protocol violation, but it is reachable by an ordinary unprivileged unit poster acting as an "asset issuer"/"registry".

### Recommendation
Normalize asset metadata `name` (and `suffix`) using Unicode NFKC before storage/comparison, and additionally restrict names to a constrained character set (e.g., ASCII alphanumerics plus a small punctuation set) similar to ticker-symbol conventions, rejecting names containing mixed scripts or confusable code points. Enforce this both in `fetchAssetMetadata` validation (`wallet.js`) and consider surfacing the `registry_address`/`asset` hash alongside the display name in the UI to reduce reliance on the name alone for identification.

### Proof of Concept
1. Attacker defines asset A (unit `assetA`) and, from any address `R_attacker` acting as a "registry", posts a `data` message: `{app:'data', payload:{asset:'assetA', name:'Ο𝐛уte', decimals:0}}` using homoglyphs that render identically to a well-known ticker (e.g., "Obyte").
2. A victim wallet queries `hub/get_asset_metadata` for `assetA`, receives `registry_address = R_attacker`, and `fetchAssetMetadata` accepts the name unchanged since only non-emptiness is checked ( [5](#0-4) ).
3. `readAssetMetadata` displays this spoofed name to the user identically to the genuine asset's name ( [3](#0-2) ), and the two entries coexist without collision because the `UNIQUE` constraint is scoped per `registry_address` ( [2](#0-1) ).
4. The user, trusting the displayed name, sends payment intending to interact with the real asset but is misled about which asset instance they are dealing with.
