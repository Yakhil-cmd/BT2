### Title
Webhook signature is verified against an org selected from `repository.owner.login`, while all handlers act on the independently-controlled `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / webhook secret to validate a payload against using `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Every `Webhooks::Handlers::Handler` subclass, however, resolves the `Repository`/`Stack` to act on using a *different* JSON field of the same payload: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so an attacker who can get a valid signature for *any* configured organization (including one with no `webhook_secret` set, which is explicitly supported as "optional") can forge a payload whose `repository.full_name` points at a stack that belongs to a completely different, properly-secured organization.

### Finding Description
- Signature/organization selection: [1](#0-0)  selects the `GitHubApp` instance via `Shipit.github(organization: repository_owner)` and verifies the HMAC using that org's secret.
- `repository_owner` is read from `repository.owner.login` (or `organization.login`): [2](#0-1) .
- Every handler resolves the affected repository/stacks from a *different* field, `repository.full_name`, with no cross-check against `repository.owner.login`: [3](#0-2) .
- `webhook_secret` is documented and coded as optional per organization; when absent, signature verification trivially passes: [4](#0-3) . Multi-org configuration is a first-class supported mode: [5](#0-4) , and the setup docs show `webhook_secret` as optional per org: [6](#0-5) .
- `PushHandler` (and other handlers, e.g. `StatusHandler` for commits by sha) act purely on data scoped by `stacks`/`Repository.from_github_repo_name(repository_name)`, i.e. `full_name`: [7](#0-6) .

Because the raw body is what's HMAC-signed, in a *single-organization* deployment this is fine (the whole body, including `full_name`, is covered by one secret). But in a multi-organization deployment — which the engine explicitly supports — the secret used to validate the request is chosen by `repository.owner.login`, not by `repository.full_name`. An attacker who is a legitimate GitHub user for **any** one of the configured organizations (or targets an org intentionally left with no `webhook_secret`, which the docs mark optional) can send Shipit a webhook whose `X-Hub-Signature` is valid for that org, but whose `repository.full_name` names a repository belonging to an entirely different tracked organization/stack. Verification passes (secret matches for the attacker's own org, or is skipped because none is configured), yet the handler dispatches actions against the victim organization's stack.

This is the direct structural analog of the reported bug: the wrapper (webhook controller) trusts one field (`registry`/`owner.login`) for a security check while a different, unguarded field (`_cachedVaults`/`full_name`) drives the actual state change — the two are never reconciled or bound together.

### Impact Explanation
For `push` events this triggers `stack.sync_github(expected_head_sha: ...)` on **any tracked stack in any organization**, using an attacker-chosen `after` SHA and forged `ref`/branch, which is an unauthorized GitHub sync trigger for a foreign organization's stack; combined with the merge queue/CI machinery this can precipitate unintended deploy attempts. This crosses the "an organization that authenticated versus the repository that is written" boundary explicitly named in scope and constitutes cross-repository/cross-organization forged webhook delivery, i.e., an unauthorized action against a stack the attacker's own organization credentials should not be able to touch — matching the High-severity category "escalation ... or unauthenticated read/write of stack state" via a broken multi-tenant trust boundary.

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations (a documented, supported configuration), and (2) the attacker being able to trigger any webhook event from one of those orgs' repos (e.g., pushing to any repo they control within an org that is configured, or targeting an org whose `webhook_secret` was left blank, which the docs present as an acceptable/optional setting) while forging the JSON body's `repository.full_name` to name another org's tracked repository, sent directly to Shipit's `/webhooks` endpoint (not proxied strictly through GitHub, since the check only validates the signature, not the source). This is plausible in real multi-tenant Shipit deployments and requires no privileged Shipit credentials at all — only ordinary GitHub push access to a repo in any one configured org, or knowledge that a given org has no secret set.

### Recommendation
- Derive the organization used for `verify_signature` from the *same* identifier used later to resolve the `Repository`/`Stack` (i.e., parse `repository.full_name` and use its owner segment, not a separate `owner.login`/`organization.login` field), or better, verify the signature against *all* configured organizations' secrets and additionally confirm the resolved `Repository`'s owner matches the org whose secret validated the payload.
- Do not treat `webhook_secret` as safely optional in multi-organization mode; require it whenever more than one GitHub org is configured, and fail closed if missing.
- Add an explicit invariant check that `repository.owner.login` (used for auth) equals the owner segment of `repository.full_name` (used for stack lookup) before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgAttacker` (attacker has push access to a repo tracked there, or `webhook_secret` intentionally left blank) and `OrgVictim` (properly secured, tracks stack `orgvictim/prod-app`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "orgvictim/prod-app"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `OrgAttacker`'s webhook secret (which they know, e.g. because they operate/administer a repo under that org, or because it is unset).
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: 'OrgAttacker')` and succeeds (own secret matches, or no secret configured) — see [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('orgvictim/prod-app')` — see [3](#0-2)  and [8](#0-7)  — and calls `stack.sync_github(expected_head_sha: ...)` on the victim org's stack, despite the request never being signed by `OrgVictim`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
