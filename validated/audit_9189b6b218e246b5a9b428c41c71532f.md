### Title
`load_rules` resolves rule file glob relative to process CWD instead of `CLAUDE_PROJECT_DIR`, enabling workspace-drift rule injection - ([File: plugins/hookify/core/config_loader.py])

### Summary
`load_rules` builds its glob pattern with `os.path.join('.claude', 'hookify.*.local.md')`, a path relative to the process's current working directory, rather than anchoring to the validated project root exposed via `CLAUDE_PROJECT_DIR`. If the CWD used to spawn the hook process drifts from the canonical workspace root (e.g. nested checkout, subdirectory session, or any mechanism that changes the effective CWD seen by the hook process), `load_rules` will silently load and enforce rules from whatever `.claude` directory happens to sit under that CWD instead of the intended project's rules.

### Finding Description
`load_rules` (plugins/hookify/core/config_loader.py:198-241) computes:
```python
pattern = os.path.join('.claude', 'hookify.*.local.md')
files = glob.glob(pattern)
```
This is purely CWD-relative — there is no call to `os.getcwd()` validation, no reference to `CLAUDE_PROJECT_DIR`, and no canonicalization against a known workspace root anywhere in `config_loader.py` (confirmed via repo-wide search: `CLAUDE_PROJECT_DIR` has zero matches in `plugins/hookify/`, whereas the sibling `plugins/security-guidance/hooks/*.py` files use `CLAUDE_PROJECT_DIR` extensively (41 matches in `security_reminder_hook.py` alone) to correctly bind filesystem operations to the approved workspace). This shows the codebase already has an established, correct pattern for workspace-root binding that `hookify`'s loader does not follow.

The four hook entry points (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) all call `load_rules(event=...)` directly with no CWD/workspace validation before or after the call [1](#0-0) . Because `Rule` objects loaded this way are fed straight into `RuleEngine.evaluate_rules`, any `.claude/hookify.*.local.md` file reachable from the effective CWD is trusted and enforced as if it belonged to the current session's project — violating the invariant that hook enforcement state must stay bound to the approved workspace root, not to an incidental CWD value.

### Impact Explanation
If CWD binding drifts (multi-repo/nested-workspace scenarios, or any wrapper/tooling that spawns the hook subprocess from a different directory than the canonical project root), an attacker-controlled `.claude/hookify.*.local.md` file placed in a foreign directory can be picked up and enforced against a different, legitimate workspace/session. Since rules can define `action: block/warn` and arbitrary messages surfaced back into the agent's decision loop, this is a workspace-escape / cross-repo rule-injection primitive — the enforcement/guidance layer for one project becomes attacker-controlled by content that lives outside that project's boundary.

### Likelihood Explanation
Exploitability depends entirely on whether the process CWD supplied to the hook subprocess can, in practice, diverge from the canonical project root (e.g., nested checkouts, monorepo submodule sessions, or any host-side mechanism that launches hook scripts from a working directory other than the fixed project root). This precondition is external to this plugin's code and could not be confirmed from the repository alone, since the host process that spawns `pretooluse.py`/etc. and sets its CWD is not part of this codebase. Within the plugin itself, though, the code has no defense at all against such drift — it is fully CWD-trusting.

### Recommendation
Anchor `load_rules` (and any other path derived in `config_loader.py`) to `os.environ.get('CLAUDE_PROJECT_DIR')` (falling back to a resolved/validated project root, not raw `os.getcwd()`), matching the pattern already used in `plugins/security-guidance/hooks/*.py`. E.g.:
```python
project_dir = os.environ.get('CLAUDE_PROJECT_DIR') or os.getcwd()
pattern = os.path.join(project_dir, '.claude', 'hookify.*.local.md')
```
and ideally validate that the resolved path is inside the expected workspace root before globbing/loading.

### Proof of Concept
Integration test:
1. Create canonical workspace dir `WORKSPACE/.claude/hookify.safe.local.md` with a benign rule.
2. Create a foreign subdirectory `WORKSPACE/subdir/.claude/hookify.evil.local.md` with a malicious `action: block` rule.
3. `chdir(WORKSPACE/subdir)` and call `load_rules()`.
4. Current behavior: the evil rule from `subdir/.claude` is returned/enforced instead of (or in addition to) the canonical workspace's rules — demonstrating that `load_rules` output depends on CWD rather than the fixed project root, i.e., `CLAUDE_PROJECT_DIR` environment variable pointing at `WORKSPACE` is ignored.
5. Expected assertion after fix: `load_rules()` called from any CWD, given `CLAUDE_PROJECT_DIR=WORKSPACE`, only returns rules from `WORKSPACE/.claude/`, never from `subdir/.claude/`.
