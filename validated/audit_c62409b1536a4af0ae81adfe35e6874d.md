### Title
Silently dropped evaluation callback on zero-parse-result formulas causes AA trigger processing to hang - (File: formula/evaluation.js)

### Summary
`libyara/grammar.y`'s CVE-2017-5923 shows that a bison/yacc-based parser can be driven into a state where the parser's internal invariants are violated by a crafted input, producing memory-safety corruption and a crash (DoS). `ocore` does not use a C parser generator for its oscript/AA formula language — it uses the JS `nearley` Earley parser [1](#0-0) [2](#0-1)  — so the memory-corruption bug class does not translate directly (V8 guarantees memory safety for JS). However, the underlying bug class — "crafted input drives the grammar/parser into an unhandled state, causing mishandled results" — has a reachable analog in `ocore`: the parser-result branch in `exports.evaluate` (`formula/evaluation.js`) does not handle the case where `nearley` successfully feeds a formula but yields zero parse trees.

### Finding Description
In `formula/evaluation.js`, after parsing a formula with `nearley`, the code checks the parse result set: [3](#0-2) 

If `parser.results.length === 1`, it evaluates normally. If `parser.results.length > 1` (ambiguous grammar), it calls `callback('ambiguous grammar', null)`. But if `parser.results.length === 0` — a state that `nearley.Parser.feed()` can legitimately produce without throwing, when the fed tokens are consistent with the grammar up to a point but never reduce to a complete valid `main` symbol — **neither branch executes**, so `callback` is never invoked.

Compare this with the sibling function in `formula/validation.js`, which is used to statically validate a formula (e.g., at AA-registration time) and correctly handles all three cases, including the zero-result case: [4](#0-3) 

Because `formula/evaluation.js`'s equivalent branch omits the `else` fallback for the zero-results case, any code path that reaches `exports.evaluate` with a formula string whose parse produces zero results will hang forever waiting on a callback that is never called.

### Impact Explanation
`exports.evaluate` in `formula/evaluation.js` is invoked from `aa_composer.js` while executing AA bounce/response formulas, state-variable formulas, and getters during trigger processing. If a formula string reaches this function with a fresh (non-cached) parse that yields zero results, the enclosing async continuation for that AA trigger (and potentially the surrounding response/bounce chain) never resolves. This can stall a validator/witness node's AA response-processing worker for that unit indefinitely (until process restart), i.e., a node becomes unable to finish processing that trigger and any triggers serialized behind it for the same AA/response-generation flow — a node-level denial of service on AA execution, matching the "network unable to confirm new units"/node-disagreement class of impact called for in scope.

### Likelihood Explanation
Reaching this exact code path requires that:
1. A formula string used at evaluation time differs from what was checked in `formula/validation.js` (which does correctly reject `results.length !== 1`), OR
2. There exists an evaluation-time-only formula construction (e.g., via `fixFormula`, dynamically composed getter/remote-call formulas, or cache staleness) that can produce a distinct parse outcome not exercised during validation.

I was not able to fully confirm within the available context whether `fixFormula` (`formula/common.js`) or any dynamically-built formula string used only at evaluation time (not validation time) can actually drive `nearley` to a genuine zero-result parse for attacker-supplied AA definitions/triggers — my investigation was cut off before I could inspect `fixFormula`'s implementation and all call sites of `evaluation.evaluate` (`aa_composer.js`, `formula/index.js`, `network.js`) to determine whether attacker-controlled input can produce a formula string that was never validated with the length-checking guard. This is a **structural code defect** (missing `else` branch causing a silent hang) that is confirmed by direct comparison of the two files, but the concrete end-to-end trigger path from an unprivileged AA-trigger sender to this exact code state is **not fully proven** with the tools available.

### Recommendation
In `formula/evaluation.js`, mirror the exhaustive handling already present in `formula/validation.js`: add an explicit `else` for the `parser.results.length === 0` (or any non-1, non->1) case that always invokes `callback` with an error (e.g., `callback('parser failed', null)`), guaranteeing the callback fires exactly once regardless of parse outcome. Additionally, audit every caller of `exports.evaluate` (`aa_composer.js`, `formula/index.js`, `network.js`) to confirm formulas passed to it are always the exact strings that passed through `formula/validation.js`'s exhaustive check, and add defensive re-validation or a timeout/guard around AA formula evaluation to prevent indefinite hangs regardless of root cause.

### Proof of Concept
Not fully constructible from static analysis alone: reproducing this requires identifying a concrete formula string that `nearley.Parser.feed()` accepts without throwing but resolves to `parser.results.length === 0`, and confirming a code path (e.g., via `fixFormula` transformation or a dynamically-built getter/remote-call formula) that feeds such a string into `formula/evaluation.js`'s `exports.evaluate` without first passing through `formula/validation.js`'s exhaustive-result check. This would need to be validated interactively against the actual `nearley`-compiled `oscript` grammar (`formula/grammars/oscript.js`) and the call sites in `aa_composer.js`, which was not completed within the available investigation budget.
