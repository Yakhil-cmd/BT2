### Title
Unbounded memory allocation via crafted private payment chains message — ([File: wallet.js])

### Summary
`handlePrivatePaymentChains()` in `wallet.js` accepts a `body.chains` array from any paired device (relayed via the hub) and only checks that it is non-empty and that each element has the right *shape* — it never bounds the number of chains, the length of each chain, or the size of the `inputs`/`outputs` arrays inside each chain element, unlike the equivalent checks that exist for ordinary units.

### Finding Description
`handlePrivatePaymentChains(ws, body, from_address, callbacks)` validates `arrChains = body.chains` with: [1](#0-0) 
This only requires `arrChains` and each `c` to be non-empty arrays/objects with a few string/array fields present — there is no cap on:
- the number of chains in `arrChains`,
- the number of elements in each chain `c`,
- the number of `inputs`/`outputs` per element.

Compare this to ordinary unit validation, which enforces hard limits before doing any heavy work: `isTooDeeplyNestedOrHasTooManyNodes` (depth ≤100, nodes ≤10000) and `MAX_MESSAGES_PER_UNIT` / `MAX_UNIT_LENGTH`: [2](#0-1) [3](#0-2) 

No such bound exists for `body.chains` before it is hashed, cached, and persisted: [4](#0-3) 
`objectHash.getBase64Hash(arrChains)` walks the entire attacker-supplied structure, and for every chain, `network.handleOnlinePrivatePayment` is invoked, which — for light clients or unresolved chains — serializes the entire (attacker-controlled, unbounded) chain back to JSON and stores it in the database: [5](#0-4) 

Because this pathway is reached directly from a device-to-device (hub-relayed) `private_payment` message before any of the unit-level size/depth guards apply, a single paired device (or a device impersonated through a compromised/malicious hub relay of a legitimate device's message channel) can submit a message with an enormous number of chains, extremely long chains, or huge `inputs`/`outputs` arrays per element, forcing the receiving wallet to allocate large amounts of memory for hashing, cloning (`_.cloneDeep` calls further down the validation pipeline in `indivisible_asset.js`/`divisible_asset.js`), and `JSON.stringify`/`JSON.parse` round-trips — all before any per-element validation (e.g., `isValidBase64`, hash-length checks) can reject the bulk of the payload.

### Impact Explanation
This matches the reported bug class: a normally-reachable, authenticated-but-untrusted-content endpoint (a wallet handling messages from a paired device or via the hub) performs allocation-heavy operations (hashing, deep cloning, JSON serialization) whose cost scales with attacker-controlled structure size that is not bounded prior to processing, potentially exhausting memory/CPU of the receiving wallet process and causing a Denial of Service to that node. It does not directly enable spending, but it is a resource-exhaustion vector that falls in the "wallet and contract message handling" scope explicitly allowed by the rules.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the ability to send a `private_payment_chains`-style message to a wallet, which is available to any device paired with the victim (or to a hub that can relay/forge such traffic on behalf of a paired device), i.e., a fairly low-privilege actor within the intended reachable-actor set (paired device / private-payment counterparty). No cryptographic bypass or race condition is needed — a single oversized message suffices.

### Recommendation
Add explicit size limits (analogous to `MAX_MESSAGES_PER_UNIT`, `isTooDeeplyNestedOrHasTooManyNodes`) in `handlePrivatePaymentChains` before any hashing/cloning/serialization work is performed: cap the number of chains, cap chain length, and cap `inputs`/`outputs` array sizes per element, rejecting oversized payloads immediately.

### Proof of Concept
A malicious/compromised paired device (or hub acting as relay) sends a `private_payment_chains`-style hub message with `body.chains` containing, e.g., tens of thousands of chain arrays, each with a large `inputs`/`outputs` array of syntactically valid-looking objects (satisfying `isNonemptyObject`, `isNonemptyString(e.unit)`, etc., but not yet hash/length validated). `handlePrivatePaymentChains` will compute `objectHash.getBase64Hash(arrChains)` over the whole structure and, for unresolved/queued chains, `JSON.stringify` the entire oversized array into the `unhandled_private_payments` table, consuming excessive memory/CPU on the receiving wallet before any per-field validation can discard the bulk of the data.

```javascript
function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
```
