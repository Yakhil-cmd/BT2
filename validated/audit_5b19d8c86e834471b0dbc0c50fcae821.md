### Title
Unbounded disk writes during `gh skills install` allow disk-exhaustion DoS from a malicious skill repository - (File: internal/skills/installer/installer.go)

### Summary
`gh` can install "agent skills" from any GitHub repository specified by the user (`gh skills install owner/repo ...`). The install path fetches every file listed for the skill's git tree and writes its raw content to disk with no per-file or total size limit, unlike the sibling `gh skills preview` command, which explicitly caps bytes fetched.

### Finding Description
`installSkill` in `internal/skills/installer/installer.go` lists all blobs under a skill's tree via `discovery.DiscoverSkillFiles`, then for every file calls `discovery.FetchBlob` and writes the decoded content verbatim to disk with `os.WriteFile`: [1](#0-0) 

There is no check on individual blob size or cumulative bytes written before or during this loop. By contrast, the `gh skills preview` command explicitly enforces a byte cap when rendering skill file contents, stopping further fetches once a size limit is reached ("size limit reached"): [2](#0-1) 

This shows the codebase is aware that skill repositories are attacker-controlled/untrusted content and that unbounded fetch/render needs a defensive cap — but that cap was only applied to the preview path, not the install path that actually writes bytes to the user's or CI runner's filesystem. Since the tree/blob content is entirely attacker-controlled (an untrusted third-party skill repository the user is instructed to install from, e.g. as suggested by `gh skills install owner/repo`), an attacker can publish a repository with one or many very large blobs (each up to GitHub's blob size limits, and repeated across many files/skills) to make `installSkill`/`Install` (`internal/skills/installer/installer.go:56-142`) consume arbitrary amounts of disk space on the victim machine or CI runner during a single `gh skills install --all` invocation.

### Impact Explanation
Unbounded writes driven entirely by attacker-supplied repository content can exhaust disk space on the invoking machine, which for CI runners or shared environments can produce a denial-of-service condition (failed subsequent jobs, inability to write further files, host instability) — directly analogous to the storage-exhaustion DoS pattern in the reference report, except triggered per-install rather than per-transaction. Root cause and impact are demonstrated by code (missing size guard) rather than confirmed by an actual disk-exhaustion PoC run.

### Likelihood Explanation
Likelihood is moderate: it requires a user (or automation) to run `gh skills install` against a repository they do not fully trust, which the tool's UX explicitly supports and encourages (`gh skills install owner/repo`, `--all` flag installs every discovered skill in one command). No privileged access or MITM is needed — a public attacker-controlled repository is sufficient.

### Recommendation
Apply the same defensive byte-size cap used in `pkg/cmd/skills/preview/preview.go` to the install path in `internal/skills/installer/installer.go`: enforce a maximum per-file size and a maximum cumulative size across all fetched files in `installSkill`, aborting the install with a clear error when limits are exceeded, before any bytes are written via `os.WriteFile`.

### Proof of Concept
1. Publish a public GitHub repository containing a `SKILL.md` (with valid frontmatter) plus one or more additional files that are extremely large blobs (e.g., near GitHub's file size limits, repeated across many files/skills in the repo).
2. Victim runs `gh skills install attacker/repo --all` (or targets a specific skill).
3. `installSkill` (`internal/skills/installer/installer.go:251-309`) fetches and writes every listed blob with no size cap, unlike `gh skills preview`, consuming large amounts of disk on the victim's machine/runner. [3](#0-2) [4](#0-3)

func installSkill(opts *Options, skill discovery.Skill, baseDir string) error {
	// Use skill.Name (not InstallName) for a flat directory layout.
	skillDir := filepath.Join(baseDir, skill.Name)
	if err := os.MkdirAll(skillDir, 0o755); err != nil {
		return fmt.Errorf("could not create directory %s: %w", skillDir, err)
	}

	files, err := discovery.DiscoverSkillFiles(opts.Client, opts.Host, opts.Owner, opts.Repo, skill.TreeSHA, skill.Path)
	if err != nil {
		return fmt.Errorf("could not list skill files: %w", err)
	}

	safeSkillDir, err := safepaths.ParseAbsolute(skillDir)
	if err != nil {
		return fmt.Errorf("could not resolve skill directory path: %w", err)
	}

	for _, file := range files {
		fetchedContent, err := discovery.FetchBlob(opts.Client, opts.Host, opts.Owner, opts.Repo, file.SHA)
		if err != nil {
			return fmt.Errorf("could not fetch %s: %w", file.Path, err)
		}

		// Install path: the blob is written to disk verbatim, so the raw bytes
		// must be preserved.
		content := fetchedContent.Raw()

		relPath := strings.TrimPrefix(file.Path, skill.Path+"/")

		safeDest, err := safeSkillDir.Join(relPath)
		if err != nil {
			var traversalErr safepaths.PathTraversalError
			if errors.As(err, &traversalErr) {
				return fmt.Errorf("blocked path traversal in %q", relPath)
			}
			return fmt.Errorf("could not resolve destination path: %w", err)
		}
		destPath := safeDest.String()

		if dir := filepath.Dir(destPath); dir != skillDir {
			if err := os.MkdirAll(dir, 0o755); err != nil {
				return fmt.Errorf("could not create directory: %w", err)
			}
		}

		if filepath.Base(relPath) == "SKILL.md" {
			content, err = frontmatter.InjectGitHubMetadata(content, opts.Host, opts.Owner, opts.Repo, opts.Ref, skill.TreeSHA, opts.PinnedRef, skill.Path)
			if err != nil {
				return fmt.Errorf("could not inject metadata: %w", err)
			}
		}

		if err := os.WriteFile(destPath, []byte(content), 0o644); err != nil {
			return fmt.Errorf("could not write %s: %w", destPath, err)
		}
	}

	return nil
}
