## Title
Webhook signature verification selects the signing organization from the same attacker‑controlled payload used to pick the target repository, allowing cross‑organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` chooses which GitHub App/webhook secret to verify a webhook against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted JSON body it is about to verify. Every `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the `Repository`/`Stack` it will actually mutate from a *different* field of that same body: `repository.full_name`. Nothing ties these two fields together, so on a multi‑organization Shipit install, anyone who legitimately knows (or obtains) the webhook secret for **one** onboarded GitHub organization can forge a signed payload whose `repository.full_name` names a repository belonging to a **different** onboarded organization, and the forged event will be processed against that other organization's stacks.

### Finding Description
`verify_signature` picks the `GitHubApp`/secret using a field taken from the very payload being authenticated: [1](#0-0) [2](#0-1) 

Every handler, independently, derives the repository it will act on from `repository.full_name` in the same payload: [3](#0-2) 

and resolves it via `Repository.from_github_repo_name`, which splits `owner/name` straight out of that string with no relation to the org used for signature verification: [4](#0-3) 

Because Shipit supports multiple GitHub organizations, each with its own `webhook_secret` (as documented and fixtured): [5](#0-4) [6](#0-5) 

an attacker who is a legitimate (or compromised) member of Org A can craft a JSON body with `repository.owner.login = "org-a"` and `repository.full_name = "org-b/victim-repo"`, sign it with Org A's real webhook secret, and post it to `/webhooks`. `verify_signature` will succeed because it only checks the HMAC against Org A's secret (which the attacker legitimately possesses), while the handler that runs afterward acts on Org B's repository/stack — an equality binding (`organization authenticated == organization of the repository written`) that is never enforced.

The concrete write path is `PushHandler`, which syncs a victim stack from an attacker‑forged `after` SHA once the (irrelevant) signature check passes: [7](#0-6) 

The same `stacks`/`repository_name` pattern is shared by `StatusHandler`, `CheckSuiteHandler`, and every `PullRequest::*Handler` (open/close/reopen/label/unlabel), all of which resolve their target `Repository`/`Stack` the same way: [8](#0-7) 

### Impact Explanation
This breaks the repository‑write boundary the webhook signature is supposed to enforce: an attacker only needs valid webhook credentials for *any one* organization configured on the shared Shipit instance to forge events (fake pushes, fake commit statuses/check runs, pull‑request open/close/label actions, review‑stack provisioning/archival) against stacks belonging to *any other* onboarded organization. Forged `status`/`check_suite` events are particularly severe because commit deployability gating (`ci.require`/blocking statuses) relies on `Status`/check‑run records created from these webhooks, so an attacker can manufacture "green CI" on a victim repository's commit and thereby influence/unblock an unauthorized deploy of that victim's stack — a cross‑repository/cross‑organization write and a precursor to an unauthorized deploy, matching the Critical‑tier impact category (cross‑repository writes / unauthorized deploy).

### Likelihood Explanation
This requires a Shipit deployment onboarding more than one GitHub organization (a documented, supported configuration) and requires the attacker to hold valid webhook credentials for at least one of those organizations — e.g., as a member/admin of a lower‑trust org sharing the instance, or via leak/compromise of that org's webhook secret. This is a realistic multi‑tenant configuration and does not require any Shipit session, API token, or GitHub App private key — only knowledge of one organization's `webhook_secret`, which is explicitly the credential the endpoint is designed to accept from that organization's own GitHub App.

### Recommendation
After parsing the payload, verify that the organization used to select the signing secret (`repository.owner.login` / `organization.login`) matches the owner portion of `repository.full_name` (and any other repository identifiers the handler will use) before dispatching to handlers; reject the request (422) on mismatch.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker, a legitimate holder of `org-a`'s webhook secret, builds a `push` payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a's webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` returns `"org-a"`, `verify_signature` succeeds using `org-a`'s secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on `org-b`'s stack, even though the signature never proved anything about `org-b`.
