### Title
CCMenu API Token Stack-Scope Bypass Grants Cross-Stack Deploy State Disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's stack-resolution method with an unscoped lookup, breaking the binding between the stack an `ApiClient` token is authorized for and the stack whose data is actually served. A token that is deliberately scoped to a single stack (as created by `CCMenuUrlController`) can be replayed against any other stack ID to read that stack's deploy/task state.

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through the `stacks`/`stack` helpers: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This means that when an `ApiClient` record has `stack_id` set (i.e., it was minted for exactly one stack), any controller relying on this `stack` helper is confined to that stack, regardless of what `stack_id` is passed in the request params.

`Shipit::Api::CCMenuController`, however, defines its own `stack` method that bypasses this scoping entirely: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(operation, scope)`, which merely checks that the `"read:stack"` string is present in the client's `permissions` array — it never re-validates that the requested `stack_id` matches the client's `stack_id`: [3](#0-2) 

The equality that should hold is: `stack the token authorizes == stack the controller resolves and serves`. Because `CCMenuController#stack` uses `Stack.from_param!` instead of the scoped `stacks.from_param!`, this equality is broken — the token authorizes stack A, but the controller will happily serve stack B if `params[:stack_id]` is changed.

This is compounded by how these tokens are minted and distributed. `CCMenuUrlController` creates (or reuses) a permanently-scoped, narrowly-permissioned `ApiClient` and embeds its raw authentication token directly in a URL query parameter meant for external CI-status aggregators: [4](#0-3) 

```ruby
def fetch
  uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
  uri.query = { 'token' => client.authentication_token }.to_query
  render(json: { ccmenu_url: uri.to_s })
end

def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

Anyone holding this CCMenu URL (deliberately designed for unauthenticated dashboard polling — `authenticate_api_client` here reads the token from a query param, not `Authorization: Basic`) can swap the `stack_id` segment in the path to any other stack the Shipit instance manages and retrieve that stack's deploy status.

### Impact Explanation
This qualifies as High severity: "unauthenticated read of stack state" — the CCMenu token, by design, does not require an authenticated Shipit session or basic-auth header to use (it's a bare query-string token meant for polling by external CI dashboards), yet it can be leveraged to read the deploy/task status (`deploys_and_rollbacks.last`, running state, timestamps) of *every* stack in the installation, not just the one it was minted for.

### Likelihood Explanation
Any holder of a single, legitimately obtained CCMenu URL (e.g., pasted into a chat channel, CI dashboard config, or leaked via referrer/logs, which is the expected distribution path for this feature) can trivially enumerate other stacks by changing the `stack_id` path segment and reusing the same token — no privilege escalation, credential theft, or additional access is required beyond what the feature already exposes.

### Recommendation
Have `Shipit::Api::CCMenuController#stack` reuse the scoped `stacks.from_param!(params[:stack_id])` helper from `BaseController` (i.e., remove the local override, or explicitly intersect with `current_api_client.stack_id` when present) so that the resolved stack is always the one the token's `stack_id` restricts it to.

### Proof of Concept
1. As a legitimate Shipit user, visit a stack and trigger `GET /stacks/:owner/:repo/:env/ccmenu_url`, obtaining a URL such as `https://shipit.example.com/api/stacks/1/ccmenu.xml?token=<TOKEN>` where the underlying `ApiClient` has `stack_id = 1` and `permissions = ["read:stack"]`.
2. Take that `TOKEN` and request `https://shipit.example.com/api/stacks/2/ccmenu.xml?token=<TOKEN>` (a different, unrelated stack ID).
3. Because `CCMenuController#stack` calls unscoped `Stack.from_param!(params[:stack_id])` instead of the token-scoped `stacks.from_param!`, and `check_permissions!` only checks the `"read:stack"` permission string (not the stack binding), the request succeeds and returns stack 2's deploy status XML, even though the token was only ever authorized for stack 1.
