This confirms the vulnerability. The `Handler` base class provides a `stacks` helper that properly scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, but `StatusHandler#process` bypasses this scoping entirely and queries `Commit.where(sha: params.sha)` directly across the whole `commits` table, with no repository filter. [1](#0-0) [2](#0-1) 

The uniqueness constraint on `commits` is `(sha, stack_id)`, not a global unique constraint on `sha` alone, so the same SHA can legitimately exist as a `Commit` row belonging to different stacks (e.g., shared upstream history between forks/mirrors tracked as separate Shipit stacks). [3](#0-2) 

`WebhooksController#verify_signature` only checks the HMAC signature against the GitHub App keyed by `repository_owner` derived from the attacker-controlled JSON payload's `repository.owner.login`/`organization.login` field — it does not cross-check that the SHA in a `status` event actually belongs to a commit under that same repository's stacks. [4](#0-3)  Since an attacker can register/own a GitHub repository, they can generate a validly-signed `status` webhook (signed with their own repo's webhook secret via `Shipit.github(organization: repository_owner)`) referencing a SHA that also exists as a `Commit` in a victim's stack, and `StatusHandler#process` will iterate all matching `Commit` rows and call `create_status_from_github!` on each of them, regardless of which repository authenticated the request.

`create_status_from_github!` → `add_status` triggers `stack.schedule_merges if new_status.pending? || new_status.success?` [5](#0-4) , which is the mechanism that drives the merge queue forward on a stack with `merge_queue_enabled` true, and also affects `deployable?`/`blocked?` evaluation used elsewhere. [6](#0-5) 

### Title
Cross-repository `status` webhook forges `ci/integration` state via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table instead of scoping to the repository that authenticated the webhook, unlike the base `Handler#stacks` helper which correctly scopes by `repository_name`. Because the `commits` table is only unique on `(sha, stack_id)` and not globally on `sha`, an attacker who owns any GitHub repository sharing a SHA with a victim's stack can send a signed `status` webhook from their own repo and have it applied to the victim's `Commit`, flipping its status/CI state and triggering `stack.schedule_merges` on a `merge_queue_enabled` stack.

### Finding Description
The broken binding: the code assumes `Commit.where(sha: params.sha)` == "commits belonging to the repository that authenticated this webhook," but in reality it equals "all commits in the database with this SHA, across any stack/repository." [1](#0-0) 

Path: `POST /webhooks` → `WebhooksController#create` → signature verified against `Shipit.github(organization: repository_owner)` (using the attacker's own repository's owner, which passes because the attacker legitimately owns/controls that repo) → `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` → `StatusHandler.call(params)` → `new(params).process`. `process` never consults `payload.dig('repository', 'full_name')` or the `stacks`/`Repository.from_github_repo_name` scoping used by every other handler (e.g., `PushHandler`, `PullRequest::*Handler`), and instead does a bare `Commit.where(sha: params.sha)`. [2](#0-1) 

Exploit flow: attacker owns repo `attacker/repo` registered with a legitimate GitHub webhook secret for that org/owner. Victim stack tracks `victim/repo` with `merge_queue_enabled: true` and requires `ci/integration` as a status check. If a `Commit` row with SHA `X` exists in the victim's stack (e.g., a widely-known/shared commit, a rebased/cherry-picked commit that happens to coincide, or more practically any scenario where two Shipit-tracked stacks reference overlapping git history producing identical SHAs), the attacker sends a validly-signed `status` event from `attacker/repo` with `sha: X`, `context: ci/integration`, `state: success`. `StatusHandler` finds the victim's `Commit` by that bare SHA and calls `create_status_from_github!`, which appends a `success` status, changes `new_status.success?` to true, and calls `stack.schedule_merges`, advancing the victim's merge queue and potentially causing `merge!`/deploy to fire on attacker-uncontrolled but attacker-triggered code. [7](#0-6) [8](#0-7) 

Existing guards fail to catch this: `verify_signature` authenticates only that the payload was signed by *some* registered GitHub organization/repo owner — it has no concept of "this status event must only affect commits under this same repository." `drop_unhandled_event` and `ExplicitParameters` schema (`requires :sha`, `accepts :context`) validate shape, not ownership. There is no `Repository`/`stacks` scoping check inside `StatusHandler#process` at all, unlike `Handler#stacks`.

### Impact Explanation
A payload authenticated for one repository (`attacker/repo`) mutates commit/status state belonging to a different, unrelated stack (`victim/repo`'s `Commit`), matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." On a `merge_queue_enabled` stack, this can directly trigger `stack.schedule_merges`/`merge!`, i.e., an unauthorized merge/ship decision, matching "unauthorized deploy, rollback or merge." The blast radius spans any two stacks/repositories whose commit histories intersect on at least one SHA (forks, mirrors, template repos, monorepo splits, or repos that happen to share initial/common ancestor commits) — this is repeatable per-SHA and per-victim-stack.

### Likelihood Explanation
Preconditions: (1) the victim stack must have a `Commit` row whose SHA the attacker also knows/controls a repo that can emit a signed webhook for, and (2) `merge_queue_enabled: true` amplifies the effect but is not strictly required for the write to happen (status/deployability change occurs regardless). The attacker only needs to own or push to any GitHub repo (free, unprivileged) and know a target SHA present in a victim's Shipit-tracked stack, which is discoverable via Shipit's own UI/API for public stacks or through common ancestor commits between forks. Cost is low and the attack is fully repeatable against any stack.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring `Handler#stacks`: filter `Commit.where(sha: params.sha, stack: stacks)` (or join through `stack_id in stacks.select(:id)`) instead of a bare SHA lookup, ensuring a `status` event can only affect commits belonging to stacks of the repository named in `payload['repository']['full_name']`.
