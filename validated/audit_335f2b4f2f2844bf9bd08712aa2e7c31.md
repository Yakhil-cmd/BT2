### Title
Unhandled invariant-violation `throw` in AA author validation crashes the full node process - ([File: validation.js])

### Summary
`cometbft`'s fix addressed a `panic` that fired when an internal invariant ("there is always at least one lane") was violated, turning a should-never-happen condition into a process crash. `ocore` contains an structurally identical pattern in `validateAuthor()`: when validating an author of an AA-generated response unit, the code assumes an AA definition must always be resolvable and `throw`s a bare `Error` if it isn't, with no error-callback path.

### Finding Description
In `validateAuthor()`, for the AA-response-validation branch (`objValidationState.bAA`), the code does:

```js
if (objValidationState.bAA) {
    storage.readAADefinition(conn, objAuthor.address, objValidationState.aa_mci, function (arrDefinition) {
        if (!arrDefinition)
            throw Error("AA definition not found " + objAuthor.address);
        checkSerialAddressUse();
    });
    return;
}
``` [1](#0-0) 

This is invoked from `aa_composer.js`'s `validateAndSaveUnit()`, which runs `validation.validate()` on every AA response unit produced while executing a trigger, with `ifJointError`/`ifTransientError` handlers themselves converted into hard `throw Error(...)` calls rather than being surfaced as recoverable errors: [2](#0-1) 

The invariant being assumed — "the AA that is about to author its own response unit must have a resolvable definition at `aa_mci`" — mirrors exactly the CometBFT assumption "there is always at least one lane." Both are un-defensive invariant checks placed on a hot path that is exercised on every unit/transaction that reaches it (every AA trigger in ocore's case), and both `throw`/`panic` instead of returning a typed, recoverable error.

Because this executes inside an asynchronous DB callback (`conn.query(...)`), any `throw` here is not caught by the calling `async.series`/`try/catch` chains; it propagates as an uncaught exception. `network.js` explicitly re-throws uncaught exceptions to crash the process by design:
```js
process.on('uncaughtException', (err) => {
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [3](#0-2) 

So any code path that manages to violate the "AA definition always found" assumption turns into a full-node crash, not merely a rejected unit.

### Impact Explanation
AA trigger execution is deterministic and mandatory: every full node that advances the main chain must execute AA triggers identically in order to reach consensus on state and outputs. If a single crafted unit can drive execution into the `throw Error("AA definition not found ...")` branch (e.g., via a race between AA (re)definition visibility and the `aa_mci` snapshot used for validating the freshly composed response author, or via `base_aa` redirection paths that change which address's definition is checked), every full node processing that trigger would independently crash at the same point. This is a network-wide denial of confirmation: the network becomes unable to process new units past that point, since AA execution is required for the writer to finalize the trigger and any subsequent units depending on that processing, until nodes are restarted — a Medium/High-severity availability issue for a permissionless system where any user can send an AA trigger.

### Likelihood Explanation
This throw sits deep inside the AA response-generation/validation pipeline that runs on every accepted AA trigger unit, which any unprivileged user (unit poster or asset issuer sending funds to an AA address) can create. Reaching the specific violated-invariant state requires a narrow edge case (e.g., timing/`base_aa` redirection or definitions becoming visible/invisible relative to the `aa_mci` snapshot used), so likelihood of triggering by accident is low, but the risk class matches the reported bug exactly: an assumed-always-true invariant guarded only by a `throw`, with no graceful degradation, on a mandatory consensus-critical execution path.

### Recommendation
Replace the `throw Error(...)` in the `bAA` branch of `validateAuthor()` with a proper error propagated through `callback(err)` (or the AA validation callback contract), so the caller (`aa_composer.js`'s `validateAndSaveUnit`) can bounce/log the trigger instead of crashing the process. Additionally, review `aa_composer.js`'s `ifJointError`/`ifTransientError`/`ifNeedHashTree`/`ifNeedParentUnits` handlers in `validateAndSaveUnit`, which likewise convert recoverable validation outcomes into hard `throw Error(...)` calls, and make them return controlled bounce/revert paths instead of crashing.

### Proof of Concept
Concrete exploitation requires demonstrating an execution path where `storage.readAADefinition(conn, objAuthor.address, objValidationState.aa_mci, ...)` returns `null` for an address that is legitimately about to author an AA response (e.g. via `base_aa` parameterized-AA redirection combined with a specific `aa_mci`/registration-mci relationship, or a data race between concurrent AA registration and secondary-trigger dispatch in `handleSecondaryTriggers`). I was not able to fully verify a concrete reachable input sequence within the available exploration — this would require deeper analysis of `storage.readAADefinition`'s `mci<=?` query semantics against `aa_composer.js`'s `handleTrigger`/`handleSecondaryTriggers` mci bookkeeping (including the `base_aa` redirect at aa_composer.js:436-444) to confirm feasibility. The structural risk (uncaught `throw` in a should-never-happen check inside a consensus-critical, unprivileged-attacker-reachable code path) is confirmed by the cited code.
