### Title
Unconstrained strategy routes can execute attacker-controlled transfers under the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

Controller strategy entrypoints accept opaque router payload bytes and invoke an external router while the account owner or delegate’s authorization is active. Because the controller only constrains its own exact input transfer and measured output, a crafted route can execute arbitrary third-party contract code beneath the caller’s authorization tree. If simulation records an unauthorized wallet transfer and the caller signs the poisoned tree, route-selected code can steal unrelated tokens from the caller’s wallet.

### Finding Description

`swap_tokens` authorizes exactly one `token_in.transfer(controller, router, amount_in)` invocation using the controller’s authority, then calls the configured router with caller-provided `StrategySwap` bytes. It later checks only the controller’s `token_in` and `token_out` balance deltas, imposing no allowlist or restriction on contracts reached inside the route. [1](#0-0) 

`swap_collateral` is a representative reachable path: an account owner or delegate supplies `swap: Bytes`, the controller withdraws collateral, invokes the router, and redeposits only the measured output. The same router helper is used by `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [2](#0-1) 

The vulnerability is analogous to Copier’s symlink escape: a seemingly scoped operation is allowed to resolve attacker-controlled intermediate objects, and a generated/signed request can therefore affect resources outside the intended destination.

### Impact Explanation

An attacker can craft a swap route whose hop contract performs `token.transfer(victim, attacker, amount)` on an unrelated wallet token. Under Soroban authorization recording, that nested transfer can appear beneath the victim’s controller authorization entry; if the victim signs the returned authorization tree, the rogue transfer executes. The loss is not limited to the collateral being swapped and can include arbitrary unrelated tokens held by the victim.

The repository’s own authorization-tree test demonstrates this behavior: simulation records a malicious `wallet_token.transfer(alice, attacker, balance)` beneath `swap_collateral`, and enforcing mode succeeds when that poisoned tree is signed. [3](#0-2) [4](#0-3) 

### Likelihood Explanation

The attacker needs the victim to submit a malicious route and sign the simulation-produced authorization tree. That requires social engineering or a compromised/malicious route-generation path, but no privileged role, leaked key, or contract upgrade is needed. Since routes are intentionally opaque controller arguments, ordinary callers must inspect the full authorization tree to notice unrelated token transfers.

### Recommendation

Constrain strategy execution to an allowlisted route structure and venue set, or require the router payload to expose every external contract that can execute and enforce that list before invocation. At minimum, reject routes that produce any authorization child other than the single expected `token_in.transfer(controller, router, amount_in)` under the controller grant, and make clients/simulation reject any additional child transfers under the caller’s root authorization.

### Proof of Concept

1. Victim owns a funded lending account and holds an unrelated token in their wallet.
2. Attacker deploys a route hop contract whose `swap` function calls `token::Client::transfer(victim, attacker, wallet_balance)`.
3. Victim calls `swap_collateral(caller=victim, account_id=victim_account, current=USDC, amount=X, new=ETH, swap=malicious_route)`.
4. The controller authenticates the victim and verifies account ownership or delegation, withdraws the current collateral, and calls `swap_tokens`. [5](#0-4) 
5. The router executes the malicious route hop. That hop issues the unrelated wallet-token transfer beneath the still-active victim authorization.
6. Simulation records the transfer as a child of the victim’s `swap_collateral` authorization. If the victim signs that returned tree, the unrelated tokens move to the attacker while the controller’s measured swap output still satisfies its checks.

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
