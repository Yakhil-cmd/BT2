## Title
AMM "virtual price" (share ratio) in the market-maker AA template is manipulable via un-tracked balance donations — ([File: test/samples/uniswap_like_market_maker.oscript])

## Summary
The reported issue describes a `virtualPrice`/invariant that is supposed to be monotonic but can be skewed by manipulating a component of the price formula. The closest reachable analog in this repository is the Uniswap-like market-maker Autonomous Agent (AA) template shipped with ocore, which computes its share price (`$current_ratio`, `$investor_share`) and constant-product invariant purely from the AA's live on-chain `balance[...]`, while tracking outstanding shares in a separate state var `var['mm_asset_outstanding']`. Any trigger sender can add funds to the AA's balance without matching a defined `case`, so the balance used in the price formula can be inflated independently of the tracked share supply, exactly mirroring the reported bug class of an invariant/price value being manipulable through an out-of-band input.

## Finding Description
The AA computes deposit and withdrawal amounts from the *live* balance of the contract rather than from an internally accounted, invariant-protected value: [1](#0-0) 

The initial-deposit branch mints shares equal to the entire current base-byte balance with no floor and no relation to the deposited asset amount: [2](#0-1) 

Subsequent deposits and withdrawals derive the price purely from `balance[$asset]` / `balance[base]` compared against `var['mm_asset_outstanding']`: [3](#0-2) 

Because the `messages.cases` array only matches specific triggers — `define`, `invest` (`base>1e5 AND asset>0`), `divest` (`mm_asset` output present), `exchange bytes→asset` (`base>1e5 AND asset==0`), `exchange asset→bytes` (`asset>0`) — a payment to the AA address that satisfies none of these conditions (e.g., `base ≤ 1e5` and zero of `$asset`/`$mm_asset`) does not match any case: [4](#0-3) 

An AA that receives a unit whose outputs don't satisfy any `if` condition does not bounce; the transferred coins are simply added to the AA's address balance with no state update executed. That balance is exactly what `balance[base]` / `balance[$asset]` reads on the next trigger, so an attacker can inflate the "virtual price" inputs (the token balances backing `mm_asset_outstanding`) without any corresponding change to the outstanding-share accounting that the price/ratio checks are supposed to protect.

## Impact Explanation
This lets an unprivileged AA trigger sender:
- Become the first depositor with a minimal amount, minting shares proportional only to `balance[base]` (line 39), then donate additional un-tracked funds to skew `$current_ratio` / `$p = asset_balance * bytes_balance` for later investors and swappers (lines 42–47, 108, 130).
- Cause later "invest" triggers to be bounced (wrong-ratio check, line 44–45) or to receive a disproportionate `$issue_amount` (line 47) relative to real economic value, diluting or inflating other participants' share of `var['mm_asset_outstanding']`.
- Extract value from existing `mm_asset` holders when they `divest`, since `$investor_share = trigger.output[[asset=$mm_asset]] / var['mm_asset_outstanding']` is multiplied against a `balance[...]` that includes attacker-donated, unaccounted funds (lines 71–99).

This is a concrete AA-fund-loss / unfair-pricing vector for anyone who deposits into or trades against this AA pattern — directly analogous to the reported `virtualPrice` manipulation, where a price/invariant meant to move monotonically with legitimate flows can instead be skewed by an out-of-band input.

## Likelihood Explanation
Any address can post a unit paying the AA an amount that fails to satisfy every `if` condition (e.g., small `base` amount with none of `$asset`/`$mm_asset`), which is trivial and requires no privileges, no cooperation from the AA definer, and only ordinary unit-posting capability.

## Recommendation
Track pool reserves in dedicated state vars (e.g., `var['reserve_base']`, `var['reserve_' || $asset]`) that are updated exclusively by the AA's own state-update formulas, and compute `$current_ratio`, `$p`, and all share-price math from those tracked reserves instead of from the live `balance[...]` getter, so the invariant cannot be perturbed by payments that don't match any case. Additionally, enforce a minimum-liquidity/burn-on-first-deposit safeguard (as in standard AMM designs) so the first depositor cannot mint shares in a way that is exploitable by later, differently-sized deposits.

## Proof of Concept
1. Attacker deploys/uses the AA from `test/samples/uniswap_like_market_maker.oscript`.
2. Attacker sends `trigger.data.define` to create `mm_asset` (lines 8–32).
3. Attacker sends a unit with `trigger.output[[asset=base]] > 1e5` and `trigger.output[[asset=$asset]] = 1` to become the first depositor, receiving `$issue_amount = balance[base]` shares (lines 38–48, 62).
4. Attacker sends a follow-up unit paying the AA `trigger.output[[asset=base]] ≤ 1e5` and `0` of `$asset`/`$mm_asset` — this matches none of the `if` conditions in `messages.cases` (lines 8, 34, 70, 103, 125), so the payment silently increases `balance[base]` with no state update.
5. On the next legitimate "invest" or "divest" trigger, `$current_ratio` / `$investor_share` (lines 42, 73) are computed against the inflated `balance[base]`, causing the new depositor's expected-ratio check to fail or an existing `mm_asset` holder's divestment payout to be skewed relative to `var['mm_asset_outstanding']`, demonstrating that the AA's implicit "virtual price" is not protected against manipulation via un-tracked balance changes.
