### Title
Unbounded AA triggers accumulated in a single MCI can DOS unit stabilization and node writes - ([File: main_chain.js])

### Summary
When an MCI stabilizes, `handleAATriggers` in `main_chain.js` queries **all** units in that MCI with outputs to AA addresses and inserts one trigger row per distinct `(unit, address)` pair into `aa_triggers`, with no limit on the number of triggers generated for a single MCI. Immediately afterward, `aa_composer.handleAATriggers()` is invoked and processes every one of these triggers sequentially (`async.eachSeries`), each requiring a full AA evaluation, its own DB transaction, and a synchronous KV-store batch write, all while the node still holds the global `write` mutex acquired at the start of `saveJoint`.

### Finding Description
`markMcIndexStable`'s `handleAATriggers` sub-function [2](#0-1)  selects every `(unit, address)` pair where a unit in the newly stable MCI pays to an AA address, with no cap on the number of rows inserted into `aa_triggers`. This query is bounded only by how many distinct units/messages an attacker can pack into a single MCI and how many distinct AA addresses they send outputs to — a unit can have up to `constants.MAX_MESSAGES_PER_UNIT` payment messages, each with multiple outputs to different AA addresses, and an attacker can post many low-value units (all cheap, fee-bearing but inexpensive) within the same MCI window.

Once inserted, `stabilizeMci`/`saveJoint` immediately calls `aa_composer.handleAATriggers()` [3](#0-2) , which pulls every pending row from `aa_triggers` and processes them one at a time via `handlePrimaryAATrigger`, each doing a `BEGIN`/execute AA formula/`COMMIT` cycle plus a synchronous `batch.write({sync:true})` [5](#0-4) . Crucially, this call chain executes while the node is still holding the global `write` mutex acquired in `saveJoint` [1](#0-0) , and `writer.js` explicitly awaits `aa_composer.handleAATriggers()` before releasing that lock [4](#0-3) . Because the `write` lock also gates `validation.validate` for competing addresses via `mutex.lock(arrAuthorAddresses, ...)` and the overall unit-processing pipeline in `network.js`'s `handleJoint` acquires `handleJoint`/`write` locks in sequence, a sufficiently large trigger backlog can stall processing of all new incoming units for as long as it takes to drain the queue.

This is directly analogous to the `RootManager` bug: an attacker-controlled batch of items (roots vs. AA triggers) accumulated in one commit window (block vs. MCI) is later dequeued/processed in full by a single synchronous step (`propagate`/`dequeueVerified` vs. `handleAATriggers`) that has no batching or per-call bound, and that step blocks the critical path (root propagation to spokes vs. node's ability to accept/confirm further units) for everyone.

### Impact Explanation
If exploited, the node processing the stabilizing MCI would be stuck executing a large, attacker-controlled number of AA triggers sequentially, each with its own DB transaction and synchronous disk write, while holding the `write` lock that blocks all further unit validation and writing. This degrades to a "network unable to confirm new units" condition on the affected node(s) for the duration of the backlog, and because AA triggers stemming from a stabilized MCI are deterministic and required by protocol, all full nodes will independently hit the same processing storm when they stabilize that MCI, causing a broad availability disruption rather than an isolated one.

### Likelihood Explanation
Reachable by any unprivileged unit poster: constructing many units, each with payment outputs to AA addresses, and getting them included/stabilized within the same MCI, requires only paying normal bytes fees per unit (no special privilege or hub/peer trust needed). The cost is proportional to fees for many small units, which is a much lower bar than the smart-contract analog's gas cost, making this more of an economic/rate-limiting question, but the core code path has no explicit maximum number of AA triggers processed per MCI.

### Recommendation
Cap the number of AA triggers processed per MCI (or per stabilization step), and if the cap is exceeded, process the remainder in bounded batches across multiple event-loop turns/DB transactions instead of a single unbroken `async.eachSeries` while holding the global `write` lock. Consider releasing/re-acquiring the `write` lock between batches of trigger execution so that new unit validation is not starved during a large trigger backlog, mirroring the "bound the batch size and process in batches" mitigation used for `RootManager`.

### Proof of Concept
1. An attacker crafts and submits many units within a short time window, each unit containing payment messages with outputs to one or more existing AA addresses (varying either the AA address, the paying unit, or both) so that `handleAATriggers`'s `SELECT DISTINCT address, ..., units.unit, ...` in `main_chain.js` produces a very large row set for the MCI these units stabilize into.
2. When that MCI stabilizes, `INSERT INTO aa_triggers (...) VALUES ...` inserts one row per distinct `(unit, address)` pair with no cap [6](#0-5) .
3. `stabilizeMci`/`saveJoint` then calls `aa_composer.handleAATriggers()`, which loads and processes every row sequentially, each doing its own DB transaction and AA evaluation [7](#0-6) , all while still holding the global `write` lock acquired at the top of `saveJoint` [8](#0-7) .
4. During this processing window, all other incoming units competing for the same lock are queued and cannot be validated/written, effectively stalling the node's ability to confirm new units until the attacker-sized trigger backlog is drained.
