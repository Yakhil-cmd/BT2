### Title
Webhook signature verification selects the signing organization from unauthenticated payload fields, decoupling the authenticated org from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub organization's `webhook_secret` to validate a webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unauthenticated JSON body. Once verification passes (or is skipped because that particular organization has no `webhook_secret` configured), the very same body is handed to event handlers that independently resolve the target `Stack`/`Repository` from other body fields such as `repository.full_name` or `sha`. Nothing binds the two: the organization that "authenticated" the message is not cryptographically tied to the repository that ends up being written to.

### Finding Description
`verify_signature` derives the signing organization purely from body content and looks up a per-organization `GitHubApp`: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank: [3](#0-2) 

Shipit explicitly supports multiple independently configured organizations, each with its own optional `webhook_secret`, selected at runtime via `Shipit.github(organization:)`: [4](#0-3) 

The documentation and shipped example configs show `webhook_secret: # nil` as an accepted, unremarkable value per organization: [5](#0-4) [6](#0-5) 

Meanwhile, downstream handlers (push, status, etc.) locate the `Stack`/`Repository`/`Commit` they act on using *other* body fields (`repository.full_name`, `sha`), not the `repository.owner.login` value that was used to select the signing secret — confirmed by the test suite, which independently manipulates `repository.full_name` and `repository.owner.login` in the same payload: [7](#0-6) [8](#0-7) 

This reproduces the analog LayerZero pattern described in the report: the value that gates trust (the org whose secret is checked, analogous to the LayerZero source-chain check) is not the value the destination logic actually operates on (the repository/commit being written, analogous to the payload executed on the destination chain). The equality that should hold — `organization authenticated == organization owning the repository being written` — is not enforced; `organization authenticated` is chosen by the attacker's own JSON, and `repository written` is chosen independently by a different field of the same attacker JSON.

### Impact Explanation
If any organization configured on a Shipit instance has no `webhook_secret` set (a state the shipped docs/examples treat as normal), an unauthenticated actor can submit a webhook whose `repository.owner.login`/`organization.login` names that no-secret org (satisfying `verify_signature` unconditionally) while `repository.full_name` / `sha` in the same payload target a completely different, secret-protected repository/stack tracked by Shipit. This lets an external, credential-less attacker inject `status` events (`commit.statuses.create!`) or trigger `GithubSyncJob`/`RefreshCheckRunsJob` for stacks that have nothing to do with the "authenticating" organization. Because commit statuses influence Shipit's deployability/merge-queue gating, this can be used to forge a passing CI status on a commit belonging to an unrelated, protected repository, undermining the deploy-gating checks Shipit relies on for authorizing merges/deploys.

### Likelihood Explanation
Medium: it requires only one organization on the instance to be configured without a `webhook_secret` — a configuration explicitly presented as valid/default in the shipped docs and secrets examples — and requires no session, API token, or GitHub credential from the attacker; only knowledge of the target repository's `full_name`/`sha`, which is public information for public repos.

### Recommendation
Bind organization/repository identity cryptographically to the verified signature instead of trusting fields in the unauthenticated body to select the verification key: verify the signature using every configured secret (or the specific secret configured for the *stack's known* repository owner, resolved from Shipit's own `Repository`/`Stack` records) rather than trusting `repository.owner.login`/`organization.login` taken from the request body. Additionally, require a non-blank `webhook_secret` for every configured organization (reject configuration/requests when one is missing) so `verify_webhook_signature` can never unconditionally return `true`.

### Proof of Concept
1. Operator configures two organizations in `secrets.yml`: `OrgOne` (real, has a `webhook_secret`) and `OrgTwo` (test/staging org configured with `webhook_secret: nil`, as shown acceptable in `docs/setup.md`/`secrets_double_github_app.yml`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/protected-repo" },
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example"
}
```
3. `repository_owner` resolves to `"OrgTwo"`; `Shipit.github(organization: "OrgTwo")` is used; `verify_webhook_signature` returns `true` unconditionally because `OrgTwo`'s `webhook_secret` is blank — no valid `X-Hub-Signature` needed.
4. `StatusHandler` processes the event using `sha`/`repository.full_name` (`OrgOne/protected-repo`), creating a forged "success" status on a real commit under `OrgOne`, an organization the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
