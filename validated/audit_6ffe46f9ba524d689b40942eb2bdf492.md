### Title
Unchecked `IERC721.transferFrom()` Return in Bridge Allows Silent NFT Transfer Failure — (`File: contracts/service_chain/bridge/BridgeTransferERC721.sol`)

### Summary

`BridgeTransferERC721` calls `IERC721(_tokenAddress).transferFrom()` in both `requestERC721Transfer` and `handleERC721Transfer` without verifying that the transfer actually succeeded. Unlike the ERC20 bridge — which correctly uses OpenZeppelin's `SafeERC20` — the ERC721 bridge has no equivalent protection. If a registered ERC721 token's `transferFrom` silently fails (does not revert), the bridge permanently consumes a handle nonce and emits cross-chain events as if the transfer succeeded, while no actual token movement occurs.

### Finding Description

`BridgeTransferERC20` imports and uses `SafeERC20`:

```solidity
// BridgeTransferERC20.sol line 22-29
import "../../libs/openzeppelin-contracts-v2/contracts/token/ERC20/SafeERC20.sol";
...
contract BridgeTransferERC20 is BridgeTokens, IERC20BridgeReceiver, BridgeTransfer {
    using SafeERC20 for IERC20;
``` [1](#0-0) 

`BridgeTransferERC721` makes no such import and calls bare `transferFrom` in two places:

**Location 1 — `handleERC721Transfer` (destination-side release):**

```solidity
// line 49-70
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);          // nonce permanently consumed here

emit HandleValueTransfer(...);                // event emitted here

if (modeMintBurn) {
    require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(...), "mint failed");
} else {
    IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId); // no revert check
}
``` [2](#0-1) 

The nonce update (`_updateHandleNonce`) and event emission happen **before** the `transferFrom` call. If `transferFrom` silently fails, the bridge nonce is permanently consumed and the `HandleValueTransfer` event is emitted, but the recipient never receives the NFT. The bridge will not retry because the nonce is marked handled.

**Location 2 — `requestERC721Transfer` (source-side lock):**

```solidity
// line 129-130
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId); // no revert check
_requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
``` [3](#0-2) 

`_requestERC721Transfer` emits `RequestValueTransferEncoded` and increments `requestNonce` regardless of whether the bridge actually received the token:

```solidity
// line 93-105
emit RequestValueTransferEncoded(..., requestNonce, ...);
requestNonce++;
``` [4](#0-3) 

The off-chain bridge operator (`handleRequestValueTransferEvent` in `node/sc/bridge_manager.go`) observes the `RequestValueTransferEncoded` event and calls `handleERC721Transfer` on the counterpart bridge, which mints or releases an NFT to the user — even though the original NFT was never locked. [5](#0-4) 

### Impact Explanation

**Scenario A — `requestERC721Transfer` silent fail (unauthorized minting):**
A non-standard ERC721 token registered in the bridge whose `transferFrom` does not revert on failure allows any caller to initiate a cross-chain transfer without actually locking their NFT. The counterpart bridge mints or releases an NFT to the attacker. The attacker retains their original NFT and gains a free copy on the counterpart chain. This is an unauthorized mint of a bridged asset.

**Scenario B — `handleERC721Transfer` silent fail (permanent loss):**
A non-standard ERC721 token's `transferFrom` silently fails on the destination side. The bridge nonce is permanently consumed and `HandleValueTransfer` is emitted, but the recipient never receives the NFT. The source-chain NFT was already locked/burned. The user suffers a permanent, unrecoverable loss of their bridged asset with no retry path.

Both scenarios affect protected bridge asset ownership. Scenario A is the higher-severity path: it allows unauthorized creation of bridged NFTs.

### Likelihood Explanation

The trigger requires a registered ERC721 token whose `transferFrom` does not revert on failure. Token registration is controlled by bridge operators (`onlyRegisteredToken` modifier), which is a semi-trusted role. However:

- The bridge is designed to support arbitrary ERC721 tokens, and non-standard implementations are common in practice.
- `requestERC721Transfer` is `public` with no caller restriction — any user can call it once a token is registered.
- The ERC721 standard does not mandate that `transferFrom` reverts; it only requires the function to exist. Tokens that are paused, have custom access control, or have implementation bugs may silently succeed the call without moving the token.

The contrast with the ERC20 path — which is explicitly protected by `SafeERC20` — shows the developer was aware of this class of bug and addressed it for ERC20 but not ERC721.

### Recommendation

1. **For `requestERC721Transfer`**: After calling `transferFrom`, verify the bridge actually received the token:
   ```solidity
   IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
   require(IERC721(_tokenAddress).ownerOf(_tokenId) == address(this), "token not received");
   ```

2. **For `handleERC721Transfer`**: Use `safeTransferFrom` where the recipient is an EOA, or verify ownership after transfer:
   ```solidity
   IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
   ```
   Or verify post-transfer:
   ```solidity
   IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
   require(IERC721(_tokenAddress).ownerOf(_tokenId) == _to, "transfer failed");
   ```

3. Move the `_updateHandleNonce` and event emission **after** the transfer call in `handleERC721Transfer`, so that a failed transfer reverts the entire state change (consistent with the checks-effects-interactions pattern).

### Proof of Concept

Deploy a non-standard ERC721 token whose `transferFrom` does nothing (no revert, no state change):

```solidity
contract SilentERC721 is ERC721 {
    function transferFrom(address, address, uint256) public {
        // silently does nothing
    }
}
```

1. Bridge operator registers `SilentERC721` in the bridge.
2. Attacker calls `bridge.requestERC721Transfer(silentERC721Addr, attacker, tokenId, "")`.
3. `SilentERC721.transferFrom` executes silently — attacker still owns `tokenId`.
4. `_requestERC721Transfer` emits `RequestValueTransferEncoded` and increments `requestNonce`.
5. Off-chain operator calls `handleERC721Transfer` on the counterpart bridge.
6. Counterpart bridge mints `tokenId` to the attacker on the other chain.
7. Attacker holds the original NFT on chain A **and** a minted copy on chain B.

The corrupted state: `requestNonce` is incremented and a `RequestValueTransferEncoded` event is emitted for a transfer that never locked any asset, causing the counterpart bridge to release/mint an NFT backed by nothing. [6](#0-5) [7](#0-6) [8](#0-7)
