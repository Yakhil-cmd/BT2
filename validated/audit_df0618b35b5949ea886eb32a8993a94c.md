### Title
Unbounded synchronous recursion via nested `not` in address/asset-condition definitions causes stack overflow - ([File: definition.js])

### Summary
`definition.js`'s `validateDefinition()` inner `evaluate()` function recurses synchronously (not via `async.eachSeries`/`setImmediate`) for the `not` opcode: `case 'not': evaluate(args, path, true, cb); break;` [1](#0-0)  The equivalent `evaluate()` in `validateAuthentifiers()` has no explicit `not` handling shown but shares the same general pattern of direct synchronous recursion for nested definitions, e.g. the `address` case recursing directly into `evaluate(arrInnerAddressDefinition, path, cb2)` [2](#0-1) . Unlike the AA formula evaluator and AA definition validator, which explicitly interrupt the JS call stack every 100 calls via `setImmediate` [3](#0-2) [4](#0-3) [5](#0-4) , `definition.js`'s address-definition evaluators have no such stack-yielding mechanism. This mirrors the CVE-2020-8285 bug class: an attacker-controlled recursive structure that causes the interpreter to recurse on itself with only a "logical" limit (complexity/ops counters here, "skip" count in curl) but no actual JS call-stack depth guard.

### Finding Description
`validateDefinition()` is called from `validateAuthentifiers()`, which is invoked from `validateAuthor()` during ordinary unit validation for every author's address definition and from asset-definition/condition validation [6](#0-5) . Any unprivileged unit poster can supply an address definition (or an asset's spending-condition definition) containing deeply nested `not` operators, e.g. `['not', ['not', ['not', ... ['sig', {...}] ...]]]]`. Each `not` node consumes one `complexity` and one `count_ops` unit [7](#0-6)  but the recursive call to `evaluate()` for the nested `not` is a direct, synchronous JS function call that adds a new stack frame per nesting level — it is not deferred with `setImmediate` the way the sibling `or`/`and`/`r of set` branches are (those use `async.eachSeries`, which still recurses synchronously per iteration, but critically none of these paths ever yield the stack the way the AA formula evaluator does every 100 iterations).

Because `MAX_COMPLEXITY`/`MAX_OPS` are checked only after incrementing (i.e., the limit is a counter, not a JS-stack-depth throttle), an attacker can craft a definition whose nesting depth approaches those numeric limits. If the numeric limits (`MAX_COMPLEXITY`/`MAX_OPS`) are large enough — which they need to be to permit legitimate complex multisig/`r of set`/`weighted and` structures — the resulting synchronous recursion depth can exceed the Node.js V8 stack limit before the complexity counter check aborts, causing a `RangeError: Maximum call stack size exceeded` (uncaught in some call paths) and crashing the validating node process. This is reachable purely by posting a unit with a new address definition (author's own inline definition) or a private/public asset with a nested spending condition — no privileged access required.

### Impact Explanation
A crash of `validateDefinition`/`validateAuthentifiers` during unit validation halts processing of that validation call. If this throws an uncaught `RangeError` outside of the `cb`-based async error channel (as JS stack overflow errors typically are not caught by ordinary `try/catch` around async callback chains, especially deep within `async.eachSeries` recursion), the exception can propagate up and crash the Node.js process for any node that attempts to validate the malicious unit — including light/full/hub nodes independently validating incoming units, and witnesses. This creates a network-wide denial-of-service condition against unit validation: a node that crashes stops confirming new units until restarted, and if enough validating nodes crash on the same malicious unit, the network's ability to reach agreement on/stabilize new units is impaired.

### Likelihood Explanation
Medium: the attack requires posting a single unit with a specially crafted address definition or asset condition. It requires no signature forgery, no network position, and no privileged role, and it is validated by every full node/light-vendor/witness that processes the unit through `validateAuthor()` → `validateAuthentifiers()` → `validateDefinition()`. The exact required nesting depth to overflow the stack is implementation/JS-engine-dependent (V8's default stack size, whether `--stack-size` was tuned, node version), so exploitability depends on the platform's stack limits versus `MAX_COMPLEXITY`, similar to curl's caveat that "the exact amount does vary with platforms, compilers and other environmental factors." I was not able to directly confirm the value of `MAX_COMPLEXITY`/`MAX_OPS` in `constants.js` due to tool/search limitations in this session, so I cannot state with certainty whether these constants are large enough in practice to reach V8's default stack limit purely through `not` nesting (or through nested `address`-reference chains). This uncertainty should be verified by a follow-up review of `constants.js`.

### Recommendation
- Add an explicit recursion-depth counter (independent of `complexity`/`count_ops`) to `evaluate()` in both `validateDefinition()` and `validateAuthentifiers()` in `definition.js`, capped at a conservative depth (e.g., ~100, matching the `MAX_DEPTH`/`setImmediate`-every-100 pattern already used in `aa_validation.js` and `formula/evaluation.js`/`formula/validation.js`).
- Periodically yield the call stack (e.g., via `setImmediate`) inside the recursive `evaluate()` calls for `not`, `and`/`or`, `r of set`, `weighted and`, and `address`/`definition template` branches, mirroring the pattern already used elsewhere in the codebase (`count % 100 === 0` → `setImmediate`).
- Ensure any resulting `RangeError`/stack-overflow condition is caught and converted into a normal validation failure (`callback(err)`), rather than allowed to propagate as an uncaught exception that can crash the process.

### Proof of Concept
Construct an address definition (or asset spending-condition definition) for a unit author consisting of `N` nested `not` wrappers around a valid `sig` leaf, where `N` is chosen close to `MAX_COMPLEXITY`/`MAX_OPS` (exact threshold unverified in this session):
```
['not', ['not', ['not', /* ... N times ... */ ['sig', {pubkey: '<valid pubkey>'}] /* ... */ ]]]
```
Post a unit whose author uses this definition (or an asset whose issue/transfer condition uses it). When a node calls `validateAuthor()` → `Definition.validateAuthentifiers()` → `validateDefinition()` [6](#0-5) , the nested `not` cases cause `N` synchronous nested calls to the inner `evaluate()` function [1](#0-0) , unlike the throttled recursion used elsewhere in the codebase, potentially exceeding the JS engine's call stack and crashing/hanging the validating node.
