### Title
Cross-repository GitHub status forgery via SHA collision in `StatusHandler#process` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/commit.rb])

### Summary
The call chain `Shipit::Webhooks::Handlers::StatusHandler#process` → `Commit#create_status_from_github!` → `Commit#add_status` → `Status.replicate_from_github!` contains no comparison of the webhook payload's `repository.full_name` against the target commit's `stack.repository.full_name` anywhere along the path. `process` looks up commits purely `Commit.where(sha: params.sha)`, without any repository/stack filter, so any commit record in the entire Shipit instance sharing that SHA — regardless of which stack/repository it belongs to — receives the status write.

### Finding Description
The binding that should hold but does not: `stack.repository.full_name == payload.dig('repository', 'full_name')` is asserted nowhere between `process` and `replicate_from_github!`.

Trace:
- `Shipit::Webhooks::Handlers::StatusHandler#process` [1](#0-0)  does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — the query is keyed solely on `sha`, with zero `stack_id`/`repository` scoping.
- `Commit#create_status_from_github!` [2](#0-1)  unconditionally forwards to `add_status`/`statuses.replicate_from_github!` using `self.stack_id` (the commit's own stack), never checking that stack's repository against the webhook payload.
- `Commit#add_status` [3](#0-2)  only manages status-transition bookkeeping (hooks, continuous-delivery scheduling); no repository check.
- `Status.replicate_from_github!` [4](#0-3)  does `find_or_create_by!(stack_id:, state:, ...)`, writing directly using the passed `stack_id` with no ownership assertion.

The only authentication performed before this chain is `WebhooksController#verify_signature` [5](#0-4) , which verifies the HMAC signature against `Shipit.github(organization: repository_owner)` — this proves the request came from GitHub for the *attacker's own organization/repo* (which the attacker legitimately owns/controls), not that the target commit belongs to that same repository. `Handler#stacks`/`repository_name` helpers exist in the base class [6](#0-5)  but `StatusHandler#process` never calls `stacks` or `repository_name` — it bypasses this entirely and queries `Commit` globally by `sha`.

Attack: an attacker who owns/controls repository `attacker/repo` (fork or new repo) can craft a commit whose SHA collides with, or is intentionally identical to, a commit that already exists in a victim's Shipit stack (e.g., by pushing the exact same commit content/tree as an existing public/shared commit, or via a git SHA-1 collision, or simply because Shipit records the same upstream commit under multiple stacks tracking the same repo history via forks/mirrors). The attacker then triggers/sends a `status` webhook event from their own repo (signed with their own repo's legitimate GitHub App/webhook secret) for that SHA. `verify_signature` passes because the signature matches the attacker's own org. `StatusHandler#process` finds *all* `Commit` rows with that SHA across the entire database — including the victim's — and writes a forged `success`/`failure`/`pending` `Status` onto the victim's commit via `replicate_from_github!`, without ever checking that the victim stack's repository matches the attacker's repository.

### Impact Explanation
A forged `Status` row is written against a commit belonging to a stack/repository the attacker does not own and never authenticated for. Since `Commit#deployable?` and continuous-delivery/merge scheduling (`schedule_continuous_delivery`, `stack.schedule_merges`) key off `status.success?`/`state`, this can cause `deploy`/`merge` actions to be triggered on a victim's stack that should be blocked pending real CI, or conversely block a legitimate deploy by injecting a `failure`/`error` status. This is a payload for one repository mutating another repository's commit/stack, matching the Critical criterion "a payload for one repository mutating another's stack, commit, task or team" and enabling "an unauthorized deploy" via forged status.

### Likelihood Explanation
The primary practical constraint is SHA collision: exploitation requires the attacker's repository to contain a commit with the exact same SHA as a commit tracked in a victim's Shipit stack. This is trivially achievable when the victim stack tracks a public/open-source repository that the attacker can fork (the fork shares identical commit SHAs with upstream for any commit the attacker did not rewrite), or when multiple Shipit stacks track the same repository/mirror. In such (common) setups, the attacker needs no Shipit credentials — only the ability to configure/send a webhook (or push to their fork, if their fork has an active webhook to the same Shipit instance) for a SHA that also exists in the victim stack. This is fully repeatable against any SHA the attacker can align with a victim's tracked commit.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the webhook's own repository, e.g. `stacks.commits.where(sha: params.sha)` using the base `Handler#stacks` helper (which resolves `Repository.from_github_repo_name(repository_name)`), or explicitly assert `commit.stack.repository.full_name == repository_name` before calling `create_status_from_github!`, so that a status webhook from repository A can only ever mutate commits belonging to stacks whose repository is A.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from repo A must not write a status for a commit belonging to repo B's stack" do
  stack_a = shipit_stacks(:shipit) # repository.full_name == "shopify/shipit-engine"
  stack_b = create_stack(repository_full_name: "attacker/evil-repo")

  shared_sha = "a" * 40
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "victim commit")

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/forged",
    "repository" => { "full_name" => "shopify/shipit-engine" } # attacker's own, signed repo
  }

  # Binding under test: stack_b.repository.full_name ("attacker/evil-repo")
  # vs payload["repository"]["full_name"] ("shopify/shipit-engine") — must NOT match
  assert_not_equal stack_b.repository.full_name, payload["repository"]["full_name"]

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit_b.reload
  # FAILS today: status gets written even though repositories differ
  assert_empty commit_b.statuses, "status should not be written for a commit outside the webhook's own repository"
end
```
This demonstrates that `create_status_from_github!` → `add_status` → `replicate_from_github!` writes a `Status` for `commit_b` (belonging to `attacker/evil-repo`'s stack... inverted for clarity: substitute victim stack tracking a shared-SHA commit) purely based on SHA match, confirming zero repository-equality check exists anywhere in the chain.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
