Based on my research, I found a genuine structural analog to the reported vault bug in the `hookify` plugin's rule engine. Both bugs share the same root cause: **an authorization/enforcement decision is derived from checking "which entity" is involved (app ID / tool name) without checking "which sub-mode/OnCompletion path" was actually taken, so an alternate completion path silently downgrades enforcement to a no-op.**

### Title
Hookify `block` rules silently downgrade to a non-blocking warning for any hook event other than `Stop`/`PreToolUse`/`PostToolUse` - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine.evaluate_rules` decides how to enforce a matched `action: block` rule by branching on `hook_event_name`, with explicit denial formats only for `Stop`, `PreToolUse`, and `PostToolUse`. Any other event name — notably `UserPromptSubmit`, which the plugin explicitly documents and ships a dedicated hook script for (`event: prompt`) — falls into the `else` branch that returns only `{"systemMessage": ...}`, which is advisory text with no blocking semantics. A user who configures a `block` rule on `event: prompt` (e.g., to stop prompts containing secrets, prohibited instructions, or dangerous intents from ever reaching the model) gets no actual enforcement: the rule "matches," Claude is shown a message, but the prompt still proceeds exactly as if the rule had never fired.

### Finding Description
`evaluate_rules` builds `blocking_rules` from any rule whose `action == 'block'` and which matched via `_rule_matches`, then formats the response purely based on `hook_event_name`: [1](#0-0) 

For `Stop` it returns `{"decision": "block", ...}`, and for `PreToolUse`/`PostToolUse` it returns the `hookSpecificOutput.permissionDecision: "deny"` shape. For every other `hook_event_name` — which includes `UserPromptSubmit`, the event the plugin's own `userpromptsubmit.py` hook fires under — the code falls into the final `else`, returning only `{"systemMessage": combined_message}`: [2](#0-1) 

The vulnerable assumption here parallels the vault bug: the vault's TEAL checks "is `gtxn[0].ApplicationID` the vault app?" without checking which program (`ApprovalProgram` vs `ClearStateProgram`) actually ran, so satisfying the app-ID identity check while diverting into `ClearStateProgram` bypasses all the approval logic. Here, `evaluate_rules` checks "did a rule match with `action: block`?" and assumes reaching that state always means one of the three explicitly-handled hook events fired, but the correct-vs-actual `hook_event_name` diverges for `UserPromptSubmit` — a legitimate, documented entry point into the exact same rule engine — and the code has no enforcement path for it. `systemMessage` alone does not stop the tool/prompt from executing; Claude Code hooks require `"decision": "block"` (or `additionalContext`/exit-code semantics) for `UserPromptSubmit` to actually prevent the prompt from being processed, per the plugin's own hook-development guidance elsewhere in the repo describing correct blocking shapes for each event type. Because the `else` branch is a silent fallback rather than a fail-closed/explicit-event allowlist, this passes CI/tests trivially (any 'warn' rule looks identical) and is invisible until a user relies on `event: prompt` + `action: block` for real enforcement.

### Impact Explanation
Any project relying on hookify's `prompt`-event `block` rules (documented and packaged as a supported feature — `event: prompt` is listed alongside `bash`/`file`/`stop`/`all` in the README and skill docs) to prevent specific user prompts from reaching Claude — e.g., blocking prompts that would leak secrets, invoke prohibited automation, or trigger destructive workflows — silently gets **no enforcement at all**. The user sees a warning-looking message but the operation proceeds unblocked, which is a false sense of security in exactly the same class as the vault's "any vault can be drained" bypass: a documented protection mechanism (`action: block`) is defeated by using a valid-but-unhandled entry point (`UserPromptSubmit`) into the same validation code. This is a genuine hook-bypass / tool-authorization trust-boundary issue reachable by an unprivileged project author who configures hookify rules expecting them to work as documented.

### Likelihood Explanation
High likelihood of being hit in practice, not requiring any adversarial exploitation beyond normal, documented usage: any user who follows the plugin's own docs to write an `event: prompt`, `action: block` rule (a supported, advertised configuration) will silently get a no-op enforcement. No attacker sophistication is needed — the "attack" is simply submitting the prompt the rule was meant to block, which now succeeds.

### Recommendation
- **Short term:** In `evaluate_rules`, explicitly handle `UserPromptSubmit` by returning the hook's real blocking shape (`{"decision": "block", "reason": ...}` per Claude Code's `UserPromptSubmit` hook contract), and change the final `else` branch from a silent pass-through into a fail-closed/explicit case: log or reject unrecognized `hook_event_name` values for `block`-action rules rather than silently degrading to `systemMessage`-only output.
- **Long term:** Add integration tests asserting that for every `event:` type the plugin documents as supported (`bash`, `file`, `stop`, `prompt`, `all`), an `action: block` rule actually produces an output shape that Claude Code's hook runner treats as blocking — not just a rendered message. This mirrors the vault's own "long term" recommendation to test every accepted/rejected interaction path explicitly rather than assuming one enforcement branch generalizes to all entry points.

### Proof of Concept
1. Create `.claude/hookify.block-secret-prompt.local.md`:
```markdown
---
name: block-secret-prompt
enabled: true
event: prompt
action: block
conditions:
  - field: user_prompt
    operator: contains
    pattern: SECRET_TOKEN
---
Blocked: prompt contains a secret token.
```
2. Submit a prompt containing `SECRET_TOKEN`. `userpromptsubmit.py` invokes `RuleEngine.evaluate_rules` with `input_data["hook_event_name"] == "UserPromptSubmit"`.
3. The rule matches and `action == "block"`, so it lands in `blocking_rules`, but `hook_event_name` is neither `"Stop"` nor in `["PreToolUse", "PostToolUse"]`, so the function returns only `{"systemMessage": "**[block-secret-prompt]**\nBlocked: prompt contains a secret token."}`.
4. This output has no `decision` or `hookSpecificOutput.permissionDecision` field, so Claude Code does not block the prompt — it is processed normally despite the rule author's intent and the plugin's documented `action: block` semantics. [3](#0-2) [4](#0-3) [5](#0-4)

```python
    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)

        # If any blocking rules matched, block the operation
        if blocking_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in blocking_rules]
            combined_message = "\n\n".join(messages)

            # Use appropriate blocking format based on event type
            if hook_event == 'Stop':
                return {
                    "decision": "block",
                    "reason": combined_message,
                    "systemMessage": combined_message
                }
            elif hook_event in ['PreToolUse', 'PostToolUse']:
                return {
                    "hookSpecificOutput": {
                        "hookEventName": hook_event,
                        "permissionDecision": "deny"
                    },
                    "systemMessage": combined_message
                }
            else:
                # For other events, just show message
                return {
                    "systemMessage": combined_message
                }

        # If only warnings, show them but allow operation
        if warning_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in warning_rules]
            return {
                "systemMessage": "\n\n".join(messages)
            }

        # No matches - allow operation
        return {}
```

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
