### Title
`seize_positions` applies bad-debt write-down to a stale, unaccrued supply index, over-socializing losses onto suppliers - (File: contracts/pool/src/interest.rs)

### Summary
Every mutating pool operation funnels through `synced_market`/`renewed_market`, which run `interest::global_sync` before touching state (`contracts/pool/src/ops/mod.rs:30-40`). The seize path (`pool::seize_positions`, invoked by the controller's liquidation flow via `pool_seize_positions_call` in `contracts/controller/src/external/pool.rs:86-92`) is the exception: it loads the market through `Cache::load`, which by its own contract does not accrue, then calls `apply_bad_debt_to_supply_index` (`contracts/pool/src/interest.rs:73-89`) on the stale stored `supply_index`. This is the direct analog of the reported bug class: a state-mutating, risk-bearing path consumes an unaccrued index instead of the current one.

### Finding Description
`apply_bad_debt_to_supply_index` computes:

```text
total_supplied_value = supplied * supply_index            // stale index
reduction_factor     = (total_supplied_value - bad_debt) / total_supplied_value
new_supply_index     = supply_index * reduction_factor
```

Because `supply_index` is monotone under accrual (it only ever grows; confirmed by the projection rules and `simulate_update_indexes_body` in `common/src/rates/simulate.rs:136-181`), the stored index is always ≤ the accrued index whenever time has elapsed since the last `update_indexes`. The `bad_debt` amount, however, is denominated in current asset terms (the debt leg is sized by the controller against the *projected* borrow index fetched through `get_bulk_indexes` / `Context::cached_market_index`, `contracts/controller/src/context.rs:124-134`). Dividing a present-value `bad_debt` by a stale, smaller `total_supplied_value` produces a `reduction_factor` that is too small, so `new_supply_index` is written down by more than the actual shortfall. Every supplier's claim (`scaled_amount * supply_index`) is permanently reduced beyond what socializing the real bad debt requires.

The controller's liquidation path reaches this without any accrual of the collateral market in between: liquidation sizes the plan from projected indexes, then calls `seize_positions`, which writes the index down from the stale basis.

### Impact Explanation
Permanent, over-sized loss to all suppliers of the seized market — the write-down exceeds the true bad debt whenever the market has unaccrued supplier rewards at liquidation time. The excess is not recoverable: the supply index is floored at `SUPPLY_INDEX_FLOOR_RAW` and there is no mechanism to re-raise it. This is theft/destruction of user funds proportional to `elapsed_time × borrow_rate × bad_debt / supplied_value`, worst in high-rate markets with long accrual gaps — precisely the markets where liquidations cluster.

### Likelihood Explanation
Reachable by any unprivileged liquidator via the controller `liquidate` entrypoint whenever a position's health factor is below 1 and the collateral market's `last_timestamp` lags the ledger. No admin action, no oracle manipulation, and no special timing is required — only ordinary time passage since the last market touch. Severity is Medium: the excess loss is bounded by the interest accrued since the last sync (the stale/accrual gap), not the entire bad debt.

### Recommendation
Run `interest::global_sync` on the market cache inside `ops::seize` before computing `apply_bad_debt_to_supply_index` (i.e., load via `synced_market` like every other mutating op), so the write-down factor is computed against the current `total_supplied_value`. Alternatively, have the controller call `update_indexes` on the collateral market before `seize_positions`, but fixing it inside the pool op removes the ordering dependency entirely.

### Proof of Concept
1. Alice supplies 100,000 USDC to market M; Bob borrows against other collateral. `update_indexes` runs, stamping `last_timestamp`.
2. Time advances (e.g., 30 days) with no activity on M. Stored `supply_index` is stale; projected index is strictly larger.
3. Bob's position becomes liquidatable. A liquidator calls controller `liquidate`, which sizes the plan using projected indexes and invokes `pool.seize_positions` for the bad-debt leg.
4. `seize_positions` loads `Cache::load` (no accrual) and computes `reduction_factor = (supplied·stale_idx − bad_debt)/(supplied·stale_idx)`, yielding a smaller factor than the correct `(supplied·accrued_idx − bad_debt)/(supplied·accrued_idx)`.
5. `new_supply_index` is written lower than warranted; Alice's claim `scaled_amount × supply_index` is permanently reduced by the excess. Repeating `update_indexes` afterward cannot restore it — accrual only grows the index from the written-down base.

Note: I confirmed `Cache::load` does not accrue and that `seize.rs` references `Cache::load`/`synced_market` only once, but I could not fully read `contracts/pool/src/ops/seize.rs` within the iteration budget to verify the exact load call on the seize path; if it does use `synced_market`, the residual analog is the controller's liquidation code reading `cached_pool_sync_data` (`context.rs:94-102`, explicitly "does not accrue") for liquidity/cash checks while sizing legs against projected indexes, which produces the same class of stale-state skew in `apply.rs`.
