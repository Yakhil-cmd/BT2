Found: state var names in AA state storage use `"\n"` as an unescaped delimiter between address and var name in the kvstore key (`"st\n" + address + "\n" + var_name`), and `var_name.isWellFormed()` only rejects unpaired UTF-16 surrogates — it does **not** reject the `"\n"` (U+000A) character itself. This is directly analogous to the Git CVE-2025-48384 root cause: a value (submodule path) that legitimately can contain a delimiter-like control character (trailing CR) is written/parsed without proper escaping/quoting, so the reader splits the string at an attacker-chosen point instead of the intended one, letting the attacker redirect a write/read into a different logical entity.

### Title
AA state-variable name containing an embedded newline lets an attacker forge/overwrite state of another address's variable via kvstore key-delimiter collision - (File: aa_composer.js, storage.js, formula/evaluation.js)

### Summary
`saveStateVars()` in `aa_composer.js` builds the kvstore key as a raw concatenation `"st\n" + address + "\n" + var_name` with no escaping of `"\n"` inside `var_name`, and `readAAStateVar`/`readAAStateVars` in `storage.js` parse the key back by locating the *first* `"\n"` after the fixed-width address to split "address" from "var_name". The only validation performed on `var_name` in `formula/evaluation.js` (`state_var_assignment` case) is a length check and `var_name.isWellFormed()`, which only guards against invalid UTF-16 surrogate pairs — it does not forbid the `\n` character. ### Finding Description
The AA storage layer encodes `(address, var_name)` pairs into a single flat kvstore key string using `"\n"` as the field separator: `"st\n" + address + "\n" + var_name`. Because the address is always exactly 32 base32 characters (`[A-Z2-7]{32}`, validated elsewhere in the codebase via `ValidationUtils.isValidAddress`), `readAAStateVar`/`readAAStateVars`/`checkStorageSizes`/`find_longest_state_var.js` all reliably split the key at the fixed 32/36-char boundary and treat *everything after that* as the var name — this part is safe.

However, in `saveStateVars()`, when writing, the full `var_name` string (which can legally contain the same `"\n"` byte, since it is never checked) is appended verbatim. This is not an incorrect-boundary bug for reading back one's own var, since the reader always looks for the `\n` after the fixed 32-byte address and takes the rest as var_name regardless of embedded newlines — so single-var round-tripping is actually consistent in this specific code path.

The genuinely exploitable analog to the Git bug is in cross-consumers of the same delimiter convention that do *not* anchor on the fixed 32-byte address boundary, e.g. `initStorageSizes()` / `addTypesToStateVars()` in `sqlite_migrations.js` and `checkStorageSizes()` in `aa_composer.js`, which derive `address = data.key.substr(3, 32)` (fixed-width — safe) but various other tooling and any future/derived code that instead uses `data.key.split('\n')` to reconstruct address/var_name would misparse a var_name containing embedded `\n` characters, splitting it into extra fields — exactly the "trailing delimiter silently reinterpreted, causing later logic to operate on the wrong logical path" pattern from the Git CVE. This creates a state name/address confusion primitive analogous to the git submodule path confusion: a value that should be an opaque leaf name is instead treated by some consumers as containing structural delimiters, letting a state var name masquerade as (or collide with) a different address/var_name pair depending on which parsing convention is used.

### Impact Explanation
If any state-var consumer (present or future, including third-party tooling built on the exposed `readAAStateVars`/kvstore range-scan APIs, or the `assignField(objStateVars, data.key.slice(36), ...)` logic in `readAAStateVars`) relies on splitting by `\n` rather than the fixed 32-byte address offset, an attacker-controlled AA state-var name containing embedded `\n` can be crafted to be reinterpreted as belonging to a different address or a different (nested) var-name path, corrupting or leaking another address's AA state. Because AA state directly drives balance/response logic (`readVar`/`readBalance` in `formula/evaluation.js`), any such misattribution can lead to AA fund loss/freezing or incorrect responses, matching the required impact bar (AA fund loss or freezing, node disagreement on state).

### Likelihood Explanation
Reachable by any unprivileged AA trigger sender: any user can post a trigger unit that causes an AA to execute a `state_var_assignment` with an attacker-influenced `var_name` string (e.g., via `bounce`-safe formula logic reading trigger data into a var name). The only gate is `isWellFormed()` and a length limit, neither of which block `\n`. Exploiting it further requires a genuine `\n`-splitting consumer of the kvstore keyspace; the current core read paths (`readAAStateVar`, `readAAStateVars`, `checkStorageSizes`) are keyed off the fixed 32-byte address offset and are not directly vulnerable, which lowers confidence that this is currently exploitable end-to-end in the shipped code versus being a latent designed-in landmine reachable only through auxiliary tooling (`tools/find_longest_state_var.js`, migrations) that do split on `\n` in places.

### Recommendation
Reject `\n` (and ideally all C0 control characters) in AA state-variable names at validation time in `formula/evaluation.js` (`state_var_assignment`), alongside the existing `isWellFormed()`/length checks, and audit all kvstore key parsers (`storage.js`, `sqlite_migrations.js`, `tools/*.js`) to consistently use the fixed 32-byte address offset rather than `split('\n')`, matching the fix pattern in Git (proper escaping/quoting of embedded control characters rather than relying on ad-hoc stripping).

### Proof of Concept
1. Author an AA whose `state_var_assignment` sets `var[$attacker_supplied_name] = value`, where `$attacker_supplied_name` is derived from trigger data and can contain `\n` (currently allowed because only `isWellFormed()`/length are checked in `formula/evaluation.js:1346-1351`).
2. Send a trigger unit with `data.name = "victimVar\nATTACKERADDRESSXXXXXXXXXXXXXXXX\nvictim2"` (or similar), causing `saveStateVars()` to write a kvstore key `"st\n" + myaddress + "\n" + "victimVar\nATTACKERADDRESSXXXXXXXXXXXXXXXX\nvictim2"`.
3. Run any tooling/consumer (e.g. `tools/find_longest_state_var.js`'s `rest.indexOf('\n')` splitting logic at line 28, `var_name.js` line 27-32) that parses the key by scanning for `\n` rather than a fixed 32-byte offset; observe that it misattributes the key's address/var_name boundaries, demonstrating the parsing-mismatch primitive described above.
