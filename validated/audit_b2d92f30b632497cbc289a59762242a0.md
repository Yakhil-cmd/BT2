### Title
`LiquidityPool::recapitalize` pays out pool tokens to an arbitrary payer without pulling any funds in, draining custody while the cash book still claims the funds — supplier withdrawals then pass the liquidity guard and fail in the SAC transfer - ([File: contracts/pool/src/lib.rs])

### Summary
The Derby analog is "an outbound transfer leaves the vault without enough to cover funds reserved for users." In XOXNO Lending the reserved amount is the pool's `cash` book, which is what `require_reserves` checks before any withdrawal (`contracts/pool/src/cache/cash.rs:15-21`). `recapitalize` can send the pool's entire token custody to a caller-chosen `payer` address without requiring any inbound deposit, so the accounting cash continues to claim the funds exist. Subsequent supplier `withdraw` calls clear `require_reserves` because the book still shows the cash, then revert inside the SAC `token::transfer` for insufficient custody — exactly the "sent funds out, nothing left to cover the obligation" shape of the original bug, except it is a direct drain rather than a missing post-check.

### Finding Description
The pool's solvency model separates the `cash` book from the actual token balance: `debit_cash` enforces `cash >= amount`, and `transfer_out` moves tokens without adjusting custody assumptions (`contracts/pool/src/cache/cash.rs:34-53`). The in-repo test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` demonstrates the issue end-to-end (`contracts/pool/tests/flows.rs:3408-3483`):

1. A supplier deposits 10,000,000,000; book `cash` equals token balance.
2. An attacker calls `recapitalize(hub_asset, payer, custody)` with `payer` being an arbitrary generated address and `custody` equal to the pool's full token balance.
3. `token.balance(pool) == 0` afterward — custody is gone — while `state.cash >= deposit` still claims the supplier's funds are present.
4. The supplier's `withdraw` passes both `require_reserves` and `require_supply_for_debt` (the test asserts neither `InsufficientLiquidity` nor `PoolInsolvent` is what fails) and reverts inside the SAC transfer with `BalanceError = 10`.

So `recapitalize` performs an unauthenticated outbound `transfer_out` to `payer` with no check that an equal or greater amount was first received — the same missing "post-transfer funds must cover obligations" guard as `rebalanceXChain`, but worse: here the outbound leg itself is the bug.

### Impact Explanation
Theft of user funds and protocol insolvency: any unprivileged address can drain the pool's token custody to itself (`payer` is attacker-controlled), while the cash book overstates custody, so suppliers' claims become unpayable. Even the failure mode is deceptive — exits fail in the token contract rather than in a pool guard, so the market still reports itself solvent.

### Likelihood Explanation
High if reachable: `recapitalize` is a public pool interface entrypoint (`interfaces/pool/src/lib.rs`), the test fixture invokes it directly with a freshly generated `payer`, and no authorization of `payer` is exercised in the demonstrated path. One caveat: pool mutators are `#[only_owner]`-gated to the controller (`contracts/pool/src/lib.rs:9-16`), so exploitability depends on whether the controller exposes a `recapitalize` path that forwards a user-chosen payer — `recapitalize` is listed among the unprivileged controller flows, and the test proves the pool-level mechanism. I was unable to read the controller-side `recapitalize` wrapper to confirm whether the payer argument is attacker-controlled there, so this residual uncertainty should be verified.

### Recommendation
Make `recapitalize` pull the recapped amount in (e.g., `transfer_from(payer, pool)` or require the payer to pre-fund and assert `balance_after == balance_before + amount`), and reconcile the cash book to actual custody — credit cash only after confirming tokens arrived, and never `transfer_out` more than an explicitly authorized rescue amount to the owner. Add a check that post-operation `token.balance(pool) >= state.cash` before committing.

### Proof of Concept
The repo already contains the reproducer at `contracts/pool/tests/flows.rs:3408-3483`:

```rust
token_admin.mint(&t.pool, &deposit);
let supplied = t.client().supply(&t.sup(0, deposit)).get_unchecked(0).position.scaled_amount;
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody);   // drains all custody
assert_eq!(token.balance(&t.pool), 0);
assert!(t.state_snapshot().cash >= deposit);                 // book still overstates custody
// withdraw then fails inside the SAC transfer (BalanceError = 10), not in a pool guard
```

Steps: supply any amount, call `recapitalize` with `payer` = attacker address and `amount` = pool token balance, observe custody at zero while `cash` still covers supplier claims, then any supplier `withdraw` reverts on the SAC balance check.
