### Title
Signature verification is scoped to `repository.owner.login`, but every webhook handler acts on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The multi-org GitHub App feature lets an operator configure a per-organization `webhook_secret`. `WebhooksController#verify_signature` picks which app/secret to validate the HMAC against using `repository_owner`, which is read from `payload.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . However, every event handler resolves the target `Stack`/`Repository` from a *different* JSON field, `payload.dig('repository', 'full_name')` [2](#0-1) . These two fields are never checked for consistency anywhere in the request-handling path.

### Finding Description
The equality that should hold is:

`organization whose secret authenticated the signature == organization that owns the repository the handler mutates`

i.e. `payload.repository.owner.login` (used to select the `GitHubApp`/secret in `verify_signature`) must equal the owner embedded in `payload.repository.full_name` (used by every `Handlers::Handler#stacks`/`#repository_name` to locate the `Stack`).

Nothing in `WebhooksController` or `Shipit::Webhooks::Handlers::Handler` enforces this. An attacker who knows (or controls) the webhook secret for *one* configured organization — including an org for which no `webhook_secret` was set, since `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank [3](#0-2)  — can craft a single JSON body where:
- `repository.owner.login` = the organization whose secret they control/know (or one with no secret configured), so `verify_signature` succeeds and looks up that org's `GitHubApp` [4](#0-3) , and
- `repository.full_name` = `"victim-org/victim-repo"`, an entirely different, unrelated repository they don't control.

Because `verify_signature` never checks that `repository.full_name`'s owner matches `repository_owner`, and `Handler#repository_name`/`#stacks` blindly trusts `full_name` to resolve `Repository.from_github_repo_name` [2](#0-1) , the forged event is dispatched against the victim's `Stack`. For the `push` event this triggers `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the forged branch [5](#0-4) , forcing a resync to an attacker-chosen `after` SHA on a repository the attacker has no write access to and never had its signature verified for.

### Impact Explanation
This breaks the deployment-trust binding between "the organization that authenticated the webhook" and "the repository the engine mutates." Under a multi-org configuration (documented in `docs/setup.md`) with even one organization configured without a `webhook_secret`, or where an attacker knows one org's secret (e.g., a low-trust org they administer), they can forge events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) against any other configured organization's repositories, causing unauthorized state changes such as forced `sync_github` to an arbitrary commit, spurious commit statuses, or membership/team churn — all without ever satisfying the signature check for the victim organization. This is a cross-repository/cross-organization write achieved purely by crafting an HTTP payload, matching the "cross-repository writes" high/critical impact bucket.

### Likelihood Explanation
Requires: (1) a multi-org GitHub App deployment (explicitly supported and documented), and (2) either an organization configured with a blank `webhook_secret` (documented as optional) or knowledge of one org's secret. Given Shipit explicitly supports multiple orgs sharing one instance with independently-configured secrets, and `webhook_secret` is optional per org, this is a realistic misconfiguration/multi-tenant scenario rather than a purely theoretical one.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after determining `repository_owner` and before dispatching to handlers, assert that the owner segment of `payload.dig('repository', 'full_name')` matches `repository_owner` (and reject `organization.login` payloads whose repositories don't belong to that org). Alternatively, require `webhook_secret` to be present for every configured organization and fail closed instead of returning `true` when it is blank.

### Proof of Concept
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<valid HMAC computed with orgA's (blank/known) webhook_secret>

{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "orgA" },       // used only for signature/app lookup
    "full_name": "victim-org/victim-repo"  // used by PushHandler to locate the Stack
  }
}
```
`verify_signature` looks up `Shipit.github(organization: "orgA")` and validates using orgA's secret (or trivially passes if blank) [4](#0-3) ; `PushHandler` then resolves and mutates `victim-org/victim-repo`'s stacks [5](#0-4) [2](#0-1) , even though the signature never authenticated anything about `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
