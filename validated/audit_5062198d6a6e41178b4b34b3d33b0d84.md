### Title
Unprivileged accounts can grief `Withdraw` on any vote account by permissionlessly inflating `pending_delegator_rewards` via `DepositDelegatorRewards` - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The `VoteInstruction::DepositDelegatorRewards` handler lets **any signer** push lamports into **any** vote account and permanently increase that vote account's `pending_delegator_rewards` counter, with no relationship to the vote account's owner/withdrawer required. That counter is later consulted by `withdraw()` to gate full account closure and to compute the minimum withdrawable balance, so an attacker can grief a validator's ability to fully withdraw/close a vote account for the cost of a few lamports, mirroring the "front-run a balance-gated privileged operation via a cheap permissionless call" pattern from the PoolTogether `VaultBooster` report.

### Finding Description
`deposit_delegator_rewards()` only requires that the **source account** (the depositor) sign the transfer — it never checks that the caller is the vote account's authorized voter, withdrawer, or node identity: [1](#0-0) 

After the CPI transfer, it unconditionally increments the vote account's `pending_delegator_rewards`: [2](#0-1) 

The instruction dispatcher likewise imposes no ownership/authorization restriction on the `source` account relative to the target vote account — it just checks two accounts are present and forwards to `deposit_delegator_rewards`: [3](#0-2) 

This means **any address holding a trivial amount of lamports** can call `DepositDelegatorRewards` against a vote account it doesn't control, sign as `source`, and deposit as little as 1 lamport, which is confirmed by the "zero-lamport deposit" success test showing even a 0-lamport deposit is accepted as a no-op (and any nonzero deposit succeeds and increments state): [4](#0-3) 

`pending_delegator_rewards` is subsequently enforced inside `withdraw()`, the function that the authorized withdrawer must use to reclaim funds: [5](#0-4) 

Specifically:
- A full withdrawal (`remaining_balance == 0`, i.e., closing the account) is rejected outright if `pending_delegator_rewards > 0`.
- A partial withdrawal is capped so that the remaining balance must stay at or above `rent_exempt_minimum + pending_delegator_rewards`.

This is directly analogous to the reported PoolTogether bug: a permissionless, unprivileged call (`liquidate()` in the report; `DepositDelegatorRewards` here) can be used, at negligible cost, to manipulate a balance-derived state variable that a privileged/authorized operation's precondition check depends on, causing that legitimate operation to revert or be constrained. In the PoolTogether case the owner's `setBoost()` reverts; here the vote account withdrawer's `Withdraw` to zero (account close) reverts, and partial withdraws are capped below the true balance.

There is no instruction in the vote program that lets the withdrawer voluntarily clear/consume `pending_delegator_rewards` on demand — the tests show it is only cleared through the epoch-boundary reward distribution/commission-collector machinery (`calculate_block_reward` / commission distribution in `runtime/src/bank/partitioned_epoch_rewards/*`), not via a direct withdrawer-triggered instruction: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker can repeatedly call `DepositDelegatorRewards` with a dust amount (as small as 1 lamport) against a target validator's vote account whenever the authorized withdrawer attempts to fully close the account or withdraw beyond `rent_exempt_minimum + pending_delegator_rewards`. This:
- Blocks the legitimate `Withdraw` instruction that would otherwise succeed (reverts with `InstructionError::InsufficientFunds`), a direct griefing/DoS on a stake/vote-program instruction handler.
- Can be maintained indefinitely and cheaply (the attacker's lamports are not lost — they land in the target vote account, so the attack is nearly free), making the vote account's full balance effectively locked/frozen from ever being withdrawn to zero as long as the attacker keeps front-running closure attempts, which functionally approaches a "frozen account" condition for the closure use case even though partial withdraws below the threshold still work.

This does not itself mint or steal lamports and requires the attacker to actively and repeatedly grief (no single deposit permanently freezes funds since a subsequent epoch's reward distribution can consume `pending_delegator_rewards`), so the concrete, permanent-impact bar (theft/minting of lamports, misattributed rewards, permanently frozen accounts, cross-node divergence, epoch halt) is only partially met — the mechanism can degrade to sustained griefing rather than a guaranteed permanent freeze, since epoch-boundary reward processing may reduce `pending_delegator_rewards` over time.

### Likelihood Explanation
Likelihood is high for triggering the griefing condition: the call is fully permissionless (any signer can be `source`), costs are negligible (deposit amounts as low as 1 lamport are accepted), and it requires no special timing beyond observing a pending `Withdraw` transaction in the mempool to front-run — directly mirroring the front-running technique described in the referenced report.

### Recommendation
Restrict `DepositDelegatorRewards` so that `pending_delegator_rewards` can only be increased by parties authorized to interact with the vote account's delegator-rewards flow (e.g., require the `source` to be an already-registered delegator/stake account or gate the deposit path through a system that cannot be invoked by arbitrary third parties), and/or provide the authorized withdrawer an explicit, permissionless-to-itself instruction to reconcile/settle `pending_delegator_rewards` before a `Withdraw` so legitimate closures are not indefinitely blockable by dust deposits from unrelated accounts.

### Proof of Concept
Using the existing test harness in `programs/vote/src/vote_processor.rs`:
1. Set up a `VoteStateV4` account with `authorized_withdrawer` = W and `pending_delegator_rewards = 0`, funded above rent-exempt minimum (as in `create_test_account_with_authorized`).
2. As an attacker with an unrelated `source_pubkey` (signer only, no relation to the vote account), submit `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` with the attacker as `source` — this succeeds and sets `pending_delegator_rewards = 1`, per the deposit-handling flow verified in `test_deposit_delegator_rewards`: [8](#0-7) 
3. The withdrawer W then submits `VoteInstruction::Withdraw(full_balance)` intending to close the account. This now fails with `InstructionError::InsufficientFunds` because `pending_delegator_rewards > 0`, exactly as demonstrated in `test_withdraw_pending_delegator_rewards`: [9](#0-8) 
4. The attacker can repeat step 2 with another dust deposit whenever W retries closing the account, sustaining the block indefinitely at negligible cost.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

    let remaining_balance = vote_account
        .get_lamports()
        .checked_sub(lamports)
        .ok_or(InstructionError::InsufficientFunds)?;

    // Always zero until SIMD-0123 is activated.
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();

    if remaining_balance == 0 {
        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.
        if pending_delegator_rewards > 0 {
            return Err(InstructionError::InsufficientFunds);
        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());
        } else {
            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }
    } else {
        // SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
        // is lamports - pending_delegator_rewards - rent_exempt_minimum.
        let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());
        let min_balance = min_rent_exempt_balance
            .checked_add(pending_delegator_rewards)
            .ok_or(InstructionError::ArithmeticOverflow)?;
        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
        }
    }
