### Title
Permanent freezing of staked and reward tokens in `pallet-asset-rewards` after pool expiry due to unbounded `last_update_block` causing arithmetic underflow - (File: substrate/frame/asset-rewards/src/lib.rs)

### Summary
`pallet-asset-rewards` (the FRAME analog of a Synthetix-style staking-rewards contract, explicitly modeled on it per its own doc comment) reproduces the same class of bug flagged in the external report: reward accounting depends on a "reward end block" comparison (`expiry_block`) combined with a `last_update_block` checkpoint that is not properly bounded once the pool has expired. Unlike the original report (silently lost rewards), here the flaw is worse: it causes a permanent arithmetic-underflow `DispatchError` on every subsequent pool interaction, permanently freezing all staked tokens (frozen via `Freeze`) and all undistributed reward tokens in the pool.

### Finding Description
`reward_per_token()` caps "rewardable blocks" at `expiry_block` via `last_block_reward_applicable`, which always returns `min(now, expiry_block)`: [1](#0-0) 

`reward_per_token()` then computes elapsed blocks as `last_block_reward_applicable(expiry_block) - last_update_block` using `ensure_sub` (an error-returning, non-saturating subtraction): [2](#0-1) 

Crucially, `update_pool_rewards`, which persists the new checkpoint, sets `last_update_block` to the *actual current block number*, with no cap at `expiry_block`: [3](#0-2) 

Sequence of events (attacker needs no privileges — any signed account with a staked position, or, per the permissionless post-expiry paths, any account at all):

1. Pool created with `expiry_block = E`. Some account stakes and the pool accrues `last_update_block < E`.
2. After expiry, at block `N1 > E`, any account calls `unstake` or `harvest_rewards` (post-expiry these calls are explicitly permissionless: `ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin)`). [4](#0-3) 
   This call succeeds: `reward_per_token()` correctly computes `E - last_update_block` (still valid, no underflow), then `update_pool_rewards` sets `pool_info.last_update_block = N1` (> `E`) and this corrupted state is persisted via `Pools::<T>::insert(pool_id, pool_info)`.
3. From this point on, `last_update_block (N1) > expiry_block (E)`. Any further call to `stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, or `set_pool_expiry_block` (extending it, if the pool still has zero admin action, but that too first calls `reward_per_token`) invokes `reward_per_token()` again, which now computes `last_block_reward_applicable(E) = E` minus `last_update_block = N1 > E`, i.e. `E.ensure_sub(N1)` — an unsigned underflow, returning `Err(ArithmeticError::Underflow)` (or an equivalent trait error) propagated with `?` through `update_pool_and_staker_rewards` up to the dispatchable, aborting the whole extrinsic.
4. Because `unstake` and `harvest_rewards` both call `update_pool_and_staker_rewards` *before* unfreezing/transferring any tokens, this failure occurs before any state mutation that would let a staker recover funds. Every subsequent `unstake`/`harvest_rewards`/`stake` call on this pool for any staker fails identically and permanently — the pool's `Freeze` on staked assets can never be lifted and reward assets in the pool account can never be harvested. `cleanup_pool` also requires the pool to have zero stakers (`ensure!(stakers.is_none(), Error::<T>::NonEmptyPool)`), which is now permanently unreachable since stakers can no longer unstake.

This mirrors the report's violated invariant exactly: a reward-per-token cutoff computed against a fixed "reward end" bound, combined with a checkpoint (`last_update_block`/`lastUpdateBlockNumber`) that is allowed to drift past that bound once no in-time update occurs — except here the missing bound produces underflow/DoS instead of silent loss.

### Impact Explanation
This is an irreversible freezing of user funds (staked assets under a `Freeze`) and protocol/pool-operator funds (reward assets locked in the pool account), triggered by ordinary, permissionless, non-privileged extrinsic calls with no attacker cost beyond one transaction fee. This matches the "Critical" category of irreversible freezing explicitly prioritized by the assessment criteria.

### Likelihood Explanation
High likelihood: any pool that reaches its `expiry_block` and receives even a single ordinary post-expiry interaction (which is a normal, expected user action — harvesting final rewards or unstaking after expiry is exactly the documented use case) enters the broken state. No attacker coordination, governance, or malicious peer is required; a legitimate staker harvesting rewards after expiry triggers it inadvertently for themselves and every other staker in the pool.

### Recommendation
In `update_pool_rewards`, cap `last_update_block` at `expiry_block` (`new_pool_info.last_update_block = last_block_reward_applicable(pool_info.expiry_block)` rather than the raw current block number), or, in `reward_per_token`, guard against `last_update_block > applicable_block` and short-circuit to `reward_per_token_stored` in that case, mirroring the report's own recommended fix pattern.

### Proof of Concept
Not executed against a live network. Reproduction path is described structurally above based on static analysis of `substrate/frame/asset-rewards/src/lib.rs` (`reward_per_token`, `update_pool_rewards`, `last_block_reward_applicable`, `unstake`, `harvest_rewards`). A minimal FRAME unit test (using the pallet's own mock runtime, `substrate/frame/asset-rewards/src/mock.rs` and `tests.rs`) would: create a pool with a short `expiry_block`, stake, advance blocks past expiry, call `unstake` once (succeeds, corrupts `last_update_block`), then call `unstake`/`harvest_rewards` again and assert it returns `Err` due to arithmetic underflow — this was not run in this session; I could not execute Rust/cargo tests in this environment, so this remains a static-analysis-based finding pending compiled/test confirmation. The existing test suite (`tests.rs`, e.g. the `integration` test) does not appear to exercise two consecutive post-expiry pool interactions, which is consistent with this edge case being untested.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
