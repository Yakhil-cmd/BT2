### Title
Per-recipient rounding of `earned_headers_commission_recipients` shares can inflate total headers-commission credited beyond the payer unit's actual commission - (File: headers_commission.js)

### Summary
`calcHeadersCommissions()` splits a winning child unit's headers commission among the addresses listed in `earned_headers_commission_recipients` by rounding each recipient's share independently with `Math.round(full_amount * share / 100.0)`, then inserts each rounded amount directly into `headers_commission_contributions`, which is later summed into `headers_commission_outputs` and becomes unconditionally spendable balance. [1](#0-0) [2](#0-1) 

### Finding Description
For a single payer unit, `full_amount` (the payer's `headers_commission`) is divided across recipients using per-recipient `Math.round(full_amount * share / 100.0)`, where the shares are values the unit's author freely sets via `earned_headers_commission_recipients` in the unit they post (they must nominally sum to 100). [3](#0-2)  The code itself acknowledges the rounding is applied "before summing up header commissions won from several parent units," i.e., independently per recipient/per payer rather than against a running total that would conserve the exact `full_amount`. [4](#0-3) 

Because each recipient's amount is rounded independently (each can round up by nearly 0.5), an author who structures many small-share recipients (e.g. splitting 100% share among a large number of addresses with tiny percentages) can cause the sum of rounded amounts credited to `headers_commission_contributions` to exceed the payer unit's actual `headers_commission` value. These contributions are summed with no further correction into `headers_commission_outputs`, which directly becomes new spendable balance (headers-commission outputs are treated like normal MC outputs with no consuming input on the other side), so any positive rounding excess is newly created value rather than a redistribution of an existing pot. [2](#0-1) 

This is structurally analogous to the Salty.io finding: a value meant to be split across multiple recipients is rounded per-recipient rather than accounted for with a single "round up once, round down elsewhere" or "remainder-tracking" mechanism, so the split can silently drift in the recipients' favor and against the protocol's actual pool of commission.

### Impact Explanation
If the rounding excess can be reliably produced and is not clawed back elsewhere, headers-commission distribution silently creates value beyond what parent units actually paid into headers_commission, i.e., a supply-inflation vector reachable purely by an ordinary unit author setting `earned_headers_commission_recipients`. Because this runs as part of routine core-protocol MC-stability processing (not a witness/hub-only operation), any full node computing balances is exposed to the drift, which over many units/recipients could accumulate to a non-negligible amount of unbacked byte balance.

### Likelihood Explanation
Reachable by any address that authors a unit and wins headers commission for a child unit while specifying `earned_headers_commission_recipients` with many small-share entries — no special privilege is required. The magnitude of leaked value from a single unit is small (bounded by roughly half a byte per additional recipient), so exploitation requires repeating the pattern across many winning units/recipients to accumulate a material effect, similar to the "cumulative effect" characterization in the original report.

### Recommendation
Do not round each recipient's share independently. Track a running remainder while distributing `full_amount` across recipients (e.g., round down for all but the last recipient and assign the last recipient `full_amount - sum(previous rounded amounts)`), or use a single deterministic rounding rule (always round down, i.e., `Math.floor`) and carry any leftover into a protocol-owned residual bucket rather than crediting it to the last-considered recipient's up-rounding. This guarantees `sum(recipient_amounts) <= full_amount` for every payer unit, exactly mirroring the "round the removable/creditable component down in favor of the protocol" fix recommended in the original Salty.io report.

### Proof of Concept
I was unable to fully verify the exact bounds `validation.js` imposes on the number and granularity of `earned_headers_commission_recipients` entries (e.g., maximum recipient count, minimum share increment) before running out of investigation iterations, so I cannot state a concrete numeric worst case (e.g., "N recipients each round up by X, yielding Y excess bytes per unit"). This should be confirmed against the exact validation constraints in `validation.js` (search for `earned_headers_commission_recipients`/`earned_headers_commission_share`) to determine the maximum achievable rounding drift per unit before treating this as fully confirmed.
