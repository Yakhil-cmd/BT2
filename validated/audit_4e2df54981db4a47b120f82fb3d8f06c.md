### Title
Webhook signature verification is scoped to a different payload field than the one used to select the repository to act on, allowing cross-organization forged events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate `X-Hub-Signature` based on `repository_owner`, which is read from the request payload itself (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). The HMAC signature only proves that *some* configured GitHub organization signed the payload with its own secret — it does not bind that organization to the `repository.full_name` field that the event handlers subsequently use to decide which `Stack`/`Repository` to act on.

### Finding Description
`verify_signature` in [1](#0-0)  does:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

where `repository_owner` is derived purely from attacker-controlled payload content: [2](#0-1) .

Every webhook handler, however, resolves the target repository/stack using a *different* payload field, `repository.full_name`, via `Handler#stacks`/`Handler#repository_name`: [3](#0-2) .

Shipit supports multiple independently configured GitHub organizations, each with its own `webhook_secret` (e.g. `somegithuborg`, `someothergithuborg` in [4](#0-3) ). Because there is a single shared `/webhooks` endpoint that dispatches by event type only, and the signing-secret lookup key (`repository.owner.login`) and the acting key (`repository.full_name`) are two unrelated JSON fields inside the same unauthenticated JSON body, nothing cryptographically ties them together.

This reproduces the exact bug class from the report: two logically-related values (here, "the org whose secret signed this request" and "the repository the request claims to be about") are expected to correspond, but the code never checks/enforces that correspondence — it only validates one of them and blindly trusts the other for the actual write.

### Impact Explanation
An attacker who legitimately controls one configured GitHub organization/app in `Shipit.github` config (i.e., they can generate valid webhook deliveries signed with *their own* `webhook_secret`) can craft a raw JSON body where:
- `repository.owner.login` (or `organization.login`) = their own org → signature check passes using their own secret.
- `repository.full_name` = `"victim-org/victim-repo"` → used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. to look up and mutate a completely different, unrelated `Stack`.

This lets the attacker forge events for a repository they do not own/control, e.g.:
- `push` → enqueues `GithubSyncJob` for the victim stack: [5](#0-4) 
- `status` → creates fabricated commit statuses on a victim commit: [6](#0-5) 

Forged/fabricated commit statuses and sync triggers on a victim's stack can influence deploy/merge gating decisions and stack state that Shipit trusts as authentic GitHub data, constituting a cross-repository write / spoofed-authority action performed by an unrelated, unprivileged (relative to the victim repo) org.

### Likelihood Explanation
Exploitability requires the attacker to control at least one legitimately configured GitHub organization entry in the deployment's `Shipit.github` multi-org configuration (so they have a real, valid `webhook_secret` to sign with) — this is a realistic scenario for any Shipit deployment that onboards multiple orgs/teams, which the config format explicitly supports. No access to the victim's secret, `GITHUB_TOKEN`, or a Shipit session/API token is needed; the request is a plain unauthenticated HTTP POST to `/webhooks` with a self-signed body.

### Recommendation
Bind the signing-secret selection and the acting-repository field together instead of trusting two independent, non-cross-checked payload fields:
- After verifying the signature with the app selected via `repository_owner`, additionally verify that `repository.full_name`'s owner segment matches the same `repository_owner`/organization that supplied the secret (reject if they diverge), or
- Look up the `Repository`/`Stack` first from `repository.full_name`, derive its owning organization from that authoritative record, and use that organization to select the `webhook_secret` for verification — rather than trusting the payload's own `repository.owner.login`/`organization.login` field.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` (attacker-controlled GitHub App/secret) and `victim-org` (has a `Stack` tracking `victim-org/victim-repo`).
2. Attacker crafts a `status` (or `push`) webhook JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s own `webhook_secret` (which they legitimately know) over the raw body.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against the attacker's own secret [1](#0-0) .
6. `StatusHandler#process` then runs against `params.sha` and creates/updates a `Status` for the victim's commit, unrelated to `attacker-org` [6](#0-5) , demonstrating the org that authenticated the signature diverges from the repository that gets written.
