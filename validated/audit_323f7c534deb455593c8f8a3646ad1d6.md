### Title
Loose (`!=`) comparison of `signed_message` against contract `title` allows signature content to diverge from the accepted contract text - ([File: wallet.js])

### Summary
When a peer responds to a `prosaic_contract_offer` or `arbiter_contract_offer` with an `accepted` status, the wallet validates the peer's cryptographic signature over a `signed_message` object and then checks that the signed content equals the contract's `title`. The equality check uses JavaScript's loose `!=` operator rather than a strict, type-and-value-safe comparison, and `signed_message` itself is not constrained to be a string by `signed_message.js`'s `validateSignedMessage`. This mirrors the CVE-2018-18509 bug class: a cryptographically valid signature is accepted as covering content that a human/consuming code path interprets as the contract's title, even though the actual signed payload can be a different JS value that only *coerces* to the same value under `==`/`!=` semantics.

### Finding Description
`validateSignedMessage` only requires `signed_message` to be present (`'signed_message' in objSignedMessage`) and does not enforce it to be a string: [1](#0-0) 

The unit hash that is actually signed is computed over the full `objSignedMessage`, so a signature is only valid for the exact JS value/type placed in `signed_message` (e.g. an array `[]`, a number `0`, an object, etc.), not for its *string coercion*.

In `wallet.js`, after validating the signature cryptographically, the code accepts the peer's response as proof that they signed the contract `title` using a loose comparison: [2](#0-1) [3](#0-2) 

Because `!=` performs type coercion, a peer (the contract counterparty — an unprivileged actor able to send `arbiter_contract_response`/`prosaic_contract_response` device messages) can produce a `signed_message` value that is loosely-equal to `objContract.title` (e.g. an empty array coerces to `""`, and `"" == []` is `true` in JS; other numeric/string coercions are also possible depending on the title text) while cryptographically signing a completely different value than the actual title string. `validateSignedMessage` will still accept this as a properly signed message from `objContract.peer_address`, and the wallet will mark the contract `accepted`, storing/emitting `objSignedMessage` as proof of agreement.

### Impact Explanation
The signed proof-of-agreement (used for `prosaic_contract`/`arbiter_contract`, including arbiter-mediated shared-address fund release) can be crafted so that the cryptographic signature does not actually cover the displayed/agreed contract text, while the code path treats it as valid consent to that title. This is a direct code-level analog to CVE-2018-18509: verifiers see a validly signed acceptance of "contract text X" while the attacker actually signed a different, non-string value. This can be leveraged in arbiter disputes or downstream consumers of the stored `signed_message` (which is kept as evidence of agreement) to misrepresent what was agreed to, potentially affecting fund release decisions tied to `arbiter_contract` shared addresses — a fund-loss/dispute-manipulation impact reachable purely from a private-payment counterparty sending a device message, with no privileged access required.

### Likelihood Explanation
Likelihood is moderate: it requires the contract `title` (attacker-controlled at offer time or otherwise) to have a value for which some non-string JS type coerces equal to it under `==`. Common cases (empty title `""` vs. `[]`, or numeric-looking titles vs. numbers) are trivially reachable by the same party crafting the original offer or by contract flows where title content is not tightly constrained. Because both `prosaic_contract` and `arbiter_contract` flows share this exact pattern, the bug class is systemic rather than a one-off typo.

### Recommendation
Replace the loose `!=` comparisons with strict equality after confirming `signed_message` is a string (reject non-string `signed_message` values outright), i.e. `typeof objSignedMessage.signed_message !== 'string' || objSignedMessage.signed_message !== objContract.title`. Additionally, consider having `validateSignedMessage` itself enforce that `signed_message` is restricted to expected primitive types (or require callers to specify/validate the expected schema) so that signature verification cannot be decoupled from a canonical content representation.

### Proof of Concept
1. Attacker (contract peer) receives an `arbiter_contract_offer` with `title: ""` (or any title reachable to have a coercion partner).
2. Attacker builds `objSignedMessage = { signed_message: [], authors: [...], ... }`, signs it validly with their key (a normal, valid signature over the actual JS array value).
3. Attacker sends `arbiter_contract_response` with `status: "accepted"` and this `signed_message` package (base64-encoded) as required in the handler.
4. `signed_message.validateSignedMessage` succeeds (signature is valid for the array value actually signed).
5. `wallet.js`'s check `objSignedMessage.signed_message != objContract.title` evaluates `[] != ""` → `false`, so the mismatch check is bypassed and the contract is marked `accepted`, even though the attacker never signed the string `""` (the title) — analogous to how Thunderbird accepted a signature not actually covering the displayed content.
