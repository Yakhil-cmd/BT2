### Title
Webhook signature verification uses an unauthenticated `repository.owner.login`/`organization.login` field to select the GitHub App/secret, decoupling the authenticated organization from the repository actually written to by the event handler - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* `GitHubApp` (and therefore which `webhook_secret`) to use for HMAC validation based on `repository_owner`, a value read directly from the unauthenticated JSON body, before the signature has been verified. Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves the target `Repository`/`Stack` from a *different* field of the same unauthenticated body: `payload.dig('repository', 'full_name')`. Nothing ties these two payload reads together, so the "organization whose secret authenticated this request" and the "repository the handler actually writes state for" are never checked for equality.

### Finding Description
`verify_signature` in [1](#0-0)  computes:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

where `repository_owner` is derived purely from the request body itself: [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (in multi-org deployments, `secrets.github` is keyed by organization, each with its own optional `webhook_secret`) via [3](#0-2) .

Critically, `verify_webhook_signature` treats a missing `webhook_secret` as automatic success: [4](#0-3) 
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Meanwhile, every `Handler` subclass (which actually performs the mutating action - syncing commits, creating statuses, archiving/merging pull requests, etc.) resolves the target repository from a *separate* JSON path in the same unverified body: [5](#0-4) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` then acts on `stacks` using an attacker-controlled `after` SHA: [6](#0-5) .

Because `repository_owner` (used to pick the verifying GitHub App/secret) and `repository.full_name` (used to pick the target `Repository`/`Stack`) are read independently from the same untrusted body, a legitimate GitHub-originated webhook always keeps them consistent, but nothing in the engine enforces that consistency. In a multi-organization deployment (a documented, supported configuration - see `config/secrets.development.shopify.yml` / `docs/setup.md` "Using Multiple Github Applications"), each organization can independently have a `webhook_secret` set or left blank. If **any** configured organization has no `webhook_secret` (which the setup docs explicitly mark as optional), an attacker can craft a POST to `/webhooks` with:
- `X-Github-Event: push`
- Body: `repository.owner.login` (or `organization.login`) set to the org with no secret (verification auto-succeeds), and `repository.full_name` set to `AnotherOrg/victim-repo` (a *different*, properly secured organization that has a real `Stack` configured).

`verify_signature` authenticates against the unsecured org's (non-existent) secret and passes unconditionally, yet `PushHandler` (and any other handler: `status`, `check_suite`, `pull_request` handlers, etc.) subsequently acts on the victim repository resolved from `full_name`, entirely bypassing that victim organization's `webhook_secret`.

This breaks the binding: `authenticated_organization (via GithubApp secret selected by repository_owner) == organization_of_repository_actually_written (via repository.full_name in Handler)`. The equality is assumed but never enforced.

### Impact Explanation
An attacker can forge GitHub webhook events (push, status, check_suite, pull_request state changes) for any repository/stack configured in the Shipit instance, as long as at least one configured GitHub organization lacks a `webhook_secret`. This can:
- Trigger `GithubSyncJob` with an attacker-chosen `expected_head_sha` via the forged `push` event, causing Shipit to sync arbitrary commit state for a stack it doesn't control the org of.
- Forge `status`/`check_run` events that mark commits as `success`, which feeds directly into `MergeRequest#all_status_checks_passed?` [7](#0-6)  and `ProcessMergeRequestsJob`, which auto-merges pending pull requests once CI is (falsely) reported green [8](#0-7) , and can also trigger continuous-deployment deploys on transition to `success`.

This maps to the impact categories "unauthorized deploy, rollback or merge" and "escalation ... unauthenticated ... task streams" listed as High/Critical in the program rules.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` set - an explicitly documented, supported configuration (`docs/setup.md`, `config/secrets.development.shopify.yml`). No credentials, tokens, or privileged access are required by the attacker; only network access to the public `/webhooks` endpoint and knowledge of one victim repository's `full_name`.

### Recommendation
Do not select the verifying GitHub App/secret from unauthenticated payload data alone. After identifying candidate organization(s) from the payload, re-verify that the same organization also owns the `repository.full_name`/`organization.login` used by the handler, and reject the request if they diverge. Additionally, do not implicitly treat "no configured webhook_secret" as an automatic pass when the engine is configured with multiple organizations sharing one webhook endpoint — require an explicit secret per organization in multi-org mode, or fail closed rather than open.

### Proof of Concept
Given a Shipit instance configured with two organizations, `UnsecuredOrg` (no `webhook_secret`) and `SecuredOrg` (has `webhook_secret` and an active `Stack` for `SecuredOrg/victim-repo`):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "SecuredOrg/victim-repo",
    "owner": { "login": "UnsecuredOrg" }
  }
}
```

1. `WebhooksController#repository_owner` returns `"UnsecuredOrg"`.
2. `Shipit.github(organization: "UnsecuredOrg")` returns a `GitHubApp` with `webhook_secret == nil`.
3. `verify_webhook_signature` returns `true` unconditionally (no signature header needed).
4. `PushHandler.call(params)` resolves `Repository.from_github_repo_name("SecuredOrg/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on `SecuredOrg`'s stack despite its `webhook_secret` never being checked.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
