### Title
`StatusHandler#process` updates commit status by `sha` alone, without verifying `payload_repository == stack.repository`, enabling cross-repository forged CD deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` for every match, with no check that the webhook's `repository.full_name` matches the `stack.repository.full_name` of the commit/stack being updated. This means `Commit#schedule_continuous_delivery` can fire for a stack whose `deployable?` transition was driven by a status event that never actually originated from that stack's own repository.

### Finding Description
The broken binding: the code should enforce `payload.dig('repository','full_name') == commit.stack.repository.full_name` before calling `commit.create_status_from_github!(params)`, but it never does. [1](#0-0) 

Trace:
- The base `Handler` class exposes a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, using `payload.dig('repository', 'full_name')`. [2](#0-1) 
- `StatusHandler#process` does **not** use this helper. It queries `Commit.where(sha: params.sha)` directly and updates every matching `Commit` row across the entire database, regardless of which repository the webhook payload claims to be from. [1](#0-0) 
- `Commit#create_status_from_github!` (via `add_status`) creates a `Status`, and on a state transition into `success`, triggers `Hook.emit(:deployable_status, ...)` and calls `stack.schedule_merges`. [3](#0-2) 
- `Commit#deployable?` becomes true once the newest status is `success?` (assuming not blocked/locked), and `after_commit :schedule_continuous_delivery` on `Commit` create/status update chains into `ContinuousDeliveryJob`, which is what the question references. [4](#0-3) 
- `WebhooksController#verify_signature` only checks that the HMAC signature is valid for the organization named in the payload (`Shipit.github(organization: repository_owner)`); it does not compare `repository.full_name` in the payload against any specific stack, and by design one signature verification covers the entire org, not a specific repo. [5](#0-4) 

Exploit flow: An attacker who owns/controls a repository sharing git history with the victim's tracked repository (e.g., a fork, or any repo containing the same commit object with an identical SHA) can cause GitHub to emit a legitimately-signed `status` webhook event for that SHA from their own repository (e.g., via a CI integration they control, or the GitHub Statuses API on a repo they have push access to). Because `StatusHandler` matches on `sha` alone, this single event updates the `Status`/`Commit` row belonging to the **victim's stack** as well (since `Commit.where(sha: ...)` is not scoped by stack/repository), potentially flipping `deployable?` to true and triggering `schedule_continuous_delivery` → `ContinuousDeliveryJob` → an unauthorized `Deploy` for the victim stack, without any push, PR, or webhook ever having been sent by/for the victim's actual repository.

Existing guards do not catch this: `verify_signature` validates only the org-level HMAC, not per-repository authorization of the SHA; the `ExplicitParameters` schema on `StatusHandler` only validates the *shape* of `sha`/`state`/etc., not their binding to a specific stack; and there is no `require_permission!`/`stacks` scoping check anywhere in `StatusHandler#process`, unlike the pattern the base `Handler` class otherwise provides via `stacks`.

### Impact Explanation
An attacker can cause a `Status` record — and consequently a `Deploy` — to be created for a stack that never authenticated the payload as belonging to its own repository, satisfying "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." This is repeatable against any stack/commit whose SHA also exists in a repository under attacker control (most realistically forks sharing commit history with the victim's tracked repository), and the blast radius spans any Shipit stack with `continuous_deployment: true` tracking a public/forkable repository.

### Likelihood Explanation
Preconditions: the target stack must have CD enabled and otherwise be `deployable?` (no blocking statuses, not locked); the attacker needs a SHA collision, which in practice means the same literal commit object exists in both the victim's tracked repo history and a repo the attacker can trigger a status webhook from (e.g., a fork prior to divergence, or shared upstream commits) — this is a common occurrence on GitHub. The attacker also needs their own repository/org to be a "known organization" to the Shipit instance's webhook signature verification (`Shipit.github(organization:)`), which constrains the attack to Shipit instances that recognize the attacker's org for signature purposes; this is consistent with the stated attacker capability of "emit webhooks from a repository they own." Given these preconditions, the attack is cheap (one webhook/status API call) and repeatable.

### Recommendation
In `StatusHandler#process`, restrict the commit lookup to commits belonging to stacks whose repository matches the payload's `repository.full_name`, e.g., use the `stacks` helper already defined in the base `Handler` class: iterate `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }` (or `Commit.where(sha: params.sha, stack_id: stacks.pluck(:id))`) instead of `Commit.where(sha: params.sha)` unscoped.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/status_handler_test.rb`, or `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks, `victim_stack` (repository `"victim/repo"`, `continuous_deployment: true`) and an unrelated repository record `"attacker/fork"`.
2. Create a `Commit` under `victim_stack` with `sha: "deadbeef"`, and ensure it is otherwise `deployable?` (no blocking statuses).
3. Assert the binding before: `payload_repository = "attacker/fork"`, `stack.repository.full_name = "victim/repo"` → `payload_repository == stack.repository.full_name` is `false`.
4. POST to `/webhooks` with `X-Github-Event: status`, a stubbed valid signature, and body `{ "sha": "deadbeef", "state": "success", "repository": { "full_name": "attacker/fork", "owner": { "login": "attacker" } } }`.
5. Assert `assert_difference 'Deploy.count', 1 do ... end` and/or `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])`, proving a deploy was scheduled for `victim_stack` despite the webhook's repository never matching `victim_stack.repository.full_name`.
6. Confirm the equality check from step 3 remains `false` after the request — demonstrating the binding is violated and unenforced by the code.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
