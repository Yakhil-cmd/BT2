### Title
Unbounded per-message allocation of async validation tasks and listeners in `handlePrivatePaymentChains` - ([File: wallet.js])

### Summary
`wallet.js`'s `handlePrivatePaymentChains` processes the `private_payment_chains` message from a paired device (or hub) by iterating over an attacker-controlled `body.chains` array and, for every chain, kicking off an independent asynchronous validation task and registering a persistent `eventBus.once` listener keyed by unit/payload hash, without any limit on the number of chains or on the number of elements per chain. This mirrors the strawberry-graphql WS bug class: unbounded per-message allocation of concurrent async work/handles with no cap, driven entirely by client input.

### Finding Description
`handlePrivatePaymentChains(ws, body, from_address, callbacks)` only validates the *shape* of `body.chains` (non-empty array of non-empty arrays with well-formed elements) but never bounds `arrChains.length` or the length of each individual chain `c`: [1](#0-0) 

For every chain it then, inside `async.eachSeries`, computes a hash, registers a tracking key in `assocValidatedByKey`, and calls `network.handleOnlinePrivatePayment`, which for light clients can go into the `ifQueued` branch, registering a listener via `eventBus.once(key, ...)` that is only ever removed when the corresponding unit is eventually received and validated, or when `cancelAllKeys()` is triggered by a validation failure: [2](#0-1) 

Each queued chain also causes a DB write (`unhandled_private_payments`) and triggers `updateLinkProofsOfPrivateChain` / `rerequestLostJointsOfPrivatePayments`, and (in `network.js`) `savePrivatePayment` inserts a row per submitted private-payment chain unconditionally: [3](#0-2) 

Because `arrChains` can contain an arbitrary number of independently-crafted chains (each with fabricated `unit`, `payload`, `inputs`, `outputs` fields that only need to pass the shallow shape check), a single paired device or hub-relayed message can register an unbounded number of `eventBus.once` listeners, `assocValidatedByKey` entries, and pending DB rows/queued private payments per invocation, with no cap analogous to `constants.MAX_MESSAGES_PER_UNIT`, `MAX_SPEND_PROOFS_PER_MESSAGE`, `MAX_PARENTS_PER_UNIT`, etc. that are enforced elsewhere in the codebase for other unit-level structures.

### Impact Explanation
Repeated or large `private_payment_chains` messages can grow `handledChainsCache`, `assocValidatedByKey`, and the global `eventBus` listener count without bound, and continuously insert rows into `unhandled_private_payments`, causing progressive memory growth and event-loop/DB overhead on the receiving wallet/hub process. In a sustained scenario this can degrade or crash the node process (Denial of Service), matching CWE-400/CWE-770 in the advisory. This does not directly cause double-spend or fund loss, but it can render a wallet or hub unresponsive, i.e., "a network unable to confirm new units" for the affected node while under attack.

### Likelihood Explanation
The `private_payment_chains` message path is reachable by any paired device counterparty (or via a hub relaying messages) without further authentication beyond an established device pairing, and the per-chain and per-element checks are only structural, not quantity-bounded, making the attack straightforward for anyone who can send device messages to a target wallet.

### Recommendation
Add explicit upper bounds (mirroring existing anti-spam constants) on:
- the number of chains accepted per `private_payment_chains` message (e.g., a `MAX_CHAINS_PER_MESSAGE` constant),
- the number of elements per chain,
and reject/rate-limit messages exceeding these bounds before any `eventBus.once` registration or DB insertion occurs. Additionally, ensure listeners registered in the `ifQueued` branch are time-bounded (e.g., via a timeout that removes stale listeners) so a partially-processed chain cannot pin resources indefinitely.

### Proof of Concept
A malicious paired device (or a hub forwarding on its behalf) sends a `private_payment_chains` message with `body.chains` containing a very large array of syntactically-valid-but-otherwise-fabricated single-element chains (minimal shape satisfying the `every` check in lines 959-971). Each chain causes `handlePrivatePaymentChains` to allocate an `assocValidatedByKey` entry and, for light-wallet targets, an `eventBus.once` listener plus an `unhandled_private_payments` row via `savePrivatePayment`, none of which are bounded by count. Repeating this message (or sending one very large message) drives unbounded growth of pending listeners/DB rows and memory usage on the target device/hub process.

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
