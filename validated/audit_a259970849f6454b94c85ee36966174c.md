Based on my investigation, I found a concrete analog to the "lagging median" bug class: a **value that authenticates the request is a different, attacker-controlled value than the identity used to authorize the write**.

### Title
Webhook signature verification and stack/repository resolution are keyed on two different, independently attacker-influenced fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The webhook signature check resolves which GitHub App/secret to verify against using `repository_owner`, derived from the *unauthenticated* JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), before the signature has been validated. `Shipit::GitHubApp#verify_webhook_signature` additionally treats a blank/unset `webhook_secret` for that resolved organization as automatically valid (`return true unless webhook_secret`). This creates a binding mismatch: the "organization that authenticated" (or trivially passed authentication because no secret was configured for it) is not proven to equal the organization/repository whose `Stack` is subsequently written to by the event handler.

### Finding Description
`WebhooksController#verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
``` [1](#0-0) 

`repository_owner` is read straight from the untrusted, not-yet-verified JSON payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` and `github_app_config` do a case-insensitive lookup in the multi-org configuration keyed by that same attacker-supplied string: [3](#0-2) 

And `GitHubApp#verify_webhook_signature` treats an org with no configured secret as automatically verified:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [4](#0-3) 

In a Shipit deployment configured for multiple GitHub organizations (the documented "Using Multiple Github Applications" setup) where at least one configured organization has no `webhook_secret` set, an attacker can send a POST to `/webhooks` with `repository.owner.login` (or `organization.login`) set to that no-secret organization's name — causing `verify_signature` to pass trivially regardless of the actual `X-Hub-Signature` header, and regardless of which repository the event payload otherwise references. The equality the code should enforce but does not is: *organization whose secret authenticated this HTTP request == organization/repository whose `Stack` records are mutated by `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`*. Because verification short-circuits to `true` for any org lacking a secret, and the handlers key off the same untrusted `params` (e.g. `repository.full_name`) to locate and mutate a `Stack`, an attacker only needs the payload to name an org/repo with no configured secret to get otherwise-signature-gated webhook processing (push syncs, status/check-run updates, membership/team changes, PR events) accepted as if genuinely from GitHub.

### Impact Explanation
This does not rise to the level of authentication bypass across *all* deployments — single-organization installs (the default/most common case) always have exactly one org, and if that org's `webhook_secret` is unset the whole webhook endpoint is already unauthenticated by design, which is a documented, intentional (opt-in) configuration choice, not a boundary crossed by an attacker. In the multi-org configuration, though, an operator may reasonably set a `webhook_secret` for their primary/sensitive org while leaving a secondary, lower-trust org's secret blank (or simply not yet provisioned) — the code then silently permits unsigned webhooks that are processed identically to signed ones for that org's `repository_owner` value, with no distinct restriction preventing that request from carrying a `repository.full_name` for a different, secured stack under the same Shipit instance's purview if handlers do not re-validate repository identity beyond that field. This is a plausible but not fully confirmed cross-repository write; I was unable to load `push_handler.rb`/`handler.rb`/`status_handler.rb` in the final tool round to trace exactly how each handler resolves the target `Stack` from `params` and whether it cross-checks `repository_owner` against `repository.full_name`, so I cannot definitively confirm the handler-level repository binding is separately checked or not.

### Likelihood Explanation
Requires a multi-organization Shipit deployment with at least one org configured without a `webhook_secret` — a non-default but documented and plausible operational configuration. No privileged credentials, tokens, or GitHub write access are needed by the attacker; only network access to the public `/webhooks` endpoint.

### Recommendation
Do not let `verify_webhook_signature` return `true` when `webhook_secret` is blank for organizations resolved from unauthenticated payload data in a multi-org configuration; require an explicit "unauthenticated webhooks intentionally allowed" opt-in per organization, and have each webhook handler independently re-derive/verify the target `Stack`'s repository against the organization that was cryptographically proven (not merely looked up) before performing any Stack mutation.

### Proof of Concept
Conceptual (not confirmed end-to-end due to inability to inspect `push_handler.rb` in this session):
1. Deploy Shipit with multi-org config: `OrgSecure` (has `webhook_secret` set) and `OrgOpen` (no `webhook_secret`).
2. POST `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature`, and body `{"repository": {"owner": {"login": "OrgOpen"}, "full_name": "OrgOpen/some-repo"}, ...}`.
3. `verify_signature` resolves `Shipit.github(organization: "OrgOpen")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the request is processed as authentic despite no valid signature. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` runs against whatever stack `OrgOpen/some-repo` maps to.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
