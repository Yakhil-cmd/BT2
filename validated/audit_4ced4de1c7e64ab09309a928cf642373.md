## Analog Found

### Title
Integer/precision overflow in asset denomination cap calculation allows unchecked `count_coins` to corrupt supply accounting - (File: validation.js)

### Summary
CVE-2023-25516 is an integer overflow in unprivileged-reachable input processing that corrupts internal accounting (leading to further impact). The closest reachable analog in ocore is in `validateAssetDefinition()`, where an unprivileged asset issuer can post an `asset` message whose `denominations` array contains a `count_coins` value that is validated only as a positive integer with no upper bound, while it is multiplied against `denomination` (itself bounded by `MAX_CAP`) and accumulated into `total_cap_from_denominations` using plain JavaScript number arithmetic.

### Finding Description
In `validateAssetDefinition`, each denomination entry is validated as: [1](#0-0) 

`denomInfo.denomination` is checked against `constants.MAX_CAP`, but `denomInfo.count_coins` is checked only with `isPositiveInteger`, with **no upper bound**: [2](#0-1) 

Since `count_coins` and `denomination` are unbounded/bounded-but-large 53-bit-range integers respectively, `count_coins * denomination` can exceed `Number.MAX_SAFE_INTEGER` (2^53-1). JavaScript numbers are IEEE-754 doubles, so this operation silently loses integer precision (rounds to the nearest representable double) rather than throwing — the classic "integer overflow" bug class from the CVE, adapted to a scripting-language accounting context rather than a kernel memory-safety context.

The resulting (possibly imprecise) `total_cap_from_denominations` is then compared against the declared `payload.cap`: [3](#0-2) 

Because `payload.cap` is separately bounded to `<= MAX_CAP`: [4](#0-3) 

An attacker who crafts `count_coins`/`denomination` pairs across multiple denomination tiers can attempt to make the *rounded* floating-point sum coincidentally equal a `cap` value at or under `MAX_CAP`, even though the true (arbitrary-precision) sum of `count_coins * denomination` across all tiers is far larger than the declared cap. This creates a discrepancy between the value nodes accept as "cap matches declared denominations" and the actual enumerable supply implied by the denomination table.

### Impact Explanation
If downstream issuance/consumption logic (e.g., `indivisible_asset.js`, `writer.js`, or per-denomination issuance limits) relies on the assumption that `cap === sum(count_coins * denomination)` holding as validated at definition time, a successful precision collision could let an asset definer claim a small, cap-compliant asset while the denomination table actually permits issuing more distinct coin units than the cap should allow — a supply-inflation vector reachable purely by an unprivileged asset issuer posting a single `asset` definition unit, no privileged party needed.

### Likelihood Explanation
Exploitability is bounded by the difficulty of engineering `count_coins`/`denomination` combinations whose IEEE-754-rounded sum lands exactly on an attacker-chosen small `cap` value while the true sum differs — this requires precise construction but is a well-known class of floating-point/large integer collision attacks and is fully within the reach of a single unprivileged asset-definition poster (no special role required). Constants such as `MAX_DENOMINATIONS_PER_ASSET_DEFINITION` limit the number of tiers, which constrains but does not eliminate the search space, since `count_coins` itself is completely unbounded.

### Recommendation
Bound `denomInfo.count_coins` (e.g., by `constants.MAX_CAP` or by `constants.MAX_CAP / denomInfo.denomination`), and validate the running `total_cap_from_denominations` at every iteration against `constants.MAX_CAP`, rejecting the unit if the accumulator would exceed the safe integer range before the multiplication/addition is performed, similar to the existing `MAX_BALANCE` overflow guard used in `aa_composer.js`: [5](#0-4) 

### Proof of Concept
Post an `asset` definition message with `fixed_denominations: true`, `cap: <small value X ≤ MAX_CAP>`, and a `denominations` array where at least one entry has a `count_coins` value large enough (e.g., near `Number.MAX_SAFE_INTEGER / denomination`) that `count_coins * denomination` summed across entries produces IEEE-754 rounding that equals `X`, while the true arbitrary-precision sum is substantially larger — passing the check at `validation.js:2790` despite the denomination table describing more issuable coin units than the declared cap.

### Note on verification limits
I was not able to fully trace how `count_coins` is consumed downstream (e.g. in `indivisible_asset.js` issuance logic or `writer.js`) within the available tool budget, so I cannot fully confirm whether a separate, independent enforcement mechanism there would still bound total issuance regardless of this precision-loss discrepancy. This should be verified before treating the impact as certain (supply inflation) rather than a definition-time accounting inconsistency.
