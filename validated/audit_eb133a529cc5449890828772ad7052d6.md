### Title
Unbounded recursive query in `readAllControlAddresses` allows infinite loop / resource-exhaustion DoS via cyclic shared-address definitions - ([File: wallet_defined_by_addresses.js])

### Summary
`readAllControlAddresses` in `wallet_defined_by_addresses.js` recurses over `shared_address_signing_paths` to collect "control addresses" (addresses that co-sign a shared address) without any cycle detection, visited-set tracking, or depth limit. A shared/multi-signature address definition can be constructed such that address A's signing path uses address B as a signer, and B's signing path uses A (or a longer cycle A→B→C→A), which is accepted by `handleNewSharedAddress`/`addNewSharedAddress` because `Definition.validateDefinition` validates a single definition tree and does not check for cross-referencing address cycles among independently-registered shared addresses stored in `shared_address_signing_paths`.

### Finding Description
`readAllControlAddresses`: [1](#0-0) 
recursively calls itself with `arrControlAddresses` (the newly discovered "member" addresses of `arrAddresses`) until the query returns zero rows. There is no `assocKnownAddresses` set or depth counter to stop re-visiting addresses already seen. If the shared-address graph contains a cycle (address X is signed by shared address Y, and Y is (indirectly) signed by X), the query at each recursion level will keep returning non-empty rows forever, causing infinite recursion/an unbounded chain of nested async DB queries — never terminating and consuming memory/CPU/DB connections, i.e., the classic "infinite loop on crafted input" bug class from CVE-2018-20099 (there an image parser looped forever on crafted structure; here the wallet's address-graph walker loops forever on a crafted set of shared-address definitions).

Reachability: a peer (paired device / correspondent) can push a `new_shared_address` device message that is handled by `handleNewSharedAddress`: [2](#0-1) 
This only validates that the definition hash matches, that signer addresses match the definition's paths, and calls `Definition.validateDefinition`/`validateAddressDefinition`: [3](#0-2) 
None of this validates that the newly registered shared address, combined with previously registered shared addresses (from other peers/devices), does not form a signing cycle in `shared_address_signing_paths`. Once such addresses are persisted via `addNewSharedAddress`, any later call to `readAllControlAddresses(conn, [address], ...)` (e.g. when determining which addresses/devices need to be notified of new transactions/private payments involving a shared address) triggers unbounded recursion.

### Impact Explanation
This is reachable by an unprivileged paired device sending crafted `new_shared_address` messages that establish a cyclic shared-address control graph. Once triggered, `readAllControlAddresses` never completes, hanging the wallet node's event loop / async chain and exhausting DB connections/memory — a denial-of-service that can prevent the node from confirming new units, processing private payments, or otherwise operating (matches the "network unable to confirm new units" / node freezing bar for Medium severity, analogous to the infinite loop DoS in the CVE).

### Likelihood Explanation
Medium likelihood: requires only that an attacker be a paired device (correspondent) capable of sending `new_shared_address` device messages — a bar met by "asset issuer / private-payment counterparty or paired device can reach" scope. Constructing two or three shared addresses whose signing paths reference each other back is not prevented by the existing validation logic, which validates each definition tree independently and never queries prior shared-address graphs for cycles.

### Recommendation
Add a visited-address set (or maximum recursion depth) to `readAllControlAddresses` so that any address already processed in the traversal is not re-queried, guaranteeing termination regardless of cycles in `shared_address_signing_paths`. Additionally, when accepting a new shared address definition in `handleNewSharedAddress`/`addNewSharedAddress`, validate that none of the referenced `address` signers create a cycle back to the newly defined address before persisting it.

### Proof of Concept
1. Device D1 creates shared address SA1 whose definition signer set includes address SA2 (as a signer address) via `handleNewSharedAddress`.
2. Device D2 (or the same attacker acting as another correspondent) creates shared address SA2 whose definition signer set includes SA1.
3. Both `handleNewSharedAddress` calls succeed because `Definition.validateDefinition` only checks the definition tree in isolation, not the shared_address_signing_paths graph across addresses.
4. Any subsequent call to `readAllControlAddresses(conn, [SA1], cb)` (used, e.g., when determining who to forward private chains/notifications to for outputs on SA1) will recurse indefinitely: SA1 → discovers SA2 as a control address → SA2 → discovers SA1 → ... never reaching `rows.length === 0`.

Note: I was not able to fully trace every call site of `readAllControlAddresses` (only `wallet_defined_by_addresses.js` and one reference in `wallet.js` were found in the index) to confirm exactly which unprivileged-triggerable operation eventually invokes it after a malicious shared address is registered; this should be verified with a full-repository check (e.g., a Devin session) since index coverage limits may have truncated the call graph in `wallet.js`.

function handleNewSharedAddress(body, callbacks){

		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];

			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");

		});
	});
}

function readAllControlAddresses(conn, arrAddresses, handleLists){
	conn = conn || db;
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, (correspondent_devices.device_address IS NOT NULL) AS have_correspondent \n\
		FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?)", 
		[arrAddresses], 
		function(rows){
			if (rows.length === 0)
				return handleLists([], []);
			var arrControlAddresses = rows.map(function(row){ return row.address; });
			var arrControlDeviceAddresses = rows.filter(function(row){ return row.have_correspondent; }).map(function(row){ return row.device_address; });
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
