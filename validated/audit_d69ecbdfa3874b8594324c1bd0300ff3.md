### Title
Bridge Token Deregistration Without Pending Transfer Validation Permanently Locks Bridged ERC20/ERC721 Assets — (`contracts/service_chain/bridge/BridgeTokens.sol`, `node/sc/api_bridge.go`)

### Summary

`deregisterToken` in `BridgeTokens.sol` and `doDeregisterToken` in `api_bridge.go` remove a token's registration from both the on-chain contract and the Go-level bridge manager without checking whether there are unhandled pending `RequestValueTransfer` events for that token. Any in-flight bridge transfer for the deregistered token becomes permanently unprocessable: the Go bridge manager cannot resolve the counterpart token address, the handle transaction is never submitted, and the user's assets (burned on the source chain in mint/burn mode, or locked in the source bridge in lock mode) are permanently lost.

### Finding Description

The `deregisterToken` function in `BridgeTokens.sol` removes a token from `registeredTokens`, `lockedTokens`, `indexOfTokens`, and `registeredTokenList` with no guard on outstanding pending transfers: [1](#0-0) 

The Go-level API wrapper `doDeregisterToken` mirrors this by deleting the token from both the in-memory `counterpartToken` map and the on-chain contract on both sides of the bridge pair: [2](#0-1) 

When the Go bridge manager processes a pending `RequestValueTransfer` event in `handleRequestValueTransferEvent`, it must resolve the counterpart token address before it can call `handleERC20Transfer` on the destination bridge: [3](#0-2) 

After deregistration, `bi.GetCounterPartToken(tokenAddr)` returns `common.Address{}` (deleted from Go map), and the fallback call to `bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)` also returns `common.Address{}` (deleted from on-chain contract). The function returns the error `"can't get counterpart token from bridge"`, causing the event to be re-queued indefinitely: [4](#0-3) 

Critically, `handleERC20Transfer` on the destination bridge has **no** `onlyRegisteredToken` check — it would succeed if called directly — but the Go manager can never reach that call because the counterpart address lookup fails first: [5](#0-4) 

By contrast, the outbound path `_requestERC20Transfer` correctly enforces `onlyRegisteredToken` and `onlyUnlockedToken`: [6](#0-5) 

### Impact Explanation

**Mint/burn mode (`modeMintBurn = true`):** The user's ERC20 tokens are burned on the source chain at request time. If the token is deregistered before the handle is processed, the corresponding mint on the destination chain never occurs. The user's tokens are permanently destroyed with no compensation.

**Lock/unlock mode (`modeMintBurn = false`):** The user's ERC20 tokens are locked inside the source bridge contract. The handle on the destination chain never executes. The tokens are permanently locked with no recovery path.

The `lowerHandleNonce` on the destination bridge never advances past the stuck nonce, and the `valueTransferRecovery` loop retries the failed event indefinitely without success, consuming bridge operator resources.

### Likelihood Explanation

The trigger is a bridge owner calling `DeregisterToken` (via `subbridge_deregisterToken` RPC) while there are in-flight transfers. This is a realistic operational scenario: an owner migrating to a new token contract, responding to a security incident, or performing routine maintenance may deregister a token without first verifying that `requestNonce == lowerHandleNonce` (i.e., all pending transfers are settled). No unprivileged attacker action is required; the owner's own legitimate administrative action causes the loss.

### Recommendation

**Short term:** In `doDeregisterToken` (and/or `deregisterToken` on-chain), add a check that the source bridge's `requestNonce` equals the destination bridge's `lowerHandleNonce` before allowing deregistration. If pending transfers exist, revert with a descriptive error.

**Long term:** Introduce a two-phase deregistration: first lock the token (preventing new requests) and wait for all pending transfers to be handled, then allow full deregistration. Add a view function that returns the count of unhandled pending transfers for a given token to assist operators.

### Proof of Concept

1. Deploy a bridge pair in mint/burn mode with token `T` registered on both sides.
2. User calls `requestERC20Transfer(T, ...)` on the source bridge — tokens are burned, `RequestValueTransfer(nonce=0)` is emitted, `requestNonce` becomes 1.
3. Before the Go bridge manager processes nonce 0, the bridge owner calls `subbridge_deregisterToken` — `doDeregisterToken` removes `T` from both Go maps and both on-chain contracts.
4. The bridge manager calls `handleRequestValueTransferEvent` for nonce 0:
   - `bi.GetCounterPartToken(T)` → `0x000...` (deleted from Go map)
   - `bi.counterpartBridge.RegisteredTokens(nil, T)` → `0x000...` (deleted on-chain)
   - Returns `errors.New("can't get counterpart token from bridge")`
   - Event is re-queued: `bi.AddRequestValueTransferEvents(ReadyEvent[0:])`
5. The recovery loop (`valueTransferRecovery`) detects `requestNonce(1) != lowerHandleNonce(0)` and repeatedly calls `recoverPendingEvents`, which re-submits the same failing event forever.
6. The user's tokens are permanently burned on the source chain with no mint on the destination chain. The destination bridge's `lowerHandleNonce` remains 0 indefinitely.

    function deregisterToken(address _token)
        external
        onlyOwner
        onlyRegisteredToken(_token)
    {
        delete registeredTokens[_token];
        delete lockedTokens[_token];

        uint idx = indexOfTokens[_token];
        delete indexOfTokens[_token];

        if (idx < registeredTokenList.length-1) {
            registeredTokenList[idx] = registeredTokenList[registeredTokenList.length-1];
            indexOfTokens[registeredTokenList[idx]] = idx;
        }
        registeredTokenList.length--;

        emit TokenDeregistered(_token);
    }

func (sb *SubBridgeAPI) doDeregisterToken(cBridgeAddr, pBridgeAddr, cTokenAddr, pTokenAddr common.Address) error {
	if !sb.subBridge.bridgeManager.IsValidBridgePair(cBridgeAddr, pBridgeAddr) {
		return ErrInvalidBridgePair
	}

	cBi, cExist := sb.subBridge.bridgeManager.GetBridgeInfo(cBridgeAddr)
	pBi, pExist := sb.subBridge.bridgeManager.GetBridgeInfo(pBridgeAddr)

	if !cExist || !pExist {
		return ErrNoBridgeInfo
	}

	pTokenAddrCheck := cBi.GetCounterPartToken(cTokenAddr)
	cTokenAddrCheck := pBi.GetCounterPartToken(pTokenAddr)

	if pTokenAddr != pTokenAddrCheck || cTokenAddr != cTokenAddrCheck {
		return errors.New("invalid toke pair")
	}

	cBi.DeregisterToken(cTokenAddr, pTokenAddr)
	pBi.DeregisterToken(pTokenAddr, cTokenAddr)

	cBi.account.Lock()
	defer cBi.account.UnLock()
	tx, err := cBi.bridge.DeregisterToken(cBi.account.GenerateTransactOpts(), cTokenAddr)
	if err != nil {
		return err
	}
	cBi.account.IncNonce()
	logger.Debug("cBridge deregistered token", "txHash", tx.Hash().String(), "cToken", cTokenAddr.String(), "pToken", pTokenAddr.String())

    function _requestERC20Transfer(
        address _tokenAddress,
        address _from,
        address _to,
        uint256 _value,
        uint256 _feeLimit,
        bytes memory _extraData
    )
        internal
        onlyRegisteredToken(_tokenAddress)
        onlyUnlockedToken(_tokenAddress)
    {
        require(isRunning, "stopped bridge");
        require(_value > 0, "zero ERC20 token amount");

        uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);

        if (modeMintBurn) {
            ERC20Burnable(_tokenAddress).burn(_value);
        }

        emit RequestValueTransfer(
            TokenType.ERC20,
            _from,
            _to,
            _tokenAddress,
            _value,
            requestNonce,
            fee,
            _extraData
        );
        requestNonce++;
    }
