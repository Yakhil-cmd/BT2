### Title
CR/newline injection via git tree entry names in `writeTSV` allows terminal output/prompt spoofing - (File: pkg/cmd/repo/read-dir/read_dir.go)

### Summary
`writeTSV` in `pkg/cmd/repo/read-dir/read_dir.go` writes the attacker-controlled `dirEntry.Name` field directly into TSV output with a plain `fmt.Fprintf`, with no escaping of control characters such as `\r`, `\n`, or ANSI/cursor-movement sequences. Because git tree/blob entry names are arbitrary byte strings (only NUL and `/` are disallowed), a malicious repository owner can create a file whose name contains carriage returns or escape sequences that get rendered verbatim by `gh repo read-dir` when its output reaches a terminal (directly or via a later `cat`/pager of the redirected output).

### Finding Description
`fetchTree` in `pkg/cmd/repo/read-dir/http.go` populates `dirEntry.Name` straight from the GraphQL `Tree` entry `Name` field returned by GitHub, with no sanitization: [1](#0-0) . This name is fully attacker-controlled: any user who can commit a file into a repository, fork, or PR branch controls the exact bytes of the tree entry name, and git does not restrict tree entry names beyond forbidding `/` and NUL bytes, so a name containing `\r`, `\n`, or terminal control sequences can be committed with low-level plumbing (e.g. `git mktree`/`update-index`) and pushed to GitHub.

`writeTSV` then writes this name unescaped into the output stream: [2](#0-1) 

This path is taken whenever stdout is not a TTY: [3](#0-2) . Unlike the TTY path (`writeTable`, which uses `tableprinter`), there is no escaping mechanism applied to `e.Name` here. The codebase does have a dedicated mechanism for handling untrusted terminal content (`pkg/iostreams/untrusted.go`), indicating that this is a recognized problem elsewhere in the CLI, but `writeTSV` does not use it.

Because `writeTSV`'s output is typically consumed by scripts, files, or later piped/`cat`'d to a terminal, embedded `\r` characters can overwrite previously "printed" lines and any ANSI escape/cursor-repositioning sequences embedded in the name can manipulate the terminal display when that output is eventually rendered on a TTY (e.g., `gh repo read-dir | cat`, or the output is saved to a file and displayed later). A carefully crafted entry name can therefore redraw a line to look like a trusted `gh` prompt (e.g., `? Paste your GitHub token:`).

### Impact Explanation
This matches a "High: Terminal output/prompt spoofing" impact class. An attacker-controlled repository, fork, or PR branch containing a maliciously named file can cause `gh repo read-dir`'s non-TTY output to contain forged lines (including fake credential prompts) once that output reaches a terminal, potentially tricking a victim into pasting a GitHub token or approving a destructive action they didn't intend to approve.

### Likelihood Explanation
Exploitation requires only that the attacker control the name of a file/blob within a git tree that the victim lists with `gh repo read-dir` (any public repo, fork, or PR ref works), and that the victim's shell/tooling eventually renders that TSV output on a terminal (a very common workflow: piping to `cat`, `less`, or saving/inspecting the output later). Constructing such filenames requires only plumbing-level git commands, not any elevated privilege, so the attack is fully repeatable and low-cost for the attacker.

### Recommendation
Sanitize `e.Name` (and any other attacker-controlled string values) in `writeTSV` before emitting it — strip or escape `\r`, `\n`, and other C0 control/ANSI escape characters (e.g., via a shared "untrusted text" sanitizer such as the pattern already used in `pkg/iostreams/untrusted.go`), and apply this consistently to all reachable rendering paths (`writeTSV` and `writeTable`) for names, and other free-text values sourced from remote data.

### Proof of Concept
Go unit test outline:
```go
func TestWriteTSV_EscapesControlCharacters(t *testing.T) {
    ios, _, out, _ := iostreams.Test()
    dir := &repoDir{
        Entries: []dirEntry{
            {Type: "file", Name: "safe.txt\r\x1b[2K? Paste your GitHub token: ", Size: 10},
        },
    }
    err := writeTSV(ios, dir)
    require.NoError(t, err)
    rendered := out.String()
    require.NotContains(t, rendered, "\r")
    require.NotContains(t, rendered, "\x1b[") // no cursor-movement / ANSI escape sequences
}
```
Expected current (vulnerable) behavior: the test fails because `\r` and the escape sequence pass through unmodified into `out`. After applying sanitization to `e.Name` in `writeTSV`, the assertions should pass.

func writeTSV(io *iostreams.IOStreams, dir *repoDir) error {
	var sb strings.Builder
	for _, e := range dir.Entries {
		fmt.Fprintf(&sb, "%s\t%s\t%s\t%d\n", e.Type, e.Name, e.modeOctal(), e.Size)
	}
	_, err := io.Out.Write([]byte(sb.String()))
	return err
}
