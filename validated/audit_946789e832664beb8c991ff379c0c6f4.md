### Title
`DenyReserveTransferToRelayChain` is applied only at the top level (not `DenyRecursively`-wrapped) on Asset Hub Polkadot, allowing a nested reserve-transfer-to-Relay-Chain instruction to bypass the deny filter - (File: system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs)

### Summary
The `Barrier` on Asset Hub Polkadot wraps `DenyReserveTransferToRelayChain` directly in `DenyThenTry`, without the `DenyRecursively` combinator that other chains in this same repository (e.g. `bridge-hub-polkadot`, `bulletin-polkadot`) already use for the identical filter. `DenyReserveTransferToRelayChain::should_execute` only scans the top-level instruction list of a message for `InitiateReserveWithdraw`/`DepositReserveAsset`/`TransferReserveAsset` targeting the Relay Chain, so nesting such an instruction inside `SetAppendix`, `SetErrorHandler`, or `ExecuteWithOrigin` at the top level is not inspected.

### Finding Description
`DenyReserveTransferToRelayChain` (defined upstream in `xcm-builder`, used here at [1](#0-0) ) implements `ShouldExecute::should_execute` by iterating the flat top-level instruction slice passed to it and pattern-matching for reserve-transfer instructions whose destination/reserve is the Relay Chain. This iteration does not descend into instruction lists nested inside other instructions (`SetAppendix(Xcm)`, `SetErrorHandler(Xcm)`, `ExecuteWithOrigin { xcm, .. }`), because those nested programs are separate `Vec<Instruction>` fields, not part of the outer slice being iterated.

Within this repository, the exact same filter is used inconsistently:
- Asset Hub Polkadot/Kusama, Collectives, Coretime (Polkadot/Kusama), People (Polkadot/Kusama), and Encointer use the bare `DenyReserveTransferToRelayChain` [2](#0-1) .
- Bridge Hub Polkadot and Bulletin Polkadot wrap the same filter in `DenyRecursively<...>` [3](#0-2) [4](#0-3) .

`DenyRecursively` exists specifically to walk into nested XCM programs (appendix/error-handler/`ExecuteWithOrigin`) and re-apply the wrapped deny filter to them. Its selective adoption for only two chains, while Asset Hub Polkadot (the highest-value chain, holding the bulk of DOT/asset liquidity) retains the non-recursive version, is the concrete gap the question asks about.

An unprivileged, signed user can reach the `Barrier` directly via `pallet_xcm::execute`, which lets a signed origin submit an arbitrary local `Xcm` program for immediate local execution through the same `xcm_executor::Config::Barrier` used for XCMP/DMP-originated messages. By crafting a top-level program such as:
```
WithdrawAsset(..) ->
SetAppendix(Xcm(vec![DepositReserveAsset { dest: RelayChainLocation, .. }]))
```
or wrapping the reserve-transfer instruction inside `ExecuteWithOrigin { descendant_origin: None, xcm: Xcm(vec![InitiateReserveWithdraw { reserve: RelayChainLocation, .. }]) }`, the outer instruction seen by `DenyReserveTransferToRelayChain::should_execute` is `SetAppendix`/`ExecuteWithOrigin`, not the reserve-transfer instruction itself — the `matches!` check against `InitiateReserveWithdraw | DepositReserveAsset | TransferReserveAsset` never fires, and `DenyThenTry` falls through to the "allow" side of the tuple (e.g. `AllowTopLevelPaidExecutionFrom<Everything>`), and execution proceeds into the appendix/nested program where the disallowed reserve-transfer instruction actually runs.

### Impact Explanation
If reachable and unweighted, this would let an unprivileged user bypass a chain-configured policy explicitly designed to disallow reserve transfers of the native/foreign asset to the Relay Chain from Asset Hub via a specific instruction path (as opposed to `LimitedReserveTransferAssets`/teleport, which are the sanctioned paths). This does not by itself create asset duplication or theft — the underlying `AssetTransactor`/reserve accounting still runs correctly and burns/moves the sender's own assets — but it is a deliberate protocol-level restriction whose bypass constitutes a broken invariant of the "Filters ... must not be bypassable by normal users" category, and could set an unintended trust/reserve relationship in motion between Asset Hub and the Relay Chain outside the reviewed/allowed path.

### Likelihood Explanation
This requires no privileged access: any signed account with sufficient balance for fees/weight can call `pallet_xcm::execute` with a hand-crafted `Xcm` program. It is fully attacker-controlled and repeatable. The feasibility depends on:
1. Confirmed reachability of `pallet_xcm::execute` with `SendXcm`/local execution not additionally filtered (`XcmExecuteFilter`/`SafeCallFilter`) in a way that blocks `SetAppendix`/`ExecuteWithOrigin`/reserve-transfer instructions — this could not be fully verified from the indexed content of this repo (the `pallet_xcm::Config` block for Asset Hub Polkadot, including `XcmExecuteFilter`, was not retrievable in the available context).
2. Whether the actual weight/fee checks (`WithComputedOrigin`, `AllowTopLevelPaidExecutionFrom`) that run after the deny check would still permit the nested instructions to execute with sufficient weight — this is a separate, existing barrier layer that must also be satisfied but does not re-check the deny condition.

Given the demonstrated inconsistency in this same codebase (identical filter deliberately hardened with `DenyRecursively` elsewhere but not on Asset Hub Polkadot/Kusama), this is a credible configuration gap rather than a purely theoretical one.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` in `DenyRecursively<..>` for Asset Hub Polkadot and Asset Hub Kusama (and other affected system chains: Collectives, Coretime, People, Encointer), matching the pattern already used for Bridge Hub Polkadot and Bulletin Polkadot:
```rust
pub type Barrier = TrailingSetTopicAsId<
    DenyThenTry<
        DenyRecursively<DenyReserveTransferToRelayChain>,
        ( ... )
    >,
>;
```

### Proof of Concept
xcm-emulator / integration test plan for Asset Hub Polkadot:
1. Fund a test account on Asset Hub Polkadot with DOT.
2. Construct message A (control, should be denied): top-level `DepositReserveAsset { dest: RelayChainLocation, .. }` — assert `pallet_xcm::execute` fails with `Barrier`/`Unsupported` error.
3. Construct message B (nested via `SetAppendix`): `WithdrawAsset(..)`, `ClearOrigin`, `SetAppendix(Xcm(vec![DepositReserveAsset { dest: RelayChainLocation, assets: All, xcm: Xcm(vec![]) }]))` as the sole top-level program, submitted via `pallet_xcm::execute(origin, VersionedXcm::from(message_b), max_weight)`.
4. Construct message C (nested via `ExecuteWithOrigin`): top-level `ExecuteWithOrigin { descendant_origin: None, xcm: Xcm(vec![InitiateReserveWithdraw { reserve: RelayChainLocation, assets: All, xcm: Xcm(vec![]) }]) }`.
5. Assert for B and C: with the current (non-recursive) `Barrier`, execution is NOT rejected by the deny filter (i.e., `Barrier::should_execute` returns `Ok(())`) and the nested reserve-transfer instruction is subsequently attempted during execution — demonstrating the bypass.
6. Apply the recommended fix (`DenyRecursively<DenyReserveTransferToRelayChain>`) and re-run B and C, asserting they are now rejected identically to message A.

Note: full confirmation of end-to-end asset movement (not just barrier bypass) and confirmation of `XcmExecuteFilter`/fee-weight gating for `pallet_xcm::execute` on Asset Hub Polkadot could not be completed from the available indexed file contents; a Devin session with full repository access would be needed to inspect `impl pallet_xcm::Config for Runtime` in `system-parachains/asset-hubs/asset-hub-polkadot/src/lib.rs` and confirm the exact `XcmExecuteFilter` value before treating this as fully proven end-to-end.
