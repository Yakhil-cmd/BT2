Unbounded attacker-controlled `proof: Vec<Vec<u8>>` in `remote_proxy` charges fixed weight regardless of proof size, allowing weight/PoV under-pricing DoS - (File: pallets/remote-proxy/src/lib.rs)

### Summary
`Pallet::remote_proxy` / `Pallet::do_remote_proxy` accept a caller-supplied `RemoteProxyProof::RelayChain { proof: Vec<Vec<u8>>, .. }` whose size is only bounded by the runtime's `BlockLength` extrinsic-length limit (5 MiB, 75% for `Normal` class), yet the `#[pallet::weight]` annotation for `remote_proxy` charges only a fixed benchmarked constant (`WeightInfoOf::<T,I>::remote_proxy()`) plus the inner call's declared weight, with no term proportional to `proof.len()`/byte size. `sp_trie::StorageProof::new(proof).into_memory_db()` hashes and inserts every supplied node into a `MemoryDB` before `read_trie_value` even attempts path traversal, so the actual compute/PoV cost scales with the full submitted proof size while the declared weight does not.

### Finding Description
`Pallet::remote_proxy` (`pallets/remote-proxy/src/lib.rs:293-304`) is dispatched by any signed account and forwards to `Pallet::do_remote_proxy` (`pallets/remote-proxy/src/lib.rs:394-463`). For the `RelayChain` proof variant, the code does:
```
let db = sp_trie::StorageProof::new(proof).into_memory_db::<RemoteHasherOf<T, I>>();
let value = sp_trie::read_trie_value::<sp_trie::LayoutV1<_>, _>(&db, &storage_root, &key, None, None)
``` [1](#0-0) 

`into_memory_db` hashes and stores every node blob supplied in `proof: Vec<Vec<u8>>` into a `MemoryDB` unconditionally — this happens before any verification that a node is actually on the path from `storage_root` to `key`. Only afterward does `read_trie_value` walk the (possibly tiny) real path and returns `Error::InvalidProof` on failure via `.ok().flatten().ok_or(...)` [2](#0-1) .

The declared weight for this call is:
```
#[pallet::weight({
    let di = call.get_dispatch_info();
    (WeightInfoOf::<T, I>::remote_proxy()
        .saturating_add(T::DbWeight::get().reads_writes(1, 1))
        .saturating_add(di.call_weight),
    di.class)
})]
``` [3](#0-2) 
`WeightInfoOf::<T,I>::remote_proxy()` is a fixed constant (e.g. `Weight::from_parts(18_259_000, 0).saturating_add(Weight::from_parts(0, 1846))` for asset-hub-kusama), benchmarked using a small, realistic proof produced by `T::RemoteProxy::create_remote_proxy_proof`, which builds one minimal proxy proof, not a worst-case proof [4](#0-3) [5](#0-4) . Nowhere in the weight formula is there a component proportional to `proof.len()` or the encoded size of `proof`.

The only constraint on `proof` size is the general `frame_system::CheckWeight`/`BlockLength` extrinsic-length limit — 5 MiB total, 75% (`NORMAL_DISPATCH_RATIO`) for `Normal` class [6](#0-5) [7](#0-6)  — which bounds encoded transaction bytes, not weight/compute. A caller can therefore submit `proof` filled with megabytes of structurally-arbitrary byte blobs (each wrapped as a `Vec<u8>` "node"). `StorageProof::new(proof).into_memory_db()` will hash and store all of them (O(total bytes) hashing cost) even though `read_trie_value` will ultimately fail with `InvalidProof` because none of the garbage nodes form a valid path to `key` in `storage_root`. This means the pallet accepts, hashes, and pays DB-insert cost for an amount of data far exceeding what `remote_proxy()`'s constant weight assumes, while the transaction is charged (and block space accounted) only at the fixed benchmark rate plus the cheap inner call's weight (e.g. a `remark`).

No check exists that rejects the extrinsic before this cost is incurred: there's no proof-size cap, no growth of weight/PoV consumption with `proof` size, and no early bail-out based on node count/size before calling `into_memory_db`.

### Impact Explanation
An unprivileged signed account can submit `remote_proxy` extrinsics with an oversized, invalid `proof` (up to the ~3.75 MiB Normal-class extrinsic length budget) paired with a cheap inner call (e.g. `System::remark`). Each such extrinsic is priced at the fixed benchmarked weight (tens of microseconds of ref-time, ~1846 bytes of PoV) but actually forces the node to hash and memory-insert megabytes of proof data before failing with `InvalidProof`. Repeating this across many extrinsics in a block lets an attacker consume real CPU time/PoV disproportionate to the weight accounted against `BlockWeights`/`BlockLength`, degrading block-production throughput and crowding out honest extrinsics — a weight-mispricing/DoS issue scoped to block-fill/queue congestion as described in the question.

### Likelihood Explanation
Feasible with only a funded signed account (transaction fees apply per byte/weight as usual, but the fee model does not offset the compute mismatch since fees are based on declared weight/length, not actual proof-verification cost). The call is fully reachable via the public `remote_proxy` extrinsic; no proxy relationship, XCM, or privileged origin is required — the `proof` can be entirely garbage since the failure (`InvalidProof`) occurs only after the expensive hashing/insertion step. Repeatable per block, limited only by the attacker's balance to pay per-extrinsic fees and the Normal-class length budget.

### Recommendation
Add a weight component to the `remote_proxy`/`remote_proxy_with_registered_proof` extrinsics that scales with the size of the supplied `proof` (e.g., `T::WeightInfo::remote_proxy_proof_size(proof.encoded_size() as u32)` derived from a proper benchmark using worst-case garbage proofs), and/or impose an explicit maximum node count/byte size on `RemoteProxyProof::RelayChain.proof` (enforced before calling `into_memory_db`) consistent with what a legitimate proxy-definition storage proof would realistically require (`sp_trie` proof-size verification typically bounded by trie depth × max node size). Reject oversized proofs early with a dedicated error before performing the DB insertion/hash step.

### Proof of Concept
Rust benchmark/fuzz test plan:
1. Construct `N` `remote_proxy` calls, each with a `RemoteProxyProof::RelayChain { proof: vec![vec![0xAA; MAX_NODE_SIZE]; MAX_NODES], block }` sized close to the Normal-class extrinsic length limit, wrapping a cheap `System::remark` call.
2. Measure wall-clock/PoV of `Pallet::do_remote_proxy` execution for these garbage proofs versus the declared `WeightInfoOf::<T,I>::remote_proxy()` constant.
3. Assert: `actual_measured_weight <= declared_weight` fails (i.e., actual ref-time/PoV significantly exceeds the constant benchmark weight, e.g., >2x or more depending on proof size), proving the declared weight is not a valid upper bound.
4. Integration test: submit a block filled with such extrinsics and confirm block-authoring/import time exceeds the target block time while weight accounting reports the block as under `BlockWeights` limits.
