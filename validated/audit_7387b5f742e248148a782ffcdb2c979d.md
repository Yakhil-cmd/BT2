### Title
Webhook organization used for signature verification is decoupled from the repository the handler writes to, allowing cross-repository status/state forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify a webhook against using the `repository.owner.login` (or `organization.login`) field of the *unverified* JSON body, but the event handlers (e.g. `StatusHandler`, `PushHandler`) resolve the actual `Stack`/`Repository` they act on using a **different** field of the same body — `repository.full_name` — via `Repository.from_github_repo_name`. Nothing ties "the organization whose secret validated this request" to "the repository the handler subsequently writes state for." Combined with `GitHubApp#verify_webhook_signature` returning `true` whenever an organization has no `webhook_secret` configured (a supported, documented configuration for multi-org Shipit installs), an attacker can pick an organization with no configured secret to satisfy `verify_signature`, while pointing `repository.full_name` at a completely different, protected organization/repository tracked by the same Shipit instance.

### Finding Description
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) is read straight from the JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) short-circuits to `true` when no `webhook_secret` is configured for that org:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

- The docs explicitly support multiple, independently-configured GitHub Apps/organizations in one Shipit instance, each with its own (optional) `webhook_secret` (`docs/setup.md:181-209`, `docs/setup.md:119`).


- After the (org-scoped) signature check passes, `create` dispatches `params` — the same raw JSON — to handlers that resolve the target repository via an unrelated field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

- `StatusHandler` (and the underlying `Status` model, exercised by `webhooks_controller_test.rb:42-59`) creates a `Status` record directly from unverified payload fields (`sha`, `state`, `description`, `context`, `target_url`, `created_at`) for whatever commit/repository `repository.full_name` names, with no round-trip call to GitHub to confirm the status is real. [5](#0-4) 

- These commit statuses feed directly into merge/deploy gating: `MergeRequest#all_status_checks_passed?` and `StatusChecker` decide whether a PR can be merged/deployed based on exactly these `Status` records. [6](#0-5) 

**Binding broken (equality that should hold, but doesn't):**
`organization whose secret authenticated the request == organization owning repository.full_name that the handler mutates`.

Because `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the mutated repository/stack) are two independent, attacker-controlled fields inside the same unauthenticated JSON body, an attacker who can satisfy verification for *any one* configured organization (trivially true if that org has no `webhook_secret` set, a state explicitly allowed by the multi-org configuration documented in `docs/setup.md`) can forge state (e.g., a "success" CI status) for a repository belonging to an entirely different, properly-secured organization tracked by the same Shipit instance.

### Impact Explanation
A forged "success" `Status` on a targeted repository/commit can satisfy `StatusChecker`/`MergeRequest#all_status_checks_passed?`, bypassing required CI checks and allowing Shipit's merge queue to merge, or a stack's deploy gate to accept, a commit that never actually passed CI — an unauthorized merge/deploy. This is reachable with no `ApiClient` token, no `webhook_secret` for the targeted org, no GitHub App private key, and no repository write access — only knowledge that some organization configured in the multi-org Shipit install has no webhook secret set.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (explicitly documented/supported), and (2) at least one configured organization without a `webhook_secret` (also an explicitly supported/optional configuration per `docs/setup.md`). Given these two conditions — both within the engine's own documented operating envelope, not host misconfiguration outside spec — exploitation requires only a single crafted HTTP POST to `/webhooks` with mismatched `repository.owner.login` vs `repository.full_name`.

### Recommendation
- Bind repository resolution to the same organization that authenticated the webhook: after `verify_signature` succeeds, ensure every handler validates that `payload.dig('repository','full_name')`'s owner matches `repository_owner` (or better, pass the verified organization through to handlers and reject payloads referencing a different owner).
- Do not allow `verify_webhook_signature` to silently return `true` for organizations without a configured secret; either require `webhook_secret` for all configured organizations or refuse to process events for organizations lacking one.
- Consider signing/verifying against the specific repository identity rather than only the top-level HMAC of the raw body keyed by a org selected from unauthenticated data.

### Proof of Concept
Preconditions: Shipit instance configured for two GitHub orgs, `OrgA` (no `webhook_secret` set) and `OrgB` (secret configured, repository `OrgB/protected-repo` tracked with an open PR whose head commit lacks a passing required CI status).

```bash
curl -X POST https://shipit.example.com/webhooks \
  -H "X-Github-Event: status" \
  -H "Content-Type: application/json" \
  -d '{
        "sha": "<head-sha-of-protected-pr>",
        "state": "success",
        "context": "required-ci-check",
        "description": "forged",
        "target_url": "https://example.com",
        "created_at": "2026-09-01T00:00:00Z",
        "repository": {
          "owner": { "login": "OrgA" },
          "full_name": "OrgB/protected-repo"
        }
      }'
```
`verify_signature` looks up `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` unconditionally regardless of the (absent/incorrect) `X-Hub-Signature` header. `StatusHandler` then resolves the target via `repository.full_name = "OrgB/protected-repo"` and creates a forged successful `Status` on `OrgB`'s protected commit, which `StatusChecker`/`MergeRequest#all_status_checks_passed?` will treat as a passing check.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
