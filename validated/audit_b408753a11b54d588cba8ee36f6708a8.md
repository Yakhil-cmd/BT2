Confirmed: the CCMenu API endpoint bypasses the stack-scoping that every other API controller enforces on `ApiClient` tokens.

### Title
Stack-scoped API tokens can read the build/deploy status of any stack via the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
Every other resource controller under `Shipit::Api::BaseController` resolves the target stack through the `stacks` helper, which restricts the query set to the stack the authenticated `ApiClient` is bound to (`current_api_client.stack_id`) [1](#0-0) . `Shipit::Api::CCMenuController`, however, overrides `stack` to resolve directly against the global `Stack` relation, ignoring the client's `stack_id` binding entirely [2](#0-1) .

### Finding Description
`ApiClient` records can be scoped to a single stack (`belongs_to :stack, optional: true`) [3](#0-2) . The intended trust binding is: *"the set of stacks a token authorizes" == "the set of stacks the token can touch"*. `BaseController#stacks` enforces exactly this equality by filtering to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id` [4](#0-3) , and `Api::StacksController#stack` (and other resource controllers) always resolve through that scoped relation, e.g. `stacks.from_param!(params[:id])` [5](#0-4) .

`Api::CCMenuController` breaks this binding: its `stack` method calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model instead of `stacks.from_param!` [6](#0-5) . The `require_permission :read, :stack` check only validates that the permission string `read:stack` is present in `ApiClient#permissions` [7](#0-6) ; it never checks whether the requested `stack_id` matches the token's bound stack. As a result, a token that is only supposed to authorize reading one specific stack (e.g. the `here_come_the_walrus` fixture, scoped to the `shipit` stack with `read:stack` permission [8](#0-7) ) can be used to fetch the CCMenu status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, deploy activity) of *any* stack in the installation by simply changing the `stack_id` URL parameter, since `authenticate_api_client` here only validates the token itself, not stack membership [9](#0-8) .

### Impact Explanation
This is an unauthenticated-scope read of stack state: a token deliberately narrowed to one stack (commonly distributed as a CI-badge/CCMenu URL, generated by `CCMenuUrlController` and often embedded in public dashboards or config files) can be replayed with a different `stack_id` to disclose build/deploy status of stacks the token holder was never granted access to. This matches the "High - unauthenticated read of stack state, task streams or deploy output" impact category, since it breaks the "stack a token authorizes" vs "stack it touches" binding.

### Likelihood Explanation
Likelihood is high in practice: CCMenu tokens are specifically designed to be embeddable in third-party CI-status tools/widgets (see `CCMenuUrlController`, which mints a `read:stack` token and builds a shareable URL) [10](#0-9) . Anyone who obtains one such URL/token (which is expected to be shared more widely than a full API credential) can trivially swap the `stack_id` query parameter to enumerate other stacks, no signature or extra secret is checked against the requested stack.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` collection (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so the stack-binding enforced everywhere else in the API is also enforced here.

### Proof of Concept
1. Obtain (or generate via `CCMenuUrlController#fetch`) an `ApiClient` token scoped to `stack_id: <stack A id>` with `permissions: ['read:stack']`.
2. Send `GET /api/stacks/:stack_id_of_stack_B/ccmenu.xml?token=<token>` where `stack_id_of_stack_B` is a different stack the token was never scoped to.
3. `authenticate_api_client` succeeds because the token is valid (`ApiClient.authenticate` only verifies the signed id) [9](#0-8) .
4. `require_permission :read, :stack` passes because the client has `read:stack` in its permissions list, regardless of which stack is requested [7](#0-6) .
5. `stack` resolves stack B directly via the unscoped `Stack.from_param!`, and `show` renders stack B's `lastBuildStatus`/`lastBuildLabel`/`webUrl` even though the token was only authorized for stack A [11](#0-10) .
