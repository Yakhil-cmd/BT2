### Title
Unrestricted route pools can execute attacker code under the sender’s authorization tree - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
`execute_strategy` accepts caller-supplied pool addresses inside `StrategyPayload.assets`, and venue adapters invoke those addresses as contracts. A malicious route can therefore place attacker-controlled code on the call stack below the sender’s authorized root invocation. That code can invoke an unrelated token’s `transfer(sender, attacker, amount)`. Soroban simulation records the call as a child of the sender’s authorization tree, and if the resulting tree is signed, the host permits the transfer.

### Finding Description
`execute_strategy` only authenticates `sender`, decodes the packed route, resolves `token_in` and `token_out`, pulls the measured input, and executes each instruction. It does not restrict the addresses stored in `assets`. [1](#0-0) 

For a swap instruction, `idx_a` is loaded directly from `assets` as `hop.pool`, then dispatched to the selected venue adapter. [2](#0-1)  Route validation checks opcode, registry bounds, mode, token-chain structure, and split weights, but not whether the pool address is trusted or even implements the intended DEX ABI. [3](#0-2) 

The Soroswap adapter invokes the supplied pool address twice: `get_reserves` and `swap`. Either call can execute attacker-controlled contract code. [4](#0-3)  Because the call remains within the sender-authorized transaction tree, the malicious pool can call `token.transfer(sender, attacker, amount)` for an unrelated wallet token. The repository’s regression test demonstrates that simulation records that rogue transfer under the caller’s `swap_collateral` authorization entry and that signing the recorded tree permits it. [5](#0-4) [6](#0-5) 

This is analogous to the Lavamoat realm escape: route validation confines the instruction stream structurally, but the pool address introduces an unconfined execution realm whose code can exceed the apparent authority of the approved swap.

### Impact Explanation
A malicious route can steal arbitrary SAC/custom-token balances from the swapper’s wallet, beyond the declared router input. The malicious pool can preserve route success by returning the expected output token to the router during its `swap` call, so the measured-output and minimum-output checks do not prevent the theft.

The affected entrypoints include direct `swap-aggregator::execute_strategy`, and controller paths that pass caller-provided route bytes to the configured router, such as `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. For controller strategies, the router’s declared `sender` is the controller, but a token transfer naming the account owner as `from` still searches that owner’s transaction authorization tree.

### Likelihood Explanation
Likelihood is moderate rather than high because the victim must sign the expanded authorization tree produced by simulation. A wallet or client that displays only the root call, or a user that signs without inspecting nested invocations, enables the theft. The regression test shows the same route fails when the signed tree omits the rogue transfer and succeeds when the tree contains it. [7](#0-6) 

### Recommendation
Do not treat an address in `assets` as permissionless code. Add a governance-managed venue/pool allowlist or pool registry, and reject route hops whose pool is not approved for the selected venue. As a secondary mitigation, clients must display the complete authorization tree and reject unexpected child token transfers, but contract-level pool admission is needed to remove the untrusted realm.

### Proof of Concept
1. Deploy a contract that implements the Soroswap-facing calls `get_reserves` and `swap`.
2. Configure it with `(victim, wallet_token, attacker, amount)`.
3. Have `get_reserves` or `swap` call `wallet_token.transfer(victim, attacker, amount)`.
4. In `swap`, transfer the requested `token_out` amount to the router so the hop produces a positive measured output.
5. Construct `StrategyPayload` with:
   - `assets` containing the malicious pool, route input token, route output token, and any other required entries;
   - `ops` containing one `Swap(Soroswap)` instruction whose `idx_a` indexes the malicious pool;
   - `amounts[min_out]` not exceeding the pool’s returned output.
6. Call either:
   - `execute_strategy(victim, total_in, swap_xdr)`, or
   - a controller strategy such as `swap_collateral(victim, account_id, current, amount, new, swap_xdr)`.
7. Simulation records a nested `wallet_token.transfer(victim, attacker, amount)` under the victim’s authorization entry.
8. If the victim signs that recorded tree, the unrelated wallet token is transferred to the attacker while the route can still satisfy its output checks.

The in-repository harness demonstrates the authorization behavior directly: recording mode attaches the rogue wallet transfer to the caller’s `swap_collateral` entry, and enforcing mode accepts it only when that child invocation is signed. [5](#0-4)

    /// Validates every instruction's opcode, mode, and indices before execution begins,
    /// including the `Prev` chain, same-token swaps, and split-weight bounds.
    fn validate(&self, env: &Env, assets_len: u32, amounts_len: u32, weight_count: u32) {
        for i in 0..self.op_count {
            let record = self.raw(i);
            let Some(opcode) = Opcode::from_u8(record[field::OPCODE]) else {
                panic_with_error!(env, Error::InvalidRouteXdr);
            };
            let mode = Mode::from_u8(record[field::MODE]);
            let (idx_a, idx_b, idx_c) = (
                record[field::POOL] as u32,
                record[field::TOKEN_IN] as u32,
                record[field::TOKEN_OUT] as u32,
            );

            // `Prev` is a purely structural link: the predecessor must exist,
            // must have a single output, and that output must be this
            // instruction's input.
            if mode == Mode::Prev {
                if i == 0 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
                let previous = self.raw(i - 1);
                let produced = match Opcode::from_u8(previous[field::OPCODE]) {
                    // A swap produces its `token_out`, a mint its share token.
                    Some(Opcode::Swap(_)) => previous[field::TOKEN_OUT],
                    Some(Opcode::Mint) => previous[field::TOKEN_IN],
                    // A burn releases every constituent at once.
                    _ => panic_with_error!(env, Error::BrokenTokenChain),
                };
                if idx_b != produced as u32 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
            }
            match mode {
                Mode::Fixed(idx) if idx as u32 >= amounts_len => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                Mode::Ppm(idx) if idx as u32 >= weight_count => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                _ => {}
            }

            if idx_a >= assets_len || idx_b >= assets_len {
                panic_with_error!(env, Error::InvalidRouteXdr);
            }
            match opcode {
                Opcode::Swap(_) => {
                    if idx_c >= assets_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_b == idx_c {
                        panic_with_error!(env, Error::SameToken);
                    }
                }
                // Liquidity legs spend the full vault balance, so only `Mode::All` is valid.
                Opcode::Burn | Opcode::Mint => {
                    if mode != Mode::All {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_c >= amounts_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                }
            }

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
