### Title
Donated tokens sent directly to the pool or controller are permanently unrecoverable - (File: contracts/pool/src/cache/cash.rs)

### Summary
The LiquidityPool and Controller contracts hold token balances (any SAC asset, including native XLM) whose accounting is tracked entirely in stored state (`cache.cash`), never reconciled against the actual token balance. Any unprivileged address can call `transfer(sender, pool_or_controller, amount)` on a market's asset SAC. Those tokens raise the real balance but are invisible to every accounting path, and no in-scope entrypoint can credit or return them. The funds are frozen permanently, the direct analog of UXDController's unprotected `receive()`.

### Finding Description
Pool solvency, liquidity, and payout logic all operate on the stored `cash` field, not on `token::balance(pool)`:

- `Cache::debit_cash` / `require_reserves` gate withdrawals and borrows against `self.cash` only, so the excess real balance is never drawable (`contracts/pool/src/cache/cash.rs:15-41`).
- `backing_shortfall` computes `cash + debt - supplied` from storage; a donation does not reduce a shortfall and cannot be claimed (`contracts/pool/src/guards.rs:61-66`).
- `recapitalize::accounting` credits only `min(amount, shortfall)` of the `amount` the controller just pushed and refunds the rest to `payer`; a pre-existing unsolicited balance is never adopted (`contracts/pool/src/ops/recapitalize.rs:52-58`).
- `flash::terms` computes expected balances from the live balance at call time, so donations neither break flash loans nor become claimable as fees (`contracts/pool/src/ops/flash.rs:107-121`).

On the controller side the design explicitly preserves pre-existing balances: `refund_controller_balance_delta` refunds only the balance *increase* measured since `balance_before`, and the harness test `test_migrate_refund_ignores_preexisting_controller_balance` asserts that a pre-existing controller token balance "must remain (not used as refund or swept)" (`contracts/controller/src/payments.rs:41-52`, `contracts/controller/tests/strategy/migrate_blend.rs:496-535`). There is no rescue/sweep function in `contracts/pool`, `contracts/controller`, or `common`.

### Impact Explanation
Permanent freezing of funds. Tokens transferred directly to the pool or controller by any user (mistakenly or otherwise) can never be withdrawn: suppliers can only draw against recorded `cash`, recapitalize ignores pre-existing balance, controller refunds only flow deltas, and no entrypoint lets anyone recover the surplus. The sender's loss is total with no protocol-side recourse.

### Likelihood Explanation
Low-but-real likelihood: it requires a user to send tokens directly to a contract address rather than through `supply`. However, hub/spoke addresses are discoverable on-chain and front-end or integration mistakes make direct transfers a realistic accident, which is exactly the scenario class the source report covers. Severity is Medium: funds at risk are limited to unsolicited senders, not depositors.

### Recommendation
Add an admin/governance-gated sweep or adopt-excess mechanism: for each market, compute `excess = token.balance(pool) - cash` (and equivalently any positive controller balance not attributable to an in-flight operation) and either credit it to protocol revenue shares or transfer it to a treasury address. Alternatively, document the donation behavior and have `recapitalize` credit `min(amount + pre_existing_excess, shortfall)` so stranded funds can at least cover bad debt. Note that fixing by reverting inbound transfers is not possible on Soroban (SAC `transfer` cannot be refused by the recipient), so an explicit recovery path is required.

### Proof of Concept
1. Deploy pool, create market for XLM SAC (hub `H`), have a supplier call `controller.supply` so `cash = S > 0` and `balance(pool) = S`.
2. Unprivileged attacker/victim calls `token::Client(xlm).transfer(victim, pool, D)` directly.
3. State: `balance(pool) = S + D`, but `state.cash = S` (unchanged, since no op ran).
4. Attempt recovery: `withdraw` caps at `cash` via `require_reserves`; `recapitalize` only inspects its `amount` argument and refunds the rest to `payer`; `claim_revenue`/`flash_loan`/`clean_bad_debt` never touch the excess. No entrypoint returns `D`.
5. Same on the controller: send `D` to the controller, then run `migrate_from_blend` or any liquidation refund — `refund_controller_balance_delta` returns only the delta above `balance_before`, leaving `D` stranded (mirrors `test_migrate_refund_ignores_preexisting_controller_balance`).
