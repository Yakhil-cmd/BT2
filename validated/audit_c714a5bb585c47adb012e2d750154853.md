### Title
Cross-organization forgery of GitHub webhook events via organization/repository binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook only against the GitHub *organization* named in the payload's `repository.owner.login` (or `organization.login`), by looking up that organization's `webhook_secret` via `Shipit.github(organization: repository_owner)`. Once the signature is accepted, the actual event handler (`Shipit::Webhooks::Handlers::*`) decides which `Stack`/`Commit` to mutate using a *different* payload field — `repository.full_name` (or, in the `status` handler, no repository field at all, just a global `sha` lookup). Because a legitimate multi-tenant Shipit deployment can host several independently-configured GitHub Apps/organizations (documented in `docs/setup.md`, "Using Multiple Github Applications"), the org whose secret authenticates the request is never checked against the org whose repository is written to.

### Finding Description
`verify_signature` derives the signing org from the payload itself: [1](#0-0) [2](#0-1) 

This only proves the request was signed with `github(organization: repository_owner).webhook_secret`. It never binds the verified organization to the repository the handler will subsequently act on.

The base `Handler` class instead resolves the target `Stack`s purely from `repository.full_name`, a sibling field of `repository.owner.login` inside the very same signed payload, but a value the *sender* — who legitimately possesses their own org's `webhook_secret` — fully controls: [3](#0-2) 

`PushHandler` uses this to sync any stack whose repository matches the attacker-chosen `full_name`: [4](#0-3) 

`StatusHandler` is worse: it doesn't even consult `repository` — it matches purely on `sha` across the entire `Commit` table, i.e. across every organization's stacks: [5](#0-4) 

`Repository.from_github_repo_name` performs no ownership cross-check either — it simply looks up whatever owner/name pair is embedded in the field the attacker controls: [6](#0-5) 

**Binding broken (as an equality):**
`organization that authenticated the webhook (repository.owner.login → webhook_secret)` **==** `organization/repository whose Stack/Commit is mutated (repository.full_name / sha lookup)`

Before the attack: for a well-behaved sender, `repository.owner.login` and `repository.full_name`'s owner segment are the same real organization, so the equality holds by convention, not by code enforcement.

After the attacker's request: a tenant that legitimately owns *its own* GitHub App and `webhook_secret` (org "OrgA", already configured in `config/secrets.yml` per the multi-org setup docs) crafts and signs a payload where `repository.owner.login = "OrgA"` (so `verify_signature` succeeds using OrgA's own secret) but `repository.full_name = "OrgB/some-repo"` (or, for `status` events, simply picks a `sha` value known to exist in OrgB's `commits` table). The handler then mutates OrgB's `Stack`/`Commit` data, even though OrgB never issued and never authorized this request.

### Impact Explanation
This is a cross-repository/cross-tenant write performed by an entity that only holds credentials for a *different*, unrelated organization on the same Shipit instance — matching the "cross-repository writes" Critical impact category. Concretely:
- Via `StatusHandler`, an attacker can inject a fabricated `success` `Status` for a `sha` present in a victim stack's history (statuses are persisted straight from the webhook payload with no re-verification against GitHub): [5](#0-4) 
- A forged passing status can satisfy `deployable?`/`schedule_continuous_delivery`, letting the attacker cause an unauthorized automatic deploy on a stack with continuous deployment enabled: [7](#0-6) [8](#0-7) 
- Other handlers (`push`, `pull_request/*`, `check_suite`) similarly resolve their target `Stack`/`Repository` from the attacker-controlled `full_name` field, letting a tenant from one org trigger `sync_github`, review-stack archival/unarchival, or PR metadata changes on another org's repository.

### Likelihood Explanation
Requires only that the Shipit instance is configured (as documented) to serve multiple GitHub organizations with independent `webhook_secret`s, and that the attacker controls (or compromises) one of those organizations' GitHub App webhook secret — a routine, low-privilege tenant scenario in a multi-org Shipit deployment, not requiring any Shipit `ApiClient` token, session, or private key belonging to the victim organization.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after signature verification, assert that the organization used to verify the signature matches the owner segment of `repository.full_name` (and, for `status_handler.rb`, additionally scope `Commit.where(sha:)` by the stacks belonging to the verified organization instead of a global lookup) before dispatching to any handler.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `github.webhook_secret` (per `docs/setup.md`'s multi-org setup).
2. As an operator/holder of `OrgA`'s webhook secret, build a `status` event JSON body: `{"sha": "<sha known to exist on an OrgB-owned stack>", "state": "success", "context": "<required-context>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/decoy"}}`.
3. Compute `X-Hub-Signature` using OrgA's `webhook_secret` and `POST` to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` succeeds because it only checks the signature against `github(organization: "OrgA")` per `app/controllers/shipit/webhooks_controller.rb` lines 24-30.
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb` lines 20-24) matches the `Commit` in OrgB's stack purely by `sha` and creates a forged `success` status on it, with no relation to `OrgA`'s ownership, potentially triggering `schedule_continuous_delivery` / an unauthorized deploy on OrgB's stack.
