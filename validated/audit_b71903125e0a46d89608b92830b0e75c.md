### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while every event handler acts on the independently-attacker-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` or the fallback `params.dig('organization', 'login')`. [1](#0-0)  Every event handler, however, resolves the actual `Repository`/`Stack` to mutate using a completely different field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. [2](#0-1)  Because the whole HTTP body is attacker-authored JSON (not a real GitHub-signed struct), nothing enforces that `repository.owner.login` and `repository.full_name` refer to the same organization/repository. `GitHubApp#verify_webhook_signature` additionally treats a missing/blank `webhook_secret` as automatically verified: `return true unless webhook_secret`. [3](#0-2)  Combined, an attacker who knows (or picks) any configured GitHub organization in this Shipit instance that has **no** `webhook_secret` set (a supported, documented configuration - see `webhook_secret: # nil` in `config/secrets.development.shopify.yml`) can produce a payload whose `repository.owner.login`/`organization.login` = that unsecured org (making `verify_signature` pass unconditionally) while `repository.full_name` names a repository that actually belongs to a *different, secured* organization tracked by Shipit.

### Finding Description
The binding that should hold is: **organization authenticated by the signature check == organization/repository the handler writes to**. This binding is broken because:

1. `verify_signature` computes `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature`. If that organization has no `webhook_secret` configured, the check returns `true` for *any* signature/body pair, with no cryptographic proof that the specific `repository.full_name` in the body is legitimate. [4](#0-3) [3](#0-2) 
2. Once `verify_signature` passes, `WebhooksController#create` parses the raw JSON and dispatches it, unmodified, to every registered handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [5](#0-4) 
3. Handlers such as `Handler#stacks`/`#repository_name` resolve the target `Repository` purely from `payload.dig('repository', 'full_name')` — a field the signature check never inspected or bound to the verified organization. [2](#0-1) 
4. `StatusHandler`, in particular, looks up commits **globally by SHA** (`Commit.where(sha: params.sha)`, with no repository/stack scoping at all) and creates a `Status` from fully attacker-controlled `state`, `context`, `description`, and `target_url`. [6](#0-5) 
5. A forged "success" status that matches an entry in `merge.require`/`ci.require` for a target stack changes `Commit#status`, which triggers `stack.schedule_merges` and `ProcessMergeRequestsJob`. [7](#0-6) 
6. `ProcessMergeRequestsJob` merges any `pending` merge request once `MergeRequest#all_status_checks_passed?` (backed by `StatusChecker`, which checks the forged status records) is true, invoking `stack.github_api.merge_pull_request(...)` — a real GitHub merge performed with Shipit's own GitHub App credentials. [8](#0-7) [9](#0-8) [10](#0-9) 

The webhook endpoint requires no session, no `ApiClient` token, and no privileged account — an unauthenticated network client that merely knows Shipit hosts at least one GitHub organization without a configured `webhook_secret` can exploit this to affect stacks belonging to *other, secured* organizations, because the code never checks that `repository_owner` (verified) equals the owner embedded in `repository.full_name` (acted upon).

### Impact Explanation
This breaks the equality `organization authenticated == repository/organization written`, letting an unprivileged network attacker forge webhook events (push syncs, status/check-run updates, pull-request archive/unarchive, team membership) against stacks that belong to a securely-configured organization, by merely satisfying the (vacuous) verification for an unrelated, unsecured organization on the same Shipit instance. In the worst case (`StatusHandler`), this enables triggering an **unauthorized merge** of a pull request via `MergeRequest#merge!`/`stack.github_api.merge_pull_request`, which falls squarely in the Critical impact category ("unauthorized deploy, rollback, or merge").

### Likelihood Explanation
Exploitability depends on the operator's configuration: it requires (a) a multi-organization Shipit deployment and (b) at least one configured organization lacking a `webhook_secret` (a state the shipped example config explicitly shows as valid: `webhook_secret: # nil`). Given that state, exploitation requires no authentication whatsoever — just crafting a JSON POST to the public `/webhooks` endpoint with a chosen `repository.owner.login` and an arbitrary `repository.full_name`/`sha`. The attacker also needs to know or guess a valid commit SHA for the targeted stack (obtainable from the public GitHub repo) to abuse `StatusHandler`.

### Recommendation
- Reject webhook payloads where `repository.full_name`'s owner does not match the organization used for signature verification (`repository_owner`).
- Do not treat a missing/blank `webhook_secret` as "verified" (`return true unless webhook_secret`); instead require every configured organization to have a secret, or explicitly refuse to process events for organizations without one.
- In `StatusHandler`, scope the `Commit` lookup by the verified organization/repository (via the associated `Stack`/`Repository`), not solely by `sha`.

### Proof of Concept
1. Configure Shipit with two organizations: `secure-org` (has `webhook_secret` set, hosts the target stack/repo `secure-org/prod-repo`) and `open-org` (no `webhook_secret` configured), per `config/secrets.development.shopify.yml`.
2. An unauthenticated attacker sends, with no valid `X-Hub-Signature`:
```
POST /webhooks
X-Github-Event: status

{
  "repository": { "owner": { "login": "open-org" }, "full_name": "secure-org/prod-repo" },
  "sha": "<known head sha of a pending PR on secure-org/prod-repo>",
  "state": "success",
  "context": "<required CI context from merge.require>",
  "description": "forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
3. `verify_signature` computes `repository_owner = "open-org"`, calls `Shipit.github(organization: "open-org").verify_webhook_signature(...)`, which returns `true` immediately because `open-org` has no `webhook_secret`. [11](#0-10) [3](#0-2) 
4. `StatusHandler#process` matches the commit by `sha` (global lookup, unscoped) and calls `create_status_from_github!`, creating a forged "success" status on the commit belonging to `secure-org/prod-repo`. [12](#0-11) 
5. This flips `Commit#status`, scheduling `ProcessMergeRequestsJob` via `stack.schedule_merges`. [13](#0-12) 
6. If a pending merge request on `secure-org/prod-repo` was only blocked by the now-forged status context, `ProcessMergeRequestsJob` calls `merge_request.merge!`, which performs `stack.github_api.merge_pull_request(...)` — an unauthorized merge executed with Shipit's `secure-org` GitHub credentials, despite the attacker never possessing `secure-org`'s webhook secret. [14](#0-13) [15](#0-14) 

Note: I was not able to fully trace whether `ci.require`/`merge.require` context matching in `StatusChecker`/`Status::Group` (not indexed in detail here) imposes any additional constraint that would block this specific merge scenario beyond context-name matching; that logic lives outside the files I was able to inspect in depth, so the exact conditions for `all_status_checks_passed?` returning `true` from a single forged status should be verified against `app/models/shipit/status/group.rb` before treating the merge-trigger PoC as fully confirmed. The core signature/authorization-binding flaw (verified org ≠ acted-upon repo) is confirmed directly from the cited code.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  class ProcessMergeRequestsJob < BackgroundJob
    include BackgroundJob::Unique
    on_duplicate :drop

    queue_as :default

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
