### Title
Stack-scoped API client token can read CCMenu build status for any stack, bypassing its `stack_id` authorization scope - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` restricted to a single stack (`ApiClient#stack_id`) can only see that stack, by scoping all stack lookups through `stacks`/`stack`. `Shipit::Api::CCMenuController` overrides `stack` to bypass this scoping entirely, so a token that is only supposed to authorize `read:stack` on one stack can be replayed with any `stack_id` to read another stack's build/deploy status.

### Finding Description
`Shipit::Api::BaseController` defines the authorization boundary that binds an `ApiClient`'s token to the specific stack it was created for: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the client is scoped (`stack_id?`), and `stack` looks up `params[:stack_id]` only within that restricted set. This is exactly how the general permission check is documented and tested to work — e.g. `"an api client scoped to a stack will only see that one stack"`.

`Shipit::Api::CCMenuController` however defines its own `stack` method that ignores this scoping and resolves directly against all stacks: [2](#0-1) 

Because `require_permission :read, :stack` only calls `current_api_client.check_permissions!('read', 'stack')`, which merely checks that the string `"read:stack"` is present in the client's `permissions` array and never consults `stack_id`: [3](#0-2) 

the equality that should hold — *the stack a token authorizes == the stack it is allowed to touch* — is broken specifically in `CCMenuController#show`. Any token that has the `read:stack` permission (even one deliberately restricted via `ApiClient#stack_id` to a single stack) can be presented with an arbitrary `stack_id` param and will be resolved via the unrestricted `Stack.from_param!`, returning that other stack's data.

`CCMenuController` also has its own `authenticate_api_client`, which supports token-in-query-string authentication in addition to Basic Auth, making the token trivially replayable via a simple GET request: [4](#0-3) 

### Impact Explanation
This breaks the authorization boundary "a stack a token authorizes versus a stack it touches." A caller holding only a stack-scoped, read-only token (e.g. the fixture `here_come_the_walrus`, which is `belongs_to stack: shipit`, `permissions: read:stack`) can use it to read the CI/build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock status, etc., rendered via `shipit/ccmenu/project`) of any other stack in the Shipit instance, not just the one it was authorized for. This matches the High-impact category "unauthenticated read of stack state, task streams or deploy output," since it grants read access across a stack boundary the token issuer did not intend to grant.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` authentication token that carries `read:stack` permission — no privileged capability beyond having been issued that one restricted token is needed. The engine's own test suite demonstrates this exact pattern is supported and expected to be enforced elsewhere (`stacks_controller_test`/`api/stacks_controller_test` assert stack-scoped clients see only their stack), which shows the scoping is a real, relied-upon control that `CCMenuController` silently omits.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the same scoped lookup used elsewhere (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that `ApiClient#stack_id` scoping is honored consistently across all API controllers.

### Proof of Concept
1. As an authorized administrator, create (or have created) an `ApiClient` scoped to Stack A only: `permissions: ['read:stack']`, `stack: StackA`.
2. Obtain that client's `authentication_token` (as documented, e.g. via `api_client_token` helper for the creator).
3. Send: `GET /api/StackB_owner/StackB_repo/StackB_branch/ccmenu.xml?token=<StackA-scoped token>`
4. The request passes `authenticate_api_client` (valid token) and `require_permission :read, :stack` (permission string present), and `CCMenuController#stack` resolves `Stack.from_param!` against Stack B directly — returning Stack B's build/deploy status even though the token was only ever authorized for Stack A. # frozen_string_literal: true

```ruby
module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
```
