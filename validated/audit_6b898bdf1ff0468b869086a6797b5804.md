### Title
Plaintext logging of device-message payloads (pairing secrets, private-payment chains) exposes credentials via logs - (File: device.js)

### Summary
`device.js` logs the full plaintext content of device-to-device messages both before encryption (when sending) and after decryption (when receiving). These messages routinely carry `pairing_secret` values and private-payment chains, which function as bearer credentials in ocore. Anyone with read access to the node's stdout/log files (log aggregation, crash dumps, support requests, misconfigured log shipping) obtains these secrets directly, mirroring the Undertow CWE-532 pattern of dumping the entire request object into logs at high verbosity.

### Finding Description
In `reliablySendPreparedMessageToHub`, the outgoing plaintext `json` object (before it is encrypted) is written to the log: [1](#0-0) 

That `json` body is built by `sendMessageToHub`/`sendMessageToDevice` and, for pairing, contains the raw `pairing_secret` as constructed in `sendPairingMessage`: [2](#0-1) 

For private/asset transfers, the same code path carries the entire chain of private elements via `wallet_general.sendPrivatePayments`, which sets `body.chains = arrChains` and calls `device.sendMessageToDevice(..., "private_payments", body, ...)`: [3](#0-2) 

Symmetrically, on the receiving side `decryptPackage` logs the fully decrypted plaintext message before it is dispatched to any handler: [4](#0-3) 

Both logging statements are unconditional `console.log` calls (not gated by a debug flag), so in any deployment that captures stdout/stderr to persistent log files (common in production Node.js/PM2/Docker setups), the plaintext pairing secrets and private-asset payment chains are written to disk in cleartext, exactly the CWE-532 pattern described in the Undertow advisory (dumping the full exchange/request object at a routine log level).

### Impact Explanation
- `pairing_secret` values leaked from logs let an attacker who reads the log complete the pairing handshake with a device/hub before or instead of the intended correspondent (`handlePairingMessage` only checks the secret string and expiry, not who is trying to use it): [5](#0-4)  This allows impersonation of a wallet correspondent, enabling social-engineering-free interception/redirection of payment requests and private payment chains intended for the legitimate device.
- Private-payment chains (`arrChainsOfRecipientPrivateElements`/`arrChainsOfCosignerPrivateElements`) sent via `sendPrivatePayments` are the actual bearer proof needed to claim private/asset outputs (see how they are forwarded and stored, e.g. `preCommitCb` in `wallet.js`): [6](#0-5)  An attacker who extracts these chains from logs can present them as valid private-payment proof to a hub/peer and potentially claim or double-spend the private asset, causing genuine unauthorized fund loss for the legitimate recipient.

### Likelihood Explanation
Every pairing operation and every private/asset payment triggers these log lines automatically, with no attacker interaction required beyond gaining read access to the node's logs (a very common secondary exposure vector — shared hosting, log aggregation services, crash reporters, support screenshots, or an operator debugging with logs enabled). No privileged access to the ocore process itself is needed once the log data is exposed, only access to the log stream.

### Recommendation
Remove or redact these logging statements: do not log the plaintext `json` body in `reliablySendPreparedMessageToHub`, and do not log `decrypted_message` in `decryptPackage`. If debug logging of message flow is required, log only non-sensitive metadata (e.g. `subject`, message length, hash) and explicitly strip/mask fields such as `pairing_secret`, `reverse_pairing_secret`, `chains`, and `private_payloads` before logging.

### Proof of Concept
1. Run an ocore-based wallet/hub node with logs captured to a file (standard practice, e.g. `node start.js > app.log 2>&1`).
2. Have User A generate a pairing code (`startWaitingForPairing`) and send it to User B, or have User A send a private/asset payment to User B (`sendMultiPayment` with a private asset, which internally calls `walletGeneral.sendPrivatePayments`).
3. Observe `app.log`: the line `will encrypt and send to <addr>: {"from":...,"subject":"pairing","body":{"pairing_secret":"...","device_name":"..."}}` (from `device.js:572`) or the equivalent `"private_payments"` body containing `chains` is written in cleartext.
4. Anyone with read access to `app.log` (support staff, log-aggregation platform, backup, or an attacker who compromises log storage) can extract the `pairing_secret` and use it against the hub before the legitimate peer completes pairing, or extract the `chains` payload and attempt to use it as proof to claim/spend the associated private asset outputs.
