### Title
CCMenu tokens are not stack-scoped and their target stack is never verified against the requested one - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `CCMenuController#stack` method resolves the target stack purely from the URL parameter `params[:stack_id]`, without ever checking it against the stack (if any) the presented `ApiClient` token is authorized for. Combined with the fact that `CCMenuUrlController` mints a single, non-stack-scoped `ApiClient` per user (reused across every stack), any leaked CCMenu token can be replayed against an arbitrary stack, breaking the intended binding "stack a token authorises == stack it touches."

### Finding Description
`CCMenuUrlController#fetch` builds a "CCMenu" status URL for a given stack by creating (or reusing) an `ApiClient` scoped only by `creator` and `name`, never by `stack_id`: [1](#0-0) 

Because `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` never sets `stack_id`, the resulting `ApiClient` is globally unscoped for `read:stack`. In the normal API flow, `Shipit::Api::BaseController#stacks`/`#stack` enforce this scoping: [2](#0-1) 

restricting queries to `Stack.where(id: current_api_client.stack_id)` when the client is bound to a stack. However, `CCMenuController` overrides `stack` and completely bypasses this scoping logic: [3](#0-2) 

`stack` is resolved via `Stack.from_param!(params[:stack_id])` directly — the `current_api_client`'s `stack_id` (the value the token was actually authorized for/derived alongside) is never compared to the `stack_id` param that is actually acted on.

The binding that should hold is:
`current_api_client.stack_id (the stack the token authorises) == params[:stack_id] (the stack the request touches)`

This never holds in `CCMenuController`, and since the token itself is not even stack-scoped to begin with (per `CCMenuUrlController`), any user who obtains one CCMenu URL/token (these are explicitly designed to be handed out to external CI dashboard aggregators, i.e., a lower-trust consumer) can swap `stack_id` in the query string and pull build status, activity, and web URLs for every other stack managed by the Shipit instance, including ones they are not a member of/have no legitimate reason to view.

### Impact Explanation
This grants unauthenticated (token holder needs no further session/permission check beyond the reused, unscoped token) read access to stack state (`lastBuildStatus`, `activity`, `lastBuildLabel`, `webUrl`) for stacks outside of what the token was ever meant to expose, which matches the "High - unauthenticated read of stack state" impact class.

### Likelihood Explanation
Likelihood is high: the CCMenu URL/token is intentionally designed for external, low-trust consumption (CI dashboard tools such as CCTray clients), so it is routinely shared outside of the originating user's control. No special privilege beyond possessing one such URL is required to enumerate other stacks by editing the `stack_id` query parameter.

### Recommendation
- When creating the CCMenu `ApiClient` in `CCMenuUrlController#client`, scope it to the specific stack (`stack: stack`) instead of only `creator`/`name`.
- In `CCMenuController#stack`, verify that `params[:stack_id]` matches `current_api_client.stack_id` (when the client is stack-scoped) before rendering, mirroring the scoping already implemented in `Shipit::Api::BaseController#stacks`.

### Proof of Concept
1. User A visits stack `foo`'s page and fetches `GET /stacks/foo/ccmenu_url`. `CCMenuUrlController#client` creates (or reuses) an `ApiClient` named "CCMenu Client" for User A with no `stack_id`, and returns a URL like `.../api/stacks/foo/ccmenu.xml?token=<TOKEN>`.
2. User A later visits stack `bar`'s page and fetches the same endpoint; `find_or_create_by!(creator:, name:)` returns the *same* `ApiClient`/`<TOKEN>`, now embedded in `.../api/stacks/bar/ccmenu.xml?token=<TOKEN>`.
3. Anyone who obtains the first URL (e.g., an external CI aggregator) can simply change the path segment to `.../api/stacks/<ANY_OTHER_STACK>/ccmenu.xml?token=<TOKEN>` — `CCMenuController#authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])`, and `#stack` resolves `Stack.from_param!(params[:stack_id])` without ever checking it against the token's (non-existent) stack scope — successfully retrieving build status for stacks never intended to be exposed to that token holder.

```ruby
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end
```
