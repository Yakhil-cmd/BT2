Based on my research, writer.js (the module that actually commits units/outputs/inputs and marks outputs as spent) does check `affectedRows` at the points where `is_spent=1` updates occur, so the ledger's own critical spend-marking is guarded. In contrast, the private-payment saving paths in `divisible_asset.js` and `indivisible_asset.js` build their spend-marking `UPDATE` queries through `conn.addQuery()`/`async.series()` without ever inspecting the query result before declaring success. ## Title
Unchecked result of output "mark-as-spent" UPDATE in private payment chain saving - (File: divisible_asset.js / indivisible_asset.js)

## Summary
`validateAndSaveDivisiblePrivatePayment()` in `divisible_asset.js` and `validateAndSavePrivatePaymentChain()` in `indivisible_asset.js` persist a private payment chain by queuing a series of SQL statements (`INSERT` for the new output/input rows and an `UPDATE ... SET is_spent=1 ... WHERE unit=? AND message_index=? AND output_index=?`) and running them with `async.series(arrQueries, callbacks.ifOk)`. The `UPDATE` is meant to atomically flag the spent source output, but the callback passed to `async.series` is invoked unconditionally as soon as all queries finish — the number of rows the `UPDATE` actually affected is never checked. [3](#0-2) [4](#0-3) 

## Finding Description
`conn.addQuery(arrQueries, sql, params)` wraps a `conn.query(sql, params, cb)` call into a function pushed onto `arrQueries`; `async.series` just calls these wrapped functions in order and moves to the next one when the DB callback fires, regardless of the result object (which for an `UPDATE` includes `affectedRows`). This mirrors exactly the class of bug in the original report: a state-changing call whose boolean/success-indicating return value is ignored, and the caller proceeds as if it always succeeded.

In `divisible_asset.js`, the `UPDATE outputs SET is_spent=1 WHERE unit=? AND message_index=? AND output_index=?` has no `AND is_spent=0` guard at all, so it is idempotent but gives no signal whether the row existed. In `indivisible_asset.js`, the guard is present (`... WHERE unit=? AND message_index=? AND output_index=? AND is_spent=0`), which means the statement is intentionally a no-op if the output is already spent — but the code never checks `affectedRows` to detect that no-op condition. `callbacks.ifOk()` is called by `async.series` in both cases whenever the queries complete without a driver-level error, not whenever the intended row mutation actually happened.

This is directly analogous to the reported issue: a critical financial state transition (marking a coin as spent, the on-chain equivalent of `transferFrom`'s success flag) is performed via a call whose result is discardable, and the discarding is never audited.

## Impact Explanation
This path handles private payment chains — plain UTXO transfer/issue records reachable by any device that is a party to (or cosigner of) a private asset payment, i.e., an unprivileged private-payment counterparty. If a race, retry, or malformed/duplicate chain submission causes the intended source-output row to not exist or not match the WHERE clause at update time (e.g., output not yet inserted due to ordering, or already marked spent by a concurrent chain), the code silently treats the private payment as successfully saved (`ifOk`) even though the source coin was not actually flagged spent. Because private outputs are the wallet's only local record of "this coin is spent," this can allow the same private output to be presented again in another payment chain (an unchecked double-spend of a private output), since nothing else besides this local bookkeeping enforces uniqueness for the recipient's local database view before validation elsewhere catches up.

## Likelihood Explanation
The likelihood is moderate: exploiting this requires manipulating timing/ordering of private-payment chain elements or replaying/duplicating chain submissions such that the `UPDATE ... is_spent=1` WHERE-clause fails to match while the surrounding inserts still succeed — plausible since `arrQueries` are executed independently and the row targeted by `UPDATE` depends on prior `INSERT`s in the same batch or previously-processed elements, with no verification step confirming the mutation.

## Recommendation
After each `UPDATE ... SET is_spent=1 ...` (and in general for any `INSERT`/`UPDATE` whose success is a precondition for correctness), check `affectedRows` (or, for SQLite, the equivalent `this.changes`) in the callback before continuing the `async.series` chain, and call `callbacks.ifError(...)` instead of proceeding to `callbacks.ifOk()` if the expected row was not affected.

## Proof of Concept
Not applicable as a runnable exploit — this is a code-review-level finding based on tracing `conn.addQuery`/`async.series` semantics: `async.series` advances on any successful DB callback (`function(){ ... }` with no arguments checked) regardless of `affectedRows`, as shown in the cited `divisible_asset.js:39-72` and `indivisible_asset.js:252-294` blocks, where the sequence ends with `async.series(arrQueries, callbacks.ifOk)` / `async.series(arrQueries, function(){ ...; callbacks.ifOk(); })` with no inspection of any query's result.
