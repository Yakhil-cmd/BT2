### Title
Cross-organization webhook confused deputy: signature verified against `repository.owner.login` but handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), but every event handler then resolves the target repository/stack independently from `repository.full_name`. Because these are two separate, attacker-controlled fields in the same unauthenticated JSON body, an attacker who legitimately controls one organization's webhook secret on a multi-tenant Shipit instance can forge a signature that is valid for "their" org while pointing the payload's `repository.full_name` at a completely different organization's stack.

### Finding Description
`verify_signature` derives the signing organization from the payload itself, not from any independently trusted source: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization config (`secrets.github[organization]`), each with its own `webhook_secret`, when the instance is configured in multi-org mode: [3](#0-2) 

The HMAC is computed over the *entire raw request body* using that organization's secret, then the raw body is parsed and dispatched to handlers: [4](#0-3) 

Every handler, however, resolves the repository/stack to act on using a *different* JSON path, `repository.full_name`, with no cross-check that its owner segment matches the organization used for signature verification: [5](#0-4) 

`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, and the `PullRequest::*` handlers (via `Repository.from_github_repo_name(params.repository.full_name)`) all inherit this same lookup: [6](#0-5) [7](#0-6) [8](#0-7) 

The equality that should hold but is never checked: `organization used to select the webhook secret (repository.owner.login / organization.login)` == `owner segment of repository.full_name used by handlers to pick the stack/repository to mutate`. Since both are attacker-supplied fields inside the same raw, unauthenticated JSON body (the signature only proves "signed by holder of org X's secret," it says nothing about which org's data the body describes), an attacker holding a valid secret for their own onboarded organization can set `owner.login` to their own org (so `verify_signature` succeeds) while setting `repository.full_name` to `victim-org/victim-repo` (so handlers act on the victim's stack).

This is the direct analog of the lnd bug class: a value used for one purpose (selecting/authenticating against a keyed record) is trusted without re-validating that a *different* value derived from the same unauthenticated input, and used for the actual state-changing action, matches it — i.e. an "authenticated identity" vs "acted-upon identity" mismatch, only here it's an availability/integrity mismatch across a trust boundary rather than a type-assertion panic.

### Impact Explanation
An attacker with a valid webhook secret for any single organization configured on the instance can forge webhook deliveries that affect **any other organization's stacks** hosted on the same Shipit deployment:
- Force `PushHandler` to trigger `stack.sync_github` on a victim stack/branch.
- Force `CheckSuiteHandler`/`StatusHandler` to inject bogus commit statuses/check-run refreshes that influence a victim stack's deployability gates.
- Force `PullRequest::ClosedHandler` to archive a victim's review stack.

This is a cross-tenant integrity break: actions on a stack are triggered using a webhook signature that was never actually generated by (or for) the owning organization/repository, breaking the "organization authenticated vs. repository acted upon" binding called out in scope.

### Likelihood Explanation
Requires the target deployment to be configured in the multi-organization mode (`secrets.github` keyed by org, each with its own `webhook_secret`) and requires the attacker to already legitimately hold a webhook secret for at least one organization onboarded to the shared instance — a realistic scenario for shared/multi-tenant Shipit deployments where different teams/orgs configure their own webhook secrets independently but share the same Shipit instance and webhook endpoint. No GitHub App private key, session, or `ApiClient` token is needed; only the HTTP webhook endpoint and knowledge of one org's `webhook_secret`.

### Recommendation
After signature verification, re-derive the organization from `repository.full_name`'s owner segment (or `organization.login` for org-scoped events) and require it to match the organization whose secret was used to verify the signature; reject the request otherwise.

### Proof of Concept
1. Attacker legitimately controls organization `attacker-org`, configured on the shared Shipit instance with webhook secret `S`.
2. Attacker crafts a `push` payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, which succeeds because the signature matches `attacker-org`'s secret [9](#0-8) .
5. `PushHandler#process` resolves `stacks` from `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github` on the victim's stack [6](#0-5) , even though the request was never signed by, or intended for, `victim-org`.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
