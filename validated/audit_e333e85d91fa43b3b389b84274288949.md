Based on my investigation, I found a legitimate structural analog to the Rolla `QToken` symbol-collision issue within this repo's Snowbridge asset-registration path.

### Title
Arbitrary, unvalidated token `name`/`symbol` metadata in `register_token` allows symbol spoofing of bridged assets - (File: `system-parachains/asset-hubs/asset-hub-polkadot/src/bridge_to_ethereum_config.rs`)

### Summary
Similar to the Rolla report — where a `QToken`'s human-readable `symbol` is not guaranteed to be unique/collision-free, letting users be tricked into trading the wrong option — this runtime's Snowbridge `register_token` extrinsic lets any asset owner (not just root) freely choose an arbitrary `AssetMetadata{name, symbol, decimals}` for a token being bridged to Ethereum, with no uniqueness or reserved-word check against existing, well-known symbols (e.g. `DOT`, `USDT`, `KSM`).

### Finding Description
`RegisterTokenOrigin` for `snowbridge_pallet_system_frontend::Config` on Asset Hub Polkadot permits either `LocalAssetOwner` or `ForeignAssetOwner` (i.e., any account that owns/controls the underlying asset location) to call `register_token`, in addition to root: [1](#0-0) 

The caller supplies the `AssetMetadata` (`name`, `symbol`, `decimals`) directly, and this is only checked for ownership of the location, not for content collisions with existing registered tokens' symbols, as shown across the test suite where arbitrary strings like `"usdt"`, `"dot"`, `"ah_asset"` are freely passed in by callers: [2](#0-1) [3](#0-2) 

The only origin restriction enforced is *who* can register a given asset location (its owner), not *what* symbol/name they may pick — e.g., a legitimate owner of some unrelated foreign asset can still set `symbol: "USDT"` or `symbol: "DOT"` for their own asset, since the check is purely about asset ownership, not symbol content: [4](#0-3) 

### Impact Explanation
Once registered, this metadata is propagated to Ethereum via the outbound queue (`MessageQueued`/token registration events), where wallets/DEXs on the Ethereum side display the bridged token by the chosen `symbol`/`name`. As with the Rolla finding, this can mislead end users into interacting with (trading, approving, bridging) a spoofed/incorrect token that displays an identifier matching a legitimate, well-known asset (e.g. `DOT`, `USDT`, `KSM`), while actually being backed by a different, attacker-chosen Polkadot-side asset location.

### Likelihood Explanation
Likelihood is moderate: the actor must legitimately own/control some asset (local trust-backed asset or foreign asset reserve) on Asset Hub — this is a realistic bar for an unprivileged but resourceful user (e.g., creating a cheap `pallet-assets` asset, then calling `register_token` for it with a spoofed symbol), not a trusted-role compromise. No special privilege beyond asset creation/ownership is required.

### Recommendation
Add a symbol/name collision check in `register_token` (or in the pallet's runtime `Config`) that rejects registration if the requested `symbol`/`name` matches an already-registered token's metadata (case-insensitively), or reserve well-known symbols (`DOT`, `KSM`, `USDT`, `USDC`, etc.) so they can only be set by `EnsureRootWithSuccess`, consistent with how `register_relay_token_from_asset_hub_user_origin_will_fail` already restricts the native relay token's symbol to root-only registration: [5](#0-4) 

### Proof of Concept
1. An unprivileged user creates or owns a `pallet-assets`/`pallet-foreign-assets` asset on Asset Hub Polkadot for some arbitrary location (e.g. a wrapped, low-value token).
2. The user calls `SnowbridgeSystemFrontend::register_token` as the owner, as shown in the test pattern: [6](#0-5) , but substitutes `symbol: "USDT"` / `name: "usdt"` instead of the real USDT's metadata.
3. `RegisterTokenOrigin`'s `LocalAssetOwner`/`ForeignAssetOwner` check passes because the user does own that particular asset location — there is no check that the symbol collides with the real, already-registered USDT token.
4. The spoofed token is registered on Ethereum with a `MessageQueued` event, and downstream wallets/DEXs may display it as `"USDT"`, leading users to trade against the wrong contract, mirroring the QToken symbol-collision issue.
