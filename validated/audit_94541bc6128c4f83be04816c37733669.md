### Title
Stale/superseded address definitions remain valid for `is_valid_signature()` / signed-message verification, bypassing key-revocation via `address_definition_change` - (File: `signed_message.js`)

### Summary
The GitLab report describes a credential (token) that should have been invalidated by a state change (password expiry) but was still accepted by an alternate access path (API/Git) because that path skipped the freshness check enforced elsewhere. `ocore` has an analogous inconsistency: full unit authorship validation (`validateAuthor` in `validation.js`) always resolves an address to its **current, latest stable definition** via `storage.readDefinitionByAddress` and additionally blocks any pending/unstable key change with `checkNoPendingChangeOfDefinitionChash`/`checkNoPendingDefinition` [1](#0-0) , so once a user rotates their address definition (e.g., because a key was compromised), the old key can no longer author units. The parallel signed-message verification path in `signed_message.js`, which backs the `is_valid_signature()` oscript function used by Autonomous Agents, does not enforce the same freshness guarantee in its non-network-aware branch.

### Finding Description
`validateSignedMessage` has two verification modes selected by the presence of `last_ball_unit`:

- **Network-aware** (`bNetworkAware = true`): resolves the address's definition as of `last_ball_mci`, which is closer to (but still can lag) the "current" definition used by full unit validation.
- **Non-network-aware** (`bNetworkAware = false`, no `last_ball_unit` field): the code only checks that the *supplied* definition hashes to the address, with no reference to whatever definition is currently active for that address: [2](#0-1) 

Because an Obyte address is a `chash160` of its **initial** definition, and that value never changes even after the owner rotates keys with an `address_definition_change` message, this check `objectHash.getChash160(objAuthor.definition) === objAuthor.address` is satisfied by supplying the **original (now-superseded) definition** — i.e., the old, revoked key. The verifier then runs `Definition.validateAuthentifiers` against that stale definition [3](#0-2) , with no lookup of the address's actual current definition and no check for a pending/blocked key change (unlike `validateAuthor`'s `checkNoPendingChangeOfDefinitionChash`) [4](#0-3) .

This is the same bug class as the report: a security-relevant state transition (definition/key rotation, analogous to a password reset) is enforced on the "main" path (unit authoring) but silently bypassable on a secondary, still-trusted verification path (signed-message / `is_valid_signature`).

### Impact Explanation
`validateSignedMessage` underlies the `is_valid_signature()` oscript function, which AAs commonly use to authenticate off-chain-signed data (e.g., authorization messages, oracle-style attestations, claims used to release/route AA funds) without requiring a full DAG unit. If an address owner rotates their definition specifically to revoke a compromised or no-longer-trusted key, anyone still in possession of the old private key can produce a signed message that still validates successfully with `is_valid_signature()` when the caller omits `last_ball_unit` (non-network-aware mode). An AA (or any application logic) that trusts this function to gate fund release, permissioned actions, or data-feed authenticity can therefore act on authorization from a key the user believed was revoked, leading to unauthorized AA fund movement/loss or acceptance of forged authorization for actions tied to that address.

### Likelihood Explanation
Exploitation only requires possession of the original private key (which the attacker has by definition of a "compromised key" scenario prompting rotation) and knowledge that the target AA/dApp calls `is_valid_signature()`/`validateSignedMessage` without a `last_ball_unit`, which is a common and simpler usage pattern in oscript templates. No special privileges, network position, or race condition are required — it is a straightforward re-use of a revoked signing key against a component that other on-chain logic (AA) treats as authoritative proof of authorization for the address.

### Recommendation
In the non-network-aware branch of `validateSignedMessage` (`signed_message.js`, function `validateOrReadDefinition`), do not accept the definition solely because it hashes to the address. Instead, always resolve and use the address's **current** definition (as `validateAuthor` does via `storage.readDefinitionByAddress`), and reject supplied definitions that don't match the currently active one, or explicitly document/require `last_ball_unit` for any use of `is_valid_signature()` where authorization freshness matters, and have `formula/evaluation.js`'s `is_valid_signature` reject/flag non-network-aware calls for AA-trust-sensitive use cases.

### Proof of Concept
1. Address `A` is created with initial definition `D_old` (so `chash160(D_old) === A`), and the corresponding private key `K_old` is later suspected compromised.
2. Owner posts an `address_definition_change` unit updating `A`'s active definition to `D_new` (signed with `K_old`, as required) — analogous to "resetting the password."
3. Attacker, still holding `K_old`/`D_old`, constructs a `signed_message` object with authors `[{address: A, definition: D_old, authentifiers: {...signed with K_old}}]` and **no `last_ball_unit` field**.
4. Any caller of `validateSignedMessage`/`is_valid_signature()` on this object with `address = A` succeeds, because `validateOrReadDefinition`'s non-network-aware branch only checks `chash160(D_old) === A` [2](#0-1)  and never consults the address's current (`D_new`) definition.
5. Any AA/oscript logic relying on `is_valid_signature()` to gate an action for address `A` accepts the message as legitimately authorized by `A`, despite the key having been rotated out.
