### Title
Unbounded `system_votes` growth lets any unit author DoS main-chain stabilization via `countVotes` - (File: main_chain.js)

### Summary
`countVotes()` in `main_chain.js` is invoked synchronously during main-chain stabilization (`markMcIndexStable`) whenever a `system_vote_count` message becomes stable. It reads **every distinct address that ever voted** for a subject via `SELECT DISTINCT address FROM system_votes WHERE subject=?` and builds an in-memory/SQL `IN (...)` list from it with no upper bound, then runs several further queries keyed on that unbounded address list.

### Finding Description
Any unprivileged unit author can attach a `system_vote` message to a unit they post; validation only checks structural well-formedness of the vote (valid subject/value, sorted/valid OP addresses, etc.) with no restriction on which addresses may vote and no cap on the number of distinct voting addresses over time: [1](#0-0) 
Each distinct author address that ever casts a `system_vote` is permanently recorded in `system_votes`, and stabilization then persists it: [2](#0-1) 
There is no limit on the number of unique addresses; an attacker can create arbitrarily many addresses (each requiring only a small amount of funds to author a unit) and have each cast a `system_vote`. Any author can also freely add a `system_vote_count` message, which is themselves subject to no special permission: [3](#0-2) 
Once a `system_vote_count` unit becomes stable, `countVotes()` runs unconditionally for that subject as part of `markMcIndexStable`, on the hot consensus path shared by every node: [4](#0-3) 
Inside `countVotes()`, the full historical set of distinct voter addresses for the subject is loaded without any pagination/limit and used to build a `strAddresses` list used in subsequent balance/`voter_balances` queries: [5](#0-4) 
This list then drives multiple further unbounded operations, including a `while(true)` loop widening the vote time window and repeatedly re-scanning `system_votes`/`voter_balances` for the growing address set, and per-address `op_votes`/`numerical_votes` INSERT statement construction: [6](#0-5) [7](#0-6) 
As the number of distinct addresses that have ever voted grows (which is entirely attacker-controlled and cumulative — votes are never pruned, only overridden per-address), the SQL statement size, memory usage, and query cost of `countVotes()` grow without bound. Because this function runs synchronously and is not resumable/incremental (it's an atomic all-or-nothing pass over `assocUnstableUnits`/`system_votes` executed inside the same DB transaction as stabilization), a sufficiently large address set can make `countVotes()` (and thus `markMcIndexStable`) take excessively long or exceed statement-size/memory limits, stalling stabilization for the whole node.

### Impact Explanation
Because `countVotes()` is invoked from `markMcIndexStable`, which every full node executes to advance the stability point, a sufficiently bloated `system_votes` table can stall or crash stabilization on all full nodes that process the offending `system_vote_count` unit once it stabilizes. This is a node-wide denial of service impacting the network's ability to confirm new units past that MCI (stabilization halts network-wide, not just for one peer), which matches the "network unable to confirm new units" acceptance criterion. Unlike the original report's per-contract impact, here the blast radius is the entire DAG's stabilization pipeline.

### Likelihood Explanation
Likelihood is moderate: an attacker needs to fund and post many low-value units, each from a distinct address, each containing a valid `system_vote` message, over time (votes are cumulative and never deleted from `system_votes`, only overridden), and then post one `system_vote_count` unit. There's no admin/witness gate preventing this — any address can vote and any address can trigger the count. The cost to the attacker scales roughly linearly with the number of poison addresses (transaction fees to post units), which is a real but non-trivial economic barrier; still, over enough time this is entirely achievable by a moderately funded attacker, and the resulting query/loop cost inside `countVotes()` scales with total accumulated voters, not with recent activity, since old votes are read via `SELECT DISTINCT address FROM system_votes WHERE subject=?` with no bound.

### Recommendation
- Cap the number of distinct voters considered per subject (e.g., limit to top-N addresses by balance, or require a minimum balance/bond to have a vote counted) rather than scanning all-time distinct addresses.
- Add an explicit sanity limit / reject-and-log path in `countVotes()` if the address set for a subject exceeds a safe threshold, rather than building unbounded SQL `IN`/`VALUES` lists.
- Consider pruning or compacting `system_votes` for addresses whose current balance is (and has long been) zero, since they cannot contribute to the vote-balance threshold anyway.
- Batch the address-list based queries in `countVotes()` (`voter_balances` inserts, `op_votes`/`numerical_votes` inserts) so a single unbounded string-concatenated SQL statement is never constructed.

### Proof of Concept
1. Attacker generates `N` (e.g., 100k) distinct addresses, funding each with the minimal amount needed to author one unit.
2. From each address, post a unit containing a `system_vote` message for `subject: "threshold_size"` (or another cheap subject) — validated per [8](#0-7)  with no per-address cap.
3. Once these units are stable, post one more unit containing a `system_vote_count` message for the same subject — validated per [3](#0-2) .
4. When this unit stabilizes, every full node calls `countVotes()` per [4](#0-3) , which loads all `N` distinct addresses [9](#0-8)  and performs address-list-bound queries and a widening `while(true)` balance-sum loop [10](#0-9) , whose cost scales with `N`, on the shared stabilization path for every node in the network.
