### Title
Unhandled exception via malformed c-hash decoding in `isChashValid` reachable through `isValidAddressAnyCase` - (File: chash.js)

### Summary
CVE-2016-3822 is an out-of-bounds/crafted-length parsing bug in `jhead`'s EXIF parser: a maliciously-crafted length field drives the parser to read/write outside the intended buffer, causing a crash or code execution. The closest reachable analog in this codebase is the c-hash checksum parser in `chash.js`, where a decoded buffer whose bit-length does not match the two hard-coded expected lengths (160/288) causes an uncaught `throw Error(...)` deep inside `separateIntoCleanDataAndChecksum`/`checkLength`, outside of any `try/catch`, when reached through the unchecked entry point `isValidAddressAnyCase`.

### Finding Description
`chash.isChashValid(encoded)` [1](#0-0)  decodes an externally supplied string with `base32.decode()` or `Buffer.from(encoded,'base64')` inside a `try/catch`, but the subsequent steps — `buffer2bin(chash)` and `separateIntoCleanDataAndChecksum(binChash)` — are **not** covered by that `try/catch`: [2](#0-1) 

`separateIntoCleanDataAndChecksum` only accepts bit-strings of exactly 160 or 288 bits; any other length causes an unguarded `throw Error("bad length=...")`: [3](#0-2) 

The public entry `isValidAddress` first enforces a strict base32 charset and length via `/^[A-Z2-7]{32}$/` before calling `isValidChash`, guaranteeing `base32.decode` always yields exactly 20 bytes (160 bits): [4](#0-3) . However, `isValidAddressAnyCase` calls `isValidChash` **without** that charset restriction: [5](#0-4) , relying solely on `isStringOfLength(address,32)`: [6](#0-5) . Because the `thirty-two` base32 library is lenient with character sets/padding, a 32-character string containing characters outside `[A-Z2-7]` (but still decodable) can produce a decoded buffer whose length is not exactly 20 bytes, causing the uncaught `throw` in `separateIntoCleanDataAndChecksum` to propagate out of `isChashValid` → `isValidChash` → `isValidAddressAnyCase`, crashing the calling code path if it is not itself defensively wrapped.

This mirrors the jhead bug class: a length value derived from attacker-controlled encoded data is trusted without being re-validated against the actual expected structure before being used to index/parse further, and the failure path is an unhandled low-level exception rather than a graceful validation error.

### Impact Explanation
An uncaught exception thrown from a fundamental validation utility that is invoked while processing untrusted, network-supplied data (units, AA triggers, private payment/attestation payloads, addresses referenced in oscript) can propagate up through asynchronous validation call chains and crash the Node.js process handling that data, i.e., a node can be made to fail while validating/relaying a unit, which — if this path is reachable from unit or trigger processing without a wrapping `try/catch` — could make affected nodes unable to validate/confirm new units (denial of validation for the network segment relying on that node).

### Likelihood Explanation
Reachability depends on finding a caller of `isValidAddressAnyCase` (rather than `isValidAddress`) that processes attacker-controlled address-like strings without its own `try/catch`. I found only two call sites in `validation_utils.js` (self-referencing) and one in `validation.js`, but I was not able to fully inspect that single call site in `validation.js` before running out of tool iterations, so I cannot confirm with certainty whether it operates on untrusted external input or whether it is wrapped in a `try/catch` at the call site. This uncertainty means the finding should be treated as **plausible but unverified** — a background Devin session with full read access to `validation.js` (and its callers) would be needed to confirm exact reachability from a posted unit/trigger/attestation payload.

### Recommendation
Wrap `buffer2bin(chash)` and `separateIntoCleanDataAndChecksum(binChash)` inside the same `try/catch` in `isChashValid` that currently only guards the decode step, and return `false` on any parsing failure instead of throwing. Additionally, align `isValidAddressAnyCase` with `isValidAddress` by validating the character set of the c-hash-encoded string before calling `isValidChash`, so that malformed/lenient base32 decoding cannot produce buffers of unexpected length.

### Proof of Concept
Not independently verified end-to-end due to tool-call exhaustion; the theoretical PoC is:
1. Construct a 32-character string that is not `/^[A-Z2-7]{32}$/` (e.g., contains lowercase or other characters accepted by the `thirty-two` decoder) such that `base32.decode()` returns a buffer whose length is not exactly 20 bytes.
2. Call `ValidationUtils.isValidAddressAnyCase(str)`.
3. Observe `chash.isChashValid` throwing an uncaught `Error("bad length=...")` from `separateIntoCleanDataAndChecksum`, propagating past `isChashValid`/`isValidChash`/`isValidAddressAnyCase` since none of them catch it.

Given the incomplete verification of the exact reachability from network-facing validation code, this should be confirmed with further investigation of all callers of `isValidAddressAnyCase` in `validation.js` before treating it as a confirmed high-severity finding.
