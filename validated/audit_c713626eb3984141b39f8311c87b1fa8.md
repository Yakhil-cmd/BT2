### Title
Unsanitized CR/LF in check name, description, and link fields enables terminal output/prompt spoofing in `gh pr checks` - (File: pkg/cmd/pr/checks/output.go)

### Summary
`addRow` in `pkg/cmd/pr/checks/output.go` feeds `o.Name`, `o.Description`, `o.Workflow`, `o.Event`, and `o.Link` directly into `tp.AddField(...)` without stripping carriage returns or newlines, unlike sibling list commands in the same codebase that explicitly sanitize attacker-controlled text before adding it to a table. Because these fields originate from GitHub Checks API data that an unprivileged fork/PR author fully controls (check-run name, output title, details URL), a crafted value containing `\r` can redraw the current terminal line and visually spoof trusted `gh` output, including a fake credential prompt.

### Finding Description
`printTable` builds the checks table by calling `addRow` for every check, and `addRow` writes `o.Name` (workflow/job name), `o.Description` (check output title/summary), and `o.Link` (details URL) straight into the table cell via `tp.AddField(...)` with no escaping: [1](#0-0) 

Compare this with other table-rendering commands in the same codebase, which explicitly collapse embedded newlines/carriage returns from remote-controlled text (issue titles, discussion titles, release names, commit messages, project field values) before adding them as table fields: [2](#0-1) [3](#0-2) [4](#0-3) 

This established, repo-wide convention (`text.RemoveExcessiveWhitespace` / `singleLineFieldValue`) exists specifically because free-form remote text can contain `\r`/`\n` that corrupts single-line table rendering, and its consistent presence elsewhere strongly implies the underlying `tableprinter` does not itself strip these control characters — `printTable`/`addRow` in `pkg/cmd/pr/checks/output.go` is the outlier that omits this sanitization for `Name`, `Description`, and `Link`.

An attacker who opens a PR from a fork (or otherwise causes a check run to be reported against a PR, e.g. via a workflow job name or check-run title they control) can set the check/job name or output title to contain a `\r` followed by fabricated text such as `? Paste your GitHub token: `. When a victim later runs `gh pr checks` against that PR, the maintainer's terminal renders the malicious row; the embedded `\r` resets the cursor to the start of the current line, and characters after it (attacker's forged prompt text) overwrite what preceded it on that line, producing output that looks like a legitimate `gh`/credential prompt even though `gh` never actually reads input at that point.

### Impact Explanation
This is a terminal output/prompt spoofing issue: the victim sees fabricated, trusted-looking `gh` text (e.g., a fake "paste your token" prompt) that they did not expect, potentially causing them to paste a secret into their terminal (which could then be captured by other means, e.g. shell history, or misinterpreted as a command if combined with a trailing newline). This matches the "Terminal output/prompt spoofing leading to credential capture or unintended destructive confirmation" impact class referenced in the question. It does not by itself achieve remote code execution or direct exfiltration since `gh pr checks` does not read stdin during/after rendering, but it is a legitimate output-integrity/spoofing weakness with a plausible path to credential exposure through victim confusion.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs to control a public repo/fork/PR check-run's name, output title, or details URL (achievable by any unprivileged GitHub user via a workflow job name or an app reporting a check run) and does not require any special privilege on the victim's repo or account. The victim needs only to run `gh pr checks` on the attacker's PR, which is an ordinary workflow for reviewers/maintainers.

### Recommendation
Sanitize `o.Name`, `o.Description`, `o.Workflow`, `o.Event`, and `o.Link` in `addRow` (pkg/cmd/pr/checks/output.go) the same way other commands do — strip `\r` and collapse `\n` to a space (e.g., reuse `text.RemoveExcessiveWhitespace` or a `singleLineFieldValue`-style helper) before calling `tp.AddField`, so remote text cannot reposition the cursor or overwrite prior terminal output.

### Proof of Concept
Go unit test asserting no `\r` reaches the rendered table for a check whose `Name`/`Description` contain a crafted spoofing payload:

```go
func TestPrintTable_NoCarriageReturnInjection(t *testing.T) {
    io, _, out, _ := iostreams.Test()
    io.SetStdoutTTY(true)

    checks := []check{
        {
            Name:        "build\r? Paste your GitHub token: ",
            Description: "ok\rFake prompt",
            Bucket:      "pass",
            Link:        "https://example.com",
        },
    }

    err := printTable(io, checks)
    require.NoError(t, err)

    rendered := out.String()
    require.NotContains(t, rendered, "\r", "rendered table must not contain raw carriage returns")
}
```
Expected (current) behavior: the assertion fails because `\r` from `Name`/`Description` passes through `addRow` unmodified into the rendered table, confirming the missing sanitization.

// singleLineFieldValue collapses carriage returns and newlines so a multi-line
// field value stays within a single table cell. Following the convention used by
// StatusItem.Preview, carriage returns are dropped and newlines become spaces.
func singleLineFieldValue(s string) string {
	return strings.ReplaceAll(strings.ReplaceAll(s, "\r", ""), "\n", " ")
}
