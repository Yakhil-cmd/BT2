## Title
Cross-organization/cross-repository webhook forgery via signature-verified-org vs. content-written-repository mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The reported bug class ("acting on a payload value that the verification step never actually authenticated for") has a direct analog in Shipit's webhook ingestion pipeline. The `X-Hub-Signature` check authenticates only that *some* configured GitHub organization's secret produced the HMAC over the raw body — it authenticates the **organization**, not the specific repository the handlers then act on. Handlers resolve the target repository from a *different* JSON field in the same attacker-crafted body, with no cross-check that it matches the organization whose secret was used to authenticate the request.

### Finding Description
`Shipit::WebhooksController#verify_signature` derives which org's `webhook_secret` to validate against from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). This is only used to pick which of Shipit's configured GitHub Apps' secret (`Shipit.github(organization: repository_owner)`) verifies the HMAC over the raw request body.

Once verified, the event is dispatched to handlers that resolve the actual repository/commit target from a **different** field of the same body: [3](#0-2) 

`repository_name` comes from `payload.dig('repository', 'full_name')` — a value never compared against `repository_owner` used in signature verification. Nothing in `Repository.from_github_repo_name` or the handler layer enforces that `repository.full_name`'s owner segment equals `repository.owner.login`/`organization.login`.

Worse, `StatusHandler` doesn't even scope by repository: [4](#0-3) 

`Commit.where(sha: params.sha)` looks up a commit by SHA **globally across the entire Shipit instance**, with no repository or organization filter at all.

In a multi-organization Shipit deployment (the config schema explicitly supports this, each org with its own `webhook_secret`): [5](#0-4) 

any organization that is a legitimate customer of the platform — and therefore legitimately knows its own `webhook_secret` — can POST directly to the public, unauthenticated `/webhooks` endpoint (no session, no `ApiClient` token required) with a body it signs correctly using its own secret, while filling in `repository.full_name` (for push/check_suite handlers) or `sha` (for `StatusHandler`, unscoped) that reference a completely different organization's/tenant's repository or commit.

The binding that should hold is:
`organization authenticated by verify_signature == organization owning the repository/commit acted upon by the handler`

This is broken because `verify_signature` only proves "the sender knows org X's secret," while the handlers act on repository/commit identifiers taken from unauthenticated fields of the same body.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy, rollback or merge" impact bar named in scope:
- `StatusHandler` lets any org with a valid `webhook_secret` write a forged commit `Status` (`state`, `context`, `target_url`, `description`) onto **any commit in any stack in the Shipit instance**, not just its own repositories, since the lookup is entirely unscoped. Because commit statuses are the primary signal Shipit uses for deployability/merge gating, this is a cross-tenant write that can flip a commit's perceived CI state and influence merge/deploy decisions on repositories the attacker's organization has no legitimate access to.
- `PushHandler`/`CheckSuiteHandler` similarly resolve `stacks` via `Repository.from_github_repo_name(repository_name)`, where `repository_name` is an unauthenticated field, letting one org trigger GitHub sync/check-run refresh jobs against another org's stacks using Shipit's own GitHub credentials for that unrelated repository.

### Likelihood Explanation
Any tenant that legitimately operates a GitHub App/org registered in Shipit's `github:` config already possesses a valid `webhook_secret` for signing its own requests — this is not a "stolen secret" scenario, it is the credential the platform hands to every onboarded organization. The `/webhooks` endpoint is unauthenticated apart from that per-organization HMAC, and none of the handler code cross-checks the verified organization against the repository/commit fields the handler acts on. This makes the analog straightforwardly reachable by any unprivileged (from the target repository's perspective) but validly-onboarded organization.

### Recommendation
After `verify_signature` succeeds, re-derive the repository/commit target strictly from fields whose ownership was proven by the verified organization (e.g., require `payload.dig('repository','owner','login')` used for signature selection to equal the owner segment of `payload.dig('repository','full_name')`), and scope `StatusHandler`'s `Commit.where(sha:)` lookup to commits belonging to stacks owned by the authenticated organization, rather than a global, unscoped SHA search.

### Proof of Concept
1. Shipit is configured with two GitHub orgs, `org-a` (victim, tracked stacks) and `org-b` (attacker-controlled but legitimately onboarded, so it holds a real `webhook_secret_b`).
2. Attacker crafts a `status` event payload: `{"sha": "<known commit sha of an org-a stack>", "state": "success", "repository": {"owner": {"login": "org-b"}, "full_name": "org-b/whatever"}}`.
3. Attacker signs the raw body with `webhook_secret_b` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `org-b`, verifies successfully against `webhook_secret_b`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matches the org-a commit regardless of the fact that the authenticated organization was `org-b` — and writes a forged `Status` on it.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
