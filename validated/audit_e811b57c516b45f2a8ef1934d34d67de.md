### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field of the same unverified JSON body - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to use for HMAC validation based on `repository.owner.login` (falling back to `organization.login`), but the individual webhook handlers (e.g. `PushHandler`, the `pull_request` handlers) resolve the actual `Repository`/`Stack` to mutate using the completely separate `repository.full_name` field from the same, otherwise-unverified JSON body. Nothing cross-checks that these two fields refer to the same repository/organization.

### Finding Description
`WebhooksController#verify_signature` derives the org used to pick the webhook secret purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GitHubApp` instance carrying that organization's own `webhook_secret` (Shipit supports one distinct GitHub App/secret per organization, as documented in `docs/setup.md`'s multi-org config example). The signature check only proves that *some* configured organization's secret produced this HMAC: [3](#0-2) 

Once verified, the controller dispatches the **entire raw params** — not just the `repository`/`organization` sub-object used for verification — to the handler registered for the event: [4](#0-3) 

Handlers determine which `Stack`/`Repository` to act on using `repository.full_name`, a different JSON field from the one used to select the signing secret: [5](#0-4) [6](#0-5) 

The equality that should hold but does not:
`organization used to authorize signature (repository.owner.login / organization.login)` == `organization implied by repository.full_name used to select the Stack acted upon`.

Because the whole HMAC covers the raw body, in principle a legitimate GitHub-generated payload always has these fields consistent. The break occurs because an attacker who legitimately controls (and thus knows the `webhook_secret` of) one org registered in Shipit's multi-org configuration can hand-craft an arbitrary raw JSON body — since `WebhooksController#create` never re-validates that the payload actually originated from GitHub's servers beyond the HMAC, any attacker holding a valid secret for org A can forge a `repository.owner.login: "org-A"` (to pass signature selection) while setting `repository.full_name: "org-B/victim-repo"` (to target an arbitrary Stack tracked by Shipit for a different organization).

### Impact Explanation
A successfully forged webhook lets an attacker who controls one onboarded organization's GitHub App/webhook secret trigger event handling for stacks belonging to a **different** organization/repository, e.g.:
- `PushHandler#process` invoking `stack.sync_github(expected_head_sha: params.after)` for a victim's stack: [7](#0-6)  — this fetches commits from GitHub for that stack and appends them, and can trigger `CacheDeploySpecJob`, corrupting or forcing sync state for a repository the attacker does not own.
- Several `pull_request` handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, etc.) resolve `Repository.from_github_repo_name(params.repository.full_name)` and can archive/unarchive/create review stacks belonging to the victim organization.

This crosses the "cross-repository writes" bar in the Critical impact category, since state belonging to a repository/organization outside the authenticated one is mutated.

### Likelihood Explanation
Exploitability is contingent on Shipit being deployed with the multi-organization GitHub App configuration (`docs/setup.md`'s example with per-org `webhook_secret`), and the attacker being an admin/owner of at least one of the onboarded organizations (so they legitimately possess that org's own `webhook_secret`). In a typical single-organization/single-GitHub-App deployment, all repos share one secret and this specific binding break (org-selection vs. repo-selection) is not exploitable this way, though it still shows the general design flaw of no cross-field consistency check.

### Recommendation
- After signature verification succeeds, re-derive `repository_owner`/`organization` a second time from the payload consumed by the handler and assert it equals the owner encoded in `repository.full_name` before dispatching.
- Alternatively, make each handler's `Repository.from_github_repo_name` lookup validate that the resolved repository's owner matches the organization whose secret validated the request.
- Consider signing/verifying per-organization webhooks with a nonce or organization-bound claim embedded and checked at the handler layer, not just at the controller layer.

### Proof of Concept
Preconditions: Shipit configured with multiple orgs, e.g. `org-A` and `org-B` (victim), each with distinct GitHub Apps/`webhook_secret`s as shown in `docs/setup.md`. Attacker is an admin of `org-A` and thus knows `org-A`'s `webhook_secret`.

1. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-A" },
    "full_name": "org-B/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-A's webhook_secret, body)>`.
3. POST to `/webhooks` with `X-Github-Event: push` and the above signature.
4. `verify_signature` resolves `repository_owner = "org-A"`, fetches `org-A`'s `GitHubApp`, and the HMAC check passes (attacker knows the secret they used to sign it).
5. `create` parses the full body and dispatches to `PushHandler`, which resolves `stacks` via `payload.dig('repository','full_name')` = `"org-B/victim-repo"`, causing `GithubSyncJob`/`sync_github` to run against the victim's stack — despite the request never being signed by org-B's GitHub App.

Note: I could not fully trace `Stack#sync_github`'s downstream write behavior or `Shipit.github`'s full org-resolution/`GithubOrganizationUnknown` logic (`lib/shipit.rb`) within the available context/iterations; a Devin session with full repo access would be needed to confirm the exact multi-org secret resolution code and whether any additional cross-checks exist elsewhere in `lib/shipit.rb` that might mitigate this before it reaches the handler.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
