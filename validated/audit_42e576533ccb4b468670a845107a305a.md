### Title
Stale/Superseded Address Definitions Accepted by `is_valid_signed_package()` When `last_ball_unit` Is Omitted - (File: signed_message.js)

### Summary
`is_valid_signed_package()` in oscript/AA formulas lets an AA author "authorize" fund release, order matching, or channel updates based on a signed message tied to some address. When the caller-supplied `signed_package` omits `last_ball_unit`, `validateSignedMessage()` takes the "no references" branch and only checks that `chash160(author.definition) === author.address`, without ever consulting whether that definition is still the address's *current, effective* definition on the DAG. An address's definition can be superseded via `change` / `has definition change` mechanics, effectively "rotating out" old keys, yet the old, superseded definition + its corresponding private key still satisfies `is_valid_signed_package()` forever. This mirrors the ZITADEL bug class: one validation path (network-aware, tied to a stable `last_ball_unit`) correctly resolves the address's live definition, while the other path (no references) accepts stale/expired key material for an authorization decision.

### Finding Description
In `formula/evaluation.js` the `is_valid_signed_package` opcode only enforces `last_ball_unit` constraints *if the field is present*: [1](#0-0) 

If `signedPackage.last_ball_unit` is absent, `signed_message.validateSignedMessage()` is called with `bNetworkAware = ("last_ball_unit" in objSignedMessage)` evaluating to `false`: [2](#0-1) 

In the network-aware branch, the code correctly re-derives the address's definition as of the last stable ball via `storage.readDefinitionByAddress`, and explicitly rejects an attacker-supplied inline `definition` once the address already has one on record (`ifFound: ... if (bHasDefinition) return handleResult("should not include definition")`): [3](#0-2) 

But the non-network-aware (`bNoReferences`) branch simply trusts whatever `definition` the caller attaches, as long as its hash equals the address, with no lookup of the address's actual/current definition on the DAG: [4](#0-3) 

This means: once an address rotates its key/definition (e.g., via `["cosigned by"]`, multisig re-key, or `change definition` upgrade paths defined in `definition.js`), the *old* definition/key pair remains fully capable of producing a `signed_message` payload that `is_valid_signed_package()` accepts as `true`, provided the attacker simply drops `last_ball_unit` from the package. There is no expiry/staleness check comparable to the one enforced in the network-aware path.

### Impact Explanation
AAs that use `is_valid_signed_package()` as an authorization gate (e.g., off-chain vouchers for payment channels, order-book matching, or any oscript pattern that trusts a signed statement from a counterparty address to release/allocate AA-held funds — as seen in `test/samples/payment_channels.oscript` and `test/samples/order_book_exchange.oscript`) can be tricked into accepting authorization from a key the address owner believes has been revoked/rotated out. An attacker who once held a valid signing key for an address, after the legitimate owner rotates the address's definition (e.g., following suspected compromise), can still forge fresh `is_valid_signed_package()`-passing messages using the old key and drain or misdirect AA funds gated on that address's authorization — a concrete AA fund loss scenario reachable by any AA trigger sender who controls the `signed_package` argument.

### Likelihood Explanation
Exploitability requires: (1) an AA design that gates value transfer/authorization on `is_valid_signed_package()` for a specific address, and (2) that address having rotated away from an old definition while an attacker retains the old private key (e.g., after a suspected leak prompted rotation, or in any multi-key custody rotation). This is a realistic scenario for payment-channel and voucher-style AA patterns explicitly shipped as samples in this repo, making the trigger path readily reachable by any unprivileged AA trigger sender who supplies the `signed_package` data.

### Recommendation
When `last_ball_unit` is absent (`bNoReferences` branch), `validateSignedMessage()` should still verify against the address's current definition on chain when one exists, rather than unconditionally trusting an inline `definition` field — mirroring the `ifFound`/`ifDefinitionNotFound` logic used in the network-aware branch. At minimum, `is_valid_signed_package()` should require `last_ball_unit` to be present (rejecting packages that omit it) so that all authorization checks route through the definition-freshness logic, closing the gap between the two validation paths.

### Proof of Concept
1. Address `A` is created with definition `D1 = ["sig", {pubkey: P1}]`, and its owner later executes a `change`-based definition update to `D2 = ["sig", {pubkey: P2}]` (rotating away from `P1`).
2. An AA `X` contains logic such as `if (is_valid_signed_package(trigger.data.signed_package, address)) { ... release funds ... }`, following the pattern in `test/samples/payment_channels.oscript`.
3. An attacker who still possesses the old private key for `P1` builds:
```json
{
  "signed_message": {...malicious authorization content...},
  "authors": [{
    "address": "A",
    "definition": ["sig", {"pubkey": "P1"}],
    "authentifiers": {"r": "<signature by old key P1>"}
  }]
}
```
   omitting `last_ball_unit` entirely.
4. Triggering AA `X` with this `signed_package` causes `is_valid_signed_package()` to evaluate `true` via the `bNoReferences` branch in `signed_message.js` lines 241-252, because only `chash160(D1) === A` is checked — the fact that `A`'s live definition is now `D2` is never consulted.
5. AA `X` releases funds/authorizes an action based on the stale key `P1`, even though the address owner believed it was revoked.
