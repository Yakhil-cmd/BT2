### Title
Floating-Point Integer Overflow/Precision Loss in Asset Denomination Cap Validation Allows Cap/Supply Mismatch - (File: validation.js)

### Summary
The NATS advisory concerns an unchecked integer addition that can overflow and be exploited by a remote party without special privileges. In `ocore`, the analogous unguarded arithmetic sits in the asset-definition validation path that any unit poster can reach when defining a `fixed_denominations` asset: the per-denomination `count_coins * denomination` products are summed with plain JS number arithmetic and compared against the declared `cap`, with no bound placed on `count_coins` itself.

### Finding Description
When an asset (public or AA-issued) declares `fixed_denominations` with explicit `denominations`, each `denomInfo.count_coins` is only checked with `isPositiveInteger()`, which merely verifies `Math.floor(x) === x` — it never checks `x <= constants.MAX_CAP` or `x <= Number.MAX_SAFE_INTEGER`: [1](#0-0) 

In `validateAssetDefinition`, the loop accumulates `total_cap_from_denominations` using unchecked floating-point multiplication/addition of attacker-controlled `count_coins` and `denomination`: [2](#0-1) 

Only `denomInfo.denomination` is capped by `MAX_CAP` (and only under certain MCI conditions); `count_coins` has no such cap. Because JavaScript numbers are IEEE-754 doubles, once `count_coins * denomination` (or the running sum) exceeds `2^53` (~9.007e15), the addition silently loses precision — a floating-point analog of integer wraparound/overflow (CWE-190). Two different sets of `(denomination, count_coins)` pairs can therefore produce the exact same rounded `total_cap_from_denominations`, even though the “true” mathematical sum differs. Because `payload.cap` is checked only for equality against this imprecise, rounding-prone sum: [3](#0-2) 

an attacker can craft `denominations` where the computed sum matches a chosen `cap` due to floating-point rounding, while the individual per-denomination limits used later at issuance time (`denomination * denomInfo.count_coins`, checked independently per denomination row) do not actually reflect the cap the network believes is authoritative: [4](#0-3) 

The same unguarded pattern is duplicated in the AA asset-definition path, reachable from an AA definition author / AA trigger flow: [5](#0-4) 

### Impact Explanation
If the declared `cap` can be made to falsely appear consistent with a denomination table whose real per-denomination issuance limits sum to a larger amount, an asset issuer could get an asset definition accepted by the network with an advertised cap that undersells the true maximum issuable supply, or otherwise cause the network's belief about total asset supply to diverge from the wallet/wallet-verification logic that also performs this same floating-point sum check. This is a supply-integrity issue (CWE-190 class) for the affected indivisible asset, meeting the "supply inflation" bar for validity, though the practical magnitude depends on how tightly an attacker can align floating-point rounding to produce an exact `===` collision with a target `cap`.

### Likelihood Explanation
Reachable by any unprivileged unit poster who defines an asset (`asset` message) or an AA author who defines an asset inside an AA definition — no special privileges, hub/peer trust, or network position needed. Constructing an exact floating-point collision between the summed value and `cap` is nontrivial but deterministic (attacker fully controls both operands and can precompute IEEE-754 rounding behavior offline before submission), so likelihood is feasible for a motivated attacker but requires precise crafting, keeping it below "trivial."

### Recommendation
- Bound `count_coins` (and the running `total_cap_from_denominations`) by `constants.MAX_CAP` (or `Number.MAX_SAFE_INTEGER`) explicitly in `validation.js` and `aa_validation.js`, rejecting any denomination whose `count_coins * denomination` or cumulative sum exceeds the safe-integer range.
- Perform the cap-consistency check using an arbitrary-precision integer library (e.g., BigInt) instead of native `+=`/`*` on JS numbers, to eliminate floating-point rounding as an attack surface.
- Add unit tests with adversarial `count_coins`/`denomination` values near `2^53` to confirm the check cannot be bypassed by rounding collisions.

### Proof of Concept
Conceptual (not executed, requires precise IEEE-754 crafting to validate in a live environment):
1. Attacker crafts an `asset` message with `fixed_denominations: true`, `cap: X`, and `denominations` array containing entries whose true mathematical sum of `count_coins * denomination` differs from `X`, but whose IEEE-754 double-precision summation (as computed by the exact code path in `validation.js:2763-2783`) rounds to exactly `X`.
2. `validateAssetDefinition` accepts the asset since `total_cap_from_denominations === payload.cap` holds under floating-point rounding, even though the real theoretical maximum issuable amount across per-denomination rows (enforced independently at issuance time in `validateIndivisibleIssue`, `validation.js:2210-2226`) does not match the declared cap.
3. Further work (not verified here) would be needed to demonstrate concrete over-issuance across denominations at spend time to fully confirm supply inflation impact — this requires deeper analysis of `indivisible_asset.js` issuance accounting, which was not fully explored due to iteration limits.
