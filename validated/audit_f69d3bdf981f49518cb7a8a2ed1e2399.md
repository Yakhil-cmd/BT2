### Title
Unvalidated PR label names propagate to review-stack deploy environment variables via `Shipit::PullRequest::LabelCapturingHandler#capture_labels` and `ReviewStack#env` - (File: app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb)

### Summary
`capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim with no allowlist, and `ReviewStack#env` merges every stored label name (upcased) into the process environment used for every deploy `Command` with value `"true"`. This lets any GitHub user who can label a PR on a repository with a Shipit review stack inject arbitrary environment variable *names* (e.g. `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`) into commands spawned via `PTY.spawn`, with no constraint tying accepted label names to the deploy-spec's approved `VariableDefinition` set.

### Finding Description
The claimed binding — "`capture_labels`'s accepted label names == deploy_spec-approved `VariableDefinition` names" — does not hold. `capture_labels` writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` with no filtering [1](#0-0) , and `ReviewStack#env` unconditionally folds every stored label into the env hash: `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` merged over `Stack#env` [2](#0-1) . `Shipit::VariableDefinition` (the deploy-spec-approved variable schema) is never consulted anywhere in this path [3](#0-2) .

This env is consumed by `TaskCommands#env`, which merges `@stack.env` (including the label-derived keys) ahead of `deploy_spec.machine_env` and `@task.env` [4](#0-3) , and ultimately reaches `Command#unbundled_env`, which is passed directly to `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` [5](#0-4) .

Dispatch is reachable via `WebhooksController#create`, gated only by `verify_signature`, which validates the GitHub HMAC signature (or is a no-op if no `webhook_secret` is configured for the organization) [6](#0-5) . This check authenticates that GitHub sent the payload — it does not, and cannot, restrict which label names GitHub users choose to apply, so it doesn't prevent the divergence. `capture_labels?` only gates on stack presence/archival state (`labeled_active_stack?` etc.) [7](#0-6) , not on label content.

Attack: a GitHub user with permission to label a PR against a repository that has a non-archived `ReviewStack` (this is a normal per-PR review app, and label permission on the user's own PR is a GitHub authorization question outside this engine, but is explicitly assumed available per the question's threat model) applies a label named `LD_PRELOAD` (or any other env var name with security meaning, e.g. `BUNDLE_GEMFILE`, `RUBYOPT`, `GIT_SSH_COMMAND`) to their own PR. GitHub delivers a genuine, correctly-signed `pull_request` "labeled" webhook. `LabelCapturingHandler` persists the label, and the next deploy/task on that review stack computes an environment with `LD_PRELOAD=true` (or attacker-chosen key), spawned into every child process of the deploy (`git`, `bundle`, `ruby`, etc.).

### Impact Explanation
As stated in the question itself, the fixed value `"true"` is not a valid shared-object path, so `LD_PRELOAD=true` alone does not achieve code execution — the dynamic linker would fail loudly rather than load anything. The real demonstrated impact is that this is an **unrestricted env-key injection primitive** into every command run on the deploy host for that review stack, confined to whatever `VariableDefinition`-style keys/values an attacker can name (value is always the literal string `"true"`, upcased key derived from the label name). Since Shipit repo maintainers still control the deploy-spec's script contents and `machine_env`/`@task.env` are merged *after* `@stack.env` and can override label-derived keys with the same name, full RCE would require an additional gap (a way to control the *value*, or a env-var whose mere presence as `"true"` is dangerous to a tool invoked during that specific deploy pipeline) that isn't demonstrated here. This most closely matches a **High**-severity finding (unauthorized mutation of review-stack deploy environment by an unprivileged PR labeler) rather than a proven **Critical** RCE, because the value is hard-coded to `"true"` and no working exploit chain to arbitrary command execution is shown.

### Likelihood Explanation
Requires: (1) Shipit configured with review apps / `ReviewStack` for a repository, (2) an existing PR with a non-archived stack, (3) the attacker being able to add a label to that PR (a GitHub-side permission question — typically requires triage/write access to the repo, not merely "opening a PR", contradicting the "unprivileged" framing for private/most public repos with branch protections, though the question's threat model asserts this is available), and (4) a correctly configured `webhook_secret` (if unset, forgery is trivially available regardless, which is a separate, pre-existing misconfiguration issue). Given those, the attack is fully repeatable and costs nothing beyond normal GitHub UI interaction.

### Recommendation
Constrain `capture_labels` (or `ReviewStack#env`) to only propagate label names that appear in the stack's `deploy_spec`-declared `VariableDefinition` allowlist (or a dedicated, explicit `review_labels` allowlist in `shipit.yml`), rejecting/dropping any other label names before persisting or before merging into `env`.

### Proof of Concept
Add a minitest to `test/models/shipit/review_stack_test.rb`-style coverage (not included here per scope, but conceptually):
```ruby
test "#env does not allow labels to inject reserved env var names" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["LD_PRELOAD"]
  assert_nil stack.env["LD_PRELOAD"] # currently FAILS: returns "true"

```
and a webhook-level test posting a `labeled` payload with `pull_request.labels: [{name: "LD_PRELOAD"}]` against a fixture non-archived `ReviewStack`, then asserting `TaskCommands.new(task).env["LD_PRELOAD"]` is absent — currently it equals `"true"`, confirming the unrestricted key-injection primitive described above.
