### Title
Unauthenticated CI status forgery leading to unauthorized merge queue merges when `webhook_secret` is unset - ([File: lib/shipit/github_app.rb])

### Summary
`GithubApp#verify_webhook_signature` unconditionally accepts any webhook payload when no `webhook_secret` is configured for the organization, which is the documented default in every shipped configuration template. This means the "signature verified" state is never bound to the payload content for such orgs, yet `WebhooksController#create` still dispatches the raw, unverified payload to handlers that persist state (like `commit_status`) directly into the database. That persisted state is later trusted by the merge-queue logic (`MergeRequest#all_status_checks_passed?` / `merge!`) to trigger a real GitHub merge using Shipit's own credentials.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub app config for `repository_owner` (extracted from the unauthenticated request body itself) and calls `verify_webhook_signature`: [1](#0-0) [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
  ...
end
```

`verify_webhook_signature` in `GithubApp` returns `true` before doing any cryptographic check whenever `webhook_secret` is blank: [2](#0-1) 

Every shipped configuration example (development, dummy test config) ships `webhook_secret` as `nil`/commented-out by default: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (trivially, since no secret is configured), `WebhooksController#create` parses the raw body and dispatches it to the registered handler for the event with no further trust check: [5](#0-4) 

For the `status` event, the handler persists the attacker-supplied `state`/`context`/`description` directly as a `Commit::Status`, as confirmed by the controller test asserting a `Status` row is created from the raw payload fields: [6](#0-5) 

This status is exactly the data source that the merge queue trusts to decide mergeability. `MergeRequest#all_status_checks_passed?` builds a `StatusChecker` from `head.statuses_and_check_runs` (which includes rows created by the webhook handler above) and, if all required statuses show success, `ProcessMergeRequestsJob` calls `merge_request.merge!`, which invokes the real GitHub API using Shipit's own installation credentials to merge the pull request: [7](#0-6) [8](#0-7) [9](#0-8) 

The binding broken is the analog described in the rules: **the organization that "authenticated" the webhook request (via `verify_webhook_signature`) versus the repository/commit state that is actually written** — because for any org running with the documented default (no `webhook_secret`), the "authenticated" side is vacuously true regardless of payload content, while the "written" side (a fabricated `success` CI status on an arbitrary commit) is fully attacker-controlled and gets consumed by a privileged, credentialed action (an actual GitHub merge).

### Impact Explanation
This crosses the Critical bar of "an unauthorized deploy, rollback or merge": an unprivileged, unauthenticated network attacker can forge a `status` webhook claiming a required CI check passed on any commit tracked by Shipit for an org that has no `webhook_secret` configured (the shipped default). If that commit belongs to a pull request queued in the merge queue, Shipit's background job will merge it into the target branch on GitHub using its own installation token — an unauthorized merge fully triggered by an outside, unauthenticated party.

### Likelihood Explanation
Likelihood is high for any deployment that follows the documented/example configuration without explicitly setting a per-org `webhook_secret` — which is the default in every configuration template shipped with the engine. No credentials, session, or GitHub write access are required; the attacker only needs to know (or guess) the organization/repository name and post a crafted `status` event to the public webhook endpoint.

### Recommendation
- Make `webhook_secret` mandatory (fail closed) rather than defaulting to "verified" when absent: `verify_webhook_signature` should reject the request instead of returning `true` when no secret is configured.
- Do not derive the org used for signature verification from unauthenticated payload fields; require it to be resolved independently of attacker-controlled input, or verify the signature against every configured org's secret before trusting `repository_owner`.
- Independently re-validate CI/status state against the GitHub API before allowing `MergeRequest#merge!` to proceed, rather than relying solely on locally stored `Commit::Status` rows populated from webhooks.

### Proof of Concept
1. Deploy Shipit with the default/example configuration (`webhook_secret` left `nil` for organization `acme`), as shown in the shipped templates.
2. Attacker (no credentials) sends `POST /webhooks` with header `X-Github-Event: status` and body:
   ```json
   {
     "sha": "<head sha of a queued PR>",
     "state": "success",
     "context": "ci/required-check",
     "description": "forged",
     "created_at": "...",
     "repository": { "owner": { "login": "acme" }, "full_name": "acme/target-repo" }
   }
   ```
3. `verify_signature` calls `verify_webhook_signature` which returns `true` unconditionally (no secret configured) — request is accepted with `head(:ok)`.
4. The handler creates a `Commit::Status` with `state: "success"` for the given SHA (confirmed by existing test behavior for the `status` event).
5. On the next `ProcessMergeRequestsJob` run, `MergeRequest#all_status_checks_passed?` sees the forged success status, and `merge!` is invoked, causing Shipit to call `github_api.merge_pull_request` and merge the PR upstream — an unauthorized merge triggered entirely by an unauthenticated attacker.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(

        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
```

```ruby
    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
```
