### Title
Unauthenticated GitHub webhooks trigger unauthorized commit status forgery and deploys when `webhook_secret` is unset - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
The external report's root cause is that `CollateralSettlerERC20#claimHA()` performed a privileged, identity-bound action (claiming a perpetual on behalf of an owner) with **no check that the caller was authorized to act on that identity**. The same class of bug exists in Shipit's webhook trust boundary: `WebhooksController` treats any inbound HTTP POST as an authentic GitHub event as long as `GitHubApp#verify_webhook_signature` returns `true` — but that method unconditionally returns `true` whenever no `webhook_secret` is configured for the organization named in the payload.

### Finding Description
`WebhooksController#verify_signature` looks up the app for the organization named in the *unauthenticated* payload and asks it to verify the signature: [1](#0-0) 

The verification itself is implemented as: [2](#0-1) 

`return true unless webhook_secret` means that for any GitHub App configured without a `webhook_secret` — which the project's own setup documentation marks as **optional** — signature verification is a no-op, and `WebhooksController#create` will dispatch the raw, attacker-supplied JSON body to whichever handler matches `X-Github-Event`: [3](#0-2) 

This breaks exactly the binding class called out in the rules: the *organization the request claims to be authenticated as* (`repository_owner`, taken straight from the JSON body) is never cryptographically tied to the request when no secret is set, yet the `repository`/`commit` the handlers subsequently write to is taken from that same untrusted payload.

The `status` event handler is the most consequential: it creates a `Status` record directly from attacker-controlled `state`/`context`/`sha` fields for any commit matching the given `sha`: [4](#0-3) 

Creating a `Status` fires `schedule_continuous_delivery`: [5](#0-4) 

For any stack with `continuous_deployment: true`, this can drive `Stack#trigger_continuous_delivery` → `trigger_deploy`, i.e. an unauthenticated third party can forge a "success" CI status for a chosen commit and cause Shipit to deploy it: [6](#0-5) [7](#0-6) 

Other handlers are similarly reachable without any real authentication in this configuration (e.g. `push` triggers a `GithubSyncJob`, `membership` creates/deletes `Team`/`User`/`Membership` records feeding `Shipit.github_teams` authorization), matching the "High: escalation into `Shipit.github_teams` authorization" impact category as well.

### Impact Explanation
- If a Shipit deployment is configured per the documented (optional) setup without a `webhook_secret`, any unauthenticated internet client can forge GitHub webhook events for that organization's repositories.
- Forged `status` events can flip CI state to `success`, and combined with `continuous_deployment: true` this results in an **unauthorized deploy** — a Critical-tier impact per the program's rules.
- Forged `membership` events can add/remove `Membership` rows and create `User`/`Team` records, directly influencing `Shipit.github_teams`-based authorization decisions elsewhere in the app.
- Forged `push`/`check_suite` events can trigger `GithubSyncJob`/`RefreshCheckRunsJob`, causing the app to fetch attacker-influenced commit data from `Repository`/`Commit` under a namespace it does not truly control.

### Likelihood Explanation
Likelihood depends on whether an operator has left `webhook_secret` blank. Because `docs/setup.md` explicitly lists the webhook secret as "(optional)", this is a supported, documented configuration and not a deviation from how the engine is meant to be mounted, so it is a realistic operational scenario rather than a theoretical misconfiguration. Any installation following the documented minimal setup and skipping the optional secret is exposed to fully unauthenticated webhook forgery.

### Recommendation
- Make `webhook_secret` a required (non-optional) configuration value, failing fast at boot if it is absent for any configured GitHub App/organization.
- Change `GitHubApp#verify_webhook_signature` to fail closed (`return false`) when `webhook_secret` is blank, rather than treating the absence of a secret as automatic success.
- Update `docs/setup.md` to remove the "(optional)" designation and instead state that the webhook secret is mandatory.

### Proof of Concept
1. Deploy Shipit following `docs/setup.md` without setting `webhook_secret` for the GitHub App (a documented, supported configuration).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: status` and a JSON body such as:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "<target-org>" } }
}
```
3. `WebhooksController#verify_signature` calls `verify_webhook_signature`, which returns `true` unconditionally because `webhook_secret` is blank [8](#0-7) .
4. `StatusHandler#process` creates a `Status` record for the targeted commit [4](#0-3) , which schedules continuous delivery and can trigger `Stack#trigger_deploy` for any stack with `continuous_deployment` enabled and tracking that commit — an unauthorized deploy performed entirely by an unauthenticated attacker.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
