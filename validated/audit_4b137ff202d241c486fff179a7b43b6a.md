### Title
Webhook signature verification binds to `repository.owner.login`/`organization.login`, but event handlers act on the unrelated `repository.full_name` field — allowing cross-organization stack actions - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`), both taken directly from the attacker-supplied JSON body. Every webhook `Handler`, however, determines *which* `Stack`/`Repository` the event actually mutates using a different field from the same body: `repository.full_name`. Because the field that authorizes the request (which org's secret must match) is decoupled from the field that is acted upon (which repo/stack is mutated), an attacker who legitimately controls the webhook secret for one onboarded GitHub organization (or targets an org configured with no `webhook_secret` at all) can forge a signed payload that verifies under "their" organization while causing Shipit to execute the event against a completely different organization's repository/stack.

### Finding Description
`WebhooksController#verify_signature` computes the organization used for secret lookup purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GithubApp` instance whose `verify_webhook_signature` is used: [3](#0-2) 

Note line 77: `return true unless webhook_secret` — if the organization resolved from the attacker-controlled `repository_owner` field has no `webhook_secret` configured, the signature check is skipped entirely and `verified` is unconditionally `true`.

Once the request passes `verify_signature`, `WebhooksController#create` dispatches the *entire raw payload* to handlers without re-checking which organization it "belongs" to: [4](#0-3) 

Handlers then resolve the target repository/stack from a *different* payload field, `repository.full_name`, not `repository.owner.login`/`organization.login`: [5](#0-4) 

For example, `PushHandler` uses this `stacks` scope (derived from `repository.full_name`) to force a `sync_github` on any matching stack: [6](#0-5) 

Similarly, `MembershipHandler` (exercised in `test/controllers/webhooks_controller_test.rb`'s `:membership` tests) creates/removes `Team`/`Membership` records purely from payload content once the signature step passes, again independent of `repository.owner.login`.

**Broken binding (equality that should hold but doesn't):**
`organization used to select/verify webhook_secret` (`repository.owner.login` / `organization.login`) **≠** `repository/organization whose stack is mutated` (`repository.full_name`).

Because both fields live in the same attacker-authored JSON body, and because the HMAC only proves "this body was signed with organization X's secret," it proves nothing about which repository the body's other fields claim to describe. An attacker who legitimately administers Organization A's GitHub webhook (and thus legitimately knows Organization A's `webhook_secret`, since GitHub hands it to whoever configures the webhook) can:
1. Set `organization.login` / `repository.owner.login` = `"OrgA"` (sign with OrgA's real secret), or pick any org configured in this Shipit instance with a blank `webhook_secret` to skip signing entirely.
2. Set `repository.full_name` = `"OrgB/victim-repo"` — an org/repo the attacker does not control.
3. POST the forged, correctly-"verified" payload to the public `/github/webhooks` endpoint (this endpoint is intentionally unauthenticated — no Shipit session or `ApiClient` token is required, since it's designed to receive unauthenticated GitHub webhook deliveries).

This causes handlers to act on OrgB's stack: forcing sync jobs, mutating check-suite/status state used for CI gating on deploys, or creating/removing team memberships — all attributed to a payload that "verified" only because it was signed by an unrelated organization's secret.

### Impact Explanation
This is a cross-repository/cross-organization write: an attacker with legitimate credentials for one tenant organization onboarded to a shared Shipit instance can trigger writes and state changes against a different tenant's repository/stack. Depending on the handler reached (e.g. forcing `GithubSyncJob`, tampering with `commit_status`/`check_suite` records that gate whether a commit is "deployable", or manipulating `Team`/`Membership` records that back `Shipit.github_teams` authorization), this can be leveraged to manipulate CI-gating state that influences whether a deploy is authorized to ship, or to corrupt team membership data used for access control — satisfying the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" categories.

### Likelihood Explanation
Multi-organization Shipit deployments are an explicitly supported configuration (see `test/dummy/config/secrets_double_github_app.yml`, which configures multiple GitHub Apps/orgs with independent `webhook_secret`s). Any tenant organization onboarded to such a shared instance already possesses a legitimate `webhook_secret` for their own org (GitHub requires it to configure the webhook), and the webhook endpoint is intentionally public/unauthenticated. No privileged Shipit account, session, or `ApiClient` token is required — only knowledge of one's own organization's already-known secret (or discovery of an org configured with a blank secret).

### Recommendation
After signature verification, re-derive the organization solely from the field that was actually verified (`repository_owner`), and reject or scope the event if `repository.full_name`'s owner does not match the verified organization. Do not let handlers resolve the target `Repository`/`Stack` purely from unverified payload fields once a different field was used to pick the verification key.

### Proof of Concept
1. Configure/observe that the Shipit instance manages ≥2 organizations, e.g. `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim, unrelated secret).
2. Craft JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } },
  "organization": { "login": "OrgA" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>`.
4. `POST /github/webhooks` with `X-Github-Event: push`, the header above, and the body.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches OrgA's `GithubApp`, and `verify_webhook_signature` succeeds (signed correctly for OrgA).
6. `PushHandler#process` runs `stacks` derived from `repository.full_name` = `"OrgB/victim-repo"`, forcing `sync_github` on OrgB's stack — despite the request having authenticated as OrgA.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
