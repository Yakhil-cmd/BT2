### Title
Front-running a `SignedDelegateAction` consumes the sender's access-key nonce, causing the intended relayer's meta-transaction to revert - ([File: runtime/runtime/src/actions.rs])

### Summary
NEP-366 meta transactions let a user (e.g. Alice) sign a `DelegateAction`/`DelegateActionV2` off-chain and hand it to a relayer, who wraps it in an outer `SignedTransaction` and pays the gas. `apply_delegate_action` never checks who submitted the outer transaction — it only checks the signature over the `DelegateAction` itself, expiry, and that `sender_id` matches the outer tx's `receiver_id`. Because the nonce check in `validate_delegate_action_key` accepts any strictly-increasing nonce and permanently rejects re-use (`delegate_nonce.nonce() <= current_nonce`), anyone who observes a pending `SignedDelegateAction` (e.g. sitting in the intended relayer's transaction in the mempool, or shared with multiple relayer candidates) can copy it into their own outer transaction and get it included first. This "steals"/consumes Alice's nonce, so when the intended relayer's original transaction executes afterward, `validate_delegate_action_key` returns `DelegateActionInvalidNonce`, causing the relayer's transaction/receipt to fail even though the relayer paid gas for it. [1](#0-0) 

### Finding Description
`apply_delegate_action` performs these checks, in order: signature verification, `max_block_height` expiry, and `sender_id` vs the outer transaction's receiver. [2](#0-1) 
None of these checks bind the `SignedDelegateAction` to a specific relayer/outer-transaction-signer — any account holding NEAR to pay gas can package the exact same `SignedDelegateAction` bytes (sender_id, actions, nonce, max_block_height, public_key, signature) into its own outer transaction addressed to `sender_id`, since only `tx.receiver_id == delegate_action.sender_id` is required.

`validate_delegate_action_key` then enforces strict nonce monotonicity and permanently invalidates any earlier value: [3](#0-2) 
Once any copy of the `SignedDelegateAction` is applied on-chain (by whoever's outer transaction lands first), the access key's nonce (or, for `DelegateActionV2`/gas keys, the selected `nonce_index`'s nonce) is bumped. This exactly mirrors the bug class in the report: a signature-based authorization (`safePermit`/`DelegateAction`) is consumable by any third party, not only the intended relayer, and its associated nonce/allowance state is a shared, front-runnable resource. A malicious actor who front-runs consumes the authorization first, forcing the legitimate submitter's identical follow-up submission to revert with `DelegateActionInvalidNonce`.

The `docs/architecture/how/meta-tx.md` documentation acknowledges general trust issues between relayer and user (e.g. Alice reusing a relayer's account-creation gas) but does not address third-party front-running of an already-signed `SignedDelegateAction` observed off-chain or in the mempool. [4](#0-3) 

### Impact Explanation
This is a griefing/denial-of-service vector against relayer services (the "external integrations" analog called out in the original report): the legitimate relayer's outer transaction is admitted to a chunk, its `SignedDelegateAction` fails nonce validation, `ActionResult` records the error, gas already purchased by the relayer is burnt without the sender's intended action ever executing (per the "Gas costs for meta transactions" model, gas is paid by the relayer regardless of the inner delegate action outcome). Repeated front-running can be used to reliably deny service to a specific relayer or to a user's meta-transaction flow, wasting relayer funds and preventing the desired state change, without theft of user funds or protocol-level invariant violation.

### Likelihood Explanation
The `SignedDelegateAction` must be observable to the attacker before the intended relayer's transaction is finalized — for example, while the relayer's transaction sits in the mempool/pending transaction pool, or if the same `SignedDelegateAction` is shared with multiple candidate relayers (a plausible integration pattern, since it is a value object with no built-in relayer binding). No special privileges are required by the attacker beyond a funded account to pay gas for the front-running transaction, and no protocol-level access-key ownership is needed. This is analogous in exploitability to the original report's rating (unprivileged front-running, low-severity griefing) rather than fund theft.

### Recommendation
Consider binding a `SignedDelegateAction` to an authorized relayer (e.g., by including an expected signer/relayer account id inside the signed payload, similar to how EIP-2612 could be hardened by checking allowance before calling `permit`), or allow relayers to pre-check nonce validity immediately before broadcast and treat `DelegateActionInvalidNonce` failures as retryable/non-fatal for gas-refund purposes. At minimum, document this front-running risk explicitly for relayer implementers alongside the existing trust-model caveats in `docs/architecture/how/meta-tx.md`.

### Proof of Concept
1. Alice signs `DelegateAction { sender_id: alice, receiver_id: ft, actions: [...], nonce: N, max_block_height, public_key }` and sends it to Relayer R off-chain (or R broadcasts an outer transaction containing it, visible in the mempool before inclusion).
2. Attacker A observes the `SignedDelegateAction` (same struct, verifiable signature) and constructs their own outer `SignedTransaction` with `receiver_id = alice`, `actions = [Action::Delegate(same SignedDelegateAction)]`, signed and paid for by A.
3. A's transaction is included first (e.g. by paying a higher gas price or simply beating R to broadcast). `apply_delegate_action` succeeds for A's outer tx, and `validate_delegate_action_key` bumps Alice's access key nonce to N. [5](#0-4) 
4. R's original outer transaction (containing the identical `SignedDelegateAction`) is subsequently applied; `validate_delegate_action_key` now sees `delegate_nonce.nonce() (N) <= current_nonce (N)` and returns `DelegateActionInvalidNonce`, failing R's transaction after R has already paid for gas. pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }
