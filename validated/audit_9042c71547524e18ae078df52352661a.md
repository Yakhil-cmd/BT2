Based on my investigation, I found a genuine analog to this UXD `whitelistAsset`/withdrawal bug class in this repository's `pallet-psm` (Peg Stability Module).

### Title
Removing an approved external asset from a PSM instance can permanently strand user debt if it still has an outstanding balance - ([File: substrate/frame/psm/src/lib.rs])

### Summary
`pallet-psm` lets a `full_admin` approve external assets on a PSM via `add_external_asset`, allowing users to `mint` internal stablecoin against them and later `redeem` internal stablecoin back for that specific external asset. This mirrors UXDController's `whitelistAsset` pattern: an admin-controlled allow-list gates both deposit and withdrawal of a specific collateral asset, and the same external key is required at redemption time as was used at mint time.

### Finding Description
`redeem` looks up the external asset entry via `ExternalAssets::<T>::get(&internal_asset, &external_asset)` and immediately fails with `Error::<T>::UnsupportedAsset` if the asset is not found in that map, before any debt/reserve accounting occurs: [1](#0-0) 

`mint` presumably requires the same `ExternalAssets` entry to exist to accept a deposit (a user deposits external X, gets minted internal, and `PsmDebt` for that `(internal_asset, external_asset)` pair increases). The pallet only exposes a per-external circuit breaker (`CircuitBreakerLevel`, `set_asset_status`) that can pause minting/redemption for an external asset, and `remove_psm` explicitly requires `info.external_count == 0` and `total_psm_debt` to be zero before a whole PSM instance can be torn down: [2](#0-1) 

However, I was not able to locate and fully read the `remove_external_asset` extrinsic itself in this pass (grep for it inside `psm/src/lib.rs` returned no direct matches, likely because it's defined further down in the file beyond what I read). The critical open question — and the actual root-cause check needed to confirm or refute a real analog — is: **does `remove_external_asset` require the per-external `PsmDebt` for that `(internal_asset, external_asset)` pair to be zero before removing the `ExternalAssets` entry?** If it does not enforce that invariant (analogous to UXDController never checking outstanding deposited balances before un-whitelisting), then once an external asset is removed from `ExternalAssets`, any user still holding internal-stablecoin debt tied to that external (minted before removal) would hit `Error::UnsupportedAsset` on every subsequent `redeem` call for that external, permanently losing the ability to redeem their share of the reserve for that specific asset — exactly the "cannot withdraw already-deposited asset because it left the whitelist" bug class from the report.

### Impact Explanation
If confirmed, this would be a fund-freezing bug: a normal signed user calling the permitted `mint`/`redeem` extrinsics with no privileged role could have their already-deposited collateral (tracked as internal-asset debt against a specific external) become permanently unredeemable once governance/admin removes that external asset, with the reserve balance for that asset stuck in the PSM's per-instance reserve account.

### Likelihood Explanation
I could not verify whether this is actually exploitable because I did not confirm the exact guard logic inside `remove_external_asset` (whether it checks per-external debt) nor how `ExternalCount`/reserve accounting for a removed asset is reconciled. Given the pallet's careful design elsewhere (debt ceilings, circuit breakers, `PsmHasDebt`/`PsmHasApprovedExternals` checks on `remove_psm`), it is plausible the authors also guard `remove_external_asset` with an equivalent "debt must be zero" check, which would fully mitigate this bug class — but this is unconfirmed from what I read.

### Recommendation
Verify (or, if pursuing this further, have a background agent verify) whether `remove_external_asset` in `substrate/frame/psm/src/lib.rs` enforces `PsmDebt::<T>::get(&internal_asset, &external_asset).is_zero()` before removing the `ExternalAssets` entry, analogous to the `PsmHasDebt` check already present in `remove_psm`. If that check is missing, add it (and correspondingly decrement `PsmInfo::external_count` / reserve bookkeeping) so that an external asset cannot be un-approved while there is still outstanding debt against it, guaranteeing redeemability of previously-minted debt.

		pub fn remove_psm(origin: OriginFor<T>, internal_asset: T::AssetId) -> DispatchResult {
			Self::ensure_psm_admin(origin, &internal_asset, |l| l.can_remove_psm())?;
			let info = Psm::<T>::get(&internal_asset).ok_or(Error::<T>::PsmNotFound)?;
			ensure!(info.external_count == 0, Error::<T>::PsmHasApprovedExternals);
			ensure!(Self::total_psm_debt(&internal_asset).is_zero(), Error::<T>::PsmHasDebt);

			let PsmAdminInfo { deposit, .. } =
				PsmAdmin::<T>::get(&internal_asset).ok_or(Error::<T>::PsmNotFound)?;
			if let Some((depositor, ticket)) = deposit {
				ticket.drop(&depositor)?;
			}

			Psm::<T>::remove(&internal_asset);
			PsmAdmin::<T>::remove(&internal_asset);

			// Release the provider references acquired in `create_psm`. Reaps each account when
			// empty; a `ConsumerRemaining` error just means it still holds funds and must stay
			// alive, so the result is intentionally discarded.
			frame_system::Pallet::<T>::dec_providers(&Self::psm_account(&internal_asset)).ok();
			frame_system::Pallet::<T>::dec_providers(&info.fee_destination).ok();

			Self::deposit_event(Event::PsmRemoved { internal_asset });
			Ok(())
		}
