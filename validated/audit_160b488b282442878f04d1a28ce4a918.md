### Title
Cross-organization webhook status forgery enables unauthorized continuous deployment - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), but the handlers that actually act on the payload (e.g. `StatusHandler`) key off unrelated, unscoped fields (a bare commit `sha`) or a separate `repository.full_name` field. This breaks the equality "organization whose secret authenticated the request == repository/commit the request is allowed to affect." In a multi-GitHub-App deployment, any organization configured without a `webhook_secret` (documented as optional) becomes a free pass to forge events that mutate state belonging to *any other* organization's stacks, including triggering `ContinuousDeliveryJob` and an unauthorized deploy.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` to validate against solely based on the attacker-supplied `repository_owner` value: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` in `GitHubApp` short-circuits and returns `true` (i.e., skips signature checking entirely) whenever the selected organization has no `webhook_secret` configured: [3](#0-2) 

This is a documented, supported per-organization opt-in ("Webhook secret (optional)") in multi-app configuration: [4](#0-3) 

Once `verify_signature` passes (trivially, for the no-secret org), `create` hands the *entire, attacker-controlled* JSON body to every registered handler for the event, with no re-validation that the payload's content is scoped to the "authenticated" organization: [5](#0-4) 

Most handlers use `payload.dig('repository', 'full_name')` — a field entirely independent of the `repository_owner` field used for authentication — to select which `Repository`/`Stack` to act on: [6](#0-5) 

`StatusHandler` is worse: it does not even scope by repository at all, it queries commits globally by `sha`: [7](#0-6) 

Thus, the "organization authenticated" (via `repository_owner`) and "repository/commit actually written" (via `repository.full_name` or bare `sha`) are two independent, attacker-controlled fields inside the same unsigned-for-that-org JSON body — exactly the class of binding break described in the reference report (getter used one reference value while verification used another, causing the two to diverge under attacker influence).

An attacker who is aware of (or can discover, e.g. via a 422 error triggering with the wrong org, or via trial) any configured GitHub organization in Shipit's `secrets.yml` that has no `webhook_secret` set can:
1. POST to `/webhooks` with `X-Github-Event: status`, `repository.owner.login` set to that unsecured org (satisfies `verify_signature`, auto-passing since `webhook_secret` is blank for that org), and
2. Supply an arbitrary/known-public commit `sha` belonging to a *completely different, secured* stack, with `state: "success"`.

`StatusHandler#process` will call `commit.create_status_from_github!(params)` for every commit matching that sha across the whole installation, regardless of which org's secret authenticated the request. If that commit is now considered CI-passing/deployable and the target stack has `continuous_deployment: true`, `Stack#trigger_continuous_delivery` will run on the next `ContinuousDeliveryJob` tick and deploy it: [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
This achieves an **unauthorized deploy** without any Shipit session, API token, or knowledge of the target organization's webhook secret — only knowledge that *some* configured org lacks a secret (a supported, documented configuration) and a public commit SHA of the target stack. This matches the Critical-tier impact bar ("an unauthorized deploy, rollback or merge"). Similarly `CheckSuiteHandler`, `PushHandler`, and pull-request handlers are reachable the same way via forged `repository.full_name`, enabling forced resyncs, review-stack archiving/unarchiving, and label-triggered provisioning across stacks that never share a GitHub App/secret with the "authenticating" organization.

### Likelihood Explanation
Realistic in any Shipit deployment that uses the documented multi-organization GitHub App configuration where at least one organization intentionally omits `webhook_secret` (the docs explicitly present this as optional per-org). No credential, session, or attacker-side secret is required — only the public `/webhooks` endpoint and a commit SHA, which is typically discoverable from a public/semi-public repository or GitHub UI.

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub App/organization, or fail closed (reject, not auto-accept) when a secret is absent instead of returning `true` in `verify_webhook_signature`.
- Bind the authenticated organization to the scope of the action: after signature verification, require that `payload.dig('repository', 'owner', 'login')` (used to select the app) matches `payload.dig('repository', 'full_name')`'s owner, and reject handlers/commits that resolve to a repository/stack not owned by the authenticated organization.
- In `StatusHandler`, scope the `Commit.where(sha:)` lookup by the repository derived from the same organization that authenticated the webhook, not by a global, org-agnostic SHA lookup.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `org-victim` (has `webhook_secret: S`) and `org-empty` (no `webhook_secret` set — supported per docs).
2. Attacker POSTs to `/webhooks`:
```
X-Github-Event: status
Body:
{
  "repository": { "owner": { "login": "org-empty" }, "full_name": "org-empty/whatever" },
  "sha": "<known sha of org-victim's stack HEAD commit>",
  "state": "success",
  "context": "ci/attacker",
  "created_at": "2026-09-02T00:00:00Z"
}
```
3. `verify_signature` calls `Shipit.github(organization: "org-empty")`; since `org-empty` has no `webhook_secret`, `verify_webhook_signature` returns `true` without checking `X-Hub-Signature` at all.
4. `StatusHandler#process` finds the commit(s) with that `sha` across the entire install (including `org-victim`'s stack) and creates a passing status via `commit.create_status_from_github!`.
5. If `org-victim`'s stack has `continuous_deployment: true`, the next `ContinuousDeliveryJob` run deploys that commit — an unauthorized deploy triggered entirely without knowledge of `org-victim`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  class ContinuousDeliveryJob < BackgroundJob
    include BackgroundJob::Unique

    queue_as :deploys
    on_duplicate :drop

    def perform(stack)
      return unless stack.continuous_deployment?

      # If there is a schedule defined for this stack, make sure we are within a
      # deployment window before proceeding.
      return if stack.continuous_delivery_schedule && !stack.continuous_delivery_schedule.can_deploy?

      # checks if there are any tasks running, including concurrent tasks
      return if stack.occupied?

      stack.trigger_continuous_delivery
    end
  end

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

        continuous_delivery_delayed!
        return
      end

      begin

      rescue Task::ConcurrentTaskRunning
      end
    end
