### Title
Webhook signature verification is bypassed via attacker-chosen `repository.owner.login` combined with an unset `webhook_secret` on any configured organization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects which `GithubApp` configuration (and therefore which `webhook_secret`) to validate a webhook against based on an unauthenticated field taken directly from the JSON body — `repository.owner.login` (or `organization.login`) — before any signature check has succeeded. `GithubApp#verify_webhook_signature` then unconditionally returns `true` when that selected organization's `webhook_secret` is blank. Because Shipit explicitly supports multiple organizations configured simultaneously, and the documented/fixture configuration allows an organization to have no `webhook_secret` at all, an attacker can pick that unprotected organization to satisfy the signature check while the rest of the payload (the actual `repository.full_name`, `sha`, `ref`, team/membership data, etc.) targets a completely different, protected stack/repository that the handlers act on.

### Finding Description
`verify_signature` derives the signing organization purely from attacker-supplied payload content: [1](#0-0) [2](#0-1) 

The organization string is used only to look up which `GithubApp` (and its `webhook_secret`) will be used to validate the signature; it is never itself part of what the signature covers, and nothing ties it to the repository/stack that the event handlers subsequently operate on. `GithubApp#verify_webhook_signature` degrades to an always-true check whenever that organization's `webhook_secret` is not configured: [3](#0-2) 

Shipit is designed to host multiple organizations concurrently (each with its own `GithubApp` config), and a `nil`/blank `webhook_secret` per organization is an explicitly supported configuration state, as shown in the shipped multi-org fixtures/config used across the app: [4](#0-3) [5](#0-4) 

After `verify_signature` passes (or is bypassed), the full raw JSON body is parsed independently and dispatched to handlers keyed only by the `X-Github-Event` header, with no re-validation that the organization used for verification matches the repository/stack the payload claims to modify: [6](#0-5) 

This breaks the binding: **organization whose webhook signature was verified == organization/repository the payload's handler subsequently writes to**. An attacker who knows (or guesses) that any one organization on a multi-tenant Shipit install has no `webhook_secret` configured can set `repository.owner.login` (or `organization.login`) to that organization to force `verify_webhook_signature` to return `true` unconditionally, while setting the actual `repository.full_name`/`sha`/`ref`/team fields in the same payload to reference a different, secret-protected organization's stack. The push/status/membership/pull_request handlers then act on that unrelated, protected repository or team data as if it had been legitimately signed.

### Impact Explanation
This is a cross-repository/cross-organization write achieved with zero valid credentials: no `webhook_secret`, no `ApiClient` token, and no GitHub App private key for the targeted (protected) organization is required. Depending on event type, an unauthenticated attacker can:
- Trigger `GithubSyncJob` for an arbitrary stack (spoofed `push` event) belonging to a fully-secured organization.
- Inject spoofed commit statuses via the `status` handler, manipulating deploy-gating checks for a protected stack.
- Create/delete team memberships via the `membership` handler for a protected organization, potentially affecting `Shipit.github_teams` authorization used by `current_user.authorized?`.

This satisfies the Critical/High impact bar: cross-repository writes / unauthorized state changes achieved by exploiting a signature-selection binding that never actually covers the data being trusted.

### Likelihood Explanation
Exploitability requires only that the Shipit deployment (a) hosts more than one organization and (b) has at least one organization configured without a `webhook_secret` — a state the codebase's own fixtures and sample configs treat as normal/supported (`webhook_secret: # nil`). No attacker needs any secret, token, or prior access — only the ability to send an HTTP POST to the public `/webhooks` endpoint, which is unauthenticated by design (it's meant to be called by GitHub).

### Recommendation
- Never allow the value used to select the verification key (`repository.owner.login` / `organization.login`) to also be trusted for identifying which repository/stack/team the event acts upon unless the signature check strictly used a secret bound to that same organization.
- Do not allow `verify_webhook_signature` to silently succeed when `webhook_secret` is blank; either require a `webhook_secret` for every configured organization, or explicitly reject/flag webhooks for organizations with no configured secret instead of treating them as automatically verified.
- After signature verification, re-validate that the repository/organization referenced by the payload's business data (`repository.full_name`, team org, etc.) actually belongs to the organization whose secret was used to verify the signature.

### Proof of Concept
1. Shipit is configured with two organizations, e.g. `OrgA` (has `webhook_secret: some-secret`) and `OrgB` (has `webhook_secret:` left blank/nil) — a configuration pattern present verbatim in the repo's own fixtures/config samples.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and a body such as:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/protected-repo" },
  "after": "<arbitrary sha belonging to OrgA/protected-repo>"
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required.
3. `verify_signature` computes `repository_owner = "OrgB"`, loads `OrgB`'s `GithubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` immediately — bypassing signature validation entirely.
4. `Shipit::Webhooks.for_event('push')` handlers then process the payload using `repository.full_name = "OrgA/protected-repo"`, enqueuing a `GithubSyncJob` for `OrgA`'s protected stack despite the attacker never possessing `OrgA`'s `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
