### Title
Webhook signature verification authenticates the payload's `repository.owner.login` but the event handlers act on the unverified `repository.full_name`, allowing cross-organization/cross-repository writes in multi-GitHub-App deployments - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
Analogous to the ZeroLocker bug where `merge` acted on values (`_locked0.start`/`_locked1.end`) that were never bounded by the `MAXTIME` invariant enforced elsewhere, Shipit's webhook pipeline verifies the HMAC signature using one field of the payload (`repository.owner.login`, used only to pick which configured GitHub App/org secret to check) while every event `Handler` resolves the target repository/stack using a *different* field of the same payload (`repository.full_name`), with no check that the two are consistent.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to select the verification secret purely from the untrusted request body: [1](#0-0) 
`repository_owner` is read straight from the JSON payload: [2](#0-1) 

`Shipit.github(organization:)` looks up the app config for that claimed org and raises only if the org name is entirely unknown; otherwise it selects that org's `webhook_secret` for verification: [3](#0-2) 

Signature verification (`GitHubApp#verify_webhook_signature`) proves only that the *whole raw body* was signed by the secret belonging to whatever organization `repository.owner.login` claims to be — it does not bind that organization to any other field in the payload: [4](#0-3) 

Critically, if that organization's `webhook_secret` is unset (which the setup docs explicitly document as optional/nil), the check is bypassed entirely: [5](#0-4) 

Once the request passes this check, every `Handler` (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, pull-request handlers, etc.) resolves the stack/repository to act on using a **separate, unverified payload field** — `repository.full_name` — not `repository.owner.login`: [6](#0-5) 

`PushHandler#process`, for example, uses that resolved repository's stacks to trigger a GitHub sync: [7](#0-6) 

Shipit explicitly supports hosting multiple GitHub Apps/organizations in one instance, each with its own `webhook_secret`: [8](#0-7) 

This is precisely the ZeroLocker binding-break pattern: the property enforced at verification time (`_locked0.start`/`MAXTIME` in ZeroLocker; `repository.owner.login` ↔ selected `webhook_secret` here) is not the property acted upon downstream (`end` used unbounded in `_calculatePower`; `repository.full_name` used unchecked in `Handler#stacks`). Equality that should hold: `verified_org(repository.owner.login) == owner(repository.full_name)`. Nothing enforces it.

### Impact Explanation
In a multi-org Shipit deployment, a sender who can produce a validly-signed webhook for **Org A** (i.e., knows/controls Org A's `webhook_secret`, or Org A has no secret configured, which the docs list as an accepted "optional" configuration) can set `repository.owner.login = OrgA` (to select and pass verification against Org A's secret) while setting `repository.full_name = "OrgB/some-repo"`. The signature check only confirms the org named in `owner.login` signed the body; it never re-derives or checks the owner encoded in `full_name`. The handler then acts on the Org B repository/stack — e.g., `PushHandler` triggers `GithubSyncJob` for a stack that belongs to an entirely different, uninvolved GitHub organization also hosted by the same Shipit instance, and other handlers (status, check_suite, membership, pull_request) can inject fabricated CI/deploy-relevant state for that unrelated repository's commits. This is a cross-repository write across an organization boundary that the attacker was never authorized for, driven purely by an unauthenticated field in a payload whose signature check binds to a different field.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with the documented multi-organization GitHub App layout, and (2) either an attacker with legitimate signing capability for one configured org (e.g., an org's own webhook secret) or any one configured org left without a `webhook_secret` (explicitly documented as an accepted "optional" setting). Under those realistic, documented configurations, exploitation requires nothing more than a single unauthenticated POST to `/webhooks`.

### Recommendation
After selecting `repository_owner` and verifying the signature, re-derive the actual repository owner from `repository.full_name` (or `organization.login`) inside `Handler#stacks`/`repository_name` and reject/ignore the event if it does not match the organization whose secret verified the signature. Alternatively, verify the signature using the app resolved from `repository.full_name`'s owner rather than a separately-read `repository.owner.login`/`organization.login` fallback, so the same value both selects the secret and gates which repository can be acted upon.

### Proof of Concept
Conceptual (index-derived, not executed against a live app — needs verification with a Devin session that can run the test suite):
1. Configure Shipit (per `docs/setup.md` "Using Multiple Github Applications") with two orgs, `OrgA` (webhook_secret set and known/controlled by attacker, or left blank) and `OrgB` (a victim org with a Stack for `OrgB/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and a body where `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/victim-repo"`, `ref`, and `after` set to an attacker-chosen SHA.
3. Compute `X-Hub-Signature` using OrgA's `webhook_secret` (or omit the header entirely if OrgA has none configured, per `verify_webhook_signature`'s early `return true unless webhook_secret`).
4. `WebhooksController#verify_signature` passes (verifies against OrgA), but `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `sync_github` on a stack belonging to Org B, which the attacker was never authorized to sign webhooks for.

```ruby
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
