### Title
Webhook signature verification keys on an attacker-influenced organization field while `StatusHandler` applies the resulting trust globally, with no repository/organization scoping - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
This mirrors the OndoFees bug class ("a field acted on but never covered by the check that was supposed to gate it") as a broken deployment-trust binding: **the GitHub organization whose secret authenticates the webhook ≠ the repository/commit whose state Shipit actually mutates.**

### Finding Description
`Shipit::WebhooksController#verify_signature` selects which webhook secret to verify against using an attacker-supplied field of the JSON body itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted payload (`repository.owner.login`, falling back to `organization.login`), and `Shipit.github(organization: repository_owner)` is used only to pick which `GitHubApp`/secret to check the HMAC against: [3](#0-2) 

Critically, `GitHubApp#verify_webhook_signature` treats an org with **no configured `webhook_secret`** as automatically verified: [4](#0-3) 

Shipit explicitly supports multi-organization installs where each org has its own (optionally blank) `webhook_secret`, as shown in the sample config: [5](#0-4) 

Once signature verification passes (for *whatever* org the attacker names in the payload), the event is dispatched to a handler based on the event type. `StatusHandler` performs **zero repository or organization scoping** — it looks up commits by `sha` alone, globally across the entire Shipit database, and immediately writes GitHub-status state onto them: [6](#0-5) [7](#0-6) 

This is the exact equality that should hold but doesn't: `organization authenticating the signature == organization owning the commit being mutated`. Since `verify_signature`'s organization comes from the same untrusted JSON body whose other fields (`sha`, `state`, `context`) are consumed unchecked by `StatusHandler`, an attacker can pick *any* org configured in the multi-tenant Shipit instance that has no `webhook_secret` set (a documented, supported configuration) to pass verification, while targeting a `sha` belonging to a completely different, victim organization/repository tracked by the same Shipit instance.

### Impact Explanation
A forged `status` webhook writes a fabricated GitHub commit status (e.g. `state: success`, arbitrary `context`) onto any commit SHA in the database, regardless of which organization actually owns that repository. `Commit#status`/`Commit#deployable?` and `schedule_continuous_delivery` feed directly off these locally-stored statuses: [8](#0-7) [9](#0-8) 

If a targeted stack has `continuous_deployment` enabled and is gated on CI status (`ci.require`), injecting a fake "success" status for the required context can flip `deployable?` to true and trigger `ContinuousDeliveryJob`, resulting in an **unauthorized deploy** — meeting the "Critical" impact bar defined by the rules (unauthorized deploy). This requires no session, `ApiClient` token, or GitHub write access — only that the target Shipit instance is configured for multiple GitHub organizations and at least one of them has no webhook secret set (an explicitly documented/supported configuration, not a misconfiguration this engine warns against).

Note: `PushHandler` (unlike `StatusHandler`) does scope stacks via `Repository.from_github_repo_name(payload['repository']['full_name'])`, so the same class of forgery there is far weaker (still crosses the auth-org boundary, but a `GithubSyncJob` re-fetch of the real upstream commits from GitHub limits direct impact). The `StatusHandler` path is the one that fully breaks the binding because it has no repository check whatsoever.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations (a documented supported mode) with at least one org lacking a `webhook_secret`, or the attacker otherwise possessing a valid secret for any one onboarded org; (2) knowledge of a target commit SHA on a tracked victim stack (public information via GitHub) and the CI `context` name required by that stack's `shipit.yml` (also often discoverable/guessable, e.g., common CI provider names). No credentials to the victim org, no session, and no `ApiClient` token are needed — only a plain HTTP POST to the public `/github/webhooks` endpoint.

### Recommendation
- Verify the webhook signature using the organization actually owning the *processed* repository (derived and cross-checked consistently, e.g., resolved from `Repository.from_github_repo_name` before selecting the verification key), not from a field read independently and prior to determining which repository/stack the event will affect.
- In `StatusHandler`, scope `Commit.where(sha: params.sha)` by the repository/organization that was cryptographically verified for this request (e.g., restrict to commits whose `stack.repository` matches the verified org), rather than matching purely on `sha` across the entire installation.
- Reject webhooks for organizations configured with a blank `webhook_secret` when the instance is running in multi-organization mode, or require all organizations to define one.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md` / `secrets_double_github_app.yml`-style multi-org config) with two orgs: `OrgAttacker` (no `webhook_secret`) and `OrgVictim` (secret configured, has a tracked stack with `continuous_deployment: true` and `ci.require: ["ci/tests"]`).
2. Look up a pending/undeployed commit `sha` on the victim's public GitHub repo tracked by Shipit.
3. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
   ```json
   {
     "repository": {"owner": {"login": "OrgAttacker"}},
     "sha": "<victim-sha>",
     "state": "success",
     "context": "ci/tests"
   }
   ```
   Omit/forge `X-Hub-Signature` — `verify_webhook_signature` returns `true` immediately because `OrgAttacker` has no `webhook_secret` (`lib/shipit/github_app.rb#L76-L83`).
4. `WebhooksController#verify_signature` passes (verified against `OrgAttacker`'s config), and `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb#L20-L24`) finds the victim commit purely by `sha` and calls `create_status_from_github!`, writing a fabricated "success" status onto it.
5. If this satisfies the victim stack's `ci.require`/`deployable?` gate, `schedule_continuous_delivery` (`app/models/shipit/commit.rb#L281-L287`) queues an unauthorized deploy.

```ruby
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
```
