## Title
Merkle Tree Leaf/Internal-Node Hash Domain Confusion Enables Forged Inclusion Proofs - (File: merkle.js)

### Summary
`merkle.js` computes both leaf hashes and internal (parent) node hashes with the exact same function and no domain-separation prefix, so a valid Merkle proof can be forged for an "element" that was never actually one of the tree's original leaves. This is the same class of "cryptographic primitive handling" defect flagged in the external report (imprecise/insecure Merkle proof verification), and it is directly reachable by an unprivileged unit poster via the `in merkle` address-definition authentifier and by an AA trigger sender via the `is_valid_merkle_proof` oscript function.

### Finding Description
`getMerkleRoot`/`getMerkleProof`/`verifyMerkleProof` all use the identical `hash()` primitive (plain SHA-256 over the raw string) both to hash a leaf element and to hash the concatenation of two children into a parent node: [1](#0-0) [2](#0-1) 

There is no tag/prefix (e.g. `0x00` for leaves vs `0x01` for internal nodes) distinguishing "this hash is a leaf hash" from "this hash is an internal node hash." Consequently, if an attacker knows any two sibling hash values `h1`, `h2` at some level of the tree (which are the base64 SHA-256 hashes of two real leaves/subtrees, and hashes of leaves are not secret — they can be derived from any two disclosed elements or by brute force from short/guessable data-feed values), the attacker can:

1. Compute the string `h1 + h2` and treat it as a forged "element" (a fabricated leaf), since `hash(h1+h2)` equals the value that would legitimately appear as the parent node in the real tree.
2. Build a shorter proof that starts one level higher (using only the siblings above that node) with an adjusted `index`.
3. Call `verifyMerkleProof(forged_element, forged_proof)`, which returns `true` because the computation is indistinguishable from a real proof — the verifier has no way to know that `h1+h2` should have been treated as an internal node's pre-image rather than a genuine leaf pre-image.

This lets an attacker prove "inclusion" of an arbitrary, non-existent data value against a legitimate, already-published Merkle root, without needing the root author's cooperation.

### Impact Explanation
This primitive is exposed to untrusted unit/trigger content in two places:
- The `in merkle` address-definition authentifier, which any unit author can attempt to satisfy by supplying a `serialized_proof` and having it checked against a data-feed-published root: [3](#0-2) 
- The `is_valid_merkle_proof` oscript function, directly callable by any AA trigger sender with attacker-controlled `element` and `proof` arguments evaluated against attacker-supplied or contract-referenced roots: [4](#0-3) 

If an address's spending condition uses `in merkle` to gate fund release on membership of some value in an oracle-attested Merkle root (e.g., a whitelist, KYC set, voucher list, etc.), or an AA relies on `is_valid_merkle_proof` to admit a value as valid before releasing/crediting funds, an attacker who can obtain any two sibling hashes from the same tree (trivial if any legitimate proof for a neighboring leaf has ever been published, or the leaf set is guessable/small) can forge a proof of "inclusion" of an unauthorized value. Depending on how the calling definition/AA uses the verified element (e.g., as an authorization token, a whitelisted address, or an amount unlocking key), this can lead to unauthorized spending or AA fund loss, matching the "concrete unauthorized spending / AA fund loss" impact bar.

### Likelihood Explanation
Exploitation requires the attacker to know (or brute-force) two adjacent-level hash values from the specific Merkle tree being checked. In many realistic Obyte use cases (data feeds with small/enumerable value sets, or any previously disclosed proof for a neighboring element), this is straightforward, since the leaf/inner hashes are all base64 SHA-256 values that are either public (disclosed in any prior valid proof) or easily derivable when the underlying leaf values have low entropy (booleans, short IDs, prices, etc., which is typical for `in merkle`/data-feed use). No special privileges are needed — a normal unit poster or AA-trigger sender can attempt this at will.

### Recommendation
Add domain separation to the Merkle hashing scheme in `merkle.js`, e.g. prefix leaf hashes and internal-node hashes with distinct tags before hashing (`hash("\x00" + element)` for leaves vs `hash("\x01" + left + right)` for internal nodes), consistent with common mitigations for this exact class of Merkle-proof forgery (as in Certificate Transparency RFC 6962). This must be applied consistently in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof`, and will require a network-wide activation MCI given it changes root/proof semantics for existing consumers (`in merkle` authentifier and `is_valid_merkle_proof`).

### Proof of Concept
1. Build any tree with `merkle.getMerkleRoot(arrElements)` where `arrElements` has ≥4 entries, and obtain a legitimate `merkle.getMerkleProof` for two elements `e_i`, `e_{i+1}` that are siblings at the leaf level (e.g., indices 0 and 1).
2. Compute `h_i = sha256(e_i)`, `h_{i+1} = sha256(e_{i+1})` (as done by `hash()` in `merkle.js`, base64 output).
3. Set `forged_element = h_i + h_{i+1}` (the same concatenation `verifyMerkleProof`/`getMerkleProof` would use internally at that tree level).
4. Take the original proof's siblings from level 1 upward (drop the leaf-level sibling), set `index = i/2` (per `getMerkleProof`'s indexing), and call `merkle.verifyMerkleProof(forged_element, {root, index, siblings})` per [2](#0-1) .
5. The call returns `true`, confirming a forged "leaf" (`forged_element`, which was never in `arrElements`) is accepted as included in the same `root` — demonstrating the same acceptance path exercised by `in merkle` (`definition.js:1016`) and `is_valid_merkle_proof` (`formula/evaluation.js:1799`).

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
