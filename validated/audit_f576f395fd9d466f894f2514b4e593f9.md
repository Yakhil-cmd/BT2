### Title
Webhook Signature Only Binds to the Selecting Organization, Not to the Repository/Commit the Handler Actually Mutates - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a payload against using only `repository.owner.login` (or `organization.login`), then hands the *entire, unvalidated-for-scope* JSON payload to event handlers that act on a completely different field (`repository.full_name`, or — in the `status` handler — no repository scoping at all, just a global `sha`). Any operator who legitimately controls one configured GitHub App/organization in a multi-org Shipit deployment can forge events that target stacks/commits belonging to a different organization's repository, because the HMAC only proves "this org's secret produced this byte-for-byte payload," not "this org owns the repository/commit referenced inside the payload."

### Finding Description
`verify_signature` resolves the app via `repository_owner`, derived straight from the untrusted payload: [1](#0-0) [2](#0-1) 

Once `github_app.verify_webhook_signature(signature, raw_post)` succeeds for that org's secret, the full raw payload is dispatched to handlers unmodified: [3](#0-2) 

Handlers, however, key their side effects off a *different* payload field — `repository.full_name` — via the shared base class: [4](#0-3) 

`PushHandler` and `CheckSuiteHandler` use this `repository_name`-derived `stacks` scope to trigger `sync_github` / `schedule_refresh_check_runs!`: [5](#0-4) [6](#0-5) 

`StatusHandler` is worse: it does not scope to any repository at all — it looks up commits globally by `sha` across the entire Shipit instance and writes a GitHub status onto them: [7](#0-6) 

The equality the code assumes is:
`org whose secret validated the HMAC == org that owns the repository/commit the handler mutates`

This equality is never enforced. Shipit explicitly supports multiple independently-configured GitHub Apps/organizations sharing one instance (see the multi-org `github:` config block), each with its own `webhook_secret`: [8](#0-7) 

An operator who legitimately controls Org A's app secret can craft a raw payload where `repository.owner.login = "org-a"` (satisfies signature-selection) but `repository.full_name = "org-b/victim-repo"` (or, for `status` events, an arbitrary `sha` belonging to any tracked commit anywhere in the instance) and self-compute a valid HMAC using their own known secret. `verify_signature` only checks that the byte stream matches Org A's secret — it has no opinion about the semantic content of that stream — so the forged cross-organization payload passes.

### Impact Explanation
This breaks the trust boundary between organizations sharing one Shipit deployment: an org-scoped webhook secret is treated as authorization to act on a completely different org's stacks and commits. Concretely:
- `StatusHandler` lets the attacker call `commit.create_status_from_github!` on any commit tracked anywhere in the Shipit instance, forging arbitrary CI/status states (e.g., marking a victim's commit as passing required checks), which feeds directly into deployability/mergeability decisions elsewhere in Shipit.
- `PushHandler`/`CheckSuiteHandler` let the attacker trigger `stack.sync_github` or check-run refresh cycles on a victim organization's stacks without ever touching that org's real webhook secret.

This maps to an unauthorized/forged deploy-readiness signal on a repository the attacker does not control, satisfying the "unauthorized deploy, rollback or merge" / cross-organization write impact class.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to be a legitimate operator/owner of at least one of those configured orgs' GitHub Apps — i.e., an "unprivileged" party relative to the *other* orgs sharing the instance, with no access to the victim org's secrets, tokens, or repositories. No GitHub App private key, `ApiClient` token, or Shipit session is needed — only knowledge of a webhook secret the attacker legitimately possesses for their own org.

### Recommendation
After signature verification, re-derive the organization from the same field(s) used to select the verifying app (`repository.owner.login`) and require it to match the organization/owner embedded in `repository.full_name` before dispatching to any handler. `StatusHandler` in particular must scope its `Commit` lookup to the verified organization's stacks/repositories rather than querying `Commit.where(sha: ...)` globally.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `org-a` (attacker-controlled app/secret) and `org-b` (victim), per the documented multi-org `github:` config.
2. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<victim commit sha in org-b's tracked stack>",
     "state": "success",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/attacker-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, body)` themselves (they legitimately hold `org-a`'s webhook secret).
4. `verify_signature` resolves `repository_owner => "org-a"`, fetches `org-a`'s `GitHubApp`, and the HMAC matches — request passes with `head(422)` never called: [1](#0-0) 
5. `StatusHandler#process` looks up the commit purely by `sha` (no org/repo check) and writes a forged `success` status onto the victim's commit: [7](#0-6)

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
