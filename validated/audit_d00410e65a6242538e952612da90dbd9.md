### Title
Webhook signature verification binds trust to `repository.owner.login`, not to the `repository.full_name` that handlers act on, enabling cross-organization/cross-repository writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository.owner.login` (falling back to `organization.login`), but every event `Handler` resolves the actual `Repository`/`Stack` to mutate using an entirely different JSON field, `repository.full_name`. Because the HMAC only proves "this body was signed with the secret belonging to the org named in `repository.owner.login`," and does not bind that org to `repository.full_name`, any organization onboarded into this Shipit instance can forge a payload whose `owner.login` matches its own org (and its own legitimate secret) while `full_name` points at a completely different, unrelated repository tracked by Shipit — causing writes against that other repository's stacks/commits.

Shipit explicitly supports multi-organization deployments where each organization has its own `webhook_secret`/`app_id`/`private_key` under `config/secrets*.yml`: [8](#0-7) 

This is exactly the bug class in the report: a value that is checked/verified (`repository.owner.login`, used to pick the signing key) is not the same value that the downstream logic actually acts on (`repository.full_name`, used to select the DB records to mutate), and the two are never cryptographically bound to each other — analogous to `ComputeWithdrawals` trusting a validator `status` field that lagged behind the real withdrawal state instead of the field that should have gated the classification.

**Equality that should hold, but doesn't:**
`org(repository.owner.login used for HMAC key selection) == org(repository.full_name whose Stack/Repository is written)`

Before the attack: for legitimate GitHub-originated webhooks, GitHub always sets both fields consistently for the same real event, so the equality happens to hold.
After the attack: an org admin of Org B (who legitimately possesses Org B's own `webhook_secret` because they configured Org B's GitHub App to point at the shared Shipit instance) crafts a raw POST body where `repository.owner.login = "org-b"` (so the HMAC computed with Org B's own secret passes) but `repository.full_name = "org-a/target-repo"`. `verify_signature` passes because it only checked Org B's secret against Org B's own name. The dispatched handler then looks up `Repository.from_github_repo_name("org-a/target-repo")` and mutates Org A's stacks/commits — a repository Org B never had write/webhook access to.

### Impact Explanation
This breaks the deployment-trust boundary between "the organization that authenticated the request" and "the repository that gets written," matching the Critical impact category of cross-repository writes. Concrete effects reachable through in-scope handlers:
- `StatusHandler#process` calls `commit.create_status_from_github!(params)` for any commit `sha` that happens to exist in Org A's stacks, letting Org B inject a fabricated commit status (e.g. a fake "success" CI status) for another org's repository, which can gate `ci.require` checks and unblock continuous deployment/merge queue decisions for a repo Org B doesn't own.
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` (queues `GithubSyncJob`) against Org A's stacks.
- `CheckSuiteHandler#process` schedules `schedule_refresh_check_runs!` on Org A's commits.

These are legitimate unauthorized cross-organization writes to another tenant's deployment state, potentially influencing an unauthorized deploy decision (via forged CI/status data used for merge/deploy gating).

### Likelihood Explanation
Requires the attacker to be an administrator of *some* organization already onboarded into the same multi-tenant Shipit instance (a supported, documented configuration — see `config/secrets.development.shopify.yml` listing multiple orgs). No access to the target organization, no GitHub App private key of the target, and no Shipit session/API token for the target repository is required — only the attacker's own legitimate webhook secret for their own onboarded org, which they are entitled to use to send webhooks to this endpoint. This is a realistic, moderate-likelihood scenario for any Shipit deployment shared across multiple organizations/tenants.

### Recommendation
Bind the verified identity to the field actually used for record resolution: after computing the HMAC using the secret selected via `repository.owner.login`/`organization.login`, additionally verify that `repository.full_name`'s owner segment matches that same verified organization (i.e., `repository.full_name.split('/').first == repository_owner`) before dispatching to handlers, and reject (422) on mismatch. Alternatively, resolve the signing secret from the `Repository` record matched by `full_name` (looking up the owning organization from Shipit's own `Repository`/`Stack` records) rather than trusting an attacker-suppliable field for key selection.

### Proof of Concept
1. Onboard/attack from Organization B, which has a legitimate GitHub App installed on the shared Shipit instance with its own `webhook_secret_B`.
2. Craft a raw JSON body for a `status` (or `push`/`check_suite`) event:
   ```json
   {
     "repository": { "owner": { "login": "org-b" }, "full_name": "org-a/target-repo" },
     "sha": "<known sha of a commit tracked under org-a/target-repo>",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_B, raw_body)>` using Org B's own secret.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-b")` and successfully verifies the signature against Org B's own secret.
6. `Shipit::Webhooks.for_event("status")` dispatches to `StatusHandler`, which looks up `Commit.where(sha: ...)` — matching commits under `org-a/target-repo` — and calls `commit.create_status_from_github!(params)`, injecting a forged status onto Org A's repository despite the request having been authenticated only as Org B.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
