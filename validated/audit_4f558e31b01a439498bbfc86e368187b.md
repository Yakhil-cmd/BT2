### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but handlers dispatch on the unrelated `repository.full_name` field, letting a signature valid for one configured org authorize writes against any repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using `repository_owner`, a value taken straight out of the untrusted JSON body. All the downstream event handlers, however, resolve the actual `Stack`/`Repository` to mutate using a completely different, equally attacker-controlled field: `repository.full_name`. Because these two payload fields are never cross-checked against each other, a signature that is valid for organization A (the value put in `repository.owner.login`) can be attached to a payload whose `repository.full_name` names a repository belonging to organization B, letting the request act on B's stacks despite never being signed by B's secret.

### Finding Description
`WebhooksController#verify_signature` computes the organization to authenticate against purely from the payload: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once the request passes this check (or is dropped with 422), the handler for the event is invoked with the full JSON body. Every handler independently determines which `Repository`/`Stack` records to touch using `repository.full_name` from that same body: [3](#0-2) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository_owner` (used for signature verification) and `repository.full_name` (used to select the target stack) are two independent JSON paths inside the same attacker-controlled payload; nothing enforces that `full_name`'s owner segment matches `repository_owner`. An attacker who can obtain a valid signature for *any one* organization configured in Shipit (for example, an org with `webhook_secret` left blank in `secrets.yml`, for which `GithubApp#verify_webhook_signature` unconditionally returns `true`) can set `repository.owner.login` to that organization while setting `repository.full_name` to an entirely different, victim repository that has real stacks configured. Verification passes because it only inspects `repository.owner.login`; the handler then acts on the victim's stacks because it only inspects `repository.full_name`. [4](#0-3) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

`Shipit.github(organization:)` looks up the app config by whatever organization name is supplied, so an attacker only needs to know or guess the name of one configured (or unconfigured-secret) organization, not the victim's.

### Impact Explanation
This breaks the trust binding "the organization that authenticated == the repository being written," which the rules identify as a Critical/High analog class. The `PushHandler` triggers `stack.sync_github`, which drives `GithubSyncJob`/`CacheDeploySpecJob` against the victim stack, and other handlers (`opened_handler`, `labeled_handler`, etc.) can archive/unarchive stacks or mutate pull-request/review-stack state for a repository the forged payload never actually authenticated for. This is an unauthorized write against a repository/stack the request was not signed for — i.e., a cross-repository write triggered by an unprivileged, unauthenticated attacker (no Shipit session, no `ApiClient` token, no repository write access — only knowledge of an organization name and, in the weakest case, the fact that one configured org has no `webhook_secret`).

### Likelihood Explanation
Exploitability depends entirely on whether an attacker can produce a signature that verifies for *some* configured organization while naming a different, victim repository. This is trivially possible when any configured GitHub App entry has `webhook_secret` unset (the code explicitly treats that as "always verified" — see `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.shopify.yml`, which both ship with `webhook_secret: # nil` examples), or if an attacker otherwise learns/leaks one org's `webhook_secret` (which itself is a lower-privilege secret than write access to the victim repository). Likelihood is therefore configuration-dependent but concretely reachable through the engine's own code path, not through any assumption that the host misconfigures the mounting of the engine.

### Recommendation
After verifying the signature, re-derive (or cross-check) the organization actually referenced by `repository.full_name` and reject the request if it does not match the organization whose secret produced a valid signature. Concretely, `verify_signature` should extract the owner segment of `repository.full_name` (not a separate `repository.owner.login`/`organization.login` field) and use that single, consistent value both to select the `GithubApp` and to resolve the target repository, so the two lookups can never diverge.

### Proof of Concept
1. Configure/observe that org `unsecured-org` has `webhook_secret: nil` in `secrets.yml` (or otherwise obtain `unsecured-org`'s webhook secret).
2. POST to `/webhooks` with header `X-Github-Event: push` and a body such as:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured), so the request passes signature checking with any (or no) `X-Hub-Signature` value.
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef")` on the victim's stacks - a write the request was never signed for by `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
