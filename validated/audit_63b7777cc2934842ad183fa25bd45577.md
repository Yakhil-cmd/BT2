## Title
Cross-organization webhook forgery via unbound `repository.owner.login` vs `repository.full_name` fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a signature against using `repository.owner.login` (or `organization.login`), but every event handler that actually mutates state resolves its target `Stack`/`Repository` using a completely different, unchecked field: `repository.full_name`. Nothing in the request path verifies that these two fields agree. In a multi-organization Shipit deployment (explicitly documented and supported), this breaks the intended binding `organization that authenticated == repository that is written`, letting the legitimate administrator of one configured GitHub organization forge webhook events that are processed as if they belong to any other organization/repository tracked by the same Shipit instance.

### Finding Description
`Shipit::WebhooksController#verify_signature` computes which `GitHubApp` (and therefore which `webhook_secret`) to validate the HMAC signature against solely from the payload field `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (including a distinct `webhook_secret`) via `github_app_config`, which is exactly how multi-tenant installs are documented to work: [3](#0-2) [4](#0-3) 

Once the signature is accepted, the *handlers* that actually act on the request never look at `repository.owner.login` again — they resolve the target repository/stack from a different payload field, `repository.full_name`: [5](#0-4) [6](#0-5) 

The same pattern repeats in the pull-request handlers, which trust `params.repository.full_name` to pick the target repository/review-stack and then persist attacker-supplied JSON (labels, PR state, head sha, assignees) directly, without any independent GitHub API confirmation: [7](#0-6) [8](#0-7) [9](#0-8) 

Because `request.raw_post` (the entire JSON body) is what's HMAC-signed, and Shipit never cross-checks that `repository.owner.login` (used to pick the secret) actually matches the owner segment of `repository.full_name` (used to pick the target), an operator of GitHub organization "A" — who legitimately knows organization A's own `webhook_secret` because they configured that GitHub App themselves, exactly as documented — can build an arbitrary payload where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` selects and validates against OrgA's own secret, which the attacker legitimately possesses), and
- `repository.full_name` = `"OrgB/victim-repo"` (or any repository name tracked by any stack on the shared Shipit instance).

Since the handlers only trust `repository.full_name`, this forged-but-validly-signed request is processed as a legitimate event for OrgB's stack, e.g. archiving/unarchiving/deprovisioning a review stack, or injecting fabricated pull-request/label state, `stack.sync_github` triggers, etc. — all against a repository the attacker has no actual access to.

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written," directly matching the Critical "cross-repository writes" impact category: an actor with legitimate credentials scoped to one tenant/organization can cause writes (review-stack provisioning/archival, pull-request record mutation, forced sync) against stacks belonging to a completely different, unrelated organization hosted on the same shared Shipit instance.

### Likelihood Explanation
Requires a Shipit deployment configured with multiple GitHub organizations (a documented, supported configuration — see "Using Multiple Github Applications" in `docs/setup.md`). Any party that legitimately administers one of those configured GitHub Apps (and therefore knows only their own org's `webhook_secret`, not a stolen credential) can exploit this with a single crafted HTTP POST to `/webhooks`. No access to other tenants' secrets, private keys, or Shipit sessions is required.

### Recommendation
Cross-validate that the organization used to select/verify the webhook signature is consistent with the repository the handlers act on: derive both from the same trusted field (e.g. always resolve the organization from `repository.full_name`'s owner segment, or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before dispatching to handlers), and reject the request if they diverge — analogous to validating `token0`/`token1` against the pair actually being swapped rather than trusting an unchecked field.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (per `docs/setup.md` multi-org example). `OrgB/victim-repo` has an active review stack.
2. Attacker administers `OrgA`'s GitHub App and knows `OrgA`'s `webhook_secret` (legitimately, as its own app owner).
3. Attacker crafts a `pull_request` webhook JSON body with `organization.login` / `repository.owner.login` = `"OrgA"` but `repository.full_name` = `"OrgB/victim-repo"`, `action: "labeled"`, and a forged label that matches OrgB's `provisioning_label_name`.
4. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` over the raw body and POSTs to `/webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully validates the signature (attacker knows this secret).
6. `Shipit::Webhooks::Handlers::PullRequest::LabeledHandler` resolves the target repository from `params.repository.full_name` = `"OrgB/victim-repo"` and calls `stack.archive!` / `unarchive!` on OrgB's review stack — a write the attacker was never authorized to perform.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
