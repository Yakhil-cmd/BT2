### Title
CCMenu API endpoint bypasses per-stack authorization scoping, letting a stack-scoped ApiClient token read the status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces two independent authorization layers for API clients: an operation/scope permission (`read:stack`, `write:stack`, ...) and a per-object scope restriction when the `ApiClient` is bound to a single `stack_id`. `Shipit::Api::CCMenuController` inherits the permission check but overrides the stack-lookup helper in a way that silently drops the per-object scope restriction, so the "operation authorised" check passes while the "which stack it touches" check is never applied - exactly the acted-upon-field vs. verified-field mismatch pattern of the referenced bug class.

### Finding Description
`BaseController` computes the accessible stack set from the authenticated `ApiClient`: [1](#0-0) 

`current_api_client.stack_id?` restricts `stacks` (and therefore `stack`) to the single stack the client was scoped to when it was created (see the `here_come_the_walrus` fixture, scoped to the `shipit` stack): [2](#0-1) 

`CCMenuController` requires only the coarse `read:stack` operation permission, which is a global "can this client read *some* stack" bit, not a "which stack" check: [3](#0-2) 

It then overrides `stack` to bypass the scoped `stacks` collection entirely and resolve the stack directly against the global `Stack` table: [4](#0-3) 

`ApiClient#check_permissions!` only compares the `operation:scope` string; it has no knowledge of `stack_id` and cannot detect that the requested `params[:stack_id]` differs from the client's authorized stack: [5](#0-4) 

The controller even supports authenticating via a query-string `token` param (in addition to Basic Auth), which is how CCMenu URLs are normally shared/embedded: [6](#0-5) [7](#0-6) 

**Binding broken:** `stack a token authorises == stack it touches`. Before the request, `here_come_the_walrus`'s token authorises only `stack_id = shipit.id` (enforced by `BaseController#stacks`). After the request (`GET /api/stacks/:stack_id/ccmenu.xml` with an arbitrary `stack_id`), the same token successfully touches any stack in the instance because `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Impact Explanation
A scoped `ApiClient` (e.g., a CCMenu widget/status-badge token deliberately restricted to one stack via `ApiClient#stack_id`, generated for example by `CCMenuUrlController#client`) can be used to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state) of every other stack managed by the Shipit instance, including stacks the token holder was never granted access to. This is a scope-escalation / unauthorized cross-stack read of stack state, matching the "escalation into `Shipit.github_teams` authorization... unauthenticated read of stack state" High-impact category, since it defeats the per-stack containment that the rest of the API (`BaseController#stack`) correctly enforces.

### Likelihood Explanation
High. Exploitation requires only possession of any valid, narrowly-scoped `ApiClient` token (which by design is meant to be shared broadly, e.g., embedded in CI dashboards or CCMenu URLs) and changing the `stack_id` in the request path/query string - no privileged access, no signature forgery, and no additional credentials are needed beyond the low-trust token itself.

### Recommendation
Make `CCMenuController#stack` reuse the scoped `stacks` collection from `BaseController` instead of querying `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a stack-scoped `ApiClient` can never resolve a `stack_id` outside `current_api_client.stack_id`.

### Proof of Concept
1. Create (or use fixture) `ApiClient` `here_come_the_walrus` scoped to stack `shipit` with `permissions: ['read:stack']` and note its `authentication_token`. [2](#0-1) 
2. Send `GET /api/stacks/<some-other-stack>/ccmenu.xml?token=<here_come_the_walrus_token>` for a stack the client is not scoped to.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` (not the scoped `stacks` helper), and `check_permissions!` only checks the `read:stack` string, the request succeeds and returns the other stack's CCMenu XML (name, lastBuildStatus, lastBuildLabel, webUrl), even though the token is only supposed to authorise the `shipit` stack — contrast with `Api::StacksController#show`, which uses the scoped `stack` helper and correctly returns 404/empty for out-of-scope stacks (see the passing "an api client scoped to a stack will only see that one stack" test): [8](#0-7)
