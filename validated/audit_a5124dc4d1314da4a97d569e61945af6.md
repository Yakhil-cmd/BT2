I found a confused-deputy authorization gap in the CCMenu API endpoint that exactly matches the "a stack a token authorises versus a stack it touches" binding pattern described in the rules.

### Title
Stack-scoped ApiClient token can read CCMenu status of any stack, bypassing its `stack_id` restriction - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` resolution helper from `Shipit::Api::BaseController` with an unscoped lookup, so an `ApiClient` token that is supposed to be restricted to a single stack (`ApiClient#stack_id`) can be used to read the CCMenu status of *any* stack in the installation.

### Finding Description
`Shipit::Api::BaseController` implements per-token stack scoping: any endpoint calling `stack` goes through `stacks`, which filters by `current_api_client.stack_id` when the token has one set. [1](#0-0) 

`Shipit::Api::CCMenuController`, however, defines its own private `stack` method that ignores this scoping entirely and resolves the stack directly from the request parameter: [2](#0-1) 

The only authorization check performed before `show` executes is the generic permission-scope check `require_permission :read, :stack`, which validates that the token carries the `read:stack` permission string but does not verify that the requested stack matches the token's bound `stack_id`: [3](#0-2) 

This is the same class of bug as the reported Solidity issue: a verification step operates on the wrong binding — the code checks "does this token have `read:stack` permission generally" instead of "does this token's authorized stack equal the stack being touched." The equality that should hold and is broken is:

`current_api_client.stack_id == params[:stack_id]` (enforced everywhere else via `stacks.from_param!`) vs. what `CCMenuController` actually evaluates: `Stack.from_param!(params[:stack_id])` (no comparison to `current_api_client.stack_id` at all).

Contrast with `TasksController`, `HooksController`, and other API controllers that inherit the scoped `stack`/`stacks` helpers from `BaseController` unmodified. [4](#0-3) [5](#0-4) 

### Impact Explanation
Any legitimately-issued, stack-scoped API token (e.g. `here_come_the_walrus`, fixture-restricted to the `shipit` stack with only `read:stack` permission) can be used to enumerate and read CCMenu status (build/deploy status, lock state, stack name) for every other stack hosted by the Shipit instance, including stacks belonging to unrelated teams/repositories. This is an unauthorized cross-stack read of deploy/build state, which falls under the "unauthenticated read of stack state" High-severity category since it grants visibility outside of the credential's intended authorization boundary. [6](#0-5) 

### Likelihood Explanation
Exploitation only requires possessing any existing stack-scoped `read:stack` API token (a routine, low-privilege credential handed out for CI/status-badge integrations) and changing the `stack_id` route parameter to a different stack's identifier — no additional secrets, sessions, or elevated privileges are needed.

### Recommendation
Have `CCMenuController#stack` reuse the scoped `stacks` helper from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack.from_param!` directly, so the `current_api_client.stack_id` restriction is enforced consistently with the rest of the API.

### Proof of Concept
1. Create/obtain an `ApiClient` token scoped to Stack A only, e.g. `stack: A, permissions: ['read:stack']` (mirrors fixture `here_come_the_walrus`).
2. Send `GET /api/stacks/:B_id/ccmenu.xml` using Basic Auth with that token, where `B_id` is a different stack the token is not associated with.
3. Observe that `require_permission :read, :stack` passes (token has `read:stack`) and `CCMenuController#show` returns Stack B's CCMenu XML (`assert_payload 'name', ...`, `lastBuildStatus`, etc.), even though the token's `stack_id` is A. [7](#0-6)
