### Title
Unvalidated swap-route addresses can inject token transfers into the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary

**Severity: Medium**

Strategy entrypoints accept an opaque `swap: Bytes` route and pass it to the configured router without constraining which pool or token contracts the route invokes. A malicious route can therefore place attacker-controlled code below the caller’s authorized controller invocation. That code can request an unrelated `token.transfer(caller, attacker, amount)`; transaction simulation records it as a child authorization, and it executes if the caller signs the generated tree. [1](#0-0) [2](#0-1) 

### Finding Description

`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` all accept caller-supplied route bytes. [3](#0-2) [4](#0-3) [5](#0-4) 

`process_swap_collateral` authorizes the caller, loads the owned or delegated account, and forwards the supplied `swap` into the withdrawal/swap path. [6](#0-5) 

`swap_tokens` obtains the configured router, snapshots only the controller’s input and output balances, grants exactly one controller-token transfer, and then invokes `router.execute_strategy(&controller, &amount_in, swap)`. It does not decode the route, allowlist route-selected contracts, or prevent those contracts from requesting additional authorization from the original caller. [7](#0-6) 

The post-swap checks only reject controller input growth, spending above `amount_in`, and non-positive controller output. They do not detect a transfer from the caller’s unrelated wallet balance requested by route-selected code. [8](#0-7) 

The project’s threat model confirms that route payload addresses are not allowlisted and that a token transfer requested by third-party route code is recorded as a child of the caller’s authorization entry. [9](#0-8) 

### Impact Explanation

A malicious route can steal tokens unrelated to the lending position and unrelated to the routed input amount. The swap can still return a fair output and satisfy the controller’s measured-output and final-risk checks, so the transaction appears successful while the route’s injected child transfer moves wallet assets to the attacker. [10](#0-9) 

The exploitable surface is not limited to collateral swapping: the same opaque route reaches the router from `swap_debt`, `repay_debt_with_collateral`, and `multiply`. [11](#0-10) [12](#0-11) 

### Likelihood Explanation

The attack requires the victim to execute a malicious route and sign the poisoned authorization tree produced by simulation. It does not require protocol privileges, leaked keys, a compromised router, or control of listed token contracts. The unsigned rogue transfer fails under an honest authorization tree, but succeeds when the caller signs the tree containing it. [13](#0-12) 

Because current wallet and client flows can present simulation-produced authorization trees as opaque signing material, this is a realistic phishing/route-supply-chain risk rather than direct unauthorized access. The residual user-signing requirement lowers likelihood, supporting Medium severity.

### Recommendation

Do not allow arbitrary route-selected pool or token contracts to execute beneath strategy entrypoints. Enforce a governance-approved venue/pool allowlist when decoding the route, or constrain the router interface to a fixed set of audited venue adapters that cannot dispatch to arbitrary payload addresses.

In addition, clients should simulate the full transaction, decode the returned authorization tree, and reject any strategy whose caller authorization contains children other than the expected input-token transfer. The current threat model already identifies this client-side requirement, but contract-level venue allowlisting would prevent the malicious authorization request from arising in the first place. [9](#0-8) 

### Proof of Concept

The repository contains an executable model in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Alice has supplied USDC and also holds `WALLET_BALANCE` of an unrelated token. The test installs a router double as the configured swap aggregator. [14](#0-13) 
2. The route names an attacker-controlled `hop_pool`; the router decodes that route-selected address and invokes its `swap` function. [15](#0-14) 
3. The rogue pool calls `token.transfer(Alice, attacker, WALLET_BALANCE)` for the unrelated wallet token. [16](#0-15) 
4. The attacker submits a `swap_collateral` route to:

```text
swap_collateral(
    caller = Alice,
    account_id = Alice's account,
    current = HubAssetKey(USDC),
    amount = 50_000_000_000,
    new = HubAssetKey(ETH),
    swap = route naming RogueHopPool
)
```

The test constructs exactly these controller arguments. [17](#0-16) 

5. Simulation records the unrelated wallet-token transfer as a child beneath Alice’s `swap_collateral` authorization. [18](#0-17) 
6. With the poisoned signed tree, Alice’s entire unrelated wallet balance moves to the attacker while she still receives the expected ETH supply output. [19](#0-18)
