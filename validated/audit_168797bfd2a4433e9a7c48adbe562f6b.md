### Title
Webhook signature verification keyed on `repository.owner.login` is decoupled from the repository mutated via `repository.full_name`, letting an attacker-controlled no-secret org authorize writes to another org's `PullRequest` - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) to check using `repository.owner.login` from the untrusted JSON body, while every `pull_request` handler, including `AssignedHandler`, resolves the actually-affected `Shipit::Repository` using the separate `repository.full_name` field from the same body. Because `GitHubApp#verify_webhook_signature` returns `true` whenever no `webhook_secret` is configured for the selected organization, an attacker who names any Shipit-known-but-secretless org in `repository.owner.login` bypasses signature verification entirely, and can then set `repository.full_name` to point at a victim org's real repository/stack, causing `AssignedHandler` to `update` that victim's persisted `PullRequest` record.

### Finding Description
The broken binding: the code implicitly assumes
`params.dig('repository','owner','login') == params.dig('repository','full_name').split('/').first`
but nothing enforces this equality.

Path:
1. `before_action :verify_signature` computes `repository_owner` purely from `params.dig('repository','owner','login')` [1](#0-0)  and looks up `github_app = Shipit.github(organization: repository_owner)` to verify the signature [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` when the resolved org has no `webhook_secret` configured: `return true unless webhook_secret` [3](#0-2) . So naming any Shipit-known org that lacks a configured secret in `repository.owner.login` passes verification unconditionally, without needing to forge any HMAC.
3. `create` then dispatches the *entire raw JSON* to handlers with no re-check that `repository.owner.login` matches anything else in the payload [4](#0-3) .
4. `AssignedHandler#repository` resolves the target repository independently, from `params.repository.full_name`, which is attacker-controlled and unrelated to the field used in step 1: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) .
5. `AssignedHandler#process` looks up an existing `Shipit::PullRequest` joined through that resolved repository/stack by `number`, and calls `.update(github_pull_request: params.pull_request)` on it — a real write to a real record belonging to whatever org owns `full_name`, not the org that "authenticated" the request [6](#0-5) .

Existing guards do not stop this: `drop_unhandled_event`/`check_if_ping` only gate on event type; `verify_signature`'s only failure modes are an unrecognized org (`GithubOrganizationUnknown` → 422) or a bad HMAC for a *secreted* org — neither applies when the chosen org is known but secretless. The `ExplicitParameters` schema on `AssignedHandler` only validates types/presence of `repository.full_name`, not its relationship to `repository.owner.login` [7](#0-6) . `Repository.from_github_repo_name` performs a plain lookup with no ownership cross-check [8](#0-7) .

### Impact Explanation
An unprivileged internet user can cause Shipit to accept an unauthenticated/unverified `pull_request` webhook and have it mutate a `PullRequest` record belonging to a completely different, victim-owned repository/stack (including a production-environment stack) — a "payload for one repository mutating another's stack" scenario, matching the Critical impact category. The attacker controls the injected `github_pull_request` JSON (head sha/ref, labels, assignees, additions/deletions, title, state) for an existing tracked PR number on the victim stack, which can corrupt data used for merge/deploy decision-making downstream. This is repeatable against any Shipit-configured organization that has no `webhook_secret` set, against arbitrary victim repositories/stacks known to the attacker (repo names are public), with no session, token, or GitHub secret required.

### Likelihood Explanation
Preconditions: (a) Shipit must have at least one organization configured in `Shipit.github` config without a `webhook_secret` (a realistic multi-org/enterprise misconfiguration — nothing in the code enforces that all configured orgs have secrets), and (b) the attacker must know the victim's `owner/repo` full name and an existing PR number on the victim's production stack — both of which are public GitHub information. Attacker cost is a single crafted `POST /webhooks` HTTP request with a `pull_request`/`unassigned` payload; no GitHub App keys, `secret_key_base`, `api_clients_secret`, or session are needed. This is fully repeatable and scriptable against any number of victim stacks.

### Recommendation
Cross-validate that `params.dig('repository','owner','login')` matches the owner segment of `params.dig('repository','full_name')` before accepting the event, and/or select and verify the webhook secret based on the repository actually resolved by handlers (`full_name`), not a separate, independently-controlled field. Additionally, require that every configured GitHub organization have a non-blank `webhook_secret`, and fail closed (reject, not accept) when a secret is absent rather than treating "no secret configured" as "verification not required".

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in `Shipit.github_apps` test config: `"attacker-org"` with `webhook_secret: nil`, and `"victim-org"` with a real `webhook_secret`.
2. Create `victim_repo = shipit_repositories(:shipit)` owned by `"victim-org"`, a production-environment `stack` on it, and a `Shipit::PullRequest` with `number: 42` and known `github_pull_request` baseline data.
3. Build a `pull_request`/`action=unassigned` JSON body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/shipit"`, and `pull_request.number = 42` with attacker-chosen `head.sha`, `labels`, `assignees`.
4. `POST /webhooks` with `X-Github-Event: pull_request` and an arbitrary/garbage `X-Hub-Signature` (no valid HMAC for either org's secret).
5. Assert response is `200 OK` (not `422`), proving signature verification was bypassed via the "attacker-org" no-secret path.
6. Reload the victim `PullRequest` record and assert its `github_pull_request` fields now equal the attacker-supplied values — proving a write occurred on the victim's production stack despite the request never being authenticated by `victim-org`'s secret.
7. Equality check before/after: assert `pull_request.reload.github_pull_request['head']['sha'] == attacker_sha` (violated invariant) versus the expected invariant `repository_owner_used_for_auth == full_name.split('/').first` (false in this run).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
