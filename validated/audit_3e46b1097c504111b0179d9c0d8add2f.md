## Analysis

The curve report's bug class is: a privileged actor exploits a code path where a critical invariant (fund custody) is checked/enforced in one place but bypassed through an alternate execution path (reentrancy / `withdraw_admin_fees`). The reachable analog in `shipit-engine` is a scope-binding bypass in the API layer: **the invariant "an `ApiClient` token scoped to stack A may only touch stack A" is enforced by one code path (`Api::BaseController#stacks`/`#stack`) but a sibling controller reaches the `Stack` model through a different path that skips that scoping entirely.**

### Root cause

`Shipit::Api::BaseController` is the only place that binds an `ApiClient`'s `stack_id` to the `Stack` it is allowed to touch: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

`require_permission!` (used via the `require_permission` class macro) never checks the target stack — it only checks the `ApiClient#permissions` array: [2](#0-1) [3](#0-2) 

So the *only* place that turns "authorised stack" into "touched stack" is the overridden `stack`/`stacks` method. `Api::CCMenuController` overrides `stack` to bypass this binding entirely, loading directly from `Stack.from_param!(params[:stack_id])` with no scoping to `current_api_client.stack_id`: [4](#0-3) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`require_permission :read, :stack` on this controller only proves the token has the string `"read:stack"` somewhere in its `permissions` array; it never checks that `params[:stack_id]` equals `current_api_client.stack_id`. Fixtures confirm scoped clients legitimately exist (`stack: shipit`, `permissions: [read:stack]`): [5](#0-4) 

### The equality that breaks

`stack authorised by token (current_api_client.stack_id)` ≠ `stack touched by the request (params[:stack_id] via Stack.from_param!)` for `Api::CCMenuController#show`, whereas that equality is exactly what `BaseController#stacks` is designed to enforce for every other API controller (`StacksController`, `TasksController`, etc., which all call the scoped `stack`/`stacks` helpers).

### Title
Stack-scoped ApiClient token can read CCMenu status of any stack via unscoped lookup - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController#stack` overrides the base `stack` helper and loads the target `Stack` directly by `params[:stack_id]` instead of going through `stacks.from_param!`, which is the only mechanism binding an `ApiClient`'s `stack_id` scope to the stack a request may act on.

### Finding Description
`ApiClient` supports being scoped to a single stack (`belongs_to :stack, optional: true`) with limited permissions such as `read:stack`. The intended invariant, enforced in `Api::BaseController#stacks`/`#stack` (`app/controllers/shipit/api/base_controller.rb:74-80`), is that a scoped client can only resolve stacks matching its own `stack_id`. `require_permission!` (`app/controllers/shipit/api/base_controller.rb:82-84` and `app/models/shipit/api_client.rb:38-45`) never re-checks this scope — it purely checks the string permission. `Api::CCMenuController` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly, completely skipping the `stacks` scoping method. As a result, any holder of a stack-A-scoped `read:stack` token can request `/{any_org}/{any_repo}/{any_env}/ccmenu.xml?token=<their_token>` for stack B and successfully authenticate and read stack B's deploy status.

### Impact Explanation
This is an unauthorized cross-stack read of stack/deploy state by a credential that was explicitly restricted to a single stack — the token authorises stack A but the code lets it touch stack B. It discloses deploy/task status (`running?`, `ended_at`, last deploy id) for stacks outside the token's authorized scope, which falls under unauthorized/escalated read of stack state across the multi-tenant deployment boundary that `ApiClient.stack_id` scoping exists to enforce.

### Likelihood Explanation
High for anyone who already legitimately holds a stack-scoped `read:stack` token (e.g., a CI system or team given least-privilege access to one stack): no additional exploitation technique is needed beyond supplying a different `stack_id` in the URL. The bug is a straightforward code path divergence, not a race condition or timing-dependent bug.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction from `BaseController#stacks` is honored for this controller as it is for the others.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` (mirrors `here_come_the_walrus` fixture: `stack: shipit`, `permissions: [read:stack]`).
2. Using this client's token, call `GET /api/:owner_b/:repo_b/:env_b/ccmenu.xml?token=<token>` where `owner_b/repo_b/env_b` resolve to Stack B, a stack the client is not scoped to.
3. Observe `Api::CCMenuController#authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (client has `read:stack` in its permissions list), and `stack` resolves to Stack B via unscoped `Stack.from_param!`, returning Stack B's deploy/task status in the response — despite the client only being authorized for Stack A.
