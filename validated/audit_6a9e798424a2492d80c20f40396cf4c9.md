### Title
Cross-tenant forged `status` webhook triggers unauthorized merges/deploys via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub organization named in the attacker-supplied payload (`repository.owner.login`), and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization has no `webhook_secret` configured. `StatusHandler#process` then looks up `Commit.where(sha: params.sha)` globally, with no filter on `repository`/`stack`, so an attacker who only "authenticates" as one no-secret org can write a `Status` onto a commit belonging to an entirely different, unrelated stack (including a production stack) merely by knowing that commit's SHA.

### Finding Description
The broken binding: the code implicitly assumes `authenticated_organization == commit.stack.repository.owner`, but nothing enforces this equality.

- `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the attacker-controlled JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that organization: `return true unless webhook_secret` [2](#0-1) . `webhook_secret` is explicitly documented as optional (`docs/setup.md`), so it is common/expected for at least one configured org to have none.
- Once past signature verification, `WebhooksController#create` dispatches to `StatusHandler.call(params)` [3](#0-2) .
- `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this is a global, cross-tenant lookup with no join/filter on `repository`, `stack`, or the `repository_owner` used for authentication [4](#0-3) . Its `params` schema does not even require a `repository` field, unlike every other handler (e.g. `PushHandler`/`PullRequest` handlers), which all resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` and scope subsequent operations to that repository's stacks (see e.g. `OpenedHandler#repository`, `ClosedHandler#repository`) [5](#0-4) . `StatusHandler` never calls the base `Handler#stacks`/`repository_name` helpers that would provide this scoping [6](#0-5) .
- `create_status_from_github!` writes a `Status` row unconditionally tied to the commit's real `stack_id` (not anything derived from the forged payload's repository): `statuses.replicate_from_github!(stack_id, github_status)` [7](#0-6) . `Status#replicate_from_github!` persists `state`/`description`/`target_url`/`context` directly from attacker-controlled params [8](#0-7) .

**Exploit flow:** Attacker sends `POST /webhooks` with header `X-Github-Event: status`, body `{"repository": {"owner": {"login": "<attacker-controlled-or-any-no-secret-org>"}}, "sha": "<victim commit sha>", "state": "success", ...}`. If any org configured on the Shipit instance has no `webhook_secret` (attacker's own onboarded org, or any org an operator left unconfigured, which the docs present as a normal/optional setup), signature verification passes trivially. `StatusHandler` then finds and mutates the `Status` for whatever commit(s) in the entire database share that SHA — which can belong to a completely different stack/org's production environment.
- The victim commit's SHA is not secret: it is visible on GitHub commit pages, PRs, CI checks, or Shipit's own UI/API for that stack.

**Why guards fail:** `force_github_authentication`/`User#authorized?`/`require_permission!`/`stacks` scope do not apply to `WebhooksController`, which is unauthenticated by design (it authenticates via HMAC signature only). The `ExplicitParameters` schema on `StatusHandler` enforces types but adds no repository binding. No model validation on `Status`/`Commit` restricts creation by originating organization.

**Amplification via production environment:** Once a forged `success` status lands on the targeted commit, `Status#schedule_continuous_delivery` fires `Commit#schedule_continuous_delivery`, which — if the victim stack has `continuous_deployment?` enabled — enqueues `ContinuousDeliveryJob` [9](#0-8) [10](#0-9) . It also calls `stack.schedule_merges` when the new status is `pending` or `success`, enqueuing `ProcessMergeRequestsJob`, which merges pending merge requests once `all_status_checks_passed?` [11](#0-10) [12](#0-11) . On a stack configured as the production environment, this can trigger an unauthorized deploy or an unauthorized merge of attacker-influenced pull requests.

### Impact Explanation
An unprivileged attacker can forge a CI status for any commit in the Shipit instance's database, regardless of which repository or organization actually owns it, as long as they can authenticate as any single org configured with no `webhook_secret`. On a production stack with continuous deployment or auto-merge enabled, this can cause an unauthorized deploy or merge — satisfying "a payload for one repository mutating another's stack, commit... or an unauthorized deploy, rollback or merge" (Critical). The action is repeatable against any commit whose SHA the attacker knows, across every stack/tenant hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: (1) at least one organization configured on the Shipit instance with no `webhook_secret` (explicitly documented as optional), which the attacker can authenticate as by naming it in the payload; (2) knowledge of a target commit SHA (public via GitHub); (3) the target stack has `continuous_deployment` or merge automation enabled for full deploy/merge impact (a bare `Status` row is written regardless). Attacker cost is a single crafted unauthenticated HTTP POST; no secrets or session are required. Highly feasible and trivially repeatable.

### Recommendation
Scope `StatusHandler` (and any handler relying on cross-cutting lookups) to the authenticated repository: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name`, and restrict `Commit.where(sha:)` to `commits joins(stack: :repository).where(repositories: { id: repository.id })` (or equivalent), mirroring the pattern already used by `PullRequest::*Handler` classes. Additionally, do not allow silent bypass of signature verification for organizations without a configured `webhook_secret`; require an explicit secret for any org whose webhooks can mutate stack state, or reject processing when `webhook_secret` is absent.

require 'test_helper'

module Shipit
  class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
    test "forged status from a no-secret org mutates an unrelated production stack's commit" do
      # Binding under test: authenticated_organization == commit.stack.repository.owner
      victim_stack = shipit_stacks(:shipit) # assume configured with environment: 'production', continuous_deployment: true
      victim_stack.update!(environment: 'production', continuous_deployment: true)
      victim_commit = victim_stack.commits.last

      attacker_org_login = 'attacker-org-with-no-secret'
      Shipit.stubs(:github).with(organization: attacker_org_login).returns(
        Shipit::GitHubApp.new(attacker_org_login, {}) # no webhook_secret configured
      )

      forged_payload = {
        'repository' => { 'owner' => { 'login' => attacker_org_login } },
        'sha' => victim_commit.sha,
        'state' => 'success',
        'context' => 'ci/forged'
      }

      assert_difference -> { victim_commit.statuses.count }, 1 do
        assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
          post_webhook('status', forged_payload) # POST /webhooks with X-Github-Event: status
        end
      end

      # Equality check after: attacker authenticated as attacker_org_login,
      # but wrote state onto victim_stack (different repository/org) -> binding broken.
      assert_equal 'success', victim_commit.reload.status.state
      refute_equal attacker_org_login, victim_stack.repository.owner
    end

    private

    def post_webhook(event, payload)
      post shipit.webhooks_path, params: payload.to_json,
           headers: { 'X-Github-Event' => event, 'Content-Type' => 'application/json' }
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
