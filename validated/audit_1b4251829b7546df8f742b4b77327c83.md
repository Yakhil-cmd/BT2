### Title
Missing minimum-value validation on `FriendGroup::inheritance_delay` allows a self-chosen "friend" to seize account control with zero warning delay - ([File: substrate/frame/recovery/src/lib.rs])

### Summary
`pallet-recovery`'s `bound_friend_groups` (called by the permissionless, signed `set_friend_groups` extrinsic) validates `cancel_delay != 0` but never validates `inheritance_delay`, letting an account owner configure a friend-group with `inheritance_delay = 0`. Once configured, a designated "friend" (an ordinary, unprivileged account chosen by the owner — not a validator/root/governance actor) can `initiate_attempt` and, if `friends_needed == 1`, immediately `finish_attempt` in the very same block, taking over the account before the owner has any chance to notice or call `cancel_attempt`/`slash_attempt`.

### Finding Description
`FriendGroup::inheritance_delay` is documented as "Minimum time that a recovery attempt must stay active before it can be finished" [1](#0-0) , and the pallet's own README frames this delay as the core security guarantee of the whole design ("even the most skilled attacker will need to wait this long before they can access your account") [2](#0-1) .

The sanity-check routine that all friend groups pass through when set via the signed `set_friend_groups` extrinsic enforces several invariants (friends non-empty, friends sorted/unique, `friends_needed > 0`, `cancel_delay != 0`) but has no lower bound on `inheritance_delay`: [3](#0-2) 

`finish_attempt` computes `inheritable_at = attempt.init_block.checked_add(&friend_group.inheritance_delay)` and only requires `now >= inheritable_at`: [4](#0-3) 

With `inheritance_delay = 0`, `inheritable_at == init_block`, so the check passes as soon as the attempt is created (`now == init_block` at that point) — the "minimum wait time" the pallet is built around is entirely bypassed.

`initiate_attempt` auto-approves the initiating friend as the first vote [5](#0-4) , so if `friends_needed == 1` (a configuration explicitly allowed and exercised in the pallet's own tests, e.g. `threshold: 1` / `friends_needed: 1` cases) the approval threshold is reached in the same call that creates the attempt, and `finish_attempt` can then be dispatched successfully in the same block.

This is structurally identical to the reported Cooler bug: a user-supplied "duration" parameter is never checked against zero, so an ordinary counter-party (a friend the owner explicitly nominated — analogous to Cooler's lender, not a privileged role) can immediately trigger the state transition that the duration was supposed to delay, causing loss for the party who mis-configured the value.

### Impact Explanation
If an account owner misconfigures (or is socially engineered into configuring) `inheritance_delay: 0`, any single nominated friend with `friends_needed == 1` can seize full control of the account (become `Inheritor`) in the same block the attempt starts, with no time window for the true owner to react, cancel, or slash the attempt. Once `Inheritor` is set, the attacker can call `control_inherited_account` to act as the lost account, e.g. transfer funds, defeating the entire "give yourself time to react" security model documented in the pallet's README. This is a total, irreversible loss of account control for the misconfiguring user — the recovery pallet's core safety property is nullified by a single unchecked zero value.

### Likelihood Explanation
Requires the account owner to set `inheritance_delay = 0` (a configuration mistake or social-engineering target, e.g. mirroring a `duration = 0` typo in Cooler) and to have selected a friend group with `friends_needed == 1` (this pallet's own benchmarks/tests use `friends_needed: 1` as a normal, supported configuration, so it's not an edge case). No governance, root, or validator privilege is needed by the "friend" who completes the attack — matching the audit scope's "no privileged role" requirement. Likelihood is Medium: it depends on user misconfiguration (as in the original Cooler finding), but the configuration surface (`set_friend_groups`) is fully user-controlled and unguarded for this specific field, unlike the analogous `cancel_delay` field which the pallet authors clearly intended to floor at 1 block.

### Recommendation
In `bound_friend_groups`, add a validation analogous to the existing `cancel_delay` check:
```rust
ensure!(!friend_group.inheritance_delay.is_zero(), Error::<T>::NoInheritanceDelay);
```
(or enforce a configurable `MinInheritanceDelay` via `Config`), returning a new `Error::<T>::NoInheritanceDelay`, consistent with how `NoCancelDelay` already guards the sibling field.

### Proof of Concept
Reachable through `pallet_recovery`'s own test harness (`substrate/frame/recovery/src/tests.rs`), no mocked authority/proof required:

1. Alice (victim) calls `Recovery::set_friend_groups(signed(ALICE), vec![FriendGroupOf::<T> { friends: friends([BOB]), friends_needed: 1, inheritor: BOB, inheritance_delay: 0, inheritance_priority: 0, cancel_delay: 1 }])`. This currently succeeds — `bound_friend_groups` only fails on `cancel_delay == 0` (`Error::NoCancelDelay`), never on `inheritance_delay == 0` [6](#0-5) .
2. Bob (unprivileged friend) calls `Recovery::initiate_attempt(signed(BOB), ALICE, 0)`. Because `friends_needed == 1`, Bob's auto-approval as initiator satisfies the threshold immediately [5](#0-4) .
3. In the same block, Bob calls `Recovery::finish_attempt(signed(BOB), ALICE, 0)`. `inheritable_at = init_block + 0 == init_block == now`, so `ensure!(now >= inheritable_at, Error::NotYetInheritable)` passes [4](#0-3) , and `Inheritor::<T>::insert(&lost, (priority, &inheritor, ticket))` sets Bob as inheritor of Alice's account.
4. Bob then calls `Recovery::control_inherited_account(signed(BOB), ALICE, ...)` to act on Alice's behalf.

	/// Sanity check the friend groups and bound them into a bounded vector.
	pub fn bound_friend_groups(
		lost: &T::AccountId,
		mut friend_groups: Vec<FriendGroupOf<T>>,
	) -> Result<FriendGroupsOf<T>, Error<T>> {
		for friend_group in &mut friend_groups {
			ensure!(!friend_group.friends.is_empty(), Error::<T>::NoFriends);
			// cannot contain the lost account itself
			ensure!(!friend_group.friends.contains(&lost), Error::<T>::LostAccountInFriendGroup);
			ensure!(
				friend_group.friends.windows(2).all(|w| w[0] < w[1]),
				Error::<T>::FriendsNotSortedOrUnique
			);
			ensure!(
				friend_group.friends_needed as usize <= friend_group.friends.len(),
				Error::<T>::TooManyFriendsNeeded
			);
			ensure!(friend_group.friends_needed > 0, Error::<T>::NoFriendsNeeded);
			// prevent mempool frontrunning by requiring at least 1 block
			ensure!(!friend_group.cancel_delay.is_zero(), Error::<T>::NoCancelDelay);
		}
