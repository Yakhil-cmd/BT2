### Title
RAY-scale market value multiplication overflows before index cap, permanently freezing the market - (File: `common/src/rates/scaling.rs`)

### Summary

Interest accrual computes aggregate debt and supply as `scaled_shares * index` in an `i128`-backed `Ray`. For sufficiently large markets, this product can exceed `i128::MAX` before the configured borrow-index ceiling is reached, causing `MathOverflow` and reverting accrual. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

`Controller::update_indexes(caller, assets)` is reachable by an authorized but otherwise unprivileged caller and forwards the selected `HubAssetKey` list to the pool. [4](#0-3)  The pool’s `update_indexes` entrypoint calls `ops::market::accrue`, which loads each market and invokes `interest::global_sync`. [5](#0-4) [6](#0-5) 

During accrual, utilization materializes both `total_borrowed = borrowed * borrow_index` and `total_supplied = supplied * supply_index`. [1](#0-0)  Both totals use `scaled_to_original`, which delegates to `Ray::mul`; although the intermediate uses widened `I256`, conversion back to `i128` fails when the resulting RAY-denominated market value exceeds `i128::MAX`. [2](#0-1) [7](#0-6) 

The borrow index is nominally protected by `MAX_BORROW_INDEX_RAY`, but `update_borrow_index` multiplies `old_index * interest_factor` before applying that cap. [8](#0-7) [9](#0-8)  More importantly, the aggregate `borrowed * borrow_index` calculation can overflow before index growth ever reaches the index ceiling. [10](#0-9) 

Every ordinary pool mutation also accrues first: `load_leg` calls `synced_market`, which calls `global_sync` before the operation-specific logic. [11](#0-10)  Consequently, once the market reaches the overflowing state, subsequent `supply`, `borrow`, `withdraw`, `repay`, liquidation-related settlement, and explicit `update_indexes` calls all revert on the same multiplication. [12](#0-11) [13](#0-12) [14](#0-13) 

### Impact Explanation

This is a permanent freezing of user funds and market operation failure. Suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot process unhealthy positions because each path recomputes the overflowing aggregate from the last committed state. [11](#0-10) [15](#0-14) 

Because the accrual panics before `cache.commit()`, `last_timestamp` is not advanced; later transactions reload the same last committed state and hit the same overflow again. [16](#0-15) [17](#0-16)  The regression test demonstrates the terminal state by asserting `MATH_OVERFLOW` for index updates, withdrawal, and repayment. [18](#0-17) 

### Likelihood Explanation

A single attacker can create the state by supplying both the large borrowed asset and sufficient collateral, borrowing most of the market, and then invoking `update_indexes` as ledger time advances. [19](#0-18) [4](#0-3)  The existing test uses `1e9` units of an 18-decimal asset supplied, `98%` borrowed, and a collateral position in another market before repeatedly advancing accrual. [20](#0-19) 

The precondition requires a market configuration whose caps, liquidity, collateral value, and rate model permit scaled market totals near the `i128` boundary. This is capital- and configuration-dependent, but it does not require privileged execution after the market exists, and the resulting freeze affects all users of that market. [21](#0-20) 

### Recommendation

Do not materialize `scaled_shares * index` as an `i128` `Ray` when deriving accrual utilization or interest totals. Keep aggregate debt and supply in widened `I256` internally, or calculate the utilization ratio without first materializing both absolute RAY values. [1](#0-0) [22](#0-21) 

Apply `MAX_BORROW_INDEX_RAY` through a pre-multiplication bound such as `interest_factor <= MAX_BORROW_INDEX_RAY / old_index`, rather than multiplying first and clamping afterward. [8](#0-7)  If absolute aggregate values cannot be represented, accrual should saturate the rate input or clamp the index while still committing `last_timestamp`, rather than reverting before state commitment. [16](#0-15) 

### Proof of Concept

The repository contains a direct reproduction in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`: it creates an 18-decimal market, supplies `BILLION * 10^18` base units, supplies collateral, and borrows `principal * 98 / 100`. [23](#0-22) 

On a live deployment, the analogous sequence is:

1. Call `supply(caller, 0, spoke_id, [(HubAssetKey { hub_id, asset: BIG18 }, 1_000_000_000_000_000_000_000_000_000), (HubAssetKey { hub_id, asset: COL }, sufficient_collateral)])`.
2. Call `borrow(caller, account_id, [(HubAssetKey { hub_id, asset: BIG18 }, 980_000_000_000_000_000_000_000_000)], Some(caller))`.
3. Advance ledger time and call `update_indexes(caller, [HubAssetKey { hub_id, asset: BIG18 }])` until `borrowed * borrow_index` exceeds `i128::MAX`. [4](#0-3) [2](#0-1) 
4. The call returns `GenericError::MathOverflow`; later `withdraw` and `repay` calls revert identically because they execute accrual first. [11](#0-10) [18](#0-17)

    t.supply_raw(BOB, "BIG18", principal);

    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
