### Title
Webhook signature verification is skipped entirely for any configured GitHub organization with a blank `webhook_secret`, allowing unauthenticated forgery of `membership`/`push`/`pull_request` events - ([File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which HMAC secret) to verify a webhook against using an **attacker-controlled field from the unverified JSON payload** (`repository.owner.login` / `organization.login`), and `GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever that organization's `webhook_secret` is blank. This breaks the intended binding of "GitHub-authenticated organization" versus "organization whose webhook payload is trusted and acted upon": the org identity is taken from the payload itself, and if that org happens to have no secret configured, the signature check never actually runs.

### Finding Description
The controller derives the org used for verification purely from the request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the corresponding app config by that untrusted key: [3](#0-2) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` when the resolved organization's `webhook_secret` is blank: [4](#0-3) 

This isn't a hypothetical: the shipped example configs explicitly show `webhook_secret: # nil` as a valid/likely-copied configuration for one org in a multi-org setup: [5](#0-4) [6](#0-5) 

If any org in `Shipit.github` config has a blank `webhook_secret` (the default/unset state), an anonymous, unauthenticated attacker can `POST /webhooks` with `X-Github-Event` set to any handled event and `repository.owner.login` (or `organization.login`) set to that org's name. `verify_webhook_signature` will return `true` with no comparison against the `X-Hub-Signature` header at all, and the payload is dispatched to the real handlers: [7](#0-6) [8](#0-7) 

The `membership` event handler is reachable this way and creates/mutates `Team`, `User`, and `Membership` records directly from attacker-supplied JSON, as demonstrated by: [9](#0-8) 

Those `Team`/`Membership` records are exactly what gates authorization in the app: [10](#0-9) [11](#0-10) [12](#0-11) 

So an attacker (any GitHub user who can complete Shipit's normal OAuth login, which by design does not require any pre-existing authorization) can forge a `membership` webhook to add their own already-existing `Shipit::User` row to a `Team` matching one of `Shipit.github_teams`' handles, flipping `current_user.authorized?` to `true` and gaining full access to the application - all Stacks, deploys, rollbacks, and settings - despite never actually being a member of the real GitHub team/org.

### Impact Explanation
This is an unauthenticated-attacker escalation into `Shipit.github_teams` authorization, which is explicitly listed as an accepted High-severity impact: an attacker with no privileges bypasses the organization-membership gate entirely and becomes a fully authorized Shipit user, able to trigger deploys, rollbacks, lock/unlock stacks, and manage repositories. Depending on other configured orgs, the same signature bypass also lets the attacker inject arbitrary `push`/`pull_request`/`status` events, influencing commit deployability and merge-queue state for that org's stacks.

### Likelihood Explanation
Likelihood is directly tied to deployment configuration: it requires at least one configured GitHub org/app entry with a blank `webhook_secret`. This is a realistic, easy-to-hit misconfiguration because `webhook_secret` is optional/nil by default in every shipped example config in this repo, and nothing in `lib/shipit/github_app.rb` or the webhook controller warns or rejects a blank secret - the code path exists specifically to silently "allow" unsigned webhooks for such orgs rather than to reject requests. No credentials, session, API token, or repository write access are needed by the attacker - only knowledge of the target org's name (which is public) and the ability to log in once via normal (unauthorized) OAuth to have a `User` row to elevate.

### Recommendation
- Never treat a blank/missing `webhook_secret` as "verification not required." Reject (422) any webhook for an organization that has no `webhook_secret` configured, or require `webhook_secret` presence at boot/config-validation time.
- Do not select the verification secret (and thus the trust boundary) using unauthenticated payload fields (`repository.owner.login` / `organization.login`). If multiple orgs/apps are configured, verify the signature against all configured secrets, or bind the webhook endpoint to a specific org via the URL/route rather than trusting the JSON body to declare its own signer.
- Fail closed: `verify_webhook_signature` should return `false` (not `true`) whenever a secret cannot be established.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `OrgA` (has `webhook_secret` set) and `OrgB` (`webhook_secret:` left blank), matching the pattern in `config/secrets.development.shopify.yml`.
2. As an unauthenticated attacker (no ApiClient token, no session, no webhook secret), send:
   ```
   POST /webhooks
   X-Github-Event: membership
   Content-Type: application/json

   {
     "action": "added",
     "organization": {"login": "OrgB"},
     "team": {"id": 48, "name": "Admins", "slug": "admins", "url": "https://example.com"},
     "member": {"login": "attacker-github-login"}
   }
   ```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of (or absent) `X-Hub-Signature` header.
4. The `membership` handler processes the forged event and creates/updates the `Team`/`Membership` records exactly as shown in `test/controllers/webhooks_controller_test.rb` lines 129-173, without any real GitHub-signed authenticity.
5. If `admins` matches a handle in `Shipit.github_teams`, the attacker's existing `Shipit::User` (created by simply logging in through the normal, unauthorized OAuth flow once) now satisfies `current_user.authorized?`, granting full application access.

Note: I was not able to locate the concrete source file for `Handlers::MembershipHandler` in the indexed content (only referenced via `app/models/shipit/webhooks.rb` and covered by `test/controllers/webhooks_controller_test.rb`); its exact field-handling logic could not be fully verified from the available index and would benefit from direct inspection in a full checkout.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
