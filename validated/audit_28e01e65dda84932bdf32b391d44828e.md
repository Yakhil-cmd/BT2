### Title
PR label named `ENVIRONMENT` overwrites the review stack's real `ENVIRONMENT` variable, redirecting deploy/rollback capistrano stage - (File: app/models/shipit/review_stack.rb)

### Summary
`Shipit::ReviewStack#env` merges pull-request labels (upcased, value `"true"`) on top of `Shipit::Stack#env`, with no exclusion for reserved keys like `ENVIRONMENT`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `LAST_DEPLOYED_SHA`, or `BRANCH`. An attacker who can apply a label to their own pull request on a repository that has an active review stack can set `env['ENVIRONMENT']` to `"true"` instead of the stack's real `environment` (e.g. `pr123`), which then flows unchanged through `TaskCommands#env`/`DeployCommands#env` into `Command#interpolate_environment_variables`/`Command#unbundled_env`, causing any deploy step that references `$ENVIRONMENT` to run against the wrong capistrano stage.

### Finding Description
The binding that should hold is: `env['ENVIRONMENT'] == stack.environment` for every review stack, where `stack.environment` is the value assigned at provisioning time by `ReviewStackAdapter#stack_attributes` (`"pr#{number}"`).

`Shipit::Stack#env` correctly establishes this: [1](#0-0) 

`Shipit::ReviewStack#env` breaks it by merging attacker-controlled label names on top, with no key exclusion: [2](#0-1) 

The labels stored on `pull_request.labels` come directly from the GitHub webhook payload, captured verbatim without filtering out names that collide with the reserved env keys: [3](#0-2) [4](#0-3) 

This merged env is passed unmodified from `TaskCommands#env`: [5](#0-4) 

into `Command`, where `interpolate_environment_variables` substitutes `$ENVIRONMENT` literally with whatever value is in the hash before the command line is passed to `PTY.spawn`: [6](#0-5) [7](#0-6) 

An existing repo test already documents that labels overwrite same-name keys case-insensitively (uppercased), confirming the merge semantics: [8](#0-7) 

Exploit flow: attacker opens a PR on their own repository that has GitHub App/webhook integration configured with Shipit review stacks enabled, and applies (or asks a collaborator to apply, per the stated threat model that they "can label their own PR") a label literally named `ENVIRONMENT` (case-insensitive, since it's `.upcase`'d). GitHub emits a real, correctly-signed `pull_request` `labeled` webhook (no forgery needed — it's a genuine event from a repo the attacker owns/controls), `LabelCapturingHandler` stores the label on `PullRequest#labels`, and the next deploy/rollback/task computes `env['ENVIRONMENT'] => 'true'`. Any deploy step template using `$ENVIRONMENT` (a documented/expected pattern per `Stack#env` providing it for exactly this purpose) now runs against stage `true` instead of `pr123`.

Existing guards do not prevent this: `verify_signature`/webhook signature checks only validate that the payload came from the attacker's own registered repository — they do nothing to sanitize env key collisions. `EnvironmentVariables#permit`'s whitelist (`variable_definitions`) is used elsewhere for task input filtering, but review-stack deploy/rollback commands read `@stack.env` directly and merge it in without going through `permit`. No model validation on `PullRequest#labels` restricts label names to avoid reserved words.

### Impact Explanation
A single label application by the PR author causes every subsequent deploy or rollback of that review stack to interpolate a bogus/attacker-chosen `ENVIRONMENT` value into commands executed via `PTY.spawn` on the deploy host, for any deploy-spec step written as `cap $ENVIRONMENT deploy` (or similar). This is an unauthorized-deploy/rollback-target class issue: capistrano is invoked against a stage the review-stack provisioning process never authorized, potentially a stage belonging to another tenant/stack if a stage named `true` or matching another repo's environment exists. This matches the "unauthorized deploy, rollback" Critical impact category. The attack is repeatable on any repository/PR the attacker owns with review stacks enabled, and is not limited to a one-time exploitation — every deploy while the label remains applied is affected.

### Likelihood Explanation
Preconditions: the target repository must have GitHub App/webhooks configured and review stacks enabled, an active (non-archived) review stack must exist for a PR, and the deploy spec must contain a step interpolating `$ENVIRONMENT` (a common/documented pattern, since `Stack#env` exposes it for exactly this purpose). The attacker only needs the ability to label their own PR — no Shipit credentials, GitHub App keys, or webhook secrets are required, since the webhook event is genuine and correctly signed. This is low-cost and trivially repeatable.

### Recommendation
In `Shipit::ReviewStack#env` (app/models/shipit/review_stack.rb), exclude the reserved/core keys defined in `Stack#env` from being overridden by label-derived entries — e.g. compute the label hash first and then `.reverse_merge` under `super`, or explicitly filter out `%w[ENVIRONMENT GITHUB_REPO_OWNER GITHUB_REPO_NAME DEPLOY_URL LAST_DEPLOYED_SHA BRANCH]` from the label-derived hash before merging.

### Proof of Concept
In `test/models/shipit/review_stack_test.rb`, add:
```ruby
test "#env does not allow a PR label to override the reserved ENVIRONMENT key" do
  stack = shipit_stacks(:review_stack)
  real_environment = stack.environment
  stack.pull_request.labels = ["environment"]

  assert_equal real_environment, stack.env["ENVIRONMENT"]
end
```
And in `test/unit/command_test.rb`:
```ruby
test "interpolate_environment_variables does not let attacker-labeled ENVIRONMENT redirect the cap stage" do
  command = Command.new("cap $ENVIRONMENT deploy", chdir: Dir.tmpdir, env: { "ENVIRONMENT" => "true" })
  refute_equal "cap true deploy", command.interpolated_arguments.join(' ')
end
```
Currently, both assertions fail: `stack.env["ENVIRONMENT"]` becomes `"true"` and the interpolated command becomes `cap true deploy`, confirming the vulnerability.
