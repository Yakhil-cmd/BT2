### Title
Webhook authenticity is bound to attacker-supplied `repository.owner.login`, not to the `repository.full_name` the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate a webhook against using `repository.owner.login` (or `organization.login`), which is a field taken straight from the untrusted JSON body being verified. All downstream webhook handlers, however, resolve the `Repository`/`Stack` they act on using a *different* field of the same body: `repository.full_name`. Nothing binds the "org that authenticated the request" to the "repository the request actually writes to." If the organization selected for authentication has no `webhook_secret` configured (a state explicitly documented as optional and present by default in single-org configurations), signature verification is bypassed unconditionally, and the attacker's forged `repository.full_name` is used to mutate state (commit statuses, review stacks, sync jobs) for a completely different, properly-configured repository/org.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config via: [1](#0-0) 
where `repository_owner` is read directly out of the unauthenticated request body: [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true`, with no signature/header check at all, if that particular org's `webhook_secret` is blank: [3](#0-2) 

This is not a misconfiguration outside the documented flow: `docs/setup.md` explicitly labels the webhook secret as "(optional)", and both `test/dummy/config/secrets.yml` and `config/secrets.development.shopify.yml` ship with `webhook_secret: # nil` by default: [4](#0-3) 

Meanwhile, every webhook handler resolves the target `Stack`/`Repository` using `repository.full_name`, a field completely independent of the `repository.owner.login` used for authentication: [5](#0-4) 

In single-org (`github_default_organization.nil?`) mode - the base configuration shown throughout `docs/setup.md` - `Shipit.github(organization:)` ignores the `organization` argument entirely and always returns the one configured `GitHubApp`: [6](#0-5) 

So the "authenticated organization" is, by construction, decoupled from the "repository actually written." Any attacker who can reach `/webhooks` unauthenticated (no session, no `ApiClient` token, no GitHub App key required) can:
1. Set `repository.owner.login` (or, in multi-org setups, pick any configured org whose `webhook_secret` happens to be unset) to satisfy `verify_webhook_signature`.
2. Set `repository.full_name` to the `full_name` of any other tracked repository/stack in the same Shipit instance, and forge arbitrary event bodies (`status`, `push`, `pull_request`, `check_suite`) for it.

### Impact Explanation
The most severe consequence is via the `status` handler: [7](#0-6) 
A forged `state: "success"` status for an arbitrary commit SHA is written via `Commit#create_status_from_github!`, and is consumed by `MergeRequest#all_status_checks_passed?` / `any_status_checks_failed?` through `StatusChecker`: [8](#0-7) 
`ProcessMergeRequestsJob` will then merge a pull request whose real CI never passed: [9](#0-8) 
This is an unauthorized merge into the target repository - matching the Critical bucket ("unauthorized deploy, rollback or merge"). The same mechanism also permits fake `push` webhooks to trigger `stack.sync_github`, and fake `pull_request` events to create/archive review stacks for arbitrary tracked stacks.

### Likelihood Explanation
No credentials of any kind are required to reach `/webhooks`; it is explicitly public and unauthenticated by design (it is the GitHub webhook receiver). The only precondition is that at least one configured GitHub organization in the Shipit instance has no `webhook_secret` set - which is the documented "optional" default, and the default shipped in this engine's own test/dummy secrets files. In that state, exploitation requires zero secret knowledge: the attacker only needs to know the target repository's `full_name`, which is public information.

### Recommendation
Bind authentication to the data actually being acted upon: after selecting the GitHub App config, verify that the authenticated organization actually owns the `repository.full_name` referenced in the payload (or resolve the target `Repository`/`Stack` only from the same org identity that produced a valid signature). Additionally, treat a missing `webhook_secret` as "reject all webhooks for this org" rather than "accept unconditionally," or require `webhook_secret` to be mandatory instead of optional.

### Proof of Concept
Assume a Shipit instance tracks `orgA/production-app` (properly configured, real `webhook_secret` unknown to the attacker) and also has some org `orgB` configured with `webhook_secret` unset (per documented-optional configuration, or the single-org default).

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "sha": "<victim commit sha in orgA/production-app>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "orgB" },
    "full_name": "orgA/production-app"
  }
}
```
- `WebhooksController#verify_signature` reads `repository_owner` = `"orgB"`, resolves the `orgB` `GitHubApp`, whose `webhook_secret` is blank, and `verify_webhook_signature` returns `true` unconditionally (no `X-Hub-Signature` needed).
- `StatusHandler#process` resolves the target commit purely by SHA, unrelated to `orgB`, and records a forged `success` status.
- If this SHA belongs to a pending merge request in `orgA/production-app`, `ProcessMergeRequestsJob` will merge it once all (forged) required statuses report success.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
