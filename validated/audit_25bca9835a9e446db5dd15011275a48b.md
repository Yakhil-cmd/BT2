### Title
Stale `last-update` timestamp during zero-debt periods causes new borrowers to be retroactively overcharged interest that benefits existing depositors/treasury - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent code in all other `v0-vault-*.clar` files)

### Summary
Every Zest vault (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`) shares the same debt-accrual pattern found in the referenced Ion Protocol report. `accrue` only advances the shared `last-update` variable when the computed `index`/`lindex` actually change. When `total-debt` is `0`, `utilization` is `0`, the borrow rate resolves to `0`, and both `next-index` and `next-liquidity-index` equal the current `index`/`lindex`, so `last-update` is never bumped for as long as the pool has no debt. When a new borrower later opens a position, the very next `accrue()` call (triggered by any unrelated depositor/borrower/redeemer) computes `time-delta` back to the stale `last-update`, silently baking the entire zero-debt idle period into the accrual applied to the pool's current `principal-scaled`. This inflates the debt of whichever borrower(s) hold `principal-scaled` at that moment, and the extra "interest" is booked into `assets`/`total-assets`, increasing the value backing existing `zft` shares (and minting extra treasury LP via `fee-reserve`).

### Finding Description
`next-index` and `next-liquidity-index` compute a multiplier from `interest-rate()`/`calc-liquidity-rate` and the elapsed `time-delta = stacks-block-time - last-update`: [1](#0-0) 

`utilization` and `interest-rate` are driven by `total-debt`; when debt is `0`, `calc-utilization` returns `0`, so at the standard rate-curve origin point the resolved rate is `0`: [2](#0-1) [3](#0-2) 

`accrue()` only writes `last-update` when `index` or `lindex` actually changed: [4](#0-3) 

Because at zero utilization the rate (and therefore the multiplier) is `0`/unity, `next == idx` and `nliq == lidx`, so the final `(if (or ...) (var-set last-update stacks-block-time) false)` branch is skipped, leaving `last-update` frozen indefinitely while the vault is debt-free — exactly mirroring the reported Ion Protocol `_calculateRewardAndDebtDistribution`/`timestampIncrease` bug.

The devs were aware of an analogous staleness problem for the *paused* state and fixed it there by forcing `last-update` forward on unpause, but the same fix was not applied to the zero-debt case: [5](#0-4) 

Concrete exploitable path:
1. User A fully repays all outstanding debt via `system-repay`, driving `principal-scaled`/`total-debt` to `0` (capped-amount = debt on full repay): [6](#0-5) 
2. The vault sits debt-free for an extended period (any number of `deposit`/`redeem` calls keep calling `accrue()`, which is a no-op with respect to `last-update` since `next==idx`/`nliq==lidx` at 0 utilization).
3. Victim (User B) opens a fresh debt position via `system-borrow`. The internal `accrue()` call still doesn't move `last-update`, so the borrow itself looks clean: [7](#0-6) 
4. Any later, unrelated interaction by a third party (User C depositing, redeeming, or repaying) calls `accrue()`. `time-delta` is now computed from the stale `last-update` set at step 1, spanning the entire zero-debt idle period plus the time since User B's borrow. This full duration's interest multiplier is applied to the pool's current `principal-scaled` (User B's debt), inflating `debt-delta`, which increases `assets`/`total-assets-preview` (benefiting all `zft` holders) and mints extra treasury LP proportional to `fee-reserve`.

### Impact Explanation
User B (victim borrower) is charged interest for a period during which no debt existed at all — interest that legitimately should never have accrued. This surplus is not lost; it flows directly into `assets` (backing every outstanding `zft` share) and into treasury LP minted to `.dao-treasury`, meaning existing depositors and the treasury gain at the direct expense of the new borrower. This is theft of borrower funds transferred to other unprivileged principals (LPs/treasury) via a shared, improperly-maintained accrual timestamp — qualifying as Critical (direct theft of user funds in motion) since the borrower's excess repayment obligation is a real economic loss transferred to other parties, not merely unclaimed yield.

### Likelihood Explanation
Zero-debt periods are a completely normal, frequent occurrence for any vault (e.g., right after `initialize`, after a wave of full repayments, or in low-utilization assets). No privileged action or malicious intent is required to trigger the staleness — it happens automatically any time `utilization()` hits `0` for a non-trivial period, which is a routine operating condition, making this highly likely to occur in production across all six vaults that share this identical logic.

### Recommendation
In `accrue()` (and equivalently in `next-index`/`next-liquidity-index`), always advance `last-update` to `stacks-block-time` whenever accrual is not paused, regardless of whether `index`/`lindex` changed value, e.g.:
```clar
(if (not (get accrue states))
    (var-set last-update stacks-block-time)
    false)
```
placed unconditionally instead of gating it on `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))`. This ensures no debt-free interval is ever silently carried forward and applied to debt created after that interval, closing the gap in the same way the existing pause/unpause handling already does.

### Proof of Concept
1. Deploy/initialize `v0-vault-usdc` with a rate curve that returns `0` at `0%` utilization (the typical/default configuration).
2. Have all existing borrowers fully repay via `system-repay` so `principal-scaled` becomes `0` (`total-debt = 0`). Confirm via `get-last-update` that `last-update` stops advancing across subsequent `deposit`/`redeem` calls while debt stays `0`.
3. Advance the chain by a large time delta (e.g., 30 days) with the vault debt-free.
4. Victim calls `system-borrow` for some amount; observe `last-update` is still the old, stale value from step 2 (`get-last-update` unchanged).
5. Any third party calls `deposit`/`redeem`/`system-repay` (any function invoking `accrue`). Observe via `get-debt`/`get-index` that the victim's debt has jumped by an amount corresponding to ~30 days of interest despite only holding the position for a fraction of that time, and that `get-total-assets`/`total-supply` for `zft` increased correspondingly, showing the surplus flowed to existing LP/treasury holders at the victim's expense.

(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
                (var-set lindex nliq)
                false)
            (if (> treasury-lp u0)
                (try! (ft-mint? zft treasury-lp .dao-treasury))
                false)
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))

(define-public (system-repay (amount uint))
  (let (
        (states (var-get pause-states))
        (u (try! (accrue)))
        (scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (debt (total-debt))
        (total-borrowed-amount (var-get total-borrowed))
        (capped-amount (if (> amount debt) debt amount))
        (principal-reduction (calc-principal-ratio-reduction capped-amount scaled-principal debt))
        (capped-reduction (if (> principal-reduction scaled-principal) scaled-principal principal-reduction))
        (updated-scaled-principal (- scaled-principal capped-reduction))
        (principal-repaid (mul-div-down capped-amount total-borrowed-amount debt))
        (interest-paid (- capped-amount principal-repaid))
        (total-borrowed-new (if (> total-borrowed-amount principal-repaid) (- total-borrowed-amount principal-repaid) u0)))

    (try! (check-caller-auth))
    (asserts! (not (get repay states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-underlying capped-amount tx-sender))
    (var-set principal-scaled updated-scaled-principal)
    (var-set total-borrowed total-borrowed-new)
    (var-set assets (+ (var-get assets) interest-paid))

    (print {
      action: "system-repay",
      caller: contract-caller,
      data: {
        amount-requested: amount,
        amount-repaid: capped-amount,
        principal-repaid: principal-repaid,
        interest-paid: interest-paid,
        principal-scaled: updated-scaled-principal,
        total-borrowed: total-borrowed-new,
        assets: (var-get assets),
        index: idx
      }
    })

    (ok true)))
