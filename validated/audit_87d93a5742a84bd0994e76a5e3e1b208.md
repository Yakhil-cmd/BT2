### Title
Insufficient metacharacter filtering in `has_only()` allows regex-class injection via leading `^` negation - ([File: formula/evaluation.js])

### Summary
The `has_only(str, sub)` oscript function builds a JavaScript `RegExp` from an attacker/AA-controlled `sub` string by wrapping it in a character class: `new RegExp("^[" + sub + "]*$")`. Its filtering step only rejects `sub` values containing an escaped `\]` or ending in a lone `\`, then blanket-escapes any remaining `]`. It never filters or escapes the `^` metacharacter. Just like CVE-2020-6581 (Nagios NRPE's `nasty_metachars`, which failed to treat `\n` as an escape sequence and thus let a crafted string bypass the intended filter), this filter only guards against one specific bypass shape (closing the bracket early) while leaving another regex metacharacter — `^` as the first character inside `[...]` — completely unfiltered, changing the semantics of the generated pattern from a positive allow-list match to a negated one.

### Finding Description
`has_only` is implemented identically in the validation and evaluation formula engines: [1](#0-0)  The filtering logic is:
```
if (sub.match(/\]/) || sub[sub.length - 1] === '\\')
    return setFatalError(...);
sub = sub.replace(/]/g, '\\]');
var bMatches = new RegExp("^[" + sub + "]*$").test(str);
```
This is analogous to the `has_only` validation-phase counterpart at [2](#0-1) , which only checks types/arity and defers all metacharacter safety to the evaluation-time code above.

Any oscript formula that constructs its allow-list dynamically (e.g., from `trigger.data`, an oracle data feed value, or a value derived from AA state that itself was seeded by a previous, less-trusted trigger) passes attacker-influenced text into `sub`. Because the sanitizer only special-cases `]` and trailing `\`, an attacker who controls (fully or partially) `sub` can prepend `^` to invert the meaning of the character class: `has_only($x, "^" || $allowed_chars)` becomes the regex `^[^<allowed_chars>]*$`, which now matches only strings that contain **none** of the intended allowed characters — the exact opposite of the intended check. This mirrors the NRPE bug class: a filter that recognizes only the literal characters it was told to look for, rather than correctly parsing escape/metacharacter semantics, so a single unblocked metacharacter (`^` here, `\n`/backslash-escaping there) subverts the intended sanitization and the "allowed" check silently returns an unintended boolean.

### Impact Explanation
If an AA uses `has_only` as a security/validation gate — for example, to whitelist a set of characters that a submitted asset ticker, memo field, or address-like string must be restricted to before proceeding to fund transfer, data-feed publication, or a downstream `bounce`-guarded branch — an attacker (unit poster or AA-trigger sender) who can influence the `sub` argument (directly, or indirectly through a chain such as an oracle feed value copied into state and later reused as an allow-list) can flip a "must only contain safe characters" check into "must contain none of the safe characters," causing the AA to accept/execute a branch that was meant to be unreachable. Depending on how the AA gates spending or issuance on this check, this can lead to AA fund loss, unauthorized branch execution, or bypass of a validation gate protecting balances — satisfying the "AA fund loss or freezing" / "concrete unauthorized spending" bar. The severity depends heavily on how a given AA uses the dynamic pattern, which is why this is rated High rather than Critical.

### Likelihood Explanation
Likelihood is moderate: exploitation requires an AA design where the second `has_only` argument is not a hardcoded literal but instead derives, even partially, from trigger data, an oracle feed, or a previous AA response that an attacker can influence. This is a plausible AA pattern (dynamic allow-lists built from configuration stored in state variables that were seeded by external data) but is not universal to all AAs using `has_only`. The vulnerable code path itself is trivially reachable by any unit/trigger sender supplying appropriately formed data to an AA that uses this pattern.

### Recommendation
Harden `has_only`'s sanitization in `formula/evaluation.js` (and correspondingly document the constraint enforced in `formula/validation.js`) to reject or escape `^` when it appears as the first character of `sub` (or disallow it entirely, since a "has-only" allow-list should never need negation), in addition to the existing `]`/trailing-backslash checks. More robustly, avoid building a `RegExp` from unescaped user input altogether — expand `sub` into an explicit set of literal allowed characters (handling only `-` ranges and a small enumerated set of `\d`, `\w`, `\s` shorthand tokens explicitly) rather than passing raw text into a dynamically constructed character class.

### Proof of Concept
```
# oscript formula pattern vulnerable if `sub` is influenced by trigger/oracle data:
has_only(trigger.data.value, "^" || allowed_chars)

# e.g. with allowed_chars = "a-z0-9"
# generated regex: new RegExp("^[^a-z0-9]*$")
# Input "ABC!@#" (which should be REJECTED as containing disallowed chars)
# now returns true because "^" negates the class, matching any string
# containing NONE of a-z0-9 -- the opposite of the intended allow-list check.
