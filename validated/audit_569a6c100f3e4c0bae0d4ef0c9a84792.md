### Title
Cross-organization commit-status forgery via `StatusHandler`'s missing repository binding to the signature-verified organization - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Shipit's multi-tenant GitHub App configuration allows more than one organization to be registered, each with its own `webhook_secret`, via `Shipit.github(organization:)` and `github_app_config` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against using `repository_owner`, computed from the payload's own `repository.owner.login` (falling back to `organization.login`) [2](#0-1) . Once the signature check passes, `StatusHandler#process` writes a commit status using only the `sha` field from the payload — with no check at all that the `sha` belongs to a commit under the same repository/organization that was used to select and validate the signing secret: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` [3](#0-2) .

### Finding Description
The binding that should hold is: **organization that authenticated the webhook == organization whose repository/commit data is written**. In this engine that binding is broken for the `status` event.

- `verify_signature` derives `repository_owner` purely from attacker-controlled JSON fields (`repository.owner.login` or `organization.login`) and looks up the corresponding `GitHubApp`/`webhook_secret` for that organization [4](#0-3) . It only proves that *some* org registered in this Shipit instance produced a body whose HMAC matches — it never ties that org identity to the data the handler subsequently acts on.
- The base `Handler` class does compute a `repository_name` from `payload.dig('repository','full_name')` for use in repository/stack scoping [5](#0-4) , and most handlers (`PushHandler`, `PullRequest::ClosedHandler`, etc.) scope their side effects through `stacks`/`repository`, which is at least self-consistent within the payload.
- `StatusHandler`, however, never references `repository` at all. Its parameter schema only requires `sha`, `state`, and optional descriptive fields [6](#0-5) , and `process` globally queries `Commit.where(sha: params.sha)` across the entire `commits` table, independent of which repository/organization the commit belongs to [3](#0-2) .

Consequently, an operator of *Organization A*, who is legitimately configured in Shipit's multi-org GitHub App credentials (their own `webhook_secret`, distinct from Organization B's), can forge a `status` webhook body: set `repository.owner.login` (or `organization.login`) to `"A"` so `verify_signature` selects and validates against A's own secret — which the attacker legitimately possesses/controls the ability to trigger events for — while setting `sha` to the SHA of a commit that is actually tracked by a stack belonging to a completely different, unrelated `Organization B`. Git commit SHAs are not secrets; they are visible on GitHub, in Shipit's own UI/API (`Commit#sha`), and in `X-Shipit-User`-less public endpoints. Because `StatusHandler` never checks that the SHA belongs to a commit whose repository matches the authenticated organization, the forged status is written onto Organization B's commit.

Before the attacker's request:
- `authenticated_org == B` (`false`, actual authenticator is A) and `written_repo == B` — binding holds trivially because nobody but B can produce a valid signature for B's commits.

After the attacker's forged `status` event, signed with A's secret:
- `authenticated_org == A`, but `written_repo == B`. The equality `authenticated_org == written_repo` is broken.

### Impact Explanation
`Commit#create_status_from_github!` persists a `Status` row for the targeted commit; downstream, Shipit's deploy-gating logic (`ci.require`, `ci.blocking`, `ci.allow_failures` in `shipit.yml`, documented in `README.md`) consumes these `Status` records to decide whether a commit is `deployable?` / whether continuous delivery may proceed. An attacker who can inject a fabricated "success" status for a commit under a stack they do not own and have no write access to can defeat CI gating for that unrelated stack, enabling continuous-delivery/auto-deploy to proceed on a commit that never actually passed CI — an unauthorized deploy precondition being satisfied by forged data. This crosses the organization boundary that the per-organization webhook secret is meant to enforce, and it requires no Shipit session, ApiClient token, or privileged account within the victim organization — only that the attacker is a legitimate, distinctly-configured organization within the same multi-tenant Shipit deployment.

### Likelihood Explanation
Medium. It requires:
1. The instance to be configured for multi-organization GitHub Apps (more than one `secrets.github` entry, each with its own `webhook_secret`) — a supported and documented configuration path (`github_app_config`), not a hypothetical.
2. The attacker to control (or be) one such registered organization, which is a normal tenant of the platform, not a privileged actor.
3. Knowledge of a target commit SHA, which is public information for any commit visible on GitHub or via Shipit's own read-only surfaces.

No credential theft, no GitHub App private key, and no interception of TLS is required — only the attacker's own legitimately-provisioned webhook secret for their own organization.

### Recommendation
In `StatusHandler#process` (and any other handler that does not already scope through `stacks`/`repository`), restrict the `Commit` lookup to commits whose repository matches the repository/organization derived from the same `repository` payload field used by `WebhooksController#verify_signature`, e.g. scope via `Repository.from_github_repo_name(repository_name)` before matching by `sha`, mirroring what `PushHandler`/`PullRequest::*Handler` already do through `Handler#stacks`. More generally, `verify_signature` should bind the verified organization identity to the exact repository the request claims to act on, rather than trusting a payload-supplied `repository.owner.login`/`organization.login` in isolation from the acted-upon repository field.

### Proof of Concept
1. Configure a multi-org Shipit instance with two organizations in `secrets.github`: `orga` (attacker-controlled, webhook secret known to the attacker) and `orgb` (victim, tracked stack with an existing tracked commit, e.g. `sha = "deadbeef..."`, visible publicly on GitHub or via Shipit's commit list).
2. Attacker crafts a JSON body:
```json
{
  "sha": "deadbeef...",           // commit that belongs to orgb's tracked repo
  "state": "success",
  "context": "ci/forged",
  "organization": { "login": "orga" },
  "repository": { "owner": { "login": "orga" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `orga`'s own `webhook_secret` and sends `POST /webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner == "orga"`, fetches `Shipit.github(organization: "orga")`, and successfully verifies the signature against the attacker's own secret [7](#0-6) .
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — finds the commit belonging to `orgb`'s stack — and calls `create_status_from_github!`, persisting a forged `success` status on a commit the attacker never had write access to [3](#0-2) .
6. If `orgb`'s stack has continuous delivery enabled and requires that CI context, the forged status can unblock/trigger a deploy for `orgb`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
