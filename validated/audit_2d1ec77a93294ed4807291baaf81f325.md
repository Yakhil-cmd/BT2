### Title
Webhook signature verification is bound to an attacker-controlled `repository.owner.login` field that is disconnected from the `repository.full_name` / `organization.login` actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) is used to authenticate an incoming webhook based on `repository.owner.login` (or `organization.login`) read straight out of the unverified JSON body. Once that check passes, the actual webhook handlers (`PushHandler`, `MembershipHandler`, etc.) read *different* fields from that same unverified body - `repository.full_name` and `organization.login` - to decide which `Stack`/`Team`/`Repository` to mutate. Nothing ties the field used to pick the verifying secret to the field used to pick the target of the action, so a signature that only proves "this body was HMAC-signed by Org A's secret" is used to authorize writes against a completely different, unrelated repository/organization named elsewhere in the same body.

### Finding Description
This is the same trust-binding class as the reported `_msgSender()` bug: a privileged decision (which principal authenticated) is made from one piece of attacker-supplied data, while the sensitive action (whose funds/state get touched) is driven by another piece of attacker-supplied data that is never cross-checked against the first.

Verification: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the untrusted `params` hash before any signature check occurs, and is used to look up the `Shipit.github(organization: repository_owner)` app config whose `verify_webhook_signature` is then applied to the *entire* raw body: [3](#0-2) 

Note `verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank - a state explicitly documented as an acceptable, optional configuration: [4](#0-3) 

Once verification "passes" (either because the attacker knows that organization's secret, or - unavoidably, per the documented optional-secret feature - because that organization simply has no secret configured), the dispatched handler reads a *different* field of the same body to find its target: [5](#0-4) [6](#0-5) 

`repository.full_name` is never checked for consistency with `repository.owner.login`. The same disconnect exists in `MembershipHandler`, which trusts `organization.login` to attribute a `Team` while the outer signature check trusted the same field name but the handler additionally creates/links arbitrary `User` and `Team` records purely from body content: [7](#0-6) 

The equality that should hold and is broken:
`verified_organization (from repository.owner.login used in verify_signature) == acted_upon_repository_owner (implied by repository.full_name used by Repository.from_github_repo_name in Handler#stacks)`

### Impact Explanation
If a Shipit deployment hosts multiple GitHub organizations (a documented, supported configuration - see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), and any one of those organizations is configured without a `webhook_secret` (also documented as "optional"), an unauthenticated attacker can:
1. POST to `/webhooks` with `X-Github-Event: push`, setting `repository.owner.login` to the secret-less organization (satisfying `verify_signature` unconditionally), while setting `repository.full_name` to `"<other-org>/<real-repo>"` belonging to a fully protected organization with stacks.
2. `PushHandler` resolves `Repository.from_github_repo_name("<other-org>/<real-repo>")`, matches real `Stack` records, and calls `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen SHA - completely bypassing the target organization's own `webhook_secret`.

This is an unauthorized cross-organization write into Shipit's tracked commit/ref state (forced sync to an attacker-chosen commit), and the same pattern lets an attacker fabricate arbitrary `Team`/`User`/membership records via `MembershipHandler` regardless of which organization actually owns them. This maps to the "unauthorized deploy/rollback" and "cross-repository writes" impact tiers.

### Likelihood Explanation
Requires only: (a) the deployment to serve more than one GitHub organization (explicitly documented multi-org setup) and (b) at least one configured organization having no `webhook_secret` (explicitly documented as optional). No GitHub credentials, no `ApiClient` token, and no session are needed - the request is a plain unauthenticated `POST /webhooks`. Given the feature is documented and encouraged for flexibility ("Webhook secret (optional)"), this is a realistic, low-effort attack surface for any multi-tenant Shipit instance.

### Recommendation
- Verify the webhook signature using the organization/app configuration that matches the resource actually being mutated (e.g., derive it from `repository.full_name`'s owner segment, or require it to equal `repository.owner.login` before dispatch), and reject the request if they disagree.
- Do not allow `verify_webhook_signature` to silently return `true` for organizations with no configured secret when other organizations in the same installation do have one; either require all configured organizations to set a secret, or scope trust per-organization so a secret-less org cannot be leveraged to forge events for a different org's repositories.
- In each `Handler`, cross-validate that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name` before resolving `Stack`/`Team`/`User` records.

### Proof of Concept
Assuming a Shipit instance configured for two organizations, `no-secret-org` (no `webhook_secret`) and `victim-org` (with `webhook_secret` set, containing a real `Stack` for `victim-org/prod-app`):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/prod-app"
  }
}
```

`WebhooksController#verify_signature` resolves `repository_owner` = `"no-secret-org"`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` with no signature required. `PushHandler#process` then loads `Repository.from_github_repo_name("victim-org/prod-app")` and enqueues `stack.sync_github(expected_head_sha: "deadbeef...")` for the real, protected `victim-org` stack, entirely bypassing `victim-org`'s own `webhook_secret`.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
