### Title
Webhook signature verification keys on `repository.owner.login` while handlers act on `repository.full_name` - cross-repository stack sync forgery on multi-org instances - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate a signature against using the `repository.owner.login` field of the *unauthenticated* JSON payload, but the handler that is subsequently invoked (`PushHandler`/`Handler#stacks`) resolves the target `Stack` using the *different* `repository.full_name` field of that same payload. Because the HMAC only proves that the sender knows the secret configured for the organization named in `owner.login`, not that they have any relationship to the repository named in `full_name`, an attacker who controls a GitHub App/webhook secret for any one organization configured on a multi-tenant Shipit instance can forge a payload claiming a different organization's repository, sign it with their own known secret, and have it accepted, triggering `GithubSyncJob` (and other webhook side effects) for a stack they do not own.

### Finding Description
`Shipit.github(organization:)` supports a multi-tenant configuration where multiple GitHub organizations, each with its own `webhook_secret`, are configured in `secrets.github` (see `lib/shipit.rb:170-200`, `github_app_config`). This is a legitimate deployed configuration, not a hypothetical one.

In `app/controllers/shipit/webhooks_controller.rb`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read straight from the attacker-controlled JSON body, *before* any signature has been verified. It is used only to select which org's `webhook_secret` to HMAC-check the raw body against.

After verification succeeds, `create` re-parses the same raw body and dispatches it to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [2](#0-1) 

`Handler#stacks` (used by `PushHandler`) resolves the target stack from a *different* field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

```ruby
class PushHandler < Handler
  params do
    requires :ref
    requires :after
  end

  def process
    stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
  end
end
``` [4](#0-3) 

The binding that is broken as an equality:
```
org whose secret authenticated the request (repository.owner.login)
        !=
repo/stack that gets acted on (repository.full_name)
```
Both fields are inside the HMAC-signed bytes, so the signature is *technically* valid for the exact bytes sent — but the signature only proves the sender possesses the secret for `owner.login`'s organization. It proves nothing about the sender's relationship to `full_name`. Since the attacker fully controls both fields and signs the payload with their own known secret, they can set `owner.login` to their own org and `full_name` to any other org/repo tracked by the same Shipit instance, and the check passes.

### Impact Explanation
On a Shipit instance configured to serve multiple GitHub organizations (the multi-org config path in `lib/shipit.rb`), any actor who holds the webhook secret for one organization (e.g., because they own/administer that org's GitHub App installation pointed at this Shipit instance) can forge webhook deliveries that are accepted as authentic for a *different* organization's repositories. This lets them:
- Force `GithubSyncJob` for an arbitrary stack belonging to another org, forcing GitHub API calls and commit ingestion for that repository (`app/jobs/shipit/github_sync_job.rb`), which is the trigger step feeding continuous-delivery / auto-deploy pipelines on stacks that have `continuous_delivery` scheduling enabled.
- More broadly, this pattern (signature scoped to `owner.login`, side effects scoped to `full_name`) applies to every handler that derives its target from `payload.dig('repository', 'full_name')`, since all of them inherit from `Handler#stacks`.

This crosses a repository/organization trust boundary without requiring any Shipit session, API token, or GitHub write access to the victim repository — only knowledge of a secret belonging to some other org hosted on the same instance. It maps to the "unauthorized deploy" trigger surface described in the engagement's impact criteria, since it can force sync/deploy-pipeline activity on a stack the attacker does not control.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (`secrets.github` keyed by org, per `github_app_config`/`github_default_organization`) — a supported, documented configuration, not a contrived one. The attacker needs a valid webhook secret for *any one* of the configured organizations (e.g., because they administer a legitimate GitHub App installation for their own org on that same shared instance) — a much lower bar than needing credentials for the victim org.

### Recommendation
Bind the signature-selection key to the same field(s) that handlers use for authorization, and re-verify after parsing: derive `repository_owner` and validate that the stack ultimately resolved by `full_name` actually belongs to the org whose secret matched. Concretely, after computing `repository_owner`, also cross-check that `repository.full_name` starts with `"#{repository_owner}/"` (or resolve the target `Stack`/`Repository` and compare its recorded owner to `repository_owner`) before dispatching to handlers, rejecting the request if they diverge.

### Proof of Concept
1. Shipit instance hosts two orgs, `attacker-org` and `victim-org`, each with a distinct `webhook_secret` (multi-org config in `secrets.github`).
2. Attacker (who legitimately knows `attacker-org`'s webhook secret, e.g. because they administer that GitHub App installation) crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC(attacker-org_webhook_secret, raw_body)` and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates the HMAC against `attacker-org`'s secret — which matches, since the attacker used the correct secret for the exact bytes sent.
5. `create` re-parses the body and dispatches to `PushHandler`, whose `repository_name` reads `"victim-org/victim-repo"` from `full_name`, resolving `victim-org`'s `Stack` and invoking `stack.sync_github(expected_head_sha: ...)`, forging a GitHub sync trigger for a repository the attacker does not control.
