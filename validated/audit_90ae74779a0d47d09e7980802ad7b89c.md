### Title
Unhandled TypeError on `payload.outputs` when dry-running a new AA trigger with a payment message that has no inline payload - ([File: network.js])

### Summary
When a full node has `conf.bDryRunNewTriggers` enabled and receives/posts a unit that pays a primary AA trigger, `handleJoint()`'s `ifOk` callback in `network.js` builds `outputAddresses` by filtering the unit's messages for `msg.app === 'payment'` and then unconditionally dereferencing `msg.payload.outputs`, without checking that `msg.payload` is actually present. A payment message can legitimately have `payload_location !== "inline"` (e.g. `"none"`, used for private/hidden payments whose payload is delivered out-of-band), in which case `msg.payload` is `undefined`. Dereferencing `.outputs` on `undefined` throws an uncaught `TypeError`, mirroring the libheif pattern where `heif_image_handle_get_image_tiling()` assumed a companion property (`ispe`) was present whenever another property (`uncC`) existed, and crashed via a null/undefined dereference when that assumption was violated.

### Finding Description
`validation.js` requires `payload.outputs` to be a valid array only when a payment message actually carries an inline payload: [1](#0-0) 
This means a fully valid, validation-passing unit can contain a `payment` message with `payload_location: "none"` and **no `payload` field at all** (this is exactly how outputs for private assets, e.g. blackbytes, are transmitted — the payload arrives separately, see `wallet.js`'s handling of `payload_hash` for `payload_location === "none"` payment messages): [2](#0-1) 

After such a unit passes `validation.validate()` and reaches the `ifOk` callback, `network.js` performs a dry-run of any primary AA trigger it contains: [3](#0-2) 
The `outputAddresses` computation filters only by `msg.app === 'payment'`, not by presence of `msg.payload`, then calls `.map(output => output.address)` directly on `msg.payload.outputs`: [4](#0-3) 
If `msg.payload` is `undefined` (payload_location `"none"`), `msg.payload.outputs` throws `TypeError: Cannot read properties of undefined (reading 'outputs')`. This callback is not wrapped in a try/catch, so the exception propagates out of the `async ifOk` handler as an unhandled promise rejection / unhandled exception in the unit-processing pipeline for every full node that has `conf.bDryRunNewTriggers` enabled.

This is analogous in root-cause shape to the CVE: `heif_image_handle_get_image_tiling()` assumed the co-presence of `ispe` whenever `uncC` was present and dereferenced it unconditionally; here the code assumes the co-presence of `payload.outputs` whenever `app === 'payment'` is present and dereferences it unconditionally, without checking that the payload was actually inlined.

### Impact Explanation
An uncaught exception thrown while processing an accepted unit inside the core joint-handling pipeline can crash or destabilize the node process (unhandled exception in Node.js terminates the process unless a global handler exists). Because `ifOk` runs for units that are otherwise fully valid and are about to be written via `writer.saveJoint`, a node hit by this bug fails to finish processing/confirming that unit and any of its dependents, which maps to the "network unable to confirm new units" impact category for nodes running with `conf.bDryRunNewTriggers` enabled. Any attacker or ordinary user who can compose and post/relay a unit with (a) a `payment` message using `payload_location: "none"` (a normal mechanism for private-asset payments) and (b) an output that is also a primary AA trigger (paying an AA address) can trigger this without any special privileges — it requires only posting a normally-constructed unit.

### Likelihood Explanation
Likelihood depends on whether `conf.bDryRunNewTriggers` is enabled by default/in production configurations; I was unable to confirm its default value from the available index (grep only found the two usage sites in `network.js`, not the default declaration in `conf.js`, which was not indexed/found). If it defaults to `true` on full (non-light) nodes, essentially any unprivileged unit poster can trigger this on any node running that configuration by constructing a unit with a `payment` message that both (1) has `payload_location` other than `"inline"` and (2) pays an existing AA address. This is straightforward to construct with the existing private-payment machinery and requires no compromise of any peer, hub, or key.

### Recommendation
In `network.js`, before computing `outputAddresses`, filter payment messages to those that actually have an inline payload (`msg.payload_location === "inline" && msg.payload`) or otherwise guard the `.outputs` access with a null/undefined check, mirroring the checks already used elsewhere (e.g. in `aa_composer.js`'s `getTrigger`, which does check `message.payload` truthiness before touching it). Wrap the dry-run block in a try/catch (or ensure the `async ifOk` promise rejection is caught) so that a crash in the dry-run logic cannot escape as an unhandled exception and take down unit processing.

### Proof of Concept
1. Enable `conf.bDryRunNewTriggers = true` on a full (non-light) node that has at least one deployed AA at address `AA_ADDR`.
2. Compose a unit containing two messages:
   - A `payment` message with `app: 'payment'`, `payload_location: 'none'` (used for a private/indivisible asset payment whose real payload is sent out-of-band, per the mechanism in `wallet.js`/`indivisible_asset.js`), with no `payload` field, referencing an output that ultimately targets `AA_ADDR` for the purposes of unit validity per the private-payment flow.
   - A base-currency `payment` message paying `AA_ADDR` in bytes so that `objValidationState.count_primary_aa_triggers` is `> 0` for this unit.
3. Post/broadcast this unit to a node with `conf.bDryRunNewTriggers` enabled.
4. Once the unit passes `validation.validate()` and reaches `ifOk`, `network.js` executes:
   ```js
   const outputAddresses = objJoint.unit.messages
       .filter(msg => msg.app === 'payment')
       .reduce((acc, msg) => acc.concat(msg.payload.outputs.map(output => output.address)), []);
   ```
   For the message with `payload_location: 'none'`, `msg.payload` is `undefined`, so `msg.payload.outputs` throws `TypeError: Cannot read properties of undefined (reading 'outputs')`, propagating out of the `async ifOk` handler as an unhandled exception and disrupting further processing/confirmation of the unit on that node.
