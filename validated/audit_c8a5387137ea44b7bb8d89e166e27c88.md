### Title
Cross-Organization Webhook Forgery via Unbound `repository.owner.login`/`repository.full_name` Fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit's webhook endpoint selects which GitHub App/organization's `webhook_secret` to verify a signature against using `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON body, but the actual handler logic that decides which `Stack`/`Repository` gets written to uses a **different** field from the same body — `repository.full_name`. Because the HMAC signature only proves "this body was produced by someone who knows organization A's secret," and nothing binds `repository.owner.login` to `repository.full_name`, an attacker who legitimately controls one org's webhook secret (a supported, documented multi-org configuration) can forge a validly-signed payload whose `repository.full_name` points at a victim org/stack, causing Shipit to process pushes, commit statuses, check runs, or membership changes against a repository/stack the attacker does not own.

### Finding Description
The webhook signature verification step picks the GitHub App configuration to check against, based on an unauthenticated payload field: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` straight from the JSON body before any cryptographic check has taken place, and uses it to select which org's `webhook_secret` to validate the signature against, via `Shipit.github(organization: repository_owner)`.

The signature check itself, in `GithubApp#verify_webhook_signature`, is a straightforward HMAC comparison over the full raw request body: [3](#0-2) 

This proves only that the *entire byte sequence* of the body was produced/signed by someone possessing organization A's secret. It says nothing about whether the content of that body is a truthful representation of an event that happened in organization A's repositories — an attacker with organization A's secret can construct an arbitrary payload with any `repository.full_name`.

Downstream, the handler base class resolves which stacks to act on from a *different* payload field: [4](#0-3) 

`repository_name` reads `payload.dig('repository', 'full_name')`, independent of `repository.owner.login`. There is no check anywhere in `WebhooksController` or `Handler` that `repository.owner.login` (used to pick the verifying secret) is consistent with `repository.full_name` (used to pick the stack to mutate).

This is precisely the "single-step ownership change" bug class applied to a deployment-trust binding: the report's `LibOwnable._setAdmin` changes privileged state in one step based on a single unchecked input; here, Shipit changes which repository's state gets mutated in one step based on an input (`repository.full_name`) that is never cross-checked against the input that determined trust (`repository.owner.login`/the verifying secret). The equality that should hold — `organization that authenticated == organization owning the repository being written` — is never enforced.

Multi-organization webhook secret configuration is a first-class, documented feature, which is exactly what makes an attacker's "own" org a legitimate signing identity distinct from the victim's: [5](#0-4) 

The existing test suite demonstrates the write side-effects that get executed keyed off `repository.full_name`/`repository_params` (i.e., what an attacker could redirect at a victim stack): [6](#0-5) [7](#0-6) [8](#0-7) 

These show that a `push` event enqueues `GithubSyncJob` scoped to the stack resolved from the repository name in the payload, a `status` event creates a `Status` row on a commit in that stack, and a `membership` event creates `Team`/`User` records — all driven by attacker-controlled JSON fields that were never bound to the identity that was cryptographically verified.

### Impact Explanation
An attacker who administers their own GitHub organization (and therefore legitimately knows/controls that organization's `webhook_secret`, a normal, unprivileged capability when multiple orgs are configured on one Shipit instance) can forge webhook deliveries that are correctly signature-verified for their own org but whose content (`repository.full_name`) targets a victim organization's stack. This allows unauthorized writes into another organization's Shipit state: injecting fabricated commit statuses/check runs (which can flip a stack's CI gating and enable an unauthorized deploy/merge to proceed), triggering `GithubSyncJob` against a victim stack, and creating arbitrary `Team`/`User` records. This is a cross-repository/cross-organization write achieved without any credential belonging to the victim, matching the Critical "cross-repository writes" / "unauthorized deploy" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker control (or be permitted to configure) a second GitHub organization/App on the same Shipit deployment with its own `webhook_secret` — a normal, documented, and unprivileged multi-tenant configuration path, not GitHub org admin rights over the victim, not any Shipit session, `ApiClient` token, or `api_clients_secret`. The attacker crafts the JSON body directly and POSTs it to the public `/webhooks` endpoint; no interaction with GitHub's actual webhook delivery pipeline is needed since Shipit trusts the raw body's `repository.owner.login` for secret selection but a separate field for the write target.

### Recommendation
Enforce that the organization used to select/verify the webhook secret is the same organization referenced by the payload field used to resolve the target `Stack`/`Repository`. Concretely: after verifying the signature, re-derive `repository_owner` from the *same* field (`repository.full_name`'s owner segment) that `Handler#repository_name` will use, and reject the request if the two disagree, or simply derive both values from a single canonical field. Do not let `Handler#repository_name`/`#stacks` trust an org-qualified field that was not the one bound to the verifying secret.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, `attacker-org` (secret known to the attacker, e.g., because they administer it) and `victim-org` (a stack the attacker does not control).
2. Craft a JSON `push`/`status` payload where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"`.
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org-secret, raw_body)>`.
4. POST the payload to `/webhooks` with `X-Github-Event` set to `push` (or `status`/`membership`).
5. `WebhooksController#verify_signature` selects `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), verifies the HMAC successfully since it matches `attacker-org`'s secret.
6. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` runs `PushHandler`, whose `stacks`/`repository_name` resolve `"victim-org/victim-repo"` from `repository.full_name`, causing `GithubSyncJob` (or a fabricated `Status`, or new `Team`/`User` records) to be enqueued/created against the victim's stack — despite the attacker never having presented any credential tied to `victim-org`.

```ruby
      verified = github_app.verify_webhook_signature(
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
