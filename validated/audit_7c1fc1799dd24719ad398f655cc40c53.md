### Title
`Api::CCMenuController#stack` bypasses `stacks` scoping via `Stack.from_param!`, allowing cross-stack read with a token scoped to a different stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController#stack` correctly resolves stacks through the scoped `stacks` relation (`Stack.where(id: current_api_client.stack_id)`), but `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, bypassing the tenant-scoping binding entirely.

### Finding Description
The intended binding is: `stack ∈ Stack.where(id: current_api_client.stack_id)` whenever `current_api_client.stack_id?` is true, as implemented by `Api::BaseController#stacks`/`#stack`: [1](#0-0) 

`Api::CCMenuController` redefines `#stack` to skip the `stacks` helper entirely: [2](#0-1) 

This means for any request routed to `CCMenuController#show`, `stack = Stack.from_param!(params[:stack_id])` resolves against the entire `Stack` table, not the caller's scope. The only authorization check applied is `require_permission :read, :stack`, which is implemented by `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` only verifies that the string `"read:stack"` is present in `permissions` — it never compares `current_api_client.stack_id` to the resolved stack's id. There is no other guard: no `before_action` re-checks that `stack.id == current_api_client.stack_id` in this controller. Given a valid `ApiClient` token with `permissions=['read:stack']` and `stack_id = A.id`, an attacker constructs a GET request against the ccmenu endpoint with `params[:stack_id]` set to stack B's `to_param` (and the client's own `params[:token]`, since `CCMenuController#authenticate_api_client` reads the token from the query string rather than Basic auth): [4](#0-3) 

The request resolves `stack` to stack B and renders `latest_deploy = stack.deploys_and_rollbacks.last`, exposing stack B's latest deploy/rollback status (build state, `ended_at`, `running?`) despite the token being scoped only to stack A. This is exactly the "Api subcontroller calling a from_param-style resolver directly, bypassing `#stacks`" case the question asks about.

### Impact Explanation
An attacker holding any valid `ApiClient` token scoped to one stack (even a low-privilege `read:stack`-only token created for a single CI dashboard integration) can enumerate and read the deploy/build status of every other stack in the Shipit instance, across repositories/tenants, by varying `params[:stack_id]`. This is a cross-tenant unauthorized read of stack state (deploy status, running/ended state), matching the "High — unauthenticated/unauthorized read of stack state" impact category. It is fully repeatable against arbitrary stack IDs with no rate limiting bypass required — one request per target stack.

### Likelihood Explanation
Preconditions: the attacker must already possess one valid `ApiClient` token (any operator-issued token scoped to any single stack with `read:stack`), which is a normal, low-privilege credential many CI/CD integrations legitimately hold (e.g., a CCMenu/build-monitor integration token). No GitHub secrets, session, or team membership is needed. Cost is a single authenticated HTTP GET with a different `stack_id`. This is highly feasible and trivially repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` helper instead of calling `Stack.from_param!` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Additionally, audit all Api subcontrollers for direct `Stack.` / `Stack.from_param!` / `Stack.find` calls that bypass `#stacks`, and add a regression test asserting `check_permissions!`/`#stack` resolution together enforce `stack.id == current_api_client.stack_id` for every subcontroller when `stack_id?` is set.

### Proof of Concept
```ruby
test "ccmenu#show returns 404 (not stack B) for a token scoped to a different stack" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cocaine)
  api_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-token',
    stack: stack_a,
    permissions: ['read:stack']
  )

  get "/stacks/#{stack_b.to_param}/ccmenu.xml", params: { token: api_client.authentication_token }

  # Broken binding today: stack resolves to stack_b even though
  # stack_b.id != api_client.stack_id, so this currently returns 200
  # with stack_b's data instead of the expected 404.
  assert_response :not_found
end
```
(Route path taken from `Shipit::Engine.routes` for the ccmenu resource; exact path segment may need adjustment to match `config/routes.rb`, but the assertion — 404 for cross-stack access vs the current 200 — is the reproducible proof.)
