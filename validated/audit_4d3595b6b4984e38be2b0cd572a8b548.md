### Title
Precompile signature verification (secp256k1/ed25519/secp256r1) runs synchronously and unmetered by the compute meter, letting a single transaction perform unbounded expensive cryptography on a leader before any CU-based throttling applies - ([File: program-runtime/src/invoke_context.rs])

### Summary
`InvokeContext::process_precompile` invokes the precompile `verify_fn` (secp256k1 recovery, ed25519-dalek `verify_strict`, or OpenSSL secp256r1 ECDSA verification, each looping over up to the signature count encoded in the instruction) directly, with no call to `compute_meter.consume_checked` before or during the call. [1](#0-0) 
The cost model does assign a per-signature cost (`SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST`) but this is used only for block-cost-limit scheduling accounting, not as a compute-unit charge that gates or aborts the actual synchronous verification work during execution. [2](#0-1) [3](#0-2) 
A dedicated regression test confirms that a precompile instruction consumes **zero** compute units from the actual CU meter during VM execution, even though the cost model assumes a full default builtin allocation for it. [4](#0-3) 

### Finding Description
When a transaction includes a `secp256k1_program`, `ed25519_program`, or `secp256r1_program` instruction, `InvokeContext::process_message` detects it is a precompile and calls `process_precompile`, which forwards directly to the crypto verify function without any compute-budget accounting: [5](#0-4) [1](#0-0) 

The `secp256r1::verify` function permits up to 8 signatures per instruction and performs, per signature: `BigNum` parsing, `EcPoint::from_bytes`, `EcKey::from_public_key`, and an OpenSSL ECDSA `Verifier::verify` call — all of it real, synchronous CPU-bound cryptography. [6](#0-5) 
The `ed25519::verify` function similarly loops over `num_signatures` (bounded only by instruction data size, i.e. up to the ~1232-byte packet limit) doing dalek `verify_strict` calls. [7](#0-6) 

Unlike ordinary BPF or builtin program instructions, whose CU consumption is metered via `compute_meter.consume_checked` and can be aborted mid-flight when the budget is exhausted (see the zk-elgamal-proof or vote programs, which explicitly `consume_checked` before doing expensive proof/signature verification work) [8](#0-7) [9](#0-8) 
precompile verification has no such gate. The compute unit limit set by the transaction (via `ComputeBudgetInstruction::SetComputeUnitLimit`) has zero bearing on whether/how much precompile crypto work executes: a transaction can request the minimum compute-unit limit while still forcing full execution of arbitrarily many precompile instructions (bounded only by `MAX_INSTRUCTION_TRACE_LENGTH`, checked purely on instruction *count*, not on the number of encoded signatures per instruction) each with up to 8 secp256r1 signatures or the packet-size-bound cap of ed25519/secp256k1 signatures.

This is structurally the same bug class as the referenced Zebra advisory: cheap, unprivileged input is accepted and routed straight into synchronous, CPU-heavy cryptographic verification before any inexpensive resource-budget check (the SVM's compute-unit metering, which is the analogous "policy/standardness" gate here) can bound or reject the work. Because this happens inside `process_message`/`process_precompile` on the banking/replay execution path, a leader (or any validator replaying the block) performing execution for such a transaction spends real wall-clock CPU time on OpenSSL EC and ed25519/secp256k1 verification that is not reflected in, or limited by, the per-transaction CU budget actually enforced at execution time.

### Impact Explanation
The practical damage is bounded to a leader-side/validator-side performance and cost-accounting concern rather than an unsigned fund movement, consensus divergence, or replay: the actual signature verification result is still deterministic and does not permit forging signatures or bypassing checks — the instruction still fails if signatures are invalid. The impact is that unmetered CPU-bound crypto work can be performed per instruction, independent of the compute-unit limit the transaction pays for, meaning the fee/CU market does not accurately price the true cost of packing many precompile signature checks into one transaction. This matches the "leader-side cost limits" category called out as in-scope, but the block-level cost model still counts these signatures toward `MAX_BLOCK_UNITS` for scheduling purposes, which caps the aggregate blast radius per block, unlike the fully-unbounded description in the Zebra report.

### Likelihood Explanation
Reachable trivially by any unprivileged transaction sender — no special privileges are required to submit a transaction with several precompile instructions, each maximizing the signature count field. No feature gate or leader configuration prevents it.

### Recommendation
Charge compute units for precompile verification proportional to the number of signatures actually processed (matching the cost-model constants `SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST`) via `compute_meter.consume_checked` inside `process_precompile` (or inside each `verify_fn`) before performing the expensive cryptographic operations, so that a transaction's declared CU limit actually bounds the amount of precompile verification work performed, consistent with how CU consumption gates other program execution.

### Proof of Concept
Not independently reproduced in this pass (no execution environment available); the finding is based on static code review of:
- `program-runtime/src/invoke_context.rs:601-631` (`process_precompile` has no CU accounting),
- `precompiles/src/secp256r1.rs:18-138` and `precompiles/src/ed25519.rs:11-79` (real, expensive crypto work per signature),
- `core/tests/scheduler_cost_adjustment.rs:381-402` (existing test explicitly documents "VM Execution: consume 0 from CU-meter" for a precompiled instruction).

A concrete PoC would construct a transaction with the minimum requested `ComputeBudgetInstruction::SetComputeUnitLimit` and multiple `secp256r1_program`/`ed25519_program` instructions each encoding the maximum signature count, and measure wall-clock execution time against the nominal CU cost charged, confirming the mismatch. This step is left to a background agent with code execution access to validate empirically.

    let half_order: BigNum =
        BigNum::from_slice(&SECP256R1_HALF_ORDER).map_err(|_| PrecompileError::InvalidSignature)?;

    // Parse order - 1 from constant
    let order_minus_one: BigNum = BigNum::from_slice(&SECP256R1_ORDER_MINUS_ONE)
        .map_err(|_| PrecompileError::InvalidSignature)?;

    // Create a BigNum for 1
    let one = BigNum::from_u32(1).map_err(|_| PrecompileError::InvalidSignature)?;

    // Define curve group
    let group = EcGroup::from_curve_name(Nid::X9_62_PRIME256V1)
        .map_err(|_| PrecompileError::InvalidSignature)?;
    let mut ctx = BigNumContext::new().map_err(|_| PrecompileError::InvalidSignature)?;

    for i in 0..num_signatures {
        let start = i
            .saturating_mul(SIGNATURE_OFFSETS_SERIALIZED_SIZE)
            .saturating_add(SIGNATURE_OFFSETS_START);

        // SAFETY:
        // - data[start..] is guaranteed to be >= size of Secp256r1SignatureOffsets
        // - Secp256r1SignatureOffsets is a POD type, so we can safely read it as an unaligned struct
        let offsets = unsafe {
            core::ptr::read_unaligned(data.as_ptr().add(start) as *const Secp256r1SignatureOffsets)
        };

        // Parse out signature
        let signature = get_data_slice(
            data,
            instruction_datas,
            offsets.signature_instruction_index,
            offsets.signature_offset,
            SIGNATURE_SERIALIZED_SIZE,
        )?;

        // Parse out pubkey
        let pubkey = get_data_slice(
            data,
            instruction_datas,
            offsets.public_key_instruction_index,
            offsets.public_key_offset,
            COMPRESSED_PUBKEY_SERIALIZED_SIZE,
        )?;

        // Parse out message
        let message = get_data_slice(
            data,
            instruction_datas,
            offsets.message_instruction_index,
            offsets.message_data_offset,
            offsets.message_data_size as usize,
        )?;

        let r_bignum = BigNum::from_slice(&signature[..FIELD_SIZE])
            .map_err(|_| PrecompileError::InvalidSignature)?;
        let s_bignum = BigNum::from_slice(&signature[FIELD_SIZE..])
            .map_err(|_| PrecompileError::InvalidSignature)?;

        // Check that the signature is generally in range
        let within_range = r_bignum >= one
            && r_bignum <= order_minus_one
            && s_bignum >= one
            && s_bignum <= half_order;

        if !within_range {
            return Err(PrecompileError::InvalidSignature);
        }

        // Create an ECDSA signature object from the ASN.1 integers
        let ecdsa_sig = openssl::ecdsa::EcdsaSig::from_private_components(r_bignum, s_bignum)
            .and_then(|sig| sig.to_der())
            .map_err(|_| PrecompileError::InvalidSignature)?;

        let public_key_point = EcPoint::from_bytes(&group, pubkey, &mut ctx)
            .map_err(|_| PrecompileError::InvalidPublicKey)?;
        let public_key = EcKey::from_public_key(&group, &public_key_point)
            .map_err(|_| PrecompileError::InvalidPublicKey)?;
        let public_key_as_pkey =
            PKey::from_ec_key(public_key).map_err(|_| PrecompileError::InvalidPublicKey)?;

        let mut verifier =
            Verifier::new(openssl::hash::MessageDigest::sha256(), &public_key_as_pkey)
                .map_err(|_| PrecompileError::InvalidSignature)?;
        verifier
            .update(message)
            .map_err(|_| PrecompileError::InvalidSignature)?;

        if !verifier
            .verify(&ecdsa_sig)
            .map_err(|_| PrecompileError::InvalidSignature)?
        {
            return Err(PrecompileError::InvalidSignature);
        }
    }
