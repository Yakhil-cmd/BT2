### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository scoping, letting a `ci/coverage` status from any GitHub org drive another stack's `continuous_deployment` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` loads commits with `Commit.where(sha: params.sha).each` and calls `create_status_from_github!` on every match, with no filter on the payload's `repository.full_name`. Since `Commit.sha` is not globally unique to one stack (any repository/fork/mirror sharing a commit — same content, cherry-pick, or a repository registered under an attacker-controlled GitHub org that a victim also happens to reference), a correctly signed webhook from an unrelated, attacker-owned repository can create a `success` status attached to a victim's commit, and if that victim stack has `continuous_deployment` enabled and is waiting on that context, `Commit#schedule_continuous_delivery` will fire `ContinuousDeliveryJob` for the victim stack.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.repository.full_name == payload['repository']['full_name']`, but nothing enforces this equality.

Path:
- `Shipit::WebhooksController#create` parses raw JSON and dispatches to handlers registered for the `status` event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:10-15`).
- `verify_signature` only checks that the HMAC signature is valid for `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-supplied payload (`params.dig('repository','owner','login')`). This proves the request came from *some* GitHub org/app registered with Shipit — it does not prove the `sha`/`context` belongs to a specific stack (`app/controllers/shipit/webhooks_controller.rb:24-49, 59-62`).
- `StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
(`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) — no `repository`/`stack` scoping at all, unlike the base `Handler#stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), which `StatusHandler` doesn't even use.
- `Commit#create_status_from_github!` writes the status (`app/models/shipit/commit.rb:165-169`), and `add_status` re-evaluates deployability and calls `stack.schedule_merges` (`app/models/shipit/commit.rb:366-386`).
- Separately, `after_commit :schedule_continuous_delivery, on: :create` was already wired at commit creation time (`app/models/shipit/commit.rb:24-25, 281-287`): `schedule_continuous_delivery` checks `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)`. Because status changes affect `deployable?`/`blocked?`, a `success` status landing on the shared SHA row can flip a previously not-ready commit into a deployable one for the buffered continuous-delivery evaluation, or unblock a stack that requires `ci/coverage`.

Exploit flow: attacker registers/controls a repository under a GitHub org that Shipit trusts (so `verify_signature` passes for that org), crafts a `status` webhook payload with `sha` equal to a SHA that also exists as a `Commit` row belonging to a victim's stack (e.g., a shared commit from a common upstream, a rebase/cherry-pick, or any repository whose commits get imported into multiple stacks with overlapping history), sets `context: ci/coverage`, `state: success`, and POSTs it to `/webhooks`. `StatusHandler` finds and updates every `Commit` row with that SHA regardless of which repository/stack it belongs to.

Why existing guards don't stop it: `verify_signature` authenticates the *org*, not the *commit-repository binding*; `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` schema only validates types/presence, not repository ownership; there is no `before_action` or model validation tying a `Commit` to the `repository.full_name` in the payload before writing its status.

### Impact Explanation
An unprivileged attacker who owns/pushes to a repository connected to any GitHub org registered with the Shipit instance can write a `Status` record onto a `Commit` belonging to a completely different, victim stack, and thereby influence that stack's deployability computation (`Commit#deployable?`, `Commit#blocked?`) and trigger `ContinuousDeliveryJob`/`stack.schedule_merges` for a stack the attacker never authenticated for. This is a cross-tenant write: "a payload for one repository mutating another's stack/commit," matching the Critical impact category (unauthorized deploy/rollback/merge of code the attacker doesn't control the outcome of, or blocking a legitimate deploy by injecting a spurious status).

### Likelihood Explanation
Preconditions: the attacker must control a repository behind a GitHub org/App already registered in `Shipit.github_teams`/`Shipit.github` config (so `verify_signature` passes), and a `Commit` row with the same `sha` must already exist for the victim stack (requires SHA reuse/collision across repos — plausible via forks, mirrored/imported histories, or shared upstream commits, since Git SHAs are content-addressed and not globally scoped per repository in Shipit's DB schema). The victim stack must have `continuous_deployment` enabled and be waiting on the affected status context. Attacker cost is a single crafted HTTP POST; the action is trivially repeatable against any commit whose SHA is guessable or known (e.g., commits from a public shared repo).

### Recommendation
Scope `StatusHandler#process` (and similarly `CheckSuiteHandler`) to only update commits belonging to the stack(s) whose repository matches `payload.dig('repository', 'full_name')`, e.g., use the existing `Handler#stacks` helper to find the repository first, then filter `Commit.where(sha: params.sha, stack: stacks)` before writing any status, ensuring one repository's status can never write to another repository's stack/commit.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
