Confirmed: `sha` is indexed per `stack_id` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), meaning the same SHA can legitimately exist across many different stacks/repositories tracked by the same Shipit instance, and `Commit.belongs_to :stack` has no global uniqueness constraint on `sha` alone [1](#0-0) . This confirms the exploit path below is structurally sound: an attacker can produce a commit with an identical SHA to a victim's commit (e.g., by pushing the exact same tree/parent/author/committer/timestamp/message to their own repository) and then have that SHA match a row in the victim stack's `commits` table.

### Title
Unscoped commit-status webhook handler allows cross-organization forgery of CI status, enabling unauthorized deploys - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook handler resolves the target commit purely by `sha`, without ever checking which repository/organization the event's GitHub App signature actually authenticated. Because Shipit supports multiple GitHub Apps/organizations, each with its own `webhook_secret` that can be verified only against its own payload, this breaks the trust equality: `organization that authenticated the webhook == repository/stack the status update is written to`. An operator who legitimately owns *any* GitHub App/organization onboarded to the same Shipit instance can sign an arbitrary payload with their own known secret and inject a fabricated "success" CI status onto a commit belonging to an entirely different organization's stack, as long as the `sha` values collide.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App's secret to validate the HMAC signature against using `repository_owner`, itself read straight from the attacker-controlled JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`): [2](#0-1) [3](#0-2) 

Once the signature is accepted (which only proves the payload was signed with *some* known org's secret — one the attacker controls, since they administer that org's GitHub App), the request is dispatched to handlers based solely on `X-Github-Event`: [4](#0-3) 

`StatusHandler#process` never uses `repository_name`/`repository_owner` at all — it looks up commits globally by `sha` across the whole database and mutates them: [5](#0-4) 

Contrast this with other handlers (`ClosedHandler`, `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`) which at least scope via `Repository.from_github_repo_name(params.repository.full_name)` before acting [6](#0-5) . Even those are still vulnerable to the same root cause (the field used to select the webhook secret is different from, and not checked against, the field used to select which repository is mutated), but `StatusHandler` doesn't even attempt a repository/stack scoping — it is the most direct instance of the class of bug: **the identity verified by the signature (the organization owning the webhook secret) is never bound to the identity operated on (the stack/commit that gets mutated)**.

Applying `create_status_from_github!` on a commit directly affects deployability: `Commit#deployable?` returns true when `success? && !blocked?` [7](#0-6) , and `Status#state` becomes `success` from the forged payload data, which is exactly the field `StatusHandler` writes through `commit.create_status_from_github!(params)`.

### Impact Explanation
This is an unauthorized-deploy-class bug: any operator of a GitHub App organization already integrated with a shared Shipit instance (a low-privilege boundary — they only need to run their own GitHub App/webhook, not touch the victim's repository or Shipit session) can forge a "success" (or any) CI status on a commit belonging to a completely unrelated organization's stack, as long as the SHA matches. `Commit.commits.sha` is only unique per `stack_id` [8](#0-7) , not globally, so an attacker can engineer a SHA collision by reproducing the exact same commit content in their own repository (SHA-1 is deterministic over tree, parents, author/committer identities+timestamps, and message) and pushing it, or even guessing/duplicating an already-public open-source commit shared across forks. Once the forged `success` status lands, `deployable?` is satisfied and required-status gating configured in the victim's `shipit.yml` can be silently bypassed, letting a legitimate operator deploy a commit that never actually passed CI, or letting the merge queue (`stack.schedule_merges`) proceed based on falsified state [9](#0-8) .

### Likelihood Explanation
Exploitability requires only: (1) being an administrator of any GitHub App/org configured in the shared Shipit `secrets.yml` multi-org section, which is a normal, low-privilege, non-Shipit-session credential level explicitly supported by this engine [10](#0-9) , and (2) crafting a raw HTTP POST to `/webhooks` with a valid HMAC using their own known secret. No Shipit session, `ApiClient` token, or victim repository access is needed, satisfying the "unprivileged attacker" boundary from the rules.

### Recommendation
Bind the verified organization identity to the mutation target: after `verify_signature` succeeds, propagate the authenticated `repository_owner`/organization into the handler dispatch, and require every handler (including `StatusHandler`) to scope its lookup (`Commit`/`Stack`/`Repository`) to that authenticated owner, rejecting/ignoring any event whose `repository.full_name` owner does not match the organization whose secret validated the signature.

### Proof of Concept
Conceptual PoC (cannot be executed in ask-only mode, described for the background engineer):
1. Attacker administers `AttackerOrg`, a GitHub App configured in the shared Shipit `secrets.yml` (multi-org schema) with a webhook secret they know.
2. Attacker crafts a JSON body for a `status` event: `{"sha": "<victim_commit_sha>", "state": "success", "context": "ci/forged", ...}` where `<victim_commit_sha>` is chosen to collide with a commit tracked in `VictimOrg`'s stack (e.g., by reproducing the exact commit content, including identical author/committer/timestamps/parents/message, in an `AttackerOrg`-owned repo).
3. Attacker computes `X-Hub-Signature` using `AttackerOrg`'s own webhook secret and sets `X-Github-Event: status`.
4. `POST /webhooks` — `verify_signature` resolves `Shipit.github(organization: repository_owner)` to `AttackerOrg`'s app and successfully verifies the HMAC (signed with their own secret) [11](#0-10) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [12](#0-11) , matching and updating the commit that actually belongs to `VictimOrg`'s stack — with no check that the commit's stack/repository is owned by `AttackerOrg`.
6. `VictimOrg`'s commit now shows a forged `success` status, potentially satisfying `deployable?` and enabling deploy/merge of that commit.
