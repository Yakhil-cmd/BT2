### Title
Deterministic AA-trigger execution ordering is manipulable via attacker-chosen `level`, enabling unprivileged front-running/profit-stealing in order-matching AAs - (File: main_chain.js, writer.js, validation.js)

### Summary
In Hubble, the exclusive right to *match* orders let a validator insert its own order ahead of a pending liquidation/trade and skim the spread. Ocore has no validator-controlled matching engine, but its AA execution model has an analogous weakness: when several units trigger the *same* AA within one main-chain-index (MCI) batch, the order in which the triggers are executed is decided purely by `ORDER BY units.level, units.unit, address` [1](#0-0) , and `level` is not a network-observed arrival order — it is simply `max(parent levels) + 1`, entirely chosen by whoever authors the unit [2](#0-1) . `validateParents()` does not require parents to be "free"/tip units — it only checks non-conflicting parents and non-retreating timestamp/last_ball [3](#0-2) . Any unprivileged unit author can therefore pick older, shallower (but still valid) parent units to force an artificially low `level` on their own trigger, guaranteeing it is ordered *before* an already-broadcast competing trigger to the same AA in the same batch — a form of consensus-free, permissionless front-running available to any AA trigger sender, without needing to be a witness/order provider.

### Finding Description
AA contracts that implement price/priority-sensitive logic (e.g. an on-chain limit-order/matching contract such as the reference `order_book_exchange.oscript` sample, which lets any two signed orders be matched against each other through a trigger [4](#0-3) ) rely on the *sequence* in which competing AA triggers are processed to decide who gets the better price/liquidity. That sequence is not protected by any consensus or fairness rule: it is simply the ordering of primary triggers collected when an MCI stabilizes:

```
ORDER BY units.level, units.unit, address // deterministic order
``` [1](#0-0) 

`level` is computed for every new unit as `MAX(level of parent_units) + 1` [2](#0-1) . A unit author is free to choose *any* valid, non-conflicting set of parent units — they do not have to be current free/tip units, and `validateParents()` enforces only that timestamps/last_ball do not retreat and that parents are not mutually related [5](#0-4) . This means an attacker who observes a pending (unstable, but already broadcast and thus publicly visible) trigger targeting an order-matching AA can construct their own competing trigger using shallower parents so that its `level` is lower than the victim's trigger, guaranteeing it is executed first once the MCI stabilizes and `handleAATriggers()` runs — even though the victim's unit was created/broadcast earlier.

This is directly analogous to the Hubble H-3 pattern: a party with no special protocol privilege (not a witness, not governance-approved) can unilaterally decide execution order of trades that should be fairly matched between third parties, then insert their own more favorable order ahead of the legitimate match and immediately capture the price difference by trading against the remaining liquidity — exactly the "insert your own order at 1980, then resell at 2000" pattern described in the report, except here it requires no validator role at all, only ordinary unit-posting rights and control over `parent_units`.

### Impact Explanation
Any AA implementing order matching, auctions, or other price/priority-dependent logic on ocore (the platform explicitly ships a sample order-book AA demonstrating this exact pattern) is exposed to unauthorized value extraction: an attacker can systematically win the priority race against honest counterparties' matching triggers and skim the spread that should have gone to them, causing direct fund loss to legitimate users of such AAs. Because this requires no elevated role (unlike Hubble's validator-only privilege), the practical severity is at least as high; anyone able to post units and observe pending unstable units on the network can exploit it repeatedly and cheaply.

### Likelihood Explanation
Constructing a unit with attacker-chosen (older/shallower) parents is fully within the normal capability of any wallet/node — it is not prevented by unit or parent validation, and multiple valid parent sets naturally coexist prior to MCI stabilization. An attacker only needs visibility into a pending, not-yet-stable competing trigger (units are gossiped/visible on the network before their MCI stabilizes) and the ability to select older parents to depress their own unit's `level`. No consensus-breaking or privileged access is required, so likelihood is high wherever an order-priority-sensitive AA is deployed and has any meaningful volume.

### Recommendation
Do not rely on unit `level` (attacker-controllable via `parent_units` selection) as a fairness/priority mechanism for AA trigger execution when multiple triggers target the same AA in the same MCI. Consider tie-breaking/execution-order rules for same-MCI AA triggers that are not manipulable by parent selection (e.g., based on values fixed at broadcast time and validated against the DAG structure, or require AAs implementing matching logic to use commit-reveal / batch-auction designs immune to same-block ordering games), and document to AA authors that `trigger` order within an MCI must not be assumed fair or first-broadcast-first-served.

### Proof of Concept
1. Deploy an order-matching AA analogous to `test/samples/order_book_exchange.oscript`, where any two valid signed orders can be matched via a trigger, price determined by whichever pair of orders is processed [4](#0-3) .
2. Alice and Bob broadcast (but not-yet-stable) `order1`/`order2` trigger units that would fairly match at price P.
3. Attacker Mallory observes Alice's or Bob's pending trigger unit before it stabilizes, and crafts her own trigger unit (matching her own pre-signed order at a slightly better price for her) using deliberately older/shallower `parent_units` (still valid, non-conflicting, satisfying the last_ball/timestamp checks in `validateParents()` [6](#0-5) ) so that `level(Mallory's unit) < level(Alice/Bob's unit)`.
4. When the MCI stabilizes, `handleAATriggers()` selects and orders triggers strictly by `units.level, units.unit, address` [1](#0-0) , so Mallory's trigger executes first and consumes the favorable liquidity/price.
5. Mallory then immediately matches against the remaining counterparty (or resubmits) at the fair price P, pocketing the spread that should have gone to Alice/Bob — reproducing the Hubble H-3 "insert own order ahead of the legitimate match" exploit without any validator/witness privilege.
