### Title
`ci/test` status webhook flips deployability/CI state for any stack sharing a commit SHA, regardless of repository — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` writes a GitHub status onto every `Commit` row matching the raw `sha`, with no scoping by `repository`/`stack`. Because commit SHAs are content-addressed and Shipit stores commits per-stack independently of repository identity, a status webhook that is validly signed for one organization/repository can flip CI state (and thus deployability, via `Commit#create_status_from_github!` → `Status#schedule_continuous_delivery` / `enable_ci_on_stack`) on any other stack whose `commits` table happens to contain a row with the same SHA — including a `review_stacks_enabled: true, allow_all` stack.

### Finding Description
The broken binding the code should enforce is: `status.repository == commit.stack.repository` before the status is attached. Instead: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no `repository`/`stack` filter is applied at all, so the payload's `repository.full_name` (which *is* present in a real `status` webhook payload) is never consulted.

Each matched commit then runs `add_status`/`create_status_from_github!`, which creates a `Shipit::Status` row, calls `enable_ci_on_stack` and `schedule_continuous_delivery` for **that commit's own stack** [2](#0-1) , which can flip `deployable_status`, unblock/trigger continuous deployment jobs (`ProcessMergeRequestsJob`), or mark the stack's required context as failed — all observed in tests where a status transitions `commit.state` and enqueues `ProcessMergeRequestsJob` [3](#0-2) .

Signature verification is scoped by **GitHub organization**, not by repository: `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and HMAC-validates against that org's single `webhook_secret` [4](#0-3) [5](#0-4) . This means the signature check authenticates "this payload came from a repository belonging to organization X," not "this payload came from repository Y." Any repository within the same GitHub organization/App installation (which is exactly the scope `review_stacks_enabled: true, allow_all` targets — auto-provisioned PR-driven stacks in that org, per `OpenedHandler#provision?` [6](#0-5) ) can emit a validly-signed `status` event whose `sha` is crafted/coincides with a commit that also exists in a victim stack's `commits` table (e.g. shared history via fork/rebase within the org, or because the review-stack commit and the base-repo commit are literally the same SHA fetched into both stacks). `StatusHandler` then writes the status cross-stack with no additional check.

This confirms the audited invariant — "a `ci/test` status affects only the repository that authenticated it" — is false at the repository granularity: the actual enforced boundary is organization-level (via `webhook_secret`), not repository-level, and `StatusHandler` performs no per-repository/per-stack filtering of `Commit.where(sha: ...)`.

### Impact Explanation
A repository within the same GitHub App/organization installation as a victim `review_stacks_enabled: true, allow_all` stack can, by emitting a `status` webhook for a shared SHA, write a `failure` status on the victim's commit. Since review stacks auto-execute `shipit.yml` deploy/rollback tasks driven by CI state and continuous-delivery scheduling, this can force deploy/block decisions on a stack the attacker's repository never authenticated for. This is a cross-tenant write (payload for one repository mutating another's stack/commit state) matching the Critical class "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Exploitation requires: (1) a `review_stacks_enabled: true, allow_all` victim stack in the same GitHub organization/App installation as an attacker-controlled repository, and (2) a colliding commit SHA present in both stacks' `commits` tables (achievable via forks/shared history within an org, or repos that mirror/rebase the same commits — a realistic scenario for monorepo-style orgs or repos that are forks of one another). Given those preconditions, the attack is cheap and repeatable: any push to the attacker's own repo that triggers a `status` event for the shared SHA is fully attacker-controlled and requires no Shipit credentials. Uncertainty remains around how reliably an unprivileged attacker can force a genuinely colliding SHA into a specific victim stack's `commits` table without first controlling that stack's ingestion (e.g., via `GithubSyncJob` or `PullRequest` sync) — this repo-boundary weakness is confirmed in code, but the practical SHA-collision setup step is scenario-dependent and not independently traced end-to-end here.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook: resolve `params.repository.full_name`, find the corresponding `Shipit::Repository`, and restrict `Commit.where(sha: params.sha)` to `commits` belonging to stacks under that repository (e.g. `repository.stacks.joins(:commits).where(commits: { sha: params.sha })`), mirroring the repository-scoping already done in `PullRequest::OpenedHandler#repository`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status for a sha does not affect commits belonging to a different repository" do
  repo_a = shipit_repositories(:shipit) # attacker-controlled repo, same org
  repo_b = create(:repository, github_repo_name: 'org/victim-review-target')
  stack_b = create(:stack, repository: repo_b, review_stacks_enabled: true, provisioning_behavior: :allow_all)

  shared_sha = 'a' * 40
  commit_b = stack_b.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  stack_b.required_statuses = ['ci/test']

  # Precondition equality to violate: status.repository (repo_a) != commit_b.stack.repository (repo_b)
  refute_equal repo_a, commit_b.stack.repository

  params = ActionController::Parameters.new(
    sha: shared_sha, state: 'failure', context: 'ci/test',
    repository: { full_name: repo_a.github_repo_name }
  )

  assert_difference -> { commit_b.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.new(params).process
  end

  assert_equal 'failure', commit_b.reload.state
  # Demonstrates a payload authenticated only for repo_a mutated repo_b's stack/commit state.
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
