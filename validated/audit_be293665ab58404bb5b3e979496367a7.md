This confirms the vulnerability. `PushHandler#process` and `CheckSuiteHandler#process` both scope their queries through `stacks` (which is derived from `Repository.from_github_repo_name(repository_name)`, i.e., the repository named in the webhook payload) [1](#0-0) [2](#0-1) . `StatusHandler#process`, by contrast, does not scope by repository at all — it does a global `Commit.where(sha: params.sha)` lookup across the entire database and calls `create_status_from_github!` on every match, regardless of which stack/repository that commit belongs to: [3](#0-2) .

### Title
Cross-tenant forged commit status via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone with no repository/stack scoping, unlike `PushHandler` and `CheckSuiteHandler` which both scope through `stacks` (derived from the payload's `repository.full_name`). Because git commit SHAs are content-addressed and identical across forks that share history, an attacker who owns a repository sharing ancestry with a victim's tracked repository can send a legitimate, signed `status` webhook from their own repo and have Shipit attach the forged `Status` to the victim's `Commit` row and stack.

### Finding Description
The broken binding is: `statuses_and_check_runs consulted by MergeRequest::StatusChecker for repository R's PR == statuses whose stack_id/commit was created by a webhook that GitHub genuinely emitted for repository R`. `StatusHandler#process` violates this: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2)  matches by `sha` globally, ignoring `payload.dig('repository', 'full_name')` entirely (the base `Handler` class does define a `stacks`/`repository_name` scoping helper, but `StatusHandler` never uses it) [4](#0-3) .

`create_status_from_github!` -> `add_status` -> `statuses.replicate_from_github!(stack_id, github_status)` creates the `Status` using `commit.stack_id` — the matched commit's own (victim's) stack — with `state`, `description`, `context`, `target_url` taken verbatim from the attacker-controlled webhook payload [5](#0-4) [6](#0-5) .

`verify_signature` only checks that the payload is signed with the GitHub App credentials configured for `repository_owner` (`params.dig('repository','owner','login')`) [7](#0-6) ; it says nothing about whether the named repository is the one that legitimately owns the commit sha. If the attacker's own repository/org is a valid, Shipit-configured GitHub App organization (a normal precondition for any multi-tenant Shipit install, e.g. multiple repos/teams in one org, or several onboarded orgs), GitHub will happily produce a genuinely signed `status` event for the attacker's own repo. Since commit SHAs are pure hashes of tree+parents+author+committer+timestamps+message, any commit inherited via fork (unmodified history) keeps the exact same SHA in both the attacker's fork and the victim's tracked repository. The attacker can create a commit status via the GitHub API on their own fork (`POST /repos/:owner/:fork/statuses/:sha`) for a SHA that is a real commit already tracked by Shipit under the victim's stack (e.g., the SHA of the victim PR's head or of a shared base commit). GitHub relays this as a normal, correctly-signed `status` webhook. Shipit's `StatusHandler` then attaches the forged `Status` to the victim commit's stack because the lookup is `sha`-only.

`MergeRequest::StatusChecker` (a `Status::Group` subclass) consumes `head.statuses_and_check_runs` [8](#0-7) , and `Commit#statuses_and_check_runs` is simply `statuses + check_runs` with no per-status provenance check [9](#0-8) . If the forged status has `state: 'success'` and a `context` that either matches a `required_statuses` entry or is simply an additional passing status, it can flip `all_status_checks_passed?`/`any_status_checks_missing?` for the victim's PR, and it is also indistinguishable pollution of the merge decision data model — none of `verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema validation, or model validations on `Status`/`Commit` check that the reporting repository matches the commit's owning stack.

### Impact Explanation
An attacker can inject an arbitrary, attacker-authored `Status` (state/context/description of their choosing) onto any commit tracked by any Shipit stack, as long as that commit's SHA also exists in a repository the attacker controls (trivial for any commit inherited via fork without rebase — i.e., most historical/base commits of public repos). This directly corrupts `MergeRequest#all_status_checks_passed?`/`any_status_checks_missing?`/`any_status_checks_failed?`, letting an attacker either force a false "success" status to help auto-merge a PR that shouldn't be mergeable, or force a false "failure"/pending status to deny/stall merges on a victim's repository — a payload from one repository (or tenant) mutating another repository's/stack's/commit's merge-readiness data. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." It is repeatable against any tracked commit whose SHA the attacker can reproduce, across arbitrary victim stacks within the same multi-tenant Shipit installation.

### Likelihood Explanation
Preconditions: the victim repository must already be tracked as a Shipit stack (commits ingested), the attacker must control a repository (their own fork or unrelated repo) sharing an identical commit SHA with a commit tracked in the victim stack, and that attacker-controlled repository must be one for which Shipit's webhook signature verification succeeds (i.e., a repo whose owning org/organization is configured in Shipit — a routine situation in shared, multi-tenant/multi-org Shipit deployments, and even simpler if the attacker's own fork lives under the same org as the victim). No Shipit session, API token, or GitHub secret is required; the attacker only needs ordinary push/fork rights on their own repository and the ability to call GitHub's standard `statuses` API on their own repo, both unprivileged capabilities. This is highly feasible and repeatable at will.

### Recommendation
Scope `StatusHandler#process` to the reporting repository, mirroring `PushHandler`/`CheckSuiteHandler`: resolve `stacks` from `payload.dig('repository', 'full_name')` and only update/create statuses for commits belonging to `stacks.commits` (or otherwise verify `commit.stack.repository.full_name == repository_name` before calling `create_status_from_github!`), rejecting matches where the reporting repository does not own the target commit's stack.

### Proof of Concept
minitest (`test/models/shipit/webhooks/handlers/status_handler_test.rb`), no live GitHub:
```ruby
test "status from an unrelated repository is not attached to a victim commit" do
  victim_commit = shipit_commits(:first) # belongs to stack A / repo "acme/victim"
  # Simulate attacker-controlled repository sharing the same sha (forked history)
  forged_payload = ExplicitParameters::Parameters.define do
    requires :sha, String
    requires :state, String
    accepts :description, String
    accepts :context, String
  end.parse!(
    'sha' => victim_commit.sha,
    'state' => 'success',
    'description' => 'forged by attacker',
    'context' => 'attacker/ci',
    'repository' => { 'full_name' => 'attacker/evil-fork' }
  )

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.new(forged_payload.to_h).process
  end

  forged_status = victim_commit.statuses.last
  assert_equal 'attacker/ci', forged_status.context
  assert_includes victim_commit.reload.statuses_and_check_runs, forged_status

  merge_request = shipit_merge_requests(:first) # head == victim_commit, stack A
  checker = Shipit::MergeRequest::StatusChecker.new(
    merge_request.head, merge_request.head.statuses_and_check_runs, merge_request.stack.cached_deploy_spec
  )
  assert checker.success?, "forged cross-repo status flipped merge readiness for victim's PR"
end
```
Equality asserted before: `victim_commit.statuses_and_check_runs` contains only statuses genuinely reported for `acme/victim`. Equality asserted after: it now also contains a `Status` whose reporting `repository.full_name` (`attacker/evil-fork`) never matched `acme/victim`, and `StatusChecker#success?` becomes `true` solely because of that forged entry — demonstrating the binding is broken.
