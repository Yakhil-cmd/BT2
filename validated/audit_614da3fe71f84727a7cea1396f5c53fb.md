### Title
Webhook signature verification organization is chosen from unauthenticated payload data, decoupling the signing organization from the repository actually written - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification by reading an untrusted field straight out of the still-unverified JSON body, instead of deriving it from any already-authenticated context. Because Shipit explicitly supports multiple GitHub Apps/organizations, each with its own `webhook_secret` (`lib/shipit/github_app.rb`, `test/dummy/config/secrets_double_github_app.yml`), an attacker who legitimately controls one onboarded organization ("Org A", with a real `webhook_secret` they can compute HMACs with) can forge a payload whose `repository.owner.login` says "Org A" (so verification passes with Org A's secret) while embedding a different `repository.full_name`/nested data that downstream handlers use to identify the repository/stack that actually gets written to.

and `repository_owner` is computed purely from attacker-controlled JSON, before any signature has been checked: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a distinct `GithubApp` instance per organization, each carrying its own independent `webhook_secret`: [3](#0-2) [4](#0-3) 

The test fixtures confirm multiple organizations can be configured with different `webhook_secret`/app credentials simultaneously (`OrgOne`/`OrgTwo` style setup): [5](#0-4) 

The verification step only proves "this byte-for-byte payload was HMAC-signed by whichever organization's secret matches the `repository.owner.login`/`organization.login` field inside the payload itself." It does **not** prove that the repository/stack subsequently identified and mutated by the event handlers (which use `repository.full_name`, e.g. via `Repository.from_github_repo_name`) belongs to that same authenticated organization: [6](#0-5) 

Because the org used to pick the verifying secret (`repository.owner.login`) and the repository actually acted upon (`repository.full_name`, split into owner/name inside the handlers) are two independently attacker-supplied fields of the same unsigned-at-read-time JSON body, nothing forces them to refer to the same organization. An attacker who is a legitimate member/admin of "Org A" (and therefore knows Org A's real `webhook_secret`, since GitHub App webhook secrets are configured/known to whoever set up that org's installation) can sign an arbitrary crafted JSON body with Org A's secret while setting `repository.full_name` to `"OrgB/some-repo"`. The request passes `verify_signature` (HMAC matches Org A's secret over the exact bytes sent), then `create` dispatches the same JSON to handlers (push, status, check_suite, membership, pull_request) which trust `repository.full_name`/`organization.login` fields to locate or create `Repository`/`Stack`/`Commit`/`Membership` records under Org B, an organization the attacker never authenticated for.

### Impact Explanation
This breaks the intended binding: `organization whose secret authenticated the request == organization whose repository/stack data gets mutated`. Depending on event type this enables cross-repository/cross-organization writes inside Shipit's database that were never authorized by Org B: fabricating commit `status` records (`app/models/shipit/webhooks/handlers/status_handler.rb`, confirmed present in the handlers directory) that can flip a commit to "success" and unlock deploy gating for a stack belonging to Org B, injecting fake `check_suite` results, or creating `Membership`/`Team`/`User` records for Org B (confirmed handler exists: `membership_handler.rb`). Falsifying CI/status signals that gate deploys is a direct path to an unauthorized deploy of code the attacker does not control, and forging membership records affects `Shipit.github_teams` authorization decisions used elsewhere in the app (`app/models/shipit/user.rb#authorized?`). This satisfies the Critical/High bar: cross-repository writes and escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
Requires only that the attacker control (or be an authorized operator of) any single organization/GitHub App already onboarded into the same Shipit instance — no Shipit session, `ApiClient` token, or GitHub App private key theft is needed, since `webhook_secret` is a value the org's own admin legitimately possesses. The webhook endpoint is unauthenticated by design (that's its purpose) and only gated by this per-org signature check, so the only barrier is exactly the check being bypassed by this field confusion.

### Recommendation
Do not let handlers trust any organization/repository identifying field from the JSON body that was not the same field used to select the verifying secret. Concretely: after selecting `github_app` via `repository_owner` and verifying the signature, re-derive/validate that every organization-identifying field consumed later by handlers (`repository.full_name`'s owner segment, `organization.login`, etc.) is identical to `repository_owner`; reject (422) on mismatch. Alternatively, bind webhook verification to a per-installation identifier (e.g., GitHub App installation ID resolved server-side) rather than to an attacker-suppliable login string.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with a distinct GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker is a legitimate admin of `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a JSON body for a `status` (or `push`/`membership`) event where:
   - `repository.owner.login` = `"OrgA"` (so `WebhooksController#repository_owner` picks OrgA's `GithubApp`, whose secret the attacker knows)
   - `repository.full_name` = `"OrgB/victim-repo"` (or `organization.login` = `"OrgB"` for the membership handler)
4. Attacker computes `X-Hub-Signature` as `sha1=` HMAC-SHA1 over the raw body using `OrgA`'s `webhook_secret` and POSTs to `/webhooks`.
5. `verify_signature` succeeds (`Shipit.github(organization: 'OrgA').verify_webhook_signature` returns true).
6. `create` dispatches the parsed body to the relevant handler, which resolves/creates a `Repository`/`Stack`/`Commit`/`Membership` record scoped to `OrgB` using `repository.full_name`/`organization.login`, without any check that `OrgB == OrgA` (the organization that actually signed the request). # frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
