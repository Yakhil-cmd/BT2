### Title
Unprivileged stakers can be stripped of reward lamports via unrestricted `UpdateCommissionBps` "commission sandwich" - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The `UpdateCommissionBps` vote instruction (SIMD-0291/SIMD-0123) lets a vote account's `authorized_withdrawer` change the commission rate applied to inflation and block-revenue rewards with no timing restriction whatsoever, unlike the legacy `UpdateCommission` path. This mirrors the FERC1155 report's core flaw: a single privileged party controls a fee parameter that is applied against unprivileged counterparties (there, secondary-market buyers/sellers; here, delegated stakers), and can flip it to an extreme value immediately before value changes hands and revert it right after.

### Finding Description
`update_commission` (legacy, percentage-based) enforces `is_commission_update_allowed`, restricting commission increases to the first half of an epoch and gating the rest via the `delay_commission_updates` feature, which forces `redeem_delegation_rewards` to read the commission from a prior-epoch snapshot (`snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts`) rather than the live value. [1](#0-0) [2](#0-1) 

By contrast, `update_commission_bps` explicitly documents and implements **no such rule**: "No commission update rule, per SIMD-0249 and SIMD-0291," for both `CommissionKind::InflationRewards` and `CommissionKind::BlockRevenue`. The only check is that the current `authorized_withdrawer` signs. [3](#0-2) 

The reward-splitting math itself has no cap enforcement beyond clamping to 10,000 bps (100%), so an authority can instantaneously set commission to 100%, capturing the entire reward for a redemption cycle, then set it back to its prior low value: [4](#0-3) 

The epoch-delay protection that guards the legacy path is implemented as commission lookups keyed off `delay_commission_updates`; whether/if the same delayed-lookup protection is applied to the `block_revenue_commission_bps` path used by `calculate_block_reward` for block-reward distribution could not be confirmed from the sections inspected — that reward path is computed separately from `redeem_delegation_rewards` in `calculate_stake_rewards_and_commissions`. [5](#0-4) 

### Impact Explanation
If a vote account's `authorized_withdrawer` sets `inflation_rewards_commission_bps` or `block_revenue_commission_bps` to a high value (up to 10,000 bps = 100%) immediately before the relevant reward calculation/distribution and reverts it afterward, the split functions `commission_split`/`commission_split_preserve_lamports` will award all or nearly all of the reward lamports to the vote/commission account instead of the delegating stakers, permanently misattributing lamports away from unprivileged stakers — the same fee-frontrunning primitive described in the FERC1155 report, applied to Agave's vote/reward-distribution path.

### Likelihood Explanation
Exploitation requires only that the attacker controls a vote account's `authorized_withdrawer` key (a normal, permissionless capability any operator can hold, no special validator-consensus role is needed to trigger the instruction) and times the `UpdateCommissionBps` calls around the epoch's reward-calculation slot. Since the instruction imposes no cooldown, cap, or same-epoch restriction, the only barrier to exploitation is whether the `delay_commission_updates`-style lookback is actually wired into the `block_revenue_commission_bps` reward path — a detail not confirmed in the inspected code.

### Recommendation
Apply the same prior-epoch commission snapshot lookup (or an equivalent minimum-delay/cap mechanism) used for legacy `commission()`/`inflation_rewards_commission_bps` to `block_revenue_commission_bps`, and/or reinstate a same-epoch increase restriction for `UpdateCommissionBps` so that no commission-rate change can affect a reward distribution computed within the same delay window it was set in.

### Proof of Concept
Not independently reproduced; based on static analysis of `update_commission_bps` (`programs/vote/src/vote_state/mod.rs:827-859`), `commission_split_preserve_lamports` (`runtime/src/inflation_rewards/mod.rs:413-435`), and the commission lookup logic in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:701-724`. Full confirmation of exploitability (specifically whether `block_revenue_commission_bps` reward payouts have equivalent delay protection) requires further code review beyond what indexing coverage exposed here; a Devin session with full repo access would be needed to trace `calculate_block_reward` and confirm whether any delay/cap applies to the `BlockRevenue` commission kind.

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

fn commission_split_preserve_lamports(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let staker_bps = MAX_BPS
                .checked_sub(split)
                .expect("commission cannot be greater than MAX_BPS");
            let staker_rewards = u128::from(on)
                .checked_mul(u128::from(staker_bps))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let staker_rewards = staker_rewards as u64;
            let voter_rewards = on
                .checked_sub(staker_rewards)
                .expect("staker rewards cannot exceed total rewards");

            (voter_rewards, staker_rewards, true)
        }
    }
}
