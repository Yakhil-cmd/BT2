## Title
Merkle leaf/internal-node hash collision (no domain separation) in `merkle.js` allows forging membership in `is_valid_merkle_proof` used by AAs - (File: `merkle.js`, `formula/evaluation.js`)

### Summary
`merkle.js` computes both leaf hashes and internal-node hashes with the exact same one-argument SHA256 function, with no prefix/domain separator distinguishing a leaf from an internal node. This is the classic "node-as-leaf" second-preimage weakness (CVE-2012-2459-style) referenced in the original report. Since AA (Autonomous Agent) bytecode can call `is_valid_merkle_proof(element, proof)` with **both `element` and `proof` fully attacker-controlled** (e.g. from `trigger.data`), an unprivileged AA trigger sender can forge a "membership proof" for an arbitrary string against a legitimate Merkle root that was never actually included as a leaf, by using two known sibling hashes concatenated together as the fake leaf.

### Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree using a single hash function for everything: [1](#0-0) 

Internal nodes are computed as `hash(arrHashes[i] + arrHashes[hash2_index])` — a direct concatenation of two children hashes, hashed the same way a leaf `hash(element)` is computed: [2](#0-1) 

`verifyMerkleProof` walks the same undifferentiated hash chain from the supplied `element` up through `proof.siblings` to the claimed `root`, with an explicit acknowledgement of this exact class of bug in the code comment ("Node-as-Leaf issue might matter in some cases"): [3](#0-2) 

This primitive is exposed directly to oscript/AA authors via the `is_valid_merkle_proof(element, proof)` formula function. Both `element` and `proof` are evaluated from arbitrary expressions (which in AA definitions typically come from `trigger.data`, i.e. fully attacker-controlled), and the only constraint enforced is on the syntactic shape of the proof, not on whether the "element" is a genuine data leaf versus a forged concatenation of two internal hashes: [4](#0-3) 

Because `hash(element)` for a leaf and `hash(leftHash + rightHash)` for an internal node use identical hashing with no domain tag (e.g. `0x00`/`0x01` prefix), an attacker who knows any two sibling hash strings anywhere in the tree (which are visible in any legitimate proof, or in a published data structure) can submit:
- `element` = `leftHash + rightHash` (the raw concatenation string)
- `proof` = the real proof truncated to start one level above that pair (i.e., skipping the lowest level, reusing the remaining siblings up to the root)

`verifyMerkleProof` will then compute `hash(element)` which collides exactly with the true internal node's hash, and the remaining chain will correctly reconstruct the real root — validating a "leaf" that was never actually part of the original dataset.

The same undifferentiated hashing is also used by the `"in merkle"` address-definition authentifier via `merkle.deserializeMerkleProof`/`merkle.verifyMerkleProof`, though there the `element` is fixed at definition-creation time by the address owner rather than attacker-controlled at spend time: [5](#0-4) 

### Impact Explanation
Any AA that implements a Merkle-based whitelist, airdrop, or prize/reward claim scheme using `is_valid_merkle_proof(trigger.data.element, trigger.data.proof)` against a fixed or oracle-published root is exposed to unauthorized fund release: an attacker (an ordinary AA trigger sender) can forge a proof of "membership" for an address/amount pair that was never actually committed in the tree, exactly mirroring the referenced `claimEthPrize` drain scenario. This is a concrete path to AA fund loss/drainage, not merely a resource or availability issue.

### Likelihood Explanation
Exploitability depends entirely on AA design: any AA author who builds a claim/whitelist mechanism on top of `is_valid_merkle_proof` (a documented, first-class oscript primitive intended for exactly this kind of use case per `test/formula.test.js`) is affected, and the attack requires no special privilege — only knowledge of two sibling hashes from the published tree, which are trivially obtainable from any single legitimate proof or from the tree's public leaves. This makes exploitation practical for a common AA pattern (Merkle airdrops/whitelists), even though the base `ocore` protocol itself doesn't use `is_valid_merkle_proof` for a monetary claim.

### Recommendation
Add domain separation in `merkle.js`: hash leaves with a distinct prefix (e.g., `hash("0" + element)`) and internal nodes with another (e.g., `hash("1" + left + right)`), and update `verifyMerkleProof`/`getMerkleProof`/`getMerkleRoot` consistently so leaf hashes cannot collide with internal-node hashes. This mitigation must ship as a protocol/formula-behavior change guarded by an MCI/version flag (similar to `bPostPemCurvesFix`) to avoid breaking existing deployed Merkle trees and AAs.

### Proof of Concept
1. Build a small tree, e.g. 4 leaves `L0..L3`, with `H0=hash(L0)`, `H1=hash(L1)`, `H2=hash(L2)`, `H3=hash(L3)`, and root `R = hash(hash(H0+H1) + hash(H2+H3))`.
2. Obtain any legitimate proof for `L0` (or just know `H0, H1, H2, H3` from the published tree data): siblings = `[H1, hash(H2+H3)]`, index 0.
3. Craft a forged claim: `element' = H0 + H1` (raw string concatenation of the two child hashes at level 0), `proof' = { index: 0, siblings: [hash(H2+H3)], root: R }` (one level shallower, using only the level-1 sibling).
4. Call `merkle.verifyMerkleProof(element', proof')` (or `is_valid_merkle_proof(element', proof')` from an AA trigger): `hash(element')` collides with `hash(H0+H1)`, and combining with `hash(H2+H3)` reproduces `R`, so the function returns `true` even though `element'` was never one of `L0..L3`.
5. In an AA that trusts `is_valid_merkle_proof` output to authorize a payout keyed by the "leaf" content (address/amount), the attacker substitutes `element'` encoding their own address and an inflated amount, draining the AA.

function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
