### Title
Cross-organization commit-status/repository forgery via webhook signature not binding to acted-upon repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a GitHub webhook against using the organization named in the payload's own `repository.owner.login` field, but the handlers that subsequently act on the payload (`StatusHandler`, `PushHandler`, and the `PullRequest` handlers) use a different field — `repository.full_name` (or, for `StatusHandler`, no repository field at all) — to decide which commit/stack is written to. Because both fields are attacker-controlled inside the same signed body, an attacker who legitimately administers *any* single GitHub organization onboarded to this Shipit instance (and therefore knows that organization's `webhook_secret`, since they configured the GitHub webhook themselves) can forge a payload that authenticates as their own organization while acting on a completely different, victim organization's repository/commit.

### Finding Description
`verify_signature` computes the signing organization purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `webhook_secret` configured for that specific organization and verifies the raw POST body's `X-Hub-Signature` against it. If it matches, the *entire* raw body — including any other field — is treated as authentic and handed unmodified to the event handlers: [3](#0-2) 

Downstream, handlers do not re-derive or cross-check the organization used for signing against the repository they act on:

- `Handler#stacks`/`#repository_name` resolves the target repository from `payload.dig('repository', 'full_name')`, a field completely independent from `repository.owner.login` used for signing: [4](#0-3) 
- `StatusHandler#process` is even weaker: it does not scope by repository/organization at all, matching purely on commit SHA across the entire database: [5](#0-4) 
- `PushHandler#process` resolves stacks via the same unchecked `full_name` and directly triggers a GitHub sync with an attacker-supplied `expected_head_sha`: [6](#0-5) 

The trust binding that should hold is:
`organization that authenticated the request (repository.owner.login → webhook_secret)` == `organization/repository that is written to (repository.full_name / commit sha lookup)`

Because both values are supplied inside the same attacker-crafted JSON body, and only the former is covered by the signature-selection logic (not cryptographically bound to the latter), this equality can be broken: an attacker sets `repository.owner.login` to an organization they administer (to pass HMAC verification with a secret they know) while setting `repository.full_name` (or, for `status` events, an arbitrary `sha`) to point at a victim organization's stack/commit.

### Impact Explanation
Once the forged, "verified" payload is dispatched to handlers:
- Via `status`, the attacker can inject a fabricated CI status (e.g., `state: success`) onto any commit SHA tracked by any stack on the instance, regardless of which organization owns it, since `Commit.where(sha: params.sha)` performs no repository/organization scoping.
- Via `push`, the attacker can force `stack.sync_github(expected_head_sha:)` on a stack belonging to another organization's repository, since `stacks` is resolved from the unchecked `repository.full_name`.

Because Shipit uses commit statuses/checks to gate whether a commit is deployable, forging a passing status on a victim's commit can be used to make an otherwise-blocked commit appear deployable, i.e., to bypass required CI checks and enable an unauthorized deploy — this crosses the Critical bar ("an unauthorized deploy"). At minimum it allows an authenticated-to-their-own-org attacker to write cross-organization state (commit statuses, sync triggers) they should have no authority over.

### Likelihood Explanation
This requires the attacker to control (or own) at least one GitHub organization/repository that is legitimately onboarded to the same Shipit instance, since they must know that organization's real `webhook_secret` (which they themselves configure when wiring up the GitHub webhook for their own org). No Shipit session, API token, or `github_access_token` theft is required — only the ability to send a raw HTTP POST to the shared `/webhooks` endpoint with a validly-signed-for-their-own-org, but internally inconsistent, JSON body. This is a realistic scenario for any Shipit deployment shared across multiple organizations/teams, which is an explicitly supported configuration (`Shipit.github(organization:)` is keyed per-org).

### Recommendation
After signature verification, re-derive the organization strictly from the same `repository.owner.login`/`organization.login` value used to select the verification secret, and enforce that every field the handlers act upon (`repository.full_name`, and for `status` events, the commit's owning repository) belongs to that same, verified organization before performing any lookup or mutation. For `StatusHandler` specifically, scope the `Commit` lookup by the verified repository, not by SHA alone.

### Proof of Concept
1. Attacker legitimately owns/administers GitHub organization `attacker-org`, which is configured in this Shipit instance with `webhook_secret = S`.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha-in-other-org>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` using their known secret `S`.
4. POSTs to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `webhook_secret = S`, and the signature check passes: [7](#0-6) 
5. `StatusHandler#process` then matches `Commit.where(sha: params.sha)` — the victim's commit — and records a fabricated successful status on it: [5](#0-4)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
