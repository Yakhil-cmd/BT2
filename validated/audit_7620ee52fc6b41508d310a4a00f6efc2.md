### Title
Cross-organization webhook forgery via mismatch between the signature-verifying organization and the repository actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App deployment (as documented in `config/secrets.development.example.yml`, which supports one `webhook_secret` per organization), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify the HMAC against using a payload field, while the handlers that actually mutate state use a *different* payload field to decide which repository/stack to act on. Because both fields live in the same signed body, an attacker who controls (or has compromised) the webhook secret of *any one* configured organization can forge a validly-signed webhook whose "owning" organization is the one they control, but whose "target repository" field points at a stack belonging to a different, unrelated organization.

### Finding Description
`verify_signature` computes the organization used to pick the verification secret directly from attacker-supplied payload content, before the signature has been checked: [1](#0-0) [2](#0-1) 

```
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This looks up `Shipit.github(organization: repository_owner)` and verifies the raw body against **that** organization's `webhook_secret`: [3](#0-2) 

However, once the signature check passes, the actual event handlers (e.g. `PushHandler`, `StatusHandler`) resolve the target `Repository`/`Stack` using a *different* field of the same JSON body — `repository.full_name` — via `Handler#stacks`/`Handler#repository_name`: [4](#0-3) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` splits `owner/name` from this field and looks up the local `Repository` record purely by string match, with no re-check that `owner` here matches the `repository.owner.login` used for signature verification: [5](#0-4) 

Equality that should hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login / organization.login)` **≠** `repository actually written by the handler (repository.full_name)`.

Concretely: `repository.owner.login` and `repository.full_name`'s owner segment are two independently attacker-suppliable strings inside the same JSON body. Nothing forces `repository.full_name.split('/').first == repository.owner.login`. An attacker who legitimately administers (or has otherwise obtained the webhook secret for) organization `evil-org` — which is one of the organizations configured in Shipit's multi-org `github:` credentials block — can send a POST to `/webhooks` where:
- `repository.owner.login = "evil-org"` (so `verify_signature` picks `evil-org`'s secret and the HMAC, computed with that secret, is valid), but
- `repository.full_name = "victim-org/some-tracked-repo"` (so the handler resolves and mutates the `victim-org/some-tracked-repo` `Stack`).

### Impact Explanation
This breaks the trust boundary between organizations that Shipit's multi-org GitHub App model is meant to enforce: each organization's webhook secret should only authorize writes to that organization's own repositories/stacks. Exploiting this allows an attacker who controls one onboarded organization's webhook secret to forge `push`, `status`, `check_suite`, `membership`, or `pull_request` events against a completely different organization's stacks — e.g., calling `stack.sync_github(expected_head_sha:)` on `PushHandler`, injecting fabricated commit statuses via `StatusHandler`, or manipulating check-run/PR state used to gate deploy safety checks. This is a cross-repository/cross-organization write achieved purely by exploiting the signature-organization vs. acted-repository mismatch — matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
This requires the deployment to be configured with multiple GitHub organizations (a documented, supported configuration — see `config/secrets.development.example.yml`), and requires the attacker to control/possess one configured organization's `webhook_secret` (e.g. as the legitimate owner/admin of their own onboarded org, or via leaking that specific org's secret). It does not require any Shipit session, `ApiClient` token, or GitHub App private key — only the ability to send an HTTP POST with a validly-HMAC-signed body for the org they control. In single-organization deployments this analog does not apply since there is only one secret and the ambiguity disappears in practice (any signature valid for the sole org will match its own repos anyway) — but multi-org configurations are explicitly documented and supported.

### Recommendation
After `verify_signature` succeeds, re-derive and enforce that the organization whose secret validated the signature matches the owner segment of `repository.full_name` (or `organization.login`) actually used by the handler, rejecting the webhook (422) on mismatch. Alternatively, have `Handler#repository_name`/`stacks` scope lookups to `Repository.where(owner: verified_organization)` rather than trusting an independent payload field.

### Proof of Concept
1. Configure Shipit with two organizations, `evil-org` and `victim-org`, each with its own `webhook_secret` (per the documented multi-org config format in `config/secrets.development.example.yml`).
2. Attacker, who controls `evil-org`'s webhook secret, crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "evil-org" },
       "full_name": "victim-org/tracked-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(evil-org_webhook_secret, raw_body)>` and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "evil-org")` (from `repository.owner.login`) and successfully verifies the signature against `evil-org`'s secret.
5. `PushHandler#process` resolves `repository_name` as `"victim-org/tracked-repo"` and calls `stack.sync_github(expected_head_sha: params.after)` on `victim-org`'s stack — a write the attacker had no authorization to trigger, using only `evil-org`'s credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
