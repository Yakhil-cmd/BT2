### Title
Uncaught `throw Error(...)` in `countVotes()` during governance parameter tallying can crash/halt nodes at MC stabilization - ([File: main_chain.js])

### Summary
The CometBFT advisory describes a chain halt caused by insufficiently validated governance-driven parameter changes: a validator-approved parameter update reaches consensus-critical code that then panics, taking down nodes at a deterministic height. `ocore`'s analog is the on-chain governance vote-counting mechanism for system parameters (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`). The counting function `countVotes()` in [1](#0-0)  is invoked synchronously as part of main-chain stabilization when a `system_vote_count` message becomes stable, and it contains several unconditional `throw Error(...)` statements that fire based on the aggregate on-chain vote state rather than on data any single node can locally fix. Because every full node executes `countVotes()` deterministically while advancing the stable MC index, a data condition that trips one of these `throw` paths will crash/halt every synced node at the same MCI - the same failure shape as the reported CometBFT bug.

### Finding Description
`system_vote` and `system_vote_count` messages are unprivileged messages that any address with a positive balance can post [2](#0-1) . Once a `system_vote_count` unit becomes stable, `countVotes()` is executed as part of MC stabilization to tally votes and set the new system parameter value into `storage.systemVars` and the `system_vars` table [3](#0-2) .

Inside `countVotes()`, several code paths use `throw Error(...)` instead of returning a graceful/transient error:
- `throw Error(`no votes for subject ${subject}`)` if no `first_vote_row` exists once `mci >= constants.pemCurvesFixMci` [4](#0-3) .
- `throw Error(`wrong number of voted OPs: ` + ops.length)` if the number of aggregated top `op_address` rows for `op_list` is not exactly `constants.COUNT_WITNESSES` [5](#0-4) .
- `throw Error(`no median value for ` + subject)` if the accumulated-balance loop for numerical subjects (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) never reaches the `total_voted_balance / 2` threshold [6](#0-5) .
- `throw Error(`no MC unit on just stabilized MCI ` + mci)` / `throw Error(`no MC unit on OP vote activation MCI ` + constants.v4UpgradeMci)` [7](#0-6) .

The validation layer for `system_vote` (validation.js) only checks the *shape* of an individual vote message (e.g., `op_list` must have exactly `COUNT_WITNESSES` addresses sorted and unique, `threshold_size >= 1000`, TPS-related numeric bounds) [8](#0-7) . It does not, and cannot, validate the *aggregate* outcome of tallying many independently-posted votes across many addresses and asset balances at count time. This is structurally identical to the CometBFT bug class: individual proposal/vote objects pass local validation, but the code path that later applies/aggregates the accepted change (here, `countVotes`) can reach a state that was never defensively handled, and instead of degrading gracefully it throws.

Because `countVotes` is `async` and is invoked from the deterministic MC-stabilization pipeline (triggered for every node once the relevant `system_vote_count` unit becomes MC-stable), an uncaught exception here becomes an unhandled promise rejection / thrown error inside the write path shared by all nodes converging on the same MC index. Since Node.js processes typically terminate on unhandled exceptions/rejections in this kind of codebase (see the repo's own pattern of `throwError()` invoking `throw` for supposed-unreachable invariants elsewhere, e.g. [9](#0-8) ), any of these three conditions is capable of crashing every full node that reaches that MCI — a synchronized, height-triggered chain halt, exactly mirroring the reported CometBFT `VoteExtensionsEnableHeight` validation gap.

### Impact Explanation
If a set of unprivileged addresses casts `system_vote` messages such that:
- for `op_list`: the top-`COUNT_WITNESSES` aggregation by summed balance produces fewer than `COUNT_WITNESSES` distinct `op_address` rows with nonzero recorded votes at the time `system_vote_count` stabilizes (e.g., votes are split so fewer than 12 distinct OP addresses have any recorded balance-weighted vote in the counting window), or
- for numerical subjects: floating aggregate balances/rounding leave the accumulated sum never reaching exactly `total_voted_balance / 2` (an off-by-one/rounding edge case, since the comparison is `>=` over floating/decimal sums built from potentially large balances) — 

then every node executing `countVotes()` at that MCI throws an uncaught `Error`, halting main-chain progress network-wide. This matches the "network unable to confirm new units" / "node disagreement on validity or stability" impact bar: the chain stops advancing past that MCI for all synced nodes simultaneously, requiring an out-of-band software fix and coordinated restart — the same soft-halt scenario CometBFT patched.

### Likelihood Explanation
Triggering `system_vote` / `system_vote_count` requires only posting standard, unprivileged units (any address with a balance can vote; anyone can send `system_vote_count`) once voting for system params is enabled (`last_ball_mci >= constants.v4UpgradeMci`, already active given `v4UpgradeMci` values in `constants.js` [10](#0-9) ). No governance approval beyond ordinary balance-weighted voting is needed, and the aggregation edge cases (ties/rounding at the vote-count boundary, or fewer than 12 distinct OP addresses receiving any balance-weighted vote) are realistically reachable by a modest number of addresses splitting votes, especially since `op_rows` only returns rows with `total_balance` for names that appear in `op_votes`/`op_votes_tmp` — if turnout is low or fragmented, `ops.length !== constants.COUNT_WITNESSES` is easily hit.

### Recommendation
Replace the unconditional `throw Error(...)` statements in `countVotes()` (main_chain.js, lines ~1784-1791, ~1794-1799, ~1860-1862, ~1900-1901) with defensive fallback logic that cannot crash the node: e.g., if the tally does not produce a valid new value (wrong OP count, no median found), keep the previous `storage.systemVars[subject]` value unchanged (skip updating `system_vars` for this vote-count event) and log a non-fatal warning via `eventBus.emit('nonfatal_error', ...)`, matching the pattern already used elsewhere in the file (`throwError()` at main_chain.js:1965-1971) but without actually calling `throw` on data-dependent branches. Additionally, add explicit validation in `validation.js`'s `system_vote_count` handling to pre-check, where feasible, that a countable outcome is likely (though full aggregate validation before count time is not generally possible, since it depends on final vote/balance state at MC stabilization time).

### Proof of Concept
1. Deploy/observe a live network where `v4UpgradeMci` is active (already the case per `constants.js`).
2. Have a set of unprivileged addresses each post a valid, well-formed `system_vote` unit for `subject: "op_list"`, splitting their `arrOPs` choices such that no single 12-address slate accumulates a top-12 ranked count of exactly `constants.COUNT_WITNESSES` distinct addresses with any recorded balance-weighted votes (e.g., total distinct addresses voted-for across all voters is fewer than 12, or ties truncate the `LIMIT ?` result below 12).
3. Post a valid `system_vote_count` unit with `payload: "op_list"`.
4. Once this unit's MCI stabilizes, every node calls `countVotes(conn, mci, "op_list")`, reaches `main_chain.js:1860-1862`, finds `ops.length !== constants.COUNT_WITNESSES`, and throws — crashing/halting all nodes that reach this MC-stabilization step at the same time. (Exact reproduction requires a testnet/devnet due to the balance/turnout thresholds involved, but the code path is deterministic and reachable purely with unprivileged unit posting.)
