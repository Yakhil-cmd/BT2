### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but every event handler resolves the target `Repository`/`Stack` from the independent `repository.full_name` field, allowing cross-organization status/webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
The bug report's pattern is a role permitted for one binding (Cloner-only transfer) silently extended to actors bound to a different, unintended context (Custodian/Minter transferring based on ownership rather than role). The analogous break in `shipit-engine` is that the webhook signature check authenticates the **organization** derived from one payload field (`repository.owner.login` / `organization.login`), while the code that decides **which repository/stack is actually written to** reads a different, independently attacker-controlled payload field (`repository.full_name`). The signature never covers the equality "organization verified == repository written."

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/org config and validates the HMAC using only the `repository_owner` value: [1](#0-0) [2](#0-1) 

Downstream, every handler (`PushHandler`, `PullRequest::*Handler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the `Repository`/`Stack` to mutate purely from `payload.dig('repository', 'full_name')`, a completely separate JSON field never covered by the signature computation over `repository_owner`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` additionally short-circuits to `true` whenever no `webhook_secret` is configured for that organization: [4](#0-3) 

Shipit explicitly supports multiple organizations configured side by side, each with its own (optional) `webhook_secret`: [5](#0-4) 

Because `repository_owner` (used only to select/verify against an org's secret) and `repository.full_name` (used to pick the actual `Repository`/`Stack`) are independent fields in the same JSON body, an attacker who can produce a validly-signed request for **any one** configured organization (e.g., one they administer, or one whose `webhook_secret` is left blank per the "optional" setup docs) can set `repository.full_name` to point at a **completely different** organization's repository/stack. The signature-verified identity ("org A's webhook is authentic") is decoupled from the entity actually acted upon ("write to org B's stack"), exactly mirroring the cloned-pet bug: the verified authority (Cloner role / organization A signature) doesn't match the entity actually moved (the clone owned elsewhere / repository belonging to organization B).

### Impact Explanation
This breaks the binding `organization authenticated == repository written`, matching the report's out-of-scope-but-adjacent High-impact category: "escalation into `Shipit.github_teams` authorization" is not directly hit, but the more concrete consequence is cross-repository state corruption via forged CI status. `StatusHandler`/`CheckSuiteHandler` write `Commit#status`/check state used later by legitimate deploy authorization logic (`deployable?`), meaning an attacker controlling a low-trust organization's (optionally secret-less) webhook path can inject a fabricated "success" status for a commit belonging to a totally unrelated, higher-trust stack/organization configured in the same Shipit instance. That forged green status can later let a legitimate operator ship a commit that never actually passed CI, i.e., contributes to an unauthorized deploy path. This is cross-repository write access driven purely by a payload field the signature never bound to the correct scope.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce (or trivially satisfy) a valid signature for **some** organization configured on the shared Shipit instance — e.g., one whose `webhook_secret` was left blank (explicitly documented as "optional"), or one where the attacker is a GitHub org admin able to read/rotate that org's webhook secret. Directly POSTing to `/webhooks` with a divergent `repository.full_name` requires no GitHub-side privileges for the victim repository at all, only knowledge of one configured org's secret (or lack thereof). This is plausible in any multi-tenant Shipit deployment, which the engine explicitly supports and documents.

### Recommendation
Bind the signature verification to the exact repository being mutated, not just the coarse "owner" fallback field. Concretely:
- After computing `verify_signature`, re-derive `repository_owner` from the *same* `full_name` field the handlers use (`payload.dig('repository', 'full_name').split('/').first`), so the org used for HMAC verification is provably tied to the repository the handler will act on.
- Reject webhooks where an org has no `webhook_secret` configured instead of treating them as automatically verified, or require webhook secrets to be mandatory for all configured organizations.
- Consider additionally validating that the resolved `Repository` record's stored owner matches `repository_owner` before invoking handlers.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` (no `webhook_secret` set, per the documented "optional" field) and `victim-org` (hosts a real deployable stack).
2. Compute (or skip, since none is required) a signature that satisfies `attacker-org`'s check — `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank.
3. POST directly to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "context": "ci",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. `verify_signature` authenticates using `attacker-org`'s (blank) secret and passes.
5. `StatusHandler` resolves the `Repository`/`Commit` via `full_name` = `victim-org/victim-repo`, writing a forged "success" status onto a real commit in `victim-org`'s stack — despite the signature having never proven anything about `victim-org`.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

    end
