### Title
Unauthorized third-party address redefinition can permanently freeze an unrelated address that references it via `['address', ...]` - (File: definition.js)

### Summary
Obyte address definitions can delegate part of their authorization logic to another, unrelated address using the `['address', 'BASE32']` opcode. The referenced address's definition is *not* pinned or authorized by the referencing address at the time of reference — it is looked up fresh, from the current chain state, every single time an authentifier is validated. Because the owner of the referenced address is free to change their own definition at any time (a fully legitimate, self-authorized action for their own address), they can — deliberately or accidentally — turn the referencing address's spending condition into something permanently unsatisfiable (e.g. an oversized/looping definition), bricking every future unit signed by the referencing address, with no way for the referencing address's owner to undo it.

### Finding Description
`Definition.validateAuthentifiers`/`evaluate` handles the `address` opcode by re-reading the current definition of the referenced address on every validation pass: [1](#0-0) 

The comment immediately preceding `validateAuthentifiers`/`validateDefinition` explicitly documents the danger this creates: [2](#0-1) 

```
// we need to re-validate the definition every time, not just the first time we see it, because:
// 1. in case a referenced address was redefined, complexity might change and exceed the limit
// 2. redefinition of a referenced address might introduce loops that will drive complexity to infinity
// 3. if an inner address was redefined by keychange but the definition for the new keyset not supplied before last ball, the address
// becomes temporarily unusable
```

The critical point is that **the owner of the referenced address never consented to being referenced**, and is under no obligation to preserve any particular complexity or shape of their own definition for the benefit of a third party that included `["address", their_address]` in their own definition. Nothing in `validateDefinition`'s complexity accounting (the code paths that walk `arrDefinition` and enforce `constants.MAX_COMPLEXITY`/`MAX_OPS`-style limits) checks or restricts what "inner" address owners may change their own definition to. The referencing address's owner has no lever to prevent, override, or recover from this: once the inner address is redefined to exceed the complexity limit, or to introduce a self-referential loop that drives complexity to infinity, **every future signature check for the referencing address permanently fails** at `validateAuthentifiers`, because `validateDefinition` is invoked fresh before each `evaluate` call (see `definition.js:1454`) and will reject the (now-oversized/looping) definition tree.

This is structurally the same access-control failure pattern described in the report: a critical, cross-entity dependency is gated only by a "self" check (here, "is the inner address definition-valid on its own terms," analogous to `_isInitialized(msg.sender)`), while the actual authorization question — "does the party who can mutate this dependency have any relationship of trust/consent with the party being affected?" — is never asked. Just as any attested module could route the OCL into calling `onUninstall` on itself and irreversibly clearing `ecdsaValidatorStorage`, any unrelated address owner referenced via `["address", ...]` can, through their own perfectly ordinary `address_definition_change` unit (validated at `validation.js:1719-1745` and `validation.js:2003-2050` path), irreversibly clear the ability of a third-party address to ever validate again.

### Impact Explanation
Any address that includes `["address", "OTHER_ADDR"]` in its own definition is permanently at the mercy of `OTHER_ADDR`'s owner. That owner can post a single ordinary `address_definition_change` unit for their own address (a completely permissionless, self-authorized action) that:
- exceeds the complexity limit enforced during definition validation, or
- introduces a self-referential/looping structure that drives complexity to infinity,

causing `validateDefinition`/`validateAuthentifiers` to permanently fail for every future unit signed by the referencing address. Because address definitions cannot be "rolled back" — the referencing address has no way to detach from or re-pin the inner reference — this is a **permanent freeze of funds** held at the referencing address: the node network will consistently and correctly reject the address's future units as invalid, matching the "AA fund loss or freezing" / "node disagreement on validity" impact classes, with no recovery path once triggered.

### Likelihood Explanation
Shared/multisig address templates (`wallet_defined_by_addresses.js`) and other address-definition-template features actively encourage composing `["address", ...]` references to member addresses, so this pattern is commonly used in practice, not a theoretical corner case. The developers themselves flagged the underlying re-validation hazard in the comment at `definition.js:1449-1453`, indicating the code path and its risk are well known internally, but no mitigating restriction (e.g., pinning the inner definition's complexity contribution, or requiring the inner address to co-sign/consent) exists in `validateDefinition`. Triggering the freeze requires nothing more than the inner address's owner posting one additional definition-change unit for their own address — a single ordinary, unprivileged unit.

### Recommendation
Constrain redefinition of an address that is referenced by other addresses' definitions, or decouple the dependency so that a referencing address's validity cannot be unilaterally destroyed by an unrelated party:
- Cap and pin the complexity budget consumed by inner `["address", ...]` references at first-use time, so a later redefinition of the inner address cannot retroactively push the outer definition over the complexity limit.
- Alternatively, require that any address referenced via `["address", ...]` explicitly opts in (e.g. via a co-signed declaration) to being depended upon, and disallow definition changes for such addresses that would violate previously-declared complexity guarantees.
- At minimum, document this as an explicit "acceptable risk" for users composing definitions with `["address", ...]`, and consider surfacing a warning/validation step in wallet UX (`wallet_defined_by_addresses.js`) when a user creates a definition referencing an address they do not control.

### Proof of Concept
1. Address `A` (attacker-controlled) defines itself with a small, valid definition, e.g. `["sig", {pubkey: pkA}]`.
2. Address `B` (victim) creates a definition `["address", "A"]` (directly, or nested inside an `and`/`or`/`r of set` structure), referencing `A`. This is validated once, successfully, per `definition.js:774-800`.
3. `B` operates normally for a while, signing units validated against `A`'s current (small) definition.
4. `A`'s owner posts an ordinary `address_definition_change` unit (validated via `validation.js:1719-1745`, `validation.js:2003-2050`) that redefines `A` to a definition that is extremely large/deeply nested (or self-referential/looping) so that its complexity exceeds `constants`' complexity limit when evaluated.
5. From this point on, any unit signed by `B` fails at `Definition.validateAuthentifiers` → `validateDefinition` (`definition.js:1454`) because the fresh lookup of `A`'s definition now exceeds the complexity budget — `B`'s funds are permanently frozen, with no action `B`'s owner can take to recover, mirroring the permanent, unrecoverable bricking described in the source report.

**Note:** I was not able to fully trace the exact numeric complexity/loop-limit constants and every branch of `validateDefinition`'s complexity accounting within the available indexed context (some deeper portions of `definition.js`'s complexity-counting logic were not retrieved). The core mechanism — fresh re-validation of externally-controlled inner definitions on every check, as explicitly called out in the code's own comment — is confirmed, but a full step-by-step numeric PoC would benefit from a dedicated Devin session with full repository access to pin down the exact complexity threshold values in `constants.js` and confirm the minimal redefinition needed to trigger the failure.
