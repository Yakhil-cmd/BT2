## Title
Stack-scoped API token can read deploy/build status of any stack via CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via the `stack_id` column, which is meant to restrict every API request made with that client's token to that one stack. `Shipit::Api::BaseController` enforces this binding through the `stacks`/`stack` helper methods, which filter `Stack.where(id: current_api_client.stack_id)` before resolving the requested stack param. `Shipit::Api::CCMenuController`, however, overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing the `stack_id` scoping check, while still only requiring the generic `read:stack` permission.

### Finding Description
`Shipit::Api::BaseController` defines the trust boundary for stack-scoped tokens: [1](#0-0) 

`current_api_client.stack_id?` restricts the `stacks` relation, and `stack` resolves the requested `params[:stack_id]` only within that relation — so a scoped token can never resolve a stack it isn't bound to. `Shipit::Api::StacksController` follows this pattern correctly: [2](#0-1) 

`Shipit::Api::CCMenuController` instead overrides `#stack` to bypass the scoped relation entirely and look the stack up globally: [3](#0-2) 

The only authorization check applied is `require_permission :read, :stack`, which is enforced by `ApiClient#check_permissions!` and only checks that `read:stack` is present in the token's `permissions` list — it never checks `stack_id`: [4](#0-3) 

Consequently, the equality the engine is supposed to preserve — "the stack a token authorizes" (`current_api_client.stack_id`) equals "the stack it touches" (`params[:stack_id]` resolved for the response) — is broken specifically in `CCMenuController`. Any token holding `read:stack`, even one created and scoped to a single stack (e.g. via `Shipit::CCMenuUrlController#client`, which mints tokens with `permissions: %w[read:stack]`), can be replayed against `/api/stacks/*stack_id/ccmenu` for an arbitrary other stack simply by changing the `stack_id` in the URL, and the controller will happily resolve and render that unrelated stack's data: [5](#0-4) 

The test suite only validates permission checks and never exercises stack scoping for this controller, matching what the code shows: [6](#0-5) 

### Impact Explanation
The exposed data includes the stack's build/deploy activity, last build status/label/time, and lock status, rendered from `Stack#deploys_and_rollbacks` and `Stack#merge_status`: [7](#0-6) 

This constitutes an escalation into `Shipit.github_teams`/stack-level authorization: a token deliberately narrowed to a single stack (e.g. distributed for embedding in a CI-status widget) can be used to read the deploy/lock/build state of every other stack in the Shipit instance, which the operator never intended to expose through that token.

### Likelihood Explanation
Exploitation requires only possession of any valid `read:stack` API token, including a legitimately narrow, stack-scoped one obtained from `CCMenuUrlController#fetch` (a routine, low-privilege workflow for embedding CI status badges). No special access, secrets, or session is required beyond the token itself, and the `token` query-string authentication path documented and tested in `ccmenu_controller_test.rb` makes exploitation trivial (just swap `stack_id` in the URL).

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` relation (as `StacksController` and `BaseController#stack` do) instead of calling `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that a stack-scoped `ApiClient` can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Create a stack-scoped API client bound only to `stackA` with permission `read:stack` (e.g. via `POST /stackA/... /ccmenu_url` which calls `CCMenuUrlController#client`, or any `ApiClient` with `stack_id` set to `stackA.id`).
2. Using that client's `authentication_token`, issue `GET /api/stacks/<ownerB>/<repoB>/<envB>/ccmenu?token=<token>` where `stackB` is an unrelated stack the client was never scoped to.
3. Observe that `CCMenuController#stack` resolves `stackB` via `Stack.from_param!(params[:stack_id])`, the `read:stack` permission check passes, and the response renders `stackB`'s build status, activity, and lock state — despite the token being scoped only to `stackA`.
