**Analysis:**

The `module_storage`/`code_storage` object is constructed once per transaction by the VM harness and passed by reference through the entire lifecycle — prologue validation, entry-function/script execution, and epilogue — with no attacker-controlled selection point.

In `execute_user_transaction_impl`, the same `code_storage: &impl AptosCodeStorage` parameter is threaded through:
- prologue validation (`validate_signed_transaction`)
- session creation (`into_user_session`)
- entry function/script execution (`execute_script_or_entry_function`) or multisig execution
- epilogue/failure cleanup [1](#0-0) [2](#0-1) [3](#0-2) 

`SessionExt::execute_function_bypass_visibility` and `execute_loaded_function` both simply use whatever `module_storage`/`loader` reference is passed in by the caller via the `dispatch_loader!` macro; they do not independently select or cache a stale loader: [4](#0-3)  The macro itself only switches between `LazyLoader` and `EagerLoader` based on a static VM config flag (`enable_lazy_loading`), not module version or any attacker-influenced state: [5](#0-4) 

There is no code path where transaction payload bytes (attacker-controlled) can cause a different `module_storage`/`loader` instance to be substituted between the admission-time prologue check (`run_prologue`/`run_script_prologue`, which also takes the same `module_storage` parameter) and the actual execution of the entry function/script [6](#0-5) [7](#0-6) . The `module_storage` is derived from the current state-view resolver at the top of the harness and is immutable/consistent for the duration of the single transaction execution — module publishing across "two sessions" as described in the proof idea would require separate, distinct transactions committed on-chain (which itself requires validated prologues per transaction), not a divergence exploitable within a single unprivileged transaction's admission path.

This scenario requires artificially constructing a test harness where two different `module_storage` instances are manually substituted between calls — that is not a path reachable by an unprivileged attacker controlling only payload bytes of a single transaction. It does not meet the boundary condition of starting from an unprivileged transaction/authenticator/API input and does not describe an actual sender/signer/replay/domain-binding break at admission.

#[macro_export]
macro_rules! dispatch_loader {
    ($module_storage:expr, $loader:ident, $dispatch:stmt) => {
        if $crate::WithRuntimeEnvironment::runtime_environment($module_storage)
            .vm_config()
            .enable_lazy_loading
        {
            let $loader = $crate::LazyLoader::new($module_storage);
            $dispatch
        } else {
            let $loader = $crate::EagerLoader::new($module_storage);
            $dispatch
        }
    };
