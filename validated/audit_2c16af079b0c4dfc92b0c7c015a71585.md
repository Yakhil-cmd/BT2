### Title
`shipit.yml` `machine.environment` overrides `GITHUB_TOKEN`/`GIT_ASKPASS` in task env, letting a repo contributor override credentials used by `Command`/`PTY.spawn` - ([File: lib/shipit/task_commands.rb])

### Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` verbatim, with no key allowlist, and `TaskCommands#env` merges it in after the real `GITHUB_TOKEN`/`GIT_ASKPASS` values are set. Because `Hash#merge` gives precedence to the later hash, a `shipit.yml` containing `machine: {environment: {GITHUB_TOKEN: "attacker"}}` overrides Shipit's real GitHub token before the hash is handed to `Command.new` and ultimately `PTY.spawn`.

### Finding Description
The broken binding: the question posits the invariant `TaskCommands#env['GITHUB_TOKEN'] == Shipit.github.token` always, regardless of `shipit.yml`. Tracing the code shows this invariant does **not** hold.

- `Commands#base_env` sets the legitimate credentials: `'GITHUB_TOKEN' => github.token`, and conditionally `'GIT_ASKPASS' => .../git-askpass` [1](#0-0) .
- `TaskCommands#env` builds the final hash as `super.merge(@stack.env).merge({...fixed keys...}).merge(deploy_spec.machine_env).merge(@task.env)` [2](#0-1) . `deploy_spec.machine_env` is merged **after** `super` (which contains the real `GITHUB_TOKEN`/`GIT_ASKPASS`), so any key it contains wins.
- `DeploySpec#machine_env` is `config('machine', 'environment') || {}` — a direct read of the parsed `shipit.yml`, with no key filtering/allowlist [3](#0-2) . This contrasts with `filter_deploy_envs`/`filter_rollback_envs`, which explicitly call `EnvironmentVariables#permit` against a declared variable list [4](#0-3) ; no equivalent permit/allowlist exists for `machine_env`.
- `DeploySpec::FileSystem` sources this config straight from the checked-out repository's `shipit.yml`/`.shipit/shipit.yml` file via `load_config`/`read_config` [5](#0-4) , so the attacker fully controls the `machine.environment` hash contents by editing that file on the branch/commit being deployed.
- The resulting hash (with attacker's `GITHUB_TOKEN` override) is passed as `env:` to `Command.new(command_line, env:, chdir:)` [6](#0-5) . `Command#unbundled_env` computes `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [7](#0-6) , and `start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` [8](#0-7) . Since `@env` (the attacker-influenced merged hash) is applied last, the attacker's `GITHUB_TOKEN`/`GIT_ASKPASS` values reach `PTY.spawn` and are used for any git/GitHub CLI operations performed by deploy/rollback/fetch steps.

Existing guards checked and found insufficient: there is no `EnvironmentVariables#permit`/allowlist applied to `machine_env` (unlike `deploy`/`rollback` variables); `Repository`/`Stack` model validations do not constrain `shipit.yml` content; and no code path filters out reserved key names (`GITHUB_TOKEN`, `GITHUB_DOMAIN`, `GIT_ASKPASS`) from `machine.environment`. A test explicitly documents that arbitrary `machine_env` keys (e.g. `'GLOBAL'`) flow into `command.env` unfiltered: `test "#perform merges shipit.yml machine_env in ENVIRONMENT"` [9](#0-8) , and a separate test only asserts the *default* (non-attacker) case sets the correct token: `test "#env uses the correct Github token for a stack"` [10](#0-9)  — no test asserts that `machine_env` cannot override `GITHUB_TOKEN`/`GIT_ASKPASS`.

Attacker path: a repository contributor opens a PR (or pushes to a branch that becomes a ReviewStack, or is merged to the deployed branch for `main`/production stacks) modifying `shipit.yml`/`.shipit/shipit.yml` to include:
```yaml
machine:
  environment:
    GITHUB_TOKEN: "attacker-controlled-or-empty-to-break-auth"
    GIT_ASKPASS: "/path/to/malicious/script"
```
Once this spec is used as the `cached_deploy_spec` (or read live from the checked-out working directory) for a deploy/rollback/fetch task, every `Command` run for that task/stack executes with the attacker's `GITHUB_TOKEN`/`GIT_ASKPASS`, which (for `GIT_ASKPASS`, an executable path) is direct RCE on the deploy host under the Shipit worker process, and for `GITHUB_TOKEN` is exfiltration/replacement of the credential used for GitHub auth in that command's `git`/API calls.

### Impact Explanation
The impact is on the deploy host running the Shipit worker: an attacker-controlled `GIT_ASKPASS` path is executed by any git operation needing credentials, yielding arbitrary code execution as the Shipit deploy/task user, and an attacker-controlled `GITHUB_TOKEN` can redirect git/GitHub-authenticated network calls to an attacker-chosen token (masking or hijacking the app's auth) or, by unsetting/clobbering it with an invalid value, break the app's own GitHub auth for that task's git operations. This affects the specific stack/task whose `shipit.yml` was modified — a repository maintainer/contributor with PR/branch push rights to that repository can repeat this on every deploy against their own stack (Critical: RCE on deploy host via `Command`/`PTY.spawn`, and credential-substitution matching "exfiltration of `GITHUB_TOKEN`" impact category).

### Likelihood Explanation
Preconditions: the attacker needs their `shipit.yml` change to be the one used as the effective deploy spec for a task — i.e., either a merged PR on the deployed branch, or (for ReviewStacks) an accepted PR/branch that Shipit tracks. This generally requires some review/merge step for production stacks, but ReviewStack usage or looser branch protection could let an unprivileged-but-authorized contributor achieve this without special Shipit privileges. Given "attacker action... via a merged/reviewed PR" is explicitly named as the vector in the question, the cost is a normal PR contribution; feasibility is high once merged, and the effect repeats on every subsequent deploy/rollback/fetch task for that stack until the `shipit.yml` is reverted.

### Recommendation
Apply an explicit allowlist/denylist to `DeploySpec#machine_env` (mirroring `filter_deploy_envs`/`filter_rollback_envs`'s use of `EnvironmentVariables#permit`), rejecting or stripping reserved keys such as `GITHUB_TOKEN`, `GITHUB_DOMAIN`, `GIT_ASKPASS`, `PATH`, and any other security-sensitive env vars set by `Commands#base_env`. Alternatively, change the merge order in `TaskCommands#env` so `deploy_spec.machine_env` is merged before the trusted keys are applied, and additionally re-apply `super`/`base_env`'s security-critical keys last (after all user-controlled merges) so they cannot be overridden regardless of merge order elsewhere.

### Proof of Concept
```ruby
# test/models/deploy_spec_test.rb or test/unit/task_commands_test.rb
test "machine_env cannot override GITHUB_TOKEN" do
  Shipit.github(organization: 'shopify').stubs(:token).returns('real-token')
  deploy_spec = DeploySpec::FileSystem.new(@task.working_directory, @stack)
  deploy_spec.stubs(:machine_env).returns('GITHUB_TOKEN' => 'attacker-token')
  commands = TaskCommands.new(@task)
  commands.stubs(:deploy_spec).returns(deploy_spec)

  # Binding under test: commands.env['GITHUB_TOKEN'] == Shipit.github.token
  assert_equal 'real-token', commands.env['GITHUB_TOKEN']
  # Currently fails: commands.env['GITHUB_TOKEN'] == 'attacker-token'
end
```
This demonstrates that `TaskCommands#env['GITHUB_TOKEN']` diverges from `Shipit.github.token` when `deploy_spec.machine_env` contains a `GITHUB_TOKEN` key, confirming the merge-order/no-allowlist flaw described above.

            ".shipit/#{app_name}.#{@env}.#{ext}",

        YAML_EXTENSIONS.flat_map do |ext|

        end.uniq
      end

        shipit_file_names_in_priority_order.each do |filename|

      def build_config(path, config_obj)
