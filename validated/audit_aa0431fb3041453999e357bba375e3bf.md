### Title
Cross-repository commit status forgery leading to unauthorized continuous deployment - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler`, the handler for GitHub `status` webhook events, resolves the target `Commit` records purely by SHA, with no scoping to the repository that the webhook's signature was verified against. This breaks the intended binding between "the organization/repository GitHub authenticated the webhook for" and "the repository/stack whose state Shipit mutates."

### Finding Description
`WebhooksController#verify_signature` selects the HMAC secret to validate the payload with by resolving `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the payload's `repository.owner.login` (or `organization.login`) [1](#0-0) [2](#0-1) . This only proves the request came from *some* GitHub App installation belonging to that organization — it says nothing about which specific repository/commit inside that org's installation the event concerns, and does not bind the payload to any particular Shipit `Stack`.

Compare this to `PushHandler` and `CheckSuiteHandler`, which correctly scope their effects to stacks tracking the exact repository named in the payload, via `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [3](#0-2) [4](#0-3) [5](#0-4) .

`StatusHandler`, however, never calls `stacks` / never checks `params.repository`. It looks up **every** `Commit` row across the entire database that has a matching `sha`, regardless of which repository/stack it belongs to, and writes the status onto it:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5) 

Its own `params` block doesn't even require a `repository` object [7](#0-6) , confirming the repository identity is deliberately not used to constrain which commits are affected.

Because a commit's SHA1 is a hash purely of its git content (tree, parent(s), author/committer, timestamp, message) and not of the repository it lives in, an identical commit (e.g. a public commit, a forked/mirrored repository, or a commit cherry-picked/copied byte-for-byte) can exist with the same SHA under a different repository. Any org whose GitHub App installation can legitimately deliver a `status` webhook to Shipit (a correctly, GitHub-signed request for a repository the attacker merely has commit-status write access to) can therefore poison the CI state of a `Commit` row belonging to an entirely unrelated `Stack`/repository, as long as that stack happens to have a `Commit` with the same SHA.

### Impact Explanation
Writing a `success` status onto an unrelated stack's commit directly feeds `Commit#schedule_continuous_delivery`, which is triggered whenever a status is added and checks `deployable?` [8](#0-7) . If that stack has continuous deployment enabled, this enqueues `ContinuousDeliveryJob`, which calls `stack.trigger_continuous_delivery`, which calls `trigger_deploy` and actually performs a deploy [9](#0-8) [10](#0-9) . Tests confirm that creating a `success` status is sufficient by itself to enqueue and run a deploy when CD is enabled: [11](#0-10) .

This means an attacker who never authenticated to, or wrote to, the victim repository/stack can cause an **unauthorized deploy** of that stack by forging (through a legitimately-signed webhook from a different, attacker-influenced repository) a passing CI status for a commit that also exists in the victim stack. This satisfies the Critical impact bucket: "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Exploitation requires: (1) the attacker to control (or have status-write access to) at least one repository whose org's GitHub App is installed and configured with Shipit, and (2) a `Commit` row with the same SHA to already exist in a target `Stack`. Condition (2) is realistic in common setups such as forked/mirrored repositories, monorepo-derived stacks, or any scenario where identical commit content is pushed to more than one tracked repository — the attacker fully controls the content of their own repository and can therefore intentionally reproduce an identical commit object (same tree/parent/author/committer/message/timestamp) to match a known target SHA. No `webhook_secret`, `GITHUB_TOKEN`, or Shipit session is required — the signature is generated by GitHub itself for the attacker's own legitimately-authorized delivery.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks tracking the repository named in the payload, mirroring the pattern already used in `PushHandler`/`CheckSuiteHandler` — require and validate `params.repository.full_name`, resolve the repository via `Repository.from_github_repo_name`, and constrain the `Commit` lookup to `stacks`'s commits (e.g. `Commit.where(sha: params.sha, stack_id: stacks.ids)`) rather than a global SHA-only lookup.

### Proof of Concept
1. Shipit tracks `victim-org/prod-service` as `Stack` A (continuous deployment enabled), which has a `Commit` row for SHA `deadbeef...` currently in a `pending`/`failure` CI state.
2. Attacker controls `victim-org/pet-project` (a low-value repository in the same org/installation, or any org whose GitHub App installation is configured in Shipit) with commit-status write access.
3. Attacker crafts/pushes a git commit object into `pet-project` with byte-identical content (tree, parents, author, committer, timestamp, message) to the target commit in `prod-service`, reproducing SHA `deadbeef...`.
4. Attacker calls the GitHub Statuses API to set `state=success` on `deadbeef...` in `pet-project`.
5. GitHub delivers a correctly HMAC-signed `status` webhook to Shipit's `/webhooks` endpoint using the org's real webhook secret; `verify_signature` passes because `repository.owner.login` matches a configured org.
6. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')`, which also returns the `Commit` in `Stack` A (`prod-service`), and calls `create_status_from_github!` on it, marking it `success`.
7. `Commit#schedule_continuous_delivery` fires, `ContinuousDeliveryJob` runs, and `Stack` A is deployed — despite the attacker never having any access to `prod-service`.
