### Title
`Shipit::Api::CCMenuController#stack` bypasses `ApiClient#stack_id` scoping, allowing cross-tenant stack read via `#show` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuController#authenticate_api_client` falls through to `BaseController`'s Basic-Auth path when the `token` query param is missing or invalid, letting any holder of valid `ApiClient` Basic-Auth credentials authenticate. `CCMenuController#stack` then resolves `params[:stack_id]` via the unscoped `Stack.from_param!` instead of the scoped `stacks.from_param!` inherited from `BaseController`, so `current_api_client.stack_id` is never consulted before `#show` renders `stack.deploys_and_rollbacks`.

### Finding Description
The binding that should hold is: `stack_from_param ∈ Stack.where(id: current_api_client.stack_id? ? current_api_client.stack_id : Stack.all)`, i.e. the resolved stack must be a member of the set the authenticated `ApiClient` is scoped to, exactly as enforced by `BaseController#stacks`/`#stack`: [1](#0-0) 

`CCMenuController` overrides `#stack` and drops that scoping entirely, resolving directly against `Stack.from_param!(params[:stack_id])`: [2](#0-1) 

Authentication in this controller is also weakened: `#authenticate_api_client` tries `ApiClient.authenticate(params[:token])` and only calls `super` (the Basic-Auth path) when that fails: [3](#0-2) 

`super` is `BaseController#authenticate_api_client`, which accepts any valid Basic-Auth `ApiClient` credential unrelated to the requested stack: [4](#0-3) 

The only authorization gate applied afterward is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`. That method checks only whether the string `"read:stack"` is present in `permissions`, never whether the target `stack_id` matches the client's `stack_id`: [5](#0-4) [6](#0-5) 

Attacker's exact request: omit or send a garbage `token` query param, and instead present a valid Basic-Auth `Authorization` header for their own `ApiClient` (which they legitimately hold, scoped to their own stack with `read:stack` permission), and set `params[:stack_id]` to the victim's stack id/slug: `GET /api/stacks/<victim_stack_id>/ccmenu.xml` with `Authorization: Basic <own-valid-creds>`.

Exploit flow: `authenticate_api_client` fails the token check, falls to `super`, which successfully authenticates the attacker's own `ApiClient` via Basic Auth → `require_permission :read, :stack` passes because the attacker's own client has `read:stack` in its permission list (unrelated to which stack) → `#show` calls `stack`, which uses the unscoped `Stack.from_param!(params[:stack_id])` and resolves the victim's stack regardless of `current_api_client.stack_id` → `stack.deploys_and_rollbacks.last` (branch/revision/status of the victim's latest deploy or rollback) is rendered back to the attacker.

None of the listed guards stop this: `require_permission!`/`check_permissions!` only checks the permission-scope string, not the stack identity; the `stacks` scope (`current_api_client.stack_id?`) is never invoked because `CCMenuController#stack` doesn't call the inherited `#stack`/`#stacks`; there is no `ExplicitParameters` schema or model validation involved in this read path.

### Impact Explanation
Any authenticated `ApiClient` holder can read another tenant's stack deploy/rollback state (deploy id, end time, running status, branch info as rendered by the `shipit/ccmenu/project` template) for any stack id they can guess or enumerate, without that stack ever being in their own `stack_id` scope. This is a cross-tenant authorization bypass on a read endpoint, repeatable against arbitrary stacks with no rate limiting beyond normal HTTP requests.

### Likelihood Explanation
Precondition is minimal: the attacker only needs any valid `ApiClient` Basic-Auth credential with `read:stack` permission for their own legitimately owned stack (a normal, low-privilege credential many API consumers would hold), plus knowledge/guess of the target `stack_id`/slug. No Shipit or GitHub secrets, no session, and no special repository configuration are required. This is a low-cost, fully repeatable attack.

### Recommendation
Make `CCMenuController#stack` use the scoped resolver inherited from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`) so it honors `current_api_client.stack_id`. Additionally, reconsider allowing the Basic-Auth fallback in this controller's `authenticate_api_client`, since CCMenu URLs are designed to be scoped/opaque per-stack tokens; if a `token` param is present and invalid it should not silently defer to unrelated credentials.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb`-style, no live GitHub needed):
1. Create `stack_a` (attacker-owned) and `stack_b` (victim), each with a completed deploy.
2. Create `api_client_a = Shipit::ApiClient.create!(creator: user, stack: stack_a, permissions: ['read:stack'])`.
3. Send `get "/api/stacks/#{stack_b.to_param}/ccmenu.xml"` with `Authorization: Basic` header built from `api_client_a`'s credentials, and no/garbage `token` query param.
4. Assert both sides of the binding before/after: assert `api_client_a.stack_id == stack_a.id` and `stack_b.id != api_client_a.stack_id` (binding should exclude `stack_b`).
5. Assert response status is `200` (not `403`/`404`) and response body contains `stack_b`'s latest deploy id/status — demonstrating the binding is violated in production code, matching the described exploit.
