### Title
Cross-organization webhook forgery via mismatched signature-selection and processing fields - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a Shipit instance configured with multiple GitHub organizations (a documented and supported configuration, each with its own `webhook_secret`), the field used to select *which* organization's HMAC secret verifies the inbound webhook is not the same field used by webhook handlers to determine *which repository/stack* the payload is applied to. An attacker who controls a legitimate GitHub App/webhook secret for one configured organization can forge a webhook whose signature validates against their own organization's secret, while the payload's `repository.full_name` — read later by handlers — points at a different, victim organization's repository.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from the untrusted JSON body, before any cryptographic check: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` instance (and thus `webhook_secret`) configured for that organization login, per the documented multi-org configuration: [3](#0-2) 

`verify_webhook_signature` then HMAC-validates the *entire* raw request body against whichever organization's secret was selected by the attacker-controlled `repository.owner.login`: [4](#0-3) 

Once the signature is accepted, the full unfiltered payload is dispatched to all registered handlers for the event: [5](#0-4) 

Handlers, however, resolve the target repository/stack using a *different* JSON field, `repository.full_name`, not `repository.owner.login`: [6](#0-5) 

For example, `PushHandler` uses that repository-derived `stacks` scope to trigger a GitHub sync to an attacker-chosen `after` SHA for any un-archived stack on the resolved repository: [7](#0-6) 

Because `repository.owner.login` (used only for secret selection) and `repository.full_name` (used only for target resolution) are independent, unrelated fields inside the same signed body, an attacker who legitimately owns a GitHub App/webhook secret for **organization A** can:
1. Set `repository.owner.login` = `"org-a"` so `verify_signature` selects `org-a`'s webhook secret, which the attacker knows.
2. Set `repository.full_name` = `"org-b/victim-repo"`, a repository belonging to a different, victim organization also hosted on the same Shipit instance.
3. Sign the raw body with `org-a`'s secret; the signature check passes because it only validates the secret matches the org named in the (attacker-controlled) payload — it never confirms that the *content* of the payload (the repository being acted upon) actually belongs to that org.
4. The handler then acts on `org-b/victim-repo` as if GitHub itself had sent the event for that repo.

This is exactly the "organization that authenticated versus the repository that is written" trust binding: `verify_signature` authenticates *an organization*, but the handler pipeline writes/acts on *a repository* selected from an unrelated, unauthenticated field in the same untrusted body.

### Impact Explanation
Depending on which event/handler is exploited against the victim repository's stacks, this can produce: forged `push` events causing `stack.sync_github` to run with attacker-chosen commit SHAs, forged `status`/`check_suite` events that could satisfy CI-gating (`ci.require`) used by continuous deployment / merge-queue logic, and forged `pull_request` events that archive/unarchive or otherwise manipulate review stacks belonging to a repository the attacker does not control. Where continuous deployment or merge queue is enabled and gated on commit statuses/checks, this chain can lead to an **unauthorized deploy** of a victim repository's stack — satisfying the Critical impact bar in the rules ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability requires only that: (a) the Shipit instance is configured with more than one GitHub organization (the documented, supported multi-org configuration), and (b) the attacker legitimately administers a GitHub App/webhook for at least one of those organizations (their own). No access to the victim organization, no `ApiClient` token, and no GitHub credentials for the victim repo are required — the attacker only needs their own, unrelated organization's webhook secret, which they already legitimately possess. This is a realistic scenario for any shared/multi-tenant Shipit deployment.

### Recommendation
Bind the signature-verification organization to the same identity used for handler dispatch. Concretely, after selecting `github_app` by `repository_owner`, re-validate that the `repository.full_name` in the payload actually belongs to that same organization (e.g., assert `payload.dig('repository', 'full_name')&.split('/')&.first&.casecmp?(repository_owner)`) before invoking any handler, and reject the request otherwise. Alternatively, always resolve the target `Repository`/`Stack` and re-derive the expected owning organization from Shipit's own database record instead of trusting the payload for cross-org routing.

### Proof of Concept
1. Configure/observe a Shipit instance with two organizations, e.g. `org-a` and `org-b`, each with its own `github.<org>.webhook_secret` as documented in `config/secrets.development.shopify.yml`.
2. As an attacker who legitimately owns the GitHub App for `org-a` (and thus knows `org-a`'s `webhook_secret`), craft a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a-webhook-secret, raw_body)>`.
4. `POST /webhooks` with header `X-Github-Event: push`. `verify_signature` selects `org-a`'s `GitHubApp` via `repository_owner` (`"org-a"`) and validates successfully against the attacker-known secret.
5. `PushHandler#process` resolves `stacks` from `repository.full_name` = `"org-b/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `org-b`'s stack, despite the attacker never having any credential for `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
