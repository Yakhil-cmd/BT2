### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` attaches an incoming GitHub `status` webhook to *any* `Shipit::Commit` row that matches the given `sha`, with no check that the webhook's `repository` actually corresponds to the stack that owns that commit. Because GitHub commit SHAs are content-addressed and shared verbatim between a repository and any fork of it, an attacker who forks `victim/prod` and gets a webhook delivered from their own (attacker-controlled, separately-authenticated) repository referencing that shared SHA can write a `success` status onto the victim's `Commit` row, which is then read by `MergeRequest#all_status_checks_passed?` and can unblock `reject_unless_mergeable!`/merging.

### Finding Description
The broken binding: `merge_request.head.sha == sha_of_commit_whose_CI_state_was_authentically_set_by_victim's_repository` is assumed true wherever `all_status_checks_passed?` is called, but the actual write path only enforces `merge_request.head.sha == params.sha`, dropping the repository/organization dimension entirely.

Path:
- `Shipit::WebhooksController#create` dispatches the parsed JSON payload to handlers matched on `X-Github-Event` [1](#0-0) .
- `verify_signature` selects the `GitHubApp`/webhook secret using `repository_owner`, which is read straight from the payload's `repository.owner.login` (attacker-controlled) [2](#0-1) [3](#0-2) . This only proves the request came from the org that owns the sending repo (i.e. an org already onboarded/configured in `secrets.github`), it proves nothing about which `Commit`/`Stack` the payload's `sha` belongs to.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a **global**, cross-stack, cross-repository lookup by `sha` alone, with no `stack_id`/repository filter [4](#0-3) .
- `Commit#create_status_from_github!` unconditionally records the status via `add_status` [5](#0-4) , which also schedules `stack.schedule_merges` when the new status is `pending`/`success` [6](#0-5) .
- Later, `MergeRequest#all_status_checks_passed?` builds `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?` off that same `Commit` row [7](#0-6) , and `reject_unless_mergeable!` uses `any_status_checks_missing?`/`any_status_checks_failed?` built the same way to decide whether to reject the merge [8](#0-7) .

Exploit flow: attacker forks `victim/prod`. Because git commits are content-addressed (sha1 over tree + parents + author/committer + message + timestamps), the attacker's fork naturally contains the *exact same object* for any commit reachable from the shared history, including the victim's open PR's head commit — no preimage attack is required, this is standard fork behavior. The attacker creates/points a branch in their own fork at that SHA and uses (or triggers) GitHub's real status API/webhook from their own repository, referencing that SHA with `state: success`. GitHub signs and delivers this webhook using the webhook secret configured for the attacker's own onboarded organization (a distinct, legitimately-configured `GitHubApp`/secret per the documented multi-tenant "Using Multiple Github Applications" setup) [9](#0-8) [10](#0-9) . `verify_signature` passes because it only checks that the signature matches *some* org's configured secret, not that the org matches the commit's stack. `StatusHandler#process` then finds the victim's `Commit` row purely by `sha` and writes the attacker-originated `success` status onto it.

Existing guards that fail to stop this: `verify_signature` authenticates the *sender org*, not the *sha ownership*; `ExplicitParameters` schema on `StatusHandler` only validates types/presence of `sha`/`state`/etc., not repository binding [11](#0-10) ; there is no `stack.commits.find_by(sha:)` or repository-name check anywhere in this handler.

### Impact Explanation
An attacker who controls any repository onboarded to the same multi-tenant Shipit instance (their own fork/org, fully unprivileged with respect to the victim) can inject a forged passing CI status onto a victim stack's queued `MergeRequest.head` commit. This flips `all_status_checks_passed?` to `true` and neutralizes `reject_unless_mergeable!`'s `ci_missing`/`ci_failing` rejections, allowing `ProcessMergeRequestsJob`/`MergeRequest#merge!` to merge a PR into `victim/prod` without any real passing CI from the victim's own GitHub checks. This is a cross-tenant integrity violation — one repository's authenticated event mutates another repository's stack/commit state — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge"). The attack is repeatable against any stack/commit whose SHA the attacker can reproduce via fork history sharing, and scales to any tenant sharing the Shipit instance.

### Likelihood Explanation
Preconditions: the target Shipit instance must be multi-tenant (multiple GitHub orgs/apps configured, per `docs/setup.md`'s "Using Multiple Github Applications" section), the attacker must control at least one onboarded repository/org (e.g., their own team's project on the same Shipit instance, or a public app installation) — not necessarily the victim's org — and the victim stack must have `merge_queue_enabled` with a pending `MergeRequest` whose head has no passing status yet. Achieving the SHA collision requires no cryptographic attack: it is the normal outcome of git fork history sharing, so cost is essentially the price of an unprivileged GitHub account plus onboarding to the same Shipit deployment. This is fully repeatable and requires no secrets, sessions, or maintainer privileges belonging to the victim.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) to the repository that actually sent the webhook, e.g. resolve `Stack`/`Repository` from `params.dig('repository','full_name')` first, then do `stack.commits.where(sha: params.sha)` instead of a global `Commit.where(sha:)`. Reject or ignore statuses whose repository does not match the commit's owning stack.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from unrelated repository cannot forge success for another stack's merge request" do
  victim_stack = shipit_stacks(:shipit) # tracks "victim/prod"
  colliding_sha = "d0c22ffee..." # sha shared by victim's PR head and attacker's fork branch
  head_commit = victim_stack.commits.create!(sha: colliding_sha, ...)
  merge_request = victim_stack.merge_requests.create!(head: head_commit, merge_status: 'pending', number: 42)

  refute merge_request.all_status_checks_passed?
  assert_equal 'ci_missing', (merge_request.reject_unless_mergeable! && merge_request.rejection_reason)

  # Attacker-controlled repository payload, sha collides due to shared fork history
  attacker_payload = {
    "sha" => colliding_sha,
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => "attacker/unrelated-repo", "owner" => { "login" => "attacker-org" } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  merge_request.reload
  # Binding check: sha match alone should NOT be sufficient to authorize the status
  assert merge_request.all_status_checks_passed?, "status forged onto victim's commit without repository binding check"
  refute merge_request.reject_unless_mergeable!
end
```
This demonstrates that `StatusHandler#process`'s sha-only lookup lets a payload carrying an unrelated `repository` flip `all_status_checks_passed?` and defeat `reject_unless_mergeable!`, confirming the missing repository-binding check.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
