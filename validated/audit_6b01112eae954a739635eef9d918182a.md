### Title
Unchecked Remote AA Address in `remote_func_call`/`callGetter` Allows Attacker-Controlled Return Values to Corrupt AA Accounting - ([File: formula/evaluation.js])

### Summary
Oscript's remote-call feature (`$remote_aa.$getter(args)`) lets an Autonomous Agent (AA) invoke a getter defined in another AA and use the returned value in its own logic (state updates, payment amounts, etc.). The only validation performed on the `remote_aa` address is that it is a syntactically valid address and, optionally, that its complexity/getter signature matches declared bounds. There is no requirement that the target AA be a specific, pre-agreed, trusted contract. If an AA author builds logic where the `remote_aa` value is derived from attacker-controlled input (e.g. `trigger.data`), any unprivileged unit poster can deploy their own malicious AA and steer the caller into treating its fabricated getter output as trustworthy data for balance/state calculations — structurally the same root cause as the Treasury `fetchSurplusFromVaultManagers` bug: an externally supplied, unchecked contract/AA address whose return value is blindly trusted to update critical accounting state.

### Finding Description
In `formula/evaluation.js`, the `remote_func_call` case evaluates the `remote_aa` expression and only checks that it is a valid address before calling into it: [1](#0-0) 

`callGetter` then loads whatever AA definition lives at that address, executes its `getters` formula, and returns the value with essentially no restriction on shape or magnitude — any address that resolves to a deployed AA is accepted as a legitimate "remote AA": [2](#0-1) [3](#0-2) 

As demonstrated in the test suite, the getter's return value can carry arbitrary computed fields (`sq`, `bal`, `this`, etc.) which are then assigned directly into the caller's state variables via `var[]`: [4](#0-3) [5](#0-4) 

This mirrors the audited Solidity pattern where `IVaultManager(vaultManagers[i]).accrueInterestToTreasury()` was called on an unchecked, user-supplied address and its return values were summed directly into `surplusBufferValue`/`badDebtValue`. In ocore, the analogous unchecked input is the `remote_aa` address; if it is derived (directly or indirectly) from `trigger.data` or another attacker-influenced source rather than being hardcoded to a specific known counterparty AA, the calling AA has no way to distinguish a legitimate remote AA from an attacker-deployed one that returns fabricated numbers, balances, or object fields.

### Impact Explanation
Any AA that resolves its `remote_aa` target dynamically (e.g. to implement pluggable oracles, exchange-rate providers, reputation lookups, or "call any counterparty AA" patterns) and then uses the returned values to compute payout amounts, update `var[]` accounting, or gate fund releases is exposed to fabricated data from an attacker-authored AA. This can lead to AA fund loss (excess payouts based on inflated fake values), corrupted internal state accounting, or freezing of legitimate operations if the caller's invariants are violated by attacker-supplied numbers/objects. This satisfies the "AA fund loss or freezing" and "unauthorized spending" impact categories.

### Likelihood Explanation
Exploitation requires an AA author to have chosen a dynamic/attacker-influenceable `remote_aa` expression rather than a hardcoded, trusted counterparty address — a real-world and common pattern for composable DeFi-style AAs (e.g., generic “call any price/insurance/lending AA specified by the trigger”). Since deploying a malicious AA and sending a single trigger unit is fully within reach of any unprivileged unit poster, and `isValidAddress` is the only gate on `remote_aa`, likelihood is significant for any AA following this composability pattern.

### Recommendation
- Document and strongly discourage using attacker-influenceable expressions as `remote_aa` unless the returned data is independently validated (bounds-checked, sanity-checked) before being used to update balances or state.
- Consider adding an oscript-level primitive or best-practice pattern for AA authors to declare/whitelist trusted remote AA addresses rather than relying purely on address validity.
- For any core financial AAs shipped with the platform (bridges, oracles, exchanges) that use remote calls, ensure the target address is fixed at definition time or restricted to an author-controlled allow-list, mirroring the Treasury fix of removing the ability to pass an arbitrary list of external contracts and instead using an enumerated, trusted set.

### Proof of Concept
1. Attacker authors and posts AA `M` with a getter such as `$f = ($x) => { { bal: 1000000000, valid: true } }` that returns arbitrarily large/fabricated values regardless of real state.
2. Victim AA `V` is written with logic like:
   ```
   $remote_aa = trigger.data.oracle_aa;
   $ret = $remote_aa.$f(trigger.data.x);
   ...
   var['collateral_value'] = $ret.bal;
   ```
   as illustrated by the remote-call pattern in `test/aa_composer.test.js:1066-1139` (`calling a remote function`), where the caller trusts `$ret.bal`/`$ret.sq` from whichever AA address is supplied.
3. Attacker sends a trigger unit to `V` with `trigger.data.oracle_aa = M` (attacker's own AA address).
4. `V` calls `callGetter` on `M` (`formula/evaluation.js:2611-2627`, `3289-3376`), receives the fabricated `bal` value, and uses it to update `var['collateral_value']` or compute a payment amount — allowing the attacker to trigger an oversized payout or corrupted internal accounting state in `V`.
