## Analysis

The CVE-2016-0756 root cause is that Prosody's `generate_dialback` concatenated the stream ID and target domain **without an unambiguous field separator**, so a crafted domain (a suffix-crafted value) could make two different (id, domain) pairs collapse to the same dialback key, spoofing identity.

The same root-cause pattern — concatenating variable-length, attacker-influenced fields with no delimiter before hashing — exists in ocore's contract-commitment hashing used by the arbiter/prosaic contract features.

`exports.NEW_HASH_DATE = '2026-11-01'` and `exports.DELIMITER = "[|#|]"` show the maintainers are aware that delimiter-less concatenation is unsafe and only apply a fix for contracts with `creation_date > '2026-11-01'` — i.e. the fix is not yet in effect (today is 2026-09-15), so every contract created right now still uses the vulnerable `.join("")` branch, which joins `title`, `text`, `creation_date`, `payer_name`, `arbiter_address`, `payee_name`, `amount`, `asset` with no separator at all. `title` and `text` are fully attacker/counterparty-controlled free-text fields.

### How the hash is relied on as a security boundary

`contract.hash` is generated locally at offer time and becomes the canonical commitment to the negotiated contract text: [3](#0-2) 

It is posted on-chain inside a `data` message (`contract_text_hash`) and used as the arbiter's data-feed key (`"CONTRACT_" + contract.hash`) that gates fund release from the shared address: [4](#0-3) 

The peer-side signing flow validates the received signing unit strictly by comparing the posted hash to the locally stored `contract.hash`: [5](#0-4) 

Because the underlying string is built by naive concatenation without a delimiter, `getHash` is not a true binding commitment to the *structured* fields — it only commits to the flattened byte string. Any redistribution of characters across the `title`/`text` (and other adjacent-field) boundary that preserves the flattened string yields an identical SHA-256 hash while the structured fields, and therefore what is displayed to a human reviewing "title" and "text" separately, differ.

## Title
Delimiter-less field concatenation in arbiter/prosaic contract hash allows contract-text spoofing via field-boundary shifting - (File: arbiter_contract.js, prosaic_contract.js)

## Summary
`getHashSrc`/`getHash` in `arbiter_contract.js` (for `creation_date` before the scheduled `NEW_HASH_DATE` cutover) and `getHash`/`getHashV1` in `prosaic_contract.js` build the hashed source string by concatenating `title`, `text`, `creation_date`, party names, `arbiter_address`, `amount`, `asset` with `Array.prototype.join("")` — no separator. Because `title` and `text` are attacker/peer-controlled free text, characters can be shifted across the field boundary so that two structurally different contracts collapse to the identical flattened string and thus the identical `contract.hash`, exactly the CVE-2016-0756 class of bug (ambiguous field concatenation enabling identity/content spoofing via crafted suffix).

## Finding Description
`getHashSrc` (old branch) and `prosaic_contract.js`'s `getHash`/`getHashV1` compute:
```
title + text + creation_date + payer_name + arbiter_address + payee_name + amount + asset
```
with no delimiter between components (`.join("")`). Since `title` and `text` have no length prefix and no reserved separator character, a counterparty crafting an offer can move an arbitrary substring from the end of `title` to the start of `text` (or vice versa) without changing the concatenated byte string, hence without changing the resulting SHA-256 hash. The same applies at other field boundaries (e.g., shifting characters between `payee_name` and the fixed literal fields around it).

This means `contract.hash`, which is treated throughout the module as a cryptographic commitment uniquely identifying the agreed contract text (used for DB lookup via `getByHash`, for on-chain `contract_text_hash` verification in `handleReceivedSigningUnit`, and as the arbiter's data-feed key `"CONTRACT_"+hash`), does not actually bind to a unique `(title, text, ...)` tuple. Two semantically different contracts (different visible title/body split) can share the same `hash`.

The compensating control the developers themselves added — a fixed `DELIMITER` used only for `creation_date > NEW_HASH_DATE` ('2026-11-01') — is not active for any contract created before that date, i.e., not active today, leaving the delimiter-less concatenation as the live code path.

## Impact Explanation
`contract.hash` is the sole cryptographic anchor tying the negotiated free-text terms to the on-chain data message and to the arbiter's dispute data-feed key that ultimately controls release of escrowed funds from the shared address. Because the hash can be produced from two structurally different `(title, text)` splits, a malicious counterparty in the contract negotiation (peer device) can exploit the field-boundary ambiguity to present one decomposition to the victim during acceptance/signing and effectively have the same commitment hash validated against a different decomposition later (e.g., in the dispute path, or when reconstructing/sharing the contract to cosigners/arbstore), because none of the consuming code re-derives or checks the field boundaries — only the final hash. This can be used to misrepresent contract terms to a counterparty or arbiter while still satisfying the `payload.contract_text_hash !== contract.hash` check in `handleReceivedSigningUnit`, undermining the integrity guarantee the contract-hash mechanism is meant to provide for fund-controlling arbitration outcomes.

## Likelihood Explanation
The attacker is simply one of the two contracting parties (a paired device counterparty), which is squarely within the reachable "private-payment counterparty" / "wallet and contract message handling" surface. No special privileges, network position, or dependency exploitation are needed — only free-text fields (`title`, `text`) that the module already allows the user to fully control. Constructing a colliding boundary shift is trivial (no cryptographic search needed, since it is an exact string-equality collision, not a hash collision).

## Recommendation
Apply the same delimiter-based fix (`exports.DELIMITER`) unconditionally for all contracts regardless of `creation_date`, or better, use ocore's existing length/type-tagged canonicalization (`getSourceString`/`getJsonSourceString` from `string_utils.js`, which already prefixes each field with a type tag and joins with a reserved `STRING_JOIN_CHAR` and rejects that byte inside string values) instead of ad hoc `.join("")`/string concatenation in `arbiter_contract.js#getHashSrc` and `prosaic_contract.js#getHash`/`getHashV1`. Remove the `NEW_HASH_DATE` gate so the fix is not deferred.

## Proof of Concept
Using the pre-cutover branch of `getHashSrc` (or `prosaic_contract.js#getHash`), craft two contracts with identical concatenation but different structured fields:

Contract A: `title = "Pay Bob 100 USD"`, `text = ""`
Contract B: `title = "Pay Bob 100 US"`, `text = "D"`

With identical `creation_date`, `payer_name`, `arbiter_address`, `payee_name`, `amount`, `asset`, both produce the exact same concatenated source string (`"Pay Bob 100 USD" + "" + ... === "Pay Bob 100 US" + "D" + ...`) and therefore the identical `crypto.createHash("sha256")` output in `getHash`, despite the visibly different `title`/`text` split — demonstrating the field-boundary spoofing analogous to CVE-2016-0756's dialback key ambiguity.
