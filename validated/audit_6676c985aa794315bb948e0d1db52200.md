## Missing existence validation on `DeleteAccountAction.beneficiary_id` causes silent burning of the deleted account's balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` lets any account holder delete their own account and redirect the remaining balance to an arbitrary `beneficiary_id`. The protocol validates that `beneficiary_id` is a *syntactically* well-formed `AccountId`, but never validates that the account actually **exists**. If it does not exist, the balance-refund receipt generated for the deletion is guaranteed to fail (refunds cannot trigger implicit account creation), and the failed refund's tokens are unconditionally burnt. This is the exact "missing zero/invalid-address check" bug class from the report, applied to NEAR's `beneficiary_id` field: a trivial typo, copy-paste error, or use of a not-yet-created account silently destroys the deleted account's entire balance with no error surfaced to the actor beyond an internal refund failure.

### Finding Description
`validate_delete_action` only checks that `beneficiary_id` parses as a valid `AccountId` string; it performs no existence check: [1](#0-0) 

When the `DeleteAccount` action executes, the runtime unconditionally emits a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` and then removes the account, without ever checking whether `beneficiary_id` corresponds to an existing account: [2](#0-1) 

`Receipt::new_balance_refund` builds a receipt with `predecessor_id: "system"`, which is the marker for a "refund" receipt: [3](#0-2) 

When this refund receipt is later processed as a `Transfer` action, the runtime explicitly disallows implicit-account creation for refunds: [4](#0-3) [5](#0-4) 

`implicit_account_creation_eligible` is computed as `is_the_only_action && !is_refund`, so for any refund (`is_refund == true`) it is always `false` — meaning `check_transfer_to_nonexisting_account` will always return `AccountDoesNotExist` if the beneficiary account is missing, regardless of whether `beneficiary_id` looks like a valid implicit account.

The protocol documentation confirms the consequence of a failed refund: [6](#0-5) 

So: delete an account with a `beneficiary_id` that does not exist (never created, mistyped, or simply not yet registered) → the account is deleted, the refund receipt to `beneficiary_id` is created, that receipt fails with `AccountDoesNotExist`, and per the documented behavior the refund amount is **burnt** — the account owner's remaining NEAR balance disappears entirely, with no compensating mechanism.

### Impact Explanation
This causes concrete, irreversible token loss: any account's full remaining balance can be destroyed by a single self-submitted `DeleteAccount` action with a non-existent `beneficiary_id`. There is no code path that returns this NEAR to the deleting account, the network, or any recoverable location — the docs explicitly state failed refunds are burnt. This is a direct token-loss impact triggered purely by an ordinary, unprivileged transaction (identical to the underlying "zero/invalid address" bug class referenced in the report — a missing check that a critical destination address is valid/exists before performing an irreversible balance transfer).

### Likelihood Explanation
`DeleteAccountAction` is directly reachable by any account owner via a standard signed transaction or via a contract issuing `promise_batch_action_delete_account`, requiring no special privileges. Typos in `beneficiary_id`, races where the intended beneficiary account has not yet been created, or naive use of an implicit-account-style string as the beneficiary are all realistic, easily-triggered scenarios — mirroring the original report's premise that passing an invalid/zero destination address "in most cases is a mistake."

### Recommendation
Add an existence check for `beneficiary_id` as part of `DeleteAccountAction` validation/execution — either:
- Reject the action (return an `ActionError`, e.g. an `InvalidBeneficiary`/`AccountDoesNotExist`-style validation error) before deleting the account if `beneficiary_id` does not correspond to an existing account, or
- Allow implicit-account creation specifically for the delete-account balance refund case (removing the blanket "refunds never create accounts" restriction for this particular, deliberate, user-specified beneficiary), or
- At minimum, disallow burning in this specific case and instead fail the whole `DeleteAccount` action atomically so the account and its balance are preserved when the beneficiary is invalid/non-existent.

### Proof of Concept
1. Create account `alice.near` with balance `B`.
2. Submit `SignedTransaction` from `alice.near` with a single action: `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent123.near" })`, where `nonexistent123.near` has never been created.
3. `validate_delete_action` passes (format is valid) — see [1](#0-0) .
4. `action_delete_account` deletes `alice.near` and enqueues `Receipt::new_balance_refund(&"nonexistent123.near", B)` — see [2](#0-1) .
5. The refund receipt is later processed against `nonexistent123.near`; since it's a refund (`predecessor_id == "system"`), `implicit_account_creation_eligible` is `false` — see [4](#0-3)  and [5](#0-4) , causing the transfer to fail with `AccountDoesNotExist`.
6. Per documented behavior, the failed refund amount `B` is burnt — see [6](#0-5) . `alice.near`'s entire balance is now unrecoverable.

fn check_transfer_to_nonexisting_account(
    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
}

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
