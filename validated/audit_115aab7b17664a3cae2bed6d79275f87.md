### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the handlers act on the repository named in `repository.full_name` — allowing cross-repository/cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` picks which organization's webhook secret to verify a payload against by reading `repository.owner.login` (or `organization.login`) straight out of the **unauthenticated, attacker-supplied** JSON body, then verifies the HMAC signature using that organization's secret. [1](#0-0) [2](#0-1) 

Once the signature passes, `create` hands the very same raw JSON to the event handlers, but the handlers resolve the actual repository/stack to act on from a **different field of the same payload**: `repository.full_name`. [3](#0-2) [4](#0-3) 

Nothing ties `repository.owner.login` (used to select the verifying secret) to `repository.full_name` (used to select the repository that is actually written to). This is directly analogous to the Gravity bug: a value that gates the trust decision (`_amount` in the signed event / here, the org whose secret is checked) is not the value that determines the real effect (actual tokens transferred / here, the actual repository whose stacks are synced).

### Finding Description
The binding that should hold is:
`organization whose webhook_secret validated the signature == organization owning the repository whose Stacks are mutated`

Concretely:
1. `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)` to get that org's `webhook_secret`, then HMAC-verifies `request.raw_post` against it. [5](#0-4) 
2. If the HMAC matches, `create` dispatches the full JSON body to the registered handlers for the event (e.g. `PushHandler`). [3](#0-2) 
3. Every handler resolves its target `Stack`s via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a completely separate key from `repository.owner.login` used above — and looks up `Repository.from_github_repo_name(repository_name)`. [4](#0-3) 
4. `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the matching branch of that resolved repository. [6](#0-5) 

Because the endpoint is a public, unauthenticated HTTP endpoint whose only gate is this signature check, and because `repository.owner.login` and `repository.full_name` are never cross-validated against each other, anyone who legitimately knows (or controls) the webhook secret for **any one organization** already onboarded to this Shipit instance can craft a payload where:
- `repository.owner.login` = their own organization (so the secret they know verifies the HMAC), and
- `repository.full_name` = an entirely different, victim organization/repository already onboarded to the same Shipit instance.

This causes `Shipit::Webhooks` handlers to run against the victim repository's `Stack`s even though the signature only proves knowledge of a different organization's secret.

### Impact Explanation
This crosses the repository-authorization boundary explicitly called out as in-scope: "an organization that authenticated versus the repository that is written." An attacker who is a legitimate, low-privilege member/administrator of Organization A (with the app installed there and access to A's webhook secret) can forge webhook traffic that mutates state for Organization B's stacks — triggering `sync_github` (and, depending on the event type, other handlers such as `status`, `check_suite`, `pull_request`, or `membership`) for repositories they have no legitimate relationship with. This is a cross-repository write performed under someone else's authorization boundary, satisfying the "cross-repository writes" high/critical impact category, since GitHub-sync driven state changes can affect deploy eligibility (e.g. forcing/blocking sync of undeployed commits) for a stack the attacker does not own.

### Likelihood Explanation
The `WebhooksController` endpoint is intentionally public (it must accept real GitHub webhooks), and the only defense is `verify_signature`. Exploitation requires the attacker to already know one organization's configured `webhook_secret` — a bar that is easily met by anyone who is themselves an org admin configuring/owning that organization's GitHub App installation in Shipit (a routine, semi-privileged but non-Shipit-privileged actor, not requiring any Shipit session, ApiClient token, or repository write access on the victim side). No other credential is required to forge the `repository.full_name` field.

### Recommendation
Ensure the field used to select the verifying webhook secret is the exact same field used by every handler to resolve the target repository. Concretely, derive `repository_owner` from the same `full_name`-based repository record the handlers use (e.g. parse the owner out of `repository.full_name`, or have `Handler#repository_name` and `WebhooksController#repository_owner` share a single, mutually-consistent extraction method), and reject the payload if the two disagree.

### Proof of Concept
1. Attacker is an admin of GitHub organization `attacker-org`, which has the app installed on Shipit with known `webhook_secret = S`.
2. Attacker crafts a JSON body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<sha already present in victim-org/victim-repo>"
}
```
3. Attacker computes `sha1=HMAC-SHA1(S, body)` and sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<computed>
```
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `webhook_secret` = `S`, and the HMAC matches — verification passes. [1](#0-0) 
5. `PushHandler#process` (via `Handler#repository_name` reading `full_name`) resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github(expected_head_sha: ...)` on its stacks — mutating state for a repository entirely unrelated to `attacker-org`, whose secret was actually used for verification. [6](#0-5) [7](#0-6)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
