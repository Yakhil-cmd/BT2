### Title
`StatusHandler#process` matches commits globally by SHA with no per-organization/stack scoping, letting one authenticated repository's status webhook mutate any other tenant's stacks - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Every other GitHub webhook handler (`PushHandler`, `PullRequest::*Handler`) scopes its side effects through `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload['repository']['full_name'])` before touching any `Stack`/`Commit`. `StatusHandler#process` never calls `stacks`; it queries `Commit.where(sha: params.sha)` directly, so any commit row in the entire database sharing that SHA — regardless of which stack/repository/organization it belongs to — gets a `Status` created from attacker-supplied `state`/`description`/`target_url`/`context`.

### Finding Description
The broken binding is: **organization that authenticated the webhook == organization(s) whose stacks are mutated**. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves that the request was signed for `repository_owner` (`payload.dig('repository','owner','login')`), i.e., a *single* org — the one the attacker names in their own payload. It performs no check that the mutated records belong to that org.

`StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This is unscoped — no `.where(stack: stacks)`, no join through `Repository`/`Stack`. Compare with `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which explicitly restricts to `stacks.not_archived.where(branch:)`, where `stacks` comes from `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`), itself scoped by `Repository.from_github_repo_name(repository_name)`.

Because `commits` table has only a `(sha, stack_id)` unique index (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`) — not a global unique index on `sha` — the same SHA can legitimately exist across many unrelated stacks (e.g., the empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904` shared by every freshly initialized empty git repo, or any two forks/mirrors sharing history). `StatusHandler` iterates over *all* matches.

Exploit flow:
1. Attacker owns (or controls the GitHub App configuration for) their own repository/org tracked by Shipit, `attacker/repo`, which is a legitimate Shipit tenant with its own webhook secret — this is the only precondition, and it is normal/unprivileged tenant onboarding, not a Shipit operator role.
2. Attacker sends (or triggers, e.g. by pushing a commit) a `status` event to `POST /webhooks` with `payload['repository']['full_name'] = 'attacker/repo'` and `payload['repository']['owner']['login'] = 'attacker'`, signed with `attacker`'s own webhook secret. `verify_signature` passes because `Shipit.github(organization: 'attacker')` verifies correctly for `attacker`'s own signature.
3. `params.sha` is set to a SHA known to exist in `victim1`, `victim2`, `victim3` stacks (e.g., the shared empty-tree commit, or any commit whose SHA the attacker can discover/guess, since SHAs are public git object hashes, not secrets).
4. `StatusHandler#process` finds and mutates `Commit` rows across all matching stacks, creating `Status` records with attacker-controlled `state`, `description`, `target_url`, `context` for stacks the attacker's org never authenticated.

`create_status_from_github!`/`add_status` (`app/models/shipit/commit.rb`) has downstream side effects: enabling CI on the stack (`Status#enable_ci_on_stack`, `app/models/shipit/status.rb:38-40`), scheduling continuous delivery (`schedule_continuous_delivery`), and — per `test/models/commits_test.rb:763-777` — enqueuing `ProcessMergeRequestsJob`, and potentially triggering deploys if `continuous_deployment` is enabled and the transition is to `success` on the last commit (see `test/models/commits_test.rb:291-297` showing this deploy-triggering path exists, gated by state). A forged `success` status can thus unblock/trigger a deploy on a victim stack the attacker never authenticated against.

None of the listed guards prevent this: `verify_signature` only checks the *claimed* org's signature, not a binding between that org and the mutated commit's owning stack; `ExplicitParameters` schema only validates types of `sha`/`state`/etc., not ownership; `drop_unhandled_event` and `force_github_authentication` are irrelevant to server-to-server webhooks; `Repository`/`Stack` model validations don't constrain cross-tenant commit lookups because `StatusHandler` never queries through `Repository`/`Stack` at all.

### Impact Explanation
A single unprivileged webhook request (self-authenticated only for the attacker's own tenant) writes `Shipit::Status` rows into an unbounded number of unrelated tenants' stacks/commits, matching "a payload for one repository mutating another's stack, commit, task, or team" (Critical). Consequences per compromised commit include: forcing `enable_ci!` on victim stacks, scheduling continuous delivery evaluation, and — depending on stack `continuous_deployment` settings and whether the targeted commit is the stack's HEAD — potentially triggering an unauthorized deploy. This is repeatable against any SHA the attacker can guess or that is trivially shared (empty-tree commits are a certainty across all repos), and blast radius scales with however many tenant stacks happen to share that SHA.

### Likelihood Explanation
Preconditions are minimal and match "unprivileged attacker": the attacker only needs to be a legitimate (even low-trust) tenant with their own repository registered in Shipit and a working webhook (which is automatically configured for any onboarded repo). No cross-tenant secret, GitHub App key, or Shipit session is required — only a validly signed webhook for the attacker's *own* org. Discovering a colliding SHA is trivial for the empty-tree case (constant across all git repos) and plausible for shared history via forks/mirrors/templates. Attack is fully repeatable and requires no timing or race conditions.

### Recommendation
Scope `StatusHandler#process` through `stacks` the same way `PushHandler` does:
```ruby
def process
  Commit.where(sha: params.sha, stack: stacks).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
where `stacks` resolves via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, ensuring only commits belonging to stacks whose repository matches the authenticated payload's `repository.full_name` are mutated.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create 3 fixtures: `Repository`/`Stack` for `attacker/repo`, `victim1/repo`, `victim2/repo`, each with a `Commit` sharing the same `sha` = `"4b825dc642cb6eb9a060e54bf8d69288fbee4904"` (or any fixed test SHA), each in a different stack/organization.
2. Stub/allow signature verification for `attacker`'s org only (`GithubHook.any_instance.stubs(:verify_signature).returns(true)` or mock `Shipit.github(organization: 'attacker')`).
3. POST a `status` webhook event with `payload['repository']['full_name'] = 'attacker/repo'`, `payload['repository']['owner']['login'] = 'attacker'`, `sha` set to the shared SHA, `state: 'success'`.
4. Assert the binding equality before the request: `organizations_authenticated = ['attacker']` vs. `organizations_mutated = Shipit::Status.where(state: 'success').joins(commit: {stack: :repository}).distinct.pluck('repositories.owner')`.
5. Assert `Shipit::Status.where(state: 'success').count` increases by 3 (one per matching commit across all 3 stacks), not 1 — i.e. `organizations_mutated.sort != ['attacker']`, proving the cardinality mismatch and cross-tenant mutation.
