### Title
Webhook signature verification is bound to `repository.owner.login`, but event handlers act on the independently-attacker-supplied `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the raw JSON body. Once the signature check passes, the very same raw JSON body is forwarded unmodified to the event handlers, which instead derive the target repository/stacks from `repository.full_name`. These two fields are independent, attacker-controlled JSON keys in the same payload — nothing ties them together. An attacker who can produce a validly-signed payload for **any one** organization configured in the Shipit instance can set `repository.full_name` to point at a **different** organization's repository, causing handlers to act on stacks that the signing organization has no relationship to.

### Finding Description
`verify_signature` picks the org config purely from payload content: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`create` then dispatches the **whole raw payload**, unfiltered, to every handler for the event:

```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```

Handlers, however, resolve the target stacks from a different field of that same payload — `repository.full_name` — via the shared `Handler` base class: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` (used for signature/organization selection) and `repository.full_name` (used to pick the affected `Repository`/`Stack`) are two independent keys inside the same JSON document the attacker fully controls. Nothing in `WebhooksController` or `Handler` cross-checks that `full_name`'s owner segment equals `repository.owner.login`. This is the same class of "field acted on but not covered by what was actually verified" flaw as the reported Curve issue: the verification is scoped to one identity, while the action is scoped to a different, independently-supplied identity.

### Impact Explanation
Any organization the operator has configured in Shipit (`Shipit.github(organization: ...)`, keyed by `webhook_secret` per org — e.g. a low-trust or self-service organization onboarded to the same Shipit instance) can be used as a valid signer for events that are actually processed against a completely different organization's stacks.
