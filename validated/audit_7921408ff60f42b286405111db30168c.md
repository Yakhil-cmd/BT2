### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for `prevent_with_label`/`allow_with_label` behaviors, creating review stacks for repos with review stacks disabled - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` in `OpenedHandler` combines `review_stacks_enabled` with the provisioning-behavior checks using `&&`/`||` in a way that, due to Ruby operator precedence, only gates the `allow_all` behavior on `review_stacks_enabled`. The `allow_with_label` and `prevent_with_label` branches are evaluated independently of `review_stacks_enabled`, so a repository with `review_stacks_enabled: false` and `provisioning_behavior: 'prevent_with_label'` will still provision a review stack for any PR lacking the provisioning label.

### Finding Description
The expected binding is: stacks are only provisioned when `repository.review_stacks_enabled == true`, regardless of which `provisioning_behavior` is configured. The actual code is: [1](#0-0) 

Due to Ruby's operator precedence (`&&` binds tighter than `||`), this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first disjunct. For a repo configured `review_stacks_enabled: false`, `provisioning_behavior: 'prevent_with_label'`:
- term1: `false && allow_all?` → `false`
- term2: `allow_with_label?` is `false` (behavior enum is `prevent_with_label`) → `false`
- term3: `prevent_with_label?` (`true`) `&& !has_label?` (`true`, attacker adds no label) → `true`

Overall `provision?` returns `true` even though review stacks are disabled for the repo. `respond_to_pull_request_opened?` then permits `process` to call `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which creates a `Shipit::ReviewStack` record with `branch: params.pull_request.head.ref` and queues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`. [2](#0-1) [3](#0-2) 

No existing guard prevents this: the webhook signature check authenticates that the payload came from the configured GitHub repo/app, but does not enforce the `review_stacks_enabled` flag - that enforcement is solely the job of this buggy `provision?` predicate. The identical pattern also exists in `ReopenedHandler#unarchive?`, meaning a PR reopened event on the same misconfigured repo can also unarchive/recreate a stack. [4](#0-3) 

### Impact Explanation
Any attacker who can open a pull request against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` can force Shipit to create a `Shipit::ReviewStack` (and its `PullRequest` record) and queue it for provisioning, using an attacker-controlled `branch` (`head.ref`) and `environment` (`pr#{number}`), fully bypassing the operator's explicit opt-out of review-stack provisioning for that repo. This matches the "unauthorized... a payload for one repository mutating another's stack" pattern class in spirit (an explicit disable control is bypassed to create infrastructure state), though it is scoped to the same repository - it does not cross into unrelated repositories/tenants. Repeatable on every PR the attacker opens against that repo.

### Likelihood Explanation
Requires only that the target repository is configured with `review_stacks_enabled: false` and `provisioning_behavior: 'prevent_with_label'` (a documented, supported, non-default combination an operator could plausibly set while migrating away from review stacks). No label, no privileges, and no secrets are needed - default PR state (no label) already triggers the bug. Attacker cost is a single PR open action via a normal webhook delivery from GitHub for a repo they control (fork/PR).

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "does not provision a stack when review_stacks_enabled is false even with prevent_with_label behavior and no label" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: 'prevent_with_label')

  params = default_params(labels: []) # no provisioning label

  assert_equal false, repository.review_stacks_enabled
  assert_no_difference -> { Shipit::ReviewStack.count } do
    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process
  end
end
```
Before the fix, this assertion fails because `Shipit::ReviewStack.count` increases by 1 - confirming `provision?` returns `true` when `review_stacks_enabled == false` and `provisioning_behavior_prevent_with_label? == true` with no label present.
