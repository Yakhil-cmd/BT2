### Title
Unauthenticated SSE stream at `/events` bypasses `Shipit::Authentication` and exposes live stack/task broadcast data - ([File: config/routes.rb])

### Summary
`Pubsubstub::StreamAction` is mounted directly as a Rack endpoint in the engine's route set, completely outside of `ApplicationController`/`Shipit::ShipitController`, so it never runs the `force_github_authentication` before_action. Any unauthenticated client can `GET /events?channels[]=stack.<id>` and receive the live SSE broadcast for that stack/task, with no session, token, or team membership required.

### Finding Description
The broken binding is: `authorized?(current_user) == true` must hold for every request that reads stack/task broadcast data, but for `/events` this equality is never evaluated at all.

- `config/routes.rb` mounts the stream endpoint at the top level of `Shipit::Engine.routes.draw`: `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` [1](#0-0) .
- All access control in the engine is implemented as a controller concern, `Shipit::Authentication`, which adds `before_action :force_github_authentication` and is only exercised by classes that `include` it [2](#0-1) [3](#0-2) .
- `Shipit::ShipitController < ApplicationController` is the class that actually `include Shipit::Authentication` [4](#0-3) .
- `Pubsubstub::StreamAction` is a plain Rack endpoint (`.new` instance mounted with `mount`), not a subclass of `ApplicationController`/`ShipitController`. Rails `mount` dispatches requests straight into the Rack app's `call` method; it never instantiates any Shipit controller and therefore never runs `force_github_authentication`, `current_user.authorized?`, or any session check.
- Because the mount line sits above/parallel to all `namespace`/`scope`/`resources` blocks that map to Shipit controllers, and Rails engines have no route-level middleware/filter mechanism equivalent to `before_action`, there is no code path in this engine that gates `/events`.

Attacker's exact request: an anonymous HTTP client sends `GET /events?channels[]=stack.<id>` (no cookies, no `Authorization` header) directly to the mounted engine. Pubsubstub accepts the connection, subscribes to the requested Redis pub/sub channel(s), and streams every message published to that channel (task/deploy/stack state changes) as SSE, indefinitely, for any stack id the attacker guesses or enumerates.

Existing guards that were checked and do not apply here: `verify_signature`/webhook signature checks are irrelevant (this is not the webhooks path); `force_github_authentication` and `User#authorized?` are the intended guard but are structurally unreachable for a `mount`-ed Rack app; the `stacks` scope and model validations govern write paths, not this read-only stream; there is no `ExplicitParameters` schema or controller filter applicable to a raw Rack mount.

### Impact Explanation
An attacker gains unauthenticated, repeatable read access to live stack/task/deploy status updates for any stack id they can guess (stack ids appear to be numeric/sequential based on `stack_id_format`/`:id` route usage elsewhere), across every tenant/repository configured on the Shipit instance. This matches the "High - unauthenticated read of stack state, task streams or deploy output" impact category. It does not by itself grant write access, secrets, or RCE, but it discloses deployment activity, task output events, and stack state for arbitrary repositories to anyone who can reach the host over HTTP, with no rate limiting or authentication barrier.

### Likelihood Explanation
No special configuration is required beyond the documented default mount (`mount Pubsubstub::StreamAction.new, at: '/events'`) present in every deployment of this engine. The attacker needs only network access to the Shipit host and knowledge/guessing of a stack id, both trivial given stack ids are small integers or predictable identifiers used throughout the UI/API. No secrets, sessions, or privileged roles are required, matching the "unprivileged attacker" threat model exactly. This is fully repeatable against arbitrary stacks.

### Recommendation
Wrap the `/events` mount with the same authentication guard used by the rest of the engine, e.g. mount it inside a constraint/route that runs through `Shipit::Authentication`, or place a Rack middleware in front of the mounted app that validates `session[:user_id]`/`current_user.authorized?` (and ideally scopes the allowed `channels[]` to stacks the user is authorized to view) before delegating to `Pubsubstub::StreamAction`.

### Proof of Concept
```ruby
# test/integration/unauthenticated_events_stream_test.rb
require "test_helper"

module Shipit
  class UnauthenticatedEventsStreamTest < ActionDispatch::IntegrationTest
    test "GET /events is reachable without any session/authorization" do
      stack = shipit_stacks(:shipit)

      # No session cookie, no api_client token, no login.
      get "/events", params: { channels: ["stack.#{stack.id}"] }

      # Binding under test: authorized?(current_user) must be true for any
      # response other than redirect-to-login/403. Assert it never gets checked:
      assert_not_equal 302, response.status, "expected no redirect to github_authentication_path"
      assert_not_equal 403, response.status, "expected no 'must be a member of ...' rejection"
      # Pubsubstub::StreamAction responds 200 with text/event-stream and starts streaming
      assert_equal "text/event-stream", response.media_type
    end
  end
end
```
This demonstrates that the engine's own middleware/controller stack never rejects the connection before it reaches `Pubsubstub::StreamAction`, confirming the authentication bypass.

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
