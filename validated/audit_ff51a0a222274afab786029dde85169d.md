### Title
`CCMenuController#stack` bypasses `ApiClient#stack_id` scoping for both token and Basic-Auth clients - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuController#authenticate_api_client` authenticates `params[:token]` via the exact same `ApiClient.authenticate` call used for Basic-Auth, so the two authentication mechanisms are not divergent — they resolve to the identical `ApiClient` record with the identical `stack_id` restriction. However, `CCMenuController` overrides the inherited `stack` accessor to call `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!(params[:stack_id])` defined in `BaseController`, so the `stack_id` restriction stored on a scoped `ApiClient` is never enforced for the `#show` action, regardless of whether the client authenticated via the URL `token` or via Basic-Auth.

### Finding Description
Binding as stated by the question: `ApiClient.authenticate(params[:token])` (token path) == `ApiClient.authenticate(token)` (Basic-Auth path via `BasicAuth.authenticate`), both must enforce identical `stacks` scoping.

- `CCMenuController#authenticate_api_client` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`) calls `ApiClient.authenticate(params[:token])`, which is byte-for-byte the same class method used by `BaseController#authenticate_api_client` (`app/controllers/shipit/api/base_controller.rb:48-56`) for Basic-Auth. `ApiClient.authenticate` (`app/models/shipit/api_client.rb:24-27`) just verifies the signed token and loads the same `ApiClient` row — permissions and `stack_id` are identical regardless of transport. So the two authentication paths do **not** diverge in authorization truth; the token is not "weaker" than Basic-Auth.
- The actual scoping bug is elsewhere: `BaseController#stack` (`app/controllers/shipit/api/base_controller.rb:78-80`) correctly scopes lookups through `stacks` (`base_controller.rb:74-76`, `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`). `CCMenuController` overrides this with its own `stack` method (`ccmenu_controller.rb:29-31`) that calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model, completely skipping the `stacks` scope. `require_permission :read, :stack` (`ccmenu_controller.rb:6`) only checks that `"read:stack"` is present in `ApiClient#permissions` via `check_permissions!` (`api_client.rb:38-45`); it does not check `stack_id` at all — that check only happens through the `stacks` scoping helper, which this controller bypasses.
- Consequence: an `ApiClient` created with `stack_id` restricted to stack A can call `GET /stacks/:owner/:repo/:env/cc_menu.xml?token=<token>` (or with Basic-Auth) for any other stack B and receive B's deploy status, because `stack` resolves via unscoped `Stack.from_param!`.

This is a real cross-tenant scope-bypass bug, but it is not caused by a divergence between the token and Basic-Auth authentication paths as framed in the question — it affects both paths identically, because the root cause is the overridden `stack` accessor in `CCMenuController`, not `authenticate_api_client`.

### Impact Explanation
An `ApiClient` scoped to one stack can read CI/CD deploy status (`stack.deploys_and_rollbacks.last`, environment name, branch) for any other stack on the same Shipit instance, via either the `token` query parameter or Basic-Auth. This is a cross-tenant unauthorized read of stack state, matching the High-severity category "unauthorized read of stack state." It is fully repeatable against arbitrary stacks by any holder of a validly-signed, stack-scoped `ApiClient` token (or the same value leaked via server/proxy logs since it's passed in the URL). It does not achieve RCE, credential exfiltration, or write access, so it does not reach Critical.

### Likelihood Explanation
Requires possession of a valid, signed `ApiClient` token (created by a Shipit operator with `stack_id` restricted to a given stack) — the attacker must already be a legitimate, if narrowly-scoped, API client, or must have intercepted such a token from logs (as the question posits for the URL-token vector). Given that precondition, exploitation is a single unauthenticated-scope HTTP GET with an arbitrary `stack_id` — trivial and fully repeatable, no GitHub secrets or webhook forgery needed.

### Recommendation
Remove the `stack` override in `CCMenuController` and rely on the inherited, properly-scoped `stack` method from `BaseController` (i.e., use `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so `current_api_client.stack_id` is enforced identically for the `#show` action.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "#show does not return data for a stack outside the client's stack_id scope" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cocoaframework) # a different stack

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-client',
    stack_id: stack_a.id,
    permissions: ['read:stack'],
  )

  get "/stacks/#{stack_b.repo_owner}/#{stack_b.repo_name}/#{stack_b.environment}/cc_menu.xml",
      params: { token: scoped_client.authentication_token }

  # Binding under test: token path must enforce the same stack_id scope as Basic-Auth.
  # Expected (secure) behavior: request for stack_b should be rejected/not found
  # because scoped_client.stack_id == stack_a.id, not stack_b.id.
  assert_response :not_found
  refute_includes response.body, stack_b.environment
end
```
Running this against the current code shows the request succeeds (`200 OK`) and returns stack B's data, confirming that `stack_id` scoping is not enforced in `CCMenuController#show` for either the `token` or Basic-Auth authentication path — the divergence claimed between the two auth mechanisms does not exist (both are authenticated identically via `ApiClient.authenticate`), but the underlying scope-bypass in the overridden `stack` method is real and independently exploitable.
