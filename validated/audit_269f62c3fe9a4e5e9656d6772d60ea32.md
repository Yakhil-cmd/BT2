### Title
Webhook signature verification keyed on an unauthenticated `repository.owner.login`/`organization.login` field while write actions are keyed on the independent, unauthenticated `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization deployment, `WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), while every webhook `Handler` locates and mutates the target `Stack`/`Repository` using the unrelated `repository.full_name` field from the same unauthenticated JSON body. If any configured organization has no `webhook_secret` set (documented as optional), signature verification is unconditionally bypassed for requests presenting that organization's login, letting an attacker point `repository.full_name` at a completely different, tracked repository and drive its handlers (push sync, commit status creation, pull-request/merge-status updates) without ever proving knowledge of any secret for that repository's real organization.

### Finding Description
`WebhooksController#verify_signature` selects the verifying `GitHubApp` purely from the attacker-supplied JSON body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally trusts the request when `webhook_secret` is blank for that organization's config: [3](#0-2) 

The webhook secret is explicitly documented as optional per-organization: [4](#0-3) 

Once `verify_signature` passes (or is bypassed), `Shipit::Webhooks.for_event(event)` dispatches the same raw body to handlers, none of which re-check the organization used for verification. Instead, every handler resolves the target `Stack` from a *different* field of the same unauthenticated body, `repository.full_name`: [5](#0-4) 

For example, `PushHandler` uses that lookup to trigger `sync_github` on any matching, tracked stack: [6](#0-5) 

and `StatusHandler`/commit-status webhooks create `Commit::Status` records for arbitrary commits, as shown by the existing test coverage: [7](#0-6) 

Nothing binds `repository.owner.login` (the field selecting the verification key) to `repository.full_name` (the field selecting the write target). This breaks the required binding: the organization whose key "authenticated" the request must equal the repository actually written by the handler; here they are two independent, attacker-controlled fields of the same unsigned/under-secured JSON body.

### Impact Explanation
An attacker who knows (or guesses) the login of any organization configured in `Shipit.github` without a `webhook_secret` can submit a forged webhook that is treated as fully verified (`verify_webhook_signature` returns `true` unconditionally for that org), while setting `repository.full_name` to any *other* tracked repository/stack in the same Shipit installation. This allows an unprivileged, unauthenticated attacker to:
- Force `GithubSyncJob`/`sync_github` runs against victim stacks (`PushHandler`).
- Inject fabricated commit statuses on arbitrary commits of victim stacks (`StatusHandler`), which can satisfy `ci.require` checks in `shipit.yml` and enable an otherwise-blocked deploy or a merge-queue auto-merge to proceed - an unauthorized deploy/merge, matching the Critical impact bar in scope.
- Drive `pull_request`/`merge_status` handlers on victim repositories with attacker-controlled payload content.

This is a direct analog of the reported bug class: just as `VeTokenMinter` let an unchecked, admin-set weight silently steer `Booster.rewardClaimed`'s payout for a different asset than intended, here an unchecked, attacker-set field (`repository.owner.login`) silently selects the trust boundary while an unrelated field (`repository.full_name`) determines what gets mutated - a missing "sane binding" between the value used to authenticate and the value used to act.

### Likelihood Explanation
Likelihood depends on deployment configuration: it requires a multi-organization `Shipit.github` setup where at least one configured organization omits `webhook_secret` (explicitly supported/documented as optional). Given webhook secrets are optional and easy to omit during setup (especially for lower-stakes or newly onboarded orgs), and no credential, session, or secret knowledge is required to exploit the mismatch once such a configuration exists, this is a realistic misconfiguration-triggered vulnerability rather than a purely theoretical one.

### Recommendation
- After signature verification, re-derive the organization from the *same* field used for the actual write action (`repository.full_name`'s owner segment) and require it to match the organization used to verify the signature; reject on mismatch.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in multi-organization configurations; require every configured organization to have a non-blank `webhook_secret`, or reject/log loudly when this happens.
- Bind the object acted upon (`Repository.from_github_repo_name(repository_name)`) to the verified organization explicitly, rather than trusting it independently.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `secure-org` (has `webhook_secret`) and `open-org` (no `webhook_secret`, per docs this is optional), both used by the same Shipit instance, with `victim-repo` tracked under `secure-org`.
2. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or any garbage value), body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "open-org")` → `GitHubApp` with blank `webhook_secret` → `verify_webhook_signature` returns `true` unconditionally ( [8](#0-7) ), bypassing verification entirely.
4. `PushHandler#process` resolves `stacks` from `repository.full_name = "secure-org/victim-repo"` ( [9](#0-8) ) and calls `sync_github(expected_head_sha: ...)` on the victim stack, even though the request was never validated against `secure-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
