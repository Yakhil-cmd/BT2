### Title
Unchecked `INSERT IGNORE` in `addNewSharedAddress` Allows Signing-Path/Device-Address Squatting and Permanent Freeze of Shared-Address Funds - (File: wallet_defined_by_addresses.js)

### Summary
`addNewSharedAddress()` writes rows to `shared_address_signing_paths` (keyed `UNIQUE(shared_address, signing_path)`) using `INSERT `+db.getIgnore()`, exactly the unchecked-return-value pattern flagged in the source report (`dispatcher.add` silently returning `false` on a pre-existing key). The insert's success/failure is never checked, so whichever `new_shared_address` message reaches a device first "wins" the `signing_path → device_address` binding for a given member address, and any later, correct message for the same path is silently dropped.

### Finding Description
`handleNewSharedAddress()` [1](#0-0)  validates that each `signing_path`'s claimed member `address` matches the address actually referenced at that path in the definition (via `extractAddressPathsFromDefinition`), but it does **not** validate that the claimed `device_address` for that signing path is the legitimate/expected correspondent for that member address. It then calls `addNewSharedAddress()`.

`addNewSharedAddress()` persists the mapping with an ignored-on-conflict insert: [2](#0-1) 

Because the primary key of `shared_address_signing_paths` is `(shared_address, signing_path)` and the statement uses `db.getIgnore()`, the affected-rows / success of the insert is never checked. If two different `new_shared_address` messages (or forwarded copies) arrive for the same `shared_address`/`signing_path` with different `device_address` values, the first one to be processed is durably kept and every subsequent (possibly correct) message for that same path is silently discarded — exactly analogous to the reported `dispatcher.add` return-value bug, where the "second" registration for an existing key silently fails and the caller has no way to detect or react to it.

This binding is later trusted as the authoritative route for signing requests: `findAddress()` reads `device_address` straight from `shared_address_signing_paths` to decide who to ask to sign [3](#0-2) , and `wallet.js`'s signer forwards the actual signing request only to that `device_address`, refusing anyone else (`"you are not listed as a cosigner for this address"`) [4](#0-3) .

### Impact Explanation
Any device that is a correspondent of the address owner (this message class is processed via `device.js`'s message pipeline reachable from any paired device — an "asset issuer / private-payment counterparty / paired device" surface) can send (or race to deliver) a crafted `new_shared_address` message naming itself as `device_address` for a signing path whose `address` legitimately belongs to a victim's key. Because the address-vs-path check passes (the address at that path is real) but the device binding is never re-validated once first set, and the insert that would correct/refresh the mapping is silently ignored, the shared/multisig address's signing_path becomes permanently pinned to the attacker's (or simply wrong) device. All future spend/signing requests for that member address+path will be routed to that device via `sendOfferToSign`/`ifRemote` and never reach the legitimate co-signer, permanently freezing funds held at that shared address (an AA/wallet fund-freezing condition), since the legitimate signer is never asked and the composer has no fallback.

### Likelihood Explanation
Medium: it requires the attacker to be a paired device (correspondent) able to send a `new_shared_address` justsaying to a victim device, or to win a race against the legitimate propagation of the real definition (which is plausible since `sendNewSharedAddress`/forwarding is asynchronous and multi-hop across `forwardNewSharedAddressToCosignersOfMyMemberAddresses`). No cryptographic forgery is needed — the attacker only needs a valid definition/signers structure that passes the `assocDefinitionAddresses[signing_path] === signerInfo.address` check, which is derivable from any legitimately shared definition once observed (e.g. from a prior legitimate `new_shared_address` message the attacker was copied on, or one they help construct as a claimed cosigner in `createNewSharedAddressByTemplate`/`validateAddressDefinitionTemplate`).

### Recommendation
- Check the affected-rows result of the `INSERT ... IGNORE INTO shared_address_signing_paths` in `addNewSharedAddress()`, and when a row already exists for `(shared_address, signing_path)`, explicitly verify that the new `device_address`/`address` matches the existing one; reject (and surface an error/alert) on mismatch instead of silently keeping-or-dropping.
- Do not allow the `device_address` binding for a signing path to be established or overwritten purely from an unauthenticated peer-supplied message; cross-check against `correspondent_devices`/wallet-approval state, or require multi-party confirmation (as already implemented for `pending_shared_address_signing_paths` via `approvePendingSharedAddress`, which is the "approved" flow) before trusting a `device_address` binding for signing routing.
- Add explicit conflict handling/logging wherever `db.getIgnore()` is used for security-relevant tables (`shared_address_signing_paths`, `shared_addresses`) so silent duplicate-suppression is never mistaken for successful registration, mirroring the report's recommendation to check return values of calls that can return false.

### Proof of Concept
1. Attacker device D_A is a correspondent of victim device D_V, and both are cosigners (or D_A learns) of a shared address definition `Def` where signing_path `r.1` legitimately maps to member address `Addr_V` owned by D_V.
2. Before the genuine `new_shared_address` message (with the correct `signers['r.1'] = {address: Addr_V, device_address: D_V}`) is delivered/forwarded to the target node (e.g. it is delayed by network hops through `forwardNewSharedAddressToCosignersOfMyMemberAddresses`), attacker D_A sends its own `new_shared_address` justsaying with the same `body.definition` (so `body.address` / c-hash checks pass) but `body.signers['r.1'] = {address: Addr_V, device_address: D_A}`.
3. `handleNewSharedAddress()` passes all validations (`assocDefinitionAddresses['r.1'] === Addr_V` still holds) and calls `addNewSharedAddress(address, arrDefinition, signers, ...)`.
4. `addNewSharedAddress()` runs `INSERT `+db.getIgnore()+` INTO shared_address_signing_paths ... VALUES (address, Addr_V, 'r.1', member_signing_path, D_A)`, which succeeds and is stored (first writer wins).
5. When the genuine message from D_V's side later arrives with `device_address: D_V` for the same `(shared_address, 'r.1')`, the same `INSERT IGNORE` is executed, but since the row already exists it is silently ignored — the return value is never checked, so no error is raised and the legitimate binding is never installed.
6. Any subsequent attempt to spend from the shared address causes `wallet.js`'s `findAddress`/signer logic to route the signing request for path `r.1` to `D_A` (`sendOfferToSign(D_A, ...)`), not to `D_V`; `D_A` never responds (or actively refuses), permanently blocking completion of the multisig transaction and freezing funds at the shared address.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
