This confirms the vulnerability. `Shipit.github(organization:)` looks up per-organization config keyed by name, each with its own independent `webhook_secret` [1](#0-0) , and `Shipit::Webhooks.for_event` dispatches to handlers with the raw, unscoped `params` regardless of which organization's secret validated the request [2](#0-1) , [3](#0-2) .

### Title
Cross-organization stack mutation via decoupled webhook signature org and target repository resolution - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb, app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb)

### Summary
`WebhooksController#verify_signature` verifies the HMAC signature using an app config selected by `params.dig('repository','owner','login')` (or `organization.login`), while every `pull_request` handler (including `LabelCapturingHandler`) resolves the actual target `Repository`/`Stack` from the independent `params.repository.full_name` field. These two JSON fields are never cross-checked, so a request signed with one organization's `webhook_secret` can carry a `repository.full_name` pointing at a completely different organization's repository/stack.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces: `organization_that_verified_signature (params.repository.owner.login) == organization_owning_the_resolved_repository (params.repository.full_name.split('/').first)`.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and does `github_app = Shipit.github(organization: repository_owner)`, then verifies the signature against **that org's** `webhook_secret` [4](#0-3) .
- `Shipit.github(organization:)` looks up a fully independent per-organization config block (`github_app_config(organization)`), each with its own `webhook_secret`, `private_key`, etc, per the documented multi-org deployment model [1](#0-0) , [5](#0-4) .
- Once verified, `create` hands the **entire raw JSON body** (unmodified, unscoped) to every registered handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .
- `LabelCapturingHandler#repository` resolves the target repository from `params.repository.full_name` (a separate field from `repository.owner.login` used for signature verification), via `Shipit::Repository.from_github_repo_name` [6](#0-5) .
- `ReviewStackAdapter#stack` finds `scope.find_by(environment:)` where `scope = repository.review_stacks` and `environment = "pr#{params.number}"` [7](#0-6) , [8](#0-7) .
- `capture_labels` then calls `stack.pull_request.update!(labels: params.pull_request.labels.map(&:name))`, mutating the resolved stack's `PullRequest` record [9](#0-8) .

Exploit flow: An attacker who legitimately owns/administers "attacker-org" — a real, separate tenant onboarded into the same multi-org Shipit deployment, and therefore knows attacker-org's `webhook_secret` (they configured it when setting up their own GitHub App per the documented multi-tenant flow) — POSTs directly to `/webhooks` with:
- `X-Github-Event: pull_request`
- `X-Hub-Signature` computed with attacker-org's own `webhook_secret`
- body: `{"action":"reopened","number":42,"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/some-repo"}, "pull_request": {...,"labels":[{"name":"malicious-label"}]}, "sender": {...}}`

`verify_signature` passes (attacker-org's secret matches attacker-org's own signature). The handler then resolves `repository.full_name = "victim-org/some-repo"`, unrelated to the org that verified the signature, finds the victim's `Repository`, and if the victim has a review stack whose environment happens to be `pr42` (a predictable, guessable naming scheme `pr#{number}` used by every review stack), `LabelCapturingHandler` overwrites that PR's labels. `ReopenedHandler#unarchive!` would similarly de-archive/re-provision the victim's stack (`stack.unarchive!` invoked with `params.sender.login`, an attacker-controlled login used to `find_or_create_by_login!` as the acting user).

No existing guard prevents this: `drop_unhandled_event` and `check_if_ping` only gate on event type; the `ExplicitParameters` schema validates types/presence but performs no cross-field equality between `repository.owner.login` and `repository.full_name`'s owner segment; `verify_signature` only authenticates that the requester knows some organization's secret, not that the claimed target repository belongs to that organization; `Repository.from_github_repo_name`/`review_stacks` scoping trusts `full_name` at face value with no re-derivation from the verified org.

### Impact Explanation
An attacker who is a legitimate (but otherwise unprivileged w.r.t. the victim) tenant of a multi-organization Shipit deployment can mutate another tenant's live `PullRequest#labels`, and (via `ReopenedHandler`) de-archive/re-provision or (via `LabelCapturingHandler`+other pull_request handlers) otherwise manipulate another tenant's `Stack`/`ReviewStack` state, without any relationship to that repository or organization. This matches the explicitly listed Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any repository/organization onboarded to the same Shipit instance, for any PR number the attacker can guess (numbers are small, sequential, and typically discoverable/guessable), and generalizes beyond `LabelCapturingHandler` to every `pull_request` handler that derives its target `Repository` from `params.repository.full_name` (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `AssignedHandler`, `EditedHandler`) since none of them re-verify the org.

### Likelihood Explanation
Requires the Shipit deployment to use the documented multi-organization `github:` config (separate `webhook_secret` per org) with at least two distinct onboarded organizations. The attacker must be an admin/owner of one legitimately onboarded org (able to configure and thus know its own `webhook_secret`) but need not have any privilege on the victim org. Cost is a single crafted HTTP POST; no GitHub-side interaction, no live GitHub calls, and no secrets beyond the attacker's own org's secret (which they legitimately possess) are required. Fully repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after, before dispatch), assert that the organization used to select the verifying `GitHubApp`/secret matches the owner segment of `params.repository.full_name` (and reject/`head(422)` when mismatched or when `full_name` is absent). Alternatively, have every handler derive its target repository strictly from the same `repository_owner` value that was already authenticated, rather than independently trusting `params.repository.full_name`.

### Proof of Concept

test "cross-organization pull_request payload cannot mutate another org's stack" do
  # Arrange: two orgs, two repos, colliding environment naming ("pr42")
  attacker_repo = Repository.create!(owner: "attacker-org", name: "attacker-repo")
  victim_repo   = Repository.create!(owner: "victim-org", name: "victim-repo")
  victim_stack  = create_review_stack(repository: victim_repo, environment: "pr42")

  payload = payload_parsed(:pull_request_reopened)
  payload["number"] = 42
  payload["repository"]["owner"] = { "login" => "attacker-org" } # org that verified signature
  payload["repository"]["full_name"] = "victim-org/victim-repo"  # org with NO relationship
  payload["pull_request"]["labels"] = [{ "name" => "malicious-label" }]

  # Binding under test:
  #   verified_org  = payload["repository"]["owner"]["login"]      == "attacker-org"
  #   resolved_repo_org = payload["repository"]["full_name"].split("/").first == "victim-org"
  # assert verified_org != resolved_repo_org (cross-org divergence exists)
  assert_not_equal payload["repository"]["owner"]["login"],
                    payload["repository"]["full_name"].split("/").first

  LabelCapturingHandler.new(payload).process

  # Bug demonstration: victim's stack/PR was mutated despite signature belonging to a different org
  assert_includes victim_stack.reload.pull_request.labels, "malicious-label"

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
