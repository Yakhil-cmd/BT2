### Title
Cross-repository forged CI status via unscoped `Commit.where(sha:)` lookup in `StatusHandler` enables unauthorized merge - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `sha`, with no scoping to the repository named in the webhook payload, unlike every other handler in the same module (`PushHandler`, `PullRequest::*`) which resolve `stacks` via `Repository.from_github_repo_name(repository_name)` before acting. Because GitHub's "create commit status" API does not require the target `sha` to exist in the calling repository's history, an attacker who controls (or legitimately owns) any repository already onboarded to the same Shipit instance can push a real, correctly-signed `status` webhook for their own repo naming an arbitrary/foreign `sha`, and Shipit will attach that forged status to any `Commit` row anywhere in the database that happens to share that sha - including a victim stack's stalled/never-passing merge request head commit.

### Finding Description
The broken binding, stated explicitly: the equality that should hold is
`Status.state authorized for sha S` iff `webhook.payload.repository.full_name == stack.github_repo_name owning commit(sha=S)`.
In code, this equality is never checked: [1](#0-0) 

`params.sha` and `params.state` come straight from the webhook body; `process` does `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` with no reference to `params.repository` at all.

Contrast this with the base `Handler#stacks` helper, which every other handler uses to scope work to the repository actually named in the payload: [2](#0-1) [3](#0-2) 

`WebhooksController#verify_signature` only proves that the request was signed with the secret belonging to `Shipit.github(organization: repository_owner)`, i.e. the organization *named in the payload* - it says nothing about which `sha`/commit the payload is allowed to touch: [4](#0-3) 

The database schema itself confirms `sha` is not globally unique - it is only unique per `(sha, stack_id)` pair - so identical sha strings legitimately coexist across unrelated stacks/repositories: [5](#0-4) 

`Status.replicate_from_github!` is purely additive (`find_or_create_by!`), so a forged status is not purged by a later legitimate `refresh_statuses!` poll of the real repository; it simply becomes the only status recorded for that `context` if no genuine CI ever posted one: [6](#0-5) [7](#0-6) 

Exploit flow:
1. Attacker owns/controls a repository already tracked by Shipit (any org, any low-risk stack) with a legitimate GitHub-configured webhook (`X-Hub-Signature` computed by GitHub with the real secret - attacker never needs to know the secret).
2. Attacker opens a low-risk PR (`MergeRequest.request_merge!`) against the victim stack, or simply reads the public head sha of the victim's stalled/rejected `MergeRequest` (PR head shas are public GitHub metadata).
3. Attacker calls GitHub's "create commit status" API on their own repository with `sha = victim_head_sha`, `state = success`, and a `context` matching one of the victim stack's `merge_request_required_statuses` / `ci.require` entries.
4. GitHub delivers a `status` webhook to Shipit, signed with the secret for the attacker's own organization - `verify_signature` passes because that organization's secret is legitimately correct.
5. `StatusHandler#process` matches `Commit.where(sha: victim_head_sha)`, which includes the victim's `Commit` row (belonging to the victim's `stack`), and creates a `Status` record with `state: 'success'` on it, scoped to the victim's `stack_id` (via `stack.enable_ci_on_stack`/`add_status`).
6. `Status#after_commit :schedule_continuous_delivery` (and `Commit`'s deployable-status hook) trigger `ProcessMergeRequestsJob.perform(stack)` for the victim stack.
7. In `ProcessMergeRequestsJob#perform`, the victim's pending `MergeRequest` is refreshed (`refresh!` re-polls the *real* victim GitHub repo's statuses, which is additive and doesn't remove the forged status; if no genuine status exists for that context, the forged one is the only entry), then `merge_request.all_status_checks_passed?` returns true via `StatusChecker.new(head, head.statuses_and_check_runs, ...).success?`.
8. `merge_request.merge!` executes `stack.github_api.merge_pull_request(stack.github_repo_name, number, ..., sha: head.sha, ...)` using the victim stack's own `GITHUB_TOKEN`, merging code that never had genuine passing CI. [8](#0-7) [9](#0-8) 

None of the listed guards intercept this: `verify_signature` checks signature-per-organization only, not sha ownership; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape (`sha`, `state`, etc.), not repository binding; there is no `stacks`/`Repository.from_github_repo_name` scoping in `StatusHandler` at all, unlike its sibling handlers.

### Impact Explanation
Critical. An unprivileged GitHub user who merely controls their own onboarded repository can cause Shipit to execute an authenticated `merge_pull_request` call, using the victim stack's `GITHUB_TOKEN`/GitHub App credentials, merging a pull request whose head commit never received real passing CI in the victim's own repository. This is a cross-tenant authentication-bypass: a payload authenticated for repository A is used to mutate repository B's commit/status/merge-request state, satisfying "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized merge." It is repeatable against any stack whose stalled merge request's head sha the attacker can learn (trivially public via the PR page) and any repository the attacker controls that is already onboarded to the same Shipit instance.

### Likelihood Explanation
Preconditions: `stack.allows_merges?` true and merge queue enabled (per the question's own precondition, matching normal Shipit merge-queue usage); the attacker must control at least one repository already tracked/onboarded on the target Shipit instance (very low bar - could be their own personal repo added under a stack they own) with a real GitHub webhook wired to the same Shipit host; they need only call GitHub's normal "create commit status" API with an arbitrary `sha`, which GitHub permits without validating that the sha exists in that repo's history. No secrets, no session, no maintainer role on the victim repo are required. This is highly feasible and repeatable at will.

### Recommendation
Scope `StatusHandler#process` to the repository actually named in the payload, mirroring `PushHandler`/`PullRequest::*`: resolve `stacks` via `Repository.from_github_repo_name(params.repository.full_name)` (or the commit's own `stack.github_repo_name`) and only apply the status to commits belonging to stacks whose repository matches the payload's `repository.full_name`, e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })` or filter `Commit.where(sha: params.sha).select { |c| c.stack.github_repo_name == params.repository.full_name }`. Require `repository.full_name` in the `StatusHandler` params schema (it is currently optional/unused) and reject/ignore statuses whose payload repository doesn't match the commit's owning stack.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extend `webhooks_controller_test.rb`):
1. Create `stack_victim` (repo `victim/repo`) with a `Commit` `head` (`sha = "deadbeef...`) belonging to a pending `MergeRequest`, with no successful status for a required context (e.g. `ci/travis`), and `merge_queue_enabled: true`, `merge_request_required_statuses = ['ci/travis']`.
2. Send a `status` webhook payload with `repository.full_name = "attacker/unrelated-repo"`, `sha = head.sha`, `state = "success"`, `context = "ci/travis"`, correctly signed for `attacker`'s organization (stub `verify_signature` to true, matching existing test patterns).
3. Assert: `Status.where(commit: head, state: 'success', context: 'ci/travis').exists?` becomes true even though `repository.full_name` differs from `stack_victim.github_repo_name`.
4. Then run `Shipit::ProcessMergeRequestsJob.new.perform(stack_victim)` with `Shipit.github.api.expects(:merge_pull_request).with(stack_victim.github_repo_name, merge_request.number, anything, sha: head.sha, ...)` and assert it fires, and `merge_request.reload.merged?` is true - demonstrating the merge executes off a status created via a payload naming a different `repository.full_name`.

      end

      true

      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
