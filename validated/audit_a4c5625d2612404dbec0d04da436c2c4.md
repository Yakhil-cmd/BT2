### Title
Cross-organization webhook confusion: signature verified against `repository.owner.login` while writes are keyed by `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization config (and thus the webhook secret) using an attacker-supplied field of the *same* JSON payload it is about to verify, while every downstream handler resolves *which Stack/Repository to mutate* using a different, independently-controlled field of that payload (`repository.full_name`). Nothing binds the "organization whose secret validated this signature" to the "repository that gets written to," so a payload signed with organization A's webhook secret can carry a `repository.full_name` pointing at a stack owned by organization B, and Shipit will act on it.

### Finding Description
`verify_signature` derives the signing organization purely from the payload: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once the HMAC check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the entire, now-"trusted" payload to handlers such as `PushHandler`. Handlers never re-check that `repository.owner.login` (the field that selected the signing secret) matches the `repository.full_name` (the field that selects which stacks are mutated): [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` then syncs every matching stack directly from this unauthenticated-with-respect-to-org value: [4](#0-3) 

The same pattern repeats in the review-stack pull_request handlers, which key stack creation/archival purely off `params.repository["full_name"]` and `params.number`, with no cross-check against the verifying organization: [5](#0-4) 

This mirrors the reported analog exactly: the pool-address bug let a field (`to`) that is *not* covered by the accounting invariant (`liquidity leaves/enters`) diverge from the field that *is* covered (`reserve.updateInterestRates` assumption), causing the update to be applied to the wrong side of the equation. Here, `repository.owner.login` (bound to secret selection / "authentication") and `repository.full_name` (bound to "which repository is written") are two different, independently attacker-controlled sub-objects of one JSON body; HMAC verification proves the whole byte string was signed by *some* configured secret, but it does not prove any relationship *between* those two sub-fields. The binding that should hold — "organization whose key signed this == organization owning the repository being written" — is never enforced.

### Impact Explanation
If an attacker (or a compromised/malicious low-privilege GitHub App installation) controls a webhook secret for *any* organization configured in `Shipit.github`, they can forge a `push` or `pull_request` payload with an arbitrary `repository.full_name`. Because verification only proves "this body was signed by org A's secret," not "this body may only reference org A's repos," the attacker can trigger `GithubSyncJob`, create/unarchive Review Stacks, or archive them for a stack belonging to an entirely different, unrelated organization/repository. This is a cross-repository/cross-organization write triggered without holding any credential tied to the victim repository, satisfying the "cross-repository writes" Critical-impact bucket.

### Likelihood Explanation
Exploitation requires possession of a valid webhook secret for *some* organization onboarded to the Shipit instance — a realistic scenario in multi-tenant/enterprise Shipit deployments where many orgs share one Shipit instance but each configures its own GitHub App/webhook secret. No repository write access, API token, or session is needed; only the ability to deliver a crafted HTTP POST with a correctly computed HMAC using a secret the attacker legitimately possesses for their own (unrelated) organization. This is a plausible confused-deputy condition inherent to how `repository_owner` and `repository_name` are decoupled.

### Recommendation
After signature verification, re-validate that the field used to select the verifying secret is consistent with the field used to select the affected resource — e.g., require that the `Repository` resolved from `repository.full_name` actually belongs to the organization identified by `repository_owner`/`repository.owner.login`, and reject the webhook otherwise. Alternatively, bind `Repository#from_github_repo_name` lookups to also check the owning organization matches the one that produced a valid signature.

### Proof of Concept
1. Attacker legitimately manages "Org-Attacker" in the target Shipit instance and knows its webhook secret (a normal GitHub App configuration on their own org).
2. Attacker computes a valid `X-Hub-Signature` for a JSON body using Org-Attacker's secret, but sets `repository.full_name` to `"victim-org/victim-repo"` (a stack actually owned by a different organization on the same Shipit instance) and `repository.owner.login` to `"Org-Attacker"`.
3. `verify_signature` calls `Shipit.github(organization: "Org-Attacker")` and successfully validates the HMAC (it was computed with that org's secret over the exact body sent).
4. `PushHandler#process` (or the review-stack PR handlers) resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and syncs/creates/archives stacks belonging to `victim-org`, even though the signing organization never had rights over that repository.
