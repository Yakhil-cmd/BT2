### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while handlers act on the unrelated `repository.full_name` field, allowing cross-organization forged webhooks in multi-app deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment (the officially documented "Using Multiple Github Applications" configuration), `WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used to validate the inbound HMAC using `repository_owner`, a value read from `payload.dig('repository','owner','login')` (or `organization.login`). All downstream webhook handlers, however, resolve the actual `Repository`/`Stack` to mutate using a completely different field, `payload.dig('repository','full_name')`. Nothing ties these two fields together, so a party who legitimately controls the webhook secret for one onboarded, lower-trust organization can forge a validly-signed webhook whose `repository.owner.login` matches their own org (so signature verification passes) while `repository.full_name` points at a repository belonging to a different, unrelated organization also onboarded to the same Shipit instance.

### Finding Description
`verify_signature` computes the app/secret to check against from `repository_owner`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a **per-organization** config (different `webhook_secret`, `app_id`, `private_key`) when the "multiple GitHub Applications" schema is used, as documented and tested: [3](#0-2) [4](#0-3) [5](#0-4) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire raw payload* to handlers: [6](#0-5) 

All handlers derive the repository to act on from `payload.dig('repository','full_name')`, via the shared `Handler#repository_name`/`#stacks`, or explicit `Repository.from_github_repo_name(params.repository.full_name)` (push, status, pull-request handlers): [7](#0-6) [8](#0-7) [9](#0-8) 

`Repository.from_github_repo_name` splits `owner/name` straight out of that field with no cross-check against the org used for signature verification: [10](#0-9) 

The equality that should hold but does not:
`repository_owner` (the field the verified HMAC signature is scoped to) == the org portion of `repository.full_name` (the field every handler actually writes against). Nothing in `verify_signature` or in `Handler` enforces this equality, and the HMAC only proves the *raw body was signed by whichever org's secret was picked*, not that the `full_name` inside that body legitimately belongs to that org.

### Impact Explanation
In the documented multi-org setup, an attacker who legitimately controls the GitHub App/webhook secret for OrgA (a low-privilege org onboarded to the same Shipit instance) can craft and HMAC-sign a payload where `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/victim-repo"` for a higher-privilege org OrgB tracked by the same Shipit instance. `verify_signature` validates successfully (it authenticates OrgA, whose secret the attacker holds), and the dispatched handlers then act on OrgB's repository/stacks:
- `PushHandler` enqueues `GithubSyncJob` for OrgB's stacks with an attacker-chosen `expected_head_sha`, effectively driving unauthorized sync/deploy state for a repository the attacker does not control.
- `StatusHandler` can inject fabricated CI statuses onto OrgB commits, which can unblock deploys/merges gated on commit status.
- `PullRequest::OpenedHandler`/`ClosedHandler` can create or archive OrgB review stacks.

This is a cross-organization write achieved purely by forging the `repository`/`organization` fields of a payload signed with a different, less-privileged org's secret — matching the "organization that authenticated versus the repository that is written" trust-binding break, and reaching the Critical "cross-repository writes" / unauthorized-deploy-influencing impact bar.

### Likelihood Explanation
This requires: (1) the Shipit deployment uses the multi-organization GitHub App config (explicitly documented and supported), and (2) the attacker has legitimate webhook-sending capability for at least one onboarded organization (i.e., is a webhook-secret holder for some org configured on the instance, but not the target org). This is a realistic scenario for shared Shipit instances serving multiple, differently-trusted GitHub orgs — exactly the use case the multi-app feature exists for.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that the organization used to select the verifying GitHub App/secret matches the organization embedded in `repository.full_name` (and in `organization.login` for org-scoped events) before dispatching to handlers. Reject the webhook (422) if the two disagree, rather than only checking a single flexible field independent from the field handlers actually consume.

### Proof of Concept
1. Deploy Shipit with the multi-org config (`config/secrets.yml` using the `github: { OrgA: {...}, OrgB: {...} }` schema), tracking a stack for `OrgB/victim-repo` (secret `S_B`) and also onboarding `OrgA` (secret `S_A`, held by attacker).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, raw_body)` using the secret they legitimately hold for `OrgA`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `S_A`.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob` for OrgB's stack with the attacker-controlled `expected_head_sha`, despite the attacker never having authenticated as, or holding credentials for, `OrgB`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
