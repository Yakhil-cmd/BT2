### Title
Webhook signature verification keys off `repository.owner.login` while handlers resolve target repository from `repository.full_name`, allowing cross-organization stack mutation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` picks which organization's `webhook_secret` to verify the HMAC against using `repository_owner`, which reads only `params.dig('repository', 'owner', 'login')` (or `organization.login`) from the raw JSON body. `#create` then re-parses that same raw body and hands it to handlers (e.g. `PushHandler`) which resolve the actual target `Stack`/`Repository` from `repository.full_name`. Nothing in the controller enforces that `repository.owner.login` is consistent with the owner implied by `repository.full_name`, so an attacker who controls the whole JSON payload can make these two fields point at different organizations.

### Finding Description
The binding the controller implicitly relies on is:
`organization_that_signed_and_verified (params.dig('repository','owner','login'))` == `organization_that_owns_the_repository_the_handler_mutates (owner implied by params.dig('repository','full_name'))`.

Code path:
- [1](#0-0)  — `repository_owner` derives the verifying org purely from `repository.owner.login` (or `organization.login`), a field fully controlled by whoever crafts the JSON body.
- [2](#0-1)  — `verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies the HMAC using that organization's own `webhook_secret`. Since HMAC verification is org-scoped and self-consistent, an attacker who owns/controls org `attacker-org` can always produce a payload that passes this check using `attacker-org`'s own secret — no knowledge of any other org's secret is required.
- [3](#0-2)  — `create` re-parses `request.raw_post` (the very same bytes just verified) and dispatches it to handlers.
- [4](#0-3)  — `PushHandler#process` resolves `stacks` and filters by `branch` derived from `params.ref`; the underlying `stacks`/repository resolution in the shared `Handler` base class keys off `repository.full_name`, not `repository.owner.login`.

Because `repository.owner.login` and `repository.full_name` are two independent strings in a single attacker-supplied JSON document, the controller never checks that they agree. An attacker who controls `attacker-org` (and thus its `webhook_secret`) can:
1. Set `repository.owner.login = "attacker-org"` so `verify_signature` selects `Shipit.github(organization: "attacker-org")` and the HMAC — signed with the attacker's own known secret — verifies successfully.
2. Set `repository.full_name = "acme/repo"` (a real victim stack) in the same payload.
3. `create` re-parses the identical payload and hands it to `Shipit::Webhooks.for_event('push')`, whose `PushHandler` resolves the target repository/stack from `full_name`, landing on the victim's real `acme/repo` stack, and invokes `stack.sync_github(expected_head_sha: params.after)` — or, for other handler types (pull_request labeled/closed/opened/etc.), state-changing logic driven entirely by attacker-supplied JSON fields (labels, merged flags, head sha, etc.) that are not independently re-fetched from GitHub before being applied to the victim's stack.

The scenario in the question (where owner.login and full_name's owner coincide) is safe by construction, but the controller does not enforce that they must coincide — it only checks that *some* configured organization's secret matches the bytes, then trusts unrelated fields of the same attacker-controlled bytes for repository targeting.

### Impact Explanation
An attacker who registers or controls any organization present in `Shipit.github_domains` (which only requires being onboarded as a legitimate Shipit-connected org — not a privileged role, and per the threat model an unprivileged actor who can "emit webhooks from a repository they own") can forge webhook events targeting **any other repository/stack** configured in the same Shipit instance, because the signing key and the mutation target are decoupled fields of the same payload. This matches "a payload for one repository mutating another's stack, commit, task or team" — Critical. The blast radius spans all stacks across all tenants sharing one Shipit instance, and is repeatable per request with no rate limiting concerns needed for the exploit itself.

### Likelihood Explanation
Requires: (a) attacker controls at least one organization already registered in `Shipit.github_domains` with its own `webhook_secret` (a normal onboarding precondition, not a privileged Shipit role), and (b) a target stack exists for another organization's repository. Both are stated preconditions in the question. Computing the HMAC costs nothing beyond knowing one's own secret. The request is a single unauthenticated POST to `/webhooks` — fully repeatable.

### Recommendation
In `verify_signature`, after resolving `repository_owner` and verifying the signature, additionally assert that the owner implied by `params.dig('repository', 'full_name')` (i.e., `full_name.split('/').first`) equals `repository_owner`; reject (422) on mismatch before dispatching to `create`/handlers. Alternatively, derive `repository_owner` solely from `full_name` so a single, consistent field determines both which secret verifies the request and which repository the handlers act upon.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "push webhook signed by one org cannot mutate another org's stack via mismatched full_name" do
  acme_stack = shipit_stacks(:shipit) # existing stack for e.g. "acme/repo"
  attacker_secret = 'attacker-secret'
  Shipit.github_domains['github.com'].organizations['attacker-org'] = { webhook_secret: attacker_secret }

  payload = {
    ref: 'refs/heads/master',
    after: 'deadbeef',
    repository: {
      owner: { login: 'attacker-org' },       # used for signature org lookup
      full_name: acme_stack.repository.full_name, # used by PushHandler to pick the target stack
    },
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_secret, payload)

  assert_no_difference -> { acme_stack.reload.updated_at } do
    # Expect this to be rejected once fixed; currently it succeeds and triggers sync_github on acme_stack
    post shipit.github_webhooks_path, params: payload,
      headers: { 'X-Github-Event' => 'push', 'X-Hub-Signature' => signature, 'CONTENT_TYPE' => 'application/json' }
    assert_response :unprocessable_entity # after fix
  end
end
```
This asserts that `repository_owner` (verifying org, "attacker-org") and the owner implied by `repository.full_name` (real stack's org) must match, and that a divergence is rejected rather than silently mutating the victim's stack.
