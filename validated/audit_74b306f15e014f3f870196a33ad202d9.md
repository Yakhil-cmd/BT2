### Title
AA balances denominated in `cosigned_by_definer` assets can be permanently frozen because AAs can never satisfy the cosign requirement - ([File: validation.js])

### Summary
Obyte assets can be defined with `cosigned_by_definer=true`, which forces every payment message of that asset to include the asset's `definer_address` among the unit's authors, exactly like Linea's centralized sequencer being a mandatory, un-bypassable gatekeeper for every L2 transaction. Autonomous Agents (AAs) execute deterministically and sign their own response units alone; they have no mechanism to obtain a cosignature from an external human/definer address. If a user (or another AA) sends such an asset to an AA as part of a trigger payment, the AA's balance in that asset increases, but the AA can never construct a valid outgoing payment message for it, because `validatePayment` unconditionally rejects any payment lacking the definer as an author. There is no "L1-style" escape hatch in ocore to move these funds without the definer's continuous cooperation, so the funds become permanently stuck in the AA if the definer is unavailable, uncooperative, or malicious - the same failure mode described in the Linea report (single centralized party can indefinitely block a lower-privileged party's ability to move already-owned funds).

### Finding Description
When an asset is defined, `cosigned_by_definer` is a validated boolean/formula field of the asset payload [1](#0-0) . For AA-defined assets, the validator explicitly forbids `cosigned_by_definer` from being anything other than `false`, "because AA can't cosign" [2](#0-1) , proving that the codebase itself recognizes an AA cannot supply the definer's cosignature.

However, this restriction only prevents an AA from *issuing* a `cosigned_by_definer` asset itself. It does nothing to stop a third-party-defined `cosigned_by_definer` asset from being paid *into* an AA as part of a trigger unit. `validatePayment` enforces the cosign rule generically for every payment message, independent of whether the payer or (implicitly) the future payer is an AA:

```
if (objAsset.cosigned_by_definer && arrAuthorAddresses.indexOf(objAsset.definer_address) === -1)
    return callback("must be cosigned by definer");
``` [3](#0-2) 

The same check is duplicated in the composer path used when building payment joints outside of AA response composition [4](#0-3) [5](#0-4) .

An AA response unit is single-authored by the AA's own address (deterministically derived from its own definition); it has no way to add the definer as a co-author/co-signer during automatic execution, since AA execution is fully automatic and cannot pause to request an external signature. Consequently, once such an asset lands on an AA's balance (e.g., a user pays it in as part of a trigger, or another AA forwards it), the AA can never again produce a payment message moving that balance out — every attempt fails the `must be cosigned by definer` check in `validatePayment`, and the response is bounced. There is no protocol-level mechanism (analogous to an L1 escape-hatch withdrawal) allowing the AA (or, transitively, the depositing user who expects the AA to forward/return the funds per its business logic) to retrieve the funds without the definer's willing, repeated cooperation for every single transfer.

This mirrors the Linea report's bug class precisely: a single centralized party (there, the sequencer; here, the asset `definer_address`) holds unilateral, non-bypassable gatekeeper power over whether a lower-privileged party (there, an L2 user; here, an AA and its users) can ever move funds they already legitimately hold, and no fallback path exists to bypass that gatekeeper.

### Impact Explanation
Any AA that accepts payments in third-party-issued `cosigned_by_definer` assets (a legitimate and discoverable asset flag any issuer can set) is exposed to permanent freezing of that asset balance. If the definer refuses, disappears, or is compromised/coerced, all AA-held funds in that asset become unspendable forever, regardless of what the AA's own oscript logic says it should do with them (forward, refund, distribute, etc.). Because AAs commonly implement automated exchanges, DEXes, or custody-like logic that could accept arbitrary asset deposits from users, this can result in AA fund freezing at potentially unbounded scale, with no recovery path — the exact "AA fund loss or freezing" impact category called out as an acceptable finding.

### Likelihood Explanation
This does not require any malicious node, network censorship, or multi-party collusion — a single unprivileged user can trigger it by simply sending a `cosigned_by_definer` asset payment to any AA whose logic accepts arbitrary-asset deposits (many AA templates iterate over `trigger.output[[asset!=base]]` without asset-flag filtering). The asset issuer only needs to set one boolean flag when defining the asset (a normal, permitted asset feature) — no unusual on-chain state or race condition is needed. The AA developer would need to be aware of and specifically defend against this narrow asset flag to avoid it, which is unlikely to be common practice.

### Recommendation
- Have AAs explicitly reject or bounce trigger payments in assets whose `cosigned_by_definer` flag is `true` before crediting the AA's balance for that asset (validated via `storage.loadAssetWithListOfAttestedAuthors`/`objAsset.cosigned_by_definer`).
- Alternatively, extend AA validation/execution semantics so that AAs can never receive spendable balances in assets that require third-party cosigning, effectively firewalling such assets from ever reaching AA addresses at the protocol level (similar to how `issued_by_definer_only` is disallowed for AA-issued private assets).
- Document this asset flag's interaction risk prominently for AA developers so oscript templates can defensively filter deposits by asset properties.

### Proof of Concept
1. Address `D` defines an asset `A` with `cosigned_by_definer: true` (a normal, permitted configuration) [6](#0-5) .
2. User `U` triggers AA `X` (e.g. a generic asset-accepting AA/exchange contract) with a payment message carrying asset `A`. The trigger unit is authored by `U` only, but since `U` is not the recipient/definer-authoring party for the *incoming* payment's cosign check, and this is the initial transfer from `U`'s own previously-acquired coin of asset `A` (which itself required `D`'s cosignature to reach `U`), assume `U` already legitimately holds spendable `A` and sends it to `X`. AA `X`'s balance in asset `A` increases by the trigger amount.
3. AA `X`'s oscript logic later attempts to pay asset `A` out (e.g., to fulfill an exchange, refund, or withdrawal) by emitting a `payment` message for asset `A`. The AA response unit is authored solely by `X`.
4. `validatePayment` checks `objAsset.cosigned_by_definer && arrAuthorAddresses.indexOf(objAsset.definer_address) === -1` — since `arrAuthorAddresses` is `[X]` and does not include `D`, the check fails with `"must be cosigned by definer"` [3](#0-2) , causing the AA response for that message to bounce.
5. No matter how many times AA `X` retries, it can never author a valid outgoing payment for asset `A` without `D`'s cooperation, which AA `X` structurally cannot obtain (it has no signing/negotiation capability with external addresses during automated execution). The AA's balance of asset `A` is permanently frozen, matching the reported bug class of centralized, unilateral, non-bypassable control over fund movement.
