## Analog Found: `status` webhook handler writes to arbitrary commits without validating repository ownership [1](#0-0) [2](#0-1) 

### Title
Webhook signature verification is scoped per-organization, but the `status` handler writes commit statuses without validating that the commit belongs to that organization's repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret is used to authenticate an inbound webhook based on an attacker-controlled field of the payload (`repository.owner.login`, falling back to `organization.login`), then verifies the *whole request body* against that organization's `webhook_secret`. However, once verification passes, `Shipit::Webhooks::Handlers::StatusHandler#process` looks up the row(s) to mutate purely `Commit.where(sha: params.sha)` — with no re-check that the target `Commit`/`Stack`/`Repository` actually belongs to the organization that was used to authenticate the request. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` derives the org used to pick a `webhook_secret` from the payload itself: [3](#0-2) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This only proves "the sender knows the secret configured for organization X" - a Shipit instance that hosts more than one organization (as documented and exercised in `test/dummy/config/secrets_double_github_app.yml`) trusts each organization only for its own secret. The `create` action then dispatches the whole, already-parsed `params` blob to the registered handler for the event type, with no further scoping to organization X: [4](#0-3) 

For the `status` event, `StatusHandler#process` resolves the target purely by SHA, globally, with zero repository/organization scoping: [2](#0-1) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Contrast this with every other handler in the same module (`PushHandler`, `PullRequest::*Handler`, `Handler#stacks`), which all resolve their target strictly through `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`: [5](#0-4) 

`StatusHandler` is the outlier: it never consults `repository`/`full_name` at all, so the field that was actually covered by verification (the whole signed payload, tied to organization X's secret) has no relationship to the field the write logic keys off (`sha`, matched across every `Commit` row in the entire multi-tenant Shipit database, i.e. across every organization/stack). Since git commit SHAs are content-addressed and identical between forks/mirrors that share history, an organization that legitimately controls its own webhook secret can forge a `status` event naming a SHA that is shared with, or copied from, another organization's tracked repository, and flip that other repository's `Commit#state` (used to gate `deployable?`) to `success`.

### Impact Explanation
`Commit` status rows produced here feed directly into deploy-eligibility checks (`deployable?`/CI gating) used before Shipit will let a commit be deployed. An attacker who only possesses a webhook secret for their own, unrelated organization/repository registered on the same multi-tenant Shipit instance can forge a signed `status` webhook that marks a commit belonging to a *different* organization's protected repository as passing CI ("success"), bypassing required-status-check gating for that other stack. This can enable an unauthorized deploy of a commit that never actually passed CI, meeting the "unauthorized deploy" Critical-impact bar defined for this engine.

### Likelihood Explanation
Exploitability depends on the target Shipit instance tracking more than one organization/repository (a documented, supported configuration - see `test/dummy/config/secrets_double_github_app.yml`) and on the attacker being able to name a SHA that also exists as a `Commit` row belonging to the victim stack (trivially true for forks/mirrors that share git history, or any commit imported into more than one tracked `Stack`). No `Shipit` session, API token, or victim's webhook secret is required - only the attacker's own, legitimately-issued webhook secret for their own registered repository.

### Recommendation
- Scope `StatusHandler#process` (and any other handler) to the `Repository`/organization implied by `repository_owner`, mirroring the pattern already used in `Handler#stacks`/`Handler#repository_name`, instead of matching `Commit` globally by `sha`.
- After `verify_signature` selects an organization, propagate and enforce that identity through to every handler so the payload's `repository.full_name` (and any DB row it resolves to) is checked to actually belong to the authenticated organization, per Rails Guides best practice: fail closed with an explicit error/`return` if the identities diverge, rather than silently trusting fields the signature doesn't semantically constrain.

### Proof of Concept
1. Register two organizations on a single Shipit instance: `OrgA/repoA` (attacker-controlled, attacker knows `webhook_secret_A`) and `OrgB/repoB` (victim, tracked as a `Stack` with `continuous_deployment` or manual deploy gated on commit status).
2. Identify a commit SHA that exists in `OrgB/repoB`'s tracked history and is also reachable/known to the attacker (e.g., `repoA` is a fork of `repoB`, or the attacker previously had read access and recorded a SHA).
3. Attacker crafts a GitHub `status` webhook payload:
   ```json
   { "sha": "<victim commit sha>", "state": "success", "context": "ci/attacker", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/repoA"} }
   ```
4. Attacker signs the raw body with `webhook_secret_A` (`sha1=HMAC(...)`) and POSTs it to `/github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` → `"OrgA"`, verifies successfully against `webhook_secret_A`.
6. `StatusHandler#process` executes `Commit.where(sha: "<victim commit sha>")`, finds the `Commit` row under `OrgB`'s stack, and calls `create_status_from_github!`, marking it `success` — even though the request was never authenticated for `OrgB`.
