### Title
Cross-tenant status write via unscoped `Commit.where(sha:)` in StatusHandler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a `status` webhook only against the GitHub organization derived from the payload's `repository.owner.login`/`organization.login`, using that org's `webhook_secret`. `StatusHandler#process` then looks up commits solely by `sha` with `Commit.where(sha: params.sha)`, with no check that the matched `Commit`'s stack/repository belongs to the authenticated organization, letting an attacker who controls a repo/webhook in org A write a bogus status onto any commit sharing that SHA in org B's stack.

### Finding Description
The binding the endpoint should enforce is: `repository_owner (authenticated via github_app.verify_webhook_signature using Shipit.github(organization: repository_owner)) == commit.stack.repository.owner`, i.e., the org whose secret signed the payload must equal the org owning the `Commit` row being mutated.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and verifies the HMAC signature against that org's app/secret [1](#0-0) , [2](#0-1) . This only proves "the sender controls org A's webhook secret" — it says nothing about which commit/stack the event's `sha` should touch.
- `Handler#process` dispatch is generic; the base `Handler` class does expose a `stacks` helper scoped by `repository_name` from the payload [3](#0-2) , but `StatusHandler` never uses it.
- `StatusHandler#process` instead does a global, unscoped lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . `Commit` belongs to `stack` (and thus indirectly to a repository/org) [5](#0-4) , but this ownership is never checked against `repository_owner`/`organization.login` from the authenticated payload.

Exploit: an attacker owns/controls a GitHub repo under org A and configures a Shipit webhook there with A's legitimate `webhook_secret` (this is a normal, unprivileged setup step — owning any org/repo with Shipit's webhook installed is not a privileged Shipit role). The attacker crafts a `status` event body with `repository.owner.login` = A (so the signature check passes using A's real secret) but `sha` equal to a commit SHA that exists in victim org B's stack (SHAs are 40-hex values and can be learned from B's public repo history, PRs, or Shipit's public commit list UI). Because `StatusHandler` does not scope by repository, `Commit.where(sha: ...)` matches B's commit row directly, and `commit.create_status_from_github!(params)` writes an attacker-controlled `state`/`description`/`target_url`/`context` onto it.

Existing guards do not stop this: `verify_signature` authenticates the sender as "org A", not as "owner of the target commit"; `drop_unhandled_event` only checks event type; the `ExplicitParameters` schema in `StatusHandler.params` validates types (`sha`, `state`, etc.) but not ownership; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` involved at all since this is an unauthenticated webhook endpoint gated purely by HMAC signature — and the HMAC signature is scoped to the wrong entity (org, not commit/stack).

### Impact Explanation
An attacker can write an arbitrary CI status (e.g., `state: 'success'`) onto a specific commit belonging to a completely unrelated victim stack/org, without ever authenticating against or being a member of that victim org. If the victim's merge/deploy pipeline gates on `Status::Group`/required statuses reaching `success`, this can unblock a merge or deploy that should have been blocked — matching "a payload for one repository mutating another's stack/commit" and "an unauthorized deploy" impact categories (Critical). The attack is repeatable against any commit SHA the attacker can learn, across any number of victim stacks, as long as the attacker controls one org with a valid webhook secret (attacker's own repo).

### Likelihood Explanation
Preconditions: the attacker needs Shipit configured with a webhook for at least one GitHub org/repo they control (a normal, unprivileged setup available to anyone who can install a Shipit-connected app on their own repo), and knowledge of a target commit SHA in the victim's stack (trivially obtainable from public GitHub history or Shipit's own commit/stack UI). No Shipit session, API token, or victim-org secret is required. Cost is a single signed HTTP POST to `/webhooks`; the exploit is fully repeatable and scriptable.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the authenticated repository/stack, e.g. use the `stacks` helper already provided by `Handler` (`stacks.commits.where(sha: params.sha)` or equivalent joining through `Stack -> Repository` and comparing to `repository_name`/`repository_owner`) instead of a global `Commit.where(sha:)`. Apply the same repository-scoping check pattern to any other handler that resolves records by content-derived fields (SHA, branch name) without joining through the authenticated repository.

### Proof of Concept
Minitest plan (no live GitHub calls; signature verification can be satisfied since the attacker's own org's real secret is used, or stubbed via `Shipit.github` fixture, per the existing `webhooks_controller_test.rb` patterns):

```ruby
test "status webhook for org A cannot write a status onto a commit belonging to org B's stack with the same sha" do
  org_a_stack = shipit_stacks(:shipit) # repository owned by "org-a"
  org_b_stack = shipit_stacks(:cyclimse) # repository owned by "org-b", different owner
  victim_commit = org_b_stack.commits.create!(sha: "a" * 40)

  payload = {
    'repository' => { 'full_name' => org_a_stack.repository.full_name, 'owner' => { 'login' => org_a_stack.repository.owner } },
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'attacker-forged',
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body: payload.to_json, headers: signed_headers_for(org_a_stack.repository.owner, payload, event: 'status')
  end
end
```

Assertions on both sides of the binding:
- Before: `repository_owner` derived and authenticated == `org_a_stack.repository.owner` (org A).
- `victim_commit.stack.repository.owner` == `org_b_stack.repository.owner` (org B), i.e., `org_a_stack.repository.owner != org_b_stack.repository.owner`.
- After calling the handler with the current unscoped implementation, `victim_commit.statuses.count` increases (demonstrating the write across the mismatched binding) — the test should assert this does NOT happen once the fix scopes the lookup through `stacks`/repository ownership.
