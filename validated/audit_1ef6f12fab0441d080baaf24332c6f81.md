### Title
No vulnerability - unbounded encode() side is not attacker-reachable because ChunkStateWitness inputs are already capped upstream

### Summary
`CompressedData::encode` in `core/primitives/src/utils/compression.rs` indeed performs `borsh::to_writer` with an uncounted/uncapped write side, but the `ChunkStateWitness` passed to it is constructed by the chunk producer only after enforcing a documented set of hard/soft size limits (transaction size, receipt size, combined transaction size, storage proof size, outgoing receipt size), keeping the total witness size to roughly 17 MiB regardless of attacker behavior. An unprivileged attacker cannot inflate the pre-`encode()` witness beyond these caps through transactions/receipts alone.

### Finding Description
`CompressedData::encode` does not itself cap the amount of data written before compression [1](#0-0) , unlike `decode`, which explicitly limits decompressed size via `CountingRead::new_with_limit` to guard against zip-bomb style attacks [2](#0-1) . However, the object being encoded, `ChunkStateWitness`, is not attacker-controlled in an unbounded way: it is built by the chunk producer during chunk production, and its size is governed by a well-documented set of protocol-level limits — `max_transaction_size` (1.5 MiB), `max_receipt_size` (4 MiB), `combined_transactions_size_limit` (4 MiB hard limit), `new_transactions_validation_state_size_soft_limit` (500 KiB), `main_storage_proof_size_soft_limit` (4 MB soft limit, ~8 MB worst case), and outgoing receipt size limits (100 KiB usual / 4.5 MiB big), together bounding the total witness to ~17 MiB [3](#0-2) . These limits are enforced via `WitnessConfig` fields such as `main_storage_proof_size_soft_limit` and `combined_transactions_size_limit` [4](#0-3) , and additionally there is a hard cap `MAX_UNCOMPRESSED_STATE_WITNESS_SIZE` (64 MiB, or 512 MiB under `test_features`) associated with `EncodedChunkStateWitness` used both for decode limiting and documented as the expected upper bound for the encoded structure [5](#0-4) . Since these limits are enforced during chunk/witness construction (before `encode()` is ever called), an attacker submitting many large `FunctionCallAction` args or `DeployContractAction` payloads cannot cause the pre-`encode()` borsh-serialized data to grow unbounded — the chunk producer stops adding transactions/receipts once soft/hard limits are hit, deferring the rest to later chunks or the delayed queue.

### Impact Explanation
No exploitable impact: the amount of data reaching `encode()` is already bounded to roughly 17 MiB by pre-existing protocol-level witness size limits, so the missing cap on the write-side of `encode()` does not translate into unbounded memory or CPU usage reachable by an ordinary transaction-submitting attacker.

### Likelihood Explanation
Not exploitable by an unprivileged attacker: reaching a genuinely unbounded witness size would require bypassing the transaction/receipt/storage-proof size limits enforced during chunk production, which are separate, already-audited invariants, not something addressable purely through crafting large `FunctionCallAction`/`DeployContractAction` payloads within existing gas limits.

### Recommendation
No fix required for this specific concern; the current design relies on upstream size-limit enforcement (documented in `docs/misc/state_witness_size_limits.md`) rather than in `encode()` itself. If defense-in-depth is desired, `encode()` could be enhanced to cap the write side using `CountingWrite` with a hard limit similar to `decode_with_limit`, but this is a hardening measure, not a fix for an exploitable bug.

### Proof of Concept
N/A — no valid vulnerability chain from unprivileged attacker input to unbounded `encode()` resource usage.

```rust
    fn encode(uncompressed: &T) -> std::io::Result<(Self, usize)> {
        // Flow of data: Original --> Borsh serialization --> Counting write --> zstd compression --> Bytes.
        // CountingWrite will count the number of bytes for the Borsh-serialized data, before compression.
        let mut encoder = zstd::stream::Encoder::new(Vec::new().writer(), COMPRESSION_LEVEL)?;

        encoder.multithread(N_WORKERS)?;

        let mut counting_write = CountingWrite::new(encoder);
        borsh::to_writer(&mut counting_write, uncompressed)?;

        let borsh_bytes_len = counting_write.bytes_written();
        let encoded_bytes = counting_write.into_inner().finish()?.into_inner();

        Ok((Self::from(encoded_bytes.into()), borsh_bytes_len.as_u64() as usize))
```

```markdown
The limits are:

* `max_transaction_size = 1.5 MiB`
  * All transactions must be below 1.5 MiB, otherwise they'll be considered invalid and rejected.
  * Previously was 4MiB, now reduced to 1.5MiB
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
* `combined_transactions_size_limit - 4 MiB`
  * Hard limit on total size of transactions from this and previous chunk. `ChunkStateWitness` contains transactions from two chunks, this limit applies to the sum of their sizes.
* `new_transactions_validation_state_size_soft_limit - 500 KiB`
  * Validating new transactions generates storage proof (recorded trie nodes), which has to be limited. Once transaction validation generates more storage proof than this limit, the chunk producer stops adding new transactions to the chunk.
* `per_receipt_storage_proof_size_limit - 4 MB`
  * Executing a receipt generates storage proof. A single receipt is allowed to generate at most 4MB of storage proof. This is a hard limit, receipts which generate more than that will fail.
* `main_storage_proof_size_soft_limit - 4 MB`
  * This is a limit on the total size of storage proof generated by receipts in one chunk. Once receipts generate more storage proof than this limit, the chunk producer stops processing receipts and moves the rest to the delayed queue.
  * It's a soft limit, which means that the total size of storage proof could reach 8 MB (3.99MB + one receipt which generates 4MB of storage proof)
  * Due to implementation details it's hard to find the exact amount of storage proof generated by a receipt, so an upper bound estimation is used instead. This upper bound assumes that every removal generates additional 2000 bytes of storage proof, so receipts which perform a lot of trie removals might be limited more than theoretically applicable.
* `outgoing_receipts_usual_size_limit - 100 KiB`
  * Limit on the size of outgoing receipts to another shard. Needed to keep the size of `source_receipt_proofs` small.
  * On most block heights a shard isn't allowed to send receipts larger than 100 KiB to another shard.
* `outgoing_receipts_big_size_limit - 4.5 MiB`
  * On every block height there's one special "allowed shard" which is allowed to send larger receipts, up to 4.5 MiB in total.
  * A receiving shard will receive receipts from `num_shards - 1` shards using the usual limit and one shard using the big limit.

In total that gives 4 MiB + 500 KiB + 8MB + 5*100 KiB + 4.5 MiB ~= 17 MiB of maximum witness size. Possibly a little more on missing chunks.
```
