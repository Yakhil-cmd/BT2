### Title
Unauthenticated PR label injects arbitrary environment variables (e.g. `GIT_SSH_COMMAND`) into deploy commands - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` blindly maps every pull-request label name to an uppercase environment variable set to `"true"`, and `TaskCommands#env` merges this stack env ahead of the deploy-spec/task env without any allow-list. Any GitHub user who can label a PR on a repository with review stacks enabled can therefore inject env vars like `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, etc. into the `git`/build commands run on the Shipit host for that PR's review-stack task.

### Finding Description
The claimed broken binding — "every key in `Command#unbundled_env` == a key present in `Shipit.env` or `deploy_spec.machine_env` approved by an operator" — is indeed broken. `pull_request.labels` (attacker-supplied names from the `labeled`/`unlabeled`/`opened`/`reopened` webhook events, captured verbatim by `LabelCapturingHandler#capture_labels`) [6](#0-5)  flow directly into `ReviewStack#env`, which does `labels[label_name.upcase] = "true"` for every label with no filtering of key names. [1](#0-0)  `TaskCommands#env` calls `super.merge(@stack.env)` before merging its own static keys (`SHIPIT_USER`, `EMAIL`, etc.), `deploy_spec.machine_env`, and `@task.env` [2](#0-1) ; none of those later merges happen to redefine `GIT_SSH_COMMAND` unless an operator explicitly configured it. `TaskCommands#clone`/`#checkout` invoke `git(...)` which builds a `Command` using this merged `env` [3](#0-2) , and `Commands#git` passes that env straight through to `Command.new`. [4](#0-3)  The `LabelCapturingHandler` params schema only validates that `name` is a `String` [7](#0-6)  — no character/name restriction exists anywhere in this path, so an attacker who can label their own PR (`opened`, `labeled`, `unlabeled`, `reopened` all trigger `capture_labels`) fully controls the resulting env var name. The Rules note that `EnvironmentVariables#permit` is one of the guards to check for this class of bug; that mechanism guards `Stack#environment_variables`/user-provided env, not `ReviewStack#env`'s label-derived hash, so it does not apply here and provides no protection.

Attack: attacker opens a PR against a repo with review stacks configured, adds a label named `git_ssh_command` (or `git_askpass`, `bundle_gemfile`, `ld_preload`, etc.), and triggers any deploy/task on that review stack. No Shipit session, API token, or GitHub secret is required — only the ability to label a PR they control, which is an unprivileged GitHub action reachable via the standard webhook flow that this engine already accepts as a normal event.

### Impact Explanation
This lets an unauthenticated (from Shipit's perspective) PR author corrupt the environment of `git clone`/`git checkout`/build commands running on the Shipit deploy host for their review stack. Setting `GIT_SSH_COMMAND=true` neuters SSH-based git transport (causing clone/fetch to silently no-op), and other labels could set `GIT_ASKPASS`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, `PATH`, or similar dangerous variables consumed by subsequent shell/tool invocations in the deploy pipeline, depending on what the deploy spec's build steps actually read from the environment. This maps to the engine's own severity taxonomy as a form of unauthorized code/command manipulation on the deploy host, scoped to the attacker's own repository/review stack (blast radius limited to stacks the attacker controls, but fully repeatable per-label and per-PR).

### Likelihood Explanation
Preconditions are minimal: a repository must have review stacks/PR deploys enabled (a standard, common Shipit feature), and the attacker only needs to be able to label a PR they opened against that repo — no maintainer approval, no Shipit credentials, and no special repo permissions beyond what any contributor with a PR already has (labeling one's own PR is possible in many repo configurations, or via a fork+webhook replay depending on GitHub permission model). Attacker cost is a single label add and a deploy trigger; the attack is fully repeatable against any repository configured this way and against arbitrary label names, i.e., arbitrary target env var names.

### Recommendation
In `ReviewStack#env` (`app/models/shipit/review_stack.rb`), stop mapping arbitrary label names to environment variable keys. Either require an explicit allow-list/prefix convention (e.g., only labels prefixed `env:` map to variables, and even then restrict to a fixed set of safe keys), or remove this label-to-env-var feature entirely and require operators to configure needed variables via `deploy_spec.machine_env`/`Stack#environment_variables`, which are actually operator-controlled.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (or task_commands_test.rb)
test "PR label injects arbitrary env var into TaskCommands#env" do
  stack = shipit_stacks(:shipit) # a ReviewStack fixture, or build one
  pull_request = stack.pull_request || create_pull_request(stack: stack)
  pull_request.update!(labels: ['git_ssh_command'])

  task = create_task(stack: stack) # e.g. a Deploy
  env = Shipit::TaskCommands.new(task).env

  assert_equal 'true', env['GIT_SSH_COMMAND']
  # and confirm no operator-configured source set it:
  refute_includes Shipit.env.keys, 'GIT_SSH_COMMAND'
  refute_includes stack.deploy_spec.machine_env.keys, 'GIT_SSH_COMMAND'
end
```
This demonstrates the equality `TaskCommands#env['GIT_SSH_COMMAND'] == 'true'` holds solely because of the unauthenticated `pull_request.labels` value, with no operator-approved source (`Shipit.env`, `deploy_spec.machine_env`, `@task.env`) defining that key — confirming the binding is broken exactly as claimed.
