### Title
`DenyReserveTransferToRelayChain` in bridge-hub-kusama's `Barrier` is not wrapped in `DenyRecursively`, allowing nested `SetAppendix`/`ExecuteWithOrigin` programs to bypass the reserve-transfer-to-relay deny-list - ([File: system-parachains/bridge-hubs/bridge-hub-kusama/src/xcm_config.rs])

### Summary
`bridge-hub-kusama`'s `Barrier` uses a bare `DenyReserveTransferToRelayChain` filter, whereas `bridge-hub-polkadot` deliberately wraps the identical filter in `DenyRecursively<...>`. Because the bare filter only inspects the top-level instruction list of an incoming XCM program, an unprivileged signed user calling `pallet_xcm::execute` can hide a denied reserve-transfer instruction (`DepositReserveAsset`/`InitiateReserveWithdraw`/`InitiateTeleport` targeting `Parent`) inside a nested program carried by `SetAppendix` (or `ExecuteWithOrigin`), which the non-recursive deny check never inspects.

### Finding Description
The `Barrier` type for bridge-hub-kusama is: [1](#0-0) 

compared to bridge-hub-polkadot's: [2](#0-1) 

Both use the same underlying `DenyReserveTransferToRelayChain` filter from `xcm-builder`, which walks the top-level instruction sequence of the program handed to `ShouldExecute` and rejects programs whose top-level instructions include an outbound reserve-transfer/teleport aimed at the Relay Chain (`Parent`). `DenyRecursively`, used only on bridge-hub-polkadot (and bulletin-polkadot) but not on bridge-hub-kusama, generalizes any inner `ShouldExecute`/deny check by additionally descending into any nested `Xcm<Call>` program carried by instructions such as `SetAppendix`, `SetErrorHandler`, and `ExecuteWithOrigin`. Without that wrapper, a nested copy of the denied instruction placed inside `SetAppendix`'s embedded program is invisible to the deny check on bridge-hub-kusama.

An unprivileged signed account on bridge-hub-kusama can reach this path via `pallet_xcm::Pallet::execute`, which lets any signed origin submit an arbitrary XCM program to be locally executed by the chain's own `XcmExecutor` (subject to `Barrier`). A program of the shape:
- top-level: `WithdrawAsset`, `BuyExecution` (to satisfy `AllowTopLevelPaidExecutionFrom<Everything>` in the second arm of `DenyThenTry`), `SetAppendix(Xcm(vec![DepositReserveAsset { assets: All, dest: Parent, xcm: Xcm(vec![]) }]))`, `DepositAsset` (to `Here`)

passes `DenyReserveTransferToRelayChain` because the denied instruction is not at the top level — it is embedded inside the `SetAppendix` payload. The main program then executes normally and, per XCM semantics, the appendix executes afterward, running the smuggled `DepositReserveAsset` targeting the Relay Chain — exactly the operation the barrier is meant to block.

### Impact Explanation
`DenyReserveTransferToRelayChain` exists specifically because bridge-hub-kusama does not recognize the Relay Chain as a valid reserve/teleport destination for a reserve-transfer route (`type IsReserve = ()`), so allowing this instruction to execute risks assets being burned/withdrawn locally and sent via a route the Relay Chain does not correctly reconcile, i.e., an unauthorized/unaccounted asset movement toward `RootLocation` that the deny-list is designed to prevent. This directly violates the invariant that "filters/barriers must not be bypassable by normal users" and that asset movements must remain properly accounted for.

### Likelihood Explanation
The precondition is only a valid signed origin on bridge-hub-kusama and knowledge of XCM instruction composition (`SetAppendix`/`ExecuteWithOrigin` nesting) — no privileged access, proxy abuse, or bridge compromise is required. The attack is fully repeatable and deterministic given the same non-recursive filter configuration is used consistently across many of this repo's chains (asset-hub-kusama, asset-hub-polkadot, collectives-polkadot, coretime-kusama/polkadot, encointer, people-kusama/polkadot all use the bare `DenyReserveTransferToRelayChain` too), confirming this is a systemic gap rather than an isolated typo, and bridge-hub-kusama specifically lacks the `DenyRecursively` hardening that bridge-hub-polkadot already received.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` in `DenyRecursively` in bridge-hub-kusama's `Barrier` (mirroring bridge-hub-polkadot), i.e. change:
```rust
DenyThenTry<
    DenyReserveTransferToRelayChain,
    ...
>
```
to
```rust
DenyThenTry<
    DenyRecursively<DenyReserveTransferToRelayChain>,
    ...
>
```
and audit the other affected runtimes for the same fix.

### Proof of Concept
xcm-emulator integration test (bridge-hub-kusama):
1. Fund a signed test account on `BridgeHubKusama` with native balance.
2. Build XCM: `Xcm(vec![WithdrawAsset(fee.clone()), BuyExecution { fees: fee, weight_limit: Unlimited }, SetAppendix(Xcm(vec![DepositReserveAsset { assets: AllCounted(1).into(), dest: Parent.into(), xcm: Xcm(vec![]) }])), DepositAsset { assets: AllCounted(1).into(), beneficiary: Here.into() }])`.
3. Call `PolkadotXcm::execute(signed_origin, Box::new(VersionedXcm::from(xcm)), max_weight)`.
4. Assert: with the current (bare) filter, execution succeeds and the account's balance is reduced by the reserve-transferred amount plus an XCM message is queued toward the Relay Chain (`assert_ok!` on execute, and check `System::events()`/`XcmpQueue`/UMP outbound queue for a message destined to `Parent`).
5. Apply the recommended fix (`DenyRecursively<DenyReserveTransferToRelayChain>`) and re-run: assert the call now fails with `Filtered`/`Barrier` error and no outbound message to `Parent` is produced.
