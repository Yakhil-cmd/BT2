### Title
Cross-repository commit-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` writes commit CI-status data using only the `sha` field from the webhook payload, with no validation that the `sha` belongs to the repository/organization that was authenticated by `WebhooksController#verify_signature`. This breaks the binding "an organization that authenticated versus the repository that is written," analogous to the `KangarooVault` report's core flaw of acting on an unverified/unbound field.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, itself parsed directly out of the untrusted JSON body: [1](#0-0) [2](#0-1) 

Once the signature check passes for *some* organization, the raw JSON body is dispatched by event type to handlers: [3](#0-2) 

`StatusHandler`'s parameter schema only requires `sha` and `state` — it never requires or validates a `repository` field: [4](#0-3) 

Its `process` method looks up commits **globally by `sha` across the entire installation**, with no scoping to the repository/organization whose secret validated the signature: [5](#0-4) 

`create_status_from_github!` unconditionally creates a `Status` record from whatever the caller supplies: [6](#0-5) 

`Status` creation has real side effects: it enables CI on the stack and schedules continuous delivery / merge-request processing: [7](#0-6) 

This is confirmed by tests showing that a `success`/`pending` transition on a commit's status enqueues `ProcessMergeRequestsJob` and fires `deployable_status`/continuous-delivery hooks: [8](#0-7) 

**Binding broken:** the organization whose credential (`webhook_secret`) was verified ≠ the repository/stack whose commit and deploy pipeline is written to. `repository_owner` (used only for signature selection) and `params.sha` (used for the actual write) are two independently-attacker-controlled fields inside the same JSON body that are never cross-checked against each other.

### Impact Explanation
An attacker who controls (or is granted, e.g. as a legitimate but unprivileged member of) one organization/repository already wired into this Shipit instance can forge a `status` webhook whose top-level `repository.owner.login` matches their own org (satisfying signature verification with a secret they legitimately possess for their own integration) while `sha` references a commit belonging to an entirely different stack/repository. Because `StatusHandler` performs no repository/organization scoping, this forged event:
- Injects an arbitrary CI status (`success`/`failure`/`error`, arbitrary `description`/`target_url`/`context`) onto any commit anywhere in the Shipit installation.
- Can flip a blocked commit to `success`, unblocking `Stack#trigger_continuous_delivery` and triggering an **unauthorized deploy**, or enqueue `ProcessMergeRequestsJob`, causing an **unauthorized merge** of a victim's pull request — both are explicitly listed Critical impacts.

Additionally, if a target organization is configured without a `webhook_secret` (an explicitly supported, optional configuration per `Shipit::GithubApp#verify_webhook_signature`, which returns `true` unconditionally when no secret is set), any unauthenticated caller can reach this same code path with zero credentials at all: [9](#0-8) 

### Likelihood Explanation
Moderate-to-high in multi-tenant deployments: any Shipit instance servicing more than one GitHub organization (explicitly supported per the changelog "Support multiple GitHub organisations") allows one org's legitimately-configured webhook credential to be replayed against any other org's stacks, since the handler performs no cross-check between the authenticated organization and the acted-upon commit's stack/repository. No git push access, no Shipit session, and no `ApiClient` token are required — only the ability to deliver an HTTP POST with a validly-signed body for any one configured organization (or none, if that organization's secret is unset).

### Recommendation
`StatusHandler` (and any other handler that mutates records keyed only by a payload field like `sha`) must scope its query to the repository derived from the same authenticated payload path used for signature verification — e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { ... matching repository_owner/name ... })`, or better, require and validate the `repository.full_name`/`owner.login` fields against the organization that successfully verified the signature, rejecting any payload where they diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` (attacker-controlled, webhook secret known to the attacker) and `org-b` (victim, unrelated stack tracked by Shipit).
2. Attacker crafts a `status` event JSON body:
```json
{
  "repository": { "owner": { "login": "org-a" } },
  "sha": "<victim commit sha in org-b's stack>",
  "state": "success",
  "context": "ci/travis",
  "description": "forged",
  "branches": [{ "name": "master" }]
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac using org-a's known webhook_secret>` over this exact body and POSTs it to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner => "org-a"`, fetches `org-a`'s `webhook_secret`, and the signature verifies successfully.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the victim commit belonging to `org-b`'s stack, and calls `create_status_from_github!`, creating a forged `success` status.
6. This triggers `schedule_continuous_delivery`/`ProcessMergeRequestsJob` side effects on `org-b`'s stack, potentially causing an unauthorized deploy or PR merge, despite the attacker having no relationship to `org-b`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
