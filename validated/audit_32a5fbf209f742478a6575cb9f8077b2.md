### Title
Unbounded route venues let a crafted `swap` payload execute arbitrary third-party contracts under the caller's authorization tree and drain the caller's wallet - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The axios supply-chain incident's bug class is "malicious code smuggled into a trusted execution path via a dependency the user did not audit". XOXNO Lending's analog: `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept opaque `swap: Bytes` from the caller and forward them to the router, which invokes whatever pool/venue contracts the payload names. Neither the controller nor the router keeps an allowlist of hop venues, so a route can place attacker-deployed code on the call stack underneath the caller's `require_auth`. That code can issue `token.transfer(victim, attacker, amount)` calls, which Soroban records as child invocations of the caller's own authorization entry — a signature the victim produces when signing what looks like a routine collateral swap. The result mirrors the advisory: code the user never audited executes with the user's own authority.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` authorizes exactly one input transfer to the configured router and then invokes `router.execute_strategy(&controller, &amount_in, swap)`, where `swap` is the raw caller-supplied `StrategySwap`/`Bytes` from `swap_collateral`/`swap_debt`. The controller treats the payload as opaque; all of its own guards (`RouterOverspend`, `NoSwapOutput`, `with_flash_guard`, final risk checks in `strategy_finalize`) only bound the routed funds, not what the route's named contracts do while on the stack.

The router's documented behavior calls the pool and token addresses the payload names with no allowlist (`docs/explanation/threat-model.md`, "Routes, callbacks, and external integrations"). A token transfer performed by such a contract `from` the caller executes if the caller's signed auth tree contains it, and Soroban simulation records it as a sub-invocation under the caller's `swap_collateral` entry — indistinguishable in structure from the one legitimate child transfer an honest route produces, unless the client decodes every child.

This is proven by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `RogueHopPool.swap()` performs `token::Client::transfer(&victim, &attacker, &amount)` during the swap, and the test asserts the recorded auth tree contains the stolen transfer as a child of Alice's `swap_collateral` authorization, Alice's unrelated wallet token balance goes to 0, and the attacker receives `WALLET_BALANCE` — while the swap itself still pays out fairly and the account ends healthy.

### Impact Explanation
Theft of user funds: an arbitrary amount of an arbitrary token in the victim's wallet (not just the routed input) is transferred to the attacker, nested inside a transaction whose protocol-visible behavior — a fair-priced collateral swap — is completely benign. The controller's measured-output check, `RouterOverspend`, `NoSwapOutput`, and the post-swap health-factor gate all pass; none of them bound the caller's wallet, only the routed amount.

### Likelihood Explanation
Route bytes are produced by the off-chain quote service and are explicitly not to be constructed on-chain ("Route bytes come from the quote service; do not construct `StrategyPayload` on-chain"), so users sign opaque XDR — the same trust relationship as `npm install` on a compromised package. Any unprivileged party that can get a victim to sign a crafted route (malicious quote response, phishing frontend, compromised SDK) achieves the drain. The threat model itself acknowledges that only client-side auth-tree inspection prevents it, and the standard builders pass `routeXdr` through without decoding it.

### Recommendation
Enforce a venue allowlist on-chain: the router (or the controller before forwarding) should validate every pool/venue address decoded from `StrategyPayload` against a governance-administered registry, so payload-named contracts cannot introduce foreign code into the caller's auth tree. Until then, SDK/client builders must decode the signed authorization tree and reject any child invocation other than the single expected input transfer — and this check should be enforced inside `execute_strategy`/`swap_tokens` consumers rather than left to wallet hygiene.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `UnlistedPoolRouter.execute_strategy` pulls `total_in`, invokes `route.hop_pool.swap` (the attacker-registered `RogueHopPool`), and pays a fair `min_out`. `RogueHopPool.swap` calls `token.transfer(alice → attacker, WALLET_BALANCE)` on an unrelated wallet token. The test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` asserts the theft transfer is recorded as a sub-invocation of Alice's `swap_collateral` auth, `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, and the swap still credits `FAIR_OUT_ETH`. Signing that recorded tree executes the drain on mainnet.
