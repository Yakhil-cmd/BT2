### Title
Unsynchronized dry-run AA-trigger execution mutates shared unit caches without the write mutex, causing stale/dangling cache references (analog of CVE-2022-1485 use-after-free) - (File: aa_composer.js)

### Summary
`aa_composer.dryRunPrimaryAATrigger()` is invoked by `network.js` for every unit posted to the node (when `conf.bDryRunNewTriggers` is set) to "pre-execute" AA triggers addressed to the unit's outputs, before the unit is actually validated/saved. Unlike the real write path, this function does **not** acquire the global `"write"` mutex, yet it calls into `handleTrigger()` → `validateAndSaveUnit()` → `writer.saveJoint()`, which populates the same process-global, shared caches (`storage.assocUnstableUnits`, `assocBestChildren`, `assocKnownUnits`, `assocUnstableMessages`, etc.) that every other unit-validation/stabilization path reads and writes under the `"write"` mutex. After the dry run, `revertResponsesInCaches()` deletes the fake response units from these caches via `storage.forgetUnit()`, but any other concurrent consumer of the same caches (real AA-trigger execution, main-chain stabilization, another posted-unit validation) can observe, reference, or link to the temporary objects while they still exist, and then have those references become dangling the instant `forgetUnit()`/`fixIsFreeAfterForgettingUnit()` deletes them — the JS analog of a "use after free": a live pointer/reference into a cache entry that is asynchronously freed out from under it.

### Finding Description
`dryRunPrimaryAATrigger` in [1](#0-0)  takes its own DB connection, begins its own local transaction, and runs `handleTrigger()` directly — with no call to `mutex.lock(["write"], …)` anywhere in the call chain from `network.js`'s invocation site.

The trigger it executes flows into the ordinary unit-saving code path, `validateAndSaveUnit`, which calls `writer.saveJoint()`: [2](#0-1) 

`writer.saveJoint()` itself only skips acquiring the write mutex when the caller explicitly marks `objValidationState.bUnderWriteLock = true` (which the *real* AA-trigger handler in `handlePrimaryAATrigger`, running under `mutex.lock(['aa_triggers'])`, sets, but which is a different lock — not `"write"`): [3](#0-2)  and [4](#0-3) 

During its execution, `saveJoint` mutates the same global, unlocked-during-dry-run caches: `assocUnstableUnits`, `assocBestChildren`, `assocKnownUnits`, `assocUnstableMessages` (see for example the general shape of these caches and how `forgetUnit` tears them down): [5](#0-4) 

Once the dry run's `onDone` fires, `revertResponsesInCaches()` deletes the fabricated response units from cache and mutates the *parent* units' `is_free`/best-children state: [6](#0-5)  using `storage.forgetUnit` and `storage.fixIsFreeAfterForgettingUnit`: [7](#0-6) 

Because none of this — from cache population to cache teardown — is protected by the `"write"` mutex that every other concurrent writer (`writer.saveJoint` for real units, `main_chain.markMcIndexStable`, `handlePrimaryAATrigger`) is required to hold, a second concurrent unit-processing pipeline can, in the same tick window:
- read `storage.assocUnstableUnits`/`assocBestChildren` and pick up the dry run's ephemeral unit object as a `best_parent_unit`, parent reference, or "best child" entry (arrays of *object references*, not copies — see `_.pull(assocBestChildren[parent_unit], assocUnstableUnits[unit])` in `forgetUnit`), and
- then have that referenced object deleted from the canonical map by `revertResponsesInCaches`/`forgetUnit`, leaving the referencing structure holding a stale/dangling object that is no longer present in `assocUnstableUnits`/`assocStableUnits`.

Subsequent code that indexes back into these maps by unit id (e.g. `storage.assocStableUnits[objMcUnitProps.last_ball_unit]`, or `getFinalTps`'s traversal in [8](#0-7) ) will then throw ("no last ball ... found in cache") or silently diverge in main-chain/TPS-fee/stability bookkeeping, because the object graph and the canonical caches have gone out of sync — the direct analog of the browser's File System API UAF: a heap object (cache entry) is freed while a live reference to it is retained and later dereferenced.

### Impact Explanation
This can cause node-level state corruption of the in-memory unit graph (`assocUnstableUnits`/`assocBestChildren`/`assocKnownUnits`) that drives stability determination, best-parent selection, and TPS-fee/main-chain bookkeeping. Depending on timing, this manifests as: unhandled exceptions crashing the write pipeline (denial of service — inability to confirm/process new units), or corrupted best-parent/is_free bookkeeping causing a node to diverge from network consensus on unit stability, both of which are impacts explicitly in scope (node disagreement on validity/stability, network unable to confirm new units).

### Likelihood Explanation
`conf.bDryRunNewTriggers` gates this path in `network.js` and is not proven (from the available index) to be enabled by default in production full nodes, so exploitability depends on that configuration flag. Any unprivileged peer can trigger a dry run merely by posting a normal unit with a payment output to an AA address (`ifOk` handler in `network.js`), and the race window depends on normal unit/AA processing happening concurrently — which is routine on an active hub/full node. Given the complexity of proving deterministic exploitation of the race without runtime testing, I rate likelihood as medium, but the root-cause absence of the write-mutex in a path that mutates the shared write-protected caches is a clear high-severity code defect.

### Recommendation
Acquire the `"write"` mutex for the entire duration of `dryRunPrimaryAATrigger` (from before `insertFakeOutputsIntoMcUnit`/`handleTrigger` through `revertResponsesInCaches`), exactly as `handlePrimaryAATrigger` and `writer.saveJoint` require for real trigger processing, so that no concurrent reader/writer of `assocUnstableUnits`, `assocBestChildren`, `assocKnownUnits`, or `assocUnstableMessages` can observe or retain references to the dry run's ephemeral cache entries.

### Proof of Concept
Conceptual PoC (concurrency-dependent, not directly executable from the indexed code alone):
1. Node runs with `conf.bDryRunNewTriggers = true`.
2. Attacker posts unit `U1` with a payment output to AA address `A`, causing `network.js`'s `ifOk` handler to call `aa_composer.dryRunPrimaryAATrigger` (no `"write"` lock held) — this creates and inserts a temporary AA response unit `R` into `storage.assocUnstableUnits`/`assocBestChildren` via `writer.saveJoint`.
3. Concurrently, real unit processing / main-chain stabilization (which does hold the `"write"` lock) runs on another already-in-flight unit and, while `R` is present in the caches, records `R` as a `best_parent_unit`/best child, or otherwise stores a direct reference to the object in `assocUnstableUnits[R]`.
4. The dry run finishes and calls `revertResponsesInCaches([...])`, which runs `storage.forgetUnit(R)` and `fixIsFreeAfterForgettingUnit(parent_units)`, deleting `R` from `assocUnstableUnits`/`assocBestChildren`/`assocKnownUnits` while the reference recorded in step 3 still points to the now-detached object.
5. Later code that looks up `R` via `assocStableUnits[R]`/`assocUnstableUnits[R]` (e.g., `getMcUnitProps`/`getFinalTps` in `storage.js`) finds it missing, throwing or silently diverging from what the other in-progress computation believed was true, corrupting stability/TPS bookkeeping or crashing the write pipeline.

function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
