### Title
CCMenu URL tokens are created without a `stack` scope, granting unscoped `read:stack` access to all stacks - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` creates/reuses an `ApiClient` with `read:stack` permission but never sets the client's `stack` association, so `current_api_client.stack_id` is `nil`. `Api::BaseController#stacks` treats a nil `stack_id` as "no restriction" and returns `Stack.all`, so a token minted for viewing one repo's CCMenu XML also authorizes `GET /api/1/stacks` to enumerate/read every stack in the instance.

### Finding Description
The intended binding is: a CCMenu token generated for stack `S` should only ever authorize reads scoped to `S`, i.e. `visible_stacks(token) == {S}`. That binding is broken in code:

- `CCMenuUrlController#client` builds the token's backing record with only `creator` and `name`, omitting `stack:`: [1](#0-0) 
Because `ApiClient belongs_to :stack, optional: true`, the resulting record's `stack_id` is `nil`. Rails' generated `stack_id?` attribute predicate therefore returns `false`.

- `Api::BaseController#stacks` uses that predicate to decide the scope of every other API action that calls `stacks`: [2](#0-1) 
When `stack_id?` is `false`, it falls back to `Stack.all` — unscoped.

- `StacksController#index` only checks `require_permission :read, :stack` (present on this client) and then filters `stacks` (which is `Stack.all` for this token) by an attacker-supplied `repo_owner`/`repo_name`: [3](#0-2) 

Additionally, `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` is keyed only on `creator` + `name`, not on the target stack, so the *same* single `ApiClient`/token is reused across every stack for which that user ever generates a CCMenu URL — meaning leaking one low-value URL (e.g., for a public repo) leaks a token equally valid for enumerating and reading metadata of every private stack that user's account touches.

Existing guards do not catch this: `require_permission!` only checks the permission string `read:stack`, which this client legitimately has; there is no check tying the permission to a specific stack unless `stack_id` is actually set. `authenticate_api_client` in `StacksController`'s parent just verifies the signed token, not its intended scope.

Attacker flow: obtain a leaked CCMenu URL (`/ccmenu/<owner>/<repo>/<branch>?token=...`) for any public repo the target Shipit instance manages, extract the `token` query param, then call `GET /api/1/stacks?repo_owner=X&repo_name=Y` with HTTP Basic auth using that token for arbitrary `X`/`Y` to determine existence and metadata (environment, branch, id, etc.) of private stacks.

### Impact Explanation
A token meant to expose only build-status XML for one specific, often public, stack instead grants read access to `StacksController#index`/`#show` for **every** stack in the Shipit instance, disclosing existence and metadata (environment, branch, deploy URL flags) of stacks the attacker has no business seeing. This is a real authorization-scope escalation reachable with only a leaked low-value token, matching "escalation into ... unauthenticated read of stack state" — the token was never authorized for anything beyond one stack's status feed. It is fully repeatable against arbitrary owner/name pairs from a single leaked credential, and because the underlying `ApiClient` is shared per-user across all their CCMenu URLs, a leak of any one such URL compromises the equivalent of a global read-scope credential for that user.

### Likelihood Explanation
Preconditions: the attacker needs a leaked/obtained CCMenu URL token (plausible since these URLs are designed to be embedded in low-security public places like CI badges or public monitoring dashboards), and the Shipit instance must actually have generated such tokens (feature exercised via `/ccmenu/*stack_id` route, which calls `ShipitController`-gated `CCMenuUrlController#fetch`). No Shipit secrets, no session, no privileged role are needed once the token is obtained — only the signed token string. This is low-cost and fully repeatable once a single token is captured. No dedicated test file exists for `CCMenuUrlController` in the repo, and no test asserts that CCMenu-issued tokens are restricted to their originating stack, so this behavior is unverified/unguarded.

### Recommendation
Set `stack:` when creating/finding the CCMenu `ApiClient`, and scope the `find_or_create_by!` lookup by stack (not just creator+name) so each stack gets its own narrowly-scoped token:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client', stack: stack)
end
```
This makes `current_api_client.stack_id?` true and restores the `Stack.where(id: current_api_client.stack_id)` scoping in `Api::BaseController#stacks`, preventing the token from being valid for any stack other than the one it was minted for.

### Proof of Concept
Add a minitest test (e.g. under `test/controllers/api/stacks_controller_test.rb` and/or a new `test/controllers/ccmenu_url_controller_test.rb`):
1. As an authenticated user with access to stack `A` (public repo), hit `CCMenuUrlController#fetch` for stack `A` and extract the returned `token`.
2. Assert on the created `ApiClient` record: `assert_equal stack_A.id, ApiClient.last.stack_id` — this currently **fails** (`stack_id` is `nil`), proving the broken binding.
3. Using that token via HTTP Basic auth, call `get :index, params: { repo_owner: stack_B.repository.owner, repo_name: stack_B.repository.name }` on `Api::StacksController` for an unrelated private stack `B` the token's creator does not have this scope for.
4. Assert `assert_response :ok` and that the JSON body contains stack `B`'s metadata — proving the CCMenu token (intended for stack `A` only) discloses stack `B`.
