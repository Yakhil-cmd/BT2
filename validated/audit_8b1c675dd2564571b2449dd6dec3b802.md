Based on my research, the strongest Aptos-native admission analog to the Arrakis "trusted setup, then untrusted payload" bug class is in the **encrypted-transaction filtering/admission path**, where filters make allow/deny decisions on unverified, attacker-supplied metadata that is never re-checked against what actually executes.

### Title
Encrypted-transaction module/entry-function filters admit based on unverified `claimed_entry_fun`, allowing filter bypass at execution - (File: `crates/aptos-transaction-filters/src/transaction_filter.rs`, `types/src/transaction/encrypted_payload.rs`)

### Summary
Aptos's encrypted-transaction feature lets a sender submit a `TransactionPayload::EncryptedPayload` whose real `TransactionExecutable` (module/function/args) is only revealed after the consensus decryption pipeline runs, well after mempool/batch/block admission decisions have already been made [1](#0-0) . Node operators can configure `TransactionFilter`/`BatchTransactionFilter`/`BlockTransactionFilter` rules keyed on `ModuleAddress` or `EntryFunction` to allow or deny transactions [2](#0-1) . For an encrypted transaction, the only pre-decryption signal available to these matchers is the optional, sender-supplied `claimed_entry_fun` field [3](#0-2) , which is never cryptographically bound to be present or accurate before execution — it is merely checked *after* decryption, and only if the sender chose to set it at all.

### Finding Description
`EncryptedInner::claimed_entry_fun` is an `Option<ClaimedEntryFunction>` fully controlled by the transaction sender at submission time [4](#0-3) . The commitment that actually binds the ciphertext to what will execute is `payload_hash`, checked only inside `try_into_decrypted`, which runs deep in the consensus decryption pipeline, long after batch/block filtering has already decided the transaction is included: [5](#0-4) 

Critically, the `claimed_entry_fun` check is conditional — `if let Some(claim) = &original.claimed_entry_fun { ... }` — so if the sender omits it (leaves it `None`), no consistency check is ever performed between the "claim" and the real decrypted executable. Node-level `TransactionMatcher::ModuleAddress`/`TransactionMatcher::EntryFunction` filters, which are the mechanism operators use to deny transactions calling specific modules/functions (e.g., to block a known-malicious or paused module), run on `SignedTransaction` at mempool/batch/block admission time [6](#0-5) . For an encrypted, undecrypted transaction, these matchers can only ever see the `claimed_entry_fun` (if present) — never the real target — since the true `TransactionExecutable` is inside the ciphertext and unavailable until the decryption pipeline runs post-admission.

This produces exactly the admission-boundary defect described in the report: the entity trusted to whitelist/deny is validator configuration (the "admin" analog), and the sender (untrusted, unprivileged) supplies the "malicious payload" (real ciphertext content) that is applied only after the trusted gate (`ModuleAddress`/`EntryFunction` deny rule) has already made its decision based on a value the sender fully controls and can simply omit or misstate. The result is a pre-validation mismatch: a transaction that should fail admission (be denied by a module/entry-function filter) can instead reach decryption and execution/commit, because the admission check and the executed content are decoupled and never reconciled by any enforced invariant when `claimed_entry_fun` is absent.

### Impact Explanation
An operator relying on `BlockTransactionFilter`/`BatchTransactionFilter`/`TransactionFilter` `ModuleAddress` or `EntryFunction` deny rules to block calls into a specific (e.g., paused, exploited, or otherwise disallowed) module can be silently bypassed by submitting the call as an encrypted transaction with `claimed_entry_fun: None` (or a benign/mismatched claim engineered to still pass the matcher used, if any). The transaction will pass filtering (since the filter cannot see the real target), be admitted into a batch/block, and later execute the attacker's real (originally undisclosed) entry function once decrypted — since `try_into_decrypted` only enforces the claim when one was supplied. This is a High-severity admission-rule bypass: it lets an unprivileged sender achieve unauthorized execution of a module/function class that validators explicitly configured to reject at the admission boundary, defeating a security control that operators depend on for blocking malicious modules.

### Likelihood Explanation
Likelihood is High for any deployment that (a) enables `FeatureFlag::ENCRYPTED_TRANSACTIONS` and (b) uses module/entry-function-based transaction filters for security purposes (e.g., blocking a compromised module during incident response). No special privileges are needed — any account can submit an `EncryptedPayload` transaction and simply choose not to populate `claimed_entry_fun`, which is explicitly optional by design [4](#0-3) .

### Recommendation
Either (1) require `claimed_entry_fun` to be always present and enforced (not `Option`) for encrypted transactions so admission-time filters have a value to check and `try_into_decrypted` always validates it, or (2) re-apply the same `ModuleAddress`/`EntryFunction` transaction-filter rules against the real `TransactionExecutable` after decryption and discard the transaction (without materializing effects) if the post-decryption target would have been denied by configured filters, closing the gap between admission-time filtering and execution-time content.

### Proof of Concept
1. Configure a validator with a `BlockTransactionFilter`/`TransactionFilter` rule: `Deny: [ModuleAddress: <malicious_module_addr>]`.
2. Craft an `EncryptedPayload::Encrypted` transaction whose ciphertext actually calls an entry function in `<malicious_module_addr>`, but set `claimed_entry_fun = None` (or omit it) as allowed by `EncryptedInner` [4](#0-3) .
3. Submit the transaction; `TransactionMatcher::ModuleAddress` cannot inspect the real (still-encrypted) module address and does not match, so the deny rule does not trigger and the transaction is admitted into a batch/block [6](#0-5) .
4. The consensus decryption pipeline later decrypts the payload; `try_into_decrypted` only checks `payload_hash` (which matches, since the sender built it correctly) and skips the `claimed_entry_fun` branch entirely because it is `None` [5](#0-4) .
5. The transaction executes the call into `<malicious_module_addr>` despite the configured admission-time deny rule.

Note: I was not able to view the exact implementation bodies of `matches_entry_function_module_address` and `matches_entry_function` (only their call sites), so I cannot 100% confirm they don't have some additional fallback behavior for encrypted transactions; this is stated as the one unverified assumption in this analysis, though the architecture (real executable is genuinely unavailable pre-decryption) strongly supports the conclusion.

/// A matcher that defines the criteria for matching transactions
#[derive(Clone, Debug, Deserialize, Eq, PartialEq, Serialize)]
pub enum TransactionMatcher {
    All,                                           // Matches any transaction
    TransactionId(HashValue),                      // Matches a specific transaction by its ID
    Sender(AccountAddress), // Matches any transaction sent by a specific account address
    ModuleAddress(AccountAddress), // Matches any transaction that calls a module at a specific address
    EntryFunction(AccountAddress, String, String), // Matches any transaction that calls a specific entry function in a module
    AccountAddress(AccountAddress), // Matches any transaction that involves a specific account address
    PublicKey(AnyPublicKey),        // Matches any transaction that involves a specific public key
    EncryptedTransaction,           // Matches any encrypted transaction
}

impl TransactionMatcher {
    /// Returns true iff the matcher matches the given transaction
    pub(crate) fn matches(&self, signed_transaction: &SignedTransaction) -> bool {
        match self {
            TransactionMatcher::All => true,
            TransactionMatcher::TransactionId(id) => signed_transaction.committed_hash() == *id,
            TransactionMatcher::Sender(sender) => {
                matches_sender_address(signed_transaction, sender)
            },
            TransactionMatcher::ModuleAddress(address) => {
                matches_entry_function_module_address(signed_transaction, address)
            },
            TransactionMatcher::EntryFunction(address, module_name, function) => {
                matches_entry_function(signed_transaction, address, module_name, function)
            },
            TransactionMatcher::AccountAddress(address) => {
                matches_sender_address(signed_transaction, address)
                    || matches_entry_function_module_address(signed_transaction, address)
                    || matches_multisig_address(signed_transaction, address)
                    || matches_script_argument_address(signed_transaction, address)
                    || matches_transaction_authenticator_address(signed_transaction, address)
            },
            TransactionMatcher::PublicKey(public_key) => {
                matches_transaction_authenticator_public_key(signed_transaction, public_key)
            },
            TransactionMatcher::EncryptedTransaction => {
                matches_encrypted_transaction(signed_transaction)
            },
        }
    }
