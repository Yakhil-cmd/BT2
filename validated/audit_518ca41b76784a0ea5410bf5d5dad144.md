### Title
Incomplete cache cleanup after reverting a chained AA trigger leaves free/parent bookkeeping inconsistent - ([File: aa_composer.js])

### Summary
`revertResponsesInCaches()` in `aa_composer.js` mirrors the ALPINE-CVE-2022-23035 bug class: an iterative cleanup over *multiple* related objects (here, multiple AA response units produced by a chain of primary→secondary AA calls) only captures the "parent" bookkeeping needed for cleanup from the *first* item, then unconditionally tears down (forgets) *all* items, leaving state derived from the other items' relationships uncorrected — exactly the "insufficient cleanup when multiple items are involved" pattern in the advisory.

### Finding Description
When a primary AA trigger fans out into secondary AA calls (a chain of AAs calling AAs), `handleTrigger()` accumulates one `objAAResponse` per AA in the chain into `arrResponses`, each carrying its own `response_unit` [1](#0-0) .

If any AA later in the chain bounces, `revert()` is invoked, which — unless in `bAir` (dry-run) mode — calls `revertResponsesInCaches(arrResponses)` to roll the in-memory unstable-unit caches back before the SQL `ROLLBACK TO SAVEPOINT` [2](#0-1) .

`revertResponsesInCaches` then does:
```js
function revertResponsesInCaches(arrResponses) {
	var arrResponseUnits = [];
	arrResponses.forEach(function (objAAResponse) {
		if (objAAResponse.response_unit)
			arrResponseUnits.push(objAAResponse.response_unit);
	});
	if (arrResponseUnits.length > 0) {
		var first_unit = arrResponseUnits[0];
		var objFirstUnit = storage.assocUnstableUnits[first_unit];
		var parent_units = objFirstUnit.parent_units;
		arrResponseUnits.forEach(storage.forgetUnit);
		storage.fixIsFreeAfterForgettingUnit(parent_units);
	}
}
``` [3](#0-2) 

`parent_units` is captured only from the *first* response unit in the chain, before any unit is forgotten. Then `arrResponseUnits.forEach(storage.forgetUnit)` deletes the in-memory record (`assocUnstableUnits[unit]`, `assocBestChildren`, etc.) for **every** response unit in the chain — including secondary/tertiary response units whose own `parent_units` differ from the first unit's (in a multi-AA chain, each subsequent response unit's parent is typically the previous response unit, not the first unit's parents). Finally, `fixIsFreeAfterForgettingUnit` is called with only the first unit's `parent_units`, so the "is_free" recompute logic
```js
function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
``` [4](#0-3) 
never runs for the parents of the 2nd..Nth forgotten units. Any of those parents (e.g. an intermediate response unit that itself is a parent of a now-forgotten unit and has no other children) is left with a stale `is_free=0` in the in-memory cache, even though its only child was just erased from the cache and from the DB (rolled back).

This is precisely the CVE's bug class: an iterative cleanup across several related objects where the retry/fixup step is scheduled/executed for only one of them, while the rest are torn down anyway, leaving cached bookkeeping ("pointers") that other code continues to trust as valid.

### Impact Explanation
`is_free` in `storage.assocUnstableUnits` is the in-memory source of truth used by the local node's own unit composer (`parent_composer.js`) to select "free" (childless) units as parents when building new units for this node, and by `main_chain.js` main-chain/stability logic. A unit incorrectly stuck at `is_free=0` after its only child was removed will be silently excluded from being chosen as a parent by this node's own composer, and any main-chain/stability logic in `main_chain.js` that trusts the `is_free` flag to decide free-unit set membership can diverge from the DB's authoritative `is_free` column (which the aborted transaction's rollback should have restored correctly). This is an unprivileged, remotely triggerable in-memory cache desync (any user/AA author can construct a chained-AA trigger that ends in a bounce), and depending on how the divergence propagates, it can cause the affected node to build on stale/incorrect free-unit sets, contributing to node-level disagreement about which units are free/eligible tips, or missed reuse of legitimately free units — a systemic correctness bug reachable purely by posting units/triggers.

### Likelihood Explanation
Reachable by any unprivileged AA trigger sender: crafting a primary AA that calls a secondary (or tertiary) AA and having the final AA in the chain bounce (e.g., insufficient balance, thrown formula error, `bounce()` call) is an entirely normal, attacker-controllable operation, no special privileges needed. The only requirement is a chain of length ≥ 2 (`arrResponses.length` > 1 with distinct parent relationships) ending in a bounce that triggers `revert()` outside of `bAir` (i.e., during real/live AA execution, not just dry-run estimation).

### Recommendation
In `revertResponsesInCaches`, collect and fix up the parent units of **every** response unit being forgotten, not just the first one — e.g., gather `parent_units` for each unit in `arrResponseUnits` before calling `storage.forgetUnit` on any of them, deduplicate, and pass the full set to `storage.fixIsFreeAfterForgettingUnit`. Alternatively, call `fixIsFreeAfterForgettingUnit` once per unit immediately after forgetting it, using that unit's own `parent_units` captured beforehand.

### Proof of Concept
1. Deploy an AA chain of at least 3: `A` (primary) → `B` (secondary) → `C` (secondary), where `C`'s message logic causes a bounce (e.g. insufficient AA balance or an explicit `bounce()`).
2. Post a trigger unit to `A` with sufficient funds to get past `A` and `B` but insufficient/failing at `C`.
3. During `handleTrigger` execution, `arrResponses` accumulates response units for `A`'s response and `B`'s response (parent chain: `A_response`'s parent is the trigger unit; `B_response`'s parent is `A_response`) before `C` bounces and `revert()` fires.
4. `revertResponsesInCaches` captures `parent_units` only from `arrResponseUnits[0]` (the `A` response unit, whose parent is the original trigger unit), then forgets both `A_response` and `B_response` from `assocUnstableUnits`, but only calls `fixIsFreeAfterForgettingUnit` on the trigger unit's parent set — never recomputing `is_free` for `A_response` (which was `B_response`'s parent and just lost its only child).
5. Inspect `storage.assocUnstableUnits[A_response_unit].is_free` in memory after the rollback: it remains `0` even though the unit has no children anymore in the cache (and its child row was rolled back in the DB), diverging from the DB-persisted state and from what a freshly-initialized cache (`initUnstableUnits`) would compute.
