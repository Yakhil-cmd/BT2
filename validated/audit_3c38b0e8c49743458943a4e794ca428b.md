Based on my investigation, I found a concrete analog vulnerability in `pox-5.clar`'s L1 lockup verification logic.

### Title
`register-for-bond` allows the same L1 Bitcoin lockup output to be replayed across multiple registrations to credit sats never re-locked - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
The reported bug class is a "return/validation dropped on one code path causes an equality to be violated" — in the mTOFT case a missing `return true` broke correctness (a fail-safe direction). The stacks-core analog found is the inverse-but-related failure mode explicitly called out in the rules ("sats credited by an L1 proof that were never locked on Bitcoin"): `verify-l1-lockups` in `pox-5.clar` only prevents duplicate outpoints *within a single call's fold*, via a `seen-outpoints` accumulator that is freshly initialized to `(list)` on every invocation, and there is no persistent, contract-wide map recording previously consumed L1 lockup outpoints.

### Finding Description
`register-for-bond` computes `sats-total` for the L1 path by calling `verify-l1-lockups`, which folds `validate-l1-lockup` over the caller-supplied list of Bitcoin outputs: [1](#0-0) 

Inside the fold, duplicates are only rejected against the `seen-outpoints` list that is part of the accumulator, and that accumulator is reset to `(list)` at the start of `verify-l1-lockups` itself: [2](#0-1) 

`validate-l1-lockup` validates that the Bitcoin output exists, matches the expected script, and hasn't been repeated *within this same list*, then adds its outpoint to `seen-outpoints`: [3](#0-2) 

Nothing in this code, nor in `register-for-bond`, persists which `(txid, output-index)` outpoints have already been counted toward a previous bond registration. `register-for-bond` accepts this `sats-total` and uses it to set `amount-sats`/`is-l1-lock: true` in `protocol-bond-memberships`, and to add shares via `add-staker-to-bond-cycles`: [4](#0-3) [5](#0-4) 

Because the same locked Bitcoin UTXO proof can be resubmitted in a later `register-for-bond` call (e.g. for a new/rolled bond, or after `roll-sbtc`/rollover logic clears prior membership), the contract will re-credit `amount-sats` for BTC that was locked once but is being claimed as backing for multiple, disjoint bond memberships/reward-cycle share allocations.

### Impact Explanation
This breaks the core equality the L1-lockup path is meant to guarantee: sats credited in `protocol-bond-memberships`/`bond-shares` should correspond 1:1 to actual locked BTC. If the same on-chain lockup output can be reused across separate `register-for-bond` calls, a staker can inflate `amount-sats`, `total-sbtc-staked`-equivalent bond shares, and thus signer/reward weighting or reward-slot allocation without any additional BTC ever being locked. This is a double-counting-of-commitment class issue (rated High/Critical per the given impact taxonomy: "signing weight or reward slots exceeding locked value" / "double-counting a commitment or reward").

### Likelihood Explanation
Reachable by any allowlisted staker with a single previously-executed BTC lockup transaction and no privileged role required — they only need to call the public `register-for-bond` function twice (or reuse the proof after a rollover event clears/enables re-registration), each time supplying the same L1 Merkle proof/output data. No admin, signer, or miner cooperation is required, and the check that would prevent this (a persistent, cross-call outpoint registry) does not exist in the visible code.

### Recommendation
Add a durable map (e.g. `used-l1-lockup-outpoints: {txid: (buff 32), output-index: uint} -> bool`) that is checked and updated (via `map-insert`, asserting it doesn't already exist) inside `validate-l1-lockup`/`verify-l1-lockups`, in addition to the intra-call `seen-outpoints` check, so that once an L1 lockup output has been credited toward any bond registration, it can never be credited again in a subsequent call.

### Proof of Concept
Conceptual sequence (cannot fully confirm without running the full contract-test harness, since I could not view the entirety of `register-for-bond`'s rollover/overlap gates or confirm whether any other map in the file independently tracks consumed outpoints across calls):
1. Staker locks BTC output `O` for a `staker-unlock-bytes` script tied to bond `B0`, and calls `register-for-bond` for `B0` supplying `O` as `btc-lockup`. `verify-l1-lockups` validates `O` and returns `sats-total = amount(O)`; membership for `B0` is recorded with `amount-sats = amount(O)`.
2. After `B0`'s term completes (or via the rollover path that clears `protocol-bond-memberships`/`staker-info`), the staker calls `register-for-bond` again for a new bond `B1`, again supplying the *same* output `O` (same `txid`/`output-index`, same Merkle proof, same header) as `btc-lockup`.
3. Because `seen-outpoints` is freshly initialized per call [2](#0-1) , and no persistent cross-call registry exists, `validate-l1-lockup` accepts `O` again, and `sats-total` is computed as `amount(O)` a second time — crediting the same locked BTC toward `B1`'s `amount-sats`, shares, and signer weighting, even though no new BTC was locked for `B1`.

This should be verified against the full contract (particularly `bond-overlaps-new-position?`/`verify-bond-rollover-window` gates and any additional membership state) using a Devin session with full file access, since the index may not capture every helper function that could incidentally reject reuse.
