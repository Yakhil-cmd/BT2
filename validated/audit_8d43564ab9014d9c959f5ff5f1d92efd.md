## Finding: Multisig payload-substitution during execution is only prevented by an opt-in feature flag, allowing an executing owner to run a different entry function than the one approved by quorum

### Title
Multisig quorum admission does not bind approvals to the executed payload unless `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is enabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The Code4rena Hybra Finance report's root cause is a validation gap where the admission layer (`GaugeManager._createGauge`) trusts unverified input (`isPair = true`) instead of enforcing that the object it operates on matches what was actually vetted/approved. The Aptos-native analog is in the multisig execution path: `validate_multisig_transaction` (the VM prologue that gates whether a multisig transaction may execute) only checks that the *payload actually being executed* matches the *payload that was voted on* when a feature flag (`abort_if_multisig_payload_mismatch_enabled`) is turned on. When a transaction was created via `create_transaction` (full payload stored on-chain, not just a hash) and that flag is disabled, there is no invariant tying the quorum of votes to the bytes that end up executing.

### Finding Description
Aptos multisig transactions are proposed with `create_transaction` (stores the full `MultisigTransactionPayload` on-chain) or `create_transaction_with_hash` (stores only a `sha3_256` hash) [1](#0-0) . Owners vote via `approve_transaction`/`reject_transaction`, which only record a boolean vote keyed by `sequence_number` [2](#0-1) ; they never re-validate the payload at vote time beyond what was originally stored.

The actual bytes that execute on-chain are **not** re-fetched from the stored `MultisigAccount.transactions` table at execution time. Instead, whoever finally submits the top-level `SignedTransaction` supplies the `executable` (`TransactionExecutableRef::EntryFunction`), which the VM executes directly [3](#0-2) . The only gate preventing a rogue final-executor from substituting a completely different function call is the prologue's payload check, run in `run_multisig_prologue`/`validate_multisig_transaction`:

```
if (transaction.payload_hash.is_some()) {
    assert!(sha3_256(payload) == *payload_hash, ...);   // only applies to hash-based creation
};
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()) {
    assert!(payload == *stored_payload, ...);           // only enforced if feature flag is ON
}
``` [4](#0-3) 

If a transaction was created with `create_transaction` (full payload stored, `payload_hash = None`) **and** `abort_if_multisig_payload_mismatch_enabled()` is not enabled, neither `if` branch executes. In that state, `validate_multisig_transaction` only checks: multisig account exists, caller is an owner, sequence number matches, and quorum count (`num_signatures_required`) is met [5](#0-4) . It never asserts that the `payload` bytes handed to the prologue (and subsequently executed by the VM) match `transaction.payload`, the content the owners actually voted on.

This mirrors the external report's pattern precisely: an admission function (`_createGauge`) is supposed to bind trust to a specific verified object (the factory-created pool) but instead accepts anything meeting superficial criteria (`isPair = true`), because the "real" check was intentionally short-circuited. Here, `validate_multisig_transaction` is supposed to bind quorum trust to a specific verified payload, but the binding is intentionally short-circuited unless a feature flag is enabled — the equivalent of the removed `require(_pool_hyper == _pool_factory, ...)` line.

### Impact Explanation
Any account already holding an M-of-N owner slot who is also the one to submit the final on-chain execution transaction (a normal, unprivileged part of the multisig workflow — anyone with enough votes recorded for a sequence number, including the executing owner's own implicit vote, may call execute) can supply an arbitrary `EntryFunction` as the `executable` of the top-level transaction, bypassing the intent that was actually voted on by the other owners. Because the quorum check only counts votes against a `sequence_number`, not against the specific bytes ultimately executed (when the mismatch-check feature is off and the transaction was created with `create_transaction`), the executing owner effectively obtains unilateral control to execute unapproved logic under the identity of the multisig account (`multisig_account`'s signer). This is a state-transition-under-the-wrong-approval-set bug at the transaction admission boundary — a "should fail admission" transaction is instead allowed to execute and commit.

### Likelihood Explanation
Likelihood depends entirely on the on-chain configuration state of `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` (feature ID from `features.move`) and on whether the specific pending multisig transaction was created with `create_transaction` (full payload) rather than `create_transaction_with_hash`. I could not confirm from the indexed code whether this flag is enabled by default on Aptos mainnet/testnet, nor its current rollout status — this is the primary source of uncertainty in this finding. The very existence of a dedicated feature flag named `abort_if_multisig_payload_mismatch_enabled`, with an explicit code comment describing exactly this check, strongly suggests the Aptos team is aware of and has already engineered a fix for this exact gap; the residual risk is scoped to any deployment or migration window where the flag remains off while `create_transaction` (non-hash) multisig proposals are in use.

### Recommendation
- Make the payload-match check for `create_transaction`-style (full payload) multisig transactions unconditional (remove the feature-flag gate), or reject `create_transaction` (non-hash) multisig proposals entirely once `create_transaction_with_hash` is available, so admission is always bound to the exact approved payload.
- Ensure `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is enabled on all live networks before this code path can be reached, and add an explicit invariant/test asserting `validate_multisig_transaction` always aborts on any payload mismatch regardless of feature-flag state.

### Proof of Concept
1. Multisig account `M` with owners `{A, B, C}`, `num_signatures_required = 2`.
2. `A` calls `create_transaction(M, entry_function_transfer_1_APT_to_A)`, which stores the full payload (`payload_hash = None`) at `sequence_number = N` [1](#0-0) .
3. `B` reviews the on-chain `transaction.payload` (transfer 1 APT to A) and calls `approve_transaction(M, N)`, reaching quorum (`A`'s creation vote + `B`'s approval = 2) [6](#0-5) .
4. Assuming `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is disabled on this network, `A` (or any owner) submits the top-level `SignedTransaction` with `executable = entry_function_transfer_all_APT_to_A_and_drain_treasury` instead of the approved transfer.
5. `validate_multisig_transaction` checks: account exists ✓, caller is owner ✓, sequence number matches ✓, quorum (2) met ✓ — and since `payload_hash` is `None` and the mismatch-check feature is off, it never compares the submitted executable against the approved `transfer_1_APT_to_A` payload [4](#0-3) .
6. The VM executes the substituted, unapproved entry function under `M`'s signer, draining funds that `B` never approved to be moved.

    public entry fun vote_transanction(
        owner: &signer, multisig_account: address, sequence_number: u64, approved: bool) {
        assert_multisig_account_exists(multisig_account);
        let multisig_account_resource = borrow_global_mut<MultisigAccount>(multisig_account);
        assert_is_owner_internal(owner, multisig_account_resource);

        assert!(
            multisig_account_resource.transactions.contains(sequence_number),
            error::not_found(ETRANSACTION_NOT_FOUND),
        );
        let transaction = multisig_account_resource.transactions.borrow_mut(sequence_number);
        let votes = &mut transaction.votes;
        let owner_addr = address_of(owner);

        if (votes.contains_key(&owner_addr)) {
            *votes.borrow_mut(&owner_addr) = approved;
        } else {
            votes.add(owner_addr, approved);
        };

        emit(
            Vote {
                multisig_account,
                owner: owner_addr,
                sequence_number,
                approved,
            }
        );
    }
