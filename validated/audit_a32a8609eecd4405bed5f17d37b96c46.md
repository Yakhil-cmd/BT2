## Title
Webhook signature is verified against the organization named in `repository.owner.login`, but every event handler acts on the repository named in `repository.full_name` from the same attacker-controlled payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization deployments (a documented, supported configuration — see `config/secrets.development.shopify.yml` and `docs/setup.md`), each GitHub organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects which secret to verify the HMAC signature against using `repository_owner`, a field taken from the unauthenticated JSON body itself. Every webhook handler, however, resolves the `Repository`/`Stack` to mutate using a *different* field from the same body: `repository.full_name`. Because both fields live in the same attacker-supplied JSON and only one of them is bound to the verified organization, a party who legitimately controls the webhook secret for *any* configured organization can forge a signature that Shipit accepts, while pointing `repository.full_name` at a completely unrelated, victim-owned repository/stack.

### Finding Description
`WebhooksController#verify_signature` looks up the GitHub App config to verify against like this: [1](#0-0) 

`repository_owner` is derived purely from the JSON payload the "attacker" (an organization owner already in control of some registered org's webhook secret) sends: [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `webhook_secret` per organization key in `secrets.github` when multiple orgs are configured: [3](#0-2) 

Once the signature is accepted, `WebhooksController#create` dispatches the *entire, still attacker-controlled* payload to handlers: [4](#0-3) 

Every default handler resolves the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')` — a separate field from `repository.owner.login` used for signature selection: [5](#0-4) 

`PushHandler`, for example, uses this `stacks` scope (bound to `full_name`, not `owner.login`) to trigger a GitHub sync on whatever branch/stack it finds: [6](#0-5) 

The `pull_request`-family handlers (label/labeled/unlabeled) likewise resolve `repository` from `params.repository.full_name` and then archive/unarchive review stacks or capture PR labels for that repository — again unrelated to the organization whose secret validated the signature: [7](#0-6) 

**Binding broken (equality that should hold but doesn't):**
`organization whose secret authenticated the HMAC signature` (`repository.owner.login`) **≠** `repository/stack that the handler logic actually writes to` (`repository.full_name`).

Before the attack: signature verification and payload action are implicitly assumed to refer to the same repository, since in a legitimate GitHub-originated webhook `owner.login` and `full_name`'s owner segment always match.

After the attacker's forged request: `owner.login` is set to an organization the attacker legitimately controls (so the HMAC check passes with a secret the attacker legitimately possesses), while `full_name` is set to any other organization/repository already registered as a `Shipit::Repository` — a value the attacker does not control any secret for, yet whose associated `Stack` is now acted upon.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Concretely, with a forged `push`/`status`/`pull_request` event an attacker who owns/administers any one organization onboarded to this Shipit instance can:
- Force `GithubSyncJob` to run against a victim stack with an attacker-chosen `expected_head_sha` (`PushHandler`), influencing which commit is considered `HEAD` for deploy purposes.
- Write `Commit::Status` rows for arbitrary shas/contexts on a victim's commits via the `status` handler path, which can be used to satisfy `required_statuses`/CI gating checks that gate merges and deploys.
- Archive/unarchive review stacks or mutate PR label state for repositories the attacker does not own, via the PR label handlers.

Depending on downstream CI-gating and merge-queue configuration, this can translate into an unauthorized deploy or merge on a repository the attacker has no legitimate access to — squarely inside the defined Critical/High impact categories (unauthorized deploy/merge, cross-repository writes) without requiring a Shipit session, an `ApiClient` token, or any privileged account on the *victim* side.

### Likelihood Explanation
Exploitability is limited to environments running the documented multi-organization GitHub App configuration (multiple entries under `secrets.github`, each with its own `webhook_secret`), which is an explicitly documented and supported setup, not a misconfiguration. Any party who is granted (or self-registers, where the host's onboarding process allows self-service org registration) one organization's app installation automatically obtains that organization's `webhook_secret`, which is all that's needed to forge requests targeting any other org's repositories tracked by the same Shipit instance. No interaction with the victim org, no Shipit account, and no `ApiClient` token are required.

### Recommendation
Bind signature verification and payload action to the same field: verify the signature using the secret associated with the organization portion of `repository.full_name` (or explicitly re-validate that `repository.owner.login` matches the owner segment of `full_name`) before dispatching to handlers. Reject events where these two fields disagree.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md` multi-org schema), and register a `Shipit::Repository`/`Stack` for `victim-org/victim-repo`.
2. As the owner of `attacker-org`'s GitHub App installation, craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` using `attacker-org`'s legitimately-known `webhook_secret` over the raw body.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` (per `repository_owner`, i.e. `owner.login`), successfully verifies the signature, and `PushHandler` subsequently looks up `victim-org/victim-repo` via `full_name` and enqueues `GithubSyncJob` for the victim's stack with the attacker-supplied `expected_head_sha`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
