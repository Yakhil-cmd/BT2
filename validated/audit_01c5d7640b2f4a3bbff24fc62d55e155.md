Based on my investigation, I found a valid analog: the merge-status page bypasses Shipit's team-authorization gate the same way UMA's actual implementation deviated from what the documentation promised — the check that's actually enforced (`logged_in?`) is weaker than the check the rest of the application relies on (`authorized?`).

### Title
`MergeStatusController#show` renders stack merge/CI/lock status to any authenticated GitHub user, bypassing `Shipit.github_teams` authorization - (File: `app/controllers/shipit/merge_status_controller.rb`)

### Summary
Every other Shipit page is gated by `Authentication#force_github_authentication`, which requires a user to be both **logged in** *and* **a member of `Shipit.github_teams`** (`current_user.authorized?`) before any stack data is rendered [1](#0-0) . `MergeStatusController` explicitly opts its `:check` and `:show` actions out of that filter [2](#0-1) , and re-implements its own weaker gate in `show`, checking only `current_user.logged_in?` [3](#0-2) . `logged_in?` on `User` is unconditionally `true` [4](#0-3) , so any GitHub account that completes the (unrestricted) OAuth login flow satisfies it — team membership is never verified, unlike `authorized?` [5](#0-4) .

### Finding Description
The trust binding the rest of the engine relies on is:
`render(stack data)` requires `current_user.authorized?` (member of `Shipit.github_teams`)

`MergeStatusController#show`'s actual binding is:
`render(stack data)` requires only `current_user.logged_in?` (any signed-in GitHub identity)

Because GitHub OAuth login itself (`GithubAuthenticationController#callback` / `sign_in_github`) is not restricted to org/team members — it creates or finds a `User` record for *any* GitHub account that completes the OAuth dance [6](#0-5)  — an attacker only needs a plain GitHub account, not membership in any configured `Shipit.github_teams`, to satisfy `logged_in?`. `show` then resolves the target stack either from `params[:stack_id]` or by parsing an attacker-controlled `Referer` header and looking up any stack by owner/repo/branch [7](#0-6) , and renders `stack.merge_status` (lock state, CI/merge-queue state) for that stack without ever calling `current_user.authorized?`.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization — explicitly one of the High-severity impact categories: an outside GitHub user (never vetted against the configured teams) can read stack lock/merge/CI state that the rest of the application deliberately restricts to team members via `force_github_authentication`.

### Likelihood Explanation
Any GitHub user can complete OAuth login against the Shipit instance (login itself isn't gated on team membership), then hit `/merge_status/*stack_id` directly with a known/guessed stack path, or spoof a `Referer` header pointing at any `owner/repo/pull/N` URL. No `ApiClient` token, webhook secret, session hijack, or privileged account is required — just a personal GitHub identity.

### Recommendation
Have `MergeStatusController#show` (and `#check`, if it is meant to expose more than a public build-status badge) call the same `current_user.authorized?` check used by `force_github_authentication`, or explicitly restrict `skip_authentication` to only the routes intended to be fully public, rather than substituting a weaker inline `logged_in?` check for the shared team-authorization gate.

### Proof of Concept
1. An attacker with any GitHub account (not a member of the org's configured `Shipit.github_teams`) visits `/github/auth/github` and completes OAuth; `sign_in_github` creates/finds a `User` and sets `session[:user_id]` regardless of team membership [8](#0-7) .
2. The attacker requests `GET /merge_status/<owner>/<repo>/<env>` (or any URL routed to `MergeStatusController#show` with a `Referer` header pointing at a target PR URL).
3. Because `show`/`check` skip `force_github_authentication`, only `current_user.logged_in?` is checked [9](#0-8) ; the attacker is not a team member but passes this weaker check and receives the target stack's lock/merge/CI status, which should have been restricted to `Shipit.github_teams` members.

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
