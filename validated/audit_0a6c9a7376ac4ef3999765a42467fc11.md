### Title
Cleartext logging of decrypted device-message content and full private-payment/wallet payloads - ([File: device.js])

### Summary
`device.js` logs the complete plaintext body of every device message — both when sending and when decrypting a received one — to `console.log`. This mirrors the Sentry bug class (`GHSA-6cjm-4pxw-7xp9`): sensitive authentication/spend material is written to application logs in cleartext where any operator, log aggregator, or process with log access can recover it. Device messages in ocore carry private payment chains, textcoin mnemonics/private keys, wallet-definition and shared-address signing-path data, and xpubkeys exchanged between paired wallets/AA-bot correspondents — an unprivileged paired counterparty (or a bot the user pairs with, e.g. via pairing code) fully controls the content that ends up in these logs.

### Finding Description
`reliablySendPreparedMessageToHub` logs the outgoing message body before it is encrypted: [1](#0-0) 
`console.log('will encrypt and send to '+recipient_device_address+': '+JSON.stringify(json));` prints the full `json` object, which for `sendMessageToDevice`/`sendMessageToHub` includes `subject` and `body` — i.e., the actual application payload sent between paired devices (private-payment chains, wallet definitions/xpubkeys, shared-address signing paths, chat messages, textcoin claim data, etc.), as built in [2](#0-1) .

Symmetrically, `decryptPackage` logs the fully decrypted plaintext of every inbound device message: [3](#0-2) 
`console.log("decrypted: "+decrypted_message);` writes out the entire decrypted JSON string before it is even parsed, regardless of `subject`/`body` type.

Both logging calls fire unconditionally on the standard hot path of pairing/messaging (`sendMessageToDevice` → `sendMessageToHub` → `reliablySendPreparedMessageToHub`, and `decryptPackage` invoked from the `hub/message`/`hub/deliver` handlers in `network.js`), so any content that two paired devices exchange — which is initiated by an ordinary user/bot pairing over a pairing code, not a privileged operator — is captured verbatim in logs. This includes:
- Textcoin/private-asset claim mnemonics and payload contents (`wallet.js`, `storePrivateAssetPayload`, `handlePrivatePaymentFile` area) which carry actual spendable private keys/private-payment chains.
- Wallet co-signing material: extended pubkeys, signing paths, shared-address definitions exchanged during multisig wallet setup.
- Chat/text messages that a correspondent may embed with sensitive data.

An attacker with any access to node logs (log files, log-shipping/aggregation infra, crash reports, etc.) can read these logs and recover private payment chains or wallet key material sent by any paired counterparty, enabling unauthorized spending of otherwise-private funds or takeover of shared-address material — without needing to compromise the node’s database or keys directly.

### Impact Explanation
If a private payment chain (e.g., ochanged textcoin) is exchanged over device messaging and ends up in cleartext logs, whoever reads those logs obtains the ability to spend those private funds before or instead of the intended recipient — a concrete unauthorized-spending / double-spend risk. Because private-asset/textcoin chains function as bearer instruments (whoever presents the valid chain first claims the funds), log exposure is directly equivalent to leaking a "cleartext password" that grants spending authority. This satisfies the “concrete unauthorized spending” bar in the validation rules.

### Likelihood Explanation
This is not a rare configuration — `console.log` calls execute on every send/receive of a device message with no log-level guard, and any user who pairs with another device/bot (a routine, permissionless action) can trigger transmission of private-payment or wallet material through this path. Any deployment that persists stdout/stderr to disk or a log-aggregation pipeline (the common case for hosted wallets, bots, or hub operators) is affected, making exploitation likelihood high once any log access is obtained.

### Recommendation
- Remove or heavily redact the `console.log` statements in `device.js` (`decryptPackage`'s `"decrypted: "+decrypted_message` and `reliablySendPreparedMessageToHub`'s `JSON.stringify(json)`), or gate them behind an explicit `debug`/opt-in flag that defaults to off and never runs in production.
- When any debug logging of message content is genuinely needed, log only non-sensitive metadata (message hash, `subject`, sender/recipient addresses) and never the full `body`/decrypted payload.
- Audit other `console.log(JSON.stringify(...))` calls touching `objValidationState`, private coin data, etc. (e.g., `validation.js:2437` logging `objValidationState` which can include `src_coin` details for private assets) for the same class of leakage.

### Proof of Concept
1. Node A pairs with Node B via a normal pairing code (no special privilege required).
2. Node A sends Node B a textcoin claim / private-payment chain using the wallet.js flow that calls `device.sendMessageToDevice(...)`.
3. On Node A's side, `reliablySendPreparedMessageToHub` executes `console.log('will encrypt and send to '+recipient_device_address+': '+JSON.stringify(json))`, printing the entire private-payment payload (including mnemonic/spend chain) to A's log output.
4. On Node B's side, when the message arrives, `decryptPackage` executes `console.log("decrypted: "+decrypted_message)`, printing the same sensitive payload to B's log output.
5. Anyone with read access to either node's logs (log files, centralized logging, crash-report tooling) can extract the private-payment chain/mnemonic and claim the funds themselves, effectively stealing the transferred asset. [3](#0-2) [1](#0-0)

function sendMessageToHub(ws, recipient_device_pubkey, subject, body, callbacks, conn){
	// this content is hidden from the hub by encryption
	var json = {
		from: my_device_address, // presence of this field guarantees that you cannot strip off the signature and add your own signature instead
		device_hub: my_device_hub, 
		subject: subject, 
		body: body
	};
	conn = conn || db;
	if (ws)
		return reliablySendPreparedMessageToHub(ws, recipient_device_pubkey, json, callbacks, conn);
	var recipient_device_address = objectHash.getDeviceAddress(recipient_device_pubkey);
	conn.query("SELECT hub FROM correspondent_devices WHERE device_address=?", [recipient_device_address], function(rows){
		if (rows.length !== 1)
			throw Error("no hub in correspondents");
		reliablySendPreparedMessageToHub(rows[0].hub, recipient_device_pubkey, json, callbacks, conn);
	});
}
