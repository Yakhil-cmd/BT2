### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` allows one repository's status webhook to mutate another stack's commit state and trigger auto-merge/deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by bare SHA across the entire database, with no repository or stack scoping, unlike the base `Handler` class's `stacks` helper used by other handlers. A validly-signed status webhook for one repository (which an attacker can obtain simply by owning/controlling a repo where the Shipit-connected GitHub App/organization is configured) can therefore write a `Status` record onto a `Commit` belonging to a completely different stack, as long as the SHA values collide (trivially achievable via a fork sharing commit history with the victim's tracked repository).

### Finding Description
The broken binding: the code assumes `commit.sha == params.sha ⟺ commit.stack.repository == payload.repository`, but the handler only enforces the left-hand side.

- `StatusHandler#process` does: [1](#0-0) 
This iterates `Commit.where(sha: params.sha)` with zero reference to `payload['repository']`.

- By contrast, the base `Handler` class provides a `stacks` helper that properly scopes lookups to the repository that authenticated the webhook: [2](#0-1) 
`StatusHandler` does not use this helper at all, unlike other handlers (e.g. `PushHandler`, `CheckSuiteHandler`) which are expected to scope to `stacks`.

- `verify_signature` in the controller only checks the HMAC of the raw payload against `Shipit.github(organization: repository_owner)` — it authenticates that "GitHub sent this for some org configured on this Shipit instance," not that "this specific repository owns this specific SHA": [3](#0-2) 

- Once `create_status_from_github!` is called on the wrongly-matched commit, `Commit#add_status` fires hooks and, critically, calls `stack.schedule_merges` on state transitions to `pending`/`success`: [4](#0-3) 
This is exactly the mechanism verified in tests to enqueue `ProcessMergeRequestsJob` and fire `deployable_status` hooks that drive auto-merge/auto-deploy: [5](#0-4) 

Exploit flow: attacker forks (or otherwise obtains push access to) a repository that shares commit SHAs with the victim's tracked repository (e.g., a fork of the victim's public repo, or any repo where the same commit was cherry-picked/pushed). Attacker triggers a `status` event for context `github-actions` on that shared SHA (e.g., by pushing to their fork and letting GitHub Actions report a status, or by controlling a CI integration that posts a status) with `state: success` (or `failure`). GitHub signs and delivers this webhook using the attacker-controlled repository's org/app config, which passes `verify_signature`. `StatusHandler#process` then finds ALL `Commit` rows across the DB with that SHA — including the victim stack's commit — and writes a `github-actions` status onto it, even though the victim stack's repository never emitted that status. If the victim stack requires `github-actions` for merge/deploy gating and has `bot_login` configured (a `Shipit.user` identity used to auto-trigger merges/deploys), this forged status can flip the gate and cause `stack.schedule_merges` to auto-merge/auto-deploy attacker-influenced state, executed under the bot's identity.

None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) prevent this, because they validate payload *shape* and webhook *authenticity for some org*, not the binding between the authenticated repository and the specific `Commit` row being mutated.

### Impact Explanation
A payload authenticated for repository A directly mutates commit/status state belonging to stack/repository B — this is the "payload for one repository mutating another's stack, commit, task or task" category explicitly called out as Critical. Combined with `bot_login` (a configured `Shipit.user` bot identity) driving auto-merge/auto-deploy via `stack.schedule_merges`, this can cause an unauthorized deploy or merge on the victim stack triggered by an attacker who never interacted with the victim's actual repository or CI. This is repeatable against any stack whose tracked commits share a SHA with an attacker-controlled repository (most commonly via forks, which is a very common real-world topology for Shipit-managed open source or internally-forked repos).

### Likelihood Explanation
Preconditions: (1) the victim stack must have commits whose SHA is shared with a repository the attacker can emit signed webhooks from (trivial via forking — fork commits retain identical SHAs), (2) the victim stack must gate merges/deploys on a `status` context (e.g. `github-actions`) that the attacker's status event can satisfy, and (3) `bot_login` must be configured so the resulting auto-merge/auto-deploy executes without additional human approval. Attacker cost is low — forking a public repo and letting normal CI report a status, or directly controlling a status-emitting integration, is within reach of an "unprivileged" GitHub user as defined by the rules. This is repeatable per-SHA/per-stack.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to stacks whose repository matches `payload['repository']['full_name']`, using the same `stacks` helper (or equivalent repository-scoped lookup) that other handlers rely on, instead of the bare `Commit.where(sha: params.sha)` query.

### Proof of Concept
minitest plan (models/controllers test, no live GitHub):
1. Create two `Repository`/`Stack` fixtures, `victim_stack` (with `bot_login` configured, e.g. `Shipit.user` set, and requiring `github-actions` for merge) and `attacker_stack`, both containing a `Commit` with the identical `sha` value (`shared_sha`).
2. Assert-before: `victim_commit.statuses.where(context: 'github-actions').count == 0` and `victim_stack.commits.find_by(sha: shared_sha).state != 'success'`.
3. POST to `/webhooks` with `X-Github-Event: status`, a payload whose `repository.full_name` equals the attacker's repository, `sha: shared_sha`, `context: 'github-actions'`, `state: 'success'`, with `verify_signature` stubbed to return true (simulating a legitimately signed webhook from the attacker's own repo).
4. Assert-after: `victim_stack.commits.find_by(sha: shared_sha).statuses.where(context: 'github-actions').count == 1` and that `ProcessMergeRequestsJob`/`schedule_merges` was enqueued for `victim_stack`, proving the attacker's webhook (authenticated only for their own repository) mutated the victim stack's commit state and triggered the merge/deploy pipeline.
5. Compare against the intended invariant `commit.stack.repository.full_name == payload['repository']['full_name']` — show it is false yet the write still occurred, proving the equality is broken.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
