### Title
Cross-organization webhook forgery via mismatched `repository`/`organization` login vs. verified webhook secret — org authenticated ≠ entity written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which HMAC secret) to verify a webhook against based on an attacker-controlled JSON field (`repository.owner.login` or `organization.login`), but the code that subsequently *acts* on the webhook (`Repository.from_github_repo_name(payload['repository']['full_name'])` in `Handler#stacks`, or `params.organization.login` used to tag/find a `Team` in `MembershipHandler`) re-reads a *different* field from the same, unauthenticated JSON body. Nothing binds these two fields together. In Shipit's documented multi-org mode, each org has its own `webhook_secret` in `secrets.yml`. An attacker who legitimately administers one onboarded org's GitHub App (and thus knows that org's `webhook_secret`, exactly as any org admin does when they create the App per `docs/setup.md`) can sign a forged payload with their own secret while setting the `repository.full_name` / `team` / `organization` fields to point at a *different* tracked organization's stack or team.

### Finding Description
`repository_owner` is derived purely from the untrusted JSON body: [1](#0-0) 
It is used to pick the verifying secret: [2](#0-1) 
`Shipit.github(organization:)` resolves a distinct `webhook_secret` per org in multi-org mode: [3](#0-2) 
Once verified, the handler dispatch re-parses the body and derives the *acted-upon* entity from a different, equally attacker-controlled field, with no cross-check against `repository_owner`: [4](#0-3) 
`PushHandler` then syncs whatever stack that lookup resolves to, using an attacker-chosen `after` SHA: [5](#0-4) 
`MembershipHandler` is even more direct: it creates/updates a `Team` keyed by `params.team.id` and tags it with `params.organization.login`, then adds the (attacker-supplied) `member.login` to it, all without ever checking that `params.organization.login` matches the org whose secret verified the signature: [6](#0-5) 
`Team#add_member` and `Shipit.github_teams`/`User#authorized?` then treat that membership as authoritative: [7](#0-6) [8](#0-7) 

This is the same class of bug as the reported `DstSwapper._processTx` issue: a security check validates one signal (token balance delta / HMAC-verified org) while a *different*, unchecked signal (subsequent swap's source token / the `full_name`/`team`/`organization` field used downstream) drives the state change that matters, letting an attacker who is legitimate with respect to one binding (their own tokens/org) inflate or redirect trust onto another binding (someone else's liquidity/org) that was never actually verified together with it.

### Impact Explanation
This breaks the equality: `organization that authenticated (HMAC secret owner)` == `organization/repository/team that is written`. In multi-org deployments (explicitly documented and supported, see `docs/setup.md` "Using Multiple Github Applications" / `config/secrets.development.shopify.yml`), any org admin who legitimately owns a GitHub App installed against this Shipit instance can:
- Force `GithubSyncJob`/continuous-delivery-driven syncs against a *different* org's `Stack` (`PushHandler`), an unauthorized cross-repository/cross-org state change and potentially an unauthorized deploy if continuous delivery is enabled on the targeted stack.
- Add themselves (or any GitHub login) to any `Team` tracked by Shipit, including teams listed in `Shipit.github_teams`, directly escalating into the `Shipit.github_teams` authorization gate that governs who is `authorized?` to use the whole instance.

This matches the Critical/High impact categories: cross-repository writes / unauthorized deploy, and escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
Requires the attacker to be a legitimate admin of *any one* org onboarded to a multi-tenant Shipit instance — not privileged access to the victim org, no `ApiClient` token, no session, no stolen secret. This is exactly the kind of unprivileged-relative-to-victim, cross-tenant condition the multi-org feature (`docs/setup.md`) is designed to support, making the likelihood non-trivial for any shared/multi-tenant Shipit deployment.

### Recommendation
Bind the fields together: after selecting the GitHub App/secret via `repository_owner` (or `organization.login`), re-validate that every entity subsequently acted upon (`repository.full_name`'s owner, `organization.login` used by `MembershipHandler`, `team.organization`) matches that same verified organization before dispatching to handlers. Reject the webhook (422) on mismatch instead of silently trusting the second field.

### Proof of Concept
1. Onboard `attacker-org` to the Shipit instance as documented in `docs/setup.md` ("Using Multiple Github Applications"), obtaining its own `webhook_secret`.
2. POST to `/webhooks` with `X-Github-Event: membership`, body:
```json
{
  "action": "added",
  "team": {"id": <victim_team_github_id>, "name": "Victim Team", "slug": "victim-team", "url": "https://api.github.com/..."},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-github-login"}
}
```
signed with `HMAC-SHA1(attacker-org_webhook_secret, raw_body)` as `X-Hub-Signature`.
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and verifies successfully with the attacker's own secret.
4. `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`) finds/creates the victim's `Team` by `team.id` and calls `team.add_member(attacker_user)`, granting the attacker membership in a team it never authenticated against — escalating into `Shipit.github_teams` authorization if that team is configured there.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first

  end
