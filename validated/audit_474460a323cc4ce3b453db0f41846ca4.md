## Finding

### Title
Documented oscript pattern for forwarding `trigger.data` as payment payload enables unrestricted draining of AA funds - (File: `test/samples/sending_prepared_objects_through_trigger_data.oscript`)

### Summary
The ocore AA documentation/reference samples teach AA authors a pattern in which the entire `outputs` array or `payment` payload of an AA response message is built directly from `trigger.data` — the JSON payload supplied by whoever posts the triggering unit — with no restriction tying the recipient address or amount to the actual sender or actual amount deposited. This mirrors the CWE-1336 template-injection documentation-pattern bug class in the referenced Airflow advisory: an official example shows an unsanitized, attacker-controlled value flowing straight into a sensitive execution context (there: `bash_command`; here: a `payment` message's `outputs`), and any AA author who copies the pattern literally exposes their AA to unauthorized fund transfers triggered by any address.

### Finding Description
`trigger.data` is populated directly from the first `data`-app message payload of the *incoming* unit, with no validation of its structure or ownership relationship to the amount actually sent to the AA: [1](#0-0) 

`trigger.data` is exposed to oscript templates verbatim via the `trigger.data` operator, returned as a `wrappedObject` clone of whatever the trigger's data message contained: [2](#0-1) 

The documented sample `sending_prepared_objects_through_trigger_data.oscript` — surfaced in the test suite as a canonical usage pattern — shows an AA whose `payment` message payload is composed by inlining `trigger.data.output` (a single output element) or even the entire `trigger.data.payment` object as the message's `payload`: [3](#0-2) 

During template expansion (`replace` in `aa_composer.js`), any string value matching `{...}` is evaluated as a formula with `bObjectResultAllowed: true`, meaning the evaluated `trigger.data` object (attacker-controlled) is substituted wholesale into the message/payload tree with no additional sanity check that the resulting object's `address`/`amount` correspond to `trigger.address` or the amount actually received: [4](#0-3) 

`aa_validation.js`'s static validator only confirms an output *string* looks like a syntactically valid formula — it does not, and cannot, constrain what object the formula will evaluate to at trigger time: [5](#0-4) 

The only runtime guard before the AA sends its composed unit is generic well-formedness checking — valid address format, non-negative integer amount, and no unknown fields — but nothing that requires the output address to equal `trigger.address` or the amount to be bounded by what the trigger actually paid in: [6](#0-5) 

Consequently, if an AA author follows the documented pattern literally (as the sample encourages), any party can post a trivial trigger unit whose `data` message contains `{payment: {asset: "base", outputs: [{address: "<attacker_address>", amount: <AA_balance>}]}}`, and the AA will faithfully compose and send that exact output from its own balance to the attacker-chosen address, as long as the AA holds sufficient balance in that asset.

### Impact Explanation
Any AA built on the documented pattern of directly embedding `trigger.data` into `payment` outputs, without restricting the destination address to `trigger.address` or the amount to the value actually deposited by the trigger, allows an unprivileged, arbitrary trigger sender to redirect the AA's entire balance in any asset to an address of their choosing. This is a concrete unauthorized spending / fund-loss vulnerability for the AA and its legitimate users, matching the "unauthorized spending, AA fund loss" acceptance criterion.

### Likelihood Explanation
This requires an AA author to have modeled their contract on the pattern shown in the official sample (`sending_prepared_objects_through_trigger_data.oscript`), which is exactly the scenario the referenced Airflow advisory describes: developers copy an insecure canonical example verbatim into production. Because the sample is presented without an explicit warning that the address/amount must be constrained, and because oscript's data-templating mechanism performs no implicit sanitization of `trigger.data` before substitution, any AA following this pattern with real funds is directly exploitable by any address capable of posting a unit to the AA.

### Recommendation
Update the documentation/sample to add an explicit warning that any `trigger.data`-derived object used to construct `payment` outputs must be constrained (e.g., output address forced to `trigger.address`, amount capped by `trigger.output[[asset=...]]`) before being embedded in a `payment` message payload, or provide/require an oscript-level primitive that automatically restricts output composition. Consider also adding an aa_validation.js static check that flags/rejects AA definitions where an entire `outputs` array or `payment.payload` is a bare formula sourced from `trigger.data`/`params` without any accompanying `if`/`init` logic that visibly bounds address or amount.

### Proof of Concept
1. Deploy the AA definition exactly as in `test/samples/sending_prepared_objects_through_trigger_data.oscript`, funded with, say, 10,000,000 bytes.
2. As an arbitrary user (not the AA owner), post a unit with a `data` message payload:
```json
{ "payment": { "asset": "base", "outputs": [ { "address": "<ATTACKER_ADDRESS>", "amount": 10000000 } ] } }
```
3. The AA's `handleTrigger`/`replace` logic (`aa_composer.js:658-695`) evaluates `payload: "{trigger.data.payment}"`, substituting the attacker-supplied object verbatim as the payment payload.
4. `sendUnit`'s generic checks (`aa_composer.js:1259-1278`) pass because the address is a syntactically valid address and the amount is a non-negative integer — with no requirement that the address equal `trigger.address`.
5. The AA composes and posts a unit draining its balance to `<ATTACKER_ADDRESS>`.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
