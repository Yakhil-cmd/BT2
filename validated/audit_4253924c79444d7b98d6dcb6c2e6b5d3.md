Based on my research, I found a directly analogous bug-class instance in the `split` oscript operator used in AA (Autonomous Agent) formula evaluation.

### Title
Unbounded array allocation via `split()` in AA formulas causes disproportionate CPU/memory cost during mandatory node-wide AA validation - (File: formula/evaluation.js)

### Summary
The oscript `split` function, reachable by any user who triggers an Autonomous Agent whose formula calls `split()` on attacker-influenced data (e.g. `trigger.data` fields), calls JavaScript's native `String.prototype.split()` with no limit on the number of resulting array elements when the `limit` argument is omitted, and applies only a fixed, size-independent complexity/op-count charge.

### Finding Description
In `formula/evaluation.js`, the `split` case evaluates the separator and target string and, when no `limit_expr` is supplied, directly returns `new wrappedObject(res.split(separator))` with no post-condition check on the resulting array's size: [1](#0-0) 
This is unlike the sibling `join`/`replace` operations in the same switch statement, which explicitly bound the *output string* length against `constants.MAX_AA_STRING_LENGTH` before returning: [2](#0-1) [3](#0-2) 

Formula evaluation charges a fixed `count_ops`/complexity increment per AST node evaluated, not proportional to the size of the string being processed: [4](#0-3) 
So an attacker-controlled string containing many separator occurrences (analogous to the many-comma `Access-Control-Request-Headers` value in the `rs/cors` advisory) causes `split()` to allocate a large array of substrings while the formula engine only accounts for it as a single, cheap operation — exactly the "prohibitive heap allocations relative to declared cost" pattern from CVE-2025-47908.

Because AA trigger evaluation (including `split()`/`join()` calls in bounce/response formulas) is **mandatory, deterministic work every full node performs** when validating a unit that triggers the AA (unlike client-side or peer-only processing), this allows an unprivileged AA trigger sender to impose disproportionate CPU/memory cost on every validating node for a single posted unit.

### Impact Explanation
Every full node must re-execute the AA's formula, including any `split()` calls, while validating the triggering unit. If the split result size is unbounded and cheaply chargeable, an attacker can force expensive array construction on all nodes for the same posted unit, disproportionate to the complexity/ops budget enforced by `constants.MAX_COMPLEXITY`/`MAX_OPS`. This can degrade the performance of AA processing network-wide, delaying validation/stabilization of units, which is one of the accepted impacts (network struggling to confirm/validate new units).

### Likelihood Explanation
Any address can define an AA using `split()` with the `trigger.data`/`trigger.output` string as input, and any unprivileged user can send a trigger unit with a large string payload containing many separator characters. The formula parser/evaluator caches and validates formulas at AA-definition time, but the *validation* phase (`formula/validation.js`, case `'split'`) also does not bound result size — it only evaluates sub-expressions for correctness, not the runtime cost of a large split: [5](#0-4) 
This makes the bug reachable at both AA-definition validation time and every subsequent trigger-execution time.

### Recommendation
Bound the number of elements/array size produced by `split()` (and similarly check the size of the resulting `wrappedObject`), similar to how `join`/`replace` already bound their output length against `constants.MAX_AA_STRING_LENGTH`, e.g. reject or cap when `res.split(separator).length` exceeds a sane maximum, and factor result size into `count_ops`/complexity accounting so the cost is proportional to work performed.

### Proof of Concept
1. Deploy an AA whose formula includes something like: `split(trigger.data.s, ",")` and stores/uses the result (e.g. via `foreach`/`array_length`) in a response.
2. Send a trigger unit whose `data.s` field is a string near the maximum allowed AA string/data length, filled almost entirely with the separator character (e.g. thousands of commas).
3. Every node validating this trigger unit executes `split()`, producing a correspondingly large array while `formula/validation.js`/`formula/evaluation.js` charge only a fixed op cost, disproportionate to the actual heap allocation incurred — reproducing the amplification pattern described in GHSA-mh55-gqvf-xfwm/CVE-2025-47908.

Note: I was unable to confirm within the available tool budget the exact maximum size of `trigger.data` string fields (`constants.MAX_AA_STRING_LENGTH` and related payload size constants), which bounds how large the amplification can practically get; a Devin session with full repo access could verify the exact numeric limits in `constants.js` to quantify the worst-case allocation size.
