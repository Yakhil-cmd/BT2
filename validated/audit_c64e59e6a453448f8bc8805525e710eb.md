### Title
Cross-organization webhook forgery via owner/full_name binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and therefore the HMAC secret) used to authenticate an inbound webhook based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), while the actual event handlers resolve the target `Repository`/`Stack` using a *different* JSON field: `payload.dig('repository', 'full_name')`. Because HMAC verification only proves "this body was signed by whoever holds the secret for the organization named in `repository.owner.login`," it never proves that `repository.full_name` belongs to that same organization.

### Finding Description
`WebhooksController#verify_signature` derives the org used to pick the verifying secret from the payload itself: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` on `GitHubApp` just HMAC-verifies the raw body against the secret configured for whichever organization was selected above: [3](#0-2) 

Once verified, `WebhooksController#create` dispatches the parsed params to handlers without re-checking that the org used for verification matches the repository the handler will act on: [4](#0-3) 

`Handlers::Handler#stacks`/`#repository_name`, used by every handler (e.g. `PushHandler`), resolves the target repository from a *different* field, `repository.full_name`: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` simply splits `owner/name` from that string and looks it up directly, with no cross-check against `repository.owner.login`: [7](#0-6) 

**Binding broken:** *organization that authenticated* (`repository.owner.login`, used to pick the HMAC secret) *≠ repository that is written* (`repository.full_name`, used by the handler to select the `Stack`). Shipit supports multi-tenant deployments where each customer organization has its own GitHub App and webhook secret (documented in `docs/setup.md`, "Using Multiple GitHub Applications"). Any organization onboarded this way can compute a valid signature for a payload it fully controls (since the HMAC covers the entire raw body, including a `repository.full_name` value that names a *different* organization's repository), because the verifying org is selected from a value the attacker also controls.

### Impact Explanation
An org admin who is legitimately provisioned with their own GitHub App/webhook secret on a shared Shipit instance can forge a `push` webhook where `repository.owner.login` = their own org (so their own secret verifies the signature) but `repository.full_name` = `"other-org/victim-repo"`. This causes `PushHandler#process` to enqueue a `GithubSyncJob` for the victim stack with an attacker-chosen `expected_head_sha`, and would similarly let the attacker fabricate `status`, `check_suite`, `pull_request`, or `membership` events against a repository/stack outside the organization whose secret authenticated the request. This is a cross-repository/cross-organization write against Shipit's own trust boundary between tenants, matching the Critical "cross-repository writes" impact criterion.

### Likelihood Explanation
Requires the attacker to be an administrator of *any one* organization onboarded to a shared, multi-tenant Shipit deployment (a documented, supported configuration), and to know only their own org's webhook secret — not the victim org's secret, not a Shipit session, and not privileged Shipit access. The `WebhooksController` endpoint is intentionally unauthenticated (CSRF is skipped) so GitHub can reach it, and no code path cross-validates `repository.owner.login` against `repository.full_name` before dispatching to handlers.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handlers::Handler`, require that the organization portion of `repository.full_name` (and `organization.login` if present) matches `repository.owner.login` before processing; reject the webhook (422) on mismatch. Alternatively, always resolve the target `Repository` using the same identifier that was used to select the verifying secret.

### Proof of Concept
1. Shipit instance configured for two tenants, `orgA` and `orgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md` multi-org setup).
2. Attacker controls `orgA`'s GitHub App and therefore knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "orgB/victim-repo",
    "owner": { "login": "orgA" }
  }
}
```
4. Attacker signs the raw body with `orgA`'s `webhook_secret` and sends it as `X-Hub-Signature` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s `GitHubApp`, and the signature verifies successfully.
6. `PushHandler#process` resolves the target repository via `repository.full_name` = `"orgB/victim-repo"`, finds `orgB`'s `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — acting on `orgB`'s stack despite the request only being authenticated as `orgA`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
