### Title
Session Fixation via Missing Session Reset in GitHub OAuth Callback - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`Shipit::GithubAuthenticationController#callback` binds a freshly authenticated GitHub identity to the *existing* session without first rotating the session identifier, unlike `#logout` which explicitly calls `reset_session`. This breaks the equality that should hold between "the session the browser presents" and "the session the authenticated `User` is bound into," allowing an unprivileged attacker to fix a session prior to authentication and later have that same session upgraded to an authenticated victim's identity.

### Finding Description
`callback` is the OmniAuth GitHub App callback action mounted (per `config/routes.rb`) unauthenticated at `/github/auth/github/callback`: [1](#0-0) 

It writes the resulting `user.id` directly into `session[:user_id]` and sets `session[:authenticated] = true`, but never calls `reset_session` beforehand: [2](#0-1) 

Contrast this with `logout`, which does call `reset_session`: [3](#0-2) 

and with `Authentication#force_github_authentication`, which itself calls `reset_session` when a stale/legacy token is detected before redirecting to re-authenticate: [4](#0-3) 

The binding that should be enforced is: *the session identifier bound to `session[:user_id]` after `callback` == a session identifier that was not known/controllable by anyone other than the just-authenticated browser*. Because `callback` reuses whatever session ID/session hash was already active when the OAuth flow began (i.e., it upgrades the pre-existing session in place rather than issuing a new one), an attacker who can pre-establish or predict a victim's session before the OAuth dance completes can have that pre-established session promoted to a fully authenticated session for the victim's GitHub identity. This is the "GitHub identity vs. `User` bound to the session" binding called out in scope — here it is broken in the direction of the session identity persisting across an authentication-state transition instead of being rotated.

### Impact Explanation
If an attacker can fix or otherwise reuse the session state active before the callback executes (e.g., via a session identifier that is not rotated on privilege change and is otherwise obtainable/settable by the attacker), the attacker's browser session becomes authenticated as the victim once the victim completes the GitHub OAuth handshake. That grants the attacker `current_user`'s Shipit access, including the ability to trigger deploys/rollbacks and any actions gated purely on `session[:user_id]`/`current_user.authorized?`, i.e., an unauthorized deploy/rollback capability equivalent to the victim's. This matches the enumerated High-impact category "session fixation / forced OAuth completion."

### Likelihood Explanation
The default Rails cookie-based session store partially mitigates classic session-fixation (session data is stored client-side and signed), but the engine does not itself enforce session ID rotation on login as defense-in-depth, and does not prevent forced OAuth completion followed by session reuse in deployments that use a server-side session store (e.g., Redis-backed `ActionDispatch::Session::CacheStore` or similar), which Shipit explicitly supports given its Redis dependency (`Shipit.redis_url`). Because the engine's own code is the only place this rotation could be enforced, and it deliberately omits it in the one action that transitions from anonymous to authenticated, the flaw is squarely in-scope and reachable by any unauthenticated actor who can reach the callback endpoint and coerce or ride along on a victim's OAuth completion.

### Recommendation
Call `reset_session` in `Shipit::GithubAuthenticationController#callback` before assigning `session[:user_id]`/`session[:authenticated]`, mirroring the pattern already used in `logout` and in `Authentication#force_github_authentication`, so that a new session identifier is always issued at the point authentication state changes.

### Proof of Concept
1. Attacker visits the Shipit host and notes/fixes the session (e.g., session cookie/session key) prior to any login, or otherwise arranges for a victim's browser to carry a session state known to the attacker (e.g., via a session store where the session identifier is not entropy-bound to the cookie signing key, or via any mechanism that lets the attacker set the victim's session before login).
2. Attacker lures the victim to `/github/auth/github` and the victim completes the GitHub OAuth authorization.
3. `GithubAuthenticationController#callback` fires and sets `session[:user_id] = sign_in_github(auth)` on the *existing* (attacker-known) session, without rotating it: [2](#0-1) 
4. Attacker, sharing the same session identifier, is now recognized as the victim by `Authentication#current_user`: [5](#0-4) 
5. Attacker performs privileged actions (deploys/rollbacks) as the victim.

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```
