### Title
Uncaught exception via unauthenticated-length `throw` inside async DB callback in address-definition `'definition template'` evaluation causes full-node crash (Denial of Service) - (File: `definition.js`)

### Summary
`definition.js`'s `validateDefinition`/`validateAuthentifiers` evaluator supports a `'definition template'` operator inside an address (or asset) definition. When this operator is evaluated, it runs an SQL query and, in the query's asynchronous callback, does `throw Error("not 1 template")` if the referenced template unit is not found (or is ambiguous) rather than passing an error back through the `cb2`/`handleResult` callback chain used everywhere else in the same function.

### Finding Description
In the `evaluate()` closure of `validateAuthentifiers` (and the corresponding `getFilterError`/evaluate path used from `validateDefinition`), the `'definition template'` case is: [1](#0-0) 
```
case 'definition template':
    var unit = args[0];
    var params = args[1];
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            var template = rows[0].payload;
            var arrTemplate = JSON.parse(template);
            var arrFilledTemplate = replaceInTemplate(arrTemplate, params);
            evaluate(arrFilledTemplate, path, cb2);
        }
    );
    break;
```
Every other branch of this evaluator reports errors by calling `cb2(false)`/`handleResult(err)`, which are properly propagated back up through `validateAuthor` → `validateAuthors` → `validate()` callbacks (`ifUnitError`/`ifJointError`), i.e. rejecting the unit gracefully. This branch instead throws synchronously *inside the asynchronous `conn.query` callback*. Because the SQL driver invokes this callback on a different tick/stack than the original `evaluate()`/`validate()` call, the thrown exception is not caught by any surrounding `try { } catch` in `validation.js` or `network.js`'s `handleJoint`. It becomes an uncaught exception.

`network.js` registers a global handler that deliberately re-throws to terminate the process on any uncaught exception: [2](#0-1) 
```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	console.error('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```
So any unit that defines (or references, via signing) an address whose definition contains `['definition template', [some_unit, {...}]]` where `some_unit` is not exactly one stable `definition_template` message will crash the receiving/validating node process the moment `validateAuthentifiers`/`validateDefinition` evaluates that op — this is exactly analogous to CVE-2021-46044's pattern: an attacker-controlled, malformed input reaches a code path that dereferences/consumes unchecked data and improperly terminates the process (there: pointer dereference panic; here: unguarded `throw` inside an async callback outside all protective try/catch and error-callback plumbing), causing Denial of Service.

The main synchronous `validate()` entry point in `validation.js` wraps the top-level unit-hash calculation in try/catch, but that protection does not extend into the deeply nested asynchronous chain that eventually reaches this `conn.query` callback: [3](#0-2) 

### Impact Explanation
Any unprivileged party who can get a unit accepted for validation — a normal unit poster defining/using an address whose definition contains a bogus `'definition template'` reference, or an AA trigger author whose definition or trigger data is evaluated against such a definition — can crash any full node (light-vendor/hub or witness) that validates the unit. Since `process.on('uncaughtException')` explicitly re-throws to kill the process, this is a reliable full-node crash: "a network unable to confirm new units" if repeated against witnesses/hubs, satisfying the required impact bar (node disagreement/availability loss due to crash, not merely resource exhaustion).

### Likelihood Explanation
High: the attack requires only composing an ordinary unit whose author uses a custom address definition containing the `'definition template'` operator pointing at a non-existent or non-unique template unit, then getting any single message signed/posted referencing that address — no special privileges, no witness/hub cooperation, and no need to control network peers. `'definition template'` is a standard, publicly documented oscript definition primitive, so constructing the malicious definition is straightforward for any unit poster.

### Recommendation
Replace the `throw Error("not 1 template")` inside the `conn.query` callback with proper asynchronous error propagation, e.g. `return cb2(false)` (or `handleResult("not 1 template")` in the `validateDefinition` variant), consistent with every other branch of the same evaluator, so malformed/ambiguous template references are treated as ordinary unit-validation failures instead of crashing the process. Add defensive `try/catch` around `JSON.parse(template)` and `replaceInTemplate` in this callback as well, since those can also throw inside the same unprotected async context.

### Proof of Concept
1. Compose an address whose definition is `["definition template", ["<unit_hash_of_a_unit_that_never_posted_a_definition_template_message>", {}]]` and make it the definition of a brand-new address (or an inline `definition` in a unit's author).
2. Post (or have an AA-triggering counterparty post) a unit signed by/using that address so that `validateAuthor` → `Definition.validateAuthentifiers` → `evaluate()` is invoked on this definition during `validation.validate()`.
3. When the evaluator reaches the `'definition template'` case, the `conn.query` callback executes with `rows.length === 0`, triggering `throw Error("not 1 template")` inside the async callback.
4. The exception is uncaught by any surrounding try/catch, is captured by `process.on('uncaughtException')` in `network.js`, which explicitly re-throws, crashing the Node.js process on every full node/witness/hub that attempts to validate this unit.
