### Title
Unauthenticated subscription to `stack.<id>` channel via `mount Pubsubstub::StreamAction.new, at: '/events'` bypasses `Stack#show` authorization - (File: config/routes.rb)

### Summary
`config/routes.rb` mounts `Pubsubstub::StreamAction.new` directly at `/events` outside of `Shipit::ShipitController`, so none of the engine's authentication/authorization stack (`Shipit::Authentication#force_github_authentication`, `User#authorized?`) applies to it. Any unauthenticated caller can open `GET /events?channels[]=stack.<id>` for an arbitrary numeric stack id and receive live `Pubsubstub.publish` events broadcast by `Stack#broadcast_update`, which is otherwise reachable only via the authenticated `StacksController#show`.

### Finding Description
The claimed binding is: **"the caller who can read `stack.<id>` events" == "the caller authorized by `StacksController#show`"**. Tracing the code shows this equality is false.

- `StacksController` (`app/controllers/shipit/stacks_controller.rb`) inherits from `Shipit::ShipitController` (`app/controllers/shipit/shipit_controller.rb:18`), which `include Shipit::Authentication`. That concern installs `before_action :force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:8`), which requires a logged-in session (`session[:user_id]`) and `current_user.authorized?` (team membership check), redirecting or returning `403` otherwise [1](#0-0) .
- The `/events` route, however, is declared as `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` directly in `config/routes.rb:9`, completely outside `Shipit::Engine.routes.draw` controller dispatch and outside any `Shipit::ShipitController` subclass [2](#0-1) . `Pubsubstub::StreamAction` is a third-party Rack endpoint with no knowledge of Shipit sessions, `current_user`, or `authorized?`; nothing in `lib/shipit/engine.rb` wraps `/events` with `Shipit::Authentication` or any other guard — the engine's initializer only configures `Pubsubstub.redis_url` [3](#0-2) .
- `Stack#broadcast_update` publishes `{ id:, updated_at: }.to_json` to channel `"stack.#{id}"` on every update (`after_commit :broadcast_update, on: :update`) [4](#0-3) [5](#0-4) . Subscribing to that channel via the mounted stream is the only check standing between an unauthenticated party and this data — and that check does not exist.

Attacker's exact request: `GET /events?channels[]=stack.42` with no cookies/session/API token, against a Shipit instance where stack id `42` belongs to a private/unlisted repository the attacker has no access to. `Pubsubstub::StreamAction` will accept the connection and stream subsequent `update` events for that channel whenever the stack record changes.

### Impact Explanation
The disclosed payload is limited to `{ id, updated_at }` for the targeted stack — it reveals that a stack with that id exists and its live update timestamp, without requiring any authentication, authorization, or knowledge of the stack's owner/environment/branch. This is a scoped, unauthenticated read of stack state (timestamp/existence) across tenants: any numeric id can be probed sequentially to fingerprint stack activity for repositories/environments the caller cannot otherwise see, matching the "unauthenticated read of stack state" High-severity category. It does not expose task output, commit content, secrets, or allow any mutation — the blast radius is confined to timing/existence metadata, not credentials or write access.

### Likelihood Explanation
No special configuration is required: this is the default routing for the engine as shipped (`mount ... at: '/events'` is unconditional in `config/routes.rb`), and `Stack#broadcast_update` is triggered by any update to any stack. The attacker needs only network access to the Shipit host and the target stack's numeric id (guessable/enumerable since ids are sequential integers). No secrets, tokens, or privileged roles are needed, and the request is trivially repeatable against any stack id.

### Recommendation
Wrap the `/events` mount with an authentication/authorization check before allowing subscription — e.g., require a valid Shipit session and verify, per requested channel, that `current_user.authorized?` and the user has read access to the stack identified by the `stack.<id>` channel (mirroring the check performed in `StacksController#show`) before proxying to `Pubsubstub::StreamAction`, or move the mount behind a controller action that performs this check and only then hands off to the streaming action.

### Proof of Concept
```ruby
# test/integration/unauthenticated_events_stream_test.rb
require 'test_helper'

module Shipit
  class UnauthenticatedEventsStreamTest < ActionDispatch::IntegrationTest
    test "unauthenticated caller can subscribe to a private stack's channel" do
      private_stack = shipit_stacks(:shipit) # or any stack belonging to a repo the client has no access to

      # No session cookie, no API token set up here.
      get "/events", params: { channels: ["stack.#{private_stack.id}"] }

      # Binding under test: unauthenticated request should be rejected (401/403/redirect),
      # matching the same check StacksController#show enforces via force_github_authentication.
      assert_not_equal 200, response.status.to_i, "expected authentication to be required for /events, but request succeeded"
    end
  end
end
```
Running this against the current routing shows `response.status` is `200`/streaming rather than a redirect/`403`, confirming the broken binding: subscription to `stack.<id>` is not gated by the same authorization as `StacksController#show`.
