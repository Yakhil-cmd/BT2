### Title
Unverified "creator" principal in `initialize_with_permission` allows attacker-controlled routing/freezing of pool creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` binds the pool's permanent `pool_creator` field to an attacker-supplied account that is never validated as a signer or otherwise proven to be the actual party authorizing pool creation, mirroring the CVE-2025-0237 root cause of trusting a supplied "principal" instead of verifying the actual sending/authorizing party.

### Finding Description
In `InitializeWithPermission`, `creator` is declared as a plain `UncheckedAccount` with only a doc comment (`/// CHECK: creator of pool`) and no signer requirement or ownership/relationship constraint tying it to `payer`: [1](#0-0) 

This is in stark contrast to the regular, non-permissioned `initialize` instruction, where the equivalent role is a required `Signer`: [2](#0-1) 

Despite `creator` never being required to sign or otherwise prove authorization, its raw pubkey is written directly into the pool's permanent on-chain state as `pool_creator` via `pool_state.initialize(...)`: [3](#0-2) [4](#0-3) 

`pool_creator` is subsequently the sole address entitled to accrued `creator_fees_token_0`/`creator_fees_token_1` in `collect_creator_fee` (which requires `creator` to be a signer matching `pool_state.pool_creator`) and is also the fixed recipient in `collect_creator_fee_permissionless` (any payer can trigger the transfer, but funds always land in an ATA owned by whatever `pool_creator` value was recorded): [5](#0-4) [6](#0-5) 

Because `payer` (who only needs a valid `Permission` PDA to invoke `initialize_with_permission`) fully controls the `creator` account value with no cross-check, they can set `pool_creator` to any arbitrary pubkey — including one for which no private key exists (e.g. `System Program::ID`, a mint address, or any other keyless/unreachable pubkey).

### Impact Explanation
Once the pool is created with an unreachable `pool_creator`:
- `collect_creator_fee` can never succeed because no one can produce a valid signature for that pubkey (`address = pool_state.load()?.pool_creator` constraint on the `Signer`).
- `collect_creator_fee_permissionless` will still execute, but the collected `creator_fees_token_0`/`creator_fees_token_1` are transferred into an associated token account whose authority is the unreachable pubkey, permanently locking those funds since no key exists to move them further.

This results in permanent freezing of accumulated creator-fee funds that are meant to be claimable value for the pool's designated creator, satisfying the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
Any account holding a `Permission` PDA (an allowed, non-admin actor explicitly in scope per the rules — `initialize_with_permission` is a listed unprivileged/permissioned entry point) can trigger this in a single transaction by simply passing an arbitrary `creator` account. No collusion, special timing, or privileged signer is required beyond the standard permission gate on the `payer`, making this straightforward and reliably reproducible.

### Recommendation
Require `creator` to either be a `Signer` (as in `initialize.rs`) or explicitly constrain it to equal `payer.key()` (or another already-authenticated signer) so that the recorded `pool_creator` always corresponds to a principal that actually authorized the pool's creation and can subsequently reclaim fees.

### Proof of Concept
1. Attacker (or any permissioned payer) obtains/possesses a valid `Permission` PDA for their own `payer` key (as required to call `initialize_with_permission`).
2. Attacker calls `initialize_with_permission`, supplying `payer` = their own signer, but sets the `creator` account field to `system_program::ID` (or any other pubkey with no known private key).
3. The instruction succeeds; `pool_state.pool_creator` is permanently set to `system_program::ID` per `PoolState::initialize` at [7](#0-6) .
4. As trading occurs, `creator_fees_token_0`/`creator_fees_token_1` accrue in the pool per the fee split logic in swaps.
5. Any call to `collect_creator_fee` fails permanently (no signer can match `pool_creator`); calls to `collect_creator_fee_permissionless` succeed but deposit the fees into an ATA owned by `system_program::ID`, which is permanently unrecoverable — freezing those funds forever.
