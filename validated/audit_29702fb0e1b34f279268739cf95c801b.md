### Title
Uncaught exception (DoS) via unvalidated address/c-hash length in `isChashValid` - (File: chash.js)

### Summary
`chash.isChashValid()` throws an unhandled `Error` when the input string's length is not exactly 32 or 48 characters, instead of returning `false`. This function is the core c-hash/checksum validator used by `validation_utils.isValidAddress()`, which in turn gates address fields throughout unit, AA-definition, oscript, and device-message validation. A crafted address string of an unexpected length reaching this code path can throw synchronously and crash the validating process, mirroring the CVE-2019-10050 pattern where a parser fails to validate a length before proceeding and a subsequent operation faults on the malformed remainder.

### Finding Description
`isChashValid` starts with: [1](#0-0) 
```
function isChashValid(encoded){
	var encoded_len = encoded.length;
	if (encoded_len !== 32 && encoded_len !== 48) // 160/5 = 32, 288/6 = 48
		throw Error("wrong encoded length: "+encoded_len);
```
Only the base32/base64 decode step that follows is wrapped in `try/catch`: [2](#0-1) 
The length check itself is a bare `throw`, not caught locally. This function is called from `validation_utils.js` (the sole call site found) as the implementation behind `isValidAddress`, which is used pervasively: in `definition.js` for address/definition validation, in `aa_validation.js` for AA definition/message validation, in `formula/evaluation.js`/`formula/validation.js` for the `is_valid_address` oscript operator, and in device/wallet code for correspondent/payment addresses.

This is directly analogous to the Suricata bug class: a length/bounds condition is checked, but instead of the code gracefully rejecting malformed input, an unexpected condition (here, a length outside the two accepted values) causes an uncaught fault that propagates up the call stack. In Suricata this manifested as a memory read past the buffer; in this Node.js codebase the equivalent fault is an uncaught JavaScript exception, which — if not caught by an enclosing `try/catch` in every calling code path — terminates the Node process (unhandled exception → process crash), since Node does not recover from synchronous uncaught exceptions the way it does from rejected promises.

### Impact Explanation
Address strings originate from attacker-controlled data: unit `authors[].address`, `messages[].payload.outputs[].address`, address-definition `['address', addr]` opcodes, AA trigger/definition data, and oscript `is_valid_address(expr)` calls evaluated during AA execution. Any of these can carry a string of a length other than 32 or 48 characters. If the code path that calls `isValidAddress` (and thus `isChashValid`) is not wrapped in a try/catch at that specific call site, a single malformed unit or AA trigger causes an uncaught exception that crashes the node process performing validation. Because unit/AA validation is performed by every full node (and often light wallets) processing new units, a crafted unit broadcast to the network could crash multiple validating nodes simultaneously — a network-wide denial of service that prevents confirmation of new units, which matches the accepted impact criteria (network unable to confirm new units) without requiring any privileged access; only the ability to post a unit or AA trigger is needed.

### Likelihood Explanation
Likelihood is high for any code path where `isValidAddress`/`isChashValid` is invoked without a pre-existing length check on the input and without a surrounding try/catch. Constructing a string with a length other than 32 or 48 is trivial for an attacker (e.g., using a 33-character address field in an output, or a definition template argument). The main uncertainty is whether every call site of `isValidAddress` used during consensus-critical validation is wrapped in try/catch; this could not be exhaustively confirmed for `validation_utils.js` in the available index, so likelihood should be considered high but not fully proven without inspecting every caller.

### Recommendation
- In `chash.js`, change `isChashValid` to return `false` (not throw) when `encoded.length` is not 32 or 48, consistent with its boolean-returning contract.
- Alternatively/additionally, ensure `isValidAddress` in `validation_utils.js` performs a length/type check before calling `isChashValid`, and/or wrap the call in try/catch so malformed input always yields `false` rather than propagating an exception.
- Audit all call sites of `isChashValid`/`isValidAddress` reachable from unit, AA, and device-message validation to confirm none rely on the function never throwing.

### Proof of Concept
```js
const chash = require('./chash.js');
// Any address-like string whose length is not 32 (base32) or 48 (base64) chars
try {
    chash.isChashValid('SHORT_ADDRESS_STRING_23CHARS'); // length = 28
} catch (e) {
    console.log('Uncaught exception:', e.message); // "wrong encoded length: 28"
}
```
Embedding such a string in an attacker-controlled field that flows into `isValidAddress` (e.g., an output `address`, an `['address', ...]` definition opcode, or an oscript `is_valid_address(...)` argument inside an AA trigger/definition) and posting the unit/trigger reaches this throw during validation. If the specific call site lacks a try/catch, the validating node process crashes.

**Note on verification limits:** I was unable to retrieve the full source of `validation_utils.js` (definition of `isValidAddress`) and every consumer of `isChashValid` within the tool budget to conclusively confirm the absence of a protective try/catch at each call site. This should be verified directly in the repository (a Devin session with full file access would be needed) before treating this as a confirmed, unconditionally exploitable crash.
