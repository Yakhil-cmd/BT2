## Title
Pre-publish exechook is fired asynchronously and does not gate `publishSymlink`, allowing new (possibly malicious) content to be published before/without the gating hook completing or succeeding - (File: `main.go`)

### Summary
The reported bug describes `zkPayCallback` being invoked in a way that lets the caller supply just enough gas to make the callback fail while the surrounding critical logic (`settleQueryPayment`) still completes, because the "gate" (the callback) is not guaranteed to run to completion before the security-relevant action proceeds. `git-sync` has a structurally analogous decoupling between its `--pre-publish-exechook-command` (documented as running "before publishing the symlink" so it can validate/gate a new sync) and the actual symlink publish step, which does not wait for that hook to finish or succeed.

### Finding Description
In `main.go`, the `syncHooks.beforePublish` closure is wired to `prePubExechookRunner.Send(hash)` and unconditionally returns `nil`: [1](#0-0) 

`HookRunner.Send` is explicitly non-blocking - it stores the hash and does a non-blocking channel write, so the caller (the main sync loop) never waits for the underlying `Exechook.Do` to actually execute or finish: [2](#0-1) [3](#0-2) 

Immediately after calling `beforePublish` (which just enqueues the hook and returns success), `SyncRepo` proceeds to call `git.publishSymlink(newWorktree)` without any synchronization on the hook's actual outcome: [4](#0-3) 

The only place the code ever actually waits on hook completion is in `--one-time` mode via `WaitForCompletion()`, which blocks on `oneTimeResult`, a channel that is only initialized when `oneTime` is true: [5](#0-4) [6](#0-5) 

In the default, continuous-sync mode (no `--one-time`), there is no such wait at all - the symlink is published to the new worktree unconditionally, while the pre-publish-exechook command (which the README documents as "to be executed ... before publishing the symlink") may still be running, queued behind a backoff retry of a previous hash, or may fail outright: [7](#0-6) 

This mirrors the report's core flaw: a gating check (`zkPayCallback` / pre-publish-exechook) is invoked in a way where the surrounding control flow does not actually depend on its success or completion, letting the critical downstream action (`settleQueryPayment` / `publishSymlink`) proceed regardless.

### Impact Explanation
Operators who rely on `--pre-publish-exechook-command` to perform pre-publish validation (e.g., signature verification, content/security scanning, policy checks) on synced content, per the documented semantics of running "before publishing the symlink", will have new content published via the `--link` symlink even if that validation hook fails or has not finished executing. This can result in consumers of the synced directory (e.g., other containers reading from the `--link` path) observing unvalidated or attacker-controlled content that the operator intended to gate. This falls under "publishing wrong or partial content."

### Likelihood Explanation
This triggers on every sync in continuous (non `--one-time`) mode whenever `--pre-publish-exechook-command` is configured, since the async `Send`/publish race is unconditional and does not require any special attacker action beyond causing a new hash to sync (e.g., via a normal or malicious push to the tracked ref). No misconfiguration or privileged access is needed - it is inherent to how `beforePublish` is wired in the default run loop.

### Recommendation
Make `syncHooks.beforePublish` block on the pre-publish exechook's actual completion/result before returning from `main.go`'s `SyncRepo` publish step, similar to how `WaitForCompletion` already works for `--one-time` mode - i.e., always initialize/use a completion signal (not only when `oneTime` is set) so that `publishSymlink` is only invoked once the pre-publish hook has genuinely succeeded (or the operator has explicitly opted out of a synchronous gate).

### Proof of Concept
1. Configure git-sync in continuous mode with `--pre-publish-exechook-command` pointing to a script that sleeps for the sync period or exits non-zero (simulating a slow/failing validation hook), and `--link` pointing to a path consumed by another process.
2. Push a new commit to the tracked ref.
3. Observe via `SyncRepo` (`main.go:1955-1963`) that `git.publishSymlink(newWorktree)` executes immediately after `syncHooks.beforePublish` returns (which happens right after the non-blocking `Send`, per `pkg/hook/hook.go:79-89` and `122-125`), i.e., before the exechook command has actually finished/succeeded - the consumer-facing symlink is updated to the new (unvalidated) content regardless of the hook's real outcome.
