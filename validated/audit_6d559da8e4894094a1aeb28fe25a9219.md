### Title
Unsanitized username/hostname displayed in `gh auth switch` prompt allows terminal escape injection - ([File: pkg/cmd/auth/switch/switch.go])

### Summary
`switchRun` builds prompt option strings with raw, unsanitized `c.user`/`c.host` values pulled from persisted config and passes them straight to `opts.Prompter.Select`. Because usernames are sourced from an arbitrary GraphQL `viewer.login` response during `gh auth login --hostname <attacker-host> --with-token` (no charset validation), an attacker who controls a host the victim points `gh auth login` at can persist a username containing ANSI/control sequences, which later corrupts or forges lines in the `gh auth switch` selection menu.

### Finding Description
In `switchRun`, when more than one candidate account/host pair exists, the code builds prompt strings with plain `fmt.Sprintf("%s (%s)", c.user, c.host)` and feeds the slice directly into `opts.Prompter.Select` with no escaping: [1](#0-0) 

The `c.user` and `c.host` values originate from `authCfg.Hosts()`/`UsersForHost()`, i.e. what was persisted during `gh auth login`. During `--with-token` login, the username is fetched via `GetCurrentLogin`, which issues a GraphQL query to the *hostname the user configured* and blindly trusts the returned `viewer.login` string with no character-set or length validation: [2](#0-1) 

If the victim runs `gh auth login --hostname <attacker-controlled-enterprise-host> --with-token`, the attacker (who controls that host's API responses) can return any string as `login`, including one embedding ANSI escape sequences or carriage returns. This value flows unmodified into `authCfg.Login(hostname, username, ...)` and is persisted to config with no sanitization at the persistence boundary either.

Unlike many other output paths in this codebase (e.g. `pkg/iostreams/untrusted.go`, `internal/text/text.go`, and their use in `pkg/cmd/repo/view/http.go`, `pkg/cmd/issue/shared/display.go`, etc., which explicitly sanitize/strip untrusted API-derived text before display), `switch.go`'s prompt-building code path performs no such sanitization before handing the string to the interactive prompter. This is inconsistent with the codebase's established defense pattern for untrusted display strings and is the concrete root cause.

### Impact Explanation
A crafted username with embedded ANSI/control sequences can rewrite terminal cursor position/attributes when rendered by the interactive `Select` prompt, allowing an attacker to overwrite or hide the true hostname portion of a prompt line, or fabricate what looks like additional/different menu entries. Since `gh auth switch` result determines which stored credential becomes the CLI's active account, this can trick a victim into activating an attacker-favored account instead of the one they intended — a wrong-account routing / authorization confusion impact.

### Likelihood Explanation
Exploitation requires the victim to have previously executed `gh auth login --hostname <attacker-host> --with-token` (or interactive login) against a host under attacker control, so that the malicious `viewer.login` value is persisted to the local config, and to later run `gh auth switch` with 3+ ambiguous candidates so the interactive prompt path is triggered. This is a real but narrower precondition than a stateless remote-content attack (it depends on the victim configuring/trusting an attacker-operated GitHub Enterprise-style host and completing a token login against it), which the threat model explicitly allows ("attacker controls responses from a host the victim points gh at"). Given that precondition, the injection itself is deterministic and repeatable.

### Recommendation
Sanitize `c.user` and `c.host` before building prompt strings in `switchRun` (e.g. reuse the existing `internal/text` / `pkg/iostreams/untrusted.go` sanitization helpers already used elsewhere for untrusted API-derived strings), and additionally validate/restrict the username returned by `GetCurrentLogin` (and any host-supplied login field) to the expected GitHub username charset before persisting it via `authCfg.Login`.

```go
// pkg/cmd/auth/switch/switch_test.go (illustrative)
func TestSwitchRun_UnsanitizedPromptInjection(t *testing.T) {
    maliciousUser := "monalisa\x1b[2K\x1b[1Ahacker (evil.com)" // embeds ANSI escapes
    cfg := // ... seed config with two hosts, one user = maliciousUser

    var capturedOptions []string
    pm := &prompter.PrompterMock{
        SelectFunc: func(_, _ string, opts []string) (int, error) {
            capturedOptions = opts
            return 0, nil
        },
    }
    opts := &SwitchOptions{Config: func() (gh.Config, error) { return cfg, nil }, Prompter: pm, IO: ios}
    _ = switchRun(opts)

    for _, o := range capturedOptions {
        assert.NotContains(t, o, "\x1b") // expect escape sequences stripped/escaped
    }
}
```
Expected (failing) result today: `capturedOptions` contains the raw `\x1b[...]` bytes verbatim, confirming no sanitization occurs before the string reaches `Prompter.Select`.

```go
func GetCurrentLogin(httpClient httpClient, hostname, authToken string) (string, error) {
	query := `query UserCurrent{viewer{login}}`
	reqBody, err := json.Marshal(map[string]interface{}{"query": query})
	if err != nil {
		return "", err
	}
	result := struct {
		Data struct{ Viewer struct{ Login string } }
	}{}
	apiEndpoint, err := safeurl.JoinPathWithHostPrefix(ghinstance.GraphQLEndpoint(hostname))
	if err != nil {
		return "", err
	}
	req, err := http.NewRequest("POST", apiEndpoint.String(), bytes.NewBuffer(reqBody))
	if err != nil {
		return "", err
	}
	req.Header.Set("Authorization", "token "+authToken)
	res, err := httpClient.Do(req)
	if err != nil {
		return "", err
	}
	defer res.Body.Close()
	if res.StatusCode > 299 {
		return "", api.HandleHTTPError(res)
	}
	decoder := json.NewDecoder(res.Body)
	err = decoder.Decode(&result)
	if err != nil {
		return "", err
	}
	return result.Data.Viewer.Login, nil
```
