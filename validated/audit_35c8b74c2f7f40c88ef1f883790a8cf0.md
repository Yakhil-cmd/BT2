### Title
Webhook signature verification is silently bypassed when an organization's `webhook_secret` is not configured - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved app's `webhook_secret` is blank, instead of rejecting the request. This mirrors the reported bug class (a missing "zero value" guard on a security-relevant field): just as `getSyntRepresentation` returning the zero address should be rejected by a `require`, a GitHub App configuration with a blank `webhook_secret` should never allow a webhook to be treated as verified.

### Finding Description
The webhook signature check performed by `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, which resolves the `GitHubApp` instance for the organization named in the *attacker-supplied* payload (`repository_owner` reads `params.dig('repository','owner','login')` or `params.dig('organization','login')`). [1](#0-0) [2](#0-1) 

Inside `verify_webhook_signature`, the very first line is:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [3](#0-2) 

`@webhook_secret` is set from `@config[:webhook_secret].presence` in the constructor, so any organization/app configuration without a `webhook_secret` key (or with an empty string) will have `webhook_secret` be `nil`, and the method will unconditionally return `true` — i.e., the webhook is treated as verified regardless of the actual `X-Hub-Signature` header or payload content. [4](#0-3) 

This breaks the intended equality: *"the organization that cryptographically authenticated the webhook == the organization/repository whose webhook handlers get invoked."* Because `repository_owner` is taken directly from the untrusted JSON body and used to select which app's secret governs verification, any deployment that has one or more configured GitHub Apps/organizations without a `webhook_secret` set effectively disables signature verification for all webhooks claiming to originate from that organization — with no authentication of the sender at all.

### Impact Explanation
If `verify_signature` passes unconditionally, `WebhooksController#create` proceeds to run `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` on fully attacker-controlled JSON. [5](#0-4) 
Webhook handlers drive state that is normally trust-boundary-protected (e.g., pull request state/label/merge status updates, commit/status ingestion, membership/team sync depending on which handlers are registered) purely from the payload. An unauthenticated remote attacker who only needs to know (or guess) an organization login lacking a `webhook_secret` can forge arbitrary GitHub events for repositories under that organization, causing unauthorized writes to stack/PR/commit state that should only be updatable by verified GitHub events. This crosses the "cross-repository writes" / "unauthorized deploy" impact class depending on which webhook handlers are registered in the host app, since the compromised control point is the trust anchor (signature verification) itself, not a specific handler.

### Likelihood Explanation
Exploitability depends entirely on configuration: it requires at least one organization/app entry in `Shipit.github_apps`-style config to have a blank or unset `webhook_secret`, which is plausible for enterprise/multi-org setups where operators forget to set a per-org secret, or where a default/fallback app config omits it. This is a config-dependent bypass rather than a universally-exploitable bug, so likelihood is conditional on a documented but easy-to-miss operational requirement (every configured app must have a non-blank `webhook_secret`) — not a hard runtime guarantee enforced by the code.

### Recommendation
Change the guard in `verify_webhook_signature` so that a blank `webhook_secret` results in rejection (`false`) rather than automatic acceptance, e.g.:
```ruby
def verify_webhook_signature(signature, message)
  return false if webhook_secret.blank?
  ...
end
```
Additionally, validate at boot/config-load time (e.g., in `Shipit.github_apps=` or wherever `GitHubApp` instances are constructed) that `webhook_secret` is present for every configured organization, raising a configuration error otherwise — analogous to adding a `require`-style check against the "zero value" case instead of silently treating it as trusted.

### Proof of Concept
1. Configure Shipit with a GitHub App/organization entry that omits `webhook_secret` (or sets it to an empty string), e.g. in `secrets.yml` under `github.apps.<org>`.
2. As an unauthenticated remote client, POST to `/github/webhooks` with headers `X-Github-Event: <handled-event>` and a JSON body whose `repository.owner.login` (or `organization.login`) matches that organization — omit or forge any `X-Hub-Signature` header value.
3. Observe that `verify_signature` passes (`webhook_secret` is `nil` → `verify_webhook_signature` returns `true`) and `WebhooksController#create` invokes the registered handlers on the forged payload, mutating state that should only be reachable via a GitHub-signed webhook. [3](#0-2) [6](#0-5)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
