### Title
Asset definer can unilaterally revoke the attestor list to freeze holders' funds of a `spender_attested` asset - (File: `validation.js`)

### Summary
For assets flagged `spender_attested`, spending is gated on the spender being attested by an address in the asset's *current* attestor list, which the asset definer alone controls and can change at any time via an `asset_attestors` message. Because attestor-list changes are validated with no continuity or consent requirement from existing holders, a definer (a privileged, permissionless-to-users party analogous to the "DAO/LSD owner" in the referenced report) can post a replacement attestor list after users have already received/deposited the asset in reliance on being attested, instantly and unilaterally cutting off their ability to move funds they legitimately hold — mirroring the pattern where a privileged role-holder swaps out an authorization binding without regard to funds already committed under the old binding.

### Finding Description
Payments of a `spender_attested` asset are validated in `validatePayment` (`validation.js`), which calls `storage.loadAssetWithListOfAttestedAuthors` to compute `objAsset.arrAttestedAddresses` and then requires at least one author to be attested, and requires the issuer to be attested when issuing: [1](#0-0) 

`loadAssetWithListOfAttestedAuthors` delegates to `filterAttestedAddresses`, which matches `attestations` rows only against the asset's *current* attestor list (`objAsset.arrAttestorAddresses`), read as the single latest `asset_attestors` update for the asset: [2](#0-1) [3](#0-2) 

Output addresses receiving the asset in a transfer are checked the same way, again against the current attestor list: [4](#0-3) 

The attestor list itself is updated via the `asset_attestors` app, validated by `validateAttestorListUpdate`, which only checks that the message is single-authored and posted by `objAsset.definer_address` — it performs no check on whether removing or replacing attestors would strand funds already held by users who were attested under the old list, and there is no cooldown, timelock, or holder consent mechanism: [5](#0-4) 

Because `readAsset`/`filterAttestedAddresses` only look up the *latest* attestor-list unit for the asset (`ORDER BY ... DESC LIMIT 1`), a single new `asset_attestors` message from the definer completely replaces the effective attestor set used for all subsequent payment validation, retroactively invalidating attestations that were valid (and relied upon) when the holder acquired the asset.

### Impact Explanation
A malicious or compromised asset definer can:
1. Set up a `spender_attested` asset with an attestor they control (or a legitimate attestor).
2. Let users acquire/receive the asset after being attested (analogous to the node runner depositing 4 ETH under an existing binding).
3. Post a new `asset_attestors` message dropping the users' attestor (or replacing the whole list), instantly making `arrAttestedAddresses` empty for those holders.
4. Those holders can no longer pass the `spender_attested` check in `validatePayment`, so they cannot spend or transfer the asset they already legitimately hold — a permanent freeze of their funds, entirely at the definer's discretion and without any of the holders' cooperation or notice period.

This is a direct analog of the reported bug: a privileged party (there, the DAO/LSD owner; here, the asset definer) can retroactively swap out a binding (node runner vs. attestor list) that other users' already-deposited/held funds depend on, causing fund loss/freezing for those users without their consent.

### Likelihood Explanation
The attack requires only that the attacker be the asset's own definer (or gain control of the definer key), which is entirely within the reach of any single unprivileged unit poster who creates the asset themselves, and requires no cooperation from witnesses, miners, or other privileged network roles. Since `validateAttestorListUpdate` places no restriction beyond "sender == definer_address", the attack is a one-message operation (`asset_attestors`) that becomes effective the moment it stabilizes.

### Recommendation
When updating an asset's attestor list, do not let the new list retroactively invalidate attestations of addresses that already hold a balance of the asset, e.g.:
- Grandfather already-attested holders' existing balances under the attestor that attested them (track attestor-list version alongside balances), or
- Require the new attestor list to be a strict superset of holders' attestors for outstanding balances, or
- Introduce a delay/grace period before an attestor-list change takes effect, during which existing holders can move funds out, or
- Emit a warning/require holder consent (e.g., via a cosigned condition) before an attestor removal that would strand existing balances.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and posts `asset_attestors` listing attestor `T1`.
2. Attestor `T1` posts an `attestation` for user `U`'s address.
3. `D` sends `A` to `U` (validated fine, since `U` is attested by `T1`, which is in the current list per `filterAttestedAddresses`).
4. `D` posts a new `asset_attestors` message for asset `A` listing only attestor `T2` (controlled by `D`, who never attests `U`).
5. `U` now tries to spend/transfer asset `A`: `validatePayment` calls `loadAssetWithListOfAttestedAuthors`, which computes `arrAttestedAddresses` using only `T2`'s attestations; `U` is not in that set, so `validatePayment` returns `"none of the authors is attested"` and the unit is rejected — `U`'s funds are permanently stuck as long as `D` keeps `T2` as the sole attestor and never attests `U`. function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });

		}
