### Title
Vote Account Closure Uses Vote-Credit Recency As a Flawed Proxy for "No Active Stake" - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The `withdraw` instruction handler in the vote program allows an authorized withdrawer to fully drain and deinitialize a vote account based solely on how recently the vote account earned epoch credits, rather than checking whether stake is still actively delegated to it. This mirrors the reported `_checkNoLiquidity` flaw: an indirect proxy (recent voting activity) is used in place of the actual invariant that should gate a destructive state transition (no active delegations), letting the account be torn down while delegators still have stake pointed at it.

### Finding Description
`withdraw` in [1](#0-0)  only rejects a full-balance withdrawal (which deinitializes the account by zeroing its data via `VoteStateHandler::deinitialize_vote_account_state`) when `reject_active_vote_account_close` is true. That flag is derived purely from vote-credit recency: [2](#0-1) 

It never inspects whether stake accounts are currently delegated to this vote account (there is no equivalent of "no open borrows/no deposits" — the real invariant that matters, analogous to `_checkNoLiquidity`'s missing borrow/deposit check). A validator that has simply gone offline for two epochs (e.g., temporarily down, but with plenty of active/activating stake delegated to it) satisfies `reject_active_vote_account_close == false`, letting the authorized withdrawer close the account even though delegated stake still references its pubkey.

By contrast, the CLI helper for the equivalent stake-side operation (closing a vote account) attempts to check `activated_stake != 0` off-chain before submitting the withdrawal, exactly the check that is missing on-chain: [3](#0-2) . This confirms that "no active stake" was intended to be the real gating condition, but the on-chain program substitutes an unrelated proxy (credit recency) instead, just like the Riz `_checkNoLiquidity` used aToken balance as a flawed proxy for "no open borrows."

Once the vote account is deinitialized (all-zero data, `is_uninitialized`), reward computation for any stake still delegated to it cannot find the vote account in `distribution_epoch_vote_accounts` and silently drops or skips reward attribution for that delegation: [4](#0-3) 

### Impact Explanation
Delegators whose stake remains bound to a vote pubkey that has been deinitialized lose the ability to earn/receive inflation and block-revenue rewards for that delegation, and the delegation is effectively orphaned to a non-existent voting identity until they notice and manually undelegate/redelegate. This is a direct funds/rewards-accounting impact reachable purely from a single signed transaction by the vote account's authorized withdrawer, without any validation of the true "no active delegation" invariant — the reward loss is silent (no error is raised) and stems from a checked condition that does not match the actual invariant it claims to enforce, precisely the bug class in the analog report.

### Likelihood Explanation
Any validator/authorized withdrawer who is delinquent for 2+ epochs (a common, non-malicious scenario — downtime, misconfiguration, migration) can trigger this by simply withdrawing the full vote account balance, an ordinary and expected operation for decommissioning a validator. No coordination with the stake owner is required, and the affected delegators may not even be aware their delegation is silently orphaned.

### Recommendation
Change the check in `withdraw` (`programs/vote/src/vote_state/mod.rs`) to directly verify there is no stake currently delegated to the vote account (e.g., consult total activated/activating delegated stake for this vote pubkey, similar to what the CLI's `activated_stake` check attempts client-side) before permitting the account to be zeroed/deinitialized, rather than relying on epoch-credit recency as a stand-in for delegation activity.

### Proof of Concept
1. Create and fund a vote account; delegate stake to it from one or more stake accounts so it has non-zero activated/activating delegated stake.
2. Do not vote for 2+ epochs (delinquency), so `current_epoch.saturating_sub(last_epoch_with_credits) >= 2`.
3. As the authorized withdrawer, submit `VoteInstruction::Withdraw(full_balance)`. Per the logic at [5](#0-4) , `reject_active_vote_account_close` evaluates to `false` (no recent credits) even though delegated stake is nonzero, so the withdrawal succeeds and the account is zeroed via `deinitialize_vote_account_state`.
4. On the next reward distribution, delegations still pointing at this vote pubkey fail the `distribution_epoch_vote_accounts.get(&vote_pubkey)` lookup in `redeem_delegation_rewards` and receive no reward, silently, with no error surfaced to the delegator.
