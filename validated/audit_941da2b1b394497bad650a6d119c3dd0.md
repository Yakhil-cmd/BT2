### Title
Reachable assertion (`throw Error`) in `checkForDoublespends` allows a private-payment counterparty to crash any validating node - (File: validation.js)

### Summary
`checkForDoublespends()` in `validation.js` contains multiple `throw Error(...)` statements that are meant to guard "impossible" states but are reachable with attacker-controlled unit content, mirroring the TensorFlow `CHECK`-fail pattern where a value taken from user input is fed into logic that assumes it can never violate an invariant, and a hard crash (`CHECK`/`throw`) is used instead of returning a validation error.

### Finding Description
`validateSpendProofs()` builds a doublespend-detection SQL query directly from the `spend_proofs` array supplied in the posted unit: [1](#0-0) 

The `address` used in the `WHERE` clause is taken from `objSpendProof.address` (falling back to `objUnit.authors[0].address` only if omitted) with no requirement that it match one of the unit's own authors before the query executes. The result rows are then passed into `checkForDoublespends`: [2](#0-1) 

If a matching row is found whose `address` is not among the current unit's author addresses, the code assumes this "can't happen" and crashes with `throw Error("conflicting "+type+" spent from another address?")` instead of returning a normal validation error to the caller. Two further `throw Error(...)` branches in the same function (`"unreachable code, conflicting ... in inner unit"` and `"double spending ... without double spending address?"`) make the same unchecked assumption about graph/sequence state derived from attacker-supplied unit content: [3](#0-2) 

A spend-proof `(value, address)` pair is not secret to everyone: it is exposed to the intended recipient of a private (indivisible-asset) payment as part of the private payment chain during a normal transfer, since spend proofs are built and shared as part of `validateAndSavePrivatePaymentChain`/`buildPrivateElementsChain` in `indivisible_asset.js`. A private-payment counterparty who has legitimately received such a pair can therefore construct a new, unrelated unit as its own author, include a `spend_proofs` message that cites the *other* address's known spend-proof value, and broadcast it. When any node validates this poisoned unit, the SQL lookup returns the pre-existing spend-proof row, `arrAuthorAddresses.indexOf(objConflictingRecord.address)` is `-1` (the address belongs to someone else, not the poison unit's author), and the assumed-invariant `throw Error(...)` fires inside an `async.eachSeries` callback.

Because this throw happens asynchronously (inside a DB-query callback), it becomes an uncaught exception. `network.js` explicitly re-throws on `uncaughtException` to intentionally crash the whole process: [4](#0-3) 

### Impact Explanation
Any full node (including hubs) that processes the crafted unit crashes the entire Node.js process. Because unit validation and relay are core to network operation, a single crafted unit propagating through the DAG can crash every node/hub that attempts to validate it, i.e., a network unable to confirm new units — this is the strongest reachable impact class permitted by the rules for this type of reachable-assertion bug, directly analogous to the TensorFlow `CHECK`-fail DoS.

### Likelihood Explanation
Exploitation requires the attacker to know at least one `(spend_proof, address)` pair belonging to someone else. This is achievable for a legitimate private-payment counterparty, who receives exactly such data as part of a normal private indivisible-asset payment. No node compromise, key leakage, or privileged access is required — only participation as a private-payment recipient, which is explicitly an in-scope actor.

### Recommendation
Replace the assumed-invariant `throw Error(...)` calls in `checkForDoublespends` (validation.js lines ~1673, ~1688, ~1692) with a normal validation-error return (`cb2(...)`/`cb(...)`) so that malformed/mismatched spend-proof references are rejected as an ordinary unit error instead of crashing the process. Additionally, validate that `objSpendProof.address` (when explicitly provided) belongs to `objUnit.authors` before it is used to build the doublespend lookup query, so foreign addresses can never enter this code path at all.

### Proof of Concept
1. As a private-payment counterparty, receive a private indivisible-asset payment and obtain the sender/owner's `(spend_proof, address)` pair from the shared private payment chain (as produced by `buildPrivateElementsChain`/`validateAndSavePrivatePaymentChain` in `indivisible_asset.js`).
2. Compose and sign a new, otherwise-valid unit as your own author, adding a message with a `spend_proofs` entry: `{ spend_proof: <known_value>, address: <owner_address> }`, where `<owner_address>` is not one of your own author addresses.
3. Broadcast the unit. On any node, `validateSpendProofs` → `checkForDoublespends` finds the pre-existing row for `<owner_address>` and executes `throw Error("conflicting spend proof spent from another address?")` inside the async callback.
4. The uncaught exception hits `process.on('uncaughtException', ...)` in `network.js`, which logs and re-throws, crashing the node process. [5](#0-4) [4](#0-3) 

Note: I was not able to fully trace the field-level validation of the `spend_proofs` array elements (e.g., whether some other code path in `validation.js` forces `objSpendProof.address` to be an author address before `validateSpendProofs` runs) due to index/search limitations; if such a check exists elsewhere, it would need to be confirmed to fully rule out or confirm this exact trigger path.
