### Title
Data-feed key injection via unsanitized `feed_name` newline delimiters in KV-store keys - (File: `data_feeds.js`, `main_chain.js`)

### Summary
The CVE describes a class of bug where user-controllable fields are written into a structured, delimiter-based artifact (an NGINX config) without sanitizing characters that have structural meaning in that format, letting an authenticated-but-limited actor inject directives that were not intended by the schema. The closest reachable analog in ocore is the construction of LevelDB keys for oracle data feeds: `feed_name`, a field fully controlled by any unit poster/oracle author via a `data_feed` message, is concatenated with the literal `\n` delimiter into KV keys without escaping or rejecting embedded `\n` characters.

### Finding Description
When a `data_feed` message becomes stable, `main_chain.js`'s `addDataFeeds` writes KV entries keyed as `'df\n'+address+'\n'+feed_name+'\n'+type+'\n'+value+'\n'+mci` and `'dfv\n'+address+'\n'+feed_name+'\n'+mci`, using `feed_name` directly as supplied in the payload: [1](#0-0) 

The read/query side in `data_feeds.js` builds range-scan prefixes the same way, relying on `\n` as the sole field separator between `address`, `feed_name`, value-type, and encoded value: [2](#0-1) [3](#0-2) 

Because `feed_name` is attacker-supplied string content from an ordinary `data_feed` message (postable by any unit author, not just a privileged oracle role), and I could not confirm from the code reviewed that `feed_name` content is restricted to disallow the `\n` delimiter character (only a length check via `MAX_DATA_FEED_NAME_LENGTH` was located, in `validation.js`), a crafted `feed_name` containing embedded `\n` sequences could forge key fragments that overlap with a different, unintended `feed_name`/type/value/`mci` field boundary — analogous to how an unsanitized CRD field in the CVE could inject unintended directives into the generated NGINX config by breaking out of its intended field boundary in a delimiter-based format.

### Impact Explanation
If exploitable, an attacker-controlled `feed_name` could inject a forged `\n`-delimited suffix that is interpreted by `in data feed`/`data feed value` oscript operators (used inside AA formulas and address-definition conditions, e.g., `['in data feed', [...]]` in `definition.js`) as belonging to a *different* feed name or oracle than what a smart contract or bot actually expects, causing an AA or address condition to observe a forged/attacker-chosen value for an oracle feed it trusts. This can lead to fund loss, incorrect payment release, or node disagreement about whether a condition (`in data feed`) is satisfied — one of the accepted high-severity outcomes (AA fund loss, node disagreement on validity).

### Likelihood Explanation
Reachability is high: any unit author can post a `data_feed` message with an arbitrary `feed_name` string, no special privilege required, matching the CVE's "authenticated actor with write access to a CRD/annotation field" pattern. However, I was not able to fully verify in this session whether `validation.js`'s data-feed field-name validation already restricts characters (only a length constant `MAX_DATA_FEED_NAME_LENGTH` was located via grep, not the exact regex/character-class check). If `validation.js` already rejects control characters like `\n` in `feed_name` (which is plausible for a mature, audited codebase), this analog is not exploitable and should be treated as unconfirmed rather than proven.

### Recommendation
- Explicitly reject or escape `\n` (and any other characters used as field separators in the `df\n...`/`dfv\n...` key scheme) in `feed_name` during `data_feed` message validation in `validation.js`, in addition to the existing length check.
- Alternatively, use a length-prefixed or otherwise unambiguous encoding for `feed_name` in `main_chain.js`'s `addDataFeeds` and `data_feeds.js` key construction so that no possible string value of `feed_name` can shift field boundaries.

### Proof of Concept
Could not be fully constructed/verified in this session — determining exploitability requires reading the exact `data_feed` validation rules in `validation.js` (specifically whether embedded `\n` in `feed_name` is rejected), which was not retrievable within the available tool calls. The mechanism described (unsanitized `feed_name` embedded in `\n`-delimited KV keys in `main_chain.js:1592-1617` and `data_feeds.js:119-139,287-306`) is the concrete, cited root-cause candidate; a PoC would involve posting a `data_feed` message with `feed_name` = `"legit_feed\nn\n<forged_encoded_value>\n<forged_mci>"` and checking whether a subsequent `in data feed`/`data feed value` lookup for `legit_feed` on that oracle address returns the forged value.
