### Title
Cross-stack authorization bypass via `Api::CCMenuController#stack` ignoring `ApiClient#stack_id` scope binding - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` scopes every resource lookup to the stacks a token is authorized for via `stacks`, which filters by `current_api_client.stack_id` when the client is stack-scoped [1](#0-0) . `Api::CCMenuController` overrides `stack` to bypass this scoping entirely, resolving the target stack directly from `params[:stack_id]` with no relation to the authenticated client [2](#0-1) . This breaks the equality "stack a token authorizes == stack it touches".

### Finding Description
`ApiClient` records can be created scoped to a single `stack_id`, and `BaseController#stacks` is meant to enforce that scope for every other API controller: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . `stack` then calls `stacks.from_param!(params[:stack_id])`, so a stack-scoped token cannot address a stack outside its `stack_id`.

`Api::CCMenuController`, however, defines its own `stack` method that does not go through `stacks`:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`require_permission :read, :stack` only checks that the client has the `read:stack` permission string via `check_permissions!` [3](#0-2)  — it never checks that the client's `stack_id` matches the requested `params[:stack_id]`. Any client with `read:stack` permission (including one created and scoped to Stack A only, e.g. via the `CCMenuUrlController` which auto-creates a client scoped to one stack with `permissions: %w[read:stack]` [4](#0-3) ) can supply an arbitrary `stack_id` and read the CCMenu status of any other stack in the installation.

Root cause: the scoping check performed in `BaseController#stacks`/`#stack` (path A: token authorizes a specific stack) is silently absent from `CCMenuController#stack` (path B: which stack is actually touched), so the two diverge for this controller only.

### Impact Explanation
This crosses the "unauthenticated/unauthorized read of stack state" boundary called out as High severity: an attacker holding a token that was only meant to see one stack's CI status can enumerate/read `lastBuildStatus`, `lastBuildLabel`, `activity`, and `webUrl` for every other stack managed by the Shipit instance, disclosing deployment/build state for repositories the token was never granted access to.

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with `read:stack` permission — which is exactly the low-privilege, narrowly-scoped token type the `stack_id` restriction feature exists to support (e.g., the CCMenu URL feature deliberately mints such single-stack-scoped tokens for embedding in third-party CI dashboards, at `app/controllers/shipit/ccmenu_url_controller.rb`). No elevated privileges, session, or additional secret is needed beyond the token itself, and the request is a single unauthenticated-relative-to-scope GET with a different `stack_id` parameter.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack through the same authorization-scoped `stacks` method used by `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a `stack_id`-scoped `ApiClient` cannot address stacks outside its authorized scope.

### Proof of Concept
1. Create (or have the app auto-create via `CCMenuUrlController#client`) an `ApiClient` scoped to `stack_id: A` with `permissions: ["read:stack"]`, and obtain its `authentication_token`.
2. Send `GET /api/stacks/:other_stack_id/ccmenu.xml?token=<token>` where `:other_stack_id` refers to a different stack `B` that the token was never scoped to.
3. Observe that `require_permission :read, :stack` passes (the client does have `read:stack`), and `stack` resolves via `Stack.from_param!(params[:stack_id])` directly to stack `B`, returning `B`'s build/deploy status — despite the token being restricted to stack `A`.
