This is exactly the equality-binding mismatch the rules describe: "an organization that authenticated versus the repository that is written."

### Title
Webhook signature is verified against an organization derived from unauthenticated payload fields, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, attacker-controlled JSON body, *before* the signature has been validated. The signature is only proven to match *some* organization's secret — not necessarily the organization that Shipit subsequently treats the payload as belonging to for writing state (creating commits, teams, users, deploy statuses, etc.), because the handlers act on the same untrusted `repository`/`organization` fields the attacker fully controls.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 

`repository_owner` is computed purely from the JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

If Shipit hosts multiple GitHub organizations (each with its own `webhook_secret` via `Shipit.github(organization:)`), an attacker who is a legitimate (unprivileged, ordinary contributor-level) webhook sender for **organization A** — and therefore knows organization A's `webhook_secret` HMAC only insofar as GitHub itself computes and sends it, but who *can fully control the JSON body content of events GitHub sends for org A's repos* (e.g., by choosing PR titles, branch names, commit messages, pushing to a repo they only have limited/webhook-triggering rights to) — can craft a payload whose `repository.owner.login` still says "A" (so the signature is checked with A's secret, which GitHub itself signs) but whose `repository.full_name`/other identifying fields inside nested objects used by the handler do not match, causing Shipit to bind organization A's authenticated signature to actions/records for a *different* repository than the one actually authorized. Concretely: `event`, `params`, and `repository_owner` are all read from the same unverified body before the HMAC check passes, and downstream handlers (`CheckSuiteHandler`, `PushHandler`, `StatusHandler`, etc.) re-parse further nested fields such as `check_suite.head_branch`, `check_suite.head_sha`, or commit SHAs to decide which `Stack`/`Commit` records to mutate — see `CheckSuiteHandler#process`, which trusts `params.check_suite.head_sha` / `head_branch` to select `stacks.where(branch: ...)` and schedule check-run refreshes without re-validating that this data corresponds to the same repository whose secret validated the signature. [3](#0-2) 

This is the direct structural analogue of the oracle report's core flaw: the *authorization check* (HMAC verification against org A's secret) and the *state-mutating action* (writing to Stack/Commit rows keyed by `repository`/`sha`/`branch` fields drawn from the same body) are computed from the same attacker-supplied JSON but are never cross-checked against each other for consistency — exactly like `_eth2dyad`/`_dyad2eth` using a price that isn't temporally/structurally bound to the trade it authorizes.

### Impact Explanation
If exploitable, this allows an attacker who can trigger genuine GitHub webhook deliveries for one organization/repository under Shipit's control to inject event data that is processed as if it pertained to another organization's repositories/stacks that Shipit also manages, causing unauthorized writes to commit/check/build state across repository boundaries (cross-repository writes) — one of the explicitly listed Critical impacts.

### Likelihood Explanation
Low-to-uncertain. This requires: (1) the deployment to actually configure `Shipit.github_apps`/organizations such that more than one GitHub organization's webhooks are handled by the same Shipit instance, and (2) a concrete field in one of the webhook handlers (`push`, `status`, `check_suite`, `membership`, etc.) that is used to select/write a `Stack`/`Commit`/`Team`/`User` record based on repository identity independent of `repository_owner`, in a way where that identity can diverge from the org whose secret validated the request. From the code reviewed, all handlers I could inspect (`CheckSuiteHandler`) scope lookups by `stacks.where(branch: ...)` combined with commit `sha`, which are still fields of the same JSON body — I was not able to confirm within the available in-scope code whether any handler cross-organization write is actually reachable (e.g., whether `Stack`/`Repository` records for different orgs could collide on branch/sha, or whether `repository.full_name` is ever validated against the stack being mutated). This requires deeper tracing through all `Shipit::Webhooks::Handlers::*` classes (push, status, membership, pull_request) than was available in this pass.

### Recommendation
Bind the webhook's cryptographically verified organization to every subsequent database lookup: after `verify_webhook_signature` succeeds for organization `O`, all handler queries (`stacks.where(...)`, `Repository.from_github_repo_name(...)`, etc.) must additionally filter by `repository_id`/`owner == O`, not merely by branch/sha/login fields taken from the same unauthenticated body. Consider verifying the signature using the full `repository.full_name` (owner+repo) rather than only `owner.login`, and reject events where any nested identity field is inconsistent with the top-level `repository` object.

### Proof of Concept
Not concretely demonstrable from the in-scope code alone: I traced the org-selection-before-signature-verification pattern in `WebhooksController#verify_signature`/`#repository_owner` and the branch/sha-only scoping in `CheckSuiteHandler#process`, but could not confirm, within the available files, a specific handler where a mismatched `repository.full_name` vs. `repository.owner.login` payload would cause a write against a *different* organization's `Stack`. This would need to be validated by inspecting the remaining `app/models/shipit/webhooks/handlers/*.rb` files (push, status, pull_request, membership) for any lookup keyed only by fields other than a fully-qualified, owner-scoped repository identifier — which was not completed in this session. Given this residual uncertainty and lack of a concrete cross-repository write path confirmed end-to-end, I cannot assert this finding meets the bar with full confidence.
