Confirmed the exploit chain. `StatusHandler#process` at [1](#0-0)  looks up commits purely by `Commit.where(sha: params.sha)` — a global lookup with no scoping to the organization/repository that was used to verify the webhook signature. This directly feeds `Status` records that determine `Commit#deployable?` at [2](#0-1)  and gate deploy creation via `require_ci` in the deploy API, and also trigger continuous deployment through `Status#schedule_continuous_delivery` at [3](#0-2) .

### Title
Webhook signature verification is bound to the payload's `repository.owner`/`organization` login while all event handlers act on the payload's `repository.full_name`, allowing an attacker who controls one configured GitHub organization to forge CI status/push/PR events for any stack belonging to any other configured organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, defined as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, at [4](#0-3) [5](#0-4) . Once the signature check passes, the *entire raw payload* — including a `repository.full_name` field that is never checked against `repository_owner` — is dispatched unchanged to all registered handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` at [6](#0-5) .

Every handler resolves the target `Repository`/`Stack`/`Commit` from `full_name` or bare `sha`, not from `repository_owner`:
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [7](#0-6) 
- `PushHandler#process` syncs stacks matched by that repository/branch [8](#0-7) 
- `StatusHandler#process` matches commits by **bare sha only**, with zero repository/org scoping at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) 
- `PullRequest::ClosedHandler#repository` resolves via `params.repository.full_name` [9](#0-8) 

The binding that should hold is: **organization authenticated (signature-verifying org) == organization of the repository actually written to**. In Shipit's supported multi-organization configuration — explicitly documented in `docs/setup.md` ("Using Multiple Github Applications", lines 182-209) and exercised in `test/dummy/config/secrets_double_github_app.yml` — each organization has its own independent `webhook_secret`. Nothing in `verify_signature` or in any handler enforces that the `full_name`/`sha` acted upon actually belongs to the org whose secret validated the request.

### Finding Description
An attacker who legitimately controls (or is a collaborator/admin on) any one GitHub organization/repository configured in Shipit's multi-org `github:` secrets — and therefore knows or can trigger delivery of a validly-HMAC-signed webhook for that org — can send a raw POST to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) set to **their own controlled org** (so `verify_signature`'s `Shipit.github(organization: repository_owner)` picks their org's `webhook_secret`, which they can correctly sign, e.g. by simply relaying a real webhook GitHub sends them, or by computing the HMAC themselves if they know/reset their own org's secret),
- but `repository.full_name` (for push/PR events) or a bare `sha` (for status events) referencing a **stack belonging to a completely different, unrelated organization** hosted on the same Shipit instance.

Because the signature check and the handler dispatch use two different fields of the same untrusted JSON body without cross-checking them, the forged event is accepted and acted upon as if it legitimately originated from GitHub for the victim organization's repository.

The most severe consequence is via `StatusHandler`, whose commit lookup is not scoped by owner/repo at all — only by `sha` — so an attacker need only guess/observe a real commit SHA (SHAs are not secret; they're visible in PRs, in Shipit's own UI, etc.) belonging to a victim stack in another organization, and inject a forged `state: success` (or `pending`/`failure`) status for any `context`, including one listed in that stack's `ci.require`/`ci.blocking` config (`app/models/shipit/deploy_spec/file_system.rb` lines 49-54, README.md lines 444-480).

### Impact Explanation
A forged `success` status flips `Commit#deployable?` at [2](#0-1)  to true for a commit the attacker does not control CI for. This:
- Removes the `require_ci` guard in `Api::DeploysController#create` (`param_error!(:require_ci, ...) if params.require_ci && !commit.deployable?`) allowing a caller with only `deploy:stack` API permission to push through a deploy of a commit whose real CI never passed.
- Directly triggers an **unauthorized deploy** on stacks with `continuous_deployment: true`, since `Status#schedule_continuous_delivery` fires a `ContinuousDeliveryJob` whenever a commit transitions to `success` (validated in `test/models/commits_test.rb` lines 233-243).
- Also unblocks other commits gated by `blocking_statuses` (`Commit#blocked?`), and can similarly forge `push` events to trigger `GithubSyncJob` or `pull_request closed` events to archive review stacks belonging to an unrelated organization.

This satisfies the "unauthorized deploy" Critical impact criterion: the deploy pipeline is triggered/unblocked for a target stack the attacker does not otherwise have write access or CI control over, purely by exploiting the org-vs-repository binding mismatch in webhook processing.

### Likelihood Explanation
Requires only that the attacker control (or be a collaborator with push/webhook-trigger ability on) **any one** organization configured in a multi-org Shipit deployment — a materially lower bar than compromising the victim organization, the deploy host, or Shipit's own credentials. Multi-org configuration is an explicitly documented, supported feature (`docs/setup.md`), and commit SHAs are not secrets. No Shipit session, `ApiClient` token, or GitHub App private key for the *victim* org is needed.

### Recommendation
In `WebhooksController#verify_signature`, and in each `Handler#process`, cross-validate that the organization/owner used to select the verifying `GitHubApp`/`webhook_secret` matches the actual `owner` of the `Repository` record resolved from `repository.full_name` (or, for `StatusHandler`, scope the `Commit` lookup by `stack.repository` matched against the verified `repository_owner`, not by bare `sha` alone). Reject the webhook if these do not match.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled) and `OrgB` (victim), each with its own `webhook_secret`, per `docs/setup.md` "Using Multiple Github Applications".
2. Attacker obtains a valid signature for `OrgA` (e.g., by triggering a real GitHub webhook delivery from a repo they own in `OrgA`, or by knowing `OrgA`'s `webhook_secret` since they administer it).
3. Attacker crafts a JSON body:
```json
{
  "sha": "<known-sha-of-OrgB-victim-commit>",
  "state": "success",
  "context": "ci/circleci",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s `webhook_secret` over this exact body and POSTs it to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, verifies successfully against `OrgA`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — finds the victim commit in `OrgB`'s stack (no org check) — and creates a `success` `Status` on it, potentially unblocking `deployable?` and triggering `ContinuousDeliveryJob` for `OrgB`'s stack.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
