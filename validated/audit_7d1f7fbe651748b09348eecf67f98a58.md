### Title
AA payment messages for fixed-denomination assets are silently dropped while `state` accounting still executes - (File: `aa_composer.js`)

### Summary
When a triggered Autonomous Agent (AA) response includes a `payment` message that targets an asset with `fixed_denominations`, `aa_composer.js` silently removes that payment message from the outgoing response unit instead of failing/bouncing. Meanwhile the `state` formula that was already captured during oscript evaluation (and which typically assumes the payment succeeded, e.g. by decrementing a balance state var) is executed unconditionally via `executeStateUpdateFormula`, independent of whether the payment message survived the filtering. This mirrors the `_calcRewardIntegral` finding: a transfer silently fails/never happens, yet the accounting layer proceeds as if it did.

### Finding Description
During `handleTrigger`, the oscript template is evaluated and the `state` update formula is captured separately from the `messages` array: [1](#0-0) 

After evaluation, `aa_composer.js` filters `messages`, and specifically removes any `payment` message whose asset `fixed_denominations` is true, without generating any error: [2](#0-1) [3](#0-2) 

If this silent removal empties the `messages` array entirely, the code explicitly falls back to `handleSuccessfulEmptyResponseUnit(null)`, which still runs the state-update formula and persists the response as *successful*: [4](#0-3) 

More importantly, even when other messages remain (so the unit is still sent via `sendUnit`), `executeStateUpdateFormula` is invoked on the already-filtered `objUnit` at the very end of unit construction, completely decoupled from whether the fixed-denomination payment message that the oscript author intended to send actually made it into the unit: [5](#0-4) [6](#0-5) 

Because the `state` formula's locals/computed values were fixed at evaluation time (before the fixed-denomination filtering occurred), an oscript such as:
```
messages: [
  { app: 'payment', payload: { asset: "{$fixed_denom_asset}", outputs: [{address: "{trigger.address}", amount: "{$amount}"}] } },
  { app: 'state', state: `{ var[$key] = var[$key] - $amount; }` }
]
```
will decrement the user's tracked balance in AA storage even though the payment to that user for the fixed-denomination asset was silently dropped and never sent.

### Impact Explanation
This causes a genuine, permanent accounting discrepancy inside the AA's persistent state: the AA "books" a withdrawal/payout that never actually occurred. Coins that were supposed to leave the AA's balance for the user remain trapped in the AA (fund freezing for the user, or fund loss for the AA's declared internal accounting), and there is no way for the oscript author to detect or react to the silent drop since no error/bounce is raised. Any oscript that manages balances for a fixed-denomination asset (e.g. an indivisible/asset-of-fixed-denomination based bank/exchange AA) is exposed to this class of accounting corruption.

### Likelihood Explanation
Likelihood is Medium: it requires an AA to send payments in an asset with `fixed_denominations: true` and to compute its own accounting deltas in an accompanying `state` message assuming that payment succeeds — a realistic and encouraged pattern for AAs managing asset balances (as seen in the deposit/withdraw bank pattern in `test/samples/a_bank_without_percent.oscript`). Once such an AA is deployed, the condition triggers automatically and deterministically whenever an output is composed for a fixed-denomination asset, with no attacker interaction required beyond normal use.

### Recommendation
Before silently dropping `payment` messages for `fixed_denominations` assets, `aa_composer.js` should either:
- Reject/bounce the whole response (treat it as a hard error) instead of silently filtering the message out, so the `state` formula's assumed accounting changes are never persisted along with a dropped transfer, or
- Perform the fixed-denomination filtering earlier (before/along with capturing `objStateUpdate`) and expose the outcome to the oscript evaluation so the author's `state` formula can conditionally react to whether the payment output was actually retained.

### Proof of Concept
1. Deploy an AA whose response messages include a `payment` message to `trigger.address` using an asset defined with `fixed_denominations: true`, paired with a `state` message that unconditionally does `var[$balance_key] -= $amount;`.
2. Trigger the AA with a valid request that satisfies the `if` condition for this branch.
3. Observe in `aa_composer.js` (`sendUnit`) that the payment message is removed at line `1327`/`1356` due to `objAsset.fixed_denominations`, so no output is ever created for the user.
4. Observe that `executeStateUpdateFormula` still runs (either via `handleSuccessfulEmptyResponseUnit` if no messages remain, or later in `sendUnit` if other messages remain), decrementing the AA's tracked balance state var as though the transfer succeeded — permanently desynchronizing the AA's internal accounting from its real token balance.
