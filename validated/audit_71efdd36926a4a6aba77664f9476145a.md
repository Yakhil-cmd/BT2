### Title
Cross-organization webhook signature confusion allows forging commit statuses and sync events for any stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using fields taken from the *attacker-controlled JSON body* (`repository.owner.login` or `organization.login`), while the handlers that actually act on the payload (`Handler#stacks`, and especially `StatusHandler#process`) select the target repository/commit using a *different* field of the same payload (`repository.full_name`, or no repository scoping at all). This breaks the binding "organization that authenticated == repository that is written," analogous to the `smFeePercentage`/`previousSmFeePercentage` cache-confusion bug where two logically-coupled values are allowed to diverge across the same operation.

### Finding Description
`verify_signature` picks the GitHub App config (and therefore the `webhook_secret` used for HMAC validation) from the payload itself: [1](#0-0) [2](#0-1) 

Once the signature is verified for whatever organization the payload *claims* to belong to (`repository.owner.login` / `organization.login`), the raw payload is dispatched unmodified to the registered handlers: [3](#0-2) 

The base `Handler` resolves which `Stack`/`Repository` to operate on using a *separate* field, `repository.full_name`: [4](#0-3) 

`PushHandler` then triggers `stack.sync_github` on whatever stack matches that `full_name`: [5](#0-4) 

`StatusHandler` is worse: it does not scope by repository/stack at all, it matches purely on commit SHA across the *entire* Shipit instance: [6](#0-5) 

Because `repository.owner.login` (used for signature/secret selection) and `repository.full_name` (used for targeting, in `PushHandler`) or nothing at all (in `StatusHandler`) are two independent, unauthenticated fields inside the same signed JSON blob, nothing ties them together. Any organization/repository that is legitimately registered in this Shipit instance and can trigger (or replay) a validly-signed webhook for its own `webhook_secret` can set `repository.owner.login`/`organization.login` to its own org (so the signature check passes against its own secret) while setting `repository.full_name` (for push/sync) — or simply providing a target `sha` (for status) — to point at a *different* organization's stack/commit.

This is the same class of bug as the reported `smFeePercentage` issue: a value that is supposed to be re-derived/consistent with another value on every call is instead taken from two independently-controllable inputs, so the "authorized" side (organization whose secret validated the request) and the "acted-upon" side (repository/commit actually mutated) can diverge.

### Impact Explanation
Via `StatusHandler`, an attacker who controls a webhook for any registered organization on the Shipit instance can forge a "success" CI status (e.g. `ci/travis`, or whatever `required_statuses`/`ci.require` context the victim stack uses) on a victim commit belonging to a completely unrelated stack/repository, since the lookup is `Commit.where(sha: params.sha)` with no repository scoping. A required-status check that gates deploys (`ci.require` in `shipit.yml`) can thus be satisfied fraudulently, enabling an **unauthorized deploy** of a commit that never actually passed CI — matching the Critical impact bar ("unauthorized deploy"). Via `PushHandler`, cross-organization signature confusion can trigger `sync_github` with an attacker-chosen `expected_head_sha` against another stack, which is a lower-severity nuisance/cache-poisoning vector but still a cross-repository write into state that does not belong to the authenticating organization.

### Likelihood Explanation
Exploitation requires the attacker to control (or have configured) a `webhook_secret` for at least one organization/repository already registered on the shared Shipit instance — i.e., they must be a legitimate tenant able to send validly-signed requests to the webhook endpoint for their own org, but with an unrelated victim org/stack/commit also present on the same instance. This is realistic for any multi-tenant Shipit deployment (the documented `config/secrets.*.yml` supports multiple `github:` orgs each with their own `webhook_secret`). No `ApiClient` token, GitHub App private key, or `Shipit` session is required — only a self-controlled webhook secret for one tenant — so this does not fall under the excluded "requires webhook_secret access" case (the attacker's own secret, not the victim's, is used).

### Recommendation
Bind the signature-verification organization to the repository actually acted upon: after selecting the GitHub App/secret via `repository_owner`, verify that every repository-identifying field used downstream (`repository.full_name`, and any `sha` lookup) is scoped to a `Repository`/`Stack` that belongs to that same verified `repository_owner`. In `StatusHandler`, scope `Commit.where(sha: params.sha)` by the repository resolved from the verified webhook organization instead of matching bare SHA across the entire instance. In `Handler#stacks`, cross-check that `payload.dig('repository','owner','login')` (used for signature selection) matches `payload.dig('repository','full_name')`'s owner segment before trusting it.

### Proof of Concept
1. Register two tenants on the same Shipit instance: `orgA` (attacker-controlled, has its own `webhook_secret`) and `orgB` (victim, has an existing Stack tracking commit SHA `abc123` that is not yet CI-approved and has `ci.require: ["ci/travis"]`).
2. Attacker crafts a JSON body:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/attacker-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `orgA`'s own known `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s GitHub App config, and successfully verifies the signature (attacker knows this secret). [7](#0-6) 
5. `StatusHandler#process` runs `Commit.where(sha: "abc123")`, finds the `orgB` commit (unrelated to `orgA`), and calls `create_status_from_github!`, injecting a fake "ci/travis success" status onto `orgB`'s stack. [6](#0-5) 
6. `orgB`'s commit now satisfies `ci.require`, and can be deployed even though CI never actually passed — an unauthorized deploy path opened purely by cross-tenant signature/target confusion.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
