### Title
Stale delegate grants reactivate when an account NFT returns to its original owner - (File: contracts/controller/src/storage/account.rs)

### Summary
The controller stamps each delegate list with `granted_by` owner and treats ownership changes as invalidating prior grants, but it never deletes the stale `ControllerKey::Delegates` entry on NFT transfer. If the position NFT leaves owner A and later returns to A, a delegate A granted before the transfer silently regains full owner-equivalent spending authority over the account — including `withdraw` to an arbitrary recipient and `borrow` — without any fresh consent. This mirrors the incident class (a compromised/previously-trusted actor exercising destructive control over an account it should no longer reach).

### Finding Description
`get_delegates` only filters grants by `granted_by == owner` and returns them; the comment acknowledges "Ownership changes invalidate a previous owner's grants without deleting them" (`contracts/controller/src/storage/account.rs:174-181`). The only path that actually removes a stale grant is `remove_delegate`, whose own comment admits the purpose: "Deletes stale grants but returns false, preventing those grants from reactivating if the NFT returns to their original owner" (`contracts/controller/src/storage/account.rs:223-238`). That cleanup runs only if a subsequent owner happens to call `remove_delegate` (or `add_delegate`, which overwrites the entry). If the intermediate owner never touches delegates, the A-stamped `DelegateGrant` persists.

After NFT transfer A → B → A, `account_owner` resolves to A again, so `is_owner_or_delegate` loads `get_delegates(env, account_id, A)`, finds `granted_by == A`, and admits the old delegate (`contracts/controller/src/account.rs:115-127`). The test `transfer_revokes_prior_owner_and_delegates` (`contracts/controller/tests/helpers/account.rs:387-433`) verifies only the A→B leg; it never exercises B→A, so the reactivation gap is untested. Once reactivated, the delegate passes `require_owner_or_delegate` on `withdraw`, `borrow`, `swap_collateral`, `repay_debt_with_collateral`, etc., and `process_withdraw` allows `to` to be any external recipient (`contracts/controller/src/positions/supply.rs:150-155`).

### Impact Explanation
A delegate (active position manager) that was legitimately granted once, then later turns malicious or is compromised — exactly the incident's compromised-credential shape — can drain all collateral and borrow up to the account's LTV after the NFT returns to the original owner, routing proceeds to itself via `withdraw(..., to: Some(attacker))` and `borrow(..., to)`. This is theft of user funds on any account that round-trips ownership (sale and buyback, OTC transfer chains, custody migrations).

### Likelihood Explanation
Medium. Exploitation requires (a) the target owner previously delegated to the attacker, (b) the attacker still holds `is_active` manager status, and (c) the NFT returns to the original owner without any intermediate owner calling `add_delegate`/`remove_delegate`. No owner signature is needed at exploit time. The conditions are narrow but plausible and entirely silent — the account owner receives no event and no re-consent prompt.

### Recommendation
Invalidate delegate grants on ownership change rather than relying on lazy cleanup: clear `ControllerKey::Delegates(account_id)` whenever the NFT owner changes (e.g., on the controller-side owner resolution path or via an NFT transfer hook), or include an owner epoch in the grant key so a grant can never match a later ownership tenure even for the same address.

### Proof of Concept
1. Owner A holds account `id`; governance lists M as active position manager. A calls `add_delegate(A, id, M)` — `DelegateGrant{granted_by: A, delegates: [M]}` stored.
2. A transfers NFT `id` to B (`position_nft::transfer(A, B, id)`). Grants are now filtered out but remain in storage.
3. B never calls `add_delegate`/`remove_delegate`; B transfers NFT back to A.
4. `account_owner(id) == A`; `is_owner_or_delegate(id, M, A)` returns `true` because `grant.granted_by == A`.
5. M calls `withdraw(M, id, [collateral legs], to: M)` and `borrow(M, id, ..., to: M)`, draining the account without any authorization from A in the current ownership tenure.
