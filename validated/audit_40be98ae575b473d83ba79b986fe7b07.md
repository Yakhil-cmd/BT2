### Title
Unauthenticated read of live task/deploy stream via `/events` mount bypassing `force_github_authentication` - (File: config/routes.rb)

### Summary
The engine mounts `Pubsubstub::StreamAction.new` directly as a Rack application at `/events` rather than routing to a Shipit controller action. Because `Shipit::Authentication#force_github_authentication` is a `before_action` defined on `Shipit::ApplicationController` (via the `Authentication` concern) and only runs inside the ActionController filter chain, a request routed to a raw mounted Rack app never enters that filter chain and never executes the check.

### Finding Description
The claimed binding is: `response_for_GET(/events?channel=X) == response_for_GET(/events?channel=X) AFTER force_github_authentication(current_user) passed`. In other words, every response containing stack/task/deploy event data was supposed to be gated by `current_user.authorized?` (or at least `current_user.logged_in?`/`Shipit.authentication_disabled?`) as enforced in [1](#0-0) .

The route table shows: [2](#0-1) 

`mount` in Rails routes attaches an arbitrary Rack endpoint directly into the middleware/dispatch stack for that path — it is not dispatched as a Shipit controller action, so it never runs `Shipit::ApplicationController`'s `before_action :force_github_authentication` (included via `Shipit::Authentication`) at [3](#0-2) . There is no other controller, middleware, or route constraint in `config/routes.rb` wrapping this mount with an authentication check — no `constraints:`, no custom middleware insertion for this path is present.

`Pubsubstub::StreamAction` (a third-party gem app) itself has no notion of Shipit sessions, `current_user`, or `authorized?`; it simply streams events for whatever `channel` parameter is supplied in the request. Since stack event channels are derived from predictable/enumerable identifiers (stack `owner/repo/environment` triples, which are also the public `stack_id` route format used everywhere else, e.g. `stack_id_format = %r{[^/]+/[^/]+/[^/]+}}` at [4](#0-3) ), an attacker can guess or enumerate a target stack's channel name and open a stream with **no session cookie, no `Shipit.github_teams` membership, and no `authorized?` check**, before the request ever reaches any Shipit-authored authentication code.

Existing guards checked and found not applicable here: `force_github_authentication`, `User#authorized?`, and `require_permission!` only apply to controller actions under `Shipit::ApplicationController`; `verify_signature`/`GitHubApp#verify_webhook_signature` are unrelated (webhook path); `ExplicitParameters` schemas are unrelated. None of them wrap the `mount Pubsubstub::StreamAction.new, at: "/events"` route.

### Impact Explanation
An unauthenticated attacker can subscribe to the live event stream for any stack whose channel/identifier they can guess (stack identifiers follow the public, guessable `owner/repo/environment` scheme used throughout the app), obtaining real-time task and deploy state (status changes, log/output events, deploy lifecycle) without ever authenticating. This matches the "High" category: unauthenticated read of stack state, task streams, or deploy output. It is fully repeatable against arbitrary stacks/tenants hosted by the same Shipit instance, since the same unauthenticated Rack mount serves all channels.

### Likelihood Explanation
No privileged access, secrets, or GitHub credentials are required — only knowledge or a guess of the target stack's identifier, which is often discoverable from the Shipit UI URLs, GitHub org/repo names, or brute-forcing common environment names (`production`, `staging`, etc.). The attack is a single unauthenticated HTTP GET to `/events?channel=...`, making it low-cost and highly repeatable.

### Recommendation
Do not mount `Pubsubstub::StreamAction` as a bare Rack app on the engine's route table. Instead, wrap it in a Shipit controller action (subclassing `Shipit::ApplicationController`) so `force_github_authentication`/`authorized?` runs before streaming, and additionally verify the requested channel belongs to a stack the authenticated user is authorized to view before delegating to `Pubsubstub::StreamAction`.

### Proof of Concept
Add a minitest integration test under `test/` (e.g. `test/integration/events_stream_authentication_test.rb`, not shown here since it's out-of-scope path but described for the PoC):
1. Load fixture stack (e.g. `shipit_stacks(:shipit)`), compute its known event channel.
2. Issue `get "/events", params: { channel: <stack_channel> }` with no session (`session[:user_id]` unset, no `current_user` set).
3. Assert response is **not** a redirect to `github_authentication_path` and **not** `403 Forbidden` — i.e. assert `response.status == 200` (or streaming `Content-Type: text/event-stream`), demonstrating that `force_github_authentication`/`authorized?` never executed for this path, in contrast to the same assertion made against any real Shipit controller action (e.g. `get stack_path(stack)`) which does redirect/403 under the same unauthenticated conditions.

    module ClassMethods
      def skip_authentication(*args)
        skip_before_action(:force_github_authentication, *args)
      end
    end

    private

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
