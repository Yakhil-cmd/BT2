### Title
Webhook signature is verified against the organization inferred from `repository.owner.login`, while the stack/team that gets written is looked up from a different, independently attacker-controlled field in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
The bug class in the report is: a value used to compute one part of a protocol invariant (`bidClaim.paid`) is not the same value used for the corresponding check elsewhere (`purchased_ - refund`), so two logically-linked fields silently diverge, breaking a trust equality. In Shipit's webhook pipeline the analogous binding is: **`organization that authenticated (via HMAC secret lookup)` MUST equal `organization that owns the repository/team actually written`.** These are computed from two independently-controlled fields of the same attacker-supplied JSON body, and the engine never checks that they agree.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to verify the HMAC against using a field pulled straight out of the unauthenticated body: [1](#0-0) [2](#0-1) 

That is: `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`. This value is only used to pick *which secret* to HMAC-check against; multi-tenant Shipit installs configure one `webhook_secret` per organization: [3](#0-2) 

Once the signature validates against organization A's secret, `WebhooksController#create` hands the *entire raw body* to the handlers — none of which re-check that the fields they act on belong to the same organization that owns the secret used for verification: [4](#0-3) 

- `Handler#stacks` resolves the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — a completely separate field from `repository.owner.login` used for signature routing: [5](#0-4) 
- `Repository.from_github_repo_name` blindly splits that string into owner/name and looks up any repository configured in the shared instance, with no relation to the verified organization: [6](#0-5) 
- `MembershipHandler#find_or_create_team!` similarly trusts `params.organization.login` (independent from the signature-selection field when the `repository` key is absent, but still just body content) to create/attach a `Team`, and then adds/removes arbitrary `User` records from that team: [7](#0-6) 

Because a genuine, weaker-privileged organization owner who has legitimately onboarded their own org/app into a shared multi-tenant Shipit instance knows their **own** `webhook_secret`, they can produce a request that passes `verify_signature` (keyed off `repository.owner.login` = their own org) while setting `repository.full_name` / `organization.login` inside the same signed body to point at a **different** organization's repository or team that is also configured in the same Shipit instance. The engine has no code path that cross-checks "the org whose secret validated this HMAC" against "the org whose stack/team this payload will mutate" — it is the same class of missing equality as `bidClaim.paid` vs. `purchased_ - refund` in the referenced report: two values that are supposed to always match are instead independently taken from attacker input.

### Impact Explanation
An attacker who legitimately controls webhook credentials for their own onboarded organization can forge events that mutate state belonging to a different organization's stacks/teams in the same shared Shipit deployment:
- `PushHandler#process` triggers `stack.sync_github` for a foreign stack.
- `StatusHandler#process` injects arbitrary commit statuses (`create_status_from_github!`) against any commit `sha` regardless of which org actually owns that commit/stack — this can be used to fabricate a passing CI status Shipit relies on to gate merges/deploys.
- `CheckSuiteHandler#process` schedules check-run refreshes for foreign stacks.
- `MembershipHandler#process` creates/attaches an arbitrary `Team` and adds/removes `User` records from it; since `User#authorized?` checks membership against `Shipit.github_teams` (globally configured team IDs), this can escalate into `Shipit.github_teams` authorization if the forged team ID collides with (or is later configured as) one of the authorizing teams.

This matches the "High" bar in the rules: escalation into `Shipit.github_teams` authorization and unauthorized writes/deploy-gating status forgery across repositories that are not the attacker's own.

### Likelihood Explanation
This requires the Shipit instance to be configured for **multiple** organizations (as shown by `config/secrets.development.shopify.yml` supporting several org keys, each with its own `webhook_secret`) and requires the attacker to already control a valid webhook secret for at least one onboarded organization — which is the normal, unprivileged level of access such an org owner has. No repository write access, GitHub App private key, or Shipit session is required; only knowledge of a secret the attacker's own organization was issued. The binding break is deterministic and requires no timing/race conditions, only that the JSON body's routing field (`repository.owner.login`/`organization.login`) differs from the field consumed by the handler (`repository.full_name`/`organization.login` used to create global `Team` records).

### Recommendation
After `verify_signature` succeeds, thread the verified organization through to the handler layer and assert equality before any state mutation: reject (422) if `payload.dig('repository','full_name')`'s owner segment does not case-insensitively match `repository_owner`, and reject `membership` events whose `organization.login` doesn't match the org whose secret validated the signature. This restores the single source of truth (`repository_owner` established during signature verification) as the only value handlers are allowed to act on for organization-scoped writes.

### Proof of Concept
1. Configure Shipit for two organizations, `org-a` (attacker-controlled, `webhook_secret: SECRET_A`) and `org-b` (victim, has a `Stack` for `org-b/private-repo`), per `config/secrets.*.yml` schema shown in `config/secrets.development.shopify.yml`.
2. Attacker (owner of `org-a`) computes `X-Hub-Signature: sha1=HMAC(SECRET_A, body)` over a crafted `status` event body where:
   - `repository.owner.login = "org-a"` (so `WebhooksController#verify_signature` looks up and validates against `SECRET_A`).
   - `repository.full_name = "org-b/private-repo"`, `sha = <target commit sha>`, `state = "success"`.
3. POST to `/github/webhooks` (routed to `WebhooksController#create`) with that body and signature.
4. `verify_signature` passes (`Shipit.github(organization: "org-a")` verifies HMAC against `SECRET_A`, which matches). `StatusHandler#process` then resolves commits via `stacks` → `Repository.from_github_repo_name("org-b/private-repo")` and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status onto `org-b`'s commit despite the attacker never having any credential or access tied to `org-b`.
