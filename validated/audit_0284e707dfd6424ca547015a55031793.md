### Title
Unhandled length-assumption exception in c-hash decoding via `isValidAddressAnyCase` - ([File: chash.js])

### Summary
`chash.isChashValid()` only wraps the base32/base64 **decode** step in a `try/catch`; the subsequent bit-level checksum-separation step assumes the decoded buffer is exactly 160 or 288 bits and `throw`s a raw, unguarded `Error` otherwise. `isValidAddressAnyCase()` (used for case-insensitive address matching) reaches this code without the character-set pre-filter that `isValidAddress()` applies, so a 32-character string containing bytes/characters outside the base32 alphabet can reach `base32.decode()` and yield a buffer whose bit-length is not 160/288, triggering the unguarded `throw`.

### Finding Description
`isChashValid(encoded)` in `chash.js` only checks `encoded.length` (32 or 48) before decoding: [2](#0-1) 

The `try/catch` there covers only `base32.decode(encoded)` / `Buffer.from(encoded, 'base64')`. Everything downstream — `buffer2bin`, and critically `separateIntoCleanDataAndChecksum` — is called unguarded: [3](#0-2) 

`separateIntoCleanDataAndChecksum` explicitly assumes the decoded bit-length is exactly 160 or 288 and `throw`s a plain `Error("bad length=...")` for any other length. This is analogous to the mp3gain bug class: a length/bounds assumption baked into a low-level decode routine, exercised on attacker-supplied bytes without a bounds/format check at the point of use.

The gate that is supposed to prevent malformed input from reaching this code is the regex check in `isValidAddress()`: [4](#0-3) 

But `isValidAddressAnyCase()` — used for case-insensitive comparisons — omits this regex and only checks the string length: [5](#0-4) 

This means a 32-character string with characters outside `[A-Z2-7]` (case-insensitively) can flow straight into `base32.decode()`. Depending on how the `thirty-two` decoder handles invalid symbols (silently skipping/truncating vs. producing a shorter/mis-aligned buffer), the resulting byte buffer's bit-length can end up different from 160/288, hitting the unguarded `throw` in `separateIntoCleanDataAndChecksum`.

### Impact Explanation
An uncaught exception thrown deep inside a hashing/decoding helper, if it escapes any wrapping validation `try/catch` (e.g., because it fires inside an asynchronous DB-callback context where Node.js does not propagate exceptions back to a synchronous caller's `try/catch`), becomes an uncaught exception in the Node.js event loop and crashes the process. Since address validation (in either case-sensitive or case-insensitive form) is on the path of validating every posted unit, definition, and payment output, a single unprivileged unit poster who can get a case-insensitive address check to run against a malformed address string could cause a full node crash — a denial of service preventing the network from processing/confirming further units, matching the "network unable to confirm new units" impact class in scope.

### Likelihood Explanation
Likelihood is moderate but I was not able to fully confirm within the available tool budget (a) the exact call site(s) in `validation.js`/`definition.js` that invoke `isValidAddressAnyCase()` with unit-controlled input, and (b) whether every such call site itself sits inside a broader `try/catch` that would convert the thrown `Error` into a normal validation failure instead of an uncaught crash, and (c) the precise behavior of the third-party `thirty-two` base32 decoder on out-of-alphabet input (whether it ever actually yields a non-160/288-bit buffer). These are the key unresolved points that would need to be verified in a full session (with the actual runtime and the `thirty-two` package source) before this can be treated as a confirmed, exploitable DoS rather than a plausible-but-unconfirmed structural weakness.

### Recommendation
- Wrap the entire body of `isChashValid()` (not just the decode call) in the `try/catch`, so any downstream `throw` (from `separateIntoCleanDataAndChecksum`, `mixChecksumIntoCleanData`, etc.) is converted to a `return false` instead of propagating.
- Make `isValidAddressAnyCase()` validate the character set (case-insensitive base32 alphabet) before calling `isChashValid()`, consistent with `isValidAddress()`.
- Audit all call sites of `isValidAddressAnyCase` / `isChashValid` to confirm they are not invoked inside asynchronous callbacks without a surrounding `try/catch`, since Node.js does not propagate synchronous throws across the event loop boundary back to the original caller's `try/catch`.

### Proof of Concept
Conceptual PoC (unverified end-to-end due to inability to run code in this session):
1. Construct a 32-character string that is not a valid base32 (`[A-Z2-7]`) string but has length 32, e.g., contains lowercase letters or symbols outside the alphabet.
2. Trigger a code path where an unprivileged unit poster's address (or an address referenced in an AA formula/oscript "case-insensitive" comparison, if such a path exists) is checked via `isValidAddressAnyCase()`.
3. If the `thirty-two` decoder does not throw but returns a buffer whose bit length is not 160, `separateIntoCleanDataAndChecksum()` throws `Error("bad length=...")` uncaught by `isChashValid()`'s `try/catch`, potentially propagating to an uncaught exception if the enclosing call stack has no further guard.

Given the unresolved verification points above, this should be treated as a plausible analog requiring confirmation (exact call sites and decoder behavior) rather than a fully proven exploit chain.
