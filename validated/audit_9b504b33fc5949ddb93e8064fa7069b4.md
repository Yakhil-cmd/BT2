### Title
Unhandled exceptions in the AA trigger-processing loop permanently halt MCI stabilization for the entire node - (File: aa_composer.js)

### Summary
`handleAATriggers` pulls all pending AA triggers from the `aa_triggers` table and processes them strictly in order with `async.eachSeries`, delegating each one to `handlePrimaryAATrigger` → `handleTrigger`. This mirrors the Notional bug pattern: a mandatory "hook" that is invoked automatically on every core state-transition (there: SetToken issue/redeem; here: every MCI stabilization) iterates over a list of items and calls a function that can `throw Error` on invariant violations. If any single item in the list triggers such a throw, the exception is not caught anywhere in the async chain, so it propagates up out of `mutex.lock`/`db.query` callbacks and crashes the node process before the trigger's row is deleted from `aa_triggers`. On restart, the exact same trigger is selected again (deterministic ORDER BY) and the crash repeats — an infinite loop that halts all subsequent AA execution and, because `handleAATriggers` is invoked synchronously from `main_chain.js`'s MCI-stabilization path, halts main-chain stabilization for the entire node.

### Finding Description
`handleAATriggers` reads every pending trigger and processes them one-by-one via `async.eachSeries`: [1](#0-0) 

Only after `handlePrimaryAATrigger` finishes successfully is the corresponding row removed from `aa_triggers`: [2](#0-1) 

Inside the trigger-handling call chain, several conditions cause an unrecoverable `throw Error`, not a graceful `bounce`/`revert`:
- If a trigger's stabilized unit is somehow missing from the in-memory stable-units cache: `throw Error("handlePrimaryAATrigger: unit ${unit} not found in cache")` [3](#0-2) 
- If a parameterized AA's `base_aa` cannot be resolved at trigger-execution mci: `throw Error("base AA not found: " + template.base_aa)` [4](#0-3) 
- If the AA's balances row is missing when initializing balances for a trigger: `throw Error("AA not found? " + address)` [5](#0-4) 
- Batch-write failures: `throw Error("AA composer: batch write failed: "+err)` [6](#0-5) 

None of these throws are wrapped in try/catch anywhere in the call stack (`handleAATriggers` → `handlePrimaryAATrigger` → `handleTrigger`), so any one of them is a fatal, process-crashing exception, exactly like an unhandled `revert` bubbling out of a hook that Solidity/EVM callers cannot recover from.

`handleAATriggers` is not an isolated maintenance task — it is called synchronously as the direct continuation of every MCI stabilization: [7](#0-6) [8](#0-7) 

This is structurally identical to the reported bug class: a mandatory, automatically-invoked function loops over a set of items (fCash positions there, queued AA triggers here) and an unhandled failure on any single item stops the whole batch — except here the blast radius is worse, because the failing item is never removed from the queue (the DB row is deleted only on success), so the failure recurs deterministically forever on every restart, and because the hook is on the critical path of consensus (main-chain stabilization), not merely of one token's issuance/redemption.

### Impact Explanation
Once a trigger reaches this state, the node can never advance past it: `handleAATriggers` re-selects the same (unit, mci, address) row on every call because it is ordered deterministically by `(mci, level, unit, address)` and the failing row is still present, so it crashes again immediately after restart. Since this code runs as part of `markMcIndexStable`/`stabilizeMci`, MCI stabilization for the node cannot proceed past the affected MC index. All full nodes are running the same deterministic logic against the same data, so if the divergent state is reachable by consensus data (not merely local caches on one node), every node reaching that MCI would hit the same crash — freezing the ability of the network to confirm new units and advance stability, and stranding all AA balances/funds that depend on triggers queued at or after that point. This satisfies the "network unable to confirm new units" and "AA fund loss or freezing" impact bar.

### Likelihood Explanation
The concrete conditions that can flip one of these invariant checks (e.g., a parameterized AA whose `base_aa` is resolvable via `storage.readAADefinition(conn, template.base_aa, mci, ...)` at definition-validation time but not at a different trigger-execution `mci`, per the mci-bound lookup at line 436) require a specifically crafted AA definition rather than everyday usage, so likelihood is lower than an every-request occurrence, but it is fully reachable by an ordinary AA author posting a definition and any user sending a trigger to it — no privileged role, node compromise, or network-level attack is needed. The severity of the consequence (permanent, self-repeating node crash blocking stabilization) makes this worth flagging even at moderate likelihood.

### Recommendation
- Wrap `handlePrimaryAATrigger`/`handleTrigger` execution in `handleAATriggers` with error isolation so that a single bad trigger cannot crash the node; catch exceptions per-trigger and convert internal invariant violations into a deterministic bounce (as already done for normal AA formula errors via `revert`/`bounce`) rather than a raw `throw`.
- Do not leave an unprocessable trigger permanently in `aa_triggers`; either remove/quarantine a trigger that fails with a deterministic internal error after logging it, or add a retry cap that surfaces the problem without perpetually crashing the node.
- Audit all `throw Error(...)` call sites reachable from `handleTrigger`/`handlePrimaryAATrigger` (e.g., "base AA not found", "AA not found? address") to ensure they can only be reached by conditions that are impossible by construction (e.g., re-validate `base_aa` resolution using the same mci semantics at both AA-definition-validation time and trigger-execution time), or convert them into recoverable bounces.

### Proof of Concept
1. An AA author posts a parameterized AA definition (`{ base_aa: X, params: {...} }`) that passes `validateAADefinition`/definition-time checks referencing `base_aa = X`.
2. Due to the mci-bound resolution difference between definition validation and `storage.readAADefinition(conn, template.base_aa, mci, ...)` used at trigger time (`aa_composer.js:436`), a trigger sent to this AA at a later `mci` fails to resolve `base_aa`, hitting `throw Error("base AA not found: " + template.base_aa)`.
3. This throw occurs inside the `async.eachSeries` callback chain started in `handleAATriggers` (`aa_composer.js:71-86`), which is not wrapped in any try/catch, crashing the node process before the `DELETE FROM aa_triggers` at `aa_composer.js:102` ever runs.
4. On restart, `handleAATriggers` is invoked again as part of MCI stabilization (`main_chain.js:1691-1723`), re-selects the same trigger row (still present, still first in deterministic order), and crashes again — permanently blocking further stabilization and AA execution on that node.
