## Title
Unhandled null-pointer dereference crash when evaluating `unit[...]` on a purged `temp_data` message - (File: formula/evaluation.js)

### Summary
The CVE describes a NULL pointer dereference in libde265's `ff_hevc_put_weighted_pred_avg_8_sse` that a crafted input file can trigger, crashing the process (DoS). The closest reachable analog in ocore is in the `unit[...]` selector of the oscript/AA formula evaluator, where a message's `payload` is dereferenced without a null check, which can be forced to be `undefined` by posting a specially-crafted unit.

### Finding Description
In the AA formula evaluator, when a formula does `unit[<hash>]`, the code reads the referenced unit from storage and then unconditionally does:
```js
for (let m of objUnit.messages)
    if (m.app === "temp_data")
        delete m.payload.data; // delete temp data if it is not purged yet
``` [1](#0-0) 

This assumes every `temp_data` message still has a `payload` object. However, `temp_data` payloads can be purged from storage after `constants.TEMP_DATA_PURGE_TIMEOUT`, and/or a unit can validly carry a message with `payload_location` other than `"inline"` (in which case no `payload` field is stored at all — only `payload_hash`), per the general per-message validation rules in `validate()`: [2](#0-1) 

Once such a unit is stable and referenced by `unit['<hash>']` inside any AA's oscript formula (the referenced unit does not have to be authored by the same address — any stable, good-sequence unit reachable via `storage.readJoint` qualifies), `objUnit.messages` will contain a `temp_data` message object without a `payload` property. The subsequent `delete m.payload.data` then throws `TypeError: Cannot convert undefined or null to object` / "Cannot use 'in' operator" style error, because `m.payload` is `undefined`.

This is directly analogous to the CVE's root cause: a validated/parsed but incompletely-populated data structure (missing field) is dereferenced without a null check in a code path that processes attacker-influenced input (the formula author controls which unit is referenced, and the referenced unit's message content/purge status is externally influenced by other posted temp_data units).

### Impact Explanation
The `unit[...]` evaluation path runs during (a) AA trigger execution (`aa_composer.handleTrigger`) when the AA formula is evaluated for every node processing the trigger, and (b) the pre-broadcast "dry run" of AA triggers performed by `network.js` when accepting a posted unit that pays to an AA address: [3](#0-2) 
An uncaught `TypeError` thrown inside this synchronous, non-try/catch-wrapped code will propagate up as an uncaught exception. In `network.js`, `process.on('uncaughtException')` deliberately re-throws to crash the node process: [4](#0-3) 
Because every full node independently evaluates the same AA trigger/formula when the referencing unit becomes stable, a single crafted unit (temp_data message with purged/absent payload, plus an AA whose formula references it via `unit[...]`) can crash all full nodes that process/execute that trigger, producing a synchronized denial-of-service that prevents the network from confirming new units built on that AA's responses — a node-disagreement/confirmation-halting impact, not merely a single-node inconvenience.

### Likelihood Explanation
An unprivileged AA author can craft the oscript trivially (`unit['<hash>']`), and any user (or the same attacker) can post a `temp_data` message that will be purged or omitted from storage after the timeout, or use `payload_location: "none"` for a `temp_data` message that never had payload data. No special privileges, hub/light-vendor access, or protocol-level trust is required — only a normal posted unit and an AA trigger, both attacker-controlled from an ordinary wallet/AA-poster role.

### Recommendation
Guard the dereference with a null check before deleting the field, e.g.:
```js
for (let m of objUnit.messages)
    if (m.app === "temp_data" && m.payload)
        delete m.payload.data;
```
Additionally, audit other unconditional `.payload.<field>` accesses on `objUnit.messages` reached through `storage.readJoint`/`unit[...]` evaluation for the same missing-payload class of bug (e.g., messages with non-inline `payload_location`), and wrap the whole `ifFound` callback body in a try/catch that reports a formula error instead of letting the exception escape to `process.on('uncaughtException')`.

### Proof of Concept
1. Post ordinary unit A containing a `temp_data` message either (a) with `payload_location: "none"` (no `payload` field at all, only `payload_hash`) or (b) with an `inline` payload that gets purged from local storage after `TEMP_DATA_PURGE_TIMEOUT`. Let unit A stabilize.
2. Define/trigger an AA whose oscript formula contains `unit['<hash-of-A>']` (or any expression that forces evaluation of that `unit[]` selector, e.g. `$x = unit['<hash-of-A>'].unit;`).
3. Send a trigger to the AA (or have any peer send a unit paying the AA, which forces `network.js`'s dry-run trigger evaluation before acceptance).
4. On the node executing the trigger/dry-run, `storage.readJoint` returns unit A's joint with the `temp_data` message lacking `payload`; the loop `delete m.payload.data` throws a `TypeError`.
5. The exception propagates uncaught; `network.js`'s `uncaughtException` handler logs it and re-throws, crashing the node process — a reproducible, remotely-triggerable DoS. (Exact crash-vs-caught behavior in the AA composer path was not independently traced end-to-end in this analysis and should be confirmed by a background agent with a live/test node, since some intermediate AA composer wrappers may or may not catch synchronous throws from formula evaluation before they reach the top-level `uncaughtException` handler.)
