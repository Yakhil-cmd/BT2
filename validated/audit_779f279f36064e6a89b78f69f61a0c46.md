## Finding

### Title
CCMenuController bypasses stack-scoped ApiClient authorization, allowing a token scoped to one stack to read deploy status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController` enforces that a stack-scoped `ApiClient` token can only see the stack it is bound to, but `Api::CCMenuController` overrides the `stack` lookup method with an unscoped lookup, breaking that binding for its `#show` action.

### Finding Description
`Api::BaseController` centralizes record-level authorization for API tokens through the `stacks`/`stack` helper methods: [1](#0-0) 

`stacks` restricts the visible `Stack` set to `current_api_client.stack_id` when the token is scoped to a specific stack, and `stack` resolves the requested record only from that restricted set. This is the same pattern relied on by `StacksController`, `CommitsController`, etc., and is explicitly covered by the test "an api client scoped to a stack will only see that one stack": [2](#0-1) 

That the `ApiClient` model supports per-stack scoping is confirmed by the fixture and the `belongs_to :stack, optional: true` association: [3](#0-2) [4](#0-3) 

`Api::CCMenuController`, however, defines its own `stack` method that bypasses this scoping entirely, resolving the requested stack from the full, unrestricted `Stack` relation: [5](#0-4) 

The class only checks the coarse-grained operation permission via `require_permission :read, :stack`: [6](#0-5) [7](#0-6) 

`check_permissions!` only verifies that `"read:stack"` is in the token's `permissions` array — it never checks `stack_id`. The record-level restriction to a specific stack is solely implemented by `BaseController#stacks`/`#stack`, exactly the method `CCMenuController` overrides.

Equality that should hold: `stack authorized by token (current_api_client.stack_id)` == `stack actually rendered by #show`. Before the override (as in `StacksController`), this holds because `stack` is derived from the scoped `stacks` relation. In `CCMenuController`, `stack` is derived from `Stack.from_param!(params[:stack_id])` directly — any `stack_id` param is accepted regardless of `current_api_client.stack_id`, breaking the equality: a token scoped to stack A can fetch CCMenu status for stack B just by changing `stack_id` in the request.

### Impact Explanation
A holder of a legitimately-issued, narrowly-scoped `read:stack` `ApiClient` token (the exact minimal-privilege credential the application issues for the CCMenu integration, see `CCMenuUrlController`) can read deploy status (`last_deploy`, running/lock state, latest build result) of any stack in the installation, not just the one their token authorizes. This is an authorization escalation that lets an unprivileged/scoped credential obtain unauthenticated (for that target) read access to another stack's deploy/task state, matching the "unauthenticated read of stack state ... deploy output" High-impact category.

### Likelihood Explanation
Likely to be reachable in any deployment using per-stack CCMenu tokens or any other stack-scoped `ApiClient`, since exploitation only requires calling `GET /api/stacks/:stack_id/ccmenu` with a valid token and an arbitrary `stack_id` — no additional privilege beyond holding *any* valid, even minimally-scoped, `read:stack` token is required.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it using the inherited `stacks`-scoped lookup) so it respects `current_api_client.stack_id`, consistent with `Api::BaseController#stack`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. Create (or use the existing) stack-scoped `ApiClient` bound to `stack: shipit` with `permissions: ['read:stack']` (as in `test/fixtures/shipit/api_clients.yml`, `here_come_the_walrus`).
2. Authenticate an API request with that token's `authentication_token`.
3. Call `GET /api/stacks/:other_stack_id/ccmenu` where `other_stack_id` refers to a different stack than the one the token is scoped to.
4. Observe the CCMenu XML for `other_stack_id` is returned successfully (HTTP 200), even though `StacksController#index`/`#show` with the same token and `other_stack_id` would correctly return only the authorized stack or forbid access.
