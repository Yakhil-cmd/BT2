## Title
Caller deposit permanently lost when `rlp_execute` cross-contract flow fails through intermediate callback branches instead of the final one - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point accepts an attached deposit from an external (non-owner) caller and tracks it as `CallerDeposit` so that it can be refunded if the resulting cross-contract call fails [1](#0-0) . However, the refund is only issued from a single terminal callback, `rlp_execute_callback`, on its `PromiseResult::Failed` arm [2](#0-1) . Several *earlier* failure branches in the two intermediate callbacks (`address_check_callback` and `nep_141_storage_balance_callback`) return a failed `ExecuteResponse` directly and silently drop the `caller_deposit` parameter without ever creating a refund promise, causing the caller's attached NEAR tokens to be stuck in the wallet contract forever. This is the same bug class as the WeVE (FTM) redemption issue: tokens are captured up-front, an asynchronous multi-step execution can fail partway through, and only *some* failure paths trigger a refund while others silently swallow the deposit.

### Finding Description
`rlp_execute` is `#[payable]` and can be called by any predecessor account, including relayers who are not the wallet owner [3](#0-2) . `CallerDeposit::new` captures the attached deposit whenever the predecessor differs from `current_account_id`, specifically "to allow us to refund the caller's deposit if the cross-contract call fails" [1](#0-0) .

For transactions targeting another eth-implicit account, `inner_rlp_execute` schedules a call to the address registrar followed by `address_check_callback`, threading `caller_deposit` through [4](#0-3) . Inside `address_check_callback`:
- If the registrar call fails, the function returns failure without ever referencing `caller_deposit` [5](#0-4) .
- If the registrar returns an unparsable response, the function again returns failure without a refund [6](#0-5) .
- If the registrar confirms the target address maps to an existing named account and the caller is not the wallet's own signer (i.e., it's an external relayer/caller), the function again returns failure directly, dropping `caller_deposit` [7](#0-6) .

Similarly, in `nep_141_storage_balance_callback` (used for emulated ERC-20 transfers), the "unexpected response from NEP-141 storage_balance_of" and "Expected function call action" branches return failure directly, also dropping `caller_deposit` without a refund [8](#0-7) .

Only the final `rlp_execute_callback`'s `PromiseResult::Failed` branch actually creates a refund promise back to `caller_deposit.account_id` [2](#0-1) . Because the intermediate branches never reach that code path, any deposit attached by an external caller is retained by the wallet contract with no compensating action — the exact analog of the WeVE bug where the redemption process fails partway and the burned/attached asset is never returned.

### Impact Explanation
An external, unprivileged relayer or any account (not the wallet owner) that calls `rlp_execute` with an attached deposit — intending it to be used as a relayer fee or transaction value — can lose that deposit permanently if:
- The address registrar cross-contract call fails or returns malformed data, or
- The registrar confirms the eth-implicit target actually corresponds to an existing named account while the caller isn't the wallet's own signer, or
- The NEP-141 `storage_balance_of` lookup fails/returns malformed data during an emulated ERC-20 transfer.

In all these cases the caller's attached NEAR balance is transferred into the wallet contract account (via the attached deposit on the transaction) but never refunded, resulting in unauthorized permanent loss of the caller's balance — analogous to the WeVE tokens being burned but the corresponding USDC/VELO redemption failing without refund.

### Likelihood Explanation
This is reachable by any unprivileged account submitting a normal transaction/RPC call to `rlp_execute` with a nonzero attached deposit and a target that is an eth-implicit account or an ERC-20 token contract. The failure conditions (registrar unavailability/malformed response, or a target address that happens to collide with a registered account) are plausible operational scenarios rather than requiring validator or node-level compromise, making this a realistically triggerable, if capped-by-deposit-size, loss.

### Recommendation
Ensure every early-return failure branch in `address_check_callback` and `nep_141_storage_balance_callback` mirrors the refund logic in `rlp_execute_callback`: before returning a failed `ExecuteResponse`, check `caller_deposit` and, if present, create a transfer promise back to `caller_deposit.account_id` for `caller_deposit.yocto_near`. Consider factoring this refund logic into a shared helper (e.g., `fail_with_refund(caller_deposit, error)`) used by all failure branches across `address_check_callback`, `nep_141_storage_balance_callback`, and `rlp_execute_callback` to prevent this class of bug from recurring as new intermediate callbacks are added.

### Proof of Concept
1. An external account (not the wallet owner) calls `rlp_execute` on a deployed `WalletContract`, attaching a deposit, with `target` set to another eth-implicit account and an RLP transaction that triggers the `EOABaseTokenTransfer { address_check: Some(address), .. }` path.
2. `inner_rlp_execute` captures `caller_deposit` via `CallerDeposit::new` and schedules a call to the address registrar followed by `address_check_callback(target, action, caller_deposit)` [4](#0-3) .
3. The registrar lookup returns `Some(account_id)` (the target address does correspond to an existing named account), and the transaction signer is not the wallet's own account (i.e., a relayer submitted it via access key on behalf of someone else, or simply `env::signer_account_id() != current_account_id`).
4. Execution enters the `else` branch at [9](#0-8) , returning `ExecuteResponse { success: false, ... }` immediately — `caller_deposit` is never used, so no refund promise is created.
5. The originally attached deposit remains held by the wallet contract account, permanently unrecoverable by the caller through the contract's own logic.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
