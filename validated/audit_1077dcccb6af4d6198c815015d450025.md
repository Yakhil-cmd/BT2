### Title
Cross-tenant forged `status` webhook accepted for orgs without `webhook_secret`, allowing unauthenticated commit-status injection across arbitrary stacks - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects a `GitHubApp` verifier using `repository_owner`, which falls back from `params.dig('repository','owner','login')` to `params.dig('organization','login')` when `repository` is omitted. `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected org has no `webhook_secret` configured. Once past that gate, `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` with no repository/stack scoping whatsoever, so the forged status is applied to any commit matching that SHA in any stack in the installation.

### Finding Description
The broken binding is: **the org that authenticates the request (`repository_owner`, used in `Shipit.github(organization: repository_owner)` at `app/controllers/shipit/webhooks_controller.rb:25`) must equal the org/repo whose commit data actually gets mutated (`Commit.where(sha: params.sha)`, unscoped, in `app/models/shipit/webhooks/handlers/status_handler.rb:21`)**. These are never checked against each other.

Path:
1. `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) reads `params.dig('repository','owner','login') || params.dig('organization','login')`. Omitting `repository` and supplying only `organization.login` makes the attacker fully control which `GitHubApp` config is selected for verification.
2. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
3. `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`): `return true unless webhook_secret`. If the selected org has no `webhook_secret` configured, **any** signature (or none) passes verification unconditionally.
4. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) never reads `repository` or `organization` from the payload at all — it only uses `params.sha`/`params.state`, and queries `Commit.where(sha: params.sha)` across the **entire** `commits` table, which is shared by all stacks/repos in the installation, then calls `commit.create_status_from_github!(params)` for every match.

Exploit: an attacker who knows (a) that some org in the Shipit instance is configured without `webhook_secret`, and (b) the SHA of a commit belonging to a completely different, unrelated stack (git SHAs of public commits are public information), sends:
```
POST /webhooks
X-Github-Event: status
{
  "organization": {"login": "<org-without-webhook_secret>"},
  "sha": "<public sha belonging to victim stack in a different org>",
  "state": "success",
  "context": "ci/forged"
}
```
No `repository` key, no valid `X-Hub-Signature` needed. `verify_signature` passes because `webhook_secret` is blank for the selected org, and `StatusHandler` writes a status onto the commit in the unrelated victim stack. Existing guards (`drop_unhandled_event`, `ExplicitParameters` schema in `StatusHandler.params`, model validations) do not check that the commit's stack/repository corresponds to the org that authenticated the webhook — none of them reference `repository_owner` or tie the commit lookup to any owner/org.

### Impact Explanation
A forged, unauthenticated `status` event lets an attacker write a fabricated CI status (e.g., `success`) onto a commit belonging to an arbitrary, unrelated stack, as long as (a) some org in the Shipit instance lacks a configured `webhook_secret`, and (b) the attacker knows a target commit SHA (trivially obtainable for public GitHub repos). `Commit#create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb:366-386`) can trigger `stack.schedule_merges` and `ContinuousDeliveryJob` via `schedule_continuous_delivery` once the commit becomes "deployable," meaning a forged status can push an unrelated stack toward an unauthorized deploy/merge. This is a cross-tenant "payload for one repository mutating another's stack/commit," matching the Critical impact category.

### Likelihood Explanation
Requires: at least one org in the target Shipit installation configured with a `GitHubApp` that has no `webhook_secret` set (a real, documented and common misconfiguration path since `webhook_secret` is optional per `GitHubApp#initialize` at `lib/shipit/github_app.rb:50`), and knowledge of a target commit SHA in a different stack (trivial for public repos, since SHAs are exposed via GitHub UI/API/git history). No authentication, no signature, no privileged role is required — this is directly reachable via unauthenticated `POST /webhooks`. It is fully repeatable against any commit SHA present in the `commits` table.

### Recommendation
- Require every `Handler`, in particular `StatusHandler`, to scope `Commit` lookups by `stack`/`repository` derived from the payload's `repository.full_name` (or resolved via `Repository`), rather than a global `Commit.where(sha:)`.
- Enforce that `repository_owner`/`organization.login` used for signature verification matches the `repository.owner.login` actually used by the handler for the same event, rejecting payloads where they diverge.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is unset for a *configured* org handling live traffic; treat a missing secret as a hard configuration error rather than an implicit bypass, or require an explicit signature check regardless.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative addition)
test "forged :status for org without webhook_secret affects a commit from a different stack" do
  # Assume `shopify` org has webhook_secret configured, but `victimless-org` does not.
  Shipit.stubs(:github).with(organization: 'victimless-org').returns(
    Shipit::GitHubApp.new('victimless-org', {}) # no webhook_secret
  )

  other_stack_commit = shipit_commits(:first) # belongs to some unrelated stack

  request.headers['X-Github-Event'] = 'status'
  body = {
    'organization' => { 'login' => 'victimless-org' }, # no 'repository' key at all
    'sha' => other_stack_commit.sha,
    'state' => 'success',
    'context' => 'ci/forged'
  }.to_json

  assert_difference -> { other_stack_commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end
  assert_response :ok

  status = other_stack_commit.statuses.last
  assert_equal 'success', status.state
  assert_equal 'ci/forged', status.context
end
```
This demonstrates: (1) `repository_owner` resolves via the `organization.login` fallback to `victimless-org`; (2) `verify_webhook_signature` passes unconditionally because that org has no `webhook_secret`; (3) `StatusHandler` mutates a commit belonging to a stack completely unrelated to `victimless-org`, with no signature and no relationship between the authenticating org and the affected repository.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      yield
