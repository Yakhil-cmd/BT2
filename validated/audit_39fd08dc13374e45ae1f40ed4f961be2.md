### Title
Stale multisig votes silently reactivate when a removed owner is re-added before the pending transaction resolves - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`MultisigAccount` tracks per-transaction approvals in `transaction.votes: SimpleMap<address, bool>`, keyed by owner **address**. Owner-set changes (`update_owner_schema`, called by `add_owner(s)`, `remove_owner(s)`, `swap_owner(s)`) mutate `multisig_account.owners` but never touch any pending transaction's `votes` map. Approval counting (`num_approvals_and_rejections_internal`) recomputes quorum by iterating the **current** owners list and checking whether each currently-listed owner has an entry in `votes`. This correctly hides a removed owner's vote (as covered by `test_validate_transaction_should_not_consider_removed_owners`), but it also means that if the *same address* is later re-added to the owners list while the transaction is still pending, that owner's old vote is treated as valid again — with no new call to `vote_transanction`/`approve_transaction`.

### Finding Description [1](#0-0) 
`num_approvals_and_rejections_internal` only asks "is this current owner's address present in `votes`, and what value", it never checks *when* that vote was cast relative to the owner's continuous membership: [2](#0-1) 
`vote_transanction` adds/updates an entry in `transaction.votes` by `owner_addr`, and that entry is never deleted by `update_owner_schema`: [3](#0-2) 

Sequence:
1. Owner `A` approves pending transaction `#N` (`vote_transanction` writes `votes[A] = true`).
2. `A` is removed from `multisig_account.owners` via `remove_owner(s)`/`update_owner_schema` (e.g., because `A`'s key was compromised, or as routine membership rotation). At this point `can_be_executed`/`can_execute` correctly stop counting `A`'s vote, matching `test_validate_transaction_should_not_consider_removed_owners`.
3. Transaction `#N` is still pending (not yet executed or rejected, since `MultisigTransaction` state and its `votes` map are only removed from `multisig_account.transactions` on execution/rejection, not on owner-set change).
4. `A` (same address) is re-added to `owners` via `add_owner(s)`.
5. `num_approvals_and_rejections_internal`/`validate_multisig_transaction` again iterate the current owners list, find `A` in the list, look up `votes[A]`, and find the **stale** `true` entry from step 1 — counting it toward quorum without `A` ever calling `approve_transaction` again after being re-admitted.

This lets a stale, pre-removal approval be "resurrected" and combined with newly cast approvals from other owners to reach `num_signatures_required` and pass `validate_multisig_transaction`'s admission checks, causing on-chain execution of a transaction that the *current* owner set never actually, explicitly re-approved as a whole.

### Impact Explanation
This is an approval-validation binding failure directly analogous to the reported bug class: state tied to a re-assignable identity (an address that can be removed and re-added to a role) is used as the sole approval key, with no invalidation of prior approvals across membership changes. It allows a multisig transaction to execute despite the *current* owner set never having produced a valid quorum of live, freshly-cast approvals — a wrong-approval-set condition at the transaction admission boundary (`validate_multisig_transaction` is invoked from the VM prologue during mempool validation and execution). Because multisig accounts are commonly used to gate high-value operations (treasury transfers, upgrades, admin actions), a stale reactivated vote combining with legitimate new votes could push through a transaction that should require full re-approval from the current membership.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires (a) a transaction created and partially approved, (b) one of its approvers subsequently removed from the owner set while the transaction remains pending, and (c) that same address later re-added before the transaction is executed or explicitly rejected. This is a plausible operational sequence for any multisig doing routine owner rotation (e.g., temporarily removing an owner for a key rotation and re-adding the same address afterward), not a rare edge case, and requires no special privilege beyond normal owner-management actions already available to the multisig's own owners.

### Recommendation
Invalidate or purge affected votes whenever the owner set changes, e.g., have `update_owner_schema` remove entries from every pending `MultisigTransaction.votes` map for any owner address being removed (not just relying on the current-owners filter at count time), or version/tag votes with the owner-set generation/epoch at time of voting and only count votes cast under the current owner-set generation. Alternatively, require owners to re-approve (clear all votes) whenever the owner list changes while transactions are pending.

### Proof of Concept
1. Create multisig account with owners `{A, B, C}`, `num_signatures_required = 2`.
2. `create_transaction(A, multisig, payload)` → tx `#1`, `votes = {A: true}` (creator auto-approves).
3. `remove_owners(multisig_signer, [A])` → owners become `{B, C}`. At this point `can_be_executed(multisig, 1)` is `false` (only 0 of 2 required votes among current owners, matching `test_validate_transaction_should_not_consider_removed_owners`).
4. `add_owners(multisig_signer, [A])` → owners become `{B, C, A}` again. No new vote call by `A`.
5. `approve_transaction(B, multisig, 1)` → `votes = {A: true, B: true}`.
6. `num_approvals_and_rejections(multisig, 1)` now counts both `A` (stale vote from step 2) and `B` (fresh vote) as approvals = 2, satisfying `num_signatures_required`, and `validate_multisig_transaction` succeeds — even though `A` never re-approved after being re-admitted.

            *votes.borrow_mut(&owner_addr) = approved;
        } else {
            votes.add(owner_addr, approved);
        };

            Vote {
                multisig_account,
                owner: owner_addr,
                sequence_number,
                approved,
            }

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }

    /// Add new owners, remove owners to remove, update signatures required.
    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(
                        &mut owners_removed,
                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });
            // Only emit event if owner(s) actually removed.
            if (owners_removed.length() > 0) {
                emit(
                    RemoveOwners { multisig_account: multisig_address, owners_removed }
                );
            }
        };
