This confirms a genuine, exploitable gap in the multi-org webhook trust boundary.

### Title
Webhook signature verified against `repository.owner.login`'s org while `LabeledHandler` mutates the stack resolved from `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which org's HMAC secret to check against using `repository_owner` (`params.dig('repository','owner','login')`), but `LabeledHandler` resolves and mutates the stack using `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. These two fields are never checked for consistency, so a payload can authenticate as org A while archiving/unarchiving a review stack belonging to org B.

### Finding Description
The broken binding is: `repository_owner (used for HMAC verification) == owner segment of repository.full_name (used to resolve the mutated Repository/Stack)`. This equality is never enforced.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `github_app = Shipit.github(organization: repository_owner)` then calls `github_app.verify_webhook_signature(...)`.
- `repository_owner` (line 59-62) reads only `params.dig('repository','owner','login')`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`): `return true unless webhook_secret`. If the org named in `repository.owner.login` is configured in `Shipit.github_organizations` (via `secrets.github`) but has no `webhook_secret` set for it, **any signature (even absent) passes**.
- After passing this gate, `Shipit::Webhooks.for_event('pull_request')` dispatches to `LabeledHandler#process` (`app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb:41-45`).
- `LabeledHandler#repository` (lines 65-68) resolves the repo via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — this is a **completely independent field** from `repository.owner.login` used for verification.
- If `repository.provisioning_behavior_*` and `respond_to_label_change?` match, `handle` (lines 49-57) calls `stack.archive!` or `stack.unarchive!` on the `ReviewStackAdapter`-resolved stack belonging to org B, even though the request was only authenticated (trivially, due to the missing secret) as org A.

Attacker's exact request: a `pull_request` webhook POST to `/webhooks` with header `X-Github-Event: pull_request`, body:
```json
{
  "action": "labeled",
  "number": 1,
  "pull_request": { ..., "state": "open", "labels": [{"name": "<provisioning label>"}], ... },
  "repository": { "owner": {"login": "attacker-org-no-secret"}, "full_name": "victim-org/victim-repo" },
  "sender": {"login": "attacker"}
}
```
provided `attacker-org-no-secret` is a configured Shipit GitHub org with no `webhook_secret` set (or the attacker can produce a matching signature for whichever org is chosen), while `victim-org/victim-repo` is a different org with `review_stacks_enabled` and a matching provisioning label configuration.

Existing guards do not close this: `drop_unhandled_event` and `ExplicitParameters` schema only validate shape, not cross-field consistency; `verify_signature` never compares `repository_owner` to `repository.full_name`'s owner; `Repository.from_github_repo_name` performs no ownership/org check against the authenticating org.

`Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) is not directly invoked by `LabeledHandler`, but the referenced "ignore_ci true" precondition is a red herring for this specific handler — `LabeledHandler` archives/unarchives review stacks purely from label state and does not call `deployable?`. The archive/unarchive impact stands independent of `ignore_ci`.

### Impact Explanation
An unprivileged actor who controls (or can register) an org with no webhook secret configured in Shipit, or who can guess/replay a valid signature for any org, can archive or unarchive review stacks belonging to a completely different, victim-owned repository/org by simply setting `repository.full_name` to point at it. Archiving/unarchiving review stacks is a state-mutating action on infrastructure the attacker does not own — this is "a payload for one repository mutating another's stack," matching the Critical impact category. It is repeatable against any org/repo pair as long as one weakly-configured org exists in the Shipit deployment, and the org owning the target repo need not itself be misconfigured.

### Likelihood Explanation
Preconditions: (1) the Shipit deployment must be configured with multiple GitHub orgs (`Shipit.github_organizations` returns more than `[nil]`), (2) at least one configured org must lack a `webhook_secret` (or the attacker must otherwise forge a valid signature for some org), (3) the target repository must have `review_stacks_enabled` and use `provisioning_behavior_allow_with_label` or `prevent_with_label`. This is a realistic multi-tenant Shipit configuration (the engine explicitly supports per-org GitHub app configs via `github_app_config`). Attacker cost is a single unauthenticated HTTP POST; no GitHub credentials, session, or API token needed.

### Recommendation
In `WebhooksController#verify_signature`, after computing `repository_owner`, cross-validate that `params.dig('repository','full_name')` (when present) starts with `"#{repository_owner}/"`; reject (422) any payload where they diverge. Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank for a multi-org configuration — require an explicit secret for every registered org.

### Proof of Concept

1. Configure two orgs in `Shipit.github_organizations`: `"attacker-org"` (no `webhook_secret`) and `"acme"` (with `webhook_secret: "s3cr3t"`).
2. Create `Shipit::Repository` `acme/rails` with `review_stacks_enabled: true`, `provisioning_behavior: allow_with_label`, and an existing archived-eligible `ReviewStack`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and JSON body: `action: "labeled"`, `pull_request.state: "open"`, `pull_request.labels` containing the provisioning label, `repository.owner.login: "attacker-org"`, `repository.full_name: "acme/rails"`.
4. Assert response is `200 OK` (not `422`), proving `verify_signature` passed using `attacker-org`'s (absent) secret — `assert_equal "attacker-org", repository_owner_from_payload` vs `assert_equal "acme", full_name_owner_from_payload` (the two sides of the broken equality differ).
5. Assert the `ReviewStack` for `acme/rails` transitioned state (`unarchive!`/`archive!` called), proving org A's authentication mutated org B's stack.
