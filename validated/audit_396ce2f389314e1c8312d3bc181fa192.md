### Title
Webhook signature verification authenticates the organization but repository handlers write to a repository named by an unverified field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository_owner`, taken from `payload.dig('repository','owner','login')` (or `organization.login`). [1](#0-0) [2](#0-1)  Every event handler that actually mutates state, however, resolves the target `Repository`/`Stack` from a *different* field of the same untrusted JSON body: `payload.dig('repository','full_name')`. [3](#0-2)  The signature check only proves the request was authenticated for the organization identified by `repository.owner.login`; it never verifies that `repository.full_name` belongs to that same organization.

### Finding Description
Shipit supports hosting multiple independent GitHub organizations/apps from one instance, each with its own `webhook_secret`, exactly as documented in `docs/setup.md` ("Using Multiple GitHub Applications") and reflected in `config/secrets.development.shopify.yml`. `Shipit.github(organization: repository_owner)` looks up the app/secret keyed strictly by the organization name found in the payload, and `verify_webhook_signature` performs a constant-time HMAC-SHA1 comparison against the raw POST body using that secret. [4](#0-3) 

Because the webhooks endpoint accepts arbitrary POST bodies (not just GitHub-relayed traffic) and only checks that the HMAC matches *some* configured organization's secret, a party who legitimately administers **their own** onboarded organization/app on the shared Shipit instance knows that organization's `webhook_secret`. They can therefore craft an arbitrary JSON payload where:
- `repository.owner.login` = their own organization (so `verify_signature` selects their own known secret and the HMAC they compute passes), while
- `repository.full_name` = an unrelated victim organization/repository tracked by the same Shipit instance.

`Handler#stacks` / `Handler#repository_name` then resolve the target using `Repository.from_github_repo_name(repository_name)`, which is `payload.dig('repository','full_name')` — completely decoupled from the field that was authenticated. [3](#0-2) [5](#0-4) 

Concretely, `PushHandler#process` uses `stacks` (i.e. the victim's stacks, selected via the forged `full_name`) and calls `stack.sync_github(expected_head_sha: params.after)` — an attacker-chosen SHA — for every not-archived stack matching the attacker-chosen branch. [6](#0-5)  The `pull_request` handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, etc.) similarly resolve `repository` from `params.repository.full_name` and archive/unarchive review stacks, or update stored pull-request state, on the victim's repository, all gated only by the attacker's own organization's webhook secret. [7](#0-6) [8](#0-7) 

This is the direct analog of the reported bug class: a value that is checked/authenticated (`repository.owner.login`, used to pick the verifying secret) is not the same value that is subsequently acted upon and written (`repository.full_name`, used to select the repository/stack that gets mutated) — breaking the intended binding `authenticated_org == written_repository`.

### Impact Explanation
An attacker who controls only their own tenant organization on a shared, multi-organization Shipit deployment can forge webhook events (`push`, `pull_request:*`) that are cryptographically valid (per their own org's secret) but target a completely unrelated victim repository/stack tracked by the same instance. This allows cross-repository state mutation: forcing `sync_github` with an attacker-chosen `expected_head_sha`, or archiving/unarchiving/mutating review stacks belonging to a repository the attacker has no legitimate access to. Depending on downstream logic (e.g., merge queue/status gating that trusts synced commit state), this can influence which commit is considered "latest"/deployable for the victim stack, i.e. it crosses into unauthorized cross-repository writes against a repository the attacker does not control — a Critical-severity impact per the stated criteria.

### Likelihood Explanation
Exploitation requires the attacker to control the webhook secret of at least one organization configured on the shared Shipit instance (a legitimate, low-privilege tenant in a multi-org setup), and to craft a raw HTTP POST to the public `/webhooks` endpoint — no GitHub session, `ApiClient` token, or Shipit account is required, satisfying the "unprivileged attacker" requirement. The multi-organization configuration is a documented, supported deployment mode, so this is reachable without deviating from documented mounting/configuration.

### Recommendation
In `WebhooksController#verify_signature`, and in `Handler#repository_name`/`Handler#stacks`, cross-validate that the organization used to select/verify the webhook secret is the same organization contained in `repository.full_name` (i.e., reject the event if `repository.owner.login` does not match the owner segment of `repository.full_name`), or better, derive both values from a single, already-verified source rather than trusting two independent fields of the same unauthenticated JSON body.

### Proof of Concept
1. Attacker administers `attacker-org`, which is configured in `secrets.yml` with its own `webhook_secret` (`S`), per the documented multi-org setup.
2. Attacker crafts a JSON payload for the `push` event:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(S, raw_body)` using their own known secret `S`.
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against `S`. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack, despite the request never being authenticated for `victim-org`. [9](#0-8) [10](#0-9)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
