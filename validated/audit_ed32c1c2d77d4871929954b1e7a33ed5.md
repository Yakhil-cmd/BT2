### Title
CCMenu URL generates an unscoped `read:stack` API token that authorizes every stack, not just the requested one - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints (or reuses) an `ApiClient` bearer token meant to grant read access to a single stack's CCMenu status feed, but the client is created without a `stack` association. Because `ApiClient#stack_id?` is then false, the base API controller falls back to `Stack.all`, so the token actually authorizes reading every stack in the Shipit instance rather than only the one the URL was generated for.

### Finding Description
`CCMenuUrlController#fetch` builds a public-facing (bearer-token-in-URL) CCMenu status feed URL scoped to a single `stack`: [1](#0-0) 

The token used in that URL is produced by:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
``` [2](#0-1) 

`create_with` only sets `permissions`; it never sets `stack:`. `ApiClient` declares `belongs_to :stack, optional: true`, so the resulting record has `stack_id: nil`: [3](#0-2) 

Every API request authenticated with an `ApiClient` resolves the set of stacks the token may act on this way:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
``` [4](#0-3) 

Because `stack_id` is `nil` for the CCMenu client, `stack_id?` is `false`, so `stacks` resolves to `Stack.all` — every stack in the instance — instead of the single stack the CCMenu link was generated for. Any endpoint that only requires the `read:stack` permission (e.g. `Api::StacksController#index`/`#show`, `Api::CCMenuController#show` for any other stack id) is now reachable with this token for stacks the user never requested a link for.

This breaks the intended binding: *"a stack a token authorises" (the single stack passed to `CCMenuUrlController#fetch`) should equal "a stack a token touches"* (the scope actually enforced by `BaseController#stacks`). Instead the token authorizes `Stack.all` while it was only meant to touch one stack.

### Impact Explanation
The generated URL (containing the bearer token as a query string parameter) is designed to be embedded in third-party, session-less CCMenu/CI-status client configuration and is commonly stored/shared outside of the Shipit session context (desktop widgets, dotfiles, logs, etc.). Anyone in possession of that URL — without any Shipit session or additional credential — can use the embedded token against `Api::StacksController#index`/`#show` (and any other `read:stack`-gated endpoint) to enumerate and read the state of every stack managed by the instance, not just the one the link was created for. This matches the "High — unauthenticated read of stack state" impact bucket, since the leaked/shared artifact grants broader read access than the feature's design intends and requires no session or privileged credential to exploit.

### Likelihood Explanation
Likelihood is meaningful because:
- The vulnerable code path (`client` memoized via `find_or_create_by!`) executes on every legitimate use of the "Get CCMenu URL" feature — no attacker action is needed to create the over-scoped token; it is created by design flaw for every normal user of this feature.
- The URL/token is explicitly intended to be extracted from Shipit and used unauthenticated by third-party tooling, so its exposure to non-Shipit-session parties is the expected usage pattern, not an edge case.
- Exploiting it requires nothing beyond replaying the same Basic-Auth token against a different `stack_id` in the `/api/stacks` namespace.

### Recommendation
Pass the target stack when creating/finding the `ApiClient` so the token is properly scoped, e.g.:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client', stack: stack)
end
```
Additionally, consider validating that `read:stack`-only, unscoped (`stack_id: nil`) clients cannot be created by unprivileged users through this controller path, and add a regression test asserting the minted CCMenu client's `stack_id` equals the requested stack's id.

### Proof of Concept
1. As any authenticated Shipit user with access to Stack A, request `GET /A_owner/A_repo/A_env/ccmenu_url` (routed to `CCMenuUrlController#fetch`).
2. Observe the returned `ccmenu_url` contains `token=<ApiClient#authentication_token>` for a freshly created/reused `ApiClient` with `permissions: ['read:stack']` and `stack_id: nil`.
3. Using that same token as HTTP Basic auth (per `Api::BaseController#authenticate_api_client`), call `GET /api/stacks` or `GET /api/stacks/:other_stack_id` for Stack B, which the user never requested a CCMenu link for.
4. The request succeeds and returns Stack B's data, proving the token is authorized beyond the single stack it was created for. [5](#0-4)
