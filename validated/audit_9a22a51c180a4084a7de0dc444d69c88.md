## Title
Cross-Organization Repository Confusion via Mismatched `repository.owner.login` / `repository.full_name` in Webhook Verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In Shipit's multi-tenant configuration, the webhook signature is verified using an HMAC secret selected by `repository.owner.login` from the *untrusted* JSON payload, but the code that actually acts on the webhook (looking up the `Repository`/`Stack` to mutate) uses a *different* field from the same payload, `repository.full_name`, with no cross-check that the two agree. This breaks the intended binding: "the organization whose secret authenticated the request" should equal "the repository that is written to."

### Finding Description
`WebhooksController#verify_signature` selects which organization's webhook secret to verify against using a value taken directly out of the unauthenticated request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the per-organization webhook secret via `github_app_config(organization)` [3](#0-2) , and `verify_webhook_signature` performs an HMAC comparison of the *entire raw body* against that organization's secret [4](#0-3) .

Once the signature check passes, the actual handler dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create` [5](#0-4) ) resolves which `Repository`/`Stack` to act on using a *different* field of the same payload — `repository.full_name` — via `Handler#repository_name`/`#stacks`: [6](#0-5) 

Nothing in the codebase validates that `repository.owner.login` (used to pick the signing organization/secret) matches the owner segment embedded in `repository.full_name` (used to pick the actual `Repository`/`Stack`). Both are attacker-controlled fields inside the same signed JSON body, and the HMAC only proves "this body was signed by *some* organization's secret" — it does not prove that the org whose secret was used is the org that owns the repository being acted upon.

Concretely, an entity that possesses (or has legitimately configured) the webhook secret for Organization A (e.g., because they administer the GitHub App installation/webhook for a low-value or test organization/repo hosted on the same Shipit instance) can craft and sign a payload where:
- `repository.owner.login` = `"org-a"` (used only for signature verification, matches the known secret)
- `repository.full_name` = `"org-b/production-repo"` (used by the handler to find the actual `Stack`)

Since `verify_signature` only checks that *some* HMAC computed with Org A's secret matches the raw body, this passes, and the `PushHandler`/`StatusHandler`/`CheckSuiteHandler` etc. then act on `org-b/production-repo`'s stacks, e.g. triggering `stack.sync_github(expected_head_sha: params.after)` for a completely unrelated organization's stack [7](#0-6) , or injecting forged commit statuses/check-run results that Shipit's CI-gating logic uses to decide whether a deploy/merge is safe.

This is structurally analogous to the reported MSCA issue: the "owner-only" check (`runtimeValidationFunction`) validated one binding (caller identity) while a different call path (`executeFromPluginExternal`) let an unauthorized actor act on a different, unchecked target. Here, the "signature verification" binding (which org's secret signed this) is not the same as the "target being mutated" binding (which repository the payload claims to describe for handler purposes), and the two are never reconciled.

### Impact Explanation
This allows cross-repository/cross-organization writes: an attacker who controls (or has been issued) a webhook secret for one organization/repository hosted on a shared Shipit instance can forge webhook events that mutate the state (sync commits, CI/check-run status, pull request/review-stack lifecycle) of a *different* organization's stack that they have no legitimate access to. Depending on which handler is targeted (`push`, `status`, `check_suite`, `pull_request`), this can influence Shipit's continuous-deployment/merge-queue logic (which relies on commit statuses and check runs to gate deploys/merges) for a repository the attacker does not own, satisfying the "cross-repository writes" / "unauthorized deploy" criteria.

### Likelihood Explanation
Requires the attacker to already hold a valid webhook secret for at least one organization/repository configured on the shared Shipit instance (a realistic scenario for a shared multi-tenant Shipit deployment where different teams manage their own GitHub App webhook secrets on the same instance, without needing GitHub write access to the target repository). No other credential is required against the victim organization/repository.

### Recommendation
After parsing the payload, verify that the owner segment of `repository.full_name` (and/or `organization.login`) matches `repository.owner.login`/the organization whose secret was used for verification, rejecting the webhook if they diverge. Alternatively, look up the target `Repository`/`Stack` using the same organization identity that was used to select/verify the webhook secret, rather than trusting a second, independently-controlled field from the same unauthenticated payload for record lookup.

### Proof of Concept
1. Attacker has (or legitimately holds) the webhook secret configured for organization `org-a` on the shared Shipit instance.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-or-real-sha-of-victim-repo>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/production-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(org-a's webhook secret, raw_body)` and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s secret, and the HMAC matches — the request passes verification (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `PushHandler#process` uses `repository_name` = `"org-b/production-repo"` to look up stacks (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: params.after)` for `org-b`'s stack, which the attacker never authenticated against.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
