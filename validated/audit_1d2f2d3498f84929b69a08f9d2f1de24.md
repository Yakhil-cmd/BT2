### Title
Permanent market freeze: `borrowed * borrow_index` overflows `i128` in `accrue_step` before the `MAX_BORROW_INDEX_RAY` cap can engage - (File: common/src/rates/simulate.rs)

### Summary
Every mutating pool verb runs `global_sync`, which calls `accrue_step`, which computes `borrowed_original = scaled_to_original(env, borrowed, borrow_index)` — a plain `scaled.mul(env, index)` that panics with `GenericError::MathOverflow` when `borrowed_scaled * borrow_index / RAY` exceeds `i128::MAX`. The borrow index ceiling `MAX_BORROW_INDEX_RAY = 10^36` is applied only later, inside `update_borrow_index`, so on a market whose scaled borrow is large enough, index growth pushes the product over `i128::MAX` while `borrow_index` is still far below the cap. From that point on, every call that accrues — `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `update_indexes`, flash paths — panics, permanently freezing all supplier and borrower funds in that market.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs` line 60 unscales the scaled borrow book with `scaled_to_original` (a half-up `x * index / RAY` in `common/src/rates/scaling.rs:14-16`, backed by `mul_div_half_up` in `common/src/math/fp_core.rs:108-118`, which widens to `I256` but still panics if the *result* does not fit `i128`). The pool's mutating accrual `contracts/pool/src/interest.rs::global_sync`/`accrue_chunk` (lines 20-53) runs this step before any user-facing state change, and `simulate_update_indexes_body` (`common/src/rates/simulate.rs:136-181`) runs the identical step in every controller view that reads indexes through the cached market index.

The borrow index is clamped at `MAX_BORROW_INDEX_RAY = 10^36` (`common/src/constants/pool.rs:19`) only by `update_borrow_index` at `simulate.rs:66` — *after* `scaled_to_original` at line 60 has already multiplied the scaled debt by the index. For a market holding scaled borrow `B`, accrual panics once `borrow_index > i128::MAX * RAY / B`. With `B ≈ 10^56` scaled RAY (e.g. `10^29` units of an 18-decimal asset at index 1), the panic triggers at `borrow_index ≈ 1.7e36 RAY` — reachable under sustained max-rate compounding well before the `10^36` cap would stop growth. Because `compound_interest` bounds the exponent `x` at ~2 per one-year chunk (`common/src/rates/compound.rs:27-30`), the index can still grow ~7.4x per year at the steep segment of the curve.

This is the exact analog of the Brotli CVE: a "one-shot" multiplication (`scaled * index`) is evaluated in full before any bounding is applied, and chunking time (`MAX_COMPOUND_DELTA_MS`) bounds per-step growth but cannot bound the cumulative value product, exactly as ADR-0016 concedes ("bounds individual time steps without eliminating value overflow", `docs/explanation/decisions.md:134-140`). Notably, the repo's own harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-362`) demonstrates the freeze end-to-end: after the panic, `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW`, and the test asserts `last.borrow_index < MAX_BORROW_INDEX_RAY` — the cap never engages — and flags that the bound documented in `docs/reference/formulas.md` is wrong.

### Impact Explanation
Permanent freezing of funds and an inoperable contract for the affected market. Once `borrowed * borrow_index` exceeds `i128::MAX`, `global_sync` panics inside `accrue_step`, so `withdraw`, `repay`, `borrow`, `supply`, `liquidate`, `clean_bad_debt`, and `update_indexes` all revert forever — the overflow is monotone (the borrow index never decreases), so there is no recovery path short of a contract upgrade. All suppliers' deposits and all unclaimed protocol revenue in that `(hub, token)` book are frozen, and liquidations cannot proceed even as positions become deeply underwater.

### Likelihood Explanation
Reachable by a single unprivileged address, though it requires either a very large-denomination market or a long time horizon. The precondition is a scaled borrow book `B` such that `i128::MAX * RAY / B < MAX_BORROW_INDEX_RAY` (i.e. `B > 1.7e56` scaled RAY). An attacker can open a market on a low-price 18-decimal asset, supply an enormous principal, and borrow to ~98% utilization against separate collateral — the same setup the harness test builds (`principal = BILLION * 10^18`, debt at 98%). After enough years at the steep segment of the rate curve, the very next accrual freezes the market. Alternatively, the attacker can force high utilization by borrowing most of an existing whale market's liquidity. The attacker also loses their own frozen position, which lowers practical incentive, but the attack irreversibly destroys the entire market's funds — consistent with a Medium-severity, low-incentive/high-damage finding.

### Recommendation
Apply the `MAX_BORROW_INDEX_RAY` clamp *before* unscaling: compute utilization against the capped index, or reorder `accrue_step` so `update_borrow_index` runs first and `scaled_to_original` uses the clamped index. More robustly, compute `borrowed_original` with `mul_div_floor_saturating` (already available in `fp_core.rs:180-201`) so utilization saturates at 100% instead of panicking once the debt value exceeds `i128::MAX`; since `utilization` is only used to pick a curve rate, saturation at the maximum rate is economically correct at that point and keeps every verb executable. Alternatively, pre-cap scaled borrow issuance so `B * MAX_BORROW_INDEX_RAY` provably fits `i128`, closing the gap between the cap and the value ceiling that the formulas doc currently gets wrong.

### Proof of Concept
The repository already contains a runnable end-to-end reproduction at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`:

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
// advance time yearly until accrual panics:
//   t.try_update_indexes_for(&["BIG18"]) -> Error(Contract, MATH_OVERFLOW)
//   with last.borrow_index < MAX_BORROW_INDEX_RAY (cap never engaged)
// then:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Trace: `controller.update_indexes`/`withdraw`/`repay` → `pool::interest::global_sync` (`contracts/pool/src/interest.rs:20-33`) → `accrue_chunk` → `accrue_step` (`common/src/rates/simulate.rs:60`) → `scaled_to_original` (`common/src/rates/scaling.rs:14`) → `Ray::mul`/`mul_div_half_up` → `panic_with_error!(GenericError::MathOverflow)` once `borrowed * borrow_index / RAY > i128::MAX`, while `borrow_index` remains below `MAX_BORROW_INDEX_RAY` because the clamp in `update_borrow_index` (`simulate.rs:66`) is never reached.
