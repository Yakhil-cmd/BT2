### Title
`OpenedHandler#provision?` operator-precedence bug lets `review_stacks_enabled: false` repositories still auto-provision attacker-controlled `ReviewStack` branches - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` is written with `&&`/`||` operators whose precedence causes `review_stacks_enabled` to gate only the `allow_all` branch, not the `allow_with_label` or `prevent_with_label` branches. On a repository configured with `provisioning_behavior: prevent_with_label` (or `allow_with_label`) but `review_stacks_enabled: false`, an attacker opening a PR from a fork can still trigger `ReviewStackAdapter#create!`, which persists `stack_attributes[:branch] = params.pull_request.head.ref` verbatim, giving the attacker full control over the deploy branch of a newly created `Shipit::ReviewStack`.

### Finding Description
The broken binding: the intended invariant is `repository.review_stacks_enabled == false → no ReviewStack is auto-provisioned`, but the actual code enforces `(repository.review_stacks_enabled && allow_all?) == false → provision only skipped for allow_all`, while `allow_with_label?`/`prevent_with_label?` branches provision regardless of `review_stacks_enabled`.

Code path:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

If `provisioning_behavior` is `prevent_with_label` and the repository owner has never enabled `review_stacks_enabled` (default `false`, per `db/migrate/20201001125502_add_provision_pr_stacks_flag_to_repositories.rb`), the third disjunct still evaluates independently of `review_stacks_enabled` and can be `true` whenever the PR lacks the provisioning label — which is the default state of any freshly opened PR with no labels applied.

Once `provision?` returns `true`, `OpenedHandler#process` calls:
```ruby
Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter
  .new(params, scope: repository.review_stacks).find_or_create!
``` [2](#0-1) 

`find_or_create!` calls `create!`, which persists `stack_attributes` unmodified:
```ruby
def stack_attributes
  {
    branch: params.pull_request.head.ref,
    environment:,
    ignore_ci: false,
    continuous_deployment: false
  }
end
``` [3](#0-2) [4](#0-3) 

`params.pull_request.head.ref` comes directly from the untrusted webhook body (`requires :head do requires :ref, String end`) with no allow-list, format restriction, or ownership check against a pre-approved branch. [5](#0-4) 

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the payload came from GitHub for the *named* repository — they do not validate the `review_stacks_enabled` invariant, and none of the `ExplicitParameters` schema, `Stack` environment validation, or `subset`/`url` validators check branch provenance against any approver. The bug is purely in the boolean logic of `provision?`. I confirmed via `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` that the existing test suite exercises `allow_with_label`/`prevent_with_label` only with `provisioning_enabled: true` (the default in `configure_provisioning_behavior`), so the `review_stacks_enabled: false` + `prevent_with_label`/`allow_with_label` combination is never tested. [6](#0-5) [7](#0-6) 

### Impact Explanation
A repository owner who has explicitly left `review_stacks_enabled: false` (the column default, added in `db/migrate/20201001125502_add_provision_pr_stacks_flag_to_repositories.rb`) but has separately set `provisioning_behavior` to `prevent_with_label` (or `allow_with_label` with the label already applied by convention/automation) will unexpectedly have a `Shipit::ReviewStack` created for any opened PR, with the `branch` column set to whatever `head.ref` the PR author supplied — fully attacker-controlled since the PR author owns the fork and names their own branch. This is a write to the Shipit database (creation of a `ReviewStack`/`Stack` row) that the repository owner did not authorize under their stated `review_stacks_enabled=false` configuration, matching the "record written for a repository that did not authenticate it" / authorization-bypass category. The blast radius is limited to repositories where this specific behavior/flag combination exists, and to the review-stack/PR-provisioning subsystem (branch field of the created stack), not full RCE — the created stack still goes through `ReviewStackProvisioningQueue`/`provisioner.up`, which is a separate deployment step not directly triggered by this bug alone.

### Likelihood Explanation
Preconditions required: the target repository must have `review_stacks_enabled: false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (an operator/maintainer configuration choice, not attacker-controlled). Given those preconditions, the attacker cost is trivial — open a pull request from their own fork/branch with (for `prevent_with_label`) no label, or (for `allow_with_label`) with the pre-existing agreed label. No secrets, sessions, or privileged roles are needed; this matches the stated attacker capability of "any GitHub user who can open a pull request... and label their own PR." The finding is fully repeatable per matching repository configuration but is *not* universal — it does not affect repositories using `allow_all` (properly gated) or repositories with `review_stacks_enabled: true`.

### Recommendation
Fix the operator precedence in `provision?` so `review_stacks_enabled` gates every branch, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`. Apply the same review to `ReopenedHandler#provision?` if it shares the same pattern.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []
  payload["pull_request"]["head"]["ref"] = "attacker/steal-secrets"

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails: `Shipit::Stack.count` increases by 1 and the created `ReviewStack.branch` equals `"attacker/steal-secrets"` (`payload["pull_request"]["head"]["ref"]`), i.e. `stack.branch == payload['pull_request']['head']['ref']` holds even though `repository.review_stacks_enabled == false`, proving the divergence from the intended binding. After the fix, no stack is created and the equality never applies.
