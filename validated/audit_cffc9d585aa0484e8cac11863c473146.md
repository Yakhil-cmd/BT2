Based on my investigation, the exploitable analog here is not an SSL/encryption issue but a signature-verification binding that can be trivially bypassed, letting an unauthenticated attacker forge GitHub webhook events and manipulate authorization data.

### Title
Webhook signature verification is bypassed when no `webhook_secret` is configured, allowing unauthenticated event forgery - (File: `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` is the only gate protecting the public `/webhooks` endpoint [1](#0-0) . It calls `GitHubApp#verify_webhook_signature`, which is a no-op returning `true` whenever the configured GitHub App has no `webhook_secret` set: [2](#0-1) . Since `webhook_secret` is documented and shipped as an *optional* setting (`webhook_secret: # nil`) [3](#0-2)  and setup docs explicitly call it "(optional)" [4](#0-3) , any Shipit deployment following the documented setup without this optional secret accepts **any** unauthenticated POST to `/webhooks` as a legitimate GitHub event.

### Finding Description
The binding that should hold is: **verified signature == trust that the payload originated from GitHub for the claimed organization**. Instead, when `webhook_secret` is absent, this equality collapses to `true == true` unconditionally, because `verify_webhook_signature` short-circuits before ever comparing HMACs [5](#0-4) .

Once past `verify_signature`, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the fully attacker-controlled JSON body to handlers such as `PushHandler` and `MembershipHandler` [6](#0-5) . These handlers resolve the target `Stack`/`Repository`/`Team` purely from attacker-supplied payload fields — e.g. `repository.full_name` [7](#0-6)  — with no additional authentication. `PushHandler` will trigger `stack.sync_github(expected_head_sha: params.after)` for any branch/stack matching an attacker-chosen `full_name` and `after` SHA [8](#0-7) . The `membership` handler (exercised in tests) creates/deletes `Membership` records and can add an attacker-chosen GitHub login to a `Team` that is part of `Shipit.github_teams` [9](#0-8) , and `User#authorized?` grants Shipit access solely based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [10](#0-9) .

### Impact Explanation
This breaks the equality "GitHub-authenticated organization == the actor allowed to write repository/stack/team state." An unprivileged network attacker who never needs to authenticate can:
- Fabricate `membership` events to add themselves (or any known GitHub login) to a `Team` referenced by `Shipit.github_teams`, escalating into the app's authorization boundary — a High-severity outcome per the rules (escalation into `Shipit.github_teams` authorization).
- Fabricate `push`/`status`/`check_suite` events to force syncs, alter commit statuses, and manipulate deploy-eligibility signals for any repository known to the instance, without ever holding GitHub credentials, a Shipit session, or the `webhook_secret`.

### Likelihood Explanation
Likelihood is Medium-to-High in realistic deployments: the feature is optional by design and the example/documented configuration ships with it unset, so any operator who follows the documented quick-start (`docs/setup.md`, `config/secrets.development.example.yml`) without separately hardening the webhook secret is exposed. No secret, session, or privileged credential is required by the attacker — only knowledge of the public `/webhooks` route and payload shape, both of which are documented and covered by tests.

### Recommendation
Do not treat an absent `webhook_secret` as "verification passes." Instead, require a webhook secret to be configured for every organization the app serves, and fail closed (return `false`/422) when it is missing, e.g.:
```diff
def verify_webhook_signature(signature, message)
- return true unless webhook_secret
+ return false unless webhook_secret
  ...
end
```
Additionally, cross-check that the organization used to select the verification secret (`repository.owner.login` / `organization.login`) matches the organization implied by `repository.full_name` before dispatching to handlers, so a valid signature for one org cannot be replayed to act on a different org's repositories.

### Proof of Concept
1. Deploy Shipit per `docs/setup.md` without setting `github.webhook_secret` (the documented default).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 48, "name": "Ouiche Cooks", "slug": "ouiche-cooks", "url": "https://example.com" },
  "member": { "login": "attacker-controlled-login" },
  "organization": { "login": "any-org" }
}
```
No `X-Hub-Signature` header is required, since `verify_webhook_signature` returns `true` when `webhook_secret` is blank [5](#0-4) .
3. The request is processed by `Shipit::Webhooks::Handlers::MembershipHandler`, creating/updating `Team`/`Membership`/`User` records as demonstrated in the existing test suite [9](#0-8) , without any GitHub-issued credential.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
