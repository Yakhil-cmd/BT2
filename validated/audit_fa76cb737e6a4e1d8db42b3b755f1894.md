## Title
Cross-organization webhook forgery: signature verified against `repository.owner.login` but state-changing handlers act on the unrelated `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-tenant deployments configured per the documented "Using Multiple Github Applications" scheme, `Shipit::WebhooksController#verify_signature` picks the HMAC secret used to validate an inbound webhook by reading `repository.owner.login` (or `organization.login`) out of the **same attacker-controlled JSON body** it is about to validate. Once the HMAC check passes, the raw payload is dispatched unchanged to every registered handler, several of which resolve the target repository/stack from a **different field**, `repository.full_name` (see `Handler#repository_name`, `PushHandler`, `StatusHandler` → `Commit#create_status_from_github!`). Nothing ties `repository.owner.login` to the prefix of `repository.full_name`; an org admin who legitimately owns one tenant's webhook secret can sign a payload whose `owner.login` matches their own org (so the correct, known secret is selected) while `full_name` points at a completely different tenant's repository, causing Shipit to act on that other repository.

### Finding Description
`Shipit::WebhooksController#verify_signature` selects the verifying `GitHubApp`/secret using an attacker-supplied field of the very payload being authenticated: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization app configs from `secrets.github` keyed by organization name, as documented for multi-org installs: [3](#0-2) 

Once `verify_signature` succeeds (HMAC-SHA1 over the raw body, keyed by whichever org's secret `repository_owner` happened to select), the parsed body is handed unmodified to all handlers for the event: [4](#0-3) 

Handlers, however, resolve the acted-upon repository from `repository.full_name`, not from `repository.owner.login`: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` simply splits `"owner/name"` from that string and looks it up, with no cross-check against the org whose secret verified the request: [7](#0-6) 

This breaks the intended binding **"organization that authenticated == repository that is written."** An attacker who is a legitimate admin of one tenant organization onboarded into the same shared Shipit instance (and therefore knows or controls that org's `webhook_secret`, since GitHub App creation and secret configuration for each org is typically done by that org's own admins per `docs/setup.md`'s multi-org guidance) can:
1. Set `repository.owner.login` (or `organization.login`) to their own org, so `verify_signature` selects the config/secret they know.
2. Set `repository.full_name` to `"victim-org/victim-repo"` — any repository already registered as a `Shipit::Repository` in the shared instance, regardless of which org it belongs to.
3. Sign the whole raw JSON body with their own known secret and send it to `/webhooks`.

The signature check passes because it only validates the bytes against the attacker's own secret; it never checks that the signed bytes are consistent with the org that owns them. Handlers then execute against the victim's repository/stacks.

### Impact Explanation
Depending on event type this enables genuinely unauthorized state changes on a repository/stack the attacker does not control:
- `push` → `PushHandler` calls `stack.sync_github(expected_head_sha: ...)` on the victim stack, forcing a sync to an attacker-chosen SHA for a repo the attacker doesn't own.
- `status` → `StatusHandler`/`Commit#create_status_from_github!` writes CI status directly from attacker-controlled `state`/`context`/`description` fields onto commits in the victim's repository, which can be used to forge a passing CI status and enable an unauthorized deploy/merge for a repository the attacker has no legitimate access to.
- `pull_request` handlers similarly resolve `repository` via `params.repository.full_name` and can archive/unarchive/provision review stacks belonging to other tenants.

This matches the "unauthorized deploy" / "cross-repository writes" impact bar for High severity, since it lets an attacker authenticated only for their own tenant act on a stack/repository belonging to a different organization in the same Shipit instance.

### Likelihood Explanation
Requires: (a) a multi-tenant Shipit deployment configured with multiple GitHub organizations under `secrets.github` (a documented, supported configuration), and (b) the attacker having legitimate control of one tenant's webhook secret (plausible if each org's own admins configure their own GitHub App/webhook secret, which is exactly what the multi-org setup implies). No Shipit session, `ApiClient` token, or GitHub App private key is needed — only knowledge of one org's own `webhook_secret`, which that org's own admin legitimately possesses. This is a real credential/repository-boundary crossing rather than a DoS/malformed-input crash, so it is in scope per the rules even though the original CVE report is a DoS bug class.

### Recommendation
In `WebhooksController#verify_signature`/handlers, derive the organization used to select the verification secret from a value that is also enforced to match the resource actually acted upon — e.g., after verifying with the org derived from `repository.owner.login`, require that `repository.full_name.split('/').first == repository_owner` (case-insensitively) before dispatching to handlers, or resolve the acted-upon repository via a value bound within the same trust domain as the verified organization, rejecting payloads where the two disagree.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `attacker-org` (secret known to the attacker, who is a legitimate admin there) and `victim-org` (repository `victim-org/victim-repo` already registered with active stacks).
2. Craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org's webhook_secret, raw_body)>`.
4. `POST /webhooks` with header `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies using the attacker's own known secret.
5. `PushHandler#process` runs `Repository.from_github_repo_name("victim-org/victim-repo")`, finds `victim-org`'s stacks, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — a state change on a repository the attacker's org has no relationship to.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
