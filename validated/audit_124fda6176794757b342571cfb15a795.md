This is decisive: the base `Handler` class already provides a `stacks` helper that scopes to the payload's `repository.full_name`, and `PushHandler` correctly uses it. `StatusHandler`, however, ignores this scoping entirely and matches on `sha` alone across the whole `commits` table.

### Title
Cross-repository `status` webhook mutates unrelated stacks' `ignore_ci`/CI-enabled state via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, with no filter on the webhook's `repository.full_name`, unlike its sibling `PushHandler` which uses the base `Handler#stacks` helper (scoped via `Repository.from_github_repo_name(repository_name)`). Any `Commit` row anywhere in the database sharing that `sha` — regardless of which stack/repository it belongs to — gets a `Status` created against it, and `Status#enable_ci_on_stack` then calls `commit.stack.enable_ci!` on that commit's own stack, not the stack tied to the webhook's verified repository.

### Finding Description
The binding that must hold is: `commit.stack_id == Stack.find_by(repository: Repository.from_github_repo_name(payload.dig('repository','full_name'))).id` for every `Status` created and every `enable_ci_on_stack` side effect triggered by a given `status` webhook. Instead, the actual code enforces only `commit.sha == params.sha`: [1](#0-0) 

Compare with the correctly-scoped `PushHandler`, which resolves stacks through `Repository.from_github_repo_name(repository_name)`: [2](#0-1) [3](#0-2) 

`Commit` rows are only unique per `(stack_id, sha)` — confirmed by the dedicated migration index `20170524104615_index_commits_on_stack_id_and_sha.rb` and the model's `belongs_to :stack` [4](#0-3)  — so the same git SHA legitimately exists as distinct `Commit` rows under different `stack_id`s whenever two Stacks share commit ancestry (forks, mirrors, monorepo-split stacks, template repos, etc.). `Commit#create_status_from_github!` then creates the `Status` using the found commit's own `stack_id`, not the webhook's stack: [5](#0-4) [6](#0-5) 

`Status#enable_ci_on_stack` (and the analogous `CheckRun#enable_ci_on_stack`) then unconditionally calls `commit.stack.enable_ci!`, permanently flipping the CI-enabled cache flag for that stack: [7](#0-6) [8](#0-7) 

**Attack path**: attacker legitimately controls Stack A (their own repo/org, correctly configured with a working `webhook_secret` in Shipit — this is a normal, permitted tenant setup, not a secrets-bypass). Attacker forks or otherwise shares commit ancestry with victim's Stack B repo so that some `sha` is present as a `Commit` row under both `stack_id`s (no cryptographic SHA1 collision needed — ordinary shared git history via fork/mirror suffices, and is common in real deployments). Attacker triggers (via a real GitHub `status` event on their own repo, or directly at `POST /webhooks` with a validly signed payload for their own org) a `status` webhook carrying that shared `sha`. `WebhooksController#verify_signature` only checks that the payload is signed by *some* configured org's secret — it never binds the signed org to which `Commit`/`Stack` rows get touched, so this passes for the attacker's own legitimate org. `StatusHandler#process` then iterates **all** `Commit` rows matching that `sha`, including Stack B's, and creates a `Status` against Stack B's commit, triggering `enable_ci_on_stack` → `Stack#enable_ci!` on Stack B — even though Stack B's operator never authenticated any webhook for Stack B and may have intentionally left CI disabled/`ignore_ci` gating in place.

None of the listed guards catch this: `verify_signature` authenticates the *sender org*, not which stacks/commits are mutated; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape of `sha`/`state`/etc., not repository scoping; `force_github_authentication`, `User#authorized?`, `require_permission!` are irrelevant (this is an unauthenticated webhook path, not a session-based one); model validations on `Stack`/`Repository` don't constrain which stack a `Commit.where(sha:)` scan returns.

### Impact Explanation
A webhook validly signed for the attacker's own tenant repository can create a `Status` row and flip `Stack#enable_ci!` (a durable Rails-cache-backed flag consulted by `Commit#deployable?` via `stack.ignore_ci?`) on a completely unrelated victim stack, changing that stack's CI gating for all future deploys — this is a "payload for one repository mutating another's stack/commit" per the impact taxonomy (Critical). It is repeatable on every subsequent `status` webhook from the attacker's own repo as long as the shared-sha `Commit` row persists in the victim stack, and generalizes to any pair of stacks that share git ancestry (a common multi-tenant Shipit topology).

### Likelihood Explanation
Preconditions: attacker must operate a Stack A that Shipit already trusts (this is an ordinary permitted tenant, not a privilege escalation in itself), and a target Stack B whose `Commit` table contains a row with a `sha` also present in Stack A's history (achievable via GitHub fork/mirror without needing a crafted webhook_secret, session, or GitHub App key). Cost is low: fork a public repo, wait for Shipit to sync both stacks (which happens automatically via `push`/PR handling), then send one legitimately-signed `status` webhook. This is fully repeatable and does not require guessing any secret.

### Recommendation
Scope `StatusHandler#process` (and the analogous `check_run`/`check_suite` handlers if similarly unscoped) to only touch commits belonging to stacks resolved from the webhook's own `repository.full_name`, mirroring the `Handler#stacks` helper already used by `PushHandler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or filtering by `commit.stack_id.in?(stacks.ids)` before calling `create_status_from_github!`.
