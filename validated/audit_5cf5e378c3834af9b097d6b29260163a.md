### Title
Header-based user impersonation via `X-Shipit-User` when `Shipit.disable_api_authentication` is enabled - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
When `Shipit.disable_api_authentication` is true, `authenticate_api_client` sets `@current_api_client` to `UnlimitedApiClient.new`, which is not bound to any credential or user identity. `current_user`/`identify_user` then trusts the client-supplied `X-Shipit-User` header verbatim to look up an arbitrary `User` by login, letting any unauthenticated caller attribute deploys, rollbacks, or locks to any existing user.

### Finding Description
The intended binding is: `current_user` should equal the identity actually authenticated by `authenticate_api_client`'s credential, i.e. `current_user == current_api_client.creator` (or equivalent verified identity). Instead: [1](#0-0) 
`current_user` calls `identify_user`, which does `User.where('lower(login) = ?', user_login.downcase).first` using `request.headers['X-Shipit-User']` with no cross-check against `current_api_client`.

When `Shipit.disable_api_authentication` is true, `authenticate_api_client` bypasses `ApiClient` entirely: [2](#0-1)  assigning `UnlimitedApiClient.new`, which has no `creator`/user association and unconditionally permits all operations: [3](#0-2) .

Attacker request: `POST /api/stacks/:id/rollbacks` with header `X-Shipit-User: victim-login` and no Basic Auth credential (since auth is disabled). `RollbacksController#create` calls `deploy.trigger_rollback(current_user, ...)`, passing the impersonated `current_user` directly into the created `Rollback`/`Task` record: [4](#0-3) . No existing guard (`require_permission!`, `check_permissions!`, `ExplicitParameters` schema) validates that the caller is the named user — `require_permission!` only calls `current_api_client.check_permissions!`, which for `UnlimitedApiClient` is a no-op.

This root cause is present regardless of the exact endpoint chosen; any `Api::BaseController` subclass that reads `current_user` for attribution is affected under this configuration.

### Impact Explanation
An unauthenticated caller can cause a `Rollback`/`Deploy`/lock action to be misattributed to any existing `User` record (`Task#user`, `lock_author`) merely by setting a header, when `disable_api_authentication` is true. This is repeatable per request and against any stack the `UnlimitedApiClient` has access to (all stacks, since `stack_id?` is `false`, granting global scope). This matches "Critical - an unauthorized deploy/rollback" and false attribution of privileged actions to arbitrary users.

### Likelihood Explanation
This requires the operator to have explicitly set `Shipit.disable_api_authentication = true`. This is a documented, supported configuration (used for anonymous/CCMenu-style read access), and per the question's own preconditions it's explicitly in scope ("a supported configuration"). Given that precondition, the attack is trivial: one HTTP request with an arbitrary header, no credentials, no rate limiting concerns, fully repeatable.

### Recommendation
Do not trust `X-Shipit-User` when the current API client is an `UnlimitedApiClient` (or any client not bound to a verified user). Either remove the `identify_user` header trust path entirely for unauthenticated/unlimited clients, or bind `identify_user` to `current_api_client`'s actual creator/user association rather than an attacker-controlled header. At minimum, gate the header-based identification behind verified `ApiClient` authentication and ignore it when `Shipit.disable_api_authentication` is true.

### Proof of Concept
```ruby
test "rollback attributed to attacker-chosen user when api authentication disabled" do
  victim = shipit_users(:walrus) # or create a distinct existing user
  Shipit.stubs(:disable_api_authentication).returns(true)

  post api_stack_rollbacks_url(stack_id: stack.to_param),
       params: { sha: deploy.until_commit.sha },
       headers: { 'X-Shipit-User' => victim.login }

  assert_response :accepted
  assert_equal victim, Rollback.last.user
end
```
This demonstrates `current_user == victim` despite no credential proving the caller is `victim`, violating the intended binding `current_user == current_api_client`'s authenticated identity.
