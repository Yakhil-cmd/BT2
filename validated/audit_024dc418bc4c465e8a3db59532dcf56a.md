### Title
Malicious Recipient Contract Permanently Locks Bridged KAIA and Corrupts Bridge Nonce State — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` performs a push-payment to `_to` via a low-level call **after** updating critical bridge state. If `_to` is a contract that rejects KLAY, the `require(ok, ...)` causes the entire transaction to revert — including the nonce state updates — permanently locking the bridged KAIA in the bridge contract and freezing `lowerHandleNonce` and `recoveryBlockNumber`.

### Finding Description

The execution order in `handleKLAYTransfer` is:

```
1. _lowerHandleNonceCheck(_requestedNonce)
2. _voteValueTransfer(_requestedNonce)
3. _setHandledRequestTxHash(_requestTxHash)          ← state write
4. handleNoncesToBlockNums[N] = _requestedBlockNumber ← state write
5. _updateHandleNonce(N)                              ← advances lowerHandleNonce
6. emit HandleValueTransfer(...)
7. (bool ok, ) = _to.call.value(_value)("")           ← external push to user-controlled address
8. require(ok, "handleKLAYTransfer: transfer failed") ← reverts entire tx if _to rejects KLAY
``` [1](#0-0) 

Because Solidity reverts all state changes on `require` failure, steps 3–5 are rolled back when step 8 fails. The result:

- `handleNoncesToBlockNums[N]` is never written
- `lowerHandleNonce` is never advanced past `N`
- `_setHandledRequestTxHash` is rolled back, so the tx hash is not marked handled

The `_updateHandleNonce` loop in `BridgeTransfer.sol` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive nonces starting from `lowerHandleNonce`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [2](#0-1) 

Since `handleNoncesToBlockNums[N]` is never set (always reverted), `lowerHandleNonce` is permanently frozen at `N`, and `recoveryBlockNumber` is permanently frozen at its pre-`N` value.

The `_lowerHandleNonceCheck` only blocks nonces **below** `lowerHandleNonce`:

```solidity
require(lowerHandleNonce <= _requestedNonce, "removed vote");
``` [3](#0-2) 

So operators can handle nonces `N+1`, `N+2`, etc., but `lowerHandleNonce` will never advance past `N` because `handleNoncesToBlockNums[N]` is never populated. The value transfer recovery system (`vt_recovery.go`) reads `RecoveryBlockNumber()` and `LowerHandleNonce()` to determine the scan window for missed events: [4](#0-3) 

With both frozen, the recovery mechanism's hint is permanently stale.

### Impact Explanation

1. **Permanent KAIA lock**: The KAIA locked on the source chain (via `requestKLAYTransfer`) can never be released on the destination chain. The bridged KAIA for nonce `N` is permanently trapped in the bridge contract — an unauthorized permanent lock of bridged assets.

2. **Bridge nonce state corruption**: `lowerHandleNonce` and `recoveryBlockNumber` are permanently frozen at stale values. The value transfer recovery mechanism (`updateRecoveryHintFromTo`) uses these values to determine which events to re-scan. A frozen `recoveryBlockNumber` means the recovery system either re-processes already-handled events or fails to detect genuinely missed transfers.

### Likelihood Explanation

Any user can trigger this by calling `requestKLAYTransfer` with `_to` set to a contract that has no payable fallback (or an explicitly reverting fallback). This is an unprivileged, standard user operation:

```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
``` [5](#0-4) 

The attacker pays only the gas and bridge fee. The attack can be accidental (user mistakenly uses a non-payable contract address) or intentional (griefing). No operator privilege is required.

### Recommendation

Replace the push-payment pattern with a pull-payment pattern:

1. After the vote threshold is reached and nonce state is committed, record the pending KAIA amount in a mapping: `pendingWithdrawals[_to] += _value`.
2. Provide a separate `withdraw()` function that lets `_to` pull their KAIA.
3. This decouples the nonce-advancement logic from the external call, so a rejecting recipient cannot revert the bridge's state.

Alternatively, use a try/catch (Solidity ≥0.6) or check-and-log pattern: if the transfer fails, emit a `TransferFailed` event and still advance the nonce, allowing operators to handle the stuck KAIA separately.

### Proof of Concept

1. Attacker deploys `MaliciousRecipient` with no payable fallback on the destination chain.
2. Attacker calls `requestKLAYTransfer(address(MaliciousRecipient), value, "")` on the source bridge, paying `value + fee`. This emits `RequestValueTransfer` with nonce `N`.
3. Bridge operators observe the event and call `handleKLAYTransfer(..., MaliciousRecipient, value, N, blockNum, "")` on the destination bridge.
4. Steps 3–5 execute (state written), then `MaliciousRecipient.call{value: value}("")` returns `false`.
5. `require(ok, ...)` reverts the entire transaction. All state writes are rolled back.
6. Operators retry indefinitely — every attempt reverts identically.
7. **Result**: `lowerHandleNonce` is frozen at `N`. `recoveryBlockNumber` is frozen. The `value` KAIA is permanently locked in the destination bridge contract. The attacker's KAIA on the source chain is also permanently locked (burned/locked in the source bridge). The bridge's recovery mechanism is corrupted for all future transfers on this bridge pair.
