Based on the search, there is no exact analog in the Polkadot SDK where a permissionless extrinsic allows creating a persistent, unfillable "request" (zero amount / zero collateral) at negligible cost that clogs a shared order queue in a way lenders/counterparties must wade through, mirroring `Cooler.sol::requestLoan`. The closest structural analogs — e.g. `polkadot/runtime/parachains/src/on_demand/mod.rs` `do_place_order` — actually enforce a paid spot price and a bounded queue size (`QueueFull` error) before any order is accepted [1](#0-0) , so a zero-cost/zero-effect spam order cannot be queued there. Similarly, `pallet-delegated-staking` was patched specifically to make zero-amount delegations a no-op rather than creating a stale storage entry [2](#0-1) , and `pallet-revive`'s deposit/refund paths explicitly short-circuit on zero amounts [3](#0-2) . These are the FRAME idioms that prevent the exact "free spam request" class described in the report; I found no FRAME pallet, XCM handler, or bridge module in this codebase exposing a public, fee-free entry point that creates persistent, unbounded, unfillable order/request records analogous to `Cooler.requestLoan`. Additionally, this bug class (unbounded low-cost request spam / DOS via flooding) falls squarely under the explicitly excluded categories in the scan instructions (resource-exhaustion/flooding claims), so even a superficially similar pattern would not be reportable here.
