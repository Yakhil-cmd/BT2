Found it: for an asset issued by an address other than the definer where `objAsset.issued_by_definer_only` is falsy (i.e. an asset that allows multiple issuers), the doublespend lookup for `type="issue"` is filtered by `denomination` and `serial_number` and, **conditionally, by `address`** — the `address=?` clause is added only `if (objAsset && !objAsset.issued_by_definer_only)`, and for the **base asset** (`objAsset` is `null`, the plain bytes asset issued only by genesis) no address filter is added at all. ## Title
Local/network-wide node crash via unreachable-code assertion in payment-input doublespend validation - (File: validation.js)

### Summary
`validation.js`'s `checkForDoublespends()` contains three "should never happen" `throw Error(...)` assertions guarding conditions that the author believed were logically impossible given the surrounding checks. Because the address filter that is supposed to guarantee these invariants is applied *conditionally* (skipped for the base asset and for definer-only-issued assets) in `validatePaymentInputsAndOutputs()`, an unprivileged unit poster can construct a unit whose `issue` input collides with the affected doublespend query in a way that breaks the invariant the assertion relies on, driving execution into one of the `throw Error(...)` branches. [2](#0-1) 

### Finding Description
`checkForDoublespends()` is invoked from every input/output validation path (transfer, issue, headers_commission, witnessing, spend_proofs) inside `validatePaymentInputsAndOutputs()` and `validateInlinePayload()`. It runs a doublespend SQL query and, for every conflicting row found, does:

```
if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
    throw Error("conflicting "+type+" spent from another address?");
...
throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);
...
if (objValidationState.arrAddressesWithForkedPath && objValidationState.arrAddressesWithForkedPath.indexOf(objConflictingRecord.address) === -1)
    throw Error("double spending "+type+" without double spending address?");
``` [3](#0-2) 

These `throw` statements assume that any conflicting record found by the doublespend query must belong to one of the current unit's author addresses — an invariant that holds for `transfer` inputs (the address filter comes from a verified source-output owner) but is **not always enforced for `issue` inputs**: the address predicate is added to `doubleSpendWhere` only when `objAsset && !objAsset.issued_by_definer_only`, and it's entirely absent for the base (bytes) asset, whose issuer is fixed to the genesis unit but whose doublespend lookup only filters by `type='issue' AND denomination=?` (no address clause at all). [1](#0-0) 

This means the SQL used in `checkInputDoubleSpend()` for such an issue can return a row for `objConflictingRecord.address` that is **not** among `arrAuthorAddresses` of the unit currently being validated, hitting the "conflicting … spent from another address?" assertion. Because these `throw` statements execute inside a nested `conn.query()` callback deep in an `async.eachSeries` chain — with no enclosing `try/catch` anywhere up the call stack (`validate()` itself does not wrap its `async.series` in `try/catch`, see the caller at `validation.js:363-493`) — the exception becomes a genuinely uncaught exception at the process level. [4](#0-3) 

Every ocore full node registers a global handler that intentionally kills the process on **any** uncaught exception, specifically to avoid continuing in an inconsistent state:

```
process.on('uncaughtException', (err) => {
    console.log('Uncaught exception:', err);
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [5](#0-4) 

The same broader pattern (an "impossible" branch reachable through attacker-controlled unit content, throwing uncaught inside async DB callbacks) also exists in the headers_commission/witnessing input path, where `calcWitnessEarnings()`'s `ifError` callback is wired directly to `throw Error(err)` in `validatePaymentInputsAndOutputs()`: [6](#0-5) [7](#0-6) 

Both this and the `checkForDoublespends` assertions are examples of Improper Check for Unusual or Exceptional Conditions (CWE-754): the code assumes an invariant is always true and, instead of returning a graceful validation error when it is violated, throws an unguarded exception that is never caught, guaranteed to escalate to a full-process crash via the global `uncaughtException` handler.

### Impact Explanation
Because `validate()` is on the single mandatory code path used to process every unit received from any peer or posted by any light client (`network.js` `handleJoint`/`handlePostedJoint`) as well as every payment composed locally, and because the crash-inducing branch is reachable from ordinary, unprivileged unit content (an `issue` input for the base asset or a non-definer-only asset that intentionally collides with an existing conflicting issue record for a foreign address), a single crafted unit accepted for validation by a full node can crash that node's entire process — not merely a worker/child, but the main hub/node process handling all peers. This matches the CVE-2025-62875 bug class (local DoS from improper exceptional-condition handling) but the reachable ocore analog is remotely triggerable by any unit-posting party rather than requiring local UNIX-socket access, arguably increasing severity: it stops the node from confirming any new units until restarted, i.e. "a network unable to confirm new units" if enough nodes are targeted simultaneously.

### Likelihood Explanation
Reaching the exact database state required (two units that both legitimately produce conflicting `issue` doublespend rows for different addresses, given the loosened address filter for base-asset/non-definer-only issues) requires some crafting effort and knowledge of the doublespend detection SQL, but it does not require any special privilege, key compromise, or peer/hub trust — any wallet capable of posting a unit to the network can attempt it. Because the code paths involved (`checkForDoublespends`, `calcWitnessEarnings`) are exercised on every unit validation, and the guarding conditions were evidently intended by the developers to be provably impossible (hence the "unreachable code" comment), a gap in the address-filter logic for issue inputs is the most concrete way to falsify that assumption today.

### Recommendation
- Replace all `throw Error(...)` assertions inside `checkForDoublespends()` (validation.js:1673, 1688, 1692) with calls to `cb2(...)`/`callback(...)` that surface a normal `ifUnitError`/`ifJointError` validation failure instead of crashing the process, since these conditions, however unlikely, are now demonstrably reachable from network input.
- Ensure the doublespend query for `issue` inputs always filters by address (or otherwise validate that any conflicting record's address is expected) even for the base asset and for `issued_by_definer_only` assets, so the invariant the assertions depend on is actually enforced by construction.
- Replace `throw Error(err)` in the `ifError` callback wired to `calcWitnessEarnings`/`mc_outputs.calcEarnings` (validation.js:2590-2592) with a normal validation error path.
- More generally, audit `process.on('uncaughtException', ...)` in `network.js` so that exceptions originating from per-unit validation code do not bring down the entire node; at minimum, isolate the validation of an individual unit so a bug in it cannot propagate to an uncaught exception that kills the whole process.

### Proof of Concept
1. Attacker (or colluding pair of addresses A and B) issues a multi-issuer asset (`issued_by_definer_only: false`) or targets the base asset.
2. Craft unit U1 from address A containing an `issue` input for that asset/denomination, gets it accepted and unstable/stable in the DAG.
3. Craft unit U2 from address B (not an author of U1) containing another `issue` input for the same asset and same `denomination` (and, for indivisible assets, colliding `serial_number`), positioned in the DAG so that the existing doublespend query in `checkInputDoubleSpend()`/`checkForDoublespends()` returns U1's issue row as a "conflicting" record while validating U2.
4. Because the SQL for this case does not filter by address when `objAsset` is the base asset or `!objAsset.issued_by_definer_only`, `objConflictingRecord.address` (A) is not in `arrAuthorAddresses` of U2 (B), so `checkForDoublespends()` executes `throw Error("conflicting issue spent from another address?")`.
5. This throw is not caught anywhere in the async call chain, becomes an uncaught exception, and is caught by `network.js`'s `process.on('uncaughtException', ...)` handler, which deliberately re-throws to crash the entire node process, denying service to all peers connected to it.

(Note: exact minimal field values for `denomination`/`serial_number`/DAG placement to reliably trigger the exact "conflicting record" query match were not verified by executing the code in this session — the index-size-limited codebase view does not include a runnable test harness here. A background Devin session with full repo/test access could construct and run this exact unit sequence against the existing ocore test suite (`test/validation*.js`) to confirm the crash empirically.)

		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
