### Title
Webhook signature is verified against an organization key derived from the same untrusted payload field that handlers later read independently, allowing cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController` selects which GitHub App / org config (and therefore which `webhook_secret`) to use for HMAC verification based on a value taken directly out of the unauthenticated JSON body, and the per-event handlers separately re-read the repository identity from the same body to decide *what* to mutate. Because these two reads of the payload are never cross-checked against each other, an attacker who legitimately controls one org configured on the Shipit instance (and therefore knows that org's `webhook_secret`) can forge a signature that validates under their own org while pointing the actual mutated repository/stack at a completely different, victim organization's repository.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config purely from the untrusted payload: [1](#0-0) [2](#0-1) 

`repository_owner` (`params.dig('repository','owner','login')`) is used only to look up `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is then used to verify the HMAC over the raw body via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

`Shipit.github` looks the config up per-organization when multiple GitHub Apps/orgs are configured: [4](#0-3) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire raw body* to the handlers for the event, and the handlers independently derive the target repository from a **different JSON path in the same body** — `repository.full_name` — with no requirement that it match the `repository.owner.login` used for signature selection: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

The equality that should hold is: `organization whose webhook_secret authenticated the request == organization that owns the repository the handler mutates`. Because both fields are read independently from the same attacker-supplied JSON, and GitHub's real webhook payloads always keep `repository.owner.login` and `repository.full_name` consistent, nothing in this engine enforces that consistency for a forged/self-crafted payload. An attacker who is a legitimate GitHub admin of any org configured in this Shipit instance (with a valid App installation / webhook secret for their own org) can:

1. Craft a JSON body with `repository.owner.login = "attacker-org"` (their own org) and `repository.full_name = "victim-org/victim-repo"`.
2. Compute a valid `X-Hub-Signature` using their own known `webhook_secret` over that exact raw body — this passes `verify_signature` because it looks up `attacker-org`'s secret.
3. POST it directly to the public `/webhooks` endpoint. The handler for the event (`PushHandler`, `PullRequest::*Handler`, `StatusHandler`, `CheckSuiteHandler`) resolves the actual `Repository`/`Stack` via `repository.full_name`, i.e. the victim org's repo, and executes the associated action against it: forcing `Stack#sync_github`, archiving/unarchiving review stacks, updating pull request state, etc. — none of which required any credential tied to `victim-org`.

### Impact Explanation
This breaks the credential/repository binding the signature check is supposed to enforce, enabling **cross-repository writes**: an attacker with a signing secret for their own org can force GitHub-sync, review-stack archive/unarchive, and pull-request-state mutations against any other repository/stack tracked by the same Shipit instance, without ever holding credentials, GitHub App installation, or webhook secret for that target repository/org. This matches the Critical bar of "cross-repository writes" via a credential the attacker is not supposed to have for the target repo.

### Likelihood Explanation
Exploitability requires the attacker to control at least one org/App configuration registered with the Shipit instance (i.e., know that org's `webhook_secret`), which is realistic in any multi-tenant/multi-org Shipit deployment where different teams manage their own GitHub App installations pointed at a shared Shipit instance — exactly the scenario `github_app_config`/`TOP_LEVEL_GH_KEYS` multi-org support is built for. No GitHub write access to the victim repo, no Shipit API token, and no session are required, satisfying the unprivileged-attacker requirement.

### Recommendation
`verify_signature` should not blindly trust `repository.owner.login`/`organization.login` from the payload to select the verification key when handlers subsequently trust a different payload field (`repository.full_name`) to select the mutation target. Verify the signature using the org key, then re-derive and assert that the org embedded in `repository.full_name` (and any other repository identifiers subsequently used by handlers) is consistent with `repository_owner` before dispatching to handlers, or centralize a single canonical "authenticated organization" derived once and threaded through to every handler instead of allowing each handler to re-parse the raw, unauthenticated-with-respect-to-that-field JSON independently.

### Proof of Concept
Given a Shipit instance configured with two orgs, `attacker-org` (attacker controls the GitHub App/webhook secret) and `victim-org` (target, unrelated to attacker):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(payload, attacker-org's webhook_secret)>

{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```

- `verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and validates the attacker's own signature successfully.
- `PushHandler#process` (via `Handler#repository_name` / `Handler#stacks`) resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef")` on stacks the attacker has no relationship to, forcing an unauthorized GitHub sync/potential deploy trigger on the victim's stack.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
