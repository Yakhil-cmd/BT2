### Title
Floating-point precision-loss overflow in `sum` address-definition condition allows bypass of spending limits - (File: definition.js)

### Summary
The `sum` oscript/address-definition operator accumulates matched input/output amounts into a plain JavaScript number without any intermediate bound checking, analogous to Pillow's unbounded glyph-advance accumulator (CVE-2026-42308). When enough large amounts are summed, the accumulator silently loses precision once it exceeds `Number.MAX_SAFE_INTEGER` (2^53-1), while remaining `isFinite`, allowing an attacker to satisfy `at_most`/`equals` spending-authorization checks with an actual total that differs from the reported sum.

### Finding Description
`evaluate()` in `definition.js` implements the `sum` condition used in address definitions (smart contract authentifiers) to bound spending, e.g. `['sum', {filter: {...}, at_most: 123}]`: [1](#0-0) 

The accumulation loop `sum += arrFoundObjects[i].amount` uses standard IEEE-754 double arithmetic with no per-step or windowed bound check. The only sanity check afterward is `isFinite(sum)`, which only rejects `NaN`/`Infinity` — it does **not** detect precision loss that occurs once the running total exceeds `Number.MAX_SAFE_INTEGER` (9,007,199,254,740,991). Individual output/input amounts are capped at `constants.MAX_CAP`/`TOTAL_WHITEBYTES` (1e15), enforced elsewhere e.g. [2](#0-1) , but that per-item cap does nothing to bound the *sum* of many matched items in a single unit, since a unit may contain multiple messages/inputs/outputs matching the filter (bounded only by `MAX_MESSAGES_PER_UNIT`, `MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`). Summing on the order of ~10+ amounts near 1e15 each is enough to exceed 2^53 and enter the lossy-precision regime while `isFinite(sum)` still returns `true`, so the `at_most`/`equals` comparisons in lines 1168-1173 can be evaluated against an inaccurate `sum` value.

This is the direct structural analog of the Pillow bug: an accumulator that grows via repeated addition of attacker-influenced values, with no overflow/precision guard beyond a coarse finiteness check.

### Impact Explanation
The `sum` clause is used inside address definitions to gate authorization (e.g., "allow spending only if cumulative payments are at most X" or "equal to X"). If the accumulated sum silently loses precision, an attacker who controls a unit's messages/inputs matching the filter can construct a set of amounts whose true total exceeds the configured `at_most` limit (or does not exactly equal the required `equals` value) but whose floating-point-summed representation still satisfies the check. This directly undermines a fund-spending authorization control defined in a wallet/AA address's definition, enabling unauthorized spending beyond the intended limit — impacting availability/integrity of fund controls (comparable in class to the CVSS `A:H` impact of the original advisory, translated to fund-loss/authorization-bypass here rather than crash).

### Likelihood Explanation
Reachable by any unprivileged unit poster whose address (or an address referencing them) has a definition using the `sum` operator with `at_most` or `equals`; the attacker only needs to craft a single unit with enough matching inputs/outputs summing near or above `Number.MAX_SAFE_INTEGER`. This requires large individual amounts (near `MAX_CAP`) and several matching messages within the size/message limits, which is feasible within existing per-unit limits (`MAX_MESSAGES_PER_UNIT`, `MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`), making exploitation practical without special privileges, though it does require a target address definition that actually relies on `sum`.

### Recommendation
Replace the plain-number accumulation in the `sum` case with an integer-safe/BigInt or `Decimal`-based accumulator (the codebase already uses `decimal.js` elsewhere, e.g. `formula/evaluation.js`), and explicitly reject sums whose accumulation ever exceeds `Number.MAX_SAFE_INTEGER` (not just `isFinite`), before performing `at_least`/`at_most`/`equals` comparisons.

### Proof of Concept
1. Deploy an address whose definition includes a clause such as `['sum', {filter: {what: 'output', asset: 'base'}, at_most: 5000000000000000}]` guarding a spend authorization.
2. Craft a single unit whose payment message(s) contain ~10+ outputs each with `amount` close to `constants.MAX_CAP` (1e15), such that the true sum exceeds `Number.MAX_SAFE_INTEGER` (e.g., 10 outputs × 1e15 = 1e16) but whose floating point accumulation via repeated `sum += amount` rounds/truncates to a value that still satisfies `sum <= at_most` due to precision loss in the double representation.
3. Submit the unit; `validateAuthentifiers` in `definition.js` evaluates the `sum` condition, computes the lossy `sum`, and incorrectly authorizes the unit despite the true spent amount exceeding the configured limit.
