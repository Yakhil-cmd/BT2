### Title
Fee-on-Transfer / Deflation Token Accounting Mismatch in Bridge Allows Draining Counterpart Liquidity — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`requestERC20Transfer` pulls `_value + _feeLimit` tokens from the caller via `safeTransferFrom`, but never verifies how many tokens the bridge actually received. For fee-on-transfer (deflation) tokens the bridge receives `(1 − rate) × (_value + _feeLimit)`, yet the `RequestValueTransfer` event is emitted with the full caller-supplied `_value`. The counterpart bridge reads that event and releases the full `_value` to the recipient, draining its liquidity pool by the deflation delta on every cross-chain transfer.

### Finding Description

In `requestERC20Transfer`:

```solidity
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

The bridge blindly trusts `_value` as the amount locked. `_requestERC20Transfer` then emits `RequestValueTransfer` with that same `_value`: [2](#0-1) 

The counterpart bridge's `handleERC20Transfer` reads `_value` from the event and releases it unconditionally:

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [3](#0-2) 

No balance snapshot is taken before or after the `safeTransferFrom` call to compute the actual received amount. The same flaw exists in the 1-step `onERC20Received` path, where `_value` is passed in by the token contract itself and trusted without verification: [4](#0-3) 

`_payERC20FeeAndRefundChange` in `BridgeFee.sol` also issues outbound transfers (`fee` to `feeReceiver`, `feeRefund` to `from`) based on the nominal amounts, not the actual balance received: [5](#0-4) 

### Impact Explanation

**Broken invariant:** `tokens_locked_on_source ≥ tokens_released_on_destination`.

For each `requestERC20Transfer` call with a deflation token at rate `r`:
- Source bridge receives: `(1 − r) × (_value + _feeLimit)`
- Destination bridge releases: `_value`
- Net drain per call: `_value − (1 − r) × (_value + _feeLimit)` tokens from the destination bridge's liquidity pool

This is an unauthorized transfer of bridged assets from the destination bridge's reserve. Repeated calls drain the pool completely. In `modeMintBurn = false` (lock/unlock mode), the destination bridge holds real token reserves that are directly stolen. In `modeMintBurn = true`, the source-side burn of `_value` is correct but the fee/refund accounting inside `_payERC20FeeAndRefundChange` still operates on nominal amounts, causing the bridge to attempt transfers it cannot cover.

### Likelihood Explanation

The bridge owner must register a token before it can be used. However:
1. Bridge operators may not audit every registered token for fee-on-transfer behavior.
2. Some tokens add deflation mechanics via upgrades after registration.
3. Once a deflation token is registered, **any unprivileged user** can call `requestERC20Transfer` repeatedly to drain the counterpart bridge's reserves — no further privilege is required.

The trigger is therefore semi-trusted (owner registers token) + fully unprivileged exploitation (any user drains liquidity).

### Recommendation

Measure the actual received amount using a balance snapshot:

```solidity
function requestERC20Transfer(...) public {
    uint256 balBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)) - balBefore;
    require(actualReceived == _value.add(_feeLimit), "deflation token not supported");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Alternatively, document explicitly that fee-on-transfer tokens are not supported and add a token registration guard that rejects them.

### Proof of Concept

1. Deploy a deflation ERC20 token with a 10% burn-on-transfer rate.
2. Register the token on both the source and destination bridges (owner step).
3. Fund the destination bridge with 1000 tokens as liquidity.
4. As an unprivileged user, call `requestERC20Transfer(tokenAddr, attacker, 100, 0, "0x")` on the source bridge.
   - `safeTransferFrom` pulls 100 tokens; bridge receives 90 (10 burned).
   - `RequestValueTransfer` event emits `valueOrTokenId = 100`.
5. Operators observe the event and call `handleERC20Transfer(..., 100, ...)` on the destination bridge.
   - `safeTransfer(attacker, 100)` succeeds, sending 90 to attacker (10 burned in transit).
   - Destination bridge balance decreases by 100; source bridge locked only 90.
6. Net loss to destination bridge per iteration: 10 tokens. Repeat until drained. [6](#0-5) [7](#0-6)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
