### Title
AA payments to a spender-attested asset permanently fail and bounce if the payee is not attested (attestation-list blacklist equivalent) - ([File: aa_composer.js])

### Summary
When an Autonomous Agent (AA) sends a payout in a `spender_attested` asset to a specific address (e.g., a lottery/marketplace winner determined by the AA's logic), the payment message is only checked for attestation validity when the response unit is validated, not before the recipient address is fixed in the AA's `messages`. If that address is not on the asset's attestor-approved list (the ocore analog of being "blacklisted" from a whitelisted/KYC-style token such as USDC), unit validation permanently fails with `"some output addresses are not attested"`, forcing the whole AA response to bounce every single time the trigger (or a retry with the same recipient) is processed [1](#0-0) .

### Finding Description
`validatePaymentInputsAndOutputs()` enforces that for any asset with `spender_attested = true`, every output address in the payment must be on the current attestor-approved list, otherwise the unit is rejected outright: [1](#0-0) 

This same rule also governs `is_transferrable` restrictions and `transfer_condition`/`issue_condition` evaluation, any of which can permanently block a payment to a specific address depending on the asset's definition [2](#0-1) .

Inside `aa_composer.js`, when an AA builds and sends a response unit, it constructs payment outputs (e.g., to a winner address stored in state vars or computed from the trigger) and only discovers a validation failure after calling `validateAndSaveUnit(objUnit, ...)`. On any validation failure, the code calls `bounce(err)`, which discards the entire response unit (including all of its outputs and any state updates that were conditioned on that response being finalized): [3](#0-2) 

Because the recipient address is deterministic and doesn't change between retries (it's the same winner/beneficiary computed by the AA's formula), every subsequent attempt to pay that specific address in that specific asset hits the identical `"some output addresses are not attested"` (or `"the asset is not transferrable"` / `"transfer or issue condition not satisfied"`) error and bounces again. This is architecturally identical to the reported bug class: a single recipient's exclusion from an asset's allow-list (functionally equivalent to a blacklist) makes an otherwise-correct payout permanently unfulfillable, because the failure is deterministic and recipient-specific rather than transient.

### Impact Explanation
Any AA that distributes rewards, refunds, or payouts in an asset defined with `spender_attested: true` (or with `is_transferrable`/`transfer_condition` restrictions) is exposed: if the intended recipient is not (or no longer) on the attestor list, the AA's payment response bounces indefinitely. Depending on the AA's state-machine design, this can permanently freeze the winner's payout and any bytes/asset amounts bundled with it in that same response, since the AA has no code path to retry with a different address or fall back to per-asset claiming — the entire response either succeeds atomically or bounces atomically. This is a fund-freezing impact analogous to the original USDC-blacklist finding, reachable by any unprivileged party who can (a) become the computed recipient of an AA payout and (b) fail attestation for the payout asset (e.g., have their attestation revoked, or simply never having been attested).

### Likelihood Explanation
Any asset creator can define an asset with `spender_attested: true`, and any AA developer can build payout logic using such assets without realizing that unit-level, all-or-nothing output validation means one non-attested recipient blocks the entire response. Attestor lists are dynamic (`asset_attestors` messages can update them), so an address that was attested at deposit time can lose attestation before the payout unit is composed and validated, making this a realistic scenario rather than a purely theoretical one.

### Recommendation
- In AA documentation/guidance, warn AA authors against bundling a fixed, unretryable recipient address for `spender_attested` or `transfer_condition`-restricted assets in a single all-or-nothing response.
- Consider adding a composer-side pre-check in `aa_composer.js`'s `completePaymentPayload`/`sendUnit` path that validates attestation/transfer conditions for `spender_attested` assets *before* committing to send outputs, allowing the AA formula to react (e.g., skip the payout, log an error state var, or redirect to an escrow) instead of unconditionally bouncing.
- Encourage/require AA payout designs to support per-asset or per-recipient claim functions (pull payments) rather than push payments bundled with unrelated state changes, so a single unattested recipient cannot freeze the whole response.

### Proof of Concept
1. An asset is defined with `spender_attested: true` and a limited attestor list [4](#0-3) .
2. An AA-based lottery/marketplace accepts deposits in this asset and computes a winner/beneficiary address from trigger data or state vars, then attempts to pay them via a `payment` message in `sendUnit()` [5](#0-4) .
3. Before the payout unit is finalized, the winner's attestation is revoked (or they were never attested) via an `asset_attestors` update.
4. When the AA's response unit reaches `validateAndSaveUnit`, `validatePaymentInputsAndOutputs` rejects it with `"some output addresses are not attested"` [6](#0-5) , and `aa_composer.js` calls `bounce(err)` [7](#0-6) , discarding the payout and any bundled state changes.
5. Since the winner address and the attestation status don't change on retry, every future attempt to run the same payout logic bounces identically, permanently denying the winner their reward.
