### Title
`seen` spending/asset condition grants unbounded, non-consuming authorization from a single historical on-chain event, enabling replayable unauthorized issuance/spending - (File: definition.js)

### Summary
The `seen` operator in address/asset definitions (`ocore--014/definition.js`) authorizes spending, or, more critically, asset issue/transfer by simply checking whether a matching input/output *ever existed* in stable history. It never marks the matched record as consumed and never binds the check to the specific unit/spend request being authorized, so the exact same historical event can satisfy the condition an unlimited number of times, for any number of future units.

### Finding Description
`seen` is implemented in `validateAuthentifiers` in `definition.js`: [1](#0-0) 

The evaluator runs a plain existence query (`SELECT 1 ... LIMIT 1`) against historical `inputs`/`outputs` filtered only by `asset`, `type`, `address`, and `amount`/`amount_at_least`/`amount_at_most`:
```
SELECT 1 FROM {what}s CROSS JOIN units USING(unit) ...
WHERE main_chain_index<=? AND sequence='good' AND is_stable=1 AND (asset IS NULL OR is_private=0)
  AND asset=? AND address=? [AND amount=?]
LIMIT 1
```
There is no `is_spent` check, no serial/nonce binding, and no record of "this seen-event has already been used to satisfy condition X." Once a qualifying transfer/output exists on-chain, the condition evaluates `true` forever, for every unit that references it, with no per-use consumption — structurally identical to the reported bug class: "matches a transfer purely on token/to/amount... binds proof neither to the challenge... nor any record of prior use."

Crucially, `seen` can appear in **asset issue/transfer conditions**, which — unlike address-spending definitions — do **not** require a signature branch at all: [2](#0-1) 
`if (!bHasSig && !bAssetCondition) return handleResult("each branch must have a signature");` — the signature requirement is explicitly skipped when `bAssetCondition` is true. So an asset can be defined with an issue/transfer condition consisting solely of `["seen", {...}]`, meaning literally anyone can trigger issuance/transfer with zero signature, as long as the historical event was seen once.

These asset conditions are evaluated during payment validation for every issue/transfer input: [3](#0-2) 
`Definition.evaluateAssetCondition(conn, payload.asset, arrCondition, objUnit, objValidationState, ...)` — called once per unit, with no cross-unit tracking of which "seen" facts have already been consumed.

Per-issue double-spend protection only dedups on `serial_number` for the *issue message itself*, not on the underlying "seen" fact: [4](#0-3) 
An attacker simply picks a new `serial_number` for each issuance, satisfies the static "seen" filter with the same, single, already-mined historical payment, and issues again.

### Impact Explanation
An asset definer (or any unprivileged unit poster targeting an asset that uses `seen` in its issue/transfer condition) can:
- Repeatedly issue new units of a capped/limited asset using one single historical payment as "proof," causing unbounded supply inflation of that asset.
- Repeatedly satisfy a `seen`-based spending branch of an address definition using one historical event, enabling unauthorized/duplicate withdrawal authorizations from that address's fund-holding definition (e.g. escrow/AA-adjacent contracts built with definition templates), causing loss of funds for the counterpartly relying on the "occurred once, therefore may be spent once" assumption.

This satisfies the "concrete unauthorized spending / supply inflation / AA-adjacent fund loss" bar, because `seen` grants an unlimited number of independent authorizations from a single consumable-looking on-chain fact.

### Likelihood Explanation
Reachable by any unprivileged unit poster who is (a) the definer of an asset using a `seen`-based issue/transfer condition, or (b) a party who knows an address definition contains a `seen` branch and can produce units invoking that branch. No special privilege, hub cooperation, or race condition is needed — only knowledge of one prior on-chain event (which, like the CVE's public block explorer scenario, is inherently public since it must be `is_stable=1`, `sequence='good'` and non-private for `seen` to see it at all: `AND (asset IS NULL OR is_private=0)`). The bug is deterministic and repeatable, not a timing race.

### Recommendation
- Require `seen` conditions to bind to a per-use nonce/challenge (e.g., unique per triggering unit) so a single historical event cannot be reused across multiple authorizations, or
- Track consumption of `seen` matches (e.g., via a `spend_proofs`-like ledger keyed on the matched `unit`/`message_index`/`output_index`) so each historical input/output can satisfy the condition at most once, and
- Disallow `seen` (or require it be combined with a mandatory signature/other single-use authentifier) inside `bAssetCondition` branches, closing the "no-signature-required" issuance/transfer path entirely.

### Proof of Concept
1. Definer creates asset `X` with `issue_condition = ["seen", {what: "output", asset: "base", amount: 1000000, address: "DEFINER_ADDRESS"}]` (no signature required in this branch since `bAssetCondition` is true).
2. Attacker sends one public, stable payment of `1,000,000` bytes to `DEFINER_ADDRESS` (this can even be an old, already-public transaction if it happens to match the filter).
3. Attacker repeatedly posts `issue` messages for asset `X` with new `serial_number` values each time. Each issuance unit is validated by `evaluateAssetCondition` → `Definition.validateAuthentifiers` → `seen` case, which re-runs the same existence query and returns `true` every time, because the query never marks the matched output as consumed.
4. Attacker mints unlimited units of asset `X` from a single 1,000,000-byte payment, inflating supply indefinitely.
