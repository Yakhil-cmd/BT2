### Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, letting a stack-scoped token read any stack's state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` binds every `ApiClient` token to the set of stacks it is allowed to touch via the `stacks` helper, which is consumed by `stack` (`stacks.from_param!(params[:stack_id])`). `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, skipping the `stacks` scoping entirely. This breaks the binding "the stack(s) a token authorises == the stack the request actually touches," analogous to the ERC4626 report's core theme: a check (`_checkMinShares`) is bypassed because the code path that matters (`deposit()`'s `previewDeposit`) is not the one actually enforcing the invariant. Here, permission is checked generically (`read:stack`) but the specific-stack scope binding enforced everywhere else (`Stack.where(id: current_api_client.stack_id)`) is silently dropped for this one controller.

### Finding Description
`Api::BaseController#stacks` is the sole place that encodes the equality "stack(s) a token authorises": [1](#0-0) 
Every other resource controller (`CommitsController`, `DeploysController`, `TasksController`, `StacksController`, etc.) inherits `stack` from `BaseController`, so a client created with a `stack_id` (e.g. fixture `here_come_the_walrus`, scoped to stack `shipit`) can only resolve stacks inside `Stack.where(id: current_api_client.stack_id)`, confirmed by: [2](#0-1) 

`Api::CCMenuController`, however, redefines `stack` to bypass that scoping: [3](#0-2) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which merely checks that the string `"read:stack"` is present in `permissions` — it never validates against the specific stack instance being loaded: [4](#0-3) 

So the equality that should hold — `current_api_client.stack_id == requested stack.id (when stack_id is set)` — is never checked in this controller. Any token that has the `read:stack` permission bit, regardless of its `stack_id` restriction, can pass any `stack_id` param and receive that other stack's CCMenu status.

### Impact Explanation
This is an unauthorized read of stack state through a token whose entire purpose was to be scoped to a single stack (the `stack_id` column on `ApiClient`, and the UI/API flows that create restricted tokens for individual stacks/repos). It matches the in-scope "High" impact category: "unauthenticated read of stack state ... via a scope/authorization it should not have." An organization operating multiple stacks/repositories through one Shipit instance, issuing narrowly-scoped `read:stack` tokens to different teams, would have that isolation completely undermined for the CCMenu endpoint: any team's token can enumerate build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, `webUrl`) of stacks they were never granted access to.

### Likelihood Explanation
Low-to-Medium: it requires possession of *some* valid `ApiClient` token with `read:stack` permission (which is a normal, low-privilege, widely distributed credential in Shipit deployments — e.g., handed to CI dashboards, status badges, or CCMenu integrations). No repository write access, GitHub session, or admin privilege is needed; only the difference between "my token's scope" and "the stack_id I put in the URL" needs to be exploited, which is a trivial parameter substitution once any scoped token is known.

### Recommendation
Have `Api::CCMenuController#stack` reuse the inherited, scoped `stacks` method (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so the `stack_id` restriction on `ApiClient` is enforced consistently across all API controllers.

### Proof of Concept
1. Admin issues a scoped token to Team A: `ApiClient.create!(creator: team_a_user, name: 'Team A CI', stack: stack_a, permissions: %w[read:stack])`.
2. Team A uses that token as intended: `GET /api/stacks/team-a-org/repo/production/ccmenu.xml?token=<team_a_token>` → succeeds (expected).
3. Team A (or anyone who obtains this token) requests Stack B's status instead: `GET /api/stacks/team-b-org/other-repo/production/ccmenu.xml?token=<team_a_token>`.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped, request 3 succeeds and returns Stack B's build/lock status, even though `team_a_token.stack_id == stack_a.id`, demonstrating the token authorises stack A but is able to touch stack B — the very binding this class of finding targets.
