### Title
Signature-verification organization is not bound to the repository/organization actually written by webhook handlers, allowing forged webhook events - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC signature against using `repository_owner`, a value read from the same untrusted JSON body it is trying to authenticate (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). [1](#0-0)  If the organization resolved by that field has no `webhook_secret` configured, `GithubApp#verify_webhook_signature` unconditionally returns `true`: `return true unless webhook_secret`. [2](#0-1)  Once "verified," the raw payload is dispatched to handlers, but the handlers resolve the actual `Repository`/`Stack`/`Team` to mutate from a *different* JSON field — `payload.dig('repository', 'full_name')` in the base `Handler` class [3](#0-2)  — or, for `membership` events, directly from `team`/`member`/`organization` fields with no re-derivation of the signing organization. Because nothing cross-checks that the organization used to select the (possibly secret-less) verifier is the same organization/repository the handler actually acts on, an attacker can forge a payload that authenticates as an organization with no configured `webhook_secret` while writing to a completely different, victim-owned repository or team.

### Finding Description
This is the direct analog of the GroupBuy bug class: a value used to satisfy a trust check (`minReservePrices[_poolId]` bound only by an inequality in `purchase`) is not the same value later relied upon as exact truth in `claim`. Here, the "trust check" is webhook signature verification, and the "value relied upon later" is which repository/organization is mutated:

- Binding claimed: `organization used for HMAC verification == organization/repository whose state the handler writes`.
- Actual code: the verification org comes from `params.dig('repository','owner','login') || params.dig('organization','login')` [4](#0-3) , while the write target comes from an independent field, `payload.dig('repository','full_name')` [5](#0-4) , or for `membership` events from `team`/`member` fields with no repository at all (confirmed by team/membership creation directly off webhook params in tests). [6](#0-5) 
- Shipit explicitly supports multiple GitHub App configurations per organization, and the setup/test fixtures show that `webhook_secret` is optional per organization (e.g. `webhook_secret: # nil` for `OrgTwo`). [7](#0-6)  For any organization configured without a `webhook_secret`, `verify_webhook_signature` returns `true` for *any* signature header value, including a missing or garbage one. [2](#0-1) 

Because `repository.owner.login` (or `organization.login`) and `repository.full_name` / `team`/`member` are independent, attacker-supplied JSON fields inside the very payload that's supposed to be authenticated, an attacker can set the "authenticating" org to one with no secret configured on this Shipit instance, while setting the "acted-upon" repository/team fields to a victim's repository or a privileged team — with no code path ever confirming these two identities match.

### Impact Explanation
If any organization managed by the Shipit instance has no `webhook_secret` set (documented as optional, see `docs/setup.md`), an unprivileged attacker (no Shipit session, no `ApiClient` token, no GitHub App key) can:
- Forge `push`/`status`/`check_suite` events for any repository/stack tracked by the instance, since the handler resolves the stack purely from `repository.full_name` in the (auto-verified) payload, triggering `RefreshCheckRunsJob`, updating commit `Status` records that gate continuous deployment, etc.
- Forge `membership` events, which create/delete `Team` and `Membership` rows directly from payload fields with no ownership check tying them to the verifying organization, potentially adding an attacker-controlled login to a `Team` referenced by `Shipit.github_teams` authorization.

This crosses the listed High-impact category: "escalation into `Shipit.github_teams` authorization" and "unauthenticated read/mutation of stack state," and can contribute to an unauthorized deploy/rollback pipeline event, matching the rules' accepted impact categories.

### Likelihood Explanation
Requires a real, but plausible and common, operational precondition: at least one organization managed by the shared Shipit instance has not configured a `webhook_secret` (explicitly supported and documented as optional). Given that precondition, exploitation requires only an unauthenticated HTTP POST to the public `/webhooks` endpoint with a crafted JSON body — no credentials, tokens, or privileged access of any kind, matching the "unprivileged attacker" requirement.

### Recommendation
Derive the verification organization and the write-target organization/repository from the same canonical source, and reject the payload if they diverge. Concretely, after selecting `repository_owner` for signature verification, re-derive the acted-upon repository owner from the identical field, and reject any payload where `payload.dig('repository','owner','login')`/`payload.dig('organization','login')` doesn't match the owner segment of `payload.dig('repository','full_name')` (and, for `membership`, verify `organization.login` against the team's known parent organization already registered in Shipit). Additionally, do not treat a missing/blank `webhook_secret` as an automatic pass — either require every configured organization to have a secret, or fail closed when no secret is configured for a repository actually present in the database.

### Proof of Concept
1. Configure Shipit with two organizations: `victim-org` (has a `webhook_secret`) and `orgtwo` (no `webhook_secret`, per `secrets_double_github_app.yml` pattern). [7](#0-6) 
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "organization": {"login": "orgtwo"},
  "repository": {"owner": {"login": "orgtwo"}, "full_name": "victim-org/victim-repo"},
  ...push payload fields for victim-org/victim-repo...
}
```
No `X-Hub-Signature` header (or a garbage one) is required.
3. `verify_signature` resolves `Shipit.github(organization: 'orgtwo')`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally. [2](#0-1) 
4. `create` proceeds and dispatches to `Shipit::Webhooks::Handlers::PushHandler`, which resolves the target stack from `payload.dig('repository','full_name')` = `victim-org/victim-repo`, acting on the victim's stack despite the request never being authenticated for `victim-org`. [3](#0-2)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
