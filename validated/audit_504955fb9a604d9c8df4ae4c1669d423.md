### Title
Bridge Handle-Transfer Permanently Stuck When `_to` Rejects KLAY — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` performs the KLAY push-transfer to `_to` **after** recording the nonce state, but wraps both in the same atomic transaction. If `_to` is a contract that rejects KLAY (no payable fallback), the `require(ok, ...)` at line 99 reverts the entire transaction — including the nonce bookkeeping written at lines 83–84. Because the nonce entry `handleNoncesToBlockNums[N]` is never durably set, `lowerHandleNonce` can never advance past N, and the bridge's recovery system loops forever on that nonce. The same structural defect exists in `handleERC20Transfer` when the bridged ERC20 token implements a transfer blacklist.

---

### Finding Description

`handleKLAYTransfer` executes in this order:

```
_lowerHandleNonceCheck(_requestedNonce)          // line 75
_voteValueTransfer(_requestedNonce)              // line 77
_setHandledRequestTxHash(_requestTxHash)         // line 81
handleNoncesToBlockNums[N] = _requestedBlockNum  // line 83
_updateHandleNonce(N)                            // line 84  ← advances lowerHandleNonce
emit HandleValueTransfer(...)                    // line 86
(bool ok,) = _to.call.value(_value)("")          // line 98  ← push transfer
require(ok, "handleKLAYTransfer: transfer failed") // line 99
``` [1](#0-0) 

If `_to` is a contract with no payable fallback, `ok == false` and `require` reverts the entire transaction. Every write from lines 81–84 is rolled back. `handleNoncesToBlockNums[N]` remains `0`.

`_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive `i` starting from `lowerHandleNonce`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [2](#0-1) 

Because `handleNoncesToBlockNums[N]` is always `0` (every attempt reverts), `lowerHandleNonce` is permanently frozen at `N` and `recoveryBlockNumber` is frozen at the block of the last successfully handled nonce before `N`.

The off-chain recovery daemon (`valueTransferRecovery`) reads `RecoveryBlockNumber` from the contract as its scan start point: [3](#0-2) 

Since `recoveryBlockNumber` never advances, the daemon perpetually re-scans from the same old block, re-discovers nonce `N`, re-submits `handleKLAYTransfer`, and the cycle repeats indefinitely.

The identical pattern exists in `handleERC20Transfer` — if the bridged ERC20 token implements a transfer blacklist (e.g., USDC-style) and `_to` is blacklisted, `safeTransfer` reverts at line 71, rolling back the nonce state written at lines 53–54: [4](#0-3) 

---

### Impact Explanation

- **`lowerHandleNonce` is permanently frozen at nonce `N`** — the bridge's sequential nonce invariant is broken.
- **`recoveryBlockNumber` is permanently frozen** — the recovery system (`vt_recovery.go`) loops forever on nonce `N`, wasting operator gas on every cycle.
- **Bridged assets for nonce `N` are permanently locked** — the KLAY (or ERC20) that the bridge contract holds for that transfer can never be delivered; there is no skip-nonce or force-complete mechanism.
- Nonces `> N` can still be handled (they pass `_lowerHandleNonceCheck`), but `lowerHandleNonce` never advances past `N`, so the bridge's recovery state is permanently corrupted for all future nonces.

---

### Likelihood Explanation

Any user can call `requestKLAYTransfer` and supply a `_to` address that is a contract with no payable fallback — this is a zero-cost, unprivileged action. No special role or majority-validator collusion is required. The trigger is a single valid transaction on the source chain. Once the `RequestValueTransfer` event is emitted, bridge operators are obligated to call `handleKLAYTransfer` on the destination chain; they have no mechanism to skip or override the stuck nonce.

---

### Recommendation

1. **Separate nonce commitment from asset delivery.** Commit `handleNoncesToBlockNums[N]` and advance `lowerHandleNonce` unconditionally before attempting the transfer. If the transfer fails, record the failure and allow the recipient to pull their funds later (pull-payment pattern), rather than reverting the nonce state.

2. **Add a skip/rescue function** (owner-only) that can mark a nonce as permanently failed and advance `lowerHandleNonce` past it, releasing the bridge from the infinite retry loop.

3. **For ERC20 transfers**, validate that `_to` is not blacklisted by the token contract before committing the nonce, or use the same pull-payment pattern.

---

### Proof of Concept

1. Deploy `Bridge` (non-mintBurn mode) on the destination chain, funded with KLAY.
2. Deploy a `RejectKLAY` contract with no payable fallback on the destination chain.
3. On the source chain, call `requestKLAYTransfer(rejectKLAYAddr, value, "")` — this emits `RequestValueTransfer` with nonce `N` and `_to = rejectKLAYAddr`.
4. Bridge operators call `handleKLAYTransfer(..., rejectKLAYAddr, value, N, blockNum, "")` on the destination bridge.
5. Execution reaches line 98: `(bool ok,) = rejectKLAYAddr.call.value(value)("")` → `ok = false`.
6. Line 99 `require(ok, ...)` reverts the transaction; `handleNoncesToBlockNums[N]` remains `0`.
7. Verify: `bridge.lowerHandleNonce()` is still `N`; `bridge.recoveryBlockNumber()` is still the block of nonce `N-1`.
8. Repeat step 4 indefinitely — every attempt reverts. The bridge is permanently stuck on nonce `N` with no on-chain escape path. [5](#0-4) [6](#0-5) [7](#0-6)

    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;

            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];

    }
