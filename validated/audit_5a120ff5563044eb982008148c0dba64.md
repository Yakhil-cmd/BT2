### Title
`Command#start`'s `NotFound`/`Denied` rescue interpolates the fully-substituted first argument (leaking `$VAR` → host `ENV[VAR]`) into the exception message instead of the literal step - ([File: lib/shipit/command.rb])

### Summary
`Command#start` builds its `NotFound`/`Denied` error messages from `interpolated_arguments.first`, which is the *post-substitution* argument produced by `EnvironmentVariables#interpolate`, not the literal step template. Because `EnvironmentVariables#interpolate` falls back to the host process's `ENV[variable]` when the variable isn't in the command's own `@env` hash, any step whose first token is `$SOME_VAR` for a variable that resolves to a nonexistent/unusable path will cause the resolved value to be embedded verbatim in the raised message, which callers (`TaskExecutionStrategy::Default#run`, `EphemeralCommitChecks#capture`) write directly into task/check output.

### Finding Description
The claimed binding is: `raised_message == literal_step_template` (error text shown to task viewers should equal the step as written in `.shipit.yml`/definitions, never the interpolated value). This is false in the code:

- `Command#interpolated_arguments` calls `interpolate_environment_variables(@args)` → `EnvironmentVariables.with(env).interpolate(argument)`. [1](#0-0) 
- `EnvironmentVariables#interpolate` substitutes `$VAR` tokens using `@env.fetch(variable) { ENV[variable] }` — an explicit fallback to the Shipit process's own environment when the variable isn't in the command-scoped env. [2](#0-1) 
- `Command#start` raises `NotFound`/`Denied` using `Shellwords.split(interpolated_arguments.first).first`, i.e. the **interpolated** (secret-resolved) value, not `@args.first` (the literal template): [3](#0-2) 
- This exception (`Command::Error` subclass) is caught and its `.message` is written straight into task/check output in two call sites:
  - `TaskExecutionStrategy::Default#run`: `rescue Command::Error => e; @task.write("\n#{e.message}\n")`. [4](#0-3) 
  - `EphemeralCommitChecks#capture`: `rescue Command::Error => e; write(e.message); raise`. [5](#0-4) 

`EphemeralCommitChecks#run` builds its command list from `DeploySpec::FileSystem.new(directory, stack)` read from the checked-out commit itself (`dependencies_steps`, `review_checks`), i.e. from the `.shipit.yml`/`.shipit/*.yml` content of the commit under test: [6](#0-5) [7](#0-6) 

This means the step list run by ephemeral checks is literally sourced from the commit's own files — content that, for a pull request, originates from the contributor's branch. If a step's first token is `$SOME_HOST_ENV_VAR_NAME` and that name resolves via the host's `ENV` (not the stack's configured `@env`/`Shipit.env`) to a non-executable string (e.g. a secret value, connection string, token), `Command#start` will raise `NotFound`/`Denied` with that literal secret value embedded in the message, and `EphemeralCommitChecks#capture` will write it into `@output`.

Existing guards do not prevent this: `EnvironmentVariables#permit`'s whitelist is a separate code path used elsewhere and is not applied on the interpolation path used by `Command#start`; `verify_signature`/webhook auth only validate that the webhook truly came from GitHub for the target repository, they say nothing about the *content* of the commit being checked, which by design is untrusted PR content that ephemeral checks are meant to test.

### Impact Explanation
This is a genuine information-disclosure bug in `Command#start`: the exception message can contain data resolved from the Shipit process's own `ENV` rather than the literal, developer-authored step text, which is a real deviation from the expected behavior (Command-line invocation errors are supposed to only ever reveal what's already public in the step template).

That said, I could not verify within this codebase whether `EphemeralCommitChecks#output` (or the equivalent `@task.write` output in `TaskExecutionStrategy::Default`) is ever exposed to a party that holds no Shipit session and is not already a member of `Shipit.github_teams`/a stack maintainer. Shipit's task/check output viewing normally requires an authenticated, authorized session (`current_user`, team membership) — I was not able to trace a controller path in the time available that serves this output to a fully unauthenticated or merely PR-authoring party. Additionally, exploiting the leak requires the step's first token to literally be `$VARNAME` for a variable name the attacker must guess/know exists in the host process `ENV` and is not present in the stack's declared `@env`/`Shipit.env` — this is not attacker-controlled by default, it requires either the target repo's existing `.shipit.yml` to already reference such a variable, or (for ephemeral checks specifically) the attacker's PR to introduce such a step, which only matters for repositories/stacks that run checks against untrusted fork content in the first place.

Given these two unresolved preconditions (who can view the output, and whether the target variable's name/host-`ENV` layout is knowable/guessable by the attacker), I can confirm the code-level bug but cannot fully confirm an end-to-end unprivileged exploitation path to a Critical/High impact category as strictly required by the rules.

### Likelihood Explanation
- Requires a stack configured to run `EphemeralCommitChecks` (review checks) against PR commits from potentially untrusted forks, and the target repo's checked-out `.shipit.yml` at that commit to contain (or be modifiable by the PR to contain) a step whose first token is `$VARNAME`.
- Requires `VARNAME` to be absent from the stack's own `@env`/`Shipit.env` but present in the Shipit host process's `ENV`, and to not correspond to an actually-executable path (otherwise the command runs instead of raising `NotFound`/`Denied`), so this is somewhat fragile/guess-dependent.
- Requires the resulting task/check output containing the leaked value to be visible to the attacker without additional privileges, which I was unable to confirm.

### Recommendation
In `Command#start`, use the literal, non-interpolated `@args.first` (split via `Shellwords`) for the `NotFound`/`Denied` messages instead of `interpolated_arguments.first`, so the error text never contains resolved environment-variable values:
```ruby
rescue Errno::ENOENT
  raise NotFound, "#{Shellwords.split(@args.first).first}: command not found"
rescue Errno::EACCES
  raise Denied, "#{Shellwords.split(@args.first).first}: Permission denied"
```
Additionally, consider whether `EnvironmentVariables#interpolate`'s fallback to the bare host `ENV[variable]` (rather than only the explicitly-permitted/whitelisted env) is intentional, since it allows any step author to reference arbitrary host process environment variables by name.

### Proof of Concept
```ruby
# test/unit/command_test.rb (illustrative, not to be placed under review as attack-chain proof)
test "#start leaks interpolated ENV fallback value in NotFound message" do
  ENV['MISSING_SECRET_BINARY'] = '/secret/tool'
  command = Shipit::Command.new('$MISSING_SECRET_BINARY', chdir: Dir.tmpdir)
  error = assert_raises(Shipit::Command::NotFound) { command.start }
  assert_includes error.message, '/secret/tool'
ensure
  ENV.delete('MISSING_SECRET_BINARY')
end
```
This proves the `Command#start` code-level bug (binding broken: message contains interpolated value, not literal `$MISSING_SECRET_BINARY` template). It does **not** by itself establish that an unprivileged attacker (PR author with no Shipit session/team membership) can both (a) control the step text and (b) view the resulting task/check output — those two links require confirmation against the specific stack/repo configuration and the output-serving controllers, which I could not fully trace in this session.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
