### Title
Stale unstable-op-vote flag captured before lock acquisition lets stability advance without required per-MCI OP-list re-validation - (File: main_chain.js)

### Summary
`determineIfStableInLaterUnitsAndUpdateStableMcFlag` snapshots whether an OP-list vote is currently "in flight" (unstable) into `bOpListCanChange` *before* acquiring the `handleJoint` mutex, then uses that stale boolean to decide, for every MCI in the loop that follows, whether a per-step re-check of stability against the (potentially changing) OP list is required. Any `system_vote`/`system_vote_count` message for `op_list` that becomes unstable after the flag is captured, but before or during the loop, is never accounted for, so the affected MCIs are stabilized without the safety re-check the code was designed to perform.

### Finding Description
The function first determines that `earlier_unit` is stable in the caller's view, then computes:
```
const bOpListCanChange = hasUnstableOpVoteCount();
``` [2](#0-1) 

`hasUnstableOpVoteCount()` simply scans `storage.assocUnstableMessages` (in-memory unstable messages) for any pending `system_vote_count` on `op_list` [3](#0-2) . This check is a snapshot taken at a single point in time, but the subsequent code doesn't run atomically with respect to that check: the function then waits to acquire the `handleJoint` mutex lock [4](#0-3) , and only afterward loops over every not-yet-stable MCI between `last_stable_mci+1` and `new_last_stable_mci`, calling `stabilizeMci(mci)` for each one [5](#0-4) .

Inside that loop, the per-step re-validation (`determineIfStableInLaterUnits` against the best parent's up-to-date OP list) is only executed `if (bOpListCanChange && mci >= constants.v4UpgradeMci)` [6](#0-5) . The accompanying comment makes clear the intended semantics: *"check stability before every step using the best parent's OP list ... The initial stability of the earlier_unit was determined using the OP list of the last stable unit"* [7](#0-6) . This is precisely the same pattern as the Merkl `getMerkleRoot` bug: a boolean gate based on whether a "dispute" (here, a pending OP-list vote) is outstanding is computed once, and if the underlying condition changes shortly afterward (new vote arrives, or an existing vote becomes unstable) between the snapshot and the actual state transition, the code proceeds as if no dispute exists.

Any unprivileged unit author can trigger this race by broadcasting a `system_vote` for `op_list` followed by a `system_vote_count` for `op_list` (validated for regular, non-AA units) [8](#0-7) [9](#0-8) . Such a unit becomes an "unstable message" tracked in `storage.assocUnstableMessages` as soon as it's written [10](#0-9) , and remains there until its MCI is marked stable, at which point the vote is applied via `saveSystemVote`/`countVotes` [11](#0-10) .

### Impact Explanation
If an OP-list vote becomes newly unstable in the window between `hasUnstableOpVoteCount()` being evaluated and the mutex being acquired (a window that can be arbitrarily widened by concurrent unit processing / lock contention), `bOpListCanChange` remains `false` for the entire multi-MCI stabilization loop even though an OP-list change is pending. The loop then skips the per-MCI `determineIfStableInLaterUnits` re-validation and calls `stabilizeMci` directly for every MCI, including ones whose "standard rule for advancing stability" (i.e., which witness/OP set is authoritative) should have been re-derived from the newer OP list. Different nodes racing this window differently can end up stabilizing (and hence finalizing) different MCIs/OP-list states, i.e., a **node disagreement on validity/stability** — the class of impact explicitly accepted by the validation rules — with attendant risk of the chain being unable to reach consensus on which units/values are final.

### Likelihood Explanation
The race requires only an ordinary, unprivileged unit author sending an `op_list` `system_vote` + `system_vote_count`, which is a documented, fully-permitted operation (no witness/OP privilege is required) [1](#0-0) . Triggering it precisely enough to land inside the narrow window between the `hasUnstableOpVoteCount()` snapshot and the `mutex.lock(["handleJoint"], ...)` acquisition is timing-sensitive and not trivially reproducible on demand, which lowers likelihood, but the flawed pattern (capture-then-use-stale-boolean across an await/lock boundary) is a structural defect independent of any specific attacker skill.

### Recommendation
Re-evaluate `hasUnstableOpVoteCount()` (or an equivalent "is any op_list vote outstanding" check) *after* acquiring the `handleJoint` mutex lock, immediately before starting the per-MCI stabilization loop, so the decision to skip the extra `determineIfStableInLaterUnits` re-check reflects the true state at the moment stabilization is actually performed — mirroring the Merkl fix of re-checking the disputer/disputed status at the point of use rather than relying on an earlier snapshot.

### Proof of Concept
1. An attacker (or any user) broadcasts a valid `system_vote` message for `op_list` followed immediately by a `system_vote_count` message for `op_list`, both of which pass validation for a regular unit [12](#0-11) .
2. Concurrently, another unit `earlier_unit` becomes stable in the view of later units, triggering `determineIfStableInLaterUnitsAndUpdateStableMcFlag` [13](#0-12) .
3. `bOpListCanChange = hasUnstableOpVoteCount()` is computed as `false` because the attacker's vote-count message has not yet been added to `storage.assocUnstableMessages` at that exact instant.
4. The attacker's unit is processed and its `system_vote_count` message is now tracked as unstable.
5. The mutex is acquired and the stabilization loop runs over several MCIs using the stale `bOpListCanChange=false`, skipping the OP-list-aware `determineIfStableInLaterUnits` re-check [5](#0-4) , stabilizing MCIs that a node winning the race differently would not have stabilized identically — producing a stability/validity disagreement across nodes.

function hasUnstableOpVoteCount() {
	for (let unit in storage.assocUnstableMessages) {
		for (let message of storage.assocUnstableMessages[unit]) {
			if (message.app === 'system_vote_count' && message.payload === 'op_list')
				return true;
		}
	}
	return false;
}
