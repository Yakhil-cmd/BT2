### Title
Webhook signature verification keys on `repository.owner.login` while every handler acts on `repository.full_name`, allowing a valid webhook sender for one GitHub organization to forge writes against any other organization's repositories - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment (the `github: { org_a: {...}, org_b: {...} }` config schema), each organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against by reading `params.dig('repository', 'owner', 'login')` from the *attacker-controlled* JSON body, not from any organization-scoped route or GitHub App identity. Every `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the repository/stack to act on using a *different* field of the same body: `payload.dig('repository', 'full_name')`. Because HMAC verification only proves "this body was signed with organization X's secret," and does not enforce that `repository.owner.login == repository.full_name`'s owner, an attacker who legitimately knows/controls one organization's webhook secret can sign a payload whose `owner.login` matches their own org (so verification passes) while setting `full_name` to a victim organization's repository, causing handlers to write state for a repository the attacker does not control.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes:
  - `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`
  - `github_app = Shipit.github(organization: repository_owner)`
  - `github_app.verify_webhook_signature(header_signature, request.raw_post)` [1](#0-0) [2](#0-1) 

  This only proves the raw body was HMAC-signed by whoever holds the `webhook_secret` for the organization named in `repository.owner.login`. It says nothing about which repository's data the rest of the JSON body describes.

- `verify_webhook_signature` in `lib/shipit/github_app.rb` is a pure HMAC-SHA1 comparison against the *entire* raw body using the secret for the selected `organization`: [3](#0-2) 

- Every webhook handler (`Shipit::Webhooks::Handlers::Handler` base class and all subclasses such as `PushHandler`, `StatusHandler`, pull-request handlers) determines the actual `Repository`/`Stack` to mutate using `payload.dig('repository', 'full_name')`, a separate JSON key from `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository the handler writes to`

Because `owner.login` and `full_name`'s owner segment are independent, attacker-controlled JSON fields inside the same signed body, this equality is never enforced. An attacker who is a legitimate holder of `org-attacker`'s `webhook_secret` (e.g., an admin of a GitHub App installed on their own, attacker-controlled org, hosted on the same shared Shipit instance) can:
1. Build a JSON payload where `repository.owner.login = "org-attacker"` (or `organization.login`) but `repository.full_name = "org-victim/some-repo"`.
2. Sign the raw body with `org-attacker`'s known `webhook_secret` (`sha1=HMAC(secret_attacker, raw_body)`).
3. POST to `/webhooks` with `X-Github-Event` set to any handled event (`push`, `status`, `membership`, `pull_request`, etc.) and `X-Hub-Signature` set to that signature.

`verify_signature` resolves `github_app = Shipit.github(organization: "org-attacker")`, uses `org-attacker`'s secret, and the signature matches → verification passes. `Shipit::Webhooks.for_event(event)` then dispatches to the handler, which resolves the repository using `full_name = "org-victim/some-repo"` and performs its normal side effects against that victim repository's stacks.

### Impact Explanation
This breaks the organization-authenticated vs. repository-written binding and enables cross-repository/cross-organization writes without any credential belonging to the victim organization:
- `PushHandler` can trigger `stack.sync_github(expected_head_sha:)` for a victim stack, forcing a GitHub sync job against arbitrary commit SHAs the attacker chooses.
- `StatusHandler` can call `commit.create_status_from_github!(params)` to inject forged CI statuses (`state`, `context`, `target_url`, `description`) for a victim's commits. Since `Commit#deployable?` is computed from stored statuses (`success? && !blocked?`) and `Stack#required_statuses`/`blocking_statuses` gate deploys, a forged "success" status can make an otherwise-unreviewed commit `deployable?`, directly enabling an unauthorized deploy on the victim stack. [7](#0-6) 
- Pull-request handlers can archive/unarchive victim review stacks or overwrite `github_pull_request` state for a victim's `PullRequest` records.
- `membership` handlers (referenced in tests) can create/delete `Membership`/`Team`/`User` records tied to a victim organization.

This satisfies the required Critical/High impact bar: it is a cross-repository write and can produce an unauthorized deploy, achieved purely by an unprivileged-relative-to-the-victim attacker who only needs their own (unrelated) organization's webhook secret — a credential Shipit's own multi-org design intentionally hands out to every onboarded organization independently.

### Likelihood Explanation
This is only exploitable when a single Shipit instance is shared across multiple GitHub organizations using the `github: { org_a: {...}, org_b: {...} }` config schema documented in `config/secrets.development.shopify.yml` and `config/secrets.development.example.yml`. In that documented, supported multi-tenant configuration, exploitation requires no privileged access to the victim org, no GITHUB_TOKEN, and no Shipit session — only knowledge of any one onboarded organization's `webhook_secret`, which by design every onboarded organization/admin possesses to configure their own GitHub App. This is a plausible and realistic deployment pattern given the engine explicitly supports and documents multi-org secrets.

### Recommendation
Enforce that the organization used to select/verify the webhook secret matches the organization actually referenced by `repository.full_name` (and any other repository identifiers used by handlers) before dispatching to handlers. Concretely, in `WebhooksController#verify_signature`/`create`, after verifying the signature, extract the owner from `repository.full_name` (or `organization.login` for org-level events) and reject the request (422) if it does not case-insensitively match `repository_owner` used for secret selection. Alternatively, look up the `Repository` record by `full_name` first, derive its `owner`, and require that owner to equal the organization whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two organizations, `org-attacker` and `org-victim`, each with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml` schema), both onboarded to the same Shipit instance and each having at least one stack (`org-victim/app`, `org-attacker/app`).
2. As an operator with legitimate access to `org-attacker`'s GitHub App settings, obtain `org-attacker`'s `webhook_secret`.
3. Construct a `push` (or `status`) webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker chosen sha>",
     "repository": {
       "owner": { "login": "org-attacker" },
       "full_name": "org-victim/app"
     }
   }
   ```
4. Compute `sha1=HMAC-SHA1(org-attacker's webhook_secret, raw_json_body)`.
5. POST to `/webhooks` with headers `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
6. Observe `WebhooksController#verify_signature` resolves `Shipit.github(organization: "org-attacker")`, validates the signature successfully against the raw body, and then `PushHandler` resolves `Repository.from_github_repo_name("org-victim/app")` and triggers `sync_github` on `org-victim`'s stack — a write the attacker was never authorized to perform, using only `org-attacker`'s credentials.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
