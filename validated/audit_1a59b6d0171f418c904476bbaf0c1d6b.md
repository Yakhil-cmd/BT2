### Title
Unhandled deferred exception in `decryptPackage` device-message unknown-key path causes wallet/device process crash - ([File: device.js])

### Summary
`device.js`'s `decryptPackage()` reads `objMyTempDeviceKey`/`objMyPermanentDeviceKey` and, when the `encrypted_package.dh.recipient_ephemeral_pubkey` does not match any of the recipient's known keys, schedules an unconditional `throw` inside a `setTimeout` callback that is **not** covered by the caller's `try/catch`. Any peer who knows a device's `device_address` can trigger this "unknown key" branch by sending a device message whose `encrypted_package` fields are syntactically valid but whose ephemeral pubkey deliberately does not match, causing an uncaught exception on the Node.js event loop — the same class of bug as the Firebird issue: a message that is processed and dereferences/derails on an unvalidated internal-state assumption before any prior authentication/pairing has occurred, crashing the process.

### Finding Description
`decryptPackage` in `device.js` is invoked whenever a `hub/message` justsaying or a self-addressed `hub/deliver` request is received, **before** the sender is checked against known correspondents: [1](#0-0) 

The function checks `objEncryptedPackage.dh.recipient_ephemeral_pubkey` against the device's temp key, previous temp key, and permanent key. If none match, it logs "message encrypted to unknown key" and defers a `throw` via `setTimeout(..., 100)`: [2](#0-1) 

The call sites wrap `decryptPackage` in a synchronous `try/catch`, e.g. in the `hub/message` handler: [3](#0-2) 

and in `wallet.js`'s arbiter dispute handler: [4](#0-3) 

Because the `throw` happens inside a `setTimeout` callback, it executes on a **later** turn of the event loop, completely outside the scope of these `try/catch` blocks. This means the exception becomes an uncaught exception rather than a handled decryption failure.

Reachability: the checks performed before `decryptPackage` is called only validate the *shape* and the *signature* of `objDeviceMessage` — the signature is verified against `objDeviceMessage.pubkey`, which is attacker-controlled (an attacker signs the crafted message with their own key pair): [5](#0-4) 

The correspondent-known check happens only *after* successful decryption, and pairing/`my_xpubkey`/`wallet_fully_approved` subjects are explicitly whitelisted for non-correspondents, confirming that this whole pathway is designed to be reachable by unpaired devices: [6](#0-5) 

So any remote party who knows (or guesses) a target's `device_address` can construct an `encrypted_package` with a `dh.recipient_ephemeral_pubkey` value that doesn't correspond to any of the device's known keys, sign it with their own key, and send it either through a hub (`hub/message`) or directly if the target is self-hosted (`hub/deliver`, `bToMe` branch): [7](#0-6) 

### Impact Explanation
If the deferred exception is not intercepted by a process-wide handler, it crashes the target's ocore-based process (wallet, AA-adjacent bot, or hub-serving node), producing a denial of service reachable by any unauthenticated party who knows only the victim's device address — directly analogous to the Firebird `op_crypt_key_callback` null-pointer crash triggered pre-authentication. This affects wallet/device availability for any Obyte GUI wallet, bot, or headless client using this code path.

### Likelihood Explanation
Triggering the "unknown key" branch requires no valid decryption material and no prior pairing — an attacker only needs the target's public device address (often shared for receiving payments/messages) and the ability to self-sign a message, which is always possible. This makes the trigger trivial and repeatable.

### Recommendation
Move the "unknown key" handling so it does not throw asynchronously outside of caller-controlled error handling: either return an error value synchronously (as the other branches already do via `return null`), or route the notification through `eventBus.emit('nonfatal_error', ...)` (already used elsewhere in this file) instead of a deferred `throw`, and let the caller's existing `try/catch`/`ifError` callbacks handle it uniformly.

### Proof of Concept
1. Determine or learn a target device's `device_address` (derivable from an exposed permanent pubkey, e.g. shared during any prior contact, chat link, or bot pairing code).
2. Craft `objDeviceMessage`:
   - `to`: target's `device_address`
   - `pubkey`/`priv`: attacker's own freshly generated device keypair
   - `encrypted_package`: any syntactically valid iv/authtag/encrypted_message (need not decrypt) with `dh.sender_ephemeral_pubkey` = any valid-format base64 string and `dh.recipient_ephemeral_pubkey` = a base64 string guaranteed not to equal the target's temp/prev-temp/permanent pubkey.
   - Sign the message with the attacker's own private key so `ecdsaSig.verify` succeeds (self-consistent signature).
3. Send this as a `hub/message` justsaying through the target's hub (or as `hub/deliver` if the target runs its own hub).
4. Target's `decryptPackage` hits the "unknown key" branch, schedules `setTimeout(() => { throw ... }, 100)`; ~100ms later the exception surfaces outside any `try/catch`, crashing the node process (unless a global handler intercepts it — this repo does register `process.on('uncaughtException', ...)` in `network.js`, so the exact terminal behavior of that handler was not fully verifiable within this review and should be confirmed before relying on this PoC as a guaranteed crash).

**Note on verification**: `network.js` contains references to `uncaughtException`, indicating a global exception handler may exist; its exact behavior (silent log vs. process exit) could not be confirmed with the available tools, so the ultimate crash-vs-log outcome of this PoC carries some uncertainty.
