### Title
Cross-repository status forgery via SHA-only lookup in `StatusHandler#process` allows unauthorized deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits by `Commit.where(sha: params.sha)` with no scoping to the repository/organization that the verified webhook signature authenticated. Since the `commits` table only enforces uniqueness of `sha` per `stack_id` (see `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), the exact same SHA can legitimately exist as separate `Commit` rows under unrelated stacks, and a correctly-signed webhook from an attacker-controlled repository/organization will flip the status of a commit belonging to a completely different, victim stack.

### Finding Description
The broken binding: `Shipit.github(organization: repository_owner)` (the org that signed the webhook, used in `WebhooksController#verify_signature`, app/controllers/shipit/webhooks_controller.rb:24-30) must equal the org/repo whose commit gets its status mutated in `Commit#deployable?`'s underlying `status`/`success?` chain. It doesn't: [1](#0-0) 

`process` looks up commits purely `Commit.where(sha: params.sha)`, with no join/filter on `repository.full_name` or `repository_owner` from the payload. `verify_signature` only proves the payload was signed by *some* org's registered GitHub App/webhook secret [2](#0-1)  — it never constrains which `stack`/`Commit` rows that org is allowed to mutate. Because git commit SHAs are computed purely from commit content (tree, parents, author/committer, timestamps, message) and not from the hosting repository, an attacker can reproduce a byte-identical commit object (same SHA) in a repository/org they legitimately control (their own repo, or their org's GitHub App installation), and then create a GitHub status on that SHA via the normal GitHub status API. GitHub signs and delivers this webhook correctly for the attacker's own org, so `verify_signature` passes. `StatusHandler#process` then updates **every** `Commit` row across the whole database sharing that SHA — including the row belonging to the victim's stack — via `commit.create_status_from_github!(params)`, which calls `add_status`/`create_release_status!`/schedules `ProcessMergeRequestsJob` and flips `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`, app/models/shipit/commit.rb:227-229).

`Stack#deployable?` (`!locked? && !active_task? && !awaiting_provision? && deployment_checks_passed?`, app/models/shipit/stack.rb:376-378) is indeed independent of CI/status entirely, so once the shared commit is marked `success` for the victim stack, `Stack#trigger_continuous_delivery` / `next_expected_commit_to_deploy` will treat it as deployable and — in `continuous_deployment` mode — automatically enqueue a `Deploy`, with zero interaction with the victim repository's own CI provider or webhook secret.

Existing guards do not stop this: `verify_signature` authenticates the *sender org*, not the *target stack*; `ExplicitParameters` (`StatusHandler.params`) only validates payload shape (`sha`, `state`, etc.), not repository identity; there is no `Repository`/`stack_id` filter anywhere in `StatusHandler#process`.

### Impact Explanation
An attacker who controls (or can install a GitHub App/webhook on) any repository/org registered with Shipit can force an unauthorized `Deploy` to be scheduled for an unrelated victim stack, purely by replicating a commit object and setting its status through their own, fully legitimate GitHub API access. This is an unauthorized-deploy / cross-tenant-mutation issue (Critical: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). Blast radius spans every stack configured in the Shipit instance, since the lookup is global and unscoped by repository.

### Likelihood Explanation
Requires: (1) the victim stack in `continuous_deployment` mode, unlocked, idle, and passing `deployment_checks_passed?`; (2) the attacker have push/write access to some repository with a Shipit-registered GitHub App/webhook (their own repo/org is sufficient — no privileged Shipit role or secret needed); (3) the attacker construct a commit object byte-identical to one in the victim's undeployed queue (trivial for any commit whose content — tree, parents, author/committer info, timestamps, message — is known/public, e.g., via a fork or by fetching the object directly) and push it into their own repo; (4) create a `success` status on that SHA via the standard GitHub status API in their own repository. All of this is achievable without any Shipit credentials, without touching the victim repository's CI, and is fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to commits belonging to stacks whose `Repository` matches `params.dig('repository', 'full_name')` (and/or owner), e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: repository_full_name_from_payload })`, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status for a SHA shared with another stack's commit does not deploy the victim stack" do
          victim_stack = shipit_stacks(:shipit)
          victim_stack.update!(continuous_deployment: true, lock_reason: nil)
          shared_sha = 'a' * 40

          # Victim's own commit, currently not deployable (no success status)
          victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'x', author: nil)
          refute_predicate victim_commit, :deployable?

          # Attacker's unrelated stack/repo has a Commit row with the SAME sha
          attacker_stack = shipit_stacks(:cyclimse) # any other, unrelated stack/repo
          attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'x', author: nil)

          params = ExplicitParameters::Parameters.new(
            sha: shared_sha, state: 'success', context: 'ci/attacker', branches: []
          )

          assert_no_difference -> { victim_stack.deploys.count } do
            StatusHandler.new.process # invoked with attacker-controlled params
            # EXPECTED (secure): only attacker_commit is updated
            # ACTUAL (vulnerable): victim_commit.reload.deployable? becomes true,
            # and victim_stack.trigger_continuous_delivery enqueues a Deploy.
          end
        end
      end
    end
  end
end
```
Binding checked both sides: signature-authenticated org (attacker's) vs. stack/repo whose `Commit` row is mutated (victim's) — they diverge because `StatusHandler#process` never compares `params.dig('repository','full_name')`/owner against `commit.stack.repository`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
