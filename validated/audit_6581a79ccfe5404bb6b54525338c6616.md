### Title
Unscoped commit lookup in `StatusHandler#process` lets a forged status webhook satisfy `all_status_checks_passed?` for a victim's stack, causing `ProcessMergeRequestsJob#perform` to auto-merge a pending `MergeRequest` it never authenticated against - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target of an incoming `status` webhook purely by `Commit.where(sha: params.sha)`, with no check that the commit's `stack`/repository matches the repository that the webhook signature was verified for. [1](#0-0)  Because `ProcessMergeRequestsJob#perform` gates `merge_request.merge!` only on `stack.allows_merges?` and `merge_request.all_status_checks_passed?`, and the latter is computed straight off `head.statuses_and_check_runs` populated by this unscoped write, an attacker who controls any repository sharing a commit SHA with the victim's PR head can push a fabricated "success" status into the victim stack's commit and get it merged. [2](#0-1) 

### Finding Description
Binding claimed: `commit that receives the forged status == commit belonging to the stack/repository that the webhook signature was verified for`. Trace shows this binding is broken.

`WebhooksController#verify_signature` verifies the HMAC signature using the GitHub App/secret resolved from `repository_owner`, i.e. `params.dig('repository','owner','login')` taken from the *sender's own* payload. [3](#0-2)  This only proves the payload was really sent by GitHub for *some* repository whose owner resolves to a configured Shipit organization/App - it proves nothing about which `Commit`/`Stack` row the payload's `sha` should be allowed to affect.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no `stack_id`/`repository` filter at all. [1](#0-0)  `Commit` rows are content-addressed by `sha` and git SHAs are literally identical between a fork and its upstream for shared history, so a commit that is the head of a victim's pull request also exists, by the same SHA, in the attacker-controlled fork used to open that very PR.

Exploit flow for an unprivileged attacker:
1. Attacker forks the victim repo (already whitelisted attacker capability), pushes a branch, and opens a PR against the victim stack. Shipit creates a `Commit` row for the head SHA and a `MergeRequest` in `pending` state once merge is requested (`MergeRequest.request_merge!`). [4](#0-3) 
2. Using their own GitHub token (no Shipit secret needed), the attacker calls GitHub's Status API on their *own fork* for that same SHA, setting state `success`. GitHub genuinely signs and delivers this `status` webhook, so `verify_signature` passes for the attacker's own repository owner.
3. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` with no repo scoping, finds the victim's `Commit` row (same SHA), and calls `commit.create_status_from_github!(params)`, writing a fabricated success status onto it. [5](#0-4) 
4. This status write triggers `stack.schedule_merges` via `add_status`, enqueuing `ProcessMergeRequestsJob` for the victim stack. [6](#0-5) 
5. `ProcessMergeRequestsJob#perform` calls `merge_request.all_status_checks_passed?`, which evaluates `StatusChecker` over `head.statuses_and_check_runs`, now including the forged success status, and returns true; combined with `stack.allows_merges?`, it calls `merge_request.merge!`, transitioning `pending -> merged` and issuing the real GitHub merge API call. [7](#0-6) [8](#0-7) 

None of the existing guards stop this: `verify_signature` authenticates the sender's own repository, not the target commit's owning stack; `drop_unhandled_event` only checks event type; `ExplicitParameters` on `StatusHandler` only validates payload shape (`sha`, `state`, etc.), not repository ownership of the target `Commit`. [9](#0-8) 

### Impact Explanation
A completely unprivileged GitHub user (fork owner, PR author) can force Shipit to merge their own pull request into a victim repository without the merge queue ever legitimately validating CI/status for that repository - a fully unauthorized merge, matching the Critical category ("payload for one repository mutating another's stack/commit ... or an unauthorized ... merge"). The write is not scoped to the attacker's own stack: it mutates a `Commit` row that belongs to the victim's `Stack`, and via `stack.schedule_merges`/`ProcessMergeRequestsJob` triggers a real GitHub merge call on the victim's repository. The technique is repeatable for any stack where the attacker can produce a PR sharing a SHA with the target commit (i.e., any repo they can fork and PR against), so blast radius is broad across tenants that share the underlying signing secret/App configuration.

### Likelihood Explanation
Preconditions: the victim stack must have `merge_queue_enabled`/`allows_merges?` true (a normal Shipit merge-queue configuration) and the attacker must be able to open a PR (trivial, fork-based). No Shipit secrets, sessions, or API tokens are required - only the attacker's own GitHub account and a normal `git push`/status API call against their own fork, which GitHub will sign with valid webhook credentials for their own repository. This is low-cost and fully repeatable per targeted stack.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers keyed only by SHA) to the repository authenticated by the webhook, e.g. resolve the target `Stack`/`Commit` via `Commit.joins(:stack).merge(Stack.where(repository: repo_from_payload)).where(sha: params.sha)`, rejecting/ignoring commits whose owning stack's repository does not match `params.dig('repository','full_name')` from the verified payload.

### Proof of Concept
```ruby
# test/jobs/process_merge_requests_job_test.rb (concept)
test 'forged status webhook for a shared SHA merges a victim MergeRequest' do
  victim_stack = shipit_stacks(:shipit)
  head_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'PR head')
  merge_request = victim_stack.merge_requests.create!(
    number: 42, merge_status: 'pending', head: head_commit
  )
  victim_stack.stubs(:allows_merges?).returns(true)

  # Simulate the forged, but validly-signed, status webhook for the SAME sha,
  # delivered as originating from the attacker's own (different) repository.
  Shipit::Webhooks::Handlers::StatusHandler.new.call(
    'sha' => head_commit.sha, 'state' => 'success', 'context' => 'ci',
    'repository' => { 'owner' => { 'login' => 'attacker' }, 'full_name' => 'attacker/fork' }
  )

  ProcessMergeRequestsJob.new.perform(victim_stack)

  assert_equal 'merged', merge_request.reload.merge_status
end
```
Assertion under test: left side of the binding (`commit that received the forged status`) == right side (`commit belonging to the stack the webhook was authenticated for`) is false - the status lands on `victim_stack`'s commit despite the webhook only being signed for `attacker/fork`, and `merge_request.merge_status` flips from `pending` to `merged`.

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
