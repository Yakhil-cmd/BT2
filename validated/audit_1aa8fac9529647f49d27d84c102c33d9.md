### Title
Webhook signature verified for one repository, but `status` events written to a commit belonging to any repository/stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook by looking up the GitHub App/organization secret from `repository.owner.login` (or `organization.login`) in the payload, and only checks that the HMAC signature matches that organization's `webhook_secret`. [1](#0-0) [2](#0-1)  Every other handler in `Shipit::Webhooks::Handlers` scopes its side effects to the repository named in the same payload via `Handler#repository_name`/`#stacks` (`payload.dig('repository', 'full_name')`), so the entity that is authenticated and the entity that is mutated stay bound together. [3](#0-2)  `StatusHandler`, however, breaks this binding: it never calls `stacks`/`repository_name` and instead looks up commits globally by SHA across the entire `Commit` table, then writes a GitHub status onto whatever it finds. [4](#0-3) 

### Finding Description
The equality that the engine is supposed to enforce is:

`organization/repository whose webhook_secret verified the request` == `repository/stack whose commit state is mutated by the event`

For `push`, `check_suite`, and the `pull_request` handlers this equality holds because they all derive the target `Stack`/`Repository` from the very same `repository.full_name` field that `WebhooksController#repository_owner` used to select the verifying organization secret. [3](#0-2) [5](#0-4) [6](#0-5) 

`StatusHandler` violates it: its `process` method does `Commit.where(sha: params.sha).each do |commit| commit.create_status_from_github!(params) end`, an unscoped, engine-wide lookup by commit SHA with no reference to `payload['repository']` at all. [4](#0-3)  The controller only verified that the `X-Hub-Signature` matches the `webhook_secret` configured for the organization named in `repository.owner.login` of *that* payload [1](#0-0) , but this guarantee says nothing about which repositories' commits happen to share the SHA supplied in `params.sha`. Because `Commit` rows from every `Stack`/`Repository` configured in this Shipit instance live in the same table and are matched purely by `sha`, an attacker who legitimately controls (or can trigger events for) one onboarded, low-privilege GitHub repository/organization can send a `status` webhook whose signature is valid for that organization but whose `sha` value matches a commit that actually belongs to a different, unrelated stack (e.g. a shared upstream commit, a fork, a vendored/cherry-picked commit, or simply a guessed/known SHA of a target repo's commit). The forged status is then written onto that unrelated commit via `commit.create_status_from_github!(params)`.

### Impact Explanation
Commit statuses (`Shipit::Status`) are used by Shipit to gate whether a commit is "deployable"/safe to ship; forging a `success` status for a commit in a stack the attacker does not control can make an otherwise blocked or unverified commit appear deployable, effectively letting an unprivileged webhook sender manipulate the deploy-readiness state of a repository/stack that the verified signature never actually authorized them to write to. This matches the "unauthorized deploy" cross-repository-write class: the organization that signed the request is not necessarily the organization whose commit/stack state gets changed.

### Likelihood Explanation
Exploitability requires the attacker to control (or otherwise trigger a valid, signed `status` webhook delivery for) at least one repository/organization that is registered in this Shipit instance, and for a commit SHA collision/overlap to exist between that repository and the victim stack (common with forks, mirrors, or shared history/cherry-picks, or simply by guessing a public SHA of the target repo since `Commit.where(sha:)` has no repository scoping at all). This is a real, low-effort path once any repository is onboarded with its own webhook secret, since the flaw is in engine logic (`StatusHandler`) rather than requiring any credential theft.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `Handler#stacks`/`repository_name`, e.g. restrict the `Commit.where(sha: params.sha)` lookup to commits belonging to `stacks` (or `Repository.from_github_repo_name(repository_name)`) before calling `create_status_from_github!`, so that a verified-organization signature can never write status data onto commits outside that organization's own repositories.

### Proof of Concept
1. Onboard/attacker-control `Repository A` (owner `attacker-org`) in this Shipit instance, with its own `webhook_secret` configured under `Shipit.github(organization: 'attacker-org')`.
2. Identify a commit SHA that also exists in `Repository B` (a different, higher-value stack) — e.g. a shared upstream/vendor commit, or a known public SHA.
3. Send a `status` webhook to `/github/webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with `attacker-org`'s `webhook_secret`, and body `{"sha": "<shared-sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/repo-a"}, ...}`.
4. `WebhooksController#verify_signature` passes because the signature matches `attacker-org`'s secret (verified against `repository.owner.login` = `attacker-org`). [7](#0-6) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the matching commit belonging to `Repository B`'s stack, then calls `commit.create_status_from_github!(params)`, writing the forged `success` status onto `Repository B`'s commit despite the signature only having proven authenticity for `attacker-org`. [4](#0-3)
