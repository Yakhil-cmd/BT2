### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled=false` for `allow_with_label`/`prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` was intended to require `repository.review_stacks_enabled` for *any* auto-provisioning behavior, but Ruby's `&&`/`||` precedence causes `review_stacks_enabled` to gate only the `allow_all` branch. When `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, a ReviewStack is created based solely on label state, regardless of `review_stacks_enabled`.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == false` implies `provision? == false` for all provisioning behaviors. This holds only for `allow_all`.

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So `review_stacks_enabled` is ANDed only with the first disjunct. The second and third disjuncts (`allow_with_label`, `prevent_with_label`) have no dependency on `review_stacks_enabled` at all.

Reachable path: `WebhooksController#create` dispatches a validly-signed `pull_request` "opened" webhook from the attacker's own integrated repository to `OpenedHandler#process`, which calls `respond_to_pull_request_opened?` → `provision?` [2](#0-1) . Since the attacker owns the repository and can open PRs and set labels through real GitHub actions, the webhook signature check (`verify_signature`/`verify_webhook_signature`) passes normally — it does not, and cannot, protect against this internal logic flaw. [3](#0-2)  If the operator has explicitly set `review_stacks_enabled = false` with `provisioning_behavior = allow_with_label` (or `prevent_with_label`), the toggle is silently ignored: `find_or_create!` on `ReviewStackAdapter` creates a `Shipit::ReviewStack` and queues provisioning anyway. [4](#0-3) 

The same precedence bug is duplicated in `ReopenedHandler#unarchive?`. [5](#0-4)  By contrast, `LabeledHandler#respond_to_label_change?` and `UnlabeledHandler#respond_to_label_change?` correctly AND `review_stacks_enabled` across the whole condition using a top-level `&&` before the archive/unarchive OR-expression, so those handlers are NOT affected. [6](#0-5) 

The existing test suite confirms the gap: only the `allow_all` + disabled combination is tested against `review_stacks_enabled`, in `"only provision stacks for repos with auto-provisioning enabled"`. [7](#0-6)  The `allow_with_label`/`prevent_with_label` tests never set `provisioning_enabled: false`, leaving the divergence untested. [8](#0-7) 

### Impact Explanation
An operator who disables `review_stacks_enabled` expects zero dynamic `Shipit::Stack`/`ReviewStack` creation from pull-request webhooks. With `allow_with_label` or `prevent_with_label` configured, any user able to open a PR and (for `allow_with_label`) attach a matching label — or simply not attach a label for `prevent_with_label` — causes an unauthorized `Shipit::ReviewStack` record to be created and queued for provisioning (`awaiting_provision`), which drives downstream host-application `ProvisioningHandler#up` execution and deploy-time task machinery for a stack the operator explicitly tried to prevent. This is repeatable on every PR open/reopen against the same repository, and applies to any repository configured this way — a systemic, not one-off, defect.

### Likelihood Explanation
Preconditions: operator has enabled review stacks integration for a repository but explicitly set `review_stacks_enabled = false` together with `provisioning_behavior` of `allow_with_label` or `prevent_with_label` (a plausible/documented combination, e.g. temporarily pausing auto-provisioning while keeping the behavior setting). Attacker cost is trivial: open a real PR and optionally add a label they control on their own repository — no secrets, no privileged Shipit role, and the webhook signature check passes because it's a legitimate GitHub-originated event. Fully repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire OR-expression:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the identical fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks for allow_all when review_stacks disabled" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(repository:, provisioning_enabled: false, behavior: :allow_all)

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload_parsed(:pull_request_opened)).process
  end
end

test "BUG: creates stacks for allow_with_label even when review_stacks disabled" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:, provisioning_enabled: false, behavior: :allow_with_label, label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_difference -> { Shipit::Stack.count } do  # should be assert_no_difference per review_stacks_enabled=false
    OpenedHandler.new(payload).process
  end
end

test "BUG: creates stacks for prevent_with_label even when review_stacks disabled" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:, provisioning_enabled: false, behavior: :prevent_with_label, label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_difference -> { Shipit::Stack.count } do  # should be assert_no_difference per review_stacks_enabled=false
    OpenedHandler.new(payload).process
  end
end
```
The first assertion (`allow_all` + disabled → `assert_no_difference`) passes today, isolating the binding to that single branch. The second and third assertions demonstrate that `review_stacks_enabled=false` is not honored for the other two behaviors, confirming the precedence defect.
