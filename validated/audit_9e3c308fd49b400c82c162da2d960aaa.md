### Title
Cross-repository CI-state forgery via unscoped `Commit.where(sha:)` lookup in `Shipit::Webhooks::Handlers::StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no filter tying the lookup to the repository named in the verified webhook payload. Any commit record in the datastore that happens to share the SHA — including one belonging to a completely different, unauthorized repository/stack — receives a new `Status`, whose `after_create :enable_ci_on_stack` callback flips that stack's CI-enabled flag.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`commit.stack.repository.full_name == payload.dig('repository', 'full_name')` — this is never checked.

Trace of the path:
- `WebhooksController#verify_signature` verifies the webhook signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is derived from the *same* payload being processed [1](#0-0) . This only proves the payload was genuinely sent by GitHub for the organization/repo named in it (e.g., `attacker/evil`); it proves nothing about which `Commit`/`Stack` rows in Shipit's database should be touched.
- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
This query is scoped only by `sha`, not by `repository_name`/`stacks` as the base `Handler` class's `stacks`/`repository_name` helpers would allow [3](#0-2) . Unlike the `PullRequest` handlers (`OpenedHandler`, `LabeledHandler`, `ClosedHandler`, etc.), which resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` and scope all lookups through that repository [4](#0-3) , `StatusHandler` performs a global, unscoped commit lookup by SHA alone.
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` on whatever commit was matched [5](#0-4) , creating a `Shipit::Status` bound to that commit's actual `stack_id` — the victim's stack, not the attacker's.
- `Status`'s `after_create :enable_ci_on_stack` then calls `commit.stack.enable_ci!` [6](#0-5) , and `Stack#enable_ci!` writes `true` into the stack's CI-enabled cache key [7](#0-6) .

Exploit flow: since git commit SHAs are content-addressed, an attacker who knows the tree/parents/author/committer/timestamps/message of `victim/prod`'s HEAD commit (trivial for any public repo) can replicate an identical commit object in their own repository `attacker/evil`, producing the exact same SHA. The attacker then triggers (or has their own CI produce) a genuine, correctly-signed `status` webhook from GitHub for `attacker/evil` naming that SHA. Shipit's `verify_signature` legitimately passes because the webhook truly originates from `attacker/evil`'s installation. `StatusHandler#process` then matches `Commit.where(sha: <shared sha>)`, which returns the `victim/prod` commit row (because that stack already tracked that same SHA from its own git history), and mutates `victim/prod`'s CI-enabled state — despite the attacker having no relationship to `victim/prod`.

None of the listed guards prevent this: `verify_signature` only authenticates that the payload came from the named repository's app installation, not that the matched `Commit`/`Stack` belongs to that repository; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape; there is no `require_permission!`/`stacks` scoping call inside `StatusHandler#process` at all.

### Impact Explanation
A single crafted/replayed webhook lets an attacker flip `enable_ci!` on any stack whose tracked commit history happens to share a SHA with a commit the attacker controls in their own repository — a payload for `attacker/evil` mutating `victim/prod`'s stack state. This matches the "payload for one repository mutating another's stack, commit... state" Critical impact category: once CI is marked enabled on `victim/prod`, `Commit#deployable?`'s gating semantics change (per the precondition, deploys were waiting on `success?` because CI had never been enabled before), altering deploy-readiness computation for the victim stack without any authorization over that repository. This is repeatable against any stack/repository pair where the attacker can reproduce a shared SHA, and is not limited to a single tenant.

### Likelihood Explanation
Preconditions are modest: the attacker needs (1) a GitHub repository/organization they control with a Shipit webhook properly configured (something any Shipit operator would set up per onboarded repo, but the attacker only needs it for their *own* onboarded repo), and (2) the ability to produce a commit whose SHA matches the victim's tracked HEAD commit, which is straightforward for public repositories (git commit metadata is fully public and reproducible bit-for-bit). No secrets, sessions, or elevated GitHub permissions are required — only ordinary push/webhook capability on a repository the attacker owns. The attack is repeatable at will against any stack whose commits' SHAs the attacker can reproduce.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other SHA-keyed handler with the same pattern) to the repository named in the verified payload, e.g. via the `Handler` base class's `stacks` helper:
```ruby
def process
  stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ensures a `Status`/`enable_ci_on_stack` mutation can only ever be applied to a commit belonging to a stack whose repository matches the one that authenticated the webhook.

### Proof of Concept
Minitest plan (model/controller test, no live GitHub):
1. Fixtures: two stacks/repositories, `victim_repo`/`victim_stack` and `attacker_repo`/`attacker_stack`, each with its own `GithubHook` webhook secret.
2. Create a `Commit` on `victim_stack` with a known `sha` (e.g., `"deadbeef" * 5`), and ensure `victim_stack.ci_enabled?` is `false` (no prior statuses/check_runs, cache cleared).
3. Stub `GithubHook.any_instance.stubs(:verify_signature).returns(true)` to simulate a correctly verified webhook for `attacker_repo` (bypassing the need for real secrets, per existing test patterns in `test/controllers/webhooks_controller_test.rb`).
4. POST to `/webhooks` with `X-Github-Event: status`, body naming `repository.full_name == "attacker/evil"` and `sha == "deadbeef" * 5` (the shared SHA), with no relation to `attacker_repo`'s own tracked commits.
5. Assertion of the binding, before tracing: `assert_not_equal victim_stack.repository.full_name, "attacker/evil"`.
6. Expectation: `Shipit::Stack.any_instance.expects(:enable_ci!).never`, or more directly `refute victim_stack.reload.ci_enabled?` after the POST.
7. Currently (bug present): the test fails — `victim_stack.enable_ci!` is invoked and `ci_enabled?` becomes `true`, proving the payload for `attacker/evil` mutated `victim_stack`'s CI state.
