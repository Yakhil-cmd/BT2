### Title
Cross-tenant commit-status forgery triggers unauthorized deploys due to organization-authentication/repository-write binding mismatch - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
In a multi-GitHub-organization Shipit deployment (documented, supported configuration with per-organization `webhook_secret`s), the webhook signature is verified against the organization identified by `repository.owner.login`/`organization.login` in the JSON body, but the `status` event handler never re-checks that binding: it looks up commits globally by `sha` across the entire instance and creates a `Status` on whatever `Stack` that commit happens to belong to. Any organization with its own legitimately configured GitHub App/webhook secret can therefore forge a `status` webhook — self-signed with its own secret — whose `sha` matches a commit belonging to a completely different, unrelated tenant's stack, injecting a fabricated `success` CI status for it.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to check the HMAC against using `repository_owner`, which is derived purely from the JSON payload fields `repository.owner.login` (falling back to `organization.login`): [8](#0-7) 

This only proves the request was signed by *some* organization's configured secret — it does not bind the request to any particular repository being acted upon. Once verified, `create` dispatches the full JSON body to every registered handler for the event: [9](#0-8) 

`StatusHandler#process` does not use the `Handler#stacks`/`repository_name` scoping helper at all (unlike `PushHandler`, which at least scopes to `stacks` derived from `repository.full_name`). Instead it performs a completely global lookup: [10](#0-9) 

So the field that authorizes the request (`repository.owner.login`, checked against organization A's `webhook_secret`) is never cross-checked against the field that determines which `Stack`/tenant is actually mutated (`Commit.where(sha: params.sha)`, which can match a commit belonging to organization B's stack). This is the same class of bug as the referenced report: a field the code acts on (`sha` → arbitrary commit/stack) is decoupled from the identity actually verified by the signature (`repository.owner.login` → organization A).

Creating a `Status` triggers `enable_ci_on_stack` and `schedule_continuous_delivery` unconditionally: [4](#0-3) 

which calls into `Commit#schedule_continuous_delivery`, and if the target stack has `continuous_deployment` enabled and the forged status makes the commit `deployable?` (`success?`), it enqueues `ContinuousDeliveryJob`, ultimately calling `Stack#trigger_continuous_delivery` → `trigger_deploy`: [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
This breaks the trust boundary: "the organization that authenticated the webhook" ≠ "the repository/stack that is actually written to." A tenant with a legitimately configured GitHub App on the same Shipit instance (multi-org setups are explicitly documented) can forge success statuses for arbitrary commit SHAs belonging to unrelated organizations' stacks, and — where continuous deployment is enabled — cause an unauthorized deploy of a commit it does not control the CI verdict for. This matches the "unauthorized deploy" high-impact criterion.

### Likelihood Explanation
Requires knowledge of a target commit's SHA (often discoverable, e.g. via public GitHub repos, Shipit's own UI, or other webhook broadcasts) and requires the Shipit instance to be configured with multiple organizations each holding their own valid `webhook_secret` — an explicitly documented and supported configuration in `docs/setup.md`. No repository write access, GitHub App private key, or Shipit session is required; only possession of a webhook secret for any one onboarded organization is needed.

### Recommendation
`StatusHandler` (and any other handler that doesn't already scope via `Handler#stacks`) should restrict the `Commit` lookup to stacks belonging to the `Repository` identified from `payload.dig('repository','full_name')`, and that repository's owner should additionally be validated to match the organization identity that was cryptographically verified in `verify_signature`, rejecting the event otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s (per `docs/setup.md`'s multi-org documentation).
2. As an operator/compromised actor controlling `org-a`'s GitHub App webhook secret, note a commit `sha` that belongs to a stack owned by `org-b` (e.g. observed via Shipit's public commit history UI or GitHub).
3. Craft a `status` event JSON body: `{"sha": "<org-b commit sha>", "state": "success", "context": "ci", "repository": {"owner": {"login": "org-a"}}}`.
4. Sign it with `org-a`'s `webhook_secret` using the `X-Hub-Signature` HMAC scheme and POST it to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` succeeds because it validates against `org-a`'s secret using `repository.owner.login = "org-a"`.
6. `StatusHandler#process` finds `Commit.where(sha: params.sha)` — the `org-b` commit — and calls `create_status_from_github!`, creating a `success` status on `org-b`'s stack.
7. If `org-b`'s stack has `continuous_deployment` enabled, `ContinuousDeliveryJob` is scheduled and a deploy of that commit is triggered without any action or consent from `org-b`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
