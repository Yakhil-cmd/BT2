## Analysis Result

### Title
Confused-deputy authorization in zToken `transfer` allows draining a victim's vault shares via any intermediate contract - (File: `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
The zToken `transfer` function in every Zest vault contract authorizes a share transfer if **either** `contract-caller` **or** `tx-sender` equals the `from` principal supplied by the caller. Because `tx-sender` is preserved unchanged through an entire call chain (it only changes via `as-contract`), any intermediate contract that a victim interacts with — for any unrelated reason — can call the vault's `transfer` with `from` set to `tx-sender` (the victim) and `to` set to an attacker-controlled address, moving the victim's zToken balance without the victim ever directly authorizing that specific transfer. This mirrors the Evmos advisory's root cause: the authorization check validates an address (`tx-sender`) that is not the entity actually driving/approving the specific action, letting an unrelated party spend funds belonging to someone else.

### Finding Description
`transfer` in the vault contracts checks: [1](#0-0) 

```
(define-public (transfer (amount uint) (from principal) (to principal) (memo (optional (buff 34))))
  (begin
    (try! (accrue))
    (asserts! (or (is-eq tx-sender from) (is-eq contract-caller from)) (err u4))
    (asserts! (not (is-eq current-contract to)) ERR-TOKENIZED-VAULT-PRECONDITIONS)
    (try! (ft-transfer? zft amount from to))
    (match memo to-print (print to-print) 0x)
    (ok true)))
```

The same pattern is present identically in the other vault implementations, e.g.: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The `is-eq contract-caller from` branch is the correct, safe check (it means the immediate caller is transferring its own tokens). The additional `is-eq tx-sender from` branch is the confused-deputy hole: `tx-sender` in Clarity is the *original transaction signer* and stays constant across an entire nested `contract-call?` chain unless a contract explicitly flips context with `as-contract`. This means that **any contract C, called (directly or transitively) by victim V for any purpose**, can itself issue `(contract-call? .vault-stx transfer amount tx-sender attacker none)`. Inside that call, `tx-sender` still equals `V` (not `C`), so `(is-eq tx-sender from)` succeeds even though `V` never called `transfer` and never approved this specific movement of funds — `C` is the actual, unauthorized instigator. `ft-transfer?` then moves `V`'s zToken (share) balance to `attacker`.

This is exactly the class of bug the Evmos advisory describes: an authorization check keyed to an address (`CallerAddress`/`tx-sender`) different from the entity that is supposed to explicitly consent to the specific action (the funder/`from`), letting a third party spend/move another principal's funds by riding on the victim's transaction context.

### Impact Explanation
zTokens represent the user's principal + accrued interest deposited into a Zest vault and are also used directly as collateral in `market.clar`'s `collateral-add`/`supply-collateral-add` flows. An attacker able to move a victim's zToken balance to itself achieves direct theft of user funds at rest (their vault share balance, i.e., deposited principal and interest) — a Critical-impact outcome. If the victim's zTokens were posted as collateral, the drain can also push the victim's position into an underwater/liquidatable state, compounding the loss.

### Likelihood Explanation
Exploitation only requires getting a victim to interact, in any capacity, with a contract that the attacker controls or that itself makes an incidental call into the vault's `transfer` on the victim's behalf while `tx-sender` is still the victim (e.g., a helper/router/aggregator contract, or any composed DeFi flow that calls into Zest vaults). No special privileges, price manipulation, or governance compromise is needed — only a single call chain where the victim is the origin (`tx-sender`) but not the immediate `contract-caller` of `transfer`.

### Recommendation
Remove the `(is-eq tx-sender from)` disjunct from the authorization check in every vault's `transfer` function; only permit the transfer when the *immediate* `contract-caller` equals `from` (standard SIP-010 semantics), i.e.:
```
(asserts! (is-eq contract-caller from) (err u4))
```
If a legitimate need exists for `market.clar` (or another audited internal contract) to move a user's zTokens on their behalf, that should be implemented via an explicit, narrowly-scoped internal entrypoint gated by `check-impl-auth`/`check-caller-auth` (as already used for `system-borrow`/`system-repay`/`collateral-add`), not via a blanket `tx-sender` bypass on the public SIP-010 `transfer`.

### Proof of Concept
1. Victim `V` holds zSTX shares in `vault-stx` from a prior deposit.
2. Attacker deploys `Drainer.clar` with a public function `bait()`:
   ```
   (define-public (bait)
     (contract-call? .vault-stx transfer (ft-get-balance zft tx-sender) tx-sender ATTACKER none))
   ```
3. Attacker lures `V` into calling `Drainer.bait` (e.g., disguised as an airdrop-claim or yield-boost function, or embedded as a nested call inside any other protocol `V` legitimately uses that itself calls an attacker-influenced contract).
4. `V` submits a transaction whose origin `tx-sender` is `V`, invoking `Drainer.bait`.
5. Inside `bait`, `contract-caller` is `Drainer`, but `tx-sender` remains `V`.
6. `vault-stx.transfer` executes with `from = V` (passed explicitly) and checks `(is-eq tx-sender from)` → `V == V` → passes, even though `contract-caller` (`Drainer`) ≠ `from` (`V`).
7. `ft-transfer?` moves `V`'s entire zSTX balance to `ATTACKER`, with `V` never having called `transfer` or approved this movement. [1](#0-0)
