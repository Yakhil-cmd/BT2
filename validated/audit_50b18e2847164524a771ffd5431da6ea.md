### Title
Headers commission rounding across multiple `earned_headers_commission_recipients` can mint extra bytes (supply inflation) - (File: headers_commission.js)

### Summary
When a multi-authored unit specifies `earned_headers_commission_recipients` to split its earned headers commission among several addresses, `calcHeadersCommissions()` rounds each recipient's share **independently** with `Math.round()` (or SQL `ROUND()`), without normalizing the sum back to the original `full_amount`. Because the shares are validated only to sum to exactly 100% (not to produce a rounding-safe distribution), an attacker can pick a set of shares whose independently-rounded amounts sum to *more* than `full_amount`. This mints new bytes that were never actually paid by the parent unit, exactly analogous to the JOJO `requestWithdraw` bug where independent rounding of an amount split let the attacker walk away with more than they contributed.

### Finding Description
`calcHeadersCommissions()` computes, for every unit that wins a headers-commission payout, a `full_amount` (the `headers_commission` of the payer unit) and then splits it among the recipients listed in `earned_headers_commission_recipients`: [1](#0-0) 

```
for (var address in objUnit.assocEarnedHeadersCommissionRecipients) {
    var share = objUnit.assocEarnedHeadersCommissionRecipients[address];
    var amount = Math.round(full_amount * share / 100.0);
    arrValuesRAM.push("('"+payer_unit+"', '"+address+"', "+amount+")");
};
``` [2](#0-1) 

Each recipient's cut is rounded on its own with no remainder tracking and no cap ensuring `Σ amount == full_amount`. The MySQL code path does the same thing per-row with SQL `ROUND()`: [3](#0-2) 

The only validation performed on `earned_headers_commission_recipients` is that the shares are positive integers, addresses are sorted, and the shares sum to exactly 100: [4](#0-3) 

Nothing here prevents an attacker from choosing shares (e.g., `50/50`, or `33/33/34`) that, for a given integer `full_amount`, cause every individual `Math.round()` result to round *up*, so the sum paid to `headers_commission_outputs` exceeds `full_amount`. Since `earned_headers_commission_recipients` is fully attacker-controlled by any unprivileged user who authors a multi-authored unit (the default fallback assigns 100% to the change address, but a custom list can be supplied by the composer): [5](#0-4) 

any wallet/user can deliberately construct such a list. These `headers_commission_outputs` rows later become spendable balance for the recipient addresses, i.e., real, circulating bytes.

### Impact Explanation
This is a supply-inflation bug: the total bytes credited via `headers_commission_outputs` for a payer unit can exceed the actual `headers_commission` fee that was deducted from the payer, creating bytes "out of thin air." Because headers-commission distribution happens continuously (every stable unit that wins headers commission from its parent), an attacker can systematically author multi-authored units with a crafted `earned_headers_commission_recipients` split that always rounds in their favor, repeating the exploit across many units to accumulate inflated byte balances over time — the same "repeat until drained/repeat to profit" pattern described in the H-2 report.

### Likelihood Explanation
Likelihood is high in the sense that the mechanism is fully reachable by an ordinary unit poster: it only requires constructing a normal multi-authored payment unit with a custom `earned_headers_commission_recipients` array whose shares are chosen to trigger favorable rounding for a predictable `full_amount` (unit size fee, which the attacker controls by controlling unit size). No privileged role, front-running, or victim interaction is required — the attacker only needs to win headers commission for their own crafted unit, which happens naturally as part of normal DAG operation.

### Recommendation
Do not round each recipient's share independently. Compute all recipients' amounts with a remainder-aware method (e.g., round down for all but the last recipient, or an explicit largest-remainder method) and assign any leftover/deficit explicitly to a single recipient (e.g., the first or last by address) so that `Σ amount` always equals `full_amount` exactly, in both the JS in-memory path and the MySQL SQL path in `headers_commission.js`.

### Proof of Concept
1. Attacker authors a unit with two authors and sets:
```
earned_headers_commission_recipients: [
  { address: A, earned_headers_commission_share: 50 },
  { address: B, earned_headers_commission_share: 50 }
]
```
2. Attacker crafts the unit so that when it eventually wins headers commission from a parent unit, `full_amount` (parent's `headers_commission`) is an odd number, e.g. `101`.
3. In `calcHeadersCommissions()`:
   - `amount_A = Math.round(101 * 50 / 100) = Math.round(50.5) = 51`
   - `amount_B = Math.round(101 * 50 / 100) = Math.round(50.5) = 51`
   - Total inserted into `headers_commission_contributions` = `102`, exceeding the actual `full_amount` of `101` by 1 byte.
4. Repeating this pattern across many self-authored multi-author units (each time winning headers commission with an odd `full_amount` and a 50/50 or similarly crafted split) allows the attacker to accumulate a steady stream of bytes not backed by any real payer, inflating the total byte supply over time.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
