### Title
Cross-organization webhook forgery via mismatched signature-org vs. acted-on repository field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App configuration (and thus the HMAC secret) used to validate an inbound webhook based on `repository.owner.login` (falling back to `organization.login`) taken directly from the unauthenticated request body. Every event handler, however, resolves the actual `Repository`/`Stack` to mutate using a *different* field of the same payload: `repository.full_name`. Because nothing binds these two fields together, a party that legitimately controls one GitHub organization/app configured on a shared, multi-tenant Shipit instance can sign a payload as their own org while pointing `repository.full_name` at a completely different organization's repository, causing Shipit to act on a repository it was never authenticated for.

### Finding Description
`Shipit::WebhooksController#verify_signature` does: [1](#0-0) 
picking `github_app = Shipit.github(organization: repository_owner)` where [2](#0-1) 
`repository_owner` comes straight from the JSON body (`repository.owner.login`, or `organization.login`). This is the *only* value used to pick which org's `webhook_secret` validates the HMAC (`GitHubApp#verify_webhook_signature`) — it has no relation to which repository will actually be modified.

Every default handler, by contrast, resolves the target `Repository`/`Stack` using a separate field, `repository.full_name`: [3](#0-2) 
and the pull-request handlers explicitly require and use `params.repository.full_name` to load `Repository.from_github_repo_name`: [4](#0-3) 

Since the HMAC covers the raw JSON body, an attacker cannot tamper with a payload signed by someone else. But Shipit supports multiple GitHub organizations on one instance (`Shipit.github(organization: ...)`, `config/secrets.development.shopify.yml` shows several distinct orgs each with its own `webhook_secret`): [5](#0-4) 
Anyone who legitimately owns a GitHub App/organization configured on the shared instance (e.g. `org-a`) knows `org-a`'s own `webhook_secret` (it's their own app) and can compute a valid `X-Hub-Signature` for any payload of their choosing. `verify_signature` will select `org-a`'s secret because `repository.owner.login == "org-a"`, sign-check succeeds — but the attacker sets `repository.full_name` to `"org-b/victim-repo"`. The handler layer never re-validates that `repository.owner.login` (the authenticated org) matches the owner segment of `repository.full_name` (the acted-upon repository), so the event is processed against `org-b`'s stack.

This breaks the binding: *organization that authenticated* (`repository_owner` used for HMAC secret selection) ≠ *repository that is written* (`repository.full_name` used by every handler to find the `Stack`/`Repository`).

Separately, `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no secret is configured for the selected org: [6](#0-5) 
so if the operator has any org configured with a blank `webhook_secret` (a config shape the repo's own example dev secrets file uses), that org name alone is a zero-knowledge free pass to forge events against any `repository.full_name`, with no secret knowledge required at all.

### Impact Explanation
An org that is a legitimate but unprivileged tenant on a shared Shipit instance (or, in the blank-secret case, anyone at all) can forge events that mutate a different org's state without ever presenting a credential tied to that org:
- `pull_request` `opened`/`closed`/`reopened`/`labeled`/`unlabeled` handlers — provision, archive, unarchive review stacks belonging to a victim repository (`Shipit::Webhooks::Handlers::PullRequest::*`), a cross-repository write.
- `status` handler — write fabricated commit statuses (`commit.create_status_from_github!`) on a victim commit, which can influence deployability checks used to gate deploys.
- `push` handler — trigger `stack.sync_github` on a victim stack.

This satisfies the "cross-repository writes" / potential "unauthorized deploy" criteria for Critical/High severity: the authenticating identity (org used for signature) is decoupled from the repository actually written to.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment where more than one GitHub organization/app is registered (`Shipit.github_apps`), which the engine explicitly supports and documents via `Shipit.github(organization:)` and the sample multi-org secrets file. Any tenant that legitimately controls one of those orgs' webhook secrets (which is a normal, expected credential for that tenant, not a privileged secret of the platform) can exploit this without any additional access. The blank-secret variant requires no credential at all and is reachable whenever any configured org omits `webhook_secret`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), require that the authenticated organization (`repository_owner`) matches the owner segment of `repository.full_name` before dispatching to handlers; reject the request (422) on mismatch. Additionally, do not treat a missing `webhook_secret` as automatic verification success — require `webhook_secret` to be configured per org that is expected to receive webhooks, or fail closed instead of returning `true`.

### Proof of Concept
1. Tenant controls GitHub org `org-a`, registered in Shipit's multi-org config with its own `webhook_secret_a` (a normal credential for their own tenant).
2. Tenant crafts a `pull_request` `opened` event payload:
   ```json
   {
     "action": "opened",
     "number": 1,
     "pull_request": { "id": 1, "number": 1, "url": "...", "title": "x", "state": "open",
       "additions": 0, "deletions": 0,
       "head": { "sha": "deadbeef", "ref": "feature" },
       "user": { "login": "attacker" }, "assignees": [], "labels": [] },
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
     "sender": { "login": "attacker" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=HMAC(webhook_secret_a, body)`; set `X-Github-Event: pull_request`.
4. `WebhooksController#repository_owner` returns `"org-a"`; `Shipit.github(organization: "org-a")` selects `webhook_secret_a`; signature check passes.
5. `Handlers::PullRequest::OpenedHandler` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and, if review-stack provisioning is enabled for that repo, creates/provisions a review stack for `org-b`'s repository — a write the attacker was never authenticated to perform on `org-b`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
