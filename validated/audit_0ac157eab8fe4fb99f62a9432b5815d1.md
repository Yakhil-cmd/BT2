### Title
Share-price manipulation in the reference `uniswap_like_market_maker.oscript` AA leads to mint/burn slippage theft - (File: `test/samples/uniswap_like_market_maker.oscript`)

### Summary
The Obyte reference AA template `uniswap_like_market_maker.oscript` (shipped in the codebase and exercised by `test/ojson.test.js`'s `'Uniswap-like market maker'` test) implements a pooled liquidity/shares design that mints and burns a "shares" asset (`$mm_asset`) using a spot balance ratio with no minimum-output protection. This mirrors the Teller `LenderCommitmentGroup_Smart::addPrincipalToCommitmentGroup`/`burnSharesToWithdrawEarnings` bug class: an unprivileged AA trigger sender can manipulate the pool's balances immediately before a victim's deposit/withdraw trigger is processed, distorting the shares-to-assets exchange rate and stealing value or forcing victims to mint zero/near-zero shares.

### Finding Description
In `test/samples/uniswap_like_market_maker.oscript`, the "invest in MM" case computes the number of shares to mint from the *current* pool balances at processing time: [1](#0-0) 

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
...
$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance;
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
```

and the "divest MM shares" case pays out a proportional share of the pool based on the current outstanding-shares counter: [2](#0-1) 

```
$mm_asset_amount = trigger.output[[asset=$mm_asset]];
$investor_share = $mm_asset_amount / var['mm_asset_outstanding'];
...
{address: "{trigger.address}", amount: "{ round($investor_share * balance[$asset]) }"}
...
{address: "{trigger.address}", amount: "{ round($investor_share * balance[base]) }"}
```

There is no `minAmountOut`/slippage-protection parameter analogous to what the Teller report recommends. Because AA triggers are processed one at a time in deterministic MC order but an unprivileged party can freely post their own trigger units ahead of or immediately after a victim's pending (not-yet-stable) deposit/withdraw trigger, an attacker can:
1. Use the "exchange asset to bytes" / "exchange bytes to asset" swap cases (lines 102-145 of the same file) to move the pool's `$asset_balance`/`$bytes_balance` to an extreme ratio (or even to exactly zero on one side) right before the victim's deposit is processed.
2. When `$asset_balance == 0 OR $bytes_balance == 0`, the code falls into the "initial deposit" branch and mints `$issue_amount = balance[base]` **without regard to the pre-existing `var['mm_asset_outstanding']`**, i.e., it treats the pool as brand new even though outstanding shares from earlier depositors still exist. This lets an attacker who drains one side of the pool to zero cause a subsequent depositor's shares to be computed off of a manipulated "reset" state, diluting/robbing prior shareholders — directly analogous to the Teller PoC, where the attacker defaults a loan to drive `poolTotalEstimatedValue_` to zero and then captures all value from the next depositor.
3. Symmetrically, on divest, `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']` multiplied by the *current* `balance[$asset]`/`balance[base]` can be sandwiched: the attacker swaps to inflate the pool balances right before their own divest trigger executes, extracts a disproportionate payout, then reverses the swap.

### Impact Explanation
An unprivileged AA trigger sender can extract value from, or dilute, other liquidity providers of any pool instantiated from this template — a direct analog to "attacker steals all deposits" in the Teller report. Because this file is shipped as a canonical example/reference AA for building Obyte AMM/pool-style AAs (parsed and tested by the ojson parser test suite), any project instantiating it verbatim inherits the vulnerability, and funds locked in the AA (base bytes and the paired asset) are the impacted funds — this satisfies "concrete unauthorized spending / AA fund loss" per the validation criteria.

### Likelihood Explanation
High for any real deployment of this template: the attack only requires the attacker to be able to post ordinary payment-triggering AA triggers (invest/divest/swap), which any address can do; no compromised keys, no hub/node control, and no timing beyond normal unit composition/ordering are needed. The economics only require the attacker to have enough capital to move the pool's balance temporarily, which is the same capability legitimate swappers already have via the exposed "exchange bytes to asset"/"exchange asset to bytes" cases.

### Recommendation
- Track a persistent `var['mm_asset_outstanding']` (or total value) invariant that is never silently reset by an "initial deposit" special-case; instead, require `var['mm_asset_outstanding']` to be exactly `0` (not merely one balance being `0`) before treating a deposit as the very first one.
- Add slippage protection: require the trigger to specify a `min_shares_out` (for invest) and `min_asset_out`/`min_bytes_out` (for divest), and `bounce()` if the computed amount is less than the caller-specified minimum, mirroring the Uniswap-style `amountOutMin` pattern recommended in the original Teller report.
- Avoid deriving mint/burn amounts solely from the balances visible at the moment the trigger is processed without any invariant check that would detect a balance/outstanding-shares mismatch caused by a preceding manipulative trigger.

### Proof of Concept
1. Attacker deploys/uses an existing AA instance of `test/samples/uniswap_like_market_maker.oscript` and becomes the sole/majority liquidity provider, obtaining `mm_asset` shares via the "invest in MM" case at lines 33-48.
2. Attacker sends a large trigger matching the "exchange asset to bytes" case (lines 124-145 of `test/samples/uniswap_like_market_maker.oscript`) to drain `$asset_balance` to `0`, right before a victim's pending deposit trigger becomes stable.
3. Victim's deposit trigger is then processed under the `$asset_balance == 0 OR $bytes_balance == 0` branch (lines 36-41), minting `$issue_amount = balance[base]` while ignoring the already-outstanding shares recorded in `var['mm_asset_outstanding']`.
4. Attacker then calls the "divest MM shares" case (lines 67-100), computing `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']` against the now-inflated `balance[base]`/`balance[$asset]` that includes the victim's freshly deposited funds, extracting a disproportionate payout relative to the attacker's real economic contribution.
