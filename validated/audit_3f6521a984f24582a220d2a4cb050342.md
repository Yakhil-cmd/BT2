### Title
Unhandled `throw` in private-asset double-spend handling causes node crash on a crafted private payment unit - (File: validation.js)

### Summary
The Alpine advisory describes OpenVPN aborting the process via a fatal assertion when a crafted packet's length fields don't validate as expected during key extraction — i.e., a remote, authenticated peer can supply malformed-but-parseable input that trips an internal invariant the code enforces with a hard abort rather than a graceful rejection. `ocore` has a structurally analogous pattern in `validation.js` inside `validatePaymentInputsAndOutputs`: when validating the inputs of a **private asset** payment, an unexpected double-spend/spend-proof condition is handled not by rejecting the unit, but by an unconditional `throw` deep inside an asynchronous callback chain.

### Finding Description
In `checkInputDoubleSpend` (used while validating each input of a payment, for both divisible and indivisible **private** assets), the double-spend resolution logic calls `checkForDoublespends(...)`, and its completion handler contains: [1](#0-0) 

```
function onDone(err){
    if (err && objAsset && objAsset.is_private && !conf.bLight)
        throw Error("spend proof didn't help: "+err);
    cb2(err);
}
```

This `throw` fires whenever `checkForDoublespends` reports an error (e.g., a conflicting/duplicate spend-proof situation) for a private-asset input, on a full node (`!conf.bLight`). Because it executes inside a database-callback / async chain rather than inside the synchronous call stack of a caller with a `try/catch`, this is effectively an **uncaught exception** in Node.js. `network.js` even has a top-level `process.on('uncaughtException', ...)` handler that explicitly re-throws to crash the process: [2](#0-1) 

So any code path that reaches this branch terminates the node process — a hard, unconditional "assertion-style" failure, exactly like the OpenVPN bug's "trigger a fatal assertion" behavior, except here the trigger is a crafted **private-asset payment message** validated during normal unit/private-chain processing rather than a raw network packet.

The whole validation function is reachable by any unprivileged unit poster / private-payment counterparty: `validatePaymentInputsAndOutputs` is invoked from the standard message-validation path (`validation.js` around lines 1587–1619 dispatches `payment` messages here), and for private assets specifically from `indivisible_asset.js`'s `validatePrivatePayment`/`parsePrivatePaymentChain` and `divisible_asset.js`'s `validateDivisiblePrivatePayment`, both of which are driven by `private_payment.js`'s `validateAndSavePrivatePaymentChain`, itself called by `wallet.js`'s `handlePrivatePaymentChains` (a hub/peer message handler that accepts payloads posted by other users): [3](#0-2) [4](#0-3) [5](#0-4) 

### Impact Explanation
A private-payment counterparty can construct a private-asset unit/private chain that produces a conflicting double-spend against an already-processed input for the same private asset, causing `checkForDoublespends` to surface an error for that private input. On any full node processing this (validating the incoming unit or private-payment chain via `handlePrivatePaymentChains` / `handleOnlinePrivatePayment`), the `throw Error("spend proof didn't help: ...")` executes outside any protective `try/catch`, propagating to Node's `uncaughtException` handler, which deliberately re-throws to crash the process. This is a denial-of-service against any node (light wallet acting as a relay, hub, or full node with `conf.bLight` falsy) that processes such a private payment — it can stall confirmation of new units on that node and requires operator intervention to restart, matching the "network unable to confirm new units" impact bar.

### Likelihood Explanation
Reaching this exact branch requires crafting a private-asset spend/double-spend scenario where `checkForDoublespends`'s "accept doublespends" resolution still returns an error afterward (`err` truthy) for a private asset on a non-light node. This is a narrower and more specific precondition than a simple malformed field, so likelihood is Medium: it requires understanding of the double-spend/spend-proof mutual-exclusion invariants of private assets, but it does not require any privileged role — any user who can post/originate a private asset unit and a conflicting spend can attempt it.

### Recommendation
Replace the unconditional `throw` in the `onDone` callback of `checkInputDoubleSpend` (validation.js, private-asset branch) with a call to `cb2(err)` (i.e., propagate the validation error the same way as the public-asset case), so that a malformed/conflicting private payment is rejected as an invalid unit instead of crashing the process. Audit other `throw Error(...)` calls inside async DB-callback chains reachable from validating attacker-supplied units/private chains (e.g., in `indivisible_asset.js`'s `updateIndivisibleOutputsThatWereReceivedUnstable`/`buildPrivateElementsChain`) for the same uncaught-exception-crash pattern, converting internal invariant violations that can be triggered by untrusted external input into normal validation-error returns rather than hard aborts.

### Proof of Concept
Conceptual PoC (exact minimal unit-level reproduction would need to be validated in a live devnet, since the precise conditions under which `checkForDoublespends` returns an `err` after attempting to resolve/accept a doublespend depend on `graph.determineIfIncluded`/sequence state that is only fully exercised at runtime):
1. Issue a private asset and produce a valid private-payment chain output A.
2. Post two competing private-payment units that both spend output A with matching but conflicting spend proofs constructed so that, after the normal "accept-doublespend" resequencing logic runs, `checkForDoublespends`'s final callback still reports an error for the private input (e.g., by racing the private-write mutex or supplying an already-sequenced conflicting spend-proof entry).
3. Submit both units/private chains to a full node (`conf.bLight` false) via `handlePrivatePaymentChains`/`handleOnlinePrivatePayment`.
4. Observe that `checkInputDoubleSpend`'s `onDone` throws `Error("spend proof didn't help: ...")` inside the async callback, is caught by no `try/catch`, and the `process.on('uncaughtException', ...)` handler in `network.js` re-throws, terminating the node process. [6](#0-5)
