### Title
AA response atomically bounces on a single restricted-asset output, permanently blocking delivery of all bundled assets/state changes to a spender-attestation-revoked address - ([File: aa_composer.js])

### Summary
When an AA (autonomous agent) response bundles multiple payment messages (e.g., bytes plus a `spender_attested` or `transfer_condition`-restricted asset) to the same trigger address, the entire response unit is built and validated as a single atomic unit in `sendUnit()`. If validation of just one of the payment messages fails — e.g. because the recipient's attestation for a `spender_attested` asset was revoked, or a `transfer_condition` denies that specific address (the oscript analog of a USDC-style blacklist) — the whole unit fails `validateAndSaveUnit()` and the AA calls `bounce()`, discarding *all* the intended outputs and state changes for that trigger, not just the restricted asset's output.

### Finding Description
`handleTrigger()` in `aa_composer.js` composes all outgoing `payment` messages for a single trigger into one unit via `sendUnit()`: [1](#0-0) 

Each asset payment message is validated for issue/transfer conditions and attestation (`spender_attested`) at full-node validation time, not before the unit is composed: [2](#0-1) 

The `spender_attested` check requires *all* output addresses of that asset's payment to be attested: [3](#0-2) 

`sendUnit()` builds and validates the whole unit (bytes + every non-base asset message) together, then calls `validateAndSaveUnit`: [4](#0-3) 

If validation fails for any single payment message inside that unit (e.g. the attestation/transfer-condition check on the "blacklisted" asset), `validateAndSaveUnit` returns an error and the whole flow calls `bounce(err)`: [5](#0-4) 

`bounce()` then rolls back all state variable changes and AA balance updates for the trigger and instead sends back only the raw trigger inputs minus bounce fees — it never delivers the originally-intended combination of outputs (e.g., bytes + reward asset) that the AA logic computed: [6](#0-5) [7](#0-6) 

Critically, if the trigger itself included the restricted asset (the user sent it in as part of the same trigger, analogous to the depositor's own USDC now being blacklisted), `bounce()`'s own refund message paying that asset back to `trigger.address` will *also* fail the same attestation/transfer-condition check when it goes through `sendUnit()` → `validateAndSaveUnit()` again. This retriggers `bounce()` a second time; the `bBouncing` guard then short-circuits straight to `finish(null)` with **no response unit produced at all** — the trigger's coins (including the non-restricted assets bundled in the same trigger) are consumed into the AA's balance with no payout and no state change: [8](#0-7) 

Because the underlying condition (revoked attestation / denying `transfer_condition` for that specific address) is deterministic and persists across retries, every subsequent trigger from the same address hits the identical failure, permanently freezing that user's funds/rewards inside the AA with no partial-asset withdrawal path — exactly the "cannot withdraw other assets because one asset is blacklisted" bug class from the report, but realized through oscript's `spender_attested`/`transfer_condition` asset mechanics instead of an ERC20 blacklist.

### Impact Explanation
A user who is legitimately owed multiple assets (bytes + a restricted/attested asset) from a single AA trigger can permanently lose access to *all* of them — not just the restricted one — once their attestation is revoked or a `transfer_condition` denies them. Worse, if the restricted asset was also part of the incoming trigger payment, the user's funds are silently absorbed into the AA balance with zero response, causing an unrecoverable freeze of AA funds — a direct "AA fund loss or freezing" impact.

### Likelihood Explanation
This requires an asset issuer to use `spender_attested: true` (revocable attestor list) or a `transfer_condition` that can deny a specific address, combined with an AA that bundles payment of that asset together with other payments/state changes in a single trigger response — a common, supported oscript pattern (seen throughout the AA test/sample scripts, e.g. `create_an_asset.oscript`, `option_contract.oscript`, `fundraising_proxy.oscript`). Attestor revocation and restrictive transfer conditions are ordinary, expected asset features, making this reachable by any asset issuer/AA author without special privilege.

### Recommendation
- Allow the AA composer to isolate a failing payment message per-asset rather than failing the entire response unit: when a specific asset's output fails validation, drop or defer only that message (similar to how `fixed_denominations` messages are already filtered out before unit assembly) rather than triggering a full bounce that discards unrelated bytes/asset outputs and state changes.
- In `bounce()`, guard against re-attempting to return an asset whose recipient is already known to fail attestation/transfer conditions, and instead let those units succeed for the deliverable assets while leaving the undeliverable asset amount stranded in a recoverable, explicit state (e.g. a state variable) rather than silently absorbing all trigger funds via the `bBouncing`/`finish(null)` path.
- Document/require AA authors combining `spender_attested` or `transfer_condition`-restricted assets with other payments in the same response to pre-check the condition (e.g. via `is_aa` conditions or explicit attestor lookups) before composing the multi-asset response.

### Proof of Concept
1. Definer issues asset X with `spender_attested: true` and an initial attestor list containing address A.
2. AA is written so that a single trigger response bundles two payment messages to `trigger.address`: one in `base` (bytes) and one in asset X, e.g. as in `create_an_asset.oscript`'s issue case: [9](#0-8) 
3. Address A triggers the AA and receives asset X successfully once (attested).
4. The definer/attestor later removes A from the attestor list for X (analogous to a USDC blacklist) via an `asset_attestors` update.
5. A triggers the AA again in a way that (per the AA's logic) is entitled to receive both bytes and asset X in the same response unit.
6. `sendUnit()` composes both payment messages into one unit; `validateAndSaveUnit` fails validation with `"some output addresses are not attested"` for the asset X output, per `validation.js` lines 2630-2641.
7. `bounce(err)` fires, rolling back all intended state changes/outputs (not just asset X); if A's original trigger also carried asset X in, the bounce refund message for X fails the same check, `bBouncing` guard triggers `finish(null)`, and A's entire trigger payment (bytes + X) is absorbed by the AA with zero payout — permanently, since A's attestor status will not change on retry.
