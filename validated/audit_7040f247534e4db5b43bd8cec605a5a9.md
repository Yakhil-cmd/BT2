## Analysis

The external report describes a classic **weak on-chain randomness** vulnerability class: a pseudo-random value is derived purely from validator/block-producer-controlled on-chain data (e.g. `block.timestamp`), letting a block producer bias the outcome in their favor.

I found a direct analog in this repository. The Encointer runtime wires `pallet_encointer_ceremonies` to use the **insecure** collective-flip randomness source instead of the VRF-based randomness that other parachains in this same repo use for security-sensitive selection.

### Root cause

In `system-parachains/encointer/src/lib.rs`, the runtime registers: [1](#0-0) 

and configures the ceremonies pallet's randomness source directly to this collective-flip implementation: [2](#0-1) 

`pallet_insecure_randomness_collective_flip` (note the crate name itself flags it "insecure") derives its output from a rolling buffer of recent block hashes. Because a collator chooses which extrinsics to include/order in the blocks it authors, and because the relevant block hash is known to the block author before finalization, the resulting "randomness" is influenceable by whoever produces the block — the exact same manipulation vector described in the UF-3 report (validator-controlled `block.timestamp` biasing `random()`), just substituting "block hash chosen by collator" for "timestamp chosen by validator."

By contrast, this same repository demonstrates the *correct* pattern elsewhere: Asset Hub's `pallet_society` uses `RelayChainOneEpochAgoWithoutBlockNumber`, which pulls verifiable relay-chain VRF output that is fixed one epoch in advance and outside the local block author's control: [3](#0-2) [4](#0-3) 

This confirms the Fellowship is aware of the weak-randomness risk and has a hardened alternative available, but it was not applied to the Encointer ceremonies configuration.

### Impact

`RandomnessSource` in `pallet_encointer_ceremonies` is used to assign ceremony participants into meetup groups (mixing bootstrappers/reputables/newbies) each ceremony cycle, which in turn drives reputation issuance and UBI-style reward eligibility. A collaborating collator (or a party who can influence which transactions land in a given block/slot) could bias this assignment — e.g., to cluster colluding accounts together, manipulate newbie ratios, or otherwise game meetup composition — undermining the sybil-resistance and fairness guarantees of the proof-of-personhood ceremony.

### Caveat

This requires the actor to be a collator/block-producer for the Encointer parachain (a semi-privileged role, similar to the "validator" in the original report), not an arbitrary unprivileged user directly calling an extrinsic. Whether this clears the "Disqualify Immediately" bar depends on how the scope defines "trusted-role compromise" — collator manipulation of block contents is generally considered in-scope for weak-randomness findings in Substrate/Polkadot audits (this is a well-known, previously-flagged pattern for `pallet-insecure-randomness-collective-flip`), but it is not a fully permissionless attack path.

### Title
Weak On-Chain Randomness in Encointer Ceremonies via `pallet_insecure_randomness_collective_flip` — (File: `system-parachains/encointer/src/lib.rs`)

### Summary
`pallet_encointer_ceremonies` is configured with `RandomnessSource = RandomnessCollectiveFlip`, backed by `pallet_insecure_randomness_collective_flip`, whose output is derived from recent block hashes that the block-producing collator can influence, unlike the VRF-based `RelayChainOneEpochAgoWithoutBlockNumber` used elsewhere in this repo (e.g. Asset Hub's `pallet_society`).

### Finding Description
`RandomnessCollectiveFlip` computes randomness from a buffer of the last N block hashes [1](#0-0) . Because block hashes are a function of the block's contents, and the collator producing a block controls which extrinsics/ordering go into it, the collator has partial influence over the hash feeding the "randomness," and can observe/adjust it before it is finalized on-chain. This is then used directly as `RandomnessSource` for ceremony meetup assignment logic [2](#0-1) .

### Impact Explanation
Meetup assignment determines the composition of proof-of-personhood meetup groups (mix of bootstrapper/reputable/newbie participants) each ceremony, which feeds into reputation and reward issuance. A collator able to bias this randomness could skew group composition to favor specific accounts (e.g. sybil clusters), weakening the anti-sybil guarantees the ceremony protocol is designed to provide.

### Likelihood Explanation
Requires control over block production (collator role) for the Encointer parachain, which is a smaller/more constrained validator set than a full relay chain, making this more feasible than in larger networks, but it still requires a privileged/elevated position rather than being exploitable by an arbitrary unprivileged user.

### Recommendation
Replace `RandomnessCollectiveFlip` in `pallet_encointer_ceremonies::Config::RandomnessSource` with the relay-chain-VRF-backed randomness source already used elsewhere in this repository, e.g. `system_parachains_common::randomness::RelayChainOneEpochAgoWithoutBlockNumber`, as done for Asset Hub's `pallet_society` [5](#0-4) .

### Proof of Concept
Not directly demonstrable without executing the encointer runtime's ceremony-assignment algorithm off-chain against a chosen block hash; the root cause is structural — a collator can trivially rerun the assignment computation for several candidate block compositions before publishing/finalizing a block, and pick the block hash/extrinsic ordering that yields the most favorable meetup assignment, since `RandomnessCollectiveFlip`'s output is entirely determined by on-chain block-hash data available to the block author prior to finalization.
