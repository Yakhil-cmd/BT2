### Title
Webhook signature is verified against `repository.owner.login`, but every event handler acts on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to authenticate a delivery with based on `repository.owner.login` (falling back to `organization.login`), but the subsequent event handlers that decide *which stack/repository gets acted upon* key exclusively off the unrelated `repository.full_name` field, which is never part of the signature-selection decision and can diverge from the organization that was actually authenticated.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App configuration by organization name taken from the payload itself: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is read straight from the untrusted JSON body: [2](#0-1) 

Once the signature is deemed valid for that organization's app, the controller dispatches the *entire* payload to handlers with no further scoping: [3](#0-2) 

Every handler, however, resolves the target repository/stack from a completely different field — `repository.full_name` — via the shared base `Handler`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Shipit explicitly supports "Using Multiple Github Applications" where each organization in `secrets.yml` has its own `app_id`/`webhook_secret` (documented in `docs/setup.md`). This means the binding the code is supposed to enforce is:
`organization whose webhook_secret validated the signature == organization that owns the repository being modified`.

Because `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the affected stack) are two independent JSON fields with no cross-check, an entity that legitimately knows the webhook secret for **one** configured organization (e.g., an org admin who configured the GitHub App for their own org in a multi-tenant Shipit deployment) can craft an HTTP POST directly to the public `/github/webhooks` endpoint with:
- `repository.owner.login` (or `organization.login`) = their own org, so the HMAC is computed/verified successfully against a secret they legitimately possess, and
- `repository.full_name` = `"other-org/other-repo"`, an arbitrary repository belonging to a different tenant configured in the same Shipit instance.

`verify_signature` passes, and the handler for the event (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, etc.) then looks up stacks/commits for `other-org/other-repo` and acts on them, e.g.: [5](#0-4) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This lets the attacker forge a `status`/`check_suite` for a commit belonging to a stack they do not own/control, or trigger a resync (`PushHandler#process`) for that stack — none of which was gated by the organization actually verified for the signature.

### Impact Explanation
This breaks the equality "organization that authenticated == repository that is written," matching the analog class called out in the rules. The forged commit statuses/check-suite refresh feed directly into Shipit's `deployable?`/CI-gating logic used by the merge queue and deploy gating (`Commit#create_status_from_github!`, `Stack#required_statuses`/`blocking_statuses` referenced in `app/models/shipit/stack.rb` and `app/models/shipit/commit.rb`), so a cross-tenant forged "success" status can make an otherwise-non-deployable commit appear deployable, enabling an unauthorized deploy/merge for a stack the attacker does not have permission on. This aligns with the High/Critical impact categories ("escalation ... unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the attacker to already control (or have visibility into) the webhook secret for at least one organization configured in the multi-app `secrets.yml` of the same Shipit deployment — realistic in any Shipit instance shared across multiple orgs/teams, since each org's GitHub App admin knows/controls their own app's webhook secret but has no reason to be trusted with other tenants' repositories. No GitHub App private key, no Shipit session, and no `ApiClient` token are needed; only a raw HTTP POST to the public webhook endpoint with a validly-signed-for-their-own-org body.

### Recommendation
In `WebhooksController#verify_signature` / `Shipit::Webhooks::Handlers::Handler`, cross-check that the organization whose secret validated the signature actually owns the repository referenced by `repository.full_name` (i.e., compare `repository_owner` against the owner segment of `repository.full_name`) before dispatching to handlers, and reject the delivery (422) on mismatch.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `org-a` and `org-b`, each with its own GitHub App/`webhook_secret` per `docs/setup.md`'s multi-app configuration.
2. As an admin who owns `org-a`'s GitHub App (and therefore its `webhook_secret`), craft a JSON body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "sha": "<commit sha belonging to org-b/victim-repo>",
  "state": "success",
  "context": "ci/forced"
}
```
3. Compute `X-Hub-Signature` using `org-a`'s known `webhook_secret` over the raw body, set `X-Github-Event: status`, and POST to the Shipit webhook endpoint.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature. `StatusHandler#process` then updates the commit status for the commit in `org-b/victim-repo`, even though the attacker never authenticated as `org-b`.

Note: I could not fully trace every downstream consumer of a forged status through the merge-queue code in this pass (e.g., exact usage in `app/models/shipit/merge_request.rb`); the code path from webhook to `Commit#create_status_from_github!` and stack `deployable?`/status gating is confirmed structurally, but a full end-to-end unauthorized-deploy trace would benefit from a live Devin session to execute the PoC and confirm the final deploy trigger.
