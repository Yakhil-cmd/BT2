Based on the code I found, there's a structurally similar race in ocore's AA-definition/balance-initialization logic to the Malt `populateFromPreviousThrottle` vs `_fillInEpochGaps` bug: two independent code paths can call `storage.insertAADefinitions` for the *same* AA address, whichever wins the `INSERT ... IGNORE` locks in its own MCI window for computing the AA's initial balance, and the loser's balance-recalculation is silently skipped once the winner's definition has already stabilized and been evicted from `assocUnstableMessages`.

### Title
AA definition/balance race allows permanent loss of AA-received funds via duplicate `insertAADefinitions` "already exists" guard - (File: storage.js)

### Summary
`storage.insertAADefinitions` is invoked from two independent triggers for the same content-addressed AA address: synchronously when an AA-defined-AA is created inside another AA's response (`bForAAsOnly=true`, `mci=initial_trigger_mci`) [1](#0-0) , and asynchronously at MC-stabilization time when a regular unit's `definition` message stabilizes (`bForAAsOnly=false`, `mci` = stabilization MCI, `validation_mci=definer_last_ball_mci`) [2](#0-1) . Both paths perform an `INSERT ... IGNORE INTO aa_addresses` keyed by `address`, and whichever runs first "wins" and fixes the MCI window used to seed `aa_balances` [3](#0-2) .

### Finding Description
`insertAADefinitions` treats a duplicate insert (`res.affectedRows === 0`) as "already defined", and only attempts to recalc balances in the narrow case where the definition is still unconfirmed and was posted by the very same `unit` [4](#0-3) . If the previously-accepted definition has already stabilized (removed from `storage.assocUnstableMessages`, mirroring the `active`/pointer style guard in the Malt bug), `getUnconfirmedAADefinitionsPostedByAAs` returns nothing, so the code takes the "ignoring repeated definition" branch and returns without ever re-running the `aa_balances` seeding query for the second path [5](#0-4) . This is functionally identical to `RewardThrottle`'s `state[i].active` guard in `_fillInEpochGaps`: once one code path has "claimed" the slot (epoch index there, AA address here), the authoritative/late-arriving computation is permanently skipped rather than reconciled.

Because the two insertion paths use different `mci`/`validation_mci` values (`initial_trigger_mci` for AA-generated definitions vs. `definer_last_ball_mci`/stabilization MCI for regular definitions), and different `mci_cond` windows to sum `outputs` into `aa_balances` [6](#0-5) , whichever path wins the race permanently determines which outputs get counted. Any unrelated user (or the AA author itself) can trigger the AA that dynamically emits a "definition" message with a template child-AA definition (as in the `define new AA and activate it` test) whose JSON is fully deterministic and thus computable in advance by anyone [7](#0-6) . By pre-posting the identical `definition` payload as an ordinary (non-AA) unit and getting it to stabilize/get evicted from the unstable-message cache before the AA-triggered path runs (or vice-versa), an attacker can force the "loser" write path to be silently ignored, permanently excluding a window of `outputs` sent to that address from ever being credited to `aa_balances`.

### Impact Explanation
Funds sent to the AA address in the un-recalculated window are recorded on-chain as spendable outputs to that address but never reflected in `aa_balances`, i.e., they become invisible to and unspendable by the AA logic — a form of AA fund freezing/loss analogous to the "state permanently invalidated for future updates" impact flagged in the original Malt report. This is a Medium-severity fund-freezing bug reachable purely by posting units (no privileged role required).

### Likelihood Explanation
Exploitation requires the attacker to predict/compute the exact deterministic `definition` payload of a dynamically-created AA (achievable when the child AA template is static, as commonly seen in factory-style AAs) and win a timing race between unit propagation/stabilization order — feasible for a patient or well-resourced attacker but not trivial to win reliably, hence Medium rather than High likelihood.

### Recommendation
Do not gate the balance-recalculation on whether the earlier definition is still present in `assocUnstableMessages`; instead always recompute/reconcile `aa_balances` for an address whenever a second `definition` message for the same address is processed, or make the AA-address "birth" record explicitly track and merge both MCI windows so that no output range is silently dropped, similar to how the Malt team resolved the analogous issue by removing the racing catch-up function (`_fillInEpochGaps`) entirely rather than leaving two competing writers to the same state pointer.

### Proof of Concept
1. An AA `factory_aa` deploys a deterministic child AA definition `child_aa` (identical to the pattern in `test/aa_composer.test.js:922-999`) whose address is a `chash160` of static JSON.
2. An attacker computes the same `child_aa` JSON/address off-chain and posts it directly as a plain `definition` message unit before `factory_aa` is triggered.
3. Depending on which insertion (attacker's plain unit at stabilization via `main_chain.js:1564-1571`, or the AA-triggered one via `writer.js:620-628`) commits first into `aa_addresses`, the losing path hits the `affectedRows === 0` branch in `storage.js:921-940`; if the winning definition has already stabilized by the time the loser runs, `getUnconfirmedAADefinitionsPostedByAAs` finds nothing and the loser's balance-seeding query in `storage.js:946-962` never executes for its own MCI window, permanently excluding any payments made to that address in the un-covered window from `aa_balances`.
