### Title
Unsanitized `machine.environment` from `shipit.yml` injects arbitrary env vars (e.g. `GIT_TEMPLATE_DIR`) into every git subprocess, including `TaskCommands#checkout` - (File: lib/shipit/task_commands.rb, app/models/shipit/deploy_spec.rb)

### Summary
`DeploySpec#machine_env` returns the raw `config('machine', 'environment')` hash with no whitelist, unlike `deploy_variables`/`rollback_variables`, which are filtered through `EnvironmentVariables#permit`. `TaskCommands#env` merges this unfiltered hash into the environment used for every `Command` this class builds, including the `git checkout` invocation in `TaskCommands#checkout`, and that hash flows unmodified to `PTY.spawn` in `Command#start`.

### Finding Description
The broken binding: `TaskCommands#env` should equal `Shipit.env.merge(@stack.env).merge(<fixed keys>).merge(sanitized_machine_env).merge(@task.env)`, but it actually equals `... .merge(deploy_spec.machine_env)` where `machine_env` is unsanitized (`app/models/shipit/deploy_spec.rb:69-71`):
```ruby
def machine_env
  config('machine', 'environment') || {}
end
```
Compare this to `filter_deploy_envs`/`filter_rollback_envs` (`app/models/shipit/deploy_spec.rb:174-180`), which route through `EnvironmentVariables#permit` and raise `NotPermitted` for keys not declared in `deploy.variables`/`rollback.variables` (`lib/shipit/environment_variables.rb:13-18,35-44`). `machine.environment` has no equivalent allow-list — any key/value pair the repository owner puts under `machine.environment` in `shipit.yml` reaches the process environment verbatim.

`TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) merges `deploy_spec.machine_env` directly into the hash used for `checkout`, `clone`, `install_dependencies`, and `perform` commands, all built via `Command.new(..., env:, ...)`. `Command#initialize` stores `@env` as-is (`lib/shipit/command.rb:31-37`), and `Command#start` passes it straight to `PTY.spawn(unbundled_env, ...)` where `unbundled_env` merges `@env.stringify_keys` over the base/sanitized OS env (`lib/shipit/command.rb:92,103-105`). `TaskCommands#checkout` (`lib/shipit/task_commands.rb:50-59`) invokes `git(...)` using this same `env`, so any variable declared under `machine.environment`, including `GIT_TEMPLATE_DIR`, is present in the git subprocess's environment.

Exploit flow for an unprivileged fork PR under `prevent_with_label` (label absent so the review stack is created/kept from the PR branch, per `app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb` and `opened_handler.rb`):
1. Attacker opens a PR from their fork with a branch containing a `shipit.yml` with `machine: { environment: { GIT_TEMPLATE_DIR: <attacker path in working tree> } }`, plus a template directory in the same branch containing an executable hook (e.g. `hooks/post-checkout`).
2. `ReviewStack`/`Stack#branch` tracks the PR head ref, so `DeploySpec::FileSystem` loads `shipit.yml` from that attacker-controlled branch once checked out into `@task.working_directory`.
3. On a subsequent task for that stack (the next deploy/rollback, or a later commit on the same PR), `TaskCommands#env` recomputes `deploy_spec.machine_env` from the now-checked-out `shipit.yml`, injecting `GIT_TEMPLATE_DIR` unfiltered into the environment used by `clone`/`checkout` git invocations.
4. Because `GIT_TEMPLATE_DIR` is honored by `git init`/`git clone` to seed `.git` (copying template contents, including `hooks/`), a subsequent clone performed with this env populates `.git/hooks` with the attacker's executable hook, which git then executes automatically on the corresponding trigger (e.g. `post-checkout` after a checkout in that same working copy).

Existing guards do not stop this: `filter_deploy_envs`/`filter_rollback_envs` only apply to `Deploy#env`/`Rollback#env`-supplied variables, not to `machine.environment`; `EnvironmentVariables#permit` is simply never called for `machine_env`; and `prevent_with_label`/`allow_with_label` only gate *whether* a stack is provisioned/archived, not *what* environment variables a checked-out `shipit.yml` may declare once the stack exists.

### Impact Explanation
Arbitrary environment variable injection into every `Command`/`PTY.spawn` invocation for a review stack's tasks is Critical — it is a generic env-injection primitive (not limited to `GIT_TEMPLATE_DIR`; also `GIT_SSH_COMMAND`, `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, `PERL5LIB`, etc., none of which are filtered) that can be escalated to code execution on the Shipit deploy host under the identity running task/deploy commands. This affects only the review stack tied to the attacker's own fork/PR (their own repository's review stacks), but any repository owner enabling review stacks with `prevent_with_label` (or `allow_with_label`/`allow_all`) exposes this to any contributor who can open a PR against that repo.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (a fairly common configuration for this feature), and the attacker only needs the ability to open a PR from a fork with a `shipit.yml` — no Shipit credentials, GitHub App permissions, or team membership required. Achieving full RCE via `GIT_TEMPLATE_DIR` specifically requires chaining with a follow-up git clone/init reading the injected env, which is feasible across the natural multi-task lifecycle of a review stack (redeploys, rollbacks), but other environment variables not requiring that chaining (e.g., `GIT_SSH_COMMAND`, `RUBYOPT`) provide a more direct one-shot path since `machine_env` is unconditionally unsanitized.

### Recommendation
Apply the same whitelist mechanism used for deploy/rollback variables to `machine.environment`. Require repository/stack operators to declare an explicit allow-list of permitted machine environment variable names (e.g., `machine.environment_variables` declared by the host application, not the untrusted `shipit.yml`), and route `DeploySpec#machine_env` through `EnvironmentVariables#permit` against that allow-list before merging into `TaskCommands#env`. At minimum, block known-dangerous variable names (`GIT_TEMPLATE_DIR`, `GIT_SSH_COMMAND`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, etc.) from ever being sourced from repository-controlled `shipit.yml`.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb
test "checkout command inherits unsanitized machine.environment from shipit.yml (GIT_TEMPLATE_DIR)" do
  @deploy_spec.stubs(:machine_env).returns('GIT_TEMPLATE_DIR' => '/tmp/attacker-template')

  command = @commands.checkout(@task.until_commit)

  assert_equal '/tmp/attacker-template', command.env['GIT_TEMPLATE_DIR']
end
```
Binding to assert on both sides: `TaskCommands#checkout(...).env['GIT_TEMPLATE_DIR']` should equal `nil`/be rejected (expected, safe side) but actually equals `deploy_spec.machine_env['GIT_TEMPLATE_DIR']` (actual, broken side) — i.e. `EnvironmentVariables.with(deploy_spec.machine_env).permit(allowed_machine_vars)` is never invoked, so any attacker-supplied key from the fork branch's `shipit.yml` is passed straight through to the git subprocess environment.
