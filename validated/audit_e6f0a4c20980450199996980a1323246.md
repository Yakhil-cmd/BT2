### Title
Webhook signature verification is bound to `repository.owner.login`, but write actions are bound to `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App configuration—and therefore the HMAC secret used to authenticate the inbound payload—using `repository_owner`, derived from `params.dig('repository','owner','login')` (or `organization.login`). Every webhook `Handler` in the engine, however, resolves the repository/stack it will act on using a *different* field, `payload.dig('repository', 'full_name')` in `Handler#repository_name`. Nothing ties these two fields together, so a party who legitimately controls one organization's webhook secret can forge a payload whose `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name` points at a stack belonging to a completely unrelated organization/repository.

`Shipit.github(organization: repository_owner)` looks up the per-organization GitHub App config (and its `webhook_secret`) purely from that string. Once the HMAC check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs, and every `Handler` subclass locates the repository/stack to act on with: [3](#0-2) 

There is no code anywhere in the request path that checks `payload.dig('repository','full_name').start_with?("#{repository_owner}/")`. The equality the engine implicitly relies on — "the organization whose secret authenticated the payload" == "the organization that owns the repository being acted on" — is never enforced.

Concretely, `PushHandler#process` (and every other handler) trusts `repository_name`/`stacks` derived purely from `full_name`: [4](#0-3) 

An entity that operates its own GitHub organization configured in `Shipit.github_apps`/`Shipit.github(organization:)` (i.e., they legitimately know their own org's `webhook_secret`, an ordinary, unprivileged capability for any org onboarded into the multi-tenant Shipit instance) can send a signed webhook where:
- `repository.owner.login` = their own org (`A`) → passes `verify_signature` using `A`'s secret.
- `repository.full_name` = `"B/victim-repo"`, a repository belonging to an unrelated organization `B` that also has stacks configured in the same Shipit instance.

Because the signature is computed over the raw JSON body with `A`'s secret (which the attacker legitimately possesses), the forged payload is fully valid cryptographically, yet it drives handler logic against organization `B`'s stacks/commits.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated versus the repository that is written," matching one of the explicitly recognized analog classes. Depending on which handler fires, this lets org `A` write into org `B`'s tracked state: e.g., a forged `status` event can create/overwrite a `CommitStatus` on a commit belonging to `B`'s stack, and a forged `push` event can force a `GithubSyncJob`/resync for `B`'s stack. Commit statuses are used by Shipit to gate whether a commit is deployable, so a cross-organization forged status write can manipulate the deploy-readiness state of a stack the attacker's organization has no legitimate access to — a cross-repository write and a path toward influencing an unauthorized deploy decision.

### Likelihood Explanation
The prerequisite is only that the attacker's own organization is one of the tenants configured with a GitHub App/webhook secret in the Shipit instance (an ordinary, unprivileged relationship to any *other* tenant's repositories) and that a target stack for the victim `full_name` already exists in the same Shipit deployment. No repository write access, no Shipit session, and no privileged Shipit account are required — only the ability to send an HTTP POST to `/webhooks` with a valid signature computed from the attacker's own org secret, which is the standard capability GitHub gives every org owner for their own webhook configuration.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#initialize`), assert that the organization segment of `payload.dig('repository', 'full_name')` (or `organization.login`) matches `repository_owner` before dispatching to handlers, and reject the request (422) on mismatch. Equivalently, `Handler#repository_name` should re-derive the repository strictly from the same organization value that was used to select/verify the signature, rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Shipit instance `S` hosts stacks for both org `A/repo-a` and unrelated org `B/victim-repo`, each with its own GitHub App config/`webhook_secret` in `Shipit.github_apps`.
2. Org `A`'s owner (an ordinary, unprivileged tenant with respect to `B`) crafts a `status` (or `push`) webhook JSON body:
   ```json
   {
     "repository": { "owner": { "login": "A" }, "full_name": "B/victim-repo" },
     "sha": "<known sha on B/victim-repo>",
     "state": "success",
     ...
   }
   ```
3. They sign it with `A`'s own `webhook_secret` (`sha1=HMAC(A_secret, body)`) and POST it to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` computes `repository_owner == "A"`, loads `Shipit.github(organization: "A")`, verifies against `A`'s secret — passes.
5. The `status` handler resolves the target repository via `payload.dig('repository','full_name') == "B/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and writes a `CommitStatus` for `B`'s commit, even though the request was authenticated only against `A`'s credentials.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
