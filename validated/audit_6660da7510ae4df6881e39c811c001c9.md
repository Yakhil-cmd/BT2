### Title
Missing `return` in malformed-payload error path in `handleSavedPrivatePayments` causes double invocation of the async iteratee callback, corrupting private-payment processing state - (File: network.js)

### Summary
This is analogous to CVE-2021-3497 (GStreamer accessing already-freed memory because an error path in the Matroska demuxer failed to stop execution/cleanup properly). In `network.js`'s `handleSavedPrivatePayments`, a malformed private-payment payload received from an untrusted peer/device triggers an exception in `objectHash.getBase64Hash()`. The `catch` block starts the "cleanup" of that queue entry (`deleteHandledPrivateChain`, which will eventually call the `async.each` iteratee callback `cb`), but execution does **not** `return` — it falls through and re-uses the (now unset) `json_payload_hash` and re-processes the same, already-being-discarded `arrPrivateElements` through `validateAndSavePrivatePaymentChain`, whose own callbacks (`ifOk`/`ifError`) will call `deleteHandledPrivateChain(...)` (and thus `cb()`) a second time for the same row.

### Finding Description
`handleSavedPrivatePayments` iterates over rows from `unhandled_private_payments` (data originally supplied by a peer/hub as a `private_payment` message, i.e., attacker-controlled `row.json`) using `async.each`, which requires each iteratee to call its `cb` exactly once: [1](#0-0) 

Inside `validateAndSave`, the code computes a hash of the head private element's payload: [2](#0-1) 

If `objHeadPrivateElement.payload` is malformed in a way that makes `objectHash.getBase64Hash` throw (e.g. contains values that fail canonical JSON/hash serialization, similar to how deeply malformed structures elsewhere in the codebase are explicitly checked for and rejected before hashing, see the try/catch guards around `getBase64Hash` calls in `validation.js`), the `catch` block logs the error, optionally notifies the peer, and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which deletes the DB row and then invokes `cb()`, completing this `async.each` iteration: [3](#0-2) 

Crucially, there is **no `return`** after this `catch` block. Execution falls through to: [4](#0-3) 

`json_payload_hash` is `undefined` at this point (the `try` assignment never completed), yet the code proceeds to call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very same `arrPrivateElements` whose head element already failed basic hashing. Every branch of that call (`ifOk`, `ifError`) itself calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` again: [5](#0-4) 

This results in `cb` being invoked twice for the same `async.each` item — the JS analog of the native use-after-free/double-free pattern from the CVE: an object (`row`/`arrPrivateElements`) whose handling lifecycle has already been "finalized" via the error path is nonetheless reused and finalized a second time through a different path. `async.each` in the `async` library only calls its final completion callback once all iteratees call back exactly once; a double-callback for one item can cause the final callback (`unlock()`, `eventBus.emit("new_my_transactions", ...)`) to fire prematurely relative to still-in-flight sibling iterations, or fire extra spurious `sendResult`/`eventBus.emit(key, ...)` events, and it also issues a second, redundant `DELETE FROM unhandled_private_payments` and a second full asset validation/save attempt on data that was already discarded — an unprivileged peer can trigger this simply by sending a `private_payment` chain whose head payload fails `getBase64Hash`.

### Impact Explanation
The double-callback breaks the invariant that `async.each` relies on, releasing the `saved_private` mutex (`unlock()`) earlier than intended while other chains in the same batch may still be mid-processing, and can cause duplicate `deleteHandledPrivateChain` / duplicate `validateAndSavePrivatePaymentChain` invocations that race against each other on the same DB rows. This can corrupt wallet-side private-payment bookkeping (spurious/duplicate `accepted`/`error` results sent to peers, duplicate `eventBus` emissions, premature unlocking of the `saved_private` mutex leading to concurrent processing of state that assumed serialization). While this is client/wallet-side logic (reachable by any correspondent device or hub sending a private payment), it does not directly forge signatures or double-spend confirmed funds — the primary damage is state corruption / duplicated processing / DoS-like malfunction in private-payment handling reachable from a single malformed `private_payment` message.

### Likelihood Explanation
High likelihood of triggering the code path: any paired device, hub, or private-payment counterparty can send an `unhandled_private_payments` entry (via `handleOnlinePrivatePayment`/`private_payment` message) with a payload that fails `objectHash.getBase64Hash`. The exact conditions needed to make `getBase64Hash` throw depend on precise input shaping (e.g. values that break canonical serialization/hashing), but the reachable message data is fully attacker-controlled JSON, making this feasible for a moderately sophisticated attacker without special privileges.

### Recommendation
Add an explicit `return` at the end of the `catch` block in `network.js`'s `handleSavedPrivatePayments` so that once `deleteHandledPrivateChain(...)` schedules `cb()`, execution does not continue to compute `key` and re-invoke `privatePayment.validateAndSavePrivatePaymentChain`:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```
More generally, audit all `async.each`/`async.eachSeries` iteratees that have `try/catch` around externally supplied data for missing `return` statements after error-path callback invocation.

### Proof of Concept
1. As a paired device/hub, craft a `private_payment` message whose `arrPrivateElements[0].payload` is a value that passes the earlier structural checks in `handlePrivatePaymentChains` (`isNonemptyObject`, has `asset`, `inputs`, `outputs`, etc., per [6](#0-5) ) but is shaped so that `objectHash.getBase64Hash(payload, true)` throws (e.g. by including a value type that the canonical-JSON hasher cannot serialize, or a lone-surrogate/malformed string not filtered by the earlier `isNonemptyObject` checks).
2. Send it to a victim wallet so it ends up queued in `unhandled_private_payments` and processed by `handleSavedPrivatePayments`.
3. Observe that the `catch` block in `network.js:2472-2477` runs `deleteHandledPrivateChain(...)` (scheduling `cb()`), and then execution falls through to `network.js:2479` and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose completion handlers call `deleteHandledPrivateChain(...)` a second time for the same row — resulting in `cb` being invoked twice within the same `async.each` iteration, and a second, unintended full validation attempt on data already marked as handled/deleted.
