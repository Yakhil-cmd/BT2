### Title
Disabled indirect-correspondent authorization check allows unauthorized device-message actions - ([File: wallet.js])

### Summary
`wallet.js`'s `handleMessageFromHub` contains a permission check restricting which message `subject`s an "indirect correspondent" (a device that is known but not a direct pairing partner) is allowed to send, but the check is commented out, so it is never enforced.

### Finding Description
`handleMessageFromHub(ws, json, device_pubkey, bIndirectCorrespondent, callbacks)` receives `bIndirectCorrespondent`, a flag computed by the hub-message dispatcher indicating that the message sender is not a directly-paired correspondent (see `is_indirect` propagated from `correspondent_devices` in `device.js`'s `hub/message` handler). The intended authorization gate is right at the top of `doHandle()`: [1](#0-0) 
```
if (typeof subject !== "string")
    return callbacks.ifError("subject is not a string");
//if (bIndirectCorrespondent && ["cancel_new_wallet", "my_xpubkey", "new_wallet_address"].indexOf(subject) === -1)
//    return callbacks.ifError("you're indirect correspondent, cannot trust "+subject+" from you");
var from_address = objectHash.getDeviceAddress(device_pubkey);
```
Because this check is commented out, the `switch(subject)` block that follows processes **every** subject (`create_new_shared_address`, `approve_new_shared_address`, `new_shared_address`, `sign`, `create_new_wallet`, `new_wallet_address`, `arbiter_dispute_request`, etc.) identically for indirect and direct correspondents. This is structurally the same root cause as the Dragonfly Job API bug: a security gate that exists in the code and is documented in a comment/TODO but is not wired into the execution path, so state-changing operations that should be restricted to a trusted principal (a directly paired device) are instead reachable by a lesser-trusted principal (an indirect correspondent) as if it had full trust.

The device message itself is signature-verified (`ecdsaSig.verify` in `device.js`) and hash-checked before reaching `handleMessageFromHub` [2](#0-1) , so `from_address` is cryptographically authentic — the vulnerability is not spoofing of identity but a missing authorization/trust-level check for that already-authenticated but lesser-trusted identity.

### Impact Explanation
An indirect correspondent (e.g., a device introduced transitively through group/shared-address flows, arbiter/contract flows, or any mechanism that populates `correspondent_devices` with `is_indirect=1`) can trigger wallet-state-changing subjects that were meant to be gated, including:
- `create_new_shared_address` / `approve_new_shared_address` / `new_shared_address` — creating/approving shared (multisig) addresses that the local wallet will treat as valid multisig members [3](#0-2) .
- `sign` — requesting signatures for units/multilateral contracts [4](#0-3) .
- `arbiter_dispute_request` and other contract-related messages [5](#0-4) .

Since shared-address definitions and signing flows ultimately influence which addresses/definitions the wallet accepts and signs, abuse of this path can lead to a wallet cosigning or accepting a shared/multisig address definition or contract data from an untrusted (only indirectly known) party without the intended extra scrutiny, which is a fund-loss/unauthorized-spending-adjacent risk in the wallet/contract message-handling surface named in scope.

### Likelihood Explanation
Exploitation requires only that the attacker be an "indirect correspondent" of the victim device (a much lower bar than being a directly paired, trusted correspondent) and send a correctly signed device message via the hub — both attacker-controlled and requiring no privileged network position (no malicious hub/node needed, just normal hub-relayed message delivery, which is exactly the intended external interface for pairing/contract features). The check that would have blocked this is present in source as a comment, confirming it was a known/intended control that regressed to disabled, mirroring the Dragonfly report's "TODO, not yet wired in" pattern.

### Recommendation
Re-enable (and generalize) the authorization gate in `wallet.js`:
```js
if (bIndirectCorrespondent && !["cancel_new_wallet", "my_xpubkey", "new_wallet_address", "wallet_fully_approved"].includes(subject))
    return callbacks.ifError("you're indirect correspondent, cannot trust "+subject+" from you");
```
placed before the `switch(subject)` dispatch, so that all subjects other than the explicitly whitelisted ones are rejected from indirect correspondents, restoring the intended trust boundary between directly paired and indirectly known devices.

### Proof of Concept
1. Establish that device B is only an indirect correspondent of device A (`correspondent_devices.is_indirect=1` for B on A), e.g., via a flow that adds B as a correspondent without a direct pairing handshake.
2. From device B, send a properly signed hub device message to A with `subject: "create_new_shared_address"` (or `"sign"`, `"new_shared_address"`, etc.) and a valid `body`.
3. Because the commented-out check at `wallet.js:92-93` never executes, `doHandle()` proceeds directly into the `case "create_new_shared_address"` branch and processes the request exactly as it would for a directly-paired correspondent, emitting `create_new_shared_address` for user confirmation / running downstream logic — regardless of B's indirect trust status.
4. Compare against expected behavior (with the check enabled): device A should reply with `ifError("you're indirect correspondent, cannot trust create_new_shared_address from you")` and never process the request.

Note: I could not fully trace every code path that sets `is_indirect=1` in `correspondent_devices` within the indexed portion of the codebase (some call sites may be outside the indexed files), so the exact set of real-world scenarios producing an "indirect correspondent" relationship should be independently verified in a full checkout of the repository.
