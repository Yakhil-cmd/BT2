### Title
Cross-organization webhook forgery leads to unauthorized commit-status write and deploy trigger - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on an **unverified** field of the incoming JSON body (`repository.owner.login`), while the handlers that actually act on the payload use a **different** unverified field (`repository.full_name`, or in the `status` handler's case, no repository scoping at all — just a global `sha` lookup). This breaks the binding "organization that authenticated" vs. "repository that is written," letting an attacker who legitimately controls the webhook secret for one configured GitHub organization forge events that mutate state belonging to a completely different, unrelated stack/organization hosted on the same Shipit instance — including flipping a commit's CI status to `success`, which can trigger an unauthorized deploy on a stack with `continuous_deployment` enabled.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` straight from the untrusted raw JSON body, before any signature has been validated: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` selects one of possibly many independently configured GitHub Apps/organizations from `secrets.yml` (Shipit explicitly supports multi-organization configuration) and only checks that the HMAC signature matches *that* organization's `webhook_secret`: [3](#0-2) 

The verification step never checks that the org whose secret was used actually matches the repository the payload claims to act on. Handlers then resolve the target using a *separate* field: [4](#0-3) 

Worse, `StatusHandler` doesn't even use `repository.full_name` — it looks up commits globally by `sha` across the entire Shipit database, with no repository/organization scoping whatsoever: [5](#0-4) 

Because `repository.owner.login` (used to pick the verification secret) and `repository.full_name`/`sha` (used to pick the actual mutation target) are two independent, attacker-controlled fields in the same unauthenticated request body, an attacker who legitimately administers **any one** organization configured in Shipit's multi-tenant `secrets.yml` (and thus knows/controls that org's `webhook_secret`) can craft and correctly sign a `status` webhook whose `repository.owner.login` matches their own org (so it passes `verify_webhook_signature`), but whose `sha` matches a commit belonging to a totally different repository/organization managed by the same Shipit instance.

`commit.create_status_from_github!` then updates that foreign commit's status: [6](#0-5) 

If the targeted stack becomes `deployable?` as a result (`success? && !blocked?`) and has `continuous_deployment` enabled, the periodic continuous-delivery scheduler will pick it up and trigger an automatic deploy without any legitimate action from that stack's real GitHub org: [7](#0-6) 

### Impact Explanation
This is an unauthorized cross-organization write and can lead to an unauthorized deploy on a victim stack — matching the "Critical: unauthorized deploy" category. An attacker never needs push access, a Shipit session, or an `ApiClient` token to a victim's repository; they only need to control a webhook endpoint/secret for any organization configured on the shared Shipit instance (a realistic scenario for a multi-tenant Shipit deployment, e.g. `config/secrets.production.yml` supporting multiple `github:` orgs as shown in `docs/setup.md`).

### Likelihood Explanation
Exploitation requires the attacker to legitimately control one organization's webhook configuration on a multi-org Shipit install and to know the target commit `sha` of a foreign stack (easily discoverable via the public/authenticated Shipit UI or API for that stack). No repository write access to the victim org is needed, and the request forgery itself is a simple crafted HTTP POST with a valid HMAC for the attacker's own secret.

### Recommendation
Bind the verification identity to the actual mutation target: verify the webhook signature using the secret associated with the repository/organization the handler will act on (`repository.full_name`'s owner), not a value chosen independently by the attacker. Additionally, `StatusHandler` (and any other handler using cross-cutting lookups like a bare `sha`) should scope lookups to the repository asserted in the same verified payload, rejecting statuses whose commit's stack does not belong to the repository declared in `repository.full_name`.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.yml`: `attacker-org` (attacker controls the webhook secret) and `victim-org` (hosts a stack `victim/repo` with `continuous_deployment: true`).
2. Attacker finds a pending/undeployed commit `sha` in `victim/repo`'s stack (e.g., via the public Shipit stack page).
3. Attacker crafts a `status` event body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim/repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/attacker"
}
```
4. Attacker signs it with `attacker-org`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly, then POSTs to `/github/webhooks`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"` from the body, calls `Shipit.github(organization: "attacker-org")`, and the signature matches — request passes.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (no repository check), and calls `create_status_from_github!`, marking it `success`.
7. If the victim stack is `deployable?` and has continuous deployment enabled, the scheduled `ContinuousDeliveryJob` deploys the commit automatically — an unauthorized deploy triggered entirely by an attacker with no access to `victim/repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
