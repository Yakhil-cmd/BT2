### Title
Integer-precision overflow in fixed-denomination asset cap calculation lacking magnitude bound on `count_coins` - (File: `validation.js`)

### Summary
`validateAssetDefinition()` in `validation.js` sums `count_coins * denomination` across an asset's declared denominations to derive `total_cap_from_denominations`, then compares it against the declared `cap`. Unlike `denomination`, the `count_coins` field is validated only with `isPositiveInteger()`, which imposes no upper bound (unlike `denomination`, which is explicitly capped at `constants.MAX_CAP`, 9e15). Since JavaScript numbers are IEEE-754 doubles with ~2^53 (~9.007×10^15) safe-integer precision, a crafted combination of `count_coins` and `denomination` can produce a product that silently loses precision, allowing `total_cap_from_denominations` to numerically equal an attacker-chosen `cap` even though the true mathematical product does not. This is the direct analog of the libxslt `xsltAddTextString` bug class: a size/quantity computation that is trusted without an overflow/precision check.

### Finding Description
In `validateAssetDefinition`: [1](#0-0) 
`denomInfo.denomination` is bounded (`isPositiveInteger` + `> constants.MAX_CAP` rejection), but `denomInfo.count_coins` is validated only by: [2](#0-1) 
which merely checks that the value is a finite integer greater than zero — there is no upper limit comparable to `MAX_CAP`. The accumulation `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination` is then compared bit-for-bit against `payload.cap`: [3](#0-2) 
Because both operands can independently approach the JS safe-integer boundary (2^53), their product can exceed `Number.MAX_SAFE_INTEGER`, causing floating-point rounding. An attacker can choose `count_coins` and `denomination` such that the *rounded* product coincides with a smaller, "innocent-looking" `cap` value passed in the same asset-definition message, passing the `total_cap_from_denominations !== payload.cap` check even though the real (mathematically exact) issuable supply for that denomination differs from what the cap implies.

This directly feeds subsequent issuance/consensus logic that trusts `asset_denominations.count_coins` as authoritative for how many coins of that denomination may ever be issued (see `pickIndivisibleCoinsForAmount`'s `issueNextCoin`, which computes `issue_amount = count_coins_to_issue * denomination` from the stored `count_coins`): [4](#0-3) 
and the per-issue-input validation `validateIndivisibleIssue`, which recomputes `denomination * denomInfo.count_coins` from the same stored, unbounded `count_coins`: [5](#0-4) 
Every node performing this arithmetic in floating point will reach the same (rounded) result deterministically, so this does not by itself cause consensus divergence between nodes — but it does mean the on-chain "cap" bookkeeping and the true combinatorial supply diverge from what a definer/holder believes they defined, because the validation gate that is supposed to enforce `cap == Σ(count_coins·denomination)` can be satisfied with values whose true product is different from the displayed/declared `cap`.

### Impact Explanation
An unprivileged asset issuer (the message poster who defines the asset) fully controls `payload.cap`, `denomination`, and `count_coins` in the `asset` message reachable from any ordinary posted unit. This is exactly the class of "asset issuance and transfer conditions" pathway called out as in-scope. If an attacker can construct a denomination/count_coins pair whose product silently overflows/rounds to match a chosen (smaller or otherwise misleading) `cap`, they can define an indivisible/fixed-denomination asset whose declared cap does not truly reflect the maximum number of base units mintable across its denomination table — a form of asset supply integrity violation for that asset (analogous to CWE-787's "size calculated without overflow check leading to memory corruption": here the "size" being miscalculated is the mintable-supply size).

### Likelihood Explanation
Reachability is trivial and requires no privileges: any address can post a unit containing an `asset` definition message with `fixed_denominations: true` and a `denominations` array of attacker-chosen `{denomination, count_coins}` pairs, up to `MAX_DENOMINATIONS_PER_ASSET_DEFINITION` (64) entries — plenty of room to construct values near the 2^53 boundary. However, I was not able to fully confirm within available time whether all downstream consumers (wallet display, indivisible-asset issuance limits, definer expectations) actually rely on `cap` as a security-relevant invariant beyond informational/UI purposes, or whether some other check elsewhere effectively neutralizes the practical exploitability (e.g., whether any code path other than this validation function treats `cap` as authoritative for enforcement). This uncertainty affects the assessed severity.

### Recommendation
Add an explicit magnitude bound on `count_coins` analogous to the existing `denomination > MAX_CAP` check, and validate the intermediate product before accumulating, e.g.:
- Reject `count_coins` values where `count_coins > constants.MAX_CAP` or where `count_coins * denomination` exceeds `Number.MAX_SAFE_INTEGER` (`Number.isSafeInteger(count_coins * denomination)`).
- Perform the accumulation and comparisons using an arbitrary-precision arithmetic library (e.g., `Decimal`/BigInt) rather than native `number` multiplication, matching the pattern already used elsewhere in the codebase (`Decimal` in `formula/evaluation.js`) for values that can approach unsafe-integer ranges.

### Proof of Concept
1. Post a unit with an `asset` message: `{ fixed_denominations: true, cap: <C>, denominations: [{ denomination: d1, count_coins: n1 }, { denomination: d2, count_coins: n2 }, ...] }` where `d_i, n_i` are chosen (via brute search) such that `Σ n_i*d_i` computed in IEEE-754 double precision rounds to exactly `C`, while the exact (arbitrary precision) sum is different from `C`.
2. Because `isPositiveInteger` places no upper bound on `count_coins`, and `denomination`'s only bound is `<= MAX_CAP` (9e15), operands near 2^53 can be selected so their product's least-significant bits are lost to floating-point rounding, letting `total_cap_from_denominations === payload.cap` pass at line 2790 of `validation.js` despite the true product differing.
3. The asset definition is accepted; downstream issuance logic (`indivisible_asset.js` lines 516–588) subsequently uses the stored (unbounded) `count_coins` to compute `issue_amount = count_coins_to_issue * denomination` for actual minting, inheriting the same precision-loss characteristics whenever amounts approach the unsafe-integer range.
