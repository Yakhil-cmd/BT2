### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while the acted-upon repository is taken from `repository.full_name`, allowing cross-repository webhook forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` (or `params.dig('organization','login')`). But `Handler#repository_name`, used by every webhook handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) to look up the target `Stack`, reads a *different* field of the same JSON body: `payload.dig('repository','full_name')`. In a multi-organization Shipit configuration these two fields are never checked for consistency, so a payload can be validly signed with one organization's secret while acting on a repository belonging to another organization.

### Finding Description
The controller's authenticity check is: [1](#0-0) 
which picks the app/secret via `repository_owner`: [2](#0-1) 

Once the signature is accepted, the actual event dispatch resolves the target `Stack`s using a **different** JSON field: [3](#0-2) 

Shipit explicitly supports one `webhook_secret` per organization (config keyed by org name): [4](#0-3) 

The equality the deployment-trust model assumes is:
`organization whose secret authenticated the request == organization that owns the repository whose Stack the handler mutates`

This holds only because in practice `repository.owner.login` and `repository.full_name`'s owner segment are expected to match — but nothing in the code enforces that. An attacker who legitimately owns/administers an organization ("OrgOne") configured in Shipit (e.g. because they are a normal, unprivileged GitHub org owner who set up their own GitHub App/webhook per the multi-org setup docs) knows OrgOne's `webhook_secret`. They can POST a webhook body where:
- `repository.owner.login` = `"OrgOne"` (or `organization.login` = `"OrgOne"`) → `verify_signature` picks OrgOne's app and validates the HMAC using the secret the attacker controls, so the signature check passes.
- `repository.full_name` = `"OrgTwo/victim-repo"` → `Handler#repository_name` resolves the actual victim `Stack` tracked under a different, unrelated organization.

This breaks the binding between "organization that authenticated" and "repository that is written," directly matching the report's bug class: a value used for the security check (`repository.owner.login`) is not the same value later trusted for the state-changing operation (`repository.full_name`).

### Impact Explanation
Depending on which event/handler is exercised, the attacker can:
- Force `PushHandler` to enqueue `GithubSyncJob` for a victim `Stack`'s branch with an attacker-chosen `expected_head_sha`: [5](#0-4) 
- Forge a `StatusHandler` "success" CI status for an arbitrary commit on a victim repo tracked by Shipit: [6](#0-5) , which can influence continuous-delivery gating (Shipit's continuous delivery mechanism reacts to commit/CI status) and lead to an **unauthorized deploy** being triggered on a repository the attacker does not own or have write access to.
- Trigger `CheckSuiteHandler` to force a check-run refresh against a victim stack's commit: [7](#0-6) 

This satisfies the "High/Critical" bar in scope: cross-organization/cross-repository writes to Shipit's tracked state, and a plausible path to an unauthorized deploy if the victim stack has continuous delivery enabled.

### Likelihood Explanation
Exploitability requires the deployment to be configured with **multiple GitHub organizations** (each with its own `webhook_secret`), which is a documented, supported configuration (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`). The attacker only needs to be a legitimate, unprivileged administrator of one of those organizations (able to view/replay their own org's webhook secret) — no Shipit session, API token, or GitHub App private key is required, satisfying the unprivileged-attacker constraint. Single-organization deployments are not affected since there is only one secret to check against.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the organization used to select the verifying secret is the same organization embedded in `repository.full_name` — e.g., verify `params.dig('repository','full_name')&.split('/')&.first == repository_owner` before dispatching to handlers, and reject the request (422) on mismatch. Alternatively, bind the resolved `Stack`/`Repository` lookup to the same normalized owner value used for signature verification rather than trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with its own `github.webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), and track a repository `OrgTwo/victim-repo` in Shipit.
2. As an attacker who legitimately administers `OrgOne` (and thus knows `OrgOne`'s `webhook_secret`), craft a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgOne_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and the HMAC validates successfully.
5. `PushHandler#repository_name` resolves `"OrgTwo/victim-repo"` and enqueues `GithubSyncJob` for that stack — a cross-organization action reached with a signature the attacker legitimately produced for an unrelated organization.
