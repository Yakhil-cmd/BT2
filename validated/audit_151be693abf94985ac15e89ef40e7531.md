### Title
Pre-publish-exechook is decoupled from the symlink publish action, allowing the atomic-publish guarantee to be broken by a fire-and-forget hook dispatch - (File: main.go, pkg/hook/hook.go)

### Summary
The reported bug class is that a stateful pairing (pre-hook / post-hook) is not enforced to execute together, so an attacker can split the two phases and substitute unrelated data in between. The corresponding weakness in `git-sync` is that `beforePublish` (the pre-publish-exechook) is dispatched to an asynchronous `HookRunner` via a fire-and-forget, non-blocking channel send and the caller does not wait for the hook to actually run or succeed before the symlink publish proceeds. This breaks the "hook completes → then publish" contract that the tool documents.

### Finding Description
`SyncRepo` builds a `syncHooks` value where `beforePublish` is defined as: [1](#0-0) 

`beforePublish` calls `prePubExechookRunner.Send(hash)` and returns `nil` unconditionally. `Send` only performs a non-blocking write into a size-1 channel and updates a shared `hash` field protected by a mutex — it does not wait for the underlying command to run to completion: [2](#0-1) [3](#0-2) 

The actual execution happens later, asynchronously, in the separate `HookRunner.Run` goroutine: [4](#0-3) 

Meanwhile, `SyncRepo` treats the (immediate, no-op) return of `beforePublish` as proof that the pre-publish step is done and proceeds straight to `publishSymlink`, which atomically flips the consumer-visible `--link`: [5](#0-4) 

The comment right above this code explicitly documents the intended invariant — that the pre-publish hook must run *before* the link is published — but the implementation does not enforce it synchronously: [6](#0-5) 

Because `hookData` only remembers the *latest* hash (`d.hash = newHash`) and the `HookRunner` goroutine independently pulls "the latest value" when it wakes up, a fast series of remote-ref updates (fully controlled by whoever owns/pushes to the tracked branch — i.e., attacker-controlled repo content within the `--ref` git-sync follows) can cause the pre-publish-exechook goroutine to still be processing (or retrying, per its own `--pre-publish-exechook-backoff`) hash A while the main sync loop has already moved on, built worktree B, and called `syncHooks.beforePublish(B)` and `publishSymlink(B)`. Because `Send`/`get` just track the newest value with no correlation back to which `publishSymlink` call it was meant to gate, the pairing between "prepare/validate hash X" and "publish hash X" is not enforced — analogous to the report's decoupling of `rebalanceOrderPreHook` from `rebalanceOrderPostHook`.

The single unit test for this mechanism (`TestHookData`) only checks that "last update wins" — it does not test for, or guard against, the ordering/completion guarantee between publish and hook execution: [7](#0-6) 

### Impact Explanation
Consumers of `git-sync`'s `--link` rely on the documented "Atomic-Symlink Contract" that the symlink only flips once the synced tree is ready, and specifically that `--pre-publish-exechook-command` — the mechanism operators use to run pre-publish validation/preparation logic against a specific revision — completes before that revision is exposed. Because the hand-off is fire-and-forget, the tool can publish (flip the symlink to) a new hash without the pre-publish-exechook having actually completed for that hash, or while it is retrying against a stale/different hash. This can result in publishing content that has not passed the operator's pre-publish gating, i.e., "publishing wrong or partial content" to downstream consumers — one of the explicitly accepted impact categories.

### Likelihood Explanation
This requires `--pre-publish-exechook-command` to be configured (an opt-in feature), and requires rapid successive updates to the tracked ref/commits — something entirely under the control of whoever can push to the repository/ref that `git-sync` follows. No privileged access to the git-sync host, credentials, or config is needed beyond normal repo push access, and the race window is created by the tool's own architecture (independent goroutines communicating via a "latest value wins" channel) rather than by any external timing constraint, making it reasonably achievable by an attacker who controls the upstream content.

### Recommendation
- Short term: make `syncHooks.beforePublish` block until the underlying `Exechook.Do` call for the specific target hash has actually completed successfully (e.g., have `HookRunner.Send` return a per-call completion channel, similar to the existing `oneTimeResult`/`WaitForCompletion` mechanism used for `--one-time` mode, and have `SyncRepo` wait on it) before calling `publishSymlink`.
- Long term: redesign the hook dispatch so that the hash "in flight" through `hookData` is tied to the specific `SyncRepo` iteration that requested it, rather than a shared mutable "latest hash" that any concurrent goroutine can observe/execute against, removing the possibility of publish/hook-completion ordering being violated under rapid ref churn.

### Proof of Concept
1. Start `git-sync` with `--pre-publish-exechook-command=/slow-validate.sh --pre-publish-exechook-timeout=30s --pre-publish-exechook-backoff=5s --period=1s` tracking a branch the attacker controls.
2. Attacker pushes commit A. `SyncRepo` builds worktree A, calls `syncHooks.beforePublish("A")` → `prePubExechookRunner.Send("A")` (non-blocking) → returns `nil` immediately (see `main.go:1021-1038`).
3. Before `/slow-validate.sh` (running in the background `HookRunner.Run` goroutine) finishes for hash A, `SyncRepo` has already called `publishSymlink(worktreeA)`, exposing content A to consumers — even though the pre-publish validation for A has not completed.
4. Attacker then rapidly pushes commit B. On the next loop iteration, `beforePublish("B")` again just enqueues into the same `hookData` (`pkg/hook/hook.go:79-89`), overwriting the pending value, and `publishSymlink(worktreeB)` again proceeds without waiting — so the pre-publish-exechook may end up validating/acting on hash B while consumers already saw (or are about to see) hash A or vice versa, demonstrating that "pre-hook" and "publish" are not coupled as the documented contract requires.

*Note: full confirmation that no other code path (outside the excerpts reviewed) calls `prePubExechookRunner.WaitForCompletion()` in the non-`--one-time` steady-state loop could not be fully verified against every line of `main.go`'s loop given index size limits; if such a synchronous wait exists elsewhere in the main loop for the non-one-time path, it would mitigate this finding. Starting a full Devin session to grep the complete `main.go` sync loop would give definitive confirmation.*

// Run waits for trigger events from the channel, and run hook when triggered.
func (r *HookRunner) Run(ctx context.Context) {
	var lastHash string

	// Wait for trigger from hookData.Send
	for range r.data.events() {
		// Retry in case of error
		for {
			// Always get the latest value, in case we fail-and-retry and the
			// value changed in the meantime.  This means that we might not send
			// every single hash.
			hash := r.data.get()
			if hash == lastHash {
				break
			}

			if err := r.hook.Do(ctx, hash); err != nil {
				r.log.Error(err, "hook failed", "hash", hash, "retry", r.backoff)
				updateHookRunCountMetric(r.hook.Name(), "error")
				// don't want to sleep unnecessarily terminating anyways
				r.sendOneTimeResultAndTerminate(false)
				time.Sleep(r.backoff)
			} else {
				updateHookRunCountMetric(r.hook.Name(), "success")
				lastHash = hash
				r.sendOneTimeResultAndTerminate(true)
				break
			}
		}
	}
}
