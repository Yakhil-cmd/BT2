## Analog Found [1](#0-0) 

### Title
CCMenu token minted without a `stack` binding grants read access to every stack, not just the one it was issued for - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints a long-lived `ApiClient` bearer token intended to scope `read:stack` access to a single stack (the one the CCMenu URL is generated for), but the `ApiClient` record backing that token is created without ever setting its `stack` association. Because `Api::BaseController#stacks` treats an unset `stack_id` as "unscoped, see all stacks", the resulting token silently authorizes read access to every stack in the installation instead of the one stack the feature is meant to expose.

### Finding Description
The CCMenu URL feature is meant to hand out a narrow, per-stack, unauthenticated-bearer credential meant to be embedded in third-party CI dashboard tools (CCMenu clients) that poll a single project's build status: [1](#0-0) 

```ruby
class CCMenuUrlController < ShipitController
  def fetch
    uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
    uri.query = { 'token' => client.authentication_token }.to_query
    render(json: { ccmenu_url: uri.to_s })
  end

  private

  def client
    @client ||= ApiClient.create_with(permissions: %w[read:stack])
                         .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
  end

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end
end
```

The `client` lookup is keyed only on `creator` and `name` (`'CCMenu Client'`) - the target `stack` is never passed into `find_or_create_by!`, so the `ApiClient.stack_id` column is left `nil`. This means:

1. A single `ApiClient` per user is reused across every stack for which that user requests a CCMenu URL (`find_or_create_by!` returns the same record every time).
2. Since `stack_id` is `nil`, `ApiClient#stack_id?` is falsy, and `Api::BaseController#stacks` resolves to `Stack.all` rather than the single intended stack: [2](#0-1) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
```

The `permissions: %w[read:stack]` restriction passed to `create_with` is honored by `ApiClient#check_permissions!` [3](#0-2) , but permission checks only gate the *operation* (`read`), not *which* stack the operation applies to. Every `Api::*` controller that uses `require_permission :read, :stack` (e.g. `Api::CommitsController`, `Api::StacksController#index/show`, `Api::TasksController`) resolves its target stack through this same unscoped `stacks`/`stack` helper, so the token is valid there too.

This breaks the binding: **stack a token authorizes == stack it touches**. The token is generated in a UI flow that visually and semantically ties it to one stack (`api_stack_ccmenu_url(stack_id: stack.to_param)`), but the credential's actual authorization scope is "every stack in the Shipit instance."

### Impact Explanation
CCMenu URLs are explicitly designed to be pasted into third-party, often publicly-reachable, CI status-monitoring tools/dashboards - they carry the bearer token in the URL query string by design (`uri.query = { 'token' => ... }`). Anyone who obtains this URL (through a public build dashboard, browser history, proxy/log exposure, or a leaked bookmark) gains a fully functional API bearer credential with `read:stack` permission across **every** stack managed by the Shipit instance - including stacks the exposing user was never trying to share, and stacks belonging to other repositories/teams. This is unauthenticated read of stack state (commits, tasks, deploy metadata) for the entire fleet, sourced from a credential meant to be low-sensitivity and single-purpose.

### Likelihood Explanation
No privileged access is required beyond the ability to visit the (unprivileged, per-user) "CCMenu URL" feature that any logged-in Shipit user can trigger for any stack they can view; the resulting token is then commonly copy-pasted into external, less-trusted systems by design of the feature. The bug is deterministic: it fires on the very first CCMenu URL request for any user, with no edge case required.

### Recommendation
Include the target `stack` in the `find_or_create_by!` lookup/creation attributes (e.g. `find_or_create_by!(creator: current_user, name: 'CCMenu Client', stack:)`), and consider issuing one dedicated `ApiClient` per stack rather than reusing a single client keyed only on `creator`/`name`. Additionally, `Api::BaseController#stacks` should not silently fall back to `Stack.all` for any `ApiClient` whose `stack_id` is unexpectedly `nil` for scoped-only use cases.

### Proof of Concept
1. As any logged-in Shipit user, request the CCMenu URL for `stack-A` (`GET /:stack-A/ccmenu_url` route wired to `CCMenuUrlController#fetch`). This creates (or reuses) an `ApiClient` named `"CCMenu Client"` for that user with `permissions: ["read:stack"]` and `stack_id: nil`, and returns a token `T`.
2. Using `T` as HTTP Basic auth against the JSON API, call `GET /api/stacks` or `GET /api/:stack-B/commits` for any other stack `stack-B` that the requesting user never asked to expose via CCMenu.
3. Because `ApiClient#stack_id?` is `false`, `Api::BaseController#stacks` returns `Stack.all`, and the request against `stack-B` succeeds, returning commit/task data for a stack the token was never intended to authorize.
