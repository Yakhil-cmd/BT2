### Title
Unbounded recursive `evaluate()` in address/asset definition validation causes stack exhaustion via deeply nested `and`/`or` chains - (File: `definition.js`)

### Summary
`Definition.validateDefinition()` and `Definition.validateAuthentifiers()` in `definition.js` recursively walk an attacker-supplied address/asset-condition definition tree with a plain function-call recursion (`evaluate()`), bounding only the *total* number of nodes visited (`complexity`/`count_ops` vs `constants.MAX_COMPLEXITY`/`MAX_OPS`), but never bounding *recursion depth* directly. This mirrors the CVE-2019-9903 root cause: `PDFDoc::markObject`/`Dict::find()` recursed on nested dictionary structures with no depth guard, exhausting the native stack. Elsewhere in the same codebase (`formula/validation.js`) the developers explicitly added a depth counter and `setImmediate` "trampoline" specifically to avoid this class of bug, but the same protection was never applied to `definition.js`'s `evaluate()`.

### Finding Description
`validateDefinition`'s `evaluate()` increments `complexity`/`count_ops` and checks them against `constants.MAX_COMPLEXITY`/`MAX_OPS` on entry, then recurses into `and`/`or`/`r of set` branches: [1](#0-0) 

Because each nesting level of a chain like `['and',[['and',[['and',[...['sig',{...}]]]]]]]` costs only 1 unit of `complexity`, an attacker can build a chain whose *nesting depth* equals the entire `MAX_COMPLEXITY`/`MAX_OPS` budget. Each level of that chain adds a real JS stack frame (`evaluate` → `async.eachSeries` → closure → `evaluate` …) before the complexity/ops limit is ever hit, so the check happens too late to prevent stack growth — exactly the "mishandles dict marking … leading to stack consumption" pattern described in the CVE.

The same unguarded recursion pattern exists in the sibling authentication-time evaluator: [2](#0-1) 

and in the purely synchronous, completely unguarded `hasReferences()` helper (no complexity check at all): [3](#0-2) 

By contrast, the oscript/AA formula evaluator (`formula/validation.js`) was hardened against exactly this bug class with an explicit depth counter and stack-interrupting `setImmediate`/`setTimeout` trampoline: [4](#0-3) 

The comment "avoid extra long call stacks to prevent Maximum call stack size exceeded" confirms the developers already recognize and mitigate this exact bug class for formulas, but the mitigation was not carried over to `definition.js`'s definition/authentifier evaluators.

### Impact Explanation
`validateDefinition`/`validateAuthentifiers` are invoked for every unit that defines or uses an address definition, or an asset's `issue_condition`/`transfer_condition` (reachable via `validateAssetDefinition`): [5](#0-4) 

Since the malicious deeply-nested definition is deterministic content of a broadcast unit, every full node that attempts to validate that unit will hit the same unbounded recursion and crash (native stack overflow) at the same point, before complexity limits can reject it. This is not a single-victim DoS: it is a network-wide validation crash triggered by content any unprivileged unit poster can construct, satisfying "a network unable to confirm new units" (all honest nodes fail identically when validating/re-validating the offending unit or any address/asset definition built the same way).

### Likelihood Explanation
Constructing a deeply nested `['and', [['and', [...]]]]` (or `or`, or `r of set`) chain is trivial and entirely under attacker control — no special privileges, keys, or prior state are needed, only the ability to post a unit defining/using such an address or asset condition. The only unknowns are the exact numeric values of `constants.MAX_COMPLEXITY`/`MAX_OPS` (not confirmed by the available index) and the JS engine's exact stack-frame budget for this closure-heavy call chain; but because `evaluate()` uses `async.eachSeries` and creates several nested closures per level, real-world V8 stack depth typically overflows in the low thousands of frames, well within plausible values of `MAX_COMPLEXITY`/`MAX_OPS` used for legitimate complex definitions.

### Recommendation
- Add an explicit recursion-depth counter to `evaluate()` in both `validateDefinition` and `validateAuthentifiers` in `definition.js`, matching the pattern already used in `formula/validation.js` (reject once depth exceeds a small constant, e.g. 100).
- Alternatively, convert the recursion to an iterative, explicit-stack-based traversal for `and`/`or`/`r of set`/`weighted and`.
- Apply the same depth bound to `hasReferences()` in `definition.js`, which currently has no limit whatsoever.

### Proof of Concept
Construct an address (or asset `issue_condition`/`transfer_condition`) definition of the form:
```
['and', [
  ['and', [
    ['and', [
      ... (repeat N times, N close to MAX_COMPLEXITY/MAX_OPS) ...
      ['sig', {pubkey: '<valid pubkey>'}]
    ]]
  ]]
]]
```
Post a unit that defines an address with this definition (or an asset whose `issue_condition`/`transfer_condition` uses it). When any node calls `Definition.validateDefinition()` (directly during initial validation, or via `Definition.validateAuthentifiers()` during authentifier checking on subsequent spends), the synchronous recursive `evaluate()` calls will exhaust the JS call stack before the `complexity`/`count_ops` limit check can reject the deeply-nested but narrow (depth ≫ width) structure, crashing the validating node's process.
