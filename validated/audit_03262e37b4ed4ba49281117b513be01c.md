### Title
Pre-publish exechook is asynchronous and does not gate `publishSymlink`, allowing unvalidated/attacker-pushed content to be published before the gating hook runs or succeeds - (File: main.go)

### Summary
`git-sync` advertises `--pre-publish-exechook-command` as a hook that runs "after syncing a new hash... but before publishing the symlink," implying it acts as a gate that can validate a newly-fetched commit before it is exposed to consumers. In reality, `syncHooks.beforePublish` only *fires* the hook asynchronously (fire-and-forget) and immediately proceeds to `publishSymlink`, without waiting for the hook to run or succeed. This mirrors the reported bug class: a sensitive/consumer-visible state transition (vault minting shares / here, publishing new git content to the `--link` symlink) is performed on a path that skips the gating check that is enforced elsewhere (share lock timer / here, the pre-publish validation hook).

### Finding Description
The documented contract states the pre-publish hook runs "before publishing the symlink": [1](#0-0) 

The `beforePublish` closure only sends the hash into an async channel and returns `nil` unconditionally, never waiting on or propagating the result of the actual hook execution: [2](#0-1) 

In `SyncRepo`, once `beforePublish` returns, `publishSymlink` is called immediately in the very next statement: [3](#0-2) 

The `Send` method performs a non-blocking channel write and returns instantly; the actual hook (`hook.Do`) executes later, in a separate goroutine (`HookRunner.Run`), decoupled from the caller: [4](#0-3) 

Because `beforePublish` cannot return an error from the hook (it always returns `nil`), and `publishSymlink` executes unconditionally right after, the symlink flip to the newly fetched worktree (which may contain attacker-pushed content from the upstream repo) happens concurrently with — not gated by — the pre-publish validation. Even in `--one-time` mode, `prePubExechookRunner.WaitForCompletion()` is only invoked later in the outer loop, after `SyncRepo` (and therefore `publishSymlink`) has already returned: [5](#0-4) 

so that wait only affects the process exit code, not whether the new content was already exposed via the symlink. There is also no rollback of the symlink if the hook subsequently fails.

### Impact Explanation
Operators commonly use `--pre-publish-exechook-command` as a security/validation gate (e.g., signature verification, content scanning, policy checks) before untrusted upstream content reaches the consuming application container. Because the hook does not actually block publication, an attacker who can push a commit to the synced upstream repository can have that content published to the shared `--link` volume and consumed by the application before (or even if) the gating hook rejects it. This results in publishing wrong/unvalidated content to consumers, defeating the intended security control — directly analogous to the reported bypass of the vault's `shareUnlockTime` gate via an alternate mint path that skips `_afterPublicDeposit`.

### Likelihood Explanation
This is triggered on every sync in which `--pre-publish-exechook-command` is configured and a new hash is fetched — no special flags beyond enabling that (documented, commonly recommended for validation use-cases) feature are required. An attacker only needs push access to the synced upstream repository (or the ability to have their commit merged/fetched), which is the standard threat model for `git-sync`.

### Recommendation
Make `beforePublish` synchronous with respect to `publishSymlink`: block until the pre-publish-exechook command completes and propagate its success/failure into the return value of `beforePublish`, so that `SyncRepo` aborts (and does not call `publishSymlink`) when the hook fails, instead of firing the hook asynchronously and racing ahead to update the symlink.

### Proof of Concept
1. Configure git-sync with `--pre-publish-exechook-command=/validate.sh`, where `/validate.sh` is meant to reject disallowed commits (e.g., sleeps/scans and exits non-zero for a bad commit).
2. Push a malicious/disallowed commit to the synced repo.
3. Observe in `SyncRepo` (main.go:1955-1963) that `syncHooks.beforePublish(hash)` returns immediately (it only calls `prePubExechookRunner.Send(hash)`), and `git.publishSymlink(newWorktree)` executes right after — before `/validate.sh` has even started running in its goroutine, let alone finished.
4. The consumer container, reading through `--link`, observes the malicious commit's content immediately, regardless of whether `/validate.sh` eventually fails.

```go
// Send sends hash to hookdata.
func (r *HookRunner) Send(hash string) {
	r.data.send(hash)
}

// Run waits for trigger events from the channel, and run hook when triggered.
func (r *HookRunner) Run(ctx context.Context) {
	var lastHash string

	// Wait for trigger from hookData.Send
	for range r.data.events() {
		// Retry in case of error
		for {
			// Always get the latest value, in case we fail-and-retry and the
			// value changed in the meantime.  This means that we might not send
			// every single hash.
			hash := r.data.get()
			if hash == lastHash {
				break
			}

			if err := r.hook.Do(ctx, hash); err != nil {
				r.log.Error(err, "hook failed", "hash", hash, "retry", r.backoff)
				updateHookRunCountMetric(r.hook.Name(), "error")
				// don't want to sleep unnecessarily terminating anyways
				r.sendOneTimeResultAndTerminate(false)
				time.Sleep(r.backoff)
			} else {
				updateHookRunCountMetric(r.hook.Name(), "success")
				lastHash = hash
				r.sendOneTimeResultAndTerminate(true)
				break
			}
		}
	}
}
```
