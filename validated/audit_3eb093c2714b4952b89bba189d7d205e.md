## Finding: Analog Identified

### Title
Missing zero-address validation on bridge `target_address` allows permanent burning of bridged native ETH - (File: `crates/sui-framework/packages/bridge/sources/bridge.move`, `bridge/evm/contracts/SuiBridge.sol`, `bridge/evm/contracts/BridgeVault.sol`)

### Summary
The Sui Native Bridge's `send_token`/`send_token_v2` entry points only validate that the caller-supplied EVM `target_address` has the correct byte length (20 bytes); they never check that it isn't the reserved zero address. That unchecked value is embedded into a `BridgeMessage`, propagated unmodified through the EVM claim path (`decodeTokenTransferPayload` / `decodeTokenTransferPayloadV2`, `_transferTokensFromVault`), and ultimately used as the destination of `BridgeVault.transferETH`, which performs a raw low-level `.call{value: amount}("")`. A call with value to `address(0)` succeeds (no revert), so any bridged native ETH routed to the zero address is burned with no path to recovery — this is the exact same root cause as the ThorSwap bug: an unvalidated, user-supplied destination address flowing straight into a value-moving function with no whitelist/hardcode/sanity check.

### Finding Description
`send_token`/`send_token_v2` in [1](#0-0)  and [2](#0-1)  only assert `target_address.length() == EVM_ADDRESS_LENGTH` — there is no check rejecting the all-zero 20-byte address. This unvalidated `target_address` is embedded in the `BridgeMessage` and, once committee-approved, is decoded on the EVM side by `BridgeUtils.decodeTokenTransferPayload`/`decodeTokenTransferPayloadV2`, neither of which perform a zero-address check either ( [3](#0-2) , [4](#0-3) ).

That decoded `recipientAddress` is passed straight into `_transferTokensFromVault`, which likewise contains no address validation ( [5](#0-4) ), and for `tokenID == BridgeUtils.ETH` calls `vault.transferETH(payable(recipientAddress), amount)`. `BridgeVault.transferETH` unwraps WETH and sends raw ETH via a low-level call with no zero-address guard: [6](#0-5) . A `.call{value: amount}("")` to `address(0)` on Ethereum succeeds (it just accepts value, since address(0) has no code and doesn't revert), so the ETH is irrecoverably burned. Unlike the ERC20 path — where `SafeERC20.safeTransfer` typically reverts on `to == address(0)` because most ERC20 implementations (e.g., OpenZeppelin) explicitly forbid it — the native-ETH transfer path has no equivalent protection anywhere in the pipeline.

### Impact Explanation
Bridged native ETH routed with `target_address = 0x00..00` is permanently and unrecoverably burned once the committee approves and executes the transfer, with no mechanism to reclaim the funds. This matches the HackenProof "unintended permanent burning below the 10B cap" High/Medium impact category, and mirrors the ThorSwap analog precisely: an address that is syntactically valid (correct length) but semantically wrong/unusable, passed through unvalidated into a fund-moving function.

### Likelihood Explanation
The path is fully reachable by any ordinary bridge user calling `send_token`/`send_token_v2` with a crafted 20-byte all-zero `target_address` — no privileged role, validator, or governance action is required. Validation is missing consistently at every layer (Move entry point, BCS decode on EVM, internal vault transfer), so there is no compensating control anywhere in the call chain.

### Recommendation
Add an explicit reject for the zero address (and any other reserved/burn addresses) in `send_token`/`send_token_v2` in `bridge.move` immediately after the length check, and add a defense-in-depth `require(recipientAddress != address(0), ...)` check in `BridgeVault.transferETH` (and ideally in `_transferTokensFromVault`/`BridgeUtils` decode functions) mirroring the zero-address guard that ERC20 tokens already provide implicitly for the token-transfer path.

### Proof of Concept
1. Attacker/user calls `bridge::send_token<ETH>(bridge, eth_chain_id, x"0000000000000000000000000000000000000000", eth_coin, ctx)` — passes the `target_address.length() == 20` check in [7](#0-6) .
2. Bridge committee observes and signs the resulting `BridgeMessage` per normal operation (no special validator behavior needed — this is standard approval flow).
3. Relayer submits `transferBridgedTokensWithSignatures`/`transferBridgedTokensWithSignaturesV2` on `SuiBridge.sol`; `decodeTokenTransferPayload` accepts the zero recipient (only length is checked).
4. `_transferTokensFromVault` calls `vault.transferETH(payable(address(0)), amount)`.
5. `BridgeVault.transferETH` executes `address(0).call{value: amount}("")`, which returns `success = true`; the ETH is burned permanently with no recipient able to retrieve it.

public fun send_token<T>(
    bridge: &mut Bridge,
    target_chain: u8,
    target_address: vector<u8>,
    token: Coin<T>,
    ctx: &mut TxContext,
) {
    let inner = load_inner_mut(bridge);

    let bridge_seq_num = inner.get_current_seq_num_and_increment(message_types::token());
    let token_id = inner.treasury.token_id<T>();
    let token_amount = token.balance().value();
    assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
    assert!(token_amount > 0, ETokenValueIsZero);

    // create bridge message
    let message = message::create_token_bridge_message(
        inner.chain_id,
        bridge_seq_num,
        address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_id,
        token_amount,
    );

    inner.send_token_internal(target_chain, token, message);

    // emit event
    event::emit(TokenDepositedEvent {
        seq_num: bridge_seq_num,
        source_chain: inner.chain_id,
        sender_address: address::to_bytes(ctx.sender()),
        target_chain,
        target_address,
        token_type: token_id,
        amount: token_amount,
    });
}

    /// @notice Unwraps stored wrapped ETH and transfers the newly withdrawn ETH to the provided target
    /// address. Only the owner of the contract can call this function.
    /// @dev This function is intended to only be called by the SuiBridge contract.
    /// @param recipientAddress The address to transfer the ETH to.
    /// @param amount The amount of ETH to transfer.
    function transferETH(address payable recipientAddress, uint256 amount)
        external
        override
        onlyOwner
        nonReentrant
    {
        // Unwrap the WETH
        wETH.withdraw(amount);
