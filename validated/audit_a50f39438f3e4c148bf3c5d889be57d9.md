### Title
Cross-organization webhook forgery via organization/repository binding mismatch in `WebhooksController#verify_signature` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate an inbound webhook's HMAC based on `repository.owner.login`, while every event `Handler` resolves the *target* stacks/repository to act on using an entirely different field, `repository.full_name`. Because nothing ties these two fields together, an attacker who controls (and thus knows the `webhook_secret` of) any organization/GitHub App onboarded to a shared, multi-tenant Shipit instance can forge a validly-signed webhook whose `repository.owner.login` matches their own organization (so the signature check passes with their own secret) but whose `repository.full_name` points at a completely different organization's stack, causing handlers to act on that victim stack.

### Finding Description
`verify_signature` picks the verifying `GitHubApp` instance solely from `repository_owner`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`GitHubApp#verify_webhook_signature` verifies the raw body's HMAC against the `webhook_secret` configured for that specific organization only:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [4](#0-3) [5](#0-4) 

Shipit supports configuring multiple, independently-secreted GitHub Apps/organizations in a single instance (see `config/secrets.development.example.yml`), each with its own `webhook_secret`. Once the controller has verified the body's HMAC using the secret belonging to `repository.owner.login`, it hands the *entire raw payload* to `Shipit::Webhooks.for_event(event)` handlers unmodified:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [6](#0-5) 

But every `Handler` resolves the target repository/stacks from a **different** field, `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 

Because `repository.owner.login` (used only for secret selection) and `repository.full_name` (used only for target resolution) are both attacker-supplied fields inside the same signed body, and the HMAC only proves "this body was signed with organization A's secret" — not "this body's `full_name` belongs to organization A" — an attacker who knows organization A's `webhook_secret` (e.g., because they administer their own GitHub App/organization onboarded into this shared Shipit instance) can construct a payload with `repository.owner.login = "org-a"` and `repository.full_name = "victim-org/victim-repo"`, sign it with org A's secret, and have it accepted and dispatched against the victim organization's stack.

This directly matches the equality the analog must break: **organization authenticated (`repository.owner.login` → `webhook_secret` lookup) ≠ repository written (`repository.full_name` → `Stack` acted upon)**.

### Impact Explanation
The most severe reachable consequence is via the `status` event, handled by `Shipit::Webhooks::Handlers::StatusHandler`, which creates a `Shipit::Status` record for a commit on the resolved (attacker-chosen) stack:
```ruby
after_create :enable_ci_on_stack
after_commit :schedule_continuous_delivery, :broadcast_update, on: :create
``` [8](#0-7) 

If the victim stack has `continuous_deployment: true`, creating a `success` status for the latest undeployed commit triggers `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → `Stack#trigger_deploy`, which builds and enqueues a real `Deploy`:
```ruby
def trigger_continuous_delivery
  ...
  trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
end
``` [9](#0-8) 

This is confirmed by existing test coverage showing that creating a `success` `Status` on a commit for a CD-enabled stack enqueues and runs a `Deploy`: [10](#0-9) 

Thus an attacker who legitimately controls organization A's GitHub App/webhook secret within a shared Shipit deployment can spoof a fabricated "CI success" status against organization B's protected repository/stack, triggering an unauthorized deploy on B's infrastructure without ever having CI actually pass and without possessing B's `webhook_secret`, an `ApiClient` token, or a Shipit session.

### Likelihood Explanation
This requires: (1) a Shipit deployment configured for multiple GitHub organizations/Apps (a documented, supported configuration), (2) the attacker being the legitimate owner/administrator of at least one onboarded organization (and therefore of its `webhook_secret`, which is not a privilege over the victim), and (3) the victim stack having `continuous_deployment: true`. Given multi-tenant Shipit deployments are an explicitly supported configuration pattern, and continuous deployment is a common feature, this is a realistic, low-effort attack once the preconditions are met — the attacker needs no access to the victim's secrets, tokens, or repository at all.

### Recommendation
Bind the signature-verification context to the same identity used for stack resolution. Concretely, `WebhooksController` (or `Handler#stacks`) should verify that `repository.full_name`'s owner segment matches the `repository_owner`/`organization.login` used to select the verifying `GitHubApp`, and reject the webhook (422) if they diverge. Alternatively, derive both the verification key and the acted-upon repository from a single, consistently-parsed field.

### Proof of Concept
1. Shipit instance is configured with two GitHub organizations, `org-a` (attacker-controlled, secret `S_A` known to attacker) and `victim-org` (secret `S_B`, unknown to attacker), each with an onboarded stack.
2. `victim-org/victim-repo` has a Shipit stack with `continuous_deployment: true` and an undeployed commit at HEAD.
3. Attacker crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "<victim-repo HEAD sha>",
     "state": "success",
     "context": "ci/fake",
     "repository": { "owner": { "login": "org-a" }, "full_name": "victim-org/victim-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, body)` using their own known `webhook_secret` for `org-a`.
5. POST to `/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`), verifies the HMAC successfully using `S_A`, and passes.
7. `StatusHandler` resolves stacks via `repository.full_name = "victim-org/victim-repo"`, creates a `success` `Status` on the victim's commit, which — because `continuous_deployment` is enabled — triggers an unauthorized `Deploy` on `victim-org/victim-repo`.

Note: I was unable to directly view the full contents of `app/models/shipit/webhooks/handlers/status_handler.rb` due to index limitations, but its inheritance from `Shipit::Webhooks::Handlers::Handler` (which defines `stacks`/`repository_name`) and the `Status` model's `after_create`/`after_commit` callbacks together establish the exploit chain described above. A Devin session with full repository access could confirm the exact parameter requirements of `StatusHandler#process`.
