### Title
Stack-scoped ApiClient token authorizes only one stack, but CCMenuController's `stack` lookup touches any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuController` overrides the base `stack` accessor and resolves the target stack with `Stack.from_param!(params[:stack_id])`, bypassing the scoping logic in `Api::BaseController#stacks`/`#stack` that restricts a stack-bound `ApiClient` to `Stack.where(id: current_api_client.stack_id)`. This breaks the equality that should hold for every other API endpoint: `stack a token authorizes == stack the endpoint touches`. For CCMenu it becomes `stack a token authorizes != stack the endpoint touches`.

### Finding Description
Every other controller inheriting from `Api::BaseController` resolves the target stack through the inherited `stack`/`stacks` methods:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

This is the mechanism that enforces the one-stack scope of an `ApiClient` that was created with a specific `stack_id` (e.g. `belongs_to :stack, optional: true` on `ApiClient`) [4](#0-3) .

`CCMenuController`, however, defines its own `stack` method that ignores the scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

The only authorization check performed is `require_permission :read, :stack` [6](#0-5) , which only validates that the string permission `read:stack` is present in `current_api_client.permissions` via `ApiClient#check_permissions!` [7](#0-6) . It never checks that `params[:stack_id]` matches `current_api_client.stack_id`.

Such a stack-scoped, `read:stack`-only token is exactly what `CCMenuUrlController#client` self-issues for any logged-in Shipit user, intentionally scoped to a single stack:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
``` [8](#0-7) 

An attacker holding a token minted for stack A (via `/stacks/:stack_id/ccmenu_url`, or any other narrowly-scoped `read:stack` client) can call `GET /api/stacks/:other_stack_id/ccmenu.xml` with `?token=<their token>` and the request succeeds, returning the CCMenu status/build data for stack B rather than being rejected for stack scope mismatch.

### Impact Explanation
This is an authorization boundary bypass for the "a stack a token authorises versus a stack it touches" binding: a token deliberately restricted to one stack can be used to read build/deploy status (`stack.deploys_and_rollbacks.last`) of any other stack in the Shipit instance, which corresponds to unauthorized read of stack state/deploy output across stack boundaries.

### Likelihood Explanation
Any authenticated Shipit user can self-issue a stack-scoped CCMenu token via `CCMenuUrlController#fetch` without any elevated privilege, so obtaining a "restricted" credential is trivial; exploiting the bypass then only requires changing the `stack_id` route parameter in the CCMenu API request.

### Proof of Concept
1. As any authenticated Shipit user with access to stack A, call `GET /stacks/A_owner/A_repo/A_env/ccmenu_url` to obtain `{ ccmenu_url: ".../api/stacks/<A_id>/ccmenu.xml?token=<TOKEN>" }` (client created scoped to stack A, permission `read:stack` only) — see `CCMenuUrlController#client`/`#fetch` [9](#0-8) .
2. Send `GET /api/stacks/<B_id>/ccmenu.xml?token=<TOKEN>` where `B_id` is any other stack the caller does not own the CCMenu token for.
3. `Api::BaseController#authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])` [10](#0-9) , `require_permission :read, :stack` passes because the token has `read:stack`, and `CCMenuController#stack` resolves stack B directly with `Stack.from_param!(params[:stack_id])`, returning stack B's CCMenu XML despite the token only being intended for stack A.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it via the inherited `stacks` scope) so that stack-scoped tokens are enforced the same way as in every other `Api::BaseController` subclass:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
