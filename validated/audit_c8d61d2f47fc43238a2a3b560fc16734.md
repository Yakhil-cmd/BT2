### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` cascades through `Commit#blocked?` to unblock an entire victim backlog - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no check that the commit's stack/repository matches the repository that sent the webhook, unlike every sibling handler (`CheckSuiteHandler`, the `PullRequest::*Handler`s) which all scope through `Repository.from_github_repo_name(repository_name)`/`stacks`. Combined with `Commit#blocked?` walking the whole undeployed range for the *blocking* status, a single forged/misdirected `success` status write on one commit can flip `blocked?` to `false` for every subsequent queued commit in that stack, unblocking a batch deploy.

### Finding Description
The broken binding: `payload['repository']['full_name']` (the repository that emitted the webhook, verified only at the *organization* level) must equal `commit.stack.repository.full_name` for every `Commit` mutated by the handler - it does not.

- Webhook authenticity is checked once, per-organization, in `WebhooksController#verify_signature`: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) . This proves the payload came from GitHub for *some* repo belonging to that organization/App installation - it says nothing about *which* repository within that org sent it.
- Every other handler re-derives and re-scopes by repository from the payload itself, e.g. `Handler#stacks` calls `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) , and `CheckSuiteHandler#process` uses `stacks.where(branch: ...)` before touching any commit [3](#0-2) .
- `StatusHandler#process`, however, does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3)  - it never calls `stacks`/`Repository.from_github_repo_name`, so it never checks that the emitting repository matches the commit's own `stack.repository`.
- `create_status_from_github!` writes the status using the commit's own `stack_id`, not the webhook's repository [5](#0-4)  and `Status.replicate_from_github!` [6](#0-5) .
- `Commit#blocked?` scans the *whole* undeployed range for a blocking status, not just the mutated commit: `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)` [7](#0-6) , and `Status::Common#blocking?` is `!success? && commit.blocking_statuses.include?(context)` [8](#0-7) . Flipping the blocking commit's status to `success` therefore flips `blocked?` for every later queued commit in one shot, matching existing test behavior for the analogous manual-mutation case (`soc_second`/`soc_third` fixtures) [9](#0-8) .
- `Status#schedule_continuous_delivery` fires after every status create [10](#0-9) , so the newly-unblocked backlog is picked up automatically.

Exploit precondition: the attacker must control (push/status-write access to) *some* repository whose owning GitHub organization already has Shipit's GitHub App/webhook installed (this is required simply to get a validly-HMAC-signed status webhook accepted at all - `verify_signature` rejects unknown organizations). Given that, the attacker sends (or triggers via CI in their own repo) a GitHub `status` webhook whose `sha` field is set to the SHA of the victim commit belonging to a *different* stack/repository in the same organization. Because the signature check is organization-wide and `StatusHandler` performs no per-repository scoping, Shipit accepts the write and applies it to the victim's `Commit`/`Stack`, regardless of which repository actually authenticated the request.

None of the listed guards stop this: `verify_signature` authenticates the org, not the specific repository [1](#0-0) ; `drop_unhandled_event`/`ExplicitParameters` only validate shape, not ownership; there is no `require_permission!`/`stacks` scope check inside `StatusHandler` as there is in the other handlers.

### Impact Explanation
A repository that did not authenticate for the victim's stack can write a `Status` record onto the victim's `Commit`, and via `Commit#blocked?`'s range scan this single write can flip `deployable?`/`blocked?` for an entire backlog of downstream commits in the victim stack, after which `schedule_continuous_delivery` triggers an unauthorized deploy of that batch. This matches the "payload for one repository mutating another's stack, commit... / an unauthorized deploy" Critical category. Blast radius: repeatable against any stack in the same GitHub organization/App installation whose commit SHAs the attacker can learn (trivially, since commit SHAs are visible via the GitHub UI/API for any repo the attacker can read), not limited to a single mutated row.

### Likelihood Explanation
Requires the attacker to have write/status access to at least one repository within an organization that already has Shipit's GitHub App installed - this is a real but non-trivial precondition (does not require Shipit credentials, sessions, or `Shipit.github_teams` membership, only ordinary GitHub write access to some repo in the org). Given that, forging the cross-repo status is a single unauthenticated-at-the-Shipit-level API/webhook call with a known target SHA, cheap and repeatable against every stack sharing that organization/App installation.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the emitting repository the same way `CheckSuiteHandler` and the `PullRequest` handlers do: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` and only update commits belonging to those stacks (e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or a `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { ... })`), instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
test "status webhook for repo A cannot mutate a Commit belonging to repo B's stack" do
  victim_stack = shipit_stacks(:shipit) # repository X
  blocking_commit = shipit_commits(:soc_second) # belongs to victim_stack, currently blocking
  downstream_commit = shipit_commits(:soc_third) # queued behind it

  other_repo_payload = {
    'sha' => blocking_commit.sha,
    'state' => 'success',
    'context' => blocking_commit.blocking_statuses.first,
    'repository' => { 'full_name' => 'some-other-org/unrelated-repo' }
  }

  assert_changes -> { downstream_commit.reload.blocked? }, from: true, to: false do
    Shipit::Webhooks::Handlers::StatusHandler.call(
      ExplicitParameters::Parameters.define { }.parse!(other_repo_payload)
    )
  end
end
```
This demonstrates that a status payload declaring an unrelated repository as sender still mutates the victim commit and flips `blocked?`/`deployable?` for the downstream commit, because `StatusHandler` never checks `payload['repository']['full_name']` against the target stack's repository.
