### Title
Webhook signature check authenticates a GitHub organization, but event handlers act on an unrelated, unauthenticated repository/commit field — allowing cross-repository forged CI statuses and syncs - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` derives the organization to authenticate from `repository.owner.login`/`organization.login` and validates the HMAC signature using that organization's `webhook_secret`. However, `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization — a state explicitly supported by this engine's own config (`config/secrets.development.shopify.yml` shows `webhook_secret: # nil` as a valid per-org setting). Once past this check, the actual mutation targets used by handlers are taken from **different, uncorrelated payload fields**: `Handler#repository_name` reads `payload.dig('repository','full_name')` and `StatusHandler#process` queries `Commit.where(sha: params.sha)` **globally, with no repository scoping at all**. Nothing binds "the organization whose secret was (or wasn't) checked" to "the repository/commit actually written."

### Finding Description
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`):
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
If the configured organization has no `webhook_secret`, every payload claiming that `repository.owner.login` passes verification with **no cryptographic check whatsoever**. This is not a hypothetical misconfiguration — the shipped `config/secrets.development.shopify.yml` documents multiple orgs with `webhook_secret: # nil` as a legitimate configuration shape for multi-org Shipit deployments.
- After this "authentication," handlers determine *what to write* using fields never bound to `repository.owner.login`:
  - `Handler#stacks`/`#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) resolves the target via `payload.dig('repository', 'full_name')`.
  - `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) is worse still: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` — this is a **global, unscoped** lookup across every stack/repository tracked by the Shipit instance, keyed only by a commit SHA supplied in the request body.
- Equality that should hold but doesn't: `authenticated_organization == organization_owning(written_repository_or_commit)`. Before the PR/fix, this equality is never enforced; the org used to pick (or skip) signature verification is disjoint from the org/repo whose `Commit`/`Stack` records get mutated.

### Impact Explanation
Any unauthenticated external actor who can reach the public `POST /webhooks` route (`resources :webhooks, only: :create` in `config/routes.rb:14`, mounted with no `force_github_authentication`) can:
1. Discover (via response code: `422` vs `200/204`) which configured organization in a multi-org Shipit instance has no `webhook_secret`.
2. Submit a `status` event payload with `repository.owner.login` set to that unprotected organization and an arbitrary `sha` belonging to a commit in a **completely different, properly-configured** tracked repository/stack.
3. Because `StatusHandler` matches commits globally by SHA with no relation to the authenticated organization, `Commit#create_status_from_github!` will create a forged status (e.g., `state: "success"` for a required CI context) directly from attacker-supplied payload fields.
4. A forged "success" status can satisfy `Commit#deployable?` (`app/models/shipit/commit.rb`) / required CI checks, enabling an unauthorized deploy to proceed (manually or via continuous delivery) on a commit that never actually passed CI — a direct "unauthorized deploy" impact.

Push events are similarly exposed via `Handler#repository_name` using `repository.full_name` (unbound to the authenticated org), which can trigger `stack.sync_github` for a stack the attacker does not own, though the status-forging path is the more direct and severe primitive since it writes fabricated CI state with no GitHub API round-trip validation at all.

### Likelihood Explanation
Requires no privileged credentials, no repository write access, no Shipit session, and no leaked secrets — only that the multi-org Shipit deployment has at least one configured organization without a `webhook_secret`, a configuration explicitly modeled in this codebase's own sample secrets file. Given the webhook endpoint is intentionally public and unauthenticated by design (it exists to receive GitHub's webhooks), and the oracle to detect an unprotected org is trivial (HTTP status code), likelihood is realistic wherever such multi-tenant configurations exist.

### Recommendation
- Do not let `verify_webhook_signature` return `true` when `webhook_secret` is blank; treat a missing secret as "verification impossible" and reject (or require secrets to be mandatory per configured organization).
- Bind the authenticated organization to the object being mutated: after signature verification, require that the repository resolved from the payload (`repository.full_name`) belongs to the same organization used for `repository_owner`/secret lookup, and reject otherwise.
- In `StatusHandler` (and any other handler doing unscoped lookups), scope `Commit` lookups by the repository/organization derived from the verified payload rather than matching by SHA alone across the entire installation.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `victim-org` (with a real `webhook_secret`) and `test-org` (with `webhook_secret: nil`, as shown as a valid shape in `config/secrets.development.shopify.yml`).
2. `victim-org/repo` has a tracked `Stack` with commit `abc123...` requiring CI context `ci/tests`, currently pending.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature`, and body:
```json
{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/tests",
  "description": "forged",
  "repository": { "owner": { "login": "test-org" }, "full_name": "test-org/whatever" }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "test-org")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of signature validity.
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")` — finds the victim's commit in `victim-org/repo` (unrelated to `test-org`) and calls `create_status_from_github!`, writing a forged `success` status for `ci/tests` sourced entirely from attacker-controlled JSON, with no GitHub API confirmation.
6. The victim commit is now marked deployable/CI-green despite no legitimate signature covering `victim-org`'s actual secret, enabling an unauthorized deploy trigger. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
