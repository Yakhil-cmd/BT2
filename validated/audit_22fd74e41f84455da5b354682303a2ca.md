## Finding: Confirmed

Looking at `TransactionAuthenticator::verify()` for the `FeePayer` variant in `types/src/transaction/authenticator.rs`, the length relationship between `secondary_signer_addresses` and `secondary_signers` is never checked before the signatures are verified. [1](#0-0) 

### Title
`FeePayer` authenticator `verify()` never asserts `secondary_signer_addresses.len() == secondary_signers.len()`, letting an address be bound into the signed message without any authenticator validating it - (File: `types/src/transaction/authenticator.rs`)

### Summary
`TransactionAuthenticator::verify()` builds its `to_verify` list purely from `sender` and the elements of `secondary_signers`, and separately clones `secondary_signer_addresses` into the `RawTransactionWithData::new_fee_payer` message used to reconstruct the signing hash. [2](#0-1)  There is no assertion anywhere in this function (nor in `MultiAgent`'s branch) that `secondary_signer_addresses.len() == secondary_signers.len()`.

### Finding Description
For `FeePayer`, `to_verify` is seeded with `sender` and then extended by iterating `secondary_signers` only: [3](#0-2) . The signing message (`no_fee_payer_address_message` / `fee_payer_address_message`) is built from `secondary_signer_addresses.clone()` independently of how many authenticators actually exist: [4](#0-3) . Each entry in `to_verify`/`remaining` is checked with `verifier.verify(&message)`, which only confirms that the given `AccountAuthenticator`'s signature matches the message hash — it does not confirm a 1:1 correspondence between every declared secondary address and a provided authenticator. Consequently, an authenticator with 2 `secondary_signer_addresses` but only 1 `secondary_signers` entry passes `verify()` as long as `sender`, the single provided secondary authenticator, and `fee_payer_signer` produce valid signatures over the constructed message (which happens to embed both addresses as data, not as a per-address proof requirement).

Separately, the codebase does show that this invariant is understood to matter: `all_signer_auth_keys()` explicitly checks `secondary_addresses.len() != secondary_auths.len()` and returns `None` if mismatched. [5](#0-4)  This function's existence suggests the length invariant is assumed to hold by the time execution proceeds, but `verify()` itself does not enforce it.

### Impact Explanation
If no downstream layer (VM prologue / `transaction_validation.move` account-authentication logic, mempool, or vm-validator) independently re-validates that `secondary_signer_addresses.len() == secondary_signers.len()` before treating each address as an authenticated participant, a sponsored multi-agent transaction could be admitted with a secondary account address bound into the transaction hash (and thus into any downstream logic that reads `secondary_signer_addresses`) without any signature ever being checked against that address's actual authentication key. This corrupts the secondary-signer invariant that every address in `secondary_signer_addresses` corresponds to a verified `AccountAuthenticator`.

### Likelihood Explanation
This requires only unprivileged, self-crafted transaction construction (no leaked keys or pre-existing approvals) — an attacker who controls `sender` and one secondary signer's key can freely omit an authenticator for a second declared secondary address while `verify()` in this file raises no error.

### Recommendation
Add an explicit length check at the top of the `FeePayer` and `MultiAgent` branches of `verify()`:
```rust
ensure!(
    secondary_signer_addresses.len() == secondary_signers.len(),
    "Number of secondary signer addresses does not match number of secondary signers"
);
```
This mirrors the check already performed in `all_signer_auth_keys()` and closes the gap at the authenticator layer itself rather than relying solely on downstream VM/prologue checks (which I was not able to verify perform this cross-check, given the scope of this review was limited to `authenticator.rs`).

### Proof of Concept
Construct:
```rust
let auth = TransactionAuthenticator::fee_payer(
    sender_authenticator,               // valid Ed25519 AccountAuthenticator for `sender`
    vec![addr_a, addr_b],                // 2 secondary_signer_addresses
    vec![secondary_authenticator],       // only 1 secondary_signers entry
    fee_payer_address,
    fee_payer_authenticator,
);
assert!(auth.verify(&raw_txn).is_ok()); // succeeds despite the 2-vs-1 mismatch
```
As shown at [6](#0-5) , `verify()` never inspects `secondary_signer_addresses.len()` against `secondary_signers.len()`, so as long as `sender`, the lone secondary signer, and `fee_payer_signer` produce valid signatures over the message that embeds both `addr_a` and `addr_b`, `verify()` returns `Ok(())`.

**Caveat / scope limitation:** I was only able to confirm this gap inside `types/src/transaction/authenticator.rs` in the time available. I could not, within this session, inspect the VM prologue / `transaction_validation.move` account-authentication logic or `vm-validator`/mempool admission code to confirm whether they independently re-validate the address/authenticator length correspondence before execution. If such a downstream check exists and runs before any state-affecting logic reads `secondary_signer_addresses`, the practical admission impact would be mitigated to defense-in-depth rather than a full admission bypass. Recommend a Devin session with full repo access to trace this further if that distinction needs to be resolved definitively.

            Self::FeePayer {
                sender,
                secondary_signer_addresses,
                secondary_signers,
                fee_payer_address,
                fee_payer_signer,
            } => {
                // In the fee payer model, the fee payer address can be optionally signed. We
                // realized when we designed the fee payer model, that we made it too restrictive
                // by requiring the signature over the fee payer address. So now we need to live in
                // a world where we support a multitude of different solutions. The modern approach
                // assumes that some may sign over the address and others will sign over the zero
                // address, so we verify both and only fail if the signature fails for either of
                // them. The legacy approach is to assume the address of the fee payer is signed
                // over.
                let mut to_verify = vec![sender];
                let _ = secondary_signers
                    .iter()
                    .map(|signer| to_verify.push(signer))
                    .collect::<Vec<_>>();

                let no_fee_payer_address_message = RawTransactionWithData::new_fee_payer(
                    raw_txn_for_signing.clone().into_owned(),
                    secondary_signer_addresses.clone(),
                    AccountAddress::ZERO,
                );

                let mut remaining = to_verify
                    .iter()
                    .filter(|verifier| verifier.verify(&no_fee_payer_address_message).is_err())
                    .collect::<Vec<_>>();

                remaining.push(&fee_payer_signer);

                let fee_payer_address_message = RawTransactionWithData::new_fee_payer(
                    raw_txn_for_signing.into_owned(),
                    secondary_signer_addresses.clone(),
                    *fee_payer_address,
                );

                for verifier in remaining {
                    verifier.verify(&fee_payer_address_message)?;
                }

                Ok(())
            },
