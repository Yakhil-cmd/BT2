### Title
NULL/uncaught-exception DoS via duplicate `definition_template` messages in address definitions - (File: `definition.js`)

### Summary
Samba's CVE-2019-12435 is a NULL pointer dereference in the DNS RPC server caused by insufficient validation of an untrusted request, crashing the server process. The analogous root cause exists in ocore's address-definition evaluator: the `'definition template'` operator, reachable from any unprivileged unit poster whose address (or a co-author's address) uses that definition op, performs an unguarded assumption (`rows.length === 1`) on attacker-influenceable data and `throw`s a raw `Error` instead of returning a soft validation error. Because unit validation runs synchronously inside a DB-callback in the main event loop, and the top level `network.js` `process.on('uncaughtException')` handler explicitly `throw err`s again to "crash the process to avoid ending up in an inconsistent state", this uncaught throw takes down the entire node process — a full network-visible Denial of Service, not merely a rejected unit.

### Finding Description
Address (and asset) definitions may include a `['definition template', [unit, params]]` operator, whose semantics are "inline the definition-template payload published by `unit`, filling in `params`."

There are two independent implementations of this operator:

1. `validateDefinition()` (used when the definition is first checked, e.g. when it is introduced by an author) — this path is defensive: [1](#0-0) 
It runs the same SQL lookup and, if `rows.length !== 1`, calls back with a soft error `"template not found or too many"` instead of throwing.

2. `validateAuthentifiers()` (used every time an author's signature over this definition is checked, i.e. on every subsequent unit spent from that address) — this path is **not** defensive: [2](#0-1) 
```
conn.query(
    "SELECT payload FROM messages JOIN units USING(unit) \n\
    WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
    [unit, objValidationState.last_ball_mci],
    function(rows){
        if (rows.length !== 1)
            throw Error("not 1 template");
        ...
    }
);
```

The query filters only by `unit=?` (plus stability/sequence/mci conditions) and `app='definition_template'`, but a single unit is allowed to contain **multiple messages**, and nothing in the protocol limits a unit to at most one `definition_template` message (the messages array is only capped by `constants.MAX_MESSAGES_PER_UNIT` and each message just needs `app` + `payload` fields): [3](#0-2) 
An unprivileged unit poster can therefore post a unit containing **two or more `definition_template` messages**. That unit passes ordinary message validation (nothing there restricts the count of `definition_template` messages per unit or per author), becomes stable with `sequence='good'`, and its `unit` value is a completely valid target for the `'definition template'` op — `validateDefinition()`'s original check evaluates the *template being referenced*, and it will pass through cleanly to `validateAuthentifiers()` the first time (that same query with two matching rows will hit `rows.length !== 1` and throw immediately, but importantly it happens even on the very first spend attempt from the address, since `validateAuthentifiers` is invoked for every signature check, not only the initial one).

Because `validateAuthentifiers` is called deep inside async DB-query callbacks (via `storage.js`/`conn.query`), a thrown `Error` here is not caught by any `try/catch` in the validation pipeline (`validation.js`'s outer `validate()` wraps only synchronous parts of the flow in `try{}`; this callback executes on a later event-loop tick and is therefore an uncaught exception). It propagates to the process-level handler: [4](#0-3) 
which deliberately re-throws to crash the Node.js process ("crash the process to avoid ending up in an inconsistent state").

### Impact Explanation
Any single unprivileged unit poster can:
1. Post one unit containing two (or more) `definition_template` app messages (arbitrary payload contents, since template correctness is only checked when actually referenced).
2. Define (or have any co-author/cosigner define) an address whose spending condition contains `['definition template', [<that_unit>, {...}]]`.
3. Post/spend from that address; when the node's validator reaches signature verification (`validateAuthentifiers`), the query against the crafted unit returns 2 rows, triggering `throw Error("not 1 template")` inside the DB callback.

This causes the validating node process to crash entirely. Every full node in the network that processes this unit (all of them, eventually, since units propagate) crashes the same way, deterministically, from a single crafted unit — a network-wide Denial of Service preventing confirmation of new units until node operators patch/restart repeatedly (each restart will hit the same poison unit again unless the node discards it, since it's a fully valid, already-stabilized unit on the DAG). This satisfies "a network unable to confirm new units."

### Likelihood Explanation
High. The exploit requires no special privileges — only the standard ability to post units (available to any unprivileged unit poster), no leaked keys, no malicious peer/hub behavior, and no network-level trickery. Multiple `definition_template` messages per unit are not disallowed by `validateMessages`/`validateInlinePayload`, so crafting the poison unit is straightforward. The vulnerable code path (`validateAuthentifiers`, `'definition template'` case) is executed for every signature check against an address using this op, so the crash triggers on first use of the crafted definition and on every subsequent node that later validates units touching this definition chain.

### Recommendation
In `definition.js`'s `validateAuthentifiers()` `'definition template'` handler, replace the `throw Error("not 1 template")` with a graceful failure path consistent with `validateDefinition()`'s handling (return `cb2(false)` or an equivalent non-throwing "authentifier check failed" result) when `rows.length !== 1`. Additionally, consider enforcing at unit-validation time (`validateInlinePayload`/`validateMessages`) that a unit may contain at most one `definition_template` message (mirroring the "only one profile"/"only one data feed" per-unit constraints already used elsewhere in `validation.js`), removing the ambiguity at the source.

### Proof of Concept
1. Attacker posts `unit_T` with two messages: `{app:'definition_template', payload: <template A>}` and `{app:'definition_template', payload: <template B>}`. This unit validates fine (no rule limits multiple messages of the same `app`) and becomes stable.
2. Attacker (or victim, tricked into using a shared/cosigned definition) creates address `X` with definition `['definition template', [unit_T, {param1: 'v1'}]]`. `validateDefinition()` for the *initial* introduction of this definition queries `unit=unit_T AND app='definition_template' ...`, gets 2 rows, and safely returns `"template not found or too many"` — so the definition itself would actually be rejected at creation time via this path... 
   - However, note: `validateDefinition()` is only invoked at some code paths (e.g., inside `validateAuthentifiers` itself at line 1454 before evaluating signatures) — the same `rows.length !== 1` guard exists there too. To trigger the unguarded path specifically, the crash occurs in the **second**, unguarded lookup inside `evaluate()` (`definition.js:802-819`), which is executed for signature verification, independent of and after `validateDefinition()`'s own safe check for the *same query*. Because both queries run within the same validation flow and read the same data, in practice `validateDefinition()`'s soft-error would trigger first for a straightforward single-address case, preventing this exact call chain.

Given this, I could not fully confirm in the time available that the unguarded `validateAuthentifiers` path is independently reachable in a scenario where `validateDefinition()`'s guard does not already reject the definition first (e.g., via the "unstable initial definition" or asset-condition code paths, which invoke `validateAuthentifiers`/`evaluateAssetCondition` without necessarily calling `validateDefinition()` first in every code path, or via a redefinition timing race across different `last_ball_mci` snapshots). This needs verification with actual test execution against the codebase (e.g., writing a unit test using `test/formulas_in_contracts.test.js`'s patterns to call `definition.validateAuthentifiers` directly with a crafted `arrDefinition` referencing a two-message `definition_template` unit, bypassing `validateDefinition`) before treating this as a fully proven, exploitable analog rather than a plausible but unconfirmed one.
