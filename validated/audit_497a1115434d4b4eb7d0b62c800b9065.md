### Title
CCMenu API endpoint bypasses `ApiClient` stack-scoping, allowing a stack-scoped token to read deploy status of arbitrary stacks - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The binding that should hold is: `stack an ApiClient authorises == stack the endpoint touches`. `Shipit::Api::CCMenuController` breaks this equality because its `#stack` method resolves the target `Stack` directly from `params[:stack_id]` via `Stack.from_param!`, instead of going through the stack-scoped lookup (`stacks.from_param!`) used everywhere else in the API. An `ApiClient` restricted to one stack (`stack_id` set, e.g. fixture `here_come_the_walrus`) can therefore fetch CCMenu deploy-status XML for any other stack in the installation, even though `require_permission :read, :stack` only checks the permission bit, not the stack scope.

### Finding Description
`Shipit::Api::BaseController` implements scoping centrally: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to a stack, and the generic `stack` helper does `stacks.from_param!(params[:stack_id])`, so any attempt to look up a stack outside the client's authorised scope raises `ActiveRecord::RecordNotFound`.

`Shipit::Api::CCMenuController`, however, overrides `stack` and bypasses this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model — not through `stacks` — and only requires the generic `read:stack` permission via `require_permission :read, :stack` declared at the top of the controller: [3](#0-2) 

`ApiClient#check_permissions!` only checks that the permission string `read:stack` is present in the client's `permissions` array; it has no notion of which specific stack that permission applies to: [4](#0-3) 

The narrowing to a single stack is supposed to come entirely from `stack_id` on the `ApiClient` record (as seen in the `here_come_the_walrus` fixture, which is scoped to the `shipit` stack) combined with the `stacks` scoping helper in `BaseController`. Because `CCMenuController#stack` skips `stacks` and queries `Stack` unscoped, that per-token restriction is silently dropped for this one endpoint.

Additionally, this controller supports authenticating via a bare `?token=` query parameter (as intended, for CCMenu/CI-dashboard integrations that can't set an `Authorization` header): [5](#0-4) 

which is exactly the credential minted and handed out by `CCMenuUrlController` for a stack-scoped client: [6](#0-5) 

So a token that a repository owner would reasonably believe only exposes CCMenu status for *their* stack in fact exposes CCMenu status (deploy id, deploy state/output link, running status) for every stack in the Shipit installation, simply by changing `stack_id` in the URL.

### Impact Explanation
This is an unauthenticated-relative-to-scope read of stack/deploy state: a credential that is only supposed to authorize reading one stack's status can be used to read the deploy status of any stack. This matches the High-severity category "unauthenticated read of stack state, task streams or deploy output" — the attacker (holder of one CCMenu token) can enumerate/observe deploy activity (running/success/failure, deploy id, deploy timestamps) of stacks they were never granted access to, across repositories/organizations hosted by the same Shipit instance.

### Likelihood Explanation
Exploitation requires only possession of any valid stack-scoped `ApiClient` token that has `read:stack` permission (a common, low-privilege permission handed out for CI dashboard integrations via `CCMenuUrlController`) and knowledge/guessing of another stack's `to_param` (`owner/repo/environment`), which is often predictable or discoverable (e.g., via the public stacks list UI). No signature forgery or credential theft is needed — it's a straightforward scope-check omission in one controller, so likelihood is high for anyone already holding a low-privilege token.

### Recommendation
Make `CCMenuController#stack` go through the same stack-scoping as the rest of the API:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it reuses `BaseController#stacks`, which already restricts lookups to `current_api_client.stack_id` when the client is scoped. Add a regression test asserting that a stack-scoped `ApiClient` token receives a 404 (not the CCMenu XML) when requesting `stack_id` values outside its `stack_id`.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to a single stack with `read:stack` permission only, e.g. fixture `here_come_the_walrus` (`stack: shipit`, `permissions: [read:stack]`), and derive its CCMenu token via `authentication_token`/`CCMenuUrlController#fetch`.
2. Issue: `GET /api/<other_owner>/<other_repo>/<other_environment>/cc.xml?token=<the_scoped_token>` for a *different* stack than the one the client is scoped to.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `BaseController#stacks`' `current_api_client.stack_id` restriction), the request succeeds with `200 OK` and returns the CCMenu XML (deploy id, status, timestamp) for the unauthorized stack, whereas the equivalent request through any other API controller (e.g. `Api::StacksController#show`) using `stacks.from_param!` would raise `ActiveRecord::RecordNotFound` for a stack outside the client's scope.
