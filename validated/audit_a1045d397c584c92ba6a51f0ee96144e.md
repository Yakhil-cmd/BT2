### Title
`StatusHandler` updates commits and fires `deployable_status`/`commit_status` hooks for any stack sharing a commit SHA, without verifying the SHA belongs to the webhook's authenticated repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)`, with no filter on the repository that sent the webhook, unlike the base `Handler#stacks` helper which scopes lookups via `Repository.from_github_repo_name(repository_name)`. Since git SHAs are content-addressed and identical across forks/mirrors/cherry-picks, a correctly-signed status webhook from repository B can update a `Commit` belonging to an unrelated stack A and cause `Commit#add_status` to call `Hook.emit(:deployable_status, stack, ...)` with `stack == stack A`, even though repository B - not A - authenticated the request.

### Finding Description
Binding claimed: `stack` argument passed to `Hook.emit` in `Commit#add_status` == the repository that authenticated the inbound webhook causing the emit.

Trace:
- `WebhooksController#verify_signature` validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is derived from the *inbound* payload's `repository.owner.login` [1](#0-0) [2](#0-1) . This only proves the payload came from a GitHub org/App registered with Shipit - it does not bind the payload to any specific target `Stack`.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This query is **not scoped by repository at all**. Compare with the base `Handler` class, which defines a `stacks` helper explicitly scoped by `repository_name` from the payload [4](#0-3)  - `StatusHandler` never uses this helper.
- `create_status_from_github!` calls `add_status`, which reads `stack` via the `Commit`'s own `belongs_to :stack` association (the commit's real owning stack) [5](#0-4) , and then fires:
```ruby
Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
``` [6](#0-5) 

Root cause: because SHA values are content hashes, the identical SHA can legitimately exist as a `Commit` record under multiple unrelated `Stack`s (forks, mirrors, cherry-picked/identical patches applied to multiple repos tracked by Shipit). A validly-signed status webhook from repository B, whose payload never names stack A's repository, will still match and mutate stack A's `Commit` row via the unscoped `Commit.where(sha:)`, causing `Hook.emit(:deployable_status, stack_a, ...)` to fire for stack A's webhook subscribers, driven entirely by repository B's CI signal.

Existing guards do not stop this: `verify_signature` only authenticates that the payload came from a known GitHub org/App - it says nothing about which `Stack`/`Commit` may be touched; the `ExplicitParameters` schema only validates payload shape, not repository scope; there is no `require_permission!`/`stacks` filter applied in `StatusHandler`.

### Impact Explanation
An attacker who controls a repository (e.g., a fork registered under a GitHub org/App known to Shipit) can cause an unrelated `Stack`'s commit-status/`deployable_status` records and outbound webhooks to be mutated based on a CI signal that repository never authenticated. This matches the "payload for one repository mutating another's stack, commit" Critical criterion: it causes DB records (`Status`, `Commit#deployed?`-adjacent state) to be written for a repository/stack that did not authenticate the event, outbound `Hook`s (deployable_status/commit_status) to fire misleadingly for tenant A based on tenant B's data, and can trigger `stack.schedule_merges` and continuous-delivery scheduling (`schedule_continuous_delivery`) for stack A based on repo B's status [7](#0-6) . This is repeatable against any stack whose repository shares a commit SHA with an attacker-controlled repo.

### Likelihood Explanation
Requires: (1) the attacker's repository is within a GitHub org/App configuration known to Shipit (otherwise `verify_signature` rejects with `GithubOrganizationUnknown`); (2) a SHA collision (in the ordinary git sense, i.e. identical commit object) between the attacker's repo and the target stack's repo, which commonly occurs via forks, mirrors, or shared upstream history. Given those preconditions, the attacker only needs to trigger (or fake via their own CI/status API call) a `status` event on their own repository for a commit SHA also tracked in the target stack - no Shipit session, token, or secret is needed beyond what any repository owner in the same GitHub org already legitimately has.

### Recommendation
Scope `StatusHandler#process` (and any other SHA-keyed handler, e.g. `CheckRunHandler`) to only touch commits whose `stack.repository` matches the payload's `repository.full_name`, mirroring the `Handler#stacks`/`Repository.from_github_repo_name` pattern already used elsewhere, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
  test "status webhook for repo B updates and emits hooks for unrelated stack A sharing the same sha" do
    stack_a = shipit_stacks(:shipit)
    commit_a = stack_a.commits.create!(sha: "deadbeef" * 5, message: "shared commit")

    received = []
    Hook.plug(:deployable_status, stack_a) { |payload| received << payload }

    payload = {
      "sha" => commit_a.sha,
      "state" => "success",
      "context" => "ci/from-repo-b",
      "repository" => { "full_name" => "attacker/repo-b", "owner" => { "login" => "attacker" } }
    }

    Shipit::Webhooks::Handlers::StatusHandler.call(payload)

    assert_equal 1, received.size, "stack_a's hook fired despite stack_a never being named in the payload"
  end
end
```
Assertion binding: expected `stack` in `Hook.emit` == repository named in `payload["repository"]["full_name"]` ("attacker/repo-b"); actual `stack` emitted == `stack_a` (unrelated repository), proving the divergence.
