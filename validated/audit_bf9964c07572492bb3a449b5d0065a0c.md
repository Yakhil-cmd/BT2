Confirmed: `handle_stack_lockup_pox_v4` in `pox-locking/src/pox_4.rs` performs the actual STX lock immediately when `delegate-stack-stx` (or `stack-stx`) returns successfully — the lock is enacted by the node *before* `stack-aggregation-commit` is ever called. This confirms the two-step nature of pooled stacking: funds get locked at `delegate-stack-stx` time, while inclusion in the reward set requires a *separate*, later `stack-aggregation-commit` call authorized by a signer-key signature/authorization keyed only by `{signer-key, reward-cycle, topic, period, pox-addr, auth-id, max-amount}` — critically, **not** bound to `tx-sender`.

### Title
Front-runnable `auth-id`/signer-key authorization consumption in `stack-aggregation-commit` permanently denies a pool operator's PoX reward-slot registration for already-locked STX - (File: stackslib/src/chainstate/stacks/boot/pox-4.clar)

### Summary
`stack-aggregation-commit`/`stack-aggregation-commit-indexed` in pox-4.clar rely on `consume-signer-key-authorization` to validate that a signer has authorized a specific `(pox-addr, reward-cycle, topic, period, auth-id, max-amount)` tuple. The resulting `used-signer-key-authorizations` map key never includes `tx-sender`, so any account can consume a signer's authorization/signature for that exact tuple, not just the intended pool operator whose STX are already locked and waiting to be credited into the reward set.

### Finding Description
`stack-aggregation-commit` is called after `delegate-stack-stx` (or `stack-increase`/`delegate-stack-extend`) has already caused the node to lock the delegator's STX via `handle_stack_lockup_pox_v4` in [1](#0-0) , which runs as soon as `delegate-stack-stx` returns `(ok ...)` — independent of whether `stack-aggregation-commit` later succeeds. The `stacking-state` map for that stacker is set with `reward-set-indexes: (list)` and the amount is only recorded in `partial-stacked-by-cycle` keyed by `{pox-addr, sender: tx-sender, reward-cycle}` [2](#0-1) .

To actually get counted into `reward-cycle-pox-address-list`/`reward-cycle-total-stacked` for that cycle (and thus earn a reward slot), the pool operator must later submit `stack-aggregation-commit-indexed`/`stack-aggregation-commit`, which calls `consume-signer-key-authorization pox-addr reward-cycle "agg-commit" u1 signer-sig signer-key amount-ustx max-amount auth-id` [3](#0-2) .

`verify-signer-key-sig`/`consume-signer-key-authorization` validate and mark-as-used an authorization keyed only by `{signer-key, reward-cycle, topic, period, pox-addr, auth-id, max-amount}` — this key set intentionally excludes `tx-sender` [4](#0-3) . Because a `signer-sig` (a SIP-018 signature over exactly those fields, with no binding to a specific caller) is broadcast publicly in the mempool with the operator's `stack-aggregation-commit` transaction, any address that has its own outstanding `partial-stacked-by-cycle` entry for that same `pox-addr`/`reward-cycle` (trivial to obtain — anyone can call `delegate-stack-stx` toward a public pool address they don't control, since PoX addresses are just public Bitcoin scripts, not access-controlled) can copy the observed `signer-sig`/`signer-key`/`auth-id`/`max-amount` and front-run the legitimate `stack-aggregation-commit` call. The attacker's call succeeds first (verifying fine, since the signature check has no `tx-sender` binding) and inserts the authorization into `used-signer-key-authorizations`, permanently marking it consumed for that `(pox-addr, reward-cycle, auth-id, period, topic, max-amount)` tuple.

When the legitimate pool operator's original transaction then executes, `verify-signer-key-sig` finds the authorization already present in `used-signer-key-authorizations` and returns `ERR_SIGNER_AUTH_USED`, causing `stack-aggregation-commit`/`stack-aggregation-commit-indexed` to fail with `(err ERR_SIGNER_AUTH_USED)` [5](#0-4) . Since the reward cycle's PoX anchor block deadline for committing is fixed, and the compromised `auth-id` cannot be reused (its only remedy is obtaining a brand-new off-chain signature from the signer, which requires round-tripping with the signer and racing the anchor-block cutoff again), the pool operator's already-locked STX (locked at `delegate-stack-stx` time per the Rust handler above) can be permanently excluded from that reward cycle's slot — the STX remain locked for the full `lock-period` but generate no PoX reward, an equality break between "STX locked" and "STX counted toward a reward commitment."

### Impact Explanation
This breaks the equality that locked STX should correspond to a counted, reward-earning commitment: the attacker did not lock more value than the operator, yet can strip the operator's ability to register their already-locked STX into the reward set for the targeted cycle, resulting in **temporary freezing of staked funds** without a reward payout for a full lock period (STX stay locked, since `delegate-stack-stx` already triggered the lock via `pox_lock_v4`, independent of the aggregation commit succeeding). This matches the in-scope "High" impact: temporary freezing of staked funds / a stacking action (the operator's authorized aggregation-commit) blocked by an unauthorized replay of the same credential.

### Likelihood Explanation
The attack only requires: (1) observing `signer-sig`, `signer-key`, `auth-id`, `max-amount`, `pox-addr`, `reward-cycle` from the mempool-visible `stack-aggregation-commit`/`stack-aggregation-commit-indexed` call, and (2) having (or opportunistically creating) any `partial-stacked-by-cycle` entry for that same `pox-addr`/`reward-cycle` by calling `delegate-stack-stx` toward the *same public PoX address* (which requires no permission from the pool operator — any principal can be delegated-to by their own controlled account and target any Bitcoin PoX address). No privileged role, bond, or victim's private key is required; only ordinary mempool front-running capability.

### Recommendation
Bind the signer-key authorization consumption to the calling principal by including `tx-sender` (or an explicit `stacker`/`sender` field matching `partial-stacked-by-cycle`) in both the SIP-018 message hash (`get-signer-key-message-hash`) and the `used-signer-key-authorizations`/`signer-key-authorizations` map keys, so a signature/authorization can only be consumed by the account it was issued for.

### Proof of Concept
1. Operator O calls `delegate-stack-stx` for `pox-addr P`, `reward-cycle R`, locking STX (Rust `handle_stack_lockup_pox_v4` locks the STX immediately) and creating `partial-stacked-by-cycle {P, O, R}`.
2. Attacker A independently controls a delegation and calls `delegate-stack-stx` for `pox-addr P`, `reward-cycle R` too, creating their own `partial-stacked-by-cycle {P, A, R}` entry (any amount, even below threshold).
3. O obtains signer's SIP-018 signature `sig` for `(P, R, "agg-commit", 1, auth_id, max_amount)` and broadcasts `stack-aggregation-commit-indexed(P, R, sig, signer-key, max_amount, auth_id)`.
4. A observes `sig`/`signer-key`/`auth_id`/`max_amount` in the mempool and submits their own `stack-aggregation-commit-indexed(P, R, sig, signer-key, max_amount, auth_id)` with higher fee, which is mined first: `consume-signer-key-authorization` succeeds and sets `used-signer-key-authorizations {signer-key, R, "agg-commit", 1, P, auth_id, max_amount} = true`, consuming A's own (unrelated, possibly negligible) `partial-stacked-by-cycle {P, A, R}` amount into the reward set.
5. O's original transaction executes afterward; `verify-signer-key-sig` finds the authorization already used and returns `(err ERR_SIGNER_AUTH_USED)` per [5](#0-4) , so O's STX (already locked in step 1) never get registered in `reward-cycle-pox-address-list` for cycle `R` and earn no reward for that lock period, while remaining locked until natural unlock.

    );
    // applying a pox lock at this point is equivalent to evaluating a transfer

        ClarityCostFunction::StxTransfer,
        &mut global_context.cost_track,
        1,
    )?;

;;
;; - Verify that a signer key is authorized to be used
;; - Updates the `used-signer-key-authorizations` map to prevent reuse

(define-private (consume-signer-key-authorization (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                                  (reward-cycle uint)
                                                  (topic (string-ascii 14))
                                                  (period uint)
                                                  (signer-sig-opt (optional (buff 65)))
                                                  (signer-key (buff 33))
                                                  (amount uint)
                                                  (max-amount uint)
                                                  (auth-id uint))
