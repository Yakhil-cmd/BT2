## Title
Stack-scoped `write:hook` API token can create a global (`stack_id: nil`) webhook via `Api::HooksController#create` - (File: `app/controllers/shipit/api/hooks_controller.rb`)

## Summary
`Api::HooksController#hooks` derives the target `stack_id` solely from `params[:stack_id]` rather than from `current_api_client.stack_id`, so a token that is scoped to a single stack (but holds `write:hook`) can call `create` without a `stack_id` param and produce a `Hook` with `stack_id: nil` — a global hook that receives events for every stack in the installation.

## Finding Description
The broken binding is: for any `ApiClient` with a non-nil `stack_id`, every `Hook` it creates should satisfy `hook.stack_id == current_api_client.stack_id` (or be rejected). Instead: [1](#0-0) 

```ruby
def hooks
  Hook.where(stack_id:)
end

def stack_id
  stack.id if params[:stack_id].present?
end
```

`stack_id` only consults `params[:stack_id]`; it never falls back to or is constrained by `current_api_client.stack_id`. Permission enforcement is purely permission-name based and independent of stack scope: [2](#0-1) 

The stack-scoping mechanism used elsewhere in the base controller (`stacks`/`stack`) filters the queryable stack set by `current_api_client.stack_id`, but `HooksController` never routes through it for the `stack_id`-less path: [3](#0-2) 

Exploit flow: attacker holds an `ApiClient` token bound to `stack_id = X` with permission `write:hook` (a legitimate low-privilege integration token intended only to manage hooks for stack `X`). Attacker sends `POST /api/hooks` (the top-level, non-nested hooks route) with `{delivery_url:, events: [...]}}` and no `stack_id` param. `authenticate_api_client` succeeds, `require_permission :write, :hook` passes (it only checks the permission string, not stack binding), `stack_id` private method returns `nil` because `params[:stack_id]` is blank, and `hooks.create(params)` executes `Hook.where(stack_id: nil).create(params)`, persisting a `Hook` with `stack_id: nil`. Nothing in the request path re-derives or clamps this to the token's authorized stack.

## Impact Explanation
A `Hook` with `stack_id: nil` is a global hook, delivering events for all stacks/repositories in the Shipit instance — not just the one the token was scoped to. This is a cross-tenant exfiltration primitive: the attacker's `delivery_url` receives deploy/status/task events for every repository managed by the Shipit instance, not only their own. This is repeatable (each POST creates another global hook) and matches the "payload for one repository mutating another's stack" / cross-tenant data exfiltration category.

## Likelihood Explanation
Requires the attacker to already possess a valid `ApiClient` token with `write:hook` permission bound to a specific `stack_id` (a legitimately issued but narrowly-scoped integration credential) — this is a precondition stated in the question as attacker-held. Given that, the attack is a single unauthenticated-relative-to-scope HTTP POST with no other secrets or privileges needed, and it is trivially repeatable.

## Recommendation
In `Api::HooksController#hooks`/`#stack_id`, derive the effective stack scope from `current_api_client.stack_id` when present, ignoring or rejecting a client-supplied `stack_id` that doesn't match, e.g.:
```ruby
def stack_id
  if current_api_client.stack_id?
    current_api_client.stack_id
  elsif params[:stack_id].present?
    stack.id
  end
end
```
and reject creation of a hook with `stack_id: nil` (or a mismatched `stack_id`) whenever the authenticated client is stack-scoped.

## Proof of Concept
minitest plan (`test/controllers/api/hooks_controller_test.rb`, following the existing `ApiControllerTestCase` pattern):
```ruby
test "a stack-scoped write:hook client cannot create a global hook" do
  authenticate!(:here_come_the_walrus) # fixture client with stack_id set + write:hook
  assert_no_difference -> { Hook.where(stack_id: nil).count } do
    post :create, params: { delivery_url: 'https://evil.example/hook', events: ['deploy'] }
  end
  # Expect: response is not success, OR any created Hook has
  # hook.stack_id == @client.stack_id, never nil.
end
```
Assert on both sides of the binding: `@client.stack_id` (non-nil, e.g. stack `X`) vs. the resulting `Hook#stack_id` after the top-level POST — currently `Hook#stack_id` is `nil`, violating `hook.stack_id == current_api_client.stack_id`.
