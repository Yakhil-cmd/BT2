### Title
Signature verified against attacker-controlled organization while payload's `repository.full_name` (the actually-written repository) is never bound to that organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), while every event `Handler` (e.g. `PushHandler`, `CheckSuiteHandler`, `StatusHandler`) resolves the target `Stack`/`Repository` to act on using a *different* field of the same untrusted JSON body: `payload.dig('repository', 'full_name')`. These two fields are never cross-checked against each other, so the "organization whose secret authenticated the request" and "the repository that is actually written to" are decoupled.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The signature check only proves the payload was HMAC-signed by *some* configured organization's `webhook_secret` — the specific organization is picked by the attacker via `repository.owner.login` (or `organization.login`), a field inside the very payload being verified. Once verification succeeds, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers that never re-check `repository.owner.login`; instead they resolve the target purely from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler#process`, `CheckSuiteHandler#process`, and `StatusHandler#process` all act on `stacks`/`Commit` records resolved from `repository_name` (i.e. `full_name`), independent of whichever org's secret was used to authenticate the request: [3](#0-2) [4](#0-3) 

Shipit explicitly supports configuring multiple independent GitHub Apps/organizations on one instance, each with its own `webhook_secret`, as documented in the setup guide: [5](#0-4) 

Given this, an attacker who controls one legitimate-but-lower-trust organization configured on the shared Shipit instance (and therefore knows that org's `webhook_secret`, since they set up their own GitHub App) can:
1. Forge a webhook body where `repository.owner.login` = their own org (so `repository_owner` resolves to it), but `repository.full_name` = `"victim-org/victim-repo"` (a repository belonging to a different, more trusted org on the same instance).
2. Sign the raw body with their own org's known `webhook_secret` using standard `sha1=` HMAC.
3. POST it to `/webhooks` with `X-Github-Event: push` (or `check_suite`/`status`).

`verify_signature` succeeds because it validates the signature using the attacker's own org's secret — which is exactly what they used. `PushHandler` then finds the **victim's** stack via `repository.full_name` and calls `stack.sync_github(expected_head_sha: params.after)`, causing Shipit to re-sync/re-poll the victim's actual GitHub repository and, if `continuous_deployment` is enabled on that stack, potentially trigger an earlier/forced deployment of a legitimate but attacker-chosen commit on a repository the attacker has no authorization over.

This is analogous to the reported bug class: a field that governs a security-relevant decision (`closableAmount` binding to `previousMagnitude`/settled position) is not properly bound/initialized from the authoritative source, allowing a mismatch between "what was verified" and "what is acted upon." Here, the binding that breaks is exactly the one called out in scope: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
This crosses a trust boundary explicitly targeted by scope: it lets a party who only controls one configured GitHub organization on a shared Shipit deployment force webhook-driven actions (sync, continuous-deployment triggering, check-run refresh, commit status writes) against a repository/stack belonging to a completely different organization, without ever needing that organization's webhook secret or GitHub credentials. In a continuous-deployment configuration this can result in an unauthorized deploy being triggered against a victim's stack — matching the Critical impact category ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to control one of those organizations (i.e., know its `webhook_secret`) — which is plausible in shared/multi-tenant Shipit deployments where different teams or external orgs are onboarded with their own GitHub Apps. No repository write access, `ApiClient` token, or session is needed; only knowledge of one legitimately-configured org's webhook secret, which is by design accessible to whoever set up that org's GitHub App.

### Recommendation
In `Handler#repository_name`/`stacks`, or in `WebhooksController`, verify that `payload.dig('repository', 'owner', 'login')` (the field used to select the signing organization) matches the owner portion of `payload.dig('repository', 'full_name')` before dispatching to handlers, and reject the request otherwise. Alternatively, pass the verified `repository_owner` into each handler and require handlers to only resolve stacks/repositories whose owner equals the authenticated organization.

### Proof of Concept
Given Shipit configured with two orgs, `attacker-org` (attacker-controlled, webhook secret known to attacker) and `victim-org` (has a Stack for `victim-org/victim-repo` with continuous deployment enabled):

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1 of body using attacker-org's webhook_secret>

{
  "ref": "refs/heads/main",
  "after": "<sha of a real, existing commit on victim-org/victim-repo>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
`repository_owner` resolves to `attacker-org` → `Shipit.github(organization: "attacker-org")` → signature verifies with the attacker's own secret. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack, per: [3](#0-2)  and [2](#0-1)

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
