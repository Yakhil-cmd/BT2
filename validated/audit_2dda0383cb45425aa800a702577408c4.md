### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Commit#create_status_from_github!` is safe when invoked from `refresh_statuses!` because the GitHub data it persists is fetched via `stack.github_api.statuses(github_repo_name, sha, ...)`, which is scoped to `commit.stack`'s own repository through the stack's own authenticated Octokit client. `StatusHandler#process`, however, calls the same method after looking up commits with `Commit.where(sha: params.sha)`, a query with no repository/stack scoping at all, so a genuine, correctly-signed `status` webhook for repository A can write a fabricated status onto commits belonging to an unrelated stack B, C, ... whose `sha` column happens to match.

### Finding Description
The claimed binding is: *"`create_status_from_github!` is only ever invoked with data already scoped to `commit.stack`'s repository"* — call this `scoped(create_status_from_github!) == true`.

- For `refresh_statuses!` this holds: `stack.github_api.statuses(github_repo_name, sha, per_page: 100)` (`app/models/shipit/commit.rb:156-163`) fetches only statuses for `github_repo_name`, so every `github_status` passed to `create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) genuinely belongs to `self.stack`'s repo. `scoped == true`.
- For `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) the binding is broken:
  ```ruby
  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
  ```
  `Commit.where(sha:)` searches the `commits` table globally, across every `stack`/`Repository`, with no `Repository.from_github_repo_name(repository_name)` filter. The base `Handler` class already exposes exactly this scoping via `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`), and it is used correctly by `PushHandler` (`stacks.not_archived.where(branch:)`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and all `PullRequest::*Handler`s. `StatusHandler` alone bypasses it. `scoped == false`.

Root cause: `commits.sha` is unique only per `(sha, stack_id)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), i.e. the same 40-hex SHA is expected and allowed to exist in multiple stacks simultaneously (forks, mirrors, shared history, or an attacker deliberately reproducing an identical git commit object — same tree/parent/author/committer/message/timestamps — in a repository they control, which yields an identical SHA-1 regardless of which repo stores it). `StatusHandler` does not filter on repository, so it matches every such row.

Exploit flow: attacker has push/CI access to a repository they own that lives under (or is installed under) an organization for which Shipit's GitHub App is configured with a real `webhook_secret` — this is a legitimate, ordinary "repository they own" per the threat model, not a privileged Shipit role. They (a) obtain a target commit SHA that already exists in a victim stack's repository (trivially available from public git history, or via a fork that inherits identical SHAs), (b) post a commit status to that SHA in their own repository via the standard GitHub Statuses API (state=`success`, arbitrary `context`/`description`/`target_url`), (c) GitHub delivers a genuine, correctly HMAC-signed `status` webhook event to Shipit's `/webhooks` endpoint. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates the signature against `Shipit.github(organization: repository_owner)` — this passes because the event is real and signed by GitHub for a repo under a trusted org; it says nothing about which repository's commits may be mutated. `StatusHandler#process` then writes the attacker-controlled status onto every `Commit` row across all stacks sharing that SHA, including the victim's.

None of the existing guards catch this: `verify_signature` only authenticates that GitHub sent the event for *some* known organization, not that the target commit belongs to the reporting repository; `ExplicitParameters` (`requires :sha, String`) only validates types, not ownership; `drop_unhandled_event` is irrelevant; there is no `require_permission!`/`stacks`-scope check inside `StatusHandler#process` itself.

### Impact Explanation
A payload legitimately originating from repository A mutates commit/status state belonging to stack B (a different repository/tenant) without B's repository ever having authorized or sent that event. Because commit status transitions drive `deployable?`/`blocked?` and, per `test/models/commits_test.rb` (`"#add_status schedule a MergeMergeRequests job..."`, continuous-delivery scheduling tests), can trigger `ProcessMergeRequestsJob` and continuous-deployment scheduling, an attacker can force an unrelated stack's commit into `success` state and precipitate an unauthorized deploy/merge, or conversely poison it to `error`/`failure` to block deploys. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." The attack is repeatable against any stack whose repository the attacker can discover a shared/reproducible SHA for, and is not limited to one victim per request.

### Likelihood Explanation
Preconditions: the attacker needs a repository under an organization Shipit already trusts (has the GitHub App/webhook installed with a real secret) — a normal, low-privilege situation for any org member or app-install-scoped repo, not requiring `Shipit.github_teams` membership or maintainer status on the victim repo. No Shipit secrets are needed since GitHub itself signs the webhook. Producing a colliding SHA is low-cost: forking a public target repo yields identical SHAs for free; even without forking, reproducing an identical git commit object from public metadata is straightforward with standard git tooling. The remaining step (posting a status via the standard GitHub API to a SHA in one's own repo) requires no special privilege beyond normal repo push/CI access. This is repeatable at will.

### Recommendation
Scope `StatusHandler#process` to the reporting repository, mirroring `PushHandler`/`PullRequest` handlers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) so only commits belonging to stacks of the repository named in the webhook payload can be updated.

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or equivalent):
1. Create two stacks/repositories, `stack_a` (owns `repository_a`) and `stack_b` (owns `repository_b`).
2. Create `commit_a = stack_a.commits.create!(sha: "deadbeef...", ...)` and `commit_b = stack_b.commits.create!(sha: "deadbeef...", ...)` — same `sha`, different `stack_id` (valid per the `(sha, stack_id)` unique index).
3. Assert baseline: `assert_equal 0, commit_b.statuses.count`.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => 'deadbeef...', 'state' => 'success', 'repository' => { 'full_name' => repository_a.github_repo_name })`.
5. Assert the broken binding: `assert_equal 1, commit_a.reload.statuses.count` (expected) **and** `assert_equal 1, commit_b.reload.statuses.count` (the bug — should be `0` if properly scoped to `repository_a`).
6. Contrast with a `refresh_statuses!` test (already present, `test/models/commits_test.rb:329-342`) showing `Shipit.github.api.expects(:statuses).with(@stack.github_repo_name, @commit.sha, ...)` is called with the stack's own repo name, proving the trusted path is correctly scoped while `StatusHandler#process` is not.
