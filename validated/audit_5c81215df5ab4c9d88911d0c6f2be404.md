### Title
Webhook signature is verified against the organization named in `repository.owner.login`/`organization.login`, but the write is keyed off the independent `repository.full_name` field, letting an attacker forge cross-repository events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` is used to check the HMAC solely from the attacker-supplied JSON field `repository.owner.login` (or `organization.login`), while every event `Handler` (e.g. `PushHandler`) resolves the actual `Repository`/`Stack` to act on from a *different*, independently attacker-controlled field, `repository.full_name`. Nothing binds these two fields together, and if the organization chosen for verification has no `webhook_secret` configured, `GithubApp#verify_webhook_signature` short-circuits to `true` regardless of the `X-Hub-Signature` header. This lets an unauthenticated caller pick a "no-secret" organization to pass verification while pointing `repository.full_name` at a completely unrelated, secured repository/stack, so the handler executes side effects (sync jobs, commit statuses, etc.) against a repository the attacker never authenticated for.

### Finding Description
The controller resolves the signing key using one payload field: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatically verified: [3](#0-2) 

The webhook secret is explicitly documented/configured as *optional* per organization: [4](#0-3) 

Once verification "passes" (trivially, because the chosen org has no secret), the raw, unauthenticated `params` are handed to every registered handler: [5](#0-4) 

Every handler then resolves its target `Stack`/`Repository` from a *second, unrelated* field of the same payload, `repository.full_name`, never checked for consistency with `repository.owner.login`: [6](#0-5) [7](#0-6) 

`PushHandler` then dispatches a real sync against whatever `Stack` matches that `full_name`, using an attacker-chosen `after` SHA: [8](#0-7) 

The binding this breaks is: *organization authenticated* (`repository.owner.login` used to pick the verifying `webhook_secret`) should equal *repository written* (`repository.full_name` used by `Handler#repository_name`/`Repository.from_github_repo_name` to pick the mutated `Stack`). Before the attack, both fields naturally agree because GitHub always sends consistent, self-signed payloads. After the attacker's crafted POST, `repository.owner.login` = an organization configured with no `webhook_secret` (verification vacuously succeeds), while `repository.full_name` = "victim-org/victim-repo", a completely different, security-sensitive repository tracked by Shipit under an organization that *does* have a secret. Since the check in `verify_signature` never inspects `full_name`, and handlers never re-check `owner.login`, the request is processed as if it legitimately originated from GitHub for the victim repository.

### Impact Explanation
An unauthenticated network attacker (no GitHub credentials, no repository access, no Shipit session or API token) can forge `push`, `status`, `check_suite`, `pull_request`, or `membership` webhook events for any repository Shipit tracks, as long as any single organization in the multi-tenant `github` config lacks a `webhook_secret` (an explicitly supported, "optional" configuration per `docs/setup.md`). Demonstrated concretely via `PushHandler`, this forces `Stack#sync_github` on an arbitrary victim stack with an attacker-supplied `expected_head_sha`, and the same binding gap lets the equivalent `status`-event handler write forged commit statuses (seen exercised in `test/controllers/webhooks_controller_test.rb:42-59`, `:state create a Status for the specific commit`) for a repository the attacker has no relationship to. Forged/faked commit or deployable statuses can be used to make an arbitrary commit appear CI-green, feeding into Shipit's deploy-gating logic and enabling an unauthorized deploy decision by legitimate stack maintainers who trust the (forged) status. This satisfies the Critical/High bar of "unauthorized deploy" arising from a broken authentication/authorization binding.

### Likelihood Explanation
Requires only that at least one configured GitHub organization in the Shipit deployment has an unset `webhook_secret` — a state the setup docs list as optional/normal, not exceptional — and that the attacker can send an arbitrary HTTP POST to the public `/webhooks` endpoint (which is intentionally internet-reachable so GitHub can deliver events). No credentials, no repository access, and no prior session are needed, so likelihood is high in any deployment that hasn't set `webhook_secret` uniformly for every configured organization.

### Recommendation
Bind signature verification to the same value used to select the target repository: derive `repository_owner` and repository identity from a single, mutually consistent source (e.g., require `repository.full_name.split('/').first == repository.owner.login` before verification, or better, key `verify_webhook_signature` off `repository.full_name` and reject payloads whose `owner.login`/`full_name` disagree). Additionally, disallow silently-accepting webhooks for organizations with a blank `webhook_secret`, or require secrets to be mandatory for any organization that hosts repositories tracked by Shipit.

### Proof of Concept
1. In a Shipit deployment with two configured GitHub orgs, `OrgA` (no `webhook_secret`) and `OrgB` (has `webhook_secret`, hosts the real target `OrgB/victim-repo`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, loads `Shipit.github(organization: "OrgA")`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank [9](#0-8) .
4. `PushHandler#process` resolves `repository_name` from `repository.full_name` = `"OrgB/victim-repo"` [10](#0-9)  and issues `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` against the real `OrgB/victim-repo` stack, entirely bypassing OrgB's webhook secret [11](#0-10) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
