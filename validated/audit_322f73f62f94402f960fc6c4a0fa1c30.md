### Title
API token stack-scoping bypass in CCMenu endpoint allows cross-stack read of deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
An `ApiClient` token that is scoped to a single stack (`stack_id` set, e.g. only `read:stack` permission on stack A) can read the CI/build status of **any** stack in the Shipit instance through `Api::CCMenuController#show`, because that controller resolves the target stack independently of the scoping logic used everywhere else in the API.

### Finding Description
`Shipit::ApiClient` can be scoped to a single stack via its `stack_id` column [1](#0-0) . The scoping is enforced centrally in `Api::BaseController#stacks`, which restricts the queryable set of stacks to the client's own `stack_id` when one is present, and every normal API controller (e.g. `Api::StacksController#stack`) resolves the target stack through this scoped relation:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` and resolves it directly from the unscoped `Stack` relation, bypassing `current_api_client.stack_id` entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

The only authorization check applied is `require_permission :read, :stack` [4](#0-3) , which just verifies the token carries the `read:stack` permission string via `ApiClient#check_permissions!` [5](#0-4) ; it never checks whether the requested `params[:stack_id]` matches the stack the token was scoped to. This breaks the equality that should hold everywhere else in the API: `stack the token authorizes == stack the token is allowed to touch`. Here it becomes `stack the token authorizes (stack A) != stack it actually touches (any stack, attacker-supplied via params[:stack_id])`.

### Impact Explanation
A token created and scoped to one stack (e.g. via the "CCMenu Client" auto-provisioning flow in `CCMenuUrlController#client`, which creates `ApiClient` records scoped to a single stack with only `read:stack` permission [6](#0-5) ) can be replayed against `GET /api/:stack_id/ccmenu` for a completely different, unauthorized stack. The response leaks build/deploy state for that other stack — `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl` [7](#0-6)  — i.e., unauthorized read of stack/deploy state belonging to a repository the token holder should have no visibility into. This matches the "unauthenticated/unauthorized read of stack state or deploy output" class of impact.

### Likelihood Explanation
High likelihood for anyone already holding any valid `read:stack`-scoped `ApiClient` token (these tokens are routinely distributed to lightweight integrations such as CI status widgets via the CCMenu URL feature). No additional privilege is required — the attacker only needs to change the `stack_id` in the URL path to any other stack's identifier, which are non-secret, sequential/slug-based values.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (as every other API controller does), e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a stack-scoped token can only ever resolve stacks matching its own `current_api_client.stack_id`.

### Proof of Concept
1. Provision (or obtain) an `ApiClient` scoped to Stack A with only `read:stack` permission, e.g. through the "CCMenu Client" flow (`CCMenuUrlController#fetch`), yielding a token `T` and its authentic ccmenu URL `/api/A/ccmenu?token=T`.
2. Call the same endpoint for a different, unrelated Stack B that this token was never granted access to:
   `GET /api/B/ccmenu?token=T`
3. `Api::CCMenuController#authenticate_api_client` successfully authenticates `T` via `ApiClient.authenticate(params[:token])` [8](#0-7) ; `require_permission :read, :stack` passes because `T` does have `read:stack` permission; `stack` resolves Stack B directly from `Stack.from_param!(params[:stack_id])`, ignoring that `T.stack_id == A.id`.
4. The response renders Stack B's CI/build status XML, even though `T` was never authorized for Stack B.
