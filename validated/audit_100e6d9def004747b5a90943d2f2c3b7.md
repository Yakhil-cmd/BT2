### Title
Webhook signature check silently passes when `webhook_secret` is unset, allowing unauthenticated forgery of `membership` events that escalate arbitrary users into `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as an automatic pass rather than rejecting the request, exactly the "missing validation, treat unverified as verified" pattern flagged in the report (`claimTokens()` failing to check whether the callee is a contract before trusting the call). Because `webhook_secret` is documented as optional per organization, any organization configured without one accepts **completely unsigned** webhook payloads at `/webhooks`, and the `membership` event handler uses that untrusted payload to directly add arbitrary users to `Team` records that gate `Shipit.github_teams` authorization.

### Finding Description
`WebhooksController#verify_signature` delegates trust entirely to `GitHubApp#verify_webhook_signature`: [1](#0-0) 

That method returns `true` unconditionally whenever no `webhook_secret` is configured for the organization resolved from the untrusted payload (`repository_owner`): [2](#0-1) [3](#0-2) 

`docs/setup.md` explicitly documents `webhook_secret` as optional ("Webhook secret (optional): Fill it with some randomly generated string..."), so this is a supported configuration, not a misconfiguration outside the documented deployment model: [4](#0-3) 

When no secret is set, `X-Hub-Signature` verification is a no-op, so an unprivileged, unauthenticated attacker can `POST` arbitrary JSON directly to `/webhooks` with any `X-Github-Event` header for that organization, exactly like the DODOApprove case where lack of a callee check lets an EOA (a "wallet") satisfy a check meant only for a verified proxy contract.

The most impactful handler reachable this way is `MembershipHandler`, which trusts the forged payload to find-or-create a `Team` and add a `member` to it with no further verification against GitHub: [5](#0-4) [6](#0-5) 

Authorization to use Shipit is gated by team membership: `User#authorized?` checks whether the current user belongs to any team in `Shipit.github_teams`, and `Shipit.github_teams` is derived from configured `oauth.teams` handles resolved to `Team` records: [7](#0-6) [8](#0-7) 

`force_github_authentication` in the base authentication concern is the sole gate protecting every privileged controller (stacks, tasks, deploys, rollbacks, repositories) behind `current_user.authorized?`: [9](#0-8) 

The binding broken is: **the GitHub organization whose signature is supposed to authenticate the webhook == the organization whose `Team`/`Membership` records are mutated to grant application authorization.** When `webhook_secret` is absent, the left side of that binding never gets verified at all, so the right side (team membership, and thus `Shipit.github_teams` authorization) can be forged by anyone who can reach the `/webhooks` endpoint, without a GitHub session, API token, or repository access of any kind.

### Impact Explanation
An unauthenticated network attacker can:
1. `POST` a forged `membership` webhook (`action: 'added'`) naming a `team.id` matching one of `Shipit.github_teams`' underlying `github_id`s, and any `member.login`, causing `User.find_or_create_by_login!` to create/fetch that user and `Team#add_member` to grant them membership.
2. That membership satisfies `User#authorized?`, granting them full access to the Shipit UI/API for stacks, deploys, rollbacks and merges — i.e., escalation into `Shipit.github_teams` authorization, one of the explicitly listed High-severity impacts.

This requires only that the target organization's GitHub App config in `secrets.yml` omits `webhook_secret`, a state the project's own setup docs present as a normal, optional configuration rather than a deviation from documented deployment.

### Likelihood Explanation
Likelihood depends entirely on whether an operator has left `webhook_secret` blank for an organization — a state the docs call "optional," making it a realistic, supported configuration rather than a hypothetical misconfiguration. Where present, this is a zero-privilege, network-reachable forgery requiring no credentials, GitHub session, or repository access, matching the rules' bar for unprivileged-attacker analogs.

### Recommendation
Reject (not accept) unsigned webhook requests when `webhook_secret` is not configured, or make `webhook_secret` mandatory for every organization served by `WebhooksController`, so `verify_webhook_signature` never silently returns `true` for an unset secret.

### Proof of Concept
Given an organization config in `secrets.yml` with no `webhook_secret` key (a documented, optional field):

```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json
(no X-Hub-Signature required)

{
  "action": "added",
  "team": { "id": <github_id_of_an_authorized_team>, "name": "Ouiche Cooks", "slug": "ouiche-cooks", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-controlled-login" }
}
```

`WebhooksController#verify_signature` calls `verify_webhook_signature(nil, raw_post)`, which returns `true` immediately because `webhook_secret` is blank (`lib/shipit/github_app.rb:77`), and `MembershipHandler#process` adds the attacker's user to the team, satisfying `User#authorized?` for the entire application.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        end

      end
```
