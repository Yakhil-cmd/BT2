### Title
`is_valid_sig`/`is_valid_signed_package` formula primitives verify arbitrary attacker/oracle-supplied message+pubkey with no domain separation, enabling cross-AA/cross-network signature replay - ([File: formula/evaluation.js])

### Summary
The oscript primitives `is_valid_sig` and `is_valid_signed_package`, evaluated inside AA trigger-data validation, verify a raw `message`/`signed_message` against a raw `signature` and an attacker- or trigger-data-supplied `pem_key`/address, with no protocol-enforced domain separator (no chain id, no AA address binding, no app identifier baked into the hash). This mirrors the reported `bytes calldata signature` issue: signatures produced for one context can be replayed wherever an AA/DApp accepts the same message format.

### Finding Description
`is_valid_sig(message, pem_key, sig)` hashes `evaluated_message` with SHA-256 and verifies it against a signature and a PEM public key, both of which are evaluated from formula expressions (often derived directly from `trigger.data`): [1](#0-0) 

`is_valid_signed_package` calls `signed_message.validateSignedMessage`, which hashes the whole `signed_message` object (via `objectHash.getSignedPackageHashToSign`) and validates the address definition/signature over it, but the resulting authenticated statement is only "address A signed message M" — nothing in the hashed structure ties the signature to a specific AA, a specific application/DApp, or a specific network/fork: [2](#0-1) [3](#0-2) [4](#0-3) 

Because `message`/`signed_message` are plain strings/objects with a format entirely defined by the AA author (not a protocol-fixed, contract/app-scoped digest as in EIP‑712), the same off-chain signed statement can be validly replayed:
- Across multiple AAs that happen to accept the same message format (an off-chain signer who signs "approve X" for AA1 unintentionally authorizes the same action in AA2).
- By an unprivileged trigger sender who obtains/observes a signed message intended for a different purpose (e.g., an oracle attestation, a KYC statement, or a price commitment) and replays it as trigger data into an AA that performs the same `is_valid_sig`/`is_valid_signed_package` check, since the AA has no way to bind the signature to "this AA, this call, this nonce" unless the AA author manually adds nonce/timestamp/AA-address fields to the signed payload themselves.

### Impact Explanation
An unprivileged trigger sender can submit a captured/observed signature+message pair as AA trigger data. If any deployed AA uses `is_valid_sig`/`is_valid_signed_package` to gate fund release, minting, or state transitions based on a fixed address's signature over attacker-supplied message content, replay across AAs or across contexts can lead to unauthorized AA fund release or state corruption — matching the "concrete unauthorized spending / AA fund loss" bar. The severity is bounded by AA-author discipline (an AA that includes its own address/nonce inside the signed message is safe), so this is a footgun in the primitive design rather than an unconditional exploit, but it is the same root cause as the referenced Sherlock finding: no protocol-enforced domain separator on signature verification primitives.

### Likelihood Explanation
Medium: exploitation requires an AA that uses these primitives to authenticate a fixed signer without itself adding AA-specific/nonce binding to the signed content — a pattern the primitive's design encourages since it hands the AA author raw `message`/`pem_key`/`signature` values without any built-in domain tag. Given AAs are commonly built by third parties reusing patterns from documentation/examples, this is a realistic, recurring misuse surface.

### Recommendation
Extend `is_valid_sig` and `is_valid_signed_package` (or provide a safer variant) to optionally/mandatorily mix in a domain separator — e.g., the AA's own address, and/or an explicit `app`/`contract` tag and network identifier — into the hashed message before verification, analogous to EIP-712's domain separator (contract address + chain id + type hash). At minimum, document prominently that AA authors must embed their own AA address and a purpose-specific nonce inside `message`/`signed_message` to prevent cross-AA and cross-purpose replay, and consider adding a lint/validation warning during AA deployment when `is_valid_sig`/`is_valid_signed_package` is used without referencing `trigger.address`/`this_address` inside the signed message.

### Proof of Concept
1. An off-chain party P signs a message `M = "1000"` intended for AA_A's `is_valid_sig(trigger.data.message, FIXED_PEM_KEY, trigger.data.signature)` check that releases 1000 bytes when `M` matches an oracle value.
2. AA_B is deployed independently, also checking `is_valid_sig(trigger.data.message, FIXED_PEM_KEY, trigger.data.signature)` against the same signer's PEM key for an unrelated purpose (e.g., minting a token amount equal to `M`).
3. An unprivileged user who observed P's signature for AA_A (e.g., from a public unit or a leaked oracle feed) submits it as trigger data to AA_B.
4. Because neither the hash in `is_valid_sig` (`formula/evaluation.js:1704-1731`) nor the definition of the signed message (`signed_message.js:117-141`) includes any AA-address or application-scoped domain tag, AA_B accepts the same signature, causing unintended minting/fund release — the exact "signature reuse across different projects" scenario described in the referenced report.
