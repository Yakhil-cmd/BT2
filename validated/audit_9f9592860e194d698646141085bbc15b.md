## Title
Cross-Repository Commit Status Forgery via Webhook Authentication/Write-Target Mismatch — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

## Summary
The reentrancy bug in the source report ultimately reduces to a "checks-effects" ordering flaw where a value used to *authorize* an action (the recipient the transfer succeeded against) diverges from the value actually *mutated* afterward (the balance record keyed by `tokenId`), letting an attacker manipulate state for a token/recipient pair that was never validated together. The analogous binding-break in this engine is in Shipit's GitHub webhook pipeline: the identity used to *authenticate* an inbound webhook (`repository.owner.login`, used to pick which organization's `webhook_secret` validates the HMAC) is never propagated into the code that actually *writes* state. `StatusHandler` mutates `Commit` records by matching on the bare `sha` field only, with zero scoping to the repository/organization whose signature was verified.

## Finding Description
`WebhooksController#verify_signature` selects the GitHub App/organization config used to validate the inbound signature purely from an unauthenticated field of the JSON body itself: [1](#0-0) [2](#0-1) 

Once the signature is deemed valid for *that* org, the raw payload is dispatched to per-event handlers with no re-binding of "which repository/org this event is allowed to touch": [3](#0-2) 

The base `Handler` class does define a repository-scoped `stacks` helper keyed off `repository.full_name`: [4](#0-3) 

However, `StatusHandler` — which persists commit CI/status data that directly feeds `Commit#deployable?` and gate merge/deploy decisions — does not use that scoping at all. It looks up commits **globally by `sha`**, across every stack/repository/organization hosted by the Shipit instance: [5](#0-4) 

This status is then trusted directly to determine deployability: [6](#0-5) 

So the binding that should hold is:
`organization/repository whose signature was verified == organization/repository whose Commit records get new statuses written`

Because `StatusHandler#process` never consults `payload.dig('repository', ...)`, this equality is not enforced: any `sha` collision across repositories tracked by the same Shipit instance (a very common situation — Shipit stacks frequently track forks, mirrors, or multiple branches/environments of related repositories sharing git history) lets a webhook that is validly signed for repository/org A silently set CI status for identical commits that also exist in an unrelated stack B, whose CI checks were never actually satisfied by B's own CI systems.

## Impact Explanation
Forged/cross-scoped commit statuses feed directly into `Commit#deployable?`, `MergeRequest#all_status_checks_passed?`, and continuous-deployment triggering. An attacker who can get one signed `status` webhook processed for a shared SHA (e.g., via a repository/fork they control that is also onboarded to the same Shipit instance) can flip an otherwise-blocked commit in a *different* stack to `success`, which can trigger an unauthorized deploy (continuous deployment stacks deploy automatically on status transitioning to `success`) or let a merge-queue PR pass CI gating it never actually satisfied. This matches the "unauthorized deploy … or merge" High/Critical impact category.

## Likelihood Explanation
Exploitation does not require compromising `webhook_secret`, an `ApiClient` token, or a privileged Shipit account — only the ability to have one legitimately-signed webhook event delivered to Shipit for a `sha` that also exists in a victim stack's commit history (a realistic scenario for forked/mirrored repositories, which Shipit explicitly documents supporting via review stacks and multiple stacks per repository/environment). The root cause is a straightforward missing scoping check in application code, not a misconfiguration.

## Recommendation
Scope `StatusHandler#process` (and any other handler mutating commit/stack state) to the `repository.full_name`/`stacks` already exposed by the `Handler` base class, mirroring how `PushHandler` and the `PullRequest` handlers correctly restrict their effects to `stacks`/`repository`. Only update `Commit` rows whose `stack_id` belongs to a stack of the verified repository, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` instead of matching `sha` alone.

## Proof of Concept
1. Shipit instance tracks Stack A (`orgA/repo`) and Stack B (`orgB/fork-of-repo`), which share commit history/SHAs (a fork or mirror scenario).
2. Attacker controls `orgB/fork-of-repo` (or a CI integration with write access to it) and causes GitHub to send a legitimately-signed `status` webhook event for SHA `abc123` (which exists in both A and B) with `state: success`.
3. `WebhooksController#verify_signature` validates the signature against `orgB`'s `webhook_secret` — this succeeds, since it is a real, correctly signed event from `orgB`.
4. `StatusHandler#process` runs `Commit.where(sha: 'abc123')`, which matches the commit in **both** Stack A and Stack B, and sets `state: success` on all of them: [5](#0-4) 
5. Stack A's commit `abc123` is now marked `success` even though Stack A's own required CI checks were never run/passed, making it `deployable?` and eligible for continuous deployment/merge in Stack A.
