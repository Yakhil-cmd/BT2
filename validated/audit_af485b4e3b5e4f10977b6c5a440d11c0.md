### Title
Cross-organization webhook forgery: authenticated organization is not bound to the repository/commit that gets written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App configuration for a single organization derived from the request body (`repository.owner.login`, falling back to `organ ization.login`), but the webhook handlers process all stacks across all repositories matching the webhook's `repository.full_name`, regardless of which organization's GitHub App secret was used to verify the signature. An attacker with a valid webhook secret for one GitHub organization can forge webhooks for repositories in other organizations, causing unauthorized deploys, status updates, or pull request operations.

### Finding Description
The vulnerability exists in the webhook signature verification and handler dispatch flow:

1. **Signature verification is organization-scoped** [1](#0-0) : The `verify_signature` method extracts the organization from the webhook payload and verifies the signature against that organization's GitHub App secret.

2. **Handler dispatch is repository-scoped, not organization-scoped** [2](#0-1) : The webhook handlers are called with the raw payload, and they look up stacks by repository name alone.

3. **Repository lookup ignores organization** [3](#0-2) : The `stacks` method in the base handler class calls `Repository.from_github_repo_name(repository_name)`, which performs a case-insensitive lookup by owner and name but does not validate that the repository belongs to the organization that authenticated the webhook.

4. **Repository model stores owner as a simple string** [4](#0-3) : The `from_github_repo_name` method splits the full name and queries by owner and name without any organization binding.

### Impact Explanation
An attacker who obtains the webhook secret for one GitHub organization (e.g., through a compromised CI/CD system, leaked configuration, or insider threat) can craft valid webhook signatures for that organization. They can then send webhooks with a `repository.full_name` pointing to a repository in a *different* organization, and the webhook will be accepted and processed because:

- The signature verification passes (it uses the attacker's known secret)
- The handler finds the target repository by name alone
- The handler executes the webhook action (e.g., triggering a deploy, updating commit status, creating/archiving review stacks)

**Concrete attack scenario:**
- Attacker has the webhook secret for `org-a` (e.g., `webhook_secret_a`)
- Attacker crafts a push webhook with `repository.owner.login = "org-a"` and `repository.full_name = "org-b/production"`
- The webhook signature is verified against `org-a`'s secret (passes)
- The handler looks up stacks for `org-b/production` and triggers a deploy
- The deploy executes with the credentials of `org-b`'s GitHub App, not `org-a`'s

This breaks the trust boundary: the organization that authenticated the webhook is not the organization whose repository is being modified.

### Likelihood Explanation
This vulnerability requires:
1. An attacker to obtain a webhook secret for at least one organization (moderate difficulty depending on operational security)
2. Knowledge that Shipit is deployed and which repositories are configured (low difficulty; often public or discoverable)
3. The ability to send HTTP POST requests to the webhook endpoint (trivial)

The attack is deterministic once a secret is compromised; there is no race condition or timing dependency.

### Recommendation
Bind the authenticated organization to the repository being modified. Options:

1. **Strict organization matching** (recommended): After verifying the signature against an organization's secret, validate that the `repository.owner.login` in the payload matches the organization used for verification. Reject the webhook if they do not match.

2. **Repository-to-organization mapping**: Store an explicit organization association with each `Repository` record. When a webhook arrives, verify that the repository's stored organization matches the authenticated organization.

3. **Separate webhook endpoints per organization**: Use distinct webhook URLs for each organization, each with its own secret and organization context.

webhook_secret_a = "secret_for_org_a"

# Attacker crafts a push webhook for org-b/production

  "repository" => {
    "full_name" => "org-b/production",
    "owner" => { "login" => "org-a" }  # Lie: claim to be from org-a
  },
  "ref" => "refs/heads/main",
  "after" => "abc123def456"
}.to_json

# Attacker computes valid signature using org-a's secret
signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", webhook_secret_a, payload)

# Attacker sends POST to /webhooks with:
# X-Hub-Signature: sha1=<computed_signature>
# X-Github-Event: push
# Body: <payload>

# Current behavior:
# 1. verify_signature extracts "org-a" from payload
# 2. Looks up Shipit.github(organization: "org-a")
# 3. Verifies signature against org-a's secret → PASSES
# 4. Handler calls Repository.from_github_repo_name("org-b/production")
# 5. Finds the repository (if it exists in Shipit)
# 6. Triggers deploy for org-b/production using org-b's GitHub App credentials
# 7. Unauthorized deploy succeeds
