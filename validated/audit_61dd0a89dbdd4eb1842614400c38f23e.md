### Title
Webhook organization used for signature verification is decoupled from the repository actually written — cross-repository/cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and its `webhook_secret`) to verify a payload against using `repository.owner.login` (or `organization.login`) pulled out of the *unverified* request body, while every downstream `Webhooks::Handlers::Handler` resolves the `Repository`/`Stack` to mutate using a **different** field of that same unverified body: `repository.full_name`. Nothing ties these two fields together, and signature verification is a documented no-op whenever an organization has no `webhook_secret` configured. This lets an attacker who controls (or targets) an org with no configured `webhook_secret` forge a payload whose `repository.full_name` names an entirely different, unrelated repository/stack, causing Shipit to act on that stack as if the event were genuine.

### Finding Description
`verify_signature` computes the organization used to pick the verifying `GitHubApp` instance strictly from the JSON body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization: [3](#0-2) 

`webhook_secret` is explicitly documented and shipped as an optional setting (e.g. `webhook_secret: # nil` in multiple secrets templates), so operators legitimately run organizations with no webhook secret configured: [4](#0-3) [5](#0-4) 

Once past `verify_signature`, `create` re-parses the raw body and dispatches it to handlers, none of which re-check the organization: [6](#0-5) 

Every handler resolves the target `Repository`/`Stack` using `repository.full_name`, a field that was never inspected by `verify_signature` and is never checked for consistency with `repository.owner.login`: [7](#0-6) [8](#0-7) [9](#0-8) 

The binding the system implicitly relies on is:
`organization authenticated (repository.owner.login / organization.login, checked against a GitHub App's webhook_secret)` == `organization/repository actually written (repository.full_name, used by Repository.from_github_repo_name)`

This equality is never enforced. An attacker who knows (or exploits the absence of) a webhook secret for **any one** configured organization (`OrgA`) can submit a payload where `repository.owner.login = "OrgA"` (satisfying/bypassing the signature check for `OrgA`) but `repository.full_name = "OrgB/victim-repo"`, causing Shipit to write into `OrgB`'s stack — an organization whose webhook credentials were never checked at all.

### Impact Explanation
This breaks the organization-authenticated vs. repository-written binding and produces unauthorized writes to stacks that belong to a different, uninvolved GitHub organization/repository than the one nominally authenticated:
- `push` events can trigger `stack.sync_github`, which drives commit ingestion and, for stacks with `continuous_deployment` enabled, autonomous deploys — an unauthorized deploy path.
- `status`/`check_suite` events let an attacker forge commit statuses/check-run refreshes on an unrelated stack's commits, which `deployable?`/CI gating logic relies on to permit deploys.
- `pull_request` events can create/archive review stacks (`ReviewStack#archive!`/`unarchive!`) for repositories outside the attacker's control.

This matches the required impact bar of "unauthorized deploy" / cross-repository writes.

### Likelihood Explanation
Likelihood is high wherever multi-organization Shipit deployments exist and at least one configured organization has no `webhook_secret` (a state the shipped templates and docs treat as a normal, supported configuration, not a misconfiguration). No credentials, sessions, or GitHub App keys are required — only knowledge that a low-friction/no-secret organization exists in the target's `secrets.github` configuration, or the absence of `webhook_secret` on the sole configured org in single-org deployments.

### Recommendation
Bind the organization that authorizes the request to the repository that is actually mutated:
- After `verify_signature` succeeds, re-validate that `repository.full_name`'s owner matches the `repository_owner`/`organization.login` that was used to select the verifying `GitHubApp`, rejecting the request (422) on mismatch.
- Do not treat `verify_webhook_signature` as trivially satisfied (`return true unless webhook_secret`) for organizations that host repositories also reachable via other, secret-protected organizations; consider requiring `webhook_secret` for any multi-organization deployment, or scoping the "no secret configured" bypass to true single-organization installs only.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgA` (no `webhook_secret` set, per the documented optional setting) and `OrgB` (has a `Stack` for `OrgB/victim-repo` with `continuous_deployment: true`).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known/ingested>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
Any (or no) `X-Hub-Signature` header value.
3. `verify_signature` calls `Shipit.github(organization: "OrgA")` → `verify_webhook_signature` returns `true` unconditionally because `OrgA` has no `webhook_secret` (`lib/shipit/github_app.rb#L76-83`).
4. `PushHandler#process` resolves the stack via `repository.full_name = "OrgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb#L33-38`) and calls `stack.sync_github`, acting on `OrgB`'s stack despite `OrgB`'s credentials never being checked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
