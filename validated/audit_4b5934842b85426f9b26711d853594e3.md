### Title
Webhook organization used to verify signature is never bound to the repository/commit actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization (and therefore the webhook secret) used to validate `X-Hub-Signature` from one field of the attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`), while the handlers that actually mutate Shipit's data pick their target repository/commit from a *different, independently-controlled* field of the very same body (`repository.full_name`), or in the case of `StatusHandler`, from no repository field at all. Because nothing enforces that "the organization whose secret signed this payload" equals "the repository/commit this payload writes to," anyone who legitimately controls a webhook secret for *one* organization/repository configured in a multi-tenant Shipit install can forge signed events that target a completely different, unrelated repository/stack.

### Finding Description
`verify_signature` derives the signing organization purely from attacker-controlled JSON, then verifies the signature using that organization's own secret: [1](#0-0) [2](#0-1) 

Once the signature passes, event handlers select which data to mutate from a *different* payload field: [3](#0-2) 

`PushHandler` (and other repo-scoped handlers) use `stacks`/`repository_name`, i.e. `repository.full_name`, which is never checked against `repository.owner.login`/the organization whose secret validated the request: [4](#0-3) 

`StatusHandler` is worse: it does not consult the repository field at all and simply looks up **any** commit in the entire database matching an attacker-chosen `sha`: [5](#0-4) 

So the binding that should hold — `organization_whose_secret_signed_request == repository/commit_being_written` — is never enforced. An attacker who legitimately owns a webhook secret for organization A (a normal, non-privileged capability in a multi-org Shipit deployment, since Shipit supports many independently configured GitHub orgs/apps) can sign a payload with A's secret while setting `repository.full_name` (or `sha`, for status events) to point at organization B's tracked repository/commit.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust boundary called out as in-scope:
- Via `StatusHandler`, the attacker can inject a forged commit status (`state`, `context`, `target_url`, `description`) onto **any** commit tracked by Shipit across **any** stack, as long as they can guess/observe its SHA (commit SHAs are frequently public via GitHub). If a victim stack's merge queue, deployable-status checks, or deploy safety gating rely on required commit statuses being green, this allows an attacker to spoof CI success and induce an unauthorized merge or deploy on a repository they do not control — this is a cross-repository write leading to an unauthorized merge/deploy.
- Via `PushHandler`/`Handler#stacks`, the attacker can cause `GithubSyncJob` to run against a victim's stack (using Shipit's own GitHub App credentials to fetch commits) even though only organization A's webhook secret was proven, not any relationship to the victim's organization/repository.

Both outcomes match the Critical bar defined by the rules ("cross-repository writes" / "an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation only requires knowledge of one legitimately-configured organization's webhook secret in a multi-tenant Shipit deployment (an ordinary, unprivileged onboarding capability, not repository write access to the victim, not a Shipit session, and not `api_clients_secret`/`webhook_secret` of the victim organization). Crafting the payload is trivial (standard JSON fields), and the divergent fields (`repository.owner.login` vs `repository.full_name`/`sha`) are both attacker-controlled in the same request body.

### Recommendation
Enforce that the field used to select the verifying organization is the same field used to select the target repository/commit:
- In `WebhooksController#verify_signature` / handlers, after verifying the signature for `repository_owner`, additionally assert that the resolved repository owner matches the owner of `repository.full_name` used by the handler (i.e., derive both from the same trusted value, not two independently attacker-settable fields).
- In `StatusHandler#process`, scope the `Commit.where(sha: params.sha)` lookup to commits whose stack's repository matches `payload.dig('repository', 'full_name')`, and reject/ignore the event if that repository's owner does not match the organization that verified the signature.
- More generally, treat `repository.owner.login`/`organization.login` and `repository.full_name` as a single logical field for authorization purposes: never let one determine trust (signature org) while the other determines effect (target repository/commit).

### Proof of Concept
1. Attacker legitimately owns/administers GitHub organization `attacker-org`, which is configured in this Shipit install with webhook secret `S_A` (normal multi-tenant usage, not a privileged Shipit capability).
2. Attacker observes/knows a commit SHA `deadbeef...` belonging to a stack tracked under `victim-org/victim-repo` in the same Shipit instance (SHAs are public on GitHub).
3. Attacker builds a body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/throwaway" },
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check",
  "description": "forced green",
  "target_url": "https://example.com"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` using their own known secret `S_A`, and sends it as a `status` event to the webhooks endpoint.
5. `WebhooksController#verify_signature` reads `repository_owner == "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and validates the signature against `S_A` — this succeeds because the attacker legitimately owns that secret. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no relation to `attacker-org`, finds the victim's commit, and calls `create_status_from_github!`, applying the forged status to `victim-org/victim-repo`'s commit. [5](#0-4) 

I was not able to fully trace, within the remaining iterations, the exact downstream code that gates merges/deploys on commit statuses (e.g., merge-queue required-check logic) to quantify precisely which deploy/merge actions this forged status can unlock; that would need further review of the merge-queue and deployable-status logic to confirm the exact automated action triggered.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
