### Title
`handleERC721Transfer` Uses Unsafe `transferFrom` Instead of `safeTransferFrom`, Permanently Freezing Bridged ERC721 NFTs in Non-ERC721-Receiver Contracts — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

In `BridgeTransferERC721.handleERC721Transfer`, the non-mintBurn delivery path calls `IERC721.transferFrom` to send the bridged NFT to the user-specified `_to` address. If `_to` is a contract that does not implement `IERC721Receiver`, the NFT is silently transferred into that contract and permanently frozen. The bridge nonce is already consumed and the handle event already emitted before the transfer, so the bridge considers the operation complete with no recovery path. The sibling contract `BridgeTransferERC20` correctly uses `safeTransfer` (via `SafeERC20`) for the analogous delivery, making the inconsistency explicit.

---

### Finding Description

In `BridgeTransferERC721.sol`, the operator-callable `handleERC721Transfer` function finalises a cross-chain ERC721 transfer on the destination bridge. After updating the handle nonce and emitting `HandleValueTransfer`, it delivers the token:

```solidity
if (modeMintBurn) {
    require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
} else {
    IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);   // ← unsafe
}
``` [1](#0-0) 

`transferFrom` does **not** call `onERC721Received` on the recipient. EIP-721 requires that any contract wishing to receive NFTs via safe transfer must implement `IERC721Receiver`. If `_to` is a contract without that interface, the NFT is deposited into it with no revert, and no mechanism exists to retrieve it.

The `_to` address originates from the user's `requestERC721Transfer` call on the source chain:

```solidity
function requestERC721Transfer(
    address _tokenAddress,
    address _to,
    uint256 _tokenId,
    bytes memory _extraData
) public {
    IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
    _requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
}
``` [2](#0-1) 

The bridge relayer faithfully replays `_to` into `handleERC721Transfer` with no validation of whether `_to` can receive ERC721 tokens. [3](#0-2) 

By contrast, `BridgeTransferERC20.handleERC20Transfer` uses `SafeERC20.safeTransfer` for the equivalent delivery:

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [4](#0-3) 

The inconsistency is structural: ERC20 delivery is safe, ERC721 delivery is not.

---

### Impact Explanation

- The bridged ERC721 NFT is permanently frozen inside a contract that cannot handle it.
- The bridge handle nonce (`_updateHandleNonce`) and the `HandleValueTransfer` event are committed **before** the `transferFrom` call, so the bridge considers the transfer settled. There is no retry, reversal, or recovery mechanism.
- The original NFT was already burned or locked on the source chain (depending on `modeMintBurn`), so the user suffers a total, unrecoverable loss of the bridged asset. [5](#0-4) 

---

### Likelihood Explanation

Any user who specifies a contract address as `_to` when initiating an ERC721 bridge transfer triggers this path. Common real-world scenarios include:

- Bridging to a multisig wallet (e.g., Gnosis Safe) that has not implemented `onERC721Received`.
- Bridging to a DeFi protocol contract (e.g., a vault or marketplace) that accepts ERC721 via its own deposit function but does not implement the ERC721 receiver interface.
- Bridging to a contract that implements `onERC721Received` only for specific token addresses.

No special privilege is required; any user of the bridge can trigger this.

---

### Recommendation

Replace `transferFrom` with `safeTransferFrom` in the non-mintBurn delivery path of `handleERC721Transfer`:

```solidity
// Before
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
``` [6](#0-5) 

`safeTransferFrom` calls `onERC721Received` on the recipient if it is a contract, and reverts if the call fails or returns an unexpected selector. This ensures the NFT is never silently deposited into a contract that cannot handle it, and the revert will prevent the handle nonce from being consumed for an undeliverable transfer.

### Proof of Concept

1. Alice owns ERC721 token ID `42` on the child chain.
2. Alice calls `requestERC721Transfer(nftAddr, vaultContractAddr, 42, "0x")` on the source bridge, where `vaultContractAddr` is a contract that does **not** implement `IERC721Receiver`.
3. The source bridge locks/burns token `42` and emits `RequestValueTransferEncoded` with `_to = vaultContractAddr`.
4. Bridge operators relay the event and call `handleERC721Transfer(..., vaultContractAddr, ..., 42, ...)` on the destination bridge.
5. The bridge updates `lowerHandleNonce`, emits `HandleValueTransfer`, then executes:
   ```solidity
   IERC721(nftAddr).transferFrom(address(this), vaultContractAddr, 42);
   ```
6. The call succeeds (no revert), token `42` is now owned by `vaultContractAddr`.
7. `vaultContractAddr` has no `onERC721Received` and no way to call `transferFrom` or `safeTransferFrom` on the NFT contract — token `42` is permanently frozen.
8. Alice's NFT is gone from the source chain and inaccessible on the destination chain. [1](#0-0)
