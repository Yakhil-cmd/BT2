## Analog Found: Signed Payment-Channel "Fraud Proof" Voucher Can Be Frontrun to Steal the Entire Channel Balance

### Title
Signed Off-Chain Payment-Channel Proof Can Be Frontrun by Any Third Party to Steal Escrowed Funds - (File: test/samples/payment_channels.oscript)

### Summary
The Obyte oscript primitive `is_valid_signed_package()` lets an Autonomous Agent (AA) accept an off-chain message signed by a known address as authorization for an on-chain action, exactly like an NFT "voucher" signed off-chain and redeemed on-chain later. The reference payment-channel AA pattern shipped with ocore (`test/samples/payment_channels.oscript`) uses this primitive to let either channel party punish the other for lying about spent amounts ("fraud proof"). The `fraud_proof` case validates only that the embedded signed package (`trigger.data.sentByPeer`) is validly signed by the correct channel counterparty — it never checks that the AA trigger itself (`trigger.address`) comes from one of the two legitimate channel parties. As soon as this signed package appears anywhere on the public, not-yet-stable DAG (e.g. inside the `close` trigger that references it), any unrelated address can copy it into its own trigger and redirect the entire channel balance to itself, exactly mirroring the reported "voucher can be frontrun" bug class but with a concrete fund-theft outcome instead of mere griefing.

### Finding Description
`is_valid_signed_package()` is implemented in `formula/evaluation.js` and validates only the cryptographic signature of the embedded message against a caller-supplied address, delegating to `signed_message.validateSignedMessage()`: [1](#0-0) 

This mirrors `signMessage`/`validateSignedMessage` in `signed_message.js`, where an author's `authentifiers` prove the signer's identity but the signed payload carries no binding to who is authorized to *submit* it on-chain: [2](#0-1) 

The reference contract pattern that ships with ocore's oscript test suite, `test/samples/payment_channels.oscript`, uses this exact mechanism as the "voucher": each party can prove the other spent more than they admitted by presenting a `sentByPeer` package that the counterparty signed off-chain: [3](#0-2) 

The `if` condition only checks `trigger.data.fraud_proof AND var['close_initiated_by'] AND trigger.data.sentByPeer` — it does **not** require `trigger.address` to equal `$addressA` or `$addressB`. The subsequent `messages` block then pays out the **entire remaining channel balance** to `trigger.address`, i.e., to whoever submitted the trigger, not necessarily to the honest channel party: [4](#0-3) 

Once the signed `sentByPeer` package is exposed on the DAG even once — for example when it is legitimately included as data in the `close` trigger by one of the parties (also unauthenticated by `trigger.address` beyond `$bFromParties`, see lines 32-50) — it becomes visible to the entire network before the unit is stable. Any third party can then compose their own unit carrying `trigger.data = {fraud_proof: true, sentByPeer: <copied package>}` and race to get it included/stabilized first, since `is_valid_signed_package` only checks the embedded signature, never who is calling.

### Impact Explanation
This is a direct analog of "vouchers can be frontrun": the signed authorization (voucher) is bound to the signer's identity but not to whoever is entitled to execute it. In the NFT case, frontrunning only causes a failed/duplicate mint; here, the missing binding on `trigger.address` allows an unrelated address to unconditionally capture the entire remaining channel balance (`payment` message sends the "send all" output to `trigger.address`), which is unauthorized spending/theft of AA-held funds rather than mere denial of service.

### Likelihood Explanation
Exploitability requires only that the signed package appear at least once, unconfirmed, on the public DAG (which happens whenever either legitimate party submits `close` or `fraud_proof` normally) and that an attacker be watching for AA triggers referencing this specific channel address — a purely passive, unprivileged unit-posting attack requiring no special access, matching the "single posted unit/trigger" reachability criterion.

### Recommendation
Bind the trigger sender to the legitimate counterparty in the `fraud_proof` (and similarly in `close`) case, e.g. require `trigger.address == ($bInitiatedByA ? $addressB : $addressA)` in addition to signature validity, so that only the wronged party can claim the payout. More generally, any oscript AA pattern using `is_valid_signed_package()` as an authorization mechanism should also constrain `trigger.address` to the intended executor/recipient, and this guidance should be reflected in the reference examples ocore ships to AA developers.

### Proof of Concept
1. Parties A and B run the payment channel AA from `test/samples/payment_channels.oscript`, exchanging off-chain signed `sentByPeer` statements as usual.
2. A initiates `close` with a lower `transferredFromMe`/without disclosing B's true spend, and includes B's previously-received signed statement in `trigger.data.sentByPeer` (or B submits `fraud_proof` legitimately) — this unit is broadcast to the network but not yet stable.
3. Attacker C observes the not-yet-stable unit, extracts `trigger.data.sentByPeer` (still a validly signed package by B), and immediately composes and broadcasts its own unit with `trigger.address = C`, `trigger.data = {fraud_proof: true, sentByPeer: <copied>}`.
4. If C's unit gets included/validated first (race condition on the DAG), the `fraud_proof` case's condition `is_valid_signed_package(trigger.data.sentByPeer, $bInitiatedByA ? $addressA : $addressB)` succeeds (signature by B is valid regardless of who submitted the trigger), and the `payment` message sends the entire remaining channel balance to `trigger.address` = C, stealing the funds from both A and B.
