### Title
`repository_owner`/`repository.full_name` split lets an attacker use one org's (secret-less) signature to write labels onto another org's `ReviewStack#pull_request` via `LabelCapturingHandler` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates the webhook using `repository_owner`, which is read from `params.dig('repository','owner','login')`, but `LabelCapturingHandler#repository` resolves the target repository from the independent `params.repository.full_name` field. Since both fields are attacker-controlled JSON in the same forged payload and are never cross-checked, an attacker can pick a "no-secret" org for `repository.owner.login` (making `verify_webhook_signature` trivially return `true`) while pointing `repository.full_name` at a victim org/repo, causing the handler to persist attacker-chosen labels onto that victim's `ReviewStack`'s `PullRequest`.

### Finding Description
The broken binding the code implicitly assumes is:
`repository_owner (used to select the GitHubApp/secret for HMAC verification) == owner(repository.full_name) (used to resolve the Repository/Stack actually mutated)`

In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected org has no `webhook_secret` configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

Meanwhile `LabelCapturingHandler#repository` resolves the mutated `Repository`/`Stack` from a *different* payload field, `params.repository.full_name`, entirely disconnected from `repository_owner`:
```ruby
def repository
  @repository ||=
    Shipit::Repository.from_github_repo_name(params.repository.full_name) || NullRepository.new
end
``` [3](#0-2) 

`Repository.from_github_repo_name` simply splits the string on `/` and looks up by owner/name with no relation back to `repository_owner`:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [4](#0-3) 

Exploit flow:
1. Attacker finds/creates an org configured in Shipit with no `webhook_secret` (a "no-secret org"), e.g. `attacker-org`.
2. Attacker crafts a raw `pull_request` webhook JSON body with `action: "unlabeled"`, `repository.owner.login: "attacker-org"`, but `repository.full_name: "victim-org/victim-repo"` (the real, secret-protected victim repo), and any `X-Hub-Signature` header (irrelevant, since verification is skipped when no secret is set for `attacker-org`).
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, which has no `webhook_secret`, so `verify_webhook_signature` returns `true` regardless of the actual signature — the request passes authentication.
4. `Shipit::Webhooks.for_event('pull_request')` dispatches to `LabelCapturingHandler#process`. Its `repository` method looks up `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")`, the real victim repository, and `stack` resolves the matching `ReviewStack` via `ReviewStackAdapter`.
5. `capture_labels` runs `pull_request.update!(labels: params.pull_request.labels.map(&:name))`, so the labels array in the forged payload is persisted onto the *victim*'s `PullRequest` record: [5](#0-4) 
6. `ReviewStack#env` later injects these attacker-chosen labels as uppercased `"true"` environment variables into the victim stack's deploy/env context: [6](#0-5) . If the victim stack's `blocking_statuses`/deploy spec keys off such environment/label-driven state (e.g., via `deploy_spec.rb` or `commit.rb` blocking-status logic), this label injection can influence gating decisions on a stack the attacker never authenticated against.

Why existing guards fail: `drop_unhandled_event` only checks the event type exists a handler for it; `ExplicitParameters` schema in `LabelCapturingHandler.params` only validates presence/types of fields, not cross-consistency between `repository.owner.login` and `repository.full_name`; there is no code anywhere that asserts `repository_owner == Repository owner used by the handler`. The signature-picking logic and the repository-resolution logic are two independent reads of the same untrusted JSON body.

### Impact Explanation
An unauthenticated (with respect to the victim's secret) attacker can cause a write to a victim repository's `PullRequest#labels` and thereby to `ReviewStack#env`, purely by owning/controlling any Shipit-configured org that has no `webhook_secret` set. This is a cross-tenant state mutation: a request that only proves knowledge of (or absence of) `attacker-org`'s secret ends up mutating `victim-org`'s database record. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." The blast radius extends to any repository/stack reachable by guessing/enumerating `owner/repo` full names, since `Repository.from_github_repo_name` performs a global `find_by` with no scoping to the authenticated org.

### Likelihood Explanation
Preconditions: (1) at least one org configured in Shipit's GitHub app config without a `webhook_secret` (common in multi-org Shipit deployments where only some orgs enable webhook secrets), (2) a victim `ReviewStack` with an attached `PullRequest` exists for the targeted `repository.full_name`. Attacker cost is minimal — a single crafted HTTP POST to `/webhooks` with a `pull_request`/`X-Github-Event` header and arbitrary body; no valid signature, GitHub credentials, or Shipit session/API token needed. It is fully repeatable against any repository whose owner/name the attacker can guess.

### Recommendation
Verify signatures using the same organization that owns the repository the handler will actually mutate, or better, bind `repository_owner` derivation and repository resolution to the identical, single parsed value, then re-validate inside each handler that the resolved `Repository#owner` matches `repository_owner` used at verification time before performing any mutation. Alternatively, require every configured GitHub org/app to have a mandatory `webhook_secret` (remove the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`) so no org can be used as a signature-bypass vector.

### Proof of Concept
Minitest plan (no live GitHub):
1. Configure `Shipit.github_config` (or override `Shipit.github`) with two orgs: `attacker-org` (no `webhook_secret`) and `victim-org` (with a `webhook_secret`).
2. Create `victim-org/victim-repo` `Repository`, a `ReviewStack` under it, and an associated `PullRequest` with `labels: []`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, an arbitrary/invalid `X-Hub-Signature`, and JSON body: `action: "unlabeled"`, `repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" }`, `pull_request: { ..., labels: [{name: "MALICIOUS_FLAG"}] }`.
4. Assert response is `200 OK` (signature check passed via `attacker-org`'s missing secret) — i.e., assert `repository_owner == "attacker-org"` while the record mutated belongs to `Repository.from_github_repo_name("victim-org/victim-repo")`, proving the two are unequal.
5. Reload the victim `PullRequest` and assert `pull_request.labels == ["MALICIOUS_FLAG"]`, proving cross-tenant write.
6. Optionally assert `review_stack.env["MALICIOUS_FLAG"] == "true"` to demonstrate downstream env injection.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
