### Title
Webhook signature verification is scoped to the wrong GitHub organization, allowing cross-organization/cross-repository forged events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The Lombard report describes an approver that authenticates/acts using the wrong Cubist session — signing requests were verified/approved against `clientSession` even when they belonged to funds that required `noMixClientSession`, breaking the binding between "the session that authorizes" and "the funds actually being acted on." The same class of bug exists in Shipit's webhook pipeline: the field used to select *which organization's secret verifies the signature* is not cryptographically or programmatically bound to the field used to *decide which repository/stack the event actually acts on*.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/organization config (and thus the HMAC `webhook_secret` used to verify `X-Hub-Signature`) using `repository_owner`, which is read straight out of the untrusted, unsigned-at-this-point JSON body: [1](#0-0) [2](#0-1) 

Once the signature check passes, event handlers determine *which repository/stack to mutate* using a different field of the very same payload — `repository.full_name` — with no check that its owner segment matches the `repository_owner` value that was used to select the verifying secret: [3](#0-2) [4](#0-3) 

In a multi-org deployment (`config/secrets.yml` with per-organization `github` sections, as documented), `Shipit.github(organization: repository_owner)` resolves to a distinct `GitHubApp` instance with its own `webhook_secret`, per `lib/shipit/github_app.rb`: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used to pick the target repository/stack for the write) are independent, attacker-controlled strings in the same JSON body, anyone who can produce a valid signature for **any one** configured organization (e.g., they legitimately administer a repository/webhook in Org A, or that org's `webhook_secret` is blank per `verify_webhook_signature`'s `return true unless webhook_secret` short-circuit) can set `repository.owner.login = "OrgA"` while setting `repository.full_name = "OrgB/some-repo"`. The signature check passes against Org A's secret, but the handler then acts on a repository/stack belonging to Org B — a repository the attacker never authenticated against.

This breaks exactly the binding class called out by the report: *the organization whose credential authenticated the request* ≠ *the repository the code actually writes to*.

### Impact Explanation
Depending on the handler invoked, this enables unauthorized cross-repository/cross-organization writes: forged `push` events queue `GithubSyncJob` for an arbitrary stack, forged `pull_request`/`closed` events call `review_stack.archive!` on another org's review stack, and forged `status`/`check_suite` events can inject fabricated CI state that Shipit's merge/deploy logic consumes to gate deploys. This crosses the "cross-repository writes" / "unauthorized deploy" impact bar because it lets a party trusted for one organization's webhooks manipulate state belonging to a different, unrelated organization configured on the same Shipit instance.

### Likelihood Explanation
Exploitability requires a multi-organization Shipit deployment (explicitly documented and supported via `docs/setup.md`'s "Using Multiple Github Applications" section) where the attacker already controls (or has leaked) one organization's webhook secret — a realistic scenario since webhook secrets are typically visible to anyone with admin access on the sending repository, a much lower bar than access to every other organization hosted on the same Shipit instance.

### Recommendation
After verifying the signature, re-derive the organization from the same field used to resolve the target repository (`repository.full_name`'s owner segment) and reject the request if it does not match the organization/secret that produced a valid signature. Alternatively, have handlers resolve the repository/stack through the already-verified `repository_owner` instead of independently re-parsing `repository.full_name`, so a single verified field drives both signature selection and the write target.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md` multi-org config).
2. As an attacker who legitimately controls a repository/webhook under `OrgA` (and therefore knows `OrgA`'s `webhook_secret`), craft a `pull_request` event body where `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/target-repo"`, and all other required fields for `ClosedHandler`/`opened_handler` etc.
3. Sign the raw JSON body with `OrgA`'s `webhook_secret` to compute `X-Hub-Signature`, and POST to `/webhooks` with `X-Github-Event: pull_request`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature.
5. `ClosedHandler#repository` resolves `Shipit::Repository.from_github_repo_name("OrgB/target-repo")`, and the handler archives/mutates state for a repository the attacker was never authorized against under `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
