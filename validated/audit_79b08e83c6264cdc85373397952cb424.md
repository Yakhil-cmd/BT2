### Title
Block-Hash Grinding Biases Proposer-List PRNG Seed, Enabling Unauthorized Reward Redistribution — (`kaiax/valset/impl/getter_proposers.go`)

---

### Summary

`generateProposerListWeighted` and `generateProposerListUniform` derive their entire PRNG seed from the Istanbul `HeaderHash` of the "proposer update block." The proposer of that boundary block controls transaction selection and ordering, giving them a grinding surface to search for a block hash that places their address disproportionately often in the next interval's proposer list. Because block rewards (KAIA) are paid per proposed block, a biased proposer list directly constitutes unauthorized reward redistribution.

---

### Finding Description

Every `ProposerUpdateInterval` blocks, `calcBaseProposers` fetches the header of the update block and passes its hash to the list-generation functions:

```go
// kaiax/valset/impl/getter_proposers.go:40-62
updateHeader := v.Chain.GetHeaderByNumber(updateNum)
...
list = generateProposerListUniform(qualified, updateHeader.Hash())
// or
list = generateProposerListWeighted(qualified, si, useGini, updateHeader.Hash())
```

Both functions convert that hash to a 60-bit integer seed via `HashToSeedLegacy` and feed it into Go's `math/rand` LCG, then use `ShuffledListLegacy` to permute the proposer list:

```go
// kaiax/valset/impl/getter_proposers.go:267-268
seed := valset.HashToSeedLegacy(blockHash)
return valset.NewAddressSet(proposerList).ShuffledListLegacy(seed)
```

`HashToSeedLegacy` keeps only the top 60 bits of the first 8 bytes of the hash:

```go
// kaiax/valset/address_set.go:218-221
func HashToSeedLegacy(hash common.Hash) int64 {
    n8 := binary.BigEndian.Uint64(hash[:8])
    return int64(n8 >> 4)
}
```

The Istanbul `HeaderHash` is the RLP hash of the header with the proposer seal retained but committed seals stripped:

```go
// consensus/istanbul/sealer.go:290-294
func (m *IstanbulSealer) HeaderHash(header *types.Header) common.Hash {
    if filtered := istanbulFilteredHeader(header, true); filtered != nil {
        return RLPHash(filtered)
    }
    return RLPHash(header)
}
```

The header includes `TxHash`, `ReceiptHash`, `Root` (state root), `GasUsed`, `Bloom`, `Time`, `TimeFoS`, and the proposer's own `Seal`. All of these change when the proposer includes or excludes transactions, or reorders them. The proposer therefore has a large, legitimate-looking search space to grind for a hash that produces a favorable permutation.

---

### Impact Explanation

The proposer list governs which validator proposes each block for the next `ProposerUpdateInterval` blocks. Block rewards (minting amount M, plus deferred fees) are paid to the proposer via `FinalizeState → spec.Rewards → state.AddBalance`:

```go
// kaiax/reward/impl/blockstate.go:53-55
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)
}
```

A validator who appears `k` extra times in a 100-slot proposer list receives `k` additional block rewards they are not entitled to. With a minting amount of 6.4 KAIA per block and a typical `ProposerUpdateInterval` of 3600 blocks, even a modest bias of +5 extra slots yields ~32 KAIA of unauthorized reward per interval. The corrupted value is the `spec.Rewards` map entry for the attacker's reward address, which is inflated relative to the honest distribution.

---

### Likelihood Explanation

The attack requires the adversary to be the proposer of the update block (block number `U = RoundDown(N-1, ProposerInterval)`). Under `WeightedRandom` policy, any qualified validator can be scheduled as proposer of that block. Once scheduled, the attack is:

1. **Computationally cheap**: the proposer list computation is a deterministic, in-memory shuffle; the attacker can evaluate thousands of candidate transaction subsets per second.
2. **Unprivileged within role**: transaction selection is a normal proposer right; no extra keys or permissions are needed.
3. **Undetectable**: the resulting block is fully valid; other validators verify state root, tx root, and committed seals, but not whether the proposer chose the "fairest" transaction set.
4. **Repeatable**: the attacker benefits every interval in which they happen to propose the update block.

This is active on all pre-Randao deployments (`WeightedRandom` before and after Kore hardfork). After the Randao hardfork, `SelectRandaoProposer` uses BLS-based `prevMixHash`, which is not grindable by a single validator.

---

### Recommendation

1. **Short-term (pre-Randao chains):** Replace `updateHeader.Hash()` as the PRNG seed with a value the proposer cannot influence, such as the hash of a block several intervals in the past (commit-reveal delay), or XOR the hashes of multiple recent blocks.
2. **Long-term:** Accelerate migration to the Randao hardfork (`SelectRandaoProposer` / `SelectRandaoCommittee`), which already uses a cryptographically sound BLS-based `prevMixHash` that requires collusion of all BLS key holders to bias.
3. **Immediate mitigation:** Increase `ProposerUpdateInterval` to reduce the frequency of the attack surface, and monitor for anomalous proposer-frequency distributions.

---

### Proof of Concept

**Setup:** `WeightedRandom` policy, `ProposerUpdateInterval = 3600`, 4 validators `[A, B, C, D]` with equal stake (each gets ~25 slots). Validator A is scheduled to propose block `U = 3600` (the update block for interval `[3601, 7200]`).

**Attack steps:**

1. Validator A builds candidate block `U` with transaction subset `T₁`. Compute `hash₁ = HeaderHash(block_U_T1)`. Compute `seed₁ = HashToSeedLegacy(hash₁)`. Run `generateProposerListUniform` → A appears 24 times.

2. Validator A tries subset `T₂` (drop one low-fee tx, add a self-transfer). Compute `hash₂`. Run shuffle → A appears 31 times.

3. Repeat until A finds a subset where A appears ≥ 35 times (≥ 10 extra slots).

4. Validator A broadcasts the block with that transaction set. All other validators accept it (state root, tx root, committed seals are all valid).

**Result:** For the next 3600 blocks, A proposes ~35 blocks instead of ~25. At 6.4 KAIA/block, A earns ~64 extra KAIA per interval without any detectable protocol violation.

**Relevant code path:**

```

  → updateHeader = GetHeaderByNumber(3600)          // attacker-controlled hash
  → generateProposerListUniform(qualified, updateHeader.Hash())
      → seed = HashToSeedLegacy(blockHash)          // 60-bit seed from block hash
      → ShuffledListLegacy(seed)                    // LCG shuffle of proposer list
  → proposerListCache.Add(3600, list)               // cached for entire interval

// ShuffledListLegacy returns a shuffled list using the legacy shuffling algorithm.
// This is used for backward compatibility with the old committee & proposer selection.
func (as *AddressSet) ShuffledListLegacy(seed int64) []common.Address {
	as.mu.RLock()
	defer as.mu.RUnlock()

	shuffled := make([]common.Address, len(as.list))
	copy(shuffled, as.list)

	r := rand.New(rand.NewSource(seed))
	for i := range shuffled {
		j := r.Intn(len(shuffled))
		shuffled[i], shuffled[j] = shuffled[j], shuffled[i]
	}
	return shuffled
```

func istanbulFilteredHeader(h *types.Header, keepSeal bool) *types.Header {
	newHeader := types.CopyHeader(h)
	if len(newHeader.Extra) < IstanbulExtraVanity {
		return nil
	}
	var istanbulExtra *IstanbulExtra
	err := rlp.DecodeBytes(newHeader.Extra[IstanbulExtraVanity:], &istanbulExtra)
	if err != nil {
		return nil
	}

	if !keepSeal {
		istanbulExtra.Seal = []byte{}
	}
	istanbulExtra.CommittedSeal = [][]byte{}

	payload, err := rlp.EncodeToBytes(istanbulExtra)
	if err != nil {
		return nil
	}
	newHeader.Extra[IstanbulExtraVanity-1] = 0
	newHeader.Extra = append(newHeader.Extra[:IstanbulExtraVanity], payload...)
	return newHeader
}
```

func selectRandomCommittee(qualified *valset.AddressSet, committeeSize uint64, prevBlockHash common.Hash, currProposer, nextDistinctProposer common.Address) []common.Address {
	qualified = qualified.Copy()
	qualified.Remove(currProposer)
	qualified.Remove(nextDistinctProposer)

	shuffled := qualified.ShuffledListLegacy(seed)

	committee = append(committee, shuffled[:committeeSize-2]...)
