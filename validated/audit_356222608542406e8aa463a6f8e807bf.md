### Title
Webhook signature verification binds the wrong identifier to team/repository mutations, allowing escalation into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`, `lib/shipit/github_app.rb`)

### Summary
The reported bug class is "two constants that should refer to the same on-chain object are declared from different sources and silently diverge." The equivalent binding in Shipit is: *the GitHub organization whose webhook secret authenticated a request* should equal *the organization actually authorized to mutate the `Team`/`Membership` records driving `Shipit.github_teams` authorization*. These are read from different, independently-controlled fields of the same JSON body, and the second is never re-validated against the first.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/organization's secret to check the HMAC signature against using attacker-supplied payload fields: [1](#0-0) [2](#0-1) 

For the `membership` event there is no `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')` — also attacker-controlled JSON.

Crucially, `GithubApp#verify_webhook_signature` trivially passes whenever the selected organization has **no `webhook_secret` configured**, which the setup docs explicitly document as *optional*: [3](#0-2) [4](#0-3) 

Shipit explicitly supports multiple GitHub App configurations per organization, each with its own independent `webhook_secret`: [5](#0-4) 

Once past `verify_signature`, `MembershipHandler#process` trusts `params.team.id`, `params.organization.login`, and `params.member.login` from the same body to mutate the global `Team`/`Membership` tables that back authorization: [6](#0-5) 

`find_or_create_team!` only sets `team.organization` at creation time (inside the `find_or_create_by!` block); for a team that already exists (i.e. any real, previously-synced GitHub team, including ones listed in `Shipit.github_teams`), the `organization` field is never re-checked against `params.organization.login` on subsequent webhook deliveries. This means the "authenticating organization" (used only to select which secret gates the request, and trivially bypassed when that org has no secret) is never bound to the "team being written" (identified purely by numeric `github_id`, independent of which org's secret validated the request).

`Shipit.github_teams` authorization is enforced purely from these `Team`/`Membership` rows: [7](#0-6) [8](#0-7) 

### Impact Explanation
If any organization configured in `secrets.yml` is left without a `webhook_secret` (an explicitly documented, optional setting), an unprivileged external attacker can:
1. POST a forged `membership` webhook to `/webhooks` claiming `organization.login` = the org lacking a secret (signature check is bypassed by the `return true unless webhook_secret` short-circuit).
2. Set `team.id` to the numeric GitHub ID of a team already listed in `Shipit.github_teams` (any team previously synced into Shipit's DB, regardless of which org it actually belongs to), and `action: "added"`, `member.login` = the attacker's own GitHub login.
3. `MembershipHandler` finds the pre-existing `Team` row by `github_id` and calls `team.add_member(member)`, creating a `Membership` linking the attacker's `User` to that authorized team — without ever validating GitHub team membership.
4. The attacker completes a normal OAuth login as themselves; `User#authorized?` now returns `true` because of the forged `Membership`, granting full access to Shipit (deploy, rollback, task execution, stack management) as though they were a legitimate team member.

This is a direct escalation into `Shipit.github_teams` authorization — one of the explicitly listed High-impact outcomes — achieved without any Shipit session, API token, or GitHub write access, purely by exploiting the mismatch between the field used to select/skip webhook-signature verification and the field used to identify the `Team` being mutated.

### Likelihood Explanation
Requires a deployment-specific precondition (at least one configured GitHub organization without a `webhook_secret`), but this is a documented, supported, and plausible configuration (the field is explicitly optional in `docs/setup.md` and the multi-org config format is a first-class supported feature). Given that precondition, the exploit itself needs no credentials, no repository access, and no privileged account — only knowledge of a target team's numeric GitHub ID, which can be obtained from any legitimate `membership` webhook payload the app previously processed logs of, or from the target org's public API.

### Recommendation
- Do not allow `verify_webhook_signature` to unconditionally return `true` for organizations with a blank `webhook_secret`; require an explicit `Shipit.allow_unsigned_webhooks` opt-in instead of silent bypass.
- In `MembershipHandler`, validate that `params.organization.login` matches the `Team#organization` on every delivery (not only at creation), and reject/log mismatches.
- Bind the organization used for signature verification to the organization asserted inside the payload for all mutating handlers (`PushHandler`, `MembershipHandler`, `ClosedHandler`, etc.), rejecting webhooks where `repository.owner.login` / `organization.login` doesn't match the resolved `Repository`/`Team`'s recorded organization.

### Proof of Concept
1. Deployment config (`secrets.yml`) has two orgs configured per `docs/setup.md`'s multi-org example: `SecureOrg` (with `webhook_secret` set) and `OpenOrg` (webhook_secret left blank, as documented "optional").
2. Attacker sends:
```
POST /webhooks
X-Github-Event: membership
{
  "action": "added",
  "team": { "id": <ID_OF_A_SHIPIT_GITHUB_TEAM>, "name": "Shopify/developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "OpenOrg" },
  "member": { "login": "attacker-github-login" }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OpenOrg")`; since `OpenOrg` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
4. `MembershipHandler#process` finds the existing `Team` by `github_id` and adds `attacker-github-login` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
5. Attacker logs in via `/github/auth/github` as `attacker-github-login`; `User#authorized?` now returns `true` (`app/models/shipit/user.rb:80-82`), granting full Shipit access. [9](#0-8)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
