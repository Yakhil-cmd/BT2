### Title
Cross-organization webhook forgery lets a payload's `repository.full_name` write to a stack outside the org that "authenticated" it - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's secret to validate a webhook against using `repository.owner.login` (or `organization.login`) taken from the *unauthenticated* JSON body, then hands the same, fully attacker-controlled body to event handlers that instead key off `repository.full_name` (a separate, never cross-checked field) to decide which `Stack`/`Repository`/`Commit` to mutate. Because these two identity fields are never bound together, and because `verify_webhook_signature` trivially returns `true` whenever the selected organization has no `webhook_secret` configured (a state the docs call "optional"), an attacker can pick an org with no secret purely to satisfy the signature gate while pointing `repository.full_name` at a completely different, sensitive repository tracked by the same Shipit instance.

### Finding Description
`WebhooksController` computes the signing organization from the payload itself, not from any authenticated channel: [1](#0-0) [2](#0-1) 

The signature check itself is bypassed entirely (returns `true`) if that organization has no configured `webhook_secret`: [3](#0-2) 

`webhook_secret` is explicitly documented as optional per organization, including in multi-org setups: [4](#0-3) [5](#0-4) 

After the (possibly vacuous) signature check passes, the raw, attacker-supplied JSON is dispatched unchanged to handlers: [6](#0-5) 

Every handler resolves the *actual* target repository/stack from `repository.full_name`, a field independent of `repository.owner.login`: [7](#0-6) [8](#0-7) 

`StatusHandler` is even less scoped — it matches commits purely by `sha`, with no repository check at all: [9](#0-8) 

The equality this breaks is: *organization that authenticated the request* (`repository.owner.login`, validated — or trivially accepted — against a specific org's secret) **≠** *repository that is written* (`repository.full_name`, used unchecked by the handler to select the `Stack`/`Commit` to mutate). No code anywhere enforces that `repository.full_name` belongs to `repository_owner`.

`push` triggers `Stack#sync_github`, which is wired to run automatically: [10](#0-9) 

### Impact Explanation
On any Shipit deployment configured with multiple GitHub organizations (a documented, supported configuration) where at least one configured organization omits `webhook_secret` (explicitly documented as optional), an attacker with **zero credentials** can:
- Set `repository.owner.login`/`organization.login` to the org lacking a secret (satisfying `verify_signature` for free), and
- Set `repository.full_name` (and, for `status`, just `sha`) to point at any other tracked repository/commit in the same Shipit instance.

This achieves unauthenticated cross-repository writes: forcing a `push` re-sync (`GithubSyncJob`) on an unrelated stack, injecting forged commit `Status` records that can flip a commit's CI/deployability state (`Commit#create_status_from_github!`), or driving PR-based review-stack handlers (open/close/label/archive) for repositories the payload never legitimately authenticated for. Forged CI status can make an otherwise-unsafe commit appear deployable, which can lead to an unauthorized deploy on continuously-deployed stacks. This matches the report's Critical/High criteria (unauthorized deploy, cross-repository writes).

### Likelihood Explanation
Requires no privileged credential — this is exactly the unprivileged-attacker class the ruleset targets. The only precondition is a deployment configuration with more than one GitHub org where one has no `webhook_secret`, which the project's own setup docs present as a normal, supported, optional configuration rather than a hardening requirement. Given webhook endpoints are, by design, internet-reachable and unauthenticated at the transport layer (that's the entire purpose of `X-Hub-Signature`), this is straightforward to exploit once such a configuration exists.

### Recommendation
Bind the two identity fields together rather than trusting them independently: after selecting `github_app` via `repository_owner`, require that `repository.full_name`'s owner segment matches `repository_owner` (or the `organization.login`) before dispatching to handlers, and reject the payload otherwise. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for multi-org configurations; instead fail closed (or require all configured orgs to set a secret) so an org without a configured secret cannot be used as a signature bypass for other orgs' repositories.

### Proof of Concept
Given a Shipit config with two orgs, `openorg` (no `webhook_secret`) and `secureorg` (secret configured, owns `secureorg/prod-app` tracked by Shipit):

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (any/garbage value)

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "openorg" },
    "full_name": "secureorg/prod-app"
  }
}
```

`repository_owner` resolves to `"openorg"`; `Shipit.github(organization: "openorg").verify_webhook_signature` returns `true` unconditionally because `openorg` has no `webhook_secret`. `PushHandler` then resolves `stacks` via `Repository.from_github_repo_name("secureorg/prod-app")` and calls `sync_github(expected_head_sha: ...)` on the `secureorg` stack — a write to a repository the request never actually authenticated against.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
