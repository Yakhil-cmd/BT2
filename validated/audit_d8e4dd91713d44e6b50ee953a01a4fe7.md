### Title
Cross-organization Team hijack via `Team.github_id` collision in membership webhook - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up teams solely by `github_id`, which is only unique within a single GitHub organization's numbering space, not globally. Because `verify_signature` authenticates the request against the organization asserted in the payload (`params.organization.login`), not against the organization that owns the matched `Team` row, an attacker who controls a real organization can emit a validly-signed `membership` webhook whose `team.id` collides with a pre-existing `Team.github_id` belonging to a different organization, causing that victim `Team`'s membership list to be mutated.

### Finding Description
The broken binding is: `organization that signed the webhook (params.organization.login, verified via Shipit.github(organization: repository_owner).verify_webhook_signature)` == `organization owning the Team row mutated by Team.find_or_create_by!(github_id: params.team.id)`. This equality is never checked.

Code path:
- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and verifies the signature using `Shipit.github(organization: repository_owner)` [2](#0-1) . For `membership` events there is no `repository` key, so `repository_owner` resolves to `params.organization.login` — i.e., the attacker's own org, ORG_A — and the signature check legitimately passes using ORG_A's real `webhook_secret`.
- `MembershipHandler#process` then calls `find_or_create_team!`, which executes `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [3](#0-2) . If a `Team` row with that `github_id` already exists (created earlier by a legitimate ORG_B membership event), `find_or_create_by!` returns the **existing** row and the initialization block (which would set `organization`) is **not** executed, so the returned team's `organization` stays `ORG_B`.
- `process` then calls `team.add_member(User.find_or_create_by_login!(params.member.login))` [4](#0-3) , writing a `Membership` linking the attacker's GitHub login to ORG_B's `Team`.
- The DB schema confirms `github_id` has no uniqueness constraint; only `[organization, slug]` is unique [5](#0-4) , so two `Team` rows across different organizations can legitimately hold identical `github_id` values with no DB-level prevention, and the lookup by `github_id` alone cannot disambiguate them.
- If the hijacked `Team` is one of `Shipit.github_teams` (built by `github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }` [6](#0-5) ), the attacker's user gains membership in that team, and `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6)  — granting the attacker authorization system-wide.

None of the existing guards prevent this: `verify_signature` only proves the payload came from *an* org whose secret matches, not that it's the org owning the targeted `Team`; the `ExplicitParameters` schema on `MembershipHandler` only validates types/presence, not cross-record ownership [8](#0-7) ; and `find_or_create_by!` semantics silently reuse any row matching the `github_id`, regardless of organization.

### Impact Explanation
An attacker who legitimately administers ORG_A can, using ORG_A's own valid webhook secret, cause a `Membership` write against a `Team` belonging to victim ORG_B, without ORG_B's webhook secret ever being involved. If the targeted `Team` is registered in `Shipit.github_teams`, this directly escalates the attacker into Shipit's authorization group, granting `authorized?` system-wide (deploy/admin capability depending on how the host app gates access). This matches "escalation into `Shipit.github_teams` authorization" (High) and arguably crosses into "a payload for one repository/team mutating another's ... team" (Critical), since it is a genuine cross-tenant write triggered by another tenant's correctly-signed request. The action is repeatable per team-id/action pair and could be scripted to add/remove arbitrary users (subject to `User.find_or_create_by_login!` resolving a real GitHub login) into the victim's team.

### Likelihood Explanation
Exploitation requires: (1) a pre-existing victim `Team` row with a known `github_id` (these are visible/guessable, e.g., via public GitHub team IDs, which are sequential and org-scoped but overlap across orgs frequently since ids are a shared global counter allocated per creation across all of GitHub, not per-org — so collisions are far from rare over large id ranges); (2) the attacker being able to create/rename a team in their own org to get GitHub to assign or otherwise have a team whose `id` equals the victim's target `github_id` — GitHub team IDs are allocated by GitHub itself as a global auto-increment at creation time, not attacker-chosen, which somewhat limits attacker control, but with enough team creation/deletion churn in a large org an attacker could eventually land on many candidate ids, and the search space could be probed by triggering membership webhooks and observing effects (though effects aren't directly observable by the attacker without an oracle). The attacker's cost is only ownership of a GitHub org, which is free to obtain, and no privileged Shipit credentials are needed at any point — the “Preconditions” assumed in the question (existing victim team, attacker eventually holding a colliding team id) are the correct precondition set. Given no ownership/ACL check exists in the code, the theoretical exploit is confirmed to be reachable; practical likelihood depends on GitHub's actual id-collision rate across organizations, which is outside this engine's control but plausible given IDs are shared across all GitHub orgs.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization` instead of `github_id` alone, e.g. change `find_or_create_team!` to `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally consider adding a uniqueness validation/index on `github_id` scoped to `organization` (or a composite unique index) to prevent silent record reuse across tenants. If a `Team` with the same `github_id` exists under a different organization, this should raise/log rather than silently reusing the victim's row.

### Proof of Concept
minitest plan (models/webhooks test, no live GitHub):
```ruby
test "MembershipHandler does not hijack a team belonging to a different organization on github_id collision" do
  victim_team = Team.create!(github_id: 42, organization: 'victim-org', slug: 'core', name: 'Core', api_url: 'https://example.com/victim-org/core')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 42, 'name' => 'Attacker Team', 'slug' => 'attacker-team', 'url' => 'https://example.com/attacker-org/attacker-team' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker-login' }
  }

  User.any_instance.stubs(:github_user=) # or stub Shipit.github.api.user to avoid live call
  Shipit::Webhooks::Handlers::MembershipHandler.call(payload)

  victim_team.reload
  # Assert the binding is broken: signer org != team's actual org, yet team was mutated
  assert_equal 'victim-org', victim_team.organization
  assert_includes victim_team.members.map(&:login), 'attacker-login'
  # No new Team was created for attacker-org despite a distinct organization login
  assert_equal 1, Team.where(github_id: 42).count
end
```
Both sides of the equality (`repository_owner` used to verify the signature = `'attacker-org'`; `Team#organization` mutated = `'victim-org'`) diverge, confirming the vulnerability.
