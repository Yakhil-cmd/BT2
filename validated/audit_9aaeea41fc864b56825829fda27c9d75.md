### Title
Cross-tenant team membership grant via unverified `team.id`/`organization` collision in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id`, and `#process` unconditionally calls `team.add_member(member)` for the `added` action without ever checking that the payload's `organization.login` matches the existing `Team#organization`. An attacker who controls a webhook-signing organization already onboarded to a multi-tenant Shipit instance can forge a correctly-signed `membership` event whose `team.id` collides with another organization's real, pre-existing `Team#github_id`, causing an arbitrary attacker-controlled GitHub user to be added as a member of that unrelated team — with the `name`/`slug`/`url` payload fields being irrelevant to the outcome.

### Finding Description
The broken binding is: `Team.find_or_create_by!(github_id: params.team.id)` returned record's `organization` **should equal** `params.organization.login` before `team.add_member(member)` executes, but no such equality is ever checked [1](#0-0) .

Trace: `WebhooksController#verify_signature` resolves the signing organization via `repository_owner`, which for a `membership` event (no `repository` key in payload) falls back to `params.dig('organization', 'login')` [2](#0-1) . It then verifies the signature using `Shipit.github(organization: repository_owner)`, i.e. against the webhook secret configured for **that same attacker-supplied `organization.login`** [3](#0-2) . So an attacker who administers their own onboarded GitHub organization can produce a validly-signed payload where `organization.login` is their own org, while `team.id` is set to the `github_id` of a `Team` row that actually belongs to a completely different organization (already synced from a legitimate prior webhook).

In `find_or_create_team!`, `Team.find_or_create_by!(github_id: params.team.id) { |team| ... }` matches the existing row purely on `github_id`; because the row already exists, the block (which would set `team.organization = params.organization.login` and overwrite name/slug/url) never executes [4](#0-3) . The returned `team` is the real, untouched target `Team` (correct `organization`, `name`, `slug`). `process` then does `team.add_member(member)` where `member = User.find_or_create_by_login!(params.member.login)` — the attacker fully controls this login [5](#0-4) . `Team#add_member` simply appends the member with no ownership check [6](#0-5) .

This membership is not cosmetic: `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, and `Shipit.github_teams` is built from `Shipit.github_team` configuration via `Team.find_or_create_by_handle` [7](#0-6) [8](#0-7) . If the colliding `github_id` belongs to one of the teams configured in `Shipit.github_teams`, `force_github_authentication` in `app/controllers/concerns/shipit/authentication.rb` will grant the attacker's forged member access to the entire application [9](#0-8) .

None of the existing guards prevent this: `verify_signature` only proves the request came from *some* org the attacker controls, not that the `team.id`/`organization` pair is internally consistent; the `ExplicitParameters` schema only enforces types (`Integer`, `String`), not cross-field integrity; and `find_or_create_by!` has no uniqueness/ownership scoping on `organization` when matching by `github_id`.

### Impact Explanation
A malicious but legitimately onboarded GitHub organization admin can grant arbitrary GitHub logins membership in a `Team` belonging to a different organization/tenant, without that organization's webhook secret. If the target team is one referenced by `Shipit.github_teams`, this directly escalates an attacker-controlled user into `Shipit.github_teams` authorization, granting them login access to the whole Shipit deployment and to protected actions (deploys, rollbacks, task management) — matching the "escalation into `Shipit.github_teams` authorization" High-severity category, and arguably Critical since it can be used to grant unauthorized access resulting in unauthorized deploys/rollbacks by the newly-authorized attacker identity. The attack is repeatable against any `github_id` the attacker can guess or enumerate (sequential small integers, as the fixtures show teams with ids 1, 2 [10](#0-9) ), and against any tenant sharing the multi-tenant Shipit instance.

### Likelihood Explanation
Preconditions: the attacker must control (or register) at least one GitHub organization already configured in Shipit's multi-tenant `secrets`/GitHub App setup so that `Shipit.github(organization: attacker_org)` resolves and signature verification succeeds; the target `Team#github_id` must already exist in Shipit's DB (synced from a prior legitimate webhook, which is the normal steady state for any active org); and `github_id` values are small sequential integers, easily guessable or enumerable via GitHub's public team API responses. No Shipit session, API token, or secret of the *target* organization is required — only the attacker's own valid webhook secret for their own org. This is a low-cost, fully repeatable attack requiring only crafting one JSON POST per target.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` **and** `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify in `process` that the resolved `team.organization == params.organization.login` before calling `add_member`/`members.delete`, rejecting the event (or raising) otherwise so that a `github_id` collision across organizations cannot mutate/extend membership of a team belonging to a different tenant.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb`, similar to existing `:membership` tests):
1. Use fixture `shipit_teams(:cyclimse_cooks)` (`github_id: 2`, `organization: 'cyclimse'`, `slug: 'cooks'`, `name: 'Cooks'`).
2. Sign and POST a `membership` webhook as organization `shopify` (attacker-controlled org) with `action: 'added'`, `team: { id: 2, name: 'Attacker Garbage', slug: 'attacker-garbage', url: 'https://evil.example.com' }`, `organization: { login: 'shopify' }`, `member: { login: 'attacker_controlled_user' }`.
3. Assert response is `:ok`.
4. Reload `shipit_teams(:cyclimse_cooks)` and assert `team.organization == 'cyclimse'` and `team.name == 'Cooks'` and `team.slug == 'cooks'` (unchanged — proving the create block was skipped, i.e. `team.organization == params.organization.login` is **false** yet processing continued).

Assert `assert_difference -> { Membership.count }, 1` around the POST, and assert `Shipit::Team.find(shipit_teams(:cyclimse_cooks).id).members.exists?(login: 'attacker_controlled_user')` is true — proving an attacker from `shopify` gained membership in `cyclimse`'s team despite the mismatched organization/name/slug/url fields. # frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
