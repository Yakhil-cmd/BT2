### Title
Membership webhook lets an attacker's own org grant Shipit `Shipit.github_teams` membership to a Team belonging to a different organization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` only authenticates that the payload's `organization.login` belongs to a legitimately configured GitHub App/secret; it never checks that the payload's `team.id` actually belongs to that same organization. `MembershipHandler#find_or_create_team!` resolves/mutates a `Team` row purely by `params.team.id` (a GitHub-global numeric ID), so a signed-but-attacker-controlled payload from *their own org* can add/remove members on a `Team` row that was originally created for, and is used to gate authorization for, a completely different organization.

### Finding Description
The claimed binding is: `verified_organization.login == team_owner_org(params.team.id)`. Tracing the code shows this equality is never enforced.

- `repository_owner` is computed from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and for a `membership` event only `organization.login` is present, so `Shipit.github(organization: repository_owner)` resolves to the attacker's own legitimately configured app, and `verify_webhook_signature` succeeds with the attacker's own real secret [2](#0-1) .
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)`, setting `team.organization = params.organization.login` only in the creation block (never re-checked or re-validated against an existing row) [3](#0-2) . If a `Team` row with that `github_id` already exists (e.g., created earlier by a legitimate webhook from a different, privileged organization), `find_or_create_by!` simply returns the existing row - `params.organization.login` is completely ignored for lookup or reconciliation.
- `process` then does `team.add_member(member)` / `team.members.delete(member)` based solely on `params.action` and `params.member.login`, with no check that `params.organization.login` matches `team.organization` [4](#0-3) .
- `Team#add_member` unconditionally appends the member [5](#0-4) .
- Critically, `Shipit::User#authorized?` is: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) . This is the authorization gate used across API controllers (`Shipit::Api::BaseController`, `stacks_controller`, etc., all referencing `github_teams`/`authorized?`). Membership in a `Team` row - regardless of which org's webhook secret produced the mutation - is what grants this authorization.

Attacker's exact request: the attacker owns/administers org `attacker-org`, which is one of the multiple orgs configured in `Shipit.github` for this Shipit instance (multi-org precondition). They send `POST /webhooks` with header `X-Github-Event: membership`, signed with `attacker-org`'s real webhook secret, and body:
```json
{
  "action": "added",
  "team": { "id": <github_id_of_a_privileged_team_in_Shipit.github_teams>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-github-user" }
}
```
`verify_signature` succeeds (real secret, real org). `MembershipHandler#process` looks up the `Team` by `github_id` alone, finds the pre-existing privileged team, and calls `team.add_member(User.find_or_create_by_login!("attacker-github-user"))`, adding the attacker's real GitHub account to that `Team`'s `members`.

Existing guards do not catch this: `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema only validates types/presence of `team.id`, `organization.login`, etc., not their cross-consistency; `verify_signature` authenticates the org but is architected around `repository_owner`, a field irrelevant to membership events' actual target. No code path reconciles `organization.login` with the `organization` value already stored on the existing `Team` row.

### Impact Explanation
An attacker who legitimately controls one org in a multi-org Shipit deployment can, by guessing/knowing the numeric GitHub `team.id` of a team from another (privileged) organization, add an arbitrary GitHub account (typically their own) as a member of that `Team` record in Shipit's database. If that team's `id` is present in `Shipit.github_teams`, the attacker's GitHub account becomes `authorized?` for the whole Shipit instance the next time they log in via GitHub OAuth - i.e., escalation into `Shipit.github_teams` authorization, granting access to stack state, task streams, deploy/rollback/merge actions gated behind `authorized?`/`require_permission!`. This matches the "High" impact category explicitly listed in the rules (escalation into `Shipit.github_teams` authorization). It is repeatable against any `Team` row whose `github_id` the attacker can determine, and is independent of which org actually owns that team - a cross-tenant write driven entirely by unreconciled fields in a single payload.

### Likelihood Explanation
Preconditions: multi-org Shipit config with `Shipit.github_teams` configured for authorization, and the attacker legitimately controls at least one configured org (a normal, low-cost precondition - anyone can create a GitHub org and if the Shipit operator onboards it). The attacker needs to know a target `team.id` (a GitHub-global integer); these are discoverable via GitHub's team API for teams the attacker/collaborators can see, prior webhook deliveries, or brute-force since they are sequential and not treated as secret. No Shipit secrets, sessions, or privileged roles are required - only the attacker's own already-configured webhook secret, satisfying the attacker model in the rules.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and generally in webhook handlers that resolve records by GitHub numeric ID), reconcile the verified `organization.login` from the payload against the record's owning organization: e.g., use `Team.find_by(github_id: params.team.id)` and raise/ignore if `team.organization != params.organization.login`, only allowing creation of new teams under `params.organization.login`, never mutating membership of a `Team` whose stored `organization` differs from the payload's verified organization.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`, hypothetical - final assertions matter):
```ruby
test "membership webhook from org A cannot mutate a team belonging to org B" do
  victim_team = Team.create!(github_id: 999, organization: 'victim-org', name: 'Owners', slug: 'owners', api_url: 'https://api.github.com/teams/999')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 999, 'name' => 'Owners', 'slug' => 'owners', 'url' => 'https://api.github.com/teams/999' },
    'organization' => { 'login' => 'attacker-org' }, # verified org != victim_team.organization
    'member' => { 'login' => 'attacker-user' },
  }

  Webhooks::Handlers::MembershipHandler.new.call(payload)

  attacker_user = User.find_by(login: 'attacker-user')

  # Broken binding demonstrated: team resolved by github_id only, ignoring verified organization
  assert_equal 'victim-org', victim_team.reload.organization
  refute_equal payload['organization']['login'], victim_team.organization
  assert_includes victim_team.members, attacker_user # cross-tenant membership mutation succeeded
end
```
This confirms `verify_signature`'s org resolution (`organization.login` == `attacker-org`, cryptographically verified) and `MembershipHandler`'s team resolution (`team.id` == `999`, owned by `victim-org`) are independent, unreconciled fields, and that the mutation (`add_member`) proceeds despite the mismatch.
