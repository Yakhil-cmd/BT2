### Title
Stack-scoped API tokens bypass their stack restriction in CCMenuController - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single `Stack` via `stack_id`, and `Shipit::Api::BaseController` is supposed to enforce that scope on every request by resolving stacks through `current_api_client.stack_id?`-aware `stacks`/`stack` helpers [1](#0-0) . `CCMenuController`, however, overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, which performs no scoping at all [3](#0-2) [4](#0-3) .

### Finding Description
The trust binding that should hold is: **the stack a token authorizes == the stack it touches**. `ApiClient#check_permissions!` only verifies that the token carries the `read:stack` permission string; it never checks which stack the permission applies to [5](#0-4) . The actual per-stack restriction is implemented one layer up, in `BaseController#stacks`, which is supposed to be used by every controller needing a `Stack` lookup:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`CCMenuController` re-defines `stack` and calls the unscoped class method `Stack.from_param!` instead of going through `stacks`:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [6](#0-5) 

`Stack.from_param!` is a bare class-level finder with no relation to any `ApiClient`:

```ruby
def self.from_param!(param)
  repo_owner, repo_name, environment = param.split('/')
  includes(:repository)
    .where(repositories: { owner: repo_owner.downcase, name: repo_name.downcase }, environment:)
    .first!
end
``` [4](#0-3) 

`require_permission :read, :stack` before-action only calls `current_api_client.check_permissions!(:read, :stack)`, which is a string comparison unrelated to any specific stack [7](#0-6) [5](#0-4) . Consequently, once any client presents valid Basic-Auth credentials or a valid `token` query-string parameter (also accepted here, unlike other controllers, via the custom `authenticate_api_client`) [8](#0-7) , that client can pass **any** `stack_id` and read that other stack's CI status, regardless of the `stack_id` the token was originally minted for.

### Impact Explanation
This is an authorization-scope bypass matching "High - ... unauthenticated read of stack state" from the rules: a token that was deliberately scoped to a single stack (e.g., the `here_come_the_walrus` fixture, scoped to the `shipit` stack with `read:stack` permission) [9](#0-8)  can be used to read the deploy/CI status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) of any other stack in the installation, including private/locked stacks whose name and environment are guessable or discoverable, via `CCMenuController#show` [10](#0-9) . This breaks the confidentiality boundary that stack-scoped tokens (e.g. tokens minted through `CCMenuUrlController` and handed to third-party CI dashboard tools) are supposed to provide.

### Likelihood Explanation
Always reproducible for any holder of a valid, even narrowly stack-scoped, `ApiClient` token with `read:stack` permission — no additional privilege, race condition, or unusual configuration is required; only knowledge/guess of another stack's `owner/name/environment` path is needed.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped `stacks` helper instead of the raw `Stack.from_param!` class method, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so a stack-scoped `ApiClient` is restricted to its assigned stack the same way it is in `BaseController`-derived controllers such as `Api::StacksController`.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id` for stack A with `permissions: ['read:stack']` (mirrors fixture `here_come_the_walrus`) [9](#0-8) .
2. Send `GET /api/<repo-owner-B>/<repo-name-B>/<environment-B>/ccmenu.xml?token=<clientA-token>` (or via Basic-Auth header) targeting an unrelated stack B.
3. `authenticate_api_client` in `CCMenuController` validates the token successfully via `ApiClient.authenticate(params[:token])` [8](#0-7) .
4. `require_permission :read, :stack` passes because the client has `read:stack` in `permissions`, with no stack check [5](#0-4) .
5. `stack` resolves stack B directly via unscoped `Stack.from_param!`, and `show` renders stack B's CI/deploy status even though the token was only meant to authorize stack A [11](#0-10) .
