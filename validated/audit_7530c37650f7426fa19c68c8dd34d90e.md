### Title
Membership webhook trusts unauthenticated `organization.login` for both signature-key selection and team-authorization writes, enabling cross-organization `Shipit.github_teams` privilege escalation - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
The `PredyPool` bug lets an attacker set an unverified recipient field that a privileged code path later trusts without checking it against the correct authority. The same class of bug exists in Shipit's webhook pipeline: the field used to pick which GitHub App secret authenticates a webhook (`organization.login` inside the still-unverified JSON body) is later reused, without any cross-check to a second, independently-controllable field (`team.id`), to grant local database team membership that backs `Shipit.github_teams` login authorization.

### Finding Description
`WebhooksController#verify_signature` parses the raw, not-yet-verified JSON body and picks the `GitHubApp`/secret to validate the HMAC against using a value taken from that same unverified body: [1](#0-0) [2](#0-1) 

`repository_owner` falls back to `params.dig('organization', 'login')` — exactly the field a `membership` event payload carries. In a Shipit deployment configured for multiple GitHub organizations (a documented, supported configuration: `docs/setup.md` "Using Multiple Github Applications", `lib/shipit.rb#github`/`github_app_config`), each organization has its own `webhook_secret`: [3](#0-2) 

Because the HMAC key is selected purely from an attacker-suppliable field in the body being authenticated, whoever legitimately administers *any one* of the configured organizations' GitHub Apps (and therefore legitimately knows that org's `webhook_secret`) can compute a valid `X-Hub-Signature` over an **arbitrary** payload and POST it directly to the shared `/github/webhooks` endpoint — bypassing github.com entirely. `verify_signature` will select and validate against that attacker-known secret and pass.

The resulting payload is then dispatched to `MembershipHandler`: [4](#0-3) 

`find_or_create_team!` looks up (or creates) a `Team` keyed only by `github_id: params.team.id` — the real numeric GitHub team ID, which is not a secret and is discoverable to anyone who has ever seen the team via the API or the Shipit UI. If a `Team` row for that `github_id` already exists (created earlier through a legitimate webhook from the *victim* organization), the `organization:` assignment inside the `find_or_create_by!` block never executes (it only runs for newly created records), so the attacker does not even need to guess the victim's `organization.login` correctly for the team object itself — they only need it to match their own org for signature selection, and the real (victim) team's `github_id`.

`process` then does:
```ruby
member = User.find_or_create_by_login!(params.member.login)
team.add_member(member)
```
which appends an attacker-chosen `User` (identified purely by GitHub `login`, which the attacker controls and can set to their own GitHub account) as a member of the victim organization's `Team` row, purely in Shipit's local database — with no live GitHub team-membership check performed.

That local `Membership`/`Team` state is exactly what backs Shipit's login authorization gate: `force_github_authentication` in `app/controllers/concerns/shipit/authentication.rb` checks `current_user.authorized?` and reports `Shipit.github_teams` as the allow-list: [5](#0-4) 

`User` has `has_many :teams, through: :memberships`, i.e., authorization is decided from the local `Membership` rows written by `MembershipHandler`, not from a live re-check against GitHub. (The exact body of `User#authorized?` was not retrievable through search in this session, but its presence alongside `has_many :teams, through: :memberships` and the `Shipit.github_teams` allow-list in `authentication.rb` strongly indicates it is driven by these local rows — this point should be confirmed by reading `app/models/shipit/user.rb` directly, which the indexed search could not fully surface.)

### Binding broken (equality that should hold but doesn't)
`organization authenticated by verify_signature (repository_owner from payload)` **should equal** `organization whose Team/Membership state is mutated by MembershipHandler for a given github_id`. Instead, the code only guarantees the attacker's own organization matches for signature purposes; the `team.id` (github_id) that determines *which* organization's `Team` row is mutated is an independent, attacker-controlled field validated by nothing but the numeric GitHub team ID.

### Impact Explanation
This maps to the explicitly listed High-severity category: "escalation into `Shipit.github_teams` authorization." An attacker who legitimately controls one organization's GitHub App configuration in a multi-org Shipit deployment can grant an arbitrary GitHub account (their own) membership in another organization's authorization team purely at the Shipit-database level, then log in via GitHub OAuth as that account and pass `force_github_authentication`, obtaining full access to the victim organization's stacks, deploys, and secrets exposed through the UI/API — without ever being a real member of the victim's GitHub org or team.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (a documented, supported configuration), and (2) the attacker administers a GitHub App for at least one of the configured organizations (i.e., knows that org's `webhook_secret`) — a realistic scenario for shared/hosted Shipit instances serving multiple, mutually-untrusting organizations/teams. It also requires the victim's target `Team` row to pre-exist with a known/discoverable `github_id`. This is a plausible but not trivial precondition, consistent with a Medium-to-High likelihood.

### Recommendation
- In `WebhooksController#verify_signature`, do not use an unauthenticated payload field to select the verification secret when it will later be trusted to write org-scoped state; alternatively, after signature verification succeeds, re-validate that every organization-identifying field consumed downstream (`organization.login`, `team.id`'s real owning org) is consistent with the authenticated organization.
- In `MembershipHandler#find_or_create_team!`, scope the lookup/update by both `github_id` and the authenticated organization, and reject/log processing when an existing `Team`'s `organization` does not match `params.organization.login`.
- Consider re-verifying team membership against the live GitHub API before granting `Shipit.github_teams` authorization, rather than trusting webhook-driven local `Membership` rows alone.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`), where `Shipit.github_teams` includes `OrgB/some-team` (github_id `999`), and attacker legitimately administers `OrgA`'s GitHub App (knows `OrgA`'s `webhook_secret`).
2. Attacker crafts JSON body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Some Team", "slug": "some-team", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "OrgA" },
  "member": { "login": "attacker-gh-account" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(OrgA_webhook_secret, body)>` and POSTs directly to `/github/webhooks` with `X-Github-Event: membership`.
4. `verify_signature` selects `Shipit.github(organization: "OrgA")` (matches `repository_owner` derived from `organization.login`), validates successfully with the attacker-known secret [1](#0-0) .
5. `MembershipHandler#process` finds the existing `Team` with `github_id: 999` (belonging to `OrgB`) and calls `team.add_member(User.find_or_create_by_login!("attacker-gh-account"))` [6](#0-5) .
6. Attacker logs into Shipit via GitHub OAuth as `attacker-gh-account`; `force_github_authentication` finds them authorized via the newly-created local `Membership` to `OrgB/some-team`, despite never having been added to that team on GitHub itself.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
