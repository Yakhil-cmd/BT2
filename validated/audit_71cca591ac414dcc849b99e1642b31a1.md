### Title
Webhook signature verification is bound to `repository.owner.login`, but event processing acts on the unvalidated `repository.full_name` / `sha` fields — allowing a party who controls one configured GitHub organization to forge events for another organization's stacks ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-org Shipit deployments (`config/secrets.yml` with a `github:` map keyed by organization, as documented in `docs/setup.md`), each organization has its own independently-configured `webhook_secret`. `WebhooksController#verify_signature` selects which secret to check the HMAC signature against using only `repository_owner` (`params.dig('repository','owner','login')` or `organization.login`), but every downstream handler resolves the actual target `Stack`/`Commit` using other unauthenticated payload fields (`repository.full_name` for push/PR/check_suite events, or bare `sha` for status events) that are never cross-checked against the field that selected the signing secret.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 

`repository_owner` is read straight out of the same untrusted JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This only proves the raw body was HMAC-signed with *some* configured organization's `webhook_secret` (`GitHubApp#verify_webhook_signature`, `lib/shipit/github_app.rb:76-83`). It does not prove that the *rest* of the payload — in particular `repository.full_name`, which is what actually gets acted on — belongs to that same organization.

Once the signature passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers that derive the target repository independently:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`Repository.from_github_repo_name` simply splits `"owner/name"` and looks up any matching `Repository` row, with no relation to `repository.owner.login`:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [4](#0-3) 

`StatusHandler` is even weaker — it doesn't consult `repository` at all, only the bare commit `sha`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

**Binding that is broken:** `Org_that_signed(request) == Org_that_owns(stack_acted_on)`. The engine verifies the left side only (via `repository_owner`) but the right side is computed from independent, attacker-supplied fields (`repository.full_name`, or nothing at all for `status`). Any operator running Shipit with more than one GitHub organization configured (explicitly documented and supported via `docs/setup.md` "Using Multiple Github Applications" and `lib/shipit.rb#github_app_config`) has as many independent HMAC secrets as organizations, and a forged signature for OrgA does not restrict the attacker to acting on OrgA's data. [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who is a legitimate owner/admin of one org's GitHub App integration registered with a shared Shipit instance (i.e., knows OrgA's `webhook_secret`, which every org admin necessarily configures themselves per `docs/setup.md`) can sign an arbitrary JSON body with OrgA's secret while setting `repository.owner.login = "OrgA"` (to pass `verify_signature`) and `repository.full_name = "OrgB/some-repo"` (to target another tenant's stack), or for `status` events, simply guess/observe a real `sha` belonging to any tracked commit across the whole install.

Concrete cross-repository-write consequences:
- **Forged CI status injection (`status` event):** `StatusHandler` creates a `Status` for any commit matching `sha` system-wide, regardless of which org's secret signed the request. Since `required_statuses`/`blocking_statuses` gate deploys and merges (`app/models/shipit/deploy_spec.rb`), an attacker controlling OrgA can push a `success` status for a commit belonging to OrgB's repository, defeating CI gating that protects OrgB's deploy pipeline — an unauthorized-deploy-enabling primitive, achieved purely by forging a webhook signed with credentials the attacker legitimately possesses for an unrelated tenant.
- **Forced sync (`push`/`check_suite` events):** `PushHandler`/`CheckSuiteHandler` resolve stacks from `repository.full_name` and call `stack.sync_github`, which in turn uses `stack.github_app = Shipit.github(organization: repository.owner)` — i.e., OrgB's *own* real GitHub App token — to pull real commits into OrgB's stack timeline out of band, or mark stacks accessible/inaccessible, interfering with OrgB's deployment state without OrgB's webhook ever being involved.

This satisfies the "cross-repository writes" / "unauthorized deploy" impact bar because the trust boundary meant to isolate tenants by their independently-configured webhook secrets is not enforced against the fields actually consumed by state-changing handlers.

### Likelihood Explanation
This requires the Shipit operator to run the documented multi-organization configuration (a supported, first-class deployment mode, not a misconfiguration) and requires the attacker to be an authorized administrator/owner of at least one of the configured GitHub App installations (i.e., someone who legitimately knows that org's `webhook_secret`) but who should have zero standing with respect to other tenants' repositories. No Shipit session, `ApiClient` token, or `api_clients_secret` is needed — only knowledge of one org's own webhook secret, which by design is distributed to that org's own operators. Single-organization deployments (the default config) are not affected, since there both `repository_owner` and the acted-upon repository are constrained by the same (only) secret and, practically, the same GitHub organization boundary.

### Recommendation
In `verify_signature`, after validating the HMAC, additionally assert that every organization-identifying field consumed by handlers (`repository.full_name`'s owner segment, and for `status` events, the resolved commit's repository owner) matches `repository_owner`/the organization whose secret validated the request. Concretely:
- Parse `repository.full_name` and require its owner component to equal `repository_owner` before dispatching to handlers.
- In `StatusHandler`, further scope the `Commit.where(sha:)` lookup by the stack's repository owner matching the verified organization, instead of a global `sha` lookup.
- Consider rejecting webhooks where `repository.owner.login` and `repository.full_name`'s owner disagree, at the controller level, so this invariant is enforced once for all event types.

### Proof of Concept
1. Operate a Shipit instance configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. As the legitimate owner of `OrgA`'s GitHub App (you know `OrgA`'s `webhook_secret`), craft a `status` event body:
   ```json
   { "sha": "<real sha of a tracked commit in OrgB's repo>", "state": "success", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/decoy"} }
   ```
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(OrgA_webhook_secret, body)`, matching `GitHubApp#verify_webhook_signature`.
4. POST to `/webhooks` with header `X-Github-Event: status`. `verify_signature` looks up `Shipit.github(organization: "OrgA")` and succeeds because the signature is genuinely valid for `OrgA`'s secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) matches the commit by `sha` alone, system-wide, and records a forged `success` status against `OrgB`'s commit — with no verification tying the accepted signature to `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
