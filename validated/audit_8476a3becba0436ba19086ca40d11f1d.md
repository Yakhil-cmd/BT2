### Title
CCMenu read:stack tokens are not scoped to the stack they were issued for, exposing all stacks if leaked - (File: app/controllers/shipit/ccmenu_url_controller.rb, app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints (or reuses) a single `read:stack` `ApiClient` per user without ever setting `stack_id`, and `Api::CCMenuController` looks the target stack up with a global `Stack.from_param!` call that ignores `current_api_client.stack_id` entirely. The broken binding is: `token.stack_id == params[:stack_id]` is assumed but never enforced — the token is valid for every stack in the installation, not just the one the CCMenu URL was generated for.

### Finding Description
The equality that should hold is: `current_api_client.stack_id == stack.id` (or `current_api_client.stack_id?` is false only for truly unscoped/global clients). In `CCMenuUrlController#fetch`, the client is created with: [1](#0-0) 
`find_or_create_by!(creator: current_user, name: 'CCMenu Client')` keys only on `creator` and `name` — the `stack_id` column on `ApiClient` is never populated, so the same token is reused/returned for every stack the user requests a CCMenu URL for.

On the consuming side, `Api::CCMenuController` overrides authentication and stack lookup: [2](#0-1) 
`authenticate_api_client` calls `ApiClient.authenticate(params[:token])` directly (bypassing `BaseController#authenticate_api_client`), and `stack` resolves via `Stack.from_param!(params[:stack_id])` on the global `Stack` scope — it does **not** reuse `BaseController#stacks`, which is the method that would otherwise filter by `current_api_client.stack_id`: [3](#0-2) 

`require_permission :read, :stack` only checks that `"read:stack"` is in the token's `permissions` array via `ApiClient#check_permissions!`: [4](#0-3) 
it never checks `stack_id` against the requested `stack_id`. As a result, once a user's "CCMenu Client" token exists (minted for any one stack they were authorized to view), that same token string, if it leaks via Referer headers, proxy/access logs, browser history, or is shared, can be replayed against `GET /api/stacks/*any_other_stack_id/ccmenu` and will succeed, since the code path never checks the token's stack scope at all.

### Impact Explanation
An attacker who obtains a leaked CCMenu token (a plausible outcome since the URL embeds the token in the query string, matching the documented CCMenu integration pattern) gains unauthenticated read access to build/deploy status for **every** stack in the Shipit installation, not just the stack the URL was originally generated for. This is a confidentiality breach of stack state (latest deploy status, activity, lock status) across tenants/stacks, matching the "unauthenticated read of stack state" High-severity category. The blast radius is the entire Shipit instance's set of stacks, since one leaked token universally applies.

### Likelihood Explanation
Requires that a legitimate, authorized Shipit user first requests a CCMenu URL for at least one stack (via the session-authenticated `CCMenuUrlController#fetch`, gated by `force_github_authentication`/team membership) and that this token then leaks through a normal channel such as Referer headers, proxy logs, shared dashboards, or browser history — a realistic scenario given CCMenu URLs are designed to be embedded in third-party CI dashboard tools over plain HTTP. No Shipit secrets or privileged roles are needed by the attacker beyond obtaining the leaked token; the cost is low and the exploit is trivially repeatable against every stack ID once a token is captured.

### Recommendation
- Set `stack_id: stack.id` when creating/finding the `ApiClient` in `CCMenuUrlController#fetch`, and change the `find_or_create_by!` key to include `stack_id` so a distinct token is minted per stack.
- In `Api::CCMenuController`, reuse `BaseController#stacks`/`#stack` (or otherwise validate `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`) instead of calling `Stack.from_param!` on the unscoped `Stack` relation.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped token cannot be used to read a different stack" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: 'foo', name: 'bar'), branch: 'main')

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'Scoped CCMenu Client',
    permissions: %w[read:stack],
    stack_id: stack_a.id
  )

  # sanity: works for its own stack
  get :show, params: { stack_id: stack_a.to_param, token: scoped_client.authentication_token }
  assert_response :ok

  # should be rejected for a different stack, but currently succeeds
  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }
  assert_response :not_found # or :forbidden — currently returns :ok, proving the bypass
end
```
This demonstrates `current_api_client.stack_id (stack_a.id) != stack.id (stack_b.id)` yet the request succeeds, proving the missing scope check in `Api::CCMenuController#stack`.
