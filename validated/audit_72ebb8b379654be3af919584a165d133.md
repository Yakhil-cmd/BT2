### Title
Staker rewards can be permanently frozen because `signer-rewards-per-token-for-cycle` is only updated when a signer has non-zero shares at settle time - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`get-earned-staker-rewards` computes a staker's rewards using `get-signer-rewards-per-token-for-cycle` (the per-signer snapshot map) rather than the global `rewards-per-token-for-cycle` accumulator used for signer rewards. That per-signer snapshot is only advanced inside `settle-rewards` when `(> shares u0)` at the time of settlement.

### Finding Description
`get-earned` (signer-level rewards) is computed with `compute-earned-rewards` fed by the global accumulator `get-rewards-per-token-for-cycle`, which is unconditionally advanced on every `calculate-rewards` call: [1](#0-0) 

However, `get-earned-staker-rewards` (staker-level rewards, delegated under a signer) is fed by `get-signer-rewards-per-token-for-cycle`, a *different, per-signer-scoped* map: [2](#0-1) 

That per-signer map is only conditionally written inside `settle-rewards`:
```
(if (> shares u0)
    (map-set signer-rewards-per-token-for-cycle {...} rewards-per-token)
    true
)
``` [3](#0-2) 

This mirrors the `applyInterest` inconsistency in the referenced report: two conceptually parallel "earned" computations (`get-earned` for signers vs `get-earned-staker-rewards`/`settle-staker-rewards` for delegated stakers) are fed by two different state variables that are supposed to represent the same "rewards-per-token accrued so far" quantity, but one (`rewards-per-token-for-cycle`) is unconditionally updated while the other (`signer-rewards-per-token-for-cycle`) is gated on the signer's `shares > u0` condition at the moment `settle-rewards` happens to run. If a signer's `settle-rewards` is invoked at a moment when its own `shares` is `u0` (e.g., before it stakes any of its own shares for that cycle/bond-index, or after fully unstaking), the per-signer snapshot map is never advanced to the current `rewards-per-token`, even though `calculate-rewards` has already credited that cycle's accumulator. Any staker who delegated to that signer for that cycle/bond-index and calls `settle-staker-rewards`/`get-earned-staker-rewards` will then compute `earned` against a stale (lower, possibly zero) `rewards-per-token`, permanently losing the delta between the stale snapshot and the true accumulator value for that period, since `settle-rewards`/`settle-staker-rewards` are the only paths that advance these snapshots forward and neither ever revisits/backfills a skipped period.

### Impact Explanation
This causes a **temporary/permanent freezing of staker rewards** that were legitimately earned by delegated stakers (sBTC rewards owed but never paid), because the staker-facing accumulator (`signer-rewards-per-token-for-cycle`) can silently fail to advance while the signer-facing accumulator (`rewards-per-token-for-cycle`) always advances — breaking the equality that a staker's claimable reward should track the global per-token accumulator delta since their last settle. This matches the High-severity criteria: temporary freezing of staked/reward funds due to an unsigned/unintended state-update gap, not requiring any privileged role.

### Likelihood Explanation
Likelihood is moderate: it requires a signer to have `shares == u0` for a given `(reward-cycle, bond-index)` at the exact time `settle-rewards` fires for that signer (e.g., because `settle-rewards` is invoked as a side effect of another action, such as `claim-rewards`, `update-claimable-rewards`, or a shares-changing operation, before the signer itself has staked shares for that cycle), while stakers had already delegated shares to that signer for the same cycle/bond-index. Given `settle-rewards` is documented as required to run "before any update to `signer-shares-staked-for-cycle`" [4](#0-3) , ordinary staking/unstaking flows can plausibly trigger this gap.

### Recommendation
Make the staker-facing snapshot (`signer-rewards-per-token-for-cycle`) unconditionally track the same accumulator value as `rewards-per-token-for-cycle` on every `settle-rewards` call, regardless of the signer's own `shares` value — i.e., remove the `(if (> shares u0) ... true)` gate at [3](#0-2)  so the per-signer snapshot used for staker reward accounting always mirrors the true global per-token accumulator.

### Proof of Concept
1. Signer `S` has zero personal `shares` for `(reward-cycle=N, bond-index=none)` but staker `A` has delegated shares to `S` for that same cycle.
2. `calculate-rewards` runs, advancing the global `rewards-per-token-for-cycle` map for `N` (`get-rewards-per-token-for-cycle` now returns a higher value) — see [5](#0-4) .
3. Some action triggers `settle-rewards(S, N, none)` (e.g., via `claim-rewards`/`update-claimable-rewards`). Because `S`'s `shares` is `u0`, the branch at lines 2559-2568 skips updating `signer-rewards-per-token-for-cycle` for `S`/`N`/`none`, leaving it at its old (lower) value.
4. Staker `A` calls `claim-staker-rewards` → `settle-staker-rewards` → `get-earned-staker-rewards`, which reads the stale `get-signer-rewards-per-token-for-cycle` value instead of the updated global accumulator.
5. `A`'s `earned` is computed against the stale `rpt-current`, permanently losing the reward delta accrued during step 2, even though the contract's own accounting (`rewards-per-token-for-cycle`) shows those rewards as distributed.
