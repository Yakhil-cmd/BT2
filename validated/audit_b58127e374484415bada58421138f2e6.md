This confirms the binding mismatch: the webhook's HMAC signature is authenticated against the GitHub organization identified by `repository_owner` (derived from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`) in `verify_signature`, [1](#0-0) , while the actual repository whose stacks get written/synced is resolved from a completely different, unchecked field: `payload.dig('repository', 'full_name')` in `Handler#repository_name`/`#stacks` [2](#0-1) , and then acted on directly, e.g. `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for every matching stack [3](#0-2) .

### Title
Webhook signature is verified against `repository.owner.login`, but the write target is resolved from the independent, unverified `repository.full_name` field, allowing cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
In multi-organization deployments, Shipit binds one GitHub App configuration (and one `webhook_secret`) per organization via `Shipit.github(organization: ...)` [4](#0-3) . `WebhooksController#verify_signature` picks which organization's secret to verify the HMAC with using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [5](#0-4) . Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the handlers on the full raw JSON `params` [6](#0-5) . Every handler locates the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` [7](#0-6)  — a field that is never compared against, or required to be consistent with, the `repository.owner.login` value that determined which secret validated the signature.

### Finding Description
The binding the engine relies on is: `organization authenticated by verify_signature == organization that owns the repository/stack being written to`. This binding is not enforced anywhere. The HMAC signature over the raw POST body only proves the payload was signed with *some* configured organization's `webhook_secret` — it says nothing about which specific JSON fields inside that payload the signing organization is authorized to control. An organization admin who legitimately controls their own GitHub App installation (and therefore their own `webhook_secret`, entered by a Shipit operator for that org) can craft an arbitrary JSON body, set `repository.owner.login` (or `organization.login`) to their own org so `verify_signature` looks up and validates against their own secret, while setting `repository.full_name` to `"other-org/other-repo"`. Because handlers never re-derive/re-check the owner from `full_name` against the organization that authenticated the request, the forged payload is processed against the other organization's stack.

For example, `PushHandler` would call `stack.sync_github(expected_head_sha: params.after)` [3](#0-2)  for any stack found under `Repository.from_github_repo_name("other-org/other-repo")` [8](#0-7) , letting a signed webhook from OrgA's App drive sync behavior on OrgB's stack. The `pull_request` handlers (merge/close/label handling) inherit the same `repository_name`/`stacks` resolution from the base `Handler` class, so the mismatch is systemic across all webhook-driven actions, not just push.

### Impact Explanation
This breaks the cross-repository/cross-organization isolation Shipit's multi-org webhook design is meant to provide: a request that authenticates as OrgA can act on OrgB's repositories/stacks purely by putting a different value in an unauthenticated-but-trusted field of the same signed payload. Depending on which handler is reached, this can trigger a sync/deploy-relevant action against a repository the requester does not control, which is a cross-repository write.

### Likelihood Explanation
Likelihood is Low, matching the bug-class hint: it requires the attacker to already be a legitimate, configured GitHub App organization in the Shipit deployment (i.e., possess a valid `webhook_secret` for at least one onboarded org) and requires multiple organizations to be configured on the same Shipit instance. This is a narrower "unprivileged relative to the other organization" attacker, not a fully unauthenticated one, but no repository write access, API token, or session is required against the victim organization.

### Recommendation
After signature verification, re-derive the organization from `payload.dig('repository', 'full_name')` (or the `owner.login`/org fields the handlers actually use) and assert it matches the organization whose secret validated the signature, rejecting the webhook (422) on mismatch, before dispatching to any handler in `WebhooksController#create`.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `org-a` and `org-b`, each with its own `github.webhook_secret` per `lib/shipit.rb#github_app_config`.
2. As the (legitimate) owner/admin of `org-a`'s GitHub App, craft a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Sign the raw body with `org-a`'s `webhook_secret` and send it as `X-Hub-Signature` to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature validates [9](#0-8) .
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` [8](#0-7)  and calls `sync_github` on `org-b`'s stacks, even though the request only ever authenticated as `org-a`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
