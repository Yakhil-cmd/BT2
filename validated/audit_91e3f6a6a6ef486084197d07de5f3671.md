### Title
Webhook signature verification is scoped by `repository.owner.login` while stack resolution is scoped by the independent `repository.full_name` field, allowing a forged `push` for one configured org to drive `GithubSyncJob` against a victim stack in another org - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/push_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/secret to verify against using `repository.owner.login` from the untrusted JSON body, while `Handler#stacks` (used by `PushHandler`) resolves the target stack using `repository.full_name` from that same untrusted body. Because these two fields are never cross-checked, and because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved organization has no `webhook_secret` configured, an attacker can produce a webhook whose `owner.login` matches a "no-secret" configured org (satisfying signature verification) but whose `full_name` points at a stack belonging to a completely different, victim-owned repository.

### Finding Description
The broken binding: the code implicitly assumes
`params.dig('repository','owner','login') == owner_of(params.dig('repository','full_name'))`,
but nothing enforces this equality.

- `verify_signature` in [1](#0-0)  computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` (attacker JSON) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` in [2](#0-1)  returns `true` unconditionally (`return true unless webhook_secret`) whenever that specific org's config has no `webhook_secret` set — a legitimate, documented configuration state for orgs that haven't set one up.
- Once signature verification passes, `WebhooksController#create` dispatches to `PushHandler`, whose `process`/`stacks` method resolves the target stack via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a completely separate JSON field from `owner.login` used above: [3](#0-2) .
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack whose `branch` matches, using attacker-controlled `after`: [4](#0-3) .
- `Stack#sync_github` unconditionally enqueues `GithubSyncJob.perform_later(stack_id: id, expected_head_sha:)`: [5](#0-4) .
- `GithubSyncJob#perform` fetches commits from GitHub for the stack's real repository and appends/detaches commits reachable up to `expected_head_sha`, then may run `CacheDeploySpecJob`: [6](#0-5) .

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: push` and a body where `repository.owner.login` = an org configured in `Shipit.secrets.github` with no `webhook_secret` (a "no-secret org" the attacker knows about or that is the default single-org config with `webhook_secret` blank, matching `test/dummy/config/secrets.yml`'s `webhook_secret: # nil`), and `repository.full_name` = `"victim-org/victim-repo"` matching a real victim `Stack`'s tracked branch, with `ref: "refs/heads/<victim-branch>"` and `after: "<attacker-chosen-sha>"`. Verification passes trivially (no secret to check against for that org), and `PushHandler` resolves and syncs the victim stack using attacker-supplied `full_name`/`ref`/`after`.

Existing guards do not prevent this: `verify_signature` only checks that the request is a validly signed request *for the org named in the payload itself*, not that the *target repository* belongs to that org; `drop_unhandled_event` and `check_if_ping` are unrelated; `ExplicitParameters` schema in `PushHandler` only requires `ref` and `after` be present, it does not validate `repository.full_name` at all (it's read directly from `payload`, not `params`).

### Impact Explanation
An attacker who controls (or can trigger delivery for) any org configured in the Shipit installation without a `webhook_secret` can force `GithubSyncJob` to run against any other tenant/org's stack tracked by Shipit, causing Shipit to fetch and append commits up to an attacker-chosen SHA and potentially trigger continuous-deployment behavior (via `sync_github_if_necessary`/CD pipelines reacting to new commits) — an unauthorized deploy-adjacent mutation of a victim's stack state driven entirely by attacker-supplied `full_name`/`branch`/`after`. This is repeatable against any stack whose repository is reachable via `Repository.from_github_repo_name` and matches on `branch`, across all tenants configured on the same Shipit instance, matching the Critical category "a payload for one repository mutating another's stack."

### Likelihood Explanation
This requires at least one org among `Shipit.secrets.github` to be configured without a `webhook_secret` (explicitly supported and demonstrated in this repo's own test fixtures, e.g., `test/dummy/config/secrets.yml` line 13: `webhook_secret: # nil`), which is a realistic operational misconfiguration (or intentional for low-security orgs) in a multi-tenant Shipit deployment. Given that precondition, the attack costs nothing beyond a single crafted unauthenticated HTTP POST with no signature validity required, and is trivially repeatable against any target stack whose repository name and branch the attacker can guess or discover (stack names/branches are often public via GitHub itself).

### Recommendation
Bind signature verification to the same repository that is subsequently acted upon: derive `repository_owner` from the resolved `Stack`'s configured `Repository#owner` (looked up via `Repository.from_github_repo_name(repository_full_name)`) rather than from the attacker-supplied `owner.login` field, or explicitly assert `params.dig('repository','owner','login').downcase == params.dig('repository','full_name').split('/').first.downcase` before processing, rejecting mismatches with 422. Additionally, do not treat a missing `webhook_secret` as automatic success for organizations that host stacks other than the one being verified — require an explicit "no signature enforcement" opt-in scoped per repository, not per organization name taken from the payload.

### Proof of Concept
minitest plan (webhooks_controller_test.rb):
```ruby
test "push cannot use org A's lack of webhook_secret to sync org B's stack" do
  # Precondition: configure Shipit.github(organization: 'attacker-org') with no webhook_secret
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', { webhook_secret: nil })
  )
  victim_stack = shipit_stacks(:shipit) # tracks victim-org/victim-repo, branch 'master'

  forged_after = 'deadbeefattackersha'
  body = {
    ref: 'refs/heads/master',
    after: forged_after,
    repository: {
      owner: { login: 'attacker-org' },      # used for signature check (no secret -> passes)
      full_name: 'victim-org/victim-repo'    # used to resolve the *actual* stack
    }
  }.to_json

  request.headers['X-Github-Event'] = 'push'
  # no X-Hub-Signature needed since attacker-org has no webhook_secret

  assert_enqueued_with(job: Shipit::GithubSyncJob,
                        args: [stack_id: victim_stack.id, expected_head_sha: forged_after]) do
    post :create, body:, as: :json
  end
end
```
Binding under test (before): `repository_owner_for_signature == 'attacker-org'` while `repository_owner_for_stack_lookup == 'victim-org'` — these diverge and the request still succeeds, proving the invariant "a push event may only sync stacks belonging to the repository that authenticated the event" is violated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
