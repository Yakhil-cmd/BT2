## Analysis Result

I found a valid analog: a confused-deputy split between the field used to select/verify the webhook signing secret (`repository.owner.login` / `organization.login`) and the field actually used to resolve which repository's stack receives the event (`repository.full_name`). Both are attacker-controlled fields inside the same unauthenticated JSON body, and they are read independently.

### Title
Webhook organization used for signature verification is decoupled from the repository actually acted upon, allowing cross-organization event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated, attacker-supplied JSON body. The actual event processing, however, resolves the target `Repository`/`Stack` using a *different* field from the same payload: `repository.full_name`, via `Handler#repository_name`. Because these two fields are never cross-checked, an attacker can pick an organization whose `webhook_secret` is unset (which the code treats as "no verification required") for the signature check, while pointing `full_name` at a stack that belongs to a fully configured, secret-protected organization.

### Finding Description
- Signature verification org selection: `repository_owner` is read straight from JSON: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) 
- Verification is a no-op when the selected org's `webhook_secret` is blank: `return true unless webhook_secret`. [2](#0-1) 
- Event dispatch happens after this check, passing the *entire raw JSON* to handlers untouched: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 
- Every handler resolves the actual target repository/stack independently, using `payload.dig('repository', 'full_name')`, not `repository.owner.login`: [4](#0-3) 
- `PushHandler`, for example, immediately calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack found via `full_name`. [5](#0-4) 

The equality that should hold is:
`organization whose secret authenticated the webhook == organization that owns the repository/stack the handler will act on`

The engine breaks this: the org used to *authenticate* the request (`repository.owner.login`) and the org whose stack is *written to* (`repository.full_name`'s owner segment) are read from two separate, independently attacker-controlled JSON paths, with no consistency check between them.

Multi-organization deployments are an explicitly documented and supported configuration (`docs/setup.md`, `config/secrets.development.shopify.yml`), and each organization's `webhook_secret` is optional/independently configured per the docs (`github.webhook_secret` — "If you've set a webhook secret ... copy it here"), meaning it's common/expected for some orgs (e.g., ones added for OAuth-only login, or test orgs) to have no secret configured while others do. [6](#0-5) 

### Impact Explanation
An attacker with no Shipit credentials, who knows (a) the name of any GitHub organization configured in Shipit with a blank `webhook_secret`, and (b) the `owner/name` of a real tracked repository belonging to a *different*, secret-protected organization, can forge a `push`/`status`/`check_suite`/`pull_request` webhook payload:
```json
{
  "repository": { "owner": {"login": "org-with-no-secret"}, "full_name": "org-with-secret/target-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>"
}
```
`verify_signature` will look up `org-with-no-secret`'s (blank) secret and always pass, then the `PushHandler` will trigger `Stack#sync_github` against the real `org-with-secret/target-repo` stack — triggering GitHub sync, potentially unblocking/starting deploys, forged CI status ingestion, or merge-queue state changes for a repository the attacker does not control and was never authenticated against. This is an unauthenticated cross-organization write into stack/task state (matches the High-impact category: "unauthenticated read of stack state" and beyond — here it's an unauthenticated *write*).

### Likelihood Explanation
Requires: (1) at least two GitHub organizations configured on the Shipit instance, and (2) at least one of them lacking a `webhook_secret`. This is a realistic/likely operational state since multi-org support is a first-class documented feature and `webhook_secret` is presented as an optional field with `# nil` shown as example default in the shipped secrets templates.

### Recommendation
- In `verify_signature`, after computing `repository_owner`, cross-validate it against the actual repository the payload claims to reference (`repository.full_name`'s owner segment) and reject if they differ.
- Do not treat a blank `webhook_secret` as "verification not required" once any handler will use payload-derived organization/repo identifiers to look up real records — require an explicit secret for every configured organization, or fail closed rather than open in `verify_webhook_signature`.

### Proof of Concept
1. Configure two orgs in `secrets.yml`: `orgA` (has `webhook_secret: s3cr3t`) owning stack `orgA/app`, and `orgB` (no `webhook_secret` set).
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` (or any bogus value), and body:
```json
{ "repository": {"owner": {"login": "orgB"}, "full_name": "orgA/app"}, "ref": "refs/heads/main", "after": "<sha>" }
```
3. `verify_signature` resolves `Shipit.github(organization: 'orgB')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally. [7](#0-6) 
4. `PushHandler.call(params)` resolves the stack via `Repository.from_github_repo_name('orgA/app')` and invokes `sync_github` on it, despite the request never being authenticated by `orgA`'s secret. [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

      private_key:

        secret:
        teams:
    someothergithuborg:

      webhook_secret:
      private_key:
