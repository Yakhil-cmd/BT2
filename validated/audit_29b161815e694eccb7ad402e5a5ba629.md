### Title
Webhook signature verified against `repository.owner.login`, but stack lookup uses attacker-controlled `repository.full_name` — cross-organization stack targeting - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used for HMAC validation based on `repository_owner` (`repository.owner.login`, falling back to `organization.login`), while every webhook handler that acts on the payload (`PushHandler`, and the `PullRequest` handlers) resolves the target `Stack`/`Repository` via `Shipit::Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`. These are two different fields of the same untrusted JSON body, and nothing ties the verified `owner.login` to the `full_name` that is actually used to pick which repository's stacks get mutated.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` verifies webhook authenticity like this: [1](#0-0) [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks the `GithubApp` config (and thus the `webhook_secret`) purely from `repository.owner.login`. Shipit explicitly supports multiple GitHub organizations/apps with distinct `webhook_secret`s, as documented: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the entire raw payload to handlers unmodified: [4](#0-3) 

`Handler#stacks`/`#repository_name`, used by `PushHandler`, resolve the acted-upon repository from a *different* field — `repository.full_name` — not `repository.owner.login`: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` splits `full_name` on `/` and looks up by `owner`/`name` independently of any signature-verified organization: [7](#0-6) 

For a legitimate GitHub-generated push webhook, `repository.owner.login` and the owner segment of `repository.full_name` are always consistent, because GitHub itself populates both fields from the same underlying repository. However, the webhook endpoint accepts any POST with a valid `X-Hub-Signature`, and the signature is only proof that the request body was HMAC-signed with *some* organization's `webhook_secret` — not that the body's `full_name`/`owner` fields are internally consistent. An attacker who administers their own GitHub App installation in their own organization ("evil-org", a legitimate, unprivileged tenant in a multi-org Shipit deployment) knows that org's `webhook_secret` (they configured it themselves per `docs/setup.md`). That attacker can construct an arbitrary JSON body — setting `repository.owner.login` = `"evil-org"` (so `Shipit.github(organization: 'evil-org')`'s secret is used and the signature check at line 26-30 passes) while setting `repository.full_name` = `"victim-org/victim-repo"` (an unrelated stack the attacker does not own) — sign it themselves with their own known `webhook_secret`, and POST it directly to the shared `/github/webhooks` endpoint (bypassing GitHub entirely). The equality the code relies on but never enforces is:

`organization authenticated (repository.owner.login, used to select the verifying secret) == organization whose repository is written (repository.full_name, used by handlers to select the Stack)`

Before the attacker's request: only genuine GitHub events, where both fields are naturally consistent, reach handlers with a valid signature.
After the attacker's request: a request signed with `evil-org`'s own secret, but with `full_name` pointing at `victim-org/victim-repo`, still passes `verify_signature` and is dispatched to `PushHandler`, which will operate against `victim-org`'s stacks. `PushHandler#process` matches the payload branch against the stack's branch (attacker-controlled, `params.ref`) and calls `stack.sync_github(expected_head_sha: params.after)` — an attacker-controlled `expected_head_sha` — on every non-archived stack of the victim repository sharing that branch: [6](#0-5) 

### Impact Explanation
This crosses a repository/organization trust boundary: an attacker who only administers their own GitHub App installation (an unprivileged tenant with no access to the victim org or repo) can force webhook-triggered behavior (`GithubSyncJob`, which appends commits fetched via `stack.github_commits`/`FirstParentCommitsIterator`, and can call `CacheDeploySpecJob`) against a stack belonging to a completely different, victim organization. This is a cross-repository/cross-tenant write via the webhook path that the signature check was specifically designed to prevent (i.e., ensure only the owning org's signed requests can affect its stacks). Depending on continuous-delivery configuration and merge-queue settings this can influence deploy triggers (e.g., forcing sync retries via a bogus `expected_head_sha`, or perturbing merge-queue/CI status resolution for the victim's stack), qualifying as an unauthorized cross-repository interaction with another tenant's deployment pipeline.

### Likelihood Explanation
Requires only that the Shipit instance be configured with multiple GitHub organizations/Apps (a documented, supported configuration), and that the attacker legitimately controls at least one such organization's GitHub App (and hence its `webhook_secret`). No access to the victim org, no `ApiClient` token, and no Shipit session is required — only an HTTP POST to the public webhooks endpoint with a self-signed, self-crafted payload. This is a realistic configuration for shared/multi-tenant Shipit deployments.

### Recommendation
After `verify_webhook_signature` succeeds for the `repository_owner` derived from the payload, re-validate that every repository-identifying field the handlers subsequently use (`repository.full_name`, and by extension `owner`/`name`) is consistent with the same `repository_owner`/organization that produced the valid signature (e.g., reject if `params.dig('repository','full_name')&.split('/')&.first&.downcase != repository_owner&.downcase`). Alternatively, look up handlers' target repository using the already-verified `repository_owner` rather than trusting `full_name` independently.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`) with two orgs: `victim-org` (has a real Stack tracking `victim-org/victim-repo`) and `evil-org` (attacker's own org, attacker knows `evil-org`'s `webhook_secret` because they configured/installed that GitHub App themselves).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "evil-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(evil-org webhook_secret, body)>`.
4. Attacker POSTs this body with header `X-Github-Event: push` to the Shipit `/github/webhooks` endpoint.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'evil-org')` (from `repository_owner`), verifies successfully since the attacker signed with `evil-org`'s real secret.
6. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` — a repository the attacker does not control — and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` on the victim's stack.
