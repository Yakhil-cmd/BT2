### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the handler acts on the repository named in `repository.full_name` — a different, unchecked field in the same payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate an inbound webhook's HMAC against using one field of the untrusted JSON body, while the handlers that actually mutate state (create commits, set commit statuses, trigger continuous deployment, etc.) resolve the target `Stack`/`Repository` using a *different* field of that same body. Nothing enforces that these two fields agree, so an attacker who legitimately controls a webhook secret for their own GitHub organization (i.e. they have wired up their own repo/org to this Shipit instance, which is a normal, unprivileged, self-service action, not "stealing" `webhook_secret`) can forge a request whose HMAC is valid for *their* org but whose payload content targets a completely different org/repo's stack.

### Finding Description
`verify_signature` computes the signing organization like this: [1](#0-0) 

and [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — a field fully controlled by whoever sends the POST body, gated only by the `X-Hub-Signature` HMAC computed with the `webhook_secret` configured for *that same claimed organization* (`lib/shipit/github_app.rb`, `verify_webhook_signature`, lines 76-83, matched against `Shipit.github(organization: repository_owner)`).

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs with the raw, attacker-supplied `params` (`app/controllers/shipit/webhooks_controller.rb` line 10-15). Every handler (`push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, and any custom handler using the shared base class) resolves the affected repository/stacks from a *different* JSON path: [3](#0-2) 

`repository.owner.login` (used for authentication) and `repository.full_name` (used for authorization/target selection) live in the same JSON object in a genuine GitHub payload and are normally consistent, but the controller never asserts that consistency. An attacker who has configured their own GitHub org/repo to send webhooks to this Shipit instance (and therefore legitimately knows the `webhook_secret` issued to *their own* org — not a privileged secret belonging to the target) can submit:

```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  ...
}
```

signed with `attacker-org`'s webhook secret. `verify_signature` resolves and validates against `attacker-org`'s secret (success), but the handler that actually runs (e.g. `StatusHandler`) looks up the `victim-org/victim-repo` stacks via `Repository.from_github_repo_name(repository_name)` and writes commit/status/state data for that stack — a stack the attacker was never authorized to touch.

This is the exact class of trust-binding break called out in the rules: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Handlers reachable this way include `status_handler.rb` (records commit CI statuses used by Shipit to decide deployability/continuous-delivery eligibility) and `push_handler.rb`/`check_suite_handler.rb` (record commits/check-runs for a stack). By forging cross-repository status/commit records for a victim stack that has `continuous_deployment` enabled, an attacker can inject a fabricated "success" status for an arbitrary SHA on a victim's tracked branch, causing Shipit's continuous-delivery logic (`Stack#trigger_continuous_delivery`) to deploy that SHA — an unauthorized deploy. This satisfies the Critical impact bar ("cross-repository writes, or an unauthorized deploy").

### Likelihood Explanation
The only prerequisite is control of a webhook secret for *any* organization/repository already connected to the shared Shipit instance (self-service, unprivileged relative to the victim), plus knowledge of the victim's `owner/name`, which is public information on GitHub. No session, `ApiClient` token, or victim credential is required, satisfying the engine's own exploitability bar for this class of finding.

### Recommendation
In `WebhooksController#verify_signature` / `Handler#repository_name`, require that the field used to select the verifying `webhook_secret` (`repository.owner.login` / `organization.login`) is the same field used to resolve the target repository (`repository.full_name`). Concretely, derive `repository_name`/`repository_owner` from a single, consistently-parsed source, or explicitly verify `repository.full_name.split('/').first == repository.owner.login` before allowing any handler to run, rejecting the payload with `422` otherwise.

### Proof of Concept
1. Attacker owns `attacker-org/attacker-repo`, installs Shipit's GitHub App/webhook on it, and thus knows the `webhook_secret` Shipit has configured for `attacker-org` (`Shipit.github(organization: 'attacker-org')`).
2. Attacker crafts a `status` (or `push`) webhook JSON body where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `sha` = a SHA on the victim's tracked branch, `state = "success"`
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the exact raw JSON body.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and `verify_webhook_signature` succeeds because the signature matches that secret. [1](#0-0) 
5. `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` runs `StatusHandler`, which resolves `stacks` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` → `victim-org/victim-repo`'s stacks, and records the forged success status for that SHA. [3](#0-2) 
6. If `victim-org/victim-repo`'s stack has continuous deployment enabled, the forged status can trigger an unauthorized deploy of attacker-chosen state to the victim's stack.
