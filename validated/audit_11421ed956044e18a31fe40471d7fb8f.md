### Title
Use-after-free-style null dereference in `handlePrivatePaymentChains` via reordered `checkIfAllValidated`/`eventBus.once` teardown - (File: wallet.js)

### Summary
`wallet.js`'s `handlePrivatePaymentChains()` mirrors the `rt9455` bug class: a shared per-request state object (`assocValidatedByKey`) can be torn down (set to `null`) while an asynchronous event handler (`eventBus.once(key, ...)`) that references it is still registered and can fire afterward, causing the handler to dereference/write into freed state.

### Finding Description
In `handlePrivatePaymentChains` [1](#0-0) , a local map `assocValidatedByKey` tracks validation status of each private-payment chain by key. For chains whose validation is queued (light client / async DB write), a listener is registered:

```
eventBus.once(key, function(bValid){
    if (!bValid) return cancelAllKeys();
    assocValidatedByKey[key] = true;
    if (bParsingComplete) checkIfAllValidated();
    ...
});
``` [2](#0-1) 

`checkIfAllValidated()` nulls out the tracker once all currently-known keys validate: `assocValidatedByKey = null; // to avoid duplicate calls` [3](#0-2) . This is analogous to the kernel bug's `devm_` teardown ordering issue: the "resource" (`assocValidatedByKey`) is released/nulled *before* the listeners that reference it are deregistered — mirroring the rt9455 pattern where `power_supply` is freed before the IRQ handler that uses it is unregistered.

Because `arrChains` is processed with `async.eachSeries`, and each chain's `ifQueued` path resolves via `network.handleOnlinePrivatePayment` → `handleSavedPrivatePayments` in `network.js`, which emits the completion event asynchronously and independently per key, e.g. `eventBus.emit(key, true)` / `eventBus.emit(key, false)` [4](#0-3) , there is a race window: if one key's async validation completes and triggers `checkIfAllValidated()` (nulling `assocValidatedByKey`) while another key's listener (registered earlier for a different, still-in-flight `unhandled_private_payments` row processed by a separate `handleSavedPrivatePayments` invocation) fires afterward, the once-listener executes `assocValidatedByKey[key] = true;` on a `null` object, throwing a `TypeError`.

### Impact Explanation
A `TypeError` thrown inside a `db.query`/event-emission callback in Node.js is an uncaught exception in an asynchronous context, which crashes the entire wallet/hub process (equivalent in severity to a kernel use-after-free crash). Because `handlePrivatePaymentChains` is reachable directly from any device peer sending `private_payments` messages over the authenticated device-messaging channel [5](#0-4) , a remote private-payment counterparty can trigger the crash by sending multiple private chains and interleaving their (already-known/duplicate vs freshly-queued) validation outcomes to hit the null-dereference window, taking down the victim's node process — a denial of the wallet's ability to process transactions/validate the DAG until restarted.

### Likelihood Explanation
The race requires the attacker-controlled peer to send more than one private-payment chain in a single `handlePrivatePaymentChains` batch such that one is already-cached/synchronously validated (or resolves fast enough to trigger `checkIfAllValidated`) while another chain's listener resolves later via the `eventBus.once(key, ...)` path. Since the attacker fully controls the content, count, and timing/order of the chains within the message (and the second network round trip that resolves `ifQueued` keys is separately triggered by their own subsequent messages/gossip), the attacker has significant influence over ordering, making the race practically triggerable, though it depends on Node's event-loop scheduling of the underlying async DB operations.

### Recommendation
Do not null out `assocValidatedByKey` while any `eventBus.once(key, ...)` listeners created in this invocation may still be pending; instead, use a separate boolean flag (e.g., `bAlreadyNotified`) to guard against duplicate `all_private_payments_handled` emission, while keeping `assocValidatedByKey` alive (or checking `assocValidatedByKey && assocValidatedByKey[key] !== undefined`) until all registered listeners for the batch have fired or been explicitly removed via `cancelAllKeys()`.

### Proof of Concept
1. Attacker (a private-payment counterparty) sends a `private_payments` device message containing two chains in one `body.chains` array: chain A referencing a payload whose `unhandled_private_payments` row is already present/known (resolves via `ifKnown`/sync fast path), and chain B whose validation is queued (`ifQueued`) and resolves asynchronously via a later `handleSavedPrivatePayments` pass emitting `eventBus.emit(key, true)`.
2. If chain A's key satisfies `checkIfAllValidated()` before chain B's queued listener fires (e.g., by sending chain A's underlying unit slightly earlier via gossip so it's already "known" when the batch is processed), `assocValidatedByKey` is set to `null`.
3. When chain B's `eventBus.once(key, ...)` handler later fires (`network.js` line ~2488 emit), it executes `assocValidatedByKey[key] = true` on `null`, throwing `TypeError: Cannot set properties of null`, crashing the wallet/hub process.
