### Title
Unfiltered PR-label-derived env keys (e.g. `SSH_ASKPASS`) reach `git` via `StackCommands#env`/`Command#unbundled_env` with no allowlist - (File: app/models/shipit/review_stack.rb, lib/shipit/stack_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment variable key with the value `"true"`, and this merged hash is used unfiltered by `StackCommands#fetch`/`#git_clone` (via `StackCommands#env`), then by `Command#unbundled_env`, which is passed directly to `PTY.spawn`. Because `git`'s fetch/clone code path is never passed through `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` (the only allowlist mechanism in this codebase), an attacker who can label their own PR (e.g. with a label literally named `SSH_ASKPASS`) can set that env key on the `git` subprocess.

### Finding Description
The broken binding: the set of keys the deploy operator expects to reach `git`'s subprocess environment should equal `Shipit.shell_paths`/`BASE_ENV`/declared `deploy_spec.machine_env` and `VariableDefinition` names ∪ Shipit's own fixed keys (`SHIPIT_USER`, `EMAIL`, etc.) — but in practice it equals that set **union arbitrary PR label names**, because no code filters `StackCommands#env`.

Trace:
- `ReviewStack#env` (app/models/shipit/review_stack.rb:84-93) does `super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })` — this takes `pull_request.labels` (persisted directly from GitHub webhook payload) with **no key allowlist or denylist**.
- `pull_request.labels` is populated verbatim by `LabelCapturingHandler#capture_labels` (app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102): `pull_request.update!(labels: params.pull_request.labels.map(&:name))`. The webhook `params` schema only requires `labels` to be an `Array` of objects with a `name` `String` (lines 29-31) — no allowlist on label name content.
- `StackCommands#env` (lib/shipit/stack_commands.rb:13-15): `super.merge(@stack.env)` — used by `fetch`/`fetch_commit`/`git_clone` (lines 17-35, 112-114) for the `git` command invocations, all called with `env:` kwarg passed straight to `Command.new`.
- `Command#unbundled_env` (lib/shipit/command.rb:103-105): `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — merges the attacker-controlled hash over `BASE_ENV` with **no key filtering at all**.
- `Command#start` (lib/shipit/command.rb:92): `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` — the merged hash including any attacker-set key (e.g. `SSH_ASKPASS`) is passed straight to the OS process env.

Unlike `TaskCommands#env`, which merges `deploy_spec.machine_env` and `@task.env` (lib/shipit/task_commands.rb:33-48) and whose task/deploy env values are later filtered by `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` (app/models/shipit/deploy_spec.rb:174-180) using `EnvironmentVariables.with(env).permit(deploy_variables)`, the `StackCommands#fetch`/`#git_clone` path used for cloning/fetching the repository **never calls `filter_deploy_envs`**. So the review-stack-label-derived keys reach `git` unfiltered.

The attacker's exact action: an unprivileged user opens or labels a pull request in a fork-review-enabled repository with a label literally named `ssh_askpass` (case-insensitive since it's uppercased). GitHub sends a `pull_request` webhook (`labeled`/`opened`/etc.) to `POST /webhooks`; `LabelCapturingHandler` persists the label name to `pull_request.labels` (no signature bypass needed here — the webhook is legitimately signed by GitHub since the attacker owns the repo/PR and GitHub sends the real event). When Shipit's `ReviewStack` provisioning subsequently calls `fetch`/`git_clone` for that stack, `StackCommands#env` will include `SSH_ASKPASS=true` (or the attacker could name a label that is the label name only, so the value is fixed to `"true"` — the value itself is not attacker controlled, only the key). Since `SSH_ASKPASS` just needs to be set to a program path, and the value here is hardcoded `"true"`, the direct SSH_ASKPASS payload with a full path is not achievable through this specific vector because the value is always the literal string `"true"`, not an arbitrary attacker string — this limits exploitability of `SSH_ASKPASS` specifically, since `git`/`ssh` would try to execute a program literally named `true` (which exists on most systems as `/usr/bin/true`, a no-op, not attacker-controlled code). Existing guards: none prevent the key injection into env, but the injected value is fixed and not attacker-influenced content, which limits (but does not eliminate) the impact for env variables whose *value* — not just presence — is what typically confers RCE (e.g., `GIT_SSH`, `SSH_ASKPASS`, `LD_PRELOAD` require attacker-controlled paths, which this primitive does not provide).

### Impact Explanation
The vulnerability allows an attacker to inject arbitrary **environment variable keys** (set to the fixed value `"true"`) into `git fetch`/`git clone` invocations for their own review-stack repository, because `ReviewStack#env` has no allowlist and `StackCommands#env`/`Command#unbundled_env` never filter it. This is a real design flaw (key-injection with no allowlist, contrary to the intended invariant) but the concrete `SSH_ASKPASS` RCE claim requires an attacker-controlled *value* naming an executable path, which this primitive does not provide (`"true"` is always the value). Env variables that are pure boolean-like presence-based influencers of git behavior (e.g., `GIT_TERMINAL_PROMPT=true`, or safety features toggled via `_` prefix `SHIPIT_*`-alike overwrites) could plausibly be abused, but a full RCE chain via `SSH_ASKPASS` as literally described requires attacker-controlled value content that this path doesn't supply.

### Likelihood Explanation
Reaching the key-injection point is trivial and requires only: opening/labeling a PR to a repository with review-stacks enabled, which any fork PR author can do. However, achieving the specific "Critical RCE via SSH_ASKPASS" outcome as stated in the question requires the attacker to control the *value* assigned to `SSH_ASKPASS` (a path to an attacker-supplied script), and `ReviewStack#env` hardcodes the value to `"true"` regardless of label name — so the described full exploit chain (arbitrary program execution via SSH_ASKPASS) is not achievable through this exact code path.

### Recommendation
Add an explicit allowlist for review-stack label-derived env keys in `ReviewStack#env` (app/models/shipit/review_stack.rb), rejecting or filtering out any key overlapping with security-sensitive env vars (`SSH_ASKPASS`, `GIT_SSH`, `GIT_SSH_COMMAND`, `LD_PRELOAD`, `PATH`, etc.), and route `StackCommands#env` through the same `EnvironmentVariables.permit`/`VariableDefinition` allowlist mechanism used for `deploy_variables`/`rollback_variables` before it reaches `Command#unbundled_env`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (illustrative)
test "label names are merged into stack env unfiltered" do
  stack = shipit_review_stacks(:review_stack) # fixture with pull_request
  stack.pull_request.update!(labels: ['ssh_askpass'])
  env = stack.env
  assert_equal 'true', env['SSH_ASKPASS']
end

# test/unit/command_test.rb (illustrative)
test "unbundled_env passes through attacker-controlled keys with no allowlist" do
  command = Shipit::Command.new('true', env: { 'SSH_ASKPASS' => 'true' }, chdir: Dir.tmpdir)
  assert_equal 'true', command.unbundled_env['SSH_ASKPASS']
end
```
Note: this PoC demonstrates the key-injection primitive (no allowlist on env keys reaching `PTY.spawn`), but does NOT demonstrate arbitrary code execution, since `ReviewStack#env` always sets the value to the literal string `"true"`, not an attacker-chosen executable path. The `SSH_ASKPASS`-specific RCE claim in the question is therefore **not fully substantiated** by this code path as written — the underlying key-allowlist gap is real, but the "value naming an attacker program" step of the exploit chain is missing.
