### Title
API token stack-scope bypass in `Api::CCMenuController#stack` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via the `stack_id` column, and this scoping is the authorization boundary enforced by `Shipit::Api::BaseController#stack`/`#stacks`. `Shipit::Api::CCMenuController` overrides `#stack` with an implementation that skips this scoping, so a stack-scoped token can read the build/deploy status of any stack in the installation, not just the one it was authorized for.

### Finding Description
`Shipit::ApiClient` has an optional `belongs_to :stack` association [1](#0-0) . The base API controller derives an authorization-scoped `Stack` relation from this association:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every controller that inherits this `stack` helper (e.g. `MergeRequestsController`) is bound by the `stack_id?` scoping: if the authenticated `ApiClient` is scoped to a specific stack, only that stack can be resolved from `params[:stack_id]`, regardless of what value the caller supplies — this is confirmed by the test "an api client scoped to a stack will only see that one stack" for the stacks list endpoint.

`Shipit::Api::CCMenuController`, however, overrides `#stack` and drops the scoping entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

It still enforces the permission-name check (`require_permission :read, :stack`) [4](#0-3) , which only validates that the `read:stack` string is present in `current_api_client.permissions` [5](#0-4) , but never checks that the requested `stack_id` matches the token's bound `stack_id`. The binding that is broken is:

`current_api_client.stack_id` (the stack the token authorizes) ≠ `params[:stack_id]` (the stack whose status the request actually touches)

Before the crossing: for every other API endpoint, a stack-scoped token can only resolve `stack` to the one stack it belongs to. After: the same token, sent to `Api::CCMenuController#show`, can resolve `stack` to *any* stack in the database by simply changing `params[:stack_id]`, because the override bypasses the `stacks` scoping helper.

### Impact Explanation
This is an authorization-scope escape: an unprivileged holder of a legitimately-scoped, read-only API token (intended by an administrator to expose only one stack's status, e.g. for a CI status badge/CCMenu integration) can use that same token to read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`, lock state) of every other stack managed by the Shipit instance. This matches the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output" relative to the token's actual authorization, since the token was never authorized to read those other stacks.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (the `stack_id` association and its enforcement in `BaseController` exist specifically to support this use case, and is exercised by tests such as `test/controllers/api/stacks_controller_test.rb`). Exploitation requires only a valid, already-issued API token (Basic-Auth credential or `token` query param) scoped to any single stack — no additional privilege, session, or GitHub credential is needed; the attacker only changes the `stack_id` route parameter.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `BaseController` instead of querying `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that stack-scoped tokens can never resolve a stack outside their `stack_id` binding, consistent with every other API controller.

### Proof of Concept
1. As an admin, create (or have the system create) an `ApiClient` with `stack_id` set to Stack A and permission `read:stack` only (this is the exact configuration of the `here_come_the_walrus` fixture used in tests) [6](#0-5) .
2. Using that token's `authentication_token`, issue:
   `GET /api/<StackB-id>/ccmenu` (or the equivalent `stack_id` route param for an unrelated Stack B), with `Authorization: Basic <token>` or `?token=<token>`.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than `stacks.from_param!(...)`, the request succeeds (`200 OK`) and returns Stack B's CCMenu XML status, even though the token is only authorized (via `stack_id`) for Stack A. Equivalent requests to `Api::StacksController`, `Api::TasksController`, etc. with the same token and `stack_id` for Stack B correctly return an empty/404 result, confirming the bypass is specific to `CCMenuController`.
