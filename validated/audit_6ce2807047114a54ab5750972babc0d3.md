### Title
Cross-chain/cross-fork replay of `pallet-nfts` pre-signed mint and attribute approvals due to missing chain-binding data in the signed payload - (File: `substrate/frame/nfts/src/types.rs`, `substrate/frame/nfts/src/lib.rs`)

### Summary
`pallet-nfts` implements an off-chain, EIP-712-style delegated authorization scheme (`mint_pre_signed` / `set_attributes_pre_signed`) where a collection `Issuer`/`Admin` signs a `PreSignedMint`/`PreSignedAttributes` struct off-chain, and any relayer submits it on-chain. The signed payload is `Encode::encode(&mint_data)` / `Encode::encode(&data)` over fields `collection`, `item`, `attributes`, `metadata`, `deadline`, `only_account`, `mint_price` — none of which include a genesis hash, spec version, or chain/parachain identifier. This is the same missing-domain-separator pattern flagged in the Sherlock report for `CrabNetting._checkOrder()`: the signature is portable to any chain running the same pallet configuration with the same `CollectionId`/`ItemId` numbering. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The user entry point is the permissionless, signed extrinsic `mint_pre_signed`/`set_attributes_pre_signed`, callable by any account holding the token/relayer role; the origin only needs to be `Signed`, and the actual authorization comes from checking `signature` against `signer` off-chain data: [4](#0-3) 

The struct that gets hashed/signed never references genesis hash, spec version, or any parachain/relay identifier: [1](#0-0) [5](#0-4) 

By contrast, ordinary Substrate signed extrinsics are protected from cross-chain/fork replay by `frame_system::CheckGenesis`/`CheckSpecVersion` inside the runtime's normal `TransactionExtension` pipeline, as seen in every runtime's `TxExtension`: [6](#0-5) 

`pallet-nfts`'s pre-signed approval mechanism deliberately bypasses this pipeline — the signature is verified directly inside the pallet call via `Self::validate_signature(&Encode::encode(&mint_data), &signature, &signer)`, so none of the chain-binding transaction extensions apply to this payload. Both `pallet_nfts::Config` instances (Asset Hub Westend, Asset Hub Rococo, etc.) share identical `OffchainSignature`/`OffchainPublic` wiring: [7](#0-6) [8](#0-7) 

Because Substrate `AccountId`s are just public keys valid on every chain, and `CollectionId`/`ItemId` are small integers chosen sequentially per chain, an Issuer's off-chain signature for `(collection=0, item=0, ...)` on one chain is byte-identical to, and thus valid on, any other chain (a hard fork, a canary/testnet clone of the runtime, or a differently-named but identically-configured parachain) where that same account happens to hold Issuer/Admin rights over a collection with the same ID.

### Impact Explanation
If the signing account is (or later becomes) an Issuer/Admin of an identically-numbered collection on a second, protocol-compatible chain (a hard fork of the chain, or another deployment of the same runtime), a previously-issued off-chain mint/attribute authorization can be replayed there without the signer's consent, causing unauthorized minting of items, unauthorized attribute writes, and unintended fund transfers (`mint_price` is paid by the relayer's account performing the mint). This mirrors the Medium severity assigned to the original report: it is a signature-replay-across-forks/chains issue rather than a direct fund-theft primitive, since it requires the twin-chain precondition (same signer holding the matching role and identical `CollectionId`) to be reachable.

### Likelihood Explanation
Likelihood is Medium/Low in isolation: it requires either (a) the parachain undergoing a contentious hard fork that preserves state (which the referenced report explicitly calls out as an in-scope replay scenario), or (b) two distinct deployments of the same runtime (e.g. a testnet and canary network, or two similarly-configured system parachains) where the same account happens to be issuer of a matching `CollectionId`. This is materially more plausible in Substrate/Polkadot ecosystems than in isolated EVM contracts, because system parachains (Asset Hub Westend/Rococo) intentionally run byte-for-byte identical `pallet-nfts` configurations, and account keys are chain-agnostic.

### Recommendation
Bind the signed payload to the chain by including a chain-specific domain value inside `PreSignedMint`/`PreSignedAttributes` (or in the message passed to `validate_signature`), e.g. `frame_system::Pallet::<T>::block_hash(0)` (genesis hash), `<T as frame_system::Config>::Version::get().spec_version`, or an explicit `ParaId`/genesis hash constant, analogous to EIP-712's `chainId` domain field. Alternatively, route this authorization scheme through the existing `pallet_verify_signature`/`TransactionExtension` machinery which already composes `CheckGenesis`/`CheckSpecVersion` for exactly this purpose.

### Proof of Concept
I was not able to fully inspect `Self::validate_signature`'s body (only its call sites and the `PreSignedMint`/`PreSignedAttributes` encodings were retrievable before the tool budget was exhausted), so I cannot provide a compiled/executed Rust reproduction here. The existing unit tests `validate_signature`, `pre_signed_mints_should_work`, and `pre_signed_attributes_should_work` in `substrate/frame/nfts/src/tests.rs` confirm the exact wire format that is signed (`Encode::encode(&mint_data)` / `Encode::encode(&pre_signed_data)`) contains no chain-identifying field, which is the crux of the reported bug-class; however, demonstrating actual state loss would require standing up two runtime instances (e.g., two `new_test_ext()` executions with distinct genesis config but identical `CollectionId` state) and showing the same signature validates in both — this was not executed. This finding should be treated as a design-level replay-protection gap requiring further validation before treating it as a confirmed, exploitable bounty submission.
