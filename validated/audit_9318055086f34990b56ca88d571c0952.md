### Title
Membership webhook signature is verified against `organization.login` but the mutated `Team` is looked up by attacker-controlled `team.id`, allowing cross-org team-membership forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook using only `params.dig('organization','login')` to choose which org's `webhook_secret` to validate against, and `MembershipHandler#find_or_create_team!` looks up the target `Team` solely by `params.team.id` (`github_id`) with no check that the team belongs to that verified organization. An attacker who owns their own GitHub org can send a validly-signed `membership` webhook naming their own org's login (for signature selection) while pointing `team.id` at a `Team` record whose `github_id` belongs to a different organization, and thereby add/remove arbitrary GitHub logins as members of that victim `Team`.

### Finding Description
Broken binding: the equality the code implicitly assumes is `organization_whose_secret_verified_the_body == organization_owning_the_team_being_mutated`. In reality:
- `repository_owner` = `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  — for `membership` events there is no `repository` key, so this resolves purely to `params['organization']['login']`, which is attacker-supplied and only need match the org whose secret the attacker controls.
- `verify_signature` picks `Shipit.github(organization: repository_owner)` and HMAC-validates against that org's own `webhook_secret` [2](#0-1) . Since the attacker legitimately owns `attacker-org` and configured its webhook secret, this check trivially passes.
- `MembershipHandler#find_or_create_team!` resolves the target record purely via `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) . If a `Team` with that `github_id` already exists (created earlier from the victim org's own legitimate webhook), `find_or_create_by!` returns the existing record and the block (which would set `team.organization`) never runs — so `team.organization` remains the victim's, but the handler proceeds to mutate its membership anyway.
- `process` then executes `team.add_member(member)` or `team.members.delete(member)` [4](#0-3) , with `member` being an arbitrary GitHub login the attacker names in `params.member.login`, found-or-created via `User.find_or_create_by_login!` [5](#0-4) .

No code path cross-checks `params.organization.login` against the pre-existing `team.organization` before mutating membership, so an attacker's org identity used for HMAC verification is never bound to the specific team record being written.

Attacker request: POST `/webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with `attacker-org`'s own `webhook_secret`, and body:
```json
{
  "action": "added",
  "team": {"id": <victim_team_github_id>, "name": "...", "slug": "...", "url": "..."},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-controlled-login"}
}
```

### Impact Explanation
This lets an attacker add an arbitrary GitHub account (including their own) as a member of any pre-existing Shipit `Team` record, as long as they can learn/guess its numeric `github_id` (team IDs are visible via GitHub's public API for public org teams, or via any prior interaction). `User#authorized?` grants access when `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) . If the targeted `Team` is one of the configured `Shipit.github_teams`, this webhook forgery becomes a direct escalation into `Shipit.github_teams` authorization for an attacker-chosen GitHub identity — matching the High severity category ("escalation into `Shipit.github_teams` authorization"). It is repeatable against any team whose `github_id` the attacker can obtain, and requires only an attacker-owned GitHub organization to source a validly-signed webhook.

### Likelihood Explanation
Preconditions: the attacker must own/administer at least one GitHub organization already registered in `Shipit.github` configuration (so `Shipit.github(organization: 'attacker-org')` resolves and `verify_webhook_signature` succeeds using a secret the attacker set themselves), and must know the numeric `github_id` of a target team belonging to `Shipit.github_teams`. Both are low-cost: creating a GitHub org and wiring it as a Shipit-recognized organization (if the deployment allows self-registration/multiple orgs) or simply reusing a legitimately connected org is feasible, and team IDs are discoverable through GitHub's REST API for teams the attacker can view. No Shipit session, API token, or secret is required. The attack is fully repeatable per target team/member pair.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and any other handler resolving records purely by GitHub numeric ID from webhook payload), verify that `params.organization.login` matches the existing record's `organization` column before performing any mutation, raising/dropping the event on mismatch. More generally, `WebhooksController#verify_signature` should ensure the verified `repository_owner`/organization is bound to every entity the handler subsequently mutates, not just used to pick which secret to check the HMAC against.

### Proof of Concept
Minitest plan (no live GitHub, WebMock-free controller test per repo conventions in `test/controllers/webhooks_controller_test.rb`):
1. Create `victim_team = Team.create!(organization: 'victim-org', github_id: 555, name: 'core', slug: 'core', api_url: '...')`.
2. Configure two orgs in `Shipit.github_teams`/config fixtures such that `Shipit.github(organization: 'attacker-org')` resolves with a known `webhook_secret_attacker`.
3. Build a membership payload: `{"action"=>"added","team"=>{"id"=>555,...},"organization"=>{"login"=>"attacker-org"},"member"=>{"login"=>"mallory"}}`.
4. Compute `X-Hub-Signature` using `webhook_secret_attacker` (attacker's own known secret) over the raw JSON body.
5. POST to `/webhooks` with `X-Github-Event: membership` and that signature.
6. Assert response is `:ok` (signature verified) and then assert `victim_team.reload.members.map(&:login)` now includes `"mallory"` — i.e., `victim_team.organization` (`'victim-org'`) != the verifying `organization.login` (`'attacker-org'`), demonstrating the two sides of the binding diverge while the mutation still occurs.
