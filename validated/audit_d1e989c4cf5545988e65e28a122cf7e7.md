### Title
Unauthenticated cross-stack read via `Api::CCMenuController#stack` bypassing the `current_api_client.stack_id` scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the `stack` accessor with `Stack.from_param!(params[:stack_id])` instead of using the scoped `stacks.from_param!` defined in `Api::BaseController`, so the `read:stack` token minted by `CCMenuUrlController#fetch` for one stack can be replayed against any other stack's CCTray XML endpoint by simply changing `stack_id` in the URL.

### Finding Description
The intended binding is: for any request to `Api::CCMenuController#show`, `Stack.from_param!(params[:stack_id]) ∈ stacks` where `stacks = current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` (`app/controllers/shipit/api/base_controller.rb:74-80`). `CCMenuController` breaks this by redefining `stack`: [1](#0-0) 

This resolves any stack by id/param with no relation to `current_api_client` at all, so the equality never holds — `stack` is drawn from `Stack.all` unconditionally, regardless of what `stacks` would have restricted it to.

Separately, `CCMenuUrlController#fetch` creates (or reuses) a single, non-stack-scoped `ApiClient`: [2](#0-1) 

`find_or_create_by!(creator: current_user, name: 'CCMenu Client')` never sets `stack:`, so `current_api_client.stack_id` is `nil` for every such client and `current_api_client.stack_id?` is `false`. This means even the "correctly scoped" `stacks` method in `Api::BaseController` (`app/controllers/shipit/api/base_controller.rb:74-76`) would resolve to `Stack.all` for this client type, not just the stack the URL was minted for — the token itself is not stack-restricted at the `ApiClient` level. `check_permissions!` only checks the `read:stack` permission string, not any stack identity (`app/models/shipit/api_client.rb:38-45`).

Attacker flow: an authenticated (or already-permissioned) user runs `CCMenuUrlController#fetch` for stack A, receiving a URL like `/api/stacks/:stack_a/ccmenu.xml?token=T`. Anyone possessing `T` (an unprivileged party who intercepts or is handed the link, e.g. via a status badge/README embed) can request `/api/stacks/:stack_b/ccmenu.xml?token=T` for any other stack B and receive `stack_b.deploys_and_rollbacks.last` XML, because neither `CCMenuController#stack` nor the underlying `ApiClient` enforce any stack binding.

None of the existing guards catch this: `require_permission :read, :stack` only checks the permission string exists on the token (`app/controllers/shipit/api/ccmenu_controller.rb:6`, `app/models/shipit/api_client.rb:38-45`); there is no `Stack`-identity check anywhere in the request path.

### Impact Explanation
Any holder of a CCMenu token minted for stack A can read deploy/rollback status (build status, last build label/time, activity) for **any** stack in the Shipit instance, not just the intended one — an unauthenticated cross-tenant read of stack state and deploy output. This matches the "High - unauthenticated read of stack state" impact category. It does not permit writes, so it does not reach the "Critical" bar (no deploy/rollback/merge mutation), but it is a full, repeatable read-scope escape across all stacks/repositories on the instance.

### Likelihood Explanation
Preconditions: attacker needs one valid CCMenu token, which requires a legitimate CCMenu URL to have been minted at some point by any user for any stack (a very common feature use-case — CI badges are frequently shared/embedded in READMEs, status pages, or leaked via referrer headers). No GitHub secrets, session, or API-client credentials are needed beyond obtaining that one token string. Once obtained, the attacker can enumerate arbitrary `stack_id` values (stack slugs are typically `owner/repo/branch`-derived and guessable/public) and repeat the read against every stack. This is highly feasible and fully repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped resolution from `Api::BaseController` (remove the override, or implement `@stack ||= stacks.from_param!(params[:stack_id])`), and additionally bind the `ApiClient` created in `CCMenuUrlController#fetch` to the specific stack (`stack: stack`) so `current_api_client.stack_id` is always set and `stacks` correctly restricts to `Stack.where(id: current_api_client.stack_id)`.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (or a new test file under `test/controllers/api/`):
```ruby
test "a token minted for one stack cannot read another stack's status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: 'foo', name: 'bar'), branch: 'main')

  client = ApiClient.create!(creator: shipit_users(:walrus), name: 'CCMenu Client',
                              permissions: %w[read:stack], stack: stack_a)

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  # Binding under test: Stack.from_param!(params[:stack_id]) ∈ Stack.where(id: client.stack_id)
  # stack_b.id != stack_a.id  =>  request must be rejected, not rendered.
  assert_response :forbidden # currently fails: renders :ok with stack_b's XML
end
```
This demonstrates that with a stack-bound `ApiClient` and the current unscoped `Api::CCMenuController#stack`, `stack_b` (outside the client's authorized stack) is rendered successfully, proving the cross-stack read.
