### Title
Merkle tree leaf/internal-node hash collision (missing domain separation) allows forging membership proofs for `is_valid_merkle_proof` / `in merkle` - (File: `merkle.js`)

### Summary
`merkle.js` computes both leaf hashes and internal node hashes with the exact same function, `hash(str) = sha256(str)`, with no prefix or length separator distinguishing "hash of a leaf value" from "hash of two concatenated child hashes." [1](#0-0)  This is the classic Merkle-tree second-preimage weakness: any string equal to the concatenation of two existing node hashes (`h1+h2`) hashes to exactly the same value as the internal node that combines those children, with no cryptography broken — it's a structural collision. Any AA or address definition that relies on `is_valid_merkle_proof`/`in merkle` to authorize access based on tree membership can be tricked into accepting a value that was never a genuine leaf of the tree.

### Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree by repeatedly calling `hash()` on concatenated strings, with leaves hashed the same way as sibling pairs: `hash(arrHashes[i] + arrHashes[hash2_index])`. [2](#0-1)  Verification in `verifyMerkleProof` starts from `the_other_sibling = hash(element)` and then folds in `proof.siblings` exactly the same way a legitimate leaf would be folded in: [3](#0-2) 

Because there is no domain-separating byte (e.g. `0x00` for leaves vs `0x01` for internal nodes) and no length prefixing, an attacker who knows any two sibling hash values from the real tree (`h1`, `h2` — trivially recoverable from any legitimate proof, or from a publicly-known whitelist dataset) can pick `element = h1 + h2`. Then `hash(element)` equals the real internal node hash at that level by construction. By supplying `proof.siblings` = the true siblings from that level up to the root, and `proof.index` shifted accordingly, `verifyMerkleProof(element, proof)` returns `true`, and `proof.root` is the actual valid published root — with `element` never having been an original leaf.

This primitive is exposed to unprivileged callers in two places:
- The oscript `is_valid_merkle_proof` formula function, reachable from AA bytecode acting on fully attacker-controlled trigger data (`element_expr`, `proof_expr`), used by AA authors to implement merkle-whitelist gated logic (e.g. airdrop/allowlist AAs). [4](#0-3) 
- The `'in merkle'` address-definition authentifier, which verifies a fixed `element` from the definition against an attacker-supplied serialized proof and checks the resulting root against an oracle's data feed. [5](#0-4) 

For an AA that stores a `merkle_root` state var and validates trigger-supplied `(element, proof)` pairs against a whitelist (the direct analog of the NounsBuilder `MerkleReserveMinter` pattern cited in the report), an attacker fully controls both `element` and the entire `proof` object (including its embedded `root` field), enabling the collision construction above without needing to break SHA-256.

### Impact Explanation
An attacker can construct an `element` value that is falsely proven to be a member of a merkle-committed set (e.g., an AA airdrop/allowlist), causing the AA to release funds, mint an asset, or grant a privileged action to an address/value that was never actually whitelisted. This is unauthorized fund release / AA fund loss, matching the required "AA fund loss" impact category.

### Likelihood Explanation
Exploitability requires only structural knowledge of the merkle tree (any two known sibling hash values, obtainable from any legitimate proof or from a public dataset used to build the whitelist) — no cryptographic primitive is broken. Any AA that adopts the common merkle-whitelist pattern using `is_valid_merkle_proof` on trigger-supplied data is directly exposed. Likelihood is Medium-High for such AAs since the underlying `merkle.js` library provides no protection and the vulnerable pattern is a standard, expected usage of the primitive.

### Recommendation
Add domain separation in `merkle.js`: prefix leaf hashing and internal-node hashing with distinct tags, e.g. `hash('\x00' + element)` for leaves and `hash('\x01' + left + right)` for internal nodes, and update `verifyMerkleProof`/`getMerkleProof`/`getMerkleRoot` consistently. Because this changes the hash values and thus consensus-relevant results for AAs already using `is_valid_merkle_proof`, this must be introduced behind an MCI-gated protocol upgrade (similar to `bPostPemCurvesFix`) rather than as a silent change.

### Proof of Concept
1. Build (or observe) a merkle tree of ≥4 leaves via `merkle.getMerkleRoot`/`getMerkleProof` from `merkle.js`. [6](#0-5) 
2. From any legitimate proof for a leaf in the left half of the tree, extract the first-level sibling pair hashes `h1 = hash(leaf0)`, `h2 = hash(leaf1)`, and the remaining siblings array `S` used for the upper levels of that leaf's proof.
3. Set `element = h1 + h2` (raw string concatenation of the two base64 digests).
4. Build `proof = { root: <the real published root>, index: <leaf0 index >> 1>, siblings: S (with the first, lowest-level sibling removed) }`.
5. Call the AA/oscript with `is_valid_merkle_proof(element, proof)` (or `'in merkle'` if applicable) — it returns `true` even though `element` was never part of the original dataset, satisfying whatever AA logic separately compares `proof.root` to the stored whitelist root.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
