## Analog Vulnerability Found

### Title
Webhook signature verification is bound to the payload's claimed organization, not the repository the handler actually writes to, enabling cross-tenant forged events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is the same class of bug as the ERC-4626 `maxDeposit` report: a check is performed against one binding (which asset amount a redeem can cover), while a different, unguarded quantity (the effective withdrawable amount) is what actually gets used downstream, letting the two diverge and break an invariant the caller relies on. In Shipit, `WebhooksController#verify_signature` selects the `webhook_secret` to validate against using `repository_owner` (taken from the payload's `repository.owner.login`, falling back to `organization.login`), but every webhook `Handler` subsequently resolves which `Stack`/`Repository` to mutate using a *different* field, `repository.full_name` [1](#0-0) . Nothing binds these two fields together beyond both appearing in the same HMAC-signed JSON blob picked by the attacker.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration (and thus the `webhook_secret` used for HMAC verification) based on `repository_owner`: [2](#0-1) 

Shipit supports multiple GitHub organizations configured in `secrets.yml`, each with its **own** independent `webhook_secret`: [3](#0-2) 

`verify_webhook_signature` only proves that the entire raw body was HMAC-signed with the secret belonging to whichever org `repository_owner` names: [4](#0-3) 

Once verification succeeds, every event `Handler` looks up the target `Stack`/`Repository` using a *separate* JSON field, `repository.full_name`, not `repository.owner.login`/`organization.login`: [1](#0-0) 

The same pattern repeats in `PushHandler#process` (drives `Stack#sync_github`) [5](#0-4)  and in the pull-request handlers that archive/unarchive review stacks and mutate `PullRequest` labels using `Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) [7](#0-6) .

Because `repository.owner.login`/`organization.login` (the field the *secret selection* trusts) and `repository.full_name` (the field the *handler* trusts) are two independently attacker-controlled strings inside the same JSON body, an operator of tenant org `A` — who legitimately possesses their own org's `webhook_secret` because they registered/administer their own GitHub App installation on a multi-tenant Shipit instance — can craft a payload where `organization.login`/`repository.owner.login = "org-a"` (so `verify_signature` selects and validates against org-a's secret) while `repository.full_name = "org-b/victim-repo"` (an entirely different tenant's repository). The HMAC only proves *tenant A* produced the bytes; it proves nothing about which repository those bytes claim to describe.

**Binding broken**: `verified_signing_organization == payload.repository.full_name.split('/').first` is assumed but never enforced. `verify_signature` checks the former; every `Handler` acts on the latter.

### Impact Explanation
An attacker who controls only their own tenant's `webhook_secret` (an unprivileged actor with respect to any other tenant, no `ApiClient` token, no GitHub App private key, no repository write access on the victim repo) can forge webhook deliveries that are accepted as authentic for a **different** organization's repositories. Depending on handler and existing Shipit state, this can:
- Trigger `GithubSyncJob`/`stack.sync_github` for another tenant's `Stack` [8](#0-7) , forcing unscheduled resyncs/spec cache rebuilds against a repo the attacker doesn't own.
- Archive/unarchive another tenant's review stacks or flip provisioning state via the `pull_request` `labeled`/`unlabeled`/`closed`/`reopened` handlers [9](#0-8) , which is a cross-repository state write the attacker has no legitimate authorization for.

This is a cross-tenant, cross-repository write achieved purely by exploiting the mismatch between the field used for cryptographic authentication and the field used for authorization/target-selection — matching the Critical "cross-repository writes" impact category.

### Likelihood Explanation
Requires the multi-organization deployment mode (`secrets.github` with more than one org key, as documented and templated in `config/secrets.development.shopify.yml`) and requires the attacker to control one tenant's `webhook_secret` — a credential a legitimate, but unprivileged-with-respect-to-other-tenants, org owner already has by design (it's handed out to every onboarded GitHub App owner). No GitHub App private key, `ApiClient` token, or repository write access to the victim repo is needed, satisfying the unprivileged-attacker constraint.

### Recommendation
After the signature check succeeds, verify that the organization used to select the `webhook_secret` (`repository_owner`) matches the owner encoded in `repository.full_name` (and any other repo/org identifiers the handler will subsequently trust) before dispatching to a `Handler`. Alternatively, resolve the target `Stack`/`Repository` using the same trusted identifier that governed secret selection, rather than a second, independently-supplied field.

### Proof of Concept
1. Deploy Shipit with two orgs configured, e.g. `org-a` (attacker-controlled webhook, secret known to attacker) and `org-b` (victim), per `config/secrets.development.shopify.yml`.
2. Attacker crafts a `push` (or `pull_request`) JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "organization": { "login": "org-a" },
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`), and `verify_webhook_signature` succeeds because the attacker legitimately holds `org-a`'s secret.
5. `PushHandler#process` (via `Handler#repository_name` → `payload.dig('repository','full_name')`) resolves `Repository.from_github_repo_name("org-b/victim-repo")` and enqueues `GithubSyncJob` against `org-b`'s `Stack`, despite the request never having been signed by `org-b`'s GitHub App/secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit

            .where(branch:)

          params.ref.gsub('refs/heads/', '')
        end
      end
    end
```
