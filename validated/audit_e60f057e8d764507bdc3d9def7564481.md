## Title
Asset Definer Can Freeze Any Holder's Balance by Republishing the `spender_attested` Attestor List - ([File: validation.js])

### Summary
For any asset created with `spender_attested: true`, the asset **definer** (issuer) can, at any time and without limitation, publish a new `asset_attestors` message that completely replaces the list of addresses allowed to hold/spend the asset. Because every subsequent payment — for both **input owners and output recipients** — must appear on the *latest* attestor list, the definer can unilaterally strip an address that currently holds a balance from that list, permanently freezing the funds already on-chain for that address, exactly analogous to the reported pattern of a privileged party removing a registered dependency (`unregisterDepository`) and thereby blocking withdrawals for depositors who already have funds committed.

### Finding Description
When an asset is defined with `spender_attested = true`, every payment message (issue, transfer) is validated against the *current* attestor list for that asset: [1](#0-0) 

and for the output side of the transaction as well: [2](#0-1) 

and for each individual spent input: [3](#0-2) 

The "current" attestor list is not the list that was in effect when the coin was acquired — it is always the *latest* list published before the last ball, resolved via `storage.readAsset` → `addAttestorsIfNecessary`, which simply orders by level/rowid and takes the newest attestor-list unit: [4](#0-3) 

The only requirement to publish a new attestor list is to be the asset's definer — there is no restriction preventing removal of addresses that already hold a balance, no notice period, and no way for a currently-attested holder to protect existing funds: [5](#0-4) 

`checkAttestorList` only validates that the list is well-formed (sorted, valid addresses, within `MAX_ATTESTORS_PER_ASSET`) — it performs no check that previously-attested addresses with outstanding balances remain included: [6](#0-5) 

Consequently, a malicious or compromised definer can:
1. Wait until users accumulate balances of the `spender_attested` asset.
2. Publish a new `asset_attestors` message that excludes those users' addresses.
3. From that point on, any attempt by the excluded addresses to spend their existing balance fails validation with `"owner address is not attested"` (for divisible assets) or the equivalent private-asset check, and any attempt to receive/hold the asset likewise fails the output-side attestation check.

This mirrors the reported bug class precisely: a privileged entity (asset issuer/definer, analogous to the depository-registry owner) can retroactively revoke access rights that block already-deposited/held value from being withdrawn or moved, with no safeguard tied to existing balances.

### Impact Explanation
Any holder of a `spender_attested` asset can have their entire balance of that asset permanently frozen at the sole discretion of the asset definer, with no on-chain recourse — the coins remain provably existing (they show up in `outputs`/`asset_denominations`) but become permanently unspendable and unreceivable for the deattested address. This is a direct asset-freezing impact affecting real user funds, not merely a UX or DoS issue, and requires no cooperation or error from the victim.

### Likelihood Explanation
This requires only the definer role for the specific asset (the asset issuer, one of the explicitly in-scope unprivileged/allowed actors relative to normal users) to publish a single valid `asset_attestors` message — a completely permitted, cheap, and unrestricted operation already supported by the protocol. Any asset that opts into `spender_attested = true` is exposed, and the operation can be repeated at will to target any specific address.

### Recommendation
- Do not resolve attestor eligibility solely from the *latest* attestor list; instead, evaluate attestation status as of the time the coin/output was created (or grandfather previously-attested holders until they voluntarily move funds), similar to how `is_stable`/`main_chain_index` snapshots are used elsewhere.
- Alternatively, require that a removed address be given an explicit exit window (e.g., a delay before removal takes effect) or restrict attestor-list updates to only add addresses, with removal requiring a separate, balance-aware mechanism.
- At minimum, document this centralization risk clearly for asset issuers/users, since it currently allows one-sided, immediate freezing of arbitrary holders' funds.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and initial `attestors: [X]` (validated by `validateAssetDefinition`/`checkAttestorList`, `validation.js:2725-2864`).
2. Address `X` receives/holds a balance of asset `A` (validated per `validatePaymentInputsAndOutputs`, `validation.js:2606-2676`, requiring `X` to be in `arrAttestedAddresses`).
3. `D` publishes a new `asset_attestors` message for asset `A` with `attestors: [Y]` (excludes `X`). This passes validation because `validateAttestorListUpdate` only checks that `D` is the definer (`validation.js:2829-2848`) and that the list is well-formed (`validation.js:2850-2864`).
4. `storage.readAsset`'s `addAttestorsIfNecessary` now resolves the asset's `arrAttestorAddresses` to `[Y]` only, because it always picks the most recent attestor-list unit (`storage.js:1917-1946`).
5. `X` attempts to spend its existing balance of asset `A`. `validatePaymentInputsAndOutputs` rejects the input with `"owner address is not attested"` (`validation.js:2506-2507` / `2432-2433` for private assets), permanently freezing `X`'s funds.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
