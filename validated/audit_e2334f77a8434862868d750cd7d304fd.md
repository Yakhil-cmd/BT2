## Title
StatusHandler matches commits by raw sha across all stacks, letting an attacker-signed webhook for one repository trigger continuous delivery on another repository's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

## Summary
`Shipit::WebhooksController#verify_signature` only checks that the webhook signature matches the organization named in the payload's `repository.owner.login`, i.e. it authenticates *who sent this payload*, not *which stack the payload is allowed to affect*. `StatusHandler#process` then looks up commits purely by `Commit.where(sha: params.sha)` with no repository/stack scoping, so a validly-signed webhook from the attacker's own repository can flip the status of, and trigger continuous delivery on, any other stack whose commit table happens to contain a commit with the same SHA (e.g. shared history between a fork and upstream).

## Finding Description
The claimed broken binding, stated as an equality: **the organization whose `webhook_secret` authenticated the request MUST equal the organization owning the stack that `Stack#trigger_continuous_delivery` acts on.** In this code path they are not enforced to be equal.

Path:
1. `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) derives `repository_owner` from `params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. This only proves the attacker controls a repo/org whose secret matches — it can be the attacker's own org. [1](#0-0) 
2. `create` then dispatches the raw parsed payload to every handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` — the payload (including whatever `sha` the attacker chooses) is passed on unmodified. [2](#0-1) 
3. `StatusHandler#process` resolves target commits solely by SHA, with **no repository filter**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [3](#0-2) 
Note that the base `Handler` class does provide a `stacks`/`repository_name`-scoped helper (`Repository.from_github_repo_name(repository_name)&.stacks`), but `StatusHandler` does not use it at all. [4](#0-3) 
4. `Commit#create_status_from_github!` creates a `Status` row on whatever commit(s) matched by sha, regardless of stack/org: `statuses.replicate_from_github!(stack_id, github_status)`. [5](#0-4) 
5. `Status` creation triggers `after_commit :schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → if `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) is true, `Stack#trigger_continuous_delivery` is invoked on the **victim's** stack. [6](#0-5) [7](#0-6) 

Exploit flow: attacker sends `POST /webhooks` with `X-Github-Event: status`, a body whose `repository.owner.login` is the attacker's own GitHub org (so the signature check passes with the attacker's own `webhook_secret`), but whose `sha` and `state: success` matches a commit that exists in a victim stack (e.g., because the victim stack's repository and the attacker's forked/mirrored repository share commit history/SHAs, which is normal in Git). Because `StatusHandler` never checks that the commit's owning repository matches the payload's `repository.owner`/`full_name`, the victim commit gets a new successful `Status`, and if that commit is otherwise unlocked, not blocked, and the victim stack has continuous delivery enabled, a deploy is enqueued for a stack the attacker never authenticated against.

Existing guards do not stop this: `verify_signature` authenticates the org named in the payload, not the org that owns the commit being mutated; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema in `StatusHandler` only validates `sha`/`state`/etc. types, not repository binding; there is no `stacks` scoping applied in `StatusHandler#process` (unlike other handlers that use the `stacks`/`repository_name` helper from `Handler`).

## Impact Explanation
This is a payload for one repository (the attacker's) causing a mutation and unauthorized deploy trigger on another repository's stack (the victim's) — squarely a Critical-severity "unauthorized deploy" finding per the rules. The attacker gains the ability to force a `Deploy` to be enqueued against any stack with continuous delivery enabled whose commit table contains a shared SHA with a repository the attacker controls, without ever authenticating against the victim's organization or stack. This is repeatable per shared SHA/commit and is not limited to a single stack — any number of victim stacks sharing history with attacker-controlled repositories are exposed.

## Likelihood Explanation
Preconditions: the victim stack must have `continuous_delivery` enabled, the targeted commit must be unlocked and either CI-ignored or already `success?` and unblocked (per `deployable?`), and the attacker must own/control a GitHub repository (or otherwise be able to send a validly-signed webhook for some org) whose commit history shares at least one SHA with the victim's tracked repository — a very plausible scenario for forks, mirrors, or repositories with a shared upstream history. The attacker's cost is minimal: create/own a repo, get GitHub to sign (or manually construct and self-sign, since signature verification only needs the attacker's own secret) a `status` webhook, and send it to `POST /webhooks`. No Shipit credentials, session, or `Shipit.github_teams` membership are needed.

## Recommendation
Scope `StatusHandler#process` to only mutate commits belonging to stacks whose repository matches the authenticated payload's `repository.full_name`. Use the existing `Handler#stacks`/`repository_name` helper (or equivalent) to filter `Commit.where(sha: params.sha)` down to `commit.stack.repository.github_repo_name == repository_name` (or join through `stacks`) before calling `create_status_from_github!`, so a webhook signed for org A can never mutate a commit/stack owned by org B even if the SHA collides.

## Proof of Concept
Minitest plan (no live GitHub, stub `verify_signature`/`verify_webhook_signature` as done in existing tests):

```ruby
test "a status webhook for repository A cannot trigger continuous delivery on repository B's stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_delivery: true)
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, author: shipit_users(:shipit))
  # commit otherwise unlocked, stack.ignore_ci? or success+unblocked

  attacker_repo_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'created_at' => Time.now.to_formatted_s(:db),
    'repository' => { 'full_name' => 'attacker/evil-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true) # simulate attacker's own valid signature for attacker-org

  Shipit::Stack.any_instance.expects(:trigger_continuous_delivery).never

  request.headers['X-Github-Event'] = 'status'
  post :create, body: attacker_repo_payload.to_json, as: :json

  # Currently this assertion FAILS because trigger_continuous_delivery IS called,
  # proving the cross-repo trigger. The fix must make this assertion pass.
end
```

The binding equality to assert on both sides: `payload['repository']['owner']['login'] == victim_commit.stack.repository.github_repo_name.split('/').first` must hold before `Stack#trigger_continuous_delivery` runs on `victim_commit.stack`; today it is never checked.
