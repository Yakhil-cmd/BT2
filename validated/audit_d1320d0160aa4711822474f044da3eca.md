### Title
Merkle proof forgery via node-as-leaf second-preimage attack in `verifyMerkleProof` bypasses `in merkle` spending conditions - (File: merkle.js)

### Finding Description
The ZetaChain report centers on the fact that a security-critical verification (`VerifyEVMInTxBody`) uses a proof-check that is not cryptographically rigorous enough to reliably distinguish legitimate from illegitimate data, and recommends "verifying the receipt merkle trie proof" as the correct, rigorous mechanism. In `ocore`, the analogous merkle-proof verification primitive that *is* actually used to gate spending — `merkle.verifyMerkleProof()` — has the classic defect that the recommended fix is supposed to avoid: it hashes leaves and internal nodes with the exact same hash function and no domain separation. [1](#0-0) [2](#0-1) 

`getMerkleRoot`/`getMerkleProof` build the tree with `hash(x) = sha256(x)` applied identically to raw elements (leaves) and to concatenated child hashes (internal nodes). `verifyMerkleProof` starts by computing `hash(element)` and then repeatedly combines with the supplied `siblings`, comparing the final value to `proof.root`. Because there is no leaf/node prefix (e.g. `0x00`/`0x01`) distinguishing the two hash domains, any two adjacent node hashes `L` and `R` inside a tree can be concatenated into a forged "element" string `L+R`. Feeding `element = L+R` together with the sibling path *above* that level into `verifyMerkleProof` makes `hash(element)` equal exactly the real parent node hash that would have resulted from hashing the true children — so the forged element passes verification as if it were a genuine array member, even though it was never part of the original `arrElements` that produced the published merkle root.

This primitive is wired directly into address-definition spending logic via the `in merkle` operator, which authorizes signing based on whether a supplied element is included under a merkle root posted as a data feed by a trusted oracle address: [3](#0-2) 

The same primitive is validated as a syntactically-allowed address-definition condition here: [4](#0-3) 

The developers themselves flagged awareness of this exact hazard in the code comment "// Node-as-Leaf issue might matter in some cases" directly above the vulnerable verification loop, but no domain-separation fix (leaf/internal-node prefixing) was implemented.

### Impact Explanation
Any address whose spending definition uses `['in merkle', [oracle_addresses, feed_name, element, min_mci]]` to gate authorization (e.g., a shared/multisig-like address, an asset transfer condition, or a private-payment counterparty's spending path keyed to a whitelist merkle root) can potentially be unlocked by an attacker who never actually possesses a whitelisted element. By harvesting any two sibling hash values from the tree (obtainable from any legitimate proof previously published, or by requesting/observing one), an attacker constructs a forged element and truncated sibling path that `verifyMerkleProof` accepts as valid inclusion. This directly satisfies an "unauthorized spending" bypass of an on-chain authorization condition — the address-definition authentifier evaluates to `true` for data that was never authorized by the oracle/asset issuer, allowing signing/spending of funds that should have been gated by a legitimate whitelist membership check.

### Likelihood Explanation
Exploitation only requires knowledge of the raw merkle-tree hash values at some level (a normal by-product of any two published proofs, or of an attacker who is also a legitimate holder of one whitelisted element and thus knows a sibling hash), plus the ability to submit a unit with a crafted `authentifiers` proof for the `in merkle` path — something any ordinary unit poster / AA trigger sender / private-payment counterparty can do without special privilege. No control over the oracle, hub, or network is needed, and the flaw is deterministic (not probabilistic), making the attack straightforward once two sibling hash values from the same tree level are known.

### Recommendation
Add domain separation to `merkle.js`: hash leaves with a distinct prefix (e.g. `sha256(0x00 || element)`) and internal nodes with a different prefix (e.g. `sha256(0x01 || left || right)`) in both `getMerkleRoot`/`getMerkleProof` (tree construction) and `verifyMerkleProof` (verification), so that a concatenation of two node hashes can never be reinterpreted as a valid leaf value. Alternatively, reject any submitted `element` whose length/format could plausibly be two concatenated base64 sha256 hashes, though prefixing is the standard, complete fix (as employed by e.g. Certificate Transparency and Bitcoin's newer merkle designs).

### Proof of Concept
1. An oracle/asset issuer publishes a data feed `feed_name` with value = merkle root of an array `arrElements = [E0, E1, E2, E3]`, via `getMerkleRoot`.
2. An address definition uses `['in merkle', [[oracle_address], feed_name, "<any placeholder>"]]` as a spending authorization branch (per `definition.js` lines 1004-1020, evaluated during `validateAuthentifiers`).
3. Using `merkle.getMerkleProof(arrElements, 0)` and `getMerkleProof(arrElements, 1)`, the attacker (who need not own any legitimate element) learns `h0 = hash(E0)` and `h1 = hash(E1)` (siblings revealed in these proofs), and thus the internal node value `P = hash(h0 + h1)`.
4. The attacker crafts `forged_element = h0 + h1` and a proof object `{ index: 0, siblings: [remaining upper-level siblings], root: <published root> }` (using the upper part of the real proof, skipping the bottom level).
5. Submitting a unit whose `authentifiers` at the `in merkle` path is `serializeMerkleProof({index:0, siblings:[...upper siblings...], root})` with `element = forged_element` passes `merkle.verifyMerkleProof(forged_element, proof)` (per `merkle.js` lines 84-102) because `hash(forged_element) === P`, matching the tree's real internal node hash and rolling up correctly to `proof.root`.
6. `validateAuthentifiers`'s `'in merkle'` branch (`definition.js:1004-1020`) treats this as successful inclusion of `forged_element`/`proof.root` in the data feed, unlocking the spending condition without any of the real whitelisted elements `E0..E3` ever being known or possessed by the attacker.

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
