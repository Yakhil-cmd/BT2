### Title
Webhook signature verification keys on `repository.owner.login` while the write path trusts `repository.full_name` — cross-organization forged webhooks (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on the `repository.owner.login` (or `organization.login`) field of the JSON payload, but every downstream `Webhooks::Handlers::Handler` resolves the target `Repository`/`Stack` using the independent `repository.full_name` field from the same payload. Nothing enforces that these two fields agree, so a party who can produce a validly-signed payload for organization A (because they legitimately administer their own Shipit-connected org A and know its `webhook_secret`) can set `repository.full_name` to `orgB/some-repo` and have Shipit act on organization B's stacks as if the event genuinely originated from B.

### Finding Description
`verify_signature` picks the secret used for HMAC validation from `repository_owner`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the app config (and its `webhook_secret`) purely by this `owner` string from the multi-org config schema documented in `config/secrets.development.example.yml`: [3](#0-2) 

Once the signature check passes (using the org A secret an attacker who administers org A legitimately knows), the raw body is parsed and dispatched unmodified to handlers: [4](#0-3) 

Every handler resolves the acted-upon repository from a *different* field of the same attacker-controlled payload — `repository.full_name` — with no cross-check against `repository.owner.login`: [5](#0-4) [6](#0-5) 

Because the signature is only checked for byte-integrity of the body against a secret chosen from `owner.login`, and the actual repository/stack lookup trusts `full_name` from that same body, an attacker who controls the org used for key-selection can freely set `full_name` to point at any other organization's repository configured in this Shipit instance. This is the same class of bug as the referenced report: the field validated for authorization (`owner.login` → which secret was used) is not the field that is actually acted upon (`full_name` → which repository/stack is mutated), i.e. `organization authenticated != repository written`.

### Impact Explanation
An attacker who legitimately administers one org onboarded to a shared/multi-tenant Shipit instance (a common deployment, as shown by the multi-org config block in `config/secrets.development.example.yml`) can forge webhook events that are processed as if they came from an org they do not control:
- Forge `push` events for a victim stack to trigger `GithubSyncJob` (`app/jobs/shipit/github_sync_job.rb`) with attacker-chosen SHAs.
- Forge `status`/`check_suite`/`check_run` events to mark arbitrary commits on the victim's stack as passing CI, which — for stacks with `continuous_deployment` or an active merge queue (`app/models/shipit/merge_request.rb`, `MergeRequest::StatusChecker`) — can cause Shipit to auto-merge or auto-deploy a commit under false pretenses.
- Forge `pull_request` `closed` events to archive review stacks belonging to the victim org (`app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb`).

This crosses a genuine authentication/authorization boundary (org A's credential is used to act on org B's resources) and can culminate in an unauthorized deploy/merge, matching the Critical impact bar ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the attacker to control (or have configured) at least one organization/app entry in Shipit's multi-org GitHub config — this is a standard, low-privilege, self-service action for anyone who can install a GitHub App and set its own webhook secret, not a Shipit session/token/host compromise. Crafting the mismatched JSON body and computing a valid HMAC with a secret one already knows is trivial. The only constraint is that the target organization/repository must already be registered as a `Repository`/`Stack` in the same Shipit instance, which is expected in a shared deploy-platform setup.

### Recommendation
Bind the verification key and the acted-upon repository together: after selecting `github_app` via `repository_owner`, require that `payload.dig('repository','full_name')` (and `organization.login`, if present) starts with the same `repository_owner` (case-insensitively) before dispatching to handlers, rejecting the request otherwise. Alternatively, resolve the target `Stack`/`Repository` first, derive `repository_owner` from that authoritative record, and only then verify the signature against the corresponding org's secret.

### Proof of Concept
1. Attacker administers `org-attacker`, which is configured in Shipit's `secrets.github` map with its own `webhook_secret` (`S_attacker`), a standard admin action for their own org.
2. Attacker crafts a JSON payload:
```json
{
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "victim-org/victim-repo"
  },
  "after": "<attacker-chosen sha>",
  ...
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, raw_body)>` and sets `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-attacker")` and validates the signature successfully (`lib/shipit/github_app.rb#verify_webhook_signature`), because it was in fact signed with `org-attacker`'s own known secret.
5. `WebhooksController#create` parses the same body and dispatches it to `Shipit::Webhooks::Handlers::PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` (via `repository_name` in `app/models/shipit/webhooks/handlers/handler.rb`) — an org the attacker never authenticated as — and processes the event (e.g., enqueues `GithubSyncJob`) against the victim's stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
