### Title
Webhook signature is verified against an organization taken from the unverified payload, while handlers act on repository/commit data from that same untrusted payload without cross-checking it - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization's `webhook_secret` to verify a request against by reading `repository.owner.login` (or `organization.login`) directly out of the **unverified, attacker-controlled** JSON body, before the signature has been validated. Once that lookup passes (which requires only knowledge/possession of the secret for *any one* configured organization, or an organization configured with a blank `webhook_secret`), the raw payload is handed to the event handlers, which independently derive the repository/commit to act on from unrelated fields in the same payload (`repository.full_name` for most handlers, and just `sha` — with no repository scoping at all — for `StatusHandler`). Nothing binds "the organization whose secret authenticated this request" to "the repository/commit the handler is about to mutate."

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 

`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where [2](#0-1) 
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is read straight from the request body the attacker controls — it is used to *select the secret* used to verify the same body. This means the equality that should hold is:

`organization whose webhook_secret authenticated the request == organization owning the repository the handler subsequently writes to`

Nothing enforces this. `Shipit::GitHubApp#verify_webhook_signature` even short-circuits to `true` when no secret is configured for that organization: [3](#0-2) 

The sample multi-org config ships with `webhook_secret: # nil` as the default for each org: [4](#0-3) 

So in any multi-organization Shipit install (which is the documented `TOP_LEVEL_GH_KEYS`/multi-org setup, not a hypothetical unmounted configuration) where at least one configured organization has no `webhook_secret` set (or the attacker otherwise knows/leaks one org's secret), an attacker can craft a request with `repository.owner.login` = that weak/unsecured org to sail through `verify_signature`, while every other field consumed by the actual handler refers to a completely different, unrelated organization/repository/commit.

The handlers do not re-derive or check the organization used for verification:
- `Handler#stacks` / `#repository_name` reads `payload.dig('repository', 'full_name')` — independent of `repository_owner` used above: [5](#0-4) 
- `PushHandler#process` triggers `stack.sync_github` for any stack matching that `full_name`+branch, again independent of the verified org: [6](#0-5) 
- `StatusHandler#process` is worse — it doesn't scope by repository at all, only by commit `sha`, globally across the entire Shipit instance: [7](#0-6) 

So an attacker who can satisfy `verify_signature` using any single organization's (weak/leaked) secret can inject a forged `status` event (`state: "success"`, arbitrary `context`/`description`/`target_url`) for **any commit sha in the entire application**, on any stack belonging to any other, fully-secured organization, via `Commit.create_status_from_github!`.

### Impact Explanation
Shipit stacks gate deploys/continuous-deployment and merge queues on CI/commit status ("green" checks). Forging a successful status for an arbitrary commit sha — reachable with only the ability to pass signature verification for *one weakly-configured or leaked-secret organization* rather than the organization that actually owns the target stack — lets an unprivileged network attacker mark an arbitrary, real commit belonging to a protected repository as CI-passing. This directly undermines the "organization that authenticated versus the repository that is written" binding called out in scope, and can be leveraged into unauthorized/continuous deploys of the attacker's chosen commit once other required checks are satisfied, and/or corrupt commit status/CI state Shipit relies on to decide deploy eligibility — matching the in-scope "unauthorized deploy/rollback" impact class. The `PushHandler`/`CheckSuiteHandler` cross-org write is a secondary instance of the same root cause (triggering `sync_github`/check-run refresh for a stack whose owning org never authenticated the request).

### Likelihood Explanation
Any Shipit deployment configured with more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml`) is exposed if any one of those organizations has no `webhook_secret` configured (accepted by design per `verify_webhook_signature`'s `return true unless webhook_secret`) — a very plausible operational state for a newly onboarded/low-risk org — or if one org's secret is otherwise known to the attacker. No session, `ApiClient` token, or repository write access is required; only an unauthenticated POST to `/webhooks`.

### Recommendation
- Cross-validate that the organization whose secret verified the signature (`repository_owner`) matches the organization actually embedded in `repository.full_name` (and any other repository identifiers) used by handlers, rejecting mismatches.
- Do not allow `verify_webhook_signature` to succeed unconditionally when `webhook_secret` is blank for a configured multi-org app; require every org entry to have a non-blank secret, or refuse to process events for orgs without one.
- Scope `StatusHandler` (and any other handler) lookups by the verified organization/repository, not by a bare, globally-unscoped `sha`.

### Proof of Concept
1. Configure Shipit with two organizations: `orgA` (no `webhook_secret` set) and `orgB` (secured, hosts the target stack/commit an attacker wants to mark as CI-green).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" },
  "sha": "<real commit sha belonging to orgB/target-repo>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://evil.example.com"
}
```
No `X-Hub-Signature` header, or an arbitrary one — `verify_webhook_signature` returns `true` because `Shipit.github(organization: "orgA")` has `webhook_secret` blank.
3. `Shipit::Webhooks.for_event('status')` invokes `StatusHandler`, which runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` — creating a fabricated "success" status on the real `orgB` commit, with no verification tying `orgA`'s (bypassed) authentication to `orgB`'s repository.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
