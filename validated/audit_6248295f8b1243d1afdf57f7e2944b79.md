### Title
Webhook signature verification authenticates a different field than the one handlers trust for repository routing - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check against based on `repository.owner.login`/`organization.login`, while every webhook `Handler` (e.g. `PushHandler`, and the base `Handler#repository_name`) resolves which `Stack`/`Repository` to act on using `repository.full_name`. Because the raw payload is attacker-controlled up to the constraint of matching a valid signature for *some* configured organization, an attacker who legitimately controls (or has push/webhook access to) one org configured in `Shipit.github_organizations` can craft a payload whose `owner.login` matches their own org (so it authenticates) but whose `repository.full_name` names a stack belonging to a different, victim organization/repository.

### Finding Description
`Shipit.github(organization:)` supports multiple independently configured GitHub Apps, one per organization, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks the app/secret to verify against purely from the payload's `repository.owner.login` (falling back to `organization.login`), and only checks the HMAC over the raw body against that secret: [2](#0-1) 

The `Handler` base class and its subclasses never re-check `repository.owner.login`; they instead derive the target repository purely from `repository.full_name`: [3](#0-2) 

`PushHandler#process`, for example, uses `stacks` (derived from `repository_name`) to select stacks and trigger `stack.sync_github`: [4](#0-3) 

So the equality the deployment implicitly relies on is: `organization authenticated (repository.owner.login used to pick webhook_secret) == repository actually acted upon (repository.full_name used by Handler#repository_name)`. Nothing in the controller or in `Handler` enforces this equality — the HMAC only proves "this payload was produced with organization X's secret," not "this payload's `repository.full_name` belongs to organization X." An attacker who controls a GitHub org/repo configured with its own `webhook_secret` in `Shipit.github_organizations` can sign an arbitrary JSON body with their own secret and set `repository.full_name` to any `owner/repo` string tracked by Shipit, causing `verify_signature` to pass (secret matches their own org) while the handler processes the forged payload against a completely different (victim) repository's stacks.

### Impact Explanation
This breaks the authentication boundary between organizations in a multi-org Shipit deployment: an actor who is legitimate for org A can forge webhook events (push, status, check_suite, membership, pull_request, etc.) targeted at org B's repositories/stacks without ever possessing org B's webhook secret. Depending on handler, consequences include triggering `Stack#sync_github` for a victim stack (`PushHandler`), injecting fabricated commit statuses (`StatusHandler`, using `Commit.where(sha:)` matched against real commits) that can flip `Deployable`/CI status checks Shipit relies on for deploy gating, or manipulating `check_suite`/`pull_request`/`membership` state for repositories the attacker does not control. This is a cross-organization write/authorization escalation reachable by any actor holding a valid webhook secret for just one configured org — no session, `ApiClient` token, or GitHub App private key is required, satisfying the "cross-repository writes" / authorization-escalation bar.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (`Shipit.github_organizations` with more than one entry, each with its own `webhook_secret`), and requires the attacker to know one org's `webhook_secret` — typically true for the org's own administrators/CI operators who legitimately received that secret to register their webhook, but who are not supposed to have any privilege over other organizations' repositories. This is a realistic multi-tenant setup risk rather than a purely theoretical one, since Shipit explicitly supports "byorganization" GitHub App configs.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, cross-validate that the organization whose secret validated the signature actually matches the owner embedded in `repository.full_name` (or `organization.login`) before dispatching to handlers — i.e., derive `repository_owner` and the repository's owning org from the same trusted, already-verified field, and reject payloads where `repository.full_name`'s owner segment doesn't match the organization used to select the webhook secret.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s under `secrets.github` (see `Shipit.github_app_config`) [5](#0-4) .
2. As an operator with legitimate knowledge of `org-a`'s `webhook_secret` (e.g., the person who configured `org-a`'s GitHub webhook), craft a JSON push payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "org-b/victim-repo", "owner": { "login": "org-a" } }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `org-a`'s `webhook_secret` over the raw JSON body.
4. POST to `/github/webhooks` with header `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: 'org-a')` (from `repository.owner.login`), verifies successfully [6](#0-5) .
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `repository_name` as `org-b/victim-repo` [7](#0-6)  and calls `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stacks — an org the attacker never authenticated against.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
