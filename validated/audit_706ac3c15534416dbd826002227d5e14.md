### Title
Single-Mode Governing-Node Authority Bypass on Pre-Permissionless Chains — (`kaiax/gov/headergov/impl/header.go`)

### Summary

`VerifyVote` gates the single-mode authority check behind `IsPermissionlessForkEnabled`. On any chain that has not yet activated the Permissionless fork, the check is silently skipped, allowing any council member who proposes a block to cast a `governance.governingnode` vote and permanently transfer governance authority to an attacker-controlled address.

### Finding Description

`VerifyVote` enforces three checks before accepting a header vote:

1. Voter is in the council.
2. Voter is the block proposer (author).
3. **In single mode, only the governing node may vote — but only after Permissionless.** [1](#0-0) 

The comment on line 101 is explicit: *"In single mode, only the governing node can write header.Vote **after Permissionless**."* The `&&` short-circuit means that when `IsPermissionlessForkEnabled` returns `false`, the entire single-mode restriction is dead code.

`checkConsistency` for `GovernanceGoverningNode` in single mode then checks only whether the **current** governing node is still in the council — it does not verify that the **voter** is the governing node: [2](#0-1) 

So on a pre-Permissionless chain in single mode, any council member who is the round-robin block proposer can embed a `governance.governingnode` vote pointing to an attacker address. Every honest validator runs the same `VerifyVote` and reaches the same conclusion: the vote is valid. The block is accepted by 2/3+ validators, the vote is stored via `HandleVote` → `AddVote`, and at the next epoch boundary `getExpectedGovernance` ratifies it into the `Governance` header field, permanently replacing `GoverningNode`. [3](#0-2) 

### Impact Explanation

Once `GoverningNode` is overwritten, the attacker holds exclusive governance authority for all subsequent single-mode operations (unit price, minting amount, committee size, reward ratios, etc.). This is a durable, on-chain privilege escalation over protected chain state — governance authority is permanently transferred without the legitimate governing node's consent.

### Likelihood Explanation

The attacker must be a council member (validator). In IBFT, proposer selection is round-robin across all validators, so the attacker needs only to wait for their scheduled proposer slot — no majority collusion, no key compromise, no external service access required. The attack is a single malicious block.

### Recommendation

Remove the `IsPermissionlessForkEnabled` gate from the single-mode authority check so it applies unconditionally:

```go
// Before (buggy):
if h.ChainConfig.IsPermissionlessForkEnabled(...) &&
    params.GovernanceMode == "single" &&
    vote.Voter() != params.GoverningNode {
    return ErrVotePermissionDenied
}

// After (fixed):
if params.GovernanceMode == "single" &&
    vote.Voter() != params.GoverningNode {
    return ErrVotePermissionDenied
}
``` [1](#0-0) 

### Proof of Concept

1. Configure a chain with `GovernanceMode = "single"`, a designated `GoverningNode = A`, and the Permissionless fork **not** enabled.
2. Add a second council member `B` (non-governing node).
3. Wait for `B`'s proposer slot. `B` constructs a block with `header.Vote` encoding `governance.governingnode = B`.
4. All validators call `VerifyVote`: council check passes (B is in council), author check passes (B is proposer), single-mode check is skipped (`IsPermissionlessForkEnabled` = false), `checkConsistency` passes (A is still in council).
5. Block is finalized. At the next epoch block, `getExpectedGovernance` emits `{governingnode: B}` in `header.Governance`.
6. `HandleGov` → `AddGov` persists the new param set. `GetParamSet` now returns `GoverningNode = B`.
7. Assert: `B` can now cast any governance vote; `A` is locked out.
