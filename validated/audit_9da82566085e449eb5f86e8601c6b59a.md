### Title
Webhook signature is verified against the organization in `repository.owner.login`, but the event is dispatched using `repository.full_name` — allowing a valid signer for one org to forge events for a stack owned by a different org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) from the JSON body, while every webhook `Handler` resolves the actual target `Repository`/`Stack` to act on using the *different* field `repository.full_name`. Nothing ties these two fields together, so a payload can present two organizations at once: the one whose secret authenticates the request, and a completely different one whose stack actually gets acted upon.

### Finding Description
`verify_signature` computes the org used for signature verification from the untrusted request body: [1](#0-0) [2](#0-1) 

That organization is used to pick a `GitHubApp` instance (and thus a `webhook_secret`) via `Shipit.github(organization: repository_owner)`, and Shipit explicitly supports one distinct `webhook_secret` per organization key under `secrets.github`: [3](#0-2) 

Once the signature check passes, `create` dispatches the parsed JSON body to every matching handler: [4](#0-3) 

Every handler (e.g. `PushHandler`, PR handlers, etc.) resolves the repository/stack to operate on using `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` splits `owner/name` purely from that `full_name` string: [7](#0-6) 

The binding that should hold is:
`organization authenticated via repository.owner.login (signature check)` == `organization owning the repository/stack acted on via repository.full_name (handler dispatch)`

On a multi-tenant Shipit instance where multiple organizations are configured with their own `webhook_secret` (as `lib/shipit.rb#github_app_config` explicitly supports), an attacker who legitimately administers *their own* onboarded organization ("attacker-org") knows/controls that org's `webhook_secret` (they configured the GitHub App/webhook for it). They can craft a raw JSON payload where:
- `repository.owner.login` = `"attacker-org"` (used to pick the webhook secret for HMAC validation — which they can compute correctly)
- `repository.full_name` = `"victim-org/victim-repo"` (used by the handler to look up the target `Repository`/`Stack`)

`verify_signature` succeeds using the attacker's own secret, and `PushHandler`/other handlers then execute against the victim's stack, because they consult only `full_name`.

### Impact Explanation
This breaks cross-tenant isolation between organizations hosted on the same Shipit instance: an attacker who only controls one organization's webhook credentials can inject forged GitHub events (push, pull_request, status, etc.) that are processed as if they came from a completely different organization's repository. Depending on handler and stack configuration this can trigger unauthenticated-organization actions against another org's stack (e.g. `stack.sync_github` via `PushHandler`, `GithubSyncJob` enqueue as shown in tests, PR/review-stack creation, `check_suite` refreshes), which for stacks with `continuous_deployment` enabled can trigger an out-of-band deploy for a repository the attacker has no authorization over — an unauthorized action on a stack belonging to a different organization/repository trust boundary, matching the "an organization that authenticated versus the repository that is written" analog class.

### Likelihood Explanation
Exploitability is gated on the target Shipit instance running in the multi-organization configuration (distinct `webhook_secret` per org under `secrets.github`) and the attacker legitimately controlling at least one onboarded organization. No repository write access, `ApiClient` token, or `GITHUB_TOKEN`/private key of the victim org is required — only knowledge of the attacker's own org's webhook secret, which they are entitled to know as that org's administrator. I was not able to fully verify (due to iteration limits) whether `stack.sync_github`/`GithubSyncJob` further validates the fetched SHA against the real upstream in a way that fully neutralizes deploy-triggering impact, so the strength of the "unauthorized deploy" consequence versus a lesser "spurious sync/stack-state corruption" consequence is not fully confirmed.

### Recommendation
Verify the webhook signature using the same organization/repository identity that the handler will subsequently use to resolve the target `Repository`, e.g., derive both from `repository.full_name` (or explicitly assert `repository.full_name.split('/').first == repository.owner.login` before dispatch), and reject the request if they disagree.

### Proof of Concept
Conceptual request (requires the attacker to know the `webhook_secret` for `attacker-org`, an org they legitimately administer on a multi-org Shipit instance):

```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```

`verify_signature` looks up `Shipit.github(organization: "attacker-org")` and the signature validates successfully. `PushHandler` then resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack.   def github(organization: github_default_organization)
```ruby
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
