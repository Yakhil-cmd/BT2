### Title
Pre-publish exechook does not actually gate the symlink publish, allowing unvalidated/malicious content to be published - (File: main.go, pkg/hook/hook.go)

### Summary
`git-sync`'s `--pre-publish-exechook-command` is documented as a gate that runs "before publishing the symlink" [1](#0-0) , implying it can validate synced content before it is exposed to consumers. In practice, the hook is dispatched asynchronously and its result is never awaited before `publishSymlink` runs, so the symlink is published unconditionally regardless of whether the pre-publish hook succeeds or even finishes. This is structurally the same root-cause pattern as the referenced report: a check meant to gate a state-changing action (`maxLiquidity` check vs. token transfer) is evaluated against pre-callback state and the guarded action proceeds regardless of the callback's true outcome.

### Finding Description
In `SyncRepo`, the "before publish" hook and the actual publish are wired like this: [2](#0-1) 

`beforePublish` simply calls `prePubExechookRunner.Send(hash)` and returns `nil` immediately — it does not wait for the hook to execute or succeed: [3](#0-2) 

`Send` performs a non-blocking channel write (`hookData.send`), so it always returns instantly no matter what the consumer goroutine (`HookRunner.Run`) is doing: [4](#0-3) 

The actual hook execution happens in a separate, independent goroutine (`HookRunner.Run`), which retries on failure with backoff and only reports a result via `oneTimeResult` for `--one-time` mode: [5](#0-4) 

Back in `SyncRepo`, since `beforePublish` always returns `nil`, the code unconditionally proceeds to `git.publishSymlink(newWorktree)` right after — there is no wait for the pre-publish hook's actual completion or success: [6](#0-5) 

Even in `--one-time` mode, `WaitForCompletion()` for the pre-publish hook is only used to compute a process exit code *after* the symlink has already been published — it does not prevent or roll back the publish: [7](#0-6) 

The repository's own end-to-end test confirms this behavior: when the pre-publish exechook is configured to fail, the process ultimately exits non-zero (`assert_fail`), but the symlink is still created and points at the new (unvalidated) content: [8](#0-7) 

### Impact Explanation
Operators who configure `--pre-publish-exechook-command` as a content-validation gate (e.g., policy check, signature/integrity verification, malware scan) before allowing new content to reach consumers get no actual protection: the symlink is atomically flipped to the new worktree regardless of the hook's outcome. An attacker who can push a commit to the synced remote (the standard untrusted-content threat model for `git-sync`) can have that content published to all consumers of the `--link` symlink even though the operator's pre-publish gate would reject it. This matches the "publishing wrong or partial content" impact category — unvalidated/attacker-controlled content is published as if it passed the gate.

### Likelihood Explanation
This triggers on every sync of a changed hash whenever `--pre-publish-exechook-command` is configured, with no additional preconditions beyond an attacker being able to push a commit that the hook would reject. This is a default/always-reachable code path for any deployment using this documented feature.

### Recommendation
Make the pre-publish hook synchronous and blocking with respect to the publish path: `beforePublish` should invoke the hook command directly (or wait on a per-call completion signal) and propagate a real failure before `git.publishSymlink` is called, rather than firing a non-blocking `Send` and returning `nil` unconditionally. Only call `publishSymlink` after confirming the pre-publish hook actually succeeded for the specific hash being published.

### Proof of Concept
1. Configure git-sync with `--pre-publish-exechook-command` pointing to a script that always fails (simulating a validation/security gate rejecting the content), e.g. as in `e2e::pre_publish_exechook_fail_once` [8](#0-7) .
2. Push a commit to the synced repo.
3. Observe that `git-sync` still creates/updates the `--link` symlink to point at the new worktree and consumers can read the new (should-have-been-rejected) content, even though the pre-publish hook reported failure — the process only exits with a non-zero status afterward, too late to prevent the publish.

```go
// Run waits for trigger events from the channel, and run hook when triggered.
func (r *HookRunner) Run(ctx context.Context) {
	var lastHash string

	// Wait for trigger from hookData.Send
	for range r.data.events() {
		// Retry in case of error
		for {
			// Always get the latest value, in case we fail-and-retry and the
			// value changed in the meantime.  This means that we might not send
			// every single hash.
			hash := r.data.get()
			if hash == lastHash {
				break
			}

			if err := r.hook.Do(ctx, hash); err != nil {
				r.log.Error(err, "hook failed", "hash", hash, "retry", r.backoff)
				updateHookRunCountMetric(r.hook.Name(), "error")
				// don't want to sleep unnecessarily terminating anyways
				r.sendOneTimeResultAndTerminate(false)
				time.Sleep(r.backoff)
			} else {
				updateHookRunCountMetric(r.hook.Name(), "success")
				lastHash = hash
				r.sendOneTimeResultAndTerminate(true)
				break
			}
		}
	}
}
```
