## Finding [1](#0-0)  shows that when a `pull_request` webhook creates a Review Stack, its `branch` attribute is taken directly from `params.pull_request.head.ref` — the branch name as it exists in the **PR author's fork** — while the stack's `repository` scope comes from the **base/target repository** of the PR: [2](#0-1)  resolves `repository` from `params.repository.full_name`, which in a GitHub `pull_request` webhook payload is always the base (target) repository, never the fork. No check anywhere ties `pull_request.head.repo` to `pull_request.base.repo`/`params.repository`.

Downstream, git operations for the stack use only `repository` + `branch`, never the actual fork: [3](#0-2)  `github_repo_name`/`github_api` are derived from `repository` (the base repo). [4](#0-3)  fetches commits with `stack.github_commits`, which internally calls `github_api.commits(github_repo_name, sha: branch)` — i.e., it resolves `branch` (attacker-supplied string) **inside the base repository**, not the fork.

Because GitHub lets anyone opening a PR from a fork name their branch arbitrarily, an unprivileged external contributor can name their fork branch identically to an existing (possibly non-public-facing) branch of the target repository. This breaks the equality `review_stack.repository == source_repo_of(review_stack.branch)` that the review-stack feature implicitly assumes (the code shown for the base commit/PR association silently reads any ref name into `branch` while binding `repository` to the base repo): the ref that was actually "approved" for review-app treatment (the PR/fork content) is not the ref whose `shipit.yml` steps end up executed — instead, an unrelated branch of the base repository, chosen only by name-collision, gets synced and its deploy spec cached/provisioned.

Provisioning is triggered automatically once the stack exists: [5](#0-4)  `after_transition deprovisioned: :provisioning { stack.provisioner.up }` runs the `provisioning_handler_name`/steps taken from the (now colliding) branch's `shipit.yml`, and `sync_github` is enqueued automatically on stack creation via `after_commit :sync_github, on: :create` in `app/models/shipit/stack.rb`.

### Title
Review Stack `branch` taken from the fork PR's `head.ref` is resolved against the base repository, letting an external contributor provision/deploy an unrelated branch by name collision - ([File: app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb])

### Summary
`ReviewStackAdapter#stack_attributes` sets a newly created Review Stack's `branch` to `pull_request.head.ref` (a string fully controlled by the PR author, since it is simply the name of a branch in their own fork), but binds the stack's `repository` to the PR's **base** repository (`params.repository.full_name`). All subsequent git/GitHub operations for that stack (`Stack#github_commits`, `Stack#github_repo_name`, `GithubSyncJob`) resolve `branch` against `repository` (the base repo), not against the fork the PR actually came from.

### Finding Description
The binding the feature relies on is: *the ref reviewed via the PR == the ref whose `shipit.yml` is synced/cached/provisioned for the resulting Review Stack*. The code instead builds this binding from two different sources: `repository` from the base repo (`params.repository.full_name`), `branch` from the head ref string of the fork (`params.pull_request.head.ref`), with no verification that `pull_request.head.repo` equals `pull_request.base.repo`/`params.repository`. Any GitHub user able to open a PR against a repository (no write access required) can pick their own fork's branch name to collide with any existing branch name in the base repository. `GithubSyncJob`/`Stack#github_commits` then pulls commits and (`CacheDeploySpecJob`, not shown) caches `shipit.yml` for that colliding base-repo branch, not the PR's own fork content, and the review stack state machine automatically provisions it (`ReviewStack` `after_transition ... { stack.provisioner.up }`).

### Impact Explanation
This lets an unprivileged, external (fork-only) contributor cause Shipit to sync, cache the deploy spec of, and auto-provision an arbitrary existing branch of the target repository merely by naming their PR branch the same — a ref that was never part of the actual PR under review. This is an unauthorized deploy/provisioning of a ref that bypassed the review-stack's implicit "this deploys what's in the PR" guarantee, satisfying the "unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires only the ability to open a pull request against a repository that has Review Stacks enabled with an "Allow All"/"Allow With Label" provisioning behavior — a standard unprivileged capability for public repositories. No credentials, tokens, or write access are needed; only awareness of an existing branch name in the base repository.

### Recommendation
When creating a Review Stack from a `pull_request` webhook, validate that `pull_request.head.repo.full_name == pull_request.base.repo.full_name` (or otherwise refuse/flag cross-fork PRs) before using `head.ref` as the deployable `branch`, or scope commit/spec resolution to the actual head repository rather than the base repository's ref namespace.

### Proof of Concept
1. Enable Review Stacks with "Allow All" on a public repository `acme/app` that has an internal branch `staging/internal-config`.
2. As any external GitHub user, fork `acme/app` and create a branch also named `staging/internal-config` in the fork.
3. Open a pull request from the fork's `staging/internal-config` branch against `acme/app`'s default branch.
4. Shipit's `pull_request` "opened" webhook fires; `ReviewStackAdapter#create!` creates a `ReviewStack` with `repository = acme/app` and `branch = "staging/internal-config"` [6](#0-5) .
5. `GithubSyncJob` runs `stack.github_commits`, which calls `github_api.commits("acme/app", sha: "staging/internal-config")` — the base repo's real `staging/internal-config` branch, unrelated to the attacker's PR content.
6. The Review Stack's state machine auto-provisions using the deploy spec cached from that branch, deploying/running steps for a ref the attacker never actually submitted for review.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def append_commit(gh_commit)
      stack.commits.create_from_github!(gh_commit)
    end
