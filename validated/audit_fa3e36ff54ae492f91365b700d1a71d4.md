**Analysis:**

The binding to verify: `DeployCommands#env['SHA']` == `commit.sha` (from `@task.until_commit`) for every deploy, regardless of PR label content.

Tracing the merge chain from innermost to outermost:

1. `ReviewStack#env` merges label-derived keys (`label_name.upcase => "true"`) on top of the base `Stack#env` hash [1](#0-0) .
2. `TaskCommands#env` merges `@stack.env` (containing any label-derived keys) **first**, then merges a literal hash containing `TASK_ID`, `SHIPIT_LINK`, etc. **afterward**, then merges `deploy_spec.machine_env` and `@task.env` last [2](#0-1) .
3. `DeployCommands#env` calls `super` (the entire `TaskCommands#env` chain above) and merges its literal `{'SHA' => commit.sha, 'REVISION' => commit.sha, 'DIFF_LINK' => diff_url}` hash **after** that `super` call returns [3](#0-2) .

Ruby's `Hash#merge` always lets the argument (right-hand side) win on key collisions. Since `@stack.env` (which can contain attacker-influenced label keys such as `SHA` or `TASK_ID` if a PR is labeled `sha` or `task_id`) is merged first in each chain, and the literal, code-controlled keys (`TASK_ID`, `SHIPIT_LINK` in `TaskCommands#env`; `SHA`, `REVISION`, `DIFF_LINK` in `DeployCommands#env`) are merged strictly afterward in the same method chain, the literals always win. This holds identically for `DeployCommands`, because its literal merge happens after the *entire* `super` chain completes — including the `@stack.env` merge deep inside `TaskCommands#env`.

The only hashes merged after the `TASK_ID`/`SHIPIT_LINK` literals inside `TaskCommands#env` are `deploy_spec.machine_env` and `@task.env` [4](#0-3) , neither of which is derived from PR labels — `machine_env` comes from `shipit.yml`/`secrets.yml` config [5](#0-4) , and `@task.env` is a serialized column set at task-creation time via `trigger_task`/`trigger_deploy`, not from PR label content [6](#0-5) .

Existing tests confirm this ordering guarantee empirically: `test/unit/deploy_commands_test.rb` asserts `command.env['SHA']` equals `@deploy.until_commit.sha` [7](#0-6) , and `test/lib/shipit/deploy_commands_test.rb` / `test/lib/shipit/task_commands_test.rb` confirm labels only populate their own upcased keys (`WIP`, `BUG`) without colliding with reserved keys in the fixtures used [8](#0-7) .

Since a PR label named `sha`, `revision`, `task_id`, or `shipit_link` would only ever populate those keys in `@stack.env`, and every one of those keys is unconditionally overwritten later in the same call chain by code-controlled literals, the protective ordering holds for both `TaskCommands#env` and `DeployCommands#env`. No command-argument injection path exists through this mechanism.
