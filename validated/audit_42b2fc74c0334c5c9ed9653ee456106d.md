This confirms the exploit path. `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [1](#0-0) , and `Shipit.github_teams` is built via `Team.find_or_create_by_handle` from the configured `oauth.teams` handles [2](#0-1) . `force_github_authentication` gates all engine controllers on this `authorized?` check [3](#0-2) . ### Title
Webhook signature verified for one GitHub organization while the `membership` handler grants team membership for an attacker-chosen organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')` only if no `repository` key is present [4](#0-3) . `Webhooks::Handlers::MembershipHandler`, however, acts on a completely independent field, `params.organization.login`, to create/find a `Team` and add/remove members from it [5](#0-4) . Nothing enforces that the organization used to select the verifying secret equals the organization acted upon by the handler.

### Finding Description
The binding that must hold is: `organization verified by signature == organization mutated by the handler`. The controller computes the verifying organization from `repository.owner.login` (preferred) or `organization.login` (fallback) [6](#0-5) , and looks up the corresponding `GitHubApp`/`webhook_secret` via `Shipit.github(organization: repository_owner)` [7](#0-6) .

The GitHub `membership` event payload has no `repository` object at all — but the controller does not restrict `repository_owner` extraction by event type; it runs unconditionally for every event, including `membership`. An attacker who legitimately administers their own GitHub organization (`OrgA`, with a real Shipit GitHub App installation and a known `webhook_secret`) can send a crafted `membership`-typed POST to `/webhooks` whose body includes:
- a `repository.owner.login` of `OrgA` (so `verify_signature` selects `OrgA`'s secret and the attacker's correctly-computed HMAC passes) [8](#0-7) 
- an `organization.login` of `OrgB` — the *victim* organization whose team membership the attacker wants to modify.

Once the whole raw body passes signature verification (because it was computed by the attacker with the correct `OrgA` secret over the exact body they crafted), `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler`, which reads `params.organization.login` = `"OrgB"` and `params.member.login` (attacker-controlled), and calls `team.add_member(member)` [9](#0-8) . This creates/updates a `Team` scoped to `organization: "OrgB"` and adds an arbitrary GitHub login as a member — without ever presenting a valid signature for `OrgB`.

### Impact Explanation
If `OrgB`'s handle is listed in `Shipit.github_teams` (`config.github.oauth.teams`), which gates every engine controller via `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [1](#0-0) , the attacker can add any existing Shipit `User` (identified by GitHub login) to that authorized team, escalating that account (or their own, if they already have a Shipit `User` record from a prior login) into full deploy/rollback/merge authorization for stacks gated by `OrgB`'s team — all without ever possessing `OrgB`'s `webhook_secret`. This is a direct escalation into `Shipit.github_teams` authorization, satisfying the High-impact criterion.

### Likelihood Explanation
The only prerequisite is administrative control of *any* GitHub organization that has its own Shipit GitHub App installation and webhook secret (i.e., an "unprivileged" outsider relative to the victim `OrgB`) — this is a normal, unprivileged capability for any third party running their own Shipit instance's org, not a privileged Shipit credential. The forgery only requires knowing that `OrgB`'s handle is configured in `Shipit.github_teams`, which is often documented/discoverable. The core code path is unconditional for all event types, so it requires no misconfiguration beyond having more than one organization's webhook_secret known to different parties (multi-tenant Shipit setups explicitly support this via `Shipit.github(organization:)`) [10](#0-9) .

### Recommendation
`MembershipHandler` (and any handler relying on `organization.login`) should validate that the organization it is about to act on matches the `repository_owner`/organization actually used by `verify_signature` for that request, e.g. by passing the verified organization into the handler and asserting equality with `params.organization.login` before mutating any `Team`. Alternatively, restrict signature-organization selection strictly to the event-appropriate field (use `organization.login` only for org-scoped events like `membership`, never fall through to an unrelated `repository.owner.login`), and reject events where both fields are present but disagree.

### Proof of Concept
1. Attacker controls `OrgA`'s Shipit GitHub App with known `webhook_secret_A`, and knows `OrgB` is one of `Shipit.github_teams`'s handles (e.g. `OrgB/developers`).
2. Attacker crafts body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "OrgB" },
  "member": { "login": "attacker-login" },
  "repository": { "owner": { "login": "OrgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>` and sends `POST /webhooks` with `X-Github-Event: membership`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: 'OrgA')`, and the HMAC matches — request passes [11](#0-10) .
5. `MembershipHandler.process` runs using `params.organization.login == "OrgB"`, creating/finding `Team(organization: "OrgB", slug: "developers")` and adding `attacker-login` (or any target user) to it [5](#0-4) , without ever having `OrgB`'s webhook secret.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
