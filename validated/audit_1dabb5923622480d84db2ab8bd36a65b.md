### Title
Webhook signature verified against `repository.owner.login`'s secret while events are dispatched by `repository.full_name`, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) is used to validate the HMAC signature of an inbound webhook based on the `repository.owner.login` field of the JSON body, but the handlers that actually act on the payload (e.g. `PushHandler`) resolve the target `Repository`/`Stack` from the *different* `repository.full_name` field of the same body. Because the HMAC only proves "this body was signed by whoever holds the secret for the org named in `repository.owner.login`," and that org name is never cross-checked against the org embedded in `full_name`, an attacker who legitimately controls a GitHub App/webhook for one organization onboarded onto the same Shipit instance can sign a payload whose `repository.full_name` names a completely different organization's repository, and Shipit will process it as if it came from that other organization.

### Finding Description
Signature verification picks the app/secret via a value read straight out of the untrusted body: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')` and is used only to look up `Shipit.github(organization: repository_owner)` for the HMAC check. The signature is a valid, verifiable proof that the *sender knows the secret configured for that org*, nothing more — it says nothing about which repository the event actually pertains to.

Once the signature passes, the raw parsed body is dispatched unmodified to handlers: [3](#0-2) 

Handlers resolve the affected `Stack`s from a *different* field of the same body, `repository.full_name`, via `Repository.from_github_repo_name`: [4](#0-3) [5](#0-4) 

`PushHandler`, for example, uses this repository lookup to find stacks and trigger a GitHub sync with an attacker-supplied `after` SHA: [6](#0-5) 

Shipit is explicitly designed to be multi-tenant: multiple independent GitHub organizations, each with its own `webhook_secret`, can be configured on one instance: [7](#0-6) 

The trust binding that should hold is: *`organization` whose secret validated the signature == `organization` whose repository/stack is mutated by the handler*. Because `owner.login` (used for auth) and `full_name` (used for effect) are independent, attacker-controlled fields in the same body, this equality is never enforced, exactly mirroring the `BridgedGovernor` bug class where a field the receiving logic *acts on* is not the field the *authenticating check* actually covers.

### Impact Explanation
An organization that has legitimately onboarded its own GitHub App/webhook onto a shared Shipit instance (and thus knows its own `webhook_secret`) can forge webhook events — most concretely `push` events — targeting any other onboarded organization's repositories, by simply setting `repository.full_name` to the victim's `owner/repo` while keeping `repository.owner.login` equal to its own org name. This lets it trigger `stack.sync_github(expected_head_sha: attacker_chosen_sha)` on the victim's stacks, i.e. cross-repository/cross-organization state manipulation across a boundary that Shipit is supposed to isolate (each org's `Shipit.github(organization:)` config and secret should only govern that org's own repositories). This matches the "cross-repository writes" / unauthorized-action class of impact for a multi-tenant deployment engine.

### Likelihood Explanation
Any organization admin able to configure their own GitHub App/webhook entry in the shared Shipit secrets (a normal, supported, unprivileged-relative-to-other-orgs setup) can exploit this with a single crafted HTTP request; no access to the victim's secret, private key, or Shipit session/API token is required — only knowledge of one's own legitimately-configured `webhook_secret`, which is the credential the multi-tenant model intends to scope to the owner's own repositories only.

### Recommendation
Bind the verified organization to the acted-upon repository: after establishing which GitHub App/secret validated the signature, require that the owner segment of `repository.full_name` (and/or `organization.login`) matches `repository_owner` used for verification, rejecting the webhook (HTTP 422) if they diverge, before dispatching to any handler.

### Proof of Concept
1. Org "attacker" configures its own GitHub App in Shipit (`config.github.attacker.webhook_secret = S`), a supported multi-tenant configuration.
2. Attacker computes `sha1=HMAC(S, body)` over a `push` payload where `repository.owner.login = "attacker"` but `repository.full_name = "victim-org/victim-repo"` and `after = <attacker-chosen sha>`.
3. POST to `/webhooks` with `X-Hub-Signature` set to that HMAC and `X-Github-Event: push`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker")`, validates the signature successfully (it was computed with the attacker's own real secret over the exact raw body sent).
5. `WebhooksController#create` dispatches to `PushHandler`, which resolves stacks via `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` on the victim's stack — despite the signature never having been validated by (or for) `victim-org`.
