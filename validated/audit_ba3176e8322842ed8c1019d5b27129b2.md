### Title
`update_pool_rewards` records an unclamped `last_update_block`, causing permanent arithmetic-underflow DoS on `pallet-asset-rewards` after pool expiry - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet-asset-rewards` computes accrued rewards up to `min(now, expiry_block)` via `last_block_reward_applicable`, but when persisting the pool's bookkeeping state it stores the *unclamped* current block number as `last_update_block`. This is the same class of bug as the reported `_newRewards`/`endRewardTime` mismatch: the "end of emission" time is respected when computing the reward delta, but not when persisting the checkpoint used for the *next* delta computation. Once `last_update_block` exceeds `expiry_block`, every subsequent call to `reward_per_token` performs `last_block_reward_applicable(expiry_block).ensure_sub(last_update_block)`, which underflows (`expiry_block - last_update_block` is negative) and returns an `ArithmeticError`, permanently reverting `stake`, `unstake`, and `harvest_rewards` for that pool until the admin raises `expiry_block` again.

### Finding Description
`reward_per_token` correctly clamps elapsed blocks to the pool's expiry: [1](#0-0) 

```
let rewardable_blocks_elapsed: u32 =
    match Self::last_block_reward_applicable(pool_info.expiry_block)
        .ensure_sub(pool_info.last_update_block)?
        .try_into()
```

where `last_block_reward_applicable` returns `min(now, expiry_block)`: [2](#0-1) 

However, `update_pool_rewards`, which is called right after `reward_per_token` on every `stake`, `unstake`, and `harvest_rewards` to persist the new checkpoint, sets `last_update_block` to the raw, unclamped current block: [3](#0-2) 

```
pub fn update_pool_rewards(
    pool_info: &PoolInfoFor<T>,
    reward_per_token: T::Balance,
) -> Result<PoolInfoFor<T>, DispatchError> {
    let mut new_pool_info = pool_info.clone();
    new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
    new_pool_info.reward_per_token_stored = reward_per_token;
    Ok(new_pool_info)
}
```

Consequence: as soon as any *unprivileged* staker interacts with an expired-but-not-yet-extended pool (e.g. via `unstake`, which permits the staker to call it unconditionally, or `harvest_rewards`, permissionless once `now > expiry_block`), `last_update_block` is stored as a value strictly greater than `expiry_block`. Any following pool interaction — by the same or a different staker — then computes:

`last_block_reward_applicable(expiry_block) = min(now, expiry_block) = expiry_block`

`expiry_block.ensure_sub(last_update_block)` where `last_update_block > expiry_block` ⇒ underflow ⇒ `Err(ArithmeticError::Underflow)` propagated by the `?` operator all the way out of `stake`/`unstake`/`harvest_rewards`.

This is reachable through `stake` (`substrate/frame/asset-rewards/src/lib.rs:472-502`), `unstake` (`:513-560`), and `harvest_rewards` (`:568-615`), all of which call `Self::update_pool_and_staker_rewards` → `reward_per_token` → `ensure_sub`: [4](#0-3) 

No privileged role, governance action, or malicious external actor is required: a normal staker performing routine actions after natural pool expiry triggers the poisoning, and the very next normal interaction by any account fails.

### Impact Explanation
Once a pool is poisoned, `stake`, `unstake`, and `harvest_rewards` all revert with an arithmetic error for that pool. This means:
- Stakers cannot withdraw their staked (frozen) tokens (`unstake` fails).
- Stakers cannot claim already-accrued, unclaimed rewards (`harvest_rewards` fails).
- No new stakes can be added.

This is an irreversible-freezing-style DoS on user funds and rewards, only recoverable if the pool's `admin` (a role distinct from the staker/attacker) calls `set_pool_expiry_block` to push `expiry_block` past the poisoned `last_update_block` — something that is not guaranteed to happen (admin may be inactive, or the pool may have been intentionally left to expire without further admin action, which is the common/expected end-of-life flow for a rewards pool).

### Likelihood Explanation
High likelihood: this is not an edge case requiring adversarial setup — it is the *normal* lifecycle of a bounded-duration rewards pool. Every pool created with a finite `expiry_block` (the common case; `DispatchTime::After`/`At` is the standard way to create pools per `create_pool`) will hit this once it expires and receives two sequential interactions (e.g., one staker unstaking right after expiry, then a second staker trying to harvest or unstake). No special permissions or timing precision are needed by the attacker/triggering user — ordinary usage after expiry is sufficient.

### Recommendation
Clamp `last_update_block` to `min(current_block_number(), pool_info.expiry_block)` in `update_pool_rewards`, mirroring `last_block_reward_applicable`, e.g.:

```rust
new_pool_info.last_update_block =
    Self::last_block_reward_applicable(pool_info.expiry_block);
```

This ensures the persisted checkpoint never exceeds the pool's expiry, matching the invariant already enforced in `reward_per_token`.

### Proof of Concept
Reasoning-level PoC (derived from the existing test harness in `substrate/frame/asset-rewards/src/tests.rs`, e.g. `create_default_pool`, `assert_hypothetically_earned`, `System::set_block_number`):

1. `create_default_pool()` at block `B0` with `expiry_block = B0 + DEFAULT_EXPIRE_AFTER = E`.
2. Staker `S1` calls `stake` at block `B0` → `last_update_block = B0`.
3. Advance to block `E + 10` (past expiry). `S1` calls `unstake(amount)` (permitted unconditionally for `caller == staker`). This succeeds: `reward_per_token` computes `min(E+10, E) - B0 = E - B0` (valid), then `update_pool_rewards` stores `last_update_block = E + 10` (unclamped, > `E`).
4. Advance to block `E + 20`. Any account calls `harvest_rewards` (permissionless since `now > expiry_block`) or `S1` calls `unstake` again. `reward_per_token` computes `last_block_reward_applicable(E) = min(E+20, E) = E`, then `E.ensure_sub(E+10)` → underflow → `Err(ArithmeticError::Underflow)`. The call fails with a `DispatchError`, and this failure persists for all future calls until the admin extends `expiry_block` beyond `E+10`.

This was derived from static code reading of `substrate/frame/asset-rewards/src/lib.rs` (`reward_per_token`, `update_pool_rewards`, `last_block_reward_applicable`, `stake`, `unstake`, `harvest_rewards`) and the pallet's own test scaffolding (`substrate/frame/asset-rewards/src/tests.rs`); no test harness was actually executed, so this PoC is a reasoning-level trace through the exact production code paths, not an executed/observed result. I was unable to fully confirm the exact `EnsureSub`/`ensure_sub` panic-vs-error semantics (whether it returns `ArithmeticError::Underflow` via `checked_sub` or similar) from the snippets retrieved from `substrate/primitives/arithmetic/src/traits.rs`; this should be verified by running the pallet's existing test suite with an added test extending the `extends_reward_accumulation`/`integration` scenarios in `substrate/frame/asset-rewards/src/tests.rs` to interact twice after natural expiry without an admin extension.
