### Title
Cross-repository status webhook can mark a victim stack's commit deployable and trigger an unauthorized deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by SHA alone, with no scoping to the repository that authenticated the webhook. Any repository owner who can trigger a `status` webhook for a commit sharing a SHA with a commit belonging to a different stack (e.g. via a fork that preserves the original commit objects) can flip that unrelated stack's commit status to `success`, satisfying `Shipit::Commit#deployable?` and triggering `schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` for a stack/repository they never authenticated for.

### Finding Description
The broken binding, stated explicitly: the webhook signature check enforces
`request.headers['X-Hub-Signature'] verified against Shipit.github(organization: params.dig('repository','owner','login')).webhook_secret`
but the mutation actually performed is
`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`
with no constraint that `commit.stack.repository.owner == params.dig('repository','owner','login')` (or that `commit.stack.repository.full_name == params.dig('repository','full_name')`). These two are never checked to be equal, so the binding the exploit relies on — "the repo that signed the payload is the repo whose commit gets mutated" — does not hold in the code.

Trace:
- `Shipit::WebhooksController#verify_signature` derives `repository_owner` purely from the payload's `repository.owner.login` and verifies the HMAC signature using that organization's `webhook_secret` via `lib/shipit/github_app.rb#verify_webhook_signature`. [1](#0-0) 
- This only proves the payload was legitimately signed by *some* org the attacker controls (their own repo's webhook secret, configured on their own Shipit installation/App or org). It says nothing about which `Commit`/`Stack` should be affected.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this query is **global across all stacks**, matching any commit row (from any repository's stack) whose `sha` column equals the attacker-controlled `params.sha`. [2](#0-1) 
- `Commit#create_status_from_github!` → `add_status` replicates the GitHub status, recomputes `status`, and if the simple state changed, emits `Hook.emit(:deployable_status, ...)` and calls `stack.schedule_merges` when the new status is `success`. [3](#0-2) [4](#0-3) 
- `after_commit :schedule_continuous_delivery` on create is not relevant here (status isn't a commit create), but the status replication triggers `add_status`'s `stack.schedule_merges` path; more directly, once the victim commit's `status` is now `success`, any subsequent evaluation of `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) returns true. [5](#0-4) 
- `Commit#schedule_continuous_delivery` gates on `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob.perform_later(stack)` — as soon as this check is (re-)evaluated (e.g., by any other trigger that calls it, or by the same request path if the commit is freshly created), the victim's own stack — not the attacker's — is queued for deployment. [6](#0-5) 

Existing guards do not stop this:
- `verify_signature` binds only to the organization named in the *attacker's own* payload, not to the target commit's actual owning repository — it cannot detect the divergence because it never inspects which `Commit`/`Stack` rows will be touched. [7](#0-6) 
- `drop_unhandled_event` only checks that a handler exists for the event type, not repository ownership. [8](#0-7) 
- The `ExplicitParameters` schema in `StatusHandler` only requires `sha`/`state`/etc., with no repository field enforced or cross-checked against the matched `Commit#stack`. [9](#0-8) 

Attacker's exact action: attacker owns/controls `attacker-org/attacker-repo` (any GitHub org where they can configure a Shipit webhook secret and push status updates via GitHub's Status API, e.g. from their own CI). If that repository contains a commit object with an identical SHA to a commit already tracked in `victim-org/victim-repo`'s Shipit stack (trivially achievable via forking, since git SHAs are content-addressed and preserved across forks/mirrors), the attacker sends (or causes GitHub to send, e.g. via their own CI hitting the Status API) a `status` webhook with `state: success` for that shared `sha`. The payload is signed with the attacker's own org's `webhook_secret`, passes `verify_signature`, and `StatusHandler#process` updates the victim's commit row because the SQL lookup is by `sha` only.

### Impact Explanation
This allows a payload authenticated for one repository (attacker's) to mutate commit/status state belonging to another repository's stack (victim's), and — because `continuous_deployment: true` stacks auto-deploy as soon as their head commit becomes `deployable?` — this can trigger an unauthorized deploy of victim code (`Stack#trigger_continuous_delivery` → `trigger_deploy`). This matches the "Critical" category explicitly listed: *"a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy."* The blast radius spans every stack in the Shipit instance whose tracked commits can share a SHA with a repository the attacker controls (most easily via forks of public/internal repos), i.e., cross-tenant within a single Shipit deployment.

### Likelihood Explanation
Preconditions required: the attacker must control a repository whose commit history includes a SHA identical to a commit tracked by the victim's stack (straightforward for any forked repository, since fork SHAs are identical to upstream until history diverges at that commit), and must be able to get a `status` webhook for that SHA delivered to the shared Shipit instance signed with their own repo/org's webhook secret (i.e., their own repo is also configured against the same Shipit instance, or they can point their own CI's status webhook at Shipit's `/webhooks` endpoint with their legitimately-provisioned secret). Given Shipit is commonly a single shared instance serving many teams/orgs in an organization, and forking preserves SHAs exactly, this is a low-cost, repeatable attack requiring no privileged Shipit role, session, or secret beyond what the attacker already legitimately owns for their own repository.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and equivalently `CheckRunHandler`/any other SHA-keyed handler) to commits whose `stack.repository` matches the webhook's own `repository.full_name`/`owner`, e.g. join through `Stack`/`Repository` and filter by `full_name` from the payload before calling `create_status_from_github!`. Alternatively, verify at the model layer that `commit.stack.repository.owner == repository_owner` (and repo name) before applying any status/check-run mutation derived from an inbound webhook.

### Proof of Concept
Minitest plan (`test/models/webhooks/status_handler_test.rb` equivalent, no live GitHub):
1. Create `victim_repository` (`victim-org/victim-repo`) and `victim_stack` with `continuous_deployment: true`, `ignore_ci: false`.
2. Create `victim_commit` on `victim_stack` with `sha: SHARED_SHA` and an existing `failure` status (so initially `deployable?` is false and it is "undeployed").
3. Create `attacker_repository` (`attacker-org/attacker-repo`, unrelated) with `continuous_deployment: false`; no stack linkage needed beyond having a valid, distinct `webhook_secret`.
4. Build a `status` webhook payload: `{ sha: SHARED_SHA, state: 'success', repository: { full_name: 'attacker-org/attacker-repo', owner: { login: 'attacker-org' } } }`, signed with `attacker-org`'s `webhook_secret` via `X-Hub-Signature`.
5. POST to `/webhooks` with `X-Github-Event: status`.
6. Assert: before request, `victim_commit.reload.deployable?` is `false`; after request, `victim_commit.reload.deployable?` is `true`, and `ContinuousDeliveryJob` was enqueued with `victim_stack` (assert via `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])`), even though the request's signature was never valid for `victim-org` and `victim_stack.repository.full_name != 'attacker-org/attacker-repo'` — demonstrating the equality `signing_repository == mutated_stack.repository` is false while the mutation still occurs.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
