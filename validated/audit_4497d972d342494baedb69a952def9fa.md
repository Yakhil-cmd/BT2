## Title
Stack-scoped `ApiClient` tokens can read *any* stack's CI/deploy status via the CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` records can be scoped to a single stack via their `stack_id` column, and every other API controller enforces that scope by resolving the target stack through the `stacks` collection, which is filtered to `current_api_client.stack_id` when present. `Api::CCMenuController` instead overrides `stack` to resolve the target directly from the URL param via `Stack.from_param!`, bypassing that scoping. Since `require_permission :read, :stack` only checks the permission string and never checks which stack the token is bound to, a token that is supposed to be restricted to one stack can read any stack's build/deploy status.

### Finding Description
`Shipit::Api::BaseController` establishes the trust binding "an `ApiClient`'s `stack_id` authorizes only that stack": `stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` resolves via that scoped collection. [1](#0-0) 

`Api::StacksController` (and other resource controllers under `/api/stacks/*stack_id/...`) rely on this scoped `stack`/`stacks` helper, and this scoping is explicitly tested: [2](#0-1) 

`Api::CCMenuController`, however, redefines `stack` to bypass the scoped collection entirely and look up any stack by the URL parameter, and its `require_permission :read, :stack` before_action only verifies the client holds the `read:stack` permission string, not that the client is bound to *this* stack: [3](#0-2) 

The permission check itself is scope-string-only and has no notion of "which stack": [4](#0-3) 

So the equality that should hold — `token.stack_id == stack_being_read.id` (when `stack_id` is set) — is silently dropped for this one endpoint. The `ApiClient#stack_id` binding that authorizes a stack is not the same as the stack that is actually touched by `CCMenuController#show`.

### Impact Explanation
An `ApiClient` token deliberately scoped to a single stack (e.g., handed to a CI/monitoring integration that should only ever see one project's build status) can be replayed against `GET /api/stacks/:any_other_stack/ccmenu` to read that other stack's latest deploy/rollback id, status (success/failure/running), build label, and web URL. This is an unauthorized cross-stack read of stack/deploy state, breaking the isolation the token issuer relied upon — matching the "unauthenticated/unauthorized read of stack state ... deploy output" High-impact class.

### Likelihood Explanation
The bypass is unconditional and requires no special privilege beyond possessing any valid `read:stack`-scoped `ApiClient` token (which is routinely distributed for CCMenu integrations, see `Shipit::CCMenuUrlController`, which mints `read:stack`-permissioned clients for regular users): [5](#0-4) 
Any holder of such a token can simply change the `stack_id` in the request path; no signature, secret, or additional credential needs to be forged.

### Recommendation
In `Api::CCMenuController`, resolve `stack` through the same scoped `stacks` collection used by `BaseController`/`StacksController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so a stack-scoped token can only ever resolve to the stack it is bound to.

### Proof of Concept
1. Admin creates `ApiClient` `A` with `stack_id: stack_one.id`, `permissions: ['read:stack']` (e.g. via `resources :api_clients`).
2. Attacker/integration holding token `A` issues:
   `GET /api/stacks/<stack_two_owner>/<stack_two_name>/<stack_two_env>/ccmenu` with `Authorization: Basic <token A>` (or `?token=<A>`).
3. `authenticate_api_client` succeeds (token is valid); `require_permission :read, :stack` succeeds (`A` has `read:stack`).
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])`, returning `stack_two` — a stack `A` was never scoped to.
5. Response renders `stack_two`'s latest deploy status/label/URL, confirming the cross-stack read despite `A.stack_id == stack_one.id`.
