### Title
Cross-Organization Webhook Signature Confusion — Signature Validated Against `repository.owner.login` While Handlers Act On `repository.full_name` (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate a request against the organization derived from `params.dig('repository','owner','login')` (or `organization.login`), while every event handler (e.g. `PushHandler`, `StatusHandler`, membership/pull-request handlers) resolves the target `Repository`/`Stack` from a completely different field, `payload.dig('repository','full_name')`, via `Repository.from_github_repo_name`. Because `/webhooks` is an unauthenticated public endpoint and these are two independent, attacker-controlled JSON fields in the same POST body, an attacker can make the signature check pass against an organization whose webhook secret is weak/unset, while the actual mutation is applied to a stack belonging to an entirely different, "protected" organization.

### Finding Description
`verify_signature` resolves the signing org purely from the payload, not from any authenticated channel: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up a **per-organization** webhook secret from `secrets.github`, and multi-org deployments are an explicitly documented/supported configuration: [3](#0-2) [4](#0-3) 

Critically, `GitHubApp#verify_webhook_signature` treats a **blank/unset `webhook_secret`** for that org as "always valid": [5](#0-4) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Once the signature is accepted, the event body is dispatched to a `Handler`, and the mutation target (which `Repository`/`Stack` is affected) is derived from a **different** field of the same payload: [6](#0-5) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` and `repository.full_name`'s owner segment are normally the same string in a genuine GitHub-issued webhook, but since this controller accepts arbitrary unauthenticated POSTs and both values are independent JSON strings under attacker control, nothing enforces that `repository.owner.login == repository.full_name.split('/').first`. This breaks the binding: **organization whose credential authenticated the request == repository the handler writes to.**

An attacker who knows (or controls) a Shipit-configured organization with no `webhook_secret` set (documented as *optional* in `docs/setup.md`), or who can otherwise satisfy/guess a weak org secret, can set:
- `repository.owner.login` = the org with the weak/blank secret (used only for signature verification)
- `repository.full_name` = `victim-org/victim-repo` (used for the actual mutation)

The request passes `verify_signature` (because the *unrelated* org's secret check passes trivially), and the handler then mutates state for the victim org's stack, e.g.:

- `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` for the victim stack: [7](#0-6) 
- `StatusHandler#process` injects a forged CI status onto any commit matching the attacker-chosen `sha`, independent of repository/org entirely: [8](#0-7) 

`Repository.from_github_repo_name` performs a plain lookup with no cross-check against the field used for signature verification: [9](#0-8) 

### Impact Explanation
This lets an unprivileged attacker inject forged GitHub events (pushes, commit statuses, check-suite results, pull-request/merge events, membership changes) targeting a Stack/Repository belonging to an organization protected by a strong webhook secret, by "authenticating" through a different, weakly-protected (or secret-less) organization entry in the same Shipit deployment. Forged `status`/`check_suite` events can flip CI state used to gate merges/deploys, and forged `push` events can force `GithubSyncJob` to run against arbitrary SHAs for the victim stack — an authentication-bypass class issue that can enable an unauthorized deploy/merge decision downstream, satisfying the Critical/High impact bar (authentication bypass / unauthorized deploy or merge influence).

### Likelihood Explanation
Requires the deployment to run Shipit's documented multi-organization GitHub App configuration with at least one organization having no `webhook_secret` configured (explicitly called out as "optional" in `docs/setup.md`), or a guessable/leaked secret for any one organization in the fleet. This is a realistic operational configuration since `webhook_secret` is optional per the setup docs and multi-org support is a first-class documented feature. No credentials, session, or GitHub write access are required — only knowledge of the target repository's `full_name` and one org's weak/blank secret.

### Recommendation
In `WebhooksController#verify_signature`, after establishing the authenticating organization, cross-validate it against the owner encoded in `repository.full_name` (and any other repository-identifying field consumed by handlers) before dispatching — reject the request if `repository.owner.login` (or the owner segment of `repository.full_name`) does not match the organization whose secret validated the signature. Additionally, treat a blank/missing `webhook_secret` as a hard misconfiguration to warn/reject on for multi-org setups rather than silently defaulting to "verified", or scope webhook secret lookups so a given secret can only authenticate events for repositories actually owned by that installation.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub App config (as in `test/dummy/config/secrets_double_github_app.yml`) where `OrgWeak` has `webhook_secret: nil` and `OrgStrong` (owning the real target stack `OrgStrong/prod-app`) has a strong secret configured.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgWeak" }, "full_name": "OrgStrong/prod-app" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` computes `repository_owner = "OrgWeak"`, loads `Shipit.github(organization: "OrgWeak")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the request is accepted with `head(:ok)`, no valid signature required.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgStrong/prod-app")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's protected stack, despite the attacker never possessing `OrgStrong`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
