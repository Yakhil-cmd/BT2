Found a concrete analog: the webhook signature is verified using the GitHub App keyed by `repository.owner.login` (falling back to `organization.login`), but the actual data written by handlers is keyed by a *different* payload field — `repository.full_name` (`Handler#repository_name`, used by `stacks`) — and for the `membership` event, by `organization.login` for team creation and `member.login` for user/team-membership writes. These fields are never cross-checked against each other, so a signature that is valid for the GitHub App belonging to org X only proves that *some* field in the payload said "X owns this," not that the repository/organization actually operated on by the handler is the one X's secret is scoped to.

### Title
Webhook signature verification key is selected from an attacker-controlled payload field that is never cross-checked against the field the handlers act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` / `organization.login` read straight out of the unauthenticated JSON body, then verifies the signature against the *whole* raw body with that secret. Once verification passes, the event handlers key their writes off other, independently-controlled fields of the same body (`repository.full_name` for `Repository.from_github_repo_name`, or `organization.login` / `team.id` for `MembershipHandler`). Because the field used to choose the verification key and the field(s) used to decide which repository/org/team record gets mutated are never required to be consistent with each other, and Shipit explicitly supports multiple independently configured GitHub Apps/organizations sharing one instance (`Shipit.github_app_config`, `test/dummy/config/secrets_double_github_app.yml`), the binding "the org whose secret validated this signature" == "the org/repository actually written to" is not enforced anywhere.

### Finding Description
`verify_signature` in [1](#0-0)  computes `repository_owner` from the payload itself (`params.dig('repository','owner','login') || params.dig('organization','login')`, [2](#0-1) ) and looks up `Shipit.github(organization: repository_owner)` to obtain the `webhook_secret` used for HMAC verification via `GitHubApp#verify_webhook_signature` [3](#0-2) .

Once the signature check passes, `WebhooksController#create` dispatches the *entire* raw payload to all registered handlers for the event [4](#0-3) . Those handlers determine which Shipit records to touch using different payload fields than the one used for key selection:
- `Handler#stacks` resolves the target repository via `payload.dig('repository', 'full_name')` [5](#0-4) , a value fully independent of `repository.owner.login`/`organization.login` other than needing to be internally consistent in valid GitHub payloads — nothing stops it from being any string.
- `MembershipHandler#process` creates/updates a `Team` from `params.team` and sets `team.organization = params.organization.login`, and adds/removes a `User` found or created purely from `params.member.login` [6](#0-5) .

Shipit is explicitly designed to run multiple independent GitHub Apps for multiple organizations in one instance (`Shipit.github_app_config`, `Shipit.github(organization:)` in [7](#0-6) , documented in `docs/setup.md` "Using Multiple Github Applications" and exercised by `test/dummy/config/secrets_double_github_app.yml`). Each organization has its own independently generated `webhook_secret`. An operator/administrator who legitimately controls one onboarded organization's GitHub App (and therefore knows that org's `webhook_secret`) can craft a webhook body whose `repository.owner.login`/`organization.login` names *their own* org (so the correct, weaker secret is selected for verification) while setting `repository.full_name`, `organization.login`, `team`, or `member.login` fields that reference an entity belonging to a *different*, unrelated organization/repository tracked by the same Shipit instance. Because no code ever confirms that the field used to pick the verification key equals the field(s) the handler subsequently writes, a validly-signed webhook from org A can be used to mutate state belonging to org B's stacks/teams/users (e.g. `push`/`status`/`check_suite` records against org B's repository, or team membership grants under org B).

### Impact Explanation
This breaks the equality "organization whose `webhook_secret` authenticated this request" == "organization/repository the handler mutates." Concretely it allows:
- Injecting fabricated commit `status`/`check_suite` records or triggering `GithubSyncJob` for a stack belonging to another tenant's repository (`push`/`status`/`check_suite` handlers), which can influence CI-gated auto-deploy/merge-queue decisions on that other stack (`ProcessMergeRequestsJob#all_status_checks_passed?`), or
- Adding/removing arbitrary `User`s from a `Team` associated with a different organization via `MembershipHandler`, which can grant `current_user.authorized?` access (`Shipit.github_teams` membership check in `app/models/shipit/user.rb`), i.e. escalation into the app's authorization model for a different tenant.

This matches the "High" bucket (escalation into `Shipit.github_teams` authorization / unauthenticated write of stack state across tenants) rather than a benign informational issue, since it lets a party who legitimately controls only one onboarded org forge writes that affect a different org's stacks/teams within the same Shipit installation.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance to be configured with multiple GitHub Apps/organizations (a documented, supported configuration, not a hypothetical), and (2) the attacker to be an administrator/owner of one of those legitimately onboarded organizations (so they know their own `webhook_secret`) but want to affect a *different* onboarded organization's data. This is a real multi-tenancy trust-boundary gap in the engine's own webhook-authentication logic — it does not require compromising anyone else's secret, session, or API token, only knowledge of a secret the attacker was legitimately given for their own tenant.

### Recommendation
After signature verification succeeds, re-derive/require that every payload field used by handlers to select which repository/team/organization to mutate (`repository.full_name`, `organization.login`, etc.) belongs to the *same* organization whose `webhook_secret` was used to verify the signature, and reject the webhook (`head(422)`) if they disagree. Concretely, thread the verified `repository_owner` (or the resolved `GitHubApp`/organization) through to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` and have `Handler#stacks`/`MembershipHandler` validate that the repository's/team's owning organization matches it before performing any writes.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as supported by `Shipit.github_app_config`, mirroring `test/dummy/config/secrets_double_github_app.yml`).
2. As an administrator of `OrgA` (who legitimately knows `OrgA`'s `webhook_secret`), craft a `push` (or `status`/`membership`) webhook body where `repository.owner.login` (or `organization.login`) is set to `"OrgA"` but `repository.full_name` is set to `"OrgB/some-other-repo"` (a repository tracked under `OrgB`'s stacks), or, for `membership`, set `organization.login` to `"OrgA"` while `team.id`/`member.login` reference a team/user actually associated with `OrgB`.
3. Sign the raw body with `OrgA`'s `webhook_secret` using the standard `sha1=HMAC` scheme (`Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature`) and POST it to `/github/webhooks` with `X-Hub-Signature` set accordingly.
4. `verify_signature` selects `OrgA`'s app via `repository_owner`, the signature validates, and the request proceeds; `PushHandler`/`StatusHandler`/`MembershipHandler` then act on `OrgB`'s repository/team/user records purely from the unchecked `repository.full_name` / `organization.login` / `member.login` fields, even though only `OrgA`'s secret was ever proven.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
