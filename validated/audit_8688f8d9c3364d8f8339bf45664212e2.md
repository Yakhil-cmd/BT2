## Finding: Stack-scoped API tokens bypass their `stack_id` restriction on the CCMenu endpoint

### Title
Stack-scoped `ApiClient` tokens can read any stack's CI/deploy status via `CCMenuController#show` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
This is an analog of the reported bug class: a binding that is supposed to hold — "the stack a token authorizes" == "the stack the request actually touches" — is broken for one specific controller. `Shipit::ApiClient` supports scoping a token to a single stack via `stack_id`, and this scoping is enforced by the shared `stacks`/`stack` helpers in the base API controller, but `CCMenuController` reimplements `stack` in a way that skips that enforcement entirely.

### Finding Description
`Shipit::Api::BaseController` defines the intended binding between an `ApiClient` token and the stacks it may act on: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the token is scoped, and `stack` resolves the requested `stack_id` param *through* that restricted relation via `stacks.from_param!(...)`. Every other resource controller (`DeploysController`, `TasksController`, `LocksController`, etc.) relies on this inherited `stack` method, so a token scoped to stack A raises a "not found" for any other stack.

`CCMenuController`, however, overrides `stack` to bypass the scoped relation and query `Stack` directly: [2](#0-1) 

The action only checks `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` verifies only that the string `"read:stack"` is present in the client's `permissions` array — it never consults `stack_id`. Because `CCMenuController#stack` resolves `params[:stack_id]` with `Stack.from_param!` instead of the scoped `stacks.from_param!`, a token that was issued with `stack_id` set to Stack A (and `read:stack` permission) will nonetheless succeed against Stack B simply by passing a different `stack_id` in the URL.

The `stack_id` scoping mechanism is a first-class, database-backed concept (`belongs_to :stack, optional: true`) that other engine code relies on, e.g. `DestroyStackJob` cleans up `ApiClient.where(stack_id: stack.id)`: [4](#0-3) 
confirming stack-scoped tokens are an intended, supported feature of the engine, not merely a test fixture artifact.

### Impact Explanation
Any holder of a stack-scoped, `read:stack`-permissioned token (issued for one, presumably lower-trust, stack/team) can read the CI status, last deploy status, and deploy metadata of **any other stack** in the Shipit instance by hitting `/api/:stack_id/cc_menu` (or the equivalent route) with a different `stack_id`. This is an unauthenticated (relative to that stack) read of stack state, matching the High-impact bullet "unauthenticated read of stack state, task streams or deploy output" for a stack the token was never authorized to see.

### Likelihood Explanation
Exploitation requires only possession of any valid, stack-scoped `read:stack` API token (no privileged account, no GitHub access, no webhook secret) and knowledge/guessing of another stack's `repo_owner/repo_name/environment` path — information often discoverable from the Shipit UI/URLs. No signature or additional secret needs to be forged; the flaw is a straightforward missing scope check in one controller.

### Recommendation
Make `CCMenuController#stack` resolve through the same `stacks` scoping relation as `BaseController`, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the direct `Stack.from_param!` bypass so stack-scoped tokens are enforced consistently across all API controllers.

### Proof of Concept
1. Admin/integration issues an `ApiClient` scoped to Stack A: `ApiClient.create!(creator: user, name: 'monitor-A', stack: stack_a, permissions: %w[read:stack])`.
2. Using that token's `authentication_token`, an attacker (or the legitimate holder of the Stack-A token) sends:
   `GET /api/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/cc_menu.xml` with `Authorization: Basic base64(token)`.
3. `require_permission :read, :stack` passes because the token has `read:stack` in its permission list.
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (not `stacks.from_param!`), resolving Stack B despite the token being scoped to Stack A.
5. The response renders Stack B's `lastBuildStatus`, `lastBuildLabel`, `activity`, etc. — data the token was never authorized to access.
