### Title
Missing `default` case in `validateAuthentifiers`'s op-dispatch `evaluate()` silently drops the callback instead of panicking - ([File: definition.js])

### Summary
The `safe_pow()` fix in the report hardens an "unreachable" branch (reachable only if an upstream type-checker guard is ever bypassed) by replacing a silent `return None` with an explicit panic, so that any future guard-bypass fails loudly instead of producing a cryptic downstream crash. The `evaluate()` function inside `validateAuthentifiers()` in ocore's `definition.js` has the analogous defensive gap: its `switch(op)` block has no `default` clause, so if it is ever invoked with an `op` value not covered by any `case`, the callback `cb2` is simply never called.

### Finding Description
`validateAuthentifiers()` walks an address/asset spending-condition definition tree and, for each node, calls `evaluate(arr, path, cb2)`, dispatching on `op = arr[0]` via a `switch` statement [1](#0-0) . Every `case` in this switch eventually calls `cb2(...)`, e.g. the `'sig'`-equivalent branches, `'has definition change'` [2](#0-1) , and `'formula'` [3](#0-2) . However, the switch closes at line 1232 with **no `default:` case**, unlike the sibling dispatcher `evaluate()` inside `validateDefinition()`, which explicitly guards unknown ops with `default: return cb("unknown op: "+op);` [4](#0-3) , and unlike `hasReferences()`'s `evaluate()`, which also has `default: throw Error("unknown op: "+op);` [5](#0-4) .

This is structurally the same "should be unreachable, so it silently does nothing" pattern the report describes: the current design relies on `validateDefinition()` having already validated the definition tree (and rejected any unrecognized op) before `validateAuthentifiers()` is invoked on it [6](#0-5) . That invariant is exactly the kind of front-end guard the Vyper fix worried about being "bypassed" someday — e.g. by a future op being added to one switch's case list but not the other, by a different code path calling `validateAuthentifiers`/`evaluateAssetCondition` directly on unvalidated data, or by any latent mismatch between the two op tables. If such a mismatch is ever introduced, `evaluate()` returns without invoking `cb2`, so the enclosing `async.eachSeries`/direct call chain that leads to `handleResult` in `validateAuthentifiers` never fires its callback [6](#0-5) .

### Impact Explanation
Because `cb` is never called, the unit's validation (or AA definition/trigger evaluation, which reuses the same authentifier evaluation path) never completes: it neither accepts nor rejects the unit. Depending on the caller, this manifests as a hung validation call rather than a crash — for a full node this can stall processing of the affected unit/AA and, in the worst case, the whole validation pipeline serialized behind it, meaning the network is unable to confirm new units. This is qualitatively the same "silent None propagates into caller assuming a value, corrupting downstream logic/availability" failure mode the Vyper report calls out, just manifesting as a stuck callback rather than a JS exception.

### Likelihood Explanation
Today the missing `default` is not directly reachable because `validateDefinition()` is always run first and its own `default` clause rejects any unrecognized `op` before `validateAuthentifiers()` sees the tree. The bug is latent, exactly like the Vyper `safe_pow` two-variable branch, which was also "unreachable today because the type checker rejects" the input — it exists as a maintenance/defense-in-depth hazard rather than a directly exploitable path today. I could not fully verify whether the case-label sets of `validateDefinition`'s and `validateAuthentifiers`'s two `evaluate()` switches are perfectly identical for every current op (the file is large and I was cut off before completing the case-by-case diff), so I cannot rule out an existing mismatch; this should be checked directly in the full file.

### Recommendation
Add an explicit `default: throw Error("unknown op: "+op);` (matching the style already used in `validateDefinition()`'s `evaluate()` and in `hasReferences()`) to the `switch(op)` in `validateAuthentifiers()`'s `evaluate()` function in `definition.js`, so any guard bypass or op-table drift fails loudly and immediately instead of silently starving the callback chain. As a follow-up, diff the case-label lists of `validateDefinition()`'s `evaluate()` (definition.js lines ~118-618) against `validateAuthentifiers()`'s `evaluate()` (lines ~651-1232) to confirm no existing op is missing from either.

### Proof of Concept
Not directly triggerable today given the current op tables (as with the original Vyper finding, which is also "unreachable" pending a guard bypass). The theoretical trigger is: any unit/AA definition/trigger whose serialized definition array contains an `op` string accepted by `validateDefinition()`'s switch but absent from `validateAuthentifiers()`'s switch (or introduced there in the future) would hang the authentifier-evaluation callback indefinitely for that unit's validation.
