### Title
Cross-organization team membership deletion via GitHub `membership` webhook signed by an unrelated organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` resolves the target `Team` purely by `params.team.id` (the GitHub team's numeric ID) via `Team.find_or_create_by!(github_id: ...)`, without ever checking that the requesting/organization that authenticated the webhook (used in `WebhooksController#verify_signature`) matches the `organization` that actually owns the resolved `Team` record. An attacker who owns any GitHub organization configured in Shipit (with their own valid `webhook_secret`) can sign a `membership`/`removed` payload themselves, but populate `team.id` and `member.login` with a real team ID and login belonging to a completely different organization, causing Shipit to delete that victim's real `Membership` row.

### Finding Description
The broken binding, stated as an equality that should hold but does not:

`organization_that_signed_the_webhook (params.organization.login used in WebhooksController#verify_signature) == organization_that_owns_the_mutated_team (Team#organization for the record matched by github_id)`

Trace:
1. `WebhooksController#verify_signature` derives the signing organization entirely from the attacker-controlled JSON body: `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  then fetches `Shipit.github(organization: repository_owner)` and verifies the HMAC signature using that organization's own `webhook_secret` [2](#0-1) . Since `MembershipHandler`'s schema requires only `organization.login` (no `repository` key), the attacker fully controls which org's secret is used—they simply set it to their own org and sign with their own known secret. [3](#0-2) 
2. `MembershipHandler#process` then calls `find_or_create_team!`, which resolves the `Team` solely by `github_id: params.team.id`: `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [4](#0-3) . If a team with that `github_id` already exists (i.e., the real victim's team, previously synced via `Shipit.github_teams`/`Team.find_or_create_by_handle` [5](#0-4)  or `Team.fetch_and_create_from_github` [6](#0-5) ), the block is never executed and the existing record (with the real `organization`) is returned unchanged—no check that `params.organization.login` matches `team.organization`.
3. `process` then resolves/creates the member by login and, for `action == 'removed'`, calls `team.members.delete(member)` [7](#0-6) , deleting the `Membership` row for `team_id`/`user_id` with no re-check against the org that authenticated the request.

Attacker's exact request: a `POST /webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed with the attacker's own org's `webhook_secret`, and JSON body `{"action":"removed","team":{"id":<victim_team_github_id>,"name":"...","slug":"...","url":"..."},"organization":{"login":"attacker-org"},"member":{"login":"<victim-operator-login>"}}`. `verify_signature` passes because it only checks that the signature matches `attacker-org`'s own secret; nothing ties that check to the team/org actually mutated.

Existing guards don't help: `drop_unhandled_event` passes because `membership` is a handled event; `ExplicitParameters` schema only validates shape/types, not cross-field consistency between `organization.login` and the resolved `Team#organization`; there is no `require_permission!`/session check on this unauthenticated webhook endpoint by design (webhooks are meant to be authenticated by signature alone), and the signature check is itself organization-selectable by the attacker via a field they control.

### Impact Explanation
The attacker mutates a `Membership` record belonging to another organization's team—an organization they neither own nor have credentials for—using a webhook signed only with their own organization's secret. This directly revokes a legitimate Shipit operator's authorization for any team surfaced through `Shipit.github_teams` (which drives access control such as `User#authorized?`/`require_permission!` elsewhere in the app), i.e., a payload from one org mutating another org's "team" data, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). The exploit is repeatable against any team whose numeric GitHub `github_id` is known or guessable and that already exists in Shipit's database, and is not limited to a single victim—any operator/team pairing can be targeted by adjusting `member.login`.

### Likelihood Explanation
Preconditions per the question are already satisfied by an unprivileged internet attacker: they need (a) an org they control that is configured in Shipit with a known `webhook_secret` (a normal, low-cost setup in a multi-tenant Shipit instance since `Shipit.github(organization:)`/`github_app_config` support multiple orgs [8](#0-7) ), and (b) knowledge of the victim's numeric GitHub team ID and login, both of which are generally discoverable through the GitHub API/UI without special privilege. No Shipit session, API token, or victim-org secret is required. This is a single HTTP POST, fully repeatable and scriptable.

### Recommendation
In `find_or_create_team!`, verify that an existing `Team` matched by `github_id` has `organization == params.organization.login` before performing any mutation, and raise/drop the event on mismatch. Additionally, `WebhooksController#verify_signature` should not let the attacker choose which organization's secret validates the request when the target of the mutation (team/member) belongs to a different organization; the resolved organization used for signature verification should be cross-checked against the resource being mutated inside each handler.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (extending existing membership tests):
```ruby
test ":membership from a different organization cannot delete another org's real membership" do
  victim_team = shipit_teams(:shopify_developers) # organization == "shopify"
  victim_membership = shipit_memberships(:some_real_membership_for_victim_team_and_bob)

  @request.headers['X-Github-Event'] = 'membership'
  attacker_payload = {
    action: 'removed',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' }, # attacker's own org, signed with attacker-org's secret
    member: { login: 'bob' } # real victim operator login
  }.to_json

  # signature computed/stubbed using attacker-org's own webhook_secret, e.g. via Shipit.github(organization: 'attacker-org')
  assert_no_difference -> { Membership.where(team: victim_team, user: shipit_users(:bob)).count } do
    post :create, body: attacker_payload, as: :json
    assert_response :ok # currently succeeds and deletes -- should NOT
  end
end
```
Assertion on both sides of the binding: before the fix, `Membership.count` for `(victim_team, bob)` decreases even though the request was signed only against `attacker-org`'s secret (i.e., `signed_org = "attacker-org"` != `victim_team.organization = "shopify"`); after the fix, the mismatch should cause the handler to reject/no-op instead of mutating the victim's team.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
