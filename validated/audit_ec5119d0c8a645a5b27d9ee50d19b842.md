### Title
Pull request labels bypass the `VariableDefinition` env allowlist and inject attacker-chosen keys into the shell environment reaching `PTY.spawn` - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every PR label name (uppercased) with the fixed value `"true"` directly into the task/deploy environment, with no pass through `EnvironmentVariables.permit`/`VariableDefinition` allowlisting that is otherwise enforced for all other user-supplied env values. This lets any PR labeled with a shell-significant name (`IFS`, `BASH_ENV`, `ENV`, `PS4`, etc.) inject that variable, unfiltered, into the environment hash that `Command#start` passes to `PTY.spawn`.

### Finding Description
The intended binding is: *every key that ends up in the environment passed to `PTY.spawn` must have been validated against a `VariableDefinition` allowlist via `EnvironmentVariables#permit`* (as done for `Stack#trigger_task`/`Stack#build_deploy` through `definition.filter_envs`/`filter_deploy_envs`, backed by `EnvironmentVariables#permit` [1](#0-0)  and `Stack#trigger_task`/`#build_deploy` [2](#0-1) ).

That binding is violated for PR labels: `ReviewStack#env` merges `pull_request.labels` directly, uppercased, with value `"true"`, with no call to `EnvironmentVariables.permit` or any `VariableDefinition` check: [3](#0-2) 

Labels are attacker-controlled data coming straight from `github_pull_request.labels.map(&:name)` [4](#0-3) , captured on `labeled`/`opened`/`reopened`/`unlabeled` webhook events by `LabelCapturingHandler#capture_labels` [5](#0-4) .

`ReviewStack#env` (a `Stack` subclass) feeds into `TaskCommands#env`/`DeployCommands#env` via `super.merge(@stack.env)` [6](#0-5) , which is used to build every `Command` for install/perform steps [7](#0-6) . `Command#unbundled_env` merges that hash on top of the base env with no key filtering [8](#0-7) , and `Command#start` passes it straight to `PTY.spawn` [9](#0-8) .

This is confirmed by existing tests showing arbitrary label names becoming env keys unfiltered: [10](#0-9)  and [11](#0-10) .

Existing guards do not catch this: `verify_signature`/webhook auth only checks the request came from a configured GitHub webhook, not the label content; `EnvironmentVariables#permit` exists but is never invoked on this path; `VariableDefinition`-based filtering (`filter_deploy_envs`, `filter_task_envs`, `TaskDefinition#filter_envs`) only guards `task.env`/`deploy.env`, which are separate from `Stack#env`/`ReviewStack#env`. Nothing in this engine rejects reserved/dangerous variable names such as `IFS`, `BASH_ENV`, `ENV`, `PS4`, `LD_PRELOAD` from label text.

Regarding `PTY.spawn` argument semantics: if `deploy_spec` defines a step as one un-split string (e.g. Capistrano's default `'bundle exec cap $ENVIRONMENT deploy'` [12](#0-11) ), `interpolated_arguments` yields a single-element array, and `PTY.spawn(env, *interpolated_arguments, ...)` collapses to a single command string. Ruby's `Kernel#spawn`/`PTY.spawn` will run such a string via `/bin/sh -c` when it contains shell metacharacters (here `$`), meaning shell-interpreted variables in `env` (`IFS`, `ENV`, `BASH_ENV`, `PS4` under `set -x`) do reach a real shell process.

### Impact Explanation
Confirmed impact: an unprivileged PR author who can label their own PR can force an arbitrary attacker-chosen environment variable *name* (uppercased label text) with value `"true"` into the environment of every subsequent deploy/task `Command` for that review stack, bypassing the `VariableDefinition` allowlist that governs every other environment-injection path in this engine. This is a genuine violation of the intended binding and works repeatably against any review stack the attacker's PR is tied to.

Escalating this specific primitive to RCE (as speculated in the question via `BASH_ENV`) additionally requires: (a) the spawned step being a single, un-split shell string containing shell metacharacters so `/bin/sh -c` semantics kick in, (b) `/bin/sh` on the deploy host actually being `bash` (on many distributions `/bin/sh` is `dash`, which ignores `BASH_ENV`), and (c) the attacker also being able to place a file literally named `true` in the task's working directory. None of these three additional preconditions are established or demonstrated by anything in this engine's code — they depend on host/OS configuration and on the attacker separately achieving repo-content control in the checkout. Given that, the finding is solid as a **confirmed unfiltered environment-variable-name injection via PR labels**, but the specific "IFS/BASH_ENV → RCE" chain described in the question is not reliably demonstrable purely from this engine's code and remains conditional/speculative rather than proven.

### Likelihood Explanation
Adding a label to a PR normally requires `write`/`triage` access on the repository (or the label must already exist and the actor have permission to apply it) — plain unprivileged "any GitHub user who can open a PR" typically cannot add arbitrary new labels to their own PR without at least triage permissions, which is a precondition not fully satisfied by a pure outside contributor. Given the label, no other secrets or elevated Shipit state are required, and the injection into `Command#env` is deterministic and repeatable for every deploy/task on that stack. The full RCE escalation additionally requires specific shell (`bash` as `/bin/sh`) and filesystem preconditions not controlled by this engine.

### Recommendation
Filter `pull_request.labels` before merging into `ReviewStack#env`: reject/uppercase-exclude reserved/shell-significant names (`IFS`, `ENV`, `BASH_ENV`, `PS4`, `LD_PRELOAD`, `PATH`, etc.), or better, route label-derived env through `EnvironmentVariables.permit` against an explicit allowlist (e.g. require labels to match a configured `VariableDefinition`-style allowlist per deploy spec) instead of merging all label names unconditionally. Independently, harden `Command#start`/`Command#unbundled_env` to strip/reject well-known shell-interpreted variable names from any externally-influenced `env` hash before it reaches `PTY.spawn`, and avoid single-string `PTY.spawn` invocations that trigger implicit `/bin/sh -c` semantics.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (extend existing test)
test "#env allows arbitrary shell-significant keys via PR labels, bypassing the VariableDefinition allowlist" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["IFS", "BASH_ENV"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  # Binding under test: env keys reaching Command/PTY.spawn == keys permitted by
  # deploy_spec.machine_env / VariableDefinition allowlist.
  # LHS: keys actually present via PR labels
  assert_equal "true", env["IFS"]
  assert_equal "true", env["BASH_ENV"]

  # RHS: EnvironmentVariables.permit was never invoked for this path -
  # confirm no allowlist check occurred by verifying task.definition's own
  # variable allowlist does NOT include IFS/BASH_ENV, yet they are present in env.
  refute_includes task.definition.variables.map(&:name), "IFS"
  refute_includes task.definition.variables.map(&:name), "BASH_ENV"

  # Demonstrate this reaches Command's spawn env unfiltered.
  command = Shipit::TaskCommands.new(task).perform.first
  assert_equal "true", command.env["IFS"]
  assert_equal "true", command.env["BASH_ENV"]
end
```
This proves the LHS (`IFS`/`BASH_ENV` present in the `Command`'s env passed to `PTY.spawn`) diverges from the RHS (these names are absent from the `VariableDefinition` allowlist that is supposed to gate all env content), confirming the broken binding. Demonstrating actual code execution via `BASH_ENV` would additionally require controlling the host's `/bin/sh` implementation and planting a file named `true` in the working directory, which is outside what this engine's code controls and is not proven here.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
