### Title
Unsynchronized traversal of the in-memory best-children chain during out-of-band stability check races with concurrent writer mutations - ([File: network.js])

### Summary
`network.js`'s `tryToAdvanceStabilityPointForCatchupAATrigger` walks the in-memory unstable-unit "linked list" (`storage.assocUnstableUnits` / `storage.assocBestChildren`, populated and mutated by `writer.js`) via `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag` on a *dedicated* DB connection and explicitly *without* taking the `["write"]` mutex that normally serializes all mutations to these shared in-memory structures during `writer.saveJoint()`. This mirrors the Xen bug class: a shared, mutable list is traversed while it can be concurrently updated, because the code that walks it does not synchronize with the code that updates it.

### Finding Description
`storage.assocBestChildren` is a per-parent array acting as the "linked list" of best children in the DAG, used to walk the unstable-unit tree during stability determination (`main_chain.js` `createListOfBestChildren`, `readBestChildrenProps`, and the `goDownAndCollectBestChildrenFast` / `findBestChildrenNotIncludedInLaterUnits` helpers inside `determineIfStableInLaterUnits`) [1](#0-0) . This list is mutated whenever a new unit is written — `writer.js` pushes new unit props into `storage.assocBestChildren[my_best_parent_unit]` [2](#0-1)  — and it is pruned when AA responses are rolled back via `storage.forgetUnit`, which calls `_.pull(assocBestChildren[parent_unit], ...)` [3](#0-2) , invoked from `aa_composer.js` `revertResponsesInCaches` [4](#0-3) .

Normal writes to this list happen under the serializing `["write"]` mutex inside `writer.saveJoint` (comment: "without this locking, we get frequent deadlocks from mysql") [5](#0-4) . However, `network.js`'s `tryToAdvanceStabilityPointForCatchupAATrigger` deliberately runs `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag` on its own dedicated connection precisely to avoid interference "so that interleaving writes from other tasks don't interfere with this check" — but it only isolates the SQL transaction, not the shared JS in-memory caches (`assocUnstableUnits`, `assocBestChildren`) that the traversal actually reads, and it acquires no `["write"]` lock at all [6](#0-5) . Because Node.js interleaves async callbacks, another concurrent unit-write (a different `handleJoint` unlocked by per-address mutex, or an AA-trigger cascade under a different mutex key) can run `writer.saveJoint`/`revertResponsesInCaches` and mutate `assocBestChildren`/`assocUnstableUnits` mid-traversal, in the same way the Xen bug allowed the device model to mutate the ioport linked list while a vCPU was walking it without synchronization.

### Impact Explanation
If the best-children chain is mutated mid-walk (a node spliced out by `forgetUnit`/`_.pull` while `goDownAndCollectBestChildrenFast` is iterating it, or a new child pushed in after the snapshot was taken), `determineIfStableInLaterUnits` can compute an incorrect stability verdict — either declaring a unit prematurely stable/unstable relative to the persisted DB state, or throwing the "different best children" consistency-check error path (`throwError`) in `readBestChildrenProps` / `filterAltBranchRootUnits` [1](#0-0) . An incorrect stability result written via `determineIfStableInLaterUnitsAndUpdateStableMcFlag` can cause nodes to disagree on unit stability/finality, which under the "no false results" model of Obyte is a network-safety violation (nodes fork on what is considered final) — directly reachable class: node disagreement on validity/stability, potentially enabling double-spend of an output nodes disagree is stable.

### Likelihood Explanation
This path is reached automatically whenever a node is catching up and rejects a unit as a "possible AA" trigger (`ifTransientError` handling calls `tryToAdvanceStabilityPointForCatchupAATrigger(objJoint)` when `bCatchingUp` is true) [7](#0-6) . An attacker who can trigger AA cascades or post units while a node is catching up can increase the frequency of interleavings between this unlocked stability check and concurrent `writer.saveJoint`/AA-response-rollback mutations of `assocBestChildren`. Because Node.js is single-threaded, the race window is limited to `await`/callback boundaries (e.g., `conn.query`), which does narrow — but not eliminate — the exploitability; triggering it reliably requires precise timing.

### Recommendation
Take the same `["write"]` mutex (or an equivalent lock protecting `storage.assocUnstableUnits`/`storage.assocBestChildren`) around `tryToAdvanceStabilityPointForCatchupAATrigger`'s call to `determineIfStableInLaterUnitsAndUpdateStableMcFlag`, so that no concurrent `writer.saveJoint` or `revertResponsesInCaches` can mutate the in-memory best-children chain while it is being traversed, mirroring how `writer.js` already serializes its own mutations of the same structures.

### Proof of Concept
Not independently reproducible from static analysis alone: exploitation requires winning a narrow Node.js event-loop interleaving between (a) `tryToAdvanceStabilityPointForCatchupAATrigger`'s unlocked traversal of `storage.assocBestChildren`/`assocUnstableUnits` and (b) a concurrent `writer.saveJoint` push or `aa_composer.revertResponsesInCaches`/`storage.forgetUnit` mutation of the same structures during catch-up while AA-trigger units are being processed. Confirming actual exploitability (versus a benign transient inconsistency caught by the `throwError` self-checks in `main_chain.js`) would require dynamic/concurrency testing that is out of scope for this static review.

// we rejected a unit as a "possible AA" while catching up because we haven't executed its predecessor's AA triggers yet.
// try to advance the stability point to an unstable on-MC parent, which might stabilize the actual AA trigger and let the retransmitted unit through
async function tryToAdvanceStabilityPointForCatchupAATrigger(objJoint){
	const objUnit = objJoint.unit;
	const unit = objUnit.unit;
	const ball = objJoint.ball;
	if (!ball || storage.assocHashTreeUnitsByBall[ball] !== unit)
		return;
	// the parent might not be known to us yet, hence not in assocUnstableUnits
	const parent_unit = objUnit.parent_units.find(parent_unit => {
		const props = storage.assocUnstableUnits[parent_unit];
		return props && props.is_on_main_chain && !props.is_stable;
	});
	if (!parent_unit)
		return;
	const arrFreeUnits = main_chain.getFreeUnits();
	console.log(`possible AA trigger for unit ${unit}: trying to advance the stability point to its MC parent ${parent_unit} using free units ${arrFreeUnits.join(', ')}`);
	// use a dedicated connection so that interleaving writes from other tasks don't interfere with this check
	const conn = await db.takeConnectionFromPool();
	await conn.query("BEGIN");
	const bStable = await main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag(conn, parent_unit, arrFreeUnits, false);
	console.log(`AA parent ${parent_unit} stable in free units ${arrFreeUnits.join(', ')}? ${bStable}`);
	await conn.query("COMMIT");
	conn.release();
}
