## Finding: Multisig payload-mismatch check is feature-gated, allowing execution of an unapproved payload

### Title
Multisig transaction execution can bypass payload-vs-approval binding when `abort_if_multisig_payload_mismatch` is disabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, the Move function invoked by the VM prologue during multisig transaction admission/execution, only fully enforces that the executed payload matches the payload owners actually approved when a specific feature flag is enabled. When full payload storage is used (`transaction.payload`, as opposed to hash-only storage), the equality check between the submitted execution payload and the on-chain stored (approved) payload is wrapped in `features::abort_if_multisig_payload_mismatch_enabled()`.

### Finding Description
`validate_multisig_transaction` performs two separate payload-binding checks: [1](#0-0) 

1. If `transaction.payload_hash.is_some()` (i.e., the tx was created with only a hash stored on-chain), the submitted payload is hashed and compared to the stored hash — this check is unconditional.
2. If `transaction.payload.is_some()` (i.e., the tx was created with the full payload stored on-chain), the submitted payload is compared byte-for-byte to the stored payload — but **only if `features::abort_if_multisig_payload_mismatch_enabled()` is true**.

For multisig transactions created with the full payload stored on-chain, `payload_hash` is `option::none()` (the hash-only and full-payload storage paths are alternatives), so check #1 does not apply. If the `abort_if_multisig_payload_mismatch` feature is not enabled, check #2 is skipped entirely.

The Rust side confirms that `provided_payload` (the value passed as `payload` into this function) is derived from the `executable` field of the *submitted transaction being executed*, not from the on-chain approved transaction: [2](#0-1) 

This means the value that owners voted/approved (the stored `transaction.payload`) can, under this feature-gated condition, diverge from the value that is actually authenticated and — critically — from what `successful_transaction_execution_cleanup` later marks as executed, without any admission-time equality assertion.

### Impact Explanation
This is a pre-validation mismatch at the admission boundary for a multisig approval flow: an account with a multisig transaction that has enough owner approvals for payload `P1` can have a *different* payload `P2` executed and committed under that multisig account's authority, provided the transaction executable is submitted with `P2` and `abort_if_multisig_payload_mismatch` is disabled. This directly violates the "approval validation accepting the wrong approval set" invariant and can result in unauthorized state transitions/fund movement executed under the wrong (unapproved) operation while still being attributed to a legitimately-approved multisig sequence number.

### Likelihood Explanation
Exploitability is entirely contingent on the runtime state of the `abort_if_multisig_payload_mismatch` feature flag on the target network. I was not able to confirm from the available index whether this flag is enabled by default in the current mainnet/testnet configuration, or whether it is still in a gated rollout state — this could not be fully verified with the tools available. If the flag is enabled network-wide, this path is closed; if it is disabled (e.g., on a fresh devnet/testnet or a chain that has not yet enabled the flag), the mismatch is live. The existence of the flag and its explicit purpose (matching the comment "verify that the provided payload matches the stored payload") suggests this was a known gap that is being hardened behind a flag rather than a hard invariant, which increases likelihood that some deployments run without it enabled.

### Recommendation
- Make the full-payload equality check in `validate_multisig_transaction` unconditional (remove the feature gate), so that whenever `transaction.payload.is_some()`, the submitted execution payload must always match, regardless of feature-flag state.
- Alternatively, only allow `payload.is_empty()` (i.e., "use on-chain stored payload directly") as the sole way to skip the comparison, and reject any non-empty, mismatching payload unconditionally.
- Audit the current default/enablement state of `abort_if_multisig_payload_mismatch` across all Aptos networks and enable it before load-bearing multisig deployments rely on full on-chain payload storage.

### Proof of Concept
Conceptual PoC (feature-flag dependent, could not be executed against a live/local node to confirm current flag state):
1. Multisig account `M` requires 2-of-3 approvals.
2. Owner submits `create_transaction(M, payload=P1)` storing the full entry-function payload `P1` on-chain (`transaction.payload = Some(P1)`, `transaction.payload_hash = None`).
3. Two owners approve based on reviewing `P1`.
4. A malicious/compromised approving owner submits the actual execution transaction with `executable = EntryFunction(P2)` where `P2 != P1`.
5. `run_multisig_prologue` (`aptos-move/aptos-vm/src/transaction_validation.rs:419-479`) computes `provided_payload` from `P2`.
6. `validate_multisig_transaction` (`multisig_account.move:1328-1385`) skips the `payload_hash` check (it's `None`) and, if `abort_if_multisig_payload_mismatch_enabled()` is false, skips the `payload == stored_payload` check as well.
7. `P2` executes and is recorded as the completed multisig transaction for that sequence number, despite never having been approved by the required quorum.

pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
