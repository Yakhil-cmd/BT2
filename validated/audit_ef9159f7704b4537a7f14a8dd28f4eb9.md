### Title
Webhook signature verification selects the HMAC secret from an unverified `repository.owner.login` field while handlers act on a decoupled `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` chooses which GitHub App/organization's `webhook_secret` to validate an inbound webhook against based on `repository.owner.login` (or `organization.login`) pulled straight out of the **unverified** JSON body. Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#repository_name` re-reads the same body but a **different** field, `repository.full_name`, to decide which `Repository`/`Stack` the event applies to. These two attacker-controlled fields are never checked for consistency, so a party who legitimately possesses the webhook secret for one onboarded organization can forge a validly-signed payload that names a completely different organization's repository as the target.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
the secret used for `verify_webhook_signature` is looked up via [2](#0-1) 
i.e. `params.dig('repository', 'owner', 'login')`, taken from the raw, not-yet-verified request body.

Downstream, every event handler that needs to resolve a target repository (push, check_suite, etc.) inherits from `Handler` and instead reads: [3](#0-2) 
`payload.dig('repository', 'full_name')`.

Both `repository.owner.login` and `repository.full_name` are attacker-controlled JSON keys inside the same signed body — HMAC only proves *some* known secret was used to sign the whole byte string, it does not enforce that `owner.login` and `full_name` agree. So the equality the system implicitly relies on,

`organization whose secret authenticated the request == organization owning the repository the handler writes to`,

is never checked. An entity that knows the webhook secret for Org A (a legitimate, lower-trust organization onboarded to the same Shipit instance) can craft a body where `repository.owner.login = "org-a"` (so `verify_signature` selects and validates against Org A's secret) but `repository.full_name = "org-b/private-repo"` (so `PushHandler`/`CheckSuiteHandler` resolves and acts on Org B's `Stack`), sign it with Org A's secret, and submit it to `POST /webhooks`.

### Impact Explanation
This breaks the deployment-trust boundary between organizations hosted on the same Shipit instance: it is an authentication-bypass primitive for cross-organization actions rather than a benign UI bug. Concretely:
- `PushHandler#process` calls [4](#0-3)  which triggers `stack.sync_github(expected_head_sha:)` on an arbitrary victim organization's `Stack` that the forger has no legitimate access to.
- `CheckSuiteHandler#process` similarly schedules check-run refreshes for another organization's commits: [5](#0-4) .

This lets an attacker who only controls one org's webhook secret drive state changes (sync triggers, check-run refresh scheduling) for stacks/repositories belonging to any other organization configured on the shared Shipit deployment, which is exactly the "organization authenticated vs. repository that is written" binding called out as in-scope.

### Likelihood Explanation
Requires the attacker to already know a valid `webhook_secret` for at least one organization configured on the Shipit instance (e.g. as the administrator of their own onboarded GitHub App/organization in a multi-tenant Shipit deployment, per the documented multi-org config format in `docs/setup.md` and `config/secrets.development.shopify.yml`). This is a lower privilege bar than repository write access or an `ApiClient`/session token, and is plausible in any Shipit deployment serving more than one organization.

### Recommendation
After verifying the HMAC signature, re-derive the organization from the same field the handler will actually use (`repository.full_name`'s owner segment, or `repository.owner.login` consistently) and reject the webhook if the two disagree, or key handler repository resolution off the same identifier used to select the verification secret.

### Proof of Concept
1. Shipit instance configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` multi-org example).
2. Attacker knows `org-a`'s webhook secret (e.g., they administer the GitHub App for `org-a`).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/private-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(org-a-secret, body)>` and `X-Github-Event: push`, and POSTs to `/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner == "org-a"`, fetches `org-a`'s `GitHubApp`, and successfully verifies the signature ( [1](#0-0) ).
6. `PushHandler` then resolves the target via `repository.full_name == "org-b/private-repo"` ( [6](#0-5) ) and triggers `stack.sync_github` on `org-b`'s stack, an organization the attacker has no credentials for.

Note: I was unable to fully trace `Stack#sync_github` and `GithubSyncJob` to confirm whether the downstream sync can be escalated further (e.g., to trigger an unauthorized deploy) due to the final-iteration limit; this would need further investigation of `app/models/shipit/stack.rb` and `app/jobs/shipit/github_sync_job.rb`.
