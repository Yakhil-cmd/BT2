### Title
`StatusHandler#process` matches commits by SHA across all repositories, letting a forged/cross-repo GitHub status webhook trigger `ProcessMergeRequestsJob` for a victim's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no check that `params`'s `repository` matches the repository owning that commit's stack, unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`) which scope through `Repository.from_github_repo_name(repository_name)`. A signed `status` webhook whose payload SHA collides with a commit tracked by an unrelated stack will call `commit.create_status_from_github!`, which unconditionally calls `add_status`, which (via the state-transition test `#add_status schedule a MergeMergeRequests job...`) enqueues `ProcessMergeRequestsJob.perform_later(stack)` for that victim stack.

### Finding Description
The broken binding: `payload.dig('repository','full_name') == commit.stack.repository.full_name` is expected to hold for every commit that gets a new `Status` from a webhook, but `StatusHandler` never checks it.

Code path:
- `WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event('status')`, after `verify_signature` (keyed only on `repository_owner`, i.e. the org, not the specific repo/stack) and `ExplicitParameters` validation of `sha`/`state`/etc. [1](#0-0) 
- `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
This is the only place in the handler that touches commits, and it never calls `Handler#stacks`/`repository_name` to restrict to commits belonging to the payload's repository, unlike `PushHandler#process`, which scopes via `stacks.not_archived.where(branch:)` where `stacks` is `Repository.from_github_repo_name(repository_name)&.stacks`. [3](#0-2) [4](#0-3) 
- `Commit#create_status_from_github!` unconditionally calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }` with no origin/ownership check. [5](#0-4) 
- Creating the `Status` record fires `after_commit :schedule_continuous_delivery` and, per `Commit#add_status` (not shown above but exercised by the transition test), transitioning into `pending`/`success` enqueues `ProcessMergeRequestsJob.perform_later(stack)` for `commit.stack` - the test explicitly documents this side effect. [6](#0-5) [7](#0-6) 

Exploit flow: attacker owns/controls a repository (or any repository where the same GitHub App/webhook secret is valid, per the stated attacker capabilities) that shares a git commit SHA with a commit already tracked against a victim's stack (trivially achievable - git commit objects are portable; the attacker can push/cherry-pick the exact same commit object, byte-for-byte, into a repo they own, producing an identical SHA-1). The attacker then causes a real, validly-signed `status` webhook to fire from their own repository/org for that SHA with `state: success` (or `pending`). `verify_signature` only checks the signature against the org named in the payload - it does not check that the *specific commit* in the payload belongs to that org's tracked stacks. `StatusHandler` then matches the SHA against `Commit.where(sha: ...)` globally, finds the victim's row, and creates a `Status` for the victim's stack, re-triggering `ProcessMergeRequestsJob` for a stack the attacker never authenticated against.

None of the listed guards catch this: `verify_signature` validates the org owns the webhook secret, not that the commit belongs to that org's repo; `drop_unhandled_event`/`ExplicitParameters` only validate shape, not repository binding; `force_github_authentication`/`User#authorized?`/`require_permission!` don't apply to unauthenticated webhook ingestion at all.

### Impact Explanation
An attacker who controls an unrelated (even unaffiliated) repository can force creation of a `Status` row on a victim's stack and re-enqueue `ProcessMergeRequestsJob` for that stack, causing forced re-evaluation of the victim's merge queue from a party that does not own or maintain the victim's stack. Combined with `enable_ci_on_stack` also firing on `Status#after_create`, an attacker can flip a victim commit's CI state (e.g. inject a fake `success` status) purely by SHA collision, which can influence merge-queue processing/state transitions for a repository the attacker never authenticated against. This is a payload from one repository mutating another's stack/commit state and forcing an unauthorized re-evaluation of a merge pipeline, matching the Critical category ("a payload for one repository mutating another's stack, commit... or an unauthorized... merge").

### Likelihood Explanation
Preconditions: the attacker must be able to produce a validly-signed `status` webhook (granted per the stated attacker model - "emit webhooks from a repository they own") and must know/reproduce a SHA that also exists as a `Commit` row tied to a victim's stack. Because git commit objects are content-addressed and portable, an attacker can trivially reproduce an identical commit (and therefore identical SHA) in a repository they control - e.g., by copying/pushing the exact commit object from a public victim repo they can read, or by colluding with any contributor. No Shipit secrets, session, or API token are required. This is repeatable against any commit SHA the attacker can learn (e.g., from a public PR, git log, or CI logs) and works against arbitrary stacks whose repositories share the webhook-signing scope with the attacker's repo.

### Recommendation
Scope `StatusHandler#process` (and any other SHA-keyed handler) to the payload's own repository, mirroring `PushHandler`/`CheckSuiteHandler`: restrict the `Commit` lookup to commits whose `stack` belongs to `Repository.from_github_repo_name(repository_name)`'s stacks (i.e., use `stacks.joins(...).commits.where(sha: params.sha)` or equivalent), rather than an unscoped `Commit.where(sha: params.sha)` across the whole install.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not attach a status to a commit belonging to a different repository" do
  victim_commit = shipit_commits(:second) # belongs to some victim stack/repo
  other_repo_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'description' => 'forged',
    'context' => 'attacker/ci',
    'created_at' => 1.day.ago.to_s,
    'branches' => [],
    'repository' => { 'full_name' => 'attacker/unrelated-repo' }
  }

  assert_no_enqueued_jobs(only: ProcessMergeRequestsJob) do
    Shipit::Webhooks::Handlers::StatusHandler.call(other_repo_payload)
  end

  assert_equal 0, victim_commit.statuses.where(context: 'attacker/ci').count
end
```
Both sides of the equality (`other_repo_payload['repository']['full_name']` vs `victim_commit.stack.repository.full_name`) diverge, yet current code still creates the `Status` and enqueues `ProcessMergeRequestsJob.perform_later(victim_commit.stack)`, proving the vulnerability; after the fix the assertion should pass with zero enqueued jobs and zero created statuses.
