### Title
Cross-Organization Authorization Bypass via Global `Shipit.github_teams` Check in Multi-Org Deployments - (File: `app/controllers/concerns/shipit/authentication.rb`)

### Summary
Shipit supports multiple GitHub organizations, each configured with its own GitHub App, OAuth credentials, and `oauth.teams` restriction [1](#0-0) . However, the single authorization gate that decides whether a logged-in user may access *any* stack/repository checks membership against `Shipit.github_teams`, which is always derived from the **default** organization's OAuth app, never from the organization that actually owns the repository/stack being accessed [2](#0-1) .

### Finding Description
`Shipit.github_teams` is computed as:
```ruby
def github_teams
  @github_teams ||= github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }
end
``` [3](#0-2) 

`github` here is called with no `organization:` argument, so it resolves to `github_default_organization`, i.e. the **first** organization key found in `secrets.github` [4](#0-3) . This is the same "default" app whose `oauth_config` is the only one wired into the process-wide `OmniAuth::Builder` middleware:
```ruby
if Shipit.github.oauth?
  OmniAuth::Strategies::GitHub.configure(path_prefix: '/github/auth')
  app.middleware.use(OmniAuth::Builder) do
    provider(:github, *Shipit.github.oauth_config)
  end
end
``` [5](#0-4) 

Meanwhile, `force_github_authentication` — the single gate applied to *every* controller (stacks, repositories, tasks, deploys, etc.) — grants access purely based on this global team list:
```ruby
unless current_user.authorized?
  ...
  render(plain: "You must be a member of #{team_list} ...", status: :forbidden)
end
``` [6](#0-5) 
and
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [7](#0-6) 

By contrast, the webhook path already understands the multi-org model and resolves the GitHub App **per repository owner**:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(...)
``` [8](#0-7) 

This is the exact class of bug described in the report: one binding (the organization/app used to *authenticate and authorize* the user — always the default org's OAuth teams) diverges from the other binding that should govern access (the organization that actually owns the *repository/stack being written to*, per `Shipit.github(organization: repository_owner)`). Just as the Universal Router forwarded native-token calls to v4 without covering them under the same guarantee applied elsewhere in the same codebase, Shipit enforces org-scoped GitHub App/webhook security per-repository but enforces user authorization only against a single hardcoded default org's team list.

### Impact Explanation
In a multi-organization Shipit deployment (the documented `github: {org1: {...}, org2: {...}}` schema in `config/secrets.development.shopify.yml`), a user who is a member of `org1`'s restricted team (`oauth.teams`) is granted `authorized?` for the *entire* application — including stacks/repositories belonging to `org2`, whose separately configured `oauth.teams` was meant to gate access to org2's resources. This is a direct escalation into `Shipit.github_teams` authorization as explicitly listed as a High-impact category: the user's team membership in one organization's authorization boundary is being used to bypass another organization's independently configured `oauth.teams` restriction, enabling unauthorized viewing of stack state, task output, and potentially triggering deploys/rollbacks on repositories that org's administrators intended to restrict to their own team.

### Likelihood Explanation
Any operator following the documented multi-org configuration schema (`config/secrets.development.shopify.yml`, explicitly shipped as a template) with differing `oauth.teams` per organization is affected. No special privileges are needed beyond being a legitimate member of any one configured organization's authorized team — the flaw is structural (global authorization check vs. per-org app resolution) and requires no attacker-controlled input manipulation, only normal login through the single configured OmniAuth GitHub provider.

### Recommendation
Scope authorization checks to the organization owning the resource being accessed, mirroring the pattern already used for webhook signature verification (`Shipit.github(organization: repository_owner)`). Concretely: `User#authorized?` and `force_github_authentication` should accept/resolve the target repository's organization and check membership against that organization's `Shipit.github(organization: org).oauth_teams`-derived teams rather than the global default-organization team list. Additionally, evaluate whether a single global OmniAuth provider can properly support genuinely independent multi-org trust boundaries at all.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `org1` (default, first key) with `oauth.teams: [org1/restricted]`, and `org2` with `oauth.teams: [org2/restricted]`, each with distinct GitHub Apps/OAuth apps, per the documented schema in `config/secrets.development.shopify.yml`.
2. A user who is a member of `org1/restricted` (but not a member of any `org2` team) logs in via the single configured OmniAuth GitHub provider — the flow in `GithubAuthenticationController#callback` / `#sign_in_github` creates/looks up the `User` and stores `session[:user_id]` with no organization scoping [9](#0-8) .
3. `current_user.authorized?` evaluates true because `Shipit.github_teams` resolves solely from `org1`'s OAuth teams, and the user is a member of `org1/restricted`.
4. The user then visits `/repositories/org2/some-repo` or any stack under `org2`. `force_github_authentication` passes because `authorized?` is true, granting the `org1`-authorized user full access to `org2`'s stacks, task streams, and deploy/rollback actions — despite never being a member of any `org2` team.

**File:** lib/shipit.rb (L170-188)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end
```
