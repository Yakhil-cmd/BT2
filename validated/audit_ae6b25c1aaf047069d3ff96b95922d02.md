### Title
Race between periodic cache-eviction (`shrinkCache`/`resetMemory`) and AA-trigger cache mutation on `assocStableUnits` corrupts `count_aa_responses` tracking - ([File: storage.js])

### Summary
`storage.js` maintains an in-memory cache (`assocStableUnits`) of unit properties that is mutated from multiple asynchronous code paths under different (and in one path, no) mutex locks. `aa_composer.js`'s `handlePrimaryAATrigger()` reads and mutates `storage.assocStableUnits[unit].count_aa_responses` while holding only the `['aa_triggers']` lock, whereas the periodic cache-eviction routines `shrinkCache()` and `resetMemory()`/`resetStableUnits()` delete or entirely replace entries of the same `assocStableUnits` map while holding the `['write']` lock. Because these two lock domains are independent, `shrinkCache`'s `setInterval`-driven eviction (every 300s) or a rollback-triggered `resetMemory()` can run concurrently with an in-flight `handlePrimaryAATrigger()` call and delete/replace the very object that `handlePrimaryAATrigger()` is still mutating, analogous to the zsmalloc bug where an async free worker races an unlocked concurrent mutator of the same object.

### Finding Description
`aa_composer.js` runs AA trigger execution guarded only by the `aa_triggers` mutex key: [1](#0-0) 

Inside `handlePrimaryAATrigger`, after committing the DB update, the code reaches directly into the shared cache object and mutates it in place, without holding the `write` lock that protects the same cache elsewhere: [2](#0-1) 

Meanwhile, `storage.js`'s `shrinkCache()` — invoked every 300 seconds via `setInterval` — takes the `write` lock and, inside nested async DB-query callbacks, deletes entries straight out of `assocStableUnits`: [3](#0-2) 

`resetStableUnits()` (called from `resetMemory()`, which `writer.js` invokes on a failed/rolled-back write) wipes the entire `assocStableUnits` map and reinitializes it from the DB: [4](#0-3) [5](#0-4) 

Because `handlePrimaryAATrigger()`'s critical section (`storage.assocStableUnits[unit]` lookup → mutation → `batch.write`) is not serialized against the `write` lock used by `shrinkCache`/`resetMemory`, the following interleavings are possible:
1. `handlePrimaryAATrigger()` reads `objUnitProps = storage.assocStableUnits[unit]` and begins incrementing `count_aa_responses`.
2. Before the in-memory mutation is observed elsewhere, `shrinkCache()` (running under `write` lock, unrelated to `aa_triggers`) deletes `assocStableUnits[unit]` in its `db.query` callback, or `resetMemory()` wipes and reinitializes the whole map from the (not-yet-updated) DB row.
3. The mutation made by `handlePrimaryAATrigger()` is applied to a now-detached/stale object that is no longer reachable from `assocStableUnits`, so future readers of `readUnitProps()` (which serves straight from `assocStableUnits[unit]` when the cache is populated — see `storage.js:1497-1552` cache-hit path) get a `count_aa_responses` value that never reflects the increment, i.e., a torn/lost update of the exact same class as `lock_zspage()` operating on a page whose ownership already changed underneath it.

### Impact Explanation
`count_aa_responses`/`max_aa_responses` gate how many response units a single AA trigger execution is allowed to spawn — this is a resource/anti-abuse limit for AA execution reachable by any unprivileged AA trigger sender (posting a payment/trigger to an AA address). A lost update to this counter, caused by the unsynchronized cache eviction race, can desynchronize the in-memory limit-enforcement state from the persisted DB state, undermining the invariant the cap is meant to guarantee for that unit going forward. Depending on how later code paths trust the cached counter versus the DB value, this can permit the AA response cap to be bypassed on subsequent triggers referencing the same unit, or can cause spurious inconsistency-detection crashes elsewhere in `storage.js` that explicitly `throw Error` when cache and DB values disagree (see the `_.isEqual` consistency checks in `readUnitProps`), which is itself a node-availability/consensus-processing risk (a node processing AA triggers can crash mid-execution, disagreeing with peers on which units/response chains got processed).

### Likelihood Explanation
The race window depends on ordinary node timing: `shrinkCache` fires on a fixed 300s timer and `resetMemory` fires whenever a write rolls back, while `handlePrimaryAATrigger` runs for every AA trigger with no coordinating lock. An attacker does not need special privileges — merely posting AA triggers at a steady rate (fully within reach of a normal AA trigger sender) increases the probability that trigger execution overlaps with a periodic cache-eviction cycle. Because Node.js callbacks interleave only at await/callback boundaries, the actual probability of hitting the exact unlucky interleaving per single trigger is not high, but is plausible under sustained load, similar in nature (though not identical in mechanism) to the kernel race that required specific but realistic timing between page migration and zspage free.

### Recommendation
Ensure all mutations and evictions of `storage.assocStableUnits` (and the sibling caches `assocUnstableUnits`, `assocCachedUnits`, etc.) are serialized under a single, consistently-acquired lock. Specifically, have `handlePrimaryAATrigger()` in `aa_composer.js` acquire the `write` mutex (or otherwise synchronize with `shrinkCache`/`resetMemory`) before reading and mutating `storage.assocStableUnits[unit]`, or move the `count_aa_responses` update to occur strictly under the same lock domain used by cache eviction, so cache eviction cannot run concurrently with an in-flight mutation of the same cached object.

### Proof of Concept
Conceptual reproduction (exact timing-dependent, requires instrumentation to force the interleaving deterministically):
1. Start a node with `conf.js` configured for a short `shrinkCache` interval (or wait for the natural 300s tick).
2. As an ordinary user, post a unit that triggers an AA (`aa_trigger`) whose processing takes long enough (e.g., large state, many secondary triggers) to still be inside `handlePrimaryAATrigger()`'s async chain when `shrinkCache()`'s timer fires and its `db.query` callback executes `delete assocStableUnits[row.unit]` for the same unit (this is naturally more likely if `min_retrievable_mci`/`last_stable_mci` bracket happens to include the unit's MCI).
3. Observe that the `count_aa_responses` mutation performed by `handlePrimaryAATrigger()` (`aa_composer.js:104-109`) is applied to the object reference held locally, but the map entry it was retrieved from has been deleted/replaced, so a subsequent `readUnitProps()` cache-hit for the same unit returns a `count_aa_responses` that does not reflect the increment — or, alternatively, the `_.isEqual` consistency assertions in `readUnitProps` (`storage.js:1526-1551`) throw, crashing AA-trigger processing on that node.

Note: I was unable to fully trace, within the remaining investigation budget, the exact downstream enforcement logic in `validation.js` that consumes `count_aa_responses`/`max_aa_responses` to confirm the precise economic exploit path (e.g., whether the cap-bypass can be leveraged into AA fund loss versus "only" a resource-limit bypass/crash). This should be verified with a live Devin session that can trace `validation.js`'s use of these counters end-to-end and attempt to reproduce the race with instrumented timing.
