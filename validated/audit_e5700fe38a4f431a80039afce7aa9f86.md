### Title
Unscoped `Commit.where(sha:)` in `StatusHandler` lets a webhook from one repository write Status rows (and trigger deploys) on Stacks belonging to a completely different repository/organization - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no join or filter on the reporting repository, even though the base `Handler` class already provides a `stacks`/`repository_name` scoping mechanism (`Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`) that other handlers rely on. Because commit `sha` is only unique per `(sha, stack_id)` in this schema, a validly signed "status" webhook that legitimately originates from repository/org X can create `Status` rows on any other tenant's Stack whose `Commit` table happens to contain the same sha string, regardless of which repository or organization that Stack belongs to.

### Finding Description
The broken binding is: the code should enforce
`Commit.joins(stack: :repository).where(sha: params.sha, repositories: { full_name: payload.dig('repository', 'full_name') })`
but instead executes [1](#0-0) 
`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no repository/stack scoping at all.

The base `Handler` class already exposes the correct primitive for this: `stacks` resolves via `Repository.from_github_repo_name(repository_name)`, where `repository_name = payload.dig('repository', 'full_name')`: [2](#0-1) 
`StatusHandler` simply never uses it.

`WebhooksController#verify_signature` only validates that the HMAC signature matches the `Shipit.github(organization: repository_owner)` secret for the org named in the payload — it says nothing about whether the `sha` in the payload actually belongs to that repository: [3](#0-2) 

The schema confirms `sha` is only unique per stack, not globally: [4](#0-3) 

Attack flow:
1. The attacker owns/administers a repository X that is registered in Shipit as a `Repository`/`Stack` (per the rules, "emit webhooks from a repository they own" is an allowed capability). X's org has a legitimately configured GitHub App and `webhook_secret`.
2. The attacker calls the standard GitHub Statuses API (`POST /repos/{owner}/{repoX}/statuses/{sha}`), supplying an arbitrary `sha` value — GitHub does not require that sha to be reachable in repo X's own history to accept the API call.
3. GitHub sends a `status` webhook to Shipit, correctly HMAC-signed with X's real `webhook_secret` (the attacker never needs to know the secret — GitHub computes it for its own legitimate installation).
4. `verify_signature` passes because it only checks the signature against `repository_owner` (X's org), not that the sha belongs to X.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds every `Commit` row across every tenant Stack that happens to share that sha (e.g., a Stack Y tracking a completely different repository, previously synced by `GithubSyncJob`), and calls `create_status_from_github!` on each — writing an attacker-controlled `state`/`description`/`target_url` Status onto Stack Y's commit.

Existing guards fail because they check the wrong thing: signature verification authenticates "this webhook really came from GitHub for org X," but nothing subsequently checks "does this sha's Commit row actually belong to a Stack backed by repository X."

### Impact Explanation
An attacker who controls any repository tracked by Shipit can write forged CI status data onto an unrelated Stack/repository/tenant's commit, without ever touching that tenant's actual GitHub repo or credentials. If the victim Stack has continuous delivery enabled and the forged `success` status satisfies a required/blocking context, this can push the victim Stack toward `deployable?` and trigger an unauthorized deploy — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The blast radius is `Commit.where(sha: params.sha).count`, i.e., every Stack across the installation that independently synced a commit with that sha, unbounded by the attacker's own repository.

### Likelihood Explanation
Requires: (a) the Shipit instance hosts multiple Stacks/organizations, (b) the attacker controls at least one repository registered with Shipit (a normal, low-privilege situation for contributors/vendored-fork owners), and (c) knowledge of a target sha that already exists as a `Commit` row in a victim Stack (discoverable via Shipit's own UI/API or public GitHub history). No Shipit secrets, sessions, or tokens are needed — the attacker uses GitHub's own signed webhook delivery for a repo they legitimately control. This is fully repeatable and requires no timing or race condition.

### Recommendation
Scope `StatusHandler#process` through the repository named in the payload, e.g. use the base `stacks` helper (or an equivalent join through `stack.repository.full_name == payload.dig('repository','full_name')`) to restrict `Commit.where(sha: params.sha)` to commits belonging to Stacks whose repository matches the reporting `repository.full_name`, mirroring the scoping already used by other handlers.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, extending existing `":state create a Status for the specific commit"` test):
1. Seed two `Repository`/`Stack` pairs, `repo_a`/`stack_a` and `repo_b`/`stack_b`, with different `full_name`s.
2. Create `Commit` rows with identical `sha: "deadbeef..."` in both `stack_a.commits` and `stack_b.commits` (permitted by the `(sha, stack_id)` unique index).
3. Stub `Shipit.github(organization: repo_a_owner).verify_webhook_signature` to return `true` (simulating a legitimately signed webhook for org A only).
4. POST a `status` webhook with `repository.full_name = repo_a.full_name` and `sha = "deadbeef..."`.
5. Assert equality that is claimed to hold but doesn't:
   - Expected: `stack_b.commits.by_sha("deadbeef...").statuses.count == 0` (no status written for a Stack not owning the webhook's repository).
   - Actual: `stack_b.commits.by_sha("deadbeef...").statuses.count == 1` (status was written).
6. Additionally assert `Status.count` increased by 2 (one per stack) from a single webhook naming only `repo_a`, and check `stack_b.reload.deployable?` transitions if the forged state is `success` on a required context — demonstrating cross-tenant mutation from a single-repository webhook.
