### Title
Unbounded multiplication of untrusted `count_coins × denomination` in asset cap validation can desynchronize declared cap from actual issuable supply - (File: validation.js)

### Summary
`validateAssetDefinition` (and its AA-definition counterpart in `aa_validation.js`) computes the asset's total capped supply by summing `denomInfo.count_coins * denomInfo.denomination` for each fixed-denomination entry, using plain JavaScript `number` arithmetic (IEEE-754 double), not `Decimal`/BigInt. This mirrors the Primitive Finance overflow pattern: multiplying two untrusted, individually-bounded-looking values without protecting the *product* from precision loss/overflow beyond `Number.MAX_SAFE_INTEGER` (2^53−1).

### Finding Description
In `validateAssetDefinition`, each denomination entry is checked only as follows: [1](#0-0) 
`denomInfo.denomination` is bounded to `constants.MAX_CAP`, but only under a version-gated fix (`pemCurvesFixMci`), and `denomInfo.count_coins` is checked solely with `isPositiveInteger`, with **no upper bound at all**. The accumulator then does:
```
total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination;
```
which is a native JS float multiplication. If `count_coins` is chosen close to `Number.MAX_SAFE_INTEGER` and `denomination` is any value up to `MAX_CAP`, the product can exceed the 53-bit safe-integer range, silently losing precision instead of throwing, exactly the class of bug the external report describes for `res.reserveRisky * deltaTime` and `(res.reserveRisky * 1e18) / res.liquidity` prior to being cast to a wider/safer type.

The same unguarded pattern is repeated in the AA-definition validation path: [2](#0-1) 

This cap value is later relied on for issuance bookkeeping in `indivisible_asset.js`, where the identical multiplication is used to compute the amount actually issued for a denomination: [3](#0-2) 
and is cross-checked in `validation.js`'s `validateIndivisibleIssue` via a strict equality against another instance of the same unguarded multiplication: [4](#0-3) 

### Impact Explanation
The `cap` field is the invariant that fixed-denomination/indivisible assets rely on to bound total supply. If the sum used to validate `cap == Σ(count_coins × denomination)` loses precision due to double-precision float overflow, an asset issuer could construct a denomination table whose declared `cap` does not match the true achievable sum of issuable coins, undermining the supply-cap guarantee relied on by holders/AAs that trust the `cap` field for economic assumptions (e.g., total token supply, pricing formulas in AAs referencing `asset` caps). This is a supply-integrity issue analogous to the audited overflow, reachable by any address that posts an asset-definition unit or AA that defines a fixed-denomination asset — no privileged role required.

### Likelihood Explanation
Medium likelihood: exploiting float precision loss to produce an exact but false equality (`total_cap_from_denominations === payload.cap`) requires careful selection of `count_coins`/`denomination` pairs, and the individual `input.amount`/output checks elsewhere are still separately bounded by `constants.MAX_CAP`, which constrains how much can actually be issued in any single input. This limits (but does not eliminate) the practical blast radius — the main risk is inconsistency in the accounting invariant rather than an immediate unbounded mint of billions of units in a single input. I was not able to confirm from the index whether `isPositiveInteger` in `validation_utils.js` itself imposes a `Number.MAX_SAFE_INTEGER`-style ceiling (a tool call to inspect it failed), which would materially change the exploitability assessment — this should be verified directly in the repository.

### Recommendation
- Bound `count_coins` explicitly (not just `denomination`) to a safe multiplier such that `count_coins * denomination <= constants.MAX_CAP` before accumulating, performed with an overflow-safe check (e.g., verify `denomination === 0 || count_coins <= Math.floor(constants.MAX_CAP / denomination)` prior to multiplying) rather than checking the fields independently.
- Apply the same fix consistently in `validation.js` (`validateAssetDefinition`, `validateIndivisibleIssue`), `aa_validation.js` (`validateAADefinition`), and `indivisible_asset.js` (`issueNextCoin`).
- Remove the MCI-gating on the `denomination > constants.MAX_CAP` check if backward compatibility is not required for very old units, since it currently only protects one operand of the multiplication.

### Proof of Concept
1. Compose (or have an AA define) an asset with `fixed_denominations: true` and a `denominations` array containing an entry with `denomination` close to `constants.MAX_CAP` and `count_coins` chosen so that `count_coins * denomination` as a JS double rounds to a value distinct from the true mathematical product but still equals the attacker's chosen `cap` field.
2. Submit the asset-definition unit; `validateAssetDefinition` will accept it because the double-precision-computed `total_cap_from_denominations` equals `payload.cap` even though the true integer product differs.
3. Downstream issuance logic in `indivisible_asset.js`/`validation.js` recomputes the same lossy product when authorizing issuance, so the accounting invariant `cap == Σ(count_coins × denomination)` no longer holds against the true intended supply, an inconsistency exploitable to make the network/wallets disagree about true asset supply bounds.

(Note: full exploitability depends on the exact bound enforced by `isPositiveInteger`, which I could not confirm from the index — recommend verifying `validation_utils.js` directly.)
