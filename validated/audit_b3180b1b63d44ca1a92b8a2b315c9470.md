Confirmed: `is-price-update-more-recent` requires `publish-time > timestamps[price-identifier]` (strictly greater), so a second submission of the *same* (or an older) Pyth VAA for an identifier that has already been written fails with `ERR_NEWER_PRICE_AVAILABLE`, which propagates up through `write-batch-entry` → `write` → `verify-and-update-price-feeds` → `write-feed` → `write-feeds` as `ERR-PRICE-FEED-UPDATE-FAILED`, reverting the entire calling `market.clar` transaction.

### Title
Mempool front-running of bundled Pyth price-feed updates lets an attacker revert a victim's protective transaction and clear the way for liquidation - (File: `local-testing/contracts/market/market.clar`, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar`'s hot-path functions (`collateral-add`, `collateral-remove`, `borrow`, `liquidate`) accept an optional `price-feeds` parameter that is applied via `write-feeds`/`write-feed` before any position logic runs [1](#0-0) . These Pyth VAAs are broadcast in the public transaction (visible in the mempool as plain call arguments) and get submitted to the shared, protocol-wide `pyth-storage-v4` price map keyed only by `price-identifier`, not by caller [2](#0-1) . Because the underlying feed-freshness check requires the new `publish-time` to be strictly greater than the stored one (`is-price-update-more-recent`), an attacker who copies the exact price-feed bytes from a pending victim transaction and submits them first will succeed, and the victim's now-"stale" duplicate submission fails with `ERR_NEWER_PRICE_AVAILABLE` → `ERR-PRICE-FEED-UPDATE-FAILED`, reverting the victim's entire transaction [3](#0-2) [4](#0-3) .

### Finding Description
The shared state here is the global `prices`/`timestamps` map in `pyth-storage-v4.clar`, which is written by whichever transaction includes a given price-identifier update first, and consumed by every other transaction (any user, any contract call) that references the same identifier in the same or later blocks [5](#0-4) . Victim (e.g. a borrower whose position is close to the liquidation threshold) constructs a transaction such as `collateral-add` or `repay`-plus-`collateral-add`-with-feeds intended to push their position back to health, bundling a signed Pyth VAA to refresh a stale price because the position check requires fresh oracle data. Attacker observes this pending transaction in the mempool, extracts the identical `price-feeds` buffer, and submits their own (irrelevant, cheap, e.g. `collateral-add` with `amount=0`... more practically any function accepting `price-feeds`) transaction with higher priority/fee so it lands first in the same block. The attacker's transaction successfully calls `write-feed` → `verify-and-update-price-feeds` → `pyth-storage-v4.write`, which sets `timestamps[price-identifier] = publish-time` [6](#0-5) . When the victim's transaction subsequently executes with the exact same VAA (same `publish-time`), `is-price-update-more-recent` evaluates `publish-time > publish-time` = false, `write-batch-entry` fails, and this bubbles up to abort the victim's whole `market.clar` call via `ERR-PRICE-FEED-UPDATE-FAILED` [3](#0-2) [4](#0-3) . Meanwhile the price is now fresh on-chain (written by the attacker), so the attacker (or anyone) can immediately call `liquidate` against the still-unhealthy victim position, since `liquidate` itself can call `write-feeds` with `none` and simply reuse the already-updated oracle state [7](#0-6) .

### Impact Explanation
Without the attacker's front-run, the victim's protective transaction (adding collateral / repaying to restore health) would have succeeded, refreshed the price, and taken the position out of the liquidatable zone before anyone else could act. With the attacker's front-run, the victim's transaction reverts (wasting the victim's fee and, more importantly, their window to self-heal), the price is nonetheless updated on-chain (satisfying freshness for `liquidate`), and the position remains liquidatable, allowing the attacker (acting as liquidator) to immediately seize collateral plus the liquidation penalty from the victim. This is a temporary freezing / denial of the victim's ability to act on their own position, directly enabling theft of the liquidation-penalty value from the victim by an unrelated attacker — the same "deny a user from getting out of a bad position" griefing pattern as the referenced `Trader` finding, mapped onto Zest's price-feed submission path rather than an order book.

### Likelihood Explanation
The Pyth VAA bytes required to update a given identifier are fully contained in the calling transaction's arguments and are visible in the mempool, so no special information is needed by the attacker — only mempool monitoring and fee bidding, which is ordinary MEV infrastructure. The attack is cheap (the attacker only pays for a minimal transaction, e.g., zero-amount `collateral-add`, purely to consume the VAA first) and works any time a user needs to submit a stale-price refresh alongside a health-restoring action, which is precisely the scenario the in-band `price-feeds` parameter was designed to support [8](#0-7) .

### Recommendation
Do not let an unrelated third-party transaction's price submission cause another user's core state-changing call to hard-fail. Options: (1) make `write-feeds` tolerant of `ERR_NEWER_PRICE_AVAILABLE`/already-fresh-price errors (treat "price already at least as fresh" as success rather than reverting the whole call), since the caller's real intent is "ensure price is fresh," not "I must be the one to write it"; (2) check current on-chain price freshness before attempting the write and skip the write if the price is already fresh enough; (3) decouple price submission from the position-mutating logic so a losing race on the price update never aborts the user's own borrow/repay/collateral logic.

### Proof of Concept
1. Alice's position is near the liquidation threshold; the on-chain BTC price is stale (older than `max-staleness`).
2. Alice broadcasts `collateral-add(sbtc-ft, amount, feeds=[freshBtcVaa])` intending to add collateral while refreshing the price atomically [9](#0-8) .
3. Mallory sees Alice's pending tx in the mempool, copies `freshBtcVaa`, and submits `collateral-add(sbtc-ft, u1, feeds=[freshBtcVaa])` (or any function accepting `price-feeds`) with a higher fee.
4. Mallory's tx mines first: `write-feed` → `pyth-storage-v4.write` sets `timestamps[BTC] = freshBtcVaa.publish-time` successfully [6](#0-5) .
5. Alice's tx then executes: `write-feed` re-submits the same `freshBtcVaa`; `is-price-update-more-recent` now evaluates `publish-time > publish-time` = `false`, so `write-batch-entry` returns `ERR_NEWER_PRICE_AVAILABLE`, `write-feed` returns `ERR-PRICE-FEED-UPDATE-FAILED`, and Alice's entire `collateral-add` call aborts [3](#0-2) [4](#0-3) .
6. The BTC price is now fresh on-chain (written by Mallory), and Alice's position was never rescued, so Mallory (or anyone) immediately calls `liquidate(alice, ...)` and captures the collateral seizure plus liquidation penalty before Alice can resubmit her rescue transaction [10](#0-9) .

Note: I was not able to fully verify within the available context whether any additional mempool-replay or nonce-based protection exists elsewhere in the deployment tooling that might mitigate this at the wallet/relayer level; this analysis is based solely on the on-chain contract logic reviewed.
