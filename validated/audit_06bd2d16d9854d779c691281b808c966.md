### Title
Crafted swap route can hide an attacker-controlled wallet-token transfer inside a signed strategy authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy operations accept caller-supplied opaque `swap` bytes and invoke the configured router with them, while the account owner’s root authorization remains active for the whole nested invocation tree. A crafted venue reachable through the route can request a token transfer from the caller’s wallet; transaction simulation records that transfer as a child of the strategy authorization, and execution succeeds if the victim signs the poisoned tree. This can steal unrelated wallet tokens even when the strategy itself settles correctly. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_tokens` requires only a positive input amount and non-empty `swap` bytes, obtains the configured router, snapshots the controller balances, and forwards the unchanged caller-supplied bytes to `execute_strategy`; the controller itself performs no venue allowlist check or authorization-tree inspection. [1](#0-0) 

The controller’s own authorization covers only the exact controller-to-router input transfer, but that restriction does not prevent route-selected downstream code from requesting a separate `from = caller` token transfer under the caller’s original authorization root. [3](#0-2) [4](#0-3) 

The post-router accounting checks only controller-held input spend, refunds controller-held leftovers, and requires positive controller output; they do not observe or bound token movements directly out of the caller’s wallet. [5](#0-4) 

The included harness demonstrates the resulting host behavior: a route-selected rogue contract calls `wallet_token.transfer(victim, attacker, WALLET_BALANCE)`, simulation records that call as a child of Alice’s `swap_collateral` authorization, and signing that generated tree transfers the victim’s entire unrelated wallet balance while still crediting the expected strategy output. [2](#0-1) 

### Impact Explanation
An attacker can steal arbitrary unrelated tokens held by a strategy caller, not merely the collateral routed through the swap. [6](#0-5) 

The malicious swap can remain economically valid: the demonstrated route pays the expected output into the lending position while separately transferring the victim’s unlisted wallet token to the attacker. [7](#0-6) 

This affects user-controlled entrypoints that route through `swap_tokens`, including `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and leveraged strategy paths that use the same router settlement helper. [8](#0-7) 

### Likelihood Explanation
Exploitation requires delivering a malicious route and having the victim sign the authorization tree produced by simulation, so it requires user interaction and depends on client behavior. [9](#0-8) 

The barrier is nevertheless low because the payload is opaque `Bytes` at the controller boundary, and a wallet or quote UI that displays only the top-level strategy and nominal route terms can induce the victim to sign a tree containing the extra wallet-token transfer. [10](#0-9) [11](#0-10) 

A direct signer who inspects the full simulated authorization tree can reject the additional child transfer, so this is more appropriately rated Medium than Critical or High. [12](#0-11) 

### Recommendation
- Restrict production routes to a governance-maintained venue/pool allowlist, or otherwise ensure route execution cannot invoke attacker-selected contract code below the caller’s authorization. [3](#0-2) 
- Until venue allowlisting exists, make clients fail closed when the simulated authorization tree for a controller strategy contains any child invocation other than the expected protocol token pulls. [13](#0-12) 
- Surface the complete decoded invocation tree to the signer, including contract address, function, source, destination, and amount, rather than only displaying the top-level strategy arguments. [14](#0-13) 

### Proof of Concept
1. Alice owns a lending account with supplied `USDC` and also holds `WALLET_TOKEN`, an asset that need not be listed by the protocol. [15](#0-14) 
2. The attacker deploys a venue contract whose swap hook calls `WALLET_TOKEN.transfer(alice, attacker, alice_balance)`. [16](#0-15) 
3. Alice is induced to submit `swap_collateral(caller=alice, account_id, token_in=USDC, amount_in, token_out=ETH, swap=crafted_route)`, where the crafted route reaches the malicious venue but still produces a fair `ETH` output. [17](#0-16) 
4. Simulation records the malicious `WALLET_TOKEN.transfer(alice, attacker, balance)` as a sub-invocation of Alice’s `swap_collateral` authorization. [9](#0-8) 
5. Alice signs the generated authorization tree; the host accepts the nested wallet transfer, Alice’s unrelated wallet balance becomes zero, the attacker receives it, and Alice still receives the nominal swap output. [18](#0-17)

    env: &Env,

    token_in: &Address,

    token_out: &Address,

    let router = SwapAggregatorClient::new(env, &router_addr);
    let token_in_client = token::Client::new(env, token_in);

    let in_before = token_in_client.balance(&controller);
    let out_before = token::Client::new(env, token_out).balance(&controller);

    // Authorize only this token transfer to this router for this exact amount.
    authorize_transfer_as_current(env, token_in, &controller, &router_addr, amount_in);

    storage::with_flash_guard(env, || {
        let _ = router.execute_strategy(&controller, &amount_in, swap);
    });

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
