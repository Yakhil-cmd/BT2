### Title
ERC20Transactor blindly trusts the requested `amount` when constructing XCM holding credit/debit, ignoring actual ERC20 balance deltas from fee-on-transfer/deflationary or non-compliant contracts - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` call an arbitrary ERC20 contract's `transfer()` and, on receiving a `true`/success return value, unconditionally credit the XCM `AssetsInHolding` (or treat the deposit as fully successful) using the caller-supplied `amount` — never checking the checking-account's or beneficiary's actual balance before/after the call.

### Finding Description
`ERC20Matcher` (`cumulus/parachains/runtimes/assets/common/src/lib.rs` lines 157-160) is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, and `IsLocalAccountKey20` matches *any* local `AccountKey20` location [1](#0-0) . This means the "asset_id" (an arbitrary H160 contract address) used in `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` is effectively attacker-controlled — any deployed contract can be referenced as an "ERC20 asset" in an XCM `Asset` id, including a contract deployed by the attacker themselves via `pallet-revive`.

In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall` on the arbitrary `asset_id` contract to move `amount` tokens to the checking account, and — as long as the ABI-decoded return value is `true` — immediately mints `AssetsInHolding` credit of exactly `amount` via `Erc20Credit(amount)`, regardless of what the checking account's balance actually changed by: [2](#0-1) 

Symmetrically, `deposit_asset_with_surplus` calls `transfer()` to move `amount` from the checking account to the beneficiary and, on a `true` return, treats the deposit as fully successful without verifying the beneficiary's balance actually increased by `amount`: [3](#0-2) 

This is the exact bug class described in the external report: the transactor assumes `amount transferred == amount requested` from an arbitrary ERC20-like contract instead of measuring before/after balances. A malicious or non-standard ERC20 contract can:
- Implement a fee-on-transfer / deflationary mechanism that burns or redirects part of `amount` while still returning `true`.
- Simply return `true` without moving any tokens at all (fully attacker-controlled bytecode, since it's the attacker's own contract).

Because the executor trusts the declared `amount` unconditionally, on **withdraw** this can create XCM holding credit that is not backed by actual tokens moved to the checking account (the transactor's "Erc20Credit" is a bespoke imbalance type with no runtime-enforced backing — see the comment in the code: "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" [4](#0-3) ). On **deposit**, an attacker contract could under-deliver to a legitimate beneficiary while the executor still reports success and consumes the full `amount` from holding, effectively "burning" the shortfall difference from the sender's XCM program without a corresponding credit anywhere, or — depending on chaining through other reserve-backed asset transactors in a compound XCM program — could allow crediting one leg's escrow/reserve accounting with more than what was truly received on the ERC20 leg.

### Impact Explanation
This breaks the fundamental accounting invariant that XCM asset holding amounts represent real, verified value moved between accounts. Because the checking account is a shared system account used for all such transfers (`TransfersCheckingAccount`), a discrepancy from one malicious ERC20 contract could pollute the checking account's XCM accounting relative to reality, and any multi-hop XCM program that treats the checking-account-mediated transfer as ground truth (e.g., reserve-backed conversions to another local asset kind, or fee accounting) could be manipulated. This maps to Medium severity per the referenced bug class: the vulnerability is not itself unbacked issuance in the native chain's token (Erc20Credit is not convertible into pallet-balances / pallet-assets issuance without further specific configuration), but it is a genuine accounting-integrity gap directly analogous to the reported finding.

### Likelihood Explanation
Reaching this code path requires: (1) the runtime configuring `ERC20Transactor`/`ERC20Matcher` in its `AssetTransactors` tuple, and (2) an attacker deploying (or already controlling) an ERC20-like contract via `pallet-revive` and referencing it by its `AccountKey20` location in an XCM message they execute (e.g., via `pallet-xcm::execute` or a reserve/local transfer instruction). I confirmed `ERC20Transactor` is referenced in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`, indicating it is wired into a real runtime configuration, but I was not able to fully verify within the available tool budget (a) the exact ordering/composition of `AssetTransactors` in that runtime to confirm `ERC20Transactor` is actually reachable for arbitrary user-supplied contracts in production, (b) whether `pallet-revive`/EVM contract deployment is currently enabled on that specific network, and (c) whether any additional filter (beyond `IsLocalAccountKey20`) restricts which H160 addresses can be used. This limits my confidence that the bug is currently exploitable end-to-end on a live deployed chain without further confirmation.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query the ERC20 `balanceOf` for the relevant account (checking account or beneficiary) immediately before and after the `transfer()` call, and use the *actual delta* rather than the requested `amount` when constructing `Erc20Credit` / determining success. If the actual amount transferred is less than requested, either fail the XCM instruction (`FailedToTransactAsset`) or credit only the actually-received amount, consistent with the code-423n4 recommendation of "use the balance before and after the transfer to calculate the received amount instead of assuming it equals the amount passed as a parameter."

/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}
