### Title
Asset display name in `asset_metadata` is fully attacker-controlled with no registry whitelist, enabling name-spoofing/phishing analogous to the Y2K unvalidated insured-token issue - ([File: wallet.js])

### Summary
The Y2K report shows an admin can create a market with an arbitrary token/oracle pair and an arbitrary human-readable `name`, with no validation binding the name to the real underlying asset, letting users be phished into interacting with the wrong asset. ocore has the same class of flaw in its asset metadata / "registry" mechanism: any unprivileged address can author an on-chain `data` message that assigns a human-readable `name` to *any* asset ID, and the wallet code in `fetchAssetMetadata` accepts and caches that name as long as the message's declared `registry_address` equals the unit's own author — there is no check that `registry_address` is a trusted/known registry for that asset.

### Finding Description
`fetchAssetMetadata()` in `wallet.js` resolves the human-readable name/decimals shown for a given `asset` (an asset unit hash) as follows: [1](#0-0) 
It requests `{metadata_unit, registry_address, suffix}` for the asset, validates only the *format* of `metadata_unit` and `registry_address` (valid hash / valid address), then reads the referenced unit and checks that the unit's author matches the declared `registry_address`: [2](#0-1) 
It then takes `payload.name` straight from that `data` message and stores it as the display name for the asset: [3](#0-2) 

Crucially, `registry_address` is never checked against any whitelist of trusted/expected registries for the asset in question — it is simply whatever value accompanies the query response, and the only "authentication" performed is that the unit self-consistently claims to be authored by that same address. Because a `data` message (`app: 'data'`) is not consensus-validated for semantic content (it is free-form user data), **any address** can author a unit containing `{app:'data', payload:{asset: <victim_asset_unit>, name: 'USDC', decimals: 6}}`, declare itself as `registry_address`, and have this accepted as legitimate metadata for someone else's asset. The `asset_metadata` table only enforces `UNIQUE(name, registry_address)` — not any relationship between `asset` and a canonical issuer/registry: [4](#0-3) 

This is structurally identical to the Y2K bug: the protocol lets an unprivileged party attach an arbitrary display name to an arbitrary asset, and clients render that name to users without validating that the "registry" is a trusted authority for that specific asset — "Names should be derived from IERC20.name()" in the Y2K recommendation maps directly onto "names should be derived from data intrinsic to the asset definition (`storage.readAssetInfo`), not from an unauthenticated self-declared registry."

### Impact Explanation
Any user with basic ocore wallet functionality could publish a spoofed `data` message that causes wallets querying asset metadata to display a well-known name/ticker (e.g. "USDC", "GBYTE") for an unrelated, attacker-issued asset. This enables classic phishing: a victim sees a familiar asset name in their wallet UI/balance list and sends real payments believing they are interacting with the legitimate asset, when in fact they are dealing with a namesake token controlled by the attacker. Because the acceptance criterion in `fetchAssetMetadata` only checks internal self-consistency of the returned tuple (author == claimed registry_address) and not whether that registry is authoritative for the asset, the check provides no real security guarantee — it only prevents outright forgery of the *unit content*, not forgery of *meaning*. This matches "Phishing / Loss of Funds" impact class from the reference report.

### Likelihood Explanation
Likelihood is high for the specific vector of a wallet operator/hub-relayed lookup, since posting a `data` unit with an `asset` and `name` field requires no special privilege — it's a standard, unauthenticated message type reachable by any address holder. The only missing piece fully confirmed in this codebase is the exact hub-side query logic that maps `asset -> {metadata_unit, registry_address}` (which lives outside `ocore` proper, likely in a hub server component not present in this repo), so I cannot fully verify whether the hub imposes any additional first-come-first-served or registry pinning that reduces exploitability. This is a genuine unknown given the indexed files available.

### Recommendation
- Do not treat `registry_address` returned from an external metadata lookup as trustworthy; require it to belong to a maintained on-chain/off-chain whitelist of recognized registries (e.g. hard-coded canonical registry addresses) before caching or displaying `name`.
- Bind the asset's canonical name, if any, to data that is provable from the asset's own definition/issuer address (`objAsset.definer_address`) rather than from an arbitrary third-party `data` message.
- When a name for a given `asset` is supplied by a registry that is not on the trusted whitelist, the UI should clearly flag it as "unverified" rather than rendering it identically to trusted names.
- Add a uniqueness/precedence rule keyed by `asset` (not just `(name, registry_address)`) so that once a trusted registry names an asset, unrelated addresses cannot silently register conflicting/spoofed names for the same asset.

### Proof of Concept
1. Attacker issues a new asset unit `X` via a standard `asset` message (no special condition), becoming `objAsset.definer_address = attacker_address`.
2. Attacker authors a `data` unit `M` with payload `{asset: X, name: "USDC", decimals: 6}`, using `attacker_address` as author.
3. Attacker (or a hub they control/report to) answers a `get_asset_metadata` request for asset `X` with `{metadata_unit: M, registry_address: attacker_address, suffix: null}`.
4. `fetchAssetMetadata` in `wallet.js` validates format of `metadata_unit`/`registry_address`, reads unit `M`, confirms `objJoint.unit.authors[0].address === registry_address` (true, since attacker authored it), and extracts `payload.name = "USDC"`. [5](#0-4) 
5. The wallet's `asset_metadata` table now shows asset `X` labeled "USDC" to any victim, even though it has no relation to the real USDC asset — victims can be induced to send funds to/interact with `X` believing it is the legitimate stablecoin.
