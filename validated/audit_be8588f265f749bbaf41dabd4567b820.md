### Title
Delimiter injection in `arbiter_contract.getHashSrc()` allows forging a contract-text commitment hash for a different set of terms - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` builds the arbiter-contract "commitment hash" by concatenating attacker-influenceable fields with a fixed separator and hashing the result, without ever validating that the separator string cannot itself appear inside any of the joined field values. This is the same root-cause pattern as the GitPython advisory: values are embedded into a structurally-significant, delimiter-based serialization without escaping/rejecting the delimiter, so an attacker-controlled value can inject a fake delimiter and make two semantically different structured inputs collapse to the same serialized string (and thus the same hash).

### Finding Description
`getHashSrc()` computes the pre-image that is hashed to produce `contract.hash`, the value that is later posted on-chain (in the `data` message `contract_text_hash`) as an anti-repudiation commitment to the agreed contract terms: [1](#0-0) 

```
const src = contract.creation_date > exports.NEW_HASH_DATE
     ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
     : ... .join("")
```

with [2](#0-1) 

`exports.DELIMITER = "[|#|]"`.

`contract.title`, `contract.text`, and the party-name fields (`my_party_name`/`peer_party_name`) are free-form strings supplied by an unprivileged wallet counterparty when creating or accepting a contract via `createAndSend()`: [3](#0-2) 

Nothing in `createAndSend`, `store`, or `getHashSrc` rejects or escapes an occurrence of the literal delimiter string `"[|#|]"` inside `title`, `text`, or the party-name fields. Because the join is purely positional and unescaped, an attacker who controls one or more of these free-text fields can inject additional copies of the delimiter to shift field boundaries, allowing the concatenation of a maliciously-crafted `{title, text, party_name, ...}` tuple to be made byte-identical to the concatenation of a different, genuinely-agreed tuple (e.g. different amount, asset, or party name) — producing an identical `sha256` "commitment" hash for two different sets of terms. This mirrors exactly the GitPython bug class: a supposedly-safe separator is trusted to never appear in the joined values, but no validation enforces that, so the separator can be forged by the attacker to change how the concatenated blob is later interpreted.

The resulting `contract.hash` is used as a durable commitment: it is posted on-chain via `createSharedAddressAndPostUnit()`'s `data` message (`contract_text_hash`) and is checked against the mutually-signed unit in `handleReceivedSigningUnit()`: [4](#0-3) 

It is also transmitted to the arbstore/arbiter as the basis for adjudicating disputes in `openDispute()`, where the raw fields (title, text, party names, amounts) are sent encrypted to the arbiter alongside the on-chain-anchored `contract_hash` so the arbiter can verify the plaintext it receives matches the committed hash: [5](#0-4) 

Because `getHashSrc()` can be made to produce identical hashes for different plaintext content, this anti-repudiation guarantee is broken.

### Impact Explanation
The contract hash is the sole cryptographic binding between what a wallet user believes they agreed to and what is verifiable on-chain / by the arbiter. If a counterparty can construct a contract whose fields (amount, party name, terms text) differ from what was actually negotiated but still hash to the value that was signed/posted on-chain, that counterparty can later present a different (self-favoring) version of the contract to the arbiter during dispute resolution, or repudiate/substitute agreed terms, while the on-chain "proof" appears to match. Since the arbiter's ruling ultimately triggers release of escrowed funds from the shared multisig address (via `parseWinnerFromUnit`/`complete`), a successful forgery can lead to funds being released to the wrong party under a fabricated set of contract terms — i.e., unauthorized redirection of escrowed value between the private-payment counterparties. This satisfies the "concrete unauthorized spending" / fund-loss bar because the arbiter contract feature exists specifically to gate fund release on agreed contract text, and the hash-collision defeats that gate.

### Likelihood Explanation
The attack is reachable by any unprivileged private-payment counterparty in a normal arbiter-contract negotiation flow (`createAndSend`/`store`/`respond`), requiring only that they control the `title`/`text`/party-name fields of the contract they propose or accept — no special privileges, no network position, and no cryptographic hash break is needed, only careful placement of the fixed delimiter string. The delimiter `"[|#|]"` is a short, guessable ASCII sequence with no length/charset restriction preventing its use in `title`/`text`. This is a deliberate, crafted-input attack rather than a random collision, making it practical for a motivated party in a dispute.

### Recommendation
Reject (do not silently strip) any field value passed to `getHashSrc()` that contains the delimiter substring `exports.DELIMITER`, in the same way `string_utils.getSourceString()` already rejects the `STRING_JOIN_CHAR` (`\x00`) in its own field-serialization routine (see `string_utils.js:14-19`), and in the same way `validation.js`/`aa_validation.js` reject `\n` in data-feed names/values. Alternatively, use a length-prefixed or otherwise unambiguous encoding (e.g., `JSON.stringify` an ordered array, or prefix each field with its byte length) so that no combination of field values can be re-partitioned into a different tuple.

### Proof of Concept
Conceptually (cannot be executed without the full wallet/device stack, but the code path is deterministic):
1. Attacker Bob proposes a contract to Alice with `title = "T" + DELIMITER + "9999999"`, `text = "legit text"`, `amount = 100`, and other fields chosen such that the full joined string equals the joined string of an entirely different, legitimate contract C2 that specifies `amount = 9999999` and a shorter title `"T"`.
2. Because `getHashSrc()` performs a plain `join(DELIMITER)` with no escaping, `getHashSrc(C1) === getHashSrc(C2)` is achievable by choosing `title`/`text` such that the injected delimiter plus trailing content exactly reproduces the byte sequence of a different, higher-value contract.
3. `getHash(C1) === getHash(C2)`, so the `contract_text_hash` posted on-chain for the low-value/legit-looking contract C1 is identical to the hash that would also validate contract C2's terms.
4. During a later dispute, Bob supplies the arbiter with C2's terms (larger amount favoring himself); the arbiter/arbstore, verifying only that `sha256(getHashSrc(submittedTerms)) == contract_text_hash_on_chain`, accepts C2 as the "true" agreed contract, and funds are released according to the forged terms.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
