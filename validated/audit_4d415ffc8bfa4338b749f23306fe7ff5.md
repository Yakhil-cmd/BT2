### Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the secret configured for the organization named in the payload's `repository.owner.login` (or `organization.login`) field. [1](#0-0)  That binding — "the organization whose secret signed this payload" — is expected to equal "the repository/stack that gets written to" for every event type. Every other handler in the codebase enforces this by scoping lookups through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching any record, exactly as implemented in the base `Handler` class. [2](#0-1)  `StatusHandler`, however, breaks this invariant: it resolves the target purely from the attacker-suppliable `sha` field, with no repository/stack scoping at all. [3](#0-2) 

### Finding Description
`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

This queries the global `Commit` table by `sha` alone — it never checks `params.repository.full_name` (unlike `PushHandler`, which scopes via `stacks` derived from `Repository.from_github_repo_name`). [4](#0-3)  `Commit` rows across *all* tenants/stacks tracked by this Shipit instance are candidates, so any `Commit` row anywhere in the database whose `sha` matches the value in the forged payload will get a new `Status` written to it, regardless of which organization's `Repository`/`Stack` that commit actually belongs to.

The equality that is broken is:
- **Side verified by signature**: `repository_owner` (org key used to fetch `Shipit.github(organization: repository_owner).verify_webhook_signature`) — [1](#0-0) [5](#0-4) 
- **Side actually written**: whatever `Stack`/`Repository` owns the `Commit` row matched by `sha` in `Commit.where(sha: params.sha)`, with **no relation asserted to `repository_owner`**.

Since git commit SHAs are content-addressed and identical across forks/mirrors that share history, and Shipit tracks arbitrary GitHub repositories as `Stack`s, an org that legitimately controls its own GitHub App installation (and can therefore get GitHub to send it genuinely-signed `status` webhooks, e.g. by pushing to its own fork and setting a status via the GitHub Statuses API) can cause a `status` event to be delivered whose `sha` matches a commit that is also tracked by a *different* organization's `Stack` in the same Shipit instance (a very common situation for forks/mirrors of the same upstream history). The forged/received event is fully valid per `verify_signature` (correctly signed by the attacker's own org secret) yet `StatusHandler` applies the status write to the unrelated organization's `Commit`/`Stack`.

### Impact Explanation
A forged or replayed commit status can flip `commit.deployable?`/CI gating on another organization's `Stack`, since `Status` records feed into `required_statuses`/CI checks that authorize deploys and the merge queue (`Shipit::MergeRequest`, `DeploySpec#required_statuses`). [6](#0-5)  Writing a fabricated "success" status onto a commit belonging to a stack the attacker does not control can unlock an unauthorized deploy or merge for that stack — this is a cross-repository write with a direct path to an unauthorized deploy, matching the Critical-impact criteria for this analog class.

### Likelihood Explanation
Requires the attacker to already control at least one GitHub App-integrated organization/repo on the shared Shipit instance (a plausible, unprivileged-relative-to-other-tenants position in any multi-tenant Shipit deployment) and a commit SHA that is shared with the target repository (trivially satisfied for forks/mirrors of the same upstream project, which is a routine occurrence — no SHA1 collision attack needed). No `ApiClient` token, session, or secret theft is required; the exploit relies solely on the engine's own missing repository-scoping check in `StatusHandler`, distinguishing it from every sibling handler that does scope correctly.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `PushHandler`/`Handler#stacks`: resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, restrict the `Commit` lookup to that repository's stacks (e.g. `stacks.commits.where(sha: params.sha)`), and require the `repository` field in the handler's `params` block so it cannot be omitted.

### Proof of Concept
1. Attacker onboards/controls `org-attacker` on the shared Shipit instance (GitHub App installed, `webhook_secret` configured for `org-attacker`).
2. Attacker forks/mirrors the victim's public repository into `org-attacker/victim-repo`, inheriting shared commit history/SHAs with the victim's tracked `Stack` (`org-victim/victim-repo`).
3. Attacker calls GitHub's Statuses API on their own fork: `POST /repos/org-attacker/victim-repo/statuses/{shared_sha}` with `state=success`.
4. GitHub sends a `status` webhook to Shipit, correctly signed with `org-attacker`'s `webhook_secret`; `repository.owner.login == "org-attacker"`, so `verify_signature` passes. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: shared_sha)`, which returns the `Commit` row belonging to `org-victim/victim-repo`'s `Stack` (because the SHA is shared), and writes a `success` status onto it. [3](#0-2) 
6. The victim's `Stack` now has a forged passing CI status on that commit, potentially satisfying `required_statuses`/`ci.require` and enabling an unauthorized deploy or merge-queue action for `org-victim`.
