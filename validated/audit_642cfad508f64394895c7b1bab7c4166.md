### Title
API-scoped ApiClient token can read the CCMenu state of any stack, not just the one it was authorized for - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` records can be scoped to a single `stack_id`, and `Api::BaseController` enforces that scoping for every normal API endpoint by resolving the target stack through the `stacks` method, which restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` when a scope is set. [1](#0-0)  `Api::CCMenuController`, however, overrides `stack` to look the stack up directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the `stacks` scoping helper, while still only checking the coarse `read:stack` permission that says nothing about *which* stack. [2](#0-1) 

### Finding Description
The equality that should hold for every API request is:

`stack the ApiClient token is authorized for == stack the request actually touches`

`Api::BaseController#stack` enforces this by scoping through `stacks`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`Api::CCMenuController` redefines `stack` and drops the scoping:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [3](#0-2) 

The controller's only authorization check is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`:
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [4](#0-3)  This method validates only that the client holds the generic `read:stack` permission string - it has no notion of the client's `stack_id` restriction. That restriction is enforced solely by the `stacks` scoping helper in `BaseController`, which `CCMenuController` sidesteps. [5](#0-4) 

Before the attack: an `ApiClient` created scoped to stack A (`stack_id: A`, `permissions: ['read:stack']`) can only see stack A through `StacksController#index`/`#show`, as validated by the existing test "an api client scoped to a stack will only see that one stack". [6](#0-5) 

After the attack: the same token, presented to `GET /stacks/:stack_id/ccmenu.xml` with `stack_id` set to stack B (any other stack in the installation), passes `authenticate_api_client` (token is valid) and `require_permission :read, :stack` (client does have `read:stack`), and `stack` resolves unscoped to stack B via `Stack.from_param!`. The controller then renders stack B's build/CCMenu status. [7](#0-6) 

This breaks exactly the analog class called out in the rules: "a stack a token authorises versus a stack it touches."

### Impact Explanation
An attacker holding a legitimately-issued, narrowly-scoped `ApiClient` token (e.g., a third-party integration token meant to see status for one stack only) can read the CCMenu status - build success/failure, last build label, last build time, web URL - of every stack managed by the Shipit instance, including stacks the token owner has no relationship to. This is an authorization-scope escalation that lets a limited-privilege credential read cross-stack deployment state, matching the "unauthorized read of stack state" class of impact.

### Likelihood Explanation
Any holder of a scoped `read:stack` `ApiClient` token (these are routinely distributed to CI dashboards, status boards, chat integrations, etc., and are explicitly designed by the product to be stack-scoped) can trigger this by simply changing the `stack_id` in the URL/query parameters of a `GET .../ccmenu.xml?token=...` request - no privilege escalation, session, or additional secret is required beyond the token they already legitimately hold for a different stack.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack.from_param!` directly, so that clients scoped to a specific `stack_id` cannot resolve any other stack.

### Proof of Concept
1. Create an `ApiClient` scoped to stack A: `ApiClient.create!(creator: user, name: 'ccmenu-bot', stack: stack_a, permissions: ['read:stack'])`.
2. Obtain its `authentication_token`.
3. Request `GET /stacks/:owner/:repo_b/:branch_b/ccmenu.xml?token=<token>` where `repo_b`/`branch_b` belong to stack B (a stack this token was never granted access to).
4. Observe HTTP 200 with stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.), even though the token's `stacks` scope in every other API controller would resolve to stack A only, as demonstrated by the passing test in `test/controllers/api/stacks_controller_test.rb:217-223` that confirms scoping works for `StacksController#index`. [6](#0-5)
