**Analysis:**

`SessionId::Txn` only encodes `sender`, `sequence_number`, and `script_hash`; it never includes the authenticator or `authentication_proof` at all [1](#0-0) . This is true regardless of whether two candidate authenticators are structurally different — the field simply isn't part of the hash input. However, this is not a security invariant that the codebase relies on:

1. **SessionId is not an authentication mechanism.** It is only used internally by the Move VM to construct deterministic per-execution scratch context (e.g., table handle derivation, monotonic counters within a transaction execution) [2](#0-1) . Actual sender/signer authentication is performed separately in `validate_signed_transaction`, which checks each signer's `authentication_proof` (derived from the real public key and signature scheme) against the on-chain auth key, and validates keyless/abstract authenticators independently of `SessionId` [3](#0-2) .

2. **`AuthenticationProof::Key` is derived from the real public key and scheme**, not raw signature bytes, via `AuthenticationKey::from_preimage(public_key_bytes, scheme)` [4](#0-3) . Two structurally different, validly-signed authenticators for the same sender/sequence would need to resolve to the exact same 32-byte authentication key already registered on-chain — this is not something an attacker can produce without a preimage/hash collision or already controlling a matching key, which is outside the "unprivileged sender" threat model.

3. **No admission or dedup logic is keyed by `SessionId`.** The actual dedup/admission boundaries — consensus's `TxnHashAndAuthenticatorDeduper` and mempool's `TransactionStore::insert` — key off `(sender, replay_protector)` and `committed_hash()`/full authenticator, not `SessionId` [5](#0-4) [6](#0-5) . These explicitly account for the case of same-payload-different-signature by hashing/comparing the full signed transaction, not any session-scoped identifier.

4. **Replay protection via sequence number** means at most one transaction can ever commit for a given `(sender, sequence_number)` pair; once consumed, that `SessionId::Txn` value can never be reused for another execution, so there's no scenario where two differently-authenticated transactions with identical `SessionId` both get admitted/executed under that same session.

Since `SessionId` is not a security boundary for authenticator binding, and no dedup/cache logic anywhere treats it as such, the described "corruption" has no exploitable path through admission (mempool/vm-validator/VM validation already converge correctly via signature checks unrelated to `SessionId`).
