### Title
Cross-organization webhook forgery via organization/repository binding mismatch in signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) read from the *unauthenticated* JSON payload, but the handlers that actually act on the payload resolve the target `Stack`/`Repository` from a different field, `repository.full_name`. Because Shipit supports multiple GitHub organizations each configured with its own `webhook_secret`, a holder of one organization's webhook secret can forge a payload whose `owner.login` names that organization (so its secret verifies the signature) while `repository.full_name` names a repository belonging to a *different* organization, causing Shipit to act on that other organization's stack.

### Finding Description
`verify_signature` computes the verifying app as: [1](#0-0) 
using `repository_owner`, defined as: [2](#0-1) 

This determines the `Shipit::GitHubApp` (and hence the `webhook_secret`) used to `verify_webhook_signature`: [3](#0-2) 

Handlers, however, never re-check `repository.owner.login`; they resolve the target stacks purely from `repository.full_name`: [4](#0-3) 

Shipit explicitly supports configuring a distinct GitHub App (and distinct `webhook_secret`) per organization, as documented: [5](#0-4) 

Because the HMAC signature is computed over the *entire* raw JSON body, an attacker does not need to modify a signed payload after the fact — they only need to know (or legitimately hold, as an administrator of one of the smaller/less-trusted organizations onboarded to the same Shipit instance) the `webhook_secret` for organization "A". With that secret they can locally construct and sign any payload of their choosing, including one where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` looks up and validates against OrgA's `webhook_secret`, which the attacker used to sign it — verification succeeds), and
- `repository.full_name` = `"OrgB/some-repo"` (so `Handler#repository_name` / `#stacks` resolves to a `Stack` that belongs to organization B, unrelated to the secret that was actually used to authenticate the request).

This breaks the trust binding **organization that authenticated the webhook == organization/repository the webhook payload is allowed to act on**. The equality the code implicitly (and incorrectly) assumes is:
`organization_whose_secret_verified_signature == organization_owning_repository.full_name_acted_upon`
but nothing enforces that `payload.dig('repository','owner','login')` matches `payload.dig('repository','full_name')`'s owner segment, nor that the acted-upon repository actually belongs to the organization whose secret validated the request.

### Impact Explanation
This is a cross-repository / cross-organization write: possession of a single organization's `webhook_secret` (a credential scoped, by Shipit's own multi-org design, to that organization only) allows forging webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) that are processed as if they originated from GitHub for a *stack belonging to a different organization*. Depending on which handler is targeted this can trigger `GithubSyncJob`s, fabricate commit `Status`/`CheckRun` records that gate deploy eligibility, or manipulate `Team`/`Membership` records — i.e., an unauthorized cross-repository write / manipulation of deploy-gating state for a repository the attacker's credential was never meant to cover. This matches the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Exploitability requires only knowledge of one organization's `webhook_secret` configured on the shared Shipit instance — a credential intentionally scoped per-organization per the documented multi-org setup, and plausibly available to any admin/operator of that one organization's GitHub App, without any Shipit login, `ApiClient` token, or GitHub App private key for the *other* organization. The root cause is a simple, deterministic binding mismatch (verification keyed off `repository.owner.login`, action keyed off `repository.full_name`) rather than a race condition, so likelihood is High whenever more than one organization's secret is configured on the same Shipit deployment (the documented, supported "Using Multiple GitHub Applications" mode).

### Recommendation
After signature verification, re-derive the organization from `repository.full_name` (or `organization.login`) and assert it matches the organization (`repository_owner`) whose secret verified the signature, rejecting the request (422) on mismatch. Alternatively, verify the signature against the secret of the organization actually owning `repository.full_name`, rather than trusting `repository.owner.login`/`organization.login` as the sole selector.

### Proof of Concept
1. Shipit is configured for two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. Attacker has legitimate access to `OrgA`'s `webhook_secret` (e.g., as an admin of `OrgA`'s GitHub App installation) but has no relationship to `OrgB`.
3. Attacker crafts a JSON body for a `push` event:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>"
   }
   ```
4. Attacker signs the raw body with `OrgA`'s `webhook_secret` (HMAC-SHA1) and sets the `X-Hub-Signature` header accordingly, and `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'OrgA')` (from `repository.owner.login`) and the signature validates successfully against `OrgA`'s secret.
6. `Shipit::Webhooks::Handlers::PushHandler` (via `Handler#stacks`/`#repository_name`) resolves the target stack from `repository.full_name` = `"OrgB/target-repo"`, and processes the push event (enqueuing `GithubSyncJob`, updating commit/branch state) for `OrgB`'s repository — despite the request never being authenticated with any credential belonging to `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
