### Title
Cross-org webhook signature scope confusion lets a forged `pull_request` `closed` event archive another organization's `ReviewStack` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the signing secret using `repository_owner`, a field read directly from the attacker-controlled JSON body, while `ClosedHandler` (and its `ReviewStackAdapter`) resolves and mutates the target `Repository`/`ReviewStack` using a *different* attacker-controlled field, `repository.full_name`. Nothing ties these two fields together, so in any multi-org Shipit deployment where at least one configured GitHub org has no `webhook_secret`, an attacker can pass signature verification "as" that unprotected org while pointing the payload's `repository.full_name` at a completely different, properly-secured victim org/repo, causing `ClosedHandler` to archive and deprovision that victim's `ReviewStack`.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:

`repository_owner` (used by `verify_signature` to select the signing config) `==` owner segment of `params.repository.full_name` (used by `ClosedHandler`/`ReviewStackAdapter` to select the record to mutate)

In a legitimate GitHub-delivered webhook these two are always the same, because GitHub populates both from the same real repository object. But both fields are simply attacker-supplied JSON in a forged request, and the code path never cross-checks them:

- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that org's `webhook_secret` is blank: `return true unless webhook_secret`. [3](#0-2) 
- In multi-org mode, `Shipit.github(organization:)` looks up a wholly independent config per org key (`github_app_config`), so different orgs can legitimately have different (or absent) `webhook_secret`s — this is documented, supported configuration. [4](#0-3) 
- Once signature verification passes (using whatever org name the attacker put in `repository.owner.login`), `Shipit::Webhooks.for_event('pull_request')` runs `ClosedHandler#process`, which resolves the actual target repository from a *separate* field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name`, and then archives the `ReviewStack` found under that repository's `review_stacks` scope for the given PR `number`/`environment`. [5](#0-4) [6](#0-5) [7](#0-6) 

**Exploit flow:** Attacker crafts a `pull_request` webhook body with `X-Github-Event: pull_request`, `action: "closed"`, `repository.owner.login` set to an org configured in Shipit with no `webhook_secret` (satisfies `verify_signature` via the blank-secret bypass), but `repository.full_name` set to `"victim-org/victim-repo"` — an org/repo that *does* have a webhook secret the attacker does not know — and `number` set to the PR number corresponding to an existing `ReviewStack`'s `environment` (`"pr<number>"`) on that victim stack. The forged, unauthenticated-for-that-repo request causes `ClosedHandler` to call `review_stack.archive!`, which calls `stack.remove_from_provisioning_queue`, `stack.deprovision`, and `stack.archive!(user)` on the victim's `ReviewStack`. [6](#0-5) 

Existing guards do not catch this: `verify_signature` only checks that *some* configured org's secret (or lack thereof) validates the HMAC against the raw body — it never confirms that the org used for verification is the same org whose data the handler subsequently mutates. `drop_unhandled_event` and the `ExplicitParameters` schema in `ClosedHandler` only validate presence/types of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name`. [8](#0-7) 

### Impact Explanation
The attacker, with no session, no API token, and no knowledge of the victim org's `webhook_secret`, causes a real state mutation (archive + deprovision) on a `ReviewStack` belonging to a repository/org they did not authenticate against. Because the victim stack has `blocking_statuses` configured (forced statuses gate `blocked?`/deploys), archiving and deprovisioning that stack removes the review environment and its associated gating/blocking state entirely, amplifying the impact beyond a simple record deletion into disruption of the victim's deploy-gating workflow. This matches "a payload for one repository mutating another's stack" — Critical, cross-tenant state manipulation. It is repeatable against any tracked repository/PR combination as long as at least one org in the Shipit instance's multi-org config lacks a `webhook_secret`.

### Likelihood Explanation
Requires: (1) the Shipit instance uses the multi-org GitHub App configuration schema (documented and supported, see `docs/setup.md` "Using Multiple Github Applications"), and (2) at least one configured org in that schema has no `webhook_secret` set — an operator misconfiguration but one the codebase explicitly permits and even ships examples of (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml` both show `webhook_secret: # nil` for multiple orgs). Given those preconditions, the attack costs a single unauthenticated HTTP POST with a hand-crafted JSON body and correct `X-Github-Event` header — no secrets, sessions, or GitHub credentials required, and it is fully repeatable against any known PR number/environment on any tracked stack.

Note: in the single-org (legacy) configuration — which is what most of this repo's own test fixtures use (`test/dummy/config/secrets.yml`) — `Shipit.github_default_organization` returns `nil` and `Shipit.github(organization:)` always resolves to the one single config regardless of the `organization:` argument, so the cross-org bypass described here does **not** apply to single-org deployments; it is specific to multi-org configurations with an unprotected org entry.

### Recommendation
In `WebhooksController#verify_signature`, after successfully verifying the signature for `repository_owner`, require that any handler-visible `repository.full_name` owner segment matches `repository_owner` before dispatching to handlers (reject with 422 on mismatch). Additionally, treat a blank `webhook_secret` for a configured org as a hard misconfiguration warning at boot/health-check time rather than silently returning `true`, since it effectively disables authentication for any payload claiming that org.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` or similar):
1. Configure `Shipit.stubs(:secrets)` (or dummy config) with a multi-org schema: `OrgWithoutSecret` (webhook_secret: nil) and `VictimOrg` (webhook_secret: "victim-secret").
2. Create a `Shipit::Repository` for `VictimOrg/victim-repo` and a `Shipit::ReviewStack` under it with `environment: "pr42"`, then set `stack.deploy_spec`/`blocking_statuses` and confirm `stack.not_archived?` is true before the request: `assert_not stack.archived?`.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no valid `X-Hub-Signature` for `VictimOrg`, and a JSON body where `repository.owner.login = "OrgWithoutSecret"`, `repository.full_name = "VictimOrg/victim-repo"`, `action = "closed"`, `number = 42`.
4. Assert `response.status == 200` (bypassed verification) and `assert stack.reload.archived?` — proving the forged, unauthenticated-for-`VictimOrg` request archived `VictimOrg`'s stack.
5. Negative control: repeat with `repository.owner.login = "VictimOrg"` (correct owner, no forged signature) and assert `response.status == 422` and `assert_not stack.reload.archived?`, demonstrating the divergence is caused specifically by the owner/full_name decoupling.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
