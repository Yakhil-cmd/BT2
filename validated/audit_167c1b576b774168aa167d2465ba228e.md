### Title
Webhook `repository.full_name` is trusted for stack lookup without binding to the verified sending org, letting a secret-less org's push webhook trigger `GithubSyncJob` and create `Commit` rows for a victim's stack - ([File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`Webhooks::Handlers::Handler#stacks` resolves the target `Stack`/`Repository` purely from the attacker-supplied `payload.dig('repository', 'full_name')`, with no check that this value corresponds to the org whose signature (or lack thereof) was accepted for the request. `PushHandler#process` then calls `stack.sync_github`, which enqueues `GithubSyncJob`, and `append_commit` persists real `Commit` rows fetched from GitHub for the victim's actual branch - all triggered on demand by an attacker who has no relationship to the victim repository.

### Finding Description
The claimed binding is: `org that authenticated this webhook == org that owns the repository/stack being mutated`.

Trace:
- `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) computes `repository_name = payload.dig('repository', 'full_name')` and does `Repository.from_github_repo_name(repository_name)&.stacks`. This value is entirely attacker-controlled JSON in the POST body; nothing ties it to which org's secret (or absence thereof) validated the request. [1](#0-0) 
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) uses that same untrusted `stacks` scope, filters by `branch` (also attacker-supplied `params.ref`), and calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack - including stacks belonging to organizations the attacker does not control. [2](#0-1) 
- This enqueues `GithubSyncJob`, which loads the real `Stack` (`Stack.find(params[:stack_id])`) and calls `fetch_missing_commits { stack.github_commits }`, using `stack.github_api` (the app's own credentials for the victim's real repository) to pull the actual commit history via `FirstParentCommitsIterator`. [3](#0-2) 
- Any newly-discovered commits are persisted via `append_commit` → `stack.commits.create_from_github!(gh_commit)` inside a transaction. [4](#0-3) 

Given the stated precondition (a secret-less org lets an attacker's webhook be accepted as "verified" per the referenced scenario 1), the attacker can pick any `repository.full_name`/`ref` pair that matches a victim's tracked stack and branch, and force a same-moment resync. Because the ingested commit content is fetched from GitHub's real API for the real repository (not taken from the attacker's payload), the data itself is legitimate - but the write only happens because the attacker's unrelated, unauthenticated-for-that-repo webhook was accepted as the trigger. No code in `Handler`, `PushHandler`, or `GithubSyncJob` re-validates that the org which "verified" the webhook is actually authorized for `repository_name`; that binding is assumed but never enforced in this call path.

### Impact Explanation
The attacker can force `Commit` records to be created on a victim's stack timeline at a time of their choosing, independent of GitHub's real delivery cadence, for any repository/branch they can name - as long as the branch already has a legitimate advancing commit upstream. This is a cross-tenant trigger: a payload nominally about the attacker's own (secret-less) repository causes writes on a completely different repository's stack, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The commit content itself is accurate (sourced from the real GitHub API), so this does not forge malicious commit data, but it does demonstrate that stack mutation is not bound to the org that was actually authenticated, which is the same trust-boundary gap as scenario 1's signature bypass, now shown concretely against `Commit` creation instead of just event acceptance.

### Likelihood Explanation
This finding is entirely dependent on the scenario 1 precondition holding: that a secret-less org's webhook is accepted as "verified" by the engine's signature-checking logic despite `payload.dig('repository', 'full_name')` referring to an unrelated victim org. I was not able to re-verify that gating logic (`verify_signature` / `GitHubApp#verify_webhook_signature` / per-org secret lookup) within this investigation due to iteration limits, so I cannot independently confirm the precondition is true from this pass alone. Given that precondition, exploitation is cheap and repeatable (one POST per resync trigger) against any victim stack whose branch is public knowledge.

### Recommendation
Bind the resolved `Repository`/`Stack` to the org/installation that was cryptographically verified for the request, not solely to attacker-controlled `payload['repository']['full_name']`. Concretely, `Handler#stacks` (or the controller dispatching to handlers) should cross-check that the verified webhook's associated installation/org actually owns the repository named in the payload before resolving stacks, and reject the event otherwise.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers_test.rb` conceptually - not asserting existing test content):
1. Create `victim_org/victim_repo` with a `Stack` tracking `branch: "main"`, and stub `stack.github_api` so `FirstParentCommitsIterator` yields one legitimate commit with a real SHA/author unrelated to the attacker.
2. Construct a push payload with `repository.full_name = "victim_org/victim_repo"`, `ref = "refs/heads/main"`, `after = <that sha>`, but sent/attributed to a secret-less attacker org (per scenario 1's verification bypass).
3. Assert before: `Shipit::Commit.exists?(stack: victim_stack, sha: sha)` is `false`.
4. Invoke `Shipit::Webhooks::Handlers::PushHandler.call(payload)` then perform the enqueued `GithubSyncJob`.
5. Assert after: `Shipit::Commit.exists?(stack: victim_stack, sha: sha)` is `true`, proving `Commit.create_from_github!` was invoked for `victim_stack` solely from the attacker org's payload, with no authentication tying the attacker to `victim_org`.
