### Title
`status` webhook handler applies GitHub commit statuses without scoping to the signature-verified organization's repositories - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `WebhooksController` verifies the HMAC signature of an incoming webhook against the GitHub App configuration for the organization named in `params.dig('repository','owner','login')` (falling back to `organization.login`). But `Shipit::Webhooks::Handlers::StatusHandler#process` never uses that organization/repository binding at all: it looks up commits globally by `sha` across the *entire* installation (`Commit.where(sha: params.sha)`), and writes a GitHub commit status onto every matching commit, regardless of which stack/repository it belongs to.

### Finding Description
`WebhooksController#verify_signature` binds trust to one specific field of the payload — the repository/organization owner login — and asks `Shipit.github(organization: repository_owner)` for that organization's `webhook_secret` to validate the raw body HMAC: [1](#0-0) [2](#0-1) 

Every other handler that mutates a `Stack`'s data scopes its writes to the repository named in `payload.dig('repository','full_name')` via `Handler#stacks`/`#repository_name`: [3](#0-2) 

`PushHandler` and `CheckSuiteHandler` correctly use this scoped `stacks` helper before acting: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, does **not** call `stacks`/`repository_name` at all. It resolves target commits purely by SHA, with zero repository scoping: [6](#0-5) 

This calls `Commit#create_status_from_github!`, which writes a new `Status` record used directly by `Commit#deployable?` to gate deploys: [7](#0-6) [8](#0-7) 

The exploited binding: the value authenticated by the HMAC check (`repository.owner.login` → org X's `webhook_secret`) is not equal to, and is never checked against, the repository/stack whose commit is mutated (any commit anywhere with a matching `sha`). Concretely: `verified_org(payload) == X` while `stack_written(payload) ∈ {all stacks in the Shipit instance}`, an inequality that should be an equality but isn't enforced anywhere in `StatusHandler`.

An attacker who is a legitimate contributor/admin of *any* one organization that this shared Shipit instance is configured for (i.e., they can produce a validly-signed `status` webhook body using that organization's own `webhook_secret` — as documented as normal/expected operation, e.g. multiple orgs configured in `test/dummy/config/secrets_double_github_app.yml`), or who targets an org whose `webhook_secret` is left unset (documented as *optional* in `docs/setup.md` line 30, in which case `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb#verify_webhook_signature` line 76-77) can send a `status` event with an arbitrary `sha` belonging to a commit in a *completely different* stack/repository and force a `success` state onto it.

### Impact Explanation
Forcing a fabricated `success` CI status onto an arbitrary commit directly flips `Commit#deployable?` to true (assuming the stack isn't `ignore_ci` and the commit isn't otherwise blocked), which is the exact gate used to decide whether a commit can be deployed (see `require_ci` handling exercised in `test/controllers/api/deploys_controller_test.rb` lines 88-103, showing deploy eligibility hinges on `deployable?`). Because the write path is unauthenticated with respect to the *target* repository (only the signing organization is checked, and that organization has no relationship enforced with the target repository), an attacker can make an untested/malicious commit in a victim repository appear CI-green and get it deployed — this is an unauthorized deploy of unreviewed code, matching the High/Critical impact bar ("unauthorized deploy").

### Likelihood Explanation
Any of the following unprivileged conditions make this reachable without touching a privileged GitHub App private key or repository write access:
- The Shipit instance hosts more than one GitHub organization (a documented, supported configuration, per `test/dummy/config/secrets_double_github_app.yml`) — a user who legitimately controls/administers one configured org can forge the org field while targeting a different org's commit SHA.
- Any configured organization's `webhook_secret` is left unset (explicitly documented as "optional" in `docs/setup.md`), which makes `verify_webhook_signature` return `true` for anyone, with no secret needed at all.

Because `StatusHandler` performs zero scoping, the only defense against cross-repository status injection is the org-level signature check, which this handler ignores by design.

### Recommendation
`StatusHandler` should use the inherited `stacks`/`repository_name` scoping (as `PushHandler` and `CheckSuiteHandler` already do) to restrict the commits it updates to those belonging to the repository identified by `payload.dig('repository','full_name')`, and that repository's owner should be validated to match the organization whose secret validated the signature before any commit status is written.

### Proof of Concept
1. Configure Shipit for two organizations, `OrgA` and `OrgB` (as in `test/dummy/config/secrets_double_github_app.yml`), with stacks tracking repositories in each.
2. As a user who administers `OrgA` (or targeting any org with `webhook_secret` unset), craft a `status` event payload:
```json
{
  "sha": "<victim_commit_sha_in_OrgB_repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
}
```
3. Sign the raw body with `OrgA`'s `webhook_secret` (or send unsigned if `OrgA`'s secret is unset) and POST to `/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` validates using `Shipit.github(organization: 'OrgA')` and passes.
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha)` — matching the victim commit in `OrgB`'s stack — and calls `create_status_from_github!`, marking it `success` regardless of the fact the signature only vouches for `OrgA`.
6. The victim commit in `OrgB` is now `deployable?` and can be shipped via the normal deploy API.
