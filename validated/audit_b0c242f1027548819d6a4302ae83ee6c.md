## Title
StatusHandler processes GitHub `status` webhooks by SHA alone, without validating the payload's `repository` against the target commit's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

## Summary
`StatusHandler`'s `ExplicitParameters` schema requires only `:sha` and `:state` and never requires or reads `:repository`, and `#process` looks up commits with `Commit.where(sha: params.sha)` with no repository/stack scoping. Signature verification in `WebhooksController` is keyed only by GitHub *organization* (`Shipit.github(organization: repository_owner)`), not by individual repository, so a single shared `webhook_secret` per organization is valid for every repository in that org.

## Finding Description
The claimed binding is: `payload['repository']['full_name'] == commit.stack.repository.full_name` should hold before `Commit#create_status_from_github!` is invoked. In `StatusHandler` this binding is never checked: [1](#0-0) 

`params` only `requires :sha` and `:state`; `:repository` is not declared in the schema at all, and `process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no reference to any repository field.

Upstream, `WebhooksController#verify_signature` resolves the signing app by organization login extracted from the attacker-controlled payload itself (`repository_owner`), not by a specific repository: [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` compares against a single `webhook_secret` configured per organization entry in `secrets.yml` (see `config/secrets.development.example.yml`, which documents one `webhook_secret` per org, shared by every repository under that org): [4](#0-3) 

Root cause: tenant isolation for `status` events is enforced at organization granularity by signature, and at no point at repository granularity. Since `sha` values are public information (visible to anyone with read access to the repository or its commit history/PRs) and the `repository` field of the payload is neither required nor validated, an attacker who legitimately owns (or has push/webhook-admin rights over) any repository within the *same GitHub organization* as a victim's Shipit-tracked stack can craft an arbitrary raw POST body: a minimal `status` payload with `sha` copied from a victim commit and any `state`, sign it with the org-wide `webhook_secret`, and have `StatusHandler` mutate the victim commit's status - even though the payload does not name, or names a different, `repository`.

Existing guards that fail to prevent this:
- `verify_signature` only proves "this request was authorized to claim events for organization X"; it says nothing about which repository within X the event concerns.
- The `ExplicitParameters` schema in `StatusHandler` (and the `Handler` base class dispatch) never consults `payload.dig('repository', ...)`.
- `Commit.where(sha: params.sha)` has no `stack_id`/repository filter.

This matches the described attacker action precisely: the webhook route only checks signature validity against *some* registered app/repo binding at the organization level; `StatusHandler.call` -> `Commit.where(sha:).each { commit.create_status_from_github!(params) }` proceeds regardless of the (absent or mismatched) `repository` field.

## Impact Explanation
An attacker who owns one repository inside an organization that hosts multiple Shipit-tracked stacks can inject fabricated CI status entries (`create_status_from_github!`) for **any commit** in **any other stack in that org**, as long as they can obtain the SHA (public data). This can flip a commit from failing/pending to `success`, unblocking `deployable?`/`schedule_continuous_delivery` and CI-gated auto-deploys for a stack that they do not own and have no legitimate relationship to, i.e., a payload for one repository mutating another repository's commit/stack state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The action is repeatable per request against arbitrary SHAs, and blast radius spans all stacks sharing the same organization-level GitHub App / webhook secret.

## Likelihood Explanation
Preconditions: the target Shipit deployment must configure GitHub Apps at organization granularity (the documented/default multi-org config format, one `webhook_secret` per organization, shared by all repos in that org) — this is the standard configuration shown in `config/secrets.development.example.yml`. The attacker needs (a) a repository they control within the same organization as the victim stack, with a real webhook wired to Shipit's `/webhooks` endpoint using that org's secret (achievable by any GitHub org member/repo owner who can add a webhook), and (b) knowledge of the victim commit's SHA (public). No Shipit session, API token, or GitHub App private key is required. This is feasible and repeatable, though it is bounded to organizations where multiple independently-trusted repositories share one Shipit GitHub App entry — which is the common/documented setup for this engine.

## Recommendation
`StatusHandler#params` should `require :repository` (at minimum `full_name`), and `#process` should scope the commit lookup by the stack's known repository (e.g., `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id })` or equivalent), rejecting/ignoring statuses whose `repository.full_name` does not match the commit's own stack repository. More broadly, webhook signature verification should be bound per-repository/stack (or the payload's `repository.full_name` cross-checked against every commit's actual stack repository) rather than trusting organization-level signatures as authorization for arbitrary repository content.

## Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status handler mutates a commit belonging to a different repository/stack" do
  victim_stack = shipit_stacks(:shipit)               # repo: "shopify/shipit-engine"
  attacker_stack = shipit_stacks(:cyclimse)           # repo: "attacker/some-other-repo"
  victim_commit = shipit_commits(:first)               # belongs_to victim_stack, sha known publicly

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => attacker_stack.github_repo_name } # or omitted entirely
  }

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  # Binding under test: payload['repository'] should equal victim_commit.stack.repository.full_name
  refute_equal payload['repository']['full_name'], victim_commit.stack.github_repo_name
  assert_equal 'success', victim_commit.reload.status.state # mutated despite mismatched repository
end
```
This demonstrates the handler updates `victim_commit` (belonging to a stack/repository the attacker does not control) purely from `sha`, with the `repository` field mismatched or absent, confirming the missing tenant-isolation check inside `StatusHandler`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
