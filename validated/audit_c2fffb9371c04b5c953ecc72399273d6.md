Confirmed: `in_data_feed()` in AA formulas is reachable by any unprivileged AA trigger sender via `formula/evaluation.js:745` (`dataFeeds.dataFeedExists`), which for non-`=`/`!=` relations calls `dataFeedByAddressExists` in `data_feeds.js`.

### Title
Premature RocksDB iterator destruction in `dataFeedByAddressExists` can crash the node on `in_data_feed()` AA evaluation - (File: data_feeds.js)

### Summary
`dataFeedByAddressExists()` opens a `kvstore.createKeyStream()` iterator and, for `>`, `>=`, `<`, `<=` relations, calls `stream.destroy()` while the underlying RocksDB iterator may still have reads/callbacks pending, then immediately synchronously invokes `onEnd()` itself instead of waiting for the stream's own `'end'`/`'close'` event.

### Finding Description
In `data_feeds.js:174-201`, on finding a satisfying record the handler does: [1](#0-0) 
`stream.destroy()` is called and `onEnd()` is invoked manually, while the stream's own `'end'` and `'error'` listeners remain attached (`data_feeds.js:196-201`). Destroying a levelup/rocksdb key-stream while it still has an in-flight/queued native read is a resource-deallocation race: the underlying iterator can still fire a callback after `destroy()` was requested. If that callback surfaces as an `'error'` event on the (already logically finished) stream, the handler is: [2](#0-1) 
which unconditionally `throw`s. Any uncaught exception in this codebase is fatal to the process — `network.js`'s global `uncaughtException` handler re-throws to crash the process by design: [3](#0-2) 
Additionally, `onEnd()` itself guards against being invoked twice by throwing: [4](#0-3) 
so if the destroyed stream still manages to emit its native `'end'` event after the manual `onEnd()` call, the second invocation throws `"second call of onEnd"`, again crashing the process.

This function is reached directly from `in_data_feed()`/`data_feed()` formula evaluation, which is executed while validating **any AA trigger unit** authored by an unprivileged party, via `formula/evaluation.js:745` → `dataFeeds.dataFeedExists` → `dataFeedByAddressExists`. [5](#0-4) 

### Impact Explanation
A crafted `in_data_feed()` call (choosing an oracle/feed_name/relation such that a matching record is found mid-scan, hitting the "destroy prematurely" path) run inside AA formula evaluation can trigger a race that either throws from the RocksDB iterator's error path or from the duplicate-`onEnd` guard, both of which propagate as uncaught exceptions that crash the whole full node process (`network.js:4530-4543`). Since every full node validating that AA trigger unit executes the same formula, this can be a network-wide crash trigger — "a network unable to confirm new units" until nodes recover, matching the DoS impact class of the reference CVE (crafted input leading to improper resource deallocation causing a crash).

### Likelihood Explanation
Reaching the vulnerable code path requires only posting an ordinary AA trigger unit to an AA (or defining and immediately triggering one's own AA) that calls `in_data_feed()` with a relation other than `=`/`!=` against a data feed with at least one matching record — no special privileges, no malicious peer/hub role, and no reliance on network timing beyond the intrinsic race in the underlying LevelDOWN/RocksDB destroy-while-reading behavior. Because destroy-while-reading races are timing/implementation dependent (depend on `level-rocksdb` internals and OS scheduling), this is not 100% reproducible on every call, which lowers but does not eliminate likelihood; repeated triggering by an attacker increases the chance of hitting the race.

### Recommendation
- Do not call `onEnd()` manually after `stream.destroy()`; instead wait for the stream's `'close'` event (or the native `'end'`) before calling the result handler, and remove/guard the `'error'` listener once destruction has been requested so races don't surface as uncaught throws.
- Replace the unconditional `throw Error(...)` in the stream `'error'` handler with a caller-facing error path (invoke `handleResult`/callback with a transient/validation error) so a single malformed or racy data-feed read cannot crash the whole process.
- Remove or relax the `"second call of onEnd"` self-throw guard, or make it a no-op/log instead of a hard crash, since it is directly reachable via externally triggered AA formula evaluation.

### Proof of Concept
1. Post units establishing a data feed from oracle address `O` for `feed_name` `"f"` with multiple values across several MCIs so that `dataFeedByAddressExists` iterates several keys before finding a match for a non-`=` relation.
2. Define/trigger an AA whose bound/response formula calls `in_data_feed({oracles=O, feed_name="f", feed_value>0})` (or `>=`, `<`, `<=`) so that, during validation of the AA trigger unit, `formula/evaluation.js` invokes `dataFeeds.dataFeedExists` → `dataFeedByAddressExists`.
3. Repeatedly send such triggers to increase the probability of the underlying key-stream still having a pending native callback when `stream.destroy()` fires in `data_feeds.js:184`; when the race is hit, the leftover `'error'` or duplicate `'end'` event throws inside the stream handler, crashing the validating node process via the global `uncaughtException` handler in `network.js:4530-4543`.
