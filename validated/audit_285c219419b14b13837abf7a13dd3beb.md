### Title
Race condition in indivisible private-payment saving allows a spend-proof "double-pop" that silently drops a spent output while both spenders receive `ifOk` - ([File: indivisible_asset.js])

### Summary
The crossbeam-deque advisory describes a race where a concurrently-shared work item can be "popped" (claimed) more than once, so one consumer's success masks the loss/duplication of another task. ocore's private (indivisible) asset chain-saving path has an analogous check‑then‑act race: two independent private-payment chains that spend the *same* private source output are validated and persisted through **separate, unsynchronized DB connections/transactions**, and the actual insert uses `INSERT OR IGNORE` (`db.getIgnore()`), so a UNIQUE-constraint conflict is swallowed silently rather than surfaced as an error — both callers can be told `ifOk` even though only one input row is ever recorded.

### Finding Description
`private_payment.validateAndSavePrivatePaymentChain` (`private_payment.js:23-119`) opens its own pooled connection per invocation, does a `SELECT ... FROM outputs` duplicate check, then delegates to `indivisibleAsset.validateAndSavePrivatePaymentChain` (`indivisible_asset.js:239-297`), which builds `arrQueries` including: [1](#0-0) 
using `db.getIgnore()` (i.e. `INSERT OR IGNORE` / `INSERT IGNORE`) into `inputs`, whose only integrity guard against double-spend is the UNIQUE key `bySrcOutput(src_unit, src_message_index, src_output_index, is_unique)`: [2](#0-1) 

Crucially there is **no mutex/lock keyed on the spent source output** (unlike the public payment path in `validation.js`, which serializes on `arrAuthorAddresses` via `mutex.lock` at `validation.js:357` and explicitly runs `checkForDoublespends`/`checkInputDoubleSpend`). The private-chain save path never calls `checkForDoublespends`; it only performs a per-connection duplicate-output existence check before starting its own transaction: [3](#0-2) 

Two competing private chains for the same `(src_unit, src_message_index, src_output_index)` can thus run their `SELECT`/`BEGIN`/`INSERT`/`COMMIT` sequences concurrently on different pooled connections. Because the second `INSERT` is silently ignored on conflict (no error propagated), `async.series(arrQueries, callbacks.ifOk)` still calls `ifOk()` unconditionally: [4](#0-3) 
The unconditional `UPDATE outputs SET is_spent=1 ... is_serial=... WHERE ... AND is_spent=0` on the shared output rows also races between the two transactions.

This is directly reachable by a **private-payment counterparty**: nothing prevents an author from sending the same private output to two different recipients concurrently — e.g. once "directly" to a peer and once "via hub" as explicitly acknowledged in the code comment at `network.js:2391-2392`, or via two devices/sessions. Server-side batch processing of queued chains also runs multiple rows concurrently rather than serially: [5](#0-4) 

### Impact Explanation
A malicious (or buggy) private-payment sender can present the same output to two counterparties at nearly the same time. Due to the unsynchronized concurrent transactions and `INSERT IGNORE` semantics, both recipients' local nodes can independently believe the payment was **accepted** (`ifOk` fired for both, `sendResult(... result: 'accepted')` in `network.js:2480-2482`), while only one of the two actually has a persisted `inputs` row spending that output. The victim whose insert was silently dropped believes they hold a valid, accepted private payment, but the canonical spend record for that output does not reflect their receipt — leading to loss of funds/confusion for one counterparty and a state where the two nodes disagree about which chain legitimately owns the output. This matches the report's required "concrete... freezing"/"node disagreement on validity" impact class, scoped to private-payment chains reachable by any private-payment counterparty.

### Likelihood Explanation
Exploitation requires only that an attacker (as sender/author of a private asset output) transmit two conflicting private-payment chains referencing the same source output through two channels (direct peer + hub, or two devices) close enough in time that their independent DB transactions interleave — well within normal application behavior that the code itself anticipates (`network.js:2391-2392` comment about "received directly and via hub"). No node compromise or privileged access is needed; it only needs message timing that an attacker fully controls.

### Recommendation
- Serialize private-chain validation/saving per spent output, e.g. `mutex.lock(["private_output-" + src_unit + "-" + src_message_index + "-" + src_output_index], ...)` around `validateAndSavePrivatePaymentChain` in `private_payment.js`/`indivisible_asset.js`, analogous to how `validation.js` locks on `arrAuthorAddresses`.
- Do not use `INSERT OR IGNORE` for the `inputs` row that determines double-spend uniqueness without checking `affectedRows`/`changes`; if the insert is ignored due to conflict, propagate an explicit error to `callbacks.ifError` instead of calling `ifOk`.
- Make the `is_spent` update conditional on the insert actually having occurred (check affected rows), not run it unconditionally when the input write was skipped.

### Proof of Concept
1. Attacker owns a private-asset output O (`src_unit`, `src_message_index`, `src_output_index`).
2. Attacker constructs two distinct private-payment chains `chainA` (paying recipient X) and `chainB` (paying recipient Y), each spending O.
3. Attacker sends `chainA` directly to X's node (peer message) and `chainB` via the hub to Y's node, timed so that both nodes' `handleOnlinePrivatePayment` → `validateAndSavePrivatePaymentChain` executions overlap (`network.js:2412-2440`, `private_payment.js:45-118`).
4. On the shared server (or if X and Y ever synchronize through a common hub-side path handling both, e.g. `handleSavedPrivatePayments`'s `async.each` parallel processing at `network.js:2459-2511`), both `SELECT`-then-`INSERT IGNORE` sequences run concurrently on separate connections; one `INSERT` into `inputs` silently no-ops due to the UNIQUE key conflict, yet `callbacks.ifOk()` is still invoked for both chains.
5. Both X and Y receive `result: 'accepted'` for a payment from the same output, while only one input row exists in `inputs`, producing inconsistent private-payment state between the two counterparties.
