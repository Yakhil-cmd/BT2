### Title
Unauthenticated CI-status forgery via organization/secret confusion in webhook signature verification bypasses repository binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization secret to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, unsigned JSON body. If that organization is configured without a `webhook_secret` (an explicitly documented, supported configuration), signature verification is bypassed unconditionally. The event is then dispatched to a handler that establishes no independent binding between the "authenticated" organization and the resource actually mutated — in particular `StatusHandler` looks up commits purely by `sha`, globally, with no repository/organization check at all. This breaks the equality that should hold: `organization that authenticated == repository/commit that is written`.

### Finding Description
`repository_owner` is derived entirely from attacker-controlled JSON: [1](#0-0) 

This value selects the `GithubApp` instance used to verify the signature: [2](#0-1) 

`verify_webhook_signature` unconditionally returns `true` when the selected organization has no `webhook_secret` configured: [3](#0-2) 

Leaving `webhook_secret` unset is a documented, supported configuration — both the single-org setup guide and the multi-org fixture treat it as optional/nilable: [4](#0-3) [5](#0-4) 

Once the request passes this check (because the attacker simply names, in the JSON body, whichever configured organization happens to have a blank secret), the payload is dispatched to the registered handler for the event with no re-validation that the "authenticated" organization matches the resource being written. `StatusHandler#process` demonstrates this directly — it resolves target commits solely by `sha`, with no scoping to a repository or organization at all: [6](#0-5) 

So the trust binding broken is exactly the pattern called out in the rules: *"an organization that authenticated versus the repository that is written."* The attacker picks the organization side of the equation (to satisfy/bypass verification) while the handler acts on a completely different resource (any commit, in any stack/repository tracked by the Shipit instance, matched purely by `sha`).

### Impact Explanation
An unauthenticated party who can reach `/webhooks` (a public, unauthenticated endpoint by design — `WebhooksController` skips CSRF and has no session/API-token requirement) can forge a GitHub `status` event for any commit SHA already known to the Shipit instance, in any repository, as long as one configured GitHub organization in the deployment has no `webhook_secret` set. This lets the attacker inject an arbitrary CI status (`state: success`, any `context`) onto that commit without ever proving they control the real repository or organization. If that commit belongs to a stack with continuous deployment / merge-queue rules gated on the forged `context`, the attacker can synthetically satisfy CI requirements and trigger an unauthorized deploy — meeting the "Critical: unauthorized deploy" bar. Similarly, `PushHandler`/`CheckSuiteHandler` are reachable through the same signature-bypass path, letting an attacker enqueue sync/check-run-refresh jobs for stacks unrelated to the "authenticated" organization.

### Likelihood Explanation
This requires: (1) a Shipit deployment with at least one configured organization lacking a `webhook_secret` — a state the project's own docs and multi-org fixtures explicitly treat as valid/normal (e.g. for orgs where the operator didn't bother setting one) — and (2) knowledge of a target commit SHA already tracked by the instance (commit SHAs are git-public information, commonly visible via GitHub itself or Shipit's own UI). No credentials, tokens, or repository write access are required to hit the endpoint itself. Given webhook secrets are optional by design and multiple orgs are an explicitly supported topology, this is a realistic, not purely theoretical, misconfiguration-adjacent condition rather than a deviation from documented deployment.

### Recommendation
- Bind the resource acted upon to the organization/repository that passed signature verification: after `verify_signature` succeeds for organization `O`, every handler must additionally confirm that the payload's `repository.full_name`/owner actually belongs to `O` (or to the `Repository`/`Stack` record being mutated) before acting.
- In `StatusHandler` (and any other handler), scope commit/stack lookups by the repository derived from the verified organization, not solely by `sha`.
- Do not allow `verify_webhook_signature` to silently return `true` for organizations with no configured secret; either require a secret for every configured organization or reject/flag unsigned deliveries explicitly rather than treating "no secret" as "always valid."

### Proof of Concept
Given a Shipit deployment with two configured GitHub orgs where `OrgTwo` has `webhook_secret: nil` (as in `test/dummy/config/secrets_double_github_app.yml`):

```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "OrgTwo" } },
  "sha": "<sha-of-a-real-commit-tracked-under-a-different-org/repo>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake",
  "created_at": "2026-09-01T00:00:00Z"
}
```

- `repository_owner` resolves to `"OrgTwo"` from the body.
- `Shipit.github(organization: "OrgTwo").verify_webhook_signature(...)` returns `true` because `OrgTwo`'s `webhook_secret` is blank (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`) — no valid `X-Hub-Signature` is needed.
- `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), creating a forged successful status on the target commit regardless of which repository/organization it actually belongs to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
