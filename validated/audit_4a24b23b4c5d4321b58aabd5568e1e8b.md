### Title
Unverified `device_address` claims in shared-address signer definitions allow multisig cosigner identity spoofing - (File: `wallet_defined_by_addresses.js`)

### Summary
`wallet_defined_by_addresses.js`'s `handleNewSharedAddress()` accepts a `signers` map from an arbitrary correspondent device over the wallet-chat channel and persists whatever `device_address` values that peer supplies into `shared_address_signing_paths`, without ever checking those `device_address` values against the cryptographically authenticated identity (`from_address`) of the device that actually sent the message. This mirrors the SaltStack CVE-2013-4439 bug class: an authenticated principal (a paired/valid device) can assert an unverified identity (an arbitrary `device_address`) for another party, and the receiving node accepts it as authoritative without proof of control.

### Finding Description
When a peer proposes a new shared (multisig) address, it sends a `new_shared_address` message whose body is handled by `handleNewSharedAddress`: [1](#0-0) 

The function validates:
- that `body.definition` hashes to `body.address` [2](#0-1) 
- that each `signerInfo.address` in `body.signers` is a syntactically valid address and matches the address referenced at the same path in the definition [3](#0-2) 

It never validates `signerInfo.device_address`. This value is taken as-is from the untrusted network body and written directly into the local database: [4](#0-3) 

There is no check anywhere in this flow that the `device_address` claimed for a given signer actually corresponds to the device that sent the message (`from_address`), nor any proof (signature) binding that device to the claimed address/key. `determineIfIncludesMeAndRewriteDeviceAddress` only fixes up entries that are *our own* addresses (found in `my_addresses`/`shared_addresses`); it does nothing to validate device addresses claimed for the *other* co-signers: [5](#0-4) 

Contrast this with `wallet.js`'s `prosaic_contract_response` / `arbiter_contract_response` handlers, which correctly bind `peer_addresses.device_address` to the authenticated `from_address` of the message rather than trusting a self-declared field: [6](#0-5) . The shared-address flow lacks the analogous binding for co-signer device addresses.

Once `shared_address_signing_paths.device_address` is poisoned, `findAddress()` (used both to route "who should sign this input" and to decide the trust boundary for local vs. remote signing) will consult this table and route signing requests, private payment chains, and definition-forwarding traffic to whatever device address the attacker asserted: [7](#0-6) 

### Impact Explanation
An attacker who proposes (or forwards) a shared-address definition can assign the `device_address` for another cosigner slot to be a device it controls (rather than the real owner of that payment address), or to be the victim's own device address to trigger unwanted "sign" requests, private-payment-chain deliveries, and contract-deposit UI prompts on the victim. Because signing itself still requires a valid signature that satisfies the address's actual `["sig"...]`/`["and"...]` definition on-chain, this does not by itself forge a valid unit signature; but it corrupts local bookkeeping that decides where wallet-level protocol traffic (private payment chains, signing offers, forwarded shared-address definitions) is routed, enabling confusion of co-signers, targeted spam/DoS of a specific victim device, and potential social-engineering vectors where the victim's wallet displays misleading "confirm_contract_*" / "confirm_on_other_devices" prompts attributing cosigner actions to the wrong device. It also allows an attacker to silently substitute themselves as a routing hop (`row.device_address`) for private payment forwarding intended for a legitimate cosigner, since `forwardPrivateChainsToOtherMembersOfAddresses` and `sendPrivatePayments` follow the `shared_address_signing_paths.device_address` values verbatim: [8](#0-7) .

### Likelihood Explanation
Any correspondent device that has been paired with the victim (a normal, low-privilege state reachable simply by exchanging pairing info) can send a `new_shared_address` (or forwarded `new_shared_address`) message with attacker-chosen `device_address` fields for the multisig definition's signer slots. No special network position or hub compromise is needed — this is reachable by any paired wallet counterparty proposing a multi-party address, which is a standard, expected workflow in ocore's wallet layer.

### Recommendation
In `handleNewSharedAddress`, cross-check each `signerInfo.device_address` against known/authenticated identities before persisting:
- For the signer entry that the sender is proposing as itself, require `signerInfo.device_address === from_address` (the authenticated sender of the message), similar to how `wallet.js` binds `peer_addresses.device_address` to `from_address` in contract responses.
- For device addresses claimed for other cosigners, require that they already be known correspondents (`correspondent_devices`) or otherwise verifiable, and treat any unverifiable claim as advisory rather than authoritative for the purposes of routing signing requests/private payments, or explicitly warn/require user confirmation before trusting a new binding of payment-address → device_address.
- Pass `from_address` into `handleNewSharedAddress`/`addNewSharedAddress` explicitly so the binding check is enforced structurally rather than relying on caller discipline.

### Proof of Concept
1. Device M (malicious) pairs normally with victim device V (a legitimate, low-privilege pairing, no special access required).
2. M sends V a `new_shared_address` message with a valid 2-of-2 `definition` referencing addresses `A` (owned by honest cosigner C, whose real device address is `D_C`) and `B` (owned by V), but sets `signers["r.0"] = {address: A, device_address: D_M}` (M's own device address) instead of `D_C`.
3. `handleNewSharedAddress` validates only that `A` and `B` match the definition paths (`wallet_defined_by_addresses.js:391-405`) and that the definition hashes to `body.address` (`:383-390`); it never verifies `D_M` is actually associated with `A`.
4. `addNewSharedAddress` persists `(shared_address, A, "r.0", ..., D_M)` into `shared_address_signing_paths` on V's node (`wallet_defined_by_addresses.js:239-268`).
5. Subsequently, when V needs a co-signature for spending from the shared address, `findAddress` routes the signing request and any private payment chains for that address to `D_M` instead of the real owner `D_C` (`wallet.js:1262-1287`, `wallet_defined_by_addresses.js:531-543`), letting M intercept signing offers/private payment data intended for C or spam/confuse V's UI about who is co-signing.

Note: I was unable to find the exact call site in `wallet.js` that dispatches the `new_shared_address` justsaying/request to `handleNewSharedAddress` (the surrounding switch-case text did not appear in the indexed excerpts), so I could not directly confirm whether any additional `from_address`-based check is applied immediately before this call. Given the size limits on the indexed codebase, I recommend a Devin session review the full `wallet.js` dispatch table around the `new_shared_address` case to confirm there is no filtering being applied at that call site before treating this as fully confirmed.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

// {address: "BASE32", definition: [...], signers: {...}}
function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
