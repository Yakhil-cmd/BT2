### Title
No vulnerability found — allowlist upper-bound is enforced in `register-for-bond` ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
The claimed missing check does not exist as a gap; `register-for-bond` explicitly asserts `sats-total <= allowance` immediately after computing `sats-total` and looking up the caller's `protocol-bond-allowances` entry, rejecting with `ERR_TOO_MUCH_SATS` if the requested sBTC amount exceeds the staker's allowlisted `max-sats`.

### Finding Description
The equality the question asks about is: does `register-for-bond` guarantee `sats-total <= allowance` (the allowlisted `max-sats`) before crediting `sats-total` into `protocol-bond-memberships` / bond shares? Tracing the function body: `sats-total` is computed from `btc-lockup` (either via `verify-l1-lockups` for the `ok` branch, or directly as `sbtc-amount` for the `err` branch) [1](#0-0) . The allowance is looked up from `protocol-bond-allowances` keyed by `{staker: tx-sender, bond-index}`, failing with `ERR_NOT_ALLOWLISTED` if absent [2](#0-1) . After the lower-bound check (`amount-ustx >= min-ustx-for-sats-amount ...`, `ERR_INSUFFICIENT_STX`) and the bond-not-started / no-overlapping-stake checks, the contract explicitly enforces the upper bound: `(asserts! (<= sats-total allowance) ERR_TOO_MUCH_SATS)` [3](#0-2) . This assert runs before any state mutation (custody transfer, `protocol-bond-memberships` insert, or reward-share bookkeeping) further down in the function, so an attacker calling with `sbtc-amount` (the `err` branch of `btc-lockup`) strictly greater than their allowlisted `max-sats` M will revert at this line with `ERR_TOO_MUCH_SATS` and no state is written.

### Impact Explanation
No impact — the guard prevents `sats-total` from ever exceeding the allowlist's `max-sats`, so bond weight/reward-slot eligibility computed from `sats-total` cannot exceed what was authorized. No lock conservation break, no dilution, no over-claiming of rewards.

### Likelihood Explanation
N/A — the guard is unconditional and independent of cycle phase, membership state, or attacker behavior; every call path through `register-for-bond` passes through this assert before any custody or membership state is mutated.

### Recommendation
None needed; existing code correctly enforces the invariant. This is also directly covered by the repo's own integration tests confirming the revert.

### Proof of Concept
The repository's own contract test `contrib/core-contract-tests/tests/pox-5/commands/RegisterForBondErrTooMuchSats.ts` already implements exactly the proof idea requested: it constructs `sats` strictly greater than `allowance` (and `<= balance`), calls `register-for-bond` with `btcLockup: err(sats)`, asserts the call reverts with `receipt.value === errorCodes.ERR_TOO_MUCH_SATS`, and asserts pre/post state (`getBondMembership`, `sbtcBalance`, `getTotalSbtcStaked`) are unchanged [4](#0-3) , confirming `sats-total <= allowance` is enforced and no sats are credited beyond the allowance.
