### Title
GitHub webhook signature is verified against an organization derived from the payload, not the repository the event actually mutates - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to verify a webhook's HMAC signature against using a value pulled out of the untrusted JSON body itself (`repository.owner.login`, or `organization.login` as a fallback). Because the attacker fully controls the raw JSON payload, they can decouple "the organization whose secret was used to authenticate this request" from "the repository/stack that the downstream handler actually mutates."

### Finding Description
`verify_signature` computes the organization used for verification purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`Shipit::GitHubApp#verify_webhook_signature` then keys the HMAC check on that organization's configured `webhook_secret`: [3](#0-2) 

Note the `return true unless webhook_secret` short-circuit: if the organization resolved from the payload has no `webhook_secret` configured (documented as "optional" in `docs/setup.md`), verification passes unconditionally regardless of signature. Shipit explicitly supports multiple GitHub orgs, each with its own `webhook_secret`, configured under distinct top-level keys in `secrets.yml` (see `docs/setup.md` "Using Multiple Github Applications").

The controller passes the full, unvalidated `params` straight to the registered handlers after this check: [4](#0-3) 

Handlers (e.g. the push handler that resolves a `Stack`/`Repository` and enqueues `GithubSyncJob`, or handlers that record commit `Status`/`CheckRun` state) read repository-identifying fields (owner/name/full_name) from this same payload to decide which `Stack` to act on. There is no code in `WebhooksController` (or elsewhere in the request path) that re-derives the acting organization from the fields the handlers use, or that cross-checks that the org whose secret validated the signature is the same org that owns the repository the handler is about to write to. This is exactly the "organization authenticated vs. repository written" binding break: the equality `verified_org == mutated_repository.owner` is never enforced.

### Impact Explanation
If a Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration), or if any configured organization has no `webhook_secret` set (also documented as optional), an attacker can:
- Craft a payload whose `repository.owner.login`/`organization.login` names an organization with no `webhook_secret` (or one for which the attacker knows/controls the secret), causing `verify_webhook_signature` to pass trivially.
- Populate the remaining repository/commit fields (owner/name, sha, state/context, branch) with values pointing at a completely different, victim-owned stack.
- Have the request routed to real handlers (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) as if it were a legitimate authenticated event for that victim stack, because the controller never re-validates that the org used for authentication matches the repository actually referenced by the handler logic.

Depending on which event/handler is targeted, this can trigger unauthorized `GithubSyncJob` runs, forge passing/failing CI `status` on a victim commit (which the merge queue and continuous-delivery gating rely on per `app/models/shipit/deploy_spec.rb` `required_statuses`/`merge_request_required_statuses`), or otherwise influence merge/deploy gating decisions for a stack the attacker does not control — i.e., unauthorized manipulation of deploy/merge preconditions without any GitHub repository write access, ApiClient token, or privileged Shipit account.

### Likelihood Explanation
Requires only network access to the public `/webhooks` endpoint (no authentication, no ApiClient token, no TLS interception). Requires the operator to have configured at least one organization without a `webhook_secret`, or multiple organizations where the attacker legitimately controls one org's GitHub App/secret — both are explicitly documented, supported configurations rather than misconfigurations forbidden by the docs. This is a real gap in the verification logic itself, not solely an operator error.

### Recommendation
Derive the organization used for signature verification from the same trusted source the downstream handler uses to resolve the `Stack`/`Repository`, and reject the request if they diverge. At minimum, after a handler resolves the target `Stack`, re-verify that `repository_owner` (used to pick the signing secret) equals the resolved stack's `repo_owner` before performing any mutation, and stop treating a missing `webhook_secret` as an implicit "always valid" signal for cross-organization payloads.

### Proof of Concept
1. Shipit is configured with two GitHub orgs: `attacker-org` (webhook secret unset or known to the attacker) and `victim-org` (hosts the target `Stack`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and a JSON body where `repository.owner.login = "attacker-org"` (or `organization.login` fallback) but `repository.full_name`/`repository.name` set to the victim's repo, and a valid or absent `X-Hub-Signature` for `attacker-org`.
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and either finds no `webhook_secret` (passes unconditionally) or successfully verifies with `attacker-org`'s secret.
4. The registered `push` handler processes the same payload's repository fields, resolves the victim's `Stack`, and enqueues `GithubSyncJob`/updates commit state as though the event were authentically sent by GitHub for `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
