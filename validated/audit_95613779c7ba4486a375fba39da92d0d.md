### Title
Unbounded recursive inclusion depth in `readAllControlAddresses` causes remote memory exhaustion / stack growth DoS - ([File: wallet_defined_by_addresses.js])

### Summary
`readAllControlAddresses` in `wallet_defined_by_addresses.js` recursively resolves the chain of "control addresses" (addresses that are members of a shared address, which may themselves be shared addresses) with no maximum recursion depth, no cycle detection, and no de-duplication of already-visited addresses. This directly mirrors the ESI plugin bug in the report: a recursive "inclusion" operation with no maximum-depth guard that can be driven into unbounded recursion by attacker-supplied nested definitions, exhausting memory/stack.

### Finding Description
`readAllControlAddresses` walks `shared_address_signing_paths` outward from a set of addresses: [1](#0-0) 

Each iteration re-queries for the `address` column of every row whose `shared_address` is in the current set, and recurses with the newly found addresses as the new `arrAddresses`, merging results with `_.union`. There is no depth counter, no "visited" set, and no check that a previously-seen address is not being re-processed.

Shared addresses and their member/control addresses are populated from data received directly from a **paired device** over the `new_shared_address` message, handled by `handleNewSharedAddress`: [2](#0-1) [3](#0-2) 

`handleNewSharedAddress` validates only that (a) the definition hashes to the claimed address, (b) referenced member addresses are syntactically valid addresses, and (c) `Definition.validateDefinition` accepts the tree (bounded by `MAX_COMPLEXITY`/`MAX_OPS`, not by cross-shared-address cycles). It never checks whether a member/control `address` used as a signer for shared address `A` is *itself* a shared address whose own signers loop back to `A` (or to any ancestor already being resolved). `addNewSharedAddress` then persists these entries unconditionally: [4](#0-3) 

Because each shared address is validated independently (its own definition tree, bounded by complexity limits), nothing prevents two (or more) *cooperating/malicious paired devices* from registering shared address `A` whose control/member address is `B`, and shared address `B` whose control/member address is `A`. Later, whenever `readAllControlAddresses` is invoked on `A` (e.g., to enumerate all devices/addresses that must cosign or receive a private chain for a shared address), the function will recurse `A → B → A → B → …` indefinitely: `Definition.validateDefinition`'s complexity/op counters do not apply here because this is a plain SQL-driven graph walk over stored member addresses, not an evaluation of a single address's own definition AST. Each recursive call issues a new DB query, allocates new callback closures, and grows the accumulated `_.union` result arrays — driving unbounded memory growth and closure/call-stack accumulation, analogous to the ESI plugin's uncontrolled recursive inclusion.

This is exactly the bug class in the report: a graph/definition-inclusion walk with no `--max-inclusion-depth`-equivalent guard, reachable by supplying attacker-controlled nested references (here, nested shared-address memberships delivered via paired-device messages).

### Impact Explanation
An attacker who controls (or colludes with) one or two paired devices can register a cyclic shared-address membership graph. Any subsequent local operation on the victim's wallet that calls `readAllControlAddresses` (used to resolve the full set of control addresses/co-signing devices for a shared address, e.g., when composing or forwarding a private payment through that shared address) will enter unbounded recursion, growing memory usage and the async call chain without bound until the wallet process crashes or becomes unresponsive — a node/wallet unable to process further requests. This is a memory-exhaustion Denial of Service against the victim's wallet process, matching the CVSS impact profile of the ESI CVE (Availability: High, no confidentiality/integrity impact).

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to be an already-paired device (or two colluding paired devices) of the victim, which is the same trust boundary explicitly permitted by the task rules ("paired device can reach"). No special privileges beyond normal pairing are needed, and the `new_shared_address` message handler performs no cross-reference/cycle check before persisting the shared-address graph.

### Recommendation
Add a maximum recursion-depth (and/or a visited-address set) to `readAllControlAddresses`, aborting and returning an error once a bound (e.g., 100) is exceeded or once a previously-visited address reappears in `arrAddresses`. Additionally, `handleNewSharedAddress`/`addNewSharedAddress` should reject registration of shared-address membership graphs that would introduce a cycle across `shared_address_signing_paths` records.

### Proof of Concept
1. Device X and Device Y (attacker-controlled, paired with the victim) each send `new_shared_address` messages to the victim:
   - Message 1: shared address `A` with definition `["address", "B"]` embedded appropriately as one signer branch, `signers` map pointing the corresponding path to address `B`.
   - Message 2: shared address `B` with definition `["address", "A"]` similarly pointing back to `A`.
2. `handleNewSharedAddress` validates each definition independently and successfully (each definition tree alone is small and passes `Definition.validateDefinition`), then `addNewSharedAddress` persists both into `shared_addresses` / `shared_address_signing_paths`.
3. Any subsequent call to `walletDefinedByAddresses.readAllControlAddresses(conn, ['A'], cb)` (e.g., triggered while composing/forwarding a payment involving shared address `A`) recurses `A → B → A → B → …` forever, growing memory/call stack until the process runs out of memory or hangs.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

function readAllControlAddresses(conn, arrAddresses, handleLists){
	conn = conn || db;
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, (correspondent_devices.device_address IS NOT NULL) AS have_correspondent \n\
		FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?)", 
		[arrAddresses], 
		function(rows){
			if (rows.length === 0)
				return handleLists([], []);
			var arrControlAddresses = rows.map(function(row){ return row.address; });
			var arrControlDeviceAddresses = rows.filter(function(row){ return row.have_correspondent; }).map(function(row){ return row.device_address; });
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
