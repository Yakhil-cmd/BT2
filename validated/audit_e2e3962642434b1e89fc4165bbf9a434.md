### Title
Cross-organization webhook spoofing via mismatched signature-verification key and repository target - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the HMAC verification key from `repository.owner.login` (or `organization.login`) in the *untrusted* JSON body, but every event handler resolves the actual repository/stack to act on from a *different* field in the same untrusted body (`repository.full_name`). If any configured GitHub organization in this Shipit instance has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` returns `true` unconditionally, letting anyone post an arbitrary, unsigned payload that names that org as `repository.owner.login` while pointing `repository.full_name` at a completely different (victim) repository/stack.

### Finding Description
`verify_signature` selects the signing/verification org purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` intentionally treats a blank `webhook_secret` as "no verification required": [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Meanwhile, every `Shipit::Webhooks::Handlers::Handler` subclass (e.g. `PushHandler`) resolves which `Stack`/`Repository` to operate on from a *separate* field of the same body, `repository.full_name`, with no cross-check against `repository_owner`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
```

The binding that should hold is: *the organization whose credential authenticated the request* == *the organization owning the repository the handler acts on*. Because signature verification is keyed off `repository.owner.login` while the handler acts on `repository.full_name`, these two fields are never cross-validated against each other, and when the org named by `repository.owner.login` has no `webhook_secret` configured, signature verification is skipped entirely — so an attacker can name any low-security/no-secret org as the "owner" to pass the check while pointing `full_name` at any other repository tracked by this Shipit instance.

### Impact Explanation
An unauthenticated caller can invoke any webhook handler (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) against a victim stack/repository they have no GitHub permissions on, as long as one configured organization in this Shipit deployment lacks a `webhook_secret`. For `push`, this forces `Stack#sync_github(expected_head_sha: ...)` with an attacker-chosen SHA on a repository the attacker does not control, which can trigger continuous-delivery deploy scheduling and status/ref mutations for that stack — an unauthorized action on a stack outside the attacker's authority, mapping to the "unauthorized deploy" impact class.

### Likelihood Explanation
Exploitability depends entirely on deployment configuration: it requires at least one organization in `Shipit.github_config` to be set up without a `webhook_secret` (the code explicitly supports and does not warn against this — `return true unless webhook_secret`). In multi-org Shipit deployments (which the engine explicitly supports, per the `GithubOrganizationUnknown` handling and per-org `Shipit.github(organization:)` lookup), this is a plausible operator configuration, especially for a newly onboarded org before secrets are set. No GitHub credentials, session, or `ApiClient` token are required — only knowledge of the org name with a missing secret and the victim's `owner/repo` full name, both of which are effectively public.

### Recommendation
- Do not allow `verify_webhook_signature` to silently return `true` for a blank secret in production; require every registered organization to configure a `webhook_secret`, or explicitly fail closed.
- Cross-validate that `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login` before dispatching to any handler, so the field used for authentication and the field used for repository resolution can never diverge.

### Proof of Concept
1. Configure Shipit with two orgs: `victim-org` (with a real `webhook_secret`, owning stack `victim-org/victim-repo`) and `low-sec-org` (registered but with no `webhook_secret` set).
2. POST directly to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "low-sec-org" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
No `X-Hub-Signature` header is required to be valid, since `verify_webhook_signature` returns `true` for `low-sec-org`'s blank secret.
3. `WebhooksController#verify_signature` passes (using `low-sec-org`'s config), `PushHandler` resolves `stacks` via `full_name = "victim-org/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack — an action the attacker was never authorized to trigger.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
