### Title
Webhook signature verified against attacker's own GitHub App organization while repository mutation is scoped by an attacker-controlled `full_name` field, allowing cross-repository `ReviewStack` creation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and its `webhook_secret`) using `params.dig('repository','owner','login')`, but `PullRequest::OpenedHandler#repository` (and the base `Handler#stacks`) independently resolve the `Shipit::Repository` to mutate using `params.repository.full_name` from the very same JSON body. Because these two fields are never cross-checked, an attacker who owns a Shipit-configured GitHub organization can sign a payload with their own `webhook_secret` while setting `repository.full_name` to a victim organization's repository, causing a `ReviewStack` to be created under the victim's repository.

### Finding Description
The broken binding: organization whose `webhook_secret` verified the request body (`repository_owner` = `params.dig('repository','owner','login')`) **must equal** the organization owning the `Repository` actually mutated (parsed from `params.repository.full_name` in the handler). The code never enforces this.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and picks the app via `Shipit.github(organization: repository_owner)` (`lib/shipit.rb:170-181`, `github_app_config`), then calls `github_app.verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`), which HMACs the raw body against that organization's configured `webhook_secret`.
- Once verified, `create` dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:10-15`).
- `PullRequest::OpenedHandler#repository` (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`) resolves the repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, completely independent of `repository_owner` used above. `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) just splits `full_name` on `/` and looks up by `owner`/`name` — it does not compare against the organization whose secret verified the signature.
- `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) has the same pattern for other handlers.

Exploit flow: attacker configures/controls a GitHub org `evil-org` that is a legitimate Shipit-configured organization with its own `webhook_secret`. Attacker crafts a `pull_request` `opened` webhook body with `repository.owner.login = "evil-org"` and `repository.full_name = "shopify/shipit-engine"`, computes `X-Hub-Signature` using `evil-org`'s `webhook_secret` (known to the attacker as owner of that org's Shipit App config), and POSTs to `/webhooks`. `verify_signature` picks `evil-org`'s app/secret, verification succeeds, request proceeds. `OpenedHandler#repository` then resolves `shopify/shipit-engine` and, via `ReviewStackAdapter#find_or_create!`, creates a `ReviewStack` scoped to the victim's repository.

Existing guards do not prevent this: `drop_unhandled_event` only filters unsupported events, `ExplicitParameters` schema only validates shape/types (not cross-field consistency), and there is no code anywhere comparing `repository_owner` (used for signature selection) against the owner segment of `repository.full_name` (used for mutation).

### Impact Explanation
An attacker who legitimately controls one Shipit-configured GitHub organization (`evil-org`) can forge writes into any *other* configured organization's repository/stack data purely by mismatching `repository.owner.login` vs `repository.full_name` in the webhook body. This is a cross-repository/cross-tenant write: creation of `ReviewStack` records (and, by the same mechanism, `stacks`-scoped effects in other handlers such as push/status/check_suite handlers which resolve via `Handler#stacks`/`repository_name`) under a repository the attacker does not own or control. This matches the "payload for one repository mutating another's stack" Critical category. It is repeatable against any repository configured in `Shipit.github_organizations` as long as the attacker knows or guesses `owner/name`.

### Likelihood Explanation
Preconditions: multi-organization GitHub App config (`Shipit.github_organizations` with more than one entry, each with distinct `webhook_secret`), and the attacker must control at least one configured organization (`evil-org`) enough to know its `webhook_secret`, e.g., because they are an admin of a GitHub App installation Shipit trusts for their own org, or because per-org secrets are otherwise obtainable through legitimate use of their own org's Shipit integration. This is a realistic multi-tenant Shipit deployment scenario (the engine explicitly supports multiple organizations via `github_app_config`/`TOP_LEVEL_GH_KEYS`). No GitHub or Shipit secrets belonging to the victim org are needed — only the attacker's own org's secret, and knowledge of the victim's `owner/name`. The request is a simple unauthenticated HTTP POST to `/webhooks`, repeatable at will.

### Recommendation
After selecting the GitHub App/organization for signature verification, cross-check that the `repository.full_name`'s owner segment matches `repository_owner` before dispatching to handlers (and reject/422 on mismatch). Alternatively, have `Repository.from_github_repo_name` / `Handler#stacks` receive and enforce the verified `repository_owner` rather than re-deriving trust from the unauthenticated `full_name` field.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "cross-organization payload creates a ReviewStack under a different org's repository" do
  victim_repo = shipit_repositories(:shopify_shipit) # owner: 'shopify', configured with review_stacks
  # 'evil-org' is a second configured organization in credentials with its own webhook_secret
  body = {
    action: 'opened',
    number: 2,
    pull_request: {
      id: 1, number: 2, url: 'https://api.github.com/x', title: 'x', state: 'open',
      additions: 1, deletions: 0,
      head: { sha: 'abc', ref: 'feature' },
      user: { login: 'attacker' },
      assignees: [], labels: []
    },
    repository: { full_name: 'shopify/shipit-engine', owner: { login: 'evil-org' } },
    sender: { login: 'attacker' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', evil_org_webhook_secret, body)}"

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  assert_difference -> { Shipit::ReviewStack.where(repository: victim_repo).count }, 1 do
    post :create, body:, as: :json
  end
  assert_response :ok
end
```
Assertions on both sides of the binding: (1) `Shipit.github(organization: 'evil-org').verify_webhook_signature` returns `true` for the forged signature (signature side verified against `evil-org`); (2) a `Shipit::ReviewStack` is created for `victim_repo` owned by `shopify` (mutation side under a different organization) — demonstrating the two sides of the equality diverge.
