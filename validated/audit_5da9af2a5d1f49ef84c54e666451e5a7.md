### Title
Cross-Repository Forged Commit Status via Webhook Signature Bound to Attacker-Controlled Organization, Not to the Repository the Status Handler Writes - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
This is a Shipit analog of the RSK "duplicated logs" defect: a security-relevant field is acted upon by application logic while never being covered by the mechanism meant to authenticate it. In Shipit, `WebhooksController#verify_signature` picks the `webhook_secret` (and thus the entity whose authenticity is being checked) using the attacker-controlled `repository.owner.login` field from the payload, while `Status::StatusHandler#process` — the code that actually mutates state — ignores the repository entirely and matches solely on commit `sha` across the whole installation. This decouples "the organization that authenticated" from "the repository/stack that is written," exactly the binding the rules identify as the exploitable analog.

### Finding Description
`verify_signature` derives the GitHub App/secret to check against from the payload itself, before the payload is authenticated: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` unconditionally returns `true` when the resolved organization has no `webhook_secret` configured: [3](#0-2) 

Multi-organization deployments are officially supported and `webhook_secret` is documented/shown as an optional, frequently-nil field per organization: [4](#0-3) [5](#0-4) 

Once the request clears (or trivially bypasses) `verify_signature`, `WebhooksController#create` dispatches the full, attacker-supplied JSON body to handlers: [6](#0-5) 

Most handlers scope their effect to the repository named in `repository.full_name` via `Handler#stacks`/`#repository_name`: [7](#0-6) 

But `StatusHandler#process` does **not** scope to a repository at all — it looks up commits purely by `sha` across the entire database and writes a status to every matching commit, regardless of which stack/repository owns that commit: [8](#0-7) 

So the binding that should hold — "organization authenticated == repository/commit written" — is broken twice over:
1. The authenticating organization is self-declared by the attacker via `repository.owner.login`, independent of `repository.full_name`.
2. Even ignoring (1), `StatusHandler` never consults `repository.full_name`/`repository.owner` at all; it writes to whatever commit shares the given `sha`, anywhere in the installation.

### Impact Explanation
A commit status write is not cosmetic: creating a `Status` record fires `after_create`/`after_commit` callbacks that enable CI on the stack and schedule continuous delivery, and success statuses drive `ProcessMergeRequestsJob`, which can merge queued pull requests: [9](#0-8) [10](#0-9) 

Because `StatusHandler` matches purely by `sha`, an unauthenticated party who only needs to know the name of *any* organization configured on the Shipit instance with a blank `webhook_secret` (a documented, common configuration state) can forge a `success` status for a commit sha belonging to a completely different, security-sensitive stack/repository — triggering continuous deployment or unblocking a pull request merge for that stack. This satisfies the Critical/High bar: an unauthorized deploy or merge achieved without any Shipit session, API token, or knowledge of the target organization's actual webhook secret.

### Likelihood Explanation
Likelihood is High: no credentials are required beyond the public knowledge that an organization exists in the instance's `github` config without a `webhook_secret` (the setup docs present this as an acceptable, optional configuration, and multi-org configurations are explicitly supported). The `/github/webhooks` endpoint is unauthenticated by design (it's meant to receive GitHub's calls), and `StatusHandler` requires only a valid `sha` to exist somewhere in the instance — sha values are often public (visible on GitHub, PRs, commit lists) and not secret.

### Recommendation
- Bind the organization used for `verify_webhook_signature` to the same repository the handler will act upon, and reject requests where `repository.full_name`'s owner does not match the verified `repository.owner.login`.
- Scope `StatusHandler#process` (and any other handler mutating state) to commits belonging to the repository named in the payload (via `stacks`/`repository_name`), not just a global `sha` match.
- Require and enforce `webhook_secret` for every configured organization, or fail closed instead of returning `true` when it is blank.
- Add regression tests asserting that a status webhook cannot affect commits outside the repository claimed/authenticated in the same payload.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgNoSecret` (no `webhook_secret`) and `OrgTarget` (has a stack with `continuous_deployment: true` and a pending/queued merge request whose head commit sha is `deadbeef`).
2. As an unauthenticated attacker, `POST /github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "deadbeef",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "OrgNoSecret" }, "full_name": "OrgNoSecret/unrelated-repo" }
}
```
No valid `X-Hub-Signature` is needed because `Shipit.github(organization: 'OrgNoSecret').verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
3. `WebhooksController#create` dispatches to `StatusHandler`, which finds `Commit.where(sha: 'deadbeef')` — the commit belonging to `OrgTarget`'s stack — and calls `create_status_from_github!`, creating a `success` status (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`).
4. The new success status enables CI, schedules continuous delivery, and enqueues `ProcessMergeRequestsJob` for `OrgTarget`'s stack, potentially auto-deploying or auto-merging code the attacker never had access to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
