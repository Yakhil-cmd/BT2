### Title
Tokens transferred directly to the pool are permanently locked — cash accounting is storage-based and no sweep exists - (File: contracts/pool/src/cache/cash.rs)

### Summary
The ExchangeProxy bug class — value accepted by the contract that no code path can return — maps onto the pool's physical token balance versus its accounting `cash`. All inflows (supply, repay, flash repayment, recapitalize) credit `cash` by the declared amount, and all outflows debit it, but nothing ever reconciles the actual token balance against `cash`, and no entrypoint pays out uncredited surplus. A user who transfers a market asset straight to the pool address loses it permanently.

### Finding Description
The pool tracks liquidity purely in storage. `Cache::credit_cash`/`debit_cash` mutate a stored `cash` field, and `transfer_out` is the only outbound path, always tied to a mutation a caller earned (withdraw, borrow, liquidation, flash payout). [1](#0-0) 

Every inbound flow is exact-receipt by design:

- `repay` and `recapitalize` refund the excess to the payer within the same call — `recapitalize::accounting` applies only `min(amount, backing_shortfall)` and transfers `amount - applied` back. [2](#0-1) 
- Flash loans assert exact balance equality at three points and pull repayment via `transfer_from`, so they neither credit nor release stray balance. [3](#0-2) 
- Solvency and liquidity guards (`require_backed_market`, `backing_shortfall`, `require_liquidation_buffer`) read `cache.cash()`, never `token::balance`. [4](#0-3) 

Consequently `token.balance(pool) - cash` surplus accrues no shares, no debt reduction, no revenue, and is not counted toward `backing_shortfall`. There is no skim, sweep, or rescue entrypoint anywhere in the pool's op set (`supply`, `withdraw`, `borrow`, `repay`, `seize`, `flash`, `recapitalize`, `revenue`, `strategy`, `net_settle`, `market`), and protocol recipients are deliberately blocked — borrow/withdraw `to` the pool or controller reverts `InvalidFlashloanReceiver` precisely because such funds are unrecoverable. [5](#0-4) 

Unlike EVM, a Soroban contract cannot receive tokens via `msg.value`, so the only stranding path is a deliberate `token.transfer(user → pool, amount)` — which is within reach of any unprivileged address and irreversible.

### Impact Explanation
Permanent freezing of user funds. Tokens sent directly to the pool inflate its physical balance but not `cash`; suppliers cannot withdraw them (withdrawals are capped by `require_reserves` on accounting cash), recapitalize only refunds the payer's own excess within its call, and revenue claims draw on minted revenue shares, not surplus balance. The donation is unrecoverable by any user-reachable path. Severity is capped at Medium: the loss is self-inflicted and requires the sender to bypass every crediting entrypoint.

### Likelihood Explanation
Low. No controller or pool entrypoint silently accepts tokens — supply pulls the exact authorized amount, repay/recapitalize refund overpayment — so stranding requires the user to call `token.transfer` to the pool address out-of-band (mistaken address, attempted "donation," or an integrating contract misrouting a payout to the pool instead of the user). The protocol itself already treats the pool/controller as forbidden recipients, acknowledging the stranding risk.

### Recommendation
Either accept-and-document the stuck-surplus behavior, or add a governance-callable sweep that transfers `token.balance(pool) - cash` for a market to a treasury address, and/or surface the pool/controller rejection pattern already used for `to` to any future flow that could credit the pool as a recipient.

### Proof of Concept
```rust
// env: pool contract P for market asset T, accounting cash = C,
// token::balance(P) == C.
let user = /* any address */;
token::Client::new(&env, &T).transfer(&user, &P, &amount);

// After the transfer:
// token::balance(P) == C + amount
// cache.cash()     == C   (storage untouched)

// No path recovers `amount`:
// - withdraw/borrow/flash cap outflows at `cash` via require_reserves / require_liquidation_buffer
// - recapitalize::accounting refunds only `amount - applied` of *its own* call's transfer
// - backing_shortfall uses cash + debt, ignoring the surplus
// - no sweep/skim/rescue entrypoint exists in contracts/pool/src/ops/*
assert_eq!(token::Client::new(&env, &T).balance(&P), C + amount);
// `amount` is stranded permanently.
```

    /// Increases accounting cash by `amount`. Rejects negative amounts and overflow.
    pub(crate) fn credit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.cash = self
            .cash
            .checked_add(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

    /// Decreases accounting cash by `amount`. Rejects negative amounts or
    /// insufficient reserves.
    pub(crate) fn debit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.require_reserves(amount);
        self.cash = self
            .cash
            .checked_sub(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

    /// Transfers `amount` of the market asset from the pool to `recipient`.
    ///
    /// Rejects negative amounts; zero is a no-op. Does not adjust accounting cash.
    pub(crate) fn transfer_out(&self, recipient: &Address, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        if amount == 0 {
            return;
        }
        let tok = token::Client::new(&self.env, &self.params.asset_id);
        tok.transfer(&self.env.current_contract_address(), recipient, &amount);
    }

/// Asset units by which supplier claims exceed cash + debt (0 if solvent).
pub(crate) fn backing_shortfall(cache: &Cache) -> i128 {
    let supplied_claim = cache.unscale_supply_floor(cache.supplied());
    let outstanding_debt = cache.unscale_borrow_ceil(cache.borrowed());
    let backing = cache.cash().saturating_add(outstanding_debt);
    supplied_claim.saturating_sub(backing).max(0)
}
