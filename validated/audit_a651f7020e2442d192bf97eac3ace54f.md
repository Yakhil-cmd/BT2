### Title
Attacker-controlled PR label injects `GIT_CONFIG_GLOBAL` into `bundle`/`ruby` dependency-step environment, enabling git-config hook RCE - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`ReviewStack#env` merges every PR label name (uppercased) as an environment-variable key set to the literal string `"true"`, with no key allowlist, and `TaskCommands#env`/`Command#unbundled_env` pass that hash unfiltered into the spawned `bundle install`/`ruby` process. An attacker who opens a PR on an `allow_all` review-stack repository and adds a label named `git_config_global` (case-insensitive) injects `GIT_CONFIG_GLOBAL=true` into the dependency-step subprocess, which git resolves as a path relative to the process cwd (the attacker's own checked-out fork), letting the attacker supply a malicious global git config that executes on any git invocation made by the toolchain.

### Finding Description
The broken binding: the set of environment variable **keys** reaching `PTY.spawn` for a dependency step should equal `{keys defined by the deploy spec's declared variables}`, but in practice it equals `{keys defined by the deploy spec} ∪ {uppercased PR label names}` because no allowlist is applied.

Path:
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` on top of `super` (the stack's stored env), with no key filtering. [1](#0-0) 
- Any GitHub user opening a PR can name their own label arbitrarily and add it themselves (`Array.new(pull_request["labels"]).map { |label| label["name"] }`, used purely to gate provisioning under `allow_with_label`/`prevent_with_label`, but the labels themselves flow unconditionally into `ReviewStack#env` for `allow_all` repos too). [2](#0-1) 
- `TaskCommands#env` merges `@stack.env` (i.e., `ReviewStack#env`) directly into the dependency-step environment with no `EnvironmentVariables.permit` call: `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)`. [3](#0-2) 
- `install_dependencies` builds `Command.new(command_line, env:, chdir: steps_directory)` using that unfiltered `env`. [4](#0-3) 
- `Command#unbundled_env` merges `@env.stringify_keys` on top of `BASE_ENV`/`PATH` with **no key allowlist whatsoever**, and `Command#start` spawns `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`. [5](#0-4) 
- By contrast, `EnvironmentVariables#permit` (used for `task.env`/`deploy.env` set via UI/API) does enforce an allowlist derived from `deploy.yml` variable definitions, but this is never applied to `@stack.env`. [6](#0-5) 

Exploit flow: attacker opens a PR on a repo with `review_stacks_enabled` and `provisioning_behavior: allow_all`; a `ReviewStack` is provisioned and checked out into `steps_directory` (the attacker's fork content). Attacker adds a label named e.g. `Git_Config_Global`. When the stack runs `install_dependencies` (a `bundle install`/`ruby` step from the deploy spec), the spawned process environment includes `GIT_CONFIG_GLOBAL=true`. Since the value `"true"` is a relative path, git resolves it relative to the subprocess's working directory — the attacker's own checked-out repository — where the attacker has committed a file literally named `true` containing a malicious global git config (e.g., a `core.fsmonitor`, `credential.helper`, or a smudge/clean filter that shells out to attacker code). Any subsequent git invocation made by bundler/ruby toolchain during the dependency step (git-sourced gems, `git rev-parse`, etc.) loads this attacker-controlled config and executes the attacker's command, achieving RCE on the Shipit deploy host under whatever privileges the Shipit worker has (including its `GITHUB_TOKEN`).

No existing guard blocks this: `verify_signature`/`drop_unhandled_event` only validate webhook authenticity (irrelevant — label additions are legitimate, signed PR events from the attacker's own repo); `ExplicitParameters` schemas validate payload shape, not label content; `EnvironmentVariables#permit` is never invoked on `@stack.env`; there is no denylist of dangerous variable names (`GIT_CONFIG_GLOBAL`, `RUBYOPT`, `LD_PRELOAD`, etc.) anywhere in `Command`, `Commands`, `TaskCommands`, or `ReviewStack`.

### Impact Explanation
Arbitrary command execution on the Shipit deploy host, triggerable by any unprivileged GitHub user who can open a PR and add a label on a repository configured with review stacks + `allow_all` (or `allow_with_label`, since after provisioning the label mechanism still flows unfiltered into env regardless of behavior). This grants the attacker code execution in the context of the Shipit worker process, exposing `GITHUB_TOKEN`, other stacks' deploy secrets reachable from that host, and the ability to pivot to mutate/deploy other stacks. This matches the "Critical - RCE on the deploy host via `Command`/`PTY.spawn`" category. The attack is repeatable against any repository with review stacks enabled that runs a `ruby`/`bundle` dependency step and where dependency resolution shells out to git (a very common case for Gemfiles with git sources, or bundler internally calling git).

### Likelihood Explanation
Preconditions: target repository must have `review_stacks_enabled: true` and `provisioning_behavior` allowing the attacker's PR to provision a stack (`allow_all` trivially; `allow_with_label` also works since the attacker controls their own labels). The deploy spec must include a `ruby`/`bundle` dependency step that shells out to git (default for most Ruby projects via Bundler's git-source resolution or version-control detection). Attacker cost is minimal: open a PR from a fork, add a self-controlled label, commit a file named `true` with malicious git config content. No secrets, sessions, or privileged roles are required. This is highly feasible and repeatable per PR/label add.

### Recommendation
- Do not merge raw PR label names into the process environment at all, or if needed, strictly allowlist a small, fixed set of safe boolean flag names and reject/strip any label name matching known dangerous environment variables (`GIT_CONFIG_*`, `RUBYOPT`, `LD_PRELOAD`, `BUNDLE_*`, `HOME`, `PATH`, etc.).
- Apply `EnvironmentVariables#permit` (driven by the deploy spec's declared variable allowlist) to `@stack.env` inside `TaskCommands#env`, exactly as already done for `task.env`/`deploy.env`.
- As defense-in-depth, add an explicit denylist in `Command#unbundled_env` / `Commands#git` that strips known loader/toolchain-hijacking variables (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `RUBYOPT`, `RUBYLIB`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, etc.) before merging `@env` into the spawned process.

### Proof of Concept
Minitest outline (`test/models/shipit/review_stack_test.rb` / `test/unit/task_commands_test.rb`):
```ruby
test "PR label injects GIT_CONFIG_GLOBAL into dependency-step env" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  stack = ReviewStack.create!(repository:, environment: "pr1", branch: "attacker-branch")
  pull_request = PullRequest.create!(stack:, number: 1, labels: ["git_config_global"])

  # Binding under test: env key set == deploy-spec-declared variables (expected)
  # vs env key set actually reaching bundle/ruby dependency step.
  assert_not_includes stack.class.superclass.instance_method(:env).bind(stack).call.keys, "GIT_CONFIG_GLOBAL"
  assert_includes stack.env.keys, "GIT_CONFIG_GLOBAL"
  assert_equal "true", stack.env["GIT_CONFIG_GLOBAL"]

  task = create_task(stack:) # helper building a Task with definition action 'deploy'/'install_dependencies'
  commands = TaskCommands.new(task)
  command = commands.install_dependencies.first

  # Assert the fork-controllable key reaches the spawned bundle/ruby process env
  assert_equal "true", command.env["GIT_CONFIG_GLOBAL"]
  assert_equal "true", command.unbundled_env["GIT_CONFIG_GLOBAL"]
end
```
This proves the equality that should hold (`command.env.keys` ⊆ deploy-spec-declared variable names) is violated: `GIT_CONFIG_GLOBAL`, derived purely from an attacker-chosen PR label, is present in the environment handed to `PTY.spawn` for the `bundle`/`ruby` dependency step.
