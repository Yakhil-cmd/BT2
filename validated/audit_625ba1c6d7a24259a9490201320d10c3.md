### Title
Webhook signature verified against attacker's own organization while stack sync is dispatched using an unverified `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's HMAC secret to validate a webhook payload against using `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Once the HMAC check passes, the *same, attacker-supplied* JSON payload is handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and handlers (e.g. `PushHandler`, inheriting `Handler#stacks`/`#repository_name`) locate the target `Stack`/`Repository` using a *different* field of the same payload: `payload.dig('repository', 'full_name')`. Nothing binds `repository.full_name` to `repository.owner.login`/the organization whose secret validated the signature.

### Finding Description
In a multi-tenant Shipit deployment, `secrets.github` holds one entry per GitHub organization, each with its own `app_id`, `installation_id`, and `webhook_secret` (see `config/secrets.development.shopify.yml:5-23`). `Shipit.github(organization:)` (`lib/shipit.rb:170-181`) and `github_app_config` (`lib/shipit.rb:196-200`) resolve the secret to use purely from the organization name string.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` (`webhooks_controller.rb:59-62`) reads `params.dig('repository', 'owner', 'login')` from the *same request body* being verified. This is fine as a lookup key by itself (GitHub always sends its own values, and the HMAC over the full raw body still guarantees the payload is unmodified once verified) — but it establishes an equality binding: `organization used to fetch webhook_secret == repository.owner.login used to verify` should also equal `repository.full_name used to act`.

After verification succeeds, `Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and `Handler#stacks` (`handler.rb:32-34`) look up the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a *separate* field of the payload, never cross-checked against `repository.owner.login`/the organization whose secret authenticated the request.

Because Shipit's GitHub App webhook secret is scoped per-organization (not per-repository), any organization admin who legitimately owns their own GitHub App installation (and therefore legitimately knows their own `webhook_secret`) can send a request to `/webhooks` where:
- `repository.owner.login = "attacker-org"` (used only to pick the secret for HMAC verification, which the attacker satisfies with their own valid secret), and
- `repository.full_name = "victim-org/victim-repo"` (used by `PushHandler`/other handlers to locate and act on a `Stack` belonging to a completely different, unrelated organization).

The binding broken: **organization that authenticated (`repository.owner.login`, checked against `attacker-org`'s `webhook_secret`) ≠ repository that is acted upon (`repository.full_name`, resolved to any `Repository`/`Stack` in the datastore)**.

### Impact Explanation
This lets an attacker who controls one legitimately-configured organization in a multi-org Shipit deployment forge `push` (or other) webhook events that are cryptographically "valid" (per their own secret) but reference a repository belonging to a different, victim organization. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) will enqueue `GithubSyncJob` against the victim's `Stack` with an attacker-chosen `expected_head_sha`; pull-request handlers similarly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and mutate `ReviewStack`s (archive/unarchive, ReviewStack provisioning) for repositories the attacker does not own. This is a cross-repository/cross-tenant write achieved without any legitimate access to the victim's GitHub organization or repository, satisfying the "cross-repository writes" critical-impact category.

### Likelihood Explanation
Requires the deployment to configure more than one GitHub organization under `secrets.github` (the documented multi-tenant schema in `lib/shipit.rb:170-200` and `config/secrets.development.shopify.yml`), and requires the attacker to be a legitimate admin/owner of at least one of those configured organizations (so they know that organization's `webhook_secret`). Given that is Shipit's supported multi-org configuration, this is a realistic operating mode, not a hypothetical.

### Recommendation
After signature verification, re-validate that `payload.dig('repository', 'owner', 'login')` (or `organization.login`) matches the owner/organization portion of `payload.dig('repository', 'full_name')` before dispatching to handlers, or bind handler repository resolution to the same organization that was used to select the webhook secret rather than trusting `full_name` independently.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, which is configured in Shipit's `secrets.github` with `webhook_secret: S`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` using their own known secret and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the signature verifies successfully (`webhooks_controller.rb:25-30`).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (`handler.rb:32-38`) and enqueues `GithubSyncJob` for the victim's `Stack`, even though the attacker never authenticated against `victim-org`'s GitHub App/secret. module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
