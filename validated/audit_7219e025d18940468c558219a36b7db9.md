### Title
Missing check that `input_vault` != `output_vault` in `Swap` allows aliased-vault swap accounting to be corrupted - (File: `programs/cp-swap/src/instructions/swap_base_input.rs`)

### Summary
The `SENDALL` bug in the referenced report is a classic "aliasing" flaw: the code credits a receiver's balance and then unconditionally zeroes/overwrites the sender's balance without ever checking whether sender and receiver are the same account, so when they coincide the two writes clobber each other and funds vanish. The analogous pattern in this Solana program is the `Swap` accounts context used by `swap_base_input` and `swap_base_output`, where `input_vault` and `output_vault` are each independently constrained to be *one of* the pool's two vaults, but nothing forces them to be *different* vaults.

### Finding Description
In the `Swap` account struct, both vault accounts carry independent `constraint`s that only check membership in `{token_0_vault, token_1_vault}`: [1](#0-0) 

There is no constraint enforcing `input_vault.key() != output_vault.key()`. Because Anchor account validation is per-account, a caller can pass the same vault `AccountInfo` for both `input_vault` and `output_vault` in a single instruction.

Downstream, `pool_state.get_swap_params(...)` is fed `ctx.accounts.input_vault.amount` and `ctx.accounts.output_vault.amount` to derive `total_input_token_amount` and `total_output_token_amount`, and the resulting curve computation is validated only via the invariant check: [2](#0-1) [3](#0-2) 

If `input_vault` and `output_vault` alias the same account, both "reserves" fed into `CurveCalculator` are read from the identical underlying balance, and the subsequent transfers both act on that single vault: [4](#0-3) 

This mirrors the `SENDALL` root cause exactly: the code performs a "credit" (deposit into `input_vault`) and a "debit" (withdrawal from `output_vault`) against what is assumed to be two distinct balances, but never checks that they are actually the same account, so the constant-product invariant is computed against a single, self-referential reserve rather than the real two-sided pool state.

Note: I was not able to fully trace the exact behavior of `get_swap_params`/`TradeDirection` resolution in `programs/cp-swap/src/states/pool.rs` within the available investigation budget (the file appears large and I could not retrieve the function body). The vulnerable *root cause* — the absence of an `input_vault != output_vault` constraint on the `Swap` accounts struct — is confirmed directly from the account definitions above, but whether `get_swap_params` or the curve math independently neutralizes this aliasing (e.g. by rejecting when both vault keys resolve to the same enum side) could not be verified with certainty.

### Impact Explanation
If unmitigated downstream, this would let any unprivileged swapper submit a single transaction with `input_vault == output_vault` (same underlying token account) while proceeding through curve math that assumes two independent reserves, potentially allowing extraction of tokens from a single vault beyond what a correct two-sided invariant would permit — i.e., theft of pool/LP funds. This would qualify as Critical/High per the theft criteria in the validation rules if confirmed exploitable.

### Likelihood Explanation
Likelihood depends entirely on whether `pool_state.get_swap_params` (in `programs/cp-swap/src/states/pool.rs`) independently guards against `input_vault == output_vault`/same trade-direction resolution. Since I could not confirm the internals of that function, I cannot assert with full confidence that the invariant check at line 180 fails to catch this case in practice — it is possible the direction-resolution logic implicitly rejects aliased vaults (e.g., by requiring input and output to map to opposite `TradeDirection` variants derived independently, which would make identical vaults resolve to the same direction and produce a degenerate/rejected result). This uncertainty should be resolved by a background agent inspecting `get_swap_params` and `TradeDirection` handling directly.

### Recommendation
Add an explicit constraint to the `Swap` account struct: `constraint = input_vault.key() != output_vault.key()`, mirroring how the `SENDALL` fix requires checking sender/receiver equality before applying balance mutations. This closes the aliasing gap regardless of what downstream curve/direction logic does.

### Proof of Concept
Conceptual PoC (requires confirming `get_swap_params` behavior, which could not be done in this session):
1. Attacker calls `swap_base_input` (or `swap_base_output`) supplying `input_vault = output_vault = token_0_vault` of an existing pool, with `input_token_account`/`output_token_account` both owned by the attacker.
2. If `get_swap_params` does not reject same-key vaults, `total_input_token_amount == total_output_token_amount` (both read from the same account balance), corrupting the constant-product computation.
3. `transfer_from_user_to_pool_vault` deposits into `token_0_vault`, then `transfer_from_pool_vault_to_user` withdraws from the same `token_0_vault`, with the net effect governed by a curve computation performed against a degenerate single-reserve state rather than the real two-token pool, potentially enabling value extraction disproportionate to the deposit.

A background Devin agent should verify this by reading `programs/cp-swap/src/states/pool.rs::get_swap_params` and `TradeDirection` resolution logic, and, if the aliasing is not otherwise rejected, add the missing `input_vault != output_vault` constraint (and equivalent test coverage) analogous to the Polygon-Hermez `SENDALL` fix.
