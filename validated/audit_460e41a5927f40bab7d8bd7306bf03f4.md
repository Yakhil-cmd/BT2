### Title
Cross-stack authorization bypass in `Api::CCMenuController` lets a stack-scoped `ApiClient` token read any other stack's deploy state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method to bypass the stack-scoping enforcement that every other API endpoint relies on, breaking the binding between "the stack an `ApiClient` token is authorized for" and "the stack the endpoint actually touches."

### Finding Description
`Shipit::Api::BaseController` centralizes stack authorization for all API endpoints through two private methods:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

When an `ApiClient` is scoped to a specific stack (`ApiClient#stack_id` present), `stacks` restricts the queryable set to only that stack, so `stacks.from_param!` raises a not-found error for any other `stack_id` param. This is the enforcement mechanism relied on across `Api::StacksController`, `Api::DeploysController`, etc., and is explicitly exercised by tests such as "an api client scoped to a stack will only see that one stack" and "#index returns a list of stacks filtered by repo and api client." [2](#0-1) [3](#0-2) 

The permission check itself, `ApiClient#check_permissions!`, only verifies that the string `"read:stack"` is present in the client's `permissions` array — it never checks `stack_id` at all:

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [4](#0-3) 

The actual stack-boundary enforcement is entirely the controller's responsibility, via `stack`/`stacks`. However, `Api::CCMenuController` overrides `stack` with a version that ignores `current_api_client.stack_id` completely:

```ruby
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end

private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

`require_permission :read, :stack` still runs before `show`, but as shown above it only checks the permission string, not the stack identity. Since `Stack.from_param!` performs an unrestricted lookup by `repo_owner/repo_name/environment` with no `stack_id` filter, any authenticated `ApiClient` — even one deliberately scoped to a single stack with only `read:stack` — can pass an arbitrary `stack_id` in the route (`GET /api/stacks/*stack_id/ccmenu`, defined at `config/routes.rb:28`) and successfully read that other stack's latest deploy/rollback status.

### Impact Explanation
This breaks the equality that should hold for every API surface: `ApiClient#stack_id == stack acted upon`. A token that is supposed to authorize read access to exactly one stack (a supported, tested configuration in this engine, e.g., fixture `here_come_the_walrus`) can be used to disclose deploy state — latest deploy id, running/completion status, ended-at timestamp — of any other stack in the installation, including stacks the token's owner has no legitimate visibility into. This is an authorization-scope escalation / unauthorized cross-stack read of stack deploy state, matching the "High - escalation into ... unauthorized read of stack state, task streams or deploy output" impact category.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (a first-class, tested feature of `ApiClient#stack_id`) to less-trusted integrations (e.g., CI dashboards, status pages) with only `read:stack` permission. No special privilege beyond possessing such a legitimately-scoped token is required; the attacker simply changes the `stack_id` segment of the URL. No timing window or race condition is needed — the bypass is deterministic.

### Recommendation
Remove the private `stack` override in `Api::CCMenuController` (and the equivalent one in `CCMenuUrlController` if scoping is intended there too) so it inherits `Api::BaseController#stack`, which applies `stacks.from_param!` and therefore honors `current_api_client.stack_id`. If a distinct lookup is required, it must still be built from `stacks` (the scoped relation) rather than `Stack` directly.

### Proof of Concept
Using a stack-scoped API client such as the `here_come_the_walrus` fixture (`stack: shipit`, `permissions: ['read:stack']`):

1. Authenticate to the API with `here_come_the_walrus`'s token via HTTP Basic Auth.
2. Confirm scoping works elsewhere: `GET /api/stacks` returns only the `shipit` stack (as asserted in `test/controllers/api/stacks_controller_test.rb:217-223`).
3. Call the CCMenu endpoint for a different stack the token is not scoped to:
   `GET /api/stacks/<other_owner>/<other_repo>/<other_env>/ccmenu`
4. The response renders `shipit/ccmenu/project` XML containing that other stack's latest deploy/rollback id, status, and timestamp — despite the token being scoped only to `shipit`, because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unconditionally instead of `stacks.from_param!`.
