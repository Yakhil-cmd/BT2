### Title
Cross-repository status injection via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming `status` webhook by bare SHA across the entire `commits` table, with no scoping to the repository that authenticated the webhook. Because Shipit imports one `Commit` row per `(stack_id, sha)` and the same SHA can legitimately exist for multiple stacks (forks, mirrors, shared history, multiple stacks tracking the same repo), a webhook that is validly signed for repository A can write a `Status` (context `sonarqube`, state `failure`) onto a `Commit` belonging to an unrelated stack B, changing that stack's deployability/blocking state.

### Finding Description
The broken binding: the invariant claimed is `status.stack_id == authenticated_repository(payload).stack_id` for every `Status` row created from a webhook. In `StatusHandler#process`: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` iterates **every** `Commit` row with that SHA, regardless of which repository/stack it belongs to. `Commit#create_status_from_github!` then writes the status using `commit.stack_id`: [2](#0-1) 

`Status.replicate_from_github!` persists `stack_id`, `state`, `context`, etc., directly from the untrusted payload fields, and after-create hooks (`enable_ci_on_stack`, `schedule_continuous_delivery`) then act on whichever stack the matched `Commit` belongs to: [3](#0-2) 

`Commit` is `belongs_to :stack` (one row per stack/sha pair), so if the victim stack already has a `Commit` row for a SHA that is also present in an attacker-controlled repository (e.g. a public fork sharing history with the upstream repo, or any repo whose commit content happens to match), the attacker can:
1. Ensure the SHA exists in their own repo (fork retains identical commit objects/SHAs from upstream).
2. Create a GitHub status (`context: sonarqube`, `state: failure`) on that SHA via their own repo/account, which GitHub relays as a legitimately signed `status` webhook for the attacker's own repository.
3. `WebhooksController#verify_signature` only checks the signature against `Shipit.github(organization: repository_owner)` for the *attacker's own* repository/org — it validates correctly, because the webhook genuinely originated from GitHub for the attacker's own repo.
4. `StatusHandler#process` then matches and mutates the victim's unrelated `Commit`/stack because the lookup is by bare SHA only, with no `stack_id`/`repository` filter.

Existing guards do not catch this: `verify_signature` authenticates *the sender's own repository*, not the SHA's ownership; the `ExplicitParameters` schema only validates payload shape, not scope; and `StatusHandler` performs no cross-check against `params.repository.full_name` or `params.name` (GitHub's `status` payload includes the originating `repository`/`name`, but the handler never uses it to filter `Commit.where`). This is a real, distinct bug from the described "review_stacks_enabled provisioning precedence" issue in the prompt — the exploit works purely on an existing, non-review stack and does not depend on provisioning behavior at all.

### Impact Explanation
A single legitimately-signed webhook from an attacker-controlled repository can create a `Status` row on a completely unrelated stack's commit, changing that commit's required-context state (e.g., flipping a required `sonarqube` context to `failure`, which can block deploys via `Commit#blocked?`/`stack.blocking_statuses`, or conversely inject a fabricated `success` to unblock/allow a deploy). This matches the rule's Critical category: "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any stack whose commits share a SHA with an attacker-reachable repository, and the blast radius spans all stacks/tenants sharing that Shipit instance's commit history overlap.

### Likelihood Explanation
Preconditions: the attacker needs (a) a GitHub repository under their control capable of sending a validly signed `status` webhook to the Shipit instance (i.e., the Shipit GitHub App/webhook integration installed on that repo — feasible if the app is installable by any GitHub org/user, e.g., a public integration or a repo the attacker can install the app on), and (b) a SHA that also exists as a `Commit` row for the victim stack (trivially true for public forks sharing upstream history, or for any repo where the attacker can reproduce identical commit content). No Shipit session, API token, or GitHub secret is required — this is exactly the unauthenticated `POST /webhooks` path with a real, GitHub-issued signature for the attacker's own repo. This is feasible and repeatable at low cost against any target where SHA overlap can be arranged.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers) to the repository/stack that authenticated the webhook — e.g., resolve the `Repository`/`Stack` from `params.repository.full_name` (as `PullRequest` handlers already do via `Shipit::Repository.from_github_repo_name`) and filter `Commit.where(sha: params.sha, stack: repository.stacks)` before calling `create_status_from_github!`, rejecting or ignoring matches outside that scope.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status webhook does not mutate a commit belonging to a different stack/repo" do
          victim_stack = shipit_stacks(:shipit) # review_stacks_enabled: false, unrelated repo
          shared_sha = "deadbeef" * 5 # arbitrary 40-char sha shared across repos

          victim_commit = victim_stack.commits.create!(
            sha: shared_sha,
            author: shipit_users(:shipit),
            committer: shipit_users(:shipit),
            authored_at: Time.now,
            committed_at: Time.now
          )

          # Binding under test (before): victim_commit has no failing 'sonarqube' status
          assert_not victim_commit.statuses.exists?(context: 'sonarqube', state: 'failure')

          # Attacker-authenticated payload for an UNRELATED repository, same sha
          payload = {
            'sha' => shared_sha,
            'state' => 'failure',
            'context' => 'sonarqube',
            'branches' => [],
            'repository' => { 'full_name' => 'attacker/unrelated-repo' }
          }

          StatusHandler.new(payload).process

          # Binding under test (after): if it flipped, the invariant "status affects only the
          # authenticating repository" is broken.
          assert victim_commit.reload.statuses.exists?(context: 'sonarqube', state: 'failure'),
                 "victim stack's commit was mutated by a webhook for an unrelated repository"
        end
      end
    end
  end
end
```
