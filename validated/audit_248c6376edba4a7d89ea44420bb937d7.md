### Title
Silent field/operator validation gap in `Condition.from_dict` lets repo-shipped/explicit rules impersonate working `block` rules while never matching - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Condition.from_dict` accepts arbitrary `field`/`operator`/`pattern` values from rule frontmatter with no validation, unlike the legacy `pattern:` path in `Rule.from_dict`, which deterministically derives a known-good `field` from `event`. A rule authored in the "advanced" explicit-`conditions` form with a mistyped or nonexistent `field`/`operator` silently never matches (`_check_condition` / `_extract_field` in `rule_engine.py` return `False`/`None` with no error, warning, or exception), so a `block` rule that looks correct in review is permanently inert, while the legacy single-`pattern` form cannot produce this failure mode.

### Finding Description
`Rule.from_dict` supports two mutually exclusive rule authoring styles:
- Legacy: `pattern:` + `event:` → `field` is computed deterministically (`command`/`new_text`/`content`) and `operator` is hardcoded to `regex_match`. [1](#0-0) 
- Explicit: `conditions:` list → each item is passed straight into `Condition.from_dict`, which uses `.get()` with silent defaults and performs no validation of `field` or `operator` values. [2](#0-1) 

At evaluation time, `RuleEngine._extract_field` returns `None` for any `field` value it doesn't recognize, and `_check_condition` treats a `None` field value as "no match" with no logging: [3](#0-2) 
Similarly, an unrecognized `operator` string falls through to the `else` branch and silently returns `False`: [4](#0-3) 

`load_rule_file` only catches `IOError/OSError/PermissionError/ValueError/KeyError/AttributeError/TypeError/UnicodeDecodeError`, none of which are ever raised by this path since `Condition.from_dict`/`_extract_field`/`_check_condition` never throw - so there is no "Warning: Failed to parse" message a reviewer could notice. [5](#0-4) 

Because a rule with zero true-evaluating conditions simply never fires (`_rule_matches` requires all conditions to hold, and there is no distinct "this rule is misconfigured" signal), a rule file placed in the repository (or generated by `/hookify`, per `plugins/hookify/commands/hookify.md`, which explicitly instructs writing the `conditions:` block from LLM-extracted `field`/`operator`/`pattern` values) can declare `action: block`, appear syntactically identical to a working security rule, yet be permanently a no-op if any `field`/`operator` string is subtly wrong (typo, wrong case field name, nonexistent event-specific field, etc.). The equivalent legacy `pattern:` rule form cannot express this failure mode because `field` is never taken from attacker-controlled/free-form frontmatter text - it is computed from a small enumerated set based on `event`.

This breaks the stated invariant that legacy and explicit rule forms must produce the same effective security semantics: the legacy form is fail-safe with respect to `field` typos, while the explicit form is fail-silent-open.

### Impact Explanation
A hookify `block` rule is a local, opt-in guard against dangerous or sensitive actions (e.g., blocking edits to `.env`, blocking `rm -rf`, blocking disclosure of secrets/diffs). If such a rule is shipped in a repository (or generated) using the explicit `conditions:` form with an unintentionally or maliciously broken `field`/`operator`, the rule silently never triggers. This lets subsequent Bash/Edit/Write/MultiEdit/Stop operations that the rule was meant to block proceed unimpeded, potentially resulting in disclosure of sensitive code, tokens, diffs, or local files to an unintended sink, while giving the illusion that a protective rule is active. The severity is bounded by the fact that hookify rules are advisory/local guardrails, not the primary security boundary of Claude Code, and the attacker needs the ability to place a rule file (repo write, or influence `/hookify` generation) rather than gaining direct code execution.

### Likelihood Explanation
Any contributor (or attacker with repository write access, or via prompt-injection influencing the `/hookify` conversation-analyzer agent output) can add a `.claude/hookify.*.local.md` file with an explicit `conditions:` block that contains a subtly wrong `field`/`operator` value. No validation exists anywhere in `Condition.from_dict`, `Rule.from_dict`, or `RuleEngine` to catch this, and no warning is printed, so it is trivially reproducible and would not be flagged during normal review of the YAML (it looks like a valid rule).

### Recommendation
- In `Condition.from_dict`, validate `field` against the known enumerated set (`command`, `file_path`, `new_text`/`new_string`, `old_text`/`old_string`, `content`, `reason`, `transcript`, `user_prompt`) and `operator` against the supported operator set; raise a `ValueError` on unknown values so `load_rule_file`'s existing exception handling surfaces a clear "Warning: Failed to parse" message.
- In `RuleEngine._check_condition`/`_extract_field`, log (to stderr) when a condition references an unrecognized `field` or `operator` rather than silently returning `False`/`None`, so misconfigured `block` rules are visibly flagged instead of failing open.
- Add a startup/self-check (e.g., in `load_rules`) that warns when an `action: block` rule has zero conditions or contains an unrecognized field/operator, since this is a security-relevant misconfiguration.

### Proof of Concept
Unit test plan (extends existing `config_loader.py`/`rule_engine.py` test patterns):
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

# Explicit-form "block" rule with a typo'd field name (looks legitimate)
frontmatter = {
    "name": "block-env-secrets",
    "enabled": True,
    "event": "file",
    "action": "block",
    "conditions": [
        {"field": "flie_path", "operator": "regex_match", "pattern": r"\.env$"},  # typo: flie_path
    ],
}
rule = Rule.from_dict(frontmatter, "Blocked: editing .env file")

engine = RuleEngine()
input_data = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Write",
    "tool_input": {"file_path": ".env", "content": "API_KEY=secret"},
}

result = engine.evaluate_rules([rule], input_data)

# Expected (buggy) behavior today: result == {} (no block, no warning at all,
# no indication the rule silently failed) -- the .env write is allowed.
assert result == {}

# Compare against the legacy-equivalent rule, which cannot suffer this typo class:
legacy_frontmatter = {
    "name": "block-env-secrets-legacy",
    "enabled": True,
    "event": "file",
    "action": "block",
    "pattern": r"\.env$",
}
legacy_rule = Rule.from_dict(legacy_frontmatter, "Blocked: editing .env file")
legacy_result = engine.evaluate_rules([legacy_rule], input_data)
# legacy_result correctly blocks: {"hookSpecificOutput": {..., "permissionDecision": "deny"}, ...}
assert legacy_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
```
Expected assertion after fix: constructing `Condition.from_dict({"field": "flie_path", ...})` raises `ValueError`, `load_rule_file` logs a parse warning and returns `None` (rule excluded), preventing the broken/deceptive `block` rule from being silently loaded and bypassed.
