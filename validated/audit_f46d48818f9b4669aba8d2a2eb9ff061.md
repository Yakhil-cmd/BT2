### Title
Null-pointer dereference in `handleTrigger()` when checking for repeated primary triggers - crashes the whole node ([File: aa_composer.js])

### Summary
`aa_composer.js` `handleTrigger()` unconditionally indexes `storage.assocStableUnits[trigger.unit]` without checking that the entry exists, then immediately reads `.count_aa_responses` off it. If the lookup misses, this throws an uncaught `TypeError: Cannot read properties of undefined`, which is not caught anywhere in the AA-processing call chain and is ultimately caught only by the global `process.on('uncaughtException', ...)` handler in `network.js`, which explicitly re-throws to crash the process. This is directly analogous to CVE-2018-1172: a specific, reachable code path dereferences a value that can be null/undefined, causing an unauthenticated remote condition (any node processing AA triggers) to crash the daemon — a denial of service.

### Finding Description
In `handleTrigger()`: [1](#0-0) 
```
// skip this check for dry-run which uses genesis unit as trigger unit
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && storage.assocStableUnits[trigger.unit].count_aa_responses && mci >= constants.pemCurvesFixMci)
    return bounce('a second primary trigger from the same unit is not allowed');
```
This is reached for every primary AA trigger (`bSecondary` false) processed through `handlePrimaryAATrigger()` → `handleTrigger()`, which is the normal path executed whenever any unprivileged user posts a unit that pays an AA and that unit becomes a stable trigger: [2](#0-1) 

`storage.assocStableUnits` is a memory cache of unit properties for units that are considered "stable" in the node's current view; it is populated/evicted as the stability point advances and as memory is pruned (see the numerous read/write/delete sites across `storage.js`, `main_chain.js`, `graph.js`, `headers_commission.js`, `paid_witnessing.js`, `writer.js`). `handlePrimaryAATrigger()` obtains the trigger's `unit` from the `aa_triggers` table (populated when the unit became stable) and calls `handleTrigger()`, which assumes `storage.assocStableUnits[trigger.unit]` is present. Elsewhere in the same function, the code explicitly guards against this assumption failing: [3](#0-2) 
```
let objUnitProps = storage.assocStableUnits[unit];
if (!objUnitProps)
    throw Error(`handlePrimaryAATrigger: unit ${unit} not found in cache`);
```
That is, the surrounding code already anticipates that `assocStableUnits[unit]` can be missing (e.g., under memory pruning, cache eviction, unusual timing between when a unit becomes stable/queued as a trigger and when the in-memory cache still holds its properties, or on a node that restarts and rebuilds caches lazily). But the check at line 1861 lacks the same guard, and instead of throwing a controlled/handled error, it throws an uncaught `TypeError` from a property access on `undefined`. This propagates out of the deeply nested async callback chain of `handleTrigger`, is not caught by any `try/catch` in the call path (the whole AA-trigger processing pipeline uses callbacks/`async`, not the promise/exception model that would let a caller catch it), and is trapped only by the process-wide `uncaughtException` handler which deliberately crashes the process: [4](#0-3) 

### Impact Explanation
Any node that runs AA logic (i.e., every full node, and any light node used for dry runs) executes `handleTrigger()` for every AA-paying unit that becomes stable. If the code path reaches line 1861 while `storage.assocStableUnits[trigger.unit]` is `undefined`, the resulting uncaught `TypeError` crashes the node process. Because AA-trigger handling occurs deterministically for every node once the triggering unit becomes stable, a crash triggered this way is not confined to a single node — every full node that reaches the same trigger processing state will crash in the same way, since it operates on consensus data (stable units and AA triggers) rather than local-only state. Repeated/automatable triggering could produce a persistent denial of service across the network's full nodes, preventing new units (in particular AA-dependent transactions) from being confirmed — this matches the "network unable to confirm new units" bar for validity.

### Likelihood Explanation
Reaching this exact line requires: (1) `trigger.unit !== constants.GENESIS_UNIT`, (2) not a dry run/estimate (`!trigger_opts.bAir`), and (3) `mci >= constants.pemCurvesFixMci` (post-upgrade behavior, so applicable to current mainnet operation). Given the accompanying defensive check just a few dozen lines earlier in the same file (`if (!objUnitProps) throw Error(...)`) for the very same cache lookup, it strongly suggests the developers are aware that `assocStableUnits[unit]` can legitimately be absent in certain conditions (cache eviction/pruning, timing windows, node restarts) — yet this second lookup was not hardened the same way. I could not fully confirm from the available code slices the exact operational trigger (e.g., pruning timing) that causes `assocStableUnits[trigger.unit]` to be empty at this specific point without deeper tracing of `main_chain.js`/`storage.js` cache-eviction logic and the precise `aa_triggers` processing order — this should be validated further with the Devin agent's ability to run and trace the code.

### Recommendation
Add a null-check before dereferencing, mirroring the existing defensive pattern in the same file:
```js
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && mci >= constants.pemCurvesFixMci) {
    var objTriggerUnitProps = storage.assocStableUnits[trigger.unit];
    if (!objTriggerUnitProps)
        throw Error("handleTrigger: unit " + trigger.unit + " not found in cache");
    if (objTriggerUnitProps.count_aa_responses)
        return bounce('a second primary trigger from the same unit is not allowed');
}
```
More broadly, review all direct property accesses on `storage.assocStableUnits[x]` throughout `aa_composer.js`, `main_chain.js`, `headers_commission.js`, and `paid_witnessing.js` for the same unguarded-lookup pattern, and consider whether AA-trigger processing failures caused by transient cache misses should be retried rather than causing an unrecoverable process crash via the global `uncaughtException` handler.

### Proof of Concept
Concrete exploitation requires reproducing the exact runtime condition under which `storage.assocStableUnits[trigger.unit]` becomes `undefined` at the moment `handleTrigger()` runs for a primary (non-secondary, non-air) trigger post `pemCurvesFixMci`. Based on the static code inspection performed here, I identified the vulnerable, unguarded dereference and its reachability from ordinary AA-trigger processing, but I was not able to execute the code or trace `main_chain.js`/`storage.js` cache eviction timing to construct a step-by-step PoC unit sequence within this read-only investigation. A Devin session with full repository access and the ability to run the test suite (e.g., extending `test/aa_composer.test.js`) would be needed to construct a concrete unit/trigger sequence that empties or races the `assocStableUnits` cache entry for a trigger unit and confirms the crash.
