### Title
Forged `pull_request` action=`labeled` webhook accepted for orgs without `webhook_secret` lets an attacker inject arbitrary environment variables into a review stack's deploy env - (File: lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb, app/models/shipit/review_stack.rb)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for the org, so `Shipit::WebhooksController#verify_signature` accepts any unsigned/forged webhook body for that org [1](#0-0) [2](#0-1) . Once accepted, `LabelCapturingHandler#capture_labels` persists attacker-supplied `pull_request.labels[].name` strings verbatim onto the matching `ReviewStack`'s `PullRequest#labels` [3](#0-2) , and `ReviewStack#env` later upcases each stored label name and injects it as a `"true"`-valued environment variable merged into the stack's deploy environment [4](#0-3) .

### Finding Description
The broken binding: the question assumes `verify_webhook_signature(sig, body) == true` should imply "this request was cryptographically authenticated as coming from GitHub for this org's repository." In reality, for an org configured with no `webhook_secret`, `verify_webhook_signature` returns `true` for *any* input, signed or not — `return true unless webhook_secret` [5](#0-4) . This is a deliberate, documented behavior of the engine (a stack administrator can opt out of signature verification by omitting the secret in configuration), not incidental code that "should" authenticate but fails to. The controller's `verify_signature` before_action calls this method keyed only on `repository_owner` from the attacker-controlled JSON body [2](#0-1) [6](#0-5) , so for a no-secret org, any request body is processed by `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [7](#0-6) .

Given that precondition, `LabelCapturingHandler` locates the review stack by `Repository.from_github_repo_name(params.repository.full_name)` and `environment: "pr#{params.number}"` [8](#0-7) [9](#0-8) , then for `action == "labeled"` on an existing, non-archived stack it overwrites `pull_request.labels` with the attacker-supplied label names verbatim, with no restriction on characters, casing, or allow-listing beyond `String` typing in the `ExplicitParameters` schema [10](#0-9) [3](#0-2) . `ReviewStack#env` later merges `label_name.upcase => "true"` for every stored label into the environment hash used at deploy/task time [4](#0-3) . Since the attacker fully controls the label-name string (a PR label the attacker names on their own fork/PR, replayed as raw JSON to `/webhooks`), they can set arbitrary environment variable *keys* (e.g. `PATH`, `RUBYOPT`, `LD_PRELOAD`, `BUNDLE_GEMFILE`) to the fixed value `"true"` for that review stack's subsequent deploys/tasks.

Existing guards do not prevent this: `verify_signature` explicitly short-circuits when no secret is set (by design), `drop_unhandled_event` only checks whether a handler is registered for the event type, and the `ExplicitParameters` schema only enforces types, not value/format restrictions on label names. This is not a case where an authentication check meant to bind the request to `repository_owner` is being bypassed by a bug — it's the intended behavior of the no-secret configuration combined with unsanitized label-to-env-var translation.

### Impact Explanation
For an org that opts out of `webhook_secret`, any internet user (no Shipit session, no GitHub app credentials) can forge a `pull_request`/`labeled` webhook naming an arbitrary environment-variable key ending up `"true"` in a specific review stack's deploy environment (`ReviewStack#env`), potentially affecting environment-dependent build/deploy commands for that stack. This matches "a payload for one repository mutating another's [stack] environment" is not applicable here (it only affects the *same* repository/org's own review stack that already has no secret), but it does allow environment-variable injection into that stack's task execution environment (`PATH`/tool-flag style variables set to `"true"`), which could influence commands run via `Command`/`PTY.spawn` for that stack's deploys depending on stack configuration (`Cap`/`Makefile` tasks reading such env vars). Repeatable per request, limited to stacks under an org explicitly configured without `webhook_secret` and only to review stacks of that same repository — not cross-tenant, since `repository_owner`/`repository.full_name` scope the write to the matching repository's own stacks.

### Likelihood Explanation
Requires the target org to be explicitly configured with no `webhook_secret` — an operator/deployment configuration choice, not a default vulnerable state introduced by this engine's code. Given that precondition, exploitation is trivial and repeatable (single unauthenticated HTTP POST, no signature required). This is consistent with `verify_webhook_signature`'s documented fallback behavior; the residual risk is entirely in `LabelCapturingHandler`/`ReviewStack#env` failing to sanitize/allow-list label-derived environment variable names, which is a real weakness but conditioned on an intentional opt-out already accepted by the operator.

### Recommendation
1. In `ReviewStack#env` (`app/models/shipit/review_stack.rb`), sanitize or allow-list label names before turning them into environment variable keys (e.g., restrict to a configured allow-list of recognized labels, or reject/escape names containing characters outside `[A-Za-z0-9_]`, and never allow labels to shadow security-sensitive variable names like `PATH`, `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`).
2. Treat the "no `webhook_secret` configured" state as high-risk in documentation/setup and consider requiring an explicit secret for any org whose stacks use `LabelCapturingHandler`-driven environment injection, since that configuration removes all webhook authentication for the org.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/label_capturing_handler_test.rb` style):
1. Configure `Shipit.github(organization: 'no-secret-org')` with a config hash lacking `webhook_secret`.
2. Create a `Shipit::Repository` for `no-secret-org/repo`, and a `Shipit::ReviewStack` with `environment: "pr1"` and an associated `Shipit::PullRequest` with `labels: []`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no `X-Hub-Signature` (or an arbitrary bogus one), and JSON body `action: "labeled"`, `number: 1`, `repository.full_name: "no-secret-org/repo"`, `pull_request.labels: [{name: "PATH"}]` (plus all other required fields per the `params` schema).
4. Assert response is `200 OK` (accepted despite invalid/missing signature) — binding check: `GitHubApp#verify_webhook_signature(nil_or_bogus_sig, raw_body) == true` for `no-secret-org`.
5. Reload the `PullRequest` and assert `pull_request.labels == ["PATH"]`.
6. Call `review_stack.env` and assert it contains `"PATH" => "true"`, demonstrating the forged, unauthenticated request mutated the stack's deploy environment.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

    end
