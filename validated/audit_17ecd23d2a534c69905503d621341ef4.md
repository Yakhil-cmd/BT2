### Title
Cross-organization Commit/Status forgery via unscoped `Commit.where(sha:)` in StatusHandler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` only verifies that the request signature matches the `webhook_secret` of the organization named in `params.dig('repository','owner','login')`, and never checks that the `sha` in the payload actually belongs to a repository owned by that organization. `StatusHandler#process` then runs `Commit.where(sha: params.sha)` with no stack/repository/organization scoping, so any org with a valid webhook secret can mutate the `Status` of a `Commit` row that belongs to a completely different org's stack.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`organization_that_signed(request) == organization_owning(Commit.find_by(sha: params.sha).stack.repository)` 

Trace:
1. `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` (line 61) and asks `Shipit.github(organization: repository_owner)` to verify the HMAC signature against that org's own `webhook_secret`. This only proves "the sender knows org X's secret" — it says nothing about which `sha` values are legitimately X's.
2. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a global, unscoped lookup by `sha` across the entire `commits` table, with no join/filter on `stack_id`, `repository_id`, or `repository_owner`.
3. Confirming this is truly unscoped: `Commit` has a unique index on `(sha, stack_id)`, not on `sha` alone (db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb), meaning the same `sha` can legitimately exist in multiple stacks/orgs, and `Commit.where(sha:)` can return rows belonging to organizations other than the one that authenticated the request.

Exploit flow: Attacker owns org `attacker-org` with a Shipit-configured `webhook_secret`. Victim org `victim-org` has a stack Shipit tracks, and some commit sha `V` exists in `Commits` (created earlier via a legitimate push/PR sync, e.g. `GithubSyncJob`/`Commit.create_from_github!`). The attacker reads `V` off the victim's public GitHub history (no auth needed), then POSTs to `/webhooks` with header `X-Github-Event: status`, a body whose `repository.owner.login` is `attacker-org` (so `verify_signature` authenticates against the attacker's own secret and succeeds), but whose `sha` field is `V`. `StatusHandler#process` finds the victim's `Commit` row for `sha: V` and calls `commit.create_status_from_github!(params)`, writing a forged `Status` (arbitrary `state`, `context`, `description`, `target_url`) onto the victim's commit.

Why existing guards don't stop this: `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema (`requires :sha, :state`, etc.) only validates payload shape, not ownership; `verify_signature`'s org resolution is entirely attacker-controlled (it reads the org name straight from the attacker's own JSON body) and is used only to select which secret to verify against — never to constrain which records can subsequently be mutated. No other check in the `status` handling path ties the verified org to the `Commit`'s stack/repository.

### Impact Explanation
This lets an attacker with a legitimate GitHub org/webhook (satisfying only the signature check for their own org) write arbitrary CI/status data onto commits belonging to unrelated organizations' stacks, as long as the sha coincidentally/deliberately matches a commit sha known to be present in Shipit's DB. Since Shipit's deploy gating (`required_statuses`, `blocking_statuses`) relies on `Status`/commit state, forging a "success" status on a victim's pending/failing commit can enable an unauthorized deploy of that commit in the victim's stack — this is a payload for one repository (attacker's) mutating another repository's/stack's commit records, matching the **Critical** category ("a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy"). The attack is repeatable against any sha the attacker can discover in a victim's public git history that happens to also exist in Shipit's `commits` table (e.g., any sha the victim previously pushed/PR'd, since Shipit records all of history's shas for a tracked branch/stack).

### Likelihood Explanation
Preconditions are low: the attacker only needs (1) their own legitimate org configured with a `webhook_secret` in Shipit (or any org — even a throwaway one Shipit is configured to trust) and (2) knowledge of a sha from the victim's public commit history that was ingested into Shipit's `Commit` table via normal sync. No Shipit credentials, sessions, API tokens, or GitHub org membership in the victim's org are required. The attacker cost is a single crafted HTTP POST with a valid HMAC computed from their own known secret. This is fully repeatable against any commit sha they can find, for as long as that sha remains in the `commits` table.

### Recommendation
`StatusHandler#process` (and any other sha-keyed handler) must scope `Commit` lookups to the repository/organization that authenticated the webhook, e.g. join through `stack.repository.owner` and only update commits whose stack's repository owner matches the verified `repository_owner`/`repository.full_name` from the payload. Concretely, pass the verified `repository_owner`/`full_name` into the handler context and change the query to something like `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: verified_owner, name: verified_repo_name })`.

### Proof of Concept
Minitest plan (test/controllers/webhooks_controller_test.rb):
```ruby
test 'status webhook cannot mutate a commit belonging to another organization' do
  victim_stack = shipit_stacks(:shipit) # owned by org "shopify" per fixtures
  victim_commit = shipit_commits(:first) # sha belongs to victim_stack
  attacker_org = 'attacker-org'

  # Stub signature verification to succeed for the attacker's own org
  Shipit.expects(:github).with(organization: attacker_org).returns(
    stub(verify_webhook_signature: true)
  )

  payload = {
    repository: { owner: { login: attacker_org }, full_name: "#{attacker_org}/attacker-repo" },
    sha: victim_commit.sha,
    state: 'success',
    context: 'ci/forged',
    description: 'forged by attacker'
  }.to_json

  assert_difference -> { victim_commit.reload.statuses.count }, +1 do
    post shipit_engine.webhooks_path,
      params: payload,
      headers: { 'X-Github-Event' => 'status', 'X-Hub-Signature' => 'sha1=whatever', 'Content-Type' => 'application/json' }
  end

  assert_equal 'success', victim_commit.statuses.last.state
  # Assert the equality that should have held but didn't:
  # organization_that_signed == 'attacker-org'
  # organization_owning(victim_commit.stack.repository) == 'shopify'
  refute_equal attacker_org, victim_commit.stack.repository.owner
end
```
This demonstrates: signature verification succeeds for `attacker-org` (org boundary holds at the HMAC level), yet `victim_commit`, owned by a different org, receives a new `Status` row — proving the WEBHOOK_PROVENANCE binding is broken.
