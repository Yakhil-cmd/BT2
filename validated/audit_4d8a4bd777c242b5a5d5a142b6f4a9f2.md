### Title
`review_stacks_enabled` is not enforced for `allow_with_label`/`prevent_with_label` provisioning modes due to operator-precedence bug in `unarchive?`/`provision?` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` (and the identical pattern in `OpenedHandler#provision?`, `LabeledHandler`, `UnlabeledHandler`) uses `A && B || C && D || E && F` without parentheses around the `review_stacks_enabled` check, so Ruby's operator precedence only gates the `allow_all` branch with `review_stacks_enabled`. When a repository's `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, review stacks are provisioned/unarchived regardless of `review_stacks_enabled`. Combined with a `pull_request` webhook whose organization has no `webhook_secret` configured, this lets an external actor trigger unauthorized `ReviewStack` creation/unarchival on a stack the operator believed was fully disabled.

### Finding Description
The broken binding, stated as an equality that the code should but does not enforce:
`repository.review_stacks_enabled == false` should imply `unarchive? == false` for every `provisioning_behavior` value. Instead:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

`&&` binds tighter than `||` in Ruby, so this evaluates as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The last two disjuncts never reference `review_stacks_enabled`. The identical pattern exists in `OpenedHandler#provision?`: [2](#0-1) 

Path: an unauthenticated `POST /webhooks` with `X-Github-Event: pull_request`, `action: "reopened"`, hits `Shipit::WebhooksController#create`, which runs `verify_signature` first via `Shipit.github(organization: repository_owner).verify_webhook_signature`. If that organization has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` returns `true` unconditionally: [3](#0-2) 
so the forged payload is accepted and dispatched to `ReopenedHandler#process`, which calls `stack.unarchive!` → `ReviewStackAdapter#unarchive!`/`#create!`, adding the stack to `Shipit::ReviewStackProvisioningQueue` and flipping `archived?`/enqueuing provisioning: [4](#0-3) 

If the operator has `review_stacks_enabled = false` but left `provisioning_behavior` at `allow_with_label` or `prevent_with_label` (e.g., because the UI/migration default for `provisioning_behavior` is independent of the `review_stacks_enabled` checkbox), the precedence bug causes `unarchive?`/`provision?` to return `true`, and a `ReviewStack` is created/unarchived and queued for provisioning via `ReviewStackProvisioningQueue.add`.

Existing guards do not stop this: `drop_unhandled_event` only filters unregistered event types, `verify_signature` is bypassed by design when no secret is configured, and the `ExplicitParameters` schema on `ReopenedHandler` only validates payload shape, not authorization. `Repository#review_stacks_enabled` is read but only correctly enforced for one of three `provisioning_behavior` branches.

### Impact Explanation
Actual demonstrable impact via this engine's own code is limited to: unauthorized `ReviewStack` creation/unarchival and enqueueing into `Shipit::ReviewStackProvisioningQueue` for a stack whose operator explicitly disabled dynamic provisioning (`review_stacks_enabled = false`). What that provisioning step actually *does* (`stack.provisioner.up`) is delegated to a host-application-defined `ProvisioningHandler`; the engine's own default (`ProvisioningHandler::Base`) is a no-op, so the "Critical - RCE" characterization in the question is not substantiated purely from these files — real-world severity depends entirely on the host application's registered `ProvisioningHandler`, which is out of this engine's code. The concretely proven impact is a state-integrity/authorization bypass: dynamic-stack provisioning proceeds against operator intent, which is a logic bug rather than a demonstrated RCE or credential-exfiltration path in this codebase.

### Likelihood Explanation
Requires two independently-controlled preconditions: (1) the target organization has no `webhook_secret` configured (an explicitly optional, operator-controlled setting per `docs/setup.md`), and (2) the repository has the specific, unusual configuration of `review_stacks_enabled: false` combined with `provisioning_behavior: allow_with_label` or `prevent_with_label` and a matching/absent label. Neither precondition is attacker-controlled; both are operator misconfigurations. Given both hold, the attacker cost is a single unauthenticated HTTP POST, fully repeatable against that stack.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three provisioning-behavior branches in `unarchive?`/`provision?` (and the equivalents in `LabeledHandler`/`UnlabeledHandler`):
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Additionally, `webhook_secret` should be mandatory (not optional) to close the unauthenticated-webhook precondition entirely.

### Proof of Concept
minitest (unit-level, no live GitHub, mirrors existing `configure_provisioning_behavior` helper in `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`):
```ruby
test "does NOT unarchive when review_stacks_enabled is false, even with allow_with_label + matching label" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # binding under test: review_stacks_enabled == false
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  # Equality that should hold: review_stacks_enabled == false  =>  stack remains archived
  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```
Running this against current code fails the assertion (stack becomes unarchived), proving the precedence bug.
