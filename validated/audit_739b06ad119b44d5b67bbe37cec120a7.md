Based on my research, I found a genuine structural analog to the Cooler bug in ocore's **attested-spender asset** mechanism, which is reachable by any asset issuer/definer through ordinary unit posting.

### Title
Asset definer can unilaterally revoke an address's attestation to freeze already-received funds of a `spender_attested` asset - (File: validation.js, storage.js)

### Summary
For assets with `spender_attested=1`, spending an existing output requires the **current** owner address to appear in the asset's attestor-approved list at the time of the spend — not merely at the time the output was created. The definer alone controls that attestor list and can update it at will via an `asset_attestors` message, with no participation or consent required from the token holder.

### Finding Description
When validating a payment of a `spender_attested` asset, ocore checks that the address that currently owns the output being spent is attested: [1](#0-0) 

This "attested" status is not fixed at the moment the output was received — it is re-evaluated against the live attestor-approved list on every subsequent spend attempt, using `storage.filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors`, which is populated from the `attestations` table filtered by the asset's current `arrAttestors`. The attestor list itself is edited exclusively by the asset's definer through the `asset_attestors` message: [2](#0-1) 

Because the check `checkAttestorList` only validates format/uniqueness of the new list, the definer can freely swap out or drop attestors (or coordinate with an attestor to revoke a previously-issued attestation) at any point after a payment has already been made to a given address, with: [3](#0-2) 

This is structurally the same bug class as the Cooler issue: one privileged counterparty in a bilateral value-transfer arrangement (there: the lender via `setRepay`+`transferOwnership`; here: the asset definer via `asset_attestors`) can unilaterally, after the fact and without the other party's consent, invalidate the condition needed for the other party to move funds they already legitimately hold — forcing those funds into a permanently unspendable state.

### Impact Explanation
Any holder of a `spender_attested` asset can have their existing balance permanently frozen if the definer (or a colluding/compromised attestor) removes their address from the attestor list after the funds were received. Since the check applies to spending, not just issuance, this is not merely "future recipients need attestation" — it retroactively locks previously valid holdings. This matches the "AA fund loss or freezing" impact category, since the affected balance becomes permanently unspendable without any recourse for the holder.

### Likelihood Explanation
Likelihood is High for any deployed `spender_attested` asset: the definer only needs to post a normal `asset_attestors` message (a single-authored unit) to alter the list, exactly analogous to how the Cooler lender only needed to call `setRepay`/`transferOwnership`. No special privileges beyond being the asset's own definer are required, and the action is indistinguishable from legitimate attestor-list maintenance, making it hard to prevent or even detect as malicious in real time.

### Recommendation
Evaluate the attestation requirement based on the attestor list and attestation status **at the time the output was created** (or last transferred), rather than re-checking against the live/current attestor list on every subsequent spend. Alternatively, require that removal of an attestor/address from the list cannot retroactively invalidate the spendability of outputs already held by previously-attested addresses (e.g., grandfather existing balances, or require a timelock/notice period before a list change takes effect for existing holders).

### Proof of Concept
1. Definer `D` issues asset `X` with `spender_attested=true` and an initial attestor list including attestor `A`.
2. Attestor `A` attests holder `H`'s address; `D`/other party sends `H` a payment of asset `X`. This passes validation per [4](#0-3) .
3. After `H`'s output is confirmed, `D` posts a new `asset_attestors` message removing `A` (or replacing the list) so that `H`'s address is no longer covered by any current attestation, per [2](#0-1) .
4. `H` now attempts to spend the previously-received output. Validation re-checks `owner_address` against the *current* `arrAttestedAddresses` and fails: [1](#0-0) .
5. `H`'s funds are permanently frozen with no way to regain spendability short of the definer voluntarily restoring the attestation — a unilateral, unconsented action by one counterparty that traps the other party's funds, mirroring the Cooler lender's forced-default mechanism.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
