### Title
Signature verification selects the wrong organization's secret, letting an attacker forge webhook payloads for any tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` chooses which organization's `webhook_secret` to validate a webhook against using a field taken from inside the same untrusted JSON body it is trying to authenticate. In multi-organization deployments this lets an attacker pick any configured organization (in particular one whose `webhook_secret` is unset) to trivially pass signature verification, then have the handler act on a completely different organization's repository/stack data.

### Finding Description
`verify_signature` resolves the signing app via `repository_owner`, which is parsed straight out of the unauthenticated request body before the signature has been checked: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` returns a per-organization `GitHubApp` configured from `secrets.github`, a documented and supported multi-org configuration schema (see `test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.shopify.yml`): [3](#0-2) 

Crucially, `verify_webhook_signature` short-circuits to `true` whenever the resolved organization has no `webhook_secret` configured: [4](#0-3) 

Because the organization used to select the secret (`repository.owner.login` / `organization.login`) is attacker-controlled and independent from any cryptographic check, an attacker can name any configured organization that lacks a `webhook_secret` (a state explicitly shown as the default/example in `config/secrets.development.example.yml` and the double-app fixture) to make `verified` become `true` unconditionally, regardless of the actual signature header sent.

Once verification passes, the actual data written is driven by other, independent fields of the same forged body. `Handler#repository_name`/`#stacks` resolve the acted-upon repository from `payload.dig('repository', 'full_name')`: [5](#0-4) 

and `StatusHandler#process` doesn't even scope by repository — it looks up commits globally by SHA across the whole instance and writes a forged CI status: [6](#0-5) 

This breaks the binding: *the organization whose secret authenticated the request* ≠ *the repository/stack whose state is written by the handler*. The equality that should hold — "the org that signed the payload == the org that owns the data the handler mutates" — is never enforced anywhere in the controller or handler chain.

### Impact Explanation
An unauthenticated attacker who knows (or can guess/observe) that any one organization configured on the instance has no `webhook_secret` can forge webhook events — including `status` — that write into the database state of an entirely different, properly-secured organization's stacks. Via `StatusHandler`, this allows unauthenticated write of arbitrary commit statuses (`state`, `context`, `description`, `target_url`) for any commit SHA tracked by the instance, independent of which organization actually owns that commit. If a stack's deploy checks gate on required commit statuses, this can force a stack into a "deployable" state without any real CI having run, enabling an unauthorized deploy. This matches the High-severity impact class "escalation into ... unauthenticated read of stack state ... or an unauthorized deploy."

### Likelihood Explanation
Likelihood is realistic in any multi-organization Shipit deployment (a documented, first-class configuration mode) where at least one configured organization omits `webhook_secret` — which is literally the commented-out default shown in `config/secrets.development.example.yml` and used in the test fixtures. No credentials, tokens, or prior access are required; the attacker only needs to send a single unauthenticated POST to the public `/webhooks` endpoint with a crafted JSON body and an arbitrary `X-Hub-Signature` header.

### Recommendation
Do not select the verification secret from attacker-controlled payload content. Either:
- Bind the webhook endpoint to a specific organization via the URL/route (e.g., `/webhooks/:organization`) so the organization used for verification cannot be chosen by payload contents, or
- Verify the signature against every configured organization's secret and require exact match of the winning organization to the `repository.owner.login`/`organization.login` actually referenced by the handler's target repository, and
- Make `verify_webhook_signature` fail closed (reject) when `webhook_secret` is blank instead of returning `true`, at minimum in multi-org mode.

### Proof of Concept
Given a multi-org configuration where `OrgA` has no `webhook_secret` and `OrgB` (victim) does, and Shipit tracks a stack for `OrgB/victim-repo` with commit `<real_sha>`:

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=deadbeef   (arbitrary/invalid)
Content-Type: application/json

{
  "repository": { "owner": { "login": "OrgA" } },
  "sha": "<real_sha>",
  "state": "success",
  "context": "ci/required-check"
}
```

`repository_owner` resolves to `"OrgA"` → `Shipit.github(organization: "OrgA")` has no `webhook_secret` → `verify_webhook_signature` returns `true` without checking the bogus signature → request proceeds → `StatusHandler` finds `Commit.where(sha: "<real_sha>")` (which belongs to `OrgB`'s tracked repository) and writes a forged `success` status via `create_status_from_github!`, with no relationship whatsoever to `OrgA`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
