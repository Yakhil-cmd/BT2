### Title
New stakers can capture historically-accrued signer rewards via a stale `signer-rewards-per-token-for-cycle` checkpoint - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
pox-5.clar implements a Uniswap-style "rewards-per-token" accumulator pattern to distribute sBTC/uSTX rewards to signers and stakers. Just like the reported PoolUpdates.sol bug, a per-entity checkpoint ("settled" value) is initialized from another accumulator that can silently jump forward without ever being validated against "how much time/stake this entity actually had", letting a newly-joined staker capture rewards it never earned.

### Finding Description
The reward model uses three layers of accumulators:
- A cycle-global accumulator `rewards-per-token-for-cycle` updated on every `calculate-rewards` call [1](#0-0) .
- A per-signer snapshot `signer-rewards-per-token-for-cycle`, which is only advanced inside `settle-rewards`, and only when the signer currently has `shares > 0`: [2](#0-1) 
- A per-staker "paid" checkpoint `staker-rewards-per-token-settled-for-cycle`, initialized when a staker joins a signer/bond to whatever `get-signer-rewards-per-token-for-cycle` currently returns: [3](#0-2) 
and, for the "none"-pool (STX delegation) path: [4](#0-3) 

Rewards owed are then computed purely as `shares * (rpt-current - rpt-paid)`: [5](#0-4) 

The code itself documents the required invariant: `settle-rewards`/`settle-staker-rewards` "MUST be called before any update to `signer-shares-staked-for-cycle`, because changes to that state will affect reward calculations" [6](#0-5) .

This is structurally identical to Uniswap/PoolUpdates' `rewardGrowthOutside`: `signer-rewards-per-token-for-cycle` is a checkpoint that is deliberately left un-advanced while a signer has zero shares (so it can lag arbitrarily far behind the global accumulator `rewards-per-token-for-cycle`). If a staker registers under a signer that currently has zero shares in a cycle where the global accumulator has already advanced (e.g., `calculate-rewards` was called mid-cycle before this signer had any stake), the new staker's "paid" checkpoint is set to the stale, lagging `signer-rewards-per-token-for-cycle` value (e.g. 0) rather than the true global value at the moment of joining. The very next `settle-rewards` call for that signer (now with `shares > 0`) unconditionally overwrites `signer-rewards-per-token-for-cycle` with the *current* global `rewards-per-token-for-cycle`, jumping it forward across the entire period the signer had zero stake. Because `earned = shares * (rpt-current - rpt-paid)` and `rpt-paid` was frozen at the old, lower value, the newly-joined staker is credited with rewards accrued before they ever staked — sBTC that other, actually-staked signers/stakers should have received.

### Impact Explanation
This breaks the equality that reward-per-token growth attributed to a staker must correspond only to periods during which that staker actually held stake. A staker can be credited with sBTC rewards it never earned, diluting/stealing rewards that should accrue to other signers/stakers who staked during the relevant period — a double-counting/theft of reward funds from the shared sBTC reward pool tracked in `get-rewards`/`last-accounted-rewards-only` [7](#0-6) . This matches the "theft of reserve/fees" / "double-counting a commitment or reward" impact category (High/Critical).

### Likelihood Explanation
Exploitability depends on whether `register-for-bond`/`update-bond-registration`/delegate-stacking flows call `settle-rewards` for the target signer *before* mutating `signer-shares-staked-for-cycle`/adding the new staker, per the documented invariant. I was not able to fully trace the call order inside `register-for-bond`/`update-bond-registration` within the available tool budget, so I cannot confirm with certainty whether the contract already enforces "settle-before-mutate" everywhere shares transition from zero to non-zero. The comment at `settle-rewards` explicitly calling out this ordering requirement suggests it is a known sharp edge that must be respected by every caller path that changes shares, which is exactly the class of bug (checkpoint desync on a zero→non-zero transition) that caused the original Sorella/Uniswap V4 finding.

### Recommendation
- Audit every code path that can move a signer's `signer-shares-staked-for-cycle` from `0` to a positive value (`register-for-bond`, `update-bond-registration`, delegate-stacking, bond rollover) and confirm `settle-rewards` (or an equivalent that stamps `signer-rewards-per-token-for-cycle` to the current global accumulator) is always called first, atomically, before the shares/staker maps are updated.
- Alternatively, remove the `(if (> shares u0) ...)` guard in `settle-rewards` so `signer-rewards-per-token-for-cycle` always tracks the global accumulator even while shares are zero, eliminating the possibility of a stale checkpoint jump (mirrors Uniswap's approach of always keeping `feeGrowthOutside`/global trackers current rather than deferring updates based on transient state).
- Add a regression test analogous to the PoC in the external report: create a signer, let global rewards accrue while the signer has zero stake, then register a staker and assert their earned rewards for that period are `0`.

### Proof of Concept
Conceptual sequence (to be adapted into `pox-5.test.ts`/`pox-5.stateful.prop.test.ts`):
1. Deploy/setup pox-5, signer `S` registered but with zero staked shares in reward-cycle `C` (`signer-shares-staked-for-cycle[S,C] == 0`).
2. Transfer sBTC into the contract and call `calculate-rewards` one or more times within cycle `C`, advancing the global `rewards-per-token-for-cycle[C]` to some value `G > 0` while `S` still has zero shares.
3. Staker `alice` now calls `register-for-bond`/delegate-stack under signer `S` in cycle `C`. Her `staker-rewards-per-token-settled-for-cycle` is initialized from `get-signer-rewards-per-token-for-cycle(S, C)`, which is still `0` (never advanced because `S` had zero shares) — see `add-staker-to-bond-for-cycle` at [3](#0-2) .
4. Trigger `settle-rewards`/`claim-rewards` for signer `S` (now `shares > 0`): `signer-rewards-per-token-for-cycle[S,C]` jumps directly from `0` to the current global value `G` [8](#0-7) .
5. Compute `alice`'s earned rewards via `get-earned-staker-rewards`/`compute-earned-rewards`: `earned = alice_shares * (G - 0) / PRECISION`, i.e., she is credited the full `G` worth of rewards-per-token growth even though she staked for zero blocks before step 3 [5](#0-4) .
6. Assert `alice`'s earned rewards `> 0` despite having contributed no stake during the period the global accumulator advanced — demonstrating unearned reward capture, exactly mirroring the original `test_IncorrectFeeGrowthInside` PoC structure.

;; Update all earned-but-unclaimed rewards for a signer, and update the snapshot
;; (signer-rewards-per-token-settled-for-cycle) for the signer.
;;
;; This MUST be called before any update to `signer-shares-staked-for-cycle`,
;; because changes to that state will effect rewards calculations.
(define-private (settle-rewards
        (signer principal)
        (reward-cycle uint)
        (bond-index (optional uint))
    )
    (let (
            (shares (get-signer-shares-staked-for-cycle signer reward-cycle bond-index))
            (rewards-per-token (get-rewards-per-token-for-cycle reward-cycle bond-index))
            (earned (compute-earned-rewards
                shares
                rewards-per-token
                (get-signer-rewards-per-token-settled-for-cycle signer reward-cycle bond-index)
                (get-signer-unclaimed-rewards-for-cycle signer reward-cycle bond-index)
            ))
        )
        (map-set signer-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            earned
        )
        (map-set signer-rewards-per-token-settled-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            rewards-per-token
        )
        (if (> shares u0)
            (map-set signer-rewards-per-token-for-cycle {
                signer: signer,
                reward-cycle: reward-cycle,
                bond-index: bond-index,
            }
                rewards-per-token
            )
            true
        )
