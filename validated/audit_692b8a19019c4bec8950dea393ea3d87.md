### Title
Webhook signature verification uses an attacker-supplied organization field that is decoupled from the repository the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate against using `repository_owner`, a value read directly out of the *unverified* JSON body (`params.dig('repository', 'owner', 'login')`). The event handlers, however, resolve the repository/stack to act on using a different field from the same unverified body: `payload.dig('repository', 'full_name')`. Nothing enforces that the organization used to select/verify the signature is the same organization embedded in `full_name`. In a multi-org Shipit deployment, this breaks the intended binding: `organization authenticated == repository written`.

### Finding Description
`verify_signature` in [1](#0-0)  resolves the GitHub App config via `Shipit.github(organization: repository_owner)`, where `repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` at [2](#0-1) . That organization name is read from the raw, not-yet-verified request body.

`Shipit.github` then looks up the per-organization config and constructs a `GitHubApp` scoped to that org's `webhook_secret` at [3](#0-2) . Critically, `verify_webhook_signature` short-circuits to `true` whenever that organization's `webhook_secret` is blank: [4](#0-3) . A blank `webhook_secret` is an explicitly supported, documented configuration value (`webhook_secret: # nil`) shown in `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`, and `docs/setup.md`'s "Webhook secret (optional)" note.

After the (potentially vacuous) signature check passes, the event is dispatched to handlers such as `PushHandler`, which resolves the target repository/stack independently, via `payload.dig('repository', 'full_name')` in `Handler#repository_name` [5](#0-4) , then `Repository.from_github_repo_name` splits that string on `/` to get `owner`/`name` and finds the matching `Repository` [6](#0-5) .

Because `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the target stack) are two independently attacker-controlled fields in the same JSON body, an attacker can set `repository.owner.login` to any organization configured in Shipit with a blank `webhook_secret` (bypassing verification entirely) while setting `repository.full_name` to `"<other-org>/<other-repo>"` pointing at a completely different, properly-secured organization's tracked repository. The controller will accept the forged request as authentic for that other repository.

### Impact Explanation
With this decoupling, the forged, unauthenticated payload is fed to the real handlers:
- `PushHandler` will call `stack.sync_github(expected_head_sha: ...)` for any not-archived stack on the targeted branch [7](#0-6) , forcing a github sync against an attacker-chosen `expected_head_sha`.
- `StatusHandler` will create a fabricated commit status (e.g. mark CI as green) for any commit SHA present in the datastore, without ever contacting GitHub for confirmation [8](#0-7) , which can satisfy `ci.require` checks and unblock/trigger continuous deployment for that stack.

Together, these primitives let an attacker who only needs to know that *some* organization in a shared/multi-tenant Shipit instance has no `webhook_secret` configured (a documented, legitimate configuration) forge state (fake CI green status, forced sync) for a different, unrelated organization's repositories/stacks that they have no legitimate access to — an unauthorized influence over deploy/CI state for another org's stacks.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (supported feature, demonstrated by `test/dummy/config/secrets_double_github_app.yml` and `Shipit.github_organizations`), and (2) at least one configured organization with a blank/absent `webhook_secret` — a state the setup docs and example secrets files explicitly present as valid ("Webhook secret (optional)"). Given that, no credentials, tokens, or GitHub App keys are required to exploit; the attacker only needs the public `/webhooks` endpoint and knowledge of the target `full_name`/branch/SHA.

### Recommendation
Do not derive the verification organization and the acted-upon repository from independent, both-attacker-controlled fields. Bind them together: after selecting `repository_owner` for signature verification, require that `repository.full_name`'s owner segment matches `repository_owner` (and reject if they differ) before dispatching to handlers. Additionally, treat a blank `webhook_secret` as a hard misconfiguration error in multi-org mode (or at minimum log/alert loudly), rather than silently returning `true` from `verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `OrgA` (no `webhook_secret` set) and `OrgB` (a real secret, tracking repo `OrgB/secure-app`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/secure-app"
  }
}
```
No `X-Hub-Signature` header is required to match anything real, since `OrgA` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally.
3. The controller proceeds to `PushHandler`, which resolves `Repository.from_github_repo_name("OrgB/secure-app")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack — despite the request never being authenticated against `OrgB`'s actual webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
