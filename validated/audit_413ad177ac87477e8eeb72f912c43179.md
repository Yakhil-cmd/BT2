## Analysis

The reported Node.js bug is a class where a **shared, global resource-accounting invariant** (nghttp2 memory counter) can be pushed out of the state one code path expects, causing a hard failure (`CHECK`) that aborts execution for everyone sharing that resource — not just the party that caused the mismatch.

The Zest analog is the market's oracle freshness/monotonicity invariant, which is tracked in a **global, per-feed** map rather than per-user or per-transaction state. [1](#0-0) 

```
(define-map last-update
  { type: (buff 1), ident: (buff 32) }
  uint)
```

Every price resolution enforces a strict monotonicity check against this shared map and hard-reverts if violated: [2](#0-1) 

Any caller can advance `last-update[{type, ident}]` for an asset simply by including a fresh Pyth VAA in the optional `price-feeds` argument accepted by ordinary user-facing operations such as `collateral-add`, `borrow`, `repay`, and `liquidate`: [3](#0-2) [4](#0-3) 

Because `last-update` is keyed only by feed identity (shared across every user and every position that references that asset), one caller's transaction can raise the freshness floor for the *entire market*. Any other in-flight transaction in the same or a nearby block — including a liquidator's `liquidate` call against an unrelated, unhealthy borrower — that supplies its own independently-fetched (but still valid and within `max-staleness`) VAA with an earlier `publish-time` will fail `(>= ts prev)` and revert with `ERR-ORACLE-INVARIANT`, even though nothing was wrong with its own data.

### Title
Global, non-per-user oracle monotonicity floor (`last-update`) lets one caller block other users' price-dependent transactions (liquidations, borrows, repays) - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The market contract tracks Pyth/DIA price freshness in a map keyed only by feed identity, shared by all callers. Any user operation that passes `price-feeds` can advance this shared floor. Any other user's transaction on the same asset that carries a legitimately fresh (but chronologically earlier) price update will be forced to revert, regardless of who that user is or what position they are acting on.

### Finding Description
`price-resolve` requires `(>= ts prev)` where `prev` comes from the single, global `last-update` map [5](#0-4) . Because `write-feeds`/`write-feed` let *any* transaction push a new VAA into the shared Pyth storage and then bump `last-update` for that feed [6](#0-5) , an attacker (or simply an unlucky ordering of independent, honest transactions) can set the floor ahead of what a victim's own, otherwise-valid VAA timestamp satisfies. The victim's operation — which may have nothing to do with the attacker's position, e.g., a liquidator trying to liquidate a *different* borrower's unhealthy debt in the same asset — reverts with `ERR-ORACLE-INVARIANT`, purely due to transaction ordering within the block, not because the victim's price data was stale or wrong in absolute terms.

### Impact Explanation
This is an ordering dependence between two unprivileged principals sharing common state (the per-feed `last-update` floor). It can be used to grief/delay liquidations or other price-gated operations (borrow, collateral-add/remove, repay) of unrelated users, producing a temporary freezing of otherwise executable operations/funds for those third parties until a fresher VAA becomes available. This matches the in-scope "temporary freezing of funds" impact category.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to submit a transaction with a newer Pyth VAA ahead of a victim transaction in the same block (transaction ordering / fee-priority manipulation), which is a realistic and repeatable capability on Stacks given normal mempool/fee dynamics, and doesn't require any privileged role, oracle compromise, or DAO action.

### Recommendation
Do not enforce global monotonicity keyed only by feed identity for freshness gating; instead, only use the resolved price/timestamp itself (validated independently against `max-staleness` and confidence) without requiring it to be newer than the highest timestamp any other caller has ever observed. If monotonicity protection against price rollback is required, scope it more narrowly (e.g., only compare to the timestamp used within the *same* transaction/position context) so that one caller cannot raise a floor that blocks unrelated callers.

### Proof of Concept
1. Borrower C holds an unhealthy stSTX position eligible for liquidation.
2. Liquidator L builds a `liquidate` transaction with a valid Pyth VAA for stSTX, published at time `T0`, within `max-staleness`.
3. Attacker A (who may hold no relevant position, or may be Borrower C's collaborator/self) submits, just before L's transaction is mined, any operation (e.g., `collateral-add` with a 1-unit deposit) carrying a newer Pyth VAA for stSTX published at `T1 > T0`, which calls `write-feeds` → advances `last-update[{TYPE-PYTH, stSTX-ident}]` to `T1` [5](#0-4) .
4. L's `liquidate` transaction now resolves stSTX price with timestamp `T0 < T1` and reverts with `ERR-ORACLE-INVARIANT`, even though `T0` is a legitimate, non-stale Pyth timestamp.
5. Borrower C's unhealthy position survives the block; A can repeat this each block cheaply to keep delaying liquidation.
