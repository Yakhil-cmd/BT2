This is exactly the analog I was looking for. Found a clear, well-documented trust-boundary bug class that matches the flash-loan report's core pattern: **an unprivileged actor can trigger an action targeting an unrelated party (a "receiver"), and if that receiver doesn't independently verify who really originated the action, it executes with unwarranted trust/authority.**

### Title
Cross-session `SendMessage` allowed an unprivileged sender to trigger unauthorized actions in a receiving session that trusted the message as user-originated - ([File: CHANGELOG.md](CHANGELOG.md))

### Summary
Claude Code's cross-session `SendMessage`/`ListAgents` feature lets any Claude Code session (including one controlled by an unprivileged, model-driven, or even prompt-injected caller) deliver a message into another, unrelated session. Multiple changelog entries document that the receiving session originally could act on such messages as if they carried the authority of its own local user — mirroring the reported Primitive Protocol flaw where `Option.exercise()` let "anyone" trigger a flash loan against an arbitrary `IFlash` receiver that had no way to distinguish a legitimate caller from an attacker.

### Finding Description
`SendMessage` and `ListAgents` implement cross-session messaging: "Claude Code sessions can now message each other, on any of your machines" [1](#0-0) . Analogous to the `Option.exercise()` function accepting an arbitrary `receiver` address that implements `IFlash` without validating the true initiator [2](#0-1) , the receiving Claude Code session is the "unprotected receiver": it accepts inbound cross-session traffic and, in early behavior, treated it with the same trust as a genuine local user request.

This was fixed only incrementally, similar to the "partially fixed in PR#17" status noted in the external report:
- 2.1.166: "Hardened cross-session messaging: messages relayed via `SendMessage` from other Claude sessions no longer carry user authority — receivers refuse relayed permission requests, and auto mode blocks them" [2](#0-1) .
- 2.1.223: "Improved auto mode safety: messages sent to other agent sessions via `SendMessage` are now evaluated by the permission classifier before dispatch" [3](#0-2)  — meaning even the *sending* side lacked a pre-dispatch permission check until this later release.
- 2.1.224: Introduced `crossSessionInbound` and `dialogExpiry` settings specifically because "cross-session messages sent to a session running with bypassed permissions are held for your approval, and messages to other sessions auto-deliver" [4](#0-3)  — i.e., a bypass-permissions receiver is the "unprotected `IFlash` implementer": by default it would have auto-executed inbound actions without an approval gate, exactly the "receiver doesn't implement necessary validations to identify who originally triggered" pattern from the report.
- 2.1.225: still fixing "cross-session messages staying parked without a notice or expiry in headless sessions and during startup" [5](#0-4) , showing the mitigation was still maturing release-over-release, mirroring the report's note that the underlying issue was only "partially fixed."

### Impact Explanation
Before the 2.1.166 hardening and the 2.1.224 `crossSessionInbound`/`dialogExpiry` gating, any session capable of calling `SendMessage` — including one hijacked via prompt injection or a malicious teammate — could push content into another user's/session's inbox that the receiver processed with elevated (user-equivalent) trust, similar to how an unprotected `IFlash` receiver could be forced into executing arbitrary flash-loan logic and paying its own fees. In a bypass-permissions receiving session, this could translate into unauthorized tool actions being auto-delivered/auto-executed without the receiving user's review.

### Likelihood Explanation
Requires only the ability to invoke `SendMessage`/discover a target via `ListAgents` (unprivileged capability available to any Claude Code session, including one whose model output is attacker-influenced through content it processed), and a receiving session that had not yet received the later hardening (`crossSessionInbound`, permission-classifier gating, or the "no longer carry user authority" fix). Given the multi-release cadence of fixes (2.1.166 → 2.1.223 → 2.1.224 → 2.1.225), earlier builds were concretely exploitable, and the settings-gated behavior implies risk remains for any receiver misconfigured to auto-deliver.

### Recommendation
This matches the report's own recommendation: don't rely on the receiver to self-defend. Concretely: (1) ensure `SendMessage` payloads are always cryptographically/structurally marked as "relayed, non-user-authority" so a receiver can never mistake them for local user intent (as done in 2.1.166); (2) keep the sending-side permission classifier check mandatory, not opt-in (2.1.223's fix implies it wasn't originally gated pre-dispatch); (3) default `crossSessionInbound` to "hold for approval" rather than "auto-deliver" for any session, not just bypass-permissions ones, since a normal session can still be manipulated into acting on unreviewed relayed content; (4) continue closing gaps like the 2.1.225 headless/startup parking issue promptly, and publish clear guidance (akin to what the report requested for `IFlash` implementers) for anyone building on `SendMessage`/`ListAgents` about the trust boundary these APIs cross.

### Proof of Concept
Not applicable — this analysis is based on documented, already-fixed changelog entries rather than a live exploit in the current codebase; the sequence of fixes (2.1.166, 2.1.223, 2.1.224, 2.1.225) itself demonstrates the vulnerable-then-hardened progression. [2](#0-1) [4](#0-3)
