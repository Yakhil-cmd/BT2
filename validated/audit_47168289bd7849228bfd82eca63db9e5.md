### Title
Webhook Signature Verified Against `repository.owner.login`, But Target Stack Resolved From Unbound `repository.full_name` — Cross-Organization Webhook Forgery (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate an inbound webhook based on `repository.owner.login` (or `organization.login`), but every event `Handler` subsequently resolves the *actual* stack/repository to act upon using the unrelated `repository.full_name` field from the same payload. In a multi-organization Shipit deployment (a configuration explicitly supported, see `Shipit.github_app_config` / `test/dummy/config/secrets_double_github_app.yml`), an attacker who controls one configured organization's `webhook_secret` can self-sign an arbitrary payload whose `repository.full_name` points at a stack belonging to a *different* organization, and Shipit will process it as legitimate.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [2](#0-1) 

It picks the GitHub App config with `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). In `lib/shipit.rb`, this maps directly to a per-organization secret: [3](#0-2) 

This means the HMAC signature is only proof that *whoever produced this exact JSON body* knows the `webhook_secret` configured for the organization named in `repository.owner.login`. The Shipit multi-org config format explicitly supports several independently-configured organizations, each with its own app/secret (`test/dummy/config/secrets_double_github_app.yml`), which is the realistic deployment this bug targets — e.g. a single shared Shipit instance serving multiple GitHub orgs, where each org's admins configure their own webhook secret and are not trusted with each other's repositories.

Once signature verification passes, `WebhooksController#create` parses the same raw body and dispatches it to the registered handler(s) for the event: [4](#0-3) 

Every handler (`PushHandler`, `PullRequest::*Handler`, etc.) inherits `stacks`/`repository_name` from the base `Handler`, which derives the acted-upon repository from `repository.full_name` — a **different JSON field than the one used to select the signing secret**: [5](#0-4) 

For example, `PushHandler` uses that repository binding to find and mutate real stacks: [6](#0-5) 

Nothing anywhere enforces `repository.owner.login == repository.full_name.split('/').first`. Because the entire raw body is attacker-authored (not a GitHub-relayed payload — GitHub signs bodies it produces, but here the attacker is the one computing the HMAC using a secret they legitimately possess for their own org), the attacker is free to set `repository.owner.login` to their own org (to pass signature verification) while setting `repository.full_name` to `victim-org/victim-repo` (to select the actual target of the mutation).

This is precisely the "organization that authenticated versus the repository that is written" trust binding described in scope: the equality `authenticated_org(repository.owner.login) == acted_upon_repo_owner(repository.full_name)` is never checked, but is implicitly assumed by every webhook `Handler`.

### Impact Explanation
An attacker who administers/owns one GitHub organization configured on a shared, multi-tenant Shipit instance can forge webhook events (signed with their own legitimate webhook secret) that are dispatched against a stack belonging to a *different, unaffiliated* organization also hosted on that Shipit instance. Concretely, via `PushHandler`, this forces `Stack#sync_github` to run against a victim stack on attacker's demand (cross-repository interaction the attacker has no GitHub access to), and the same unbound-repository pattern applies to every other webhook handler (`pull_request`, `check_suite`, `status`, `membership`, `merge_status`, etc.), all of which resolve their target exclusively via the unverified `repository.full_name`. This is a cross-organization/cross-repository write capability triggered purely by webhook forgery, which qualifies as "cross-repository writes" under the specified High/Critical impact categories. I was not able to fully trace every downstream handler (e.g., the `status`/`check_suite` handler internals) within the remaining investigation budget to determine whether any of them can be leveraged into bypassing CI gates for `continuous_deployment` (which would escalate this into an unauthorized deploy); that additional chain is plausible given `Commit#deployable?` semantics referenced in `README.md`/tests, but is not confirmed here.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance to be configured for multiple GitHub organizations (a first-class, documented configuration path — `Shipit.github_app_config`, `secrets_double_github_app.yml`), and (2) the attacker to control (own/administer) at least one of those organizations well enough to know its `webhook_secret` — which, notably, is something org admins configure themselves and are expected to know for their *own* org, but should never grant authority over *other* orgs' repositories. No GitHub App private key, `ApiClient` token, or Shipit session is required — only knowledge of one org's own webhook secret and an HTTP client, which is a realistic capability for any semi-trusted tenant organization in a multi-tenant Shipit deployment.

### Recommendation
Bind webhook signature verification and payload processing to the *same* field. After selecting the GitHub App via `repository_owner`, `WebhooksController` (or the base `Handler`) should verify that `repository.full_name`'s owner segment equals the `repository_owner`/`organization` value used to select the signing secret, rejecting (422) any payload where they diverge. Alternatively, resolve the target repository/stack using the same value that determined the verifying secret, rather than trusting `repository.full_name` independently.

### Proof of Concept
Given a multi-org Shipit config with organizations `OrgOne` (victim, hosts stack `OrgOne/victim-repo`) and `OrgTwo` (attacker-controlled, with known `webhook_secret_two`):

1. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<any sha>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_two, body)>` themselves, since they legitimately know `OrgTwo`'s secret.
3. POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner = "OrgTwo"`, looks up `OrgTwo`'s `GitHubApp`, and the signature validates successfully (attacker generated it with the correct secret for `OrgTwo`).
5. `create` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("OrgOne/victim-repo")` — a repository that has nothing to do with `OrgTwo` — and triggers `stack.sync_github` on it, cross-organization, without the attacker ever having any credential or access tied to `OrgOne`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
