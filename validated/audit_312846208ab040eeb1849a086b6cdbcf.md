### Title
Prosaic contract hash uses unpadded string concatenation, enabling hash collisions between different (title, text, creation_date) tuples - ([File: prosaic_contract.js])

### Summary
`prosaic_contract.js` computes the identifying hash of a prosaic (arbiter) contract by directly concatenating the dynamic-length `title`, `text`, and `creation_date` fields before hashing, instead of using length-prefixed/delimited encoding like the rest of the codebase's canonical `getSourceString` serializer does.

### Finding Description
`getHash()` and `getHashV1()` in `prosaic_contract.js` build the hash input as plain string concatenation: [1](#0-0) 

This is the classic "packed encoding" collision pattern flagged by the external report: `title + text + creation_date` is ambiguous, because moving characters across the `title`/`text` boundary (or the `text`/`creation_date` boundary) produces an identical concatenated string and therefore an identical SHA-256 hash, e.g. `title="ab", text="c..."` collides with `title="a", text="bc..."`.

This directly contrasts with the codebase's own defensive pattern for hashing structured/dynamic data, `getSourceString()` in `string_utils.js`, which explicitly type-tags and null-byte-delimits every field and rejects any embedded delimiter byte to prevent exactly this class of ambiguity: [2](#0-1) 

The related `arbiter_contract.js` hash function shows the intended fix already applied for new contracts (using `exports.DELIMITER` to join fields) while explicitly keeping the old unsafe `join("")` behavior for backward compatibility (contracts created before `NEW_HASH_DATE`): [3](#0-2) 

`prosaic_contract.js`'s `getHash`/`getHashV1`, however, have no such delimiter-based fix at all — both variants concatenate the three fields with no separator.

### Impact Explanation
The `hash` value returned by `getHash`/`getHashV1` is the primary contract identifier exchanged between paired devices when offering/responding to/sharing a prosaic contract (`createAndSend`, `share`, `getByHash`, `getBySharedAddress`, `respond`, `setField`), and it is embedded into the on-chain `data` message payload as `contract_text_hash`, which `handleReceivedSigningUnit` later matches against the locally stored contract to confirm the correct contract was the one signed on-chain: [4](#0-3) 

Because the hash does not uniquely bind to the exact boundaries of `title`, `text`, and `creation_date`, a peer counterparty (or malicious message from a paired device) can construct two semantically different contracts — e.g. altering the substantive content that appears in `title` vs `text` — that hash to the same identifier. Since this hash is what's compared on-chain via `contract_text_hash` to authenticate which contract text was actually agreed to and signed, a collision undermines the guarantee that the on-chain commitment corresponds to a single, unambiguous contract text, which can let a private-payment/arbiter counterparty repudiate or substitute contract terms while still passing the local hash-match check.

### Likelihood Explanation
Exploitation requires only that one of the two paired devices (offeror or acceptor of the prosaic contract) supply crafted `title`/`text`/`creation_date` values — no privileged access or node compromise is needed, matching the "paired device"/"private-payment counterparty" threat surface explicitly in scope. Constructing a colliding pair of strings is straightforward (move characters across the field boundary), so likelihood is not negligible, though it depends on convincing a counterparty into a specific contract-content structure at drafting time.

### Recommendation
Use a length-prefixed or delimiter-based encoding (consistent with `string_utils.getSourceString`, or the `DELIMITER`-joined approach already used in `arbiter_contract.js`'s `getHashSrc` for new contracts) when hashing `title`, `text`, and `creation_date` in `prosaic_contract.js`'s `getHash`/`getHashV1`, e.g. `[contract.title, contract.text, contract.creation_date].join(DELIMITER)` with a reserved delimiter character disallowed inside the fields, mirroring the existing mitigation pattern in `arbiter_contract.js`.

### Proof of Concept
1. Device A offers a prosaic contract with `title = "Pay 100"`, `text = ""`, `creation_date = "2026-01-01"`.
2. Device A (or a colluding/malicious counterparty) later offers/asserts a different contract with `title = "Pay 10"`, `text = "0"`, `creation_date = "2026-01-01"`.
3. `getHash`/`getHashV1` computed as `sha256(contract.title + contract.text + contract.creation_date)` produce the identical hash for both variants since `"Pay 100" + "" == "Pay 10" + "0"`.
4. Because `handleReceivedSigningUnit` in `prosaic_contract.js` (lines 159-177) validates the on-chain `contract_text_hash` only against this ambiguous hash rather than the exact field contents, either contract text can be treated as matching the on-chain commitment, allowing substitution of the actual agreed-upon terms while the hash check still passes.

function getHash(contract) {
	return crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8").digest("base64");
}

function getHashV1(contract) {
	return objectHash.getBase64Hash(contract.title + contract.text + contract.creation_date);
}

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
