### Title
Case-Sensitive Rule Matching in Hookify Allows Bypassing Blocking Guardrails via Case Variation - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`hookify` lets a user define local guardrail rules (`.claude/hookify.*.local.md`) that run in the `PreToolUse` hook and can **block** dangerous tool actions (e.g. `rm -rf`, `chmod 777`, edits to sensitive files) before they execute. The condition-matching logic in `RuleEngine._check_condition` implements the `contains`, `equals`, `starts_with`, and `ends_with` operators as plain, case-sensitive Python string operations, with no normalization of the compared values. This mirrors the reported bug class exactly: a security/uniqueness gate that is case-sensitive can be trivially defeated by a value that differs only in letter case but is treated identically by the underlying system being guarded (a case-insensitive filesystem path, or command text where only capitalization is being screened).

### Finding Description
The rule engine extracts a field value (command text or file path) via `_extract_field` and then evaluates the configured operator directly against the raw string: [1](#0-0) 

Contrast this with the `regex_match`/simple `pattern` path, which explicitly compiles patterns with `re.IGNORECASE`: [2](#0-1) 

So the plugin's own documentation and examples establish `contains`/`starts_with`/`ends_with` as legitimate, supported ways to write a **blocking** rule (see the `writing-rules` skill and `help.md` examples for `block-chmod-777`, `warn-dangerous-rm`, etc.), yet these operators lack the case-insensitivity the regex path already has: [3](#0-2) 

For file-path-scoped rules, `_extract_field` returns `tool_input.get('file_path', '')` verbatim for `Write`/`Edit`/`MultiEdit`: [4](#0-3) 

On case-insensitive filesystems (default macOS, Windows), `Secret.env` and `secret.env` resolve to the same file, but a rule with `field: file_path, operator: contains/equals, pattern: "secret.env"` will only match the exact-case string. An agent (potentially steered by prompt injection from untrusted content it read) can perform the identically-effective operation by writing to a differently-cased path or issuing a command whose only difference from the blocked pattern is letter case (many shells/tools on case-insensitive filesystems, and some Windows built-ins, accept mixed case and resolve to the same target), silently bypassing the user's guardrail.

### Impact Explanation
This is a hook-bypass trust-boundary issue: a locally-defined `block`-action guardrail — the mechanism a user relies on to stop a specific dangerous Bash command or file write from executing — can be defeated purely by case variation, with the underlying OS/filesystem treating the varied-case input identically to the blocked one. That results in the exact operation the user intended to forbid (e.g., an edit to a credential/secrets file, or a destructive command pattern) executing anyway, which is a concrete unauthorized-action/guardrail-bypass impact.

### Likelihood Explanation
Any hookify rule author who uses `contains`, `equals`, `starts_with`, or `ends_with` (all explicitly documented, supported operators) instead of the case-insensitive `regex_match`/`pattern` shorthand is exposed. Because the plugin's own help/list command examples show simple substring-style patterns for blocking commands, and case-insensitive filesystems are the default on macOS and Windows, this is a realistic, easily triggered configuration rather than a contrived edge case.

### Recommendation
Normalize case in `_check_condition` for the `contains`, `equals`, `starts_with`, and `ends_with` operators when they are used in `block`-action rules (or globally), e.g. compare `field_value.lower()` against `pattern.lower()`, matching the case-insensitivity already applied to `regex_match`/`pattern`. Alternatively, document that these operators are case-sensitive and add an explicit `case_sensitive: false` (default `false`) condition flag so rule authors get safe-by-default matching for blocking guardrails.

### Proof of Concept
1. Create `.claude/hookify.block-secret-edit.local.md`:
```yaml
---
name: block-secret-edit
enabled: true
event: file
action: block
---
```
with a condition `{"field": "file_path", "operator": "contains", "pattern": "secrets.env"}`.
2. On macOS/Windows (case-insensitive filesystem), have Claude write/edit `Secrets.ENV` (or any differently-cased variant) instead of `secrets.env`.
3. `_check_condition` evaluates `"secrets.env" in "Secrets.ENV"` → `False`, so the rule does not match and the block never fires, even though the filesystem resolves both paths to the same file, letting the edit through.
