### Title
Webhook Signature Verification Uses an Attacker-Controlled Organization Field While Handlers Act on an Unrelated Repository/Commit - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on a field read directly out of the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). None of the event handlers that subsequently act on the payload re-check that this "authenticated" organization matches the repository/commit the handler actually mutates. In a multi-organization Shipit deployment (a documented and supported configuration), an operator who legitimately controls one onboarded organization's webhook secret can sign a payload with their own secret while pointing the payload's repository/commit fields at a completely different, victim organization's data.

### Finding Description
`verify_signature` computes the org used for signature verification purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

The signature is verified against `Shipit.github(organization: repository_owner).webhook_secret`, i.e. whichever organization's secret the JSON body claims. Nothing binds this "authenticating organization" to the object the handler will actually touch.

Once the signature check passes, `create` dispatches to handlers purely by event type, passing the same raw, attacker-controlled JSON: [3](#0-2) 

Handlers derive the target repository from a *different* JSON field, `repository.full_name`, entirely decoupled from `repository.owner.login` used for signature selection: [4](#0-3) 

Worse, `StatusHandler` — the handler for GitHub `status` events — does not scope by repository at all; it looks up commits globally by SHA across the entire Shipit installation and writes a `CommitStatus` for every matching commit: [5](#0-4) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` / `sha` (used by handlers to decide what gets modified) live in the same attacker-supplied JSON body but are never cross-validated, an attacker who legitimately controls one onboarded organization (and therefore legitimately knows that organization's `webhook_secret`, configured per the documented multi-app setup) can:
1. Set `repository.owner.login` (or `organization.login`) to their own org so `Shipit.github(organization: repository_owner)` resolves to their own known `webhook_secret`.
2. Sign the raw POST body with that known secret, producing a header that passes `verify_signature`.
3. Populate the rest of the payload (e.g., `sha`, `state`, `context` for a `status` event) to target a commit belonging to an entirely different, victim stack/repository tracked by the same Shipit instance.

This breaks the binding: *organization that authenticated (the org whose secret validated the HMAC) ≠ the repository/commit that is actually written*.

### Impact Explanation
A forged `status` event lets the attacker fabricate a "success" `CommitStatus` (arbitrary `context`, `state`, `description`, `target_url`) for any commit SHA already known to the Shipit instance, regardless of which repository/org it belongs to. If the victim stack's deploy spec makes deployability conditional on that CI context (a core, common Shipit configuration) and has continuous deployment enabled, this fabricated status can make an already-pending commit "deployable," triggering an automatic, unauthorized deploy of the victim's stack — i.e., attacker-triggered deploy across an organization boundary they have no legitimate access to. This satisfies the Critical bar ("unauthorized deploy") because it turns cross-tenant webhook forgery into a state change (deploy) on infrastructure the attacker does not otherwise control. Similar cross-repository state corruption (`push`→sync, `membership`/`pull_request` handlers acting on `repository.full_name` values disconnected from the signing org) is reachable the same way, though `status` gives the most direct path to an unauthorized deploy.

### Likelihood Explanation
Exploitability requires:
- The Shipit instance to be configured for multiple GitHub organizations (explicitly documented and supported in `docs/setup.md`, "Using Multiple GitHub Applications"), which is realistic for any shared/multi-tenant Shipit deployment.
- The attacker to be a legitimate operator/owner of at least one onboarded organization (so they know that org's own `webhook_secret` — not a privileged secret belonging to the victim, and not requiring any Shipit session/API token).
- Knowledge of a target commit SHA in another tracked stack, which is often public information (commit SHAs on public GitHub repos, or leaked via Shipit's own UI/API for repos visible to the attacker).

No compromise of the victim's GitHub App, private key, or Shipit session is needed — only the attacker's own legitimately-provisioned webhook secret and public knowledge of a target SHA/context — making this a realistic and moderately likely path in any multi-org deployment.

### Recommendation
Do not let attacker-supplied JSON select which secret validates the request. Bind the verifying organization to a value the handler will also use, or verify signatures against every configured organization's secret and then require the resolved organization to match the repository being mutated, e.g.:
- After signature verification, re-derive the organization strictly from the DB-resolved `Repository`/`Stack` that the handler is about to modify (not from the raw payload), and reject/ignore the event if that owner differs from the organization whose secret validated the HMAC.
- For `StatusHandler` specifically, scope `Commit.where(sha: params.sha)` to commits whose stack's repository owner matches the verified organization, instead of searching globally.
- More generally, treat `repository_owner`/`organization.login` as a hint for secret selection only, and always re-validate that any object mutated by a handler actually belongs to that same verified organization before it is persisted.

### Proof of Concept
Assume a Shipit instance configured with two onboarded GitHub orgs, `attacker-org` (attacker legitimately owns/administers this org's GitHub App, thus knows its `webhook_secret`) and `victim-org` (tracks stack `victim-org/app`, with a deploy spec gating deploy on CI context `ci/tests`, continuous deployment enabled, and a pending commit `deadbeef...` at the tip of the tracked branch).

1. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "deadbeef000000000000000000000000000000",
  "state": "success",
  "context": "ci/tests",
  "description": "forged",
  "target_url": "https://example.com",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/irrelevant" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s own `webhook_secret`.
3. POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` → `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and validates successfully because the attacker legitimately knows that secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit `deadbeef...` in `victim-org/app` regardless of the `attacker-org` value used for signing — and writes a successful `ci/tests` status onto it. [5](#0-4) 
6. If `victim-org/app`'s commit-check gating relies on that status, the stack's continuous-deployment logic now treats the commit as deployable and can trigger an automatic deploy the attacker never had access to authorize.
