### Title

Permanently frozen market through `i128` value overflow during interest accrual - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary

A sufficiently large market can reach a state where `borrowed * borrow_index` or `supplied * supply_index` no longer fits in `i128` before either index reaches its configured ceiling. Because every pool mutation accrues before executing the requested operation, the resulting `MathOverflow` permanently blocks withdrawals, repayments, liquidations, index updates, revenue claims, and other state-changing paths for that market. [1](#0-0) [2](#0-1) 

### Finding Description

The pool stores share counts and indexes as RAY-scaled `i128` values. During each accrual step, `accrue_step` reconstructs aggregate token values with `scaled_to_original`, which performs `scaled.mul(env, index)` and panics if the product exceeds `i128::MAX`. [1](#0-0) [3](#0-2) 

The borrow index is capped only after multiplication, so the cap does not prevent the aggregate debt calculation from overflowing first. [4](#0-3) 

The controller exposes this through permissionless `update_indexes(caller, assets)`, which only requires caller authorization and forwards the requested `HubAssetKey` list to the pool. [5](#0-4) [6](#0-5) 

All ordinary pool mutations load an already-accrued market through `synced_market`, meaning the same overflow is encountered before withdrawal, repayment, seizure, or other accounting changes can execute. [2](#0-1) [7](#0-6) 

### Impact Explanation

Once the boundary is crossed, the market cannot be accrued successfully and therefore cannot process ordinary exits or debt reduction. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot progress through liquidation, and protocol revenue cannot be claimed for that market. [8](#0-7) 

The repository's regression test demonstrates this exact terminal state: a billion-token, 18-decimal market at 98% utilization eventually fails inside `scaled_to_original`, before `MAX_BORROW_INDEX_RAY`, and subsequent withdraw and repay calls both revert with `MATH_OVERFLOW`. [9](#0-8) 

This is permanent freezing of user funds rather than a temporary fail-closed condition: the stored `last_timestamp` is only advanced after all accrual chunks complete, so retrying later cannot bypass the overflowing multiplication. [10](#0-9) 

### Likelihood Explanation

An unprivileged caller can trigger the transition with `controller::update_indexes(caller, vec![hub_asset])` once enough interest has accrued. [5](#0-4) [11](#0-10) 

Creating the vulnerable condition requires a very large market, sustained borrowing, and enough time for the index to make aggregate value exceed `i128::MAX`; the checked harness uses 1 billion 18-decimal tokens and approximately 98% utilization. [12](#0-11) 

After that state exists, any user can force the irreversible overflow by calling index accrual; the caller does not need account ownership or a privileged role. [6](#0-5) [11](#0-10) 

Severity is best classified as High because the impact is permanent freezing of all funds in the affected market, while the likelihood is constrained by the extreme market size and accrual horizon.

### Recommendation

Do not recompute aggregate values from potentially overflowing `scaled * index` products at the start of accrual. Track aggregate debt/supply value in a wider domain, or execute the rate and index update using widened arithmetic and persist only capped indexes. At minimum, detect the representability boundary before committing to a state from which no mutation can proceed, and preserve emergency repay/withdraw paths that can settle positions using bounded or saturated calculations.

Specifically:

- Change `scaled_to_original` use inside `accrue_step` to an `I256`-backed aggregate calculation or another representation that cannot cross the `i128` value ceiling before the index cap.
- Apply the same fix to `calculate_supplier_rewards`, `update_supply_index`, and `supply_index_reward_shortfall`, which also multiply aggregate shares by indexes. [13](#0-12) [14](#0-13) 
- Ensure `update_indexes` reaches the index ceiling safely instead of reverting before it.
- Add a regression test proving that the whale-market fixture can still accrue, repay, withdraw, and liquidate after the current overflow boundary.

### Proof of Concept

1. Use an existing listed market with 18 decimals and a steep high-utilization rate model.
2. Supply `1_000_000_000 * 10^18` base units of that asset.
3. Supply sufficient collateral in another listed asset and borrow approximately `980_000_000 * 10^18` base units of the first asset, leaving the market near 98% utilization. [12](#0-11) 
4. Allow ledger time to advance until `borrowed * borrow_index` approaches `i128::MAX`; permissionless periodic `update_indexes(caller, vec![hub_asset])` calls may be used to advance committed accrual. [15](#0-14) 
5. Call `update_indexes` once the next aggregate valuation exceeds `i128::MAX`; `accrue_step` reverts in `scaled_to_original` before the borrow-index cap engages. [16](#0-15) [17](#0-16) 
6. Subsequent `withdraw`, `repay`, liquidation, or further `update_indexes` attempts load the same stale timestamp and run the same overflowing accrual first, so they also revert with `MathOverflow`. [2](#0-1) [18](#0-17)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```
