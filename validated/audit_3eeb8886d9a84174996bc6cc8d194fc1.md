### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` only proves that a webhook body was HMAC-signed with the `webhook_secret` of the organization named in `params.dig('repository','owner','login')`. `StatusHandler#process` then looks up the target commit with a global, unscoped `Commit.where(sha: params.sha)` query, never checking that the resolved commit's stack/repository belongs to the organization that was actually authenticated.

### Finding Description
The binding that should hold is: `authenticated_organization == owning_organization_of(Commit.where(sha: params.sha))`. Before tracing the code, the two sides are: (1) the org whose `webhook_secret` verified the HMAC in `WebhooksController#verify_signature`, derived from `repository_owner` in the JSON body [1](#0-0) [2](#0-1) ; and (2) the org that actually owns the `Stack`/`Repository` of whatever `Commit` row matches `params.sha`.

Tracing the call path: `WebhooksController#create` parses the body and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature` passes [3](#0-2) . For a `status` event this reaches `StatusHandler.call(payload)` → `new(payload).process` [4](#0-3) . `StatusHandler#process` executes:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

This query is **not scoped by repository or organization at all** — `Commit.where(sha:)` searches every commit in the database, across all stacks and all repositories/organizations configured in the Shipit instance. Compare this to sibling handlers `PushHandler#process` and `CheckSuiteHandler#process`, which both go through the base class's `stacks` helper — `Repository.from_github_repo_name(repository_name)&.stacks` — which scopes lookups to the repository named in the payload [6](#0-5) [7](#0-6) [8](#0-7) . `StatusHandler`'s params schema doesn't even require a `repository` field, and `process` never calls `stacks` or checks `repository_owner` [9](#0-8) .

Root cause: `verify_signature` authenticates *who sent the request* (an org that legitimately controls its own `webhook_secret`), but authorizes nothing about *which commit rows may be mutated*. Since `sha` is a 40-character git hash chosen by the attacker's own repository/commits (fully under attacker control — they can craft commits, forks, or reuse well-known/public shas), and Shipit commonly tracks many repositories/orgs in one instance, an attacker who legitimately administers their own org's GitHub App/webhook can send a `status` payload naming a `sha` that happens to collide with a real commit tracked under a *different* organization's stack. `Commit.where(sha:)` will find and mutate that other org's commit via `create_status_from_github!`, with no check that the commit's `stack.repository` matches the authenticated `repository_owner`.

`add_status`/`create_status_from_github!` can flip a commit's state to `success`, and if the target stack has `continuous_deployment` enabled and the status is a required context, this triggers `ContinuousDeliveryJob`, i.e., an actual deploy for a repository the attacker never authenticated against [10](#0-9) .

None of the listed guards prevent this: `verify_signature` only checks the HMAC against the org derived from the payload, not against the resolved commit's owner; `drop_unhandled_event` only checks that a handler exists for the event type; `ExplicitParameters` (`params do ... end`) only validates shape/types, not ownership; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` involved anywhere in the webhook path since webhooks are inherently unauthenticated-by-session and rely solely on signature verification for trust.

### Impact Explanation
A successful forged `status` webhook lets an attacker who controls only their own org's Shipit GitHub App write a `Status` row against a `Commit` belonging to an entirely different, unrelated organization/repository tracked by the same Shipit instance, and — if that commit's stack has continuous deployment configured — trigger an unauthorized deploy for that other tenant. This is a payload for one repository mutating another's stack/commit and can drive an unauthorized deploy, matching the Critical impact category. It is repeatable against any commit sha the attacker can discover or predict (public commit shas from mirrored/forked open-source repos, or by having previously interacted with the target repo), and the blast radius spans every organization/repository hosted on the same Shipit instance, not just the attacker's own.

### Likelihood Explanation
Preconditions are minimal for a multi-tenant Shipit deployment: the attacker only needs a legitimately configured `Shipit.github(organization: 'attacker_org')` entry with their own `webhook_secret` (which they administer themselves, as stated), and knowledge of a target `sha` that exists in some other org's `Commit` table (trivially satisfiable when repos are mirrors/forks of public projects, or via commit-sha enumeration/reuse). No GitHub or Shipit secret belonging to the victim org is needed. The attacker's cost is a single signed HTTP POST to `/webhooks`, fully repeatable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through the authenticated repository, mirroring `PushHandler`/`CheckSuiteHandler`: require `repository.full_name` in the params schema and resolve via `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` (or equivalent `Repository.from_github_repo_name(repository_name)&.stacks&.commits&.where(sha: params.sha)`), so that only commits belonging to stacks under the repository/organization that was actually signature-verified can be mutated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not mutate a commit belonging to a different, unrelated stack/org" do
  org_b_commit = shipit_commits(:first) # belongs to stack "shipit" / its repository/org
  payload = {
    "sha" => org_b_commit.sha,
    "state" => "success",
    "repository" => { "full_name" => "attacker_org/attacker_repo", "owner" => { "login" => "attacker_org" } }
  }

  # Simulate verify_signature succeeding for attacker_org (as WebhooksController does)
  assert_no_difference -> { org_b_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Both sides of the equality: `authenticated_org = "attacker_org"` (from `repository.owner.login`, what `verify_signature` checked) vs. `owning_org_of(org_b_commit) != "attacker_org"`. The current implementation of `StatusHandler#process` [5](#0-4)  ignores the `repository` field entirely and will still create the status, causing the assertion above to fail against the vulnerable code — demonstrating the mutation proceeds despite no authorization check tying `params.sha`'s owning stack to the verified `repository_owner`.
