### Title
Redeem is governed by cached `assets` ledger instead of real underlying-token balance, letting an early redeemer drain liquidity and permanently freeze a later redeemer's shares - (File: mainnet/contracts/vault/v0-vault-sbtc.clar)

### Summary
Every Zest v2 vault (`v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) tracks the underlying assets it holds in a plain data variable (`assets`) that is only ever incremented on `deposit` and decremented on `redeem`. It is never checked against, or reconciled with, the actual SIP-010 token balance the vault holds. `redeem` authorizes withdrawals purely from this cached ledger (`current-assets`, `available-assets`), then calls `send-underlying`, which blindly performs a `transfer` for the computed amount.

### Finding Description
`redeem` computes eligibility solely from internal state: [1](#0-0) 

`available-assets` is derived only from the cached ledger, never from the real token balance: [2](#0-1) 

`receive-underlying`/`send-underlying`/`ubalance` never verify that the tokens actually received/sent match the accounted amount, and the real balance helper `ubalance` is not consulted anywhere in `deposit`/`redeem`: [3](#0-2) 

If the underlying token (deployed at `'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token` and analogous addresses for the other vaults) is one whose real balance can diverge from the sum of transfers into/out of the vault — e.g., a token with a "locked"/"available" split (the project's own `local-testing/contracts/utility/token/sbtc.clar` token models exactly this: `get-balance` includes a separately mutable `sBTC-locked` component, and `get-balance-available` can shrink for reasons other than a `transfer` call) — the vault's `assets` ledger stays unchanged while the real spendable balance shrinks. All depositors' shares are priced off the stale `assets`/`total-supply` ratio via `convert-to-assets-preview`, so every share is still treated as fully redeemable by the contract's own accounting, but the pool of real tokens backing those shares is smaller than the ledger believes.

Two depositors, Alice and Bob, hold `zft` shares against this single shared `assets` ledger and single real token balance. If the real balance shrinks by 10% while the ledger still reports the pre-shrink total:
- Alice calls `redeem` first: `available-assets`/`current-assets` checks pass against the ledger, `send-underlying` succeeds because enough real tokens still remain to pay her out fully.
- Bob calls `redeem` for his equally-priced shares: the ledger still says his shares are backed (`current-assets`/`available-assets` checks pass, since the ledger was only debited by Alice's nominal `inkind`, not by the real shortfall), but the actual on-chain `transfer` inside `send-underlying` now fails because the vault's real token balance is insufficient — Bob's `redeem` transaction reverts and his shares become permanently stuck, since the ledger will never reflect the true shortfall for any future call either.

### Impact Explanation
This is a shared-state harm between two unprivileged principals: Alice's earlier withdrawal consumes the finite real liquidity that Bob's later, equally-entitled shares depend on, and Bob is left holding shares that the contract's own accounting says are redeemable but the real token balance can never satisfy. This is a temporary/permanent freezing of the affected depositor's principal (their shares can never be redeemed for the underlying since the ledger never self-corrects), which falls under the in-scope "temporary freezing of funds" (or permanent freezing, if the underlying never recovers) impact class.

### Likelihood Explanation
Likelihood depends on whether any of the deployed underlying tokens used with these vaults can have their real balance move independent of a `transfer` call into/out of the vault (rebasing, fee-on-transfer, or a lock/unlock split as modeled by the project's own `sbtc.clar` test token). Given the project explicitly models a locked/available balance split for its sBTC test token, this is a realistic token behavior the vault must tolerate, and the vault code performs no balance reconciliation at any point (`deposit`, `redeem`, or `accrue`), so the bug is always latent whenever such a token property manifests, without any special ordering or privileged access required beyond two ordinary users redeeming in sequence.

### Recommendation
Reconcile the internal `assets` ledger against the real underlying balance (via `ubalance`) at the start of every state-changing entrypoint (`deposit`, `redeem`, `borrow`, `repay`, `accrue`), and cap `available-assets`/`redeem` payouts by `min(ledger-derived amount, real balance)`. Alternatively, socialize any detected balance shortfall proportionally across all outstanding shares (adjusting the share price) instead of allowing a first-mover to fully drain the real balance while the ledger still shows later redeemers as fully backed.

### Proof of Concept
1. Deploy `v0-vault-sbtc.clar` with an underlying token that supports a locked/available balance split identical to the project's own `local-testing/contracts/utility/token/sbtc.clar` (`get-balance-available` vs `get-balance`).
2. Alice and Bob each `deposit` 1000 units; `assets` ledger records 2000, real `ubalance` is 2000.
3. Some external actor/process moves half of the vault's tokens from "available" to "locked" (analogous to a rebase/fee event) — `ubalance` (available balance) drops to 1000, but `assets` still reads 2000 and is never re-synced.
4. Alice calls `redeem` for her full 1000-unit share: `current-assets`/`available-assets` checks pass against the stale ledger; `send-underlying` succeeds because 1000 of the 1000 remaining real tokens are transferred to her.
5. Bob calls `redeem` for his equally-priced 1000-unit share: ledger checks (`current-assets`, `available-assets`) still pass since the ledger was decremented only by Alice's nominal amount, but the underlying `transfer` inside `send-underlying` reverts because the vault holds 0 real available tokens — Bob's funds are permanently stuck.
