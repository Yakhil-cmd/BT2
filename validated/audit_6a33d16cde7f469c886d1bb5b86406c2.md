### Title
Cross-tenant commit status webhook: `StatusHandler` matches commits by `sha` alone, letting one repository's webhook drive continuous delivery for another repository's stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` without any repository/stack scoping, then calls `commit.create_status_from_github!` for every match. Because git commit SHAs are deterministic content hashes, an attacker who forks (or otherwise obtains) a repository sharing history with a victim's tracked repository can emit a `status` webhook from their own repo carrying a SHA that also exists in the victim's Shipit-tracked commit table, causing the victim's `Commit`/`Stack` to receive the status and potentially trigger `ContinuousDeliveryJob`.

### Finding Description
The broken binding: for a webhook whose `payload['repository']['full_name']` identifies repo R, only commits belonging to `stacks` (i.e., `Repository.from_github_repo_name(R).stacks`) should ever be mutated - `commit.stack ∈ Repository.from_github_repo_name(payload['repository']['full_name']).stacks` must hold for every commit touched by the handler.

In `StatusHandler#process` [1](#0-0) , the query is `Commit.where(sha: params.sha)` with no join/filter against `repository_name` or `stacks`, unlike the `Handler` base class which explicitly provides a `stacks` helper scoped to `Repository.from_github_repo_name(repository_name)` for this exact purpose [2](#0-1) . `StatusHandler` never uses it.

For every matched commit (which can belong to *any* stack in the installation, not just the sender's repository), `create_status_from_github!` creates a `Status` row scoped to that commit's real `stack_id` [3](#0-2) . `Status` then runs `after_commit :schedule_continuous_delivery, on: :create`, which calls `commit.schedule_continuous_delivery` [4](#0-3) , which in turn checks `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob.set(wait: ...).perform_later(stack)` using `stack = commit.stack` [5](#0-4) . `commit.stack` here is derived purely from the DB row matched by SHA - never re-checked against the webhook's `payload['repository']`.

Attacker path: fork or otherwise reference a repository that shares commit history (and therefore SHAs) with a victim repo tracked by Shipit; send a `status` webhook (signed with the attacker's own valid credentials for their own repo/app installation) whose `sha` collides with a commit that exists in the victim's Shipit `commits` table and whose `state` is `success`. Signature verification (`verify_signature`/`GitHubApp#verify_webhook_signature`) only proves the payload came from a legitimately-registered sender for *some* repository - it does not bind the payload's repository claim to the commits actually mutated, because `StatusHandler` never checks `payload['repository']` against the matched commit's owning stack. `drop_unhandled_event` and the `ExplicitParameters` schema only validate the shape of the payload (`sha`, `state`, etc.), not the repository/stack relationship.

### Impact Explanation
A successful collision lets an attacker inject a fabricated "success" status onto a commit belonging to a stack they do not own, which can flip that commit from non-deployable to `deployable?`, and if the victim stack has `continuous_deployment?` enabled, causes an unauthorized `ContinuousDeliveryJob` to be enqueued and eventually a deploy for the victim's stack - i.e., "a payload for one repository mutating another's stack/commit" and "an unauthorized deploy," both explicitly listed Critical impacts. This is repeatable against any stack whose tracked commits share SHAs with a repository the attacker controls (most directly: any fork relationship, which is trivial to create on GitHub for public repos), so the blast radius spans all tenants sharing commit ancestry with an attacker-controlled repo.

### Likelihood Explanation
Preconditions: (1) the victim stack must have `continuous_deployment?` enabled and be otherwise `deployable?`; (2) attacker must be able to produce/reference a commit SHA that also exists in the victim's Shipit `commits` table - trivially achievable by forking the victim's public GitHub repository (fork history retains identical SHAs) and then triggering a `status` webhook from the fork (e.g., via the attacker's own GitHub Actions workflow or the Statuses API, using only the attacker's own token/app installation - no victim secrets needed); (3) the webhook endpoint must accept the attacker's own valid signature, which it will since signature verification is per-sender, not per-repository-consistency. No Shipit session, API token, or GitHub team membership is required at any point, matching the stated "unprivileged attacker" model.

### Recommendation
Scope `StatusHandler#process` (and any sibling status/check-run handlers using bare `Commit.where(sha: ...)`) to the sender's own stacks, e.g. `Commit.where(sha: params.sha, stack: stacks)` using the existing `Handler#stacks` helper, so a commit is only updated if it belongs to a stack whose repository matches `payload['repository']['full_name']`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Seed two repositories/stacks, `victim_stack` (repo `victim/repo`, `continuous_deployment?` stubbed true, `deployable?` stubbed true) and `attacker_stack` (repo `attacker/repo`).
2. Create a `Commit` with `sha: "deadbeef"` belonging to `victim_stack`, and stub `deployable?` true on that commit.
3. Build a `status` webhook payload with `payload['repository']['full_name'] = "attacker/repo"` and `sha: "deadbeef"`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `commit.reload.statuses.last.state == "success"` even though the commit belongs to `victim_stack`, not `attacker/repo`'s stacks - demonstrating the equality `commit.stack ∈ Repository.from_github_repo_name(payload['repository']['full_name']).stacks` is false yet the status/continuous-delivery scheduling proceeds anyway.
6. Assert `ContinuousDeliveryJob` was enqueued with `victim_stack`, confirming the cross-tenant effect, e.g. via `assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [victim_stack])`.
