No vulnerability found for this question.

Details: I searched for FRAME/XCM/bridge analogs of a "pause mechanism checks for the wrong/stale opcode" bug pattern — i.e., a hardcoded list of call/opcode identifiers used to gate a pause check that fails to be updated after a rename or addition of a new call variant.

What I found instead:
- `pallet-tx-pause`'s `is_paused`/`Contains` implementation derives the paused/whitelisted status dynamically from `GetCallMetadata` (pallet name + call name strings) rather than a hardcoded enumeration of opcodes, so adding a new call to a pallet does not require updating a stale match arm to remain covered by the pause filter. [1](#0-0) 
- Bridge pallets (`pallet-bridge-messages`, `pallet-bridge-grandpa`, snowbridge `ethereum-client`, `inbound-queue-v2`, `outbound-queue`) all gate their dispatchables through a single `OperatingMode`/`BasicOperatingMode::is_halted()` boolean check performed at the top of each call, rather than through an opcode-style match list, so a newly added dispatchable does not risk being missed by the halt check unless the pallet author forgets to add `ensure!(!is_halted(), ...)` to that specific new dispatchable (a code-review/config concern, not a systemic stale-opcode class bug). [2](#0-1) [3](#0-2) 
- `pallet-xcm`'s `force_suspension` sets a single `XcmExecutionSuspended` flag consulted by the executor's barrier logic globally, not via an enumerated opcode list. [4](#0-3) 

The one place with a hardcoded match over call variants for pause purposes is `TxPauseWhitelistedCalls`/`SafeModeWhitelistedCalls` in the node runtime, but that is a runtime configuration (`match call { ... }` allow-list in `substrate/bin/node/runtime/src/lib.rs`), and per the scan rules, config-only findings in example/reference runtime code are excluded as bounty-eligible findings, and it is a whitelist for calls that *should never be paused* (fail-safe direction), not a bypass of an active pause. [5](#0-4) 

No production pause/halt mechanism in this repository was found to use a stale/hardcoded opcode-equivalent check that could let a new user-facing call bypass an active pause, so no direct FRAME/XCM/bridge analog of the reported TON bug class is demonstrable here.
