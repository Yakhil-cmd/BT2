### Title
Cross-repository forged status: `StatusHandler#process` matches commits by `sha` alone, letting a webhook signed for attacker's own repo inject a status on a victim's commit and enqueue `ContinuousDeliveryJob` for the victim stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` only proves that the inbound `status` webhook was signed by the org named in `payload['repository']['owner']['login']`, i.e. that the attacker's own org's `webhook_secret` matches. `StatusHandler#process` then looks up commits purely by `sha`, with no check that the matched commit's stack/repository is the one named (or signed) in the payload, so a commit sharing that `sha` in a completely different, victim-owned stack receives the forged status and triggers `Commit#schedule_continuous_delivery` -> `ContinuousDeliveryJob.perform_later(stack)` for the victim stack.

### Finding Description
The binding the question assumes should hold is:
`organization that authenticated the webhook (via Shipit.github(organization: repository_owner).verify_webhook_signature)` == `organization/stack that gets its Commit/Status mutated and its ContinuousDeliveryJob enqueued`.

Tracing the code shows this binding is never enforced:

- `WebhooksController#verify_signature` resolves `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, i.e. it authenticates the request against **whichever org name appears in the attacker's own payload** [1](#0-0) . If the attacker owns/controls a repo under an org that is configured in Shipit's multi-org `github` config (a supported, documented setup [2](#0-1) ), this check passes using the attacker's own legitimate `webhook_secret` - it says nothing about the victim.
- `Shipit::Webhooks::Handlers::Handler` defines a `stacks`/`repository_name` helper intended to scope handling to the repository named in the payload [3](#0-2) , but `StatusHandler#process` **does not use it at all**:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 
- The database schema confirms `sha` is **not** globally unique - the unique index is `(sha, stack_id)`, not `sha` alone [5](#0-4) . This means the same commit sha can legitimately exist across multiple stacks (forks, mirrors, cherry-picked/rebased history, shared upstream history), and `StatusHandler` will update **all of them** from a single signed request naming only one repository.
- Each `Status` created runs `after_commit :schedule_continuous_delivery` -> `commit.schedule_continuous_delivery`, which - if the matched commit's stack has `continuous_deployment: true` and is `deployable?` - enqueues `ContinuousDeliveryJob.perform_later(stack)` unconditionally with respect to who authenticated the request [6](#0-5) [7](#0-6) [8](#0-7) .

Exploit flow: attacker owns a repo (`attacker/evil`) whose org is registered with Shipit and has a valid `webhook_secret`. The attacker's commit history shares a `sha` with a commit currently HEAD on a victim's `continuous_deployment`-enabled stack (trivially true for forks/mirrors of public repos, or any repo whose history intersects the victim's, e.g. via a shared upstream). Attacker posts (or lets GitHub post, since it's their own real webhook) a `status` event with `state: success`, `sha: <shared sha>`, and `repository.full_name: attacker/evil`. `verify_signature` passes because it validates against the attacker's own org secret. `StatusHandler#process` finds **all** `Commit` rows with that `sha`, including the victim's, and calls `create_status_from_github!` on each, which schedules continuous delivery for the victim's stack.

Existing guards do not prevent this: `verify_signature` authenticates the *request's origin org*, not the *target stack*; `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` only validate shape (`sha`, `state`, etc.), not ownership; there is no `Repository`/`Stack` scoping applied before `Commit.where(sha:)` runs.

### Impact Explanation
An attacker who controls any repository tracked by the same Shipit instance (even a fork with overlapping history) can inject a fabricated `success` status on a victim's commit and cause `ContinuousDeliveryJob` to be enqueued for the victim's stack, which can trigger an unauthorized deploy if the victim's stack has `continuous_deployment` enabled and is otherwise deployable - matching the "Critical: a payload for one repository mutating another's stack/commit / unauthorized deploy" category. This is a cross-tenant break: any org onboarded to a shared, multi-org Shipit instance can forge status data affecting any other org's stack whenever a shared commit sha exists, which is common for forks and shared history and is repeatable per matching sha.

### Likelihood Explanation
Requires: (1) attacker owns/controls a repository whose org is configured in Shipit with its own `webhook_secret` (a legitimate onboarding, not a stolen secret) and (2) a `sha` collision - i.e. an actual, identical commit object - present both in the attacker's repo and in the victim's stack's commit history at the moment the victim's stack is `continuous_deployment`-enabled and deployable. This is not a cryptographic sha collision requirement; it is naturally satisfied for forks, mirrors, or any repositories sharing git history/tags, which is a common real-world configuration for multi-tenant CI/CD setups. Attacker cost is a single crafted HTTP POST to `/webhooks` (or a real GitHub webhook from their own repo), fully repeatable against any stack sharing history with a repo the attacker controls.

### Recommendation
Scope `StatusHandler#process` to the repository actually named (and signature-verified) in the payload, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` using the `Handler#stacks`/`repository_name` helper already defined in the base class, instead of an unscoped `Commit.where(sha: params.sha)`. More generally, every handler that mutates records by "loose" identifiers (`sha`, branch name) should first resolve the `Repository`/`Stack` from the verified payload's `repository.full_name` and constrain all queries to that scope.

### Proof of Concept
Minitest plan (`test/models/webhooks/status_handler_test.rb` or extending `webhooks_controller_test.rb`):
1. Create two `Repository`/`Stack` fixtures: `victim_stack` (org `victim`, `continuous_deployment: true`, deployable) and `attacker_stack` (org `attacker`).
2. Create `Commit` rows with the **same** `sha` value under each stack: `victim_commit = Commit.create!(stack: victim_stack, sha: 'deadbeef...', ...)` and `attacker_commit = Commit.create!(stack: attacker_stack, sha: 'deadbeef...', ...)`.
3. Stub `Shipit.github(organization: 'attacker').verify_webhook_signature` to return `true` (simulating a correctly signed request from the attacker's own org), and do **not** stub/verify anything for `victim`.
4. POST a `status` webhook payload: `{ sha: 'deadbeef...', state: 'success', repository: { full_name: 'attacker/evil', owner: { login: 'attacker' } } }`.
5. Assert the binding is broken:
```ruby
assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [victim_stack]) do
  post :create, body: payload.to_json, as: :json
end
assert_equal 1, victim_commit.reload.statuses.count
```
6. Show the equality fails: the organization that authenticated (`attacker`) is not `victim_stack.repository.owner`, yet `ContinuousDeliveryJob` was enqueued with `victim_stack` as the argument - proving the cross-repository mutation.
