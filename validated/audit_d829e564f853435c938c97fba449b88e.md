### Title
PoX-5 signer-set aggregation collapses malformed/short signer keys to an all-zero key, double-counting stacked uSTX under one unownable identity - ([File: stackslib/src/chainstate/nakamoto/signer_set.rs])

### Summary
This is confirmed by both the pre-existing PoX-4 path and the newer PoX-5 path in `signer_set.rs`: when a stored signer-key buffer is not exactly `SIGNERS_PK_LEN` (33) bytes, the code silently substitutes an all-zero `[u8; 33]` key instead of skipping/rejecting the entry. This is the direct analog of the OpenClaw bug class: a lookup/validation ("channel type"/key-shape check) that fails open into a default identity rather than failing closed, letting otherwise-distinct principals be folded into a shared, spoofable identity.

### Finding Description
In the PoX-4 reward-address parser: [1](#0-0) 
the code explicitly comments "`(buff 33)` only enforces max size, not min size, so we need to do a len check" and, if the length check fails, substitutes `[0; SIGNERS_PK_LEN]` for the signer key rather than dropping the entry or erroring.

The PoX-5 iterator (`StakeEntryIteratorPox5::fallible_next`) has the identical pattern: [2](#0-1) 
Here `get-signer-info` returns a Clarity `(buff 33)` value that Clarity only bounds from above; if the on-chain stored buffer for some registrant is shorter than 33 bytes (e.g., 0 bytes), `signer_key_buff.try_into()` fails and `unwrap_or([0; SIGNERS_PK_LEN])` maps it to the all-zero key. This entry is *not* skipped via `PoxEntryParsingError::Skip` (unlike essentially every other fallible step in the same function, which do skip on error) — it is instead accepted with a bogus zero signing key and passed downstream.

Downstream, `pox_5_make_signer_set` aggregates entries by `signer_key` using a hashmap keyed on the raw 33-byte array: [3](#0-2) 
Any number of distinct stackers whose stored `signer-key` buffer happens to be short (or zero-length) will all collapse into the single `[0;33]` bucket, and their `amount_ustx` is summed (`+=`) into that one synthetic entry. This entry then receives real reward-slot weight (`weight = stacked_amt / threshold`, possibly plus a Hare-round leftover slot) in the computed `NakamotoSignerEntry` set: [4](#0-3) 

This breaks the equality that signer-set weight must correspond 1:1 to STX actually locked under a *specific, controllable* signing key: multiple stackers' locked STX get double-counted/merged into one non-existent signer identity (`0x000...000`, not a valid secp256k1 point), while any single such stacker's real signer key (if it also legitimately registered elsewhere with a valid 33-byte key) is under-weighted relative to their locked stake. The resulting `.signers` contract state and the reward-set the Nakamoto coordinator uses to validate block-commits/signatures thus assigns aggregate signing weight that is not actually attributable to (and cannot be exercised by) any single legitimate signer — an unsigned/unattributable stacking-weight allocation, and a double-counting of distinct stackers' commitments under one slot.

### Impact Explanation
Per the rules, "double-counting a commitment or reward" mapped through pox-5/pox-locking is Critical-tier. Concretely:
- Two or more stackers whose `signer-key` entries are malformed (however that malformation arises — buggy/experimental client, or a contract that stores fewer than 33 bytes) get merged into one signer-set entry, meaning the recorded `stacked_amt` for that entry is the *sum* of unrelated stackers' locked STX rather than one signer's stake — this inflates the effective weight the network attributes to a phantom "signer" beyond what any real key controls.
- Because the key is `[0;33]`, no one holds the private key for it, so the weight allocated there can never be exercised for legitimate signing, effectively pulling reward-slot/voting weight away from real signers while still counting toward `total_ustx_locked` and slot apportionment, skewing the consensus threshold calculations that gate block-commit/signature validation (`compute_voting_weight_threshold`).
- This is a systemic, protocol-level correctness violation of the signer-set/threshold computation that underlies Nakamoto block signing, not merely a griefing/DoS concern.

### Likelihood Explanation
Reachability depends on whether the on-chain `signers`/pox-5 `signer-key`-bearing map can ever legitimately hold a buffer shorter than 33 bytes. The code's own comment ("`(buff 33)` only enforces max size, not min size") indicates the authors are aware this is possible and is not merely a theoretical Clarity type quirk — the length check exists specifically because Clarity's `(buff 33)` allows shorter buffers to type-check. Whether pox-5.clar's `register-signer`/`set-signer-key-authorization` path additionally enforces exact 33-byte length before storing (which would foreclose this path) could not be conclusively verified in the time available — the grep against `pox-5.clar` returned matches but I was not able to inspect the actual length-validation logic in `register-signer` before the tool budget ran out. This is the key open question for confirming exploitability by an unprivileged stacker versus this only being reachable via already-corrupted/legacy state.

### Recommendation
- Replace `unwrap_or([0; SIGNERS_PK_LEN])` in `StakeEntryIteratorPox5::fallible_next` (and the equivalent PoX-4 `RawRewardSetEntry` parsing) with a `PoxEntryParsingError::Skip` (or equivalent hard error) when the stored signer-key buffer length is not exactly `SIGNERS_PK_LEN`, matching the skip-on-error behavior used elsewhere in the same function, instead of silently defaulting to a shared sentinel key.
- Independently, enforce an exact-length check (`len == 33`) on `signer-key` at the point of storage in the relevant `pox-5.clar`/`pox-4.clar` registration functions so malformed keys can never be persisted in the first place.

### Proof of Concept
Conceptual (could not fully verify the on-chain write path in the time available):
1. Cause (via whatever contract-level path permits it) two or more distinct stackers' `signer-key` entries to be stored with length ≠ 33 bytes in the map read by `get-signer-info` (e.g., an empty buffer).
2. At the next prepare-phase boundary, `StakeEntryIteratorPox5::fallible_next` reads each such entry, fails the `try_into::<[u8;33]>()`, and defaults both to `signer_key = [0;33]`.
3. `pox_5_make_signer_set` sums both stackers' `amount_ustx` into the single `[0;33]` bucket via `entry(...).and_modify(|e| *e += amount_ustx)`, producing one `NakamotoSignerEntry` with `stacked_amt` equal to the combined total and weight computed from that combined total — weight that is unattributable to any real signing key and that double-counts what should have been two independent, smaller entries.
