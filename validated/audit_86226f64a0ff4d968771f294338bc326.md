### Title
`liquidate` pauses only check the debt asset's grace period, not the collateral asset's - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
Attacker A liquidates a position by choosing a debt asset X whose own liquidation-grace/pause is inactive, while the collateral asset Y is currently under a DAO-set liquidation grace period intended to shield Y from liquidation activity. Because `liquidate` only calls `is-liquidation-paused` with `debt-aid`, the grace period the DAO set for Y (asset Y's suppliers, victim B) is never consulted, letting A seize Y collateral during the exact window it was meant to be protected, harming Y's suppliers.

### Finding Description
`is-liquidation-paused` reads the manual pause flag, the global grace-end, and the per-asset grace-end keyed by a single `asset-id`: [1](#0-0) 

`liquidate` calls this check using only `debt-aid`, never `coll-aid`: [2](#0-1) 

The per-asset grace map is set by `set-liquidation-grace-period (id uint) (grace-period uint)`, which stores a grace-end keyed on whatever asset id is passed: [3](#0-2) 

The documented purpose of the per-asset grace is generic - "prevents immediate liquidation cascade" for an asset after a pause/incident is lifted - not scoped to "only when the asset is the debt leg": [4](#0-3) 

Because `is-liquidation-paused` is invoked with `debt-aid` only, a grace period entry keyed on collateral asset Y's id (`liquidation-grace-periods[Y]`) has zero effect on any `liquidate` call where Y is used as the *collateral* leg - it is only read when Y happens to be the *debt* leg of some other liquidation. A can therefore always defeat an asset-level pause on Y simply by structuring the liquidation call so that Y is the `collateral-ft` and picking any debt asset X (with a long `max-staleness`, so its own price/oracle checks pass trivially and don't mask the result) whose grace/pause is not active. The health check, same-block guard, and slippage check (`min-collateral-expected`) do not reference the grace map at all, so none of them catch this: [5](#0-4) 

Shared state: `liquidation-grace-periods` map entry for asset Y, written by the DAO's `set-liquidation-grace-period` call and read (or, critically, *not* read for the collateral role) by A's `liquidate` transaction.

### Impact Explanation
Y's suppliers (B) lose the intended protection window: their collateral can be seized by liquidators even while the DAO believed liquidations touching Y were paused (e.g., during oracle/vault instability on Y). If Y's price or accounting was unreliable during that window (which is exactly why the grace period was set), improperly executed liquidations can seize collateral at incorrect valuations and leave under-collateralized debt behind, which is later socialized via `vault-socialize-debt`, propagating losses across all suppliers of the affected vault. This is a protocol insolvency risk (Critical), since bad debt created during a period the DAO explicitly intended to be liquidation-free is spread across the pool.

### Likelihood Explanation
Preconditions: the DAO must have set (or have active) a liquidation grace period keyed on the collateral asset's id - a normal, expected operational action (post-incident unpause), not a misconfiguration. A only needs to be an ordinary liquidator with a liquidatable position to target and pick any debt asset whose own grace/pause is inactive - trivial and repeatable, at essentially zero extra cost beyond a normal liquidation. A does not need privileged access; A profits normally from the liquidation bonus, so the attack is economically rational and repeatable for every liquidatable position with the desired collateral asset during the grace window.

### Recommendation
Extend `is-liquidation-paused` (or add a second check) to also validate the collateral asset's grace/pause state, e.g. `(asserts! (and (not (is-liquidation-paused debt-aid)) (not (is-liquidation-paused coll-aid))) ERR-LIQUIDATION-PAUSED)`, so a per-asset grace period blocks liquidations where that asset is used in either the debt or collateral role.

### Proof of Concept
Clarinet/vitest simnet two-account plan:
1. Setup: register assets X (debt, long `max-staleness`) and Y (collateral) in `assets.clar`; create a borrower position with Y as collateral and X as debt that is liquidatable (LTV above `ltv-liq-partial`).
2. Baseline (B alone): DAO calls `set-liquidation-grace-period(Y-id, long-period)`. As A, call `liquidate(borrower, Y-ft, X-ft, debt-amount, 0, none, price-feeds)` with fresh valid prices for both X and Y. Assert it succeeds and Y collateral is seized (showing the Y-keyed grace period had no effect on collateral-side liquidation).
3. Control (expected-safe alternate call): Repeat the same position/prices but call `liquidate` with X as collateral and Y as debt (i.e., set `debt-aid = Y-id`). Assert it now reverts with `ERR-LIQUIDATION-PAUSED`, proving the grace map entry for Y is only honored when Y is the debt leg.
4. Diff: identical price freshness and grace-map state, only the role assignment (debt vs collateral) of Y differs between steps 2 and 3, and the liquidate outcome flips - demonstrating the missing collateral-side pause check independent of oracle staleness.

(define-private (is-liquidation-paused (asset-id uint))
  (let ((manual-pause (var-get pause-liquidation))
        (global-grace-end (default-to u0 (map-get? liquidation-grace-periods GLOBAL-LIQUIDATION-GRACE-ID)))
        (asset-grace-end (default-to u0 (map-get? liquidation-grace-periods asset-id)))
        (global-grace-active (< stacks-block-time global-grace-end))
        (asset-grace-active (< stacks-block-time asset-grace-end)))

        asset-id: id,
        grace-period: grace-period,
        grace-end: (+ stacks-block-time grace-period)
