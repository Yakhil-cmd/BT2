## Title
Frontrunning of state-dependent exact-amount checks in AAs causes guaranteed bounce-fee loss for legitimate triggers - (File: aa_composer.js, test/samples/uniswap_like_market_maker.oscript)

### Summary
Autonomous Agents (AAs) that compute an "expected" payment amount from mutable state (`balance[...]`, `var[...]`) at the moment a trigger unit is composed, and then require the actual `trigger.output` to match that expectation exactly (bouncing otherwise), are vulnerable to the same class of frontrunning issue described in the Aloe `Lender.repay` report: an unprivileged third party can post a small trigger to the same AA before the victim's trigger is processed on the DAG, shifting the AA's balance/state so the victim's precomputed exact amount no longer matches. Unlike the EVM case (where the failed call simply reverts with no loss beyond gas), in ocore the AA's `bounce()` logic unconditionally consumes the `bounce_fees` portion of the trigger's payment before refunding the remainder, so every griefed trigger causes a guaranteed, non-refundable loss of funds to the victim.

### Finding Description
Money-market/DEX-style AAs shipped as reference designs in this repository compute a required amount from the AA's current balance and then enforce an exact match against the trigger's payment, bouncing if it does not match: [1](#0-0) 

Here `$current_ratio` and `$expected_asset_amount` are derived from `balance[$asset]`/`balance[base]` at execution time, and the trigger bounces with `'wrong ratio of amounts, expected ...'` if `trigger.output[[asset=$asset]]` doesn't match exactly. The same pattern (exact-amount computed from state, bounce on mismatch) also appears in `test/samples/order_book_exchange.oscript`.

Because AA triggers are ordinary units posted to the DAG, any unprivileged party can observe a pending trigger (e.g. in the mempool/tips) and race it with their own trigger to the same AA. If the attacker's trigger is selected as a parent/processed first by `aa_composer.js`'s trigger-ordering logic (`pickParents`), it changes `balance[...]`/`var[...]` before the victim's trigger executes, so the victim's precomputed `$expected_asset_amount` (or any similar exact check) fails and `bounce()` is invoked: [2](#0-1) 

Critically, `bounce()` does not refund the victim in full: it subtracts `bounce_fees[asset]` from the received amount and only returns `bounced_amount = amount - fee` to `trigger.address`, keeping the fee for the AA: [3](#0-2) 

This mirrors the Aloe finding precisely — an unprivileged actor can grief any single legitimate transaction that depends on an exact amount computed from state at composition time — except that in ocore the victim also suffers a concrete, non-refundable loss (the `bounce_fees`), whereas the referenced audit describes only failed execution.

### Impact Explanation
Any AA that follows this common "compute exact amount from current balance/ratio, bounce on mismatch" pattern (as demonstrated in the shipped reference `uniswap_like_market_maker.oscript` and `order_book_exchange.oscript`) allows a griefer to force victims' triggers to bounce at will, causing:
- Guaranteed loss of `bounce_fees` (AA fund loss for the victim) on every griefed interaction.
- Failed execution of time-sensitive operations (e.g., trading against a moving ratio), which for AMM/order-book style AAs is directly analogous to the money-market strategy timing risk cited in the original report.
- Repeated griefing is essentially free for the attacker (a small trigger to shift the ratio) and can be executed indefinitely against any victim.

### Likelihood Explanation
Any address can observe a pending trigger and submit a competing trigger to the same AA; this requires no special privilege and is directly reachable by an ordinary AA trigger sender. The pattern of computing exact amounts from state and bouncing on mismatch is explicitly used in the project's own reference AA templates, so it is a realistic, endorsed design pattern that real-world AAs are likely to copy.

### Recommendation
- In AA design guidance/templates, avoid bouncing on strict inequality against a value derived from mutable state; instead compute outputs from the actual `trigger.output` amount (e.g., accept a tolerance/slippage parameter supplied by the trigger and clamp/compute proportional shares) rather than requiring the trigger to have pre-guessed an exact state-dependent amount.
- Where an exact check is unavoidable, refund the entire `trigger.output` (not `amount - bounce_fees`) on bounce for state-mismatch-only failures, or make `bounce_fees` optional/waivable for such cases, so a griefed sender doesn't suffer fund loss on top of a failed interaction.
- Provide official guidance/warnings in the AA documentation and in `test/samples/*` comments about the frontrunning risk of exact-match state-dependent conditions in `messages.if`/`bounce`.

### Proof of Concept
1. Deploy an AA equivalent to `test/samples/uniswap_like_market_maker.oscript`'s "invest in MM" case (lines 33-48), which computes `$expected_asset_amount = round($current_ratio * trigger.output[[asset=base]])` and bounces if the trigger's actual asset output does not match exactly.
2. Victim composes and broadcasts a trigger unit sending `base` and the exact `$asset` amount computed against the AA's current balance.
3. Attacker observes the pending trigger and quickly posts their own small trigger to the same AA (e.g., a tiny investment/divestment) that gets included/processed first, changing `balance[$asset]`/`balance[base]` and hence `$current_ratio`.
4. When the victim's trigger is processed by `aa_composer.js`, `$expected_asset_amount` no longer equals `trigger.output[[asset=$asset]]`, so the `if` in `evaluateAA` fails to satisfy the mismatch check and `bounce('wrong ratio of amounts...')` is called.
5. `bounce()` (aa_composer.js lines 932-944) refunds only `amount - bounce_fees[asset]` to the victim, permanently consuming the `bounce_fees` — demonstrating both failed execution and concrete fund loss caused purely by front-running.
