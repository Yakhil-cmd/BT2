### Title
Generic `is_valid_signed_package`/`signed_message` primitive has no built-in context/type binding, allowing a validly signed off-chain message to be replayed across different AA schemas or channel instances — ([File: formula/evaluation.js], [File: signed_message.js])

### Summary
Ocore exposes a generic off-chain signing primitive (`signMessage`/`validateSignedMessage` in `signed_message.js`, exposed to oscript via `is_valid_signed_package`/`is_valid_sig` in `formula/evaluation.js`) that AA authors use to let two parties exchange authenticated, off-chain messages (state channels, order books, etc.) which are later posted on-chain as `trigger.data`. The primitive authenticates only the *signer address* and the *literal bytes* of `signed_message`; it does not itself bind the signed content to any application, instance, or purpose. Exactly like the Astaria `nlrType` issue — where the strategist's signature covered a `Details` struct but not the discriminator (`nlrType`) that determines how the struct is interpreted — here the framework signs an arbitrary payload but leaves any "type"/context discriminator entirely up to the AA's own schema. If two AAs (or two instances of the same AA template, e.g. two independent payment channels controlled by the same signer) use overlapping payload schemas, a message validly signed for one context can be replayed/misinterpreted in another, because nothing in the cryptographic envelope forces a binding.

### Finding Description
`validateSignedMessage` in [1](#0-0)  only checks that `signed_message`, `authors`, `last_ball_unit`, `timestamp`, `version` are well formed and that the listed address(es) actually signed the object; the *content* of `signed_message` (the actual payload interpreted by the AA) is treated as an opaque, application-defined structure — no field is reserved by the framework to disambiguate "what kind of message is this" or "which contract/instance is this message meant for."

In oscript, `is_valid_signed_package` (`formula/evaluation.js` [2](#0-1)  ) merely re-validates the same envelope and returns true/false; it takes the expected signer address as a parameter but nothing that binds the message to *this specific AA instance or purpose*.

Because of this, ocore's own reference AA templates have to manually invent and check a discriminator field inside the signed payload to avoid cross-context replay. For example, `test/samples/payment_channels.oscript` explicitly checks:
```
if (trigger.data.sentByPeer.signed_message.channel != this_address)
    bounce('signed for another channel');
if (trigger.data.sentByPeer.signed_message.period != var['period'])
    bounce('signed for a different period of this channel');
``` [3](#0-2) 

and `test/samples/order_book_exchange.oscript` relies on schema fields (`sell_asset`/`buy_asset`) plus manually-derived IDs to distinguish one signed order from another, again with no framework-level type tag: [4](#0-3) 

These examples prove the underlying risk is real and already required a workaround by the ocore authors themselves: the signing/verification primitive alone (`is_valid_signed_package` + `signed_message`) provides no type/context separation. Any third-party AA author who reuses this primitive without independently inventing and checking such a discriminator (exactly the omission flagged in the original report — "the lien type is not signed by the strategist") can have off-chain-signed messages meant for one AA, one channel instance, or one purpose accepted by a different AA/instance/purpose whose payload schema happens to overlap, because the address-plus-payload signature says nothing about *where* the payload should be consumed.

### Impact Explanation
If an AA author builds a signed-message-consuming contract (state channel, order book, escrow release, etc.) and — like the strategist in the original report — assumes the schema of the signed struct alone is sufficient to disambiguate intent, a counterparty or attacker who controls or replays a signed package from one context can have it accepted in another context governed by the same signer address (e.g., two channels between the same peers, or two structurally similar AAs). This can produce unauthorized fund movement / fund loss within the receiving AA, exactly the "AA fund loss" impact category, because the AA has no cryptographic guarantee that the message was intended for it.

### Likelihood Explanation
Likelihood is moderate: it requires an AA author to omit a manual context/type field (as the shipped examples show is easy to forget, since the framework does not enforce or even suggest it structurally), and requires the same signer to be reused across two schema-overlapping deployments. Given that ocore's own canonical examples had to bolt on ad-hoc `channel`/`period` checks to close this exact gap, it is a realistic and recurring pitfall for the class of AAs that rely on `is_valid_signed_package`.

### Recommendation
Extend the signed-message primitive so context binding is enforced by the framework rather than left to convention:
- Require (or strongly encourage via a dedicated field) that `signed_message` payloads used with `is_valid_signed_package` include a mandatory, framework-checked discriminator such as the consuming AA's `this_address` and/or an explicit `type`/`app` tag, verified automatically in `validateSignedMessage` (`signed_message.js`) and in the `is_valid_signed_package` handler (`formula/evaluation.js`), rather than relying on each AA author to reimplement the check as done ad hoc in `payment_channels.oscript`.
- Document this requirement clearly for AA authors as a mandatory pattern when accepting off-chain signed data, analogous to including `nlrType` in the signed leaf in the original recommendation.

### Proof of Concept
1. Author deploys AA "ChannelX" using the `payment_channels.oscript` pattern but forgets to check `signed_message.channel != this_address` (a plausible omission since the framework does not enforce it).
2. The same two peers (address A, address B) also run "ChannelY", another instance/AA with an overlapping payload schema (`{channel, period, amount_spent}`).
3. A message signed by peer A authorizing a balance state in ChannelY is submitted as `trigger.data.sentByPeer` to ChannelX.
4. `is_valid_signed_package(trigger.data.sentByPeer, addressA)` in `formula/evaluation.js` returns true because it only validates that address A signed the bytes — it has no way to know the message was meant for ChannelY, not ChannelX.
5. ChannelX incorrectly accepts a balance/spend value that was never intended for it, resulting in unauthorized fund movement.
