### Title
Cross-tenant repository confusion in webhook processing — organization that authenticates the signature is never bound to the repository whose state is written - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController` selects which GitHub App/webhook secret to verify a webhook's HMAC signature against using one payload field (`repository.owner.login` / `organization.login`), but the downstream handlers that mutate application state select the target `Repository`/`Stack`/`Commit` using a *different, unauthenticated* payload field (`repository.full_name`), or in the case of `StatusHandler`, no repository scoping at all. This mirrors the reported bug class: data is trusted structurally (the signature check passes) without validating that the "discriminator" of the payload — here, the actual repository/organization the effects apply to — corresponds to the identity that was cryptographically bound during verification.

### Finding Description
In `Shipit::WebhooksController#verify_signature`, the GitHub App config (and thus the `webhook_secret` used to validate `X-Hub-Signature`) is chosen based on: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository','owner','login')`. This selects which per-organization `Shipit.github(organization: ...)` config (see the multi-org secrets format in `test/dummy/config/secrets_double_github_app.yml`) validates the HMAC over the raw body.

Once the signature is accepted, the whole raw JSON `params` is dispatched unchanged to every registered handler for that event: [3](#0-2) 

Handlers determine which `Repository`/`Stack` to act on via a *separate* field, `repository.full_name`, with no cross-check against the org used for signature selection: [4](#0-3) [5](#0-4) 

`StatusHandler` is even weaker: it doesn't scope by repository at all, only by commit SHA, globally across the entire instance: [6](#0-5) 

`Status#after_create` triggers continuous deployment automatically: [7](#0-6) [8](#0-7) [9](#0-8) 

This breaks the equality the rules require: **organization that authenticated (via `repository.owner.login` → its own `webhook_secret`) == repository that is written (via `repository.full_name`)**. Before the attack, these two fields always agree for legitimate GitHub-originated webhooks (GitHub itself sets both consistently). After an attacker-controlled request, the attacker (who controls a GitHub App/webhook config for one organization on a multi-tenant Shipit install, as documented by the dual-app secrets format) can set `repository.owner.login` to their own org (so the signature validates against a secret they know) while setting `repository.full_name` to an entirely different organization's repository tracked by the same Shipit instance.

### Impact Explanation
An attacker who administers their own GitHub App/webhook configuration for "OrgOne" (a legitimate, unprivileged tenant with no rights to "OrgTwo") can forge a signed `status` (or `push`, `check_suite`, `pull_request`) webhook whose `repository.owner.login` is `OrgOne` but whose `repository.full_name`/matched commit SHA belongs to `OrgTwo`. Because the signature is only checked against `OrgOne`'s secret and the payload's internal consistency is never re-validated, the forged event is accepted and dispatched to handlers operating on `OrgTwo`'s stacks:
- `StatusHandler` can inject an attacker-controlled `success` `Status` on any commit whose SHA it names, on any stack in the instance, since it scopes only by `Commit.sha` — no repository check at all. If the target stack has `continuous_deployment` enabled, this directly triggers `schedule_continuous_delivery` → `ContinuousDeliveryJob` → an unauthorized deploy of another organization's repository.
- `PushHandler` can force `GithubSyncJob`/`sync_github` calls against another organization's stacks with an attacker-chosen `expected_head_sha`.
- `PullRequest::*Handler`s can mutate PR/review-stack state cross-tenant.

Triggering an unauthorized deploy for a repository the attacker has no access to meets the Critical bar ("an unauthorized deploy... or rollback").

### Likelihood Explanation
Exploitability depends on the deployment being multi-tenant (multiple GitHub organizations/Apps configured on one Shipit instance, an explicitly supported and documented configuration per `test/dummy/config/secrets_double_github_app.yml`). Given that configuration, the attack requires no privileged Shipit credentials, no `ApiClient` token, and no access to the target organization — only the ability to send an HTTP POST to the public `/github/webhooks` endpoint with a body signed using a webhook secret the attacker legitimately possesses for their own tenant. This is a realistic path for any Shipit deployment serving more than one GitHub organization.

### Recommendation
After signature verification, re-derive the organization used to select the verification key strictly from the same identity that authorizes state mutation, and reject the request if `repository.full_name`'s owner does not match `repository_owner`. Concretely:
- In `WebhooksController#verify_signature`, capture the verified `repository_owner` and pass it into handler dispatch.
- In `Shipit::Webhooks::Handlers::Handler`, validate that `payload.dig('repository','full_name').split('/').first` (case-insensitively) equals the verified organization before resolving `Repository.from_github_repo_name`; reject (422) on mismatch.
- Fix `StatusHandler` specifically to scope `Commit.where(sha: params.sha)` further by `stack.repository` matching the verified organization, not merely by SHA.

### Proof of Concept
1. Configure a self-hosted Shipit instance with two GitHub App tenants, `OrgOne` and `OrgTwo`, per the multi-org format shown in `test/dummy/config/secrets_double_github_app.yml`.
2. As an administrator of `OrgOne` (unprivileged w.r.t. `OrgTwo`), obtain `OrgOne`'s `webhook_secret` (which they legitimately control for their own App).
3. Craft a `status` webhook payload with:
   - `sha`: the SHA of a commit belonging to a stack in `OrgTwo` that has `continuous_deployment: true`.
   - `state`: `success`
   - `repository.owner.login`: `OrgOne` (so `WebhooksController#repository_owner` resolves to `OrgOne`, whose secret the attacker controls)
4. Sign the raw JSON body with `HMAC-SHA1(OrgOne_webhook_secret, body)` and set `X-Hub-Signature`, `X-Github-Event: status`.
5. POST to `/github/webhooks`. `verify_signature` succeeds (checked against `OrgOne`). `StatusHandler#process` finds the `OrgTwo` commit purely by SHA and calls `create_status_from_github!`, creating a `success` `Status`, which (per `Status#after_create`) invokes `schedule_continuous_delivery`, deploying `OrgTwo`'s stack — a cross-tenant, unauthorized deploy triggered entirely with `OrgOne`'s own credentials.
