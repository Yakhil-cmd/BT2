### Title
Webhook organization used for signature verification is decoupled from the repository/commit the handler actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate a webhook against using `repository_owner`, a value read out of the attacker-supplied JSON body itself (`repository.owner.login` or `organization.login`). The event handlers that subsequently act on the same body (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolve the target repository/commit/stack from a *different* field of the same body (`repository.full_name`, or in `StatusHandler`'s case no repository field at all). Because `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved organization has no `webhook_secret` configured — a state explicitly documented as optional and supported for multi-organization installs — an attacker only needs one onboarded organization with no secret to authenticate a forged webhook whose payload actually targets stacks/commits belonging to a completely different, secured organization.

### Finding Description
`verify_signature` picks the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` trivially passes when the selected organization has no secret configured: [3](#0-2) 

The webhook secret is explicitly documented as optional per organization, and installs can configure several organizations independently: [4](#0-3) [5](#0-4) 

Once past `verify_signature`, `WebhooksController#create` dispatches the raw parsed body to every handler for the event, unmodified and unscoped to the organization that was used for authentication: [6](#0-5) 

Handlers resolve their target repository from `repository.full_name`, a field completely independent of `repository.owner.login`/`organization.login` used during signature verification: [7](#0-6) [8](#0-7) 

`StatusHandler` is worse still — it does not consult any repository field at all, matching commits globally by SHA across the entire install: [9](#0-8) 

The binding that should hold is: `organization authenticated (repository_owner used to pick the GitHubApp/secret) == organization/repository actually written to (repository.full_name / commit lookup in the handler)`. Because the attacker fully controls the JSON body before it is authenticated, they can make these two diverge: claim to be an organization with no configured secret (which authenticates for free) while writing against a repository/commit belonging to a different, secured organization's stack.

### Impact Explanation
This is a High-severity authorization boundary break: an unauthenticated, unprivileged network attacker who merely knows (or discovers, e.g. via error responses distinguishing `GithubOrganizationUnknown` from a processed request) that any organization configured on the Shipit instance has no `webhook_secret` set can:
- Force `GithubSyncJob` / `sync_github` calls against stacks of any other tracked repository via a forged `push` event whose `repository.full_name` points at the victim org's repo (`PushHandler`).
- Forge CI `status` updates (`state: success`) against arbitrary commits across the whole install via `StatusHandler`, which performs no repository scoping whatsoever — this can flip `deployable_status` for commits that gate automatic deploys.
- Trigger `RefreshCheckRunsJob`/other stack-scoped side effects via `CheckSuiteHandler` for any tracked branch/commit.

This can lead to unauthorized deploy-pipeline state changes (forged CI status enabling deploys of commits that never actually passed CI) without ever touching the secured organization's own `webhook_secret`, `github_access_token`, or repository permissions — satisfying the "escalation into deployable_status" / "unauthorized deploy" bar without requiring possession of any of the excluded credentials.

### Likelihood Explanation
Exploitability depends only on the operator's own multi-org configuration containing at least one organization without a webhook secret (explicitly supported and documented as optional), which is plausible in real multi-tenant Shipit deployments (as shown by the sample multi-org secrets file). No GitHub credentials, session, or repository write access are required — only the ability to POST arbitrary JSON to the public `/webhooks` endpoint with a matching `X-Github-Event` header.

### Recommendation
Bind the signature-verification organization to the repository actually acted upon: derive the organization used for `Shipit.github(organization: ...)` from the same repository the handler will subsequently look up (e.g. `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner`), and reject the webhook if these two do not match. Additionally, make `StatusHandler` (and any other handler lacking repository scoping) filter commits/stacks by the authenticated repository rather than matching globally by SHA. Consider making `webhook_secret` mandatory per organization rather than optional.

### Proof of Concept
1. Shipit instance configures two GitHub organizations: `openorg` (no `webhook_secret`) and `securedorg` (with a `webhook_secret`), each with tracked stacks — a supported and documented configuration.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "organization": { "login": "openorg" },
  "sha": "<sha of a commit belonging to a securedorg stack>",
  "state": "success",
  "context": "ci/tests"
}
```
without any valid `X-Hub-Signature`.
3. `verify_signature` resolves `repository_owner` to `openorg`, which has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a forged successful CI status on the `securedorg` commit, with no relation to `openorg` at all, potentially unblocking a deploy that depends on that status.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
