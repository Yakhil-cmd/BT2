### Title
Webhook signature is bound to `repository.owner.login`, not to `repository.full_name` the handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App config (and its `webhook_secret`) using `repository_owner`, which is read from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the HMAC check passes, the full raw payload is handed to every registered handler, and each handler independently re-derives the target repository from `payload.dig('repository','full_name')` (or `params.repository.full_name`) to find the `Stack`/`Repository` to mutate. The signature only proves "this body was signed with organization X's secret" - it never proves that `repository.full_name` in that same body actually belongs to organization X.

### Finding Description
The equality that should hold is:
`organization whose webhook_secret verified the signature == owner prefix of the repository.full_name the handler writes to`

The code never enforces this. `verify_signature` in [5](#0-4)  calls `Shipit.github(organization: repository_owner)` and verifies the raw body against that org's `webhook_secret`. `repository_owner` is computed from the same attacker-suppliable JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` ( [6](#0-5) ). Handlers such as `Handler#stacks`/`#repository_name` ( [3](#0-2) ), `PushHandler`, `StatusHandler` ( [2](#0-1) ), and all the `PullRequest::*Handler` classes look up `Repository.from_github_repo_name(payload.dig('repository','full_name'))` ( [4](#0-3) ) from the *same* untrusted body, but never compare that owner to `repository_owner` used for signature selection. In a multi-tenant Shipit install (the config format explicitly supports several independent organizations, each with its own GitHub App/`webhook_secret`, as shown in `config/secrets.development.shopify.yml`), an org admin who legitimately controls their own org's GitHub App/webhook secret can sign an arbitrary JSON body with that secret while setting `repository.owner.login` to their own org (so `verify_signature` passes) but setting `repository.full_name` to `"other-org/other-repo"` (so the handler operates on a completely different tenant's stack). Because `Status`/`Commit` webhook processing (`StatusHandler#process` → `Commit#create_status_from_github!`) trusts payload fields (`state`, `context`, `target_url`, `description`) verbatim to create `Status` rows, this lets a legitimately-onboarded-but-malicious org owner forge CI/status results, unarchive/archive review stacks, or trigger `GithubSyncJob` syncs against another tenant's repository that they were never granted access to.

### Impact Explanation
This crosses a credential/repository boundary the engine is supposed to enforce: possession of a valid webhook secret for org A is being treated as authorization to write into org B's `Stack`/`Commit`/`PullRequest`/`Repository` records. Forged `status` events can flip a commit's CI state to `success`, which feeds directly into `MergeRequest#any_status_checks_failed?`/merge queue logic and deploy gating, enabling an unauthorized merge or deploy on a repository the attacker does not own — matching the Critical "unauthorized deploy, rollback or merge" / "cross-repository writes" bar.

### Likelihood Explanation
Requires only that the target Shipit instance is configured for more than one GitHub organization (a documented, supported configuration) and that the attacker already has legitimate, unprivileged admin access to their own onboarded organization/App (not the target org, no `webhook_secret` theft, no GitHub App private key, no Shipit session). This is a realistic misuse of an ordinary, expected credential rather than a stolen secret.

### Recommendation
After computing `repository_owner` and verifying the signature, re-derive the repository/organization used by each handler from a value that is cryptographically bound to the org selected for verification (e.g., reject the webhook, or refuse to resolve `Repository.from_github_repo_name`, whenever the owner prefix of `repository.full_name`/`organization.login` in the payload does not case-insensitively match `repository_owner`).

### Proof of Concept
1. Shipit is configured with two orgs, `orgA` (attacker-controlled GitHub App/webhook, `webhook_secret = secretA`) and `orgB` (victim, has a tracked `Stack` for `orgB/app`).
2. Attacker crafts a `status` event JSON body: `{"sha": "<victim commit sha>", "state": "success", "context": "ci/required", "repository": {"full_name": "orgB/app", "owner": {"login": "orgA"}}}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(secretA, body)` using their own legitimate `secretA`, and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner == "orgA"`, fetches `Shipit.github(organization: "orgA")`, and the HMAC matches → verification succeeds.
5. `StatusHandler#process` finds `Commit` rows by `sha` (global lookup, not scoped by org) belonging to `orgB`'s stack and calls `create_status_from_github!`, creating a forged `success` `Status` for `orgB`'s commit, potentially unblocking a merge/deploy the attacker has no rights over.
