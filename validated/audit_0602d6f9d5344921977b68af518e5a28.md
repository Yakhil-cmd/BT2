### Title
Inline-dict comma-splitting in `extract_frontmatter` silently corrupts guard-rule `pattern` values, causing rule display to diverge from actual runtime enforcement - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`extract_frontmatter`'s inline-dict branch parses a list item such as `- field: command, operator: regex_match, pattern: rm\s+-rf,\s*/` by naively splitting the entire `item_text` on every comma: [1](#0-0) 
It does not respect that the `pattern` value itself may legitimately contain commas (regex alternation lists, character classes, or literal comma-separated command arguments are common). Any comma inside the intended pattern splits it into extra "parts"; parts without a `:` (e.g. the tail `\s*/`) are silently dropped since the loop only assigns `item_dict[k]=v` `if ':' in part`. The result is a `Condition.pattern` that is truncated/altered from what the rule author (or reviewer) actually wrote and intended, feeding directly into `Condition.from_dict` → `Rule.conditions` → `RuleEngine._check_condition` → `_regex_match`, which is the exact code path used by every real hookify enforcement hook (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`, all of which call `load_rules()` → `load_rule_file()` → `extract_frontmatter()`). [2](#0-1) 

Critically, `/hookify:list` (`plugins/hookify/commands/list.md`) is not a Python invocation of `config_loader.py` — it is an LLM-driven slash command that instructs Claude to `Read` the raw rule file and display fields such as `pattern`/conditions using its own (correct) understanding of the YAML-like text. [3](#0-2) 
This creates a divergence: the displayed rule (parsed correctly by the LLM from the literal file text) shows the intended dangerous-command pattern and "✅ Active/Enabled" status, while the actual enforcement engine that runs on every Bash/Edit/Stop event uses the corrupted, comma-truncated pattern produced by the buggy hand-rolled parser, and therefore may never match the dangerous command the rule was supposed to guard against.

### Impact Explanation
This is a false-guard / silent security-control degradation: a hookify rule intended to warn/block dangerous operations (e.g., `rm -rf`, destructive git commands, secret-exposing edits) can be rendered functionally inert at runtime while `/hookify:list` continues to report it as configured and enabled. A user or reviewer trusting the `/hookify:list` output would believe protection is active when it is not, enabling dangerous commands to proceed unflagged/unblocked. This matches a trust-boundary/approval-bypass class impact — the perceived guard (hook enforcement) silently fails to fire due to a parser defect, not a deliberate policy choice.

### Likelihood Explanation
Exploitability requires that the rule file use the inline-dict comma-separated condition syntax with a pattern value containing a comma. This is a plausible authoring pattern — regex patterns with alternation-like comma-containing content (e.g., `rm\s+-rf,\s*/` or multi-token dangerous-command detection) are reasonable for someone crafting a hookify rule, and nothing in `writing-rules/SKILL.md` warns against commas in inline-dict pattern values. It can occur either accidentally (a well-meaning rule author writes a pattern containing a comma and doesn't realize it silently breaks) or be deliberately planted by an attacker who can contribute a `.claude/hookify.*.local.md` file to a repository (e.g., via a PR "helpfully" adding a guard rule) since `load_rules()` globs and loads every matching file with no ownership/signature check. No special privilege beyond normal file-contribution capability is needed; the bug is 100% reproducible whenever an inline-dict condition's pattern contains a comma.

### Recommendation
Replace the hand-rolled inline-dict comma split in `extract_frontmatter` (config_loader.py lines 164-171) with a proper YAML parser (e.g., `yaml.safe_load` on the frontmatter block) or, at minimum, split only on the first two commas needed to separate `field:` and `operator:` and treat everything after the `pattern:` key as the remainder of the string (not comma-split). Additionally, add a warning/validation step that flags condition patterns which appear truncated (e.g., detect dangling `item_text` remainders with no `:` and raise a parse error instead of silently dropping them), and add an explicit note in `writing-rules/SKILL.md` recommending the multi-line dict form for patterns containing commas.

### Proof of Concept
Unit test against `extract_frontmatter`:
```python
from plugins.hookify.core.config_loader import extract_frontmatter, Rule

content = """---
name: warn-dangerous-rm
enabled: true
event: bash
conditions:
  - field: command, operator: regex_match, pattern: rm\\s+-rf,\\s*/
---

Dangerous rm command detected!
"""

fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)

# Expected (correct) behavior: full pattern preserved
assert rule.conditions[0].pattern == r"rm\s+-rf,\s*/"

# Actual (buggy) behavior observed: pattern truncated to r"rm\s+-rf"
# because the trailing ",\s*/" fragment has no ':' and is dropped.
```
Follow-up integration test: feed a `tool_input.command` value crafted to require the full pattern (e.g. one that only matches `rm\s+-rf,\s*/` as a whole but not the truncated prefix alone) through `RuleEngine.evaluate_rules` and confirm the rule fails to trigger with the corrupted pattern, while `/hookify:list`'s described display steps (reading raw frontmatter text) would still show the rule's `enabled: true` status — demonstrating the display/enforcement divergence.
