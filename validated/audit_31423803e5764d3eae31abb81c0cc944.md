### Title
Webhook organization used for signature verification is not bound to the repository the event payload actually writes to, allowing unauthenticated event forgery for any org with no `webhook_secret` configured - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config to use for HMAC verification based on `repository_owner`, a field read straight out of the untrusted, unverified JSON body. `verify_webhook_signature` treats a blank `webhook_secret` as automatically verified. Every event handler, however, resolves the repository to act on from a *different* field of the same untrusted body (`repository.full_name`). Because verification-organization and write-target-repository are two independent fields of an unauthenticated body, an attacker only needs one configured GitHub organization/App entry that has no `webhook_secret` set (a supported, documented configuration - see `test/dummy/config/secrets_double_github_app.yml`) to get a completely forged payload accepted and dispatched against an unrelated, real, tracked repository/stack.

### Finding Description
`verify_signature` computes the organization to check against solely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — both fields live inside the same raw, unauthenticated `request.raw_post` body that is being verified. `verify_webhook_signature` short-circuits to `true` whenever the resolved organization's `webhook_secret` is blank: [3](#0-2) 

This is a real, supported configuration state — the fixture `secrets_double_github_app.yml` explicitly configures an org (`OrgTwo`) with `webhook_secret: # nil`. [4](#0-3) 

Once `verify_signature` passes, `create` parses the *same* untrusted body and dispatches it to handlers based only on `X-Github-Event`: [5](#0-4) 

Every handler resolves the repository/stacks to mutate from `repository.full_name`, a field that was never checked against `repository_owner` (the field actually used to pick which org's secret — or absence thereof — governed verification): [6](#0-5) 

`PushHandler` then syncs GitHub state for any stack under that forged `full_name`, using an attacker-chosen SHA: [7](#0-6) 

Pull-request handlers similarly resolve `Repository.from_github_repo_name(params.repository.full_name)` and can archive/unarchive review stacks: [8](#0-7) [9](#0-8) 

**Binding broken:** *organization that authenticated* (`repository_owner`, used only to pick which secret — possibly absent — gates the request) `≠` *repository that is written* (`repository.full_name`, used unconditionally by every handler to find the `Stack`/`Repository` to mutate). Nothing ties these two fields together, and because the whole body is attacker-controlled when the resolved org has no `webhook_secret`, they can be made arbitrarily inconsistent.

### Impact Explanation
An unauthenticated network attacker who knows (or guesses) the login of any organization configured in Shipit's GitHub App settings *without* a `webhook_secret` can submit arbitrary, fully-controlled webhook payloads that are dispatched as if genuinely signed, targeting any *other* tracked repository/stack by setting `repository.full_name` accordingly. Consequences depending on event type:
- `push`: force `GithubSyncJob` to run with an attacker-chosen `expected_head_sha`, corrupting the commit/deploy history used to decide what is deployable.
- `pull_request` (`opened`/`labeled`/`reopened`/`closed`/`unlabeled`): forge provisioning/archival of review stacks for repositories the attacker does not control.
- `status`/`check_suite` style events on the same path could inject fabricated CI status onto real commits, undermining the "commit is deployable" safety check that gates `Deploy`/`Rollback` creation.

This maps to the report's "unauthorized deploy" / CI-integrity classes of High/Critical impact listed in scope, achieved with zero credentials, zero tokens, and zero prior access — purely by exploiting the mismatch between the field used to select (or skip) signature verification and the field used to decide what gets mutated.

### Likelihood Explanation
Requires only: (1) the deployment operator having at least one configured GitHub App/org entry without a `webhook_secret` (a state the codebase explicitly supports and ships a test fixture for), and (2) network access to the public `/webhooks` endpoint, which is mounted unauthenticated by design (it's meant to receive GitHub's callouts). No GitHub App private key, no `ApiClient` token, no session, and no social engineering are needed — only knowledge of the weakly-secured organization's login name, which is often public information (e.g., visible in Shipit's own UI/settings pages or GitHub org URLs).

### Recommendation
- Require `webhook_secret` to be present for every configured organization/App; refuse to boot or refuse verification (fail closed, not open) when it is absent, instead of returning `true`.
- Cross-validate that the organization used to select the verification secret is the same organization embedded in `repository.full_name` before dispatching handlers, rejecting payloads where they diverge.
- Consider deriving the verification target strictly from server-side configuration (e.g., the GitHub App installation associated with the specific repository) rather than trusting any field of the unauthenticated request body to pick which secret governs it.

### Proof of Concept
Given a Shipit deployment where Organization `orgWithoutSecret` is configured (any org, even unrelated to real usage) with no `webhook_secret`, and `trackedOrg/trackedRepo` is a real tracked repository/stack:

```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "0000000000000000000000000000000000dead",
  "repository": {
    "owner": { "login": "orgWithoutSecret" },
    "full_name": "trackedOrg/trackedRepo"
  }
}
```

- `repository_owner` resolves to `"orgWithoutSecret"` → `Shipit.github(organization: "orgWithoutSecret")` succeeds (known org) → `verify_webhook_signature` returns `true` because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`) — no `X-Hub-Signature` header needed at all.
- `Shipit::Webhooks.for_event('push')` runs `PushHandler.call(params)`; `repository_name` reads `payload.dig('repository','full_name')` = `"trackedOrg/trackedRepo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), resolving the real, tracked repository's stacks and enqueuing `stack.sync_github(expected_head_sha: "0000000000000000000000000000000000dead")` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — entirely unauthenticated and against a repository the attacker has no relationship with.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
