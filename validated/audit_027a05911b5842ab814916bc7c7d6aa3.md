This confirms the vulnerability: multi-tenant GitHub App configuration keys the webhook secret by organization (`Shipit.github(organization:)` → `github_app_config(organization)` in `lib/shipit.rb:170-200`), while `Shipit::WebhooksController#verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` derives that organization solely from `params.dig('repository', 'owner', 'login')`. The event handlers, however, resolve the *actual* target repository/stack from a separate field, `payload.dig('repository', 'full_name')`, in `Shipit::Webhooks::Handlers::Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), used by `PushHandler`, `StatusHandler`, `LabelCapturingHandler`, etc. Nothing in the signature verification binds `repository.owner.login` to `repository.full_name` — they are independent JSON fields inside the same signed body.

### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the independent `repository.full_name` field, enabling cross-tenant webhook forgery in multi-organization deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-GitHub-App deployments (`secrets.github` keyed by organization, see `config/secrets.development.example.yml`), each organization has its own `webhook_secret`. `WebhooksController#verify_signature` picks which secret to validate against using `repository_owner`, read from the attacker-controlled JSON body itself, not from any authenticated GitHub App context. Once the signature check passes, the actual webhook handler determines which `Stack`/`Repository` to mutate using a *different* JSON field, `repository.full_name`. An attacker who controls (or compromises) the webhook secret for organization A can forge a validly-signed payload whose `repository.owner.login` is `"org-a"` (so it passes signature verification with A's secret) while `repository.full_name` is set to `"org-b/victim-repo"`, causing the handler to act on organization B's stack.

### Finding Description
The signature/authentication check and the write/action target are bound to two different, attacker-supplied fields of the same JSON payload:

- Verification binds to `repository.owner.login`: [1](#0-0) [2](#0-1) 

- The organization-to-secret lookup for multi-app configs: [3](#0-2) 

- But the handlers that perform the actual write (sync stack, apply commit status, capture PR labels, etc.) resolve the target repository from a separate field, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) [5](#0-4) 

The HMAC signature covers the raw request body as a whole, so it does confirm the payload was signed by *some* org's secret — but it does not confirm that the org whose secret was used (`repository.owner.login`) matches the repository actually being written (`repository.full_name`). Because both fields live inside the same attacker-authored JSON body, and only one of them is used for the trust decision while the other is used for the write target, the two can be set independently in a single forged request.

### Impact Explanation
This breaks the binding "organization that authenticated versus the repository that is written." An attacker who knows (or leaks) a single organization's `webhook_secret` in a multi-tenant Shipit install can forge webhook events (`push`, `status`, `check_suite`, `pull_request` label/close/reopen handlers) that are correctly signed for their own org but target a different organization's `Stack`, e.g. triggering `stack.sync_github`, injecting fabricated commit statuses via `StatusHandler`, or manipulating PR labels/review-stack lifecycle for a repository they don't own. This is a cross-repository/cross-tenant write performed without possessing the victim organization's actual webhook secret.

### Likelihood Explanation
Exploitability requires the deployment to use the multi-organization GitHub App config schema (`secrets.github` keyed by org name, as documented in `config/secrets.development.example.yml` and `docs/setup.md`) and requires the attacker to already know one organization's `webhook_secret` (e.g. an org they legitimately administer within the same Shipit instance, or one leaked separately). Given that requirement, forging the cross-org payload itself is straightforward — it is a normal signed HTTP POST with mismatched JSON fields, no additional privilege needed against the victim org.

### Recommendation
In `WebhooksController#verify_signature`, after locating the GitHub App by `repository_owner`, additionally verify that `repository.full_name`'s owner segment matches `repository_owner` (and organization payloads' `organization.login` where relevant) before dispatching to handlers. Reject the webhook if these fields disagree.

### Proof of Concept
1. Deploy Shipit with the multi-org config schema, with `org-a` and `org-b` both installed, each with its own `webhook_secret`.
2. As an attacker who knows `org-a`'s `webhook_secret` (e.g., an org admin of `org-a` within the same instance), craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a's webhook_secret, body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature using `org-a`'s secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` and triggers `sync_github` on `org-b`'s stack — a write the attacker has no authorization for.
