## Title
CCMenu API tokens are not stack-scoped, allowing cross-stack unauthenticated read of any stack's build status - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` token intended to expose a *single* stack's CI/build status through an unauthenticated CCMenu XML feed, but the token is created without any `stack_id` binding. The `Api::CCMenuController` that consumes this token also bypasses the stack-scoping mechanism used everywhere else in the API. As a result, one legitimately-issued CCMenu URL can be used to read the build status of **any** stack in the Shipit instance, not just the one it was generated for.

### Finding Description
When a logged-in user requests a CCMenu URL for a stack, `CCMenuUrlController#client` creates (or reuses) an `ApiClient` scoped only by `creator` and `name`, with `permissions: %w[read:stack]` and **no `stack_id`**: [1](#0-0) 

That token is embedded directly in the returned URL along with the target `stack_id`: [2](#0-1) 

The consuming endpoint, `Api::CCMenuController`, authenticates purely via the raw `params[:token]` (no session, no basic auth) and — critically — resolves the target stack directly from `params[:stack_id]` rather than through the stack-scoping helper used by the rest of the API: [3](#0-2) 

Compare this to `Api::BaseController`, where stack lookup is properly constrained by the token's own `stack_id` when one is set: [4](#0-3) 

`ApiClient#check_permissions!` only checks that the permission string (`read:stack`) is present in the token's permission list — it never validates that the *specific* stack being requested matches any stack the token was scoped to: [5](#0-4) 

Because the `ApiClient` model does support a `belongs_to :stack, optional: true` binding (used correctly elsewhere via `stacks` in `BaseController`), but `CCMenuUrlController` never sets it, the equality the system implicitly promises — "stack a token authorizes == stack it touches" — is broken for every CCMenu token. The token authorizes `read:stack` globally, while the endpoint lets the caller pick *any* `stack_id` in the request.

### Impact Explanation
This is an unauthenticated read of stack state: anyone who obtains a single CCMenu URL (these are designed to be embedded in public/semi-public CI dashboard widgets, i.e., handed to third parties by design) can substitute an arbitrary `stack_id` and retrieve build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state, etc.) for every stack in the Shipit deployment — including stacks the original token-issuer has no relationship to and never intended to expose. This matches the "High - unauthenticated read of stack state" impact category.

### Likelihood Explanation
Any authenticated Shipit user can trigger `CCMenuUrlController#fetch` for one stack they can view, obtain the token, and then replay it against `Api::CCMenuController#show` with a different `stack_id`. No special privilege, secret, or session is required for the read once the token has been captured (and it's meant to be shared/embedded, increasing exposure). `stack_id` values are low-entropy, predictable slugs (`owner/repo/environment`), making enumeration trivial.

### Recommendation
Bind the `ApiClient` created in `CCMenuUrlController#client` to the specific stack (`stack:` attribute already supported by the model), and change `Api::CCMenuController#stack` to resolve through the same stack-scoping helper (`stacks.from_param!`) used by `Api::BaseController`, so the token's `stack_id` restriction is actually enforced rather than bypassed.

### Proof of Concept
1. As user A, visit a stack you can access and call `POST/GET stacks/:stack_id/ccmenu` (`CCMenuUrlController#fetch`) to obtain a CCMenu URL, e.g. `.../api/stacks/orgA/repoA/production/ccmenu.xml?token=T`.
2. Note the token `T` is created via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: user, name: 'CCMenu Client')` — no `stack_id` is stored. [6](#0-5) 
3. Request `.../api/stacks/orgB/repoB/staging/ccmenu.xml?token=T`, substituting any other stack's identifier known or guessed by the attacker.
4. `Api::CCMenuController#authenticate_api_client` accepts `token=T` and `#stack` resolves `orgB/repoB/staging` directly from `params[:stack_id]`, with no check that `T` is scoped to that stack. [7](#0-6) 
5. The response returns `orgB/repoB/staging`'s build status XML, even though the token was minted for a completely different stack/owner.
