### Title
Webhook signature is verified against the organization named in an unauthenticated payload field, but the repository acted on by handlers comes from a different, independently-read field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App secret to use for HMAC verification by reading `repository_owner` out of the still-unverified JSON body, and then verifies the raw body against that org's `webhook_secret`. Every downstream `Handlers::Handler` subclass independently re-reads `payload.dig('repository', 'full_name')` to decide which `Stack`/`Repository` to mutate. Because the "org whose secret authenticated the request" and "the repository that gets written to" are derived from two different reads of the same untrusted JSON rather than being tied together by validation, the equality `organization_that_authenticated == owner(repository_being_written)` is never enforced by the engine.

### Finding Description
`verify_signature` in [1](#0-0)  computes:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` is derived from the payload itself: [2](#0-1) 
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`Shipit.github(organization:)` looks up a per-organization `webhook_secret` from `secrets.github[org]` (see the multi-org config shape in [3](#0-2)  and the lookup logic in [4](#0-3) ). It selects and caches a distinct `GitHubApp` instance per organization key.

Once `verify_signature` passes (i.e., the signature matches whatever org's secret was selected via the `repository_owner`/`organization.login` field), `create` hands the whole parsed JSON to every registered handler: [5](#0-4) . Each `Handler` then independently resolves the target repository from the same payload via `payload.dig('repository', 'full_name')`: [6](#0-5) , and `Repository.from_github_repo_name` does a case-insensitive DB lookup with no ownership tie-back to the org that was authenticated: [7](#0-6) .

Nothing in this pipeline requires `repository.owner.login` (used for signature selection) to equal `repository.full_name`'s owner segment (used for handler dispatch) — these are two separate `dig` calls into the same untrusted body, and the code never cross-checks them. In a Shipit deployment configured with multiple GitHub organizations (as the sample multi-org secrets file demonstrates), a party who legitimately controls one configured organization's webhook secret (e.g., because they administer a repo/org that is deliberately hooked into this shared Shipit instance) can compute a valid `X-Hub-Signature` for a JSON body whose `organization.login`/`repository.owner.login` says their own org (satisfying `verify_signature`), while `repository.full_name` in that same body names a repository belonging to a *different* org/stack tracked by the same Shipit instance. The signature check passes because it only ever validates "this body was HMAC-signed with organization X's secret" — it never asserts "and repository Y named inside the body is actually owned by organization X."

### Impact Explanation
This breaks the trust boundary that per-organization webhook secrets are meant to enforce: each configured GitHub org is supposed to only be able to authenticate events about its own repositories. Handlers such as the push handler (`GithubSyncJob`), status/check-run handlers, and merge-request handlers act on `Stack`/`Commit`/`MergeRequest` records for whichever repository the payload claims, irrespective of which org's secret validated the request. This allows a party trusted for one org's webhook secret to inject events (fake push SHAs, statuses, check-run results, merge/PR state changes) that are processed against a stack belonging to a different org configured on the same Shipit instance — i.e., cross-repository/cross-org write access to deploy-relevant state without ever holding write access to, or a webhook secret for, the targeted repository. This matches the "organization that authenticated versus the repository that is written" binding called out as in-scope, and results in unauthorized writes to another repository's tracked state (commit statuses, sync jobs, merge status), which can influence downstream deploy decisions.

### Likelihood Explanation
Requires only that the attacker legitimately controls one organization already configured in this Shipit instance's `secrets.github` (a realistic scenario in shared/multi-tenant Shipit deployments, as shown by the sample config listing multiple independent orgs each with their own `webhook_secret`). No GitHub App private key, `api_clients_secret`, or session is needed — only the ability to compute an HMAC with a secret the attacker is entitled to (their own org's webhook secret) and to send an arbitrary POST body/headers to the public `/webhooks` endpoint.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner` from the verified payload and require every handler-visible `repository.full_name`/`organization.login` in the payload to match the organization key that was used to select the verifying secret before dispatching to handlers, rejecting (422) any request where they diverge.

### Proof of Concept
1. Assume Shipit is configured with two organizations, `victim-org` and `attacker-org`, each with its own `webhook_secret` (per [8](#0-7) ), and both have stacks tracked by this Shipit instance.
2. Attacker, knowing `attacker-org`'s webhook secret (because they legitimately administer a repo hooked to this Shipit instance under `attacker-org`), builds a `push` payload where:
   - `organization.login` / `repository.owner.login` = `attacker-org` (used only for signature-org selection),
   - `repository.full_name` = `victim-org/some-repo` (the actual stack the attacker wants to affect),
   - `after` = an attacker-chosen SHA.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates successfully against the attacker's own known secret [1](#0-0) .
5. `create` dispatches the payload to the push handler, which resolves the stack via `Repository.from_github_repo_name('victim-org/some-repo')` [6](#0-5)  and processes the event against `victim-org`'s stack — despite the request never being authenticated by anything belonging to `victim-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
