## Title
Guest-triggered "should be unreachable" trap classification causes host process panic in `IntoVMError::into_vm_error` - (File: runtime/near-vm-runner/src/wasmtime_runner/mod.rs)

## Summary
The wasmtime trap-to-error translation path deliberately treats a whole class of wasmtime `Trap` variants (fuel, threads, GC/function-references, component-model, stack-switching, pulley-interpreter traps) as "should never occur under NEAR's engine configuration" and calls `panic!` on them instead of returning a graceful `VMOutcome`/`VMRunnerError`. If any guest-controlled code path can cause wasmtime to actually raise one of these traps at runtime (e.g. via engine misconfiguration, feature-gating mismatch, or an as-yet-undiscovered wasmtime edge case reachable from ordinary wasm bytecode), the node process aborts instead of returning a deterministic `FunctionCallError`.

## Finding Description
`runner::run` at `runtime/near-vm-runner/src/runner.rs:89-109` calls `prepared.run(...)`, which for the Wasmtime backend eventually surfaces any trap through `IntoVMError::into_vm_error` in `runtime/near-vm-runner/src/wasmtime_runner/mod.rs:369-425`. That function classifies the underlying `wasmtime::Trap` via `TrapClassification::from(trap)` (`runtime/near-vm-runner/src/wasmtime_runner/trap_classification.rs:32-95`). Trap kinds tied to disabled proposals (fuel, threads, GC, component model, continuations, pulley interpreter opcodes) are mapped to `TrapClassification::Unreachable { trap }`, and the consuming match arm at `mod.rs:401-406` does:
```rust
C::Unreachable { trap } => {
    panic!(
        "contract produced a trap that should be unreachable \
            under NEAR's engine configuration: {trap:?}"
    );
}
```
This turns any occurrence of one of these trap codes into an unconditional host-process panic rather than a `VMRunnerError`/`FunctionCallError::WasmTrap`/`WasmUnknownError`. The design intent (per the comment) is that these traps are unreachable given NEAR's wasm feature configuration (these proposals are disabled in the validator/engine config), so in the current implementation they are believed impossible to reach from ordinary attacker-supplied wasm bytecode compiled and validated under `prepare::prepare_contract`.

## Impact Explanation
If this `panic!` branch is ever reachable from attacker-controlled wasm (i.e., if wasm validation/config does not fully prevent generating one of these disabled-feature trap codes at runtime), an unprivileged user could deploy and call such a contract to abort the host process on every validator executing the transaction, matching NEAR's "network unable to confirm new transactions (shard/chain halt)" Critical impact class. This would be a direct violation of the stated invariant that "no guest input can abort the host process," and is structurally the same class of bug the surrounding code explicitly tries to avoid for the sibling `Unknown` trap variant (which is safely converted to `VMRunnerError::WasmUnknownError` instead of panicking).

## Likelihood Explanation
Low, but not proven impossible from static analysis alone. The classification is designed to be exhaustive and defensive against wasmtime engine upgrades (`test_all_wasmtime_traps_classified`), and the traps routed to `Unreachable` correspond to wasm proposals (threads, GC, component model, fuel, continuations, pulley) that are gated off in NEAR's `Config`/`WasmFeatures` and contract validation (`prepare::prepare_contract`/`validate_contract`), so ordinary contract bytecode accepted by validation should not be able to produce these trap codes. Whether there exists a validation gap, an engine/config mismatch, or an interaction (e.g., a future wasmtime version enabling one of these codes implicitly, or a validator/config skew) that lets attacker wasm reach one of these traps at runtime could not be confirmed or ruled out from the available code; this would require deeper review of `prepare_v2.rs`/`WasmFeatures` construction and wasmtime engine configuration to fully validate.

## Recommendation
Replace the `panic!` in the `TrapClassification::Unreachable { trap }` arm of `IntoVMError::into_vm_error` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:401-406`) with the same graceful degradation used for `Unknown { trap }`: return `Err(VMRunnerError::WasmUnknownError { debug_message: format!("supposedly-unreachable trap type: {trap:?}") })` (or equivalent), so that even if this assumption is ever violated by a future wasmtime version, engine reconfiguration, or an undiscovered validation gap, the host degrades to a recoverable error instead of aborting the process. Keep a debug-only assertion/telemetry alert to detect the condition without crashing production nodes.

## Proof of Concept
Extend the existing wasm fuzz target for the wasmtime runner (as referenced in `runtime/near-vm-runner/src/prepare/prepare_v2.rs` fuzz tests) to:
1. Generate/validate arbitrary wasm modules through the same `validate_contract`/`prepare_contract` pipeline used in production.
2. Run each validated module through `runner::run` twice with identical inputs.
3. Assert the process never panics (catch_unwind around `run`), and assert that the two runs produce identical `burnt_gas`/outcome (existing determinism check).
4. Specifically fuzz for trap-code generation, targeting wasm constructs that might, despite feature gating, trigger disabled-proposal trap codes (e.g., malformed/edge-case instructions near the boundary of enabled/disabled features) to attempt to hit the `TrapClassification::Unreachable` arm.

Because reaching this branch could not be confirmed as feasible from ordinary validated wasm bytecode within the scope of this review, this should be treated as a defense-in-depth/robustness finding rather than a confirmed exploitable panic-on-demand vulnerability, unless a concrete wasm module reaching `TrapClassification::Unreachable` is demonstrated by the fuzz target.
