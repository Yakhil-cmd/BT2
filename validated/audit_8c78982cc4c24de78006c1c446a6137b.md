### Title
CCMenu API tokens are not scoped to the requesting stack, granting cross-stack read access via `Api::StacksController`/`Api::OutputsController` and via `Api::CCMenuController`'s own stack lookup - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
The reported Rubicon bug lets a duplicate, unvalidated `bonusTokens` entry break the 1:1 binding between "token added" and "reward actually owed," letting an early withdrawer draw multiples of what they're entitled to. The same bug *class* — a binding the system is supposed to enforce silently degrading to "no binding at all" — is reproduced in shipit-engine's CCMenu token issuance: the equality that should hold is `stack the token authorises == stack the token can touch`, but the code that mints the token never records a stack, and the endpoint that consumes it never checks one either.

### Finding Description
`Shipit::CCMenuUrlController#client` mints (or reuses) an `ApiClient` intended to let an external, unauthenticated CCMenu widget read the status of **one specific stack**: [1](#0-0) 

`find_or_create_by!(creator: current_user, name: 'CCMenu Client')` does not include `stack:` in either the lookup or the `create_with` attributes, even though `ApiClient` explicitly supports per-stack scoping (`belongs_to :stack, optional: true`) and that scoping is the mechanism `Api::BaseController` relies on to restrict a token's reach: [2](#0-1) 

Because the created `ApiClient` has `stack_id == nil`, `stacks` in `BaseController` resolves to `Stack.all` for that token — i.e. the "CCMenu Client" token silently becomes a global `read:stack` credential, usable against `Api::StacksController#index/#show`, `Api::OutputsController#show`, `Api::CommitsController`, etc. for *every* stack in the installation, not just the one for which the CCMenu URL was requested.

Independently, `Api::CCMenuController#stack` compounds the issue by never using the properly-scoped `stack` accessor at all: [3](#0-2) 

It calls `Stack.from_param!(params[:stack_id])` directly instead of the inherited `stacks.from_param!(params[:stack_id])` from `BaseController`. So even if `CCMenuUrlController#client` were fixed to pass `stack:`, `Api::CCMenuController#show` would still let that (properly-scoped) token read the CI/build status of any other stack simply by changing the `stack_id` query parameter, because the controller's own lookup ignores `current_api_client.stack_id`.

`require_permission :read, :stack` only checks that the operation/scope pair `"read:stack"` is present on the token (`ApiClient#check_permissions!`); it never checks *which* stack the token is bound to: [4](#0-3) 

### Impact Explanation
CCMenu URLs are explicitly designed to be embedded in third-party, unauthenticated tooling (build-status widgets), i.e. handed out to an "unprivileged" consumer who is expected to only ever be able to read the one stack's status. Due to the missing stack binding at issuance time (`ccmenu_url_controller.rb`) and the missing stack-scope enforcement at consumption time (`ccmenu_controller.rb`), possession of a single leaked/observed CCMenu token grants unauthenticated read access to the state, commit history, and task/deploy output of every stack managed by the Shipit installation — this is an unauthorized read of stack state / task output across repositories the token holder was never meant to see, matching the "unauthenticated read of stack state, task streams or deploy output" High-impact category.

### Likelihood Explanation
No privileged access, session, or webhook secret is required beyond obtaining one legitimately-issued CCMenu token (these are designed to be embedded in external URLs/widgets and are not treated as highly sensitive by users, unlike an interactive session cookie). Once obtained, the escalation to other stacks is a single parameter change (`stack_id`) against either the normal `/api/stacks` endpoints or the CCMenu endpoint itself — no additional guessing of secrets, signatures, or tokens is needed.

### Recommendation
- In `CCMenuUrlController#client`, include `stack:` in both `create_with` and `find_or_create_by!` so the minted `ApiClient` is bound 1:1 to the stack the URL was generated for (mirroring the existing `here_come_the_walrus` fixture pattern used elsewhere in the codebase).
- In `Api::CCMenuController`, remove the private `stack` override and use the inherited, properly-scoped `stack` method from `Api::BaseController` (`stacks.from_param!(params[:stack_id])`), so a stack-scoped token cannot be replayed against a different `stack_id`.

### Proof of Concept
1. As an authenticated Shipit user with access to `stack_A`, call `GET /stack_A/ccmenu_url` (`CCMenuUrlController#fetch`). This creates/reuses an `ApiClient` named `"CCMenu Client"` for `current_user` with `permissions: ["read:stack"]` and `stack_id: nil`.
2. Take the returned `token` and call the normal JSON API: `GET /api/stacks` (or `/api/stacks/<stack_B_id>`, `/api/stacks/<stack_B_id>/tasks/<id>/output`) using HTTP Basic auth with that token for `stack_B`, which the user was never granted this token for.
   - `Api::BaseController#stacks` evaluates `current_api_client.stack_id?` → `false` (nil), so it returns `Stack.all`, and the request against `stack_B` succeeds.
3. Alternatively, call `GET /api/stacks/<stack_B_id>/ccmenu?token=<token>` directly; `Api::CCMenuController#stack` performs `Stack.from_param!(params[:stack_id])` with no scoping check at all, returning `stack_B`'s CI/build status regardless of the token's intended scope.
