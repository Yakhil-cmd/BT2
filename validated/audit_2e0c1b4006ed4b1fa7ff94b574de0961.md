### Title
Webhook signature is verified against an organization selected from the unverified payload while handlers act on a `repository.full_name` never cross-checked against that organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App (and therefore which `webhook_secret`) to verify the request against by reading `repository.owner.login`/`organization.login` straight out of the still-unauthenticated JSON body, then hands the *entire* raw payload to `Shipit::Webhooks.for_event(event)` handlers. Those handlers (e.g. `PushHandler`, via `Handler#repository_name`/`Handler#stacks`) resolve the target `Repository`/`Stack` from a *different* field of the same payload, `repository.full_name`, without ever checking that this repository belongs to the organization whose secret validated the signature. In a Shipit deployment configured for multiple GitHub organizations (a documented, supported configuration), this breaks the equality "organization whose secret authenticated the webhook" == "repository/stack the webhook is allowed to act on."

### Finding Description
`verify_signature` derives `repository_owner` from the raw, unverified body and uses it to select the `GitHubApp`/secret to check the signature against: [1](#0-0) [2](#0-1) 

Once the signature check passes for that organization's secret, `create` dispatches the same raw payload to the registered handler for the event: [3](#0-2) 

However, the base `Handler` class resolves the affected stacks using a *different* payload field, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) 

`PushHandler` then syncs any stack matching that repository's branch, i.e. triggers `stack.sync_github`, which can lead to a continuous-deployment run: [5](#0-4) 

`Repository.from_github_repo_name` performs a case-insensitive, unscoped lookup across all repositories/owners stored in this single Shipit instance: [6](#0-5) 

Shipit explicitly supports hosting multiple GitHub organizations from one instance, each with its own `webhook_secret` configured independently (documented in "Using Multiple Github Applications"): [7](#0-6) 

Because `verify_signature` only proves "this payload was signed with OrgA's webhook secret," and does not enforce that OrgA's secret can only ever be used to sign events about OrgA's repositories, an entity that legitimately controls OrgA's GitHub App configuration (e.g. an OrgA admin who set the webhook URL/secret when installing the app, as instructed by Shipit's own setup docs) can send a request to Shipit's `/webhooks` endpoint whose body is signed with OrgA's secret but whose JSON sets `repository.owner.login` = `OrgA` (for signature routing) while `repository.full_name` = `OrgB/some-repo` (a repository belonging to a different, unrelated organization hosted on the same Shipit instance). The equality that should hold is:

`organization authenticating the webhook (repository.owner.login used to select the secret)` == `repository/stack that the handler is allowed to mutate (repository.full_name)`

Before the fix this engine would need, these are two independent, attacker-influenced fields inside one HMAC-covered blob, but the HMAC only proves the blob came from an entity holding OrgA's secret - it says nothing about which repository that entity is entitled to name inside the blob.

### Impact Explanation
This crosses a tenant/authorization boundary between two GitHub organizations sharing one Shipit instance: an operator/administrator who only controls OrgA's GitHub App webhook (and thus its secret) can forge webhook deliveries that are processed as if they originated from OrgB, causing `GithubSyncJob`/`stack.sync_github` to run for OrgB's stack. Depending on `continuous_deployment` settings for that stack, this can trigger unauthorized deploys of OrgB's stacks from a party that was never granted any access to OrgB's repository or Shipit stack, i.e. an unauthorized deploy / cross-organization write - matching the High/Critical impact bar ("unauthorized deploy" / "cross-repository writes").

### Likelihood Explanation
Requires: (1) the target Shipit instance to be configured with multiple GitHub organizations sharing one Shipit deployment (a documented, supported setup), and (2) the attacker to control the webhook configuration (secret) of at least one of those organizations - which is exactly the level of access Shipit's setup docs instruct each org's admin to have. No access to Shipit's own credentials (`api_clients_secret`, session, `GITHUB_TOKEN`) is required; only knowledge of one org's `webhook_secret`, which by design is held by that org's own (non-privileged with respect to other orgs) administrators. This is a realistic though setup-dependent likelihood.

### Recommendation
After `verify_signature` selects `github_app` for `repository_owner` and validates the signature, re-derive the repository/organization used by the handler from the *same* verified field (`repository.owner.login`) rather than trusting `repository.full_name` independently, or explicitly assert `repository.full_name.split('/').first == repository_owner` before dispatching to handlers. Alternatively, scope `Repository.from_github_repo_name` lookups to the organization that was actually used to verify the signature.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-org setup), each with at least one stack registered (`OrgA/repo-a`, `OrgB/repo-b`).
2. As an administrator who only controls `OrgA`'s GitHub App webhook configuration (and thus knows `OrgA`'s `webhook_secret`), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/repo-b"
  }
}
```
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1(OrgA's `webhook_secret`, raw body).
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and successfully verifies the signature using `OrgA`'s secret.
6. `Handler#stacks`/`PushHandler#process` resolve the target via `payload.dig('repository', 'full_name')` = `"OrgB/repo-b"`, and call `stack.sync_github` on `OrgB`'s stack - an action the OrgA-controlling attacker was never authorized to trigger.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

      private_key:

        id:

    someothergithuborg:
