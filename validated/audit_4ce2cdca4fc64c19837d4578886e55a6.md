## Analog Found: Unhandled Exception in AA Trigger Dry-Run Crashes the Node Process

### Title
Unprivileged AA Trigger Payment Can Crash the Full Node via Unhandled Exception in Premature Dry-Run Execution - ([File: network.js])

### Summary
`ocore`'s `handleJoint()` in `network.js` optionally executes a full, synchronous "dry run" of an Autonomous Agent (AA) trigger the moment a *new, unstable* unit that merely pays to an AA address passes basic validation — well before the unit is even confirmed/stable. This dry run calls into `aa_composer.js`'s `handleTrigger()`/formula evaluation engine, which is riddled with defensive `throw Error(...)` statements meant to catch "impossible" internal-invariant violations. None of this path is wrapped in a `try/catch`, and any thrown exception propagates out of the `async ifOk` callback straight into Node's `process.on('uncaughtException')` handler, which explicitly re-throws to terminate the process.

### Finding Description
In `network.js`, within `handleJoint()`'s `ifOk` callback: [1](#0-0) 

When `conf.bDryRunNewTriggers` is enabled (non-light node) and a freshly-validated, not-yet-stable unit (`!objJoint.ball`) pays into a known AA address, the code fetches that AA's stored definition and calls `aa_composer.dryRunPrimaryAATrigger(trigger, address, JSON.parse(definition))`, with the comment "if it would crash, let it crash now, not when we execute the trigger for real" — an explicit acknowledgment that this call path can throw.

`dryRunPrimaryAATrigger` itself has no `try/catch` around the trigger execution: [2](#0-1) 

It calls `handleTrigger(...)`, whose body contains numerous unconditional `throw Error(...)` statements guarding invariants (e.g. "bad AA definition", "base AA not found", `lightBatch.write` throwing "attempting to write a batch in a light client", assertion mismatches between `bAir`/`assocBalances`, etc.): [3](#0-2) 

Because this dry run is triggered by *any* posted/relayed unit as soon as it passes ordinary DAG validation — not after the unit is stable and its AA-trigger context has been fully re-derived the way `handlePrimaryAATrigger` does after stabilization — the trigger is executed against `readLastStableMcUnit`'s MC context with a synthetic `trigger.unit = constants.GENESIS_UNIT`, an environment that does not necessarily match all the invariants the `handleTrigger` code assumes hold for a "real" trigger execution. Any AA whose logic (directly or via nested/parameterized AA calls, formula evaluation, or getter calls) hits one of these invariant-violation throws under this premature/synthetic execution context will throw synchronously inside the `async ifOk` handler.

That exception is not caught anywhere in the call chain and reaches the global handler: [4](#0-3) 

which logs it and then does `throw err; // crash the process to avoid ending up in an inconsistent state` — deliberately terminating the entire node.

### Impact Explanation
Any unprivileged user can construct a normal payment unit that sends funds to a public, already-deployed AA address (their own AA, or someone else's — AA addresses/definitions are public). If the AA's logic (which the attacker fully controls when defining their own AA, or can select from any existing AA whose logic reaches such a throw) causes `handleTrigger`'s dry-run execution to hit one of its many defensive `throw Error(...)` invariants, simply broadcasting/posting that single payment unit crashes the full node the moment it's received and validated — before the unit is even confirmed. Because this runs on every full node that has `bDryRunNewTriggers` enabled and receives the unit via normal p2p propagation, this is a network-wide denial-of-service vector reachable from a single crafted AA trigger payment, matching the "network unable to confirm new units" impact class.

### Likelihood Explanation
The trigger requires only: (1) an existing/attacker-defined AA address, and (2) a payment to it from any wallet. No special privileges, hub/peer position, or protocol-level access are needed — it is exactly the "unprivileged AA trigger sender" scenario. The likelihood of finding/crafting an AA whose logic reaches one of the many `throw Error(...)` invariant checks under the dry-run's synthetic execution context (distinct from the real, post-stabilization execution context) is non-trivial to enumerate exhaustively but the attack surface (any nested/parameterized AA call, any formula edge case, any getter interaction) is large, and the developers' own comment acknowledges the crash is expected to be possible ("if it would crash, let it crash now").

### Recommendation
Wrap the dry-run trigger execution (`aa_composer.dryRunPrimaryAATrigger` call and, more generally, `handleTrigger`'s execution path) in a `try/catch` that converts unexpected internal-invariant violations into a handled validation/transient error (e.g., skip the dry run and defer to normal post-stabilization AA execution, which already has its own dedicated error handling) instead of letting them propagate into `process.on('uncaughtException')`. At minimum, disable or gate `bDryRunNewTriggers`-triggered execution behind the same defensive error boundary used for genuine AA trigger execution in `handlePrimaryAATrigger`, so a crafted/edge-case AA cannot use this premature code path to crash full nodes on unstable, unconfirmed input.

### Proof of Concept
1. Deploy any AA definition (or reuse an existing one) whose message/formula logic, when executed against `readLastStableMcUnit`'s context with `trigger.unit = constants.GENESIS_UNIT` (as used by `dryRunPrimaryAATrigger`), causes one of `handleTrigger`'s or the nested formula evaluator's invariant checks to fail (e.g., a parameterized AA referencing a `base_aa` interaction, or a getter/nested-AA call whose consistency assumptions differ between the dry-run synthetic context and a genuine post-stabilization context).
2. On a full node with `conf.bDryRunNewTriggers = true` (non-light), post or broadcast a normal payment unit sending funds to that AA's address.
3. Observe the node execute `aa_composer.dryRunPrimaryAATrigger` synchronously inside `handleJoint`'s `ifOk`, hit the internal `throw Error(...)`, and crash the process via the `process.on('uncaughtException')` handler at [4](#0-3) .
