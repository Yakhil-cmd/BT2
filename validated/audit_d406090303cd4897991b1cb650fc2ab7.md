### Title
Unchecked `objAsset` null-dereference in private-payment / attestor-list validation callbacks - ([File: private_payment.js, validation.js])

### Summary
Both `validateAndSavePrivatePaymentChain` in `private_payment.js` and `validateAttestorListUpdate` in `validation.js` call `storage.readAsset(...)` with an error-first callback and immediately dereference the returned `objAsset` object without checking that it is actually truthy. This mirrors the CVE-2022-34679 bug class: a callback/return value whose failure case is not fully handled, so the caller ends up dereferencing a null/undefined object, producing an unhandled JS exception rather than a controlled error path.

### Finding Description
In `private_payment.js`:
```js
storage.readAsset(db, asset, null, function(err, objAsset){
    if (err)
        return callbacks.ifError(err);
    if (objAsset.is_private !== 1)          // <-- objAsset dereferenced with no truthiness check
        return callbacks.ifError("asset is not private");
``` [1](#0-0) 

And in `validation.js`:
```js
storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
    if (err)
        return callback(err);
    if (!objAsset.spender_attested)          // <-- same pattern
        return callback("this asset does not require attestors");
``` [2](#0-1) 

In both cases the only defensive check is `if (err) return ...`; there is no `if (!objAsset) return ...`. If `readAsset` ever completes its callback with `err` falsy and `objAsset` falsy (e.g., an edge case around asset lookup with `mci=null`, a race with asset stability/definition timing, or a caching inconsistency), the subsequent property access (`objAsset.is_private`, `objAsset.spender_attested`) throws a `TypeError: Cannot read properties of undefined`. This is thrown synchronously inside a DB-callback context that is not wrapped by the normal `validation.validate()` `try/catch`-style error routing, so it becomes an **uncaught exception**.

This codebase treats uncaught exceptions as fatal by design:
```js
process.on('uncaughtException', (err) => {
    console.log('Uncaught exception:', err);
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [3](#0-2) 

So any reachable null-dereference of this kind terminates the entire node process — directly analogous to the NVIDIA driver bug where an unhandled return value led to a null-pointer dereference causing denial of service.

`asset` in `validateAndSavePrivatePaymentChain` comes directly from `headElement.payload.asset`, which is attacker-supplied by whoever sends a private payment chain to a peer (a private-payment counterparty), and `payload.asset` in `validateAttestorListUpdate` comes from a posted unit's message payload (an unprivileged unit poster), i.e. both are reachable without any special privilege.

### Impact Explanation
If the `objAsset` null case can be triggered (e.g., through crafted/edge-case asset identifiers, timing around asset definition visibility, or the `mci=null` argument path used only here), it produces an uncaught `TypeError`. Given the global `uncaughtException` handler explicitly re-throws to crash the process, this results in denial of service of the full node — validators/hubs/wallets processing the malicious unit or private payment can crash, which can prevent the network from confirming new units and matches the accepted "network unable to confirm new units" impact class.

### Likelihood Explanation
The likelihood depends on how easily `storage.readAsset` can be made to invoke its callback with `(null, undefined)`. I was not able to fully inspect `readAsset`'s implementation in `storage.js` within the available context to confirm all code paths that could produce this exact null-without-error condition (the tool session ended before this could be verified). The defensive-coding gap itself (missing `if (!objAsset)` check right after the `if (err)` check, in two independent call sites) is concretely verified, but whether an attacker can actually force `readAsset` to hit that gap needs to be confirmed against the full `readAsset` source.

### Recommendation
Add explicit `if (!objAsset) return callbacks.ifError("asset not found");` (and equivalent in `validation.js`) immediately after the `err` check in both `private_payment.js:36` and `validation.js:2836`, before any property access on `objAsset`. More broadly, audit all `storage.readAsset`/`readAssetInfo` callback sites for the same "checked err, unchecked result" pattern, and consider making the global `uncaughtException` handler in `network.js` fail more gracefully for validation-triggered exceptions rather than unconditionally crashing the process, to reduce the blast radius of any single unhandled edge case.

### Proof of Concept
Conceptual PoC (not fully verified against `readAsset`'s internals):
1. A private-payment counterparty crafts a private payment chain whose head element's `payload.asset` references an asset id chosen to hit an edge case in `storage.readAsset` (e.g., an asset id that is syntactically valid but not resolvable under the specific `mci=null` code path used by `private_payment.js`).
2. Sends this chain to a victim node via the normal private-payment message flow.
3. `validateAndSavePrivatePaymentChain` invokes `storage.readAsset(db, asset, null, cb)`; if `cb(null, undefined)` occurs, `objAsset.is_private` throws `TypeError`.
4. The exception is uncaught, hits `process.on('uncaughtException', ...)` in `network.js`, and crashes the node.

Because I could not fully trace every internal branch of `storage.readAsset` in this session (index/context limits), I recommend a Devin session with full repository access to confirm the exact conditions under which `readAsset` returns `(falsy err, falsy objAsset)`, and to implement the guard fixes above.
