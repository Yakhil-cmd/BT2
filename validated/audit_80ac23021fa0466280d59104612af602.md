### Title
Attacker-controlled PR branch name is passed through `Command`'s `$VAR` interpolation during `git fetch`/`git clone`, causing `GITHUB_TOKEN` to be substituted into subprocess argv and captured in task output - ([File: lib/shipit/command.rb], [File: lib/shipit/environment_variables.rb], [File: lib/shipit/stack_commands.rb], [File: app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb])

### Summary
`ReviewStackAdapter#stack_attributes` writes `params.pull_request.head.ref` verbatim into `Shipit::ReviewStack#branch` with no validation. `StackCommands#fetch`/`#fetch_commit` pass `@stack.branch` as a literal `git fetch`/`git clone` argument, but `Command#interpolated_arguments` applies `EnvironmentVariables#interpolate` to *every* argv element (including this one), not just deploy-spec template strings, so a branch literally equal to `$GITHUB_TOKEN` is substituted with the real token value before being handed to `PTY.spawn`.

### Finding Description
The assumed binding in the question — "the branch name == a literal git argument to `Command#start` with no environment-variable interpolation applied" — is **false**.

Path:
1. `ReviewStackAdapter#stack_attributes` sets `branch: params.pull_request.head.ref` with no format check [1](#0-0) , and `#create!` persists it via `scope.create!(stack_attributes)` [2](#0-1) .
2. `OpenedHandler#process` reaches this when `review_stacks_enabled` and `provisioning_behavior_allow_all?` are set (operator config, not an attacker-controlled boundary) [3](#0-2) .
3. `StackCommands#fetch`/`#fetch_commit` build `git('fetch', 'origin', ..., @stack.branch, env:, chdir:)` and `git_clone(..., branch: @stack.branch, ...)`, passing `@stack.branch` as one array element among `git`'s argv [4](#0-3) . `env` includes `GITHUB_TOKEN` from `Commands#base_env` [5](#0-4) .
4. `Command#start` calls `interpolated_arguments`, which calls `interpolate_environment_variables(@args)` — this recursively maps **every** element of `@args`, without distinguishing between trusted deploy-spec command strings and Shipit-internal literal git arguments like the branch name [6](#0-5) .
5. `EnvironmentVariables#interpolate` does `argument.gsub(/(\$\w+)/) { Shellwords.escape(@env.fetch(variable) { ENV[variable] }) }` on that string, unconditionally [7](#0-6) .
6. Consequently, if `@stack.branch == "$GITHUB_TOKEN"`, the argv element handed to `PTY.spawn` is the *literal token value*, not `$GITHUB_TOKEN` or the fork's real branch name [8](#0-7) .

Existing guards do not stop this: there is no `Repository`/`ReviewStack` branch-format validator, `stack_attributes` performs no sanitization, and `EnvironmentVariables#interpolate` has no allowlist/opt-out for "this argument came from user input, do not interpolate." The `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` call is argv-based (not a shell string), so classic shell-metacharacter injection (`; rm -rf`, backticks) is *not* exploitable this way — but the `$VAR` interpolation feature itself is a separate, unguarded substitution mechanism that operates on this same attacker-controlled string.

### Impact Explanation
The git subprocess is invoked with the plaintext `GITHUB_TOKEN` (or any other secret present in `Command#env`, e.g. `Shipit.env` entries) appearing as a literal argument where the branch name should be. This token then:
- Appears in the host's process table (`ps aux`) for the duration of the `git fetch`/`clone` call.
- Is echoed back by git's own error output (invalid ref name) into the command's streamed output, which is written to `Task#chunk_output` and persisted in the database, retrievable via `Api::OutputsController#show`/`TasksController#show` to any principal with `read:stack` permission on that stack.

This moves a highly sensitive credential (`GITHUB_TOKEN`, normally passed only via env/`GIT_ASKPASS` to avoid exposure) into logs/process listings reachable by a broader audience than intended, satisfying the "exfiltration of `GITHUB_TOKEN`... or deploy-time secrets" Critical category. The attacker (unauthenticated PR author) triggers the disclosure remotely with a single crafted branch name and no privileges of their own; the blast radius is scoped to the token(s) present in that stack's `Command#env` (which includes the org-wide GitHub App/organization token, not merely a repo-scoped one).

### Likelihood Explanation
Preconditions: `review_stacks_enabled` and `provisioning_behavior_allow_all` (or `allow_with_label` plus the required label) must be enabled by the repository operator — a legitimate, common configuration for review-stack automation, not a security boundary the attacker must break. Given that, the attacker's cost is trivial: open a PR from a fork with `head.ref` literally `$GITHUB_TOKEN` (GitHub branch names permit `$`). No secrets, sessions, or team membership are needed to trigger provisioning and the subsequent `git fetch`/`clone`. The attack is fully repeatable against any repository configured this way.

### Recommendation
- Validate/sanitize `ReviewStack#branch` (and any other user-controlled value fed into `Command` argv) against a strict branch-name format, rejecting `$`, backticks, and other interpolation-triggering characters, or
- Scope `EnvironmentVariables#interpolate` so it is only applied to strings that originate from trusted deploy-spec command templates (e.g., pass a flag/wrapper type) and never to values sourced from webhook payloads such as branch names, or
- Stop interpolating branch/ref arguments in `StackCommands#fetch`/`#fetch_commit`/`#git_clone` entirely — pass them through a code path that bypasses `interpolate_environment_variables`.

### Proof of Concept
```ruby
# test/unit/stack_commands_test.rb (or command_test.rb)
test "branch names containing $VAR syntax are interpolated with secret env values during fetch" do
  Shipit.github.stubs(:token).returns('aS3cr3Tt0kEn')

  stack = shipit_stacks(:review_stack) # or build a ReviewStack
  stack.update!(branch: '$GITHUB_TOKEN')

  commands = StackCommands.new(stack)
  command = commands.fetch # or fetch_commit(some_commit)

  refute_includes command.interpolated_arguments, '$GITHUB_TOKEN',
    "expected literal $GITHUB_TOKEN branch arg to have been substituted"
  assert_includes command.interpolated_arguments, 'aS3cr3Tt0kEn',
    "expected the real GITHUB_TOKEN value to appear in git argv in place of the branch name"
end
```
This demonstrates the equality claimed in the question — "no interpolation applied to attacker bytes" — is false: `Command#interpolated_arguments` substitutes the real secret value for the attacker-supplied `$GITHUB_TOKEN` branch string.

      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
