### Title
Attestation validity for `spender_attested` assets is checked against the *current* attestor list, not the attestor list in effect when the attestation was posted - ([File: storage.js])

### Summary
For assets with `spender_attested: true`, `storage.readAsset` resolves the "attestor list" as whatever is the most recently published `asset_attestors` update as of `last_ball_mci`, and `storage.filterAttestedAddresses` then accepts *any* historical `attestation` message whose `attestor_address` happens to be a member of that current list - regardless of whether that address was actually an authorized attestor for the asset at the time it posted the attestation. This is the same bug class as the `ArmadaGovernor` report: a decision (the veto / here, the attestation) is bound to an identity, but the code that later "resolves" trust reads a live, separately-mutable slot (`securityCouncil` / here, the asset's current attestor list) instead of the value that was actually true when the action occurred.

### Finding Description
`storage.readAsset` → `addAttestorsIfNecessary` looks up the single most recent `asset_attestors` list for the asset as of `last_ball_mci` and stores it as `objAsset.arrAttestorAddresses`: [1](#0-0) 

`storage.filterAttestedAddresses` then determines which addresses are "attested" by joining the `attestations` table against this **current** attestor list, with no requirement that the attesting address was actually a member of the attestor list *at the time* the `attestation` message was posted - the only mci-based constraint present is on the *attested* address's own definition-change history, not on the attestor's membership history: [2](#0-1) 

`validatePayment` in `validation.js` uses this result unconditionally to gate spending/issuance of `spender_attested` assets: [3](#0-2) [4](#0-3) 

Nothing in ocore prevents an arbitrary address from posting an `attestation` message for any other address at any time - `attestation` is a free-form message type, unrestricted to authorized attestors: [5](#0-4) 
The `asset_attestors` list itself is fully replaceable by the asset definer via `validateAttestorListUpdate`, which only checks that the *replacer* is the definer - it does not preserve or reference which addresses were attestors at earlier points in time for the purpose of validating old attestation records: [6](#0-5) 

Consequently, the "attestor→attested" trust relationship recorded on-chain in the `attestations` table is re-evaluated at spend time using whichever attestor set is live *now*, exactly mirroring the reported pattern of "resolve reads the live mutable slot, not the identity bound to the action."

### Impact Explanation
An address `A` that is not yet (or no longer) an authorized attestor for a `spender_attested` asset can post an `attestation` message today attesting an address `B` (potentially an address `A` itself controls). This attestation is inert at the time it is posted, since `A` is not in the attestor list. If the asset definer later legitimately adds `A` to the attestor list (for an unrelated, good-faith reason - e.g., onboarding a new KYC/attestation partner), `A`'s old, never-reviewed attestation of `B` retroactively becomes valid. `B` can now spend/issue the `spender_attested` asset without `A` ever having actually vetted `B` *while* `A` held attestor authority - defeating the entire point of `spender_attested`. Symmetrically, addresses attested by an attestor who is later removed instantly lose "attested" status even for legitimately-vetted, still-valid attestations, causing funds to become unspendable under the asset's own rules until re-attested - a freezing condition for legitimate holders. Both directions stem from the same root cause: attestor-membership state is read live at resolution time rather than bound to the attestation event.

### Likelihood Explanation
Reachable by any unprivileged unit poster (posting an `attestation` message costs only normal fees) plus one legitimate, unrelated action by the asset issuer (updating `asset_attestors` for its own business reasons) - no malicious intent or coordination from the issuer is required, similar to the "honest collision" framing in the original report. This makes the trigger condition realistic and low-effort for an attacker who can predict or wait for attestor-list churn.

### Recommendation
Bind attestation validity to the attestor-list membership that was in effect at the mci the `attestation` unit became stable, e.g. by additionally requiring that the attesting address was present in the `asset_attestors` snapshot whose `main_chain_index` is closest to (and ≤) the attestation's own `main_chain_index`, rather than joining against only the single most-recent attestor list. This mirrors the recommended `ArmadaGovernor` fix of consulting the identity recorded at action time (`proposer`) instead of the live mutable slot.

### Proof of Concept
1. Asset `X` is defined with `spender_attested: true` and an initial attestor list `[C]`.
2. Address `A` (not yet an attestor) posts `{app: "attestation", payload: {address: "B", attestor_address: "A", profile: {}}}` - accepted normally since `attestation` messages are unrestricted.
3. At this point, `filterAttestedAddresses` would not return `B` as attested, because `A ∉ [C]`.
4. Later, the definer of `X` posts `asset_attestors` update setting the list to `[C, A]` (a legitimate business decision, unrelated to `B`).
5. `B` now posts a payment spending/issuing asset `X`. `storage.readAsset` resolves `arrAttestorAddresses = [C, A]`; `filterAttestedAddresses` matches `B`'s old attestation from `A` and returns `B` as attested, even though `A` was never an authorized attestor when the attestation was created.
6. `validatePayment` accepts the transaction, letting `B` spend/issue `X` without ever having been vetted by a currently-authorized attestor at the time of attestation.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
