### Title
`CCMenuController#stack` bypasses the `current_api_client.stack_id` scope, letting any `read:stack` token read arbitrary stacks' CCMenu status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly instead of using `BaseController#stack`, which resolves through the `stacks` method that scopes results to `current_api_client.stack_id` when the client is stack-scoped. Because `require_permission :read, :stack` only checks that the client's `permissions` array contains `"read:stack"` and never compares `current_api_client.stack_id` to the requested `params[:stack_id]`, any previously issued stack-scoped token (e.g. one minted by `CCMenuUrlController` for stack A) can be replayed against `/api/stacks/:id/ccmenu.xml` for any other stack id, exposing `deploys_and_rollbacks.last` for stacks the token was never granted.

### Finding Description
The binding that should hold is: `current_api_client.stack_id == stack.id` (or `stack_id` unset, i.e. an unlimited/admin client) for every stack-scoped read. In `BaseController`: [1](#0-0) 

`stacks` filters by `current_api_client.stack_id` and `stack` resolves through that filtered relation, so `StacksController#stack` (which does not override `stack`) enforces the binding: [2](#0-1) 

`CCMenuController`, however, defines its own `stack` that ignores `stacks` entirely and resolves the requested id against the whole `Stack` table: [3](#0-2) 

`require_permission :read, :stack` only calls `check_permissions!`, which checks the string `"read:stack"` is present in the client's `permissions` array — it never inspects `stack_id` or compares it to `params[:stack_id]`: [4](#0-3) 

`CCMenuUrlController` mints exactly this kind of stack-scoped, `read:stack`-only token for a specific stack and hands the raw `authentication_token` to the browser in a URL: [5](#0-4) 

Attack flow: an attacker who legitimately obtains (or is handed, e.g. via a shared/public CCMenu URL, log, referrer leak, or their own stack they were granted read access to) one such token for stack A can call `GET /api/stacks/:B/ccmenu.xml?token=<token>` for any numeric `:B`. `authenticate_api_client` in the subclass validates the token via `ApiClient.authenticate` (same signature verification as `BasicAuth.authenticate`, just read from the query string) and sets `@current_api_client` regardless of which stack it was issued for: [6](#0-5) 

Then `require_permission :read, :stack` passes because the permission list includes `"read:stack"`, and `stack` resolves stack `B` unscoped, returning `deploys_and_rollbacks.last` for a stack the client was never bound to: [7](#0-6) 

Existing guards do not catch this: `check_permissions!` is scope-name based only, not instance based; `stacks`'s `stack_id` filter — the only mechanism that would enforce the binding — is never invoked because the subclass shadows `stack`. This is a genuine authorization gap in this engine's own code, not a third-party or config issue.

### Impact Explanation
A caller holding any single `read:stack` token (scoped to one stack) can enumerate `/api/stacks/:id/ccmenu.xml` for arbitrary stack ids and read that stack's latest deploy/rollback status, lock status, and last build label/time for every tenant's stack in the installation — a cross-tenant unauthenticated-by-scope read of stack/deploy state. This matches the "unauthenticated read of stack state" High-severity category. It is fully repeatable (no rate limiting relevant per the rules) and scales to every stack in the Shipit instance from a single leaked/legitimate token.

### Likelihood Explanation
Preconditions: the attacker must possess any valid `ApiClient` authentication token that includes `read:stack` permission (typically one issued via `CCMenuUrlController#fetch` for a stack the attacker does have legitimate view access to, since that endpoint is reachable by any authenticated Shipit user with read access to some stack). Given the rules state the attacker holds "no `ApiClient` token," this specific PoC requires the attacker to already have one such token through legitimate means (e.g., their own stack's CCMenu URL) — at that point exploitation is a single unauthenticated-by-scope GET request per target stack id, trivially repeatable, no GitHub secrets or additional privileges needed.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or reimplement it to go through `stacks.from_param!(params[:stack_id])` as `BaseController` and `StacksController` do), so the `current_api_client.stack_id` scoping is enforced for CCMenu reads exactly as it is for the regular Stacks API.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a read:stack token scoped to one stack cannot read other stacks' ccmenu" do
  own_stack = shipit_stacks(:shipit)
  other_stack = Stack.create!(repository: Repository.new(owner: "foo", name: "bar2"), branch: 'main')

  scoped_client = ApiClient.create!(
    creator: @user, name: 'scoped', permissions: %w[read:stack], stack: own_stack
  )

  get :show, params: { stack_id: own_stack.to_param, token: scoped_client.authentication_token }
  assert_response :ok

  get :show, params: { stack_id: other_stack.to_param, token: scoped_client.authentication_token }
  assert_response :not_found # or :forbidden — currently returns 200, exposing other_stack's data
end
```
Assert on both sides of the binding: `scoped_client.stack_id` (== `own_stack.id`) must equal `stack.id` resolved inside the action for every accepted request; the second request currently succeeds with `stack.id == other_stack.id != scoped_client.stack_id`, proving the binding is violated.
