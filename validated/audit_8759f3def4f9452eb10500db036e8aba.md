### Title
Unhandled exception (process crash) in `chash.isChashValid` from malformed 48-char address/chash strings - ([File: chash.js])

### Summary
`chash.isChashValid()` decodes an attacker-supplied c-hash string and then feeds the raw decoded bytes into `buffer2bin()` / `separateIntoCleanDataAndChecksum()` without verifying that the resulting bit-length actually matches the expected 160 or 288 bits. The only `try/catch` in the function wraps the decode step, not the subsequent length-dependent processing, so a crafted-but-length-correct input can slip through the initial `encoded_len` check yet decode to a byte buffer whose bit length is neither 160 nor 288, causing `separateIntoCleanDataAndChecksum()` to `throw Error("bad length=...")` uncaught.

### Finding Description
`chash.js` validates c-hashes (used as addresses, asset identifiers, definition_chash values, etc.) as follows: [1](#0-0) 

```
function isChashValid(encoded){
	var encoded_len = encoded.length;
	if (encoded_len !== 32 && encoded_len !== 48) // 160/5 = 32, 288/6 = 48
		throw Error("wrong encoded length: "+encoded_len);
	try{
		var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
	}
	catch(e){
		console.log(e);
		return false;
	}
	var binChash = buffer2bin(chash);
	var separated = separateIntoCleanDataAndChecksum(binChash);
	...
}
```

The 32-character branch uses `base32.decode`, which for a fixed-length input always yields a fixed 20-byte buffer, so 160-bit length is guaranteed. The 48-character branch, however, uses `Buffer.from(encoded, 'base64')`. Node.js's base64 decoder is intentionally lenient: it silently skips characters that are not part of the base64 alphabet instead of throwing, so a 48-character string containing a mix of valid base64 characters and "invalid" characters (e.g. punctuation) does **not** throw during decode, but produces a byte buffer shorter than the expected 36 bytes (288 bits).

That shorter buffer is passed straight to `buffer2bin()` (chash.js:96) and then to `separateIntoCleanDataAndChecksum()`: [2](#0-1) 

```
function separateIntoCleanDataAndChecksum(bin){
	var len = bin.length;
	var arrOffsets;
	if (len === 160)
		arrOffsets = arrOffsets160;
	else if (len === 288)
		arrOffsets = arrOffsets288;
	else
		throw Error("bad length="+len+", bin = "+bin);
```

This `throw` occurs *outside* the `try/catch` block in `isChashValid`, so the exception propagates unhandled up through `validation_utils.isValidChash` / `isValidAddress`: [3](#0-2) 

`isValidAddress`/`isValidChash` are called throughout unit and definition validation — on unit `authors[].address`, payment `outputs[].address`, `address_definition_change` payloads, the `address` operator inside address definitions, asset issuer/definer addresses, and AA trigger addresses (`definition.js`, `aa_validation.js`, `writer.js`, etc.), all of which are populated directly from an untrusted, attacker-posted unit or AA trigger.

### Impact Explanation
Any unprivileged unit poster, AA trigger sender, or asset issuer can embed a crafted 48-character base64-looking string in any address-shaped field of a unit (author address, output address, definition_chash, asset attestor/issuer address, AA-trigger-supplied address, etc.). When any full node parses/validates that unit, the uncaught `Error("bad length=...")` is thrown synchronously deep inside the validation code path. If this exception is not caught by an enclosing handler at that call site (many of these calls occur inside plain function bodies or inside asynchronous callbacks where a thrown exception is not caught by the caller's `try/catch` and becomes an `uncaughtException`), the node process crashes. Because every full node that receives and validates the same malicious unit (broadcast unit, once accepted into the DAG) would hit the identical crash, this is a network-wide condition that can prevent nodes from validating/confirming further units — mapping to the accepted impact category "a network unable to confirm new units," analogous to how the CVE's out-of-bounds condition let a guest crash the emulator process handling its data.

### Likelihood Explanation
The trigger condition only requires posting a syntactically valid-looking unit/trigger with one field containing a 48-character string that mixes valid base64 characters with a few invalid ones — no special privileges, keys, or node compromise are required. This is straightforward for any node/wallet user, AA author, or asset issuer to construct and broadcast.

### Recommendation
- In `chash.isChashValid`, validate the decoded buffer's exact byte length (20 for the 160-bit case, 36 for the 288-bit case) immediately after decoding, before calling `buffer2bin`/`separateIntoCleanDataAndChecksum`, and return `false` on mismatch instead of allowing an exception to escape.
- Alternatively, use a strict base64 validity check (matching `^[A-Za-z0-9+/]{48}$` or the project's `isValidBase64` helper) before calling `Buffer.from(encoded, 'base64')`, since Node's base64 decoder does not reject invalid characters.
- Wrap the whole body of `isChashValid` (not just the decode call) in `try/catch` so any unexpected internal error degrades to `return false` rather than throwing, consistent with the function's contract as a boolean validator for untrusted input.

### Proof of Concept
1. Construct a 48-character string that is otherwise plausible base64 but contains a few characters outside the base64 alphabet (e.g. replace some characters of a valid 36-byte base64 c-hash with `!` or other invalid symbols), keeping the total string length at 48 characters.
2. Place this string in an address-bearing field of a unit that is processed by `isValidAddress`/`isValidChash` (e.g., an author `address`, a payment output `address`, an `address_definition_change` payload, or an AA trigger `address` reference).
3. Post/broadcast the unit (or send the AA trigger) to the network.
4. On any node, `Buffer.from(encoded, 'base64')` silently ignores the invalid characters, producing a buffer whose length in bits is not 160 or 288.
5. `separateIntoCleanDataAndChecksum` throws `Error("bad length=...")`, which is not caught inside `isChashValid`, propagating an unhandled exception through the address-validation call chain during unit validation, crashing the node process handling that unit.
