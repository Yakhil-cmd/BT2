Based on my research, I found a directly analogous vulnerability class in `Shipit::WebhooksController`.

### Title
Webhook signature verification is bound to an attacker-controlled `repository.owner.login` field, not to the repository the event handlers actually act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a payload against using a value taken directly from the untrusted JSON body, rather than from any property that is cryptographically tied to the specific repository the event will be applied to. Downstream handlers (e.g. `StatusHandler`, `PushHandler`) then locate the target `Stack`/`Repository` using other fields of that same untrusted body (typically `repository.full_name`). Because nothing binds "the organization whose secret validated this signature" to "the repository that is ultimately written to", an attacker who legitimately controls a webhook secret for *any* organization configured in `Shipit.github` can forge a validly-signed payload whose `repository.owner.login` matches their own org (so the signature check passes) while other repository-identifying fields point at a stack belonging to a different, victim organization.

### Finding Description
`verify_signature` computes the expected HMAC using a `github_app` selected purely from the request body: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')`) with no further validation that it is consistent with any other repository field in the same payload. `Shipit.github(organization: repository_owner)` then picks the `webhook_secret` configured for that named organization in `secrets.yml`, and the signature is verified against that secret and the raw body.

Because the JSON body is entirely attacker-authored before hashing (an HMAC only proves *some* secret holder produced this exact byte string — it says nothing about internal field consistency), a party who has legitimate access to a webhook secret for `OrgA` (e.g., because they administer a repository under `OrgA` that is also configured on this same Shipit instance) can construct a body where:
- `repository.owner.login` (and/or `organization.login`) = `"OrgA"` — used only for secret selection.
- `repository.full_name`, `sha`, `state`, etc. reference an arbitrary repository/stack belonging to `OrgB` — used by the actual event handler.

Sign this body with `OrgA`'s webhook secret, and `verify_signature` will pass, because it never checks that the organization it used for signature selection matches the organization implied by the fields the handler consumes. The equality that should hold — `organization whose secret authenticated the request == organization that owns the repository being mutated` — is broken.

This mirrors the report's root cause: an authentication/verification step (`verify_from`/`verify_webhook_signature`) is decoupled from the object that is subsequently acted upon (`kfrag`/`repository`), letting a party with *some* valid credential manipulate state belonging to a different trust domain.

### Impact Explanation
Handlers dispatched after this check operate directly on `Stack`/`Commit`/`Repository` records looked up from the attacker-controlled `repository.full_name`:
- `status` events create/update a `Status` for an arbitrary commit on an arbitrary stack — this can forge a "success" CI status on a victim repository's commit, defeating `ci.require` checks and enabling an unauthorized deploy.
- `push` events can enqueue `GithubSyncJob` against a victim stack, and `check_suite` events can enqueue `RefreshCheckRunsJob`, both altering the deploy-readiness state Shipit uses to gate deploys.

Forging a passing CI status to unlock a deploy on a repository the attacker does not control satisfies the "unauthorized deploy" / cross-repository write impact bar in the rules.

### Likelihood Explanation
Exploitation requires the attacker to already hold a valid webhook secret for *some* organization configured on the target Shipit instance (i.e., they control a GitHub App/webhook registered against at least one tracked org). This is a real but non-trivial precondition — it is not "any unprivileged internet user," but it is far short of needing GitHub App private keys, `GITHUB_TOKEN`, or a Shipit session/API token. In multi-tenant deployments (`secrets.yml` configuring several `github:` orgs, as documented and exercised by `secrets.development.shopify.yml`/`secrets_double_github_app.yml`), this is a realistic boundary an org admin for one tenant could cross into another tenant's stacks.

### Recommendation
- Verify the signature using the `github_app`/secret associated with the repository actually referenced by the fields the handlers use (`repository.full_name`), not a separately-read `repository.owner.login`/`organization.login`.
- After signature verification, re-derive the target `Repository`/`Stack` and assert its owning organization matches the organization whose secret validated the request; reject on mismatch.
- Avoid resolving "which secret to check" and "which record to mutate" from two independently-trusted paths through the same untrusted payload.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as supported by `config/secrets.development.shopify.yml`).
2. Attacker legitimately controls a repository under `OrgA` and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
   - `organization.login` / `repository.owner.login` = `"OrgA"`
   - `repository.full_name` = `"OrgB/victim-repo"`
   - `sha` = the commit currently pending deploy on the victim stack, `state` = `"success"`, `context` = the context required by the victim's `ci.require`.
4. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POST to `/github/webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature against the forged body. [3](#0-2) 
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which looks up the commit/stack via `repository.full_name = "OrgB/victim-repo"` and records the forged `success` status, bypassing `OrgB`'s CI requirement and permitting an unauthorized deploy.
