### Title
Ambiguous, unescaped string concatenation in prosaic/arbiter contract hashing allows content-swap after signing - (File: prosaic_contract.js, arbiter_contract.js)

### Summary
`prosaic_contract.js` and `arbiter_contract.js` compute a commitment hash over user-supplied contract fields (`title`, `text`, `creation_date`, party/amount fields) by simple string concatenation rather than by hashing a properly length-delimited or type-tagged encoding, unlike the rest of the codebase (`string_utils.getSourceString`) which explicitly guards against this class of ambiguity. This mirrors the reported Certificate Controller bug class: a hash computed over concatenated fields without unambiguous framing lets an attacker construct two different sets of field values that hash identically, allowing the underlying content to be swapped after a counterparty has signed/accepted based on the hash.

### Finding Description
`prosaic_contract.js` computes the contract hash as: [1](#0-0) 
`crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8")` — there is no separator at all between `title` and `text`, so `(title="AB", text="CD")` and `(title="A", text="BCD")` hash identically.

`arbiter_contract.js` is slightly better but still flawed: it joins fields with a fixed `DELIMITER` string `"[|#|]"` [2](#0-1)  using `Array.join`: [3](#0-2) 
Because `title`, `text`, `payer_name`/`peer_party_name` and other string fields are attacker/peer-controlled free text, and the code never checks that these fields don't themselves contain the delimiter substring `"[|#|]"`, an attacker can embed the delimiter (or, in the legacy `else` branch, exploit the complete absence of a delimiter) inside one field to shift content across the field boundary while producing the exact same joined string and therefore the same hash.

This is the direct JS analog of the reported Solidity bug: the certificate controller assumed a fixed/standard encoding boundary between "the signed part" and the trailing signature/argument, and an attacker who could get a shortened signature could shift bytes across that assumed boundary. Here, the "boundary" between adjacent text fields is assumed to be exactly at the field lengths given, but because the fields are naively concatenated (or joined with a delimiter that can appear inside the fields themselves), an attacker can shift the boundary while keeping the digest identical. This directly contradicts the pattern used correctly elsewhere in the codebase — `string_utils.getSourceString` — which explicitly rejects values containing the join character to prevent exactly this ambiguity: [4](#0-3) 

### Impact Explanation
These hashes (`prosaic_contract.getHash` / `arbiter_contract.getHash`) serve as the content commitment that is offered to a peer, accepted/signed by the counterparty via `respond()`, and later referenced on-chain: `handleReceivedSigningUnit` checks `payload.contract_text_hash !== contract.hash` when linking a posted unit's data message to the locally stored contract text [5](#0-4) . If a malicious counterparty can craft a `title`/`text` (or, for arbiter contracts, party names/amount fields adjacent to unescaped strings) that hashes identically to different content, they could present one version of the contract for signature/acceptance and later assert a different version (e.g., different payer/payee, different amount context, or different agreed terms) that hashes to the same value, since the hash — which is treated as the tamper-evident fingerprint of the agreement — no longer uniquely commits to the field values. This is a private, off-chain/wallet-message trust mechanism between contract counterparties (payer/payee/arbiter), so it directly enables one party to defraud the other about the actual terms/amount of a payment obligation they believe was cryptographically committed.

### Likelihood Explanation
Both counterparties in a prosaic/arbiter contract are mutually untrusted peers by design (that's the entire point of hashing and signing the contract). The vulnerable `getHash`/`getHashSrc` functions take fully attacker-controllable string fields (`title`, `text`, party names) with no validation that they don't contain the separator or don't allow boundary-shifting concatenation, and no length-prefixing is used. Exploitation requires no privileged position — it is reachable by any wallet user who proposes or later disputes a contract with a normal counterparty (asset issuer / payment counterparty), fitting squarely in the "private-payment counterparty" reachable-actor category. No cryptographic breaking is required, just crafting text/strings containing chosen characters.

### Recommendation
Replace the ad hoc string concatenation with the same collision-resistant, self-describing encoding already used elsewhere in the codebase: compute the digest using `object_hash.getSourceString`/`getJsonSourceString` (or `objectHash.getBase64Hash`) over a structured object containing the individual fields, exactly as `prosaic_contract.getHashV1` already does via `objectHash.getBase64Hash(...)` for a single field — but extend it to hash a proper object (e.g. `{title, text, creation_date}` and, for arbiter contracts, all relevant fields) rather than a hand-rolled concatenation, so that field boundaries can never be shifted without changing the digest. Reject or escape any embedded delimiter/null bytes in the same way `getSourceString` already does for the rest of the protocol.

### Proof of Concept
1. Party A proposes a prosaic contract with `title = "Pay 10"`, `text = "0 USD"`. Concatenation yields `"Pay 100 USD" + creation_date`.
2. Party A also can prepare an alternate representation `title = "Pay 1"`, `text = "00 USD"`, which concatenates to the identical string `"Pay 100 USD" + creation_date`, producing the same SHA-256 hash via `getHash()` [1](#0-0) .
3. Party B reviews and signs/accepts based on the version showing "Pay 10 / 0 USD" (interpreted as $10), while the on-chain `contract_text_hash` and the stored digest cannot distinguish this from the "Pay 1 / 00 USD" (interpreted differently) rendering, since both hash identically — allowing Party A to later dispute or present the alternate wording with the same cryptographic commitment.
4. For `arbiter_contract.js`, the same technique applies by embedding the literal substring `"[|#|]"` inside `title`/`text`/party-name fields to shift content across the intended field boundaries of the joined string in `getHashSrc()` [6](#0-5) , since no validation prevents these fields from containing the delimiter itself.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
