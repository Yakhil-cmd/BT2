### Title
Webhook signature verification is scoped to the wrong organization, allowing forged events for repositories in unrelated, properly-secured GitHub organizations - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate an inbound webhook against using `repository_owner` (`params.dig('repository','owner','login')`), but every webhook handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, `PushHandler`, the `PullRequest::*` handlers) resolves the actual `Stack`/`Repository` to act on using a different, independently-attacker-controlled field from the *same* JSON body: `params.dig('repository','full_name')`. Because Shipit supports multiple GitHub organizations, each with its own optional `webhook_secret`, and `GitHubApp#verify_webhook_signature` returns `true` whenever that organization's secret is blank, an org with no configured secret can be used to smuggle forged events that reference a completely different (properly secured) organization's repository.

### Finding Description
`verify_signature` computes the org used for signature verification purely from `repository.owner.login`: [1](#0-0) 

`GitHubApp#verify_webhook_signature` deliberately bypasses verification when no `webhook_secret` is configured for that organization: [2](#0-1) 

Shipit's documented multi-org setup allows each organization to have an independent, optional `webhook_secret` (many example/dummy configs ship with it unset): [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (trivially, for the no-secret org), the request body is dispatched to handlers, none of which re-check `repository.owner.login`. Instead they resolve the target repository/stack from `repository.full_name` in the very same payload: [5](#0-4) [6](#0-5) [7](#0-6) 

`Repository.from_github_repo_name` and `Repository.from_param!` do a plain owner/name lookup with no relation back to the org whose signature verified the request: [8](#0-7) 

The binding that should hold is:
`organization whose webhook_secret validated the HMAC signature == organization of the repository the handler mutates`

Before the fix this binding does not exist at all — `verify_signature` only ever reads `repository.owner.login` to pick a secret, while every handler reads `repository.full_name` to pick the target. An attacker fully controls both of these string fields in the raw JSON body of an unauthenticated POST to `/webhooks`, and GitHub itself never validates that they refer to the same repository since the attacker is not GitHub at all in this scenario.

### Impact Explanation
In a realistic multi-organization Shipit deployment (explicitly documented and shipped as a supported configuration) where at least one onboarded organization has not set a `webhook_secret` (the field is optional and defaults to blank in every example/template file in this repo), an unauthenticated attacker can:
- Set `repository.owner.login` to the org with no secret (or to any org name that satisfies `Shipit.github_app_config`), causing `verify_webhook_signature` to short-circuit to `true` regardless of the `X-Hub-Signature` header sent.
- Set `repository.full_name` to any tracked repository belonging to a *different*, secret-protected organization.
- Trigger `PushHandler#process` to force `stack.sync_github` on stacks they do not control, or forge `status`/`check_suite` events that satisfy `ci.require` commit-status gating used by continuous delivery, or forge `pull_request` events to provision/archive review stacks for repositories under organizations whose real webhook secret was never compromised.

This crosses the "organization authenticated vs repository written" boundary called out in scope and can lead toward unauthorized deploy/rollback triggering via forged CI status and sync events, without ever touching a session, `ApiClient` token, `webhook_secret`, or GitHub App private key belonging to the targeted organization.

### Likelihood Explanation
Requires only:
1. A Shipit instance configured for multiple GitHub organizations (a documented, supported configuration).
2. At least one onboarded organization with `webhook_secret` left blank (the default/optional state shown in every shipped example config).
3. Knowledge of that organization's name (frequently public, e.g. visible from the Shipit UI/URLs) and the target repository's owner/name (public information).

No authentication, token, or insider access is needed — a single crafted unauthenticated HTTP POST to `/webhooks` suffices.

### Recommendation
Bind signature verification to the exact repository being mutated, not just the top-level org key used to pick a secret:
- After identifying `repository_owner` and verifying the signature, re-derive the repository/org actually referenced by `repository.full_name` (and by any nested `organization` fields used by handlers) and reject the request if it does not match `repository_owner`.
- Alternatively, verify the webhook signature using the org derived from `repository.full_name` (the value handlers actually trust) rather than a separately-controlled `repository.owner.login`/`organization.login` field.
- Consider making `webhook_secret` mandatory for every configured organization, and rejecting/erroring at boot if any organization config omits it, so a "no secret" org can never be used to obtain a free `verify_webhook_signature => true`.

### Proof of Concept
Assume `github_organizations` includes `"trusted-org"` (has `webhook_secret` set and owns tracked stacks) and `"empty-org"` (onboarded but `webhook_secret` left blank, per the documented optional field).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "full_name": "trusted-org/protected-repo",
    "owner": { "login": "empty-org" }
  }
}
```

- `WebhooksController#verify_signature` computes `repository_owner = "empty-org"`, loads `Shipit.github(organization: "empty-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — the request passes with **no valid signature at all**. [9](#0-8) 
- `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("trusted-org/protected-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on stacks belonging to `trusted-org`, which never authorized this request. [10](#0-9)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
