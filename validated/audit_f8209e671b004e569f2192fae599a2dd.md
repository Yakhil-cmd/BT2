### Title
Amount Forgery in Private Indivisible-Asset Payment Chains via Output-Hash / Amount Decoupling - (File: indivisible_asset.js)

### Summary
`buildPrivateElementsChain`/`validatePrivatePayment` commit only `{address, blinding}` into `output_hash` [1](#0-0) , while the transferred `amount` is carried in a sibling, uncommitted field of the *previous* chain element's payload and is trusted directly when computing the `spend_proof` for the current element [2](#0-1) . This is structurally the same bug class as the report: the value that is checked (`output_hash`, over `address`+`blinding`) and the value that is actually consumed as ground truth (`amount`) are extracted via two independent, non-cross-validated lookups from attacker-suppliable JSON, allowing a party who legitimately produced/relayed the head element to attach a forged `amount` to an unspent hidden output in the middle of the chain.

### Finding Description
Indivisible/private assets are transferred as JSON "private element" chains exchanged directly between wallets (never inline in the public DAG). Each hidden output entry only stores `{amount, output_hash}` where `output_hash = hash({address, blinding})` — computed and checked without the `amount` field [3](#0-2) , and independently re-verified the same way on receipt [4](#0-3) .

When validating a `transfer` input, the code reads `prev_hidden_output = objPrevPrivateElement.payload.outputs[input.output_index]` and uses `prev_hidden_output.amount` — taken straight from the attacker-controlled previous-element JSON, with no hash binding it to `address`/`blinding` — to compute the `spend_proof` that is checked against the DB-stored proof [2](#0-1) . The `objPrevPrivateElement` itself is only checked for internal self-consistency (its own `output_hash` matches its own `output`) in the *previous* call to `validatePrivatePayment` for `objPrevPrivateElement` — but that earlier call only compares `output_hash` (address+blinding), never validating `amount` against anything, and the two checks (`output_hash` match for the previous element vs. `amount` used for the current element's spend_proof) come from two unrelated fields of the same untrusted object, exactly the "independent lookups without cross-validation" pattern in the report.

The true anchor for `amount` is supposed to be the on-chain `payload_hash` of the message that originally created that output (verified only when `objPrevPrivateElement` itself is validated as the head of a request via `initPrivatePaymentValidationState`, comparing the full re-hashed `payload` against `messages.payload_hash` in the DB) [5](#0-4) . However, `parsePrivatePaymentChain` validates elements pairwise using `arrPrivateElements[i+1]` as `prevElement` purely by structural linkage (matching `unit`/`message_index`/`output_index`) [6](#0-5) , and `objPrevPrivateElement.payload.outputs[...].amount` is never independently re-derived from the DB `outputs` table nor from the message's on-unit `payload_hash` at that point in `validatePrivatePayment` — it is accepted as-is from the JSON chain supplied by whichever peer forwarded it.

### Impact Explanation
A malicious sender/relayer of a private-payment chain (any counterparty in a private-payment transaction, or a hub/device relaying a chain on someone's behalf) can tamper with `prev_hidden_output.amount` for an intermediate, not-yet-fully-revealed output while keeping its `output_hash` valid (since `output_hash` never covered `amount`). Because `spend_proof` for the *next* hop is derived from this forged amount and checked only against the DB `spend_proofs` table (which was populated from the same attacker-controlled data at write time, per `validateAndSavePrivatePaymentChain`), a receiving wallet can be made to record and later spend an output with an amount inconsistent with what was actually committed on-chain, i.e., supply inflation / unauthorized-value creation or freezing/loss of legitimate value within the private-asset ledger for the recipient wallet.

### Likelihood Explanation
Reachable by any private-payment counterparty or forwarding hub without special privileges — private chains are routinely exchanged wallet-to-wallet and via light-vendor/hub relays (`handlePrivatePaymentChains`, `handleSavedPrivatePayments`) [7](#0-6) [8](#0-7) , and no additional cryptographic capability beyond constructing a JSON chain is required.

### Recommendation
Include `amount` in the `output_hash` commitment (hash `{address, amount, blinding}` instead of `{address, blinding}`) everywhere it is computed and verified (`composer.js`, `indivisible_asset.js` `validatePrivatePayment`/`buildPrivateElementsChain`, `wallet.js` sign-request validation), so that `amount` cannot be altered independently of the committed hash, closing the gap between the value that is verified and the value that is consumed.

### Proof of Concept
1. Attacker (a genuine party in an indivisible-private-asset transfer, e.g., a payer forwarding a chain to the payee, or a hub relaying it) receives/creates a legitimate multi-hop private element chain `[headElement, midElement, issueElement]`.
2. In `midElement.payload.outputs[k]`, attacker changes `amount` from the true value to a larger value while leaving `output_hash` (computed only over `address`+`blinding`) unchanged — this passes the check at `indivisible_asset.js:78`.
3. Attacker forwards the tampered chain to the victim wallet via `handlePrivatePaymentChains`/`handleSavedPrivatePayments`.
4. During validation of `headElement` (`objPrivateElement = headElement`, `objPrevPrivateElement = midElement`), `prev_hidden_output.amount` is read from the tampered `midElement.payload.outputs[k].amount` and used to compute `spend_proof`, matching the stored proof if the attacker also controls/matches the corresponding `spend_proofs` DB row created at the time the tampered element was originally saved.
5. Victim's wallet accepts and records an output with an inflated `amount` for `headElement`, which can later be spent, producing unauthorized value.
