### Title
Bounce-fee dust donations silently inflate an AA's `balance[...]` used for share-price/AMM math, permanently distorting share price or bricking pool bootstrap - (File: aa_composer.js, test/samples/uniswap_like_market_maker.oscript)

### Summary
Any unprivileged unit author can send bytes (or an asset) to an autonomous agent (AA) address in a way that matches none of the AA's `if` cases. The trigger bounces, but the AA's `bounce_fees` (default `MIN_BYTES_BOUNCE_FEE`, or a custom amount) is never refunded and is permanently absorbed into the AA's real ledger balance (`aa_balances`). Financial AAs (e.g. the shipped market-maker/vault-style sample) read this exact balance via `balance[...]` to compute share prices, swap ratios and bootstrap conditions. This lets anyone donate funds to an AA "vault" without going through its intended deposit logic, exactly mirroring the reported `LidoMevTxFeeVault` issue where unsolicited ETH inflates a balance later used for reward/price accounting.

### Finding Description
`getTrigger()` sums every output sent to the AA address into `trigger.outputs` regardless of `trigger.data` or the amount [1](#0-0) . Before any `if` case is evaluated, `updateInitialAABalances()` unconditionally adds the *entire* received amount to the AA's persisted `aa_balances` row [2](#0-1) .

If the sent amount does not satisfy any case's `if` condition, the AA has "no messages" and calls `bounce()`. `bounce()` only refunds `amount - fee` for each asset — the configured `bounce_fees` portion (default `constants.MIN_BYTES_BOUNCE_FEE`, e.g. 10000 bytes) is *never* sent back and stays baked into `aa_balances` forever [3](#0-2) .

Financial sample AAs shipped with ocore compute prices/shares directly from this same ledger balance via the `balance[...]` oscript accessor, e.g. the Uniswap-like market maker:
- The very first deposit is special-cased on `$bytes_balance == 0` to seed the pool 1:1 [4](#0-3) .
- Every subsequent swap/divest uses `balance[base]` / `balance[$asset]` directly to compute constant-product swap amounts and to pay out investor shares [5](#0-4) .

Because bounce-fee dust silently and permanently raises `balance[base]` without any corresponding update to `var['mm_asset_outstanding']` or asset issuance, an attacker can:
1. Send an amount of bytes that matches no case (e.g. below the `1e5` threshold and without the swap/mm-asset conditions) *before* the pool is ever bootstrapped. This bounces but leaves the bounce fee in `balance[base]`, so `$bytes_balance` is no longer `0` when the legitimate first investor deposits — the "initial deposit" branch is skipped, and the ratio check `$expected_asset_amount = round($current_ratio * trigger.output[[asset=base]])` evaluates to `0` (since `$asset_balance` is still `0`), causing every future first-deposit attempt to bounce with `'wrong ratio of amounts, expected 0 of asset'`, permanently bricking bootstrap of the AMM.
2. Repeatedly trigger cheap bounces against a live pool to keep nudging `balance[base]`/`balance[$asset]` upward without minting/burning `mm_asset`, thereby diluting or inflating the redeemable value per `mm_asset` share for existing LPs — the same "fluctuation of share price from unauthorized deposits" impact described in the reference report.

### Impact Explanation
This lets an unprivileged trigger sender either (a) permanently freeze/brick a financial AA's core function (pool can never be initialized — a fund-freezing DoS), or (b) skew the balance-derived share price/exchange rate used by every subsequent investor and swapper, causing unfair value transfer between AA participants who rely on `balance[...]` faithfully reflecting only accounted deposits. This is a realistic Medium/High-severity issue for any AA that mirrors this common oscript pattern of pricing off raw `balance[...]`.

### Likelihood Explanation
The attack requires only posting a single low-value unit with an output to the target AA address that fails to match any `if` case (trivial to construct, no privileges needed), and costs only the bounce fee (as low as `constants.MIN_BYTES_BOUNCE_FEE`). It is reachable by any wallet holder able to post units, with no special access to the AA definer or governance.

### Recommendation
- In `aa_composer.js`, consider not silently retaining `bounce_fees` inside the AA's spendable/queryable `balance[...]` when a trigger bounces due to no matching case, or expose a separate accounting bucket (e.g. `accumulated_bounce_fees`) that oscript authors can subtract out before using `balance[...]` for price-sensitive math.
- Document clearly (and update sample AAs such as `uniswap_like_market_maker.oscript`) that `balance[...]` includes *all* funds ever sent to the AA, including bounced dust, and that price-critical formulas must track their own state variable for "accounted" reserves rather than trusting raw `balance[...]`.
- For the bundled sample AA, guard the bootstrap/ratio logic against non-zero dust balances, e.g. treat balances below a minimum threshold as zero, or require an explicit `define`/`init` deposit transaction that records the initial reserve into a state var instead of inferring it from `balance[...]`.

### Proof of Concept
1. Post an AA using the exact `uniswap_like_market_maker.oscript` sample logic [6](#0-5) ; do not deposit yet.
2. From any unprivileged address, send e.g. 20000 bytes (more than default `bounce_fees.base` of 10000, but with `trigger.data` empty and no relevant outputs) directly to the AA address. None of the `if` conditions match (`invest` needs `base > 1e5`; `exchange bytes to asset` needs `base > 1e5`; others need asset/mm_asset outputs), so `bounce()` fires [7](#0-6) . 10000 bytes bounce fee is retained in `aa_balances`, 10000 refunded.
3. The legitimate first investor now sends bytes + the correct 1:1 ratio of `$asset` expecting the "initial deposit" branch (`$bytes_balance == 0`) to fire. Since `balance[base]` is already 10000 from step 2, `$bytes_balance != 0`, so the code instead computes `$current_ratio = 0 / 10000 = 0` and `$expected_asset_amount = 0`, and the deposit bounces with `'wrong ratio of amounts, expected 0 of asset'` — the pool can never be bootstrapped through the intended path.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
