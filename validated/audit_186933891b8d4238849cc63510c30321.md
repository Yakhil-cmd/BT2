### Title
`gh extension upgrade` destructively removes an installed extension before confirming the replacement install succeeds, permanently losing the extension on failure - ([File: pkg/cmd/extension/manager.go])

### Summary
`Manager.upgradeExtension()` migrates a git-based extension to the precompiled binary format by first deleting the existing, working extension via `m.Remove()` and only afterward attempting to install the new binary via `m.installBin()`. If the install step fails for any reason, the user's previously working extension has already been permanently deleted, with no restoration path.

### Finding Description
When upgrading a git-installed extension, gh checks whether the extension's repository has since switched to the precompiled-binary format: [1](#0-0) 

```go
} else {
    // Check if git extension has changed to a binary extension
    var isBin bool
    repo, repoErr := repoFromPath(m.gitClient, filepath.Join(ext.Path(), ".."))
    if repoErr == nil {
        isBin, _ = isBinExtension(m.client, repo)
    }
    if isBin {
        if err := m.Remove(ext.Name()); err != nil {
            return fmt.Errorf("failed to migrate to new precompiled extension format: %w", err)
        }
        return m.installBin(repo, "")
    }
    err = m.upgradeGitExtension(ext, force)
}
```

`m.Remove()` unconditionally deletes the extension's install directory: [2](#0-1) 

Only after this destructive removal does the code call `m.installBin(repo, "")`, which can fail for multiple legitimate, remotely-triggerable reasons controlled by the (untrusted) extension repository owner or a flaky network path — e.g. no release asset matching the user's platform/architecture: [3](#0-2) 

or a failed asset download: [4](#0-3) 

If any of these occur, `upgradeExtension` returns an error, but the extension directory removed by `m.Remove()` is never restored — the extension is now completely uninstalled.

This exactly mirrors the root cause pattern in the reference report: state that is required to complete a dependent operation (the user's remaining reward balance / the user's installed extension) is destructively cleared *before* the dependent operation (`_distributeETHRewardsToUserForToken` / `installBin`) is confirmed to succeed, causing irrecoverable loss when that dependent step fails.

Notably, the codebase elsewhere explicitly avoids this exact class of bug by using atomic stage-then-swap patterns that only replace existing content after the new content is fully validated (see `updateSkillInPlace` / `swapDirectoryContents` in `pkg/cmd/skills/update/update.go`, which stages into a temp directory and only swaps in on success, with rollback on failure). The extension-manager binary migration path does not follow this safer pattern.

### Impact Explanation
An extension repository owner (or anyone who can influence the content/availability of that repository's releases — including a compromised/malicious maintainer, or simply a repository author making an incomplete binary release) can cause any user who runs `gh extension upgrade` on that extension to permanently lose their working extension installation with no fallback, since:
1. `isBinExtension` reports true because the repo has *any* release/binary indicators, but
2. the specific release lacks an asset for the invoking user's OS/architecture, or the download otherwise fails.

The user ends up with the extension completely removed and must manually reinstall it (`gh extension install`), and only if the previous git-checked-out state (e.g. any local modifications) is not recoverable, that data is lost entirely. This is a destructive, unprivileged, remotely-triggerable data-loss/availability issue reachable via a normal `gh` command against attacker-influenced repository content.

### Likelihood Explanation
Moderate. Triggering requires:
- The user having installed an extension in git format.
- The extension repo transitioning to (or claiming) binary-format releases.
- The specific release lacking a binary for the user's platform, or the download/network step failing at the moment of upgrade.

These conditions are plausible and fully controllable by the untrusted repository owner (e.g., publishing a release with a `binManifest`/binary indicator but omitting platform coverage, or temporarily removing/breaking the asset). No privileged access, MITM, or local access is required — the only "attacker" input is the content of the extension's own repository, which any extension author controls and any user might have installed following gh's normal, sanctioned extension flow.

### Recommendation
Do not delete the existing extension state until the replacement installation has fully succeeded. Restructure `upgradeExtension`'s binary-migration branch to:
1. Install the new binary version into a temporary/staging location first (similar to `installBin`'s existing per-target-directory writes, or reusing the stage-then-atomic-swap pattern used by `updateSkillInPlace`/`swapDirectoryContents`).
2. Only remove/replace the old extension directory after the new binary install is verified to be complete and valid.
3. On failure, leave the original git-installed extension completely untouched and return the error to the user.

### Proof of Concept
1. Install a git-based extension normally: `gh extension install owner/gh-foo`.
2. As the (malicious/careless) owner of `owner/gh-foo`, publish a new GitHub Release containing binary assets, but omit the asset for the victim's platform/architecture (e.g., only `gh-foo-linux-amd64` while the victim runs `darwin-arm64` with no Rosetta), so that `isBinExtension` returns `true` but `installBin`'s asset-selection loop finds no match.
3. Victim runs `gh extension upgrade owner/gh-foo`.
4. `upgradeExtension` detects `isBin == true`, calls `m.Remove("gh-foo")`, which succeeds and deletes `~/.local/share/gh/extensions/gh-foo` (or platform equivalent).
5. `m.installBin(repo, "")` then fails with `"gh-foo unsupported for darwin-arm64."` (manager.go:327-335).
6. The upgrade command reports failure, but `gh-foo` is now completely gone: `gh extension list` no longer shows it, and no rollback restores the previously working git checkout.

func (m *Manager) Remove(name string) error {
	name = normalizeExtension(name)
	targetDir := filepath.Join(m.installDir(), name)
	if _, err := os.Lstat(targetDir); os.IsNotExist(err) {
		return fmt.Errorf("no extension found: %q", targetDir)
	}
	if m.dryRunMode {
		return nil
	}
	if err := m.cleanExtensionUpdateDir(name); err != nil {
		return err
	}
	return os.RemoveAll(targetDir)
}
