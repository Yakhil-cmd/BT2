### Title
`StatusHandler#process` writes CI status to commits by bare SHA with no repository scoping - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` [1](#0-0) , which is a global lookup across every `Stack`/`Repository` in the Shipit instance. Because the webhook signature is only bound to the *organization named in the payload* and never to the specific commit/stack being mutated, a `status` event authenticated for one repository can flip CI state on a commit that belongs to a completely different, unrelated stack — including a production stack expecting `deploy/production`.

### Finding Description
The broken binding is: `authenticated_repository(payload) == commit.stack.repository` — this should always hold for any mutation performed by `StatusHandler#process`, but it is never checked.

- `WebhooksController#verify_signature` derives `repository_owner` purely from the attacker-supplied payload (`params.dig('repository','owner','login')` or `organization.login`) and validates the signature against `Shipit.github(organization: repository_owner)`'s configured `webhook_secret` [2](#0-1) . This only proves the request was signed by whichever org's secret matches the *claimed* owner — it says nothing about which `Commit`/`Stack` the payload's `sha` will resolve to.
- `StatusHandler` params schema does not even require a `repository` field [3](#0-2) , and `process` never scopes the query by repository/stack: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) .
- `create_status_from_github!` unconditionally records the status against whatever stack the matched commit belongs to and triggers deploy-gating side effects (`stack.schedule_merges`, `Hook.emit(:deployable_status, ...)`) [4](#0-3) [5](#0-4) .
- `Commit#deployable?`/`#blocked?` depend on `stack.blocking_statuses`/required statuses derived from `status`, so a forged `deploy/production` success (or failure) on a shared-SHA commit changes `deployable?`/`blocked?` for the victim stack [6](#0-5) .

Exploit flow: an attacker owns/controls a repository connected to the same Shipit instance (or any repository whose commit history shares a SHA with the victim's tracked branch — e.g. a public fork of the victim's repo, which by git design preserves identical SHAs for shared commits). The attacker triggers or sends a `status` webhook (event `status`, `context: deploy/production`, `state: success`) for a shared SHA. The signature check passes because it's validated against the attacker's own organization's webhook secret (or passes trivially if `webhook_secret` is unset for that org, since `verify_webhook_signature` returns `true` when no secret is configured [7](#0-6) ). `StatusHandler#process` then finds `Commit` rows across all stacks matching that SHA, including the victim's production stack, and writes the status there, regardless of which repository actually authenticated the request.

None of the existing guards prevent this: `verify_signature` checks org-secret validity but not repo/commit ownership; `drop_unhandled_event` only checks the event type is handled; there is no `ExplicitParameters` requirement of `repository.full_name` in `StatusHandler`; and there is no post-lookup filter comparing `commit.stack.repository` to the authenticated organization/repo.

### Impact Explanation
A payload authenticated for repository A can mutate CI status, and thus deploy/merge gating, for repository B's stack whenever a commit SHA is shared or collides between A and B. This is a "payload for one repository mutating another's stack/commit" — squarely a Critical-impact category (unauthorized deploy/rollback/merge of code the victim did not intend). Blast radius spans every stack in the Shipit instance sharing history/SHAs with an attacker-reachable repository, not limited to one tenant. The repeatability is bounded only by the attacker's ability to find or produce a shared SHA (trivial for public forks of the victim repository, which is the realistic scenario for the `deploy/production` + "production environment" framing in the question).

### Likelihood Explanation
Preconditions: (1) attacker needs a webhook signature valid for *some* organization known to Shipit (their own org/fork with `status` webhooks enabled, or any org whose `webhook_secret` is unset), and (2) a commit SHA that also exists in the victim's tracked stack (trivially achievable via public forks sharing upstream history, since fork commits retain identical SHAs). Both preconditions are realistic for open-source or multi-repo Shipit deployments. No Shipit session, API token, or GitHub team membership is required. The attack is repeatable at will for any SHA the attacker can produce/share.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to the repository that authenticated the webhook: require the payload's `repository.full_name` in the params schema, resolve the `Repository` from it, and restrict the `Commit` lookup to `repository.stacks.commits.where(sha: params.sha)` instead of a bare global `Commit.where(sha:)`. Apply the same repository-scoping check consistently to every webhook handler that resolves records by SHA/number without joining to `Repository`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook for shared SHA mutates an unrelated stack's commit" do
  attacker_repo = shipit_repositories(:rails)         # attacker-authenticated org
  victim_repo   = shipit_repositories(:shipit)        # unrelated, production stack
  victim_stack  = victim_repo.stacks.create!(environment: "production", ...)
  shared_sha    = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)

  # Attacker sends a status payload with repository owner = attacker_repo's org,
  # signature verified against attacker_repo's org webhook_secret (valid),
  # but sha == shared_sha which also belongs to victim_commit.
  params = ExplicitParameters::Params.new(
    sha: shared_sha, state: "success", context: "deploy/production",
    branches: [{ name: victim_stack.branch }]
  )

  assert_not_equal attacker_repo, victim_commit.stack.repository  # equality that should hold pre-exploit

  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  victim_commit.reload
  assert_equal "success", victim_commit.status.state   # victim stack's commit mutated
  assert victim_commit.deployable?                      # production stack now considered deployable
end
```
This demonstrates `Commit.where(sha:)` in `StatusHandler#process` [1](#0-0)  writing a status to a commit belonging to a repository that did not authenticate the request, breaking the required invariant.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
