### Title
Uncaught exception crashes the node when an AA's `data_feed[[...]]` formula reads tied unstable data feeds - ([File: data_feeds.js])

### Summary
`readDataFeedValue()` in `data_feeds.js` sorts candidate unstable data-feed messages when multiple oracles' unstable units qualify for the same `data_feed` lookup. When two candidates cannot be ordered (same `latest_included_mc_index` and same `level`) and the caller is an AA evaluation (not the `all_unstable` light-wallet path), the sort comparator executes a bare `throw Error(...)` instead of returning a safe error to the callback chain.

### Finding Description
`formula/evaluation.js` implements the oscript `data_feed` operator (case `'data_feed'`, around line 600-663), which calls `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, ...)` [1](#0-0)  with `unstable_opts = bAA` (i.e. `true`, not the string `'all_unstable'`). This is exactly the AA-formula execution path, reachable from any AA trigger sender who causes an AA to evaluate a `data_feed[[oracles=...]]` expression referencing multiple oracle addresses.

Inside `readDataFeedValue`, when `bIncludeUnstableAAs` is true, the function scans all currently unstable units authored by the listed oracle addresses and collects matching `data_feed` message candidates into `arrCandidates` [2](#0-1) . If more than one candidate qualifies and `ifseveral` is not `'abort'` (the default is `'last'`), the code sorts candidates by `latest_included_mc_index` then `level`:

```
arrCandidates.sort(function (a, b) {
    if (a.latest_included_mc_index < b.latest_included_mc_index) return -1;
    if (a.latest_included_mc_index > b.latest_included_mc_index) return 1;
    if (a.level < b.level) return -1;
    if (a.level > b.level) return 1;
    if (bIncludeAllUnstable) return 1; // OK outside AAs
    throw Error("can't sort candidates " + a + " and " + b);
});
``` [3](#0-2) 

Since the AA path passes `unstable_opts = bAA = true` (not `'all_unstable'`), `bIncludeAllUnstable` is `false` for AA formula evaluation, so any tie in both `latest_included_mc_index` and `level` between two candidate units hits the `throw Error(...)` branch. Two different unstable units authored by different oracle addresses can legitimately share the same `level` and `latest_included_mc_index` while the DAG is not yet stabilized (levels are not required to be globally unique across parallel branches). This is a normal, attacker-inducible DAG condition, not a malicious-peer or malformed-message condition — any two unprivileged posters (acting as the "oracles" named in the AA's formula) can post `data_feed` messages with the same feed name/matching value at units that end up at equal level and equal `latest_included_mc_index`.

The `throw` happens synchronously inside the `Array.prototype.sort` comparator, which runs inside the call stack of `evaluate()` in `formula/evaluation.js` — itself invoked from `aa_composer.js`'s `handleTrigger`/`evaluateAA` during processing of a posted AA trigger unit [4](#0-3) . There is no `try/catch` wrapping this call chain, and the only global exception handler found in the codebase is in `network.js`, unrelated to AA/composer processing.

### Impact Explanation
An uncaught synchronous exception thrown deep inside AA trigger processing will propagate up the call stack. Depending on the surrounding invocation context (event loop tick vs. promise chain), this either crashes the Node.js process (since there's no matching `try/catch`) or leaves the writer in an inconsistent state mid-transaction, causing that node to be unable to process/confirm the AA response and any dependent unit. This matches the CVE-2020-14868 bug class: a network-reachable, unprivileged operation (posting units / an AA trigger + normal oracle posts) causes a "hang or frequently repeatable crash" — a full denial of service of the affected node's ability to confirm units, rather than data compromise.

### Likelihood Explanation
Reaching the tie condition requires only that:
1. An AA definition includes a `data_feed[[oracles="ADDR1:ADDR2", feed_name=..., ...]]` expression using multiple oracle addresses (not attacker-controlled if the AA is pre-existing, but any AA author — including the attacker themselves, since AAs are permissionlessly deployable — can define this).
2. Two of those oracle addresses post matching data-feed values in units that end up unstable, at the same DAG level and same `latest_included_mc_index` when the AA trigger is evaluated.

Since DAG level ties across different authors in different branches are common under normal network conditions (and can be engineered by controlling parent selection when composing the two data-feed-posting units), and the code path defaults `ifseveral` to `'last'` (so no special formula syntax is even required to hit the vulnerable branch), likelihood is moderate: it requires deploying/using an AA with a multi-oracle `data_feed` reference and timing two posts to tie in level/mci, which an attacker fully controls with unprivileged posting rights.

### Recommendation
Replace the `throw Error(...)` in the tie-break branch of `readDataFeedValue`'s sort comparator with a deterministic tie-breaker (e.g., compare `unit` hash lexicographically) instead of throwing, mirroring how the `bIncludeAllUnstable` branch already tolerates ambiguity. Alternatively, propagate the ambiguous state through `objResult`/`handleResult` (as is already done for the `ifseveral === 'abort'` case) rather than throwing synchronously from within `Array.prototype.sort`.

### Proof of Concept
1. Deploy an AA whose bounce/response logic includes a formula such as:
   `data_feed[[oracles="ORACLE1:ORACLE2", feed_name="price"]]`
   with `ifseveral` left at its default (`'last'`).
2. From two different addresses (`ORACLE1`, `ORACLE2`), post `data_feed` messages with the same `feed_name` and equal/matching values, structuring parent selection so that both resulting units land at the same DAG `level` and have the same `latest_included_mc_index` while still unstable.
3. Post a trigger unit to the AA before these two units stabilize, forcing `readDataFeedValue` to evaluate with `arrCandidates.length > 1` and a tie on `latest_included_mc_index`/`level`.
4. The comparator throws `Error("can't sort candidates ...")` synchronously inside AA trigger evaluation in `aa_composer.js`, with no surrounding `try/catch`, crashing/hanging the node processing that trigger.

Note: I could not fully verify at what exact call depth (promise vs. plain callback) the exception ultimately surfaces (i.e., whether it always crashes the process vs. is sometimes swallowed by an intermediate async library), since that depends on runtime call-stack framing in `async`/`setImmediate` chains not fully traced here — a Devin session with the full codebase and a running test harness would be needed to confirm the exact crash behavior end-to-end.
