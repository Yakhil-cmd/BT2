## Title
Webhook signature verified against `repository.owner.login`/`organization.login`, but event handlers act on the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), but every event handler that actually mutates state resolves the target `Stack`/`Repository` using the independent `repository.full_name` field from the same JSON body. Nothing ties these two fields together, so a payload can be crafted where they name different repositories/organizations.

### Finding Description
`verify_signature` computes the signing organization purely from:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 
and verifies `X-Hub-Signature` against `Shipit.github(organization: repository_owner)`'s `webhook_secret` [2](#0-1) .

Once verified, `params` (the raw, attacker-controlled JSON) is dispatched unchanged to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Every handler resolves its target repository/stack from a *different* field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

This is the exact bug-class analog described in the report: a value used to authorize an action (`repository.owner.login`, which selects the signing secret) is decoupled from the value the code actually acts on (`repository.full_name`, which selects the target repository/stack). The binding that should hold is:
`verified_signature_org == owner(full_name_used_for_dispatch)`, but the code never enforces this equality — `repository.owner.login` and `repository.full_name`'s owner segment are read independently and never cross-checked.

Concretely: an attacker who can obtain (or is issued) a valid `webhook_secret` for *any* organization configured in `Shipit.github_organizations` (e.g., because they administer a sandbox/test org that has the Shipit GitHub App/webhook installed) can sign a raw payload where:
- `repository.owner.login = "attacker-org"` (used only for signature lookup)
- `repository.full_name = "victim-org/victim-repo"` (used by every handler to pick the target `Stack`)

Because `verify_signature` only checks the HMAC against `attacker-org`'s secret and never validates that `full_name` belongs to that org, the forged event is accepted and dispatched with the victim's `full_name`.

### Impact Explanation
The clearest concrete exploitation path is `StatusHandler`, which writes directly from attacker-controlled payload fields into the DB without any GitHub API round-trip:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 
This handler doesn't even use `repository.full_name`/`Repository.from_github_repo_name` scoping (it matches purely by commit `sha` across the whole Shipit instance), so a signature validated against the attacker's own org's secret lets the attacker inject fabricated `state`/`context`/`description`/`target_url` commit statuses for *any* commit SHA known to the attacker, including SHAs belonging to a victim's stack — directly influencing whether Shipit considers a commit "deployable" (CI status gating for continuous delivery). Similarly, `PushHandler`/`GithubSyncJob` and the PR handlers key off `repository.full_name` to pick the victim's `Stack`/`Repository`, letting an attacker trigger unauthorized syncs, PR label/assignment writes, or review-stack lifecycle actions against a stack they should have no relationship to, using a secret that was only ever supposed to authorize events for their own organization.

This crosses the authorization boundary defined in the rules (an "organization that authenticated versus the repository that is written") and produces unintended writes into stacks/commits that ultimately feed CD gating and deploy eligibility.

### Likelihood Explanation
Requires the attacker to control or know a `webhook_secret` for at least one organization configured in the Shipit deployment (`Shipit.github_organizations`) — plausible in multi-tenant/self-hosted Shipit installs where several orgs (including lower-trust sandbox orgs) are configured with distinct per-org secrets, since nothing in `WebhooksController` prevents cross-org payload construction once any single valid secret is available. No repository write access, GitHub App private key, or `ApiClient` token is needed — only a webhook secret for one configured org and network access to `POST /webhooks`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that the organization whose secret was used to verify the signature actually owns the repository being acted upon: derive the acting repository's owner from `full_name` and require it to equal `repository_owner`/`organization.login` before dispatching to handlers, rejecting (422) any payload where these disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), as is supported by `Shipit.github_organizations`.
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, raw_body)` using their own known secret `S_A`.
4. `WebhooksController#verify_signature` calls `repository_owner` → `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature against `S_A` [2](#0-1) .
5. `StatusHandler.call(params)` executes and writes a forged `success` status for the victim's commit `sha` [5](#0-4) , despite the attacker never having had `webhook_secret` access to `victim-org`.
