## Analysis Result

### Title
Cross-organization CI status injection via unscoped `StatusHandler` webhook - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to attach a GitHub `status` event to by SHA alone, with no scoping to the repository/organization that the webhook signature was verified against. Because the signature-selection logic and the data-mutation logic key off two different fields of the same payload (organization vs. arbitrary SHA match across the whole database), a webhook that is legitimately signed for one tenant/organization can create a `Status` record — and cascade into CI-gating and continuous-delivery logic — for a commit that actually belongs to a completely different stack/organization on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` selects which organization's webhook secret to verify the HMAC against using `repository_owner`, derived from the payload's `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

This authenticates the *sender* as being organization X (i.e., a valid, GitHub-App-configured tenant on the Shipit instance). It says nothing about which stack/repository the event's *contents* are permitted to affect.

For most webhook handlers, the base `Handler` class scopes any change to the repository named in the payload: [3](#0-2) 

However, `StatusHandler` does not use this scoping at all. It matches commits purely by `sha`, globally across every stack in the database: [4](#0-3) 

`Commit#create_status_from_github!` then creates a `Status` scoped to `stack_id` derived from the found commit's own `stack`, not from the organization that was authenticated: [5](#0-4) 

`Status` creation has real side effects, independent of which org authenticated the request: it flips `ci_enabled?` for the target stack and schedules continuous delivery evaluation: [6](#0-5) [7](#0-6) 

If the target stack has `continuous_deployment: true`, a `success` status on the "next deployable commit" directly triggers a real deploy via `ContinuousDeliveryJob` / `Stack#trigger_continuous_delivery`: [8](#0-7) [9](#0-8) 

This is corroborated by tests showing that simply creating a `success` `Status` on a commit is sufficient to enqueue a deploy when `continuous_deployment` is enabled — with no repository-ownership check involved in that path: [10](#0-9) 

**Binding broken:** *the organization that the webhook signature authenticates* (`repository.owner.login`, checked in `verify_signature`) ≠ *the stack/repository whose commit and CI state is actually mutated* (`Commit.where(sha: params.sha)`, unscoped in `StatusHandler`). Since Shipit explicitly supports multiple independently-configured GitHub organizations/App installations on one instance (`config/secrets.development.shopify.yml`, `docs/setup.md`), this is a genuine cross-tenant boundary in a deployed multi-org Shipit instance.

### Impact Explanation
An attacker who legitimately controls (or is a maintainer/admin for) one organization's GitHub App integration on a shared Shipit instance — i.e., can produce a validly-signed `status` webhook for their own org — can forge a `status` event whose `sha` matches a known commit SHA in a **different** organization's tracked repository/stack (SHAs are public information visible via GitHub, PRs, commit links, etc., and are not secrets). Because `StatusHandler` never checks that the commit's repository belongs to the authenticated organization, the attacker's forged, cross-tenant-signed webhook can:
- Fabricate a passing CI status (`state: success`) on a victim stack's commit, and
- If that victim stack has `continuous_deployment` enabled, directly cause `Stack#trigger_continuous_delivery` to fire an **unauthorized deploy** of that commit.

This matches the Critical impact category of "an unauthorized deploy" via a credential/authentication boundary crossing (organization A's signature is treated as sufficient authority to mutate organization B's CI/deploy state).

### Likelihood Explanation
Requires: (1) the target Shipit instance host multiple organizations/tenants (a documented, supported configuration — `config/secrets.development.shopify.yml`, `docs/setup.md`), (2) attacker controls at least one legitimate org's GitHub App/webhook signing capability (an intended, low-privilege capability — not a Shipit session/API token), and (3) knowledge of a target commit SHA in another org's tracked repo (trivially obtainable if that repo is public, or observable via the Shipit UI itself, which is often not access-restricted per stack). No `ApiClient` token, GitHub App private key, or Shipit session is required to exploit this beyond controlling one tenant's own webhook signing.

### Recommendation
`StatusHandler#process` should scope its `Commit` lookup to the repository identified in the *signed* payload's `repository.full_name`/`owner.login` (the same field verified in `WebhooksController#verify_signature`), analogous to how other handlers use `Handler#stacks`/`Handler#repository_name`, rather than matching any commit in the database purely by SHA. Additionally, consider asserting that `verify_signature`'s selected organization matches the `repository.owner.login` used by every handler that mutates data, to close this class of binding mismatch for any future/other handlers.

### Proof of Concept
1. Shipit instance hosts two tenants: `org-attacker` and `org-victim`, each with its own GitHub App / `webhook_secret` in `config/secrets.yml`.
2. `org-victim` has a stack with `continuous_deployment: true` and an undeployed commit with SHA `deadbeef...` (visible publicly on GitHub).
3. Attacker (a maintainer of `org-attacker`'s GitHub App) crafts a raw JSON payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-attacker/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `org-attacker`'s known `webhook_secret` over this payload and POSTs it to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-attacker"`, fetches `Shipit.github(organization: "org-attacker")`, and the signature verifies successfully (attacker signed it themselves).
6. `Shipit::Webhooks::Handlers::StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — matching the commit in **`org-victim`'s** stack — and calls `commit.create_status_from_github!(params)`, creating a `success` `Status` scoped to `org-victim`'s stack.
7. `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later(org_victim_stack)` fires, and if the commit is now the next deployable commit, `Stack#trigger_continuous_delivery` initiates an unauthorized deploy on `org-victim`'s infrastructure.

**Uncertainty:** I could not fully trace whether additional guardrails (e.g., `ci.require`/`ci.blocking` contexts configured in `org-victim`'s `shipit.yml`) would require multiple distinct `context` values to be faked before a deploy actually fires — the PoC assumes a single required CI context, which is a common configuration but not universal. This does not change the root-cause finding (missing repository/org scoping in `StatusHandler`), only the exact conditions under which it escalates to an actual deploy trigger versus merely corrupting another org's CI status history.

module Shipit
  module Webhooks

      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|

          end
        end
      end

        continuous_delivery_resumed!
        return
      end

        continuous_delivery_delayed!

      end
