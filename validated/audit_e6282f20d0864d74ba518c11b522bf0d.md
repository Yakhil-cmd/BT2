### Title
GitHub PR labels can override the `SHIPIT` environment sentinel (and arbitrary env vars) via `ReviewStack#env` - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges the upcased names of GitHub pull-request labels directly into the process environment hash *after* calling `super`, with no reserved-key filtering. Because pull-request labels are fully attacker-controlled by the PR author, an attacker can add a label named `shipit` to their own PR and have `ENV['SHIPIT']` become `"true"` instead of the sentinel value `"1"` that `Commands#env`/`Shipit.env` establishes for all shipit-driven commands.

### Finding Description
The binding that should hold is: `env['SHIPIT'] == Shipit.env['SHIPIT'] == '1'`, verified for the base case in [1](#0-0) .

`Commands#env` returns `base_env`, which is built from `Shipit.env` and is the source of the `SHIPIT` sentinel: [2](#0-1) [3](#0-2) .

`ReviewStack#env` overrides the stack-level `env` method and unconditionally merges a hash built from `pull_request.labels`, keyed by `label_name.upcase`, with the literal value `"true"`, applied *after* `super`: [4](#0-3) . There is no allow-list, reserved-word check, or filtering of the label-derived keys before they are merged — unlike the model-backed `EnvironmentVariable` records that stack maintainers configure through the UI, labels are attacker-supplied strings from a source (`pull_request.labels`) that any GitHub user who can label their own PR fully controls, and they land as raw hash keys in the same environment hash used to run shipit commands.

`Command#unbundled_env` merges `BASE_ENV`, a `PATH` override, and the caller-supplied `@env` hash (stringified) verbatim, with no key protection at all: [5](#0-4) , and `Command#start` passes this straight to `PTY.spawn`: [6](#0-5) . Whatever hash reaches `Command.new(..., env: ...)` is trusted as-is; nothing downstream re-asserts `SHIPIT == '1'`.

Exploit flow: an attacker opens a pull request against a repository that has review stacks enabled, and — using only the GitHub API access any PR author has over their own PR — adds a label literally named `shipit` (or any casing that upcases to `SHIPIT`). The label-capturing webhook handler records this label on the `PullRequest` record [7](#0-6) . The next time `ReviewStack#env` is computed for a task/deploy on that review stack, the `.merge` call at review_stack.rb:87-92 overwrites the `SHIPIT` key set by `super` with `"true"`.

None of the existing guards intercept this: `verify_signature`/webhook checks only authenticate that the payload is genuinely from GitHub for that repo, not that label content is safe; `EnvironmentVariables#permit` governs the model-backed stack environment variables UI, not this ad-hoc hash built from labels; there is no `Stack`/`ReviewStack` validation restricting label names or filtering reserved environment keys.

### Impact Explanation
Any deploy or rollback script that gates safety-relevant logic on `SHIPIT == '1'` (a common idiom for "only run this under Shipit automation") can have that check silently flipped to `'true'` by a label the attacker fully controls on their own PR, on their own review stack. This is a repeatable, self-contained manipulation of the review stack's execution environment purely through unprivileged PR-labeling actions — no privileged Shipit credentials are required. The blast radius is scoped to review stacks for repositories where review stacks are enabled; it does not itself leak `GITHUB_TOKEN` or other secrets (those come from `Commands#base_env`, established independently), but it does let an unprivileged actor corrupt a value in the environment that scripts may rely on for correctness/safety gating during real deploy command execution.

### Likelihood Explanation
Preconditions: the target repository must have Shipit review stacks enabled (a Shipit/repository configuration choice, not attacker-controlled), and a deploy/rollback/task script must actually branch on `SHIPIT`'s exact value. Attacker cost is trivial: open a PR, add a label named `shipit` via the standard GitHub label API available to any PR author on their own PR/repo, and the label-capturing webhook handler persists it automatically. This is fully repeatable and requires no Shipit secrets, sessions, or team membership.

### Recommendation
In `ReviewStack#env`, reject or filter out label-derived keys that collide with reserved environment names (at minimum `SHIPIT`, and ideally all keys already present in `super`), e.g. merge with `super` taking precedence, or explicitly delete reserved keys from the label-derived hash before merging:
```ruby
def env
  return super unless pull_request.present?

  label_env = pull_request.labels.each_with_object({}) { |l, h| h[l.upcase] = "true" }
  label_env.except!(*super.keys)
  super.merge(label_env)
end
```

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb
test "#env does not allow pull request labels to override the SHIPIT sentinel" do
  stack = shipit_stacks(:review_stack) # or build a ReviewStack fixture
  pull_request = stack.pull_request
  pull_request.update!(labels: ['shipit'])

  assert_equal '1', stack.env['SHIPIT'], "PR label should not override the SHIPIT sentinel value"
end
```
Before the fix, `stack.env['SHIPIT']` evaluates to `"true"`; after the fix it remains `"1"`.
