## Confirmed

The binding claimed to be broken: `repository_owner` used for signature verification (`params.dig('repository','owner','login')`) is assumed to equal the owner encoded in `params.dig('repository','full_name')`, which is used by `OpenedHandler#repository` to resolve the Shipit repository/stack that gets mutated. Nothing in the code enforces this equality.

### Title
Webhook signature check authenticates by `repository.owner.login` while `OpenedHandler` resolves the target repository by `repository.full_name`, letting a no-secret-org payload provision a `ReviewStack` on any repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) using `params.dig('repository','owner','login')` [1](#0-0) , but `OpenedHandler#repository` resolves the actual Shipit `Repository`/`Stack` to mutate using the independent field `params.repository.full_name` [2](#0-1) . Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved organization's config has no `webhook_secret` [3](#0-2) , an attacker who owns/controls a Shipit-configured, no-secret organization can forge a `pull_request` payload whose `repository.owner.login` is their own no-secret org (so the signature check trivially passes) while `repository.full_name` points at a victim repository under a different, secret-protected org.

### Finding Description
The broken equality is: `repository_owner_used_for_auth == repository_owner_encoded_in_full_name_used_for_mutation`. Both values are read from the same attacker-supplied JSON body but are never cross-checked.

Path:
1. `WebhooksController#verify_signature` picks the org for authentication via `repository_owner` = `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) .
2. `GitHubApp#verify_webhook_signature` short-circuits `return true unless webhook_secret` [4](#0-3) . If the attacker's own org (e.g. `attacker-org`, which the attacker installed the Shipit GitHub App on themselves, or which is simply configured in Shipit's `secrets.yml` without a secret — the multi-org config format explicitly supports per-org configs, several of which may have no secret, per `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`) has no `webhook_secret`, the signature check passes unconditionally regardless of the actual HMAC header content.
3. `Shipit::Webhooks.for_event('pull_request')` dispatches to `OpenedHandler#process`, which resolves the target repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [2](#0-1) , a completely separate JSON field from the one used for authentication.
4. If `provision?` returns true for that repository's provisioning configuration (`review_stacks_enabled` + `allow_all`/label rules, itself attacker-influenced only insofar as they can add PR labels on the victim repo, but the check is on the *victim repo's stored config*, not attacker-controlled) [5](#0-4) , `ReviewStackAdapter#find_or_create!` either finds an existing `ReviewStack` (for pre-existing `pr#<number>` environments — a no-op, no mutation) or creates a brand-new one with attacker-controlled `branch: params.pull_request.head.ref` and `environment: "pr#{params.number}"`, then enqueues it for provisioning [6](#0-5) .

Existing guards fail because: (a) `verify_signature` never compares `repository.owner.login` against the owner embedded in `repository.full_name`; (b) `drop_unhandled_event` only checks event type, not payload consistency; (c) `ExplicitParameters` schema on `OpenedHandler` only validates types/presence, not cross-field consistency [7](#0-6) ; (d) `Repository.from_github_repo_name` performs a plain lookup with no ownership/tenant check tying it back to the authenticated organization [8](#0-7) .

Regarding the `ignore_ci: true` / `Commit#deployable?` amplification asserted in the question: for an *existing* `ReviewStack` matching `pr#<number>`, `find_or_create!` returns the existing stack and performs no further mutation (branch, PR association, and provisioning queue updates only occur inside `create!`) [9](#0-8) . For newly created stacks, `stack_attributes` hardcodes `ignore_ci: false` and `continuous_deployment: false` [10](#0-9) . So `Commit#deployable?`'s CI short-circuit (`stack.ignore_ci? || (success? && !blocked?)`) [11](#0-10)  is not actually reachable through `OpenedHandler` as an amplifier — no deploy/rollback is triggered by this handler at all; it only provisions infrastructure, it doesn't call `trigger_deploy`. The "ignore_ci true" amplification claimed in the question is not substantiated by this handler's code path.

### Impact Explanation
The core, substantiated impact is: a payload authenticated only against the attacker's own (no-secret) organization can cause `Shipit::Repository.from_github_repo_name` to resolve and write to (create a `ReviewStack`, `PullRequest` record, and enqueue a `ReviewStackProvisioningQueue` job for) a *different* repository that the attacker never authenticated against — i.e., "a payload for one repository mutating another's stack." This matches the Critical bucket's "a payload for one repository mutating another's stack, commit, task or team." It does not, however, directly cause an unauthorized deploy/rollback/merge via `OpenedHandler` alone, since new review stacks are provisioned with `ignore_ci: false` and `continuous_deployment: false`, and existing stacks are untouched by this handler. Blast radius: any Shipit-configured repository with `review_stacks_enabled` and `provisioning_behavior_allow_all` (or matching label rule) is affected, repeatable per PR number/environment collision, across tenants that share one Shipit instance.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured with the multi-org config schema, and at least one configured organization must have no `webhook_secret` (documented as a supported, valid configuration — several example config files in the repo ship with `webhook_secret: # nil`); (2) attacker needs to know/control that no-secret org's name to trigger `Shipit.github(organization: repository_owner)` to resolve to it; (3) attacker needs the victim repository's `full_name` (public GitHub info) and needs the victim repository to have review-stack auto-provisioning enabled. Attacker cost is a single unauthenticated HTTP POST to `/webhooks`; fully repeatable.

### Recommendation
In `WebhooksController#verify_signature`, and/or in each handler resolving the target repository (e.g. `OpenedHandler#repository`), enforce that the owner encoded in `repository.full_name` matches the authenticated `repository_owner` used to select the `GitHubApp`/secret. Reject the request (422) on mismatch. Additionally, consider disallowing/warning on any per-org config with a blank `webhook_secret` in production, since it disables signature verification entirely for that org's payloads.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure Shipit with two orgs: `no-secret-org` (webhook_secret nil) and `victim-org` (has a `webhook_secret`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Create a `Shipit::Repository` owned by `victim-org` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` for `victim-org`'s secret, and a JSON body where `repository.owner.login == "no-secret-org"` but `repository.full_name == "victim-org/target-repo"`, `action == "opened"`, PR `number` for a not-yet-existing environment.
4. Assert response is `:ok` (not `422`) — i.e., the forged signature was accepted.
5. Assert `Shipit::ReviewStack.find_by(environment: "pr#{number}")` was created under the `victim-org/target-repo` repository, with `branch == payload["pull_request"]["head"]["ref"]`, and `Shipit::ReviewStackProvisioningQueue` received the new stack — proving cross-tenant mutation without ever supplying `victim-org`'s `webhook_secret`.
6. Contrast assertion: verify both sides of the equality (`repository_owner` used for auth vs. owner parsed out of `repository.full_name`) differ (`"no-secret-org" != "victim-org"`) yet the mutation still occurred, proving the invariant is violated.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
