### Title
`StatusHandler#process` resolves commits by SHA with no repository scoping, letting a webhook authenticated for one repo write a `Status` on any other stack's matching commit - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the **entire** `commits` table and calls `commit.create_status_from_github!(params)` for every match, without ever checking that the commit's `stack`/`repository` corresponds to `payload['repository']['full_name']` — the repository whose webhook secret authenticated the request. Unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`), `StatusHandler` never calls the `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)`. Any commit sha that exists under more than one `Stack` (a routine occurrence for forks, shared vendor history, cherry-picks, or upstream commits synced into multiple downstream stacks) will receive a `Status` row for every one of those stacks, even stacks belonging to a completely different tenant/repository than the one that sent the webhook.

### Finding Description
The binding the question expects to hold is:

`stack_id passed into Status.replicate_from_github!` == `Repository.from_github_repo_name(payload['repository']['full_name']).stacks.map(&:id)` (i.e. the stack(s) of the repository that GitHub actually signed the webhook for).

Tracing the code:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only verifies that the payload was signed by `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from `payload['repository']['owner']['login']`. This proves the payload came from GitHub for *that* org/repo — it proves nothing about which `Commit`/`Stack` rows the handler will touch.
- `Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` (`app/models/shipit/webhooks.rb:19`).
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
  ```
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This is a **global, unscoped** query — it does not call `stacks` (defined in `Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-34`), which is the mechanism every other handler (`PushHandler`, `CheckSuiteHandler`) uses to restrict effects to `Repository.from_github_repo_name(repository_name)&.stacks`.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) calls `statuses.replicate_from_github!(stack_id, github_status)` using `commit.stack_id`, i.e. whatever stack that pre-existing `Commit` row belongs to — not the stack derived from the webhook's own repository.
- `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) then does `find_or_create_by!(stack_id:, state:, ...)`, persisting the row against that (possibly unrelated) `stack_id`.

Because the sha match is the only condition, any attacker who controls a repository (and can therefore legitimately trigger a correctly-signed `status` webhook for it, e.g. by setting a commit status via the GitHub API on their own repo) can inject a `Status` into a victim's stack, provided a `Commit` row with the same `sha` already exists under the victim's stack. This is realistic without any secret compromise: git commit SHAs are content-addressed, so forks, mirrors, cherry-picked commits, or shared upstream history routinely produce identical SHAs across repositories/stacks that Shipit tracks independently. `check_if_ping`, `drop_unhandled_event`, and `verify_signature` only validate that the *sender* is the claimed repository/org — none of them, nor `StatusHandler`'s param schema, constrain which `Commit`/`Stack` the handler mutates.

### Impact Explanation
A `Status` record is written against a stack the attacker never authenticated for, using attacker-controlled fields (`state`, `description`, `target_url`, `context`, `created_at`). Because `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` fire on creation, this can flip `ignore_ci` on the victim's stack and trigger `commit.schedule_continuous_delivery`, potentially unblocking or affecting deploy eligibility for the victim's commit based on a status the attacker forged for their own repo. This matches the Critical category "a payload for one repository mutating another repository's stack, commit, task or team." It is repeatable against any stack whose tracked commits share SHAs with a repository the attacker controls (forks are the common case), and it is not limited to a single victim — any stack with matching-sha commits is affected per request.

### Likelihood Explanation
Preconditions: (1) attacker owns/administers a GitHub repository already registered as (or sharing SHA history with) another Shipit-tracked stack, and (2) a `Commit` row with an identical `sha` already exists under the victim stack (naturally true for forks/mirrors of public repos, or shared vendored commits — no collision-forging needed, only shared git ancestry). Cost to the attacker is trivial: create/own a fork of the victim's public repo (or any repo with shared history), set a commit status via the GitHub API on a commit whose SHA also exists in the victim's Shipit-tracked stack, and GitHub delivers a correctly-signed `status` webhook. No Shipit secrets, sessions, or team membership are required. This is directly repeatable against every stack sharing that SHA.

### Recommendation
Scope `StatusHandler#process` to the requesting repository, mirroring `PushHandler`/`CheckSuiteHandler`: restrict the commit lookup to `stacks` (i.e. `Commit.where(sha: params.sha, stack: stacks)` or iterate `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`) so a `Status` can only be created for commits belonging to a stack of the repository that was cryptographically verified by `verify_signature`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status webhook for repo A writes a Status onto a completely different stack's commit sharing the same sha" do
  attacker_stack = shipit_stacks(:shipit)          # repository the attacker controls / whose webhook is validly signed
  victim_stack   = shipit_stacks(:cyclimse)        # unrelated tenant's stack

  shared_sha = "deadbeef" * 5

  # A commit with the SAME sha already exists under the victim's stack
  # (models a shared/forked upstream commit synced independently into both stacks)
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared history", ...)

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature validly matches attacker's own repo/org

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'attacker/ci',
    'repository' => { 'full_name' => attacker_stack.github_repo_name, 'owner' => { 'login' => attacker_stack.repository.owner } }
  }.to_json

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end

  status = victim_commit.statuses.last
  # Binding check: stack_id written equals victim's stack, NOT the webhook's authenticated repository/stack
  assert_equal victim_stack.id, status.stack_id
  refute_equal attacker_stack.id, status.stack_id
end
```
This demonstrates that a `status` webhook signed and authenticated only for the attacker's own repository results in a `Status` row created against `victim_stack.id`, violating the claimed binding.
