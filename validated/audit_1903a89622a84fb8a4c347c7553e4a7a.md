### Title
Unbounded recursion in address-authentifier verification via mutually-referencing address definitions - ([File: definition.js])

### Summary
`validateAuthentifiers()` in `definition.js` re-evaluates an address's spending conditions (including nested `['address', 'BASE32']` references to *other* stored addresses) every time a unit that spends from that address is validated. Unlike the sibling function `validateDefinition()`, which enforces a `MAX_COMPLEXITY` / `MAX_OPS` budget on every recursive `evaluate()` call, the `evaluate()` function inside `validateAuthentifiers()` has **no complexity, op-count, or depth limit at all**. A pair of addresses whose definitions reference each other (`A → ['address','B']`, `B → ['address','A']`) can be legally stored on the DAG because at *creation* time `validateDefinition()` silently allows unresolved forward references (`bAllowUnresolvedInnerDefinitions = true`), so the cycle is never actually walked when each address is originally defined. Once both addresses exist, any later unit spending from `A` (or `B`) triggers `validateAuthentifiers()`, whose `'address'` case unconditionally recurses into the referenced address's stored definition with no cycle/depth guard, causing infinite recursion.

### Finding Description
`validateDefinition()`'s `evaluate()` increments `complexity`/`count_ops` and aborts once `constants.MAX_COMPLEXITY` / `constants.MAX_OPS` is exceeded: [1](#0-0) 

However `validateAuthentifiers()` — the function actually invoked while validating signatures on every incoming unit — defines a separate `evaluate()` with **no such guard**: [2](#0-1) 

Its `'address'` case simply looks up the other address's stored definition and recurses into it unconditionally: [3](#0-2) 

At definition-creation time, `validateDefinition()`'s own `'address'` case allows a reference to an address whose definition does not exist yet (forward reference), effectively skipping full recursive evaluation of that branch: [4](#0-3) 

This means two addresses, `A` and `B`, can be created sequentially such that `A`'s definition is `['address','B']` and `B`'s definition is `['address','A']`, without either creation step ever recursively resolving the cycle (because at the time each is created, the other side is either not-yet-stored — short-circuited via `bAllowUnresolvedInnerDefinitions` — or, when `B` is being validated after `A` already exists, the `complexity` budget from `MAX_COMPLEXITY` still bounds only that single validation pass, not the eventual verification pass against a *different*, unrelated address).

Once both `A` and `B` are stable, permanent addresses on the DAG, any subsequent unit spending from `A` (posted by anyone — the address owner, but reachable simply by that unit existing and being validated by every node) causes `validateAuthentifiers()` to evaluate `A`'s definition, hit `['address','B']`, look up and evaluate `B`'s definition, hit `['address','A']`, look up and evaluate `A`'s definition again, and so on — with no depth counter, no complexity counter, and no cycle detection to stop it.

### Impact Explanation
Because every node runs `validateAuthentifiers()` when validating the unit's inputs, every full node that processes a unit spending from `A` (or `B`) enters this unbounded recursive/async loop. This is a availability-impacting denial-of-service directly analogous to CVE-2022-21302 ("hang or frequently repeatable crash" from a low-privileged, network-reachable actor): the validating node either hangs performing endless DB lookups/recursive `evaluate()` calls or exhausts memory/stack, and cannot finish validating (and therefore cannot include/stabilize) that unit. Repeating the attack (spending again from the poisoned address, or having other nodes attempt to validate the same unit) reproduces the hang deterministically, matching the CVSS vector's "repeatable crash" / availability-only impact and satisfying the required outcome of "a network unable to confirm new units."

### Likelihood Explanation
- Reachable by an ordinary, unprivileged unit poster: the attacker only needs to control the definitions of two addresses they created themselves (a normal wallet operation, no special privilege).
- The cyclic-definition setup exploits the documented `bAllowUnresolvedInnerDefinitions = true` short-circuit in `validateDefinition()`, so no validation error is raised when the cycle is created.
- The actual unbounded recursion only manifests in the unguarded `validateAuthentifiers()` path used during ordinary unit spend validation — a code path every node executes for every incoming unit, requiring no cooperation from any other party.
- Difficulty is comparable to the referenced CVE ("difficult to exploit… AC:H") because it requires deliberately engineering the forward-reference address cycle first, but once set up, triggering the hang is trivial (one ordinary payment).

### Recommendation
Add the same complexity/op-count (and/or explicit visited-address-set cycle detection) guard used in `validateDefinition()`'s `evaluate()` to `validateAuthentifiers()`'s `evaluate()`, so recursive `'address'` lookups are bounded and self-referential/cyclic address chains cannot cause unbounded recursion during authentifier verification. Additionally, consider re-validating (or rejecting) address definitions whose resolved nested references would form a cycle, closing the gap created by `bAllowUnresolvedInnerDefinitions`.

### Proof of Concept
1. Attacker creates address `B` with a definition that references not-yet-existing address `A`: `['address', 'A']`. Since `A` isn't stored yet, `validateDefinition()`'s `'address'` branch takes the `ifDefinitionNotFound` path; because `A` is not an author of this unit, `arrDefiningAuthors.length === 0` and the check short-circuits to `cb(null, true)` — no recursion, no error.
2. Attacker then creates address `A` with definition `['address', 'B']`. Now `B` exists in storage, so `validateDefinition()` resolves and evaluates `B`'s definition (`['address','A']`); at this point `A` is one of the authors of the current unit with a matching definition hash, so `arrDefiningAuthors` matches and the branch calls `evaluate` again on `A`'s own (in-progress) definition — but this is bounded by the `complexity`/`MAX_OPS` counters in `validateDefinition()`'s `evaluate()`, so creation still completes (with an error or bounded success) without hanging.
3. Once both `A` and `B` are stable addresses with mutually-referencing stored definitions, attacker posts an ordinary payment unit spending from address `A`.
4. Every validating node calls `validateAuthentifiers()` for that unit; its `'address'` case resolves `B`'s stored definition, evaluates it, hits `['address','A']`, resolves `A`'s stored definition, evaluates it, hits `['address','B']`, and repeats indefinitely — with no depth/complexity guard to stop it, hanging or crashing the validating process.
