## Finding: CCMenuController bypasses per-token stack scoping

The vulnerability is real, but it is not the `join('--')` reconstruction itself — `ApiClient.authenticate` relies on `SimpleMessageVerifier` (HMAC-signed), so an attacker cannot forge or widen a token by manipulating how Basic-Auth parts are joined [1](#0-0) [2](#0-1) . The real break is in `Shipit::Api::CCMenuController`, which overrides the base `stack` accessor with an **unscoped** lookup.

`BaseController` scopes stacks by the authenticated client's `stack_id` when it is set: [3](#0-2) 

But `CCMenuController` redefines `stack` to bypass this entirely: [4](#0-3) 

The `require_permission :read, :stack` before-action only checks that the client's `permissions` array contains `"read:stack"` — it never checks that the requested `stack_id` matches `current_api_client.stack_id`: [5](#0-4) [6](#0-5) 

`CCMenuUrlController` issues exactly this kind of scoped-looking (but not actually stack-restricted) token via `client.authentication_token`, backed by an `ApiClient` created with only `permissions: %w[read:stack]` and no `stack_id` set: [7](#0-6) 

So the equality the design assumes — "the requested `stack_id` ∈ stacks authorized by `current_api_client.stack_id`" — holds in `BaseController#stack`/`#stacks`, but is violated specifically in `CCMenuController#stack`, which ignores `current_api_client.stack_id` and does `Stack.from_param!(params[:stack_id])` against any stack in the database. Any `ApiClient` token carrying `read:stack` (regardless of which stack it was minted for) can be replayed with a different `?token=...&stack_id=<other-stack>` to read that other stack's CI/CD status (latest deploy/rollback state) via `GET /api/stacks/:stack_id/ccmenu`.

This matches the High-severity category "unauthenticated/unauthorized read of stack state" — it's a cross-tenant leak (stack A's token reads stack B's deploy status) rather than a full authentication bypass, since it still requires a valid signed token with `read:stack` permission.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped lookup, e.g. delegate to `stacks.from_param!(params[:stack_id])` (the same scoping used in `BaseController`) instead of calling `Stack.from_param!` directly.

### Proof of Concept (minitest sketch)
```ruby
stack_a = shipit_stacks(:shipit)
stack_b = shipit_stacks(:cyclimse) # any other stack
client = ApiClient.create!(creator: shipit_users(:walrus), name: 'scoped', stack: stack_a, permissions: %w[read:stack])

get "/api/stacks/#{stack_b.to_param}/ccmenu", params: { token: client.authentication_token }
assert_response :not_found # expected if properly scoped; currently responds :success, leaking stack_b's status
``` [8](#0-7)
