### Title
Permissionless supply top-up bypasses the health-factor gate and forces adverse liquidation-parameter restamping - (contracts/controller/src/positions/supply.rs)

### Summary

A third party can add to an existing collateral position and force the controller to restamp its full liquidation-risk tuple, even when `update_account_threshold` would reject the refresh because the account’s post-update health factor is below `1.05`. The attacker can then immediately liquidate the newly undercollateralized account. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

`supply` permits a non-owner to top up an existing supply leg: `require_third_party_existing_supply` only verifies that every supplied `HubAssetKey` already exists in `account.supply_positions`. [1](#0-0) 

After pool settlement, `merge_supply_leg` loads the current listing configuration and calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, which refreshes the liquidation threshold together with the bonus and fee parameters. [4](#0-3) 

Unlike the permissionless threshold-refresh endpoint, which explicitly requires a post-refresh health factor of at least `1.05`, `process_supply` performs no post-deposit solvency or minimum-health-factor check before persisting the position. [3](#0-2) [5](#0-4) 

Consequently, a dust-sized top-up can apply a lowered liquidation threshold to another user’s account in a state that the dedicated refresh path deliberately refuses to create. [6](#0-5) [3](#0-2) 

### Impact Explanation

After a governance risk-parameter reduction, an attacker can force a victim’s stored liquidation threshold down to the current configuration, making the position liquidatable even though its previous stamped threshold kept it healthy. [2](#0-1) 

The attacker can then call the permissionless `liquidate` endpoint and seize the victim’s collateral with the applicable liquidation bonus, causing an involuntary collateral loss. [7](#0-6) 

This bypasses the safety boundary encoded in `update_account_threshold`, which requires refreshed liquidation parameters to leave the account at or above `1.05` health factor. [3](#0-2) 

### Likelihood Explanation

The attacker needs only an existing collateral leg in the victim’s account, a small amount of that listed asset, and authorization for their own address. [1](#0-0) [8](#0-7) 

The attack becomes actionable whenever a listed collateral’s liquidation threshold is reduced and a borrower is healthy under its stored threshold but below the protected refresh floor under the new threshold. [3](#0-2) [2](#0-1) 

Because third-party top-ups are intentionally permissionless, no victim signature, delegate grant, pool privilege, or leaked key is required. [9](#0-8) 

### Recommendation

Apply the same post-refresh health-factor guard to third-party supply top-ups that `update_account_threshold` applies when restamping liquidation parameters. [3](#0-2) 

If allowing a top-up to improve collateral while retaining old liquidation parameters is desired, use a narrower refresh scope for third-party deposits or preserve the threshold, bonus, and fee tuple whenever the resulting health factor would be below `1.05`. [2](#0-1) 

Alternatively, require owner or delegate authorization before any supply action can write a `FullTuple` risk refresh to an existing account. [10](#0-9) 

### Proof of Concept

1. Alice supplies USDC and borrows ETH, leaving her account healthy under the stored USDC liquidation threshold. [11](#0-10) [12](#0-11) 
2. Governance lowers USDC’s liquidation threshold. Under the new threshold, Alice’s health factor is below `1.05`, so the protected threshold-refresh path cannot push her into that state. [3](#0-2) 
3. An attacker calls `supply(attacker, alice_account_id, alice_spoke_id, [(usdc_hub_asset, dust_amount)])`. Because Alice already has a USDC supply leg, the non-owner check accepts the top-up. [1](#0-0) 
4. `merge_supply_leg` applies `RiskRefreshScope::FullTuple`, replacing Alice’s stored liquidation threshold with the reduced listing value. [2](#0-1) 
5. `process_supply` persists that refreshed position without running `enforce_post_pool_solvency`. [13](#0-12) [14](#0-13) 
6. The attacker calls `liquidate(attacker, alice_account_id, debt_payments, SeizeMode::Transfer)` and receives collateral plus the liquidation bonus. [7](#0-6)

```rust
/// Supplies collateral, creating an account when `account_id` is zero.
/// Third parties may only add to existing supply positions. Returns the account id.
pub(crate) fn process_supply(
    env: &Env,
    caller: &Address,
    account_id: u64,
    spoke_id: u32,
    assets: &Vec<HubPayment>,
) -> u64 {
    validation::require_authorized_caller(env, caller);
    let aggregated = payments::aggregate_positive_payments(env, assets);
    let mut cache = Context::new(env);

    let (acct_id, mut account) = account::load_or_create_account(
        env,
        caller,
        account_id,
        spoke_id,
        PositionMode::Normal,
        account::AccountGuard::Supply,
        &mut cache,
    );

    require_third_party_existing_supply(env, account_id, acct_id, caller, &account, &aggregated);

    process_deposit(env, caller, &mut account, &aggregated, &mut cache);

    finalize_position_flow(
        env,
        acct_id,
        &account,
        &mut cache,
        PositionSides::Supply,
        false,
    );
```

```rust
/// Restricts third parties to existing supply positions. New accounts are
/// exempt because the caller becomes their owner.
fn require_third_party_existing_supply(
    env: &Env,
    account_id: u64,
    resolved_account_id: u64,
    caller: &Address,
    account: &Account,
    aggregated: &AggregatedPayments,
) {
    if account_id != 0
        && !account::is_owner_or_delegate(env, resolved_account_id, caller, &account.owner)
    {
        for (hub_asset, _) in aggregated.iter() {
            assert_with_error!(
                env,
                account.supply_positions.contains_key(hub_asset.clone()),
                GenericError::NotAuthorized
            );
        }
    }
}
```
