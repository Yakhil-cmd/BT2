### Title
Cross-tenant commit-status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized PR merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by matching `sha` across the entire `commits` table, with no check that the webhook's `repository`/organization actually owns that commit. `WebhooksController#verify_signature` only proves the payload was legitimately signed by the org named in the payload — it says nothing about whether that org may write a status onto a commit belonging to a different stack/org. An attacker who controls a repository whose sha object graph happens to contain the victim's exact PR head commit (e.g. via a synced fork) can therefore inject a `success` status for the victim's required context and trigger an unauthorized `stack.github_api.merge_pull_request` call for the victim's repository.

### Finding Description
The broken binding, stated explicitly:

`org(webhook_secret used to verify signature)` should equal `org(repository/stack that owns the Commit row being mutated)` — but the code never enforces this.

Path:
1. `WebhooksController#verify_signature` computes `Shipit.github(organization: repository_owner)` from the payload's `repository.owner.login` (attacker's org) and calls `github_app.verify_webhook_signature(...)`. This only validates that the request was really sent by GitHub for **attacker's own** org/app installation — a correct and unforgeable check, but scoped only to "who signed this," not "which commit may be touched." [1](#0-0) 
2. `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a global lookup across **all** stacks/repositories in the Shipit instance, keyed solely on `sha`. There is no `stack_id`, `repository`, or org filter tying the payload's repository to the commit being updated. [2](#0-1) 
3. `Commit#create_status_from_github!` writes the status using the **victim commit's own** `stack_id` (`statuses.replicate_from_github!(stack_id, github_status)`), so the forged status is attributed to and evaluated against the victim's stack, not the attacker's. [3](#0-2) 
4. `Commit#add_status` calls `stack.schedule_merges` whenever the resulting status becomes `pending` or `success`, which enqueues `ProcessMergeRequestsJob` for the **victim's** stack. [4](#0-3) 
5. `ProcessMergeRequestsJob#perform` iterates `stack.merge_requests.to_be_merged`, and for each pending PR calls `merge_request.all_status_checks_passed?`, which now evaluates true because the forged status satisfies the required context. [5](#0-4) [6](#0-5) 
6. `merge_request.merge!` then calls `stack.github_api.merge_pull_request(...)` — the **victim's** stack's GitHub API client — merging the victim's PR. [7](#0-6) 

Root cause: `Commit.where(sha:)` in the handler has no notion of "repository ownership" — any Commit row anywhere with a matching sha is mutated, regardless of which org's webhook_secret validated the request. `verify_signature`, `drop_unhandled_event`, and the `ExplicitParameters` schema in `StatusHandler.params` all check payload shape/signature validity but never check that the org owning the signed payload matches the org that owns the target `Commit`/`Stack`. This is exactly the divergence the question describes: the org bound by the signature check and the org whose PR gets merged are not required to be the same.

Feasibility caveat: the sha match is not attacker-arbitrary — the attacker needs a `Commit` row in Shipit's DB with a sha identical to the victim's PR head commit, and needs to be able to legitimately push a status for that sha from a repository they control (so the signature check succeeds for their own org). This is achievable in realistic setups: forks share git object history with upstream, and syncing a fork can bring in the exact same commit object (identical sha) as the victim's PR head, especially when PRs are opened against a shared default branch or the fork is synced after the PR branch was pushed to a shared remote. GitHub's Statuses API accepts any sha string for a repo without requiring it be the tip of a branch. No Shipit secret, session, or privileged role is required — only the ability to run a GitHub webhook-emitting action against a repository the attacker owns.

### Impact Explanation
An attacker with no relationship to the victim's Shipit instance beyond controlling their own GitHub repository can cause an **unauthorized merge of a victim-org pull request**, because the forged status is written onto the victim's `Commit`/`Stack` record and directly drives `stack.github_api.merge_pull_request` for that repository. This is a cross-tenant data write: a payload authenticated for one org (attacker) mutates state (`Status`) belonging to another org's stack, and that mutation has a direct authorization consequence (bypassing the required-status gate that `all_status_checks_passed?` is meant to enforce). This matches the "Critical" category: a payload for one repository mutating another's stack/commit, and an unauthorized merge. The blast radius is any Shipit tenant/stack sharing the same Shipit instance and GitHub App/webhook_secret configuration whose PR head commit sha the attacker can reproduce in a repo they control.

### Likelihood Explanation
Preconditions: the victim must have an open, pending `MergeRequest` (`merge_status == 'pending'`) with `stack.allows_merges?` true, and the attacker needs a repository under their control whose git object store contains the exact same commit object (same sha) as the victim's PR head — realistic via fork syncing when branches share ancestry, but not guaranteed for arbitrary victim commits with no shared history. The attacker also needs to know the exact required status `context` string, which is typically visible from the target repo's branch-protection/CI configuration or by observing prior statuses on public commits. No Shipit credentials, sessions, or GitHub App secrets are needed — only ordinary GitHub actions (forking, syncing, and calling the Statuses API on their own repo, which triggers a legitimately-signed webhook to Shipit). This is repeatable against any stack/PR in the same Shipit instance whose head commit sha the attacker can reproduce.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository named in the webhook payload, not just the sha. Concretely, resolve `params.repository` to the specific `Stack`(s) matching that `repo_owner`/`repo_name`, and only update `Commit` rows belonging to those stacks (e.g. `Commit.joins(:stack).where(sha: params.sha, stack: { repo_owner: ..., repo_name: ... })`), mirroring the repository-binding checks used elsewhere (e.g. `PullRequestHandler`) so that a status webhook can only ever mutate commits that belong to the repository whose org actually signed it.

### Proof of Concept
Minitest plan (no live GitHub, Mocha stubs only):

```ruby
test "a status webhook signed by attacker's org can merge a PR belonging to a different stack" do
  victim_stack = shipit_stacks(:shipit)
  attacker_org_login = "attacker-org"

  # Victim has a pending PR whose head commit lacks the required status
  merge_request = victim_stack.merge_requests.create!(
    number: 42, state: "open", merge_status: "pending",
    merge_requested_at: Time.now.utc, revalidated_at: Time.now.utc
  )
  head_commit = victim_stack.commits.create!(sha: "a" * 40, message: "PR head")
  merge_request.update!(head: head_commit)

  deploy_spec = stub(merge_request_required_statuses: ["ci/required"], merge_request_ignored_statuses: [])
  victim_stack.stubs(:cached_deploy_spec).returns(deploy_spec)
  victim_stack.stubs(:allows_merges?).returns(true)

  # Precondition: check fails before forged webhook
  assert_equal false, merge_request.reload.all_status_checks_passed?

  # Attacker sends a status webhook whose `repository` belongs to attacker's org,
  # signed with attacker's own webhook_secret, but sha == victim's head commit sha
  payload = {
    "sha" => head_commit.sha,
    "state" => "success",
    "context" => "ci/required",
    "repository" => { "owner" => { "login" => attacker_org_login }, "name" => "attacker-repo" }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)

  # Binding check: the org that signed the webhook (attacker) != the org owning
  # the mutated Commit/Stack (victim). Assert the status was nonetheless applied
  # to the victim's commit and drives an unauthorized merge.
  assert_equal true, merge_request.reload.all_status_checks_passed?

  victim_stack.github_api.expects(:merge_pull_request).with(
    victim_stack.github_repo_name, merge_request.number, anything,
    sha: head_commit.sha, commit_message: "Merged by Shipit", merge_method: victim_stack.merge_method
  )
  victim_stack.github_api.stubs(:pull_requests).returns([])

  Shipit::ProcessMergeRequestsJob.new.perform(victim_stack)
end
```
This demonstrates that `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup lets a webhook legitimately signed for one org mutate a `Commit`/`Status` belonging to a different org's stack, and that this directly satisfies `MergeRequest#all_status_checks_passed?`, causing `ProcessMergeRequestsJob#perform` to call `stack.github_api.merge_pull_request` for the victim's repository.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end

        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict

      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.

    end
