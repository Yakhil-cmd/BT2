### Title
Architecture-Dependent Subgroup Check Omission in `bn256` Pairing Precompile Causes State-Root Divergence — (`crypto/bn256/bn256_fast.go` / `crypto/bn256/bn256_slow.go`)

### Summary

The `runBn256Pairing` precompile (0x08) is backed by two different implementations selected at compile time by build tag. On `amd64`/`arm64` the gnark library is used; on all other architectures the cloudflare library is used. The gnark `Unmarshal` methods for both G1 and G2 enforce a prime-order subgroup check (`IsInSubGroup()`), while the cloudflare `Unmarshal` methods enforce only an on-curve check (`IsOnCurve()`). A crafted G2 point that lies on the BN254 curve but outside the prime-order subgroup is therefore accepted by cloudflare nodes and rejected (precompile reverts) by gnark nodes, producing different EVM execution outcomes for the same transaction and causing a state-root divergence.

**Precompile execution path:**

`runBn256Pairing` calls `newTwistPoint` → `p.Unmarshal`. If `Unmarshal` returns an error the precompile returns `(nil, err)`, which causes the EVM `CALL` to revert (return 0). If `Unmarshal` succeeds, `bn256.PairingCheck` runs and returns `true32Byte` or `false32Byte`. [7](#0-6) 

**Exploitable divergence:**

BN254 G2 has a non-trivial cofactor `h`. A point `B` on the G2 curve that is not in the prime-order subgroup (i.e., `[r]B ≠ O`) is accepted by cloudflare (only `IsOnCurve()` checked) and rejected by gnark (`IsInSubGroup()` fails → error). The cloudflare `PairingCheck` then computes the Ate pairing via Miller loop + final exponentiation, which always maps to the `r`-th roots of unity in GT regardless of whether the input is in the prime-order subgroup: [8](#0-7) 

An attacker can construct a pair `(A, B)` where `B = B_r + T`, `B_r ∈ G2[r]`, `T` is a cofactor torsion point, such that `e(A, B_r) · e(A, T) = 1` in GT. The cloudflare implementation computes this product and returns `true32Byte`. The gnark implementation rejects `B` at `Unmarshal` time and reverts.

### Impact Explanation

A ZK-verifier smart contract (e.g., a Groth16 verifier) that gates a KAIA transfer on the result of precompile 0x08 will execute differently on different node architectures:

- **gnark nodes (amd64/arm64):** precompile reverts → `CALL` returns 0 → verifier's conditional branch is not taken → KAIA is not transferred → storage slot `verified` stays `false`.
- **cloudflare nodes (other arch):** precompile returns `true32Byte` → `CALL` returns 1 with result `true` → verifier's conditional branch is taken → KAIA is transferred → storage slot `verified` is set to `true`.

Both node sets process the same transaction from the same block. Their resulting state roots diverge. Honest nodes on different architectures disagree on the canonical chain, causing a chain split. The corrupted storage slot and unauthorized KAIA transfer are durable.

### Likelihood Explanation

The attack is fully permissionless: any account can deploy a Groth16-style verifier contract and submit a transaction with a crafted pairing input. Constructing a non-subgroup G2 point on BN254 is straightforward (take any curve point and verify `[r]P ≠ O`). Finding `(A, B_r, T)` such that `e(A, B_r) · e(A, T) = 1` requires offline pairing computation but no privileged access. The vulnerability is triggered by a single on-chain transaction. Kaia's validator set is heterogeneous in architecture (amd64 and non-amd64 nodes coexist), making the divergence reachable in production.

### Recommendation

Apply the prime-order subgroup check in the cloudflare `G1.Unmarshal` and `G2.Unmarshal` methods, mirroring the gnark implementation. Add `IsInSubGroup()` calls after `IsOnCurve()` in both cloudflare unmarshal paths. Alternatively, unify both paths to use a single implementation (gnark is already the preferred fast path) and remove the architecture split for correctness-critical precompile logic. Add a cross-architecture fuzz test that asserts identical outputs from both implementations for all valid and invalid inputs.

### Proof of Concept

1. Deploy a Groth16 verifier contract that calls precompile 0x08 and transfers KAIA if the result is `true`.
2. Offline: pick any `B_r ∈ G2[r]` and any cofactor torsion point `T` (on the G2 curve, `[r]T ≠ O`). Compute `c = e(A, T)` using the cloudflare pairing. Find `B_r` such that `e(A, B_r) = c⁻¹`. Set `B = B_r + T` (a valid curve point, not in the prime-order subgroup).
3. Submit a transaction calling the verifier with pairing input `(A, B)`.
4. On cloudflare nodes: `G2.Unmarshal(B)` succeeds → `PairingCheck` returns `true` → KAIA transferred → `verified = true`.
5. On gnark nodes: `G2.Unmarshal(B)` calls `IsInSubGroup()` → returns error → precompile reverts → KAIA not transferred → `verified = false`.
6. Assert state roots differ across the two node sets — chain split confirmed.

func PairingCheck(a []*G1, b []*G2) bool {
	acc := new(gfP12)
	acc.SetOne()

	for i := range a {
		if a[i].p.IsInfinity() || b[i].p.IsInfinity() {
			continue
		}
		acc.Mul(acc, miller(b[i].p, a[i].p))
	}
	return finalExponentiation(acc).IsOne()
}
