### Title
Webhook organization used for signature verification is attacker-controlled and decoupled from the repository/team the payload mutates, allowing signature bypass and forged team-membership grants - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) to validate a webhook against using a field taken directly from the *unauthenticated* request body (`repository.owner.login` or `organization.login`). `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected organization has no `webhook_secret` configured. Because Shipit supports multi-organization GitHub configuration (some orgs configured with a secret, others intentionally left blank, e.g. in dev/staging), an attacker can pick an organization name that maps to a blank `webhook_secret` for the *authentication* check, while filling the same payload with `team`/`member`/`repository` data belonging to a *different*, secured organization/repo whose Stack or team membership they want to manipulate. This breaks the binding "organization that authenticated == repository/team the payload mutates."

### Finding Description
`verify_signature` resolves the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the JSON body the attacker submits (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), before any authentication has occurred. That value is used to select the `GitHubApp` instance: [3](#0-2) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the resolved organization's `webhook_secret` is blank: [4](#0-3) 

Multi-org configuration explicitly allows some orgs to have `webhook_secret: # nil` while others do not, as shown in the documented/example configs: [5](#0-4) [6](#0-5) 

Once `verify_signature` passes (trivially, because the attacker chose an org with a blank secret), the *entire, unverified* JSON body is dispatched to event handlers with no re-check that the claimed organization matches the resources actually referenced in the payload: [7](#0-6) 

The `membership` handler in particular grants/revokes `Shipit::Team`/`Shipit::Membership` records purely from the `team`/`member`/`action` payload fields, with no re-validation that these are scoped to the organization used for the (already-bypassed) signature check: [8](#0-7) [9](#0-8) 

This is the same bug class as the reported SwiftSource issue: a value (`webhook_secret`/native-ETH payment channel) is used for an accounting/authorization decision, but the entity that decision is scoped to (`organization` for signing / `msg.value` accounting) is not bound to the entity actually acted upon (`repository`/`team` mutated / recipient credited). Here the equality that should hold is:
`organization whose secret authenticated the request == organization/repository/team that the payload subsequently mutates`
and it does not, because the org used for authentication is attacker-supplied and independently chosen from the org/team/repo the handler acts on.

### Impact Explanation
An unauthenticated, unprivileged network attacker who can reach `POST /webhooks` (a public, non-session, non-API-token endpoint by design) can:
- Bypass HMAC signature verification entirely by claiming an organization configured with a blank `webhook_secret` (a state that is explicitly supported/documented and common in non-production or partially configured multi-org deployments).
- Send fully forged `membership` events that create or delete `Shipit::Team`/`Shipit::Membership` records for arbitrary GitHub teams/logins, directly escalating into `Shipit.github_teams` authorization (used to gate OAuth login access), which is explicitly listed as a High-severity impact for this program.
- Send forged `push`/`status`/`check_suite` events referencing repositories under a different, secured organization to manipulate CI/deployability state or trigger sync jobs, since the handler layer trusts the payload's own `repository.full_name` independent of which org's secret was used to "authenticate" it.

### Likelihood Explanation
The webhook endpoint requires no authentication, session, or token by design (`skip_before_action :verify_authenticity_token`). The only gate is `verify_signature`, whose organization-selection logic is fully attacker-controlled via ordinary JSON body fields. Any Shipit deployment that configures more than one GitHub organization — a supported, documented configuration — with at least one organization lacking a `webhook_secret` is exploitable without any credentials.

### Recommendation
- Never allow the signature-selection organization to be derived from unauthenticated request content that is also the data being acted upon. Alternatively, require `X-Hub-Signature` verification to always fail (never default to `true`) for any organization in the multi-org list, mandating a `webhook_secret` for every configured org.
- After selecting the organization/app used to verify, cryptographically bind the verified org to the resource being mutated (e.g., re-derive the owning organization for `repository`/`team`/`member` strictly from Shipit's own stored `Stack`/`Team` records, not from attacker-supplied payload fields) before handlers execute.
- Reject webhook payloads whose claimed `repository.owner.login`/`organization.login` do not match the organization actually configured for the target Stack/Team being modified.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `SecureOrg` (has `webhook_secret` set) owning the real Stack the attacker wants to influence, and `OpenOrg` (per documented example configs, `webhook_secret:` left blank).
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "organization": { "login": "OpenOrg" },
  "action": "added",
  "team": { "id": 1, "name": "shipit-admins", "slug": "shipit-admins", "url": "https://example.com" },
  "member": { "login": "attacker-controlled-login" }
}
```
No valid `X-Hub-Signature` header is required — `verify_webhook_signature` returns `true` because `OpenOrg`'s `webhook_secret` is blank, per: [10](#0-9)  — while the actual mutation (team/membership creation) is unscoped to `OpenOrg`, letting the attacker grant themselves membership in a team such as one listed in `Shipit.github_teams`, as demonstrated by the equivalent test flow: [11](#0-10) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
