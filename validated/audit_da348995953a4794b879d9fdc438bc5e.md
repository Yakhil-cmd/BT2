### Title
Membership webhook trusts attacker-supplied GitHub team ID, enabling cross-organization escalation into `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler` binds a webhook's `team.id` to an existing local `Team` record purely by numeric `github_id`, without verifying that the `organization.login` in the same payload actually owns that team. Combined with `WebhooksController`'s signature check, which is a no-op whenever a Shipit deployment's GitHub App is configured without a `webhook_secret` (an explicitly documented/optional setting), an unauthenticated actor can add an arbitrary GitHub login to any `Team` record already used by `Shipit.github_teams`, bypassing the GitHub-team-membership gate that `Authentication#force_github_authentication` enforces.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App config to check against using an attacker-influenced field of the unsigned request body itself: [1](#0-0) [2](#0-1) 

The actual verification, however, is a no-op if that app has no `webhook_secret` configured — a state explicitly presented as optional in the setup docs: [3](#0-2) [4](#0-3) 

When the `membership` event is processed, `MembershipHandler` finds-or-creates a `Team` keyed only on the numeric `github_id` supplied in the payload, and separately trusts `organization.login` from the same payload to populate `team.organization`, but never checks that the two are consistent for an *existing* team: [5](#0-4) 

`Team#add_member` then unconditionally appends the attacker-chosen member to that team: [6](#0-5) 

Authorization to use the whole Shipit UI is gated purely on local `Team` membership rows, resolved against `Shipit.github_teams` (the `oauth.teams` configuration list), with no live re-check against GitHub: [7](#0-6) [8](#0-7) 

**Binding broken:** *the organization that "authenticates" the webhook (via app-selection/signature check) ≠ the team/organization actually written and later trusted for authorization.* Because team lookup is keyed solely by a caller-supplied `github_id` integer with no ownership check tying it back to `organization.login`, and because signature verification can be entirely absent for any app lacking a `webhook_secret`, a `membership` payload can target a `Team` row that belongs to a completely different (or the target's own) organization than the one nominally "verified", as long as the numeric team ID matches.

### Impact Explanation
If exploited, an unauthenticated caller can insert a `Membership` row linking an arbitrary GitHub login to a `Team` that is part of `Shipit.github_teams`. Any user later authenticating via the normal GitHub OAuth flow with that login is then treated as `authorized?` and gains full application access (viewing stacks, triggering deploys/rollbacks/tasks, managing API clients), even though they were never actually a member of the privileged GitHub team. This matches the explicitly listed High-severity category: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Exploitability is conditioned on the deployment operating a GitHub App without a configured `webhook_secret`, which the project's own setup documentation presents as optional — a realistic and unremarkable production configuration, not a deviation from documented mounting/setup. The attacker additionally needs the numeric GitHub `team.id` of a privileged team, which is discoverable (e.g. via the public/organization GitHub API, or simply by being a non-privileged member of the same GitHub organization who can enumerate team IDs). No Shipit session, `ApiClient` token, or `webhook_secret` knowledge is required to reach this endpoint.

### Recommendation
- Scope `Team.find_or_create_by!` lookups to `(github_id, organization)` rather than `github_id` alone, and reject/ignore `membership` events whose `organization.login` does not match the `organization` already recorded on an existing team.
- Require a `webhook_secret` to be configured before accepting any mutating webhook events (or at minimum before processing `membership` events, which directly influence authorization), rather than silently treating an absent secret as "verified."
- Consider re-validating team membership against the live GitHub API before granting `authorized?`, instead of relying solely on locally cached `Membership` rows populated from webhook events.

### Proof of Concept
Preconditions: target Shipit deployment's GitHub App has no `webhook_secret` configured (documented-optional setting), and `Shipit.github_teams` includes a team, e.g. `shipit_teams(:shopify_developers)`, whose real GitHub numeric team id the attacker has discovered.

```
POST /webhooks HTTP/1.1
Host: shipit.example.com
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {
    "id": <known_github_id_of_shopify_developers_team>,
    "name": "Developers",
    "slug": "developers",
    "url": "https://example.com"
  },
  "organization": { "login": "shopify" },
  "member": { "login": "attacker-github-login" }
}
```

Because no `X-Hub-Signature` needs to be valid (or even present) when `webhook_secret` is unset, this request is processed by `MembershipHandler#process`, matches the existing `Team` row by `github_id`, and calls `team.add_member(User.find_or_create_by_login!('attacker-github-login'))`. The attacker's GitHub account, upon subsequently logging in through the normal `/github/auth/github` OAuth flow, is now `authorized?` per `Shipit.github_teams`, despite never having been added to that team on GitHub itself.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|

            team.organization = params.organization.login
          end
        end
