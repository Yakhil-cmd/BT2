### Title
Webhook signature verification selects the signing organization from the unverified JSON body, letting an attacker forge events for a *different*, protected repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to validate an inbound webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the **unauthenticated** JSON body, before any signature has been checked. Every downstream handler that mutates state (creating commits, statuses, teams, enqueuing deploy-sync jobs, etc.) instead resolves its target `Stack`/`Repository`/`Commit` using other fields of that same attacker-controlled body (`repository.full_name`, `sha`, etc.). Because a single endpoint serves every configured GitHub organization, an attacker can pick the "authenticating organization" independently from the "repository that gets written," breaking the equality the app implicitly assumes: `org used to verify signature == org owning the repository actually mutated`.

`Shipit.github(organization: repository_owner)` returns a `GithubApp`/`GithubOrganizationHook` configured per-org (each org can have its own `webhook_secret`, `oauth`, etc. as shown in `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`'s "Using Multiple Github Applications" section). Signature verification itself is: [3](#0-2) 

Critically, `verify_webhook_signature` **unconditionally returns `true` when `webhook_secret` is blank** (line 77). Leaving `webhook_secret` empty is the documented default in every example config (`config/secrets.development.example.yml`, `template.rb`, `docs/setup.md`), so it is realistic for at least one configured organization in a multi-org Shipit install to have no secret set (e.g., a low-value or sandbox org added for testing).

The handler code that actually performs the write (creating `Status` records, enqueuing `GithubSyncJob`, creating `Team`/`Membership`/`User` records, etc., as exercised in `test/controllers/webhooks_controller_test.rb`) resolves its target strictly from body fields such as `repository.full_name` and `sha`, with no re-check that these belong to the same organization that was used to select/pass the signature check.

Because the JSON body is entirely attacker-supplied (it's the thing being "verified"), an attacker can send a POST to the shared `/github/webhooks` endpoint with:
- `repository.owner.login` = an org configured **without** a `webhook_secret` (verification auto-passes, `head(422)` never triggers),
- `repository.full_name` / `sha` = pointing at a Stack/commit that actually belongs to a **different, protected** organization that does have a real `webhook_secret`.

`verify_signature` will select the unprotected org's (secret-less) `GithubApp`, get `verified = true`, and let the request through to the handler, which will happily act on the spoofed `repository`/`sha` belonging to the protected org.

### Impact Explanation
This breaks the binding "organization that authenticated vs. repository that is written." Concretely:
- The `status` webhook handler creates a `Status` for an arbitrary commit sha on an arbitrary tracked stack purely from unauthenticated JSON (confirmed by test `":state create a Status for the specific commit"` at [4](#0-3) ). If a stack's `ci.require` gating and continuous-deployment are driven by GitHub status checks, an attacker who cannot pass real CI can forge a `success` status for a malicious commit on a protected repo/org and let Shipit auto-deploy it — an **unauthorized deploy**, matching the Critical impact bucket.
- The `push` handler enqueues `GithubSyncJob` for the spoofed `repository.full_name`/`sha` ( [5](#0-4) ), letting an attacker inject or accelerate sync of arbitrary commit references into a stack it does not control, without ever touching that org's real webhook secret.

### Likelihood Explanation
Requires: (1) a Shipit instance configured for multiple GitHub organizations (documented, supported feature — `test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`), and (2) at least one of those organizations left with a blank `webhook_secret` (the shipped default in every example/template config). No GitHub App private key, `ApiClient` token, or repository write access is needed — only the ability to send an HTTP POST to the shipit-engine host, satisfying the "unprivileged attacker" constraint.

### Recommendation
Never let the payload determine which secret is used to authenticate itself. Instead, verify the signature against **every** configured organization's secret (or a single global secret, or route webhooks per-org via distinct URLs/tokens issued out-of-band), and independently re-validate, after successful verification, that the organization that authenticated the request actually owns the `repository`/`stack` the handler is about to mutate. Also consider treating a blank `webhook_secret` as "reject all webhooks for this org" rather than "always verified," or require at least one non-blank secret across all configured orgs before accepting any webhook on the shared endpoint.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `TrustedOrg` (real `webhook_secret`) tracking stack `TrustedOrg/app`, and `SandboxOrg` (no `webhook_secret` set — the documented default).
2. POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "SandboxOrg" }, "full_name": "TrustedOrg/app" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example.com"
}
```
No `X-Hub-Signature` header is required to be valid, because `repository_owner` resolves to `SandboxOrg`, whose `GithubApp#verify_webhook_signature` short-circuits to `true` (`lib/shipit/github_app.rb` line 77).
3. The status handler creates a passing `Status` for the victim commit under `TrustedOrg/app`, which — if `TrustedOrg/app`'s `ci.require` includes `ci/required-check` and continuous deployment is enabled — triggers an unauthorized deploy of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
