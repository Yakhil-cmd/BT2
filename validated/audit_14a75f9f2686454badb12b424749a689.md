## Analysis

CVE-2017-12850's core bug class is: **a server accepts client-supplied data that implicitly claims authorization/ownership over another party's resource, without actually verifying that the claim is true.** The closest reachable analog in `ocore` is in the wallet's shared-address (multisig) handshake, which is driven entirely by messages from a *paired device* (an unprivileged peer) and only performs superficial structural checks — not a real verification that the "shared address" definition actually gives the intended parties the control they believe they have.

### Root cause

`handleNewSharedAddress` in `wallet_defined_by_addresses.js` is invoked directly from the network for the `"new_shared_address"` subject, reachable from any paired device: [1](#0-0) .

It checks that the definition hash matches, that each `signers[path].address` matches the address embedded in the definition at that path, and that every address-leaf in the definition has a corresponding signer entry: [2](#0-1) . It then calls `determineIfIncludesMeAndRewriteDeviceAddress`, which only checks that *some* address among the signers is one of my own addresses or an already-known shared address: [3](#0-2) .

Finally it calls `validateAddressDefinition`, which validates only that the oscript definition is a *well-formed, evaluable* address definition (has correct structure/complexity), and its own comment flags an unresolved TODO — it never checks that the local user's address is genuinely part of the definition in the way the message claims, nor that the definition's logical operator (`and` vs. `or`) matches the semantics the sender is representing (a "joint"/multisig requirement):

Because there is no semantic check on the operator tree, an attacker-controlled paired device can send a `new_shared_address` message whose definition is `["or", [["address", VICTIM_ADDR], ["address", ATTACKER_ADDR]]]` together with `signers` entries that satisfy the structural checks above (victim's own address correctly appears at its path, attacker's address at its path, `determineIfIncludesMeAndRewriteDeviceAddress` finds the victim's address and accepts it as "I am a member"). The victim's wallet will happily persist this as a legitimate "shared address" via `addNewSharedAddress`: [5](#0-4) , presenting it in the UI/API as if it were a joint address requiring both cosigners, while in fact the `"or"` definition lets the attacker alone spend any funds sent there — with the definition-hash consensus rules in `definition.js` fully honoring that unilateral spending condition once a unit is posted: [6](#0-5) .

### Comparison to the CVE

Just as kanboard trusted a client-supplied user identifier to authorize a password reset without checking real ownership, `ocore`'s shared-address handshake trusts a peer-supplied definition/signers mapping to represent genuine joint custody without verifying the actual cryptographic authorization semantics (`and` vs `or`, true multi-party requirement) it purports to establish.

### Title
Unverified Shared-Address Semantics in `handleNewSharedAddress` Enables Spoofed "Joint" Address Fund Theft - (File: wallet_defined_by_addresses.js)

### Summary
A paired device can send a crafted `new_shared_address` message whose oscript definition uses `"or"` instead of `"and"` while still passing all of `ocore`'s structural checks (definition hash matches, signer addresses match definition leaves, sender's own address is present). The receiving wallet persists this as a trusted "shared address" without verifying that spending genuinely requires the victim's cosignature.

### Finding Description
`handleNewSharedAddress` (`wallet_defined_by_addresses.js:378-415`) and its helper `validateAddressDefinition` (`wallet_defined_by_addresses.js:518-528`) validate only definition well-formedness and shallow address/path matching. They never inspect the boolean operator combining the addresses, so a two-party `"and"` (true multisig) and a two-party `"or"` (either party can spend alone) are treated as equally acceptable "shared addresses." `determineIfIncludesMeAndRewriteDeviceAddress` (`wallet_defined_by_addresses.js:281-315`) is satisfied as soon as *any* referenced address belongs to the local user, giving no assurance about the actual control structure.

### Impact Explanation
If the victim (or their wallet software) subsequently funds the resulting address believing it is a protected joint/multisig address, the attacker — being one of the `"or"` branches — can unilaterally spend those funds via a normally-valid signed unit, since `definition.js`'s `validateAuthentifiers`/`evaluate` logic correctly authorizes any satisfied `"or"` branch. This is a concrete unauthorized-spending / fund-loss scenario stemming from a missing authorization/semantic check, directly analogous to the referenced CVE's missing server-side ownership check.

### Likelihood Explanation
Requires only that the attacker be a paired correspondent device of the victim (a routine, low-friction relationship in Obyte's wallet UX — pairing is often done via QR/link with new or lightly-vetted contacts), and that the victim's wallet or user subsequently sends funds to the newly shared address without independently re-deriving/auditing the oscript definition — a step most wallet UIs do not require of end users.

### Recommendation
- In `validateAddressDefinition`, address the documented TODO: confirm the local address is referenced in the definition, and additionally validate that the top-level combination actually requires cooperation of all claimed signer addresses (e.g., reject bare `"or"` combinations of independent addresses, or explicitly flag/warn when the definition does not require all claimed members to jointly authorize spending).
- Surface the actual boolean structure to the user/application layer so wallets can warn when a "shared address" does not require multi-party consent.

### Proof of Concept
1. Attacker pairs with victim's device (normal, low-privilege operation).
2. Attacker sends a `"new_shared_address"` device message with:
   - `definition = ["or", [["address", VICTIM_ADDR], ["address", ATTACKER_ADDR]]]`
   - `signers = { "r.0": {address: VICTIM_ADDR}, "r.1": {address: ATTACKER_ADDR, device_address: ATTACKER_DEVICE} }`
3. `handleNewSharedAddress` accepts it: hash matches, both signer addresses match their definition leaves, victim's address is found by `determineIfIncludesMeAndRewriteDeviceAddress`, and `validateAddressDefinition` only checks well-formedness.
4. The resulting address is stored in `shared_addresses`/`shared_address_signing_paths` and presented to the victim as a shared address.
5. If the victim (or automated flow) sends bytes/assets to this address expecting 2-of-2 protection, the attacker posts a unit signed solely with `ATTACKER_ADDR`'s key satisfying the `"or"` branch, and consensus validation in `definition.js` accepts it as fully authorized, draining the funds.
