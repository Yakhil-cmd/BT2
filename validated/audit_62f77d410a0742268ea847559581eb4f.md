### Title
Webhook signature verified against attacker's own organization but the write target (`Commit`/`Stack`) is looked up with no matching organization scope - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook by resolving the GitHub App/secret for a *specific organization* taken from the payload, but the handler that subsequently executes on the payload (`StatusHandler`, and to a lesser extent the generic `Handler#stacks` lookup) does not re-check that the record it mutates actually belongs to that same organization. This breaks the binding "organization that authenticated == repository/commit that is written."

### Finding Description
`verify_signature` picks the GitHub App config to validate the HMAC using `repository_owner`, itself taken straight from the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`): [1](#0-0) [2](#0-1) 

This means the signature is only proof that *some* configured organization's `webhook_secret` was used to sign the exact bytes of the body — it says nothing about which repository/commit the rest of the same body claims to target.

`StatusHandler#process` then acts on the payload using `sha` alone, with **no repository or organization scoping whatsoever**: [3](#0-2) 

`Commit.where(sha: params.sha)` is a global lookup across every stack/organization tracked by the Shipit instance. Similarly, the generic `Handler#stacks` helper (used by `PushHandler` and others) resolves the target purely from `repository.full_name` in the same JSON body, independent of whatever value was used for `repository_owner` during signature verification: [4](#0-3) [5](#0-4) 

In a multi-tenant deployment (the documented pattern where each GitHub organization has its own `webhook_secret` in `config/secrets.yml`): [6](#0-5) 

an attacker who legitimately owns/administers **Org A** (and therefore knows Org A's `webhook_secret`, since they configured the GitHub App/webhook themselves) can POST directly to `/webhooks` with:
- `X-Hub-Signature` computed with Org A's known secret,
- `repository.owner.login` = `"orgA"` (so `verify_signature` succeeds),
- but a `sha` belonging to a commit that lives in **Org B**'s repository/stack (a customer they have no access to).

Because `StatusHandler` never checks that the commit's stack/repository belongs to Org A, the forged status is written onto Org B's commit.

### Impact Explanation
This is a cross-tenant write with no credential belonging to the victim organization: an attacker holding only their own org's webhook secret can inject an arbitrary `Status` (`state`, `context`, `target_url`, `description`) onto any commit SHA tracked anywhere in the Shipit instance. If the victim stack's `release_status` context matches (or the attacker guesses/observes the configured context string), this can satisfy the CI-gate condition Shipit uses to permit deploys, enabling an unauthorized deploy trigger on a stack/repository the attacker was never granted access to — this matches the "unauthorized deploy" Critical-impact category defined in scope. Even absent an exact context match, it is a clear violation of the "organization authenticated vs. repository/commit written" binding and a cross-repository/cross-organization data write.

### Likelihood Explanation
Requires only that the attacker (unprivileged relative to the victim organization) control/administer a *different* organization already onboarded to the same multi-tenant Shipit instance and know that organization's own `webhook_secret` — which they would legitimately know, since they configure it themselves when connecting their GitHub App/organization. No access to the victim's secret, token, or repository is needed. This is entirely plausible for any Shipit deployment serving more than one organization.

### Recommendation
`StatusHandler` (and any other handler operating on a bare `sha`/global lookup) must scope its query by the repository resolved from the same trust boundary used for signature verification, e.g. `Repository.from_github_repo_name(repository_name).commits.where(sha: params.sha)` instead of `Commit.where(sha: params.sha)`. More generally, `WebhooksController#verify_signature` should assert that `repository.owner.login` (used to pick the signing secret) is consistent with `repository.full_name`'s owner before dispatching to handlers, so a signature valid for Org A can never be used to authorize writes against Org B's records.

### Proof of Concept
1. Shipit instance configured for two tenants, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org setup).
2. Attacker is an admin of `orgA` and therefore knows `orgA`'s `webhook_secret`.
3. Attacker observes (e.g., via public commit history) a commit SHA `deadbeef...` belonging to an `orgB`-owned repository/stack, and the `context` string that `orgB`'s stack requires for its release status gate.
4. Attacker crafts a `status` event body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "<orgB's required ci context>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/irrelevant" }
}
```
5. Attacker computes `X-Hub-Signature: sha1=...` using `orgA`'s known `webhook_secret` over this exact body and POSTs it to `/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `Shipit.github(organization: "orgA")` and successfully verifies the signature. [1](#0-0) 
7. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — matching `orgB`'s commit regardless of the `orgA` context used to authenticate — and creates a `Status` record on it. [3](#0-2) 
8. If `orgB`'s stack is gated on that status context for autodeploy eligibility, this can unblock/trigger a deploy on `orgB`'s stack without any credential belonging to `orgB`.
