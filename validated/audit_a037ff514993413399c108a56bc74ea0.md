### Title
Missing Staking Info Validation in Fast-Sync Allows Malicious Peer to Corrupt Staking DB — (`datasync/downloader/queue.go`, `datasync/downloader/downloader.go`)

### Summary
During fast-sync, a remote P2P peer can serve a `P2PStakingInfo` response whose `BlockNum` field is set to an arbitrary value. Because the `validate` function in `DeliverStakingInfos` is a confirmed no-op (with an explicit `TODO` comment), and because `commitFastSyncData` uses `result.StakingInfo.BlockNum` — not `result.Header.Number` — as the DB key, the attacker can write arbitrary staking data at any block number in the staking DB.

### Finding Description

The fast-sync pipeline requests staking info for specific canonical headers (keyed by `common.Hash` in `stakingInfoTaskPool`). When the peer responds, `queue.DeliverStakingInfos` calls a `validate` stub that always returns `nil`: [4](#0-3) 

The `reconstruct` closure then stores the peer-supplied `P2PStakingInfo` directly into `fetchResult.StakingInfo` with no field-level checks. In `commitFastSyncData`, the write path is:

```go
d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
``` [5](#0-4) 

Two distinct attack vectors exist:

1. **Wrong `BlockNum`**: Peer returns staking info for canonical header at block N but sets `BlockNum = M`. The staking DB entry at key M is overwritten with attacker-controlled data, while the entry at N is never written.
2. **Side-chain data at correct `BlockNum`**: Peer returns staking info with `BlockNum = N` but with staking balances derived from a reorged/side-chain block at N. The canonical staking DB entry at N is silently replaced.

The same pattern exists in `commitPivotBlock`: [6](#0-5) 

### Impact Explanation

The staking DB is the authoritative source for:
- **Reward distribution**: staking balances determine how block rewards are split among validators and delegators.
- **Validator set computation**: the weighted-random proposer policy reads staking info to compute validator weights.

Corrupting entries at attacker-chosen block numbers causes incorrect reward amounts to be distributed and/or an incorrect validator set to be used for consensus, meeting the "invalid reward distribution" and "consensus divergence" impact criteria.

### Likelihood Explanation

Any node performing fast-sync (the default for new nodes joining the network) that connects to a malicious peer is vulnerable. The attacker only needs to be a reachable P2P peer — no privileged keys, validator majority, or governance access is required. The attack is silent (no error is returned or logged for the missing validation).

### Recommendation

In `queue.DeliverStakingInfos`, replace the no-op `validate` with a check that:
1. `stakingInfoList[index].BlockNum` equals `header.Number.Uint64()`.
2. Optionally, that the staking info content is consistent with the canonical state root committed in the header (e.g., via a Merkle proof or post-sync re-derivation).

In `commitFastSyncData` and `commitPivotBlock`, use `result.Header.Number.Uint64()` as the DB key instead of `result.StakingInfo.BlockNum` to prevent key-displacement attacks even if content validation is deferred.

### Proof of Concept

1. Stand up a fast-sync peer that serves valid headers/bodies/receipts for the canonical chain.
2. For any staking-update-interval block N, respond to the staking info request with a `P2PStakingInfo` where `BlockNum = N-1` (or any other number) and staking balances set to attacker-chosen values.
3. The syncing node calls `PutStakingInfoToDB(N-1, <attacker_data>)`.
4. Assert: the local staking DB at key `N-1` contains the attacker-supplied balances; the entry at key `N` is absent.
5. Observe that subsequent reward computations using block `N-1`'s staking info produce incorrect distributions.
