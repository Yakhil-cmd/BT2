### Title
Accrual arithmetic overflow permanently freezes a large market before the borrow-index cap engages - (File: contracts/pool/src/interest.rs)

### Summary
The NiceGUI report's bug class — a guard that checks the wrong property (`exists()` instead of `is_file()`), letting attacker-influenced input slip past validation into an unhandled error that degrades the system — maps onto the pool's index-growth path. The pool caps `borrow_index` at `MAX_BORROW_INDEX_RAY`, but that cap guards the *index*, while accrual also recomputes *value* (`scaled_shares * index`) inside `scaled_to_original`. On a high-decimals market with a very large supplied/borrowed base, the value multiplication overflows `i128` and panics with `GenericError::MathOverflow` before the index ever reaches its cap. Since `global_sync` runs at the head of every state-changing verb, the entire market is permanently bricked.

### Finding Description
`global_sync` in `contracts/pool/src/interest.rs` chunks elapsed time into `MAX_COMPOUND_DELTA_MS` windows and calls `accrue_chunk`, which invokes `accrue_step` and writes the resulting indexes unconditionally (lines 20–53). Interest computation goes through `scaled_to_original` (`common/src/rates/scaling.rs`), which multiplies scaled RAY shares by the index via `mul_div_half_up`/`mul_div_floor` in `common/src/math/fp_core.rs` — any result that does not fit `i128` panics with `GenericError::MathOverflow` (`fp_core.rs:117`, `fp_core.rs:300-303`).

The protective cap `MAX_BORROW_INDEX_RAY` bounds the index value only, not the scaled-share × index product. With an 18-decimal asset and a whale-scale principal (the in-repo test uses `BILLION * 10^18` units at ~98% utilization on the XLM rate curve), the index grows to ~170x over years while the debt *value* crosses the `i128` ceiling first. The cap therefore never engages — the guard checks the wrong invariant, exactly like `exists()` vs `is_file()` in the advisory.

The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356` demonstrates precisely this: `update_indexes` fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `withdraw` and `repay` calls fail identically because every verb accrues first.

### Impact Explanation
Permanent freezing of funds. Once the market crosses the value ceiling, every accrual panics, and since `global_sync` precedes all verbs, no supplier can withdraw, no borrower can repay, and no liquidator can liquidate. All supplied collateral and loaned principal in that market is locked forever — including for users who did nothing to cause the condition. Unlike the NiceGUI case (log amplification, per-request cost), here the unhandled error latches into a state where the contract can never operate on that market again.

### Likelihood Explanation
Reachable by a single unprivileged address through only allowed entrypoints: `supply` a large amount of a high-decimals asset and `borrow` near the utilization kink, then let the steep rate segment compound. No privileged role, oracle manipulation, or third party is required. The prerequisites are demanding — a very large principal (the test uses ~$10^9-scale units of an 18-decimal token) and sustained ~98% utilization over years — so this is not cheap or fast to trigger, but nothing in the protocol prevents an attacker (or organic whale activity) from creating the condition. Once reached it is irreversible; even `recapitalize` cannot help because it too accrues first. Medium severity.

### Recommendation
Apply the correct guard at the actual failure point: in `accrue_step`/`scaled_to_original` (or in `accrue_chunk`), clamp or saturate the accrued debt value, or engage `MAX_BORROW_INDEX_RAY` based on the *value* bound (`i128::MAX / scaled_shares`) rather than the raw index bound — i.e., cap the index at `min(MAX_BORROW_INDEX_RAY, i128::MAX / scaled_value)` before recomputing. Alternatively, switch the accrual product to a saturating variant (`mul_div_floor_saturating` already exists in `common/src/math/fp_core.rs:180`) so accrual degrades gracefully instead of panicking, preserving withdraw/repay/liquidate paths.

### Proof of Concept
Reproduced by the existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`):

```rust
let principal = BILLION * 10i128.pow(18);          // 18-decimal asset
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;                    // ~98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

// advance years; eventually:
assert_contract_error(t.try_update_indexes_for(&["BIG18"]), errors::MATH_OVERFLOW);
// market frozen: every verb accrues first and hits the same panic
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The test asserts `last.borrow_index < MAX_BORROW_INDEX_RAY`, proving the overflow occurs in the value scaling inside `scaled_to_original` before the index cap can engage.

Note: this failure mode is already documented by the in-repo test, which may mean it is a known/accepted limitation. If the team considers it documented behavior, then no novel analog exists; I was unable to fully verify whether an ADR explicitly accepts it due to iteration limits.
