### Title
Accrual panic permanently freezes a saturated market — repay/withdraw/liquidate all abort - ([File: tests/test-harness/tests/controller/large_positions_and_long_horizons.rs])

### Summary
The external report's bug class is an unchecked dereference that crashes a server process — a single request path turns a latent invalid state into a hard abort that degrades service for everyone. The XOXNO Lending analog is an unchecked arithmetic state in interest accrual: once a market's borrow index grows past the value ceiling that `scaled_to_original` can represent, every subsequent accrual panics with `GenericError::MathOverflow`. Because every user-facing verb accrues the market first, the panic permanently freezes the market — no repay, no withdraw, no liquidation — the same "crash the process, degrade everyone" shape as the Apache null-pointer DoS.

### Finding Description
The pool accrues interest by chunking elapsed milliseconds against the borrow index and then unscaling scaled debt via `scaled_to_original`. The protocol maintains an index cap (`MAX_BORROW_INDEX_RAY`), but the cap is checked too late: `scaled_to_original` overflows the `i128` RAY-scaled value before the cap can engage. An in-repo harness test proves the reachable end state:

- `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360` drives a whale market to ~98% utilization on the XLM rate curve, advances time, and observes `try_update_indexes_for(&["BIG18"])` fail with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` ("the index cap did not engage before the value overflow").
- The test then asserts `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` both fail with `MATH_OVERFLOW`, with the comment: "The market is frozen: exits and repayments accrue first and hit the same panic."

The attacker-reachable path uses only in-scope verbs: `supply`/`borrow` to push a market to sustained maximum utilization, then `update_indexes` (permissionless accrual poke) to advance the index. Once the index crosses the representable ceiling, the panic is hit by *every* subsequent call that accrues that market — `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `recapitalize`, `update_indexes` — since accrual is the first step of each. The panic is not a per-call abort the caller can route around (unlike, e.g., `get_debt_position_or_panic` in `contracts/controller/src/positions/liquidation/math.rs:129`, which only fails the offending call); it is triggered by stored market state and bricks the market for all users.

### Impact Explanation
Permanent freezing of funds: all suppliers' deposits in the affected market become unwithdrawable, borrowers cannot repay, and liquidators cannot clear unhealthy positions, so the market's entire pooled balance is locked. The failure mode also propagates protocol-wide in proportion — accounts holding that asset as collateral cannot be liquidated, so insolvency can spread to other markets while the panic persists.

### Likelihood Explanation
Reachable by any unprivileged address via `borrow` and `update_indexes`, but costly: it requires whale-scale capital to hold a market near maximum utilization and a long accrual horizon on a steep rate-curve segment (the harness loops up to 40 years of simulated time; the cliff arrived before that bound in the test's configuration). No privileged role, leaked key, or off-chain component is needed — only sustained borrow demand and elapsed time, which honest utilization can also produce. Medium: high impact, low-but-permissionless trigger.

### Recommendation
Enforce the index ceiling inside accrual itself, before unscaling: clamp `borrow_index`/`supply_index` to `MAX_BORROW_INDEX_RAY` (and the corresponding representable RAY value bound for the asset's decimals) at the point the index is advanced in the pool cache/scale path, so `scaled_to_original` can never receive an unrepresentable scaled amount. Alternatively, bound accrual by checking the post-accrual ray value with `checked_mul`/`mul_div` and saturating rather than panicking, and add a regression test mirroring `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` that asserts withdraw/repay still succeed after the cap engages.

### Proof of Concept
Reproduced by the existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`:

1. Create a high-decimals market on the XLM rate curve with caps lifted (`lift_caps`, `with_max_utilization_disabled_all_markets`).
2. `supply` ~1e9·10^18 units of the debt asset; `borrow` ~98% of it (both unprivileged calls).
3. Permissionlessly call `update_indexes` while advancing ledger time until the call returns `MATH_OVERFLOW` — observed while `borrow_index < MAX_BORROW_INDEX_RAY`.
4. Observe `withdraw` and `repay` for that market both panic with `MATH_OVERFLOW`: the market is permanently frozen, matching the report's crash-degrades-service pattern.
