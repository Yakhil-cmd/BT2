### Title
Missing type validation of `definition template` params in `validateAuthentifiers` allows unsanitized values into address definitions - (File: definition.js)

### Summary
`validateAuthentifiers()` in `definition.js` evaluates the `'definition template'` operator by reading a previously‑posted `app='definition_template'` payload and filling it with attacker‑supplied `params` via `replaceInTemplate()`, without validating that each param is a string/number, unlike the equivalent check performed in the full-definition path `validateDefinition()`.

### Finding Description
`definition_template` messages are global, unprivileged-postable data (`app: 'definition_template'`) that is stored on-chain and later referenced by any address (or asset) definition via the `['definition template', ['unit', {param1: 'value1', ...}]]` operator, in the same spirit as the Strapi bug where an unsanitized global template object could be repopulated with attacker-controlled content and reused elsewhere without validation.

In the primary definition-validation path, `validateDefinition()`'s `'definition template'` handler explicitly restricts the substitution values: [1](#0-0) 
```
case 'definition template':
    ...
    if (!isNonemptyObject(params))
        return cb("params must be non-empty object");
    for (var key in params)
        if (typeof params[key] !== "string" && typeof params[key] !== "number")
            return cb("each param must be string or number");
```

However, the second implementation of the same operator, located inside `validateAuthentifiers()`'s inner `evaluate()` (used when checking authentifiers/signatures, and for asset conditions when `bAssetCondition` is true), performs no such type check before calling `replaceInTemplate`: [2](#0-1) 
```
case 'definition template':
    // ['definition template', ['unit', {param1: 'value1'}]]
    var unit = args[0];
    var params = args[1];
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            var template = rows[0].payload;
            var arrTemplate = JSON.parse(template);
            var arrFilledTemplate = replaceInTemplate(arrTemplate, params);
            evaluate(arrFilledTemplate, path, cb2);
        }
    );
    break;
```

`replaceInTemplate()` substitutes any `"$name"` placeholder string with `params[name]` verbatim, and explicitly notes that the substituted value "may change type if params[name] is not a string": [3](#0-2) 

Because `validateAuthentifiers()` always calls `validateDefinition()` first (line 1454) before running its own `evaluate()`, the outer/top-level definition passed by the author is checked once by `validateDefinition`. But `validateDefinition`'s `'definition template'` branch itself recurses into `evaluate(arrFilledTemplate, ...)` (line 340) rather than back into `validateDefinition`, so nested `'definition template'` operators that appear *inside* a referenced/inner definition (reached via `['address', ...]` at line 774-800, or nested templates) are validated only by `validateAuthentifiers`'s `evaluate()`, which lacks the param type check. An attacker who controls an inner/referenced address definition (e.g., a multisig member address, an asset issuer condition, or any address whose definition embeds a `'definition template'` operator) can therefore supply `params` containing non-string/non-number values (objects, arrays, booleans) that get spliced into the filled template's operator tree and passed to `evaluate()` unsanitized.

### Impact Explanation
Since `params[name]` can inject an arbitrary JS value (object/array) into positions of the definition AST that are normally expected to be strings/numbers (e.g., into `sig.pubkey`, `hash.hash`, `address` operands, or nested op arrays), this bypasses the "each param must be string or number" restriction that the rest of the codebase relies on as an invariant for well-formed definitions. Depending on how the polluted structure is later interpreted by `evaluate()` (e.g., an object landing where a pubkey/hash/address string is expected), this can cause type-confusion in signature/hash/address checks, potentially causing authentifier checks to behave unexpectedly (incorrectly satisfied conditions) or to throw uncaught exceptions during consensus-critical validation, leading to node crashes/DoS on validating nodes or disagreement between nodes that hit the code path differently.

### Likelihood Explanation
Reaching this path requires only posting a `definition_template` message (unprivileged) plus constructing an address/asset definition that references it via `'definition template'` nested under an `'address'` operator or within an asset condition, both of which are attacker-reachable as an ordinary unit poster/asset issuer — no special privileges are required.

### Recommendation
Add the same param-type validation used in `validateDefinition()` (`params must be non-empty object` and `typeof params[key] === "string" || "number"`) to the `'definition template'` case inside `validateAuthentifiers()`'s `evaluate()` in `definition.js` (lines 802-819), or refactor both locations to share a single validated implementation of `replaceInTemplate` invocation.

### Proof of Concept
1. Post a `definition_template` unit whose payload embeds a placeholder, e.g. `["sig", {"pubkey": "$pk"}]`.
2. Create/reference an address whose definition uses `["definition template", ["<template_unit>", {"pk": {"malicious":"object"}}]]` nested inside an `['address', ...]` reference or an asset's `issued_by_definer_only`/attestor condition, so that the path is only checked via `validateAuthentifiers()`'s inner `evaluate()`, not the primary `validateDefinition()` params check.
3. Submit a unit spending from that address; observe that `replaceInTemplate` injects the object into the `sig.pubkey` field without rejection, and trace how `evaluate()`'s `'sig'` handler (definition.js lines 734-753) processes `args.pubkey` as a non-string value.

Note: I was unable to fully trace every call path that reaches this specific `evaluate()` branch versus `validateDefinition`'s branch (e.g., whether `bAssetCondition` or authentifier-path nesting always forces re-entry through `validateDefinition` for every nested definition), so the exact reachability/exploitability under all definition topologies is not fully confirmed and would benefit from deeper runtime tracing of `validateAuthentifiers` vs `validateDefinition` recursion in a live/dev environment.

function replaceInTemplate(arrTemplate, params){
	function replaceInVar(x){
		switch (typeof x){
			case 'number':
			case 'boolean':
				return x;
			case 'string':
				// searching for pattern "$name"
				if (x.charAt(0) !== '$')
					return x;
				var name = x.substring(1);
				if (!ValidationUtils.hasOwnProperty(params, name))
					throw new NoVarException("variable "+name+" not specified, template "+JSON.stringify(arrTemplate)+", params "+JSON.stringify(params));
				return params[name]; // may change type if params[name] is not a string
			case 'object':
				if (Array.isArray(x))
					for (var i=0; i<x.length; i++)
						x[i] = replaceInVar(x[i]);
				else
					for (var key in x)
						assignField(x, key, replaceInVar(x[key]));
				return x;
			default:
				throw Error("unknown type");
		}
	}
	return replaceInVar(_.cloneDeep(arrTemplate));
}
