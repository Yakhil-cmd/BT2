### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any other stack's deploy/CI state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` lookup method used by every other API controller, breaking the binding between "the stack an `ApiClient` token is authorised for" and "the stack the request actually touches."

### Finding Description
`Shipit::Api::BaseController` implements the authorization contract that all API controllers are supposed to rely on: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the client is scoped to one, and `stack` resolves `params[:stack_id]` **within that restricted scope**. This is the mechanism that enforces "a stack a token authorises == the stack it touches" for every other endpoint (`TasksController`, `DeploysController`, `MergeRequestsController`, etc., all inherit `stack` unmodified).

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

This calls `Stack.from_param!` directly against the unscoped `Stack` model instead of the scoped `stacks` collection defined in `BaseController`. The `require_permission :read, :stack` before_action only checks that the client's permission list contains `"read:stack"` — it never checks *which* stack the client is scoped to (`ApiClient#check_permissions!` only compares operation/scope strings): [3](#0-2) 

Because `ApiClient` supports an optional `stack` association intended to restrict a token to a single stack (as used in the `here_come_the_walrus` fixture and enforced elsewhere via `BaseController#stacks`), any client holding a `read:stack`-permissioned token — even one legitimately minted and scoped to Stack A — can supply an arbitrary `stack_id` in the `/api/*stack_id/ccmenu` route and read CI/build status (`stack.deploys_and_rollbacks.last`, lock state, last build result) for **any** other stack B in the installation, including stacks the token was never meant to access, and including archived/locked/private stacks.

Before vs. after equality broken:
- Intended: `token.stack_id == requested_stack.id` (or unscoped token) for every read.
- Actual in `CCMenuController#show`: `requested_stack = Stack.from_param!(params[:stack_id])` with no relation to `token.stack_id` at all.

### Impact Explanation
This is an authorization-scope escalation: a token that was deliberately restricted (by an administrator or automated CCMenu-URL flow) to observe one stack's build status instead gains read access to the state of every stack in the Shipit installation. This falls under the "escalation into … authorization" / "unauthenticated-equivalent read of stack state" category — a token holder with narrow, single-stack read permission is escalated to a global read-all-stacks capability, exposing build/deploy status (including for stacks belonging to unrelated teams/repositories) that the token issuer never intended to share.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker must already possess *some* valid `ApiClient` token with `read:stack` permission (even one legitimately scoped to a single stack, e.g. a CCMenu URL token handed to a CI dashboard tool). Given that any `ApiClient` with `read:stack` — however narrowly scoped — can trivially escalate by only changing the `stack_id` route segment, and that CCMenu tokens are routinely embedded in external CI-monitoring tools/URLs (increasing exposure/leak surface), exploitation requires no further privilege and is trivial once a token of any scope is obtained.

### Recommendation
Remove the `stack` override in `CCMenuController` and use the inherited, scope-respecting `stack`/`stacks` methods from `BaseController` (i.e., resolve `Stack.from_param!` via `stacks.from_param!` so the client's `stack_id` restriction is honored), consistent with every other API controller.

### Proof of Concept
1. Administrator (or the app itself, e.g. via `CCMenuUrlController`) issues an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` and `stack_id: A.id`.
2. Attacker obtains/leaks this token (e.g. from an embedded CCMenu URL) and calls:
   `GET /api/<owner>/<repoB>/<envB>/ccmenu?token=<tokenA>`
3. `authenticate_api_client` in `CCMenuController` authenticates the token via `ApiClient.authenticate(params[:token])`, succeeding since the token itself is valid.
4. `require_permission :read, :stack` passes because the token has `"read:stack"` in its permission list (no stack check performed).
5. `CCMenuController#stack` resolves `params[:stack_id]` (`repoB/envB`) directly against the global `Stack` model, returning Stack B — a stack unrelated to the token's `stack_id` (A).
6. The response renders Stack B's latest deploy/CI status in XML, disclosing information about a stack the token was never authorized for.

**Note on uncertainty**: I could not locate a UI flow (only fixtures/tests) that lets end-users create stack-scoped `ApiClient`s through `ApiClientsController` (its `create_params` only permits `name`/`permissions`, not `stack`); stack-scoped clients appear to be created programmatically (e.g., internal tooling or direct DB/fixture creation) rather than through the web form. This does not affect the validity of the code-level authorization-bypass finding, but it does affect how commonly stack-scoped tokens are actually issued in a default installation.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
