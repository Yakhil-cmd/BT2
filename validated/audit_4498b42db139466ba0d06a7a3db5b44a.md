### Title
Cross-organization webhook forgery: signature is verified against `repository.owner.login`, but handlers act on unrelated `repository.full_name` / global commit lookups - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization's `webhook_secret` to validate an incoming webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-supplied JSON body [1](#0-0) . Once the signature checks out for *that* organization, the event handlers use a *different* field of the same untrusted body — `repository.full_name` — to decide which `Stack`/`Repository` to mutate [2](#0-1) , or in the case of CI status updates, no repository scoping is applied at all [3](#0-2) . Nothing ties the two fields together, so a party that legitimately owns/administers one organization's GitHub App (and therefore knows *its own* `webhook_secret`) can forge a signed payload whose `repository.owner.login` matches their own org (to pass signature verification) while `repository.full_name`/`sha` target a completely different, victim organization's stack or commit.

### Finding Description
The binding that should hold is:
`organization whose webhook_secret authenticated the request == organization/repository that the handler is permitted to mutate`

Before this request:
- Organization A has its own GitHub App configured in `Shipit.github(organization: 'orgA')` with its own `webhook_secret`, known to Org A's administrators. Org B is a separate, unrelated tenant of the same Shipit instance with its own stacks/commits.

`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)   # repository_owner from payload
verified = github_app.verify_webhook_signature(sig, request.raw_post)
``` [4](#0-3) 
`repository_owner` is read directly from the same JSON body that the HMAC signature covers:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

An attacker who legitimately possesses Org A's `webhook_secret` can craft an arbitrary JSON body, set `repository.owner.login = "orgA"` so `verify_signature` selects and validates against Org A's own secret (which the attacker can correctly HMAC-sign), and simultaneously set unrelated fields — `repository.full_name` or `sha` — to point at Org B's stack/commit.

Downstream, handlers never re-check that the repository they operate on belongs to the organization that authenticated the request:
- The base `Handler#stacks` resolves the target purely from `payload.dig('repository','full_name')`, with no relation to `repository_owner` used for signature selection [2](#0-1) . `PushHandler` and `CheckSuiteHandler` both consume this unscoped `stacks` helper [6](#0-5) [7](#0-6) .
- `StatusHandler` is worse: it does not scope by repository/stack at all — it looks up commits globally by SHA across the entire database: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .

This is a direct structural analog of the reported bug class: the entity that was authenticated/verified (`repository.owner.login`, checked against a specific org's secret) is never re-validated against the entity that ends up being written (`repository.full_name` / arbitrary commit `sha`), exactly like `Crowdsale`'s strategy/agent addresses being verified once but never re-checked when acted upon later.

### Impact Explanation
Using a valid `webhook_secret` for their *own* organization, an attacker can:
- Forge a `status` webhook event ("success"/passing CI) for a commit `sha` belonging to any other tenant's private repository tracked by the same Shipit instance, because `StatusHandler` has zero repository scoping [3](#0-2) . If that commit's stack relies on required/blocking statuses to gate continuous delivery or the merge queue, this forged status can satisfy the gating condition and trigger an actual, unauthorized deploy of a repository the attacker has no legitimate access to — a Critical-impact outcome ("unauthorized deploy") per the stated impact categories.
- Forge `push`/`check_suite` events for a victim stack by setting `repository.full_name` to the victim's repo while authenticating with their own org's secret, causing `sync_github`/check-run refresh actions to run against a repository unrelated to the authenticating organization.

### Likelihood Explanation
This requires only that the attacker be an unprivileged, legitimate administrator of *any one* organization/GitHub App installed on the shared Shipit instance (i.e., they know their own org's `webhook_secret`, which they configured themselves) — they need no privileges over the victim organization, no `ApiClient` token, and no repository write access to the victim repo. Multi-tenant Shipit deployments that serve more than one GitHub organization/app configuration are the primary risk scenario. Constructing the forged HTTP POST with a correct HMAC signature using one's own known secret is trivial.

### Recommendation
Cross-validate the organization used for signature verification against the actual target repository/stack in every handler:
- In `Handler#stacks`/`#repository_name`, resolve the repository the same way `verify_signature` does, and reject (or scope out) any commit/stack whose actual GitHub organization does not match the verified `repository_owner`.
- In `StatusHandler`, scope the `Commit.where(sha: ...)` lookup to commits whose `stack.repository.owner` matches the verified organization, instead of a global unscoped lookup.
- Consider passing the verified organization down from the controller into `Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization: repository_owner) }` and have every handler assert `stack.repository.owner == verified_organization` before mutating state.

### Proof of Concept
1. Attacker legitimately administers Org A's GitHub App on a shared Shipit instance and knows Org A's `webhook_secret`.
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/some-repo" },
  "sha": "<sha-of-a-commit-belonging-to-orgB-victim-stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, raw_body)` — valid, since it's their own secret over their own crafted body.
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches Org A's `github_app`, and the signature validates successfully [4](#0-3) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim Org B's commit regardless of the `repository` field — and calls `create_status_from_github!`, marking it as passing CI [3](#0-2) .
6. If Org B's stack has continuous delivery enabled and this was the last required/blocking status, `Stack#trigger_continuous_delivery` proceeds to deploy the victim's commit, entirely triggered by an attacker who never had any credentials for Org B.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
