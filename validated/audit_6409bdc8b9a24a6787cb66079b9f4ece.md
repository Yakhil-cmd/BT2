### Title
Webhook signature is verified against an organization selected from unauthenticated payload fields, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the request signature against using a field taken directly from the still-unverified JSON body (`repository.owner.login` or `organization.login`). Handlers that subsequently act on the request use a *different* field from the same payload (`repository.full_name`, or no repository scoping at all) to decide which `Stack`/`Repository`/`Commit` to mutate. Because these two payload-derived values are never checked for consistency, a party who legitimately administers a GitHub App/organization already onboarded onto the same Shipit instance can sign a payload with their own `webhook_secret` while pointing the "acted upon" fields at a completely different organization's repository, letting the correctly-signed request mutate another tenant's data.

### Finding Description
`Shipit.github(organization:)` looks up per-organization GitHub App configuration (`app_id`, `webhook_secret`, etc.) by an organization key, and Shipit explicitly supports hosting multiple GitHub organizations behind a single instance and a single `/webhooks` endpoint: [1](#0-0) [2](#0-1) 

`WebhooksController` determines which organization's secret to verify the incoming signature against by reading it straight out of the unauthenticated JSON body, before the signature check has been proven valid: [3](#0-2) [4](#0-3) 

The webhook handlers that then execute the event, however, key off a *different* field of the same body to decide what to mutate. `PullRequest::OpenedHandler` (and the other pull-request handlers) resolve the target `Repository` from `params.repository.full_name`: [5](#0-4) 

`PushHandler` resolves target stacks from `stacks` (derived elsewhere from repository/branch) and triggers a full GitHub sync: [6](#0-5) 

`StatusHandler` is scoped by `sha` alone, with **no repository check whatsoever**, and writes a commit status directly: [7](#0-6) 

The binding that should hold is:
`organization used to select/verify the webhook_secret (repository_owner)` == `organization/repository actually written to by the handler (repository.full_name / matched Stack)`

Since `repository_owner` and `repository.full_name` are independent, attacker-controlled strings inside the same unsigned JSON body, an attacker who owns one organization's GitHub App config already registered in this Shipit instance (a normal, unprivileged tenant with respect to Shipit itself — they only administer their own GitHub org/app, not Shipit) can:
1. Set `repository.owner.login`/`organization.login` = `"my-own-org"` so `verify_signature` picks `my-own-org`'s `webhook_secret`, which the attacker knows because they configured that GitHub App themselves.
2. Sign the raw body with that known secret.
3. Set `repository.full_name` (used by handlers) = `"victim-org/victim-repo"`, or for `status` events simply target a `sha` that exists in the victim's `Commit` table (no ownership check).

This produces a request that passes `verify_signature` yet drives handlers to operate on a victim organization's `Stack`/`Repository`/`Commit`, entirely because the equality between "org that authenticated" and "repo that is written" is never checked.

### Impact Explanation
This crosses the required boundary of "cross-repository writes" / "unauthorized deploy" without any Shipit session, API token, or the victim organization's webhook secret. Concretely, an attacker satisfying only the low bar of controlling one already-onboarded GitHub org/app can:
- Forge `push` webhooks to force `sync_github` on a victim stack out of band with real GitHub state.
- Forge `status` webhooks to set/spoof commit statuses on a victim's tracked commits (`Commit#create_status_from_github!`), directly influencing merge-queue/CI gating and thus enabling shipment/merge decisions to be manipulated.
- Forge `pull_request` `opened`/`labeled`/`closed` events to provision, archive, or otherwise manipulate review stacks tied to a victim repository.

This matches the "cross-repository writes" / "unauthorized ship" impact bucket.

### Likelihood Explanation
Exploitability requires only that the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker administers/owns one of those onboarded orgs — no Shipit credentials, GitHub App private key, or victim-org secrets are needed. This is a plausible operating model for shared/multi-tenant Shipit deployments, making likelihood Medium-to-High in that configuration, though it does not apply to single-organization deployments (the common case), where `repository_owner` and `repository.full_name`'s owner always coincide with the sole configured org.

### Recommendation
After `verify_signature` succeeds, additionally assert that the organization used to select the webhook secret equals the organization embedded in every field the handler will act upon (e.g., compare `repository_owner` against the owner segment of `params.dig('repository','full_name')` and against any `sha`-resolved commit's stack's repository owner) and reject (422) on mismatch. Alternatively, scope commit/stack lookups in handlers like `StatusHandler` by repository/organization rather than by `sha` alone.

### Proof of Concept
Given a Shipit instance configured with two organizations, `attacker-org` (attacker-administered, secret known to attacker) and `victim-org` (unrelated tenant), the attacker crafts a `status` webhook body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<sha of a commit tracked under victim-org's stack>",
  "state": "success",
  "context": "ci/fake",
  "created_at": "2026-09-01T00:00:00Z"
}
```
and signs it with `attacker-org`'s known `webhook_secret`, sending `X-Hub-Signature` accordingly, `X-Github-Event: status`. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies successfully against the attacker's own secret [3](#0-2) , and `StatusHandler#process` then updates the status of the victim's commit purely by `sha`, with no organization check [7](#0-6) .

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
