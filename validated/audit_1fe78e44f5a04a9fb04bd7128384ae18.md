### Title
Duplicate liquidation repay legs read a stale pre-batch debt position and send it to the pool, desynchronizing account books from pool totals - (File: contracts/controller/src/positions/liquidation/apply.rs)

### Summary
`apply_liquidation_repayments` iterates the normalized repayment plan and, for every leg, reads the account's debt position from the still-unmutated `account.borrow_positions` map, builds a `PoolAction` carrying that scaled position, and only afterwards calls `apply_repay_batch`, which invokes the pool and merges all mutations. This is the same bug class as the kernel report: a value (here the scaled debt position, the analog of `skb shinfo`) is captured before an operation that relocates/mutates it (`apply_repay_batch` replaying every leg through the pool and rewriting the position via `merge_debt_leg`), and is reused for a second leg on the same `hub_asset`. If the plan contains two legs for one debt market, the second leg sends the pool a stale position snapshot taken before the first leg's burn.

### Finding Description
- `build_liquidation_plan` (`contracts/controller/src/positions/liquidation/plan.rs:14`) normalizes the liquidator-supplied `raw_payments: Vec<HubPayment>` into `repayment.repaid`. The liquidator controls `payments` in `liquidate` and there is no `aggregate_positive_payments` deduplication on this path (unlike `process_repay` at `debt.rs:77`, which aggregates).
- In `apply_liquidation_repayments` (`apply.rs:45-78`), each leg does `account.borrow_positions.get(entry.hub_asset)` to build `make_pool_action(&position, received, entry.hub_asset)`. Because `apply_repay_batch` runs once after the loop (`apply.rs:79-86`), the in-memory `account` is never updated between legs. A second leg on the same `hub_asset` therefore reads the same pre-repay `scaled_amount`.
- The pool has no per-account book and trusts the supplied position (documented as INV-ACCT-10 in `docs/reference/invariants.md:202-216`: "A controller path that ... sends a stale position to the pool, breaks this invariant without a revert"). `repay::accounting` (`contracts/pool/src/ops/repay.rs:44-60`) computes `burned` and `overpayment` against the passed position, so leg 2 resolves `burned`/`overpayment` against the pre-leg-1 debt rather than the residual.
- The controller then merges each result with `LegDirection::Exit` (`debt.rs:219-229`), overwriting `account.borrow_positions[hub]` with the second leg's stale-derived `new_scaled`, discarding leg 1's effect on the stored position.

Consequence: the account's stored debt is overstated by leg 1's burned shares while the pool's `borrowed` total was reduced by both legs' burns, so Σ account debt > pool borrowed — the INV-ACCT-10 reconciliation breaks silently.

### Likelihood Explanation
A single unprivileged liquidator triggers it with `liquidate(caller, account_id, payments, ...)` by submitting two `HubPayment` entries for the same debt asset. Reachability hinges on `normalize_repayment_plan` not collapsing duplicate `hub_asset` entries into one leg; I was not able to fully confirm the dedup behavior inside `liquidation/math.rs` within the available search budget, so the duplicate-leg premise is the one unverified link. No governance, upgrade, or oracle precondition is needed — only an unhealthy account and a duplicated payment leg surviving normalization.

### Impact Explanation
- Silent book divergence: `merge_debt_leg` with `Exit` writes `outcome.new_scaled` (computed from the stale position), so the account retains phantom debt while `cache.burn_debt` in the pool already removed those shares from market totals.
- The phantom residual debt keeps the account's health factor artificially depressed: it remains liquidatable (or is pushed into `is_socializable_bad_debt`), letting `check_bad_debt_after_liquidation`/`clean_bad_debt` socialize "bad debt" that was actually already paid — a supply-index write-down that transfers the loss to all suppliers of that market, i.e., theft of user funds / protocol insolvency.
- Alternatively, if `cache.burn_debt` or spoke-usage bookkeeping hits an inconsistency (usage underflow on the double exit), the market can be left in a state where legitimate repays/withdraws revert — freezing of funds.
- The liquidator also mis-receives the leg-2 overpayment refund: it is computed against the stale (larger) debt, so less is refunded than should be, directly burning the liquidator's excess transfer into pool cash.

### Recommendation
- Deduplicate/aggregate `raw_payments` by `HubAssetKey` inside `build_liquidation_plan`/`normalize_repayment_plan` (mirroring `payments::aggregate_positive_payments` used in `process_repay`), or assert uniqueness of `hub_asset` across `repaid` legs.
- Alternatively, apply each repay leg's mutation to `account` incrementally inside the loop (or re-read the position after each `apply_repay_batch` per-asset call) so no leg is built from a pre-batch snapshot.
- Add a runtime reconciliation check consistent with INV-ACCT-10 (e.g., post-batch assert that each account debt position equals pool-reported residual for each touched market).

### Proof of Concept
1. Target account has debt in market `(hub, X)` with scaled position `D` and HF < 1.
2. Liquidator calls `liquidate` with `payments = [(hubX, a1), (hubX, a2)]` such that both legs survive `normalize_repayment_plan` as separate `repaid` entries on the same `hub_asset`.
3. `apply_liquidation_repayments` loop:
   - Leg 1: reads `position = D`, transfers `a1`, pushes `PoolAction{position: D, amount: received1}`.
   - Leg 2: `account.borrow_positions` is still unmutated → reads `position = D` again, pushes `PoolAction{position: D, amount: received2}`.
4. `apply_repay_batch` → pool leg 1 burns `b1` (scaled for `received1`), leg 2 computes `burned`/`overpayment` against stale `D` (not `D - b1`), burning `b2` sized against already-partially-repaid debt; pool `borrowed` decreases by `b1 + b2` while liquidator's refund is computed against the stale debt figure.
5. `merge_debt_leg` (Exit) writes `new_scaled = D - b2` — leg 1's `b1` reduction is overwritten. Final state: account debt `D - b2`, pool market borrowed reduced by `b1 + b2`. Σ account debts ≠ pool borrowed, INV-ACCT-10 broken without revert, and the phantom `b1` debt remains to be liquidated/socialized against suppliers.
