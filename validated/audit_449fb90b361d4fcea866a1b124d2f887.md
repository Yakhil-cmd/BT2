### Title
Stale `pallet-asset-rate` conversion rate reused when a destroyed asset's identifier/location is recreated - (File: `substrate/frame/asset-rate/src/lib.rs`)

### Summary
`pallet-asset-rate` stores a fixed-point conversion rate keyed by `AssetKind` in `ConversionRateToNative`, used by `pallet-treasury`'s `BalanceConverter` to value non-native assets when paying spends. Removal of this rate is a separate, manually-triggered extrinsic (`remove`) gated by `RemoveOrigin`, and it is never automatically synchronized with the lifecycle of the underlying asset in `pallet-assets`. Because `pallet-assets` explicitly allows an asset identifier to be destroyed and later reused by an unrelated asset (confirmed by the pallet's own test and doc warning), a stale rate that was priced for the *old* asset can silently be applied to a *completely different* asset that now occupies the same identifier/location — mirroring the HydraDX Omnipool/EMA-oracle bug where stale oracle data for a removed asset was reused once the asset was re-added with a different price.

### Finding Description
- `pallet-asset-rate::ConversionRateToNative<T>` maps `AssetKind -> FixedU128` and is only mutated by the explicit `create`/`update`/`remove` calls: [1](#0-0) [2](#0-1) 
- `pallet-treasury`'s `BalanceConverter` (e.g. `AssetRate`, or `UnityOrOuterConversion<..., AssetRate>`) is used to convert an `AssetKind` amount to native balance for payouts, e.g. in the Westend/Rococo relay and AssetHub configs: [3](#0-2) [4](#0-3) 
- Nothing in `pallet-assets`'s destroy path (`do_start_destroy` → `do_destroy_accounts` → `do_destroy_approvals` → `do_finish_destroy`) touches `pallet-asset-rate` storage — the two pallets are fully decoupled: [5](#0-4) 
- `pallet-assets` explicitly documents and tests that an asset identifier *can* be reused once the previous asset with that id is destroyed, as long as no strict sequential `AssetIdAllocator` forbids it: `assert_ok!(Assets::create(RuntimeOrigin::signed(1), 0, 1, 1))` succeeds again for id `0` right after `finish_destroy(0)`: [6](#0-5) 
- The pallet's own doc-comment on `force_create` explicitly warns about this exact hazard: *"Reusing an id can corrupt state, most severely for bridged assets, where a collision breaks the local/remote mapping"*: [7](#0-6) 

Putting these together: if governance sets a conversion rate for asset id/location `X` via `pallet-asset-rate::create` (so treasury can pay spends denominated in that asset), and the underlying asset `X` is later destroyed (a normal, non-privileged action available to the asset's own `owner` via `start_destroy`/`finish_destroy`, no `ForceOrigin` required — see `maybe_check_owner` path), and a new, economically unrelated asset is subsequently created re-using the same id (permitted per the test above when no strict `AssetIdAllocator` blocks it), the *old* rate in `ConversionRateToNative` remains associated with that identifier/location and gets silently applied to the *new* asset unless governance separately remembers to call `remove`. This is structurally identical to the HydraDX finding: a pricing/valuation record keyed by an asset identity is not purged when the underlying asset is destroyed, so re-use of that identity with a different economic reality produces an incorrect valuation combining "old" configured data with a "new" underlying asset.

### Impact Explanation
If a treasury `spend`/payout later resolves using the stale rate for the recycled asset kind, the beneficiary could receive a very different real value than intended (either a value leak favoring the payee if the new asset is worth less than assumed by the stale rate priced for the old asset, or a shortfall if worth more) — the same "value leak or incorrect price if certain conditions are met" reasoning the original judge used to justify Medium severity. This is a bounded, config/process-dependent economic-valuation issue, not remote code execution or fund theft by a bare unprivileged actor.

### Likelihood Explanation
Low-to-Medium. It requires: (1) governance to have configured `pallet-asset-rate` for an asset kind whose underlying asset id is destroyable by a non-privileged owner (or otherwise recyclable), and (2) governance/`RemoveOrigin` to not proactively call `remove` when that asset is destroyed, and (3) the identifier to be recreated for an unrelated asset before the stale rate is cleaned up, and (4) a treasury spend against that stale rate to be approved/paid out afterward. This mirrors the original report's own required preconditions (admin re-adding a removed asset with a different price) — a legitimate operational sequence rather than a raw attacker-only exploit.

### Recommendation
- Have `pallet-assets`'s destruction hooks (`CallbackHandle::destroyed`, or a new hook) notify `pallet-asset-rate` (or any other rate/oracle-like pallet keyed by asset identity) so the corresponding `ConversionRateToNative` entry is automatically purged when an asset is destroyed.
- Alternatively, disallow identifier reuse for any asset kind that currently has an associated `pallet-asset-rate` entry, or require `RemoveOrigin` approval before an asset's id can be recycled.
- At minimum, document this cross-pallet coupling explicitly for `pallet-treasury`/`pallet-asset-rate` integrators, alongside the existing `force_create` warning about id reuse.

### Proof of Concept
I was not able to fully construct and execute an integration reproduction within the available tool budget; this is presented as a structural/config-dependent analog derived from static code inspection, not a verified live exploit. What is confirmed by inspection/tests in-repo:
- `pallet-assets` allows an asset id to be destroyed and immediately reused by an unrelated `create`, demonstrated by the existing unit test `asset_id_cannot_be_reused` (which actually shows reuse *succeeding* until an auto-increment allocator is configured): [6](#0-5) 
- `pallet-asset-rate` never listens to asset destruction and only clears its `ConversionRateToNative` entry via an explicit, separately-privileged `remove` call: [2](#0-1) 
- What remains unverified: I could not confirm within the remaining iterations whether any live Parity-maintained runtime (e.g. AssetHub Westend/Rococo, the relay chains) actually configures `pallet-asset-rate`/`pallet-treasury`'s `AssetKind` against a `pallet-assets` (`TrustBackedAssetsInstance`) identifier that is realistically destroyable/recyclable by a non-privileged asset owner (versus only against curated, non-recyclable `VersionedLocatableAsset` foreign assets), nor did I confirm the exact `AssetIdAllocator` setting used for `TrustBackedAssetsInstance` on AssetHub. Confirming those two facts would be necessary to determine whether this is exploitable on any currently deployed, in-scope runtime versus only a theoretical hazard of the generic pallet design.

	/// Start the process of destroying an asset, by setting the asset status to `Destroying`, and
	/// emitting the `DestructionStarted` event.
	pub(super) fn do_start_destroy(
		id: T::AssetId,
		maybe_check_owner: Option<T::AccountId>,
	) -> DispatchResult {
		Asset::<T, I>::try_mutate_exists(id.clone(), |maybe_details| -> Result<(), DispatchError> {
			let details = maybe_details.as_mut().ok_or(Error::<T, I>::Unknown)?;
			if let Some(check_owner) = maybe_check_owner {
				ensure!(details.owner == check_owner, Error::<T, I>::NoPermission);
			}

			ensure!(!T::Holder::contains_holds(id.clone()), Error::<T, I>::ContainsHolds);
			ensure!(!T::Freezer::contains_freezes(id.clone()), Error::<T, I>::ContainsFreezes);

			details.status = AssetStatus::Destroying;

			Self::deposit_event(Event::DestructionStarted { asset_id: id });
			Ok(())
		})
	}

	/// Destroy accounts associated with a given asset up to the max (T::RemoveItemsLimit).
	///
	/// Each call emits the `Event::DestroyedAccounts` event.
	/// Returns the number of destroyed accounts.
	pub(super) fn do_destroy_accounts(
		id: T::AssetId,
		max_items: u32,
	) -> Result<u32, DispatchError> {
		let mut dead_accounts: Vec<T::AccountId> = vec![];
		let mut remaining_accounts = 0;
		Asset::<T, I>::try_mutate_exists(&id, |maybe_details| -> Result<(), DispatchError> {
			let mut details = maybe_details.as_mut().ok_or(Error::<T, I>::Unknown)?;
			// Should only destroy accounts while the asset is in a destroying state
			ensure!(details.status == AssetStatus::Destroying, Error::<T, I>::IncorrectStatus);

			for (i, (who, mut v)) in Account::<T, I>::iter_prefix(&id).enumerate() {
				if Self::ensure_account_can_die(id.clone(), &who).is_err() {
					continue;
				}
				// unreserve the existence deposit if any
				if let Some((depositor, deposit)) = v.reason.take_deposit_from() {
					T::Currency::unreserve(&depositor, deposit);
				} else if let Some(deposit) = v.reason.take_deposit() {
					T::Currency::unreserve(&who, deposit);
				}
				if let Remove = Self::dead_account(&who, &mut details, &v.reason, false) {
					Account::<T, I>::remove(&id, &who);
					dead_accounts.push(who);
				} else {
					// deposit may have been released, need to update `Account`
					Account::<T, I>::insert(&id, &who, v);
					defensive!("destroy did not result in dead account?!");
				}
				if i + 1 >= (max_items as usize) {
					break;
				}
			}
			remaining_accounts = details.accounts;
			Ok(())
		})?;

		for who in &dead_accounts {
			T::Freezer::died(id.clone(), &who);
			T::Holder::died(id.clone(), &who);
		}

		Self::deposit_event(Event::AccountsDestroyed {
			asset_id: id,
			accounts_destroyed: dead_accounts.len() as u32,
			accounts_remaining: remaining_accounts as u32,
		});
		Ok(dead_accounts.len() as u32)
	}

	/// Destroy approvals associated with a given asset up to the max (T::RemoveItemsLimit).
	///
	/// Each call emits the `Event::DestroyedApprovals` event
	/// Returns the number of destroyed approvals.
	pub(super) fn do_destroy_approvals(
		id: T::AssetId,
		max_items: u32,
	) -> Result<u32, DispatchError> {
		let mut removed_approvals = 0;
		Asset::<T, I>::try_mutate_exists(
			id.clone(),
			|maybe_details| -> Result<(), DispatchError> {
				let details = maybe_details.as_mut().ok_or(Error::<T, I>::Unknown)?;

				// Should only destroy accounts while the asset is in a destroying state.
				ensure!(details.status == AssetStatus::Destroying, Error::<T, I>::IncorrectStatus);

				for ((owner, _), approval) in Approvals::<T, I>::drain_prefix((id.clone(),)) {
					T::Currency::unreserve(&owner, approval.deposit);
					removed_approvals = removed_approvals.saturating_add(1);
					details.approvals = details.approvals.saturating_sub(1);
					if removed_approvals >= max_items {
						break;
					}
				}
				Self::deposit_event(Event::ApprovalsDestroyed {
					asset_id: id,
					approvals_destroyed: removed_approvals as u32,
					approvals_remaining: details.approvals as u32,
				});
				Ok(())
			},
		)?;
		Ok(removed_approvals)
	}

	/// Complete destroying an asset and unreserve the deposit.
	///
	/// On success, the `Event::Destroyed` event is emitted.
	pub(super) fn do_finish_destroy(id: T::AssetId) -> DispatchResult {
		Asset::<T, I>::try_mutate_exists(id.clone(), |maybe_details| -> Result<(), DispatchError> {
			let details = maybe_details.take().ok_or(Error::<T, I>::Unknown)?;
			ensure!(details.status == AssetStatus::Destroying, Error::<T, I>::IncorrectStatus);
			ensure!(details.accounts == 0, Error::<T, I>::InUse);
			ensure!(details.approvals == 0, Error::<T, I>::InUse);
			ensure!(T::CallbackHandle::destroyed(&id).is_ok(), Error::<T, I>::CallbackFailed);

			let metadata = Metadata::<T, I>::take(&id);
			T::Currency::unreserve(
				&details.owner,
				details.deposit.saturating_add(metadata.deposit),
			);
			Reserves::<T, I>::remove(&id);
			Self::deposit_event(Event::Destroyed { asset_id: id });

			Ok(())
		})
	}
