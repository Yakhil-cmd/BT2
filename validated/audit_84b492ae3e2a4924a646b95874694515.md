### Title
Cross-tenant `status` webhook triggers unauthorized deploy via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by SHA alone, with no constraint tying the matched `Commit` rows to the repository named in the verified webhook payload. Because Git SHAs (e.g. the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any SHA an attacker can force to collide across repos by pushing identical content) are not globally unique to one repository, an attacker who owns a repository and its `webhook_secret` can send a validly-signed `status` event for their own repo and have it applied to a `Commit` row belonging to a completely different, victim stack, flipping that commit's state to `success` and triggering `Stack#trigger_continuous_delivery`.

### Finding Description
The broken binding is: `verified_webhook.repository.full_name == commit.stack.repository.full_name` for every `Commit` object that `create_status_from_github!` is applied to. This should be true but is not enforced anywhere in the code path.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) only proves that the payload was signed by the `webhook_secret` of the organization/repo named in `params['repository']['owner']['login']`. It does not check that this repository is the one whose commit(s) get updated.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` across the **entire database**, matched only on `sha`, with no `stack_id`/`repository` scoping to the webhook's authenticated repository. Any `Commit` row anywhere in Shipit sharing that SHA gets a new `Status` created and its cached state recomputed.
- `Commit#create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb:165-169`) recalculates `state`; if it flips to `success` it schedules `ProcessMergeRequestsJob`, which for a `next_commit_to_deploy` commit checks `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) and, if true, calls `Stack#trigger_continuous_delivery` → `trigger_deploy`, all evaluated on the **victim's** stack object, not the attacker's.

Attack flow: attacker pushes a commit with the empty-tree SHA (or any SHA whose content they can also produce, since git SHAs are content hashes and identical trees/commits across repos share SHAs) to their own repository, then POSTs a `status` webhook body `{"sha": "<shared sha>", "state": "success", "repository": {"full_name": "attacker/own-repo", "owner": {"login": "attacker-org"}}, ...}` signed with their own repo's `webhook_secret`. `verify_signature` passes because the signature genuinely matches attacker-org's secret and payload. `StatusHandler#process` then finds the victim's `Commit` row with the same `sha` (unscoped by repo) and applies the attacker-controlled `state`/`context` to it, potentially flipping `success? == true` on a commit that never got real CI success on the victim's actual GitHub repo.

None of the listed guards catch this: `drop_unhandled_event` and `ExplicitParameters` only validate presence/shape of `sha`/`state`, not repository ownership; `verify_signature` binds the *signature* to a repo but never binds the *effect* (which `Commit` rows get mutated) to that same repo.

### Impact Explanation
A cross-tenant write: an attacker authenticated only as themselves (their own GitHub repo/secret) can write a `Status` row and mutate the cached `state` of a `Commit` belonging to a victim's stack, and if that commit is `next_commit_to_deploy` on a `continuous_deployment: true` stack, this directly triggers `Deploy` creation via `Stack#trigger_continuous_delivery` for code that never passed the victim's own CI. This is an unauthorized deploy of another tenant's stack — matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The attack is repeatable against any stack/commit sharing a predictable SHA (empty-tree SHA is a universal, zero-cost collision target since every git repo can produce it trivially), so it generalizes across arbitrary victim stacks, not just one.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true`, and has (or will have) a `Commit` row with the colliding SHA as `next_commit_to_deploy`, with no prior successful status. Attacker cost is trivial: create/own a public GitHub repo (free), configure a webhook (standard GitHub feature they control since they own the repo), and push the empty-tree commit (`git commit-tree` with no files, or reference an existing common object) to get GitHub to fire a real signed `status` event, or replicate the signature themselves since they know their own `webhook_secret`. No Shipit credentials, session, or API token are needed. This is a low-cost, repeatable attack limited only by knowing/guessing a target commit SHA that also exists in a victim stack; the empty-tree SHA is a particularly reliable and universal target since it exists in effectively every git repository.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to only commits belonging to the stack(s)/repository named in the verified webhook payload, e.g. resolve the target repository from `params.dig('repository','full_name')` (or equivalent authenticated context) and join through `Stack` before selecting `Commit` rows:
```ruby
def process
  Commit.joins(:stack).merge(Stack.where(repository: repository_from_payload)).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
More generally, ensure every webhook handler that mutates records by content-derived identifiers (SHA) also constrains by the authenticated repository identity established during signature verification, not by SHA alone.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook for one repo must not trigger deploy for another stack's commit sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_deployment: true)
  shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904'
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: 'empty tree')
  victim_stack.update_column(:undeployed_commits_count, 1) # simulate next_commit_to_deploy

  attacker_repo_owner = 'attacker-org'
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker-org/own-repo', 'owner' => { 'login' => attacker_repo_owner } }
  }.to_json

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature genuinely valid for attacker's own repo/secret

  assert_no_difference('Deploy.count') do  # EXPECTED after fix; currently this FAILS, proving the vuln
    post :create, body: payload, as: :json
    request.headers['X-Github-Event'] = 'status'
  end

  assert_not victim_commit.reload.success?, "victim commit state must not be affected by attacker-owned repo's status webhook"
end
```
Assert both sides of the binding explicitly: `payload['repository']['full_name']` (`attacker-org/own-repo`) must equal `victim_commit.stack.repository.full_name` (`shopify/shipit-engine` or whichever the fixture stack repo is) before the mutation is allowed — the test demonstrates they currently diverge and the deploy is still triggered.
