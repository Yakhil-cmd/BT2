### Title
Stale `assocKnownBadUnits`/`known_bad_joints` entry can permanently shadow a legitimate unit sharing the same hash (unit-hash excludes authentifiers) - ([File: joint_storage.js], [File: object_hash.js])

### Summary
Obyte's unit-acceptance pipeline caches rejected units in an in-memory map keyed by the unit's `unit` hash, and this hash is computed **without** the unit's authentifiers (signatures). An attacker can craft a bad-signature variant of a legitimate, not-yet-arrived unit that hashes to the exact same value, get it rejected first, poison the cache entry, and thereby cause the real unit's arrival to be silently and permanently treated as "known bad" — with no code path that clears the entry when a correctly signed unit with the same hash is later seen. This mirrors the Zebra `parent_error_map` bug class: a rejection cache keyed by a hash that is decoupled from the data that actually determines validity (witness/authentifier data), never cleaned up on legitimate success.

### Finding Description
The `unit` field (the canonical identifier used everywhere: DAG parent references, `known_bad_joints`, in-memory caches) is computed by `getUnitHash` → `getStrippedUnit`, which includes `content_hash`, `version`, `alt`, `parent_units`, `last_ball`/`last_ball_unit`, `timestamp`, and the authors' **addresses only** — explicitly excluding `authentifiers`: [1](#0-0) 

Because authentifiers (the actual signatures) are stripped out before hashing, two joints with identical content but different (e.g., corrupted or empty) authentifier data hash to the same `unit` value.

When a joint fails validation with a joint-level error, it is written into `known_bad_joints` and the in-memory `assocKnownBadUnits[unit]` map is set: [2](#0-1) 

The gate that all future arrivals of a unit with the same hash pass through is `checkIfNewUnit`, which checks `storage.isKnownUnit` (only true once the unit is actually committed), then `assocUnhandledUnits`, and only then `assocKnownBadUnits[unit]` — if a poisoned entry exists, the callback returns `ifKnownBad(error)` **without any re-validation of the newly submitted (legitimate) unit**: [3](#0-2) 

There is no code path that removes a `unit`-keyed entry from `assocKnownBadUnits` when a subsequent, correctly signed unit with the same hash is validated and committed — the in-memory map is only ever appended to, and the on-disk `known_bad_joints` table is only bulk-wiped as a side effect of archiving descendants of a specific unit: [4](#0-3) 

The DB-backed check used during parent resolution similarly treats a `known_bad_joints` hit as terminal without re-validating the arriving unit: [5](#0-4) 

This is precisely the reported bug class: a rejection is cached against a hash that is not fully bound to the content that determines validity (authentifiers, analogous to Zebra's witness/coinbase data not being bound to the block header hash), and the cache is never invalidated when the canonical/legitimate object with that hash is later seen.

### Impact Explanation
Once poisoned, the real unit with that hash can never be accepted by the affected node through the normal reception path — every future submission (via `post_joint`, `light/post_joint`, or normal broadcast) of the legitimate unit is short-circuited to `ifKnownBad` before validation even runs, and its content is never (re)committed. Any unit that depends on this hash as a parent is also permanently blocked, either directly through `assocKnownBadUnits` propagation via `collectQueriesToPurgeDependentJoints`, or through the `known_bad_joints` DB check in `validateParentsExistAndOrdered`. This yields a durable, targeted denial of confirmation for a specific unit (and its descendants) on the affected node — "a network unable to confirm new units" for that transaction/branch — persisting until the node process restarts (the in-memory map is never evicted or aged out), which is a stronger, more persistent condition than the FIFO-bounded, ~2000-entry stall described in the Zcash advisory.

### Likelihood Explanation
Reachable by any unprivileged unit poster: the attacker only needs the plaintext content of a unit that is about to be broadcast (which is often predictable/observable, e.g., a wallet's own next payment, or any unit whose content an attacker can construct in advance) and needs their bad-signature variant to be processed by the target node before the real one. No special privileges, hub/peer trust, or protocol-level attack is required beyond normal unit submission, which is squarely in the unit-validation surface reachable from a single posted unit.

### Recommendation
- Ensure the identifying hash used for negative caching (`assocKnownBadUnits`, `known_bad_joints`) cannot be satisfied by a unit whose authentifiers are invalid while a differently-authenticated unit with genuinely correct signatures exists for the same hash — at minimum, do not treat a hit in `assocKnownBadUnits`/`known_bad_joints` as terminal without re-validating the actually-arriving payload's authentifiers/signature against the address's definition when the cached failure reason was specifically an authentifier/signature failure.
- Alternatively/additionally, remove any stale `unit`-keyed bad entry as soon as a unit with that hash is legitimately validated and requested for storage, so a poisoned entry cannot shadow a later valid arrival.
- Add bounded eviction (size/time-based) for `assocKnownBadUnits`/`known_bad_joints`, mirroring the fix direction taken for GHSA-8gxx: remove the "known bad" mark for a hash once a corresponding valid unit successfully commits.

### Proof of Concept
1. Attacker observes (or predicts) the full content of a legitimate unit `U` that the victim's own wallet/AA is about to construct and broadcast (content is deterministic given inputs the attacker can often infer, e.g., known outputs/definitions/timestamp bucket).
2. Attacker builds a joint with identical `getStrippedUnit`-relevant fields (`content_hash`, `version`, `alt`, `authors` addresses, `parent_units`, `last_ball`, `last_ball_unit`, `timestamp`) — this guarantees the same `unit` hash per `object_hash.js` `getUnitHash`/`getStrippedUnit` — but with a corrupted/garbage `authentifiers` value, causing signature verification to fail.
3. Attacker submits the poisoned joint to the target node first (e.g., via `post_joint`). Validation fails with a unit-level error; `purgeJointAndDependenciesAndNotifyPeers` → `joint_storage.purgeJointAndDependencies` inserts into `known_bad_joints` and sets `assocKnownBadUnits[U] = error`.
4. Legitimate `U` (correct authentifiers) is submitted afterward. `checkIfNewUnit` sees `assocKnownBadUnits[U]` set and returns `ifKnownBad(error)` before any validation of the real content occurs — the legitimate unit is never processed, and this state persists indefinitely (until node restart), blocking `U` and any dependents from ever confirming on that node.

		return callbacks.ifKnownBad(error);

	});
}

				delete assocUnhandledUnits[unit];
				conn.release();
				if (onDone)
					onDone();

		});
	});
}
