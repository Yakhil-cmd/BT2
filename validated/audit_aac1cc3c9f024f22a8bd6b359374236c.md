### Title
Unauthenticated `TaskId → ParaId` sovereign-account mapping allows unprivileged users to redirect Coretime revenue/renewal debits to unrelated parachains - (File: `system-parachains/coretime/coretime-kusama/src/coretime.rs`, `system-parachains/coretime/coretime-polkadot/src/coretime.rs`)

### Summary
`SovereignAccountOf::maybe_convert` blindly converts any caller-chosen `TaskId` (`u32`) into `Location::new(1, [Parachain(id)])` and derives that location's sovereign account, with no check that the caller actually owns/controls that `ParaId`. Since `TaskId` is a free-form value supplied by any signed user via `pallet_broker::assign` (the region owner picks the `task`), an attacker can set `task` equal to a victim parachain's `ParaId` and, in combination with `enable_auto_renew`, cause `pallet_broker` to route revenue credits/renewal debits against the victim's sovereign account instead of an account the attacker actually controls.

### Finding Description
`SovereignAccountOf` is configured as `pallet_broker::Config::SovereignAccountOf` in both coretime runtimes: [1](#0-0) [2](#0-1) 

The comment `// Currently all tasks are parachains` documents the (unchecked) assumption baked into the conversion. `pallet_broker` treats `TaskId` as an opaque identifier that a Region owner assigns via the `assign` extrinsic (a signed, unprivileged call available to whoever owns a purchased/leased Region — confirmed by the emulated test using `CoreAssignment::Task(id)` with arbitrary integers): [3](#0-2) 

Nothing in the runtime configuration (`AdminOrigin: EnsureRoot<AccountId>` only gates pallet-admin calls like `configure`/`reserve`, not `assign`/`enable_auto_renew`) requires the caller to prove control of the `ParaId` encoded in `task`. Because `SovereignAccountOf` is exactly the type `pallet_broker` uses to determine which account to credit with InstaPool/renewal revenue and which account to auto-debit for `enable_auto_renew` renewal charges, an attacker who owns any Region can:
1. Call `Broker::assign(region_id, task = victim_para_id, finality)` — succeeds because ownership of the *region*, not of the `task`/`ParaId`, is checked.
2. Call `Broker::enable_auto_renew(core, ...)` on that region/core.
3. On each renewal cycle, `pallet_broker` computes `SovereignAccountOf::maybe_convert(victim_para_id)` and attempts to withdraw the renewal price from that derived sovereign account — the victim parachain's own sovereign account on the Coretime chain — without the victim's consent, and independent of who actually triggered/owns the renewing region.

The existing protections (`AdminOrigin`, XCM barriers, weight/fee checks) are irrelevant here because the entire flow is a normal signed extrinsic sequence on the Coretime parachain; no XCM or cross-chain forgery is needed. The only missing check is binding `TaskId` to proof of `ParaId` ownership (e.g., via a signed origin conversion using `EnsureOriginWithArg`/`ParaId` XCM origin instead of an arbitrary `u32`).

### Impact Explanation
Any signed user who can afford to purchase or otherwise come to own a single Coretime Region can force repeated, unauthorized debits from an arbitrary parachain's sovereign account balance on the Coretime chain whenever that parachain keeps funds there (which parachains routinely do to pay for their own core purchases/renewals). This violates the core invariant that "user-controlled assets must remain fully backed and cannot be stolen ... " for the victim parachain's Coretime-chain sovereign account, and can also be used to grief/drain funds intended for legitimate renewal purposes or misattribute InstaPool revenue shares to a parachain that never contributed the underlying Region.

### Likelihood Explanation
Preconditions are modest: the attacker needs no special privilege, just enough funds to acquire one Region (via `purchase`/`renew`/secondary transfer) and to call two ordinary, permissionless extrinsics (`assign`, `enable_auto_renew`). It is fully repeatable across many regions/cores and is deterministic given any known/target `ParaId`. The main open uncertainty (not verifiable from this repo, since `pallet_broker`'s internal debit/credit logic lives in the external `pallet_broker` crate, not vendored here) is the exact accounting behavior of `enable_auto_renew`/`claim_revenue` invoking `SovereignAccountOf`; but the runtime-side root cause — an authorization-free `TaskId`→`ParaId` mapping — is confirmed in this codebase.

### Recommendation
Do not allow an arbitrary caller-chosen `u32` to silently alias to any parachain's sovereign account. Either (a) restrict `assign`'s `task` to values whose ownership can be verified against the caller (e.g., require the call to originate from that parachain's own XCM/sovereign origin, similar to how remote `Transact` calls are authenticated elsewhere in `coretime.rs`), or (b) decouple "task" bookkeeping from "sovereign account for payment," e.g., require a separate, explicitly-authorized `payee`/owner field per Region-to-task assignment (as `pool`'s `payee` parameter already does) rather than deriving payment accounts implicitly from `TaskId`.

### Proof of Concept
Rust integration test (coretime-kusama runtime, `pallet_broker` present) plan:
```rust
#[test]
fn attacker_can_redirect_autorenew_debit_to_unrelated_parachain_sovereign_account() {
    // Setup: start sales, let ATTACKER purchase a Region.
    // victim_para_id = some real ParaId (e.g. 2000) NOT controlled by ATTACKER.
    // 1. Fund victim's sovereign account (SovereignAccountOf::maybe_convert(victim_para_id)) with balance B.
    // 2. As ATTACKER (signed, non-privileged), call Broker::assign(region_id, task = victim_para_id, Finality::Provisional).
    //    assert_ok!(...) -- no check ties `task` to caller identity.
    // 3. As ATTACKER, call Broker::enable_auto_renew(core, ...).
    //    assert_ok!(...)
    // 4. Advance to next renewal timeslice / call on_initialize to trigger auto-renewal processing.
    // 5. Assert victim's sovereign account balance decreased by the renewal price,
    //    even though ATTACKER (not victim) owns/controls the region and initiated the renewal:
    //    assert!(Balances::free_balance(&victim_sovereign_account) < B);
    //    assert_eq!(Balances::free_balance(&attacker_account) unchanged by the renewal charge);
}
```
Expected result if the bug is real: the victim's sovereign account balance is debited despite the victim never calling `assign`/`enable_auto_renew`, confirming funds move based purely on an attacker-chosen `TaskId` colliding with the victim's `ParaId`.
