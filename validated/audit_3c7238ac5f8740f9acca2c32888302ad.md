### Title
Webhook signature scope bound to `repository.owner.login`, but repository resolution keyed on unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The bug class in the report is "a value is trusted/used without matching the scope the verification was actually performed against." In Shipit's webhook pipeline, the HMAC signature is validated using the GitHub organization whose secret is selected from `repository.owner.login` (or `organization.login`), but the actual repository whose stacks are mutated is chosen from a *different* JSON field, `repository.full_name`, which is never cross-checked against the signing organization.

### Finding Description
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to use for HMAC verification from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login` (falling back to `organization.login`) and is used only to pick which configured org's secret authenticates the request via `Shipit.github(organization: repository_owner)` / `GitHubApp#verify_webhook_signature`, keyed per-organization in `github_app_config`: [3](#0-2) 

Once the signature check passes, every webhook handler resolves the target stacks/repositories independently, using an entirely different field, `repository.full_name`: [4](#0-3) 

Nothing re-validates that `repository.full_name`'s owner segment equals `repository.owner.login` (the field that determined which org's secret authenticated the request). Because the JSON body is otherwise attacker-controlled (this is a public POST endpoint, `skip_before_action :verify_authenticity_token`), an operator/admin who legitimately controls **one** organization's GitHub App/webhook secret in a multi-organization Shipit deployment (`Shipit.github_organizations`, `TOP_LEVEL_GH_KEYS`) can craft a payload where:
- `repository.owner.login` = `"org-they-control"` (so the HMAC computed with that org's real `webhook_secret` validates), while
- `repository.full_name` = `"victim-org/victim-repo"` (so the handler, e.g. `PushHandler`, `StatusHandler`, resolves and mutates a completely different organization's stack).

The equality that should hold is:
`organization whose webhook_secret authenticated the request == organization owning the repository the handler writes to`

but the code only checks the former and blindly trusts the latter from the same signed-but-attacker-authored body. [5](#0-4) 

### Impact Explanation
Any handler that mutates state based on `repository.full_name` becomes reachable across organizational boundaries by anyone who holds a valid webhook secret for *any* one org configured on the same multi-tenant Shipit instance. This includes triggering `Repository.from_github_repo_name(...).stacks` sync jobs (`PushHandler`) and posting forged commit statuses against a victim organization's commits — the latter can satisfy `ci.require` gates defined in the victim's `shipit.yml` and enable an unauthorized deploy of unvetted code, which the rules classify as Critical ("an unauthorized deploy, rollback or merge"). At minimum this is a cross-repository write into stacks the attacker does not own or have permission to touch.

### Likelihood Explanation
This requires the attacker to already control one legitimate GitHub App / webhook secret configured in `secrets.github` for the Shipit install (i.e., they are a trusted org owner for at least one tenant, but not for the victim). In single-organization Shipit deployments this is not exploitable since there is only one webhook secret. In the documented multi-organization configuration (`config/secrets.development.shopify.yml`, `TOP_LEVEL_GH_KEYS`), it is directly reachable by any org admin who can configure a GitHub App and legitimately send webhooks, without needing repository write access to the victim's GitHub repo, an `ApiClient` token, or a Shipit session.

### Recommendation
After signature verification, re-derive the organization from `repository.full_name` (or `organization.login` used by handlers) and reject the webhook if it does not match `repository_owner`/the org whose secret validated the signature. Alternatively, scope `Repository.from_github_repo_name` lookups to only repositories belonging to the authenticated organization.

### Proof of Concept
1. Attacker legitimately controls Org A in a multi-org Shipit deployment and knows Org A's `webhook_secret`.
2. Attacker crafts a `push` (or `status`) webhook JSON body with:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `after` set to an attacker-chosen sha, or (for `status`) `state: "success"`, `context: "<required-ci-check>"`, `sha: "<victim-commit-sha>"`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(org_a_webhook_secret, body)` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"org-a"`, fetches Org A's `GitHubApp`, and the HMAC validates successfully.
5. The dispatched handler (e.g. `StatusHandler`/`PushHandler`) resolves `repository_name` from `repository.full_name` → `"victim-org/victim-repo"` and mutates the victim organization's stack (e.g., records a forged passing status, satisfying required checks for deploy) — despite the request never having been authenticated by victim-org's own webhook secret.

*Note: I could not open `status_handler.rb`'s exact source in this session (index truncation), so the status-forgery step is inferred from `webhooks_controller_test.rb`'s described behavior (`Status`, `sha`, `state`, `context`) and the shared `Handler#repository_name` resolution logic; a Devin session with full file access should confirm the exact `Status` creation logic in `app/models/shipit/webhooks/handlers/status_handler.rb` before treating this as fully verified.*

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
