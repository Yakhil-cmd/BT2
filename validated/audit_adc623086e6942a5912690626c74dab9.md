## Title
Single-step, unchecked `address_definition_change` can permanently freeze address funds — analog of "Loss of Veto Power" ([File: validation.js])

### Summary
The original finding flags that Nouns Governor's `updateVetoer()`/`initialize()` let a critical control address be replaced in one step with no validation that the new value is a real, controllable address, risking irreversible loss of authority. Ocore's address-definition-change mechanism has the analogous weakness: any address owner (an ordinary unit poster) can atomically replace the definition that controls signing rights over their address by posting an `address_definition_change` message, and the protocol only checks that the new value has the *format* of a valid chash — never that the poster actually knows/controls a definition matching it, and there is no two-step "propose then confirm-with-signature" process.

### Finding Description
`validateInlinePayload()` in `validation.js` validates the `address_definition_change` message payload: [1](#0-0) 

The only check on the new value is `isValidAddress(payload.definition_chash)` — a pure base32/checksum format check, not proof that the definition behind that chash is known to anyone, let alone the address owner. This mirrors the report's core complaint: "lack of zero address check" (here: lack of any check that the new value corresponds to a definition the sender can actually reveal/control).

The change takes effect in a single unit/transaction — there is no intermediate "pending" state that must be separately confirmed with the actual definition before it becomes binding, unlike a proper 2-step ownership-transfer pattern: [2](#0-1) 

Once this unit becomes part of the DAG and stabilizes, `validateAuthor()`'s pending-definition-change checks (`checkNoPendingChangeOfDefinitionChash`) require any subsequent unit from that address to be signed against the *new* `definition_chash`: [3](#0-2) 

If the new `definition_chash` was set to a value whose actual definition array is never revealed (e.g., operator typo, wallet/AA-script bug that computes the value incorrectly, or a malicious dApp tricking a user into signing such a message), the address permanently loses the ability to produce a valid `author.definition` matching that chash — the funds at the address become unspendable forever. This is the direct analog of "losing veto power unintentionally": a single, irreversible, insufficiently-validated address-control change.

### Impact Explanation
Any address (regular wallet or shared/multisig address) that posts a definition change to an incorrect/unrevealable chash permanently loses spending capability — a concrete, unrecoverable freezing of funds, matching the "AA fund loss or freezing" / "loss of authority" impact class the report describes for veto power.

### Likelihood Explanation
This is directly reachable by any unprivileged unit poster composing an `address_definition_change` message themselves (`composeDefinitionChangeJoint` in `composer.js`); no privileged role or network condition is required — only a single mistaken or maliciously-crafted `definition_chash` value. [4](#0-3) 

### Recommendation
- Require that units performing `address_definition_change` also reveal (or later separately reveal and get verified before the change takes final effect) the actual new definition array, so the protocol/wallet can confirm the new chash is backed by a definition the sender actually possesses, before the old definition is discarded irreversibly.
- Consider a two-step change: (1) announce new `definition_chash`, (2) require the first unit signed under the new definition (which itself already validates chash match) to occur within a bounded window, otherwise allow reverting to the previous definition — reducing risk of instant, irreversible lockout from a single bad message.

### Proof of Concept
1. Address `A` currently controlled by definition `D0`.
2. Owner (or a compromised/buggy client) composes and posts `address_definition_change` with `definition_chash = X`, where `X` is a syntactically valid chash for which nobody has (or will ever reveal) the corresponding definition array `D1` (`objectHash.getChash160(D1) === X`).
3. `validateInlinePayload` accepts this because `isValidAddress(X)` passes — no check that `D1` is known/controllable.
4. Once stable, any future unit from `A` must be signed with a definition matching `X` (per `checkNoPendingChangeOfDefinitionChash` / `validateDefinition` in `validation.js`), which can never be produced.
5. Address `A` and all its funds are permanently frozen.
