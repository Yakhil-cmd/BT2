### Title
Unbounded synchronous recursion in `evaluate()` for address/asset definitions can cause a stack overflow denial-of-service - ([File: definition.js])

### Finding Description
The Lighthouse bug being referenced is a stack overflow caused by an unbounded recursive tree-walk (`filter_block_tree`) that lacked a depth guard against a user-influenced structure. The analogous unguarded recursive tree-walk in ocore is the `evaluate()` closure inside `validateDefinition()` in `definition.js`, which recursively walks an address/asset spending-condition tree (`arrDefinition`) supplied directly by an unprivileged unit poster (e.g., inside an `address_definition_change` message, a new address's initial `definition`, or an asset's `issue_condition`/`transfer_condition`). [1](#0-0) 

For composite operators (`or`, `and`, `r of set`, `weighted and`), `evaluate()` recurses into each child element via `async.eachSeries`: [2](#0-1) 

Unlike the oscript/AA formula evaluators (`formula/evaluation.js` and `formula/validation.js`), which explicitly guard against native call-stack overflow with an incrementing `depth` counter that aborts at `depth > 100`, and additionally interrupt the call stack every 100 iterations via `setImmediate`: [3](#0-2) [4](#0-3) 

...`validateDefinition()`'s `evaluate()` in `definition.js` has **no depth counter and no `setImmediate`/stack-unwinding mechanism**. It only tracks a flat `complexity` and `count_ops` counter that is incremented per node visited, bounded by `constants.MAX_COMPLEXITY`/`MAX_OPS`, but this does not bound *nesting depth* — a definition can be built as a long linear chain of single-child wrapping ops (e.g., `not(not(not(...sig...)))`, or nested `address` references pointing to other addresses that recursively resolve, or a deeply nested `and`/`or` chain each with only the minimum required children) so that each unit of complexity corresponds to one additional stack frame. Because `async.eachSeries`'s iteratee is invoked synchronously when there is no I/O in between (branches such as `sig`, `hash`, `not`, `cosigned by` call `cb()` synchronously), the recursive calls build up on the native V8 call stack rather than yielding to the event loop, exactly the "unbounded recursive tree walk without depth check" class of bug in the report. [5](#0-4) 

The `address` case additionally recurses into other on-chain address definitions (`readDefinitionByAddress` → `evaluate(arrInnerAddressDefinition, ...)`), compounding depth from cross-referenced definitions, not just the immediate JSON tree: [6](#0-5) 

The sibling function `validateAuthentifiers`'s inner `evaluate()` (used both for authentifier evaluation and asset-condition evaluation) has the identical unguarded recursion pattern: [7](#0-6) 

### Impact Explanation
An attacker (an unprivileged unit poster) can craft a new address definition or asset issue/transfer condition with deep nesting (e.g., long chains of `not`, or `and`/`or`/`r of set` trees skewed to maximize depth for a given complexity budget) and post it on-chain, or embed it in an `address_definition_change`. When any full node subsequently validates a unit using or referencing that address/asset (including all future spends from that address, and initial validation of the definition-bearing unit itself), the node calls `validateDefinition`/`validateAuthentifiers`, which recurses synchronously deep enough to throw `RangeError: Maximum call stack size exceeded`. Because ocore's `catchBadWords`/`throwError` conventions in this codebase generally do not gracefully catch native `RangeError`s inside these largely-uncaught synchronous call chains, this crashes (or hangs, depending on execution context) the validating node process. Since every node that must validate the poisoned unit — or later spends from the compromised address — hits the same code path, this can be used to crash multiple/all full nodes that see the unit, i.e., a network-wide denial of service: nodes become unable to validate/confirm new units referencing the malicious definition, which maps to the "network unable to confirm new units" outcome required by the validation criteria.

### Likelihood Explanation
Likelihood is high for a determined attacker: crafting a linear or near-linear recursive definition tree is straightforward JSON construction, requires no privileged role, and only needs to stay under `MAX_COMPLEXITY`/`MAX_OPS` while maximizing recursion depth (e.g. `not(not(not(...)))` costs 1 complexity/op per level, so it can reach whatever depth the complexity ceiling allows, likely far exceeding V8's default stack-frame limit of roughly 10,000–15,000 for this kind of nested-closure/async recursion). The formula evaluator was already hardened against exactly this scenario (explicit `depth > 100` check plus periodic `setImmediate`), which shows the project is aware of this bug class in one subsystem but the fix was not carried over to `definition.js`'s `evaluate()` functions, which sit on a directly attacker-reachable input path (unit posting / definition validation).

### Recommendation
Add the same defenses used in `formula/validation.js` and `formula/evaluation.js` to `definition.js`'s two `evaluate()` closures (`validateDefinition`'s and `validateAuthentifiers`'s):
1. Track an explicit recursion `depth` parameter and reject with an error once it exceeds a safe bound (e.g. 100), independent of complexity/ops counters.
2. Periodically interrupt the call stack (e.g. every N recursive calls) via `setImmediate`/`setTimeout` so that long synchronous recursive chains don't build up on the native stack.
3. Ensure both the authoring-time validation (`validateDefinition`) and every-spend validation path (`validateAuthentifiers`, `evaluateAssetCondition`) enforce this bound, including recursion through cross-referenced `address` definitions.

### Proof of Concept
Construct an address definition consisting of a deeply right-nested `not` chain wrapping a single `sig`, e.g. (conceptually):
```
["not", ["not", ["not", ... ["sig", {pubkey: "..."}] ... ]]]
```
nested to a depth on the order of several thousand (well under `MAX_COMPLEXITY`/`MAX_OPS` limits, since each `not` costs only 1 unit of complexity/op). Post this as a new address's `definition` (or via `address_definition_change`) in a unit. When any node calls `validateDefinition`/`validateAuthentifiers` on this definition — at initial unit validation, and again on every subsequent unit spending from or referencing that address — the synchronous recursive `evaluate()` chain in `definition.js` will exhaust the V8 call stack and throw an uncaught `RangeError: Maximum call stack size exceeded`, crashing or destabilizing the validating node.
