### Title
Webhook authenticity is bound to an attacker-supplied organization field, allowing forged team-membership events to escalate into `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The report's bug class is: a state mapping is trusted for an authorization decision, but one code path that mutates that state bypasses the mechanism that is supposed to keep it consistent (the `LivenessGuard` delete-on-removal logic). The reachable analog in this repository is in the webhook pipeline: the *organization used to select the HMAC secret that authenticates a webhook* is read from the same untrusted JSON body that the corresponding event handler later uses to decide *what team/stack/user state to mutate*, and the signature check silently no-ops when that organization has no `webhook_secret` configured. This breaks the intended binding "organization whose secret authenticated the request" == "organization whose state the handler is allowed to write."

### Finding Description
`WebhooksController#verify_signature` derives the organization used to authenticate a webhook purely from the incoming JSON payload: [1](#0-0) 

That organization is then used to look up the `GitHubApp` instance and verify the HMAC signature: [2](#0-1) 

Crucially, `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the organization's `webhook_secret` is not configured: [3](#0-2) 

For a `membership` event (which carries no `repository` key, only `organization.login`), a forged payload that sets `organization.login` to any organization configured in this Shipit instance without a `webhook_secret` will pass `verify_signature` regardless of the `X-Hub-Signature` header supplied. The request then reaches `MembershipHandler#process`, which creates/looks up an arbitrary GitHub user by login and adds them to the team unconditionally: [4](#0-3) 

That `Team`/`Membership` state is exactly what `User#authorized?` trusts to decide application access: [5](#0-4) 

and what `Authentication#force_github_authentication` enforces before granting access to the Shipit UI/API: [6](#0-5) 

So the invariant "membership rows only reflect real GitHub team membership, verified via a correctly-authenticated webhook" — the analog of "removed owners must not be present in `lastLive`" — can be violated: a forged, unauthenticated (or wrongly-authenticated) `membership` webhook can insert a `Membership` row for an attacker-controlled GitHub login into a team that is part of `Shipit.github_teams`, exactly as the `LivenessModule` bypasses `LivenessGuard`'s bookkeeping and leaves the guard's authorization state inconsistent with reality.

### Impact Explanation
An attacker who can forge a `membership`/`added` webhook against an organization that lacks a configured `webhook_secret` can insert themselves (or any GitHub login they control) as a member of a `Team` matching `Shipit.github_teams`. Logging in through the normal GitHub OAuth flow afterward causes `User#authorized?` to return `true`, granting full access to Shipit's stacks, deploy/rollback controls, and API — this is an authorization escalation into `Shipit.github_teams`, matching the High-impact category (escalation into `Shipit.github_teams` authorization), and can enable an unauthorized deploy/rollback once inside.

### Likelihood Explanation
This requires that at least one organization configured in the deploying instance has no `webhook_secret` set — `webhook_secret` is an optional, per-organization config value in `GitHubApp`, not a value the engine enforces as mandatory, so this is a realistic and in-scope condition rather than a "host app not mounting the engine as documented" scenario. Given such a configuration, exploitation requires no privileged token, no repository write access, and no session — only knowledge of the organization login and the ability to POST to the public webhook endpoint.

### Recommendation
- Make `webhook_secret` mandatory for every configured organization (fail closed instead of `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`).
- For handlers like `MembershipHandler`, cross-check that the organization/team referenced in the payload actually corresponds to the organization whose secret validated the request, rather than trusting the payload's own `organization.login`/`team` fields independently of the authenticated organization context.

### Proof of Concept
1. Identify (or configure a test instance with) an organization entry in `Shipit.github` that has no `webhook_secret` set.
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
   ```json
   {
     "action": "added",
     "team": { "id": <id-of-a-team-in-Shipit.github_teams>, "name": "T", "slug": "t", "url": "https://x" },
     "organization": { "login": "<org-without-webhook_secret>" },
     "member": { "login": "attacker-github-login" }
   }
   ```
   with any (even invalid) `X-Hub-Signature` header.
3. `verify_signature` resolves `Shipit.github(organization: "org-without-webhook_secret")`, calls `verify_webhook_signature`, which returns `true` unconditionally (no secret configured), so the request is processed.
4. `MembershipHandler#process` creates/loads `User` `attacker-github-login` and adds it to the team via `team.add_member(member)`.
5. `attacker-github-login` logs into Shipit via GitHub OAuth; `User#authorized?` now returns `true` because of the forged `Membership` row, granting access to `Shipit.github_teams`-gated stacks and deploy/rollback actions.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
