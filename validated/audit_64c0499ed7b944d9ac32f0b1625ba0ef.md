### Title
Webhook signature verification key is selected using an unauthenticated payload field decoupled from the field used to resolve the target repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and thus which `webhook_secret`) to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* raw JSON body. All downstream event handlers, however, resolve the actual `Repository`/`Stack` to act on using a *different* field from the same body: `repository.full_name`. Because a genuine GitHub-issued payload always keeps these two fields consistent, but a forged payload does not have to, the two fields can be made to disagree, breaking the binding "organization whose secret authenticated the request == repository the request acts on."

### Finding Description
`verify_signature` derives the verification key from the body itself, before the body has been authenticated: [1](#0-0) [2](#0-1) 

`repository_owner` is only `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). This value selects the `GitHubApp` instance and its `webhook_secret` via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Shipit explicitly supports multiple, independently-configured GitHub App entries, one per organization key, each carrying its own `webhook_secret`, `app_id`, `private_key`, etc. (see the documented multi-tenant fixture): [4](#0-3) 

The signature check itself only proves the raw body was HMAC-signed with *whatever* `webhook_secret` corresponds to `repository.owner.login`: [5](#0-4) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the same raw, attacker-controlled JSON to the event handlers: [6](#0-5) 

Handlers, however, resolve the actual `Repository` to act on using `repository.full_name`, not `repository.owner.login`: [7](#0-6) 

`Repository.from_github_repo_name` simply splits this string on `/` and looks the repo up by owner/name, with no cross-check against the `repository.owner.login`/`organization.login` value that gated signature verification: [8](#0-7) 

The binding that should hold is:
`organization whose webhook_secret validated the HMAC` == `organization that owns the repository the handler mutates (via repository.full_name)`

In a multi-tenant deployment (one Shipit instance, several onboarded organizations, each with its own GitHub App/`webhook_secret`), an attacker who is a legitimate admin of Organization A's GitHub App can compute a valid `X-Hub-Signature` for Organization A's `webhook_secret`, while setting `repository.owner.login`/`organization.login` to `"OrgA"` (so verification passes) and `repository.full_name` to `"OrgB/victim-repo"` (a repository belonging to a completely different, unrelated tenant Organization B). `verify_signature` never inspects `full_name`, and the handler never inspects `owner.login`; the two checks are simply looking at different, independently-forgeable parts of the same unauthenticated JSON body.

### Impact Explanation
Depending on which event type is sent, this crosses the "cross-repository writes" boundary explicitly called out as Critical impact:
- `pull_request` (`opened`) handler can create/mutate a `ReviewStack` for Organization B's repository from a payload only authenticated for Organization A.
- `push` and `status` handlers can enqueue `GithubSyncJob`/create commit `Status` records against Organization B's `Stack`, corrupting deploy/commit state (e.g. false CI status, spoofed commits) for a repository/organization the attacker has no legitimate relationship with.
- `membership` handlers create `Team`/`User` records keyed off `organization.login`, which is more consistent, but PR/push/status paths that key off `repository.full_name` are exposed.

This is a cross-tenant repository-state write performed with a webhook signature that was never issued for, or scoped to, the target repository's organization — i.e., an unauthorized write across the tenant boundary that Shipit's multi-org GitHub App feature is supposed to enforce.

### Likelihood Explanation
Exploitability requires:
1. The deployment to use the multi-organization GitHub App configuration (an explicitly supported, documented mode — not a misconfiguration).
2. The attacker to control (or know) the `webhook_secret` for at least one onboarded organization's GitHub App — realistic for any tenant admin who registered their own App in GitHub and supplied Shipit with the secret.
3. The `webhooks` endpoint to be reachable directly (it is a public, unauthenticated HTTP endpoint by design, since GitHub itself calls it without a Shipit session).

No repository write access, session, or `ApiClient` token is required — only knowledge of one tenant's own webhook secret, which that tenant legitimately possesses. This is a realistic attacker for the multi-tenant deployment model.

### Recommendation
Bind the verification key to the exact same field used for repository resolution:
- Compute `repository_owner` from `repository.full_name` (split and take the owner) rather than `repository.owner.login`, or
- After verifying the signature, re-validate that `repository.owner.login` (or `organization.login`) equals the owner segment of `repository.full_name` before dispatching to handlers, rejecting the request (422) on mismatch.
- More robustly, once the target `Repository`/`Stack` is resolved in a handler, assert that its `owner` matches the organization whose `webhook_secret` validated the request, and reject otherwise.

### Proof of Concept
1. Deploy Shipit with `secrets.github` containing two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who knows `OrgA`'s `webhook_secret` (e.g., a legitimate admin of OrgA's own GitHub App), craft a `pull_request` "opened" payload:
```json
{
  "action": "opened",
  "number": 1,
  "pull_request": { "head": { "ref": "attack-branch" }, "labels": [] },
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "sender": { "login": "attacker" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: pull_request`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
5. `PullRequest::OpenedHandler#repository` resolves `Shipit::Repository.from_github_repo_name("OrgB/victim-repo")` (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`) — a repository entirely unrelated to the org whose secret signed the request — and, if provisioning is enabled for that repository, creates/updates a `ReviewStack` for OrgB's repository using a signature that was never issued for OrgB.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
