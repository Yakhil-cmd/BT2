### Title
Cross-repository commit status forgery via SHA-only lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the webhook's `repository.full_name` matches the commit's owning `Stack`/`Repository`. Any onboarded, low-privilege repository owner who can trigger a genuinely-signed `status` webhook for a commit whose SHA collides with a commit tracked by a different repository's stack (trivially achievable via a fork, since git commit SHAs are content-addressed and identical across forks until history diverges) can write arbitrary commit status/state/description/target_url onto that victim commit.

### Finding Description
The claimed binding is: `payload.dig('repository','full_name') == commit.stack.repository.full_name` must hold before `commit.create_status_from_github!(params)` executes. Tracing the code shows this equality is never checked.

- `Handler#initialize` only parses params against the `ExplicitParameters` schema; it does not enforce any repository binding itself. [1](#0-0) 
- The `Handler` base class *does* provide a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)`, and `PushHandler` correctly uses it: `stacks.not_archived.where(branch:).find_each { ... }`. [2](#0-1) [3](#0-2) 
- `StatusHandler#process`, however, never calls `stacks` or checks `repository_name` at all — it performs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, a global, unscoped lookup across every stack/repository in the Shipit instance. [4](#0-3) 
- `WebhooksController#create` dispatches to handlers without any per-event branch/repository gate of its own — it just calls `handler.call(params)` for each registered handler for the event. [5](#0-4) 
- `verify_signature` only validates the HMAC signature against `Shipit.github(organization: repository_owner)`, i.e., it confirms the payload was genuinely sent by GitHub for *some* org/repo Shipit knows about — it does not confirm the payload's repository matches the commit it will affect. [6](#0-5) 
- `Commit#create_status_from_github!` unconditionally writes the status using the commit's own `stack_id`, trusting whatever handler called it: `statuses.replicate_from_github!(stack_id, github_status)`. [7](#0-6) 

Exploit flow: An attacker who owns/controls a repository that is onboarded to the same Shipit instance (any tenant with a tracked stack) forks a victim's tracked repository (or otherwise obtains a commit with an identical SHA to one in the victim's tracked branch — trivial via fork, since SHA1 is computed from tree+parents+commit metadata and is identical until the fork's history diverges). The attacker then sets a commit status on that SHA in their *own* repo via the standard GitHub Statuses API (an action fully within their own repo permissions, requiring no Shipit secret). GitHub delivers a `status` webhook for the attacker's own repository, correctly signed by GitHub for that installation, which passes `verify_signature`. `StatusHandler#process` then matches `Commit.where(sha: params.sha)` — which returns the victim's `Commit` record (belonging to a completely different stack/repository) — and writes the attacker-controlled state/description/target_url onto it via `create_status_from_github!`.

No existing guard closes this gap: `verify_signature` proves origin-authenticity of the webhook only, not repository-binding of its payload to the record being mutated; the `ExplicitParameters` schema only validates the acceptable value shapes; and the branch-tracking filter that exists in `PushHandler` (and the referenced controller test about "untracked branches") governs stack *creation* on push events, not status attribution, and is never applied to `StatusHandler`.

### Impact Explanation
An attacker can write forged commit status (`state`, `description`, `target_url`, `context`) onto a commit belonging to a stack/repository they do not own or control, provided a SHA collision (fork-derived, not requiring a cryptographic break). Since Shipit's `deployable?`/`blocked?`/`schedule_continuous_delivery` logic and CI-gating for deploys and merges consult commit `status`, this can be used to mark a victim's commit as passing CI ("success") to unblock a deploy/merge that should have been blocked, or to mark it as failing to block a legitimate deploy — a cross-tenant integrity/availability issue matching "a payload for one repository mutating another's stack, commit". This is repeatable against any repository tracked by the same Shipit instance whose git history overlaps with a repository the attacker controls (e.g. any public repository, since anyone can fork it).

### Likelihood Explanation
Preconditions: the attacker must own or control at least one repository already onboarded/tracked by the target Shipit instance (a low bar — any Shipit-configured GitHub org/team member or self-service onboarding flow), and the victim repository/commit must be publicly forkable (or otherwise have a SHA the attacker can reproduce, e.g. by forking before divergence). No Shipit secrets, sessions, or API tokens are needed — GitHub itself generates and signs the webhook for the attacker's own repository. This is inexpensive and fully repeatable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the webhook's own repository, mirroring `PushHandler`'s use of `stacks`, e.g. restrict to `Commit.joins(:stack).merge(stacks).where(sha: params.sha)` (using the `stacks`/`repository_name` helper already available on `Handler`) before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (model-level, bypassing controller, no live GitHub):
```ruby
test 'StatusHandler mutates a commit belonging to a different repository than the payload' do
  victim_stack = shipit_stacks(:shipit) # repository e.g. "shopify/shipit-engine"
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'description' => 'forged by attacker',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' }, # different repo/tenant
  }

  assert_equal 'unknown', victim_commit.status.state

  Shipit::Webhooks::Handlers::StatusHandler.new(attacker_payload).process

  victim_commit.reload
  assert_equal 'success', victim_commit.status.state # forged status accepted despite repository mismatch
end
```
This demonstrates the equality `payload.dig('repository','full_name') == victim_commit.stack.repository.full_name` is false (`"attacker/unrelated-repo" != "shopify/shipit-engine"`), yet `create_status_from_github!` still executes and mutates `victim_commit`.
