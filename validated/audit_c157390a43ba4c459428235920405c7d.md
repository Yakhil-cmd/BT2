### Title
Missing Cosigner Authorization Check in Multisig "sign" Request Handler Allows Unauthorized Signing Requests - (File: `wallet.js`)

### Summary
In `wallet.js`, the device-to-device `"sign"` message handler (`handleMessageFromHub`) verifies that the message sender is an authorized cosigner **only** in the `ifRemote` branch of `findAddress`, but performs **no such check** in the `ifLocal` branch, where the private key actually resides on the receiving device.

### Finding Description
The `"sign"` case accepts an unsigned unit and a `signing_path`/`address` from any paired correspondent device (`from_address`), then calls `findAddress(body.address, body.signing_path, callbacks, ...)` [1](#0-0) .

When the requested key lives on the **remote** end (`ifRemote`), the code explicitly enforces that the requester is a listed cosigner of the address before forwarding/serving the request:
```
ifRemote: function(device_address, other_device_addresses){
    if (device_address === from_address)
        return callbacks.ifError("looping signing request ...");
    if (!other_device_addresses.includes(from_address))
        return callbacks.ifError("you are not listed as a cosigner for this address "+body.address);
``` [2](#0-1) 

However, when the key is **local** (`ifLocal`) — i.e. the device processing the message actually controls the signing key for `body.address` — there is no equivalent check that `from_address` is a legitimate cosigner of that address. The check that would enforce this is explicitly commented out:
```
ifLocal: function(objAddress){
    // the commented check would make multilateral signing impossible
    //db.query("SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?", [row.wallet, from_address], function(sender_rows){
    //    if (sender_rows.length !== 1)
    //        return callbacks.ifError("sender is not cosigner of this address");
        callbacks.ifOk();
        ...
        eventBus.emit("signing_request", objAddress, body.address, objUnit, assocPrivatePayloads, from_address, body.signing_path);
``` [3](#0-2) 

This means **any paired correspondent device** (not necessarily a cosigner of `body.address`) can send a `"sign"` request for an address whose signing key is held locally, and the core library will accept it, resolve the local address (via `findAddress`), and emit a `signing_request` event carrying an attacker-crafted unsigned unit (including arbitrary payment outputs) for the local device to sign — with the only remaining safeguard being whatever the higher-level application does upon receiving `signing_request`. The asymmetry between the `ifRemote` and `ifLocal` code paths (one is gated by cosigner membership, the other is not) is the root cause: a check was deliberately removed for "multilateral signing" support without limiting scope to legitimately co-owned/shared addresses, effectively trusting the sender's claim of being a signing party.

### Impact Explanation
An unprivileged correspondent (any device previously paired with the wallet, which requires no special trust beyond pairing) can trigger the wallet's core signing pipeline for arbitrary addresses it locally controls, without being validated as an actual cosigner/counterparty of that address, by supplying its own crafted `unsigned_unit`. In any deployment where the `signing_request` event handler does not itself perform strict, address-specific cosigner verification (e.g. automated/headless multisig cosigning services, hubs, or bots that respond to legitimate multilateral-signing use cases), this can lead to the wallet signing and co-authorizing a transaction that spends its own funds to an address chosen by the attacker — i.e., unauthorized spending, mirroring the BuddyPress report's "unprivileged member escalates to full control via unchecked role/permission" pattern applied to ocore's signing-authorization boundary.

### Likelihood Explanation
Requires only a normal device pairing with the target wallet (a routine occurrence for multisig/multilateral use cases) — no privileged access, no malicious hub/node, and no key leakage is needed. The vulnerable code path is reached purely through the standard `handle_message_from_hub` -> `"sign"` case, which is always active for any wallet supporting shared/multisig addresses.

### Recommendation
Reinstate and enforce a cosigner-authorization check in the `ifLocal` branch analogous to the one already present in `ifRemote`: before emitting `signing_request` for `body.address`, verify that `from_address` is actually a recognized cosigner or expected offeror for that specific address (e.g., verifying `from_address` against `shared_address_signing_paths`/`wallet_signing_paths`/`extended_pubkeys` for the target address, or against contract-specific signer lists such as `assocSignersByPath` for multilateral “dumb contract” signing use cases), rather than accepting a signing request from any correspondent for any locally-held address.

### Proof of Concept
1. Attacker device D pairs with victim wallet W (ordinary correspondent pairing, no shared wallet needed).
2. D sends a `"sign"` message to W with `body.address` = one of W's own local addresses (single-sig or one where W locally holds the key), `body.signing_path = "r"`, and `body.unsigned_unit` containing a payment message whose outputs pay funds to an address controlled by D.
3. W's `handleMessageFromHub` processes the `"sign"` case, resolves the address via `findAddress`, hits the `ifLocal` branch (no cosigner check), and emits `signing_request(objAddress, body.address, objUnit, ..., from_address=D, signing_path)`.
4. Any automated signer/service subscribed to `signing_request` that does not itself independently verify that D is an authorized party for `body.address` will proceed to sign the attacker-supplied unit, resulting in unauthorized spending of W's funds.
