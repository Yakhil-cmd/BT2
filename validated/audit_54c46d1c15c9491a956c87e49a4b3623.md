### Title
Cross-organization webhook forgery allows unauthorized commit status injection to trigger continuous deployment on an unrelated stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate against using an attacker-controlled field of the *same* unverified JSON body (`repository.owner.login`), then, once verified, hands the *entire* raw payload to event handlers. `StatusHandler`, however, resolves the target `Commit` purely by `sha` with no repository/stack scoping at all, unlike other handlers that scope via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. This breaks the intended binding: **organization that authenticated (verified via `repository.owner.login`) == repository being written (via `sha` global lookup, independent of `repository.full_name`)**.

### Finding Description
`verify_signature` picks the verifying GitHub App/secret based on `repository_owner`, itself derived from the same untrusted JSON body before verification: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization `webhook_secret` configured for that org (multi-org config is explicitly supported): [3](#0-2) [4](#0-3) 

If an attacker registers/controls their own GitHub organization/App installation on the same Shipit instance (a normal, unprivileged, self-service action — installing a GitHub App on your own org is not a "privileged account" on Shipit), they know their own org's `webhook_secret`. They can craft a payload where `repository.owner.login` is set to their own org (so `verify_signature` selects and validates against their own known secret) while other payload fields, such as `sha`/`state`, target something under a completely different (victim) stack.

Most handlers correctly re-derive the acted-upon repository from `repository.full_name` inside the same verified payload via the base `Handler#stacks`/`repository_name` helper: [5](#0-4) 

But `StatusHandler` does not use this scoping at all — it looks up `Commit` **globally by `sha`**, with no repository or organization filter whatsoever: [6](#0-5) 

Since `sha` values are public/known for any public commit (or leakable), an attacker who owns organization A can forge a `status` webhook, signed with organization A's own webhook secret, but referencing the SHA of a commit belonging to victim organization B's stack. `verify_signature` succeeds because it authenticates the payload's claimed org (A), not the org actually being mutated (B). `Commit#create_status_from_github!` then writes an attacker-chosen state/description/target_url onto the victim's commit: [7](#0-6) 

### Impact Explanation
Commit status directly drives Shipit's deployability and continuous-deployment logic. `Commit#deployable?` and `Commit#schedule_continuous_delivery` gate automated deploys on the commit's aggregated status being `success`: [8](#0-7) [9](#0-8) 

`add_status` also schedules merges when the new status is `pending` or `success`: [10](#0-9) 

By forging a `success` status for a victim commit while authenticating as an attacker-controlled organization, an attacker can flip a required CI check to green on a stack with `continuous_deployment: true`, causing Shipit to autonomously deploy/merge that commit — an unauthorized deploy triggered purely via a cross-organization webhook forgery, satisfying the High-severity "escalation... unauthorized deploy" bar.

### Likelihood Explanation
The only prerequisite is that the Shipit instance is configured for multiple GitHub organizations (explicitly a supported and documented configuration) and that the attacker controls one of those organizations/installations — no privileged Shipit account, `ApiClient` token, or `GITHUB_TOKEN` access is required. The victim commit `sha` for a target stack is typically discoverable (public repos, PR pages, or Shipit's own public stack/task pages). This requires no interaction with a legitimate Shipit user.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository asserted (and cryptographically bound) in the same payload, mirroring the base `Handler#stacks` helper, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
and add `requires :repository { requires :full_name, String }` to the parameter schema so that the repository identity used for verification and the repository identity used for the write are the same field.

### Proof of Concept
1. Attacker creates/owns GitHub organization `attacker-org` and installs a Shipit-integrated GitHub App on it, obtaining its `webhook_secret` (self-service, no victim interaction).
2. Attacker learns the SHA of a commit tracked by victim stack `victim-org/victim-repo` (public GitHub commit, or via a public Shipit page).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy" }
}
```
signed (`X-Hub-Signature`) with `attacker-org`'s own known webhook secret.
4. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, fetches `attacker-org`'s GitHub App, and validates the signature successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of org/repo — and calls `create_status_from_github!`, writing the forged `success` status.
6. If `victim-org/victim-repo`'s stack has `continuous_deployment: true` and this was the last required/blocking status, `schedule_continuous_delivery` fires `ContinuousDeliveryJob`, deploying the victim commit without any legitimate CI signal or authorization from the victim organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
