## Title
Rounding-based overpayment when splitting earned headers commission among multiple recipients can inflate byte supply - (File: headers_commission.js)

### Summary
The reported bug class (`GaugeController.distributeRevenue()` losing dust to integer truncation when splitting an amount proportionally by weight) has a structural analog in `headers_commission.js`, where a headers-commission amount won by a multi-authored unit is split among `earned_headers_commission_recipients` using per-recipient rounding instead of an exact/remainder-aware split.

### Finding Description
When a unit wins headers commission from a parent, the full commission (`full_amount`) is split among the unit's `earned_headers_commission_recipients` (percentages that a poster fully controls and that only need to sum to exactly 100, enforced in `validateHeadersCommissionRecipients()`) [1](#0-0) .

The split is computed independently, per recipient, by rounding each share rather than distributing an exact amount with any remainder assigned deterministically to a single recipient:

```
var amount = Math.round(full_amount * share / 100.0);
``` [2](#0-1) 

and equivalently in the SQL/DB path:
```
ROUND(punits.headers_commission*earned_headers_commission_share/100.0) AS hc
``` [3](#0-2) 

Because each recipient's share is rounded to the nearest integer independently, the sum of the rounded per-recipient amounts is not guaranteed to equal `full_amount`. Unlike the GaugeController example (which only loses dust via `floor` truncation), `Math.round`/SQL `ROUND` can round *up* as well as down. A unit author fully controls both the number of recipients (bounded by `MAX_AUTHORS_PER_UNIT`) and the exact percentage split (as long as the percentages are positive integers summing to 100), and can choose shares so that multiple recipients land exactly at (or just above) the `.5` rounding boundary, causing more shares to round up than the aggregate fractional remainder would allow. In the worst case this creates surplus headers-commission bytes that did not exist in the paying unit's `headers_commission` value.

### Impact Explanation
`headers_commission_outputs` become spendable byte outputs credited to attacker-controlled addresses [4](#0-3) . If the sum of rounded recipient amounts for a winning unit exceeds the actual `headers_commission` collected from the payer unit, this constitutes unbacked byte creation (a form of supply inflation), since `headers_commission_outputs` feed directly into the network's spendable byte balance and total-supply accounting [5](#0-4) . An attacker who is a multi-author unit poster (an unprivileged action fully reachable by posting an ordinary unit) chooses the recipient list and shares, and could repeat this pattern across many units/hops to accumulate inflation over time.

### Likelihood Explanation
The per-recipient rounding calculation is reachable by any unprivileged unit poster who composes a multi-authored unit and supplies `earned_headers_commission_recipients` — this requires no special privilege, hub cooperation, or timing attack, only crafting the recipient share percentages (validated only to be positive integers summing to 100). However, exploitability depends on the attacker also controlling (or influencing) `full_amount` (the parent's `headers_commission`, itself derived from unit byte size) precisely enough to land fractional parts at/above `.5` for multiple recipients simultaneously, and on winning the header-commission race for the relevant parent unit (`getWinnerInfo`) [6](#0-5) . Per-event gains are small (bounded by roughly `floor(N/2)` extra base units where N is the number of recipients, limited by `MAX_AUTHORS_PER_UNIT`), so this is a low-magnitude, high-frequency griefing/inflation vector rather than an immediately large fund-loss bug.

### Recommendation
Replace the independent per-recipient rounding with an exact distribution scheme: compute each recipient's share with `Math.floor`, sum the floored amounts, and add the remainder (`full_amount - sum_of_floors`) to a single deterministic recipient (e.g., the first recipient by sort order, matching the existing "must be sorted by address" invariant), mirroring the recommended fix pattern from the external report (leftover assigned to a single fixed party) but applied to prevent both under- and over-distribution. Apply the same fix consistently to both the JS in-memory computation and the SQL query path so the two remain equal (the code already asserts `_.isEqual` between the two paths, so both must be changed together) [7](#0-6) .

### Proof of Concept
Conceptual PoC (cannot be executed without a live node, but demonstrates the arithmetic):
1. Compose a multi-authored unit with `N` co-author addresses (attacker-controlled), setting `earned_headers_commission_recipients` shares such that `full_amount * share_i / 100` yields a fractional part of exactly `0.5` for as many recipients as possible (attacker controls `full_amount` indirectly by controlling unit byte size, since `headers_commission` scales with unit size) and the shares still sum to exactly 100 as required by `validateHeadersCommissionRecipients()`.
2. Have this unit win the headers-commission race against its parent (`getWinnerInfo`) by constructing the deterministic SHA1 tie-break in the attacker's favor (attacker controls unit content to try multiple candidate units).
3. After stabilization, `calcHeadersCommissions()` computes and inserts `headers_commission_contributions`/`headers_commission_outputs` per recipient using `Math.round`/`ROUND`; sum the resulting outputs and compare against the original `headers_commission` value paid by the parent unit — the sum can exceed the original commission by the number of recipients whose fractional part rounds up beyond what the aggregate remainder allows.
4. Repeat across many units/hops to accumulate the surplus into spendable byte balances.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
```
