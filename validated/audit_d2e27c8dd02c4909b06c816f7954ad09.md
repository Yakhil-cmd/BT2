## Title
Revoked/old address definition remains valid for signing after a definition-change ("key revocation") is posted but not yet stable, enabling unauthorized spending with the old key - (File: validation.js)

### Summary
GitLab's CVE-2020-13299 involved a revocation feature that did not immediately invalidate old session credentials, letting a previously-valid credential keep working. ocore has a structurally analogous gap: when an address owner "revokes" a compromised signing key by posting an `address_definition_change` message, the old address `definition` (the "session credential" that authenticates units from that address) is **not immediately invalidated**. It stays valid for authoring new units until the change unit becomes stable and is referenced by `last_ball_mci`. During this window an attacker who has obtained the old private key can still author and get accepted units signed with the revoked definition.

### Finding Description
Author/definition validation is done in `validateAuthor()` in `validation.js`. When an author supplies a `definition`, `validateDefinition()` calls `storage.readDefinitionByAddress(conn, objAuthor.address, objValidationState.last_ball_mci, ...)`, i.e. the *only* definition regarded as active is the one that was active as of `last_ball_mci`, not the current definition. [1](#0-0) 

If a match is found for the *new* definition too early, `handleDuplicateAddressDefinition()` is invoked, and the code explicitly documents that the old key can still be used to double-author a valid ball before the revocation takes effect: [2](#0-1) 

The gating logic `checkNoPendingChangeOfDefinitionChash()` only blocks a *serial* unit from being posted while a `address_definition_change` for that address is pending/unstable; but if the unit becomes non-serial (because of a conflicting/competing unit on the same address), it is allowed through as long as the pending change unit is not included in its parents: [3](#0-2) 

Similarly, `checkNoPendingDefinition()` applies the identical "only blocked if included in parents" rule for pending initial/changed definitions: [4](#0-3) 

The activation of a new definition is bound purely to `last_ball_mci` stability (`storage.readDefinitionByAddress`), which in `writer.js` is populated at `address_definition_changes` insert time but only takes effect for authors once the change unit is itself included and stable at or before `last_ball_mci` of the spending unit: [5](#0-4) 

Because DAG unit propagation and stabilization are not instantaneous, and units can be authored referencing an earlier `last_ball_unit`/`last_ball_mci`, an attacker in possession of a soon-to-be-revoked private key can race the legitimate definition-change unit: post a payment/AA-trigger unit signed with the old (compromised) definition, using a `last_ball_unit` from before the revocation stabilizes. Under the non-serial path documented above, this old-key-signed unit can still be accepted as valid (`sequence` becomes `'good'` if it does not directly conflict with a stable competitor), giving the attacker a window to spend funds using the very key the user believed they had revoked.

### Impact Explanation
This allows **unauthorized spending**: an attacker who compromised a private key can continue to spend funds from that address using the old definition even after the legitimate owner posts a revoking `address_definition_change`, as long as the attacker's unit's `last_ball_mci`/parents predate stabilization of the revocation. This is a direct financial-loss vector for wallet users relying on key rotation/definition-change as an incident-response mechanism, and the code explicitly flags this as an unresolved concern ("todo: investigate if this can split the nodes").

### Likelihood Explanation
Exploitation only requires an unprivileged actor (the holder of the old, revoked private key) to race the network: post a conflicting unit signed with the old key before the definition-change unit and its dependents become stable. Because unit propagation/stabilization inherently takes time (multiple main-chain confirmations), this window is realistically exploitable by any attacker with basic knowledge of DAG timing, without any special node/hub/network privileges — it is purely a property of unit validation logic reachable from a single posted unit.

### Recommendation
- Ensure that once an `address_definition_change` unit for an address is included (even before full stabilization) in the DAG, any competing unit authored with the old definition that does not include that change in its parents is treated as inherently invalid/non-serial-losing, rather than potentially resolving to `'good'`.
- Consider tightening `checkNoPendingChangeOfDefinitionChash`/`checkNoPendingDefinition` so that once a definition-change is broadcast, no further units signed with the prior definition can become `'good'`, closing the race window explicitly acknowledged in `validation.js`.
- Add explicit tests reproducing the "attacker changes definition then quickly sends a unit with old definition" scenario referenced in the code comment.

### Proof of Concept
1. Attacker obtains address A's private key (definition D_old).
2. Owner detects compromise and posts `address_definition_change` unit U1 setting new definition D_new for A.
3. Before U1 stabilizes (is referenced by `last_ball_mci` of later units), attacker crafts unit U2 spending A's funds, authored with `definition: D_old`, choosing parents/`last_ball_unit` that do not include U1.
4. Per `checkNoPendingChangeOfDefinitionChash`/`checkNoPendingDefinition`, since U1 is not included in U2's parents, U2 is allowed to proceed to `validateDefinition`, which validates against the definition active as of U2's `last_ball_mci` — still D_old.
5. If U2 does not directly conflict with a stable unit, it is accepted with `sequence = 'good'`, resulting in unauthorized spend of A's funds using the supposedly revoked key. [6](#0-5) [7](#0-6)

	function validateDefinition(){
		if (!("definition" in objAuthor))
			return callback();
		// the rest assumes that the definition is explicitly defined
		var arrAddressDefinition = objAuthor.definition;
		storage.readDefinitionByAddress(conn, objAuthor.address, objValidationState.last_ball_mci, {
			ifDefinitionNotFound: function(definition_chash){ // first use of the definition_chash (in particular, of the address, when definition_chash=address)
				try {
					if (objectHash.getChash160(arrAddressDefinition) !== definition_chash)
						return callback("wrong definition: " + objectHash.getChash160(arrAddressDefinition) + "!==" + definition_chash);
				}
				catch (e) {
					return callback("definition hash failed: " + e.toString());
				}
				callback();
			},
			ifFound: function(arrAddressDefinition2){ // arrAddressDefinition2 can be different
				handleDuplicateAddressDefinition(arrAddressDefinition2);
			}
		});
	}
	
	function handleDuplicateAddressDefinition(arrAddressDefinition){
	//	if (!bNonserial || objValidationState.arrAddressesWithForkedPath.indexOf(objAuthor.address) === -1)
			return callback("duplicate definition of address "+objAuthor.address+", bNonserial="+bNonserial);
		// todo: investigate if this can split the nodes
		// in one particular case, the attacker changes his definition then quickly sends a new ball with the old definition - the new definition will not be active yet
		try {
			if (objectHash.getChash160(arrAddressDefinition) !== objectHash.getChash160(objAuthor.definition))
				return callback("unit definition doesn't match the stored definition");
		}
		catch (e) {
			return callback("handleDuplicateAddressDefinition definition hash failed: " + e.toString());
		}
		callback(); // let it be for now. Eventually, at most one of the balls will be declared good
	}
