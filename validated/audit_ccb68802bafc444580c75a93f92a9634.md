### Title
Operator-disabled review stacks are silently re-enabled on PR reopen due to `&&`/`||` precedence bug in `ReopenedHandler#unarchive?` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` (and its sibling `OpenedHandler#provision?`) intends `repository.review_stacks_enabled` to gate *all* provisioning behaviors, but Ruby's `&&`/`||` precedence only binds it to the `allow_all` branch. When `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, the disabled flag is silently bypassed, letting an attacker who controls a labeled/unlabeled PR re-provision (and re-execute commands for) a stack after a maintainer has explicitly turned `review_stacks_enabled` off.

### Finding Description
The broken binding, stated as an equality that the code assumes but does not enforce:
`repository.review_stacks_enabled(at reopen time) == repository.review_stacks_enabled(at original provisioning decision)` is what the code *should* gate on for every `provisioning_behavior`, but it only actually gates the `allow_all` case.

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` has higher precedence than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`.
`review_stacks_enabled` is therefore only ANDed into the first disjunct; the second and third disjuncts (`allow_with_label` and `prevent_with_label`) are evaluated completely independently of whether review stacks are enabled at all.

The identical bug exists in `OpenedHandler#provision?`: [2](#0-1) 

This is confirmed to be a real design deviation (not intended behavior) by comparing to `LabeledHandler`, which correctly gates the entire decision on `review_stacks_enabled` as a *top-level* AND, separate from the behavior-specific `archive?`/`unarchive?` predicates:
```ruby
def respond_to_label_change?
  params.action == "labeled" &&
    pull_request_state == "open" &&
    repository.review_stacks_enabled &&
    (archive? || unarchive?)
end
``` [3](#0-2) 

Exploit flow:
1. Repository has `provisioning_behavior: allow_with_label` with a configured label; the attacker's PR previously had a stack (archived, or never provisioned).
2. A maintainer/operator disables review stacks entirely (`repository.review_stacks_enabled = false`) to stop provisioning for that repo.
3. The attacker (any user who can close/reopen their own PR and manage its labels) attaches the provisioning label and sends `action: 'closed'` then `action: 'reopened'` webhook events (standard GitHub behavior when they close/reopen the PR).
4. `ReopenedHandler#process` calls `respond_to_pull_request_reopened?` -> `unarchive?`, which evaluates true despite `review_stacks_enabled == false`, because that flag is not part of the `allow_with_label` disjunct. [4](#0-3) 
5. `ReviewStackAdapter#unarchive!` runs `Shipit::ReviewStackProvisioningQueue.add(stack)` and `stack.unarchive!`, or creates the stack via `create!` if none exists, re-enqueuing provisioning against the attacker's branch content. [5](#0-4) 
6. The provisioning task subsequently executes via `TaskCommands`/`Command`/`PTY.spawn`, running commands sourced from the attacker's branch/config on the deploy host.

No existing guard (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) checks `review_stacks_enabled` consistency; the schema only validates payload shape, not this business-logic gate.

### Impact Explanation
This allows unauthorized re-provisioning (and consequent command execution tied to that provisioning) of a review stack for a repository whose operator has explicitly disabled review stacks — an authorization bypass of an operator-level control. The attacker only needs the ability to label/close/reopen their own PR, which any PR author has. The blast radius is scoped to repositories using `allow_with_label`/`prevent_with_label` behaviors with `review_stacks_enabled` toggled off after initial use; it does not cross repository/tenant boundaries. This matches "unauthorized deploy" / re-provisioning and execution of branch-controlled commands via `Command`/`PTY.spawn`, categorized as Critical per the provided severity rubric.

### Likelihood Explanation
Preconditions: repository must have `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`) and a stack that was previously provisioned/archived; an operator must disable `review_stacks_enabled` afterward without changing `provisioning_behavior`. Given these are plausible operational sequences (disable review stacks temporarily/permanently while leaving other settings unchanged), and the attacker's action (close+reopen, add/remove label) requires no special privilege, this is easily and repeatably triggerable by any PR author against their own PR.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch, mirroring `LabeledHandler`:
```ruby
def unarchive?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same fix to `OpenedHandler#provision?`.

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`:
```ruby
test "does not unarchive stacks when review_stacks_enabled is false, even with allow_with_label + label" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    behavior: :allow_with_label,
    label: "pull-requests-label",
    provisioning_enabled: false # operator explicitly disabled review stacks
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  # Binding under test: review_stacks_enabled(before) == false == review_stacks_enabled(after)
  assert_equal false, repository.reload.review_stacks_enabled
  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```
Running this against current code fails (`stack.reload.archived?` is false), proving `unarchive?` ignores `review_stacks_enabled` for the `allow_with_label` branch; after applying the recommended fix, it passes.
