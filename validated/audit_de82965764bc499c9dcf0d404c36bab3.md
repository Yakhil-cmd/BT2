Confirmed. The `CCMenuController` overrides the `stack` lookup to bypass the scoping that every other API controller relies on for the "token authorizes stack X" / "controller touches stack Y" binding.

## Title
Cross-stack deploy-status disclosure via unscoped `stack` lookup in `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
Every other endpoint under `Shipit::Api::BaseController` resolves the requested stack through the `stacks`/`stack` helpers, which restrict the lookup to `current_api_client.stack_id` when the `ApiClient` is scoped to a single stack: `@stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` followed by `@stack ||= stacks.from_param!(params[:stack_id])` [1](#0-0) . `CCMenuController` overrides this private `stack` method and instead resolves directly against the global `Stack` relation: `@stack ||= Stack.from_param!(params[:stack_id])` [2](#0-1) , breaking the equality that the rest of the API enforces: `stack the ApiClient token authorizes == stack the request actually touches`.

### Finding Description
`ApiClient` records may be scoped to a single `stack_id` [3](#0-2) , and this scoping is meant to be the authorization boundary for tokens that carry only the generic `read:stack` permission — `check_permissions!` only checks that the string `"read:stack"` is present, it has no notion of *which* stack [4](#0-3) . The only place that actually restricts a scoped client to its own stack is the `stacks`/`stack` helper pair in `BaseController`. `CCMenuUrlController` deliberately mints such single-stack, `read:stack`-only tokens for the CCTray/CCMenu integration: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` [5](#0-4) . Because `CCMenuController#stack` bypasses the scoped `stacks` collection and queries `Stack.from_param!(params[:stack_id])` directly against the full `Stack` table [6](#0-5) , a token that was only ever authorized (and generated) for one specific stack can be replayed against the `GET /api/stacks/*stack_id/ccmenu` route [7](#0-6)  with any other `stack_id`, and the endpoint will happily render that other stack's data.

### Impact Explanation
The response discloses deploy/rollback state for a stack the token was never authorized to see: `stack.deploys_and_rollbacks.last`, lock status, and merge/build status rendered into the CCMenu XML [8](#0-7) [9](#0-8) . This matches the "unauthenticated read of stack state ... or deploy output" High-severity category: although the request is authenticated, it is unauthorized for the specific stack, and the vulnerable code path exists precisely because a stack-scoped token (the trust anchor the rest of the API relies on) is not honored here.

### Likelihood Explanation
Any legitimate holder of a CCMenu URL/token for one stack (these tokens are handed out fairly widely for CI-status dashboards, and the token is carried in a plain query string as shown by `CCMenuUrlController#fetch`) can trivially swap the `stack_id` segment of the URL to enumerate/read any other stack hosted on the same Shipit instance. No additional secrets, GitHub credentials, or privileged accounts are required beyond the CCMenu token itself, which is explicitly designed to be a low-privilege, single-stack, read-only credential.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it in terms of the scoped `stacks` collection from `BaseController`) so that scoped `ApiClient` tokens can never resolve a `stack_id` outside `current_api_client.stack_id`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. As a legitimate stack owner, visit a stack's settings page and trigger `CCMenuUrlController#fetch` to obtain a CCMenu URL of the form `/api/stacks/OwnerA/repo/production/ccmenu?token=<T>`, where `<T>` authenticates an `ApiClient` scoped to `stack_id = StackA.id` with permissions `['read:stack']` [10](#0-9) .
2. Replay the same token against a different, unrelated stack the token holder does not administer: `GET /api/stacks/OwnerB/other-repo/staging/ccmenu?token=<T>`.
3. Because `check_permissions!` only validates the generic `read:stack` string (not the target stack) and `CCMenuController#stack` looks the stack up via `Stack.from_param!(params[:stack_id])` instead of the client-scoped `stacks` collection, the request succeeds and returns `StackB`'s latest deploy/rollback status, lock state, and build status in the XML response, disclosing data outside the token's intended authorization boundary.

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
