### Title
Stack-scoped API token can read status of any stack via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the object-scoping `stack` helper defined in `BaseController` and instead resolves the target stack directly from the request parameter, without checking whether the authenticated `ApiClient` is actually scoped to that stack. This breaks the intended binding "the stack a token authorizes" == "the stack the request touches," allowing a token that is deliberately restricted to a single stack to read CCTray/build-status information for any other stack in the installation.

### Finding Description
`BaseController` establishes the authorization invariant for stack-scoped API clients: an `ApiClient` created with a `stack_id` is meant to only ever see that one stack. [1](#0-0) 

That invariant is enforced only through the `stacks`/`stack` helper methods (`stacks.from_param!(params[:stack_id])`), not through `check_permissions!`, which merely verifies the client owns a string permission such as `read:stack` regardless of which stack instance it applies to. [2](#0-1) 

`CCMenuController` requires the generic `read:stack` permission but defines its own private `stack` method that bypasses the scoped `stacks` collection entirely, looking the stack up globally: [3](#0-2) 

Because `require_permission :read, :stack` only checks the string permission (not stack ownership) and the local `stack` override never intersects with `current_api_client.stack_id`, any client holding `read:stack` — even one created scoped to a single stack, such as the `here_come_the_walrus` fixture (`stack: shipit`) — can supply an arbitrary `stack_id` path segment to view another stack's CI status. [4](#0-3) 

This is exactly analogous to the reported bug class: a check that should have been the exclusive authorization path (the scoped `stacks` collection) is skipped by a duplicated/independent code path (`CCMenuController#stack`) that performs the sensitive read without applying the same restriction — the equivalent of the missing `else` letting a second, unguarded execution path run.

The route further amplifies this: the token for this exact endpoint is designed to be embedded in a URL query string for polling by external CI dashboard tools (`CCMenuUrlController#fetch` builds `.../api/stacks/*stack_id/ccmenu?token=...`), so leakage or reuse of one such URL by e.g. copying the base URL and changing the stack path exposes cross-stack information. [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker with a `read:stack`-scoped ApiClient token limited to Stack A can read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state) of any other stack B in the same Shipit deployment simply by changing the `stack_id` in the request URL. This is an authorization-scope bypass and unauthorized read of stack state for repositories the token holder was never granted access to, matching the "unauthorized read of stack state" bucket called out as in-scope High impact.

### Likelihood Explanation
The only prerequisite is possession of any `ApiClient` token bearing `read:stack`, including intentionally narrow, single-stack-scoped tokens (e.g., tokens auto-created for CCMenu URLs, which are specifically designed to be embedded in third-party CI dashboard configuration and are thus more exposed than typical Basic-Auth API tokens). No privilege escalation, session, or GitHub credential is required beyond that already-limited token, and the bypass requires only substituting the `stack_id` path segment.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped `stacks` collection from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that stack-scoped API clients cannot resolve stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create (or use) a stack-scoped `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (analogous to fixture `here_come_the_walrus`).
2. As this client, request `GET /api/stacks/<owner>/<repo>/<env-of-stack-B>/ccmenu?token=<client_token>` for Stack B, a stack the client is not scoped to.
3. Observe the request succeeds with `200 OK` and returns Stack B's CCTray XML (build status, activity, last build label, web URL) because `CCMenuController#stack` resolves via `Stack.from_param!` globally instead of the client-scoped `stacks` collection, unlike e.g. `Api::StacksController#index`, which correctly restricts results per the existing test "an api client scoped to a stack will only see that one stack." [7](#0-6)
