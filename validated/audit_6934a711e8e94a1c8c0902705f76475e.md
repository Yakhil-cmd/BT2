## Analysis

This maps to the same bug class as the InsuranceFund `syncDeps()` report: a privileged party can unilaterally rewrite a critical, externally-referenced piece of state (there: the `vusd` token address; here: an asset's `attestors` list) at any time, and downstream fund-accounting/spend logic re-reads that state *at validation time* rather than at the time the user actually acquired the funds. This breaks the implicit invariant that funds legitimately received under one state of the dependency remain spendable, causing user fund freezing.

### Title
Asset definer can freeze users' already-held coins by rotating the `attestors` list of a `spender_attested` asset - (File: `validation.js`, `storage.js`)

### Summary
Assets with `spender_attested: true` gate every payment (issue, transfer, and even the identity of output addresses) on membership in the asset's *current* attestor list, which is looked up fresh at validation time based on `last_ball_mci`, not fixed at the time the recipient received the funds. The attestor list itself can be rewritten at will by the asset definer via a single, unrestricted `asset_attestors` message. Once rewritten to drop a previously attested address, any coin the affected user already holds becomes permanently unspendable, even between two mutually still-legitimate holders, exactly mirroring the `syncDeps()` pattern where a privileged actor swaps a referenced dependency between a user's deposit and withdrawal.

### Finding Description
`readAsset()` computes an asset's attestor set by finding the *latest* `asset_attestors` unit stable as of the current `last_ball_mci`: [1](#0-0) 

`filterAttestedAddresses()` intersects this always-current attestor set against the `attestations` table to decide, at validation time, which spender/output addresses currently count as "attested": [2](#0-1) 

The list can be updated at any time via an `asset_attestors` message, restricted only to being single-authored by the asset's definer — there is no cap on frequency, no timelock, and no check that removing addresses doesn't strand already-issued outputs: [3](#0-2) [4](#0-3) 

The written attestor rows simply replace/extend based on the new message, keyed by (asset, unit, attestor_address): [5](#0-4) 

This "live" list is then enforced against every prior holder attempting to spend:
- On issue, the issuer must be in the *current* attested set: [6](#0-5) 
- On transfer, the *spender* (input owner) must be in the current attested set: [7](#0-6) 
- All *output* addresses of the new payment must also be attested under the current list: [8](#0-7) 

Because these checks are re-evaluated against the attestor list as of the *spending* unit's `last_ball_mci` rather than the list in force when the coin was originally created/received, a definer can, with one posted `asset_attestors` unit, retroactively invalidate the spendability of coins that were legitimately issued/transferred to addresses under the old list — precisely the same "mutable dependency changed between two user operations" root cause as `InsuranceFund.syncDeps()` changing `vusd` between Alice's deposit and withdrawal.

### Impact Explanation
Any address holding unspent outputs of a `spender_attested` asset can have those funds permanently frozen the moment the asset definer publishes a new attestor list that excludes it — even if the holder did nothing wrong and even if they are transacting with another address that is also still legitimately attested but simply not on the new list. There is no path to recover the funds short of the definer re-adding the address (a purely off-chain, unenforceable action). This is a direct "AA/asset fund freezing" outcome triggered entirely from a single posted `asset_attestors` unit by the asset issuer, matching the fund-loss impact class of the referenced report.

### Likelihood Explanation
Reachable with a single `asset_attestors` message authored by the asset definer — no special network position, no cross-node cooperation, no timing race beyond ordinary unit posting order (`last_ball_mci` progression). This is fully within the "asset issuer" actor class explicitly permitted as an analog trigger source. Any asset marked `spender_attested` (a supported, documented asset feature) is exposed to this pattern; the only prerequisite is that some user already holds an unspent output before the list is rewritten.

### Recommendation
- Do not evaluate spend-side attestation using the attestor list current at the *spending* unit's `last_ball_mci`; instead, pin/record the attestor-list version that was current when each output was created (analogous to snapshotting balance before an external dependency swap, as recommended for `syncDeps()`).
- Alternatively, disallow removal of addresses from the attestor list (only allow additions), or require that removed addresses first prove their existing outputs are drained/migrated before the change is accepted, so already-issued coins can never become unspendable purely due to a later list rotation.
- At minimum, document and rate-limit/timelock `asset_attestors` updates so wallets can detect and react (e.g., migrate funds) before a removal takes effect, rather than allowing an instantaneous, retroactive freeze.

### Proof of Concept
1. Definer creates asset `spender_attested: true` with `attestors: [X]`.
2. Attestor `X` attests address `A`. `A` is issued/transferred coins of the asset; `filterAttestedAddresses` confirms `A` is attested as of that `last_ball_mci`.
3. Definer posts `asset_attestors` message changing the list to `[Y]` (dropping `X`), per `validateAttestorListUpdate` (`validation.js:2829-2848`), accepted since it is single-authored by the definer.
4. `A` (still holding unspent coins from step 2) attempts to spend/transfer them. `readAsset`/`filterAttestedAddresses` (`storage.js:1917-1946`, `1959-1974`) now compute the attestor set based on `[Y]`; since `A` was never attested by `Y`, `objAsset.arrAttestedAddresses` no longer contains `A`.
5. `validatePaymentInputsAndOutputs` rejects the spend with `"owner address is not attested"` (`validation.js:2506-2507`), and any attempted output to `A` fails `"some output addresses are not attested"` (`validation.js:2634-2641`).
6. `A`'s previously legitimate funds are now permanently unspendable, with no unit `A` can post to recover them.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
