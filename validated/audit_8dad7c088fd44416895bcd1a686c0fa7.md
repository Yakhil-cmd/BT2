### Title
StatusHandler writes GitHub statuses to commits in unrelated stacks/repositories, bypassing repository binding - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` and never checks that the resolved `Commit#stack` belongs to the repository named in the webhook payload, unlike every other handler which scopes to `stacks` (derived from `payload['repository']['full_name']`). A signed `status` webhook from a repository the attacker controls can therefore mutate CI/status state — and downstream deploy-gating behavior — of Commit rows belonging to any other stack that happens to share the same SHA.

### Finding Description
Broken binding: `Commit#stack.repository.full_name` (the repo whose status is being written) should equal `payload.dig('repository','full_name')` (the repo that authenticated/signed the webhook). This holds for every other handler:

- `PushHandler#process` restricts to `stacks.not_archived.where(branch:)` where `stacks` is `Repository.from_github_repo_name(repository_name)&.stacks`. [1](#0-0) 
- `Handler#stacks` / `#repository_name` establish this scoping contract for subclasses. [2](#0-1) 

`StatusHandler#process`, however, does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

This is a global, unscoped query across the entire `commits` table. It never calls `stacks` or `repository_name`, so any Commit row in any Stack/Repository whose `sha` matches `params.sha` will have `create_status_from_github!` invoked on it, updating its `statuses` association from attacker-controlled payload fields (`state`, `description`, `target_url`, `context`, `created_at`).

`create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)`, then evaluates `deployable?`/`schedule_merges`/`Hook.emit(:commit_status, ...)`/`Hook.emit(:deployable_status, ...)` against the *victim* stack. [4](#0-3) [5](#0-4) 

Exploit flow:
1. Attacker owns (or has push access to) a repository within an org/installation that Shipit's GitHub App is configured for — this is required only to obtain a validly-signed webhook via `verify_signature`, which is scoped per `repository_owner` org, not per specific repo. [6](#0-5) 
2. Attacker finds/produces a commit SHA that also exists in one or more victim `Commit` rows for other stacks (realistic via shared template initial commits, cherry-picked/rebased commits, or generally any commit that was ever pushed to both repos and ingested by Shipit — content-addressed SHAs are shared whenever byte-identical commit objects exist, which is common for scaffolded/template repositories).
3. Attacker triggers (or crafts) a `status` event on their own repo naming that SHA with attacker-chosen `state`/`description`/`context`/`target_url`.
4. GitHub (or the attacker directly, since only the org-level HMAC secret gates acceptance and the payload's `repository` field is not cross-checked against SHA ownership) sends the signed POST to `/webhooks`.
5. `StatusHandler#process` finds all `Commit` rows with that SHA — including rows belonging to victim stacks — and writes a forged status onto each, potentially flipping `deployable?` to true/false, firing `Hook.emit`, and calling `stack.schedule_merges` on unrelated stacks.

None of the existing guards prevent this: `verify_signature` only authenticates that the payload came from a GitHub org integrated with Shipit, not that the named `repository` owns the `sha`; `drop_unhandled_event` and `ExplicitParameters` schema (`requires :sha, String`) don't constrain SHA to a specific repo; and `Handler#stacks`/`#repository_name` — the mechanism meant to enforce this exact binding — is simply never invoked by `StatusHandler`.

### Impact Explanation
A payload signed for repository A can mutate CI status of commits belonging to stack(s) tied to repository B (or N other repositories), matching the "Critical - a payload for one repository mutating another's stack, commit, task or team" category. Concretely this can: forge a green/red CI status that feeds `Commit#deployable?`, trigger `stack.schedule_merges` (potentially advancing autodeploy/merge queues) on a stack the attacker has no relationship to, and fire `Hook.emit(:commit_status/:deployable_status)` webhooks/notifications with attacker-controlled `description`/`target_url` for a victim tenant. This is repeatable for every additional stack sharing that SHA and for every SHA the attacker can find in common between their repo and victims.

### Likelihood Explanation
Preconditions: the attacker needs a signed webhook, i.e., control of a repository under an org/GitHub App installation Shipit trusts (this is the only real barrier — it does not require Shipit session, API token, or per-repo Shipit configuration for the *victim* repo). It further requires SHA collision across repos' `Commit` tables, which is realistic for template-generated repos (shared initial/empty commit), forked/mirrored history, or monorepo-derived stacks — a known and fairly common real-world occurrence, not a contrived edge case. Attacker cost is a single crafted HTTP webhook per exploitation attempt, fully repeatable and automatable against any SHA/commit table state discoverable via Shipit's own UI/API (commit SHAs are typically not secret).

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup through `stacks` (the same `Repository.from_github_repo_name(repository_name)` binding used elsewhere), e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, before calling `create_status_from_github!`, so a signed webhook can only affect commits belonging to the repository named in its own payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook does not update commits belonging to a different repository" do
  attacker_stack = shipit_stacks(:shipit)          # repo: "shopify/shipit-engine"
  victim_stack   = shipit_stacks(:cyclimse)        # repo: "shopify/some-other-repo"

  shared_sha = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    'repository' => { 'full_name' => attacker_stack.repository.full_name },
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'attacker-forged',
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding under test: commit's stack repo == payload repo
  assert_equal attacker_stack.repository.full_name, attacker_commit.reload.statuses.last.stack.repository.full_name

  # This currently FAILS, proving cross-tenant corruption:
  assert_nil victim_commit.reload.statuses.last, "victim commit outside payload['repository'] must not receive a status"
end
```
Expected today: the last assertion fails because `victim_commit` receives a `Status` row from a webhook signed only for `attacker_stack`'s repository, demonstrating the broken `Commit#stack.repository.full_name == payload['repository']['full_name']` binding.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
