### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but the write target (Stack sync) is resolved from the independent, unvalidated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read directly from the untrusted, attacker-controlled JSON body (`params.dig('repository', 'owner', 'login')`). Once the HMAC is confirmed valid for that organization's secret, the entire raw payload — including a completely independent `repository.full_name` field — is trusted and handed to the event handlers, which resolve the Stack/Repository to mutate using `payload.dig('repository', 'full_name')`. Nothing enforces that the organization whose secret validated the signature is the same organization that owns the repository being acted upon.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` looks up a per-organization `GitHubApp` instance configured under the "Using Multiple GitHub Applications" scheme, where each organization has its **own** independent `app_id`, `installation_id`, and `webhook_secret`: [2](#0-1) [3](#0-2) 

After the signature passes for organization `repository_owner`, the raw JSON `params` are forwarded unmodified to the registered handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

The handlers, however, never re-read `repository.owner.login`. They independently resolve the target repository/stack from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler#process` then syncs and can trigger the deploy pipeline (`stack.sync_github`, which in turn feeds `GithubSyncJob` / continuous delivery):
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

`Repository.from_github_repo_name` splits `full_name` on `/` and does a plain, case-insensitive DB lookup with no ownership check against `repository_owner`:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [7](#0-6) 

Nothing in this chain checks that `repository.owner.login` (used to pick the verifying secret) equals the owner segment of `repository.full_name` (used to pick the Stack to mutate). This is exactly the "organization that authenticated versus the repository that is written" binding described as an analog pattern: the equality `organization_whose_secret_verified_signature == owner(repository_being_written)` is never enforced.

### Impact Explanation
In a multi-organization Shipit deployment (the officially documented configuration for hosting multiple GitHub orgs on one Shipit instance, each with its own app/secret), a party who is a legitimate administrator of *their own* organization's GitHub App — and therefore knows or controls only that organization's `webhook_secret` — is an unprivileged attacker with respect to every *other* organization/repository hosted on the same Shipit instance. By crafting a raw HTTP POST to `/webhooks` with:
- `repository.owner.login = "attacker-org"` (so the signature is computed/verified against `attacker-org`'s own known secret), and
- `repository.full_name = "victim-org/victim-repo"` (an unrelated repository the attacker has no GitHub access to),

the attacker produces a payload whose signature validly authenticates under `attacker-org`, yet whose contents cause Shipit to act on `victim-org/victim-repo`'s Stack — e.g. triggering `GithubSyncJob`, updating commit statuses, or (if continuous deployment is enabled) triggering an unauthorized deploy — all without ever holding `victim-org`'s webhook secret or having any GitHub permission on `victim-org`'s repository. This satisfies the "unauthorized deploy" / cross-repository write impact bar.

### Likelihood Explanation
Requires the target deployment to run in the documented multi-organization mode with distinct secrets per org, and requires the attacker to control (or have configured) at least one organization's GitHub App webhook secret on the same shared Shipit instance — a realistic scenario for a Shipit instance shared across multiple business units/customers/teams. No Shipit account, API token, or GitHub access to the victim repository is required. The webhook endpoint is unauthenticated by design (public HTTP endpoint), and the payload fields involved (`repository.owner.login` vs `repository.full_name`) are both fully attacker-controlled JSON, not covered by any cross-field validation.

### Recommendation
In `WebhooksController#verify_signature` / `#create`, after resolving `repository_owner` and validating the signature, also validate that the owner segment of `repository.full_name` (and of `repository.owner.login` used for `organization`, in the `membership`/`organization`-only events) matches the `repository_owner`/organization whose secret validated the signature, before dispatching to handlers. Alternatively, have each handler re-derive and cross-check the organization from the same trusted value used during signature verification rather than trusting an independent nested payload field for both authentication routing and data-mutation routing.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (webhook_secret `S_a`, known to the attacker as its GitHub App admin) and `victim-org` (webhook_secret `S_v`, unknown to the attacker), both with Stacks configured on the same Shipit instance, per `docs/setup.md`'s "Using Multiple Github Applications" scheme.
2. Attacker builds a `push` event JSON payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha that already exists on victim-org/victim-repo>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_a, raw_body)>` using the secret they legitimately know for `attacker-org`.
4. Attacker POSTs this to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against `S_a`.
6. `Shipit::Webhooks.for_event('push')` invokes `PushHandler.call(params)`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on `victim-org`'s stack — a write action taken on a repository the attacker's authenticated organization does not own, using only credentials the attacker legitimately controls for a different organization.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
