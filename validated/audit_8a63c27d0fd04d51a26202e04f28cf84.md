### Title
Multisig timelock override threshold can be retroactively lowered below a pending transaction's already-collected approvals, bypassing the timelock delay - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account`'s optional timelock feature lets owners require either (a) elapsed time, or (b) a higher "override" quorum (`override_threshold`) before a transaction can execute. When owners are later removed via `update_owner_schema`, the module clamps `override_threshold` down to the new owner count, but only re-validates it against `num_signatures_required` — never against the approval counts already accumulated on in-flight pending transactions. This lets a routine owner-removal transaction silently downgrade the override bar low enough that an already-approved, still-timelocked transaction becomes immediately executable, without any of the approving owners consenting to skip the timelock.

### Finding Description
The timelock gate is implemented in `can_execute_with_timelock`: [1](#0-0) 

`override_threshold` is only compared against the *current* approval count of the specific transaction being executed — it has no memory of when the approvals were cast or under what `override_threshold` they were originally accumulated.

`update_owner_schema`, invoked whenever owners are added/removed (e.g. `remove_owner`, `remove_owners`), clamps `override_threshold` down whenever the owner count shrinks below it, and only asserts that it stays greater than `num_signatures_required`: [2](#0-1) 

This clamp is exercised (and treated as expected behavior) by `test_owner_removal_clamps_override_threshold`: [3](#0-2) 

Crucially, nothing in `update_owner_schema` inspects the approval counts of any currently pending `MultisigTransaction`s. `validate_multisig_transaction` — which is called directly by the VM as part of the transaction prologue/admission path — recomputes approvals fresh and checks them against the *current* `override_threshold` at execution time: [4](#0-3) 

Because the threshold used for the override check is mutable state that can be lowered by an unrelated owner-management action, approvals a pending transaction accumulated *while the override bar was high* can later satisfy a *lowered* bar, letting the transaction bypass the timelock delay even though no owner ever approved it with the intent of enabling immediate execution under the new, lower bar. This is the same class of bug as the source report: a partial/derived quantity (there, `holdAmount` capped by `min()`; here, `override_threshold` capped by the new owner count) is recalculated independently of a related in-flight state (there, the position's margin; here, a pending transaction's already-cast votes), producing a state where a cost/friction that should still apply (borrowing fee / timelock delay) is silently waived.

### Impact Explanation
The timelock's entire purpose is to give owners a mandatory delay (or require a supermajority override) before a transaction can be executed — a security control specifically meant to allow owners to react to and cancel malicious or contested transactions. This flaw lets that delay be defeated for any transaction that already has enough (stale) approvals, triggered purely by a routine, otherwise-legitimate owner-list change. This is a broken approval-set invariant at the admission boundary: `validate_multisig_transaction` ends up admitting/executing a transaction whose approval set was never validated against the threshold currently governing "skip the timelock." In a multisig meant to protect high-value treasury or admin operations, this can result in unauthorized early execution of a transaction that owners specifically structured to require a cooling-off period.

### Likelihood Explanation
Exploitation requires an on-chain multisig governance action (removing an owner), which itself requires quorum — so this is not exploitable by a fully unprivileged outsider. However, it can be triggered unintentionally (e.g., normal owner rotation/offboarding) or intentionally by any subset of owners with enough votes to pass a `remove_owner`/`remove_owners` transaction, without needing any additional approval on the target pending transaction. Given that owner-list changes are a routine multisig operation and the interaction with pending transactions' override thresholds is non-obvious (and not checked anywhere), the likelihood of accidental or deliberate triggering is meaningful, especially in multisigs that actively use both timelocks and owner rotation.

### Recommendation
When clamping or updating `override_threshold` (or `num_signatures_required`) in `update_owner_schema`, re-evaluate all pending transactions (`last_executed_sequence_number+1 .. next_sequence_number`) and ensure the new threshold doesn't retroactively satisfy the override condition for transactions whose approvals were cast under a stricter threshold — e.g., by re-checking timelock eligibility only against approvals gathered strictly after the threshold change, or by disallowing threshold changes while transactions have already-collected approvals close to the old threshold, or simply by snapshotting/pinning the override threshold at transaction-creation time instead of always reading the live global value in `can_execute_with_timelock`.

### Proof of Concept
1. Create a multisig account with owners `[O1, O2, O3, O4, O5]`, `num_signatures_required = 3`.
2. Owners configure a timelock via `upsert_timelock(..., timelock_period = 24h, override_threshold = Some(4))` — i.e., 4-of-5 needed to skip the 24h delay. [1](#0-0) 
3. `O1` creates a sensitive transaction (`create_transaction`); `O2` and `O3` approve it → 3 approvals total (creator implicitly counted). This meets `num_signatures_required` (3) but not `override_threshold` (4), so `can_execute_with_timelock` returns `false` and execution must wait 24h.
4. Before the 24h elapses, owners pass a separate, unrelated transaction calling `remove_owners([O4, O5])` (owners who never voted on the sensitive transaction). `update_owner_schema` now clamps `override_threshold` from 4 down to `num_owners = 3` (since 4 > 3), and the assert `override_threshold > num_signatures_required` (3 > 3 is false — so this exact reduction would actually need `num_signatures_required` lowered first, as shown in `test_owner_removal_clamps_override_threshold`) passes given a slightly adjusted starting configuration (e.g. `num_signatures_required = 2`). [5](#0-4) 
5. `O1` (or any owner) now calls execute on the original sensitive transaction. `validate_multisig_transaction` recomputes `num_approvals = 3`, checks it against the now-lowered `override_threshold = 3`, and `can_execute_with_timelock` returns `true` — the transaction executes immediately, 24h early, even though none of `O2`/`O3` ever approved with intent to bypass the timelock, and the owners who could have blocked it (`O4`, `O5`) were removed via an unrelated action. [6](#0-5) 

Note: I could not fully trace whether any additional invariant elsewhere in the framework (outside `multisig_account.move`) re-validates pending-transaction approval timing against threshold changes, since this timelock/override feature appears to be a custom addition not present in upstream `aptos-core` and its surrounding integration points (e.g., any off-chain indexer assumptions) were outside the scope of what I could verify with the available tools.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
