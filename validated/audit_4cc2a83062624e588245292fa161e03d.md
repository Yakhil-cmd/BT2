### Title
Flat storage `get_blocks_to_head` delta-chain traversal cost is unmetered - unprivileged accounts can force O(hops) CPU work per `storage_read`/`storage_has_key` while gas charges stay fixed - (File: core/store/src/flat/storage.rs)

### Summary
`FlatStorageInner::get_blocks_to_head` walks the in-memory delta chain from the requested block back to `flat_head`, and `FlatStorage::get_value` must call `get_block_changes` for every hash in that chain until it finds the key (or falls through to the trie). An attacker who submits `FunctionCall` receipts that write a fresh, previously-untouched key in each of many consecutive blocks forces this chain to grow arbitrarily long before `flat_head` advances, while the wasm host only charges a fixed `wasm_storage_read_base` / `wasm_touching_trie_node` cost per read regardless of chain length.

### Finding Description
`get_blocks_to_head` (core/store/src/flat/storage.rs, lines 88-142) walks backwards from `target_block_hash` toward `flat_head`, skipping only blocks that have **no** flat-state changes via the `prev_block_with_changes` pointer: [1](#0-0) 
Every block that *does* have a change (e.g., a `storage_write` to any key) is pushed into the `blocks` vector and cannot be skipped — the skip-list optimization only helps when blocks have zero changes. This means an attacker who writes to a fresh distinct key in every single block defeats the optimization entirely: every block ends up in the traversed list.

The only guard against unbounded growth is a `tracing::warn!` log once `blocks.len() >= HOPS_LIMIT` (100); there is no hard limit, rejection, or extra cost applied: [2](#0-1) [3](#0-2) 
The comment explicitly acknowledges the design assumption ("When over 100, introduces significant overhead") citing near/nearcore#8006, but the mitigation is advisory-only.

Each block in the returned chain requires a separate `get_block_changes`/delta lookup (`self.deltas.get(block_hash)`) when `FlatStorage::get_value` searches for the target key, so the real CPU work of a single `storage_read` scales linearly with the number of blocks since `flat_head` that contain *any* write, not with anything charged to the caller.

Meanwhile, the wasm gas schedule charges a fixed cost per storage operation irrespective of flat-storage hop count. The `wasm_touching_trie_node`/`read_cached_trie_node` costs were explicitly reduced/removed for flat-storage reads under the assumption that flat reads are O(1): [4](#0-3) 
and integration tests explicitly assert that with flat storage enabled, no DB/mem reads are counted for a read of a cached key, only for the trie fallback path: [5](#0-4) 
There is no accounting anywhere in the charged `ExtCosts` (`storage_read_base`, `touching_trie_node`, etc.) for the number of deltas/hops walked in `get_blocks_to_head`; the cost model is a constant independent of `flat_head` distance.

### Impact Explanation
This is a compute-metering-completeness gap: an unprivileged account can make the real CPU cost of `storage_read`/`storage_has_key`/`storage_write` (which must call into flat storage's `get_value`) grow linearly with the number of blocks since finality last advanced the shard's `flat_head`, while the compute/gas charged to the transaction sender remains a small, fixed constant. This allows underpriced/free compute consumption on chunk-producing validators, potentially degrading chunk application performance chain-wide (validator CPU exhaustion / node slowdown), matching the "free or underpriced execution" and "unbounded resource use" bounty classes.

### Likelihood Explanation
Preconditions are simple and fully within an unprivileged actor's control: deploy any contract capable of `storage_write`, and submit enough `FunctionCall` receipts (one distinct-key write per receipt) across as many consecutive blocks as desired before finality/GC advances `flat_head`. No validator, node-operator, or protocol-privileged action is required — the attacker just needs enough NEAR to pay for the write receipts' base costs, which are fixed per write and don't compensate for the read-side externality. `HOPS_LIMIT` only produces a log warning, not a cap, so the chain can grow indefinitely as long as blocks keep getting produced before flat_head catches up (e.g., under network congestion, resharding, or catch-up delays where flat_head lags). This is repeatable and deterministic.

### Recommendation
Either (a) charge compute cost proportional to `blocks_to_head.len()` (or the number of delta lookups actually performed) for `storage_read`/`storage_has_key`/`storage_write` when flat storage is used, so the wasm host's fixed `storage_read_base` no longer under-charges long hop chains, or (b) enforce `HOPS_LIMIT` as a hard cap (e.g., forcing a synchronous flat-head advance, rejecting further reads, or falling back to trie-based accounting with its higher `touching_trie_node` cost) instead of only logging a warning.

### Proof of Concept
Integration test plan (extending the existing flat-storage cost tests, e.g. `integration-tests/src/tests/standard_cases/mod.rs::test_storage_read_write_costs`):
1. Deploy a contract with a `write_key(key, value)` method and a `read_key(key)` method.
2. Submit N `FunctionCall` receipts across N consecutive blocks, each writing a distinct fresh key (never touching a fixed "target" key written before block 0), keeping `flat_head` from advancing past block 0 (e.g. by holding finality via `move_head_hold_count` in tests, or simply measuring within the GC/finalization window).
3. After N blocks (N > `FlatStorageInner::HOPS_LIMIT` = 100), issue a `storage_read` receipt for the target key.
4. Instrument/count calls to `FlatStorageInner::get_block_changes` (or wrap `get_blocks_to_head`) during this final read, and assert the count grows ~linearly with N.
5. Assert the wasm gas/compute charged for the final `storage_read` receipt remains constant (equal to `wasm_storage_read_base` + fixed per-byte costs) regardless of N, demonstrating the divergence between charged cost and actual traversal work.
6. Optionally measure wall-clock time of step 3 vs N to show real CPU cost scaling while charged gas is flat.
