### Title
Blackholed correspondent's device messages are still processed because `is_blackhole` is not checked when routing incoming hub messages - ([File: device.js])

### Summary
`ocore` tracks a per-correspondent `is_blackhole` flag in the `correspondent_devices` table [1](#0-0) , intended to mark a paired device as blocked/disabled. However, the message-routing logic in `handleJustsaying`'s `'hub/message'` handler only selects `hub` and `is_indirect` when looking up the sender, and does not check `is_blackhole` before decrypting and dispatching the message to `handle_message_from_hub` / `handleMessageFromHub`: [2](#0-1) .

### Finding Description
This mirrors the reported bug class: a status flag meant to gate acceptance of a counterparty's messages exists in storage but is not enforced at the point where the message is actually processed. Once a device is a known correspondent (row exists in `correspondent_devices`), `handleJustsaying` proceeds to `handleMessage(rows[0].is_indirect)` regardless of `is_blackhole`, which in turn emits `handle_message_from_hub` and reaches `wallet.js`'s `handleMessageFromHub`, which handles high-impact subjects such as `sign` (co-signing requests for shared/multisig addresses), `create_new_shared_address` / `new_shared_address` / `approve_new_shared_address`, and `private_payments` [3](#0-2) [4](#0-3) [5](#0-4) .

If a user blackholes a correspondent device (e.g., after determining it is compromised or malicious, analogous to Lombard disabling a compromised staking key via Cubist), the intent is that the wallet should stop trusting/accepting anything from that device. But because the enabled/blocked check is missing at the message-intake site, the blocked device can still:
- Propose new shared/multisig address definitions that get silently created and later co-signed (`create_new_shared_address`, `new_shared_address`).
- Issue signing requests for existing shared addresses (`sign`), which — if the wallet auto-approves multisig co-signing under certain configurations, or the user is tricked into approving via the UI's confirmation prompt without realizing the sender was previously blackholed — can lead to funds being moved from a shared/multisig address that includes the local device as a cosigner.
- Send `private_payments` that get parsed and considered for storage.

### Impact Explanation
If a blackholed device can still successfully route protocol messages through `handleMessageFromHub`, the blocking mechanism becomes non-authoritative for anything other than possibly outbound sends. For multisig/shared addresses that include the blackholed device as one of the co-signing members, this can lead to unauthorized signing/spending flows being solicited and forwarded, undermining the trust boundary the user believed they had established by blackholing the device. This falls under "AA fund loss" / "unauthorized spending" categories to the extent shared-address signing flows are exploitable through a device the user explicitly tried to cut off.

### Likelihood Explanation
Likelihood depends on whether `is_blackhole` is otherwise enforced elsewhere in the send/receive pipeline (e.g., at the hub level, in `network.js`, or in `handleMessageFromHub` itself) — I was not able to confirm within my available tool budget whether any of those layers independently enforce `is_blackhole` before `device.js`'s message dispatch. If none of them do, the check gap is directly reachable by any previously-paired device the user has since blackholed.

### Recommendation
Add an `is_blackhole` check in `device.js`'s `hub/message` handler (alongside `is_indirect`) and reject/drop messages from blackholed correspondents before decryption/dispatch, rather than relying on downstream handlers or the UI layer to re-derive that state.

### Proof of Concept
Not independently reproduced. This assessment is based on static analysis of `device.js:203-221` [2](#0-1)  versus the schema definition of `is_blackhole` [1](#0-0) , and the message-subject dispatch in `wallet.js` [6](#0-5) .

**Caveat / uncertainty**: I could not exhaustively verify, within the available search iterations, whether `is_blackhole` is checked elsewhere in the send path (outbound) or at the hub server level (in a separate hub repository, not `ocore`), which would reduce or eliminate the practical severity of this finding. I was also unable to fully trace whether `handleMessageFromHub`'s individual case handlers (e.g., `sign`) have any additional confirmation-gating in the UI layer that would prevent silent exploitation. These are the main open questions a follow-up investigation (ideally with a live Devin session and full repo/hub-code access) should resolve before treating this as confirmed.
