### Title
`CCMenuController` bypasses stack-scoped API client authorization, allowing an `api_client` scoped to one stack to read the deploy status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one with `stack_id` set) may only resolve stacks from `stacks.from_param!(params[:stack_id])`, where `stacks` is filtered to `Stack.where(id: current_api_client.stack_id)`. [1](#0-0)  `Api::CCMenuController` overrides this `stack` helper to instead resolve directly against the full `Stack` table (`Stack.from_param!(params[:stack_id])`), completely skipping the `stacks` scoping method, while still only checking the coarse-grained `read:stack` permission via `require_permission`. [2](#0-1)  This breaks the binding: *the stack a token authorizes* (its single scoped `stack_id`) *≠ the stack it actually touches* (any `stack_id` param supplied in the request).

### Finding Description
An `ApiClient` can optionally be scoped to a single stack via the `stack` association/`stack_id` column, e.g. the `here_come_the_walrus` fixture, which is scoped to the `shipit` stack and has only `read:stack` permission. [3](#0-2)  The intended enforcement mechanism is `BaseController#stacks`, which restricts the queryable set of stacks to `Stack.where(id: current_api_client.stack_id)` when `stack_id?` is true, and `BaseController#stack` which resolves the request's `stack_id` param only within that restricted scope. [1](#0-0) 

`Api::CCMenuController` requires only `read:stack` permission — no additional check that the requested `stack_id` matches the client's own scope — and defines its own private `stack` method that queries the unscoped `Stack` model directly:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

This means any valid stack-scoped `ApiClient` token (even one deliberately restricted to a single, low-sensitivity stack) can be used to fetch the CCTray/CCMenu XML status (`show` action) — including build/deploy activity, last build status/label/time, and web URL — for **any** stack in the installation, not just the one it was issued for. [5](#0-4)  All the other `Api::*` controllers (e.g. `StacksController`, `HooksController` via `stack.id`) rely on the shared, correctly-scoped `stack`/`stacks` helpers from `BaseController`; `HooksController` for instance derives `stack_id` from the same `stack` helper. [6](#0-5)  `CCMenuController` is the outlier that reimplements stack resolution and drops the scoping.

### Impact Explanation
This satisfies the "High" impact category of unauthenticated/unauthorized read of stack state: an `ApiClient` token that was deliberately issued with a narrow scope (single stack, `read:stack` only) can be used to read the deploy/task status of every other stack managed by the Shipit instance, an authorization escalation across stack boundaries that the scoping mechanism was specifically designed to prevent.

### Likelihood Explanation
Any holder of a legitimately-scoped, low-privilege `ApiClient` credential (e.g. an external CI-status widget integration deliberately restricted to one repository/stack) can immediately exploit this by simply changing the `stack_id` request parameter — no additional secrets, sessions, or privileges are required beyond the token they were already issued. This is a direct, single-request exploit with no race conditions or preconditions.

### Recommendation
Make `Api::CCMenuController#stack` use the inherited, scope-respecting resolution instead of querying `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it reuses `BaseController#stacks`, which already restricts resolution to `current_api_client.stack_id` when the client is scoped.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: <stack_A.id>` with only `read:stack` permission (mirrors the `here_come_the_walrus` fixture). [3](#0-2) 
2. Authenticate as that client and call `GET /api/:stack_A/cctray.xml` — succeeds as expected.
3. Call `GET /api/:stack_B/cctray.xml` for an unrelated stack `stack_B` the client was never scoped to.
4. Because `CCMenuController#stack` resolves via unscoped `Stack.from_param!` and `require_permission :read, :stack` only checks the permission string (not stack ownership), the request succeeds and returns `stack_B`'s deploy/build status, proving the scoping bypass. [2](#0-1)
