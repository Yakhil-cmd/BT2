### Title
Non-deterministic use of unstable data-feed values in AA formula evaluation can cause node disagreement on AA response validity - (File: `formula/evaluation.js`, `data_feeds.js`)

### Summary
The Starknet report's root cause is that a critical validation (`funding_tick`'s funding-rate check) consumes a price value fetched by `get_synthetic_price()` without verifying that value is up to date/canonical, so different observers (or the same observer at different times) can validate the same operation against different, unreliable data. The analogous pattern in `ocore` exists in the `data_feed[[...]]` oscript function used inside Autonomous Agent (AA) formulas: when evaluated during AA (bAA) execution, it is allowed to read **unstable** (not-yet-stabilized) data-feed postings from `storage.assocUnstableMessages`, selected only by MCI range and author address, with no guarantee that the selected posting is part of the deterministic causal/ancestor set that will be shared by all nodes.

### Finding Description
In `formula/evaluation.js`, the `data_feed` case calls: [1](#0-0) 
`dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, objValidationState.last_ball_timestamp, ...)`.

Here `bAA` is passed positionally as the `unstable_opts` argument of `readDataFeedValue`, meaning that whenever the formula is evaluated as part of an AA (trigger response computation), the data-feed lookup is allowed to pull values from **unstable** DAG messages, not just from data confirmed by the last stable ball: [2](#0-1) 

The candidate-selection loop iterates `storage.assocUnstableMessages`, an in-memory structure reflecting whatever units the local node currently happens to know about and consider unstable, filtered only by:
- `objUnit.latest_included_mc_index` falling within `[min_mci, max_mci]`,
- author-address intersection with the requested oracle list. [3](#0-2) 

There is no check that the candidate unit is actually an ancestor of (or otherwise causally tied to) the specific trigger/response unit being processed. Because `storage.assocUnstableMessages`/`assocUnstableUnits` reflect the node's local, transient view of the still-unstabilized DAG, two different full nodes (or the same node at two different processing times, e.g. before vs. after a reorg among competing tips) can legitimately hold different candidate sets for the same oracle/feed_name/mci window. When `ifseveral` resolves ties by `latest_included_mc_index`/`level` sorting, the resulting selected value can differ between nodes when candidates are otherwise ambiguous or when one node has not yet received a unit the other has.

This means the value fed into `data_feed[[...]]` — and hence into any AA logic (bounce/no-bounce decisions, payout amounts, response messages) that depends on it — is not guaranteed to be identical across all nodes independently re-deriving the AA's response for the same trigger unit, unlike a purely stable-DB-backed data feed lookup which is deterministic once mci is fixed.

### Impact Explanation
AA response computation is part of consensus: every node must independently recompute the exact same AA response for a given trigger unit and agree the resulting response unit is valid. If the `data_feed[[...]]` value used by an AA's formula (e.g., to decide `bounce()` vs. proceed, or to compute a payout amount as in the sample futures contract pattern `test/samples/futures_contract.oscript`) differs between nodes because it was sourced from the unstable/pre-stabilization DAG rather than a canonical, causally-fixed data set, nodes can disagree on whether a given AA response unit is valid. That is a direct "node disagreement on validity" scenario, and in AA logic tied to payments (as in the futures/exchange-rate sample), it can manifest as erroneous fund transfers/loss for the AA or its users if the selected candidate value differs from what other nodes recompute.

### Likelihood Explanation
Triggering requires: (1) an AA whose formula uses `data_feed[[...]]` (a documented, common pattern for price-dependent AAs, as shown in the bundled sample `futures_contract.oscript`), and (2) more than one candidate data-feed posting from the oracle(s) being visible as unstable near the same mci window at the time different nodes process the trigger (e.g., an oracle posting close to (or racing) the trigger unit, or a temporary DAG reorg before stabilization). This is a plausible, oracle-timing-dependent condition rather than a rare edge case, since AA triggers are frequently processed while their own causal context is still unstable.

### Recommendation
Restrict unstable data-feed candidates used in AA formula evaluation to units that are provably part of the deterministic causal history relevant to the trigger/response unit (e.g., ancestors within the trigger's own included DAG state) rather than any unit currently present in the node-local `assocUnstableMessages`/`assocUnstableUnits` maps filtered only by mci range and author. Alternatively, disallow ambiguous multi-candidate resolution for unstable feeds in AA context unless `ifseveral='abort'`, and document/enforce that only fully-stable data (post `last_ball_mci`) be treated as consensus-safe for security-critical AA decisions.

### Proof of Concept
Not independently reproducible from the indexed code alone (would require constructing a scenario with two nodes seeing divergent unstable DAG states while a shared oracle posts multiple `data_feed` messages near the same `latest_included_mc_index`, then triggering an AA that reads that feed). 	var start_time = Date.now();
	var objResult = { bAbortedBecauseOfSeveral: false, value: undefined, unit: undefined, mci: undefined };
	var bIncludeUnstableAAs = !!unstable_opts;
	var bIncludeAllUnstable = (unstable_opts === 'all_unstable');
	if (bIncludeUnstableAAs) {
		var arrCandidates = [];
		for (var unit in storage.assocUnstableMessages) {
			var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
			if (!objUnit)
				throw Error("unstable unit " + unit + " not in assoc");
			if (!objUnit.bAA && !bIncludeAllUnstable)
				continue;
			if (objUnit.sequence !== 'good')
				continue;
			if (objUnit.latest_included_mc_index < min_mci || objUnit.latest_included_mc_index > max_mci)

				continue;

				if (message.app !== 'data_feed')
					return;

				if (!ValidationUtils.hasOwnProperty(payload, feed_name))
					return;
				var feed_value = payload[feed_name];
				if (value === null || value === feed_value || value.toString() === feed_value.toString())
					arrCandidates.push({
						value: string_utils.getFeedValue(feed_value, bLimitedPrecision),
						latest_included_mc_index: objUnit.latest_included_mc_index,
						level: objUnit.level,
						unit: objUnit.unit,

					});
