### Title
Webhook signature is verified against an organization derived from the payload while writes are dispatched to a repository derived independently from the same payload, enabling cross-tenant webhook forgery in multi-GitHub-App deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which HMAC `webhook_secret`) to validate a webhook against using `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`). Every webhook handler, however, resolves the repository/stack it *acts on* using a different, independently-controlled field of the same body: `repository.full_name`. In a Shipit deployment configured with multiple GitHub Apps (one per organization, an explicitly documented and supported configuration), an attacker who controls a webhook for one tenant organization can set `repository.owner.login` to that (their own) organization — so the signature check passes with a secret they legitimately possess (or that is unset) — while setting `repository.full_name` to point at a completely different, unrelated organization's repository tracked by the same Shipit instance. The handler layer never re-validates that the two fields agree, so the forged event is processed against the victim repository's stack.

### Finding Description
`verify_signature` picks the verifying app like this: [1](#0-0) 
and `repository_owner` is taken verbatim from the request body: [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization key when the multi-app config schema is used: [3](#0-2) 

This multi-app-per-organization mode is a first-class, documented deployment pattern: [4](#0-3) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the entire payload to the registered handlers, with no re-check that the verified organization matches anything else in the payload: [5](#0-4) 

Every default handler determines *which repository/stack to mutate* using `repository.full_name`, a field completely separate from `repository.owner.login`/`organization.login` used for signature selection: [6](#0-5) 

For example, the push handler triggers a sync job against whichever stack is found via `full_name`: [7](#0-6) 

Because `repository.owner.login` and `repository.full_name` are two independent JSON keys under attacker control before the HMAC is computed, nothing forces them to be consistent. In a genuine GitHub-originated webhook they are always consistent (GitHub itself fills them in from the real repository), but here the *validity of the signature* is evaluated against the organization named in one field, and the *write target* is resolved from another, unrelated field. This is precisely the equality the report's bug class breaks: `organization that authenticated == repository that is written` is assumed but never enforced.

### Impact Explanation
An operator who runs one Shipit instance for multiple GitHub organizations (each with its own `GitHubApp`/`webhook_secret`, as documented) is exposed to cross-tenant forgery: a party who legitimately owns/administers organization A's GitHub App webhook (and therefore knows A's `webhook_secret`, or for whom A's `webhook_secret` is left blank as the docs mark it "optional") can craft a signed request where `repository.owner.login` = `"A"` (passes signature check against A's secret) but `repository.full_name` = `"B/victim-repo"` for a different tenant B tracked by the same instance. This makes the engine execute cross-repository writes it should never authorize for an A-scoped credential: enqueuing `GithubSyncJob` for B's stack, archiving/unarchiving B's review stacks via the `pull_request`/label handlers, creating spoofed `status`/`check_suite` entries on B's commits, or creating arbitrary `Team`/`User` records via the `membership` handler — all without any credential belonging to organization B. This is a cross-repository write achieved purely by mismatched field trust, not by possessing the target's secret.

### Likelihood Explanation
Exploitation requires only: (1) a Shipit deployment using the multi-organization GitHub App configuration (an officially documented, supported setup for shared/multi-tenant Shipit instances), and (2) the attacker being a legitimate but low-trust user of *any one* of the configured organizations (or an organization for which `webhook_secret` was left unset, which the docs explicitly permit). No access to the victim organization's secret, GitHub token, or Shipit session is needed. Crafting the forged JSON body is trivial once one valid `(organization, secret)` pair is known.

### Recommendation
After computing `repository_owner`/verifying the signature, re-derive the effective organization from `repository.full_name` (or `organization.login`) used by the handlers and require it to match the organization whose secret validated the request; reject the webhook otherwise. Alternatively, bind webhook processing to the `Repository`/`Stack` record already scoped to a known organization, and refuse to process events whose `full_name` owner differs from the verified organization.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `docs/setup.md`'s "Using Multiple Github Applications" section).
2. As a party who administers `OrgA`'s webhook (and thus knows `OrgA`'s `webhook_secret`), craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Sign the raw body with `OrgA`'s `webhook_secret` and send it to `/webhooks` with `X-Github-Event: push` and the correct `X-Hub-Signature`.
4. `verify_signature` looks up `Shipit.github(organization: "OrgA")` and succeeds (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and enqueues a sync against `OrgB`'s stack — despite the request only ever proving knowledge of `OrgA`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
