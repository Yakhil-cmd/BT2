### Title
Private asset payment payloads (textcoin secrets) are written to disk with default, world-readable file permissions - (File: wallet.js)

### Summary
When a user sends a private (non-public) asset payment to a recipient who is not yet a paired device — the "textcoin" flow — `wallet.js` serializes the recipient's spending mnemonic together with the full chain of private elements needed to claim the funds, and writes that ZIP archive to disk via a bare `fs.writeFile` call with no explicit file mode. This mirrors the Himmelblau bug class: a secret that functions exactly like a bearer credential (whoever holds it can claim/spend the asset) is persisted to storage with default OS permissions instead of an owner-only mode, unlike other sensitive stores in the same codebase (`kvstore.js`, `sqlite_pool.js`) which explicitly create their data directories with `mode = parseInt('700', 8)`.

### Finding Description
`storePrivateAssetPayload` builds a JSON object containing the plaintext `mnemonic` (which, via `expandMnemonic`, deterministically derives the private key and address controlling the private-asset output) and `chains` (the full private-element proof chain required to spend it), zips it, and writes it to `fullPath`: [1](#0-0) 

The write uses Node's default `fs.writeFile` mode (`0o666` masked by the process umask, typically resulting in world- or group-readable files, e.g. `644`), with no attempt to restrict permissions to the owner only: [2](#0-1) 

Contrast this with how the library treats other sensitive local storage: application data and database directories are explicitly created with owner-only `0700` permissions: [3](#0-2) [4](#0-3) 

This inconsistency means the textcoin private-payment secret file — effectively a bearer credential for the private asset output, analogous to Himmelblau's world-readable Kerberos TGT cache — is not protected with the same rigor as the rest of the wallet's sensitive data.

### Impact Explanation
Anyone with local filesystem read access on the machine (another local user account, a background process, a backup/sync agent that preserves default permissions, etc.) can read the mnemonic and private chain before the intended recipient claims it. Since the mnemonic derives the private key controlling the private-asset UTXO, the attacker can construct and broadcast a claiming transaction ahead of the legitimate recipient (`receiveTextCoin`/`handlePrivatePaymentFile` flow validates the chain and lets whoever presents the mnemonic first sweep the funds). This results in concrete unauthorized spending / theft of the private-asset payment, i.e., a direct fund-loss condition for the sender/recipient of a private payment.

### Likelihood Explanation
Reaching this path only requires calling `sendMultiPayment` with a private (`is_private`) asset payment to an address for which no device pairing exists (the textcoin case) and supplying `opts.getPrivateAssetPayloadSavePath` — a normal wallet feature exposed to any wallet user. No malicious peer/hub cooperation, elevated privileges, or race against consensus timing beyond “read the file before the recipient imports it” is required, and the flow is triggered directly by `wallet.js:storePrivateAssetPayload` from user-initiated code: [5](#0-4) 

### Recommendation
When writing the private-asset payload ZIP (and any other file containing mnemonics/private keys/private chains), explicitly set restrictive file permissions (owner read/write only, e.g. mode `0600`) instead of relying on `fs.writeFile`'s default mode, mirroring the `0700` directory protections already used in `kvstore.js` and `sqlite_pool.js`. Consider encrypting the payload at rest or requiring the file to be moved immediately into a directory with locked-down permissions.

### Proof of Concept
1. On a multi-user machine, Alice sends a private-asset payment via `sendMultiPayment` to an email/text recipient not yet paired as a device, triggering the textcoin flow with `getPrivateAssetPayloadSavePath` pointing to a shared/download directory.
2. `storePrivateAssetPayload` (wallet.js:2850) writes the mnemonic + private chains to `fullPath` using `fs.writeFile(fullPath, zipFile, cb)` with default permissions.
3. Any other local user (or process) with read access to that directory reads the resulting ZIP, extracts `private_textcoin`, obtains `mnemonic`, and calls the equivalent of `receiveTextCoin`/`handlePrivatePaymentFile` before the intended recipient, sweeping the private-asset funds to an address they control.
