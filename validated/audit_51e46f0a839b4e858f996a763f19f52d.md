### Title
Bridge Operator Can Front-Run KLAY/ERC20 Transfer Fee to Drain User Funds Without Timelock or Upper Bound — (`contracts/service_chain/bridge/BridgeFee.sol`)

### Summary
The Kaia service-chain bridge stores `feeOfKLAY` and `feeOfERC20` with no upper bound and no timelock. A bridge operator (threshold defaults to 1) can atomically raise the fee to just below a user's `msg.value` in the same block, causing the user to lose nearly all their KAIA/ERC20 to the fee receiver. The fallback function is the most critical path because it passes `feeOfKLAY` as the `_feeLimit` at execution time, making the user's entire value subject to the fee that was in effect when the transaction executed.

### Finding Description

`BridgeFee.sol` stores the bridge fees with no cap:

```solidity
uint256 public feeOfKLAY = 0;
mapping (address => uint256) public feeOfERC20;
```

`_setKLAYFee` and `_setERC20Fee` accept any `uint256` value with no maximum: [1](#0-0) 

`setKLAYFee` in `BridgeTransferKLAY.sol` takes effect immediately once the operator threshold is reached: [2](#0-1) 

The `BridgeOperator` constructor sets the default threshold to **1** for all vote types, meaning a single operator can change fees in one transaction: [3](#0-2) 

The fallback function passes `feeOfKLAY` as the `_feeLimit` at execution time: [4](#0-3) 

Inside `_payKLAYFeeAndRefundChange`, the fee is read from storage at execution time and the only check is `_feeLimit >= fee`: [5](#0-4) 

The `_voteConfiguration` mechanism provides no timelock — it increments `configurationNonce` and returns `true` in the same transaction: [6](#0-5) 

### Impact Explanation

A malicious bridge operator can front-run a user's fallback call:

1. User sends `msg.value = 1.4 KAIA` to the bridge fallback, expecting `feeOfKLAY = 0.4 KAIA`.
2. Operator observes the pending transaction and calls `setKLAYFee(1.39 KAIA, configurationNonce)` with higher gas. With threshold = 1, this takes effect immediately.
3. User's fallback executes: `_requestKLAYTransfer(msg.sender, feeOfKLAY=1.39, ...)`.
4. `require(msg.value > _feeLimit)` → `1.4 > 1.39` passes.
5. `_payKLAYFeeAndRefundChange(1.39)`: `fee = 1.39`, `_feeLimit >= fee` passes, fee receiver receives **1.39 KAIA**.
6. `RequestValueTransfer` emits `value = msg.value − _feeLimit = 0.01 KAIA` — the user receives only 0.01 KAIA on the counterpart chain instead of 1.0 KAIA.

The user loses **1.39 KAIA** to the fee receiver instead of the expected 0.4 KAIA. The same attack applies to ERC20 transfers via `requestERC20Transfer` / `onERC20Received` where `_feeLimit` is user-supplied but the fee can be raised to equal it.

The corrupted value is `feeOfKLAY` / `feeOfERC20[token]` in bridge contract storage, which directly controls how much KAIA/ERC20 is drained from the user's `msg.value` or approved allowance.

### Likelihood Explanation

- The default operator threshold is 1, so a single operator can execute this unilaterally.
- The bridge operator is a semi-trusted actor set by the bridge owner (service chain operator). Users of the bridge implicitly trust this actor, but the actor is not cryptographically constrained from abusing fee changes.
- There is no on-chain announcement period, no maximum fee cap, and no event-based delay before the new fee takes effect.
- The fallback function is the most exposed path because it reads `feeOfKLAY` at execution time as both the fee and the feeLimit.

### Recommendation

1. **Add a maximum fee cap** in `_setKLAYFee` and `_setERC20Fee` (e.g., a percentage of the transfer value or an absolute maximum).
2. **Add a timelock** to fee changes: store a pending fee with an activation timestamp and only apply it after a delay (e.g., 24 hours), giving users time to observe and react.
3. **Require multi-operator consensus** (threshold > 1) for fee changes in production deployments, and document this as a security requirement.
4. **Emit a `FeeChangePending` event** when a fee change is proposed, so off-chain monitoring can alert users before the change takes effect.

### Proof of Concept

```
State: feeOfKLAY = 0.4 KAIA, configurationNonce = N, threshold = 1

Block N:
  Tx A (operator): setKLAYFee(1.39e18, N)
    → _voteConfiguration(N): threshold met (1/1), configurationNonce → N+1
    → _setKLAYFee(1.39e18): feeOfKLAY = 1.39 KAIA

  Tx B (user, same block, after Tx A): fallback{value: 1.4e18}
    → _requestKLAYTransfer(user, feeOfKLAY=1.39e18, "")
    → require(1.4e18 > 1.39e18) ✓
    → _payKLAYFeeAndRefundChange(1.39e18):
         fee = feeOfKLAY = 1.39e18
         require(1.39e18 >= 1.39e18) ✓
         feeReceiver.call{value: 1.39e18}()  ← 1.39 KAIA stolen
         feeRefund = 0
    → RequestValueTransfer emitted with value = 1.4e18 - 1.39e18 = 0.01 KAIA

Result: user receives 0.01 KAIA on counterpart chain; 1.39 KAIA transferred to fee receiver.
Expected: user receives 1.0 KAIA; 0.4 KAIA to fee receiver.
Loss: 0.99 KAIA drained from user.
```

    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }
