### Title
Webhook signature scope selection is unbound from the repository actually acted upon, allowing cross-repository/cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate the raw webhook body against based on `repository.owner.login` (falling back to `organization.login`) taken from the *unverified* JSON payload. Once that HMAC check passes, every downstream handler — `Shipit::Webhooks::Handlers::Handler#repository_name` and the many handlers that call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — resolves the target `Stack`/`Repository` from a *different* field of the same payload: `repository.full_name`. Nothing ties `repository.owner.login` (the value used to pick the signing organization) to `repository.full_name` (the value used to select the object that gets mutated). An attacker who can produce a validly-signed payload for any one organization configured on the Shipit instance (their own org, or any org whose `webhook_secret` is blank) can therefore forge a payload whose `full_name` field points at a completely unrelated repository/stack and have Shipit act on it.

### Finding Description
- `verify_signature` computes `repository_owner` from the payload itself and uses it to pick which GitHub App/organization's secret to verify with: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` validates the HMAC using the secret configured for that organization, but returns `true` unconditionally if no secret is configured for that org: [3](#0-2) 

- Multiple independent organizations, each with their own optional `webhook_secret`, are supported via `Shipit.github(organization:)`: [4](#0-3) 

- After the signature check passes, the controller blindly dispatches the raw JSON to handlers: [5](#0-4) 

- Every handler resolves the affected `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a field never compared to `repository_owner`: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

Equality that should hold but is never enforced:
`organization identity that authenticated the HMAC (repository.owner.login / organization.login)` == `repository whose Stack/PR/status gets mutated (repository.full_name)`

Because the entire raw body is HMAC-signed as one blob, an attacker cannot tamper with a *legitimately captured* webhook from a victim org — but the attacker is free to author an entirely new JSON body from scratch, put whatever org login they like in `repository.owner.login`/`organization.login` (selecting which secret must match), and put an unrelated victim `full_name` in `repository.full_name`. If that chosen org has no `webhook_secret` configured (a common state for a lightly-configured org in a multi-org Shipit deployment, since the field is optional per `lib/shipit/github_app.rb:50` `@webhook_secret = @config[:webhook_secret].presence`), signature verification trivially returns `true` regardless of the value of `X-Hub-Signature`, and the forged `full_name` is accepted unchecked. Alternatively, if the attacker controls (or has installed the GitHub App for) any single organization tracked by the shared Shipit instance, they know that org's real secret and can legitimately sign a payload naming a victim repository owned by a completely different, unrelated organization also tracked by the same instance.

The webhook endpoint requires no Shipit session, API token, or GitHub credentials of any kind — `resources :webhooks, only: :create` is a public unauthenticated route: [10](#0-9) 

### Impact Explanation
This is a cross-organization/cross-repository write bypassing the intended per-organization trust boundary that `Shipit.github(organization:)` is designed to enforce (Critical impact category "cross-repository writes"). Concretely, using a validly (or trivially) signed payload naming an org the attacker controls but with a forged `full_name` for a victim stack tracked by the same Shipit instance, an attacker can, without any privileged Shipit credentials:
- Force `PushHandler` to enqueue `stack.sync_github(expected_head_sha:)` against a victim stack.
- Force `PullRequest::OpenedHandler`/`LabeledHandler`/`UnlabeledHandler`/`ClosedHandler` to `archive!`/`unarchive!`/`find_or_create!` review stacks belonging to a victim repository.
- Force `StatusHandler`/`CheckSuiteHandler` to inject fabricated commit statuses/check-run refreshes on victim commits, potentially influencing CI-gated deploy/merge decisions on a repository the attacker does not own.

None of this requires possessing the victim organization's `webhook_secret`, a Shipit `ApiClient` token, or a GitHub App private key.

### Likelihood Explanation
Likelihood is highest in the common Shipit-as-a-service deployment pattern where a single Shipit instance tracks many organizations/repositories via the multi-org `Shipit.github` config (`lib/shipit.rb#github_app_config`), and where `webhook_secret` is an optional per-org setting (`lib/shipit/github_app.rb:50`). Any org lacking a `webhook_secret`, or any org the attacker themselves administers (e.g. they installed the same shared GitHub App on their own org, which is a legitimate, unprivileged action available to any GitHub user), is sufficient to exploit this against every other stack hosted on that same Shipit instance. No social engineering, TLS interception, or Shipit account is required — only crafting and POSTing a JSON body to a public endpoint.

### Recommendation
In `WebhooksController#verify_signature`/handler dispatch, cross-validate that the repository identity used to select the signing secret (`repository.owner.login`/`organization.login`) is the same repository identity used to resolve the target `Stack`/`Repository` (`repository.full_name`'s owner segment) before invoking any handler. Reject the webhook (422) if they diverge. Additionally, treat a missing per-organization `webhook_secret` as "reject unsigned webhooks for this org" rather than "skip verification entirely," or require `webhook_secret` to be mandatory for any organization added to a multi-org configuration.

### Proof of Concept
Given a Shipit instance configured with two organizations, `attacker-org` (secret known to/controlled by the attacker, or unset) and `victim-org` (hosts `victim-org/victim-repo`, tracked as a Shipit stack):

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<valid HMAC for attacker-org's secret, or anything if attacker-org has no secret configured>

{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/master",
  "after": "<any sha>"
}
```

- `repository_owner` resolves to `"attacker-org"` → `verify_signature` validates against `attacker-org`'s config/secret (or passes unconditionally if unset) → passes.
- `PushHandler#stacks` resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` → matches the victim's tracked `Stack` → `stack.sync_github(expected_head_sha:)` is invoked on the victim's stack, despite the signature only proving authorship by `attacker-org`.

The same technique substituting the `pull_request` event body drives `stack.archive!`/`unarchive!`/`find_or_create!` on the victim's review stacks via `OpenedHandler`/`LabeledHandler`/`ClosedHandler`, all of which resolve their target solely from `params.repository.full_name`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
