### Title
Asset definer can permanently freeze holders' funds by replacing the `spender_attested` attestor list via `asset_attestors` - (File: validation.js, storage.js)

### Summary
For assets defined with `spender_attested: true`, the definer can at any time post an `asset_attestors` message that fully replaces the list of trusted attestors for that asset. Spend/output validation always uses only the *latest* attestor list, with no history retained and no timelock. A holder who received (and still holds) coins of that asset while being legitimately attested under the old list becomes permanently unable to spend them the instant the definer swaps the list, exactly mirroring the reported Tokemak bug class where a privileged party clears state that another party needs to claim/use, with no protection window.

### Finding Description
When an asset is defined with `spender_attested: true`, every payment (issue or transfer) of that asset requires the relevant addresses (issuer and, for divisible assets, output addresses too) to be attested by one of the asset's current attestors: [1](#0-0) 

The set of trusted attestors is not fixed at issuance — the definer (single author only) can update it later with an `asset_attestors` message: [2](#0-1) 

Crucially, `readAsset()` never retains history of attestor lists: it always looks up the single *latest* `asset_attestors` unit (`ORDER BY level DESC LIMIT 1`) and uses only that list when deciding who is currently attested: [3](#0-2) 

`filterAttestedAddresses()` then checks `attestor_address IN (?)` against exactly that current list when validating who may receive/hold outputs: [4](#0-3) 

And spend validation of already-existing coins re-checks `objAsset.arrAttestedAddresses` (derived from the *current* list) against the coin owner on every subsequent spend, for both divisible/public and private/indivisible payment types: [5](#0-4) [6](#0-5) 

This is structurally identical to the reported bug class: a privileged party (here, the asset definer — reachable simply as the original "asset issuer") clears/replaces state (the attestor list) that other unprivileged parties (holders of already-issued/received coins) depend on to exercise a right they've already earned (the right to spend coins they already possess). Just as `MainRewarder.clearExtraRewards()` has no timelock or protection for users with unclaimed rewards, `asset_attestors` has no grace period, no requirement to keep previously-attested holders spendable, and no mechanism to "grandfather" existing coin holders when the attestor list changes.

### Impact Explanation
A holder who legitimately received transferable, `spender_attested` coins (public or private) while attested under attestor list A can be locked out of spending those coins forever if the definer later posts a new `asset_attestors` list B that drops the attestor who vouched for them (or drops all attestors who ever attested that user), and the holder cannot get themselves re-attested (e.g., attestor is unresponsive, or was intentionally dropped). Since the check is applied at every future spend (not only at receipt time), funds already held become permanently unspendable/frozen — this is a fund-freezing condition matching the "AA fund loss or freezing" acceptance criterion, without requiring any error or bug in the spender's own behavior.

### Likelihood Explanation
The path is trivially reachable by any asset definer without special network privileges — merely posting a single-authored `asset_attestors` unit is enough, as validated in `validateAttestorListUpdate()`. No cooperation from stability-conscious actors is needed beyond the unit becoming stable, which occurs through normal DAG confirmation. Because `readAsset()` always resolves to the single latest attestor-list unit with no fallback to older lists, the freezing is deterministic and occurs as soon as the new list becomes the "latest" stable one relative to the spending unit's `last_ball_mci`.

### Recommendation
Consider one or more of the following: (1) grandfather already-attested addresses so that once an address/coin owner is validly attested, they remain eligible to spend already-received outputs of that asset even after the attestor list changes; (2) require a timelock/grace period before a new `asset_attestors` list becomes effective for existing outputs, mirroring the report's suggested fix; (3) validate spend-time attestation against the attestor list that was current at the time the output was created/received, rather than only the latest list, similar to how other definition changes are pinned to `last_ball_mci`.

### Proof of Concept
1. Definer issues asset X with `spender_attested: true` and initial `attestors: [A]`.
2. Attestor A posts an `attestation` message attesting address U.
3. Definer (or A) sends coins of asset X to U; the transfer succeeds because U is attested under the current list, per `validatePaymentInputsAndOutputs` / `filterAttestedAddresses` (`storage.js:1959-1974`).
4. U does not immediately spend the coins.
5. Definer posts a new `asset_attestors` message with `attestors: [B]` (dropping A), which validates fine per `validateAttestorListUpdate` (`validation.js:2829-2848`) since it only checks that the new list is well-formed, not that it preserves existing holders' spendability.
6. Once this new list's unit is the latest stable `asset_attestors` unit at spend-validation time, `readAsset()`'s `addAttestorsIfNecessary()` (`storage.js:1917-1946`) returns only `[B]` as trusted attestors.
7. U attempts to spend the previously received coins; validation reaches `if (objAsset.spender_attested && objAsset.arrAttestedAddresses.indexOf(owner_address) === -1) return cb("owner address is not attested");` (`validation.js:2504-2507` for indivisible transfers, analogous check at `2429-2433`), which now fails because U is no longer in the attested set.
8. U's coins are permanently frozen unless attestor B (or a future attestor) re-attests U and the definer never re-adds a similarly hostile list — with no protocol-level timelock or protection, exactly analogous to losing unclaimed rewards when `clearExtraRewards()` is called before the user claims.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
