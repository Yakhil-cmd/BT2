## Analog Found

The Optimism report's core issue — an identity/binding check performed on one field of a message while a different, unguarded field is what execution actually acts on — has a direct analog in `shipit-engine`'s webhook handling pipeline.

### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every handler acts on the independent, unchecked `repository.full_name` field, allowing cross-organization stack writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to check the `X-Hub-Signature` against using `repository_owner`, read from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once verification passes, the raw payload is dispatched to handlers that instead resolve the target repository/stacks using the **separate** field `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties these two fields together, so the "authenticated organization" and the "repository actually written to" are never checked for equality.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-49` verifies the signature like this: [1](#0-0) 

`repository_owner` is taken from the payload itself: [2](#0-1) 

`Shipit.github(organization:)` picks a distinct config (including a distinct `webhook_secret`) per organization in multi-org setups, which is a documented, supported configuration: [3](#0-2) [4](#0-3) 

After signature verification succeeds, the raw parsed payload is passed unchanged to every registered handler: [5](#0-4) 

But every handler resolves its target repository/stacks from `repository.full_name`, a field completely independent from `repository.owner.login`: [6](#0-5) 

`PushHandler`, for example, uses that repository's stacks to trigger a GitHub sync/deploy pipeline with an attacker-supplied `expected_head_sha`: [7](#0-6) 

Pull-request handlers go further, performing writes such as archiving/unarchiving review stacks or updating pull request state on the repository resolved from `full_name`: [8](#0-7) [9](#0-8) 

The binding that should hold is:
```
organization_used_for_signature_verification (repository.owner.login) == owner_of(repository.full_name)
```
This equality is never checked. `verify_signature` only proves "the request body was signed by *some* configured org's webhook secret" — it does not prove that the org whose secret matched is the same org whose repository is subsequently acted upon in the same payload.

### Impact Explanation
On any Shipit instance configured with multiple GitHub organizations (the documented "Using Multiple Github Applications" setup in `docs/setup.md:182-209`, exactly mirrored by `test/dummy/config/secrets_double_github_app.yml`), an attacker who controls (or is simply a legitimate GitHub App owner/admin of) **one** of the configured organizations — call it `evil-org` — knows that org's own `webhook_secret`. That attacker can POST an arbitrary JSON body directly to the shared `/webhooks` endpoint with:
- `repository.owner.login = "evil-org"` (drives secret selection only)
- `repository.full_name = "victim-org/victim-repo"` (drives all actual handler logic)
- an `X-Hub-Signature` computed with `evil-org`'s own secret

`verify_signature` succeeds (it is checking `evil-org`'s secret against a payload the attacker controls), and the handler dispatch then operates entirely on `victim-org/victim-repo`, which the attacker has no legitimate access to. Depending on the event type this can:
- Trigger `GithubSyncJob` on the victim's stacks with an attacker-chosen `expected_head_sha` (`PushHandler`).
- Archive/unarchive victim review stacks, or mutate victim pull request records (`pull_request/*_handler.rb`).
- Manipulate victim commit statuses/check runs feeding the merge queue, depending on which webhook events are wired up.

This is a cross-organization/cross-repository write triggered purely by controlling a different, legitimately-configured tenant of the same Shipit instance — no access to the victim's GitHub App, webhook secret, or Shipit session is required. This matches the Critical impact bar ("cross-repository writes").

### Likelihood Explanation
Requires only: (1) the target Shipit instance uses the multi-org GitHub App configuration (an explicitly documented, supported deployment mode), and (2) the attacker controls/administers any one of the other organizations configured on that same instance. No privileged Shipit account, API token, or victim-org credential is needed — only knowledge of one's own org's webhook secret, which any org admin legitimately possesses. This is a realistic configuration for any Shipit deployment serving multiple GitHub organizations.

### Recommendation
After the payload is parsed but before dispatching to handlers, verify that the organization used to select the webhook secret (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` (and any other repository-identifying field consumed downstream, e.g. `organization.login` for `membership` events). Reject the webhook (422) on mismatch. Alternatively, thread the verified organization through to `Shipit::Webhooks::Handlers::Handler` and have `repository_name`/`stacks` cross-check it against the resolved repository's owner before performing any writes.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `evil-org` and `victim-org`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the admin of `evil-org`'s GitHub App, compute `sha1=HMAC(evil-org_webhook_secret, body)` for a hand-crafted `push` payload body where:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "evil-org" } }
   }
   ```
3. POST this body to `/webhooks` with headers `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "evil-org")`, verifies successfully using `evil-org`'s secret.
5. `PushHandler#process` runs `Repository.from_github_repo_name("victim-org/victim-repo").stacks... .sync_github(expected_head_sha: "<attacker-chosen-sha>")`, affecting `victim-org`'s stack despite the request never being authenticated against `victim-org`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
