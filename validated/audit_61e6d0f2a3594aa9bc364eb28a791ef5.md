### Title
AA composer sends payments of `spender_attested`/conditioned assets without pre-checking attestation or transfer/issue conditions, causing permanent bounce/freeze of AA-held asset balance - (File: aa_composer.js)

### Summary
An AA that manages an ocore asset with `spender_attested=true` or a `transfer_condition`/`issue_condition` (the ocore analog of BUIDL's admin-settable `minUSTokens` compliance rule) will unconditionally attempt to build and commit an outgoing payment for that asset without first verifying that the destination addresses are still attested, or that the transfer/issue condition still holds. The check is deferred entirely to unit-level validation, which runs only after the AA has already deducted the balance and computed its state update. If the condition fails, the AA response bounces — and since the underlying condition (attestor list, or the formula behind `transfer_condition`/`issue_condition`) has not changed, every subsequent attempt to disburse that asset from the AA will bounce identically, permanently freezing the AA's held balance of that asset, exactly mirroring the reported `ousgInstantManager`/`BUIDL` `minUSTokens` issue.

### Finding Description
In `aa_composer.js`, when an AA response includes a `payment` message for a non-base asset, the composer loads the asset info (including current attestor list) but does not check eligibility before proceeding to build the payment: [1](#0-0) 

It calls `storage.loadAssetWithListOfAttestedAuthors` purely to get `fixed_denominations`/`is_private` flags and complete the payload — it never inspects `objAsset.arrAttestedAddresses` for the AA's own address or for the output addresses, and never evaluates `objAsset.transfer_condition`/`issue_condition` before continuing. The actual enforcement of attestation and transfer/issue conditions happens only in `validation.js`, after the unit has been fully composed: [2](#0-1) 

This mirrors the `ServiceRegulated.sol` check in the BUIDL report: the compliance rule (there, `minUSTokens`; here, `spender_attested`/`transfer_condition`) is enforced only at the moment of transfer/validation, not checked proactively by the code that decides to initiate the transfer (there, `_redeemBUIDL`; here, the AA's payment-composition logic in `sendUnit`).

The attestor list itself is fully mutable by the asset's definer at any time via an `asset_attestors` message, validated with almost no constraint beyond signature and list format: [3](#0-2) 

Once `validateAndSaveUnit` is called on the composed response unit, if it fails validation (e.g. "some output addresses are not attested" or "transfer or issue condition not satisfied"), the flow calls `bounce(err)`: [4](#0-3) 

Because the AA logic that decides *what* to send is oblivious to the attestation/condition state, and that state is controlled by a third party (the asset definer) who can update it at will, the AA will keep composing the same failing payment on every subsequent trigger that tries to move this asset, indefinitely.

### Impact Explanation
An AA that custodies a `spender_attested` or condition-bearing asset (analogous to Ondo's `ousgInstantManager` custodying `BUIDL`) can have its outgoing transfers of that asset permanently blocked if the asset definer revokes attestation for the AA's address, revokes attestation for typical recipient addresses, or sets a `transfer_condition`/`issue_condition` formula that becomes unsatisfiable for the AA's payment pattern (e.g., referencing an oracle value the AA does not track, similar to `minUSTokens`). Because the AA has no fallback logic and always attempts to send the requested amount without pre-validating eligibility, every disbursement attempt bounces, and the AA's balance of that asset becomes stuck/frozen — this matches the accepted "AA fund loss or freezing" impact criterion.

### Likelihood Explanation
Reaching this requires: (1) an AA integrating a third-party issued asset that uses `spender_attested`, `issue_condition`, or `transfer_condition`, and (2) the definer of that asset changing the attestor list or condition parameters after the AA has accumulated a balance — both realistic actions available to any asset definer at any time and fully within the "asset issuer" and "AA trigger sender" threat surface named in scope. No malicious peer/node/hub cooperation is required; a single `asset_attestors` unit from the definer combined with normal AA triggers is sufficient to reproduce the freeze.

### Recommendation
Before composing an outgoing asset payment in `aa_composer.js`, have the AA logic (or the oscript/formula layer) proactively check `objAsset.spender_attested` against `arrAttestedAddresses` for both the AA's own address and the intended recipients, and evaluate `transfer_condition`/`issue_condition` via `Definition.evaluateAssetCondition` prior to deducting balances and committing the response. If the condition would fail, the AA should be able to branch (e.g. bounce early with a clear reason, or hold/queue the payment) rather than only discovering the failure after `validateAndSaveUnit`. Additionally, expose attestation/condition status to oscript (e.g. via a `attested`-style formula primitive already used in `definition.js`) so AA authors can guard transfers of externally-governed assets defensively, similar to the mitigation Ondo was asked to add for `BUIDL`.

### Proof of Concept
1. Definer creates an asset `A` with `spender_attested: true` and an initial attestor list including AA address `X` and typical user addresses (`create_an_asset.oscript` pattern shown in `test/samples/create_an_asset.oscript`).
2. AA `X` accumulates a balance of asset `A` by receiving payments/triggers over time.
3. Definer posts an `asset_attestors` message removing `X` (or removing common recipient addresses) from the attestor list — this is valid per `validateAttestorListUpdate` (validation.js:2829-2848), requiring only the definer's signature.
4. A user triggers AA `X` to redeem/send asset `A`. The AA composes the payment via `sendUnit` (aa_composer.js:1323-1344) without checking attestation, deducts its internal balance, and calls `validateAndSaveUnit`.
5. Validation fails at `validation.js:2630-2641` ("some output addresses are not attested") or at `validation.js:2115-2122` if the AA itself is an issuer/spender no longer attested; `aa_composer.js` calls `bounce(err)` (aa_composer.js:1408-1410).
6. Every subsequent trigger attempting to move asset `A` out of AA `X` repeats steps 4-5, permanently freezing the AA's `A` balance.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
