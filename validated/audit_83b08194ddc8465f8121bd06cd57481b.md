### Title
Out-of-bounds read in PEM public-key DER parsing reachable via `is_valid_sig` in oscript/AA formulas - (File: signature.js)

### Summary
CVE-2018-1000223 is a classic "trust the header, index into the buffer without validating actual length" bug in `WavInFile::readHeaderBlock()`. The analogous pattern in ocore is `validateAndFormatPemPubKey()` and `verifyMessageWithSecp256k1PemPubKey()` in `signature.js`, which parse attacker-supplied base64/DER-encoded PEM key material by reading length bytes out of the buffer and then indexing/slicing at offsets derived from those untrusted length bytes, with only partial bounds checks.

### Finding Description
`validateAndFormatPemPubKey()` decodes an attacker-controlled base64 string into a `Buffer` and then walks the DER structure using byte values read directly from the buffer as offsets and lengths, e.g.: [1](#0-0) 
The code branches on `contentAloneBuffer[1]` to decide `identifiersStart`/`identifiersLength`, but there is no explicit check that `contentAloneBuffer` is long enough to contain the bytes being read at indices like `contentAloneBuffer[3]`, `contentAloneBuffer[4]`, `contentAloneBuffer[5]` before those reads occur, and `identifiersLength` is then used to slice `contentAloneHex` at `identifiersStart*2 + identifiersLength*2` without validating that this remains within the buffer bounds relative to the actual key-length checks performed afterward: [2](#0-1) 

Similarly, `verifyMessageWithSecp256k1PemPubKey()` locates a fixed marker and then slices a fixed 65-byte window from the DER buffer based on the found index, `der.slice(bitStringIdx + 3, bitStringIdx + 68)`, relying on `.length !== 65` as the only post-hoc guard rather than validating the buffer size up front: [3](#0-2) 

This mirrors the SoundStretch bug class: header/length fields taken from untrusted input are used to compute buffer offsets before the total buffer size is validated against those offsets, which in JavaScript manifests as `undefined` reads from `Buffer` indexing (not a memory-corruption RCE as in C++, but the same "unchecked header-derived offset" root cause) potentially leading to unexpected `undefined`/`NaN` values silently accepted as valid lengths, or exceptions that could be leveraged for behavioral differences between nodes.

### Impact Explanation
If PEM-key signature verification is reachable from unit/AA content (via `is_valid_sig`-style oscript functions in `formula/evaluation.js`, which references `PemPubKey` validation paths), a malformed PEM key crafted with truncated DER structure could cause a validation function to behave inconsistently (e.g., return `undefined`/throw where one node's Buffer semantics differ from another's, or accept a malformed key/signature pair). Because signature/definition validation results directly gate spending authorization and AA execution, any consensus-relevant divergence here could translate into node disagreement on unit validity — one of the accepted impact categories.

### Likelihood Explanation
I was not able to fully confirm, within the available tool budget, the exact call path connecting `formula/evaluation.js`'s PEM/signature-related opcodes (`is_valid_sig`, etc.) to `validateAndFormatPemPubKey`/`verifyMessageWithSecp256k1PemPubKey` and confirm whether all necessary length checks are actually enforced earlier in that call chain (e.g. in `formula/validation.js` or `oscript.ne` grammar constraints on key string length before it reaches `signature.js`). The `hex_pub_key_length` check on line 180 does provide a downstream sanity check for algorithm/curve length, which reduces exploitability, but it occurs after the out-of-bounds indexing already happened.

### Recommendation
Add explicit length checks on `contentAloneBuffer` (and the DER buffer in `verifyMessageWithSecp256k1PemPubKey`) before indexing at computed offsets, e.g., verify `contentAloneBuffer.length > identifiersStart` and `contentAloneBuffer.length >= identifiersStart + identifiersLength` prior to slicing, and verify `der.length >= bitStringIdx + 68` before slicing the public key bytes. This should be done in `signature.js` functions `validateAndFormatPemPubKey` and `verifyMessageWithSecp256k1PemPubKey`.

### Proof of Concept
Not fully verifiable without confirming the exact end-to-end call path from an untrusted unit/AA field into `validateAndFormatPemPubKey`/`verifyMessageWithSecp256k1PemPubKey`; a background Devin session with full repo/test access would be needed to trace `formula/evaluation.js` opcode handling and `test/pem_sig.test.js` to construct a concrete short/truncated PEM buffer that triggers an out-of-bounds `Buffer` index during validation and confirm whether it produces an exploitable validity/consensus divergence, or is fully guarded elsewhere.

```javascript
function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;
```
