The reported bug is specific to the Gitcoin `RoundImplementation.sol` / `MerklePayoutStrategyImplementation.sol` design, where a private `_transferAmount()` helper sends a stored `_amount` via `Address.sendValue` while the enclosing function is separately `payable` and can receive an unrelated `msg.value`, causing any msg.value greater than `_amount` to be permanently stuck since `sendValue` doesn't return unspent value and the contract has no logic to refund it.

This bug class requires a decoupling between "value attached to a call" (`msg.value`) and "amount the function decides to transfer" (`_amount`), a mismatch that is possible in Solidity because `payable` functions implicitly receive `msg.value` independent of any function argument. I looked for a structural analog in the Polkadot SDK across the areas most likely to replicate this pattern:

- FRAME dispatchables never have an implicit "value sent with the call" that is decoupled from an explicit transfer amount. Balance movements in pallets like `broker`, `staking`/`staking-async`, `nomination-pools`, `society`, `tips` always transfer exactly the computed `amount`/`payout` via `T::Currency::transfer`, with no separate attached value that could exceed it, e.g. [1](#0-0) , [2](#0-1) .
- `pallet-revive`, which is the closest analog to EVM/Solidity semantics, models `call()` with an explicit `value: BalanceOf<T>` parameter that is exactly what gets transferred to `dest` — there is no separate implicit `msg.value` register that could diverge from this amount: [3](#0-2) . The pallet even explicitly reworked balance-transfer semantics to make the existential deposit transparent so that the supplied value is not silently reduced or left dangling, per [4](#0-3)  and [5](#0-4) .
- Excess/unused value handling in XCM (`RefundSurplus`, `refund_weight`, `TakeFirstAssetTrader`) is architecturally the closest concept to "returning unused value," but it operates on a completely different mechanism (holding registers and weight-based fee trading) where surplus is tracked and refunded by design, not silently dropped: [6](#0-5) , [7](#0-6) .

Since the underlying invariant violated in the report — an internal transfer amount decoupled from an attacker-controllable `msg.value` that is silently accepted and never checked — does not exist as a reachable pattern in FRAME extrinsics or in `pallet-revive`'s own value-transfer dispatchables (which bind the transferred amount directly to the declared parameter, not to a separate implicit value register), there is no demonstrable Polkadot SDK analog to this Solidity-specific bug class.

doc:
- audience: Runtime Dev
  description: |-
    This PR removes the `transfer` syscall and changes balance transfers to make the existential deposit (ED) fully transparent for contracts.

    The `transfer` API is removed since there is no corresponding EVM opcode and transferring via a call introduces barely any overhead.

    We make the ED transparent to contracts by transferring the ED from the call origin to nonexistent accounts. Without this change, transfers to nonexistant accounts will transfer the supplied value minus the ED from the contracts viewpoint, and consequentially fail if the supplied value lies below the ED. Changing this behavior removes the need for contract code to handle this rather annoying corner case and aligns better with the EVM. The EVM charges a similar deposit from the gas meter, so transferring the ED from the call origin is practically the same as the call origin pays for gas.
