### Title
Webhook signature verification is keyed by an attacker-chosen organization while the mutated commit/repository is unscoped — forged CI status enables unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/secret to validate an incoming webhook against using an unauthenticated field taken from the very payload it is about to validate (`repository.owner.login`, or `organization.login` as a fallback), then hands the entire raw body to every registered handler regardless of which organization actually owns the target data. Combined with the fact that `verify_webhook_signature` treats a missing `webhook_secret` as automatically valid, and that `StatusHandler` resolves the commit to mutate via a completely unscoped `Commit.where(sha:)` lookup, an attacker who can identify (or configure knowledge of) any org entry in `Shipit.github` that has no `webhook_secret` set can forge webhook events — including fake "success" CI statuses — for commits belonging to any other, securely configured organization/repository tracked by the instance.

### Finding Description
`WebhooksController#verify_signature` computes the "authenticating organization" purely from attacker-supplied JSON, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

That organization is used only to look up which `GithubApp` config (and therefore which `webhook_secret`) to check the signature against: [3](#0-2) 

Note `return true unless webhook_secret` — if the org selected by the attacker-controlled `repository.owner.login`/`organization.login` field has no `webhook_secret` configured (an explicitly documented, optional setting, see `docs/setup.md` line 30 and the multi-org example configs), signature verification is bypassed unconditionally, independent of the `X-Hub-Signature` header supplied.

Once verification "passes" (or is bypassed this way), `WebhooksController#create` dispatches the same raw payload to every handler for the event, with no re-binding to the organization that was used for signing: [4](#0-3) 

Handlers then act on attacker-controlled fields that are unrelated to (and unchecked against) the `repository_owner`/`organization.login` value used for signature selection. `StatusHandler` is the strongest case: it resolves the target `Commit` by a global, unscoped `sha` lookup, with no repository or organization filtering at all, and writes attacker-supplied `state`/`context`/`description` onto it: [5](#0-4) 

Creating a `Status` record has real side effects — it enables CI on the stack and schedules continuous delivery evaluation: [6](#0-5) 

Other handlers (`PushHandler`, `PullRequest::*Handler`) similarly key off `payload.dig('repository','full_name')` / `params.repository.full_name`, a field completely independent from the `repository_owner` used to pick the signing secret: [7](#0-6) [8](#0-7) 

**The broken binding, stated as an equality that should hold but doesn't:**
`organization whose secret authenticated the request == organization/repository/commit that the handler mutates`. Before the attacker's request, this equality trivially holds because a real GitHub webhook is signed per-installation and always carries a consistent `repository`/`organization`. After the attacker's request, the equality is broken: the "authenticating" side is an org picked from an unauthenticated field that may have no secret configured at all, while the "mutated" side (a `sha`-matched `Commit` in `StatusHandler`, or a `full_name`-matched `Repository` in other handlers) can belong to any organization/repository Shipit tracks.

### Impact Explanation
This allows an unprivileged external attacker (no Shipit session, no `ApiClient` token, no `webhook_secret`, no GitHub write access) to inject a forged "success" CI status for an arbitrary commit SHA it can observe (e.g. via GitHub's public API/UI, or any commit already listed on the target Shipit instance) belonging to a securely configured organization. Because `Status` creation directly feeds Shipit's CI/deployability gating (`enable_ci_on_stack`, `schedule_continuous_delivery`), this can make a commit that never actually passed CI appear deployable, leading to an **unauthorized deploy** — matching the Critical impact bar for this analysis.

### Likelihood Explanation
Exploitation requires only that the operator has configured Shipit with more than one GitHub App/organization (a supported, documented feature) and that at least one of those orgs has no `webhook_secret` set — itself explicitly documented as optional in `docs/setup.md`. No credentials, no GitHub write access, and no valid HMAC signature are required; the attacker only needs the `/webhooks` endpoint to be reachable and to know one such organization's name plus a target commit SHA.

### Recommendation
- Bind webhook signature verification to the specific configured secret for the delivery, not to an attacker-suppliable field in the unverified payload (e.g., require an explicit App/installation identifier from a trusted header, or verify against every configured secret and require a match rather than trusting a payload-selected org).
- Make `verify_webhook_signature` fail closed when no `webhook_secret` is configured for an org that has other, secret-bearing orgs configured, rather than returning `true`.
- Scope `StatusHandler` (and any other handler resolving records solely by attacker-controlled identifiers such as `sha`) to the repository/organization that was actually cryptographically verified for that specific request, not merely the event payload's `repository.full_name`/`sha`.

### Proof of Concept
1. Assume `Shipit.github` is configured with two orgs: `secure-org` (has `webhook_secret`) and `no-secret-org` (no `webhook_secret`, per the documented optional setting).
2. Attacker sends, with no valid signature:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "organization": {"login": "no-secret-org"},
  "sha": "<sha of a commit tracked under secure-org/some-repo>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://attacker.example"
}
```
3. `WebhooksController#verify_signature` computes `repository_owner = "no-secret-org"`, fetches its `GithubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the (absent/invalid) `X-Hub-Signature`.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matching the commit under `secure-org/some-repo`, and calls `commit.create_status_from_github!(params)`, persisting a forged "success" status and triggering `enable_ci_on_stack` / `schedule_continuous_delivery`.
5. The targeted commit under `secure-org/some-repo` now shows a fabricated passing CI status despite the attacker never possessing `secure-org`'s webhook secret or any GitHub credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
