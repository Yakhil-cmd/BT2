### Title
Cross-repository status forgery via unscoped SHA lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` writes GitHub `status` webhook payloads to `Commit` records matched by bare SHA with no repository/stack scoping, unlike every other handler in the same directory which resolves `stacks` via `repository_name` first. An attacker who owns a repository sharing a commit SHA with a victim's stack (e.g. via a fork, which naturally shares ancestor commit SHAs) can send a validly-signed webhook for their own repo and have it recorded as a status on the victim's identical-SHA commit, flipping deployability/merge/block state for a stack they never authenticated against.

### Finding Description
The broken binding: the code assumes `commit.sha == params.sha` for a given `Commit` record implies `commit.stack.repository == payload.repository`, i.e. `Commit.where(sha: params.sha)` is treated as if it only ever returns commits belonging to the repository that signed the webhook. That assumption is false: `sha` is a global 40-hex value not unique per repository, and the query performs no join/filter on stack/repository at all.

Code path:
- `Shipit::WebhooksController#create` parses the JSON body and dispatches to handlers after `verify_signature`, which only checks the HMAC signature against `Shipit.github(organization: repository_owner)` derived from the *attacker's own* `payload.repository.owner.login` [1](#0-0) . This proves the payload was sent by whoever controls that org/repo — it proves nothing about which stacks the SHA belongs to.
- `Handler#stacks`/`#repository_name` is the standard scoping mechanism used by other handlers (e.g. `CheckSuiteHandler#process` at [2](#0-1) , which resolves `stacks.where(branch: ...)` before touching commits) [3](#0-2) .
- `StatusHandler#process` skips this entirely: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . This queries across **all stacks in the database**, not just stacks belonging to the authenticated repository.
- `Commit#create_status_from_github!` writes a new `Status` row and recomputes `status`/`deployable?`/`blocked?` via `add_status`, which also triggers `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` when the new state is `success` [5](#0-4) .
- Deployability is derived from `Status::Group`, which computes `required_statuses` and treats a matching `context` as satisfying/blocking the commit [6](#0-5) , and `Commit#deployable?`/`#blocked?` directly react to `success?`/`blocking?` [7](#0-6) .

Exploit flow: an attacker forks the victim's GitHub repository (or otherwise ends up owning a repo whose git history contains a commit identical in SHA to one in the victim stack — trivially achievable via fork, since fork history literally shares ancestor SHAs with upstream). The attacker sends a signed `status` event from their own repo (`context: security/scan`, `state: success`, `sha: <shared-sha>`). `verify_signature` passes because the signature matches the attacker's own org's webhook secret. `StatusHandler` then finds the victim's `Commit` row with the same SHA (in a completely different `stack_id`) and writes a `success` status onto it, flipping `deployable?`/unblocking the victim stack and triggering `stack.schedule_merges`.

Existing guards do not catch this: `verify_signature` only authenticates *which org* sent the payload, not *which commit/stack* it may write to; `ExplicitParameters` only validates payload shape (`sha`, `state`, `context` types), not ownership; there is no `stacks`/`repository_name` filter anywhere in `StatusHandler`.

### Impact Explanation
An attacker-controlled webhook write is applied to a `Commit` belonging to a repository/stack the attacker does not own or authenticate as. This directly matches the "Critical: a payload for one repository mutating another's stack, commit, task or team" category — writing a `success` status for `security/scan` (a required context) can unblock a deploy, trigger `stack.schedule_merges`, and mark the victim commit `deployable?`, an unauthorized deploy/merge-adjacent state change. Repeatable against any stack whose commit history overlaps with an attacker-controlled repository (most directly, any fork relationship), and blast radius extends to any number of victim stacks sharing that SHA.

### Likelihood Explanation
Preconditions: attacker needs a GitHub repository (free to create) whose commit history shares at least one SHA with the victim stack — trivially satisfied by forking the victim repo, since forks share identical commit objects/SHAs with upstream until divergence. No Shipit credentials, GitHub App keys, or team membership required — only the ability to send a `status` webhook event that GitHub (or a crafted HTTP POST matching GitHub's signature scheme for the attacker's own registered app/org) delivers to `/webhooks`. Cost is minimal (one fork + one webhook trigger, e.g. commit status API call on their own repo), and the attack is fully repeatable against every stack that happens to track that shared history.

### Recommendation
Scope `StatusHandler#process` to the requesting repository using the same `stacks`/`repository_name` pattern as other handlers, e.g. restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`), so a status can only be applied to commits belonging to stacks whose `Repository` matches `payload.repository.full_name`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
1. Create two stacks backed by two different `Repository` records: `victim_repo` (`owner/victim`) and `attacker_repo` (`owner-evil/attacker`).
2. Create `Commit` rows with the **same** `sha` value, one for each stack (`victim_commit` on `victim_stack`, `attacker_commit` on `attacker_stack`), simulating a shared fork ancestor.
3. Configure `victim_stack`'s deploy spec (or stub `required_statuses`) to require context `security/scan`; assert before state: `victim_commit.deployable?` is `false` (binding LHS: `victim_commit.stack_id == victim_stack.id` and `victim_commit.deployable? == false`).
4. Build a webhook payload with `repository.full_name = "owner-evil/attacker"`, `sha: shared_sha`, `context: "security/scan"`, `state: "success"` — i.e., authenticated only for `attacker_repo`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, since that only ever checks org identity, not target stack).
6. Assert: `victim_commit.reload.deployable?` is now `true` (or `success?` is true), even though the payload's `repository.full_name` (`owner-evil/attacker`) never equals `victim_stack.repository.full_name` (`owner/victim`) — proving the two sides of the binding diverge and `StatusHandler` mutated a repository/stack it never authenticated against.
