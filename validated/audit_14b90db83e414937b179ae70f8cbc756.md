### Title
KLAY Bridge Transfer Permanently Blocked by Reverting Recipient — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` delivers bridged KLAY via a low-level external call to the recipient address. If that address is a contract whose fallback reverts, every operator attempt to settle the nonce will revert, the nonce is never marked handled, and the user's KLAY locked in the source bridge has no recovery path.

---

### Finding Description

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` performs all state mutations — `_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber`, `_updateHandleNonce` — and then makes an external call to the recipient:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

Because the `require` is the last statement, a revert from `_to` rolls back the entire transaction, including all the nonce-accounting state written earlier. The nonce is therefore never recorded as handled. [2](#0-1) 

The bridge's value-transfer recovery subsystem (`VTRecovery`) retries by re-submitting the same `handleKLAYTransfer` call. If `_to` always reverts, every retry fails identically — there is no alternative delivery path, no operator override of `_to`, and no refund path on the source chain. [3](#0-2) 

---

### Impact Explanation

The user's KLAY is locked in the source-chain bridge contract. The destination bridge holds the KLAY earmarked for the recipient but can never release it. No privileged function exists to redirect or refund a stuck nonce. This constitutes an unauthorized permanent lock of user-owned KAIA bridged assets.

---

### Likelihood Explanation

The trigger requires `_to` to be a contract address that reverts on receiving KLAY. Realistic scenarios:

- The user intentionally or accidentally specifies a contract without a `payable` fallback as the destination.
- The recipient contract is upgradeable and a later upgrade removes or breaks the `receive`/`fallback`.
- The recipient contract is self-destructed after the source-chain request is submitted but before operators settle it.

No privileged access is required; any user who submits a `requestKLAYTransfer` pointing to such an address triggers the condition.

---

### Recommendation

1. **Pull-payment pattern**: Instead of pushing KLAY to `_to` inside `handleKLAYTransfer`, credit an internal balance mapping and let the recipient pull funds. This decouples settlement from recipient behaviour.
2. **Operator redirect / emergency exit**: Allow operators (or the bridge owner) to redirect a stuck nonce to an alternative address after a timeout, analogous to the "emergency exit" recommended in the seed report.
3. **Soft failure**: Replace `require(ok, ...)` with a conditional that, on failure, stores the KLAY in a claimable escrow keyed by nonce, so the nonce is still marked handled and the bridge is not permanently blocked.

---

### Proof of Concept

1. User calls `requestKLAYTransfer(contractThatReverts, value, extraData)` on the source bridge, locking `value` KLAY.
2. Operators observe the `RequestValueTransfer` event and call `handleKLAYTransfer(..., contractThatReverts, value, nonce, ...)` on the destination bridge.
3. Inside `handleKLAYTransfer`, state is written (lines 81–84), then `contractThatReverts.call{value: value}("")` is executed — the callee reverts.
4. `require(ok, "handleKLAYTransfer: transfer failed")` propagates the revert, rolling back all state changes.
5. The nonce remains unhandled; `VTRecovery` retries indefinitely with the same result.
6. The user's KLAY in the source bridge is permanently locked; no refund or redirect mechanism exists. [4](#0-3)

    function handleKLAYTransfer(
        bytes32 _requestTxHash,

        uint64 _requestedBlockNumber,
        bytes memory _extraData
