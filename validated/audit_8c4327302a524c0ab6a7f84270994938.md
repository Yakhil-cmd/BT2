### Title
Cross-repository CI-status forgery via unscoped `StatusHandler` lookup combined with per-organization optional webhook signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization config (and therefore which `webhook_secret`) to verify a webhook against based on an **unverified** field taken directly from the still-unauthenticated JSON body (`repository.owner.login` / `organization.login`), *before* the signature has been checked. [1](#0-0) [2](#0-1) 

If the organization resolved from that unverified field has no `webhook_secret` configured (a documented, supported configuration — `webhook_secret: # nil`), verification is a no-op: [3](#0-2) [4](#0-3) 

Once "verified", the raw payload is dispatched to event handlers unchanged. `StatusHandler`, unlike `PushHandler`/`Handler#stacks`, never scopes its effect by repository at all — it updates **any** `Commit` row in the entire installation whose `sha` matches the attacker-supplied value: [5](#0-4) [6](#0-5) 

This breaks the binding: **the organization whose (possibly absent) secret was used to authenticate the request must equal the repository/stack whose commit-status (and downstream deploy/merge gating) is written.** It does not, because (a) the org used for verification is attacker-chosen from the same untrusted payload, and (b) `StatusHandler` doesn't even consult the `repository` field before writing.

### Finding Description
1. `WebhooksController#create` parses the body and dispatches to handlers only *after* `verify_signature` runs as a `before_action`. [7](#0-6) 
2. `verify_signature` derives `repository_owner` straight from the JSON payload (not yet authenticated) and uses it to select `Shipit.github(organization: repository_owner)`, i.e., the organization's App config/secret used to validate the HMAC. [1](#0-0) 
3. `GitHubApp#verify_webhook_signature` explicitly treats an unset `webhook_secret` as automatic success (`return true unless webhook_secret`), which is a documented supported state for a configured organization. [3](#0-2) 
4. After "verification" passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs against the full, attacker-controlled `params` — including fields not covered by any authenticated field used for org selection. [7](#0-6) 
5. `StatusHandler#process` writes a `Status` for every `Commit` matching the attacker-controlled `sha`, with **no repository/stack scoping whatsoever** — unlike the base `Handler#stacks`/`repository_name` helper that other handlers use. [8](#0-7) 
6. `Status#replicate_from_github!`/`Commit#create_status_from_github!` create the row unconditionally from payload fields, and a `success` status directly feeds `Commit#deployable?` and `MergeRequest#all_status_checks_passed?`, which gate deploys/merges. [9](#0-8) [10](#0-9) 

The `WebhooksController` is mounted publicly and unauthenticated by design (it must accept unauthenticated GitHub callbacks): `resources :webhooks, only: :create`. [11](#0-10) 

### Impact Explanation
An unprivileged, uncredentialed network attacker who knows (a) any organization name configured on the Shipit instance that has no `webhook_secret` set, and (b) the SHA of a real commit tracked by any stack on the instance (commit SHAs of public repositories are public information, and Shipit even exposes them via UI/API), can forge a `status` webhook event that:
- Bypasses signature verification entirely for that organization (`return true unless webhook_secret`), and
- Injects an arbitrary `success`/`failure` `Status` for a commit belonging to a completely different, unrelated repository/organization also hosted on the same Shipit instance, because `StatusHandler` never checks which repository the status event claims to be for.

This can flip `Commit#deployable?` to true for a commit that never actually passed CI, or flip a `MergeRequest`'s CI gate (`all_status_checks_passed?`), enabling an unauthorized deploy or an unauthorized automatic merge — matching the "Critical: unauthorized deploy/merge" bar. It requires no Shipit session, no API token, no GitHub App private key, and no possession of any webhook secret (the exploited condition is the *absence* of a secret for at least one tenant, not knowledge of one).

### Likelihood Explanation
Multi-tenant Shipit installations (multiple GitHub orgs sharing one instance, as shown in the shipped example configs) are an explicitly supported and documented configuration, and `webhook_secret` is documented as optional (`nil` is a valid, shown value in `config/secrets.development.example.yml` and the double-org fixture config). Any instance where at least one configured tenant omits the secret (misconfiguration that is easy to overlook, since the app doesn't warn about it) is exploitable. The SHA-only, repository-unaware lookup in `StatusHandler` is a straightforward code-review finding, not a theoretical edge case — it is trivially reachable via a single unauthenticated POST.

### Recommendation
- In `WebhooksController#verify_signature`, never treat an absent/unset `webhook_secret` as automatic pass; require an explicit, positively-configured secret per organization or reject the request.
- Scope `StatusHandler` (and any other handler that doesn't currently do so) to the repository asserted in the payload (`payload.dig('repository', 'full_name')`), matching the pattern already used in `Handler#stacks`/`repository_name`, and cross-check that the repository's owning organization matches the organization whose secret validated the signature.
- Consider computing `repository_owner` only after signature verification succeeds against every configured secret, or bind the verified organization identity to the specific stacks a request may mutate.

### Proof of Concept
1. Shipit instance is configured with two tenants, e.g. `OrgA` (no `webhook_secret` set) and `OrgB` (secret set, hosts the real target repository/stack).
2. Attacker learns (from public GitHub data) a real commit SHA belonging to a stack under `OrgB`, e.g. `abc123...`.
3. Attacker sends, with no signature or an arbitrary `X-Hub-Signature`:
```
POST /webhooks
X-Github-Event: status

{
  "sha": "abc123...",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")`; since `OrgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally.
5. `StatusHandler#process` executes `Commit.where(sha: "abc123...")` — finds the real commit under `OrgB`'s stack — and creates a fabricated `success` `Status`, with no check that the request was ever associated with `OrgB`.
6. The forged status can satisfy `Commit#deployable?`/`MergeRequest#all_status_checks_passed?`, allowing an unauthorized deploy or merge of that `OrgB` commit.

Note: I was unable to execute this against a running instance, so points 4–6 are derived from static code review of the cited files rather than confirmed end-to-end at runtime.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
