### Title
Coretime bulk-sale Dutch-auction price decays against a relay-chain clock the Coretime parachain cannot always keep pace with, letting purchases clear at floor price after chain stalls - (File: `substrate/frame/broker/src/utility_impls.rs`)

### Summary
`pallet-broker`'s bulk Coretime sale implements a Dutch-auction "leadin" mechanism: price starts high and decays to a fixed `end_price` over `leadin_length` **relay-chain** blocks [1](#0-0) , but the extrinsic that actually executes a purchase must be dispatched and processed **on the Coretime parachain**, whose block production is a separate, independently-failing process from the relay chain's block advancement [2](#0-1) [3](#0-2) . This is the structural analog of the reported issue: a price-decay clock that keeps ticking during a period when the venue that must record the trade (L2 sequencer / Coretime parachain) cannot process transactions, so once transacting resumes, trades clear far from the price the clock "intended" at that real-world moment.

### Finding Description
The sale price is computed as:
```rust
pub fn sale_price(sale: &SaleInfoRecordOf<T>, now: RelayBlockNumberOf<T>) -> BalanceOf<T> {
    let num = now.saturating_sub(sale.sale_start).min(sale.leadin_length).saturated_into();
    let through = FixedU64::from_rational(num, sale.leadin_length.saturated_into());
    T::PriceAdapter::leadin_factor_at(through).saturating_mul_int(sale.end_price)
}
``` [1](#0-0) 

`now` here is not the Coretime parachain's own block number but the **relay chain's** block number, obtained via `RCBlockNumberProviderOf::<T::Coretime>::current_block_number()` [4](#0-3) . The `CoretimeInterface::RelayChainBlockNumberProvider` is concretely wired to `RelaychainDataProvider<Runtime>` on the actual Coretime-Westend runtime, i.e., it always reflects the relay chain's height regardless of whether the Coretime parachain itself is producing blocks [3](#0-2) .

If the Coretime parachain stalls or is unable to include extrinsics for any duration (congestion, collator downtime, disputes delaying block inclusion, etc. — an environmental/infrastructure condition, not an attacker action, mirroring the sequencer-downtime scenario in the original report), the relay chain block number continues to advance. Because `num` is clamped by `.min(sale.leadin_length)`, any stall lasting at least the remaining leadin period will silently walk the auction from wherever it was straight down to the floor `end_price` while nobody could submit a `purchase` extrinsic. Once the parachain resumes producing blocks, the very first purchasers will transact at the auction's floor price, exactly as in the reported case where users bought L2 auction tokens far below fair value once the sequencer came back online.

### Impact Explanation
The Coretime treasury/system revenue is the "SetToken" analog here: bulk Coretime cores that should have sold progressively down the leadin curve (capturing higher revenue for the earlier, higher-priced portion of the decay) instead sell at the lowest floor price once transacting resumes, because the price clock advanced unobserved during the parachain-processing gap. This is a value-leakage issue for on-chain revenue capture, not fund theft, and is architecturally identical in kind to the sherlock issue: "clock keeps advancing while the transacting venue is unavailable, so trades clear at unintended extreme prices."

### Likelihood Explanation
Requires a sustained Coretime-parachain processing stall (no block inclusion) lasting at least the remainder of the sale's leadin window — an infrastructure/liveness condition outside attacker control, not a privileged-role or governance action, mirroring exactly how the original report also depended on an external liveness event (sequencer downtime) rather than an attacker-triggered action. This keeps it consistent with the accepted classification pattern in the source report (valid Medium, "won't fix" as a design tradeoff, addressed only via documentation warning rather than a code fix).

### Recommendation
Consistent with the upstream team's own resolution of the analogous case (documentation warning rather than code change), consider: (a) basing leadin decay on a monotonic clock that also accounts for parachain-side processing gaps (e.g., capping decay progress by elapsed *committed* timeslices rather than raw relay-chain blocks), or (b) exposing/checking `Status::last_timeslice` staleness before allowing a purchase to execute at a stale/faster-than-expected `through` value, and documenting the residual risk in `pallet-broker`'s crate docs the same way it was documented in `AuctionRebalanceModuleV1.sol`.

### Proof of Concept
Not independently executed — this analysis is based on static code tracing of `sale_price`/`current_price` in `substrate/frame/broker/src/utility_impls.rs` and `dispatchable_impls.rs`, and the `RelayChainBlockNumberProvider` wiring in `cumulus/parachains/runtimes/coretime/coretime-westend/src/coretime.rs`, confirming the price clock (relay chain blocks) is decoupled from the venue required to execute the trade (Coretime parachain extrinsic inclusion). No live network or test-harness run was performed; a concrete integration test would need to simulate a Coretime-parachain block-production gap (e.g., holding `on_initialize`/block authorship while advancing the mocked `RelayChainBlockNumberProvider`) and then assert `current_price()` lands at `end_price` before any purchase extrinsic could be dispatched. This is presented as a supported structural analog per the task's bug-class-hint methodology, not as a verified reproduction.

	pub fn current_price() -> Result<BalanceOf<T>, DispatchError> {
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let sale = SaleInfo::<T>::get().ok_or(Error::<T>::NoSales)?;

		Self::ensure_cores_for_sale(&status, &sale)?;

		let now = RCBlockNumberProviderOf::<T::Coretime>::current_block_number();
