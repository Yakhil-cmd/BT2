### Title
Cross-organization webhook authentication bypass allows forged CI status / stack sync on repositories the attacker does not control - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which organization's secret* to validate a webhook payload against using an attacker-supplied field of the same unauthenticated JSON body (`repository.owner.login` / `organization.login`), while every event handler that actually mutates state resolves the *target* repository/stack from a different field of that same body (`repository.full_name`, or an unscoped `sha` match). These two fields are never checked for consistency, so the "organization that authenticated" and "the repository/commit that is written" are not the same binding. Additionally, per-organization webhook secrets are optional (`GitHubApp#verify_webhook_signature` returns `true` when no secret is configured for the selected organization), so an attacker can choose to name an organization that has *no* webhook secret configured at all, causing signature verification to unconditionally pass with zero credentials, and then point the payload's repository/commit-matching fields at a victim stack that belongs to a completely different organization.

### Finding Description
`Shipit.github(organization: repository_owner)` resolves the `GitHubApp` (and thus the HMAC secret) using `repository_owner`, itself derived purely from the untrusted request body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured — a state the docs describe as optional: [3](#0-2) [4](#0-3) 

Per-organization configuration lookup is confirmed to be independent per org key: [5](#0-4) 

Meanwhile, the code path that actually performs the write never re-derives or cross-checks against the organization used for signature verification. `Handler#repository_name`/`#stacks` reads `repository.full_name` from the same JSON body to find the `Repository`/`Stack` to act on: [6](#0-5) 

`PushHandler` uses that repository/stack lookup to trigger `stack.sync_github`: [7](#0-6) 

`StatusHandler` is even more directly exploitable: it matches purely by commit `sha` with **no repository/organization scoping at all**, and directly persists attacker-controlled `state`/`description`/`target_url`/`context` as a real CI status on any commit sharing that sha across the whole installation: [8](#0-7) 

That status flows into `deployable?` and merge-queue gating used to authorize deploys/merges: [9](#0-8) [10](#0-9) 

**Binding broken (equality that should hold but doesn't):** `organization used to select the verification secret (repository.owner.login / organization.login)` == `organization/repository actually mutated (repository.full_name, or unscoped commit sha)`. Before the attack, these two are implicitly assumed equal only because a real GitHub webhook delivery keeps the whole JSON internally consistent. After the attack, the attacker crafts a payload where they differ: the "authenticating" side names an org with no configured secret (or, more narrowly, an org whose secret they can obtain, which is out of scope per the rules), while the "written" side names any repository/commit tracked by Shipit, including ones in wholly unrelated organizations.

### Impact Explanation
An unauthenticated network attacker (no session, no API token, no GitHub credential of any kind) who can reach the `/webhooks` endpoint of a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` set can:
- Forge a `status` event naming that unsecured/unknown-secret organization while targeting, via `sha`, a commit belonging to a completely different, victim organization's stack — causing Shipit to record a fabricated "success" CI status and mark the commit `deployable?`, which can lead to an **unauthorized deploy** or an **unauthorized merge** of a pull request that never actually passed CI (`MergeRequest#merge!` calls the real GitHub merge API using this fabricated state).
- Forge a `push` event to trigger `GithubSyncJob`/`sync_github` against a victim stack it has no authorization over.

This satisfies the required Impact bar of "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: it requires (a) the multi-organization GitHub App config schema (multiple orgs as top-level keys under `secrets.github`) to be in use, and (b) at least one configured organization lacking a `webhook_secret`. Both conditions are explicitly documented as supported/optional in `docs/setup.md`, so this is a realistic, not purely theoretical, misconfiguration for any installation onboarding several organizations incrementally. No credential, session, or write access of any kind is required by the attacker for the "no secret configured" branch — only knowledge of an organization's login name that the operator has registered without a webhook secret, and the ability to send an HTTP POST to the public `/webhooks` endpoint.

### Recommendation
- Require signature verification for every organization the `WebhooksController` will accept requests for; do not treat a missing `webhook_secret` as "verification passes" — instead reject (422) if no secret is configured, or fail closed.
- Bind the organization used for signature verification to the repository/stack actually acted upon: after selecting the handler's target `Repository`/`Stack` (e.g., via `repository.full_name`), assert that its owning organization equals the organization whose secret validated the signature, and reject mismatches.
- Scope `StatusHandler#process` (and any other handler matching purely by `sha`) to commits belonging to the repository named in the same, now-verified, payload rather than matching by `sha` across the entire installation.
- Long term: add a regression test asserting that a validly-signed webhook for organization A cannot mutate state belonging to organization B's repositories/stacks, mirroring how `collateralEnabled`/`recollateralizePaused` should have been enforced uniformly across all privileged entry points in the referenced Frax finding.

### Proof of Concept
1. Configure Shipit with two organizations under `secrets.github`: `victim-org` (with `webhook_secret: some-secret`) and `attacker-org` (with `webhook_secret` omitted).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any junk value), body:
```json
{
  "organization": { "login": "attacker-org" },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<sha-of-victim-org-pull-request-head-commit>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "http://example.com"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`; because `attacker-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally — the request is accepted without any valid signature.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, creating a `success` status on the victim's commit, independent of the `attacker-org`/`victim-org` mismatch.
5. If that commit is a pull request head being tracked for the merge queue, or the tip of an undeployed range, this fabricated status can satisfy `deployable?`/`all_status_checks_passed?`, enabling deploy or auto-merge on `victim-org`'s stack without ever having valid credentials for it.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
