### Title
Stack-scoped API tokens bypass their stack restriction in the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`ApiClient` tokens can be scoped to a single stack via `stack_id`, and `Shipit::Api::BaseController` enforces that scope for every API endpoint by resolving the requested stack through the `stacks` relation. `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!` directly, skipping the scoping relation entirely, so a token authorized only for stack A can read build/deploy status for any stack on the instance.

### Finding Description
`Shipit::Api::BaseController` defines the intended binding between a token and the stack(s) it may touch: [1](#0-0) 

`current_api_client.stack_id?` is true when the token was created scoped to one stack; in that case `stacks` (and therefore `stack`) is restricted to `Stack.where(id: current_api_client.stack_id)`. Every controller inheriting `BaseController`'s `#stack` method relies on this to enforce `token.stack_id == accessed_stack.id`.

`CCMenuController`, however, overrides `#stack` and resolves the record straight from the unscoped `Stack` class: [2](#0-1) 

The `require_permission :read, :stack` check only verifies that the token has the `read:stack` permission string, not that the target stack matches the token's `stack_id`: [3](#0-2) 

So the equality the system is supposed to enforce, `current_api_client.stack_id == stack.id` (when `stack_id` is set), is checked in `BaseController#stack` but silently dropped in `CCMenuController#stack`.

### Impact Explanation
Any holder of a valid `read:stack`-permissioned `ApiClient` token — even one deliberately restricted to a single, low-sensitivity stack — can query `GET /api/{any_stack}/cc.xml` for every other stack configured in the Shipit instance and read its `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, and lock status. This is an unauthorized read of stack state that the stack-scoping feature was specifically designed to prevent, matching the "unauthenticated read of stack state" class of High severity impact (the requester is unauthenticated with respect to the stacks it is not supposed to see).

### Likelihood Explanation
Exploitation requires nothing beyond a legitimately issued, narrowly-scoped `ApiClient` token with `read:stack` permission — the exact kind of token an operator would issue to a low-trust integration (e.g., a CI dashboard for one team's stack) specifically to prevent it from seeing other teams' stacks. The only extra step is calling the CCMenu endpoint with a different `stack_id` in the URL, which is trivial and requires no additional credentials, timing, or race conditions.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped `stacks` relation from `BaseController` instead of calling `Stack.from_param!` directly, e.g. `stacks.from_param!(params[:stack_id])`, so the token's `stack_id` restriction is enforced consistently across all API endpoints, including CCMenu.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: A` with permission `read:stack`.
2. As that client, request `GET /api/{owner}/{repo-B}/{env-B}/cc.xml?token=<token>` where `repo-B/env-B` is a different stack the client was never granted access to.
3. `authenticate_api_client` succeeds (permission check only inspects the `permissions` array), and `stack` resolves via `Stack.from_param!(params[:stack_id])` — unscoped — returning stack B's record instead of raising/`404`.
4. The response renders stack B's build status, label, and timing, which the token was never authorized to see.
