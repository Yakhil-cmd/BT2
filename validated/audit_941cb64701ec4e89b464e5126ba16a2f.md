### Title
Webhook signature verification is keyed to an attacker-controlled `repository.owner.login`/`organization.login` field, while the actual write target is taken from the unverified `repository.full_name` — cross-repository writes via cross-tenant webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, attacker-supplied JSON body, rather than from any value tied to the specific `Hook`/`GithubApp` the request is actually destined for. Once the signature check passes, the whole payload — including a completely independent field, `repository.full_name` — is handed unmodified to the event handler, which uses `repository.full_name` alone to look up the `Repository`/`Stack` to mutate. Any operator who legitimately controls one GitHub App/organization installation (and therefore knows its webhook secret) can therefore sign a payload whose `repository.owner.login` matches their own org, but whose `repository.full_name` points at a victim org/repo, and have Shipit act on the victim's stack.

### Finding Description
This is the same class of bug as the reported Perpetual `withdraw` issue: two related pieces of state that should be bound together (the authenticated organization vs. the resource actually written) are checked/derived from two different, independently-controllable fields, and only one of them is validated.

- Signature/organization selection uses fields from the raw, unverified body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `GitHubApp` (and its own `webhook_secret`) from `secrets.github`, keyed strictly by organization name: [3](#0-2) 

`verify_webhook_signature` only checks that the raw body's HMAC matches the secret configured for *that* organization — it says nothing about which repository the payload claims to represent: [4](#0-3) 

- After verification succeeds, the full, untouched JSON body (`params = JSON.parse(request.raw_post)`) is dispatched to handlers: [5](#0-4) 

- Handlers resolve the repository/stack to act on using a *different* field, `repository.full_name`, with no comparison back to `repository.owner.login`/`organization.login` used earlier for signature selection: [6](#0-5) [7](#0-6) 

`Repository.from_github_repo_name` parses `owner/name` straight out of that string with no additional check that it belongs to the organization whose secret produced a valid signature: [8](#0-7) 

The binding that should hold is:

`organization authenticated by verify_signature == organization/repository actually mutated by handler.process`

Because `repository_owner` (used to pick the secret) and `repository.full_name` (used to pick the target repo) are two unrelated, attacker-controlled fields inside the same signed body, an attacker who is a legitimate owner of Org A's GitHub App installation (and thus knows Org A's `webhook_secret`) can forge a payload that is correctly signed for Org A but whose `repository.full_name` names a repository belonging to Org B. The signature check only proves "this body was produced by someone holding Org A's secret" — it does not prove "the repository referenced in this body belongs to Org A."

### Impact Explanation
This crosses the "cross-repository writes" boundary explicitly called out as valid impact. Concretely, with a correctly-signed-but-cross-tenant `push` payload, `PushHandler#process` will call `stack.sync_github(expected_head_sha: params.after)` against a victim stack that the attacker does not own and has no legitimate relationship to, enqueuing a `GithubSyncJob` for it: [9](#0-8) 

Other handlers keyed the same way (`status`, `check_suite`, `pull_request.*`) let the attacker inject fabricated CI status entries, close/archive review stacks, or otherwise mutate state belonging to a repository/stack outside their trust boundary — e.g. `StatusHandler#process` creates a `Status` on any commit matching `params.sha` regardless of which org it belongs to: [10](#0-9) 

Fabricated CI "success" statuses can make an otherwise-unreviewed/failing commit `deployable?` and get auto-deployed by continuous delivery, which is an unauthorized deploy path.

### Likelihood Explanation
Exploitation requires the attacker to be an admin of at least one GitHub organization/App installation that is legitimately connected to this Shipit instance (so they know that org's `webhook_secret`) — this is a normal, low-privilege "regular customer of a multi-tenant Shipit deployment" scenario, not a privileged Shipit account, `ApiClient` token, or GitHub App private key. Multi-tenant configuration is explicitly supported (`github_organizations`, `github_app_config`), so this scenario is realistic wherever Shipit is deployed multi-tenant. No social engineering, TLS interception, or host access is required — only crafting one HTTP POST to `/webhooks` with a valid HMAC for the attacker's own org and a `repository.full_name` field pointing elsewhere.

### Recommendation
Bind the two checks together: after `verify_signature` succeeds for organization `O`, every handler must additionally assert that the repository/organization referenced in the payload (`repository.owner.login`/`repository.full_name`'s owner segment, or `organization.login`) equals `O` before doing any lookup or mutation — mirroring how the Perpetual fix required `status == LibTypes.Status.NORMAL` rather than merely `!= SETTLING`. Concretely, `WebhooksController` (or `Handler#stacks`/`Handler#repository_name`) should reject the request if `payload.dig('repository', 'owner', 'login')` (or `organization.login`) does not match the resolved `Repository#owner` for the target stack, independent of any per-handler business logic.

### Proof of Concept
1. Shipit is configured multi-tenant with at least two organizations, `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), each with its own GitHub App installation, per `Shipit.github_app_config`.
2. Attacker (a legitimate admin of `attacker-org`, knows `S_A`) crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "full_name": "victim-org/victim-repo",
       "owner": { "login": "attacker-org" }
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, body)` and sends `POST /webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature using `S_A` — passes. [1](#0-0) 
5. `create` dispatches the full, unmodified payload to `PushHandler`, which resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, finds `victim-org`'s `Stack`, and triggers `sync_github`/deploy-affecting side effects — despite the signature only proving control of `attacker-org`'s secret. [6](#0-5) [9](#0-8)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
