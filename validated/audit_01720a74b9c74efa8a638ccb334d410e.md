### Title
Address hashes (`chash160`) are truncated to 128 bits, weakening collision resistance and enabling a CREATE2-style address-squatting/definition-collision attack against unrevealed addresses - (File: chash.js)

### Summary
Obyte addresses are computed as `chash160(definition)` in [1](#0-0) , using `chash.getChash160`. Unlike a straightforward 160-bit hash, `getChash` actually derives the address from only a **128-bit** RIPEMD-160 fragment, with the remaining 32 bits being a deterministic checksum computed from that same 128-bit fragment, not independent entropy: [2](#0-1) 

This mirrors the structural weakness underlying the reported CREATE2 collision issue: a smaller-than-expected effective search space (128 bits here vs. the 160-bit assumption in the original report) allows a birthday-bound collision to be found with roughly `2^64` hashing operations instead of `2^80`. Combined with ocore's Bitcoin-like design where funds can be sent to an address before its definition is ever disclosed on-chain, an attacker who finds a second definition colliding with a victim's (yet-undisclosed) address can submit that definition as the legitimate one and hijack full spending authority over any funds already sent there.

### Finding Description
`getChash` builds the address as follows: it hashes the input with RIPEMD-160 (`hash`, 160 bits), then drops the first 4 bytes to get `truncated_hash` (only 128 bits), computes a 4-byte `checksum` purely as a function of `truncated_hash`, and interleaves the checksum bits back into the 128-bit `truncated_hash` to produce the final 160-bit encoded chash. [3](#0-2) 

Because the checksum is entirely determined by `truncated_hash`, two definitions collide in the full 160-bit chash **iff** they collide in the 128-bit `truncated_hash`. This means the real collision-resistance of ocore addresses is bounded by a 128-bit hash's birthday bound (~`2^64` operations), not by the full 160 bits implied by the encoded address length that `isValidAddress` checks (32 base32 characters). [4](#0-3) 

Ocore, like Bitcoin, allows funds to be sent to an address whose definition has never been disclosed on-chain. The very first author using an address is validated only by checking that the hash of the submitted `definition` matches the `definition_chash` (which equals the address itself on first use): [5](#0-4) [6](#0-5) 

The same "first disclosure wins" pattern is used for AA definitions and other definition-based address bindings: [7](#0-6) 

Because this check accepts **any** `definition` whose `chash160` equals the target address — not specifically the definition the legitimate owner intended — an attacker who has found a colliding `definition` (via the weakened 128-bit birthday search) can post a unit as the first author of that address, using a definition of their own choosing (e.g. `['sig', {pubkey: attacker_pubkey}]`), and it will validate successfully in place of the real owner's definition.

### Impact Explanation
If an attacker precomputes a large set of candidate definitions (via `getChash160`) and finds one whose address matches a target that is expected to receive funds before its real definition is revealed (e.g., a freshly generated wallet address, a payment target, or a shared/multisig address awaiting activation), the attacker can:
1. Wait for funds (bytes or assets) to be sent to that address.
2. Submit a unit spending those funds, presenting their own colliding `definition` as `author.definition`.
3. Because ocore only verifies `chash160(definition) === address` on first use (not that the definition matches what the real owner generated), the forged definition is accepted, and the attacker gains complete signing authority and can drain all funds sent to that address.

This is a direct analog of the CREATE2 "address collision" attack: attacker-controlled preimage search against a narrower-than-assumed hash space, followed by total takeover of a pre-funded but not-yet-authenticated address. The impact is unauthorized spending / complete draining of any funds sent to any address before its owner's first authenticated transaction — a scenario that occurs continuously in normal ocore usage (new wallet addresses, shared addresses pending approval, AA-created sub-accounts, textcoins, etc.).

### Likelihood Explanation
The attack requires only public information (the target address string) and offline computation — no privileged access, no cooperation from any node or peer, and no on-chain footprint until the final spend attempt. The effective search space is 128 bits rather than the 160 bits implied by the encoded address format, cutting the birthday-bound attack cost by a factor of `2^32` compared to a "proper" 160-bit hash — i.e., approximately as hard as finding a collision in MD5-scale (very roughly; 128-bit birthday ≈ `2^64` hash operations), which is within reach of dedicated hardware/cloud GPU clusters, and far cheaper than the `2^80` figure used to argue medium/high severity in the original Sherlock report. The requirement that a target address hold un-authenticated funds (i.e., funds sent before the definition is disclosed) is routine in ocore (this is the default state of virtually every fresh address until its owner's first transaction).

### Recommendation
- Do not truncate the RIPEMD-160 output before deriving the checksum in `chash.js`; use the full 160-bit hash output as the "clean data" (or otherwise ensure the address's collision resistance matches its nominal bit length) so that the effective security level matches the intended 160 bits (or upgrade to a wider hash, e.g. 256-bit, for new address formats).
- Consider binding first-use validation to something the true owner alone could have produced (e.g., requiring the definition to also be signed/committed to earlier, or requiring the address to be pre-registered/announced with a stronger commitment) rather than relying solely on `chash160(definition) === address`.
- Audit `getChash288` (asset/other 288-bit chash) for the same construction to determine whether it exhibits an analogous, if less severe, truncation issue.

### Proof of Concept
Conceptually (offline, no network interaction needed until the final step):
1. Pick or observe a target address `A` (any ocore address that is expected to receive funds before its owner ever posts a unit from it, e.g., a freshly generated wallet address shared with the victim).
2. Offline, iterate over candidate definitions of the attacker's choosing (`['sig', {pubkey: attacker_pubkey_i}]` for many attacker-generated keypairs, or other definitions the attacker fully controls) and compute `chash.getChash160(candidate_definition)` for each, per [2](#0-1) , until one candidate's resulting chash equals `A`. Because the real search space is only the 128-bit `truncated_hash` (checksum is derived, not independent), this collision is reachable with a birthday-bound search of about `2^64` hash evaluations rather than `2^80`.
3. Wait until value is sent to address `A` (as any normal transaction; no wrongdoing needed by the victim — this is ordinary usage before the owner's first spend).
4. Attacker composes and broadcasts a unit that pays from address `A`, setting `author.address = A` and `author.definition = candidate_definition` found in step 2, signed with the attacker's own key corresponding to that definition.
5. Validation in `validateAuthor`/`validateDefinition` (`ifDefinitionNotFound` branch) only checks `objectHash.getChash160(arrAddressDefinition) === definition_chash` (i.e., `=== A`), per [8](#0-7) ; since the attacker's colliding definition satisfies this, the unit validates and the attacker's spend succeeds, draining the funds sent to `A`.

Note: I could not find and did not attempt to actually execute a real 128-bit birthday search (that would require substantial offline computation outside the scope of static code review), so this PoC is a described attack path grounded in the exact hashing code, not an executed collision. The core architectural weakness (truncation of the hash before deriving the checksum, and "first-use" validation trusting whichever definition matches the chash) is directly confirmed in the cited source.
