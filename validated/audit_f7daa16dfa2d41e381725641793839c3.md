## Analog Vulnerability Found

### Title
Webhook organization used for signature verification is never bound to the repository the event actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-tenant GitHub App configuration, where each GitHub organization tracked by the instance has its own `webhook_secret` [1](#0-0) . When a webhook is received, `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against using `repository_owner`, which is read from the payload's `repository.owner.login` (or `organization.login`) field [2](#0-1) . However, the event handlers that actually act on the payload (creating/archiving stacks, syncing commits, updating pull requests) resolve the target repository from a **different** field in the same payload: `repository.full_name` [3](#0-2) . Nothing enforces that `repository.owner.login` (the organization whose secret authenticated the request) matches the owner segment of `repository.full_name` (the repository that gets written to).

### Finding Description
This is the same class of bug as the external report: a value is validated/authenticated, but a *different, unchecked* value from the same message is the one actually acted upon - exactly analogous to `pairNFTInfo.l2Contract` being registered without verifying it matches the contract that is later used in transfers.

Concretely:
- `verify_signature` picks the `GitHubApp` (and its `webhook_secret`) using `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [4](#0-3) .
- Every handler bases its target lookup on `repository_name = payload.dig('repository', 'full_name')`, via `Handler#stacks` / `Repository.from_github_repo_name` [3](#0-2) , and this pattern repeats in every pull-request handler (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `assigned_handler.rb`, `label_capturing_handler.rb`) via `Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) .
- The signature is computed over the *entire* raw JSON body, so anyone who legitimately knows one org's `webhook_secret` (e.g. an org admin who configured their own GitHub App/organization entry in `secrets.github`, per the multi-org setup this engine supports) can construct an arbitrary payload themselves — they don't need GitHub to deliver it. They can set `repository.owner.login` to their *own* org (so `verify_signature` picks their own known secret and passes) while setting `repository.full_name` to a *different* organization's repository that is also tracked by the same Shipit instance.
- Because verification never re-checks that the authenticated organization equals the owner encoded in `repository.full_name`, the forged event is dispatched to handlers that write state (archive/unarchive review stacks, create stacks, capture PR labels, trigger `GithubSyncJob`, etc.) for a repository belonging to a completely different, unrelated organization.

This precisely matches the required binding-equality violated in the rules: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
An org admin who is a legitimate (but otherwise unprivileged w.r.t. other tenants) participant in a multi-org Shipit deployment can forge webhook events that cause cross-repository/cross-organization writes: archiving or unarchiving another organization's review stacks, creating spurious review stacks, mutating pull-request label state, or triggering GitHub syncs (`stack.sync_github`) for stacks they do not own [6](#0-5) . This satisfies the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
Exploitation requires only knowledge of one already-configured organization's `webhook_secret` (something a legitimate tenant org owner has by design, without needing Shipit account privileges, GitHub App private keys, or repo write access on the target) and the ability to POST directly to the `/webhooks` endpoint — no interaction with the real GitHub webhook delivery pipeline is required, since the raw body and its signature are attacker-constructed.

### Recommendation
After verifying the HMAC, additionally verify that the organization used to select the webhook secret matches the owner encoded in the payload's `repository.full_name` (and any other repository-identifying field the handlers rely on) before dispatching to handlers, i.e. bind `repository_owner` used for authentication to the repository actually resolved and mutated by `Handler#stacks`/`Repository.from_github_repo_name`.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.github`: `OrgA` (attacker-controlled, webhook_secret known to attacker) and `OrgB` (victim, has stacks/review-stacks tracked by Shipit).
2. Attacker crafts a `pull_request` (or `push`) JSON payload with `"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}` and the rest of the fields required by the target handler (e.g. `action: "labeled"`, `pull_request.number`, etc.).
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` over the raw JSON using `OrgA`'s known `webhook_secret`.
4. POST to `/webhooks` with `X-Github-Event` set accordingly.
5. `verify_signature` resolves `repository_owner = "OrgA"`, fetches `OrgA`'s `GitHubApp`, and the signature check passes [7](#0-6) .
6. The handler resolves the target via `params.repository.full_name = "OrgB/victim-repo"` [8](#0-7)  and performs writes (e.g. `stack.archive!`/`stack.unarchive!`) against `OrgB`'s stack, despite the request having been authenticated only for `OrgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner

    end
```
