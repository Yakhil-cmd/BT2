### Title
Unchecked `transferFrom` Return Value in ERC721 Bridge Allows Unauthorized Cross-Chain NFT Minting — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.sol` calls `IERC721.transferFrom` in both `requestERC721Transfer` and `handleERC721Transfer` without checking the return value or using a safe wrapper. The ERC20 bridge counterpart (`BridgeTransferERC20.sol`) correctly uses OpenZeppelin's `SafeERC20.safeTransferFrom`/`safeTransfer`. For a non-standard ERC721 token that silently returns `false` instead of reverting on a failed transfer, the bridge emits a cross-chain request event and increments `requestNonce` without actually taking custody of the NFT, enabling an attacker to receive a minted or transferred NFT on the counterpart chain for free.

---

### Finding Description

`BridgeTransferERC20.sol` imports and uses `SafeERC20`:

```solidity
// BridgeTransferERC20.sol line 22-29
import "../../libs/openzeppelin-contracts-v2/contracts/token/ERC20/SafeERC20.sol";
...
using SafeERC20 for IERC20;
``` [1](#0-0) 

All ERC20 token movements use `safeTransferFrom` / `safeTransfer`, which revert on failure regardless of whether the underlying token reverts or returns `false`:

```solidity
// BridgeTransferERC20.sol line 133
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
``` [2](#0-1) 

```solidity

IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [3](#0-2) 

`BridgeTransferERC721.sol` makes no such import and uses bare `IERC721.transferFrom` in two places:

**Location 1 — `requestERC721Transfer` (deposit path):**

```solidity
// BridgeTransferERC721.sol line 129-130
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
_requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
``` [4](#0-3) 

`_requestERC721Transfer` unconditionally emits `RequestValueTransferEncoded` and increments `requestNonce`:

```solidity
// BridgeTransferERC721.sol line 93-105
emit RequestValueTransferEncoded(...);
requestNonce++;
``` [5](#0-4) 

**Location 2 — `handleERC721Transfer` (withdrawal path):**

The bridge nonce state is fully committed (lines 49–65) before the transfer executes:

```solidity
// BridgeTransferERC721.sol line 49-69
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);
...
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [6](#0-5) 

The `IERC721` interface declares `transferFrom` as returning nothing (`void`), so any return data from a non-standard token is silently discarded by the ABI decoder:

```solidity
// IERC721.sol line 44
function transferFrom(address from, address to, uint256 tokenId) public;
``` [7](#0-6) 

---

### Impact Explanation

**Deposit path (`requestERC721Transfer`):**

If a registered ERC721 token silently fails `transferFrom` (returns `false` or does nothing instead of reverting), the bridge emits `RequestValueTransferEncoded` and increments `requestNonce` without ever taking custody of the NFT. Bridge operators on the counterpart chain observe the event and call `handleERC721Transfer`, which either:
- **`modeMintBurn = true`**: mints a new NFT to the recipient — attacker receives a free minted NFT on the counterpart chain.
- **`modeMintBurn = false`**: transfers an NFT from the bridge's own holdings to the recipient — attacker drains the bridge's NFT reserves.

**Withdrawal path (`handleERC721Transfer`):**

If the outbound `transferFrom` silently fails, the nonce is permanently consumed (`_updateHandleNonce` deletes `handleNoncesToBlockNums[_requestedNonce]` and advances `lowerHandleNonce`), the `HandleValueTransfer` event is emitted, but the recipient never receives the NFT. The request cannot be retried because the nonce is gone, resulting in permanent loss of the bridged NFT. [8](#0-7) 

---

### Likelihood Explanation

Token registration is `onlyOwner`, so the token must be registered by the bridge owner. However:
1. The owner may register a non-standard ERC721 token without auditing its `transferFrom` behavior.
2. A malicious or buggy ERC721 token that returns `false` on failure (rather than reverting) is the trigger — this is a known class of non-standard tokens.
3. Once such a token is registered, any user can call `requestERC721Transfer` to exploit the deposit path with no further privilege.

The asymmetry with the ERC20 bridge (which uses `SafeERC20`) indicates this was an oversight rather than an intentional design choice.

---

### Recommendation

Replace bare `IERC721.transferFrom` calls with `IERC721.safeTransferFrom` (which at minimum ensures the recipient implements `onERC721Received`) and add an ownership check after the transfer to confirm custody actually changed, or implement a `SafeERC721` wrapper analogous to `SafeERC20` that reverts if the transfer does not succeed. Specifically:

In `requestERC721Transfer`:
```solidity
// Before: IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
IERC721(_tokenAddress).safeTransferFrom(msg.sender, address(this), _tokenId);
require(IERC721(_tokenAddress).ownerOf(_tokenId) == address(this), "ERC721 transfer failed");
```

In `handleERC721Transfer`:
```solidity
// Before: IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

---

### Proof of Concept

1. Deploy a non-standard ERC721 token whose `transferFrom` always returns `false` (or emits no event and does nothing) instead of reverting.
2. Bridge owner calls `registerToken(nonStandardERC721, counterpartToken)` on the source bridge.
3. Attacker calls `requestERC721Transfer(nonStandardERC721, attackerAddress, tokenId, "")` on the source bridge.
4. `IERC721(nonStandardERC721).transferFrom(attacker, bridge, tokenId)` silently fails — attacker retains the NFT.
5. `_requestERC721Transfer` emits `RequestValueTransferEncoded` and increments `requestNonce`.
6. Bridge operators observe the event and call `handleERC721Transfer` on the counterpart bridge.
7. Counterpart bridge mints (or transfers) the NFT to the attacker's address on the counterpart chain.
8. Attacker now holds the original NFT on the source chain **and** a minted/transferred NFT on the counterpart chain — unauthorized duplication of a bridged asset. [9](#0-8) [10](#0-9)
