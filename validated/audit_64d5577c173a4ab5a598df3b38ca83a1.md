### Title
Deployer Retains Operator Privileges After Ownership Transfer, Enabling Unauthorized Bridge Value Transfers — (`contracts/service_chain/bridge/BridgeOperator.sol`)

### Summary

`BridgeOperator.sol` grants the deployer (`msg.sender`) two independent roles at construction time: the `owner` role (via `Ownable`) and the `operator` role (via `operators[msg.sender] = true`). These roles are not programmatically linked. Transferring ownership to a new address does not revoke the deployer's operator status. The deployer retains the ability to unilaterally execute `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` — draining bridged KAIA or triggering unauthorized token mints — even after the bridge has been handed off to a new owner.

### Finding Description

In the `BridgeOperator` constructor:

```solidity
constructor() internal {
    for (uint8 i = 0; i < uint8(VoteType.Max); i++) {
        operatorThresholds[uint8(i)] = 1;   // default threshold = 1
    }
    operators[msg.sender] = true;           // deployer becomes operator
    operatorList.push(msg.sender);
}
``` [1](#0-0) 

The deployer simultaneously holds:
- **Owner role** (from `Ownable`): controls `registerOperator`, `deregisterOperator`, `setOperatorThreshold`, `setRunningStatus`.
- **Operator role** (`operators[deployer] == true`): controls `handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`, `setKLAYFee`.

When the owner calls `transferOwnership(newOwner)`, only the `_owner` storage slot changes. The `operators` mapping entry for the deployer is untouched. The deployer is still a valid operator and can call any `onlyOperators` function:

```solidity
modifier onlyOperators() {
    require(operators[msg.sender], "msg.sender is not an operator");
    _;
}
``` [2](#0-1) 

With the default `operatorThresholds[ValueTransfer] = 1`, a single operator vote suffices to execute a transfer. The deployer can call `handleKLAYTransfer` and immediately satisfy the threshold:

```solidity
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }
    ...
    (bool ok, ) = _to.call.value(_value)("");
    require(ok, "handleKLAYTransfer: transfer failed");
}
``` [3](#0-2) 

The code's own comment on `deregisterOperator` acknowledges the role-separation problem but frames it only as a stale-vote concern, not as a deployer-privilege-persistence concern:

```
// Note that outstanding votes by the deregistered operator are not revoked.
// The Owner shall recognize this issue and expect that operator deregistration
// takes some time to be fully effective.
``` [4](#0-3) 

There is no code path that automatically removes the deployer from `operators` when ownership is transferred.

### Impact Explanation

After ownership transfer, the deployer retains the ability to:
- Call `handleKLAYTransfer` to send arbitrary KAIA from the bridge contract to any address.
- Call `handleERC20Transfer` / `handleERC721Transfer` to mint or transfer bridged ERC-20/ERC-721 tokens.
- Call `setKLAYFee` / `setERC20Fee` to manipulate bridge fee parameters.

All of these are `onlyOperators` functions. With the default threshold of 1, no co-signature is required. The deployer can act unilaterally, draining the bridge or corrupting its accounting state.

### Likelihood Explanation

This manifests whenever:
1. The bridge is deployed and ownership is transferred to a new address (e.g., a multisig or governance contract) — a standard operational step.
2. The new owner does not explicitly call `deregisterOperator(deployer)` — an easy omission since the code provides no warning and no automatic cleanup.
3. The deployer's key is later compromised, or the deployer acts maliciously.

The default threshold of 1 means no collusion is required; the deployer alone can execute any value transfer.

### Recommendation

1. **Remove the deployer from `operators` automatically on ownership transfer** by overriding `transferOwnership` to call `deregisterOperator(msg.sender)` before handing off.
2. **Alternatively**, do not auto-register `msg.sender` as an operator in the constructor; require the owner to explicitly call `registerOperator` after deployment.
3. **Document** in the security overview that the deployer address must be deregistered as an operator after ownership transfer, analogous to the Neptune Mutual fix of removing the deployer as a protocol member.

### Proof of Concept

```
1. Alice deploys Bridge.sol → Alice is owner AND operators[Alice] = true, threshold = 1.
2. Alice calls transferOwnership(Multisig) → Multisig is now owner; operators[Alice] still true.
3. Multisig does NOT call deregisterOperator(Alice) (easy omission; no code enforces it).
4. Alice (or attacker with Alice's key) calls:
       bridge.handleKLAYTransfer(fakeTxHash, victim, attacker, bridgeBalance, nonce, blockNum, "")
   → _voteValueTransfer passes (Alice is operator, threshold=1, vote count reaches 1).
   → closedValueTransferVotes[nonce] = true.
   → attacker.call.value(bridgeBalance)("") executes.
   → Bridge is drained of all KAIA.
``` [1](#0-0) [3](#0-2) [5](#0-4)
