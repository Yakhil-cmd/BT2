## Analysis

The claim traces through three independent gaps that combine into a cross-tenant forgery:

**1. Signature verification is keyed by attacker-supplied `repository_owner`, not by the commit being mutated.**
`WebhooksController#verify_signature` looks up the GitHub App config using `repository_owner`, which is read straight from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), and then checks the signature against *that* org's secret. [1](#0-0) [2](#0-1) 

**2. `verify_webhook_signature` short-circuits to `true` whenever that org has no configured `webhook_secret`.**
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 
This is not a theoretical config: the shipped example secrets files and the test dummy config all default `webhook_secret` to nil. [4](#0-3) [5](#0-4) 
So an attacker who names *any* onboarded org that has no secret configured as `repository.owner.login` bypasses signature verification entirely — no valid HMAC of any algorithm is required. The "legacy sha1 vs sha256" framing in the question is a red herring for this class of attacker: HMAC‑SHA1 as a MAC is not forgeable without the secret, so the real hole is the no‑secret short‑circuit, not the algorithm choice.

**3. `StatusHandler` never re-checks that the forged commit belongs to the org that authenticated the request.**
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5) 
The `params` schema for this handler accepts `sha`, `state`, `context`, etc. — there is no `repository` field constraint at all. [7](#0-6) 
`Commit.where(sha:)` is a global, unscoped query across every stack in the installation. If the victim's target commit sha (public on GitHub, e.g. the head of an open PR) happens to match a `Commit` row belonging to a *different* stack than the one whose org authenticated the request, that commit still gets the forged status recorded via `create_status_from_github!` → `add_status`.

**Downstream effect on a `merge_queue_enabled` stack.**
`Commit#add_status` calls `stack.schedule_merges` whenever the new status is `pending` or `success`. [8](#0-7) 
That eventually runs `ProcessMergeRequestsJob#perform`, which checks `merge_request.all_status_checks_passed?` and calls `merge_request.merge!`. [9](#0-8) 
`MergeRequest#merge!` calls the GitHub merge API directly using the stack's own `github_api` credentials. [10](#0-9) 

**The broken binding, stated explicitly:**
Expected: `authenticated_org(request) == owning_org(Commit matched by params.sha)` for every mutation performed by a webhook handler.
Actual: `authenticated_org(request)` is whatever `repository_owner` the attacker puts in the JSON body (and can be an org with no secret, making authentication vacuous), while `owning_org(Commit matched by params.sha)` is determined solely by which stack happens to contain a commit row with that sha — these are never compared anywhere in `WebhooksController`, `Webhooks::Handler`, or `StatusHandler`. The two sides are independent, so the invariant does not hold.

No other guard intervenes: `drop_unhandled_event` only checks the event type is registered, `check_if_ping` only special-cases `ping`, and there's no `ExplicitParameters` field or before_action tying the handler's mutation target back to the authenticated repository. [11](#0-10) 

### Title
Unscoped `Commit.where(sha:)` in `StatusHandler` combined with no-secret-org signature bypass allows cross-repository forged CI status and unauthorized merge-queue `merge!` — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`, `lib/shipit/github_app.rb`, `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook against whatever organization the attacker names in the JSON body, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that named organization has no `webhook_secret` configured (the shipped default). `StatusHandler` then applies the forged `status` event to `Commit.where(sha: params.sha)` with no repository/stack scoping, so a forged status for a commit sha belonging to a completely different, secret-protected stack gets recorded, and on a `merge_queue_enabled` stack this can trigger `ProcessMergeRequestsJob` to call `MergeRequest#merge!`.

### Finding Description
The invariant that should hold is `authenticated_org(request) == owning_org(commit mutated)`. It is violated because (1) the org used for signature verification is taken from attacker-controlled `params.dig('repository','owner','login')`; (2) verification is skipped entirely for any org with no configured secret (`return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`); and (3) `StatusHandler#process` resolves the target `Commit` purely by `sha`, globally, with no check that the commit's stack/repository matches the org that was (nominally) authenticated. An attacker names a no-secret org as `repository.owner.login`, sets `sha` to the public head sha of a victim's open PR/branch on a `merge_queue_enabled` stack, sets `state: success` and a `context` matching a required check, and POSTs to `/webhooks` with `X-Github-Event: status`. The request passes `verify_signature` trivially, `StatusHandler` finds the victim's `Commit` row by sha and calls `create_status_from_github!`, which can flip the commit to `success` and trigger `stack.schedule_merges` → `ProcessMergeRequestsJob` → `MergeRequest#merge!`, causing GitHub to merge the PR.

### Impact Explanation
This is a payload authenticated for one (attacker-controlled, secretless) repository mutating another repository's `Commit`/`Status` state and, on a merge-queue-enabled stack, causing `MergeRequest#merge!` to fire against the victim's real GitHub repository using Shipit's own credentials — an unauthorized merge of code the attacker did not need review/CI approval for. This matches the Critical category "unauthorized deploy, rollback or merge" and "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any stack whose head/PR commit sha the attacker can learn (trivially public on GitHub) as long as at least one org without a `webhook_secret` is configured anywhere in the same Shipit installation.

### Likelihood Explanation
Preconditions: the Shipit deployment must have at least one onboarded GitHub organization with no `webhook_secret` set — the documented and shipped default configuration shows `webhook_secret: # nil`, making this a realistic operational state rather than a contrived edge case. The attacker needs no Shipit credentials, no GitHub write access to the victim repo, and only needs to know a target commit sha (public). Cost is a single unauthenticated HTTP POST; the attack is fully repeatable.

### Recommendation
Scope `StatusHandler` (and other sha-keyed handlers) mutations to the repository that was actually authenticated for the request — pass the verified organization/repository through to handlers and filter `Commit.where(sha:, stack: { repository: authenticated_repo })` — and remove or gate the `return true unless webhook_secret` short-circuit so organizations without a configured secret cannot bypass signature verification for events they didn't send.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb`, add (conceptually):
1. Configure two orgs in `secrets`: `victim_org` with a `webhook_secret` set, and `attacker_org` with `webhook_secret: nil`.
2. Create `stack = shipit_stacks(:merge_queue_enabled)` under `victim_org`, with `merge_queue_enabled: true`, and a pending `MergeRequest` whose `head.sha == "deadbeef..."`.
3. POST `X-Github-Event: status` with body `{"repository": {"owner": {"login": "attacker_org"}}, "sha": "deadbeef...", "state": "success", "context": "<required context>"}` and no valid `X-Hub-Signature`.
4. Assert response is `:ok` (signature check passed vacuously because `attacker_org` has no secret).
5. Assert `commit.reload.state == "success"` for the victim's commit, and assert `ProcessMergeRequestsJob` was enqueued for `victim` stack (or, with `MergeRequest.any_instance.expects(:merge!)`, that merge is attempted) — demonstrating `authenticated_org(request) ("attacker_org") != owning_org(commit) ("victim_org")` yet the mutation and merge queue advancement occurred anyway.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
