### Title
`Api::CCMenuController` overrides `stack` to bypass the `stacks` scope, letting a stack-scoped token read any other stack's deploy data - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` enforces both a permission check (`read:stack` present in `current_api_client.permissions`) and a scope restriction (`stacks` filtered to `current_api_client.stack_id` when set) before resolving `stack`. `Api::CCMenuController` keeps the class-level `require_permission :read, :stack` before_action, but overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model instead of `stacks.from_param!`, which discards the `stack_id` binding entirely.

### Finding Description
The intended binding is: `current_api_client.stack_id == params[:stack_id]` (i.e. a token issued for stack A must not be able to resolve a `stack` object for stack B) whenever `current_api_client.stack_id?` is true.

In `Api::BaseController`: [1](#0-0) 
`stacks` restricts the queryable set to the client's bound stack when `stack_id` is present, and `stack` resolves through that restricted relation. This is the mechanism that ties the `read:stack`/`deploy:stack` permission strings to a *specific* stack rather than to every stack in the system.

`Api::CCMenuController` overrides `#stack` to bypass this relation: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` on the model class directly, never touching `current_api_client.stack_id`. The class-level `require_permission :read, :stack` before_action only calls `current_api_client.check_permissions!('read', 'stack')`: [3](#0-2) 
which merely checks that the literal string `"read:stack"` is present in the `permissions` array — it never inspects `stack_id` or compares it to `params[:stack_id]`. As a result the permission check and the scope check are fully decoupled in this controller: any client holding `read:stack` (regardless of the stack it was issued for) can successfully call `show` for any stack in the system.

Attacker flow: possess a valid `ApiClient` token with `permissions: ['read:stack']` and `stack_id` bound to stack A (this is exactly the kind of read-only, per-stack token that `CcmenuUrlController#fetch` issues for CI dashboard integrations, and its token travels in a query string, further increasing exposure). Send `GET /api_stacks/:stack_b_param/cc.xml?token=<token>` for an unrelated stack B. `authenticate_api_client` (overridden in this controller to accept `params[:token]`) succeeds, `require_permission!('read','stack')` passes because the token has `read:stack`, and `stack` resolves to stack B via the unscoped `Stack.from_param!`, leaking stack B's latest deploy/rollback status, build label and web URL in the CCMenu XML.

Existing guards do not prevent this: `check_permissions!` only checks the permission string, and the scope enforcement lives solely in `Api::BaseController#stacks`/`#stack`, which this subclass does not call.

### Impact Explanation
An attacker holding any token with `read:stack` — including a narrowly-scoped, per-stack CCMenu token meant only for one project's CI dashboard — can enumerate/read deploy status (`activity`, `lastBuildStatus`, `lastBuildLabel`, `webUrl`) for every stack managed by the Shipit instance, not just the one the token was issued for. This is a cross-tenant unauthorized read of stack/deploy state, repeatable for arbitrary stacks by simply varying `params[:stack_id]`, matching the "unauthenticated/unauthorized read of stack state... deploy output" High-severity category.

### Likelihood Explanation
The attacker needs only a single valid, low-privilege `read:stack` API token bound to any one stack (such tokens are routinely generated and embedded in CCMenu URLs for CI status widgets, per `CcmenuUrlControllerTest`). No GitHub secrets, session, or elevated role is required. The exploit is a single unauthenticated-effort GET request with a different `stack_id`, fully repeatable against any stack ID/slug in the target instance.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation instead of the raw `Stack` model, e.g. `stacks.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` binding is enforced identically to every other API controller.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb`:
1. Create `stack_a` and `stack_b`.
2. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id: stack_a.id`.
3. `get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }`.
4. Assert the binding `current_api_client.stack_id == resolved_stack.id` should hold: expect `response` to be `:forbidden` or `:not_found` (since `stack_b.id != client.stack_id`), but the current code returns `:ok` with `assert_payload 'name', stack_b.to_param`, proving the divergence: permission check passes (`read:stack` present) while the scope binding (`stack_id`) is silently ignored.
