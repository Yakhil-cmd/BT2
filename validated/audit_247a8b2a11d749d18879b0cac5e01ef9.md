### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while all event handlers act on the independently-attacker-supplied `repository.full_name`, allowing an org onboarded to a multi-org Shipit instance to forge writes against a different org's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to validate an inbound GitHub webhook based on `repository_owner`, computed from the payload's `repository.owner.login` (or `organization.login`) field <cite repo="hirayap/shipit-engine--018" path="app/controllers/shipit/webhooks_controller.rb" start="24,55" end="30,62"/>. Once verified, the full, unconstrained JSON payload is dispatched unmodified to every registered handler for the event <cite repo="hirayap/shipit-engine--018" path="app/controllers/shipit/webhooks_controller.rb" start="10,12" end="10,12"/>. Every handler, however, resolves the `Repository`/`Stack` it mutates from a *different* field of the same attacker-controlled payload: `payload.dig('repository', 'full_name')` <cite repo="hirayap/shipit-engine--018" path="app/models/shipit/webhooks/handlers/handler.rb" start="32,36" end="34,38"/>, mirrored in every concrete handler (e.g. `PullRequest::OpenedHandler#repository`, `ClosedHandler#repository`, `LabeledHandler#repository`, etc., all doing `Shipit::Repository.from_github_repo_name(params.repository.full_name)`) [1](#0-0) [2](#0-1) [3](#0-2) .

### Finding Description
`Shipit.github(organization: repository_owner)` selects among the configured `github:` entries (Shipit explicitly supports one GitHub App per organization, each with its own independent `webhook_secret`, as shown in `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.example.yml`) [4](#0-3) . The signature check only proves that the byte-for-byte JSON body was signed with the secret belonging to `repository_owner` (i.e., `repository.owner.login`). Nothing constrains `repository.full_name` to be a repository actually owned by that same login - both fields live in the same attacker/GitHub-supplied JSON body, and are read independently.

Binding that is broken: `organization authenticated == repository written` is assumed but never enforced. Concretely:
- Verified side: `params.dig('repository','owner','login')` (used only to pick the HMAC key) [5](#0-4) .
- Acted-on side: `payload.dig('repository','full_name')` (used by every handler to resolve the target `Repository`/`Stack` to mutate) [6](#0-5) .

Anyone who possesses a valid `webhook_secret` for *one* onboarded GitHub organization/App on a multi-org Shipit instance (each org's own admins are expected to know their own secret, since they configured it when creating their GitHub App per `docs/setup.md`) can compute a valid `X-Hub-Signature` for an arbitrary JSON body, then set `repository.owner.login` to their own org (so the correct secret is selected) while setting `repository.full_name` to `"other-org/other-repo"` for a totally different, unrelated organization also hosted on the same Shipit instance. The forged, correctly-signed webhook is then routed to handlers that operate on the victim org's `Stack`s: e.g. `PullRequest::ClosedHandler#process` calls `review_stack.archive!` [7](#0-6) , `LabeledHandler#handle` can `stack.archive!`/`stack.unarchive!` [8](#0-7) , and `PushHandler`/`OpenedHandler` create/provision review stacks and enqueue `GithubSyncJob` for the victim's repositories.

### Impact Explanation
This crosses the "cross-repository writes" Critical bar explicitly listed in scope: a party authenticated as one GitHub organization on the Shipit instance can force writes (archiving/unarchiving review stacks, provisioning new review stacks, mutating pull-request/label state, triggering sync jobs) against a *different* organization's repositories that it has no legitimate relationship to, purely by exploiting the mismatch between the field used for signature-org selection and the field used for target-repository resolution.

### Likelihood Explanation
Requires only that the attacker be a legitimate holder of a `webhook_secret` for *some* organization already onboarded to the same multi-org Shipit deployment (a standard, documented configuration, not a privileged or exotic setup) - it does not require GITHUB_TOKEN, `api_clients_secret`, or write access to the victim repository itself, satisfying the "unprivileged attacker" bar relative to the victim organization.

### Recommendation
In `WebhooksController`/`Handler`, derive the authorization scope and the acted-upon repository from the same, single verified field. Concretely: after verifying the signature, assert that `payload.dig('repository','full_name')`'s owner segment equals the `repository_owner` used to select the webhook secret (or, better, resolve the `Repository` first and then use its own configured organization to pick the secret) before dispatching to any handler.

### Proof of Concept
1. Shipit is configured (as in `test/dummy/config/secrets_double_github_app.yml`) with two orgs, `OrgA` (secret `SECRET_A`) and `OrgB` (secret `SECRET_B`), each with repositories/stacks tracked in the same Shipit instance.
2. An attacker who is an admin of `OrgA` (and thus knows `SECRET_A`) crafts a `pull_request` `closed` event payload where:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/victim-repo"`
3. Attacker computes `X-Hub-Signature: sha1=HMAC(SECRET_A, body)` and POSTs to `/webhooks` with `X-Github-Event: pull_request`.
4. `verify_signature` computes `repository_owner == "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and the signature validates successfully [9](#0-8) .
5. `Webhooks.for_event('pull_request')` handlers run against the same `params`, and `ClosedHandler#repository` resolves `Shipit::Repository.from_github_repo_name("OrgB/victim-repo")`, archiving `OrgB`'s review stack despite the request never being signed by `OrgB`'s secret [2](#0-1) .
