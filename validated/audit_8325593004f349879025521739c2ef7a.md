## Title
Missing array-shape validation of `mci`/`age`/`timestamp` definition operator args can crash a node - ([File: definition.js])

### Summary
`definition.js`'s `validateDefinition()` handles address/asset spending-condition expressions submitted inside any unit's `author.definition` (new address definitions) or asset `issue_condition`/`transfer_condition`. In the `'mci'`/`'age'`/`'timestamp'` branch, the 2-element-array shape of `args` is checked only conditionally, gated by an mci-based feature flag, before `args[0]` and `args[1]` are dereferenced. [1](#0-0) 

### Finding Description
The generic expression evaluator in `evaluate()` only guarantees that the outer expression `arr` is a 2-element array (`op`, `args`) via `isArrayOfLength(arr, 2)`; it does **not** constrain the shape/type of `args` itself — that responsibility is delegated to each `case` handler. [2](#0-1) 

For most ops (`or`/`and`, `r of set`, `in data feed`, `in merkle`, `has`/`has equal`, `attested`, etc.) the handler unconditionally validates that `args` is an array/object of the right shape before indexing into it. But for `'mci'`, `'age'`, `'timestamp'`:

```
if (!isArrayOfLength(args, 2) && (objValidationState.last_ball_mci >= constants.pemCurvesFixMci || !objValidationState.hasBall && storage.getMinRetrievableMci() >= constants.pemCurvesFixMci))
    return cb(op + " must have 2 args");
var relation = args[0];
var value = args[1];
``` [3](#0-2) 

The shape check is skipped whenever `objValidationState.last_ball_mci < constants.pemCurvesFixMci` (and the ball/min-retrievable-mci alternative condition is also false). In that code path, `args` can be attacker-supplied JSON of any type — `null`, a number, a string, or an object — coming straight from the unit's definition payload. If `args` is `null` or `undefined`, `args[0]` throws an uncaught `TypeError: Cannot read properties of null/undefined`. This is functionally the same bug class as CVE-2017-14641 (dereferencing an attacker-influenced pointer/field without a null/shape check before use), just manifesting as a JS `TypeError` instead of a C++ null-pointer segfault.

This validation path is reached from ordinary unit processing: `validateAuthor()` → `Definition.validateDefinition()` for new/changed address definitions, and `validateAssetDefinition()` → `Definition.validateDefinition()` for `issue_condition`/`transfer_condition` on any asset message — all triggerable by an unprivileged unit poster. [4](#0-3) 

Critically, `ocore`'s network layer treats any uncaught exception as fatal by design: `process.on('uncaughtException', ...)` explicitly re-throws to crash the process ("to avoid ending up in an inconsistent state"). [5](#0-4) 

Because unit validation happens inside nested asynchronous callbacks (`async.eachSeries`/`async.series` chains) rather than directly inside a caller's `try/catch`, a thrown `TypeError` in `validateDefinition` is not caught anywhere up the stack and reaches the global `uncaughtException` handler, crashing the node process.

### Impact Explanation
A crash of a full node (or witness/hub) upon processing a single malformed/malicious unit is a remote, unauthenticated denial-of-service: any peer can broadcast a unit containing a definition with a malformed `mci`/`age`/`timestamp` filter, and every full node that validates it (while its own `last_ball_mci` is below `pemCurvesFixMci`) crashes. Repeated crashes across the network would leave nodes unable to confirm new units — satisfying "a network unable to confirm new units."

### Likelihood Explanation
Exploitability is **conditional** and time/state dependent: the vulnerable branch only triggers while `objValidationState.last_ball_mci < constants.pemCurvesFixMci` (or the equivalent `hasBall`/`getMinRetrievableMci` condition). On a long-running mainnet where `pemCurvesFixMci` has already been passed, currently-processed new units would have `last_ball_mci` above that threshold, making the shape check always enforced for freshly-posted units — closing this specific path for new activity. However, the vulnerability remains live for: (a) any network/testnet/devnet instance that has not yet reached `pemCurvesFixMci`, (b) full nodes performing initial historical catch-up/replay through the pre-upgrade mci range, and (c) light clients requesting proofs for old addresses whose defining unit predates the upgrade, if that code path re-invokes `validateDefinition` with the same conditional gating. I was not able to fully confirm the exact numeric value of `pemCurvesFixMci` relative to current mainnet mci from the available index, so the real-world reachability window on mainnet today is uncertain and should be verified against `constants.js`.

### Recommendation
Remove the mci-based gating around the `isArrayOfLength(args, 2)` check for the `'mci'`/`'age'`/`'timestamp'` operators (or apply it unconditionally regardless of `last_ball_mci`/`hasBall`), matching the pattern already used for `'in merkle'` and `'in data feed'`. As defense in depth, wrap the whole `evaluate()`/`validateDefinition()` call chain (and other unit-validation entry points) so that any unexpected synchronous exception is converted into a `callback(err)` / `ifUnitError` instead of propagating to `uncaughtException`, preventing a single malformed field from crashing the process regardless of which check is missing.

### Proof of Concept
1. Construct a unit whose `authors[0].definition` is:
```json
["mci", null]
```
(or `["age", 5]`, `["timestamp", "x"]` — any non-2-element/non-array `args`).
2. Ensure this unit is validated while `objValidationState.last_ball_mci < constants.pemCurvesFixMci` (e.g., during initial catch-up sync on a node still processing early-DAG history, or on a testnet/devnet before this upgrade point).
3. `validateDefinition()` reaches `case 'mci':`, skips the shape check because the mci gate is false, and executes `var relation = args[0];` on `args = null`, throwing `TypeError: Cannot read properties of null (reading '0')`.
4. This exception is not caught by any surrounding `try/catch` in the async validation chain and reaches `network.js`'s `process.on('uncaughtException', ...)` handler, which re-throws and crashes the node process — denial of service.

**Note on confidence:** I could not execute this PoC against a live node or confirm the current value of `constants.pemCurvesFixMci` versus present-day mainnet `last_ball_mci`, so I cannot state with certainty whether this path is exploitable on mainnet today versus only on catch-up/testnet scenarios. This should be verified directly against `constants.js` and a running node before treating this as an active mainnet-exploitable issue.
