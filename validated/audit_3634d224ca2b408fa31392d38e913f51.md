### Title
Cross-organization webhook authentication bypass via unbound `repository.owner.login` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook against by reading `repository.owner.login` (or `organization.login`) out of the *unverified* JSON body, then verifies the HMAC using that organization's secret. Because different organizations can be configured independently in multi-org mode, and any one org can be onboarded with no `webhook_secret` set, the "organization that authenticated" the request and the "repository/stack that gets written" by the event handlers are not the same value and are not both covered by a single verified binding.

### Finding Description
`verify_signature` computes the signing organization purely from attacker-controlled JSON before any signature has been validated: [1](#0-0) 

`repository_owner` is read straight out of `params`, which is just `JSON.parse(request.raw_post)`: [2](#0-1) 

`Shipit.github(organization:)` looks up that organization's own independent config block (including its own `webhook_secret`) in multi-org mode: [3](#0-2) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected org's `webhook_secret` is blank/unset: [4](#0-3) 

The per-organization config schema and the fact that `webhook_secret` is entirely optional per org are documented and exemplified: multiple orgs are configured as independent sibling blocks, each with its own optional `webhook_secret`: [5](#0-4) [6](#0-5) 

Once `head(422)` is (conditionally) skipped, the controller dispatches the full attacker-supplied `params` to the registered handlers for the event type, and downstream jobs like `GithubSyncJob` act on whatever repository/stack the payload claims, entirely independent of which org's secret (if any) was used for verification: [7](#0-6) [8](#0-7) 

**Binding broken:** `organization authenticated (repository.owner.login used to pick webhook_secret)` ≠ `repository/stack actually mutated (repository.full_name / commit data elsewhere in the same unverified body)`.

Before the attacker's request: every event is only ever accepted if signed by the specific org's configured secret, and the org whose secret validated the request is the same org whose repository is acted upon (single-org deployments, or every org has a secret configured).

After the attacker's request: an unprivileged party who knows (or guesses, e.g. from public installation lists) the name of *any* organization in the multi-org config that has not yet had `webhook_secret` set, can send `X-Github-Event: push` (or `membership`, `check_suite`, `status`, `pull_request`, etc.) with `repository.owner.login` (or `organization.login`) set to that unsecured org, while all other repository/commit/team/member fields in the body reference a *different, secured* organization's stack. `verify_webhook_signature` returns `true` unconditionally for the unsecured org, and the handler then processes the payload's claims about the secured org/repo as if genuine — e.g. enqueuing `GithubSyncJob` for a real stack, creating `Team`/`User`/`Membership` records via the `membership` handler, or injecting a fabricated commit-status via the `status` handler — none of which required possessing the secured org's `webhook_secret`.

### Impact Explanation
This allows unauthenticated read/write influence over stacks belonging to a different, properly-secured GitHub organization sharing the same Shipit instance: forging commit statuses (bypassing CI gating for deploys), fabricating `membership`/team data that feeds `Shipit.github_teams` authorization checks, and triggering sync/deploy-adjacent jobs — all without ever supplying or knowing the target organization's `webhook_secret`. This matches the High-severity bucket "escalation into `Shipit.github_teams` authorization" / unauthenticated write of stack state, and can contribute to an unauthorized deploy path once combined with CI-status forgery.

### Likelihood Explanation
Exploitability depends entirely on operational configuration: it requires a multi-organization Shipit deployment (`secrets.github` keyed by multiple org names) in which at least one configured organization has no `webhook_secret` set — a state the app permits by design (`webhook_secret` is commented/optional in every example) and that can easily occur transiently while onboarding a new org. No attacker credential, session, or secret is needed; the only prerequisite is knowledge of an org name in the multi-org config, which is often discoverable (GitHub org that installed the App, visible via the app's public listing).

### Recommendation
Bind the verified signature to the specific repository/stack being acted upon, not merely to "some configured organization derivable from the raw body":
- Require `webhook_secret` to be present for every organization in multi-org mode (fail closed instead of `return true unless webhook_secret`).
- After successful signature verification, re-derive `repository_owner`/`organization` and reject the event if it doesn't match the organization whose secret validated the signature (i.e., ensure `repository.full_name`'s owner and `repository.owner.login`/`organization.login` used to pick the app are the same and both covered by verification).
- Consider signing/authenticating using a value tied to the specific stack/repository, not the loosely-typed org field taken from an unverified body.

### Proof of Concept
1. Deploy Shipit configured for two organizations in `secrets.yml`: `secured-org` (with `webhook_secret: s3cr3t`) and `new-org` (recently added, `webhook_secret` left blank as shown permissible in `config/secrets.development.example.yml`).
2. Attacker (no secret) POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "new-org" }, "full_name": "secured-org/critical-app" },
  "after": "<attacker-chosen sha>",
  "ref": "refs/heads/main"
}
```
3. `repository_owner` resolves to `new-org` [2](#0-1) ; `Shipit.github(organization: 'new-org')` loads `new-org`'s config, whose blank `webhook_secret` makes `verify_webhook_signature` return `true` unconditionally [4](#0-3) .
4. The request passes `verify_signature` and is dispatched to the `push` handler, which resolves the stack via `secured-org/critical-app` (`repository.full_name`) and enqueues `GithubSyncJob` for that stack — even though no valid signature for `secured-org` was ever presented.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
