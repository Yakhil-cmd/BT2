### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository scoping, unlike other webhook handlers that scope through `Repository.from_github_repo_name(repository_name)`. Because git SHAs are content-addressed and identical across forks/clones of the same history, an attacker who owns a repository sharing commit history with a victim stack can send a genuinely signed `status` webhook from their own repo and have it applied to the victim's `Commit` record, altering `deployable?`/`blocked?` state.

### Finding Description
The broken binding: the code assumes `commit.sha == params.sha` implies `commit.stack.repository == webhook.repository`, i.e. `Commit.where(sha: params.sha) ⊆ commits belonging to the repository that signed this webhook`. This is false — SHA is a property of content/history, not of a specific GitHub repository, and multiple `Stack`/`Repository` records in Shipit can hold `Commit` rows with the same `sha` (e.g., a fork of the victim repo, or any repo that happens to import/rebase the same commit).

Path: `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the JSON body and dispatches to handlers via `Shipit::Webhooks.for_event(event)`. `verify_signature` (lines 24-49) only checks that the payload is signed with the secret belonging to `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload (`params.dig('repository','owner','login')`). This proves the request came from GitHub for *some* repo under that owner/org — it says nothing about which `Stack`/`Repository` inside Shipit the SHA belongs to.

`StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ignores `payload.dig('repository','full_name')` entirely and never uses the `stacks`/`repository_name` scoping helper defined in the base `Handler` class (app/models/shipit/webhooks/handlers/handler.rb:32-38), which other handlers (`pull_request/*_handler.rb`, `check_suite_handler.rb`) do use. `commit.create_status_from_github!` → `add_status` (app/models/shipit/commit.rb:165-169, 366-386) writes a `Status` row, recomputes `status`, and if the simple state flips to `success`, calls `stack.schedule_merges` and, via `Commit#schedule_continuous_delivery` (invoked on create, but re-evaluatable through `deployable?`), `ContinuousDeliveryJob` can trigger an auto-deploy that runs under the stack's configured bot identity when `bot_login`/`Shipit.user` is configured.

Exploit flow: attacker forks or otherwise obtains a repository that shares a commit SHA with the victim stack's repository (trivial via fork — SHAs are preserved). Attacker triggers (or has GitHub trigger, e.g., their own CI) a `status` event with `context: ci/jenkins`, `state: success` for that SHA on their own repo. This request is legitimately signed by GitHub for the attacker's own org/repo, so `verify_signature` passes. `StatusHandler` then matches the SHA against **all** `Commit` rows in the database, including the victim's, and writes a passing status onto the victim's commit, potentially flipping `deployable?` to true and triggering an unauthorized deploy (or, using a failing/error state, blocking the victim's pipeline).

Existing guards do not stop this: `verify_signature` authenticates the sender/org, not the specific Shipit `Stack`/`Repository` being mutated; the `ExplicitParameters` schema only validates field types, not ownership; there is no `repository`/`stack` scoping check anywhere in `StatusHandler`.

### Impact Explanation
A payload legitimately signed for repository A can write a `Status` record onto a `Commit` belonging to stack for repository B, as long as both share a commit SHA. This can flip `Commit#deployable?` (app/models/shipit/commit.rb:227-229) to true, triggering `schedule_continuous_delivery`/`ContinuousDeliveryJob` and an autodeploy under the stack's configured bot (`Shipit.user`) identity — an unauthorized deploy of attacker-influenced state — or conversely inject a failing/error status to block a legitimate release (denial of correct deploys). This is repeatable against any stack whose repository shares history (via fork) with an attacker-controlled repository, i.e., cross-tenant impact is not limited to a single victim. This matches "Critical — a payload for one repository mutating another's stack/commit" and "unauthorized deploy."

### Likelihood Explanation
Preconditions: victim must have a `Stack`/`Commit` with a SHA that is also reachable/known in a repo the attacker owns (trivially achievable by forking the victim's public repo, which is a normal GitHub action requiring no special privilege), and the victim stack must be configured to auto-deploy on `ci/jenkins` success (continuous delivery) with a bot identity. No Shipit secrets, sessions, or GitHub App keys are needed — the attacker only needs GitHub to sign a webhook for their own owned repository, which GitHub does by default for any repo they control. This is low-cost and repeatable at will.

### Recommendation
Scope `StatusHandler#process` to the reporting repository, mirroring the base `Handler#stacks` helper: resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, then restrict the commit lookup to `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))` (or equivalently filter through `stacks.flat_map(&:commits)`), so that a status only ever mutates commits belonging to stacks whose repository actually authenticated the webhook.

### Proof of Concept
minitest outline (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `Repository` A (`owner/repo-a`) with `Stack` A having `bot_login` configured (`Shipit.user`) and continuous deployment enabled, requiring `ci/jenkins`. Create `Commit` with `sha: 'deadbeef...'` on stack A, currently not deployable (no status yet).
2. Create `Repository` B (`attacker/repo-b`) with `Stack` B (attacker-controlled) — no relationship to Stack A other than the shared SHA.
3. Build a payload as if from GitHub for repository `attacker/repo-b`: `{ sha: 'deadbeef...', state: 'success', context: 'ci/jenkins', repository: { full_name: 'attacker/repo-b', owner: { login: 'attacker' } } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `commit_a.reload.deployable?` changed from `false` to `true` (or `commit_a.status.success?` is true) even though the webhook's `repository.full_name` was `attacker/repo-b`, not stack A's repository — proving `stack_a.repository.full_name == payload['repository']['full_name']` is false while the status was still applied, i.e. the equality the code implicitly relies on does not hold.
