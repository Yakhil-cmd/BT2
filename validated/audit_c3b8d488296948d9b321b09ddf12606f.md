## Title
Webhook signature verification is bound to the payload's `repository.owner.login`, but event routing is bound to the unrelated `repository.full_name` field — allowing cross-organization forgery of GitHub events - (File: app/controllers/shipit/webhooks_controller.rb)

## Summary
This is the same bug class as the QR-code report: a security decision is made against one field of attacker-supplied data (`frodo2weborderdev.page.link` substring match) while the field that actually gets *acted on* is a different, unchecked value (the full URL/host used by the WebView). In Shipit, the security decision (HMAC signature verification, which determines whose GitHub App secret is trusted) is made against `repository.owner.login` inside the JSON payload, while the value that determines *which repository/stack the event is applied to* is a separate field, `repository.full_name`, from the very same attacker-controlled payload. Nothing binds these two fields together.

## Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the signature against using a field taken directly from the untrusted JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (or `organization.login`) straight out of the still-unverified request body, then `Shipit.github(organization: repository_owner)` picks that organization's configured `webhook_secret` to check the `X-Hub-Signature` against, via `verify_webhook_signature`: [3](#0-2) 

Once the signature check passes (using whichever organization's secret matched `repository.owner.login`), the actual event handlers resolve the target `Repository`/`Stack` using a *different* field from the same payload, `repository.full_name`: [4](#0-3) 

The same pattern repeats in the pull_request handlers (`closed_handler.rb`, `reopened_handler.rb`, `review_stack_adapter.rb`), which all key off `params.repository.full_name` / `payload.dig('repository','full_name')` to find the stack to mutate — independent of `repository.owner.login`.

The binding that should hold is:
`organization used to authenticate the payload (repository.owner.login)` == `organization embedded in the repository actually written to (repository.full_name)`

The engine never asserts this equality. Both fields live inside the same JSON body and are only protected as a whole by the HMAC — the HMAC proves the body wasn't tampered with by a third party, but says nothing about which organization's secret is "supposed" to sign a body containing an unrelated repository's full name. If an attacker controls (or has legitimately set up) a GitHub App for `attacker-org` on the same multi-tenant Shipit instance (a supported configuration, evidenced by `Shipit.github(organization:)` and the `GithubOrganizationUnknown` rescue path in the same controller), they know `attacker-org`'s `webhook_secret`. They can then construct and sign (with their own secret) a payload where `repository.owner.login = "attacker-org"` (so `verify_signature` picks and validates against their own known secret) but `repository.full_name = "victim-org/victim-repo"` (so the handler routes the event to the victim's `Stack`).

## Impact Explanation
This lets an attacker who only controls their own organization's webhook secret forge `push`, `status`, `check_run`, and `pull_request` events against a victim repository/stack hosted on the same Shipit instance. Forged `status`/`check_run` "success" events feed directly into `MergeRequest::StatusChecker` (`all_status_checks_passed?`, `any_status_checks_failed?`), which gates the automated merge queue (`MergeRequest#merge!`, `Stack#schedule_merges`). Forging these checks green on a victim's pull request can result in an **unauthorized merge**. Forged `push` events can also trigger `GithubSyncJob`, corrupting the victim's synced commit history/deploy state. This satisfies the "unauthorized deploy, rollback, or merge" Critical-impact criterion and constitutes a cross-repository write across organization trust boundaries — exactly the class of binding break the rules call out ("an organization that authenticated versus the repository that is written").

## Likelihood Explanation
Exploitability requires only that the attacker control one legitimate, low-privilege GitHub App/organization already onboarded to the target Shipit instance (a normal, unprivileged, self-service condition in multi-tenant Shipit deployments) — no Shipit session, API token, or GitHub App private key for the victim org is needed. Crafting the payload is trivial (author `repository.owner.login` and `repository.full_name` independently, sign with their own known secret).

## Recommendation
After signature verification succeeds, assert that the organization/owner used to select the verifying secret is the same organization embedded in `repository.full_name` (and `organization.login` when present) before dispatching to handlers. Reject the webhook if they diverge.

## Proof of Concept
1. Attacker owns/administers a GitHub App installed for `attacker-org` on the shared Shipit instance and knows its `webhook_secret`.
2. Attacker builds a `push` (or `status`/`check_run`) JSON payload where:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"`
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the HMAC checks out against `attacker-org`'s secret → request passes.
5. `Shipit::Webhooks.for_event('push'/'status'/...)` handlers resolve the stack via `Repository.from_github_repo_name("victim-org/victim-repo")`, and the forged event is applied to the victim's stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
