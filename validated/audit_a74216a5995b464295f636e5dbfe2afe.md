### Title
Stack-scoped API tokens can read CCMenu status of any stack — (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's `stack` resolver to look up the target stack directly from the request parameter instead of going through the `ApiClient`-scoped collection used everywhere else in the API. This breaks the binding *"the stack a token authorises == the stack it touches"*: an `ApiClient` created with a specific `stack_id` (and only `read:stack` permission) can be used to fetch CCMenu status for **any** stack in the installation, not just the one it was scoped to.

### Finding Description
`Shipit::Api::BaseController` is the mechanism that enforces per-token stack scoping: [1](#0-0) 

`stacks` restricts the visible set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves the requested `params[:stack_id]` **through that restricted collection** (`stacks.from_param!`). Every other API controller (`TasksController`, `StacksController`, etc.) relies on this inherited `stack` method, so a client scoped to stack A raises `RecordNotFound`/404 when asked for stack B.

`CCMenuController`, however, defines its own `stack` method that bypasses the scoped collection entirely: [2](#0-1) 

It resolves `Stack.from_param!(params[:stack_id])` against the full `Stack` table, ignoring `current_api_client.stack_id`. The only authorization check performed is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [3](#0-2) 

That check only verifies the string `"read:stack"` is present in the client's `permissions` array — it has no knowledge of *which* stack the token is bound to. The scope enforcement is expected to come exclusively from `BaseController#stack`/`#stacks`, which `CCMenuController` does not use.

Fixture evidence confirms scoped clients are a supported, tested configuration: [4](#0-3) 

And `CCMenuUrlController` is the legitimate producer of such scoped, query-string-authenticated tokens intended for exactly this endpoint: [5](#0-4) 

The equality that should hold is: `authorized_stack(token) == touched_stack(request)`. Because `CCMenuController#stack` never consults `current_api_client.stack_id`, this equality is not enforced — the token's authorized stack and the stack actually queried can differ.

### Impact Explanation
A token minted for one stack (e.g. via `CCMenuUrlController`, which is designed to hand out narrowly-scoped, low-friction, query-string-token-authenticated CCMenu URLs) can be replayed against `/ccmenu/*stack_id` for a different stack, disclosing that stack's deploy/build status (`lastBuildStatus`, `lastBuildLabel`, lock state, activity, etc.) — information the token holder was never authorized to see. This is an unauthorized read of stack state across the intended authorization boundary, matching the High-impact class "unauthenticated/unauthorized read of stack state, task streams or deploy output."

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token that is scoped to a single stack (a supported, documented configuration surfaced through `CCMenuUrlController`) and knowledge/guessing of another stack's `to_param` (owner/repo/environment triplet, which is largely public/predictable). No privileged access, secret material, or session is needed beyond the scoped token itself — the check bypass is deterministic and always reachable at this route.

### Recommendation
Remove `CCMenuController#stack`'s custom implementation and use the inherited, scope-aware `BaseController#stack` (backed by `stacks`), so that `Stack.from_param!` is always resolved against `current_api_client.stack_id`-restricted collection, consistent with every other API controller.

### Proof of Concept
1. Create two stacks, `stack_a` and `stack_b`.
2. Create an `ApiClient` scoped to `stack_a` only (`stack_id: stack_a.id`, `permissions: ['read:stack']`), e.g. as done by `CCMenuUrlController#client`.
3. As the holder of that client's `authentication_token`, request:
   `GET /ccmenu/<stack_b-to-param>?token=<stack_a-scoped-token>`
4. Expected (correct) behavior: 404, since the token is not authorized for `stack_b`.
5. Actual behavior: `CCMenuController#stack` resolves `stack_b` directly via `Stack.from_param!`, and `show` renders `stack_b`'s CCMenu XML (build status, labels, lock state) — the token holder learns `stack_b`'s state despite being authorized only for `stack_a`.
