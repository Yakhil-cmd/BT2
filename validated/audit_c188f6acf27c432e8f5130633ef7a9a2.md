### Title
`OpenedHandler#provision?` operator precedence bug bypasses `review_stacks_enabled` gate for the `prevent_with_label` branch - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` is written as `A && B || (C && D) || (E && F)`. Because Ruby's `&&` binds tighter than `||`, the `review_stacks_enabled` check (`A`) is only applied to the `allow_all?` clause (`B`) and is never applied to the `prevent_with_label?` clause (`E && F`). Any repository configured with `provisioning_behavior: prevent_with_label`, even with `review_stacks_enabled == false`, will still auto-provision a review stack for any opened PR that carries no label.

### Finding Description
The claimed binding is: `review_stacks_enabled == the gate applied to every provisioning branch`. Tracing the code: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to Ruby operator precedence this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The last two disjuncts have no dependency on `review_stacks_enabled` at all, so the equality the intended design implies — `review_stacks_enabled` gates every behavior — does not hold: `review_stacks_enabled == false` and `prevent_with_label? && !has_label? == true` can coexist and still yield `provision? == true`.

`respond_to_pull_request_opened?` calls `provision?` unconditionally on `action == "opened"` [2](#0-1) , and `process` then calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [3](#0-2) . `find_or_create!` creates a `ReviewStack` record and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)` [4](#0-3) , which later runs `stack.provisioner.provision?` and `stack.provision` from the queue worker [5](#0-4) , driving actual provisioning/execution from the attacker-controlled branch (`params.pull_request.head.ref`) that populates `stack_attributes` [6](#0-5) .

No guard in `ExplicitParameters` schema, signature verification, or `Repository` validations checks this invariant — those layers only validate payload shape and authenticity of the webhook, not the business-logic gate. `review_stacks_enabled` being `false` therefore does not prevent stack creation in the `prevent_with_label` (and also `allow_with_label`) branches. This is confirmed independently by the existing test suite: the test "create stacks for repos what prevent_with_label when label is absent" uses `configure_provisioning_behavior` with the default `provisioning_enabled: true`, never exercising the `review_stacks_enabled: false` case, so the gap is untested [7](#0-6) .

An attacker with no privileges can: fork the target repository (which has `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false`), open a PR from their fork with no labels, and the webhook delivery (a normal GitHub-authenticated webhook, not requiring any Shipit secret) will trigger `OpenedHandler#process`, creating a `ReviewStack`/`Stack` and queuing provisioning that will execute the repository's `shipit.yml` steps sourced from the attacker's branch.

### Impact Explanation
A repository owner disables review stacks (`review_stacks_enabled = false`) expecting no PR-triggered stack creation, yet setting `provisioning_behavior: prevent_with_label` still causes unauthorized `Stack`/`ReviewStack` creation and subsequent provisioning/task execution driven by attacker-controlled branch content. This is a policy-bypass leading to command execution from an untrusted source (`Command`/`PTY.spawn` executing `shipit.yml` from the fork) — matching the "Critical: unauthorized deploy... payload... mutating another's stack" and RCE-adjacent categories, and is repeatable against any repository configured this way.

### Likelihood Explanation
Preconditions: target repository must have `provisioning_behavior: prevent_with_label` set while `review_stacks_enabled: false` — a plausible/likely misconfiguration if operators believe `review_stacks_enabled` is a global on/off switch. Attacker cost is trivial: open a PR with no labels from a public fork. No secrets, no elevated privileges, fully repeatable against any repository sharing that configuration.

### Recommendation
Fix the operator precedence in `provision?` by explicitly gating all branches with `review_stacks_enabled`:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Add a regression test with `review_stacks_enabled: false` for each behavior (`allow_all`, `allow_with_label`, `prevent_with_label`) asserting `assert_no_difference -> { Shipit::Stack.count }`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix this assertion fails (a stack is created despite `review_stacks_enabled == false`); after applying the recommended fix it passes, confirming the binding `review_stacks_enabled == false ⇒ no stack created` holds for the `prevent_with_label` branch.
