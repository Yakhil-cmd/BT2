### Title
Stack-scoped API token can read any stack's CI/deploy status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` re-implements the `stack` lookup instead of reusing `Shipit::Api::BaseController#stack`, and in doing so drops the check that ties an `ApiClient` token to the single `Stack` it is scoped to. Any valid `ApiClient` token that only has `read:stack` permission and is bound to one stack (`ApiClient#stack_id`) can be replayed against `/api/stacks/*stack_id/ccmenu` for an arbitrary other stack, exposing that stack's build/deploy status.

### Finding Description
`Shipit::Api::BaseController` defines the intended authorization binding between a token and the stacks it may touch: [1](#0-0) 

`stacks` is restricted to `current_api_client.stack_id` when the client is scoped, and every other API controller (tasks, deploys, hooks, merge_requests, etc.) inherits this `stack` method unmodified, so `require_permission :read, :stack` combined with `stacks.from_param!` enforces: `stack.id == current_api_client.stack_id` (when the client is stack-scoped).

`CCMenuController` breaks this equality by overriding `stack`: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly — not `stacks.from_param!` — so the `stack_id` scoping performed in `BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-76`) is never applied. `require_permission :read, :stack` (`app/controllers/shipit/api/ccmenu_controller.rb:6`) only checks that the token's `permissions` array contains `read:stack` via `ApiClient#check_permissions!`: [3](#0-2) 

It never checks whether the requested stack matches the token's own `stack_id`. The `ApiClient` model itself supports per-stack scoped clients (`belongs_to :stack, optional: true`), and the fixture `here_come_the_walrus` demonstrates this is a real, exercised feature: [4](#0-3) 

So the binding that should hold is: *stack a token authorizes* (`current_api_client.stack_id`) `==` *stack it touches* (`params[:stack_id]` resolved to a `Stack`). Before the request: an attacker holds a valid, unmodified `read:stack` token scoped to Stack A. After the request: the same token, unmodified, is presented against Stack B's `ccmenu` endpoint and the controller happily resolves and serves Stack B's data because `CCMenuController#stack` bypasses the `stacks` scope entirely.

### Impact Explanation
An attacker who holds any legitimate stack-scoped `read:stack` API token (e.g., one issued for a low-privilege integration against a single, non-sensitive stack) can enumerate `stack_id` path segments and pull the CCMenu XML (`activity`, `lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc. — see `test/controllers/api/ccmenu_controller_test.rb:33-39`) for every other stack managed by the Shipit instance, including stacks/repositories the token was never authorized to see. This is an unauthorized cross-stack read of deploy/build state, matching the "unauthenticated read of stack state" High-impact category (the token is authenticated but not authorized for the target stack, which is the escalation).

### Likelihood Explanation
Exploitation requires only possession of any stack-scoped API token with `read:stack` permission — no elevated privilege, no repository write access, no GitHub credentials, and no interaction with signature/HMAC verification. The mismatch is a straightforward routing/authorization bug reachable on every request to the `ccmenu` endpoint.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped lookup from `BaseController`, i.e. `stacks.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction is enforced consistently with every other API controller.

### Proof of Concept
1. As an authorized user, create (or have Shipit create, e.g. via `CCMenuUrlController#fetch`) an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` and `stack: StackA`.
2. Using that client's `authentication_token`, issue: `GET /api/stacks/<StackB-owner>/<StackB-repo>/<env>/ccmenu?token=<tokenForStackA>`.
3. Observe that `CCMenuController#show` renders Stack B's CI/deploy XML, even though the token is only authorized (`stack_id`) for Stack A, because `stack` resolves via `Stack.from_param!` instead of the scoped `stacks.from_param!` used everywhere else.
