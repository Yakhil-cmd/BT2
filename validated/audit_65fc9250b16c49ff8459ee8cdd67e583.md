### Title
`StatusHandler#process` fans out `Status` writes to every `Commit` sharing a sha, ignoring the webhook's `repository.full_name` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `sha` (`Commit.where(sha: params.sha)`), with no filter on the repository named in the verified webhook payload. Every other event handler (e.g. `PushHandler`) scopes its effect through the `stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)` before touching any `Stack`; `StatusHandler` alone bypasses this and never calls `stacks` or checks `repository_name` at all.

### Finding Description
The binding that should hold is: `stacks_receiving_status == Repository.from_github_repo_name(payload['repository']['full_name']).stacks.where(sha: params.sha)` (i.e., bounded to the single repository named and signature-verified in the payload). Instead, the actual code is: [1](#0-0) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This queries the global `commits` table by `sha` alone, across every `Stack`/`ReviewStack` in the installation, and calls `commit.create_status_from_github!(params)` on each match — this writes a new `Status` row and can trigger `Hook.emit(:deployable_status, ...)`/`stack.schedule_merges` per matched stack via `Commit#add_status`, `Commit#create_status_from_github!` ( [2](#0-1) , [3](#0-2) ).

Compare with `PushHandler`, which correctly narrows to the repository named in the payload before acting on any stack: [4](#0-3) [5](#0-4) 

`StatusHandler` never calls `stacks`/`repository_name`, so `params.repository` is entirely unused for scoping.

The webhook signature check (`WebhooksController#verify_signature` → `GithubApp#verify_webhook_signature`, keyed off `repository_owner`) only proves the request came from the org that owns *one* repository — it says nothing about which `sha`s exist in that org's repos, and does not constrain the query in `StatusHandler#process`. `ExplicitParameters` only validates the payload shape (`sha`, `state`, etc.), not that the `sha` is exclusive to the named repository. Since the same commit sha can legitimately exist in multiple `Stack`/`ReviewStack` rows across different repositories (via `Commit.where(sha:)` matching independent tables, no `stack_id`/repository filter on the sha column), and because GitHub's create-status API does not require the sha to reference an actually-existing commit inside the calling repository, an attacker who owns a repo with a Shipit webhook installed can:

1. Discover/observe a public sha belonging to a target repository (e.g. a public commit sha shown on GitHub or on a target Shipit review stack's timeline).
2. POST a `status` event (via GitHub's real API against their own repo, using their own valid credentials/webhook secret) specifying that observed `sha` and `state: "success"`.
3. GitHub delivers a legitimately signed webhook to Shipit for the attacker's own repo, which passes `verify_signature`.
4. `StatusHandler#process` runs `Commit.where(sha: <that sha>)`, which finds and mutates the `Status` state of the commit row in the *unrelated* target repository's stack(s)/review stack(s) — none of which are the repository named/verified in the payload.

### Impact Explanation
An attacker can write a fabricated `success` (or any) `Status` for a specific commit belonging to a stack or review stack they do not control, potentially triggering `deployable_status` hooks and `stack.schedule_merges` (continuous-delivery/merge-queue processing) for that unrelated repository — a payload for one repository mutating another's commit/stack state. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team." The blast radius is every `Stack`/`ReviewStack` row across the entire Shipit installation that happens to contain a `Commit` with the same sha, not just the repository named in the payload, and is repeatable per known sha.

### Likelihood Explanation
Preconditions: the attacker needs (a) their own repository with a Shipit-recognized GitHub App/webhook installed (something any GitHub user with a Shipit-integrated org/repo they control can arrange, per the threat model — "any internet user ... including POST /webhooks" and "any GitHub user who can ... emit webhooks from a repository they own"), and (b) knowledge of a target commit sha (shas are frequently public — visible in PR pages, commit history, CI dashboards, or the review-stack UI itself). No Shipit secrets, sessions, or team membership are required. This is straightforward and repeatable against any known sha.

### Recommendation
Scope `StatusHandler#process` to the repository named in the verified payload, mirroring `PushHandler`/`Handler#stacks`:

```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

or equivalently join through `stack_id` so only commits belonging to `Repository.from_github_repo_name(params.repository.full_name).stacks` are affected.

### Proof of Concept
minitest plan (place logic conceptually in `test/models/shipit/webhooks/handlers/status_handler_test.rb`, or as a controller test against `POST /webhooks`):

```ruby
test "a status webhook for one repository must not update commits belonging to other stacks" do
  shared_sha = "deadbeef" * 5  # 40-char sha shared across fixtures

  stack_a = shipit_stacks(:shipit) # repository X
  stack_b = create_stack_with_repo("other/repo-b")
  stack_c = create_stack_with_repo("third/repo-c")

  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)
  commit_c = stack_c.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => stack_a.github_repo_name, 'owner' => { 'login' => stack_a.repository.owner } }
  }

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # only to simulate a valid signature for repo X's own webhook

  post :create, body: payload.to_json, as: :json

  assert_equal 1, commit_a.reload.statuses.count, "expected the named repository's commit to get a status"
  assert_equal 0, commit_b.reload.statuses.count, "commit in unrelated stack_b must NOT receive a status"
  assert_equal 0, commit_c.reload.statuses.count, "commit in unrelated stack_c must NOT receive a status"
end
```

Binding to assert: `stacks_that_received_status == { stack_a }` (the single stack named in `payload['repository']['full_name']`), not `Commit.where(sha: shared_sha).map(&:stack) == { stack_a, stack_b, stack_c }`. With the current implementation, `commit_b` and `commit_c` will also gain a `Status` row, failing the assertions and demonstrating the cross-tenant fan-out.
