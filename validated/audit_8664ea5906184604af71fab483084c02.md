## Analysis

The reported bug class is: an unprivileged recipient of a payment can deliberately force a revert during payment settlement, so that the actor coordinating the transaction (a "keeper"/batch-processor) loses their work and possibly rewards, purely because the attacker made their own receiving contract always fail.

The ocore analog exists in the Autonomous Agent (AA) secondary-trigger cascade. When an AA response sends a payment output to an address that is itself an AA, that AA is automatically invoked as a "secondary trigger" from `handleSecondaryTriggers()`. If that secondary AA bounces (any error at all — and secondary triggers are exempt from the bounce-fee sufficiency check), the *entire* chain of responses, including any state changes and payments to unrelated, honest recipients, is unconditionally reverted through `revert()`. Because secondary triggers skip the "enough balance to cover bounce fees" requirement, and `bounce()` for a secondary trigger is a no-op that just propagates the error upward, a malicious AA needs no funds and no special conditions to always fail: [4](#0-3) 

### Title
Malicious AA at a payout address can force full revert of a batch-paying AA, freezing pooled funds for all participants - (File: aa_composer.js)

### Summary
Any AA that pays out to a set of recipient addresses in a single response (e.g. a staking/reward pool, order-matching AA, batch distributor) can be permanently denied service by a single participant who registers a malicious AA at their payout address. That AA's `handleTrigger` logic can unconditionally `bounce()`, and because secondary triggers propagate their bounce upward via `handleSecondaryTriggers` → `revert()`, the whole primary response — including payments and state updates intended for all other, honest recipients — is rolled back every time.

### Finding Description
When `sendUnit()` produces a response unit with payment outputs, `handleSecondaryTriggers()` looks up whether any output address is itself an AA and, if so, recursively invokes `handleTrigger()` on it as a secondary trigger. Secondary triggers are explicitly exempted from the requirement to have enough balance to cover bounce fees, so an attacker's AA can simply `bounce()` unconditionally with zero cost. `bounce()` for a secondary trigger does nothing but signal failure to the caller; that failure is then treated as a hard error by `handleSecondaryTriggers`, which calls `revert()` at the primary level, rolling back the entire response chain to the savepoint taken before processing began — undoing all payments and state changes accumulated so far, not just the failing leg.

This means the correctness/availability of a shared, multi-recipient AA operation depends on the goodwill of every address it happens to pay in that operation. Any one of those addresses can be a pre-deployed, attacker-controlled AA that always bounces, and there is no mechanism in the AA execution engine to isolate or skip a misbehaving payee — the failure is global by design of the atomic all-or-nothing execution model.

### Impact Explanation
This is exploitable to freeze AA funds and deny service:
- A pooled/shared AA (staking rewards distributor, DEX/order-matching AA, revenue-sharing AA, DAO payout AA) that iterates over a set of registered participant addresses and pays them in one response unit can be blocked indefinitely if even one participant registers a malicious bouncing AA as their payout address.
- Because AA state generally isn't advanced when the response reverts, the same set of pending obligations (including the malicious entry) is re-processed on every subsequent trigger, so the denial of service can be persistent until AA-level logic (if any) is redesigned/upgraded to filter out the bad actor — something the protocol itself does not provide.
- This causes concrete "AA fund loss or freezing": legitimate participants' expected payouts/state updates are perpetually reverted, with funds parked in the AA unable to be distributed.

### Likelihood Explanation
Deploying an AA with a `bounce()`-only body is trivial and cheap, and does not require any privileged access — any user can register their payout/participant address as such an AA before interacting with the target multi-recipient AA. Any existing or future oscript AA design that batches payments to multiple externally-influenced addresses in a single response is vulnerable unless it explicitly guards against this by isolating recipients into separate triggers/units.

### Recommendation
- Document (and ideally enforce at the language/engine level) that AA authors should never pay multiple independently-controlled parties out of a single response when one bad actor should not be able to block all others; instead each recipient's payment should be issued as an independent, separately-reversible unit/trigger.
- Consider adding an oscript primitive/pattern that lets an AA "try" a secondary trigger and continue on bounce (isolating failures) rather than always cascading to a full revert, so a single malicious payee cannot hold hostage the processing of unrelated, honest recipients in the same batch.

### Proof of Concept
1. Deploy AA `M` with a definition whose `messages`/`init` always calls `bounce("grief")`, e.g.:
```
{
  messages: [
    { app: 'state', state: `{ bounce("grief"); }` }
  ]
}
```
2. Deploy or use an existing pooled-payout AA `P` (e.g. a rewards/order-matching AA) that, in one trigger response, sends payment outputs to a list of registered participant addresses.
3. Register `M`'s address as one of `P`'s participants (via whatever registration mechanism `P` exposes).
4. Trigger `P`'s payout logic. `P`'s response includes an output to `M`. `handleSecondaryTriggers()` invokes `M` as a secondary trigger; `M` bounces; `handleSecondaryTriggers`'s `async.eachSeries` callback receives an error and, since the top-level trigger is primary, calls `revert()`, unwinding all of `P`'s state changes and payments — including those intended for the other, honest participants — every single time `P` is triggered.
