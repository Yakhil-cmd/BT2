## Analysis: `WebhooksController` signature-org / target-repo binding mismatch

This is a valid analog. The root cause maps to the same class of bug as the report (an ordering/binding assumption silently violated by attacker-controlled interleaving of independently-derived values), but here it's a signature-scope mismatch rather than a threading race: the field used to pick which GitHub App secret authenticates a webhook is different from — and independently attacker-controlled relative to — the field used to determine which repository/stack the webhook payload actually acts on.

### Finding Description

`WebhooksController#verify_signature` selects which per-organization webhook secret to verify against using `repository_owner`, which is read directly out of the *unauthenticated* JSON body before the signature is checked: `params.dig('repository', 'owner', 'login')`. [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config and, for that org's `GitHubApp`, `verify_webhook_signature` returns `true` unconditionally if that organization has no `webhook_secret` configured: [3](#0-2) [4](#0-3) 

The multi-organization configuration schema is explicitly documented/supported, and the example fixture shows one organization configured with `webhook_secret: # nil` while another has a secret set: [5](#0-4) [6](#0-5) 

Once the signature check passes (or is skipped because the selected org has no secret), the event is dispatched to handlers. Crucially, none of the handlers use `repository.owner.login` (the field used for authentication) to resolve the target repository/stack — they instead use the completely independent `repository.full_name` field: [7](#0-6) [8](#0-7) [9](#0-8) 

So the equality that should hold but doesn't:

`organization authenticated via repository.owner.login` **≠** `organization/repository actually written via repository.full_name`

An attacker can submit a webhook body where `repository.owner.login` names an organization configured in Shipit with no `webhook_secret` (or one the attacker otherwise knows), while `repository.full_name` names a *different*, victim organization's repository that Shipit tracks with its own strong secret. Signature verification succeeds (or is skipped) using the harmless org's identity, but the payload is processed against the victim org's `Stack`/`Commit` records.

### Impact Explanation

Via `StatusHandler`, an attacker can forge a `commit_status` (`state: success`) for any tracked commit sha, satisfying CI-gating logic used by deploys and the merge queue (`Commit#deployable?`, `MergeRequest#all_status_checks_passed?`), enabling an **unauthorized deploy** or **unauthorized merge** — this matches the Critical impact bar. Via `PushHandler`, an attacker can also trigger `stack.sync_github` for a stack under a different org/repo than the one whose secret was validated. This is a genuine authentication-bypass path with no session, `ApiClient` token, or GitHub App private key required — only knowledge that Shipit is configured for at least two GitHub organizations and that one has no (or a leaked) `webhook_secret`.

### Likelihood Explanation

Requires the deployment to use the multi-organization `github:` config with at least one organization lacking `webhook_secret` — a state the codebase itself documents and ships as an example/test fixture, i.e., not an exotic misconfiguration. No credentials or session are needed; the webhook endpoint is public and unauthenticated by design (`skip_before_action :verify_authenticity_token`). [10](#0-9) 

### Recommendation

Derive the organization used for signature verification from the same field(s) used by handlers to resolve the target repository (`repository.full_name`'s owner segment, or the resolved `Stack`/`Repository`'s configured organization) rather than trusting `repository.owner.login` independently. Alternatively, after verifying the signature, re-validate that the org whose secret matched is the same org that owns the resolved `Repository`/`Stack` before processing, and refuse to treat a missing `webhook_secret` on any organization as an implicit bypass for events targeting a different organization's repositories.

### Proof of Concept

1. Shipit configured with two organizations: `harmless-org` (no `webhook_secret`) and `victim-org` (strong `webhook_secret`), each with tracked stacks.
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-org tracked commit sha>",
  "state": "success",
  "repository": { "owner": { "login": "harmless-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "harmless-org")` → `verify_webhook_signature` returns `true` (no secret configured) regardless of the (absent/garbage) `X-Hub-Signature`.
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` scoped to whatever stack that sha belongs to (`victim-org/victim-repo`) and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status that satisfies deploy/merge CI gating for the victim stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```
