### Title
Cross-tenant commit-status forgery via webhook signature/repository binding mismatch enabling unauthorized merges - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an incoming webhook against the GitHub App/`webhook_secret` belonging to the organization named in `repository.owner.login` (or `organization.login`), but `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks that the commit SHA in the payload actually belongs to a repository owned by that authenticated organization. It writes a `Status` for `Commit.where(sha: params.sha)` globally, across the entire Shipit instance.

### Finding Description
The webhook signature check picks the verifying secret solely from the payload's declared owner: [1](#0-0) [2](#0-1) 

For most events, the base `Handler` class does correctly scope subsequent processing to the repository named in the payload: [3](#0-2) 

However `StatusHandler`, which handles GitHub's `status` event, does not use this `stacks`/`repository_name` scoping at all. It looks up `Commit` records purely by SHA, across every stack/repository/organization ever synced into this Shipit instance: [4](#0-3) 

Shipit explicitly supports multiple, independently-managed GitHub Apps/organizations sharing a single Shipit deployment (`config/secrets.yml` → `github: { orgA: {...}, orgB: {...} }`), each with its own `webhook_secret` that the *organization's own admins* choose when they create their GitHub App: [5](#0-4) 

**Binding broken:** `organization authenticated by verify_signature` (OrgA) `!=` `repository/commit actually written by the handler` (any repo/commit in OrgB, OrgC, …). Because `StatusHandler` performs a global, unscoped `Commit.where(sha: ...)` lookup, an admin of any tenant organization configured in this Shipit instance — who legitimately knows only their *own* org's `webhook_secret` — can forge a valid `X-Hub-Signature` for a `status` event whose payload names a commit SHA belonging to a *different* organization's stack, and Shipit will accept and record that status as if it came from GitHub for that commit.

### Impact Explanation
Commit statuses control the merge queue's automatic merging logic: [6](#0-5) 
and are consumed unconditionally by `ProcessMergeRequestsJob`, which merges pending pull requests once `all_status_checks_passed?` is true: [7](#0-6) 

By forging a `success` status for `ci.require`/`merge.require` contexts on a target commit SHA in a victim organization's repository (SHAs of public commits/PRs are trivially observable), a tenant of the shared Shipit instance who has no access whatsoever to the victim's GitHub organization or repository can cause Shipit to treat a CI-failing or CI-pending pull request as green, triggering `MergeRequest#merge!` and an unauthorized merge into the victim's protected branch — matching the "unauthorized deploy, rollback, or merge" Critical/High impact criteria. The same unscoped write also lets the attacker poison CI status displayed for that commit (blocking deploys/merges is a bonus but the merge-bypass is the concrete crossed boundary).

### Likelihood Explanation
Requires only that the attacker administers (or has developer access to create/own a GitHub App for) any single organization already configured as a legitimate tenant in the shared Shipit instance — a normal, documented, unprivileged (relative to the victim org) configuration supported out of the box via "Using Multiple Github Applications." No access to the victim's GitHub App, private key, repository, or any Shipit session/API token is needed; only knowledge of the target commit SHA, which is public for public repositories and observable via the PR UI even for many private setups shared with collaborators.

### Recommendation
In `StatusHandler#process` (and any other handler that doesn't already do so), scope the commit lookup to the repository named in the payload via the inherited `stacks`/`repository_name` helpers (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or joining `Commit` through `Stack`→`Repository` matching `payload.dig('repository','full_name')`), so a status can only be attributed to commits that belong to a stack whose repository matches the authenticated organization/repository. More broadly, `verify_signature` should assert that the organization used to resolve the webhook secret matches the organization of every repository-scoped resource the handler subsequently mutates, not just be used to pick a secret.

### Proof of Concept
1. Configure Shipit (per docs/setup.md's "Using Multiple Github Applications") with two tenants: `attacker-org` (attacker is admin, knows its `webhook_secret`) and `victim-org` (unrelated, victim-controlled repo/stack tracked by the same Shipit instance).
2. Attacker observes/knows a commit SHA `S` on an open pull request in `victim-org/some-repo` that is required by `victim-org`'s `shipit.yml` (`merge.require: ['ci/checks']`) but is currently failing/pending.
3. Attacker crafts a GitHub `status` webhook payload:
   ```json
   { "sha": "S", "state": "success", "context": "ci/checks",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy" } }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and POSTs to `/webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and validates successfully (attacker's own secret).
6. `StatusHandler#process` runs `Commit.where(sha: 'S')` — matching the real commit `S` in `victim-org`'s stack (no repository scoping) — and creates a `success` status on it via `commit.create_status_from_github!`.
7. `ProcessMergeRequestsJob` next sees `all_status_checks_passed?` return `true` for the victim's pull request and calls `merge_request.merge!`, merging the pull request into `victim-org/some-repo` despite failing/missing real CI.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    def any_status_checks_missing?
      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).missing?
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
