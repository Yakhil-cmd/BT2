### Title
Asset definer can retroactively freeze coins already transferred to a spender by rotating the attestor list - (File: [validation.js](validation.js))

### Summary
For assets with `spender_attested: true`, ocore only checks that the *sender* of a payment is currently on the asset's attestor list at spend time — it never fixes that check to the time the coin was received. The definer (asset issuer) can unilaterally update the attestor list at any time via an `asset_attestors` message, and the check always uses only the *latest* stable attestor list. This lets an issuer sell/transfer an asset to a counterparty while they are attested, then drop that counterparty from the attestor list, permanently freezing the coins the counterparty already holds — mirroring the reported bug where a `receiver` blacklists itself/the payer's token to block `exercise()` and force the option to expire, taking the buyer's funds.

### Finding Description
`spender_attested` assets require that whoever spends (inputs) a coin of that asset is on the current attestor list, checked in `validatePaymentInputsAndOutputs`: [1](#0-0) 

The attestor list itself is edited by a single message, restricted only to the asset definer, with no history/versioning requirement and no protection for holders who received coins under an older list: [2](#0-1) 

When resolving which attestor list applies, `storage.readAsset`/`addAttestorsIfNecessary` always selects only the single *latest* stable `asset_attestors` unit for the asset, discarding history: [3](#0-2) 

Critically, the *output* (receiving) side of a payment for a `spender_attested` asset is never checked against the attestor list at receipt time — only address/amount/blinding sanity is enforced on outputs: [4](#0-3) 

So a definer can:
1. Define an asset with `spender_attested: true` and initially attest a counterparty address.
2. Receive/transfer value in exchange for the asset (e.g., in an escrow, ICO, or option-like AA such as the `option_contract.oscript`/`futures_contract.oscript` patterns, where a party sends bytes and receives asset tokens representing an obligation).
3. Once the counterparty holds the asset (already paid for it), publish a new `asset_attestors` unit that no longer includes the counterparty's address.
4. Any subsequent attempt by the counterparty to spend/redeem those coins is rejected with `"owner address is not attested"` in `validatePaymentInputsAndOutputs` (`validation.js:2506`), permanently freezing the funds — the counterparty can never move or redeem what they legitimately received, exactly as the receiver in the Sherlock report can permanently block `exercise()` by self-blacklisting.

This is structurally identical to the reported class of bug: a single privileged party (here, the asset definer, allowed per the analog rules as "asset issuer") controls a gate (attestor list / blacklist) that is checked at settlement time rather than at receipt time, letting them retroactively invalidate funds a counterparty already legitimately holds, with no recourse for the victim.

### Impact Explanation
Impact is a permanent freezing of counterparty funds under attacker (asset issuer) control, with no mechanism for the victim to reclaim or force resolution — matching "AA fund loss or freezing" and "asset transfer conditions" categories. Any protocol built on top of `spender_attested` assets (escrow/ICO/option-like AAs releasing an asset in exchange for value, as illustrated by the `ico_with_milestones.oscript`, `fundraising_proxy.oscript`, `option_contract.oscript` samples) is exposed: a malicious definer can accept payment, hand over the token, then de-attest the recipient, permanently trapping the recipient's asset balance while the definer keeps whatever was paid for it.

### Likelihood Explanation
Likelihood is high for any deployed `spender_attested` asset where the definer is (or later becomes) adversarial or compromised, since:
- No cost or cosigning is required to update the attestor list beyond the definer's own signature (`validateAttestorListUpdate`, `validation.js:2829-2848`).
- The check is purely "is the current holder in the *latest* list," with no grandfathering for coins received while previously attested.
- The bug does not require any p2p, hub, or infrastructure-level compromise — it is a pure single-unit posting by the definer, reachable by any unprivileged (from the protocol's perspective) issuer defining and later mutating their own asset.

### Recommendation
Bind the attestation check to the state of the attestor list at (or shortly after) the time the coin was received rather than always the current/latest list, e.g., record the attestor-list version each output was created under and validate spends against that snapshot, or require attestor-list changes to only apply prospectively to coins issued/transferred after the change becomes stable. Alternatively, expose this risk clearly at the `asset` definition validation stage so that `spender_attested` assets used in irreversible payment/escrow contexts document that the definer retains unilateral freeze power over already-received funds.

### Proof of Concept
1. Definer creates asset A with `spender_attested: true`, `issued_by_definer_only: true`, initial attestor list `[Definer, Alice]`.
2. Alice sends bytes to an AA/definer in exchange for asset A tokens (as in `test/samples/ico_with_milestones.oscript` or `option_contract.oscript` patterns); Alice now holds output(s) of asset A, valid because she is attested.
3. Definer posts a new `asset_attestors` message for asset A with list `[Definer]` only (validated only against `objUnit.authors[0].address !== objAsset.definer_address` — `validation.js:2841`).
4. `storage.readAsset` will now return only this latest attestor list for any future lookup (`storage.js:1917-1946`).
5. Alice attempts to spend her previously-received asset A output; `validatePaymentInputsAndOutputs` rejects it with `"owner address is not attested"` (`validation.js:2506`), regardless of when Alice originally received the coin.
6. Alice's asset A balance is now permanently unspendable/frozen, while the Definer retains the bytes Alice paid — funds are lost with no recovery path, analogous to the reported receiver-blacklist-forces-expiry issue.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
