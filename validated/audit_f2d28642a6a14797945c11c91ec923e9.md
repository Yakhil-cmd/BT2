### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` allows cross-repository status forgery - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone, with no scoping to the repository/organization that authenticated the webhook, unlike every other handler (e.g. `PushHandler`) which scopes through `Handler#stacks`. Any GitHub organization/repository already onboarded to Shipit (with its own valid webhook signature) can send a `status` webhook naming an arbitrary victim commit `sha` and have it applied to that victim's `Commit`/`Stack`, even though that sha never belonged to their repository.

### Finding Description
The claimed binding is: `context string ownership == organization that can write it`. The actually broken binding is broader: `commit.sha ownership by stack/repository == organization whose webhook can write a Status for that sha`. This binding is broken because:

- `WebhooksController#verify_signature` selects the `GithubApp` to check the HMAC against using `repository_owner`, itself read straight from the attacker-controlled `payload.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . This only proves the payload was signed by *some* org/app onboarded to Shipit — not that the referenced `sha`/repo belongs to that org.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository/stack filter at all [3](#0-2) , whereas the base `Handler` class provides a `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) specifically to scope handlers to the authenticated repository [4](#0-3) , and `PushHandler` correctly uses it (`stacks.not_archived.where(branch:)`) [5](#0-4) .
- `Commit#create_status_from_github!` → `Status.replicate_from_github!` then creates a `Status` row scoped to the *victim's* `stack_id` (`statuses` is `commit.statuses`, i.e. victim commit's association) [6](#0-5) [7](#0-6) .
- Note the question's specific "context-keyed upsert" premise is inaccurate: `replicate_from_github!` is `find_or_create_by!` keyed on `stack_id, state, description, target_url, context, created_at` together, not on `context` alone, so it does not literally rewrite the existing failing row in place. However, since `Commit#statuses` is ordered `created_at: :desc` [8](#0-7)  and `Status::Group` computes visible/significant statuses via `statuses.to_a.uniq(&:context)` (first-per-context in that order) [9](#0-8) , an attacker-forged `Status` row with the same `context` and a `created_at` at or after the real CI failure's timestamp becomes the commit's *effective* status for that context, superseding the real failing row for `Commit#state`/`deployable?` purposes without needing an in-place DB update.
- Attack: attacker owns/controls any GitHub org/repo already configured in Shipit (or one whose `webhook_secret` is unset, since `GithubApp#verify_webhook_signature` returns `true` unconditionally when no secret is configured) [10](#0-9) . They send `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own org, `repository.owner.login` = their own org (so signature check passes), and `sha` set to the victim commit's known/public sha (shared history is common via forks or shared upstream repos), `context: 'ci/travis'`, `state: 'success'`. `StatusHandler#process` finds the matching `Commit` row(s) system-wide regardless of stack, and writes a superseding `success` `Status` for the victim's stack/commit.
- None of the existing guards catch this: `verify_signature` only authenticates *a* sender, not that the sender owns the referenced sha/repo; `drop_unhandled_event`/`ExplicitParameters` schema only validate shape (`sha`, `state`, `context` as strings) [11](#0-10) ; there is no `require_permission!`/`stacks` scoping check in this handler at all.

### Impact Explanation
An attacker who controls any onboarded GitHub organization/repo (or an org with no `webhook_secret` configured) can inject a fabricated successful CI status onto a commit belonging to a completely different, unrelated stack/repository, without needing any Shipit credentials. Since `Commit#deployable?`/`#state` are derived from the (forged) most-recent status per context, this can flip a victim's commit from non-deployable (real CI failure) to deployable, enabling an unauthorized deploy/merge — Critical impact ("a payload for one repository mutating another's stack/commit," "an unauthorized deploy... or merge"). This is repeatable against any commit sha the attacker can learn (shas are public/guessable via forks, PRs, or shared upstream history) and is not limited to a single victim stack.

### Likelihood Explanation
Preconditions: the attacker must control (or create) at least one GitHub organization/repository already registered in Shipit with a `GithubHook`/`GithubApp` config — either their own onboarded org (many self-service Shipit deployments let any team onboard a repo) or one with no `webhook_secret` set. No Shipit session, API token, or GitHub App private key is required. The attacker needs to know the victim's commit sha, which is generally public (GitHub commit shas are not secret; shared history via forks is common). Cost is a single crafted HTTP POST; fully repeatable and scriptable across arbitrary victim shas.

### Recommendation
Scope `StatusHandler#process` (and any handler resolving `Commit`s by `sha` alone) through the `Handler#stacks` helper, e.g. filter `Commit.where(sha: params.sha)` down to commits whose `stack` is in `stacks` (derived from `payload.dig('repository','full_name')`), mirroring `PushHandler`. Reject/no-op when the sha does not belong to a stack tied to the authenticated repository.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, but this belongs in a real test file, not merely conceptual):
1. Create two stacks/repos in fixtures: `victim_stack` (repo `victim/app`) with a commit `shared_sha` that has an existing `Status` with `context: 'ci/travis', state: 'failure'`; `attacker_stack` (repo `attacker/app`), with its own `GithubHook`/webhook secret, containing a commit with the same `shared_sha` (simulating shared history/fork).
2. Assert pre-condition: `victim_commit.state == 'failure'` and `victim_commit.deployable? == false`.
3. POST `/webhooks` with `X-Github-Event: status`, a signature valid for `attacker/app`'s configured secret, body `{ sha: shared_sha, state: 'success', context: 'ci/travis', repository: { full_name: 'attacker/app', owner: { login: 'attacker' } } }`.
4. Assert the forged webhook is accepted (`response :ok`) and that `victim_commit.reload.state == 'success'` (or that the newest `context: 'ci/travis'` `Status` on `victim_commit` is now `success`), and `victim_commit.deployable? == true` — demonstrating the cross-repository write despite the webhook never being scoped/authenticated for `victim/app`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
