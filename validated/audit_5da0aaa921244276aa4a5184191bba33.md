### Title
Unchecked cache access on AA primary trigger unit causes node crash (oops) when unit is not in `assocStableUnits` - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `handleTrigger()` unconditionally dereferences `storage.assocStableUnits[trigger.unit].count_aa_responses` for primary (non-secondary) AA triggers without first checking that the entry exists in the cache [1](#0-0) . Elsewhere in the very same file, the authors explicitly guard against this same cache miss and `throw` a descriptive error instead of letting an unguarded property access blow up [2](#0-1) . This mirrors the CVE-2025-38514 bug class: a lazily-populated, cache-like structure is assumed to exist by a codepath that is reachable from unprivileged input, and when it doesn't (because population is conditional), the process throws an unhandled `TypeError`.

### Finding Description
`storage.readUnitProps()` only inserts a unit's properties into `storage.assocStableUnits` when the unit's `sequence` is `'good'`: "we don't cache final-bads as they can be voided later" [3](#0-2) . This means any unit with `sequence` of `'final-bad'` or `'temp-bad'` is deliberately excluded from `assocStableUnits`.

When an AA-trigger-carrying unit is processed via `handlePrimaryAATrigger()`, `handleTrigger()` is eventually called with `bSecondary=false`. Inside `handleTrigger`, for a real (non-air, non-genesis-dry-run) primary trigger, the code does:
```
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && storage.assocStableUnits[trigger.unit].count_aa_responses && mci >= constants.pemCurvesFixMci)
    return bounce('a second primary trigger from the same unit is not allowed');
``` [1](#0-0) 
There is no `if (!storage.assocStableUnits[trigger.unit]) ...` guard here, unlike the parallel lookup performed a few hundred lines earlier in `handlePrimaryAATrigger()`, which explicitly checks for and throws on a missing cache entry:
```
let objUnitProps = storage.assocStableUnits[unit];
if (!objUnitProps)
    throw Error(`handlePrimaryAATrigger: unit ${unit} not found in cache`);
``` [2](#0-1) 

If `trigger.unit` (the unit that pays into the AA and is thus the AA trigger, fully attacker-controlled content posted by any unprivileged unit author) ends up with `sequence !== 'good'` by the time it is treated as stable and processed as an AA primary trigger — e.g., it is `final-bad` due to a conflicting/double-spend situation that resolves after the trigger row was queued in `aa_triggers` — then `storage.assocStableUnits[trigger.unit]` is `undefined`, and `.count_aa_responses` on `undefined` throws a `TypeError`. This crashes the node process handling AA triggers (an unhandled exception in `handleAATriggers`/`handlePrimaryAATrigger` is not caught anywhere in this chain), the exact "oops" pattern of the kernel CVE: code assumes an internal lazily/conditionally-populated structure exists and dereferences it directly, causing an unhandled crash instead of a controlled rejection.

### Impact Explanation
A node crash in the AA-trigger-processing pipeline halts advancement of AA responses network-wide for that node and, if this is systemic (any hub/full node that processes AA triggers hits the same code on the same unit), can prevent the network from confirming/handling subsequent AA-related units, matching the "network unable to confirm new units" / node-crash impact class accepted by the validation rules. Because the vulnerable field (`trigger.unit`) is derived directly from a unit an unprivileged author posted (an ordinary payment unit that happens to send funds to an AA address), this is reachable purely from posting units — no special privilege required.

### Likelihood Explanation
Exploitability depends on being able to get a unit whose sequence resolves to `final-bad`/`temp-bad` to nonetheless be dispatched through the AA-trigger pipeline with `bSecondary=false` while its properties are absent from `assocStableUnits`. This requires crafting a double-spend/conflicting-unit scenario timed against AA-trigger processing. I was not able to fully verify, within the available context, whether `aa_triggers` rows for such bad-sequence units are pruned/cleared before `handleAATriggers()` picks them up, or whether writer.js filters out non-good-sequence units before inserting into `aa_triggers`. This is the main uncertainty in confirming end-to-end reachability; I could not locate and inspect the exact `aa_triggers` insertion/cleanup logic in `writer.js` within the remaining investigation budget.

### Recommendation
Add the same defensive guard used in `handlePrimaryAATrigger()` to the check in `handleTrigger()`:
```js
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir) {
    const objTriggerUnitProps = storage.assocStableUnits[trigger.unit];
    if (objTriggerUnitProps && objTriggerUnitProps.count_aa_responses && mci >= constants.pemCurvesFixMci)
        return bounce('a second primary trigger from the same unit is not allowed');
}
```
This converts a potential unhandled crash into a safe no-op/bounce path, consistent with how the rest of the codebase already treats this exact cache-miss scenario.

### Proof of Concept
Conceptual PoC (could not be executed/verified against a live network in this investigation):
1. Post a unit `U` that pays to an AA address, causing `U` to be recorded as an AA trigger in the `aa_triggers` table.
2. Before `U` is processed by `handleAATriggers()`, cause `U` to be marked `final-bad` (e.g., via a conflicting double-spend that resolves in favor of a competing unit), so that `storage.readUnitProps()` never inserts `U` into `assocStableUnits` (per the `sequence === 'good'` gate).
3. When `handleAATriggers()` later dequeues the trigger row for `U` and calls `handlePrimaryAATrigger()` → `handleTrigger()`, the line `storage.assocStableUnits[trigger.unit].count_aa_responses` throws `TypeError: Cannot read properties of undefined`, crashing the node's AA processing.
