### Title
Webhook signature verification is keyed off `repository.owner.login`, while the write target is resolved from the independent `repository.full_name` field, letting an attacker satisfy verification against any organization with no `webhook_secret` and still mutate another organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) is used to authenticate an inbound webhook based on `repository.owner.login` (or `organization.login`) read straight out of the unverified request body. Once "verified", the very same body is handed to event handlers, which instead resolve the actual `Repository`/`Stack` to act on using the unrelated `repository.full_name` field. These two fields are not required to reference the same organization before the signature check runs.

### Finding Description
`WebhooksController#verify_signature` picks the authenticating organization from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GitHubApp` for that org, and `GitHubApp#verify_webhook_signature` explicitly treats a blank `webhook_secret` as "always verified": [3](#0-2) 

Shipit supports multiple configured GitHub organizations simultaneously (`github_organizations`, `github_app_config`), and it is a documented configuration state for an organization to have no `webhook_secret` set: [4](#0-3) 

After `verify_signature` passes, `create` re-parses the same raw body and dispatches it to event handlers unchanged: [5](#0-4) 

Handlers never look at `repository.owner.login` again - they resolve the repository/stack to write to purely from `repository.full_name`: [6](#0-5) [7](#0-6) 

This breaks the binding: `organization authenticated by verify_signature == organization whose repository is written by the handler`. An attacker can set `repository.owner.login` (or `organization.login`) to any GitHub organization configured on this Shipit instance with a blank `webhook_secret`, while setting `repository.full_name` to `victim-org/victim-repo` - a completely different, properly-secured organization's repository that is also tracked by the same Shipit instance. `verify_webhook_signature` returns `true` unconditionally for the blank-secret org (no valid `X-Hub-Signature` is even required), yet the dispatched handler acts on the victim repository's `Stack`/`Repository` records.

### Impact Explanation
Depending on the `X-Github-Event` chosen, this yields unauthenticated writes against a repository the attacker never authenticated for, e.g.:
- `push` → `PushHandler` calls `stack.sync_github(expected_head_sha:)` with an attacker-chosen SHA on the victim stack's tracked branch.
- `status` → forges a commit status (`success`) on an arbitrary commit, which feeds `Stack#branch_status`/`merge_status` and can make an unreviewed or CI-failing commit appear deployable, i.e. contributes to an unauthorized deploy/merge decision.
- `membership` → creates/removes `Team`/`Membership` records, escalating into `Shipit.github_teams`-based authorization.

Because verification is bypassed at the organization-selection layer, none of this requires a valid HMAC for the org actually being written to. This matches the High-impact class "escalation into `Shipit.github_teams` authorization" / "unauthenticated read/mutation of stack state," and via the `status` vector can contribute to an unauthorized deploy.

### Likelihood Explanation
Requires only that the Shipit instance has at least one configured GitHub organization with a blank `webhook_secret` (an explicitly supported, non-error configuration path in `GitHubApp#verify_webhook_signature` and shown as a valid example in the shipped secrets template) alongside at least one other tracked organization/repository. No repository write access, session, or API token is needed - only knowledge of the target `repository.full_name` and an HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Do not select the verifying organization from attacker-controlled payload fields independent of the field used to resolve the write target. Require `repository.owner.login` (or `organization.login`) used for signature-app-selection to match the owner segment of `repository.full_name` before dispatching to handlers, and treat a blank `webhook_secret` as "reject" rather than "always verified" in any multi-organization configuration (or require secrets to be mandatory once more than one organization is configured).

### Proof of Concept
1. Shipit instance configured with two orgs: `victim-org` (real `webhook_secret`) tracking `victim-org/victim-repo`, and `empty-secret-org` (no `webhook_secret` set).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "empty-secret-org" }
  }
}
```
No valid `X-Hub-Signature` header is supplied.
3. `verify_signature` computes `repository_owner = "empty-secret-org"`, fetches its `GitHubApp`, and `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank.
4. `create` dispatches to `PushHandler`, which resolves `repository_name = "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack - despite the request never being authenticated for `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
