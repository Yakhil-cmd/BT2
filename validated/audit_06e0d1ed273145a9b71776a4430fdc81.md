### Title
Optional `last_ball_unit` in `is_valid_signed_package` lets an AA-reachable signed package bypass stability/MC enforcement - (File: formula/evaluation.js)

### Summary
The CVE describes PostgreSQL accepting a weaker-than-configured protection level because an alternate connection path (direct TLS) skips the stability/consistency checks that the normal negotiated path enforces. The analogous pattern in `ocore` is the `is_valid_signed_package` oscript opcode, whose enforcement of "the signed package's context must be a stable point on the main chain" is entirely conditional on the attacker-supplied package containing a `last_ball_unit` field. Omitting it routes verification through a materially weaker path.

### Finding Description
`is_valid_signed_package` is evaluated in AA formulas [1](#0-0) . The `signedPackage` object comes from evaluating an oscript expression that is fully attacker-controlled data (e.g., derived from `trigger.data`), since any user can send a trigger to an AA that calls this opcode with data-feed–style input.

The stability check is gated behind an `if` on an optional field: [2](#0-1) 
If `last_ball_unit` is a string, the code verifies the referenced unit exists, is stable, has `main_chain_index <= mci`, and (post-fix) is actually on the main chain. If the attacker simply omits `last_ball_unit`, this entire block is skipped — no stability or main-chain-membership check occurs before the code falls through to `signed_message.validateSignedMessage(...)`.

Inside `validateSignedMessage`, the omission flips `bNetworkAware` to `false` [3](#0-2) , which routes definition resolution to the "no last_ball_unit of its own" branch: [4](#0-3) 
In this branch the address definition is *not* read from storage as of a historical, MC-stable checkpoint — it is taken verbatim from the attacker-supplied `objAuthor.definition`, and `last_ball_mci` is simply set to the *current* `mci` (post pemCurvesFix) rather than to any independently-verified stable point. `bNoReferences: !bNetworkAware` is also set to `true` [5](#0-4) , changing how definition evaluation treats state-referencing ops.

Back in the caller, the only remaining guard is `last_ball_mci === null || last_ball_mci > mci` [6](#0-5) , which trivially passes because `last_ball_mci` was just set to `mci` itself in the no-`last_ball_unit` branch. So the "network-aware" path (verify the address's on-chain definition as of a genuinely stable last-ball unit) and the "no-`last_ball_unit`" path (trust the caller-provided inline definition and current `mci` with no stability anchor) produce different, and differently strong, notions of "the signed package is valid as of a consistent point in the DAG" — exactly the enforcement-mismatch pattern in the CVE, where two paths (GSSAPI-negotiated vs. direct-TLS) are supposed to deliver equivalent protection but one silently provides less.

### Impact Explanation
An AA whose logic relies on `is_valid_signed_package` to authorize an action (e.g., "pay out only if signed_message X is validly signed by address Y as of a stable historical state") can be tricked by an unprivileged trigger sender into supplying a `signedPackage` without `last_ball_unit`. This lets the attacker present a self-declared inline `definition` for `evaluated_address` and a signature computed only against the currently supplied fields, without proving that this definition/address state was ever genuinely stable or anchored to the DAG at the time the AA expects. Depending on how the calling AA uses the result (funds release, permission checks, oracle-attestation gating), this can lead to AA fund loss or bypass of intended spending/authorization conditions — i.e., unauthorized spending of AA funds.

### Likelihood Explanation
Reachable directly from a standard AA trigger: any user can send a trigger whose `data` is passed into the AA formula and ultimately becomes the `signedPackage` argument of `is_valid_signed_package`. No special privileges, hub/peer position, or node compromise is required — only that a target AA's formula uses `is_valid_signed_package` on caller-influenced input, which is a documented, encouraged pattern for building signature-checking AAs.

### Recommendation
Require `last_ball_unit` to always be present and stability-checked before calling `validateSignedMessage` in `is_valid_signed_package`, or otherwise ensure the no-`last_ball_unit` branch in `signed_message.js` cannot be reached from AA-controlled, untrusted-origin packages — e.g., reject signed packages lacking `last_ball_unit` when invoked from `is_valid_signed_package`, so both code paths enforce equivalent (MC-stable) anchoring semantics.

### Proof of Concept
1. Define an AA whose response formula includes something like:
```
$pkg = {
  signed_message: "authorize",
  authors: [{
     address: $addr,
     definition: $attacker_definition,
     authentifiers: {r: $sig}
  }]
};
$result = is_valid_signed_package($pkg, $addr);
```
where `$addr`, `$attacker_definition`, and `$sig` are derived from trigger `data` supplied by the caller.
2. An attacker crafts a trigger with `data.pkg` omitting `last_ball_unit`, and a self-consistent `definition`/`authentifiers` pair whose hash equals `$addr` (a freshly-chosen address the attacker controls, as shown in the existing test `test/formula.test.js` patterns using `objectHash.getChash160(maliciousDefinition)` for a "freshAddr").
3. Because `signedPackage.last_ball_unit` is absent, the block at `formula/evaluation.js:1684-1692` is skipped, and `validateSignedMessage` validates using the attacker-provided inline definition with `last_ball_mci = mci`, returning `true` without ever confirming this address/definition was stable on the DAG.
4. If the AA treats `$result === true` as authorization (e.g., to release funds to `$addr`), the attacker obtains unauthorized fund release using a self-manufactured "signed package" that was never anchored to genuine DAG history.
