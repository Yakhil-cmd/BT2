## Analysis

The Sherlock report's root cause is: a `deposit()` function trusts the caller-supplied `amount` as the actual value received and credits internal accounting with that value, instead of measuring the real balance delta — a problem for fee-on-transfer/deflationary ERC20 tokens.

Polkadot SDK has a directly analogous, production-wired component: the **ERC20 Asset Transactor** (`cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`), introduced to let XCM interoperate with arbitrary ERC20 contracts deployed via `pallet-revive`, and it is actually enabled in `AssetHubWestend`'s `AssetTransactors` tuple. ### Title
XCM `ERC20Transactor` credits/moves the requested `amount` instead of the actual transferred balance, breaking accounting for fee-on-transfer/deflationary ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke the standard ERC20 `transfer(to, value)` interface and only inspect the boolean success return value, never the actual balance change of the sender/receiver. `AssetsInHolding` is then credited with the full requested `amount`, not the amount actually received. This mirrors the reported bug exactly, but at the XCM/checking-account layer instead of a Solidity `deposit()`.

### Finding Description
`withdraw_asset_with_surplus` transfers `amount` of an ERC20 token from the user (`who`) to the shared `TransfersCheckingAccount`, then — regardless of how much the checking account's balance actually increased — mints an `AssetsInHolding` credit for the full requested `amount`: [2](#0-1) 

`deposit_asset_with_surplus` mirrors this on the way out: it transfers `amount` from the checking account to the beneficiary and only checks the boolean `transfer` return value: [3](#0-2) 

Any user can permissionlessly deploy an arbitrary contract via `pallet-revive` on Asset Hub and reference it in XCM using an `AccountKey20` location — no privileged role is required, since `ERC20Matcher` matches any such location. [4](#0-3) 

If that contract implements a standard "fee-on-transfer"/deflationary pattern (a nonzero percentage of every `transfer` is deducted, e.g. burned or routed to a fee collector, while still returning `true`), the `TransfersCheckingAccount`'s real on-chain balance after a withdraw increases by less than `amount`. The `Erc20Credit(amount)` object created in `AssetsInHolding` does not reflect this: the XCM holding register believes it possesses `amount`, while the checking account actually only holds `amount * (1 - fee)`.

Because the checking account is a **shared pooled account** used for every user's ERC20 bridging operation (via `ERC20TransfersCheckingAccount`, a fixed `PalletId`-derived account), this discrepancy accumulates across all users of that asset, not just the attacker: [5](#0-4) 

Each subsequent `deposit_asset_with_surplus` call also loses value the same way (the outbound `transfer` from the checking account is itself subject to the same fee, and only the boolean success is checked, not the amount the beneficiary actually received). The net effect is that the checking account's real ERC20 balance depletes faster than the sum of credits recorded/expected across users' XCM programs — an insolvency of the shared "vault" that eventually causes deposit calls for later users to revert (insufficient real balance) or silently deliver less than the credited/expected amount to beneficiaries, while the failure is invisible to the XCM executor's accounting.

### Impact Explanation
This breaks the invariant that XCM holding-register credits for a checking-account-backed asset must be fully backed 1:1 by the checking account's real token balance. For a legitimate fee-on-transfer ERC20 registered as an XCM asset (a token property the runtime does not vet or reject), the shared checking account becomes progressively under-collateralized. Consequences range from Medium (assets trapped / failed deposits for later users, beneficiaries silently receiving less than the credited amount) up to loss-of-funds for whichever user's withdrawal ends up starved once the checking account's real balance is exhausted — a class matching the reported bug (missing balance-delta verification on transfer-in/out of a shared accounting pool).

### Likelihood Explanation
Reachability requires only: (1) permissionless contract deployment via `pallet-revive` on Asset Hub, and (2) registering/using that contract's `AccountKey20` location in an ordinary XCM program (e.g. via `pallet_xcm::execute` or `transfer_assets`) that reaches `ERC20Transactor` inside `AssetTransactors`. No governance action, no validator/collator collusion, and no privileged origin is needed — deflationary/fee-taking ERC20 contract semantics are a real-world, common token pattern (as cited in the original report), making this readily triggerable by any user who deploys or references such a token.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the actual balance delta of the relevant account (checking account or beneficiary) before and after the `transferCall`, rather than trusting the boolean return value together with the requested `amount`. Credit `AssetsInHolding` with the actually-observed delta, and use the actually-observed delta (not the nominal `amount`) when moving funds out of the checking account.

### Proof of Concept
No test was executed against a live or emulated network; this is a static-analysis-based conceptual reproduction plan, not an execution result:
1. On an `AssetHubWestend`-like test runtime with `pallet-revive` enabled, deploy a minimal ERC20 fixture contract whose `transfer(to, value)` deducts, e.g., a 10% fee (routed to a burn/fee address) but still returns `true`.
2. Fund a test account with this token; build an XCM program executed via `PolkadotXcm::execute` containing `WithdrawAsset` for `{parents:0, interior: AccountKey20{key: <contract address>}}` with `amount = X`, followed by `DepositAsset` to a beneficiary.
3. Assert, using `bare_call`/contract state inspection, that `ERC20TransfersCheckingAccount`'s real token balance after the withdraw step is `X * 0.9` (fee deducted), while `AssetsInHolding`/the XCM executor treats the held amount as the full `X` (per `Erc20Credit(amount)` at `erc20_transactor.rs:198-201`).
4. Repeat the withdraw/deposit cycle across multiple accounts to show the checking account's real balance falls below the cumulative amount recorded as "credited," eventually causing a `deposit_asset_with_surplus` call to revert (`ERC20 contract transfer failed`) for a legitimate, later user despite their XCM program appearing valid and previously accepted.

This PoC has not been run; it documents the exact reachable path and the missing check (`is_success` boolean instead of balance-delta verification) that would need to be exercised to confirm impact numerically.
