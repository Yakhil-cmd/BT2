### Title
Route-controlled code can attach arbitrary user transfers to a signed controller authorization - (File: contracts/controller/src/strategies/swap.rs) [1](#0-0) 

### Summary
A malicious swap route can execute attacker-controlled code beneath a user-signed `swap_collateral` invocation and invoke an unrelated `token.transfer(victim, attacker, amount)` using the victim’s root authorization. [2](#0-1) 

### Finding Description
`swap_collateral` accepts caller-supplied opaque `swap` bytes and passes them to the configured router without decoding or constraining which contracts the route invokes. [3](#0-2) 

The controller authenticates the caller and requires ownership or delegation over the target account, so the operation executes under the account owner’s authorization. [4](#0-3) 

Before routing, the controller authorizes only its own exact `token_in.transfer(controller, router, amount_in)` call, but this does not prevent route-selected contracts from requesting additional transfers from the user beneath the user’s signed root invocation. [1](#0-0) 

A regression test demonstrates that a route-selected rogue pool can call `token.transfer(Alice, attacker, balance)` for a token unrelated to the lending markets. [5](#0-4) 

Simulation records that transfer as a child of Alice’s `swap_collateral` authorization, and enforcement accepts it when the poisoned simulated tree is signed. [6](#0-5) 

### Impact Explanation
The attacker can steal arbitrary user-held tokens whose token contracts authenticate transfers with `from.require_auth()` and whose transfer is included in the simulated authorization tree. [7](#0-6) 

The loss is not limited to the routed collateral, measured router output, protocol balance, or final account health checks. [8](#0-7) 

### Likelihood Explanation
Any unprivileged account owner or delegate can invoke `swap_collateral` with attacker-supplied route bytes, and the protocol intentionally allows routes through venue contracts rather than enforcing a controller-side venue allowlist. [9](#0-8) 

The exploit depends on convincing the victim to sign a simulated authorization tree containing an unexpected transfer, which is realistic when routes are generated by a quote provider, interface, or aggregator and users do not independently decode every authorization child. [10](#0-9) 

The test demonstrates a fair-looking swap that still drains Alice’s entire unrelated wallet-token balance when the poisoned tree is signed. [11](#0-10) 

### Recommendation
Replace opaque route execution beneath user authorization with a decoded route format that can only invoke governance-approved venue adapters and validated token/pool addresses. [12](#0-11) 

Until route execution is constrained, clients and wallet integrations must simulate strategy calls, reject any authorization child other than the expected protocol transfer, and treat an unexpected `transfer(victim, recipient, amount)` as malicious. [10](#0-9) 

### Proof of Concept
The repository test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` implements the attack. [13](#0-12) 

1. Alice owns an account holding USDC collateral and an unrelated wallet token balance. [14](#0-13) 
2. The malicious route names an attacker-deployed pool while still producing the expected ETH output. [15](#0-14) 
3. Alice calls `swap_collateral(caller=Alice, account_id, current=USDC, amount=5_000_USDC, new=ETH, swap=malicious_route)`. [16](#0-15) 
4. The router invokes the route-selected pool, which executes `token.transfer(Alice, attacker, wallet_balance)`. [17](#0-16) 
5. Simulation attaches that unrelated transfer to Alice’s signed `swap_collateral` authorization. [18](#0-17) 
6. Signing that tree drains Alice’s wallet-token balance to the attacker while the collateral swap still completes. [19](#0-18)

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
