## Vulnerability Analysis

The Carapace bug class ("unbounded array iterated on every call, exhausting gas/CPU because no attacker input is size-limited") maps to an analogous pattern in ocore's data-feed lookup used by AA formula evaluation.

### Title
Unbounded iteration over all network-wide unstable units in `data_feed`/`in_data_feed` oscript evaluation causes AA-trigger DoS - (File: data_feeds.js)

### Summary
When an AA formula calls `data_feed[[...]]` or `in_data_feed[[...]]`, ocore looks up unstable (unconfirmed) data-feed values via `dataFeedExists()`/`readDataFeedValue()` in `data_feeds.js`. When called from AA context (`bAA`/`unstable_opts` truthy), these functions iterate over `storage.assocUnstableMessages` — the full, network-wide set of *all currently unstable units*, regardless of whether they are related to the requested oracle addresses — and run a nested `.forEach` over every message of every such unit before falling back to the indexed KV lookup.

### Finding Description
In `data_feeds.js`, both lookup entry points contain the same pattern: [1](#0-0) 

and [2](#0-1) 

`storage.assocUnstableMessages` is populated with the messages of **every** unit that is currently unstable anywhere in the DAG — there is no restriction limiting it to units authored by, or addressed to, the AA/oracle in question; the address filter (`_.intersection(arrAddresses, objUnit.author_addresses)`) is only applied *after* the loop has already touched every unstable unit and iterated its messages.

This code path is reached directly from AA formula evaluation whenever an AA uses the `data_feed` or `in_data_feed` oscript operators, which is extremely common in real AAs (oracle price feeds, etc.): [3](#0-2) [4](#0-3) 

Any unprivileged unit poster can post a `data_feed` message from any address — there is no gatekeeping requiring the poster to be a registered/trusted oracle, only feed-name/value length limits are enforced: [5](#0-4) 

Because an attacker fully controls how many units carrying `data_feed` messages they post, and controls parent selection to keep many of them parallel/unstable simultaneously (unstable units persist in `assocUnstableMessages` until MC stabilization advances past them), the size of the array iterated on every single `data_feed`/`in_data_feed` evaluation is effectively attacker-controlled and unbounded — exactly like Carapace's `activeProtectionIndexes` growing without limit and then being fully scanned inside `_accruePremiumAndExpireProtections`.

### Impact Explanation
AA trigger processing (`handleTrigger` in `aa_composer.js`) is executed synchronously as part of unit validation/writing on every full node when a unit that pays to an AA is included. If the attacker inflates `assocUnstableMessages` with a large number of parallel unstable units each carrying `data_feed` payloads, then every AA on the network that references `data_feed`/`in_data_feed` in its formula (a very common oscript pattern for price oracles, DeFi AAs, etc.) will incur an O(N) scan over all of these attacker-created messages on each trigger, for as long as those units remain unstable. Because this synchronous work happens on the node's single-threaded processing path for confirming new units, sufficiently large N can materially degrade or stall the node's ability to process/confirm subsequent units — an instance of "network unable to confirm new units."

### Likelihood Explanation
Likelihood is moderate-to-high: any address can post `data_feed` messages, no special role or authentication is required, and there is no unit-level restriction on the total number of concurrent unstable units carrying such messages. An attacker only needs to post many low-value units (each satisfying normal unit fees) that don't get quickly finalized (e.g., posted on parallel non-best-parent branches or in a burst faster than the MC advances) to inflate the array that every other AA in the ecosystem pays to scan.

### Recommendation
- Avoid the network-wide, unbounded scan of `storage.assocUnstableMessages`; instead maintain (or query) an index keyed by author address (or oracle address + feed_name) for unstable data feeds, mirroring the stable-storage KV index (`df\n<address>\n<feed_name>\n...`) so lookups are O(matching entries) rather than O(all unstable units in the DAG).
- Alternatively, cap the number of unstable units/messages scanned per call and/or cap how many concurrently-unstable `data_feed` messages a single address may have outstanding, forcing pruning/rejection once the cap is reached (analogous to introducing an upper bound on `activeProtectionIndexes` as recommended in the source report).

### Proof of Concept
1. Attacker crafts many units (U1..Un) each containing a single `data_feed` message (any feed_name/value), broadcasting them on parallel/non-conflicting parent chains so they remain simultaneously unstable for an extended period (i.e., MC finality lags behind because parents are chosen to avoid quick witnessed-level advancement, or simply broadcast in a burst faster than stabilization keeps up).
2. While U1..Un sit in `storage.assocUnstableMessages`, any AA on the network whose oscript uses `data_feed[[oracles=..., feed_name=...]]` or `in_data_feed[[...]]` is triggered by a normal payment (any unprivileged sender can trigger it).
3. `formula/evaluation.js`'s `data_feed`/`in_data_feed` handlers call into `dataFeeds.readDataFeedValue`/`dataFeeds.dataFeedExists` with `bAA=true`, which iterates the full `storage.assocUnstableMessages` map (size n, growing with attacker's unrelated units) and runs `.forEach` over each unit's messages before filtering by oracle address.
4. As `n` grows, every AA trigger evaluation that touches `data_feed`/`in_data_feed` slows proportionally, degrading the node's ability to process/confirm new units in a timely manner.
