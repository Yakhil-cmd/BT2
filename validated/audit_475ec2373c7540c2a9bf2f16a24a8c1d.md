## Finding

The `map`/`filter`/`reduce` (foreach-family) operator implementation in `formula/evaluation.js` accumulates results into a JS array/object (`retValue`) across a bounded number of loop iterations, but only validates the total size of that accumulator **after the entire loop has finished**, instead of checking it incrementally as the accumulator grows — unlike the sibling `array`/`dictionary` literal-construction code path, which explicitly re-checks size every 100 processed items, and unlike the `reduce` accumulator, which is checked after every single iteration. [1](#0-0) 

Compare this to the `array`/`dictionary` literal evaluation, which performs a periodic intermediate check (`if (count - prevCount >= 100) ... isTooBigObj(arrItems)`) in addition to a final check, explicitly to bound memory growth while the literal is being built: [2](#0-1) 

And the `reduce` branch, which checks `isTooBigObj` on the accumulator after every single call: [3](#0-2) 

For `map`, each loop iteration can call a local function or, notably, a **remote getter on another AA** via `callGetter`, whose return value (`r`) is `toJsType`-converted and deep-cloned into `retValue`: [4](#0-3) 

Each such per-element result can independently be as large as the object-size limit allowed elsewhere in the evaluator (`isTooBigObj`, bounded by `MAX_AA_STRING_LENGTH` / node/depth limits), and the loop can run over an array with up to the number of elements permitted by the outer array's own size limit. Because the aggregate `isTooBigObj(retValue)` check for `map` only fires once at the very end of `async.eachOfSeries` (and `filter` has no such check at all in its terminal callback): [5](#0-4) 

the interpreter can transiently allocate and clone a multiple of the per-value size limit before the fatal-error rejection is even evaluated — i.e., the “allowed memory allocation limit” is enforced only after the bulk of the over-sized allocation work has already happened, mirroring the ImageMagick class of bug where the memory-policy check for matrix-backed operations was missing/delayed until after the outsized allocation occurred.

## Impact

This is reachable purely through an AA's own oscript definition executing `map()` with a callback that calls a remote AA getter (or a local function returning large deep-cloned objects) over a moderately sized array. AA definitions and trigger evaluation execute deterministically on every full node validating the unit that triggers the AA, so a crafted AA (deployable by any AA author) combined with a single trigger unit (postable by any unprivileged sender) can force every validating node to build and clone very large intermediate JS objects before the `isTooBigObj` check finally rejects the bounce — this is a memory-exhaustion/DoS vector affecting node availability and potentially validation consensus across the network, which matches the “network unable to confirm new units” impact category.

## Likelihood / Caveats

I was not able to fully confirm, within the remaining tool budget, the exact numeric ceilings enforced elsewhere (`MAX_COMPLEXITY`/count_ops limits in `formula/validation.js` and `aa_validation.js`, and the precise value of `MAX_AA_STRING_LENGTH`/node-count limits in `constants.js`) that cap how large `count` (the iteration bound) and each per-element result can practically be. These limits exist and are enforced at validation time (`complexity += count * funcProps.complexity`, `count_ops += count * funcProps.count_ops`), so the actual achievable transient allocation size (and thus whether it rises to a High/Critical, practically exploitable DoS versus a bounded/limited one) depends on values I could not fully verify in this session. A background Devin session with full repo access should confirm the concrete `MAX_COMPLEXITY`/`MAX_OPS`/`MAX_AA_STRING_LENGTH` constants and compute the worst-case transient allocation (count × per-value size limit) to determine exploitability precisely, and should add an incremental `isTooBigObj` check inside the `map`/`filter` loop (matching the `reduce` accumulator check and the array/dictionary literal periodic check) as the fix.
