### Title
Webhook signature check authenticates the payload's claimed organization, but processing acts on an unrelated `repository.full_name` (and, for status events, no repository at all) — forged CI/push/status events for any tracked stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate a webhook's HMAC using `repository_owner`, derived from the payload itself (`repository.owner.login` or `organization.login`). Once verification passes, the raw JSON `params` are handed unmodified to `Shipit::Webhooks.for_event(event)` handlers, which locate the target `Stack`/`Repository` using a *different* payload field, `repository.full_name` (`Handler#repository_name`). Nothing binds these two fields together, and for `status` events the handler doesn't even scope by repository at all. This reproduces the H-10 bug class: a value that is verified/authorized (`repository_owner`) is not the value that is actually acted upon (`repository.full_name` / arbitrary commit `sha`).

### Finding Description
- Signature check: `verify_webhook_signature` short-circuits with `return true unless webhook_secret` [1](#0-0)  — for any organization configured in Shipit without a `webhook_secret` (a documented, valid configuration, e.g. `"webhook_secret": null` in `test/dummy/config/secrets.test.json`), signature validation is a no-op and any POST body claiming that organization is accepted.
- The organization used for this check is taken straight from the untrusted payload: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) , and `verify_signature` uses it to select `Shipit.github(organization: repository_owner)` before validating [3](#0-2) .
- Once verified (or trivially passed because `webhook_secret` is blank), `create` dispatches the *entire, attacker-controlled* `params` hash to every registered handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- Handlers resolve the *actual* target repository from a separate field, `payload.dig('repository', 'full_name')` [5](#0-4) , which is never cross-checked against `repository.owner.login`/`organization.login` used for the signature lookup.
- `StatusHandler` doesn't even use `repository_name`/`stacks` scoping — it updates **any** commit in the whole install matching the attacker-supplied `sha`: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) .
- `CheckSuiteHandler` similarly trusts `stacks` (derived from `repository.full_name`) and an attacker-chosen `head_branch`/`head_sha` to schedule check-run refreshes for arbitrary tracked stacks [7](#0-6) .
- `PushHandler` (not shown fully here) likewise resolves its target stack through the same `Handler#repository_name`/`stacks` helper, i.e. the field never bound to the signature check.

Binding that is broken: `organization authenticated by verify_signature == repository written by the dispatched handlers`. Before the attack, these are supposed to be the same trust domain (a webhook for org X should only be able to mutate stacks belonging to org X's repositories). After a crafted request, `organization.login` (used to pick the — possibly secret-less — verification path) and `repository.full_name` (used to select the stack that gets mutated) can point to two completely different organizations/repositories.

### Impact Explanation
An unprivileged attacker with only network access to Shipit's public webhook endpoint (no GitHub write access, no Shipit session, no `ApiClient` token) can, for any organization in the Shipit deployment whose GitHub App config has a blank `webhook_secret`:
- Inject fake `status` events that flip the CI status of arbitrary commits (via bare `sha`, no repository scoping at all), potentially satisfying `deployable_status`/CI-blocking checks used by the merge queue and continuous deployment, leading to an unauthorized merge or deploy.
- Inject fake `push` events to trigger `GithubSyncJob`, or `check_suite` events to force check-run refresh, against arbitrary tracked stacks belonging to other organizations.
- Inject `pull_request`/`membership` events that mutate PR/label/team state for repos not owned by the "authenticated" organization.

This crosses the required bar of "unauthorized deploy, rollback or merge" / "escalation" without any credential belonging to the target org, matching the Critical/High impact bar.

### Likelihood Explanation
The signature bypass requires no secret knowledge whenever any configured org's `webhook_secret` is blank — a supported and, per this codebase's own fixtures, commonly-used configuration (`test/dummy/config/secrets.test.json`, `test/dummy/config/secrets_double_github_app.yml` both ship with `webhook_secret: null`). Even where every org has a secret configured, the deeper design flaw remains: the field checked (`repository.owner.login`/`organization.login`) is never cryptographically or logically tied to the field acted upon (`repository.full_name`, bare `sha`), so a legitimate webhook signed by one org's real secret can still carry a forged `repository` block naming a different, unrelated repository/stack — the HMAC covers the raw body but the handlers never re-derive/re-validate that `repository.full_name`'s owner matches the verified `repository_owner`.

### Recommendation
- In `WebhooksController`/`Handler`, after verifying the signature for `repository_owner`, assert that `repository.full_name`'s owner (and, for `status`, the commit's stack's repository owner) equals the exact `repository_owner`/`organization.login` value used for signature verification; reject the request otherwise.
- Do not allow `webhook_secret` to be blank in production configurations; fail closed (reject) rather than short-circuiting to `true` when no secret is configured.
- Scope `StatusHandler` (and any other handler that queries by bare identifiers like `sha`) through the verified repository/stack rather than searching globally by `Commit.where(sha:)`.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs: `attacker-org` (webhook_secret: `nil`, matching this repo's own documented/test configuration pattern) and `victim-org` (a real tracked stack).
2. POST directly to `/webhooks` (no GitHub session, no ApiClient token needed) with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha you want to fake CI for>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. `verify_signature` resolves `repository_owner` = `"attacker-org"`; since `attacker-org`'s `webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally [8](#0-7) .
4. `StatusHandler#process` then updates the status of the victim's commit purely by `sha`, with no verification that it belongs to `victim-org` or any org whose secret was actually checked [6](#0-5) , potentially unblocking a merge or deploy that depends on that status.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

    end
