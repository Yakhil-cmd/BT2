Based on my research, I found a genuine analog to the "timestamp not validated to be in the future" bug class in `ocore`'s TPS-fee / rate-limiting mechanism, which is directly reachable by any unprivileged unit poster (an author choosing their own unit's `timestamp` field, exactly like the vesting contract's admin choosing `_startTimestamp`).

### Title
Missing Lower-Bound Validation on Unit `timestamp` Allows Negative Elapsed-Time in TPS Fee Calculation - (File: `validation.js`, `storage.js`)

### Summary
`validation.js` only bounds a unit's self-reported `timestamp` field from above (it must not be too far in the future), but never enforces that it be greater than (or even equal to) the `timestamp` of the `last_ball_unit` it references. This missing "must be later than reference point" check is the same class of bug as the VTVL vesting report, where `_startTimestamp`/`_endTimestamp` were never checked against `block.timestamp`, letting an unintended, already-past value slip through and change the meaning of downstream time-dependent logic.

### Finding Description
When a unit is validated, `validation.js` checks only the upper bound of the timestamp: [1](#0-0) 

There is no check that `objUnit.timestamp` is greater than the timestamp of `objUnit.last_ball_unit` (the anchor point the author themselves selects). Because of this, an unprivileged unit author can freely set an arbitrarily small `timestamp` (even earlier than their own `last_ball_unit`'s timestamp), which is then fed into the TPS-fee/anti-spam calculations that use this value as an "elapsed time": [2](#0-1) [3](#0-2) 

The same `objUnit.timestamp` value (attacker-controlled, unvalidated against the past) is passed straight into `validateTpsFee`, which relies on `storage.getLocalTpsFee` to compute the `min_tps_fee` the unit must pay: [4](#0-3) 

`elapsed` is computed as `objUnitProps.timestamp - objLastBallUnitProps.timestamp`, falling back to `elapsedTimeWhenZero` only when the difference is exactly `0`; a negative value passes through unchanged, since the `||` fallback in JS only triggers on `0`/falsy, not negative numbers: [5](#0-4) 

This mirrors the report's exact defect pattern: a user-supplied timestamp is used unconditionally for downstream time-arithmetic without ever validating it is chronologically sane ("in the future"/monotonic relative to its own reference), letting the poster manufacture an unintended and exploitable value.

### Impact Explanation
A negative `elapsed` flows into `tps = count / elapsed` (negative), and then into `base_tps_fee * (exp(tps / tps_interval) - 1)`, which for a sufficiently negative `tps` approaches `base_tps_fee * (0 - 1) = -base_tps_fee`, i.e. a negative required `tps_fee`. Since `validateTpsFee` compares `tps_fees_balance + objUnit.tps_fee * share` against `min_tps_fee * share`, a manipulated (near-zero or negative) `min_tps_fee` lets an attacker submit units while paying little to no TPS fee, undermining the network's anti-spam/congestion-pricing mechanism — the exact mechanism designed to keep the network able to confirm units at a sustainable rate under load. This falls under "a network unable to confirm new units" style impact from the accepted-impact list.

### Likelihood Explanation
Any regular node/wallet composing and posting a unit controls the `timestamp` field of its own unit (as seen in `composer.js`, where `objUnit.timestamp = Math.round(Date.now() / 1000)` is set client-side, not by consensus), and no other validation step in `validation.js` I could find cross-checks it against `last_ball_unit`'s timestamp for a lower bound. This makes the precondition trivially reachable by an unprivileged unit poster.

### Recommendation
Add a validation check in `validation.js` (in the same section that validates `objUnit.timestamp` against `current_ts + max_seconds_into_the_future_to_accept`) requiring `objUnit.timestamp` to be greater than or equal to the `timestamp` of `objUnit.last_ball_unit` (and/or the parent units), analogous to `require(_startTimestamp > block.timestamp)` in the referenced report. Additionally, `storage.js`'s `elapsed` computations (`getLocalTps`, `getFinalTps`) should explicitly clamp/reject non-positive `elapsed` values rather than relying on a `|| elapsedTimeWhenZero` fallback that only catches exact zero.

### Proof of Concept
1. Author composes a unit and sets `objUnit.timestamp` to a value earlier than (or very close to) the `timestamp` of the `last_ball_unit` it references — nothing in `composeJoint` or `validation.js` prevents this beyond the upper-bound future check. [6](#0-5) 
2. The unit is submitted; `validateTpsFee` computes `min_tps_fee` via `storage.getLocalTpsFee`, which computes `elapsed = objUnitProps.timestamp - objLastBallUnitProps.timestamp` — a small/negative number. [5](#0-4) 
3. The resulting distorted `tps`/`min_tps_fee` lets the unit pass fee validation while paying an unintended (near-zero) TPS fee, defeating the fee-based rate-limiting/anti-spam protection.

*Note: I was not able to fully trace every downstream consumer of `elapsed`/`tps` (e.g., whether other bound checks elsewhere clamp this before it reaches consensus-critical code), so the exact numeric exploitability (how negative/small `elapsed` needs to be, and whether `Math.round`/`Math.max` elsewhere mitigates it) should be confirmed with targeted testing before treating this as fully proven.*
