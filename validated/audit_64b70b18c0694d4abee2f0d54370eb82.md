### Title
`StatusHandler` writes commit statuses without binding them to the organization whose webhook signature was verified - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the `webhook_secret` of the organization named in the payload's `repository.owner.login` (or `organization.login`), but that organization binding is discarded once the signature check passes. [1](#0-0)  `StatusHandler#process` then mutates `Commit` rows purely by matching `sha`, with no check that the matched commit actually belongs to a stack/repository owned by the organization that produced the verified signature. [2](#0-1)  Sibling handlers for the same trust class explicitly re-scope by repository (`stacks`, derived from `payload.dig('repository', 'full_name')`) before acting, which shows the intended binding that `StatusHandler` fails to enforce. [3](#0-2) [4](#0-3) [5](#0-4) 

### Finding Description
The equality that must hold is: **organization whose `webhook_secret` verified the signature == repository/commit whose state is written**. Before the fix (the current code), this equality is not enforced for the `status` event:

1. `WebhooksController#verify_signature` resolves `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. The signature only proves the payload was HMAC-signed with *that organization's* secret. [6](#0-5) 
2. `create` dispatches the raw parsed payload to every registered handler for the event, with no re-verification of which repository the acted-upon record belongs to. [7](#0-6) 
3. `StatusHandler#process` looks up commits solely by `sha`, globally, across every stack/repository tracked by the Shipit instance, and calls `create_status_from_github!` on each match:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

By contrast, `PushHandler` and `CheckSuiteHandler` both call the shared `stacks` helper, which filters to `Repository.from_github_repo_name(repository_name)` before touching any row — i.e., they enforce "the repository named in the payload == the repository being mutated". [3](#0-2) [4](#0-3) [5](#0-4)  `StatusHandler` is missing this equivalent scoping.

Shipit explicitly supports multiple independently-configured GitHub organizations, each with its own `webhook_secret`, in a single deployment (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`). [8](#0-7)  Signature verification simply looks up the org matching the payload and checks the HMAC accordingly — it never confirms that the *commit sha being acted on* is actually associated with a repository under that same organization. [9](#0-8) 

### Impact Explanation
`Commit#create_status_from_github!` records status state that feeds directly into deploy-safety checks (`Commit#deployable?`), which gate whether a commit can be deployed via `Stack#trigger_deploy`. Because `StatusHandler` matches commits by `sha` alone with no repository/organization boundary, any organization that Shipit has configured with a valid `webhook_secret` — attacker-controlled if the attacker owns/operates one of the configured GitHub orgs/apps — can deliver a genuinely-signed `status` webhook whose `sha` happens to match a `Commit` row belonging to a completely different, unrelated stack/repository (e.g., shared commit history from forks/mirrors tracked as separate Shipit stacks, or any sha collision across tracked repositories). This forges CI status (including `success`) onto a commit outside the attacker's own repository, which can make that unrelated stack's commit appear deployable, enabling an unauthorized deploy decision on a repository the attacker does not control — a cross-repository write with Critical-tier impact under this engine's rules ("cross-repository writes, or an unauthorized deploy...").

### Likelihood Explanation
Exploitation requires only that the attacker control (or have push access to) one of the GitHub organizations/apps that are legitimately configured in this Shipit instance's `Shipit.github` multi-org config — no privileged Shipit account, `ApiClient` token, or webhook-secret theft is needed, since the attacker's own org's webhook deliveries are validly signed by GitHub. The precondition of a shared commit `sha` across two Shipit-tracked repositories is realistic in common setups (forked repositories, upstream/downstream mirrors, monorepo-derived stacks) where multiple stacks reference identical commit history.

### Recommendation
In `StatusHandler#process` (and any other handler that does not already scope through `stacks`), constrain the `Commit` lookup to commits belonging to stacks under `repository_name`/`repository_owner` derived from the verified payload, mirroring the pattern used by `PushHandler` and `CheckSuiteHandler` (`stacks.joins(:commits).where(commits: { sha: params.sha })` or equivalent), so a commit status can only be written for a repository that matches the organization whose signature was actually verified.

### Proof of Concept
1. Shipit is configured with two GitHub organizations/apps, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`). [10](#0-9) 
2. `OrgA` hosts the tracked upstream repository; a Shipit `Stack`/`Commit` row exists for commit `sha X` under `OrgA/repo`.
3. Attacker controls `OrgB` (e.g., a fork of `OrgA/repo` also onboarded to the same Shipit instance) and, via normal repository activity, causes GitHub to deliver a `status` webhook for `OrgB/repo` whose `sha` field is `X` (shared commit history between the fork and upstream) and `state: success`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `OrgB`, fetches `OrgB`'s `webhook_secret`, and the HMAC check passes because the delivery is genuinely signed by GitHub for `OrgB`. [6](#0-5) 
5. `StatusHandler#process` executes `Commit.where(sha: 'X')`, which returns the `Commit` row belonging to `OrgA/repo`'s stack (no repository filter), and writes a forged `success` status onto it. [2](#0-1) 
6. `OrgA`'s commit now shows a forged passing status, which `Commit#deployable?`/deploy-safety checks may treat as satisfied, allowing an unauthorized deploy decision on a repository the attacker (via `OrgB`) does not control.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
