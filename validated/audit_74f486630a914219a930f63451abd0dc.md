### Title
Missing Slippage/Minimum-Return Protection in AMM-style Autonomous Agents Enables Sandwich Attacks on Trigger Senders - (File: `test/samples/uniswap_like_market_maker.oscript`)

### Summary
The reported Yaxis issue is that `Controller`/`Manager` swap against Curve without specifying a minimum-return amount, letting MEV bots sandwich the trade. Obyte's `ocore` engine ships (and encourages via its sample library) the same anti-pattern in AA-based automated market makers: the constant-product exchange logic computes the amount out purely from the *current* on-chain reserve balances at the moment the trigger unit executes, with no user-supplied minimum-output check. Any unprivileged unit poster who can observe a pending swap trigger in the DAG can post competing units chosen so that their own trade is ordered immediately before and after the victim's trigger, extracting value exactly like a sandwich attack — because AA execution order is a deterministic function of unit `(mci, level, unit)`, which an attacker can influence by unit/parent selection before stabilization.

### Finding Description
The sample constant-product AMM AA computes swap output solely from the reserves visible at execution time, with no user-specified minimum acceptable output: [1](#0-0) 

The equivalent logic (asset→bytes direction) has the identical missing protection: [2](#0-1) 

Because the AA reads `balance[$asset]` / `balance[base]` at execution time and trusts `trigger.output[[asset=...]]` without any `min_amount`/`max_slippage` parameter from the trigger data, the resulting payout is fully determined by whatever reserve state exists immediately before the victim's trigger is processed — exactly the condition that enables sandwiching in the referenced Yaxis report (calling the DEX without specifying `minReturn`).

The order in which competing triggers to the same AA execute is deterministic but attacker-influenceable: AA triggers are collected per stabilized MCI and processed in `(mci, level, aa_triggers.unit, address)` order: [3](#0-2) 

and the underlying trigger units are picked up for the MC index by level/unit ordering: [4](#0-3) 

Because a poster's own unit's `level` and its `main_chain_index` inclusion are influenced by which parents the poster chooses (and units are relayed peer-to-peer before stabilization, so a pending large swap trigger is visible before it stabilizes), an attacker can craft two of their own trigger units — one intended to land immediately before the victim's trigger (front-run buy) and one immediately after (back-run sell) — bracketing the victim's swap and extracting the price impact as arbitrage profit, with no minimum-return check in the AA to stop it.

### Impact Explanation
Any user who sends a swap trigger to a market-maker/AMM AA of this class loses value to a sandwiching third party without any wrongdoing of their own — this is a direct "AA fund loss" for the victim and a value-leak analogous to the acknowledged Yaxis finding ("Agree with finding... this allows to 'leak value'"). Because such AMM patterns are part of ocore's own documented/sample AA design (and used as a reference implementation by third-party AA authors), any real AMM built from this pattern inherits the vulnerability, with unbounded value loss scaling with swap size and reserve depth.

### Likelihood Explanation
Likelihood is high: the attack requires only the capability the report's threat rules explicitly allow — an unprivileged AA trigger sender posting ordinary payment/trigger units, no special network or node privileges. Sandwiching pending trades visible in a public DAG mempool-equivalent (unstable units broadcast before stabilization) is a well-understood MEV technique, directly mirroring the original report's threat model of MEV searchers watching pending swap calls.

### Recommendation
Update the reference AMM sample (and document requirement for all AA authors building exchange-style AAs) to require a `min_output`/`max_slippage` field supplied by the trigger sender and enforced with a `bounce()` check before crediting/paying out, e.g. `if ($amount < trigger.data.min_amount) bounce('slippage exceeded')`, mirroring standard DEX minReturn protections. Additionally, ocore documentation for AA authors should explicitly warn that AA trigger execution order can be influenced by parent/unit selection, and instruct authors of price-sensitive AAs to always incorporate a caller-specified minimum-return guard.

### Proof of Concept
1. AA author deploys the sample constant-product AMM AA as-is: `test/samples/uniswap_like_market_maker.oscript` lines 102–121, which computes `$amount` purely from live reserves with no caller-supplied minimum.
2. Victim broadcasts a large "exchange bytes to asset" trigger unit.
3. Attacker observes the unstable trigger unit in the DAG before it stabilizes, and crafts two of their own trigger units chosen with parents/levels intended to have one execute immediately before (moving the price against the victim) and one immediately after (extracting the price back), per the deterministic `(mci, level, unit, address)` ordering used in `aa_composer.js` (`handleAATriggers`) and `main_chain.js` (`handleAATriggers` inside `markMcIndexStable`).
4. The victim's trigger executes at the manipulated reserve ratio, receiving less asset than expected, with the difference captured by the attacker's bracketing trades — no protocol or AA-level check exists to prevent or detect this because the AA never validates a minimum acceptable output.
