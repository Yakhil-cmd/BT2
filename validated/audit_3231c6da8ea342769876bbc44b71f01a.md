This confirms the multi-organization GitHub App configuration schema documented in `docs/setup.md`, where `Shipit.github(organization:)` looks up a distinct `webhook_secret`/config per top-level organization key [1](#0-0) .

### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but events are routed and acted upon using the unrelated `repository.full_name` field, allowing cross-organization webhook forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-GitHub-App deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . However, every webhook `Handler` resolves the target repository/stack using a *different* field from the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing in the code enforces that `repository.owner.login` and `repository.full_name` refer to the same repository/organization.

### Finding Description
The binding that should hold is: *the organization whose secret authenticated the signature* == *the organization whose repository is acted upon*. This engine breaks that equality:

- Signature verification: `Shipit.github(organization: repository_owner)` picks the `GitHubApp` (and its `webhook_secret`) keyed by `repository.owner.login` [4](#0-3) , using the multi-app config schema keyed per organization in `Shipit.github_app_config` [5](#0-4) .
- Handler dispatch: `WebhooksController#create` just parses the raw body and calls every registered handler for the event with the entire, single, attacker-supplied JSON payload — the same object that was (or wasn't) checked against `repository_owner`'s secret: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) .
- Handlers key off `repository.full_name`, not `repository.owner.login`, e.g. `PushHandler` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }` where `stacks` is derived from `Repository.from_github_repo_name(repository_name)` [7](#0-6) , and `repository_name` is `payload.dig('repository', 'full_name')` [8](#0-7) .

An attacker who legitimately controls (or has installed the Shipit GitHub App on) *any one* configured organization "attacker-org" — and therefore knows or can freely generate a validly-signed webhook body under `attacker-org`'s `webhook_secret` — can set `repository.owner.login = "attacker-org"` (so `verify_signature` selects and passes against `attacker-org`'s secret) while setting `repository.full_name = "victim-org/victim-repo"` (an unrelated organization/repository also configured on the same Shipit instance). The signature check in `GitHubApp#verify_webhook_signature` only checks the HMAC over the raw body using the secret chosen for `attacker-org`; it never checks that the signed body's `repository.full_name` actually belongs to `attacker-org` [9](#0-8) . The forged, validly-signed-for-`attacker-org` payload is then processed as if it genuinely originated from `victim-org`, driving handlers like `PushHandler` to enqueue `GithubSyncJob` against `victim-org/victim-repo`'s stacks with an attacker-chosen `expected_head_sha` [7](#0-6) [10](#0-9) , or similarly spoof `status`, `check_suite`, `pull_request`, or `membership` events against victim repositories/stacks/teams.

This is the direct analog of the reported bug class: a field that gates the trust decision (`repository.owner.login`, used only to pick the verification key) is disjoint from the field that the rest of the system actually acts on (`repository.full_name`), so a value the attacker fully controls and can validly sign is used to authorize actions on a completely different, unauthenticated target.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Concretely it lets an attacker who controls one Shipit-connected GitHub organization force `GithubSyncJob` synchronization, commit `Status` creation, `check_suite`/`RefreshCheckRunsJob` triggers, `Membership`/`Team` mutations, or PR-driven review-stack `archive!`/`unarchive!` transitions against a victim organization's stacks that the attacker has no access to — all without ever needing that victim's `webhook_secret`, session, or API token. Depending on which handler is exercised this can manipulate deploy readiness signals or PR-driven stack lifecycle for a repository the attacker does not control, i.e. an unauthorized/attacker-influenced deploy-adjacent action on the victim's stack.

### Likelihood Explanation
This requires a Shipit instance configured with the multi-organization GitHub App schema (`Shipit.github_app_config`) and requires the attacker to have legitimate control of at least one of the configured organizations (e.g. they can install/observe their own app's genuine webhook deliveries to learn/reuse a validly-signed payload, or their org's `webhook_secret` is blank, in which case `verify_webhook_signature` returns `true` unconditionally: `return true unless webhook_secret` [11](#0-10) ). No session, API token, or victim credential is required — only knowledge of one org's own secret/signing capability, which is realistic in any environment onboarding third-party or lower-trust organizations onto a shared Shipit instance.

### Recommendation
After signature verification, re-derive the organization from `repository.full_name` (or `organization.login`) that handlers will actually act on, and reject the webhook (422) unless it matches the organization whose secret was used to verify the signature. Equivalently, verify the signature using the GitHub App config selected by the same field the handlers use for repository resolution, so `repository_owner` (verification key selection) and `repository_name`/`full_name` (action target) are always drawn from, and cross-checked against, the same trusted field.

### Proof of Concept
1. Configure Shipit with the multi-org schema: organizations `attacker-org` and `victim-org`, each with distinct `webhook_secret`s, both with stacks configured [12](#0-11) .
2. As the owner/admin of `attacker-org` (a role the attacker legitimately holds), compute a valid HMAC-SHA1 signature over a crafted JSON body using `attacker-org`'s known `webhook_secret`, where the body's `push` payload sets `"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen-sha>"`.
3. POST this body plus header `X-Hub-Signature: sha1=<computed>` and `X-Github-Event: push` to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and the signature validates successfully against `attacker-org`'s secret [4](#0-3) .
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` and enqueues `GithubSyncJob` for `victim-org`'s stack(s) with the attacker's `expected_head_sha`, despite the request never being authenticated against `victim-org`'s secret [7](#0-6) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
