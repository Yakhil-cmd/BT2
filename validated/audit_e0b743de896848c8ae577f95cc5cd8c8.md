### Title
Floating-point precision loss in indivisible asset denomination cap/issue-amount checks due to unbounded `count_coins * denomination` multiplication - (File: validation.js)

### Summary
`LimitOrderRegistry::cancelOrder`'s bug class is a fixed-width integer multiplication (`1e18 * depositAmount` on a `uint128`) that can silently overflow and corrupt a downstream percentage/amount calculation. The equivalent risk in `ocore` (a JavaScript codebase using IEEE-754 doubles instead of fixed-width integers) is a multiplication of two attacker-controlled integers that can exceed `Number.MAX_SAFE_INTEGER` (2^53−1 ≈ 9.007e15), producing silently rounded/incorrect results instead of an explicit revert. This occurs in the indivisible-asset denomination cap calculation and the corresponding issue-amount check.

### Finding Description
In `validateAssetDefinition` (`validation.js`), when an asset defines fixed denominations, each `denomInfo.count_coins` is checked only with `isPositiveInteger`, with no upper bound tied to `constants.MAX_CAP`, while `denomInfo.denomination` is bounded to `constants.MAX_CAP` (9e15) only after `pemCurvesFixMci`: [1](#0-0) 

The cap total is then computed as: [2](#0-1) 

Because `count_coins` has no explicit upper bound and `denomination` can be close to `MAX_CAP` (9e15), the product `denomInfo.count_coins * denomInfo.denomination` can exceed `Number.MAX_SAFE_INTEGER` (~9.007e15) — the JS analog of the Solidity `uint128` overflow boundary in the report. Unlike Solidity, JS doesn't revert or wrap; it silently loses precision, rounding to the nearest representable double.

The same unchecked multiplication pattern is used later when validating an indivisible issue input against the DB-stored denomination info: [3](#0-2) 

Here `input.amount !== denomination * denomInfo.count_coins` is a JS `!==` comparison between an integer amount and a computed product; if the product loses precision, an attacker-crafted `input.amount` that doesn't actually equal the true product could still pass this equality check because both sides get rounded to the same imprecise double.

### Impact Explanation
If precision loss lets a crafted issue input pass the "issue amount must equal denomination×count_coins" check, or lets `total_cap_from_denominations` inconsistently match `payload.cap` at asset-definition time versus the true intended supply, an issuer could inflate the effective circulating supply of an indivisible, denomination-capped asset beyond its declared cap, or produce a mismatch between different nodes' assessments of validity if intermediate calculations diverge due to differing computation order — though because all nodes use the same deterministic JS arithmetic on the same inputs, the primary concrete risk is supply/definition inconsistency (asset issued in amounts inconsistent with its stated cap), which is an asset issuance/integrity violation reachable by any asset issuer/poster.

### Likelihood Explanation
Requires an asset definer to intentionally choose `count_coins` and `denomination` values whose product straddles `2^53`, which is within the allowed ranges (`denomination` up to `MAX_CAP` = 9e15, `count_coins` unbounded beyond "positive integer"). This is fully attacker-controlled data in an asset-definition and issue-input message that any user can post, requiring no privileged access.

### Recommendation
Bound `denomInfo.count_coins` to a safe value (e.g., `constants.MAX_CAP`) before multiplying, and validate that `denomInfo.count_coins * denomInfo.denomination <= Number.MAX_SAFE_INTEGER` (or perform the multiplication with `BigInt`) before comparing to `payload.cap` in `validateAssetDefinition`, and apply the same safe-integer check in `validateIndivisibleIssue`'s `denomination * denomInfo.count_coins` comparison in `validation.js`.

### Proof of Concept
Not independently reproduced against a running node in this analysis; the reasoning is based on static code inspection of `validation.js` lines 2218-2226 and 2763-2792, which shows `count_coins` has no upper bound tied to `MAX_CAP` while `denomination` can approach `MAX_CAP`, making the product exceed `Number.MAX_SAFE_INTEGER`. Full confirmation (e.g., constructing a concrete asset-definition + issue-input pair that triggers a mismatch acceptance) would require running the validation code with representative attacker-supplied `count_coins`/`denomination` values, which was not verified in this pass due to the absence of runtime access.
