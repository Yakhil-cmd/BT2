### Title
System-parameter and op_list votes are weighted by instantaneous stable balance with no holding-period requirement, enabling flash-loan-style governance manipulation - (File: main_chain.js)

### Summary
The `countVotes()` function in `main_chain.js` determines the outcome of `system_vote` messages (including changes to the order-provider/witness list `op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier`) by summing the *current* stable-good byte balance of every address that has cast a vote for a subject, with no requirement that the balance be held for any minimum duration before or after the vote is cast.

### Finding Description
`countVotes()` computes voter weight from a single balance snapshot taken as of the just-stabilized MCI: [1](#0-0) 
This balance is inserted into a temporary `voter_balances` table and directly used to weight both `op_list` votes and numerical system-parameter votes: [2](#0-1) [3](#0-2) 
Validation of a `system_vote` message only checks the format of the payload (e.g., `op_list` size/order, numeric bounds) — it never checks how long the voter has held their balance, nor does it lock/freeze the balance used for voting: [4](#0-3) 
Once a `system_vote` unit becomes stable, an address's vote is recorded permanently in `system_votes`/`op_votes`/`numerical_votes` with its balance counted at whatever MCI the recount happens to run, and the funds can be moved away immediately afterward without affecting the vote's weight, since the weight was already captured for that count. The only mitigations present are (a) the "vote timeframe" expansion loop that looks back over `system_votes` timestamps to ensure enough *voting addresses* participated within some period, and (b) `EMERGENCY_COUNT_MIN_VOTE_AGE` for emergency OP-list recounts — neither of which requires the underlying byte balance itself to have been held for a minimum period: [5](#0-4) [6](#0-5) 

This mirrors the DAO.sol flash-loan finding: voting weight is derived from a spot balance rather than a time-locked or historically-averaged one, so an actor (or a colluding group, as the judge noted regarding pooled/rotated funds — no single-transaction atomicity is required) can temporarily acquire a large byte balance, cast/refresh a `system_vote`, wait for it to stabilize, and then move the funds away, all while their vote counts at full weight in the next `countVotes()` run.

### Impact Explanation
`op_list` votes directly control which addresses serve as order providers/witnesses, which are the addresses used everywhere in the protocol to determine main-chain best-parent selection and unit/MC stability (`storage.determineWitnessedLevelAndBestParent`, `validateWitnesses`): [7](#0-6) 
An attacker who can temporarily out-weigh legitimate voters can push a compromised or colluding set of addresses into the `op_list`, which is a governance-controlled parameter that all full nodes adopt (`onSystemVarUpdated` propagates the new list to wallets/witnesses): [8](#0-7) 
This can lead to nodes disagreeing on stability/witness composition, or to numeric system parameters (fees, TPS interval/multiplier) being pushed to attacker-favorable extremes, both of which fall under "node disagreement on validity or stability" and broader network-liveness impact.

### Likelihood Explanation
The main practical constraint is that acquiring/moving balance and getting the `system_vote` unit stabilized requires DAG confirmation delays rather than a single atomic transaction as in EVM flash loans, so this is not exploitable in one block. However, as the original judge noted, no atomicity is required at all — a group of colluding holders can simply pool and rotate large balances across a short window (well within the vote-timeframe/expiration lookback of up to a year) to swing a vote, since `countVotes()` never checks balance duration, only vote timestamp recency of the *voting address*, not the *balance*.

### Recommendation
When computing voter weight in `countVotes()`, require that the balance being counted has been held by the voting address for a minimum holding period (e.g., balance must have existed as of some MCI well before the vote/recount, using historical balance snapshots) rather than the instantaneous stable balance at recount time. Alternatively, weight votes by a time-averaged balance over the vote's lifetime, or require re-affirmation of votes with balance checks at multiple points in time before counting them toward `op_list` or numeric system-parameter changes.

### Proof of Concept
1. A group of addresses (or a single actor with temporary access to a large sum) transfers a large amount of bytes into a voting address.
2. Once that transfer stabilizes, the address posts a `system_vote` message for `op_list` (or another subject) and a `system_vote_count` command, per the validation path in `validation.js` (`case "system_vote"`).
3. When `main_chain.js`'s `countVotes()` runs at the next stabilized MCI, it counts the full temporarily-held balance from `outputs`/`units` as of that MCI (`main_chain.js` lines 1757–1773), giving the attacker's vote outsized weight relative to their normal holdings.
4. Immediately after the recount, the attacker moves the funds elsewhere; the vote's recorded weight for that count is unaffected since `countVotes()` already used the snapshot balance.
5. Repeating this with rotated/pooled funds across colluding addresses can shift `op_list` or numeric parameter outcomes without any long-term economic stake in the network.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}
