### Title
`register-for-bond`'s L1 lockup proof has no persisted, cross-call replay guard, allowing the same Bitcoin lockup UTXO to be credited as sats collateral more than once - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s L1 path (`verify-l1-lockups` / `validate-l1-lockup`) proves a staker's BTC collateral purely by checking that a supplied raw Bitcoin transaction/output is merkle-included under a valid header and that its scriptPubKey/amount match the expected timelock P2WSH for that `(staker, bond-index)` pair. The de-duplication of outpoints (`seen-outpoints`) only exists as an ephemeral fold accumulator, freshly initialized to `(list)` on every call to `verify-l1-lockups` [1](#0-0) , and is never checked against, or written to, any contract-persisted map. There is no on-chain check anywhere in `pox-5.clar` that the UTXO has not been spent, nor any global "used lockup" record across separate `register-for-bond` invocations.

### Finding Description
`validate-l1-lockup` accumulates a `seen-outpoints` list solely to reject duplicate entries *within the same call's `outputs` list* (guarding against a single proof list double-counting one output three times) [2](#0-1) . This list is created fresh (`seen-outpoints: (list)`) at the start of every `verify-l1-lockups` call [1](#0-0)  and discarded afterward — it is never merged into a persistent map such as `used-l1-lockups` keyed by `(txid, output-index)`.

Nothing else in the verification path substitutes for this: `parse-block-header`/`verify-block-header`/`verify-merkle-proof` only prove that a given raw transaction was mined in a given Bitcoin block; they say nothing about whether the corresponding output has since been spent [3](#0-2) . The contract compares the *committed script* against a hash built from `(staker, unlock-burn-height, staker-unlock-bytes, early-unlock-bytes)` [4](#0-3) , so the script does bind to a specific staker and specific bond L1-unlock parameters — but it does not bind to a specific *registration event* or consume the outpoint permanently on the Stacks side.

Consequence: once a staker has proven a given `(txid, output-index)` once to `register-for-bond` for `bond-index A`, and later that bond's cycle ends (allowing the staker to exit/roll over per `verify-bond-rollover-window`), the exact same historical merkle-proof tuple — for a transaction that is still fully reconstructable off-chain and was never required to still be *unspent* — can be resubmitted to `register-for-bond` for a subsequent bond (`bond-index B`) whose admin-chosen `unlock-burn-height`/`early-unlock-bytes` happen to reproduce the identical expected script hash (or, at minimum, is fully re-derivable/re-provable by the staker at will since the raw bytes and merkle path are public information the staker retains after the first use). Because the contract has no mechanism recording "this outpoint has already been credited by pox-5," `sats-total` (and therefore bond share/allowance/reward accounting) can be inflated using a single, one-time Bitcoin lock, i.e., sats are credited on the Stacks side that were never (additionally) locked on Bitcoin for the second registration.

This matches the report's cited bug class by analogy: TYPO3's `typoLink` vulnerability stemmed from accepting attacker-controlled input into a sensitive output context without re-validating it kept the guarantees the system relied on. Here, `verify-l1-lockups` accepts attacker-controlled/replayable proof input (`tx`, `header`, `leaf-hashes`, etc.) into the sats-accounting pipeline without any persisted uniqueness guarantee across calls, breaking the intended invariant "1 unit of locked BTC == 1 unit of credited sats."

### Impact Explanation
This breaks the equality between real, still-locked Bitcoin collateral and internally-credited `sats-total`/`amount-sats` used to compute bond share, reward slots, and allowance consumption in `pox-5`. A staker (an ordinary, unprivileged bond participant — no admin/miner/other-user's key required) could double-count their own BTC lockup to receive signer/staker sBTC rewards or bond credit disproportionate to actual locked value, i.e., unbacked minting/double-counting of a reward-earning commitment. Per the scan rules this falls under Critical ("double-counting a commitment or reward").

### Likelihood Explanation
Exploitability depends on being able to find/construct two bonds whose L1-unlock parameters yield a matching (or independently re-provable) expected script for the same underlying UTXO, and on the rollover/allowlist logic permitting a second `register-for-bond` call after the first bond's membership has ended. I was not able to fully verify, within the given file scope, whether `verify-bond-rollover-window`, `ERR_ALREADY_REGISTERED`, and the allowlist checks (`protocol-bond-allowances`) collectively prevent this scenario end-to-end for all bond parameter combinations — the code I could inspect shows `existing-membership`/`existing-stake` checks gate *concurrent* double-registration, but none of them reference `seen-outpoints` or any per-outpoint persisted state, so the specific attack of reusing an outpoint across two *sequential, non-overlapping* bond registrations is not blocked by anything visible in `pox-5.clar`.

### Recommendation
Persist a durable, contract-level map (e.g., `used-l1-lockup-outpoints: { txid, output-index } -> bool`) and check/insert into it inside `validate-l1-lockup` (in addition to the ephemeral `seen-outpoints` fold check), so that once a given Bitcoin outpoint has been credited to any `register-for-bond` call, it can never be credited again regardless of bond index or staker rollover timing.

### Proof of Concept
1. Staker locks `X` sats into the canonical P2WSH derived from `construct-lockup-output-script(staker, unlock_A, staker_unlock_bytes, early_unlock_bytes_A)` for `bond-index A`, and calls `register-for-bond` with a valid merkle proof of that output — `sats-total = X` is credited, per `verify-l1-lockups`/`validate-l1-lockup` [5](#0-4) .
2. Bond A's cycle ends; the staker's membership exits/rolls over (per the rollover-window logic referenced at `verify-bond-rollover-window`), clearing `existing-membership` state for that staker.
3. The staker retains the original raw transaction, header, and merkle path (all public/off-chain data — nothing prevents reuse). They call `register-for-bond` again for `bond-index B`, whose admin-set `unlock-burn-height`/`early-unlock-bytes` are engineered (or coincide) to reproduce the same expected script hash for the *same* `(staker)` — reusing the identical `(txid, output-index)`.
4. `validate-l1-lockup`'s only anti-replay check, `seen-outpoints`, is re-initialized to `(list)` for this new call [6](#0-5) , so the duplicate outpoint passes, and `sats-total = X` is credited a second time for bond B — with no second lock of `X` sats ever having occurred on Bitcoin.

;; Verify l1 lockup information for a staker. This asserts that each lockup
;; corresponds to the right timelock script for this staker, and that the lockup
;; occurred on-chain. If everything is valid, this returns the sum of all lockups in sats.
(define-private (verify-l1-lockups
        (staker principal)
        (bond-index uint)
        (lockups {
            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        })
    )
    (let (
            (bond (unwrap! (get-protocol-bond bond-index) ERR_BOND_NOT_FOUND))
            (accumulation (try! (fold validate-l1-lockup (get outputs lockups)
                (ok {
                    sum: u0,
                    staker: staker,
                    minimum-unlock-height: (get-bond-l1-unlock-height bond-index),
                    staker-unlock-bytes: (get staker-unlock-bytes lockups),
                    early-unlock-bytes: (get early-unlock-bytes bond),
                    seen-outpoints: (list),
                })
            )))
        )
        (ok (get sum accumulation))
    )
)
