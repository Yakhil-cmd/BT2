### Title
Webhook signature verified against `repository.owner.login` while event processing routes on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using `repository.owner.login` (or `organization.login`) from the untrusted JSON body, while every event handler (`Handler#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) resolves the target `Stack`/`Repository` using the independent `repository.full_name` field from the same body. An attacker who legitimately controls a GitHub organization/app installation that Shipit trusts (and therefore knows that org's `webhook_secret`) can produce a validly-signed payload whose `owner.login` matches their own org but whose `full_name` names a different repository/stack hosted by the same Shipit instance.

### Finding Description
`verify_signature` computes the field used to pick the signing secret independently from the field used to determine which resource is mutated: [1](#0-0) [2](#0-1) 

The signature is validated using `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature`, which only proves the raw body was HMAC-signed with *some* organization's configured `webhook_secret` — it says nothing about which repository the payload's other fields refer to: [3](#0-2) 

Once the signature check passes, the parsed body is dispatched unmodified to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [4](#0-3) 

Every handler resolves the affected `Stack` using a *different* field of the same body — `repository.full_name` — not `repository.owner.login`: [5](#0-4) 

For example `PushHandler` triggers `stack.sync_github` for every non-archived stack whose branch matches, scoped only by the repository resolved from `full_name`: [6](#0-5) 

The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository being written to`. Because `repository_owner` (used for authentication) and `repository_name`/`full_name` (used for the write) are two independently attacker-controlled JSON fields inside the same signed body, the signature only proves "some trusted org's secret signed this exact byte string" — it does not prove "the org that owns this secret also owns the target repository." An organization onboarded to Shipit (with its own legitimate `webhook_secret`) can therefore forge a validly-signed webhook naming any other repository/stack hosted on the same Shipit instance as `repository.full_name`.

### Impact Explanation
With a forged, validly-signed cross-repository payload an attacker (who only controls their own onboarded org/app installation, not the target repo) can:
- Force `GithubSyncJob`/`stack.sync_github` on an arbitrary target stack via `push` events, and drive `expected_head_sha` to values the attacker chooses (potential to trigger syncs to attacker-chosen commits sourced from GitHub for the target stack).
- Inject fabricated commit `Status` records (via `status` events, matched by `sha` within the target repo's commits) that other Shipit logic (e.g., deploy safety checks) may treat as CI signal, potentially enabling an unauthorized deploy decision on a repository the attacker does not own.
- Trigger `check_suite`/`membership`/`pull_request` side effects (team/user creation, PR-driven review-stack behavior) scoped to a repository outside the attacker's control.

This crosses a repository-ownership trust boundary using only credentials for a foreign, attacker-controlled org, matching the "unauthorized deploy" / cross-repository-write class of impact.

### Likelihood Explanation
Requires the attacker to already be an org that Shipit legitimately trusts (has a configured GitHub App/webhook secret for their own org) — this is a real precondition (any org onboarding the Shipit app), but does not require compromising the *target* repository's credentials, a Shipit session, or an `ApiClient` token. The target repository's `full_name` must be known/guessable, which is generally true for any tracked stack.

### Recommendation
In `WebhooksController#verify_signature`, require that the organization/app whose secret validated the signature matches the repository actually referenced for processing (i.e., derive the same "owning organization" value used to select the signing secret from the same trusted mapping used by `Handler#repository_name`, and reject the request if `repository.full_name`'s owner segment does not match the organization that authenticated the signature). Equivalently, look up the `Repository`/`Stack` from `full_name` first, resolve its known GitHub organization from Shipit's own configuration, and use that value (not the payload's `owner.login`) to select the signing secret.

### Proof of Concept
1. Attacker's organization `attacker-org` has legitimately installed the Shipit GitHub App and knows its `webhook_secret`.
2. Attacker crafts a `push` webhook JSON body with:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"` (a real stack tracked by the same Shipit instance)
   - `ref`, `after` set to attacker-chosen branch/sha.
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the exact raw body (per `GitHubApp#verify_webhook_signature`).
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and successfully verifies the signature.
5. `PushHandler#process` resolves the stack via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on it — a write triggered on a repository the attacker does not control, using only the attacker's own org's webhook credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
