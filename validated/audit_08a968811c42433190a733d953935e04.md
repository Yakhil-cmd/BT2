### Title
Unvalidated swap routes can inject attacker-controlled contract calls beneath a user’s authorization - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
High severity. `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept caller-provided opaque swap payloads and forward them to the configured router. The controller constrains only its own input transfer and measured output; it does not constrain which pool or token contracts the route invokes. A malicious route can therefore place attacker-controlled contract code beneath the caller’s authorization tree and make unrelated token transfers from the caller if the simulated tree is signed. [1](#0-0) [2](#0-1) 

### Finding Description
The strategy endpoints receive `swap` as attacker-controlled bytes and pass it into the strategy implementation. For example, `swap_collateral` accepts `swap: Bytes` and forwards it to `process_swap_collateral`. [1](#0-0) 

`process_swap_collateral` authenticates the caller and verifies account ownership or delegation, but treats the decoded `StrategySwap` as routing instructions rather than a trusted set of contract addresses. [3](#0-2)  It then passes the payload to `withdraw_and_swap_from_supply`. [4](#0-3) 

`swap_tokens` loads the configured router, authorizes one exact input-token transfer, and calls `router.execute_strategy(&controller, &amount_in, swap)` while the caller’s authorized invocation is still on the stack. [2](#0-1)  The authorization helper is intentionally narrow for the controller-to-router transfer, but it does not validate the swap payload’s nested call targets. [5](#0-4) 

This is analogous to the AppImage empty search-path element: the route supplies the effective “search path,” and the controller/router resolves code addresses from that user-controlled path without an allowlist. A malicious pool or token contract can implement the expected venue ABI and additionally invoke an unrelated `token.transfer(caller, attacker, amount)`. Because the route executes below the caller’s authorized controller invocation, Soroban simulation can record that transfer as a child authorization; signing the simulated tree makes it executable. [6](#0-5) 

### Impact Explanation
An attacker can steal arbitrary balances of arbitrary tokens held by a user who signs a transaction containing the malicious route, not merely the swap input or the user’s lending collateral. The stolen amount is not bounded by `amount_in`, `min_out`, or the final health-factor checks because it is a separate token transfer authorized as a child of the same caller auth tree. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
Any unprivileged attacker can deploy a malicious contract that implements the relevant venue interface, encode it as a pool/token component in the swap payload, and cause a user to submit that route through `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply`. The controller performs no route-component allowlist before invoking the configured router. [2](#0-1) 

The exploit depends on the victim signing the authorization tree that simulation records. Standard wallet flows commonly rely on simulation-produced auth trees, so a malicious route can hide an additional child `transfer` unless the client explicitly rejects unexpected children. [3](#0-2) [9](#0-8) 

### Recommendation
Do not let caller-controlled route bytes introduce arbitrary contract invocations beneath a user authorization.

- Maintain an on-chain allowlist of permitted venue pool contracts and reject routes containing any other address.
- Alternatively, bind each route to a signed quote/commitment that the client independently validates before signing.
- Ensure clients reject any simulated authorization tree containing children beyond the expected route pull and controller operations.
- Document that output measurement and final solvency checks do not bound unrelated transfers authorized below the caller invocation. [10](#0-9) 

### Proof of Concept
1. The attacker deploys a contract exposing the venue/pool ABI expected by the configured router. Its `swap` implementation also calls `token::Client::transfer(victim, attacker, victim_balance)` for an unrelated token held by the victim.
2. The attacker embeds that contract address in a `StrategySwap` payload.
3. The victim calls `Controller::swap_collateral(caller, account_id, current, amount, new, swap)`, where `swap` contains the malicious route. [1](#0-0) 
4. The controller authenticates the victim and account, withdraws collateral, and calls the configured router with the attacker-controlled route. [11](#0-10) 
5. During route execution, the malicious pool performs the unrelated transfer from the victim. Simulation records it as a child of the victim’s `swap_collateral` authorization; once signed, the transaction executes both the valid-looking collateral swap and the theft.

```rust
/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
```
