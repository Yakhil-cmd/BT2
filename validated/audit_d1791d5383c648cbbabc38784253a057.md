### Title
`collect_creator_fee`/`collect_creator_fee_permissionless` permanently lock accrued creator fees if the creator's token account cannot receive transfers - ([File: programs/cp-swap/src/instructions/collect_creator_fee.rs])

### Summary
The analog matches: both `collect_creator_fee` and `collect_creator_fee_permissionless` transfer accumulated creator fees to a token account whose owner (`creator`) is fixed and immutable (recorded once at pool init in `pool_state.pool_creator`), and only reset the accrued fee counters to zero *after* a successful transfer. If that fixed destination account can never successfully receive the transfer (e.g., it becomes frozen by the mint's freeze authority, analogous to a USDC-style blacklist), the fee counters can never be reset and the accumulated fees become permanently unclaimable, exactly like the `Stream.sol#cancel()` pattern in the reference report.

### Finding Description
`collect_creator_fee` requires the `creator` signer to match `pool_state.pool_creator` [1](#0-0) , and both instructions derive/require the destination accounts as the creator's own associated token accounts (`associated_token::authority = creator`) [2](#0-1) . The fee transfer and counter reset are: [3](#0-2) 

The core transfer uses `transfer_checked` via `transfer_from_pool_vault_to_user`, which will fail (and thus abort the whole instruction, leaving `creator_fees_token_0`/`creator_fees_token_1` unchanged) if the destination token account cannot accept the transfer [4](#0-3) . The `collect_creator_fee_permissionless` variant has the identical pattern, so even a third party trying to help cannot route funds elsewhere [5](#0-4) .

There is no fallback: the destination account's owner (`creator`) is a fixed pubkey stored in `PoolState` at pool creation and cannot be changed by the pool creator or anyone else, and no other instruction exists to redirect or rescue these accrued creator fees to a different account. I found no admin/rescue path in `pool.rs`/`collect_creator_fee*.rs` that could reset or redirect these counters if the transfer permanently fails.

### Impact Explanation
If the creator's token account for token_0 or token_1 mint becomes permanently unable to receive tokens (e.g., the mint's freeze authority freezes that specific token account — the SPL-Token analog to an ERC-20 address blocklist), all future and already-accrued `creator_fees_token_0`/`creator_fees_token_1` become permanently locked inside the pool vault: neither `collect_creator_fee` nor `collect_creator_fee_permissionless` can ever succeed, and swaps continue to keep crediting the frozen counters, growing an unrecoverable balance. This is a permanent freeze of funds belonging to the pool creator, an explicitly in-scope actor role.

### Likelihood Explanation
Requires an external, token-issuer-controlled event (freezing/blacklisting a specific token account) rather than an attacker-forged transaction; it is not attacker-triggerable purely on-chain, but is a realistic and foreseeable condition for regulated stablecoins (e.g., USDC/USDT freeze functionality on Solana), matching the same risk class as the referenced Ethereum USDC blacklist issue. Given this is not directly triggerable by an unprivileged attacker's transaction alone, but relies on external token-level freezing, likelihood is Medium at best.

### Recommendation
Do not gate the reset of `creator_fees_token_0`/`creator_fees_token_1` on the transfer's success as a single atomic failure point. Consider: (1) allowing the recorded fees to be withdrawn to an alternate destination approved by the creator (e.g., a creator-provided arbitrary token account rather than a fixed ATA derived from `creator`), or (2) wrapping the transfer in a way that permits partial/deferred settlement so a frozen account for one mint does not block collection of the other mint's fees (already partially mitigated since the two transfers are separate calls, but both must succeed for `pool_state` fields to reset — verify whether a partial success leaves inconsistent state), or (3) adding an admin-guarded rescue path for stuck creator fees.

### Proof of Concept
1. A pool is created with `pool_creator` = address `C`, `vault_0_mint` = a token with freeze authority (e.g., a USDC-like SPL token).
2. Swaps accrue `creator_fees_token_0` in `pool_state`.
3. The mint's freeze authority freezes creator `C`'s associated token account for that mint (external action, not part of this program).
4. `collect_creator_fee` (or the permissionless variant) is called; `transfer_from_pool_vault_to_user` → `transfer_checked` CPI fails because the destination account is frozen [6](#0-5) .
5. The entire instruction reverts, so `pool_state.creator_fees_token_0` is never reset [7](#0-6) .
6. There is no alternative instruction to redirect or rescue these fees, so they remain permanently locked in `token_0_vault` while accruing indefinitely from further swaps.

```rust
pub fn collect_creator_fee(ctx: Context<CollectCreatorFee>) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;
```

```rust
pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
```
