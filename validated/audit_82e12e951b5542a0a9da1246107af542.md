### Title
Webhook organization-authentication bypass allows cross-organization stack targeting - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC `webhook_secret`) used to authenticate an inbound webhook based on `params.dig('repository','owner','login')`, but every event `Handler` resolves the actual `Stack`/`Repository` to act on from a completely different field of the same attacker-controlled JSON body: `payload.dig('repository','full_name')`. Nothing ties these two values together, so a request that is validly signed for organization A can name a repository belonging to organization B and have Shipit act on B's stacks.

### Finding Description
`verify_signature` picks the signing secret this way: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `repository.owner.login` (or `organization.login`) inside the same JSON body the attacker fully controls, and `Shipit.github(organization: repository_owner)` is used only to fetch that organization's `webhook_secret` for HMAC verification via `verify_webhook_signature`: [3](#0-2) .

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw parsed body to handlers [4](#0-3) . Every handler resolves its target `Stack`/`Repository` from `payload.dig('repository', 'full_name')`, not from `repository.owner.login`: [5](#0-4) . This pattern repeats identically in `PushHandler` (via `stacks`) [6](#0-5) , `CheckSuiteHandler` [7](#0-6) , and the pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.), all of which call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [8](#0-7) .

Because Shipit explicitly supports hosting multiple independent GitHub Apps/organizations from one instance (`docs/setup.md` "Using Multiple Github Applications", `lib/shipit.rb#github`/`github_app_config`) [9](#0-8) , each configured organization has its own `webhook_secret` known to that organization's own GitHub App owner. That owner can legitimately compute a valid HMAC signature over an arbitrary JSON body (simply by configuring their own App's webhook delivery, or replaying/crafting a POST to Shipit's webhook endpoint directly with their own secret), because nothing requires the webhook to actually originate from GitHub for organization A's real repositories — it only requires the raw body's `repository.owner.login`/`organization.login` to equal "A" while `repository.full_name` can be set to `"OrgB/private-repo"`. This breaks the intended binding: *the organization whose secret authenticated the request* must equal *the organization owning the repository whose stack is written to*.

### Impact Explanation
This crosses an authentication boundary between tenants/organizations sharing a single Shipit installation: an org that only "authenticated" as itself (via its own legitimate webhook secret) can force Shipit to act on another organization's `Stack`s/`Repository` records — a cross-repository write reachable without any Shipit session, `ApiClient` token, or GitHub write access to the victim's repository. Concretely:
- `PushHandler` will invoke `stack.sync_github(expected_head_sha:)` on the victim stack for an attacker-chosen branch/SHA claim, mutating commit history state (`GithubSyncJob#perform`) and triggering deploy-spec caching for a stack the attacker does not own.
- `CheckSuiteHandler`/`StatusHandler` can inject forged check-run refresh triggers or commit statuses onto the victim's commits, which can influence downstream deploy/merge gating logic that consults commit status/check state.
- PR handlers can archive/unarchive or otherwise mutate victim `ReviewStack`s tied to another organization's repository.

Because the actual GitHub API calls made by `sync_github`/`GithubSyncJob` use the victim stack's own `github_app` (`Shipit.github(organization: owner)` resolved from the `Repository` record, not from the forged payload), this is not raw RCE/credential theft, but it is an authenticated-boundary violation causing unauthorized cross-organization state changes/writes on stacks that belong to a different tenant, satisfying the "cross-repository writes" criterion.

### Likelihood Explanation
Exploitability requires the attacker to control (or know) the `webhook_secret` for *some* organization already configured in the same Shipit instance — i.e., they must be an owner/admin of one of the multiple GitHub Apps Shipit is configured to serve, which is a realistic multi-tenant deployment scenario explicitly documented and supported by this engine. No Shipit session, `ApiClient` token, or GitHub write access on the *victim* org/repo is required, and the victim repository/stack must already be registered in Shipit (which is the normal state for any actively used stack). This is fully server-side reachable via a single crafted POST to `/webhooks`.

### Recommendation
Bind the verified signature's organization to the resource being mutated: after `verify_signature` succeeds, re-derive/require that `repository_owner` (the organization whose secret validated the HMAC) matches the owner embedded in `payload.dig('repository', 'full_name')` (and, transitively, the `Repository#owner` actually resolved by each handler) before dispatching to any handler. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Shipit is configured with two GitHub Apps/orgs, `OrgA` and `OrgB`, per `docs/setup.md`'s multi-org config; `OrgB` has a legitimate `Stack` for `OrgB/private-repo` already registered.
2. An attacker who administers `OrgA`'s GitHub App (and thus knows `OrgA`'s `webhook_secret`) crafts:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>
Body:
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/private-repo"
  }
}
```
3. `WebhooksController#verify_signature` computes `repository_owner == "OrgA"`, fetches `OrgA`'s `webhook_secret`, and the signature verifies successfully.
4. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `repository_name`/`stacks` resolve `full_name == "OrgB/private-repo"`, and `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` is invoked on `OrgB`'s stack — a write the attacker has no legitimate authority to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
