### Title
Webhook signature verification binds to an attacker-chosen organization while the Status handler writes to an unrelated commit/stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the inbound webhook against using `repository_owner`, a value read directly out of the untrusted JSON body: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` returns `true` unconditionally whenever the resolved app's `webhook_secret` is blank: [3](#0-2) 

Multi-organization installs are an explicitly documented configuration (`docs/setup.md`, `config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`), and a blank `webhook_secret` per organization is a supported value (e.g. `OrgTwo` in the fixture config). Any attacker who knows (or guesses) the login of one configured organization that has no `webhook_secret` set can therefore make `verify_signature` pass with zero knowledge of any secret, simply by setting `repository.owner.login` (or `organization.login`) to that org's name in a hand-crafted POST body.

Once the signature check passes, the actual handler dispatch never re-checks that the field used for signature scoping (`repository.owner.login`) matches the field the handler acts on. `Shipit::Webhooks::Handlers::StatusHandler#process` is the most severe case: it resolves target commits purely by SHA, with **no repository/stack scoping at all**: [4](#0-3) 

This binding break is: `organization that authenticated the webhook` (attacker-chosen, blank-secret org) ≠ `repository/stack that is actually written` (any stack in the entire Shipit instance whose commit SHA happens to match, regardless of organization). The base `Handler` class also derives the acting scope only from `payload.dig('repository', 'full_name')`, a second, independently attacker-controlled field never covered by the org used to select the verifying secret: [5](#0-4) 

### Impact Explanation
Commit SHAs of any GitHub repository (including private ones the attacker cannot otherwise access, if they're mirrored in commit messages/PRs, or public repos) are not secrets — they are routinely visible on GitHub, in PRs, in CI logs, etc. Using the blank-secret organization as the authentication anchor, an attacker can POST a forged `status` event carrying an arbitrary victim commit `sha` and `state: success`, causing `Commit#create_status_from_github!` to persist a forged CI status for a commit belonging to a completely different, properly-secured organization/stack.

This forged status is consumed by:
- `MergeRequest#any_status_checks_failed?` / `#any_status_checks_missing?` via `StatusChecker`, which gate the Shipit merge queue (auto-merge of pull requests), and
- `Stack#deployment_checks_passed?` / `#deployable?`, which gate whether a deploy can proceed.

Successfully spoofing a passing status can therefore unblock an unauthorized automatic merge or deploy for a stack the attacker has no legitimate relationship to — matching the Critical impact category "unauthorized deploy, rollback, or merge."

### Likelihood Explanation
Exploitation requires only: (1) the Shipit instance host multiple GitHub App organizations where at least one has no `webhook_secret` configured (an explicitly documented, supported configuration), and (2) knowledge of a target commit SHA on any other monitored stack (public information). No GitHub push/write access, no `ApiClient` token, no webhook secret of the target organization, and no privileged Shipit account are needed — it is a pure unauthenticated HTTP POST to the public webhook endpoint.

### Recommendation
After `verify_signature` succeeds, cross-check that the organization/app used for verification actually matches the repository the handler is about to act on (e.g., derive both `repository_owner` and `repository_name` from the same trusted source and reject if the resolved `Repository`'s `owner` differs from the verified app's organization). Additionally, scope `StatusHandler#process` (and other handlers) to the specific repository identified in the verified payload rather than performing a global, repository-agnostic `Commit.where(sha: ...)` lookup. Treat a blank `webhook_secret` as "verification not possible" rather than "always verified" when the instance has other organizations configured with real secrets.

### Proof of Concept
1. Configure/observe that Shipit instance has organization `OrgTwo` (or any org) with `webhook_secret: nil` alongside a properly secured organization `OrgOne` hosting the real target stack (matches documented multi-org config in `test/dummy/config/secrets_double_github_app.yml`).
2. Identify a commit SHA `S` belonging to a stack under `OrgOne` that is pending/missing a required CI status (public info, e.g. from the GitHub commit page).
3. POST to the Shipit webhooks endpoint with header `X-Github-Event: status` and body:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/victim-repo" }
}
```
No `X-Hub-Signature` value needs to be valid for `OrgOne`; `verify_signature` resolves `Shipit.github(organization: "OrgTwo")` (via `repository_owner`), whose `verify_webhook_signature` returns `true` unconditionally because `OrgTwo`'s `webhook_secret` is blank.
4. `StatusHandler#process` runs `Commit.where(sha: "S").each { |c| c.create_status_from_github!(params) }`, writing a forged `success` status onto the target commit under `OrgOne`, independent of which organization actually authenticated the request.
5. If this satisfies the last missing required status, the corresponding `MergeRequest` becomes mergeable or the `Stack` becomes deployable, despite the request never being authenticated against `OrgOne`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
