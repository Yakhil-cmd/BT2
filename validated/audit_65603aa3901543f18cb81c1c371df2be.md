### Title
Cross-Tenant Webhook Forgery — Signature Verified Against `repository.owner.login`/`organization.login` While Handlers Mutate State Keyed by Unrelated Payload Fields (`repository.full_name`, `sha`) — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/org secret to validate a webhook against using a field pulled straight out of the *unverified* JSON body (`repository.owner.login` or `organization.login`), then verifies the HMAC over the whole raw body with that org's secret. Once verification passes, the event handlers act on completely different payload fields (`repository.full_name` for push/pull_request handlers, and a bare `sha` lookup with **no repository scoping at all** for `StatusHandler`) to decide which tenant's data to mutate. Nothing ties the org whose secret validated the signature to the repository/commit that is actually written. Any org configured on a shared multi-tenant Shipit instance can therefore forge webhook deliveries that write into another tenant's stacks.

### Finding Description
The binding that should hold is:

`organization whose webhook_secret authenticated the request == organization/repository whose state the handler mutates`

`verify_signature` resolves the signing key like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the attacker-supplied, not-yet-verified JSON body (`params.dig('repository','owner','login')` / `params.dig('organization','login')`). `Shipit.github(organization: repository_owner)` then looks up that org's dedicated `webhook_secret` from the multi-tenant config keyed by GitHub org name: [3](#0-2) 

The HMAC (`verify_webhook_signature`) is computed over the *entire* raw body, so anyone who legitimately knows one org's `webhook_secret` (e.g., because they configured or were given it for their own onboarded org "OrgA") can sign **any** JSON payload, including one where `repository.owner.login == "OrgA"` (satisfying signature lookup) but every other field — `repository.full_name`, `sha`, commit metadata, etc. — points at a completely different tenant "OrgB".

Once the signature check passes, `create` dispatches the raw params to the event handler: [4](#0-3) 

Most handlers scope by `repository.full_name` via `Handler#stacks`: [5](#0-4) 

— which is never cross-checked against `repository.owner.login` used for signature selection, so an attacker can set `repository.owner.login = "OrgA"` (their own org, to pass the signature check) while `repository.full_name = "OrgB/some-repo"` (the victim tenant).

`StatusHandler` is worse — it doesn't even scope by repository/org, only by commit `sha`, which is globally unique across the whole Shipit instance: [6](#0-5) 

So a validly-signed (with OrgA's secret) `status` event whose `sha` matches a commit belonging to OrgB's stack will create a forged `Status` on OrgB's commit, with attacker-chosen `state`, `context`, `description`, `target_url`.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated" vs. "repository that is written." An attacker who has legitimate visibility into their own org's `webhook_secret` (a normal, unprivileged onboarding artifact for org "OrgA" on a shared multi-tenant Shipit deployment) can:
- Forge a `status` event with a fabricated "success"/passing CI status attached to any commit SHA on any other tenant's stack tracked by the same Shipit instance, via `Commit.create_status_from_github!` (no cross-tenant authorization check).
- If that victim stack gates deploys on `deployable_status`/required CI checks, the forged status can satisfy the deploy gate, producing an **unauthorized deploy** of a commit that never actually passed the real CI pipeline for that repository — a cross-tenant integrity/authorization bypass.
- Similarly forge `push`/`pull_request`/`check_suite` events referencing an arbitrary `repository.full_name`, triggering resyncs, review-stack archival/unarchival, or team/membership operations against repositories the attacker's org has no relation to.

This satisfies the Critical bar of "cross-repository writes" and "an unauthorized deploy."

### Likelihood Explanation
Any org that is legitimately configured in the multi-tenant `secrets.github` map (i.e., any customer/tenant onboarded to the shared Shipit instance) already possesses their own `webhook_secret` value (it is set by the org admin in their own GitHub App settings, per `docs/setup.md`). No privileged Shipit session, API token, or GitHub write access to the victim repo is required — only knowledge of one's own webhook secret and the ability to craft an HTTP POST with a matching HMAC, which is standard, unprivileged capability for anyone administering a GitHub App webhook for their own org.

### Recommendation
After computing `repository_owner`/`organization` and verifying the signature, re-derive the same identity from the fields the handlers actually use for authorization (`repository.full_name`'s owner, and for `StatusHandler`, the resolved commit's stack/repository owner) and reject the request (422) if they don't match the org whose secret validated the signature. `StatusHandler` should also scope its `Commit` lookup to a repository resolved consistently with the verified organization, not perform a global `Commit.where(sha:)` scan.

### Proof of Concept
1. Attacker legitimately administers GitHub App/org `"OrgA"`, one of several tenants configured under `secrets.github` on a shared Shipit instance, and knows `OrgA`'s `webhook_secret`.
2. Attacker identifies a commit SHA belonging to `OrgB`'s tracked stack (SHAs are often public/guessable via GitHub).
3. Attacker builds body:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/dummy"},
  "sha": "<OrgB commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://attacker.example"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and sends `POST /webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner = "OrgA"`, fetches `OrgA`'s `GitHubApp`, and `verify_webhook_signature` succeeds (attacker signed correctly with OrgA's real secret). [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (no org/repo filter) and creates a forged "success" status on OrgB's commit. [6](#0-5) 
7. If `OrgB`'s stack requires that `context` to be green before deploy, the stack now shows as deployable based on a forged, cross-tenant status — an unauthorized deploy path.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
