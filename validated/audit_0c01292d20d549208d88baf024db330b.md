### Title
`recalculate_stake_rewards` recomputes unpaid partitioned rewards from live `StakesCache` state, letting a staker's post-calculation Split/Deactivate change their own frozen reward amount across snapshot-restore boundaries - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`Bank::recalculate_stake_rewards`, invoked only when a bank is re-initialized after a snapshot restore mid-distribution, recomputes each unpaid stake's reward using the **current** `StakesCache` delegation fields instead of the delegation state that was frozen when `calculate_rewards_for_partitioning` ran at the epoch boundary. Because `Split`/`Deactivate` on a not-yet-paid stake account are ordinary unprivileged owner instructions that can land in blocks during the multi-slot distribution window, an attacker can make their own unpaid `stake_pubkey` recompute to a different `stake_reward`/`InflationReward.stake` on a node that restarts from a snapshot than on a node that runs continuously and keeps paying the originally frozen value.

### Finding Description
`Bank::recalculate_stake_rewards` [1](#0-0)  is documented to build its stake set "from... stake accounts from StakesCache" — i.e., from the live bank state at the moment of snapshot restore, not from a copy of delegation state captured at the original epoch-boundary calculation:

```
let stakes = self.stakes_cache.stakes();
let EpochRewardCalculateParamInfo { stake_history, stake_delegations, cached_vote_accounts } =
    self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
``` [2](#0-1) 

While `point_value` (total rewards/points, the epoch-wide denominator) is frozen from `epoch_rewards_sysvar` [3](#0-2) , the per-stake numerator is not: `calculate_stake_rewards_and_commissions` → `redeem_delegation_rewards` → `redeem_rewards` → `redeem_stake_rewards` → `calculate_stake_rewards` → `calculate_stake_points_and_credits` all operate on the `Stake`/`Delegation` pulled fresh from `stake_delegations_vec()`. Inside, `tower_epoch_credits_iter`/`calculate_alpenglow_points` compute `stake_amount = delegation_effective_stake(&stake.delegation, epoch, stake_history, ...)` [4](#0-3)  and `redeem_stake_rewards` further mutates/uses `stake.delegation.stake` and its activation status directly from the live account [5](#0-4) .

`Split` and `Deactivate` are ordinary unprivileged stake-program instructions the attacker can issue against their own account: `Split` reduces the original account's `delegation.stake`, and `Deactivate` sets `deactivation_epoch`. Neither instruction is blocked by the reward-distribution machinery, and there is no snapshot of the individual stake's `Delegation` fields taken at the original `calculate_rewards_for_partitioning` call to compare against on recalculation — unlike the Alpenglow *denominator* (`RewardEpochDelegatedStakes`), which the code explicitly freezes and is regression-tested by `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` [6](#0-5) . That test only proves the total-stake denominator is stable; it does not exercise mutation of the individual unpaid stake's own delegation between distribution and recalculation.

`recalculate_partitioned_rewards_if_active` then unconditionally overwrites `epoch_reward_status` with these recomputed values via `set_epoch_reward_status_distribution` [7](#0-6) , so the recomputed (and now possibly different) reward becomes the value actually paid out by `distribute_partitioned_epoch_rewards` on the restarted node.

### Impact Explanation
A node that continues operating through the distribution window pays out the reward value fixed at the epoch boundary for every unpaid `stake_pubkey`. A node that instead reloads from a snapshot taken mid-distribution recomputes and pays a **different** amount for the same `stake_pubkey`/partition/epoch if that staker issued `Split` or `Deactivate` in between. This is a scoped, attacker-triggerable reward-miscalculation/divergence bug: it can misattribute lamports to (or away from) the attacker's own account and, because reward crediting affects account state included in bank hash, can produce state divergence between validators that took different code paths for the identical target slot — mapping to Agave's "misattributed/duplicated rewards" and "cross-node state divergence" bounty categories.

### Likelihood Explanation
Preconditions are realistic and fully within an unprivileged user's control: own a delegated stake account, wait for at least one epoch's rewards to begin partitioned distribution, submit `Split`/`Deactivate` on the same still-unpaid account before some subset of validators restart from a snapshot taken mid-distribution (a routine event — restarts, catch-up from snapshot, etc., are common cluster operations, not attacker-controlled but reliably occurring across a large validator set over time). The exploit requires no special timing precision beyond "before recalculation runs" and is deterministically reproducible in a unit test, as the existing `test_recalculate_stake_rewards`/`test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` test scaffolding already demonstrates the exact call sequence needed.

### Recommendation
Snapshot the per-stake `Delegation`/`Stake` fields (stake amount, activation_epoch, deactivation_epoch) used for reward calculation together with the `PartitionedStakeReward` at the original `calculate_rewards_for_partitioning` time, and have `recalculate_stake_rewards` recompute strictly from that frozen per-stake snapshot (analogous to how `RewardEpochDelegatedStakes` freezes the denominator) rather than re-reading `StakesCache`'s current delegation for the numerator. Alternatively, detect any stake_pubkey whose live delegation differs from its calculation-time delegation and reuse the originally-computed `PartitionedStakeReward` entry unchanged for that pubkey on recalculation.

### Proof of Concept
Extend `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`-style scaffolding (or `test_recalculate_stake_rewards`) as follows:

```rust
#[test]
fn test_split_between_distribution_and_recalculation_changes_reward() {
    // 1. Build a reward bank with >=2 delegations, distribute over >=2 partitions
    //    (as in create_reward_bank_with_specific_stakes).
    // 2. Capture EpochRewardPhase::Calculation.all_stake_rewards -> record
    //    (unpaid_index, unpaid_reward) for a stake_pubkey NOT in the first
    //    distributed partition.
    // 3. bank.set_epoch_reward_status_distribution(...) with only the first
    //    partition index, then bank.distribute_partitioned_epoch_rewards().
    // 4. As the OWNER of `unpaid_reward.stake_pubkey` (unprivileged), submit a
    //    Split instruction (or Deactivate) against that stake account via
    //    process_transaction, reducing/altering its Delegation fields.
    // 5. Call bank.recalculate_stake_rewards(&epoch_rewards_sysvar, &thread_pool)
    //    to simulate the post-snapshot-restore path.
    // 6. Assert:
    assert_ne!(
        unpaid_reward.inflation.stake_reward,
        recalculated_stake_rewards
            .enumerated_rewards_iter()
            .find_map(|(_, r)| (r.stake_pubkey == unpaid_reward.stake_pubkey).then_some(r))
            .unwrap()
            .inflation
            .stake_reward,
        "reward for the same unpaid stake_pubkey diverged after an owner-issued \
         Split/Deactivate landed between distribution and post-restart recalculation"
    );
}
```
Expected result on current code: the assertion fires (values differ), demonstrating that the same `stake_pubkey`, epoch, and partition produce two different, both-deterministic reward outcomes depending solely on whether the node restarted mid-distribution — violating the reward-exactly-once-at-fixed-value invariant.
