## Title
Feature-gated payload verification allows a multisig owner to execute an unapproved transaction payload - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`multisig_account::create_transaction` stores the *full* transaction payload on chain and other owners vote (approve/reject) against that specific stored payload. At execution time, `validate_multisig_transaction` is supposed to guarantee that the payload actually executed is the one the owners approved. However, that guarantee is only enforced when the `abort_if_multisig_payload_mismatch` feature flag is enabled — otherwise an executing owner can supply an arbitrary `payload` argument at execution time that differs from the one stored on-chain and voted on by co-owners, and it will still pass admission because only the vote *count* is checked, not the vote *content*.

### Finding Description
`create_transaction` stores the full payload optimistically (`payload: option::some(payload)`, `payload_hash: option::none()`): [1](#0-0) 

Other owners call `approve_transaction` / `reject_transaction`, which only record a vote against the `sequence_number`, with no re-verification of what payload they are approving beyond what was originally stored: [2](#0-1) 

The admission-time check that is supposed to bind the executed payload to the approved one is `validate_multisig_transaction`, invoked by the VM as part of the transaction prologue (both during mempool validation and execution): [3](#0-2) 

Critically, when the transaction was created with `create_transaction` (full payload, no hash), `transaction.payload_hash.is_some()` is `false`, so the hash-comparison branch is skipped entirely. The only remaining check that could catch a substituted payload is:
```
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
```
This check is gated behind the `abort_if_multisig_payload_mismatch` feature flag. If that flag is not enabled on a given network/environment, the executing owner (who only needs quorum of *approval count*, not approval of the actual bytes being run) can pass any `payload` bytes into the `MultisigTransaction` type at execution time, and the module will execute it as the multisig account's signer with only the vote-count check (`num_approvals >= num_signatures_required`) passing — never verifying that the executed bytes match what was actually voted on.

This is a direct admission-boundary analog of the `swapLiquidity` bug class: the "approval" (multisig votes) is bound only to a `sequence_number`/quorum count, not cryptographically/structurally bound to the specific payload content unless an optional, feature-gated check is turned on. An attacker (any single owner with enough approvals, potentially by colluding with itself if it is also a threshold-meeting owner, or after other owners' approvals accumulate for a transaction id) can redirect the multisig's authority to execute a completely different, unapproved entry function/script.

### Impact Explanation
If `abort_if_multisig_payload_mismatch` is disabled, a rogue or compromised owner who is one of the executors of an approved multisig transaction (id N) can substitute the payload with something else entirely (e.g., a fund transfer to their own address, an owner-list modification, module upgrade authorization, etc.) while the on-chain vote records still show "approved" for the original, different intent. This breaks the fundamental multisig approval-set binding invariant — the executed action is not the one other signers actually consented to — and could result in unauthorized fund transfers or account takeover of the multisig account, i.e., high/critical impact.

### Likelihood Explanation
Exploitability is entirely gated by whether `abort_if_multisig_payload_mismatch` is active in the target environment. I was not able to conclusively confirm from the indexed code/doc content whether this flag defaults to enabled on Aptos mainnet or is still an opt-in/rollout flag (the feature definition and default state live in `features.move`, whose relevant section I could not fully read due to index truncation). If the flag is not yet enabled by default everywhere the module is deployed, this is directly exploitable by any owner without any additional privilege beyond being included as an owner/executor of an in-flight transaction; if it is already default-on everywhere, the issue is dormant/mitigated (similar to the original report's fix pattern of adding a mismatch check gated behind a flag as the remediation, rather than fixing the invariant unconditionally).

### Recommendation
Enforce payload-consistency verification for `create_transaction` (full-payload) transactions unconditionally instead of gating it behind `abort_if_multisig_payload_mismatch_enabled`, i.e., always store a payload hash together with (or instead of) the raw payload and always verify submitted execution payload against it. Ensure this feature flag defaults to enabled across all live networks and eventually retire the flag once fully rolled out, so the payload actually executed by a `MultisigTransaction` is cryptographically guaranteed to be the one that received owner approvals.

### Proof of Concept
Not independently verified end-to-end due to inability to confirm the current default state of `abort_if_multisig_payload_mismatch` in this index (see Likelihood Explanation). Conceptual PoC:
1. Owner A calls `create_transaction(multisig_account, payload_X)` (transfer 10 APT to charity), which stores `payload_X` in full (no hash).
2. Owners B and C call `approve_transaction` believing they are approving `payload_X`.
3. Once quorum is reached, Owner A (or any owner attempting to execute) submits a `MultisigTransaction` execution with a different `payload_Y` (e.g., transfer all funds to Owner A's own address).
4. If `abort_if_multisig_payload_mismatch_enabled()` is false, `validate_multisig_transaction` skips both the (absent) hash check and the payload-equality check, and `payload_Y` executes with the multisig account's authority despite never having been approved by B or C. [4](#0-3)

    public entry fun create_transaction(
        owner: &signer,
        multisig_account: address,
        payload: vector<u8>,
    ) {
        assert!(payload.length() > 0, error::invalid_argument(EPAYLOAD_CANNOT_BE_EMPTY));

        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);

        let creator = address_of(owner);

            payload: option::some(payload),
            payload_hash: option::none<vector<u8>>(),
            votes: simple_map::create<address, bool>(),
            creator,
            creation_time_secs: now_seconds(),
        };
        add_transaction(creator, multisig_account, transaction);
    }

    /// Called by the VM as part of transaction prologue, which is invoked during mempool transaction validation and as
    /// the first step of transaction execution.
    ///
    /// Transaction payload is optional if it's already stored on chain for the transaction.
    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }
