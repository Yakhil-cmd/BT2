### Title
Unbounded `RemoteProxyProof::RelayChain.proof` trie-node vector lets an attacker charge fixed weight for arbitrarily large trie verification, causing collator block-time overruns - (File: pallets/remote-proxy/src/lib.rs)

### Summary
`Pallet::remote_proxy` charges a **fixed** benchmarked weight (`WeightInfoOf::<T,I>::remote_proxy()`) regardless of the size of the attacker-supplied `proof: Vec<Vec<u8>>`, while `do_remote_proxy` builds an in-memory trie DB from that proof and performs `sp_trie::read_trie_value` against it. Because the weight annotation does not scale with `proof.len()` or the number/size of nodes, a signed account can submit a maximal, well-formed-but-bloated proof to make verification take far longer than the weight paid for, allowing repeated CPU-time overruns during block execution.

### Finding Description
`remote_proxy` is a signed extrinsic dispatched via `#[pallet::call_index(0)]` [1](#0-0) . Its declared weight is:
```
WeightInfoOf::<T, I>::remote_proxy()
    .saturating_add(T::DbWeight::get().reads_writes(1, 1))
    .saturating_add(di.call_weight)
``` [2](#0-1) 

`WeightInfoOf::<T,I>::remote_proxy()` resolves to a constant produced by benchmarking with a single small proof (measured proof size `105` bytes in the AssetHub‑Kusama generated weights) [3](#0-2) , and the benchmark itself only ever constructs a proof for one storage key via `create_remote_proxy_proof` [4](#0-3) . The `proof` field type is an unbounded `Vec<Vec<u8>>` with no `MaxEncodedLen`/`BoundedVec` restriction: `RelayChain { proof: Vec<Vec<u8>>, block: RemoteBlockNumber }` [5](#0-4) .

At execution time, `do_remote_proxy` takes this attacker-supplied `proof` and builds a full in-memory trie database, then walks the trie to fetch a single key:
```
let db = sp_trie::StorageProof::new(proof).into_memory_db::<RemoteHasherOf<T, I>>();
let value = sp_trie::read_trie_value::<sp_trie::LayoutV1<_>, _>(&db, &storage_root, &key, None, None)
``` [6](#0-5) 

`sp_trie::StorageProof::new` and `into_memory_db` hash and insert every node the attacker supplies into the DB regardless of whether it is actually needed to resolve `key`; only afterwards does `read_trie_value` attempt the lookup and return `InvalidProof` if the path is not satisfied. There is no check anywhere in this pallet (or in `RemoteProxyInterface`) that bounds the number of proof nodes or total proof byte length before this expensive hashing/insertion work is performed. The only gate is `Error::InvalidProof` returned *after* the DB has already been built from however many nodes were supplied.

The weight charged is fixed and derived from a benchmark that never exercises a large or adversarial trie proof, so there is a structural mismatch between the weight model (`O(1)` in proof size) and the actual computational cost of `into_memory_db`/`read_trie_value`, which is `O(number_of_nodes * node_size)` for hashing plus trie traversal.

### Impact Explanation
This is a weight-accounting bug in a user-callable extrinsic reachable by any signed account (no special privilege, proxy setup, or governance action required — just `RuntimeOrigin::signed(who)` calling `remote_proxy`). If the mismatch between charged weight and actual CPU cost is large enough, transactions with bloated proofs can consume disproportionate execution time relative to what they paid for, degrading block production throughput on the specific chain that includes `pallet_remote_proxy` (e.g. Asset Hub Polkadot/Kusama, per the module config in `relay/*/constants/src/lib.rs`). The impact is bounded by the maximum extrinsic/PoV size the runtime's `BlockLength`/transaction-byte fee allow (not unbounded), and by the transaction-fee cost of a large call (proof bytes still cost `TransactionByteFee`), which limits — but does not eliminate — the incentive/ability to submit outsized proofs. This is a resource/weight-accounting concern rather than a proven "network-wide halt or permanently stuck queue": there is no state corruption, no fund loss, and no permanent blockage — worst case is repeated per-block CPU overrun proportional to how oversized a proof a submitter is willing to pay transaction fees for.

### Likelihood Explanation
Feasibility is moderate: an attacker only needs a signed account with enough balance to pay the transaction fee (which scales with proof byte length via `TransactionByteFee`), and can pack the `proof: Vec<Vec<u8>>` with a large number of well-formed trie nodes (siblings/branches) up to the runtime's normal-class block length limit. This is a real, unprivileged, repeatable extrinsic path (no admin/governance gate), so the attack can be attempted every block, subject to the attacker's willingness to pay per-transaction fees proportional to the proof size. It's a genuine weight-benchmarking gap, but the transaction-fee cost of large proofs and the block-length cap constrain the severity below a full network halt or permanent queue stall.

### Recommendation
- Charge weight proportional to the actual size/complexity of the supplied `proof` (e.g., use `proof.iter().map(|n| n.len()).sum()` and/or `proof.len()` as a benchmarked linear component of the `remote_proxy`/`remote_proxy_with_registered_proof` weight functions), similar to how PoV-size-dependent operations are benchmarked elsewhere.
- Enforce an explicit maximum on the number of proof nodes and/or total proof byte size (e.g., a `MaxProofNodes`/`MaxProofSize` config constant with an `ensure!` check) before calling `StorageProof::new(...).into_memory_db()`.
- Re-benchmark `remote_proxy()` and `remote_proxy_with_registered_proof()` using worst-case (maximum-size) proofs so the declared `WeightInfo` bound genuinely reflects worst-case execution time.

### Proof of Concept
Rust benchmark/fuzz test plan (in `pallets/remote-proxy/src/tests.rs` or a new bench):
1. Build a trie with a deep/wide structure containing many large sibling nodes not on the path to the target key, using `sp_trie::TrieDBMutBuilder` as in `RemoteProxyImpl::create_remote_proxy_proof` [7](#0-6) , but insert e.g. 10k unrelated large-value keys before inserting the actual proxy definition, then generate a full proof (`sp_state_machine::prove_read`) that necessarily returns many nodes.
2. Call `RemoteProxy::remote_proxy(RuntimeOrigin::signed(1), anon, None, call, RemoteProxyProof::RelayChain { proof: <bloated_proof>, block: 1 })` and measure wall-clock time via `std::time::Instant` around the call.
3. Assert: `elapsed_time_for_bloated_proof` significantly exceeds the wall-clock time for the benchmark's small single-key proof (`remote_proxy_works` test) while the dispatched weight for both remains `WeightInfoOf::<T,I>::remote_proxy()` (i.e., unchanged) — demonstrating the fixed weight does not bound the measured cost.
4. Expected assertion: `measured_time(bloated_proof) > K * measured_time(baseline_proof)` for some threshold `K`, while `pallet::weight(...)` output is identical in both cases — proving the invariant "declared weight bounds execution cost" is violated for large adversarial proofs.

	#[cfg(feature = "runtime-benchmarks")]
	fn create_remote_proxy_proof(
		caller: &u64,
		proxy: &u64,
	) -> (RemoteProxyProof<Self::RemoteBlockNumber>, u64, H256) {
		use sp_trie::TrieMut;

		let (mut db, mut root) = sp_trie::MemoryDB::<BlakeTwo256>::default_with_root();
		let mut trie =
			sp_trie::TrieDBMutBuilder::<sp_trie::LayoutV1<_>>::new(&mut db, &mut root).build();

		let proxy_definition = vec![ProxyDefinition::<u64, ProxyType, u64> {
			delegate: *caller,
			proxy_type: ProxyType::default(),
			delay: 0,
		}];

		trie.insert(&Self::proxy_definition_storage_key(proxy), &proxy_definition.encode())
			.unwrap();
		drop(trie);

		(
			RemoteProxyProof::RelayChain {
				proof: db.drain().into_values().map(|d| d.0).collect(),
				block: 1,
			},
			1,
			root,
		)
	}
