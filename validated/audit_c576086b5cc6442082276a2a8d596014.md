### Title
Webhook signature verification keys off `repository.owner.login`, but the acted-upon target is resolved from the independent `repository.full_name` field, allowing cross-organization event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret to verify a webhook against using `repository_owner`, a value read directly out of the untrusted, not-yet-verified JSON body. Once verification "succeeds", every `Handler` subclass resolves the actual `Stack`/`Repository` to mutate using a different field of the same payload, `repository.full_name`. Nothing enforces that the organization whose secret validated the signature is the same organization that owns the repository being acted on. This is directly analogous to the reported bug class: a value that gates a privileged action (`endTime`/minted-count check) is not the same value that the signature/authorization actually covers (`mintReceipt` ignoring `endTime`).

### Finding Description
In `verify_signature`: [1](#0-0) 
the secret used to HMAC-verify the raw POST body is chosen by:
```ruby
github_app = Shipit.github(organization: repository_owner)
```
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`params` here is `JSON.parse(request.raw_post)` — fully attacker-controlled content, parsed *before* the signature is checked. So the "organization" used to pick the verifying secret is itself untrusted at the moment it's chosen; only the eventual signature match constrains anything.

Once the signature check passes (using whatever org's secret the attacker aimed at), the actual work is dispatched to a `Handler`: [2](#0-1) 
Every handler resolves its target stack via: [3](#0-2) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`repository.owner.login` (used for authentication/secret selection) and `repository.full_name` (used for the write target) are **independent JSON fields in the same attacker-authored body** — there is no cross-check that `full_name`'s owner segment matches `owner.login`. `PushHandler` illustrates the exploitable target: [4](#0-3) 
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
```

Concrete equality that should hold but doesn't:
`organization whose webhook_secret authenticated the request == owner(repository.full_name) that the Handler mutates`

Before the attack: for a Shipit instance hosting stacks for both `OrgA/foo` and `OrgB/bar` (two organizations/GitHub Apps each with their own `webhook_secret` in `secrets.github`), only someone holding `OrgA`'s webhook secret can forge events that pass verification, and legitimately those events should only describe `OrgA`'s repositories.

After the attack: an actor who has `OrgA`'s webhook secret (e.g., a GitHub App installer/admin for `OrgA`, who has no privileges whatsoever over `OrgB`) can send a JSON body where `repository.owner.login = "OrgA"` (so `verify_signature` selects and matches `OrgA`'s secret) but `repository.full_name = "OrgB/bar"`. `Handler#repository_name` picks up `"OrgB/bar"` and the handler operates on `OrgB`'s `Stack`, entirely bypassing the fact that `OrgB`'s secret was never presented.

### Impact Explanation
This lets a party who is unprivileged with respect to `OrgB` (only privileged for `OrgA`) forge `push`, `status`, and `check_suite` events against `OrgB`'s stacks:
- Forged `push` events trigger `GithubSyncJob` for arbitrary target stacks (`app/models/shipit/webhooks/handlers/push_handler.rb:16`), causing unwanted resyncs/state churn on repositories the attacker has no authorization over.
- Forged `status`/`check_suite` events can inject fabricated commit statuses/check-run refresh triggers for `OrgB`'s commits (via the same `repository_name`-based target resolution), which can influence CI-derived deployability/merge gating decisions Shipit relies on for deploys and merges.

This breaks the intended per-organization isolation between tenants of a single Shipit instance and can influence deploy/merge-readiness state for a repository the caller does not control, which aligns with the engine's "unauthorized deploy"-adjacent risk bucket once combined with status-gated automatic deploys/merges.

### Likelihood Explanation
Requires the attacker to already hold a valid `webhook_secret` for *some* organization configured in the multi-tenant Shipit deployment (their own), which is a realistic scenario in any Shipit instance serving more than one GitHub organization/App installation — it does not require compromising the target organization's secret, a Shipit session, or an `ApiClient` token. The only extra step is constructing a JSON body where `repository.owner.login` and `repository.full_name` disagree, which is trivial.

### Recommendation
In `Handler#repository_name`/`stacks`, cross-check that the owner segment of `repository.full_name` (or `repository.owner.login`) matches the organization actually used to verify the signature (i.e., pass `repository_owner` from the controller into the handler and assert equality before resolving the target `Repository`). Alternatively, verify the signature using a secret bound to the resolved repository's owner (derived from `full_name`), not a separately-read `owner.login` field, so a single consistent field drives both authentication and authorization of the target.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `github.webhook_secret` (multi-tenant `Shipit.github(organization:)` config), and a `Stack` tracking `OrgB/bar`.
2. As a party holding only `OrgA`'s webhook secret, craft a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha that exists on OrgB/bar upstream>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/bar" }
}
```
3. Sign the raw body with `OrgA`'s `webhook_secret` (`sha1=` HMAC) and send `X-Github-Event: push`, `X-Hub-Signature: sha1=...` to the webhooks endpoint.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` (matches, since `repository.owner.login == "OrgA"`) and the HMAC matches → request accepted.
5. `PushHandler` resolves `repository_name = "OrgB/bar"` and calls `stack.sync_github(expected_head_sha: ...)` for `OrgB`'s stack — an action the caller was never authorized to trigger with `OrgB`'s own webhook secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
