### Title
Cross-organization webhook forgery via mismatched signature-verification key and repository-write key - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's webhook secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`), but the event handlers that actually locate and act on a `Repository`/`Stack` use a *different* field, `repository.full_name`. Because these two fields are never cross-checked, an attacker who legitimately knows the webhook secret for **one** organization configured in a multi-org Shipit deployment can forge a correctly-signed webhook whose `repository.owner.login` names their own org (satisfying signature verification) while `repository.full_name` names a repository belonging to a **different** organization on the same instance, causing Shipit to act on that victim stack.

### Finding Description
`verify_signature` computes the org used for HMAC verification like this: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This `repository_owner` is used solely to pick the `GitHubApp` (and thus the `webhook_secret`) with `Shipit.github(organization: repository_owner)` at [3](#0-2) . Shipit supports multiple independently configured GitHub organizations/apps, each with its own `webhook_secret`, as shown by the multi-org secrets fixture [4](#0-3)  and `Shipit.github_app_config` / `github_organizations` in [5](#0-4) .

However, once the signature check passes, the base `Handler` class (used by `PushHandler`, `StatusHandler`, `PullRequest::*Handler`, etc.) resolves the target `Repository`/`Stack` from a **different** field: [6](#0-5) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` then directly triggers a sync for whatever stacks match that `full_name`: [7](#0-6) .

Since the entire raw request body is what's covered by the HMAC (`request.raw_post`, see [8](#0-7) ), an attacker does not need to tamper with a GitHub-issued payload after the fact — they simply **construct their own JSON body from scratch** and sign it themselves with a secret they legitimately possess (their own organization's `webhook_secret`, which any GitHub org/App owner necessarily knows or can rotate/view). Nothing in the code requires `repository.owner.login` to match the owner segment of `repository.full_name`; these are independent, attacker-controlled string fields in a body the attacker fully authors.

Binding broken (as equality that is expected but never enforced):
`repository_owner` (organization that authenticated the request) == owner segment of `repository.full_name` (repository the handler subsequently reads/writes).

Before the attack, this equality holds for all genuine GitHub-issued webhooks (GitHub itself guarantees consistency between `repository.owner.login` and `repository.full_name`). After the attack, the attacker forges a request where the equality is broken: `repository_owner = "attacker-org"` (used only for HMAC selection) while `repository.full_name = "victim-org/victim-repo"` (used by every default handler to select the `Stack`).

### Impact Explanation
This crosses an authentication boundary the same way the report's front‑running bug breaks a distribution/removal-set binding by attacker-controlled state: here, the field validated by the signature (`repository.owner.login`/`organization.login`) is not the field consumed by the business logic (`repository.full_name`). Any Shipit instance hosting multiple GitHub organizations — a documented and tested configuration in this engine (`secrets_double_github_app.yml`) — is exposed to one org's legitimate secret holder forging events that are attributed to and acted upon for a completely different organization's repositories/stacks, without ever needing that other organization's secret, GitHub App credentials, or Shipit session. This is a cross-organization write on shared infrastructure: it can force `GithubSyncJob` to run against a victim stack (`stack.sync_github(expected_head_sha: ...)`), potentially cascading into commit ingestion, CI/status changes, and (depending on continuous-deployment configuration of the victim stack) automated deploy triggers — matching the required "cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
Requires only: (1) the attacker legitimately administers/knows the `webhook_secret` for any one GitHub organization configured in the same multi-tenant Shipit instance (a routine, low-privilege condition for any org onboarded to that instance), and (2) the ability to send an arbitrary HTTP POST to the public `/webhooks` endpoint with a custom `X-Hub-Signature` and `X-Github-Event` header — no GitHub round-trip, front-running, or race condition is needed, since the attacker authors the entire payload and signs it themselves. This is straightforward to exploit whenever multiple orgs are configured, which the engine explicitly supports and tests for.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`/`#stacks`), enforce that the organization used to select the webhook secret is derived from the same, single source of truth as the one used to resolve the target repository — e.g., require `repository.full_name`'s owner segment to equal `repository.owner.login`/`organization.login` before dispatching to handlers, and reject the request otherwise.

### Proof of Concept
1. Attacker is (or controls) a GitHub organization "AttackerOrg" configured in this Shipit instance with its own `webhook_secret` (`sha1` HMAC key), per the `secrets.github.<org>.webhook_secret` schema shown in `secrets_double_github_app.yml`.
2. Attacker crafts a JSON body without ever contacting GitHub:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(AttackerOrg_webhook_secret, body)>`.
4. Attacker POSTs to `/webhooks` (or the mounted engine's equivalent path) with `X-Github-Event: push` and the above headers/body.
5. `verify_signature` computes `repository_owner = "AttackerOrg"`, loads `Shipit.github(organization: "AttackerOrg")`, and the HMAC check succeeds (attacker used the correct secret for that org).
6. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, whose `stacks` lookup resolves `Repository.from_github_repo_name("VictimOrg/victim-repo")` — a repository belonging to a different, unrelated organization — and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on the victim's stack using a signature that only proves control of the attacker's own organization's secret.
