## Analysis

Let me trace the full call path and authentication boundary.

### Call Path

`HandleMainMsg` (sub_bridge_handler.go:260-264) dispatches `ServiceChainInvalidTxResponseMsg` directly to `handleParentChainInvalidTxResponseMsg` with no pre-check on the sender's identity. [1](#0-0) 

`handleParentChainInvalidTxResponseMsg` decodes the peer-supplied list, looks up each hash in `bridgeTxPool`, and — if `ErrStr` equals `blockchain.ErrGasPriceBelowBaseFee.Error()` — calls `RemoveTx` unconditionally: [2](#0-1) 

`RemoveTx` permanently deletes the entry from both `pool.all` and `pool.queue`: [3](#0-2) 

### Authentication Boundary

The P2P handshake only validates `NetworkId` and `ProtocolVersion` — both are self-reported by the connecting peer: [4](#0-3) 

`RegisterNewPeer` adds any peer whose self-reported `chainID` matches the configured parent chain ID: [5](#0-4) 

There is no cryptographic proof that the peer is the legitimate main-bridge node. Any node that can reach the sub-bridge's P2P port, supply the correct `NetworkId` and `ProtocolVersion`, and claim the parent `chainID` becomes a fully trusted bridge peer whose messages are processed by `HandleMainMsg`.

### No Guard on the Removal

The only condition before `RemoveTx` is a string comparison against the peer-supplied `ErrStr`: [6](#0-5) 

There is no on-chain confirmation, no receipt check, no nonce verification, and no rate limit. The code comment itself acknowledges the risk: *"For value transfer txs, Value Transfer Recovery will retry if enabled."*

### VT Recovery Does Not Fully Mitigate

`VTRecovery` is an opt-in config flag: [7](#0-6) 

When disabled (the default in many deployments), removed handle-txs are never re-queued. Even when enabled, VT recovery only re-handles *request* events that have not yet been handled on-chain; a handle-tx that was removed before it was mined is silently lost unless the recovery loop happens to re-detect the unhandled request nonce.

### Title
Unauthenticated Bridge Peer Can Force Removal of Pending Value-Transfer Handle Txs via Crafted `ServiceChainInvalidTxResponseMsg` — (`node/sc/sub_bridge_handler.go`)

### Summary
Any P2P node that passes the trivially-spoofable bridge handshake can send a `ServiceChainInvalidTxResponseMsg` whose `ErrStr` equals `blockchain.ErrGasPriceBelowBaseFee.Error()` and whose `TxHash` matches a live entry in `bridgeTxPool`. The sub-bridge unconditionally calls `RemoveTx`, permanently dropping the handle-tx. With VT recovery disabled, the corresponding value transfer is never completed, locking bridged KAIA or ERC20 tokens in the bridge contract.

### Finding Description
`handleParentChainInvalidTxResponseMsg` trusts the `ErrStr` field supplied by the remote peer without verifying that the peer is the legitimate main-bridge or that the parent chain actually rejected the transaction. The bridge handshake (`readStatus`) only checks `NetworkId` and `ProtocolVersion`, both of which are self-reported. `RegisterNewPeer` adds any peer claiming the correct parent `chainID`. Once connected, the peer can send a crafted `ServiceChainInvalidTxResponseMsg` containing any tx hash present in `bridgeTxPool` with `ErrStr = "gas price is below the base fee"`. The handler finds the tx via `txPool.Get`, matches the string, and calls `RemoveTx`, which deletes the entry from `pool.all` and `pool.queue` with no further checks.

### Impact Explanation
Pending value-transfer handle txs removed from `bridgeTxPool` are never re-broadcast to the parent chain. If VT recovery is disabled, the corresponding `RequestValueTransfer` events on the child bridge contract remain unhandled indefinitely, and the bridged assets (KAIA or ERC20 tokens) locked in the parent bridge contract cannot be released. This constitutes a durable, targeted loss of bridged funds.

### Likelihood Explanation
The sub-bridge's P2P port is reachable by any node on the same network segment (service chain operators often expose it to the internet for main-bridge connectivity). The attacker needs only: (1) network access to the P2P port, (2) the correct `NetworkId` and `ProtocolVersion` (both are public constants), and (3) a pending tx hash (observable by monitoring bridge traffic or querying the bridge RPC). No private keys, validator collusion, or operator access is required.

### Recommendation
1. **Authenticate the main-bridge peer**: Record the expected main-bridge node ID during configuration and reject `ServiceChainInvalidTxResponseMsg` from any peer whose P2P node ID does not match.
2. **Verify on-chain before removing**: Before calling `RemoveTx`, query the parent chain (via `remoteBackend`) to confirm the tx was actually rejected (e.g., nonce already consumed by a different tx, or the tx is absent from the mempool with a confirmed rejection receipt).
3. **Do not remove on gas-price errors alone**: Instead of removing the tx, update the gas price and re-sign/re-submit. The current `SyncNonceAndGasPrice()` call already fetches the new gas price; the tx should be replaced, not dropped.
4. **Enable VT recovery by default** as a defense-in-depth measure.

### Proof of Concept
1. Start a service chain with a sub-bridge connected to a main-bridge; submit a value-transfer request so a handle-tx appears in `bridgeTxPool`.
2. Connect a second node to the sub-bridge's P2P port using the bridge protocol with matching `NetworkId`/`ProtocolVersion` and the parent `chainID`.
3. From the attacker node, send a `ServiceChainInvalidTxResponseMsg` containing `[{TxHash: <pending handle-tx hash>, ErrStr: "gas price is below the base fee"}]`.
4. Assert that `bridgeTxPool.Get(txHash)` returns `nil` — the tx has been removed.
5. With VT recovery disabled, observe that the value transfer is never completed and the bridged tokens remain locked.

func (sbh *SubBridgeHandler) handleParentChainInvalidTxResponseMsg(msg p2p.Msg) error {
	var invalidTxs []InvalidParentChainTx
	if err := msg.Decode(&invalidTxs); err != nil && err != rlp.EOL {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	txPool := sbh.subbridge.GetBridgeTxPool()
	for _, invalidTx := range invalidTxs {
		if tx := txPool.Get(invalidTx.TxHash); tx != nil {
			logger.Error("A bridge tx was not executed", "err", invalidTx.ErrStr,
				"txHash", invalidTx.TxHash.String(),
				"txGasPrice", tx.GasPrice().Uint64())
			if invalidTx.ErrStr == blockchain.ErrGasPriceBelowBaseFee.Error() {
				logger.Info("[SC][HandleTxDropped] Request gasPrice and Magma values to parent chain")
				sbh.SyncNonceAndGasPrice()

				logger.Error("Bridge tx is removed which has lower gasPrice than UpperBoundBaseFee")
				// Remove the tx from the pool. For value transfer txs, Value Transfer Recovery
				// will retry if enabled. For anchoring txs, there is no automatic retry mechanism;
				if err := sbh.subbridge.GetBridgeTxPool().RemoveTx(tx); err != nil {
					logger.Error("Failed to remove bridge tx",
						"txType", tx.Type(), "txNonce", tx.Nonce(), "txHash", tx.Hash().String())
				} else {
					logger.Info("Removed bridge tx",
						"txType", tx.Type(), "txNonce", tx.Nonce(), "txHash", tx.Hash().String())
				}
			} // TODO-ServiceChain: Consider other types of tx failures with else {}
		}
	}
	return nil
}

func (p *baseBridgePeer) readStatus(network uint64, status *statusData) error {
	msg, err := p.rw.ReadMsg()
	if err != nil {
		return err
	}
	if msg.Code != StatusMsg {
		return errResp(ErrNoStatusMsg, "first msg has code %x (!= %x)", msg.Code, StatusMsg)
	}
	if msg.Size > ProtocolMaxMsgSize {
		return errResp(ErrMsgTooLarge, "%v > %v", msg.Size, ProtocolMaxMsgSize)
	}
	// Decode the handshake and make sure everything matches
	if err := msg.Decode(&status); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	if status.NetworkId != network {
		return errResp(ErrNetworkIdMismatch, "%d (!= %d)", status.NetworkId, network)
	}
	if int(status.ProtocolVersion) != p.version {
		return errResp(ErrProtocolVersionMismatch, "%d (!= %d)", status.ProtocolVersion, p.version)
	}
	return nil
}
