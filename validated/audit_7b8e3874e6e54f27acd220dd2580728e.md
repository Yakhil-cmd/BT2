### Title
Naive comma-split parser in `extract_frontmatter` can silently corrupt/invert hookify block-rule conditions - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter`'s inline-dict branch splits a condition list item on every literal `,` in the line and re-parses each fragment as an independent `key: value` pair, re-writing `item_dict` for every colon-containing fragment it finds. If any field value on that line (most plausibly `pattern`, since regex patterns commonly contain commas in alternations/char-classes) contains a comma followed later by a colon-bearing fragment, the split silently truncates or overwrites earlier keys — including the security-critical `field` key of a `file_path` condition. This lets a block rule intended to protect `.env`-style files silently evaluate a different field (or a corrupted pattern) and never trigger, while the on-disk file still looks like a valid protective rule.

### Finding Description
`plugins/hookify/core/config_loader.py:extract_frontmatter` implements an ad-hoc YAML-like parser. For a list item written on one line (the "inline comma-separated dict" style), it does: [1](#0-0) 
```
if ':' in item_text and ',' in item_text:
    item_dict = {}
    for part in item_text.split(','):
        if ':' in part:
            k, v = part.split(':', 1)
            item_dict[k.strip()] = v.strip().strip('"').strip("'")
    current_list.append(item_dict)
```
This blindly splits the whole line on every `,`, with no awareness that a `,` may be *inside* the `pattern` value (e.g. a regex alternation like `\.env$,\.pem$` or a character class `[a,b]`). Each comma-delimited fragment that itself contains a `:` is parsed as a fresh `key: value` pair and written into the same `item_dict`, so a later fragment can overwrite an earlier field's assignment (last-write-wins on the dict), and a fragment without a `:` is silently dropped. Concretely, a condition line such as:

`- field: file_path, operator: regex_match, pattern: \.env$, field: content`

produces `item_dict = {"field": "content", "operator": "regex_match", "pattern": "\.env$"}` — the originally intended `file_path` targeting is overwritten by the trailing `field: content` fragment embedded inside/after the pattern text, without any parse error. Even without a full field swap, any comma inside a `pattern` (a very ordinary regex construct) truncates the pattern or injects spurious dict keys, since `Condition.from_dict` (`config_loader.py:22-29`) reads `data.get('field', ...)`, `data.get('operator', ...)`, `data.get('pattern', ...)` from whatever the corrupted dict ends up containing. [2](#0-1) 

`hookify.md`'s documented example uses the multi-line dict form (`- field: file_path` / `  operator: regex_match` / `  pattern: \.env$`), which is not vulnerable to this comma issue because each field is on its own line and only single-colon-split per line occurs. [3](#0-2) 
However, `config_loader.py` also implements and accepts the inline single-line comma-separated form as an alternate syntax, and nothing in the `/hookify` command flow or `writing-rules` skill prevents the conversation-analyzer/LLM from emitting this inline form with a comma-bearing pattern when generating rule files via the Write tool from user or repo-influenced content (`$ARGUMENTS`, conversation-analyzer findings). None of `Rule.from_dict`, `extract_frontmatter`, or `RuleEngine._check_condition` validate that `field`/`operator`/`pattern` are internally consistent, so no downstream check catches the corruption; the rule is loaded successfully, appears well-formed, and `RuleEngine._rule_matches` simply evaluates whatever (wrong) field ended up in the `Condition`. [4](#0-3) 

### Impact Explanation
The blast radius is scoped to hookify's own security controls: a `.claude/hookify.*.local.md` rule authored to `block` edits to `.env`/secret files (the canonical example in `hookify.md` and `writing-rules/SKILL.md`) can silently become inert or start checking the wrong field (e.g. `content` instead of `file_path`), so the exact dangerous operation it was meant to block (writing/editing a secrets file) proceeds without the block/warn firing. This is a security-relevant-control-bypass in Claude Code's own hook enforcement layer, matching a "hook/guardrail bypass" style impact rather than a generic parsing bug, because it defeats a user-authored block rule without any visible error.

### Likelihood Explanation
Preconditions: a hookify rule must use the inline comma-separated condition syntax (as opposed to the documented multi-line format) and the `pattern` value on that line must contain a `,` — a very common occurrence for regex patterns (alternations, character classes, multi-extension matches). This can arise either from unintentional pattern authoring (a plausible LLM/analyzer mistake, since `pattern` is free-form regex text per `writing-rules/SKILL.md`) or from deliberate crafting via `/hookify $ARGUMENTS` or conversation content that gets echoed by the conversation-analyzer into the generated rule text. [5](#0-4) 
Full field-swap exploitation (crafting the exact trailing `, field: content` fragment) requires the attacker/analyzer to control the literal text written into the rule file precisely, which is a narrower, LLM-output-dependent path; the simpler truncation/corruption case (comma anywhere in `pattern` weakening or breaking the rule) is trivially reproducible.

### Recommendation
Replace the ad-hoc comma-split inline-dict parser with a proper delimiter-aware parser: use a real YAML parser (e.g. `yaml.safe_load` on the frontmatter block) instead of hand-rolled line splitting, or, at minimum, restrict the inline-dict branch to split only on `, ` sequences that are followed by a recognized key name (`field:`, `operator:`, `pattern:`) via regex lookahead, and reject/normalize any fragment lacking one of those exact keys instead of silently dropping/overwriting. Additionally, add a load-time invariant check in `Rule.from_dict`/`Condition.from_dict` that fails loudly (logs an error and disables the rule) if `field` is not one of the known field names, rather than silently accepting arbitrary corrupted values.

### Proof of Concept
Unit test in `plugins/hookify/core/config_loader.py` test style:
```python
def test_inline_dict_comma_in_pattern_does_not_corrupt_field():
    content = """---
name: block-env-writes
enabled: true
event: file
action: block
conditions:
  - field: file_path, operator: regex_match, pattern: \\.env$,\\.pem$
---

Blocked: editing a secrets file.
"""
    fm, _ = extract_frontmatter(content)
    rule = Rule.from_dict(fm, "msg")
    cond = rule.conditions[0]
    # Expected (author intent): field stays 'file_path', full pattern preserved
    assert cond.field == 'file_path'
    assert cond.pattern == r'\.env$,\.pem$'
    # Actual buggy behavior: pattern truncated to r'\.env$' and/or a stray
    # top-level key from the dropped fragment; assert this fails today.
```
A fuzz/invariant test can generate random `conditions` dicts (reference fixtures) with `pattern` values containing embedded commas and colons, serialize them to the markdown inline-dict form, round-trip through `extract_frontmatter`/`Rule.from_dict`, and assert the resulting `Condition.field`/`operator`/`pattern` exactly match the reference dict — demonstrating the parser differential whenever the reference pattern contains a comma.
