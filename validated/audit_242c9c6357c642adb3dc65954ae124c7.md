### Title
ERC20Transactor trusts claimed transfer amount instead of validating actual balance delta, mismatching XCM holding accounting for fee-on-transfer/deflationary ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
The `ERC20Transactor` used as an XCM `TransactAsset` implementation for ERC20 tokens (registered via `pallet-revive`/Solidity contracts on Asset Hub) records a fixed `amount` into the XCM holding register based purely on a boolean `true` return from the contract's `transfer()` call, without ever checking the actual token balance delta moved into/out of the `TransfersCheckingAccount`. This is structurally the same root cause as the Balancer STA exploit: "the contract does not validate the received tokens, leading to incorrect balance records."

### Finding Description
In `withdraw_asset_with_surplus` [1](#0-0) , the transactor calls `IERC20::transferCall{ to: checking_address, value: amount }` on the arbitrary ERC20 contract identified by `asset_id` (derived from the XCM `Asset` location, an `AccountKey20` matched by `ERC20Matcher`), and if the ABI-decoded return value is `true`, unconditionally mints an `AssetsInHolding` credit of exactly `amount` via `Erc20Credit(amount)` — regardless of what the checking account's balance actually changed by.

Symmetrically, `deposit_asset_with_surplus` [2](#0-1)  instructs the checking account to `transfer(beneficiary, amount)` for whatever `amount` is recorded in the holding register (which came from the possibly-inflated withdraw step or from a cross-chain `ReserveAssetDeposited`/`WithdrawAsset` instruction that simply states an amount).

For any ERC20 contract that implements fee-on-transfer, deflationary/rebasing, or otherwise non-1:1 transfer semantics (exactly the class of token responsible for the Balancer STA exploit), the checking account will receive less than `amount` while the executor's holding register still believes it holds the full `amount`. Since arbitrary Solidity contracts can be uploaded/instantiated permissionlessly by any signed account via `pallet-revive` (`UploadOrigin`/`InstantiateOrigin` = `EnsureSigned`) [3](#0-2) , an attacker can deploy their own fee-on-transfer ERC20 and reference it via its `AccountKey20` location in a self-authored XCM (e.g., a local `Xcm::execute` or a reserve-transfer), with no privileged role required.

The `Erc20Credit` imbalance type explicitly documents that it does not enforce runtime-level balance checks, delegating that responsibility entirely to the ERC20 contract itself [4](#0-3)  — but the contract's `bool` success return communicates nothing about the actual quantity moved, only that the call didn't revert.

### Impact Explanation
Because the XCM executor's holding register can be inflated relative to what the checking account contract truly custodies, any subsequent XCM instruction that consumes the holding value at face value — `DepositAsset`, `InitiateReserveWithdraw`/`InitiateTransfer` to a remote chain reporting `ReserveAssetDeposited(ERC20, amount)`, or `ExchangeAsset` via the asset-conversion pool — will operate on a phantom balance. This can manifest as:
- Unbacked issuance reported to a remote chain (destination mints/credits the full claimed `amount` while the source-side checking account holds strictly less), breaking the reserve-backing invariant.
- Denial of subsequent legitimate deposits from the shared `TransfersCheckingAccount`, since its real balance is smaller than what other users' pending holding-register entries assume, causing solvency issues for the shared checking-account pool.

This is a genuine cross-boundary XCM/pallet-revive integrity issue, not a contained precompile bug, so it rates Critical/High if realized against real value, though it is currently *unverified* whether it is practically triggerable end-to-end (see Likelihood/uncertainty below).

### Likelihood Explanation
Likelihood is **uncertain, not confirmed**. Reaching this from a real, unprivileged extrinsic requires:
1. Confirming `ERC20Matcher`'s exact matching rule (only regex/address-space filtered, or does it also require the contract to expose a real `pallet-revive` code hash — i.e., is it permissionless to point at *any* deployed contract address?). I located `ERC20Matcher` usage but did not have iterations left to read its full matching logic in `cumulus/parachains/runtimes/assets/common/src/lib.rs` or `fungible_conversion.rs`, so I cannot confirm whether arbitrary attacker-deployed contracts are eligible targets or whether there's an allow-list/registration step.
2. Confirming whether `AssetTransactors` ordering and the XCM barrier/origin-conversion configuration for Asset Hub genuinely allow a normal signed account to trigger `withdraw_asset_with_surplus` on an attacker-supplied ERC20 address via `pallet_xcm::execute` or `transfer_assets`, without any pre-registration analogous to `pallet-assets::create`.
3. Confirming that a downstream instruction (remote reserve deposit, or `ExchangeAsset`) actually consumes the holding register's face-value amount without any secondary on-chain balance re-check that would neutralize the discrepancy (e.g., some `check_out`/re-inspection step).

I was not able to verify points 1–3 within the available tool budget. Given the explicit design comment in `Erc20Credit` acknowledging that balance enforcement is not done at the runtime level, the structural resemblance to the reported vulnerability class is strong, but this should be treated as an unconfirmed lead requiring further code reading (`ERC20Matcher`, `fungible_conversion.rs`, and the Asset Hub `AssetTransactors`/barrier wiring) before being submitted as a bounty-eligible finding.

### Recommendation
- After each `IERC20::transferCall` in `withdraw_asset_with_surplus`/`deposit_asset_with_surplus`, read the checking account's actual `balanceOf` before and after the call and use the observed delta (not the requested `amount`) when constructing/consuming the `AssetsInHolding` credit.
- Alternatively, explicitly reject ERC20 contracts that do not conform to a verified "no fee-on-transfer" invariant before allowing them to be used as XCM-transactable assets (e.g., require a governance-curated allow-list rather than permissionless address matching).
- Add integration tests using a deliberately deflationary mock ERC20 (analogous to STA) exercised through `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` to assert holding-register accounting matches real balance deltas.

### Proof of Concept
Not executed. A full PoC would require: (a) confirming permissionless eligibility of attacker-deployed ERC20 contracts as XCM-transactable assets via `ERC20Matcher`, (b) deploying a fee-on-transfer ERC20 fixture via `pallet-revive`, (c) constructing an `Xcm::execute`/`transfer_assets` extrinsic that withdraws it and either deposits locally or triggers a remote reserve report, and (d) asserting a measurable mismatch between the checking account's real ERC20 balance and the holding-register/reported amount. This was not run; the above is a structural code-level analog, not a demonstrated exploit.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}
