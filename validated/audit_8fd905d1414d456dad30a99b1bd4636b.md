This confirms the pattern: `PushHandler#process` and `CheckSuiteHandler#process` both scope through `stacks` (which resolves via `Repository.from_github_repo_name(repository_name)`, tying results to the specific repo/owner in the webhook payload), before touching any records. `StatusHandler#process`, in contrast, does not use that scoping at all — it queries `Commit.where(sha: params.sha)` globally across the entire `commits` table, with no join or filter on `repository`, `stack`, or `owner`.### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by SHA across the *entire* `commits` table with no filter on the repository that authenticated the webhook, then calls `commit.create_status_from_github!` on every match. If two unrelated `Stack`s (belonging to different GitHub orgs) happen to contain a commit with the same SHA, an attacker who owns one of those repositories can trigger a legitimately-signed `status` webhook from their own repo and have it write a `Shipit::Status` row into the other org's stack, mutating that tenant's CI/deployability state.

### Finding Description
The broken binding: `commit.stack.repository.owner == repository_owner_from_signed_webhook_payload` is assumed but never checked for the `status` event.

Trace:
- `WebhooksController#create` parses the payload and dispatches to `Shipit::Webhooks.for_event(event)`, i.e. `Handlers::StatusHandler`, per [1](#0-0) .
- `verify_signature` only checks the HMAC using the webhook secret belonging to `repository_owner` (derived from the payload's own `repository.owner.login`), via `Shipit.github(organization: repository_owner)` [2](#0-1) . This proves only that *the attacker's own org* signed the payload — it says nothing about which `Commit`/`Stack` rows get touched afterward.
- `Handler` base class provides a `stacks` helper that scopes strictly to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) . `PushHandler` and `CheckSuiteHandler` both use this `stacks` scope before touching any record [4](#0-3) [5](#0-4) .
- `StatusHandler#process`, however, does **not** use `stacks` at all — it queries `Commit.where(sha: params.sha)` globally, with no join/filter on repository or owner: [6](#0-5) .
- For every matching `Commit` (which can belong to any stack in any tenant), `Commit#create_status_from_github!` is called, which calls `statuses.replicate_from_github!(stack_id, github_status)` using that commit's own `stack_id` — never validated against the payload's repository: [7](#0-6) .
- `Status.replicate_from_github!` unconditionally creates the record for that `stack_id`: [8](#0-7) .

Attacker's exact request: the attacker owns Repo A (in Org A, a Shipit-tracked stack). They push/merge a commit whose SHA collides with a commit SHA that also exists in victim Stack B (Org B) — plausible when both forked from the same upstream history and share an unmodified merge commit, or more directly, the attacker can simply reference (via GitHub API status creation on their own repo) any SHA string they choose in the `status` event payload's `sha` field, since the SHA is attacker-supplied data in the JSON body and is looked up in the DB with no scoping to `repository.full_name`. GitHub itself would normally only let a repo owner set a status for commits in their own repo, but nothing stops the attacker from being the actual author of a fork/branch containing an identical merge commit inherited from the shared upstream, and GitHub's real status API is signed and delivered as a normal webhook — Shipit doesn't verify that the SHA in the payload belongs to the org that signed the webhook. Once GitHub delivers this real signed webhook (or the attacker replays a similarly signed body for their own configured repo/secret), `StatusHandler` writes a `Status` for every `Commit` row anywhere in the database sharing that SHA, including in Org B's unrelated stack.

Existing guards fail because: `verify_signature` checks *who signed*, not *which records the payload is entitled to affect*; `drop_unhandled_event`/`ExplicitParameters` only validate payload shape (`sha`, `state`, etc.), not tenant scoping; there's no `stacks`/`Repository.from_github_repo_name` filter anywhere in `StatusHandler`.

### Impact Explanation
A single legitimately-signed webhook from an attacker-controlled repository writes a `Shipit::Status` row into any other stack/tenant whose commit history happens to contain the same SHA. This is a write of CI state (`state`, `context`, `description`, `target_url`) for a repository/organization that never authenticated that payload — matching "a payload for one repository mutating another's stack/commit." Because `Status#enable_ci_on_stack` and `schedule_continuous_delivery` fire on creation [9](#0-8) , a forged `success` status can flip a victim commit into "deployable," potentially triggering continuous-delivery-driven deploys (`ProcessMergeRequestsJob`/CD scheduling), which escalates this from spurious CI noise to influencing/unblocking deploys in a stack the attacker doesn't own. This is repeatable against any stack that shares a colliding SHA and is not limited to a single victim — every `Commit` row matching the SHA across the whole install gets a `Status` written in the same request. Severity matches Critical: "a payload for one repository mutating another's stack, commit... or an unauthorized deploy."

### Likelihood Explanation
Requires two Stacks (different orgs) tracking overlapping/shared commit history so a SHA collides — a real, not purely theoretical, precondition in monorepo forks, vendored branches, or repos syncing from the same upstream (git SHAs are content-addressed, so identical merge commits/trees legitimately produce identical SHAs across independent clones). No Shipit secrets, sessions, or privileged roles are needed — the attacker only needs to control a repository already onboarded into Shipit (an "unprivileged" GitHub user with any repo can qualify) and can trigger the `status` webhook by pushing/merging or via GitHub's own status API on their own repo. The attack is repeatable at will and costs nothing beyond ordinary GitHub actions.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: restrict the commit lookup to commits belonging to `stacks` (i.e., `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) so a status webhook can only mutate commits belonging to the repository/stacks that were named in — and authenticated for — that webhook payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "a status webhook for one repository must not create statuses on commits belonging to another org's stack" do
          shared_sha = "deadbeef" * 5

          org_a_stack = shipit_stacks(:shipit)          # repository owned by org A
          org_b_stack = shipit_stacks(:cyclimse)         # unrelated repository/org B

          commit_a = org_a_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                                   committer: shipit_users(:walrus),
                                                   authored_at: Time.now, committed_at: Time.now)
          commit_b = org_b_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
                                                   committer: shipit_users(:walrus),
                                                   authored_at: Time.now, committed_at: Time.now)

          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/travis',
            'repository' => { 'full_name' => org_a_stack.github_repo_name,
                               'owner' => { 'login' => org_a_stack.repository.owner } }
          }

          assert_difference 'Status.count', 1 do
            StatusHandler.call(payload)
          end

          # Binding under test: only org A's commit should get a Status; org B's must remain untouched.
          assert_equal 1, commit_a.reload.statuses.count
          assert_equal 0, commit_b.reload.statuses.count, "webhook for org A's repo must not mutate org B's stack"
        end
      end
    end
  end
end
```
With the current code, `Status.count` increases by 2 (one per stack sharing the SHA) instead of 1, demonstrating the cross-tenant write.
