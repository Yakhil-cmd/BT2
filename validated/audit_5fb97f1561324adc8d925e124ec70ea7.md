## Analysis: Private assets sent to an AA address are permanently lost

The bug class from the ERC721 report — "assets sent to a recipient that structurally cannot handle/forward them are permanently lost, and there is no protective check before sending" — maps to a concrete Obyte analog: **sending a private asset payment to an Autonomous Agent (AA) address**. AAs are architecturally excluded from ever seeing, crediting, or spending private-asset outputs, yet nothing prevents a wallet from composing and sending such a payment to an AA address.

### Root cause

1. When main-chain stability triggers AAs, the query in `handleAATriggers` explicitly excludes private outputs from consideration: [1](#0-0) 

2. Likewise, when an AA is (re)defined and its balances are backfilled from historical outputs, private outputs are excluded from `aa_balances`: [2](#0-1) 

3. `handleTrigger`'s own outgoing-payment logic even documents that AAs cannot handle private assets ("it'll fail validation anyway due to lack of spend_proofs") and bounces any AA-initiated attempt to send one: [3](#0-2) 

4. The wallet-side guard before sending to any AA address, `checkAAOutputs`, only validates that `bounce_fees` are covered — it never checks whether the destination is capable of processing the asset type being sent (private or otherwise): [4](#0-3)  This function is the sole gate invoked from `wallet.sendMultiPayment` before composing a payment to any address that happens to be an AA: [5](#0-4) 

### The gap

Because private-asset outputs to a valid on-chain address are always structurally recognized by ocore's core payment/private-payment validation (`validatePayment`/`validatePaymentInputsAndOutputs` in `validation.js` accept any `isValidAddress` recipient without checking whether it is an AA): [6](#0-5) 

...a unit sending a private asset (or, for indivisible/fixed-denomination assets sent onward from an AA, similarly unreachable funds — see `aa_composer.js:1356` where fixed-denomination outgoing messages are silently dropped) to an AA address will validate and commit successfully on the DAG. But:
- The AA never learns about the funds (`main_chain.js:1702` excludes them from triggering).
- The AA's balance table never reflects them (`storage.js:960` excludes them).
- No bounce/refund happens, because the AA is never triggered at all.
- The off-chain private-payment delivery mechanism (`sendPrivatePayments`/`forwardPrivateChainsToOtherMembersOfOutputAddresses` in `wallet.js:2402-2437`) assumes a device-connected recipient; an AA has no device to receive the private chain of custody, so even the private elements needed to later prove/spend the output can never reach an owner.

The result is functionally identical to the ERC721 `transferFrom`-without-`onERC721Received` issue: the transfer succeeds at the protocol level, the recipient (AA) has no mechanism to receive, acknowledge, or return the asset, and the sender receives no error or bounce — the tokens are permanently stranded with no code path to recover them.

### Title
Private (and non-refundable indivisible) assets sent to an AA address are permanently lost with no pre-send validation - (File: aa_addresses.js, main_chain.js, storage.js)

### Summary
`aa_addresses.checkAAOutputs`, the only wallet-side safeguard invoked before sending a payment to an address that is an AA, checks only that `bounce_fees` are covered for the base asset. It performs no check on whether the payment's asset is private (or fixed-denomination), even though AAs are structurally incapable of receiving, crediting, or bouncing such assets.

### Finding Description
`main_chain.js`'s `handleAATriggers` query filters out private outputs (`outputs.asset IS NULL OR is_private=0`) when selecting units that trigger an AA, and `storage.js`'s `insertAADefinitions` similarly excludes private outputs (`is_private=0 OR is_private IS NULL`) when computing an AA's balance from historical outputs. `aa_composer.js` documents and enforces that an AA can never itself send a private asset (`"sending private asset from AA"`), confirming AAs have zero support for the private-asset lifecycle. Despite this, `validatePayment`/`validatePaymentInputsAndOutputs` in `validation.js` place no restriction on the recipient address of a private payment — any syntactically valid address, including a known AA address, is accepted. The wallet's pre-flight check (`checkAAOutputs`) only validates `bounce_fees`, never the compatibility of the asset type with an AA recipient, so a user (or another AA forwarding funds) can send a private-asset payment to an AA address, have it validate and commit, and have the funds become permanently invisible to the AA (never triggering it, never counted in `aa_balances`) while also being undeliverable to any human owner since AAs have no device to receive the off-chain private-element chain.

### Impact Explanation
Any private-asset payment sent to an AA address results in permanent, unrecoverable loss of those tokens: the AA cannot see, hold, spend, or bounce them, and the sender/would-be recipient has no on-chain or off-chain mechanism to reclaim them since AAs cannot participate in the private-payment device-to-device protocol. This is a direct, irreversible loss of user funds/assets — matching a Medium-severity "AA fund loss" outcome.

### Likelihood Explanation
Likelihood is driven by ordinary user/wallet error or by AA-to-AA/AA-to-user forwarding logic that composes a private-asset payment to an address without verifying it isn't an AA. Since `checkAAOutputs` is the only defense and it doesn't consider asset privacy, this can happen unintentionally any time a private asset is sent to an AA address (e.g., via `sendMultiPayment` with `opts.asset` set to a private asset and `to_address` pointing at an AA), with no error surfaced beforehand.

### Recommendation
Extend `aa_addresses.checkAAOutputs` (and/or `validatePayment`/`validatePaymentInputsAndOutputs`) to reject payments to AA addresses when the asset being sent `is_private` (and consider similarly restricting non-forwardable `fixed_denominations` assets, since AAs silently drop outgoing fixed-denomination payments per `aa_composer.js:1356`). This should be enforced both at wallet compose-time (to warn/reject before the unit is even built) and, ideally, as a protocol-level validation rule so malicious or buggy peers cannot rely on user error to strand funds at AA addresses.

### Proof of Concept
1. Define/observe an existing AA address `AA_ADDR` (any deployed AA).
2. Issue a private asset `P` with `is_private: true`.
3. Using `wallet.sendMultiPayment({ asset: P, to_address: AA_ADDR, amount: N, ... })`, compose and broadcast a private payment of asset `P` to `AA_ADDR`.
4. `checkAAOutputs` (`aa_addresses.js:120-156`) only checks `bounce_fees.base`, which is satisfied by ordinary payment inputs; the payment validates and commits (`validatePayment` in `validation.js` places no AA-specific restriction on private payments).
5. When the triggering unit stabilizes, `handleAATriggers` (`main_chain.js:1691-1723`) excludes this output from `aa_triggers` because `is_private=1`; the AA is never invoked, never bounces, and `aa_balances` (`storage.js:954-961`) never reflects the asset.
6. The private payment's off-chain chain-of-custody data is sent via `sendPrivatePayments`/`forwardPrivateChainsToOtherMembersOfOutputAddresses` (`wallet.js:2405-2429`), which require a device-connected recipient — `AA_ADDR` has none, so no one ever receives the data needed to prove ownership or spend the output.
7. Asset `P`'s balance at `AA_ADDR` is permanently unspendable and unrecoverable by any party.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
}

	if (!isNonemptyArray(payload.outputs))
