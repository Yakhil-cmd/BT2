### Title
Cross-organization commit-status forgery via unscoped `StatusHandler` — organization identity authenticated vs. repository/commit state written - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` binds an inbound GitHub webhook to a specific GitHub organization's `webhook_secret` by looking up `Shipit.github(organization: repository_owner)` and validating the HMAC against that organization's secret only. Once the signature check for *that organization* passes, the raw JSON is dispatched to a handler based solely on `event`, and `StatusHandler` never re-checks that the payload's target commit actually belongs to a stack/repository owned by the organization whose secret was used to authenticate the request.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to select the verification secret purely from attacker-controlled payload fields: [1](#0-0) [2](#0-1) 

This is the intended design for Shipit's documented multi-organization deployment mode, where each org section under `github:` in `secrets.yml` has its own `app_id`/`installation_id`/`webhook_secret`: [3](#0-2) 

After the signature check succeeds for organization A (using organization A's own webhook secret — which the operator of organization A legitimately possesses, since they configured that GitHub App), the raw payload is handed to the matching event handler with no further ownership check: [4](#0-3) 

`StatusHandler`, unlike other handlers, does **not** scope its lookup to a repository/stack at all — it queries `Commit` globally by `sha`, matching commits from *any* stack tracked anywhere in the Shipit instance: [5](#0-4) 

Compare this to every other handler in the codebase, which resolves `Repository.from_github_repo_name(params.repository.full_name)` (or `payload.dig('repository','full_name')` via `Handler#repository_name`/`#stacks`) before acting: [6](#0-5) [7](#0-6) 

The trust binding that should hold is:
`organization authenticated by verify_signature` == `organization owning the repository whose commit/state is mutated by the handler`

For `StatusHandler` this equality is never enforced — the handler's `params` block doesn't even require a `repository` key, so the binding is broken by construction: any organization that legitimately controls its own GitHub App/webhook secret (as configured in a multi-org Shipit deployment) can send a signed `status` event whose `sha` field matches a commit belonging to a completely different, unrelated organization's stack, and Shipit will apply the state (`description`, `target_url`, `context`, `state`) to that foreign commit.

### Impact Explanation
`Commit` statuses (`Status` records) feed directly into deploy-gating logic (`ci.require`, `ci_enabled?`, deployability checks) in `Shipit::Commit`/`Shipit::Stack`. An attacker who legitimately owns one onboarded organization in a multi-tenant Shipit instance can forge `success` statuses for commits belonging to a victim organization's stacks that they have no access to, potentially satisfying `ci.require` checks and enabling continuous-deployment/manual deploy of a commit that never actually passed CI on the victim's real GitHub repository — or forge `failure`/`error` statuses to block a victim's deploys (denial of legitimate deploys, and enabling of illegitimate ones). This crosses the "unauthorized deploy" bar defined in scope, since it manipulates the CI-gate signal that a separate, unrelated organization's deploy pipeline relies on, without that organization's credentials.

### Likelihood Explanation
This requires:
1. The Shipit deployment to be configured in multi-organization mode (a documented, supported configuration).
2. The attacker to legitimately control at least one of the configured organizations (and hence its own webhook secret) — a low bar, since GitHub App creation/webhook-secret assignment for one's own org is self-service and not a "privileged" credential relative to the *other* organizations hosted on the same Shipit instance.
3. Knowledge of a target commit SHA in the victim organization's repository, which is public information on GitHub (or discoverable via the Shipit UI/API if read access is otherwise available).

Given these are realistic conditions for any shared multi-tenant Shipit installation, likelihood is Medium-to-High for that deployment pattern.

### Recommendation
`StatusHandler` (and any other handler that does not scope lookups by `repository.full_name`) should require and validate a `repository` field, and constrain the `Commit` lookup to `stacks` derived from `Repository.from_github_repo_name(params.repository.full_name)` (mirroring `Handler#stacks`), rather than a global `Commit.where(sha: ...)`. More broadly, `verify_signature` should ensure that the organization used to select the webhook secret is provably the same organization tied to any resource the handler subsequently mutates — i.e., re-validate `repository.owner.login` against the resolved `Repository#owner` before allowing any handler write, closing the gap analogous to the missing-length-check class of bug (an authenticated identity used without validating consistency of the field it is bound to act upon).

### Proof of Concept
1. Deploy Shipit in multi-org mode with `github.OrgA` and `github.OrgB` both configured with distinct `webhook_secret`s (per `docs/setup.md`/`secrets.yml` schema).
2. Attacker legitimately administers OrgA's GitHub App and therefore knows OrgA's `webhook_secret`.
3. Attacker crafts a `status` event JSON body: `{"sha": "<victim-orgB-commit-sha>", "state": "success", "context": "ci/required-check", "created_at": "..."}` — no `repository` key required by `StatusHandler#params`.
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and sets `X-Github-Event: status`.
5. POST to `/webhooks`. `repository_owner` falls back to `params.dig('organization','login')` (or is simply absent, if the attacker also supplies an `organization` field naming OrgA) so `Shipit.github(organization: 'OrgA')` is used and the signature verifies successfully against OrgA's secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` globally, finds the victim's OrgB commit, and calls `commit.create_status_from_github!(params)`, writing a forged `success` status onto a commit the attacker has no access to — potentially satisfying OrgB's `ci.require` gate for that commit.

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
```
