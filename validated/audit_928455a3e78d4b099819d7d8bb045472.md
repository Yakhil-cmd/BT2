### Title
AA `bounce()` push-based refund can permanently trap trigger funds when the bounced asset's transfer conditions cannot be satisfied - ([File: aa_composer.js])

### Summary
The `calculateAndDistributeManagerFees()` bug class is "push over pull": a mandatory outbound transfer that other logic depends on can fail (blacklist/callback), locking funds with no recovery path. Obyte's AA engine has an analogous push-based refund mechanism in `bounce()` inside `handleTrigger()`. When an AA needs to reject a trigger, it pushes the leftover trigger funds back to `trigger.address` via a generated `payment` message and `sendUnit()`. If that generated unit fails unit validation (e.g. because the asset being refunded has `transfer_condition`, `spender_attested`, or `is_transferrable` restrictions that `trigger.address` no longer satisfies), `bounce()` is invoked a second time, `bBouncing` is already `true`, and the code falls straight into `finish(null)` — silently eating the funds with no distribution and no way for the original sender to reclaim them.

### Finding Description
`bounce()` composes a refund message per non-fully-consumed asset in the trigger and sends it: [1](#0-0) 

The refund attempt goes through `sendUnit()` → `validateAndSaveUnit()`, where any unit validation failure calls back into `bounce(err)`: [2](#0-1) 

Crucially, `bounce()` guards against infinite recursion with the `bBouncing` flag, but the fallback for a second failure is simply `finish(null)` — there is no pull-based alternative, no escrow/claim mechanism, and no state change that records the still-unspent asset amount so it can later be retrieved by the sender or by anyone: [3](#0-2) 

The refund's `outputs` target is always `trigger.address`, taken verbatim from the incoming trigger, with no pre-check that this address still satisfies the asset's `transfer_condition` / `spender_attested` / `is_transferrable` rules at bounce time: [4](#0-3) 

Those conditions are enforced only in unit validation: [5](#0-4) [6](#0-5) 

So if a restricted-asset AA (issued/transferred under `spender_attested: true`, or with a `transfer_condition`) needs to bounce a trigger because the trigger's own payload is malformed/insufficient, and the trigger address's attestation status (or any other transfer condition) is no longer satisfied at the last-ball MCI used for the bounce unit, `sendUnit()`/`validateAndSaveUnit()` will reject the refund unit, `bounce()` re-enters with `bBouncing` already set, and the funds are absorbed into the AA's balance with `finish(null)` and no distribution path back to the sender. This is architecturally the same class of defect as the reported push-fee bug: a mandatory, unconditioned outbound transfer whose failure silently and permanently strands the underlying funds, because the code has no pull/claim fallback.

### Impact Explanation
Funds legitimately sent by a user as part of a trigger's `bounce_fees`-exceeding portion of a restricted asset can become permanently inaccessible to that user: they are not refunded (bounce failed) and there is no built-in claim mechanism for the sender to retrieve them later, nor does the AA's state record an obligation to pay them out. This matches the "Medium/High: AA fund loss or freezing" criteria — value is neither burned in a documented way nor returned; it is silently retained by the AA's balance with no path to recovery, unless the specific AA author manually coded a claim-style mechanism (which the base `ocore` bounce logic does not provide or require).

### Likelihood Explanation
This requires an AA that accepts a restricted asset (`spender_attested`, `transfer_condition`, or `is_transferrable=false`) as part of its accepted trigger outputs and a scenario where the trigger issuer's eligibility to receive that asset back changes between send and processing (e.g., attestor revokes/does not (re)attest the address, or a data-feed-based `transfer_condition` becomes false) combined with the AA needing to bounce that specific trigger. This is a narrower precondition than the general "any manager token" scenario in the original report, but it is fully reachable by an ordinary, unprivileged unit poster (the trigger sender) triggering an AA that happens to hold/require a conditioned asset, without any node/hub/peer compromise.

### Recommendation
Do not rely purely on a single push attempt with a hard-coded fallback of "silently keep the funds." Options:
- Before composing the bounce payment, verify (where feasible) that the destination address still satisfies the asset's transfer condition/attestation, and if not, explicitly route the un-refundable balance into AA state (e.g., a `var['unclaimed_refunds'][trigger.address]`) that a later, unrestricted trigger/response can use to complete the payout once the recipient becomes eligible again, mirroring the pull-over-push pattern recommended in the original report.
- Alternatively, document/emit a clear response variable or `state` update on double-bounce failure so downstream consumers (wallets, AA authors) are aware fund is retained rather than silently lost, and provide official base-layer tooling/guidance for asset issuers to avoid designing AAs that accept conditioned assets from addresses whose eligibility can change.

### Proof of Concept
1. Define/issue an asset `A` with `spender_attested: true` (or a `transfer_condition` referencing a data feed).
2. Deploy an AA that accepts asset `A` payments as triggers, with `bounce_fees` set for asset `A`, and that legitimately bounces some triggers (e.g., malformed `trigger.data`).
3. Address `X` gets attested and sends a trigger to the AA with `outputs[A] > bounce_fees[A]`, expecting the excess to be validated/rejected and refunded via `bounce()`.
4. Before the AA processes the trigger (or by using a data-feed based `transfer_condition` that flips), `X`'s attestation is revoked (or the transfer condition otherwise becomes false) so that `X` no longer satisfies asset `A`'s transfer/attestation requirement.
5. The AA processes the trigger, hits an error condition, and calls `bounce()`. `sendUnit()` composes a payment message sending the leftover `A` back to `X`; `validateAndSaveUnit()` rejects it (`objAsset.spender_attested && ... not attested` / `transfer or issue condition not satisfied`), which routes back into `bounce(err)`; `bBouncing` is already true, so `finish(null)` runs, permanently retaining `X`'s asset `A` inside the AA with no distribution and no recorded claim.
