### Title
Interest accrual can overflow `i128` before the index cap and permanently freeze a market - (File: common/src/rates/simulate.rs)

### Summary
A sufficiently large scaled debt or supply balance can make `scaled * index / RAY` exceed `i128::MAX` before `MAX_BORROW_INDEX_RAY` is reached, causing every later market operation to fail during mandatory accrual. [1](#0-0) [2](#0-1) 

### Finding Description
Every pool market leg loads a synchronized cache, and `synced_market` invokes `interest::global_sync` before the requested mutation. [3](#0-2)  `global_sync` calls `accrue_step`, which first unscales both `borrowed` and `supplied` with their stored indexes and only afterwards computes and caps the new borrow index. [4](#0-3) [1](#0-0)  The unscaling path calls `Ray::mul`, which forwards to `mul_div_half_up` and panics with `MathOverflow` when the exact result does not fit `i128`. [5](#0-4) [6](#0-5) [7](#0-6)  Because `mark_accrued` is reached only after all accrual chunks succeed, the failed transaction leaves `last_timestamp` behind and deterministically reaches the same overflow on the next attempt. [4](#0-3) 

The borrow-index cap is applied only to the newly calculated index, so it cannot prevent the earlier overflow in `scaled_to_original`. [1](#0-0) [2](#0-1) 

### Impact Explanation
An unprivileged caller can initiate the failure through controller `update_indexes(caller, assets)` once the market state has crossed the arithmetic boundary. [8](#0-7)  Afterward, public `repay`, `withdraw`, and `liquidate` calls involving the market route into pool operations that synchronize before mutating, so repayment, collateral withdrawal, liquidation, and index maintenance all revert. [9](#0-8) [10](#0-9)  The result is persistent freezing of supplier funds and inability to reduce or liquidate debt unless governance performs an out-of-band code migration.

### Likelihood Explanation
The condition is state-dependent rather than input-only: it requires a very large scaled market and enough index growth that a scaled book multiplied by its index exceeds `i128::MAX`, while the configured cap still permits that book. [1](#0-0) [11](#0-10)  A whale can establish the required state through ordinary `supply` and `borrow` calls on its own account, subject to deployed market caps, collateral value, decimals, and the configured interest curve. [12](#0-11)  Once that state exists, any authorized unprivileged caller can trigger the permanent failure with `update_indexes`, so the final denial of service does not require the original attacker to act again. [8](#0-7) 

### Recommendation
Bound index growth to a market-specific maximum derived from the maximum scaled supply and debt, or keep aggregate unscaled values in a wider representation so accrual cannot fail after a book has been admitted. [13](#0-12)  Enforce the resulting safe scaled-book ceiling during supply, borrow, strategy debt minting, market creation, and cap updates; additionally handle an over-limit legacy state by clamping indexes before unscaling rather than panicking. [14](#0-13) 

### Proof of Concept
1. On an active high-decimal market, call `supply(attacker, 0, spoke_id, [(debt_asset, 1_000_000_000 * 10^18), (collateral_asset, sufficient_collateral)])`, receiving `account_id`. [15](#0-14) 
2. Call `borrow(attacker, account_id, [(debt_asset, 980_000_000 * 10^18)], None)` to create a very large scaled debt book at high utilization. [16](#0-15) 
3. Leave the market untouched until `borrow_index` grows enough that `borrowed_scaled * borrow_index / RAY` exceeds `i128::MAX` but remains below the configured borrow-index cap. [5](#0-4) [2](#0-1) 
4. Call `update_indexes(any_caller, [debt_asset])`; `accrue_step` panics in `scaled_to_original` before it can calculate or commit the capped index. [8](#0-7) [1](#0-0) 
5. Subsequent `repay`, `withdraw`, `liquidate`, and `update_indexes` calls for that market repeat the same accrual and fail before their operation-specific logic can run. [17](#0-16) [10](#0-9)

/// Loads a market cache and accrues interest through the current ledger time.
pub(crate) fn synced_market(env: &Env, hub_asset: &HubAssetKey) -> Cache {
    let mut cache = Cache::load(env, hub_asset);
    interest::global_sync(env, &mut cache);
    cache
}

/// Renews instance TTL, then loads and accrues the market.
pub(crate) fn renewed_market(env: &Env, hub_asset: &HubAssetKey) -> Cache {
    renew_instance(env);
    synced_market(env, hub_asset)
}

/// Validates `action.amount ≥ 0`, syncs the market, and returns (cache, scaled position).
pub(crate) fn load_leg(env: &Env, action: &PoolAction) -> (Cache, Ray) {
    require_nonneg_amount(env, action.amount);
    let cache = synced_market(env, &action.hub_asset);
    (cache, Ray::from(action.position.scaled_amount))
}

pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
