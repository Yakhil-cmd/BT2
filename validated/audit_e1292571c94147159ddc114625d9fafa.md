### Title
Unscoped commit-status webhook handler allows any authenticated GitHub organization to forge CI status on commits belonging to other organizations' stacks - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook against the `webhook_secret` of the organization named in the payload's `repository.owner.login` field, but `StatusHandler#process` never checks that field when deciding which `Commit` records to update — it matches purely on `sha` across the entire database. This breaks the trust binding "the organization whose secret authenticated the webhook" == "the repository whose data gets written", letting one legitimately-onboarded (but malicious/compromised) organization inject fabricated commit statuses into any other organization's stack that happens to share this Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/secret to verify against using an attacker-supplied JSON field: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the unauthenticated request body (`params.dig('repository', 'owner', 'login')`), and `Shipit.github(organization: repository_owner)` resolves to a per-organization `webhook_secret` (as shown by the multiple distinct hook fixtures per org, e.g. `shipit_push`, `cyclimse_push`, `shopify_membership`) [3](#0-2) . This means the HMAC signature only proves "someone who knows organization X's webhook secret sent this exact body" — it says nothing about which repository/commit data inside that same body is legitimate for org X to write.

Every other handler (`PushHandler`, the `PullRequest::*Handlers`) correctly scopes the objects they mutate to the repository named in the payload via `Handler#stacks` / `Repository.from_github_repo_name(repository_name)`: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, does not use `stacks`/`repository_name` at all — it looks up commits globally by SHA and writes a status onto every matching commit, regardless of which repository/organization they belong to: [6](#0-5) 

So the equality that should hold — `organization authenticating the signature == organization owning the commit being written` — does not hold for the `status` event. Any organization with a valid webhook secret configured on this shared Shipit instance can send a `status` event whose `repository` field names their own org (to pass signature verification) while the `sha` field names a commit belonging to a completely different tracked repository/organization, and the fake status will be written to that other org's commit.

### Impact Explanation
Commit statuses drive Shipit's deploy-eligibility logic (`required_statuses`/`blocking_statuses`, review-stack CI checks, and merge queue gating) via `DeploySpec#required_statuses`/`blocking_statuses` [7](#0-6) . By forging a `success` status for a required CI context on a victim commit that the attacker does not have write access to, an attacker can make an undeployable/unreviewed commit appear deployable, enabling an unauthorized deploy of another organization's stack — this satisfies the "unauthorized deploy" Critical-impact criterion. No `ApiClient` token, GitHub write access to the victim repo, or session is required; only a legitimate GitHub App installation (with its own webhook secret) on any organization tracked by the same multi-tenant Shipit deployment.

### Likelihood Explanation
This requires the attacker to control (or have compromised) at least one GitHub organization/app installation that this Shipit instance already trusts (i.e., they know that org's `webhook_secret` — a normal, low-privilege capability for any onboarded team on a shared/multi-tenant Shipit instance), and to know or guess the SHA of the target commit in the victim stack (commit SHAs are routinely public/visible, e.g. via the Shipit UI itself). This is a realistic scenario for any Shipit deployment shared across multiple teams/organizations, which is an explicitly supported configuration (per-organization `github_teams`/webhook secrets as seen in the fixtures).

### Recommendation
Scope `StatusHandler#process` (and any other handler that currently ignores `repository`) to only touch commits belonging to stacks whose `Repository` matches `payload.dig('repository', 'full_name')`, exactly as `PushHandler` and the `PullRequest::*` handlers already do via `Handler#stacks`/`repository_name`. Reject or ignore status events whose declared `repository` does not match the actual repository owning the target commit's stack.

### Proof of Concept
1. Attacker controls organization `evil-org`, which has legitimately installed the Shipit GitHub App and therefore knows `evil-org`'s `webhook_secret`.
2. Shipit also tracks `victim-org/victim-repo`, with a stack requiring a `ci/tests` status to be `success` before it is deployable.
3. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "evil-org" }, "full_name": "evil-org/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(evil-org_webhook_secret, body)` and POSTs to `/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"evil-org"`, fetches `evil-org`'s webhook secret, and the signature verifies successfully (the attacker legitimately knows this secret).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim commit regardless of `repository` — and calls `commit.create_status_from_github!(params)`, writing a forged `success` status onto the victim's commit.
7. The victim stack's required-status check for `ci/tests` is now satisfied, allowing deployment of a commit the attacker never had access to.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
