Based on my investigation, the dhcpcd CVE describes a C-language heap use-after-free where a control socket's client object is freed in `control_recvdata()` while a stale pointer to it is still processed by `control_hangup()` for the same READ+HANGUP event. This is fundamentally a memory-safety bug class specific to manual memory management in C.

Searching the Polkadot SDK codebase for analogous patterns (control-socket-like connection/session handling, peer disconnect/hangup processing, RPC server connection lifecycle) turned up only safe-Rust client/node infrastructure code such as:
- The notifications peer-state machine in [1](#0-0) , which manages connection close events via `Entry`/`mem::replace` on an owned `FnvHashMap`, not raw pointers.
- The litep2p peerset handling in [2](#0-1) , which uses `HashMap::remove`/`insert` for state transitions.
- The JSON-RPC server connection lifecycle in [3](#0-2) , which uses owned futures and disconnect notifications (`on_session_closed`) rather than manual free/pointer reuse.

None of these exhibit a use-after-free pattern: Rust's ownership and borrow-checker model prevents a freed heap object from being referenced by a stale pointer in the way the C dhcpcd bug does, and no `unsafe` code implementing manual object lifecycle management analogous to `control.c` was found. Furthermore, this is node/client-level networking and RPC infrastructure code, not runtime/FRAME pallet logic reachable through a signed extrinsic, XCM message, or contract call, so it does not satisfy the required "real user entry" criterion for this scan's methodology (extrinsic/XCM/contract dispatch path with attacker-controlled input at the runtime level).
