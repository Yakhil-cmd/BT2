### Title
Webhook organization used for signature verification is not bound to the organization/repository the payload actually mutates, enabling cross-organization forgery of `membership` events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to validate a delivery against using a field taken from the **same unverified JSON body** it is about to accept, and that field is never re-checked against the fields the event handlers actually act on. Any actor who administers a Shipit-connected GitHub App for one organization (and therefore legitimately knows that organization's own `webhook_secret`) can forge a signed webhook whose "authenticating" identity is their own org while its "acted-upon" identity (repository/team/organization) belongs to a completely different Shipit-managed organization.

### Finding Description
`verify_signature` derives the org used to look up the verification secret purely from payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and `Shipit.github(organization: repository_owner)` selects that org's configured `webhook_secret` to check the `X-Hub-Signature` HMAC against the raw body. Shipit explicitly supports multiple independent GitHub Apps/organizations, each with its own secret (see `lib/shipit/github_app.rb` and `test/dummy/config/secrets_double_github_app.yml`).

Once `verify_webhook_signature` succeeds, the full JSON body is handed to every registered handler for the event with no further scoping to the organization that was used for verification: [3](#0-2) 

Handlers, however, derive the acted-upon entity from **other, independent** fields of the same body:
- Generic handlers key off `repository.full_name`: [4](#0-3) 
- `MembershipHandler` keys off `organization.login` and `team.id` to find-or-create a `Team`, and off `member.login` to add/remove a `Membership`: [5](#0-4) 

Nothing enforces that `repository.owner.login` (used to select the verification secret) equals `organization.login` / `repository.full_name`'s owner (used by the handler). Because these are sibling keys in one attacker-supplied JSON document, an attacker who controls a legitimately configured Org A (i.e., they created and installed their own GitHub App on this Shipit instance, so they know Org A's `webhook_secret`) can:
1. Set `repository.owner.login` = `"OrgA"` so `verify_signature` validates the HMAC using the secret the attacker knows and legitimately possesses.
2. Set `organization.login` = `"OrgB"` (a victim organization also configured on the same Shipit instance) and `team.id` = the numeric GitHub team id backing one of `Shipit.github_teams` for OrgB, with `member.login` = the attacker's own GitHub login and `action` = `"added"`.

`MembershipHandler#process` will then run `Team.find_or_create_by!(github_id: params.team.id)` scoped to `organization: "OrgB"` and add the attacker as a member: [6](#0-5) 

`Shipit.github_teams` membership is exactly the authorization gate used everywhere access is checked: [7](#0-6) [8](#0-7) 

The equality that should hold but does not is:
`organization authenticated by verify_signature (repository.owner.login / organization.login as read once)` == `organization/repository actually written by the handler (organization.login / repository.full_name as read again, independently)`.

### Impact Explanation
This escalates directly into `Shipit.github_teams` authorization: an attacker who controls any single organization onboarded to a shared Shipit instance can forge a `membership` webhook that adds their own GitHub login to a team backing `Shipit.github_teams` for an *unrelated* organization on the same instance, and thereby gain authenticated, authorized access to that organization's stacks — including triggering deploys/rollbacks. This matches the "High - escalation into `Shipit.github_teams` authorization" impact class.

### Likelihood Explanation
Requires the attacker to administer at least one GitHub App/organization already configured on the target Shipit instance (a realistic scenario for shared/multi-tenant Shipit deployments, as evidenced by first-class multi-org support in `lib/shipit/github_app.rb` and `test/dummy/config/secrets_double_github_app.yml`), plus knowledge of a numeric GitHub team id for the victim org's authorizing team (discoverable via GitHub's team API in many configurations). No Shipit session, `ApiClient` token, or GitHub App private key is needed — only the ability to send a signed HTTP request to the public `/webhooks` endpoint.

### Recommendation
Bind webhook signature verification to the same organization/repository identity the handler will act on: re-derive and hard-fail if `repository.full_name`'s owner (or `organization.login` used by the handler) differs from `repository_owner` used for verification, or better, resolve the target `Repository`/`Team` first and verify the signature using the secret tied to that specific resolved entity, not a value read once from the untrusted body before verification.

### Proof of Concept
1. Attacker creates/administers a GitHub App and installs it, configuring it in Shipit as organization `OrgA` with a known `webhook_secret_A`. Shipit also hosts victim org `OrgB` with a team `Shipit/leads` (github team id `999`) listed in `Shipit.github_teams`.
2. Attacker computes `sha1=HMAC(webhook_secret_A, body)` for the following body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Leads", "slug": "leads", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "OrgB" },
  "member": { "login": "attacker" },
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/whatever" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: membership` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `webhook_secret_A`, and the HMAC check passes.
5. `MembershipHandler#process` runs against `organization.login = "OrgB"` / `team.id = 999`, adding `attacker` as a member of `OrgB`'s `Shipit/leads` team, satisfying `User#authorized?` for `OrgB`'s stacks.
