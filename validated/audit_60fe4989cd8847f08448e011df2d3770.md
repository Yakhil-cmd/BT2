### Title
Wallet accepts `sign` requests from any paired device without verifying the sender is an authorized cosigner - ([File: wallet.js])

### Summary
`ocore` core exposes a device-message handler `sign` in `handleMessageFromHub` that lets any correspondent device ask the local wallet to produce a signature for one of the wallet's own addresses. The check that would confirm the requesting device (`from_address`) is actually a legitimate cosigner of the target address is explicitly commented out, mirroring the root cause of the reported bug: a privileged callback/handler trusts an externally supplied identity/target without verifying that the caller is authorized to invoke it on that target.

### Finding Description
In the `"sign"` case of `handleMessageFromHub`, after validating message shape, the code calls `findAddress(body.address, body.signing_path, {...})`. When the address is locally controlled, `ifLocal` fires and immediately proceeds to build a signing/confirmation flow, with the actual verification of "is `from_address` allowed to request a signature at this signing_path" left commented out: [1](#0-0) 

The comment states this check "would make multilateral signing impossible" and was intentionally disabled: [2](#0-1) 

By contrast, the `ifRemote` branch of the same handler *does* verify that `from_address` is listed among `other_device_addresses` (the legitimate cosigner set) before proxying the request: [3](#0-2) 

This asymmetry means: when the target `body.address` is a single-sig address fully controlled by the local device (the common case, resolved via `my_addresses`/`wallets`/`wallet_signing_paths` in `findAddress`), *any* correspondent device can submit a well-formed `sign` request naming that address and signing path, and the wallet will build the to-be-signed unit, validate it, and fire a `"signing_request"` event exactly as if a legitimate cosigner had asked: [4](#0-3) 

This is the same bug class as the report: `MarginTrading.executeOperation` trusted the flash-loan callback's `_initiator` parameter without checking it was the contract itself, letting an unrelated third party drive privileged internal state changes (approvals) that culminate in fund loss. Here, the wallet's privileged "produce a signature offer for my address" pathway is reachable by an unrelated device without verifying it is a party entitled to request signing for that address/path, because the authorization check was deliberately removed.

### Impact Explanation
An attacker who is merely paired as a correspondent device (not necessarily a wallet cosigner) can repeatedly submit spoofed/spurious `sign` requests targeting the victim's own addresses and signing paths. This surfaces confirmation dialogs (`"signing_request"` events) to the victim's UI for units the attacker fully controls the content of (subject to output/format validation), which can be used for spam/fatigue attacks to trick a user into approving a malicious spend, or (in any automated/headless consumer of this event that doesn't re-verify the sender) to obtain signatures on attacker-crafted transactions, i.e., unauthorized spending of the victim's funds. This falls under "concrete unauthorized spending" / fund loss category.

### Likelihood Explanation
Likelihood is High for the spam/social-engineering variant since it requires only that the attacker be a paired device (a low bar - correspondent pairing is a normal, not privileged, wallet interaction) and a syntactically valid `sign` message; no special timing or race condition is needed. The severity of actual fund loss depends on whether a consuming application (UI or bot) blindly signs on this event without an additional identity check, which the core library itself does not enforce.

### Recommendation
Restore and enforce a check in the `ifLocal` branch of the `"sign"` handler that `from_address` is a genuine cosigner (or the sole owner in the single-key case) for `body.address` at `body.signing_path`, analogous to the check already performed in `ifRemote`:
```diff
 ifLocal: function(objAddress){
-    // the commented check would make multilateral signing impossible
+    if (!isAuthorizedCosigner(body.address, body.signing_path, from_address))
+        return callbacks.ifError("sender is not an authorized cosigner of this address/path");
     callbacks.ifOk();
     ...
```
For genuinely multi-device single-address (multisig) wallets, verify membership against `wallet_signing_paths`/`extended_pubkeys` for the specific wallet rather than omitting the check entirely.

### Proof of Concept
1. Attacker device D is a correspondent (paired) with victim wallet W, but D is not listed in any of W's `wallet_signing_paths`/`shared_address_signing_paths` for address A.
2. D sends a `"sign"` message to W: `{address: A, signing_path: "r", unsigned_unit: <attacker-crafted payment spending A's funds to attacker's address>}`.
3. `handleMessageFromHub` validates message shape (`wallet.js` lines 251-330), then calls `findAddress(A, "r", callbacks)`.
4. Since A is a local wallet address, `ifLocal` fires without checking that D is an authorized cosigner (`wallet.js` lines 334-339), builds the unit hash, validates it, and emits `"signing_request"` to the victim UI/automation layer.
5. If the consuming layer signs without independently checking the true requester's authorization (core provides none), the attacker obtains a valid signature over a transaction spending the victim's coins.
