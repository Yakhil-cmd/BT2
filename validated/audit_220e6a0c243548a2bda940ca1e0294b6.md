### Title
`StatusHandler#process` updates commit status across ALL repositories/stacks with no repository-scope check — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler`'s `ExplicitParameters::Parameters` schema declares only `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` — no repository-identifying field. `process` then queries `Commit.where(sha: params.sha)` globally and calls `commit.create_status_from_github!(params)` on every match, without ever checking that the matched commit's `stack.repository` corresponds to the webhook's originating `repository` field. Any webhook signed for one repository can therefore mutate commit status/state for commits belonging to a *different* repository's stack, as long as a SHA collision exists across stacks.

### Finding Description
Binding (as claimed by the question, verified true): `StatusHandler.param_parser` fields = `{sha, state, description, target_url, context, created_at, branches}` — no `repository`/`owner` field is declared: [1](#0-0) 

`process` performs no repository/stack scoping at all: [2](#0-1) 

This is a real anomaly relative to the base `Handler` class, which *does* provide a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)`: [3](#0-2) 

`StatusHandler` never calls `stacks` or `repository_name` — it bypasses that scoping mechanism entirely and queries `Commit` unscoped by any stack/repository: [2](#0-1) 

Compare to other handlers (e.g. `PullRequest::OpenedHandler`, `ClosedHandler`, `LabelCapturingHandler`) that explicitly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and scope all subsequent lookups (`review_stacks`, `stack`) to that repository: [4](#0-3) 

The signature check in `WebhooksController#verify_signature` only authenticates that the payload was signed by the GitHub App/organization matching `repository.owner.login` in the payload — it says nothing about which specific repository's data may be applied, and GitHub Apps are typically installed at the organization level, so the same webhook secret signs events from *every* repository under that org: [5](#0-4) [6](#0-5) 

Root cause: `create_status_from_github!` / `Status.replicate_from_github!` accept a `stack_id` from the *matched* `commit.stack_id`, not from anything validated against the webhook's `repository` field: [7](#0-6) [8](#0-7) 

**Exploit flow:** An attacker who controls (owns, has push access to, or can run CI/Actions in) any repository under a GitHub organization that Shipit tracks (even an unrelated scratch/sandbox repo under that org, since webhook secrets are per-organization) can push a commit with an identical SHA-1 to a commit that already exists in a *different* stack's repository under the same Shipit install (trivially achievable by copying/cherry-picking the exact commit object, since git commit hashes are portable data, not repository-bound). They then trigger (via their own CI or a personal token with push/status rights on their own repo) a genuine, correctly-signed GitHub `status` webhook for that SHA with `state: success` (or any state) and a chosen `context`. Because `StatusHandler.process` matches on `sha` alone across the entire `Commit` table, this creates a `Status` row attached to the unrelated stack/commit, potentially triggering `enable_ci_on_stack`, `schedule_continuous_delivery`, and `ProcessMergeRequestsJob` for a completely unrelated team's stack — none of which the attacker has any legitimate access to.

Existing guards fail to prevent this: `verify_signature` only certifies the org-level webhook secret was used, not that the target commit's stack matches the payload's `repository`; `ExplicitParameters` schema validates types/presence, not repository identity, exactly as the question's binding states.

### Impact Explanation
A status/state write occurs against a commit belonging to a stack/repository the attacker has no legitimate control over. This can flip a commit from `pending`/`failure` to `success` for an arbitrary matching-SHA commit in another team's stack, which cascades into `ProcessMergeRequestsJob` (merge-queue eligibility) and continuous-delivery status changes — i.e., "a payload for one repository mutating another's stack/commit," matching the Critical impact category. Blast radius is bounded by SHA-collision feasibility (trivial for an attacker who can copy commit objects between repos they and the victim both interact with, e.g. shared upstream history, forks, or submodules) and applies across every stack tracked by the same Shipit instance/organization.

### Likelihood Explanation
Requires: (1) the attacker controls at least one repository under a GitHub org/app installation that Shipit is configured for (a low bar if Shipit tracks many repos under one org, including sandbox/low-trust repos), and (2) the ability to get a legitimately-signed `status` event fired for a chosen SHA that also exists in a victim stack (achievable by copying commit objects, common in monorepo forks/mirrors/shared history). No Shipit secrets, sessions, or privileged roles are needed — only ordinary push/CI access to one tracked repository. This is repeatable at will for any SHA the attacker can reproduce.

### Recommendation
Add a repository-identifying field to `StatusHandler`'s params schema (mirroring other handlers' `requires :repository do requires :full_name, String end`), resolve the repository via `Repository.from_github_repo_name`, and scope the commit lookup to that repository's stacks (`stacks.commits.where(sha: params.sha)` or equivalent join through `stack: :repository`) before calling `create_status_from_github!`.

require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "param_parser declares no repository-identifying field" do
          fields = StatusHandler.param_parser.parameters.keys # or equivalent introspection API
          assert_equal %i[sha state description target_url context created_at branches], fields.sort
          refute_includes fields, :repository
          refute_includes fields, :owner
        end

        test "a status payload with no repository binding updates a commit belonging to an unrelated stack" do
          stack_a = shipit_stacks(:shipit)     # repository A
          stack_b = shipit_stacks(:cyclimse)   # repository B, unrelated

          colliding_sha = "6d9278037b872fd9a6690523e411ecb3aa181355"
          commit_in_b = stack_b.commits.create!(sha: colliding_sha, ...)

          payload = {
            'sha' => colliding_sha,
            'state' => 'success',
            'context' => 'ci/attacker',
            'repository' => { 'full_name' => stack_a.repository.github_repo_name } # attacker's own repo
          }

          assert_difference -> { commit_in_b.statuses.count }, 1 do
            StatusHandler.call(payload)
          end
          # Demonstrates: webhook "authenticated" for repository A's org
          # created a Status for a commit belonging to repository B's stack —
          # no repository cross-check exists in params or process().
        end
      end
    end
  end
end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))
