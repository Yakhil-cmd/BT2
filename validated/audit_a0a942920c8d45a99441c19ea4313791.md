### Title
`BridgeTransferERC721` Uses Bare `transferFrom` Instead of `safeTransferFrom`, Enabling Unauthorized Cross-Chain NFT Minting With Non-Standard Tokens — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721` calls bare `IERC721.transferFrom()` in both the deposit path (`requestERC721Transfer`, line 129) and the withdrawal path (`handleERC721Transfer`, line 69). The sibling contract `BridgeTransferERC20` correctly uses `safeTransferFrom`/`safeTransfer` from `SafeERC20` for every ERC20 movement. The ERC721 paths have no equivalent guard. With a non-standard ERC721 token that silently returns instead of reverting on a failed transfer, the deposit path allows a user to trigger a cross-chain transfer request — and consume a bridge nonce — without the bridge ever taking custody of the NFT, causing the counterpart bridge to release or mint an NFT on the destination chain for free.

---

### Finding Description

`BridgeTransferERC20` imports `SafeERC20` and declares `using SafeERC20 for IERC20`, so every token movement uses `safeTransferFrom` or `safeTransfer`:

```
// BridgeTransferERC20.sol line 29, 71, 133
using SafeERC20 for IERC20;
IERC20(_tokenAddress).safeTransfer(_to, _value);          // handleERC20Transfer
IERC20(_tokenAddress).safeTransferFrom(msg.sender, ...);  // requestERC20Transfer
```

`BridgeTransferERC721` imports no safe wrapper and uses bare calls:

```
// BridgeTransferERC721.sol line 69 — withdrawal path
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// BridgeTransferERC721.sol line 129 — deposit path
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
_requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
```

In the deposit path the sequence is:
1. `transferFrom` is called — if the token silently returns without reverting, the bridge does **not** hold the NFT.
2. `_requestERC721Transfer` is called unconditionally, which emits `RequestValueTransferEncoded` and increments `requestNonce`.
3. The bridge relayer on the counterpart chain observes the event and calls `handleERC721Transfer`, which either mints or releases the NFT to the recipient.

The bridge invariant — *the source bridge must hold the NFT before a cross-chain request is emitted* — is broken.

In the withdrawal path (`handleERC721Transfer`, `onlyOperators`), if `transferFrom` silently fails, the bridge marks the nonce as handled (`_updateHandleNonce`) and emits `HandleValueTransfer`, but the recipient never receives the NFT. The nonce is consumed and cannot be retried, permanently locking the asset in the bridge.

---

### Impact Explanation

**Deposit path (unprivileged, high impact):** Any user can call `requestERC721Transfer` with a registered non-standard ERC721 token. If the token's `transferFrom` silently returns without reverting, the user retains the NFT on the source chain while the counterpart bridge mints or releases an equivalent NFT on the destination chain. This is an unauthorized mint/unlock of a bridged asset.

**Withdrawal path (operator-triggered, medium impact):** A non-standard token's silent `transferFrom` failure causes the bridge to consume the handle nonce and emit `HandleValueTransfer` without delivering the NFT. The asset is permanently locked in the bridge with no retry mechanism, because `_lowerHandleNonceCheck` will reject any future attempt to handle the same nonce.

---

### Likelihood Explanation

The bridge owner can register any ERC721 token address. Non-standard ERC721 tokens that do not revert on failure exist in practice (analogous to USDT for ERC20). The deposit path (`requestERC721Transfer`) is callable by any unprivileged user once a vulnerable token is registered. No special role or majority-validator collusion is required.

---

### Recommendation

Mirror the ERC20 bridge pattern. Import a safe ERC721 wrapper (e.g., OpenZeppelin's `SafeERC721` or an equivalent `callOptionalReturn` helper) and replace both bare calls:

```solidity
// deposit path
IERC721(_tokenAddress).safeTransferFrom(msg.sender, address(this), _tokenId);

// withdrawal path
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

Using `safeTransferFrom` also triggers the `onERC721Received` callback on the recipient if it is a contract, preventing NFTs from being locked in non-receiver contracts on the withdrawal path.

---

### Proof of Concept

1. Deploy a non-standard ERC721 token whose `transferFrom` emits a `Transfer` event but does **not** actually change ownership and does **not** revert.
2. Have the bridge owner register this token on both the source and counterpart bridges.
3. Call `requestERC721Transfer(tokenAddress, victimAddress, tokenId, "0x")` on the source bridge.
4. The source bridge's `transferFrom` call silently returns; the bridge does not hold `tokenId`.
5. `_requestERC721Transfer` emits `RequestValueTransferEncoded` with `requestNonce = N` and increments `requestNonce` to `N+1`.
6. The bridge relayer picks up the event and calls `handleERC721Transfer` on the counterpart bridge with nonce `N`.
7. The counterpart bridge mints or releases `tokenId` to `victimAddress` (or the attacker's chosen `_to`).
