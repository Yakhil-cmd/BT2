### Title
Cross-organization webhook signature bypass via attacker-chosen `repository.owner.login` selecting a blank-secret `GithubApp` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` config to validate a webhook against using `repository_owner`, which is read directly from the unauthenticated JSON body via `params.dig('repository','owner','login')`, before any signature has been checked. `GithubApp#verify_webhook_signature` unconditionally returns `true` when the selected app's `webhook_secret` is blank/nil, so any org configured without a secret becomes a universal bypass key for the shared `/webhooks` endpoint.

### Finding Description
The claimed binding is: `Shipit.github(organization: repository_owner).webhook_secret` must always correspond to the org that actually owns the event being processed, and `verify_webhook_signature` must never validate `true` for an unauthenticated request. Tracing the code:

- `event` and `repository_owner` are both derived from attacker-controlled input before `verify_signature` runs: [1](#0-0) 
- `verify_signature` uses `repository_owner` to pick the `GitHubApp` instance, then checks the signature against that app's own secret: [2](#0-1) 
- `Shipit.github(organization:)`/`github_app_config` map `organization` (lowercased) directly to one of the operator-configured keys under `secrets.github`, raising `GithubOrganizationUnknown` (→422) only if the org name isn't one of the configured ones: [3](#0-2) 
- `GithubApp#verify_webhook_signature` short-circuits to `true` whenever the selected app's `webhook_secret` is blank: [4](#0-3) 

In a multi-org deployment (the documented pattern in `docs/setup.md` "Using Multiple Github Applications"), each org gets its own `webhook_secret`. If *any* configured org lacks a secret (which the shipped example config `config/secrets.development.shopify.yml` explicitly shows as commented `# nil` for multiple orgs, and `docs/setup.md` calls the webhook secret "optional"), an attacker can:
1. Send `POST /webhooks` with `repository.owner.login` set to the blank-secret org (selecting that `GithubApp` so `verify_webhook_signature` returns `true` unconditionally).
2. Set `repository.full_name`/other payload fields to reference a *different*, protected org/repo's stack.
3. Because `#create` never re-validates that the verified org actually matches the repository the handlers act on — handlers key off `repository.full_name`/commit sha from the same attacker-supplied JSON body, not off `repository_owner` — the forged event is processed as if it came from the protected org, with no valid signature ever checked against that org's real secret.

The existing "protections" (`drop_unhandled_event`, `check_if_ping`, `verify_signature`'s `GithubOrganizationUnknown` rescue) all operate on the same attacker-supplied fields and do not compare the verified org identity against the repository actually referenced by the event body, so the divergence is real, not closed by any guard I found. This is a decoupling bug: authentication is scoped per-configuration-key while trust is applied to a repository name pulled from the same untrusted payload.

### Impact Explanation
An attacker who knows (or guesses) that a shipit instance has one org configured without a `webhook_secret` can forge push/status/check_suite/pull_request/membership events for **any** repository/org tracked by that Shipit instance, without possessing any real GitHub webhook secret. Depending on which handler is hit this can trigger unauthorized `GithubSyncJob` runs, fabricated commit statuses, forged team membership changes (`Team`/`Membership` creation, as seen in the `:membership` tests), or spoofed PR events feeding into deploy/merge automation — i.e., authentication bypass on `POST /webhooks` leading to unauthorized state changes for a stack that never authenticated the request. This matches the "authentication bypass (forged webhook ... accepted)" Critical impact category, scoped here as cross-org/cross-repository forgery, not merely a same-org false-authentication.

### Likelihood Explanation
This requires the operator to run **multi-org mode** with at least one configured org whose `webhook_secret` is left blank (a state the shipped docs/example configs explicitly present as valid/optional). Given that, exploitation costs the attacker nothing more than crafting a single unauthenticated HTTP POST with a chosen `repository.owner.login`/`organization.login` and an arbitrary `repository.full_name`/commit data — no secrets, sessions, or tokens are needed, and the request is trivially repeatable against any repository tracked by the instance. The precondition (a misconfigured/no-secret org present alongside protected orgs) is plausible but not guaranteed for every deployment, so likelihood is conditional on that operator configuration.

### Recommendation
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank in multi-org mode; only permit the "no secret configured" bypass for the legacy single-app schema (`github_default_organization.nil?`), and require a secret for every entry under a multi-org `secrets.github` config (fail closed / raise at boot if missing).
- After signature verification, ensure the verified `organization` actually matches the org portion of `repository.full_name` (or whatever repository identifier the handler resolves), rejecting the event if they diverge.
- Consider validating `repository.owner.login` against the Stack lookup result rather than trusting it solely for `GithubApp` selection.

```ruby
test "blank-secret org cannot be used to forge events for a protected org's repository" do
  # Multi-org secrets: orgA has webhook_secret set, orgB has webhook_secret: nil

    repository: { owner: { login: 'orgb' }, full_name: 'orga/protected-repo' },
    after: 'deadbeef'

  # No X-Hub-Signature header at all / garbage signature
  assert_no_enqueued_jobs do
    post :create, body: payload, as: :json
  end
  # Binding under test: Shipit.github(organization: 'orgb').verify_webhook_signature(nil, payload)
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
```
