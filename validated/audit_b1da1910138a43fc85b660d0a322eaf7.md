### Title
Webhook signature verified against `repository.owner.login`'s secret while handlers act on a different `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound GitHub webhook based on the attacker-controlled field `repository.owner.login` (or `organization.login`), but the event handlers that actually act on the payload resolve the target `Repository`/`Stack` using a different, independently-controlled field: `repository.full_name`. In a multi-tenant Shipit deployment (multiple GitHub organizations each configured with their own `webhook_secret` in `secrets.github`), these two fields are never checked for consistency, so a party who knows the webhook secret for one onboarded organization can forge webhook events that are processed as if they came from a different organization's repository.

### Finding Description
`verify_signature` picks the verifying app/secret using only `repository_owner`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves a per-organization `GitHubApp` (and its distinct `webhook_secret`) via `github_app_config`: [3](#0-2) 

Once the signature check passes, the raw JSON body is dispatched unmodified to the matching handlers: [4](#0-3) 

Handlers, however, determine which `Repository`/`Stack` to act on from a **different** JSON key, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

For example, `PushHandler` uses that repository resolution to look up stacks and trigger a GitHub sync: [6](#0-5) 

The binding that should hold is: `organization whose secret authenticated the request == organization/repository the handler executes side effects on`. Because `verify_signature` reads `repository.owner.login`/`organization.login` while `Handler#repository_name` reads `repository.full_name`, these two are independently attacker-supplied JSON fields inside the same signed body. A party who legitimately administers Organization A in this Shipit instance (and therefore knows Org A's GitHub webhook secret, since that secret is set by the org's own GitHub webhook configuration) can craft a payload where:
- `repository.owner.login` = `"OrgA"` (used only to pick the verifying secret)
- `repository.full_name` = `"OrgB/some-repo"` (used by the handler to find the actual Stack to act on)
- `X-Hub-Signature` computed over the full body using Org A's known secret.

`verify_signature` will resolve and validate against Org A's secret and succeed, then the handler dispatches the same payload and resolves `OrgB/some-repo`'s stacks via `repository_name`, acting on infrastructure the attacker was never authorized for.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated versus the repository that is written." Depending on which event/handler is targeted, the forged cross-organization webhook can trigger unauthorized side effects against a stack/repository the attacker does not control — e.g. `PushHandler` forcing a `sync_github` against another org's stack, or other handlers under `app/models/shipit/webhooks/handlers/pull_request/**` acting on pull-request/merge state for a repository the attacker doesn't own. This falls in the "unauthorized deploy/rollback/merge" or "unauthenticated read/state manipulation of stack state" category depending on the specific handler reached, since the request is treated as validly signed for a repository it was never actually signed for.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate administrator/owner of at least one GitHub organization that is already onboarded into the same multi-tenant Shipit instance (so they know that organization's `webhook_secret`), and for the target instance to host multiple organizations under `secrets.github` with independent secrets, which is an explicitly supported configuration (`github_app_config`/`github_organizations` in `lib/shipit.rb`). This is a realistic scenario for shared/hosted Shipit deployments serving several tenants, but does not apply to single-organization deployments where `github_default_organization` is `nil` and a single global secret is used for all events.

### Recommendation
Have `verify_signature` and the handlers derive the organization/repository identity from the **same** field, or cross-check that `repository.owner.login` matches the owner portion of `repository.full_name` before dispatching. Alternatively, once a webhook has been verified for organization X, filter/validate that all repositories referenced in the payload actually belong to organization X (e.g., via the `Repository` record's known owner) before invoking handlers, rejecting the request otherwise.

### Proof of Concept
1. Deploy Shipit with two organizations configured in `secrets.github`, `OrgA` and `OrgB`, each with a distinct `webhook_secret`.
2. As an attacker who administers `OrgA` (and therefore knows `OrgA`'s webhook secret), craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>`.
4. POST to `/webhooks` with `X-Github-Event: push` and the above headers/body.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature using `OrgA`'s secret [1](#0-0) .
6. `PushHandler` resolves stacks via `repository.full_name` = `"OrgB/target-repo"` [5](#0-4)  and triggers `stack.sync_github` for a stack the attacker does not own [6](#0-5) .

**Uncertainty**: I was unable to fully trace the concrete write/deploy impact of every handler under `app/models/shipit/webhooks/handlers/pull_request/**` within the remaining tool budget (e.g., whether `closed_handler.rb` can trigger an actual merge or deploy trigger), so the maximum severity of the cross-org forgery depends on which specific event type is abused and would need further verification by a Devin session with full file access.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
