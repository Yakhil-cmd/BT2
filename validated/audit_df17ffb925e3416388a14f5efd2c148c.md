Based on my code investigation, this is a real vulnerability. Here is the full analysis:

---

### Title
Peer-Supplied `P2PStakingInfo.BlockNum` Used as DB Key Without Validation Against Header Number During Fast-Sync — (`datasync/downloader/downloader.go`)

### Summary

During fast-sync, `commitFastSyncData` and `commitPivotBlock` write staking info to the DB using the peer-supplied `result.StakingInfo.BlockNum` as the key, with no check that it matches `result.Header.Number`. A malicious P2P peer can deliver a `P2PStakingInfo` with an arbitrary `BlockNum`, writing attacker-controlled validator/reward addresses to any epoch-boundary slot in the staking DB.

### Finding Description

`fetchResult` holds both a validated `Header` and a peer-supplied `StakingInfo`: [1](#0-0) 

The staking-info pending bit is set only for epoch-boundary headers (`header.Number % stakingUpdateInterval == 0`): [2](#0-1) 

When results are committed, the DB write uses `result.StakingInfo.BlockNum` — the peer-controlled field — not `result.Header.Number`: [3](#0-2) 

The same pattern repeats in `commitPivotBlock`: [4](#0-3) 

`PutStakingInfoToDB` passes `sourceNum` directly to `WriteStakingInfo`, which uses it as the DB key with no bounds or consistency check: [5](#0-4) [6](#0-5) 

`P2PStakingInfo.BlockNum` is fully peer-controlled — it is decoded from RLP without any validation: [7](#0-6) 

`ToStakingInfo` propagates the peer-supplied `BlockNum` into `SourceBlockNum` of the stored `StakingInfo` unchanged: [8](#0-7) 

There is no code anywhere in the downloader that asserts `result.StakingInfo.BlockNum == result.Header.Number.Uint64()`.

### Impact Explanation

The staking DB maps epoch-boundary block numbers to `StakingInfo` structs containing `NodeIds` (validator node IDs), `RewardAddrs` (block reward recipients), `StakingContracts`, `KEFAddr`, and `KIFAddr`. These are the authoritative inputs to validator-set selection and block-reward distribution for each epoch.

By delivering a `P2PStakingInfo` with `BlockNum=F` (any future epoch boundary) while the enclosing header is at block `N`, the attacker writes attacker-controlled `RewardAddrs` and `NodeIds` to `stakingInfoKey(F)`. When the synced node reaches epoch `F` in normal operation, it reads the corrupted entry and:

- Routes block rewards to attacker-controlled addresses (unauthorized reward distribution).
- Uses attacker-controlled node IDs for validator-set selection (privilege escalation over protected chain state).

The `GetStakingInfoFromDB` comment confirms this DB is the authoritative P2P-sync source, not a re-derivable cache: [9](#0-8) 

### Likelihood Explanation

The attacker only needs to be a connectable P2P peer during the victim's fast-sync. No privileged keys, governance access, or validator collusion is required. The victim initiates fast-sync on first boot or after a wipe, making this a realistic network-level attack against any new or resyncing node.

### Recommendation

In both `commitFastSyncData` and `commitPivotBlock`, validate that the peer-supplied `BlockNum` matches the enclosing header's block number before writing to the DB. Reject (and drop) the peer if they differ:

```go
if result.StakingInfo != nil {
    if result.StakingInfo.BlockNum != result.Header.Number.Uint64() {
        // drop peer, return error
    }
    d.stakingModule.PutStakingInfoToDB(result.Header.Number.Uint64(), staking.ToStakingInfo(result.StakingInfo))
}
```

Use `result.Header.Number.Uint64()` — the locally-validated value — as the DB key, never the peer-supplied `BlockNum`.

### Proof of Concept

1. Construct a mock peer that, when asked for staking info at block `N` (an epoch boundary), returns a `P2PStakingInfo` with `BlockNum=0` and attacker-controlled `RewardAddrs`/`NodeIds`.
2. Run the victim node in fast-sync mode connected only to this peer.
3. `commitFastSyncData` calls `PutStakingInfoToDB(0, ...)`.
4. Assert `ReadStakingInfo(db, 0)` returns the injected attacker data.
5. Assert `ReadStakingInfo(db, N)` is `nil` (the correct slot was never written).
6. Repeat with `BlockNum` set to a future epoch boundary `F > pivot` to pre-poison the validator set for epoch `F`.
