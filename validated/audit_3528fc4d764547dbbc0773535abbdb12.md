### Title
`spender_attested` output-attestation check is applied to `definer_address` even for `auto_destroy` assets, permanently blocking legitimate destroy-transfers - ([File: validation.js])

### Summary
For assets defined with both `auto_destroy: true` and `spender_attested: true`, `validatePaymentInputsAndOutputs` requires *every* output address (including the asset's `definer_address`, which is the designated "burn" destination for `auto_destroy` assets) to be attested. Since the definer is generally not expected to be in its own attestor's attested-addresses set, any transfer that sends an output to `definer_address` in order to destroy coins is rejected, permanently disabling the destroy mechanism for that asset — the same bug class as "perWalletLimit applied to address(0)/burn address" in the referenced report.

### Finding Description
`auto_destroy` assets treat the `definer_address` as the burn/zero address: outputs sent to it are considered destroyed, and this is specially handled when validating transfer inputs (an owner address equal to `definer_address` is rejected as "already destroyed"): [1](#0-0) 

However, when finalizing validation of a payment message for a `spender_attested` asset, the code unconditionally attests *all* `arrOutputAddresses` — there is no exemption for `definer_address` even though it is the canonical destroy target for `auto_destroy` assets: [2](#0-1) 

`arrOutputAddresses` is populated from every output address in `payload.outputs` without excluding the definer: [3](#0-2) 

Nothing in `validateAssetDefinition` prevents an unprivileged asset issuer from combining `auto_destroy: true` with `spender_attested: true`: [4](#0-3) 

Because the attestation-filter check (`storage.filterAttestedAddresses`) requires the attested-address count to equal `arrOutputAddresses.length`, any transfer whose output includes `definer_address` (i.e., every attempt to destroy tokens) will fail with `"some output addresses are not attested"` unless the definer happens to also be an attested address. This mirrors the OpenZeppelin report exactly: a wallet/attestation restriction is applied uniformly to the address that represents the burn/destroy sink, without special-casing it, so the burn path is permanently broken for any such asset unless the issuer thinks to self-attest.

### Impact Explanation
Any AA or wallet protocol built around an `auto_destroy` + `spender_attested` asset (e.g., a redemption/exit mechanism where users "burn" shares by sending them to the definer address) becomes permanently unable to process destroy-transfers. Funds represented by that asset become effectively frozen/stuck for any holder relying on the destroy path, since the validating unit will always be rejected. This falls under "AA fund loss or freezing," reachable purely by an unprivileged asset issuer defining such an asset and any user attempting a legitimate transfer to the definer.

### Likelihood Explanation
Likelihood is Medium: it requires an asset definer to choose the specific combination `auto_destroy: true` + `spender_attested: true` without also attesting their own `definer_address`. This is a plausible, unprivileged configuration (nothing in `validateAssetDefinition` warns against or disallows it), and is analogous to a common oversight pattern seen in the reference report (forgetting to exempt the special/burn address from a general-purpose restriction).

### Recommendation
In `validatePaymentInputsAndOutputs`, when `objAsset.auto_destroy` is true, exclude `objAsset.definer_address` from the set of addresses that must pass `filterAttestedAddresses`, consistent with how it is already excluded from the "not attested" ownership check for auto-destroyed inputs. Alternatively, document/enforce that `spender_attested` assets must include the definer address in every issued attestation, or reject the `auto_destroy` + `spender_attested` combination at definition time.

### Proof of Concept
1. An issuer defines an asset with `auto_destroy: true`, `spender_attested: true`, and a set of `attestors` that never attest `definer_address` itself (validation.js:2725-2733 places no restriction against this combination).
2. A holder of the asset attempts to "burn"/destroy their balance by sending a payment output to `definer_address` (the standard `auto_destroy` mechanism, validation.js:2504-2505).
3. During validation of that payment, `objAsset.spender_attested` is true, so `arrOutputAddresses` (which includes `definer_address`, validation.js:2151-2194) is checked via `storage.filterAttestedAddresses` (validation.js:2630-2642).
4. Since `definer_address` is not part of the attested-address set, `arrAttestedOutputAddresses.length !== arrOutputAddresses.length`, and the unit is rejected with `"some output addresses are not attested"`.
5. Every subsequent attempt to destroy the asset fails the same way — the destroy path is permanently unusable for this asset.
