### Title
`runWithStdin` uses `exec.CommandContext` without process-group isolation, so context expiry kills only the direct child and leaves grandchild/orphan processes running - ([File: pkg/cmd/cmd.go])

### Finding Description
`runWithStdin` builds the command with `cmd := exec.CommandContext(ctx, command, args...)` and never sets `cmd.SysProcAttr` (e.g. `Setpgid: true`) or a `Cancel`/`WaitDelay` function that kills a process group. [1](#0-0) . Go's `exec.CommandContext` default cancellation behavior only calls `Process.Kill()` (SIGKILL) on the single tracked PID when the context is done — it does not send anything to a process group, and it never propagates to any children that the command itself spawns (a shell script forking a background job, `git` invoking a remote helper, or an exec-hook script that daemonizes/detaches). [2](#0-1) 

This function is the single execution primitive used both for internal git invocations and for user-configured hooks. `Exechook.Do` derives a bounded context via `context.WithTimeout(ctx, h.timeout)` and calls `h.cmdrunner.Run(ctx, worktreePath, env, h.command, h.args...)`, which funnels into `runWithStdin`. [3](#0-2)  If the attacker-controlled repo content causes the hook command (or any git subprocess it spawns/forks) to survive past `h.timeout`/the context deadline — e.g., by forking a detached child, ignoring SIGKILL delivery to only the parent, or spawning a long-lived process — `cmd.Run()` returns once the parent is killed, but any forked descendant keeps running, holding open file descriptors/locks in the `--root` worktree and consuming CPU indefinitely.

Because there is no process-group kill, no `WaitDelay`, and no reaping of orphaned descendants, "no subprocess outlives its context" is violated whenever a hook or git-invoked helper forks before the parent is reaped.

### Impact Explanation
An attacker who controls the repository content (able to make the fetched tree trigger a hook, or otherwise trigger a git operation that forks children) can cause leaked processes that hold the shared `--root` volume, consume CPU/memory, and potentially keep file locks/mmaps open in the worktree directory, contributing to resource exhaustion and a wedged repository state — matching the "resource exhaustion / locked state" bug class referenced in the question.

### Likelihood Explanation
This requires the deployment to actually run a hook (`--exechook-command`/`--webhook-url` style flags, which are documented, supported features) with a `timeout` value, and it requires the invoked command to be able to fork/detach a child that survives its parent's SIGKILL — plausible with common shell constructs (`nohup ... &`, `setsid`, background job managers) or with git helpers that spawn subprocesses. No non-default or unsupported flags are needed beyond the documented hook flags. The vulnerability is a real gap in `runWithStdin`'s process lifecycle handling (missing `SysProcAttr.Setpgid`/`Pgid` kill and no `WaitDelay`), independent of any misconfiguration.

### Recommendation
- Set `cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}` before starting the command, and install a `cmd.Cancel` function that sends `syscall.Kill(-pgid, syscall.SIGKILL)` to the whole process group instead of relying on the default single-process kill.
- Set `cmd.WaitDelay` (Go 1.20+) so that if the process doesn't exit promptly after the group kill, `cmd.Wait()` returns instead of blocking forever, and log/report orphaned descendants.
- Consider reaping/closing the process group explicitly on context cancellation in `runWithStdin`, and add a unit test that starts a script which forks a detached grandchild, cancels the context, and asserts the grandchild is also terminated (e.g., by checking `/proc` or process liveness after a grace period).

### Proof of Concept
Unit test sketch for `pkg/cmd/cmd_test.go`:
```go
func TestRunWithStdin_OrphanSurvivesContextKill(t *testing.T) {
    ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
    defer cancel()

    // script forks a detached grandchild that sleeps well past the deadline
    script := `sh -c 'nohup sleep 30 & echo $!'`
    _, _, err := runWithStdin(ctx, testLogger, "", nil, "", "/bin/sh", "-c", script)
    // err will be DeadlineExceeded
    time.Sleep(500 * time.Millisecond)
    // Assert: the "sleep 30" PID printed to stdout is still alive -- demonstrates
    // that CommandContext's kill did not reach the orphaned grandchild.
}
```
Expected (buggy) result: the `sleep 30` process is still running after the parent was killed by context expiry, demonstrating the orphan leak described above. A fixed implementation (process-group kill + `WaitDelay`) should terminate the grandchild as well.
