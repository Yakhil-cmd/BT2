Confirmed: `Shipit::Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the model class, bypassing `BaseController#stacks`, which is the method that enforces `current_api_client.stack_id?` scoping [1](#0-0) . Every other API controller (`StacksController`, `MergeRequestsController`, etc.) reaches `stack` through the scoped `stacks` relation [2](#0-1) , but `CCMenuController` does not [3](#0-2) .

### Title
Stack-scoped `ApiClient` tokens can read any stack's CCTray status via `CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target `Stack` directly from `Stack.from_param!(params[:stack_id])` instead of going through `BaseController#stacks`, the method responsible for restricting a stack-scoped `ApiClient` to its own `stack_id`. This breaks the equality `stack a token authorizes == stack a token touches`: a token minted for stack A is accepted (`require_permission :read, :stack` only checks the permission name, not the scope) and then used to read status/output data for any stack B.

### Finding Description
`ApiClient` records can optionally be scoped to a single stack via `belongs_to :stack, optional: true` [4](#0-3) . The intended enforcement of that scoping lives in `BaseController#stacks`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

Every permission check in the API is scope-name based only — `require_permission :read, :stack` calls `current_api_client.check_permissions!(:read, :stack)`, which merely verifies that the string `"read:stack"` is in `permissions`, with no per-stack awareness [5](#0-4) . The actual stack restriction depends entirely on the base `stack`/`stacks` helper being used.

`CCMenuController` overrides that helper:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

This calls the `Stack` model directly, never consulting `current_api_client.stack_id`, so a token scoped to stack A is honored for any `stack_id` supplied in the request. The fixtures confirm stack-scoped clients exist by design, e.g. `here_come_the_walrus` is scoped to the `shipit` stack [6](#0-5) , and other controllers/tests demonstrate the intended restriction (`"an api client scoped to a stack will only see that one stack"`) [7](#0-6) . No equivalent restriction test exists for `CCMenuControllerTest`, and its own test suite passes an arbitrary `stack_id` while authenticating with the generic `:spy` client whose token is unscoped [8](#0-7) .

### Impact Explanation
An `ApiClient` token that was deliberately restricted to one stack (e.g. issued via `CCMenuUrlController`, which always creates a `read:stack`-only, unscoped-by-default client, or any stack-scoped client created through the `ApiClientsController` UI) can be replayed against `/api/:stack_id/cctray.xml` with a different `stack_id` and will successfully read that other stack's deploy/rollback status and build metadata. This is a read-only cross-repository/cross-stack information disclosure that violates the intended per-token stack boundary, matching the "unauthenticated/unauthorized read of stack state" class of impact — though note this still requires possession of *some* valid API token, and the boundary crossed is stack-scope, not authentication itself.

### Likelihood Explanation
Any holder of a valid `ApiClient` authentication token (Basic auth or `?token=` query param, both accepted by `CCMenuController#authenticate_api_client`) can trivially exploit this by changing the `stack_id` route segment. No special privilege beyond having any token is required, and the token does not need `deploy`/`write` permissions — `read:stack` (the minimum permission) is enough.

### Recommendation
Change `CCMenuController#stack` to reuse the base `stacks` scoping instead of calling `Stack.from_param!` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
and remove the now-redundant private override, relying on `BaseController#stacks`/`#stack`.

### Proof of Concept
1. Create two stacks, `stack_a` and `stack_b`.
2. Create an `ApiClient` scoped to `stack_a` (`stack_id` set) with only the `read:stack` permission, and obtain its `authentication_token`.
3. Request `GET /api/stack_b/cctray.xml` (or the equivalent `stack_id` route for `CCMenuController#show`) using Basic auth with that token, e.g.:
```
curl -u "<client.authentication_token>:" https://shipit.example.com/api/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/cctray.xml
```
4. Observe a `200 OK` response containing `stack_b`'s deploy status, despite the token being scoped only to `stack_a` — because `CCMenuController#stack` never checks `current_api_client.stack_id`.
