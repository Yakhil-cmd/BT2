### Title
Tokens sent directly to the liquidity pool are permanently locked — the pool only pays out against its `cash` book, which donations never credit - (File: contracts/pool/src/cache/cash.rs)

### Summary
The UXD report's bug class — "contract can receive funds but has no way to release them" — maps onto XOXNO Lending's `LiquidityPool` contract. Any user can push an arbitrary amount of a market's underlying token to the pool address with a plain Stellar Asset Contract `transfer`. The pool tracks liquidity in an internal bookkeeping field `cash` (per `(hub_id, asset)` market state), and every outbound token movement is bounded by that book, never by the real `token.balance()` of the pool. A direct transfer raises the SAC balance but leaves `cash` untouched, so no entrypoint can ever pay the donated amount out. There is no rescue/sweep/recover entrypoint on the pool ABI — all fourteen mutators are `#[only_owner]` (the controller), and the controller itself exposes no sweep either.

### Finding Description
The pool's outbound paths are:

- `borrow` / `withdraw` / `claim_revenue` / `create_strategy` — call `Cache::debit_cash` / `require_reserves` before `transfer_out`, so they are capped by the `cash` book (`contracts/pool/src/cache/cash.rs:15-53`). `debit_cash` requires `self.cash >= amount`; `transfer_out` just sends the token.
- `repay` and `recapitalize` refund legs — bounded by the declared inbound `amount`, which the controller measures from its own transfer (`contracts/pool/src/ops/recapitalize.rs:52-55`); a stray balance is never included.
- `flash_loan` — reconciles balances with strict equality around the callback, but only over principal + fee; it never touches excess balance.

Inbound paths (`supply`, `repay`, `recapitalize`) credit `cash` only on the controller's word for amounts the controller itself moved (`contracts/pool/README.md:54-63` — "`supply`, `repay` and `recapitalize` all credit `cash` on the controller's word, without verifying the transfer. `cash` is a bookkeeping number."). A third-party `transfer` to the pool address therefore inflates real custody while the book stays flat: `get_reserves` returns `state.cash`, not the SAC balance (`contracts/pool/src/views.rs:22-24`).

The pool constructor sets the owner once to the controller (`contracts/pool/src/lib.rs:94-96`) and the ABI exposes no `sweep_balance`, `rescue`, or arbitrary-transfer function — contrast `contracts/swap-aggregator/src/lib.rs:189-203`, which has an owner-gated `sweep_balance` precisely for this class. The controller's own entrypoints (`supply`, `recapitalize`, etc.) all measure their own transfers; none drains a pre-existing pool balance, and nothing is callable on the pool by a user to skim the excess.

### Impact Explanation
Permanent freezing of funds: any token amount pushed to the pool contract address outside a controller-mediated flow is irrecoverable. The funds are not even socialized to suppliers — supply-share value derives from `supplied * supply_index`, which the donation does not change — so the tokens are simply burned inside the contract. The same applies to direct transfers to the controller address for tokens the controller never measures.

### Likelihood Explanation
Low-to-moderate. It requires a user (or an integrating contract with a buggy payout target) to send tokens to the pool/controller address by mistake, or a griefing/donation transaction. SAC `transfer` is a single unprivileged call, so the path is trivially reachable; accidental sends are the realistic scenario, matching the original report's Medium framing.

### Recommendation
Add an owner-gated (controller-gated) skim that pays out `token.balance(pool) - total_obligations` (i.e., balance above `cash` across the relevant market, or for non-market tokens the full balance), or have the controller expose a `claim_revenue`-style recovery for unbooked balances. At minimum, document that direct transfers are unrecoverable and add a monitored allowlist in integrations. Alternatively, let `recapitalize` optionally credit the measured live-balance surplus over the book rather than only the controller-declared amount.

### Proof of Concept
```rust
// Any user; no auth from pool/controller needed.
let sac = token::StellarAssetClient::new(&env, &usdc);
sac.mint(&alice, &1_000);
token::Client::new(&env, &usdc).transfer(&alice, &pool_addr, &1_000);

// Pool state is unchanged: cash book does not see the donation.
assert_eq!(pool_client.get_reserves(&hub_asset), cash_before);
assert_eq!(token::Client::new(&env, &usdc).balance(&pool_addr), custody_before + 1_000);

// No entrypoint can move the extra 1_000 out:
//  - withdraw/borrow/claim_revenue are capped by `cash` via require_reserves
//  - recapitalize/repay refunds are capped by the controller-declared amount
//  - there is no sweep/rescue function on the ABI
// The 1_000 units are locked for the lifetime of the contract (pre-upgrade).
```

Note: a donation also widens the gap between real custody and the `cash` book, which interacts with `flash_loan`'s strict balance reconciliations; I did not fully verify whether the check is `balance == balance_before + fee` (donation-safe) or `balance == cash` (donation breaks flash loans) — if the latter, the same transaction is also a fail-closed DoS vector, though that secondary effect would be out of scope per the scan rules.
