### Title
Unsafe `uint64`→`int64` Cast in `consolidatedNode.Split` Corrupts CN/CL Reward Distribution — (`File: kaiax/staking/staking_info.go`)

### Summary

`consolidatedNode.Split`, the function that proportionally divides every block reward between a validator's CN staking contract and its CL (consensus-liquidity) pool, converts both `uint64` staking amounts to `int64` via a bare Go cast before constructing `big.Int` weights. If either amount exceeds `math.MaxInt64` KAIA (~9.22 × 10⁹ KAIA), the cast silently produces a negative value, corrupting the divisor used for every reward split in that block.

### Finding Description

`consolidatedNode.Split` is called at every block finalization for each validator that has a CL pool registered (Prague hardfork / KIP-226). The function computes the proportional share of a reward `amount` that goes to the CL pool:

```go
// kaiax/staking/staking_info.go  lines 174-181
cnAmountBig = big.NewInt(int64(c.StakingAmount))               // ← unsafe cast
clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount)) // ← unsafe cast
totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)

clAmount := new(big.Int).Mul(clAmountBig, amount)
clAmount  = clAmount.Div(clAmount, totalAmount)                 // ← divides by corrupted value
cnAmount  := big.NewInt(0).Sub(amount, clAmount)
```

`c.StakingAmount` and `c.CLStakingInfo.CLStakingAmount` are both `uint64` (KAIA units). `int64` can only represent values up to 9,223,372,036,854,775,807. Any value above that wraps to a negative `int64`, so `big.NewInt` receives a negative argument and `totalAmount` becomes wrong.

`Split` is invoked from four reward-distribution sites in `kaiax/reward/impl/getter.go`:

| Call site | Lines |
|---|---|
| `assignStakingRewards` (Kore/Prague staker rewards) | 523 |
| `assignStakingRewardsFlex` (Osaka flex staker rewards) | 475 |
| `specWithProposerAndFunds` (proposer reward, Prague) | 633 |
| `specWithProposerAndFundsFlex` (proposer reward, Osaka) | 583 |

### Impact Explanation

Two failure modes depending on the exact corrupted `totalAmount`:

1. **`totalAmount == 0`** (e.g., `cnAmountBig` and `clAmountBig` are equal in magnitude but opposite in sign): `big.Int.Div` panics with a division-by-zero. Every honest node crashes while finalizing the block → consensus halt / chain split.

2. **`totalAmount < 0`**: `clAmount` becomes negative. `cnAmount = amount − clAmount` becomes larger than `amount`. The CL pool address receives a negative credit (effectively a debit), and the CN reward address receives more than the full reward. This is a silent, per-block mis-accounting of KAIA rewards that persists in state.

Both outcomes satisfy the allowed-impact gate: invalid state transition / incorrect reward distribution affecting KAIA and system-managed funds.

### Likelihood Explanation

`StakingAmounts` are stored in KAIA units (raw kei balance ÷ `params.KAIA` = 10¹⁸). The overflow threshold is `math.MaxInt64` ≈ 9.22 × 10⁹ KAIA. The current circulating supply is approximately 5.4 × 10⁹ KAIA, so the threshold cannot be crossed today. However:

- The `reward.mintingamount` governance parameter has no upper bound and can be set to any non-negative `*big.Int`, allowing the supply to grow arbitrarily over time.
- A single validator's `consolidatedNode.StakingAmount` is the **sum** of all staking contracts sharing the same reward address (accumulated in `consolidateNodes` via `cn.StakingAmount += si.StakingAmounts[i]`), so it can exceed any individual contract's balance.
- No cap or overflow guard exists anywhere between the on-chain balance read and the `int64` cast.

Likelihood is **medium-low** today but increases monotonically with supply growth and is a latent design defect in the Prague/Osaka reward path.

### Recommendation

Replace the bare `int64` cast with `new(big.Int).SetUint64(...)`:

```go
// kaiax/staking/staking_info.go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    cnAmountBig := new(big.Int).SetUint64(c.StakingAmount)
    clAmountBig := new(big.Int).SetUint64(c.CLStakingInfo.CLStakingAmount)
    totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)
    if totalAmount.Sign() == 0 {
        return amount, big.NewInt(0)
    }
    clAmount := new(big.Int).Div(new(big.Int).Mul(clAmountBig, amount), totalAmount)
    cnAmount  := new(big.Int).Sub(amount, clAmount)
    return cnAmount, clAmount
}
```

`new(big.Int).SetUint64` correctly handles the full `uint64` range without sign truncation.

### Proof of Concept

1. A validator registers two staking contracts (same `RewardAddr`) in AddressBook, each holding 5 × 10⁹ KAIA. After consolidation, `cn.StakingAmount = 10 × 10⁹ KAIA` (> `math.MaxInt64` ≈ 9.22 × 10⁹).
2. The validator also has a CL pool with `CLStakingAmount = 1 × 10⁹ KAIA`.
3. At block finalization (Prague HF active), `assignStakingRewards` calls `cn.Split(reward)`.
4. `int64(10_000_000_000)` wraps to `int64(-8_446_744_073_709_551_616)` (negative).
5. `totalAmount = -8_446_744_073_709_551_616 + 1_000_000_000 = -8_445_744_073_709_551_616` (negative).
6. `clAmount = 1_000_000_000 * reward / (-8_445_744_073_709_551_616)` → negative.
7. `cnAmount = reward - clAmount` → larger than `reward`.
8. The CL pool's balance is decremented; the CN reward address receives more than the total block reward. The corrupted `RewardSpec` is applied to state in `FinalizeState`, permanently mis-accounting KAIA.

func (si *StakingInfo) consolidateNodes() *[]consolidatedNode {
	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))
	nToR := make(map[common.Address]common.Address)

	for i, n := range si.NodeIds {
		r := si.RewardAddrs[i]
		// Unique nodeId is guaranteed by AddressBook.
		nToR[n] = r
		if cn, ok := cmap[r]; ok {
			cn.NodeIds = append(cn.NodeIds, n)
			cn.StakingContracts = append(cn.StakingContracts, si.StakingContracts[i])
			cn.StakingAmount += si.StakingAmounts[i]

				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}
