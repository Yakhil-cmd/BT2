## Title
Stale market-level `index-cache` liquidity index lets zToken collateral be overvalued after same-block bad-debt socialization - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` caches each vault's `(index, lindex)` pair per block timestamp in the `index-cache` map so that multiple operations touching the same asset within one block avoid re-calling the vault. However, a vault's `lindex` (liquidity index used to price zToken collateral) can also be mutated directly by `socialize-debt`, which is called by `liquidate` outside of the `accrue-and-cache` path. Because the cache key is only `{ timestamp, aid }` and is never invalidated by `socialize-debt`, any transaction that primes the cache for an asset earlier in a block will cause every later transaction in that same block to read a stale, pre-socialization `lindex`, even though the vault's real state has since dropped.

### Finding Description
`accrue-and-cache` is the only writer of `index-cache`: [1](#0-0) 

It is consulted by `get-cached-indexes`/`resolve-ztoken` to price zToken collateral via the liquidity index, and by `accrue-user-collateral`/`accrue-user-debts` before every `borrow`, `collateral-add`, `repay`, and `liquidate` call: [2](#0-1) [3](#0-2) 

The market's `liquidate` function, on full liquidation with no remaining collateral, socializes bad debt directly against the vault via `vault-socialize-debt`, which routes to the vault's public `socialize-debt` function: [4](#0-3) 

`socialize-debt` writes a **lower** `lindex` directly into vault state (`var-set lindex new-lindex`) — this bypasses `market.clar`'s `index-cache` map entirely. There is no call from `socialize-debt` (or from `liquidate`) that updates/invalidates `index-cache` for the affected `aid`.

Consequently, within a single block at timestamp `T`:
1. Any user's transaction that touches asset `X` (e.g. `collateral-add`, `borrow`) causes `accrue-and-cache` to call `vault-accrue`, caching `{ index, lindex }` for `{ timestamp: T, aid: X }`.
2. A later transaction in the same block triggers `liquidate` on an insolvent position denominated in `X`, which calls `socialize-debt`, lowering the vault's real `lindex` (writing down the value of zX shares to reflect the loss).
3. A third transaction, still in block `T`, that needs to price zX collateral (via `resolve-ztoken`/`get-cached-indexes`) hits the now-stale cache entry from step 1 (cache key unchanged since timestamp is unchanged) and values zX collateral using the pre-socialization (higher) `lindex` instead of the true, written-down value.

### Impact Explanation
Because collateral value derived from the stale `lindex` is used in LTV health checks (`is-healthy`/`is-healthy-with-mask`) for `borrow` and in the liquidation health check for `liquidate`, this stale cache can:
- Allow a borrower to open/extend a debt position against zX collateral that is actually undercollateralized relative to its true (post-socialization) value, since the health check passes using the inflated value.
- Allow an already-unhealthy position collateralized in zX to escape liquidation in the same block because its LTV appears healthier than it is.

Either outcome creates undercollateralized debt that the protocol/suppliers must eventually absorb, i.e., protocol insolvency / permanent loss of supplier funds — a Critical-class impact, and it happens purely due to interaction between an unrelated user's cache-priming transaction and a liquidator's socialization transaction, without either directly being the "victim."

### Likelihood Explanation
Requires a same-block sequence: (a) some transaction priming `index-cache` for asset `X` (very common — any borrow/collateral-add touching X), (b) a liquidation causing bad-debt socialization on `X` afterward in the same block, and (c) a third operation pricing zX collateral before the block ends. Liquidators/attackers can engineer this ordering deliberately (e.g., front-run/back-run within the block using transaction fee bidding) making exploitation feasible whenever a socialize-debt event is imminent.

### Recommendation
Invalidate or refresh the `index-cache` entry for `aid` whenever `vault-socialize-debt`/`socialize-debt` is called (e.g., have `liquidate` re-fetch/overwrite the cached `{index, lindex}` with the vault's post-socialization values via `map-set index-cache`), or have `resolve-ztoken` always read the vault's current `lindex` directly rather than relying on the possibly-stale per-block cache when a socialization has occurred in the same block.

### Proof of Concept
1. Block `T`: User Bob calls `collateral-add` posting zX (or any operation touching aid `X`), causing `accrue-and-cache(X)` cache MISS → caches `{index, lindex}` at `{timestamp: T, aid: X}`.
2. Still in block `T`: Liquidator fully liquidates an insolvent borrower whose debt is in `X` with no remaining collateral, triggering `socialize-debt-asset` → `vault-socialize-debt(X, scaled-amount)` → vault's `socialize-debt` writes a lower `lindex` directly on the vault (`v0-vault-usdh.clar:961`), never touching `market`'s `index-cache`.
3. Still in block `T`: User Carol calls `borrow` (or another `collateral-add`) whose position holds zX collateral. `accrue-user-collateral` → `accrue-and-cache(X)` hits the cache from step 1 (same `timestamp`), returning the stale, higher `lindex`. `resolve-ztoken` prices Carol's zX collateral using this inflated `lindex`, and the health check in `borrow` (`v0-4-market.clar:1272`, `1287`) passes using overvalued collateral, letting Carol borrow more than her true collateral supports. (define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
