**Analysis summary:**

`Config::make_free()` at [1](#0-0)  sets `limit_config.max_gas_burnt = Gas::MAX`, but this method is only invoked from test and estimator code paths — [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6)  — none of which are on the production chunk-application path. It is never called by `RuntimeConfigStore::new`, `RuntimeConfigStore::for_chain_id`, or `TryFrom<&ParameterTable> for RuntimeConfig`, which are the only constructors used in real chunk execution.

`RuntimeConfigStore::new` builds each historical `RuntimeConfig` strictly from the base YAML plus append-only diffs via `TryFrom<&ParameterTable> for RuntimeConfig` [8](#0-7) [9](#0-8) , and `limit_config` is deserialized directly from the parameter table's `max_gas_burnt` YAML value [10](#0-9) , with no fallback to `Gas::MAX` or default. The recorded historical snapshots for every protocol version show `max_gas_burnt` as a concrete finite value (e.g. 200 or 300 TGas), never `Gas::MAX`/`u64::MAX` [11](#0-10) [12](#0-11) . There is also an integration test asserting gas burnt stays within `config.wasm_config.limit_config.max_gas_burnt` [13](#0-12) .

Since `make_free()` and any code path that could set `max_gas_burnt` to `Gas::MAX` are confined to non-production test/estimator harnesses, and the production `RuntimeConfigStore`/`ParameterTable` pipeline never invokes `make_free()` or otherwise omits `max_gas_burnt`, there is no reachable path for an unprivileged attacker to trigger unbounded-gas execution during real chunk application.
