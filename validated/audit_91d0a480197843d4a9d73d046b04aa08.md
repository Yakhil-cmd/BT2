### Title
Uncaught exception on duplicate-output check leaks the DB connection and crashes the node - ([File: private_payment.js])

### Summary
CVE-2021-20265 is a Linux kernel bug where `unix_stream_recvmsg` fails to release resources when a signal interrupts it mid-operation, letting an unprivileged local user repeatedly trigger the path and exhaust memory. The reachable analog in ocore is in `private_payment.js`, where the duplicate-output check inside `validateAndSavePrivatePaymentChain` can `throw` from inside an async DB callback while a transaction is open and a pooled connection is checked out, bypassing the normal `ifError`/`ifOk` cleanup path that calls `conn.release()`. An unprivileged private-payment counterparty can trigger this repeatedly.

### Finding Description
`validateAndSavePrivatePaymentChain` takes a connection from the pool, begins a transaction, and queries existing `outputs` rows for the referenced `(unit, asset, message_index[, output_index])`: [1](#0-0) 

For a divisible (non fixed-denomination) private asset, the `output_index` filter is intentionally omitted from the SQL (comment: "divisible outputs are never hidden individually and sql has no output_index filter, so match against any of them"). Since a single payment message routinely produces more than one output row (payee output + change output) sharing the same `unit`, `asset`, and `message_index`, this SELECT can legitimately return more than one row once the referenced unit is already known/stable with a multi-output message: [2](#0-1) 

When `rows.length > 1`, the code does `throw Error("more than one output ...")` instead of calling `transaction_callbacks.ifError(...)`. Because this throw happens inside the asynchronous `conn.query` callback, it is not caught by the surrounding function and never reaches `transaction_callbacks.ifError`, which is the only code path that issues `ROLLBACK` and `conn.release()`: [3](#0-2) 

The result: the transaction is left open and the connection is never returned to the pool. Repeating this trigger (each time referencing a different already-known unit whose message has ≥2 outputs) leaks one pooled connection per call. No global `uncaughtException`/domain recovery specific to this call path releases the connection; ocore's process-level handlers in `network.js` are unrelated to this internal DB-pool bookkeeping. This is directly reachable by any private-payment counterparty — the same trust level and reachability class as the AA-trigger/private-payment paths explicitly listed as in scope.

### Impact Explanation
Repeatedly triggering this path exhausts the finite DB connection pool (`MAX_CONNECTIONS` in `sqlite_pool.js`/`mysql_pool.js`). Once exhausted, subsequent `db.takeConnectionFromPool()` callers used throughout validation and writing (`validation.js`, `writer.js`, `aa_composer.js`, `joint_storage.js`) can no longer obtain a connection, stalling unit validation, AA trigger processing, and joint saving. This matches the required impact bar: "a network unable to confirm new units" — the node effectively stops processing new units/transactions until restarted, a resource-exhaustion denial of service directly analogous to the kernel CVE's memory exhaustion via an unprivileged, repeatable local trigger.

### Likelihood Explanation
Any device that exchanges private payments with the victim (a normal, unprivileged private-payment counterparty) can supply a private-payment chain whose head element references a `unit`/`message_index` combination that already has multiple output rows recorded for that asset (a very ordinary situation for divisible-asset payments with change outputs). No special privileges, timing races, or malicious peer/hub behavior are required — this is a straightforward application-level bug reachable from the documented private-payment message-handling flow (`wallet.js` → `network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain`). The trigger can be repeated arbitrarily to leak connections at will.

### Recommendation
Replace the `throw Error(...)` at line 75 of `private_payment.js` with `return transaction_callbacks.ifError("more than one output " + sql + ' ' + params.join(', '))` so that the existing `ROLLBACK`/`conn.release()` cleanup path executes. More generally, audit all `conn.query` callbacks in this file (and similar transaction-wrapped flows) for `throw` statements that can fire before `transaction_callbacks.ifError/ifOk` is invoked, and wrap such blocks so any exception is converted into a call to `ifError` guaranteeing connection release.

### Proof of Concept
1. Establish a normal private-asset payment relationship where a divisible private payment message legitimately creates 2+ output rows in `outputs` for the same `(unit, asset, message_index)` (e.g., a payment output plus a change output) — this is the default composition behavior for divisible payments.
2. As an unprivileged private-payment counterparty/device, send (or resend) a `private_payments` message via `wallet.js`'s `handlePrivatePaymentChains` whose head private element references that same `unit`/`message_index`/`asset` but a different/invalid disclosed content, forcing `validateAndSavePrivatePaymentChain` in `private_payment.js` to run its duplicate check.
3. The `SELECT ... FROM outputs WHERE unit=? AND asset=? AND message_index=?` query returns >1 rows, hitting `throw Error("more than one output ...")` inside the `conn.query` callback — the transaction is never rolled back and the connection is never released.
4. Repeat step 2 with distinct qualifying units to leak one connection per attempt until `db.takeConnectionFromPool` callers across the node (validation, writer, AA processing) start blocking indefinitely, halting new-unit confirmation.

Note: I could not fully verify at runtime whether ocore's Node.js process has any top-level domain/`uncaughtException` handler that would restart or recover gracefully rather than crash outright; only `network.js` references such handlers and they do not appear tied to this DB-pool cleanup path. This uncertainty does not change the conclusion that the connection leak/pool exhaustion occurs regardless of whether the process eventually crashes or merely stalls.
