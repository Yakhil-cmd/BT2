### Title
Provisioning gate bypass via operator-precedence bug in `unarchive?` - (File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`PullRequest::ReopenedHandler#unarchive?` replicates the same `&&`/`||` precedence bug as `opened_handler.rb`, so when `repository.provisioning_behavior` is `prevent_with_label` and the PR carries no label, the method returns `true` regardless of `repository.review_stacks_enabled`. This lets an attacker reopen their own PR to trigger review-stack (re)creation and enqueue it for provisioning even on repositories that have review stacks disabled. `PullRequest::UnlabeledHandler`, by contrast, does **not** share this defect: it applies an explicit top-level `repository.review_stacks_enabled &&` gate before calling `archive?`/`unarchive?`, so the same bypass does not apply there.

### Finding Description
The binding that should hold is: `repository.review_stacks_enabled == true` must equal the actual condition gating any `Command`/`PTY.spawn` for that repository's review stacks.

In `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`:
```ruby
def respond_to_pull_request_reopened?
  params.action == "reopened" &&
    unarchive?
end

def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present) || (prevent_with_label? && !label_present)`

Only the `allow_all?` branch is conditioned on `review_stacks_enabled`; the `prevent_with_label?` and `allow_with_label?` branches are not. There is no other check of `review_stacks_enabled` anywhere in `respond_to_pull_request_reopened?` or `process`, unlike `UnlabeledHandler`, whose `respond_to_label_change?` ANDs `repository.review_stacks_enabled` at the top level with `(archive? || unarchive?)` [2](#0-1)  — that separate top-level gate means `UnlabeledHandler`'s own `unarchive?`/`archive?` lacking a `review_stacks_enabled` check internally is harmless, since `handle` is never invoked when `review_stacks_enabled` is false.

`OpenedHandler` shares the identical flawed pattern for `provision?` [3](#0-2) , confirming this is a repeated bug across handlers, but the finding in this question is specifically substantiated only for `ReopenedHandler`.

Exploit flow for `ReopenedHandler`: attacker owns a repository connected to Shipit with `review_stacks_enabled = false` and `provisioning_behavior = :prevent_with_label` (an admin-configured combination that is supposed to mean "review stacks are off entirely"). Attacker opens a PR with no label, lets it close, then reopens it (or simply sends a `pull_request` webhook with `action: "reopened"`). `unarchive?` evaluates true via the `prevent_with_label? && !label` clause. `process` calls `stack.unarchive!` [4](#0-3) , which delegates to `ReviewStackAdapter#unarchive!`; if no stack exists it calls `create!`, both of which push the stack onto `Shipit::ReviewStackProvisioningQueue` [5](#0-4) [6](#0-5) . From the provisioning queue, standard task machinery eventually runs `shipit.yml` for the stack's branch/environment via `Command`/`PTY.spawn` in `lib/shipit/command.rb`.

No other guard intervenes: `repository.review_stacks` scope is unconditional (`has_many :review_stacks`) and is not filtered by `review_stacks_enabled` [7](#0-6) ; `Repository` model validations only cover `name`/`owner` format [8](#0-7)  and do not enforce the `review_stacks_enabled`/`provisioning_behavior` invariant.

### Impact Explanation
An unprivileged GitHub user who owns/controls a repository connected to Shipit (with the specific misconfiguration `review_stacks_enabled=false` + `provisioning_behavior=:prevent_with_label`) can force creation/unarchiving of a review stack and enqueue it for provisioning by simply reopening their own PR with no label, ultimately causing `shipit.yml` from their ref to be executed via `Command`/`PTY.spawn` — Critical RCE on the deploy host. This is repeatable at will against any repository sharing that configuration and is scoped to the attacker's own repository/stack (no cross-tenant pivot demonstrated).

### Likelihood Explanation
Requires the specific repository configuration `review_stacks_enabled=false` combined with `provisioning_behavior=:prevent_with_label`, which an operator might reasonably set believing it fully disables review stacks. Attacker cost is trivial (open/reopen a PR with no label, or replay a `reopened` webhook payload) and fully repeatable. Likelihood depends entirely on this configuration existing, which is plausible but not the default.

### Recommendation
Fix the operator precedence in `unarchive?` by explicitly parenthesizing so `review_stacks_enabled` gates every branch:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the equivalent fix to `OpenedHandler#provision?`. `UnlabeledHandler` does not require this change since its top-level gate already ANDs `review_stacks_enabled` correctly, but adding the same explicit grouping inside its `archive?`/`unarchive?` would improve defense-in-depth/consistency.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`):
```ruby
test "does not unarchive or provision when review_stacks_enabled is false, even with prevent_with_label and no label" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = []

  Shipit::ReviewStackProvisioningQueue.expects(:add).never

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived when review_stacks_enabled is false"
end
```
Expected: with the current code, `unarchive?` returns `true` because `(prevent_with_label? && !label)` is unaffected by `review_stacks_enabled`, so `ReviewStackProvisioningQueue.add` is called and the assertion/mock expectation fails, proving the bug. After applying the parenthesization fix, the test passes.
