## Finding

### Title
LPs can front-run `socialize-debt` write-downs by redeeming zTokens before bad-debt liquidation is executed - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Zest vaults (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, etc.) price zTokens via a liquidity index (`lindex`) that is only written down when the market explicitly calls `socialize-debt` during a `liquidate` transaction. Because an under-collateralized borrower's position (and the resulting bad debt) is publicly visible on-chain before anyone actually triggers `liquidate`, any LP can `redeem` their zTokens at the pre-write-down (stale, too-high) share price, escaping the loss entirely and shifting 100% of the socialized bad debt onto the LPs who remain. This is the same LP-timing-game bug class as Buffer's H-2, applied to Zest's bad-debt socialization mechanism instead of option expiry.

### Finding Description
Each vault tracks `assets`, `principal-scaled`, `index` and `lindex`, and exposes `deposit`/`redeem` with only an `accrue()` call (interest-rate based) and no epoch/lockup buffer: [1](#0-0) 

`redeem` computes `inkind = convert-to-assets-preview(amount)` using the current `lindex`/`total-assets`, and is available to any LP as soon as they're not paused — with no time delay or epoch buffer tying withdrawal timing to pending loss events: [2](#0-1) 

Bad debt is only realized and pushed into the vault's share price via `socialize-debt`, which writes down `lindex` proportionally to the loss, and this is called exclusively from `market.clar`'s `liquidate` flow, at the moment a liquidator chooses to act: [3](#0-2) [4](#0-3) 

The `liquidate` function itself confirms that bad debt is only socialized inside the liquidation transaction, not automatically as soon as a position becomes underwater: [5](#0-4) 

Because oracle prices and borrower obligations are public, and because `redeem` prices shares using the *current* (not-yet-written-down) `lindex`, any LP watching the oracle feed for a borrower crash (exactly the scenario exercised in the protocol's own `ATK-LG-05` test, where a BTC crash leaves $42k debt against $10k collateral) can race to redeem before `liquidate` is called, capturing full asset value while the impending bad debt has not yet been reflected in share price: [6](#0-5) 

### Impact Explanation
This is a direct analog of Buffer's H-2: knowledge of a public, deterministic future loss event (here, a borrower's insolvency, instead of an option's expiry) lets one unprivileged LP escape the loss entirely by redeeming before `socialize-debt` fires, while the loss — the write-down of `lindex` — is instead fully absorbed by the LPs who remain in the vault at the time `liquidate` executes. This is exactly the "socialization charged to all suppliers" pattern called out as in-scope: the attacker (fast-exiting LP) harms a distinct set of victims (remaining LPs), via the shared vault state (`lindex`/`total-assets`) that both read and write into. The remaining LPs suffer a disproportionate, avoidable loss of principal that they would not have suffered had withdrawals been fairly rationed relative to the timing of the loss discovery — this is theft of principal/yield from the remaining suppliers, an in-scope High-severity impact.

### Likelihood Explanation
Likelihood is high in practice: oracle price feeds and borrower obligations (via `market-vault`) are fully public and readable on-chain, undercollateralized positions are simple to detect by monitoring price feeds against the health-check formula, and `redeem` has no lockup, cooldown, or epoch-buffer to prevent same-block or same-window withdrawal ahead of a `liquidate` call. Any sufficiently attentive LP or bot can execute this race with ordinary transaction submission — no special privilege, oracle manipulation, or flashloan is required.

### Recommendation
Introduce an epoch-based deposit/withdrawal buffer (batching redemptions so that pending, foreseeable bad debt is accounted for before any LP can exit), or require that vault `redeem` calls first "mark-to-market" any known-liquidatable positions collateralized by that vault's debt (i.e., proactively call an equivalent of `socialize-debt` for any position that is currently unhealthy) before computing `convert-to-assets-preview`. Alternatively, add a minimum holding/cooldown period on zToken redemption to reduce the window in which LPs can react to a specific, already-public insolvency event.

### Proof of Concept
1. Alice deposits sBTC collateral and borrows USDC from `v0-vault-usdc`.
2. BTC price craters (via Pyth feed update) such that Alice's collateral, even fully seized with liquidation penalty, cannot cover her full USDC debt (mirrors `ATK-LG-05` in `local-testing/tests/security/liquidation.test.ts:153-188`). At this point, the vault's `lindex`/`assets` values still reflect the full (yet-to-be-realized) 100 cent-on-the-dollar debt.
3. Bob (an LP holding zUSDC) observes the price crash and Alice's now-undercollateralized position on-chain, and immediately calls `redeem` on `v0-vault-usdc`, receiving USDC based on the current, not-yet-written-down `lindex`.
4. Some time later, Charlie calls `market.clar liquidate` on Alice's position; this seizes her remaining collateral and, finding `no-collateral-left`, invokes `socialize-debt-asset` → `vault-socialize-debt`, which writes down `lindex` proportionally to the bad debt.
5. Remaining zUSDC holders (who did not redeem before step 3) now bear the entire write-down that would otherwise have been shared with Bob, who exited at the stale, higher price and suffered zero loss.

                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc

            (failed-status { borrower: borrower, success: false })
