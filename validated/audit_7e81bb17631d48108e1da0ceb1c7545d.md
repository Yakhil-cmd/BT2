### Title
`Repository#review_stacks_enabled` is bypassed for `allow_with_label`/`prevent_with_label` behaviors due to `&&`/`||` precedence in `provision?` - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`provision?` correctly ANDs `review_stacks_enabled` with `provisioning_behavior_allow_all?` for the `:allow_all` clause (negative control confirmed: `false && true || ... == false`), but the `review_stacks_enabled` flag is never referenced in the second and third `||` clauses covering `:allow_with_label` and `:prevent_with_label`. This means disabling review stacks (`review_stacks_enabled = false`) has zero effect whenever `provisioning_behavior` is `allow_with_label` or `prevent_with_label`.

### Finding Description
Binding claimed to hold: `provision?() == (repository.review_stacks_enabled && <any enabled behavior>)`. Traced code: [1](#0-0) 

Due to Ruby's `&&` binding tighter than `||`, the expression parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

- For `review_stacks_enabled == false`, `behavior == :allow_all`: clause 1 is `false`, clauses 2/3 are `false` (their behavior predicates are `false`), so `provision? == false`. The flag IS honored here — this side of the boundary matches, no bug.
- For `review_stacks_enabled == false`, `behavior == :allow_with_label`, with a matching label on the PR: clause 1 is `false`, but clause 2 is `allow_with_label?(true) && has_label?(true) == true`, so `provision? == true` — `review_stacks_enabled` is completely ignored.
- For `review_stacks_enabled == false`, `behavior == :prevent_with_label`, with no label present (the default case, no attacker action needed beyond opening a PR): clause 3 is `prevent_with_label?(true) && !has_label?(true) == true`, so `provision? == true` — again `review_stacks_enabled` is ignored.

This is corroborated by the existing test suite, which only exercises the disabled-flag case against `:allow_all` (`"only provision stacks for repos with auto-provisioning enabled"`) and never against `:allow_with_label`/`:prevent_with_label`: [2](#0-1) 

No other guard intervenes: `respond_to_pull_request_opened?` only checks `params.action == "opened" && provision?`, and webhook signature/`drop_unhandled_event` checks only validate that the payload came from GitHub for the named repository — they do nothing to enforce `review_stacks_enabled`. [3](#0-2) 

### Impact Explanation
For any repository an operator has configured with `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false` (intending to disable auto-provisioning entirely), an attacker who can open a pull request against that repository (or one on their own fork depending on webhook subscription) with no special label will still cause `Shipit::Stack.count` to increase — a review stack is created and queued for provisioning against the operator's explicit intent to disable it. For `allow_with_label`, the attacker additionally needs to apply their own label to their own PR, which the threat model permits. This produces an unauthorized stack, feeding into subsequent provisioning/task execution against the disabled repository — repeatable on every PR open event for any repository configured this way.

### Likelihood Explanation
Requires the repository operator to have set `provisioning_behavior` to `allow_with_label` or `prevent_with_label` while separately toggling `review_stacks_enabled` to `false` (e.g., temporarily pausing auto-provisioning without changing the configured behavior). Given the UI exposes both settings independently, this is a plausible, low-cost, fully attacker-repeatable misconfiguration trigger requiring no secrets or privileged access — just opening a PR.

### Recommendation
Add parentheses so `review_stacks_enabled` gates every clause: `repository.review_stacks_enabled && (repository.provisioning_behavior_allow_all? || (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))`.

### Proof of Concept
```ruby
test "review_stacks_enabled is honored for allow_all (negative control)" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(repository:, provisioning_enabled: false, behavior: :allow_all)

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload_parsed(:pull_request_opened)).process
  end
end

test "review_stacks_enabled is bypassed for prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(repository:, provisioning_enabled: false, behavior: :prevent_with_label, label: "pull-requests-label")
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # no label => prevent_with_label defaults to create

  assert_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "review_stacks_enabled is bypassed for allow_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(repository:, provisioning_enabled: false, behavior: :allow_with_label, label: "pull-requests-label")
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
