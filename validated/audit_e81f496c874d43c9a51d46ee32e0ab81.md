### Title
`StatusHandler#process` writes commit statuses via a global, repository-unscoped `Commit.where(sha:)` lookup, enabling cross-repository/cross-tenant status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely by `sha` across the entire database, never consulting `payload['repository']['full_name']`, unlike every sibling handler (`PushHandler`, `CheckSuiteHandler`, `LabeledHandler`, etc.) which route through `Handler#stacks`/`repository_name` or a local `repository` method scoped to `Repository.from_github_repo_name`. Because git commit SHAs are content-addressed and shared across forks of the same public repository, an attacker who owns a fork of a victim's tracked repository (and has a legitimately signed webhook channel for their own onboarded org) can send a `status` event naming their own `repository.full_name` but a `sha` that also exists as a tracked commit in a victim stack, causing Shipit to write a forged `Status` onto the victim's commit/stack.

### Finding Description
The claimed binding is: `repository_name_in_payload == repository_that_owns_the_written_record`. For `LabeledHandler`, `OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `UnlabeledHandler`, `PushHandler`, and `CheckSuiteHandler`, this holds because they all resolve `repository`/`stacks` from `params.repository.full_name` before touching any persisted record: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

`StatusHandler#process` breaks this binding: it looks up commits solely by `sha`, with no repository scoping at all, and then mutates them: [5](#0-4) 

The write path is `Commit#create_status_from_github!` → `Status.replicate_from_github!(stack_id, github_status)`, which persists using the found commit's own `stack_id`, not anything derived from the incoming payload's repository: [6](#0-5) [7](#0-6) 

**Why existing guards don't stop this:** `WebhooksController#verify_signature` checks the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the *attacker's own* payload (`params.dig('repository','owner','login')`): [8](#0-7) [9](#0-8) 

This only proves the request was signed by *some* onboarded org's webhook secret (i.e., a GitHub App installation the Shipit operator configured) — it says nothing about whether that org is authorized to write statuses for the specific `sha` referenced. On a multi-tenant Shipit host (common deployment: one Shipit instance, multiple GitHub orgs/apps configured), an attacker who owns/administers any onboarded org can legitimately trigger a real, correctly-signed `status` webhook from GitHub for their own repository. If that repository is a fork of (or shares commit history with) a repo tracked under a different, victim org's stack, the shared ancestor commits have identical SHAs. The attacker:
1. Forks the victim's public tracked repository into their own onboarded org/account (`attacker/evil`).
2. Uses the Statuses API (or CI integration) on their fork to set an arbitrary status (`state`, `description`, `context`, `target_url`) on a SHA that is a shared ancestor commit also tracked by the victim's stack.
3. GitHub sends a genuinely signed `status` webhook with `repository.full_name = "attacker/evil"` and the shared `sha`.
4. `verify_signature` passes (it's a real signature for the attacker's own org).
5. `StatusHandler#process` finds ALL `Commit` rows with that `sha`, including the victim's, and writes a forged `Status` onto the victim's commit/stack — with no check that `attacker/evil` has anything to do with the victim's repository.

### Impact Explanation
This is a payload for one repository (`attacker/evil`) mutating another's commit/stack state (the victim's), matching the Critical category explicitly listed in scope. A forged `success` status can flip a victim commit's `merge_status`/`branch_status` to success, potentially unblocking automatic merges or continuous deployment (`Stack#schedule_merges`, `ContinuousDeliveryJob`), or a forged `failure`/`error` status can block a legitimate victim deploy — both are integrity attacks on deploy gating. The attack is repeatable against any victim stack whose tracked repository shares commit history (via fork or otherwise) with any repository the attacker controls in an onboarded org, and is not limited to a single request.

### Likelihood Explanation
Preconditions: the Shipit host must be configured for at least one org the attacker legitimately controls (a realistic multi-tenant setup, or even a single-org setup where the attacker is a member with fork/push rights but not a Shipit operator/maintainer), and a victim stack must track a public/forkable repository sharing commit ancestry with the attacker's repo. No secrets, sessions, or API tokens are required — only the ability to fork a repo and set a status via the ordinary GitHub Statuses API/webhook flow, which is squarely within the "attacker action" allowed by the threat model (push to a fork they own, emit legitimately-signed webhooks from a repository they own).

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `Handler#stacks`/other handlers, e.g. restrict the commit lookup to `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })` or filter `commit.stack.repository` against `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (no live GitHub, using existing fixtures):
```ruby
test "StatusHandler must not write a status onto a commit belonging to a different repository" do
  victim_commit = shipit_commits(:first) # belongs to shipit_stacks(:shipit) repository
  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/evil' } # unrelated repository
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end
end
```
Currently this assertion fails: `StatusHandler.call` creates a `Status` on `victim_commit` regardless of `attacker_payload['repository']['full_name']`, because `Commit.where(sha: params.sha)` in [5](#0-4)  never consults the repository. A contrast assertion, `LabeledHandler`'s `repository`/`stack` methods ( [2](#0-1) ) demonstrably route mutation through `repository.review_stacks`, while `StatusHandler` has no equivalent method, confirming the structural gap.
