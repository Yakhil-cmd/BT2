Based on my investigation, I found a strong analog to the reported bug class in `Shipit::Api::CCMenuController`.

### Title
Stack-scoped API token bypasses stack scoping to read CCMenu status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
This is an equality-binding failure analogous to the `registerToken` finding: a token that is supposed to authorize access to exactly one `stack` is not checked for equality against the `stack` that is actually touched. `Shipit::Api::CCMenuController` overrides `authenticate_api_client` and its own `stack` finder so that neither ever validates `current_api_client.stack_id == stack.id`, unlike every other API controller which resolves the target stack through the scoped `stacks` collection.

### Finding Description
`Shipit::Api::BaseController` implements stack scoping through two cooperating methods: [1](#0-0) 
`stacks` restricts the visible `Stack` collection to `current_api_client.stack_id` when the client is scoped, and every controller that needs "the current stack" (e.g. `StacksController#stack`) is expected to resolve it via `stacks.from_param!(...)`, e.g.: [2](#0-1) 

`CCMenuController`, however, defines its own `stack` method that bypasses the scoped `stacks` collection entirely and resolves directly against the global `Stack` table: [3](#0-2) 

It also overrides `authenticate_api_client` to accept the token from a query-string `params[:token]` (needed because CCMenu clients such as CruiseControl cannot send an `Authorization` header), but this override only re-implements *authentication* (does the token verify to a valid `ApiClient`?) — it never re-applies *authorization scoping* (is `stack.id == current_api_client.stack_id`?): [4](#0-3) 

The only authorization check performed is the class-level `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [5](#0-4) 

That method only checks the string permission (e.g. `"read:stack"`) is in the client's permission list — it has no knowledge of, and does not compare against, `stack_id`. The binding that should hold is: `current_api_client.stack_id == stack.id` (when `stack_id` is present), but `CCMenuController#show`/`#stack` never enforces this equality; it only enforces `current_api_client` validity and `read:stack` permission, using the attacker-supplied `stack_id` URL param.

### Impact Explanation
An `ApiClient` token that was created scoped to a single stack (`ApiClient#stack_id` present, as created via `CCMenuUrlController#client`: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`) can be replayed against `GET /stacks/:stack_id/ccmenu` with **any other** `stack_id`, and the controller will happily render that other stack's CCMenu status (deploy activity, last build status/label, lock status). This is an unauthenticated-read escalation across stack boundaries using a token that was only supposed to authorize one stack — matching the report's "High: unauthenticated read of stack state" impact category, and directly analogous to registering `localToken == remoteToken` causing a binding that should differentiate two entities to silently collapse.

### Likelihood Explanation
Likelihood is high for any deployment where CCMenu URLs are used: the scoped token is embedded directly in a URL (`CCMenuUrlController#fetch` puts `client.authentication_token` in a query string), which is inherently more exposed to disclosure (browser history, logs, proxies) than a header-based Basic Auth credential. Once obtained, exploitation requires only changing the `stack_id` path segment — no cryptographic work, no additional access.

### Recommendation
In `Shipit::Api::CCMenuController`, resolve `stack` through the same scoped `stacks` helper used elsewhere (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so that a stack-scoped `ApiClient` cannot address stacks outside its `stack_id`. Equivalently, add an explicit check in `#show` (or a `before_action`) enforcing `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`.

### Proof of Concept
1. As a legitimate user, generate a CCMenu URL for Stack A: `GET /ccmenu/*stack_id=A` → returns a URL containing `token=<T>` where `T` authenticates an `ApiClient` with `stack_id = A.id` and `permissions = ["read:stack"]` (see `app/controllers/shipit/ccmenu_url_controller.rb`).
2. Take token `T` and request Stack B's status instead: `GET /api/stacks/B/ccmenu?token=T`.
3. `CCMenuController#authenticate_api_client` verifies `T` via `ApiClient.authenticate(params[:token])`, succeeding regardless of `stack_id`.
4. `require_permission :read, :stack` calls `check_permissions!('read', 'stack')`, which only checks `"read:stack"` is in the permissions array — true.
5. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` = Stack B directly, ignoring `current_api_client.stack_id == A.id`.
6. The response renders Stack B's real deploy/lock status to a token that was only ever meant to expose Stack A. [6](#0-5)

# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
