### Title
Cross-organization webhook forgery via organization/repository binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App (`config/secrets.yml` multi-org) Shipit deployment, the field used to select which organization's webhook secret verifies the HMAC signature (`repository.owner.login`, read from the still-unverified JSON body) is **not** the same field later used by webhook handlers to resolve which repository/stack the event actually acts on (`repository.full_name`). Both fields live inside the same attacker-supplied JSON body, so an attacker who controls (or is an admin of) any one organization configured in this Shipit instance can forge a webhook whose signature is valid for *their own* org's secret while its `repository.full_name` field points at a stack belonging to a *different* organization on the same instance.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against based on `repository_owner`, which is extracted directly from the unverified JSON payload: [1](#0-0) [2](#0-1) 

That selects the correct `webhook_secret` for HMAC verification via `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature`: [3](#0-2) [4](#0-3) 

This per-organization secret scheme is a documented, supported configuration (`docs/setup.md`, "Using Multiple Github Applications"), where each org key in `config/secrets.yml` has its own independent `webhook_secret`.

Once the signature check passes, the *same raw payload* is handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create`: [5](#0-4) 

Handlers resolve the target repository/stack using a *different* field of the same body — `repository.full_name` — not `repository.owner.login`: [6](#0-5) [7](#0-6) 

Because HMAC-SHA1 covers the entire raw request body but the two lookups (which secret authenticates the request vs. which repository the request acts on) read from two independent JSON keys, nothing forces `repository.owner.login` to equal the owner portion of `repository.full_name`. The binding that should hold is:

`organization whose webhook_secret authenticated the request == owner of the repository the handler mutates`

but the engine never enforces this equality — it only enforces `signature == HMAC(secret_for(repository.owner.login), raw_body)`, independent of `repository.full_name`.

### Impact Explanation
An attacker who is an administrator of, or otherwise controls the webhook secret for, any single organization configured in a multi-org Shipit instance can craft a JSON body such as:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  ...
}
```
sign it with `attacker-org`'s known `webhook_secret`, and send it to `/webhooks`. `verify_signature` succeeds (it only checks `attacker-org`'s secret against `repository.owner.login = "attacker-org"`), but the dispatched handler (e.g. `push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, or the `pull_request/*` handlers that drive the merge queue) resolves stacks via `repository.full_name = "victim-org/victim-repo"`. This lets the attacker inject forged `status`, `check_suite`, `push`, or `pull_request` events (labels, merges, deployable/merge status) into a completely unrelated organization's stacks — an unauthorized cross-repository/cross-organization write into another tenant's deploy pipeline (e.g. forcing a PR into "labeled for merge" or manipulating commit/check status used by the merge queue), without ever having credentials for the victim organization. This matches the "cross-repository writes" / "unauthorized deploy or merge" Critical/High impact class.

### Likelihood Explanation
This requires the host to run Shipit with the documented multi-organization GitHub App configuration and requires the attacker to control (be an org owner/admin able to set the `webhook_secret`, or otherwise know it) for at least one of the organizations sharing that Shipit instance — a materially lower bar than compromising the victim organization, an `ApiClient` token, or the victim's GitHub App private key, none of which the rules exclude here since no Shipit session, API token, or GitHub write access to the *victim* repo is needed.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner` from the same trusted field used for handler dispatch (`repository.full_name`'s owner segment) and reject the request (422) if it disagrees with the organization whose secret validated the signature. Alternatively, bind webhook delivery scoping explicitly to `installation.id`/organization id rather than trusting free-text `repository.owner.login` vs. `repository.full_name` independently.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker is an admin of `OrgA`'s GitHub App and knows `OrgA`'s `webhook_secret`.
3. Attacker builds payload:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo", "name": "victim-repo"},
  "sha": "<victim commit sha>",
  "state": "success"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and the signature verifies successfully.
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which (via `Handler#stacks`/`Repository.from_github_repo_name`) resolves `OrgB/victim-repo` from `repository.full_name` and applies the forged commit status to `OrgB`'s stack — a cross-organization write achieved with only `OrgA`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
