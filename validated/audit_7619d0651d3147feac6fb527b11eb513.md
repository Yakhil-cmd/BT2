### Title
Arbitrary commit-author spoofing via unauthenticated `Merge-Requested-By` trailer parsing - ([File: app/models/shipit/user.rb])

### Summary
`Shipit::User.find_or_create_author_from_github_commit` blindly trusts a `Merge-Requested-By: <login>` line anywhere in a commit's message and creates/attributes the `Commit#author` to that arbitrary, pre-existing `Shipit::User`, without verifying that the login corresponds to the actual GitHub identity that produced or pushed the commit. Since `PushHandler` triggers `stack.sync_github` for any push to a tracked branch of a stack the attacker controls (their own repository, verified with that repository's own valid `webhook_secret`), and `Commit.from_github` calls this method for every ingested commit, an attacker who can push a commit to a branch tracked by any Shipit stack can forge the recorded author of that commit to be any existing Shipit user login of their choosing.

### Finding Description
The broken binding is: **the GitHub identity that authored/committed the commit == the `author_id` recorded on the `Shipit::Commit` row**. This should always hold, but does not.

Code path:
1. `WebhooksController#create` verifies the webhook signature against the repository owner's own `webhook_secret` [1](#0-0) . This proves the payload came from *some* repository the attacker legitimately administers (their own fork/org), but proves nothing about the content of individual commit messages within that payload.
2. `PushHandler#process` finds all non-archived stacks tracking the pushed branch and calls `sync_github` [2](#0-1) .
3. Eventually commits are ingested via `Commit.from_github`, which calls `User.find_or_create_author_from_github_commit(commit)` [3](#0-2) .
4. `find_or_create_author_from_github_commit` matches `github_commit.commit.message` against `/^Merge-Requested-By: ([\w\-.]+)$/` and, on match, calls `find_or_create_by_login!(match_info[1])` — creating or reusing **any** existing `Shipit::User` by that login, with zero correlation to `github_commit.author`, `github_commit.committer`, or the webhook sender [4](#0-3) .

Root cause: the `Merge-Requested-By` trailer is only supposed to be *written* by Shipit itself, inside `MergeRequest#merge_message`, when Shipit performs a merge queue merge on behalf of `merge_requested_by` [5](#0-4) . However, the *parser* in `find_or_create_author_from_github_commit` has no way to distinguish a trailer that Shipit itself generated during a legitimate merge from one an attacker fabricated by simply typing that literal string into any commit message pushed to a branch a Shipit stack tracks. There is no signature, no cross-check against `merge_request.merge_requested_by`, and no restriction to commits that are actually `merge_request` merge-commits produced through `MergeRequest#merge!`.

Attacker request: push a commit with message body:
```
Some commit title

Merge-Requested-By: victim-login
```
to a branch tracked by a Shipit stack in a repository/org the attacker administers (so the webhook signature verifies with that org's own secret), then let the normal push webhook (or PR merge into that branch) flow through `PushHandler` → `sync_github` → `Commit.from_github`.

Existing guards do not catch this: `verify_signature` only authenticates which *repository/org* sent the webhook, not commit message contents; `drop_unhandled_event` and `ExplicitParameters` (`requires :ref`, `requires :after`) validate webhook shape, not commit semantics; there is no model validation on `Commit#author` correlating it to `committer` or to the webhook sender; `identify_merge_request` in `Commit` only overrides `author` from `merge_request.merge_requested_by` when a matching `MergeRequest` row already exists for that PR number — it does not prevent the independent, unconditional trailer-based lookup that already ran inside `Commit.from_github`.

### Impact Explanation
Every commit ingested this way results in a `Shipit::Commit` row whose `author` is falsely attributed to an arbitrary existing `Shipit::User` (identified only by login), rather than to the real committer/author. This corrupts audit trails, `identifiers_for_ping` data, `repositories_contributed_to`/`stacks_contributed_to` derived from `author_id`/`committer_id`, and any downstream logic keyed on commit authorship (e.g., blame, notifications, statistics). It is repeatable against any stack/branch the attacker's authenticated webhook can reach and against any existing Shipit user login the attacker knows (e.g., an operator's GitHub login is typically public). This is a cross-identity write: a payload authenticated for one GitHub identity/org causes an authorship record to be written under a different, arbitrary identity, matching the "commit ... attribution" concern raised, but it does not escalate into `Shipit.github_teams` authorization, does not trigger an unauthorized deploy/rollback/merge, and does not expose secrets or execute commands — it is a data-integrity/audit-record spoofing issue confined to the `author` field of `Commit`, not a control-plane compromise.

### Likelihood Explanation
Preconditions: the victim login must already exist as a `Shipit::User` (easily satisfied for any Shipit operator who has previously logged in or been referenced), and the attacker must control a repository/branch that is genuinely tracked as a Shipit stack (i.e., they need to be able to push into a branch Shipit monitors — typically requires write access to that specific repository, which for an "unprivileged fork owner" pushing to their own fork does not by itself reach a tracked branch unless/until the commit lands on the tracked branch, e.g. via a maintainer merging their PR, or if the attacker's own repository/fork is itself configured as a Shipit stack). Given those preconditions, exploitation cost is trivial: crafting a single commit message. This is entirely feasible for any contributor whose commits get merged upstream into a tracked branch, and is repeatable per commit/per PR.

### Recommendation
Restrict `find_or_create_author_from_github_commit`'s trailer-based attribution to only apply when the commit is verified to be the actual Shipit-generated merge commit for a `MergeRequest` (i.e., cross-check against `stack.merge_requests.find_by(number: ...).merge_requested_by` as `identify_merge_request` already does), and remove or gate the free-text regex match on arbitrary commit messages from arbitrary pushes. At minimum, only trust the `Merge-Requested-By` trailer on commits whose SHA matches `merge_request.head`/merge commit produced by `MergeRequest#merge!`, not on arbitrary incoming commits.

### Proof of Concept
```ruby
# test/models/user_test.rb (conceptual, no live GitHub)
test "find_or_create_author_from_github_commit trusts unauthenticated commit trailer" do
  victim = shipit_users(:walrus) # pre-existing user, login "walrus"
  attacker_commit = stub(
    commit: stub(
      message: "Fix bug\n\nMerge-Requested-By: walrus\n",
      author: stub(id: 999_999, login: "attacker"),
    ),
    author: stub(id: 999_999, login: "attacker"),
  )

  author = Shipit::User.find_or_create_author_from_github_commit(attacker_commit)

  assert_equal victim.login, author.login
  refute_equal "attacker", author.login
  # No code path reconciles `author` back to the actual committer/sender identity.
end
```
This demonstrates that `author.login == "walrus"` (the victim) while the actual GitHub commit author/sender identity is `"attacker"`, confirming the broken binding.

```ruby
    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
```
