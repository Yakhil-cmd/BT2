### Title
Shallow-clone (`--depth`) reused verbatim for `git submodule update`, with no unshallow fallback, causes permanent sync denial when a submodule pointer references a commit outside the fetched depth window - (File: main.go)

### Summary
`repoSync.fetch` fetches the main repository with a hard-coded `--depth` and, when depth is later reduced to zero, explicitly detects a shallow repo and appends `--unshallow` to recover [1](#0-0) . No such fallback exists for submodules: `configureWorktree` blindly reuses `git.depth` as the submodule fetch depth with no shallow-detection/unshallow logic [2](#0-1) . If a tracked submodule's pinned commit is not reachable within that fixed depth window from the submodule remote's advertised tip, `git submodule update --init --depth N` fails deterministically and there is no code path to widen the depth or retry with `--unshallow`, unlike the main-repo fetch.

### Finding Description
`SyncRepo` always recreates the worktree for the same target hash and re-runs `configureWorktree` on every sync attempt while the ref is unchanged [3](#0-2) . `configureWorktree` runs `git submodule update --init [--recursive] [--depth N]` unconditionally whenever `git.submodules != submodulesOff` [4](#0-3) . This is structurally analogous to the reported bug class: a fixed/default parameter (here, the shallow `--depth` value, functionally similar to Yearn's un-overridable `maxLoss`) is forwarded into a downstream git operation without any mechanism to relax it when the operation's success criteria (reachability of the pinned commit within the shallow window) are violated by legitimate upstream state (an older/side-branch submodule commit), exactly as a bear-market loss legitimately exceeding 0.01% breaks Yearn's hard-coded `maxLoss=1`.

By contrast, the main repository fetch path explicitly handles this case: it checks `isShallow` and appends `--unshallow` to guarantee the target ref becomes reachable [5](#0-4) . The submodule branch of `configureWorktree` has no equivalent check, so once a submodule pointer lands outside the configured depth's history, every subsequent identical retry hits the same git error.

### Impact Explanation
Because the failing hash never changes (the attacker/operator only needs to push once and the resulting `remoteHash` is stable until it advances again), every sync loop iteration reproduces the same `configureWorktree` failure. This drives `failCount` up on each iteration; once `getMaxFailures()` is exceeded the process calls `os.Exit(1)`, terminating the git-sync sidecar/pod entirely [6](#0-5) . Until an operator intervenes (bumps `--depth`, unshallows the clone, or the upstream ref moves again), the target directory can never be updated—matching the "persistent sync denial" impact class.

### Likelihood Explanation
Anyone with push access to the tracked repository (an "attacker-pushed commit" in the threat model) can update a `.gitmodules`/gitlink entry to point at an older or side-branch commit of a submodule that is outside the shallow window implied by `--depth`. Since `--depth` (and recursion) are legitimate, commonly used operator flags (`--recursive-submodules`, `--depth`), this is readily triggerable in any deployment that combines shallow clones with submodules—an unprivileged, ordinary repository-content change, not a malicious-operator or leaked-credential scenario.

### Recommendation
Mirror the main-repo shallow-handling logic for submodules: check whether the module's local clone is shallow (or whether the requested commit is unreachable) before running `submodule update`, and fall back to `--unshallow` (or drop `--depth` and retry) instead of failing unconditionally. Alternatively, expose the submodule fetch depth as an independently configurable/overridable flag with a documented fallback path, rather than always reusing the top-level `--depth`.

### Proof of Concept
1. Configure `git-sync` with `--repo=<upstream>` `--depth=1` `--submodules=recursive`.
2. In the upstream repo, add a submodule pinned to commit `C` that is reachable in the submodule's history.
3. Push a new commit to upstream changing the submodule pointer to an older commit `C'` that lies beyond the last 1 commit of the submodule's default branch tip.
4. `git-sync` fetches the new top-level commit successfully, creates a new worktree, then `configureWorktree` runs `git submodule update --init --recursive --depth 1`, which fails because `C'` is not present in the shallow submodule fetch.
5. Every subsequent sync loop iteration reproduces the identical failure against the same `remoteHash`; `failCount` increments until `--max-failures` is reached, at which point `os.Exit(1)` terminates the process, leaving the published symlink permanently stuck on the last good revision (persistent sync denial).

// fetch retrieves the specified ref from the upstream repo.
func (git *repoSync) fetch(ctx context.Context, ref string) error {
	git.log.V(2).Info("fetching", "ref", ref, "repo", redactURL(git.repo))

	// Fetch the ref and do some cleanup, setting or un-setting the repo's
	// shallow flag as appropriate.
	args := []string{"fetch", git.repo, ref, "--verbose", "--no-progress", "--prune", "--no-auto-gc"}
	if git.depth > 0 {
		args = append(args, "--depth", strconv.Itoa(git.depth))
	} else {
		// If the local repo is shallow and we're not using depth any more, we
		// need a special case.
		shallow, err := git.isShallow(ctx)
		if err != nil {
			return err
		}
		if shallow {
			args = append(args, "--unshallow")
		}
	}
	if git.filter != "" {
		args = append(args, "--filter", git.filter)
	}
	if _, _, err := git.Run(ctx, git.root, args...); err != nil {
		return err
	}

	return nil
}
