### Title
Unchecked division by zero in `PoolState::token_price_x32` reachable from every swap instruction - (File: `programs/cp-swap/src/states/pool.rs`)

### Summary
`PoolState::token_price_x32` performs raw (non-`checked_div`) `u128` division using each side's "trading" vault balance as the divisor. Both `swap_base_input` and `swap_base_output` call this function on every invocation through `PoolState::get_swap_params`. If either side's trading balance (vault balance minus already-accrued-but-uncollected protocol/fund/creator fees) is zero, the division panics, aborting the transaction with a runtime panic instead of a controlled error.

### Finding Description
`token_price_x32` computes TWAP-oracle input prices with plain `/` operators instead of `checked_div`: [1](#0-0) 

It is invoked unconditionally inside `get_swap_params`, which both swap instructions call before running the curve math: [2](#0-1) 

`vault_amount_without_fee` (the source of the divisors) subtracts the pool's internally-tracked, not-yet-collected `protocol_fees`, `fund_fees`, and `creator_fees` from the actual vault token balance: [3](#0-2) 

Unlike every division in `curve/fees.rs` and `curve/calculator.rs`, which is wrapped in `Option`-returning `checked_div`/`ceil_div`/`floor_div` helpers that explicitly guard the zero-denominator case, this oracle-price computation performs the division directly, so a zero divisor causes an unrecoverable panic rather than a propagated `Result::Err`: [4](#0-3) 

A trading balance of zero for one token side is reachable without any privileged action: `withdraw` only rejects the transaction if the *withdrawn* `results.token_0_amount`/`token_1_amount` are zero, it does not guarantee the *remaining* pool trading balance stays above zero: [5](#0-4) 

If the last (or a majority) LP withdraws essentially all liquidity in a single `withdraw` call, the vault's actual token balance can be driven down to (approximately) just the amount of previously accrued but uncollected fees for one side, making `vault_amount_without_fee` return `0` for that token. Any subsequent `swap_base_input`/`swap_base_output` call by any unprivileged swapper against that pool then triggers the unchecked division in `token_price_x32` and panics.

### Impact Explanation
A panic inside `token_price_x32` aborts the swap transaction, denying all swap functionality for the affected pool. Because there is no minimum-liquidity lock enforced at `initialize`/`initialize_with_permission` time (unlike Uniswap-style AMMs that permanently burn a small minimum-liquidity LP amount), the pool can legitimately reach a state where the trading balance for one token is zero while the pool account, vault, and observation state still exist and are otherwise reachable. This is a reachable, unprivileged-triggerable denial-of-service on core swap functionality; whether it is fully permanent (i.e., whether a subsequent `deposit` or fee-collection instruction can restore the pool to a non-zero trading balance and unbrick swaps) could not be fully confirmed within the scope of this review, since `deposit.rs` was not inspected in detail.

### Likelihood Explanation
Reaching a zero-balance trading side requires a specific but plausible sequence: normal LP fee accrual over time followed by a withdrawal that removes essentially all remaining tradeable liquidity in one transaction, something any LP (including one acting adversarially against their own or another's pool) can trigger deterministically by choosing `lp_token_amount` to drain the pool.

### Recommendation
Replace the raw division in `token_price_x32` with `checked_div` (mirroring `curve/fees.rs`), propagate `None` to a proper `ErrorCode` instead of panicking, and consider enforcing a minimum reserve/trading-balance floor (or minimum-liquidity lock at pool initialization) so vault trading balances cannot be reduced to zero by a `withdraw` call while fees remain uncollected.

### Proof of Concept
1. Create a pool via `initialize` and perform swaps so that `protocol_fees_token_0`/`fund_fees_token_0`/`creator_fees_token_0` accrue in `PoolState` (see `pool_state.update_fees`, reachable from `swap_base_input`/`swap_base_output`).
2. As the LP, call `withdraw` with `lp_token_amount` equal to (or close to) the full `lp_supply`, driving the vault's actual `token_0_vault.amount` down to approximately the uncollected `fees_token_0` value, without triggering the `ZeroTradingTokens` check in `withdraw.rs` (which only checks the *withdrawn* amount, not the remaining balance).
3. Any user then calls `swap_base_input` or `swap_base_output` on this pool; `get_swap_params` → `token_price_x32` computes `... / token_0_amount as u128` with `token_0_amount == 0`, causing an unchecked integer-division panic that aborts the transaction and blocks all swaps against the pool.

**Confidence note:** I verified the unchecked division and its call path definitively, but did not have remaining tool calls to inspect `deposit.rs` or the fee-collection instructions to confirm whether the pool can ever recover from this zero-balance state (i.e., whether the freeze is permanent or temporary). This should be validated before treating impact as "permanent freezing of funds" versus a transient DoS.

        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }

fn ceil_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {
    if fee_denominator == 0 {
        return None;
    }
    token_amount
        .checked_mul(u128::from(fee_numerator))?
        .checked_add(fee_denominator)?
        .checked_sub(1)?
        .checked_div(fee_denominator)
}

/// Helper function for calculating swap fee
pub fn floor_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {
    if fee_denominator == 0 {
        return None;
    }
    token_amount
        .checked_mul(fee_numerator)?
        .checked_div(fee_denominator)
}
