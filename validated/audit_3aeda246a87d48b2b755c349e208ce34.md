### Title
Webhook signature verification is keyed on `repository.owner.login`, while the actual write target is selected from the independent, unverified `repository.full_name` field — allowing cross-repository/cross-stack writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) validates the incoming HMAC using one JSON field, while the code path that actually performs the write (`Shipit::Webhooks::Handlers::Handler#stacks`) resolves the target `Stack`/`Repository` from a *different*, independent JSON field in the same unauthenticated request body. Nothing binds the two together, so a payload can be "authenticated" as belonging to one organization while its side effects are applied to a completely different organization's stack — the same class of bug as the `ManagedWallet` finding, where a value (`activeTimelock`) was armed via one code path (`receive()`/`confirmationWallet`) without being bound to the specific proposal it was meant to gate.

### Finding Description
`WebhooksController#verify_signature` selects the app/secret to verify against using: [1](#0-0) 

`repository_owner` is read straight from the untrusted JSON body: [2](#0-1) 

Verification itself is a no-op whenever that organization's configuration has no `webhook_secret` set: [3](#0-2) 

Shipit explicitly documents `webhook_secret` as optional per organization in multi-org setups: [4](#0-3) 

Separately, once the request passes `verify_signature`, the actual event handlers (`PushHandler`, `StatusHandler`, `MembershipHandler`, `pull_request/*`, etc.) resolve which `Stack`/`Repository` to write to using a *different* JSON field, `repository.full_name`, via the shared `Handler` base class: [5](#0-4) 

Because `repository.owner.login` (used only to pick the verifying secret) and `repository.full_name` (used only to pick the write target) are two independent, attacker-supplied fields of the same JSON body, there is no enforcement that the repository being "authenticated for" is the repository being written to. `PushHandler`, for instance, enqueues a real sync against whatever stack `repository.full_name` names: [6](#0-5) 
which ultimately fetches commits from GitHub and appends them into the target stack's timeline: [7](#0-6) 

**Before/after of the broken binding:**
- Expected binding: `organization-that-signed(payload) == organization-that-owns(repository.full_name written to)`.
- Actual behavior: `organization-that-signed(payload)` is derived from `repository.owner.login`/`organization.login`, entirely decoupled from `repository.full_name`, so an attacker can make these unequal while both are still accepted, exactly as `ManagedWallet`'s `activeTimelock` could be armed independent of any real proposal.

### Impact Explanation
If any organization configured in `Shipit.github` (per the documented multi-org schema) has a blank/optional `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally regardless of payload contents. An unauthenticated, unprivileged attacker can then send a forged webhook with `repository.owner.login` set to that no-secret organization (satisfying `verify_signature`) but `repository.full_name` set to any other onboarded repository/stack in the same Shipit install. The `create` action will process the event and dispatch handlers (`push`, `status`, `pull_request`, `membership`, etc.) against the victim stack — enqueuing `GithubSyncJob`, creating commit statuses, opening/closing merge requests, or creating teams/users — without any credential belonging to that victim organization. This is an unauthorized cross-repository write into another org's deployment pipeline, which is explicitly listed as a Critical-severity impact in scope.

### Likelihood Explanation
Reachability requires only knowledge of one onboarded organization/repo name that has no `webhook_secret` configured (an explicitly supported, documented configuration state — `config/secrets.development.example.yml` shows `webhook_secret: # nil` as a normal per-org setting) and the target repository's full name, both of which are non-secret, discoverable values. No session, API token, or GitHub credential is required — the `WebhooksController` is unauthenticated by design (it authenticates via HMAC only). This is reachable purely through the engine's own routing/controller code as documented, not through host misconfiguration outside the documented setup.

### Recommendation
Bind the signature-verification identity to the write target: require that the organization/owner used to select the `GitHubApp`/`webhook_secret` (`repository_owner`) matches the organization portion of `repository.full_name` (and of `organization.login` when present) before dispatching any handler. Additionally, treat a missing `webhook_secret` for an organization as "signature required to be absent from a header, but payload's declared repository must belong to that exact org" rather than an automatic pass allowing arbitrary target repositories.

### Proof of Concept
Conceptual PoC (assuming a multi-org Shipit deployment where org `attacker-org` has no `webhook_secret` configured, and `victim-org/victim-repo` is a stack tracked by the same Shipit instance):

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-empty

{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
- `verify_signature` calls `Shipit.github(organization: "attacker-org")`; since that org's `webhook_secret` is nil, `verify_webhook_signature` returns `true` unconditionally regardless of the (bogus) `X-Hub-Signature`.
- `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")`, not `attacker-org`, and calls `stack.sync_github(expected_head_sha: "deadbeef")`, enqueuing a real `GithubSyncJob` against the victim's stack — with zero credentials belonging to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
