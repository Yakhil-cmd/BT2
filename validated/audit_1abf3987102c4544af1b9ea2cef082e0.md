### Title
Unbounded iteration over globally shared `assocUnstableMessages` in data-feed lookups allows AA-trigger DoS - (File: data_feeds.js)

### Summary
`dataFeedExists()` and `readDataFeedValue()` in `data_feeds.js` contain a code path (`bAA`/`unstable_opts` branch) that iterates over **every currently unstable unit in the whole DAG** (`storage.assocUnstableMessages`) rather than a scoped, bounded set, in order to find data-feed messages posted by the queried oracle addresses. This mirrors the reported `Carousel.getRolloverTVL`/`getDepositQueueTVL` pattern: a collection that any unprivileged unit poster can grow, and that is only shrunk by an external process (main-chain stabilization), is fully scanned on every call of a widely used function.

### Finding Description
`dataFeedExists` (used for the `in data feed` / `in_data_feed` operators) and `readDataFeedValue` (used for the `data_feed[[...]]` operator) both have a branch that runs before falling back to the indexed kvstore lookup: [1](#0-0) 

```
for (var unit in storage.assocUnstableMessages) {
    var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
    ...
    storage.assocUnstableMessages[unit].forEach(function (message) { ... });
}
``` [2](#0-1) 

and the equivalent in `readDataFeedValue`: [3](#0-2) 

`storage.assocUnstableMessages` holds the messages of **all** units that are not yet stable network-wide, not just the messages of the oracle addresses being queried — the address/oracle filter (`_.intersection(arrAddresses, objUnit.author_addresses)`) is applied only *inside* the loop, after already touching every unstable unit. Entries are only removed when a unit's main-chain index stabilizes (during `markMcIndexStable`), a process entirely outside the control of the caller performing the data-feed lookup.

This code is reachable from AA (oscript) evaluation on every trigger that uses `data_feed[[...]]` or `in_data_feed[[...]]`: [4](#0-3) [5](#0-4) 

An unprivileged unit poster can inflate the size of `assocUnstableMessages` by broadcasting a large volume of units (any app, including trivial `data_feed` or `text` messages) faster than they can be included on the stable main chain, keeping the in-memory unstable-unit set large for as long as they keep posting. Because the loop cost is `O(number_of_unstable_units × messages_per_unit)` and is paid by **every** node evaluating **every** AA trigger that touches a data feed (a very common oscript primitive used by oracle-driven AAs), this degrades or stalls AA trigger processing across the whole node, and by extension network throughput for AA-based contracts, whenever the unstable-unit backlog is inflated.

### Impact Explanation
Because the vulnerable loop executes inside `handleTrigger`/AA formula evaluation, which runs while holding the `aa_triggers` mutex lock (see `handlePrimaryAATrigger` in `aa_composer.js`), an attacker inflating `assocUnstableMessages` can slow down or effectively freeze processing of AA triggers for all AAs that rely on `data_feed`/`in_data_feed`, causing delayed/failed AA responses (fund freezing for users interacting with oracle-backed AAs) and a general slowdown of the node's ability to keep up with AA-trigger backlog, which is a network-wide "unable to confirm/process new units" style impact, satisfying the Medium bar analogous to the source report.

### Likelihood Explanation
Any unprivileged unit poster can grow the unstable-unit backlog just by posting many valid units; no special privilege, oracle role, or AA is required to trigger the expensive loop — only that at least one AA/formula in active use queries a data feed via `data_feed[[...]]`/`in_data_feed[[...]]`, which is a routine, commonly used oscript feature. The backlog shrinkage depends on independent, non-attacker-controlled stabilization timing, so a sustained flood can keep the collection inflated for extended periods.

### Recommendation
Do not scan the entire `assocUnstableMessages` map. Instead:
- Maintain a secondary index keyed by `(address, feed_name)` (or at least by author address) for unstable data-feed messages, so lookups touch only messages relevant to the requested oracle addresses.
- Alternatively, cap the number of unstable units/messages considered (with a hard limit and early bail-out), returning a deterministic "ambiguous/not found" once the cap is exceeded, similar to the `ifseveral: 'abort'` semantics already present.
- Consider bounding how large `assocUnstableMessages` can grow before rejecting further unit posting/relaying at the mempool layer, independent of this fix.

### Proof of Concept
1. Attacker (unprivileged) repeatedly posts many valid units (any payload, e.g., minimal `data_feed` messages) in quick succession, faster than the network's main-chain stabilization rate, so that `storage.assocUnstableMessages` accumulates a large number of unstable units/messages.
2. Any AA that is triggered and whose oscript formula evaluates `data_feed[[oracles="X", feed_name="Y", ...]]` (or `in_data_feed[[...]]`) now causes `readDataFeedValue`/`dataFeedExists` to iterate the full, attacker-inflated `assocUnstableMessages` map before doing the indexed lookup.
3. As the map size grows, the per-trigger evaluation time grows proportionally, delaying/blocking `handlePrimaryAATrigger` (held under the `aa_triggers` mutex) for that and subsequent triggers, causing all oracle-dependent AAs on the node to fall behind or effectively stall until the backlog is cleared by main-chain stabilization — a process the attacker does not control and can keep re-triggering.
