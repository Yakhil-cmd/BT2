### Title
Cross-organization webhook forgery via signature-selection field decoupled from event target - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / webhook secret to validate an inbound webhook against by reading an attacker-controlled field out of the very payload it is about to authenticate, rather than deriving trust from a fixed, out-of-band binding. In a multi-organization Shipit deployment (multiple GitHub Apps, one per org, each with its own `webhook_secret`, as shown by `test/dummy/config/secrets_double_github_app.yml`), this lets an attacker who controls their own onboarded organization forge a webhook whose `repository.owner.login` matches their own org (so it validates with a secret they legitimately know) while the rest of the payload (`repository.full_name`, commit SHAs, PR data, etc.) references a completely different, victim organization/repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` resolves the GitHub App config with:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization app configuration/secrets:
```ruby
def github(organization: github_default_organization)
  if github_default_organization.nil?
    config = secrets.github
  else
    config = github_app_config(organization)
    raise GithubOrganizationUnknown, organization if config.nil?
  end
  @github ||= {}
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [3](#0-2) 

and multi-org deployments configure a distinct `webhook_secret` per org, e.g. `OrgOne`/`OrgTwo` in the fixture config: [4](#0-3) [5](#0-4) 

The HMAC check itself (`verify_webhook_signature`) only proves that the raw body was signed with *the secret chosen above* — it says nothing about whether that secret's organization actually matches the repository the payload claims to describe elsewhere in the same JSON body: [6](#0-5) 

Downstream event handling (e.g. the push handler that resolves a `Stack`/`Repository` and enqueues `GithubSyncJob`) resolves the *target* repository from a different payload field, `repository.full_name`, independently of `repository.owner.login`: [7](#0-6) 

Because `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository/stack) are two independent, attacker-supplied fields of the same forged JSON body, there is no cryptographic or logical binding forcing them to refer to the same organization. An attacker who legitimately owns an organization (`OrgA`) with the Shipit GitHub App installed knows `OrgA`'s own `webhook_secret` (they configured the App). They can craft a payload with `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")` is used and the attacker's own valid HMAC passes) but `repository.full_name = "OrgB/victim-repo"`, where `OrgB` is an unrelated organization/repository tracked by the same Shipit instance. The signature check passes (it's a legitimately-signed, attacker-authored body under `OrgA`'s key), yet the event handlers act on `OrgB`'s stack — e.g. queuing `GithubSyncJob`, updating commit statuses, or driving merge/pull-request state — none of which the attacker is authorized to touch.

This is the exact class of trust-binding break called out in the report analog: address-aliasing broke the equality between "the entity that authenticated at L1" and "the entity permitted to act at L2." Here, the equality broken is: *organization whose secret authenticated the request* == *organization/repository the payload's content is applied to*. Those are never checked to be equal.

### Impact Explanation
This allows an attacker who merely has a legitimately-onboarded organization on a shared Shipit instance to inject validly-signed webhook events that are attributed to and acted upon for a different organization/repository. Depending on which webhook handler is triggered, this can drive `GithubSyncJob` execution, alter commit/check statuses used as deploy gating conditions, or manipulate the merge queue/pull-request state for a repository the attacker does not own or have write access to — a cross-repository/cross-organization write performed without the corresponding organization's authorization. This matches the Critical impact bucket "cross-repository writes."

### Likelihood Explanation
Requires only that (a) the Shipit instance is configured for multiple GitHub organizations/Apps (a supported, documented configuration — see `secrets_double_github_app.yml`), and (b) the attacker controls at least one onboarded organization (which they can do legitimately, e.g., by asking to have their own team/org repo tracked by Shipit, a common self-service pattern). No repository write access, session, or API token is needed — only knowledge of a webhook secret the attacker legitimately possesses for their own org. This is a realistic scenario for any Shipit deployment serving more than one organization.

### Recommendation
Do not select the verifying secret from an attacker-controlled field of the payload being verified. Instead, bind webhook secret selection to a value established out-of-band (e.g. keep a single global secret when only one org is expected, or, for multi-org setups, verify the signature against *all* configured org secrets and require that the org whose secret validates is the same org referenced by `repository.full_name`/`repository.owner.login` used later by handlers — rejecting the request if they diverge). At minimum, after signature verification, re-derive `repository_owner` and confirm it matches the owner segment of `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Attacker configures/owns organization `OrgA`, which has the Shipit GitHub App installed with `webhook_secret = SECRET_A` (known to the attacker as the org admin).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  },
  "after": "<arbitrary sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(SECRET_A, body)` and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature using `SECRET_A` [1](#0-0) .
5. The push handler resolves the target using `repository.full_name = "OrgB/victim-repo"` and enqueues sync/processing for `OrgB`'s stack — even though only `OrgA`'s secret validated the request [7](#0-6) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
