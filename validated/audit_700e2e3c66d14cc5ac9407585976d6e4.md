### Title
`swap_debt` reverts with `PositionLimitExceeded` for accounts at the borrow-position cap even though the rotation nets to the same count - (File: contracts/controller/src/strategies/swap_debt.rs)

### Summary
`swap_debt` mints the new debt leg via `borrow_into_controller` before repaying the existing debt leg. `borrow_into_controller` runs `validate_position_entry_gates` → `validate_bulk_position_limits`, which counts the account's *current* borrow book (old leg still present) plus the new slot. An account holding `max_borrow_positions` debt legs can never rotate one of them into a new asset, even though the final book would still contain exactly `max_borrow_positions` legs.

### Finding Description
The order of operations in `process_swap_debt` is:

1. `borrow_into_controller(env, account, new_debt, ...)` — opens the new debt leg and runs `validate_position_entry_gates` against the *pre-repay* account.
2. `swap_tokens_or_passthrough` — converts the new asset into the old asset.
3. `repay_debt_from_controller(...)` — repays (potentially fully, removing) the `existing_debt` leg.
4. `strategy_finalize` — post-pool solvency gate on the net result. [1](#0-0) 

Inside `borrow_into_controller`, `validate_position_entry_gates` calls `validate_bulk_position_limits`, which computes `current_count = account.borrow_positions.len()` and adds 1 for `new_debt` — which is never `already_present`, because `existing_debt != new_debt` is asserted at line 39-43. [2](#0-1) [3](#0-2) 

Since `existing_debt` is still in `borrow_positions` at this point, `total_positions = max_borrow_positions + 1` reverts with `PositionLimitExceeded`, even though the repay leg would have freed the slot. This is the same shape as the OrderBook finding: a combined reduce+replace operation is priced/gated on the gross intermediate state rather than the net final state. The docs acknowledge the constraint ("The new borrow must fit its borrow cap and the borrow-position limit before repayment," `docs/reference/endpoints.md:33`) but that is the bug, not a mitigating design — there is no reason the count gate must see the pre-repay book.

Note the contrast with `swap_collateral`, which withdraws *first* and only then deposits the new leg, so its supply-count gate already observes the net book. [4](#0-3) 

### Impact Explanation
Any unprivileged account owner whose borrow book is at `max_borrow_positions` (e.g. a leveraged position diversified across debt assets) cannot use `swap_debt` to refinance into a new debt asset, including cases where refinancing is needed to escape a depegging asset, a rising-rate market, or a market about to be delisted. The only workaround is repaying a full debt leg out of pocket in a separate transaction to free a slot — requiring external liquidity the user may not have. This is a temporary freezing of a protocol function and forced multi-transaction sequencing, the same harm class as the source finding.

### Likelihood Explanation
Reachable by any account owner with `account.borrow_positions.len() == max_borrow_positions` calling `controller::swap_debt(caller, account_id, existing_debt, amount, new_debt, swap)` where `new_debt` is a market not already in the book. `PositionLimitExceeded` reverts deterministically before any token movement; no oracle, price, or counterparty dependency is needed. The default cap is small (`POSITION_LIMIT_MAX`, exercised as 5 in Certora fixtures), making a full borrow book a routine state.

### Recommendation
In `process_swap_debt`, pre-check whether the repay leg will close `existing_debt` (e.g. skip the count contribution when the planned repay covers the full ceiled debt), or perform the position-limit validation on the post-repay book inside `strategy_finalize` instead of inside `borrow_into_controller`. Alternatively, add a swap-debt-specific entry-gate path that exempts the `new_debt` slot when `existing_debt` is being fully repaid in the same call.

### Proof of Concept
Conceptual sequence (single unprivileged account owner):

1. Governance-configured `max_borrow_positions = 2` (or governance later lowers it; existing books are grandfathered per `validate_bulk_position_limits` line 99-102).
2. Account holds collateral plus debt in `ETH` and `WBTC` → `borrow_positions.len() == 2`.
3. Call `swap_debt(caller, account_id, ETH_key, amount, USDC_key, swap)` intending to close the ETH leg and open a USDC leg — net count still 2.
4. `borrow_into_controller` → `validate_bulk_position_limits` sees `current_count = 2`, `new_debt` (USDC) `already_present = false` → `new_positions_count = 1`, `total_positions = 3 > 2` → `CollateralError::PositionLimitExceeded`.
5. The call reverts even though the subsequent `repay_debt_from_controller` would have removed the ETH leg. The test harness confirms the same gate ordering: `test_borrow_position_limit_exceeded` (`tests/test-harness/tests/controller/borrow.rs:141-152`) shows `borrow_positions.len() == max` rejects any new debt asset.

```rust
    let limits = storage::get_position_limits(env);

    let (current_count, max_allowed) = match position_type {
        AccountPositionType::Deposit => {
            (account.supply_positions.len(), limits.max_supply_positions)
        }
        AccountPositionType::Borrow => {
            (account.borrow_positions.len(), limits.max_borrow_positions)
        }
    };

    let mut seen: Map<HubAssetKey, bool> = Map::new(env);
    let mut new_positions_count: u32 = 0;
    for (hub_asset, _) in aggregated.iter() {
        if seen.contains_key(hub_asset.clone()) {
            continue;
        }
        seen.set(hub_asset.clone(), true);

        let already_present = match position_type {
            AccountPositionType::Deposit => account.supply_positions.contains_key(hub_asset),
            AccountPositionType::Borrow => account.borrow_positions.contains_key(hub_asset),
        };
        if !already_present {
            new_positions_count += 1;
        }
    }

    // Existing positions remain usable after governance lowers the position limit.
    if new_positions_count == 0 {
        return;
    }

    let total_positions = current_count
        .checked_add(new_positions_count)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        total_positions <= max_allowed,
        CollateralError::PositionLimitExceeded
    );
```
