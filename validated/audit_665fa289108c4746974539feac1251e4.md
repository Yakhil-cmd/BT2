### Title
`StatusHandler` resolves commits by SHA globally instead of by repository, letting an attacker-controlled repository's status webhook write `Status` rows onto any other tenant's stack that happens to share the same commit SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha).each`, which is not scoped to the repository that sent the webhook, unlike every other handler that derives its `stacks`/commits via `Repository.from_github_repo_name(repository_name)`. Because the `commits` table's uniqueness constraint on `sha` is scoped to `(sha, stack_id)`, not global, a status payload for a SHA that exists in an unrelated victim stack (e.g. the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee491`, or any coincidental SHA collision such as no-op squash merges across independent repos) will create/replicate a GitHub status on the victim stack's commit.

### Finding Description
The broken binding, stated explicitly: the code path assumes `sha` is unique across the entire multi-tenant `Commit` table (`Commit.where(sha: params.sha)` returning "the" commit), when in reality uniqueness is only enforced per stack via the index `add_index :commits, %i(sha stack_id), unique: true` [1](#0-0) .

The handler's `process` method:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This never consults `payload.dig('repository', 'full_name')` or the base class's `stacks` helper, which is exactly what other handlers use to scope their side effects to the sending repository: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [3](#0-2) .

`verify_signature` in the controller only checks that the webhook is validly signed for the organization named in the payload (`repository_owner`) using `Shipit.github(organization: repository_owner)` [4](#0-3) ; it does not, and cannot, restrict which `sha` values the payload may reference or which stacks the handler ultimately mutates. So a legitimately signed webhook from any onboarded GitHub organization/repository B can carry an arbitrary `sha` (including one that has never existed in repository B at all), and `StatusHandler` will apply it to every `Commit` record across every stack/repository in the installation whose `sha` column matches, calling `commit.create_status_from_github!(params)` on each [5](#0-4) . That method creates a `Status` row via `statuses.replicate_from_github!(stack_id, github_status)` and triggers `add_status`, which emits hooks and can call `stack.schedule_merges` when the new status is `success`/`pending` [6](#0-5) .

Exploit flow: attacker owns/controls repository B (onboarded under some org with the GitHub App/webhook secret configured, satisfying `verify_signature`). Attacker triggers (or crafts) a `status` event referencing `sha = "4b825dc642cb6eb9a060e54bf8d69288fbee491"` (the git empty-tree SHA, which naturally recurs across many independent repositories/commits, e.g. no-op squash merges) with `state: "success"`. If any unrelated victim stack A already has a `Commit` row with that same SHA (highly plausible given the empty-tree SHA is git-universal, or any other naturally colliding SHA), Shipit writes a new success `Status` onto stack A's commit, potentially unblocking `deployable?` checks and triggering `schedule_merges`/continuous delivery for stack A - despite the webhook never originating from stack A's repository.

### Impact Explanation
This is a cross-tenant write: a webhook authenticated only for repository B's organization causes state changes (`Status` creation, potential `schedule_merges`/deploy-readiness changes) on stack A, a completely unrelated repository/tenant, with no validation that B has any relationship to A. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." The blast radius spans every stack in the Shipit installation that happens to contain a commit with a colliding SHA - trivially achievable via the git empty-tree SHA, which is deterministic and identical across all repositories that ever produce an empty commit (common with squash-merge no-ops, initial commits, or CI tooling). It is repeatable indefinitely and requires no cryptographic collision construction, since the empty-tree SHA is a known constant.

### Likelihood Explanation
Preconditions: the attacker must control a repository that is legitimately onboarded to a GitHub App/org for which Shipit already has a configured webhook secret (so `verify_signature` passes) - this is the same precondition the question's threat model grants ("send one status webhook from B claiming success for that sha... from any signed org"). No GitHub token, Shipit session, or knowledge of any secret belonging to the victim is required. The victim precondition (a stack already containing a commit with the colliding SHA) is not attacker-controlled but is realistic given the empty-tree SHA's ubiquity, or any other repo pair sharing history (forks, mirrors, template repos). Given these preconditions, the attack is cheap (one HTTP webhook POST) and fully repeatable against any SHA collision the attacker can find or wait for.

### Recommendation
Scope `StatusHandler#process` to the repository that sent the webhook, mirroring the `Handler#stacks` pattern used elsewhere: resolve `Repository.from_github_repo_name(repository_name)&.stacks` (or the equivalent commits scoped to that repository/stack) and restrict `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring only commits belonging to stacks under the sending repository are updated.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create two stacks, `victim_stack` (repo `victim/repo`) and `attacker_stack` (repo `attacker/repo`).
2. Seed `victim_commit = Shipit::Commit.create!(stack: victim_stack, sha: '4b825dc642cb6eb9a060e54bf8d69288fbee491', ...)` with no statuses.
3. Build a `status` webhook payload for `attacker/repo` with `sha: '4b825dc642cb6eb9a060e54bf8d69288fbee491'`, `state: 'success'`, and dispatch it through `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (bypassing signature verification, as the finding is about the handler logic, not signature bypass).
4. Assert: before the call, `victim_commit.statuses.count == 0`; after the call, `victim_commit.reload.statuses.count == 1` and `victim_commit.status.success?` is true - proving that a webhook whose payload names `attacker/repo` mutated `victim/repo`'s stack's commit state.
5. Equality check to assert: `victim_commit.stack_id != Repository.from_github_repo_name('attacker/repo')&.stacks&.pluck(:id)&.first` (i.e., the victim stack does not belong to the attacker's repository) while the `Status` was still created - demonstrating the binding "sha uniqueness across the Commit table == sha uniqueness within a repository" is false yet exploited.

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
