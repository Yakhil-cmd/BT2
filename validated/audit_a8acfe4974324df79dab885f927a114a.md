### Title
CCMenu API token is not stack-scoped, allowing any stack's public radiator URL to read every stack's deploy status - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`Api::BaseController` is designed to scope `ApiClient` tokens to a single stack via `stack_id`, but the CCMenu ("build radiator") flow creates a token with no stack binding at all and the CCMenu API controller bypasses the stack-scoping helper entirely. The result: the token embedded in a URL meant for one specific stack's public/semi-public status radiator can be reused to read the deploy status of **every** stack in the Shipit instance.

### Finding Description
`Api::BaseController` normally restricts a stack-scoped `ApiClient` to the stack it was issued for: [1](#0-0) 

`CCMenuUrlController#client`, which mints the token embedded in the CCMenu/CCTray URL handed back to the browser, creates the `ApiClient` with the `read:stack` permission but never sets `stack:`, so `stack_id` is `nil`: [2](#0-1) 

Because `stack_id` is `nil`, `current_api_client.stack_id?` is false, so even the generic `stacks` scoping in `BaseController` would already resolve to `Stack.all` instead of the one stack the URL was generated for.

On top of that, `Api::CCMenuController` doesn't even use the inherited `stacks`/`stack` scoping — it overrides `stack` to look up directly by the `stack_id` param, and authenticates purely via a `token` query parameter (rather than the Basic-Auth header used elsewhere): [3](#0-2) 

`ApiClient.authenticate` only verifies the signature of the token (proving it names a valid `ApiClient` id) and does not re-check any per-stack claim, since none was ever embedded: [4](#0-3) 

The binding that should hold is: `token.stack == stack_being_read`. Instead, because `client` is a single, unscoped `ApiClient` shared per creator (`find_or_create_by!(creator: current_user, name: 'CCMenu Client')`), and `CCMenuController#stack` accepts any `stack_id` from the request, the actual relationship is `token.stack == nil` (authorizes `read:stack` broadly) while `stack_being_read == any stack_id supplied in the URL`. Anyone who obtains one CCMenu URL — which is explicitly designed to be pasted into external CI dashboards/build radiators (a lower-trust distribution context) — can swap the `stack_id` in the URL and read the status/deploy output of any other stack hosted on the same Shipit instance.

### Impact Explanation
This is an unauthenticated (from the target stack's perspective) read of stack state for stacks the token was never meant to access — matching the "unauthenticated read of stack state, task streams or deploy output" High-severity class, since the leaked/shared radiator token silently escalates from single-stack to whole-instance read access.

### Likelihood Explanation
CCMenu/CCTray URLs are intentionally generated to be embedded in third-party status-board tools and shared outside of the authenticated Shipit session (that's the entire purpose of `CCMenuUrlController`), so exposure of the URL/token to a party who should only see one stack is a realistic, low-effort scenario — no privileged access or session is required beyond having obtained any one stack's radiator link.

### Recommendation
Bind the `ApiClient` created in `CCMenuUrlController#client` to the specific `stack` (`ApiClient.create_with(permissions: %w[read:stack], stack:)`), scope `find_or_create_by!` per stack (not just per creator), and make `Api::CCMenuController#stack` go through the inherited `stacks` scoping (or explicitly verify `current_api_client.stack_id == stack.id`) instead of resolving `Stack.from_param!` unconditionally.

### Proof of Concept
1. As user A, visit stack `foo`'s settings page and fetch its CCMenu URL via `GET /ccmenu/foo` → `CCMenuUrlController#fetch` returns `.../api/foo/ccmenu?token=<T>` [5](#0-4) .
2. Take token `<T>` and request `GET /api/bar/ccmenu?token=<T>` for an unrelated stack `bar` that user A (or whoever leaked the URL) has no relation to.
3. `Api::CCMenuController#authenticate_api_client` accepts `<T>` (it only verifies the signature, not the stack) [6](#0-5) , and `#stack` resolves `bar` directly from `params[:stack_id]` [7](#0-6) , returning `bar`'s deploy/build status — an out-of-scope read.
