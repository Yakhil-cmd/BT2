### Title
`PYTHONPATH` injected via uppercased pull-request label reaches shell-interpreted `shipit.yml` step env - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased, value `"true"`) into the environment with no key allowlist, and that hash flows unfiltered into `TaskCommands#env` and then into `Command#env`/`unbundled_env`, which is passed to `PTY.spawn`. An attacker who opens/labels a PR on their own fork can set a label literally named `pythonpath` to inject a `PYTHONPATH=true`-style variable into the process environment of any shell-interpreted `shipit.yml` step for that stack.

### Finding Description
The broken binding: the set of environment variable keys that reach `PTY.spawn` for a review-stack task should equal the set of keys explicitly whitelisted by the task/stack configuration (`TaskDefinition#filter_envs` / `EnvironmentVariables#permit`). Instead, for review stacks it equals `whitelisted_keys ∪ pull_request.labels.map(&:upcase)`.

Path:
- `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` straight from the webhook body with no name restriction: [1](#0-0) .
- `ReviewStack#env` merges those label names, uppercased, directly into the stack env with `labels[label_name.upcase] = "true"`, with no allowlist check: [2](#0-1) .
- `TaskCommands#env` merges `@stack.env` into the command env used to build each step's `Command`: [3](#0-2) .
- `Command#parse_arguments` keeps a string step (a plain YAML string in `shipit.yml`) as a single array element rather than splitting it into argv, and `#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` — a single string argument makes Ruby invoke the command through `/bin/sh -c`: [4](#0-3) [5](#0-4) .
- `unbundled_env` merges `@env.stringify_keys` (which includes the label-derived keys) on top of `BASE_ENV`/`PATH`, so any key the attacker names via a label becomes part of the actual child process environment: [6](#0-5) .

Existing guard that does exist but doesn't cover this path: `TaskDefinition#filter_envs` uses `EnvironmentVariables#permit` to whitelist variables against `variable_definitions` [7](#0-6) , and `EnvironmentVariables#permit` raises `NotPermitted` for any non-whitelisted key [8](#0-7) . However, `filter_envs`/`permit` is not invoked anywhere in `TaskCommands#env` or `ReviewStack#env` — those methods merge the label-derived hash unconditionally, so this allowlist mechanism never runs against PR-label-derived environment variables. `docs`/tests confirm the intended, unfiltered behavior: `test/models/shipit/review_stack_test.rb` and `test/lib/shipit/task_commands_test.rb` both assert that arbitrary label names appear verbatim (uppercased) in `env`, e.g. `env["WIP"]`/`env["BUG"]` [9](#0-8) [10](#0-9) .

Attacker request/PR: opens a PR from a fork against a repository with `provisioning_behavior=allow_with_label` (per Q2255's stated precondition) and applies a label literally named `pythonpath` (any case) via the GitHub UI/API on their own PR — no Shipit or GitHub secret required, since labeling one's own PR is an action any PR author with triage-less permissions can generally do only if they have label permission; on most repos only collaborators can add labels, but the webhook payload itself is attacker-shaped data captured verbatim by `LabelCapturingHandler`. Once captured, every review-stack task/deploy for that PR runs shell steps from `shipit.yml` with `PYTHONPATH=true` (or any attacker-chosen value if the label mechanism is abused further) merged into the environment, potentially altering `python` module resolution for any Python-invoking step in `shipit.yml`.

### Impact Explanation
If a `shipit.yml` step invokes `python` (or any interpreter respecting a similarly named env var), the injected variable can alter interpreter/module resolution behavior for that shell-interpreted step, executing on the Shipit deploy host. This affects only the specific stack/PR where the label was applied (the ReviewStack belonging to that PR), not arbitrary other tenants' stacks, since `ReviewStack#env` is scoped to `pull_request.labels` on `self`. Severity depends heavily on whether the target repository's `shipit.yml` actually has a python step and whether an attacker-controlled module path can be placed on disk in the working directory (the "attacker prepends an attacker module path" claim in the question is not substantiated anywhere in the traced code — there is no code here that writes attacker-controlled files to a location `PYTHONPATH` could point to). Without a concrete file-write primitive, this is at most an environment-variable-injection primitive, not a demonstrated RCE.

### Likelihood Explanation
Requires: (1) `review_stacks_enabled` and `provisioning_behavior=allow_with_label` on the target repository (an operator/maintainer configuration choice), (2) actual repository `shipit.yml` steps that are shell/string-form and sensitive to `PYTHONPATH` (or another dangerous variable name), and (3) ability to add a label to the PR, which typically requires write/triage access on the base repository (label creation/assignment is normally restricted to collaborators, not arbitrary fork PR authors) — this weakens the "unprivileged attacker" premise for the labeling step itself, though `LabelCapturingHandler` will capture whatever labels are present in the webhook payload without validating who applied them.

### Recommendation
Apply the same `EnvironmentVariables#permit` allowlist used by `TaskDefinition#filter_envs` to pull-request-label-derived environment entries before merging them into `ReviewStack#env`/`TaskCommands#env`, or maintain an explicit prefix/allowlist (e.g., only merge label keys matching a safe pattern, and always reject/strip well-known dangerous variable names such as `PATH`, `PYTHONPATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `BASH_ENV`, `IFS`) at the point labels are turned into env vars in `app/models/shipit/review_stack.rb`.

Given the current code, this assertion fails: `stack.env["PYTHONPATH"]` equals `"true"`, confirming the unfiltered merge in `app/models/shipit/review_stack.rb:84-93`. Full RCE demonstration (attacker module import) is not verifiable from this codebase alone since no code path was found that writes an attacker-controlled Python module to a path `PYTHONPATH` could reference — this part of the question's claim remains unconfirmed within the traced files.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
