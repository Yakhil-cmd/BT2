### Title
Unsanitized pip/venv stderr tail leaks into `sdk_bootstrap_err` telemetry, risking private-index credential exposure - ([File: plugins/security-guidance/hooks/ensure_agent_sdk.py])

### Summary
When `pip install` fails during the SDK bootstrap and the failure doesn't match one of the explicit categorized patterns (`pip_no_match`, `dns_fail`, `proxy_auth`, etc.), `main()` falls back to embedding the last 60 characters of the last non-empty stderr line verbatim into `err_kind` as `f"other:{tail}"`. That value is emitted unmodified as the `sdk_bootstrap_err` telemetry metric via `print(json.dumps(...))`, with no scrubbing for embedded credentials such as Basic-Auth tokens in a private-index URL.

### Finding Description
The bootstrap runs `pip install --quiet --disable-pip-version-check claude-agent-sdk` without an explicit `--index-url`, intentionally inheriting whatever private registry configuration exists on the machine (comment at [1](#0-0) ). If that inherited index is a credentialed URL (e.g. `https://user:TOKEN@pip.internal/simple/`, configured via `pip.conf`, `PIP_INDEX_URL`, or `.netrc`) and the connection/auth attempt fails in a way not covered by the specific `elif` branches (DNS, connection-refused, SSL, permission, disk, proxy-407, timeout), the code falls into the catch-all branch: [2](#0-1) 
This takes the raw last line of stderr, truncates to 60 chars, and sets `err_kind = f"other:{tail}"` with no credential redaction. Underlying HTTP/connection-error messages from `requests`/`urllib3` (which pip uses internally) frequently include the full connection URL, including userinfo, in exception text for failure modes that aren't pip's own formatted, auth-redacted log lines (pip's `redact_auth_from_url` is applied to pip's own progress/log messages, not necessarily to lower-level library exception strings surfaced on connection failure). That raw tail is then printed to stdout as JSON: [3](#0-2) 
This stdout line is consumed by Claude Code's hook metrics pipeline and forwarded to the metrics/telemetry event, per the comment describing how CC's async-hook registry parses this exact JSON line. No allowlist, redaction, or secret-scrubbing step exists between the raw pip stderr and the emitted metric.

### Impact Explanation
If a victim's machine is configured with a credentialed private PyPI index and a pip failure surfaces the credential in an uncategorized error message, that credential (or a truncated 60-character fragment of it) is exfiltrated into the plugin's telemetry channel — a sink an attacker with visibility into telemetry logs/metrics (but no shell access to the victim machine) can read. This matches a secret-disclosure / trust-boundary-bypass impact: a local credential becomes readable through a diagnostic channel it was never intended to reach, and repeated triggering (each failed SessionStart bootstrap) could allow leaking successive 60-character windows of a longer secret if the attacker can influence or observe successive stderr tails.

### Likelihood Explanation
Requires: (1) the victim machine has a credentialed private package index configured, (2) `pip install claude-agent-sdk` against that index fails, (3) the failure mode is NOT one of the eight explicitly categorized patterns (so it lacks pip's own auth-redacted formatting and instead surfaces a raw urllib3/requests exception line), and (4) the attacker has read access to the telemetry sink. This is a plausible but non-trivial combination — most common pip failures against credentialed indexes (401/407, connection refused, SSL, DNS) are already caught by name-matching branches that emit fixed non-leaking strings, narrowing the exposure window to less-common error text shapes.

### Recommendation
Sanitize the stderr tail before using it as a telemetry value: strip or redact any `scheme://user:pass@` / `Authorization:` style substrings (e.g., regex-strip URL userinfo, or drop the whole tail if it contains `@` following `://`) before truncation, or avoid embedding raw stderr entirely and instead hash/bucket the tail (e.g., a hash of the normalized line) so diagnostic value is retained without any possibility of literal secret leakage.

### Proof of Concept
Unit test `test_other_branch_redacts_credentials`:
1. Construct `subprocess.CalledProcessError(1, cmd, output=b"", stderr=b"ERROR: HTTPSConnectionPool(host='user:sk-supersecrettoken@pip.internal', port=443): Max retries exceeded")`.
2. Monkeypatch `subprocess.run` so the `pip install` step raises this exception inside `main()`.
3. Call `main()` and capture `err_kind`.
4. Assert `"sk-supersecrettoken"` (and generally `"user:.*@"` patterns) is NOT a substring of `err_kind`, and that the returned value is bounded/redacted rather than the raw stderr tail — this assertion currently fails against the existing implementation, confirming the leak path.
