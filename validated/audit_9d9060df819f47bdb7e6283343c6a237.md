### Title
Unscoped, Perpetual `grant-signer-key` Authorization Lets a Signer-Manager Contract Stack Under Any PoX Address/Amount the Staker Never Approved - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5`'s new signer-manager delegation feature introduces a broad, unscoped authorization credential (`grant-signer-key`) that is the structural analog of the reported "cookie with an overly broad path" bug class: a single signature intended to authorize a narrow action is instead valid across a scope far wider than what the signer could have intended or reviewed, and it never expires.

### Finding Description
In `pox-4.clar`, every stacking action (`stack-stx`, `stack-extend`, `stack-aggregation-commit`, etc.) requires a signature over a message that binds the exact `pox-addr`, `reward-cycle`, `period`, `topic`, `amount`/`max-amount`, and a single-use `auth-id`, verified by `verify-signer-key-sig` [1](#0-0) . This tightly scopes what an authorization can be used for and consumes it (`consume-signer-key-authorization`) so it cannot be reused for a different action [2](#0-1) .

`pox-5.clar` replaces this per-action model, for signer-manager delegation, with `grant-signer-key`, whose signed message hash (`get-signer-grant-message-hash`) only commits to `signer-manager` and `auth-id` — it does not bind `pox-addr`, `reward-cycle`, `period`, or any amount: [3](#0-2) 

The contract's own comment states the intent was for `pox-addr` to be an *optional* field ("When `none`, it means the signer key can be used for any PoX address"), implying a design where the signer could optionally restrict the grant to one PoX address [4](#0-3) . However, the actual `get-signer-grant-message-hash` function takes no `pox-addr` parameter at all, so there is no way for a staker to scope the grant even if they wanted to — every grant is unconditionally valid for **any** PoX address, **any** reward cycle, **any** stacking period, and **any** amount.

Once `grant-signer-key` succeeds, it records `signer-key-grants { signer-key, signer-manager } -> true` permanently (until explicit `revoke-signer-grant`) [5](#0-4) . Every subsequent check against this authorization, `verify-signer-key-grant`, only checks the presence of `(signer-key, signer-manager)` in the map — again with no parameter for `pox-addr`, `amount`, or `reward-cycle` [6](#0-5) .

This is the direct analog of the cookie vulnerability: a credential meant to authorize a specific, narrow action (register this signer-manager to represent me for a stacking cycle/amount I reviewed) ends up valid for a scope broader than the signer intended — any PoX payout address, any amount, indefinitely — because the message that was actually signed and the map that gates re-use omit the very fields (`pox-addr`, `amount`, `reward-cycle`) that `pox-4` uses to keep authorizations narrowly scoped and single-use.

### Impact Explanation
A staker who signs one `grant-authorization` message for a `signer-manager` contract believing it authorizes that manager for a specific stacking arrangement in fact grants that contract-manager perpetual authority to register the signer key under `register-signer`/`register-self` for **any** PoX reward address and **any** locked amount, in any future reward cycle, without a further per-action signature from the staker. If the signer-manager contract is later compromised, upgraded maliciously, or was always adversarial, it can redirect the staker's future stacking rewards to an attacker-controlled PoX address, or lock amounts the staker never approved for a given cycle — a stacking action the staker never specifically authorised, which is explicitly in-scope impact ("an unsigned/un-scoped stacking action").

### Likelihood Explanation
The only precondition is that a staker signs a `grant-authorization` message once for a `signer-manager` contract (a normal onboarding step for this delegation feature). No admin, miner, or other privileged role is required — the caller of `grant-signer-key` is the `signer-manager` itself, which is exactly the untrusted third-party contract the grant is meant to constrain. Because the grant persists indefinitely and is not re-validated against pox-addr/amount/cycle on each use, likelihood of a mismatch between staker intent and eventual usage is high in any long-lived delegation relationship.

### Recommendation
Bind the `grant-signer-key` message hash (and the `signer-key-grants` map key) to the specific `pox-addr` (or an explicit `none` sentinel chosen by the signer, consistent with the existing comment), and consider adding `max-amount`/expiry (reward-cycle bound) fields analogous to `pox-4`'s `verify-signer-key-sig`, so a single signed grant cannot be silently reused for arbitrary reward addresses or amounts the staker never reviewed.

### Proof of Concept
1. Staker signs `get-signer-grant-message-hash(signer-manager, auth-id)` intending to authorize `signer-manager` to register them for a specific arrangement (in their mental model, tied to a specific pox-addr/amount they discussed off-chain).
2. `signer-manager` calls `grant-signer-key(signer-key, signer-manager, auth-id, signer-sig)`; this succeeds and sets `signer-key-grants {signer-key, signer-manager} = true` with no pox-addr/amount recorded [7](#0-6) .
3. At any later time, `signer-manager` (or its trait callback, if compromised/malicious) calls `register-signer` and subsequently drives stacking actions that use this same grant validated only via `verify-signer-key-grant(signer-manager, signer-key)`, which checks nothing about pox-addr/amount/cycle [6](#0-5) .
4. `signer-manager` picks an arbitrary PoX reward address and amount for the stacker's locked STX — a choice the staker never signed for — redirecting future BTC/sBTC rewards.

(define-public (grant-signer-key
        (signer-key (buff 33))
        (signer-manager principal)

                    (secp256k1-recover?

                    ERR_INVALID_SIGNATURE_RECOVER

;; Construct the message hash for validating a signer key grant. Unlike [get-signer-key-message-hash],
;; this message hash does not include `max-amount`, `period`, or `reward-cycle`. The topic is always `"grant-authorization"`.
;; The `pox-addr` field is optional. When `none`, it means the signer key can be used for any PoX address.
(define-read-only (get-signer-grant-message-hash
        (signer-manager principal)
        (auth-id uint)
    )
    (sha256 (concat SIP018_MSG_PREFIX
        (sha256 (unwrap-panic (to-consensus-buff? POX_5_SIGNER_DOMAIN)))
        (sha256 (unwrap-panic (to-consensus-buff? {
            topic: "grant-authorization",
            signer-manager: signer-manager,
            auth-id: auth-id,
        })))
    ))
)
