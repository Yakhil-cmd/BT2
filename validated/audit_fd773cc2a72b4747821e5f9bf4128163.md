### Title
Webhook signature verification key is chosen from an unverified payload field, letting an unauthenticated attacker forge events for stacks/teams belonging to a different organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects **which** GitHub App/`webhook_secret` to verify the HMAC signature against using a field taken directly from the unverified JSON body (`repository.owner.login` or `organization.login`). The handlers that actually act on the webhook (`Repository`/`Stack` lookup, team membership mutation, etc.) use a **different, independently attacker-controlled** field (`repository.full_name`, `team.id`, `member.login`). Because `GithubApp#verify_webhook_signature` short-circuits to `true` whenever the selected app has no `webhook_secret` configured, an attacker only needs one configured organization with a blank secret (an explicitly documented/valid configuration in this codebase) to make the controller skip verification entirely, while directing the payload's *effective* fields at a completely different organization's repository/team/stack.

### Finding Description
`verify_signature` picks the org used for verification purely from payload content, before the signature has been checked: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns the `GithubApp` configured for that specific org (multi-org configuration is a first-class, documented feature, e.g. `config/secrets.development.shopify.yml`, `config/secrets.development.example.yml`, each org independently configuring `webhook_secret`, defaulting to `nil`): [3](#0-2) 

`GithubApp#verify_webhook_signature` unconditionally passes verification when that org's secret is blank: [4](#0-3) 

Once `create` runs, the actual repository/stack/team that is mutated is resolved from an entirely different field, `repository.full_name` (for `PushHandler`, `StatusHandler`, etc.) or `organization.login`/`team.id`/`member.login` (for `MembershipHandler`) — none of which were part of the value used to pick the verification secret: [5](#0-4) [6](#0-5) 

This is the same class of bug as the reported Vow issue: a guard (`vat.dai(address(this)) == 0` / HMAC signature check) is evaluated against one piece of state, while the state actually acted upon by the privileged operation (`flop` debt / `repository.full_name`, `team.id`) is a different, attacker-controlled value never covered by the guard. Concretely, the binding that should hold is:

`organization used to select webhook_secret == organization/repository/team actually mutated by the handler`

Before this bug class is exploited, that equality trivially holds because both come from the same trusted, GitHub-signed payload. An attacker who controls `repository.owner.login`/`organization.login` independently from `repository.full_name`/`team.id`/`member.login` breaks the equality: they set the "selector" field to an org with `webhook_secret: nil` (bypassing verification) and set the "actor" fields to point at a victim org's team/repository.

### Impact Explanation
The `/webhooks` endpoint is public and unauthenticated by design (it must be reachable by GitHub); `WebhooksController` has no session or API-token requirement. If any organization in this Shipit deployment is configured with a blank `webhook_secret` (the documented default, `webhook_secret: # nil`), an unprivileged internet attacker can:
- Send a forged `membership` event with `organization.login` set to the org lacking a secret, but `team.id`/`member.login` pointing at a real team included in `Shipit.github_teams` and an existing Shipit `User`'s login, causing `MembershipHandler#process` to add that member to the privileged team — escalation into `Shipit.github_teams` authorization (`User#authorized?` checks membership in exactly this team set).
- Send forged `push`/`status`/`check_suite` events whose `repository.full_name` targets any stack, to make `Stack#sync_github` accept an attacker-chosen `expected_head_sha`, or forge passing CI/status/check-run state consumed by `MergeRequest#all_status_checks_passed?`, potentially enabling merges/deploys to proceed based on fabricated status.

This lands in the "High" bucket defined by the rules ("escalation into `Shipit.github_teams` authorization") and can chain toward the "Critical" bucket ("unauthorized deploy, rollback or merge") depending on downstream deploy/merge-queue configuration.

### Likelihood Explanation
Likelihood is contingent on deployment configuration: the vulnerability is only exploitable if at least one configured GitHub organization in `Shipit.github` has no `webhook_secret` set. This is not a corner case invented for the exercise — it is the shipped default in the engine's own example secrets files (`webhook_secret: # nil`) and is explicitly supported by the multi-org `Shipit.github(organization:)` lookup. Any operator who installs Shipit for multiple organizations and forgets (or is not prompted) to set a secret for one of them exposes every other configured stack/team to this cross-organization forgery, with zero credentials required by the attacker.

### Recommendation
- Do not let a payload-derived field decide the verification secret before the signature is verified. Verify the raw body's signature against every configured `webhook_secret` (or against the organization actually referenced by `repository.full_name`), and require all configured organizations to have a non-blank secret in production (fail closed instead of `return true unless webhook_secret`).
- Ensure `repository_owner` (verification selector) and `repository_name`/`team.id`/`member.login` (handler actor fields) are derived consistently from the same trusted sub-object once signature verification has succeeded, not from independently attacker-chosen paths in the JSON body.
- Reject webhooks outright when the resolved `GithubApp` has no `webhook_secret` configured rather than treating it as "verification passed."

### Proof of Concept
Preconditions: Shipit configured with two orgs, e.g. `orgA` (no `webhook_secret`) and `orgB` (has stacks/teams the attacker wants to affect).

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=anything   # ignored, orgA has no secret

{
  "action": "added",
  "organization": { "login": "orgA" },
  "team": { "id": <id_of_privileged_team_in_orgB>, "name": "...", "slug": "...", "url": "..." },
  "member": { "login": "attacker_shipit_login" }
}
```
`repository_owner` resolves to `orgA` → `Shipit.github(organization: "orgA").verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank) → `MembershipHandler#process` runs and adds `attacker_shipit_login` to the team identified by `team.id`, regardless of that team's real organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end
```
