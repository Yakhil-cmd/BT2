This confirms the vulnerability. `StacksController#stack` (the "correct" pattern) uses `stacks.from_param!(params[:id])` where `stacks` is scoped to `current_api_client.stack_id` when the client is stack-scoped: `app/controllers/shipit/api/base_controller.rb:74-80`. But `CCMenuController#stack` overrides this and bypasses the scoping entirely, calling `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table: `app/controllers/shipit/api/ccmenu_controller.rb:29-31`. Since `check_permissions!` in `app/models/shipit/api_client.rb:38-45` only checks the string `"read:stack"` is in the permissions array — with no reference to `stack_id` at all — a stack-scoped token with `read:stack` permission passes `require_permission :read, :stack` regardless of which stack is requested, and then `CCMenuController#show` fetches and renders whatever stack ID the attacker supplies in the URL.

### Title
Stack-scoped ApiClient token can read any stack's CCMenu deploy status via unscoped lookup - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuController` overrides the inherited `stack` helper with a version that looks up `Stack.from_param!(params[:stack_id])` directly, instead of using the stack-scoped `stacks` collection that `BaseController` and `StacksController` use. Combined with `require_permission :read, :stack` only checking a global boolean permission (not stack identity), any valid `ApiClient` token with `read:stack` permission — even one issued and scoped to a single, low-privilege stack — can read the CCMenu XML (build/deploy status) of any other stack on the instance by supplying its `stack_id`.

### Finding Description
The broken binding: `current_api_client.check_permissions!(:read, :stack)` (a global capability check) is treated as equivalent to "this client may read *this* stack" — but it is not, because it never consults `current_api_client.stack_id`.

Trace:
- `require_permission :read, :stack` (`app/controllers/shipit/api/ccmenu_controller.rb:6`) registers a `before_action` that calls `require_permission!` (`app/controllers/shipit/api/base_controller.rb:82-84`), which just runs `current_api_client.check_permissions!(:read, :stack)`.
- `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`) only checks `permissions.include?("read:stack")` — a flat string list with no notion of which stack the client is scoped to.
- The correct scoping mechanism exists in `BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-76`): `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `BaseController#stack` (`base_controller.rb:78-80`) uses `stacks.from_param!(...)`. `StacksController` inherits this correctly (`app/controllers/shipit/api/stacks_controller.rb:87-89`).
- `CCMenuController` overrides `stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) with `@stack ||= Stack.from_param!(params[:stack_id])`, bypassing the `stacks` scoping entirely and querying the full `Stack` table.

Exploit flow: attacker obtains any valid `ApiClient` token (e.g., one legitimately issued for their own repo's CCMenu badge, scoped via `stack_id` to their stack, with `read:stack` permission). They request `GET /api/1/ccmenu.xml?token=<their_token>&stack_id=<victim-repo-slug>`. `authenticate_api_client` succeeds; `require_permission!(:read, :stack)` passes because the check is not stack-aware; `#show` then calls `stack`, which resolves the victim's stack unconditionally, and renders its deploy status.

Existing guards do not catch this: `authenticate_api_client`, `require_permission!`, and `ApiClient` model validations all operate on the token/permission level only; none of them re-derive or check `stack_id` against `params[:stack_id]` in this controller's own `stack` method.

### Impact Explanation
Any token with `read:stack` permission (which is a common permission to grant, e.g., for CI badges) can enumerate and read the build/deploy status (branch, last build outcome, lock state, build time, web URL) of every stack on the Shipit instance, not just the one it was scoped to. This is an unauthenticated-for-other-tenants read of stack state — cross-tenant information disclosure that matches the "High - escalation into... unauthenticated read of stack state, task streams or deploy output" impact category. It is fully repeatable against arbitrary stacks by varying `stack_id`, and requires no additional privilege beyond possessing any single valid token.

### Likelihood Explanation
The attacker only needs one legitimate, low-privilege `ApiClient` token scoped to their own stack with `read:stack` permission — a normal configuration for CCMenu/CI-badge integrations that a repo owner could set up for themselves via the Shipit admin. From there, simply changing `stack_id` in the request query string exposes any other stack's data. No brute-forcing of `api_clients_secret` is required if the attacker legitimately holds any scoped token; the flaw is purely in the missing stack-identity check in `CCMenuController#stack`. This is low-cost and trivially repeatable.

### Recommendation
Change `CCMenuController#stack` to use the inherited, scope-aware `stacks` collection instead of the raw `Stack` model:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures a stack-scoped `ApiClient` (`current_api_client.stack_id` present) can only resolve its own stack, matching the behavior already used correctly in `StacksController`.
