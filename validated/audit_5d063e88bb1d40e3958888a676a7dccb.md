### Title
Signature verification key is selected using an unauthenticated payload field, decoupling the "organization that authenticated" from the "repository that is written" - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The reported bug class is: a payload field is acted upon (used to select accounting/behavior) but is not covered by the cryptographic check meant to bind it. In `WebhooksController`, the `X-Hub-Signature` HMAC is verified using a per-organization `webhook_secret`, but the organization used to select *which* secret to verify against is itself read out of the same untrusted, not-yet-verified JSON body (`repository.owner.login` / `organization.login`), before any signature check occurs.

### Finding Description
`WebhooksController#verify_signature` first extracts `repository_owner` directly from the raw JSON body, then fetches the `GitHubApp` (and its `webhook_secret`) for *that* organization, and only then verifies the signature over `request.raw_post` using that org's secret: [1](#0-0) [2](#0-1) 

Because Shipit supports multiple GitHub App configurations, each keyed by organization with its own independent `webhook_secret`, `Shipit.github(organization:)` resolves a *different* `GitHubApp`/secret per organization: [3](#0-2) 

The actual routing of the event to a `Stack`/`Repository` inside the handler layer is done later, independently, using `payload.dig('repository', 'full_name')`: [4](#0-3) 

The binding this design implicitly relies on is:
`organization that authenticated the signature == organization that owns the repository the handler writes to`

But nothing enforces this equality. An attacker who controls a GitHub organization that is *also* configured in Shipit (i.e., who can generate a validly-signed webhook using **their own org's `webhook_secret`**) fully controls the raw JSON body being signed, including `repository.full_name`. They can set `repository.full_name` to point at a *different* org/repo (any Stack's `Repository#from_github_repo_name` match) while keeping `repository.owner.login`/`organization.login` consistent with their own org so the signature check passes against their own secret. The HMAC does cover the raw body bytes, but it only proves "the party who knows secret X signed this JSON" — it does not, by itself, prove that secret X's org is authorized to emit events for the repository named inside that JSON, because that authorization link is never checked anywhere in the codebase; `repository_owner` (used to pick the secret) and `repository.full_name` (used to pick the target Stack) are two independent, attacker-controlled fields in the same signed body that are never cross-validated against each other or against the `Repository`'s actual configured organization.

### Impact Explanation
If exploitable, this allows an organization that legitimately holds one configured `webhook_secret` to forge events (`push`, `status`, `pull_request`, `check_suite`, `deployable_status`, `merge`, etc.) that are attributed to and processed against a completely different repository/stack that they do not own, e.g. triggering `GithubSyncJob` syncs, commit/status creation, or merge/deploy-adjacent state changes for someone else's Stack — an authorization boundary crossing between "org that authenticated" and "repository that is written," matching the High-impact class of "escalation into authorization" for stacks the attacker does not control.

### Likelihood Explanation
Exploitability is conditional on the deployment using the **multi-organization** GitHub App configuration (`github_default_organization` not nil) with more than one organization's secret configured, and on the attacker legitimately controlling one of those configured organizations/webhook secrets while a target `Repository`/`Stack` exists whose `full_name` they can forge into the payload. This is a real, code-visible gap (no cross-check exists between `repository_owner` used for secret selection and `repository.full_name` used for stack routing), but I could not fully verify from the available index whether `Repository.from_github_repo_name` or any surrounding model additionally re-validates the owning organization before dispatching handlers — this would need confirmation via a live/full-repo Devin session, since some file contents may be excluded from this index.

### Recommendation
In `WebhooksController#verify_signature`, after resolving the target `Stack`/`Repository` from `repository.full_name`, cross-check that the repository's actual configured/owning organization matches `repository_owner` (the value whose secret was used to verify the signature) before dispatching to handlers, rejecting the event otherwise.

### Proof of Concept
Not executable from the indexed context alone (requires a live multi-org Shipit deployment with two configured `webhook_secret`s and two GitHub-App-side orgs to demonstrate cross-organization forgery); the code path enabling it is cited above.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
