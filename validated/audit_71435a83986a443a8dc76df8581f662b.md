### Title
CCMenu API token is never scoped to its issuing stack, granting org-wide `read:stack` access to every stack - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` is supposed to mint a narrow, per-stack, read-only `ApiClient` token that a user embeds in an external CI status widget for one stack. The `ApiClient` model supports this via its optional `stack` association [1](#0-0) , and `Api::BaseController#stacks` enforces the scoping by restricting the visible stacks to `current_api_client.stack_id` when it is set [2](#0-1) . However the token-creation code never actually binds the client to the stack, and the CCMenu API controller that consumes the token bypasses the scoping helper entirely, so the token behaves as an unlimited, org-wide `read:stack` credential usable against any stack.

### Finding Description
`CCMenuUrlController#client` creates (or reuses) the `ApiClient` keyed only on `creator` and `name`, passing `stack:` nowhere: [3](#0-2) 

Because `stack:` is never supplied, the created `ApiClient.stack_id` is `nil`. In `Api::BaseController`, scoping to a single stack only happens when `current_api_client.stack_id?` is true: [2](#0-1) 

With `stack_id` nil, `stacks` resolves to `Stack.all`, so the token silently grants `read:stack` on every stack in the installation instead of just the one the user asked for. Compounding this, the `CCMenuController` used by the CCMenu XML endpoint doesn't even use the scoped `stack` helper from the base controller — it overrides it to look the stack up unscoped, directly by whatever `stack_id` is supplied in the request: [4](#0-3) 

`require_permission :read, :stack` only checks that `'read:stack'` is present in the `ApiClient#permissions` array via `check_permissions!` [5](#0-4) ; it performs no comparison between the token's intended stack and the stack named in the request. So even if `stack:` were fixed to be set at creation, the `CCMenuController#stack` override would still bypass the enforcement, since it never consults `stacks`/`stack_id` at all.

The binding that is broken: **the stack a token is authorised for (the single stack the user requested a CCMenu URL for) ≠ the stack the token actually touches (any `stack_id` param supplied to the CCMenu endpoint)**.

### Impact Explanation
CCMenu URLs are designed to be embedded in external, often publicly-visible build-status dashboards/radiators (that is the entire purpose of the CCMenu XML protocol). A user who generates such a URL for one stack — believing, per the UI/route design (`api_stack_ccmenu_url(stack_id: ...)`), that the embedded token is limited to that stack — is actually distributing a token that can read the build/deploy status (`lastBuildStatus`, `activity`, `lastBuildLabel`, lock status, etc.) of every stack managed by the Shipit instance, including stacks the token holder was never meant to see. Anyone who obtains this token (e.g., by viewing the embedding page's source, or via network capture on the semi-public dashboard) can enumerate and read the state of arbitrary stacks by simply changing the `stack_id` query/path parameter. This matches the High-impact category "unauthenticated read of stack state ... or deploy output" via escalation beyond the token's intended authorization scope.

### Likelihood Explanation
Likelihood is high: no privileged action beyond obtaining a legitimately-issued, low-privilege CCMenu token is required. The token is created automatically on every visit to the CCMenu settings page (`CCMenuUrlController#fetch`) and is meant to be shared/embedded by design, so exposure of the token to third parties is the expected/normal usage pattern of this feature, not an edge case. Exploitation only requires changing one URL parameter (`stack_id`).

### Recommendation
- In `CCMenuUrlController#client`, bind the created `ApiClient` to the current stack, e.g. pass `stack:` both into `create_with` and the `find_or_create_by!` lookup so distinct stacks get distinct, properly-scoped clients.
- In `Api::CCMenuController`, remove the `stack` override and use the inherited, scoped `stack` method from `Api::BaseController` (which respects `stacks`/`current_api_client.stack_id`), so a stack-scoped token cannot be redirected to a different `stack_id`.
- Consider having `require_permission!`/`check_permissions!` also validate that the requested stack matches the token's `stack_id` when one is set, so any future controller that forgets to use the scoped `stack` helper fails closed rather than open.

### Proof of Concept
1. As an authenticated user, visit the stack settings page for `stack A`, triggering `GET /stacks/A/ccmenu_url` → `CCMenuUrlController#fetch`, which creates (or reuses) an `ApiClient` named "CCMenu Client" for the user with `permissions: ['read:stack']` and **no `stack_id`** set [6](#0-5) .
2. The response contains `ccmenu_url` = `.../api/A/ccmenu?token=<TOKEN>`. The user embeds this in a public CI dashboard.
3. An attacker who obtains `<TOKEN>` (from the public dashboard/page source) sends `GET /api/B/ccmenu?token=<TOKEN>` for any other stack `B` in the installation.
4. `CCMenuController#authenticate_api_client` accepts the token (it is valid, signed by `Shipit.api_clients_secret`) [7](#0-6) ; `require_permission :read, :stack` passes because the token has `read:stack` [5](#0-4) ; `stack` is resolved unscoped via `Stack.from_param!(params[:stack_id])` [8](#0-7) , returning stack `B`'s data (build/deploy status) even though the token was only meant for stack `A`.
