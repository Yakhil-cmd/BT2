### Title
`instantiate` RPC/runtime-API dry-run returns a `CREATE1` address that diverges from the address used by the real transaction, due to unfixed nonce off-by-one - ([File: substrate/frame/revive/src/exec.rs])

### Summary
The bug reported on real-wagmi/zkSync is a case of "computed address ≠ actually used address," where an off-chain/dry-run computation of a deterministic contract address (`CREATE2`) does not match what the execution engine actually produces, leading to protocol misuse and possible fund loss when users send value/interact with the wrongly-predicted address. `pallet-revive` (the EVM-compatibility pallet in this polkadot-sdk fork) has a functionally identical bug in its own address-derivation code for `CREATE1`: the nonce used to derive the future contract address during a dry-run (e.g., `eth_estimateGas`/`eth_call`/state-call based instantiate simulation) differs from the nonce used during the real, dispatched transaction, so the two computed addresses diverge.

### Finding Description
`pallet-revive`'s `Stack::new`/frame-building code computes the address of a to-be-instantiated contract as follows: [1](#0-0) 

```rust
FrameArgs::Instantiate { sender, executable, salt, input_data } => {
    let deployer = T::AddressMapper::to_address(&sender);
    let account_nonce = <System<T>>::account_nonce(&sender);
    let address = if let Some(salt) = salt {
        address::create2(&deployer, executable.code(), input_data, salt)
    } else {
        use sp_runtime::Saturating;
        address::create1(
            &deployer,
            // the Nonce from the origin has been incremented pre-dispatch, so we
            // need to subtract 1 to get the nonce at the time of the call.
            if origin_is_caller {
                account_nonce.saturating_sub(1u32.into()).saturated_into()
            } else {
                account_nonce.saturated_into()
            },
        )
    };
```

The comment makes the assumption explicit: for a *real, dispatched extrinsic*, `frame_system`'s nonce has already been incremented pre-dispatch, so subtracting 1 recovers the nonce that Ethereum's `CREATE1` (RLP(sender, nonce)) formula expects: [2](#0-1) .

The project's own change history documents that this exact assumption breaks when the same code path is exercised through a dry-run/simulation context (e.g., a runtime-API/RPC call used to estimate gas or preview the address a future `instantiate` would receive), because in that context the nonce has **not** actually been incremented pre-dispatch, so subtracting 1 produces an address one nonce too low — different from the address that will actually be used once the real transaction is submitted: [3](#0-2) 

Critically, although this repository contains a prdoc (`prdoc/stable2506/pr_8504.prdoc`) describing a fix — introducing an `ExecContext` check so the nonce-adjustment only applies `if origin_is_caller && matches!(exec_context, ExecContext::Transaction)` — **that fix was never actually applied to the source**. A repo-wide search confirms `ExecContext` and the described conditional appear only in the prdoc file, not anywhere in `substrate/frame/revive/src/exec.rs` or elsewhere in the crate. The live code at `exec.rs:1204-1213` is still the unconditional, pre-fix version quoted above. This is a real, currently-present bug in the inspected snapshot, not a hypothetical or already-patched issue.

### Impact Explanation
`CREATE1`-style address prediction (no explicit `salt`) is a normal, unprivileged usage pattern: any Ethereum-compatible tool/dApp that wants to know in advance the address a contract-instantiation transaction will produce (to display it to a user, to pre-fund it, or to reference it in downstream logic before the deployment transaction is even mined) will call the dry-run/estimation path of `instantiate`. Because the dry-run computes the address with a nonce that is off by one relative to what the real transaction later uses, the address shown to the user during simulation is different from the address the contract actually lands at. Any value or state anchored to the "predicted" address (e.g. a user pre-funding a not-yet-existing contract account, matching an "auto-derive contract address" convention common in Ethereum tooling) will not match the real, deployed contract, and funds sent to the mismatched address are stranded exactly like the "fund lock" scenario described in the original report, plus general protocol-usability breakage for anyone relying on address prediction (wallets, factories, front-ends). This mirrors the audit's Medium classification: not an outright unauthorized-fund-theft primitive, but a deterministic-address-computation defect leading to unusable/mis-targeted flows and possible locked funds, reachable by any ordinary signed user with no privileged role.

### Likelihood Explanation
Likelihood is high for anyone who actually relies on the dry-run/estimation mechanism to predict a `CREATE1` address before submitting the real deployment transaction — this is a standard integration pattern for EVM-compatible chains. No attacker privilege, governance action, or malicious peer is required; it's simply a consequence of routine query→submit workflow. The bug is deterministic (not probabilistic) once the code path is hit under a non-transaction execution context with `origin_is_caller` true and no `salt` supplied.

### Recommendation
Apply the fix already documented (but not actually merged) in `prdoc/stable2506/pr_8504.prdoc`: gate the nonce-subtraction on the caller genuinely being in a real dispatched-transaction execution context (e.g., `if origin_is_caller && matches!(exec_context, ExecContext::Transaction)`), so dry-run/estimation code paths compute the `CREATE1` address with the nonce value that will actually be in effect once the transaction executes, guaranteeing that predicted and actual addresses always match. Add/restore a regression test analogous to the described `nonce_not_incremented_in_dry_run()` to lock in the behavior.

title: Fix generated address returned by Substrate RPC runtime call
doc:
- audience: Runtime Dev
  description: |-
    ## Description

    When dry-running a contract deployment through the runtime API, the returned address does not match the actual address that will be used when the transaction is submitted. This inconsistency occurs because the address derivation logic doesn't properly account for the difference between transaction execution and dry-run execution contexts.

    The issue stems from the `create1` address derivation logic in `exec.rs`:

    ```rust
    address::create1(
        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )
    ```

    The code correctly subtracts 1 from the account nonce during a transaction execution (because the nonce is incremented pre-dispatch), but doesn't account for execution context - whether it's a real transaction or a dry run through the RPC.

    ## Review Notes

    This PR adds a new condition to check for the `ExecContext` when calculating the nonce for address derivation:

    ```rust
    address::create1(
        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller && matches!(exec_context, ExecContext::Transaction) {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )
    ```

    A new test `nonce_not_incremented_in_dry_run()` has been added to verify the behavior.

    ## Before Fix

    - Dry-run contract deployment returns address derived with nonce N
    - Actual transaction deployment creates contract at address derived with nonce N-1
    - Result: Inconsistent addresses between simulation and actual execution

    ## After Fix

    - Dry-run and actual transaction deployments both create contracts at the same address
    - Result: Consistent contract addresses regardless of execution context
    - Added test case to verify nonce handling in different execution contexts

    This fix ensures that users can rely on the address returned by a dry run to match the actual address that will be used when the transaction is submitted.
```
