### Title
Webhook signature verification keyed on `repository.owner.login` while stack lookup uses unrelated `repository.full_name` allows cross-organization status/push spoofing - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')`. `Shipit::Webhooks::Handlers::Handler#repository_name`, used by every default handler (push, status, pull_request, check_suite) to look up the target `Repository`/`Stack`, instead reads `payload.dig('repository', 'full_name')`. These are two independently attacker-supplied fields of the same unauthenticated JSON body, and the code never checks that they refer to the same organization.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [6](#0-5) 

`GitHubApp#verify_webhook_signature` explicitly downgrades to no verification at all when the selected org has no `webhook_secret` configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [2](#0-1) 

Multi-org Shipit deployments are explicitly supported and documented, keyed by top-level organization name in `secrets.yml`, each with its own independent `webhook_secret` (which can be left blank per org, as shown in the example/dummy configs). [7](#0-6) [8](#0-7) 

Once the (possibly trivially-passing) signature check succeeds, the entire raw JSON payload is dispatched unmodified to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [9](#0-8) 

Every handler resolves the target repository/stack from a *different* payload field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Because `repository.owner.login` (used for authentication) and `repository.full_name` (used for the write target) live in the same freely-attacker-controlled JSON body and are never cross-validated, an attacker who controls (or is granted membership on) any organization configured in Shipit with no `webhook_secret` set can craft a payload where `repository.owner.login` names that unsecured org (so the signature check trivially passes via `return true unless webhook_secret`) while `repository.full_name` names a completely unrelated, protected repository/stack tracked under a different, properly-secured organization. The handler layer only ever consults `full_name`, so the forged event is applied to the victim stack.

This breaks exactly the binding "an organization that authenticated versus the repository that is written."

### Impact Explanation
The `status` webhook handler creates `CommitStatus` records directly from unauthenticated fields (`sha`, `state`, `context`, `target_url`, `description`) of the spoofed payload for the victim commit, as exercised in `test/controllers/webhooks_controller_test.rb`'s `:state create a Status for the specific commit` test. Shipit's continuous-deployment/merge-queue gating (`Commit#deployable?`, `DeploySpec#required_statuses`, `MergeRequest#reject_unless_mergeable!`) relies on these very `Status` records to decide whether a commit is safe to auto-deploy or auto-merge. [10](#0-9) [11](#0-10) 

By forging a "success" status for an arbitrary commit sha on a protected repository while authenticating as an unrelated, unsecured org, an unprivileged attacker can satisfy `ci.require`/merge-queue checks for a commit that never actually passed CI, leading continuous delivery to trigger an unauthorized deploy, or the merge queue to merge a PR that shouldn't be mergeable. This matches the Critical impact category "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Exploitability depends on at least one configured GitHub organization in the deployment lacking a `webhook_secret` — a configuration explicitly shown as valid/expected in the shipped example and dummy config files for multi-org setups, and reachable by anyone with knowledge of (or membership in) that org, without needing any Shipit session, API token, or the *target* org's `webhook_secret`. The `/webhooks` endpoint is unauthenticated by design (it's meant to receive GitHub webhooks), so the only barrier is knowing/controlling one under-secured configured org name and the full_name of the target repo, both often discoverable.

### Recommendation
Cross-validate that the payload's `repository.full_name` owner matches `repository_owner`/the organization whose secret verified the signature before dispatching to handlers, and reject the webhook if they diverge. Additionally, consider requiring `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), and/or bind webhook signature verification to the destination repository's configured org rather than an attacker-supplied field.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `unsecured-org` (no `webhook_secret`) and `victim-org` (has a `webhook_secret`, hosts a tracked `victim-org/protected-repo` stack with `ci.require: ['ci/build']`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "victim-org/protected-repo" },
  "sha": "<head sha of a malicious/untested commit>",
  "state": "success",
  "context": "ci/build",
  "target_url": "https://example.com",
  "description": "forged"
}
```
No valid `X-Hub-Signature` for `victim-org`'s secret is required, since `repository_owner` resolves to `unsecured-org`, whose `verify_webhook_signature` returns `true` unconditionally.
3. `Shipit::Webhooks::Handlers::StatusHandler` resolves the stack via `payload.dig('repository','full_name')` = `victim-org/protected-repo` and records the forged `success` status against that commit, satisfying `ci.require` and enabling an unauthorized deploy/merge.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
