### Title
Cross-Repository Commit Status Injection via Unbound Webhook Signature Scope - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook's signature using `repository_owner`, a field derived from the JSON body (`repository.owner.login`), but the handler that actually mutates state (`StatusHandler`) uses an entirely different, unbound field of the same body (`sha`) to select which DB rows to write to, with no scoping to the repository/organization whose secret validated the request.

### Finding Description
`WebhooksController#verify_signature` looks up `Shipit.github(organization: repository_owner)` and verifies the raw POST body's HMAC signature against that organization's configured `webhook_secret`: [1](#0-0) [2](#0-1) 

Because the shared webhook endpoint (`Shipit::WebhooksController#create`) serves every organization configured in the app, any GitHub organization admin who legitimately owns a webhook integration in Shipit knows their own `webhook_secret` and can send an arbitrary raw JSON body of their choosing, provided `repository.owner.login` in that body names their own org (so signature verification succeeds).

The `status` event handler, however, never checks `repository.owner.login`/`repository.full_name` at all — it resolves target rows purely by commit `sha`, globally across the entire `commits` table, and writes a new status record for any commit matching that sha, regardless of which stack/repository it belongs to: [3](#0-2) [4](#0-3) 

The equality that should hold but is broken: `organization authenticated by verify_signature == repository/stack actually written by the handler`. Before the attack, these coincide because GitHub itself generates and signs payloads reflecting the real event's repository. After the attack (attacker crafts an arbitrary body signed with their own org's secret but naming a `sha` belonging to a commit tracked under a different organization's stack), the two diverge: the org authenticated (attacker's own) is no longer the stack being written to (a victim stack).

`Commit#deployable?` and `Commit#blocked?` gate deploy eligibility on the aggregated `status` derived from these `statuses` rows, and `ci.require`/`ci.blocking` configured in `shipit.yml` rely on this same status data: [5](#0-4) 

An attacker controlling their own low-value Shipit-tracked organization can therefore forge a `success` status update for a commit sha they do not own, as long as that sha exists in the `commits` table for some other tracked stack (e.g., a shared/forked commit, a cherry-picked commit, or a commit whose SHA the attacker can predict/observe via the victim's public GitHub repo before it is pushed/synced). This satisfies required CI checks and can unblock/trigger deploy or merge-queue automation (`stack.schedule_merges`) for a stack the attacker has no legitimate access to: [6](#0-5) 

### Impact Explanation
This breaks the authentication↔authorization binding of the webhook signature: signature validity is scoped to "the org who owns this payload's repository," but the actual write target is unscoped. The consequence is a cross-repository write (forged CI status on a victim's commit) that can be leveraged to satisfy `ci.require` gating and drive an unauthorized deploy/merge decision on a stack the attacker does not control — matching the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires the attacker to already administer a legitimate webhook integration for some organization tracked by the same Shipit instance (i.e., they know one org's real `webhook_secret`) and to know/guess a target commit `sha` in a different tracked stack. Both preconditions are attacker-attainable without any elevated Shipit privilege (no Shipit session, ApiClient token, or GitHub App key required) — only knowledge of one org's webhook secret, which the org owner necessarily possesses to run this feature. This is a moderate-likelihood, high-impact issue because SHAs must be known/guessed and the attacker must already run an organization onboarded into the same Shipit instance.

### Recommendation
Bind the write scope to the authenticated organization: after resolving `repository_owner` for signature verification, every handler must additionally filter targeted commits/stacks by `repository_name`/`repository.owner.login` from the same verified payload (e.g., `StatusHandler` should scope `Commit.joins(:stack => :repository).where(sha: params.sha, repository: { owner: repository_owner })` instead of the current global `Commit.where(sha: params.sha)`), so that the identity verified by `verify_signature` is provably the same identity the handler is permitted to mutate.

### Proof of Concept
1. Attacker administers `org-attacker` on GitHub and has configured/knows its Shipit `webhook_secret` (standard integration setup, not privileged access to Shipit itself).
2. Attacker identifies a commit `sha` that exists in `Shipit::Commit` for a victim stack under `org-victim/repo` (e.g., because the commit is a common ancestor/fork commit, or was observed via GitHub's public API before Shipit synced it).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status` and body:
   ```json
   {
     "sha": "<victim-commit-sha>",
     "state": "success",
     "context": "ci/circleci",
     "repository": { "owner": { "login": "org-attacker" } }
   }
   ```
   signing the raw body with `org-attacker`'s `webhook_secret` as `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner = "org-attacker"`, fetches `org-attacker`'s app config, and successfully verifies the signature [1](#0-0) .
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which finds the victim's `Commit` purely `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a forged `success` status onto the victim's stack's commit [3](#0-2) .
6. This status feeds `stack.schedule_merges`/`Commit#deployable?` for `org-victim`'s stack, potentially satisfying `ci.require` and enabling deploy/merge automation the attacker never had rights to influence.
