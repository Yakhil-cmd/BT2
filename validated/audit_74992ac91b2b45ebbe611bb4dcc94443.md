### Title
Cross-repository status forgery drives `Stack#schedule_merges` on an unrelated stack via SHA-only commit lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the commit(s) to update purely by SHA (`Commit.where(sha: params.sha)`) with no verification that the SHA belongs to the repository that sent the webhook. Since git commit SHAs are content-addressed, an attacker who owns a public fork of `victim/repo` (or any repo that legitimately shares a commit with it) can send a signed `status` webhook from *their own* repository referencing that shared SHA, causing Shipit to write a forged `success`/`pending` status onto `victim/repo`'s `Commit` record and invoke `Stack#schedule_merges` on `victim/repo`'s stack.

### Finding Description
Binding claimed to hold: `commit.stack.repository.full_name` (the stack whose `schedule_merges` fires) `== payload.repository.full_name` (the repo whose CI actually produced the status event).

Trace:
- `StatusHandler#process` [1](#0-0)  does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. The `params` schema only declares `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` [2](#0-1)  — there is no repository field used to scope the lookup, and no filter on `stack_id`/`repository` is applied to the `Commit.where` query.
- `Commit#create_status_from_github!` → `add_status` runs the status write and, on a state transition, unconditionally calls `stack.schedule_merges if new_status.pending? || new_status.success?` [3](#0-2) , where `stack` is `self.stack` — i.e., whichever stack happens to own the `Commit` row matching the SHA, not the stack tied to the webhook's originating repository.
- Because `Commit` rows are looked up globally by `sha` across all stacks, two different repositories (e.g., `victim/repo` and `attacker/fork-of-repo`, or any two repos sharing common ancestry/cherry-picked commits) can each have a `Commit` row with the identical SHA under different `stack_id`s. A signed webhook from `attacker/fork-of-repo` referencing that shared SHA will update **all** matching `Commit` rows, including `victim/repo`'s, and trigger `victim/repo`'s stack's `schedule_merges`.

Existing guards do not close this gap: webhook signature verification (`verify_signature`/`GitHubApp#verify_webhook_signature`) only proves the payload was sent by GitHub for *some* repository configured with a matching secret (the attacker's own repo, which they legitimately control and can configure in Shipit) — it says nothing about whether the SHA in the payload belongs to that repository's history. `ExplicitParameters` for `StatusHandler` validates payload shape only, not repository/SHA ownership. No model validation ties `Commit.sha` uniqueness or lookup to `stack_id`/repository at the handler layer.

### Impact Explanation
A payload signed for `attacker/fork-of-repo` mutates `victim/repo`'s `Commit` status and triggers `victim/repo`'s `Stack#schedule_merges`, which processes the merge queue for a stack the attacker does not own or control. This is a cross-tenant write triggered by an unrelated repository's webhook — matching the Critical category "a payload for one repository mutating another's stack". Repeatable for any SHA shared between an attacker-controlled repo and a target repo (trivial for forks that share commit ancestry, or for any commit whose content attacker can reproduce byte-for-byte, since SHA1 is content-addressed).

### Likelihood Explanation
Preconditions: the attacker needs (a) a GitHub repository they control that is already configured as a Shipit stack (so their own webhook secret validates), and (b) a commit SHA shared with `victim/repo`'s own tracked commit history — trivially satisfied for a fork before divergence, or for any identical commit merged/cherry-picked into both repos. No Shipit credentials, sessions, or GitHub App keys are required; the attacker only pushes/points their own repo's `status` webhook (or triggers their own CI to post a status) referencing the shared SHA. This is low-cost and repeatable against any stack sharing history with attacker-controlled repos.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other handler resolving `Commit`/`Stack` purely by SHA, e.g. check-run handlers) by the webhook's `repository.full_name`, joining through `Stack`/`Repository` so only commits belonging to the stack whose repository actually sent the event are updated: e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: params.repository.owner.login, name: params.repository.name })`.

### Proof of Concept
Minitest plan (Mocha), no live GitHub required:
1. Create two stacks, `victim_stack` (repo `victim/repo`) and `attacker_stack` (repo `attacker/fork`), each with a `Commit` sharing the identical `sha` value (simulate content-addressed collision by setting the same `sha` on commits belonging to each stack).
2. `victim_commit = Shipit::Commit.create!(stack: victim_stack, sha: 'deadbeef'*5, ...)`; `attacker_commit = Shipit::Commit.create!(stack: attacker_stack, sha: 'deadbeef'*5, ...)`.
3. `Shipit::Stack.any_instance.expects(:schedule_merges).never` is too broad; instead stub precisely: `victim_stack.expects(:schedule_merges)` (Mocha expectation on the victim stack instance) while stubbing `attacker_stack.stubs(:schedule_merges)`.
4. Build a `status` webhook payload for repository `attacker/fork` with `sha: 'deadbeef'*5, state: 'success'`, and call `Shipit::Webhooks::Handlers::StatusHandler.new(...).call` (or drive it through `WebhooksController#status` equivalent) with that payload.
5. Assert the Mocha expectation on `victim_stack.schedule_merges` is satisfied, proving a webhook signed for `attacker/fork` triggered merge-queue processing on `victim/repo`'s stack.
6. Additionally assert `victim_commit.reload.status.state == 'success'` to show the victim's commit record was mutated by an unrelated repository's webhook.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
