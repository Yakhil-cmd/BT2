### Title
`is_valid_signed_package`/`validateSignedMessage` fallback path trusts a stale (revoked) address definition when `last_ball_unit` is omitted - (File: signed_message.js)

### Summary
`signed_message.validateSignedMessage()` has two verification modes selected purely by whether the attacker-controlled signed package includes a `last_ball_unit` field: a "network-aware" mode that looks up the address's *current, on-chain* definition via `storage.readDefinitionByAddress()`, and a fallback mode (no `last_ball_unit`) that only checks that the embedded definition hashes to the address, without ever consulting the chain for a definition update/rotation. This mirrors the CVE-2018-0501 class of bug: a fallback verification path silently drops a check that the primary path performs.

### Finding Description
`validateSignedMessage()` sets `bNetworkAware = ("last_ball_unit" in objSignedMessage)` [1](#0-0) . When `bNetworkAware` is true, `validateOrReadDefinition()` calls `storage.readDefinitionByAddress(conn, objAuthor.address, last_ball_mci, {...})`, which returns the address's *currently registered* definition on-chain if one exists, and explicitly rejects an embedded definition in that case ("should not include definition") [2](#0-1) .

When `last_ball_unit` is absent, the code takes the `else` branch instead: it requires `objAuthor.definition` to be present and only verifies `objectHash.getChash160(objAuthor.definition) === objAuthor.address` — it never queries `storage.readDefinitionByAddress` at all [3](#0-2) . Because ocore addresses can rotate their authoritative definition over time while keeping the same address (the address is only guaranteed to equal the *original* definition's chash; the chain tracks subsequent definition changes looked up via `readDefinitionByAddress`), an old/superseded definition (and its old signing key) still satisfies the fallback branch's only check.

This fallback is directly reachable from oscript: `is_valid_signed_package()` in the formula evaluator only performs its own `last_ball_unit` stability check `if (typeof signedPackage.last_ball_unit === 'string')` — if the field is simply omitted by the sender, that check is skipped entirely and `signed_message.validateSignedMessage()` is invoked with `bNetworkAware=false` [4](#0-3) . An untrusted AA trigger sender fully controls `trigger.data`, so they can freely omit `last_ball_unit` from an embedded signed package.

The `payment_channels.oscript` sample demonstrates the exact affected pattern: it authenticates a counterparty's off-chain state updates via `is_valid_signed_package(trigger.data.sentByPeer, $bFromB ? $addressA : $addressB)` for both the "start closing" and "fraud proof" cases [5](#0-4) [6](#0-5) .

### Impact Explanation
If a channel counterparty ever rotates the definition on their address (e.g., after suspecting key compromise, or as routine key hygiene) via ocore's definition-change mechanism, the old definition/key should no longer be authoritative. However, because `is_valid_signed_package` accepts signed packages lacking `last_ball_unit`, an attacker who has (or has previously had) access to the *old, revoked* private key can still forge a validly-accepted `signed_message` for that address. In the payment-channel AA this can be used to submit a stale/forged "sentByPeer" package claiming an incorrect `amount_spent`, directly manipulating channel balances and the fraud-proof send-all outcome — i.e., unauthorized fund movement / fund loss inside the AA. Any other AA relying on `is_valid_signed_package` for identity/authorization of a counterparty (private-payment counterparties, oracle-style off-chain attestations, etc.) is similarly affected. This is a concrete AA fund-loss/unauthorized-spending vector, not merely a denial-of-service.

### Likelihood Explanation
Exploitation requires the attacker to possess a private key that was valid for the target address at some point but is no longer the *current* authoritative definition (e.g., a revoked cosigner key, or a key from before a definition rotation). This is a realistic scenario for any long-lived AA-mediated relationship (payment channels, escrows) where key rotation is a normal security practice. The attacker does not need to be a hub, node, or privileged party — merely an unprivileged AA trigger sender who can omit one JSON field (`last_ball_unit`) from data they already fully control.

### Recommendation
Require `last_ball_unit` to always be present (reject `is_valid_signed_package` / `validateSignedMessage` calls that omit it), or, in the fallback branch of `validateOrReadDefinition()`, still consult `storage.readDefinitionByAddress()` (using the current/highest known stable MCI) to confirm the embedded definition matches the address's *current* on-chain definition rather than only checking the original chash-derived binding.

### Proof of Concept
1. Address `X` initially deploys with `definition_v1 = ["sig", {"pubkey": pub1}]`, so `address(X) = chash160(definition_v1)`.
2. `X` rotates to `definition_v2` (e.g., new pubkey) via ocore's on-chain definition-change mechanism; `readDefinitionByAddress(X, latest_mci)` now returns `definition_v2`.
3. An entity that still holds the private key for `pub1` (the revoked key) crafts a `signed_message`:
   ```json
   {
     "signed_message": { "channel": "<AA address>", "period": N, "amount_spent": 0 },
     "authors": [{
       "address": "X",
       "definition": ["sig", {"pubkey": "<pub1>"}],
       "authentifiers": { "r": "<sig with priv1>" }
     }]
   }
   ```
   Note: no `last_ball_unit` field.
4. Submits this as `trigger.data.sentByPeer` to the payment-channel AA (`test/samples/payment_channels.oscript`).
5. `is_valid_signed_package` skips the `last_ball_unit` stability check (absent) and calls `signed_message.validateSignedMessage`, which takes the fallback branch, verifies only `chash160(definition_v1) === X` (true, since `X`'s address was originally derived from `definition_v1`), and accepts the forged package as validly "signed by X" — even though `X`'s current authoritative definition is `definition_v2` and `pub1` should no longer count as an authorization for `X`.
