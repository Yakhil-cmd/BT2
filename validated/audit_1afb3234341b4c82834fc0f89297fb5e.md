### Title
Webhook signature verification is keyed on `repository.owner.login` while the acted-upon repository is taken from the unrelated `repository.full_name` field, allowing cross-organization stack injection - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization (and therefore the `webhook_secret` used to validate the HMAC) from `repository.owner.login` (or `organization.login`) in the *attacker-controlled* JSON body, then, once the signature check passes, hands the *entire same body* to the event handlers, which resolve the target `Stack`/`Repository` from a completely different field, `repository.full_name` (via `Repository.from_github_repo_name`). Because the HMAC only proves "this body was signed with organization X's secret," not "the `repository.full_name` in this body belongs to organization X," an attacker who legitimately owns a repository/organization configured with its own GitHub App (multi-org `secrets.github` config, e.g. `test/dummy/config/secrets_double_github_app.yml`) can self-sign a payload where `repository.owner.login` names their own org (so verification succeeds with a secret they know) while `repository.full_name` names a victim organization's repository, causing Shipit to process the webhook as if it originated from the victim's repository.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` is used only to select which configured GitHub App's `webhook_secret` verifies the HMAC, per `Shipit.github` / `github_app_config`, which supports multiple, independently-secreted organizations in `secrets.github`: [3](#0-2) 

The HMAC itself is computed over `request.raw_post` in `GitHubApp#verify_webhook_signature`: [4](#0-3) 

So a valid signature only proves that the raw body was produced by someone who knows the `webhook_secret` belonging to the organization named in `repository.owner.login`. It says nothing about the *other* repository field used downstream. Once `verify_signature` passes, `create` parses the same body and dispatches it to handlers unmodified: [5](#0-4) 

Handlers such as `Handler#stacks` resolve the affected repository from `repository.full_name`, not from `repository.owner.login`: [6](#0-5) 

`Repository.from_github_repo_name` then looks up any `Repository` record matching that name, with no cross-check against the organization/app whose secret validated the request: [7](#0-6) 

The binding that should hold is:
`organization whose secret authenticated the payload == organization owning the repository the handler acts on`

but the engine only enforces:
`repository.owner.login (used to pick secret) == repository.owner.login (echoed back)`

with `repository.full_name` (the field actually driving `Stack`/`Repository` lookups, commit creation, GithubSyncJob enqueuing, etc.) never checked against the authenticating organization at all. This is analogous to the audited `veGUAN.increaseStakeAndLock()` bug where the validated field (`lockedUntil`/derived duration) is not what the code actually needs to check for the operation being performed (adding stake) — here the validated/authenticating field (`repository.owner.login`) is disjoint from the field the handlers actually operate on (`repository.full_name`).

### Impact Explanation
An attacker who administers their own GitHub organization/App entry in Shipit's multi-org configuration (a legitimate, unprivileged use case supported by `secrets.github` per `test/dummy/config/secrets_double_github_app.yml`) knows that org's `webhook_secret`. They can craft and self-sign a webhook body where `repository.owner.login` is their own org but `repository.full_name` is set to a victim organization/repository tracked by the same Shipit instance. Passing the signature check, this forged event flows into handlers keyed off `full_name`, enabling cross-repository writes such as:
- Enqueuing `GithubSyncJob` for the victim's stack/branch, forcing synchronization of attacker-chosen SHAs into the victim's tracked repository state.
- Injecting fabricated commit statuses (`status` event) or check-suite refreshes against the victim's stack, which can influence "deployable" gating and unauthorized deploys.
This crosses the repository-write / unauthorized-deploy boundary using no privileged credential beyond an attacker's own legitimately-configured org secret.

### Likelihood Explanation
This requires a Shipit deployment using the multi-organization GitHub App configuration (supported and shipped as a first-class option, see `lib/shipit.rb#github_app_config` and the dummy fixture `secrets_double_github_app.yml`) where the attacker controls at least one of the configured organizations/repos (e.g., a public-repo contributor org, or an org intentionally onboarded with lower trust). Under that realistic multi-tenant setup, no additional privilege is needed beyond crafting an HTTP POST with a correctly computed HMAC using a secret the attacker legitimately possesses — likelihood is moderate-to-high wherever multi-org configs are used with differing trust levels.

### Recommendation
After verifying the signature, cross-validate that the resolved `repository_owner` (or `organization.login`) actually matches the owner segment of `repository.full_name` before dispatching to handlers, and reject the payload otherwise. Alternatively, bind the webhook secret lookup and the repository resolution to the same authenticated field, or restrict each configured GitHub App/organization to only accept webhooks whose `repository.full_name` is under that same organization's namespace.

### Proof of Concept
1. Deploy Shipit with a multi-org config similar to `test/dummy/config/secrets_double_github_app.yml`, with `OrgAttacker` and `OrgVictim` both configured, each having distinct `webhook_secret`s, and with a `Stack`/`Repository` tracked for `OrgVictim/victim-repo`.
2. As the owner of `OrgAttacker` (holder of `OrgAttacker`'s `webhook_secret`), build a `push` event JSON body:
   ```json
   {
     "repository": { "owner": { "login": "OrgAttacker" }, "full_name": "OrgVictim/victim-repo" },
     "after": "<attacker-chosen-sha>",
     "ref": "refs/heads/master"
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `OrgAttacker`'s known `webhook_secret` over the raw body, matching `GitHubApp#verify_webhook_signature`.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")` and successfully verifies the signature.
5. `create` dispatches the parsed body to `Shipit::Webhooks.for_event('push')`; the push handler resolves the stack via `repository.full_name == "OrgVictim/victim-repo"`, enqueuing `GithubSyncJob` against the victim's stack despite the request only ever being authenticated for `OrgAttacker`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
