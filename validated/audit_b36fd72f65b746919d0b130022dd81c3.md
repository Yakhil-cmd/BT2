### Title
Tokens transferred to the Controller can be permanently locked - (File: contracts/controller/src/lib.rs)

### Summary
The `Controller` can hold arbitrary token balances, but exposes no generic withdrawal or sweep mechanism to recover them. Funds sent directly to the controller, or sent during `flash_position` without being declared as collateral or a refund asset, remain under the controller address without an exit path.

### Finding Description
`Controller::flash_position` snapshots only the declared collateral and `refund_assets` balances before invoking the caller-selected receiver, then deposits only declared collateral deltas and refunds only declared refund deltas. [1](#0-0) 

The controller’s public strategy API documents that undeclared callback assets receive neither credit nor refunds and that no controller sweep endpoint exists. [2](#0-1) 

A direct token transfer to the controller is also accepted by the asset contract, and integration tests show pre-existing controller balances remaining unchanged through `flash_position`. [3](#0-2) 

### Impact Explanation
Any tokens held by the controller outside an operation’s declared balance-delta accounting are permanently frozen at the controller address. The sender cannot recover them, no unprivileged endpoint credits them to an account, and no administrative or governance endpoint sweeps them.

This causes permanent loss of accidentally transferred user funds and callback-delivered undeclared assets.

### Likelihood Explanation
The path is reachable by any token holder through a direct token `transfer` to the controller address. It can also occur through the permissionless `flash_position` flow when a receiver transfers an asset that was omitted from both `collaterals` and `refund_assets`.

No privileged access, oracle manipulation, or protocol failure is required.

### Recommendation
Add a restricted controller rescue function that transfers arbitrary residual token balances to governance or a configured treasury while excluding balances required by active operations.

Alternatively, make `flash_position` reject or automatically refund every positive controller balance delta not present in `collaterals`; this still would not recover unrelated direct donations, so a separate sweep function is preferable.

### Proof of Concept
1. An unprivileged user calls the token contract’s `transfer(user, controller, amount)` for any supported token.
2. The token balance of `Controller` increases by `amount`.
3. No controller entrypoint lets the user withdraw or associate that pre-existing balance with an account.
4. A later `Controller::flash_position(..., collaterals=[other_asset], refund_assets=[])` leaves the pre-existing balance untouched because only declared collateral and refund-asset deltas are processed. [4](#0-3) 
5. The transferred tokens remain locked on the controller indefinitely.

Refund assets must be unique, listed in the debt hub and account spoke, disjoint from collateral declarations, and bounded by the maximum supply-position count. Refund eligibility requires an active spoke and an existing listing; it does not check collateralizable, borrowable, paused or frozen flags. Only positive balance changes above pre-callback balances return to the caller. The debt token can be a refund asset, but refunding it does not repay the minted debt.
