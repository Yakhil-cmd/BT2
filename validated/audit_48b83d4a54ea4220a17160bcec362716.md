Confirmed: the index on commits is `[stack_id, sha]` (not a global unique constraint on `sha` alone), meaning identical shas can legitimately exist across many different stacks/repositories simultaneously. This confirms the shared-sha precondition is realistic (e.g., forked repositories, shared history) and that `StatusHandler#process`'s global `Commit.where(sha: params.sha)` lookup is unscoped by tenant, unlike every sibling handler that filters through `stacks` (which is derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`).

### Title
`StatusHandler#process` applies forged CI statuses to commits across unrelated repositories/stacks, enabling unauthorized continuous deployment - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Unlike every other webhook handler (`PushHandler`, the `PullRequest::*Handlers`), `Shipit::Webhooks::Handlers::StatusHandler#process` never scopes its lookup through the base `Handler#stacks` method, which restricts operations to stacks belonging to the repository named in the verified payload. Instead it runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` globally, so a legitimately-signed `status` webhook for one repository can create a `Status` on a `Commit` belonging to a completely different stack whenever the sha values collide (which is common and attacker-inducible via forks/shared history, since the DB only enforces uniqueness of `sha` per `[stack_id, sha]`, not globally).

### Finding Description
The binding claimed by the security model is:
`stacks_derived_from_verified_payload = Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` must equal (i.e. be a superset boundary for) `the set of stacks whose commits get mutated by the handler`.

Every other handler enforces this: e.g. `PushHandler#process` operates on `stacks.not_archived.where(branch:)` [1](#0-0) , and the `PullRequest` handlers resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any stack [2](#0-1) . The base class explicitly defines this scoping primitive: `stacks` = `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, `repository_name` = `payload.dig('repository', 'full_name')` [3](#0-2) .

`StatusHandler` breaks this pattern. Its param schema doesn't even require `:repository`; it only requires `:sha` and `:state` [4](#0-3) , and `process` looks up commits with no repository filter at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

`Commit` records are only unique per `[stack_id, sha]` (index `index_commits_on_stack_id_and_sha`), not globally unique on `sha` [6](#0-5) , so it's entirely legal for the same sha to exist attached to many stacks belonging to different repositories/tenants (e.g. via forks sharing git history, or any other route by which an identical commit object ends up recorded against two stacks).

`create_status_from_github!` calls `add_status` which creates the `Status` using the target commit's own `stack_id` (`statuses.replicate_from_github!(stack_id, github_status)` on `Commit#create_status_from_github!`) [7](#0-6) . `Status` then fires `after_commit :schedule_continuous_delivery` which calls `commit.schedule_continuous_delivery` [8](#0-7) , which in turn checks `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob.perform_later(stack)` [9](#0-8) . `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [10](#0-9) , so a forged `success` status flips it true for the victim's commit, and `Stack#next_expected_commit_to_deploy`/`trigger_continuous_delivery` will pick it up and deploy [11](#0-10) .

**Exploit flow:** the attacker owns a GitHub repository/org that is a known, configured tenant of the same Shipit host (satisfies `verify_signature`, which only checks that the payload's `repository.owner.login` matches a Shipit-known org's webhook secret — it never checks that the sha belongs to that repo) [12](#0-11) . The attacker sets a commit status to `success` on a commit in their own repository whose sha happens to also be recorded against the victim's stack (trivial when the attacker's repo is a fork sharing history with the victim's repo, or otherwise contains an identical commit object). GitHub sends a legitimately-signed `status` webhook. `StatusHandler#process` finds *all* `Commit` rows with that sha — including the victim's — and creates a `success` `Status` on the victim's commit, using the victim's `stack_id`, without ever checking that the payload's `repository.full_name` matches the victim stack's repository.

Existing guards do not stop this: `verify_signature` authenticates "a request from *some* known organization," not "a request authorized to mutate *this* stack" [13](#0-12) ; `drop_unhandled_event`/`check_if_ping` are irrelevant; the `ExplicitParameters` schema for `StatusHandler` has no `repository` requirement to even leverage for scoping [4](#0-3) ; there is no model validation preventing duplicate shas across stacks.

### Impact Explanation
A `Status` record with `state: success` gets written against a repository/stack that never authenticated the request, satisfying "a payload for one repository mutating another's stack, commit" and "an unauthorized deploy." If the victim stack has `continuous_deployment: true` (a normal, common configuration) and its next undeployed commit was merely `pending`/`failure` and otherwise unlocked/unblocked, this single forged webhook flips `Commit#deployable?` to true and triggers a real `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → deploy, running the victim's untested/blocked commit in production. This is repeatable against any stack whose commit sha the attacker can arrange to also exist in a repository they control (fork-sharing is the common, cheap case), and the blast radius spans every tenant/stack on a shared Shipit install where `Repository`/`Stack` records aren't otherwise segregated by sha. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task ... or an unauthorized deploy."

### Likelihood Explanation
Preconditions: (1) attacker controls a repository that is a recognized organization/tenant in the target Shipit install (so `verify_signature` passes using that org's legitimate webhook secret sent by GitHub itself — no Shipit secret needed by the attacker); (2) attacker can get a commit with a matching sha recorded in their own repo (trivially achieved for forks that share unmodified ancestor commits, or any workflow producing identical git commit objects); (3) the victim stack has `continuous_deployment: true` and an otherwise-eligible next commit. All of this is achievable by an unprivileged GitHub user with no Shipit session, API token, or app secrets — exactly the threat model in scope. Cost is a single GitHub status update on their own repo/commit.

### Recommendation
Scope `StatusHandler#process` through the same repository-derived `stacks` mechanism used by every other handler: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit` lookup to `commit.stack_id` values belonging to that repository's stacks (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or a join through `Commit.joins(:stack).where(sha: params.sha, stack: { repository_id: repository.id })`) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":status webhook only updates commits belonging to the payload's own repository" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_deployment: true)
  victim_commit = victim_stack.commits.create!(
    sha: 'deadbeef' * 5,
    author: shipit_users(:walrus),
    committer: shipit_users(:walrus),
    authored_at: Time.now,
    committed_at: Time.now,
    message: 'victim commit'
  )

  attacker_repo = shipit_repositories(:cyclimse) # a different, unrelated repository/tenant
  attacker_stack = attacker_repo.stacks.first
  # attacker's own commit shares the exact same sha as the victim's commit
  attacker_commit = attacker_stack.commits.create!(
    sha: victim_commit.sha,
    author: shipit_users(:walrus),
    committer: shipit_users(:walrus),
    authored_at: Time.now,
    committed_at: Time.now,
    message: 'attacker commit'
  )

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_repo.github_repo_name, 'owner' => { 'login' => attacker_repo.owner } }
  }.to_json

  assert_no_difference -> { victim_commit.statuses.count } do
    assert_difference -> { attacker_commit.statuses.count }, 1 do
      post :create, body:, as: :json
    end
  end

  refute_predicate victim_commit.reload, :deployable? # still false: no forged status applied
end
```
This asserts the binding as an explicit equality: statuses/deploy-eligibility for `victim_commit` (belonging to a stack under `victim_stack.repository`) must not change as a result of a webhook whose verified payload's `repository.full_name` resolves only to `attacker_repo`'s stacks. Under the current unscoped `Commit.where(sha: params.sha)` implementation, this assertion fails — the victim's commit statuses count changes and `deployable?` can flip to `true`, confirming the vulnerability.
