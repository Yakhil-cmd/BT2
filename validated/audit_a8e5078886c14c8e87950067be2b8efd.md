### Title
Missing zero-address validation on `creator` account in `initialize_with_permission` permanently freezes creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` accepts an arbitrary, unchecked `creator` account and stores its key as `pool_creator` in `PoolState` without any zero/foreign-address validation, analogous to the missing `guardian != address(0)` check in the reported Lido `DepositSecurityModule.addGuardian` bug. A caller can set `creator` to `Pubkey::default()` (Solana's zero-address equivalent) or any other address nobody controls the private key for, permanently bricking the pool's creator-fee claim path.

### Finding Description
In `InitializeWithPermission`, `creator` is declared as an `UncheckedAccount` with only a `/// CHECK: creator of pool` comment and no constraints validating it is non-zero, a signer, or otherwise controllable: [1](#0-0) 

This raw key is later written directly into pool state as the pool creator, with no validation: [2](#0-1) 

The two downstream instructions that rely on `pool_creator` are:
- `collect_creator_fee`, which requires the `creator` account to be a `Signer` matching `pool_state.load()?.pool_creator`: [3](#0-2) 
- `collect_creator_fee_permissionless`, which sends fees to an ATA whose `authority` is the unchecked `creator`/`pool_creator` value: [4](#0-3) [5](#0-4) 

If `creator` is set to `Pubkey::default()` (or any address with no known private key), no wallet can ever produce a valid signature matching `pool_creator`, so `collect_creator_fee` can never succeed. `collect_creator_fee_permissionless` still succeeds mechanically, but it deposits the accumulated creator fees into an associated token account owned by an address nobody controls — funds that can never be moved out again.

### Impact Explanation
Any creator fees accrued by the pool (enabled via `creator_fee_on` at pool init, per `pool_state.initialize`) become permanently frozen and unrecoverable once `pool_creator` is set to a zero/uncontrolled address. This is a permanent loss of funds for whatever share of fees is meant to go to the pool creator — the funds sit in an ATA that is functionally a black hole, matching the "permanent freezing of user/LP funds" impact bar.

### Likelihood Explanation
`initialize_with_permission` is in the explicitly in-scope set of pool-creation entry points. The `creator` field is fully attacker-controlled data supplied in the single instruction call; no additional validation, signature, or permission-check constrains its value to a real, controllable key. Any account holding a valid `Permission` PDA (the only gating on the instruction) can trigger this by simply passing `Pubkey::default()` as `creator`, making this trivially and deterministically reachable.

### Recommendation
Add an explicit non-zero (and ideally non-default-program) check on `creator` in `initialize_with_permission`, e.g.:
```rust
require!(ctx.accounts.creator.key() != Pubkey::default(), ErrorCode::InvalidCreator);
```
and consider requiring `creator` to either be a `Signer` or to be constrained to a known, funded token-account owner so fee distribution can always be completed.

### Proof of Concept
1. Attacker (or any account with a valid `Permission` PDA) calls `initialize_with_permission` with `creator = Pubkey::default()` and `creator_fee_on` enabled.
2. `pool_state.initialize(...)` stores `pool_creator = Pubkey::default()` with no validation, per `programs/cp-swap/src/instructions/initialize_with_permission.rs:357-372`.
3. Swaps against the pool accrue creator fees into the pool vaults as tracked by `PoolState`.
4. `collect_creator_fee` can never be called because no signer can match `pool_creator = Pubkey::default()` (`collect_creator_fee.rs:10-13`).
5. `collect_creator_fee_permissionless` can be called by anyone, but it moves the accrued fees into an ATA owned by `Pubkey::default()` (`collect_creator_fee_permissionless.rs:61-69`), from which they can never be withdrawn — permanently freezing those funds.
