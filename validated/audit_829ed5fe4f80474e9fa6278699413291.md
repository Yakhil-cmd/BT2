### Title
Cross-tenant `CommitStatus` mutation via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` and never scopes the query to the repository/stack that the incoming webhook belongs to, unlike every other handler that touches records (e.g. `PullRequestHandler` subclasses use `repository.review_stacks`/`stacks`). Because `sha` is not unique across the `commits` table when multiple Shipit-tracked repositories (e.g. a repo and its fork) share history, a status webhook legitimately signed for repository A can create/update a `CommitStatus` on a commit that belongs to repository B's stack.

### Finding Description
Binding under test: `Commit.where(sha: params.sha)` (current code) vs. `Commit.where(sha: params.sha, stack: stacks)` (the scoping every sibling handler applies through `Handler#stacks`).

- `Handler#stacks` resolves `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [1](#0-0) , and this is the pattern PR handlers rely on via `repository.review_stacks`/`stacks` to constrain effects to the webhook's own repository.
- `StatusHandler#process` bypasses this entirely: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . It never calls `stacks` or `repository_name`, so the query is not restricted to the stack owned by the repository that sent the webhook.
- `sha` alone does not identify a tenant: two different `Repository`/`Stack` records (e.g. an upstream repo and a fork onboarded separately into Shipit, or two repos that happened to import the same history) can each have a `Commit` row with the identical `sha` value, because git commit hashes are computed from content/history and are not scoped to a single GitHub repository.
- The attacker's path: they control (own or can push to) a fork/mirror repository A that is tracked as a Shipit `Repository`/`Stack`, and repository A shares one or more commits (identical `sha`) with victim repository B, also tracked in Shipit. The attacker triggers (or GitHub naturally emits) a `status` event for repository A referencing that shared `sha`, with attacker-controlled `state`, `description`, `target_url`, and `context` fields per the `params` schema [3](#0-2) . `Commit.where(sha:)` finds the row for both stacks and calls `create_status_from_github!` on all of them, writing the attacker-controlled status onto the victim's commit.
- Existing guards do not stop this: webhook signature verification only authenticates that the payload came from GitHub for the sender's own installation/repo — it does not, and cannot, bind the `sha` lookup to the sender's repository; that binding is supposed to happen inside the handler via `stacks`, which `StatusHandler` omits. The `ExplicitParameters` schema validates field types/presence only, not tenancy. `Repository.from_github_repo_name` and `Stack` validations constrain what a legitimate repository/stack look like, but do nothing once the handler ignores `stacks`.

### Impact Explanation
An attacker who controls any Shipit-tracked repository that shares commit history with another tenant's tracked repository can write a `CommitStatus` (state/description/target_url/context of their choosing) onto a commit belonging to a repository/stack they do not control. Commit statuses are used by Shipit to gate readiness/deployability of commits, so this is a cross-tenant record-mutation primitive that can influence another team's deploy pipeline, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable for every shared `sha` and for as many victim stacks as share that history.

### Likelihood Explanation
The attacker needs no Shipit privileges: they only need a repository they own/push to that is onboarded into the same Shipit instance and that shares git history (identical commit SHAs) with a victim repository also onboarded into that instance — a realistic scenario for forks, mirrors, or repos migrated/split from a common upstream. The webhook itself (`status` event) is standard GitHub behavior triggerable by pushing/CI on the attacker's own repo; no secrets are required beyond what any GitHub user already has for their own repository.

### Recommendation
Scope the lookup to the requesting repository's stacks, mirroring the rest of the handlers: `Commit.where(sha: params.sha, stack: stacks).each { |commit| commit.create_status_from_github!(params) }`, using the existing `Handler#stacks` helper.

### Proof of Concept
Two-part minitest under `test/models/webhooks/handlers/status_handler_test.rb` style (characterization only, not asserting the fix is present):

1. Setup: create `repository_a` and `repository_b` (different `owner`/`name`), a `stack` for each, and a `Commit` row with the same `sha` value under each stack (`commit_a.stack == stack_a`, `commit_b.stack == stack_b`, `commit_a.sha == commit_b.sha`).
2. Part 1 (current behavior): invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload_for(repository_a, sha: shared_sha, state: 'success'))` and assert `commit_b.reload.statuses` (or equivalent) now contains the attacker-supplied status — proving `Commit.where(sha: params.sha)` mutated a commit outside `repository_a`'s stack.
3. Part 2 (characterizing the missing filter): re-run the same scenario but replace the query in isolation with `Commit.where(sha: shared_sha, stack: stacks)` (e.g., via a test double/subclass or by asserting on the relation directly) and show that this scoped relation excludes `commit_b`, i.e. `Commit.where(sha: shared_sha, stack: stack_a).to_a == [commit_a]` and does not include `commit_b`. This demonstrates the binding `Commit.where(sha: params.sha) != Commit.where(sha: params.sha, stack: stacks)` and that the absence of the `stack: stacks` filter is the root cause of the cross-tenant write.
