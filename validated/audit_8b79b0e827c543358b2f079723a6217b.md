### Title
`pallet-psm` mint/redeem trust a frozen `decimals` snapshot that the external asset's own `Issuer` can invalidate post-registration via `Assets::set_metadata`, producing an `ld2sd_rate`-style stale conversion-rate exploit - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
The Solana report's root cause is that a cross-chain OFT/ONFT config caches a decimals-derived conversion rate (`ld2sd_rate`) once at initialization and never re-validates it against the mint's live decimals, so anyone who can later change the mint's real decimals can desynchronize the cached rate from reality and extract value. `pallet-psm` in this repo has the structurally identical pattern: it snapshots an external asset's `decimals` once in `add_external_asset` [1](#0-0)  and, as of the intentional change documented in `pr_13062.prdoc`, `mint`/`redeem` use only that frozen snapshot for their `external_to_internal`/`internal_to_external` scaling with no live-decimals check [2](#0-1) [3](#0-2) .

### Finding Description
`add_external_asset` reads the external asset's decimals from live metadata via `T::Fungibles::decimals(external_asset)` and stores it permanently in `ExternalAssetInfo.decimals` [1](#0-0) . Ownership/metadata authority over that asset in `pallet-assets` remains with whoever created it (the `Issuer`), not with PSM governance — `pallet-assets::set_metadata` is a normal, non-privileged, permissionless-asset-owner call [4](#0-3) [5](#0-4) .

`mint` and `redeem` never re-read live decimals; they pull `ext_decimals = external.decimals` and `internal_decimals = info.internal_decimals` straight from the stored snapshots and feed them into `external_to_internal`/`internal_to_external`, which apply a `10^diff` scaling factor as the economic conversion rate between the two assets [6](#0-5) [7](#0-6) . This is exactly the `ld2sd_rate` pattern: a decimals-derived scale factor computed once and trusted forever, even though the underlying asset's live decimals can diverge afterward.

The project's own test suite proves this is now the intended, exercised behavior after `pr_13062` deliberately removed the earlier `DecimalsMismatch` halt-guard from `pr_11819`: `mint_uses_snapshot_when_asset_decimals_drift` and `redeem_uses_snapshot_when_asset_decimals_drift` show that after the asset owner unilaterally calls `Assets::set_metadata` to change decimals post-registration, PSM keeps minting/redeeming using the **old** snapshot rate without error [8](#0-7) [9](#0-8) . The prdoc explicitly states this was a deliberate design choice ("Changes to live asset metadata no longer stop minting or alter the debt conversion rate") [10](#0-9) , meaning the maintainers consciously chose to keep using the stale conversion rate rather than treat drift as an error.

Meanwhile, other consumers of the same asset's metadata (e.g. the ERC-20 precompile view used by revive/EVM tooling) read **live** decimals directly from `Metadata` on every call, not a frozen snapshot [11](#0-10) . This creates the same "two views of the same asset disagree on its real precision" condition that the Solana report exploited between the OFT program's cached `ld2sd_rate` and the mint's actual live decimals.

### Impact Explanation
If PSM approves an external asset and that asset's `Issuer` later changes its `decimals` (a normal, unprivileged action available to any asset creator, not requiring PSM admin or root), every subsequent `mint`/`redeem` against that asset uses the wrong `10^diff` scaling factor relative to how every other consumer (wallets, DEXs, the ERC-20 precompile view) now interprets that asset's real value. This can be used to mint disproportionately large amounts of the internal pUSD-like asset for a small deposit, or redeem disproportionately large external-asset payouts for a small burn of internal debt — draining the PSM's reserve/debt ceiling, the same "arbitrage-like advantage" and mispriced-conversion outcome described in the Solana report's two example exploits.

### Likelihood Explanation
Reaching this requires only: (1) creating your own asset in `pallet-assets` (permissionless, deposit-only) with an initial decimals value, (2) getting it approved once as a PSM external asset (a normal governance action performed in good faith based on the decimals visible at approval time — the PSM admin is not colluding, they simply never re-check later), and (3) calling `set_metadata` again on your own asset to change its decimals — which is a routine, unprivileged capability of any asset `Issuer`. No stolen keys, no governance capture, no privileged role beyond owning the asset you yourself created is required.

### Recommendation
Either (a) re-read and validate live decimals against the stored snapshot at the top of `mint`/`redeem` and hard-fail with `DecimalsMismatch` (restoring and always enforcing the guard introduced in `pr_11819` rather than the loosened behavior from `pr_13062`), or (b) freeze the asset's metadata (e.g. lock decimals, or require the `Issuer` to be transferred to a system/PSM-controlled account with no `set_metadata` capability) as a precondition of `add_external_asset`, analogous to the Solana recommendation of rejecting mints with a mutable `MintCloseAuthority`/decimals-affecting authority and forcing the authority to `None`.

### Proof of Concept
This is a static-analysis-derived analog, not an executed PoC; I did not run an integration test against this repository. The reasoning is fully supported by cited code: the frozen decimals snapshot at `add_external_asset` [1](#0-0) , its unconditional reuse in `mint`/`redeem` with no live check [6](#0-5) [7](#0-6) , and the project's own passing tests demonstrating the drift is tolerated by design [8](#0-7) [9](#0-8) . I was unable to fully verify within available tool calls (a) whether `pallet-assets` blocks reuse of a fully-destroyed asset ID (a test named `asset_id_cannot_be_reused` exists, suggesting the "destroy-and-recreate-same-identity" variant from the original report may be blocked in this codebase — the PSM analog above instead uses the simpler and clearly-reachable "mutate decimals via `set_metadata` after approval" path, which does not require destroying/reusing an asset ID at all), and (b) the exact authorization requirements of `set_metadata`'s `Issuer` role across all asset configurations. A background Devin session with full repo/test-execution access would be needed to write and run a concrete `pallet-psm` integration test (create asset with decimals=2 → approve via `add_external_asset` → call `Assets::set_metadata` to change decimals to 18 → call `Psm::mint`/`redeem` → assert the resulting `PsmDebt`/balance deltas are computed with the stale decimals) to obtain execution-verified before/after state and quantify the exact loss.

	fn redeem_uses_snapshot_when_asset_decimals_drift() {
		new_test_ext().execute_with(|| {
			register_external_asset_with_weight(USDX_ASSET_ID, Permill::from_percent(100));
			set_zero_fees(USDX_ASSET_ID);

			// Mint first, then change decimals.
			assert_ok!(Psm::mint(
				RuntimeOrigin::signed(ALICE),
				INTERNAL_ASSET_ID,
				USDX_ASSET_ID,
				10_000 * USDX_UNIT,
				Permill::zero()
			));
			assert_ok!(Assets::set_metadata(
				RuntimeOrigin::signed(ALICE),
				USDX_ASSET_ID,
				b"USDX".to_vec(),
				b"USDX".to_vec(),
				4
			));

			let alice_usdx_before = get_asset_balance(USDX_ASSET_ID, ALICE);
			let alice_internal_before = get_asset_balance(INTERNAL_ASSET_ID, ALICE);
			let debt_before = PsmDebt::<Test>::get(INTERNAL_ASSET_ID, USDX_ASSET_ID);

			assert_ok!(Psm::redeem(
				RuntimeOrigin::signed(ALICE),
				INTERNAL_ASSET_ID,
				USDX_ASSET_ID,
				100 * INTERNAL_UNIT,
				Permill::zero()
			));

			assert_eq!(
				get_asset_balance(USDX_ASSET_ID, ALICE),
				alice_usdx_before + 100 * USDX_UNIT
			);
			assert_eq!(
				get_asset_balance(INTERNAL_ASSET_ID, ALICE),
				alice_internal_before - 100 * INTERNAL_UNIT
			);
			assert_eq!(
				PsmDebt::<Test>::get(INTERNAL_ASSET_ID, USDX_ASSET_ID),
				debt_before - 100 * INTERNAL_UNIT
			);
		});

	/// Execute the decimals call.
	fn decimals(
		asset_id: <Runtime as Config<Instance>>::AssetId,
		env: &mut impl Ext<T = Runtime>,
	) -> Result<Vec<u8>, Error> {
		env.charge(<Runtime as Config<Instance>>::WeightInfo::get_metadata())?;

		let metadata = pallet_assets::Pallet::<Runtime, Instance>::get_metadata(asset_id)
			.ok_or(Error::Revert(Revert { reason: "Metadata not found".into() }))?;

		Ok(IERC20::decimalsCall::abi_encode_returns(&metadata.decimals))
	}
