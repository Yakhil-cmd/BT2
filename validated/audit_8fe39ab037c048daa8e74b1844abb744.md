### Title
Missing `isRunning` Validation in Bridge Handle Transfer Functions — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The `isRunning` state variable in the ServiceChain bridge contracts is checked in all user-facing request functions but is never checked in the operator-facing handle functions (`handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer`). When the bridge owner stops the bridge via `setRunningStatus(false)`, operators can still execute handle transfers and move KAIA, ERC20, or ERC721 assets out of the bridge, bypassing the intended circuit breaker.

---

### Finding Description

`BridgeTransfer.sol` declares `bool public isRunning = true` and exposes `setRunningStatus(bool _status)` (owner-only) to toggle it. [1](#0-0) 

All three request-side internal functions enforce this flag:

- `_requestKLAYTransfer`: `require(isRunning, "stopped bridge")` [2](#0-1) 

- `_requestERC20Transfer`: `require(isRunning, "stopped bridge")` [3](#0-2) 

- `_requestERC721Transfer`: `require(isRunning, "stopped bridge")` [4](#0-3) 

However, the three handle-side public functions contain **no `isRunning` check**:

- `handleKLAYTransfer` — transfers KAIA to `_to` via `.call.value(_value)("")` [5](#0-4) 

- `handleERC20Transfer` — mints or transfers ERC20 tokens to `_to` [6](#0-5) 

- `handleERC721Transfer` — mints or transfers ERC721 tokens to `_to` [7](#0-6) 

This is the direct analog of the `isLpCreated` bug: `isRunning` is set in one function (`setRunningStatus`) but never validated in the functions that actually move assets out of the bridge.

---

### Impact Explanation

When the bridge owner calls `setRunningStatus(false)` — for example, in response to a security incident, a bug in the counterpart chain, or an emergency pause — the intent is to halt all bridge asset movement. However, because `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` do not check `isRunning`, bridge operators can still:

1. Call `handleKLAYTransfer` to send KAIA from the bridge contract to any `_to` address.
2. Call `handleERC20Transfer` to mint or transfer ERC20 tokens to any `_to` address.
3. Call `handleERC721Transfer` to mint or transfer ERC721 tokens to any `_to` address.

This constitutes an unauthorized transfer of KAIA and bridged assets from a contract that is supposed to be stopped. The `_voteValueTransfer` mechanism requires operator consensus, but the operator threshold can be set to 1 (as demonstrated in tests), meaning a single operator can execute a handle transfer unilaterally. [8](#0-7) 

---

### Likelihood Explanation

**Medium.** The trigger requires a bridge operator (semi-trusted role) to call a handle function while `isRunning == false`. The operator threshold can be 1, so a single operator suffices. The scenario is realistic: the bridge is stopped due to a security incident, and a compromised or malicious operator exploits the window to drain assets before the incident is fully contained. The Go-layer `BridgeInfo.handleRequestValueTransferEvent` calls these handle functions automatically when processing pending events, and does not check `isRunning` before dispatching. [9](#0-8) 

---

### Recommendation

Add an `isRunning` guard to all three handle functions, consistent with the request-side pattern:

```solidity
// In handleKLAYTransfer, handleERC20Transfer, handleERC721Transfer:
require(isRunning, "stopped bridge");
```

Alternatively, introduce a shared modifier in `BridgeTransfer`:

```solidity
modifier onlyRunning() {
    require(isRunning, "stopped bridge");
    _;
}
```

and apply it to all six transfer entry points (both request and handle sides).

---

### Proof of Concept

1. Deploy the `Bridge` contract (inherits `BridgeTransferKLAY`, `BridgeTransferERC20`, `BridgeTransferERC721`). Fund it with KAIA via `chargeWithoutEvent`.
2. Owner calls `start(false)` → `isRunning = false`. Any call to `requestKLAYTransfer` now reverts with `"stopped bridge"`.
3. Operator (threshold = 1) calls `handleKLAYTransfer(txHash, from, attackerAddress, bridgeBalance, nonce, blockNum, "")`.
4. The function passes `_lowerHandleNonceCheck`, passes `_voteValueTransfer` (threshold met), and executes `_to.call.value(_value)("")` — transferring the full KAIA balance to `attackerAddress`.
5. The bridge is drained despite `isRunning == false`.

The existing test suite confirms `handleKLAYTransfer` succeeds with a single owner/operator and no `isRunning` check: [10](#0-9) 

The "stopped bridge" test only covers the request path (`fallback`), not the handle path, confirming the gap is untested.

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}
