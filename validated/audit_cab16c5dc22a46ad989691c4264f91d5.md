Confirmed: `generateQueriesToVoidJoint` in `archiving.js` explicitly deletes `inputs` rows (`DELETE FROM inputs WHERE unit=?`) for a unit being voided (final-bad, non-serial loser), while keeping the unit's row itself.

### Title
Capped-asset re-issuance after voiding a nonserial "issue" unit enables asset supply inflation - (File: aa_composer.js)

### Summary
The ShopXO advisory describes a missing "already initialized" guard that lets an attacker re-run a one-time critical action (install) via `app/install/controller/Index.php`. The analogous flaw in ocore is a missing "already issued and cannot be undone" guard for capped-asset issuance by an AA: the "already issued" check only looks for a live row in the `inputs` table, and that row is deleted whenever the issuing unit becomes non-serial (`final-bad`) and gets voided/pruned. This lets the capped asset be issued again, breaking the fixed-supply invariant the asset's `cap` field is supposed to guarantee.

### Finding Description
When an autonomous agent issues a capped asset, `aa_composer.js`'s `issueAsset()` guards against double issuance solely with: [1](#0-0) 
This query checks only for the *existence* of any `issue` input row for the asset — it does not check `sequence='good'`, stability, or whether the issuing unit was later voided. The non-AA counterpart in `inputs.js` has the identical pattern: [2](#0-1) 

Separately, when a unit loses the serial race and becomes non-serial (`final-bad`), the archiving/pruning code strips its content while keeping the unit shell, and explicitly removes its `inputs` rows: [3](#0-2) 

Because the capped-asset "already issued" check is a raw existence check against `inputs`, and voided/final-bad units have their `inputs` rows deleted by `generateQueriesToVoidJoint`, a capped asset's issuing unit that is later ruled non-serial (e.g., because it lost a fork/double-spend race for the issuing address, or is otherwise voided as final-bad) leaves no trace in `inputs`. The AA (or, symmetrically, any address issuing a capped asset through a normal wallet payment via `pickDivisibleCoinsForAmount`/`issueAsset` in `inputs.js`) is then free to issue the same capped asset again, since `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` returns no rows.

This differs from the normal double-spend protection used elsewhere for payment inputs, which explicitly checks `main_chain_index`, `sequence`, and graph inclusion via `checkForDoublespends()`/`findConflictingUnits()` in `validation.js` before deciding whether a competing spend is legitimate: [4](#0-3) 
The issue-input check has no equivalent temporal/graph-aware logic — it's a flat existence check, and that existence can be erased by pruning.

### Impact Explanation
A capped asset (`objAsset.cap`) is defined once with a fixed total supply. The `issue` input type is meant to mint that supply exactly once (`serial_number` fixed to `1` for capped assets, per `validation.js:2321-2324`). If the sole guard against re-minting can be defeated by causing the original issuing unit to become non-serial and pruned, an attacker (the asset definer / AA owner, who is an unprivileged actor with respect to consensus rules and reachable via the AA trigger/unit-posting path) can mint the capped supply a second time, directly inflating the asset's supply beyond its documented cap. This is a concrete supply-inflation impact.

### Likelihood Explanation
Exploitation requires engineering a race so that the first `issue` unit for the capped asset ends up non-serial/`final-bad` and is voided/pruned (e.g., by causing two conflicting definer-address units to compete, with the loser voided), then issuing again from the same address. This requires understanding of ocore's serial/non-serial resolution and pruning timing, but does not require any special network privilege — an ordinary unit poster or AA author fully controls the issuing address and can post the conflicting units needed to trigger this sequence. This makes it a realistic, if not trivial, unprivileged attack path.

### Recommendation
Change the "already issued" check for capped assets to be sequence/stability-aware (mirroring `checkForDoublespends`), or record capped-asset issuance state in a way that survives pruning of the issuing unit (e.g., a separate `assets` table flag set once issuance is confirmed stable, rather than relying on the presence of a row in `inputs` that can be deleted on voiding). At minimum, `generateQueriesToVoidJoint`/`generateQueriesToRemoveJoint` should not silently remove the historical fact that a capped asset was already issued.

### Proof of Concept
1. Definer address `D` defines asset `A` with `cap=100`.
2. `D` posts unit `U1` containing `payment` message with `input.type='issue', amount=100, serial_number=1` for asset `A`. `SELECT 1 FROM inputs WHERE type='issue' AND asset='A'` now returns 1 row.
3. Before `U1` stabilizes, `D` posts a conflicting unit `U2` from the same address using the same parents/short-lived nonserial construction that ends up winning the serial race, causing `U1` to resolve as non-serial (`final-bad`).
4. Once `U1` is archived/voided, `generateQueriesToVoidJoint` runs `DELETE FROM inputs WHERE unit=U1`, removing the only evidence that asset `A` was ever issued.
5. `D` posts a new unit `U3` with another `issue` input for asset `A`, amount 100, serial_number 1. The guard query now returns 0 rows, so `addIssueInput(1)` succeeds, and asset `A`'s total supply becomes 200 despite `cap=100`.

	conn.query(
		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
					graph.determineIfIncludedOrEqual(conn, objConflictingRecord.unit, objUnit.parent_units, function(bIncluded){
						if (bIncluded){
							var error = objUnit.unit+": conflicting "+type+" in inner unit "+objConflictingRecord.unit;

							// too young (serial or nonserial)
							if (objConflictingRecord.main_chain_index > objValidationState.last_ball_mci || objConflictingRecord.main_chain_index === null)
								return cb2(error);

							// in good sequence (final state); final-bad is excluded by the query and treated as non-existent
							if (objConflictingRecord.sequence === 'good')
								return cb2(error);

							throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);
						}

								throw Error("double spending "+type+" without double spending address?");
							cb2();
						}
					});
				},
				function(err){
					if (err)
						return cb(err);
					onAcceptedDoublespends(cb);
				}
			);
		}
	);
}
