### Title
Zero `_requestedBlockNumber` in Bridge Handle Functions Permanently Corrupts `lowerHandleNonce` and Breaks VTR Recovery — (`contracts/service_chain/bridge/BridgeTransfer.sol`)

---

### Summary

`handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` accept `_requestedBlockNumber = 0` without validation. The `_updateHandleNonce` loop and the off-chain `isHandledEvent` check both use `handleNoncesToBlockNums[nonce] > 0` as the sentinel for "this nonce was handled." A zero block number breaks that sentinel, permanently freezing `lowerHandleNonce`, stalling `recoveryBlockNumber` at its initial value of `1`, and causing the Value Transfer Recovery (VTR) system to misclassify the nonce as unhandled on every recovery cycle.

---

### Finding Description

**Root cause — missing zero-check on `_requestedBlockNumber`:**

In all three handle functions the pattern is identical:

```solidity
// BridgeTransferKLAY.sol line 83-84
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
```

No guard requires `_requestedBlockNumber > 0`. [1](#0-0) 

**Broken sentinel in `_updateHandleNonce`:**

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    delete handleNoncesToBlockNums[i];
    delete closedValueTransferVotes[i];
}
lowerHandleNonce = i;
```

The loop advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0`. If any nonce `N` is stored with block number `0`, the loop halts at `N` on every future call, `lowerHandleNonce` is frozen at `N`, and `recoveryBlockNumber` never advances. [2](#0-1) 

**Broken sentinel in the off-chain VTR recovery:**

```go
func isHandledEvent(to *BridgeInfo, ev IRequestValueTransferEvent) bool {
    blk, err := to.bridge.HandleNoncesToBlockNums(nil, ev.GetRequestNonce())
    if err == nil && blk > 0 {
        return true   // only skips if block number > 0
    }
    return false      // returns false for a handled nonce with blkNum == 0
}
```

`isHandledEvent` returns `false` for the poisoned nonce, so the VTR recovery loop re-queues it as a pending event on every recovery interval. [3](#0-2) 

The recovery loop then calls `handleRequestValueTransferEvent`, which calls `HandleKLAYTransfer` again. That call hits `_voteValueTransfer`, which reverts with `"closed vote"` because `closedValueTransferVotes[N]` is still `true` (the cleanup `delete closedValueTransferVotes[i]` inside the loop was never reached). The re-handle fails, but the VTR system keeps retrying indefinitely. [4](#0-3) 

The normal bridge manager path passes `ev.GetRaw().BlockNumber` (always ≥ 1 for a real on-chain event), so the bug is not triggered by the automated relay. It is triggered by a bridge operator calling the contract directly with `_requestedBlockNumber = 0`. [5](#0-4) 

---

### Impact Explanation

| Corrupted value | Effect |
|---|---|
| `handleNoncesToBlockNums[N] = 0` | Sentinel broken; loop halts at `N` forever |
| `lowerHandleNonce` frozen at `N` | All nonces ≥ `N` accumulate in `handleNoncesToBlockNums` and `closedValueTransferVotes` without cleanup (unbounded storage growth) |
| `recoveryBlockNumber` frozen at `1` | VTR recovery always scans from block 1, re-processing the entire bridge history on every interval |
| `isHandledEvent` false-negative | VTR re-queues the poisoned nonce as pending on every cycle; each attempt reverts with `"closed vote"`, consuming operator gas and blocking the recovery pipeline |

The concrete protected-state impact is **persistent corruption of the bridge's nonce-accounting state** (`lowerHandleNonce`, `recoveryBlockNumber`) and **permanent disruption of the VTR recovery system**, which is the mechanism that re-handles missed cross-chain transfers. Legitimate missed transfers that arrive after the corruption may not be recovered, causing users to lose bridged assets.

---

### Likelihood Explanation

Trigger requires a registered bridge operator to call `handleKLAYTransfer` (or the ERC-20/ERC-721 variants) directly with `_requestedBlockNumber = 0`. Bridge operators are semi-trusted: they are not the owner, but they are a small, known set. A single compromised or malicious operator with threshold = 1 (the default) can trigger this unilaterally. The existing test suite already exercises `_requestedNonce = 0` with a non-zero block number, confirming the code path is reachable; the zero-block-number variant is not tested or rejected. [6](#0-5) 

---

### Recommendation

Add a non-zero block number guard in all three handle functions, mirroring the existing `_lowerHandleNonceCheck`:

```solidity
// In BridgeTransfer.sol or as a shared internal helper
function _requestedBlockNumberCheck(uint64 _requestedBlockNumber) internal pure {
    require(_requestedBlockNumber > 0, "zero block number");
}
```

Call it at the top of `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer`, before `_voteValueTransfer`. This ensures `handleNoncesToBlockNums[nonce]` is always non-zero for any successfully handled nonce, preserving the sentinel invariant relied upon by both `_updateHandleNonce` and `isHandledEvent`.

---

### Proof of Concept

1. Deploy bridge with operator threshold = 1.
2. Operator calls `handleKLAYTransfer(txHash, from, to, value, 0, 0, "")` — note `_requestedBlockNumber = 0`.
3. Transfer executes (KLAY sent), `closedValueTransferVotes[0] = true`, `handleNoncesToBlockNums[0] = 0`.
4. `_updateHandleNonce(0)`: loop checks `handleNoncesToBlockNums[0] > 0` → false; loop body never runs; `lowerHandleNonce` stays at `0`; `recoveryBlockNumber` stays at `1`.
5. Handle nonces 1, 2, … with valid block numbers. `_updateHandleNonce` is called each time but the loop still halts at `i = 0` because `handleNoncesToBlockNums[0] = 0`. `lowerHandleNonce` remains `0` forever.
6. VTR recovery calls `isHandledEvent` for nonce 0: `HandleNoncesToBlockNums(nil, 0)` returns `0`; `0 > 0` is false; returns `false`. VTR re-queues nonce 0 as pending.
7. VTR calls `HandleKLAYTransfer` for nonce 0 again; `_voteValueTransfer` reverts with `"closed vote"`. Recovery loop logs error and retries on next interval — indefinitely.

The existing test at `contracts/test/Bridge/bridge.test.ts` line 807 already shows `lowerHandleNonce() == 0` when nonce 0 is unhandled while nonces 1–205 are handled; the same freeze occurs permanently when nonce 0 is handled with block number 0. [7](#0-6)
