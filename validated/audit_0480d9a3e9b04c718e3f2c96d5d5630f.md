### Title
`roll-sbtc` credits `total-sbtc-staked` by the nominal transfer amount without verifying the sBTC actually received - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`roll-sbtc`, the private helper used by `register-for-bond`/bond-rollover paths to move a staker's custodied sBTC, increases the `total-sbtc-staked` accounting variable by the full nominal `delta` it asked the `sbtc-token` contract to transfer in, without ever checking that the contract's real sBTC balance grew by that same amount.

### Finding Description
When a staker increases their bond commitment, `roll-sbtc` computes `delta = new-sbtc - old-sbtc`, calls `sbtc-token transfer delta tx-sender current-contract none`, and then unconditionally does `(var-set total-sbtc-staked (+ (var-get total-sbtc-staked) delta))`: [1](#0-0) 

This mirrors the reported bug class exactly: the code assumes `amount requested to transfer == amount actually credited to the recipient`. In the original report this assumption broke for fee-on-transfer ERC20 tokens; here it breaks for any `sbtc-token` implementation whose `transfer` does not deliver the full nominal amount to the contract (e.g., a future fee, rounding, or partial-transfer semantics on the trait implementation). Because `pox-5.clar` treats `sbtc-token` as an external, upgradeable trait call (`'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token`) rather than verifying the resulting balance delta, `total-sbtc-staked` can become permanently larger than the sBTC actually custodied by the `pox-5` contract.

By contrast, the decrease branch of the same function moves funds *out* under an explicit `with-ft` post-condition via `as-contract?`, which at least bounds the outbound side, but there is no equivalent balance verification protecting the inbound accounting invariant (`total-sbtc-staked <= actual contract sBTC balance`): [2](#0-1) 

The initial (non-rollover) case shares the same code path, since `register-for-bond` calls `roll-sbtc` with `old-sbtc` of `u0`, transferring and crediting the full amount the same unverified way, per the function's own doc comment: "A registration with no rollover passes `old-sbtc` of `u0`, which transfers the full amount." [3](#0-2) 

### Impact Explanation
`total-sbtc-staked` and the staker/bond share bookkeeping (`staker-shares-staked-for-cycle`, bond min-ratio checks, and reward distribution which nets rewards against staked sats vs. the contract's actual sBTC balance) all rely on the equality "recorded staked sats == sBTC physically custodied by `pox-5`." If that equality is broken upward (recorded > actual), the contract's collateralization becomes overstated relative to reality: later `unstake-sbtc`/reward payouts can be under-collateralized, meaning some stakers may be unable to fully recover their custodied sBTC (temporary or permanent freezing of staked sBTC), and the reward-pool calculation (which subtracts the staked total from the raw balance to determine distributable rewards) would misallocate real, distributable sBTC as phantom "staked" balance, effectively freezing/double-counting a commitment beyond what was actually locked.

### Likelihood Explanation
Likelihood is low-to-moderate and conditional: `sbtc-token` is presently a well-known, non-fee, 1:1 pegged FT, so the bug is dormant under current conditions. It becomes live only if the `sbtc-token`/wrapping contract's `transfer` behavior is upgraded or ever deviates from delivering the exact nominal amount (analogous to how USDT could add a fee post-deployment, as the original report and the C4 judge both note). Because `pox-5` hard-codes the `sbtc-token` principal and cannot control that contract's future logic, this is an externally-triggerable risk that `pox-5`'s own accounting code fails to defend against.

### Recommendation
Verify the actual balance delta after calling `sbtc-token transfer` in `roll-sbtc` (and in the initial registration path) rather than trusting the requested `delta`: snapshot `get-balance current-contract` before and after the transfer, and credit `total-sbtc-staked` with the observed difference (or `asserts!` that it equals `delta`, reverting otherwise) so that on-chain bookkeeping can never drift ahead of the sBTC actually held in custody.

### Proof of Concept
1. Assume (or simulate via a mock/updated `sbtc-token`) that `sbtc-token`'s `transfer` function delivers `delta - fee` to the recipient instead of the full `delta` (e.g., a hypothetical future fee-on-transfer upgrade).
2. Staker calls `register-for-bond` (or a bond upgrade path) requesting `new-sbtc = 1_000_000` sats with `old-sbtc = 0`.
3. `roll-sbtc` calls `sbtc-token transfer 1_000_000 tx-sender current-contract none`; the token only credits `pox-5` with `999_000` sats due to the fee.
4. `roll-sbtc` still executes `(var-set total-sbtc-staked (+ total-sbtc-staked 1_000_000))`, recording 1,000,000 sats staked even though the contract's real sBTC balance only grew by 999,000.
5. `total-sbtc-staked` now exceeds the contract's actual custodied sBTC by 1,000 sats; subsequent reward calculations and `unstake-sbtc` calls for this or other stakers can be shorted by this shortfall, since the contract no longer holds enough sBTC to honor all recorded stakes.
