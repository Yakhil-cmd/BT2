This is the vulnerability. The webhook signature is verified using the secret for the organization derived from `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` — but every default handler (`Handler#repository_name`) looks up the target `Repository`/`Stack` using a completely different field, `payload.dig('repository', 'full_name')`. Since these two fields are independent, unsigned attacker-controlled JSON values (`repository.owner.login` vs. `repository.full_name`), an attacker who controls a GitHub App installation on their own organization (and thus knows that organization's valid `webhook_secret`) can forge a payload where `repository.owner.login` names their own org (so signature verification passes) while `repository.full_name` names a victim's repository/stack, causing the engine to act (e.g., trigger `GithubSyncJob`, create teams/memberships, or drive review-stack lifecycle events) on a repository the attacker does not control.

### Title
Webhook signature is verified against `repository.owner.login` while handlers act on the unrelated, unsigned `repository.full_name` field, allowing cross-repository forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

Once the signature check passes, `create` dispatches the full JSON body to every registered handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 

Every default `Handler` subclass (push, status, check_suite, pull_request handlers, etc.) resolves the target `Stack`/`Repository` from an entirely different JSON field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` splits `full_name` on `/` and does an independent DB lookup unrelated to the field used for signing. [6](#0-5) 

### Finding Description
The trust binding that should hold is: **organization whose secret authenticated the request == repository the handlers act on**. The controller only enforces `HMAC(secret_for(repository.owner.login), raw_body) == signature_header`; it never checks that `repository.owner.login` and `repository.full_name`'s owner segment refer to the same repository, nor does it bind the verified signature to any specific target repository beyond the "select-which-secret-to-use" decision. Because `repository.owner.login` and `repository.full_name` are two independent, attacker-controlled JSON keys in the same unsigned-until-verified request, an attacker who owns/administers a GitHub organization with a Shipit GitHub App installed (and therefore legitimately knows that org's `webhook_secret`, e.g. via `secrets.yml`/App config they control for their own org) can craft a payload where:
- `repository.owner.login = "attacker-org"` (used only to pick the secret for HMAC verification — passes, because the attacker knows `attacker-org`'s real webhook secret and can locally compute a valid HMAC over the raw body)
- `repository.full_name = "victim-org/victim-repo"` (used by every handler to find the actual `Stack`)

This breaks the equality `organization authenticated == repository written`, i.e., the organization whose credential authorizes the message is not the same as the repository the message causes actions on.

### Impact Explanation
Once past `verify_signature`, handlers act on `victim-org/victim-repo`'s stacks: `PushHandler` triggers `stack.sync_github(expected_head_sha:)` (queues `GithubSyncJob` against the victim stack), `StatusHandler`/`CheckSuiteHandler` can inject fabricated CI statuses/check runs that continuous-deployment logic relies on to gate/trigger deploys, and `MembershipHandler` can create/delete `Team`/`Membership`/`User` records unrelated to the attacker's own org. Because `Shipit.github_teams` authorization and merge/deploy gating (ignore_ci, required statuses, check runs) depend on this same webhook data pipeline, an attacker able to inject fabricated, "successful" status/check_suite events for a victim stack can move that stack into a state where a legitimate operator's next deploy/merge action proceeds against forged CI signals — this is an escalation into `Shipit.github_teams`-adjacent authorization and stack-state integrity that the report classifies as High.

### Likelihood Explanation
The precondition is that the attacker administers at least one GitHub organization/App installation configured in this Shipit instance (a normal, low-privilege scenario for any multi-tenant Shipit deployment supporting several organizations), which is enough to know that organization's own `webhook_secret` and legitimately send it valid signed requests. No access to the victim's secret, no repository write access to the victim repo, and no Shipit session or `ApiClient` token are required — only the ability to hit `POST /webhooks` with a crafted JSON body and a valid signature computed with the attacker's own org secret.

### Recommendation
Bind the verified signature to the actual target repository, not just to whichever key is used to look up the secret. Concretely, derive `repository_owner` from the same field handlers use for repository resolution (`repository.full_name`'s owner segment), or reject requests where `repository.owner.login` does not match the owner segment of `repository.full_name`/`organization.login`. Longer term, verify the signature against the webhook secret associated with the specific `Repository` record ultimately targeted by the payload (once resolved), not a value chosen purely from unauthenticated request content before the target is even determined.

### Proof of Concept
1. Attacker legitimately installs/controls the Shipit GitHub App on `attacker-org`, thus knows `webhook_secret_attacker-org`.
2. Attacker crafts a push-event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_attacker-org, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature [7](#0-6) .
5. `PushHandler.call(params)` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues a sync/deploy-relevant job for the victim's stack [5](#0-4) [6](#0-5) , despite the attacker having no relationship to `victim-org`.
