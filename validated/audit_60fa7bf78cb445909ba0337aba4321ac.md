### Title
Webhook signature is verified against an attacker-chosen organization while the mutated repository/commit is selected from unauthenticated payload fields, enabling cross-tenant webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate the inbound HMAC signature against by reading the *attacker-supplied* JSON body itself, then hands the very same attacker-supplied body to handlers that select the repository/commit to mutate using *different* fields of that same unauthenticated body. In a multi-organization Shipit deployment (one Shipit instance serving several GitHub organizations, each with its own GitHub App and `webhook_secret`), this breaks the binding: `organization_that_authenticated(payload) == organization_owning_repository(written)`.

### Finding Description
`verify_signature` picks the `GitHubApp` used to check `X-Hub-Signature` using `repository_owner`, which is read straight out of the untrusted JSON payload: [1](#0-0) [2](#0-1) 

Shipit explicitly supports one `GitHubApp`/`webhook_secret` per organization, each configured independently by that organization's own admins: [3](#0-2) [4](#0-3) 

Once the signature check passes (using the secret belonging to whichever organization the attacker put in the `repository`/`organization` field), the raw JSON is dispatched to handlers unmodified: [5](#0-4) 

Handlers, however, resolve *which repository/commit to act on* from other, independently-controlled fields of the same payload, with no re-check that they belong to the organization whose secret validated the signature: [6](#0-5) [7](#0-6) 

`StatusHandler` is the most severe case: it doesn't even key off `repository.full_name` — it looks up commits **globally by sha**, across every repository/organization known to the Shipit instance: [8](#0-7) 

Because GitHub itself is not the one guaranteeing consistency here — the endpoint accepts any raw POST from anyone who knows *any one* organization's `webhook_secret` — the "organization that authenticated" (derived from `repository.owner.login`/`organization.login`, checked only against that org's HMAC secret) and "the repository/commit that is written" (derived from `repository.full_name` or a bare `sha` field) are never cryptographically tied together.

### Impact Explanation
In any multi-tenant configuration (multiple entries under `secrets.github`, each organization owning its own GitHub App and `webhook_secret` — the officially documented setup), an admin/owner of Org A's GitHub App knows Org A's `webhook_secret` because they configured it themselves. That is not a privileged Shipit credential; it is knowledge inherent to running their own tenant's GitHub App integration. Using it, they can:
- Set `repository.owner.login`/`organization.login` = `"OrgA"` so `verify_signature` succeeds with the secret they legitimately know, while setting `sha` (status event) or `repository.full_name` (push event) to target a stack belonging to a completely different organization, `OrgB`, hosted on the same Shipit instance.
- Forge a `status` webhook that flips any commit belonging to `OrgB` to `success` via `StatusHandler#process`/`Commit#create_status_from_github!`, which is exactly the kind of blocking/required status Shipit's merge-queue and deploy gating rely on — potentially causing an unauthorized merge or deploy on a repository the attacker has no legitimate access to.
- Forge a `push` webhook that triggers `GithubSyncJob` against `OrgB`'s stacks by setting `repository.full_name` to an `OrgB` repo, since `Handler#stacks` never checks that the resolved repository's organization matches the one that authenticated the request.

This is a cross-repository/cross-tenant write achieved purely through a webhook the attacker is entitled to send for their own organization, matching the "cross-repository writes / unauthorized deploy or merge" impact class.

### Likelihood Explanation
This requires a genuinely multi-tenant Shipit deployment (multiple GitHub Apps/organizations configured in `secrets.github`) and an attacker who legitimately controls one tenant's GitHub App configuration (its `webhook_secret`) but not others — precisely the trust boundary such multi-org deployments are meant to enforce between tenants. No Shipit user session, `ApiClient` token, or `api_clients_secret` is needed; only knowledge of one org's own webhook secret, which that org's admins possess by design.

### Recommendation
After verifying the HMAC signature, re-derive the authorized organization from the verified `GitHubApp`/secret used, and reject (or clamp) any request where payload fields used by handlers (`repository.full_name`, and for `StatusHandler`, the resolved commit's repository) do not belong to that same organization. Concretely:
- In `WebhooksController#verify_signature`, once `github_app` is resolved, also assert that every commit/repository the handler will touch belongs to that `github_app`'s organization.
- In `StatusHandler#process`, scope the `Commit.where(sha:)` lookup to commits whose stack/repository owner matches the verified organization, instead of a global sha lookup.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the admin of `OrgA`'s GitHub App, compute a valid `X-Hub-Signature` over a crafted JSON body using `OrgA`'s known `webhook_secret`:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/anything"},
  "sha": "<sha of a commit belonging to OrgB's private stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. POST this to `/webhooks` with header `X-Github-Event: status` and the computed signature.
4. `verify_signature` succeeds because it only checks the signature against `OrgA`'s secret (matching `repository.owner.login`).
5. `StatusHandler#process` ( [8](#0-7) ) finds the commit by `sha` regardless of which organization it belongs to and creates a `success` status on `OrgB`'s commit, without the attacker ever having access to `OrgB`'s GitHub App, webhook secret, or Shipit account.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
