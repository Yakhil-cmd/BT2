### Title
Disk filling from orphaned worktrees left behind by failed syncs after checkout - (File: main.go)

### Summary
`git-sync`'s cleanup routine (worktree pruning + git gc) only runs after a **successful** `SyncRepo()` call. Any sync attempt that creates a new worktree and checks out (potentially large) attacker-controlled content, but then fails during the subsequent submodule step (or any later step of the same sync), returns an error without removing the worktree it just created. Since the outer loop's cleanup call is gated behind the success branch, these partially-completed worktrees are never pruned, so a remote repo that repeatedly changes its head commit while making the post-checkout steps fail can accumulate an unbounded number of on-disk worktree directories.

### Finding Description
The sync loop in `main()` only calls `git.cleanup()` (which internally calls `removeStaleWorktrees()` and runs `git gc`) inside the success branch of the `git.SyncRepo()` call: [1](#0-0) 

Inside `SyncRepo()`, when the remote hash has changed, a brand-new worktree directory is created via `createWorktree()`, and then `configureWorktree()` is invoked to actually populate it (`git reset --hard <hash>`, then `git submodule update --init [--recursive]`). If `configureWorktree()` returns an error — e.g. because a `.gitmodules` entry points at an unreachable/broken URL — `SyncRepo()` immediately returns the error, **after the worktree has already been created and fully checked out**, without any cleanup of that worktree: [2](#0-1) 

`createWorktree()` only guards against re-creating a worktree for the *same* hash (a "wedge" case), it does not clean up unrelated, previously-orphaned worktree directories for other hashes: [3](#0-2) 

`configureWorktree()` performs the actual file checkout (`git reset --hard`) before the submodule step that can fail: [4](#0-3) 

The only routine that removes non-current ("stale") worktrees, `removeStaleWorktrees()`/`cleanup()`, is reachable exclusively from the success path of the main loop, never from the error path: [5](#0-4) [6](#0-5) 

Because a malicious or compromised remote can change its `HEAD`/ref on every poll interval (`--period`) while deterministically breaking the submodule step (or any step after checkout) each time, each failed sync attempt leaves behind a brand new, fully checked-out worktree directory under `--root/.worktrees/<hash>` that is never garbage collected. `--max-failures`/`--init-max-failures` are documented to support "-1" (retry forever) precisely to tolerate exactly this kind of transient failure, which means the loop (and disk growth) can continue indefinitely by design if such a value is configured; even with a positive limit, the container will typically be restarted by Kubernetes and resume accumulating worktrees (fail counters are process-local, not persisted).

### Impact Explanation
Each failed-after-checkout sync attempt permanently consumes disk space equal to the size of the checked-out tree (fully attacker-controlled, since it comes from the synced remote repo/content) under `--root`, with no automatic reclamation. Over a long-running sidecar deployment with a malicious or compromised upstream repo, this leads to unbounded growth of the shared volume (often a size-limited `emptyDir` in Kubernetes), eventually causing disk exhaustion. This can crash the git-sync container, the co-located application container sharing the volume, or other pods on the same node — a persistent sync/service denial, matching the accepted impact categories.

### Likelihood Explanation
Exploitation requires an attacker who controls (or can influence, e.g. via compromised credentials/MITM on the upstream repo) the git remote referenced by `--repo`, so they can repeatedly change the ref to a new commit each `--period` while making a later phase of the sync fail. This is a realistic scenario for `--submodules=recursive`/`shallow` (default is `recursive`), where an attacker who controls the top-level repo can plant a submodule entry pointing to a broken/unreachable URL. No special git-sync flags beyond defaults are required (submodules default to `recursive`), though a permissive `--max-failures`/`--init-max-failures` (e.g. `-1`, an explicitly documented use case) maximizes the persistence of the issue.

### Recommendation
Run `git.cleanup()` (or at least `removeStaleWorktrees()`) unconditionally at the end of each sync loop iteration, regardless of whether `SyncRepo()` succeeded or failed, so orphaned worktrees created during a failed attempt are pruned on the very next iteration. Additionally, `SyncRepo()` should remove the worktree it just created if any subsequent step (`configureWorktree`, `beforePublish`, `publishSymlink`, `afterPublish`) fails, rather than leaving it in place for the outer loop to (currently never) clean up.

### Proof of Concept
1. Host a git server whose `HEAD` can be repeatedly force-updated to a new commit on every fetch (e.g. a script that runs `git commit --allow-empty` and force-updates the branch every second).
2. Add to that repo a `.gitmodules` entry referencing an unreachable submodule URL, so `git submodule update --init --recursive` always fails.
3. Run `git-sync --repo=<that repo> --root=/root --link=link --period=1s --submodules=recursive --max-failures=-1`.
4. Observe: every ~1s a new directory appears under `/root/.worktrees/<new-hash>` fully populated with the (attacker-controlled, can be made arbitrarily large) checked-out content, and none of them are ever removed because `configureWorktree` always errors on the submodule step, so `main.go`'s success-only `git.cleanup()` call at line 1090 is never reached for these attempts. Disk usage under `/root/.worktrees` grows without bound over time.

func (git *repoSync) removeStaleWorktrees() (int, error) {
	currentWorktree, err := git.currentWorktree()
	if err != nil {
		return 0, err
	}

	git.log.V(3).Info("cleaning up stale worktrees", "currentHash", currentWorktree.Hash())

	count := 0
	err = removeDirContentsIf(git.worktreeFor("").Path(), git.log, func(fi os.FileInfo) (bool, error) {
		// delete files that are over the stale time out, and make sure to never delete the current worktree
		if fi.Name() != currentWorktree.Hash() && time.Since(fi.ModTime()) > git.staleTimeout {
			count++
			return true, nil
		}
		return false, nil
	})
	if err != nil {
		return 0, err
	}
	return count, nil
}

// createWorktree creates a new worktree and checks out the given hash.  This
// returns the path to the new worktree.
func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}

// cleanup removes old worktrees and runs git's garbage collection.  The
// specified worktree is preserved.
func (git *repoSync) cleanup(ctx context.Context) error {
	// Save errors until the end.
	var cleanupErrs multiError

	// Clean up previous worktree(s).
	if n, err := git.removeStaleWorktrees(); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	} else if n == 0 {
		// We didn't clean up any worktrees, so the rest of this is moot.
		return nil
	}

	// Let git know we don't need those old commits any more.
	git.log.V(3).Info("pruning worktrees")
	if _, _, err := git.Run(ctx, git.root, "worktree", "prune", "--verbose"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Expire old refs.
	git.log.V(3).Info("expiring unreachable refs")
	if _, _, err := git.Run(ctx, git.root, "reflog", "expire", "--expire-unreachable=all", "--all"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Run GC if needed.
	if git.gc != gcOff {
		args := []string{"gc"}
		switch git.gc {
		case gcAuto:
			args = append(args, "--auto")
		case gcAlways:
			// no extra flags
		case gcAggressive:
			args = append(args, "--aggressive")
		}
		git.log.V(3).Info("running git garbage collection")
		if _, _, err := git.Run(ctx, git.root, args...); err != nil {
			cleanupErrs = append(cleanupErrs, err)
		}
	}

	if len(cleanupErrs) > 0 {
		return cleanupErrs
	}
	return nil
}
