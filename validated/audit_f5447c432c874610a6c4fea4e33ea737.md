### Title
Webhook signature bypass via organization/repository field confusion when an organization has no `webhook_secret` configured - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives the GitHub App/secret to validate a webhook against from `repository_owner`, a value read from the payload itself (`repository.owner.login`, falling back to `organization.login`). The actual repository a handler subsequently *acts on* (creating tasks, syncing commits, triggering deploys) is derived independently from `repository.full_name` inside `Shipit::Webhooks::Handlers::Handler#repository_name`. These two payload fields are never cross-checked. If the organization identified by `repository_owner` has no `webhook_secret` configured, `GithubApp#verify_webhook_signature` unconditionally returns `true`, and the unverified `repository.full_name` field can then be forged to point at any other repository/stack managed by Shipit — including ones belonging to organizations that do have a secret configured.

### Finding Description
The bug class from the report is: a check bypasses enforcement entirely when a governing configuration value is "zero"/unset, while an invariant tied to that check (locked amount ≤ balance) is silently violated later. The Shipit analog is that webhook authentication is bypassed entirely when `webhook_secret` is blank, while the invariant "the repository written to (`repository.full_name`) is the repository the organization actually authenticated for (`repository_owner`)" is silently violated later.

`verify_webhook_signature`: [1](#0-0) 

returns `true` immediately if `webhook_secret` is falsy — i.e., it never checks the signature at all — before the `X-Hub-Signature` is compared to anything. The sample production config explicitly documents `webhook_secret` as an optional (`# nil`) field per organization: [2](#0-1) 

The controller selects *which* organization's app/secret to use for verification purely from attacker-controlled payload content: [3](#0-2) 

Meanwhile, every handler (push, status, check_suite, pull_request, etc.) resolves the actual `Stack`/`Repository` to act on from a *different* payload field, `repository.full_name`, with no relation back to `repository_owner`: [4](#0-3) 

and then performs a genuine write, e.g. `PushHandler` triggers `stack.sync_github(...)` for every non-archived stack matching that repository/branch: [5](#0-4) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated (repository_owner used for signature lookup) == repository actually written (repository.full_name used by handlers)`

Before the attack: for any request, the organization whose secret validates the HMAC over the full raw body is necessarily the same organization whose repository is referenced in that body (since `full_name` is part of the signed payload).

After the attack: an attacker who knows (or guesses, since it's documented as an intentionally supported blank config value) that some organization `OrgA` configured in this Shipit deployment has no `webhook_secret`, can send an unsigned/arbitrary-signature request with `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) but `repository.full_name = "OrgB/target-repo"`. `verify_signature` looks up `Shipit.github(organization: "OrgA")`, calls `verify_webhook_signature` which short-circuits to `true` because `OrgA`'s `webhook_secret` is blank — no HMAC check occurs on the body at all. The handler then acts on `OrgB/target-repo`'s stacks using the forged `full_name`, even though `OrgB` may have a fully configured `webhook_secret`.

### Impact Explanation
This allows an unprivileged external attacker to forge GitHub webhook events (push, status, check_suite, pull_request, membership) for repositories/stacks belonging to *any* organization onboarded to the Shipit instance, as long as at least one other onboarded organization has no `webhook_secret` set (an explicitly supported, documented configuration). Concretely via `PushHandler`, this triggers `Stack#sync_github`, which is used to advance the deployable commit/branch state used to gate and drive deploys — an unauthorized manipulation of stack/deploy state without possessing any legitimate GitHub webhook secret, session, or API token. This crosses the "unauthorized deploy" / cross-repository-write boundary called out as in-scope Critical impact.

### Likelihood Explanation
Requires only that the target Shipit instance be configured for more than one GitHub organization and that at least one of those organizations omits `webhook_secret` (shown as a normal/expected configuration value in the shipped sample config). No credentials, session, GitHub App key, or repository access are required — only knowledge (or a public listing) of one onboarded organization's login that has no secret configured, which is easily discoverable since organization logins are public GitHub identities.

### Recommendation
Do not allow signature verification to auto-pass based on the attacker-supplied `repository_owner`/`organization` field alone. At minimum:
- Cross-validate that `repository.owner.login`/`organization.login` matches the owner portion of `repository.full_name` before trusting either for verification or handler dispatch.
- Do not silently bypass signature verification when `webhook_secret` is blank for *some* organizations in a multi-organization deployment; either require `webhook_secret` for all configured organizations or scope handler dispatch strictly to the organization that was actually verified (not a payload-controlled field read independently by handlers).

### Proof of Concept
1. Deploy Shipit configured with two organizations: `OrgA` (no `webhook_secret`, per the documented nil-secret support) and `OrgB` (has `webhook_secret` configured, hosting a real stack `OrgB/target-repo`).
2. Send `POST /webhooks` with header `X-Github-Event: push`, `X-Hub-Signature: sha1=deadbeef` (arbitrary/invalid), and JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/target-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which returns `true` unconditionally because `OrgA` has no `webhook_secret`, per `lib/shipit/github_app.rb` lines 76-77.
4. `Shipit::Webhooks::Handlers::PushHandler` resolves stacks via `repository.full_name = "OrgB/target-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s real stack, with no signature ever validated against `OrgB`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

**File:** app/controllers/shipit/webhooks_controller.rb (L24-62)
```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
