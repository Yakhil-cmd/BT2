This confirms the vulnerability described in the question. Let me verify the exact code path and check for any tenant-scoping guard I may have missed.### Title
Cross-tenant commit status write via SHA-only lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target `Commit` rows solely by `sha`, with no scoping to the repository/organization that authenticated the webhook. Since `sha` is not unique across repositories/stacks, an attacker who owns any repository can send a `status` webhook signed with their own repo's `webhook_secret` and mutate CI status (and trigger deploy-relevant side effects) on a `Commit` belonging to a completely unrelated tenant repository, as long as the two commits share a SHA.

### Finding Description
The claimed binding is: `organization_that_signed_the_webhook == organization_owning_every_Commit_row_mutated_by_the_handler`. Tracing the code shows this does not hold.

`WebhooksController#verify_signature` selects the GitHub app to verify against using `repository_owner` taken from the payload (`params.dig('repository', 'owner', 'login')`), then calls `github_app.verify_webhook_signature(signature, raw_post)` [1](#0-0) . This only proves the request body was signed with the secret for the organization named in the payload (`attacker`) — it says nothing about which `Commit` rows the handler is permitted to touch.

`WebhooksController#create` then dispatches the parsed body to all handlers for the event [2](#0-1) . For a `status` event, `StatusHandler#process` runs:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This query is global across the `commits` table — it is not scoped by `stack_id`, `repository_id`, or any owner/organization derived from the verified payload. `Commit#create_status_from_github!` then calls `add_status`, which creates a `Status` record via `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) . `Status#after_create` callbacks then run `enable_ci_on_stack` (which calls `commit.stack.enable_ci!`) and `schedule_continuous_delivery` (which calls `commit.schedule_continuous_delivery`) [5](#0-4) . If the victim's stack has `continuous_deployment: true`, this can trigger `Stack#trigger_continuous_delivery`.

Attack flow:
1. Attacker owns `attacker/public-repo`, which is configured/onboarded in Shipit and thus has a known `webhook_secret` (their own).
2. Attacker crafts (or naturally has) a commit with SHA `X` that happens to collide with a SHA already tracked as a `Commit` in `victim/private-repo`'s stack (e.g., shared root/empty-tree commit, cherry-pick, or a rebase-preserved commit).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body `{sha: X, state: 'success', repository: {owner: {login: 'attacker'}}}`, signed with `attacker`'s own webhook secret.
4. `verify_signature` succeeds because it only checks that the signature matches `attacker`'s secret for the `attacker` org named in the payload — it never checks that `X` belongs to a commit owned by `attacker`.
5. `StatusHandler#process` runs `Commit.where(sha: X)`, which returns **every** commit row across **every** stack/repo with that SHA, including `victim/private-repo`'s commit, and writes a `Status` to it.

None of the existing guards prevent this: `verify_signature` only authenticates the org named in the payload, not the actual commit ownership; `drop_unhandled_event` and the `ExplicitParameters` schema (`params.sha`, `params.state`, etc.) only validate shape, not tenancy; there is no `Repository` or `Stack` scoping check anywhere in `StatusHandler` or `Commit.create_status_from_github!`.

### Impact Explanation
An attacker can write a fabricated CI `Status` (state, description, target_url, context) onto a `Commit` in a victim's private/unrelated stack, without ever having access to that repository. This is a cross-repository write: a payload authenticated for one repository mutates another tenant's commit/stack state. If the victim stack has `continuous_deployment: true`, this can improperly flip a commit's CI status to `success`, potentially triggering the continuous-deployment pipeline (`schedule_continuous_delivery` → `ProcessMergeRequestsJob` / `trigger_continuous_delivery`), i.e., causing an unauthorized deploy decision on a tenant the attacker never touched. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team ... or an unauthorized deploy."

Blast radius: any repository already onboarded to Shipit is a viable attack repo, and every `Commit` row sharing that SHA in the whole instance (potentially many stacks/orgs, if multi-org config is used) is affected per request. It's fully repeatable — the attacker can pick any known/colliding SHA and any state.

### Likelihood Explanation
Preconditions: the attacker must own at least one repository already registered with Shipit (so a webhook secret exists and their webhook requests are accepted), and a SHA collision must exist between attacker-controlled and victim commits already tracked in Shipit. SHA collisions are realistic in common scenarios: shared base/root commits across forks, cherry-picked or rebased commits with byte-identical trees/messages, or the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, which is identical byte-for-byte across every repository and requires no cryptographic collision — only that both attacker and victim histories reference it as a tracked `Commit`. Attacker cost is low (they only need to send one signed HTTP POST); the exploit is trivially repeatable.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository/organization that authenticated the webhook, not just by `sha`. For example, join through `Stack`/`Repository` and filter by the repository's `owner`/`full_name` extracted from the verified payload (matching the same `repository_owner` used in `WebhooksController#verify_signature`), e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repository_name })`. Apply the analogous fix to any other handler (e.g. check_suite/check_run handlers) that resolves records purely by `sha` without repository scoping.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":status cross-tenant SHA collision writes to unrelated stack's commit" do
  shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904'

  attacker_stack  = shipit_stacks(:shipit) # owned/authenticated org "shopify" in fixtures
  victim_stack    = Shipit::Stack.create!(
    repository: Shipit::Repository.create!(owner: 'victim', name: 'private-repo'),
    environment: 'production',
    continuous_deployment: true
  )

  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'attacker commit', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: shared_sha,
    state: 'success',
    repository: { owner: { login: 'shopify' } } # attacker's own authenticated org
  }.to_json

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end
  # This proves a webhook authenticated ONLY for the "shopify"/attacker org
  # wrote a Status onto a Commit belonging to an unrelated "victim" stack,
  # violating: signing_org(attacker) == owning_org(every mutated Commit).
end
```
