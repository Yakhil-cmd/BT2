### Title
Unchecked debt-value overflow in `accrue_step` permanently freezes an entire market — any user can wedge it past the point of no return - (File: common/src/rates/simulate.rs)

### Summary
CVE-2020-24265 is a heap buffer overflow that crashes `tcpprep` — a crash/DoS driven by an unchecked size assumption. The analog on XOXNO Lending is the `scaled_to_original` value-overflow panic inside `accrue_step`: once a market's scaled debt value crosses the `i128` RAY-value ceiling, every subsequent accrual panics with `MathOverflow`, and because every pool verb accrues first via `interest::global_sync`, the market is permanently frozen — no repay, no withdraw, no liquidation, no cleanup. A single unprivileged whale can push a market into this terminal state, after which no one (including suppliers and liquidators) can touch it.

### Finding Description
`simulate_update_indexes_body` (common/src/rates/simulate.rs:136-181) and the pool's mutating `global_sync` (contracts/pool/src/interest.rs:20-33) share one accrual step, `accrue_step`. Each step recomputes utilization as `scaled_to_original(borrowed, borrow_index) / scaled_to_original(supplied, supply_index)` — i.e., it multiplies scaled RAY shares by a RAY index. The borrow index is capped at `MAX_BORROW_INDEX_RAY` (10^36 raw), but the *product* `borrowed_shares × borrow_index` is not: `scaled_to_original` uses checked multiplication and reverts with `MathOverflow` on overflow. The codebase itself proves this is reachable and terminal:

- `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` constructs a 18-decimal whale market (10^9 × 10^18 principal supplied, 98% borrowed on the steep XLM curve segment), advances time, and shows `try_update_indexes_for` eventually returning `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` — the value ceiling hits *before* the index cap engages. It then asserts `try_withdraw_raw` and `try_repay` both fail with the same `MATH_OVERFLOW`, i.e. the freeze is total.
- The panic is non-recoverable: `last_timestamp` is only advanced by `mark_accrued()` after the chunk loop completes (interest.rs:26-32), so the failed accrual leaves `last_timestamp` in the past and every future call re-runs the same overflowing step. Elapsed time only grows, so the state can never return below the overflow cliff. There is no admin escape hatch — `global_sync` runs inside `Cache::load`/`mutate` for every market mutation, including owner-only ones.
- INV-IDX-01 (docs/reference/invariants.md:229-236) concedes "Debt-value overflow can still revert accrual before that ceiling is reached," confirming the panic site rather than excusing the impact.

Reachability requires only `controller::supply` and `controller::borrow` (or direct `update_indexes`, which is a permissionless entrypoint) plus ledger-time passage — all unprivileged. No oracle manipulation, no privileged call, no leaked key.

### Impact Explanation
Permanent freezing of funds: once the market's scaled-debt value exceeds `i128::MAX / index`, every entrypoint that touches the market (`supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `clean_bad_debt`, `claim_revenue`, `recapitalize`, `update_indexes`) panics in `global_sync` before any state change. All suppliers' deposits and the protocol's revenue shares in that market are frozen forever; borrowers cannot repay and liquidations cannot run. This satisfies the "permanent freezing of funds" / "protocol insolvency-adjacent market death" acceptance criterion — it is not a fail-closed price-outage revert (ADR-0005) that resolves when a feed recovers; no external condition can ever lift it.

### Likelihood Explanation
Medium-to-low likelihood, high certainty once reached. The trigger needs a large market (the demonstrated case uses ~10^27 asset units at 18 decimals — plausible for an 18-decimal token with low unit price, and caps must permit it, which is a governance parameter rather than an invariant) and sustained high utilization long enough for the borrow index to grow ~170x. Utilization near 100% is an ordinary market condition under organic demand or a deliberate borrow-and-hold attack by a single whale who both supplies and borrows. Once conditions are met, any caller of the permissionless `update_indexes` detonates the freeze; there is nothing a user can do to avoid crossing it and no governance action that can undo it (governance `op` calls into the same contract functions that accrue first). Documentation acknowledges the residual risk but the code contains no clamp, circuit breaker, or last_timestamp advance that bounds it.

### Recommendation
- Clamp instead of reverting: cap the borrow index growth the moment the unscaled debt value approaches the representable ceiling (e.g., clamp `borrow_index'` to `i128::MAX / borrowed_shares` in addition to `MAX_BORROW_INDEX_RAY` inside `update_borrow_index` or `accrue_step`), mirroring the existing "sticky ceiling" behavior at `MAX_BORROW_INDEX_RAY` (common/tests/rates/simulate.rs:351-367 already encodes that pattern).
- Alternatively, advance `last_timestamp` per completed chunk inside `accrue_chunk` rather than once after the loop, so a panic still commits earlier chunks and cannot leave the market permanently behind.
- Add a market-level guard: a hard `MathOverflow`-independent debt ceiling in `borrow`/`global_sync` that stops accrual-driven growth before `scaled_to_original` overflows, so suppliers retain a working exit path.

### Proof of Concept
The shipped test is a self-contained PoC: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361). Steps:

1. Create market `BIG18` (18 decimals, XLM rate curve), lift supply/borrow caps via governance.
2. `supply(BOB, BIG18, 10^9 * 10^18)`; `supply(ALICE, COL, …)`; `borrow(ALICE, BIG18, 98% of supply)` — all unprivileged.
3. Repeatedly `advance_time(YEAR_SECS)` + `update_indexes(BIG18)`. Within ≤40 simulated years `try_update_indexes_for` returns `MATH_OVERFLOW` with `borrow_index < MAX_BORROW_INDEX_RAY`.
4. Permanent freeze verified: `try_withdraw_raw(BOB, BIG18, 1)` and `try_repay(ALICE, BIG18, 1.0)` both revert `MATH_OVERFLOW` — and will forever, since `last_timestamp` never advances past the failing step.
