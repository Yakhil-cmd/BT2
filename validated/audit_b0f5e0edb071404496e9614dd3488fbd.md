### Title
`StatusHandler#process` writes GitHub status to every `Commit` sharing a SHA, ignoring the authenticated repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and applies the incoming status to **all** matching rows across the entire Shipit instance, with no filter on `payload['repository']['full_name']`. Because git SHAs are content-addressed and independent of the repository they live in, an attacker who controls any onboarded repository can push the exact bytes of a victim's commit into their own repo, trigger a real, validly-signed `status` webhook for it, and have that status applied to the victim's identical-SHA `Commit` record in a completely different stack.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`commit.stack.repository.full_name == payload['repository']['full_name']` for every `Commit` mutated by `StatusHandler#process`.

Code path:
1. `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) dispatches the parsed JSON body to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which validates the HMAC using `Shipit.github(organization: repository_owner)` (app/controllers/shipit/webhooks_controller.rb:24-30). This authenticates *that the payload really came from GitHub for the named `repository_owner`/org* — it says nothing about which stack/commit rows should be touched. [1](#0-0) 
2. `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with **no** scoping by repository/stack, unlike sibling handlers such as `PullRequest::ReopenedHandler`, which explicitly resolve `Repository.from_github_repo_name(params.repository.full_name)` before touching any stack. [2](#0-1) [3](#0-2) 
3. `create_status_from_github!` calls `add_status`, which replaces the commit's status group and, if the `simple_state` changes, emits `deployable_status` hooks and reschedules merges — directly affecting `deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`). [4](#0-3) [5](#0-4) [6](#0-5) 

Attacker flow:
- Attacker fetches the victim's public commit (from a PR, a fork, or any exposed ref) — since SHAs are content hashes, pushing the identical commit object into a repository the attacker owns produces the identical SHA.
- Attacker's repository is a genuinely onboarded Shipit repo/stack (Shipit supports self-service repository/stack creation via `RepositoriesController#create`/`StacksController#create`, and `Repository.find_or_create_by(owner:, name:)` performs no ownership check against the caller). [7](#0-6) 
- Attacker sets a commit status (`context: review/approved`, `state: failure`) on that SHA in their own repo via the normal GitHub API/UI. GitHub genuinely and correctly signs this webhook for the attacker's own org/repo — no forged signature is needed, because `verify_signature` only checks that the payload came from *some* legitimate GitHub org configured in Shipit, not that the SHA "belongs" to that org.
- `StatusHandler` then rewrites the status on every `Commit` row with that SHA, including the victim's, in a completely unrelated stack.

Existing guards do not stop this: `verify_signature` authenticates origin-of-payload, not scope-of-effect; there is no `Repository`/`Stack` filter in `StatusHandler`; `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not ownership.

### Impact Explanation
An attacker who owns/controls any repository onboarded to the shared Shipit instance can force a required status context (e.g., `review/approved`) to `failure` (or forge `success`) on a victim commit that they don't own, directly manipulating that victim stack's `Commit#deployable?` and merge-queue eligibility (`stack.schedule_merges`, `deployable_status` hook). This is a cross-tenant/cross-repository state mutation — one repository's authenticated payload writes another repository's records — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is fully repeatable against any commit whose SHA the attacker can reproduce (trivial for forked/mirrored public repos, or any commit whose content the attacker can obtain and re-push).

### Likelihood Explanation
Preconditions: Shipit hosts (or the attacker can self-onboard) at least one additional repository/stack besides the victim's, and the attacker can reproduce the victim's commit SHA by pushing the same commit content into their own repository — trivial for any public commit/PR (which is the normal case for open-source CI or review-stack setups). No secrets, sessions, or elevated GitHub permissions are needed; the attacker only ever authenticates their own legitimate webhook for their own repository. Cost is minimal (git push + one API status call), and the attack is repeatable at will against any target SHA that has been mirrored.

### Recommendation
Scope `StatusHandler#process` (and any other handler using unscoped `Commit.where(sha:)`) to only the commits belonging to the repository identified in the webhook payload, e.g. filter through `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks&.commits` before applying `create_status_from_github!`, mirroring the pattern already used in the pull-request handlers.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook mutates commits across unrelated repositories sharing a SHA" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(cached_deploy_spec: { 'ci' => { 'require' => ['review/approved'] } })
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim commit")
  victim_commit.statuses.create!(stack: victim_stack, context: "review/approved", state: "success")

  attacker_repo = Shipit::Repository.create!(owner: "attacker", name: "evil-repo")
  attacker_stack = Shipit::Stack.create!(repository: attacker_repo, environment: "production")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "attacker commit")

  before_deployable = victim_commit.reload.deployable?
  assert before_deployable

  payload = {
    "sha" => shared_sha,
    "state" => "failure",
    "context" => "review/approved",
    "repository" => { "full_name" => "attacker/evil-repo" }
  }
  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  after_deployable = victim_commit.reload.deployable?

  # Binding under test: victim_commit's status should only change if the
  # authenticated repository (attacker/evil-repo) is the victim's repository.
  assert_not_equal "attacker/evil-repo", victim_stack.repository.full_name
  refute after_deployable, "victim commit's deployability was mutated by an unrelated repository's webhook"
end
```
This demonstrates that `before_deployable != after_deployable` even though the equality `commit.stack.repository.full_name == payload['repository']['full_name']` is false, proving the cross-repository write.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
