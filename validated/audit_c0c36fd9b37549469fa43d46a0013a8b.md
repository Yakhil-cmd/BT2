### Title
Webhook signature verification org (`repository.owner.login`) is decoupled from the repository actually mutated (`repository.full_name`), allowing cross-repository forgery via `LabelCapturingHandler` - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository','owner','login')`. But every downstream handler, including `LabelCapturingHandler`, resolves the actual `Repository`/`Stack` to mutate using `params.repository.full_name`. These two fields are never checked for consistency, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for the named organization. This lets an attacker pick an org with no configured secret for the signing check while pointing `full_name` at a victim repository under a different, secured org.

### Finding Description
The broken binding, stated as an equality that must hold but does not:
`organization_used_to_verify_signature (params.repository.owner.login)` MUST equal `organization_owning_the_repository_actually_mutated (params.repository.full_name.split('/').first)`, but no code enforces this.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) [2](#0-1) 
- `Shipit.github` looks up per-org config via `github_app_config(organization)` when running in multi-org mode (`github_default_organization` present), raising `GithubOrganizationUnknown` only if the org is entirely unknown; if the org is known but has no `webhook_secret` configured, `config[:webhook_secret]` is blank [3](#0-2) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank: `return true unless webhook_secret` [4](#0-3) 
- Once verification passes, `create` dispatches `params` to handlers for the event, unmodified [5](#0-4) 
- `LabelCapturingHandler#repository` resolves the repo to mutate using `params.repository.full_name`, entirely independent of `repository_owner`/the org used for signing: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) 
- The stack is then found via `ReviewStackAdapter#stack`, scoped to `repository.review_stacks`, matched by `environment: "pr#{params.number}"` [7](#0-6) [8](#0-7) 
- `capture_labels` then writes attacker-controlled label names onto the victim's `PullRequest` record: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [9](#0-8) 

Exploit flow: attacker crafts a `pull_request` webhook with `X-Github-Event: pull_request`, `action: "opened"`, `repository.owner.login` set to some org configured in `Shipit.github_organizations` that has no `webhook_secret` set, and `repository.full_name` set to `"victim-org/victim-repo"` (a real, tracked repository with an active review stack matching `pr#{number}`). Because the org named in `owner.login` has no secret, `verify_webhook_signature` returns `true` regardless of the (attacker-controlled, arbitrary) `X-Hub-Signature` header, so the request passes `verify_signature` unauthenticated in effect. The handler then resolves and mutates the victim repository's stack/PR using `full_name`, which was never checked against the org that "authenticated" the request.

Existing guards do not prevent this: `drop_unhandled_event` and `check_if_ping` are unrelated; `ExplicitParameters` schemas only validate types/presence of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name`; `Repository#from_github_repo_name` performs a straightforward DB lookup with no ownership/secret binding [10](#0-9) ; there is no code anywhere in the traced path that compares `repository_owner` to `repository.full_name`'s owner segment.

Note: the "shared commit SHA with attacker repo stack" element of the question's premise is not actually required for this specific handler — `LabelCapturingHandler` matches the stack by PR number/environment (`pr#{number}`), not by commit SHA, so the SHA-collision framing in the question is a red herring for this particular handler, but it does not diminish the core vulnerability, which is fully reachable with just the owner/full_name mismatch and a matching PR number on an active review stack.

### Impact Explanation
An attacker who can identify (or has visibility into) any multi-org-configured GitHub organization on the Shipit instance that lacks a `webhook_secret` can forge webhooks against **any other tracked repository's review stack** by simply setting `repository.owner.login` to the no-secret org and `repository.full_name` to the target repo. This is a payload for one repository (the attacker's fabricated no-secret-org identity) mutating another repository's stack/PR records — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Concretely: attacker-chosen label names get persisted onto the victim `PullRequest` and, per the question's broader chain, those label names become uppercased env-var keys via `ReviewStack#env`, which can inject/override environment variables surfaced to deploy/build commands for that review stack — an unauthenticated cross-tenant record write. This is repeatable against any repo with an active review stack whose PR number the attacker knows or guesses, requiring only one webhook POST per attempt.

### Likelihood Explanation
Preconditions: Shipit must be running in multi-org GitHub App configuration (`github_default_organization` present, i.e., `secrets.github` keyed by org names) with at least one configured org lacking a `webhook_secret`. In single-org mode, `Shipit.github` ignores the passed `organization` for config purposes and always uses the single top-level `webhook_secret`, so this exploit path does not apply there. Given multi-org mode with a no-secret org, attacker cost is trivial: one unauthenticated HTTP POST, no GitHub credentials, no Shipit session needed, and the org name is discoverable from Shipit's own UI/config or by trial (the response differentiates `GithubOrganizationUnknown` "unknown org" 422 vs. a processed request). Repeatable indefinitely against any repository whose review stack exists.

### Recommendation
In `WebhooksController#verify_signature`, require that the organization used to verify the signature is consistent with the organization implied by `repository.full_name` (and reject if they diverge). Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` for organizations with no configured `webhook_secret` — either require every configured organization to have a webhook secret, or reject (422) webhooks for organizations without one, rather than treating a missing secret as "verification not required."

### Proof of Concept
minitest plan (e.g., in `test/controllers/webhooks_controller_test.rb`, illustrative):
```ruby
test "pull_request webhook with owner/full_name split bypasses signature and mutates victim stack" do
  # Setup: multi-org secrets config where org "no-secret-org" is configured with no webhook_secret,
  # and org "victim-org" has a webhook_secret configured.
  victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo")
  victim_stack = shipit_review_stacks(:some_review_stack) # environment "pr42", repository: victim_repo
  victim_pr = victim_stack.pull_request

  # Binding under test (BEFORE):
  assert_not_equal victim_pr.labels, ["pwned"]

  payload = {
    action: "opened",
    number: 42,
    pull_request: {
      id: 1, number: 42, url: "x", title: "x", state: "open", additions: 1, deletions: 1,
      head: { sha: "deadbeef", ref: "feature" },
      user: { login: "attacker" },
      assignees: [],
      labels: [{ name: "pwned" }]
    },
    repository: { full_name: "victim-org/victim-repo", owner: { login: "no-secret-org" } },
    sender: { login: "attacker" }
  }.to_json

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = 'sha1=totally_bogus_signature'

  post :create, body: payload, as: :json
  assert_response :ok # signature check passed despite bogus signature, because "no-secret-org" has no webhook_secret

  # Binding under test (AFTER): victim repo's PR mutated by a payload that was "authenticated" as no-secret-org
  victim_pr.reload
  assert_equal ["pwned"], victim_pr.labels
end
```
This demonstrates the equality `organization_used_to_verify_signature == organization_owning_mutated_repository` is violated (`"no-secret-org" != "victim-org"`), and that the mismatch results in a record write to the victim's `PullRequest` from a request that never possessed the victim org's `webhook_secret`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
