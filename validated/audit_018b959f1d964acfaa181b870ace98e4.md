### Title
API-token stack-scope bypass in CCMenu status endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup helper to resolve the stack directly from `Stack.from_param!(params[:stack_id])` instead of going through the scoped `stacks`/`stack` helpers defined in `Shipit::Api::BaseController`. This breaks the invariant "stack a token authorizes == stack it touches": an `ApiClient` created with a `stack_id` restriction (i.e. authorized to act only on one specific stack) can be used with the CCMenu endpoint to read the build/deploy status of *any* stack in the installation, not just the one it is scoped to.

### Finding Description
`Shipit::Api::BaseController` implements stack scoping consistently for every other API resource: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the `ApiClient` is scoped, and `stack` resolves `params[:stack_id]` only within that restricted set. This is the mechanism that is exercised and asserted in `StacksControllerTest#"an api client scoped to a stack will only see that one stack"` and in the fixture where `here_come_the_walrus` is bound to a single stack: [2](#0-1) [3](#0-2) 

`CCMenuController`, however, redefines the private `stack` method to bypass this scoping entirely, resolving the stack from the *unscoped* `Stack` relation using only the request parameter: [4](#0-3) 

The only authorization check that remains is `require_permission :read, :stack`, which is enforced by `ApiClient#check_permissions!`: [5](#0-4) 

That check only verifies the client holds the `read:stack` permission string; it says nothing about *which* stack. The stack-level restriction (`ApiClient#stack_id`) is enforced exclusively by the `stacks`/`stack` helper in `BaseController`, which `CCMenuController` does not use for the object it renders.

The route confirms `stack_id` is a free-form path parameter supplied by the caller, not something scoped server-side: [6](#0-5) 

This is the exact analog of the reported bug class: the report's `_deposit()` enforced one restriction type (`SOFT_RESTRICTED_STAKER_ROLE`) but omitted the other (`FULL_RESTRICTED_STAKER_ROLE`) on the same operation, letting a restricted actor act outside its intended boundary. Here, the "restriction type" is `ApiClient.stack_id` scoping: it is enforced for `StacksController`, `TasksController`, `DeploysController`, `HooksController`, etc. (all routed through `BaseController#stack`/`#stacks`), but the check is silently dropped for `CCMenuController`, letting a stack-scoped token act (read) outside the one stack it was authorized for.

### Impact Explanation
An `ApiClient` token deliberately scoped to a single stack — the mechanism operators use to hand out narrowly-authorized credentials to third parties (e.g. CI dashboards, status widgets) — can be replayed against `GET /api/stacks/:stack_id/ccmenu` with an arbitrary `stack_id` to read another stack's deploy/build state: last build status, last build label/time, lock state and lock reason (rendered via `shipit/ccmenu/project`). This is a scoped-credential escalation into unauthorized read of stack state, matching the "High" impact category defined by the rules ("escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state, task streams or deploy output"). No repository write, session, or GitHub credential is required — only the CCMenu-scoped API token itself, which the attacker is assumed to legitimately hold for one stack only.

### Likelihood Explanation
High likelihood for any deployment that issues stack-scoped `ApiClient` tokens (a documented, intended use-case per the `stack` association and the existing scoping tests). Exploitation requires only knowing/guessing another stack's `stack_id` (owner/repo/environment triple), which is not secret information (visible in the Shipit UI/URL structure), and sending one HTTP GET with the already-possessed token.

### Recommendation
Remove the private `stack` override in `CCMenuController` (and the `authenticate_api_client` override should still call `super`, which it does) so that it resolves the stack via the scoped `stacks.from_param!(params[:stack_id])` helper inherited from `BaseController`, exactly like every other API controller. This restores the invariant that a stack-scoped `ApiClient` can never resolve a `Stack` outside its `stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: <shipit_stack.id>` with `permissions: ['read:stack']` (matching fixture `here_come_the_walrus`).
2. As that client, issue `GET /api/stacks/<authorized_owner>/<authorized_repo>/<authorized_env>/ccmenu?token=<authentication_token>` — succeeds as expected.
3. Issue `GET /api/stacks/<other_owner>/<other_repo>/<other_env>/ccmenu?token=<authentication_token>` using the *same* token, where `<other_owner/repo/env>` is a stack the client is not scoped to.
4. Because `CCMenuController#stack` calls `Stack.from_param!` (unscoped) rather than `stacks.from_param!` (scoped), step 3 returns `200 OK` with the unauthorized stack's XML status (build status, lock reason, last build time), instead of the expected `403 Forbidden`/`404 Not Found` that `StacksController#show` would return for the same scoped client (compare with `test/controllers/api/stacks_controller_test.rb:217-223`, which enforces the opposite behavior for `StacksController#index`).
