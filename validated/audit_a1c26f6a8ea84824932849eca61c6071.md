### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but the write target (`Stack`/`Repository`) is resolved from the unrelated `repository.full_name` field — allowing cross-organization webhook forgery in multi-App deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the request against based on `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Every event handler that actually *acts* on the payload (push, status, check_suite, and several pull_request handlers) instead resolves the target `Repository`/`Stack` from a completely different JSON field: `payload.dig('repository', 'full_name')`. Because the whole raw body is attacker-supplied and only the *organization used for secret selection* is cross-checked, an attacker who legitimately controls one configured GitHub App/organization's `webhook_secret` can forge a signature that is valid for "their" org while making the payload's `repository.full_name` point at a **different** organization's repository, causing Shipit to sync/deploy/annotate a stack the attacker has no relationship to.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end
```
This binds *only* the HMAC check to the org named in `repository.owner.login`. `Shipit.github(organization:)` looks up per-organization app configs (`lib/shipit.rb#github_app_config`), which is the documented mechanism for hosting multiple GitHub Apps for multiple orgs on one Shipit instance ("Using Multiple Github Applications", `docs/setup.md`), each with its own independent `webhook_secret`.

Once the signature check passes, `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers, all of which derive the affected repository/stack via `Shipit::Webhooks::Handlers::Handler#repository_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
(see `app/models/shipit/webhooks/handlers/handler.rb`, used by `PushHandler`, `CheckSuiteHandler`, `StatusHandler` via `Commit.where(sha:)`, and PR handlers).

`repository.owner.login` (used for signature/secret selection) and `repository.full_name` (used to pick the acted-upon `Repository`) are two independent JSON keys inside the same attacker-controlled request body — HMAC-SHA1 covers the raw bytes of the whole body, but it says nothing about *internal consistency* between these two fields. Nothing in the controller or handlers verifies that the organization implied by `repository.full_name`'s owner segment matches `repository.owner.login`/the org whose secret validated the signature.

This is the direct structural analog of the disputed finding: two logically-linked authorization facts (whitelist role vs. blacklist role in the original bug; "org whose secret signed this" vs. "org whose repo will be mutated" here) are expected to be kept in lockstep by the caller, but the code only checks one of them and blindly trusts the other — breaking the equality `organization_that_authenticated == organization_of_repository_written`.

### Impact Explanation
In a multi-organization Shipit deployment (explicitly supported and documented), an entity that legitimately owns/administers the GitHub App for **Organization A** (and therefore knows or can compute a valid signature with Org A's `webhook_secret`) can send a POST to `/github/webhooks` with:
- `repository.owner.login = "OrgA"` (so `verify_signature` looks up and validates against Org A's known secret — succeeds), and
- `repository.full_name = "OrgB/target-repo"` (so the handler operates on a stack belonging to Org B, an org the attacker has no access to).

Concretely this enables, without ever touching Org B's actual webhook secret or GitHub credentials:
- Forcing `GithubSyncJob` on Org B's stacks via the `push` event (`PushHandler#process` → `stack.sync_github(expected_head_sha:)`), which can trigger unauthorized deploy pipelines depending on `continuous_deployment` settings on the target stack.
- Injecting forged commit `Status` rows for Org B's commits via the `status` event (`StatusHandler#process` → `commit.create_status_from_github!`), which can be used to satisfy `ci.require` checks and enable an otherwise-blocked merge/deploy on Org B's stack.
- Triggering `RefreshCheckRunsJob`/check-run refresh on Org B via `check_suite`.
- Manipulating Org B's review-stack/pull-request lifecycle (archive/unarchive/label capture) via the `pull_request` handlers.

This crosses the "unauthorized deploy/rollback" and "cross-repository writes" impact bar defined in scope, achieved purely by exploiting the mismatch between the organization bound to the signature check and the organization whose repository is actually mutated — with no access to Org B's `webhook_secret`, `GITHUB_TOKEN`, or any privileged Shipit account.

### Likelihood Explanation
This requires:
1. The host Shipit instance to be configured with **multiple** GitHub Apps for multiple organizations (the documented multi-org config in `docs/setup.md`), and
2. The attacker to control/administer at least one of those configured GitHub Apps/organizations (i.e., know that org's webhook secret) while targeting a stack belonging to a different org on the same instance.

This is a realistic operating mode for shared/hosted Shipit deployments serving several organizations — the exact scenario the multi-org configuration feature is built for — so an "org admin for org A" is a low-privilege, plausible attacker role relative to org B's resources. This mirrors the disputed report's own reasoning: the vulnerability requires two independently-administered entities (Blacklist/Whitelist managers there; separate GitHub App owners here) to not coincidentally coordinate, which the report's authors themselves argued was "highly likely" to occur in practice.

### Recommendation
Cross-validate the two org-identifying fields before dispatching to handlers: derive the organization from `repository.full_name`'s owner segment (or equivalently resolve the `Repository`/`Stack` first) and require it to match the organization used to select the app/secret in `verify_signature`. Reject the webhook (422) if they diverge. Alternatively, avoid using `repository.owner.login`/`organization.login` merely for secret selection—verify the signature against *all* configured secrets whose matching organization also matches the repository being resolved by the handler, so a single successful HMAC match is inherently scoped to the correct organization/repository.

### Proof of Concept
Given a Shipit instance configured (per `docs/setup.md` "Using Multiple Github Applications") with:
```yaml
github:
  orga:
    webhook_secret: secretA   # attacker knows this (owns Org A's GitHub App)
  orgb:
    webhook_secret: secretB   # attacker does NOT know this
```
1. Attacker builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/target-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, raw_body)>` — a signature they can freely generate since they know `secretA`.
3. `WebhooksController#verify_signature` computes `repository_owner => "orga"`, calls `Shipit.github(organization: "orga")`, and validates successfully against `secretA` (`lib/shipit/github_app.rb#verify_webhook_signature`).
4. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `repository_name` reads `"orgb/target-repo"`, resolving `Stack`s under Org B and invoking `stack.sync_github(expected_head_sha: "deadbeef")` — a write against Org B's resources despite the attacker never possessing `secretB`.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
