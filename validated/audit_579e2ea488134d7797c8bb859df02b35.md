The vulnerability claim does not hold. The security-critical guard is `EnvironmentVariables#interpolate`, which explicitly applies `Shellwords.escape` to every substituted variable value before it is spliced into the command string, and this happens regardless of whether the underlying value came from `stack.env`, `deploy_spec`, or `TaskCommands#env`'s `SHIPIT_USER`.

**The binding to check:** "the identity string an authorized user approved to appear in `$SHIPIT_USER`" == "the literal bytes interpolated into the shell argument reaching `PTY.spawn`." This equality is false by design — the code deliberately breaks it via escaping.

**Trace:**
1. `TaskCommands#env` builds `'SHIPIT_USER' => "#{@task.author.login} (#{normalized_author_name}) via Shipit"` where `normalized_author_name` is `ActiveSupport::Inflector.transliterate(@task.author.name)`, both of which are attacker-influenceable via `User#github_user=` [1](#0-0) [2](#0-1) .
2. This env hash flows into `Command.new(command_line, env:, chdir:)` for each step in `shipit.yml` [3](#0-2) .
3. When the command runs, `Command#start` calls `interpolated_arguments`, which calls `interpolate_environment_variables`, which delegates to `EnvironmentVariables#interpolate` [4](#0-3) [5](#0-4) .
4. `EnvironmentVariables#interpolate` does: `argument.gsub(/(\$\w+)/) { |variable| ...; Shellwords.escape(@env.fetch(variable) { ENV[variable] }) }` — every substituted value is passed through `Shellwords.escape` before being spliced into the resulting command string [6](#0-5) .

Because `Shellwords.escape` neutralizes shell metacharacters (backslash-escaping `$`, `(`, `)`, spaces, etc.), a value like `$(reboot)` in `SHIPIT_USER` becomes a shell-escaped literal token when substituted for `$SHIPIT_USER` in a step — it is not re-interpreted as a subshell invocation even if the resulting command line is ultimately handed to a shell. This is exactly what the existing test validates, generically (not specific to `SHIPIT_USER`, but exercising the exact same code path any attacker-controlled env value — including `SHIPIT_USER` — takes): [7](#0-6) .

The `#interpolate_environment_variables coerce nil to empty string` and `escape the variable contents` tests confirm the escaping applies uniformly to whatever value sits in the `env` hash, regardless of its source (stack env, task env, or `SHIPIT_USER`) [8](#0-7) . There is also an existing test specifically confirming `SHIPIT_USER` construction from a hostile-looking name is limited to transliteration, not sanitization bypass, and the downstream escaping (not the transliteration) is what neutralizes shell metacharacters: [9](#0-8) .
