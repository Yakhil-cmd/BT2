### Title
`OpenedHandler#provision?` operator precedence bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` intends to require `review_stacks_enabled == true` before consulting any `provisioning_behavior`, but Ruby's `&&`/`||` precedence makes `review_stacks_enabled` only gate the `allow_all?` branch. The `allow_with_label?` and `prevent_with_label?` branches are evaluated independently of `review_stacks_enabled`, so a repository with review stacks disabled will still provision a stack if the PR carries (or omits) the configured label.

### Finding Description
Binding claimed: `review_stacks_enabled == true` is required before any `provisioning_behavior` branch is consulted.

Actual code:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

So with `review_stacks_enabled = false`, `provisioning_behavior = :allow_with_label`, `provisioning_label_name = 'pull-requests-label'`, and the PR opened with that label present in `pull_request.labels`, the second disjunct alone (`allow_with_label? && pull_request_has_provisioning_label?`) evaluates true, making `provision?` true and bypassing the intended `review_stacks_enabled` gate entirely. The same applies to `prevent_with_label?` with the label absent.

`respond_to_pull_request_opened?` only checks `params.action == "opened" && provision?` [2](#0-1) , then `process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [3](#0-2) , which creates a `Stack`/`ReviewStack` regardless of `review_stacks_enabled`. Newly created review stacks start `deprovisioned` and `awaiting_provision: true` (`assert_pending_provision` in the existing tests confirms this state) [4](#0-3) . The background queue `ReviewStackProvisioningQueue.work` picks up any `ReviewStack` with `awaiting_provision: true` and `deprovisioned` status and calls `stack.provisioner.provision?` then `stack.provision` [5](#0-4) , with no re-check of `review_stacks_enabled` at that stage.

No existing guard prevents this: signature verification (`verify_signature`/`GitHubApp#verify_webhook_signature`) authenticates that the webhook came from GitHub for that repository, but it does not enforce `review_stacks_enabled`; that check is supposed to live entirely in `provision?`, which is broken by the precedence bug. `ExplicitParameters` only validates payload shape, not business authorization. No model validation on `Repository`/`Stack` blocks stack creation when `review_stacks_enabled` is false. The existing test suite for `OpenedHandler` never exercises `review_stacks_enabled: false` combined with `allow_with_label`/`prevent_with_label` (all such tests leave `review_stacks_enabled` at its default `true`) [6](#0-5) , so this gap is untested and unnoticed.

The attacker's exact action: open a pull request (or push a branch and let GitHub emit the `opened` webhook) against a repository whose owner/admin has configured `review_stacks_enabled = false`, `provisioning_behavior = :allow_with_label`, `provisioning_label_name = 'pull-requests-label'`, while attaching that label to the PR (attacker can label their own PR if they have write access to add labels, or the label may be attachable by anyone with triage/write permission depending on repo settings — in either case this requires no Shipit credentials, only ordinary GitHub PR/label permissions on that repository). GitHub sends the signed `opened` webhook as normal (no forged signature needed), Shipit processes it, and a `ReviewStack` is created and enters the provisioning queue despite the repository having opted out of review stacks.

### Impact Explanation
A stack is materialized (created and eventually provisioned via `ReviewStackProvisioningQueue.work` → `stack.provision`) for a repository that explicitly disabled review stacks (`review_stacks_enabled = false`). This is a tenant/repository-boundary violation: the repository owner's configuration is silently overridden by a PR author's label choice. Depending on what `provision`/deployment hooks do for that repository (running provisioning commands, deploying infrastructure, invoking CI), this can result in unwanted infrastructure being created and unwanted commands executing for a repo whose maintainers explicitly opted out — matching the "record/stack written for a repository that did not authenticate that action" category. This is repeatable per PR/label toggle and is not scoped to a single stack; it applies to every PR opened against any repository with this specific configuration combination.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` and `review_stacks_enabled = false` — an unusual but plausible administrative configuration (e.g., an operator disabling review stacks broadly while leaving label-based behavior configured, expecting it to be dormant). The attacker needs only standard GitHub permissions to open a PR and attach the configured label (or, for `prevent_with_label`, to simply not attach it) — no Shipit secrets, sessions, or API tokens are required. This is a code-level logic bug (not attacker-specific timing), so it is deterministic and fully repeatable once the configuration precondition holds.

### Recommendation
Fix operator precedence with explicit grouping so `review_stacks_enabled` gates all three behavior branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the equivalent fix to `ReopenedHandler` and any other handler (`labeled_handler.rb`, `unlabeled_handler.rb`) that repeats this pattern, since `review_stacks_enabled` gating should be checked there as well.

### Proof of Concept
Minitest in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (illustrative; add as a new case):
```ruby
test "does not create stacks for repos with review_stacks disabled even when allow_with_label label is present" do
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false
  repository.provisioning_behavior = :allow_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding assertion before fix: `repository.review_stacks_enabled == false` yet `Shipit::Stack.count` increases and the created stack's `awaiting_provision?` is `true` (matching `assert_pending_provision`), demonstrating `provision?` returned `true` despite `review_stacks_enabled == false`. After applying the recommended fix, the same test asserts `Shipit::Stack.count` does not change, restoring `review_stacks_enabled == false` ⇒ no provisioning for any `provisioning_behavior`.

    def work
      queued_stacks.find_each(&method(:provision))
    end

    def queued_stacks
      @queued_stacks ||= Shipit::ReviewStack
                         .with_provision_status(:deprovisioned)
                         .where(awaiting_provision: true)
    end

    private

    def provision(stack)
      if stack.provisioner.provision?
        stack.provision
      else
        Rails.logger.info(
          "Putting review ReviewStack<#{stack.id}> back into the provisioning queue - #provision? was falsey."
        )
      end
    end
