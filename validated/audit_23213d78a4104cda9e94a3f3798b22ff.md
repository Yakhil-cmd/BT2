### Title
`StatusHandler#process` writes CommitStatus rows by global SHA lookup with no repository/organization scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)`, an unscoped, database-wide lookup, and then writes a `CommitStatus` from attacker-controlled `state`/`description`/`target_url`/`context` fields onto whatever commit(s) match that sha. Unlike `PushHandler`, which scopes its work through `stacks` (derived from the payload's `repository.full_name`), `StatusHandler` never checks that the matched commit's `stack.repository` corresponds to the organization whose webhook signature was verified.

### Finding Description
The broken binding is: `commit.stack.repository.owner == repository_owner_verified_by_signature` should hold for every `CommitStatus` created from a webhook, but the code never establishes or checks this equality.

Path:
1. `WebhooksController#verify_signature` picks the `GithubApp` config keyed by `params.dig('repository','owner','login')` (i.e., whatever the JSON body claims) and validates `X-Hub-Signature` against that org's `webhook_secret` [1](#0-0) [2](#0-1) . This only proves the bytes were signed by *some* org whose secret matches the org name embedded in the very same attacker-controlled JSON - it does not prove any specific commit sha belongs to that org.
2. `WebhooksController#create` dispatches purely by event type header (`X-Github-Event: status`), not by repository, to `StatusHandler.call(params)` [3](#0-2) .
3. `StatusHandler`'s param schema only requires `sha`, `state`, and optional description/target_url/context/branches - it never requires or reads `repository` [4](#0-3) .
4. `StatusHandler#process` looks up commits **globally by sha alone** and writes a status to each match: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . Compare with `PushHandler`, which correctly scopes to `stacks` derived from the payload's `repository.full_name` before acting [6](#0-5) , and with the `Handler` base class, which provides exactly this scoping mechanism (`stacks`/`repository_name`) that `StatusHandler` simply does not use [7](#0-6) .
5. `create_status_from_github!` then unconditionally records a `Status`/`CommitStatus` with attacker-supplied `state`, `description`, `target_url`, `context` [8](#0-7) .

Exploit: attacker legitimately administers GitHub org A, which is installed/configured in Shipit with its own `webhook_secret` (a realistic multi-tenant Shipit deployment keys `GithubApp` config per organization, per `Shipit.github(organization: repository_owner)`). Attacker crafts a `status` event JSON body with `"repository": {"owner": {"login": "orgA"}}` (so `verify_signature` resolves and validates against org A's secret) and `"sha": "<sha of a real, public commit in org B's tracked repo/stack>"`, with arbitrary `state`, `description`, `target_url`. Attacker computes the HMAC-SHA1 signature using org A's own webhook secret (which they legitimately possess) and POSTs to `/webhooks`. The signature check passes (org A's bytes, org A's secret). `StatusHandler` then matches org B's commit purely by sha and writes the forged status onto it - a payload authenticated for org A mutates a record belonging to org B's stack, breaking repository scope.

Existing guards do not prevent this: `verify_signature` authenticates the byte string against the organization *named in the payload itself*, not against the resulling record's actual owner; `ExplicitParameters` schema for `StatusHandler` doesn't even require/validate a `repository` field to cross-check; and there is no `Repository`/`Stack` ownership check anywhere in `StatusHandler#process`.

### Impact Explanation
This is a payload authenticated for one repository/organization (A) mutating another organization's (B) stack data - specifically writing arbitrary `state`/`description`/`target_url`/`context` into a `CommitStatus` on a commit belonging to org B's stack. Since Shipit uses commit status/CI state to gate deploy eligibility (`Commit#deployable?`, `Commit#blocked?`, continuous delivery scheduling) [9](#0-8) , an attacker can poison org B's CI/deploy-gating status (e.g. force a `success` state on a commit that never actually passed CI, or force `failure`/blocking states to sabotage deploys), affecting a tenant they do not control. This is repeatable against any commit sha the attacker can discover from any tracked repository's public history, across arbitrary organizations, matching the "payload for one repository mutating another's stack/commit" Critical category.

### Likelihood Explanation
Preconditions: a multi-tenant Shipit deployment where different organizations have distinct GitHub App / webhook configurations (each with its own `webhook_secret`), and the attacker legitimately controls one such organization (or otherwise can produce a validly-signed request for some org recognized by `Shipit.github`). The attacker needs no access to org B's secrets, no Shipit session, and no knowledge beyond org B's public commit SHAs (which are typically discoverable from public GitHub history). Cost is a single crafted HTTP POST; the attack is fully repeatable and scriptable against any known sha.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the stacks/repository derivable from the verified organization (mirroring `PushHandler`'s use of `stacks`), e.g. resolve commits via `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })` or equivalently `Commit.where(sha: params.sha, stack: stacks)`, so a status is only ever attached to a commit whose stack's repository matches the repository/organization that was cryptographically verified for this request. Reject or ignore matches outside that scope.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status from org A cannot write a status onto a commit belonging to org B's stack" do
  org_b_commit = shipit_commits(:cyclimse) # fixture belonging to a different stack/org than :shipit
  org_a_repository_params = { 'repository' => { 'full_name' => 'shopify/shipit-engine',
                                                  'owner' => { 'login' => 'shopify' } } }

  body = {
    'sha' => org_b_commit.sha,
    'state' => 'success',
    'description' => 'forged by org A',
    'target_url' => 'https://evil.example.com'
  }.merge(org_a_repository_params).to_json

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature verified as org A

  assert_no_difference -> { org_b_commit.statuses.count } do
    post :create, body:, as: :json
  end
end
```
Assert both sides of the equality: `org_b_commit.stack.repository.owner` must equal the organization verified by `verify_signature` (`'shopify'`/org A) for a status to be written; currently they diverge (`org_b_commit`'s real owner != `'shopify'`) yet a `Status` is still created, proving the vulnerability.
