### Title
Unbounded `proof: Vec<Vec<u8>>` in `remote_proxy`/`remote_proxy_with_registered_proof` is not weighed proportionally to its size, allowing a signed extrinsic to spend disproportionate CPU on `StorageProof::into_memory_db`/`read_trie_value` for a fixed weight charge - (File: pallets/remote-proxy/src/lib.rs)

### Summary
`Pallet::remote_proxy` and `Pallet::remote_proxy_with_registered_proof` charge a fixed, benchmarked weight (`WeightInfoOf::<T, I>::remote_proxy()` / `remote_proxy_with_registered_proof()`) that does not scale with the size of the caller-supplied `proof: Vec<Vec<u8>>` field of `RemoteProxyProof::RelayChain`. Since `sp_trie::StorageProof::new(proof).into_memory_db(...)` and `sp_trie::read_trie_value` cost is proportional to the number/size of proof nodes supplied, a signed account can submit a proof filled with the maximum number of large, valid-looking (but useless) nodes permitted by the extrinsic length limit, forcing the runtime to hash/insert all of them into the in-memory trie DB while paying only the benchmark-derived fixed weight.

### Finding Description
`Pallet::remote_proxy` is declared with `#[pallet::weight(...)]` returning `WeightInfoOf::<T, I>::remote_proxy().saturating_add(...).saturating_add(di.call_weight)` [1](#0-0)  — a constant benchmarked weight plus the inner call's weight, with no term dependent on `proof.len()`. The same pattern applies to `remote_proxy_with_registered_proof` [2](#0-1) .

`do_remote_proxy` takes the untrusted `proof` vector directly from extrinsic input and builds a `MemoryDB` from it, then walks it with `read_trie_value`: [3](#0-2) 
`StorageProof::new(proof).into_memory_db::<RemoteHasherOf<T, I>>()` hashes and inserts every byte blob the caller supplied into the memory trie DB — this cost is linear in the total size of `proof`, independent of whether those blobs are ever used by `read_trie_value`'s traversal from `storage_root`. Nothing in the pallet enforces a `MaxEncodedLen`/bounded size on `proof: Vec<Vec<u8>>` inside `RemoteProxyProof::RelayChain` [4](#0-3) ; the only implicit bound is the runtime's global extrinsic/block length limit.

The benchmark that produces the fixed weight uses a minimal, realistic proof generated by `T::RemoteProxy::create_remote_proxy_proof` for a single existing proxy definition [5](#0-4) , i.e., a small number of trie nodes reflecting an actual short proof path. It does not attempt to measure the worst case of a maximally sized `proof` vector filled with junk nodes. Because `#[pallet::weight]` uses this constant regardless of the actual submitted `proof` size, an attacker can submit a `proof` close to the maximum allowed extrinsic length, all populated with valid RLP/SCALE-decodable-looking node blobs (they don't need to be reachable from `storage_root` — `into_memory_db` inserts unconditionally), while paying the same declared weight as the benchmarked minimal case.

Existing protections that partially limit but do not close the gap:
- `ensure_signed(origin)` only checks the caller is a real signed account — does not limit proof content/size [6](#0-5) .
- Block/extrinsic length limits (`frame_system::limits::BlockLength`) bound the total proof size but only to megabyte-scale, still allowing a large, weight-underpriced payload per extrinsic, and the length-based transaction fee compensates for bandwidth/storage cost, not for the CPU cost of trie-node hashing done inside the pallet's logic.
- There is no explicit cap on the number of proof nodes or total proof bytes in the pallet's `Config` (e.g., no `MaxProofNodes` or `MaxProofSize` bound), unlike typical bounded-vec patterns used elsewhere in the codebase for user input.

### Impact Explanation
Every accepted `remote_proxy`/`remote_proxy_with_registered_proof` extrinsic with an inflated but structurally-valid `proof` performs `MemoryDB` insertion/hashing work proportional to the proof size while being billed a fixed weight benchmarked against a much smaller, realistic proof. Multiple such extrinsics packed into a block (up to the block length limit) can push actual block execution time well past the time budget implied by the weight-derived block weight limit, causing block-production slowdown on the parachain hosting `pallet-remote-proxy` (deployed on asset-hub-kusama per `system-parachains/asset-hubs/asset-hub-kusama/src/lib.rs`).

### Likelihood Explanation
The precondition is simply having a signed account able to submit extrinsics (unprivileged), and being able to compute a `proof: Vec<Vec<u8>>` filled with SCALE/StorageProof-decodable node bytes of near-maximal length under the block/extrinsic length limits — no valid trie root, cryptographic secret, or governance access is required, since node blobs are inserted into the `MemoryDB` unconditionally regardless of trie connectivity. `read_trie_value` will simply fail to find the key afterward (`Error::InvalidProof`), but the CPU cost of building the `MemoryDB` from a maximal `proof` has already been paid by that point. This is straightforward and fully repeatable each block.

### Recommendation
Scale the declared weight of `remote_proxy` / `remote_proxy_with_registered_proof` by the size of `proof` (e.g., benchmark cost per KB of proof and add `proof_size * PER_BYTE_WEIGHT` to the declared weight), and/or enforce a hard cap on the number/total size of proof nodes accepted (e.g., a `MaxProofSize`/`MaxProofNodes` config bound checked before calling `into_memory_db`), rejecting oversized proofs with a dedicated error before doing any hashing work.

### Proof of Concept
Rust benchmark/fuzz plan:
1. Build a `RemoteProxyProof::RelayChain { proof, block }` where `proof` is a `Vec<Vec<u8>>` filled with N entries of random bytes each close to the max single-field size, sized so the total SCALE-encoded extrinsic approaches (but stays under) the runtime's `BlockLength` normal-class limit.
2. Register a matching `block`/`storage_root` pair in `BlockToRoot` (as a signed account would via a legitimate anchor) so the call passes the `UnknownProofAnchorBlock` check and reaches `StorageProof::new(proof).into_memory_db(...)`.
3. Measure wall-clock time of `Pallet::<T,I>::remote_proxy` executing this call vs. the benchmarked weight-derived time budget (`WeightInfoOf::<T,I>::remote_proxy()` converted to a time bound via the runtime's `WEIGHT_REF_TIME_PER_MILLIS`).
4. Assert: `actual_execution_time_ms > declared_weight_time_budget_ms * SAFETY_MARGIN`, demonstrating the fixed weight underestimates true cost as `proof.len()` grows, while the call is still accepted (`Error::InvalidProof` may ultimately be returned, but only after the costly `into_memory_db` insertion completes).
