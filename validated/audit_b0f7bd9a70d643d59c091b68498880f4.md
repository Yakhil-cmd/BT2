### Title
CCMenu API endpoint ignores per-stack ApiClient scoping, allowing a stack-scoped read token to read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target `Stack` directly from the request parameter (`Stack.from_param!(params[:stack_id])`) instead of going through the standard `stacks`/`stack` scoping helpers defined in `Shipit::Api::BaseController`, which restrict lookup to `current_api_client.stack_id` when the authenticating `ApiClient` is scoped to a single stack.

### Finding Description
Every other API controller in the engine authorizes stack access via `Shipit::Api::BaseController#stacks` and `#stack`: [1](#0-0) 
This enforces the binding: `ApiClient.stack_id` (the stack the token authorizes) == `params[:stack_id]` (the stack the request touches), by filtering the `Stack` relation through `Stack.where(id: current_api_client.stack_id)` before resolving the requested `stack_id`.

`CCMenuController` overrides `stack` and bypasses this relation entirely: [2](#0-1) 
It only checks `require_permission :read, :stack` (a scope-name check via `ApiClient#check_permissions!`, which merely verifies the string `"read:stack"` is present in the permission list, independent of which stack it applies to): [3](#0-2) 

The authentication step for this endpoint also allows passing the token via a query-string parameter (`params[:token]`) instead of only via HTTP Basic Auth: [4](#0-3) 

The `ApiClient` model supports being scoped to a single stack (`belongs_to :stack, optional: true`), and `ApiClientsController#create` lets any authenticated Shipit user create an `ApiClient` with `read:stack` permission via the standard settings UI: [5](#0-4) 
Because the create form only permits `:name` and `permissions`, `stack_id` is not settable there, so in the current UI flow-scoped tokens actually only originate through model-level `stack_id` assignment (e.g. `ApiClient.create!(stack: some_stack, ...)`, which is a supported and documented `belongs_to` association). Regardless of how a stack-scoped token comes to exist, `CCMenuController` never respects that scoping: any valid token with `read:stack` permission — no matter which stack it was minted for — can be replayed with an arbitrary `stack_id` in the URL to read build state (`lastBuildStatus`, `activity`, `lock` state, etc.) for *any* stack in the installation, including stacks the token holder was never granted read access to.

### Impact Explanation
This breaks the "stack a token authorizes vs. stack it touches" binding described in scope. A token intended to be embedded, unauthenticated, in a CI dashboard/build-monitor widget for one stack (the entire purpose of the CCMenu XML feed, which is designed to be consumed by tools like CCMenu without further login) can be reused to enumerate and read the deployment/build status of arbitrary other stacks in the Shipit instance — including private or access-restricted stacks — bypassing the intended per-token stack restriction. This matches the in-scope High-impact category "unauthenticated read of stack state."

### Likelihood Explanation
Exploitation requires possessing any single valid CCMenu/API token with the `read:stack` permission (e.g., one legitimately obtained by the attacker for a stack they do have access to, or one leaked/embedded in a public CI dashboard as is standard practice for CCMenu feeds). No additional credentials, GitHub identity, or session are required beyond that one token; the only action needed is changing `stack_id` in the request. Given CCMenu URLs are explicitly designed to be embedded in third-party, unauthenticated tooling, likelihood of token exposure/reuse is realistic.

### Recommendation
Make `CCMenuController#stack` reuse the base `stacks`/`stack` scoping (i.e., `stacks.from_param!(params[:stack_id])`) so that a stack-scoped `ApiClient` can only resolve the stack it is bound to, consistent with every other API controller.

### Proof of Concept
1. Admin creates (or the engine host application creates) an `ApiClient` scoped to `stack: stack_a` with `permissions: ['read:stack']` (supported by the `belongs_to :stack, optional: true` association on `ApiClient`).
2. This token is embedded in a public CI dashboard widget for `stack_a`'s CCMenu feed, e.g. `GET /api/stacks/stack_a/ccmenu.xml?token=<token>`.
3. An unprivileged party who obtains that token requests `GET /api/stacks/stack_b/ccmenu.xml?token=<token>` for an unrelated `stack_b`.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than `stacks.from_param!(...)`, the `current_api_client.stack_id` restriction to `stack_a` is never enforced, and the request succeeds, returning `stack_b`'s build/lock status.
