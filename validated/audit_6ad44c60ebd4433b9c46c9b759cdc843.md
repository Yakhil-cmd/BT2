### Title
`StackStxOp.sender` is bound to an unauthenticated `PreStxOp.output` claim, not to the Bitcoin key that actually spends the referenced UTXO - (File: `stackslib/src/chainstate/burn/operations/stack_stx.rs`)

### Summary
`StackStxOp::get_sender_txid` only enforces that the tx's first input references `vout == 1` of *some* prior transaction; the identity used as `StackStxOp.sender` comes from that prior transaction's `PreStxOp.output` field, which is never checked against the key that actually signs/spends that output. An attacker can broadcast their own `PreStxOp` naming an arbitrary victim `StacksAddress` in output 0 while keeping output 1 payable to themselves, then spend output 1 with their own key to build a `StackStxOp` whose `sender` resolves to the victim - all funded and signed entirely by the attacker's own Bitcoin UTXOs.

### Finding Description
The equality that must hold is:

`op.sender == StacksAddress(actual Bitcoin key that signs the input spending txid:vout=1)`

Tracing the code:
- `PreStxOp::parse_from_tx` (`stackslib/src/chainstate/burn/operations/stack_stx.rs:74-144`) sets `output = outputs[0].address...try_into_stacks_address()`. This is decoded purely from the destination script of output 0 - **there is no check that this address corresponds to any key used by the transaction's own inputs**. Anyone paying the Bitcoin fee can put any `StacksAddress` there.
- `StackStxOp::get_sender_txid` (`stackslib/src/chainstate/burn/operations/stack_stx.rs:232-247`) only verifies `vout == 1` on the tx's first input and returns the referenced prior `txid`. It performs no signature/key check.
- `Burnchain::classify_transaction` (`stackslib/src/burnchains/burnchain.rs:929-963`) resolves that `txid` via `pre_stx_op_map` / `burnchain_db.find_burnchain_op` (`stackslib/src/burnchains/db.rs:783-804`, a pure txid lookup with no key linkage) and takes `sender = &pre_stack_stx.output` directly, then calls `StackStxOp::from_tx(..., sender, ...)`.
- The resulting `StackStxOp.sender` is fed straight into `StacksChainState::process_stacking_ops` (`stackslib/src/chainstate/stacks/db/blocks.rs:4077-4130`), which calls `tx.run_contract_call(&sender.clone().into(), ...)` invoking `stack-stx` in the active PoX contract **with `tx-sender` set to this unauthenticated address** - no Stacks-level signature from that principal is ever checked in this burnchain-op path.

Exploit flow: attacker crafts `PreStxOp_A` with `output[0] = victim_address` (arbitrary, no proof of key ownership required) and `output[1]` payable to an address the attacker controls. Attacker later spends `output[1]` (their own UTXO, their own valid Bitcoin signature) as input 0 of a `StackStxOp` tx, setting `reward_addr` (from that tx's own output 0) to an address the attacker controls. `get_sender_txid` accepts this (vout==1 satisfied); `find_burnchain_op` resolves it to `PreStxOp_A`; `sender = victim_address` is produced and passed to `stack-stx` as `tx-sender`, locking the victim's STX (if unlocked and not already stacking) with rewards flowing to the attacker's chosen address.

Existing guards do not prevent this:
- `vout == 1` check only constrains *which* output index is spent, not *whose* key spends it.
- `find_burnchain_op` / `pre_stx_op_map` lookups are txid-keyed only; Bitcoin correctly enforces that the attacker can only spend a UTXO they hold the key for (`output[1]`), but nothing ties that key to `output[0]`'s address, which is what becomes `sender`.
- `pox-4.clar`'s `stack-stx` only checks balance/state of `tx-sender` and validates a `signer-key` authorization over `pox-addr`/cycle/amount - it never authenticates that `tx-sender` (the victim) approved this action; that authentication was supposed to happen at the burnchain layer and does not.

### Impact Explanation
The victim's unlocked STX gets locked into stacking without their consent (temporary freezing of staked STX for `num_cycles`), and the PoX/BTC rewards for that commitment accrue to a `reward_addr` chosen entirely by the attacker (theft of stacking rewards that should have gone to/been controlled by the legitimate STX holder). This is repeatable against any account with unlocked STX and no existing stacking/delegation state, at the cost of only Bitcoin transaction fees to the attacker. This matches the Critical category ("theft ... of ... sBTC/BTC rewards", "temporary freezing of staked STX", "an unsigned stacking action").

### Likelihood Explanation
Preconditions: victim must have unlocked STX and not already be stacking/delegating (`is-none (get-stacker-info tx-sender)` and `is-none (get-check-delegation tx-sender)` in pox-4/pox-5). No prepare-phase restriction blocks this - it can be done in any reward cycle. Attacker cost is only Bitcoin tx fees for two transactions (`PreStxOp` + `StackStxOp`), fully repeatable against any number of victim addresses meeting the precondition. Feasibility is high since it requires no compromise of any key beyond the attacker's own.

### Recommendation
Cryptographically bind `PreStxOp.output` to the actual signer of the transaction (e.g., require that the address encoded in `PreStxOp.output` match a hash of the public key used in the `PreStxOp`'s own input(s), or require the follow-up op's spending key to match the address recorded in `PreStxOp.output`) before accepting `sender` from `PreStxOp.output` in `classify_transaction`.

### Proof of Concept
Rust integration test plan (extending `stackslib/src/burnchains/tests/db.rs` patterns):
1. Construct `pre_stx_op_victim`: a `BitcoinTransaction` with opcode `PreStx`, `outputs[0].address` = victim's legacy address, `outputs[1].address` = attacker-controlled address, inputs funded/signed by the attacker only.
2. Construct `stack_stx_op_attacker`: opcode `StackStx`, `inputs[0].tx_ref = (pre_stx_op_victim.txid, 1)`, signed only by the attacker's key for that UTXO.
3. Feed both through `Burnchain::classify_transaction` / `BurnchainDB::get_blockstack_transactions`.
4. Assert (documenting the break): `parsed_stack_stx_op.sender == victim_address` while the Bitcoin input's signing key corresponds to the attacker, i.e. assert `parsed_stack_stx_op.sender != attacker_stacks_address_derived_from_signing_key` is **false** in current code (the sender equals victim, not the actual UTXO controller) - demonstrating `op.sender != StacksAddress(actual signer of input 0)`.

    pub fn get_sender_txid(tx: &BurnchainTransaction) -> Result<&Txid, op_error> {
        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!("Invalid tx: StackStxOp must spend the second output of the PreStxOp");
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }

    pub fn find_burnchain_op<B: BurnchainHeaderReader>(
        &self,
        indexer: &B,
        txid: &Txid,
    ) -> Option<BlockstackOperationType> {
        let qry = "SELECT DISTINCT op FROM burnchain_db_block_ops WHERE txid = ?1";
        let args = params![txid];

        let ops: Vec<BlockstackOperationType> =
            query_rows(&self.conn, qry, args).expect("FATAL: burnchain DB query error");
        for op in ops {
            if indexer
                .find_burnchain_header_height(&op.burn_header_hash())
                .expect("FATAL: burnchain DB query error")
                .is_some()
            {
                // this is the op on the canonical fork
                return Some(op);
            }
        }
        None
    }
