### Title
Attackers can DOS multi-asset AA responses by poisoning one payment message, causing the entire response to bounce - (File: aa_composer.js)

### Summary
`sendUnit()` in `aa_composer.js` builds an AA response unit out of one or more `payment` messages (one per asset). It processes them with `async.eachSeries`, and if a single message fails for any reason, the whole batch is aborted and the entire trigger is bounced instead of only dropping the failing asset payment.

### Finding Description
When an AA response contains multiple `payment` messages (e.g. paying out several different assets to the same recipient), `sendUnit()` iterates over `messages` with `async.eachSeries`: [1](#0-0) 

For every non-base asset it calls `storage.loadAssetWithListOfAttestedAuthors`, then rejects the whole batch via `cb(err)`/`bounce(err)` if the asset is private (`"sending private asset from AA"`) or if `completePaymentPayload` fails (e.g. not enough of that asset available): [2](#0-1) 

The `async.eachSeries` final callback propagates the very first error straight into `bounce(err)`: [3](#0-2) 

`bounce()` then discards **all** of the response's constructed messages (not just the offending asset payment) and instead sends back whatever the trigger originally deposited, minus bounce fees, to `trigger.address`: [4](#0-3) 

This is structurally the same bug class as the OpenQ report: a loop over a set of token/asset payments where a single failing entry (analogous to a blacklisted `USDC` transfer) aborts delivery of every other, otherwise-valid, payment in the same batch instead of skipping/isolating the failure.

An attacker can engineer this failure deterministically because AA balances are shared, mutable state that anyone can top up. If an AA holds (or is later made to hold) a balance of an asset whose transfer will predictably fail when the AA tries to pay it out — e.g. a `spender_attested` asset with no attested authors, or simply an asset for which the AA's own logic will build a `payment` message that gets rejected in `completePaymentPayload`/`loadAssetWithListOfAttestedAuthors` — the attacker only needs to send that asset to the AA address (a normal, unprivileged payment) to poison the AA's balance for that asset. Any later legitimate trigger whose response logic tries to forward/pay out that same asset (e.g. "send back everything you hold" or "sweep all balances" patterns common in exchange/vault-style AAs) will then always hit `bounce(err)`, and the entire response — including any other, perfectly valid, asset/byte payments meant for the legitimate caller — gets reverted back to the trigger's own address instead of reaching the intended recipient.

### Impact Explanation
A legitimate trigger sender who is owed a multi-asset payout from an AA can have that entire payout denied repeatedly by an attacker who only needs to seed the AA with a small amount of a "poison" asset. Because the bounce fully discards the constructed response and refunds the trigger's own deposit instead of executing the AA's intended state transition, this can be used to freeze/deny funds that an AA is otherwise supposed to release to third parties (e.g., in AAs that forward/sweep multiple asset balances to a target address computed from AA state, not equal to `trigger.address`), matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Reachable by any unprivileged actor: sending an asset to an AA address is a normal, permissionless `payment` message that any unit poster can send at any time, with no special privileges. No malicious peer/hub/node behavior is required — the whole exploit path is a single crafted unit followed by a trigger, both within the scope of an ordinary AA-based dApp.

### Recommendation
In `sendUnit()`, do not abort the entire response when one payment message fails validation. Isolate per-asset payment message construction so that a failure building the payment for one asset does not `bounce()` the whole unit; instead, either drop just that asset's message (documented/deterministic behavior) or make the failure condition impossible to trigger with attacker-controlled balances (e.g., validate assets before crediting an AA's balance, or fail closed only for the specific asset being paid rather than for the whole batch in `async.eachSeries`).

### Proof of Concept
1. Attacker sends a normal payment of a `spender_attested` (or otherwise transfer-restricted) asset directly to a target AA address, incrementing that AA's `aa_balances` for the asset (a routine deposit, no special access needed).
2. A legitimate user sends a trigger that causes the AA's oscript logic to include a `payment` message paying out that asset (e.g. as part of "forward all held balances" or "settle multi-asset payout" logic).
3. In `sendUnit()`, when processing that message, `storage.loadAssetWithListOfAttestedAuthors` / the asset-property checks make `completePaymentPayload`/`cb` return an error because there is no attested author for the restricted asset.
4. `async.eachSeries`'s final callback receives this `err` and calls `bounce(err)` (`aa_composer.js` lines 1346-1349), discarding the whole response — including any unrelated, otherwise valid, byte/asset outputs meant for the legitimate user — and refunding the trigger's own deposit back to `trigger.address` instead.
5. Repeating step 1 at any time re-poisons the AA's balance for that asset, letting the attacker deny this payout path indefinitely at negligible cost.
