### Title
Unhandled TypeError in address-definition `'in merkle'` authentifier evaluation crashes node validation - ([File: definition.js])

### Summary
The `'in merkle'` operator in address/asset definition evaluation passes the raw authentifier value straight into `merkle.deserializeMerkleProof()` without checking that it is a string, and without any surrounding try/catch. `deserializeMerkleProof` immediately calls `.split("-")` on its input, which throws a `TypeError` for any non-string value (number, boolean, object, array, null). This mirrors the Fluent Bit CVE-2024-23722 pattern: content is dispatched to a parser based on an assumed type/format without validating that the actual payload conforms, and the parser dereferences/operates on the malformed value, crashing the process.

### Finding Description
In the address-definition evaluator, the `'in merkle'` condition reads the caller-supplied authentifier and deserializes it unconditionally: [1](#0-0) 

`deserializeMerkleProof` assumes its argument is a string and calls `.split("-")` on it with no type check: [2](#0-1) 

Contrast this with the oscript `is_valid_merkle_proof()` function, which explicitly type-checks the proof (`wrappedObject` vs `string`, length limit) before calling `deserializeMerkleProof`, and wraps the actual verification in `try/catch`: [3](#0-2) 

The `'in merkle'` path in `definition.js` has neither of these protections. If an address (or asset) uses an `['in merkle', [...]]` spending-condition clause at a signing path, and the unit author supplies a non-string value for `authentifiers[path]` (e.g. `123`, `true`, `{}`, `null`, or an array), `assocAuthentifiers[path]` will not be a string, `serialized_proof.split` will not exist, and the evaluator throws a `TypeError` synchronously inside the `evaluate()` callback chain used during unit/definition validation — not inside any try/catch in this code path.

### Impact Explanation
Address/asset definitions and their authentifiers are supplied by any unprivileged unit poster (this is exactly the kind of "unit poster"/"address definition and authentifier" surface explicitly in scope). If this exception propagates as an uncaught exception during validation of an incoming unit (rather than being caught by a `try` wrapper elsewhere in the validation call stack), it would crash the Node.js process performing validation. Because full nodes must validate every unit they receive, a single crafted unit containing this construct could crash every full node that attempts to validate it — a network-wide denial-of-service on unit validation/confirmation, analogous to Fluent Bit "crashes and does not restart, logs not delivered" but here "crashes, units not confirmed."

### Likelihood Explanation
Likelihood is difficult to rate with full confidence because I could not verify from the visible code whether an earlier stage of unit/author validation enforces that every `authentifiers[path]` value must be a string before `validateAuthentifiers`/`evaluate()` is invoked. If such a check already exists elsewhere (not found in the reviewed portions of `validation.js`), the non-string case would be rejected earlier and this path would be unreachable with a non-string value, downgrading this to a non-issue. Given the uncertainty, this should be treated as a candidate finding requiring confirmation of the exact caller of `validateAuthentifiers` and how `author.authentifiers` is validated before that call — this is explicitly flagged as an area I could not fully verify.

### Recommendation
- In `definition.js`, before calling `merkle.deserializeMerkleProof(serialized_proof)` in the `'in merkle'` branch, validate `typeof serialized_proof === 'string'` (and bound its length) and fail the definition evaluation (`cb2(false)`) otherwise, matching the guard already present in `formula/evaluation.js`'s `is_valid_merkle_proof`.
- Wrap the `deserializeMerkleProof`/`verifyMerkleProof` call in `definition.js` in a try/catch, converting any exception into a validation failure rather than letting it propagate.
- Audit the full call path from unit/author submission to `validateAuthentifiers` to confirm whether `authentifiers` values are guaranteed to be strings prior to this point; if not, add that guarantee at the earliest possible validation stage.

### Proof of Concept
1. Post a unit that defines (or uses) an address whose definition contains an `['in merkle', [arrAddresses, feed_name, element, min_mci]]` clause at some signing path `p`.
2. As the unit author, sign the unit with `authentifiers[p]` set to a non-string value, e.g. `123` or `{}` (bypassing/patching a wallet library that would normally serialize this as a string).
3. Submit the unit to a full node for validation. During authentifier evaluation, `evaluate()` reaches the `'in merkle'` case, retrieves `assocAuthentifiers[p]` (the non-string value), and calls `merkle.deserializeMerkleProof(nonStringValue)`, which throws `TypeError: serialized_proof.split is not a function`, uncaught in this code path.

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};

	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}
