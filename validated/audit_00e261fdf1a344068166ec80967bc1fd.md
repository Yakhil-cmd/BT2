### Title
Webhook signature verification is keyed off an attacker-controlled organization field, while `StatusHandler` writes commit statuses with no repository/organization scoping at all - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The `writeVarInt` bug is a case of a check being performed with the wrong data — a value is validated/transformed using a narrower type than the one that is ultimately used for the write. The same *class* of bug exists in Shipit's webhook trust boundary: `WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the signature against using an attacker-supplied JSON field (`repository.owner.login` / `organization.login`), while `StatusHandler`, the code that performs the actual write, never re-derives or checks that organization/repository binding — it looks up the target `Commit` purely by `sha`, globally across every stack in the Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the trust anchor (which org's `webhook_secret` to check the signature against) from the payload itself: [1](#0-0) [2](#0-1) 

If that organization's `webhook_secret` is not configured (which the setup docs explicitly describe as *optional*, and which is the actual default in `test/dummy/config/secrets.yml`/`secrets.test.json`), `GitHubApp#verify_webhook_signature` returns `true` unconditionally, without checking any signature at all: [3](#0-2) 

So an unprivileged, unauthenticated caller can send an arbitrary POST to `/webhooks` and pass verification simply by setting `repository.owner.login` (or `organization.login`) to any organization name that Shipit has configured *without* a webhook secret.

Once verification "passes," the event is dispatched to handlers with the raw, attacker-controlled JSON: [4](#0-3) 

Most handlers (`PushHandler`, PR handlers, etc.) at least scope their side effects to a `Repository` looked up via `repository.full_name`: [5](#0-4) 

But `StatusHandler` does not use that scoping at all — it looks up the target `Commit` **globally by `sha`**, with no repository or organization binding whatsoever, and directly writes attacker-supplied `state`, `description`, `target_url`, and `context` onto it: [6](#0-5) 

This write feeds directly into deploy-safety-relevant logic: `Commit#add_status` recomputes `deployable?`-affecting state, fires `deployable_status` hooks, and schedules merges/continuous deployment when the new status is `success`/`pending`: [7](#0-6) 

**Equality that should hold but doesn't:** *organization whose secret authenticated the request* == *organization/repository that owns the commit being written to*. In `StatusHandler`, the right-hand side doesn't exist at all — any commit sha in the entire Shipit installation is writable once any single configured organization lacks a webhook secret.

### Impact Explanation
An attacker who can guess/know a real commit sha belonging to a *different, properly-secured* organization's stack (trivial, since commit shas are public git data, and often visible in Shipit's own UI/API) can forge a `status` webhook event that:
- Claims `repository.owner.login` = an organization configured in Shipit without a `webhook_secret` (bypassing signature verification entirely).
- Sets `sha` = the victim commit's real sha, and `state: "success"`.

This writes a forged "success" CI status onto the victim commit, which can flip `Commit#deployable?` to true and, if `continuous_deployment` is enabled on that stack, trigger `ProcessMergeRequestsJob`/an actual unauthorized deploy of that commit — all without any credential, session, or GitHub write access to the victim's repository. This matches the "unauthorized deploy" impact category.

### Likelihood Explanation
This requires only: (1) the `/webhooks` endpoint being reachable (unauthenticated by design), (2) at least one organization configured in Shipit's `github` config without a `webhook_secret` (explicitly documented as optional, and the shipped default in test/dummy configs), and (3) knowledge of a target commit sha (public information). No GitHub App private key, `webhook_secret`, session, or API token is needed.

### Recommendation
- In `StatusHandler` (and any other handler that mutates state), scope the lookup by the repository derived from `repository.full_name` (as `Handler#stacks` already does), not just by `sha`.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; require a webhook secret to be configured for every organization, or reject/flag events from orgs without one.
- Cross-check that the organization used to select the verification secret actually owns the repository named in the payload before dispatching to handlers.

### Proof of Concept
1. Configure two GitHub orgs in Shipit: `victim-org` (has `webhook_secret` set, hosts a real stack with `continuous_deployment: true`) and `attacker-org` (configured in Shipit but with `webhook_secret` left blank/nil, e.g. as shown in `test/dummy/config/secrets.yml`).
2. Obtain the sha of an existing, undeployed commit on a `victim-org` stack (public git data).
3. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, body:
```json
{
  "repository": { "owner": { "login": "attacker-org" } },
  "sha": "<victim commit sha>",
  "state": "success"
}
```
4. `verify_signature` resolves `repository_owner` to `attacker-org`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb` line 77) — no valid signature required.
5. `StatusHandler#process` finds the victim `Commit` purely by `sha` (no repo/org check) and creates a forged `success` status, potentially triggering an unauthorized deploy via continuous deployment.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
