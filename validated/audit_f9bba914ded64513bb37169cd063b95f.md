### Title
`StatusHandler#process` performs a global `Commit.where(sha:)` lookup with no repository scoping, letting a webhook from repo A write `Status` records onto commits owned by repo B - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire `commits` table and calls `create_status_from_github!` on every match, never calling the inherited `Handler#stacks`/`Handler#repository_name` helpers to scope the query to the repository that signed the webhook. Every sibling handler (`PushHandler`, the `PullRequest` handlers) scopes writes through `stacks`, so `StatusHandler` breaks the same invariant they enforce.

### Finding Description
The binding that should hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` mutated by a webhook. `PushHandler#process` enforces this by first resolving `stacks` (which is derived from `Repository.from_github_repo_name(repository_name)`) and only acting on stacks under that repository: [1](#0-0) 
`Handler#stacks`/`Handler#repository_name` are defined for exactly this purpose: [2](#0-1) 

`StatusHandler#process`, however, queries `Commit` directly by `sha` with no join or filter on repository/stack: [3](#0-2) 

`WebhooksController#verify_signature` only proves that the request was signed by the GitHub App/organization associated with `repository_owner` (`payload.dig('repository','owner','login')`); it does not - and cannot - constrain which `sha` values appear inside the payload body: [4](#0-3) [5](#0-4) 

So an attacker who owns `attacker/repo` and configures (or is granted, per any repo owner) a webhook there can send a legitimately-signed `status` event whose `sha` value is copied from a commit that actually lives in a victim's stack (e.g., a shared open-source commit, a forked repository sharing history, or any sha the attacker learns of, such as from a public PR). Because `Commit.where(sha: params.sha)` is unscoped, it will match the victim's `Commit` row and call `commit.create_status_from_github!(params)` on it, writing a new `Status` row against the **victim's** commit/stack: [6](#0-5) 

This mutates `stack.commits.*.statuses`, which directly feeds `deployable?`/`blocked?`/`status` used for gating deploys: [7](#0-6) 

None of the existing guards prevent this: `verify_signature` validates the *sender's own* organization's signature, not that the payload's `sha`/`repository` pair is consistent; the `ExplicitParameters` schema in `StatusHandler` only validates types (`sha: String`, `state: String`), not ownership; and `drop_unhandled_event` merely checks that a handler exists for the event type. No check anywhere ties the verified `repository_owner` to the `sha` being updated in `StatusHandler`, unlike `PushHandler`, which resolves `stacks` from `repository_name` before touching any record.

### Impact Explanation
A payload correctly authenticated for `attacker/repo` can create/replace a `Status` on a commit belonging to a completely different repository/stack (`victim/repo`) as long as the attacker can produce (or already knows) a matching `sha`. This can flip a victim commit's aggregated `status` (e.g., inject a passing/failing `context`), which is consumed by `deployable?`, `blocked?`, and continuous-delivery scheduling (`schedule_continuous_delivery`), potentially unblocking or blocking a deploy the attacker has no rights to. This matches the "payload for one repository mutating another's stack/commit" Critical category. The attack is repeatable against any commit sha the attacker can discover (public repos, forks, cherry-picked shas), and generalizes across all stacks/tenants sharing the same Shipit instance since the lookup has no tenant boundary at all.

### Likelihood Explanation
Precondition is minimal: the attacker only needs a repository they own (or control a webhook for) that Shipit's `Shipit.github(organization: repository_owner)` recognizes, so `verify_signature` succeeds using that org's legitimate GitHub webhook secret — no Shipit secret, session, or token is required. The attacker must know a `sha` that also exists in a victim stack's `commits` table, which is very feasible for public repositories, upstream/fork relationships, or cherry-picked/rebased commits shared between repos. This is a straightforward, repeatable exploit costing only the ability to send a self-authenticated `status` webhook.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` does: resolve the commit only within `stacks` (i.e., `Commit.where(sha: params.sha, stack: stacks)` or equivalently filter through `Repository.from_github_repo_name(repository_name)`), so a status update can never cross repository boundaries.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — file itself is out of scope for grading but describes the required assertions):
1. Create `stack_victim` under `Repository` `"victim/repo"` and `stack_attacker` under `"attacker/repo"`.
2. Create `commit = stack_victim.commits.create!(sha: "deadbeef...")`.
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"` and `sha = commit.sha`.
4. Call `StatusHandler.call(payload)`.
5. Assert `commit.reload.statuses.count == 1` and the status's `context`/`state` match the injected payload — proving the write landed on `victim/repo`'s commit despite the payload's `repository.full_name` being `attacker/repo`.
6. Contrast with `PushHandler`: build an equivalent push payload with `repository.full_name = "attacker/repo"` targeting `stack_victim`'s branch, call `PushHandler.call(payload)`, and assert `stack_victim` is untouched (`stacks` resolves to `Stack.none` for the mismatched repo), demonstrating the asymmetric scoping between the two handlers.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))

      ].join(' '))
    end
