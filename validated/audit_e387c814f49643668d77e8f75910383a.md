No vulnerability found for this question.

**Reasoning:**

This finding targets `RandKeys` in [1](#0-0) , which is part of the consensus randomness (DKG/weighted-VUF) subsystem, not the transaction admission path (mempool/vm-validator/authenticator/API). Per the boundary conditions, peer-driven scenarios in consensus protocols are explicitly excluded, and `RandShare`/`ProofShare` submissions originate from validator peers in the rand-gen protocol, not from unprivileged transaction, authenticator, or API input.

Independent of scope, the premise is also factually wrong: every consumer of `pk_shares` alongside `certified_apks` already gates on `certified_apks[index].get().is_some()` before trusting the share:

- `Share::verify` explicitly checks `maybe_apk.get()` and bails with "No augmented public key for validator id..." if empty: [2](#0-1) 
- `RandConfig::get_certified_apk` returns `Option<&APK>` via `.get()`, and `build_apks_and_proofs` propagates an error if the APK is missing rather than trusting `pk_shares` directly: [3](#0-2) [4](#0-3) 
- `RandConfig::verify_structural` performs exactly the check the finding calls for — `self.keys.certified_apks[index].get().is_some()` — before any share is treated as valid: [5](#0-4) 

`pk_shares` is only used raw for deriving/augmenting a party's own APK (`get_pk_share` in `derive_apk`), not for accepting proof shares as certified: [6](#0-5) [7](#0-6) 

So the described "corrupting the approval set invariant" scenario does not exist in the code — the invariant is already enforced everywhere pk_shares indices are consumed for share validity, and the code path is outside the required transaction-admission scope.
