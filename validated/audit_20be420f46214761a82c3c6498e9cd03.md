### Title
Cross-organization webhook confusion: signature verified against `repository.owner.login`/`organization.login`, but stack lookup keyed on unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-tenant GitHub App configuration where each organization has its own `webhook_secret` [1](#0-0) . Webhook signature verification selects which organization's secret to check the HMAC against using a field read straight out of the *unverified* JSON body, while every event handler resolves the target `Stack`/`Repository` using a completely different field of that same unverified body. Nothing ties the two fields together, so a payload correctly signed with Org A's secret can name Org B's repository, and Org B's stack will be mutated.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against using `repository_owner`, itself derived from the request body: [2](#0-1) [3](#0-2) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` looks up a per-organization `webhook_secret` from `secrets.github[org]` [1](#0-0) , and `verify_webhook_signature` only proves that whoever sent the payload knows *that organization's* secret [4](#0-3) . It says nothing about which repository the payload's other fields describe.

Once the signature is accepted, `WebhooksController#create` dispatches the same raw params to every handler for the event [5](#0-4) . Every handler resolves the affected `Stack`/`Repository` from a **different** field, `repository.full_name`, without ever re-checking it against `repository.owner.login`: [6](#0-5) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler`, and the pull_request handlers (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`) all follow the same pattern, resolving `Shipit::Repository.from_github_repo_name(params.repository.full_name)` independent of the signature-checked owner [7](#0-6) [8](#0-7) .

The broken binding, stated as an equality that the code fails to enforce:

`organization authenticated by verify_signature (repository_owner) == owner(repository.full_name) used by every Handler#stacks / #repository lookup`

The HMAC computed in `verify_signature` covers the entire `raw_post`, so the JSON body as a whole is authentic for *some* organization's secret - but that only proves "the org named in `repository.owner.login`/`organization.login` produced/authorized this exact byte string," not "the org named in `repository.full_name` is the same org." Since GitHub itself always sends these two fields consistently for a real webhook, this gap is only exploitable by whoever can legitimately obtain a *valid signature* for one organization's webhook secret (e.g. an attacker who configures their own GitHub App/organization on Shipit, matching the documented multi-org secrets schema in `secrets.github`) and then crafts a payload naming a victim organization's repository in `repository.full_name` while keeping `repository.owner.login`/`organization.login` set to their own org.

### Impact Explanation
An attacker who controls one tenant/organization onboarded to a multi-org Shipit instance can forge a validly-signed webhook (signed with their own org's secret) whose `repository.full_name` points at a stack belonging to a different, victim organization on the same instance. Depending on handler, this can:
- Force `PushHandler` to trigger `Stack#sync_github` on a victim's stack with an attacker-chosen `after` SHA [9](#0-8) , causing the app to sync/deploy commits the attacker names for a repository they do not own.
- Force pull_request handlers to archive/unarchive review stacks or mutate merge/label state for a victim's repository, since `repository` and `stack` resolution in those handlers is entirely driven by the unchecked `full_name` field [10](#0-9) .

This is a cross-repository/cross-tenant write triggered without the attacker holding any credential for the victim organization, matching the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (the `github_organizations` multi-tenant secrets schema) and requires the attacker to control one of those onboarded organizations/GitHub Apps (so they legitimately possess that organization's `webhook_secret`). Given that assumption, forging the cross-repository payload is trivial - it's just editing one JSON field before computing/sending the HMAC that the attacker is already entitled to compute. Likelihood is Low/Medium: it depends on a specific deployment topology (multi-org single Shipit instance) rather than being exploitable against a single-tenant install, similar in spirit to the source report's requirement of a specific state (deprecated market) before the missing cross-check becomes exploitable.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after, before dispatching to handlers), assert that the organization whose secret validated the signature is the same organization referenced by `params.dig('repository','full_name')` (or `params.dig('repository','owner','login')` compared against `repository_name.split('/').first`). Reject the request (422) if they differ, mirroring how the bad-debt report recommends explicitly gating the alternate path rather than relying on an implicit invariant that "well-formed" payloads keep these fields consistent.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with a distinct `webhook_secret` under `secrets.github`.
2. As the attacker, who legitimately knows `attacker-org`'s `webhook_secret` (e.g., because they administer that GitHub App), build a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(attacker-org-webhook_secret, body)`.
4. POST to `/webhooks` with `X-Github-Event: push` and the computed signature.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the HMAC, so the request passes [2](#0-1) .
6. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [6](#0-5) [9](#0-8) , even though the signature only proved knowledge of `attacker-org`'s secret, not any credential for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
