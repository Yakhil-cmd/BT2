### Title
Pull request label names bypass all environment-variable allowlisting and are injected verbatim as env var names (e.g. `GIT_CONFIG_GLOBAL`) into `ruby`/`bundle` dependency-install subprocesses for review stacks - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the process environment with no allowlist, and this hash flows unfiltered through `TaskCommands#env` → `Command.new(..., env:)` → `Command#unbundled_env` → `PTY.spawn`. Because the review-stack working directory is the attacker's own checked-out PR branch, an attacker who can label their PR and control its `Gemfile`/tree content can set arbitrary environment-variable *names* (their value is always the fixed string `"true"`) such as `GIT_CONFIG_GLOBAL`, which git will resolve relative to the current directory and interpret as a config file — letting the attacker plant a file named `true` in their own repo containing a malicious `core.fsmonitor`/hook directive that git executes when `bundle install` shells out to git.

### Finding Description
The broken binding: `TaskCommands#env` is expected to only expose an allowlisted/known set of environment variables to subprocess execution, i.e. `env.keys ⊆ {known Shipit-defined keys}`. In practice, for review stacks: [1](#0-0) 

merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" } ` into the stack's env with **no key allowlist whatsoever**, unlike the API-triggered paths that go through `EnvironmentVariables#permit`: [2](#0-1) 

`TaskCommands#env` blindly merges this stack env into the task/command environment: [3](#0-2) 

`TaskCommands#install_dependencies` builds `Command.new(command_line, env:, chdir: steps_directory)` for each dependency step (e.g. the auto-discovered `bundle install`), with `chdir` equal to the checked-out PR branch content: [4](#0-3) [5](#0-4) 

The merged env is passed straight into the spawned process: [6](#0-5) 

Labels themselves are captured verbatim from the webhook payload with no name filtering: [7](#0-6) [8](#0-7) 

Exploit flow: on a repo with review stacks enabled (`allow_with_label` or `allow_all`), the attacker (with label-write permission, per the audit's assumed attacker capabilities) opens/labels a PR from a fork whose branch contains: (1) a `Gemfile` with a git-sourced gem (forcing bundler to shell out to `git`), and (2) a file literally named `true` at the repo root containing a malicious global git config (e.g. `[core] fsmonitor = "touch /tmp/pwned"`). The attacker adds a label named `git_config_global` (case-insensitive) to the PR. When Shipit's `TaskCommands#install_dependencies` runs `bundle install` in `steps_directory` (the checked-out PR branch), `GIT_CONFIG_GLOBAL=true` is present in the child's env; git resolves this relative path against the current working directory — the attacker's own checked-out tree — and loads the attacker's config, executing the injected hook/fsmonitor command.

Existing guards do not stop this: `EnvironmentVariables#permit` is only invoked for user/API-driven `env` params (deploys, rollbacks, tasks triggered via controllers), not for `ReviewStack#env`'s label-derived hash; there is no model validation restricting label names beyond what GitHub itself allows.

### Impact Explanation
If exploitable, this results in arbitrary command execution on the Shipit deploy host during dependency installation for a review stack, matching the Critical RCE class (execution via `Command`/`PTY.spawn`). The blast radius is scoped to whichever repository/stack the attacker controls a PR for, but since the deploy host and its credentials (e.g. `GITHUB_TOKEN`) are shared across stacks, RCE on the host is a full compromise, not merely stack-scoped.

### Likelihood Explanation
Preconditions: review stacks must be enabled for the target repository, and the attacker must be able to add a label to their own PR (label-write permission on the repo, as granted by the audit's attacker-capability assumptions) and control the PR branch's tree (fork PR). The rest of the chain (uppercased label→env key, unfiltered merge, `chdir` into attacker content, `bundle install` shelling to git) is deterministic engine behavior with no additional secrets or privileged access required. The one caveat weakening likelihood is that the label-derived value is *always* the literal string `"true"`, not an attacker-chosen string — the attack therefore depends specifically on env vars like `GIT_CONFIG_GLOBAL` where the fixed value `"true"` happens to be a usable (relative-path) value, combined with the attacker being able to name a same-named file in their own tree. This is a narrower, coincidence-dependent primitive than a fully attacker-controlled value, but it is still a concrete, reproducible exploit path given the fully attacker-controlled repository tree and `Gemfile`.

### Recommendation
Apply an explicit environment-variable name allowlist to `ReviewStack#env`'s label-derived hash (e.g. reject/skip label names colliding with sensitive/loader-style variable names, or prefix all label-derived keys with a fixed namespace like `SHIPIT_LABEL_`) before merging into `TaskCommands#env`. Do not let raw, attacker-influenced strings become environment variable *names* that reach `Command`/`PTY.spawn` without going through `EnvironmentVariables#permit` or an equivalent allowlist.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_git_config_global_test.rb
require 'test_helper'

module Shipit
  class ReviewStackGitConfigGlobalTest < ActiveSupport::TestCase
    test "a PR label named git_config_global reaches the install_dependencies subprocess env" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.update!(labels: ["git_config_global"])

      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      command = Shipit::TaskCommands.new(task).install_dependencies.first

      # Binding under test: env["GIT_CONFIG_GLOBAL"] should NOT be attacker-settable via PR labels
      assert_nil command.env["GIT_CONFIG_GLOBAL"], "GIT_CONFIG_GLOBAL should not be settable via pull request labels"
    end
  end
end
```
Before the fix, `command.env["GIT_CONFIG_GLOBAL"]` equals `"true"`, demonstrating the unsanitized label→env binding reaching the `bundle install` subprocess environment used by `Command#start`/`PTY.spawn`.
