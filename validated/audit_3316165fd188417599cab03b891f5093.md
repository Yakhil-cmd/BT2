### Title
Cross-stack commit status injection via unscoped `Commit.where(sha:)` lookup in status webhooks - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by SHA, with no scoping to the repository/stack that the webhook signature was verified for. Because git commit SHAs are content-addressed and preserved across forks/cherry-picks, an attacker who owns any repository tracked by the same Shipit instance can legitimately trigger a correctly-signed webhook that injects a fabricated `success` status onto an identically-shaed commit belonging to a completely unrelated stack, flipping `Commit#deployable?` to true for a victim's commit that never received real CI success.

### Finding Description
The broken binding is: `Commit#status` (used by `deployable?` via `success?`) should equal `Status::Group.compact(self, statuses posted only by the GitHub App-verified sender of *this* commit's own repository)`. In practice it equals `Status::Group.compact(self, statuses whose sha string matches, from ANY verified sender of ANY repository tracked by this Shipit instance)`.

Path:
1. `WebhooksController#verify_signature` looks up the GitHub App config keyed by `repository_owner` (`params.dig('repository','owner','login')`) and checks the HMAC against that org's `webhook_secret` [1](#0-0) . This step is legitimate and does correctly bind the signature to *some* tracked repository/org — but not to the specific commit's owning stack.
2. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1)  — this query is **not** scoped by `stack_id`, `repository`, or any tenant boundary, only by the raw `sha` string.
3. `Commit#status` recomputes from `statuses_and_check_runs` via `Status::Group.compact` [3](#0-2) , and `deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [4](#0-3) .

Exploit flow: attacker owns/controls `attacker/fork` (a legitimate Shipit-tracked stack, satisfying "emit webhooks from a repository they own"). They fork `victim/prod`'s public repository, which — being git — preserves the exact commit SHA for any un-modified commit. They then post a `success` GitHub status (via the ordinary GitHub API, on a commit they legitimately own) on that shared SHA within their own repo. GitHub fires a `status` webhook, correctly signed with `attacker`'s org's `webhook_secret`, which passes `verify_signature`. `StatusHandler#process` then matches `Commit.where(sha: <shared_sha>)`, which returns **both** the attacker's own `Commit` row **and** `victim/prod`'s `Commit` row for the identical SHA (since `Commit` uniqueness/lookup is not scoped to `stack_id`/repository at this call site). Both rows receive the injected `success` status. If `victim/prod`'s commit previously only had a `pending` real-CI status, its `status` recomputes to `success`, `deployable?` flips true, and the commit becomes eligible for deploy via `Stack#next_commit_to_deploy` without the victim's actual CI ever succeeding.

Existing guards do not stop this: `verify_signature` authenticates "a request came from a legitimate repository the app tracks," not "this status belongs to the specific commit's own stack," so it does not close the gap.

### Impact Explanation
An attacker who has onboarded (or forked into) any repository/stack on the same Shipit instance can inject fabricated CI-success statuses onto commits belonging to an unrelated, higher-privilege stack (e.g. `victim/prod`), as long as the SHA is shared (trivial via fork/cherry-pick of public history). This directly satisfies the "payload for one repository mutating another's stack/commit" and "unauthorized deploy" Critical impact categories, since `deployable?` becoming true can unblock `next_commit_to_deploy` and continuous deployment (`schedule_continuous_delivery`) for the victim stack [5](#0-4) . It is repeatable against any stack whose tracked repository shares commit history (forks, mirrors, subtree/cherry-picked shared commits) with a repository the attacker controls.

### Likelihood Explanation
Requires: (1) the attacker owns or controls a repository that is itself tracked as a Shipit stack (or otherwise able to legitimately trigger a correctly-signed webhook, e.g. via "emit webhooks from a repository they own" as stated in the threat model), and (2) a commit SHA shared between that repo and the victim's tracked repo, which is trivially achievable for any public upstream repo via forking. No secrets, no privileged Shipit role, and no GitHub org membership on the victim's side are needed — only the ability to fork a public repo and post a status on one's own commit. This is a low-cost, repeatable attack against any Shipit instance that hosts multiple independently-owned/forked stacks of the same codebase.

### Recommendation
Scope the `StatusHandler#process` lookup by repository, not just SHA — e.g. resolve the target stack(s) from `params.dig('repository','full_name')` (or org/repo id) and constrain `Commit.where(sha: params.sha, stack_id: matching_stack_ids)` before calling `create_status_from_github!`. More generally, any commit lookup keyed only by `sha` in webhook handlers should be scoped to the stack(s) whose configured repository matches the webhook's `repository.full_name`/owner.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status from repo A cannot flip deployable? on an identical-sha commit belonging to repo B" do
  stack_a = shipit_stacks(:cyclimse)     # attacker-controlled stack
  stack_b = shipit_stacks(:shipit)       # victim stack

  shared_sha = 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef'
  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)
  commit_b.statuses.create!(stack_id: stack_b.id, state: 'pending', context: 'ci/travis')

  refute_predicate commit_b.reload, :deployable?

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => stack_a.repository.full_name, 'owner' => { 'login' => stack_a.repository.owner } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  assert_predicate commit_b.reload, :deployable?   # BEFORE fix: true (bug); AFTER fix: should remain false
  assert_includes stack_b.next_commit_to_deploy... # demonstrate downstream deploy eligibility
end
```
This demonstrates the equality `Commit#status(commit_b) == aggregate(statuses posted for commit_b's own stack)` is violated: a status submitted under `stack_a`'s payload leaks into `commit_b`'s (stack_b's) computed status and flips `deployable?`.
