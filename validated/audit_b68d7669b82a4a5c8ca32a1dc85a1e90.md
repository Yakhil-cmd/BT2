### Title
`ReopenedHandler#unarchive?` has the same operator-precedence bug as `OpenedHandler#provision?`, ignoring `review_stacks_enabled` when `provisioning_behavior` is `prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` uses the exact same `&&`/`||` expression as `OpenedHandler#provision?`, and due to Ruby operator precedence it does **not** gate the `prevent_with_label` clause on `repository.review_stacks_enabled`. This means a maintainer/operator who sets `review_stacks_enabled = false` on a repository still has its stacks unarchived (and re-queued for provisioning) via a `reopened` webhook event when `provisioning_behavior` is `:prevent_with_label` and the offending label is absent.

### Finding Description
The claimed binding is: `unarchive? == (repository.review_stacks_enabled && <any provisioning_behavior clause>)`. Tracing the code:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`.

The third disjunct — the `prevent_with_label` branch — never references `review_stacks_enabled` at all. So with `review_stacks_enabled = false`, `provisioning_behavior = :prevent_with_label`, and the provisioning label absent from the PR, `unarchive?` evaluates to `true` regardless of the disabled flag, and `process` calls `stack.unarchive!` [2](#0-1) .

This is byte-for-byte the same flaw already present in `OpenedHandler#provision?` [3](#0-2) , so the premise of the question ("unlike OpenedHandler") is false — `ReopenedHandler` does **not** correctly gate on `review_stacks_enabled`; it inherits the identical bug.

Attacker flow: attacker owns a fork/branch on a repository with the Shipit GitHub App installed (webhooks are genuinely signed by GitHub for real PR events, so `verify_signature`/`GitHubApp#verify_webhook_signature` pass legitimately). Repository is configured with `review_stacks_enabled = false` and `provisioning_behavior = :prevent_with_label`. Attacker opens a PR (creating an archived/no-op stack or one that later gets archived by `ClosedHandler`), ensures the provisioning label is not applied, closes the PR, then reopens it. The `reopened` webhook reaches `ReopenedHandler#process`, `unarchive?` returns `true` due to the precedence bug, and `stack.unarchive!` runs, which (per the existing test suite, e.g. `assert_pending_provision`) sets the stack to `awaiting_provision: true`/`deprovisioned`, causing `ReviewStackProvisioningQueue` to later call `stack.provision`, triggering `stack.provisioner.up` and downstream `Command`/`TaskCommands` execution [4](#0-3) [5](#0-4) .

No existing guard (`drop_unhandled_event`, `ExplicitParameters` schema, `force_github_authentication`, model validations) checks this logical relationship between `review_stacks_enabled` and `provisioning_behavior`; the bug is purely in the boolean expression's precedence.

### Impact Explanation
An attacker who controls only their own PR's label/open/close/reopen state on a repository can force re-provisioning of a review stack (unarchiving it and enqueueing it for `provision`, ultimately invoking the deploy-host command pipeline) even though the repository owner explicitly disabled review-stack provisioning (`review_stacks_enabled = false`). This is a command execution/task-execution path running on infrastructure that should be inert for that repository, matching the "Critical - RCE on the deploy host via Command/PTY.spawn ... or an unauthorized deploy" category, since it is a second (reopen-based) route to the same `TaskCommands#perform`/provisioner invocation described for `OpenedHandler`. It is scoped to the attacker's own repository/PR (no cross-tenant contamination observed), but is fully repeatable by opening/closing/reopening PRs at will.

### Likelihood Explanation
Preconditions: the target repository must have the Shipit GitHub App/webhook installed and configured with `provisioning_behavior = :prevent_with_label` and `review_stacks_enabled = false`. No secrets are needed by the attacker; GitHub itself signs the real webhook for genuine PR state transitions the attacker triggers by manipulating their own PR (open/close/reopen, adding/removing labels). This requires no privileged Shipit role and is trivially repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire decision in both `ReopenedHandler#unarchive?` and `OpenedHandler#provision?`:
```ruby
def unarchive?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` style (for engineer to add):
```ruby
test "does not unarchive stacks when review_stacks_enabled is false, even with prevent_with_label and no label" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = []

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived (review_stacks_enabled=false)"
  assert_not stack.awaiting_provision?, "Expected stack NOT to be queued for provisioning"
end
```
With the current code, `repository.review_stacks_enabled == false` and `unarchive?` still returns `true` (via the `prevent_with_label?` disjunct), so `stack.archived?` becomes `false` and `awaiting_provision?` becomes `true` — the assertions fail, confirming the vulnerability. [6](#0-5)
