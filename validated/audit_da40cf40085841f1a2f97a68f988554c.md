### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the stack that gets mutated is looked up via the independent `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate an incoming webhook against using one payload field (`repository.owner.login` / `organization.login`), while every webhook `Handler` resolves the `Stack`/`Repository` to act on using a *different, independently attacker-controlled* payload field (`repository.full_name`). Because `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatically valid, any organization configured in `secrets.yml` without a webhook secret becomes a skeleton key: an unauthenticated caller can name that org in `repository.owner.login` to skip signature verification entirely, then point `repository.full_name` at a stack that belongs to a completely different (secured) organization.

### Finding Description
`WebhooksController#verify_signature` picks the app config to check the signature with based on the requester-supplied owner field: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no configured `webhook_secret`: [3](#0-2) 

`webhook_secret` is explicitly documented and configured as optional per organization, and the test fixtures for a multi-organization installation show it left blank for both configured orgs: [4](#0-3) [5](#0-4) 

Meanwhile, every event handler resolves the target `Repository`/`Stack` using `repository.full_name` — an entirely separate JSON field from the one used to pick the signing organization: [6](#0-5) 

The equality that must hold for the trust boundary to be sound is: `organization_that_signed(repository.owner.login) == organization_owning(repository.full_name)`. For genuine GitHub-originated webhooks these two always describe the same repository, so the equality holds. But because the endpoint is a plain public HTTP POST target (no session, no `ApiClient` token, no GitHub App key required by the caller), an attacker can submit an arbitrary JSON body directly. By setting `repository.owner.login` (or the fallback `organization.login`) to an org that has no `webhook_secret` configured, `verify_webhook_signature` passes unconditionally regardless of the request body content — including a `repository.full_name` that names a stack belonging to a different, secured organization.

### Impact Explanation
Once signature verification is bypassed this way, any registered handler will act on the attacker-chosen `repository.full_name`:
- `StatusHandler#process` writes a CI status (`commit.create_status_from_github!`) for an arbitrary SHA on the targeted repository's commits: [7](#0-6) 
This can forge a passing/required status context for a commit that never actually passed CI, which — combined with Shipit's required-status/merge-queue logic — can enable an unauthorized deploy or merge of a commit that should have been blocked.
- `PushHandler#process` and `CheckSuiteHandler#process` can likewise be triggered against arbitrary tracked stacks in other organizations: [8](#0-7) [9](#0-8) 

This matches the accepted High/Critical impact category of "an unauthorized deploy, rollback or merge," achieved without any credential, session, or GitHub App key — purely by exploiting the mismatch between the field used to authenticate the webhook and the field used to select what gets written.

### Likelihood Explanation
Likelihood depends on a concrete, plausible operational condition: a multi-organization Shipit deployment where at least one configured organization has not set a `webhook_secret` — a state the documentation explicitly allows ("Webhook secret (optional)") and which is exactly what the engine's own multi-org test fixtures model. Any organization added to the config without immediately setting its webhook secret (e.g., during onboarding) silently downgrades authentication for every other, already-secured organization's stacks, since the handler dispatch trusts `repository.full_name` unconditionally after the check passes.

### Recommendation
- Verify the webhook signature using the same repository/organization that the handler will subsequently act on: reject events where the organization derived for signature verification does not match the organization actually owning `repository.full_name`.
- Do not allow `verify_webhook_signature` to return `true` for organizations lacking a `webhook_secret`; require an explicit opt-in ("insecure/no-signature" mode) instead of silently trusting any payload naming that org.
- Reject webhooks where `repository.owner.login` and the owner segment of `repository.full_name` disagree, before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`, e.g. `OrgA` (has stacks and a `webhook_secret` set) and `OrgB` (added later, `webhook_secret` left blank), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. As an unauthenticated network client, `POST /webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, and JSON body:
```json
{
  "sha": "<victim-commit-sha-in-OrgA-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally — the request passes with a 200/204 despite no valid signature.
4. `StatusHandler` resolves the commit via `Commit.where(sha: params.sha)` (scoped to whatever stack tracks that SHA, in `OrgA`) and calls `create_status_from_github!`, injecting a forged `"success"` status for `OrgA`'s commit, potentially satisfying a required-status gate for deploy/merge in a repository the attacker never had signature access to.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
