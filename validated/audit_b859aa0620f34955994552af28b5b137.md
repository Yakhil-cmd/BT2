### Title
Webhook signature verification authenticates the wrong field, allowing a trusted-organization signer to forge push/pull_request/status events for repositories owned by other organizations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and its `webhook_secret`) used to validate the `X-Hub-Signature` HMAC based on `repository_owner`, which is read from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). However, the event handlers that actually act on the payload (`PushHandler`, `PullRequest::*Handler`, etc.) identify the target `Repository`/`Stack` using a *different* field, `payload.dig('repository','full_name')`, via `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties these two fields together, so the organization whose secret validated the signature is not required to match the repository the handler subsequently writes to.

### Finding Description
In a multi-tenant Shipit deployment (explicitly documented and supported in `docs/setup.md` "Using Multiple Github Applications" and `lib/shipit.rb#github`/`#github_app_config`), each GitHub organization onboarded to the instance has its own `GitHubApp` with its own `webhook_secret`: [1](#0-0) 

The webhook signature check picks which secret to verify with, purely from the `repository.owner.login` (or `organization.login`) field of the untrusted, attacker-supplied JSON body: [2](#0-1) 

Once the signature validates, the raw `params` hash is dispatched unmodified to every registered handler for the event: [3](#0-2) 

But the base `Handler` (and every concrete handler such as `PushHandler`, `PullRequest::OpenedHandler`, `PullRequest::ClosedHandler`) resolves the target repository/stack from a *different* JSON field, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

Because HMAC-SHA1 verification only proves "this body was signed by the secret belonging to whatever `repository.owner.login` the body itself claims," and the body is entirely attacker-controlled JSON (not an authentic GitHub-generated payload), an organization admin who legitimately controls their own GitHub App installation in a shared/multi-org Shipit instance can:
1. Know their own org's `webhook_secret` (they configure/receive it when the GitHub App is created for their org).
2. Craft an arbitrary JSON payload where `repository.owner.login` = their own org (so `Shipit.github(organization: repository_owner)` selects their own `GitHubApp`, whose secret they know) — signature verification succeeds.
3. Set `repository.full_name` inside the *same* payload to an unrelated org/repo already tracked by Shipit (`victim-org/victim-repo`) — a value never checked against `repository.owner.login`.
4. The dispatched handler (`PushHandler`, `PullRequest::OpenedHandler`, etc.) resolves the victim `Stack`/`Repository` via `Repository.from_github_repo_name(params.repository.full_name)` and performs a real mutating action against it (e.g. `stack.sync_github(expected_head_sha: params.after)`, provisioning a review stack, archiving a review stack, updating pull request state) — all attacker-controlled, none of it scoped to the attacker's own organization.

This is the same class of bug as the referenced Mochi report: the value the system *authenticates/authorizes* (the organization tied to the verified signature) is not the value the system subsequently *acts on* (the repository extracted from the same payload). The binding `signing organization == acted-upon repository owner` is never enforced.

### Impact Explanation
This crosses a repository-ownership trust boundary: an entity that is only entitled to send authenticated webhooks for its own GitHub organization can forge events that are dispatched against Stacks belonging to any other organization onboarded to the same Shipit instance. Depending on the event/handler this enables triggering GitHub syncs with attacker-chosen `expected_head_sha` on victim stacks (`PushHandler`), creating/archiving review stacks and mutating pull-request state for victim repositories (`PullRequest::*Handler`), and posting fabricated commit statuses (`StatusHandler`) for a victim repository — none of which the attacker should be authorized to influence. This is a cross-repository/cross-organization write achieved purely by forging a webhook body, matching the "cross-repository writes" / "unauthorized deploy" tier of impact for multi-tenant Shipit deployments.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration — `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), and (b) the attacker to control at least one of the onboarded organizations' GitHub Apps (i.e., know that org's `webhook_secret`, which they would as the org's own admin). No repository write access, Shipit session, or `ApiClient` token is needed — only the ability to send an HTTP POST to the public `/webhooks` endpoint with a self-crafted body and a valid HMAC for their own org.

### Recommendation
After verifying the webhook signature, re-derive and enforce that the organization used to select the verifying `GitHubApp` matches the owner encoded in `repository.full_name` (or `organization.login`) used by the handlers, e.g. compare `repository_owner` against `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner` before dispatching to handlers, and reject the event if they differ.

### Proof of Concept
Assuming a multi-org Shipit instance with organizations `attacker-org` (attacker-controlled GitHub App, secret known to the attacker) and `victim-org/victim-repo` (an existing tracked Stack):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC_SHA1(attacker_org_webhook_secret, raw_body)>
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```

- `verify_signature` computes `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and successfully verifies the HMAC using the attacker's own known secret. [7](#0-6) 
- `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, entirely ignoring the `attacker-org` value used for authentication, and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's Stack. [8](#0-7) [9](#0-8)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
