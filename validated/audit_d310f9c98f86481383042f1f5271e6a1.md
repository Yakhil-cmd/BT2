### Title
Cross-repository forgery of commit CI status via `status` webhook — enables unauthorized deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` GitHub webhook handler resolves the target `Commit` purely by SHA, with no check that the SHA belongs to the repository that the inbound webhook was authenticated for. Any org/repo owner with a Shipit GitHub App installation (and therefore knowledge of their own `webhook_secret`) can forge a signed `status` event whose `repository` block names their own org (to pass signature verification) but whose `sha` matches a commit that also exists in a completely different stack (trivial via a fork, since git commit SHAs are content-addressed and identical across repositories sharing history). This creates a `Shipit::Status` record on the victim stack's commit, which can flip CI to `success` and trigger deploy/merge automation there.

### Finding Description
Webhook signature verification in `WebhooksController#verify_signature` picks the `GitHubApp`/secret to check against based on a payload field, `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

This only proves the request was signed by *some* organization's registered app — it says nothing about which repository/stack the event's data actually belongs to. Other handlers correctly re-derive the target repository from `repository.full_name` in the same payload before acting, e.g. the base `Handler#stacks`/`repository_name` helpers and `PushHandler`: [3](#0-2) [4](#0-3) 

`StatusHandler`, however, never scopes to `stacks`/`repository_name`. It looks up commits **globally by `sha`** and writes a status onto whatever `Commit` rows match, regardless of stack/repository: [5](#0-4) 

`Commit.create_status_from_github!` then unconditionally records the forged status against that commit's stack: [6](#0-5) [7](#0-6) 

This is exactly the analog bug class from the report: `hookHandleSwap` trusts an unverified/uncorrelated field (expected vault deposit amount) to update accounting state; here `StatusHandler` trusts an unverified/uncorrelated field (`sha`, decoupled from the `repository` used for authentication) to update commit-status accounting state. The broken binding, stated as an equality that should hold but doesn't:

`organization authenticated via webhook signature (repository.owner.login) == repository/stack whose Commit/Status row is mutated (derived only from sha, with no repository check)`

### Impact Explanation
A `Status` transitioning a commit to `success` can satisfy `Shipit::DeploySpec#required_statuses`/CI gating and unblock the merge queue and deploy triggers for a stack the attacker does not own or have any legitimate relationship with, since `Status#enable_ci_on_stack` and `schedule_continuous_delivery` fire regardless of which org actually authenticated the request: [8](#0-7) 
This can lead to an unauthorized deploy being unblocked/triggered on a victim's stack, which falls under the "unauthorized deploy" Critical impact bucket.

### Likelihood Explanation
The attacker only needs their own legitimate GitHub App installation (their own org, their own `webhook_secret`, which they control since they configure it — see multi-org config docs), a target commit SHA shared with a victim repo (trivially obtained by forking a public/shared-history repo tracked by another Shipit stack), and the ability to POST directly to the Shipit `/webhooks` endpoint (a route Shipit is designed to expose to the public internet for GitHub delivery). No repository write access, GitHub App private key, or Shipit session/API token is required — only crossing the "authenticated org ↔ repository written" boundary described in scope.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository named in the payload (as other handlers do via `stacks`/`repository_name`), and reject/ignore the event if the commit's stack's repository does not match `payload.dig('repository', 'full_name')` (and ideally cross-check that this also matches the organization that authenticated the webhook signature).

### Proof of Concept
1. Attacker registers/owns a GitHub org `attacker-org` with its own Shipit GitHub App installation and thus knows its `webhook_secret`.
2. Attacker forks (or otherwise obtains) a commit SHA `S` that is also tracked by a `Commit` row belonging to victim stack `victim-org/victim-repo` in the same Shipit instance.
3. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s own `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` picks `attacker-org`'s app (via `repository.owner.login`) and the signature validates.
6. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the victim's `Commit`, and calls `create_status_from_github!`, creating a `success` `Status` on the victim's stack — with no verification that `attacker-org` has anything to do with `victim-org/victim-repo`.
