### Title
Webhook signature verification keys on `repository.owner.login` while all event handlers act on the unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GithubApp`/webhook secret to verify the request with by reading `repository.owner.login` (or `organization.login`) out of the **same** untrusted JSON payload it is about to verify, then verifies the raw body against that organization's `webhook_secret`. Every registered webhook handler, however, resolves the target `Shipit::Repository`/`Stack` using a *different* field of that same payload — `repository.full_name` — via `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties `repository.full_name`'s owner segment back to the `repository_owner` value that was actually used to select the verifying secret.

### Finding Description
`verify_signature` does: [1](#0-0) 
selecting the app config for HMAC verification using `repository_owner`, which is read from the same payload: [2](#0-1) 

Every handler, though, determines which `Repository`/`Stack` to mutate using `repository.full_name`, not `repository.owner.login`: [3](#0-2) 

and e.g. `PushHandler` uses that `stacks` scope directly to enqueue a GitHub sync to an attacker-chosen `after` sha: [4](#0-3) 

Shipit explicitly supports one `webhook_secret` per GitHub organization (multi-org configuration): [5](#0-4) 

The binding that should hold is: *organization whose secret authenticated the request* == *organization that owns the repository being written to*. Because verification keys off `repository.owner.login`/`organization.login` while every handler keys off the independent `repository.full_name` field, an operator/attacker who legitimately controls (and knows the secret for) **Organization A** in a multi-org Shipit deployment can craft and correctly HMAC-sign a payload where `repository.owner.login = "OrgA"` (so it passes verification against OrgA's secret) but `repository.full_name = "OrgB/victim-repo"` (so the handler acts on OrgB's stack). This breaks the "organization authenticated versus repository written" binding required by this engine's trust model, letting a party with only OrgA's webhook credentials cause writes against OrgB's stacks that Shipit also manages.

### Impact Explanation
A malicious/compromised org-scoped webhook secret holder can force `PushHandler` to enqueue `GithubSyncJob`/`stack.sync_github(expected_head_sha: ...)` against a `Stack` belonging to an entirely different, unrelated repository/organization that they have no legitimate relationship to, using an attacker-chosen `after` sha. If that target stack has continuous deployment enabled, this can trigger deployment of a commit sha of the attacker's choosing against a stack the attacker was never authorized to touch — an unauthorized cross-repository/cross-organization action satisfying the "cross-repository writes"/"unauthorized deploy" impact bar. Other handlers (`MembershipHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*`) that also resolve their target purely from `repository.full_name` are similarly affected (team/membership churn, forged commit statuses, forged check-suite refreshes, or review-stack archival on a foreign repository).

### Likelihood Explanation
Requires the attacker to legitimately control a webhook secret for at least one organization configured in a multi-org Shipit deployment (a realistic and common deployment topology per `secrets.development.example.yml`), plus knowledge that another org's repository is also managed by the same Shipit instance (discoverable via the public `/repositories` or `/stacks` UI/API if not otherwise restricted). No GitHub App private key, `api_clients_secret`, or Shipit session is needed — only the ability to send an HTTP POST with a correctly HMAC-signed body using a secret the attacker legitimately possesses for their own org.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after verifying the signature, assert that the organization used to select the verifying secret (`repository_owner`) matches the owner segment actually used to resolve the target repository (`repository.full_name`'s owner, or `Repository#owner`). Reject (422) any payload where these disagree, rather than trusting `full_name` independently of the field used for authentication.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret`, and a `Stack` tracking `OrgB/victim-repo`.
2. As an operator who legitimately knows `OrgA`'s `webhook_secret` (e.g., because they administer OrgA's GitHub App), build a `push` payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-existing-sha-on-OrgB/victim-repo>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature` as `sha1=HMAC(OrgA_webhook_secret, raw_body)`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and verifies successfully against OrgA's secret (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `Shipit::Webhooks::Handlers::PushHandler#process` resolves `stacks` via `repository.full_name = "OrgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for OrgB's stack — despite the request only being authenticated as belonging to OrgA.
