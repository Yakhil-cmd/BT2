### Title
i128 overflow in `borrowed × borrow_index` permanently freezes a market before the index cap can engage - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` values total debt as `borrowed.mul(new_borrow_index)` — a ray-scaled `scaled × index / RAY` product. Because the `MAX_BORROW_INDEX_RAY` ceiling (1e36) is applied to the index itself, not to the `borrowed × index` product, a sufficiently large market hits an `i128` overflow inside the accrual before the index ever reaches its cap. Since every state-changing entrypoint runs `global_sync` (accrual) first, once this threshold is crossed the market is permanently frozen: no supply, borrow, withdraw, repay, liquidation, or bad-debt cleanup can ever execute again.

### Finding Description
The analog to CVE-2025-0725 (an integer overflow causing memory corruption) is an integer overflow in fixed-point accrual whose effect is unrecoverable panic rather than memory corruption — Soroban traps instead of overflowing a buffer, so the damage manifests as permanent freezing of funds.

Mechanism:

- `accrue_step` calls `scaled_to_original(env, borrowed, borrow_index)` and then `calculate_supplier_rewards`, which computes `borrowed.mul(env, new_borrow_index)` (`common/src/rates/simulate.rs:60-69`, `common/src/rates/index.rs:80-81`). `Ray::mul` is `mul_div_half_up(scaled, index, RAY)`; the intermediate product `borrowed × new_borrow_index` must fit in `I256`-widened math, but the resulting ray-scaled *value* must fit `i128`, otherwise `mul_div_half_up` panics with `GenericError::MathOverflow` (`common/src/math/fp_core.rs:108-118`).
- The index ceiling is applied only to the index in `update_borrow_index` (`common/src/rates/index.rs:13-19`). `MAX_BORROW_INDEX_RAY = 1e36` (`common/src/constants/pool.rs:19`), so the cap only binds when the *index* reaches ~1e9 × RAY. The value ceiling `borrowed × index / RAY ≤ i128::MAX ≈ 1.7e38` is reached far earlier for large books: with `borrowed` at ray scale ~1e30 (e.g., a 1e9-unit position on an 18-decimal token ≈ 1e27 raw → 1e54 ray is too big; the test uses borrowed scaled ≈ 1e18 × ... ) — concretely, the repo's own test shows a market with ~1e9 tokens at 18 decimals borrowed at 98% utilization on the XLM curve overflows after several years while `borrow_index < MAX_BORROW_INDEX_RAY` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-353`).
- Every mutating path calls `interest::global_sync` before touching state (`contracts/pool/src/interest.rs:20-33`), and `global_sync` calls `accrue_chunk` → `accrue_step`, which panics. The panic reverts the whole transaction, so the freeze cannot be bypassed by any entrypoint.

Reachable path for a single unprivileged address: `supply` a very large amount of a high-decimals token, `borrow` near max utilization against separately supplied collateral, then let time pass (or repeatedly call public `update_indexes`). Once `borrowed × borrow_index / RAY` exceeds `i128::MAX`, the next accrual panics permanently.

### Impact Explanation
Permanent freezing of all funds in the affected market. Once the ray-value product overflows, every verb that accrues first — `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `borrow`, `supply`, flash paths, `recapitalize` — traps with `MathOverflow`. The index cap cannot rescue the market because the overflow occurs at a lower index than the cap, and there is no recovery path that skips accrual. The repo's own regression test asserts exactly this: `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW` after the cliff (`large_positions_and_long_horizons.rs:354-356`).

### Likelihood Explanation
Requires a whale-scale position: the overflow needs `borrowed_ray × borrow_index_ray / RAY > 1.7e38`, i.e. roughly `borrowed_value > 1.7e38 / index`. With the index growing to ~170× on the steep curve segment, `borrowed` must exceed ~1e12 raw units (~1e-6 of 18-decimal supply is not enough — the test uses 1e9 × 1e18). This is a large capital requirement and needs sustained high utilization over an extended period, but it is fully unprivileged, needs no governance action, and no bound in the code prevents it: `calculate_scaled_cap` intentionally saturates rather than rejects large caps (`common/src/rates/scaling.rs:20-33`), and the supply/borrow verbs accept any amount within caps. Severity: Medium (high impact, high capital/time requirement).

### Recommendation
Enforce the value ceiling at accrual rather than letting the product panic:

- In `update_borrow_index` (`common/src/rates/index.rs:13-19`), clamp `new_index` to `min(MAX_BORROW_INDEX_RAY, i128::MAX * RAY / borrowed)` — i.e., cap the index at the largest value that keeps `borrowed × index / RAY` inside `i128`. Pass `borrowed` into the function or perform the clamp in `accrue_step` before `calculate_supplier_rewards`.
- Alternatively, saturate `calculate_supplier_rewards` / `scaled_to_original` at `i128::MAX` instead of panicking, so accrual completes (index pinned, no further interest) and exits/repayments remain possible — mirroring the intended semantics of the unreachable index cap.

### Proof of Concept
The repo contains a working demonstration in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`:

1. Attacker supplies `1e9` units of `BIG18` (18 decimals) and borrows 98% of it against `COL` collateral, with utilization cap disabled.
2. Ledger time advances one year at a time while calling `update_indexes` on the market.
3. After several years, `try_update_indexes_for(&["BIG18"])` fails with `errors::MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` — the `borrowed × index` product overflowed `i128` inside `accrue_step`.
4. From then on `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` both fail with `MATH_OVERFLOW`, confirming the market — and all supplier funds in it — is frozen permanently.

Uncertainty note: whether this cliff is considered an accepted design bound is ambiguous — the math docs (`skills/xoxno-lending/math.md`) describe index caps and a formulas bound, and the test asserts the panic as expected behavior, which may mean the team treats the freeze as a known limitation. If it is an acknowledged bound, this reduces to a documented trade-off; the code as written nonetheless gives an unprivileged user a path to permanently freeze a market.
