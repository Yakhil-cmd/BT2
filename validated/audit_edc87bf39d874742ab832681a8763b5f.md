This confirms the mechanism precisely. Key facts established:

- `Shipit.github(organization:)` resolves the GitHub App config by looking up `secrets.github` keyed on the (attacker-controlled) organization string, case-insensitively: `github_app_config` does `secrets.github.deep_transform_keys(&:downcase); github_config[organization.downcase.to_sym]` [1](#0-0) .
- `WebhooksController#repository_owner` derives that organization name straight from the unauthenticated JSON body, before any signature check: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) .
- `verify_webhook_signature` unconditionally returns `true` when that resolved org's `webhook_secret` is blank: `return true unless webhook_secret` [3](#0-2) .
- The multi-org config schema explicitly supports per-org secrets, and shows `webhook_secret:` left blank as a valid/documented value [4](#0-3) [5](#0-4) .
- Once "verified" (or skipped), handlers dispatch purely on `payload.dig('repository', 'full_name')`, with no re-check that this repo belongs to the org used for verification: `Repository.from_github_repo_name(repository_name)` [6](#0-5) , and `PushHandler#process` triggers `stack.sync_github` for any matching stack [7](#0-6) .

This is a concrete, provable binding break: "an organization that authenticated versus the repository that is written." An attacker who knows (or targets) any org configured in a multi-org Shipit instance without a `webhook_secret` can set `repository.owner.login` to that unsecured org while setting `repository.full_name` to any *other* tracked repository, bypassing signature verification entirely and injecting arbitrary `push`/`status`/`merge`/`pull_request` events against that unrelated repo's stacks — no credentials, tokens, or repo access required.

### Title
Unauthenticated cross-repository webhook forgery via organization/repository binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate a webhook against using an unauthenticated field taken straight from the request body (`repository.owner.login` / `organization.login`), before any cryptographic verification occurs. If that selected organization is configured without a `webhook_secret` (an explicitly documented, valid configuration for multi-org installs), `GitHubApp#verify_webhook_signature` returns `true` unconditionally. Because none of the downstream webhook handlers re-validate that the payload's `repository.full_name` actually belongs to the organization used to select/bypass the secret, an attacker can forge a payload naming an unsecured org as the "owner" while pointing `repository.full_name` at a completely unrelated, secured repository/stack.

### Finding Description
The verification flow is:
1. `repository_owner` is read directly from the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) .
2. That string selects a `GitHubApp` instance via `Shipit.github(organization: repository_owner)`, which case-insensitively indexes into `secrets.github` [8](#0-7) .
3. `verify_webhook_signature` is then evaluated against *that* app's secret, but bypasses verification entirely if the secret is unset: `return true unless webhook_secret` [3](#0-2) .
4. If verification passes/bypasses, `WebhooksController#create` dispatches the full, attacker-supplied `params` to every registered handler for the event type with no further authorization check [9](#0-8) .
5. Handlers resolve the target `Stack`/`Repository` purely from `payload.dig('repository', 'full_name')` — a field that was never covered by the org-selection logic — via `Repository.from_github_repo_name(repository_name)` [6](#0-5) .

The equality that should hold but doesn't:
`organization authenticated (used to pick/bypass the webhook secret)` == `organization owning the repository the handlers actually act on`.

Because `repository.owner.login` and `repository.full_name` are two independently-attacker-controlled fields in the same unauthenticated JSON body, this equality can be broken trivially whenever at least one configured org in the install has no `webhook_secret` — a state the project's own docs and sample configs present as normal/supported [4](#0-3) .

### Impact Explanation
Any tracked repository in a multi-org Shipit deployment inherits the weakest org's webhook posture: if one configured org omits `webhook_secret`, every repository tracked by the instance — regardless of which (properly-secured) org it belongs to — becomes forgeable. An unauthenticated attacker can synthesize `push`, `status`, `check_suite`, `pull_request`, `merge`, and `membership` events for a victim stack, e.g. injecting fake commits via `GithubSyncJob` [7](#0-6) , forging green CI `status` records that gate deploy eligibility (`commit.deployable?`), or manipulating pull-request/merge-queue state and team memberships. This crosses the "cross-repository writes" / "unauthorized deploy" impact bar since it lets an outsider corrupt state or CI signal for a repository they have no relationship to, purely by exploiting another, unrelated organization's lax webhook configuration on the same Shipit instance.

### Likelihood Explanation
Requires only that the Shipit operator has configured more than one GitHub organization and left `webhook_secret` blank for at least one of them — a configuration explicitly shown as valid in `docs/setup.md` and the bundled multi-org secrets fixtures. No GitHub credentials, repository access, or Shipit account are needed; the attacker just POSTs a crafted JSON body to `/github/webhooks` with mismatched `repository.owner.login` and `repository.full_name`.

### Recommendation
After selecting the `GitHubApp` used for verification, `WebhooksController` (or the individual handlers) should assert that the app's configured organization actually matches the owner of `repository.full_name` targeted by the event, rather than trusting `repository.owner.login`/`organization.login` alone to pick the verification context. Additionally, consider making `webhook_secret` mandatory whenever more than one organization is configured, since an unset secret on any one org currently disables verification for the whole multi-tenant install.

### Proof of Concept

```
POST /github/webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgWithoutWebhookSecret" },
    "full_name": "victim-org/victim-repo"
  }
}
```
Given a `secrets.yml` with multiple orgs configured where `OrgWithoutWebhookSecret.webhook_secret` is blank (as shown in `test/dummy/config/secrets_double_github_app.yml`), `Shipit.github(organization: 'OrgWithoutWebhookSecret').verify_webhook_signature(...)` returns `true` unconditionally regardless of the `X-Hub-Signature` header sent (or omitted). The request then reaches `PushHandler#process`, which locates `victim-org/victim-repo`'s stacks solely via `repository.full_name` and triggers `stack.sync_github`, all without ever presenting a valid signature for `victim-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)

  end
```
