### Title
Unchecked `transferFrom` Return Value in `handleERC721Transfer` Permanently Consumes Bridge Nonce Without Delivering Token — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer` updates all bridge state (nonce, handled-tx-hash, vote records) and emits `HandleValueTransfer` **before** calling `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)`, and does **not** check the return value of that call. If the ERC721 token's `transferFrom` silently returns `false` instead of reverting, the bridge nonce is permanently consumed, the event is emitted, and the recipient never receives the token. The analogous ERC20 path uses `SafeERC20.safeTransfer`, which does check the return value — making this an explicit inconsistency within the same contract family.

---

### Finding Description

In `BridgeTransferERC721.sol`, the `handleERC721Transfer` function executes the following sequence:

1. `_setHandledRequestTxHash(_requestTxHash)` — marks the source tx hash as handled (irreversible)
2. `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber` — records nonce
3. `_updateHandleNonce(_requestedNonce)` — advances `lowerHandleNonce` / `upperHandleNonce`, deletes `closedValueTransferVotes[_requestedNonce]`
4. `emit HandleValueTransfer(...)` — emits the settlement event
5. `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` — **return value ignored** [1](#0-0) 

Steps 1–4 are irreversible state mutations. Step 5 is the actual asset delivery. If the token's `transferFrom` silently returns `false` (non-standard ERC721 that does not revert on failure), the EVM does not revert the transaction, so steps 1–4 stand permanently while the token remains in the bridge contract.

By contrast, `handleERC20Transfer` in `BridgeTransferERC20.sol` uses `IERC20(_tokenAddress).safeTransfer(_to, _value)` — the `SafeERC20` wrapper that explicitly checks the return value and reverts if it is `false`. [2](#0-1) 

There is also a secondary instance in `requestERC721Transfer`:

```solidity
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
_requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
``` [3](#0-2) 

Here the `transferFrom` is called first, but its return value is still not checked. If it silently fails, `_requestERC721Transfer` still runs, emitting `RequestValueTransferEncoded` and incrementing `requestNonce`, causing the counterpart bridge to release/mint a token that was never actually locked.

---

### Impact Explanation

**`handleERC721Transfer` (lock/unlock mode):**
- The bridge nonce for `_requestedNonce` is permanently consumed (`handleNoncesToBlockNums`, `closedValueTransferVotes`, `lowerHandleNonce` all updated).
- `HandleValueTransfer` is emitted, signalling successful settlement to off-chain monitors and the recovery system.
- The ERC721 token stays in the bridge contract; `_to` receives nothing.
- The nonce cannot be replayed (`_lowerHandleNonceCheck` will reject it), so the loss is permanent and unrecoverable. [4](#0-3) 

**`requestERC721Transfer` (lock/unlock mode):**
- If `transferFrom` silently fails, the token is never deposited into the bridge.
- `RequestValueTransferEncoded` is still emitted with an incremented `requestNonce`.
- The bridge operator on the counterpart chain observes the event and calls `handleERC721Transfer` on the counterpart, releasing or minting a token to the recipient.
- Net result: a token is created on the counterpart chain with no corresponding locked token on the source chain — cross-chain asset inflation.

---

### Likelihood Explanation

The trigger requires a registered ERC721 token whose `transferFrom` returns `false` instead of reverting. Token registration is owner-controlled, which limits the attack surface. However:

- Non-standard ERC721 implementations (pre-EIP-721 or custom tokens) that return `false` on failure are known to exist in the wild.
- A registered token that is later upgraded (proxy pattern) to a non-standard implementation would expose this path to any caller of `requestERC721Transfer` (unprivileged) or any bridge operator calling `handleERC721Transfer`.
- The `handleERC721Transfer` path is callable by any registered operator, not just the owner. [5](#0-4) 

---

### Recommendation

**For `handleERC721Transfer`:** Move the `emit HandleValueTransfer` and all state mutations to **after** the transfer, and use `safeTransferFrom` (or check the return value explicitly):

```solidity
// Perform transfer first
if (modeMintBurn) {
    require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
} else {
    // Use safeTransferFrom or check success
    IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
}

// Only update state and emit after confirmed success
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);
```

**For `requestERC721Transfer`:** Verify the token was actually received by the bridge before proceeding:

```solidity
uint256 balanceBefore = IERC721(_tokenAddress).balanceOf(address(this));
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
require(IERC721(_tokenAddress).ownerOf(_tokenId) == address(this), "transfer failed");
_requestERC721Transfer(...);
```

Alternatively, adopt a `SafeERC721` wrapper analogous to `SafeERC20` used in `BridgeTransferERC20`.

---

### Proof of Concept

1. Deploy a non-standard ERC721 token where `transferFrom` always returns `false` without reverting, and register it with the bridge (owner action).
2. Call `requestERC721Transfer(tokenAddress, recipient, tokenId, "")` from any account.
   - `transferFrom(msg.sender, bridge, tokenId)` returns `false` silently — token stays with caller.
   - `_requestERC721Transfer` runs: `RequestValueTransferEncoded` is emitted, `requestNonce` incremented.
3. The bridge operator observes the event and calls `handleERC721Transfer` on the counterpart bridge.
   - Counterpart mints/releases a token to `recipient`.
4. Result: `recipient` holds a token on the counterpart chain; the source token was never locked. Cross-chain supply is inflated.

For the `handleERC721Transfer` path:
1. A registered ERC721 token's `transferFrom` silently returns `false` (e.g., due to insufficient bridge balance or a token upgrade).
2. Operators reach quorum and call `handleERC721Transfer`.
3. `_setHandledRequestTxHash`, `_updateHandleNonce`, and `emit HandleValueTransfer` all execute successfully.
4. `transferFrom(address(this), _to, _tokenId)` returns `false` — no revert.
5. `_to` receives nothing; the nonce is permanently consumed; the token is locked in the bridge forever. [6](#0-5)
