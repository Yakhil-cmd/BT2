### Title
Webhook organization used for signature verification is not bound to the repository/stack the event actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the HMAC signature against by reading the **attacker-supplied JSON body itself** (`repository.owner.login` / `organization.login`), then dispatches the same, already-parsed payload to event handlers that identify the target `Stack`/`Repository`/`Commit` from **other fields of that same payload** (e.g. `repository.full_name`, `sha`). Nothing ties the organization whose secret validated the signature to the repository/commit that is actually written to. This is the direct analog of the Sherlock finding: a state comparison (`signerCount`/`validSignerCount`, here "authenticated org" vs "acted-upon repository") is checked using data from the same untrusted source instead of being independently, cryptographically bound.

### Finding Description
`verify_signature` computes the trust anchor purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the per-organization `webhook_secret` from `config/secrets.yml`, which explicitly supports multiple independent GitHub organizations sharing one Shipit installation: [3](#0-2) 

Signature check itself is a straightforward HMAC compare: [4](#0-3) 

Once `verified` is true, the raw JSON body is dispatched, unmodified, to the registered handler for the event: [5](#0-4) 

The bug: the field used to pick *which org's secret validates the signature* (`repository.owner.login`) is not the same value the handler subsequently trusts to decide *which repository/commit/stack is mutated*. The webhooks controller test suite confirms handlers only receive `repository.owner.login`, distinct from whatever repository/commit identifiers drive the mutation (`sha`, full_name, etc.), and that this owner login is exactly what's merged in ad hoc to make signature verification pass for test payloads: [6](#0-5) [7](#0-6) 

This is structurally identical to the `_removeSigner` bug: a security-relevant decision (`newSignerCount`, here "is this delivery legitimately from org X") is derived by comparing/reading a value from state that can independently drift (`validSignerCount` recomputed from signer hats; here, the org field embedded in the very payload being verified) rather than a value cryptographically tied end-to-end to the object being modified. An attacker who legitimately controls their own GitHub App installation/org on the same Shipit instance (a supported deployment topology per `docs/setup.md`) can craft and self-sign a payload where `repository.owner.login`/`organization.login` names their own org (so `Shipit.github(organization: ...)` selects their own `webhook_secret`, and the signature they compute with that secret passes), while other payload fields (`repository.full_name`, `sha`, `branches`) reference a completely different, victim-owned `Stack`/`Commit`.

### Impact Explanation
Because commit-status and push-derived jobs act on whatever repository/commit identifiers are in the payload, a forged but validly-"signed" (by the attacker's own org secret) delivery can:
- Create bogus `Status` records or flip `deployable?` for a victim's commit via the `status` handler, which can gate/trigger continuous deployment (`Stack.schedule_continuous_delivery` / `trigger_deploy`), leading to an **unauthorized deploy**.
- Enqueue `GithubSyncJob`/`RefreshCheckRunsJob` against an arbitrary victim `Stack` via the `push`/`check_suite` handlers.

This crosses the "organization authenticated vs. repository that is written" trust boundary called out in the rules, and its worst-case outcome (forged deployable status triggering continuous deployment) falls under the Critical impact of "an unauthorized deploy."

### Likelihood Explanation
Requires the attacker to control (or register) their own GitHub organization/App that is configured as one of the multiple orgs on a shared Shipit instance — a documented, supported multi-tenant configuration, not a hypothetical. No GitHub write access to the victim repository, no Shipit session, and no leaked secrets are needed; the attacker only needs their own legitimately-issued `webhook_secret` and knowledge of the victim's repository/commit identifiers (public information for public repos).

### Recommendation
Bind the verified organization to the actual object mutated by each handler: after verifying the signature for `repository_owner`, handlers must additionally assert that every repository/stack/commit identifier referenced in the payload actually belongs to that same, already-authenticated organization (e.g., look up the `Stack`/`Repository` first, then require `stack.repository.owner == repository_owner`) rather than trusting `repository.full_name`/`sha` unconditionally once the outer signature check succeeds.

### Proof of Concept
1. Attacker operates `OrgAttacker`, which is configured as a valid entry under `Shipit.github` (multi-org setup, per `docs/setup.md`), and thus knows `OrgAttacker`'s real `webhook_secret`.
2. Attacker crafts a `status` (or `push`) event JSON body: `repository.owner.login = "OrgAttacker"`, but `repository.full_name` / `sha` reference a commit belonging to victim `Stack` under `OrgVictim/victim-repo`.
3. Attacker signs the raw body with `OrgAttacker`'s webhook secret and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")`, matches, verification passes.
5. `Shipit::Webhooks.for_event('status')` handler processes the forged payload against the victim's commit/stack, updating status/triggering sync — without ever confirming that `OrgAttacker` actually owns `OrgVictim/victim-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
