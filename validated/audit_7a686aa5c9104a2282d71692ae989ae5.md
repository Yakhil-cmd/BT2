### Title
Governance-style `system_vote` parameter changes are weighted by current balance at count-time (not by locked/snapshot stake), enabling a cheap, temporary-balance "flash governance" takeover of network TPS-fee parameters - ([File: main_chain.js])

### Summary
Obyte's on-chain governance for global network parameters (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) is implemented via `system_vote` messages that any unprivileged unit author can post, and finalized via a `system_vote_count` message that any unprivileged unit author can also post, with almost no restriction beyond payload shape. [1](#0-0) [2](#0-1) 

### Finding Description
`countVotes()` determines the winning value for a numeric subject by summing the **current** on-chain balance of every address that has ever cast a `system_vote` for that subject and taking the value where accumulated balance crosses 50% of total voted balance: [3](#0-2) 

The voting weight is not a snapshot of balance held at the time the vote was cast, nor is it escrowed/locked - it is re-read from the live `outputs`/`units` tables at count time: [4](#0-3) 

The "quorum" mechanism (`SYSTEM_VOTE_MIN_SHARE`) only requires that a small fraction of total supply has *ever* voted on that subject within an expanding lookback window (1 year, then 2, then 3, ...), not that a broad community actually participated: [5](#0-4) 

Anyone can trigger the count at will by posting a `system_vote_count` message - there is no cooldown, no minimum voting period, and no check that a meaningful number of independent voters participated before the tally is written to `system_vars` and takes effect from the next MCI: [1](#0-0) [6](#0-5) 

This mirrors the Moonwell bug class: a governance system where (a) the token/weight required to swing a vote can be cheaply and briefly acquired, and (b) the process for finalizing a proposal has an artificially low bar for quorum/timing, letting an attacker force a parameter change before the broader community can react - here, by voting with a temporarily large GBYTE balance for one of the unrestricted numeric subjects (`base_tps_fee`, `tps_interval`, `tps_fee_multiplier`, `threshold_size`) and then immediately posting `system_vote_count` to lock in the result while few or no other real voters have ever registered a vote on that subject, satisfying `SYSTEM_VOTE_MIN_SHARE` on the attacker's own stake alone. Unlike `op_list`, these numeric subjects have no `checkWitnessesKnownAndGood`-style eligibility gate, only range checks on the value itself: [7](#0-6) 

Once counted, the attacker can move the funds elsewhere; the new `system_vars` value persists regardless of subsequent balance changes: [8](#0-7) 

### Impact Explanation
`base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` directly control the network-wide TPS fee that every unit author and AA pays/receives (`tps_fees_balances`). An attacker who cheaply and briefly acquires a large GBYTE balance can push these to extreme values (e.g., `base_tps_fee` up to `1e8`, `tps_fee_multiplier` up to `1000`), which can be used to grief the network's fee economics, drain/freeze AA and user TPS-fee balances, or make it economically infeasible for the network to confirm new units at normal cost - a network-availability/fund-freezing impact in the same class the report is concerned with (loss of protocol funds/parameters via a rushed, under-quorum governance vote).

### Likelihood Explanation
Exploitation requires only posting a valid `system_vote` unit (accessible to any address, no privileged role) followed by a `system_vote_count` unit for the same subject, both cheap unit-posting operations. The main precondition is finding/being the (first) subject with low historical voter participation, which is plausible for subjects such as `tps_interval` or `tps_fee_multiplier` that are rarely voted on. Likelihood is Medium because it also depends on network/community conditions (total voted balance vs. `SYSTEM_VOTE_MIN_SHARE * TOTAL_WHITEBYTES`) that I could not fully verify from the available code alone.

### Recommendation
- Require votes to be weighted by balance held continuously since (or locked at) the time the vote was cast, not by balance read at arbitrary future count time.
- Enforce a minimum voting period / minimum number of distinct voting addresses before `system_vote_count` is allowed to finalize a subject, in addition to the existing balance-share quorum.
- Consider restricting `system_vote_count` triggering to conditions with stronger anti-manipulation guarantees (e.g., mandatory minimum elapsed time since first vote for the subject, similar to `EMERGENCY_COUNT_MIN_VOTE_AGE` already used for `op_list`'s emergency path) and apply it uniformly to numeric subjects.

### Proof of Concept
1. Attacker acquires a large temporary GBYTE balance on a fresh/rarely-voting address.
2. Attacker posts a `system_vote` unit with `{subject: "tps_fee_multiplier", value: 1000}` from that address (passes validation as shown in `validation.js:1893-1904`).
3. Attacker immediately posts a `system_vote_count` unit with payload `"tps_fee_multiplier"` (passes validation in `validation.js:1913-1923`, no quorum or timing check at validation time).
4. Once the triggering unit stabilizes, `saveSystemVote`/`countVotes` runs: since likely few/no other addresses have historically voted on `tps_fee_multiplier`, the attacker's own current balance alone can satisfy `SYSTEM_VOTE_MIN_SHARE` and set the median value to the attacker's chosen extreme, written to `system_vars` and applied from the next MCI (`main_chain.js:1878-1912`).
5. Attacker moves the balance elsewhere; the malicious `tps_fee_multiplier` value remains in effect network-wide.
