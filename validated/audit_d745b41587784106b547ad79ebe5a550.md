### Title
Assets sent to an AA that its oscript logic doesn't reference become permanently stuck since the AA engine credits every received asset unconditionally to the AA's balance - ([File: aa_composer.js])

### Summary
The Allo report describes native tokens sent via `allocate()` being forwarded unconditionally to Strategies that never check whether they use/expect that token, leaving the value permanently stranded because `withdraw()` is hardcoded to a single known token. The analogous ocore pattern is in the AA (Autonomous Agent) trigger-handling engine: any asset amount sent to an AA address is unconditionally merged into `trigger.outputs` and credited to the AA's persistent balance, regardless of whether the AA's own bytecode (`messages`/`cases`) ever references, forwards, or returns that particular asset.

### Finding Description
`getTrigger()` scans every `payment` message of the triggering unit and adds every asset/amount pair sent to the AA address into `trigger.outputs`, with no restriction to assets the AA definition is aware of: [1](#0-0) 

`updateInitialAABalances()` then unconditionally credits all of these assets into the AA's persistent `aa_balances` table before any AA-specific logic (`init`/`messages`/`cases`) is even evaluated: [2](#0-1) 

The AA's actual behavior toward a given trigger is determined purely by `if` conditions written by the AA author, which normally reference specific, expected assets (e.g. `$asset`, `$mm_asset`) via `trigger.output[[asset=...]]`. If a trigger unit includes an output in an asset that is *not* referenced by the branch condition that ends up matching, that asset's value is silently accepted into the AA's balance as a side effect of `updateInitialAABalances`, but the executing case's `messages` never mention it, so no payment output is ever produced for it. For example, in `test/samples/uniswap_like_market_maker.oscript`, the "exchange bytes to asset" case only checks `trigger.output[[asset=base]]` and `trigger.output[[asset=$asset]]`: [3](#0-2) 

If a trigger unit simultaneously pays enough base bytes to satisfy this condition *and* includes an output of a third, unrelated asset to the same AA address, this case still matches and executes successfully (it is not bounced), yet the third asset is never spent, referenced, or returned by any `payment` message. `updateFinalAABalances()` only debits assets that appear in the AA's own outgoing `payment` messages, so the stray asset's balance is left sitting permanently in `aa_balances` for that AA address: [4](#0-3) 

Crucially, the safety net that returns received funds — `bounce()` — only runs when the *entire* trigger evaluation is bounced (e.g. no case matches, or an explicit `bounce()` call in the oscript); it is not invoked, and cannot retroactively return, individual assets when a different branch successfully executes: [5](#0-4) 

Because an AA's definition is immutable once posted (it cannot be upgraded to add a case that recognizes the new asset after the fact), any value sent this way is stuck forever, with no `withdraw`-style path for the AA (or its owner) to recover it — a direct structural analog of the reported Allo issue where the Strategy's `withdraw()` only knows about its designated `token` and any other received token is unrecoverable.

### Impact Explanation
An unprivileged unit poster can send a payment to any AA address that includes, alongside inputs matching a normal use case, an extra output of an unrelated asset (base or custom asset). The AA balance permanently records this asset amount (verified consistent by `checkBalances()` against `outputs`/`aa_balances`), but since the AA definition never expresses logic for that asset, the funds can never be spent, forwarded, or reclaimed by anyone — a permanent freeze of user funds inside the AA, matching the "AA fund loss or freezing" impact criteria.

### Likelihood Explanation
This can happen accidentally (a wallet/UI bug sending an extra asset output, or a user manually crafting a unit) or be deliberately triggered by anyone posting a unit, since the required conditions are just: (1) an output in an unhandled asset to the AA address, and (2) other outputs sufficient to satisfy an existing case's `if` condition so the trigger is not bounced. No special privileges, hub cooperation, or race conditions are required — any single posted unit suffices.

### Recommendation
Have the AA-trigger engine (`aa_composer.js`) surface to the executing AA logic which assets in `trigger.outputs` were *not* consumed/referenced by any executed `payment` message, and either (a) automatically bounce back any unreferenced non-bounce-fee assets to `trigger.address` after case evaluation completes, similar to what `bounce()` already does for the fully-bounced path, or (b) document/require AA authors to always include a catch-all "return any other asset" branch (as some sample scripts like `order_book_exchange.oscript`/`a_bank_without_percent.oscript` already do defensively), and provide validation tooling (e.g., in `aa_validation.js`) that warns when an AA definition's `cases` do not cover a default "unexpected asset" branch.

### Proof of Concept
1. Post an AA definition equivalent to `test/samples/uniswap_like_market_maker.oscript`'s "exchange bytes to asset" case (or any AA whose branches condition only on specific assets via `trigger.output[[asset=X]]`).
2. Post a trigger unit with two payment outputs to the AA address in the same unit: (a) `> 1e5` bytes of base asset (satisfying the case's `if`), and (b) a nonzero amount of an unrelated third asset `Z` not referenced anywhere in the AA definition.
3. `getTrigger()` merges both outputs into `trigger.outputs = {base: N, Z: M}` [1](#0-0) ; `updateInitialAABalances` credits both into `aa_balances` for the AA address [2](#0-1) .
4. The "exchange bytes to asset" case matches and executes normally, producing a `payment` message only for `$asset`, never for `Z`.
5. `updateFinalAABalances` leaves `Z`'s balance untouched in `aa_balances`, and no bounce or subsequent trigger can ever cause the AA to spend `Z`, since its definition contains no case referencing it — the `M` units of asset `Z` are permanently frozen in the AA.
