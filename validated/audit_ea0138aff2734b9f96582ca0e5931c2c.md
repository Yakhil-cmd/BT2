### Title
Cross-organization forged commit status via globally-scoped SHA lookup in `StatusHandler` breaks the organization-signature-to-repository-write binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit selects the GitHub App / `webhook_secret` used to verify an inbound webhook signature based solely on the `repository.owner.login` (or `organization.login`) field of the payload, but the `status` event handler applies the payload's effects by matching commit SHA **globally across every stack and organization** in the Shipit instance, with no check that the authenticating organization actually owns the commit being mutated.

### Finding Description
`WebhooksController#verify_signature` picks the app config to verify against using only the organization name embedded in the payload: [1](#0-0) [2](#0-1) 

This correctly proves the payload was genuinely emitted by GitHub for organization `X` (per `GitHubApp#verify_webhook_signature`, HMAC-checked against `X`'s `webhook_secret`): [3](#0-2) 

However, once verification passes, `StatusHandler#process` never re-checks that organization `X` is the owner of the commit being updated. It resolves the target purely by SHA, across the whole `commits` table: [4](#0-3) 

Contrast this with the base `Handler` class, which *does* have a `repository_name`/`stacks` helper scoped to the payload's `repository.full_name` — but `StatusHandler` deliberately bypasses it and queries `Commit.where(sha: params.sha)` unscoped: [5](#0-4) 

Because git commit SHAs are content-addressed, an identical commit object (same tree, parents, author/committer timestamps and message) pushed to two different repositories/organizations produces the identical SHA1. Shipit supports hosting multiple, unrelated GitHub organizations behind one instance, each with its own GitHub App and `webhook_secret` (documented multi-org config): [6](#0-5) 

So the equality that should hold — `organization_whose_secret_validated_the_signature == owner_of_repository_whose_commit_row_is_mutated` — is not enforced. `StatusHandler` writes a `CommitStatus` (`commit.create_status_from_github!`) onto whatever `Commit` row shares that SHA, regardless of which stack/repository/organization it belongs to.

`Commit#create_status_from_github!` feeds directly into `Commit#status`, `#deployable?`, and `#schedule_continuous_delivery`, which can trigger deploy eligibility and continuous delivery: [7](#0-6) [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker who has only legitimate, unprivileged control over a low-trust GitHub organization/repository that is also onboarded to the same Shipit instance (e.g., their own sandbox org, configured with its own GitHub App and its own `webhook_secret`) can forge a "green" CI status for a commit that is actually tracked under a completely different, high-trust organization's stack — provided that commit's exact SHA also exists in their own repo (trivial: cherry-pick / fast-forward the victim's public commit into their own repo, which reproduces the identical SHA1). GitHub will legitimately sign the resulting `status` webhook with the attacker's own organization's `webhook_secret`, which passes `verify_webhook_signature` for that organization. `StatusHandler` then mutates the commit status/state on the victim's stack's commit, since the lookup is by SHA only. If the victim stack is configured with `continuous_deployment` or required/blocking status checks gating deploys, this can unlock an unauthorized deploy on a repository/organization the attacker never had any credential for — no `webhook_secret` theft, no Shipit session, and no GitHub write access to the victim repo is required. This satisfies the "unauthorized deploy" Critical-impact criterion.

### Likelihood Explanation
Requires: (1) the target Shipit instance hosts multiple organizations (a documented, supported configuration), (2) the attacker controls at least one onboarded low-trust organization/repo, and (3) the attacker can reproduce (not brute-force — simply replicate) the exact commit object of a real commit tracked in the victim stack, which is realistic when the victim's history is public (open-source) or otherwise obtainable. This is a moderate-likelihood, plausible attack path for any multi-tenant Shipit deployment mixing public/open-source and private stacks.

### Recommendation
Scope the `status` (and similarly any other globally-keyed) webhook handler's `Commit` lookup to the repository/organization that was cryptographically verified for that request — e.g., join through `stacks`/`repositories` filtered by `payload.dig('repository', 'full_name')` the same way `Handler#stacks` already does for other handlers, rather than a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `OrgAttacker` (attacker-controlled) and `OrgVictim` (has a stack with `continuous_deployment` enabled and a required status check), per the documented multi-org `secrets.yml` layout.
2. Attacker forks/clones a public commit `C` (SHA `abc123...`) from `OrgVictim`'s tracked repository into their own `OrgAttacker` repository (same commit content ⇒ identical SHA1) and pushes it (or otherwise gets it recorded) in a repo under `OrgAttacker`.
3. Attacker (as an authorized user of `OrgAttacker`'s repo) sets a commit status via the GitHub API on their own repo for SHA `abc123...` with `state: success`, `context: <the-context-OrgVictim-requires>`.
4. GitHub sends a `status` webhook to Shipit, signed with `OrgAttacker`'s `webhook_secret`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgAttacker"`, fetches `OrgAttacker`'s app, and the signature verifies successfully.
6. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, which also matches `OrgVictim`'s tracked commit row, and calls `commit.create_status_from_github!(params)` — flipping the required check to success and potentially unblocking `OrgVictim`'s continuous deployment, entirely without any credential belonging to `OrgVictim`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
