## Analysis

The GitLab CVE describes a **missing authorization check that lets an unauthorized party reach data/actions they should not be able to reach** because a scoping/identity check was bypassed. The closest analog in `ocore--024` is in the device-message handler for signing requests in `wallet.js`, where a check that verifies the *sender* of a `sign` request is actually an authorized cosigner of the wallet has been deliberately commented out.

### Title
Missing authorization check on incoming `sign` requests allows any paired (non-cosigner) device to solicit signatures for a wallet's local address - (File: `wallet.js`)

### Summary
`handleMessageFromHub`'s `sign` case processes signing requests received from *any* paired/correspondent device. For local addresses (`ifLocal`), the code that used to verify the sender (`from_address`) is actually a listed cosigner (`extended_pubkeys`) of the wallet owning the address has been disabled, with the check left in as a comment. Any correspondent device — not just a genuine cosigner of a shared/multi-sig address — can therefore submit a `sign` request that is unconditionally accepted (`callbacks.ifOk()`), validated, and forwarded via the `signing_request` event to whatever consumer is listening (UI or an automated/headless signer). [1](#0-0) 

### Finding Description
In the `sign` message branch of `handleMessageFromHub`, once `findAddress` resolves the target address as `ifLocal` (an address controlled by *this* device, potentially as one member of a shared/multi-sig address), the code is supposed to confirm that the *sending device* is actually one of the cosigners entitled to request a signature for that address:

```js

        //    if (sender_rows.length !== 1)
        //        return callbacks.ifError("sender is not cosigner of this address");

``` [2](#0-1) 

Because this check is disabled, **any correspondent device** (i.e., anyone who has ever paired with the wallet, which in ocore only requires knowledge of a pairing code/QR, not being a wallet cosigner) can send a `sign` request naming one of the wallet's own addresses and an arbitrary `signing_path`. The handler will:
1. Accept the message (`callbacks.ifOk()`), deleting it from the hub queue regardless of legitimacy.
2. Build/validate the attacker-supplied unit (`objUnit`), including attaching attacker-controlled private payloads.
3. Emit `signing_request(objAddress, body.address, objUnit, assocPrivatePayloads, from_address, body.signing_path)` — the same event that is emitted for legitimate cosigner-initiated multisig-signing flows.

By contrast, the `ifRemote` branch (for addresses not local to this device) still performs the equivalent check explicitly:
```js
if (!other_device_addresses.includes(from_address))
    return callbacks.ifError("you are not listed as a cosigner for this address "+body.address);
``` [3](#0-2) 

This asymmetry confirms that the `ifLocal` path is missing the analogous authorization gate that legitimately belongs there — the comment explicitly documents that the check was intentionally removed for "multilateral signing," but it removes sender authentication rather than solving the actual multisig-flow problem (verifying that some cosigner is entitled to request the signature, as `ifRemote` still does for the same feature).

### Impact Explanation
This weakens the trust boundary for shared/multi-sig addresses (see `shared_address_signing_paths`, `extended_pubkeys` tables) which is the intended protection for wallet/contract message handling of a paired device: [4](#0-3) 

Any paired device — including one that is not among the actual cosigners recorded in `extended_pubkeys`/`shared_address_signing_paths` — can trigger a `signing_request` for an address it does not control, with an arbitrary attacker-crafted unit (including custom payment inputs/outputs) and arbitrary `signing_path`. Deployments that automate signing on `signing_request` (headless wallets, exchange/DAO bots built on `ocore`, arbiter/arbstore automation) commonly key their trust on "the request arrived on a device_address that is a known correspondent," since human UI confirmation is not always implemented for every signing path. Because ocore never re-validates that the *requesting* device is an authorized cosigner before raising this event, such automation can be tricked into producing signatures for attacker-chosen units/outputs, enabling unauthorized spending from the wallet's own or shared addresses.

### Likelihood Explanation
Reaching this code path requires only pairing with the victim's device (a normal, low-friction operation in ocore's wallet protocol) and sending a well-formed `sign` justsaying message naming the victim's own address and any signing path known to the attacker (e.g., learned from a previous, unrelated payment or from public multi-sig definitions shared during negotiation). No cosigner status, private key material, or special network privileges are required — this squarely matches the "paired device" reachability class explicitly in scope.

### Recommendation
Restore (in a form compatible with legitimate multilateral signing) an authorization check in the `ifLocal` branch that confirms the sending device is actually entitled to request a signature for the given `(address, signing_path)` — e.g., checking `extended_pubkeys`/`shared_address_signing_paths` for a matching `device_address`, or requiring that the sender be one of the addresses/paths derivable from the address definition (similar to the check retained in the `ifRemote` branch) rather than accepting any correspondent unconditionally.

### Proof of Concept
1. Attacker device pairs with victim's `ocore` wallet (standard pairing handshake via `device.js`'s `handlePairingMessage`), becoming a `correspondent_devices` entry.
2. Attacker crafts an unsigned unit `objUnit` with a payment message paying itself, and any `signing_path` used by one of the victim's addresses.
3. Attacker sends a `sign` justsaying message: `{address: <victim_address>, signing_path: <path>, unsigned_unit: objUnit}`.
4. `handleMessageFromHub` resolves `ifLocal` for `victim_address` and, without checking that the attacker device is a genuine cosigner, validates the unit and emits `signing_request(objAddress, victim_address, objUnit, ..., attacker_from_address, path)`.
5. Any listener automatically or via a permissive UI approving requests keyed only on "sender is a known correspondent" will produce a signature for the attacker-controlled unit, enabling unauthorized spend/signing.
