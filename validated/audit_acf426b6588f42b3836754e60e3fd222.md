### Title
`Api::CCMenuController#stack` bypasses `stack_id`-scoped ApiClient authorization, allowing cross-stack read via CCMenu token - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides both `authenticate_api_client` and `stack` from `BaseController`, but its `stack` method resolves `params[:stack_id]` via `Stack.from_param!` directly instead of the scoped `stacks.from_param!` used by the base class. Since a CCMenu token created by `CCMenuUrlController#client` has `permissions: %w[read:stack]` and no `stack` association, `current_api_client.stack_id?` is false and `check_permissions!` only checks the permission string, never the stack identity — so the token authorizes reading *any* stack, not just the one it was issued for.

### Finding Description
The intended binding is: `stack.id == current_api_client.stack_id` whenever `current_api_client.stack_id?` is true, otherwise `stack` must be drawn from `stacks` (which for a client without a bound stack is `Stack.all`, i.e., effectively unscoped by design in `BaseController`, but that path is only reached through the safe accessor `stacks.from_param!`).

In `BaseController`: [1](#0-0) 
`stacks` correctly narrows to `Stack.where(id: current_api_client.stack_id)` when the client has a bound stack, and `stack` resolves through that scope.

`Api::CCMenuController` however defines its own `stack` and `authenticate_api_client`: [2](#0-1) 
`stack` calls `Stack.from_param!(params[:stack_id])` — the unscoped class method — completely bypassing the `stacks` scoping helper. `require_permission :read, :stack` only invokes `current_api_client.check_permissions!('read', 'stack')`: [3](#0-2) 
which is a pure string-membership check against `permissions`, with no reference to `stack_id` at all.

The token created for CCMenu is minted without a bound stack: [4](#0-3) 
so `current_api_client.stack_id?` is `false` for this token, meaning even the base class's `stacks` scope would return `Stack.all` for it — but that is irrelevant here because `CCMenuController#stack` never calls `stacks` at all; it calls `Stack.from_param!` directly. The net effect: any holder of this token can substitute an arbitrary `stack_id` in the URL and read that stack's latest deploy/rollback status, entirely independent of which stack the token was originally generated for.

**Exploit flow**: An authenticated Shipit user with legitimate view access to Stack A visits the CCMenu URL feature for Stack A, obtaining a `read:stack`, no-`stack_id` token (shared across all their CCMenu requests, since `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` reuses the same client for that user). They then issue `GET /api/stacks/<STACK_B>/ccmenu.xml?token=<token>` for a stack B they have no access to. `authenticate_api_client` succeeds (token verifies), `require_permission!(:read, :stack)` succeeds (permission list contains `read:stack`), and `stack` resolves Stack B unconditionally via `Stack.from_param!`. The response renders Stack B's latest deploy/rollback state.

Existing guards do not catch this: `verify_signature`/webhook checks are irrelevant (this is a GET/API path); `ExplicitParameters` is not used here; `force_github_authentication` is not applied to `Api::BaseController`; the `stacks` scope exists but is simply never called by this controller's overridden `stack` method.

### Impact Explanation
An attacker who has (or can obtain) a CCMenu API token for one stack can read deploy/task status (branch, latest deploy id, success/failure, timestamps) for **any** stack in the Shipit instance, including stacks belonging to other teams/repositories they have no authorization for. This is a cross-tenant unauthorized read of deploy state, matching the "High" impact category (unauthenticated/under-scoped read of stack state). It is fully repeatable against arbitrary stack IDs with a single valid CCMenu token.

### Likelihood Explanation
Preconditions: the attacker needs one valid CCMenu token, obtainable for any stack they have legitimate (even minimal) read access to via the normal `CCMenuUrlController#fetch` UI flow — no special privilege, GitHub team membership, or secret is required beyond ordinary access to one stack's CCMenu feature. Once obtained, forging requests for other `stack_id`s is trivial (just changing the URL parameter), no additional secrets are needed, and the attack is fully repeatable/scriptable across all stack IDs.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped accessor consistent with `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that clients with a bound `stack_id` are restricted to that stack, matching the binding enforced everywhere else in the API.

### Proof of Concept
Minitest `ActionDispatch::IntegrationTest` plan:
1. Create two stacks, `stack_a` and `stack_b`, with distinct repositories/environments.
2. Create a user `current_user`, and mint a token the same way `CCMenuUrlController#client` does: `ApiClient.create!(creator: current_user, name: 'CCMenu Client', permissions: %w[read:stack])` (no `stack` set) — assert `client.stack_id.nil?` and `client.stack_id?` is falsy.
3. Assert the binding before tracing: `stack.id == current_api_client.stack_id` should hold or the stack should be drawn only from `stacks`; here `current_api_client.stack_id` is `nil`.
4. Send `GET /api/stacks/#{stack_b.to_param}/ccmenu.xml?token=#{client.authentication_token}`.
5. Assert response status is `200` and the rendered XML corresponds to `stack_b` (e.g., contains `stack_b.to_param` / `stack_b`'s latest deploy id), proving the token minted in the context of (or intended for) `stack_a` successfully authorized reads against `stack_b`, violating the intended per-stack scoping.
