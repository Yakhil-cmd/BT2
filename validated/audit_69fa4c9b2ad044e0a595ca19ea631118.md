### Title
Webhook signature verification is scoped to one GitHub organization while payload processing writes to a different, attacker-chosen repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which HMAC `webhook_secret`) to validate a webhook against based on `repository.owner.login` (or `organization.login`) from the JSON body. Once the signature check passes, every webhook handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, …) independently determines *which repository's stacks/commits to mutate* using `repository.full_name` — a separate field in the same attacker-controlled payload. Because these two fields are read independently and never cross-checked, a party who legitimately possesses the webhook secret for one organization configured in Shipit (`OrgA`) can forge a signed webhook whose `repository.owner.login` says `OrgA` (to pass signature verification) but whose `repository.full_name` says `OrgB/victim-repo` (a different organization's repository hosted on the same Shipit instance), causing Shipit to act on `OrgB`'s stacks/commits without ever having proven control of `OrgB`.

### Finding Description
Signature verification: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization `GitHubApp` (with its own `webhook_secret`) from `config/secrets.yml`, keyed only by the organization name derived above: [3](#0-2) 

Shipit explicitly supports multiple organizations, each with its own `webhook_secret`, in `config/secrets.yml`: [4](#0-3) 

After signature verification succeeds, handlers resolve the *target* repository from a different field of the same payload (`repository.full_name`), with no relation to `repository.owner.login`/`organization.login` used for verification: [5](#0-4) 

Concrete write paths that trust this unchecked binding: [6](#0-5) [7](#0-6) [8](#0-7) 

The binding that should hold is: `organization authenticated by signature == organization owning the repository/commit that gets mutated`. Before the attack: an admin of `OrgA`'s installed GitHub App can only forge webhooks affecting `OrgA`'s own stacks. After the attack (forged payload with mismatched `repository.owner.login` vs `repository.full_name`): the same `OrgA` secret lets that party create commit statuses (`StatusHandler#process` → `Commit#create_status_from_github!`) on `OrgB`'s commits, or trigger `stack.sync_github` / `schedule_refresh_check_runs!` on `OrgB`'s stacks — i.e., writes into a repository/organization the requester never authenticated for.

### Impact Explanation
This breaks the organization-authenticated vs. repository-written binding and enables cross-organization writes: an actor who only controls one org's GitHub App configuration can inject forged CI statuses, force github-sync jobs, or trigger check-run refreshes against another organization's stacks/commits hosted on the same Shipit instance. Because `ci.require`/merge-queue logic in `DeploySpec` consumes these same `Status` records to gate deploys and automatic merges, forged "success" statuses on a victim org's commit can be used to satisfy required-status gating and enable an unauthorized deploy or merge for a repository the attacker does not control — a Critical-tier outcome (cross-repository writes / unauthorized deploy or merge).

### Likelihood Explanation
Exploitation requires the attacker to already hold a legitimately configured `webhook_secret` for at least one organization onboarded to the shared Shipit instance (multi-tenant deployments are an explicitly documented and supported configuration). Given that, forging the payload only requires crafting arbitrary JSON with mismatched `repository.owner.login` and `repository.full_name` fields and computing the HMAC over the raw body with the known secret — no additional Shipit session, API token, or GitHub write access to the victim org is needed.

### Recommendation
In `WebhooksController#verify_signature`, after successfully verifying the signature for the organization derived from `repository_owner`, assert that the organization portion of `repository.full_name` (and any other repository-identifying field consumed by handlers) matches the organization used for verification, rejecting the request otherwise. Alternatively, derive the verifying organization strictly from the same `repository.full_name` field that handlers use to resolve `stacks`, so a single payload field drives both authentication and the write target.

### Proof of Concept
1. Shipit is configured with two organizations in `config/secrets.yml`, `OrgA` and `OrgB`, each with its own GitHub App / `webhook_secret` (per docs/setup.md multi-org setup), and both have Shipit stacks.
2. An actor with legitimate access to `OrgA`'s GitHub App settings retrieves `OrgA`'s `webhook_secret`.
3. The actor crafts a `status` event JSON body:
```json
{
  "sha": "<victim-orgB-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. The actor computes `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` → `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `StatusHandler#process` resolves `stacks`/commit via `payload.dig('repository', 'full_name')` = `"OrgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and creates a forged "success" status on `OrgB`'s commit (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), even though the request was authenticated only against `OrgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
```
