### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled` master switch for `allow_with_label`/`prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with the three provisioning behaviors using Ruby's `&&`/`||` precedence, so `review_stacks_enabled` is only ANDed into the `allow_all?` branch and is completely ignored for the `allow_with_label?` and `prevent_with_label?` branches. An attacker who can open a pull request and control its labels can trigger stack creation on a repository whose maintainer explicitly disabled review-stack provisioning.

### Finding Description
The documented binding is `repository.review_stacks_enabled == true` must gate stack creation for **every** `provisioning_behavior` value (per `docs/review_stacks.md` step "Check 'Dynamically provision stacks for Pull Requests?'" before selecting a behavior, and the settings UI at [1](#0-0) ).

The actual code is: [2](#0-1) 

Due to Ruby operator precedence (`&&` binds tighter than `||`), this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present) || (prevent_with_label? && !label_present)`

So when `review_stacks_enabled == false` but `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, the second/third clauses still evaluate independently of `review_stacks_enabled` and can return `true`, causing `respond_to_pull_request_opened?` to return `true` and `ReviewStackAdapter#find_or_create!` to create a `Shipit::Stack` at [3](#0-2) . The same precedence bug exists in the sibling `ReopenedHandler#unarchive?` [4](#0-3) . By contrast, `LabeledHandler#respond_to_label_change?` and `UnlabeledHandler#respond_to_label_change?` correctly AND `review_stacks_enabled` across the whole `(archive? || unarchive?)` expression at the top level [5](#0-4) , proving the intended semantics and that `OpenedHandler`/`ReopenedHandler` diverge from it.

**Attacker request:** open a pull request (`action: "opened"`) against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (or `prevent_with_label`), applying (or omitting) the configured provisioning label — both fully attacker-controlled on a PR they open. The webhook triggers `OpenedHandler#process`, `provision?` returns `true` despite the master switch being off, and a `Shipit::Stack` is created and queued for provisioning.

**No existing guard prevents this:** signature verification, `ExplicitParameters` schema validation, and `drop_unhandled_event` only gate delivery/format, not this business-logic condition; there is no additional check for `review_stacks_enabled` elsewhere in the code path.

**Test coverage confirms the gap:** in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, the only test combining `provisioning_enabled: false` is with `behavior: :allow_all` [6](#0-5) . The `allow_with_label` tests (lines 129-157) and `prevent_with_label` tests (lines 159-187) all use the default `provisioning_enabled: true` from `configure_provisioning_behavior` [7](#0-6) . No test pins `provisioning_enabled: false` together with `allow_with_label`/`prevent_with_label` and asserts `assert_no_difference -> { Shipit::Stack.count }`, so this precedence bug is currently unguarded by regression coverage.

### Impact Explanation
An attacker opening a PR against a repository they don't administer can force `Shipit::Stack` creation and queue it for provisioning even though the repository owner explicitly disabled "Dynamically provision stacks for Pull Requests" — a security control bypass of an owner-set master switch. Stack creation feeds into `Shipit::ReviewStackProvisioningQueue` and downstream `ProvisioningHandler`/deploy machinery, which can run host-defined provisioning tasks (potentially involving `Command`/`PTY.spawn`-backed tasks) that the repository owner believed were disabled. This is repeatable against any repository misconfigured this way (any repo with `review_stacks_enabled: false` and a label-based behavior) and constitutes an unauthorized-provisioning/deploy-trigger bypass — matching the "unauthorized deploy" Critical category.

### Likelihood Explanation
Requires the target repository to be configured with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a plausible transitional/misconfiguration state — e.g., an owner temporarily disabling the feature without resetting the behavior dropdown). No Shipit credentials, session, or GitHub App secrets are needed; the attacker only needs to open a PR and set/omit a label on it, both actions available to any GitHub user with fork/PR access to the repository. Cost is trivial and fully repeatable.

### Recommendation
Add explicit parentheses in `OpenedHandler#provision?` (and the identical bug in `ReopenedHandler#unarchive?`) so `review_stacks_enabled` gates the entire OR expression, matching the pattern already used in `LabeledHandler`/`UnlabeledHandler`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks for allow_with_label when review stacks are disabled" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "does not create stacks for prevent_with_label when review stacks are disabled" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Both assertions fail against current code (a `Shipit::Stack` is created despite `review_stacks_enabled == false`), demonstrating the bypass.
