### Title
Sensitive plaintext content of every decrypted device message (including pairing secrets and private payment/key material) is unconditionally written to logs - ([File: device.js])

### Summary
CVE-2019-11283 concerns Cloud Foundry SMB Volume accidentally writing volume usernames/passwords to logs, letting anyone with log access hijack the volume. The analogous root cause in ocore is `decryptPackage()` in `device.js`, which unconditionally logs the full plaintext of every decrypted device-to-device message via `console.log("decrypted: "+decrypted_message)` [1](#0-0) . This function is the single decryption point for all inbound paired-device traffic — pairing confirmations (`pairing_secret`), correspondent introductions, wallet/shared-address setup messages, private-payment chains, and signed responses all pass through it before being logged.

### Finding Description
`decryptPackage()` derives the shared secret, decrypts the AES-GCM payload, and immediately logs the decrypted JSON string in full, regardless of message subject or sensitivity [2](#0-1) . This same module handles `pairing_secret`-based correspondent authentication (24 references to `pairing_secret` in `device.js`), meaning the secret used to authorize a new paired device relationship is logged in plaintext the moment it is received. It also handles private-payment chain payloads exchanged between correspondents (`handlePrivatePaymentChains` in `wallet.js` receives its `body` from this same decrypted-message path) [3](#0-2) , so blinding factors, addresses, and payment amounts belonging to `private-payment counterparties` end up in the logs too. Anyone who can read the node's stdout/log files (an operator, a misconfigured log shipper, a shared hosting log directory, etc.) can therefore recover `pairing_secret` values and private-payment secrets that were never meant to leave the two paired devices — the exact "accidentally outputs sensitive information to the logs" bug class described in the CVE.

A related, narrower instance of the same bug class is in `wallet.js`'s textcoin-reclaim job, which logs the full mnemonic (equivalent to a private key controlling the textcoin's funds) on both success and failure: `console.log("failed claiming back old textcoin "+row.mnemonic+...)"` and `console.log("claimed back mnemonic "+row.mnemonic+...)"` [4](#0-3) .

### Impact Explanation
A `pairing_secret` leaked from logs lets an attacker complete device pairing as the legitimate correspondent, after which they can receive private payment chains, wallet-sharing invitations, and shared-address cosigning requests meant for the real device — enabling unauthorized spending from shared/multisig addresses and disclosure of private-asset transaction details. Leaked textcoin mnemonics directly grant control of the funds on that address, i.e., outright theft/unauthorized spending. This satisfies the "concrete unauthorized spending" / "AA fund loss" bar required by the validation rules.

### Likelihood Explanation
No cryptographic weakness needs to be broken — the sensitive value is written to disk/console as a side effect of normal message handling every time any paired device sends any message (`decryptPackage`), and every time the textcoin-reclaim cron job runs. Any environment where logs are collected, forwarded, rotated to a shared path, or otherwise readable by a lower-trust party (common in production/cloud deployments, exactly as described in the CVE) exposes the secret. This requires only normal use of the paired-device or textcoin feature — no attacker action against the victim is needed to trigger the log write.

### Recommendation
- Remove or redact the `console.log("decrypted: "+decrypted_message)` line in `decryptPackage()` (device.js); if debug logging is needed, mask/whitelist non-sensitive fields (e.g., `subject` only) rather than dumping the full payload.
- Audit all `console.log` calls in `device.js` for other cases that print keys, secrets, or `pairing_secret` values, and strip them or gate them behind a debug flag that is off by default in production builds.
- Remove `row.mnemonic` from the `console.log` calls in `claimBackOldTextcoins` (wallet.js); log only the unit/address, never the mnemonic.
- Establish a lint/CI rule flagging `console.log` calls that reference variables named like `*secret*`, `*mnemonic*`, `*priv*`, or `*key*`.

### Proof of Concept
1. Pair two devices normally, or have any correspondent send a message to a node (e.g., a `pairing_secret` confirmation, or a private-payment chain forward via `handlePrivatePaymentChains`).
2. On the receiving node, `device.js`'s `decryptPackage()` decrypts the incoming package and executes `console.log("decrypted: "+decrypted_message)`, printing the full JSON (including `pairing_secret`, private payment blinding/addresses, or other correspondent-supplied secrets) to stdout/log files.
3. An attacker with read access to those logs (via shared hosting, misconfigured log aggregation, or log-forwarding infrastructure — matching the CVE's threat model) extracts the `pairing_secret` and completes pairing as the legitimate correspondent, or extracts private-payment secrets to link/replay private transactions.
4. Separately, run/observe `claimBackOldTextcoins`: any unclaimed textcoin's `mnemonic` (its private key) is printed in full to the log on both the success and failure path, letting a log reader claim the funds before the intended recipient.

function deriveSharedSecret(peer_b64_pubkey, privKey){
	var pubkey = new Buffer(peer_b64_pubkey, 'base64');
	var shared_secret_src = Buffer.from(ecdsa.ecdh(pubkey, privKey, {hashfn: (x, y) => x}, Buffer.alloc(32)));
	var shared_secret = crypto.createHash("sha256").update(shared_secret_src).digest().slice(0, 16);
	return shared_secret;
}
