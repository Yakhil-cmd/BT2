### Title
Unsynchronized `dryRunPrimaryAATrigger` mutates and prematurely tears down shared unit caches, racing with real validation/stabilization - ([File: aa_composer.js])

### Summary
`dryRunPrimaryAATrigger()` writes autonomous-agent response units into the node's global, process-wide in-memory caches (`storage.assocUnstableUnits`, `assocBestChildren`, etc.) and then, in its rollback path, calls `revertResponsesInCaches()` → `storage.forgetUnit()` to synchronously tear those cache entries back out — all **without acquiring the `"write"` mutex** that every other writer of these caches (`saveJoint`, `handleAATriggers`, `validation.validate`) takes before touching them. This lets a dry run's teardown of shared state race with a concurrent, mutex-protected real validation/stabilization pass that is reading or writing the very same cache entries, mirroring the kernel bug class: an object is torn down/freed on one path while a concurrent holder that captured a reference to it earlier is still using it, with no synchronization barrier between the two.

### Finding Description
`dryRunPrimaryAATrigger` is reachable by any unprivileged peer through the `'light/dry_run_aa'` network command [1](#0-0)  and also fires automatically for any freshly-posted, ordinary unit whose payment output targets an AA address, via the `conf.bDryRunNewTriggers` branch inside `handleJoint`'s `ifOk` callback [2](#0-1) . Neither caller takes any mutex before calling into `aa_composer.dryRunPrimaryAATrigger`.

Inside `dryRunPrimaryAATrigger`, a brand-new DB connection/transaction is opened and `handleTrigger` is executed with no lock at all [3](#0-2) . This differs from every other writer of the same caches: `writer.saveJoint` explicitly takes `mutex.lock(["write"])` before touching `storage`'s caches [4](#0-3) , and `aa_composer.handleAATriggers` takes `mutex.lock(['aa_triggers'])` [5](#0-4) . `dryRunPrimaryAATrigger` has no equivalent guard.

When the dry run's `onDone` fires, it synchronously calls `revertResponsesInCaches(arrResponses)` *before* `batch.clear()` and the `ROLLBACK` [6](#0-5) . `revertResponsesInCaches` walks the response units and calls `storage.forgetUnit` for each one [7](#0-6) . `forgetUnit` unconditionally dereferences and deletes the *global* caches shared by the whole node process — `assocUnstableUnits`, `assocBestChildren`, `assocKnownUnits`, `assocCachedUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`, `assocStableUnits`, `assocUnstableMessages` — and even throws if it detects the unit has meanwhile become stable: `if (!conf.bLight && assocStableUnits[unit]) throw Error("trying to forget stable unit "+unit);` [8](#0-7) .

Because there is no `"write"` lock held around the dry-run's cache writes/teardown, a concurrent, properly-locked real validation/stabilization pass (which does hold the `"write"` mutex, e.g. inside `writer.saveJoint` or `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag`) can interleave with the dry run at any `await`/callback boundary: it can observe a cache entry that the dry run has already synchronously deleted (`forgetUnit`'s first line reads `assocUnstableUnits[unit].parent_units` — a `TypeError` on `undefined` if the entry was concurrently deleted), or the dry run's teardown can race the exact moment a unit legitimately becomes stable and trip the `"trying to forget stable unit"` throw. Both are unhandled exceptions in the middle of consensus-critical code paths.

### Impact Explanation
- Any unprivileged peer can trigger repeated/concurrent dry runs (`'light/dry_run_aa'`) targeting AA addresses that are simultaneously subject to real, incoming triggering units, forcing interleaving of unsynchronized cache mutation/teardown with mutex-protected consensus caches.
- The resulting crash (`throw Error`) is unhandled inside async callback chains and will crash the Node.js process — a remotely triggerable node crash reachable from a single network message, which can be repeated against many nodes to degrade the network's ability to confirm new units.
- Short of a crash, silent corruption of `assocUnstableUnits`/`assocBestChildren`/`assocStableUnits` (entries deleted or left in an inconsistent state relative to what real validation expects) can cause different full nodes to disagree on `is_free`/`is_on_main_chain`/stability computations derived from these caches, i.e., node disagreement on validity/stability.

### Likelihood Explanation
`'light/dry_run_aa'` is a normal light-client RPC with only shape validation on the trigger object (`validateAATriggerObject`) and no rate limiting or locking tied to the target AA address; multiple dry runs against a busy/popular AA, timed against real traffic to that AA, will race routinely under load. The `conf.bDryRunNewTriggers` auto-dry-run path makes this even easier to trigger by simply posting ordinary payment units to any AA address, which is a completely unprivileged, everyday action.

### Recommendation
Have `dryRunPrimaryAATrigger` (and any other caller of `handleTrigger`/`revertResponsesInCaches`/`forgetUnit` outside the real-write path) acquire the `"write"` mutex (or a dedicated dry-run mutex that is mutually exclusive with `"write"`) for the duration of its cache mutation and rollback, matching the discipline already used by `writer.saveJoint` and `aa_composer.handleAATriggers`. Alternatively, make dry runs operate on a private, copy-on-write snapshot of the relevant caches instead of mutating the shared global `storage.assocUnstableUnits`/`assocBestChildren`/etc. directly, so `forgetUnit`'s teardown can never observe or corrupt state that a concurrently-running, lock-protected real validation pass depends on.

### Proof of Concept
1. Deploy/observe an AA address `A` that regularly receives real payment-triggering units (so `conf.bDryRunNewTriggers` or ordinary trigger processing is continuously exercising `storage.assocUnstableUnits`/`assocBestChildren` for units that reference `A`).
2. As an unprivileged light-client peer, repeatedly send `'light/dry_run_aa'` requests targeting `A` with triggers that reuse `objMcUnit` (`aa_composer.js:279-287`) as parent context, so that the synthetic response units and the concurrently-processed real units interleave in the shared caches.
3. Because `dryRunPrimaryAATrigger` takes no `"write"` mutex, its `handleTrigger`/`revertResponsesInCaches`/`forgetUnit` sequence can interleave with a real `writer.saveJoint`/stabilization pass that is running under the `"write"` lock at the same time.
4. Trigger the race so that `forgetUnit` executes for a unit either (a) already removed/replaced in `assocUnstableUnits` by the real writer, causing `assocUnstableUnits[unit].parent_units` to throw on `undefined`, or (b) just stabilized by the real writer, tripping `throw Error("trying to forget stable unit "+unit)` — in both cases crashing the node process from an unauthenticated network request.
