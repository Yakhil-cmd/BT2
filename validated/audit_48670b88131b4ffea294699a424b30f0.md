### Title
Cross-Organization Forged CI Status Triggers Unauthorized Continuous Deployment - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate a webhook against based solely on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body. Once that check passes, the event is dispatched to a handler (e.g. `StatusHandler`) that never re-checks that binding: it looks up the target `Commit`/`Stack` purely by `sha` (or, in other handlers, by `repository.full_name`), a field that was never covered by the signature check. Any multi-tenant Shipit install that has even one configured GitHub organization with a blank `webhook_secret` (an explicitly supported, documented "optional" configuration) lets an unauthenticated network attacker forge a signed-looking webhook for that org while writing effects onto a completely different organization's stack.

### Finding Description
`verify_signature` picks the app config to verify against using attacker-controlled payload fields: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` trivially returns `true` when the selected organization has no `webhook_secret` configured — a state that is explicitly documented as optional and shown as a valid config value (`nil`): [3](#0-2) [4](#0-3) 

Once `verify_signature` passes, `create` dispatches to registered handlers using the raw, unverified body: [5](#0-4) 

`StatusHandler#process` writes a new `Status` for *any* commit matching the given `sha`, with no re-validation that the `sha` belongs to the organization whose secret validated the signature: [6](#0-5) 

Creating a `Status` schedules continuous delivery for the stack owning that commit: [7](#0-6) [8](#0-7) 

And a green status on a stack with `continuous_deployment` enabled triggers a real deploy, verified by tests: [9](#0-8) 

Other handlers (e.g. `PushHandler`/`Handler#stacks`) have the same disconnect: the org used for signature verification (`repository.owner.login`) and the repo actually acted on (`repository.full_name`) are two independent, unrelated fields of the same attacker-supplied JSON body: [10](#0-9) [11](#0-10) 

**Equality that should hold, but is broken:** `organization authenticated by verify_signature == organization/stack whose data is written by the handler`. Before the attack, this equality trivially holds because a legitimate webhook's signature is computed by GitHub over the whole payload for one specific repository/org. After the attack, the attacker sends `repository.owner.login = "org-with-no-secret"` (so `verify_signature` passes with a trivial/absent signature) while `sha`/`repository.full_name` reference a stack belonging to a different, victim organization — the equality no longer holds, and `StatusHandler`/`PushHandler` still act on the victim's data.

### Impact Explanation
This maps to the report's "High" tier: "escalation into `Shipit.github_teams` authorization" is not directly hit, but the impact is stronger — "an unauthorized deploy" (explicitly listed as Critical impact) via forged CI success statuses that flip `continuous_deployment` stacks into deploying, without possessing any Shipit session, API token, or the victim organization's `webhook_secret`. The only prerequisite is that the Shipit instance is multi-tenant (`Shipit.github` configured for more than one organization, as the codebase explicitly supports — see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`) and that at least one configured organization has no `webhook_secret` set, which the setup docs describe as optional.

### Likelihood Explanation
Likelihood is contingent on a specific but documented and realistic configuration mistake: any org onboarded to a shared Shipit instance without setting a `webhook_secret`. The docs describe the webhook secret as "(optional)" rather than mandatory, increasing the odds that some tenant in a multi-org deployment omits it. Given that assumption, exploitation requires no credentials at all — just an HTTP POST to the public `/webhooks` endpoint with a crafted `X-Github-Event: status` header and a JSON body naming the unsecured org as owner while embedding a victim `sha`.

### Recommendation
- Bind the org/repo used for signature verification to the exact same repository/commit the handler subsequently acts upon; reject requests where `repository.full_name`'s owner differs from `repository_owner`, and have `StatusHandler` scope its `Commit` lookup by the verified repository, not by `sha` alone.
- Do not allow `verify_webhook_signature` to unconditionally return `true` when `webhook_secret` is blank; require a webhook secret for every configured organization, or reject unsigned requests by default.
- Add belongs-to validation in `Handler#stacks`/`StatusHandler#process` that cross-checks the payload's declared repository against the commit's actual stack repository before writing.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `victim-org` (has `webhook_secret` set) and `attacker-org` (left with `webhook_secret: nil`, per the documented-optional config).
2. Shipit already tracks a stack for `victim-org/victim-repo` with `continuous_deployment: true`, and knows a commit `sha=deadbeef` on it (from normal `push` syncing).
3. Attacker sends, with no valid signature required:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/anything" },
  "sha": "deadbeef",
  "state": "success",
  "context": "ci/forged"
}
```
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the header.
5. `StatusHandler#process` finds `Commit.where(sha: "deadbeef")` — the real `victim-org/victim-repo` commit — and calls `create_status_from_github!`, creating a `success` `Status`.
6. `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` schedules `ContinuousDeliveryJob` for the victim stack, which (per `test/models/commits_test.rb:233-243`) triggers an unauthorized `Deploy` on `victim-org/victim-repo`, entirely outside the victim organization's control.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
