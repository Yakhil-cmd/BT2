## Finding

### Title
Signature malleability in `is_valid_sig()` / `vrf_verify()` oscript primitives due to signature normalization before verification - (File: signature.js)

### Summary
The external Kairos report flags OpenZeppelin's pre-4.7.3 `ECDSA.recover()` malleability, where a contract used the raw signature bytes as a de-facto nonce, and two distinct byte-strings ((r,s) and (r, n-s)) both recover/verify successfully, letting the same authorization be replayed. Ocore exposes an analogous primitive to AA (Autonomous Agent) authors: the oscript function `is_valid_sig(message, pem_key, sig)` (and `vrf_verify`), implemented in `signature.js`, which is reachable by any AA trigger sender supplying arbitrary signature data in `trigger.data`.

### Finding Description
`is_valid_sig` is evaluated in `formula/evaluation.js` and delegates to `signature.verifyMessageWithPemPubKey`: [1](#0-0) 

For secp256k1 PEM keys post `pemCurvesFixMci`, verification is routed through `verifyMessageWithSecp256k1PemPubKey`, which explicitly **normalizes** the signature before verifying: [2](#0-1) 

Because the signature is normalized (`ecdsa.signatureNormalize(rawCompact)`) prior to calling `ecdsaVerify`, both the canonical low-S encoding `(r, s)` and the malleated high-S encoding `(r, n-s)` of the exact same ECDSA signature will verify successfully as two *different byte strings* for the same `(message, pubkey)` pair. The same is true for the generic PEM/OpenSSL path used for all other curves (`prime256v1`, `secp384r1`, brainpool curves, etc.) via `crypto.createVerify(...).verify(...)`, which does not enforce canonical-S DER encoding either: [3](#0-2) 

This contrasts with the core address-authentication path (`['sig', {...}]` authentifier used to sign units/messages), which calls `signature.verify()` → `ecdsa.ecdsaVerify()` directly on the raw 64-byte signature **without normalization**, and libsecp256k1's `ecdsaVerify` rejects non-canonical (high-S) signatures outright: [4](#0-3) 
So unit/device/hub authentication signatures are NOT malleable. The malleability is confined to the `is_valid_sig`/`vrf_verify` oscript primitives, which are explicitly designed for AA authors to validate externally-supplied signed data (e.g., oracle attestations, off-chain authorizations, VRF proofs) supplied via `trigger.data`.

### Impact Explanation
AA authors commonly use a signed message's raw signature (or a hash derived from it) as a uniqueness/replay-protection nonce — exactly the pattern that caused the referenced Kairos vulnerability (`checkOfferArg()`), where the signature itself, not the underlying message hash, guarded against reuse. Because `is_valid_sig` accepts two distinct valid signature encodings for the same authorization, an AA that records "already used signature" (e.g. `var[sig] = true` or a state-var set keyed by the signature string) to prevent double-redemption of a signed voucher/order/claim can be tricked into accepting the *same* authorization twice under two different signature byte-strings. This can lead to double-spend of AA funds (double payout for a single signed claim), directly matching "Impact: An offer may be accepted against more than once" from the original report, mapped onto ocore's AA fund-loss impact category.

### Likelihood Explanation
Any unprivileged AA trigger sender can supply arbitrary `trigger.data` including a malleated signature and message; no special privileges are required. Exploitability further depends on an AA author's implementation choosing to dedupe by the raw signature string instead of the signed message content/hash — a natural but incorrect pattern, since ocore's documentation and primitive naming (`is_valid_sig`) do not warn that the signature is not canonicalized/unique. Given this is a widely usable pattern in AA templates dealing with off-chain signed authorizations (vouchers, oracle attestations, payment channel closes not using `is_valid_signed_package`), likelihood is Medium.

### Recommendation
- Do not normalize the signature silently in `verifyMessageWithSecp256k1PemPubKey`; instead reject non-canonical (high-S) signatures by comparing the supplied raw signature against its normalized form and failing verification if they differ (mirroring the strict behavior of `signature.verify()`).
- For the generic OpenSSL-based curves in `verifyMessageWithPemPubKey`, additionally validate that the DER-encoded `s` value is in the lower half of the curve order before accepting the signature.
- Document that `is_valid_sig`/`vrf_verify` signatures are not unique identifiers for a given `(message, pubkey)` pair, and recommend AA authors dedupe on `sha256(message)` (or the message/business nonce itself) rather than on the raw signature bytes.

### Proof of Concept
1. An AA is written to accept a signed voucher via `is_valid_sig(trigger.data.message, pem_key, trigger.data.sig)` and marks the voucher redeemed by storing `var[trigger.data.sig] = true` to prevent replay.
2. The legitimate holder (or anyone who has seen a valid signature, e.g. leaked via a public unit or oracle feed) computes the ECDSA-malleated counterpart `(r, n-s)` of the same signature (trivial: `s' = curve_order - s`), re-encodes it in DER/base64.
3. First trigger uses signature `(r, s)`, is accepted, `var[(r,s)] = true` stored.
4. Second trigger uses the malleated `(r, n-s)`; because `verifyMessageWithSecp256k1PemPubKey` normalizes before verifying, `is_valid_sig` returns `true` again; since `var[(r,n-s)]` was never set, the AA's replay guard does not trigger and the voucher is redeemed a second time, resulting in double payout from the AA.
