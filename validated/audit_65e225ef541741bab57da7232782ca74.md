### Title
Missing `nonReentrant` on `handleERC20Transfer` Enables Malicious Operator to Drain Bridged ERC20 Assets via ERC777 Callback — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.handleERC20Transfer` is missing the `nonReentrant` modifier that its sibling `BridgeTransferKLAY.handleKLAYTransfer` carries. When an ERC777-compatible token is registered as a bridge token, the `safeTransfer` call at the end of `handleERC20Transfer` triggers the ERC777 `tokensReceived` hook on the recipient. If the recipient contract is also a registered bridge operator, it can re-enter `handleERC20Transfer` with a different nonce, executing a chain of bridge payouts in a single transaction and draining the bridge of all pending ERC20 balances.

---

### Finding Description

`BridgeTransferKLAY` inherits `ReentrancyGuard` and marks `handleKLAYTransfer` with `nonReentrant`: [1](#0-0) [2](#0-1) 

`BridgeTransferERC20` does **not** inherit `ReentrancyGuard` and `handleERC20Transfer` carries only `onlyOperators`: [3](#0-2) 

After all nonce-state updates are written, the function makes an external call to the token contract: [4](#0-3) 

For an ERC777 token, `safeTransfer` internally calls `_callTokensReceived`, which invokes `tokensReceived` on the recipient address: [5](#0-4) 

If `_to` is a contract that is also registered as a bridge operator (`operators[_to] == true`), its `tokensReceived` implementation can call `handleERC20Transfer` again with a different nonce. Because `onlyOperators` checks `msg.sender` and `_to` is the new `msg.sender` in the re-entrant call, the check passes.

The nonce-tracking loop in `_updateHandleNonce` is called once per re-entrant frame: [6](#0-5) 

Each re-entrant frame sets `handleNoncesToBlockNums[M]` and advances `lowerHandleNonce`, then makes another external call, allowing the chain to continue until the bridge's token balance is exhausted or the call stack limit is reached.

`BridgeTransferERC721.handleERC721Transfer` has the same missing guard: [7](#0-6) 

---

### Impact Explanation

A malicious operator whose contract address is also registered as an operator can:

1. Pre-vote (with threshold = 1, or pre-accumulate votes from other operators) for nonces N, N+1, N+2, …
2. Call `handleERC20Transfer(nonce=N, _to=attacker_operator_contract)`.
3. The ERC777 `tokensReceived` hook fires on `attacker_operator_contract`, which re-enters with `handleERC20Transfer(nonce=N+1, _to=attacker_operator_contract)`.
4. The chain continues, executing every pre-voted nonce in a single transaction.

Each frame transfers the full `_value` for that nonce out of the bridge. The bridge's entire ERC20 token balance for all pending nonces is drained in one atomic transaction. The corrupted `lowerHandleNonce` and `recoveryBlockNumber` values left behind also break the bridge's recovery mechanism, permanently blocking any future legitimate transfers for skipped nonces (the `_lowerHandleNonceCheck` rejects them as `"removed vote"`). [8](#0-7) 

---

### Likelihood Explanation

- **Operator registration** is controlled by the bridge owner (`onlyOwner`), so the attacker must either be the owner or socially engineer the owner into registering a malicious contract as an operator.
- **ERC777 token** must be registered as a bridge token; standard ERC20 tokens without callbacks are not exploitable.
- With operator threshold = 1 (the default set in the constructor), a single operator can vote for any nonce unilaterally. [9](#0-8) 

The combination of a compromised or malicious operator and an ERC777 bridge token is a realistic semi-trusted threat scenario, especially for service-chain deployments where operators are often the same entity as the bridge deployer.

---

### Recommendation

1. Add `nonReentrant` to `handleERC20Transfer` and `handleERC721Transfer`, mirroring `handleKLAYTransfer`:

```solidity
// BridgeTransferERC20.sol
contract BridgeTransferERC20 is BridgeTokens, IERC20BridgeReceiver, BridgeTransfer, ReentrancyGuard {
    function handleERC20Transfer(...) public onlyOperators nonReentrant { ... }
}

// BridgeTransferERC721.sol
contract BridgeTransferERC721 is BridgeTokens, IERC721BridgeReceiver, BridgeTransfer, ReentrancyGuard {
    function handleERC721Transfer(...) public onlyOperators nonReentrant { ... }
}
```

2. Consider using `safeTransferFrom` with a pull-payment pattern instead of push-transfer to further reduce external-call surface.

---

### Proof of Concept

```solidity
// Attacker contract — registered as both an operator and used as _to
contract AttackerOperator is IERC777Recipient {
    Bridge bridge;
    address token;
    uint64 nextNonce;

    // Called by ERC777 after each safeTransfer
    function tokensReceived(
        address, address, address, uint256,
        bytes calldata, bytes calldata
    ) external override {
        if (nextNonce <= MAX_NONCE) {
            // Re-enter handleERC20Transfer with the next pre-voted nonce
            bridge.handleERC20Transfer(
                bytes32(uint256(nextNonce)),
                victim,
                address(this),   // _to = this operator contract
                token,
                DRAIN_AMOUNT,
                nextNonce,
                block.number,
                ""
            );
            nextNonce++;
        }
    }
}
```

**Steps:**
1. Deploy `AttackerOperator`; have bridge owner register it as an operator.
2. With threshold = 1, call `handleERC20Transfer(nonce=0, _to=AttackerOperator)` from `AttackerOperator`.
3. Each ERC777 callback re-enters with nonce 1, 2, 3, … until the bridge is drained.
4. All token balances for pending nonces are transferred to `AttackerOperator` in one transaction; `lowerHandleNonce` is advanced past all skipped nonces, permanently blocking recovery. [10](#0-9) [11](#0-10)
