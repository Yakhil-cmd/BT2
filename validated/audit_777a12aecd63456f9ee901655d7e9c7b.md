### Title
Webhook signature verification uses an attacker-controlled org while payload processing targets an unrelated repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using an org name read straight out of the *unverified* request body, while the handlers that actually act on the webhook (creating stacks syncs, statuses, memberships, etc.) resolve their target `Repository`/`Stack` from a *different, independently-controlled* field of that same unverified body. On a multi-org Shipit deployment, these two lookups are never checked for consistency, so a signature that is valid for org A can be used to authorize a payload that writes to org B's repository/stack.

### Finding Description
`Shipit` supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret` (`lib/shipit.rb:170-200`, `docs/setup.md` multi-org config example). The webhook signature check is: [1](#0-0) 

`repository_owner` used to pick the app config comes straight from the JSON body before any signature check: [2](#0-1) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw payload* to handlers, and the base `Handler` class resolves the actual `Repository`/`Stack` to mutate from a completely separate JSON field, `repository.full_name`, with no cross-check against `repository.owner.login`: [3](#0-2) 

`Repository.from_github_repo_name` then looks up any repository by `owner/name` regardless of who authenticated the request: [4](#0-3) 

This breaks the binding the engine implicitly relies on: *the organization whose secret authenticated the webhook* must equal *the repository/stack that the webhook is allowed to write to*. Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the write target) are two unrelated, attacker-supplied strings inside the same unverified body, an attacker who legitimately administers one org onboarded to the Shipit instance (and therefore knows that org's own `webhook_secret`) can forge a signature that validates against their own org while forging a payload whose `repository.full_name` points at a victim org's repository.

### Impact Explanation
A forged `push`, `status`, `check_suite`, `membership`, `pull_request`, etc. event lets the attacker drive `Shipit::Webhooks::Handlers::*` against a repository/stack they do not own or control (e.g., `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for the victim's stack, and a forged `status` event can mark an arbitrary victim commit "success", which can feed `Stack#deployable?`/`trigger_continuous_delivery`). This is a cross-organization/cross-repository write achieved purely by exploiting a mismatch between the entity whose credential (webhook secret) was checked and the entity whose data got mutated — meeting the "organization that authenticated versus the repository that is written" analog and the Critical bucket for cross-repository writes / unauthorized deploy.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (a fully documented, supported configuration in `docs/setup.md`), and requires the attacker to control (or be an admin of) at least one org already onboarded to that Shipit instance — no Shipit session, API token, or GitHub token belonging to the victim org is needed. This is a realistic multi-tenant scenario and does not depend on the host application deviating from documented mounting.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after selecting the GitHub App by `repository_owner`, verify that the org used for signature selection actually matches the owner encoded in `repository.full_name` (and any `organization.login`) before dispatching to handlers; reject the request if they diverge instead of trusting the unverified `full_name` field independently.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per the documented multi-org `secrets.yml` schema).
2. Attacker administers `attacker-org`'s GitHub App and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker POSTs to the webhooks endpoint with `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body.
5. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and validates successfully, since the attacker signed with the correct secret for that org.
6. `PushHandler#process` (dispatched with the full payload) calls `Repository.from_github_repo_name('victim-org/victim-repo')` and invokes `stack.sync_github(expected_head_sha: ...)` on the victim's stack — a write to a repository the attacker never authenticated for.
