This confirms the critical binding-break vulnerability. The `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository', 'owner', 'login')` to select which GitHub App's `webhook_secret` verifies the HMAC signature [1](#0-0) , while `Handlers::Handler#stacks` derives the repository actually acted upon from a completely different field, `params.dig('repository', 'full_name')` [2](#0-1) . Nothing enforces that `repository.owner.login` and the owner segment embedded in `repository.full_name` refer to the same organization — these are two independent, attacker-supplied JSON fields in the same unsigned-until-verified payload.

### Title
Webhook signature verified against `repository.owner.login` while the repository acted on is selected from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The `WebhooksController` picks the GitHub App (and thus the `webhook_secret` used for HMAC verification) using `repository.owner.login`/`organization.login` from the JSON body, but every webhook handler resolves the target `Repository`/`Stack` using the sibling field `repository.full_name`. Because both fields live in the same attacker-controlled JSON body and are never cross-checked, an attacker who legitimately controls a GitHub App installation on their own organization (and therefore knows that org's `webhook_secret`) can forge a validly-signed webhook whose `full_name` points at a victim organization's tracked repository.

### Finding Description
`WebhooksController#verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [3](#0-2) . This selects the HMAC secret to check against, but it is computed from the exact same attacker-supplied `request.raw_post`, so an attacker who owns any GitHub App installed on some organization "attacker-org" knows the corresponding `webhook_secret` and can sign an arbitrary payload with it, as long as `repository.owner.login` (or `organization.login`) says `"attacker-org"`.

Every default handler (`PushHandler`, `PullRequest::*`, `StatusHandler`, `CheckSuiteHandler`) inherits `Handlers::Handler#stacks`, which instead resolves the target using:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`Repository.from_github_repo_name` splits this string on `/` and looks up by `owner`/`name` columns independently of the `repository.owner.login` field used for signature verification [4](#0-3) .

Nothing in the codebase asserts `repository.owner.login == repository.full_name.split('/').first`. The signature-authenticating field and the field actually driving which `Repository`/`Stack` record is mutated are disjoint, unsigned-relative-to-each-other JSON keys in the same payload — exactly the "organization that authenticated versus the repository that is written" binding break.

### Impact Explanation
This breaks the equality: `organization whose webhook_secret authenticated the request == organization whose repository record is acted upon`. With a forged `full_name` pointing at a victim's tracked stack, an attacker can drive `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the matching branch [5](#0-4) , enqueuing `GithubSyncJob` against the victim stack with an attacker-chosen `expected_head_sha` [6](#0-5) . `StatusHandler` and `CheckSuiteHandler` can similarly be driven to alter the recorded CI/status state of the victim's commits, and continuous-deployment pipelines gated on green statuses can be manipulated to trigger an unauthorized deploy on the victim's stack. This crosses a repository trust boundary and can result in an unauthorized deploy/rollback trigger on a repository the attacker does not own.

### Likelihood Explanation
The only prerequisite is that the attacker controls (or can install) any GitHub App on an arbitrary organization that this Shipit instance also has configured/knows about — which is a normal, low-privilege, self-service action on GitHub (create your own org, install your own app, get `webhook_secret`). No access to the victim's org, no `ApiClient` token, and no Shipit account is required. The attacker only needs to know the victim's tracked `owner/name` (public information for any public repo).

### Recommendation
After verifying the HMAC signature, re-derive the organization from `repository.full_name` (the same field the handlers use) rather than trusting `repository.owner.login`/`organization.login` independently — or better, verify that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting the request (422) on mismatch.

### Proof of Concept
1. Attacker creates their own GitHub organization `attacker-org` and installs a Shipit-integrated GitHub App on it, obtaining `webhook_secret_A` (something they legitimately possess for their own org).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha, e.g. sha of a bad/malicious commit already reachable>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')`, whose `webhook_secret_A` correctly verifies the attacker's own signature — the request passes verification.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's real tracked stack, even though the request was never signed by `victim-org`'s webhook secret.
