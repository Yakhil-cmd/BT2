### Title
Stack-scoped API tokens can read any stack's CCMenu status, bypassing the token's `stack_id` binding - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` resolves the target `Stack` via a raw `Stack.from_param!(params[:stack_id])` lookup instead of the scope used by every other API controller, which filters by the authenticated `ApiClient`'s bound `stack_id`. This breaks the equality "stack a token authorises == stack it touches" and allows a token that is supposed to be restricted to a single stack to read the deploy/CI status of any stack in the instance.

### Finding Description
Every other resource in `Shipit::Api::BaseController` resolves the target stack through the `stacks` scope, which restricts results to the stack the `ApiClient` is bound to: [1](#0-0) 

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` class, not through `stacks`, so the check "does `current_api_client.stack_id` match the requested stack" is never performed. The controller only enforces `require_permission :read, :stack`, which is a coarse permission-name check (`ApiClient#check_permissions!`) unrelated to *which* stack the client is bound to: [3](#0-2) 

An `ApiClient` can legitimately be created bound to a single stack (`belongs_to :stack, optional: true`), and the codebase relies on this binding for authorization elsewhere: [4](#0-3) 

Because `CCMenuController#stack` never consults `current_api_client.stack_id`, a client whose token was minted (or manually scoped by an admin) for Stack A can be presented with `stack_id=B` on the `GET /api/stacks/:stack_id/ccmenu` route and will be served Stack B's latest deploy/rollback status, deploy id, and completion timestamps.

The equality broken is exactly the class of bug flagged in the report by analogy: a resource is checked against a "amount"/authorization value (here, `current_api_client.stack_id`) in one code path (`BaseController#stack`), but a parallel code path (`CCMenuController#stack`) computes the resource directly from attacker-controlled input without re-applying that same authorization filter — mirroring how `pendingPayouts` was tracked separately but excluded from the balance calculation used by other functions.

### Impact Explanation
This meets the "High" bar of "unauthenticated read of stack state, task streams or deploy output" in spirit — more precisely it is an authenticated-but-unauthorized cross-stack read: a token deliberately scoped to one stack (least-privilege token, e.g. handed to a monitoring dashboard for a single project) discloses build/deploy status of unrelated stacks it was never authorized for. This can leak deployment cadence, revision SHAs, and deploy timestamps of other teams' stacks to a holder of a narrowly-scoped token.

### Likelihood Explanation
Likelihood is high given the attack requires nothing beyond `read:stack` permission and any valid, even narrowly stack-scoped, API token/Basic-Auth credential (which routes through `authenticate_api_client`'s `super` path when no `params[:token]` is supplied). No special privilege, GitHub identity, or session is required beyond possessing such a token — only the target `stack_id` (a simple `owner/repo/environment` path segment) needs to be guessed or known.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the same `stacks` scope used elsewhere:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so the `current_api_client.stack_id` restriction is uniformly enforced, consistent with `StacksController`, `TasksController`, `DeploysController`, etc.

### Proof of Concept
1. Create/obtain an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A only (e.g., an intentionally least-privilege token issued to a third party for monitoring Stack A).
2. Using that client's Basic Auth credentials, issue `GET /api/stacks/<owner>/<repo>/<environment-of-stack-B>/ccmenu` (Stack B being any other stack in the instance).
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(...)`, the request succeeds and returns Stack B's CI/deploy status in the CCMenu XML response, despite the client being authorized only for Stack A.
