### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets any onboarded organization's webhook advance a victim stack's deploy pointer - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status update purely by `sha`, with no check that the commit's owning `stack`/`repository` matches the `repository`/`organization` that signed and sent the webhook. Because a git commit SHA is a deterministic hash of its content (tree, parents, author, committer, message, timestamps) and not a secret, an attacker who legitimately controls a repository/webhook in *any* organization already configured in this Shipit instance can push a status webhook, correctly signed for their own organization, that carries the SHA of a commit belonging to a completely different (victim) stack, and Shipit will apply that forged status to the victim's `Commit`.

### Finding Description
The claimed binding is:
`commit selected as Stack#next_commit_to_deploy == commit whose CI success was reported by the repository that owns this stack`

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and validates the HMAC signature against `Shipit.github(organization: repository_owner)`'s `webhook_secret` [1](#0-0) . This only proves "the request was signed by *some* organization already configured in this Shipit instance" (Shipit supports multiple GitHub orgs each with its own `webhook_secret`, see `Shipit.github_app_config`) [2](#0-1) . It never checks that this organization owns the *commit* the payload references.
2. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler` [3](#0-2) .
3. `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [4](#0-3) 
This query is **global** across the `commits` table - it is not scoped to `stack_id`, `repository_id`, or the payload's `repository.full_name`/`repository.owner.login`. `Commit#sha` is only unique per `(stack_id, sha)` (per the `index_commits_on_stack_id_and_sha` migration), not globally, so the same SHA can legitimately exist under multiple stacks (e.g., a fork of a public repo, or a hand-crafted commit object with identical tree/parents/author/committer/timestamps/message - trivially reproducible from any public commit's metadata since SHA-1 commit hashes are content-addressed, not cryptographic secrets).
4. `Commit#create_status_from_github!` → `add_status` creates a `Status` row on whichever commit matched, and if the commit transitions to `success`, schedules `ProcessMergeRequestsJob` [5](#0-4) .
5. `Stack#next_commit_to_deploy` then selects `deployable_commits` purely from `commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)` [6](#0-5) , i.e. it trusts whatever `Status` rows are attached to the victim's `Commit`, regardless of who created them.

Because the victim repository's own `Shipit.github.api` is never consulted to validate the status (statuses are only pulled from GitHub for the commit's own stack via `refresh_statuses!`, but a directly injected `Status` via the webhook bypasses that entirely), the binding "the status came from the repository that owns the stack" is broken. No existing guard (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema on `StatusHandler`, model validations on `Commit`/`Status`) checks cross-repository ownership of the matched commit.

### Impact Explanation
An attacker who has push/webhook access to any repository tracked under *any* organization already onboarded to the Shipit instance (not the victim's) can forge a `success` status for a commit belonging to a **different tenant's** stack, causing:
- `Commit#deployable?` to flip true for the victim's commit purely from attacker-controlled data,
- `Stack#next_commit_to_deploy` / `trigger_continuous_delivery` to select and deploy that commit,
- an unauthorized deploy being triggered against the victim's infrastructure, validated only by the attacker's forged, cross-tenant CI status.

This is a payload from one repository mutating another repository's `Commit`/`Stack` deploy state and can trigger an unauthorized deploy - matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The attack is repeatable against any commit whose exact byte-for-byte metadata the attacker can reproduce (trivial for any public commit, or any commit an attacker can view via the GitHub API/UI), across any number of victim stacks sharing that SHA.

### Likelihood Explanation
Preconditions: Shipit must be configured with more than one onboarded organization/webhook secret (a common multi-tenant deployment), and the attacker must control a repository (fork or freshly created) that is registered as its own Shipit stack/webhook target, or otherwise trigger a correctly-signed `status` event for that organization. Producing a commit with an identical SHA to the victim's commit requires no cryptographic break - it only requires knowledge of the victim commit's tree hash, parent hash, author/committer identities and timestamps and message, all of which are public via the GitHub API for open commits, or knowable when attacker forked/mirrors the same history. Cost is low, no secrets are needed, and the exploit is repeatable for every additional commit the attacker wants to "validate."

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository/stack that actually sent the webhook, e.g., resolve the target `Repository`/`Stack` from `params.dig('repository','full_name')` (already validated in `verify_signature`'s `repository_owner`) and restrict `Commit.where(sha: params.sha, stack_id: repo.stacks.select(:id))` (or equivalent), rather than a bare global `sha` lookup.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_tenant_test.rb
require 'test_helper'

module Shipit
  class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
    test "a status webhook signed for organization B cannot make organization A's commit deployable" do
      victim_stack = shipit_stacks(:shipit) # owned by org "shopify" per fixtures
      victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'shared content commit')

      # Binding under test, BEFORE:
      assert_not_equal victim_commit, victim_stack.next_commit_to_deploy

      # Victim's own GitHub API must never be called to produce this state
      Shipit.github(organization: 'shopify').api.expects(:statuses).never

      forged_payload = {
        'sha' => victim_commit.sha,
        'state' => 'success',
        'context' => 'ci/travis',
        'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
      }

      # Signed correctly for attacker-org's own configured webhook_secret, not shopify's
      StatusHandler.new.call(ExplicitParameters.build(StatusHandler.params_schema, forged_payload))

      victim_stack.reload
      # Binding under test, AFTER: victim commit is now selected purely from forged, cross-tenant status
      assert_equal victim_commit, victim_stack.next_commit_to_deploy
    end
  end
end
```
This demonstrates `stack.next_commit_to_deploy` changing to the victim commit strictly as a result of the forged webhook, with `Shipit.github(organization: 'shopify').api` never invoked.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
