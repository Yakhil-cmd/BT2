### Title
Cross-organization webhook forgery via unbound `repository.owner.login` vs `repository.full_name` fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App's webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), a field read directly out of the unauthenticated, attacker-suppliable JSON body. The stack/repository that is actually *acted upon* by the event handler is derived from a different field in the same payload, `repository.full_name`. These two fields are never cross-validated, and if the resolved GitHub App has no `webhook_secret` configured, signature verification is skipped entirely, letting an attacker mint a "verified" webhook for one organization while manipulating a stack that belongs to a completely different, properly-secured organization.

### Finding Description
`verify_signature` picks the GitHub App/secret using a value taken straight from the JSON body of the incoming, unauthenticated POST: [1](#0-0) [2](#0-1) 

The chosen app's `verify_webhook_signature` short-circuits to `true` whenever that app has no `webhook_secret` configured — a state explicitly presented as valid/optional in the shipped example configs: [3](#0-2) [4](#0-3) 

Meanwhile, every event handler resolves the target `Stack`/`Repository` using an entirely different payload field, `repository.full_name`, with no relation to `repository.owner.login`: [5](#0-4) 

Because Shipit explicitly supports multiple independently configured GitHub organizations/Apps in one deployment (`Shipit.github(organization:)`, `github_app_config`), an attacker only needs to know (or guess) that *any one* configured organization has `webhook_secret` left blank (shown as a normal/example value in the docs and templates) in order to satisfy `repository_owner`/`organization.login` for that org, while setting `repository.full_name` in the same JSON body to `victim-org/victim-repo`, a stack tracked under a different, properly secured organization: [6](#0-5) [7](#0-6) 

The binding that should hold — `organization whose signature authenticated the request == organization owning the repository the handler writes to` — is not enforced anywhere in `WebhooksController` or `Handler`.

### Impact Explanation
Once "verified" this way, the attacker controls arbitrary `push`, `status`, `check_suite`, `pull_request`, and `membership` event payloads against a victim stack they don't own. The `status` webhook handler creates a `Commit::Status` directly from attacker-controlled `sha`, `state`, `context`, `target_url` fields (as exercised in `test/controllers/webhooks_controller_test.rb`): [8](#0-7) 

Forging a `success` status for a required CI context on a malicious commit can satisfy `required_statuses`/`StatusChecker` checks used by `deployable?` and the merge queue (`reject_unless_mergeable!`, `any_status_checks_missing?`), potentially leading to an unauthorized deploy or an auto-merge via continuous delivery/merge queue on a victim's stack: [9](#0-8) [10](#0-9) 

This satisfies the "unauthorized deploy/merge" impact tier.

### Likelihood Explanation
Exploitation requires: (1) a Shipit deployment configured with more than one GitHub organization (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), and (2) at least one of those organizations having a blank `webhook_secret` (shown as the default/example value in shipped config templates). No authentication, API token, or GitHub write access is required — only the ability to POST to the public `/webhooks` endpoint.

### Recommendation
Bind the two identities: derive the target repository/stack strictly from the organization that successfully authenticated the request (or verify `repository.owner.login`/`organization.login` equals the owner of the resolved `repository.full_name` before processing). Additionally, do not silently treat a missing `webhook_secret` as "verification passed" — fail closed (reject) instead of returning `true` when no secret is configured, or require an explicit opt-in flag to disable signature checking.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (properly configured with a real `webhook_secret`) and `orgB` (left with `webhook_secret: nil`, as templated in `config/secrets.development.shopify.yml`). `orgA` owns the tracked stack `orgA/victim-repo`.
2. Attacker sends an unauthenticated POST to `/webhooks` with header `X-Github-Event: status` and a JSON body:
```json
{
  "sha": "<malicious-commit-sha-in-orgA/victim-repo>",
  "state": "success",
  "context": "ci/required",
  "target_url": "https://evil.example",
  "repository": {
    "owner": { "login": "orgB" },
    "full_name": "orgA/victim-repo"
  }
}
```
3. `repository_owner` resolves to `"orgB"` → `Shipit.github(organization: "orgB").verify_webhook_signature` returns `true` unconditionally because `orgB.webhook_secret` is blank (`app/lib/shipit/github_app.rb` lines 76-83).
4. The `status` handler (via `Handler#stacks`/`repository_name`, `app/models/shipit/webhooks/handlers/handler.rb` lines 30-38) resolves `Repository.from_github_repo_name("orgA/victim-repo")`, writing a forged "success" status onto `orgA`'s commit despite the request never being signed by `orgA`'s real webhook secret.

Note: I was not able to view the full contents of `app/models/shipit/webhooks/handlers/status_handler.rb` and `check_suite_handler.rb` directly (only inferred their effect via `test/controllers/webhooks_controller_test.rb` and `Handler` base class) due to index size limits; a Devin session with full repository access would be needed to confirm the exact status-creation code path and enumerate all other handlers similarly affected (e.g., `membership_handler.rb`, `pull_request/*`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    # Backward compatibility

      config = secrets.github
    else
      config = github_app_config(organization)
```
