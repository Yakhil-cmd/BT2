### Title
Webhook signature is verified against the payload's claimed organization, but handlers act on repositories/commits identified by a different, unverified payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to check the HMAC signature against using `repository_owner`, which is read straight from the untrusted JSON body (`repository.owner.login` or `organization.login`). The event handlers that subsequently mutate application state pick their target `Repository`/`Stack`/`Commit` using a *different* field from that same body (`repository.full_name`, or for `StatusHandler`, no repository field at all). Because the signature check only proves "this body was signed by *some* organization configured in Shipit," and never proves that the organization used for verification is the same one that owns the resource being written, an attacker who controls (or has webhook access to) one organization tracked by the Shipit instance can forge a webhook whose signature is valid for their own org while its payload content targets a stack/commit belonging to a different, victim organization.

### Finding Description
`verify_signature` computes the app/secret to check against from the payload itself, before any handler runs: [1](#0-0) [2](#0-1) 

Once verification passes, the raw parsed body is dispatched unchanged to every registered handler for the event: [3](#0-2) 

The base `Handler` class resolves the target `Stack`s via `repository.full_name` - a field completely independent from the `repository.owner.login`/`organization.login` field used for signature verification: [4](#0-3) 

`PushHandler` uses this repository-scoped lookup to enqueue a sync with an attacker-supplied `after` SHA: [5](#0-4) 

`StatusHandler` is worse: it does not scope by repository at all. It looks up commits globally by SHA across the entire Shipit database and writes a CI status onto them: [6](#0-5) 

`Repository.from_github_repo_name` further shows that the owner is only ever used to select a `Repository` record and its associated GitHub App for *outbound* API calls, not to constrain which record the inbound webhook is allowed to touch: [7](#0-6) 

**Equality the code is supposed to enforce:** `organization used to select webhook_secret for verification == organization/repository that owns the resource being mutated by the handler`.

**What actually holds:** the controller derives the verification organization from `params.dig('repository','owner','login') || params.dig('organization','login')` (webhooks_controller.rb:61), while `Handler#repository_name`/`StatusHandler` derive (or entirely skip) the target resource from `payload.dig('repository','full_name')` or a bare `sha`. Nothing forces these two payload-derived values to agree, so an attacker who can produce a validly-signed webhook for organization A (e.g., because they administer or can register a webhook on any org/repo Shipit tracks) can set `repository.full_name` (or, for `status`, just a matching `sha`) to point at organization B's tracked repository/commit. The signature check passes using A's secret, yet the write lands on B's resources - exactly the "organization that authenticated versus the repository that is written" binding break called out as an in-scope analog class.

### Impact Explanation
This is a cross-repository write: an actor who is a legitimate but low-privilege webhook sender for one tracked organization/repo can affect Stacks/Commits belonging to a completely different organization/repo tracked by the same Shipit instance, without ever authenticating to that victim organization. Concretely:
- Via `status` events, an attacker can set arbitrary CI status (`state`, `context`, `description`, `target_url`) on any commit SHA in the entire installation merely by knowing/guessing the SHA, because `StatusHandler` never checks which repository owns the commit at all (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`). Since Shipit's deploy pipeline gates progress on commit statuses (`Shipit::Status`, `Shipit::CommitChecks`), this can be used to fabricate a passing/blocking status on a victim's commit, directly affecting deploy-readiness decisions.
- Via `push`/`check_suite` events, an attacker can force sync/check-run-refresh jobs on a victim's stack by supplying `repository.full_name` for the victim while signing with their own org's secret.

This satisfies the "cross-repository writes" / unauthorized-influence-on-deploy criteria in scope.

### Likelihood Explanation
Exploitability requires the attacker to be able to produce a validly-signed webhook body for at least one organization configured in the same Shipit deployment (i.e., they must be able to trigger/craft webhook deliveries for an org they control, which is a normal, low-privilege capability for anyone who can add a webhook to their own GitHub org/repo pointed at the shared Shipit instance - a realistic scenario for the documented "Using Multiple GitHub Applications" multi-org configuration, see `docs/setup.md:181-209`). No Shipit session, API token, or GitHub App private key is needed for the victim organization. This is a design-level gap rather than a rare race condition, so likelihood is elevated whenever a single Shipit instance serves more than one GitHub organization/repository.

### Recommendation
Enforce that the organization/repository used to verify the webhook signature is the same one the handler is permitted to act on:
- Have `WebhooksController#verify_signature` record the verified organization, and pass it (not just the raw payload) into `Shipit::Webhooks.for_event(event)`.
- In `Handler#stacks`/`Handler#repository_name` and in `StatusHandler`, explicitly re-derive the owning organization of the resolved `Repository`/`Stack`/`Commit` and assert it equals the organization that was cryptographically verified before performing any mutation.
- In particular, scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup by the verified repository/organization instead of querying globally.

### Proof of Concept
1. Shipit is configured with two GitHub organizations, `attacker-org` (attacker administers a repo/webhook here, and thus knows or can retrieve `attacker-org`'s `webhook_secret` from their own GitHub App webhook delivery settings/logs) and `victim-org/victim-repo` (a Stack tracked by the same Shipit instance), per the multi-org config in `docs/setup.md:181-209`.
2. Attacker crafts a `status` webhook body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"` (`app/controllers/shipit/webhooks_controller.rb:61`), fetches `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully because it was computed with that org's real secret.
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then runs `Commit.where(sha: params.sha)` globally and writes a forged `success` status onto the victim's commit - a commit in `victim-org/victim-repo`, an organization the attacker never authenticated against.
