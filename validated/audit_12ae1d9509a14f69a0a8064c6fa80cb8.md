### Title
`provision?` operator-precedence bug lets `review_stacks_enabled: false` repositories still auto-provision ReviewStacks via the `allow_with_label`/`prevent_with_label` branches - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends `repository.review_stacks_enabled` to gate every provisioning behavior, but due to Ruby operator precedence it only gates the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches are evaluated independently. An unprivileged fork contributor who opens a PR with the configured label on a repo where an operator explicitly left `review_stacks_enabled` off can force creation of a `ReviewStack` whose `branch` is the attacker's fork ref, leading to provisioning and eventual command execution from attacker-controlled `shipit.yml`/branch content.

### Finding Description
The broken binding is: `repository.review_stacks_enabled` (the flag an operator toggles in Settings) should equal the actual gating condition applied to *all* provisioning behaviors reachable from `provision?`. Instead: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Ruby parses `a && b || c || d` as `(a && b) || c || d`. So `review_stacks_enabled` only participates in the first disjunct (`allow_all`); the `allow_with_label` and `prevent_with_label` disjuncts are entirely independent of `review_stacks_enabled`.

Call path: `POST /webhooks` with `X-Github-Event: pull_request`, `action=opened` → `OpenedHandler#process` → `respond_to_pull_request_opened?` (`action == "opened" && provision?`) → `provision?` returns true via the label branch even though `review_stacks_enabled == false` → `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` → `find_or_create!` → `create!`, which sets `branch: params.pull_request.head.ref` from attacker-controlled PR head ref and enqueues it for provisioning: [2](#0-1) [3](#0-2) 

Existing guards do not prevent this: `ExplicitParameters` schema in the `params do ... end` block only validates payload shape, not authorization; webhook signature verification (elsewhere in the base `Handler`) authenticates that GitHub sent the payload but does not check `review_stacks_enabled`; and no model validation on `Repository` or `ReviewStack` re-derives or enforces `review_stacks_enabled` at creation time — `create!`/`stack_attributes` trust whatever the caller (here, the buggy `provision?`) decided.

The attacker's exact action: fork the target repo, open a pull request (action=opened) with a branch name/ref of their choosing, and label it with the configured `provisioning_label_name`, on a repository configured with `provisioning_behavior: allow_with_label` and `review_stacks_enabled: false`. GitHub will emit the `pull_request` webhook for this action to the Shipit host, which — assuming the app's own webhook signature verification passes for genuine GitHub-originated events (this part is not attacker-controlled but doesn't need to be, since it's a legitimate webhook from GitHub for the fork's PR against the target repo) — triggers the handler.

### Impact Explanation
A `ReviewStack` record is created and queued for provisioning for a repository whose operator explicitly disabled review stacks (`review_stacks_enabled: false`), using the attacker's fork branch as the deploy source. Since review stack provisioning subsequently checks out and runs the branch's `shipit.yml`/deploy steps, this leads to command execution on the deploy host driven by attacker-controlled repository content — matching the Critical impact category ("RCE on the deploy host ... via ... an unauthorized deploy"). The write happens for a repository/record whose configuration ("review stacks disabled") was not honored, and is repeatable against any repository configured with `allow_with_label` or `prevent_with_label` plus `review_stacks_enabled: false`.

### Likelihood Explanation
Preconditions are configuration-only and plausible: `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`) while `review_stacks_enabled` is left false — a state an operator could easily reach if they configure a label policy before flipping the master "enable review stacks" switch, or intentionally disable review stacks later without changing the behavior setting. No attacker privilege beyond opening a PR and applying a label (which PR authors can typically do on their own PRs, or via automation) is required. Attacker cost is minimal: fork, branch, label, open PR. Fully repeatable across any repository matching the misconfiguration.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates every branch, e.g.:

```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same fix to the analogous logic in `labeled_handler.rb`, `unlabeled_handler.rb`, and `reopened_handler.rb`, which share the same `provisioning_behavior_*` pattern and should be checked for the identical precedence bug.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
1. Create a `Shipit::Repository` fixture with `review_stacks_enabled: false` and `provisioning_behavior: "allow_with_label"`, `provisioning_label_name: "deploy-preview"`.
2. Build a `pull_request_opened` payload for that repository with `pull_request.labels = [{name: "deploy-preview"}]` and `pull_request.head.ref` set to an attacker-controlled branch name.
3. Assert binding before: `repository.review_stacks_enabled == false` and expect `Shipit::Stack.count`/`Shipit::ReviewStack.count` to remain unchanged after `OpenedHandler.new(params).process`.
4. Run `OpenedHandler.new(payload_parsed(:pull_request_opened)).process`.
5. Assert `Shipit::ReviewStack.count` changed (bug present) vs. expected `no_change` (post-fix) — i.e., `assert_no_difference("Shipit::ReviewStack.count") { OpenedHandler.new(params).process }` should pass only after applying the recommended fix; currently it fails, demonstrating the vulnerability.
