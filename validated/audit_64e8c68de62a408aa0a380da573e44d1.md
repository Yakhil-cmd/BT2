### Title
Missing `review_stacks_enabled` gate in `provision?` allows review-stack creation on repos that opted out - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` only requires `review_stacks_enabled` to be true for the `provisioning_behavior_allow_all?` branch; the `allow_with_label` and `prevent_with_label` branches are evaluated independently of `review_stacks_enabled`. An attacker who can open a labeled PR against a repository configured with `provisioning_behavior: allow_with_label` can trigger `ReviewStack` creation and provisioning even when `review_stacks_enabled` is `false`.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` must hold for any `ReviewStack` to be created. Tracing `provision?`: [1](#0-0) 

Due to `&&` binding tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

Only the first disjunct is gated by `review_stacks_enabled`; the second and third are not. So for a repository with `review_stacks_enabled: false`, `provisioning_behavior: allow_with_label`, and a configured `provisioning_label_name`, an attacker opening a PR from their own fork with that label attached makes `pull_request_has_provisioning_label?` true, making the middle disjunct true and `provision?` true — independent of `review_stacks_enabled`.

`respond_to_pull_request_opened?` then permits `process` to call: [2](#0-1) 

`ReviewStackAdapter#find_or_create!` → `create!` builds the stack straight from attacker-controlled PR data with no re-check of `review_stacks_enabled`: [3](#0-2) 

`branch: params.pull_request.head.ref` is taken directly from the PR head, i.e. the attacker's fork branch, and the stack is queued via `Shipit::ReviewStackProvisioningQueue.add(stack)`. No other guard in `ReviewStackAdapter`, `Repository`, or the webhook handler chain re-validates `review_stacks_enabled` before creation; the only enforcement point is the flawed `provision?` predicate itself. I did not find a model-level validation on `ReviewStack`/`Stack` requiring the owning `Repository#review_stacks_enabled` to be true, based on the searches performed.

### Impact Explanation
Once created and queued, the review stack's `shipit.yml`/deploy steps derive from the attacker's branch content, and provisioning proceeds through `TaskCommands#perform` → `Command#start` → `PTY.spawn` on the deploy host — Critical impact (RCE on the deploy host) for a repository that explicitly never opted into review stacks (`review_stacks_enabled: false`). This is repeatable against any repository configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`, inverted) regardless of the `review_stacks_enabled` flag, since the flag is silently ignored for those two branches.

### Likelihood Explanation
Preconditions: a `Repository` record must exist with `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`) and a `provisioning_label_name`, and `review_stacks_enabled: false`. This is a plausible/likely misconfiguration since an operator may reasonably believe `review_stacks_enabled: false` fully disables review-stack provisioning regardless of the `provisioning_behavior` setting. The attacker only needs to open a labeled PR from their own fork — no credentials, tokens, or team membership required — making the attacker cost minimal and the exploit trivially repeatable.

### Recommendation
Fix operator precedence/logic so `review_stacks_enabled` gates all branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Additionally, add a defensive check in `ReviewStackAdapter#create!` (or a `ReviewStack`/`Repository` validation) that refuses to create/provision a review stack when the owning repository has `review_stacks_enabled == false`.

### Proof of Concept
Minitest plan (webhook controller/integration test, no live GitHub):
1. Create `Shipit::Repository` fixture with `review_stacks_enabled: false`, `provisioning_behavior: :allow_with_label`, `provisioning_label_name: "deploy-preview"`.
2. Assert precondition: `repository.review_stacks_enabled == false` and `Shipit::Stack.count` baseline recorded.
3. POST `payload_parsed(:pull_request_opened)` webhook payload for this repository with `pull_request.labels` containing `{ name: "deploy-preview" }` and `pull_request.head.ref` set to an attacker-controlled branch name (e.g. `"evil-branch"`).
4. Assert `Shipit::Stack.count` increased by 1, the new stack's `branch == "evil-branch"`, and `Shipit::ReviewStackProvisioningQueue` received/queued the new stack — despite `repository.review_stacks_enabled == false`, demonstrating the binding `repository.review_stacks_enabled == true` does not hold before creation, disproving the intended invariant.
