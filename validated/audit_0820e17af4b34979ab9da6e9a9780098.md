### Title
Cross-organization forged webhooks via mismatched signature-authentication and target-repository binding - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC key used to authenticate an inbound webhook based on `repository.owner.login` (or `organization.login`) taken from the untrusted, attacker-controlled JSON body, while every `Handler` subclass resolves the repository/stack that is actually mutated from a *different* field of the same body, `repository.full_name`. In a multi-organization Shipit deployment these two fields are never cross-checked, so a party that legitimately knows one organization's `webhook_secret` can produce a validly-signed payload whose `repository.full_name` points at a completely different, unrelated organization's repository.

### Finding Description
`verify_signature` computes the signing organization like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the attacker-supplied JSON (`params.dig('repository', 'owner', 'login')`), and is fed to `Shipit.github(organization: repository_owner)`, which — in the documented multi-organization configuration — looks up a per-organization `webhook_secret` to verify the signature: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` hands the parsed JSON to every registered handler for the event: [4](#0-3) 

Every `Handler` (and every `PullRequest::*Handler`) resolves the repository it will act on from a *different, independently attacker-controlled* field of the very same payload, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

For example `StatusHandler` writes a new commit status using only `params.sha`/`params.state` after `stacks` (or `Commit.where(sha:)`, unscoped by repository) is resolved: [6](#0-5) 

`PushHandler` resolves stacks via `Repository.from_github_repo_name(repository_name)` (i.e., `full_name`) and triggers a resync: [7](#0-6) [8](#0-7) 

Nothing in the request path enforces that `repository.owner.login` (the value used to select the verifying secret) is consistent with `repository.full_name` (the value used to select the mutated repository/stack). This is exactly the class of bug the external report describes: one code path (`addValidators`) enforces a strict correspondence between the input and what is trusted, while a sibling path (`setWithdrawer`) accepts an unchecked value and uses it downstream. Here, the "authenticating organization" and the "repository actually written to" are two separate, unchecked fields of the same untrusted JSON body.

### Impact Explanation
If a Shipit instance is configured with multiple GitHub organizations (a documented, supported configuration — `docs/setup.md`'s "Using Multiple Github Applications" section, `config/secrets.development.shopify.yml`), any party who knows the `webhook_secret` for their own, lower-trust organization (necessary and expected, since org admins configure this secret on their own GitHub App) can sign an arbitrary JSON body themselves and POST it directly to the shared `/webhooks` endpoint — bypassing GitHub entirely. Because the verifying secret is selected using `repository.owner.login` (their own org) while the mutated repository is selected using `repository.full_name` (forged to point at a victim org's repo/stack), they can:
- Inject forged commit statuses (`StatusHandler`) on a victim organization's commits, potentially satisfying required-status gating and enabling an unauthorized deploy.
- Force `GithubSyncJob` resyncs on a victim stack (`PushHandler`) or trigger review-stack archive/unarchive and label-driven state transitions on a victim repository's pull requests (`PullRequest::*Handler`), all cross-tenant.

This maps to "an organization that authenticated versus the repository that is written" — a High-impact escalation into cross-repository state manipulation without any credential belonging to the victim organization.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (documented, supported feature), and (2) the attacker controlling/knowing the `webhook_secret` of at least one onboarded organization — which is normal for any org admin who configured their own GitHub App webhook. No access to the victim org's secret, GitHub credentials, or a Shipit session/API token is needed. This is a realistic scenario for any shared/SaaS-style Shipit deployment serving several organizations.

### Recommendation
After verifying the signature, re-derive and cross-check that `repository.owner.login` (or `organization.login`) used to select the signing secret matches the owner embedded in `repository.full_name` before invoking any handler. Reject the request (422) on mismatch, mirroring how `addValidators` in the referenced report enforces a strict, checked relationship between the length field and the data rather than trusting an independent unchecked field.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`).
2. As an admin/operator of `OrgA` (who legitimately knows `OrgA`'s `webhook_secret`), craft a JSON body:
```json
{
  "sha": "<victim-commit-sha-in-OrgB>",
  "state": "success",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
3. Compute `sha1=<hmac>` over the raw body using `OrgA`'s `webhook_secret` and set it as `X-Hub-Signature`; set `X-Github-Event: status`.
4. POST directly to `/webhooks`. `verify_signature` resolves `repository_owner` = `"OrgA"`, verifies successfully with `OrgA`'s secret [1](#0-0) , then `StatusHandler` creates a forged commit status on `OrgB`'s commit [6](#0-5) , despite the attacker having no credentials for `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
