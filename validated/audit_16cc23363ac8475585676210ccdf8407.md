### Title
Release asset verification trusts unverified statement subjects instead of the cryptographically verified digest - (File: pkg/cmd/release/verify-asset/verify_asset.go)

### Summary
`gh release verify-asset` establishes trust ("this file is part of release X") by checking whether the file's digest textually appears among the JSON `subject` entries of an attestation's DSSE payload — data that is only cryptographically bound to the *release ref* digest, not to each individual subject entry.

### Finding Description
`verifyAssetRun` in `pkg/cmd/release/verify-asset/verify_asset.go` fetches attestations keyed on `releaseRefDigest` (line 153-164) and filters them by tag name (line 170). It then filters again with `shared.FilterAttestationsByFileDigest` (line 180), which parses the DSSE `Payload` and does a plain string match of `fileDigest.Digest()` against each `subject.Digest["sha256"]` entry [1](#0-0) . Crucially, `AttVerifier.VerifyAttestation` (invoked at line 190) is only ever run against `releaseRefDigest` — the release ref's SHA — via `buildVerificationPolicy`'s digest policy option [2](#0-1) [3](#0-2) . The Sigstore/cryptographic verification (`verifier.Verify`) never actually asserts that the specific asset's digest is one of the cryptographically-signed subjects; it only proves the ref digest is signed. The per-asset "membership" check is a plain, unauthenticated JSON string comparison performed on the same statement payload whose signature covers the *ref*, not each subject digest individually pinned by a separate verification step — this is architecturally analogous to the vault report's core flaw: a value used to grant trust/credit (the weight / the "this file belongs to this release" claim) is derived from unvalidated data rather than from the actually-verified quantity. [4](#0-3) 

### Impact Explanation
If the DSSE statement's `subject` array can contain entries not independently corroborated by the certificate/signature binding for that specific subject (e.g., a release attestation predicate populated with attacker-influenced or looser subject lists, or a future/self-hosted-runner-generated attestation with a broader subject set), `gh release verify-asset` would report "Verification succeeded!" for a file whose actual provenance was never independently proven beyond string-matching the digest inside the payload. This could mislead downstream consumers relying on `gh release verify-asset` to gate execution or trust decisions on a supply-chain artifact that was not the artifact the signer actually produced/attested with cryptographic assurance for that specific subject.

### Likelihood Explanation
This requires that an attacker control or influence the content of a `release` predicate's `subject` list for an attestation associated with the target release/tag SHA (e.g. via a compromised or permissive workflow that emits a broad statement) — a narrower condition than a fully remote unauthenticated attack, and it is the intended attestation schema rather than a clear parsing bug. I could not fully verify server-side guarantees (e.g., whether GitHub's release-attestation issuance pipeline strictly binds each subject digest individually at signing time) within the available codebase context, so confidence in exploitability is moderate rather than certain.

### Recommendation
Have `VerifyAttestation`/`buildVerificationPolicy` include the specific asset's digest as part of the cryptographically-checked policy (e.g., an artifact digest policy option scoped to the asset, not just the release ref), rather than relying on a post-hoc unauthenticated string match against `FilterAttestationsByFileDigest`. Ensure the subject-membership check is validated against data that carries the same verified provenance as the overall bundle signature.

### Proof of Concept
Not independently reproducible from the indexed code alone: exploitation depends on the ability to get GitHub (or a workflow with elevated release-attestation permissions) to emit a `release`-predicate attestation whose `subject` list includes a digest for a file not actually produced/verified as part of that release — a server-side/workflow-side precondition outside the scope of files indexed here. This should be validated with a live Devin session that can construct a test attestation bundle and run `gh release verify-asset` against it end-to-end.

	td, err := v.AttClient.GetTrustDomain()
	if err != nil {

	}

		ExternalHttpClient: v.ExternalHttpClient,
		Logger:             att_io.NewHandler(v.IO),
		NoPublicGood:       true,
		TrustDomain:        td,
		TrustedRoot:        v.TrustedRoot,
	})
	if err != nil {
		return nil, err
	}

	policy := buildVerificationPolicy(*art, td)
	sigstoreVerified, err := verifier.Verify([]*api.Attestation{att}, policy)
	if err != nil {
		return nil, err
	}

	return sigstoreVerified[0], nil
}

func FilterAttestationsByFileDigest(attestations []*api.Attestation, fileDigest string) ([]*api.Attestation, error) {
	var filtered []*api.Attestation
	for _, att := range attestations {
		statement := att.Bundle.Bundle.GetDsseEnvelope().Payload
		var statementData v1.Statement
		err := protojson.Unmarshal([]byte(statement), &statementData)

		if err != nil {
			return nil, fmt.Errorf("failed to unmarshal statement: %w", err)
		}
		subjects := statementData.Subject
		for _, subject := range subjects {
			digestMap := subject.GetDigest()
			alg := "sha256"

			digest := digestMap[alg]
			if digest == fileDigest {
				filtered = append(filtered, att)
			}
		}

	}
	return filtered, nil
}

// buildVerificationPolicy constructs a verification policy for GitHub releases
func buildVerificationPolicy(a artifact.DigestedArtifact, trustDomain string) verify.PolicyBuilder {
	// If no trust domain is specified, default to "dotcom"
	if trustDomain == "" {
		trustDomain = "dotcom"
	}
	// SAN must match the GitHub releases domain. No issuer extension (match anything)
	sanMatcher, _ := verify.NewSANMatcher("", fmt.Sprintf("^https://%s\\.releases\\.github\\.com$", trustDomain))
	issuerMatcher, _ := verify.NewIssuerMatcher("", ".*")
	certId, _ := verify.NewCertificateIdentity(sanMatcher, issuerMatcher, certificate.Extensions{})

	artifactDigestPolicyOption, _ := verification.BuildDigestPolicyOption(a)
	return verify.NewPolicy(artifactDigestPolicyOption, verify.WithCertificateIdentity(certId))
}
