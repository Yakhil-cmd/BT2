## Title
Unprivileged global-contract owner can swap live code mid-flight of a pending/postponed/yielded receipt, changing execution semantics for in-progress cross-contract flows with no lock protecting the waiting party - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
When an account uses `GlobalContractDeployMode::AccountId`, every account that references it via `UseGlobalContractAction` resolves to whatever code is *currently* stored under that owner's `GlobalContractIdentifier::AccountId`, resolved fresh at execution time rather than pinned at the time the interaction began. The owner of that global contract (an ordinary, unprivileged account, no validator/admin role required) can redeploy the code at any time with no cooldown beyond normal shard propagation, while receipts that are postponed (awaiting a `DataReceipt`), delayed, or in a multi-block `yield`/`resume` flow keep waiting to execute against that same account. This is structurally the same defect as the NibblVault report: a multi-step process a counterparty is committed to (`BUYOUT_DURATION`) can have its underlying implementation swapped out from under it by a party who controls an "update" action with no matching lock (`UPDATE_TIME`), and the waiting party has no way to cancel.

### Finding Description
`GlobalContractDeployMode::AccountId` is documented to let "the owner update the contract for all its users" [1](#0-0) , and `action_deploy_global_contract` allows redeployment at any time via `initiate_distribution`, gated only by an ever-incrementing nonce, not any user-facing waiting period [2](#0-1) .

When another account calls `use_global_contract`, it stores a reference (`AccountContract::GlobalByAccount(id)`) rather than a snapshot of the code [3](#0-2) . Code identity is resolved dynamically at execution time by looking up the account's current `AccountContract` state, as seen in the pipelining preparation logic which explicitly separates `AccountContract::GlobalByAccount` and checks a set of contracts blocked *within the current chunk only* [4](#0-3) . The accompanying comment confirms the protection is scoped to actions that change code identity "within this chunk", explicitly not addressing longer-lived pending state [5](#0-4) .

However, NEAR receipts routinely remain pending across many blocks:
- Postponed action receipts wait for missing `DataReceipt`s and are stored as-is in state, re-fetching the account/contract at the time they finally become ready [6](#0-5) .
- Delayed receipts sit in a persistent queue and are processed in later chunks whenever gas allows [7](#0-6) .
- `promise_yield_create`/`promise_yield_resume` explicitly support waiting many blocks for a resume before timing out [8](#0-7) , with timeouts resolved only after `yield_timeout_length_in_blocks` [9](#0-8) .

None of these mechanisms pin the global contract's code version at the time the flow was initiated. If the global contract owner redeploys new code (`AccountId` mode) at any point while a caller's postponed receipt, delayed receipt, or yield/resume flow targeting an account using that global contract is outstanding, the eventual execution will run against the new code, not the code the caller reasoned about when the multi-step interaction began. There is no lock, cooldown, or way for the waiting counterparties to detect or cancel this, exactly mirroring the NibblVault `BUYOUT_DURATION` vs `UPDATE_TIME` mismatch (an unprivileged "update" action that races an unprivileged, multi-step, non-cancellable process).

### Impact Explanation
An account can use a `UseGlobalContractAction` to adopt behavior it has audited (e.g., an escrow, marketplace, or vault-like contract). Users may then submit deposits or start multi-step flows (cross-contract calls with data dependencies, yielded promises awaiting callback data) that assume the account's currently deployed logic. The global contract owner — who need not be privileged in any way, just the original deployer — can redeploy different code at any time. Any receipt still in flight (postponed on a data dependency, delayed by congestion, or awaiting `promise_yield_resume`) will be executed under the new code, which could behave differently regarding balance transfers, storage handling, or authorization checks, potentially resulting in unauthorized state or balance changes relative to what the counterparty expected when they entered the interaction, and no mechanism exists for that counterparty to bail out.

### Likelihood Explanation
This requires the target account to be using an `AccountId`-mode global contract (an explicit builder choice, not automatic) and requires an in-flight multi-block interaction (postponed/delayed/yielded receipt) to exist at the moment of redeployment. Both conditions are readily reachable by any account through ordinary transactions (`DeployGlobalContractAction`, `UseGlobalContractAction`, cross-contract calls, and `promise_yield_create`), with no special privileges, keys, or validator status needed.

### Recommendation
Either (a) pin the resolved global-contract code hash/version at the time a dependent receipt (postponed, delayed, or promise-yield) is created and re-resolve against that pinned version rather than the live `AccountId` mapping, or (b) enforce a mandatory delay/lock before an `AccountId`-mode global contract redeployment can take effect (analogous to increasing `UPDATE_TIME` beyond any protocol-level maximum pending-receipt/yield-timeout duration), so in-flight interactions cannot have their underlying code swapped mid-execution.

### Proof of Concept
1. Account `owner` deploys a global contract in `AccountId` mode via `DeployGlobalContractAction` [10](#0-9) .
2. Account `vault` calls `UseGlobalContractAction{contract_identifier: AccountId(owner)}`, adopting `owner`'s code [11](#0-10) .
3. A user submits a `FunctionCall` to `vault` that internally issues a `promise_yield_create` (or a cross-contract call creating a postponed receipt awaiting a `DataReceipt`), expecting `vault`'s current logic to eventually resolve the callback [12](#0-11) .
4. While that receipt is still pending (potentially for many blocks, up to `yield_timeout_length_in_blocks` or however long a delayed/postponed receipt takes to clear), `owner` submits a new `DeployGlobalContractAction` with different code under the same `AccountId` mode, which is accepted immediately with only a nonce check [2](#0-1) .
5. When the pending callback/postponed receipt finally executes, the runtime resolves `vault`'s contract by its `AccountContract::GlobalByAccount(owner)` reference, which now points at the newly deployed code instead of the code that existed when the interaction was started, altering the outcome the user relied on with no way for the user to have cancelled the in-flight interaction beforehand.

    state_update: &mut TrieUpdate,
    account_id: AccountId,

    deploy_mode: &GlobalContractDeployMode,

    result: &mut ActionResult,
) -> Result<(), RuntimeError> {

            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())

    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.

        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);

        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
