Based on my research, I found one reachable analog to the TIFF divide-by-zero crash: an explicit `throw Error(...)` triggered by attacker-controlled zero-valued division inputs inside unit validation, rather than an actual runtime divide-by-zero (JavaScript itself returns `Infinity`/`NaN` on numeric division by zero and doesn't crash).

### Title
Uncaught exception via zero `tps_fee` share crashes node during unit validation - ([File: validation.js])

### Summary
`validateTpsFee()` in `validation.js` computes a per-recipient `share` from `earned_headers_commission_recipients` and immediately `throw`s an uncaught `Error` if that share evaluates to `0`/falsy, instead of returning a normal validation rejection through the `callback`. This mirrors the TIFF divide-by-zero bug class: attacker-supplied data that is expected to be non-zero reaches an arithmetic path with no defensive check before use, causing a crash instead of a graceful rejection.

### Finding Description
`validateTpsFee` derives `recipients` from `objUnit.earned_headers_commission_recipients` (a field fully controlled by the unit's poster) via `storage.getTpsFeeRecipients(...)`, then for each recipient computes: [1](#0-0) 
```
const recipients = storage.getTpsFeeRecipients(...);
for (let address in recipients) {
    const share = recipients[address] / 100;
    if (!share)
        throw Error(`invalid share for address ${address}: ${share}`);
    ...
    const tps_fee = tps_fees_balance / share + objUnit.tps_fee;
```
If a poster crafts a unit whose `earned_headers_commission_recipients` share for some address is `0`, `share` becomes `0`, and the code path `throw`s a raw JS `Error` inside `validateTpsFee`, called from the main unit-validation pipeline for any unit at/after `v4UpgradeMci`. Unlike the rest of the validation code (which reports errors through `callback(err)` so the unit is simply rejected), this specific branch throws synchronously. Depending on how the calling context (`async` control flow, promise chains) propagates this, an uncaught throw inside validation processing can crash the node process handling the unit, which is functionally analogous to the TIFF crafted-image divide-by-zero crash: malformed-but-syntactically-valid attacker input causes an unhandled application/process crash rather than a controlled rejection.

### Impact Explanation
If reachable without prior sanitization, a single crafted unit posted by any unprivileged party could crash validating nodes processing it — a network-wide denial of service on new unit confirmation, matching this scan's "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
Likelihood is uncertain: I was not able to fully verify, within the available searches, whether `earned_headers_commission_share` values of `0` (or entries producing a `0` share after `storage.getTpsFeeRecipients`'s normalization) are rejected earlier in unit-content validation (e.g., a required-positive-integer check on `earned_headers_commission_share` fields) before `validateTpsFee` runs. If an earlier validator already rejects `share <= 0` recipients, this throw is unreachable dead code and not exploitable. [1](#0-0)  confirms the vulnerable computation exists, but I could not confirm within the given iterations whether upstream field-level validation of `earned_headers_commission_share`/`earned_headers_commission_recipients` closes this gap.

### Recommendation
- Confirm whether `earned_headers_commission_share` is validated to be a positive integer (>0, ≤100) before `validateTpsFee` executes.
- If not already enforced, add that check earlier in unit content validation.
- Regardless, change the `throw Error(...)` in `validateTpsFee` to `return callback(...)` so malformed input results in unit rejection rather than a process crash, consistent with the rest of the function.

### Proof of Concept
Not independently confirmed against runtime behavior; conceptually: construct and post a unit with `earned_headers_commission_recipients: [{address: <addr>, earned_headers_commission_share: 0}]` at `last_ball_mci >= v4UpgradeMci`, triggering `validateTpsFee` to compute `share = 0` and throw.

**Note:** Given the uncertainty about whether an upstream validator already blocks zero-share recipients, this finding should be treated as a leads-for-verification item rather than a confirmed exploit — a Devin session with full codebase/test access would be needed to trace all validators of `earned_headers_commission_recipients` and confirm reachability end-to-end.
