### Title
Address Definition Change Accepts Unverified `definition_chash`, Enabling Permanent Address Lockout - ([File: validation.js])

### Summary
The `address_definition_change` message — Obyte's equivalent of an ownership/key-transfer operation for an address — only validates that the new `definition_chash` is *syntactically* a valid 32-byte chash. It never checks that the chash corresponds to a definition that will ever be resolvable/revealed. This mirrors the reported `Ownable.transferOwnership` issue: the "new owner" (new signing definition) is format-checked but not verified to be valid/active, so a mistaken or malicious commit permanently locks the address out of all of its permissioned functionality (signing units, controlling funds, or acting as a shared-wallet/AA-controlling address).

### Finding Description
When an address wants to change its signing definition (analogous to changing the owner/keys that control it), it posts an `address_definition_change` message. The inline-payload validator only checks the chash format: [1](#0-0) 

No check exists to ensure the new `definition_chash` is ever backed by an actual, resolvable definition, or that whoever controls it can supply one. The definition op-validator for the related `has definition change` / `seen definition change` predicates likewise only checks address/chash format, not resolvability: [2](#0-1) 

The DB schema comment for `address_definition_changes.definition_chash` explicitly acknowledges the definition is "almost always... not defined" at the time of the change: [3](#0-2) 

And the core signature-validation code documents the direct consequence — the address becomes unusable if the new definition is never disclosed before last ball: [4](#0-3) 

Once the `address_definition_change` unit is stable, `readDefinitionChashByAddress`/`readDefinitionByAddress` will always resolve the address's expected definition hash to the new, unresolved chash: [5](#0-4) 

Since `validateAuthor` requires any future unit from that address to supply (or match) a definition hashing to that chash, and there is no way to "undo" or invalidate an already-stable definition change, a wrong or unreachable `definition_chash` permanently and irreversibly locks the address: [6](#0-5) 

### Impact Explanation
Because there is no validation that the new `definition_chash` is "valid and active" (i.e., resolvable to a spendable/usable definition), a single erroneous or malicious `address_definition_change` message permanently locks the affected address out of signing any future unit. If this address is a shared/multisig wallet controlling pooled funds, an asset's `definer_address`, or an address that an Autonomous Agent or governance flow depends on for authorization, the funds and permissioned capabilities tied to that address become permanently frozen — directly matching the reported class of "whole protocol locked out of its permissioned functionalities."

### Likelihood Explanation
Likelihood is low, matching the original report's score, since it requires either a self-inflicted mistake (typo in the chash) or a compromised/malicious key holder deliberately committing to a chash they cannot or will not ever reveal a matching definition for. No network-level or privileged access is needed — a single unprivileged unit from the address's own author is sufficient to trigger it.

### Recommendation
Add validation logic (or at minimum a wallet/client-side safeguard) to require the definition being changed to be revealed in the same unit, or to strongly warn/prevent commits to a `definition_chash` for which no verifiable, controllable definition is provided. Given this mirrors the same accepted-risk pattern as the original finding, it may similarly be accepted as a documented risk of the commit/reveal design of Obyte's address-definition mechanism rather than fixed immediately.

### Proof of Concept
1. An address `A` (e.g., a shared wallet, asset definer, or AA-controlling address) posts a unit containing an `address_definition_change` message with `definition_chash` set to a random but validly-formatted 32-character base32 chash for which no one holds/can produce a matching `definition` array (e.g., a typo'd hash, or one derived from a definition the poster doesn't actually control the keys for).
2. Validation only checks `isValidAddress(payload.definition_chash)` — passes trivially (`validation.js:1743`).
3. The unit becomes stable; `address_definition_changes` table now maps address `A` to the new, unresolved `definition_chash`.
4. Any subsequent unit authored by `A` must supply a `definition` whose chash matches the new value (`validation.js:1469-1483`); since no one can produce such a definition, `A` can never author a valid unit again.
5. All funds/permissions tied to address `A` (multisig treasury, AA governance address, asset issuance rights, etc.) are now permanently frozen.

CREATE TABLE address_definition_changes (
	unit CHAR(44) CHARACTER SET latin1 COLLATE latin1_bin NOT NULL,
	message_index TINYINT NOT NULL,
	address CHAR(32) NOT NULL,
	definition_chash CHAR(32) NOT NULL, -- might not be defined in definitions yet (almost always, it is not defined)
	PRIMARY KEY (unit, message_index),
	UNIQUE KEY byAddressUnit(address, unit),
	FOREIGN KEY (unit) REFERENCES units(unit),
	CONSTRAINT addressDefinitionChangesByAddress FOREIGN KEY (address) REFERENCES addresses(address)
) ENGINE=InnoDB  DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_520_ci;
