### Title
Webhook signature verification selects the per-organization secret from an unverified `repository.owner.login`/`organization.login` field, while event handlers act on a different unverified field (`repository.full_name`) - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-org Shipit deployments, `WebhooksController#verify_signature` picks which organization's `webhook_secret` to verify against using `repository_owner`, a value read straight out of the still-unauthenticated JSON body. The HMAC signature is then checked against that chosen secret. But the code path that actually decides *which repository/stack* to act on (`Handler#repository_name`) reads a separate field, `repository.full_name`, from the same unauthenticated body. Nothing ties these two fields together before the org's secret is chosen, so an attacker who legitimately controls a GitHub App installation for one organization (and thus knows that organization's `webhook_secret`) can forge a signed payload that is verified as "belonging" to their own org, while `repository.full_name` names a stack owned by a different, victim organization configured in the same Shipit instance.

### Finding Description
`Shipit.github(organization:)` supports a config schema keyed by organization, each with its own independent `webhook_secret`, as documented in `docs/setup.md` ("Using Multiple Github Applications") and implemented in [1](#0-0) .

The webhook signature-verification step chooses which of these per-organization secrets to use based on an attacker-controlled field taken from the raw, not-yet-verified request body: [2](#0-1) [3](#0-2) 

Once `verify_signature` succeeds (using the secret for whatever organization `repository.owner.login` claims), `create` dispatches the full JSON body to the registered handlers unchanged: [4](#0-3) 

The handlers, however, resolve the target repository/stack from a *different* JSON field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

Because the same payload contains both fields but only `repository.owner.login` (or `organization.login`) influences which secret is used for verification while `repository.full_name` decides which stack is affected, an attacker who is an owner/admin of their own org's GitHub App installation (and therefore knows that org's `webhook_secret`) can HMAC-sign a payload with `repository.owner.login` = "attacker-org" and `repository.full_name` = "victim-org/victim-repo". The signature is valid for "attacker-org"'s secret, `verify_signature` passes, and `PushHandler` (for example) then enqueues a `GithubSyncJob` / triggers a deploy sync for the victim's stack: [7](#0-6) 

This mirrors the reported bug class: the field that is cryptographically bound (verified) is not the same field the privileged action is actually keyed on, breaking the equality "organization whose secret authenticated the request == organization whose repository is acted upon."

### Impact Explanation
This crosses an organization/tenant trust boundary within a single Shipit instance. It allows an attacker who is a legitimate but low-privilege tenant (controls one GitHub org's webhook secret) to inject fabricated webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) that are attributed to and acted on a completely different organization's stacks/repositories. Depending on which handler is triggered, this can force unwanted `GithubSyncJob` runs, spoof commit statuses/check-run refreshes, or manipulate membership/team records tied to the victim organization — i.e., cross-repository/cross-tenant writes performed under a forged trust context, which maps to the "cross-repository writes" / unauthorized-action Critical/High impact bar for this engine.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly supported and documented) where the attacker legitimately administers at least one configured organization's GitHub App/webhook secret — a real, unprivileged-relative-to-other-tenants scenario, not requiring any Shipit session, API token, or host access. The webhook endpoint is unauthenticated by design (relies solely on the HMAC check), so exploitation only requires crafting one HTTP POST with a body whose two organization-identifying fields diverge.

### Recommendation
Bind the same field used to select/verify the signing secret to the field used to resolve the acted-upon repository. Concretely: after selecting `github_app` via `repository_owner`, verify that `params.dig('repository', 'full_name')` (and `organization.login`, if used) is consistent with (has the same owner as) `repository_owner` before dispatching to handlers; or require handlers to reject/short-circuit if `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (multi-org schema per `docs/setup.md`).
2. As the attacker, who knows `attacker-org`'s `webhook_secret` (they administer that GitHub App installation), build a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "deadbeef",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and verifies successfully against the attacker's own known secret [8](#0-7) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` via `repository_name` [5](#0-4)  and syncs/deploys the victim's stack, even though the request was never signed by `victim-org`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
