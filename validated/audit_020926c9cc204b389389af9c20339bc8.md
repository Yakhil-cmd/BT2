### Title
Attacker-controlled submodule/ref content in a synced repo can cause persistent, unrecoverable sync denial (crash-loop) via `configureWorktree`/`SyncRepo` failure - ([File: main.go])

### Summary
The externally reported ERC20 bug is a class of "attacker-controlled dependency makes an operation permanently unable to complete" — a party who controls one input to a critical state-transition (the `_currency` contract) can force every subsequent attempt at that transition (`paySeller`) to revert forever, with no privileged escape hatch. The reachable analog in `git-sync` is that content pushed to the synced repository (submodule URLs/`.gitmodules`, or a moved/rewritten ref) is a similarly attacker-influenced input to `SyncRepo`'s critical state-transition (publishing a new worktree via the atomic symlink). If that content makes `fetch`, `configureWorktree`, or the pre-publish hook fail deterministically, `SyncRepo` returns an error every loop iteration with no way for an operator to skip past the bad commit without out-of-band intervention, and by default this terminates the process entirely.

### Finding Description
`SyncRepo` performs, in order: `fetch` [1](#0-0) , `createWorktree`/`configureWorktree` (which runs `git submodule update --init --recursive` using submodule URLs/config that live inside the attacker-influenced repository content) [2](#0-1) , then `beforePublish` hook and `publishSymlink` [3](#0-2) . If any of these steps errors (e.g., a submodule URL that never resolves, requires interactive credentials, or a repo host that always rejects the fetch), `SyncRepo` returns an error and the symlink is never updated — mirroring how `paySeller` in the report can never succeed once a hostile `_currency.transfer` is in the payment path [4](#0-3) .

Crucially, the outer sync loop treats every such failure as a hard failure: `failCount` increments and, once it reaches `--max-failures` (which defaults to 0, i.e. "any sync failure will terminate git-sync" per the documented default), the process calls `os.Exit(1)` [5](#0-4) . The manual explicitly documents this default: "If not specified, this defaults to 0, meaning any sync failure will terminate git-sync." [6](#0-5) . Because `git-sync` is normally run as a long-lived Kubernetes sidecar, that process exit results in the container being restarted by the kubelet, which will immediately re-attempt the same broken ref/commit/submodule on startup and fail again — an unbounded crash-loop, with no built-in seller/arbitrator-equivalent mechanism to skip, quarantine, or roll back the offending commit without external operator action (e.g., manually pinning `--ref` to an older hash).

This is directly analogous to the report's core defect: a value chosen/controlled by an untrusted party (there: `_currency` address; here: repo/ref/submodule content reachable via `--repo`/`--ref`) is trusted as an input to a critical, repeatedly-invoked state transition, and the codebase provides no privileged way to bypass or revoke a bad instance of that transition once it is stuck.

### Impact Explanation
If `--repo`/`--ref` point at a branch or ref that untrusted contributors can push to (a common CI/CD or GitOps pattern where `git-sync` tracks a PR branch or a shared mainline with multiple committers), a malicious commit that breaks `fetch`/submodule resolution/checkout causes:
- The symlink to stop advancing (stale, but not incorrect, content — lower severity), and
- With default flags, the `git-sync` process to exit and the sidecar to crash-loop indefinitely until the bad commit is manually rewound — a persistent sync denial matching the accepted impact category.

### Likelihood Explanation
Requires the operator to point `--repo`/`--ref` at a source where untrusted parties can introduce commits (submodule additions, `.gitmodules` edits, or moving a tracked branch), and to be running with default (or low) `--max-failures`. This is a realistic but non-default-hostile configuration for many sidecar deployments (e.g., tracking a shared branch), making likelihood moderate rather than certain — it depends on the deployment's trust boundary for the tracked ref.

### Recommendation
- Distinguish between transient network/auth errors and content-integrity errors (bad submodule URL, broken tree) so a permanently-broken commit does not repeatedly trigger `os.Exit(1)`; instead, keep retrying at the configured `--period`/`--max-failures` cadence without killing the container, or expose a way to skip/blacklist a known-bad hash while still serving the last-known-good published symlink.
- Consider making `--max-failures` non-zero by default, or documenting explicitly the crash-loop risk of the current default combined with less-trusted `--ref` sources.
- Continue serving the last successfully published symlink target when a new sync fails, rather than terminating the whole process, so a hostile commit cannot cause total service denial for consumers of the shared volume.

### Proof of Concept
1. Configure `git-sync --repo=<repo> --ref=<branch> --root=<root> --link=link` with default `--max-failures=0`, tracking a branch that untrusted contributors can push to.
2. An attacker pushes a commit to that branch adding/modifying `.gitmodules` to reference a submodule URL that is unreachable or requires interactive authentication (or otherwise reliably fails `git submodule update --init --recursive`).
3. On the next `--period` tick, `SyncRepo` reaches `configureWorktree`, the submodule step fails, and `SyncRepo` returns an error [7](#0-6) .
4. Back in the main loop, `failCount` becomes ≥ `getMaxFailures()` (0), so `log.Error(...)` is logged and `os.Exit(1)` is called [8](#0-7) .
5. Under Kubernetes, the sidecar container restarts, re-fetches the same malicious ref, and repeats step 3–4 indefinitely (crash-loop) until an operator manually intervenes (e.g., pins `--ref` to a prior known-good hash) — a persistent sync denial analogous to the un-finalizable offer in the source report.
