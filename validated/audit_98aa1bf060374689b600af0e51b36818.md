### Title
Unsafe `_mint` and `transferFrom` in Bridge ERC721 Delivery Permanently Locks Bridged NFTs — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer` delivers bridged ERC721 tokens to the user-supplied `_to` address using either `mintWithTokenURI` (which internally calls `_mint`) or `transferFrom`, neither of which performs the `IERC721Receiver` callback check. When `_to` is a contract that does not implement `onERC721Received`, the token is minted or transferred into that contract and permanently locked, while the corresponding asset on the source chain has already been burned or escrowed.

---

### Finding Description

`handleERC721Transfer` in `BridgeTransferERC721` has two delivery branches:

**Branch 1 — mintBurn mode:**
```solidity
require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
```
`mintWithTokenURI` calls `_mint` directly:
```solidity
function mintWithTokenURI(address to, uint256 tokenId, string memory tokenURI) public onlyMinter returns (bool) {
    _mint(to, tokenId);   // no _checkOnERC721Received
    _setTokenURI(tokenId, tokenURI);
    return true;
}
```

**Branch 2 — lock/unlock mode:**
```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
```
`transferFrom` also skips the `_checkOnERC721Received` callback, as documented in the OZ base contract itself: *"Usage of this method is discouraged, use `safeTransferFrom` whenever possible."*

The `_to` address originates from the user's original `requestERC721Transfer` call on the source chain and is relayed verbatim by bridge operators. There is no validation that `_to` can receive ERC721 tokens.

---

### Impact Explanation

A user who specifies a contract address as `_to` (e.g., a multisig wallet, DAO treasury, or any contract without `IERC721Receiver`) will have their source-chain NFT burned (mintBurn mode) or locked in the source bridge, while the destination-chain token is minted/transferred into a contract that cannot move it. The bridged ERC721 asset is permanently lost with no recovery path. This is a direct loss of bridged assets.

---

### Likelihood Explanation

Medium. The `_to` address is freely chosen by any user initiating a cross-chain ERC721 transfer. Accidental loss occurs when users specify multisig wallets, DAO contracts, or other smart contracts that hold assets but do not implement `IERC721Receiver`. Intentional griefing is also possible (e.g., specifying `address(0x1)` or any non-receiver contract). No privileged access is required beyond initiating a normal bridge request.

---

### Recommendation

1. Replace `mintWithTokenURI` with a `safeMintWithTokenURI` variant that calls `_safeMint` instead of `_mint`, so the `_checkOnERC721Received` callback is invoked before finalizing the mint.
2. Replace `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` with `IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId)` in the lock/unlock delivery branch.

Both changes ensure that delivery to a non-receiver contract reverts the handle transaction, allowing operators to retry or the bridge to surface the failure, rather than silently locking the asset.

---

### Proof of Concept

**Affected files and lines:**

`ERC721MetadataMintable.mintWithTokenURI` calls `_mint` with no receiver check: [1](#0-0) 

`handleERC721Transfer` mintBurn branch invokes `mintWithTokenURI(_to, ...)`: [2](#0-1) 

`handleERC721Transfer` lock/unlock branch uses `transferFrom` (not `safeTransferFrom`): [3](#0-2) 

`_mint` in the OZ base has no receiver callback: [4](#0-3) 

`_checkOnERC721Received` exists and is only called by `safeTransferFrom`, not by `_mint` or `transferFrom`: [5](#0-4) 

**Attack path:**

1. Attacker (or user) calls `requestERC721Transfer(tokenAddress, contractWithoutReceiver, tokenId, extraData)` on the source chain. The source-chain NFT is burned (mintBurn) or locked in the source bridge.
2. Bridge operators observe the `RequestValueTransferEncoded` event and call `handleERC721Transfer(..., _to=contractWithoutReceiver, ...)` on the destination chain.
3. In mintBurn mode: `mintWithTokenURI(contractWithoutReceiver, tokenId, uri)` → `_mint(contractWithoutReceiver, tokenId)` succeeds silently. The token is now owned by `contractWithoutReceiver` which has no way to move it.
4. In lock/unlock mode: `transferFrom(bridge, contractWithoutReceiver, tokenId)` succeeds silently. Same outcome.
5. The bridged ERC721 is permanently locked. The source-chain asset is already gone.

    function _checkOnERC721Received(address from, address to, uint256 tokenId, bytes memory _data)
        internal returns (bool)
    {
        if (!to.isContract()) {
            return true;
        }

        bytes4 retval = IERC721Receiver(to).onERC721Received(msg.sender, from, tokenId, _data);
        return (retval == _ERC721_RECEIVED);
    }
