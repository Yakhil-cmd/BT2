### Title
Anyone Can Forcibly Repay a Victim's Debt via `repay()` to Trigger an Unwanted Efficiency-Group Transition and Force Liquidation - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`repay()` lets any caller specify an arbitrary `on-behalf-of` account and fully clear that account's debt in a chosen asset. Because clearing a debt bit changes the account's risk-parameter (egroup) mask, and `repay()` performs no post-mutation health/egroup check, an attacker can weaponize a "helpful" repayment to shove a victim (with other remaining debt/collateral) into a stricter egroup, making a previously healthy position immediately liquidatable — without the victim's consent, exactly the class of harm flagged in the STPV2 report where a caller-controlled recipient parameter let one user force a state transition on another user's position.

### Finding Description
`repay()` resolves the target account from an unrestricted parameter: [1](#0-0) 

The amount is auto-capped to the account's full outstanding debt for that asset, so an attacker only needs to pass a large `amount` to guarantee full repayment (`repaying-all`) regardless of the victim's exact balance: [2](#0-1) 

The only precondition is `tx-sender == contract-caller` (anti-contract-relay), not that `account == contract-caller` or any signature/consent from the victim: [3](#0-2) 

`debt-remove-scaled` in `v0-market-vault.clar` unconditionally updates the account's bitmask when the asset's debt reaches zero, removing that asset's debt bit from the mask that determines the account's egroup: [4](#0-3) 

Unlike `collateral-add`, which explicitly guards against egroup transitions that reduce a user's borrowing capacity (`;; CRITICAL CHECK: Future capacity must not decrease`): [5](#0-4) 

`repay()` has no equivalent check. It never re-resolves the egroup or asserts the victim's remaining position is still healthy under the new (post-mask-change) egroup's `LTV-LIQ-PARTIAL`/`LTV-LIQ-FULL` thresholds. Since egroups with fewer debt-asset bits set can carry stricter liquidation thresholds (as documented in the egroup superset invariant, where supersets must have lower-or-equal LTVs — implying subsets/more-specific groups can be materially more permissive): [6](#0-5) 

a victim holding two debt assets under a favorable "multi-debt" egroup can be knocked, by a third party fully repaying just one of those debts, into a different egroup governing their remaining single-asset position — one with a lower `LTV-LIQ-FULL`/`LTV-LIQ-PARTIAL` — instantly making their unchanged remaining debt/collateral ratio cross the liquidation threshold.

### Impact Explanation
Without the attacker's transaction, the victim's position remains healthy under their intended multi-asset egroup. With the attacker's unsolicited `repay()` call, the victim's mask changes, their egroup resolution changes, and their now-larger relative debt-to-collateral ratio (under the stricter egroup) can exceed `LTV-LIQ-PARTIAL`/`LTV-LIQ-FULL`, making them liquidatable by anyone (including the attacker) via `liquidate()`/`liquidate-multi()`. This results in theft of the victim's collateral via an unwarranted liquidation penalty that would not have occurred under the position's original egroup — a direct loss of user funds at rest, satisfying the Critical/High impact bar (theft of funds / temporary freezing of funds through forced, unconsented liquidation).

### Likelihood Explanation
The attack requires only: (1) the attacker holds/acquires enough of the victim's debt asset to fully cover it (recoverable in the same or a follow-up transaction via liquidation profit), and (2) the victim holds a multi-debt-asset position whose "reduced" egroup (after one debt is cleared) has stricter LTV thresholds than their current egroup — a condition that is a normal, expected outcome of the egroup subset/superset design and therefore commonly satisfiable by an attacker who inspects public egroup configurations and target accounts' on-chain positions.

### Recommendation
Restrict `repay()`'s `on-behalf-of` parameter so it can only reduce the debt of `contract-caller` unless the account has opted in (e.g., via signature or explicit allowance), mirroring the fix applied to `collateral-add`/`mintAdvanced` for third-party state changes. Alternatively, after mutating the mask in `debt-remove-scaled`, re-resolve the account's egroup and assert the resulting position (given unchanged collateral/other debt) remains at least as healthy as before the repayment, restoring the same "future capacity must not decrease" invariant already enforced in `collateral-add`.

### Proof of Concept
1. Victim V has collateral C and debt in assets A and B, correctly resolving to Egroup-X (mask includes debt bits for A and B) with `LTV-LIQ-FULL = 90%`. V's current debt/collateral ratio is 85% — healthy.
2. Attacker M, with no relationship to V, calls `repay(ft=A, amount=MAX_UINT, on-behalf-of=(some V))`. The function auto-caps `amount` to V's exact outstanding debt in A, fully repaying it using M's own tokens.
3. `debt-remove-scaled` clears V's debt bit for A, changing V's mask so it now resolves to Egroup-Y (debt bit B only), which — per the design where more specific/smaller-population egroups can have arbitrarily different LTVs — has `LTV-LIQ-FULL = 80%`.
4. V's unchanged debt-B/collateral-C ratio (85%) now exceeds Egroup-Y's 80% full-liquidation threshold. V is now liquidatable although nothing about V's own debt or collateral changed — only M's unsolicited repayment altered V's egroup classification.
5. M (or a colluding third party) immediately calls `liquidate(borrower=V, ...)`, seizing V's collateral at the liquidation penalty, capturing value that could not have been extracted had M not forced the egroup transition.
