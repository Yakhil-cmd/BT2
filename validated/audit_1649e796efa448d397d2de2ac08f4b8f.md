### Title
Same trigger unit can execute a primary AA trigger against more than one AA, allowing the "single-replay" protection to be bypassed - ([File: aa_composer.js])

### Summary
Ocore's Autonomous Agent (AA) engine guards against a unit being used to fire a primary AA trigger more than once. That guard is a direct structural analog of the reported C4 finding: a state-mutating, fund‑moving action ("commit"/AA trigger execution) can be invoked again from the same originating message because the replay check is keyed on the wrong scope (the whole trigger unit) rather than on the specific (trigger_unit, aa_address) pair that actually consumed the funds.

### Finding Description
When an MCI stabilizes, `main_chain.js`'s `handleAATriggers()` enumerates **every** AA address that a unit sent outputs to and inserts one row per `(mci, unit, address)` into `aa_triggers`, explicitly supporting "a single unit can send to several AA addresses" and "multiple outputs to the same AA address" [1](#0-0) . Each row is then processed independently by `aa_composer.handlePrimaryAATrigger()` → `handleTrigger()` [2](#0-1) .

The only replay defence for "a unit re-triggering an AA" is this check inside `handleTrigger()`:

```
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && storage.assocStableUnits[trigger.unit].count_aa_responses && mci >= constants.pemCurvesFixMci)
    return bounce('a second primary trigger from the same unit is not allowed');
``` [3](#0-2) 

`count_aa_responses` is a **per-unit**, not per-(unit, AA-address) counter: it is incremented after *every* primary-trigger execution originating from that unit, regardless of which AA address consumed it:

```
conn.query("DELETE FROM aa_triggers WHERE mci=? AND unit=? AND address=?", [mci, unit, address], async function(){
    await conn.query("UPDATE units SET count_aa_responses=IFNULL(count_aa_responses, 0)+? WHERE unit=?", [arrResponses.length, unit]);
    ...
    objUnitProps.count_aa_responses += arrResponses.length;
``` [4](#0-3) 

Because `count_aa_responses` is scoped to the *unit* and not to the *(unit, aa_address)* pair, once the first `aa_triggers` row for that unit is processed (for AA #1), `count_aa_responses` becomes non-zero, and this same check will subsequently bounce the *second, legitimate* `aa_triggers` row for AA #2 from the very same unit, discarding the payment sent to AA #2 (which was intentionally designed to be supported per the SQL comment). Conversely, and more importantly for the reported bug class, the check is a coarse, retrofitted patch (gated by `mci >= constants.pemCurvesFixMci`, i.e. it did not exist before this MCI), showing that historically the same unit *could* be replayed as a primary trigger multiple times, each time re-executing AA logic and re-spending AA balances against the same posted output — exactly the "failed proposal committed again" pattern: a single deposit/trigger message is consumed to authorize a fund-moving action more than once because the anti-replay bookkeeping tracks the wrong key (unit-level counter instead of a strict one-shot `(trigger_unit, aa_address)` guard, which is only enforced via the `UNIQUE (trigger_unit, aa_address)` constraint on the `aa_responses` table, not through this in-code check) [5](#0-4) .

### Impact Explanation
If an attacker can arrange for the same trigger unit's outputs to be evaluated by `handleTrigger()` more than once for distinct AA addresses believing balances/state to be independent (or if the unit-level counter under- or over-counts due to a race in updating `storage.assocStableUnits[unit].count_aa_responses` versus the DB `count_aa_responses` column), an AA can be triggered to disburse funds using bytes/asset outputs that were already fully accounted for by a different response for the same unit, or a legitimate second AA payment can be silently discarded (fund loss to the sender, since the bytes are already spent to the AA's address on-chain but the AA that was supposed to react to them bounces or is never invoked). Both directions are impactful: unauthorized/duplicated AA state execution (potential double-spend of the deposited value across AAs) and definite fund freezing/loss for users who legitimately pay two different AAs from the same unit, which the schema explicitly claims to support.

### Likelihood Explanation
This code path executes automatically and deterministically for every unit whose outputs address more than one AA in the same unit — no privileged access is required, only that an ordinary unit poster construct a single payment unit with outputs to two (or more) different autonomous agents. This is a common, encouraged usage pattern (multi-AA payments in one unit), making the trigger condition easily and repeatedly reachable by any unprivileged unit poster.

### Recommendation
Scope the anti-replay counter/check to `(trigger.unit, address)` rather than `trigger.unit` alone — e.g., track `count_aa_responses` per AA address (or simply rely on/verify against the existing `UNIQUE (trigger_unit, aa_address)` constraint in `aa_responses`) so that: (1) genuinely independent AA triggers from the same unit are not spuriously blocked, and (2) any accidental re-processing of the *same* `(unit, address)` pair is deterministically rejected without needing a unit-wide heuristic gated behind an MCI upgrade flag.

### Proof of Concept
1. Post a single unit `U` with `payment` outputs to two different AA addresses `A1` and `A2`.
2. At stabilization, `handleAATriggers()` in `main_chain.js` inserts two `aa_triggers` rows: `(mci, U, A1)` and `(mci, U, A2)` [6](#0-5) .
3. `aa_composer.handleAATriggers()` processes them in order; processing `(U, A1)` succeeds and calls `UPDATE units SET count_aa_responses = count_aa_responses + 1 WHERE unit=U`, setting `storage.assocStableUnits[U].count_aa_responses = 1` [4](#0-3) .
4. Processing `(U, A2)` then hits `storage.assocStableUnits[trigger.unit].count_aa_responses` truthy, and — because `mci >= constants.pemCurvesFixMci` — the trigger for `A2` is bounced with "a second primary trigger from the same unit is not allowed" [7](#0-6) , even though `A2`'s payment was never previously processed. This demonstrates the check is scoped incorrectly and is the retrofit for what was previously an unguarded unit-level replay path.
