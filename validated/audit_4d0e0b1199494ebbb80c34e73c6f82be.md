### Title
Webhook signature is verified against the org named in the payload, but downstream handlers write cross-repository/cross-organization data with no matching scope check - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to check the HMAC signature against using a value taken from the untrusted payload itself (`repository.owner.login` or `organization.login`), then hands the same raw payload to handlers that operate on a completely different, unchecked value (`repository.full_name`, or in the case of `StatusHandler`, no repository scoping at all). This breaks the equality "organization whose secret authenticated the request" == "repository/commit actually written to."

### Finding Description
`verify_signature` computes `repository_owner` from the payload and uses it purely to pick which per-organization `webhook_secret` to validate the signature with: [1](#0-0) 

`repository_owner` is derived from attacker-controlled JSON fields: [2](#0-1) 

Once the signature check passes (because the attacker legitimately possesses the `webhook_secret` for *some* org configured in the same multi-tenant Shipit install — Shipit supports multiple orgs each with their own `webhook_secret`, see `Shipit.github_app_config`), the handler dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) passes the **entire, still-attacker-controlled** JSON body onward, unchanged and unre-verified, to the event handler.

The base `Handler` class resolves the target repository from a *different* field (`repository.full_name`) than the one used for signature-org selection (`repository.owner.login`): [3](#0-2) 

Nothing enforces that `repository.owner.login` (used to pick the verifying secret) is consistent with `repository.full_name` (used to pick the target `Stack`s). An attacker who owns/administers one organization in a shared, multi-org Shipit deployment can therefore sign a payload with their own org's `webhook_secret` while setting `repository.full_name` to any other tracked repository.

The worst case is `StatusHandler`, which doesn't even use the `Handler#stacks` repository scoping — it looks up commits **globally** by SHA with no repository/owner constraint at all: [4](#0-3) 

Since GitHub commit SHAs are public (visible via web UI, PRs, CI logs, etc. for any repository whose commits Shipit already tracked), the attacker only needs to know a SHA belonging to a *different* repo/organization tracked by the same Shipit instance in order to forge a `state`, `context`, `description`, and `target_url` for that commit's CI status — entirely under the authentication umbrella of their own organization's webhook secret.

`CheckSuiteHandler` has similar exposure: it resolves the target stacks via `repository.full_name` (a field never checked against the signing org), so an attacker who controls one org's secret can trigger check-run refresh actions against another org's stacks/commits: [5](#0-4) 

### Impact Explanation
Commit statuses recorded via this path (`context`, `state`) are the mechanism Shipit uses to gate CI-readiness for deploys and the merge queue (`ci.require`, `ci.blocking`, etc., documented in `README.md`). By forging a "success" status for a required-check `context` on a commit belonging to a repository/organization the attacker does not control, they can make a commit in a foreign repository appear CI-green and eligible for an unauthorized deploy or merge queue advancement — a cross-repository write and an unauthorized-deploy vector, both explicitly in-scope impact categories. This requires no `ApiClient` token, no `webhook_secret` for the *target* org, no repository write access to the target repo, and no privileged Shipit account — only knowledge of a public commit SHA and possession of the webhook secret for any one organization onboarded to the shared Shipit instance.

### Likelihood Explanation
This is only exploitable when a single Shipit instance is configured with more than one GitHub organization (`Shipit.github_organizations` / multi-org `secrets.github` schema), which is an explicitly supported, documented configuration (`config/secrets.development.shopify.yml`, `lib/shipit.rb#github_app_config`). In that multi-tenant configuration, the "attacker" is effectively any organization administrator sharing the Shipit deployment with other, unrelated organizations — an unprivileged party relative to the victim org/repo. Constructing the forged `X-Hub-Signature` requires no special access beyond that org's own webhook secret, and target commit SHAs are typically public. Likelihood is moderate: it depends on multi-org deployment and on the attacker guessing/knowing a target SHA, but no additional secrets or session are needed.

### Recommendation
Verify the webhook signature using the same field(s) that are actually acted upon by the handler, and enforce that every handler scope its side effects (commit/status lookups, stack lookups) to the specific `Repository` whose organization's secret validated the signature — never derive the signing organization from one payload field and the write target from a different, unvalidated field. In particular, `StatusHandler` must scope its `Commit` lookup to commits belonging to the repository named in the verified payload (and that repository's owner must match the organization whose secret verified the signature), not perform an unscoped, instance-wide `Commit.where(sha: ...)`.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org schema).
2. As an administrator of `orgA` (not `orgB`), obtain `orgA`'s `webhook_secret` (legitimately, as its owner).
3. Find a public commit SHA `S` belonging to a repository tracked under `orgB` in the same Shipit instance, that has a CI-required `context` (e.g. `"ci/tests"`).
4. Craft a JSON body for a `status` event:
   ```json
   {"sha": "S", "state": "success", "context": "ci/tests", "repository": {"owner": {"login": "orgA"}}}
   ```
5. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POST it to `/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s `GitHubApp`, and the signature validates successfully (attacker's own secret).
7. `StatusHandler#process` executes `Commit.where(sha: "S")` — matching the `orgB` commit with no ownership check — and calls `create_status_from_github!`, recording a forged "success" status for `ci/tests` on a commit that belongs to `orgB`, potentially unblocking that commit for deploy/merge in `orgB`'s stack.
