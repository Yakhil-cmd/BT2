### Title
Hookify's PreToolUse hook fails open on any exception, silently bypassing `action: block` rules - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The external report's root cause is a mismatch between what a security guard/hook is expected to return/signal and what actually happens on an error path, which defeats the intended enforcement decision (`GnosisSafe.execTransactionFromModule()` reverting because `checkModuleTransaction()`'s return contract wasn't honored). The `hookify` plugin in this repository has the analogous but inverted flaw: any exception raised while loading or evaluating a user's block rule is swallowed, and the hook unconditionally exits with success and no deny decision, silently letting the "blocked" tool call through.

### Finding Description
`hookify`'s `PreToolUse` hook is documented to block destructive operations such as `rm -rf` when a matching rule has `action: block` [1](#0-0) . The blocking decision is produced by `RuleEngine.evaluate_rules`, which only emits `hookSpecificOutput.permissionDecision: "deny"` when it reaches the "blocking_rules" branch without error [2](#0-1) .

The hook executor `main()` wraps rule loading and evaluation in a single `try/except Exception`, and its `finally` clause unconditionally calls `sys.exit(0)`:

```python
except Exception as e:
    # On any error, allow the operation and log
    error_output = {
        "systemMessage": f"Hookify error: {str(e)}"
    }
    print(json.dumps(error_output), file=sys.stdout)

finally:
    # ALWAYS exit 0 - never block operations due to hook errors
    sys.exit(0)
``` [3](#0-2) 

Any exception anywhere in the call chain — malformed `.claude/hookify.*.local.md` frontmatter parsing edge cases in `extract_frontmatter`/`Rule.from_dict` [4](#0-3) , unexpected `tool_input` shapes reaching `_extract_field` (e.g. non-dict items in `MultiEdit`'s `edits` list) [5](#0-4) , or any other latent bug in `_check_condition`/`_rule_matches` [6](#0-5)  — is caught by this single outer handler and converted into an `exit 0` with no `permissionDecision` field at all, which Claude Code's hook contract treats as "no opinion / allow."

This is the same class of bug as the external report: a security-relevant check's error/edge-case path fails to produce the enforcement signal the rest of the system expects, so the control silently does not fire. The direction differs — the Gnosis Safe bug fails closed (DoS on legitimate module calls), while this fails open (a `block` rule for e.g. `rm\s+-rf|dd\s+if=|mkfs|format` silently does not block) — but the latter is the more severe direction because it is a genuine bypass of a user-authored safety control rather than a mere denial of service.

### Impact Explanation
A user who installs `hookify` and authors an `action: block` rule (e.g. the shipped example blocking `rm -rf`, `dd`, `mkfs`, `format`) [1](#0-0)  relies on it to actually stop Claude Code from executing matching commands. Because the hook's outer error handler always exits `0` regardless of whether a blocking decision was in progress, any exception in the rule-loading/evaluation pipeline (malformed rule file authored earlier, an edge case in frontmatter parsing, or an unexpected tool-input shape) causes the dangerous command to run anyway, with only a `systemMessage` noting an internal "Hookify error" — easy to miss and not a hard stop. This is a real bypass of a locally-configured command-approval/hook-block control, not a mocked or no-impact scenario.

### Likelihood Explanation
The bug is deterministic once any exception occurs on the hot path (rule loading or condition evaluation), and `config_loader.load_rules`/`load_rule_file` already demonstrate that malformed rule files (which end users author, including AI-generated ones) are common enough to warrant multiple dedicated `except` clauses [7](#0-6) ; the outer handler in `pretooluse.py` is a catch-all safety net specifically because such errors are expected to happen. The "ALWAYS exit 0" comment shows this is a deliberate design choice to prioritize availability over enforcement, meaning the bypass is not a rare corner case but the designed fallback behavior for the entire block-enforcement path.

### Recommendation
Distinguish between "hook infrastructure error" (safe to fail open, e.g. missing config) and "error occurred after a blocking rule was determined to match." At minimum, when any blocking rule's condition evaluation raises, the hook should fail closed for that specific tool call (emit `permissionDecision: "deny"` with a clear "internal error, denying by default" message) rather than unconditionally exiting `0`. Consider also validating regex patterns and rule files eagerly (e.g. at rule-load time with a lint/test step) so malformed rules are surfaced to the user instead of silently defeating enforcement at tool-call time.

### Proof of Concept
1. Create `.claude/hookify.test.local.md` with a `block` rule matching destructive Bash commands, mirroring the shipped example:
```markdown
---
name: block-destructive-ops
enabled: true
event: bash
pattern: rm\s+-rf|dd\s+if=|mkfs|format
action: block
---
Destructive operation blocked.
```
2. Introduce (or naturally trigger, e.g. via a second malformed rule file, or a `MultiEdit` call whose `edits` entries are not well-formed dicts) an exception during `RuleEngine.evaluate_rules`/`_rule_matches` for that call.
3. Observe that `plugins/hookify/hooks/pretooluse.py`'s `except Exception` branch runs, prints only a `systemMessage`, and the `finally: sys.exit(0)` fires — Claude Code receives no `permissionDecision: "deny"`, so the `rm -rf ...` command proceeds despite the configured `block` rule.

        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        if rule.tool_matcher:

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True

def extract_frontmatter(content: str) -> tuple[Dict[str, Any], str]:
    """Extract YAML frontmatter and message body from markdown.

    Returns (frontmatter_dict, message_body).

    Supports multi-line dictionary items in lists by preserving indentation.
    """
    if not content.startswith('---'):
        return {}, content

    # Split on --- markers
    parts = content.split('---', 2)
    if len(parts) < 3:
        return {}, content

    frontmatter_text = parts[1]
    message = parts[2].strip()

    # Simple YAML parser that handles indented list items
    frontmatter = {}
    lines = frontmatter_text.split('\n')

    current_key = None
    current_list = []
    current_dict = {}
    in_list = False
    in_dict_item = False

    for line in lines:
        # Skip empty lines and comments
        stripped = line.strip()
        if not stripped or stripped.startswith('#'):
            continue

        # Check indentation level
        indent = len(line) - len(line.lstrip())

        # Top-level key (no indentation or minimal)
        if indent == 0 and ':' in line and not line.strip().startswith('-'):
            # Save previous list/dict if any
            if in_list and current_key:
                if in_dict_item and current_dict:
                    current_list.append(current_dict)
                    current_dict = {}
                frontmatter[current_key] = current_list
                in_list = False
                in_dict_item = False
                current_list = []

            key, value = line.split(':', 1)
            key = key.strip()
            value = value.strip()

            if not value:
                # Empty value - list or nested structure follows
                current_key = key
                in_list = True
                current_list = []
            else:
                # Simple key-value pair
                value = value.strip('"').strip("'")
                if value.lower() == 'true':
                    value = True
                elif value.lower() == 'false':
                    value = False
                frontmatter[key] = value

        # List item (starts with -)
        elif stripped.startswith('-') and in_list:
            # Save previous dict item if any
            if in_dict_item and current_dict:
                current_list.append(current_dict)
                current_dict = {}

            item_text = stripped[1:].strip()

            # Check if this is an inline dict (key: value on same line)
            if ':' in item_text and ',' in item_text:
                # Inline comma-separated dict: "- field: command, operator: regex_match"
                item_dict = {}
                for part in item_text.split(','):
                    if ':' in part:
                        k, v = part.split(':', 1)
                        item_dict[k.strip()] = v.strip().strip('"').strip("'")
                current_list.append(item_dict)
                in_dict_item = False
            elif ':' in item_text:
                # Start of multi-line dict item: "- field: command"
                in_dict_item = True
                k, v = item_text.split(':', 1)
                current_dict = {k.strip(): v.strip().strip('"').strip("'")}
            else:
                # Simple list item
                current_list.append(item_text.strip('"').strip("'"))
                in_dict_item = False

        # Continuation of dict item (indented under list item)
        elif indent > 2 and in_dict_item and ':' in line:
            # This is a field of the current dict item
            k, v = stripped.split(':', 1)
            current_dict[k.strip()] = v.strip().strip('"').strip("'")

    # Save final list/dict if any
    if in_list and current_key:
        if in_dict_item and current_dict:
            current_list.append(current_dict)
        frontmatter[current_key] = current_list

    return frontmatter, message
