### Title
Spot-reserve donation inflates Aquarius LP collateral price, enabling over-borrow and bad debt — (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
The PancakeBunny incident class — manipulating an AMM-derived valuation used for credit decisions — maps onto XOXNO Lending's Aquarius LP fair-value oracle. `fair_lp_price_wad` prices an LP share as `2 * sqrt(value_a * value_b) / total_shares` using the pool's **live spot reserves** read via `get_reserves`. A plain token transfer to the Aquarius pool inflates one reserve without minting shares, inflating the reported LP price by `sqrt(1 + D/V_a)`. An attacker who is the dominant LP can supply LP shares as collateral, donate, borrow against the inflated price, and leave lenders with bad debt — while recovering nearly all of the donation through the shares' pro-rata claim on the enlarged reserves. No oracle dishonesty, no privileged call, and no flash loan is required; the donation is an ordinary unprivileged `token.transfer`, and the borrow is an ordinary `borrow`.

### Finding Description
The Aquarius provider reads live pool state every time the LP price key is resolved: `aquarius_pool_reserves_call` pulls `get_reserves` directly from the pool contract, and `aquarius_total_shares_call` pulls `get_total_shares`. [1](#0-0) [2](#0-1) 

The fair value is `2 * sqrt(value_a * value_b) * WAD / share_supply_wad` where each leg value is `reserve * price_wad / 10^decimals`. [3](#0-2) [4](#0-3) 

This geometric-mean form neutralizes *swaps* (one reserve shrinks as the other grows, product roughly constant) — the stable-pool variant even has a `swap_cannot_move_the_price` test — but it is **not neutral to donations**. A raw `token.transfer(attacker → aquarius_pool, D)` raises `reserve_a` to `reserve_a + D` while `total_shares` is unchanged, multiplying the reported share price by `sqrt(1 + D / value_a)`. Nothing in `read` detects the donation: `bound_tokens`, `pool_kind_matches`, `decimals_match`, and `min_pool_value_wad` all still pass — the donation only *raises* measured pool value, so `InsufficientAquariusLiquidity` cannot trip. [5](#0-4) 

Because prices are resolved live inside `Context` during `borrow`/`supply`, the inflated quote is used in the same transaction in which the donation lands: the attacker calls `controller.borrow(...)` immediately after the transfer. The LP source is sole-source and "waives smoothing and tolerance checks" per the docs, so there is no second leg to disagree with the inflated value; only the static sanity band bounds it. [6](#0-5) 

Critical economic detail: the donation is not burned. It accrues to the pool's reserves, so LP share holders — including the shares posted as collateral — own it pro-rata. An attacker holding essentially all of the pool's share supply (attainable by providing most of the liquidity in a small but admissible pool) pays almost nothing for the manipulation: the donated funds remain locked inside the attacker's own collateral claim.

Worked example with `LT = 0.6` (the Liqvid hub range per the threat model, `LT < 1/u` argument assumes honest prices): [7](#0-6) 

- Attacker owns ~100% of a listed Aquarius constant-product LP share; true share value `P`, holds `n` shares as collateral worth `n·P`.
- Donates `D ≈ 3·value_a` to the pool → reported price `P' ≈ 2P`.
- `borrow` up to `LT · n · P' = 1.2 · n·P` — healthy by construction, immediately under-collateralized at the true price.
- The position defaults; `clean_bad_debt`/`liquidate` cannot recover more than the real `n·(P + D·sharefrac)` which, even counting the donation's real value captured by shares, is below the debt because `D` was already the attacker's own money cycling through the pool. Net theft ≈ `(LT·f − 1)·n·P` funded by lending-pool suppliers.

### Impact Explanation
Theft of lender funds / protocol insolvency: the borrowed assets are real pool liquidity; the seized collateral's true value is below the debt, producing bad debt that the supply-index write-down socializes onto suppliers. The same primitive works on the stable-pool path (`fair_stable_lp_price_wad` solves `D` from the same donated reserves; `min_price` leg pricing only bounds the *oracle price* leg, not the reserve manipulation). [8](#0-7) 

### Likelihood Explanation
Requirements: a listed collateral whose price resolves to an Aquarius LP source, and an attacker able to dominate that pool's share supply. Both are plausible for long-tail Aquarius LP collateral listings; no privileged access, no oracle misbehavior, and no flash loan is needed — only `token.transfer` plus `controller.borrow`, both unprivileged. The main mitigation in code is the static sanity band: if `min`/`max` are set tightly around the true price, inflation beyond ~`1/LT` is rejected — but bands are fixed absolute bounds set at config time and the docs admit they "cannot establish economic correctness," so a wide band or a price drifted near `min` re-opens the window. [9](#0-8) 

### Recommendation
Do not derive LP fair value from raw spot reserves. Options:
- Track reserve changes per pricing session and reject when a reserve moved without a corresponding share mint/burn within the read window (requires the pool to expose mint/burn-derived reserves, e.g., read balances net of accrued donations is not observable — instead require the pool's own `virtual_price`/invariant view where available).
- For constant-product pools use the Alpha-style formula `2·sqrt(p_a·p_b)·sqrt(r_a·r_b)/shares` **combined with a donation check**: compare `r_a·r_b` (invariant `k`) against a persisted/TWAP'd `k` so pure donations that raise `k` without minting are detected.
- Constrain accepted reserves to those implied by a manipulation-resistant invariant rather than the raw balance (e.g., for stable pools use the `D`-implied balanced reserves).
- As defense in depth, make the sanity band dynamic (e.g., bound relative to a smoothed/TWAP LP price) rather than fixed min/max, and require the LP token's two leg keys to be dual-source.

### Proof of Concept
1. Governance (or existing config) lists Aquarius constant-product LP share `S` of pool `P(A,B)` as a collateral; the price key resolves via `AssetOracle::AquariusLp(lp)` with `stable=false`.
2. Attacker acquires ≥95% of `S` supply by providing liquidity to `P`.
3. Attacker calls `supply(account, S, n)` posting all `S` as collateral, then `update_account_threshold(account)`.
4. Attacker calls `token(B).transfer(attacker, P, D)` with `D = 3·(reserve_b·p_b)` — a direct token transfer, explicitly an in-scope unprivileged action.
5. Attacker calls `controller.borrow(attacker, account_id, debt_asset, LT·n·P'_wad ...)`. Inside `Context`, `engine::resolve_nested` → `aquarius::read` → `aquarius_pool_reserves_call` sees the donated reserve; `fair_lp_price_wad` reports `≈2P`; HF and `min_borrow_collateral_usd` pass.
6. Price reverts to `P` for subsequent reads (no further donation needed — the inflated read already happened). Position is under-water: `n·P < debt`. Liquidators seizing `S` recover less than the debt; `clean_bad_debt` writes the remainder down against supplier indexes.

The attacker recovers most of `D` because their shares (collateral + any retained) claim the enlarged reserves; cost is bounded by the non-owned share fraction plus liquidation bonus on the seized collateral, while profit equals the over-borrowed debt assets — pure lender loss.

pub fn aquarius_pool_reserves_call(env: &Env, pool: &Address) -> Option<(i128, i128)> {
    let reserves = match AquariusPoolClient::new(env, pool).try_get_reserves() {
        Ok(Ok(reserves)) => reserves,
        _ => return None,
    };
    if reserves.len() != 2 {
        return None;
    }
    Some((
        i128::try_from(reserves.get_unchecked(0)).ok()?,
        i128::try_from(reserves.get_unchecked(1)).ok()?,
    ))
}

**File:** docs/explanation/threat-model.md (L199-210)
```markdown
Lender safety depends only on the reported collateral prices. Bad debt occurs
only when the reported collateral is less than the debt. Take one collateral
leg with `n` units and a debt `D`. A borrow at the reported price `p1` gives
`D <= LTV * n * p1`. Bad debt at a later reported price `p2` needs
`n * p2 < D`. Both conditions need `p1 / p2 > 1 / LTV >= 1 / LT`. When
`LT < 1 / u`, `1 / LT > u`, and the band does not allow this ratio. An account
that is healthy at a report `p1` has `D <= LT * n * p1`, so the same result
applies from that report. A liquidation does not decrease the units held for
each unit of debt, so the result also applies after a liquidation. Thus
lenders cannot lose while `LT < 1 / u`. The band ratio `u` is the threshold,
not the price deviation. The Liqvid hub has LT 60% or 53% and `u` at most
11/9, so it has a large margin.
```
