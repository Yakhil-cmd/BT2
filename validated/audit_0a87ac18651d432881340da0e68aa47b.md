### Title
Cross-organization webhook forgery: signature verified against `repository.owner.login`'s secret, but handlers act on `repository.full_name` — (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound webhook using one field of the untrusted JSON payload (`repository.owner.login`), while the event handlers that actually mutate state select the target `Repository`/`Stack` using a *different* field of the same payload (`repository.full_name`). Because the HMAC covers the raw request body as a whole but nothing ties `owner.login` to `full_name`, an operator of any organization configured in this Shipit instance's multi-org `github:` secrets can sign a payload with their own known `webhook_secret` while pointing `full_name` at a repository belonging to a different, victim organization.

### Finding Description
`verify_signature` derives the organization to authenticate against purely from the payload: [1](#0-0) [2](#0-1) 

`repository_owner` (`repository.owner.login`, falling back to `organization.login`) is used to look up `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is then used to validate `X-Hub-Signature` against the raw POST body: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the *same, single* payload to the matching handlers: [4](#0-3) 

Handlers, however, resolve the target repository/stack from a **different** payload field, `repository.full_name`, via `Handler#repository_name` / `#stacks`: [5](#0-4) 

`PushHandler#process` then acts on whichever stacks belong to that repository, using an attacker-controlled `after` SHA and branch parsed straight from the same payload: [6](#0-5) 

This is exactly the class of bug in the reference report: two logically-related values that should be bound together (the identity used to *authenticate* the request vs. the identity that is *acted upon*) are instead read from independent, unauthenticated fields of the same payload, and only one of them is meaningfully checked (via signature) while the other flows straight into state-changing logic. Configuration such as `config/secrets.development.shopify.yml` / `secrets_double_github_app.yml` shows that a single Shipit instance is explicitly designed to host multiple, independently-secreted GitHub organizations: [7](#0-6) 

### Impact Explanation
An attacker who legitimately controls a GitHub organization/App configured on the same Shipit instance (and therefore knows that organization's own `webhook_secret`, which they configured themselves) can:
1. Set `repository.owner.login` (or `organization.login`) to their own org, so the signature check passes using a secret they know.
2. Set `repository.full_name` to `victim-org/victim-repo`, causing `PushHandler` (or other handlers keyed off `repository_name`) to resolve and act on stacks belonging to an organization/repository they have no legitimate relationship to.

This lets a tenant of a shared, multi-org Shipit deployment force GitHub-sync/push processing (and any other handler keyed the same way, e.g. `check_suite`, `status`, `pull_request`) against another tenant's stacks — a cross-repository write triggered under a forged trust binding, satisfying the "organization that authenticated versus the repository that is written" boundary called out in scope. The concrete blast radius depends on what each handler does with the forged `full_name` (e.g. `PushHandler` enqueues `sync_github`, which could interact with continuous-deployment/merge-queue logic on the victim stack).

### Likelihood Explanation
Requires only that Shipit be configured for multiple organizations (a documented, supported configuration) and that the attacker be a legitimate operator/admin of at least one of those organizations (able to configure/know their own app's `webhook_secret`) — no privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repository is needed. This matches an "unprivileged-attacker" analog relative to the victim organization.

### Recommendation
Bind the field used for signature-secret selection to the field used for repository resolution: derive both from the same, single value (preferably `repository.full_name`'s owner, or explicitly validate that `repository.owner.login` matches `repository.full_name`'s owner segment before invoking handlers). Reject the webhook if these are inconsistent.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` format).
2. As the operator of `attacker-org`, craft a payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` — known because attacker configured `attacker-org`'s own app.
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` looks up `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and validates successfully.
5. `PushHandler` resolves `stacks` via `payload.dig('repository','full_name')` → `victim-org/victim-repo`, and calls `stack.sync_github(expected_head_sha: 'deadbeef')` on the victim's stack — despite the request never having been signed with anything belonging to `victim-org`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
