Based on my investigation, I found a genuine analog. `findAddress()` in `wallet.js` resolves `body.address` to `ifLocal` for **any** address (single-key `my_addresses` *or* shared-address paths) that this device holds fully locally — the moment the requested `signing_path` fully resolves to a locally-held key, `ifLocal` fires regardless of whether `from_address` (the correspondent device that sent the `"sign"` request) is actually one of the parties associated with that address. [1](#0-0) 

The authorization check that would have prevented this was explicitly written and then commented out: [2](#0-1) 

Note the contrast: for the `ifRemote` branch (i.e., when the request is being *proxied* to another device), the code does verify `other_device_addresses.includes(from_address)` before doing anything: [3](#0-2) . But for the `ifLocal` branch — the path that actually leads to the wallet owner being asked to sign and broadcast a transaction from their own funds — no equivalent check exists that `from_address` is a legitimate cosigner/party for `body.address`/`body.signing_path`. This is the same class of bug as the WOPI report: a permission check exists for one code path (`ifRemote`) but is disabled/missing on the sibling path (`ifLocal`) that performs the sensitive action.

### Title
Missing cosigner authorization check lets any paired device trigger signing requests for the wallet owner's own addresses - (File: wallet.js)

### Summary
The `"sign"` message handler in `handleMessageFromHub()` accepts a `{address, signing_path, unsigned_unit}` payload from any correspondent device and resolves it via `findAddress()`. When the resolved key is held locally by the current device (`ifLocal`), the handler immediately proceeds to build the unit and emit `signing_request` (which drives a UI confirmation and potential automatic signing/broadcast for e.g. shared-address cosigning flows), without ever verifying that the sending device (`from_address`) is actually a wallet cosigner, a shared-address participant, or otherwise entitled to request a signature on that specific address/path. The check that would enforce this is written directly above the vulnerable code, but is commented out.

### Finding Description
`findAddress()` walks `my_addresses`, `shared_address_signing_paths`, and `peer_addresses` to classify a `(address, signing_path)` pair as local, remote, merkle, or secret. [4](#0-3)  When the path resolves to a key that lives on the current device, `callbacks.ifLocal(objAddress)` fires unconditionally — there is no check tying the request back to the identity of `from_address`, the device that originated the "sign" justsaying message. [5](#0-4) [2](#0-1) 

The intended safeguard — verifying that the sender is a listed cosigner of the multi-device wallet/shared address before proceeding — is present as a SQL query in a comment, with an explanatory note that enabling it "would make multilateral signing impossible": [6](#0-5) . This mirrors the WOPI report's root cause precisely: an authorization value/mechanism is known and even implemented, but deliberately not enforced on the "write"-equivalent path (here, the path that leads to producing and potentially broadcasting a signed unit), while the sibling path (`ifRemote`) does enforce essentially the same authorization semantically (`other_device_addresses.includes(from_address)`). [3](#0-2) 

As a result, any correspondent device (or any device that manages to get itself paired — e.g., via a discovered/guessed permanent pairing secret, since `getOrGeneratePermanentPairingInfo` reuses a long-lived secret across arbitrary numbers of peers) can send a forged `"sign"` message naming any of the victim's own `my_addresses`/shared address paths and an attacker-crafted `unsigned_unit`. The wallet will validate the unit (`network.handleOnlineJoint`) and then fire `signing_request`, which most wallet UIs use to prompt (or, in headless/multi-sig-automation setups, to auto-approve) a signature — without any code-level confirmation that the requesting device had any legitimate relationship to that address.

### Impact Explanation
If the UI's `signing_request` handler is invoked (e.g., in a scripted/multisig automation node, a co-signing bot, or a UI where the confirmation is not diligently distinguishing which device sent the request vs. which addresses that device is entitled to sign for), an attacker-controlled paired device can cause the victim's wallet to sign and broadcast a transaction that spends the victim's own funds to an address of the attacker's choosing (unauthorized spending), or manipulate multi-party contract/shared-address flows the same way arbiter/prosaic contracts do (`arbiter_contract.js`, referenced from the same code path). This is a fund-loss / unauthorized-spending impact analogous to the WOPI write bypass, reachable purely by a paired device sending a crafted `device_message` — no operator, hub, or network-level compromise required.

### Likelihood Explanation
Requires the attacker's device to already be a correspondent (paired) of the victim, which the report's threat model explicitly allows ("paired device" is in scope). Exploitation additionally depends on the UI/automation reacting to `signing_request` without separately validating the requester against the address's legitimate cosigners — this is plausible especially for automated multi-device wallets/cosigning services (the very "multilateral signing" scenario the comment references) where confirmation may be automatic or insufficiently scoped.

### Recommendation
Restore and adapt the disabled check: before invoking `ifLocal`'s handling for the `"sign"` command, verify that `from_address` corresponds to a legitimate signer/cosigner relationship for `body.address` (e.g., a `shared_address_signing_paths` entry, a wallet member device, or a known contract counterparty), mirroring the check already enforced in the `ifRemote` branch (`other_device_addresses.includes(from_address)`). At minimum, `signing_request` consumers should be handed enough information to verify that the requesting device is entitled to request a signature on the specific address/path, and default UIs/automations should refuse silently-mismatched requests rather than relying solely on user vigilance.

### Proof of Concept
1. Attacker pairs their device with the victim's wallet (device pairing, in scope per threat model), becoming a `correspondent_devices` entry.
2. Attacker sends a hub `device_message` with `subject: "sign"` and `body: {address: <victim's own my_addresses address>, signing_path: "r", unsigned_unit: <attacker-crafted unit paying attacker's address>}`.
3. `handleMessageFromHub` → `doHandle()` → case `"sign"` performs structural validation only (address format, signing path format, payload-hash consistency) but does not check that the attacker's device is entitled to request this signature. [7](#0-6) 
4. `findAddress(body.address, body.signing_path, …)` resolves to `ifLocal` since the address is one of the victim's own keys. [8](#0-7) 
5. The commented-out cosigner check is never executed; `signing_request` is emitted directly to the victim's UI/automation for a unit the attacker fully controls. [9](#0-8)
