### Title
Sparse-checkout content restrictions are silently bypassed for submodules, publishing "hidden" data - (File: main.go, function `configureWorktree`)

### Summary
`--sparse-checkout-file` is git-sync's mechanism for operators to restrict which paths of a synced repo are checked out and published via the atomic symlink (analogous to Nextcloud's "Hide Download" toggle: a feature that gives the operator/consumer a false sense that certain content is excluded from what's exposed). In `configureWorktree`, the sparse-checkout configuration is applied to the main worktree, but the subsequent, unconditional `git submodule update --init [--recursive]` step is not scoped by the sparse-checkout patterns, so submodule paths are always fully cloned and published regardless of sparse-checkout exclusions.

### Finding Description
`configureWorktree` first applies sparse-checkout (if `git.sparseFile != ""`) via `sparse-checkout init` plus a hand-written `info/sparse-checkout` file [1](#0-0) , then resets the worktree to the target hash, and finally — with no interaction with sparse-checkout state — unconditionally updates submodules whenever `git.submodules != submodulesOff`: [2](#0-1) 

Git's `sparse-checkout` mechanism only controls which paths are materialized in the *main* worktree; it has no effect on `git submodule update --init`, which will still clone and check out a submodule in full even if the submodule's path is excluded by the sparse-checkout patterns. The e2e test suite exercises sparse-checkout and submodules as independent features [3](#0-2)  but there is no test combining a sparse-checkout exclusion with a submodule at the excluded path, so this gap is untested and unaddressed in the code.

Consequently, if an operator relies on `--sparse-checkout-file` to keep a given path out of the published `--link` tree (e.g., to hide a directory containing sensitive files from downstream consumers of the synced volume), an attacker who can influence repository content (e.g., by contributing a PR/branch that is later synced, or by controlling a nested/remote submodule reference) can convert that path into a git submodule. Because submodule checkout ignores sparse-checkout restrictions, the "hidden" path becomes fully populated and published anyway.

### Impact Explanation
This matches the Impact category "publishing wrong or partial content": the intended content-restriction contract (only sparse-checkout-selected paths are published) is violated, and normally-excluded content is exposed to any consumer of the `--link` symlink. In a git-sync deployment where sparse-checkout is used precisely to gate what an application container can see, this is a content-disclosure/access-control-bypass analogous to the "Secure View" bypass: the exclusion setting is easily circumvented ("just add a submodule instead of a plain directory") without any error, warning, or code change on git-sync's part.

### Likelihood Explanation
Likelihood depends on how sparse-checkout is used and whether repository content is attacker-influenced. It requires: (1) the operator configured `--sparse-checkout-file` to exclude a path, (2) `--submodules` is not `off` (the default is `recursive`), and (3) the excluded path can be turned into (or already is) a submodule under attacker/contributor control. This is a plausible but non-default configuration combination — not universally exploitable in every git-sync deployment, but realistic where sparse-checkout is deliberately used as a data-minimization/access boundary against partially-trusted repo content.

### Recommendation
- Document explicitly that `--sparse-checkout-file` does not apply to submodules, and that submodule paths are always fully checked out regardless of sparse-checkout exclusions.
- Optionally, when both `--sparse-checkout-file` and submodules are enabled, either (a) skip/deinit submodules whose paths fall outside the sparse-checkout patterns before running `submodule update`, or (b) refuse to combine the two features unless the operator explicitly acknowledges the limitation.
- Add e2e coverage that combines `--sparse-checkout-file` with a submodule located at an excluded path to make the current (unsafe) behavior visible in tests.

### Proof of Concept
1. Configure git-sync with `--submodules=recursive` (default) and `--sparse-checkout-file` containing patterns that exclude directory `secret/` (e.g. `!/secret/`), similar to the pattern used in `e2e::sparse_checkout` [4](#0-3) .
2. In the synced repository, add a git submodule at path `secret/` pointing to any reachable repo containing the data that should be hidden.
3. Run git-sync; the sparse-checkout file successfully excludes ordinary tracked files/directories named `secret/*`, but because `configureWorktree` always runs `git submodule update --init --recursive` unconditionally after applying sparse-checkout [2](#0-1) , `secret/` is nonetheless fully cloned and appears under the published `--link` symlink — bypassing the intended content restriction.

Note: I was unable to execute git-sync to empirically confirm the runtime behavior (no execution environment available), so this is based on static analysis of `configureWorktree`'s code path and known git sparse-checkout/submodule semantics; a Devin session with a sandbox could run the e2e scenario above to confirm empirically.

# Test sparse-checkout files

function e2e::sparse_checkout() {
    echo "!/*" > "$WORK/sparseconfig"
    echo "!/*/" >> "$WORK/sparseconfig"
    echo "file2" >> "$WORK/sparseconfig"
    echo "${FUNCNAME[0]}" > "$REPO/file"
    echo "${FUNCNAME[0]}" > "$REPO/file2"
    mkdir "$REPO/dir"
    echo "${FUNCNAME[0]}" > "$REPO/dir/file3"
    git -C "$REPO" add file2
    git -C "$REPO" add dir
    git -C "$REPO" commit -qam "${FUNCNAME[0]}"

    GIT_SYNC \
        --one-time \
        --repo="file://$REPO" \
        --root="$ROOT" \
        --link="link" \
        --sparse-checkout-file="$WORK/sparseconfig"
    assert_link_exists "$ROOT/link"
    assert_file_exists "$ROOT/link/file2"
    assert_file_absent "$ROOT/link/file"
    assert_file_absent "$ROOT/link/dir/file3"
    assert_file_absent "$ROOT/link/dir"
    assert_file_eq "$ROOT/link/file2" "${FUNCNAME[0]}"
}
