### Title
Missing authorization check allows untrusted "indirect correspondents" to send privileged wallet/device messages - ([File: wallet.js])

### Summary
`device.js` computes `is_indirect` for every correspondent and passes it as `bIndirectCorrespondent` into `handleMessageFromHub` in `wallet.js` specifically so that devices which are only *indirectly* known (introduced automatically as co-signers of a shared/multisig address, never explicitly paired by the user) can be restricted to a small, safe whitelist of message subjects. That restriction is implemented but has been disabled by commenting it out, so any subject is now accepted from an indirect, untrusted correspondent.

### Finding Description
`device.js`'s `handleJustsaying` (`hub/message` case) authenticates the signature/hash of an incoming device message and determines whether the sender is a known correspondent, then looks up `is_indirect` from `correspondent_devices` and forwards this flag into the event `handle_message_from_hub`: [1](#0-0) 

In `wallet.js`, `handleMessageFromHub(ws, json, device_pubkey, bIndirectCorrespondent, callbacks)` receives that flag, and the intended access-control gate that would reject sensitive subjects from indirect correspondents is present in the source but disabled: [2](#0-1) 

With this check commented out, the giant `switch(subject)` in `doHandle()` processes *every* subject identically regardless of `bIndirectCorrespondent`, including highly privileged flows such as `signing_request`/`sign` handling that triggers unit validation and signing-confirmation dialogs, `private_payments` chain forwarding, `create_new_shared_address`, `prosaic_contract_offer`/`arbiter_contract_*`, and `new_wallet_address`. `addIndirectCorrespondents` in `device.js` shows how trivially an "indirect correspondent" relationship is created — simply by being listed as a cosigner in a wallet-creation offer, without any explicit user pairing action: [3](#0-2) 

This is the same bug class as the Mattermost advisory (CWE-862 Missing Authorization / CWE-284 Improper Access Control): a message/event channel that is supposed to be gated to a privileged group (correspondents the user actually trusts / team members) instead reaches an unauthorized recipient class (indirect, auto-added correspondents / non-members) because the authorization check was removed while the surrounding plumbing (the `bIndirectCorrespondent` flag, the whitelist array) was left in place — indicating the gate used to exist and was intentionally bypassed.

### Impact Explanation
An indirect correspondent (any device automatically added to `correspondent_devices` as `is_indirect=1` merely by being named as a cosigner in a wallet/shared-address creation flow, with no explicit trust decision by the user) can now send arbitrary subjects that were previously reserved for fully-trusted, explicitly paired correspondents. Concretely reachable, wallet/AA-relevant paths include:
- `sign`/signing-request handling (`wallet.js` ~line 341+), which can trigger `network.handleOnlineJoint` processing of an attacker-influenced unsigned unit and pop confirmation dialogs, potentially tricking a user's wallet into signing unintended spends.
- `private_payments` handling and forwarding to other cosigners of shared addresses, exposing/propagating private payment chain data (`wallet.js` `handlePrivatePaymentChains`, `forwardPrivateChainsToOtherMembersOfSharedAddresses`) to parties that were never meant to see it.
- `create_new_shared_address`/`new_shared_address` flows that can inject unexpected address definitions/co-signers into the victim's wallet state.

This maps to the "wallet and contract message handling" and "private payment chains" categories called out as in-scope, and the concrete effect is potential unauthorized fund-signing exposure and unauthorized dissemination of private-payment data — consistent with a Medium severity confidentiality/integrity issue analogous to the Mattermost broadcast-to-non-members bug.

### Likelihood Explanation
Reachability is straightforward: any device that becomes a cosigner candidate in a wallet-creation or shared-address flow is automatically registered as an indirect correspondent (`addIndirectCorrespondents`), and can subsequently message the victim over the hub channel with any subject, since the authorization gate that would otherwise stop this is dead code. No malicious hub or peer compromise is needed — this is reachable purely through the standard wallet/shared-address/contract message protocol that unprivileged users interact with.

### Recommendation
Re-enable (or reimplement, since requirements may have evolved) an authorization gate in `wallet.js`'s `handleMessageFromHub` that restricts `bIndirectCorrespondent` senders to an explicit, reviewed whitelist of subjects (e.g., only the subjects needed to complete cosigner-onboarding flows such as `my_xpubkey`, `wallet_fully_approved`, and the minimal shared-address bootstrap messages). All other subjects — especially `sign`, `private_payments`, `signing_request`, `create_new_shared_address`, and contract-related subjects — should be rejected from indirect correspondents unless/until the user has explicitly upgraded them to a direct/trusted correspondent.

### Proof of Concept
1. Device B (attacker) is included as a cosigner address in a shared-address/multisig wallet-creation template offered to Device A (victim), or otherwise becomes listed in `arrOtherCosigners`. Device A's wallet calls `device.addIndirectCorrespondents`, inserting B into `correspondent_devices` with `is_indirect=1` — without any explicit pairing/trust action by A's user. [3](#0-2) 
2. Device B now sends a `hub/message` to A's hub with `json.subject` set to a privileged subject (e.g., `sign` or `private_payments`) instead of one of the originally-intended whitelisted subjects.
3. `device.js` looks up `is_indirect=1` for B and forwards `bIndirectCorrespondent=true` into `handle_message_from_hub`. [1](#0-0) 
4. In `wallet.js`, the intended rejection `if (bIndirectCorrespondent && !whitelist.includes(subject)) return callbacks.ifError(...)` is commented out, so the message flows straight into the `switch(subject)` handler for `sign`/`private_payments`/etc., exactly as if B were a fully-trusted correspondent. [2](#0-1)
