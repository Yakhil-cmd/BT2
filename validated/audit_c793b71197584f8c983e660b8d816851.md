### Title
ERC20Transactor credits `AssetsInHolding` with the *requested* transfer amount instead of the amount actually confirmed on-chain, mismatching non-standard/fee-on-transfer ERC20 reserve assets - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Matcher` matches **any** local `AccountKey20` location as an ERC20 asset for XCM purposes [1](#0-0) , and `ERC20Transactor` is wired into Asset Hub Westend's `AssetTransactors` [2](#0-1) . This transactor calls an arbitrary contract's `transfer(address,uint256)` and, on success, credits `AssetsInHolding` with the amount **that was requested**, not the amount actually delivered, mirroring the exact bug class from the report (fee-on-transfer/non-standard ERC20 accounting is trusted rather than measured).

### Finding Description
Per the PR that introduced this transactor, any XCM asset id of the form `{parents:0, interior: X1(AccountKey20{key,...})}` is matched and its `transfer` function is invoked on the contract at that address [3](#0-2) . Since `pallet-revive` allows permissionless contract deployment, an ordinary user can deploy a custom "ERC20" contract implementing whatever `transfer` semantics they choose (e.g. fee-on-transfer, or a contract that always returns `true` while moving less than `value`), and reference it in an XCM program via its `AccountKey20` location — this is a normal, unprivileged extrinsic path (`pallet_revive::Pallet::instantiate` and `pallet_xcm::execute`/`transfer_assets`), with no governance or admin gate on which contract addresses can be used as ERC20 "assets."

In `withdraw_asset_with_surplus`, the transactor calls `transfer(checking_account, amount)` on the user-supplied contract, and only checks the boolean return value:
```
let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data)...;
if is_success {
    Ok((AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount))), surplus))
}
``` [4](#0-3) 

The `amount` credited into the XCM `AssetsInHolding` is the value from `Matcher::matches_fungibles(what)` (i.e., the amount the sender *requested* to move), not a value derived from an actual before/after balance check of the checking account. `Erc20Credit` is an "unsafe manual accounting" imbalance type that explicitly does not enforce runtime-level balance constraints, trusting the ERC20 contract entirely [5](#0-4) .

Symmetrically, `deposit_asset_with_surplus` transfers the same `amount` from the checking account to the beneficiary and again only inspects the returned bool [6](#0-5) .

This is the direct analog of the report's Issue #2 (fee-on-transfer tokens: "the contract will actually receive a lesser amount... the contract code does not check if the amount received is the expected amount"). If a malicious/non-standard ERC20 contract implements a fee/burn on `transfer` (or simply lies and returns `true` while transferring less than requested), the checking account's actual ERC20 balance increases by less than `amount`, but the XCM executor's `AssetsInHolding` still records the full `amount`. When the executor later tries to `deposit_asset_with_surplus` that full `amount` to a destination (potentially on a different chain/hop, or with `DepositAsset { Wild(AllCounted) }` semantics), the deposit call to `transfer(beneficiary, amount)` on the checking account will either fail (checking account has less than `amount`, XCM program errors) or, more importantly, drains the checking account below what other in-flight/concurrent XCM programs for the *same* ERC20 contract assume it holds, since `TransfersCheckingAccount` is a single shared account for that asset type. This creates a divergence between the XCM-internal ledger (`AssetsInHolding`) and the true, contract-enforced balance, i.e., exactly the "receives less than expected without any check" failure mode from the report, but implemented via a substrate `TransactAsset` rather than a bespoke Solidity contract.

### Impact Explanation
Because the credited amount is never reconciled against the checking account's real post-transfer balance, an attacker-controlled ERC20 contract used as an XCM reserve asset can cause the runtime's XCM holding ledger to diverge from actual on-chain ERC20 balances. This can lead to failed/stuck XCM programs (denial of service for the checking account's future transfers of that asset) or, in multi-hop/DOT-fee-refund scenarios, an accounting mismatch that lets a user register a fee-on-transfer ERC20 asset and have the executor believe more value moved through the checking account than actually did — undermining the "exactly what was withdrawn is what gets deposited" invariant that XCM's asset transactor model relies on. This is comparable in class (accounting divergence from ERC20 non-standard behavior) to the original BaseJackpot report but confined to the ERC20-precompile/XCM bridge feature, which itself is a new, narrowly-scoped feature (Asset Hub Westend only, permissionless contract deployment via `pallet-revive`).

### Likelihood Explanation
Reachability requires only: (1) deploying an arbitrary contract via `pallet-revive` (permissionless, `EnsureSigned` origin) [7](#0-6) , and (2) submitting an XCM program (e.g. via `pallet_xcm::execute` or `transfer_assets`) referencing that contract's `AccountKey20` location as the asset — both are unprivileged, ordinary user actions. No validator/collator/governance compromise is needed. However, whether this reaches a genuinely exploitable state (vs. merely a failed/erroring XCM program, which is the more likely outcome given `deposit_asset_with_surplus` would then also fail against the shorted checking-account balance) depends on interaction with concurrent XCM programs sharing the same `TransfersCheckingAccount`, which I could not fully trace within the available context (I did not find how/whether multiple concurrent withdraw/deposit sequences for the same ERC20 asset are serialized within a single block, and did not locate a full local repro).

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, snapshot the checking/beneficiary account's actual ERC20 `balanceOf` before and after the `transfer` call, and credit/require exactly the delta rather than the caller-requested `amount` — mirroring the report's recommendation to measure pre/post balances rather than trusting the nominal transfer amount. Alternatively, explicitly document/enforce (via a governance-controlled allow-list, not simple location matching) that only known-compliant ERC20 contracts (no fee-on-transfer, honest boolean return) may be used as XCM reserve assets through this transactor, since `ERC20Matcher`/`IsLocalAccountKey20` currently accept any `AccountKey20` location without restriction [1](#0-0) .

### Proof of Concept
I was not able to construct and execute a full local Rust/XCM integration reproduction within the available tools/iterations. The finding is based on static code review of `erc20_transactor.rs`, its wiring in `asset-hub-westend/src/xcm_config.rs`, and the `ERC20Matcher`/`IsLocalAccountKey20` location matcher, showing the missing balance-delta check where the report's Issue #2 pattern (fee-on-transfer accounting not verified) applies. A concrete PoC would require: deploying a minimal `pallet-revive` contract whose `transfer` returns `true` but moves less than `value` to the recipient, registering/using it as the asset in an XCM `WithdrawAsset`/`DepositAsset` program via `pallet_xcm::execute`, and asserting the checking account's real ERC20 balance vs. the `AssetsInHolding` amount reported by the executor — this execution was not run, so no confirmed pass/fail result is available; this should be treated as an unverified analog pending a background Devin session with build/test tooling.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}
