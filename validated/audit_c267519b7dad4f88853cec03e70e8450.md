### Title
Webhook signature verification is bound to `repository.owner.login`, but every event handler acts on the independent, unverified `repository.full_name` field, allowing cross-organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's GitHub App/webhook secret to use for HMAC verification from an attacker-controlled field in the *same, not-yet-verified* payload, then hands the *entire* payload to event handlers that resolve the actual `Repository`/`Stack` to mutate from a *different*, equally attacker-controlled field. Nothing binds the two together, so in a multi-organization Shipit deployment an attacker who legitimately controls one configured organization can forge a validly-signed webhook that acts on a different organization's repository/stack.

### Finding Description
`Shipit.github(organization:)` supports per-organization GitHub App configuration, each with its own `webhook_secret`, as documented in `docs/setup.md` ("Using Multiple Github Applications"). [1](#0-0) 

`WebhooksController#verify_signature` picks the app/secret to validate against using `repository_owner`, which is read straight out of the unverified JSON body: [2](#0-1) [3](#0-2) 

Once the HMAC check passes for *that* org, the full, unmodified payload is dispatched to the matching handler(s): [4](#0-3) 

Every handler, however, resolves the target repository/stack from a *different* field, `repository.full_name`, with no relation to the organization used for signature verification: [5](#0-4) [6](#0-5) 

This is used for state-changing actions, e.g. syncing a stack from GitHub on `push`: [7](#0-6) 

or archiving/provisioning review stacks on `pull_request` events, which triggers `stack.deprovision` / re-enqueues provisioning (running the stack's `shipit.yml` provision/deploy steps): [8](#0-7) 

The broken equality is:
`organization used to select/validate the webhook_secret (repository.owner.login / organization.login)` **must equal** `owner(repository.full_name)` — the repository/stack the handler actually mutates.
Nothing in `verify_signature` or in any handler enforces this. Both fields live in the same attacker-supplied JSON body and can be set independently.

### Impact Explanation
In a multi-organization deployment (the officially documented configuration), anyone who administers a GitHub App on **any one** of the configured organizations (and therefore legitimately knows that organization's `webhook_secret`) can:
1. Set `repository.owner.login` (or `organization.login`) to their own organization so `verify_signature` succeeds using a secret they legitimately possess.
2. Set `repository.full_name` to `"<victim-org>/<victim-repo>"`, an org/repo they do not control.
3. Have the resulting, validly-signed request processed by handlers (`PushHandler`, `ReopenedHandler`, `LabeledHandler`/`UnlabeledHandler`, `EditedHandler`, `ClosedHandler`, etc.) against the victim's `Stack`.

This crosses the "cross-repository writes" / "unauthorized deploy" boundary: an attacker can force a `git`/commit sync, or unarchive+provision a victim's review stack (running its `shipit.yml` provisioning/deploy steps), without ever having credentials for the victim organization.

### Likelihood Explanation
Requires the Shipit instance to be configured with more than one GitHub organization/app (a supported, documented setup) and requires the attacker to control at least one of those configured organizations (e.g., their own sandbox org onboarded to the same Shipit instance). No Shipit session, API token, or the victim org's secret is needed — only knowledge of a secret the attacker legitimately owns for a *different* configured org. This is a realistic and inexpensive attack for any tenant sharing a multi-org Shipit deployment.

### Recommendation
After computing `repository_owner` for signature selection, re-derive the organization from `repository.full_name` (or `organization.login`) and require it to match the organization whose secret validated the signature before dispatching to handlers. Reject the webhook (422) on mismatch.

### Proof of Concept
Assume `config/secrets.yml` configures two orgs, `attacker-org` (attacker administers its GitHub App, knows its `webhook_secret`) and `victim-org` (has a Stack for `victim-org/victim-repo`).

```
POST /webhooks HTTP/1.1
X-Github-Event: pull_request
X-Hub-Signature: sha1=<HMAC-SHA1 of body using attacker-org's webhook_secret>
Content-Type: application/json

{
  "action": "reopened",
  "number": 1,
  "pull_request": { "id": 1, "number": 1, "url": "...", "title": "x", "state": "open",
                     "additions": 0, "deletions": 0,
                     "head": { "sha": "deadbeef", "ref": "feature" },
                     "user": { "login": "attacker" }, "assignees": [], "labels": [] },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```

- `verify_signature` calls `Shipit.github(organization: "attacker-org")` and succeeds because the HMAC was computed with `attacker-org`'s real secret.
- `Webhooks::Handlers::PullRequest::ReopenedHandler` resolves `repository` via `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")`, finds `victim-org`'s stack, and calls `stack.unarchive!`, which enqueues `ReviewStackProvisioningQueue.add(stack)` — provisioning `victim-org`'s repository despite the request never being signed by `victim-org`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
