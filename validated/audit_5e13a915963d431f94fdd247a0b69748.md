### Title
Permanent loss of staking rewards in `pallet-asset-rewards` due to rounding-to-zero in `reward_per_token` accumulator - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` computes a monotonic reward-per-token accumulator the same way GPToke's `accRewardPerShare` does: `reward_rate_per_block * elapsed_blocks * PRECISION_SCALING_FACTOR / total_tokens_staked`. The scaling constant is only `4096` (12 bits), far smaller than a typical 18-decimal balance denominator. Any unprivileged holder of the staked asset can call the public `stake`/`unstake`/`harvest_rewards` extrinsics, which trigger this computation and immediately commit `last_update_block` forward, discarding any fractional/rounded-to-zero reward increment for that period with no way to recover it later.

### Finding Description
The reward accumulator is computed in `reward_per_token`: [1](#0-0) 

and the scaling constant is defined as: [2](#0-1) 

`update_pool_rewards` unconditionally commits the freshly computed value and advances `last_update_block` to the current block, with no side channel to retain any lost precision: [3](#0-2) 

This is structurally identical to the reported GPToke bug: `amount * REWARD_FACTOR / supply` is added directly to a monotonic accumulator, and if the numerator is smaller than the denominator, the increment silently truncates to `0` and that reward-period's contribution is permanently discarded, with no mechanism to carry the remainder forward.

Any account holding the staked asset can invoke the pallet's public `stake`/`unstake`/`harvest_rewards` calls (per the pallet's own documentation, "holders of the 'staking asset' can 'stake' them in a corresponding pool" — no admin/privileged origin is required for staking or harvesting), each of which triggers `update_pool_and_staker_rewards` → `reward_per_token` → `update_pool_rewards`, permanently advancing `last_update_block`: [4](#0-3) 

This is materially different from the sibling `pallet-nomination-pools`, which the codebase deliberately hardened against exactly this class of bug: its `current_reward_counter` derives the pending amount from the pool's *actual accumulated balance* (`current_balance`), which is not reset per interaction, so a reward that rounds to zero in one call remains un-recorded in `last_recorded_reward_counter` and is retried/accumulated on the next call — proven by the dedicated regression test `zero_reward_claim_does_not_update_reward_counter`: [5](#0-4) 
and by explicit design commentary about rounding-to-zero collapse in `current_reward_counter`: [6](#0-5) 

`pallet-asset-rewards`, in contrast, has no such "retain the un-recorded remainder" mechanism: `reward_rate_per_block` is a rate applied only over `elapsed_blocks` since `last_update_block`, and once `last_update_block` advances (which happens on every stake/unstake/harvest call, triggerable by anyone at will, including the pool's own stakers or third parties holding the staked asset), the window used for the next computation resets to zero elapsed blocks. An attacker (or even an innocuous but frequently-interacting staker population) can therefore keep `elapsed_blocks` at its minimum (as low as 1) on every call, ensuring the numerator `reward_rate_per_block * elapsed_blocks * 4096` never exceeds `total_tokens_staked`, permanently truncating `reward_per_token_stored`'s growth to zero increments while `reward_asset` funds continue to sit un-attributed in the pool account.

### Impact Explanation
If exploited (or simply triggered by normal, frequent, unprivileged interaction with a large-`total_tokens_staked` pool and a comparatively low `reward_rate_per_block`), reward funds transferred into the pool's account become permanently unattributable to any staker's `reward_per_token_stored`/`rewards` fields — matching the "permanent freezing" impact class in the source report. This constitutes a Medium-severity issue: no funds are directly stolen, but they become irrecoverably stuck (never credited to any staker, and the pool has no sweep/reclaim mechanism visible in the reviewed code), which fits the report's "loss of rewards, permanently frozen" characterization rather than a more severe theft/mint bug.

### Likelihood Explanation
Likelihood is Medium: it requires no privilege, governance, or forged input — only ordinary use of the public `stake`/`unstake`/`harvest_rewards` extrinsics, which is the pallet's intended access pattern for any staked-asset holder. The precision constant (`4096`, i.e., 2^12) is small relative to realistic 18-decimal-denominated `total_tokens_staked` values, meaning the rounding-to-zero window is easy to hit even without adversarial intent, and trivially forceable by an attacker who simply calls `harvest_rewards`/small stake-unstake cycles every block to keep `elapsed_blocks` minimal.

### Recommendation
Use a design analogous to `pallet-nomination-pools`'s balance-accumulation approach (derive pending rewards from actual un-claimed pool balance rather than resetting the elapsed-block window on every interaction), or increase `PRECISION_SCALING_FACTOR` substantially (e.g., to `10^18`-scale fixed point, as `FixedU128`/`RewardCounter` does in nomination-pools) and/or track a remainder/dust carry-over so that a rounded-to-zero period's contribution is retained and combined with future periods instead of being silently dropped whenever `last_update_block` is advanced.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
