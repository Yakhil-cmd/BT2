### Title
Auto-accepted shared-address definitions are not verified to actually require the local device's signature - ([File: wallet_defined_by_addresses.js])

### Summary
`handleNewSharedAddress()` and `validateAddressDefinition()` in `wallet_defined_by_addresses.js` accept a peer-supplied multi-signature ("shared") address definition and persist it as a controlled address as long as (a) the definition is syntactically valid per `Definition.validateDefinition`, and (b) at least one leaf address in the definition happens to belong to the local wallet (`determineIfIncludesMeAndRewriteDeviceAddress`). Neither check verifies that the local device's key is actually *necessary* to authorize spending from the resulting address — an `'or'` branch containing the victim's key alongside the attacker's key satisfies both checks while letting the attacker's signature alone move funds.

### Finding Description
`Definition.validateDefinition()` in `definition.js` only enforces that "each branch must have a signature" (`definition.js:626`), i.e. every `or`/`and` branch must resolve to *some* signature path — it never enforces that a claimed "N-of-M" address actually requires N signatures. An address definition such as:

```
['or', [
  ['address', VICTIM_ADDRESS],
  ['address', ATTACKER_ADDRESS]
]]
```

is a perfectly valid definition under this validator: each branch has a signature, so `bHasSig` is satisfied.

When a paired device sends `new_shared_address` (handled by `handleNewSharedAddress`, `wallet_defined_by_addresses.js:378-415`), the code:
1. Confirms the definition hashes to the claimed address (`objectHash.getChash160`).
2. Confirms every signer entry maps 1:1 to a leaf `['address', ...]` node in the definition (`extractAddressPathsFromDefinition`, lines 396-405).
3. Calls `determineIfIncludesMeAndRewriteDeviceAddress` (lines 281-315), which only checks that *at least one* member address in the definition belongs to `my_addresses` or `shared_addresses` — not that this address sits on a mandatory (`and`/`r of set` with sufficient quorum) branch.
4. Calls `validateAddressDefinition` (lines 520-528), which itself carries the stale/incomplete TODO comment `// fix: 1. check that my address is referenced in the definition` and only re-runs the generic `Definition.validateDefinition` syntax check — it performs no semantic check that the local signature is required to spend.
5. On success, `addNewSharedAddress` persists the address into `shared_addresses` / `shared_address_signing_paths` (lines 239-268), and the wallet subsequently treats it as a jointly-controlled address (e.g. it is watched, funds may be routed to it, private-payment chains are forwarded to it via `forwardPrivateChainsToOtherMembersOfAddresses`).

This is the direct analog of the reported issue: just as `FixedStrikeOptionTeller` accepts `guardian_`/`authority_` without checking they can actually exercise admin control, ocore's shared-address acceptance path accepts a peer-controlled address "authority" structure without checking that the local party's authentifier is actually load-bearing for spending — an unvalidated "authority parameter" whose validity is purely syntactic, not semantic/functional.

### Impact Explanation
A malicious paired device (a counterparty in shared/multisig address setup, or an escrow/marketplace counterparty) can present what looks like a joint 2-of-2 (or N-of-M) address, get it silently accepted and recorded as a shared address, receive funds into it (e.g. via `sendToPeerAllSharedAddressesHavingUnspentOutputs`, private payment forwarding, or manual crediting by the victim who believes both parties must co-sign), and then unilaterally spend all funds using only their own key because the underlying definition is actually an `'or'` rather than the represented `'and'`/quorum condition. This results in concrete unauthorized spending / theft of funds that the victim believed were protected by joint control — matching the "unauthorized spending" impact bar.

### Likelihood Explanation
Reachable by any paired device without special privileges — simply by sending a `new_shared_address` network message with a crafted definition. No node operator, hub, or leaked-key access is required; it is a standard part of the shared-wallet/multisig-address creation flow (`createNewSharedAddress` / `handleNewSharedAddress`) that any correspondent device can initiate against a peer. The victim would need to visually inspect the raw definition (which the UI, if any, must render faithfully) to notice the `'or'` instead of `'and'`; the protocol/validation layer itself provides no defense.

### Recommendation
In `validateAddressDefinition` (and/or `determineIfIncludesMeAndRewriteDeviceAddress`), add a semantic check — analogous to validating `guardian_`/`authority_` are non-zero and functional — that evaluates the definition tree and confirms the local member address(es) sit on a path that is *necessary* (i.e., under `and`, or under `r of set`/`weighted and` with a quorum that cannot be met without it) rather than merely present under an `or` branch that can be bypassed. Reject or explicitly flag definitions where the local signature is optional for spending, and surface this clearly before persisting the address in `shared_addresses`.

### Proof of Concept
1. Attacker device pairs with victim device and proposes a shared address using:
```js
var arrDefinition = ['or', [
  ['address', VICTIM_ADDRESS],   // victim's real address, satisfies determineIfIncludesMeAndRewriteDeviceAddress
  ['address', ATTACKER_ADDRESS]
]];
var assocSignersByPath = {
  'r.0': { address: VICTIM_ADDRESS, device_address: VICTIM_DEVICE },
  'r.1': { address: ATTACKER_ADDRESS, device_address: ATTACKER_DEVICE }
};
```
2. Attacker calls `createNewSharedAddress(arrDefinition, assocSignersByPath, callbacks)` (or sends `new_shared_address` directly), which internally invokes `handleNewSharedAddress`.
3. `Definition.validateDefinition` accepts the definition (`or` with 2 branches, each has a signature).
4. `determineIfIncludesMeAndRewriteDeviceAddress` succeeds because `VICTIM_ADDRESS` is one of victim's `my_addresses`.
5. `validateAddressDefinition` re-validates syntactically and succeeds; `addNewSharedAddress` stores the address as a "shared" address on the victim's device, which the victim believes requires both signatures.
6. Attacker later signs alone using `ATTACKER_ADDRESS`'s key and spends all funds sent to the shared address — no victim signature required, despite the wallet's shared-address bookkeeping implying joint control. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });

						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
