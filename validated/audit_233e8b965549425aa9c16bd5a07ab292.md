### Title
Unchecked scaled-value overflow permanently freezes an active market - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` converts aggregate scaled debt and supply to RAY values with panicking `i128` multiplication before applying the borrow-index cap. Once `borrowed * borrow_index / RAY` exceeds `i128::MAX`, every accrual path panics, permanently freezing the market’s funds. [1](#0-0) [2](#0-1) 

### Finding Description
The liquidity pool stores aggregate supply and debt as RAY-scaled shares. During accrual, `accrue_step` calls `scaled_to_original` on `borrowed` and `supplied`; that helper performs half-up `i128` multiply-divide through `Ray::mul`. [3](#0-2) [2](#0-1) [4](#0-3) 

Although `mul_div_half_up` widens the intermediate product to `I256`, the final result must still fit in `i128`; otherwise it returns `None` and the wrapper panics with `MathOverflow`. [5](#0-4) [6](#0-5) 

The borrow-index cap is applied only when deriving `new_borrow_index`; it does not bound the already-existing `borrowed * borrow_index` value read at the start of the step, nor the `borrowed * new_borrow_index` value used to calculate rewards. [7](#0-6) [8](#0-7) 

Every pool market mutation first loads a synced market, and `synced_market` unconditionally calls `interest::global_sync`. [9](#0-8)  The explicit index updater does the same for each requested market. [10](#0-9)  Consequently, once the multiplication crosses the representable range, withdrawal, repayment, liquidation, borrowing, supply, revenue claim, recapitalization, and `update_indexes` all revert before performing their own logic.

### Impact Explanation
This is permanent freezing of user funds and protocol insolvency for the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot close unsafe positions, and `clean_bad_debt`/`recapitalize` paths still need accrual before they can normalize the book.

The repository’s long-horizon harness demonstrates the exact state transition: a one-billion-token, 18-decimal market at 98% utilization reaches `MathOverflow` inside `scaled_to_original`; the borrow index is still below `MAX_BORROW_INDEX_RAY`, and subsequent withdraw and repay calls fail with the same error. [11](#0-10) 

Because the panic occurs before `last_timestamp` is committed, the transaction rolls back the entire accrual. Retrying at a later timestamp starts from the same stored state and still calculates an unrepresentable debt value, so there is no unprivileged recovery path.

### Likelihood Explanation
An unprivileged address can construct the required state through ordinary controller calls when market caps, oracle valuation, and available capital permit the required size:

1. Supply the target asset to create pool liquidity through `Controller::supply`.
2. Supply sufficient collateral and borrow the target asset through `Controller::borrow`.
3. Leave the debt outstanding while sustained high utilization compounds the borrow index.
4. Call permissionless `Controller::update_indexes`; the overflow turns the crossing into a persistent market halt. [12](#0-11) [13](#0-12) 

The attack requires very large balances or an already-large market, enough collateral, and sustained utilization under a steep rate model. Those economic prerequisites limit likelihood, but no privileged role, oracle manipulation, leaked key, malformed contract call, or route dependency is required.

### Recommendation
Do not convert aggregate scaled balances with an unbounded panicking `i128` result during accrual.

A robust fix should either:

- perform aggregate value and interest calculations in a wider representation such as `I256`, with explicit protocol-defined behavior when an external token-unit conversion cannot represent the result; or
- enforce market-level scaled-share and accrued-value limits that guarantee `supplied * supply_index / RAY` and `borrowed * borrow_index / RAY` remain representable across the complete configured index range, including `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY`.

The bound must be checked before positions are minted, not only when caps are admitted at index `RAY`, because index growth changes the representable maximum. A regression test should place aggregate debt just below the overflow boundary, advance time across the boundary, and prove that `update_indexes`, `repay`, `withdraw`, and liquidation retain defined behavior rather than permanently panicking.

### Proof of Concept
Conceptual transaction sequence for a market `A` with 18 decimals and collateral market `C`:

```text
supply_account = controller.supply(
    caller = attacker,
    account_id = 0,
    spoke_id = S,
    assets = [(A, 1_000_000_000 * 10^18)]
)

borrow_account = controller.supply(
    caller = attacker,
    account_id = 0,
    spoke_id = S,
    assets = [(C, sufficient_collateral)]
)

controller.borrow(
    caller = attacker,
    account_id = borrow_account,
    borrows = [(A, 980_000_000 * 10^18)],
    to = attacker
)

// Wait while high utilization compounds the borrow index.
controller.update_indexes(
    caller = attacker,
    assets = [A]
)
```

For `A`, scaled borrowed value is approximately `9.8e35`. Once the stored or next borrow index is high enough that `borrowed * index / RAY > i128::MAX`, `update_indexes` panics with `MathOverflow`. Thereafter:

```text
controller.repay(caller = attacker, account_id = borrow_account, payments = [(A, 1)])
controller.withdraw(caller = attacker, account_id = supply_account, withdrawals = [(A, 0)], to = attacker)
controller.liquidate(...)
```

all enter the pool’s synced-market path and fail before repayment, withdrawal, or seizure logic executes. The repository test reproduces this sequence and observes `MathOverflow` for `update_indexes`, `withdraw`, and `repay` while the index remains below its configured cap. [14](#0-13)

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
