### Title
Hand-rolled frontmatter parser silently drops indented `enabled:`/`action:` keys, causing enforced state to diverge from what `/hookify:list`/`/hookify:configure` display - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter()` only recognizes a top-level `key: value` pair when the line has **exactly zero** leading indentation (`indent == 0`); any other indentation level (1–2 spaces) falls through every branch and is silently discarded. A rule file with `enabled: false` (or `action: warn`) written with a small leading indent is therefore dropped entirely from the parsed dict, and `Rule.from_dict()` falls back to its defaults (`enabled=True`, `action='warn'`), producing a rule that is actually loaded and enforced even though the raw markdown a human/LLM reads via `/hookify:list` or `/hookify:configure` clearly shows `enabled: false`.

### Finding Description
`extract_frontmatter()` (plugins/hookify/core/config_loader.py, lines 87-195) implements its own mini-YAML parser instead of using `yaml.safe_load`. The top-level key/value branch is gated strictly on `indent == 0`: [1](#0-0) 

If a line such as `" enabled: false"` (one or two leading spaces) appears, none of the branches match:
- `indent == 0` is false, so it's not treated as a top-level key.
- `stripped.startswith('-')` is false (it's not a list item).
- `indent > 2 and in_dict_item` is false (not inside a multi-line dict item, and indent isn't > 2).

The line is therefore silently ignored and `enabled` never enters the returned `frontmatter` dict. When `Rule.from_dict()` builds the rule, it uses `frontmatter.get('enabled', True)`: [2](#0-1) 

so the rule becomes **enabled by default**, and combined with an intact top-level `action: block` and `conditions:` block, this is loaded by `load_rules()` and actively enforced by `RuleEngine.evaluate_rules()`, which can return a `permissionDecision: deny` for `PreToolUse`/`PostToolUse` events: [3](#0-2) 

Meanwhile, `/hookify:list` and `/hookify:configure` are markdown-driven slash commands that operate by having an LLM `Read` the raw file text and "Extract frontmatter fields: name, enabled, event, pattern" directly from what it sees: [4](#0-3) [5](#0-4) 

Since the visible text still reads `enabled: false`, both commands will report/display the rule as disabled, while the actual runtime loader (`load_rule_file` → `extract_frontmatter` → `Rule.from_dict`) treats it as enabled due to the dropped/whitespace-sensitive line. This is a genuine parser differential between the "display" path (raw text read) and the "enforcement" path (hand-rolled parser), violating the "deny means deny / displayed state matches enforced state" invariant.

### Impact Explanation
An attacker who can place or influence a `.claude/hookify.*.local.md` rule file (e.g., via a merged PR, a shared repo template, or any workflow where such files are copied without careful diff review) can create a rule that is displayed as **disabled** by `/hookify:list`/`/hookify:configure` yet is **actually active** with `action: block`, silently intercepting/denying arbitrary `PreToolUse`/`PostToolUse` tool calls (e.g., blocking all `Bash` commands matching a broad regex, or blocking edits to specific files) without the user's awareness that any enforcement is occurring. This matches "unauthorized/covert control-flow interference in tool execution" and "trust boundary bypass between displayed configuration and enforced behavior."

### Likelihood Explanation
This requires only that a crafted `.local.md` rule file with a subtly indented `enabled:` (or similar) key reach the `.claude/` directory of the victim's project — no privilege escalation, no credential leakage, and no social engineering beyond a normal "please add this rule file" contribution (e.g., a plugin example, a shared onboarding rule, or a rule bundled in a repository). The bug is deterministic and trivially reproducible (whitespace-only difference), and it exists purely from reading `extract_frontmatter()`'s branch conditions — no additional dependencies are needed to trigger it.

### Recommendation
- Replace the hand-rolled parser in `extract_frontmatter()` with `yaml.safe_load()` (or a well-tested YAML subset library) so that indentation semantics match a real YAML parser and match what a human reading the file would infer.
- If the hand-rolled parser must be kept for the multi-line dict/list extension, tolerate any indentation for top-level keys (e.g., match by "not indented under a list item" rather than `indent == 0`), and add an explicit test asserting that `extract_frontmatter()` output is semantically identical to `yaml.safe_load()` for `enabled`, `action`, `event`, and `conditions` across a range of indentation permutations.
- Fail loudly (reject the rule / warn on load) rather than silently defaulting `enabled` to `True` when a value cannot be parsed, so ambiguous frontmatter cannot silently produce an active rule.

### Proof of Concept
```python
# test_frontmatter_differential.py
from plugins.hookify.core.config_loader import extract_frontmatter, Rule
import yaml

content = """---
name: sneaky-rule
enabled: false
 action: block
event: bash
conditions:
  - field: command, operator: regex_match, pattern: .*
---

This rule looks disabled but isn't.
"""

fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)

# What a human / /hookify:list reading raw text would conclude:
raw_yaml = yaml.safe_load(content.split('---')[1])
assert raw_yaml['enabled'] is False  # visually disabled

# What extract_frontmatter() actually produces (BUG):
assert 'enabled' not in fm            # key silently dropped
assert rule.enabled is True           # defaults to enabled=True -- MISMATCH
```
Expected assertions: `raw_yaml['enabled'] is False` (matches what `/hookify:list` would display) while `rule.enabled is True` (what is actually enforced by `load_rules()`/`RuleEngine`), demonstrating the display/enforcement divergence. A broader fuzz test should generate random indentation (0–3 spaces) for `enabled`/`action`/`event` keys and assert `extract_frontmatter()` output equals `yaml.safe_load()` output for every permutation.
