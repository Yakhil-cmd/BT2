### Title
Front-runnable proof-based AA rewards due to unbound cryptographic proof verification - (File: formula/evaluation.js)

### Summary
The oscript functions `vrf_verify`, `is_valid_sig`, and `is_valid_merkle_proof` verify a submitted proof/signature/merkle-proof against caller-supplied data, but nothing in their evaluation logic binds the proof to `trigger.address` or `trigger.unit`. An AA that pays a reward to whoever submits a valid proof (e.g., a VRF-based lottery, a puzzle/bounty AA, or a commit-reveal scheme) is vulnerable to exactly the front-running pattern described in the external report: the party who did the real work of producing the proof can have their reward stolen by anyone who observes the still-unstable trigger unit on the network and copies the same proof into their own unit before the original unit stabilizes.

### Finding Description
`vrf_verify`, `is_valid_sig`, and `is_valid_merkle_proof` are implemented purely as stateless verification primitives over evaluated arguments — they check only that a proof/signature is valid for a given seed/message/element, with no linkage to the identity of the unit's author [3](#0-2) . The grammar exposes these to any AA author as generic building blocks [4](#0-3) .

A bounty-style AA typically looks like: `if: "{vrf_verify(trigger.data.seed, trigger.data.proof, $pubkey)}"` followed by a payment to `trigger.address`. Because the check only validates the proof against the public key, and never checks anything unique to the sender (there is no equivalent of embedding `trigger.address` inside the signed/proved message unless the AA author explicitly does so), any unit carrying an identical `trigger.data.proof` will pass the same check regardless of who posted it.

Units are not private before stabilization: as soon as a unit is posted it is validated and forwarded/broadcast to all subscribed peers via `broadcastJoint`/`forwardJoint` [2](#0-1) [5](#0-4) , well before the unit becomes stable and its AA trigger is actually executed. AA triggers only fire after `stabilizeMci`/`markMcIndexStable` runs, in a deterministic order by `level, unit, address` [1](#0-0) . This creates a visible window during which an attacker who is watching the network can extract the `trigger.data` payload (the valid proof) from the honest party's pending unit, and post a new unit with the exact same proof and their own address as `trigger.address`, targeted at the same AA. Depending on unit ordering (level, DAG structure, or which unit's ancestor becomes final first), the attacker's copy can be processed first (or exclusively, if the AA logic is "first valid proof wins").

This directly mirrors the reported `finalizeBlocks` front-running bug: the verification step (`_verifyProof` / `vrf_verify`/`is_valid_sig`/`is_valid_merkle_proof`) accepts a "proof" that is not bound to the identity of the submitter who is supposed to be rewarded for producing it, so an unprivileged, non-working front-runner can appropriate the reward meant for whoever actually performed the underlying computation.

### Impact Explanation
Any AA that rewards the submitter of a valid proof for work (VRF-based fairness/lottery draws, puzzle bounties, oracle-style commit/reveal schemes, or any custom "first correct answer wins" AA) is exposed to reward theft by a front-runner who contributes no computation. This is a fund-loss/fund-theft vector for AA authors and their legitimate users: the honest party who does the real off-chain work (e.g., generating the VRF proof with a private key, finding the merkle-proven element, etc.) can have the entire payout diverted to an unrelated address, while their own transaction subsequently fails or receives nothing.

### Likelihood Explanation
Exploitability requires only running an ordinary (non-privileged) full node or light peer subscribed to the network, since pending units are broadcast to all subscribed peers before stabilization. No special access, witness/OP privilege, or protocol vulnerability is needed — only the ability to observe unstable units and quickly compose+broadcast a copy with substituted addressing before the original stabilizes. This makes the attack broadly reachable by any unprivileged network participant, though it only bites AA designs that expose a "first valid proof" reward pattern using `vrf_verify`/`is_valid_sig`/`is_valid_merkle_proof` without independently binding the proof to the claiming address.

### Recommendation
- Oscript AA authors using `vrf_verify`, `is_valid_sig`, or `is_valid_merkle_proof` for reward-granting logic should always include `trigger.address` (or another value unique to the legitimate submitter) as part of the signed/proved message itself, so a copied proof cannot be revalidated for a different address.
- Consider documenting this pattern prominently in the oscript/AA developer documentation, and potentially adding a built-in helper (or template) for "reward-for-proof" AAs that automatically binds the trigger address into the message being verified, to prevent AA authors from unknowingly introducing this class of bug.

### Proof of Concept
1. Author AA `X` with logic: `if: "{vrf_verify(trigger.data.seed, trigger.data.proof, $pubkey)}"` → pays `trigger.output[[asset=base]]*10` to `trigger.address`, intended as a reward for whoever is first to produce a valid VRF proof for the current round's seed (the seed being derivable off-chain, e.g. from a previous data feed value).
2. Legitimate solver Alice computes a valid VRF proof for the seed using the appropriate private key, and broadcasts a trigger unit `U_A` containing `{seed, proof}` in its `data` payload, with `trigger.address = Alice`.
3. `U_A` is validated and forwarded to all subscribed peers by `broadcastJoint`/`forwardJoint` before it stabilizes [6](#0-5) .
4. Attacker Bob, watching the network, receives `U_A`, extracts the identical `{seed, proof}` data, and immediately composes and broadcasts his own unit `U_B` sending the same payment to AA `X` with the same `trigger.data`, but `trigger.address = Bob`.
5. If `U_B`'s ancestor becomes final-good and is ordered before/instead of `U_A` (e.g., due to DAG parent selection, level, or Alice's unit being orphaned/losing the race for stabilization), the AA in `handleAATriggers` executes Bob's trigger with the same valid `vrf_verify` result and pays the reward to Bob, while Alice's identical transaction is not rewarded despite having done the actual proof-generation work.
