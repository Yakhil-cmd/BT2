## Title
Reentrancy in `pox-5.clar#register-for-bond` via attacker-controlled `signer-manager` trait callback lets a staker double up bond/stake commitments before state is written, inflating signer weight and reward shares beyond actually-locked STX — (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond` in `pox-5.clar` accepts a caller-supplied `signer-manager <signer-manager-trait>` argument and performs a dynamic `contract-call?` into it (`signer-manager-validate-stake`) *before* the overlap/duplicate-membership check is evaluated and long before any state (`protocol-bond-memberships`, `protocol-bonds-total-staked`, per-cycle share maps) is written. Because the "already staked" snapshot (`existing-membership`, `existing-stake`, `old-sbtc`) is captured in the function's initial `let` before this external call, a staker who supplies a malicious `signer-manager` contract can re-enter `register-for-bond` (or `stake`) from inside the callback and register a second, overlapping bond/stake using the same stale, pre-mutation view of state.

### Finding Description [1](#0-0) 

The `signer-manager` parameter is a dynamic-dispatch trait reference supplied directly by `tx-sender`, so it can point to any contract the caller deploys and controls.

Inside the function body, the external call happens here: [2](#0-1) 

Note that `signer-manager-validate-stake` (a `contract-call?` into the attacker-supplied contract) executes **before** the `bond-overlaps-new-position?` assertion at line 767-770, and long before the effects: [3](#0-2) 

`settle-rewards`, `roll-sbtc`, `map-set protocol-bond-memberships`, `map-set protocol-bonds-total-staked`, `add-staker-to-bond-cycles`, and `add-staker-to-signer-cycles` are all performed only *after* the external call returns. Since `existing-membership`, `existing-stake`, and `old-sbtc` were computed once at function entry (lines 679-691), a reentrant inner call sees exactly the same "no existing membership / no existing stake" snapshot as the outer call. Both the inner and outer invocation's overlap/duplicate checks therefore pass, and both proceed to commit their own `add-staker-to-bond-cycles` / `add-staker-to-signer-cycles` writes for two different (non-overlap-checked) bonds or a bond+stake combination, in the same transaction, for the same principal.

This is the same checks-effects-interactions violation described in the external report (state reset/checks performed too late relative to the external call), mapped onto this repo's PoX-5 signer-manager callback instead of Solidity's `kernel.executeAction`.

Critically, the STX lock itself is not applied by Clarity code — it is applied once, node-side, keyed off the parsed response of the (outermost) special-cased contract call: [4](#0-3) 

Only one `pox_lock_update_v5`/lock application occurs per top-level special-cased call, but the Clarity-level bookkeeping structures that back signer weight and reward-share accounting (`add-staker-to-bond-cycles`, `add-staker-to-signer-cycles`, `protocol-bonds-total-staked`) can be incremented twice — once by the inner reentrant call and once by the outer call — for the same underlying STX collateral, because both calls compute their additions from the same pre-mutation base values.

### Impact Explanation
This breaks the equality "signing weight / reward-cycle shares == actually locked STX (and custodied sBTC)". A staker can obtain reward-cycle participation/signer weight in two bond or stake positions simultaneously while the enforced STX lock reflects only one position's amount, i.e. "signing weight or reward slots exceeding locked value" — explicitly listed as a **High** impact in scope.

### Likelihood Explanation
The staker fully controls the `signer-manager` argument (it is validated only by `verify-signer-key-grant`/`contract-of`, not restricted to a fixed principal), so deploying a malicious `validate-stake!` implementation that re-enters `register-for-bond`/`stake` is straightforward and requires no privileged role — only an ordinary account willing to stand up its own signer-manager contract.

### Recommendation
Move all state-reading `let` bindings that gate duplicate/overlap checks (`existing-membership`, `existing-stake`, membership/overlap asserts) to be re-validated immediately before the state-mutating effects, or move the `signer-manager-validate-stake` / `verify-signer-key-grant` external call to occur strictly after all checks and effects are finalized (checks-effects-interactions ordering), or add an explicit reentrancy guard (e.g., a `staking-in-progress` flag per `tx-sender`) that is set before the external call and checked/cleared at the very start/end of `register-for-bond` and `stake`.

### Proof of Concept
1. Attacker deploys `evil-signer-manager` implementing `signer-manager-trait`, whose `validate-stake!` callback calls back into `.pox-5 register-for-bond` (or `.pox-5 stake`) for a second bond index/position, passing the same `tx-sender` context.
2. Attacker calls `register-for-bond bond-index=A signer-manager=evil-signer-manager amount-ustx=X btc-lockup=... signer-calldata=...`.
3. Execution reaches `signer-manager-validate-stake` (pox-5.clar line ~754) — at this point `existing-membership`/`existing-stake` for the attacker are still `none` in the map, and no `bond-overlaps-new-position?` check has run yet.
4. Inside the callback, `evil-signer-manager` re-enters `.pox-5 register-for-bond bond-index=B ...` (non-overlapping per the *stale* check). This inner call also reads `existing-membership = none`, passes its own overlap check, and commits `map-set protocol-bond-memberships`, `add-staker-to-bond-cycles`, `add-staker-to-signer-cycles` for bond B.
5. Control returns to the outer call for bond A, which — using its own already-captured `existing-membership = none` snapshot — also passes its overlap check and commits its own membership/share writes for bond A.
6. Result: the attacker now holds active reward-cycle shares/signer weight in both bond A and bond B for the same transaction, while the node's single STX-lock application (`pox_lock_update_v5` in `pox-locking/src/pox_5.rs`) only reflects one locked amount/unlock height — signing weight and reward eligibility exceed the STX actually locked for the account.

/// Handle responses from `stake-update` in pox-5 -- the function that
/// *extends or increases already-locked* STX.
fn handle_stake_lockup_update_pox_v5(
    global_context: &mut GlobalContext,
    function_name: &str,
    value: &Value,
) -> Result<Option<StacksTransactionEvent>, VmExecutionError> {
    debug!(
        "Handle special-case contract-call to {:?} {function_name} (which returned {value:?})",
        boot_code_id(POX_5_NAME, global_context.mainnet),
    );

    runtime_cost(
        ClarityCostFunction::StxTransfer,
        &mut global_context.cost_track,
        1,
    )?;

    let parsed = parse_pox_stake_result(value).map_err(|e| {
        locking_error_to_vm_error(e, &format!("pox-5 {function_name}: bad response"))
    })?;
    let (staker, amount_ustx, unlock_height) = match parsed {
        ParsedStakeResult::Ok {
            staker,
            amount_ustx,
            unlock_burn_height,
        } => (staker, amount_ustx, unlock_burn_height),
        ParsedStakeResult::ContractErr => return Ok(None),
    };

    match pox_lock_update_v5(
        &mut global_context.database,
        &staker,
        unlock_height,
        amount_ustx,
    ) {
        Ok(_) => {
            // Log the extension in the asset map.
            global_context.log_stacking(&staker, amount_ustx)?;

            let event =
                StacksTransactionEvent::STXEvent(STXEventType::STXLockEvent(STXLockEventData {
                    locked_amount: amount_ustx,
                    unlock_height,
                    locked_address: staker,
                    contract_identifier: boot_code_id(POX_5_NAME, global_context.mainnet),
                }));
            Ok(Some(event))
        }
        Err(e) => Err(locking_error_to_vm_error(
            e,
            &format!(
                "pox-5 {function_name}: failed to extend lock from {staker} until {unlock_height}"
            ),
        )),
    }
}
