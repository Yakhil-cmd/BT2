### Title
`StatusHandler` binds a forged commit status to any repository's commit by SHA alone, decoupling the authenticating organization from the repository written - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit's webhook signature verification selects the signing organization/secret from the payload's `repository.owner.login` field, but `StatusHandler#process` never checks that field (or `repository.full_name`) when applying the status - it matches purely on the globally-unique-but-not-repository-scoped `sha`. This breaks the intended binding "organization that authenticated == repository being written."

### Finding Description
`WebhooksController#verify_signature` picks the HMAC secret to validate against using `repository_owner`, derived from the payload itself: [1](#0-0) [2](#0-1) 

This only proves the payload was signed by *some* organization's `webhook_secret` matching `repository.owner.login`; it says nothing about which repository/commit the payload is allowed to affect.

`Shipit::Webhooks::Handlers::Handler` normally re-derives the target repository from `payload.dig('repository', 'full_name')` for scoping (`stacks`), and every other handler (push, pull_request, membership, check_suite) filters through `Repository.from_github_repo_name(params.repository.full_name)`: [3](#0-2) 

`StatusHandler`, however, ignores the `repository` field entirely and looks up commits **instance-wide** by `sha`: [4](#0-3) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`Commit.where(sha: ...)` is not scoped by `stack_id`/`repository_id`. Any `Commit` record in the whole Shipit database sharing that SHA (e.g. a fork of the victim repository that shares ancestor commits, or any onboarded repository whose git history happens to contain the same commit object) receives the forged status. Since git commit SHAs are content-addressed and shared across forks/clones of the same history, an attacker who administers a *different*, independently-onboarded GitHub organization/repository on the same multi-tenant Shipit instance can legitimately sign a `status` webhook with their own `webhook_secret` (passing `verify_signature`, because it's checked against their own org) that references a SHA which also exists as a tracked commit in a victim stack belonging to a different organization.

`create_status_from_github!` → `add_status` creates a `Status` record on the victim's `Commit`, which fires `schedule_continuous_delivery`: [5](#0-4) [6](#0-5) 

If the victim stack has `continuous_deployment` enabled and this forged status is the last required check to turn the commit "green," this can trigger an unauthorized deploy via the continuous-delivery pipeline, and independently corrupts the victim's CI/status history used to gate manual deploys.

### Impact Explanation
This breaks the equality "organization whose signature authenticated the webhook == repository/stack whose commit status is mutated." The concrete consequence is an unauthorized deploy trigger (via continuous deployment) or corruption of the required-status gate that humans/CI rely on before deploying — matching the Critical impact category "unauthorized deploy" without requiring any Shipit session, `ApiClient` token, or the victim's `webhook_secret`.

### Likelihood Explanation
Requires only that the attacker control (as an ordinary GitHub org admin, not privileged within Shipit) a second organization/repository onboarded to the same shared Shipit instance, and that a shared commit SHA exists between the attacker's repo and the victim's tracked branch (trivially satisfied for a fork of the victim project, a common, unprivileged relationship). No compromise of GITHUB_TOKEN, other orgs' webhook secrets, or Shipit accounts is needed.

### Recommendation
Scope `StatusHandler#process` to the repository identified in the same payload, mirroring the base `Handler#stacks`/`repository_name` pattern, e.g. filter `Commit.joins(:stack => :repository).where(sha: params.sha, repositories: { id: repository.id })` where `repository = Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, and reject/ignore the event if no repository is provided or it does not match `repository_owner` used for signature verification.

### Proof of Concept
1. Attacker owns/administers GitHub org `attacker-org`, which is independently onboarded to the shared Shipit instance with its own `webhook_secret`.
2. Attacker forks victim's repository `victim-org/app` into `attacker-org/app` (or otherwise ensures a shared ancestor commit SHA `abc123` exists in both, which Shipit already tracks for `victim-org/app`).
3. Attacker uses the GitHub Status API (write access to their own fork is sufficient) to create a `status` event on `attacker-org/app` for commit `abc123` with `state: "success"`, `context: "<victim's required context>"`.
4. GitHub signs and delivers this webhook using `attacker-org`'s `webhook_secret`; `WebhooksController#verify_signature` validates it successfully because `repository.owner.login == "attacker-org"` matches the secret used.
5. `StatusHandler#process` executes `Commit.where(sha: "abc123")`, which also returns the `victim-org/app` commit tracked by Shipit, and calls `create_status_from_github!` on it — injecting the forged "success" status into the victim's stack and potentially triggering `schedule_continuous_delivery`/an unauthorized deploy.
