### Title
Membership webhook allows cross-organization team hijack via `github_id` collision - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` only proves that the request body was signed by the `webhook_secret` belonging to the organization named in `params.dig('organization','login')` (or `repository.owner.login`), not that this organization owns the `team.id` referenced in the payload. `MembershipHandler#find_or_create_team!` then looks up (or lazily creates) a `Shipit::Team` solely by `github_id`, and `MembershipHandler#process` unconditionally calls `team.add_member(member)` on whatever `Team` row is returned — even one that was originally created for a different organization.

### Finding Description
The broken binding is: the organization whose secret authenticated the webhook bytes must equal the organization that owns the `Team` being mutated —
`Shipit.github(organization: repository_owner).webhook_secret` (verified against `attacker-org`) should equal `team.organization` (`shopify`), but it does not.

Code path:
- `verify_signature` derives `repository_owner` purely from the payload (`params.dig('organization', 'login')`) [1](#0-0)  and verifies the HMAC using that organization's own configured `webhook_secret` [2](#0-1) . In a multi-org configuration each org has its own independent `webhook_secret` [3](#0-2) , so a request signed with `attacker-org`'s own secret and `organization.login = "attacker-org"` passes verification legitimately.
- `#create` then dispatches the parsed body to `MembershipHandler#process`, which calls `find_or_create_team!` [4](#0-3) .
- `find_or_create_team!` performs `Team.find_or_create_by!(github_id: params.team.id) do |team| team.organization = params.organization.login end` [5](#0-4) . The `do...end` block only runs when a **new** record is built; if a `Team` row with that `github_id` already exists (e.g., previously synced for `shopify-developers`), the block is skipped and the pre-existing record — with `organization = "shopify"` — is returned untouched.
- `process` then calls `team.add_member(member)` [6](#0-5) , adding the attacker-controlled `User` to the `shopify-developers` team, regardless of the fact that the request was authenticated only for `attacker-org`.

No code anywhere checks `team.organization == params.organization.login` before mutating membership. `verify_signature`'s `Shipit.github(organization: repository_owner)` call only proves the requester controls **an** org's secret, not that it controls the org tied to the `Team` row being written.

### Impact Explanation
A party that legitimately owns/configures one GitHub organization on a multi-tenant Shipit instance can add an arbitrary GitHub login as a `Shipit::Membership` of a `Team` belonging to a **different** tenant organization, by replaying a `github_id` that collides with an already-synced team. Since `Shipit.github_teams` and other authorization code paths consume `Team`/`Membership` data for access decisions, this is a cross-tenant authorization escalation: an attacker's chosen GitHub handle becomes a member of another org's team without that org's webhook secret ever being used to authenticate the request. This matches "escalation into `Shipit.github_teams` authorization" (High) for a single-secret deployment, and edges toward Critical impact in a genuinely multi-org deployment because it is a payload authenticated for one organization mutating another organization's team/membership state.

### Likelihood Explanation
The finding requires: (1) Shipit configured for **multiple** GitHub organizations, each with its own `webhook_secret` (the multi-org config schema is a supported, documented mode) [3](#0-2) ; (2) the attacker controls one of those configured organizations (a legitimate tenant of this Shipit instance) and can therefore emit correctly-signed `membership` webhooks; and (3) the attacker knows/guesses a `github_id` matching an already-synced `Team` belonging to another tenant. GitHub team IDs are opaque integers, not secret but not trivially enumerable either, which lowers but does not eliminate feasibility. Given those preconditions, exploitation is a single crafted HTTP POST and is fully repeatable.

### Recommendation
In `find_or_create_team!`, verify that the payload's `organization.login` matches the existing `Team#organization` before permitting `add_member`/`delete` on it, e.g. raise/reject (or scope the `find_or_create_by!` on both `github_id` and `organization`) when `team.organization != params.organization.login`, rather than only setting `organization` in the create-block.

### Proof of Concept
Minitest sketch (`test/controllers/webhooks_controller_test.rb`):
```ruby
test ":membership from a different org cannot write to a pre-existing team of another org" do
  shopify_team = shipit_teams(:shopify_developers) # github_id already set, organization: "shopify"

  # Configure a second org "attacker-org" with its own webhook_secret in test secrets.
  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = attacker_org_signature(body)

  body = membership_params.merge(
    organization: { login: 'attacker-org' },
    team: { id: shopify_team.github_id, name: shopify_team.name, slug: shopify_team.slug, url: shopify_team.api_url },
    member: { login: 'attacker-handle' },
    action: 'added'
  ).to_json

  assert_no_difference -> { shopify_team.members.count } do
    post :create, body:, as: :json
  end
end
```
Assert `shopify_team.organization == "shopify"` (unchanged) while `params.dig('organization','login') == "attacker-org"` was the value that authenticated the request — i.e., the two sides of the required equality diverge, and today's code allows the write to proceed despite that divergence.
