### Title
`status` webhook resolves target `Commit`s by bare SHA with no repository/organization scoping, letting one repo's webhook flip `release/gate` status on another repo's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes a `Status` for every `Commit` row whose `sha` matches the webhook payload, without filtering by the repository that authenticated the webhook. Every other webhook handler in this codebase (`PullRequest::*Handler`) scopes its side effects through `Handler#stacks`, which is derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, but `StatusHandler` does not use this helper at all.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`payload['repository']['full_name'] == commit.stack.repository.full_name` for every `Commit` mutated by the `status` event.

Trace:
1. `Shipit::WebhooksController#create` parses the raw body and dispatches to `Shipit::Webhooks.for_event('status')`, i.e. `Handlers::StatusHandler`, with no repository binding attached to the handler call itself: [1](#0-0) .
2. `verify_signature` only checks that the payload's `repository.owner.login` (or `organization.login`) matches a GitHub App/organization known to Shipit and that the signature was produced with that organization's shared secret; it does not tie the signature to a specific repository within that organization: [2](#0-1) . Any repository under an organization where Shipit's app/webhook secret is installed can forge a fully valid signature for a `status` event.
3. `Handler` base class exposes a `stacks` helper that scopes work to `Repository.from_github_repo_name(repository_name)` where `repository_name` comes from `payload.dig('repository', 'full_name')`: [3](#0-2) . Handlers such as `PullRequest::ClosedHandler`, `LabeledHandler`, `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler` all route through this `stacks` scoping.
4. `StatusHandler#process`, however, ignores `stacks`/`repository_name` entirely and does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`: [4](#0-3) . `sha` is indexed only as `(sha, stack_id)`, not unique per `sha` alone: [5](#0-4) , so the same SHA value can legitimately exist under multiple stacks/repositories (e.g. identical commit content pushed to two repos, or a review-stack-provisioned PR head SHA that also exists in the base stack's history).
5. `create_status_from_github!` → `add_status` writes a `Status` row, recomputes `commit.status`, and on a `simple_state` transition schedules `stack.schedule_merges` and fires `deployable_status`/`commit_status` hooks: [6](#0-5) . `Status#required?` checks `commit.required_statuses.include?(context)` — so a forged `context: 'release/gate', state: 'success'` payload can satisfy the exact required-context check used to gate deploy/merge decisions: [7](#0-6) .

Attacker's exact request: an unauthenticated `POST /webhooks` with `X-Github-Event: status`, a valid signature computed against a repository the attacker legitimately controls (e.g. their own repo under an org that has Shipit's app installed), and a JSON body `{"sha": "<sha shared with victim commit>", "state": "success", "context": "release/gate", "repository": {"full_name": "attacker/own-repo", "owner": {"login": "<org>"}}}`. Because `StatusHandler` never re-derives or checks `params.dig('repository', ...)` against the `Commit`'s actual stack/repository, the write lands on any `Commit` row anywhere in the database sharing that SHA — including one belonging to a victim's `review_stacks_enabled: true, allow_all: true` stack, which auto-provisions review stacks for external PRs that execute `shipit.yml`.

None of the existing guards intercept this: `verify_signature` authenticates the organization, not the specific repository/stack; `ExplicitParameters` schema in `StatusHandler.params` only validates types (`sha`, `state`, `context`, etc.), not repository ownership; there is no `require_permission!`/`stacks` scoping call in `StatusHandler#process` unlike its siblings.

### Impact Explanation
A `status` webhook forged for one repository can flip the CI/gate status recorded against a `Commit` belonging to a completely different repository/stack, as long as the SHA values collide. Because `add_status` schedules `stack.schedule_merges` and fires `deployable_status` on a `success` transition, this can force a merge/deploy decision (or block one, using `failure`/`error`) for a stack the attacker never authenticated against — this is a payload for one repository mutating another's stack/commit, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The blast radius spans every stack across every organization configured in the same Shipit instance whose commit history can be made to share a SHA with an attacker-controlled repo (trivial via forks, cherry-picks, or identical tree/commit metadata). It is repeatable per SHA/context pair and requires no privileged Shipit role.

### Likelihood Explanation
Preconditions: (1) attacker needs to control at least one repository that shares a GitHub organization/app installation trusted by the target Shipit instance (to produce a validly signed webhook), or the ability to trigger a genuine GitHub `status` event from such a repo; (2) a target stack must have `review_stacks_enabled: true` with `allow_all`, and a commit/PR SHA that also appears (or can be engineered to appear, e.g. via a fork with identical commit) in the attacker's own repository's history; (3) the target context (`release/gate`) must be one of the stack's `required_statuses`. Given GitHub's willingness to let any user fork or create repos under many orgs, and that SHA collisions across repos with identical commit content are straightforward to engineer, likelihood is moderate-to-high for organizations with review-stack auto-provisioning enabled.

### Recommendation
Scope `StatusHandler#process` the same way the `PullRequest::*Handler`s do: resolve `stacks` (or at minimum the specific `Repository`) from `payload.dig('repository', 'full_name')` and only update `Commit`s that belong to that repository's stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook does not affect commits belonging to a different repository" do
  attacker_repo_full_name = 'attacker/unrelated-repo'
  victim_stack = shipit_stacks(:shipit) # review_stacks_enabled: true, allow_all
  victim_commit = shipit_commits(:first)
  shared_sha = victim_commit.sha

  # Sanity: no commit exists yet under the attacker's own repository/stack with this sha
  refute Repository.from_github_repo_name(attacker_repo_full_name)&.stacks&.flat_map(&:commits)&.any? { |c| c.sha == shared_sha }

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'release/gate',
    'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Currently this assertion fails: `StatusHandler.call` writes a `Status` on `victim_commit` (via `Commit.where(sha: shared_sha)`) even though `payload['repository']['full_name']` is `attacker/unrelated-repo`, proving the repository binding is not enforced.
