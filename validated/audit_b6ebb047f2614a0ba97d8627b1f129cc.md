## Analysis Result

### Title
Stack-scoped API tokens can create Stacks for arbitrary repositories, bypassing their `stack_id` authorization scope - (File: `app/controllers/shipit/api/stacks_controller.rb`)

### Summary
`ApiClient` records can be scoped to a single `Stack` via `belongs_to :stack, optional: true` [1](#0-0) , and `Api::BaseController#stacks` is meant to enforce that scope for every stack-touching action: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) . `Api::StacksController#show`, `#update`, `#destroy`, and `#refresh` all resolve their target stack through this scoped `stacks` relation via the private `stack` method [3](#0-2) . However, `#create` never consults this scope at all — it builds a brand-new `Stack` directly and attaches an arbitrary `Repository` found/created from client-supplied `repo_owner`/`repo_name` params [4](#0-3) [5](#0-4) .

### Finding Description
The binding that should hold is: **stack a token authorizes == stack a token touches**. For `create`, only the coarse-grained permission `write:stack` is checked via `require_permission :write, :stack, only: %i[create update destroy]` [6](#0-5)  and `ApiClient#check_permissions!` [7](#0-6) ; there is no check that the repository/stack being created corresponds to `current_api_client.stack_id`. Because `repository` is resolved via `Repository.find_or_create_by(owner: repo_owner, name: repo_name)` [5](#0-4)  using fully attacker-controlled params, and the new `Stack` is never filtered through `stacks`/`stack_id`, a token that was explicitly scoped to a single stack (e.g. the `here_come_the_walrus` fixture with `stack: shipit`) [8](#0-7)  and that also carries `write:stack` can create Stacks for any other repository in the instance.

This exactly matches the report's analog class: an authorization scope (`stack_id`) that the deployment-trust model claims restricts a token, versus the actual object the endpoint acts on (an unrelated repository/stack), left unchecked because only the coarse permission bit was validated — analogous to `mirrorConnector`/`fxRootTunnel` binding being skippable and then claimable through an under-guarded setter.

### Impact Explanation
Creating a `Stack` wires up a `Repository`, branch, deploy URL, and CI/merge-queue settings for that repository under Shipit's control. An attacker holding a legitimately-issued, narrowly-scoped API token (one intended to only manage its own stack) can leverage the `write:stack` permission to provision Shipit management, and subsequently deploy/rollback/merge tooling, over a repository they were never meant to have any access to. This is a cross-repository write and can lead to unauthorized deploys against repositories outside the token's intended authorization boundary.

### Likelihood Explanation
Exploitation requires only an existing stack-scoped `ApiClient` token that also has the `write:stack` permission — a normal, documented configuration for tokens meant to manage their own stack's lifecycle (see `create`/`update`/`destroy` all gated by the same permission at [6](#0-5) ). No additional privilege escalation, session, or GitHub credentials are needed beyond the token itself, and the request is a single `POST` to the `create` action.

### Recommendation
In `Api::StacksController#create`, reject the request (or ignore `repo_owner`/`repo_name`) when `current_api_client.stack_id?` is true and the resolved repository does not match `current_api_client.stack.repository`. More generally, `create` should route through the same `stacks`-scoped authorization used by `show`/`update`/`destroy`/`refresh` rather than instantiating an unrestricted `Stack.new`.

### Proof of Concept
1. As an owner, create an `ApiClient` scoped to `stack: shipit-engine/shopify` with permissions `['write:stack']` (or reuse a fixture like `here_come_the_walrus` with `write:stack` added) [8](#0-7) .
2. Using that token's Basic-Auth credentials, call:
   `POST /api_clients_or_stacks_root/stacks` with `repo_owner=some-other-org`, `repo_name=some-other-repo`, `environment=production`, `branch=main`.
3. `Api::StacksController#create` [4](#0-3)  succeeds and creates a new `Stack` for `some-other-org/some-other-repo`, even though the token's `stack_id` is bound to a completely different stack — demonstrating the token touched a stack/repository outside what it was authorized for.
