### Title
Global unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets any authenticated GitHub organization/repo forge status updates on another stack's commits, bypassing `blocking_statuses` CI gates - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by SHA across the entire `commits` table, with no filter on `stack_id` or the webhook's `repository.full_name`, unlike every other handler (e.g. `PushHandler`) which scopes to `stacks` derived from the payload's own repository. Because git commit SHAs are content-addressed and not globally unique to one GitHub repository (forks, cherry-picks, or manually reconstructed objects can reproduce an identical SHA), a webhook that is cryptographically valid for repository B can create/update a `Status` row on a `Commit` that actually belongs to repository A's stack, silently altering that commit's `blocking?`/`blocked?` evaluation.

### Finding Description
The broken binding, stated explicitly: the question's audit assumes
`repository authenticated by webhook_secret/verify_webhook_signature == repository whose blocking_statuses policy the status satisfies`.
In this code this equality is never enforced.

- `WebhooksController#verify_signature` authenticates the payload only against `Shipit.github(organization: repository_owner)` using the payload's own `repository.owner.login` [1](#0-0) . This proves the request came from GitHub for *that* organization/app installation, not that the SHA inside the payload "belongs" to that repository.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query has **no `stack_id`/repository filter at all** — it matches every `Commit` row in the database sharing that SHA, regardless of which stack/repository it belongs to.
- Contrast with `PushHandler#process`, which correctly scopes via `stacks` (derived from `Repository.from_github_repo_name(repository_name)`) before acting [3](#0-2) [4](#0-3) . `StatusHandler` never calls `stacks` or checks `repository_name`, so the "WEBHOOK PROVENANCE" invariant other handlers implicitly maintain is absent here.
- The resulting `Status` is used by `Status::Common#blocking?`, which checks `commit.blocking_statuses.include?(context)` (i.e. stack A's own config) against the state written by the forged webhook [5](#0-4) , and `Commit#blocked?` re-scans `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)` [6](#0-5) , so any later `deployable?` check on stack A picks up the poisoned status [7](#0-6) .

Exploit flow: attacker owns repository B (any repo they can push to/fork, with a valid GitHub App/webhook secret for their own org — which is not a Shipit secret, it's GitHub's own signing for that org's installation). They construct a commit in B whose SHA collides with a specific commit already present in stack A's `commits` table (trivial via fork-and-preserve-history, or reconstructing an identical git object graph — no SHA-1 collision attack needed, just identical content). They then trigger (or directly POST, since GitHub relays exactly what's sent) a `status` event for that SHA with `context: 'security/scan', state: 'success'` from repo B. `verify_signature` succeeds because it's a legitimately signed webhook for org/repo B. `StatusHandler#process` finds stack A's `Commit` row (same SHA) and writes the "success" status onto it. Stack A's blocking gate is now bypassed for every commit ordered after that SHA and before the actually-approved commit.

Existing guards do not catch this: `verify_signature` only proves organization identity of the sender, not SHA-to-repository ownership; `ExplicitParameters` schema only validates types of `sha`/`state`/`context`, not their relation to a specific stack; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
This is a **payload for one repository mutating another's commit/stack state** — an authentication-bypass-class issue per the rules' Critical category. Concretely: an attacker who controls only their own GitHub repo/organization can write a `Shipit::Status` record on a commit belonging to a victim stack they have no relationship with, flipping `blocking?`/`blocked?`/`deployable?` for that victim stack and causing an unauthorized deploy to proceed past a CI/security gate the victim's operators explicitly configured (`ci.blocking` in `shipit.yml`) [8](#0-7) . This is repeatable against any stack in the installation whose tracked commit SHAs the attacker can reproduce (most feasible via forks sharing commit history with the victim's upstream repo).

### Likelihood Explanation
Preconditions: attacker needs (1) a GitHub repository/org they legitimately control so their webhook signature verifies, (2) the ability to make Shipit's `/webhooks` endpoint receive a `status` event referencing that SHA (via GitHub's normal webhook delivery from their own repo, or by directly POSTing a validly-signed payload if they can compute/replay a valid HMAC for their own app installation), and (3) a commit in victim stack A whose SHA the attacker can reproduce in repo B — trivially achievable by forking any repo whose history the victim tracks (shared history ⇒ identical SHAs) or by crafting an equivalent git object graph. No Shipit secrets, sessions, or GitHub org membership on the victim side are required. Cost is low and the attack is repeatable for every SHA the attacker wants to poison.

### Recommendation
Scope `StatusHandler#process` (and `CheckSuiteHandler`/any other handler operating on shared identifiers) to only the commits belonging to stacks whose repository matches the payload's `repository.full_name`, mirroring `PushHandler`'s use of the `stacks` helper, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces that a status can only affect commits that actually belong to a stack tracking the authenticated repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook from a colliding-SHA foreign repository does not unblock a victim stack" do
  stack_a = shipit_stacks(:shipit) # victim stack A
  stack_a.update!(cached_deploy_spec: DeploySpec.new('ci' => { 'blocking' => ['security/scan'] }))

  colliding_sha = 'deadbeef' * 5
  blocking_commit = stack_a.commits.create!(sha: colliding_sha, message: 'unapproved change', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  target_commit = stack_a.commits.create!(sha: 'cafebabe' * 5, message: 'later commit', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  assert_predicate target_commit, :blocked? # binding LHS: blocked? is true before forged webhook

  # payload signed for attacker-controlled repository B, unrelated to stack A
  forged_payload = ExplicitParameters::Parameters.new(
    sha: colliding_sha, state: 'success', context: 'security/scan',
    repository: { full_name: 'attacker/repo-b' }
  )
  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  target_commit.reload
  refute_predicate target_commit, :blocked? # binding RHS: flipped to false by repo B's webhook
end
```
This demonstrates the equality `repository authenticated for webhook == repository whose blocking_statuses gate the SHA` does not hold, and that `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup is the root cause.
