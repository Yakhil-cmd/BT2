### Title
Cross-AA Signature Replay via `is_valid_signed_package`/`is_valid_sig` Missing Mandatory Address Binding - (File: formula/evaluation.js, test/samples/payment_channels.oscript)

### Summary
Autonomous Agents (AAs) built with the oscript primitives `is_valid_signed_package(signed_package, address)` and `is_valid_sig(message, pem_key, sig)` verify only that a signature is valid for a given address/pubkey, exactly as `StoryBadgeNFT.mint()` verified only `keccak256(msg.sender)`. Neither primitive forces the signed content to include the verifying AA's own identity (`this_address`). Any AA design that authorizes privileged actions (minting an asset, releasing escrowed funds) based on an off-chain-signed message from a shared signer, without explicitly embedding `this_address` in the signed payload, is vulnerable to having the exact same signature replayed against a different AA instance that trusts the same signer address.

### Finding Description
`is_valid_signed_package` is implemented in `formula/evaluation.js` (case `'is_valid_signed_package'`) and delegates to `signed_message.validateSignedMessage(conn, signedPackage, evaluated_address, mci, ...)`. That validation, in `signed_message.js:117-303`, checks that the package is signed by `evaluated_address` (the address argument supplied by the calling AA) and that the definition/authentifiers verify against `objectHash.getSignedPackageHashToSign(objSignedMessage)` [1](#0-0) [2](#0-1) 

Critically, `getSignedPackageHashToSign` only hashes the package's own fields (`signed_message`, `authors`, `last_ball_unit`, `version`) — it contains **no reference to which AA/contract instance is asking for verification**: [3](#0-2) 

The similar low-level primitive `is_valid_sig(message, pem_key, sig)` is even more permissive: it verifies an arbitrary message/signature/pubkey triple with zero notion of the calling contract's address at all [4](#0-3) 

Because of this, binding a signed message to "this specific AA instance" is entirely the responsibility of the AA author, who must manually embed `this_address` inside the `signed_message` payload and check it in the `if`/`init` logic. The ocore codebase's own reference sample demonstrates that this binding is a manual, easy-to-forget precaution rather than an enforced protocol guarantee: [5](#0-4) 
Here the AA explicitly checks `trigger.data.sentByPeer.signed_message.channel != this_address` **before** calling `is_valid_signed_package`, precisely because `is_valid_signed_package` on its own does not guarantee the message was intended for this AA. If an AA author omits this check — exactly as the Story team omitted the contract address from `StoryBadgeNFT`'s signature digest — a signature produced for AA-instance #1 (e.g., one badge/vault template deployment) validates identically for AA-instance #2 sharing the same off-chain signer, since `evaluated_address` (the signer) is identical and the signed content contains nothing instance-specific.

This class of AA is realistic and reachable by any unprivileged AA author or trigger sender: factory-style patterns are supported natively via the `'definition template'` op in `definition.js`, which lets one canonical template be parameterized and instantiated multiple times, mirroring the Beacon-Proxy factory pattern (`OrgStoryNFTFactory`) that originally caused the replay in the external report [6](#0-5) 

### Impact Explanation
An AA deployed from a shared template that grants privileged actions (minting a custom asset, releasing bonded/escrowed funds, authorizing a withdrawal) upon presentation of a signature from a designated off-chain signer — and that fails to embed `this_address` in the signed payload — allows any trigger sender holding one valid signature to replay it against every other AA instance trusting the same signer. This can cause unauthorized asset issuance or unauthorized release of AA-held funds across multiple AA instances, i.e., concrete fund loss / supply inflation as required by the validation criteria.

### Likelihood Explanation
Likelihood depends entirely on individual AA authorship: the primitives themselves function as documented low-level signature-verification tools (analogous to `ecrecover`), and the correct binding pattern (checking `this_address`/`channel` inside the signed message) is already demonstrated in the codebase's own sample AAs (`payment_channels.oscript`, `order_book_exchange.oscript`, which binds orders to `signed_message.address` and asset pair rather than to `this_address` because it is a single, non-factory-deployed AA). The risk materializes specifically for factory/template-deployed AAs (via `'definition template'`) that use a shared signer across multiple instances and forget the `this_address` check — the same human-error root cause documented in the external report. This is a design footgun rather than a universally-exploitable core-protocol bug, since ocore itself provides the tools to bind correctly and its own sample code shows the safe pattern; unaffected/careful AA templates are not vulnerable.

### Recommendation
- Document explicitly (and enforce via linting/best-practice guidance) that any AA design using `is_valid_signed_package` or `is_valid_sig` to gate privileged state changes MUST embed `this_address` (or an equivalent unique per-deployment identifier) inside the signed message and verify it, mirroring the pattern already used in `payment_channels.oscript`.
- Consider adding an optional mode to `is_valid_signed_package` that automatically requires/checks a `contract`/`aa_address` field inside `signed_message` matching `this_address`, removing reliance on manual developer discipline.
- Audit any officially distributed AA templates/factories that use a shared external signer across multiple deployed instances to confirm the signed payload is bound to the specific instance address.

### Proof of Concept
Conceptual PoC mirroring the external report, translated to oscript AA templates:
1. Deploy AA-instance-1 and AA-instance-2 from the same `'definition template'`, both trusting `signer_address` as the authorized off-chain signer, both exposing a case such as:
   ```
   if: `{ !is_valid_signed_package(trigger.data.auth, 'SIGNER_ADDRESS_HERE') }` → bounce
   messages: [ mint asset / release funds to trigger.address ]
   ```
   without checking `trigger.data.auth.signed_message.contract == this_address`.
2. Off-chain signer signs one package: `signed_message = { action: 'authorize', beneficiary: 'BOB_ADDRESS' }`, producing `objSignedPackage` per `signMessage()` in `signed_message.js`.
3. Bob submits `trigger.data.auth = objSignedPackage` to AA-instance-1 → `is_valid_signed_package` succeeds → Bob receives minted asset/funds.
4. Bob resubmits the identical `objSignedPackage` unchanged to AA-instance-2 → `is_valid_signed_package` again succeeds (nothing in the signed content differs), and Bob receives a second, unauthorized mint/fund release from a different AA instance using the same signer.

Note: I was unable to find an actual production AA/template distributed in this repository that reproduces steps 1–4 verbatim (the only factory-style primitive found is the generic `'definition template'` op); the PoC is constructed from the documented primitives and the codebase's own sample AA that demonstrates the necessary (and otherwise optional) mitigation. Confirming whether any specific shipped AA template in this repo is actually missing the `this_address` check would require further review of official production `.oscript`/`.ojson` templates beyond what indexing surfaced.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)

	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
