### Title
Arbitrary `machine.environment` keys from a fork's `shipit.yml` reach `PTY.spawn` unsanitized for review-stack tasks, enabling `GIT_PROXY_COMMAND` RCE - (File: `lib/shipit/task_commands.rb`, `app/models/shipit/deploy_spec.rb`, `lib/shipit/command.rb`)

### Summary
`DeploySpec#machine_env` returns the raw `machine.environment` map from the checked-out `shipit.yml` with no key whitelist, and `TaskCommands#env` merges it directly into the environment hash used to build every `Command`, including the `bundle`/`ruby` dependency-install step. Since a review stack's working directory is checked out from the PR's own head branch (on the contributor's fork), an unprivileged PR author can set `GIT_PROXY_COMMAND` (or similar loader/transport env vars) in their branch's `shipit.yml`, and it will be present in the environment of the `bundle install` command that Shipit executes on the deploy host.

### Finding Description
The broken binding: the intended invariant is `TaskCommands#env keys ⊆ EnvironmentVariables.permit(whitelist)`, i.e. no attacker-controlled key should reach `PTY.spawn` without going through the whitelist sanitizer defined in `lib/shipit/environment_variables.rb`. In fact, `TaskCommands#env` merges `deploy_spec.machine_env` [1](#0-0)  is merged straight from `DeploySpec#machine_env`, which is just `config('machine', 'environment') || {}` [2](#0-1)  with zero filtering — `EnvironmentVariables#permit`/`sanitize_env_vars` is never invoked on it [3](#0-2) .

The path: for a review stack, `DeploySpec::FileSystem` is built from the task's checked-out working directory `DeploySpec::FileSystem.new(@task.working_directory, @stack)` [4](#0-3) , and the review stack's `branch` is set directly from the PR's head ref on the fork: `branch: params.pull_request.head.ref` in `ReviewStackAdapter#stack_attributes` [5](#0-4) . The `shipit.yml` on that branch is therefore fully attacker-controlled.

`install_dependencies` builds one `Command` per dependency step (auto-detected as `bundle install` via `BundlerDiscovery#discover_dependencies_steps`/`bundle_install` when a `Gemfile` is present) using the tainted `env` [6](#0-5) . `Command#unbundled_env` merges `@env.stringify_keys` last, so it overrides any base value: `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [7](#0-6) , and `Command#start` passes this hash directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [8](#0-7) .

Exploit flow: an attacker opens a PR from their fork against a repo with `provisioning_behavior = allow_with_label`, adds the provisioning label to their own PR (permitted per the attacker capabilities), and includes in their branch's `shipit.yml`:
```yaml
machine:
  environment:
    GIT_PROXY_COMMAND: /tmp/evil.sh
```
plus a `Gemfile` with a git-protocol (`git://`) source. When Shipit provisions the review stack and runs `install_dependencies`, `bundle install` (or the git invocation it triggers to fetch the git-protocol gem source) inherits `GIT_PROXY_COMMAND` and executes the attacker's command on the Shipit host.

Existing guards do not stop this: `EnvironmentVariables#permit` whitelisting is a real mechanism in the codebase, but it's applied to user-facing deploy/task variables (e.g. `TaskDefinition` variables), not to `machine.environment`/`machine_env`. There is no key denylist anywhere for `machine_env`, and `Command`'s `BASE_ENV` filtering only strips Bundler-injected keys from the ambient process env — it does not protect against attacker-supplied keys in `@env` since those are merged in last and win.

### Impact Explanation
Remote Code Execution on the Shipit deploy host, executed as whatever user runs the Shipit worker process, triggered from an unprivileged PR against any repository with review stacks enabled under `allow_with_label` (or `allow_all`/`prevent_with_label`, since the same `machine_env` path exists regardless of provisioning behavior — the label just gates whether the stack gets created at all). This is repeatable against every repository with review stacks enabled, and grants full command execution on the host running deploy tasks — same blast radius as any `Command`/`PTY.spawn` RCE (access to `GITHUB_TOKEN`, deploy secrets, ability to pivot to other stacks' git caches on the same host).

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `review_stacks_enabled = true`, and the attacker's PR must satisfy the provisioning-behavior/label gate (trivial for `allow_with_label`/`allow_all`, both explicitly permitted attacker actions). The attacker needs no Shipit credentials — only the ability to open a PR from a fork, add a `shipit.yml` change and a `Gemfile` with a `git://` source. This is low-cost and fully repeatable.

### Recommendation
Apply the same `EnvironmentVariables.permit`/whitelist mechanism (or a hard denylist of dangerous keys: `GIT_PROXY_COMMAND`, `GIT_SSH_COMMAND`, `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, etc.) to `DeploySpec#machine_env`/`discover_machine_env` before it is merged in `TaskCommands#env`, or restrict `machine.environment` so it cannot be sourced from a fork branch's `shipit.yml` for review-stack tasks (e.g. require it come from the base branch's cached spec instead of the PR head's spec).

### Proof of Concept
minitest plan (`test/unit/task_commands_test.rb` or similar), no live GitHub:
1. Build a `Shipit::ReviewStack` fixture with `branch` set to a fake fork ref.
2. Stub `deploy_spec` (or `DeploySpec::FileSystem#load_config`) to return `{'machine' => {'environment' => {'GIT_PROXY_COMMAND' => '/tmp/evil.sh'}}, 'dependencies' => {'override' => ['bundle install']}}`.
3. Call `TaskCommands.new(task).install_dependencies` and assert:
   - `command.env['GIT_PROXY_COMMAND'] == '/tmp/evil.sh'` (left side: attacker's fork-controlled value; right side: value that should have been rejected by a whitelist — assert they are equal, proving the divergence).
4. Additionally assert that `Shipit::EnvironmentVariables.new(command.env).permit([])` would raise `NotPermitted` for `GIT_PROXY_COMMAND`, demonstrating the existing whitelist mechanism exists but is not applied on this path.
