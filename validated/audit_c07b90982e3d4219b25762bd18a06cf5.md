### Title
Webhook signature verification selects the GitHub App/org used to authenticate a request, but handlers act on unrelated payload fields that are never bound to that org — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives *which* organization's `webhook_secret` to verify the HMAC against from attacker-influenced JSON body fields (`repository.owner.login` / `organization.login`), then, once verified, hands the *entire* raw payload to event handlers that identify the target `Stack`/`Commit` using different, unrelated fields (or none at all). The equality the design assumes — "organization whose secret verified this request" == "organization that owns the repository/commit actually mutated" — is never enforced, breaking the deployment-trust binding between authenticated org and acted-upon repository, analogous to the `BufferBinaryPool` report where the amount authorized (unlocked) and the amount acted upon (transferred) silently diverged.

### Finding Description
`Shipit::WebhooksController#verify_signature` selects the verification secret like this: [1](#0-0) 

`repository_owner` is read straight out of the untrusted JSON body before the signature is checked: [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization config (each org can have its own distinct `webhook_secret`, as shown in the multi-org fixture): [3](#0-2) [4](#0-3) 

Once `verify_webhook_signature` succeeds (HMAC computed with the secret belonging to whatever org the attacker names in `repository.owner.login`), the controller dispatches the **entire** raw payload to handlers, unfiltered by that same org binding: [5](#0-4) 

Downstream handlers then locate the target record using fields that are not re-validated against the organization that authenticated the request:

- `PushHandler`/`Handler#stacks` resolves the target purely from `repository.full_name`, with no check that its owner matches `repository_owner` used for signature selection: [6](#0-5) , [7](#0-6) 
- `StatusHandler` is worse: it doesn't even use the `repository` field — it looks up `Commit` **globally by `sha` alone**, across every stack/org in the instance: [8](#0-7) 

Creating a status transitions the commit and, when it becomes `pending`/`success`, schedules the merge queue for that commit's actual stack: [9](#0-8) 

`ProcessMergeRequestsJob`/`MergeRequest#merge!` then performs a real GitHub merge using the app's own installation credentials (`stack.github_api`), not anything the attacker controls: [10](#0-9) [11](#0-10) 

**The broken equality:** `organization_that_authenticated(repository_owner in payload, verified via its own webhook_secret)` is implicitly assumed to equal `organization_that_owns(stack/commit acted upon by the handler)`. Nothing in `WebhooksController` or in `Handler#stacks`/`StatusHandler#process` enforces this. Before the report's analog fix would apply, one org's legitimately-known secret is sufficient to forge signed traffic that mutates state (commit statuses, triggering the merge queue, or a `GithubSyncJob` push-sync) belonging to a *different* organization hosted on the same Shipit instance, exactly as the original report describes tokens/amounts being "authorized" for one thing but "acted upon" for a larger/different scope.

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization" / "unauthorized ... merge" bar explicitly listed as High/Critical impact: an actor who legitimately controls one organization's GitHub App installation and knows only that org's `webhook_secret` can forge a `status` (or `push`/`check_suite`) event that is authenticated against their own org, but whose effective content (`sha`, or `repository.full_name`) targets a completely different organization's stack on the same shared Shipit deployment. Because `StatusHandler` has zero repository scoping, this can flip a status to `success` on any commit anywhere in the instance and trigger `stack.schedule_merges`, which can lead to an unauthorized GitHub pull-request merge performed with the app's own (victim org's) installation credentials.

### Likelihood Explanation
This requires the operator to run one shared Shipit instance serving multiple GitHub organizations (a documented, supported configuration — see `docs/setup.md` "Support multiple GitHub organisations" and the `OrgOne`/`OrgTwo` fixture). Within that scope, no privileged Shipit session, API token, or the victim org's secret is needed — only knowledge of one's own (attacker-controlled) organization's `webhook_secret`, which is inherent to running any GitHub App integration with Shipit. The `sha` needed for `StatusHandler` is discoverable via GitHub's public API/commit history for the target repo. This is a realistic, low-effort exploitation path for any multi-tenant Shipit deployment.

### Recommendation
- In `WebhooksController`, after verifying the signature for `repository_owner`, re-derive the resource(s) each handler is allowed to act on and assert they belong to that same `repository_owner`/organization — reject or drop events whose `repository.full_name` (or, for `status`, the commit's stack's repository owner) does not match the organization whose secret validated the request.
- In `Shipit::Webhooks::Handlers::StatusHandler`, stop resolving `Commit` globally by `sha`; scope the lookup through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (consistent with other handlers) and bind that repository's owner to the authenticated organization.
- Ensure `Handler#stacks` (used by `PushHandler`, `CheckSuiteHandler`, etc.) also validates that the resolved repository's owner equals the organization used to authenticate the webhook signature.

### Proof of Concept
1. Deploy Shipit with two GitHub organizations configured, `OrgA` (attacker-controlled, secret `secretA`) and `OrgB` (victim, secret `secretB`), each with its own `shipit.yml` stack — matching the supported multi-org config shown in `test/dummy/config/secrets_double_github_app.yml`.
2. As an administrator of `OrgA`'s GitHub App, the attacker already legitimately knows `secretA`.
3. Attacker crafts a `status` webhook body: `{"repository": {"owner": {"login": "OrgA"}}, "sha": "<sha of a commit on an OrgB-owned stack>", "state": "success", "context": "ci/travis"}`, computes `X-Hub-Signature: sha1=HMAC(secretA, body)`, and POSTs it to the shared `/webhooks` endpoint with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and successfully verifies the signature against `secretA`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (no repository scoping) and finds the OrgB commit, calling `create_status_from_github!`, which can flip the commit to `success` and invoke `stack.schedule_merges`, potentially causing `ProcessMergeRequestsJob` to merge a pull request on `OrgB`'s repository using Shipit's OrgB installation credentials — without the attacker ever knowing `secretB`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end

    def merge!
      raise InvalidTransition unless pending?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
