### Title
extractDuplicateIssueNumber always selects the first listed duplicate, allowing agent-influenced ordering to bind issue closure to the wrong target - (File: scripts/auto-close-duplicates.ts)

### Summary
`extractDuplicateIssueNumber` uses non-global `.match()` calls against `/#(\d+)/` and a GitHub issue-URL regex, both of which return only the **first** match in the comment body [1](#0-0) . Because `comment-on-duplicates.sh` renders up to three candidate duplicates as a numbered list of `https://github.com/<repo>/issues/<n>` URLs [2](#0-1) , the auto-close automation silently binds the `duplicate-of` target to whichever candidate happens to be **listed first**, ignoring candidates #2 and #3 entirely.

### Finding Description
`comment-on-duplicates.sh` accepts an ordered array via `--potential-duplicates` and writes each entry as `N. https://github.com/$REPO/issues/$dup` into the comment body, in the order the caller supplied them [3](#0-2) . That order is produced upstream by the dedupe agent (`.claude/commands/dedupe.md`), i.e., an LLM-driven process that reads issue titles/bodies — untrusted, user-controlled content — to rank similarity.

`auto-close-duplicates.ts` later parses that bot comment via `extractDuplicateIssueNumber`:
- It first tries `/#(\d+)/`. Since the comment body contains no literal `#<digits>` token (only markdown-free URLs), this pattern does not match.
- It falls through to `github\.com\/[^\/]+\/[^\/]+\/issues\/(\d+)`, and because `.match()` without the `g` flag returns only the first match in the string, this always resolves to the **first URL in the list** [4](#0-3) , i.e., candidate #1, regardless of whether #2 or #3 is the actual best match.

This extracted number is then used unconditionally as the `duplicateOfNumber` argument to `closeIssueAsDuplicate`, which closes the issue with `state_reason: 'duplicate'` and posts a comment referencing that number as authoritative [5](#0-4) . There is no code path that considers candidates #2/#3, no re-verification that candidate #1 is actually the most relevant, and no cross-check against the dedupe agent's confidence ranking beyond list position.

If the ranking/order of candidates emitted by the dedupe agent can be influenced by content embedded in issue bodies/titles (a plausible prompt-injection vector into an LLM-driven triage agent, since the agent reads arbitrary user-submitted issue text to rank "possible duplicates"), an attacker can cause an unrelated or attacker-chosen issue to be listed first. The auto-close script will then bind the closed issue's `duplicate-of` metadata to that attacker-controlled/unrelated issue instead of the true duplicate, with no validation preventing it.

### Impact Explanation
Scoped impact is cross-issue metadata corruption: a legitimate issue gets closed with `state_reason: duplicate` and a public comment claiming it is a duplicate of an attacker-influenced (wrong) issue number. This can be used to misdirect reporters/maintainers to an unrelated or attacker-controlled issue thread, suppress a real bug report under an incorrect duplicate link, or manipulate visible issue-tracker history/trust signals. It does not grant code execution, secret disclosure, or privilege escalation — it is limited to the TARGET_BINDING correctness of GitHub issue-closure metadata.

### Likelihood Explanation
The parsing bug itself is deterministic and 100% reproducible: any dedupe-bot comment with ≥2 numbered duplicate URLs will always resolve to the first one, independent of attacker involvement, purely from `.match()` semantics. The exploitable escalation — attacker-controlled ranking via prompt injection into the dedupe agent — depends on an unverified precondition (the ability to influence the LLM agent's candidate ordering through crafted issue text), which is plausible for LLM-driven triage but not directly demonstrated in this codebase snapshot beyond the referenced `.claude/commands/dedupe.md` command.

### Recommendation
Do not rely on regex extraction of "the first mentioned number" as ground truth. Instead:
- Have the dedupe agent (or `comment-on-duplicates.sh`) emit an unambiguous, structured, machine-parseable primary-duplicate marker (e.g., a dedicated `<!-- primary-duplicate: 123 -->` HTML comment or a JSON payload) rather than relying on list position and generic `#\d+`/URL regexes.
- Update `extractDuplicateIssueNumber` to parse that structured marker explicitly rather than taking the first regex match in free-form text.
- Consider requiring the auto-close script to only act when there is exactly one candidate duplicate, or to verify similarity independently before closing.

### Proof of Concept
Unit test for `extractDuplicateIssueNumber`:
```ts
const body = `Found 3 possible duplicate issues:

1. https://github.com/anthropics/claude-code/issues/999
2. https://github.com/anthropics/claude-code/issues/456
3. https://github.com/anthropics/claude-code/issues/789

This issue will be automatically closed as a duplicate in 3 days.`;

expect(extractDuplicateIssueNumber(body)).toBe(999); // always picks entry #1
```
This demonstrates that candidates #2 (456) and #3 (789) are always ignored regardless of which is the actual best match.

Integration test plan: mock the dedupe-agent output ordering to place a chosen "least-related" issue first (simulating prompt-injection-influenced ranking), run `autoCloseDuplicates()` against a mocked GitHub API, and assert that `closeIssueAsDuplicate` is invoked with `duplicateOfNumber` equal to the attacker-influenced first entry rather than the actual best-matching duplicate, confirming the wrong-target closure.

```typescript
function extractDuplicateIssueNumber(commentBody: string): number | null {
  // Try to match #123 format first
  let match = commentBody.match(/#(\d+)/);
  if (match) {
    return parseInt(match[1], 10);
  }
  
  // Try to match GitHub issue URL format: https://github.com/owner/repo/issues/123
  match = commentBody.match(/github\.com\/[^\/]+\/[^\/]+\/issues\/(\d+)/);
  if (match) {
    return parseInt(match[1], 10);
  }
  
  return null;
}
```
