### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while the acted-upon repository is resolved from `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which configured GitHub App/`webhook_secret` to validate the request against using `repository.owner.login` (or `organization.login`) pulled from the untrusted JSON body, while the handlers that actually act on the payload (`Handler#repository_name`, used by `PushHandler` and `CheckSuiteHandler`) resolve the target `Repository`/`Stack` using `repository.full_name` from the same body. On a multi-tenant Shipit instance (multiple orgs each with their own GitHub App and `webhook_secret`, as documented in `config/secrets.development.shopify.yml`), these two fields are never checked against each other.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
with
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GitHubApp#verify_webhook_signature` only checks that the raw body's HMAC matches the secret configured for that particular org entry; it never checks that the signed body's `repository.full_name` belongs to that same org: [3](#0-2) 

Once signature verification passes, the event handlers act on a *different* field of the same body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler` then synchronizes every matching stack to an attacker-supplied `after` SHA:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

`CheckSuiteHandler` similarly resolves stacks via `repository_name` (i.e. `full_name`) and triggers check-run refreshes independent of `repository_owner`: [6](#0-5) 

The binding that breaks: `verified_organization (repository.owner.login → webhook_secret used)` ≠ `acted_upon_repository (repository.full_name → Repository/Stack looked up)`. Both values are attacker-controlled fields inside the same JSON body — GitHub itself always keeps them consistent when it emits a webhook, but nothing in Shipit enforces that `repository.full_name` actually belongs to the org identified by `repository.owner.login`, or to the org whose app installation the request supposedly came from.

### Impact Explanation
On a single-org Shipit deployment this is not exploitable, since there is only one `webhook_secret` and any signed body necessarily targets that org's repositories. However, Shipit explicitly supports and documents multi-org configuration (`config/secrets.development.shopify.yml`, `lib/shipit/github_app.rb#initialize` keyed `per organization`). In that configuration, an actor who legitimately controls installation A (their own org, with knowledge/receipt of org A's `webhook_secret` via real GitHub webhook deliveries they can trigger) can construct a JSON body where `repository.owner.login = "orgA"` (so `verify_webhook_signature` selects and validates against org A's secret) but `repository.full_name = "orgB/private-repo"` (a different tenant's tracked repository). The signature check only verifies the bytes match org A's HMAC — it says nothing about which repo the body claims to describe. This crosses a repository-write boundary: an operator authorized only for org A's webhook events can force `GithubSyncJob`/`stack.sync_github` runs, or check-run refresh scheduling, against a stack belonging to a completely different, unauthorized organization/repository on the same Shipit instance.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (documented, supported configuration) and requires the attacker to already be able to produce a validly-signed webhook body for at least one configured org (i.e., control an installation of the app for org A, or otherwise be able to trigger/replay a real webhook for org A). This is a real but non-trivial precondition — it does not require compromising Shipit secrets directly, only abusing one's own legitimately-authorized organization's webhook channel to affect another tenant's repository state.

### Recommendation
After signature verification succeeds, re-derive the acted-upon repository binding from the same trust anchor used for verification: assert that `repository.full_name`'s owner segment equals the `repository_owner` (or the specific org/installation) whose secret validated the signature, rejecting (422) any mismatch before dispatching to `Shipit::Webhooks.for_event(event)` handlers. Alternatively, resolve the target `Repository`/`Stack` by installation ID (tied to the GitHub App config that validated the signature) rather than by the payload's free-form `full_name` string.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with its own GitHub App and `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As a party controlling org A's installation, obtain a validly HMAC-signed webhook body for org A (e.g., a real `push` event delivered by GitHub for org A) and note the `X-Hub-Signature` for that raw body — or, since `verify_webhook_signature` HMACs the exact raw bytes, craft your own JSON payload and self-sign it offline using org A's `webhook_secret` if it is known/leaked to you as the org's app owner.
3. Set the payload's `repository.owner.login` to `"orgA"` and `repository.full_name` to `"orgB/target-repo"` (a repository tracked under org B in the same Shipit instance), with `ref`/`after` pointing at an arbitrary SHA.
4. POST to `/webhooks` with `X-Github-Event: push` and the computed `X-Hub-Signature`. `verify_signature` selects org A's `GitHubApp` (via `repository_owner`) and the signature validates.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `payload.dig('repository', 'full_name')` = `"orgB/target-repo"` and calls `stack.sync_github(expected_head_sha: params.after)` on org B's stack — an action never authorized by org B's own webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
