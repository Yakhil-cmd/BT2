### Title
Webhook signature verification is bound to the payload's `repository.owner.login`, but the mutation targets are resolved independently and unscoped — allowing cross-organization/cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to HMAC-verify a webhook against using the attacker-controlled `repository.owner.login` (or `organization.login`) field of the JSON body. Once that check passes, the actual event handlers (`Handler#repository_name`, and especially `StatusHandler#process`) resolve *which* record in the database to mutate using **other, independently-controlled fields of the same body** (`repository.full_name`, or in the status handler's case, nothing at all — just the raw commit `sha`), with no cross-check that those fields describe a resource belonging to the organization whose secret was actually verified.

### Finding Description
The signature check is: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This picks the `GitHubApp` (and its `webhook_secret`) purely from the payload's `repository.owner.login`, which is completely attacker-supplied JSON — nothing about it is authenticated except that *some* HMAC over the whole raw body validates against *that org's* secret.

Shipit explicitly supports multiple GitHub Apps/organizations configured with independent `webhook_secret`s in a single instance: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full, attacker-controlled JSON body to the handler: [5](#0-4) 

Handlers resolve the target resource from **different** fields than the one used for signature selection:
- Generic handler base class uses `payload.dig('repository', 'full_name')`: [6](#0-5) 
- `StatusHandler`, used for the `status` event, doesn't even use the repository at all — it looks up commits **globally by SHA**, with no organization/repository scoping whatsoever: [7](#0-6) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

So the equality the system implicitly, but never actually, enforces is:

`organization_whose_secret_signed_the_request == organization_that_owns_the_commit/repository_being_mutated`

Before an attack: for a legitimate webhook, GitHub itself guarantees this equality because it only sends a payload for org A signed with org A's secret, describing org A's own repository/commit.

After the attacker's crafted request: the attacker (who legitimately controls a webhook secret for Org A — e.g. they administer a repository in Org A that Shipit also tracks, in a multi-org Shipit deployment) can send an arbitrary JSON body signed with Org A's secret, but set `repository.owner.login` = "OrgA" (to pass the signature check) while setting the mutation-driving fields (`sha` for the `status` event, or `repository.full_name` for `push`/`pull_request`/`check_suite`) to reference a completely different organization/repository/stack ("OrgB") that Shipit also manages. Nothing in `verify_signature` or in the handlers cross-checks that these two independent fields agree.

### Impact Explanation
This breaks the deployment-trust binding between "the organization that authenticated the webhook" and "the repository/commit that is written," matching the required Critical impact category of **cross-repository writes**. The clearest concrete exploitation path is via the `status` event: an attacker who legitimately owns a webhook secret for Org A can forge a CI status (`state: "success"`) for **any commit SHA in Shipit's database**, regardless of which organization or stack it belongs to, because `StatusHandler#process` scopes the mutation only by `sha`, never by the org/repository that was used to select the verifying secret. A forged "success" status can satisfy CI requirements (`ci.require`) used to gate continuous delivery/deploy eligibility on a totally unrelated stack the attacker has no legitimate access to, potentially leading toward an unauthorized deploy trigger on that other stack.

### Likelihood Explanation
Exploitability requires:
1. The Shipit instance to be configured with multiple GitHub Apps for multiple organizations (a documented, supported configuration — `docs/setup.md`, "Using Multiple Github Applications").
2. The attacker to legitimately control one org's webhook secret (e.g. by being allowed to configure webhooks on a repo within their own, unprivileged organization that Shipit tracks) — no Shipit credentials, `ApiClient` token, or GitHub App private key are needed.
3. Knowledge of a target commit `sha` belonging to another tracked repository (commit SHAs of public repos are trivially discoverable).

No Shipit-side privilege is required beyond having a webhook configured for one's own repository in a multi-org Shipit deployment, satisfying the "unprivileged attacker" constraint.

### Recommendation
Bind signature verification to the resource actually being mutated: after establishing which `GitHubApp`/organization successfully verified the signature, re-derive `repository_name`/commit ownership from the payload and require that it belongs to that same, verified organization before dispatching to handlers. In particular, `StatusHandler#process` should scope `Commit.where(sha: params.sha)` to commits whose `stack.repository.owner` matches the organization that verified the signature (and similarly the generic `Handler#stacks` lookup should reject payloads whose `repository.full_name` owner does not match `repository_owner`/`organization.login` used for signature verification).

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct GitHub Apps/`webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`), both tracking stacks in Shipit.
2. As an attacker who legitimately controls (or knows) `OrgA`'s `webhook_secret` (e.g., because they configured a webhook on their own repository under `OrgA`), craft a `status` event JSON payload:
```json
{
  "sha": "<sha of a commit belonging to a stack under OrgB>",
  "state": "success",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POST it to `/github/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and the HMAC validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the commit under `OrgB` — and calls `commit.create_status_from_github!(params)`, creating a forged "success" status for a commit in `OrgB`'s stack despite the request only being authenticated for `OrgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
