### Title
API client token scoped to one stack can read CCMenu build/deploy status of any other stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces stack-level authorization for scoped `ApiClient` tokens by resolving the requested stack through the `stacks` scope, which restricts lookups to `current_api_client.stack_id` when the token is scoped to a specific stack. `Shipit::Api::CCMenuController` overrides `stack` to bypass that scope entirely, breaking the binding between "the stack a token authorizes" and "the stack it touches."

### Finding Description
`BaseController#stacks` restricts the queryable set of stacks to the one the `ApiClient` is scoped to: [1](#0-0) [1](#0-0) 

`stack` in the same base controller resolves the requested `params[:stack_id]` through that authorized scope: [2](#0-1) 

`ApiClient` records optionally belong to a `stack`, and `check_permissions!` only validates the coarse-grained `operation:scope` permission string (e.g. `read:stack`) — it never checks which stack is being accessed: [3](#0-2) [4](#0-3) 

The stack-scoping is therefore entirely dependent on `BaseController#stack` routing lookups through `stacks`. `Api::CCMenuController` overrides that method to query `Stack.from_param!(params[:stack_id])` directly, ignoring the `current_api_client.stack_id` restriction: [5](#0-4) 

So the equality that should hold — `token.authorized_stack == requested_stack` (when the token is scoped to a single stack) — is broken specifically for this controller: the `require_permission :read, :stack` check only verifies the token has the generic `read:stack` permission, not that the target stack matches the one the token is bound to.

### Impact Explanation
Any valid `ApiClient` token with `read:stack` permission — even one deliberately scoped to a single stack via `stack_id` — can be replayed against `Api::CCMenuController#show` with an arbitrary `stack_id` parameter to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) of any other stack in the installation. This is an unauthenticated-for-that-stack read of stack state via a token that was never authorized for it, matching the "escalation into authorization / unauthenticated read of stack state" High-severity category.

### Likelihood Explanation
Any team member who creates a stack-scoped `ApiClient` (a normal, supported workflow via `ApiClientsController`, e.g. to give a CI system limited access) already holds a token that fully bypasses the scoping restriction against this one endpoint. No privileged access beyond possessing that one legitimately-scoped token is required, and the token format/authentication path (`ApiClient.authenticate(params[:token])`) is identical to normal use, so exploitation is a simple, repeatable GET request.

### Recommendation
Change `CCMenuController#stack` to resolve the stack through the authorized `stacks` scope (i.e. `stacks.from_param!(params[:stack_id])`), consistent with `BaseController`, so a stack-scoped token can never resolve a stack outside its authorization.

### Proof of Concept
1. Create (or obtain) two stacks, `stack_a` and `stack_b`.
2. Create an `ApiClient` scoped to `stack_a` with permission `read:stack` (e.g. via `ApiClientsController#create` with `stack_id: stack_a.id`), yielding `token`.
3. Request `GET /api/stacks/stack_a/ccmenu.xml?token=token` → succeeds as expected (authorized stack).
4. Request `GET /api/stacks/stack_b/ccmenu.xml?token=token` → also succeeds and returns `stack_b`'s build/deploy status, even though the token is scoped only to `stack_a`, because `CCMenuController#stack` uses `Stack.from_param!` directly instead of the scoped `stacks.from_param!` used everywhere else in `BaseController`.
