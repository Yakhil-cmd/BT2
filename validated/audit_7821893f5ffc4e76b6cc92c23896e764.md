## Title
Mutable attestor list for `spender_attested` assets lets an asset issuer unilaterally freeze already-held or in-flight funds (including AA balances) at any time - (File: `validation.js`, `storage.js`)

## Summary
The original report flags stablecoins like TUSD whose implementation can be upgraded post-integration, silently changing spending/transfer rules and freezing funds that a protocol assumed were fixed. ocore has a directly analogous mechanism for custom assets: when an asset is created with `spender_attested: true`, the definer (asset issuer) retains permanent, unrestricted, unilateral power to rewrite the list of addresses allowed to spend the asset via an `asset_attestors` message, at any point after issuance, with no rate limit, no timelock, and no protection for holders (including AAs) that already received/hold the asset.

## Finding Description
When validating a `payment` message for a non-base asset, the current attestor list is loaded fresh from the DB and used to gate whether authors/issuers are allowed to move the asset: [1](#0-0) 

The attestor list itself is not fixed at asset-definition time; it is a separate, ongoing message stream (`asset_attestors`) that only requires being signed by the definer address, with no other constraint besides format checks: [2](#0-1) [3](#0-2) 

`storage.readAsset`/`loadAssetWithListOfAttestedAuthors` always resolve to the *latest* stable attestor list as of `last_ball_mci`, so every future spend attempt is checked against whatever list the definer currently has in force, not the list that existed when the asset was received: [4](#0-3) [5](#0-4) 

Because this check is re-evaluated on every spend attempt (not pinned at receipt time), a definer can:
1. Issue an asset with `spender_attested: true` and an initial attestor list that includes some recipients/AAs.
2. Let holders (including autonomous agents that integrate the asset as collateral, a payment token, or trigger currency) accumulate balances, on the assumption that being currently attested means they can freely move the asset later.
3. Post a new `asset_attestors` unit removing those addresses from the attestor list.
4. All of those holders (and any AA holding a balance in that asset) permanently lose the ability to spend their already-owned balance, because `validatePayment` will reject any future payment authored by a now-unattested address (`"issuer is not attested"` / `"none of the authors is attested"`).

This mirrors the TUSD-style risk precisely: the "token" (asset) contract's issuer can change enforcement logic after the fact in a way that other code (wallets, AAs, exchange/DeFi-style AAs built on top of `ocore`) did not - and structurally cannot - anticipate at design time, because nothing in the protocol pins or grandfathers the conditions in force when the asset was acquired.

## Impact Explanation
- Funds held by an AA (or any address) in a `spender_attested` asset can be permanently frozen by the asset issuer at will, with no on-chain recourse, satisfying the "AA fund loss or freezing" impact bar.
- Any AA that integrates a third-party `spender_attested` asset as a settlement/collateral token is exposed: the issuer can retroactively revoke the AA's own attested status (or that of its expected counterparties), stranding the AA's balance and breaking its accounting/business logic that assumed the asset would remain transferable.
- This differs from ordinary "trusted issuer" risk (e.g. `issued_by_definer_only`, which only affects future issuance) because it retroactively affects funds already transferred and held by third parties, not just the issuance path.

## Likelihood Explanation
Reachable without any special privilege beyond being the asset's own definer - an ordinary, unprivileged unit poster can create such an asset and later post an `asset_attestors` update; no additional consensus, cosigning, or governance step is required (`validateAttestorListUpdate` only checks single-authorship and definer address). Any protocol or AA that decides to accept a `spender_attested` asset as a payment/collateral token is exposed the moment it starts holding a balance of it.

## Recommendation
- Pin the attestor requirement to the point of receipt for existing balances, or provide a way for holders/AAs to "lock in" attestation status at receipt time rather than re-checking it against the current list on every future spend.
- Alternatively, require a timelock/cooldown before an `asset_attestors` update takes effect, giving holders a window to move funds out before new restrictions apply.
- Document explicitly (and expose via the `asset[...]` formula getters) that `spender_attested` assets carry this "issuer can freeze already-held funds" risk so AA authors can defensively avoid or bound their exposure (e.g., cap balances, avoid using such assets as core collateral).

## Proof of Concept
1. Definer `D` creates asset `A` with `spender_attested: true` and initial attestor list `[AA_addr, X]` via an `asset` message (`validateAssetDefinition` in `validation.js`).
2. `D` issues `A` and sends a payment of `A` to autonomous agent `AA_addr`; `AA_addr` accepts it as collateral and updates its internal state assuming the balance is spendable.
3. `D` posts an `asset_attestors` unit for asset `A` with a new list `[X]` (removing `AA_addr`) - accepted per `validateAttestorListUpdate` (`validation.js:2829-2848`) since `D` is still the definer.
4. `AA_addr` later tries to send out `A` (e.g., to honor a withdrawal): `validatePayment` (`validation.js:2115-2121`) now finds `AA_addr` absent from `arrAttestedAddresses` and rejects the payment with `"issuer is not attested"`, permanently freezing `AA_addr`'s balance of asset `A`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
