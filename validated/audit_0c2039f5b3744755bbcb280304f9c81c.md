### Title
Cross-tenant Status forgery via no-secret organization signature bypass and unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`, `lib/shipit/github_app.rb`)

### Summary
`Shipit::GitHubApp#verify_webhook_signature` returns `true` unconditionally, before ever parsing the `X-Hub-Signature` header, whenever the resolved organization has no `webhook_secret` configured [1](#0-0) . Since the organization used for that lookup is taken directly from attacker-controlled payload fields (`repository.owner.login` / `organization.login`) [2](#0-1) , an attacker who can name any Shipit-registered but secret-less organization gets a fully authenticated webhook. `StatusHandler#process` then updates `Commit.where(sha: params.sha)` with zero repository or stack scoping, so if that SHA also exists in a victim stack's commit history, the victim's commit receives an attacker-forged status write [3](#0-2) .

### Finding Description
The broken binding is: *"a `status` event authenticated for organization A must only mutate commits belonging to stacks under organization A."* In the code, this becomes false because:

1. `WebhooksController#verify_signature` picks the `GitHubApp` instance using `repository_owner`, itself read straight out of the untrusted JSON body [4](#0-3) [2](#0-1) .
2. `verify_webhook_signature` short-circuits to `true` before the `signature.split("=", 2)` call is ever reached whenever that organization's `webhook_secret` is blank [1](#0-0) . This means the "malformed signature with no `=`" detail from the question is actually irrelevant for this exact org — any header value, or none at all, passes, because the split code is never executed. The exploit only requires that *some* organization known to Shipit's config has no secret set.
3. `StatusHandler#process` performs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` with no filter on stack, repository, or organization at all [3](#0-2) . Git SHA1s are content-addressed and identical commits routinely exist across forks/mirrors/shared history, so a commit SHA present in an attacker-controlled repo can coincide with one already ingested into a victim's stack.

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: status` and a body whose `repository.owner.login` (or `organization.login`) names an organization that is configured in Shipit but has no `webhook_secret`. `verify_signature` passes unconditionally. `StatusHandler` then looks up `Commit` rows by the bare `sha` in `params`, with no relation to the authenticated organization, and calls `create_status_from_github!` on any match — including commits belonging to an entirely different, properly-secured victim stack.

None of the listed guards prevent this: `drop_unhandled_event` only checks the event name is handled; `ExplicitParameters` for `StatusHandler` only validates `sha`/`state`/etc. types, not repository ownership [5](#0-4) ; there is no `require_permission!`/`stacks` scope check on this unauthenticated controller at all.

### Impact Explanation
An attacker who can get any single Shipit-managed organization configured without a `webhook_secret` can inject fabricated commit statuses (`state`, `description`, `target_url`, `context`) onto commits of unrelated, fully-secured victim stacks whenever a SHA collision exists (shared upstream history, forks, cherry-picks, or identical trees). Because commit deployability/CD gating in Shipit is driven by status state (`Commit#deployable?`, `blocked?`, `schedule_continuous_delivery`) [6](#0-5) [7](#0-6) , a forged "success" status can unblock/trigger continuous deployment for a victim stack the attacker never authenticated against — a payload for one repository mutating another's commit/stack state, matching the Critical category in scope. This is repeatable against any victim commit whose SHA the attacker can predict/reproduce.

### Likelihood Explanation
Requires a specific server-side misconfiguration: at least one organization registered in Shipit's GitHub app config with a blank/missing `webhook_secret` (unrelated to the victim org, which can remain fully secured). Given that, the attacker's cost is a single unauthenticated HTTP POST with a crafted JSON body; no GitHub credentials, sessions, or API tokens are needed. Feasibility of the SHA-collision precondition depends on shared commit history between attacker and victim repos (forks, common upstream, vendoring) — plausible in many real deployments but not universal, so likelihood is conditioned on both the config gap and repository relationship existing.

### Recommendation
Scope `StatusHandler` (and any handler doing bare `Commit`/`sha` lookups) to the repository/organization that authenticated the webhook — e.g., restrict `Commit.where(sha: ...)` to commits whose `stack.repository` matches `params.repository`/`repository_owner`, or key it off stacks pre-associated with the verified organization. Additionally, do not allow `verify_webhook_signature` to trivially return `true` for organizations lacking a secret; require an explicit "signature verification disabled" opt-in rather than a silent default, and reject webhooks whose `X-Hub-Signature` cannot be parsed regardless of secret presence.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test, no live GitHub)
test ":status from a no-secret org writes a status onto an unrelated victim commit by shared SHA" do
  victim_commit = shipit_commits(:first)  # belongs to a different, secured stack/org

  # Simulate an organization configured in Shipit but WITHOUT a webhook_secret
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', {}) # no :webhook_secret key => verify returns true unconditionally
  )

  request.headers['X-Github-Event'] = 'status'
  request.headers['X-Hub-Signature'] = 'malformedsignaturewithnoequals'

  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'description' => 'forged by attacker',
    'branches' => [{ 'name' => 'master' }],
    'repository' => { 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body: body, as: :json
  end
  assert_response :ok

  status = victim_commit.statuses.last
  assert_equal 'forged by attacker', status.description
end
```
Both sides of the invariant equality — "authenticated organization" (`attacker-org`, unrelated, secret-less) vs. "organization owning the mutated commit" (victim's actual stack organization) — diverge after the request, confirming the cross-tenant write.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
