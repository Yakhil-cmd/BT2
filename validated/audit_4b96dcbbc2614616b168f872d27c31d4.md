### Title
Missing `review_stacks_enabled` check in `ReopenedHandler#unarchive?`'s label branches allows repeatable re-provisioning/RCE via close+reopen cycling - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` and `OpenedHandler#provision?` only gate the `allow_all` provisioning behavior on `repository.review_stacks_enabled`; the `allow_with_label` and `prevent_with_label` branches never check it. Combined with `ClosedHandler#process`, which archives a review stack unconditionally with no `review_stacks_enabled` check at all, an attacker who already got a stack created on a `review_stacks_enabled=false` repository (via the same bug in `OpenedHandler`) can repeatedly close and reopen their PR to re-enqueue and re-provision the stack, re-executing whatever `shipit.yml` currently sits at the HEAD of their own branch.

### Finding Description
Broken binding: `stack.branch`'s `shipit.yml` executed at provisioning time (queued via `Shipit::ReviewStackProvisioningQueue.add(stack)` in `ReviewStackAdapter#unarchive!`) is claimed/expected to equal the content that was approved/reviewed when the stack was first created; in fact it always equals whatever is currently pushed to the branch HEAD at the moment `ReviewStackProvisioningQueue.work` processes the queue [1](#0-0) .

Root cause is the same operator-precedence/logic bug in `ReopenedHandler#unarchive?` as in `OpenedHandler#provision?`: only the first disjunct is guarded by `review_stacks_enabled`, the other two are not: [2](#0-1) 

`ClosedHandler#process` has no `review_stacks_enabled` gate whatsoever - it fires on any `action == "closed"`: [3](#0-2) 

Given precondition (stack already exists on a `review_stacks_enabled=false` repo, from the prior `provision?` exploit) and `repository.provisioning_behavior_allow_with_label?` with the attacker's own label on their own PR: closing the PR calls `review_stack.archive!` → `ReviewStackAdapter#archive!`, which deprovisions and archives the stack unconditionally [4](#0-3) . Reopening re-evaluates `unarchive?`, which is true via the unguarded label branch, and calls `stack.unarchive!` → `ReviewStackAdapter#unarchive!`, re-adding the stack to `ReviewStackProvisioningQueue` and unarchiving it [5](#0-4) . The queue worker later re-provisions from the branch's current HEAD [6](#0-5) . None of `verify_signature`, `respond_to_pull_request_closed?`, or `unarchive?` block this because the closed-handler check is entirely absent and the reopened-handler check is logically incomplete.

### Impact Explanation
Each close→push-new-`shipit.yml`→reopen cycle causes the engine to re-run the deploy pipeline (ultimately reaching `Command`/`PTY.spawn` execution paths) against attacker-controlled `shipit.yml` content, on a repository whose owner explicitly disabled review stacks (`review_stacks_enabled=false`). This is repeatable indefinitely by the same unprivileged PR author, giving them an on-demand, refreshable RCE primitive scoped to that repository's deploy host/environment - Critical severity, matching "RCE on the deploy host via `Command`/`PTY.spawn`."

### Likelihood Explanation
Requires the precondition from the linked prior exploit (a stack already created despite `review_stacks_enabled=false`, via the identical unguarded branch in `OpenedHandler#provision?`), and the repository's `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (label control is entirely in the attacker's hands as PR author). No Shipit secrets, sessions, or maintainer privileges are needed - only the ability to open/close/reopen one's own PR and push commits to one's own branch. This is low-cost and fully repeatable.

### Recommendation
Fix `unarchive?` (and the analogous `provision?` in `OpenedHandler`) so `repository.review_stacks_enabled` gates all three provisioning-behavior branches, e.g. `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`. Additionally, add an explicit `repository.review_stacks_enabled` guard to `ClosedHandler#respond_to_pull_request_closed?` (or centralize the check inside `ReviewStackAdapter`) so archive/unarchive/provisioning can never run against a repository that has review stacks disabled.

### Proof of Concept
In a minitest under `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`-style setup (not included per scope, but described): create a repository with `review_stacks_enabled: false`, `provisioning_behavior: allow_with_label`; create a `ReviewStack` bypassing the create-path bug directly to satisfy the precondition; label the PR with the provisioning label; send a `closed` webhook and assert `stack.reload.archived?` is true despite `review_stacks_enabled == false`; push a new `shipit.yml` commit to the PR branch; send a `reopened` webhook and assert `stack.reload.archived?` is false and the stack is enqueued (`awaiting_provision?` true); run `Shipit::ReviewStackProvisioningQueue.work` and assert the `Command#args` captured for the provisioning step reflect the new `shipit.yml`'s steps, not the original ones - proving repeated re-execution of attacker-controlled content on a `review_stacks_enabled=false` repository.
