### Title
`StatusHandler#process` matches commits by SHA1 across all repositories with no ownership check, allowing a webhook from one (attacker-controlled) repository to trigger continuous deployment of a commit belonging to an unrelated stack - (`File: app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` without ever checking that the commit's owning stack/repository matches the repository named in the webhook payload that was actually signature-verified. Unlike the PullRequest handlers, which resolve stacks through `Handler#stacks` (`Repository.from_github_repo_name(repository_name)`), `StatusHandler` never calls `stacks` or `repository_name` at all, so any validly-signed webhook (signed with the attacker's own `webhook_secret` for their own repository) can post a status for any SHA that happens to exist in any other stack in the installation.

### Finding Description
The binding that should hold is: `payload.dig('repository','full_name') == commit.stack.repository.full_name` for every `commit` the handler mutates. Tracing the code:

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves the payload was signed by the GitHub App belonging to `repository_owner = params.dig('repository','owner','login')`. It proves nothing about which SHAs may legitimately be referenced in that payload — it only proves "this org sent this JSON."
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. `params.sha` is attacker-supplied content inside the signed body (the attacker fully controls their own commit's sha because they own the repo/commit), and the query has no `stack_id`/`repository` scope at all.
- `Handler#stacks`/`Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) exist precisely to bind a handler's actions to the repository that authenticated the request, and are used by the PullRequest handlers, but `StatusHandler` never invokes them.
- `Commit#create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb:165-169`, `366-386`) records the status and, on a state transition, emits `Hook.emit(:deployable_status, ...)` and, via the `after_commit :schedule_continuous_delivery` callback path being re-triggered through `schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`), enqueues `ContinuousDeliveryJob.perform_later(stack)` if `commit.deployable? && stack.continuous_deployment? && stack.deployable?`.

So the equality never holds and is never checked: `payload['repository']['full_name']` is the attacker's own repo, while `commit.stack.repository.full_name` can be an arbitrary victim repository that merely happens to contain a `Commit` row with the same `sha` value. Given the stated precondition (attacker engineers/possesses a commit whose sha collides with one in the victim's stack — e.g., copies a public commit that also exists in the victim's history, which is trivial and requires no cryptographic collision at all, just re-pushing the same publicly known commit to their own repo), the attacker can drive the victim stack's `Commit#status` to `success` and cause `ContinuousDeliveryJob` to run against the victim's stack purely by controlling their own repository's webhook.

None of the existing guards stop this: `verify_signature` authenticates the sender's own org, not the SHA scope; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema only validates shape (`sha` is `String`); there is no `force_github_authentication`, `User#authorized?`, or `stacks`/`repository_name` check anywhere in `StatusHandler`.

### Impact Explanation
An attacker who owns any GitHub repository with a properly configured Shipit webhook can cause `Commit#create_status_from_github!` to run against a `Commit` row belonging to a victim stack they do not control, updating its status and — if `stack.continuous_deployment?` and the commit becomes `deployable?` — enqueueing `ContinuousDeliveryJob.perform_later(stack)`, which calls `Stack#trigger_continuous_delivery` and initiates an unauthorized deploy of the victim's own already-merged code. This is a cross-tenant write: a payload authenticated for one repository mutates another repository's stack/commit state and can trigger a deploy action the victim never approved for that specific commit's readiness. This matches the "unauthorized deploy" / "payload for one repository mutating another's stack/commit" Critical impact category. The attack is repeatable against any stack whose commits share a SHA with a commit reachable/reproducible by the attacker (most trivially, an identical publicly known commit deliberately pushed to both repos, which requires no cryptographic break at all).

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment?` true and an undeployed commit whose `sha` also exists as a row (any stack) matching what the attacker can push to their own repository; the attacker needs only a Shipit-connected GitHub repo of their own (their own webhook/App installation, no Shipit secrets). Practically, forcing a SHA1 collision against an arbitrary pre-existing hostile target is not currently feasible; however, the simplest and fully realistic variant is that both the attacker's and victim's repositories legitimately contain the *same* commit (e.g., a shared open-source commit, a cherry-pick, a vendored dependency bump, a common base commit shared via fork/subtree) — this requires no cryptography at all and is the primary, cheap, repeatable exploitation path. Cost to the attacker is essentially one webhook POST per target SHA once repository/commit overlap is identified.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the PullRequest handlers: filter commits through `stacks` (i.e., `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent join restricting `Commit#stack_id` to `Repository.from_github_repo_name(repository_name).stacks`) before calling `create_status_from_github!`, so a status can only ever be applied to commits belonging to the repository named in the verified payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not update commits belonging to a different repository" do
  attacker_stack = shipit_stacks(:shipit)
  victim_stack = Shipit::Stack.create!(
    repository: Shipit::Repository.create!(owner: 'victim-org', name: 'victim-repo'),
    environment: 'production',
    continuous_deployment: true
  )
  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'legit commit')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo' }
  }

  assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  refute victim_commit.reload.success?
end
```
Currently this assertion fails: `StatusHandler.call(payload)` updates `victim_commit`'s status to success and enqueues `ContinuousDeliveryJob` for `victim_stack`, even though the payload's `repository.full_name` names `attacker-org/attacker-repo`, demonstrating the missing repository-scoping in `app/models/shipit/webhooks/handlers/status_handler.rb`.
