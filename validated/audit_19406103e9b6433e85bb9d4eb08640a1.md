### Title
`has_only()` character-class construction lets a caret bypass the intended allowlist and accept any string - (File: formula/evaluation.js)

### Summary
`has_only(str, chars)` is documented and used in oscript/AA formulas as an allowlist check: "does `str` consist only of characters from `chars`?" The implementation builds this check by naively interpolating the caller-supplied `chars` string into a regex character class (`^[` + chars + `]*$`). It escapes a trailing `]` but does not escape or reject a leading `^`, which is a POSIX/ECMAScript regex-class control character, not an ordinary literal. This is directly analogous to the OpenClaw advisory: an allowlist check that inspects a string for disallowed content but misses a "combined"/control-flag form of the input (there, combined POSIX inline flags; here, the `^` negation flag inside a character class), letting attacker-influenced input completely invert the intended filter and match anything.

### Finding Description
`has_only` is evaluated in `formula/evaluation.js`: [1](#0-0) 

The code only defends against two specific escape sequences (`\]` and a trailing lone backslash) before building `new RegExp("^[" + sub + "]*$")`. It does not check for or neutralize a leading `^` inside the class. In a JavaScript/ECMAScript regex, `[^...]` negates the character class, and the empty negated class `[^]` matches *any single character* (including newlines), because there is nothing to exclude. Consequently:

- `has_only(str, "^")` compiles to `/^[^]*$/`, which matches **any** string of any length, defeating the allowlist entirely.
- More generally, prefixing the allowed-characters string with `^` inverts the semantics from "only these characters are allowed" to "any character except these," which is the opposite of what an AA author intends when calling `has_only`.

This mirrors the OpenClaw bug class exactly: a security-relevant string filter builds an allowlist from a special-syntax mini-language (regex character classes / shell flags) but fails to account for a "combined"/meta form of that syntax (`^` negation / combined POSIX flags), so validation content that should have been checked is instead silently bypassed.

The validation-time counterpart in `formula/validation.js` only checks activation MCI and evaluates the operand expressions; it performs no compile-time inspection of the character-class content either: [2](#0-1) 

So there is no separate guard elsewhere in the pipeline that would catch this at parse/validation time — the flaw is purely in the runtime regex construction in `evaluation.js`.

### Impact Explanation
`has_only` is a general-purpose oscript function available to any AA author and evaluated against values that ultimately originate from AA trigger data, state variables, or other AA-controlled inputs (see grammar entries wiring `has_only` into the language: [3](#0-2) ). AAs commonly use `has_only` as an input-sanitization gate before using a value in a security-sensitive way (e.g., accepting only alphanumeric identifiers, restricting characters in an address/asset/state-key derived from `trigger.data`, or gating whether funds/state updates proceed). If the character set passed to `has_only` is influenced, directly or indirectly, by a trigger sender (e.g., an AA that validates part of `trigger.data` against another part of `trigger.data`, or that concatenates a fixed prefix with attacker data before calling `has_only`), an attacker can inject a leading `^` to make the "allowed characters" check accept unrestricted data. Because AA logic (fund release, state transitions, freezing conditions) frequently branches on the result of such checks, this can lead to AA fund loss, bypassing of intended state/asset key restrictions, or freezing/incorrect state transitions in AAs that rely on `has_only` as a security boundary. All full nodes evaluate the same formula deterministically, so this does not by itself create consensus disagreement, but it does allow spending/logic bypass in any AA that depends on this allowlist behaving as documented.

### Likelihood Explanation
The bug is trivial to trigger for anyone who can (a) author an AA using `has_only` with an attacker-influenced character set, or (b) send a trigger to an already-deployed AA that passes attacker-controllable data into the "chars" argument of `has_only` (directly or via string concatenation). No special privileges are needed — a single crafted trigger unit posted by any user is sufficient to exploit an AA that has this pattern. The likelihood of exploitation therefore hinges on how common this `has_only` usage pattern is among deployed AAs, but the underlying primitive (character-class allowlist silently invertible via `^`) is unconditionally present in the `ocore` formula engine for every full node.

### Recommendation
In the `has_only` handler in `formula/evaluation.js`, reject or escape a leading `^` in `sub` the same way `]` is already escaped, e.g. treat `^` as a literal by escaping it (`sub.replace(/^\^/, '\\^')` or reject it as an "invalid character group" like the existing `\]`/trailing-`\` checks), and audit for any other regex metacharacters (`-` ranges, `\d`/`\w` are intentionally supported per existing tests, but should be documented/whitelisted) that could similarly change the semantics of the constructed character class beyond simple literal-character allowlisting.

### Proof of Concept
Within an AA (illustrative oscript), assuming `has_only` is used to gate on trigger-supplied "allowed characters" (or any AA pattern where the second argument incorporates trigger data):
```
{
  bounce_fees: {base: 10000},
  messages: [{
    app: 'state',
    state: "{
      $ok = has_only(trigger.data.value, trigger.data.charset);
      if ($ok) {
        // security-sensitive branch, e.g., release funds / update sensitive state
      }
    }"
  }]
}
```
An attacker posts a trigger unit with:
```
trigger.data = { value: "<anything, arbitrary length/content>", charset: "^" }
```
`has_only` compiles the regex `/^[^]*$/`, which matches the entirely attacker-controlled `trigger.data.value` regardless of its content, so `$ok` evaluates to `true` even though the AA author intended `has_only` to restrict `value` to a narrow, safe character set (e.g. `"a-zA-Z0-9"`).
