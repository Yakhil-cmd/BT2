### Title
Unvalidated Peer-Supplied Staking Info Written to DB During Fast Sync Corrupts Reward Distribution — (`File: datasync/downloader/queue.go`)

### Summary
During fast sync, staking information received from a remote peer is written to the local database without any content validation. The `DeliverStakingInfos` validate callback is an explicit no-op (`// TODO-Kaia-Snapsync update validation logic`), meaning a malicious peer can inject arbitrary `RewardAddrs`, `StakingAmounts`, and fund addresses (`KEFAddr`/`KIFAddr`/`KPFAddr`) into the node's staking DB. This corrupted data is subsequently used for block reward distribution calculations, enabling reward redirection and potential consensus divergence.

### Finding Description

The `DeliverStakingInfos` function in `datasync/downloader/queue.go` registers a `validate` callback that unconditionally returns `nil`: [1](#0-0) 

Unlike receipts — which are validated against `header.ReceiptHash` via `types.DeriveReceiptsRoot` — staking info has no analogous commitment in the block header that is checked at delivery time. The peer-supplied `P2PStakingInfo` struct is accepted as-is and stored via `PutStakingInfoToDB`: [2](#0-1) 

The same unchecked write occurs in the `SyncStakingInfo` admin-triggered recovery path: [3](#0-2) 

The only check performed is that `stakingInfo.BlockNum` matches the expected block number — the *content* (validator node IDs, staking contracts, reward addresses, staking amounts, fund addresses) is never verified against the canonical state root committed in the block header.

The staking info stored in the DB is later consumed by `GetBlockReward` to compute reward splits among validators, proposer, and treasury funds: [4](#0-3) 

And by `assignStakingRewards` which reads `RewardAddrs` directly from the staking info to determine where KAIA flows: [5](#0-4) 

### Impact Explanation

A malicious fast-sync peer can supply staking info with:
- Attacker-controlled `RewardAddrs` replacing legitimate validator reward addresses
- Inflated or zeroed `StakingAmounts` distorting proportional reward splits
- Attacker-controlled `KEFAddr`/`KIFAddr`/`KPFAddr` redirecting treasury fund distributions

For pre-Kaia-fork blocks (where staking info is sourced from DB, not re-derived from state), the node will compute incorrect reward distributions. When the node later acts as a proposer, it will produce blocks with a state root that diverges from the canonical chain — causing consensus divergence on the affected honest node. Additionally, any reward payments computed using the corrupted staking info will credit wrong addresses.

### Likelihood Explanation

Fast sync is a standard sync mode used by new or recovering nodes. Any peer the syncing node connects to can supply staking info responses. The missing validation is explicitly marked as a TODO, confirming it is a known gap rather than an intentional design choice. No cryptographic or hash-based guard exists to detect content tampering.

### Recommendation

Implement content validation in the `DeliverStakingInfos` validate callback. After fast sync completes and the state trie is available, re-derive staking info from the AddressBook contract state at each staking interval block and compare against the DB-stored values. Alternatively, include a commitment to the staking info (e.g., a hash of the serialized `StakingInfo`) in the block header so it can be verified at delivery time, analogous to `header.ReceiptHash` for receipts.

### Proof of Concept

1. Operator starts a node in fast sync mode.
2. Attacker operates a peer that responds to `StakingInfoRequestMsg` with crafted `P2PStakingInfo` entries where `RewardAddrs[i]` is replaced with attacker-controlled addresses.
3. The syncing node's `handleStakingInfoMsg` → `DeliverStakingInfos` → `commitFastSyncData` path writes the crafted entries to DB via `PutStakingInfoToDB` with no content check.
4. After sync completes, when the node processes new blocks, `GetStakingInfo` returns the corrupted DB entries for pre-Kaia blocks.
5. `assignStakingRewards` distributes KAIA to the attacker's addresses instead of legitimate validator reward addresses.
6. The node's proposed blocks carry a state root reflecting these wrong transfers, causing rejection by honest peers and consensus divergence. [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8)

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining

// handleStakingInfoMsg handles staking information response message.
func handleStakingInfoMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
	if pm.chainconfig.Istanbul == nil || pm.chainconfig.Istanbul.ProposerPolicy != uint64(istanbul.WeightedRandom) {
		return errResp(ErrUnsupportedEnginePolicy, "the engine is not istanbul or the policy is not weighted random")
	}

	// A batch of stakingInfos arrived to one of our previous requests
	var stakingInfos []*staking.P2PStakingInfo
	if err := msg.Decode(&stakingInfos); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	// Deliver all to the downloader
	if err := pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos); err != nil {
		logger.Debug("Failed to deliver staking information", "err", err)
	}
	return nil
