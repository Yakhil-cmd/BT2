### Title
Cross-organization repository substitution in webhook handlers due to missing binding between verified `repository.owner.login` and `repository.full_name` - ([File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub organization named in `payload['repository']['owner']['login']`/`payload['organization']['login']`, using that organization's `webhook_secret` via `Shipit.github(organization: repository_owner)`. Every handler (`Handler#stacks`/`repository_name`, and each `PullRequest::*Handler#repository`) independently resolves the target `Repository`/`Stack` from `payload['repository']['full_name']` (or `params.repository.full_name`) via `Repository.from_github_repo_name`, with no check that this repository actually belongs to the verified organization.

### Finding Description
The broken binding is: **organization used to verify the HMAC signature (`repository_owner` in `WebhooksController#verify_signature`) == owner of the repository resolved for mutation (`Repository.from_github_repo_name(repository_name).owner`)**. This equality is never asserted anywhere in the request path.

Code path:
- `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_body)`. [1](#0-0) 
- `Shipit#github` looks up a per-organization config/secret (`github_app_config(organization)`) in multi-org deployments, each with its own independent `webhook_secret`. [2](#0-1) 
- `GitHubApp#verify_webhook_signature` computes the HMAC purely over the raw request body using that organization's own `webhook_secret` — it never inspects or constrains other fields of the JSON body, including `repository.full_name`. [3](#0-2) 
- Once verification passes, `WebhooksController#create` dispatches the full parsed body to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 
- `Handler#stacks` resolves the repository purely from `payload.dig('repository', 'full_name')`, downcased and split on `/`, with no reference to `repository_owner`/verified org: [5](#0-4) 
- `Repository.from_github_repo_name` performs a bare `find_by(owner:, name:)` lookup with no ownership/org check. [6](#0-5) 
- All `PullRequest::*Handler` subclasses (`AssignedHandler`, `ClosedHandler`, `EditedHandler`, `LabeledHandler`, `LabelCapturingHandler`, `ReopenedHandler`) repeat the identical unchecked pattern: `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. [7](#0-6) 

Exploit flow: In a multi-org Shipit instance (`config/secrets.yml` keyed per GitHub org, as documented in `docs/setup.md:182-209` and exercised by `test/dummy/config/secrets_double_github_app.yml`), an attacker who legitimately owns/administers a repository under `attacker-org` (a real, already-onboarded Shipit tenant) knows `attacker-org`'s `webhook_secret` (they configured it themselves in that org's GitHub App/webhook settings, or can trigger genuine deliveries and observe/compute a valid signature since they control the source repo delivering it). They construct a webhook body where `repository.owner.login = "attacker-org"` (so the request passes `verify_signature`, signed with the attacker's own known secret) but `repository.full_name = "VICTIM-ORG/victim-repo"`. The HMAC is computed over the raw body chosen entirely by the attacker, so this divergence is trivial to embed. The handler layer never checks that `full_name`'s owner matches the verified `repository_owner`, so `Repository.from_github_repo_name("VICTIM-ORG/victim-repo")` resolves the real victim `Repository`/`Stack`, and the handler (e.g. `PushHandler` enqueuing `GithubSyncJob`, `LabeledHandler` archiving/unarchiving a review stack, `ClosedHandler` archiving a review stack, `AssignedHandler`/`EditedHandler`/`ReopenedHandler` mutating a victim `PullRequest`) acts on the victim's data.

Existing guards fail because: `verify_signature` only proves "this request was signed for org X", not "every repository reference inside this payload belongs to org X"; `drop_unhandled_event` only filters by event type; `ExplicitParameters` schemas only validate field presence/types, not cross-field/org consistency; and `Repository.from_github_repo_name`/`Stack` scopes contain no organization/tenant check.

### Impact Explanation
An attacker who administers one legitimate, already-configured GitHub organization/tenant on a shared multi-tenant Shipit instance can forge webhook events that mutate any other tenant's `Stack`/`PullRequest`/`ReviewStack` state — e.g. triggering `GithubSyncJob` (push handler), archiving/unarchiving review stacks via label or close/reopen handlers, or updating a victim's `PullRequest#github_pull_request`/labels — without ever authenticating against the victim organization's own webhook secret. This is a genuine cross-tenant write ("a payload for one repository mutating another's stack ... or task"), matching the Critical severity category, and is repeatable against any repository name the attacker can guess/enumerate, since `Repository.from_github_repo_name` performs no per-request rate limiting or ownership assertion.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (single-org deployments have only one `webhook_secret`, collapsing the "victim org" and "attacker org" into the same secret domain, so the equality trivially holds); (2) attacker administers/controls a repository under one legitimate configured org (a realistic scenario for shared internal or vendor-hosted Shipit instances serving multiple business units/customers); (3) knowledge of that org's own `webhook_secret`, which the attacker's own org naturally has since they configure their own GitHub App/webhook. Given these (common, sanctioned) preconditions, exploitation cost is a single crafted HTTP POST with a valid HMAC computed from a secret the attacker legitimately possesses — trivial and fully repeatable.

### Recommendation
In `Handler#stacks`/`repository_name` (and each `PullRequest::*Handler#repository`), require that the resolved `Repository#owner` matches the verified `repository_owner`/organization the request was authenticated against — e.g. pass the verified organization into `Handler.call`/`initialize` and assert `repository.owner == verified_organization.downcase` before returning any `stacks`/`repository`, short-circuiting to `Stack.none`/`NullRepository` otherwise.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
