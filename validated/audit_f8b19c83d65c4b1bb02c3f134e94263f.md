### Title
Tokens transferred directly to the pool are permanently locked — no skim or recovery path exists - ([File: contracts/pool/src/lib.rs](contracts/pool/src/lib.rs))

### Summary
The pool contract keeps an internal `cash` ledger per `(hub_id, asset)` market and never reconciles it against the real SAC balance except inside `flash_loan`. Any token amount pushed to the pool address outside a measured protocol flow becomes unbooked surplus that no entrypoint — public or owner-only, reached through any controller path — can ever return to the sender or to anyone else. There is no `skim`/`sweep` analogue.

### Finding Description
Per `contracts/pool/README.md`, every state-mutating pool entrypoint is `#[only_owner]` (the controller) and credits or debits the `cash` book on the controller's word. The README states explicitly: "`supply`, `repay` and `recapitalize` all credit `cash` on the controller's word, without verifying the transfer. `cash` is a bookkeeping number. The only reconciliation against a real `token.balance()` is in `flash_loan`, which checks it three times with strict equality." The threat model confirms "Direct donations do not rewrite those books" (`docs/explanation/threat-model.md`).

All outbound token movements are bounded by the book, not the balance:

- `withdraw`, `borrow`, `claim_revenue` pay out only against booked `cash`/shares.
- `repay` and `recapitalize` refunds are computed from `transfer_amount_measured` — the balance delta *during the call* (`tests/test-harness/tests/controller/outbound_transfer_measurement.rs`: "The refund basis is `received`, the pool's measured balance delta"). A pre-existing surplus contributes nothing to `received`, so `controller.recapitalize(payer, key, donation_amount)` measures zero receipt and refunds zero — a user cannot use it to claw back a mistaken direct transfer. This is pinned by `contracts/pool/tests/flows.rs::test_recapitalize_refunds_everything_when_market_is_already_backed`, which shows the refund only works because the transfer happened immediately before the measured call.
- The controller rejects `borrow`/`withdraw` recipients equal to the pool or controller address (`tests/test-harness/tests/controller/recipient_is_protocol_contract.rs`), closing the "send it back via a leg" escape.
- Unlike `swap-aggregator`, which has `sweep_balance` for stray tokens (`contracts/swap-aggregator/tests/unit/sweep.rs`), the pool ABI lists no such function — its fourteen entrypoints are enumerated in the README and none moves unbooked tokens.

Since `cash` is only ever incremented by measured receipts and decremented by booked payouts, the surplus `token.balance(pool) - cash` grows permanently inaccessible.

### Impact Explanation
Permanent freezing of funds: any user who calls `token.transfer(user, pool, amount)` directly (a listed reachable path), or whose tokens are pushed to the pool by a third party (e.g., Aquarius reward pushes noted in the threat model), loses them irrevocably. The tokens sit in custody that no code path can spend — not by the sender, not by suppliers (the book doesn't credit them), not by governance (no sweep operation exists in `governance/op.rs` for pool balances). A secondary effect: `flash_loan`'s strict-equality balance checks mean a donation makes the book and balance disagree, which can interfere with the one place that does reconcile.

### Likelihood Explanation
Requires a user error (direct transfer to the pool contract instead of a controller `supply`/`repay` call) or an external push of tokens to the pool. Front-ends mitigate but cannot eliminate this; the threat model itself documents that third parties can push rewards into the pool address unbooked. The loss is unbounded per incident but each incident is self-inflicted, matching the original report's Medium rating.

### Recommendation
Add a `skim`/`sweep` entrypoint to the pool that transfers `token.balance(pool) - total_booked_cash(asset)` for a listed asset (and the full balance for unlisted assets) to a governance-controlled address, callable by anyone; or route recovery through the controller with the same balance-minus-book computation. Alternatively, document and enforce at the controller level that unbooked surplus is donated to the insurance/revenue balance by crediting it via `seize_positions`-style accounting rather than leaving it stranded.

### Proof of Concept
```rust
// Pool-level (contracts/pool/tests/flows.rs style):
let t = TestSetup::new();
let token = token::Client::new(&t.env, &t.asset);
let user = Address::generate(&t.env);
token_admin.mint(&user, &1_000_000);

// User mistakenly transfers directly to the pool contract.
token.transfer(&user, &t.pool, &1_000_000);
assert_eq!(token.balance(&t.pool), custody_before + 1_000_000);
assert_eq!(t.state_snapshot().cash, cash_before); // book unchanged

// Recovery attempt 1: controller.recapitalize measures delta == 0 → refunds 0.
// Recovery attempt 2: no skim/sweep entrypoint exists on pool or controller.
// Recovery attempt 3: withdraw/borrow pay out only booked cash.
// Result: 1_000_000 units permanently locked; token.balance(pool) > cash forever.
```
