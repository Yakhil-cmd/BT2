### Title
Unbounded memory/CPU consumption via oversized DSSE envelope Payload during attestation statement parsing - ([File: pkg/cmd/release/shared/attestation.go])

### Summary
`FilterAttestationsByTag` and `FilterAttestationsByFileDigest` call `protojson.Unmarshal` directly on the DSSE envelope `Payload` string taken from an attestation bundle fetched from the GitHub API (or an external bundle URL / attacker-controlled host), with no size or complexity limit enforced anywhere in the fetch or filter path. An attacker who controls the repository's attestation data (or the host the victim points `gh` at) can supply an arbitrarily large or deeply nested payload, causing the victim's `gh` process to consume excessive memory/CPU while unmarshalling.

### Finding Description
The call chain is `verifyRun` → `config.AttClient.GetByDigest` → `shared.FilterAttestationsByTag`/`FilterAttestationsByFileDigest`: [1](#0-0) 

`GetByDigest` fetches attestation metadata via `getAttestations` (through `githubApiClient.RESTWithNext`) and then resolves each attestation's actual bundle via `fetchBundleFromAttestations`/`getBundle`, which reads the entire HTTP response body with `io.ReadAll(resp.Body)` (no `io.LimitReader`/`http.MaxBytesReader`), snappy-decompresses it, and `protojson.Unmarshal`s it into a `v1.Bundle`: [2](#0-1) 

The resulting `Bundle`'s DSSE envelope `Payload` (attacker-controlled content, ultimately base64-decoded JSON) is then fed again into `protojson.Unmarshal` with no length check in the filter functions: [3](#0-2) [4](#0-3) 

No allowlist, safeurl restriction, or content-length/size validation stops the size of the fetched bundle body or the decoded `Payload` string before it reaches `protojson.Unmarshal`. The only bounds present in the codebase are on the *number* of attestations fetched (`maxLimitForFlag = 1000`, `maxLimitForFetch = 100`), not on the size of any individual bundle or payload: [5](#0-4) 

### Impact Explanation
This is a client-side (victim-machine) resource-exhaustion/DoS issue: a maliciously large or deeply nested JSON payload can cause excessive memory allocation and CPU time in the `gh` process during `gh release verify` / `gh attestation verify`, potentially causing the process to hang or be OOM-killed. This maps to the "unbounded resource consumption" impact class, not to code execution, credential leakage, or file write, since `protojson.Unmarshal` failures are handled and simply return an error.

### Likelihood Explanation
Exploitability requires the attacker to control the content served for attestation bundles — either by attaching a bundle whose `BundleURL` points to attacker-controlled storage, or by controlling the API host itself (e.g., victim configured `gh` against a GHES-like/attacker host). For a standard github.com repo, the real bundle URL and body are ultimately served by GitHub's storage/API, which likely enforces its own size limits server-side; those are outside this codebase's control and not verifiable here. So realistic exploitation is essentially limited to the explicitly-allowed "attacker controls host" precondition, making this a low-severity, host-dependent DoS rather than a broadly exploitable issue against ordinary GitHub-hosted repos.

### Recommendation
- Apply `http.MaxBytesReader` or wrap `resp.Body` in `io.LimitReader` with a sane cap (e.g., a few MB) before `io.ReadAll` in `getBundle`.
- Validate/cap the length of `att.Bundle.Bundle.GetDsseEnvelope().Payload` before calling `protojson.Unmarshal` in `FilterAttestationsByTag`/`FilterAttestationsByFileDigest`.
- Consider using a streaming JSON decoder with a depth/size limit, or set `protojson.UnmarshalOptions` guarded by pre-validated size bounds.

### Proof of Concept
Go test plan (httpmock-based):
1. Stub `attClient.GetByDigest` (or the underlying `externalHttpClient.Get` for the bundle URL) to return an `api.Attestation` whose `Bundle.Bundle.DsseEnvelope.Payload` is a multi-hundred-MB (or deeply nested) base64/JSON string.
2. Call `shared.FilterAttestationsByTag(attestations, tagName)` directly and measure process RSS/time via `runtime.ReadMemStats` before/after, asserting memory growth stays under a fixed threshold (e.g., 10MB) and the call returns within a bounded time (e.g., 1s), which currently would fail without a size limit.
3. Repeat for `getBundle` in `pkg/cmd/attestation/api/client.go` with an oversized HTTP response body from an `httptest.Server`, asserting the read is capped rather than fully buffered.

func FilterAttestationsByTag(attestations []*api.Attestation, tagName string) ([]*api.Attestation, error) {
	var filtered []*api.Attestation
	for _, att := range attestations {
		statement := att.Bundle.Bundle.GetDsseEnvelope().Payload
		var statementData v1.Statement
		err := protojson.Unmarshal([]byte(statement), &statementData)
		if err != nil {
			return nil, fmt.Errorf("failed to unmarshal statement: %w", err)
		}
		tagValue := statementData.Predicate.GetFields()["tag"].GetStringValue()

		if tagValue == tagName {
			filtered = append(filtered, att)
		}
	}
	return filtered, nil
}

func FilterAttestationsByFileDigest(attestations []*api.Attestation, fileDigest string) ([]*api.Attestation, error) {
	var filtered []*api.Attestation
	for _, att := range attestations {
		statement := att.Bundle.Bundle.GetDsseEnvelope().Payload
		var statementData v1.Statement
		err := protojson.Unmarshal([]byte(statement), &statementData)

		if err != nil {
			return nil, fmt.Errorf("failed to unmarshal statement: %w", err)
		}
		subjects := statementData.Subject
		for _, subject := range subjects {
			digestMap := subject.GetDigest()
			alg := "sha256"

			digest := digestMap[alg]
			if digest == fileDigest {
				filtered = append(filtered, att)
			}
		}

	}
	return filtered, nil
}
