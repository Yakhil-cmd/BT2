Based on my research, I found a clear analog to the `MIN_GNS_WEI_IN` rounding-to-zero bug in `earned_headers_commission_recipients` handling: a unit author can specify a share (as low as 1 out of 100) that, when applied against small full commission amounts via `Math.round(full_amount * share / 100.0)` in `headers_commission.js`, can round down to zero, silently losing (burning) the commission for that recipient instead of it being validly credited — while the total was already deducted/attributed as paid.

### Title
Rounding to zero in `earned_headers_commission_recipients` share distribution causes header-commission funds to be lost - (File: `headers_commission.js`)

### Summary
`validateHeadersCommissionRecipients` in `validation.js` only enforces that recipient shares are positive integers summing to 100, with no minimum share threshold. When headers-commission payouts are later aggregated in `calcHeadersCommissions`/`buildPaidWitnessesForMainChainIndex`-style logic, each recipient's payout is computed as `Math.round(full_amount * share / 100.0)`. For small `full_amount` (headers commission is often a small number of bytes) combined with a small `share` (e.g., 1%), the rounded result is 0, so that recipient (and, in effect, that portion of the commission) is never inserted into `headers_commission_contributions`/`headers_commission_outputs`. The value is neither burned in a tracked way nor paid — it simply disappears from the accounting, all while the parent unit's `headers_commission` field records the full amount as paid out under a specific unit/child, i.e. spendable funds "vanish" without being credited to any address.

### Finding Description
`validateHeadersCommissionRecipients` (`validation.js:1101-1126`) validates:
```
if (!isPositiveInteger(recipient.earned_headers_commission_share))
    return cb("earned_headers_commission_share must be positive integer");
...
if (total_earned_headers_commission_share !== 100)
    return cb("sum of earned_headers_commission_share is not 100");
``` [1](#0-0) 
There is no lower bound preventing a share such as `1` (1%) from being specified by a co-author who is entitled to earn headers commission, and no check ensuring that `1% * full_amount` rounds to a nonzero value.

Distribution then happens with:
```
var amount = Math.round(full_amount * share / 100.0);
``` [2](#0-1) 
and, for the SQL/consensus path:
```
var amount = (row.earned_headers_commission_share === 100)
    ? full_amount
    : Math.round(full_amount * row.earned_headers_commission_share / 100.0);
``` [3](#0-2) 

Because `full_amount` here is a single parent unit's `headers_commission` — commonly a small integer number of bytes — a recipient with a low share percentage can legitimately receive `0` after rounding. This mirrors the `MIN_GNS_WEI_IN` bug exactly: a validated minimum ("positive integer" share, analogous to `MIN_GNS_WEI_IN`) is set too permissively, so the downstream proportional-distribution arithmetic silently truncates to zero, and the corresponding value is lost rather than credited to anyone.

### Impact Explanation
Any unpaid/lost commission portion represents byte-funds that are permanently unspendable by any address — a form of fund loss/freezing analogous to the original finding ("transferred tokens not being recorded as rewards"). While each individual occurrence is small (a few bytes per rounding event), this is systemic: any multi-author unit (or unit with `earned_headers_commission_recipients` set) that intentionally or accidentally uses small percentage shares on small commission amounts will lose commission dust on every affected parent unit across the network's lifetime. This affects consensus-level accounting of spendable header-commission outputs (`headers_commission_outputs`), a network-wide resource, not merely a private balance.

### Likelihood Explanation
Likelihood is medium: any single- or multi-authored unit author can freely set `earned_headers_commission_recipients` with shares like `1` for one address and `99` for another (fully valid per `validateHeadersCommissionRecipients`), and headers-commission amounts per parent unit are frequently small (a handful of bytes), making the rounding-to-zero condition easy to trigger deliberately or incidentally. This requires no special privilege — any unit-posting author with multiple co-authors can configure it.

### Recommendation
Add a floor to `validateHeadersCommissionRecipients` (or to the distribution logic) that rejects/refuses shares which, combined with plausible/actual commission sizes, would round to zero — e.g., either require a minimum `earned_headers_commission_share` (analogous to raising `MIN_GNS_WEI_IN`) or change the distribution algorithm to allocate remainders (e.g., largest-remainder method) instead of independently rounding each recipient's cut, ensuring `sum(amount) === full_amount` and no recipient legitimately entitled to a nonzero share receives 0.

### Proof of Concept
1. Two co-authors create a unit with `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 1}, {address: B, earned_headers_commission_share: 99}]` — this passes `validateHeadersCommissionRecipients` because shares are positive integers summing to 100. [4](#0-3) 
2. This unit later wins headers commission from a parent unit whose `headers_commission` is small (e.g., 50 bytes, common for lightweight units).
3. During `calcHeadersCommissions`, address A's share is computed as `Math.round(50 * 1 / 100) = Math.round(0.5) = 0` (or for smaller amounts, strictly `0`), so address A's row is either omitted or inserted with `amount=0`, while `full_amount` was already fully attributed as paid header commission for that parent-unit/child pairing. [5](#0-4) 
4. The lost fraction is never added to `headers_commission_outputs` for any address — it disappears from circulation permanently, matching the "transferred but not recorded" pattern from the external report.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
