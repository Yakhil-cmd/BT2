### Title
Webhook signature verification keys off an attacker-supplied `repository.owner.login` while handlers act on the independently attacker-supplied `repository.full_name`, allowing forged events against any tracked repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to validate the HMAC signature against using a value pulled straight out of the *unauthenticated* JSON body: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` in turn treats a missing/blank `webhook_secret` for that organization as automatic success: [3](#0-2) 

Meanwhile, once the signature check passes (trivially, for any org with no configured `webhook_secret`), the *entire raw, unauthenticated* payload is dispatched unchanged to the event handlers: [4](#0-3) 

The handlers determine which `Stack`/`Repository` to act on using a *different* field of the same untrusted payload — `repository.full_name` — with no cross-check against the `repository.owner.login` that was used for the signature/org lookup: [5](#0-4) [6](#0-5) 

This breaks the equality that should hold: `organization used to authenticate the webhook == organization owning the repository that is acted upon`. Because `repository.owner.login` and `repository.full_name` are two independently attacker-controlled JSON fields in the same unsigned/mis-keyed request, an attacker can pick an organization for signature purposes that has no `webhook_secret` configured (a documented, supported configuration state — see `webhook_secret: # nil` in `docs/setup.md` and `config/secrets.development.shopify.yml`), while pointing `repository.full_name` at a genuinely tracked repository belonging to a *different*, properly-secured organization.

### Impact Explanation
An attacker who knows (a) that some organization configured in `Shipit.github` has no `webhook_secret` set, and (b) the `owner/repo` full name of a real tracked stack, can forge arbitrary GitHub events for that stack without ever possessing the real webhook secret, an API token, or repository write access. For the `push` event this reaches `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen SHA — forcing the stack to treat an arbitrary, attacker-chosen commit as the new head to sync/deploy candidate. For the `status` event, `StatusHandler#process` lets the attacker inject arbitrary CI/check statuses (`state`, `context`, `target_url`) onto any existing commit by SHA, which can satisfy required-status gating used to authorize deploys. This crosses the "unauthenticated write to stack state / unauthorized deploy trigger" boundary called out as in-scope impact.

### Likelihood Explanation
Requires only knowledge of a misconfigured (secret-less) organization entry in `Shipit.github` config and the target repository's full name — both plausible in real multi-org deployments (the shipped example configs explicitly show `webhook_secret: # nil` as a supported/expected value), and no privileged credentials, session, or repository access are needed. The endpoint is unauthenticated by design (it's the GitHub webhook receiver).

### Recommendation
Bind the signature-verification organization to the same value the handler will act on, and reject if they diverge: derive `repository_owner` and the handler's `repository_name` from the same parsed field, and additionally verify that `repository.full_name.split('/').first == repository_owner` before dispatching to handlers. Do not allow `verify_webhook_signature` to short-circuit to `true` for an organization lacking a `webhook_secret` unless that organization is also confirmed to own the target repository; consider making `webhook_secret` mandatory for any organization with tracked stacks.

### Proof of Concept
1. In `Shipit.github`, org `no-secret-org` is configured with `webhook_secret: nil` (supported per `docs/setup.md`), while org `victim-org` has a `victim-org/victim-repo` stack with `webhook_secret` set.
2. Attacker POSTs to the webhooks endpoint with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": {"login": "no-secret-org"},
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/master",
  "after": "deadbeefattackerchosen sha"
}
```
3. `verify_signature` calls `Shipit.github(organization: "no-secret-org")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured), skipping HMAC validation entirely regardless of `X-Hub-Signature`. [7](#0-6) 
4. `create` dispatches the untouched payload to `PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the real victim stack. [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
