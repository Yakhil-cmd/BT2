### Title
Missing replay/nonce protection in `is_valid_signed_package()` allows unlimited reuse of an off-chain signed message to repeatedly authorize AA fund transfers - (File: `formula/evaluation.js`, `signed_message.js`)

### Summary
The oscript primitive `is_valid_signed_package()`, backed by `signed_message.validateSignedMessage()`, only verifies that a `signed_package` object carries a valid signature from a claimed address (and, if network-aware, that its `last_ball_unit` is stable and not from the future). It performs no bookkeeping to mark a signed package as "consumed." Any Autonomous Agent (AA) that uses this primitive to authorize a stateful action (fund release, debt reduction, balance transfer) based on an off-chain-signed message is vulnerable to the exact same class of bug as Community.sol's `escrow()`: the same `_data`/signature pair can be replayed across many separate trigger units to repeat the authorized action, unless the AA author manually implements a nonce/sequence check in its own state variables.

### Finding Description
`is_valid_signed_package` in the formula evaluator decodes a `signed_message` object, checks basic structural constraints, optionally validates `last_ball_unit` freshness, and then delegates to `signed_message.validateSignedMessage()`, which checks the signature against the definition of the supplied address [1](#0-0) . Crucially, this validation is stateless with respect to the AA: it never checks whether this exact `signed_package` (message + signature) has already been used to trigger a state change in this AA before. `validateSignedMessage` itself only checks the signature, definition and (optionally) last-ball freshness of the package - it does not track or invalidate previously-seen packages [2](#0-1) .

Because oscript/AA execution is triggered by ordinary units posted to the DAG (each unit is unique, but the `trigger.data` payload it carries, including an embedded `signed_package`, can be copy-pasted into any number of separate units by anyone holding it), an attacker holding a validly-signed package can submit it inside many different trigger units. Every one of those triggers will re-evaluate `is_valid_signed_package()` as `true`, since nothing in the primitive itself binds the check to "first use only."

This is precisely the missing-nonce class from the Community.escrow bug: there, the signed `_data`/`_signature` pair lacked a nonce field, so calling `escrow()` repeatedly with the same signed payload kept reducing debt. In ocore, the analogous defense (a nonce/period counter) is not provided by the platform primitive at all - it must be implemented entirely by the AA author using `var[...]` state, exactly as shown in the reference `payment_channels.oscript` template, which defends itself only by checking `trigger.data.sentByPeer.signed_message.period == var['period']` before honoring the signed package [3](#0-2) . Any AA that omits an equivalent explicit state-based nonce/sequence check when consuming `is_valid_signed_package()` inherits the full replay vulnerability, with the platform providing no safety net.

### Impact Explanation
Any AA (deployed by any user, unprivileged) that uses `is_valid_signed_package()` to gate a fund-moving or debt/balance-adjusting `state` block without independently tracking consumption (e.g., a `var['nonce']`/`var['period']` field) can be drained or manipulated by repeatedly submitting the same signed package in new trigger units. This directly leads to AA fund loss: an attacker can trigger the same authorized transfer/reduction an unbounded number of times using a single valid signature, exactly mirroring the code4rena H-03 finding, but at the level of the oscript/AA execution engine that ocore ships and that third-party AA authors build upon.

### Likelihood Explanation
Likelihood is high in practice because:
- The primitive is fully unprivileged: any account can send a trigger unit to any AA, and the `trigger.data` (including a copied `signed_package`) is fully attacker-controlled.
- The platform documentation/reference implementation (`payment_channels.oscript`) explicitly demonstrates that a manual `period`/nonce check is *required* to prevent exactly this replay scenario, which strongly implies this is a well-known but easy-to-miss pitfall for AA authors, not a hardened default.
- No AA-independent mechanism exists in `formula/evaluation.js` or `signed_message.js` to reject a previously-used signed package.

### Recommendation
- Add an optional platform-level, per-AA-address consumption tracking mechanism for signed packages (e.g., allow `is_valid_signed_package` to accept/require a caller-supplied nonce and internally track "first use" per address+nonce+AA, similar to what the diff in the original finding added to `ProjectDetails`), so that AA authors are not solely responsible for reimplementing replay protection.
- At minimum, update documentation/reference oscript templates to make explicit, in bold, that every AA using `is_valid_signed_package()`/`signed_message` for authorizing state changes MUST embed and check an application-level nonce/sequence field inside the signed message content, and validate it against AA state before acting on it.
- Consider adding a lint/static-analysis warning during AA validation (`formula/validation.js`) when `is_valid_signed_package` is used to gate a `payment` or balance-decrementing `state` message without any accompanying `var[...]` comparison against a field inside `signed_message`.

### Proof of Concept
1. Deploy an AA whose `state` code contains something like the (insufficiently protected) pattern:
   ```
   if (trigger.data.sentByPeer AND is_valid_signed_package(trigger.data.sentByPeer, counterparty_address)) {
       $amount = trigger.data.sentByPeer.signed_message.amount_spent;
       var['balance'] -= $amount;
       // ... pays out $amount ...
   }
   ```
   without checking any nonce/period field against a `var[...]` counter (i.e., omitting the protection that the shipped `payment_channels.oscript` template applies via `var['period']`, see [3](#0-2) ).
2. The counterparty signs one `signed_message` (e.g., `{channel, amount_spent: 5000}`) once, producing a `signed_package` with a valid signature.
3. The attacker, who has legitimate possession of this signed package (e.g., received it once as intended), submits it as `trigger.data.sentByPeer` in a new trigger unit. `is_valid_signed_package()` returns `true` (per `formula/evaluation.js` lines 1666-1699) since it only re-verifies the signature/freshness, not prior use.
4. The attacker resubmits the identical `trigger.data.sentByPeer` payload in additional, distinct trigger units. Each time, `is_valid_signed_package()` again returns `true`, and the AA repeats the payout/decrement, because no nonce check exists in the primitive itself.
5. Repeat until the AA's balance is drained, analogous to the Community.escrow debt-reduction replay. [4](#0-3) [2](#0-1) [3](#0-2)
