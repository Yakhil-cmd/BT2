### Title
`supply_index_reward_shortfall` can panic when half-up rounding makes distributed rewards exceed accrued rewards, freezing the market - (File: common/src/rates/index.rs)

### Summary
The streebog bug class is an internal update function that produces an incorrect result or a panic for specific inputs. The analog here is `supply_index_reward_shortfall` in `common/src/rates/index.rs:53-64`, which is invoked on every accrual step by `accrue_step` (`common/src/rates/simulate.rs:72-78`) and therefore by `global_sync`/`accrue_chunk` (`contracts/pool/src/interest.rs:20-53`), which runs before every mutating pool operation. For certain `(supplied, old_index, rewards_increase)` triples it computes `distributed > rewards_increase` purely due to half-up rounding, and the `checked_sub` panics with `MathOverflow`, reverting the accrual — permanently freezing repay, withdraw, borrow, liquidation, and flash paths on that market.

### Finding Description
`update_supply_index` computes the grown index as `floor((hup(supplied*old_index) + rewards) * RAY / supplied)` (`common/src/rates/index.rs:34-44`). The shortfall helper then computes:

```rust
let distributed = supplied.mul(env, new_index)
    .checked_sub(env, supplied.mul(env, old_index));
rewards_increase.checked_sub(env, distributed)
```

Both `mul` calls round **half up**. Algebraically:

- `supplied*new_index ≤ hup(supplied*old_index) + rewards_increase ≤ supplied*old_index + rewards_increase + 0.5`
- `hup(s*new) − hup(s*old) ≤ (s*new + 0.5) − (s*old − 0.5) ≤ rewards_increase + 1.5`, i.e. `distributed` can equal `rewards_increase + 1` (raw unit) when the two half-up roundings align adversarially — the new-index product lands ≥ 0.5 above its floor while the old-index product lands ≤ −0.5 below its value.

When `distributed = rewards_increase + 1`, `rewards_increase.checked_sub(env, distributed)` panics (`common/src/rates/index.rs:63`). Since `accrue_step` calls this unconditionally whenever `supplier_rewards > 0` and the new index advanced, the panic propagates through `accrue_chunk` → `global_sync`, which every pool entrypoint executes first. The shared simulate path (`simulate_update_indexes`, controller `Context::cached_market_index` views) uses the same `accrue_step`, so it is not a mutator-only quirk.

### Impact Explanation
Once a market state reaches a rounding-aligned triple, **every** subsequent call that triggers accrual on that market reverts with `MathOverflow`: `supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `flash_position`, `claim_revenue`, `recapitalize`, `update_indexes`. Because the panic happens inside accrual *before* any state mutation, no operation can advance past it — supplier funds and borrower collateral backing this market are permanently frozen, and bad debt cannot be liquidated or written down. This is a permanent freezing of user funds / contract unable to operate, not a fail-closed parameter guard: no admin action (short of a contract upgrade) can restore the market since even governance-driven flows route through the same pool accrual.

### Likelihood Explanation
The triggering condition is a 1-raw-unit boundary alignment of two half-up products, so any single step hitting it is a low-probability edge. However, an unprivileged attacker does not need luck: `rewards_increase` is a deterministic function of `(borrowed, supplied, indexes, delta_ms)`, and `delta_ms` is controlled by the attacker's call timing (any millisecond granularity within a chunk). An attacker who supplies/borrows dust amounts to steer `supplied` and `borrowed` and then calls `update_indexes` (permissionless) at chosen timestamps can search the input space for the poisoned triple. Once found, the freeze is permanent and affects all users of the market. The state space is large (i128 products), but the attacker fully controls several inputs, making this a targeted rather than accidental trigger — analogous to the streebog sigma bug's input-dependent panic.

### Recommendation
Make `supply_index_reward_shortfall` saturating instead of panicking: return `rewards_increase.saturating_sub(distributed)` (or clamp `new_index` inside `update_supply_index` so the implied distributed value can never exceed `rewards_increase`, e.g. recompute `grown = min(grown, exact bound)`). Additionally, use `mul_floor` for the `supplied * new_index` product in the shortfall computation so `distributed` is a strict lower bound of `rewards_increase` by construction.

### Proof of Concept
1. Attacker supplies and borrows into a market (any listed hub asset), leaving the market with borrowed > 0 so accrual produces nonzero `supplier_rewards`.
2. Attacker calls `update_indexes` (or any pool verb) repeatedly at attacker-chosen ledger timestamps, or first adjusts `supplied`/`borrowed` via dust `supply`/`borrow` calls, until a step produces `supplied`, `old_index`, `rewards_increase` such that `hup(s*new_index) − hup(s*old_index) = rewards_increase + 1`.
3. `supply_index_reward_shortfall` panics in `checked_sub` (`common/src/rates/index.rs:63`); the transaction reverts.
4. All subsequent calls to `withdraw`, `repay`, `liquidate`, `update_indexes`, `claim_revenue`, `flash_loan` on that market revert identically, because `global_sync` (`contracts/pool/src/interest.rs:20-33`) re-executes the same `accrue_step` against the unchanged cached state — the remaining elapsed time never shrinks below the poisoned chunk.

Note: I verified the rounding algebra but did not execute a concrete numeric triple; the exact constants of a triggering input would need to be confirmed by running the harness (e.g. fuzzing `accrue_step` over small `supplied` values where the 1-raw-unit granularity is attainable). If the Certora spec proves `distributed ≤ rewards_increase` over the full reachable domain (I located `accrued_interest_split_is_conservative` rules but could not confirm a nonnegativity rule for the shortfall), this finding reduces to a defense-in-depth recommendation rather than a live freeze.
