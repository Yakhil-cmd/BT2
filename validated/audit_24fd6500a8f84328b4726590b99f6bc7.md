### Title
Webhook signature is verified against an attacker-chosen organization while the write target is taken from an unrelated payload field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the `X-Hub-Signature` against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body. Once the signature check passes, every event handler (e.g. `PushHandler`) resolves the actual `Stack`/`Repository` to act on using a *different* field of the same unverified body: `repository.full_name`. Nothing ties these two fields together, so in a multi-organization Shipit deployment an attacker who legitimately controls one onboarded organization's webhook secret can forge a webhook whose `repository.owner.login` matches their own org (so the signature check passes) but whose `repository.full_name` points at a stack belonging to a completely different organization on the same Shipit instance.

### Finding Description
`Shipit.github(organization: repository_owner)` picks a `GitHubApp` (and thus a distinct `webhook_secret`) keyed by an organization name that is read from the request body itself: [1](#0-0) [2](#0-1) 

This is the documented multi-tenant configuration schema (`Shipit.github_default_organization` non-nil), where each organization key has its own `webhook_secret`: [3](#0-2) 

After `verify_signature` passes, `create` dispatches the *entire* raw payload to handlers: [4](#0-3) 

Handlers resolve the target `Repository`/`Stack` using `repository.full_name`, a field never consulted during signature verification: [5](#0-4) [6](#0-5) 

The binding that should hold is: `organization authenticated by verify_signature == organization that owns the repository being written by the handler`. Because both values are read from attacker-controlled JSON with no cryptographic link between them, this equality is never enforced. An attacker who legitimately owns a webhook secret for `OrgA` (a valid tenant configured on the shared Shipit instance) can set `repository.owner.login = "OrgA"` (so the org-specific HMAC check passes) while setting `repository.full_name = "OrgB/victim-repo"` (an unrelated tenant's repository), causing handlers to act on `OrgB`'s stack.

Before the attacker's request: only requests carrying a valid `X-Hub-Signature` computed with `OrgA`'s secret can ever influence `OrgA`'s repositories. After: the same signature, computed with the same `OrgA` secret, can influence any repository/stack configured under any other organization on the instance, because the handler layer keys exclusively off `repository.full_name`, not off the authenticated organization.

### Impact Explanation
This crosses the "organization authenticated vs. repository written" trust boundary explicitly called out as in-scope, and results in cross-repository/cross-tenant writes performed under another organization's identity:
- `PushHandler` can enqueue `stack.sync_github(expected_head_sha:)` for a victim stack the attacker has no relationship to.
- Other handlers keyed the same way (`status`, `check_suite`, `pull_request` sub-handlers via `Handler#repository_name`/`from_github_repo_name`) allow archiving/unarchiving review stacks, injecting commit statuses, or acting on pull requests belonging to a different organization's repository.

This satisfies the "Critical - cross-repository writes / unauthorized deploy" bar: state belonging to `OrgB` is mutated using credentials that only prove knowledge of `OrgA`'s webhook secret.

### Likelihood Explanation
Exploitability requires only that the Shipit instance uses the multi-organization secrets schema (a documented, supported configuration, not a misconfiguration) and that the attacker legitimately controls one onboarded organization's GitHub App/webhook secret — no privileged Shipit account, `ApiClient` token, or GitHub write access to the victim's repository is needed. The forged request is sent directly to the public `/github/webhooks` endpoint, bypassing GitHub entirely.

### Recommendation
`verify_signature` should not be the sole authentication check; handlers must verify that the organization used to authenticate the signature is the same organization that owns `repository.full_name` (e.g., by comparing `repository.full_name.split('/').first` against `repository_owner`/the app that verified the signature), or the signature verification should itself be scoped to the specific `Repository`/`Stack` record (matching against its own stored per-repo secret) rather than to an organization name pulled from the untrusted payload.

### Proof of Concept
1. Deploy Shipit with the multi-org secrets schema, e.g. `somegithuborg` and `someothergithuborg`, each with its own `webhook_secret` (as shown in `config/secrets.development.shopify.yml`).
2. As the legitimate owner of `somegithuborg`'s GitHub App, compute `sha1=HMAC(webhook_secret_of_somegithuborg, body)` for the body:
   ```json
   {
     "repository": { "owner": { "login": "somegithuborg" }, "full_name": "someothergithuborg/victim-repo" },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>"
   }
   ```
3. `POST /github/webhooks` with headers `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner = "somegithuborg"`, verifies successfully against `somegithuborg`'s secret.
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("someothergithuborg/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, acting on a stack belonging to an organization the attacker never authenticated as.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
