### Title
Webhook signature verification is keyed on the payload's claimed organization while the acted-upon repository is resolved independently, allowing cross-organization webhook confusion in multi-tenant Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
This is the closest structural analog to the `_deductFees()` bug: a value used to select/validate a security control (`params.feeX64` gating the fee transfer) diverges from the value actually acted upon (`feeAmount0/1/2` being zero yet still transferred). In Shipit, the field used to select *which secret verifies the HMAC signature* (`repository_owner`, derived from `params.dig('repository','owner','login') || params.dig('organization','login')`) is not the same field that determines *which `Repository`/`Stack` the handler subsequently writes to* (`payload.dig('repository','full_name')` in `Handlers::Handler#repository_name`). The signature is verified against one binding (org login) while the write happens on another binding (repository full_name) that is not itself covered by any check that it belongs to the org whose secret validated the request.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret used for HMAC verification purely from the organization login embedded in the JSON payload: [1](#0-0) [2](#0-1) 

Once the signature check passes, the raw, attacker/GitHub-supplied JSON is dispatched unmodified to the registered handlers: [3](#0-2) 

Every handler (e.g. `PushHandler`) resolves the target `Stack`/`Repository` using `repository.full_name` from that same payload, via `Handlers::Handler#repository_name` / `#stacks`: [4](#0-3) [5](#0-4) 

Nothing ties `repository.full_name` back to `repository_owner` used for signing. In a single-organization deployment this is moot (only one secret exists). But the engine explicitly supports "Using Multiple Github Applications", where each organization has its own `webhook_secret`, keyed by organization name: [6](#0-5) 

In that configuration, `Shipit.github(organization: repository_owner)` picks the org-specific `GithubApp` and its `webhook_secret` to validate the signature — but the handler layer never checks that the `full_name`'s owner matches `repository_owner`. This is exactly the equality the report's bug class targets: "organization that authenticated" (`repository_owner`, used to select the verifying secret) vs "repository that is written" (`repository.full_name`, used to resolve the `Stack` acted upon) — a payload field acted upon (`full_name`) that is never itself covered by the verifying binding.

### Impact Explanation
In a multi-organization Shipit deployment, if an attacker can produce (or capture/replay) a validly-signed webhook payload from one onboarded, lower-trust organization ("OrgA", whose secret they can obtain e.g. through a compromised or malicious repo admin under OrgA), they can rewrite `repository.full_name` (and related fields) to point at a stack belonging to a different, higher-trust organization ("OrgB") whose GitHub App has separate credentials. Because the signature check only confirms "this request was signed by *some* configured org's secret", not "the org that signed this request owns the repository being mutated", the handler will process the forged payload against OrgB's stack — e.g. triggering `sync_github`/`GithubSyncJob` for a fabricated `after` SHA on an OrgB stack, or creating fabricated commit `status` records, or manipulating `Membership`/`Team` records cross-organization. This can facilitate an unauthorized deploy trigger against a stack the attacker does not control, satisfying the "unauthorized deploy" bar in scope.

### Likelihood Explanation
Exploitability is conditioned entirely on the deployment using the multi-organization `github:` configuration described in `docs/setup.md`, and on the attacker being able to produce a payload correctly signed by *one* of the configured orgs' secrets (e.g., because they administer a repository under that lesser-trusted org and can create/replay a webhook delivery there). This still requires some privileged foothold in at least one onboarded organization, which is a boundary-crossing condition, but not "repository write access to the target stack's own repository" — it is a cross-repository/cross-organization trust-boundary break, matching the requested analog class. Single-organization deployments (the default template) are not affected since there is only one secret in play.

### Recommendation
After verifying the HMAC signature, re-validate that `repository.full_name`'s owner (and/or `organization.login`) matches the `repository_owner` value that was used to select the verifying secret before dispatching to handlers. Reject the webhook (422) on mismatch, e.g. inside `WebhooksController#verify_signature` or as an additional `before_action`, rather than trusting the handler layer to independently re-derive trust from the same untrusted payload.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. Obtain a validly HMAC-signed webhook payload for `OrgA` (e.g., attacker administers/compromises a webhook on any repo under `OrgA`), for the `push` event.
3. Modify the JSON body's `repository.full_name` (and `owner.login`) to reference a repository/stack that belongs to `OrgB`, while leaving `X-Hub-Signature` computed over the modified body using `OrgA`'s secret (since `repository_owner` still resolves to `OrgA` from `organization.login`/original owner field used for verification) — or, more directly, keep `organization.login`/top-level owner as `OrgA` for signature-selection purposes while `repository.full_name` names an `OrgB` repo, since `repository_owner` and `repository_name` are read from different, independently attacker-influenced sub-paths of the same JSON body (`app/controllers/shipit/webhooks_controller.rb:59-62` vs `app/models/shipit/webhooks/handlers/handler.rb:36-38`).
4. Submit the POST to `/webhooks` with `X-Github-Event: push`; `verify_signature` succeeds because it only checks the signature against `OrgA`'s secret using `repository_owner`.
5. `Handlers::PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name(repository_name)` using the forged `full_name`, and triggers `stack.sync_github(expected_head_sha: params.after)` on the `OrgB` stack — a write/trigger action on a stack outside the organization that actually signed the request.

*(Note: exact feasibility of forging the signature depends on details of how GitHub computes/attaches signatures per-org and on obtaining OrgA-level webhook access, which could not be fully verified with static code review alone; a live/dynamic test against a running multi-org Shipit instance would be needed to conclusively confirm exploitability.)*

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
