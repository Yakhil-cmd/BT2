### Title
Insecure default file permissions on saved private-textcoin payload files expose spending mnemonic - ([File: wallet.js])

### Summary
When a wallet sends a private asset payment to a "textcoin" address, `sendMultiPayment` generates a spending mnemonic for the recipient and, via `storePrivateAssetPayload`, writes that mnemonic together with the private payment chain to a local file using `fs.writeFile` without specifying a restrictive file mode [1](#0-0) . This mirrors CVE-2017-1000485's root cause: sensitive authentication material (there, `$HOME/.nylas-mail`; here, the textcoin mnemonic/private key) is persisted to disk with the platform's default, overly permissive file mode instead of an owner-only mode.

### Finding Description
`storePrivateAssetPayload` builds a zip containing `{mnemonic, chains}` — the mnemonic is the raw private-key-deriving secret that authorizes spending of the private asset output — and writes it with `fs.writeFile(fullPath, zipFile, cb)` [1](#0-0) . No file mode (e.g., `0600`) is passed, so Node.js applies the process's default mode (`0666` minus umask), which on most Linux/desktop configurations resolves to a world- or group-readable file (`0644`), regardless of the sensitivity of the content. This is invoked from `sendMultiPayment`'s private-asset flow whenever an application supplies `opts.getPrivateAssetPayloadSavePath` for a "textcoin"-style private payment, i.e., addresses generated on the fly via `generateNewMnemonicIfNoAddress`/`expandMnemonic` [2](#0-1) [3](#0-2) . Elsewhere in the codebase, sensitive data directories are correctly created with owner-only mode `0700` (e.g. `kvstore.js` and `sqlite_pool.js`), confirming the project's own security expectation that secret-bearing files/directories must not be world-accessible, which `storePrivateAssetPayload` fails to uphold [4](#0-3) [5](#0-4) .

### Impact Explanation
Any other local, unprivileged user or process on the same multi-user machine that can read the saved payload file can extract the mnemonic before the intended recipient claims it. Using `expandMnemonic`/`receiveTextCoin`, that mnemonic directly derives the private key and definition needed to sign and broadcast a claim of the private asset (`ecdsaSig.sign(...,addrInfo.xPrivKey...)`), resulting in unauthorized spending/theft of the funds intended for the legitimate recipient [6](#0-5) .

### Likelihood Explanation
This is triggered on the standard "send private asset payment via textcoin file" code path that a wallet UI wires to `opts.getPrivateAssetPayloadSavePath`; no attacker interaction with the network protocol or peers is required — only local file read access on the machine where the payload was saved, e.g. a shared/multi-user desktop, a synced folder, or a backup that isn't scoped to the owner. Given default Unix umasks, exploitation requires no special privileges, matching the same low-effort, high-impact profile as CVE-2017-1000485.

### Recommendation
Pass an explicit restrictive mode when writing the private payload file, e.g. `fs.writeFile(fullPath, zipFile, { mode: 0o600 }, cb)`, and if the target directory is created, create it with `0700` mode consistent with the pattern already used in `kvstore.js` and `sqlite_pool.js`. Additionally, consider encrypting the mnemonic/chains payload at rest so file permission mistakes on the caller's filesystem don't directly expose spendable secrets.

### Proof of Concept
1. A wallet application calls `wallet.sendMultiPayment` with a private asset and `opts.getPrivateAssetPayloadSavePath` set, producing a textcoin mnemonic for a newly generated recipient address [2](#0-1) .
2. `storePrivateAssetPayload` is invoked and writes the zip (containing the plaintext mnemonic and private chain) to `fullPath` via `fs.writeFile` without a `mode` option [1](#0-0) .
3. On a typical Linux system with umask `022`, the resulting file has mode `0644`, readable by any local user.
4. A second local user reads the file, unzips it, extracts `mnemonic`, and calls `wallet.receiveTextCoin(mnemonic, attackerAddress, ...)` to claim/spend the private asset before the intended recipient, using `expandMnemonic` to derive the same signing key [7](#0-6) .

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}
