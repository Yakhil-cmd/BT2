### Title
Webhook Signature Verification Is Scoped to `repository.owner.login`/`organization.login` While Event Handlers Act on the Independent `repository.full_name` Field, Allowing Cross-Organization Forged Webhook Events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController` selects which GitHub App/organization config (and therefore which `webhook_secret`) to verify the inbound webhook signature against using one field of the JSON body — `repository.owner.login` (falling back to `organization.login`) — but the actual event handlers that mutate state resolve the target `Stack`/`Repository`/`Commit` using a *different*, independently attacker-controlled field of the very same body: `repository.full_name`. In a multi-organization Shipit deployment where at least one configured GitHub organization has no `webhook_secret` set (a documented, supported configuration), signature verification is unconditionally skipped for any payload claiming to originate from that org, letting an attacker forge a payload whose `repository.full_name` points at a completely different, properly-secured stack.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to verify against from the payload itself: [1](#0-0) 

and [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, both of which are ordinary, unauthenticated fields inside the JSON body.

The chosen `GitHubApp`'s `verify_webhook_signature` short-circuits to `true` whenever the org has no `webhook_secret` configured: [3](#0-2) 

Leaving `webhook_secret` unset per-organization is an explicitly supported/documented setup, shown in the example multi-org configs: [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature` (either legitimately, or because the resolved org has no secret), `WebhooksController#create` dispatches the full raw JSON body to the matching handlers: [6](#0-5) 

Every handler resolves its target `Stack`/`Repository` from a **different** payload field than the one used for signature/org selection: [7](#0-6) 

For example `PushHandler` triggers a GitHub sync for every stack matching `repository.full_name`+branch: [8](#0-7) 

`StatusHandler` writes a `Status` record for any commit matching the attacker-supplied `sha`, using attacker-controlled `state`/`context`/`target_url`/`description`, entirely independent of `repository`: [9](#0-8) 

`CheckSuiteHandler` similarly acts on `repository.full_name` + attacker supplied `head_sha`/`head_branch`: [10](#0-9) 

**The broken binding:** `organization that authenticated the request (repository.owner.login / organization.login, used to pick the GitHub App and webhook_secret) == repository that is written (repository.full_name, used by every Handler to resolve the Stack/Commit acted upon)`. Nothing in `WebhooksController` or `Handler` enforces these two independently-settable JSON fields agree. An attacker who knows (or can infer, e.g. from public engine configuration/docs, or an organization that intentionally omits a secret for testing/legacy reasons) that one configured organization has no `webhook_secret` can send a completely unsigned request that is treated as verified for that org, while `repository.full_name` names a stack belonging to a different, properly-secured organization whose real `webhook_secret` the attacker never had.

### Impact Explanation
This lets an unprivileged, unauthenticated network attacker forge webhook events (`push`, `status`, `check_suite`, etc.) against arbitrary stacks in the installation, as long as any one configured GitHub organization is left without a `webhook_secret`. Concretely this allows:
- Forcing arbitrary `Stack#sync_github` refresh cycles on victim stacks (`PushHandler`).
- Injecting fabricated commit `Status` records (`state`, `context`, `target_url`) for arbitrary commit SHAs on victim stacks (`StatusHandler`), which feed into Shipit's deployability/merge-gating checks (`app/models/shipit/commit.rb`, `app/models/shipit/status/group.rb`, `app/models/shipit/commit_checks.rb`) that Shipit relies on to decide whether a commit can be deployed or merged.
- Triggering check-run refresh workflows tied to an arbitrary commit/branch of a victim stack (`CheckSuiteHandler`).

Because forged statuses can influence the "commit is deployable" determination used elsewhere in the engine, this crosses the required bar of an unauthorized/forced deploy path, not merely a benign data write. I was not able to fully trace, in the remaining budget, the exact merge-queue/continuous-deployment code path that consumes `Status`/`CommitChecks` state to gate an actual deploy trigger — this final linkage should be verified in the engine's `Stack`/`CommitChecks`/merge-queue logic before treating this as a fully proven Critical-severity chain.

### Likelihood Explanation
Requires the operator to run a multi-organization Shipit configuration (`Shipit.github(organization: ...)`) with at least one configured org lacking a `webhook_secret` — an explicitly supported and documented configuration shape (see `config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`). No GitHub App private key, webhook secret, session, or repository write access is required by the attacker; only knowledge of the target's repository full name and the vulnerable org's name (often discoverable from Shipit's own public UI/URLs, since stacks are addressed by `owner/repo/branch`).

### Recommendation
Bind the organization/App used for signature verification to the same repository identity used by the handlers: derive both from `repository.full_name` (or verify that `repository.owner.login` matches the owner segment of `repository.full_name`) before dispatching to handlers, and reject the request if they diverge. Additionally, do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for organizations backing real stacks — require an explicit "no verification" opt-in flag rather than treating an absent secret as an implicit bypass, and consider failing closed (422) instead of always-true when a secret is unset in a multi-org configuration.

### Proof of Concept
1. Deploy Shipit with a multi-org config where `OrgA` (attacker-known, no real stacks of value) has `webhook_secret: nil`, and `OrgB` hosts the real target stack `OrgB/victim-repo`.
2. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any garbage value), body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "sha": "<known open commit sha in OrgB/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://attacker.example"
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`), regardless of signature header.
4. `create` dispatches the payload to `StatusHandler`, which locates the commit by `sha` (independent of `repository`) inside `OrgB/victim-repo` and creates a forged `Status` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), even though the attacker never possessed `OrgB`'s real `webhook_secret`.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
