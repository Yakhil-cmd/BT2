### Title
Webhook auth uses `repository.owner.login` while all handlers act on `repository.full_name`, allowing an org's own valid signature to authorize actions on any other tenant's repo/stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC using `repository_owner` (`payload.dig('repository','owner','login')`), but `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` (and every concrete handler) resolves the target `Repository`/`Stack` using `payload.dig('repository','full_name')`. Since no code anywhere compares these two values, a payload whose `repository.owner.login` names one org (used purely to pick the verifying secret) but whose `repository.full_name` names a completely different org/repo will pass signature verification and then be processed against the *other* repo's stack.

### Finding Description
Broken binding: the code implicitly assumes `repository_owner == payload.dig('repository','full_name').split('/').first`, but this is never asserted.

Path:
- `app/controllers/shipit/webhooks_controller.rb:59-62` — `repository_owner` reads `params.dig('repository','owner','login')`.
- `app/controllers/shipit/webhooks_controller.rb:24-30` — `verify_signature` does `Shipit.github(organization: repository_owner)` then verifies `X-Hub-Signature` against `request.raw_post` using that org's `webhook_secret` (`lib/shipit/github_app.rb:76-83`).
- `app/controllers/shipit/webhooks_controller.rb:10-15` — `#create` re-parses the same `raw_post` and dispatches to handlers.
- `app/models/shipit/webhooks/handlers/handler.rb:32-38` — `stacks`/`repository_name` resolve the target using `payload.dig('repository','full_name')`, completely independent of `repository_owner`.
- `app/models/shipit/repository.rb:53-56` — `Repository.from_github_repo_name` splits `full_name` on `/` to find the actual `Repository`/`Stack` and has no relation to the org used for signature verification.
- Concrete handlers (`push_handler.rb`, `pull_request/*_handler.rb`) never read or check `repository.owner.login`, confirming no cross-check exists anywhere in the call chain to `Handler#stacks`.

Exploit precondition and flow: Shipit supports multi-organization configuration (`docs/setup.md` "Using Multiple Github Applications", `config/secrets.development.shopify.yml`), where each org has its own `webhook_secret` known to that org's own administrators/app owners. An attacker who administers one such configured org ("attacker-org", with a real GitHub App installed and a `webhook_secret` they legitimately know) can:
1. Craft a payload with `repository.full_name = "victim-org/victim-repo"` (an unrelated tenant/stack hosted on the same Shipit instance) but `repository.owner.login = "attacker-org"`.
2. Compute `X-Hub-Signature` with `attacker-org`'s own `webhook_secret` against this raw payload.
3. POST to `/webhooks`. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, verifies the signature against the attacker's own valid secret — it passes.
4. `#create` dispatches to e.g. `PushHandler`, which resolves `stacks` via `full_name = "victim-org/victim-repo"`, and calls `stack.sync_github(expected_head_sha: params.after)` on the **victim's** stack — or for PR handlers, archives/unarchives/updates the victim's review stack — using attacker-controlled `sha`/`ref`/PR data.

No guard (`drop_unhandled_event`, `ExplicitParameters` schemas, `Repository` validations, or any handler) checks that the org used to select the verifying secret matches the org embedded in `full_name`.

### Impact Explanation
An attacker who legitimately controls one org's GitHub App/webhook secret in a shared/multi-tenant Shipit deployment can forge push/pull_request/status/etc. events for **any other org's repository and stack** on the same Shipit instance, triggering GitHub sync jobs, archiving/unarchiving review stacks, or updating commit/PR state for a tenant they do not own. This is a cross-tenant confused-deputy vulnerability — "a payload for one repository mutating another's stack, commit, task or team" — matching the Critical severity bucket.

### Likelihood Explanation
Requires a Shipit instance configured with multiple GitHub organizations/apps (a documented, supported configuration). The attacker only needs legitimate control of their own org's app/webhook secret (no Shipit session, no victim secrets) — a low-cost, fully repeatable attack against every other tenant's repo/stack. In a single-org Shipit deployment this specific cross-tenant path collapses (there is only one org/secret), but the missing equality check remains present in code and is the root cause identified.

### Recommendation
In `WebhooksController#verify_signature`, after resolving/verifying, assert that `repository_owner` (or the org used to pick `Shipit.github`) equals the owner segment of `payload.dig('repository','full_name')` (case-insensitively), rejecting with `head(422)` on mismatch; alternatively, have `Handler#repository_name`/`#stacks` derive the repository strictly from the same trusted `repository_owner` value used for authentication rather than independently re-reading `full_name`.

### Proof of Concept
```ruby
test "signature for org A does not authorize acting on org B's repository" do
  request.headers['X-Github-Event'] = 'push'
  payload = JSON.parse(fixture_payload(:push_master))
  payload['repository']['owner']['login'] = 'attacker-org'   # used for signature org selection
  payload['repository']['full_name'] = 'victim-org/victim-repo' # used by PushHandler#stacks
  body = payload.to_json

  Shipit.stubs(:github).with(organization: 'attacker-org').returns(fake_valid_app)
  # fake_valid_app.verify_webhook_signature returns true for attacker's own secret

  request.headers['X-Hub-Signature'] = attacker_signature_for(body)

  assert_no_enqueued_jobs do
    post :create, body: body, as: :json
  end
  assert_response :unprocessable_entity  # currently fails: response is :ok and victim stack is synced
end
```
Assert both `repository_owner` (`'attacker-org'`) and the owner segment of `full_name` (`'victim-org'`) — they differ, and the current code performs no equality check between them anywhere from `#create` to `Handler#stacks`, so the request is accepted and the victim's stack is processed.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.
