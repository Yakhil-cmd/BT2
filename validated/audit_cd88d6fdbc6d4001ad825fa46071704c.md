### Title

Arbitrary swap-route venues can execute unauthorized token transfers under the caller’s authorization - ([File: `contracts/controller/src/strategies/swap.rs`])

### Summary

The controller accepts attacker-controlled `swap` bytes and passes them to the configured router without imposing a venue allowlist or otherwise constraining which contracts the route invokes. A malicious route can therefore place attacker-controlled code below the caller’s authorized `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` invocation and perform unrelated `token::transfer` calls that are recorded under the caller’s authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description

`process_swap_collateral` authenticates `caller` and verifies account ownership, but forwards the caller-controlled `swap` payload into `withdraw_and_swap_from_supply` without validating the route’s destination contracts. [3](#0-2) 

`swap_tokens` authorizes only the exact input-token transfer from the controller to the router, but then executes the opaque caller-supplied route through `router.execute_strategy`. [4](#0-3) 

The post-swap checks only bound the controller’s input spend and require a positive output-delta; they do not prevent route-selected contracts from making unrelated calls that consume the original caller’s broader authorization tree. [5](#0-4) 

The repository’s authorization-tree PoC demonstrates that a route-selected contract can call `token.transfer(victim, attacker, amount)` and that simulation records that transfer as a child of the victim’s `swap_collateral` authorization. [6](#0-5) [7](#0-6) 

### Impact Explanation

A malicious route can transfer tokens unrelated to the lending operation from the calling account to an attacker while still returning enough swap output for the controller’s measured-output and final risk checks to pass. [8](#0-7) 

This is theft of user funds rather than merely poor execution: the demonstrated route pays the expected collateral to the controller while draining the victim’s entire balance of an unrelated token. [9](#0-8) 

### Likelihood Explanation

Any unprivileged account owner or delegate can reach `swap_collateral`, and the same primitive is reachable through `swap_debt`, `multiply`, and `repay_debt_with_collateral` whenever a cross-token route is supplied. [10](#0-9) [11](#0-10) 

Exploitation requires the victim to sign the authorization tree produced by simulation, but Soroban’s model places the malicious nested transfer inside that tree rather than exposing it as a separate top-level operation. [12](#0-11) 

### Recommendation

Constrain executable routes to governance-approved venue contracts and reject payloads that can invoke arbitrary addresses. [1](#0-0) 

Until routes are allowlisted, clients must decode every `swap` payload and reject any authorization tree containing children other than the expected exact input-token transfer. [13](#0-12) 

### Proof of Concept

1. Deploy a malicious route venue that calls `token::Client::transfer(victim, attacker, victim_balance)` for an unrelated wallet token. [14](#0-13) 
2. Submit or induce the victim to submit `controller.swap_collateral(caller, account_id, usdc_market, 5_000_usdc, eth_market, malicious_route)`. [15](#0-14) 
3. Simulation records the unrelated wallet-token transfer as a child authorization beneath the victim’s controller call. [16](#0-15) 
4. Signing that tree allows the malicious venue to drain the wallet token while the controller still receives the declared swap output and completes successfully. [8](#0-7)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
