### Title
CCMenu API endpoint bypasses stack-scoped ApiClient authorization, allowing cross-stack read of build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` restricts every API action to the stacks an `ApiClient` is authorized for via its `stacks`/`stack` helpers, but `Shipit::Api::CCMenuController` overrides `stack` to bypass that scoping entirely, letting any `read:stack`-permissioned token read the CI/build status of a stack it was never granted access to.

### Finding Description
`Shipit::Api::BaseController` defines the authorization binding between a token and the stacks it may touch: [1](#0-0) 

`stacks` narrows the queryable set to `Stack.where(id: current_api_client.stack_id)` when the `ApiClient` is scoped to a specific stack (`stack_id?`), and `stack` resolves `params[:stack_id]` only within that scoped relation. Every other API controller (e.g. `StacksController`, `DeploysController`, `TasksController`) relies on this `stack`/`stacks` helper to enforce the "stack a token authorizes" boundary.

`Shipit::Api::CCMenuController` overrides `stack` to query the model directly, discarding the scoping: [2](#0-1) 

`require_permission :read, :stack` only checks that the token's `permissions` array contains `read:stack` — it never checks whether the requested `stack` is the one the token is bound to: [3](#0-2) 

So a token created with `stack:` set to Stack A (e.g. `here_come_the_walrus` in fixtures, or any stack-scoped token issued through `ApiClientsController`) is meant to only see Stack A through `stacks.where(id: current_api_client.stack_id)`. But because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly, that same token can be presented with any other `stack_id` (Stack B, C, …) and the controller will happily render Stack B's CCMenu status, breaking the equality "stack a token authorizes == stack the request touches."

### Impact Explanation
This is an authorization-boundary break, not merely leftover unused code: it exposes another stack's build state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state) to a credential holder who was only ever granted `read:stack` on one specific stack. This matches the "unauthenticated/unauthorized read of stack state" High-impact class — the requester never proved authorization for the target stack, yet the engine discloses its deploy/CI status.

### Likelihood Explanation
Any environment issuing per-stack scoped `ApiClient` tokens (a documented and tested feature — see `here_come_the_walrus` fixture and `"an api client scoped to a stack will only see that one stack"` test) is affected the moment such a token is used against `GET /api/stacks/:stack_id/cc.xml` with a different `stack_id`. No special privileges beyond possessing a valid, narrowly-scoped API token are required, and the query-string `token` param even allows this without an Authorization header, making it trivially exploitable from any browser/CI dashboard puller.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and rely on `BaseController#stack` (i.e. `stacks.from_param!(params[:stack_id])`) so CCMenu requests are constrained the same way as every other API endpoint.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` (as in `here_come_the_walrus` fixture).
2. `GET /api/stacks/:stack_B_id/cc.xml?token=<stack_A_scoped_token>` where Stack B differs from Stack A and was never authorized for this token.
3. Observe the response renders Stack B's CCMenu XML (build status, label, time) successfully, even though `stacks.where(id: current_api_client.stack_id)` would have returned `Stack.none` for Stack B under `BaseController`'s scoping used by every other endpoint.
