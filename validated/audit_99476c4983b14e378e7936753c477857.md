### Title
`StatusHandler#process` uses an unscoped `Commit.where(sha:)` allowing any authenticated-org webhook to mutate another repository's commit status - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks.for_event('status')` resolves to exactly one handler, `Handlers::StatusHandler`, and `WebhooksController#create` calls `handler.call(params)` for every matched handler with no additional per-handler repository check. Unlike `PushHandler` and `CheckSuiteHandler`, which scope their queries through `stacks` (derived from `payload.dig('repository', 'full_name')`), `StatusHandler#process` queries `Commit.where(sha: params.sha)` globally, across all stacks/repositories, so the controller's org-level signature check is the only gate before a cross-repository write.

### Finding Description
Binding claimed: `authenticate(org_signature) ∧ authorize(repo_scope_check_in_handler) = enforce(repository_scope)`.

Traced code:
- `WebhooksController#create` runs `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` then `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [1](#0-0) 
- `verify_signature` resolves the GitHub App config keyed only by `repository_owner` (the org/owner login taken from the payload) and validates the HMAC signature against that org's `webhook_secret`. It never inspects which specific repository or stack the event concerns beyond the owner login. [2](#0-1) 
- `Shipit::Webhooks.for_event('status')` returns exactly `[Handlers::StatusHandler]`. [3](#0-2) 
- `Handler` (the base class) provides a `stacks` helper that scopes to the reporting repository via `Repository.from_github_repo_name(repository_name)&.stacks`, using `payload.dig('repository', 'full_name')`. `PushHandler` and `CheckSuiteHandler` both use this scoped `stacks` relation before touching commits. [4](#0-3) [5](#0-4) [6](#0-5) 
- `StatusHandler#process`, by contrast, never calls `stacks` or checks `repository_name` — it runs `Commit.where(sha: params.sha)` unscoped, iterating **every** commit in the database sharing that SHA and calling `create_status_from_github!` on each. [7](#0-6) 
- The `commits` table's index is a composite `(stack_id, sha)`, not a global uniqueness constraint on `sha` alone, so the schema does not prevent multiple stacks from holding commits with identical SHAs (e.g., forks, mirrors, or repositories sharing git history). [8](#0-7) 

Root cause: the org-level signature check authenticates *that the payload's declared repository/owner is legitimate*, but it does not authorize *that the SHA being acted upon belongs to that repository*. `StatusHandler` has no code path that cross-checks `params.sha` against the reporting repository's commit set, so the conjunction of controller-level authentication and (missing) handler-level authorization collapses to authentication alone, exactly as the question posits.

Exploit flow: an attacker who legitimately controls a repository whose org is registered in Shipit (and thus can produce genuinely GitHub-signed `status` webhook deliveries) sends a `status` event whose `sha` matches a commit that also exists in a different, unrelated stack (e.g., shared commit history from a fork or mirrored repository). `Commit.where(sha: params.sha)` matches that commit in the victim stack and calls `create_status_from_github!`, writing an attacker-controlled state (e.g., `success`) onto it — which can affect `deployable?`/`schedule_merges` logic on the victim's stack. [9](#0-8) 

None of the listed guards close this gap: `verify_signature` only authenticates org ownership of the payload, not SHA-to-repository binding; `ExplicitParameters` schema for `StatusHandler` only validates presence/type of `sha`/`state`/etc., not repository membership; there is no `require_permission!`, `stacks` scope, or model validator invoked inside `StatusHandler#process`.

### Impact Explanation
A commit status record can be written for a stack/repository that did not itself send (or authenticate) the webhook — a payload nominally about repository A can mutate commit state belonging to repository B's stack, matching the Critical category "a payload for one repository mutating another's stack, commit... or an unauthorized deploy." This is repeatable per matching SHA and is not limited to a single tenant; any two stacks whose commit histories intersect (forks, mirrors, subtree-split repos) are cross-contaminable via this handler.

### Likelihood Explanation
Exploitation requires the attacker to already be able to produce a genuinely-signed `status` webhook for some org tracked by Shipit (i.e., control of a repository under that org, or the app is installed broadly for their account) — this is a real but non-trivial precondition, not requiring any Shipit secret since GitHub itself signs deliveries for legitimate repository owners. The harder constraint is causing SHA collision with a target stack's commit, which is realistic for forked/mirrored repositories sharing git objects but not for arbitrary unrelated repositories. Attacker cost is otherwise low (a normal push or manual status API call) and the primitive is repeatable at will.

### Recommendation
In `StatusHandler#process`, scope the lookup through the reporting repository, e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` (mirroring `PushHandler`/`CheckSuiteHandler`'s use of the `stacks` helper) instead of the global `Commit.where(sha: params.sha)`, so a status update can only ever affect commits belonging to stacks of the repository named in the verified payload.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, hypothetical — file itself not required to exist for the assertion to be demonstrable):
1. Create `stack_a` (repository `owner-a/repo-a`) and `stack_b` (repository `owner-b/repo-b`).
2. Create `commit_a` under `stack_a` and `commit_b` under `stack_b` with the **same** `sha` value (`"deadbeef"`), reflecting a shared-history/mirrored scenario.
3. Build a `status` payload declaring `repository.full_name = 'owner-a/repo-a'` and `sha: 'deadbeef', state: 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller signature, as controller-level auth is not in question here).
5. Assert: `commit_b.statuses.count` increased by 1 (i.e., `stack_b`, whose repository never appeared as the reporting repository, received a status write) — proving the equality `authenticate(org) ∧ authorize(repo_scope) = enforce(repo_scope)` is false for `StatusHandler`, since no `authorize(repo_scope)` step exists and `commit_b` was mutated despite the payload being about `repo-a`.
6. Contrast with an equivalent test for `PushHandler`/`CheckSuiteHandler` using `stacks.where(branch:)`/`stacks.where(branch:)` scoping, asserting no cross-stack mutation occurs there, to show the divergence is specific to `StatusHandler`.

      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
