### Title
Free, unlimited pre-commit simulation of AA triggers via `light/dry_run_aa` allows deterministic gambling AAs to be "solved" before paying — analog of the nutsgambling roll-back exploit ([File: network.js])

### Summary
The `light/dry_run_aa` network command (handled in `network.js:3939-3963`) lets any unprivileged peer submit an arbitrary `trigger` object (including fully attacker-controlled `trigger.data`) against any deployed AA address and receive the *exact*, deterministic simulated result — response messages, bounce/no-bounce outcome, and updated state vars — without ever broadcasting a real unit or paying anything. This is functionally the same "test-before-you-pay" primitive that the EOS `nutsgambling` attacker abused via roll-back of deferred transactions: an attacker can bet the outcome for free, and only commit funds (broadcast the real trigger unit) once it knows the bet wins.

Any "randomness" inside an AA (`number_from_seed`, `sha256`) is a pure deterministic function of inputs the caller controls or already knows before broadcasting — e.g. `trigger.data`, `trigger.address`, `mci`, `mc_unit`: [5](#0-4) 

Because `dryRunPrimaryAATrigger` only fixes `trigger.unit` to the constant `GENESIS_UNIT` (not a real, unpredictable hash), any gambling AA that seeds its RNG from `trigger.data` (a common, documented oscript pattern — see `number_from_seed`/`data_feed` usage in the AA test-suite and sample gambling-style contracts) is fully and freely "solvable" offline: an attacker can iterate different `trigger.data` values through repeated `light/dry_run_aa` calls (each is stateless, free, and leaves no trace) until it finds a `trigger.data` value that produces a winning payout, and only then construct and broadcast the real unit with that exact data.

This is the direct architectural analogue of the EOS `nutsgambling` incident: in EOS, the attacker exploited inline-action rollback to discard losing attempts without cost and replay until a win; in ocore, `light/dry_run_aa` provides an explicit, sanctioned "free replay" oracle for AA outcomes, eliminating the cost-of-trial that a fair game (based on probability) depends on for house edge / statistical profitability.

### Impact Explanation
Any AA design that uses attacker-suppliable inputs (`trigger.data`, or any value derivable before the real unit is signed) as a randomness seed, and that is not otherwise protected by unpredictable, poster-uncontrollable entropy (e.g., a value determined only after unit assembly, such as `response_unit`, `trigger.unit`, or a witness/oracle-provided value posted *after* the bet is locked in) can be drained: the attacker submits `light/dry_run_aa` requests until finding a winning `trigger.data`/outcome combination for free, then broadcasts only the winning bet. This is a concrete AA fund-loss vector (Medium/High depending on AA design prevalence) analogous to the EOS incident's "roll back until you win" pattern; it does not require any privileged position — any node peer (light or full) can issue the request.

### Likelihood Explanation
Likelihood depends on whether deployed AAs seed randomness from attacker-controlled/known-in-advance values. Given that `number_from_seed` is a first-class oscript primitive documented and used in test AAs/sample contracts for gambling-style logic, and that `light/dry_run_aa` is a standard, unauthenticated, network-exposed light-wallet API with no rate limiting visible in the handler itself, the attack surface is realistic for any casino/lottery-style AA that does not deliberately avoid attacker-predictable seeds.

### Recommendation
- AA authors writing gambling/lottery logic must avoid seeding `number_from_seed`/`sha256` randomness from data that is fully known to the trigger author before broadcast (`trigger.data`, `trigger.address`, `params`); instead they should rely on entropy unknown until after the bet is irrevocably committed (e.g., combine with `response_unit`, a future oracle/data_feed value posted by an independent party after the trigger, or a committed hash-then-reveal scheme).
- At the platform level, consider making `dryRunPrimaryAATrigger`'s simulated `trigger.unit`/`response_unit` non-trivially predictable/unusable for outcome-grinding (e.g., explicitly documenting that dry-run results must never be relied upon as proof of a real trigger's outcome, and ensuring randomness primitives depending on `trigger.unit`/`response_unit` fail deterministically differently in dry-run vs. real execution) so that grinding via dry-run cannot be used to pre-validate a winning bet.
- Consider rate-limiting/attributing `light/dry_run_aa` per-peer given it allows unlimited free computation against arbitrary AAs.

### Proof of Concept
1. Attacker connects to a full node as a light peer and repeatedly sends `light/dry_run_aa` with `params.address` = a deployed gambling AA and varying `params.trigger.data` (e.g. incrementing a `seed` field used by the AA's `number_from_seed(trigger.data.seed)` logic).
2. Each call is evaluated for free via `aa_composer.dryRunPrimaryAATrigger` (network.js:3939-3963 → aa_composer.js:272-306), and the DB/batch changes are always rolled back/cleared, so there is no cost, no rate limiting, and no on-chain trace.
3. Attacker inspects `arrResponses[i].objResponseUnit`/`updatedStateVars` returned in each response to determine the winning payout for that `trigger.data` value.
4. Once a winning `trigger.data` is found, the attacker constructs and broadcasts the real trigger unit with that exact `data`, guaranteeing a win and draining the AA's funds — the same "only pay when you know you'll win" pattern the `nutsgambling` attacker used via EOS transaction rollback.
