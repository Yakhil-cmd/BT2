### Title
Webhook signature is verified against one organization while handlers act on a different, attacker-controlled repository — cross-organization/cross-repository writes ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to authenticate an inbound webhook based on `repository_owner`, which is parsed from the payload itself (`params.dig('repository', 'owner', 'login')`). However, every `Webhooks::Handlers::*` class that subsequently processes the same payload identifies which `Repository`/`Stack` to act on using a *different* field of the same payload: `repository.full_name` (via `Handler#repository_name` and the various `Shipit::Repository.from_github_repo_name(params.repository.full_name)` calls). Nothing in the request pipeline enforces that `repository.owner.login` (the field whose organization key selected the verifying secret) matches the owner encoded in `repository.full_name` (the field the handlers actually act on). This is structurally identical to the reported bug class: a verification check covers one field/selector while the code that executes the privileged action is driven by a different, unchecked field — creating an addressable ("shadowed") action that bypasses the intended trust boundary.

### Finding Description
- `verify_signature` looks up the signing secret with `Shipit.github(organization: repository_owner)` and validates the raw POST body's HMAC against that organization's `webhook_secret`: [1](#0-0) 
- `repository_owner` is derived from the payload's `repository.owner.login` (or `organization.login`) field: [2](#0-1) 
- Once the signature check passes, the full, unconstrained `params` hash (including any attacker-chosen `repository.full_name`) is dispatched to every registered handler for the event: [3](#0-2) 
- All handlers resolve the target `Repository`/`Stack` purely from `repository.full_name`, e.g. `Handler#repository_name`: [4](#0-3) 
and pull-request handlers such as `PullRequest::ClosedHandler#repository`, `LabeledHandler#repository`, `ReopenedHandler#repository`, `UnlabeledHandler#repository`, `AssignedHandler#repository`, `EditedHandler#repository`: [5](#0-4) [6](#0-5) [7](#0-6) 

None of these handlers cross-check `repository.owner.login` (the field the signature-selecting organization was based on) against `repository.full_name` (the field determining which real-world `Stack`/`Repository` is mutated).

The binding that should hold is:
`organization used to select/validate the webhook secret == owner of the repository actually mutated by the handler`

but the engine only enforces:
`HMAC(raw_body, secret_of(payload["repository"]["owner"]["login"])) == signature`

while acting on `payload["repository"]["full_name"]`, a sibling field of the *same, attacker-fully-controlled JSON body* that is never required to be consistent with `owner.login`.

### Impact Explanation
Shipit explicitly supports hosting multiple GitHub organizations on one instance, each with its own GitHub App and `webhook_secret`, sharing the single `POST /webhooks` route (`resources :webhooks, only: :create` in `config/routes.rb`): [8](#0-7) 
and `Shipit.github(organization:)` is documented to be looked up dynamically per organization key: [9](#0-8) 

Any GitHub organization admin who legitimately controls their own onboarded org's `webhook_secret` (a low-privilege operation relative to any *other* tenant organization on the same Shipit instance) can construct and correctly sign a JSON body where `repository.owner.login` is their own org (so the HMAC check passes against their own secret) but `repository.full_name` names a repository belonging to a completely different, more-privileged organization also configured on the instance. Because handlers resolve the target purely from `repository.full_name`, this forges cross-organization/cross-repository events: e.g. `PushHandler` will call `stack.sync_github(expected_head_sha: ...)` for a victim org's stack: [10](#0-9) 
and PR handlers will archive/unarchive review-stacks or overwrite pull-request state for a victim repository: [11](#0-10) 

This is a cross-repository/cross-organization write triggered by forging a signature binding, matching the "unauthorized deploy/rollback" and "cross-repository writes" impact category.

### Likelihood Explanation
Requires: (1) the target Shipit instance to be configured for multiple GitHub organizations (documented, supported feature), and (2) attacker control of a `webhook_secret` for any one of those organizations — which is a normal, low-privilege administrative capability scoped to that attacker's own org, not the victim org. No GITHUB_TOKEN, `api_clients_secret`, or Shipit session is required; the exploit is entirely a crafted HTTP POST to the public `/webhooks` endpoint. Likelihood is moderate-to-high specifically in multi-tenant deployments, which the engine markets as a first-class configuration.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification, require that every organization-scoped identifier in the payload (`repository.owner.login`, `organization.login`) matches the organization whose secret validated the signature, and reject (422) on mismatch. Equivalently, `Handler#repository_name`/`from_github_repo_name` resolution should additionally assert that the resolved `Repository`'s owner equals the verified `repository_owner` before any handler mutates state, closing the gap between the field covered by the HMAC-selection logic and the field actually acted upon.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (attacker is admin, knows `webhook_secret_A`) and `victim-org` (onboarded separately, has stack `victim-org/prod-app`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/prod-app",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker signs the raw body with `webhook_secret_A` (which they legitimately possess for `attacker-org`) and sets `X-Hub-Signature` accordingly, then POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `attacker-org`'s app, and the HMAC check passes.
5. `PushHandler` is invoked with the full payload; `repository_name` resolves to `victim-org/prod-app`, and `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` executes against the victim's stack — despite the request never being authenticated against `victim-org`'s webhook secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
