### Title
`StatusHandler#process` writes cross-repo Status records by matching commit SHA globally, independent of `params.branches` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` never reads `params.branches`, so the branches array's presence, absence, or content has no effect on whether the write occurs. The actual gating value is `params.sha`, matched against `Commit.where(sha: ...)` across the entire `commits` table with no repository/stack scoping at all, so the "gap" the question focuses on (branch filtering) is real but is really a symptom of a broader missing repository-scoping check.

### Finding Description
The claimed binding — "`params.branches` content is a required precondition gating the cross-repo write" — is false as stated, but not because branches are checked elsewhere; it's false because `process` doesn't scope by repository at all, branches included: [1](#0-0) 

`process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
It ignores `params.branches` entirely and also ignores the `stacks`/`repository_name` helper defined on the base `Handler` class [2](#0-1) , unlike other handlers such as `LabeledHandler` which resolve a `stack` from `payload['repository']['full_name']` [3](#0-2) .

Before both equality sides:
- Claimed: `params.branches present/non-empty == required to permit write`.
- Actual: `params.branches (any value, including omitted or []) == irrelevant to write`; the only gating value is `params.sha` matched with no repository filter, i.e. `Commit.where(sha: params.sha)` can return commits belonging to *any* stack in the database that happen to share that SHA.

`create_status_from_github!` then writes a `Status` scoped to whatever `stack_id` the matched `Commit` record belongs to [4](#0-3) , which is not necessarily the stack/repository that signed the incoming webhook.

Reachability: `WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event('status')`, i.e. `StatusHandler.call(params)` [5](#0-4) . Before dispatch, `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and validates the HMAC signature using the webhook secret configured for that *organization* [6](#0-5) [7](#0-6) . This check authenticates that the payload came from GitHub for that org — it does **not** verify that the `sha` field actually belongs to a commit reachable from that org/repo's history. If an attacker owns (or forks) a repository that shares git history with a victim's tracked repository (e.g., a fork), a real, validly-signed GitHub status webhook for the attacker's own repo can carry a `sha` that also exists as a `Commit` row under the victim's stack (created via prior push/PR sync). `StatusHandler#process`'s unscoped `Commit.where(sha: ...)` query will then update the victim's `Commit`/`Status` too, regardless of what `branches` the attacker's webhook declares (empty, omitted, or forged) — because that field is never read.

### Impact Explanation
A validly-authenticated webhook for organization A can cause a `Status` write against a `Commit` (and its owning `Stack`) belonging to organization B, whenever the two share a commit SHA (fork/shared-history scenario). This is a cross-repository/cross-tenant record write triggered by an unprivileged party who only controls their own fork — matching the "payload for one repository mutating another's stack/commit" Critical category. The `branches` array is a red herring: its content, presence, or absence never changes the outcome since it's never referenced in `process`. The attacker's leverage is entirely the choice of `sha`, not `branches`.

### Likelihood Explanation
Requires: (1) the attacker owns/controls a GitHub repository configured as a Shipit-tracked repo (or one they can push signed webhooks for, i.e., legitimate GitHub-signed traffic for their own org — no `webhook_secret` needed since GitHub itself signs it), and (2) that repository shares at least one commit SHA with the victim's tracked repository (e.g., attacker forked the victim repo, so `Commit` rows for that SHA exist under both stacks after normal push/PR ingestion). This is a plausible, low-cost scenario for any public open-source project accepting forks/PRs — not a contrived edge case.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stacks belonging to the repository named in the webhook payload (using the existing `stacks` helper from `Handler`) rather than a bare `Commit.where(sha: params.sha)` across the whole table, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent stack-scoped query, mirroring what other handlers (e.g., `LabeledHandler`) already do.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`, out-of-scope path noted only for reference — actual test would live under the engine's existing test suite):
1. Create `stack_a` for repo `victim/repo` and `stack_b` for repo `attacker/repo`.
2. Create `Commit` with `sha: 'deadbeef'*5` under `stack_a` (victim).
3. Create a second `Commit` with the same `sha` under `stack_b` (simulating shared fork history).
4. Build a status payload with `repository.full_name = 'attacker/repo'`, `sha = 'deadbeef'*5`, `branches: []` (or key omitted).
5. Call `StatusHandler.call(payload)`.
6. Assert both `stack_a`'s commit and `stack_b`'s commit received a new `Status` row — proving the write on the victim's (`stack_a`) commit occurred despite the payload declaring `attacker/repo` and regardless of the `branches` value.
7. Repeat with `branches: [{name: 'main'}]` (attacker-chosen) and confirm identical outcome — demonstrating `branches` content has zero effect on both sides of the equality.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
