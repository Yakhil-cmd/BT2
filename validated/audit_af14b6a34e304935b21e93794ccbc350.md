## Title
Webhook signature scoped to `repository.owner.login`/`organization.login` is verified against one GitHub App's secret, while the payload's `repository.full_name` (used to select the target `Stack`) is never covered by that binding — allowing cross-organization webhook forgery in multi-app deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body, then verifies the raw body against that org's secret. Once verified, the whole raw body — including a *different* `repository.full_name` field used later by webhook handlers — is dispatched to handlers unchanged. In a multi-GitHub-App deployment (`Shipit.github(organization: ...)`, as documented in `docs/setup.md` "Using Multiple Github Applications"), a party who possesses OrgA's `webhook_secret` can sign a payload where `repository.owner.login == "OrgA"` (to pass verification) but `repository.full_name == "OrgB/some-repo"` (to select an OrgB stack for processing).

### Finding Description
`verify_signature` computes the org used for secret lookup from body content, not from anything cryptographically tied to it: [1](#0-0) [2](#0-1) 

The secret used for HMAC verification comes from `Shipit.github(organization: repository_owner)`, which resolves to a per-organization `GitHubApp` instance holding its own `webhook_secret`, as configured in `docs/setup.md` for the multiple-GitHub-App case: [3](#0-2) [4](#0-3) 

`verify_webhook_signature` only proves that *some* field derived as `repository_owner` matches the secret holder; it does not prove that every other field in the body (in particular `repository.full_name`) actually belongs to that same organization. After verification, `create` re-parses the same raw body and dispatches it, unmodified, to handlers: [5](#0-4) 

Handlers determine the target `Stack` using `repository.full_name`, a completely separate field from the one used for signature-secret selection: [6](#0-5) [7](#0-6) 

`Repository.from_github_repo_name` splits this field to find any repository/owner pair in the database, without any cross-check against `repository.owner.login`: [8](#0-7) 

This is exactly the "organization that authenticated versus the repository that is written" binding-break pattern: the signature proves authenticity for OrgA (`repository.owner.login`), but the code that decides *which repository/stack gets mutated* trusts `repository.full_name` — a field the signature check never separately validates against the authenticated organization.

### Impact Explanation
In a single-GitHub-App deployment this is not exploitable because there's only one shared `webhook_secret`, and possessing it already implies broad trust. However, per the documented "Using Multiple GitHub Applications" configuration (`docs/setup.md`), each organization has its **own** app/secret specifically to segregate trust between organizations. The `verify_signature`/handler split defeats that segregation: an attacker (or compromised low-privilege actor) who obtains OrgA's `webhook_secret` — which was intended to only authorize webhooks for OrgA's repositories — can forge a signed payload whose `repository.owner.login` says "OrgA" (satisfying the signature check) while `repository.full_name` names an OrgB repository. Handlers like `PushHandler` then trigger `stack.sync_github` on the OrgB stack, and other handlers act on OrgB commits/PRs/deploy status — a cross-organization write triggered without ever having OrgB's own secret. This crosses the "cross-repository writes" / "unauthorized deploy" impact bar for organizations that were explicitly isolated via separate GitHub Apps.

### Likelihood Explanation
Requires possession of one organization's `webhook_secret` in a multi-app setup — the same secret an attacker would need to forge webhooks for that organization anyway. But that secret is *only supposed to authorize actions within that organization's own repositories*; the bug lets it authorize webhook effects against any other configured organization's stacks. This is a low-effort escalation once one org's secret is compromised, and multi-app configuration is documented as a first-class supported deployment mode.

### Recommendation
After signature verification succeeds for `repository_owner`, cross-validate that `repository.full_name`'s owner segment matches the same `repository_owner`/organization used to select the secret before dispatching to handlers (or resolve the `Repository`/`Stack` using the authenticated organization rather than trusting `full_name` alone in `Handler#repository_name`).

### Proof of Concept
1. Deploy Shipit with two GitHub Apps configured, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md`).
2. Obtain/leak `OrgA`'s `webhook_secret` (e.g., via OrgA's own GitHub App settings — a credential scoped only to OrgA).
3. Craft a `push` event JSON body: `{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/target-repo"}, "ref": "refs/heads/main", "after": "<attacker-controlled sha>"}`.
4. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)`.
5. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` looks up `Shipit.github(organization: "OrgA")` and successfully verifies the signature against OrgA's secret.
6. `create` dispatches the parsed body to `PushHandler`, which reads `repository.full_name` = `"OrgB/target-repo"`, resolves an `OrgB` stack via `Repository.from_github_repo_name`, and triggers `stack.sync_github(expected_head_sha: "<attacker sha>")` — an OrgB stack is synced/deployed using a signature that only proved possession of OrgA's secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
