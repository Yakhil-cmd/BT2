### Title
Webhook signature verification keys off `repository.owner.login` while handlers act on the independently-controlled `repository.full_name` — cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-org Shipit deployments (`secrets.github` configured with per-organization sub-keys), `WebhooksController#verify_signature` selects the HMAC secret to validate the request using `repository.owner.login`/`organization.login` pulled straight out of the still-unverified JSON body. Every webhook handler, however, resolves the target repository/stacks using a *different* field from that same untrusted body: `repository.full_name` (`Handler#repository_name`). Because these two fields are never cross-checked, an attacker who legitimately knows one organization's `webhook_secret` can forge a signature that passes verification while pointing the payload's `repository.full_name` at a stack belonging to a completely different organization tracked by the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config via: [1](#0-0) [2](#0-1) 

`repository_owner` is read from the same JSON body whose signature it is about to check — it is trusted before verification and used only to look up which secret to verify against, via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Once the signature check passes (using whatever org's secret matched `repository_owner`), the full unmodified body is handed to the handlers: [4](#0-3) 

All handlers derive the actual target repository not from `repository.owner.login` but from `repository.full_name`: [5](#0-4) [6](#0-5) 

Nothing enforces `repository.owner.login == repository.full_name.split('/').first`. An attacker who administers/operates one org configured in Shipit (and thus has legitimate access to that org's `webhook_secret`, e.g. because they set up their own GitHub App integration under a multi-tenant Shipit config) can:
1. Compute a valid `X-Hub-Signature` over a crafted JSON body using their own org's known `webhook_secret`.
2. Set `repository.owner.login` (or `organization.login`) to their own org so `verify_signature` picks their own secret and passes.
3. Set `repository.full_name` (used by `PushHandler`, `StatusHandler`, etc.) to `victim-org/some-repo`, a repository belonging to an entirely different organization tracked by the same Shipit instance.

This breaks the intended binding: `organization whose secret authenticated the request == organization whose repository is acted upon`.

### Impact Explanation
With a forged, "verified" webhook the attacker can drive handlers against a victim organization's stacks:
- `PushHandler#process` invokes `stack.sync_github(expected_head_sha: params.after)` on any not-archived stack matching the forged `branch`/`full_name`, for a victim repo they do not control: [7](#0-6) 
- `StatusHandler#process` writes a `Status` (`state`, `context`, `target_url`, `description`) onto any existing `Commit` matching the forged `sha`, regardless of which org/repo that commit belongs to: [8](#0-7) 

Since commit statuses are used elsewhere in Shipit to gate whether a commit is considered "deployable" (CI green), an attacker can inject a fabricated `success` status for a commit in a victim organization's repository they have no write access to, which can influence deploy-readiness checks in that other org's stack — an unauthorized-deploy-enabling, cross-repository write. This satisfies the "cross-repository writes / unauthorized deploy" bucket. The `MembershipHandler` similarly trusts `params.organization.login` for team scoping without tying it back to the signature-verifying org: [9](#0-8) 

### Likelihood Explanation
This only applies when the operator runs Shipit in the documented multi-organization mode (`secrets.github` keyed by org, each with its own `webhook_secret`) — i.e. more than one organization's traffic is served by one Shipit instance, which is an explicitly supported configuration (`Shipit.github_organizations`, `github_app_config`). An attacker only needs to be a legitimate operator/holder of one tenant's `webhook_secret`, no privileged Shipit account, GitHub write access, or session is required — they interact solely with the public `/webhooks` endpoint. This is a realistic multi-tenant deployment scenario and requires no code execution or MITM, only knowledge of one org's own webhook secret and the ability to POST a crafted JSON body.

### Recommendation
After signature verification, hard-fail the request unless the organization that authenticated the request matches the owner encoded in `repository.full_name` (and `organization.login` for org-scoped events). Concretely, in `WebhooksController#verify_signature`/`create`, compare `repository_owner` (used to pick the secret) against `params.dig('repository', 'full_name')&.split('/')&.first` (and equivalently for `organization` events) and reject (422) on mismatch before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `attacker-org` (secret `S1`, controlled/known by attacker) and `victim-org` (secret `S2`, unknown to attacker), each with repos tracked as stacks.
2. Attacker builds a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/critical-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S1, body)>` using their own known secret `S1`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner == "attacker-org"`, loads `attacker-org`'s `GitHubApp`, and successfully verifies the signature with `S1`.
5. `PushHandler#process` runs against `Repository.from_github_repo_name("victim-org/critical-repo")`, invoking `sync_github` on victim-org's stack — despite the request never being authenticated by `victim-org`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
