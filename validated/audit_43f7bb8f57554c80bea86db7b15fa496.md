### Title
Blank-`webhook_secret` bypass lets forged webhooks set commit status on any commit in any stack, unblocking merges/deploys - ([File: lib/shipit/github_app.rb], [File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify a webhook against using only `repository.owner.login` (or `organization.login`) from the unauthenticated request body [1](#0-0) . `GithubApp#verify_webhook_signature` skips HMAC verification entirely whenever that organization's configured `webhook_secret` is blank [2](#0-1) . Once past that check, `StatusHandler#process` writes a commit status using only `Commit.where(sha: params.sha)` — with **no repository/organization scoping at all** [3](#0-2) . The binding between "which organization was authenticated" (or, in this case, not authenticated) and "which commit/repository is mutated" is completely broken.

### Finding Description
This mirrors the Bond `findMarketFor`/`payoutFor` bug class: a check is performed over one input (`minAmountOut_` vs `maxPayout`) while the action is taken over a different, unguarded input (`amountIn_`). Here:

- The verification gate keys off `repository_owner`, itself pulled from the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [4](#0-3) .
- `Shipit.github(organization: repository_owner)` resolves per-org config, and `verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank: `return true unless webhook_secret` [5](#0-4) .
- After this gate, `create` dispatches the entire attacker-controlled JSON body to every handler for the event, unmodified: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) .
- `StatusHandler` (event `status`) never re-derives or checks a repository at all — it looks up `Commit.where(sha: params.sha)` globally across the whole Shipit instance and calls `commit.create_status_from_github!(params)` [3](#0-2) .

So the equality the deployment trust model is supposed to hold is:
`organization whose signature was verified == organization/repository whose commit status is mutated`

Before the attack: only GitHub, holding the real per-org `webhook_secret`, could produce a valid signature for org X's webhooks, and only commits belonging to org X's repositories would be affected.

After the attack: if **any** configured organization in `Shipit.github` config has a blank `webhook_secret` (a supported configuration state, as shown by the shipped sample `webhook_secret: # nil` in `config/secrets.development.shopify.yml`), an attacker can send an arbitrary `status` webhook claiming `repository.owner.login`/`organization.login` equal to that blank-secret org. `verify_signature` passes trivially (no HMAC needed), and `StatusHandler` then updates the commit status for **any commit sha in any stack/repository across the entire installation** — completely decoupled from the org that "authenticated."

### Impact Explanation
Commit statuses gate CI-based decisions in Shipit (blocking statuses in `shipit.yml`, merge-queue eligibility, deployable checks). An attacker who can forge a `success` status for a commit that never actually passed CI can push that commit through the merge queue or unlock a deploy that should have been blocked, without ever needing a Shipit session, API token, or the real `webhook_secret` for the targeted repository. This falls under "unauthorized deploy, rollback, or merge" (Critical) since the trust boundary broken is exactly organization-authenticated vs. repository/commit-affected, as called out in the allowed analog list.

### Likelihood Explanation
Requires only that one configured GitHub organization on the instance have no `webhook_secret` set — a state the engine explicitly tolerates (`return true unless webhook_secret`) rather than rejecting, and which is documented as a valid setup in the shipped sample config. Once that condition holds for any org, exploitation needs a single unauthenticated POST to `/webhooks` with a crafted `status` payload; no credentials, tokens, or write access are required.

### Recommendation
- Do not silently bypass signature verification when `webhook_secret` is blank; either require a secret to be configured for every organization or explicitly reject/flag such webhooks as untrusted.
- Scope `StatusHandler` (and any other handler that queries by global attributes like `sha`) to the repository identified in the verified webhook, rather than querying `Commit` globally.
- Ensure the organization used for signature verification is cryptographically tied to the repository/commit acted upon, not just two independent, unauthenticated fields in the same JSON body.

### Proof of Concept
1. Operator configures Shipit with two GitHub orgs: `victim-org` (has a real `webhook_secret`) and `blank-org` (no `webhook_secret`, e.g. left `nil` as shown in the sample config).
2. Attacker knows (or brute-forces/enumerates) a commit `sha` belonging to a stack under `victim-org/some-repo` that is currently blocked from merging/deploying by a failing/pending CI status.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "organization": { "login": "blank-org" },
  "repository": { "owner": { "login": "blank-org" }, "full_name": "blank-org/irrelevant" }
}
```
No `X-Hub-Signature` value is needed to pass verification, since `webhook_secret` for `blank-org` is blank.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'blank-org')`, whose `verify_webhook_signature` returns `true` unconditionally [5](#0-4) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a `success` status onto the victim commit in `victim-org/some-repo` — a repository the attacker never authenticated against [3](#0-2) .
6. If that status is a blocking CI check, the commit can now proceed through merge/deploy despite never having passed real CI.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
