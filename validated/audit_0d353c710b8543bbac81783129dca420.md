Confirmed: the default/initial value of `tps_fee_multiplier` is `10` [1](#0-0) , and it is a governance-votable system var (like `base_tps_fee`, `tps_interval`) that OPs can change over time [2](#0-1) . This confirms the multiplier is a real, materially significant (10x by default) and mutable scaling factor — matching the report's precondition that "the multiplier can change" and produce a meaningful discrepancy, not a benign edge case.

### Title
`getFinalTpsFee()` drops `tps_fee_multiplier` while `getLocalTpsFee()`/validation apply it, corrupting the tps-fee ledger - (File: storage.js)

### Summary
The tps-fee anti-spam mechanism requires every non-AA unit to prepay a tps fee, verified against `getLocalTpsFee()` at validation time, and later reconciled into a per-address running balance (`tps_fees_balances`) using `getFinalTpsFee()` once the unit stabilizes. `getLocalTpsFee()` scales the fee by the system var `tps_fee_multiplier`, but `getFinalTpsFee()` — used to compute the "true" fee that is credited/debited against the ledger — omits this multiplier entirely, exactly mirroring the `extendLock()`/`increaseLock()` inconsistency in the reported issue (one code path retroactively applies a scaling factor that the sibling path does not).

### Finding Description
`getLocalTpsFee()` computes the required prepaid fee as:
```
tps_fee_per_unit = round(tps_fee_multiplier * base_tps_fee * (exp(tps/tps_interval) - 1))
``` [3](#0-2) 

This is what `validateTpsFee()` uses to compute `min_tps_fee`, the minimum a poster must attach as `objUnit.tps_fee` [4](#0-3) , and it's also what the composer uses (via `parentComposer.getLocalTpsFee`/`getTpsFee`) to decide how much `tps_fee` to actually attach to a newly composed unit [5](#0-4) .

However, once a unit stabilizes, `updateTpsFees()` recomputes the "actual" fee that should have been charged using `getFinalTpsFee()`:
```
tps_fee = round(base_tps_fee * (exp(tps/tps_interval) - 1))   // no tps_fee_multiplier
``` [6](#0-5) 

and then computes the delta between what was actually paid (which included the multiplier) and this final, un-multiplied amount, crediting the difference back into `tps_fees_balances` for the payer's address:
```
const tps_fee = getFinalTpsFee(objUnitProps) * (1 + (objUnitProps.count_aa_responses || 0));
...
const total_tps_fees_delta = (objUnitProps.tps_fee || 0) - tps_fee; // can be negative
...
await conn.query("REPLACE INTO tps_fees_balances ... VALUES(?,?, tps_fees_balance + tps_fees_delta)");
``` [7](#0-6) 

With the default `tps_fee_multiplier = 10` [1](#0-0) , `getFinalTpsFee()` returns roughly 1/10th of what `getLocalTpsFee()` demanded for the same congestion level. Since the "final" (settlement) fee is silently ~10x smaller than the "required" (validation) fee for the same tps, `total_tps_fees_delta` will be systematically inflated for every unit that pays close to the minimum required fee, and this surplus is credited back into `tps_fees_balances`. That balance is directly consumed later by `getPaidTpsFee()`/`validateTpsFee()` to offset the fee required on future units from the same address (or headers-commission recipients) [8](#0-7) [9](#0-8) .

### Impact Explanation
This is the same root-cause pattern as the reported issue: a multiplier is applied on one calculation path but silently dropped on the semantically-equivalent sibling path, causing a persistent, protocol-visible discrepancy in an accounting ledger. Concretely:
- Any unposted-privilege unit author benefits automatically and without any special action from this discrepancy, since it fires on every stabilized unit through `updateTpsFees()`, which runs unconditionally as part of stability advancement.
- Because the credited surplus accumulates in `tps_fees_balances` and directly reduces the tps fee required on subsequent units (`getPaidTpsFee`/`validateTpsFee`), the tps-fee anti-congestion mechanism becomes systematically under-collecting relative to what governance (the `tps_fee_multiplier` vote) intended, weakening the network's ability to price/throttle spam during congestion — the exact mechanism this fee was designed to protect (tps-based congestion control safeguarding the network's ability to confirm units at a sustainable rate).
- The magnitude of the miscalculation is governed directly by the `tps_fee_multiplier` system var (currently 10x), so the discrepancy is not a rounding artifact but a full order-of-magnitude gap.

### Likelihood Explanation
`updateTpsFees()` runs on every stabilized main-chain interval for every non-AA unit; the bug is deterministic and requires no attacker action beyond normal unit posting, since the discrepancy is baked into the formula difference between `getLocalTpsFee` and `getFinalTpsFee`.

### Recommendation
Apply `tps_fee_multiplier` consistently in `getFinalTpsFee()` (storage.js:1238) the same way it is applied in `getLocalTpsFee()` (storage.js:1339), i.e. multiply `base_tps_fee * (exp(tps/tps_interval)-1)` by `getSystemVar('tps_fee_multiplier', mci)` before rounding, so that the settlement/ledger-crediting formula in `updateTpsFees()` matches the requirement formula used in `validateTpsFee()`/`getLocalTpsFee()`.

### Proof of Concept
1. Network is running with `tps_fee_multiplier = 10` (the deployed default) [1](#0-0) .
2. A unit is posted paying `tps_fee` equal to the minimum required by `validateTpsFee()`, i.e. `min_tps_fee = getLocalTpsFee(...)`, which internally is `10 * base_tps_fee * (exp(tps/tps_interval)-1)` [3](#0-2) [10](#0-9) .
3. Once the unit stabilizes, `updateTpsFees()` computes the "actual" fee via `getFinalTpsFee()` = `base_tps_fee * (exp(tps/tps_interval)-1)` (no `x10`) [6](#0-5) .
4. `total_tps_fees_delta = paid_tps_fee - actual_tps_fee ≈ 9 * base_tps_fee * (exp(tps/tps_interval)-1)`, i.e. roughly 90% of what was paid is credited back to the author's `tps_fees_balances` entry [7](#0-6) .
5. That credited balance is then consumed to reduce/eliminate the tps fee requirement on the same address's future units via `getPaidTpsFee()` [8](#0-7) , letting the author post subsequent units far below the fee level that the governance-configured multiplier was meant to enforce, undermining the tps-based anti-spam/congestion-control mechanism network-wide.
