### Title
Attacker-controlled submodule reference can cause unbounded per-sync hangs and persistent sync denial in `configureWorktree` — (File: `main.go`)

### Summary
`git-sync` clones an operator-specified `--repo` and, by default (`--submodules=recursive`), recursively initializes/updates any submodules declared inside that repository's tree. Submodule URLs are untrusted content that comes from whatever commit is currently checked out — i.e., from the repo content itself, not from an operator-controlled flag. An attacker who can push a commit to the synced repo (or to any ref that `--ref` follows) can add or repoint a `.gitmodules` entry to an unresponsive, slow, or otherwise "paused" remote. Because `git submodule update --init --recursive` is executed inside the very same bounded context used for the rest of the sync (`fetch`, `reset`, worktree creation, publish), this single call can consume the whole `--sync-timeout` budget on every single sync attempt, indefinitely preventing git-sync from ever completing a sync and publishing new content — directly analogous to the reported NFT-pause issue, where an externally-controlled dependency that can stall/"pause" blocks the entire operation while the caller is stuck retrying with no way to bypass it.

### Finding Description
`configureWorktree` unconditionally runs the submodule update step whenever submodules are not disabled: [1](#0-0) 

This call shares the same `context.Context` (and thus the same deadline) as the rest of the sync pipeline. That context is created once per sync-loop iteration with a fixed timeout of `--sync-timeout` (default 120s): [2](#0-1) 

`SyncRepo` runs `fetch`, worktree creation, and `configureWorktree` (which performs the submodule fetch) sequentially against this single deadline: [3](#0-2) 

The submodule URL itself is not controlled by the git-sync operator — it comes from `.gitmodules` in whatever commit is currently synced, which is untrusted content from the tracked repo/ref. If that URL points to a host that never responds (or is deliberately slow, similar to how CryptoKitty/CryptoFighter can pause `transfer`/`transferFrom`), the `git submodule update` invocation will hang until the shared context's deadline fires, causing the whole `SyncRepo` call to fail with a timeout error on every single sync attempt, since the underlying `.gitmodules` state persists across syncs until further malicious content changes it back. The e2e test harness even has a dedicated tool (`_test_tools/git_slow_fetch.sh`) demonstrating this exact hang class against `fetch`, confirming that slow/unresponsive git operations are a recognized failure mode: [4](#0-3) 

On failure, the main loop increments `failCount` and checks it against `--max-failures` (default `0`, meaning "abort after the first failure" since the check is `failCount >= maxFails`): [5](#0-4) 

With the widely-recommended `-1` (retry forever) or any positive `--max-failures` setting — common in long-running sidecar deployments to avoid crash-looping — git-sync will retry the sync every `--period`, but each retry re-triggers the same submodule hang and consumes the full `--sync-timeout` again, forever. With the default `0`, the process exits after the very first hang, and in Kubernetes it will be restarted by the kubelet only to hang identically on the next attempt (since `.gitmodules` content persists in the repo), producing an effectively permanent CrashLoopBackOff. In both configurations, the consumer-facing symlink is never advanced to any commit that includes (or follows) the malicious `.gitmodules` change, and if this is the very first sync, no content is ever published at all.

### Impact Explanation
This matches the accepted "persistent sync denial" impact class: an attacker who can push commits to the tracked repository/ref (untrusted repo content) can permanently deny git-sync's ability to complete syncs by making a submodule URL unreachable/slow, without needing any credential compromise or additional privilege. This mirrors the original report's core mechanic — an externally controlled dependency that can be "paused"/stalled blocks the primary operation (sync = borrowing/repaying), and the caller (git-sync / the borrower) has no way to detect or route around the block, being forced into a permanent failure loop.

### Likelihood Explanation
Likelihood depends on the threat model of who can write to the synced repo/ref. In many real deployments (CI/CD GitOps, multi-tenant repos, or repos that ingest external PRs/commits before merge/sync), an attacker with commit access to the target ref is a realistic actor — the same class of actor implicitly assumed by "untrusted repo content" in this analysis. `--submodules=recursive` is the documented default, so no special operator flag is required for the vulnerable path to be active: [6](#0-5) 

### Recommendation
- Bound the submodule-update step with its own sub-timeout that is meaningfully shorter than `--sync-timeout`, so a single hung submodule cannot consume the entire sync budget, and surface a clear, actionable error distinguishing "submodule fetch hung" from generic sync failure.
- Consider exposing a per-submodule or overall submodule fetch timeout flag independent of `--sync-timeout`.
- Document and/or enforce that operators intentionally opt in to `--submodules=recursive` when the tracked repository content (including submodule pointers) is not fully trusted, and provide guidance to use `--submodules=off` for repos with untrusted contributors.

### Proof of Concept
1. Configure `git-sync` with `--repo=<REPO>`, default `--submodules=recursive`, `--sync-timeout=120s`, and `--max-failures=-1` (retry forever, a commonly recommended sidecar setting).
2. As an attacker with commit access to `<REPO>` (or a ref/branch git-sync tracks), add a `.gitmodules` entry pointing to a URL that is reachable at the TCP level but never completes the git handshake (e.g., a TCP listener that accepts and never responds, or a very slow HTTP endpoint), then commit and push.
3. On the next sync cycle, `git.fetch` succeeds (fetches the new commit including `.gitmodules`), then `configureWorktree`'s `git submodule update --init --recursive` call blocks until the shared `ctx` (bounded by `--sync-timeout`) expires, causing `SyncRepo` to return an error every single cycle.
4. Observe that the published symlink never advances past the last good commit prior to the malicious `.gitmodules` change (or, on first sync, is never created at all), and that this condition persists indefinitely as long as the malicious submodule reference remains in the tracked history — confirmed structurally by the shared-context design in `configureWorktree`/`SyncRepo` and the per-cycle timeout construction in the main loop cited above. (Direct dynamic execution was not performed; this PoC path is derived from static analysis of the cited control flow, not from running the tool live.)
