## Title
Cross-organization webhook signature mismatch enables cross-repository `PullRequest` mutation - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

## Summary
`WebhooksController#repository_owner` selects the `GitHubApp` used for HMAC verification from an attacker-controlled field (`repository.owner.login` or, if absent, `organization.login`), while `AssignedHandler#process` (and sibling PR handlers) locate and mutate the target `PullRequest`/`Repository` using a completely different, independently attacker-controlled field: `repository.full_name`. These two values are never checked for consistency, so the org whose secret validates the signature does not have to be the org that owns the repository actually mutated.

## Finding Description
Binding claimed broken: `org_used_for_signature_verification == org_owning(params.repository.full_name)`.

- `verify_signature` picks the app via `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) .
- `AssignedHandler#process` resolves the target `Shipit::Repository` purely from `params.repository.full_name`, independent of whatever org was used above, then finds/updates a `PullRequest` joined to that repository's stack [2](#0-1) .
- Crucially, `Shipit.github` only differentiates by organization when Shipit is configured in *multi-org* mode (top-level `secrets.github` keyed by org name, e.g. `OrgOne`/`OrgTwo` as in `secrets_double_github_app.yml`). In that mode each org has its **own independent `webhook_secret`** [3](#0-2) . In single-org mode (`github_default_organization` nil, as in the test dummy `secrets.yml`/`secrets.test.json`), the `organization:` argument is ignored entirely and one shared app/secret is always used [4](#0-3) , so the described divergence cannot occur there.
- In multi-org mode, `verify_webhook_signature` **returns `true` unconditionally whenever that org's `webhook_secret` is blank** [5](#0-4) . This is a documented/intentional escape hatch, not a secret an attacker must possess.

Exploit flow (multi-org deployment only): attacker sends `POST /webhooks` with `X-Github-Event: pull_request`, a body containing `action: "assigned"`, `organization: {login: "OrgWithBlankSecret"}`, no `repository.owner`, and `repository.full_name` set to a victim repository belonging to a different configured org whose real webhook secret the attacker does not know. `repository_owner` resolves to `OrgWithBlankSecret` via the fallback; `verify_signature` calls `Shipit.github(organization: "OrgWithBlankSecret")`, whose `webhook_secret` is blank, so verification passes with **no valid signature required at all**. Processing then proceeds using `params.repository.full_name` (the victim org's repo), and `AssignedHandler#process` updates the victim's `PullRequest#github_pull_request` — a write to a stack whose organization never authenticated the request.

This does require a specific, non-default deployment shape (multi-org `secrets.github` configuration with at least one org lacking a `webhook_secret`) to be exploitable without any secret knowledge; the "weak/known secret" variant posed in the question additionally requires possessing/guessing a real secret for some org, which the threat model explicitly disallows for an unprivileged attacker. Existing guards (`drop_unhandled_event`, `check_if_ping`, `ExplicitParameters` schema on `AssignedHandler`) do not check that the verifying org matches `repository.full_name`'s owner, and none of them close this gap.

## Impact Explanation
An attacker who knows only that a given Shipit installation runs in multi-org mode, and that at least one configured org has no `webhook_secret`, can forge PR-assignment (and analogous edited/labeled/closed/opened/reopened) webhook events for **any repository tracked by any other org on the same Shipit instance**, causing writes to `PullRequest` rows (title, state, assignees, labels, head commit, etc.) that belong to a victim tenant, without ever authenticating against that victim's actual GitHub App/secret. This matches "a payload for one repository mutating another's stack" (Critical). It is repeatable per request and applies to every handler that resolves its target repository from `repository.full_name` rather than from the org used for signature verification (also affects `EditedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `OpenedHandler`, `ReopenedHandler`, `LabelCapturingHandler`).

## Likelihood Explanation
Requires: (1) the Shipit instance configured in multi-org mode with more than one org and (2) at least one of those orgs having no `webhook_secret` configured. Single-org deployments (the default/common case, as reflected in `secrets.yml`) are not exploitable this way because the organization argument is ignored by `Shipit.github`. Given the precondition is deployment-specific and not demonstrable purely from this engine's default/test configuration guaranteeing a vulnerable multi-org+blank-secret combination in production, likelihood is conditional on operator configuration rather than universal.

## Recommendation
Do not select the verifying `GitHubApp` from attacker-supplied payload fields that are independent of the repository actually being mutated. Bind the organization used for signature verification to the same repository identifier used for mutation (`repository.full_name`'s owner segment), or verify the signature against every configured org's secret and require the matched org to equal the owner of `repository.full_name` before processing. Additionally, disallow (or explicitly opt-in only) blank `webhook_secret` per-org in multi-org configurations, since it silently disables authentication for that org's webhook endpoint while still being reachable via a spoofed `organization.login`.

## Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or similar), using multi-org fixtures analogous to `secrets_double_github_app.yml` but with `OrgOne.webhook_secret` blank and `OrgTwo` representing the victim org owning `shipit_stacks(:shipit)`'s repository:

```ruby
test "cross-org spoofed organization mutates victim PullRequest" do
  Shipit.stubs(:secrets).returns(multi_org_secrets_with_blank_secret_for_org_one)
  pull_request = shipit_pull_requests(:review_stack_review) # belongs to OrgTwo repo
  pull_request.update!(title: "old title")

  request.headers['X-Github-Event'] = 'pull_request'
  body = JSON.parse(payload(:pull_request_assigned))
  body.delete('repository') # drop repository.owner entirely, replace with just full_name
  body['repository'] = { 'full_name' => pull_request.stack.github_repo_name } # OrgTwo/victim-repo
  body['organization'] = { 'login' => 'OrgOne' } # attacker-chosen org, blank webhook_secret
  body['number'] = pull_request.number
  body['pull_request']['number'] = pull_request.number

  post :create, body: body.to_json, as: :json

  assert_response :ok
  assert_not_equal "old title", pull_request.reload.title # victim row mutated despite no OrgTwo secret used
end
```

Assertion on both sides of the binding: before the request, `org_used_for_verification` ("OrgOne") != `org_owning(repository.full_name)` ("OrgTwo"); after the request, the victim's `PullRequest` was still updated, proving the divergence was not blocked.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
