## Analysis Summary

I found a strong analog matching the requested bug class: the `StatusHandler` binds its write target (a `Commit` by `sha`, resolved **globally across all stacks**) to a field never covered by the webhook-signature-selecting organization, breaking the binding `verified organization == repository/commit actually written`.

### Title
Cross-Organization Status Forgery via Global `sha` Lookup Bypasses Per-Organization Webhook Signature Scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Finding Description
`WebhooksController#verify_signature` selects **which** GitHub App/organization secret to verify the HMAC against using a field taken from the very payload being verified: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . The signature check only proves "this payload was signed by *some* configured organization's webhook secret" [2](#0-1)  — it does not bind that organization to which resource the handler actually mutates.

`Shipit::Webhooks::Handlers::StatusHandler` then processes the `status` event by looking up **any** `Commit` row across the **entire installation** whose `sha` matches the attacker-controlled `params.sha`, with no repository/organization scoping at all: [3](#0-2) 

Compare this to every other handler (`PushHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`, `MembershipHandler`), which all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` or otherwise scope to the repository named in the payload before touching any record, e.g. [4](#0-3) . `StatusHandler` is the outlier: it never validates that `params.repository.full_name` (if present at all — it's not even required by its `params do ... end` block) corresponds to the stack owning the matched commit.

This is exactly the reported bug class translated to this engine: the field used to authenticate/authorize the request (`repository_owner`/`organization.login`, used to pick the signing secret) is decoupled from the field the handler actually acts on (a bare, cross-tenant `sha` match). In a multi-organization Shipit deployment (explicitly supported per `docs/setup.md` and `lib/shipit.rb#github_app_config`), an org that legitimately owns its own GitHub App/webhook secret can sign an arbitrary `status` payload with **its own valid secret** while pointing `sha` at a commit that belongs to a completely different organization's stack.

Binding broken (as an equality):
```
organization whose webhook_secret validated the signature  ==  organization/stack that owns the Commit being written
```
Before the PR (multi-org config as documented), this equality is never checked. Any org’s valid signature authorizes a `Status` write against a commit from any other tracked org, because `Commit.where(sha: params.sha)` has no scope.

### Impact Explanation
`Status#create` triggers `after_commit :schedule_continuous_delivery` [5](#0-4) , and `Commit#create_status_from_github!` → `add_status` feeds into commit state transitions that gate deploys. If the target stack has `continuous_deployment: true`, injecting a `state: "success"` status for the correct commit `sha` on a stack outside the attacker's own organization schedules `ContinuousDeliveryJob`, which calls `stack.trigger_continuous_delivery` and can `trigger_deploy` [6](#0-5)  — an **unauthorized deploy** on a stack/repository the attacker has no legitimate access to, satisfying the "Critical: unauthorized deploy" bar. Getting the correct `sha` only requires knowing a public commit hash of the target repo (trivial for any public GitHub repo, or a private one with a leaked/observed hash).

### Likelihood Explanation
Requires: (1) the Shipit instance is configured with multiple GitHub organizations (an explicitly documented, supported configuration — `docs/setup.md` "Using Multiple Github Applications"), (2) the attacker controls one legitimate, distinct organization/app in that same Shipit instance (their own webhook secret — no Shipit account, API token, or privileged access needed), and (3) the target stack has `continuous_deployment` enabled and a known/guessable commit sha. Given multi-tenant Shipit deployments are a supported first-class use case, this is a realistic configuration, though the attack is scoped to that specific deployment topology.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stack(s) belonging to the same organization/repository that was authenticated by `verify_signature`, mirroring the pattern used by `Handler#stacks`/`Handler#repository_name` in every other handler. Additionally, require and validate `params.repository.full_name` in `StatusHandler`'s `params do...end` block and filter `Commit.where(sha: params.sha, stack: stacks)` rather than an unscoped global lookup.

### Proof of Concept
1. Configure Shipit with two organizations, `victim-org` (tracking `victim-org/app`, `continuous_deployment: true`) and `attacker-org` (attacker's own legitimate GitHub App installation, distinct `webhook_secret`) — per `docs/setup.md` multi-org config.
2. Attacker learns/observes a commit sha `S` on `victim-org/app` that is next in the deploy queue (e.g., via public GitHub API).
3. Attacker crafts a `status` event payload: `{"sha": "S", "state": "success", "context": "ci/forged"}` and signs it with `attacker-org`'s real webhook secret, sending `X-Hub-Signature` computed against that payload.
4. `WebhooksController#verify_signature` resolves `repository_owner` from the payload (absent `repository` key in a minimal status payload, or attacker sets `repository.owner.login = "attacker-org"`), calls `Shipit.github(organization: "attacker-org")`, and the signature validates successfully because it was HMAC'd with `attacker-org`'s own secret [2](#0-1) .
5. `StatusHandler#process` runs `Commit.where(sha: "S")` [3](#0-2) , finds the commit under `victim-org/app`'s stack, and creates a `success` status, triggering `ContinuousDeliveryJob` and an unauthorized deploy on `victim-org`'s stack.
