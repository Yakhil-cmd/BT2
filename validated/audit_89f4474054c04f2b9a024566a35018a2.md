This confirms the vulnerability. The `MembershipHandler` directly grants `Shipit.github_teams` membership (used for app authorization) based purely on the webhook payload, with no cross-check against the actual GitHub state, and the signature verification that gates this event is keyed off an attacker-controlled field decoupled from the actual write target.

### Title
Signature verification key selection (`repository_owner`) is decoupled from the org/repo actually acted upon, allowing webhook signature-check bypass and forged `membership`/`push`/`status` events in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to verify the inbound signature against using `repository_owner`, a value read straight out of the **unverified** JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`). This lookup key is never re-validated against the field the handlers actually act on (`payload.dig('repository','full_name')`, `params.organization.login`, `params.team`, etc.). This is the same class of bug as the reported issue: a key computed for one purpose (looking up the credential to check) is not the same key bound to the object actually mutated afterward.

### Finding Description [1](#0-0) 
`verify_signature` does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
`repository_owner` comes entirely from the attacker-supplied JSON body: [2](#0-1) 

`Shipit.github(organization:)` looks up the app config for that org name only when a multi-org config schema is used (`docs/setup.md`, "Using Multiple Github Applications"): [3](#0-2) 

Critically, `verify_webhook_signature` short-circuits to `true` when the selected app has no `webhook_secret` configured: [4](#0-3) 
and `@webhook_secret = @config[:webhook_secret].presence`, so a blank/omitted secret (shown as the default in the documented example configs) makes verification a no-op for that org: [5](#0-4) [6](#0-5) 

Because `repository_owner` is attacker-controlled and independent from the fields the handlers use to decide what to act on (`payload.dig('repository','full_name')` in `Handler#repository_name`, or `params.organization.login`/`params.team` in `MembershipHandler`), an attacker can pick `repository.owner.login` (or `organization.login`) equal to *any configured org that has no `webhook_secret`* to make `verify_signature` accept the request unconditionally, while setting the rest of the payload (`repository.full_name`, `organization`, `team`, `member`) to target a completely different, real org/stack registered in the Shipit instance: [7](#0-6) [8](#0-7) 

`MembershipHandler#process` grants/revokes `Team` membership purely from the payload, with `Team` records backing `User#authorized?`, which gates access to the entire app via `Shipit.github_teams`: [9](#0-8) [10](#0-9) 

### Impact Explanation
This is a signature-verification-key vs. write-target-key mismatch (the "organization that authenticated versus the repository that is written" binding called out as in-scope). In a multi-org Shipit deployment where at least one configured organization has no `webhook_secret` (the documented default/example), an unauthenticated attacker can forge a `membership` webhook to add an arbitrary GitHub login as a member of an authorized `Team`, which is exactly the set checked by `authorized?`/`force_github_authentication` to gate access to the whole application — an authentication-bypass/escalation into `Shipit.github_teams` authorization. The same mismatch also lets an attacker forge `push`/`status`/`check_suite` events for repositories under organizations that do have a properly configured secret, since the field used to select/verify the signing secret is never checked against the field used to resolve the actual `Stack`/`Repository` being mutated.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (a documented, supported configuration), and (2) at least one configured organization without a `webhook_secret` set — which is exactly what the shipped example configs (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`) show as the default. No session, token, or GitHub credential is needed; the attacker only needs to know the name of one such under-secured configured organization and POST directly to `/webhooks`.

### Recommendation
Do not let the attacker-supplied payload determine which secret is used to validate itself independent of what is acted upon. Verify the signature using the secret bound to the organization that actually owns the resource the handler will mutate (derived consistently, e.g., from the resolved `Repository`/`Stack`/`Team` record after loading, not from raw untrusted payload fields), and require every configured organization to have a non-blank `webhook_secret` (fail closed instead of returning `true` when absent) in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Deploy Shipit with multi-org config where `OrgWithoutSecret` has `webhook_secret: nil` and `OrgWithSecret` (containing the real target stack `OrgWithSecret/target-repo`) has a real secret configured.
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": <id-of-an-authorized-team>, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "organization": {"login": "OrgWithoutSecret"},
  "member": {"login": "attacker-github-login"}
}
```
No valid `X-Hub-Signature` header is required because `Shipit.github(organization: "OrgWithoutSecret")` resolves to a `GitHubApp` with `webhook_secret = nil`, so `verify_webhook_signature` returns `true` unconditionally.
3. `MembershipHandler#process` runs and adds `attacker-github-login`'s corresponding `User` to the authorized `Team`, granting them access to the Shipit instance per `User#authorized?` / `force_github_authentication`.

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
