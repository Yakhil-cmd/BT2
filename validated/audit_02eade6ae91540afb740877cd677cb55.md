### Title
Forged cross-repository `Status` rows persist indefinitely because `Commit#refresh_statuses!` never reconciles/deletes stale statuses - (File: `app/models/shipit/commit.rb`)

### Summary
`StatusHandler#process` resolves the target commit purely by `sha` (`Commit.where(sha: params.sha)`) with no check that the webhook's originating repository matches the commit's own stack/repository, so a status event delivered for one repository can attach a `Status` row to a commit that actually belongs to a different stack whenever the sha is shared (e.g. via forks/common ancestry). Once that forged row exists, `Commit#refresh_statuses!` only *adds* rows for whatever GitHub currently reports for that commit's real repo - it never removes previously-persisted rows whose `context` GitHub no longer reports, so the forged row survives every legitimate refresh cycle.

### Finding Description
The intended binding is:
`commit.statuses.pluck(:context) == stack.github_api.statuses(github_repo_name, sha).map(&:context)` for `commit`'s own repository.

This binding is violated on both ends of the code path:

1. **Creation side** - `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
Unlike the PR handlers, it never uses `Handler#stacks`/`repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) to scope the update to the repository named in `payload['repository']['full_name']`. Any commit sha present in Shipit - regardless of which stack/repo it belongs to - is matched and updated.
`create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then calls `statuses.replicate_from_github!(stack_id, github_status)`, and `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) does a `find_or_create_by!` keyed on `(stack_id, state, description, target_url, context, created_at)` - it happily creates a new row scoped to the *victim's* `stack_id`/`commit_id` using attacker-supplied `state`/`context`/`description`.

2. **Reconciliation side** - `Commit#refresh_statuses!` (`app/models/shipit/commit.rb:156-163`):
```ruby
def refresh_statuses!
  github_statuses = stack.handle_github_redirections do
    stack.github_api.statuses(github_repo_name, sha, per_page: 100)
  end
  github_statuses.each do |status|
    create_status_from_github!(status)
  end
end
```
This only iterates GitHub's real statuses and creates/finds matching rows; there is no corresponding delete/prune of `commit.statuses` rows whose `context` is absent from the fresh GitHub response. So a forged status with a context GitHub never reports for that sha is never removed.

Because `Status::Group.compact` (used by `Commit#status`, `app/models/shipit/commit.rb:304-306`) folds in every status row attached to the commit, the forged row keeps influencing `Commit#status`, `#deployable?`, and `#blocked?` after every legitimate refresh.

### Impact Explanation
A forged `Status` row keeps affecting the **victim stack's** commit status (`Commit#status`, `#deployable?`) indefinitely, surviving normal `RefreshStatusesJob` cycles. Depending on the forged `state`/`context`, this can spuriously mark a required check as `success` (potentially contributing to an unauthorized deploy decision) or as `failure`/`error` (denial of a legitimate deploy) for a repository the attacker does not control - i.e., "a payload for one repository mutating another's stack/commit state," matching the Critical impact category. The condition is durable (it is never self-healed by the refresh job) and repeatable against any commit sha shared between an attacker-controlled repo and a victim stack.

### Likelihood Explanation
The reconciliation flaw in `refresh_statuses!`/`create_status_from_github!` is unconditional and requires no special configuration - any Status row ever attached to a commit remains forever unless GitHub happens to report a status with the exact same `context` again. The overall exploitability of this finding is conditioned on the ability to get `StatusHandler#process` to create the initial forged row on a victim's commit; that step depends on obtaining a validly-signed webhook whose `sha` collides with a commit tracked by a different stack (e.g. shared ancestor commits between a fork and the tracked repo) - a precondition supplied by this question rather than independently re-verified here.

### Recommendation
- Scope `StatusHandler#process` to the repository named in the webhook payload (use `Handler#stacks`/`repository_name`, or verify `commit.stack.github_repo_name == payload.dig('repository','full_name')`) before calling `create_status_from_github!`, exactly like the PR handlers do.
- Make `Commit#refresh_statuses!` authoritative: after fetching GitHub's status list, delete/expire any `Status` rows for that commit whose `context` is not present in the fresh response (or otherwise mark them stale) instead of only adding new rows.

### Proof of Concept
Minitest plan (`test/models/commits_test.rb`):
```ruby
test "refresh_statuses! does not clear a forged status with a context not reported by GitHub" do
  commit = shipit_commits(:cyclimse) # belongs to victim stack
  forged_context = "attacker-context"

  # Simulate a forged row identical to what StatusHandler#process would persist
  commit.statuses.create!(stack: commit.stack, state: "success", context: forged_context)

  legit_status = stub(
    state: "success", description: nil, target_url: nil,
    context: "ci/circleci", created_at: Time.now.iso8601
  )
  commit.stack.github_api.expects(:statuses).returns([legit_status])

  commit.refresh_statuses!

  assert commit.statuses.exists?(context: forged_context),
    "forged status should not survive legitimate refresh_statuses!"
  assert_includes commit.status.statuses.map(&:context), forged_context
end
```
This asserts the forged `Status` row (context `attacker-context`) still exists and still contributes to `Commit#status` after a legitimate `refresh_statuses!` call that only returns `ci/circleci` from GitHub. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
