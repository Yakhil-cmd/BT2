## Finding [1](#0-0) 

### Title
Stack-scoped ApiClient token can read CCMenu status of any stack, bypassing its `stack_id` authorization scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup used by `BaseController`, dropping the enforcement that restricts a stack-scoped `ApiClient` to the single stack it was created for. Any holder of a stack-scoped, `read:stack`-only CCMenu token can query the status of an arbitrary stack by simply changing the `stack_id` in the URL.

### Finding Description
`ApiClient` records can optionally be scoped to a single stack via `belongs_to :stack, optional: true` [2](#0-1) . The generic API controller enforces this binding by scoping the queryable stacks to the client's own `stack_id` before resolving the requested `stack_id` param:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [3](#0-2) 

`Shipit::CCMenuUrlController` builds exactly this kind of scoped, low-privilege client: it creates (or reuses) an `ApiClient` with only the `read:stack` permission, tied to `creator: current_user`, and embeds its `authentication_token` directly into a shareable URL intended for third-party CI/build-radiator tools:

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
``` [4](#0-3) 

However, `Shipit::Api::CCMenuController` does not use the scoped `stacks`/`stack` binding from `BaseController`. It defines its own `stack` method that resolves the stack directly from the request parameter, with no relation to the authenticated client's `stack_id`:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [5](#0-4) 

The only authorization check performed is `require_permission :read, :stack`, which merely checks that `'read:stack'` is present in `permissions` — it never validates that `current_api_client.stack_id` matches the requested `params[:stack_id]`:

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [6](#0-5) 

This breaks the equality that should hold: **stack a token authorizes == stack it touches**. Before the fix in the analogous scenario, the invariant "withdrawal count only increments for meaningful transfers" was broken by a zero-value bypass; here, the invariant "an ApiClient can only see stacks matching its own `stack_id`" is broken by `CCMenuController` re-deriving `stack` from raw params instead of the client-scoped `stacks` relation.

### Impact Explanation
An attacker who legitimately holds one CCMenu token (e.g., a token they were given/shared for their own stack, or one they created themselves via `CCMenuUrlController` for a stack they can view) can swap the `stack_id` in the CCMenu XML request to read the CI/deploy status — including `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, and `webUrl` — of *any* stack in the Shipit instance, including stacks/repositories they have no read access to. This is an unauthorized cross-stack read of deploy/task state via a credential whose entire purpose is to be scoped to one stack, matching the "unauthorized read of stack state / deploy output" impact class.

### Likelihood Explanation
CCMenu tokens are specifically designed to be embedded in plain URLs and shared with external tooling (build radiators, CI dashboards), so their exposure surface is intentionally wider than a typical `Authorization` header credential. Exploitation requires only changing a URL parameter (`stack_id`) — no additional privilege, secret, or session is needed beyond possessing one such token.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the same scoped `stacks` relation used by `BaseController`, e.g. `stacks.from_param!(params[:stack_id])`, so that stack-scoped `ApiClient` tokens can only ever resolve their own bound stack, consistent with the enforcement everywhere else in the API.

### Proof of Concept
1. User `alice` visits stack `org/repo-a/production` and calls `GET /org/repo-a/production/ccmenu_url`, receiving a URL like `https://shipit/api/stacks/1/ccmenu.xml?token=<T>`, backed by an `ApiClient` with `permissions: ['read:stack']` and `stack_id: 1`.
2. Using the same token `T`, request `GET /api/stacks/2/ccmenu.xml?token=<T>` for an unrelated stack (`id=2`) that `alice`/the client was never scoped to.
3. `CCMenuController#authenticate_api_client` accepts `T` (valid signature via `ApiClient.authenticate`), `require_permission :read, :stack` passes because permission `read:stack` is present, and `stack` resolves stack `2` directly via `Stack.from_param!`, ignoring `current_api_client.stack_id == 1`.
4. The response renders stack `2`'s status data (`show` action) despite the client only being authorized for stack `1`.

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

          0
        end

          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      end
