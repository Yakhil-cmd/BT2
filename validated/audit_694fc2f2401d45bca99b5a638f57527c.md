### Title
Webhook status events let a signature verified for one GitHub organization forge commit statuses on commits belonging to any other tracked repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which HMAC secret to validate the inbound webhook against using an attacker-supplied field of the JSON body, not the repository that will actually be mutated: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the parsed JSON payload (`repository.owner.login`, falling back to `organization.login`), and is used only to pick a `GitHubApp` config via `Shipit.github(organization: repository_owner)`, which resolves to a per-organization `webhook_secret` when the multi-tenant `github_organizations` config is used: [3](#0-2) 

Once the HMAC over `raw_post` validates against *that* organization's secret, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the handler with the full, attacker-controlled JSON body: [4](#0-3) 

Handlers are expected to scope their side effects to the repository named in the payload via `Handler#repository_name` / `#stacks` (`payload.dig('repository', 'full_name')`), as `PushHandler` correctly does: [5](#0-4) [6](#0-5) 

`StatusHandler`, however, never uses `repository_name`/`stacks` at all — it writes a status onto whatever commit matches the attacker-supplied `sha`, globally, across every tracked repository on the Shipit instance: [7](#0-6) 

This is the exact analog of the reported bug class: the field that is verified (`repository_owner`, used to pick the webhook secret / tenant) is not the field the effectful write is actually bound to (`params.sha`, which is unscoped and can belong to any repository/stack in the instance). The equality that should hold — "organization whose secret authenticated the request == repository/stack whose commit is mutated" — is broken: the code checks the former and silently writes to the latter without any cross-check.

### Impact Explanation
An attacker who controls (or has legitimately been onboarded with) any single organization's webhook secret in a multi-tenant Shipit deployment (`Shipit.github_organizations`) can send a forged `status` webhook that passes signature verification for their own organization, but sets `sha` to a commit belonging to a completely different, victim-owned stack/repository tracked by the same Shipit instance. `Commit#create_status_from_github!` will persist an attacker-chosen `state`/`context`/`description` for that victim commit. Because commit statuses feed into deployability/mergeability checks (`deployable_status`, required-check gating used by CI/CD and merge automation in Shipit), this can be used to make a malicious or unreviewed commit in a repository the attacker has no access to appear "green," enabling an unauthorized deploy or auto-merge decision by a legitimate operator/automation acting on the forged status — a cross-tenant integrity break with no repository write access, API token, or session required beyond knowledge of one tenant's webhook secret.

### Likelihood Explanation
Requires only the ability to send an HTTP POST with a valid HMAC-SHA1 signature for *any one* organization configured in the multi-tenant `github` secrets block; the attacker does not need any relationship to the victim repository, no `ApiClient` token, no session, and no repository write access on GitHub. This is directly reachable via the public `WebhooksController#create` endpoint.

### Recommendation
In `StatusHandler#process` (and any other handler that queries by attacker-controlled identifiers such as `sha`), scope the lookup to the repository resolved from the verified webhook context, e.g. restrict to `stacks`/`Repository.from_github_repo_name(repository_name)` before matching commits, mirroring what `PushHandler` already does. More generally, `WebhooksController#verify_signature` should ensure the organization used to select the webhook secret is consistent with the repository/organization that the handler is permitted to mutate, rather than trusting an unauthenticated payload field for tenant selection.

### Proof of Concept
1. Deploy Shipit configured for multiple GitHub organizations (`Shipit.github_organizations`), e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret`.
2. Attacker knows (or legitimately owns) `attacker-org`'s webhook secret.
3. Attacker crafts a JSON body: `{"repository": {"owner": {"login": "attacker-org"}}, "sha": "<victim commit sha>", "state": "success", "context": "ci/required-check"}` and computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)`.
4. POST to `/github/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), writing the forged "success" status onto the victim's commit with no check that it belongs to `attacker-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
