## Analysis

`User#authorized?` grants Shipit application access based on team membership in `Shipit.github_teams`: [1](#0-0) 

Team membership itself is populated by the `membership` webhook, handled entirely from the untrusted JSON body with no cross-field consistency check against the organization used for signature verification: [2](#0-1) 

### Title
Authorization escalation via unauthenticated webhook forgery when an organization's `webhook_secret` is unset - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/secret to check the `X-Hub-Signature` against using a field taken directly from the untrusted request body (`repository.owner.login` or `organization.login`), not from anything cryptographically bound to the request. `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatically verified. Because Shipit supports multiple GitHub organizations each with independently optional `webhook_secret` config, an attacker who can reach the `/webhooks` endpoint can pick an org value whose secret happens to be unset, trivially pass "signature verification" for that org, then have the payload processed by `MembershipHandler`, which uses the same attacker-controlled `organization.login`/`team` fields to create/update a `Team` and add an arbitrary GitHub login as a member — with no real correlation to any genuine GitHub-originated event.

### Finding Description
The verification org and the org actually written to the database come from the same untrusted JSON body, and the signature check can be trivially satisfied: [3](#0-2) 

`verify_webhook_signature` short-circuits to `true` when no secret is configured for the app: [4](#0-3) 

Shipit's documentation explicitly treats `webhook_secret` as optional, and explicitly supports per-organization configuration where multiple orgs can each have their secret set or left blank: [5](#0-4) [6](#0-5) 

If any one configured organization has a blank `webhook_secret` (a documented, supported configuration), then a POST to `/webhooks` with `organization.login` set to that org bypasses signature verification entirely — the `equality` the code assumes ("the organization whose signature was verified" == "the organization the payload legitimately originates from") never actually holds; it degrades to "the organization named in the unauthenticated payload happens to have no secret."

`MembershipHandler` then trusts the very same unauthenticated body to create a `Team` and add a `member`: [7](#0-6) 

Because `Team.organization` and `Membership` records are plain application data with no additional GitHub-side confirmation, an attacker can create a `Team` record with `organization`/`slug` matching one of `Shipit.github_teams` (the set of teams configured via `github.oauth.teams` that grant application access) and add a `member` whose `login` matches their own GitHub login. `User#authorized?` will then evaluate to `true` for that attacker the next time they log in through the real GitHub OAuth flow, because it only checks Shipit's local `teams` association, not GitHub's actual team membership at request time: [1](#0-0) 

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization — explicitly listed as a High-severity impact. An attacker who is not a member of any required GitHub team can forge a `membership` webhook (exploiting the optional/per-org secret binding gap) to insert themselves into a `Team` that Shipit treats as authorizing, then complete a normal OAuth login to gain full access to the Shipit application (viewing stacks, triggering deploys/rollbacks depending on further permission checks tied to team-gated features).

### Likelihood Explanation
This requires: (1) the Shipit deployment to have at least one configured GitHub organization with no `webhook_secret` set — a state the project's own setup docs describe as optional/acceptable — and (2) the attacker to know or guess that organization's login name (often public knowledge, e.g., the org name itself). No GitHub credentials, no `ApiClient` token, and no privileged Shipit account are required, satisfying the unprivileged-attacker constraint. The likelihood is contingent on operator configuration (secret left blank for some org in a multi-org setup), which is a realistic and documented scenario rather than a purely theoretical one.

### Recommendation
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank in production; require every configured GitHub organization to have a non-blank webhook secret, or fail closed when in doubt.
- Do not derive the organization used for signature verification purely from unauthenticated payload fields without cross-checking it against the resulting `Team`/`Repository` records being mutated.
- Consider binding the `membership` handler's trust boundary to the specific `GithubHook` record delivering the event (already tracked in `test/fixtures/shipit/github_hooks.yml` as `Shipit::GithubHook::Organization`) rather than trusting `organization.login` from the body alone for both verification and mutation.

### Proof of Concept
1. Deploy Shipit configured for multiple GitHub organizations (per `docs/setup.md` "Using Multiple Github Applications"), where `OrgWithoutSecret` has `webhook_secret` left blank and `Shipit.github_teams` includes `OrgWithoutSecret/some-team` (configured via `github.oauth.teams`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "some-team", "slug": "some-team", "url": "https://example.com" },
  "organization": { "login": "OrgWithoutSecret" },
  "member": { "login": "attacker-github-login" }
}
```
No valid `X-Hub-Signature` header is needed because `verify_webhook_signature` returns `true` for a blank secret ( [4](#0-3) ).
3. `MembershipHandler` creates/updates the `Team` and adds `attacker-github-login` as a member ( [7](#0-6) ).
4. Attacker logs into Shipit via the normal GitHub OAuth callback; `User#authorized?` now returns `true` because `teams` includes the forged team matching `Shipit.github_teams` ( [1](#0-0) ), granting full application access despite never actually being a member of the real GitHub team.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
