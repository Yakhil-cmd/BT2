Confirmed. This is a real, exploitable, in-scope analog of the duplicate-token binding-break bug class.

### Title
CCMenu token is not scoped to the stack it was minted for, allowing cross-stack build-status disclosure - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
### Finding Description
The `NounsDAOLogicV1Fork.quit` bug is a mismatch between the value a check is performed against and the value actually acted upon (duplicated `erc20TokensToInclude` entries bypass the intended one-token-per-request invariant, letting a "requested tokens" set diverge from an "authorized tokens" set). The structural analog in this engine is a mismatch between the stack an `ApiClient` token is *authorized for* and the stack the request actually *touches*.

`Shipit::CCMenuUrlController#client` mints (or reuses) an `ApiClient` with the `read:stack` permission but never sets `stack:` on it: [1](#0-0) 

Because `stack_id` is left blank, `ApiClient#stack_id?` is false, which in the generic `Api::BaseController#stacks` helper is meant to fall back to unscoped access: [2](#0-1) 

`Api::CCMenuController` (which serves the actual `ccmenu_url`) overrides `#stack` to bypass the `stacks` scoping relation entirely and instead resolve the requested stack directly from `Stack.from_param!(params[:stack_id])`, an unscoped lookup across all stacks: [3](#0-2) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`, it never compares `current_api_client.stack_id` to the requested `params[:stack_id]`: [4](#0-3) 

The binding that should hold is: `stack the token authorizes == stack the request touches`. Before the token is even scoped, the design already breaks this equality because the client is created without a `stack` at all, and the controller that consumes the token further bypasses the one scoping mechanism (`stacks.from_param!`) that exists elsewhere in the API (`Api::BaseController#stack`, used by `Api::StacksController`, `Api::TasksController`, etc.). Any holder of a single stack's CCMenu URL can substitute an arbitrary `stack_id` query parameter and read another stack's build/deploy status.

### Impact Explanation
CCMenu URLs are designed to be embedded in third-party CI dashboards/widgets and are commonly treated as "public enough" to paste into semi-shared tooling, since they only expose build status. Because the underlying token is not stack-scoped and the controller ignores any scoping that might exist, possession of one stack's CCMenu token grants unauthenticated read access to `lastBuildStatus`, `lastBuildLabel`, `activity`, and `webUrl` for every stack in the Shipit instance, not just the one it was generated for: [5](#0-4) . This is an unauthorized cross-stack read of stack state, matching the "unauthenticated read of stack state" High-impact category — a lesser-privileged, single-purpose token silently authorizes reads of state well beyond the one stack it was minted for.

### Likelihood Explanation
Any user who can reach `CCMenuUrlController#fetch` for a stack they can see (i.e., any authenticated Shipit user who requests a CCMenu URL for a project) automatically obtains a token usable against any other stack merely by swapping `stack_id` in the query string. No special privilege, secret, or additional access is required beyond normal use of the CCMenu integration feature.

### Recommendation
- When minting the CCMenu `ApiClient` in `CCMenuUrlController#client`, set `stack:` to the requested stack so the token is genuinely scoped (`ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(...)`).
- In `Api::CCMenuController#stack`, use the scoped `stacks.from_param!(params[:stack_id])` (as `Api::BaseController#stack` does) instead of the unscoped `Stack.from_param!(params[:stack_id])`, so a stack-scoped token cannot be replayed against other stacks.

### Proof of Concept
1. As user A, call `GET /stacks/:stack_a/ccmenu_url` to obtain a CCMenu URL/token for `stack_a` via `CCMenuUrlController#fetch`.
2. Take the returned `token` query parameter and issue `GET /api/stacks/:stack_b/ccmenu.xml?token=<token>` for an unrelated `stack_b`.
3. `Api::BaseController#authenticate_api_client` accepts the token (it is a valid, signed `ApiClient` id) and `require_permission :read, :stack` passes because the client has `read:stack` in its `permissions` array.
4. `Api::CCMenuController#stack` resolves `stack_b` via unscoped `Stack.from_param!`, so the response discloses `stack_b`'s build/deploy status even though the token was minted only for `stack_a`.
