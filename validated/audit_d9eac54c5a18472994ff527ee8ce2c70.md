## Finding: Cross-organization webhook forgery via unbound `repository.owner.login` vs `repository.full_name` / commit `sha`

### Title
GitHub webhook signature is verified against `repository.owner.login`, but handlers act on `repository.full_name` or a bare `sha` that is never checked against the authenticated organization — allowing cross-repository/stack forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is the closest analog to M-17's root cause: a security check (auction/liquidation state) is performed on one identity, while the effect (new lien) is applied without re-validating that same identity across all relevant positions. Here, `WebhooksController` verifies an HMAC signature keyed to the *organization* found in the JSON body, then hands the *entire attacker-controlled body* to handlers that key their writes off a *different, unverified field* in that same body.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the signature against purely from a field inside the payload the attacker supplies: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), and `Shipit.github(organization: repository_owner)` is used to look up the webhook secret to validate against. Since the attacker constructs the whole raw JSON body themselves (this is an HTTP request they send, not something GitHub is relaying unmodified), they fully control every field, including `repository.owner.login` used for verification **and** every other field used later.

Once signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw JSON to handlers: [3](#0-2) 

The base `Handler` class resolves *which repository/stack to mutate* from `repository.full_name`, a completely independent field from `repository.owner.login`: [4](#0-3) 

`PushHandler` uses this to trigger a sync for any stack of that resolved repository: [5](#0-4) 

`StatusHandler` is even weaker: it does not scope by repository at all, only by `sha`, across the entire Shipit instance: [6](#0-5) 

The binding that should hold but doesn't is:
`organization whose secret authenticated the request == organization that owns the repository/commit being written to`.

An attacker who legitimately administers *their own* GitHub organization/repository tracked by the Shipit instance (and therefore knows/possesses that organization's `webhook_secret`) can craft a payload where `repository.owner.login` = their own org (so `verify_signature` passes using their own secret) while `repository.full_name` (for push/pull_request handlers) or `sha` (for `StatusHandler`) references a completely different, victim stack/commit they have no access to.

### Impact Explanation
Via `StatusHandler`, an attacker can inject a fabricated commit status (`state`, `context`, `target_url`) for **any commit sha tracked anywhere in the Shipit instance**, without any repository-ownership check at all — the handler only matches on `sha`. Since commit statuses drive CI-gating for deploys/merges in Shipit (`Commit#deployable?`, merge-queue/continuous-delivery checks reference status state), forging a "success" status on a victim's commit can cause Shipit to treat an unreviewed/failing commit as deployable, leading to an unauthorized deploy or an unauthorized merge decision — matching the Critical/High impact bar (unauthorized deploy/merge). `PushHandler`/pull-request handlers extend the same class of forgery to arbitrary tracked repositories via the unchecked `repository.full_name` field, enabling spoofed sync/merge-queue events on stacks the attacker does not own.

### Likelihood Explanation
Requires only that the attacker legitimately controls (or has onboarded to Shipit) *some* organization/repository tracked by the instance and knows/derives its webhook secret — they need no access whatsoever to the victim repository or stack. This is directly analogous to the Sherlock report's scenario where the check (`AuctionHouse`/signature) is scoped to one entity while the actual write (`createLien`/handler side effect) is applied to an unrelated entity that was never re-validated.

### Recommendation
In `WebhooksController#verify_signature`, and in `Handler#repository_name`/`StatusHandler#process`, cross-validate that the resolved `Repository`/`Commit`'s actual owning organization matches the organization whose secret validated the signature (`repository_owner`) before dispatching to any handler. `StatusHandler` in particular must scope `Commit.where(sha:)` by the repository resolved from the verified organization, not by `sha` alone.

### Proof of Concept
1. Attacker is the admin of `AttackerOrg`, which they have legitimately connected to the shared Shipit instance (knows `AttackerOrg`'s `webhook_secret`).
2. Attacker crafts a raw JSON body for a `status` event:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/whatever" },
  "sha": "<victim commit sha, often public on GitHub>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(AttackerOrg_webhook_secret, raw_body)` and POSTs to `/github/webhooks`.
4. `verify_signature` resolves `repository_owner = "AttackerOrg"`, fetches `AttackerOrg`'s secret, and the signature checks out.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit in an entirely different stack — and calls `create_status_from_github!`, injecting a forged "success" CI status the attacker was never authorized to set.
