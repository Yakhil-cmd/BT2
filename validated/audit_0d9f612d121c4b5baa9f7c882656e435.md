### Title
Cross-organization webhook forgery via unbound `repository_owner` used for signature selection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify a webhook payload against based on an unverified field extracted from the request body itself (`repository.owner.login` / `organization.login`), but none of the webhook handlers re-check that the *repository actually acted upon* (`repository.full_name`, used by `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`) belongs to that same authenticated organization. In a multi-tenant Shipit deployment configured with "Multiple Github Applications" (documented in `docs/setup.md`, lines 182-209), this breaks the binding: `organization whose secret validated the signature == organization whose repository/stack is mutated`.

### Finding Description
`Shipit.github(organization:)` supports per-organization configuration, each with its own independent `webhook_secret` [1](#0-0) , intended for hosting multiple unrelated GitHub organizations/customers on one shared Shipit instance.

The webhook entrypoint picks the app/secret to verify with using an attacker-supplied, not-yet-verified field: [2](#0-1) 

Specifically, `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) is read from the raw JSON body before the signature check, then used to fetch `Shipit.github(organization: repository_owner)` and verify `X-Hub-Signature` against that org's `webhook_secret`. If verification succeeds, the code only proves the request was signed with *that organization's* secret — it does not prove anything about which repository the payload's handlers will actually act on.

Every webhook handler, however, determines the target stack from a *different, independent* field of the same payload — `repository.full_name` — with no cross-check against `repository_owner`: [3](#0-2) 

So `repository_owner` (used for authentication) and `repository.full_name` (used to select the stack that gets mutated) are two separate unauthenticated JSON fields that are never checked for consistency. `StatusHandler` makes the impact worse because it doesn't even scope by stack/repository at all — it matches any commit row in the entire database by raw SHA: [4](#0-3) 

`create_status_from_github!` feeds directly into merge-queue scheduling logic: [5](#0-4) 

`PushHandler` and `CheckSuiteHandler` similarly resolve their target `stacks` purely from `repository.full_name` with no relation to the authenticated organization: [6](#0-5) [7](#0-6) 

### Impact Explanation
On a Shipit instance configured for multiple GitHub organizations (a documented, supported configuration), the administrator/owner of *any one* onboarded GitHub organization (`OrgA`) legitimately possesses `OrgA`'s webhook secret (it is generated/settable by the org's own GitHub App owner, not a Shipit-issued secret). That admin is an "unprivileged attacker" with respect to every *other* tenant (`OrgB`) hosted on the same Shipit instance, yet they can:

1. Craft a JSON body with `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) so `verify_signature` picks `OrgA`'s `webhook_secret`, sign it with that (legitimately known) secret, and satisfy `verify_webhook_signature`.
2. Set `repository.full_name = "OrgB/some-repo"` inside the same signed body.
3. POST directly to `/webhooks` (no need to go through GitHub at all — Shipit itself doesn't validate that the request actually originated from GitHub for that repo, only that the HMAC matches the chosen org's secret).

Because handlers key exclusively off `repository.full_name`, this forged, `OrgA`-signed payload is processed as if it legitimately came from `OrgB`. Concretely, via `StatusHandler`, the attacker can inject an arbitrary `state: "success"` commit status for any commit SHA that exists in `OrgB`'s stacks (or any stack on the instance, since the SHA lookup is unscoped), which flips `deployable_status` and triggers `stack.schedule_merges` — enabling an **unauthorized merge** of an `OrgB` pull request that never actually passed CI. This matches the Critical impact bar ("unauthorized deploy, rollback or merge") without the attacker ever holding any Shipit `ApiClient` token, GitHub App key, or webhook secret belonging to `OrgB`.

### Likelihood Explanation
Requires: (a) the operator running Shipit with the "Multiple Github Applications" multi-tenant configuration — an officially documented and supported setup — and (b) the attacker being the legitimate owner/admin of at least one of the onboarded organizations, a role granted independently of Shipit itself (each org sets its own GitHub App webhook secret). No Shipit credentials, GitHub App private key, or knowledge of any other tenant's secret are needed. The forged request can be sent directly to the public `/webhooks` endpoint, bypassing GitHub entirely.

### Recommendation
After successfully verifying the signature for `repository_owner`, additionally verify that the repository/stack targeted by the payload (`repository.full_name`, or the stacks resolved via `Repository.from_github_repo_name`) actually belongs to that same authenticated organization before dispatching to handlers. Alternatively, scope `Repository`/`Stack` lookups by the organization that authenticated the request, and scope `StatusHandler`'s `Commit.where(sha:)` lookup to commits within stacks belonging to the verified organization rather than a global, unscoped SHA match.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md` "Using Multiple Github Applications": `OrgA` (secret known to attacker, who is `OrgA`'s GitHub App owner) and `OrgB` (a separate tenant with a stack tracking `OrgB/some-repo`, containing a commit with sha `deadbeef...` on an open, unmerged pull request awaiting CI).
2. Attacker builds JSON body:
   ```json
   {
     "sha": "deadbeef...",
     "state": "success",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/some-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: "OrgA")` and validates the signature successfully [8](#0-7) .
5. `StatusHandler#process` matches the `OrgB` commit by raw sha and calls `create_status_from_github!`, marking it as `success`, which schedules merges for `OrgB`'s stack — an unauthorized/attacker-forced merge signal on a repository the attacker has no legitimate access to [9](#0-8) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
