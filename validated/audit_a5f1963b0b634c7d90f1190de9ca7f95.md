### Title
Unbounded recursive self-redirect via attacker-controlled skill upstream metadata - (File: pkg/cmd/skills/install/install.go)

### Summary
`gh skill install` performs a recursive call to `installRun(opts)` whenever it detects that the selected skill was "re-published" from an upstream source, based on `github-repo` metadata read from the target repository's `SKILL.md` frontmatter. This metadata is attacker-controlled content in the repository being installed from, and the recursive call has no visible depth limit or visited-set/cycle protection in the code I inspected.

### Finding Description
In `installRun`, after skills are discovered and selected, the code checks for upstream provenance: [1](#0-0) 

If `checkUpstreamProvenance` returns a non-nil `upstreamRepo` (derived from the currently-installed repo's `SKILL.md` frontmatter `github-repo` field), the function mutates `opts.repo`/`opts.SkillSource`/`opts.version`/`opts.Pin` and calls `installRun(opts)` again — recursively — with no depth counter, no "already visited" tracking, and no check that `upstreamRepo` differs from a previously seen repo in the chain. Each recursive call re-executes the full install pipeline (`resolveVersion`, `discoverSkills`/`DiscoverSkillByPath`, `checkUpstreamProvenance` again, several HTTP round-trips), so a chain or cycle of repos each declaring an "upstream" pointer to the next would recurse without bound.

This mirrors the reported bug class: an attacker-controlled linked/chained data structure (here, upstream-redirect metadata embedded in a repo's `SKILL.md`, analogous to the Hats Protocol's `linkedTreeAdmins` chain) is traversed recursively during a normal client operation (`isAdminOfHat()` ↔ `installRun()`) without a depth cap, so the attacker fully controls how deep the recursion goes.

By contrast, a nearby, structurally similar recursive traversal in this same codebase — `walkTree` in the skills discovery package — was explicitly hardened with a `maxTreeDepth` bound to defend against exactly this class of issue: [2](#0-1) 

No equivalent bound is visible on the `installRun` upstream-redirect recursion.

### Impact Explanation
If exploitable as described, a user running `gh skill install <attacker-repo>` against a malicious or compromised repository (or chain of repositories) that declares circular or very deep upstream-redirect metadata could cause the `gh` process to recurse indefinitely (or for a very large number of iterations), each iteration performing additional network calls to GitHub. This could hang the CLI, consume excessive time/resources, or in the worst case exhaust the Go call stack, causing a crash (denial of service against the local `gh` invocation). This fits the "unprivileged remote-attacker" class allowed by the rules (an attacker publishes repo content that a victim voluntarily installs via `gh skill install`).

### Likelihood Explanation
Likelihood is uncertain because I could not read `checkUpstreamProvenance`'s implementation before running out of tool calls — it is possible that function already contains guard logic (e.g., comparing `upstreamRepo` against the current repo, or refusing self-referential redirects) that would prevent at least the trivial two-node cycle. I was not able to confirm or rule this out. The one-hop case (A→A, i.e., a repo claiming itself as upstream) seems like an obvious case a defender would guard against, but a longer chain (A→B→C→…→A) is less likely to be defended against without an explicit visited-set, and I found no such visited-set threaded through `InstallOptions` or passed into the recursive call.

### Recommendation
Add explicit protection against unbounded/cyclic upstream redirects in `installRun`, e.g.:
- Track visited repositories (owner/repo) across recursive calls in `InstallOptions` and abort with an error if a repeat is encountered.
- Alternatively, cap the number of upstream redirects to a small constant (e.g., 1–2 hops) similar to the `maxTreeDepth` pattern already used in `internal/skills/discovery/discovery.go`.

### Proof of Concept
Not fully constructible from the index alone: reproducing this requires publishing two (or more) GitHub repositories whose `SKILL.md` frontmatter `github-repo` fields point to each other (or form a longer chain), then running `gh skill install <repoA> <skill>@<version>` and observing whether the process hangs/recurses without bound. I could not verify this end-to-end because `checkUpstreamProvenance`'s source was not retrieved before the tool budget was exhausted — **this is a confirmed gap in my verification, not a confirmed exploit**. A Devin session with full repository access should read `checkUpstreamProvenance` (in `pkg/cmd/skills/install/install.go`) to confirm whether cycle/depth protection already exists before treating this as a confirmed, exploitable vulnerability.
