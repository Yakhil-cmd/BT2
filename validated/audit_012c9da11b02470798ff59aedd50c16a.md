Confirmed: `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [1](#0-0)  which relies entirely on `Membership` rows created by the `membership` webhook handler [2](#0-1) , and `verify_webhook_signature` trivially returns `true` whenever no `webhook_secret` is configured for the organization [3](#0-2) .

### Title
Unauthenticated webhook `membership` events can grant `Shipit.github_teams` authorization when `webhook_secret` is unset - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` for the org named in the (still-unverified) JSON body and calls `verify_webhook_signature` [4](#0-3) . `GitHubApp#verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank [3](#0-2) , and the setup docs explicitly list the webhook secret as "(optional)" [5](#0-4) . When it is left unset, `POST /webhooks` with `X-Github-Event: membership` is processed with zero credential checks by `MembershipHandler#process`, which creates arbitrary `Team`/`Membership` records for any GitHub login the attacker names [2](#0-1) .

### Finding Description
The equality that should hold is: *the GitHub identity that authenticated the webhook == the identity that is granted `Shipit.github_teams` membership*. When `webhook_secret` is absent, there is no verification at all on that binding — `verify_signature` still executes and logs, but `verified` is always `true` [6](#0-5) . `User#authorized?` (used by `force_github_authentication`) trusts the `teams` association populated purely from these webhook-created `Membership` rows [1](#0-0) [7](#0-6) . An attacker who knows (or brute-forces) any user's GitHub login can therefore forge a `membership` `added` webhook naming that login and the numeric `github_id`/`slug` of one of `Shipit.github_teams`, without ever touching `webhook_secret`, `api_clients_secret`, or a GitHub token.

### Impact Explanation
This directly escalates into `Shipit.github_teams` authorization (a listed High-impact outcome), letting an attacker who controls a Shipit account/login gain access to a stack normally gated by team membership — potentially chaining into deploy/rollback/merge actions once `authorized?` returns `true`.

### Likelihood Explanation
The only precondition is an installation where `webhook_secret` is left blank — a state the project's own setup guide presents as a supported, optional configuration rather than a documented hard requirement, so this is plausible in real deployments rather than a "misconfiguration outside the engine's control."

### Recommendation
Make `webhook_secret` mandatory (fail closed instead of returning `true`) in `GitHubApp#verify_webhook_signature`, or reject webhook processing entirely when no secret is configured instead of treating it as an implicit "trust everything" mode.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": 48, "name": "Ouiche Cooks", "slug": "developers", "url": "https://example.com"},
  "organization": {"login": "shopify"},
  "member": {"login": "victim-or-attacker-github-login"}
}
```
With no `webhook_secret` configured for `shopify` in `config/secrets.yml`, this unauthenticated request creates a `Membership` linking the named GitHub login to the team, satisfying `Shipit.github_teams` and bypassing `User#authorized?`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
