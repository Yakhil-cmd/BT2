### Title

Opaque swap route can inject caller-authorized token transfers from arbitrary route contracts - ([File: contracts/controller/src/strategies/swap.rs](https://github.com/Jaredbentat/rs-lending-xlm--024/blob/main/contracts/controller/src/strategies/swap.rs))

### Summary

`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept opaque `StrategySwap` bytes and execute them through the configured router. The route can invoke attacker-selected contracts; code executing below the caller-authorized controller invocation can request additional `token.transfer` calls from the caller. If simulation records that child transfer and the user signs the resulting authorization tree, an attacker-controlled route contract can steal unrelated wallet tokens while still returning a valid swap output.

### Finding Description

The controller defines `StrategySwap` as raw `Bytes`, so the lending contract does not decode or constrain the venues named by the route. [1](#0-0)  `swap_collateral` is public, requires the caller's authorization and account ownership or delegation, and forwards the supplied `swap` bytes into the withdrawal-and-swap strategy. [2](#0-1) [3](#0-2) 

`swap_tokens` authorizes only the controller's exact input transfer, but then invokes `router.execute_strategy(controller, amount_in, swap)` with the opaque route. [4](#0-3)  Its balance checks verify only the controller's input spend and positive output receipt; they do not prevent route-selected code from requesting a separate transfer from the original caller under that caller's authorization tree. [5](#0-4) 

The repository's threat model explicitly documents that route-named pools and tokens are not allowlisted and that a transfer from the caller by third-party route code is recorded as a child of the caller's authorization entry. [6](#0-5)  The test fixture demonstrates a route-designated contract calling `token.transfer(victim, attacker, amount)`, simulation recording it beneath `swap_collateral`, and enforced authorization succeeding when the poisoned tree is signed. [7](#0-6) [8](#0-7) [9](#0-8) 

### Impact Explanation

An attacker can steal arbitrary transferable tokens held by the caller, including assets unrelated to the lending position and not listed by the protocol. The controller can receive economically acceptable swap output and pass all collateral and risk checks while the unauthorized-looking wallet transfer executes under the caller's signed authorization tree. The accepted impact category is theft of user funds.

### Likelihood Explanation

Exploitation requires inducing a position owner or delegate to submit a malicious route and sign the authorization tree containing the extra transfer. This is plausible when routes originate from an external quote service or UI and the wallet does not clearly display nested contract authorizations; the repository test shows that simulation represents the theft only as a child invocation. The attack does not require protocol privileges, leaked keys, or control of the aggregator contract, but it does require the victim's signature, so its likelihood is lower than a purely permissionless theft.

### Recommendation

Do not allow opaque routes to invoke arbitrary venue contracts. Enforce a governance-controlled venue allowlist in the router, decode and validate every route leg before execution, and reject payloads containing unexpected calls or assets. Clients should independently decode `routeXdr`, simulate the complete controller transaction, and reject any authorization tree containing children beyond the expected exact input transfer. The controller documentation already identifies this client-side authorization-tree check as required. [10](#0-9) 

### Proof of Concept

1. Alice supplies 10,000 USDC and holds 77,770 units of an unrelated token in her wallet. [11](#0-10) [12](#0-11) 
2. The attacker constructs a route naming an attacker-deployed `hop_pool` while promising fair ETH output. [13](#0-12) 
3. Alice calls `swap_collateral(caller=alice, account_id=alice_account, current=USDC, amount=50_000_000_000, new=ETH, swap=malicious_route)`. [14](#0-13) 
4. The controller forwards the opaque bytes to the router after authorizing only the controller-to-router input transfer. [4](#0-3) 
5. During route execution, the named pool calls `token.transfer(alice, attacker, WALLET_BALANCE)`. [8](#0-7) 
6. Simulation records that transfer as a child of Alice's `swap_collateral` authorization, and the honest simulation result shows Alice's unrelated token balance reduced to zero while the attacker receives it. [15](#0-14) 
7. In enforcing mode, the same route succeeds when Alice signs the poisoned tree and moves `WALLET_BALANCE` to the attacker. [9](#0-8)
