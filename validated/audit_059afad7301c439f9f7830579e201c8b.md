### Title
Webhook signature verification selects the signing organization from an unauthenticated payload field, decoupling the org that authorizes the request from the repository that is actually acted upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp`/webhook secret to validate a webhook against using `repository_owner`, a value read straight out of the still-unauthenticated JSON body [1](#0-0) . The field actually used to decide *which repository/Stack gets acted upon* by the event handlers is a different field, `repository.full_name`, read independently by `Handler#repository_name` [2](#0-1) . In a multi-organization deployment (`config/secrets.yml` with one sub-hash per GitHub org, as documented) these two fields are never bound to each other by the signature, so an attacker can pick an org for `owner.login` that has no `webhook_secret` configured (or whose secret they otherwise possess) purely to satisfy verification, while pointing `full_name` at a victim organization's real, secret-protected repository.

### Finding Description
The invariant that should hold is: *the organization whose secret verified the request == the organization/repository whose Stack is mutated by the handler*. This binding is broken:

- Verification side: `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` selects the `GitHubApp` config via `Shipit.github(organization: repository_owner)` [3](#0-2) , which in multi-org mode resolves to `github_app_config(organization)` [4](#0-3) .
- `GitHubApp#verify_webhook_signature` explicitly short-circuits to `true` when that organization has no configured secret: `return true unless webhook_secret` [5](#0-4) .
- Handler/business-logic side: every handler (e.g. `PushHandler`) resolves the target `Stack` via `Handler#stacks`, which uses `payload.dig('repository', 'full_name')`, a completely separate JSON key never covered by the signature check that gated execution [6](#0-5) , [7](#0-6) .

Since the whole request body is otherwise unauthenticated except for this signature check, an attacker who controls the raw JSON body can set `repository.owner.login` to any organization name that Shipit has configured with a blank/absent `webhook_secret` (documented as "optional" in `docs/setup.md`), causing `verify_signature` to pass unconditionally, while setting `repository.full_name` to `victim-org/real-repo` so the actual handler logic (`PushHandler#process` → `stack.sync_github`, or `StatusHandler#process` → `commit.create_status_from_github!`) operates on the victim's real Stack/commits.

### Impact Explanation
This lets an unauthenticated attacker forge webhook deliveries (`push`, `status`, `check_suite`, etc.) targeting any Stack registered under a *different, legitimately-secured* organization, as long as any other organization configured in Shipit lacks a `webhook_secret`. Concretely:
- Forged `push` events can drive `Stack#sync_github(expected_head_sha:)` with an attacker-chosen `after` sha on the victim Stack.
- Forged `status` events can create arbitrary commit `Status` rows via `Commit#create_status_from_github!` for shas belonging to the victim's commits, which is the exact signal continuous-delivery/merge gating logic consumes.

Because Shipit's own model is that GitHub is the sole trust anchor validated by the webhook signature, and this defeats that anchor for cross-org traffic, this crosses into unauthorized manipulation of another repository's deploy pipeline (matching the "unauthorized deploy"/cross-repository-writes class). The severity in a real deployment depends on whether the operator actually runs a multi-org config with at least one secret-less org, mirroring how the original finding was downgraded because an "alternative path" (a config choice) had to exist for exploitation.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (`secrets.github` keyed by org, as documented in `docs/setup.md`), and (2) at least one configured organization without a `webhook_secret` — explicitly presented as an acceptable/optional configuration in the docs. Given the docs describe `webhook_secret` as optional per-org, this is a realistic operator configuration, not a hypothetical requiring code changes outside the engine.

### Recommendation
Do not let an unauthenticated payload field determine which secret is used to authenticate the request. Either: require every configured organization to have a mandatory `webhook_secret` in multi-org mode, or bind the org used for verification to the org that owns the `repository.full_name`/Stack actually being mutated (i.e., resolve the target `Repository`/`Stack` first from `full_name`, then require its owner's secret to validate the signature) instead of trusting the caller-supplied `owner.login`.

### Proof of Concept
1. Configure Shipit with two orgs: `victim-org` (has `webhook_secret` set, owns Stack `victim-org/app`) and `attacker-org` (configured, no `webhook_secret`).
2. POST to `/webhooks` with header `X-Github-Event: push` and no (or garbage) `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/app" }
}
```
3. `repository_owner` resolves to `attacker-org` → `verify_webhook_signature` returns `true` because `attacker-org` has no `webhook_secret` [8](#0-7) .
4. `PushHandler#process` resolves the Stack via `payload.dig('repository','full_name')` = `victim-org/app` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` [7](#0-6)  on the real victim Stack, without ever having presented a valid signature for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
