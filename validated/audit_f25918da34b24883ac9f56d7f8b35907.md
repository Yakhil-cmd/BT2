### Title
Cross-organization team membership forgery via unbound `team.id` in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#process` locates a `Team` purely by the attacker-supplied `params.team.id`, and adds or removes members on it without ever checking that the *signing* organization (the one whose `webhook_secret` validated the request) actually owns that team. An attacker who legitimately controls any GitHub organization onboarded into Shipit can sign a `membership` webhook with their own org's secret while pointing `team.id` at a `Team` record belonging to a completely different organization, corrupting that team's membership.

### Finding Description
The broken binding is: `params.organization.login` (the organization whose `webhook_secret` produced a valid `X-Hub-Signature`) **should equal** `team.organization` for the `Team` row identified by `params.team.id` before any membership mutation is applied. This equality is never checked.

Trace:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , then does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . For a `membership` event (no `repository` key), `repository_owner` is exactly the attacker-controlled `organization.login` field of the JSON body. The attacker names their **own** organization here, so `Shipit.github(organization: "attacker-org")` resolves to the attacker's own legitimately-configured `webhook_secret`, and the HMAC they compute with that secret validates correctly. Signature verification therefore only proves "this request was signed by attacker-org's secret" — it does not prove anything about the `team` object referenced inside the payload.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login ... }` [3](#0-2) . The block that sets `team.organization` **only executes on record creation**. If a `Team` row with that `github_id` already exists (e.g., a privileged team already present in `Shipit.github_teams`), `find_or_create_by!` just returns the existing record, completely ignoring `params.organization.login`. There is no `assert team.organization == params.organization.login` anywhere in the handler.
3. `member = User.find_or_create_by_login!(params.member.login)` [4](#0-3)  resolves (or creates) the victim's `User` row purely from the attacker-supplied login string — no relation to the signing organization is checked here either.
4. `team.add_member(member)` [5](#0-4)  unconditionally appends the membership (or, for `action: 'removed'`, `team.members.delete(member)` removes it) with zero further validation — `Shipit::Membership` only enforces `user_id` uniqueness scoped to `team_id` [6](#0-5) , not organization ownership.

Existing guards do not stop this:
- `verify_signature` only checks the HMAC against the org named in the payload itself, which the attacker freely controls and legitimately owns a secret for [7](#0-6) .
- The `ExplicitParameters` schema in `MembershipHandler` only enforces types/presence of `team.id`, `organization.login`, `member.login` — it enforces no cross-field relationship [8](#0-7) .
- `Team` has no validation tying `github_id` to a specific `organization`, and `find_or_create_by!` silently no-ops the block on lookup hits.

Attacker's exact request: an HTTP `POST /webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed as `sha1=HMAC(attacker-org's webhook_secret, raw_body)`, and JSON body:
```json
{
  "action": "added",
  "team": { "id": <victim_team.github_id>, "name": "x", "slug": "x", "url": "https://x" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "victim-login" }
}
```
Because `attacker-org` is a real Shipit-configured org the attacker owns, this signature check passes, and `Team.find_or_create_by!(github_id: victim_team.github_id)` returns the pre-existing victim team, onto which the victim's `User` is appended as a member.

### Impact Explanation
This lets an attacker write a `Shipit::Membership` row associating an arbitrary existing `User` (identified only by GitHub login, a public string) with any `Team` already tracked by Shipit — including teams listed in `Shipit.github_teams`, which gate `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [9](#0-8)  and thus `force_github_authentication`'s access gate [10](#0-9) . If the victim later authenticates via OAuth, they (or anyone able to authenticate under that login) is granted authorization to the whole Shipit instance despite never having been a GitHub member of that team, and despite the attacker's org having no relationship to the target organization. The same primitive with `action: 'removed'` lets the attacker strip real members from any team Shipit already tracks. This is a cross-tenant authorization-state corruption: any org onboarded to Shipit (webhook_secret + config entry) can mutate membership state of teams belonging to unrelated organizations, repeatable at will since nothing rate-limits or re-validates this relationship. This matches the "escalation into `Shipit.github_teams` authorization" High-severity category.

### Likelihood Explanation
Preconditions are modest and match realistic multi-tenant Shipit deployments: (1) the attacker must own/administer at least one GitHub organization that has a Shipit webhook configured with its own `webhook_secret` (a normal, low-privilege setup step available to anyone who can create a GitHub org and register it with the Shipit instance, per the "Using Multiple Github Applications" configuration documented for multi-org Shipit deployments); (2) the target `Team`'s `github_id` must be known — team ids are visible to any member of the target org via the GitHub API and slugs are frequently guessable/public; (3) the victim's GitHub login must be known, which is always public. No GitHub or Shipit secrets belonging to the victim organization are required. The attack is a single HTTP POST, fully scriptable, and repeatable against any team already present in Shipit's database.

### Recommendation
In `MembershipHandler#find_or_create_team!` / `#process`, reject the webhook (or refuse to mutate membership) whenever the found/created `Team#organization` does not equal `params.organization.login` (case-insensitively, matching existing downcase handling), e.g.:
```ruby
team = find_or_create_team!
raise ArgumentError, "organization mismatch" unless team.organization.casecmp?(params.organization.login)
```
Alternatively/additionally, harden `verify_signature` for organization-scoped events so that the signing organization is cryptographically bound to the specific team/resource being mutated, not just to whichever organization name appears unauthenticated in the JSON body.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership from an unrelated organization can mutate another org's team" do
  victim_team = shipit_teams(:cyclimse_cooks) # organization: 'cyclimse'
  victim_user = shipit_users(:walrus)         # or any existing User by login

  @request.headers['X-Github-Event'] = 'membership'
  # Signature verification stubbed/mocked as legitimately produced by 'shopify' org's own secret,
  # exactly as the existing test suite does via `GithubHook.any_instance.stubs(:verify_signature).returns(true)`
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'shopify' }, # attacker's own org, signs with shopify's secret
  }.merge(member: { login: victim_user.login })

  assert_difference -> { Membership.count }, 1 do
    post :create, body: payload.to_json, as: :json
    assert_response :ok
  end

  # Binding check: signing org ('shopify') != team.organization ('cyclimse'), yet the membership was created.
  assert_not_equal 'shopify', victim_team.organization
  assert Membership.exists?(team: victim_team, user: victim_user)
end
```
This demonstrates that a payload whose verified signing organization (`shopify`) differs from the target team's actual `organization` (`cyclimse`) still results in a persisted `Membership` row, proving the absence of the equality check between the signing organization and `team.organization`.
