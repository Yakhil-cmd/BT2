### Title
Cross-repository commit status forgery via unscoped SHA lookup in StatusHandler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook payload by selecting a GitHub App configuration keyed on the *organization that owns the repository in the payload*, then verifying the HMAC signature with that organization's `webhook_secret` [1](#0-0) . This authenticates that "this payload was really produced by GitHub for organization X." However, `StatusHandler#process` never scopes its side effects to the repository/organization that was actually authenticated — it looks up commits globally by SHA across the entire Shipit instance and writes a status to every match [2](#0-1) .

### Finding Description
The binding that should hold is: `organization authenticated by verify_signature == organization whose data is mutated by the handler`. Every other handler enforces this by scoping through `Repository.from_github_repo_name(repository_name)` before touching any record [3](#0-2) . `StatusHandler`, in contrast, does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`Commit.where(sha: params.sha)` is a global query against the whole `commits` table, not scoped to `stacks` belonging to the authenticated `Repository`/organization [2](#0-1) . Because commit SHAs are content-addressed and frequently identical/colliding across unrelated repositories (e.g., shared history, cherry-picks, forks, or simply two independent commits with an intentionally forced/short-SHA-adjacent collision — but even the trivial case of the same commit being tracked by two different stacks/repos in the same Shipit instance is common), a webhook that is validly signed for organization/repository A can inject a fabricated commit status onto a `Commit` row that actually belongs to organization/repository B.

Before the attacker's request: commit statuses for repository B's commits can only be set by webhooks whose HMAC signature is verified against repository B's `webhook_secret` (i.e., only GitHub, acting for org B, can set them). After the attacker's request: a payload legitimately signed with org A's secret (attacker only needs push access / a triggerable status event in a repo they control under org A) can write an arbitrary status (`state`, `description`, `target_url`, `context`) onto a commit belonging to org B's stack, as long as it can reference/predict a matching SHA in B's history.

### Impact Explanation
Commit statuses are load-bearing for Shipit's deploy gating: the CHANGELOG documents "blocking statuses" that "prevent deploy even if they were reported on any of the commits in the deploy range," and merge-queue logic rejects commits missing/failing required statuses [4](#0-3) . An attacker who can get a status webhook accepted for *any* organization/repository configured in the Shipit instance can forge a `success` status for a commit in a different repository, bypassing CI/required-check gating and enabling an unauthorized deploy of a commit that never actually passed the checks it claims to have passed. This satisfies the "unauthorized deploy" impact bar, since it undermines the deploy-authorization decision made from commit status state, without requiring any Shipit session, API token, or write access to the victim organization/repository.

### Likelihood Explanation
Exploitability requires only: (1) the attacker controls (or can trigger a `status` event webhook for) some repository/organization already configured in the same Shipit instance, and (2) the ability to reference a SHA that also identifies a commit tracked under the victim stack (trivially achievable when the same upstream commit is mirrored/forked into multiple tracked stacks, a common real-world Shipit topology, or via engineered SHA reuse). No secrets, sessions, or elevated GitHub permissions for the victim org are needed — this is exactly the "verified-but-uncovered-binding" bug class from the report, applied to the organization-vs-written-repository equality instead of a hedge cap.

### Recommendation
Scope `StatusHandler#process` to the authenticated repository, mirroring every other handler's use of `stacks`/`Repository.from_github_repo_name(repository_name)` [3](#0-2) , e.g. restrict the `Commit` lookup to `stacks.map(&:commits)` (or a joined scope on the repository derived from the verified `repository_owner`) instead of a global `Commit.where(sha:)`.

### Proof of Concept
1. Configure two organizations/repositories in the same Shipit instance, `org-a/repo-a` and `org-b/repo-b`, each with its own `webhook_secret`.
2. Ensure a commit with SHA `S` is tracked by a stack under `org-b/repo-b` (e.g. because it was cherry-picked/mirrored from a shared upstream, or because SHA collision/prediction is engineered).
3. As the operator/attacker of `org-a/repo-a`, send a `status` event to `/webhooks` signed with `org-a`'s `webhook_secret`, with body `{"sha": "S", "state": "success", "repository": {"owner": {"login": "org-a"}, "full_name": "org-a/repo-a"}, ...}`.
4. `verify_signature` authenticates the request as originating from `org-a` [1](#0-0) .
5. `StatusHandler#process` executes `Commit.where(sha: "S")`, which matches the commit tracked under `org-b/repo-b`'s stack, and writes the forged `success` status onto it [2](#0-1) , potentially unblocking a deploy in `org-b`'s stack despite the payload never being authenticated for `org-b`.
