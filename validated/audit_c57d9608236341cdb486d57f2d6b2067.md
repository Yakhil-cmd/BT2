### Title
Merkle "node-as-leaf" collision allows forging membership proofs in `in merkle` address definitions and `is_valid_merkle_proof` AA checks - (File: merkle.js)

### Summary
`merkle.js`'s `verifyMerkleProof()` hashes the leaf element with the exact same function used to hash internal nodes, with no domain separation between leaf-level and node-level hashing. This is the same root cause as the Footium report: because leaves and internal nodes have the same shape/hash function, an attacker who knows two sibling hash values from a real tree can submit a "fake element" equal to the concatenation of those two hashes, together with the remaining real siblings, and have it verify against a genuinely published Merkle root — even though that "element" was never a real leaf.

### Finding Description
`getMerkleRoot`/`getMerkleProof` build the tree with `hash(str)` applied uniformly to leaves and to concatenated pairs of children: [1](#0-0) 
`verifyMerkleProof(element, proof)` recomputes `hash(element)` and folds in `proof.siblings` using the identical concatenation/hash operation, with the code itself flagging the risk: [2](#0-1) 

Because leaf-hashing and node-hashing are indistinguishable, if an attacker knows any two sibling hash strings `h1`, `h2` that are genuine internal nodes of a real tree whose root `R` has been legitimately published (e.g., via a data feed), they can set `element = h1 + h2` and supply the true siblings from that node up to the root. `verifyMerkleProof` will then report success against the real root `R`, "proving" membership of `h1+h2`, a value that was never one of the tree's actual leaves.

This bug class is reachable in two places in ocore:
1. Address definition authentifier `'in merkle'`, which lets an address require: verify a Merkle proof for a fixed `element` against a root that must exist in an oracle's `data_feeds` history: [3](#0-2) 
Any wallet user can author such an address definition and choose the `element` value themselves (analogous to Footium's attacker-chosen club `id`), then, when spending from that address, supply an attacker-crafted `serialized_proof` (siblings/root) as the authentifier at that path. If the oracle's already-published root happens to have (or the attacker can locate) two known sibling sub-hashes anywhere in its tree, the address owner can satisfy the `'in merkle'` condition without the oracle ever having actually published that specific `element`.
2. The oscript/AA formula function `is_valid_merkle_proof(element, proof)`, evaluated inside AA triggers: [4](#0-3) 
Here both `element` and `proof` (including `siblings`) can come directly from attacker-controlled `trigger.data`, making the forgery fully attacker-driven if an AA uses this primitive to check membership in a whitelist/allowlist Merkle root (e.g., to gate a payout), since `trigger.data.element` need not correspond to a real leaf at all — only the composed hash needs to match a root value known/stored by the AA.

### Impact Explanation
Where an AA or an address definition uses Merkle-root membership checks (`'in merkle'` or `is_valid_merkle_proof`) as an authorization gate — e.g., verifying an address, amount, or eligibility flag is part of an oracle-published or AA-stored allowlist — this collision lets an attacker satisfy the check for values that were never actually included in the tree. Depending on how the AA/definition uses the verified element (e.g., to authorize a payout, unlock funds, or grant a privileged action), this can lead to unauthorized fund release from an AA or bypass of an oracle-gated address condition, i.e., concrete unauthorized spending/fund loss.

### Likelihood Explanation
Exploitation requires the attacker to know two genuine sibling hash values from the real Merkle tree used by the oracle/AA — feasible whenever the tree's construction is deterministic and public (e.g., whitelist lists commonly published in full, or when other holders' proofs reveal sibling hashes), and requires the affected address definition or AA to place trust in unverified Merkle membership as an authorization mechanism. This is not automatically exploitable against every Merkle-check usage, but is a design flaw in the shared `merkle.js` primitive that any definition/AA author relying on it inherits, and is explicitly acknowledged as a known risk in the source comment.

### Recommendation
Add domain separation to `merkle.js`: hash leaves with a distinct prefix/tag (e.g., `hash("leaf:" + element)`) different from the prefix used for internal node hashing (e.g., `hash("node:" + left + right)`), so that no valid element hash can ever equal an internal node's hash. Apply this consistently in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof`.

### Proof of Concept
1. Oracle publishes Merkle root `R` for a data feed built by `getMerkleRoot` over some element set; tree structure (or at least two adjacent internal-node hash values `h1`, `h2` whose parent equals some ancestor of `R`) is knowable/public.
2. Attacker authors an address definition containing `['in merkle', [[oracle_address], feed_name, h1 + h2]]` (using `h1+h2` as the "expected element"), per [5](#0-4) .
3. When spending, attacker supplies a `serialized_proof` whose `siblings` are the real sibling hashes from the node containing `h1,h2` up to `R`.
4. `merkle.verifyMerkleProof(h1+h2, proof)` recomputes `hash(h1+h2)`, which equals the real internal node hash, then folds remaining real siblings and arrives at `R`, per [2](#0-1) .
5. `dataFeeds.dataFeedExists(...)` finds `R` genuinely published by the oracle, so `cb2(true)` is returned, satisfying the `'in merkle'` condition despite `h1+h2` never being a real leaf/data value.

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){

			index = Math.floor(index / 2);
