### Title
Full plaintext of every decrypted device message (private-payment blinding factors, xpubkeys, signing payloads) is written to console logs by default - ([File: device.js])

### Summary
Any paired correspondent device (or an attacker relaying through a hub as `hub/message`) causes `decryptPackage()` in `device.js` to log the entire decrypted device-message plaintext to `console.log`, with no redaction of sensitive fields. This mirrors the root cause of CVE-2021-20180 (Ansible `bitbucket_pipeline_variable`): secret-bearing data is unconditionally written to a log sink instead of being masked.

### Finding Description
`decryptPackage()` decrypts the AES-GCM `encrypted_package` of an incoming device message and then unconditionally logs the full plaintext: [1](#0-0) 

This function is reached directly from the `hub/message` justsaying handler as soon as signature and hash checks pass, i.e. from any correspondent device or anyone able to relay a message through the hub to `my_device_address`: [2](#0-1) 

The decrypted JSON (`json`) that gets printed in full is exactly the payload later dispatched to `wallet.js`'s `handleMessageFromHub`, which handles subjects that legitimately carry sensitive material:
- `sign` requests carry `private_payloads` — the address, blinding factor and amount of private (indivisible/divisible) asset outputs in plaintext: [3](#0-2) 
- `private_payments` carries private payment chains with blinding factors and addresses (see `validateAndSavePrivatePaymentChain` also logging output blinding data): [4](#0-3) 
- Correspondent pairing/wallet setup exchanges extended public keys (`my_xpubkey`) and other wallet metadata through the same message pipe (`wallet.js:96-100`, referenced subjects list includes `my_xpubkey`, `cancel_new_wallet`, `new_wallet_address`).

Because `decryptPackage` logs the raw decrypted string before any field-level filtering happens, all of this — blinding factors that protect the amount/ownership of "private" asset outputs, wallet-linking xpubkeys, and full unsigned-unit contents used in remote multisig signing — ends up in plaintext in the node's console/log output. Any downstream consumer of that log (log aggregation, crash reporting, `pm2`/systemd journals, debug consoles bundled into wallet apps) is exposed to the same data the private-payment/privacy feature is specifically designed to keep secret. Additionally, `createEncryptedPackage` and `reliablySendPreparedMessageToHub` log the same JSON in plaintext when *sending* a message: [5](#0-4) 

### Impact Explanation
Blinding factors and addresses of private-asset outputs are the confidentiality mechanism of ocore's private payments feature — leaking them defeats the privacy guarantee and can let an observer of the logs link amounts/addresses of a private chain, which is the equivalent of "credential/secret disclosure" in the analog CVE. Leaked extended pubkeys can be used to derive/watch all addresses of a wallet, degrading user privacy and enabling targeted analysis of funds. This is a confidentiality-only impact (matches the CVSS vector `C:H/I:N/A:N` of the source CVE): no direct fund loss, but private financial data belonging to the message sender is unconditionally exposed to whoever has access to the receiving device/hub's logs.

### Likelihood Explanation
Every hub-relayed or direct device message triggers this logging path with no configuration flag to disable it; the only requirement is that the attacker/counterparty is (or becomes) a correspondent device — which is the normal, expected trust model for pairing and private payments. This makes the disclosure deterministic and easy to trigger by any paired counterparty or hub operator, though it requires local/log access to actually read the leaked data (hence Medium severity, matching AV:L in the source CVE).

### Recommendation
Remove or heavily redact the `console.log("decrypted: "+decrypted_message)` (and the corresponding plaintext log in `reliablySendPreparedMessageToHub`/`createEncryptedPackage`) so private_payloads, blinding factors, and xpubkey fields are never written to logs. If logging is needed for debugging, log only the `subject` and a truncated/masked summary, gated behind an explicit debug flag that defaults to off.

### Proof of Concept
1. Pair two wallets (device A and B) so B is a correspondent of A.
2. From B, send A a `private_payments` or `sign` message containing a private asset output (has `blinding`, `address`, `amount`) or an extended pubkey via `my_xpubkey`.
3. On A's node, observe stdout/log: `decryptPackage` prints `"decrypted: " + decrypted_message`, i.e. the full JSON body including the private payload's blinding factors/addresses/xpubkey, in plaintext — regardless of any "private" flag on the asset.
