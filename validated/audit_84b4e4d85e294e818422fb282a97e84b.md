### Title
Expired debt map lets borrower withdraw all collateral while pool debt remains - (File: contracts/controller/src/storage/account.rs)

### Summary

The controller treats a missing `BorrowPositions` persistent map as an empty map instead of proving that the account is debt-free. An account owner can let the account’s persistent entries expire, selectively restore only the NFT ownership, `AccountMeta`, and `SupplyPositions` entries, and then call `withdraw(account_id, [(collateral_asset, 0)], to)` to remove all collateral while the pool still records the borrowed shares. [1](#0-0) [2](#0-1) 

### Finding Description

`get_account` fails when metadata or NFT ownership is unavailable, but it unconditionally converts missing supply and debt maps into empty maps. [3](#0-2) [4](#0-3) 

The account’s metadata, supply map, debt map, and delegates are separate persistent keys, so Soroban archival restoration does not inherently force all four entries to be restored together. [5](#0-4) [6](#0-5) 

After the owner authenticates, `settle_withdraw` obtains the stored supply position and submits the withdrawal to the pool before the post-operation solvency check. [2](#0-1) [7](#0-6) 

Because the omitted `BorrowPositions` key reads as an empty map, the calculated debt is zero and `health_factor` is set to `i128::MAX`, so the solvency gate cannot detect the outstanding debt. [8](#0-7) 

The pool tracks global `borrowed` scaled shares independently of the controller’s per-account map, so losing the map does not erase the protocol-level liability. [9](#0-8) 

### Impact Explanation

The borrower can withdraw the entire collateral position while retaining an unrecorded pool debt. The resulting account appears debt-free to controller risk calculations, while the pool’s global `borrowed` balance still includes the debt, leaving other suppliers and the protocol with an unbacked liability. This is theft of pool collateral and can create protocol insolvency when the withdrawn collateral exceeds the debt’s remaining backing. [1](#0-0) [10](#0-9) 

### Likelihood Explanation

A single unprivileged borrower can reach this path by opening a collateralized debt position, leaving it dormant until persistent storage expires, and then restoring only the entries needed for account resolution and collateral withdrawal: NFT ownership, `AccountMeta`, `SupplyPositions`, the relevant spoke/market/oracle state, and contract instances. Omitting `BorrowPositions` makes the controller load an empty debt map while still resolving the owner and supply position. [3](#0-2) [6](#0-5) 

The required withdrawal is permissionless for the account owner and does not require governance, oracle manipulation, a malicious token, or a privileged route. A zero withdrawal amount is explicitly interpreted as withdrawal of the whole position. [11](#0-10) [12](#0-11) 

### Recommendation

Do not interpret an absent position-map entry as an empty position when account metadata exists and the NFT resolves. Represent the three states explicitly—no account, absent map, and empty map—and make account-loading and value-moving flows fail closed when a required position-map key is absent or archived. At minimum, store an explicit position-map marker or embed position state in the account record so selective archival cannot convert real debt into `Map::new`. The same treatment should cover `SupplyPositions`, since silently substituting an empty map creates the same missing-state ambiguity. [4](#0-3) [13](#0-12) 

### Proof of Concept

1. Supply collateral through `supply(caller=owner, account_id=0, spoke_id=S, assets=[(C, collateral_amount)])`, receiving `account_id=A`. [14](#0-13) 
2. Borrow through `borrow(caller=owner, account_id=A, borrows=[(D, debt_amount)], to=Some(owner))`; the controller stores the debt under `ControllerKey::BorrowPositions(A)`. [15](#0-14) [1](#0-0) 
3. Leave the account dormant until the controller’s per-account persistent entries expire.
4. Submit a Soroban restore transaction whose footprint includes the position-NFT ownership entry, `ControllerKey::AccountMeta(A)`, `ControllerKey::SupplyPositions(A)`, and the market/oracle/spoke entries needed by withdrawal, while omitting `ControllerKey::BorrowPositions(A)`. The code defines these as independent storage keys. [5](#0-4) 
5. Call `withdraw(caller=owner, account_id=A, withdrawals=[(C, 0)], to=Some(owner))`; owner authorization succeeds, zero requests the full supply position, and the missing debt map loads as `Map::new`. [16](#0-15) [17](#0-16) [12](#0-11) 
6. The post-withdrawal risk calculation sees zero debt and returns `i128::MAX` health factor, allowing the withdrawal to finalize even though the pool’s global `borrowed` shares remain outstanding. [8](#0-7) [9](#0-8)

/// Stores a nonempty position map without renewing TTL; deletes an empty map.
fn write_side_map<V: TryFromVal<Env, Val> + IntoVal<Env, Val>>(
    env: &Env,
    key: &ControllerKey,
    map: &Map<HubAssetKey, V>,
) {
    let persistent = env.storage().persistent();
    if map.is_empty() {
        persistent.remove(key);
    } else {
        persistent.set(key, map);
    }
}
