### Title
Cross-tenant webhook forgery via divergent `repository.owner.login` vs `repository.full_name` fields lets an org-A signer mutate org-B's Stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against using `repository.owner.login` [1](#0-0) [2](#0-1) , but `LabeledHandler` (via `ReviewStackAdapter`) resolves and mutates the target Stack using the *independent* JSON field `repository.full_name` [3](#0-2) [4](#0-3) . Nothing enforces that `repository.owner.login` is a prefix of `repository.full_name`, so a valid HMAC computed with org A's secret can carry a `full_name` pointing at org B's repository/stack.

### Finding Description
The intended binding is: **`repository_owner` (the value used to choose the `webhook_secret` that validated the HMAC) == the owner segment of `repository.full_name` (the value used to locate/mutate the Stack)**. These are read from two structurally separate JSON keys of the same POST body — `repository.owner.login` and `repository.full_name` [2](#0-1)  vs [5](#0-4)  — and no validation anywhere ties them together.

Exploit flow:
1. Attacker controls (or is the legitimate admin of) organization A's Shipit tenant and therefore knows org A's `webhook_secret` (the shared secret they themselves configured between GitHub's webhook settings and Shipit's per-org config).
2. Attacker crafts a raw JSON body for a `pull_request` `labeled` event where `repository.owner.login = "orgA"` but `repository.full_name = "orgB/target-repo"` (org B being any tenant with review stacks enabled and a matching `TaskDefinition`/provisioning label config), sets `pull_request.state = "open"`, and includes a label matching org B's `provisioning_label_name`.
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC(secretA, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: pull_request`.
4. `verify_signature` calls `Shipit.github(organization: repository_owner)` with `repository_owner = "orgA"` (from `repository.owner.login`), fetches org A's `webhook_secret`, and the HMAC matches because the attacker signed with that exact secret [1](#0-0) . The request is accepted.
5. `WebhooksController#create` dispatches the full, unmodified params to `LabeledHandler.call` [6](#0-5) .
6. `LabeledHandler#repository` looks up `Shipit::Repository.from_github_repo_name(params.repository.full_name)` = org B's repo [3](#0-2) , and `handle` calls `stack.archive!`/`stack.unarchive!` on org B's `ReviewStack` via `ReviewStackAdapter#archive!`/`#unarchive!`, which perform real state changes — `deprovision`, `remove_from_provisioning_queue`, enqueue to `ReviewStackProvisioningQueue`, and construct a `Shipit::User` from the attacker-controlled `sender.login` as the actor [7](#0-6) .

Existing guards do not stop this: `verify_signature` only checks the HMAC against whichever secret the *attacker-supplied* `owner.login` selects — it never cross-checks `full_name`'s owner segment [8](#0-7) . `ExplicitParameters` schemas in `LabeledHandler` only validate types/presence of `repository.full_name`, not its relationship to `repository.owner.login` (which isn't even part of the handler's own schema) [5](#0-4) . `Repository.from_github_repo_name` and model validations only constrain the *format* of owner/name, not cross-field consistency with the signing owner [9](#0-8) .

### Impact Explanation
An attacker who legitimately controls one Shipit-integrated organization (and therefore knows only that organization's `webhook_secret`) can forge a webhook that is accepted as authentic and then trigger unauthorized stack lifecycle mutations (`archive!`/`unarchive!`, deprovision, re-enqueue to provisioning queue) against a review stack belonging to a completely different, unrelated organization's repository. This is a payload for one repository/tenant mutating another tenant's stack — matching the "Critical" category (payload for one repository mutating another's stack). Because the only precondition is knowledge of any one org's configured secret, this is repeatable against any org whose repo name the attacker can guess/target, as long as that repo has review stacks enabled with a label-driven provisioning behavior.

### Likelihood Explanation
Requires: (1) Shipit configured as multi-tenant with per-organization `webhook_secret`s, (2) attacker legitimately administers at least one such organization's Shipit/GitHub webhook integration and thus knows that org's secret, (3) knowledge/guess of a target org+repo name that has `review_stacks_enabled` and a `provisioning_behavior` (`allow_with_label`/`prevent_with_label`) configured. No GitHub session, no Shipit session, and no privileged Shipit role beyond ordinary webhook-signing capability for one's own org are needed — this fits the described unprivileged attacker profile as long as they are treated as a legitimate signer for *some* org. The attack is a single crafted HTTP POST, fully repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after, before dispatch), enforce that the owner used to select the signing secret matches the owner segment of every repository reference in the payload actually acted upon (e.g., validate that `repository.full_name.split('/').first.casecmp(repository_owner).zero?`), and reject the request otherwise. Additionally, harden `LabeledHandler`/`Handler` base class to re-derive the owner from `full_name` and assert equality with the `repository_owner` established at verification time before performing any Stack mutation, so a mismatch fails closed rather than silently trusting `full_name`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "signature verified for org A cannot mutate a stack belonging to org B" do
  org_a_secret = "secret-a"
  org_b_stack  = shipit_review_stacks(:orgb_review_stack) # repo owner = "orgb"
  Shipit.stubs(:github).with(organization: "orga").returns(
    stub(verify_webhook_signature: true)
  )

  payload = {
    action: "labeled",
    number: org_b_stack.pull_request.number,
    pull_request: {
      id: 1, number: org_b_stack.pull_request.number, url: "http://x",
      title: "t", state: "open", additions: 1, deletions: 1,
      head: { sha: "abc", ref: "feature" },
      user: { login: "attacker" },
      assignees: [],
      labels: [{ name: org_b_stack.repository.provisioning_label_name }],
    },
    repository: { owner: { login: "orga" }, full_name: org_b_stack.repository.full_name },
    sender: { login: "attacker" },
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', org_a_secret, payload)}"
  @request.headers["X-Github-Event"] = "pull_request"
  @request.headers["X-Hub-Signature"] = signature

  assert_no_changes -> { org_b_stack.reload.archived? } do
    post :create, body: payload, as: :json
  end
  # Binding under test: repository_owner ("orga", used to verify signature)
  # must equal repository.full_name's owner segment ("orgb") for any mutation
  # to be permitted. They diverge here, so no Stack belonging to org B may change.
end
```
This test currently fails against the existing code, because `LabeledHandler` archives/unarchives `org_b_stack` despite the signature only proving authenticity for `orga`.

          def archive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no Stack exists. Ignoring."
              )
              return true
            end
            return if stack.archived?

            stack.remove_from_provisioning_queue
            stack.deprovision
            stack.archive!(user, *args, &block)
          end

          def unarchive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no ReviewStack exists. Creating."
              )
              return create!
            end
            return unless stack.archived?

            stack.transaction do
              Shipit::ReviewStackProvisioningQueue.add(stack)
              stack.unarchive!(*args, &block)
            end
          end

          def user
            @user ||= Shipit::User.find_or_create_by_login!(params.sender["login"])
