### Title
Scope-token bypass in `Api::CCMenuController` allows any stack-scoped API token to read every stack's deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` bound to a specific `stack_id` can only ever see that one stack, by scoping all lookups through the `stacks` helper: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . `Api::CCMenuController`, however, overrides `stack` and resolves it directly against the full `Stack` relation, completely bypassing that scoping: `@stack ||= Stack.from_param!(params[:stack_id])` [2](#0-1) .

### Finding Description
The authorization model for API tokens in this engine is: `read:stack`/`write:stack`/etc. permission strings authorize an *operation*, while the `stack_id` column on `ApiClient` is meant to authorize a *scope* (which stack that operation may act on). `ApiClient#check_permissions!` only checks the operation string [3](#0-2) ; the scope binding is enforced elsewhere, in `BaseController#stacks`/`#stack` [1](#0-0) . This equality the engine implicitly relies on is:

`stack a token authorizes (current_api_client.stack_id) == stack the request actually touches (params[:stack_id] resolved through `stacks`)`

`Api::CCMenuController` breaks this equality. It keeps `require_permission :read, :stack` (so the operation check still passes for any token that merely has `read:stack`), but its private `stack` method resolves `params[:stack_id]` against the unscoped `Stack` relation instead of the api-client-scoped `stacks` relation:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Compare this with the correct pattern used everywhere else in the API (e.g. `DeploysController`, which relies on the inherited `stack` helper from `BaseController` that filters through `stacks`) [4](#0-3) . `Api::CCMenuController#authenticate_api_client` also swaps the normal Basic-Auth-token flow for a query-string `token` param but still delegates to the same `ApiClient.authenticate` [5](#0-4) , so the same class of token — including the very common "CCMenu URL" tokens minted specifically scoped to one stack — is affected.

These per-stack CCMenu tokens are explicitly generated with an implicit expectation of stack-only scope: the UI `CCMenuUrlController` mints a `read`-only `ApiClient` bound to a given stack and embeds its `authentication_token` directly in a plain-text query string URL, which is by design shared outside the authenticated Shipit session (e.g. pasted into a CI dashboard / CCMenu build monitor) [6](#0-5) . Because that same token authenticates against `Api::CCMenuController`, and that controller ignores the `stack_id` scope, anyone holding one such stack-scoped CCMenu URL can rewrite `stack_id` in the query string to fetch the CCMenu XML status feed (deploy/rollback state, running status, timestamps) of **any other stack in the installation**, including private or restricted repositories the token holder was never authorized to see.

### Impact Explanation
This is an unauthenticated-read-style escalation: a token that was only supposed to authorize reading one stack's build status can be used to enumerate and read the deploy status of every stack managed by the Shipit instance, crossing repository/stack boundaries without ever touching `Shipit.api_clients_secret`, a GitHub credential, or a privileged account. This matches the "High" impact bucket for "unauthenticated read of stack state, task streams or deploy output" via a broken deployment-trust binding (stack a token authorizes vs. stack it actually touches).

### Likelihood Explanation
Likelihood is high for anyone who already holds *any* valid, low-privilege, stack-scoped `read:stack` CCMenu token (these are routinely distributed to third-party CI dashboards/build-monitor tools since they're embedded in a plain URL query string by design). No additional secrets, sessions, or elevated access are required — only changing the `stack_id` query parameter of the URL they already legitimately possess.

### Recommendation
Make `Api::CCMenuController#stack` go through the same `stacks` scoping helper used by `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` unscoped, so a stack-bound `ApiClient` cannot resolve a `stack_id` outside its `stack_id` binding.

### Proof of Concept
1. Create/obtain a Shipit CCMenu URL for `stack A` (e.g. via `GET /stacks/A/ccmenu.xml`, which mints a `read:stack`-only `ApiClient` scoped to stack A and returns a URL like `.../api/stacks/A/ccmenu.xml?token=<verified-token>`) — matching the flow exercised in `test/controllers/ccmenu_controller_test.rb` [6](#0-5) .
2. As the holder of that URL (who has no access to stack B), send `GET /api/stacks/B/ccmenu.xml?token=<same-token>`.
3. `authenticate_api_client` in `Api::CCMenuController` successfully authenticates the token via `ApiClient.authenticate(params[:token])` [5](#0-4) ; `require_permission :read, :stack` passes because the token has `read:stack` [7](#0-6) ; `stack` resolves `params[:stack_id]` ("B") against the unscoped `Stack` relation [2](#0-1) , returning stack B's `deploys_and_rollbacks.last` status in the response, despite the token being scoped only to stack A.
