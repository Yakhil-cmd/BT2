### Title
Missing HTTP timeout / context deadline in `downloadAsset` allows indefinite hang on attacker-controlled asset host - (File: pkg/cmd/release/download/download.go)

### Summary
`downloadAsset` builds and sends an outbound `GET` request with `http.NewRequest` (no `context.Context`, no deadline) and calls `httpClient.Do(req)`, where `httpClient` originates from `api.NewHTTPClient` / `HttpClientFunc` in the factory, neither of which set an `http.Client.Timeout` or per-request cancellation. A malicious release-asset host (or a GitHub archive endpoint if compromised/spoofed within the attacker's control such as a redirect target) can therefore stall the response headers or body indefinitely and hang the download goroutine forever.

### Finding Description
`gh release download` walks release assets (`toDownload`, populated from attacker-controlled `release.Assets` names and `APIURL`s, see `pkg/cmd/release/download/download.go:171-243`) and dispatches them to worker goroutines in `downloadAssets` (`pkg/cmd/release/download/download.go:262-298`). Each worker calls `downloadAsset` (`pkg/cmd/release/download/download.go:300`), which:

- Builds the request with `http.NewRequest("GET", assetURL.String(), nil)` — using the context-less constructor rather than `http.NewRequestWithContext`, so there is no cancellation path (`pkg/cmd/release/download/download.go:305`).
- Issues the request via `resp, err := httpClient.Do(req)` (`pkg/cmd/release/download/download.go:326`), then reads the entire body through `dest.Copy` / `io.Copy` (`pkg/cmd/release/download/download.go:350`, `pkg/cmd/release/download/download.go:452`) with no read/write deadlines.

Tracing the `httpClient` back to its construction: `HttpClientFunc` in `pkg/cmd/factory/default.go:188-209` builds it via `api.NewHTTPClient` (`api/http_client.go:33-87`), which wraps `ghAPI.NewHTTPClient` from `go-gh`. Nowhere in this chain is `http.Client.Timeout` set, nor is a `Transport` with `ResponseHeaderTimeout`/dial timeouts configured, nor is a bounded `context.Context` threaded into the request. `downloadRun` uses a bare `context.Background()` for the release-metadata fetch (`pkg/cmd/release/download/download.go:156`) which is likewise never given a deadline, and that context isn't even passed into `downloadAsset` at all.

Because `assetURL` and asset names come straight from the release API response (`shared.ReleaseAsset.APIURL`, `.Name`), which is populated by an untrusted repository owner (or gist/artifact/archive equivalent), an attacker who publishes a release with an asset pointing at a slow-loris-style endpoint can make the victim's `gh release download` block indefinitely: no client-side timeout, no context deadline, and no read deadline on the socket exist to bound the call.

### Impact Explanation
This is a Denial-of-Service / unbounded resource consumption vulnerability on the victim's machine: a hung worker goroutine holds an open TCP connection and blocks the corresponding CLI worker slot forever (with default `Concurrency = 5`, a release with ≤5 stalling assets can fully wedge the command). In CI pipelines that run `gh release download` unattended, this can hang the job until an external CI-level timeout intervenes, consuming compute/agent time and blocking pipeline progress — matching the "High: Unbounded resource consumption from a single attacker-published object" impact class described in the prompt.

### Likelihood Explanation
Highly feasible and fully attacker-controlled: any unprivileged GitHub user can publish a public release with an asset whose download URL (or the server backing that URL) is under their control, or where the underlying host they operate responds slowly. No privileges beyond publishing a release, no MITM, and no victim opt-in beyond running the ordinary `gh release download` command are required. The behavior is deterministic and repeatable against any victim that downloads the crafted release.

### Recommendation
- Thread a bounded `context.Context` (e.g., `context.WithTimeout`) from `downloadRun` through `downloadAssets` into `downloadAsset`, and use `http.NewRequestWithContext` instead of `http.NewRequest`.
- Alternatively/additionally, set `http.Client.Timeout` (or a `Transport` with `ResponseHeaderTimeout`/`DialContext` timeouts) on the client returned by `api.NewHTTPClient`/`HttpClientFunc`, and enforce a minimum read-throughput or absolute deadline while copying the body in `destinationWriter.Copy`.
- Ensure the per-asset context is independent per worker so one stalling asset cannot affect others, and surface a clear timeout error to the user.

### Proof of Concept
Go test using `httptest` with a handler that accepts the connection but never writes a response body (slow-loris):

```go
func TestDownloadAsset_HangsWithoutTimeout(t *testing.T) {
    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusOK)
        flusher, _ := w.(http.Flusher)
        for {
            w.Write([]byte{0})
            if flusher != nil {
                flusher.Flush()
            }
            time.Sleep(time.Hour) // simulate a stalled attacker endpoint
        }
    }))
    defer srv.Close()

    dest := destinationWriter{dir: t.TempDir()}
    httpClient := &http.Client{} // as produced by api.NewHTTPClient — no Timeout set

    done := make(chan error, 1)
    go func() {
        done <- downloadAsset(&dest, httpClient, safeurl.NewImmutableSafeURL(srv.URL), "evil.bin", false)
    }()

    select {
    case <-done:
        // expected: should return before deadline
    case <-time.After(2 * time.Second):
        t.Fatal("downloadAsset did not respect any timeout/deadline — hung indefinitely")
    }
}
```

Expected result today: the test times out/fails because `downloadAsset` never returns — confirming the missing-timeout invariant is violated.
