### Title
Cross-organization webhook forgery bypasses signature binding, enabling unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit's webhook signature verification selects *which* GitHub App/organization secret to check against using an attacker-controlled JSON field (`repository.owner.login` or `organization.login`), while every downstream event handler resolves the *repository/stack to act on* from a different attacker-controlled field (`repository.full_name`). Nothing enforces that these two fields are consistent, so a payload can be "authenticated" as belonging to one (weakly protected or secret-less) organization while its effects are applied to a Stack belonging to a completely different, protected organization/repository.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to verify against solely from the payload's own `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` also unconditionally returns `true` whenever no `webhook_secret` is configured for that organization: [3](#0-2) 

Shipit explicitly supports multiple, independently configured GitHub Apps/organizations sharing the single `/webhooks` endpoint, each with its own (optional) `webhook_secret`: [4](#0-3) 

Meanwhile, every event `Handler` resolves the repository/stack that actually gets mutated purely from `repository.full_name` in the same JSON body — a field independent of `repository.owner.login`: [5](#0-4) [6](#0-5) 

The binding that should hold is:
`organization authenticated (repository.owner.login / organization.login used to pick the verifying secret) == organization that owns the repository actually written (repository.full_name used by the handler)`

This equality is never checked. An attacker who can produce a validly-signed body for *any* configured organization (trivially true for any org with `webhook_secret` unset/blank, per the `return true unless webhook_secret` short-circuit, or for any org whose secret the attacker legitimately knows because they administer that org's own GitHub App installation) can set `repository.owner.login`/`organization.login` to that org while setting `repository.full_name` to `"target-org/target-repo"` for a completely unrelated, protected Stack. `verify_signature` passes because it only checked the (weak) organization's secret; the handler then acts on the target repository's Stack.

### Impact Explanation
This breaks the deployment-trust binding between "which organization proved its identity via HMAC" and "which repository's Stack gets mutated." Concretely reachable handlers include:
- `PushHandler`, which triggers `stack.sync_github(expected_head_sha: params.after)` for any stack matching the forged `repository.full_name`/branch — an attacker-controlled sync trigger on a target repo the attacker has no access to.
- `StatusHandler`, which creates a `Status` (CI status) record for an arbitrary `sha` on the target repository/commit. If the target Stack has continuous deployment enabled, forging a "success" status for a chosen commit can cause Shipit to automatically pick it up and deploy it — an **unauthorized deploy**, which is explicitly listed as a Critical impact.
- `PullRequest::OpenedHandler`/`ReviewStackAdapter`, which can provision Review Stacks (and their deploy pipeline) for the target repository based entirely on forged payload content.

Because the org-selection field and the repo-target field are independent, unrelated attacker-supplied JSON keys, and because at least one configured organization having no `webhook_secret` (a documented, supported configuration) makes verification a no-op for that org, this is directly reachable by an unprivileged external attacker with only network access to the public `/webhooks` endpoint — no Shipit session, API token, or repository write access is required.

### Likelihood Explanation
Likelihood is high in any multi-organization Shipit deployment (explicitly documented/supported via `config/secrets.*.yml` with per-org `github:` blocks) where at least one configured organization has no `webhook_secret` set (shown as the default/example value `webhook_secret: # nil` in the shipped example configs) or where an attacker otherwise has legitimate access to one org's real webhook secret (e.g., they administer their own low-value GitHub org/app that is also configured on the same Shipit instance). The webhook endpoint is unauthenticated by design (it's meant to receive GitHub's calls), so no credentials beyond crafting the HTTP request are needed.

### Recommendation
Bind webhook processing to a single, verified organization: derive the organization used for repository/stack lookup from the same identity that was cryptographically verified (e.g., resolve and pin the `Repository`/`Stack` via the GitHub App's own known installation/org, not from an unauthenticated JSON field), or explicitly assert `repository.full_name.split('/').first == repository_owner` (and reject on mismatch) before dispatching to any handler. Additionally, treat a blank/missing `webhook_secret` as "reject all webhooks for this org" rather than "always verified," or require `webhook_secret` to be mandatory for any org configuration.

### Proof of Concept
1. Configure (or find deployed) Shipit instance with two orgs: `weak-org` (no `webhook_secret` configured) and `victim-org` (has an active, continuous-deployment-enabled Stack for `victim-org/critical-app`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "weak-org" }, "full_name": "victim-org/critical-app" },
  "sha": "<attacker-chosen-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "target_url": "https://example.com",
  "branches": [{ "name": "master" }]
}
```
No `X-Hub-Signature` (or any value) is required because `repository_owner` resolves to `weak-org`, whose `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. `WebhooksController#verify_signature` passes; `Shipit::Webhooks.for_event('status')` dispatches to the status handler, which creates a `Status(state: "success")` against `victim-org/critical-app`'s commit — potentially satisfying that Stack's continuous-deployment gating and triggering an unauthorized deploy of an attacker-chosen commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
