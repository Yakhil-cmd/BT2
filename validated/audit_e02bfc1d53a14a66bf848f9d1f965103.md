## Title
Private payment "duplicate" detection improperly validates the full private‑payment chain before treating it as already‑verified - ([File: private_payment.js])

### Summary
The Shopware advisory describes a bug where a state‑transition check (double opt‑in) could be skipped because the validation of the confirming input was too weak, letting an attacker complete registration without actually proving ownership of the resource being confirmed. The analogous pattern in `ocore` is in `validateAndSavePrivatePaymentChain` in `private_payment.js`, where a private‑payment element is treated as an already‑validated "duplicate" — and the entire cryptographic chain validation is skipped — based on an insufficiently strict comparison against a single previously stored output.

### Finding Description
`validateAndSavePrivatePaymentChain` is the entry point used to validate and persist a chain of private-payment elements (`arrPrivateElements`) received from a payment counterparty (e.g. over a device message) [1](#0-0) .

Before running the real validation (`indivisibleAsset`/`divisibleAsset` `validateAndSavePrivatePaymentChain`, which checks spend proofs, chain linkage, and input/output balance), the code performs a "duplicate" check against the `outputs` table: [2](#0-1) 

For divisible assets, the comment itself acknowledges the weakness: *"divisible outputs are never hidden individually and sql has no output_index filter, so match against any of them"* [3](#0-2) . The code matches the incoming `headElement.payload.outputs` array against **any** row previously stored for that `unit`/`asset`/`message_index`, rather than verifying that the *entire* incoming chain (`arrPrivateElements`, including all upstream elements referenced via `payload.inputs`) is cryptographically identical to what was previously validated.

If `bDuplicate` evaluates `true`, the function immediately calls `transaction_callbacks.ifOk()` and returns, entirely skipping `assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, transaction_callbacks)` — meaning no spend-proof checks, no chain-linkage checks (`parsePrivatePaymentChain` in `indivisible_asset.js`), and no balance checks are performed on the rest of `arrPrivateElements` [4](#0-3) .

Because the SQL query and comparison only require one output entry in `payload.outputs` to numerically match a previously stored, already-revealed output (address, amount, blinding, denomination), a malicious private-payment counterparty can attach a legitimate/known output entry to a chain payload while supplying forged or unvalidated earlier elements (`arrPrivateElements[1..]`, spend proofs, or additional outputs), and the callback path `ifOk()` is reached without those elements ever being checked.

### Impact Explanation
A wallet (light client) receiving a crafted private-payment chain from a counterparty can be told the payment chain is valid (`callbacks.ifOk()`) even though the actual chain of custody, spend proofs, and input/output balancing were never verified. This is a direct analog of skipping the "confirming" validation step (like the newsletter double opt-in), and in the private-payment context this can lead a wallet to trust and act upon (e.g., forward or re-spend) a coin whose provenance was never actually proven — a violation of the "prove root cause -> concrete spending / freezing / disagreement on validity" bar, since it undermines the guarantee that `ifOk()` only fires after full chain verification.

### Likelihood Explanation
Any unprivileged private-payment counterparty (or paired device) can trigger this path simply by sending a private payment chain whose head element reuses a previously-seen, already-validated output value while attaching unverified/forged earlier chain elements. No special privileges are required beyond normal private-payment message exchange.

### Recommendation
Tighten the duplicate-detection logic so it requires the entire submitted `arrPrivateElements` chain (not just one output value) to be byte-for-byte identical to a previously fully-validated chain (e.g., by hashing/comparing the full chain, or storing and comparing the full spend-proof/element list) before skipping `assetModule.validateAndSavePrivatePaymentChain`. Alternatively, always run full validation and only use the duplicate DB lookup as an optimization/short-circuit for genuinely-identical resubmissions, never bypassing verification of unseen chain elements.

### Proof of Concept
1. Attacker (Bob) sends Alice a valid private payment chain once; Alice's wallet validates and stores the resulting `outputs` row (address, amount, blinding, denomination now known).
2. Bob later sends Alice a new `arrPrivateElements` chain where `headElement.payload.outputs` still contains the same previously-revealed output entry, but earlier elements in the chain (`arrPrivateElements[1..]`) are forged/invalid (e.g., unverifiable spend proofs or a broken chain link).
3. `validateAndSavePrivatePaymentChain` in `private_payment.js` matches the reused output entry, sets `bDuplicate = true`, and calls `ifOk()` without ever invoking `assetModule.validateAndSavePrivatePaymentChain` to validate the forged earlier elements [5](#0-4) .
4. Alice's wallet treats the chain as fully validated, even though the forged elements were never checked.

function parsePrivatePaymentChain(conn, arrPrivateElements, callbacks){
	var bAllStable = true;
	var issuePrivateElement = arrPrivateElements[arrPrivateElements.length-1];
	if (!issuePrivateElement.payload || !issuePrivateElement.payload.inputs || !issuePrivateElement.payload.inputs[0])
		return callbacks.ifError("invalid issue private element");
	var asset = issuePrivateElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in issue private element");
	var denomination = issuePrivateElement.payload.denomination;
	if (!denomination)
		return callbacks.ifError("no denomination in issue private element");
	async.forEachOfSeries(
		arrPrivateElements,
		function(objPrivateElement, i, cb){
			if (!objPrivateElement.payload || !objPrivateElement.payload.inputs || !objPrivateElement.payload.inputs[0])
				return cb("invalid payload");
			if (!objPrivateElement.output)
				return cb("no output in private element");
			if (objPrivateElement.payload.asset !== asset)
				return cb("private element has a different asset");
			if (objPrivateElement.payload.denomination !== denomination)
				return cb("private element has a different denomination");
			var prevElement = null; 
			if (i+1 < arrPrivateElements.length){ // excluding issue transaction
				var prevElement = arrPrivateElements[i+1];
				if (prevElement.unit !== objPrivateElement.payload.inputs[0].unit)
					return cb("not referencing previous element unit");
				if (prevElement.message_index !== objPrivateElement.payload.inputs[0].message_index)
					return cb("not referencing previous element message index");
				if (prevElement.output_index !== objPrivateElement.payload.inputs[0].output_index)
					return cb("not referencing previous element output index");
			}
			validatePrivatePayment(conn, objPrivateElement, prevElement, {
				ifError: cb,
				ifOk: function(bStable, input_address){
					objPrivateElement.bStable = bStable;
					objPrivateElement.input_address = input_address;
					if (!bStable)
						bAllStable = false;
					cb();
				}
			});
		},
		function(err){
			if (err)
				return callbacks.ifError(err);
			callbacks.ifOk(bAllStable);
		}
	);
}
