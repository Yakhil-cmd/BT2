### Title
Webhook signature verification is bound to a different field (`repository.owner.login`) than the field used to select the repository/stack being acted upon (`repository.full_name`), allowing cross-tenant webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization whose `webhook_secret` will validate the HMAC signature using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login` as a fallback). Once the signature is accepted, `create` hands the *entire, attacker-controlled* JSON payload to the registered webhook handlers. Those handlers (e.g. `Shipit::Webhooks::Handlers::Handler#stacks`) resolve the target repository/stack from a **different** field: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so a payload can be crafted where the "owner" used for signature verification and the "full_name" used for execution point to two unrelated repositories/organizations.

### Finding Description
- Signature verification: `verify_signature` picks the signing GitHub App by `repository_owner`: [1](#0-0) [2](#0-1) 

- Signature checking itself is a plain HMAC compare against the raw body using whichever organization's `webhook_secret` was selected: [3](#0-2) 

- Execution/target selection is entirely decoupled and instead reads `repository.full_name`: [4](#0-3) 

- `PushHandler` (and other default handlers) act on whatever stacks match that `full_name`: [5](#0-4) 

Shipit's multi-tenant GitHub App configuration (documented, supported) allows several independent organizations to each register their own app/`webhook_secret`: [6](#0-5) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by signature (repository.owner.login / organization.login)` ≠ `repository actually acted upon (repository.full_name)`.

Before the attack: for a legitimate GitHub webhook, `repository.owner.login` is always the owner segment of `repository.full_name` (GitHub itself sets both), so the two are always consistent, and the org whose secret validated the signature is always the org actually being modified.

After the attack: an attacker who controls their own org ("org-attacker", with a Shipit-configured `webhook_secret` they know because they set it up) can POST a JSON body where:
- `repository.owner.login` = `"org-attacker"` → makes `verify_signature` pick `org-attacker`'s webhook secret, which the attacker correctly signs the raw body with, so signature validation passes.
- `repository.full_name` = `"victim-org/victim-repo"` (any repository/stack tracked by the shared Shipit instance).

`Handler#stacks` then resolves stacks for `victim-org/victim-repo`, entirely bypassing the fact that the signature only proved possession of `org-attacker`'s secret, not `victim-org`'s.

### Impact Explanation
`PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for every matching (non-archived) stack of the victim repository/branch, which schedules `GithubSyncJob`. For stacks configured with continuous deployment, a forced/attacker-timed sync can trigger an unrequested deploy of the victim's stack — an unauthorized deploy triggered by an attacker who never had any credential, permission, or relationship to the victim organization or repository, only knowledge of an unrelated organization's own webhook secret. This satisfies the Critical impact category "an unauthorized deploy, rollback or merge," since the attacker is able to act on a repository/stack they have no authorization over, purely by exploiting the mismatch between the signature-verification identity and the execution-target identity.

Other default handlers (`pull_request`, `status`, `check_suite`) are reachable the same way, extending the blast radius to any repository/stack hosted on the shared Shipit instance, not just the attacker's own.

### Likelihood Explanation
The only prerequisite is that the attacker legitimately controls one org/app entry in Shipit's `github:` config (a normal, documented multi-tenant setup) and can therefore compute a valid HMAC with their own secret. No Shipit session, `ApiClient` token, GitHub App private key of the victim, or repository write access is required — the attacker interacts solely with the public `WebhooksController#create` endpoint. Crafting the JSON body with mismatched `repository.owner.login`/`repository.full_name` values requires no special access, only knowledge of the target repository's `owner/name` string, which is public.

### Recommendation
Bind the signature-verification identity to the exact same field used for execution. Concretely:
- Derive `repository_owner` from `repository.full_name`'s owner segment (or otherwise ensure `repository.owner.login` and the owner segment of `repository.full_name` match before proceeding), and reject the payload if they diverge.
- Alternatively, verify the signature using the organization actually resolved by `Handler#repository_name` rather than a field the attacker can set independently.

### Proof of Concept
1. Shipit hosts stacks for `victim-org/victim-repo` (owned by "victim-org", a separate GitHub App/webhook_secret) and is also configured (per documented multi-tenant support) with an app for "org-attacker", whose `webhook_secret` the attacker knows (they created it).
2. Attacker crafts a push-event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<any sha the victim repo may have>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker's webhook_secret, raw_body)>` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "org-attacker")` (from `repository.owner.login`), verifies successfully against the attacker's own secret.
5. `create` dispatches to `PushHandler`, whose `stacks` resolves via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, invoking `stack.sync_github` on the victim's real stacks — despite the attacker never having proven any relationship to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
