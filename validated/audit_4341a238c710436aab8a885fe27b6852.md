### Title
Race condition between concurrent AA-trigger caches causes unhandled null-pointer TypeError and node crash - ([File: aa_composer.js])

### Summary
The CVE describes a race condition in the Linux kernel's `dvbdmx_write()` where concurrent access to a shared structure leaves a pointer null before it is dereferenced, causing a kernel panic. The analogous pattern in `ocore` is the shared, unlocked in-memory unit cache `storage.assocUnstableUnits`, which multiple asynchronous AA-execution and stabilization paths mutate concurrently, and which is dereferenced without a null-check in `aa_composer.js`'s revert path.

### Finding Description
`storage.assocUnstableUnits` is a global, in-process cache of not-yet-stable unit properties, populated in `writer.js` when a unit is written [1](#0-0)  and pruned as units stabilize or get archived, e.g. in `main_chain.js`'s `markMcIndexStable` [2](#0-1)  and in `joint_storage.js`'s `purgeUncoveredNonserialJoints`, which calls `storage.forgetUnit` while holding only the `write` mutex [3](#0-2) .

When an AA response chain bounces or is reverted, `aa_composer.js`'s `revertResponsesInCaches` reads the first response unit directly out of `storage.assocUnstableUnits` and immediately dereferences its `parent_units` field without checking whether the entry still exists: [4](#0-3) 

This function is invoked from the AA trigger-handling pipeline (`handleTrigger`/`handleSecondaryTriggers`) whenever a chain of AA responses needs to be unwound because a later secondary AA in the chain bounced [5](#0-4) . AA trigger execution (`handleAATriggers`) runs under the `aa_triggers` mutex and iterates units serially [6](#0-5) , but the underlying `writer.saveJoint` calls, cache purges (`purgeUncoveredNonserialJoints`), and MCI stabilization (`markMcIndexStable`) all mutate the same `assocUnstableUnits`/`assocStableUnits` maps under a *different* lock key (`write`), and units can be moved from unstable to stable, or forgotten entirely, between when a response unit is created and when a later bounce forces `revertResponsesInCaches` to look it up. If the response unit has already been migrated out of `assocUnstableUnits` (e.g., its MCI stabilized concurrently, or it was purged as an uncovered/non-serial unit) by the time the bounce path executes, `storage.assocUnstableUnits[first_unit]` returns `undefined`, and the subsequent `.parent_units` access throws a `TypeError: Cannot read properties of undefined`, an uncaught exception in Node.js that crashes the process (analogous to a NULL-pointer dereference causing a kernel panic).

### Impact Explanation
An uncaught `TypeError` inside the write/AA-execution pipeline is a synchronous throw with no `try/catch` around this path, which propagates up and crashes the ocore process, exactly like a kernel panic/DoS in the original CVE. Because this occurs inside AA trigger processing, which every node executing autonomous agents runs as part of consensus-critical unit stabilization, a crash here halts the affected node's ability to process new units, and if reproducible deterministically by a chain of AA definitions and triggers that any unprivileged AA author can construct, it can be used to repeatedly crash full nodes that host AAs, degrading network liveness (nodes unable to confirm new units) until manually restarted.

### Likelihood Explanation
Triggering this precisely requires winning a race between the moment a response unit is added to `assocUnstableUnits` and the moment a chain-bounce needs to revert it — a scenario that requires deep AA-chain crafting (nested/secondary AA triggers where a downstream AA bounces) combined with unlucky timing of MCI stabilization or uncovered-unit purging on the executing node. This is architecturally reachable by any AA trigger sender who composes a chain of AAs with a bouncing tail, but the timing window is narrow and node-state dependent, making it a plausible but not trivially reproducible race — consistent with the CVSS AC:H (high attack complexity) rating of the original CVE.

### Recommendation
Add a defensive existence check before dereferencing cache entries in `revertResponsesInCaches` (and any other code path indexing `storage.assocUnstableUnits`/`assocStableUnits` by unit without first confirming presence), and audit whether cache mutation (`writer.saveJoint`, `markMcIndexStable`, `purgeUncoveredNonserialJoints`) and AA revert logic need to share a single mutex key so that a response unit cannot be evicted from the in-memory caches while its AA response chain is still being unwound.

### Proof of Concept
Concrete reproduction would require constructing: (1) a primary AA trigger that invokes secondary AA(s) forming a multi-unit response chain, (2) the final secondary AA bouncing so `revertResponsesInCaches` is invoked on the earlier response units in the chain, and (3) timing the trigger so that a concurrent `stabilizeMci`/`purgeUncoveredNonserialJoints` cycle removes the first response unit from `storage.assocUnstableUnits` before the revert executes. I was not able to fully verify the exact interleaving/timing feasibility within the available static analysis (no access to execute the code or a debugger); this is inferred from the code paths cited above and should be validated by a background agent with runtime/test access.
