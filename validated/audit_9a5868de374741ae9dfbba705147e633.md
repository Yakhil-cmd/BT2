## Analysis: Signed-package replay across AA instances (analog of "signature replayable across domains")

### Title
Signed off-chain packages (`is_valid_signed_package`) are not bound to the verifying AA/contract, enabling cross-instance signature replay - ([File: formula/evaluation.js], [File: signed_message.js])

### Summary
The reported bug is about EIP-712-style signatures that omit a domain separator (contract name/address/chain), letting a signature intended for one deployment be replayed on another. The closest reachable analog in ocore is the `is_valid_signed_package()` oscript function, backed by `signed_message.validateSignedMessage()` [1](#0-0) , which AAs use to verify off-chain-signed data (e.g. trading orders in `order_book_exchange.oscript`) [2](#0-1) .

### Finding Description
`getSignedPackageHashToSign()` hashes only `signed_message`, `authors`, `last_ball_unit`, `version`, `timestamp` fields of the package [3](#0-2) ; `validateSignedMessage` explicitly restricts the package to exactly these fields [4](#0-3) . Crucially, **no domain-binding field ties the signature to a specific verifying AA address, alt/network id, or intended-use context**. The verifying function `is_valid_signed_package(package, address)` in the formula evaluator only checks that `package` was signed by `address` — it does not check that the package was created for the particular AA instance evaluating it [5](#0-4) .

Because oscript templates (e.g. `order_book_exchange.oscript`) can be deployed multiple times at different AA addresses with identical logic, and the signed content itself (e.g. `sell_asset`, `buy_asset`, `price`, `sell_amount`) contains no reference to which AA instance it is meant for [2](#0-1) , a user's signed order for AA instance #1 is bit-for-bit valid when submitted as a trigger to any other AA instance #2 running the same template (same asset pair), exactly analogous to the CPortModule.sol issue of a signature crafted for one deployment being replayable on another due to missing domain separator.

### Impact Explanation
An attacker who obtains a signed order intended for one AA deployment (order book contract instance) can replay it against a different, unintended AA instance that shares the same code/logic, causing unauthorized execution of a trade the signer never authorized against that specific pool/instance. This can result in unintended balance transfers, loss of funds, or state corruption for a party who believed their signature was scoped to a single deployment. Medium severity, matching the original finding, since it depends on parallel deployments of AA templates that reuse the same signed-message schema (a realistic and encouraged Obyte pattern for order books/payment channels, per `test/samples/order_book_exchange.oscript` and `test/samples/payment_channels.oscript`).

### Likelihood Explanation
Medium likelihood: exploitation requires that (a) multiple AA instances exist using the same oscript template and same signed-message schema (a common and encouraged pattern for reusable AA templates), and (b) a party's signed order/message can be obtained (it's typically transmitted off-chain to a counterparty or posted publicly to be filled), and then replayed against a sibling AA. This mirrors the original report's requirement of "deployed across chains" — here it's "deployed as multiple AA instances of the same template."

### Recommendation
Add a mandatory domain-binding field to the signed-package schema and to `getSignedPackageHashToSign()`/`validateSignedMessage()` — e.g., require (and hash) the specific AA address the package is intended for, and optionally the network `alt` identifier — so that `is_valid_signed_package` inherently ties a signature to one verifying AA instance and network. Alternatively, document and enforce (at the oscript template level, e.g. in `order_book_exchange.oscript`) that the signed `$order.signed_message` must include the consuming AA's own address as a field and that the AA checks `$order.address_field == trigger.address` (self-address) before accepting the order, closing the cross-instance replay gap.

### Proof of Concept
1. Deploy `order_book_exchange.oscript` twice as AA₁ and AA₂ (identical template, e.g. both trading GB/USD).
2. Alice signs an order via `signMessage`/`is_valid_signed_package`-compatible package: `{signed_message: {sell_asset, buy_asset, sell_amount, price}, last_ball_unit, authors:[{address: Alice, authentifiers:{r: sig}}]}` intending it to be filled at AA₁.
3. The counterparty (or an attacker who intercepts the order data, which is typically shared off-chain/publicly to find a taker) submits the identical, unmodified signed package as `trigger.data.order1` to AA₂ instead.
4. AA₂'s `if` clause runs `is_valid_signed_package(trigger.data.order1, $order1.address)` [6](#0-5)  which succeeds because `validateSignedMessage` only checks the ECDSA signature against `unit_hash_to_sign` (which contains no AA-address binding) and does not verify the package was intended for AA₂ [7](#0-6) . Alice's order executes against AA₂'s liquidity/state instead of (or in addition to) AA₁'s, without her consent for that specific instance.

**Note on uncertainty**: I could not find any existing domain-binding mechanism (e.g., an implicit AA-address check) elsewhere in the codebase that would neutralize this gap beyond what template authors choose to add manually in their own oscript logic; if such a mitigation exists in application-level AA templates not indexed here, that would reduce, but not eliminate at the protocol level, the underlying gap in `is_valid_signed_package`/`validateSignedMessage`.

function getUnitHashToSign(objUnit) {
	var objNakedUnit = getNakedUnit(objUnit);
	for (var i=0; i<objNakedUnit.authors.length; i++)
