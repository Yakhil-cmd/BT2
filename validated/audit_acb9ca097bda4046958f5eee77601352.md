### Title
`StatusHandler#process` creates `Status` records keyed only by SHA with no repository binding, letting a forged status for a shared commit trigger `Pubsubstub.publish("stack.#{victim_stack.id}", ...)` and `commit.schedule_continuous_delivery` for a victim stack the attacker does not own - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by raw SHA across the entire `commits` table (`Commit.where(sha: params.sha)`), completely ignoring the `repository.full_name` present in the same webhook payload, unlike the `Handler` base class's own `stacks`/`repository_name` helpers which exist precisely for that purpose. Any commit record that happens to share a SHA with the attacker's payload - most plausibly via a public fork sharing git history with the victim repository - gets a new `Status` created against the victim's own `stack_id`, firing `Status`'s `after_commit :schedule_continuous_delivery, :broadcast_update, on: :create` for that victim stack.

### Finding Description
The binding the design implicitly assumes is: `webhook.repository.full_name == commit.stack.repository.full_name` (the repository that signed/sent the status event is the same repository that owns the target commit/stack). This binding is never checked.

Trace:
- `app/controllers/shipit/webhooks_controller.rb` `verify_signature` selects the GitHub App/secret to check using `repository_owner` taken from `params.dig('repository','owner','login')`, and dispatches the raw payload to `Shipit::Webhooks.for_event(event)` handlers [1](#0-0) . This only proves the payload was legitimately signed by *some* organization/app installation - it says nothing about whether the `sha` inside the payload belongs to that repository.
- `Shipit::Webhooks::Handlers::Handler` provides a `stacks`/`repository_name` helper specifically meant to scope handler logic to the repository named in the payload [2](#0-1) .
- `StatusHandler#process` does **not** use that scoping. It queries commits globally by SHA and calls `create_status_from_github!` on every match: [3](#0-2) 
- `Commit#create_status_from_github!` creates the `Status` using the *found commit's own* `stack_id`, not anything derived from the attacker's payload: [4](#0-3) 
- `Status` then unconditionally fires, on create: [5](#0-4) 
which calls `commit.schedule_continuous_delivery` [6](#0-5)  and (via the `broadcast_update` delegation to `stack`) `Pubsubstub.publish("stack.#{id}", {id:, updated_at:}.to_json, name: 'update')` for the victim's stack [7](#0-6) .
- `Commit#schedule_continuous_delivery` only gates on `deployable? && stack.continuous_deployment? && stack.deployable?` [8](#0-7)  - none of which checks who submitted the status or which repository sent the webhook.

Exploit flow: attacker forks (or otherwise obtains a repository sharing commit history with) the victim's tracked repo, so a legitimate, real SHA already present in Shipit's `commits` table for the victim's stack also exists in the attacker's own repository. The attacker sets a commit status on that SHA in their own repository (or via any means that produces a real, validly-signed `status` webhook event whose `repository` block names the attacker's own repo). Because `verify_signature` only validates that the payload was signed for `repository_owner` (the attacker's own org/repo), the request passes signature verification while carrying `sha` = the victim's commit and `state`/`context`/`description` fully attacker-controlled. `StatusHandler` then finds the victim's `Commit` by SHA alone and creates a `Status` bound to the victim's `stack_id`, which broadcasts the update event for `stack.#{victim_stack.id}` and can schedule `ContinuousDeliveryJob` for the victim's stack if the forged state is `success` and the victim stack has continuous deployment enabled.

### Impact Explanation
The attacker causes a write (`Shipit::Status` row) and a Pub/Sub broadcast (`stack.#{victim_stack.id}` "update" event) for a stack/repository they have no relationship to and no permission on, purely by controlling `sha`, `state`, `context`, `description` inside a webhook payload nominally originating from their own repository. Beyond the requested side-channel signal, this same missing scoping can influence `Commit#deployable?`/`blocked?` (used by `Stack#deployable?`/continuous delivery evaluation) for the victim's commit, meaning a forged "success" status for a required CI context can help satisfy deploy-gating logic and schedule `ContinuousDeliveryJob` against the victim stack. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy," because the write and the broadcast are for a stack authenticated only by the attacker's own, unrelated repository's signature.

### Likelihood Explanation
Preconditions: (1) the attacker's own repository must be onboarded to the same GitHub App/webhook-secret domain that Shipit trusts for `repository_owner` (i.e., they can produce a signature that `Shipit.github(organization: repository_owner)` accepts for their own org - a normal, low-privilege state for any GitHub user who can install or already has access to a webhook-emitting repository of that App), and (2) a SHA must be shared between the attacker's repository and a commit already tracked in Shipit's `commits` table for the victim's stack - trivially achievable via a public fork of the victim repository, since forks share full git history and thus many identical, content-addressed commit SHAs. No Shipit session, API token, or GitHub secret for the victim's org is required. The attack is repeatable against any commit whose SHA is common to a public fork, which is essentially every historical commit of the victim repository predating the fork point.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository named in the webhook payload (use the existing `stacks`/`repository_name` helper from `Handler`, e.g., `stacks.joins(:commits).where(commits: { sha: params.sha })` or equivalently filter `commit.stack` against `repository_name`) before calling `create_status_from_github!`, so a status event can only mutate commits/stacks that belong to the repository that actually sent the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "a status webhook 'from' an unrelated repository broadcasts an update for a victim stack sharing the same commit sha" do
          victim_stack = shipit_stacks(:shipit)
          victim_commit = victim_stack.commits.create!(
            sha: 'deadbeefcafefeed0000000000000000000000',
            message: 'shared ancestor commit',
            authored_at: Time.now,
            committed_at: Time.now
          )

          # Payload purportedly signed by/for an attacker-owned, unrelated repository,
          # but naming the victim's commit sha.
          forged_payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'context' => 'ci/attacker',
            'branches' => [],
            'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
          }

          Pubsubstub.expects(:publish).with("stack.#{victim_stack.id}", anything, name: 'update')

          Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

          assert victim_commit.statuses.exists?(state: 'success', context: 'ci/attacker'),
                 "expected a Status to be created against the victim's stack from an unrelated repository's payload"
        end
      end
    end
  end
end
```
Binding checked: BEFORE fix, `webhook.repository.full_name ('attacker/unrelated-repo') != commit.stack.repository.full_name (victim's repo)` yet the broadcast for `stack.#{victim_stack.id}` still fires and a `Status` row is written against `victim_commit`; AFTER the recommended fix, the lookup scoped by `repository_name` would find no matching commit for `attacker/unrelated-repo`, no `Status` would be created, and `Pubsubstub.publish` would not be called for the victim stack.
