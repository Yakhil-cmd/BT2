I found a directly analogous bug class: `threshold_size` is a network-wide `system_vote` parameter that any unprivileged token holder can vote to change, and unlike its sibling parameters (`tps_interval`, `base_tps_fee`, `tps_fee_multiplier`), it has **no upper bound**, only a lower bound. This value feeds directly into the oversize-fee formula used by every unit-validity check, which is exactly the "unbounded governance parameter → protocol-level DoS" pattern from the report (`setDuration`/`setTimeBuffer` lacking bounds → endless auction).

### Title
Missing upper-bound validation on `threshold_size` system vote allows oversize-fee formula to be neutralized or made unusable, risking network-wide inability to confirm units - (File: validation.js)

### Summary
`system_vote` messages let any address with a balance vote to change network-wide parameters (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`). Three of these numeric subjects (`base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) are validated with both a lower and an upper bound once `pemCurvesFixMci` is active: [1](#0-0) 
`threshold_size`, however, is validated only for a lower bound (`>= 1000`), with no upper bound whatsoever: [2](#0-1) 

`threshold_size` is not a cosmetic parameter — it is the divisor in the exponential `getOversizeFee()` formula that every unit's `oversize_fee` field is checked against during validation: [3](#0-2) [4](#0-3) 

Votes are weighted by voter's stable balance and tallied by `countVotes()`, taking the value with majority-weighted support, with no sanity clamp on the resulting median: [5](#0-4) 

### Finding Description
Just like `setDuration()`/`setTimeBuffer()` in the referenced report accept any owner-supplied numeric value with no upper bound (letting the auction duration/time-buffer become effectively infinite), `threshold_size` accepts any `payload.value >= 1000` with no ceiling. Because the "owner" here is actually the collective of arbitrary unprivileged unit posters (any balance holder can cast a `system_vote`), a large enough coordinated (or accidental, since threshold_size directly composes with `oversize_fee` calculated for every unit) or economically-favorable vote can push `threshold_size` to an astronomically large value (up to `Number.MAX_SAFE_INTEGER`/`1e15`-scale — nothing prevents e.g. `9e15`). At that scale, `size <= threshold_size` will always hold for virtually all conceivable unit sizes, so `getOversizeFee()` will return `0` for all units, permanently and silently disabling the oversize-fee anti-spam mechanism network-wide, with no protocol-level recovery path other than another vote (which is asynchronous and depends on the very same unbounded mechanism working correctly).

Conversely, an adversarial/careless vote could also push `threshold_size` toward its minimum-permitted `1000`, which combined with the exponential term `exp(size/threshold_size - 1)` in `getOversizeFee()` could produce extremely large required `oversize_fee` values for typical-sized units, making it economically impossible for ordinary unprivileged unit posters to produce valid units that satisfy `objUnit.oversize_fee !== oversize_fee` — this is the direct structural analog of the "endless auction": normal usage becomes permanently stuck because the parameter, once set to an extreme, has no bound and no assisted recovery.

### Impact Explanation
This maps to the "network unable to confirm new units" acceptance criterion: since `oversize_fee` is checked in `validateParents()` for every version-4.0+ serial unit, and the required fee is a direct function of the unbounded `threshold_size`, an extreme value can (a) neutralize an anti-spam/fee mechanism (mild, allows spam/oversized units cheaply) or (b) make computing/paying the correct `oversize_fee` practically unattainable for ordinary senders composing units of typical size, causing systematic unit-validity failures across the network until a new vote count changes the value. Because this parameter is voted on-chain by ordinary token holders (not gated by any operator/hub privilege) and is missing exactly the same class of value validation the report criticizes, it is a Medium-severity structural analog of the report's core defect.

### Likelihood Explanation
Exploitability requires accumulating majority-weighted vote balance for the `threshold_size` subject over the vote counting window in `countVotes()`, which is a real but non-trivial economic/coordination bar (same category of assumption as needing an "owner mistake or malicious owner" in the original report, except here the actor pool is the wider set of unprivileged balance holders rather than a single contract admin). Given the parameter is missing any bound while its sibling parameters explicitly received bounds during the `pemCurvesFixMci` fix, this looks like an overlooked instance of the same value-validation defect rather than an intentional design choice.

### Recommendation
Add an explicit upper bound (and reconsider the lower bound in relation to `MAX_UNIT_LENGTH`/typical unit sizes) for `threshold_size` in the `system_vote` validation branch, mirroring the bounds already added for `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier`: [2](#0-1) 

### Proof of Concept
1. A coalition of addresses controlling majority-weighted stable balance casts `system_vote` messages with `{subject: "threshold_size", value: <extreme value, e.g. 1e13>}` (only bound-checked as `isPositiveInteger` and `>=1000`): [2](#0-1) 
2. A `system_vote_count` message triggers `countVotes()`, which computes the balance-weighted median and stores it into `system_vars` / `storage.systemVars.threshold_size` with no bound check: [5](#0-4) 
3. From the next MCI onward, `getOversizeFee()` uses this new `threshold_size` for every unit; with an extreme large value, `size <= threshold_size` holds for all realistic units, so `oversize_fee` becomes `0` for everyone, defeating the anti-spam mechanism: [6](#0-5) 
4. Alternatively, an extreme small value near the allowed floor combined with large `size` drives the exponential term up sharply, making the `oversize_fee` requirement in `validateParents()` unpredictable/expensive for ordinary posters, causing valid-looking units to be rejected as `oversize_fee mismatch` until governance intervenes: [4](#0-3)

function getOversizeFee(objUnitOrSize, mci, bAA) {
	let size;
	if (typeof objUnitOrSize === "number")
		size = objUnitOrSize; // must be already without temp data fee
	else if (typeof objUnitOrSize === "object") {
		if (!objUnitOrSize.headers_commission || !objUnitOrSize.payload_commission)
			throw Error("no headers or payload commission in unit");
		// AA-generated units pay the oversize fee based on the unit size excluding its payment messages to avoid swelling the fee while spending dust outputs
		const payload_commission = (bAA && mci >= constants.pemCurvesFixMci)
			? objectLength.getTotalPayloadSize({ ...objUnitOrSize, messages: objUnitOrSize.messages.filter(message => message.app !== 'payment') })
			: objUnitOrSize.payload_commission;
		size = objUnitOrSize.headers_commission + payload_commission - objectLength.getPaidTempDataFee(objUnitOrSize);
	}
	else
		throw Error("unrecognized 1st arg in getOversizeFee");
	const threshold_size = getSystemVar('threshold_size', mci);
	if (size <= threshold_size)
		return 0;
	return Math.ceil(size * (exp(size / threshold_size - 1) - 1));
}
