### Title
Data feed keys built with unescaped `\n` delimiters allow feed_name/value boundary injection - (File: `data_feeds.js`, `string_utils.js`, `main_chain.js`)

### Summary
Like the CPython bug where a comment consisting entirely of "unfoldable" characters caused the folding algorithm to silently drop the enclosing parenthesis — corrupting the structural boundary of a header field and enabling injection — ocore builds its data-feed lookup keys by naively concatenating attacker/oracle-controlled strings (`feed_name`, string `value`) with a `\n` character used purely as a structural field separator, without ever checking that the untrusted content itself does not contain that separator.

### Finding Description
Data feed keys are constructed as `'df\n'+address+'\n'+feed_name+'\n'+type+'\n'+value+'\n'+strMci` in `data_feeds.js` (`dataFeedByAddressExists`, `readDataFeedByAddress`) [1](#0-0) [2](#0-1) , and identically when the feed is written to the KV store on stabilization in `main_chain.js`'s `addDataFeeds` [3](#0-2) .

Both `feed_name` and the string `value` originate directly from the `data_feed` message payload posted by any address (including AA-triggering users or oracle-role addresses chosen by AA authors), i.e. `payload[feed_name] = value` where both are attacker-supplied JSON strings. Nothing in this construction path escapes or rejects a `\n` byte inside `feed_name` or `value` before it is spliced into the `\n`-delimited key.

On the read side, `string_utils.getMciFromDataFeedKey` and `getValueFromDataFeedKey` recover structured fields purely by `key.split('\n')` and positional indexing, assuming exactly 6 parts (`df:address:feed_name:type:value:strReversedMci`) [4](#0-3) . If `feed_name` or `value` itself contains embedded `\n` characters, the split produces a different number/positioning of segments than intended, exactly analogous to the CPython bug where an “unfoldable” payload broke the invariant the parser relied on (a fixed structural delimiter that was assumed never to appear inside user content).

This is the same bug class as the report: a serializer/deserializer relies on a delimiter character to demarcate fields, but never validates that user-controlled content is free of that delimiter, so crafted input can shift or duplicate field boundaries and be reinterpreted differently than the poster's stated data.

### Impact Explanation
AA formulas such as `data_feed[[oracles=..., feed_name=..., feed_value=...]]` and `in_data_feed[[...]]` in `evaluation.js` rely on exact-match lookups of `feed_name` against stored keys via `dataFeeds.dataFeedExists` / `dataFeedByAddressExists` [5](#0-4) . If an oracle-controlled or unprivileged data-feed poster can smuggle a `\n` into `feed_name` (e.g., `"price\nEXTRA"`), the on-disk range-scan keys built with `key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+...` no longer correspond 1:1 with the logical feed name that an AA's oscript expects, and the reversed-mci ordering/parsing logic in `getMciFromDataFeedKey` can misread the trailing mci hex, or an unrelated feed can end up falling inside range queries meant for a different `feed_name`/`value` pair. Any resulting mismatch between what the AA condition intends to check and what the KV-store range query actually returns can cause an AA to release funds against a data feed condition that was never legitimately satisfied — leading to fund loss/drain from the AA, or a stability/agreement discrepancy between nodes that parse feed keys differently.

### Likelihood Explanation
`feed_name` is fully attacker-controlled JSON string content in any `data_feed` unit message; no length/charset validation preventing an embedded `\n` was found on this path in `data_feeds.js` / `main_chain.js` / `string_utils.js`. Constructing such a payload requires only posting an ordinary unit with a `data_feed` message, which is reachable by any unprivileged unit poster acting as (or impersonated as) an oracle referenced by an AA's `data_feed[[oracles=...]]` condition.

### Recommendation
Reject (at validation time, before the message is ever accepted into a unit) any `feed_name` or string `value` in a `data_feed` payload that contains the `\n` (or other reserved key-separator) byte, mirroring the existing `STRING_JOIN_CHAR` (`\x00`) rejection already enforced in `getSourceString` [6](#0-5) . Alternatively, switch the data-feed key encoding to a length-prefixed or escaped format so that delimiter characters inside user content can never be confused with structural boundaries.

### Proof of Concept
1. Post a unit with message `app: "data_feed"`, `payload: { "price\nEXTRA": 100 }` from an address referenced as an oracle by a target AA's `data_feed[[oracles=<address>, feed_name="price", ...]]` condition.
2. On stabilization, `addDataFeeds` writes key `'df\n'+address+'\n'+"price\nEXTRA"+'\ns\n'+ value +'\n'+strMci` into the KV store [3](#0-2) .
3. Because `feed_name` itself now contains an internal `\n`, subsequent range scans in `dataFeedByAddressExists`/`readDataFeedByAddress` that build `key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value` for the *intended* `feed_name="price"` can match/miss keys inconsistently with what a naive `key.split('\n')` parser in `getMciFromDataFeedKey`/`getValueFromDataFeedKey` expects (which assumes exactly 6 `\n`-delimited segments) [4](#0-3) , demonstrating the boundary-confusion primitive.

function getMciFromDataFeedKey(key){
	var arrParts = key.split('\n');
	var strReversedMci = arrParts[arrParts.length-1];
	var reversed_mci = parseInt(strReversedMci, 16);
	var mci = 0xFFFFFFFF - reversed_mci;
	return mci;
}

// df:address:feed_name:type:value:strReversedMci
function getValueFromDataFeedKey(key){
	var m = key.split('\n');
	if (m.length !== 6)
		throw Error("wrong number of elements in data feed "+key);
	var type = m[3];
	var value = m[4];
	return (type === 's') ? value : decodeLexicographicToDouble(value);
}
