### Title
`StatusHandler#process` writes Status records via global `Commit.where(sha:)` with no repository/stack scoping, allowing any onboarded repository to mutate any other tracked repository's commit status - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::Handler` defines `#stacks` and `#repository_name` to scope handling to the webhook's own repository, and `PushHandler`, `CheckSuiteHandler`, and all `PullRequest::*Handler` subclasses use `stacks`/`repository` to constrain their effects to the originating repo's stacks. `StatusHandler#process` never calls either method and instead runs `Commit.where(sha: params.sha)` against the entire `commits` table, so a validly signed "status" webhook from repository/org A can attach a `Status` to a commit that actually belongs to repository/stack B.

### Finding Description
The broken binding: for every other handler, `handler.process` operates within `commit ∈ stacks(repository_name_from_payload)`. For `StatusHandler`, `handler.process` operates over `commit ∈ Commit.where(sha: params.sha)` with no relation to `repository_name` or `stacks` at all.

`Handler` base class: [1](#0-0) 

Contrast with `PushHandler#process` (scoped via `stacks`): [2](#0-1) 

and `CheckSuiteHandler#process` (also scoped via `stacks`): [3](#0-2) 

and `PullRequest::ReopenedHandler#process` (scoped via its own `repository`/`stack`): [4](#0-3) 

`StatusHandler` requires only `sha`/`state`/etc, never `repository`, and `#process` never references `stacks`, `repository_name`, or `repository`: [5](#0-4) 

`Commit#create_status_from_github!` unconditionally creates the `Status` scoped to `commit.stack_id` (the victim's own stack), regardless of who sent the webhook: [6](#0-5) 

Root cause: adding `requires :repository` to `StatusHandler`'s `ExplicitParameters` spec (as the question posits) would only make `params.repository` available - it would not change behavior because `#process` never reads `params.repository` or calls `stacks`. The gap is architectural, not a schema/validation gap.

Signature verification does not close this gap either. `WebhooksController#verify_signature` resolves the GitHub App config purely by the **organization** named in the attacker's own payload (`repository_owner`), and validates the HMAC using that organization's real `webhook_secret`: [7](#0-6) [8](#0-7) 

This proves only that the webhook genuinely originated from GitHub for *some* repository the attacker controls - it says nothing about which `sha` the payload claims, and GitHub's "create commit status" API accepts an arbitrary 40-hex-char `sha` string for any repository the caller can push to, without requiring that sha to be a real commit in that repository. An attacker with push/status access to their own tracked repository can therefore set a status against the exact `sha` of a commit that exists in a completely unrelated tracked stack (their own org, or another onboarded org/tenant on a multi-tenant Shipit install), and GitHub will deliver a correctly-signed `status` webhook naming their own repository but the victim's `sha`. `StatusHandler` then matches that `sha` globally and writes the `Status`.

### Impact Explanation
A `Status` record is created against a victim's `Commit`/`Stack` that the attacker does not own and never authenticated for. This directly triggers `Commit#create_status_from_github!` → `add_status` side effects, including `enable_ci_on_stack`, `schedule_continuous_delivery`, and `ProcessMergeRequestsJob` enqueue on state transitions to `pending`/`success`, potentially influencing continuous-deployment/merge automation for a repository the attacker has no relationship to: [9](#0-8) 
This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any commit sha the attacker knows (trivial for public repositories) and is not bounded to a single tenant/org since the organization used for signature verification is chosen entirely from the attacker's own payload.

### Likelihood Explanation
Preconditions: the attacker needs write/push (or status-creation) access to at least one repository that is onboarded into the same Shipit instance (their own repo, or a fork added to Shipit), so that GitHub will deliver a genuinely-signed `status` webhook. No Shipit secrets, sessions, or tokens are required - only ordinary GitHub repository permissions the attacker already has on their own repository. Knowledge of a target `sha` in another tracked stack is the only other requirement, which is public for public repositories. This is low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, mirroring `PushHandler`/`CheckSuiteHandler`: require `repository.full_name` in the params spec and restrict the commit lookup to `stacks.commits.where(sha: params.sha)` (or equivalent join through `Repository.from_github_repo_name(repository_name)`), rather than a global `Commit.where(sha:)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require "test_helper"

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "process is not scoped to the payload's repository" do
          method = StatusHandler.instance_method(:process)
          file, _line = method.source_location
          body = File.read(file)
          # Demonstrates the asymmetry: StatusHandler never references stacks/repository
          refute_match(/\bstacks\b/, body)
          refute_match(/\brepository\b/, body)

          # Contrast: ReopenedHandler#process path calls #stack -> #repository
          reopened_file, _ = Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler
            .instance_method(:process).source_location
          reopened_body = File.read(reopened_file)
          assert_match(/\bstack\b/, reopened_body)
        end

        test "status webhook for repo A writes a Status onto repo B's commit" do
          victim_stack = shipit_stacks(:shipit)          # repo B, victim
          victim_commit = shipit_commits(:first)
          assert_equal victim_stack.id, victim_commit.stack_id

          # Payload claims to originate from an unrelated repository ("attacker/repo")
          payload = {
            "sha" => victim_commit.sha,
            "state" => "success",
            "repository" => { "full_name" => "attacker/repo" }
          }

          assert_difference -> { victim_commit.reload.statuses.count }, 1 do
            StatusHandler.new(payload).process
          end
        end
      end
    end
  end
end
```

```ruby
module Shipit
  module Webhooks

        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
