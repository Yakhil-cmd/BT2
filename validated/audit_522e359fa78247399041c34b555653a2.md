### Title
Webhook signature is verified against the organization owning `repository.owner.login`, but handlers act on the attacker-controlled `repository.full_name` / unscoped `sha` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `webhook_secret` used to validate the HMAC signature based on `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) in the *unverified* JSON body itself. Once the signature check passes, the raw payload is dispatched to handlers that key their side effects off a different field of that same attacker-controlled body — `repository.full_name` in the base `Handler` class, or, worse, an entirely unscoped `sha` in `StatusHandler`. This breaks the binding "organization that authenticated" == "repository that is written."

### Finding Description
`verify_signature` computes which GitHub App/organization config (and therefore which `webhook_secret`) to check the signature against using data taken directly from the request body: [1](#0-0) [2](#0-1) 

The signature itself is only an HMAC over the raw JSON body using whatever secret was selected — it proves the sender knew *some* organization's `webhook_secret`, not that the `repository` fields describe a repo belonging to that organization: [3](#0-2) 

After verification, `create` dispatches the same raw, attacker-controlled JSON to handlers: [4](#0-3) 

The base `Handler` resolves the target repository/stack from `payload.dig('repository', 'full_name')` — a field independent of the `owner.login` used for signature selection: [5](#0-4) 

`PushHandler` uses this to call `stack.sync_github` on whatever stacks match that (attacker-chosen) `full_name`: [6](#0-5) 

`StatusHandler` is worse: it does not scope by repository/organization at all, only by `sha`: [7](#0-6) 

Since commit `sha`s are effectively global (any 40-hex string, or any commit that happens to exist across any stack tracked by Shipit), an attacker who legitimately controls one GitHub organization's Shipit webhook configuration (and thus knows/can trigger that organization's `webhook_secret` — an "unprivileged" actor with respect to Shipit itself, not a GitHub App admin of every org) can craft a `status` webhook whose `repository.owner.login` matches their own org (so `verify_signature` picks their known secret and passes) while the `sha` field references a commit belonging to a completely unrelated stack/repository. `create_status_from_github!` will then write a forged CI status onto that unrelated commit.

This directly feeds into deploy/merge gating logic that trusts `Commit` statuses: `required?`/`blocking?` checks in `Status::Common`, `Status::Group`, and `MergeRequest::StatusChecker` treat any status matching a required context as satisfying that requirement: [8](#0-7) [9](#0-8) 

and `Commit#deployable?`/merge-queue logic (`app/models/shipit/merge_request.rb` `StatusChecker`) rely on exactly these required/missing status computations to allow a deploy or a merge to proceed, as confirmed by tests asserting `deployable?` flips based on required-status presence: [10](#0-9) 

### Impact Explanation
An attacker who administers one Shipit-tracked GitHub organization (and thus possesses that organization's webhook secret through legitimate means, not a Shipit session or GitHub App private key) can forge a `status` webhook that is authenticated against their own org's secret but whose `sha` targets a commit in a completely unrelated stack/repository they do not control. This can satisfy a `required`/`blocking` CI status for that foreign commit, unblocking an otherwise-gated deploy or merge-queue entry on a stack belonging to a different team/organization — a cross-repository write that enables an unauthorized deploy or merge. This matches the report's "Critical" impact bucket for unauthorized deploy/merge via a broken trust binding.

### Likelihood Explanation
Exploitation requires only crafting a raw HTTP POST with a valid `X-Hub-Signature` computed from a secret the attacker legitimately possesses for their own organization, and a `sha` value guessable/discoverable from Shipit's public-ish commit/stack pages or GitHub. No GitHub App private key, Shipit session, or `ApiClient` token is required — only knowledge of one organization's `webhook_secret`, which is a much lower bar than compromising the whole deployment. This is a realistic, low-effort path for multi-tenant Shipit deployments (multiple organizations configured under `Shipit.github_apps`).

### Recommendation
- Verify that the `repository.owner.login` (or `organization.login`) used to select the webhook secret in `verify_signature` is the *same* organization that the acting handler ultimately uses to resolve the target `Repository`/`Stack`, rejecting the webhook if they diverge.
- In `StatusHandler`, scope the `Commit.where(sha: params.sha)` lookup to commits whose stack's repository matches the authenticated `repository.full_name`/owner rather than matching by `sha` alone across the entire installation.
- More generally, ensure every handler in `app/models/shipit/webhooks/handlers/**` binds mutations to the organization that was cryptographically authenticated, not merely to attacker-supplied payload fields.

### Proof of Concept
1. Attacker legitimately administers GitHub organization `attacker-org`, which is registered in Shipit's `Shipit.github_apps` config with webhook secret `S`.
2. Attacker crafts a JSON body for a `status` event:
   ```json
   {
     "sha": "<sha-of-a-commit-belonging-to-victim-org/victim-repo-stack>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S, raw_body)` using their own known secret `S`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` → `attacker-org`, fetches `Shipit.github(organization: 'attacker-org')`, and successfully verifies the signature against `S`. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, writing a forged "success" status onto the victim's commit regardless of which organization it belongs to. [7](#0-6) 
7. If `ci/required-check` is a `required` or `blocking` status for the victim stack, the victim's commit now appears `deployable?`/mergeable, allowing an unauthorized deploy or merge-queue advance.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
