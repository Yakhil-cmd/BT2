## Title
Webhook signature verification is keyed on an unauthenticated org field while event handlers act on a different, unverified repository field, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which HMAC secret) to check the incoming webhook against based on `repository_owner`, a value read straight out of the untrusted JSON body. The event handlers that subsequently act on the webhook, however, resolve the target repository/stack from a completely different, equally untrusted field (`repository.full_name`). Nothing ties the two together, so the "organization that authenticated" the request is not required to equal the "repository that is written." In any multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` (an explicitly documented, optional setting), an attacker can forge a webhook payload that claims to originate from the unsecured organization while pointing `repository.full_name` at a repository belonging to a different, secured organization, bypassing signature verification entirely for that protected repository.

### Finding Description
`verify_signature` derives the app/secret to check against purely from the payload: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially passes whenever the resolved app has no configured secret: [3](#0-2) 

`Shipit.github(organization:)` looks the config up per-organization when the installation is multi-org (per `github_app_config`), so different organizations can have independent (and independently absent) `webhook_secret` values, as shown in the shipped sample config: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the raw, attacker-controlled JSON to handlers unmodified: [6](#0-5) 

Every handler resolves its target repository from `repository.full_name`, a field never consulted during signature verification: [7](#0-6) 

`PushHandler` (and similarly `StatusHandler`, `CheckSuiteHandler`, pull-request handlers) then act directly on the stacks matched from that field: [8](#0-7) 

The equality that must hold for the trust boundary to be sound is: *organization whose secret authenticated the request == owner of the repository the handler subsequently mutates*. The code never enforces this; it only enforces that the app for `repository.owner.login`/`organization.login` produced a valid (or absent) signature, and the handler's repository resolution is entirely independent of that value.

### Impact Explanation
Where a multi-org deployment has one organization configured without a `webhook_secret` (explicitly an "optional" setting per `docs/setup.md`), any unauthenticated party can:
- Forge a `push` event with `repository.full_name` pointing at a protected organization's repository to trigger `stack.sync_github`, feeding an attacker-chosen `after` SHA into the deploy pipeline for that stack.
- Forge `status` or `check_suite` events to inject fabricated CI state for commits in the protected repository, which downstream can gate/allow deploys.
- Forge `membership` events (`MembershipHandler`) to add or remove arbitrary GitHub users from `Shipit::Team`s, affecting `User#authorized?` and thus authentication/authorization within the Shipit UI.

This crosses a credential/authentication boundary the signature check is meant to enforce, and can lead to an unauthorized deploy/rollback of a protected stack, satisfying the Critical impact bar in this engine's threat model.

### Likelihood Explanation
Requires only an engine deployment that configures more than one GitHub organization (a documented, supported configuration) where at least one organization omits `webhook_secret` — itself explicitly documented as optional. No attacker-held credentials, tokens, or repository access are needed; the payload fields consumed (`repository.owner.login`, `organization.login`, `repository.full_name`) are all attacker-controlled JSON body content.

### Recommendation
Bind the resolved authenticating organization to the repository being acted upon: after `verify_webhook_signature` succeeds, re-derive `repository_name`/`repository.owner` from the payload and assert it matches (case-insensitively) the organization whose secret validated the signature, rejecting (422) on mismatch. Additionally, do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is unset if any other configured organization does have a secret configured, or require all organizations in a multi-org config to define a webhook secret.

### Proof of Concept
Assume a Shipit deployment configured with two orgs: `attacker-org` (no `webhook_secret`) and `victim-org` (has `webhook_secret` set, hosting a stack for `victim-org/critical-repo`).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef   (garbage, irrelevant)
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/critical-repo",
    "owner": { "login": "attacker-org" }
  }
}
```

1. `repository_owner` resolves to `"attacker-org"` per `WebhooksController#repository_owner`.
2. `Shipit.github(organization: "attacker-org")` loads a `GitHubApp` with `webhook_secret` blank, so `verify_webhook_signature` returns `true` unconditionally regardless of `X-Hub-Signature`.
3. `create` parses the same body and dispatches to `PushHandler`, whose `repository_name` reads `"victim-org/critical-repo"` from `repository.full_name`, matching stacks for the victim organization's repository and invoking `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — despite `victim-org` having webhook signing enabled.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
