### Title
Bond stake additions skip `settle-rewards`/`settle-staker-rewards`, letting newly added shares retroactively earn already-accrued bond rewards - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar` implements a Synthetix-style rewards accumulator (`rewards-per-token-for-cycle`) per bond/cycle, where each signer's earned amount is `shares * (rpt-current - rpt-paid)`. The invariant documented at `settle-rewards`/`settle-staker-rewards` is that these settlement functions **must** be called before any change to `signer-shares-staked-for-cycle` / `staker-shares-staked-for-cycle`, because the settlement freezes the "paid" snapshot against the *old* share amount. The bond-staking "add" path, `add-staker-to-bond-for-cycle`, violates this invariant: it mutates `total-shares-staked-for-cycle` and `signer-shares-staked-for-cycle` directly without first calling `settle-rewards`, unlike the symmetric bond "remove" path `unstake-sats-from-bond-cycle`, which explicitly settles both signer- and staker-level rewards first.

The comment on `settle-rewards` explicitly states the required call ordering: [2](#0-1) 

The bond "remove"/unstake path honors this rule — it settles both the signer and staker accumulators for the affected cycle *before* decrementing `total-shares-staked-for-cycle`/`signer-shares-staked-for-cycle`/`staker-shares-staked-for-cycle`: [3](#0-2) 

But the bond "add" path, `add-staker-to-bond-for-cycle` (invoked by `add-staker-to-bond-cycles`, reached from bond-registration entry points such as `register-for-bond`), directly increases `total-shares-staked-for-cycle` and `signer-shares-staked-for-cycle` with **no** preceding call to `settle-rewards`: [4](#0-3) 

Compare this to the STX-only staking add path, `add-staker-to-signer-for-cycle`, which correctly calls `settle-rewards`/`settle-staker-rewards` *before* mutating `signer-shares-staked-for-cycle`/`total-shares-staked-for-cycle`: [5](#0-4) 

Because `add-staker-to-bond-for-cycle` skips the settlement step, a signer's `signer-rewards-per-token-settled-for-cycle` snapshot is not advanced when new stake is added mid-cycle. Since bond rewards are computed and distributed multiple times per cycle (via `calculate-rewards`/`calculate-bond-rewards`, callable once per half-cycle), the accumulator `rewards-per-token-for-cycle` can already have accrued value from a period when a signer held fewer bond shares. If additional shares are added to that signer's bond position afterward (still within the same reward cycle, before the signer's next settlement, e.g., an unstake or claim), the eventual `settle-rewards`/`settle-staker-rewards` call multiplies the **new, larger** share count against the **entire** accumulated `rpt` delta since the last real settlement — including the portion that accrued while only the smaller amount was staked.

### Impact Explanation
This breaks the core equality the accumulator pattern is meant to preserve: `sum(earned per signer) == total rewards actually distributed for that bond/cycle`. A signer who tops up bond stake mid-cycle is credited rewards for a period before the added stake existed, over-crediting sBTC rewards not backed by any corresponding contribution. Since the total reward pool for the cycle is fixed (computed from `gross-accrued-rewards`/`target-yield` in `calculate-bond-rewards`), this over-crediting to one signer either drains the shared reserve/pool or comes at the expense of other signers'/stakers' legitimate rewards — i.e., "sBTC rewards paid that were not earned or counted twice," which the rules classify as Critical/High impact (double-counting a reward commitment, theft from the shared reward pool).

### Likelihood Explanation
This is reachable by any unprivileged staker: mid-cycle bond stake increases occur through normal, user-authorized flows (e.g., `register-for-bond` used to add to an existing bond position, or similar "increase" entry points reaching `add-staker-to-bond-cycles`). No admin, miner, or other user's key is required — only calling the bond top-up path after at least one `calculate-rewards` invocation has already updated the bond's `rewards-per-token-for-cycle` for that cycle. The main uncertainty (not fully confirmed due to tool-call limits) is whether the contract's guards (e.g., `bond-start-height`/"already started" checks around `register-for-bond`) prevent adding to a bond position **after** rewards have already been calculated for it in the current half-cycle; if such a guard exists and unconditionally blocks any share increase after the first `calculate-rewards` call for that bond in a cycle, the exploitable window would be narrower (or non-existent). This could not be verified with certainty in the available context and would need direct confirmation against `register-for-bond`'s preconditions.

### Recommendation
Call `settle-rewards` (signer-level) and, when the staker already has pre-existing shares, `settle-staker-rewards` (staker-level) for the affected `(reward-cycle, bond-index)` at the top of `add-staker-to-bond-for-cycle`, *before* reading/updating `current-total-staked`/`current-signer-staked` and writing the new share totals — mirroring the pattern already used in `unstake-sats-from-bond-cycle` and `add-staker-to-signer-for-cycle`.

### Proof of Concept
1. Signer `S` registers a bond position in bond `B` for cycle `C` with 100 sats via `register-for-bond` → `add-staker-to-bond-for-cycle` sets `signer-shares-staked-for-cycle(S,C,B)=100`, `total-shares-staked-for-cycle(C,B)=100`, and `signer-rewards-per-token-settled-for-cycle(S,C,B)=0`.
2. sBTC rewards are deposited and `calculate-rewards` is called at the first half-cycle boundary. `calculate-bond-rewards` computes `accrued-rewards-per-sat = earned1 / 100` and sets `rewards-per-token-for-cycle(C,B) = X` (where `X = earned1/100`).
3. Before `S` claims or unstakes, `S` (or another allowed staker under the same signer) adds another 100 sats to the same bond position in the same cycle via the bond-add path → `add-staker-to-bond-for-cycle` bumps `signer-shares-staked-for-cycle(S,C,B)` to 200 and `total-shares-staked-for-cycle(C,B)` to 200, **without** calling `settle-rewards`, so `signer-rewards-per-token-settled-for-cycle(S,C,B)` remains `0`.
4. More rewards are deposited; `calculate-rewards` runs again for the second half-cycle using `total-sats=200`, computing `accrued-rewards-per-sat = earned2/200 = Y`, bringing `rewards-per-token-for-cycle(C,B)` to `X+Y`.
5. `S` calls `claim-rewards`/triggers `settle-rewards(S,C,B)`: `earned = shares(200) * (rpt-current(X+Y) - rpt-paid(0)) = 200*(X+Y)`.
6. The correct entitlement, however, is `100*X + 200*Y` (100 sats earned only from period 1, both amounts earn period 2 proportionally). The bug credits an extra `100*X` in sBTC rewards that were never actually apportioned to `S`'s pre-existing 100 sats for period 1 — a straightforward reward double-count/over-mint at the expense of the shared reward pool/reserve.

(define-private (settle-rewards
        (signer principal)
        (reward-cycle uint)
        (bond-index (optional uint))
    )
    (let (
            (shares (get-signer-shares-staked-for-cycle signer reward-cycle bond-index))
            (rewards-per-token (get-rewards-per-token-for-cycle reward-cycle bond-index))
            (earned (compute-earned-rewards
                shares
                rewards-per-token
                (get-signer-rewards-per-token-settled-for-cycle signer reward-cycle bond-index)
                (get-signer-unclaimed-rewards-for-cycle signer reward-cycle bond-index)
            ))
        )
        (map-set signer-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            earned
        )
        (map-set signer-rewards-per-token-settled-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            rewards-per-token
        )
        (if (> shares u0)
            (map-set signer-rewards-per-token-for-cycle {
                signer: signer,
                reward-cycle: reward-cycle,
                bond-index: bond-index,
            }
                rewards-per-token
            )
            true
        )
        {
            earned: earned,
            rewards-per-token: rewards-per-token,
        }
    )
)
