### Title
Cross-tenant `Status` write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no filter on the repository/stack that authenticated the webhook, then writes a `Status` onto every matching `Commit` regardless of which `Repository` owns it. Because `sha` is attacker-controlled and shared blobs/commits (e.g. an identical empty-tree commit, or a shared history) can exist across unrelated repositories/stacks, an attacker who owns any GitHub org/repo (and thus its `webhook_secret`) can inject a signed `status` event that mutates a `Commit` belonging to a victim `Stack` in a completely different `Repository`.

### Finding Description
The binding the endpoint is supposed to preserve is: `repository_owner` (the org whose `webhook_secret` verified the request, per `WebhooksController#verify_signature`, `app/controllers/shipit/webhooks_controller.rb:24-49,59-62`) must equal the owning organization of every `Commit` mutated as a result of processing that payload.

`WebhooksController#verify_signature` only checks that the signature matches the `webhook_secret` configured for `repository_owner = params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . It never checks that `params.repository.full_name` corresponds to any `Repository`/`Stack` actually touched downstream — that responsibility is left to each handler.

`StatusHandler` fails this responsibility. Its `params` schema doesn't even require a `repository` field [3](#0-2) , and `process` resolves target commits purely by `sha` across the entire `commits` table:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

This contrasts with the sibling handlers, which correctly scope by repository/stack before mutating anything — e.g. `PushHandler#process` filters `stacks.not_archived.where(branch:)` (the `stacks` scope is repository-bound) before calling `sync_github` [5](#0-4) , and `PullRequest::OpenedHandler#process` resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and scopes to `repository.review_stacks` before creating anything [6](#0-5) .

`Commit#create_status_from_github!` then unconditionally calls `statuses.replicate_from_github!(stack_id, github_status)` and fires `Hook.emit(:commit_status, stack, ...)`, `stack.schedule_merges`, etc., using the victim commit's own `stack` — none of these downstream calls re-validate that the payload's origin repository matches `commit.stack.repository` [7](#0-6) [8](#0-7) .

Exploit flow:
1. Attacker registers/owns `attacker-org/attacker-repo` in Shipit (or any repo whose `webhook_secret` they know, since they administer that GitHub org's webhook settings).
2. Attacker finds/engineers a `sha` that collides with a `Commit` row already tracked in a victim `Stack` (e.g., an identical initial/empty-tree commit, a shared vendored commit, or any commit reachable by both repos' histories — GitHub SHAs are content-addressed, so cross-repo collisions of legitimate commits are realistic in monorepo-splits, forks, or shared submodules).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, `X-Hub-Signature` computed with their own repo's `webhook_secret`, and body `{sha: <shared_sha>, state: 'success', repository: {full_name: 'attacker-org/attacker-repo'}}`.
4. `verify_signature` succeeds because it only validates against `attacker-org`'s own secret.
5. `StatusHandler.process` finds the victim's `Commit` (same `sha`, different `stack_id`/`Repository`) via the global `Commit.where(sha:)` query and writes a forged `Status` (`state: 'success'`) onto it, potentially unblocking `deployable?`/`blocked?` checks and triggering `stack.schedule_merges` on the victim stack.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type is handled, `ExplicitParameters` schema only validates payload shape (no repository requirement here), and `verify_signature` only authenticates that the payload came from *some* org matching the claimed `repository_owner` — it does not bind that org to the specific `Commit` rows touched by `process`.

### Impact Explanation
An attacker who owns any repository (and thus its `webhook_secret`) can forge CI status results (`success`/`failure`/`pending`/`error`) on commits belonging to a victim organization's `Stack`, without any relationship to or credentials for the victim repository. This can flip `Commit#deployable?`/`blocked?` state, trigger `stack.schedule_merges`, and fire `commit_status`/`deployable_status` hooks on the victim stack — a payload for one repository mutating another's commit/stack state. This matches the "Critical" category: "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any commit whose `sha` happens to be shared across repositories tracked by the Shipit instance, and blast radius spans all tenants hosted by the same Shipit installation.

### Likelihood Explanation
Preconditions: the attacker must control a GitHub org/repo already known to Shipit (so a `webhook_secret` exists and signature verification passes), and a `sha` collision must exist between the attacker's repo history and a victim `Commit` row (realistic for shared ancestry, forks, cherry-picks, or degenerate cases like the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, which is identical across every git repository). No GitHub App private key, session, or API token is required — only the ability to compute an HMAC with a secret the attacker's own org already possesses and send an HTTP POST. This is a low-cost, fully repeatable attack once a colliding `sha` is identified.

### Recommendation
Scope `StatusHandler#process` to the reporting repository: require `repository.full_name` (and/or `repository.id`) in the params schema, resolve the corresponding `Shipit::Repository`, and restrict the `Commit` lookup to that repository's stacks (e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id })`), mirroring the pattern already used in `PushHandler` and the `PullRequest` handlers.

### Proof of Concept
Minitest (`ActionDispatch::IntegrationTest`), signed with a second organization's secret, targeting a commit fixture owned by a different stack:
```ruby
test "status webhook cannot write a status onto a commit owned by another repository" do
  victim_commit = shipit_commits(:first) # belongs to victim stack/repository
  attacker_org_secret = Shipit.github(organization: 'attacker-org').webhook_secret # attacker knows own secret

  payload = {
    sha: victim_commit.sha,
    state: 'success',
    repository: { full_name: 'attacker-org/attacker-repo', owner: { login: 'attacker-org' } }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', attacker_org_secret, payload)

  assert_no_difference -> { victim_commit.statuses.count } do
    post shipit.webhooks_path,
      params: payload,
      headers: {
        'X-Github-Event' => 'status',
        'X-Hub-Signature' => signature,
        'Content-Type' => 'application/json'
      }
  end
end
```
Assert both sides of the binding: `repository_owner` resolved from the signed payload (`attacker-org`) must equal the org owning `victim_commit.stack.repository`; the test demonstrates the write occurs (or, once patched, that `victim_commit.statuses.count` stays unchanged) despite the mismatch.
