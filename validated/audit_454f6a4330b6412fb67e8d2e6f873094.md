### Title
Uppercased pull-request label name injects arbitrary env keys (e.g. `BASH_ENV`) into unfiltered `fetch` command execution - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) into the process environment with no key allowlist, and `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook payload. `StackCommands#fetch_deployed_revision` runs the `shipit.yml` `fetch` section commands using this unfiltered `env`, unlike deploy/rollback which pass through `filter_deploy_envs`/`filter_rollback_envs`.

### Finding Description
The broken binding: for review stacks, `env_reaching_fetch_command == Stack#env.merge(base_env)` should equal `filtered_env` (allowlisted via `EnvironmentVariables#permit`) but instead equals the raw merge with attacker-controlled keys.

`ReviewStack#env` does:
```ruby
super.merge(
  pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
)
``` [1](#0-0) 

Label names come straight from the webhook body via `LabelCapturingHandler#capture_labels`, which stores `params.pull_request.labels.map(&:name)` with no allowlist or character restriction (confirmed by the test accepting emoji names) [2](#0-1) .

`StackCommands#env` merges this stack env into the base command environment [3](#0-2) , and `fetch_deployed_revision` runs each `shipit.yml` `fetch` step with that same unfiltered `env:` [4](#0-3) . This is different from `Deploy`/`Rollback`, which route through `Stack#filter_deploy_envs`/`filter_rollback_envs` (`EnvironmentVariables.with(env).permit(deploy_variables)`) before execution [5](#0-4) [6](#0-5) ; there is no equivalent filtering call in `StackCommands#fetch_deployed_revision`.

The resulting `env` reaches `Command#start`, which builds `unbundled_env` by merging `@env.stringify_keys` over `BASE_ENV` and hands it to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [7](#0-6) .

Exploit flow: an unprivileged fork-PR author adds a label literally named `bash_env` to their own PR on a repo configured with `provisioning_behavior=prevent_with_label`. `ReviewStack#env` turns this into `BASH_ENV="true"`. Because `fetch_deployed_revision` executes inside the checked-out PR branch's working directory (via `with_temporary_working_directory`), and the attacker fully controls that repository tree, they can also commit a file literally named `true` containing malicious shell commands at the repo root. When the `fetch` section's command line is executed as a shell command with `BASH_ENV=true` set and cwd pointing at the attacker's checkout, a `bash` invocation of that command would source `./true` before running the step, achieving code execution.

Why existing guards fail: `filter_deploy_envs`/`filter_rollback_envs` only guard the `deploy`/`rollback` sections, not `fetch`. `EnvironmentVariables#permit` is never invoked on the path from `ReviewStack#env` into `StackCommands#fetch_deployed_revision`. Webhook signature verification and payload schema validation only constrain payload shape (label `name` must be a `String`), not its value, so any label text is accepted and captured.

Caveat: the actual severity is conditioned on the system shell used by `PTY.spawn`/`Process.spawn` to interpret the multi-word `fetch` command string honoring `BASH_ENV` (only true `bash`, not POSIX-mode `sh`, reads `BASH_ENV`), and on the fixed literal value `"true"` matching a real file the attacker plants at that exact relative path — both of which are plausible but were not verified further due to iteration limits; the underlying missing-filtering vulnerability (attacker-controlled env keys reaching an unfiltered `fetch` command execution) is confirmed in code.

### Impact Explanation
If the deploy host's shell used to run `fetch` command lines is bash proper, an attacker-controlled `BASH_ENV` combined with an attacker-controlled working directory (their own PR checkout) can result in arbitrary command execution on the Shipit deploy host during the `fetch` phase of processing their own review stack — Critical RCE per the stated impact class, `Command`/`PTY.spawn`. Blast radius is scoped to whichever repository/stack the PR belongs to, but is repeatable by any fork contributor against any repo using `prevent_with_label` review stacks.

### Likelihood Explanation
Preconditions: repo must have review stacks enabled with a `fetch` step defined in `shipit.yml`, an unprivileged contributor opens a PR from a fork and applies a label named to match a sensitive env key, and the deploy host's shell for multi-word commands must be true bash reading `BASH_ENV` in non-POSIX mode. Attacker cost is trivial (label + a repo file named after the fixed value `"true"`), but exploitability hinges on that shell precondition, which is not guaranteed on all deployments (many Linux systems' `/bin/sh` is dash, which ignores `BASH_ENV`).

### Recommendation
Apply an allowlist/`EnvironmentVariables#permit` filter to the `fetch` step's env exactly as done for `deploy`/`rollback` (e.g., add `fetch_variables`/`filter_fetch_envs` and use it in `StackCommands#fetch_deployed_revision`), and/or prefix or namespace label-derived env keys (e.g., `LABEL_<NAME>`) so they can never collide with sensitive variable names like `BASH_ENV`, `LD_PRELOAD`, `PATH`, etc.

### Proof of Concept
```ruby
# test/unit/stack_commands_test.rb (prevent_with_label)
test "#fetch_deployed_revision inherits BASH_ENV from a pull request label" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bash_env"]

  command = Shipit::StackCommands.new(stack)
  env = command.env

  assert_equal "true", env["BASH_ENV"]
  # Left side: attacker-controlled label -> BASH_ENV in fetch's env
  # Right side (expected safe binding): env["BASH_ENV"] should be nil/filtered
  refute_nil env["BASH_ENV"], "fetch step inherited a fork-controllable key (BASH_ENV)"
end
```
