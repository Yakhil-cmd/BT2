### Title
Cross-Organization Webhook Forgery via Multi-Tenant Signature Verification Bypass - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the inbound signature against based on an attacker-controlled field in the *unverified* JSON body — `repository.owner.login` — while the handlers that actually act on the payload key off a different attacker-controlled field, `repository.full_name`. If any configured organization has no `webhook_secret` set, signature verification silently passes for that organization, and the payload's `repository.full_name` can point to a stack belonging to a *different*, fully-configured organization.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App via: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the JSON body (`params.dig('repository', 'owner', 'login')`) *before* any signature has been proven valid. This value is used to pick a `GitHubApp` instance via `Shipit.github(organization: repository_owner)` [3](#0-2) , and `verify_webhook_signature` on that instance short-circuits to `true` when the selected organization's config has no `webhook_secret`: [4](#0-3) 

Multiple shipped/dummy configs demonstrate `webhook_secret` being optional/nil per organization: [5](#0-4) 

Once `verify_signature` passes, `create` dispatches the same raw payload to handlers: [6](#0-5) 

Handlers, however, resolve the target `Repository`/`Stack` using an *independent* field, `repository.full_name`, not `repository.owner.login`: [7](#0-6) [8](#0-7) 

`PushHandler`, for example, uses this to enqueue `stack.sync_github` for whatever stack matches `full_name`/branch: [9](#0-8) 

The equality that should hold — "organization whose secret authenticated the request" == "repository whose stack state gets written" — is not enforced. An attacker can craft a JSON body with `repository.owner.login` set to an organization that has no `webhook_secret` configured (verification trivially passes for that org) while setting `repository.full_name` to `"<org-with-secret>/<real-repo>"`, targeting a stack that belongs to a different, properly-secured organization. Since `Repository.from_github_repo_name` only looks at `owner/name` strings and has no relationship back to which App/org "authenticated" the request, the forged event is processed as if it legitimately came from GitHub for that repository.

### Impact Explanation
This breaks the deployment-trust binding between "the organization that authenticated" and "the repository that is written," letting an unprivileged attacker forge `push` events (triggering `GithubSyncJob` / `stack.sync_github`) or `status`/`check_suite`/`pull_request` events for a stack that belongs to a different, secured organization, without ever possessing that organization's `webhook_secret`. Depending on which handler is exercised, this can influence deploy-gating commit statuses, force review-stack archive/unarchive, or drive sync state that downstream deploy tooling relies on — falling under "unauthorized deploy" style impact for any Shipit installation that hosts more than one GitHub organization and where not every organization has a `webhook_secret` configured (a state the codebase explicitly supports and ships example configs for).

### Likelihood Explanation
Exploitability requires only that: (1) the target Shipit instance is configured for multiple GitHub organizations (a supported and documented configuration, `github_organizations`/`github_app_config`), and (2) at least one configured organization lacks a `webhook_secret` — which the code treats as a valid, intentional setting (`return true unless webhook_secret`). No authentication, no valid signature, no repository access, and no prior session are needed; the attacker only needs the public `/webhooks` endpoint URL.

### Recommendation
Do not select the verification key from unauthenticated payload data that differs from the field handlers act on. Either: (a) require `webhook_secret` to be present for every configured organization and fail closed if any is missing, or (b) after signature verification, re-derive `repository_owner` strictly from the verified raw body and assert it matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting mismatches with 422.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `OrgA` (no `webhook_secret`) and `OrgB` (with `webhook_secret`, tracked stack `OrgB/prod-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/prod-repo" }
}
```
No valid `X-Hub-Signature` is required.
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
4. `PushHandler` resolves `Repository.from_github_repo_name("OrgB/prod-repo")` and enqueues `GithubSyncJob` for that stack, even though the request was never signed with `OrgB`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
