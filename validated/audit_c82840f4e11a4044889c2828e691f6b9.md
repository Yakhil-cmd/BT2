### Title
Cross-organization webhook forgery via unbound `repository_owner` signature check enables cross-tenant CI-status/deploy manipulation - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is a valid analog of the C4 finding. The C4 bug is that a *sub-item* of a batched request (a sell order) is acted upon without being covered by the same validation that authorizes the batch. In this Shipit engine, `WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify against using a field read directly out of the *unverified* JSON body (`repository_owner`, i.e. `params.dig('repository','owner','login')` or `params.dig('organization','login')`), but the handlers that actually mutate application state key off a *different, independently attacker-controlled* field of that same body (`repository.full_name`) or, in the `status` webhook, off no repository scoping at all. Nothing ties the organization whose secret validated the signature to the resource actually written.

### Finding Description
`Shipit.github(organization:)` supports per-organization GitHub App configuration, each with its own independent `webhook_secret` (see `lib/shipit.rb` `github`, `github_app_config`, and `docs/setup.md` "Using Multiple Github Applications", and the double-org fixture `test/dummy/config/secrets_double_github_app.yml`). [1](#0-0) 

`WebhooksController#verify_signature` picks the app/secret to check the HMAC against using `repository_owner`, which is parsed straight from the attacker-supplied JSON body before any signature verification occurs: [2](#0-1) 

The HMAC (`X-Hub-Signature`) only proves that whoever sent the request knows the secret associated with `repository_owner`'s GitHub App — it does not, and cannot, prove anything about any other field in the body. `#create` then hands the *entire raw payload* to the registered handlers: [3](#0-2) 

Handlers resolve the target `Stack`/`Repository` from a completely different field — `repository.full_name` — with zero cross-check against `repository_owner`: [4](#0-3) 

This is structurally identical to the C4 bug class: the field the "authorization" (secure_compare/signature) covers is not the field the mutation acts on, so an attacker who legitimately owns/controls one configured organization's GitHub App (and therefore genuinely knows that org's `webhook_secret` — a routine, unprivileged position for an org admin in a multi-tenant Shipit install) can freely set `repository.full_name` inside the signed body to point at a victim organization's repository/stack while keeping `repository.owner.login` (or `organization.login`) pointed at their own org so `verify_signature` passes with their own legitimate secret.

The `status` handler is an even sharper instance of the same class: it performs **no repository/organization scoping whatsoever** — it looks up commits globally by `sha` across the entire database and mutates their CI status: [5](#0-4) [6](#0-5) 

Setting a commit's status feeds directly into deployability and continuous-deployment/merge decisions: [7](#0-6) [8](#0-7) 

**Equality broken:** `organization authenticated by verify_signature (repository_owner)` ≠ `stack/commit actually written to (repository.full_name / global sha lookup)`.

Before the attack (single-tenant, or an attacker with no configured app): the signature check fails for any org the attacker doesn't control, so no write occurs.
After: in any multi-org deployment (explicitly documented and supported: `docs/setup.md` lines 182-209, `github_app_config`), an attacker controlling org A's App/secret sends a `status` (or `push`/`check_suite`) webhook signed with org A's secret, but with `sha`/`repository.full_name` referencing org B's commit/stack. `verify_signature` passes (org A's secret matches org A's declared owner), and the handler writes a fabricated CI status or triggers a sync/merge decision on org B's stack, which the attacker has no legitimate authority over.

### Impact Explanation
This crosses the "authorization" boundary explicitly called out as in-scope: escalation into a stack the attacker does not control, forging CI status that drives automated `continuous_deployment`/merge decisions (`stack.schedule_merges`, `ProcessMergeRequestsJob`), and injecting fake `deployable_status`/`commit_status` events — a cross-repository write performed under a different organization's authorization than the one whose secret validated the request. This matches the "cross-repository writes" / "unauthorized deploy/merge" Critical category, since a forged `success` status can unblock an automatic merge/deploy on a stack belonging to an org the attacker was never granted access to.

### Likelihood Explanation
Requires the deployment to use Shipit's documented multi-organization GitHub App configuration (a supported, non-default-but-documented setup) and requires the attacker to control at least one of the configured orgs' GitHub App installations (i.e., know that org's own `webhook_secret`) — a routine unprivileged capability for any org admin, not an insider of the victim org. No token, session, or victim-org credential is needed. The `status` handler path additionally requires no repository field manipulation at all — it is exploitable by any org whose signature validates, with only a `sha` guess/enumeration needed for the specific commit.

### Recommendation
- Bind the field used for signature-secret selection to the same field used for authorization of the mutation: after verifying the signature, re-derive the acting organization from the verified body and assert it equals the owner of `repository.full_name` (or the `Repository`/`Stack` being targeted) before any handler runs.
- In `StatusHandler` (and similarly `check_suite`/`push`), scope `Commit.where(sha: params.sha)` to commits whose `stack.repository` belongs to the organization that was cryptographically verified (`repository_owner`), rather than a global, cross-tenant lookup.
- Reject webhooks where `repository.owner.login`/`organization.login` does not match `repository.full_name`'s owner segment.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` (attacker-controlled, webhook_secret known to attacker) and `OrgB` (victim, has a tracked `Stack`/`Commit` with sha `abc123`), per `docs/setup.md` multi-org schema.
2. Attacker crafts a `status` event JSON body: `{"sha": "abc123", "state": "success", "context": "ci/tests", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/attacker-repo"}}` and computes `X-Hub-Signature` using OrgA's own `webhook_secret`.
3. POST to `/webhooks` with header `X-Github-Event: status`. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature against OrgA's secret.
4. `StatusHandler#process` runs `Commit.where(sha: "abc123")` — matching OrgB's commit — and calls `create_status_from_github!`, creating a forged `success` status on OrgB's stack, potentially triggering `stack.schedule_merges` / continuous deployment for a repository the attacker never controlled.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
