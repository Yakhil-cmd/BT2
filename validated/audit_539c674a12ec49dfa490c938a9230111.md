### Title
Withdraw reverts entirely when either computed token amount rounds to zero, permanently freezing an LP's tokens in a skewed pool - (File: programs/cp-swap/src/instructions/withdraw.rs)

### Summary
`withdraw()` computes a depositor's proportional share of `token_0`/`token_1` via `CurveCalculator::lp_tokens_to_trading_tokens` and unconditionally rejects the **entire** withdrawal if either resulting amount rounds down to zero, even though the other token amount may be legitimately non-zero and owed to the user.

### Finding Description
In `withdraw()` [1](#0-0) , the LP share is computed with `RoundDirection::Floor` and then:
```rust
if results.token_0_amount == 0 || results.token_1_amount == 0 {
    return err!(ErrorCode::ZeroTradingTokens);
}
```
This "all-or-nothing" gate is a direct analog of the EigenPod `MIN_EXCESS_FULL_WITHDRAWAL_ETH_FOR_SCRAPE` threshold: instead of a fixed minimum, the pool's own reserve ratio and integer-division rounding act as an implicit minimum floor that a user's redeemable share must clear for *both* tokens simultaneously, or the whole withdrawal transaction reverts — including the portion of the share that is non-zero and rightfully claimable.

An unprivileged actor can reach this state without any special privilege: any swapper can drive the constant-product pool reserves to an extreme ratio via `swap_base_input`/`swap_base_output` (bounded only by normal curve mechanics, no admin action required) [2](#0-1) . Once one side of the pool (e.g. `token_1_vault`) becomes very small relative to `pool_state.lp_supply`, any LP holder whose proportional share of that side floors to `0` (via `lp_tokens_to_trading_tokens`, using `RoundDirection::Floor` [3](#0-2) ) is blocked from withdrawing *any* of their LP position, even the token_0 portion they are indisputably owed.

Unlike `initialize`/`initialize_with_permission`, where the pool creator locks a fixed `100` LP amount at pool creation (a design choice, not a per-user gate) [4](#0-3) , `withdraw`'s zero-check applies to every LP holder's redemption attempt and has no fallback path (there is no partial-withdraw option, no minimum-amount bypass, and no way to specify only the non-zero side).

### Impact Explanation
An LP provider's deposited tokens (both principal and any accrued trading fees represented by their LP share) can become permanently unwithdrawable while the pool remains skewed, since `withdraw` has no alternate code path to claim only the non-zero-valued token. This is a concrete freezing-of-user-funds condition reachable purely through normal, permissionless swap activity by any actor — no privileged signer, leaked key, or off-chain component is required.

### Likelihood Explanation
Likelihood scales with (a) how skewed the constant-product curve can get through ordinary swaps and (b) how small an LP holder's proportional stake is relative to `lp_supply`. Pools with low decimals tokens, large trading volume relative to a minority LP's stake, or tokens with very different value/decimals are realistic candidates for this to occur without any adversarial intent — just from normal trading pushing the reserve ratio to an extreme.

### Recommendation
Remove the strict `token_0_amount == 0 || token_1_amount == 0` all-or-nothing revert, or add a fallback path that allows a user to withdraw the non-zero-valued token even when the other side rounds to zero (mirroring the report's own recommendation to "remove the minimum requirement... or add another way to withdraw the funds in case they get stuck"). At minimum, ensure withdrawal is not blocked when only one side is legitimately zero due to rounding, so LP holders are never permanently unable to redeem their non-zero entitlement.

### Proof of Concept
1. Pool initialized normally by an unprivileged creator via `initialize`.
2. Small LP #2 deposits a modest amount, receiving LP tokens proportional to their share of `token_0_vault`/`token_1_vault`.
3. Unprivileged swapper repeatedly calls `swap_base_input`/`swap_base_output` in one direction, skewing reserves so `token_1_vault.amount` becomes very small relative to `pool_state.lp_supply` (a permitted, permissionless action bounded only by curve math, per `swap_base_input.rs`/`swap_base_output.rs`).
4. LP #2 calls `withdraw(lp_token_amount = their_full_balance, 0, 0)`. `CurveCalculator::lp_tokens_to_trading_tokens` floors `token_1_amount` to `0` because their proportional share of the now-tiny `token_1_vault` rounds down.
5. `withdraw` hits `if results.token_0_amount == 0 || results.token_1_amount == 0 { return err!(ErrorCode::ZeroTradingTokens); }` and reverts the entire transaction — LP #2 cannot redeem any token_0 either, and remains stuck until/unless the pool ratio reverses (which they cannot force, being unprivileged and possibly outbid by ongoing trading in the skewing direction).         input_amount: u128,
        input_vault_amount: u128,
        output_vault_amount: u128,
    ) -> u128 {
        // (x + delta_x) * (y - delta_y) = x * y
        // delta_y = (delta_x * y) / (x + delta_x)
        let numerator = input_amount.checked_mul(output_vault_amount).unwrap();
        let denominator = input_vault_amount.checked_add(input_amount).unwrap();
        let output_amount = numerator.checked_div(denominator).unwrap();

    }
