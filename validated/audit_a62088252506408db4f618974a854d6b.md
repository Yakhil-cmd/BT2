### Title
`Webhooks::Handlers::StatusHandler` matches commits by `sha` alone across all stacks, letting a foreign, correctly-signed status webhook write a `Status` into a victim stack's `Commit`, which `Commit#blocked?`/`#schedule_continuous_delivery` then trust - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no filter on the payload's `repository.full_name`. `create_status_from_github!` writes the status to `stack_id` taken from the matched `Commit` row, not from the webhook payload's repository, so a webhook that is validly signed for the attacker's own GitHub organization can create a `Status` row attributed to a completely different stack whenever a `Commit` row with the same `sha` exists there (e.g., a forked repository sharing git history with the victim's repository). `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) and `Status#schedule_continuous_delivery` (`app/models/shipit/status.rb:42-44` → `Commit#schedule_continuous_delivery`, `app/models/shipit/commit.rb:281-287`) then evaluate that forged `Status` as if it came from the victim's own CI.

### Finding Description
Binding claimed: for stack `S`, every `Status` counted by `S`'s commits' `blocked?`/`blocking?` must have been produced by a webhook whose payload's `repository.full_name` resolves to `S`'s repository, i.e. `status.stack_id == Repository.from_github_repo_name(payload['repository']['full_name']).stacks.map(&:id)`.

Tracing the code:
- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and checks `X-Hub-Signature` against that organization's `webhook_secret`. This authenticates *which organization's secret* signed the payload, but never checks that the `sha` inside the payload actually belongs to a commit under that organization/repository.
- `Shipit::Webhooks::Handlers::StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha`, with no `stack_id`/`repository` scoping, even though the base `Handler` class already provides a `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`) that other handlers use to scope to the payload's own repository - `StatusHandler` does not use it.
- `Commit#create_status_from_github!` → `add_status { statuses.replicate_from_github!(stack_id, github_status) }` (`app/models/shipit/commit.rb:165-169`) uses the matched commit's own `stack_id`, i.e. the victim stack, regardless of which organization's secret signed the incoming webhook.
- The `commits` table has a unique index on `["sha", "stack_id"]` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming the same `sha` can legitimately exist as distinct rows in multiple stacks (this is expected for forks/mirrors sharing git history), yet `StatusHandler` treats all rows sharing a `sha` as one target set.
- `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) then does `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)`, and `blocking?` delegates to `status`, which is built from all `Status` rows on the commit - including the forged one. `Status#schedule_continuous_delivery` (`app/models/shipit/status.rb:19,42-44`) fires on every created `Status`, calling `Commit#schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`), which checks `deployable?` (depends on `blocked?`) and enqueues `ContinuousDeliveryJob` if it now passes.

Exploit flow: attacker owns/controls a GitHub organization/repository already known to Shipit (e.g., they forked the victim's public repo and registered their fork as a Shipit-tracked repository, or otherwise control an org whose `webhook_secret` they know). Because the fork shares git history with the victim's repo, some commit `sha`s are literally identical rows in both the attacker's stack and the victim's stack (per the unique `[sha, stack_id]` index, both rows independently exist). The attacker sends `POST /webhooks` with `X-Github-Event: status`, a payload naming their own `repository.owner.login` (so `verify_signature` passes using their real, self-known secret), and `sha` set to the shared commit, `state: 'success'`. `StatusHandler` finds **all** `Commit` rows with that `sha`, including the victim's, and writes a `success` `Status` there. If that commit sits in the victim's `newer_than(last_deployed_commit).older_than(later_commit)` window and was previously blocking (e.g., `failure`/`pending`), `blocked?` now returns `false` for later commits, `deployable?` flips true, and `schedule_continuous_delivery` may enqueue a real deploy job.

None of the existing guards catch this: `verify_signature` authenticates the organization owning the payload, not the target commit's stack; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `StatusHandler` only validates `sha`/`state`/etc. types, not repository scoping; there is no `require_permission!`/`stacks` scope check inside `StatusHandler#process` unlike other handlers that use `Handler#stacks`.

### Impact Explanation
A payload for one repository (attacker's) mutates another repository's stack/commit state (victim's), matching the "Critical" category of "a payload for one repository mutating another's stack, commit, task or team" and potentially triggering "an unauthorized deploy" via `ContinuousDeliveryJob`. The forged `Status` is a real DB row on the victim's `Commit`, permanently counted by `blocked?`/`state`/`deployable?` for that stack going forward, and is repeatable against any repository pair that shares commit `sha`s (forks, subtree merges, cherry-picked/imported history) as long as the attacker controls one side's webhook secret.

### Likelihood Explanation
The attacker needs: (1) an organization/repository already integrated with Shipit for which they know the `webhook_secret` (self-service repo onboarding is explicitly listed as attacker capability - "push to a fork" and "emit webhooks from a repository they own"); and (2) a commit `sha` shared between their repo and the victim's repo. Shared shas naturally occur for forks of the same upstream history (very common), so this is not a cryptographic SHA-1 collision requirement in the realistic case - only the audit's synthetic PoC ("mark the blocking commit sha collidable") needs to artificially force the collision for a deterministic test. Given real-world forking, the precondition is plausible and repeatable at will by the attacker.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed handler) to the stacks belonging to the webhook's own `repository.full_name`, mirroring the `Handler#stacks` helper already defined in the base class, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of a global `Commit.where(sha: params.sha)`. Verify that the resolved commit's `stack.repository` matches `repository_name` from the payload before writing a `Status`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "does not create a status on a commit belonging to a different repository sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)              # repo: shopify/shipit
  attacker_stack = shipit_stacks(:cyclimse)          # repo owned by attacker, different repository

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  # Same sha exists for a commit under the attacker's own stack/repository
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => attacker_stack.github_repo_name, 'owner' => { 'login' => attacker_stack.repo_owner } }
  }

  assert_no_difference -> { victim_commit.statuses.reload.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Assert both sides of the binding: `status.stack_id` created by the handler must equal `Repository.from_github_repo_name(payload['repository']['full_name']).stacks.map(&:id)` — before the fix, `victim_commit.statuses.count` increases (violating the binding); after scoping the handler to `stacks`, it stays at 0.
