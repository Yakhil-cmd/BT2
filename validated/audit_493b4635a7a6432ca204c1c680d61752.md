### Title
`NonTransfer` proxy can escalate to reach `Registrar::swap` via `Auction` sub‑proxy - ([File: polkadot/runtime/rococo/src/lib.rs])

### Summary
The relay-chain runtimes (`rococo`, `westend`) and the `staking-async` relay-chain runtime declare `ProxyType::NonTransfer` a blanket superset of *every* other `ProxyType` in `is_superset`, while `NonTransfer`'s own `filter` explicitly and intentionally excludes `paras_registrar::Call::swap` (the code even carries the comment "Specifically omitting Registrar `swap`"). Because `pallet_proxy::do_proxy` authorizes `add_proxy`/`remove_proxy` solely through `ProxyType::is_superset`, a delegate holding only a `NonTransfer` proxy can use it to grant itself an `Auction` proxy — whose filter admits the *entire* `Registrar` pallet, including `swap` — and thereby reach a call that `NonTransfer`'s own filter was designed to deny. This is the exact bug class that was already identified and fixed for the `NonTransfer`/`Governance` pair on Asset Hub Westend (see `prdoc/pr_12769.prdoc`, fixing GH issue #12724), but the analogous `NonTransfer`/`Auction` gap on the relay-chain runtimes was not addressed.

### Finding Description
`pallet_proxy`'s privilege model relies entirely on `InstanceFilter::is_superset` to prevent a restricted proxy from escalating itself: [1](#0-0) 
`add_proxy`/`remove_proxy` executed through an existing proxy are only permitted `if def.proxy_type.is_superset(proxy_type)`. This check is a pure declaration and is *not* re-validated against `filter`, so any incorrect `is_superset` claim is directly exploitable.

In `polkadot/runtime/rococo/src/lib.rs` (and identically in `polkadot/runtime/westend/src/lib.rs` and `substrate/frame/staking-async/runtimes/rc/src/lib.rs`), the filters are defined as: [2](#0-1) 
Note the explicit comment `// Specifically omitting Registrar \`swap\`` — `NonTransfer` is deliberately designed to deny `paras_registrar::Call::swap`.

The `Auction` proxy type, however, admits the whole `Registrar` pallet unconditionally: [3](#0-2) 
`RuntimeCall::Registrar { .. }` matches `swap` as well as `register`/`deregister`/`reserve`.

Yet `is_superset` claims `NonTransfer` is a superset of *all* other proxy types, including `Auction`: [4](#0-3) 
`(ProxyType::NonTransfer, _) => true` — this single wildcard arm makes the "NonTransfer is superset of Auction" relation hold even though `NonTransfer.filter` rejects `Registrar::swap` while `Auction.filter` accepts it. This directly violates the lattice invariant that the codebase itself later documented and enforced for the `Governance` pair on Asset Hub Westend: [5](#0-4) [6](#0-5) 

The same broken `(ProxyType::NonTransfer, _) => true` wildcard pattern, combined with the same "omit swap" comment in the `filter` impl, is present in `polkadot/runtime/westend/src/lib.rs` (lines ~954, ~1004-1010, ~1022-1030) and `substrate/frame/staking-async/runtimes/rc/src/lib.rs` (lines ~1327-1363, ~1392-1398, ~1410-1418).

### Impact Explanation
A signed account that has been granted only a `NonTransfer` proxy (a role explicitly meant to exclude the ability to move/rebind parachain slots via `Registrar::swap`) can:
1. Use the `NonTransfer` proxy to call `Proxy::add_proxy(delegate = <attacker account>, proxy_type = Auction, ...)` on behalf of the real (delegator) account. This passes `pallet_proxy`'s `is_superset` check because of the flawed wildcard rule.
2. Use the newly created `Auction` proxy to dispatch `paras_registrar::Call::swap` as the real account — a capability the delegator never intended to expose through the `NonTransfer` role and which the runtime authors explicitly tried to withhold from it.

This breaks the confidentiality/integrity guarantee of the proxy delegation model: a lower-privilege delegate obtains a materially different (higher/different-scope) capability than granted, mirroring the Vault CVE's core defect — a permitted, less-privileged write path (`add_proxy`, analogous to Vault's identity-endpoint write) is used to mint a token/role (`Auction` proxy) whose effective privileges exceed what was authorized, bypassing the intended access boundary. The blast radius depends on what `Registrar::swap` allows an unauthorized party to do to a parachain's registration/lease state; I was not able to inspect the `swap` extrinsic's own origin/authorization body in the time available (tool budget exhausted), so I cannot confirm whether `swap`'s internal checks (e.g., requiring both para managers to agree) independently neutralize the escalation. This uncertainty is the main gap in fully proving impact.

### Likelihood Explanation
Likelihood is high for the *mechanism*: the vulnerable code path is a normal, no-privilege signed-extrinsic flow (`Proxy::add_proxy` via an existing proxy, then `Proxy::proxy` to dispatch the escalated call) — no governance, no stolen keys, no privileged role is required beyond holding an ordinary `NonTransfer` proxy grant, which is a common, low-trust delegation pattern (e.g., for utility calls). The exact same class of bug was independently discovered and fixed for one pair (`NonTransfer`/`Governance`) in this very codebase, confirming the pattern is a real, previously-triaged bug class rather than a hypothetical concern — it simply was not swept across all runtimes/pairs.

### Recommendation
Apply the same fix pattern used in the Asset Hub Westend regression fix (`prdoc/pr_12769.prdoc`) to `polkadot/runtime/rococo/src/lib.rs`, `polkadot/runtime/westend/src/lib.rs`, and `substrate/frame/staking-async/runtimes/rc/src/lib.rs`: replace the blanket `(ProxyType::NonTransfer, _) => true` wildcard with an explicit, audited list of subset types whose `filter` is provably fully contained in `NonTransfer`'s filter (excluding `Auction`, since `Auction` admits `Registrar::swap`, which `NonTransfer` explicitly denies). Additionally, port the lattice-consistency regression test (`proxy_type_superset_relation_matches_call_filters` from `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`) to these runtimes so that any future `is_superset`/`filter` mismatch is caught automatically instead of requiring manual, pair-by-pair discovery.

### Proof of Concept
I could not execute a live reproduction within the available tool budget (all remaining iterations were consumed by static analysis). The static evidence establishing the bug is:
- `NonTransfer.filter` explicitly denies `Registrar::swap` (comment "Specifically omitting Registrar `swap`") — [7](#0-6) 
- `Auction.filter` admits the full `Registrar` pallet, including `swap` — [3](#0-2) 
- `NonTransfer.is_superset` unconditionally returns `true` for every other `ProxyType`, including `Auction` — [4](#0-3) 
- `pallet_proxy` gates `add_proxy`/`remove_proxy` solely on `is_superset`, with no re-check against `filter` — [1](#0-0) 

A minimal integration test analogous to the existing `non_transfer_proxy_is_not_a_superset_of_governance` test (but targeting `ProxyType::Auction` and `paras_registrar::Call::swap`) in the rococo/westend runtime test suites would deterministically demonstrate: `ProxyType::NonTransfer.is_superset(&ProxyType::Auction)` returns `true` while `ProxyType::Auction.filter(&swap_call)` returns `true` and `ProxyType::NonTransfer.filter(&swap_call)` returns `false` — the same assertion pattern already used to prove and fix the `Governance` variant of this bug. I was unable to actually run this test or inspect `paras_registrar::Call::swap`'s internal origin checks before the session ended, so full end-to-end impact (what an attacker can concretely do once holding an unauthorized `Auction` proxy) remains partially unverified and should be confirmed by a background agent with continued tool access.

title: 'asset-hub-westend: fix `NonTransfer` proxy falsely claiming `Governance` containment'
doc:
- audience: Runtime User
  description: |-
    On Asset Hub Westend, the `NonTransfer` proxy type declared itself a superset of the
    `Governance` proxy type while its call filter denied the `Treasury`, `ConvictionVoting`,
    `Referenda` and `Whitelist` calls that `Governance` admits.

    Because `pallet_proxy` authorizes `add_proxy`/`remove_proxy` through `is_superset`, a
    `NonTransfer` proxy could add a `Governance` proxy for its delegator and thereby reach calls
    that its own filter denies. `NonTransfer` no longer declares `Governance` as a subset, so this
    is rejected.

    Existing `Governance` proxies are unaffected; only the ability of a `NonTransfer` proxy to
    create or remove one changes. The `Collator`, `Staking`, `NominationPools` and
    `StakingOperator` subsets of `NonTransfer` are unchanged.
