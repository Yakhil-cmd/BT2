### Title
Webhook signature verification org derived from attacker-controlled `repository.owner.login`/`organization.login` diverges from `repository.full_name` used by handlers, enabling cross-tenant stack mutation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to check against using `repository_owner`, computed from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. This value is independent of `params.repository.full_name`, which is later used by `UnlabeledHandler#repository` (via `Shipit::Repository.from_github_repo_name`) to resolve the actual stack to mutate. Since both fields are attacker-controlled in the raw JSON body of an unauthenticated POST, an attacker can make the signature check pass against an org with no `webhook_secret` while the mutated repository belongs to a different, secured org.

### Finding Description
The broken binding: the org used to verify the signature (`repository_owner` from `repository.owner.login`/`organization.login`) is assumed to equal the org that owns the repository being mutated (`owner` parsed from `repository.full_name` in `Repository.from_github_repo_name`). These are two independently-controlled JSON fields with no cross-check.

Code path:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` via `repository_owner` (line 59-62), which reads `params.dig('repository', 'owner', 'login')` first, falling back to `params.dig('organization', 'login')`. It then calls `Shipit.github(organization: repository_owner)` and `verify_webhook_signature`.
- `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83): `return true unless webhook_secret` — if the resolved org has no configured `webhook_secret`, the signature check is skipped entirely and any (or no) `X-Hub-Signature` header passes.
- Once `verify_signature` passes, `WebhooksController#create` parses the *same raw body* and dispatches to handlers (line 10-15), e.g. `UnlabeledHandler`.
- `UnlabeledHandler#repository` (app/models/shipit/webhooks/handlers/pull_request/unlabeled_handler.rb:59-63) resolves the repository using `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a completely separate field from `repository.owner.login`.
- `Repository.from_github_repo_name` (app/models/shipit/repository.rb:53-56) splits `full_name` on `/` and does `find_by(owner:, name:)`, with no relation to the org used for signature verification.
- `handle` then calls `stack.archive!` / `stack.unarchive!` (unlabeled_handler.rb:49-57), mutating the resolved stack's persisted state.

Attacker's exact request: POST `/webhooks` with header `X-Github-Event: pull_request`, arbitrary/absent `X-Hub-Signature`, and JSON body:
```json
{
  "action": "unlabeled",
  "number": 1,
  "pull_request": { "id":1,"number":1,"url":"x","title":"x","state":"open","additions":0,"deletions":0,
    "head":{"sha":"x","ref":"x"}, "user":{"login":"attacker"}, "assignees":[], "labels":[] },
  "repository": { "full_name": "securedorg/target-repo", "owner": { "login": "weakorg" } },
  "sender": { "login": "attacker" },
  "organization": { "login": "weakorg" }
}
```
Because `weakorg` has no `webhook_secret` configured, `verify_signature` passes unconditionally. The handler then resolves and mutates the `securedorg/target-repo` stack (archive/unarchive of a review stack), which belongs to the org whose webhook_secret was never checked.

Existing guards fail because: `verify_signature` never checks that the org used for the HMAC lookup matches the org that owns the repository referenced in the same payload; `drop_unhandled_event` and `ExplicitParameters` schemas only validate shape/presence of fields, not cross-field consistency; `Repository.from_github_repo_name` performs no association back to a "verified organization."

### Impact Explanation
An unprivileged, unauthenticated attacker can trigger a webhook-authenticated mutation (archive/unarchive of a review stack, and by extension any other handler keyed off `repository.full_name` while `verify_signature` used a different, weaker org's identity) on a repository belonging to an org that has a `webhook_secret` configured, without ever knowing that secret. This is a cross-tenant authentication bypass: the "more sensitive" (secured) org's data is written under the credentials of the "weaker" (unsecured) org. This is repeatable against any repository/stack as long as at least one configured org lacks a `webhook_secret`. This matches Critical impact — "a payload for one repository mutating another's stack" / authentication bypass (forged webhook accepted).

### Likelihood Explanation
Preconditions: multi-tenant Shipit deployment with `Shipit.secrets.github` containing more than one org key (per `github_organizations`/`TOP_LEVEL_GH_KEYS` in lib/shipit.rb), and at least one of those orgs configured without a `webhook_secret`. This is a realistic misconfiguration (e.g., a newly onboarded org, a test org, or an org intentionally left open), and nothing in the engine enforces that all configured orgs must have a `webhook_secret`. Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body; no GitHub account, no secrets, no session required. Fully repeatable/scriptable against any repo/stack in the secured org.

### Recommendation
In `WebhooksController#verify_signature`, require that the org used to select the `GitHubApp`/`webhook_secret` be consistently derived from the same trusted source as the repository whose stack will be mutated, and reject the request if `repository.owner.login` doesn't match the owner parsed from `repository.full_name` (or simply derive `repository_owner` solely from `repository.full_name`'s owner segment, not from a separate `owner.login` object or the top-level `organization.login`). Additionally, consider requiring every configured org in a multi-tenant setup to have a non-blank `webhook_secret` (fail closed instead of `return true unless webhook_secret`), so a misconfigured org can't be used as a signature bypass vector for the rest of the fleet.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (minitest, no live GitHub)
test "cross-tenant bypass: weak org signature check mutates secured org's stack" do
  # Two orgs configured: "weakorg" (no webhook_secret), "securedorg" (has webhook_secret)
  # via test/dummy secrets fixture with two github_config entries.

  secured_repo = shipit_repositories(:secured_org_repo) # owner: "securedorg"
  review_stack = create_review_stack(repository: secured_repo, provisioning_behavior: "allow_with_label")
  assert_not review_stack.reload.archived?

  payload = {
    action: "unlabeled",
    number: 1,
    pull_request: {
      id: 1, number: 1, url: "x", title: "x", state: "open", additions: 0, deletions: 0,
      head: { sha: "x", ref: review_stack.branch },
      user: { login: "attacker" }, assignees: [], labels: []
    },
    repository: { full_name: secured_repo.full_name, owner: { login: "weakorg" } },
    sender: { login: "attacker" },
    organization: { login: "weakorg" }
  }.to_json

  post "/webhooks", params: payload, headers: {
    "X-Github-Event" => "pull_request",
    "X-Hub-Signature" => "sha1=deadbeef", # bogus, never checked because weakorg has no webhook_secret
    "CONTENT_TYPE" => "application/json"
  }

  assert_response :ok
  # BEFORE fix: securedorg's stack is mutated despite signature only validated (trivially) against weakorg
  assert review_stack.reload.archived?, "secured org's stack was mutated via weak org's identity"
end
```
Both sides of the equality to assert explicitly in the test: `org_used_for_signature = "weakorg"` (from `repository.owner.login`) vs `org_owning_mutated_repo = "securedorg"` (parsed from `repository.full_name`) — before the fix these diverge and the mutation still succeeds; after the fix the request must be rejected (`head(422)`) when they diverge.
