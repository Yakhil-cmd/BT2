### Title
Webhook signature is bound to `repository.owner.login`, not to the `repository.full_name` the handler actually acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every default handler (`Shipit::Webhooks::Handlers::Handler#stacks`), however, resolves the `Repository`/`Stack` to act on using a completely different payload field, `payload.dig('repository','full_name')`. Because the two fields are never cross-checked against each other, a signature that is valid for organization A's webhook secret can carry a `repository.full_name` pointing at organization B's stack.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-49) does: [1](#0-0) 
picking the app config via `repository_owner` (line 59-62): [2](#0-1) 
- `GitHubApp#verify_webhook_signature` computes the HMAC using that organization's `webhook_secret`, and explicitly returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 
- The base handler class, used by every default handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`), looks up the target `Stack` via a *different* field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 
- `PushHandler#process` then syncs the resolved stack to an attacker-supplied `after` SHA: [5](#0-4) 
which is passed straight into `GithubSyncJob#perform` as `expected_head_sha` and only affects retry-timing behavior, but real content still comes from the stack's own `github_api` fetch, not from the payload: [6](#0-5) 

**Binding broken (as an equality):** the code implicitly assumes
`organization authenticated by verify_signature == repository.owner(full_name) acted on by the handler`
but nothing enforces `repository_owner == repository.full_name.split('/').first`. In a multi-tenant Shipit deployment (one Shipit instance serving multiple GitHub organizations, each with its own `Shipit.github(organization:)` config, as documented for `Shipit.github_teams`/OAuth-per-org support), an attacker who legitimately controls (or knows the `webhook_secret`/OAuth config of) their own onboarded organization "attacker-org" can craft a webhook payload with `repository.owner.login = "attacker-org"` (signed with attacker-org's own secret, which they possess because they administer that org's GitHub webhook settings) but `repository.full_name = "victim-org/victim-repo"`. `verify_signature` validates successfully against attacker-org's secret, and the handler then acts on victim-org's `Stack`.

### Impact Explanation
This crosses the "organization authenticated versus repository written" boundary called out in the rules. Concretely, an attacker who only has legitimate access to their own onboarded org can:
- Force `PushHandler` to enqueue `GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha` value, influencing sync retry/timing against a repository they do not control.
- Force `StatusHandler`, `CheckSuiteHandler`, and `PullRequest::*Handler` to write CI status/check-run/PR-label state onto a victim's commits/PRs, potentially manipulating merge-queue or CI-gating logic Shipit relies on to decide whether a commit is safe to deploy (`ci.require`, merge-queue `require`, etc., as configured in `shipit.yml`).

Because the actual git content is still fetched by Shipit's own GitHub App credentials (`stack.github_commits`), this alone does not achieve full "unauthorized deploy," but it does allow cross-organization writes into another repository's Shipit-tracked state (statuses, check-run refresh triggers, PR labels) — matching the High-impact "escalation... unauthenticated read of stack state" / cross-repository write category, and edging toward the Critical "cross-repository writes" bucket if a downstream CI-gate or merge-queue decision can be poisoned by forged status/check-run events.

### Likelihood Explanation
Requires only that: (1) the Shipit instance is configured for more than one GitHub organization (a documented, supported multi-org deployment pattern via `Shipit.github(organization:)`), and (2) at least one onboarded organization has either a blank `webhook_secret` (explicitly allowed by `verify_webhook_signature`'s `return true unless webhook_secret`) or a secret the attacker can obtain by controlling that org's own GitHub webhook settings. Neither condition requires access to the victim's repository, a Shipit session, or an `ApiClient` token — only administrative control of one's own onboarded org's webhook configuration, which is a materially lower privilege than the victim's repository write access.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the organization used to select/verify the webhook secret matches the owner encoded in `repository.full_name` (and `organization.login` when present) before dispatching to handlers — i.e., reject the request if `repository_owner != payload.dig('repository', 'full_name')&.split('/')&.first`. Additionally, consider making `verify_webhook_signature` fail closed (reject) rather than pass when `webhook_secret` is blank for a configured organization, to remove the trivial bypass path for unconfigured/no-secret organizations.

### Proof of Concept
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1 of body using attacker-org's known/blank webhook_secret>
Body:
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
`verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates the signature against attacker-org's own secret (or passes unconditionally if that org has no secret configured); `PushHandler#stacks` then resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` for a stack the attacker does not own, with an attacker-chosen `expected_head_sha`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
