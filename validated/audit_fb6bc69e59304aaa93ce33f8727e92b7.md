### Title
Webhook signature is bound to the payload's `organization`/`repository.owner`, but event handlers act on the unrelated `repository.full_name`/`sha` field — allowing cross-organization commit-status forgery and stack sync triggering - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook against the GitHub App/organization derived from `repository.owner.login` (or `organization.login`) in the JSON body, then hands the *entire, unvalidated* JSON body to the registered handlers. The handlers act on other fields of that same body — `repository.full_name` for `PushHandler`/PR handlers, and a bare `sha` for `StatusHandler` — without ever re-checking that those fields belong to the organization that was actually authenticated. This breaks the equality `organization that signed the payload == repository/commit the payload is allowed to affect`.

### Finding Description
`verify_signature` picks the signing app purely from the payload: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```

`repository_owner` is read straight from the attacker-controlled body: [2](#0-1) 

Shipit supports multiple GitHub Apps/organizations, each with its *own* `webhook_secret` (see the double-app fixture used in tests): [3](#0-2) 

Once the signature validates against *that one organization's* secret, `create` dispatches the raw JSON to every registered handler for the event, with no further scoping: [4](#0-3) 

The `status` handler then looks up the target purely by commit SHA, globally, across the entire Shipit instance/database — it never consults `repository.full_name` or any organization/repo binding at all: [5](#0-4) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`Commit.where(sha:)` is not scoped by stack/repository, so any commit SHA that happens to exist anywhere in Shipit's DB — belonging to any organization/stack configured on the instance — will get a forged status attached, as long as the request is signed by *any one* of the organizations Shipit trusts.

The equality that should hold and is violated:
`organization authenticated via repository.owner.login (webhook signature check)` == `repository/commit the handler is permitted to mutate (repository.full_name / sha lookup)`.

Other handlers (`PushHandler`, PR handlers) at least scope by `repository.full_name` via `Repository.from_github_repo_name`, but that field is likewise never cross-checked against the organization used for signature verification: [6](#0-5) [7](#0-6) 

So an attacker who legitimately administers (or otherwise knows the `webhook_secret` for) *any* organization configured in Shipit's `secrets.yml` can craft a signed payload whose `repository.owner.login`/`organization.login` matches their own org (so signature verification passes), while other fields (`repository.full_name`, `sha`) target a completely unrelated organization's stack/commit — including one they have no push access to and possibly cannot even see.

### Impact Explanation
`create_status_from_github!` feeds `Commit#deployable?`/CI-check state, which gates whether a commit can be shipped and can also trigger continuous delivery: [8](#0-7) [9](#0-8) 

By forging a `success` status for a targeted commit belonging to a stack the attacker has no access to, and if that stack has `continuous_deployment?` enabled, this can cause an **unauthorized deploy** to fire (`schedule_continuous_delivery`/`ContinuousDeliveryJob`), or unblock a merge/deploy that CI would otherwise have blocked (`stack.schedule_merges`) — matching the "unauthorized deploy/merge" Critical-impact category. Additionally, this cross-tenant reachability across `PushHandler` allows an attacker to force `sync_github` on a foreign stack, which is a lower-severity confused-deputy trigger but still crosses the organization boundary the webhook signature was supposed to enforce.

### Likelihood Explanation
Exploitability requires the attacker to be able to produce a validly signed webhook for *some* organization configured on the shared Shipit instance (e.g. they administer that org's GitHub App/webhook, a realistic scenario for any multi-tenant Shipit deployment supporting several `github_apps` entries, as the codebase itself demonstrates via the dual-app fixture). No push access, no Shipit `ApiClient` token, and no privileged Shipit account is required — only membership/administration of one (any) of the trusted GitHub organizations, which is a materially weaker privilege than the target stack's own organization.

### Recommendation
After signature verification, re-derive and enforce that every field a handler consumes (`repository.full_name`, commit `sha`, etc.) actually belongs to the organization/GithubApp that was used to validate the signature — e.g. resolve the `Repository`/`Stack` from the verified organization and reject/ignore the payload if `repository.full_name`'s owner does not match `repository_owner`. For `StatusHandler` specifically, scope the `Commit` lookup by the authenticated organization's repositories rather than a bare global `sha` match.

### Proof of Concept
1. Shipit is configured with two GitHub Apps/organizations, `OrgTwo` (attacker-administered, webhook secret known to attacker) and `OrgOne` (victim, has stack `victim-stack` with `continuous_deployment: true` and a pending commit `deadbeef...` awaiting a passing CI status).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "state": "success",
  "context": "ci",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgTwo/attacker-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `OrgTwo`'s known `webhook_secret` over the raw body and POSTs it to `/github/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgTwo")` and validates successfully (attacker knows this secret).
5. `Shipit::Webhooks::Handlers::StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — matching the victim's commit in `OrgOne`'s `victim-stack` — and calls `create_status_from_github!`, marking it `success`.
6. `Commit#schedule_continuous_delivery` observes `deployable?` now true and `stack.continuous_deployment?` true, enqueuing `ContinuousDeliveryJob`, causing an unauthorized deploy of `OrgOne`'s stack triggered entirely by an actor with only `OrgTwo` credentials.
