### Title
Webhook signature verification is keyed on `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` (or, for `status`, on a global `sha` lookup) — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's HMAC secret to validate the inbound webhook against using `repository_owner`, a value pulled from the JSON body itself (`repository.owner.login`, or `organization.login` as fallback). Once the signature check passes, the same raw JSON body is handed to `Shipit::Webhooks::Handlers::Handler`, which resolves the *actual* repository/stack to act on from a **different** field: `repository.full_name`. Nothing binds these two fields together, and `StatusHandler` doesn't even use `repository_name` — it looks up commits globally by `sha`. This reproduces the reported bug class ("field acted on but never covered by the verification") as: *the organization whose secret authenticated the request ≠ the repository the handler writes to*.

### Finding Description
- `verify_signature` resolves the signing organization solely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` explicitly **skips verification entirely** when no `webhook_secret` is configured for the resolved organization — a documented, optional setting (`docs/setup.md`: "Webhook secret (optional)"), and a real deployment pattern shown in the fixtures where multiple organizations are configured with independent (and possibly absent) secrets: [3](#0-2) [4](#0-3) 

- After the (possibly no-op) signature check, `create` dispatches the *entire raw payload* to handlers: [5](#0-4) 

- The base `Handler` resolves the target stacks from `repository.full_name`, a field completely independent of `repository.owner.login` used for signature-org selection: [6](#0-5) 

- `PushHandler` uses that mismatched resolution to trigger a sync with an attacker-chosen `after` SHA on stacks belonging to a repository that was never covered by the verification: [7](#0-6) 

- `StatusHandler` is worse: it doesn't even scope by `repository_name`. It looks up commits **globally by `sha`** across the entire Shipit instance and writes a forged CI status to whichever commit matches, regardless of which repository/organization was used to pass the signature check: [8](#0-7) 

Equality that is broken: `organization_that_authenticated (repository.owner.login / organization.login) == repository_that_is_written (repository.full_name, or in the status case, the repo of the matched commit)`. Before the attack these are always equal for legitimate GitHub-originated webhooks (both fields derive from the same real repository object). An attacker who controls, or targets, an organization onboarded to this Shipit instance **without a configured `webhook_secret`** can submit a POST to `/webhooks` with `repository.owner.login` set to that unsecured organization (satisfying `verify_signature`, since `verify_webhook_signature` returns `true` when no secret exists) while setting `repository.full_name` (for push/pull_request/check_suite) — or simply a known `sha` (for status) — to reference a completely different, secured stack tracked by the same Shipit instance.

### Impact Explanation
- Via `status`: an unauthenticated caller (no secret, no Shipit session, no `ApiClient` token) can forge a `success` CI status for any commit SHA known to exist in any stack on the instance, because `Commit.where(sha: params.sha)` is global and unscoped by the (correctly or incorrectly) verified organization. Many Shipit deploy pipelines gate deploy eligibility on required statuses/checks, so this can be used to make an otherwise-blocked commit appear deployable, contributing to an **unauthorized deploy**.
- Via `push`: the same mismatch lets the caller enqueue `GithubSyncJob`/`stack.sync_github` against a stack belonging to a repository/organization that was never authenticated, using an attacker-chosen `expected_head_sha`.
- This satisfies the report's Critical/High bar ("unauthorized deploy") without requiring a Shipit session, an `ApiClient` token, or knowledge of a *targeted* organization's `webhook_secret` — only the (documented-as-optional) absence of a secret on **any one** organization configured on the instance.

### Likelihood Explanation
Requires: (1) the deployment to have at least one organization onboarded with `webhook_secret` unset (explicitly supported/documented as optional), and (2) knowledge of a target commit `sha` (public git data) or repository full name (also public). Both conditions are realistic in multi-tenant Shipit deployments and don't require compromising any secret, making this a genuine unauthenticated-attacker path rather than a theoretical one.

### Recommendation
Bind the value used to select/verify the signing organization to the exact value used by handlers to resolve the affected repository/stack — i.e., derive both from the same `repository.full_name` (or the same `owner`/`name` pair), and reject the payload if the org selected for verification does not match the owner of the repository being acted upon. Additionally, `StatusHandler#process` should scope its `Commit` lookup by the verified repository (via `stacks`/`repository_name`) instead of a global `sha` lookup. Do not silently allow `verify_webhook_signature` to `return true` when `webhook_secret` is blank; require an explicit secret for all onboarded organizations, or clearly document/flag unsecured organizations as unable to safely coexist with secured ones on the same instance.

### Proof of Concept
1. Configure (or target) two organizations on one Shipit instance: `unsecured-org` (no `webhook_secret`) and `secured-org` (has commits/stacks tracked in Shipit) — a supported configuration per `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "unsecured-org/whatever" },
  "sha": "<sha of a commit belonging to secured-org's tracked stack>",
  "state": "success",
  "context": "ci/required-check"
}
```
No `X-Hub-Signature` header is required to pass, because `verify_signature` resolves `Shipit.github(organization: "unsecured-org")` and `verify_webhook_signature` returns `true` when that org has no `webhook_secret` [9](#0-8) .
3. `StatusHandler#process` then writes a forged `success` status onto the targeted commit in `secured-org`'s stack, unscoped by which organization was verified [8](#0-7) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
