### Title
Cross-repository sha-collision status webhook forces `ProcessMergeRequestsJob` on a victim stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)`, a query that spans every stack in the database rather than being scoped to the repository named in the verified webhook payload. Since `Commit#create_status_from_github!` (via `add_status`) enqueues `ProcessMergeRequestsJob.perform_later(stack)` whenever the matched commit transitions to `pending`/`success`, any correctly-signed webhook from an attacker-controlled organization can trigger merge-queue processing on an unrelated victim stack whose commit table happens to contain a commit with the same sha (e.g., a shared ancestor commit from a common fork/upstream history).

### Finding Description
The intended binding is: `stack_named_in_verified_payload == stack_passed_to_ProcessMergeRequestsJob.perform_later`. Tracing the code shows this does not hold.

- `WebhooksController#verify_signature` only verifies the HMAC signature against the GitHub App configured for `repository_owner` (`params.dig('repository','owner','login')`) [1](#0-0) . This proves the webhook was legitimately sent by the app installed on the *sender's own* organization/repo — it says nothing about which stack's commits may be mutated.
- `Webhooks::Handlers::Handler` exposes a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)` [2](#0-1) , but `StatusHandler#process` never uses it.
- `StatusHandler#process` instead does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This query is not filtered by `stack_id` or by the repository named in the payload, so it matches every `Commit` row across every stack/tenant sharing that sha.
- `Commit#create_status_from_github!` calls `add_status`, and `add_status` calls `stack.schedule_merges` whenever the state transitions to `pending` or `success` [4](#0-3) , which is exactly how `ProcessMergeRequestsJob.perform_later(stack)` gets enqueued for whatever `stack` owns the matched commit — not the stack tied to the webhook's own repository.

Exploit flow: an attacker who owns/forks a public repository that shares history with a victim's tracked stack (e.g., both forked from the same upstream) has a commit with an identical sha to a commit already synced into victim stack B's `commits` table. The attacker triggers a `status` event on their own repository (which is entirely under their control — they can set any CI/commit-status state via their own GitHub App/webhook configuration for their own org). The webhook is legitimately signed for the attacker's own organization, so `verify_signature` passes. `StatusHandler#process` then finds the commit row(s) with the matching sha in the DB, which includes stack B's row, and calls `create_status_from_github!` on it, potentially flipping stack B's commit to `success`/`pending` and enqueuing `ProcessMergeRequestsJob.perform_later(stack_b)`.

None of the existing guards prevent this: `verify_signature` only authenticates the sender's own organization, not the target stack; `ExplicitParameters` schema only validates payload shape; there is no `require_permission!`/`authorized?` check in this webhook path at all (webhooks are unauthenticated-by-signature, not by-user); and no model validation ties `Commit.where(sha:)` results to the repository in the payload.

### Impact Explanation
A successful exploit lets an attacker force `ProcessMergeRequestsJob` to run against a stack (repository/tenant) they never authenticated against, using only a webhook signed for their own organization. `ProcessMergeRequestsJob` re-evaluates and can merge pending PRs in the victim's merge queue that were only blocked on CI status [5](#0-4) . This is a payload for one repository (attacker's) causing state changes/actions (merge-queue processing, potentially a merge) for another repository's stack — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized... merge." The blast radius is any stack whose commit history overlaps in sha with an attacker-accessible repository (most plausible via shared/forked history, cherry-picks, or import of the same commit across multiple tracked stacks), and is repeatable per shared-sha commit.

### Likelihood Explanation
Preconditions: the attacker needs (a) a GitHub repository with the Shipit-compatible GitHub App/webhook installed and able to emit `status` events under their own control (trivial for any repo owner/CI integrator), and (b) knowledge of a sha that also exists as a `Commit` row in the victim stack. The second condition is the limiting factor — genuine SHA1 collision is infeasible, but identical shas across independently-tracked stacks arise naturally whenever repos share git history (forks, mirrors, monorepo splits, vendoring of the same upstream commit), which is a realistic scenario for products tracking many related repositories. No Shipit secrets, sessions, or privileged roles are required; cost per attempt is one HTTP webhook POST with a valid signature for the attacker's own org.

### Recommendation
Scope `StatusHandler#process`'s commit lookup to the repository named in the verified webhook payload, e.g. filter `Commit.where(sha: params.sha, stack: stacks)` (using the existing `Handler#stacks` helper based on `repository_name`) instead of a bare `Commit.where(sha: params.sha)`, so a status update can only affect commits belonging to stacks under the repository that signed the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook for repo A does not enqueue ProcessMergeRequestsJob for stack B via shared sha" do
  stack_a = shipit_stacks(:shipit)          # tenant A, repository "shopify/shipit-engine"
  stack_b = shipit_stacks(:cyclimse)        # tenant B, unrelated repository
  shared_sha = "a" * 40

  commit_b = stack_b.commits.create!(sha: shared_sha, ...)  # pending/failure state

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/travis",
    "repository" => { "full_name" => stack_a.repository.full_name, "owner" => { "login" => stack_a.repository.owner } }
  }

  assert_no_enqueued_jobs only: ProcessMergeRequestsJob do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  assert_not_equal "success", commit_b.reload.state
end
```
Before the fix, `Commit.where(sha: shared_sha)` matches `commit_b` regardless of `payload["repository"]`, and `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [stack_b])` would pass — demonstrating the cross-tenant enqueue. After scoping the lookup to `stacks` derived from `repository_name`, the job for `stack_b` is never enqueued.
