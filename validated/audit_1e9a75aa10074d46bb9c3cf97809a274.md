## Analysis [1](#0-0) [2](#0-1) [3](#0-2) 

The webhook signature check selects *which organization's* secret to verify against using a field taken from the unauthenticated request body itself, while the `status` event handler performs its write with **no scoping to that organization or repository at all**. This is the same class of bug as the USDT report: a value that is checked/consumed by one part of the system (the signing secret bound to an organization) is silently disconnected from the value that is actually acted upon (an arbitrary commit, in any stack, in any organization).

### Title
Organization-scoped webhook signature does not bind the `status` event to that organization's repositories, enabling cross-tenant unauthorized deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit supports hosting multiple GitHub organizations from one instance, each configured with its own `webhook_secret` in `secrets.yml`. `WebhooksController#verify_signature` picks which organization's secret to validate the HMAC against using `repository_owner`, a value read straight out of the unverified JSON body. Once the signature is accepted, `StatusHandler#process` looks up commits **by SHA only, across the entire database**, with no check that the matched commit's stack belongs to the organization whose secret produced the valid signature.

### Finding Description
`WebhooksController#verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [4](#0-3) 

`repository_owner` is derived from the body itself:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`Shipit.github(organization:)` resolves per-org config from a multi-tenant `secrets.yml` layout (`github_app_config`), exactly as documented for "Using Multiple Github Applications": [3](#0-2) [6](#0-5) 

This means the HMAC only proves the request was signed with *some* onboarded organization's secret — a secret the attacker legitimately possesses if they administer their own GitHub App/organization integrated with the same Shipit instance. Nothing after signature verification re-checks that the payload's actual target (a specific commit/stack) belongs to that same organization.

Unlike every other handler, which scopes to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before acting (see `Handler#stacks`), `StatusHandler` does not use `repository_name`/`stacks` scoping at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [7](#0-6) [8](#0-7) 

`Commit#create_status_from_github!` → `add_status` schedules continuous delivery/merges once a commit becomes `success`: [9](#0-8) [10](#0-9) [11](#0-10) 

**The broken equality:** the organization whose secret authenticated the request `≠` the organization/repository whose commit is written. The signature proves possession of Org A's secret; the write lands on any commit whose SHA matches, in any Org's stack, including Org B's, entirely independent of which organization signed the request.

### Impact Explanation
An attacker who is a legitimate, low-privilege customer/administrator of their **own** GitHub organization integrated into a shared, multi-tenant Shipit instance (a normal, unprivileged relationship to the target) can:
1. Craft a `status` webhook body with `sha` set to a commit belonging to a **different** organization's stack, `state: "success"`.
2. Sign it with their own organization's `webhook_secret` (which they legitimately hold) and set `repository.owner.login`/`organization.login` to their own org so `verify_signature` picks the matching secret.
3. `StatusHandler` matches `Commit.where(sha: ...)` globally and applies the forged "success" status to the victim's commit, potentially triggering `schedule_continuous_delivery` / `schedule_merges` on the **victim organization's stack** — an unauthorized deploy of a commit the attacker chose, and a cross-tenant write into data (`Status`, `Commit`) they have no legitimate right to touch.

This satisfies the Critical bar: cross-repository/cross-tenant writes and an unauthorized deploy triggered without any credential belonging to the victim organization.

### Likelihood Explanation
Requires only that the Shipit deployment hosts more than one GitHub organization (a documented, supported configuration — see "Using Multiple Github Applications") and that the attacker controls one of them (a normal tenant, not a privileged Shipit user, GitHub team member, or holder of any victim secret). SHA collision across unrelated repos is unnecessary if the attacker can guess/observe a target SHA (commit SHAs are often public via GitHub) — they only need the correct SHA, not any relationship to the owning repository.

### Recommendation
Have `StatusHandler` (and any other handler that does not already do so) scope its lookup through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`/`stacks`, and additionally verify the resolved repository's owner matches `repository_owner`/the organization key used to select and verify the webhook signature, rejecting the payload otherwise.

### Proof of Concept
1. Deploy Shipit configured with two organizations (`OrgA`, `OrgB`) each with their own `webhook_secret`, per `docs/setup.md`'s multi-org example.
2. As the operator of `OrgA`, compute `sha1=HMAC(OrgA_webhook_secret, body)` for:
```json
{
  "sha": "<sha-of-a-commit-in-OrgB-stack>",
  "state": "success",
  "repository": {"owner": {"login": "OrgA"}}
}
```
3. POST to `/github/webhooks` with header `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and accepts the signature (valid for OrgA's secret).
5. `StatusHandler#process` finds the commit by SHA (belonging to OrgB) and creates a `success` `Status` on it, potentially triggering continuous delivery for OrgB's stack — without ever presenting OrgB's secret or any OrgB credential.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
