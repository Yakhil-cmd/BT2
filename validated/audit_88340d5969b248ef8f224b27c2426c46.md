### Title
Commit status webhook handler updates commits across all repositories/organizations, bypassing the org binding enforced by webhook signature verification - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController` verifies the GitHub webhook HMAC signature using the secret configured for the organization named in the payload's `repository.owner.login` field [1](#0-0) . This authenticates "this payload legitimately originated from organization X". However, `StatusHandler#process`, which handles the `status` event, never uses that organization/repository binding when applying the payload: it looks up commits globally by SHA alone and writes the status to every matching row.

### Finding Description
Every other event handler in the engine scopes its side effects to the stacks that belong to the repository named in the payload, via the shared `Handler#stacks` helper that resolves `Repository.from_github_repo_name(repository_name)` before touching any data: [2](#0-1) 
This is used, e.g., by `PushHandler` and `CheckSuiteHandler`: [3](#0-2) [4](#0-3) 

`StatusHandler`, in contrast, does not use `stacks`/`repository_name` at all — it matches purely on commit SHA across the entire `Commit` table: [5](#0-4) 

The webhook signature check only proves the payload's `repository.owner.login`/`organization.login` matches an org configured in Shipit — it does not prove, nor does `StatusHandler` check, that the `sha` referenced belongs to a commit actually tracked under that same repository/stack. Since `Shipit::Commit` rows are stored per `Stack` (and the same git commit SHA is legitimately synced into multiple `Stack` records — e.g. staging and production stacks of the same repository, or any repository that shares history with another configured repository), a validly-signed `status` webhook from one org/repo can flip the CI status of a `Commit` row belonging to a *different* stack that happens to share the same SHA. This breaks the binding "organization authenticated by the webhook signature" == "repository/stack whose commit-status record is written."

### Impact Explanation
`Commit#statuses` feeds directly into `ci.require` / `ci.blocking` deploy gating described in the README [6](#0-5) . An attacker able to trigger a genuine, validly-signed `status` webhook for any repository configured in this Shipit instance (e.g. by pushing a commit status via the GitHub API to a repo/org they have status-write access to) can cause a `success` status to be recorded against a `Commit` row of an unrelated stack that shares the same SHA (same repo tracked under multiple environments is the common case in Shipit). This can satisfy required-status deploy gating and enable an unauthorized deploy to proceed on a stack the attacker has no authorization over, meeting the "unauthorized deploy" Critical impact bar.

### Likelihood Explanation
Every Shipit deployment that tracks the same repository under more than one `Stack` (a first-class, documented use case — separate stacks per environment/branch) is affected as soon as any org configured for webhooks in that installation has an attacker capable of setting a commit status (a low-privilege GitHub capability, often available to CI bots, external contributors' checks, or other integrations). No Shipit session, API-client token, or repository write access on the *target* stack's repository is required — only a valid signed webhook for a *configured* organization, which GitHub itself generates whenever any status is posted to that org's repos.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, consistent with the other handlers: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` and constrain the `Commit` lookup to `stacks.flat_map(&:commits)` (or an equivalent `Commit.where(sha:, stack_id: stacks.select(:id))`) instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Shipit is configured with organizations `org-a` and `org-b`, each with its own webhook secret; `org-a/repo` is tracked by two stacks: `production` and `staging`.
2. A commit with SHA `abc123` exists in both the `production` and `staging` stacks (common when the same repository/branch history is shared across environments).
3. An attacker with only status-write access to `org-a/repo` (e.g. a scoped CI bot token) posts a `success` status for SHA `abc123` via the real GitHub API for the `staging` context.
4. GitHub delivers the webhook to Shipit, correctly signed with `org-a`'s secret; `WebhooksController#verify_signature` passes.
5. `StatusHandler#process` executes `Commit.where(sha: 'abc123').each { |c| c.create_status_from_github!(params) }`, which updates the status on the `Commit` row for **both** the `staging` and `production` stacks, satisfying `ci.require` on `production` even though no such status was ever produced for the production deploy pipeline.
6. A deploy trigger relying on `ci.require`/`ci.blocking` for the `production` stack now proceeds using the forged status, without the attacker ever holding production deploy authorization.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

<h3 id="ci">CI</h3>

**<code>ci.require</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want Shipit to disallow deploys if any of them is missing on the commit being deployed.

For example:
```yml
ci:
  require:
    - ci/circleci
```

**<code>ci.hide</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want Shipit to ignore.

For example:
```yml
ci:
  hide:
    - ci/circleci
```

**<code>ci.allow_failures</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want to be visible but not to required for deploy.

For example:
```yml
ci:
  allow_failures:
    - ci/circleci
```

**<code>ci.blocking</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want to disallow deploys if any of them is missing or failing on any of the commits being deployed.

For example:
```yml
ci:
  blocking:
    - soc/compliance
```
