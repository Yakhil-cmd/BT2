### Title
Stack-scoped API token bypasses its stack binding via `Api::CCMenuController#stack` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true`, and `Api::BaseController#stacks`/`#stack` enforce that scoping by restricting lookups to `Stack.where(id: current_api_client.stack_id)` when `stack_id?` is true. [1](#0-0)  `Api::CCMenuController`, however, overrides `#stack` to query `Stack.from_param!(params[:stack_id])` directly against all stacks, never consulting `current_api_client.stack_id`. [2](#0-1)  This breaks the equality "stack a token authorizes == stack a token touches": the permission check only validates the coarse-grained `read:stack` scope, never the specific stack the token was minted for. [3](#0-2) 

### Finding Description
`ApiClient#authenticate` verifies the bearer token's signature and loads the record by id; it does not encode or re-verify a stack binding at request time. [4](#0-3)  The only enforcement of the "single stack" scope declared on an `ApiClient` (`belongs_to :stack, optional: true`) lives in `Api::BaseController#stacks`, which is `stack`-scoped only when consumed through `Api::BaseController#stack`. [1](#0-0) 

`Api::CCMenuController` inherits from `Api::BaseController` and requires only the generic `read:stack` permission, then defines its own `#stack` method that resolves `params[:stack_id]` against `Stack.from_param!` unscoped by the client's `stack_id`. [5](#0-4)  `require_permission!` only checks that the string `"read:stack"` is present in `permissions`; it never compares `current_api_client.stack_id` to the requested stack. [3](#0-2) 

The intended real-world minting path for such scoped tokens is `CCMenuUrlController#client`, which creates an `ApiClient` with only `permissions: %w[read:stack]` and no explicit `stack:` attribute set on the client itself (the stack binding is only implied by convention/URL, not enforced server-side). [6](#0-5)  More importantly, any `ApiClient` created elsewhere with an explicit `stack_id` (e.g. the `here_come_the_walrus` fixture, scoped to stack `shipit` with `read:stack` only) is intended to see only that one stack, as enforced and tested for `Api::StacksController#index`. [7](#0-6)  Before/after the trust boundary: before the request, the token's signature and DB row establish "this client may read stack A only" (`stack_id` set, `Stack.where(id: ...)`); after dispatch through `CCMenuController#show`, the code touches whatever stack the caller names in `params[:stack_id]`, i.e. any stack B — the binding "stack authorized == stack touched" no longer holds for this one action.

### Impact Explanation
This is an unauthenticated-relative-to-scope read of stack state: an attacker holding a `read:stack` token that was only meant to authorize CI-badge polling for one stack can enumerate/read build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, deploy id/timestamps) for every other stack in the Shipit instance, including private/internal ones, by supplying a different `stack_id` param. This matches the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output," since it escalates a narrowly-scoped credential into instance-wide stack-state disclosure.

### Likelihood Explanation
Exploitation requires only possession of any valid `read:stack`-scoped API token (e.g., a CCMenu URL shared for one stack's badge, which is designed to be embeddable/distributable and low-privilege) and knowledge or guessing of another stack's `to_param` (owner/repo/environment), which is often predictable or discoverable via `Api::StacksController#index` if the token is otherwise unscoped, or simply guessed from repository naming conventions. No write access, no additional secrets, and no privileged account are needed — only the pre-existing believed-safe scoped token.

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped `Api::BaseController#stacks`/`#stack` lookup (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack.from_param!` against all stacks, so the `current_api_client.stack_id` binding is enforced consistently across every API action, including CCMenu.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack_id = A` with only the `read:stack` permission (e.g. via `CCMenuUrlController#fetch` for stack A, or any equivalently-scoped token such as the `here_come_the_walrus` fixture).
2. Note the resulting CCMenu URL: `GET /api/stacks/A/ccmenu.xml?token=<token>` — this succeeds as intended, returning stack A's status.
3. Reuse the same token against a different stack B the client was never authorized for: `GET /api/stacks/B/ccmenu.xml?token=<token>`.
4. `Api::CCMenuController#stack` resolves `params[:stack_id]` via `Stack.from_param!` (unscoped), bypassing the `stack_id` restriction that `Api::BaseController#stacks` would have applied, and returns stack B's build status/activity/deploy info despite the token only being authorized for stack A.
