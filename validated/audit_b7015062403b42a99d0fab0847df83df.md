### Title
Scoped API client tokens can read CCMenu status for any stack, not just the stack they are authorized for — ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the `stack` lookup helper inherited from `Api::BaseController` with a version that bypasses the per-token stack scoping. This lets an `ApiClient` token that was deliberately restricted to a single stack read deploy/build status (`show`) for any other stack in the installation, breaking the binding between "the stack a token authorizes" and "the stack it actually touches."

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0)  and permission is enforced only on the `operation:scope` string (e.g. `read:stack`), not on which specific stack is being accessed [2](#0-1) .

The intended enforcement of the stack scope lives in `Api::BaseController`: when a client is scoped (`current_api_client.stack_id?`), the `stacks` collection is restricted to just that stack, and `stack` is resolved from that restricted collection: [3](#0-2) 

`Api::CCMenuController`, however, defines its own private `stack` method that ignores this scoping entirely and resolves the stack globally from `params[:stack_id]`: [4](#0-3) 

Because Ruby method resolution picks the subclass's `stack` over the inherited scoped one, `require_permission :read, :stack` only checks that the token has the string permission `read:stack` (which it does, since it was granted `read:stack` for its own stack), but the actual object returned by `stack` is looked up with `Stack.from_param!`, completely unscoped to `current_api_client.stack_id`.

This creates the exact binding break: the stack a token is **authorized** for (`current_api_client.stack_id`) is not the stack that is **touched** (`Stack.from_param!(params[:stack_id])`), and no equality/ownership check ties the two together in this controller.

### Impact Explanation
Any holder of a legitimately-issued, stack-scoped API token (with only `read:stack` permission on Stack A) can call `/stacks/:stack_id/cc_menu.xml` (or the equivalent API route) with an arbitrary `stack_id` belonging to a different stack (Stack B) and successfully receive Stack B's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, lock state, etc.), as rendered by `shipit/ccmenu/project` [5](#0-4) . This is an unauthorized cross-stack read of deploy/task state that the token was never granted access to, matching the High-severity category of "unauthenticated read of stack state, task streams or deploy output" via an authorization scope escalation.

### Likelihood Explanation
High. The attacker only needs one legitimately-issued, narrowly-scoped API token (e.g. one created for a specific team/stack's CCMenu integration) and knowledge/enumeration of another stack's `stack_id`/slug — no additional secrets, sessions, or elevated privileges are required. The flaw is a straightforward method-override bug reachable on every request to this controller.

### Recommendation
Remove the overriding `stack` method in `Api::CCMenuController` (or reimplement it using the scoped `stacks` collection from `Api::BaseController`, i.e. `stacks.from_param!(params[:stack_id])`) so that stack-scoped tokens can only resolve stacks within their authorized scope, consistent with every other controller inheriting from `Api::BaseController`.

### Proof of Concept
1. As an authorized Shipit user, create an `ApiClient` scoped to Stack A with permission `read:stack` (as done for fixture `here_come_the_walrus`, which has `stack: shipit`, `permissions: ['read:stack']`) [6](#0-5) .
2. Obtain that client's `authentication_token`.
3. Send `GET /stacks/<stack_A_param>/cc_menu.xml` using Basic auth with the token — succeeds as expected.
4. Send `GET /stacks/<stack_B_param>/cc_menu.xml` (a different, unrelated stack) using the same token.
5. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped [7](#0-6)  instead of the scoped `stacks.from_param!` used elsewhere [8](#0-7) , the request succeeds and returns Stack B's deploy/build status XML, even though the token was only ever authorized (`stack_id`) for Stack A.
