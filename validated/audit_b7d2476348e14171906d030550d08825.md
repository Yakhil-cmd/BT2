### Title
Webhook signature verification authenticates the sending organization's GitHub App but never binds that identity to the `repository.full_name` actually acted upon, allowing cross-tenant webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to use for HMAC verification based on `repository_owner`, computed from the payload's `repository.owner.login` (or `organization.login`) field. [1](#0-0)  The `repository_owner` lookup value is the *only* thing tying a request to a specific GitHub App/organization. [2](#0-1)  However, downstream event handlers resolve the actual target `Repository`/`Stack` from a completely different field in the same payload: `payload.dig('repository', 'full_name')`. [3](#0-2)  Nothing cross-checks that `repository.full_name`'s owner matches `repository.owner.login`/the organization whose secret validated the signature. This is structurally identical to the reported bug class: a value is authenticated/verified (the org's secret via `pointsPerShare`-style manipulable input) while the value actually acted upon (`repository.full_name`, analogous to `_shares * pointsPerShare` in `_correctPoints()`) is taken from unverified attacker-controlled payload content that diverges from what was checked.

### Finding Description
Shipit supports hosting multiple GitHub Apps/organizations in one instance, each with its own `webhook_secret`, configured under `github.<org>.webhook_secret` in `secrets.yml`. [4](#0-3)  `verify_webhook_signature` in `GithubApp` does a plain HMAC-SHA1 compare of the raw POST body against the secret belonging to whichever organization `Shipit.github(organization: ...)` resolves to. [5](#0-4)  `WebhooksController#verify_signature` picks the organization purely from `repository_owner`, which the request itself defines: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) 

An organization/tenant that legitimately controls its own GitHub App installation (and therefore knows its own `webhook_secret`) can craft an arbitrary JSON body where:
- `repository.owner.login` = its own org (so `verify_signature` selects its own, correctly-known secret, and the HMAC it computes over the full raw body validates)
- `repository.full_name` = `"<victim-org>/<victim-repo>"`

Because the signature is computed over the *entire* raw body using the attacker's own known secret, the attacker can produce a syntactically valid, signature-passing webhook whose `repository.full_name` names a repository/org it does not control. `PushHandler` (and other handlers) then resolve stacks purely from that unverified `full_name`: `Repository.from_github_repo_name(repository_name)&.stacks`, then triggers `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the matching branch. [6](#0-5) 

The equality the deployment-trust binding is supposed to enforce is:
`organization authenticated by verify_signature == owner(repository.full_name acted upon by the handler)`

That equality is never checked; only the org used to *pick a secret* is verified, not that it matches the repo the payload claims to affect.

### Impact Explanation
By abusing this, a tenant with any legitimately configured GitHub App/org in a multi-org Shipit deployment can inject forged `push`, `status`, `check_suite`, `pull_request`, or `membership` events attributed to another org's/tenant's repository, since every handler keys off `repository.full_name` from the same unauthenticated JSON body region. Concretely:
- `PushHandler` will enqueue `GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha`, causing Shipit to resync/consider deploying a specific commit on a stack it does not own. [7](#0-6) 
- Status/check_suite-style events could inject fabricated CI status entries for a victim stack's commits (handled similarly through the shared `Handler#stacks`/`repository_name` resolution), which feeds continuous-deployment eligibility and merge-queue gating in `MergeRequest#all_status_checks_passed?`. [8](#0-7) 

This can enable an unauthorized deploy/merge trigger against a stack the attacker's org has no legitimate relationship with — squarely within the in-scope "Critical: unauthorized deploy, rollback, or merge" category, since it lets a tenant force sync/CI-state changes on another tenant's stack purely by knowing its own webhook secret.

### Likelihood Explanation
Exploitability requires only that Shipit is configured with more than one GitHub App/org (a documented, supported configuration) and that the attacker is a member/operator of one of those orgs (i.e., possesses that org's own legitimately-issued `webhook_secret` — not the victim's). No `ApiClient` token, GitHub write access to the victim repo, or session is required; only crafting an HTTP POST to `/webhooks` with a body signed with the attacker's own known secret. This is a realistic scenario in shared/multi-tenant Shipit deployments as explicitly documented in `docs/setup.md`.

### Recommendation
After verifying the HMAC signature, cross-check that the resolved `repository.owner.login`/`organization.login` used to select the verifying GitHub App actually matches the owner portion of `repository.full_name` (and any other repository identifiers used by handlers) before dispatching to `Shipit::Webhooks.for_event(event)`. Reject the webhook (422) on mismatch. Alternatively, bind handlers to look up the `Repository`/`Stack` scoped by the verified organization rather than by an independently-supplied `full_name` field.

### Proof of Concept
1. Shipit is configured with two GitHub App orgs: `attacker-org` (attacker legitimately controls, knows its `webhook_secret`) and `victim-org` (hosts the target stack), per the multi-org setup in `docs/setup.md`.
2. Attacker builds a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, attacker-org's webhook_secret)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s app, and the HMAC validates successfully. [1](#0-0) 
5. `PushHandler#process` resolves `repository_name` = `"victim-org/victim-repo"` from the same body, finds victim-org's `Stack`s, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on them, despite the request never being authenticated by victim-org's GitHub App. [6](#0-5) [3](#0-2) 

Note: I could not read the full contents of `status_handler.rb`, `check_suite_handler.rb`, and `membership_handler.rb` due to index limits, so I have not verified the exact downstream effects for those specific event types beyond confirming they inherit the same `Handler#stacks`/`repository_name` resolution as `push_handler.rb`. Starting a Devin session would allow full inspection of those files to confirm the exact blast radius per event type.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
