### Title
`StatusHandler#process` applies GitHub status webhooks to commits across all stacks by SHA alone, with no repository scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)`, without any check that the commit's owning stack/repository matches the repository that generated the webhook. `verify_signature` in `WebhooksController` only proves the payload was legitimately signed by GitHub for the *attacker's own* repository's organization; it never re-binds the `sha` to that repository. An attacker who owns any repository can therefore push a commit with a SHA colliding with (or, more realistically for a real Git SHA, a commit that is cherry-picked/rebased with identical content producing the same SHA as) a commit in a victim stack, then emit a `status` event from their own repo, causing the victim's commit's `deployable?` state and `stack.schedule_merges`/`schedule_continuous_delivery` to be evaluated with an attacker-authored status.

### Finding Description
Broken binding: `stack_that_trigger_continuous_delivery_operates_on == stack_whose_webhook_secret_verified_payload_reported_the_status` is expected, but the actual code only enforces `commit.sha == params.sha`, with the commit resolved from the entire `commits` table regardless of stack/repository.

Code path:
1. `WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the JSON body and dispatches to handlers for the event.
2. `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` from the **attacker's own payload** (`params.dig('repository','owner','login')`) and verifies the signature using `Shipit.github(organization: repository_owner)`. This only proves the request was signed by GitHub for the attacker's own org/app installation - it says nothing about which commit SHAs are legitimately "owned" by that repository.
3. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha`, with **no `stack_id`/repository filter tying the lookup back to the repository that signed the webhook**.
4. `Commit#create_status_from_github!` → `Commit#add_status` (app/models/shipit/commit.rb:165-169, 366-386) creates the status record, and if the simple state changed, calls `stack.schedule_merges` (line 383).
5. `Commit#schedule_continuous_delivery` (app/models/shipit/commit.rb:281-287), fired `after_commit` on `Status` creation via `deployable?` (line 227-229: `!locked? && (stack.ignore_ci? || (success? && !blocked?))`), enqueues `ContinuousDeliveryJob.perform_later(stack)` for the **victim's** `stack`, purely because the attacker's webhook set the status to `success`.

Root cause: the commit-lookup query in `StatusHandler#process` trusts the `sha` field alone to select which commit(s)/stack(s) to mutate, while the signature verification only authenticates the *sender's own* repository/org, not the specific commit or stack being mutated. There is no re-check inside `Commit#create_status_from_github!`, `Commit#add_status`, or `Commit#deployable?` that the commit's `stack.repository` (or `stack.github_repo_name`) matches `params.repository`/`repository_owner` from the verified webhook.

Existing guards do not close the gap: `verify_signature` authenticates the sender's org, not the target commit's stack; `drop_unhandled_event` only filters event types; the `ExplicitParameters` schema (`params do ... end` in `StatusHandler`) only validates field types/presence, not repository identity; `blocked?`/`locked?` are stack-local conditions the attacker's preconditions already satisfy per the scenario.

### Impact Explanation
An attacker who controls any GitHub repository can inject a `status` (or, by identical pattern, other SHA-keyed webhooks) that is applied to any commit in the system sharing that SHA, including commits belonging to unrelated victim stacks. Where the victim stack has `continuous_deployment?` enabled and the shared-SHA commit is unlocked and unblocked, this results in an unauthorized `ContinuousDeliveryJob.perform_later(stack)` enqueue for the victim's stack (`app/models/shipit/commit.rb:286`), i.e., a payload originating from one repository triggering deploy/merge actions on another's stack - matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The action is repeatable against any stack/commit combination sharing a SHA, and requires no privileges beyond owning a GitHub repository capable of emitting webhooks.

### Likelihood Explanation
Feasibility hinges entirely on SHA collision/reuse across repositories. Git SHA-1 is content-addressed (tree+parent+metadata), so two independent repositories producing byte-identical commit objects (e.g., through vendored/mirrored history, deliberate reproduction, or fetched forks that both know a shared upstream commit) is exactly the scenario the question stipulates ("naming a `sha` shared with a commit at the HEAD of a victim stack"). Given that precondition holds, the rest of the chain (`verify_signature` for the attacker's own org, no cross-repo binding in `StatusHandler#process`) executes deterministically and requires nothing from the victim's org secrets. The main constraint is engineering a SHA that legitimately exists in both the attacker's repo history and the victim's, which is plausible in shared-history/fork scenarios but not for arbitrary unrelated SHAs.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other SHA-keyed handler, e.g. check-run handlers) by the repository that was authenticated in `verify_signature`, e.g. filter `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_owner: ..., repository_name: ... })` using the `repository`/`organization` fields from the verified payload, rather than a bare global `sha` lookup. Alternatively, pass the verified repository identity from the controller into the handler and assert `commit.stack.github_repo_name == payload_repo_full_name` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook from an unrelated repository triggers continuous delivery on a victim stack sharing the SHA" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment? => true
  shared_sha = "deadbeef" * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim head", author: AnonymousUser.new)

  ContinuousDeliveryJob.expects(:perform_later).with(victim_stack)

  # Attacker's own repo/org, never touching victim's webhook_secret
  Shipit::Webhooks::Handlers::StatusHandler.new(
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  ).call

  assert victim_commit.reload.deployable?
end
```
This demonstrates: (a) no assertion or filter in `StatusHandler#process` ties `params.repository`/`attacker` to `victim_stack`, and (b) `ContinuousDeliveryJob.perform_later` is enqueued for `victim_stack` solely from the attacker-authored status.     def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
