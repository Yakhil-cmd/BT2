### Title
Cross-org webhook signature check lets attacker mutate a victim repo's `PullRequest` via `AssignedHandler` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used to authenticate a webhook based solely on `params.dig('repository','owner','login')` (`repository_owner`), while every `pull_request` handler (including `AssignedHandler`) resolves the target `Repository`/`Stack`/`PullRequest` using the independent `params.repository.full_name` field. Because these two fields are never checked for consistency, an attacker can pick an org name for `repository.owner.login` that has no `webhook_secret` configured (so `verify_webhook_signature` trivially returns `true`) while pointing `repository.full_name` at a victim org's repository, causing the victim's persisted `PullRequest` record to be mutated by an unauthenticated request.

### Finding Description
The broken binding: the code implicitly assumes `repository_owner == owner_of(repository.full_name)`, i.e., that the org whose secret authenticates the webhook is the same org that owns the repository being mutated. This is never enforced.

- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(signature, raw_post)` [1](#0-0) , where `repository_owner` is read from `params.dig('repository','owner','login')` (or `organization.login` fallback) [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally "unless webhook_secret" is configured for that org [3](#0-2) . So any org configured in `Shipit.github_apps`/config without a `webhook_secret` set causes signature verification to be bypassed entirely, regardless of the actual `X-Hub-Signature` header.
- `AssignedHandler#repository` resolves the repository to act on strictly from `params.repository.full_name`, completely independent from `repository_owner`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [4](#0-3) .
- `AssignedHandler#process` then finds and updates the victim's persisted `PullRequest` row (joined through that resolved repository's stacks) when `action` is `assigned`/`unassigned`: `pull_request.update(github_pull_request: params.pull_request)` [5](#0-4) .

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, an arbitrary/garbage `X-Hub-Signature`, and a JSON body where `repository.owner.login` = an org configured in Shipit but with no `webhook_secret` set (a "no-secret org"), while `repository.full_name` = `"victim-org/victim-repo"` (a real, secret-protected victim repo/org that owns a stack with `blocking_statuses` configured). `action` = `"assigned"`. Because `repository_owner` resolves to the no-secret org, `verify_webhook_signature` returns `true` without ever checking the real signature against the victim org's secret. The request then proceeds to `AssignedHandler`, which resolves and updates the victim's `PullRequest` record using `full_name`, entirely bypassing the victim org's actual webhook secret.

Why existing guards fail: `drop_unhandled_event`/`check_if_ping` don't check org consistency; `verify_signature` only guards against an *unknown* org (`GithubOrganizationUnknown` -> 422) but does nothing if the chosen org is known yet has no secret configured; the `ExplicitParameters` schema on `AssignedHandler` only requires `repository.full_name` to be present as a `String` — it performs no cross-check against the org used for signature verification.

### Impact Explanation
An unauthenticated attacker can cause a repository/org's webhook payload (signed with no secret, or with a bogus signature routed to a no-secret org) to mutate another repository's persisted `PullRequest` state (`github_pull_request` JSON blob, which downstream code uses to determine assignee/label/status-derived state feeding `blocked?`/mergeability checks used to gate deploys). This is a cross-tenant/cross-repository state write triggered by a payload that authenticated as a different repository entirely, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The blast radius extends to any victim org/repo whose `full_name` the attacker can guess or knows, as long as any org in the Shipit installation is configured without a webhook secret.

### Likelihood Explanation
Preconditions: the Shipit instance must have at least one configured GitHub org/app entry with no `webhook_secret` set (common in setups with per-org tokens where some orgs are treated as low-risk, or where an operator has not yet rotated in a secret) — `Shipit.github(organization: repository_owner)` must resolve without raising `GithubOrganizationUnknown`. Attacker cost is a single unauthenticated `POST /webhooks` with a crafted JSON body, no GitHub account or Shipit credentials required. Fully repeatable and automatable against any victim repo/stack that has `blocking_statuses` configured (or any other webhook-handler-driven state), as it doesn't require the attacker to have any particular relationship to the victim org.

### Recommendation
Enforce that the org that authenticates the signature is the same org that owns the resource being mutated: derive/verify `repository_owner` against the owner parsed from `repository.full_name` (reject if they differ) before dispatching to any handler, and/or have `verify_webhook_signature` fail closed (return `false`) rather than `true` when no secret is configured, unless that org has been explicitly and intentionally opted out. Additionally, `GitHubApp#verify_webhook_signature`'s "unless webhook_secret" bypass should be reconsidered — a webhook from an org with no secret should not implicitly authenticate payloads referencing other repositories.

### Proof of Concept
minitest plan (no live GitHub, under `test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/assigned_handler_test.rb`):

1. Configure two orgs in test `Shipit.github_apps`/`Rails.application.config.shipit.github_apps` (or equivalent test config): `"no-secret-org"` with `webhook_secret: nil`, and `"victim-org"` with a real `webhook_secret`.
2. Create a `Stack`/`Repository` for `"victim-org/victim-repo"` with `blocking_statuses` configured, and an existing `PullRequest` record with `number: 42` and some baseline `github_pull_request` state (assert baseline: `pull_request.github_pull_request['assignees']` == `[]` or known initial value).
3. Build a `pull_request` webhook JSON payload with `action: "assigned"`, `number: 42`, `repository.owner.login: "no-secret-org"`, `repository.full_name: "victim-org/victim-repo"`, and `pull_request.assignees` set to a new attacker-chosen value.
4. `POST /webhooks` with headers `X-Github-Event: pull_request` and an arbitrary/incorrect `X-Hub-Signature` (not signed with victim-org's secret).
5. Assert response is `200 OK` (not `422`), proving signature check was bypassed via the no-secret org lookup.
6. Reload the victim `PullRequest` record and assert `pull_request.github_pull_request['assignees']` now equals the attacker-supplied value — i.e., `Equality broken: repository_owner ("no-secret-org") != owner_of(repository.full_name) ("victim-org")`, yet the victim's record was written anyway.
7. As a control, repeat with `repository.full_name` pointing at a repo owned by `"no-secret-org"` itself and confirm no cross-tenant record is touched, isolating the vulnerability to the divergence between `repository_owner` and `full_name`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
