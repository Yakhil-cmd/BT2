### Title
Cross-repository forged commit-status webhook mutates arbitrary stack's commit status via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, across the entire `commits` table, and never restricts the query to the repository/stack that actually authenticated the inbound webhook. This lets an attacker who controls a repository containing a commit whose SHA coincidentally (or, more realistically, due to shared git ancestry with a fork) matches a SHA in a victim's stack, send a legitimately signed status webhook for their own repository and have it applied to the victim's commit, firing `Hook.emit(:deployable_status, victim_stack, ...)`.

### Finding Description
The claimed binding is: `commit.stack (passed into Hook.emit) == stack whose webhook_secret authenticated the request (derived from repository_owner)`. This does not hold.

`WebhooksController#verify_signature` only proves that the HTTP request was signed with the GitHub App secret belonging to `repository_owner` (`params.dig('repository','owner','login')`), i.e. it authenticates *an* org, not a specific stack: [1](#0-0) 

The base `Handler` class provides a `stacks` helper that scopes lookups to the repository named in the payload: [2](#0-1) 

However, `StatusHandler#process` never uses this scope. It queries `Commit` globally by `sha` only: [3](#0-2) 

Each matched commit (regardless of which stack/repository it belongs to) is then updated: [4](#0-3) 

and `add_status` emits the `deployable_status` hook using `commit.stack` — a stack determined solely by whichever rows happen to share that SHA, not by the repository that was cryptographically verified: [5](#0-4) 

Exploit flow: an attacker who owns/operates a repository (e.g., a public fork of the victim's repo, or any repo that shares a common ancestor commit with the victim's tracked branch — a common occurrence since forks share commit SHAs for unmodified history) creates or already has a Shipit stack for their own repo, causing their commit (with the shared SHA) to also exist as a `Commit` row scoped to their own stack. Because Shipit's Commit table is not deduplicated by (repo, sha) at the query layer used here, the same SHA can independently exist as separate `Commit` rows in both the attacker's stack and the victim's stack. The attacker then sends `POST /webhooks` with `X-Github-Event: status`, a payload naming their own repository (so `verify_signature` resolves and validates against their own org's legitimate `webhook_secret`), and `sha` equal to the shared commit, `state: "success"`. `StatusHandler#process` matches `Commit.where(sha: params.sha)` against *all* stacks, including the victim's, and calls `create_status_from_github!` on the victim's commit row too, transitioning it and firing `Hook.emit(:deployable_status, victim_stack, ...)`.

None of the existing guards prevent this: `verify_signature` authenticates the org but not which stack's data may be mutated; `drop_unhandled_event` only filters unsupported event types; the `ExplicitParameters` schema for `StatusHandler` validates types, not ownership; there is no `require_permission!`/`stacks` scoping applied in this handler as there is in other handlers (e.g. pull request handlers use `stacks`/`repository_name`).

### Impact Explanation
An attacker who authenticates only as their own (unrelated) GitHub organization can force a status transition (e.g. pending/failure → success) on a completely different tenant's commit, triggering that tenant's `Hook.emit(:deployable_status, ...)` outbound webhook toward external CI/CD or ChatOps integrations bound to the victim stack. This is a cross-tenant data-integrity/authorization bypass: a payload authenticated for one repository mutates another repository's stack/commit state and triggers automation on the victim's behalf — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any commit SHA shared between an attacker-controlled repository and a victim stack (most realistically via forks of the tracked repository, which is a very common Shipit deployment pattern).

### Likelihood Explanation
Preconditions: the victim stack must have an active `Hook` subscribed to `deployable_status`; the attacker must control (or create) a repository/stack whose commit history shares a SHA with the victim's tracked commit (trivially achievable by forking the victim's repo prior to divergence, since ancestor commits keep identical SHAs) and must be able to send correctly-signed webhooks for their own repository, which is normal GitHub behavior for any repo they own or that has the Shipit GitHub App installed. No victim secrets, sessions, or privileges are needed. This is a low-cost, easily repeatable attack requiring nothing beyond normal fork/push access to a repository under the attacker's control.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by `sha` alone) to the repository that authenticated the request, mirroring the `stacks` helper already used elsewhere, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or add a `stack_id`/`repository_id` filter to the `Commit.where(sha:)` query so only commits belonging to stacks tied to the authenticated `repository_name`/`repository_owner` can be updated.

### Proof of Concept
Minitest plan (`test/models/commits_test.rb` style, no live GitHub):
1. Create two stacks, `victim_stack` (repo `victim/repo`) and `attacker_stack` (repo `attacker/repo`), each with a `Commit` row sharing the same `sha` value (`"deadbeef" * 5`).
2. Attach a `Shipit::Hook` on `victim_stack` subscribed to `deployable_status`.
3. Instantiate `Shipit::Webhooks::Handlers::StatusHandler` (or call `Commit.where(sha: shared_sha)`) with a payload whose `repository.full_name == "attacker/repo"` and `state: "success"`, simulating a webhook that passed `verify_signature` for `attacker`'s org only.
4. Assert both `attacker_stack`'s and `victim_stack`'s `Commit` rows transitioned to `success`.
5. Using `expect_hook_emit(:deployable_status)`, assert the hook payload's `stack` equals `victim_stack` even though the authenticated `repository_owner`/org was `attacker`, proving `commit.stack != stack derived from the authenticated repository_owner`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))

      end
