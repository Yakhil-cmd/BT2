### Title
AA `$attestation[]` formula trusts stale attestations after the attested address's definition (control) has changed - ([File: formula/evaluation.js])

### Summary
The oscript/AA formula function `attestation[...]` (used inside Autonomous Agent bytecode to gate behavior on third-party attestations, e.g. KYC/whitelisting) looks up rows in the `attestations`/`attested_fields` tables by address and attestor only. Unlike the equivalent address-definition primitive `['attested', [address, attestors]]`, it never checks whether the attested address's controlling definition was changed after the attestation was posted. This lets whoever currently controls an address inherit an attestation that was made about a *previous* controller of that same address — an auto-linking-without-revalidation flaw analogous to CVE-2025-64717.

### Finding Description
In `definition.js`, the `attested` operator used for address-definition/spending conditions delegates to `storage.filterAttestedAddresses`: [1](#0-0) 

`storage.filterAttestedAddresses` explicitly excludes any attestation whose `main_chain_index` is not *after* the most recent `address_definition_changes` entry for that same address: [2](#0-1) 

This invalidation is deliberate: once an address's definition (i.e. its controlling keys/logic) is changed, any previously issued attestation about "the person controlling this address" must stop applying to whoever controls it afterward.

However, the AA-only formula primitive `attestation[...]` in `formula/evaluation.js` (case `'attestation'`) performs the equivalent lookup without this safeguard. It queries `attestations`/`attested_fields` joined only with `units` (and, for the unstable-unit branch, `unit_authors`/`aa_addresses`), filtering solely by `attestor_address`, `address`, `field`, and `main_chain_index`/`sequence`: [3](#0-2) 

There is no join against `address_definition_changes` and no check of when the address's definition was last modified. As confirmed by a repo-wide search, `address_definition_changes` is referenced by `witness_proof.js`, `storage.js`, `network.js`, `validation.js`, `archiving.js`, `composer.js`, `wallet.js`, `writer.js`, and `definition.js`, but never by `formula/evaluation.js`, confirming the AA formula path omits this check entirely.

### Impact Explanation
Any AA that gates funds, actions, or state on `$attestation[address=$some_address, attestors="ATTESTOR_ADDR"]` (a very common pattern for KYC-gated DeFi, allowlists, proof-of-humanity, age/jurisdiction checks, etc.) can be manipulated as follows:
1. Address A is legitimately attested by a trusted attestor (e.g. "KYC passed" or "whitelisted").
2. The controller of A posts an `address_definition_change`, handing control of A to a completely different key/definition (e.g. sells the address, or an attacker who was co-signer takes over via a definition change allowed by the original definition).
3. Because `$attestation[...]` never checks `address_definition_changes`, the AA still treats A as attested, even though the entity now controlling A was never vetted by the attestor.

This can result in unauthorized fund release from an AA (AA fund loss), bypass of intended access-control gating implemented purely at the AA layer, and inconsistent treatment of the same condition compared to the address-definition-level `attested` operator — a functional security regression that mirrors the ZITADEL bug class (an identity/authorization link persists despite a state change that should have invalidated it).

### Likelihood Explanation
Reachable by any unprivileged unit poster: triggering an `address_definition_change` on an already-attested address is a normal, always-available operation, and any AA author can (intentionally or not) rely on `$attestation[...]` for access control since it is a documented, commonly used oscript primitive. No special privileges beyond posting units and interacting with an AA that uses this primitive are required.

### Recommendation
Modify the `'attestation'` case in `formula/evaluation.js` to mirror `storage.filterAttestedAddresses`: join against `address_definition_changes` for the attested address and require the attestation's `main_chain_index` (or unstable equivalent ordering) to be strictly after the address's most recent definition change, for both the unstable-AA-unit branch and the stable-unit branch of the query.

### Proof of Concept
1. Deploy an AA that grants a benefit based on `{ if: "{$attestation[attestors='ATTESTOR', address=trigger.address]}", ... }` (e.g. releasing funds only to KYC'd addresses).
2. Have `ATTESTOR` attest address `A` (owned by legitimate user U1).
3. U1 posts an `address_definition_change` for `A`, transferring control to attacker-controlled keys (e.g. sells the address, or a multisig co-signer defects).
4. Attacker, now controlling `A`, triggers the AA from address `A`; `$attestation[...]` still returns the stale attestation truthy/field value because the query in `formula/evaluation.js:966-1006` performs no `address_definition_changes` check, letting the AA release the gated benefit to the attacker despite the attestation no longer applying to the current controller.
