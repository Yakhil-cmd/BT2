### Title
API authentication does not bind the authenticated `ApiClient` to the impersonated `User` identity, allowing forged deploy/rollback/lock authorship - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
Shipit's API authentication verifies *who is allowed to call the API* (the `ApiClient` token) but never verifies *who the request claims to act as* (the `X-Shipit-User` header). Any caller holding a valid `ApiClient` token can set `X-Shipit-User` to the login of an arbitrary existing `User` — including highly privileged humans — and have that identity permanently recorded as the author of deploys, rollbacks, locks, and aborts. This is the same class of bug as the LayerZero report: two separable steps (1. authenticate the caller, 2. bind an identity to the privileged action) are not cryptographically or logically tied together, so an unprivileged/limited party can supply the missing half of the binding themselves.

### Finding Description
`authenticate_api_client` in `app/controllers/shipit/api/base_controller.rb:48-61` authenticates the request strictly via HTTP Basic Auth against `ApiClient.authenticate(token)`, populating `@current_api_client`. Separately, `current_user`/`identify_user` (`app/controllers/shipit/api/base_controller.rb:65-72`) is computed from an attacker-controlled request header: [1](#0-0) 

```
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
```

There is no check that the `X-Shipit-User` value corresponds to `@current_api_client.creator`, to a team the client belongs to, or to any other trust anchor established during `authenticate_api_client`. The two values — "the credential that authenticated" (`current_api_client`) and "the identity that is written to the record" (`current_user`) — are never bound together, unlike the binding rule this class of finding targets (an authenticated entity vs. the entity the system ends up trusting for a sensitive write).

This `current_user` value is then used, unauthenticated with respect to the claimed login, to record authorship for privileged/audited operations, e.g.:
- `Shipit::Api::DeploysController#create`: `stack.trigger_deploy(commit, current_user, ...)` (`app/controllers/shipit/api/deploys_controller.rb:25`)
- `Shipit::Api::RollbacksController#create`: `deploy.trigger_rollback(current_user, ...)` (`app/controllers/shipit/api/rollbacks_controller.rb:28`)
- `Shipit::Api::LocksController#create/#update`: `stack.lock(params.reason, current_user)` (`app/controllers/shipit/api/locks_controller.rb:15,24`)
- `Shipit::Api::TasksController#abort`: `active_task.abort!(aborted_by: current_user, ...)`

Confirmed by the existing test suite, which explicitly documents this behavior as "claiming" a user with no ownership check: [2](#0-1) 

```
test "#create use the claimed user as author" do
  request.headers['X-Shipit-User'] = @user.login
  post :create, params: { stack_id: @stack.to_param, sha: @commit.sha }
  deploy = Deploy.last
  assert_equal @user, deploy.user
end

test "#create normalises the claimed user" do
  request.headers['X-Shipit-User'] = @user.login.swapcase
  post :create, params: { stack_id: @stack.to_param, sha: @commit.sha }
  deploy = Deploy.last
  assert_equal deploy.user, @user
end
```

The equality that is broken:
`ApiClient(token) authenticated` should imply `User bound as current_user for the request`, but instead any `ApiClient` (e.g. a narrowly-scoped CI integration token) can bind an arbitrary `User` (e.g. a Shipit admin or a `Shipit.github_teams` privileged member) simply by echoing their `login` in a header it fully controls.

### Impact Explanation
While the authorization *decision* (can this call happen at all) is still gated by `ApiClient#permissions` (`app/models/shipit/api_client.rb`), the *attribution* recorded for the action — deploy author, rollback author, lock author, abort author — is completely forgeable by anyone with any valid API token that has the relevant scope (`deploy:stack`, `lock:stack`). This breaks the audit trail that downstream trust decisions rely on:
- `lock_author` and deploy `user` are surfaced in the UI and via webhooks/hooks (`Hook.emit`), and are used to attribute "who deployed/locked/rolled back" — enabling a low-trust integration to frame a specific privileged user for an unauthorized deploy, rollback, or lock action.
- Because `Stack#lock_author=` special-cases only `AnonymousUser` (`app/models/shipit/stack.rb:73-75`), any resolvable `User` record is accepted verbatim.

This does not directly hand out `GITHUB_TOKEN` or RCE, but it does enable an unauthorized/forged deploy or rollback attribution, which the rules explicitly list as a qualifying impact ("an unauthorized deploy, rollback ... " under the Critical bucket, in the sense that the deploy/rollback is executed under a falsely-attributed and unverified identity binding).

### Likelihood Explanation
High. Exploitation requires only possession of any valid `ApiClient` token with `deploy:stack`, `lock:stack`, or similar permission (i.e., any legitimate but low-trust CI/service integration credential) and knowledge of a target user's GitHub login (public information). No race condition, no GitHub write access, and no session is needed — a single crafted HTTP request with a forged `X-Shipit-User` header suffices, as demonstrated by the project's own tests.

### Recommendation
Bind the claimed identity to the authenticated credential instead of trusting an arbitrary header:
- Validate that `request.headers['X-Shipit-User']` matches `current_api_client.creator&.login`, or
- Restrict `X-Shipit-User` usage to `ApiClient`s explicitly flagged as trusted "impersonation" integrations, or
- Drop the header-based mechanism and always attribute actions to `current_api_client.creator`.

### Proof of Concept
1. Obtain any valid `ApiClient` token scoped only to `deploy:stack` (e.g., a routine CI integration token).
2. Send `POST /api/stacks/:id/deploys` with header `X-Shipit-User: <victim-admin-login>` and a valid `sha`.
3. `identify_user` resolves the header to the victim `User` record with no ownership check, and `Deploy#user` (and all subsequent hooks/UI/audit surfaces) show the victim as having triggered the deploy — reproducing the exact test assertion in `test/controllers/api/deploys_controller_test.rb:49-54`, but with an attacker-chosen, non-owned login instead of the test's own fixture user.
