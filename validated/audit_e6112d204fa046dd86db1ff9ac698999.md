### Title
Cross-repository commit status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming `status` webhook purely by `Commit.where(sha: params.sha)`, with no filter on the repository that authenticated the webhook. Any commit row in any stack across the entire Shipit instance that happens to share that SHA receives the attacker-supplied status, which can flip `deployable?`/`blocked?` for a victim stack.

### Finding Description
The broken binding is: **`commit.stack.repository.full_name` should equal `payload.repository.full_name` before a status is written**, but the code never checks this.

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit#create_status_from_github!` unconditionally records the status and re-evaluates deployability/blocking state via `add_status`, which triggers `stack.schedule_merges` when the new status is `success` or `pending`: [2](#0-1) [3](#0-2) 

`Commit` rows are scoped to a `stack` (`belongs_to :stack`), and `stack.deployable?`/`blocked?` logic keys directly off the attached statuses, so a written status for `ci/kubernetes` with `state: success` on a matching-SHA commit in a different stack directly changes that stack's deployability without any check that the webhook signature/payload's `repository` field matches the stack's repository: [4](#0-3) [5](#0-4) 

GitHub webhook signature verification (`verify_signature`/HMAC) only proves the payload came from *a* configured GitHub App/repository installation — it does not scope which stacks the payload's SHA may affect. Since `Commit.where(sha:)` has no `joins` to `Repository`/`Stack` and no comparison against `params` repository fields (the `params do ... end` schema for `StatusHandler` doesn't even declare a `repository` field to check against), any repository whose webhook is registered with Shipit can write a status for a commit SHA that also exists in a completely different repository/stack — most plausibly when `review_stacks_enabled: true, allow_all: true` auto-provisions per-PR review stacks from a shared upstream history, so PR branches and the base/victim stack can share commit SHAs. Because review stacks execute `shipit.yml` (deploy/build commands) once "deployable", this status flip can force an unauthorized deploy/merge decision on a stack the attacker never authenticated for.

No existing guard intercepts this: signature verification only authenticates that the request came from a registered GitHub webhook config, not which SHAs/stacks it is entitled to affect; `ExplicitParameters` only validates payload shape, not repository ownership; there is no `Repository` format validator invoked in this path.

### Impact Explanation
An attacker who controls (or can trigger) a `status` webhook for a repository they own — where a commit SHA coincides with a commit that also exists in a victim's stack (a real scenario under `review_stacks_enabled true, allow_all`, since fork/PR review stacks share upstream commit history with the base repo) — can write a forged `success` (or `failure`) status for `ci/kubernetes` that is applied to the victim stack's commit. This can make the victim stack `deployable?` (triggering `schedule_merges`/auto-deploy of `shipit.yml` tasks) or block it, i.e., "a payload for one repository mutating another's commit/stack," matching the **Critical** impact category (unauthorized deploy/merge triggered by a payload that did not authenticate for that repository).

### Likelihood Explanation
Preconditions: attacker needs a repository with a webhook registered to the same Shipit instance (which is the normal, low-cost setup for any repo onboarded to Shipit, including the attacker's own fork), and a victim stack with `review_stacks_enabled: true, allow_all: true` so PR-derived review stacks and shared upstream commits exist and require the `ci/kubernetes` context. Since review stacks are auto-provisioned from external PRs, shared SHAs between fork/PR commits and the target repo's stack are a realistic, attacker-influenceable condition (e.g., opening a PR that doesn't change the tip commit, or racing a shared merge-base SHA). The attack is fully repeatable — every `status` webhook execution re-runs the same unscoped query — and requires no privileged credentials, matching the "unprivileged attacker" model in the prompt.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository that authenticated the webhook, e.g.:
```ruby
def process
  Commit.joins(stack: :repository)
        .where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repository_name })
        .each { |commit| commit.create_status_from_github!(params) }
end
```
using the `payload`'s `repository.owner.login`/`repository.name` (as already available to other handlers such as `PushHandler`) instead of a bare, cross-tenant SHA match.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status for a SHA shared across repositories does not affect an unrelated stack" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(review_stacks_enabled: true, allow_all: true)
  victim_stack.update!(ignore_ci?: false)
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim commit")
  attacker_stack = shipit_stacks(:other) # different repository
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "attacker commit")

  before = victim_commit.reload.deployable?

  payload = {
    sha: shared_sha,
    state: "success",
    context: "ci/kubernetes",
    repository: { full_name: attacker_stack.repository.full_name } # attacker's own repo webhook
  }
  Shipit::Webhooks::Handlers::StatusHandler.new(payload:, delivery: "x").process

  after = victim_commit.reload.deployable?

  # binding under test: victim_commit.deployable? before == after
  assert_equal before, after,
    "status webhook authenticated only for the attacker's repository altered a commit belonging to a different stack"
end
```
This directly demonstrates the equality `commit.stack.repository == webhook.repository` is not enforced by `StatusHandler#process` — the victim commit's `success` status (and thus `deployable?`) changes even though the webhook payload's `repository` never matched the victim stack.
