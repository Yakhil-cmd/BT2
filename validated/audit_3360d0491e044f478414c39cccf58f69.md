### Title
Attacker-controlled `assets` registry lets `execute_strategy` invoke arbitrary contract code inside the caller's authorization tree, draining the caller's wallet - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
ALPINE-CVE-2019-3463 is an argument-sanitization failure: `rssh` forwards user-controlled arguments to `rsync`, and insufficient filtering lets restricted users escape into arbitrary shell command execution. The structural analog in this codebase is the swap router's route program. `execute_strategy` treats the caller-supplied `swap_xdr` as a restricted swap description, but the `assets` address registry inside it is never allowlisted. Every hop's `pool` and `token_in`/`token_out` addresses come straight from that registry, and the router `invoke_contract`s those addresses mid-execution — while the sender's `require_auth` tree is active. A crafted route therefore executes attacker-deployed contract code under the caller's authorization scope, bypassing the intended "one exact input transfer" restriction and letting the malicious pool transfer any wallet token out of the caller's account.

### Finding Description
`Program::validate` checks opcodes, modes, and index bounds only: `idx_a`/`idx_b`/`idx_c` must be `< assets_len`, meaning any address the caller puts in `assets` is accepted [1](#0-0) . `dispatch_hop` then builds a `HopContext` from that hop and calls a venue adapter [2](#0-1) . The adapters call the payload-named `pool` directly — e.g. `env.invoke_contract(pool, "swap", args)` for Aquarius [3](#0-2) , and Phoenix/Sushi/Comet/Soroswap do the same against `hop.pool`.

The router's only auth contribution is `sender.require_auth()` plus one nested `token_in.transfer(sender → router, total_in)`. Nothing constrains the callee set reachable below that entry, so a rogue pool's `swap` can execute `token.transfer(sender → attacker, N)`: the host records it as a child invocation of the sender's auth entry and simulation faithfully lists it. The test harness proves this end-to-end — `RogueHopPool::swap` transfers `victim → attacker` and, once the simulated tree includes that child, the call succeeds and the wallet is emptied [4](#0-3) [5](#0-4) . The threat model itself acknowledges the router "keeps no allowlist" and that "the loss is then the caller's wallet, not the routed amount" [6](#0-5)  — i.e. the restricted-operation invariant (pull `total_in`, swap, return ≥ `min_out`) is bypassed by unsanitized route arguments exactly as rssh's rsync restriction was bypassed by unsanitized rsync arguments.

### Impact Explanation
Theft of user funds. Any token balance in the caller's wallet (or in a composing contract's wallet, including a lending strategy contract) can be transferred out by a malicious pool contract, with loss bounded only by the wallet's balances — not by `total_in`, `min_out`, or any controller risk gate. The same `routeXdr` path is reachable standalone via `execute_strategy` and through every controller strategy verb (`multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`), since the controller forwards `swap` bytes without decoding them.

### Likelihood Explanation
An attacker crafts a valid route XDR whose `assets` contains a rogue pool contract that returns a fair-looking output (passing `ZeroOutput`/slippage checks) while also transferring wallet tokens. Exploitation requires the victim to sign the simulated authorization tree that includes the rogue `transfer` child. The protocol's defense is client-side verification (`verifyRouteBytes`/`verifyStandaloneEnvelope` only check pair/min-out/program shape, not pool identities), so wallets or integrators that sign whatever simulation returns — the common path — are exposed. That precondition and the documented threat-model treatment make this a Medium rather than a Critical/High: it is a real, code-level escape of the router's restricted-operation boundary, but it hinges on the signer not auditing child authorizations.

### Recommendation
Constrain what the router can invoke: maintain a governance-managed venue/pool allowlist (per venue opcode) and reject any `hop.pool` not on it, so third-party code can never sit below the sender's auth entry. Additionally, isolate the venue call from the caller's authorization — e.g. pull `total_in` into router custody, drop the sender's auth requirement before dispatching hops, or execute hops under a router-only auth context — so a rogue callee cannot piggyback `sender` transfers. At minimum, restrict the functions callable on allowlisted addresses to the expected `swap`/`get_tokens`/`share_id` signatures.

### Proof of Concept
```rust
// Attacker deploys this contract and inserts its address as `hop.pool`
// in the assets registry of a quoted route.
#[contractimpl]
impl RogueHopPool {
    pub fn swap(env: Env) {
        // Victim, wallet_token, attacker, amount stored at construction.
        let (victim, token, to, amount): (Address, Address, Address, i128) =
            env.storage().instance().get(&symbol_short!("PLAN")).unwrap();
        // Recorded as a child of the caller's auth entry; executes if
        // the simulated tree is signed as returned.
        token::Client::new(&env, &token).transfer(&victim, &to, &amount);
    }
}
```
Demonstrated in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: with the honest tree the rogue transfer is refused (`Unauthorized function call`); with the simulation-produced tree containing the rogue `transfer` child, `execute_strategy` succeeds and the victim's `WALLET_BALANCE` moves to the attacker.

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
