### Title
CCMenuController bypasses stack-scoped API-client authorization, allowing a token issued for one stack to read any stack's CI/build status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`ApiClient` records can be scoped to a single `Stack` via the `stack_id` column, and `Api::BaseController#stack` enforces this scoping by resolving the requested stack only from the client's own `stacks` relation (`Stack.where(id: current_api_client.stack_id)` when scoped). `Api::CCMenuController` overrides `#stack` and looks the stack up directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the scoping check, so any valid `read:stack` token — including one deliberately narrowed to a single stack — can be used to read the CI status of arbitrary other stacks by changing the `stack_id` URL parameter.

### Finding Description
`Api::BaseController` defines the canonical, scope-respecting accessor: [1](#0-0) 

`stacks` is restricted to the client's authorized stack when `current_api_client.stack_id?` is true, and `stack` resolves `params[:stack_id]` only within that restricted relation. This is the binding that is supposed to hold everywhere: `token.stack_id == stack acted upon`.

`Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 

It resolves the target stack straight from `Stack.from_param!(params[:stack_id])` — the full, unscoped `Stack` table — and only checks `require_permission :read, :stack` (a permission-name check, not a stack-identity check): [3](#0-2) 

`ApiClient#check_permissions!` only verifies the client has the `read:stack` permission string; it never compares `current_api_client.stack_id` against the requested `stack.id`: [4](#0-3) 

This exactly mirrors the report's bug class: a "scoped" configuration/authorization value (here, `ApiClient.stack_id`, analogous to the report's per-asset `navProvider`) is meant to bind a credential to one specific resource, but a code path (`CCMenuController#stack`) treats the credential as if it applied uniformly to all resources, silently dropping the scope check.

Notably, the engine explicitly supports creating stack-scoped, single-purpose `read:stack` clients for this exact endpoint: [5](#0-4) 

The intended contract is: this token/URL is only good for reading the CI status of the one stack it was generated for. Because `CCMenuController#stack` bypasses the scoping relation, that contract is broken — an attacker in possession of one such CCMenu URL/token (these URLs are commonly embedded in third-party CI dashboards, IDE plugins, or shared semi-publicly since they carry the auth token as a query string) can enumerate and read the build/CI status, name, last build label, and web URL of every other stack in the installation, not just the one it was minted for.

### Impact Explanation
This is a stack-scope escalation: a credential authorized (and believed by its issuer) to read exactly one stack's state can instead read the state of every stack, matching the report's "impact must be... unauthenticated read of stack state" (or the "escalation into ... authorization" bucket, since the token's own declared authorization boundary — its `stack_id` — is bypassed). It discloses stack names, environments, and deploy/CI status across the whole Shipit installation to a party who was only supposed to see one stack.

### Likelihood Explanation
Exploitation requires only a valid `ApiClient` authentication token with `read:stack` permission scoped to any single stack (such tokens are routinely generated and distributed via `CcmenuUrlController#fetch`, embedded as plaintext query parameters in URLs meant for external CI dashboard tools). No privileged account, GitHub credentials, or webhook secret is required — the attacker only needs one such already-issued, narrowly-scoped token/URL, then simply changes the `stack_id` in the request to a different stack.

### Recommendation
Remove the `CCMenuController#stack` override, or make it explicitly check that the requested stack matches the scoping used by `Api::BaseController#stacks`/`#stack` (i.e., raise/`404` unless `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id`), so `read:stack` permission checks are always paired with the stack-identity scope check already enforced elsewhere in the API.

### Proof of Concept
1. As an authenticated Shipit user, request a CCMenu URL for Stack A via `GET /stacks/A/ccmenu_url` (`CcmenuUrlController#fetch`), obtaining a token whose `ApiClient` row has `stack_id = A.id` and `permissions = ['read:stack']`. [6](#0-5) 
2. Use the same token against the CCMenu endpoint for a different stack B: `GET /api/stacks/B/ccmenu.xml?token=<token>`.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully; `require_permission :read, :stack` passes because the client has `read:stack`; `#stack` resolves `Stack.from_param!('B')` with no ownership check. [7](#0-6) 
4. The response renders Stack B's CI project status (name, activity, last build status/label, URL) even though the token was issued and intended solely for Stack A — confirming the scope bypass.

Note: I was unable to find an existing automated test exercising cross-stack access on this endpoint (the visible `ccmenu_controller_test.rb` only tests same-stack access and the unscoped `spy` client), so this analysis is based on direct code-path review rather than an observed failing test; a background agent with full repo/test access should add a regression test asserting `here_come_the_walrus` (scoped to stack `shipit`) is rejected when requesting `ccmenu` for a different stack.
