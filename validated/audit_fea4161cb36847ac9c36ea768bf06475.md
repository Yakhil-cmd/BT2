### Title
Hand-rolled YAML frontmatter parser silently drops indented `action: block` keys, downgrading deny rules to default `warn` - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` implements a hand-rolled, indentation-sensitive YAML-like parser instead of using a real YAML library. Top-level keys are only recognized when `indent == 0` [1](#0-0) , and any line with `indent` of 1 or 2 that is not part of an in-progress list/dict falls through all branches and is silently discarded with no error or warning. If an `action: block` line in a `.claude/hookify.*.local.md` rule file happens to carry 1-2 leading spaces (e.g., from copy/paste, template reuse, or crafted repository content), the key is dropped entirely and `Rule.from_dict` falls back to the default `action = 'warn'` [2](#0-1) , silently converting a deny rule into a non-blocking one while the file still visually reads `action: block`.

### Finding Description
`load_rule_file` reads the `.md` rule file and calls `extract_frontmatter(content)` to get a frontmatter dict, then constructs a `Rule` via `Rule.from_dict` [3](#0-2) . The parser processes lines in `frontmatter_text` and branches based on `indent`:
- `indent == 0` and `:` in line → top-level key/value [1](#0-0) 
- `stripped.startswith('-') and in_list` → list item [4](#0-3) 
- `indent > 2 and in_dict_item and ':' in line` → continuation of a multi-line dict item under a list [5](#0-4) 

There is no `else` branch and no error path for a line with `indent` of 1 or 2 that isn't inside a list context — such a line is simply skipped with zero feedback to the author or operator. Since `action` is a scalar top-level key that is expected at `indent == 0`, any accidental or crafted leading whitespace (1-2 spaces) on the `action: block` line causes it to be ignored. `Rule.from_dict` then falls back to `frontmatter.get('action', 'warn')`, defaulting to `'warn'` [6](#0-5) . The rule file visibly reads as a blocking rule, but the parsed `Rule.action` is `'warn'`, breaking the invariant that a deny rule must never be parsed into a non-blocking configuration. `load_rules` further swallows all parsing exceptions and only logs to stderr, meaning even outright malformed content produces no hard failure that would force the operator to notice discrepancies [7](#0-6) .

### Impact Explanation
Because `action` controls whether the hookify hook blocks a dangerous tool invocation or merely warns, a silently mis-parsed `action: block` line means a rule intended to block dangerous commands (e.g., `rm -rf`, destructive git operations) instead only warns or is treated as non-blocking. This is a genuine Security-control bypass: a rule author or reviewer inspecting the `.md` file would see `action: block` and reasonably assume enforcement is active, while the runtime hook never actually blocks the operation — silently disabling a blocking/permission boundary without any diagnostic output.

### Likelihood Explanation
Exploitability depends entirely on a hookify rule file entering the `.claude` directory with a subtly mis-indented `action` line — via copy-paste from indented examples/documentation, template reuse, AI-assisted rule generation through `/hookify configure`, or crafted content in ordinary repository files (e.g., a PR or template) that a user later adopts as a rule without noticing 1-2 stray leading spaces. No privilege escalation or file-write bypass is needed beyond what's already required to place any rule file, but the vulnerability specifically defeats an operator's visual/manual review of the file, since the parser gives no error and the difference (1-2 spaces) is easy to overlook.

### Recommendation
Replace the hand-rolled parser with a real YAML parser (e.g., Python's `yaml.safe_load`) for frontmatter extraction, or, if keeping the custom parser, add strict validation that rejects/errors on any line with non-zero, non-standard indentation instead of silently discarding it. Additionally, treat `action` field parsing failures as fatal for rule loading (raise instead of defaulting), so `action` never silently reverts to `warn` when the source explicitly specifies `block`.

### Proof of Concept
Unit test in `config_loader.py`'s test harness or a pytest module:
```python
content = """---
name: block-rm
enabled: true
event: bash
 action: block
pattern: "rm -rf"
---
Blocked!
"""
fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)
assert 'action' not in fm  # key silently dropped due to indent=1
assert rule.action == 'warn'  # should be 'block' per visible file content
```
Expected assertion failure demonstrates that the parsed `Rule.action` diverges from the visibly-authored `action: block`, confirming the deny-rule-downgrade behavior described in the invariant.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
