### Title
Cross-organization webhook signature confusion allows forged CI status to trigger unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an incoming webhook using the organization derived from the payload (`repository.owner.login` / `organization.login`), but none of the downstream event handlers verify that this same organization owns the repository/commit that the handler actually acts on. In particular, `Shipit::Webhooks::Handlers::StatusHandler` looks up commits **only by SHA, with no repository/stack scoping at all**, so a correctly-signed webhook from an organization the attacker legitimately controls in Shipit can inject a fabricated CI status onto a commit belonging to a completely different (victim) stack, which can trigger an unauthorized deploy via continuous delivery.

### Finding Description
`verify_signature` picks which GitHub App/secret to validate against based on the attacker-controlled JSON payload: [1](#0-0) [2](#0-1) 

Once the signature check passes (using the secret belonging to `repository_owner`, i.e. an organization that Shipit is configured for and whose webhook secret the requester therefore knows/controls if they are an admin of that org), the raw parsed payload is dispatched unchanged to the registered handlers: [3](#0-2) 

`StatusHandler` then updates the CI/deployment status of **any** commit in the system whose SHA matches the payload's `sha` field, with no check that the commit's repository/stack corresponds to the organization that was authenticated in `verify_signature`: [4](#0-3) 

This breaks the intended binding: *organization that authenticated the webhook (via its own webhook secret) == repository/stack whose data the webhook is permitted to mutate*. An entity that legitimately controls one Shipit-tracked GitHub organization (and thus knows/can compute that organization's webhook secret, exactly as the test suite does via `Shipit.github(organization: 'shopify')`) can sign a webhook payload whose `repository.owner.login` matches their own org (satisfying `verify_signature`) while its `sha` field references a commit belonging to an entirely different, victim stack. `Commit.where(sha: params.sha)` is a global, unscoped lookup, so the forged status is applied to the victim commit.

Applying a status is not cosmetic: `Commit#create_status_from_github!` ultimately drives the commit's deployability state, and stacks configured with `continuous_deployment` and a `release_status_context` trigger a real deploy once the required CI context transitions to `success`: [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who is a legitimate GitHub org admin for any organization already onboarded to this Shipit instance (and thus can register/know that org's webhook secret) can forge a signed webhook whose `repository` fields claim their own org, but whose `sha` targets a specific commit of a **victim** stack belonging to a different organization/repository. Since `StatusHandler` resolves commits purely by SHA with no ownership check, the attacker can inject a `success` status matching the victim stack's `release_status_context`, causing `trigger_continuous_delivery`/`ContinuousDeliveryJob` to ship that commit — an unauthorized deploy triggered purely by manipulating webhook content, without any repository write access, deploy token, or `ApiClient` permission on the victim stack. This matches the "unauthorized deploy" High-impact criterion.

### Likelihood Explanation
Requires the attacker to control (or register with a known secret) at least one organization/webhook config already recognized by the Shipit instance (`Shipit.github(organization: ...)`), and to know/predict the target commit SHA of the victim stack (commit SHAs of public repos are typically discoverable). Given multi-tenant Shipit deployments serving several organizations through one `/webhooks` endpoint, this is a realistic scenario and requires no privileged Shipit session, `ApiClient` token, or GitHub App private key — only the ability to send a signed webhook for an org one legitimately administers.

### Recommendation
In `StatusHandler` (and other handlers that look up records only by `sha`/global identifiers), scope the lookup by the repository derived from the webhook payload (as `Handler#stacks`/`repository_name` already does) and/or verify, after `verify_signature`, that the authenticated organization actually owns the commit's stack/repository before mutating any state. Do not treat "signature valid for org X" as authorization to write data belonging to a repository outside org X.

### Proof of Concept
1. Attacker legitimately administers org `attacker-org`, configured in Shipit with its own webhook secret.
2. Attacker learns/derives the SHA of a commit `deadbeef` belonging to victim stack `victim-org/victim-repo`, which has `continuous_deployment: true` and `release_status_context: "ci/travis"`.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, body:
   ```json
   {
     "sha": "deadbeef",
     "state": "success",
     "context": "ci/travis",
     "repository": { "owner": { "login": "attacker-org" } }
   }
   ```
   signed with `X-Hub-Signature` computed using `attacker-org`'s webhook secret.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, validates successfully against `attacker-org`'s secret.
5. `StatusHandler#process` executes `Commit.where(sha: "deadbeef")`, finds the victim commit (regardless of repository), and applies the forged `success` status, potentially causing `victim-org/victim-repo`'s stack to auto-deploy via continuous delivery.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
```
