## Title
Cross-organization Webhook Forgery via Payload-Controlled Signature Selection — Forged CI Status Enables Unauthorized Deploy ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against using a field taken from the *unverified* JSON body itself (`repository.owner.login`), rather than from the actual repository/stack the event will subsequently be applied to. Because `Shipit::Webhooks::Handlers::Handler#repository_name` (and `StatusHandler`, which doesn't even scope by repository) act on other payload-controlled fields (`repository.full_name`, `sha`) without re-checking that they belong to the organization whose secret produced the signature, an attacker who legitimately knows the webhook secret for *any* one organization configured in Shipit can forge events (push, status) that are applied to a *different* organization's stacks.

### Finding Description
`verify_signature` computes the organization to authenticate against purely from request-body content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns the `GitHubApp` (and its `webhook_secret`) configured for whatever organization name appears in the attacker-supplied `repository.owner.login` (or `organization.login`) field: [3](#0-2) 

Multi-org Shipit deployments configure a distinct `webhook_secret` per GitHub organization: [4](#0-3) 

An attacker who legitimately administers the GitHub App for `OrgOne` (i.e., knows `OrgOne`'s `webhook_secret` — this is not a Shipit credential, it's a secret set on a GitHub App the attacker created and owns) can freely craft the JSON body. Signature verification only checks that the body was HMAC-signed with `OrgOne`'s secret; it never checks that `repository.full_name`/`sha` used later actually belongs to `OrgOne`.

The event handler that is dispatched next derives the acted-upon repository from a *different, independently attacker-controlled* field of the same payload: [5](#0-4) 

`Repository.from_github_repo_name` looks up any repository/owner pair verbatim: [6](#0-5) 

`PushHandler` then acts on whatever `Stack`s belong to that (attacker-chosen) repository: [7](#0-6) 

Even worse, `StatusHandler` does not scope by repository at all — it matches purely by commit `sha` across the entire `commits` table: [8](#0-7) 

`sha`s of commits in a victim organization's public/private stack are frequently discoverable (visible in the Shipit UI, GitHub, PR links, etc.). The attacker forges a `status` webhook signed with their own org's secret, but with `sha` set to a real commit belonging to a victim stack in a completely different organization, `state: "success"`, and `context` matching whatever context the victim stack's `shipit.yml` requires. `Commit#create_status_from_github!` stores this directly as a real deploy-blocking status: [9](#0-8) [10](#0-9) 

`deployable?` only checks `success?` (derived from stored statuses) and lock/block state — it has no cross-check that the status genuinely originated from the victim's own GitHub repository/organization. If the victim stack has `continuous_deployment` enabled, this forged status directly triggers an unauthorized deploy: [11](#0-10) 

**Binding broken:** the organization whose secret authenticated the webhook request ≠ the repository/stack whose state the webhook handlers write to. Signature verification is bound to `payload.dig('repository','owner','login')`; the actual mutation is bound to `payload.dig('repository','full_name')` (for push) or bare `sha` with no owner check at all (for status) — both independently attacker-controlled fields of the same unauthenticated-origin body.

### Impact Explanation
This maps to "High — escalation into authorization, unauthenticated read/write of stack state" and potentially "Critical — unauthorized deploy" per the impact rubric:
- An attacker who owns/administers a GitHub App for any org onboarded to a shared multi-org Shipit instance can forge `status` events that mark arbitrary commits in *other organizations'* stacks as CI-successful, bypassing the CI gate that `deployable?` is meant to enforce, and — if continuous deployment is enabled — trigger an actual unauthorized deploy of that stack.
- It can also forge `push` events that force `sync_github`/re-evaluation on stacks belonging to organizations the attacker has no legitimate relationship with.

### Likelihood Explanation
Requires only that the attacker legitimately controls one GitHub App/organization already integrated with the shared Shipit instance (a realistic scenario for any self-service, multi-tenant Shipit deployment using the documented multi-org `secrets.yml` schema) and knowledge of a target commit sha and required status context (both are typically discoverable, e.g., via the public Shipit UI/GitHub). No Shipit session, API token, or repository write access on the victim org is required — only an HTTP POST to `/webhooks`.

### Recommendation
- Do not select the verification secret based on a field inside the unauthenticated payload alone; after verifying with the claimed organization's secret, re-validate that every payload field the handlers act on (`repository.full_name`, `sha`'s owning stack, etc.) actually belongs to that same, verified organization before dispatching to handlers.
- In `StatusHandler`, scope the `Commit` lookup to commits whose `stack.repository.github_repo_name` matches the payload's `repository.full_name`, and confirm that name matches the organization used for signature verification.
- Consider signing/verifying per-repository rather than per-organization where feasible, or cross-check `repository.owner.login` against the resolved `Stack`/`Repository`'s actual `owner` column before applying any mutation.

### Proof of Concept
1. Attacker is the administrator of a GitHub App for `attacker-org`, already configured in Shipit's multi-org `secrets.yml` (legitimate onboarding, e.g. a self-service SaaS-style Shipit instance). They know `attacker-org`'s `webhook_secret`.
2. Attacker identifies a commit `sha` belonging to `victim-org/victim-repo`'s Shipit stack (visible via Shipit's public UI) and the CI `context` string required by that stack's `shipit.yml`.
3. Attacker crafts a `status` webhook payload:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "<required-ci-context>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` → `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the signature validates successfully because it was legitimately produced with that org's own secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (no ownership check performed), and calls `create_status_from_github!`, marking it `success`.
7. If `victim-org/victim-repo`'s stack has `continuous_deployment: true`, `schedule_continuous_delivery` fires and the commit is deployed — an unauthorized deploy triggered entirely by an attacker with no relationship to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
