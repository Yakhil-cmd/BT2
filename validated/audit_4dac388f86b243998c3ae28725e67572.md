### Title
`StatusHandler#process` matches commits by SHA only, mutating commit status across repositories/tenants - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` and never restricts the lookup to the repository named in the webhook payload, even though the base `Handler` class provides `stacks`/`repository_name` helpers precisely for this purpose. Because Git commit SHAs are content-addressed and identical commit content produces an identical SHA in any repository, an attacker who owns/administers any repository that Shipit is also watching can cause a `status` webhook for their own repo to overwrite the GitHub status of an identical-SHA commit that belongs to a completely different tenant's stack.

### Finding Description
The broken binding is:
`Commit.where(sha: params.sha)` (LHS, what the code actually does) `==` `stacks.commits.where(sha: params.sha)` scoped by `repository_name = payload.dig('repository', 'full_name')` (RHS, what is required to bind the write to the authenticated repository).

Tracing the code:
- `Shipit::WebhooksController#create` dispatches the parsed JSON `params` to every registered handler for the event, after only `verify_signature`, which authenticates that the payload originates from GitHub for the organization named in the payload's own `repository.owner.login` — it says nothing about which *commit rows* the handler may touch: [1](#0-0) 
- `Handler` provides `stacks` and `repository_name` helpers, explicitly meant to scope lookups to the repository named in the payload: [2](#0-1) 
- `StatusHandler#process` ignores those helpers entirely and queries `Commit` globally by `sha`: [3](#0-2) 
- `Commit#create_status_from_github!` then writes the attacker-supplied `state`/`description`/`target_url`/`context` as a real status row and triggers `deployable?`/`schedule_continuous_delivery` side effects: [4](#0-3) [5](#0-4) 

Exploit flow: the attacker controls (or is a legitimate tenant of) a repository that Shipit also monitors. Since Git commit SHAs are a hash of commit content (tree, parent(s), author, committer, timestamps, message), the attacker can construct a commit object in their own repository that is byte-identical to a commit already tracked by another tenant's stack (e.g., copying a known/public commit, or the well-known empty-tree initial commit), producing the exact same SHA — no cryptographic collision is needed, just content replication. The attacker then triggers (or lets GitHub naturally emit) a `status` event on their own repo for that SHA (e.g., via the GitHub Status API on their own repository, which they fully control). `verify_signature` passes because the event genuinely originates from GitHub for the attacker's own organization/repository — signature verification authenticates the sender's tenant, not the target of the write. `StatusHandler#process` then matches and mutates every `Commit` row across all stacks/repositories sharing that SHA, including the victim's.

Why guards fail: `verify_signature` and `drop_unhandled_event` correctly gate *whether the event is processed*, but do nothing to gate *which records the event may modify*; `ExplicitParameters` only validates payload shape, not repository ownership; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
An attacker with control of any repository onboarded to a shared/multi-tenant Shipit instance can inject arbitrary commit statuses (`state`, `description`, `target_url`, `context`) onto another tenant's commit records for any SHA they can reproduce. This directly feeds `Commit#deployable?` and `#status`, which govern whether a commit is eligible for deploy/merge/continuous-delivery in the victim's stack — i.e., a payload for one repository mutating another repository's commit/stack state, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is fully repeatable against any SHA the attacker can reproduce and is not limited to a single victim stack.

### Likelihood Explanation
Preconditions: a multi-tenant Shipit deployment where the attacker legitimately controls at least one onboarded repository, and where a target commit's exact content (enabling identical-SHA reproduction) is available to the attacker (e.g., public commits, or trivially predictable content such as the canonical empty-tree commit). No Shipit secrets, sessions, or elevated GitHub permissions are required — only ordinary push/API access to the attacker's own repository. This is inexpensive and repeatable.

### Recommendation
Scope `StatusHandler#process` to the repository named in the webhook payload, mirroring the `stacks` helper already defined on `Handler`, e.g. iterate `stacks.commits.where(sha: params.sha)` instead of the bare `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (no live GitHub required):
1. Create two `Stack`/`Repository` pairs, `victim/repo` and `attacker/repo`.
2. Create a `Commit` under the victim stack with a known `sha` (e.g. `"4b825dc642cb6eb9a060e54bf8d69288fbee4904"`), asserting its initial status is unset/pending.
3. Build a `payload` hash with `'repository' => { 'full_name' => 'attacker/repo' }`, `'sha' => '<same sha>'`, `'state' => 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process` directly.
5. Assert: `victim_commit.reload.state == 'success'` even though `payload['repository']['full_name']` never referenced `victim/repo` — proving the sha-based lookup mutated a commit outside the authenticated repository, i.e. LHS (`Commit.where(sha:)`, global) != RHS (repository-scoped lookup via `stacks`).
