### Title
`ProxyType::is_superset` lattice violation lets a `NonTransfer` proxy escalate to `Sudo(Balances::*)` via a self-granted `SudoBalances` proxy - ([File: substrate/frame/staking-async/runtimes/rc/src/lib.rs])

### Summary
In `substrate/frame/staking-async/runtimes/rc/src/lib.rs`, the `ProxyType::is_superset` implementation uses a blanket rule `(ProxyType::NonTransfer, _) => true` [1](#0-0)  that declares `NonTransfer` a superset of every other proxy type, including `SudoBalances`. However, `ProxyType::filter` for `NonTransfer` explicitly denies the entire Sudo pallet ("Specifically omitting Sudo pallet") [2](#0-1)  while `SudoBalances`'s filter explicitly admits `Sudo(pallet_sudo::Call::sudo)` wrapping a `Balances` call [3](#0-2) . This is the identical bug class already found and fixed for `NonTransfer`/`Governance` on Asset Hub Westend (PR/prdoc `pr_12769.prdoc` [4](#0-3) ), but the equivalent `NonTransfer`/`SudoBalances` inconsistency in this `rc` runtime was not addressed.

### Finding Description
`pallet_proxy::do_proxy` gates `add_proxy`/`remove_proxy` sub-calls dispatched through an existing proxy relationship purely on `is_superset`, not on `filter`:
```
Some(Call::add_proxy { ref proxy_type, .. }) | Some(Call::remove_proxy { ref proxy_type, .. })
    if !def.proxy_type.is_superset(proxy_type) => false,
...
_ => def.proxy_type.filter(c),
``` [5](#0-4) 

This means a delegate holding a `NonTransfer` proxy can dispatch `Proxy::add_proxy { proxy_type: SudoBalances, .. }` on behalf of the real account as long as `NonTransfer.is_superset(SudoBalances)` returns `true` — which it does, unconditionally, in this runtime's blanket match arm [1](#0-0) . Once that new `SudoBalances` proxy exists, the same (or a colluding) delegate can call `Proxy::proxy` with `force_proxy_type: SudoBalances` and dispatch `RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(RuntimeCall::Balances(..)) })`, which `SudoBalances`'s filter explicitly admits [3](#0-2) . The invariant this violates is exactly the one from the CVE analog: a "session" with limited privileges (`NonTransfer`) is used to grant itself broader privileges and modify highly sensitive account state (Sudo-authorized Balances calls) without the actual authority (the real account's own signed re-confirmation of the escalation) ever being independently checked — the superset/filter lattice inconsistency substitutes for a missing re-authorization boundary.

Note: `pallet_sudo::Call::sudo` itself still requires the call to actually be dispatched by the configured `Key` (root) account at execution time inside `pallet-sudo`; but that check is against the *proxy real account* being sudo key, not against the delegate. If the real (delegator) account happens to be the chain's `Sudo::Key` — a scenario the proxy mechanism is explicitly designed to support (delegating sudo-adjacent balance operations to an operator) — then the escalation is real and lets a `NonTransfer` delegate reach sudo-gated Balances calls that its own filter was designed to deny.

### Impact Explanation
If the real/delegator account is (or later becomes) the runtime's `Sudo::Key`, a `NonTransfer` proxy delegate — who was only supposed to reach non-transfer, non-privileged calls — can add itself/another account a `SudoBalances` proxy and thereby execute privileged `Sudo(Balances::*)` operations (e.g., `force_set_balance`, `force_transfer`, `force_unreserve`) on behalf of the delegator. This is an unauthorized-dispatch / privilege-escalation class bug consistent with unbacked issuance or fund manipulation if reachable, matching the CVE's "modify critical security settings without re-authentication" pattern.

### Likelihood Explanation
Likelihood is constrained by two factors that could not be fully verified from the index alone:
1. Whether `substrate/frame/staking-async/runtimes/rc` is compiled into a live, deployed relay-chain runtime or is purely an integration-test/reference fixture (`substrate/frame/staking-async/integration-tests` references it) — if it is test/fixture-only, this is out of scope per the report's exclusion of "tests/mocks/generated" findings.
2. Whether any deployed instance of this runtime configures `Sudo::Key` to be a routinely-proxied account (sudo keys are typically not proxied in production for exactly this reason), which would be required for practical exploitation.

Given the uncertainty about deployment status of this specific `rc` runtime crate, and that the analogous Asset Hub Westend bug (a confirmed live-runtime instance of this exact lattice-violation class) was already found and patched via `pr_12769`, I cannot confirm this is a *new*, currently-live, in-scope vulnerability rather than a residual inconsistency in a staging/test runtime.

### Recommendation
Add the same regression coverage that was added for Asset Hub Westend (`proxy_type_superset_relation_matches_call_filters` [6](#0-5) , adjusted for repo name) to `substrate/frame/staking-async/runtimes/rc`, asserting that for every `(superset, subset)` pair where `superset.is_superset(&subset)` holds, every call admitted by `subset.filter` is also admitted by `superset.filter`. Concretely, either narrow `is_superset` to return `false` for `(NonTransfer, SudoBalances)` (and any other pair where `NonTransfer`'s filter denies calls the target type admits), or replace the blanket `(ProxyType::NonTransfer, _) => true` arm with an explicit, filter-consistent enumeration, mirroring the fix applied for `Governance` in `pr_12769.prdoc`.

A concrete PoC would require: (1) confirming `rc` runtime is a live/deployed target and identifying its bounty program, (2) building a FRAME test harness instantiating `pallet_proxy` + `pallet_sudo` + `pallet_balances` with this `ProxyType`, (3) granting account A a `NonTransfer` proxy for account B (where B = `Sudo::Key`), (4) dispatching `Proxy::proxy(A, B, None, Box::new(Proxy::add_proxy{delegate: A, proxy_type: SudoBalances, delay:0}))` and confirming it succeeds, then (5) dispatching `Proxy::proxy(A, B, Some(SudoBalances), Box::new(Sudo::sudo{call: Balances::force_set_balance{..}}))` and confirming it executes. This reproduction was not run in this session — the finding is based on static code-path analysis only, and deployment-status/eligibility for this specific runtime crate remains unverified.
