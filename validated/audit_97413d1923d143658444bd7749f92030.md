### Title
Webhook signature verification authenticates a different organization field than the one handlers use to select the repository/stack to write - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to verify the inbound signature against using `repository_owner`, which is read from the payload itself: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

However, once the signature (or lack of a signature requirement, see below) passes, the actual event handlers select the repository/stack to mutate using a *different* payload path, `payload.dig('repository', 'full_name')`, defined in the shared base `Handler`: [3](#0-2) 

The equality that is supposed to hold is: **the organization whose webhook secret authenticated this request == the organization that owns the repository whose stacks/commits get written**. In this engine, the first side is `repository.owner.login` (or `organization.login`) and the second side is `repository.full_name`'s owner segment. Both come from the *same* attacker-controlled JSON payload, but `GithubApp#verify_webhook_signature` short-circuits when no `webhook_secret` is configured for that organization: [4](#0-3) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Shipit explicitly documents `webhook_secret` as **optional** per configured GitHub organization (`docs/setup.md`, `config/secrets.development.example.yml`), and supports multiple GitHub orgs each with an independent `webhook_secret` (`Shipit.github(organization:)`, multi-org secrets fixture `test/dummy/config/secrets_double_github_app.yml`). In a legitimately configured multi-org deployment where at least one configured organization has no `webhook_secret` set (a documented, supported configuration), an unauthenticated network attacker can:

1. Craft an arbitrary JSON payload with `repository.owner.login` (or `organization.login`) set to the no-secret organization — this makes `verify_signature` skip the HMAC check entirely (`head(422) unless verified` is never triggered since `verified` is `true`).
2. Set `repository.full_name` inside the *same* payload to point at a **different, secret-protected** organization's repository.
3. POST this to `/webhooks` with any `X-Github-Event` header for an event whose handler is keyed off `repository.full_name` (e.g. `push`, `check_suite`, `pull_request` closed/labeled/opened, etc.), because signature verification and repository resolution use two different fields of the same untrusted body.

### Impact Explanation
Handlers gated only by `repository.full_name` perform state changes scoped to that repository's `Stack`s without any binding back to the organization that was actually authenticated:
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching the branch [5](#0-4) .
- `PullRequest::ClosedHandler#process` calls `review_stack.archive!` for review stacks resolved purely from `params.repository.full_name` [6](#0-5) .
- `CheckSuiteHandler#process` schedules check-run refreshes for commits of stacks resolved the same way [7](#0-6) .

This is a cross-repository write: a payload nominally "authenticated" for organization A (the one with no secret, or whose secret the attacker does not need) triggers writes/actions against organization B's repository/stack records because the `Handler#repository_name` lookup is never re-checked against the value used for signature/org selection in `WebhooksController#repository_owner`. This satisfies the required "organization authenticated vs. repository written" binding break and the "unauthorized deploy-adjacent state change / cross-repository writes" impact bar (stack archiving via forged PR-closed events, forced sync attempts, forced check-run refresh scheduling).

### Likelihood Explanation
This requires a specific but documented and supported deployment shape: multi-organization GitHub App configuration where at least one organization is configured with no `webhook_secret` (explicitly called "optional" in `docs/setup.md`). Given that shape, exploitation requires no credentials, no GitHub App key, and no prior session — only knowledge of the target's `/webhooks` endpoint and the victim organization's repository full name, both of which are public information. This is not a host-misconfiguration outside the documented feature set (the engine's own docs and example secrets files describe `webhook_secret` as optional per org, and multi-org configuration is a first-class supported feature with its own fixture/config file `test/dummy/config/secrets_double_github_app.yml`).

### Recommendation
Bind repository resolution to the same authenticated identity used for signature verification instead of re-parsing the payload independently in each handler:
- Pass the verified `repository_owner` (or the resolved `github_app`/organization) from `WebhooksController` into `Webhooks.for_event(event).each { |handler| handler.call(params) }`, and have `Handler#repository_name` validate that the owner segment of `payload.dig('repository', 'full_name')` matches the authenticated organization, rejecting the event (e.g., `422`) on mismatch.
- Alternatively, when a webhook secret is absent for an organization, do not treat the signature as "verified" for purposes of trusting payload-supplied repository ownership — require operators to either always configure a `webhook_secret` or restrict which organizations can be configured without one.

### Proof of Concept
Preconditions: multi-org config where `OrgWithoutSecret` has no `webhook_secret`, and `OrgWithSecret/private-repo` is a real Shipit-tracked stack.

```
POST /webhooks
X-Github-Event: pull_request
X-Hub-Signature: sha1=anything   # ignored, webhook_secret is nil for OrgWithoutSecret

{
  "action": "closed",
  "number": 1,
  "organization": { "login": "OrgWithoutSecret" },
  "repository": {
    "owner": { "login": "OrgWithoutSecret" },
    "full_name": "OrgWithSecret/private-repo"
  },
  "sender": { "login": "attacker" },
  "pull_request": {
    "id": 1, "number": 1, "url": "x", "title": "x", "state": "closed",
    "additions": 0, "deletions": 0,
    "head": { "sha": "deadbeef", "ref": "some-branch" },
    "user": { "login": "attacker" },
    "assignees": [], "labels": []
  }
}
```

`verify_signature` calls `Shipit.github(organization: "OrgWithoutSecret")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`), bypassing signature verification entirely. `PullRequest::ClosedHandler` then resolves `Shipit::Repository.from_github_repo_name("OrgWithSecret/private-repo")` and calls `review_stack.archive!`, an unauthorized state change on a repository whose organization the request was never actually authenticated for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
