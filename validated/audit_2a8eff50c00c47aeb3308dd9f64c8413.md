### Title
Webhook signature check is trivially bypassed when `webhook_secret` is unset, allowing unauthenticated forged GitHub events to escalate `Shipit.github_teams` authorization and spoof CI status - (File: `lib/shipit/github_app.rb`)

### Summary
The reported bug class is "handler accepts input from any sender because the trust check silently no-ops instead of enforcing an allow-list" (Solidity `receive()` accepting funds from anyone instead of only the bridge contract). The equivalent trust binding in this engine is: **"GitHub App has cryptographically verified this payload" == "the payload is trusted enough to mutate authorization state / CI status / deploy triggers."** `GithubApp#verify_webhook_signature` breaks this binding whenever an organization is configured without a `webhook_secret`, because it returns `true` unconditionally instead of rejecting the request.

### Finding Description
`Shipit::WebhooksController#verify_signature` is the only gate protecting the fully unauthenticated `/webhooks` endpoint (no session, no `ApiClient` token, no GitHub OAuth required): [1](#0-0) 

It delegates trust entirely to `GithubApp#verify_webhook_signature`: [2](#0-1) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If the organization resolved from the attacker-controlled `repository_owner` (taken straight from the unauthenticated JSON body, see `WebhooksController#repository_owner`) has no `webhook_secret` configured, **every payload is treated as verified regardless of the `X-Hub-Signature` header supplied**. The setup documentation explicitly labels this field "optional": [3](#0-2) 

Once "verified," the raw JSON body is dispatched unmodified to registered handlers: [4](#0-3) [5](#0-4) 

Two default handlers turn this forged, unauthenticated input directly into privileged state changes:

1. **`membership`** handler creates/removes `Membership` records from attacker-supplied `member`/`team`/`action` fields (seen exercised in `WebhooksControllerTest` at lines 129-181), and `User#authorized?` gates access purely on team membership: [6](#0-5) 
An attacker who forges a `membership` event adding an arbitrary (existing or self-created) `User` to a team listed in `Shipit.github_teams` escalates that identity into full Shipit authorization — this maps directly to the report's "High" bucket: *"escalation into `Shipit.github_teams` authorization."*

2. **`status`** handler writes `Status` records for any commit SHA from the unauthenticated body (`WebhooksControllerTest`, lines 42-59), and stacks with `continuous_deployment` enabled auto-trigger deploys once required statuses report success. Forging a `success` status for an arbitrary commit can therefore trigger an unauthorized deploy through the normal continuous-deployment path (`Stack#trigger_continuous_delivery` / `continuous_deployment?`), matching the report's Critical bucket ("unauthorized deploy").

### Impact Explanation
This breaks exactly the binding class targeted by the rules: *"an organization that authenticated versus the repository that is written"* — the code checks "does this org have a secret configured," and if not, treats the request as authenticated for that org's repositories anyway, rather than rejecting it. The downstream consequences reach both the High bar (`Shipit.github_teams` authorization escalation via forged `membership` events) and potentially the Critical bar (unauthorized deploy via forged `status` events on continuously-deployed stacks) defined in the validation rules, with zero credentials, no session, and no `ApiClient` token required — only knowledge of a configured repository/organization name, which is public.

### Likelihood Explanation
Likelihood is elevated because: the endpoint is intentionally exposed with no other authentication layer; the vulnerable code path is reached by simply *not* setting an optional config field, which the shipped documentation frames as a normal, supported configuration; and no attacker-side secret, session, or write access is needed — only an HTTP POST to `/webhooks` with a crafted JSON body and an arbitrary `X-Github-Event` header. The main mitigating factor is that operators who do set `webhook_secret` are unaffected, so exploitability is conditioned on that one omitted setting — matching the original report's moderate likelihood (3) with high impact (5).

### Recommendation
Change `GithubApp#verify_webhook_signature` (`lib/shipit/github_app.rb`) so that a missing `webhook_secret` fails closed instead of failing open, e.g. raise a configuration error or reject the request when `webhook_secret` is blank rather than `return true`. At minimum, `WebhooksController` should refuse to process events for organizations that have no `webhook_secret` configured, and the setup documentation should be updated to state that omitting `webhook_secret` disables all webhook authenticity checks (rather than presenting it as an inconsequential "optional" field).

### Proof of Concept
Given a Shipit deployment where an organization's `github` config in `secrets.yml` omits `webhook_secret` (as shown to be a supported configuration in `config/secrets.development.example.yml`, lines 8-16), an unauthenticated attacker can:

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": <id-of-authorized-team>, "slug": "developers", "name": "Developers", "url": "..."},
  "organization": {"login": "<target-org-without-webhook_secret>"},
  "member": {"login": "attacker-controlled-login"},
  "repository": {"owner": {"login": "<target-org-without-webhook_secret>"}}
}
```

Because `repository_owner` resolves to an org with no `webhook_secret`, `verify_webhook_signature` returns `true` for any (or no) `X-Hub-Signature` value (`lib/shipit/github_app.rb:76-83`), the request passes `WebhooksController#verify_signature`, and `Handlers::MembershipHandler` (dispatched via `Shipit::Webhooks.for_event('membership')`) creates the `Membership`, granting `authorized?` (`app/models/shipit/user.rb:80-82`) to the attacker-named user with no GitHub credentials ever presented.

*Note: I could not view the full contents of `app/models/shipit/webhooks/handlers/membership_handler.rb` and `app/models/shipit/webhooks/handlers/status_handler.rb` (index size limits truncated those files), so the exact field-by-field handler logic for `status`-triggered auto-deploy is inferred from `Stack#trigger_continuous_delivery`/`continuous_deployment?` references and the `WebhooksControllerTest` coverage rather than direct line citations of those two handler files. A Devin session with full repo access could confirm the precise status→auto-deploy trigger chain.*

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
