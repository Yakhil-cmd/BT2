### Title
Webhook signature verification selects the signing secret from an attacker-controlled field decoupled from the field handlers act on - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub organization's `webhook_secret` to validate an inbound webhook's HMAC against by reading `repository.owner.login` (or `organization.login`) straight out of the same untrusted JSON body it is about to authenticate. Handlers, however, resolve the target `Stack`/`Repository`/`Commit` to mutate using a *different* field of the same body, `repository.full_name` (or `sha`/`check_suite.head_sha`), which is never cross-checked against the field used to pick the secret. An attacker who legitimately controls the webhook secret for *any one* GitHub org configured in this Shipit instance can therefore forge a validly-signed webhook whose "acted-upon" repository field points at a completely different org/stack.

### Finding Description
The binding that should hold is: **"the organization whose secret authenticated the request" == "the repository/stack the request is permitted to mutate."** This binding is broken.

`verify_signature` chooses the app/secret with:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read from the raw request body itself — the very payload whose signature is being checked — not from any trusted, pre-verified source (e.g. a path/route parameter tied to a specific installation). Once `verify_signature` passes, `create` hands the *entire* JSON body to the registered handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [2](#0-1) 

Handlers resolve their target stack via `repository.full_name`, a field that is never compared to `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` uses that resolution to trigger a sync against the target stack:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

`StatusHandler` and `CheckSuiteHandler` are even less scoped — they match purely on `sha`/`head_sha` and `head_branch`, again values fully controlled by the attacker's own crafted (and self-signed) payload: [5](#0-4) [6](#0-5) 

Because `Shipit.github` is configured per-organization (multiple orgs, each with its own `app_id`/`webhook_secret`, as shown in the sample config) — [7](#0-6)  — any org admin who can install/configure this same shared Shipit app on their own org obtains a webhook secret of their own choosing under the code's trust model. Nothing forces the `repository.owner.login`/`organization.login` field used to select that secret to correspond to the `repository.full_name` (or `sha`) field that handlers use to decide what to mutate. An attacker can therefore:
1. Set `repository.owner.login` = their own org (`evil-org`), for which they know the `webhook_secret`.
2. Set `repository.full_name` = `"victim-org/victim-repo"` (or an arbitrary commit `sha` belonging to a stack tracked under a different org).
3. Sign the whole JSON body with `evil-org`'s webhook secret and POST it to `/webhooks`.

`verify_signature` selects `evil-org`'s `GithubApp`, validates the HMAC successfully (because the attacker legitimately knows that secret), and the request is accepted. The handlers then act on `victim-org/victim-repo` because that value was never bound by the signature check.

### Impact Explanation
This breaks the trust boundary between tenants of a multi-org Shipit deployment: signing with org A's secret should only authorize writes to org A's tracked repositories, but the code allows it to authorize writes to *any* repository/stack tracked anywhere in the same Shipit instance. Concretely reachable primitives include:
- Forcing `GithubSyncJob`/`stack.sync_github` to run against a victim stack on attacker-chosen `expected_head_sha` (`push` event).
- Injecting fabricated commit statuses via `StatusHandler` for arbitrary shas belonging to victim stacks, which can flip `ci.require` gating used to authorize deploys.
- Fabricating `check_suite` completion (`CheckSuiteHandler`) to trigger `schedule_refresh_check_runs!` on victim commits.
- Archiving/unarchiving review stacks or mutating `PullRequest` records for repositories owned by other orgs via the `pull_request` handlers, since those too key off `repository.full_name`.

Because gating status/CI checks feeds directly into whether Shipit permits a deploy/merge to proceed, this can escalate into an unauthorized deploy or merge, satisfying the "Critical: ... cross-repository writes, or an unauthorized deploy, rollback or merge" bar in scope.

### Likelihood Explanation
Requires an attacker who legitimately possesses a webhook secret for *some* org configured on the shared Shipit instance — no Shipit session, `ApiClient` token, repository write access to the victim, or GitHub App private key theft is needed. In any Shipit deployment servicing more than one GitHub organization (the documented, supported multi-org config shape), this is directly exploitable by any org admin among the tenants, entirely from the outside, over the unauthenticated `/webhooks` endpoint.

### Recommendation
Bind the secret-selection field to the field the handlers act on. Do not resolve the signing organization from a field read out of the same unauthenticated payload separately from the field used to identify the target repository; instead, derive both from a single canonical, pre-validated value (e.g. verify the signature per-installation using a route/path-scoped webhook endpoint, or require `repository.owner.login` == the owner portion of `repository.full_name` and reject if they diverge before dispatching to handlers).

### Proof of Concept
1. Attacker configures/administers `evil-org`'s installation of the shared Shipit GitHub App, obtaining `webhook_secret_evil`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": {"login": "evil-org"},
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_evil, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` selects `Shipit.github(organization: 'evil-org')`, HMAC matches, request passes.
5. `PushHandler#process` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: '<attacker chosen sha>')` on the victim's stack, even though the attacker has no relation to `victim-org`.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
