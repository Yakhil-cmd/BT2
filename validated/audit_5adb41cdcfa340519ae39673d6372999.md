### Title
`OpenedHandler#provision?` and `ReopenedHandler#unarchive?` bypass `repository.review_stacks_enabled` via operator-precedence bug - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb], [File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`LabeledHandler#respond_to_label_change?` correctly requires `repository.review_stacks_enabled && (archive? || unarchive?)` with explicit parentheses, but `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` write `review_stacks_enabled && provisioning_behavior_allow_all? || (label_disjunct_1) || (label_disjunct_2)` without wrapping the leading `&&` in parentheses. Because `&&` binds tighter than `||` in Ruby, `review_stacks_enabled` only gates the `provisioning_behavior_allow_all?` branch; the label-based disjuncts execute unconditionally of `review_stacks_enabled`.

### Finding Description
Binding claimed: `review_stacks_enabled` must gate provisioning identically in `LabeledHandler#respond_to_label_change?`, `OpenedHandler#provision?`, and `ReopenedHandler#unarchive?`.

- `LabeledHandler#respond_to_label_change?` (correct): [1](#0-0) 
This evaluates as `action=="labeled" && state=="open" && review_stacks_enabled && (archive? || unarchive?)` — `review_stacks_enabled` gates the whole disjunction.

- `OpenedHandler#provision?` (broken): [2](#0-1) 
Ruby precedence parses this as `(review_stacks_enabled && provisioning_behavior_allow_all?) || (provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)`. `review_stacks_enabled` is ANDed only with the first term.

- `ReopenedHandler#unarchive?` (same bug): [3](#0-2) 

`NullRepository` and `Repository` expose `review_stacks_enabled`, `provisioning_behavior_allow_with_label?`, etc. as plain booleans with no cross-cutting enforcement elsewhere: [4](#0-3) . Nothing in `ReviewStackAdapter#create!`/`unarchive!` re-checks `review_stacks_enabled` — it unconditionally creates/unarchives the stack and enqueues provisioning: [5](#0-4)  and [6](#0-5) .

Attack setup (attacker is the repository owner/maintainer of a Shipit-tracked repo, or a contributor able to open PRs and apply labels on their own fork/repo which is registered in Shipit with `review_stacks_enabled = false` but `provisioning_behavior = allow_with_label`, e.g. a leftover/misconfigured setting): open a PR, add the configured provisioning label, then trigger `opened` (initial creation) or `reopened` (close/reopen) webhook. `pull_request_has_provisioning_label?` becomes true, satisfying the middle disjunct, so `provision?`/`unarchive?` return `true` regardless of `review_stacks_enabled`, and `find_or_create!`/`unarchive!` execute, provisioning a stack (which triggers deploy/task pipelines driven by the repo's `shipit.yml`). The same PR/label state sent via the `labeled` event would be correctly rejected by `LabeledHandler`, proving the divergence.

No other guard intercepts this: `verify_signature`/webhook signature checks only authenticate that the payload came from GitHub for that repo (they don't enforce `review_stacks_enabled`), and there is no model-level validation on `Stack`/`ReviewStack` creation that re-checks the repository's `review_stacks_enabled` flag.

### Impact Explanation
For any repository configured with `review_stacks_enabled = false` and `provisioning_behavior = allow_with_label` (or `prevent_with_label`), a PR author able to add the trigger label and cause an `opened` or `reopened` event can force Shipit to create/unarchive a review stack and enqueue provisioning — an action that should have been globally disabled by the operator via `review_stacks_enabled = false`. This results in unauthorized deploy/task pipeline execution against that repository, driven by content in the PR branch. The blast radius is limited to repositories that have this specific (arguably unusual) combination of settings — `review_stacks_enabled=false` with a non-default `provisioning_behavior` — so it does not cross tenant/repository boundaries by itself, but it silently defeats the operator's explicit "review stacks disabled" control for any repo where the behavior setting isn't also reset to `allow_all`'s implicit default. This matches "unauthorized deploy" impact category, scoped to a repository whose operator disabled review-stack provisioning.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled = false` while `provisioning_behavior` is `allow_with_label` or `prevent_with_label` (not the default `allow_all`, which is unaffected since its disjunct is still correctly ANDed). The attacker needs only the ability to open a PR and apply/remove a label on it (or have PR labels visible/settable), which is available to any contributor with PR/label permissions on that repo — no Shipit credentials required. Cost is a single PR + label action, fully repeatable across PR numbers.

### Recommendation
Add explicit parentheses in `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` to make `review_stacks_enabled` gate the entire disjunction, matching `LabeledHandler`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

4. Build equivalent `labeled` webhook params with the same repository/label state; assert `LabeledHandler.new(params).send(:respond_to_label_change?) == false`, proving the two handlers diverge on identical repository/label state — the equality `review_stacks_enabled_gate(OpenedHandler) == review_stacks_enabled_gate(LabeledHandler)` fails.
5. Repeat steps 1–4 for `ReopenedHandler#unarchive?` with a `reopened` event.
6. Optionally assert `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter#find_or_create!` is invoked (e.g., via mocha expectation) in the `OpenedHandler#process` path despite `review_stacks_enabled == false`.

          def archive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no Stack exists. Ignoring."
              )
              return true
            end
            return if stack.archived?

            stack.remove_from_provisioning_queue
            stack.deprovision
            stack.archive!(user, *args, &block)
          end

          def unarchive!(*args, &block)
            if stack.blank?
              Rails.logger.info(
                "Processing #{action} event for #{repo_name} PR #{pr_number} but no ReviewStack exists. Creating."
              )
              return create!
            end
            return unless stack.archived?

            stack.transaction do
              Shipit::ReviewStackProvisioningQueue.add(stack)
              stack.unarchive!(*args, &block)
            end
          end
