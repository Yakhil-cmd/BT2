### Title
Cross-organization webhook forgery via mismatched `repository.owner.login` vs `repository.full_name` fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using the `organization` field taken from `repository.owner.login` (or `organization.login`), but every event handler that actually *acts* on the payload resolves the target `Stack`/`Repository` from the completely separate `repository.full_name` field. Nothing ties these two fields together, so a party who legitimately knows the webhook secret for *one* onboarded GitHub organization can forge a signed webhook whose `owner.login` matches that known organization while `repository.full_name` points at a *different* organization's repository/stack that is also configured in the same Shipit instance.

### Finding Description
The binding that should hold is:

`organization that authenticated (used to pick the webhook_secret) == organization that owns the repository being written (used to resolve the Stack/Repository that gets mutated)`

`verify_signature` picks the signing organization purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

Once the signature check passes, the raw `params` are handed unmodified to the registered handler for the event: [3](#0-2) 

Every handler, however, resolves which `Repository`/`Stack` to touch from the unrelated `repository.full_name` field, not `repository.owner.login`: [4](#0-3) [5](#0-4) 

`PushHandler` uses that `stacks` scope directly to trigger a GitHub sync using the attacker-controlled `after` SHA: [6](#0-5) 

`StatusHandler` writes a `Commit::Status` straight from the payload's `state`/`context`/`sha`, with no field cross-checking the signing organization at all: [7](#0-6) 

Because the code confirms only "was this raw body signed by *some* organization named in the body", and that organization name is one of the very fields inside the signed body, an attacker who is a legitimate (even unprivileged-with-respect-to-other-tenants) webhook operator for Organization A can craft:
```json
{
  "repository": { "owner": {"login": "org-a"}, "full_name": "org-b/target-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha already known/reachable>"
}
```
sign it with Organization A's `webhook_secret` (which `verify_signature` will happily fetch via `Shipit.github(organization: "org-a")` since `repository_owner` == `"org-a"`), and the signature will validate. The `PushHandler`/`StatusHandler`/pull-request handlers then act on `org-b/target-repo`'s `Stack`, which Organization A's operator has no legitimate authority over.

This is confirmed by the existing test suite, which shows the org lookup is driven purely by the payload and unrelated to which repo is mutated: [8](#0-7) 

### Impact Explanation
A party holding the webhook secret for one onboarded organization can forge events for stacks belonging to any other onboarded organization in the same Shipit deployment. Concretely this lets the attacker:
- Inject a fabricated `success` commit `Status` via `StatusHandler` for any tracked commit in another org's repository, bypassing CI gating checks used by `required_statuses`/`merge_request_required_statuses`.
- Trigger `GithubSyncJob`/merge-queue revalidation (`PushHandler`) and pull-request state transitions (open/close/label/archive review stacks) for a repository they do not own.
- Combined with `continuous_deployment` / merge-queue configuration, a forged passing CI status can enable an otherwise-blocked deploy or PR merge to proceed — i.e., an **unauthorized deploy or merge**, matching the Critical impact bar in the rules.

### Likelihood Explanation
The precondition — knowing one organization's `webhook_secret` while having no authority over a different organization hosted on the same Shipit instance — is realistic for any multi-tenant Shipit deployment (a common real-world setup, e.g. a shared internal deploy tool serving several teams/orgs). No GitHub App private key, `ApiClient` token, or Shipit session is required; only the ability to send an HTTP POST with a correctly-computed `X-Hub-Signature` for one org's known secret.

### Recommendation
In `WebhooksController#verify_signature` (or in the base `Handler`), require that the organization portion of `repository.full_name` matches `repository.owner.login` (or `organization.login`) before dispatching to any handler, and reject the webhook (422) on mismatch. Alternatively, resolve the target `Stack`/`Repository` in handlers using the same organization field that was used to select the signing secret, rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Attacker has legitimate GitHub App/organization-level webhook access for `org-a` (already onboarded to the Shipit instance), and thus knows/can compute `X-Hub-Signature` for `org-a`'s `webhook_secret`.
2. Attacker builds a `push` (or `status`) event payload where `repository.owner.login = "org-a"` but `repository.full_name = "org-b/target-repo"` (an org-b stack tracked by the same Shipit instance).
3. Attacker computes the `X-Hub-Signature` HMAC over the full raw body using `org-a`'s secret and POSTs to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` (from `repository.owner.login`) and validates successfully.
5. `PushHandler`/`StatusHandler` resolve the target `Stack` via `Repository.from_github_repo_name("org-b/target-repo")` and act on it (sync commits, or write a forged `success` `Status`), even though the attacker has no relationship with `org-b`.
