### Title
Uncaught exception in `chash.isChashValid` on malformed c-hash input causes unhandled crash — analogous to CVE-2016-5038 (`[File: chash.js]`)

### Summary
`chash.isChashValid()` only wraps the base32/base64 *decode* step in `try/catch`. The subsequent parsing of the decoded bytes into checksum/clean-data segments (`separateIntoCleanDataAndChecksum`) throws a raw, uncaught `Error` whenever the decoded buffer does not have the exact expected bit length (160 or 288 bits). Just like CVE-2016-5038 — where `dwarf_get_macro_startend_file` trusted a crafted string offset into `.debug_str` without bounds validation and crashed the parser — this code trusts that decoding a fixed-length, attacker-controlled string always yields a fixed-length buffer, and has no bounds/length guard around the offset-based slicing that follows.

### Finding Description [1](#0-0) 

```
function isChashValid(encoded){
	var encoded_len = encoded.length;
	if (encoded_len !== 32 && encoded_len !== 48)
		throw Error("wrong encoded length: "+encoded_len);
	try{
		var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
	}
	catch(e){
		console.log(e);
		return false;
	}
	var binChash = buffer2bin(chash);
	var separated = separateIntoCleanDataAndChecksum(binChash);   // <-- unguarded
	...
}
```

`separateIntoCleanDataAndChecksum` immediately throws if the bit-length of the decoded buffer isn't exactly 160 or 288: [2](#0-1) 

Only the *decode* call (`base32.decode`/`Buffer.from`) is wrapped in `try/catch`; if decoding succeeds but produces a buffer of an unexpected byte length (e.g., because the base32 library is lenient about characters outside `A-Z2-7`, or accepts padding it does not fully validate), `buffer2bin` produces a bit string whose length is neither 160 nor 288, and `separateIntoCleanDataAndChecksum` throws `Error("bad length=...")` **outside** the guarded block, propagating up as an uncaught exception.

This function is invoked from `ValidationUtils.isValidChash`, which itself feeds `isValidAddress` and `isValidAddressAnyCase`: [3](#0-2) 

`isValidAddress` short-circuits with a strict `/^[A-Z2-7]{32}$/` regex before calling `isValidChash`, which limits (but does not by itself formally prove) exposure for that specific call path. However, `isValidAddressAnyCase` calls `isValidChash` directly with only a length check (`isStringOfLength`) and **no character-set pre-filter**, so any 32-character string reaches `chash.isChashValid` regardless of its actual alphabet. Address/definition validation is performed on every posted unit for every author address, definition-referenced address, and related string fields throughout `validation.js` and `definition.js` (e.g. `arrAuthorAddresses.every(isValidAddress)` at [4](#0-3) ), none of which wrap these boolean-returning validity checks in `try/catch` — they expect a boolean, not an exception.

### Impact Explanation
An uncaught exception thrown deep inside a supposedly pure boolean-returning validator (`isChashValid` → `isValidChash` → `isValidAddress`/`isValidAddressAnyCase`) that is called synchronously from array iterators (`.every()`, `.filter()`) without surrounding `try/catch` will propagate up and crash the calling code path. In a Node.js process this typically results in an unhandled exception that terminates the process (or at minimum permanently breaks validation for that code path), which is a denial-of-service reachable by **any unprivileged unit poster** who can get a crafted address-like string into a field validated with the unguarded `isChashValid` path. If widely exploited across full nodes, this can render the network unable to validate/confirm new units — the same DoS impact class as the referenced libdwarf CVE, just triggered via unchecked buffer-length assumptions instead of unchecked string offsets.

### Likelihood Explanation
Medium: the primary `isValidAddress` gate is protected by a strict regex, so the most obvious exploitation path is closed. Exploitability depends on (a) confirming that the `thirty-two` base32 library can decode inputs outside `A-Z2-7` or with malformed padding into a buffer whose bit-length isn't 160, and (b) locating a concrete unguarded caller of `isValidAddressAnyCase`/`chash.isChashValid` reachable from a posted unit, AA trigger, or definition. I could not fully enumerate all callers of `isValidAddressAnyCase` within the available search budget, so this should be verified before treating it as fully confirmed.

### Recommendation
Wrap the entire body of `isChashValid` (not just the decode step) in `try/catch`, returning `false` on any parsing error, mirroring the defensive pattern already used elsewhere in the codebase (e.g., `merkle.verifyMerkleProof`'s `try/catch`). Additionally, audit and restrict all callers of `isValidChash`/`isValidAddressAnyCase` to first apply the same base32 alphabet regex used by `isValidAddress` before invoking `chash.isChashValid`.

### Proof of Concept
1. Identify (or add, for testing) a call site that invokes `ValidationUtils.isValidAddressAnyCase(str)` or `chash.isChashValid(str)` directly on a 32-character attacker-controlled string without prior regex filtering (e.g., a field in a unit/message processed via this helper).
2. Craft a 32-character string containing characters outside `A-Z2-7` (or malformed padding) that the `thirty-two` library decodes without throwing but into a buffer whose length is not exactly 20 bytes (160 bits).
3. Submit a unit/message containing this string to a node; when `chash.isChashValid` is reached, `separateIntoCleanDataAndChecksum` throws `Error("bad length=...")` uncaught by the caller, crashing or corrupting the validation flow for that unit — reproducible deterministically once a qualifying string and unguarded call site are confirmed.
