### Title
CCMenuController bypasses stack-scoped ApiClient restriction, allowing a stack-scoped token to read any other stack's status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one with `stack_id` set, e.g. fixture `here_come_the_walrus`) can only resolve stacks via `stacks.from_param!`, which restricts the query to `Stack.where(id: current_api_client.stack_id)`. `Shipit::Api::CCMenuController#stack` overrides this and calls `Stack.from_param!(params[:stack_id])` directly, completely skipping the `stacks` scoping helper, so a client scoped to stack A can be pointed at stack B's `stack_id` in the URL and successfully read its CCMenu status.

### Finding Description
The intended binding is: for any `ApiClient` with `stack_id` present, `resolved_stack.id == current_api_client.stack_id` must hold for every stack-resolving action.

- `Api::BaseController#stacks` enforces this: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `#stack` calls `stacks.from_param!(params[:stack_id])`. [1](#0-0) 
- `Api::CCMenuController` redefines `#stack` to bypass this scoping entirely: `@stack ||= Stack.from_param!(params[:stack_id])`, and it also overrides `authenticate_api_client` to accept the token via `params[:token]` in addition to Basic Auth. [2](#0-1) 
- `ApiClient.authenticate` only verifies the signature of the id embedded in the token and looks up the record by id; it performs no stack-binding check itself: `find_by(id: message_verifier.verify(token).to_i)`. [3](#0-2) 
- The fixture data confirms stack-scoped clients are a real, intended concept (`here_come_the_walrus` has `stack: shipit`, `permissions: [read:stack]`), distinct from the unscoped `spy` client. [4](#0-3) 

Exploit flow: an attacker who has obtained a valid token for a stack-scoped client (e.g., leaked from a status page, log, or a legitimately shared CCMenu URL) sends `GET /api/stacks/<other_owner>/<other_repo>/<other_branch>/ccmenu` with that token as the Basic Auth password (or `?token=`). `authenticate_api_client` in `CCMenuController` authenticates the client successfully (the signature is valid and the client exists), `require_permission :read, :stack` passes because the client does have `read:stack`, and `#stack` resolves the *attacker-chosen* stack via `Stack.from_param!` with no ownership check, returning stack B's build/deploy status even though the token's `stack_id` is stack A.

Existing guards do not catch this: `require_permission!` only checks the permission name, not the stack binding; the `#stacks` scoping exists but is never invoked in this controller.

### Impact Explanation
An attacker holding one previously-issued stack-scoped API token can read the CCMenu status (name, last build status/label/time, web URL) of any other stack on the same Shipit instance, not just the one the token was originally scoped to. This is a cross-repository confused-deputy read: the token's "stack" scope, which other endpoints enforce via `#stacks`, is silently ignored here. This matches the "unauthorized read of stack state" category. It is repeatable against arbitrary stacks by simply changing `stack_id` in the URL, with no rate limiting on the token itself.

### Likelihood Explanation
Preconditions: the attacker must possess one previously issued, valid API-client token that carries `read:stack` (any client credential leaked via a CCMenu URL, log, or similar). Note that the built-in `ccmenu_url_controller.rb` currently issues a single **unscoped** per-user "CCMenu Client" (no `stack` set) via `find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, so tokens generated through that specific UI flow are already global by design and not an example of this bug. However, the `ApiClient` model and fixtures show that stack-scoped clients are a first-class, supported configuration (created outside that UI, e.g. via console/seed, matching the `here_come_the_walrus` fixture), and any such token reaching this controller loses its scoping. Attacker cost is low once such a token is obtained; no GitHub or Shipit secret is required.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped lookup consistent with the rest of the API, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that clients with `stack_id` set are restricted to their own stack.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a stack-scoped client cannot read another stack's ccmenu status" do
  scoped_client = shipit_api_clients(:here_come_the_walrus) # stack: shipit, permissions: [read:stack]
  other_stack = Stack.create!(repository: Repository.new(owner: "other", name: "repo"), branch: "main")

  assert_not_equal scoped_client.stack_id, other_stack.id

  request.headers['Authorization'] = "Basic #{Base64.encode64(scoped_client.authentication_token)}"
  get :show, params: { stack_id: other_stack.to_param }

  # Binding under test: resolved stack.id must equal current_api_client.stack_id
  assert_response :not_found # currently fails: returns :ok, leaking other_stack's status
end
```
