### Title
Fork PR pull-request label names inject arbitrary env keys (e.g. `BASH_ENV`) into every executed step for a `ReviewStack` - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the stack's environment hash with no key allowlist, and this hash is unconditionally merged into `TaskCommands#env`, which is passed straight to `Command.new(..., env:)` and ultimately into `PTY.spawn(unbundled_env, ...)`. Since labels come verbatim from the webhook payload (`LabelCapturingHandler#capture_labels`), an unprivileged fork PR author can set an env-critical key such as `BASH_ENV` for every step Shipit runs on that review stack (deploy steps, `install_dependencies`, tasks) — not specifically the informational `review.checklist` text, which is never executed as a command.

### Finding Description
The claimed broken binding: `ReviewStack#env.keys` should be a subset of `deploy_variables.map(&:name)` (an explicit allowlist), but instead `ReviewStack#env.keys ⊇ {LABEL_NAME.upcase for every PR label}` with zero restriction: [1](#0-0) 

```
def env
  return super unless pull_request.present?
  super.merge(
    pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
  )
end
```

Labels reach `pull_request.labels` straight from the webhook body via `LabelCapturingHandler#capture_labels`, which persists `params.pull_request.labels.map(&:name)` with no schema restriction on the label string content (only that it's a `String`): [2](#0-1) 

`TaskCommands#env` (used by `DeployCommands`, `RollbackCommands`, and plain task execution) merges `@stack.env` unconditionally into the environment used to build every `Command`: [3](#0-2) 

That env hash flows straight into `Command.new(command_line, env:, ...)` for `perform`/`install_dependencies` steps: [4](#0-3) 

`Command#unbundled_env` merges `@env` (stringified, unfiltered) into `BASE_ENV`, and `Command#start` passes that hash directly to `PTY.spawn`: [5](#0-4) 

The existing allowlist guard, `EnvironmentVariables#permit`/`filter_deploy_envs`, is real but is applied only to the deploy's explicitly user-submitted `env` field (`Stack#build_deploy`, `DeploysController#deploy_params`) — never to `@stack.env`/`ReviewStack#env`: [6](#0-5) [7](#0-6) 

This is confirmed as intended-but-unbounded behavior by the existing test asserting arbitrary label names become env keys with no filtering: [8](#0-7) 

**Important caveat regarding the specific target named in the question**: `review.checklist` (`DeploySpec#review_checklist`) is a purely textual, non-executable array of strings rendered on the deploy page for human review; it is never passed to `Command`/`PTY.spawn`. [9](#0-8) 
The question's premise that "the `review.checklist` step inherits `BASH_ENV`... before running a non-interactive `shipit.yml` step" does not correspond to a real execution path — there is no `review.checklist` step that spawns a process. The exploitable env-injection path exists, but through the executed `deploy`, `install_dependencies`, and task steps (`TaskCommands#perform`/`#install_dependencies`), not `review.checklist`.

I was also unable to fully confirm (given tool/iteration limits) whether `Command#start`'s `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` invocation shape (single joined string vs. argv array) actually causes bash to consult `BASH_ENV` on this host's `/bin/sh`/`/bin/bash` — that depends on `parse_arguments`/`interpolated_arguments` producing a single shell string executed via `/bin/sh -c`, and on whether the target OS's `/bin/sh` is bash itself. This is a real uncertainty that a background agent/tester would need to verify with a live spawn test.

### Impact Explanation
An attacker who can open or label a pull request against a repository configured with `provisioning_behavior: allow_all` and `review_stacks_enabled: true` can set arbitrary uppercase env-variable names (e.g. `BASH_ENV`, `LD_PRELOAD`-style vectors are not applicable since PTY.spawn env is process-level, but `BASH_ENV`, `RUBYOPT`, `NODE_OPTIONS`, etc. are plausible) into the environment of every subsequent deploy/task step run for that specific review stack. This affects only that attacker's own review stack (their fork/branch), so blast radius is scoped to the one review stack's execution environment and any secrets/state reachable from within the app's working directory and the Shipit host during that stack's execution — this is a real Command/PTY.spawn env-injection primitive, matching the "Critical - RCE on the deploy host via Command/PTY.spawn" category if a working `BASH_ENV`-sourcing (or similar interpreter env hijack) vector is confirmed in the runtime deployment scripts actually invoked (e.g. `bundle exec cap ...`, `npm install`, etc., many of which do invoke a shell or a Ruby/Node interpreter honoring such env vars).

### Likelihood Explanation
Preconditions: repository must have `review_stacks_enabled` and `provisioning_behavior` set to `allow_all` (or `allow_with_label` with the label present), which are legitimate, documented, and commonly used configurations for open review-stack workflows. No secrets, tokens, or privileged roles are required — only the ability to open a PR from a fork and add/rename a label, which any GitHub user with fork access can do. This is fully repeatable per PR/label change and costs nothing beyond a GitHub account.

### Recommendation
Do not merge raw, attacker-controlled PR label names directly into the process environment. `ReviewStack#env` should either: (1) prefix all label-derived keys with a fixed, non-colliding namespace (e.g. `SHIPIT_LABEL_<NAME>`) so they can never shadow security-sensitive variable names like `BASH_ENV`, `PATH`, `LD_PRELOAD`, `RUBYOPT`, `NODE_OPTIONS`, `GEM_HOME`, etc.; and/or (2) run label names through `EnvironmentVariables#permit` against an explicit allowlist (e.g., only keys already declared in `deploy_variables`) before merging; and/or (3) strip/reject label names that collide with a denylist of interpreter/loader-affecting environment variables before upppercasing and merging them into `TaskCommands#env`.

### Proof of Concept
minitest plan (extends the existing `ReviewStackTest`/`TaskCommandsTest` pattern already in the repo):
```ruby
test "#env does not allow pull request labels to set BASH_ENV" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bash_env"]

  env = stack.env
  # Binding under test: env["BASH_ENV"] should never be attacker-settable
  assert_nil env["BASH_ENV"], "fork PR label should not be able to define BASH_ENV"
end

test "TaskCommands#env propagates label-derived BASH_ENV into spawned Command env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bash_env"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  command = Shipit::TaskCommands.new(task).perform.first
  # Demonstrates the value reaches Command#env, which feeds Command#unbundled_env -> PTY.spawn
  assert_equal "true", command.env["BASH_ENV"]
end
```
Both assertions currently fail on the "should not" expectation given the code shown above (`env["BASH_ENV"]` will be `"true"`), confirming the unguarded env-injection primitive exists for executed steps — though it exists via deploy/task steps, not via the specific `review.checklist` mechanism named in the question.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env

    end
