### Title
Cross-organization commit-status / stack forgery via webhook signature scoped to a different payload field than the one handlers act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a webhook against using `repository_owner`, taken from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). But the event handlers that actually execute the write (`StatusHandler`, `PushHandler`, and the `PullRequest::*` handlers) key their DB lookups off a *different* field of the same JSON body — `sha` alone, or `repository.full_name` — which is never cross-checked against the field used to select/verify the signature. When Shipit is configured with multiple GitHub organizations (a documented, supported configuration, see `docs/setup.md` "Using Multiple Github Applications") and any one of those organizations has no `webhook_secret` configured (explicitly documented as "optional"), `verify_webhook_signature` short-circuits to `true` for any payload claiming to be from that unsecured organization, regardless of the actual `X-Hub-Signature` header. An attacker can then set `repository.owner.login` to the unsecured org (to pass the trivial signature check) while setting `repository.full_name`/`sha` to reference a completely different, secured organization's tracked stack/commit, and the handler will act on it.

### Finding Description
- Signature check binds trust to `repository_owner`: [1](#0-0) [2](#0-1) 
- `verify_webhook_signature` trivially passes when the resolved org's `webhook_secret` is blank: [3](#0-2) 
- Multi-org config with per-org optional `webhook_secret` is a documented, first-class configuration: [4](#0-3) , and `Shipit.github(organization:)` resolves the app/secret purely from that same `repository_owner`-derived key: [5](#0-4) 
- Once `create` runs, the *entire raw payload* (not scoped by `repository_owner`) is dispatched to handlers: [6](#0-5) 
- `StatusHandler` never checks `repository` at all — it applies the status to any commit matching `sha` in the whole database: [7](#0-6) 
- `PushHandler`/pull-request handlers key their target Stack off `repository.full_name`, a sibling field of `repository.owner.login` inside the same object, never reconciled with the field used for signature scoping: [8](#0-7) [9](#0-8) [10](#0-9) 

The binding that should hold is: `organization authenticated by verify_signature (repository_owner) == organization/repository actually written to by the handler (repository.full_name / commit lookup by sha)`. This binding is never enforced — the two are read from independent, unauthenticated-relative-to-each-other fields of the same JSON body, exactly analogous to the report's `excessFeeRefundAddress`/`callValueRefundAddress` fields being read from `msg.sender` while the actually-affected L2 address is a different, uncovered value.

### Impact Explanation
If any configured GitHub organization in a multi-org Shipit deployment omits `webhook_secret` (an explicitly supported/"optional" setting per the setup docs), an unauthenticated network attacker can send a completely unsigned POST to `/webhooks` claiming `repository.owner.login`/`organization.login` = that unsecured org, and freely forge:
- Commit statuses for any commit/stack in the whole install (`StatusHandler`), including stacks belonging to unrelated, properly-secured organizations, since no repository check is performed at all.
- Push-triggered syncs, pull-request open/close/label events, and review-stack archive/unarchive actions for any repository whose `full_name` is guessed/known, by setting `repository.owner.login` to the unsecured org while `repository.full_name` points elsewhere.

This crosses the "organization authenticated versus the repository that is written" boundary and can be used to manipulate deploy-relevant state (commit statuses gating deploys, review-stack lifecycle, sync triggers) without possessing any of that target organization's credentials — this is an unauthenticated write into stack state for a different repository/org than the one whose (lack of) secret was checked.

### Likelihood Explanation
Requires only that the operator's multi-org configuration include at least one organization without a `webhook_secret` — a state the documentation itself presents as an acceptable, optional configuration, not a misconfiguration. No token, session, or secret of any kind is needed by the attacker; only knowledge of the target stack's `repository.full_name` (public information) or a target commit `sha`.

### Recommendation
In `WebhooksController#verify_signature`, and in every `Webhooks::Handlers::Handler` subclass, enforce that the field used to select/verify the webhook signature (`repository.owner.login` / `organization.login`) is the same field used to resolve the repository/stack/commit acted upon (`repository.full_name`), rejecting any payload where they diverge. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for an organization that has other organizations configured with secrets; require a `webhook_secret` for every configured organization, or scope commit/stack lookups in handlers strictly to the repository asserted by the verified organization.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `SecureOrg` (with `webhook_secret` set) and `OpenOrg` (with `webhook_secret` left blank), both tracked by Shipit stacks (per `docs/setup.md` multi-org section).
2. Send an unsigned POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<sha of a commit belonging to a SecureOrg-owned stack>",
  "state": "success",
  "organization": { "login": "OpenOrg" }
}
```
3. `repository_owner` resolves to `OpenOrg` (`app/controllers/shipit/webhooks_controller.rb:61`), `Shipit.github(organization: 'OpenOrg').verify_webhook_signature` returns `true` unconditionally because `OpenOrg`'s `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
4. `StatusHandler#process` then updates the commit status for the `SecureOrg` commit purely by `sha`, with no check that the commit belongs to `OpenOrg` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), forging a commit status for an organization whose secret was never presented.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
