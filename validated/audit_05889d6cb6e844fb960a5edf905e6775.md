### Title
Repository-owner/repository-name confusion in `WebhooksController#repository_owner` allows cross-organization webhook forging - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`repository_owner` falls back to `params.dig('organization', 'login')` whenever `repository.owner.login` is missing, even if `repository.full_name` is present and points to a different organization. This lets an attacker who controls the webhook secret of one onboarded GitHub organization ("org A") sign a payload that is verified against org A's secret while `repository.full_name` names a repository belonging to a different onboarded organization ("org B"), causing Shipit to execute the webhook handler against org B's stacks.

### Finding Description
The intended binding is: **the organization used to select the webhook secret for signature verification must equal the organization that owns `repository.full_name`**, i.e. `repository_owner == repository.full_name.split('/').first`.

`repository_owner` is defined as: [1](#0-0) 

The comment says the `organization` fallback is meant for payloads where `repository` is entirely absent, but the code only checks `params.dig('repository', 'owner', 'login')`. If `'repository'` is present but lacks an `'owner'` sub-key (while still carrying a `'full_name'`), the dig returns `nil` and the code falls through to `organization.login` — a field the attacker fully controls and that is unrelated to `repository.full_name`.

`verify_signature` then does: [2](#0-1) 

`Shipit.github(organization: repository_owner)` selects a per-organization `GitHubApp` (`app_id`/`installation_id`/`webhook_secret`) from `secrets.github`, confirming Shipit supports multi-organization configuration where each org can have its own webhook secret: [3](#0-2) 

Once verification passes, `create` dispatches the raw JSON payload — untouched — to the registered handlers: [4](#0-3) 

Every handler resolves its target repository purely from `payload.dig('repository', 'full_name')`, with no re-check against `repository_owner`: [5](#0-4) 

Exploit flow: an attacker who legitimately administers "org-A" (onboarded to this Shipit instance, e.g. because they set up their own GitHub App/webhook integration and know org-A's `webhook_secret`) sends:
```json
{"repository": {"full_name": "org-B/victim-repo"}, "organization": {"login": "org-A"}}
```
correctly HMAC-signed with org-A's secret. `verify_signature` resolves `repository_owner` to `"org-A"` via the fallback, verifies successfully against org-A's secret, and `create` then runs handlers (e.g. `PushHandler`, `StatusHandler`, `PullRequest::ClosedHandler`, `CheckSuiteHandler`) against `org-B/victim-repo`'s stacks — a repository the attacker has no relationship with and whose org's secret they never possessed.

No existing guard catches this: `drop_unhandled_event` only checks the event name; `ExplicitParameters` schemas in handlers only validate the shape of `repository.full_name`, not its ownership consistency with the org used for signature verification; there is no code anywhere that compares `repository_owner` to the owner segment of `repository.full_name`.

### Impact Explanation
This is a cross-tenant authentication bypass: a payload authenticated for organization A is accepted and processed against organization B's repository/stack. Depending on the registered handler for the event, this can archive/unarchive review stacks (`PullRequest::ClosedHandler`/`ReopenedHandler`), create commit statuses that gate deploys (`StatusHandler`), enqueue check-run refreshes, or trigger push-driven stack updates (`PushHandler`) for a repository/organization the attacker does not control. This matches the Critical category "a payload for one repository mutating another's stack" since the attacker forges provenance for org B using credentials only valid for org A. It is repeatable against any org pair configured on the same Shipit instance and does not require any Shipit session or API token.

### Likelihood Explanation
Requires: (1) Shipit configured with multiple GitHub organizations (`secrets.github` keyed by org, each with its own `webhook_secret`), which is an explicitly supported and documented configuration path in `Shipit.github_app_config`; and (2) the attacker legitimately controls org-A's webhook secret (e.g. as the admin/owner of an org that is itself onboarded to the same Shipit instance) while targeting a different onboarded org-B. This is not a single-org deployment issue but is realistic for any Shipit instance serving multiple organizations/tenants, which is the scenario the `organization.login` fallback code path was written for. Attacker cost is low: crafting one JSON body and computing one HMAC with a secret they already legitimately possess.

### Recommendation
Only use the `organization.login` fallback when the `'repository'` key is entirely absent from the payload, and when `repository` is present, require `repository.owner.login` to be present and non-empty — do not silently fall through to a different payload field. Additionally, after handler dispatch, verify that the org segment of `payload.dig('repository', 'full_name')` matches the `repository_owner` used for signature verification, rejecting the request otherwise.

### Proof of Concept
Minitest plan for `test/controllers/webhooks_controller_test.rb` (illustrative, not to be placed under `test/` per scope rules, but described for the fix's validation):
1. Configure `secrets.github` with two orgs, `org_a` (known `webhook_secret`, e.g. `secretA`) and `org_b` (`webhook_secret` `secretB`), each with a repository/stack fixture (`org_a/repo_a`, `org_b/repo_b`).
2. Build body: `{"repository": {"full_name": "org_b/repo_b"}, "organization": {"login": "org_a"}}` plus event-specific fields for e.g. `push`.
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1(`secretA`, raw body).
4. POST to `/webhooks` with `X-Github-Event: push`.
5. Assert: `repository_owner` (via `WebhooksController#repository_owner`) equals `"org_a"`, while the handler's `repository_name` (`payload.dig('repository','full_name')`) resolves to `"org_b/repo_b"` — i.e. assert these two values differ (the broken binding) and that the handler still executed against `org_b/repo_b`'s stack (e.g. assert a job/state change enqueued/applied for that stack) despite verification only ever touching `secretA`/`org_a`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
