### Title
Shared-memory allocation leak in `ExternalCheckWorker::check_batch` on address-lookup-table resolution failure or backpressure - ([File: core/src/banking_stage/transaction_scheduler/check_worker.rs])

### Summary
`ExternalCheckWorker::check_batch` allocates a `CheckResponseRegion` from the shared `rts_alloc::Allocator` before performing per-transaction checks, and `check_resolve_pubkeys` allocates further `SharablePubkeys` regions from the same allocator while resolving address-lookup-table (ALT) accounts. Both allocations are represented as plain POD structs (`CheckResponseRegion` / `SharablePubkeys`, offset+count only) with no `Drop`/RAII cleanup. Several early-return error paths in `check_batch` propagate errors via `?` without freeing these allocations, leaking shared-memory space that is only reclaimed by an explicit `allocator.free()` call.

### Finding Description
`check_batch` allocates a response region up front: [1](#0-0) 

This returns a raw `CheckResponseRegion` (an offset/count pair with no destructor) whose backing memory must be freed manually by the caller once it is no longer needed - it is only ever freed by explicit calls such as in test helpers (`CheckResponsesPtr::free`) or once the message is consumed by the other side of the shared-memory channel: [2](#0-1) 

After this allocation, `check_batch` calls `self.check_resolve_pubkeys(...)?` when `LOAD_ADDRESS_LOOKUP_TABLES` is requested: [3](#0-2) 

Inside `check_resolve_pubkeys`, for any transaction whose resolved account keys exceed its static keys (i.e., it uses an address lookup table - fully attacker-controlled via a submitted transaction's ALT usage), a second allocation is made from the same shared allocator, and if that allocation fails the function returns `Err(ExternalCheckWorkerError::AllocationFailure)` via `?`: [4](#0-3) 

When this error propagates back up through `check_batch`'s `?` on line 331, the function returns immediately - the `responses_ptr` / `CheckResponseRegion` allocated earlier at lines 285-289 (and any earlier successful `SharablePubkeys` allocations made for previous transactions in the same batch loop) are never freed. Additionally, the final `self.sender.try_write(...).map_err(...)?` at the end of `check_batch` can also fail if the outbound shaq queue to "Pack" is full/disconnected, again returning an error and leaking the already-populated `responses` region: [5](#0-4) 

This is structurally analogous to CVE-2017-7392: an operation allocates a buffer sized/triggered by client-controlled input (number of transactions / number of ALT-resolved pubkeys) before the operation is guaranteed to fully complete, and an error path returns without releasing that allocation, leaking memory in server-owned storage (here, the fixed-size shared `rts_alloc::Allocator` region instead of the process heap).

### Impact Explanation
The shared allocator backing this pipeline is a fixed-size arena (e.g., `allocator_size: 64 * 1024 * 1024` in tests/config). Repeated triggering of this leak by submitting transaction batches whose ALT-resolution allocation fails (once the arena is nearly full) or whose result cannot be flushed to the "Pack" component (queue full) will progressively exhaust the shared arena. Once exhausted, all subsequent `allocate_check_response_region` / `allocator.allocate` calls fail, degrading or halting the external check-worker pipeline used to validate/schedule incoming transactions on the leader - a validator/leader-side denial-of-service reachable purely from unprivileged transaction submission (crafting many transactions with lookup tables and driving allocator pressure). It does not directly cause fund movement, consensus divergence, or unsigned execution, so the impact is a resource-exhaustion/DoS on the leader's transaction-intake path rather than a fund-safety or consensus-safety violation.

### Likelihood Explanation
Reaching this bug requires driving the shared allocator into a state where either the `SharablePubkeys` allocation for ALT-resolved accounts fails, or the `check_worker_to_pack` shaq queue is full/disconnected, while a batch is being processed by `ExternalCheckWorker::check_batch`. Both are plausible under sustained load from an unprivileged sender submitting many transactions that use address lookup tables (which any user can construct), but require the allocator/queue to already be under pressure (i.e., the leak is not triggered by a single trivial transaction in isolation - it requires the shared memory region to already be significantly consumed). This makes it a real but load-dependent bug, more of a slow-leak/DoS amplifier than an immediately exploitable one-shot bug.

### Recommendation
Wrap the response-region and pubkeys allocations in RAII guards (types that free the corresponding allocator offset on `Drop`) so that any error path - including the `?` propagations in `check_batch` and `check_resolve_pubkeys` - automatically frees prior allocations. Alternatively, use a scope-guard/`Drop`-based cleanup for `responses_ptr` at the top of `check_batch` that is disarmed only once the response is successfully handed off via `self.sender.try_write`, and similarly track and free any `SharablePubkeys` allocations made for earlier transactions in the batch before returning early from `check_resolve_pubkeys`.

### Proof of Concept
1. Configure/observe a validator running with the external scheduler pipeline (`agave_scheduler_bindings`/`agave_scheduling_utils`), where `rts_alloc::Allocator` has a fixed size (e.g., 64 MiB per handle as used in tests).
2. Submit a sustained stream of transactions that reference address lookup tables (causing `check_resolve_pubkeys` to allocate `SharablePubkeys` per transaction) while also generating enough total transaction throughput to keep the shared allocator near capacity and/or the `check_worker_to_pack` queue backed up.
3. When the `self.allocator.allocate(...)` call inside `check_resolve_pubkeys` (line ~406) fails due to allocator pressure, `check_batch` returns `Err(AllocationFailure)` without freeing the `CheckResponseRegion` allocated at the top of the function (and without freeing pubkeys allocations from earlier transactions in the same batch).
4. Repeating this pattern steadily leaks allocator capacity; over time `allocate_check_response_region` calls begin failing entirely, degrading transaction check/scheduling capability for all subsequent transactions - reproducible by unit-testing `ExternalCheckWorker::check_batch` with an allocator sized just large enough to succeed on the first allocation but fail on the second, and observing that `self.allocator`'s available space does not recover after the error is returned.
