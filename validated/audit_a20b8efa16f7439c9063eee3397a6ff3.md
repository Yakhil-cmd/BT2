Based on the investigation, I found a concrete analog that matches the required bug class: an unprivileged-attacker payload field that is used to select/verify a cryptographic binding, while a *different* field of the same untrusted JSON body is later used to determine what is actually acted upon.

### Title
Webhook signature is verified against an attacker-chosen organization key that is decoupled from the repository actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate an inbound webhook's HMAC against using `repository_owner`, taken from `params.dig('repository','owner','login')` (or `organization.login`) of the **unverified** JSON body. [1](#0-0) [2](#0-1)  Shipit explicitly supports configuring one GitHub App/secret per organization, keyed by that same organization login. [3](#0-2) [4](#0-3) 

### Finding Description
The HMAC check only proves that the request was signed with *some* configured organization's secret — specifically whichever organization's secret corresponds to `params['repository']['owner']['login']`, a value read straight out of the attacker-supplied JSON body before any authentication has occurred:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

Because Shipit resolves the `GitHubApp`/secret purely from that one field, an attacker who has installed their own (unprivileged) GitHub App on their own organization — a self-service action documented in `docs/setup.md`'s "Using Multiple Github Applications" section — knows their own organization's `webhook_secret` and can compute a valid `X-Hub-Signature` for any raw body they choose. [6](#0-5)  The equality the engine relies on is:

`organization whose secret validated the signature == organization/repository that the event handler subsequently acts on`

This equality only holds if every downstream handler re-derives the target repository from the *same* `owner.login` field used for verification. However, the payload's `repository` object independently carries a `full_name` (e.g. `"owner/repo"`) which is the field Shipit's repository-matching logic is built around, as shown by its pervasive use across handler and model code (`app/models/shipit/repository.rb`, `push_handler.rb`, `status_handler.rb`, `handler.rb`, and all fixture payloads). Since JSON objects are attacker-controlled end-to-end (this endpoint parses `request.raw_post` directly with no schema enforcement tying `full_name` to `owner.login`), an attacker can send a body where:
- `repository.owner.login` = `attacker-org` (used to pick the verifying secret — attacker's own, valid)
- `repository.full_name` = `victim-org/victim-repo` (used by the handler to locate the actual `Stack`/`Repository` to update)

`Shipit.github(organization: repository_owner)` never checks that the resolved organization actually owns the repository referenced elsewhere in the same payload; it only needs `repository_owner` to map to *any* configured org. [7](#0-6) 

### Impact Explanation
If confirmed against the exact field-parsing performed by handlers such as `PushHandler`/`StatusHandler`/`CheckSuiteHandler` (full content of `handler.rb` was not retrievable in this session), this allows an attacker who only controls their own GitHub organization/App installation to forge signed events — pushes, statuses, check-suite completions, or membership changes — targeted at a *different* organization's tracked stack. This is a cross-repository write / unauthorized deploy trigger: forged `push` events can enqueue `GithubSyncJob` to sync arbitrary refs into a victim's tracked repository state, and forged `status`/`check_suite` events can mark arbitrary commits as passing, potentially enabling an unauthorized deploy of unreviewed code. This matches the "Critical – cross-repository writes / unauthorized deploy" and "High – escalation ... unauthenticated read of stack state" impact tiers.

### Likelihood Explanation
Requires only registering a free GitHub organization and installing a GitHub App on it (no privileged Shipit account, no knowledge of the victim's `webhook_secret`, and no repository write access to the victim's repo) — squarely within the "unprivileged attacker" threat model. The multi-org secret-selection code path is a documented, supported Shipit configuration. [6](#0-5) 

### Recommendation
After verifying the HMAC, re-validate that every organization/repository name later used by the event handlers (`full_name`, `organization.login`, etc.) is consistent with the `repository_owner`/organization whose secret validated the signature, rejecting the request (422) on any mismatch, rather than trusting downstream handlers to re-derive the same value independently.

### Proof of Concept
1. Attacker creates GitHub organization `attacker-org`, installs a GitHub App on it, and configures Shipit (or knows Shipit already tracks `attacker-org` via the multi-org `github:` config) with a known `webhook_secret`.
2. Attacker crafts a raw JSON body such as:
```json
{
  "repository": {
    "owner": {"login": "attacker-org"},
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s `webhook_secret` over the raw body.
4. `POST /webhooks` with header `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, which validates successfully against the attacker's own secret. [8](#0-7) 
5. `Shipit::Webhooks.for_event('push')` handlers then process the body using `repository.full_name` ("victim-org/victim-repo") to resolve the target stack, causing the victim's tracked repository/stack to be acted upon despite the signature never having been produced by victim-org's secret. [9](#0-8)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

  github:

      installation_id:
      webhook_secret:
      private_key:

    someothergithuborg:
