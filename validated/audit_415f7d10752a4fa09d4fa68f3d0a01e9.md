### Title
Webhook signature verification authenticates on `repository.owner.login`, but every handler acts on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-organization GitHub App configuration, where each configured organization has its own `webhook_secret` used to authenticate inbound GitHub webhooks [1](#0-0) . The equality this is supposed to enforce is: *organization whose secret signed the payload == organization that owns the repository the payload writes to*. The engine breaks that binding: it selects the verification secret from `repository.owner.login` (or `organization.login`), but every downstream handler resolves the actual target `Repository`/`Stack` from the completely independent `repository.full_name` field, which is never checked against the authenticated organization.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) to validate the signature against using `repository_owner`, derived solely from the payload itself: [2](#0-1) [3](#0-2) 

Once the HMAC check passes (using the secret belonging to whatever organization `repository.owner.login`/`organization.login` names), the raw event is dispatched unmodified to handlers: [4](#0-3) 

Every handler, however, resolves the target repository/stack from a *different* field, `repository.full_name`, via `Handler#stacks`/`#repository_name`, with no cross-check against `repository.owner.login`: [5](#0-4) 

This pattern repeats in every handler that resolves a repository, e.g. `PushHandler` (which triggers `stack.sync_github`) [6](#0-5) , `PullRequest::OpenedHandler`/`ReopenedHandler`/`UnlabeledHandler` (which create/archive/unarchive review stacks) [7](#0-6) [8](#0-7) , and `StatusHandler` (which writes commit statuses matched purely by `sha`, with no repository scoping at all) [9](#0-8) .

In a multi-organization deployment, an attacker who legitimately administers their own GitHub App/organization "attacker-org" registered in this Shipit instance's `config/secrets.yml` (and therefore knows `attacker-org`'s `webhook_secret`, since they control that organization's GitHub App settings) can:
1. Craft an arbitrary JSON payload with `repository.owner.login` = `"attacker-org"` (so `verify_signature` selects and successfully validates against `attacker-org`'s secret), but
2. Set `repository.full_name` to a repository belonging to an entirely different organization also configured/tracked by the same Shipit instance (e.g. `"victim-org/victim-repo"`), and
3. Sign the whole raw body with `attacker-org`'s known secret.

The signature only proves the payload was produced by someone who knows `attacker-org`'s secret; it says nothing about which repository the payload is allowed to reference. Since `repository_owner` (the authenticated identity) and `repository.full_name` (the write target resolved by every handler) are two independent JSON fields with no equality check between them, the attacker's forged-but-validly-signed event is processed against `victim-org/victim-repo`'s stacks.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written," directly matching the required High/Critical impact categories: it is effectively a cross-organization/cross-repository write via unauthorized event injection. Concretely:
- `PushHandler` calls `stack.sync_github(expected_head_sha:)` for any victim stack whose branch matches, letting the attacker trigger unauthorized GitHub sync/commit ingestion cycles on a repository they do not own.
- `StatusHandler` has no repository scoping whatsoever (`Commit.where(sha: params.sha)`), so a forged status event from any configured organization's secret can set arbitrary CI status text/state/target_url on any commit in the entire Shipit instance, which can influence deploy-safety checks (e.g. CI gating) for repositories the attacker has no rights to.
- `PullRequest::*Handler`s can archive/unarchive/create review stacks for a victim's repository, i.e. cross-repository writes.

### Likelihood Explanation
Requires the attacker to be a legitimate administrator of at least one organization/GitHub App configured in the same Shipit instance (a realistic scenario for shared/self-hosted multi-tenant Shipit deployments using the documented `github: { org: {...} }` multi-org secrets schema) [10](#0-9) . No privileged Shipit session, API token, or GitHub write access to the victim repository is needed — only the ability to sign an arbitrary HTTP POST with a secret the attacker legitimately possesses for their own org.

### Recommendation
In `WebhooksController#verify_signature`/`#create`, after verifying the HMAC, additionally assert that the organization used to select the webhook secret (`repository_owner`) matches the organization prefix of `repository.full_name` (and of `organization.login` when present) before dispatching to handlers. Reject the event (422) on mismatch, rather than trusting `repository.full_name` unconditionally in every handler.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `attacker-org` (secret known to the attacker, who legitimately administers that org's GitHub App) and `victim-org` (has a Stack tracking `victim-org/victim-repo`).
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and successfully verifies the signature [2](#0-1) .
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on its stacks, despite the payload only being authenticated for `attacker-org` [11](#0-10) [12](#0-11) .

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
