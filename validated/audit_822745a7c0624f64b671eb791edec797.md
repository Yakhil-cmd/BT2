Based on my investigation, this vulnerability is confirmed. The core issue: `WebhooksController#verify_signature` selects the HMAC key by `repository.owner.login` (or `organization.login`) via `Shipit.github(organization: repository_owner)`, but `Handler#stacks`/`repository_name` resolves the actual repository/stack to mutate using `payload.dig('repository', 'full_name')` — a completely separate field that is never cross-checked against `repository.owner.login`. `verify_webhook_signature` returns `true` unconditionally when the resolved GitHub app has no configured `webhook_secret` (`return true unless webhook_secret`). If the attacker names an org (`repository.owner.login` / `organization.login`) that Shipit has configured (or defaults to) without a `webhook_secret`, signature verification is bypassed entirely — while `repository.full_name` (used downstream by every handler, e.g. `Repository.from_github_repo_name(repository_name)` in `Handler#stacks`, or `params.repository.full_name` in `PullRequest::*Handler`s and presumably `PushHandler`/`CheckSuiteHandler`) can point to an arbitrary victim repo whose stacks get mutated. Neither `Handler#initialize`/`ExplicitParameters::Parameters.parse!` schema (`requires :repository do requires :full_name end`) nor any handler asserts `repository.owner.login == full_name.split('/').first`.

### Title
Webhook signature verification keys off `repository.owner.login` while repository resolution uses `repository.full_name`, with no equality check between them - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret for signature checking by `repository.owner.login` (or `organization.login`), but every downstream handler resolves the target `Repository`/`Stack` using the unrelated `repository.full_name` field. Because these two owner references are never asserted equal, an attacker can craft a payload where `owner.login` names an organization with no configured `webhook_secret` (bypassing verification via `return true unless webhook_secret`) while `full_name` points at any victim repository, allowing forged webhook events to mutate a repository the attacker does not control.

### Finding Description
The broken binding, stated as an equality that should hold but never does: `payload.dig('repository','owner','login') == payload.dig('repository','full_name').split('/').first`.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) , then fetches `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature` [1](#0-0) .
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` if that specific org's `@webhook_secret` is blank/unconfigured [3](#0-2) .
3. Once past this gate, `Handler.call(params)` runs `new(params).process`; `Handler#initialize` only runs `ExplicitParameters::Parameters.parse!(payload)`, which validates types/presence, not cross-field consistency [5](#0-4) .
4. `Handler#stacks` and `#repository_name` (and equivalent per-handler `repository` methods in the pull_request handlers) resolve the target repository purely from `payload.dig('repository','full_name')` / `params.repository.full_name`, with no reference back to `owner.login` [6](#0-5) , e.g. `Shipit::Repository.from_github_repo_name(params.repository.full_name)` in `PullRequest::OpenedHandler#repository` [7](#0-6) .

Attacker request: POST `/webhooks` with header `X-Github-Event: pull_request` (or `push`/`check_suite`), body `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, ...}`, where `attacker-org` is an org Shipit resolves to a `GitHubApp` config lacking `webhook_secret` (e.g. unconfigured/default entry). `verify_signature` computes the HMAC key for `attacker-org`, finds no secret, and accepts the request unconditionally regardless of the actual `X-Hub-Signature` header (attacker can omit or send garbage). The handler then operates on `victim-org/victim-repo`'s real `Repository`/`Stack` records — e.g. archiving/unarchiving review stacks, updating pull request state, or (per the question's stated scope) affecting `PushHandler`/`CheckSuiteHandler` stack resolution — despite the attacker having no credentials for `victim-org`.

Why guards fail: `drop_unhandled_event` and `check_if_ping` don't validate ownership at all; `verify_signature` validates against the wrong/attacker-controlled key namespace; the `ExplicitParameters` schema enforces shape, not cross-field identity; no model validation in `Repository`/`Stack` re-derives or checks the owner used for auth against the owner used for the mutation target.

### Impact Explanation
An unauthenticated attacker can trigger mutations (stack archive/unarchive, pull request label/state syncs, and per the question's broader scope, push/check-suite driven stack updates) against any repository configured in Shipit, as long as they can find or create an org without a configured `webhook_secret` to place in `owner.login`/`organization.login`. This is a cross-tenant authentication bypass: a payload for one (attacker-controlled or secret-less) namespace mutates another (victim) repository's Shipit-tracked state, matching the Critical category "payload for one repository mutating another's stack/commit/task/team" / "authentication bypass (forged webhook ... accepted)". It is repeatable against every repository/stack tracked by the Shipit instance and is not limited to a single victim.

### Likelihood Explanation
Preconditions: the attacker needs the ability to find (or, if Shipit is configured to fall back to a default/wildcard GitHub app config for unknown organizations rather than raising `GithubOrganizationUnknown`) an organization login with no `webhook_secret` set — this depends on the host's `Shipit.github` / secrets configuration, which I could not fully verify without reading `lib/shipit.rb`'s `github`/`github?` method and the deployed secrets file in this session. If every organization strictly requires a configured secret and unknown organizations always raise `GithubOrganizationUnknown` (rejected with 422), this exact path is not exploitable and the impact would depend entirely on whether any legitimately configured org secret-lessly exists. This uncertainty should be verified against `lib/shipit.rb` and the deployment's `secrets.yml` before treating this as conclusively exploitable in a given deployment. Assuming at least one secret-less/default org config exists (a common misconfiguration path, e.g. `secrets.development.example.yml` patterns), attacker cost is a single unauthenticated HTTP POST with no signature required, fully repeatable.

### Recommendation
Cross-check `repository.owner.login` against the owner segment of `repository.full_name` in `Handler#initialize` (or in `WebhooksController#verify_signature`) and reject the payload if they diverge. Additionally, do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank for a resolvable organization — require a non-blank secret per configured organization, or reject organizations that aren't explicitly configured with a secret (avoid a "default" no-secret app config).

### Proof of Concept
Minitest plan under `test/controllers/webhooks_controller_test.rb` and `test/models/shipit/webhooks/handlers_test.rb`:
1. Configure test secrets so that one org (e.g. `attacker-org`) has no `webhook_secret` while another org (`victim-org`) does (mirroring `test/dummy/config/secrets_double_github_app.yml`).
2. POST to `/webhooks` with `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and body `{"action":"opened","repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"}, ...}`.
3. Assert response is `200`/handled (not `422`), proving `verify_signature` passed for `attacker-org`'s absent secret.
4. Assert a `Shipit::Stack`/`Shipit::ReviewStack` under `victim-org/victim-repo` was created/mutated, proving the equality `owner.login == full_name.split('/').first` was never enforced and a cross-tenant write occurred.
5. Unit-level: call `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks` (or a concrete subclass) directly with a payload where `owner.login = "attacker-org"` and `full_name = "victim-org/some-repo"`, and assert no exception is raised and the `victim-org/some-repo` stack is returned unchanged.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
