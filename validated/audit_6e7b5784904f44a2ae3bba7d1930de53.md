### Title
Webhook signature verification keys off `repository.owner.login` while event handlers act on the unauthenticated `repository.full_name` field, allowing cross-repository event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature with by reading `repository.owner.login` (or `organization.login`) out of the untrusted JSON body itself, but the handlers that subsequently act on that same body (e.g. `PushHandler`, `StatusHandler`) resolve the *target* repository/stack from a different field, `repository.full_name`. Nothing binds these two fields together, so the "organization that authenticated" and "the repository that is written" are not the same equality the code implicitly assumes.

### Finding Description
`verify_signature` picks the signing secret using an attacker-controlled field of the very payload being verified: [1](#0-0) [2](#0-1) 

Once the HMAC check passes, `create` dispatches to the registered handlers with the raw parsed JSON: [3](#0-2) 

Every handler resolves its target `Stack`/`Commit` from `repository.full_name`, a completely separate field of the same JSON body: [4](#0-3) [5](#0-4) [6](#0-5) 

Shipit explicitly supports hosting multiple GitHub organizations, each with its own independent `webhook_secret`, as documented in the config schema: [7](#0-6) 

In this multi-tenant configuration, the binding the code needs to hold is: `organization whose secret validated the signature == organization that owns the repository being acted upon`. The controller only checks that the signature is valid for *some* configured organization named by `repository.owner.login`; it never re-checks that `repository.full_name` (used everywhere downstream to select the `Stack`/`Repository`/`Commit`) is actually owned by that same organization. Since the entire raw body — including both `repository.owner.login` and `repository.full_name` — is covered by the HMAC that is computed with the *attacker's own* organization's secret, anyone who controls a webhook secret for one organization onboarded onto the shared Shipit instance (e.g., an org admin who configured their own GitHub App's webhook secret) can freely author a JSON body where `repository.owner.login` says their own org (to select the secret they know) while `repository.full_name` names an arbitrary other tenant's `owner/repo` and sign the whole thing legitimately with their own secret.

This mirrors the Kakarot pattern exactly: the field the trust decision is made on (`repository.owner.login`, standing in for "the aliasing/authenticating identity") is not the field that is actually acted upon (`repository.full_name`, standing in for "the address/repository that gets written"), even though the code implicitly assumes they are the same.

### Impact Explanation
An attacker who administers (or has been granted) a webhook secret for one organization hosted on a shared, multi-org Shipit deployment can forge `push`, `status`, or `check_suite` events for a `Stack` belonging to a completely different organization/repository they do not control:
- Forged `push` events cause `PushHandler#process` to call `stack.sync_github(expected_head_sha: params.after)` on a victim's stack with an attacker-chosen SHA. [5](#0-4) 
- Forged `status` events let the attacker inject arbitrary CI/check state (`state`, `context`, `description`) onto a victim's commits via `Commit#create_status_from_github!`, which can feed into Shipit's continuous-delivery/merge-status logic that gates automatic deploys/merges. [6](#0-5) 

Because commit/check statuses are inputs to Shipit's continuous-deployment and merge-status machinery, this can escalate to triggering unauthorized syncs and potentially unauthorized deploy scheduling on a repository the attacker does not own — matching the "unauthorized deploy" impact category.

### Likelihood Explanation
Exploitation requires the attacker to control a valid `webhook_secret` for at least one organization configured on a shared/multi-tenant Shipit instance, which is a realistic but non-trivial precondition (it requires the deployment to host multiple orgs and the attacker to be a legitimate admin of one of them, not a GitHub App private key holder or a Shipit session). Given the config format explicitly documents per-organization `webhook_secret` entries, multi-org deployments are an intended, supported use case, making this a credible cross-tenant boundary crossing rather than a purely theoretical one.

### Recommendation
After the HMAC check succeeds, verify that `repository.full_name` (and any other repository identifiers acted on by handlers) actually belongs to the organization/owner (`repository.owner.login`) whose secret validated the signature, rejecting the webhook if they diverge. Alternatively, resolve the target `Stack`/`Repository` first and use *that* record's associated organization to select the webhook secret, rather than trusting an unauthenticated field of the same payload to make the security decision.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` (attacker-administered, secret known to attacker: `secretA`) and `org-b` (victim, has a stack tracking `org-b/victim-repo`).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` themselves, since they know `secretA`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`), validates the HMAC against `secretA` — passes, because the attacker signed with their own known secret.
6. `PushHandler#process` resolves the stack via `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: <attacker sha>)`, acting on the victim's stack despite the request only having been authenticated as belonging to `org-a`.
