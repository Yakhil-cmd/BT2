### Title
Stack-scoped ApiClient token authorizes only its own stack but CCMenuController lets it read any stack's CI status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` binds the set of stacks an `ApiClient` token is authorized to touch to `current_api_client.stack_id`, but `Shipit::Api::CCMenuController` overrides the `stack` lookup and resolves `params[:stack_id]` against the full `Stack` table, breaking that binding.

### Finding Description
`Shipit::Api::BaseController#stacks` establishes the equality that every stack-scoped endpoint is supposed to respect: the stacks a token authorizes == the stacks a token can touch. When an `ApiClient` is scoped to a stack (`stack_id?` true), `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)`, and `#stack` resolves `params[:stack_id]` only within that restricted relation: [1](#0-0) 

`CCMenuController` inherits from `BaseController` and declares `require_permission :read, :stack`, relying on the same permission model, but it overrides `#stack` to bypass the scoped `stacks` relation entirely, resolving directly against the unrestricted `Stack` model: [2](#0-1) 

The permission check (`require_permission :read, :stack` → `current_api_client.check_permissions!('read', 'stack')`) only checks the client's `permissions` array; it never checks whether the target stack matches `current_api_client.stack_id`: [3](#0-2) 

So a token that is scoped to Stack A (has `stack_id == A.id`) and has the `read:stack` permission passes `require_permission!`, and then `stack` (overridden in `CCMenuController`) happily loads any stack the caller specifies via `params[:stack_id]`, including stacks the token was never meant to access. This is directly analogous to the AffiliateValidator bug: a credential ("signature"/token) is validated for authenticity/permission but not cryptographically/structurally tied to the specific resource ("caller address"/stack) it is later used against, so it can be redeemed against an unintended target.

### Impact Explanation
An attacker holding a valid but narrowly stack-scoped `ApiClient` token (e.g. obtained through `CCMenuUrlController#fetch`, which is reachable by any authenticated Shipit user for a stack they can view) can query `Shipit::Api::CCMenuController#show` with an arbitrary `stack_id` for any other stack in the instance and receive that stack's CI/deploy status (`stack.deploys_and_rollbacks.last`), leaking deploy state across stacks the token holder is not authorized to see. This matches the High-impact category: "unauthenticated/unauthorized read of stack state, task streams or deploy output" across a trust boundary the token was scoped to respect.

### Likelihood Explanation
Any party that legitimately obtains one stack-scoped token (a normal, low-privilege artifact created via `CCMenuUrlController#fetch` for CI dashboard integration) can trivially exploit this by changing the `stack_id` query parameter on the CCMenu API request — no additional secrets, no privileged account, and no interception of another user's credentials is required. This is a straightforward parameter-substitution attack once any token is held.

### Recommendation
Change `CCMenuController#stack` to resolve stacks through the scoped `stacks` relation (as `BaseController#stack` does), e.g. `stacks.from_param!(params[:stack_id])`, so that stack-scoped tokens cannot read data belonging to stacks outside their `stack_id` binding.

### Proof of Concept
1. As an authenticated Shipit user with access only to Stack A, call `GET /stacks/<A>/ccmenu_url` (`CCMenuUrlController#fetch`) to obtain a `read:stack`-scoped `ApiClient` token for Stack A (or use any existing stack-scoped `ApiClient` fixture such as `here_come_the_walrus`).
2. Send `GET /api/stacks/<B>/ccmenu.xml?token=<token>` where `B` is a different stack the token was never scoped to.
3. `authenticate_api_client` succeeds (valid token), `require_permission :read, :stack` succeeds (token has `read:stack`), and `stack` in `CCMenuController` loads Stack B directly via `Stack.from_param!`, returning Stack B's latest deploy/CI status in the XML response — despite the token being scoped only to Stack A.
