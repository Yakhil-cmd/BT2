### Title
Membership webhook signature-verification organization binding mismatch allows cross-organization `Shipit.github_teams` privilege escalation - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to validate an incoming webhook based on `repository_owner`, which is computed as `params.dig('repository','owner','login') || params.dig('organization','login')`. The `membership` event handler, however, mutates team/authorization state using an entirely different payload field — `params.organization.login` — without ever checking that it matches the field that was actually authenticated. In a multi-organization Shipit deployment (explicitly supported, see `config/secrets.development.shopify.yml`), an attacker who knows the webhook secret for *any one* configured organization can forge a `membership` payload whose `organization.login` names a *different*, privileged organization, and get the signature check to pass using the attacker's own organization's secret while the state-changing code operates on the victim organization's name.

### Finding Description
Signature verification: [1](#0-0) [2](#0-1) 

`repository_owner` prefers `params.dig('repository', 'owner', 'login')` over `params.dig('organization', 'login')`. This value is used only to pick which configured GitHub App's `webhook_secret` to verify the raw payload against, via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Multiple, independently-secreted organizations are an explicitly supported configuration: [4](#0-3) 

Once the signature is accepted, the raw JSON body is dispatched unchanged to registered handlers for the event: [5](#0-4) 

For `membership` events, `MembershipHandler#process`/`find_or_create_team!` derives the `Team#organization` (and therefore membership/authorization scope) strictly from `params.organization.login`, a field that is completely independent of the field used for signature verification: [6](#0-5) 

Because HMAC verification only proves the payload bytes were signed with *some* known-to-the-attacker secret (the one belonging to whichever org the attacker controls/knows), and the `repository` sub-object used to pick that secret is not the same sub-object the handler trusts to determine which `Team` gets a member added, an attacker can:

1. Craft a `membership` webhook body containing `repository: { owner: { login: "attacker-org" } }` (an org whose webhook secret the attacker knows) and `organization: { login: "victim-org" }` (the org whose team they want to join), `action: "added"`, and `member: { login: "attacker-github-login" }`.
2. Sign the full raw payload with `attacker-org`'s webhook secret and send it to `/webhooks` with `X-Github-Event: membership`.
3. `verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature validates successfully.
4. `MembershipHandler` runs unmodified and creates/updates a `Team` scoped to `organization: "victim-org"` (via `params.organization.login`), and appends the attacker's `User` (created on the fly via `User.find_or_create_by_login!`) as a member of that team.
5. If `victim-org`'s team is included in `Shipit.github_teams`, the attacker's Shipit `User#authorized?` now returns true for that scope: [7](#0-6) [8](#0-7) 

The binding that is broken, expressed as an equality that should hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login / organization.login fallback) == organization whose Team membership is mutated by MembershipHandler (organization.login)`.
These are read from independent JSON paths of the same request, so an attacker fully controls both simultaneously while only needing to know the secret for one.

### Impact Explanation
This allows escalation into `Shipit.github_teams` authorization (High severity per the given rubric) without ever needing GitHub organization admin/write access to the victim organization, and without needing an existing Shipit session, `ApiClient` token, or the victim org's webhook secret — only the webhook secret of any organization configured in the same Shipit instance's multi-org GitHub config. Once team membership is granted, the attacker can pass `force_github_authentication` and access any part of Shipit gated by `Shipit.github_teams`, including stacks, deploys, and API clients tied to the victim organization's teams.

### Likelihood Explanation
Exploitability requires: (1) a multi-organization `Shipit.github` configuration (a documented and supported setup), and (2) knowledge of the webhook secret for at least one configured organization (which the attacker may legitimately possess if they administer that org's own GitHub App installation within the same shared Shipit deployment). Given those preconditions, forging the payload and computing the signature is trivial (standard HMAC-SHA1 over attacker-controlled bytes with a known key), and the vulnerable code path (`repository_owner` vs. `params.organization.login` divergence) is unconditional — no additional race condition or timing is needed.

### Recommendation
Make `MembershipHandler` (and any other organization-scoped handler) use the exact same field that was used to select and verify the webhook signature (i.e., pass `repository_owner`/the verified organization down to handlers, or re-derive `Team#organization` from that value rather than independently re-reading `params.organization.login`). Alternatively, `verify_signature` should reject payloads where `params.dig('repository','owner','login')` and `params.dig('organization','login')` are both present but disagree, and always prefer the field(s) actually consumed by the event-specific handler for a given event type.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. Ensure a `Team` for `victim-org` (e.g., `victim-org/developers`) is included in `Shipit.github_teams`.
3. Build the JSON body:
```json
{
  "action": "added",
  "team": { "id": 123, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/123" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org secret, body)>`.
5. `POST /webhooks` with header `X-Github-Event: membership` and the body/signature above.
6. `verify_signature` passes (uses `attacker-org`'s secret), `MembershipHandler` runs, creating/updating the `victim-org/developers` `Team` and adding `attacker-github-login` as a member — see `app/models/shipit/webhooks/handlers/membership_handler.rb` lines 22-43 and `app/controllers/shipit/webhooks_controller.rb` lines 24-62.
7. The corresponding Shipit `User` for `attacker-github-login` is now `authorized?` for any resource gated by that team, per `app/models/shipit/user.rb` lines 80-82.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?

        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))

        end
      else

      end
```
