### Title
Webhook signature authenticates the payload's `repository.owner.login` organization while handlers dispatch writes based on the unbound `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using only `repository.owner.login` (or `organization.login`) from the JSON body, but every event handler (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, etc.) resolves the target `Repository`/`Stack` using a *different* field of the same untrusted payload: `repository.full_name`. Nothing enforces that `full_name` is consistent with `owner.login`.

### Finding Description
The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository being acted upon`. In practice the two checks read different, independently-attacker-controlled fields of the same JSON body:

- `verify_signature` computes `repository_owner` from the payload and fetches the GitHub App/secret for that org: [1](#0-0) [2](#0-1) 

- Every handler instead resolves the acted-upon repository/stacks from `repository.full_name`: [3](#0-2) 

- `Repository.from_github_repo_name` blindly splits that string on `/` to find owner/name with no cross-check against the org that signed the request: [4](#0-3) 

Because `verify_signature` only inspects `repository.owner.login` (falling back to `organization.login`) to pick the webhook secret, and the handlers act on `repository.full_name`, an attacker who legitimately controls (and knows the webhook secret for) Organization A can submit a forged JSON body directly to the `/webhooks` endpoint where `repository.owner.login = "OrgA"` (so the signature validates with a secret they legitimately possess) but `repository.full_name = "OrgB/victim-repo"`. The signature check passes, and `PushHandler`, `CheckSuiteHandler`, `StatusHandler`, `MembershipHandler`, etc. then act on stacks/commits belonging to OrgB's repository — an org the attacker never authenticated as.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly, and enables cross-repository writes: an attacker holding a valid secret for one onboarded organization can trigger `GithubSyncJob` (`PushHandler#process` -> `stack.sync_github`), inject fabricated commit statuses (`StatusHandler#process` -> `commit.create_status_from_github!`), schedule check-run refreshes, or manipulate team membership (`MembershipHandler`) for stacks/repositories that belong to a completely different, unauthorized organization managed by the same multi-tenant Shipit instance. This matches the Critical impact bucket of "cross-repository writes."

### Likelihood Explanation
Exploitability requires only that the attacker legitimately know a webhook secret for *any* one organization configured on a shared Shipit instance (a normal, unprivileged capability for someone who administers their own org's GitHub App installation in a "Using Multiple Github Applications" deployment) and be able to POST directly to the public `/webhooks` endpoint, which is unauthenticated aside from the HMAC check. No GitHub session, `ApiClient` token, or repository write access to the *victim* repository is required — only to their own, unrelated org. This is a realistic misconfiguration risk specifically in the documented multi-org setup.

### Recommendation
In `WebhooksController#verify_signature`, after validating the HMAC using `repository_owner`, additionally assert that `repository.full_name`'s owner segment (and/or `organization.login`) matches `repository_owner` before dispatching to handlers, rejecting (422) any payload where these fields disagree. Alternatively, have handlers derive the repository strictly from the same field used for signature verification, never trusting `full_name` independently.

### Proof of Concept
1. Attacker administers a legitimate GitHub App installation for `OrgA` on a Shipit instance configured with the multi-organization `github` block (per `docs/setup.md`), and thus knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=...` using `OrgA`'s known `webhook_secret` over the raw body and POSTs it directly to `POST /webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s GitHub App, and the signature validates successfully.
5. `PushHandler#process` is invoked and resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, triggering `stack.sync_github` on OrgB's stack despite the request only being authenticated for OrgA.
