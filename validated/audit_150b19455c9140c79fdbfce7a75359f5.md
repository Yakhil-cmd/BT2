### Title
RAY aggregate-value overflow permanently freezes a high-utilization market - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` converts aggregate scaled debt and supply through `scaled_to_original`, which returns an `i128` RAY value and panics with `MathOverflow` when `scaled * index / RAY` exceeds that domain. [1](#0-0) [2](#0-1) [3](#0-2)  The existing borrow-index ceiling is applied only after this aggregate valuation, so a sufficiently large market can cross the `i128` value ceiling before reaching `MAX_BORROW_INDEX_RAY`. [4](#0-3) [5](#0-4) 

### Finding Description
An unprivileged caller reaches the vulnerable path through `Controller::supply`, `Controller::borrow`, and later `Controller::update_indexes`; `update_indexes` only requires caller authorization and forwards the selected hub assets to the pool. [6](#0-5) [7](#0-6) [8](#0-7)  The pool’s `global_sync` runs `accrue_step`, whose first operation computes `borrowed * borrow_index` and `supplied * supply_index` before calculating or applying the new capped index. [9](#0-8) [10](#0-9)  Every pool leg loads `synced_market`, which invokes the same accrual before withdrawal, repayment, liquidation-related repayment/seizure, or further supply/borrow accounting. [11](#0-10)  The repository’s horizon test demonstrates a reachable state in which `update_indexes` returns `MathOverflow`, the borrow index remains below its configured cap, and both withdrawal and repayment subsequently revert with the same error. [12](#0-11) [13](#0-12) 

### Impact Explanation
This permanently freezes all supplier claims and pool liquidity in the affected hub market because users cannot withdraw, borrowers cannot repay, liquidations cannot progress through synced pool legs, and index updates can never commit past the overflowing valuation. [11](#0-10) [14](#0-13)  The accepted impact is permanent freezing of user funds and a market unable to operate, not a loss limited to the attacker’s own position. [15](#0-14) 

### Likelihood Explanation
Triggering the condition requires a very large market, sustained high utilization, and enough ledger-time accrual for the relevant index to exceed `i128::MAX * RAY / scaled_amount`; the demonstrated setup uses one billion 18-decimal tokens with 98% utilization. [16](#0-15)  These requirements are economically significant, but they are not privileged actions, special authorization, malformed parameters, or an upgrade, and the admitted numeric domain allows the aggregate-value ceiling to be reached before the index ceiling. [17](#0-16) 

### Recommendation
Before minting supply, debt, or revenue shares, compute the post-mutation aggregate and reject any state for which `scaled * current_index / RAY` cannot fit in `i128`; equivalently enforce `new_scaled <= floor(i128::MAX * RAY / current_index)` for both aggregates. [18](#0-17) [19](#0-18)  During accrual, cap each next index at both its protocol maximum and the aggregate-specific bound `floor(i128::MAX * RAY / scaled_amount)` before calling `calculate_supplier_rewards`, `update_supply_index`, or `supply_index_reward_shortfall`. [20](#0-19) [21](#0-20)  Add the existing horizon scenario as a permanent regression boundary so accrual clamps safely instead of crossing into an unrecoverable `MathOverflow` state. [22](#0-21) 

### Proof of Concept
```rust
// One attacker-controlled account:
// 1. Supply `principal = 1_000_000_000 * 10^18` of an 18-decimal asset.
// 2. Supply enough separate collateral and borrow `principal * 98 / 100`.
// 3. Allow ledger time to advance and repeatedly call `update_indexes`.
// 4. Once aggregate debt value exceeds i128::MAX, every later synced call reverts.

controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(big18_key, principal), (collateral_key, collateral)],
);
controller.borrow(
    attacker,
    account_id,
    vec![(big18_key, principal * 98 / 100)],
    Some(attacker),
);
controller.update_indexes(attacker, vec![big18_key]); // eventually MathOverflow
controller.withdraw(attacker, account_id, vec![(big18_key, 1)], None); // MathOverflow
controller.repay(attacker, account_id, vec![(big18_key, 1)]); // MathOverflow
```
The checked-in test performs the equivalent sequence with `supply_raw`, `borrow_raw`, repeated `try_update_indexes_for`, and then proves both withdrawal and repayment fail with `MATH_OVERFLOW`. [23](#0-22)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
