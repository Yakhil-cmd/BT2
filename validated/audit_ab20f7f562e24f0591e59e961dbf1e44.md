### Title
`MultiKey`/`MultiKeyAuthenticator` accepts duplicate public keys, letting one key holder alone satisfy a k-of-n threshold that is supposed to require k distinct signers - (File: `types/src/transaction/authenticator.rs`)

### Summary
The `MultiKey` construction and `MultiKeyAuthenticator` verification logic never checks that the public keys in a k-of-n authentication set are distinct. Threshold satisfaction is counted purely by the number of *bitmap slots* filled with a valid signature, not by the number of *distinct* keys that actually produced a signature. If the same public key occupies more than one slot, its single holder can fill multiple slots by resubmitting the same signature at each duplicate index, satisfying the threshold alone.

### Finding Description
`MultiKey::new` only validates the threshold bounds and the key-count vs. threshold relationship - it does not reject duplicate entries in `public_keys`: [1](#0-0) 

`MultiKeyAuthenticator::new` only guards against duplicate *signature indices* in the bitmap and out-of-range indices; it does not compare the underlying public keys at those indices for equality: [2](#0-1) 

Verification (`to_single_key_authenticators` / `verify`) counts satisfied threshold purely from `signatures.len() >= public_keys.signatures_required()`, with each signature checked only against the public key stored at its own bit index — there is no cross-index uniqueness or distinct-signer check: [3](#0-2) 

This is demonstrated by the existing unit test itself: a `MultiKey` is built with `[sender0_pub, sender1_pub, sender1_pub]` (index 1 and 2 hold the *same* key) with `signatures_required = 2`, and `MultiKey::new` succeeds without any duplicate-key error: [4](#0-3) 

The test then shows that the same `sender1` signature can be reused at index 1 *and* index 2 to independently satisfy the 2-of-3 threshold — `mk_auth_12` uses `(1, signature1)` and `(2, signature1)`, both derived from `sender1` alone, and the resulting transaction verifies successfully: [5](#0-4) 

In other words: sender1 alone — without any participation from sender0 — can authorize a transaction from an account whose authentication key was set up as a "2 distinct signers required" threshold key, because the underlying key list secretly contains a duplicate.

By contrast, the framework-level `multisig_account.move` module (the pure-Move multisig resource-account model) *does* explicitly enforce owner uniqueness at setup time via `validate_owners`, which asserts `EDUPLICATE_OWNER` on any repeated address: [6](#0-5) 

This shows the invariant ("k distinct authorizers required") is understood and enforced in one authentication path in the codebase, but is missing from the native `MultiKey`/`MultiEd25519`-style k-of-n authentication key path that underlies ordinary account authentication (`AccountAuthenticator::MultiKey`, `TransactionAuthenticator::SingleSender`/`MultiAgent`/`FeePayer` when the signer's auth key is a `MultiKey`). The multi-agent duplicate-signer check that exists at the transaction level (`contains_duplicate_signers`, enforced in `aptos_vm.rs` via `SIGNERS_CONTAIN_DUPLICATES`) only catches duplicate *account addresses* across sender/secondary signers — it does not, and cannot, catch duplicate *public keys inside a single account's* MultiKey authentication key: [7](#0-6) [8](#0-7) 

### Impact Explanation
Accounts secured by a k-of-n `MultiKey` authentication key (e.g., a treasury or shared account meant to require independent approval from k distinct parties) silently lose their security guarantee if any two of the n public keys are equal — deliberately or accidentally introduced during key generation/rotation. A holder of the duplicated key can then unilaterally authorize transactions/transfers/governance actions that were supposed to require independent co-signers, i.e., unauthorized execution under a signer set that was never actually satisfied. This is a genuine authenticator/approval-set binding failure at the transaction-admission boundary matching the required impact category ("Authenticator ... multisig ... approval validation accepting the wrong ... approval set").

### Likelihood Explanation
The condition requires that the `MultiKey` (or `MultiEd25519`) authentication key used by the victim account contain a duplicate public key. This can arise from: (a) wallet/SDK tooling bugs that fail to de-duplicate keys during multi-key account setup or key rotation, (b) a malicious co-owner intentionally inserting a duplicate of their own key during a multi-party setup ceremony (which co-signers would need to review and would not obviously catch since keys are opaque byte strings), or (c) key reuse across roles. Because neither `MultiKey::new` nor `MultiKeyAuthenticator`/`MultiEd25519` verification perform any distinctness check, nothing in the validation stack (mempool, VM prologue, or authenticator verification) would ever reject such a configuration or flag the resulting transaction as improperly authorized.

### Recommendation
Enforce distinct public keys as an invariant in `MultiKey::new` (and equivalently in `MultiEd25519PublicKey::new`), rejecting duplicate entries the same way `multisig_account::validate_owners` rejects `EDUPLICATE_OWNER`. Additionally, consider having `MultiKeyAuthenticator`/`MultiEd25519Signature` verification confirm that the public keys backing the accepted signature indices are pairwise distinct before counting them toward the threshold, to defend even against already-existing on-chain accounts that may have been set up with duplicate keys.

### Proof of Concept
The existing repository test itself is a proof of concept (no new code needed): [9](#0-8) 
1. `MultiKey::new(vec![any_sender0_pub, any_sender1_pub, any_sender1_pub], 2)` succeeds — no duplicate-key rejection.
2. `sender1` signs the transaction once, producing `signature1`.
3. `MultiKeyAuthenticator::new(multi_key, vec![(1, signature1.clone()), (2, signature1.clone())])` succeeds and `signed_txn.verify_signature()` returns `Ok(())`, satisfying the "2 signatures required" threshold using only `sender1`'s single signature reused across the two indices that happen to map to the same public key — `sender0` never participates.

**Note on limitations**: I was unable to fully trace the on-chain flow that sets a `MultiKey` as an account's authentication key (e.g. `rotate_authentication_key`/account-creation entry functions in the Move framework) within the available index, so I could not verify whether any additional on-chain check outside `types/src/transaction/authenticator.rs` performs deduplication before persisting the auth key. If such a check exists elsewhere, it would mitigate this finding; based on everything located, no such check appears in the authenticator/crypto layer itself.

impl MultiKeyAuthenticator {
    pub fn new(public_keys: MultiKey, signatures: Vec<(u8, AnySignature)>) -> Result<Self> {
        ensure!(
            public_keys.len() < (u8::MAX as usize),
            "Too many public keys, {}, in MultiKeyAuthenticator.",
            public_keys.len(),
        );

        let mut signatures_bitmap = aptos_bitvec::BitVec::with_num_bits(public_keys.len() as u16);
        let mut any_signatures = vec![];

        for (idx, signature) in signatures {
            ensure!(
                (idx as usize) < public_keys.len(),
                "Signature index is out of public key range, {} < {}.",
                idx,
                public_keys.len(),
            );
            ensure!(
                !signatures_bitmap.is_set(idx as u16),
                "Duplicate signature index, {}.",
                idx
            );
            signatures_bitmap.set(idx as u16);
            any_signatures.push(signature);
        }

        Ok(MultiKeyAuthenticator {
            public_keys,
            signatures: any_signatures,
            signatures_bitmap,
        })
    }

    pub fn to_single_key_authenticators(&self) -> Result<Vec<SingleKeyAuthenticator>> {
        ensure!(
            self.signatures_bitmap.last_set_bit().is_some(),
            "There were no signatures set in the bitmap."
        );

        ensure!(
            (self.signatures_bitmap.last_set_bit().unwrap() as usize) < self.public_keys.len(),
            "Mismatch in the position of the last signature and the number of PKs, {} >= {}.",
            self.signatures_bitmap.last_set_bit().unwrap(),
            self.public_keys.len(),
        );
        ensure!(
            self.signatures_bitmap.count_ones() as usize == self.signatures.len(),
            "Mismatch in number of signatures and the number of bits set in the signatures_bitmap, {} != {}.",
            self.signatures_bitmap.count_ones(),
            self.signatures.len(),
        );
        ensure!(
            self.signatures.len() >= self.public_keys.signatures_required() as usize,
            "Not enough signatures for verification, {} < {}.",
            self.signatures.len(),
            self.public_keys.signatures_required(),
        );
        let authenticators: Vec<SingleKeyAuthenticator> =
            std::iter::zip(self.signatures_bitmap.iter_ones(), self.signatures.iter())
                .map(|(idx, sig)| SingleKeyAuthenticator {
                    public_key: self.public_keys.public_keys[idx].clone(),
                    signature: sig.clone(),
                })
                .collect();
        Ok(authenticators)
    }

    pub fn verify<T: Serialize + CryptoHash>(&self, message: &T) -> Result<()> {
        let authenticators = self.to_single_key_authenticators()?;
        authenticators
            .iter()
            .try_for_each(|authenticator| authenticator.verify(message))?;
        Ok(())
    }
