### Title
Webhook signature verification is keyed by an attacker-controlled organization field distinct from the organization the handler mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to verify the HMAC against using an organization value taken directly from the still-unverified JSON body. Because webhook secrets are optional per-organization and any org without one causes verification to be trivially bypassed, an attacker can pick a "victim" field set that is processed by the handler (e.g. the organization a `Team` is scoped to) independently of the field used to select the verification secret, breaking the equality: *organization that authenticated the request* == *organization whose state is mutated*.

### Finding Description
`verify_signature` computes the verifying organization from the raw, not-yet-verified body: [1](#0-0) [2](#0-1) [3](#0-2) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` prefers `repository.owner.login` over `organization.login`. Nothing constrains the payload's shape to match a real GitHub webhook for the declared `X-Github-Event`, so an attacker can include both keys in one crafted body.

`Shipit.github(organization:)` resolves per-organization config, and signature verification is a no-op whenever that organization has no configured `webhook_secret`: [4](#0-3) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Multi-organization GitHub App configuration is a supported, tested deployment mode (`secrets.github` keyed by org names), as shown by `Shipit.github_app_config`/`github_organizations` and the dedicated fixture `test/dummy/config/secrets_double_github_app.yml`: [5](#0-4) 

The `membership` handler then mutates a `Team` and its membership using a *different* payload field, `organization.login`, and arbitrary `team`/`member` sub-objects, entirely independent of whatever organization was used to select the verification secret: [6](#0-5) 

Because `repository.owner.login` (used only for signature selection) and `organization.login` (used for the actual `Team` write) are two unrelated keys, an attacker can:
1. Set `repository.owner.login` to an organization configured in `secrets.github` with no `webhook_secret` — verification trivially returns `true` for any body/signature.
2. Set `organization.login`, `team.id/name/slug`, and `member.login` to target a real, protected organization's `Team`, adding an arbitrary GitHub login (including the attacker's own) as a member of that `Team`.

This breaks the binding "organization that authenticated the webhook" == "organization/team whose authorization data is written," which is exactly the class of bug described in the report (an entity used for one purpose treated as trusted for an unrelated, more sensitive purpose because two related-looking fields were never bound together).

### Impact Explanation
`Team` records created/modified via `MembershipHandler` back `Shipit.github_teams`, which authorization checks in the app rely on for granting/using team-based access (`app/controllers/concerns/shipit/authentication.rb`, `lib/shipit.rb#github_teams`). An attacker who can add themselves (or any GitHub login) to such a team without ever presenting a valid HMAC signature for the real target organization achieves escalation into `Shipit.github_teams` authorization — a High-impact outcome per the engine's own severity classification, entirely without a Shipit session, API token, or the app's real `webhook_secret`.

### Likelihood Explanation
Requires only that (a) the deployment uses per-organization GitHub App configuration (a supported, documented mode) and (b) at least one configured organization has no `webhook_secret` set — an explicitly allowed configuration state per `verify_webhook_signature`'s `return true unless webhook_secret` short-circuit. No credentials, GitHub App private key, or prior access are needed; the attacker only needs to know/guess one org name in the config that lacks a secret and send a single crafted HTTP POST.

### Recommendation
Bind signature verification to the same field(s) actually consumed by the handler for state mutation (e.g., always require `organization.login` and validate it is consistent with `repository.owner.login` when both are present), and reject/require `webhook_secret` to be present for every configured organization instead of treating it as optional.

### Proof of Concept
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=anything   # or omit/garbage

{
  "action": "added",
  "repository": { "owner": { "login": "org-with-no-webhook-secret" } },
  "organization": { "login": "victim-org" },
  "team": { "id": 999, "name": "Deployers", "slug": "deployers", "url": "https://x" },
  "member": { "login": "attacker-github-login" }
}
```
`verify_signature` resolves `Shipit.github(organization: "org-with-no-webhook-secret")`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` unconditionally. `MembershipHandler#process` then runs `team.add_member(member)` against a `Team` scoped to `"victim-org"`, granting `attacker-github-login` membership without any valid signature ever being checked against `victim-org`'s real secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
