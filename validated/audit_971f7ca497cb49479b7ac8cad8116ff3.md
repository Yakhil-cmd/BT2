### Title
Manipulatable/grindable randomness available to AA developers via `number_from_seed(trigger.unit)` / `number_from_seed(mc_unit)` - (File: formula/evaluation.js)

### Summary
The oscript formula language exposes `number_from_seed()`, a deterministic SHA-256-based pseudo-random number generator, together with getters such as `trigger.unit` and `mc_unit` that AA authors commonly use as a randomness "seed" for lotteries, reward distribution, or other selection logic inside Autonomous Agents. Both of these seed sources are attacker-influenceable in the same way `blockhash`/`slotStart` are in the reported EVM bug: the party who authors the triggering unit fully controls and can pre-compute the hash of that unit before broadcasting it, and the current stable `mc_unit` at trigger time is knowable in advance and can be waited-out/timed by the poster. This lets a malicious trigger author grind or time their submission until `number_from_seed()` returns a favorable outcome.

### Finding Description
`number_from_seed` is implemented in `formula/evaluation.js` as a plain SHA-256 hash of a caller-supplied seed, mapped into a numeric range: [1](#0-0) 

This function is a general-purpose oscript primitive, and the two natural "unpredictable" values exposed to formulas for use as a seed are `trigger.unit` (the hash of the unit that triggered the AA) and `mc_unit` (the last stable main-chain unit at the time the trigger is processed), both allowed as getters in AA formulas: [2](#0-1) 

`trigger.unit` is simply the hash of the unit that the caller themselves authored and posted: [3](#0-2) 

Because the unit's hash is computed over its own content (parents, timestamp, messages, data payload, etc.), the author of the trigger unit can freely vary any of these non-essential fields (extra data fields, timestamp, parent selection) prior to broadcasting, recomputing the resulting hash offline each time, until `number_from_seed(trigger.unit)` yields whatever outcome benefits them — this is a direct grinding analog to blockhash manipulation.

`mc_unit` is likewise attacker-observable ahead of time: it is fixed to the last stable MC unit at the moment the trigger is processed: [4](#0-3) 

Since stabilization of the MC unit happens independently of when a user chooses to post their trigger, an attacker can simply wait and repeatedly query the current stable `mc_unit`/derived `number_from_seed(mc_unit)` value off-chain, and only submit their trigger unit at a moment when the seed produces a favorable result for them — analogous to waiting for a favorable `slotStart` blockhash.

Neither `number_from_seed` nor the validation logic for it place any restriction preventing its use with `trigger.unit`/`mc_unit`, nor is there a warning discouraging this pattern in the validator: [5](#0-4) 

Notably, the codebase does provide a more robust alternative — `vrf_verify` — for verifying VRF-based randomness, but nothing in the AA formula validator prevents developers from instead using the much weaker, grindable `number_from_seed(trigger.unit)`/`number_from_seed(mc_unit)` pattern: [6](#0-5) 

### Impact Explanation
Any AA that implements probabilistic logic (e.g., picking a winner, choosing a reward recipient/distributor, splitting funds randomly) using `number_from_seed` seeded from `trigger.unit` or `mc_unit` can have its outcome biased by the party who controls unit composition or posting timing. Because AAs hold and disburse funds automatically based on formula results, a manipulated "random" outcome can lead to direct fund loss for the AA (e.g., an attacker always winning a payout) — this is a concrete AA fund-loss vector, matching the required impact bar.

### Likelihood Explanation
Likelihood is medium: exploitation requires an AA developer to actually adopt this common but insecure randomness pattern (which is a natural, unguided choice given `number_from_seed`, `trigger.unit`, and `mc_unit` are all readily available oscript primitives with no built-in warning), and requires the attacker to control or time the triggering unit — something any ordinary unprivileged unit poster can do without any special privilege.

### Recommendation
- Document and warn (via `formula/validation.js` and developer docs) against seeding `number_from_seed` with attacker-controlled or attacker-predictable values such as `trigger.unit` or the immediately-preceding `mc_unit`.
- Encourage/require AAs that need unbiased randomness to use `vrf_verify` (already implemented) with an externally supplied VRF proof instead of `number_from_seed` over self-controlled unit hashes.
- Consider disallowing or flagging `number_from_seed(trigger.unit, ...)` / `number_from_seed(mc_unit, ...)` combinations at validation time, since these are almost never a safe randomness source.

### Proof of Concept
1. An AA is written to select a "winner"/distributor via:
   `{ var['winner_index'] = number_from_seed(trigger.unit, 0, n-1); }`
2. An attacker crafts a trigger unit and, before broadcasting, freely varies the unit content (adds an unused data field, tweaks timestamp/parents) and recomputes `objectHash.getUnitHash()` locally (per `object_hash.js` `getUnitHash`) to preview what `trigger.unit` — and hence `number_from_seed(trigger.unit, 0, n-1)` — would evaluate to via `formula/evaluation.js`'s `number_from_seed` logic.
3. Once the attacker finds a variant whose resulting index selects themself, they post that specific unit, guaranteeing they are chosen as winner/distributor, at the expense of other honest triggers/participants.
