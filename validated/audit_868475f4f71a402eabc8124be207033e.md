### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler resolves the target repository from the independent `repository.full_name` field, allowing an app installed on one organization to write to any other organization's repository/stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the incoming payload against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Every downstream `Shipit::Webhooks::Handlers::Handler` subclass instead resolves the affected repository/stack from a *different* JSON field: `payload.dig('repository', 'full_name')`. Because Shipit natively supports multiple GitHub App configurations keyed by organization (`Shipit.github_app_config`, `TOP_LEVEL_GH_KEYS`, multi-org secrets layout as in `secrets_double_github_app.yml`), the field used to pick the verifying secret (`repository.owner.login`) and the field used to determine which repository/stack is actually mutated (`repository.full_name`) are two independent, attacker-influenced strings inside the same signed payload.

### Finding Description [1](#0-0) 

`verify_signature` does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`.

Every handler, however, derives the operative repository independently: [2](#0-1) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
The same divergence appears in every pull-request handler (`opened_handler.rb`, `closed_handler.rb`, `reopened_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `assigned_handler.rb`, `edited_handler.rb`, `label_capturing_handler.rb`), all of which call `Shipit::Repository.from_github_repo_name(params.repository.full_name)`.

`Shipit.github(organization:)` supports per-organization GitHub App configuration: [3](#0-2) 
```
def github(organization: github_default_organization)
  ...
  config = github_app_config(organization)
  raise GithubOrganizationUnknown, organization if config.nil?
  ...
  @github[organization] ||= GitHubApp.new(organization, config)
end
...
def github_app_config(organization)
  github_config = secrets.github.deep_transform_keys(&:downcase)
  github_organization = organization.downcase.to_sym
  github_config[github_organization]
end
```
This multi-org key layout is a documented, in-scope configuration shape (see `test/dummy/config/secrets_double_github_app.yml`), each organization having its own independent `webhook_secret`.

**The binding that is broken:** `organization authenticated (repository.owner.login) == organization whose secret is used to verify HMAC` is *not* the same binding as `repository written (repository.full_name) == repository actually mutated by the handler`. An attacker who is a legitimate GitHub App installer/admin for Organization A (and therefore knows or can trigger valid webhook deliveries signed with Org A's `webhook_secret`, e.g. by installing the app on a repo they control in Org A and firing a real event, or via any SSRF/replay of a legitimately-signed delivery) can craft/replay a payload whose `repository.owner.login` is `org-a/some-repo` (so `Shipit.github(organization: 'org-a')` is picked and the HMAC — computed over the full raw body with Org A's secret — validates, since the attacker controls that delivery) while setting `repository.full_name` to `org-b/target-repo`. Because Org A's HMAC only proves the payload was sent by someone possessing Org A's webhook secret, not that its `repository.full_name` belongs to Org A, the handler operates on `org-b/target-repo`'s stacks — an organization the attacker never authenticated against.

This directly matches the required pattern: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Handlers gated on this repository resolution execute state-changing, authorization-relevant actions on the resolved stack:
- `PushHandler#process` [4](#0-3)  triggers `stack.sync_github`, causing an unrelated organization's repository's commits/branch state to be resynced/mutated based on attacker-supplied `ref`/`after`.
- Pull-request handlers can `archive!`/`unarchive!` review stacks or create new ones (`ReviewStackAdapter#create!`), and update `PullRequest` records belonging to a completely different organization's repository, based on attacker-forged PR payload contents that were never verified against that organization's own secret.

This is a cross-organization/cross-repository write achieved purely by crafting the JSON body differently from the field used for authentication, without ever needing valid credentials for the victim organization. It matches the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Requires only: (1) legitimate control of the GitHub App/webhook secret for *some* organization configured on the same Shipit instance (a realistic scenario for a shared/multi-tenant deployment using the documented multi-org `github:` secrets layout), and (2) the ability to send an arbitrary JSON body with a valid signature for that organization (trivial once the secret is known, or by replaying/modifying a delivery before HMAC is computed client-side is not needed — the attacker who owns Org A's GitHub App can compute the HMAC themselves). No GitHub write access to the victim repo, no Shipit session, and no victim organization credentials are needed.

### Recommendation
Do not use two different fields for "which secret verifies this payload" and "which repository is mutated." After verifying the signature, re-validate that `repository.full_name`'s owner matches the `repository_owner` (or `organization.login`) that was used to select the signing organization/secret, and reject the webhook (422) if they diverge. Alternatively, restrict `Repository.from_github_repo_name` lookups performed by handlers to repositories belonging to the same verified organization.

### Proof of Concept
1. Instance is configured with two GitHub Apps, e.g. `secrets.github = { org_a: { webhook_secret: S_A, ... }, org_b: { webhook_secret: S_B, ... } }` (per `test/dummy/config/secrets_double_github_app.yml`), each installed on its respective organization, and `org_b/target-repo` has a Shipit stack.
2. Attacker administers the GitHub App installed on `org_a` and therefore possesses/can compute a valid HMAC-SHA1 signature using `S_A`.
3. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "org_a" }, "full_name": "org_b/target-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'org_a')` (from `repository.owner.login`), verifies against `S_A` — passes.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('org_b/target-repo')` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: <attacker sha>)` for a repository the attacker never authenticated for.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
