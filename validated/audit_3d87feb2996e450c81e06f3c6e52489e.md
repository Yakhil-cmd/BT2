### Title
Unprotected `InitializeBuffer` instruction lets an attacker seize authority over another user's freshly created buffer account - ([File: programs/bpf_loader/src/lib.rs])

### Summary
The `InitializeBuffer` handler in the BPF Upgradeable Loader sets the buffer account's `authority_address` from whatever pubkey is supplied as instruction account index 1, without requiring that account to be a signer. Any transaction sender can race a legitimate deployer's account-creation flow and initialize the buffer with an authority key of the attacker's choosing.

### Finding Description
`process_loader_upgradeable_instruction` handles `UpgradeableLoaderInstruction::InitializeBuffer` by only checking that the target account is currently `Uninitialized`, then unconditionally setting its state to `Buffer { authority_address: authority_key }`, where `authority_key` is simply `get_key_of_instruction_account(1)` — no signer check is performed on that account: [1](#0-0) 

This is directly analogous to the reported `L2EthToken.initialize()` bug: the initializing call is not bound to the legitimate creator's identity/signature, so whoever's transaction lands first on-chain wins the initialization. In the Solana deployment flow, a client normally: (1) `system_instruction::create_account` for the buffer keypair with owner set to `bpf_loader_upgradeable`, then (2) sends `InitializeBuffer` for that same account, followed by `Write`/`DeployWithMaxDataLen` calls gated on `authority_address` matching a signer: [2](#0-1) 

Because step (1) and step (2) are not atomic and `InitializeBuffer` does not require the "authority" account to sign, an unrelated third party can observe the pending/just-landed `CreateAccount` for the buffer address (which is a writable, `Uninitialized`, loader-owned account) and submit their own `InitializeBuffer` instruction naming themselves as `authority_address` before the legitimate deployer's `InitializeBuffer` transaction executes. Once initialized, any subsequent `InitializeBuffer` attempt by the legitimate owner fails with `AccountAlreadyInitialized`, and all authority-gated operations (`Write`, `SetAuthority`, `Close`, use as buffer in `DeployWithMaxDataLen`) now require the attacker's signature.

Critically, `Close` on a `Buffer` state redirects the account's lamports to an arbitrary recipient chosen by whoever signs as `authority_address`: [3](#0-2) 

Since the attacker who hijacked `InitializeBuffer` now legitimately holds `authority_address`, they can call `Close` and drain the buffer account's lamports (rent-exempt reserve paid for by the victim) to any account of their choosing.

### Impact Explanation
An unprivileged attacker can, purely by racing a public mempool/transaction observation, seize control of a victim's freshly created buffer account and subsequently drain its lamports via `Close`, or permanently deny the victim the ability to use the account for program deployment (since the victim no longer controls `authority_address`). This constitutes concrete unsigned fund movement: the victim funded the account (paid for its rent-exempt lamports via `CreateAccount`), but the attacker — without ever needing the victim's signature — gains sole authority and can redirect those lamports to themselves.

### Likelihood Explanation
Exploitation requires only observing a pending `CreateAccount`+`InitializeBuffer` sequence for a program-buffer account (a routine, publicly visible step of any BPF program deployment) and front-running the `InitializeBuffer` instruction with the attacker's own account as the "authority" argument — no special privileges, validator cooperation, or private information are needed, only ordinary transaction submission and typical MEV/mempool front-running capability.

### Recommendation
Require the `authority_address` account (instruction account index 1) to be a signer in `InitializeBuffer`, or alternatively require the buffer account creator (payer) to co-sign initialization, similar to how `Write`, `SetAuthority`, and `Close` already enforce `is_instruction_account_signer` checks on the authority. This closes the front-running window since only someone possessing the intended authority's private key could complete initialization.

### Proof of Concept
1. Victim signs and broadcasts `system_instruction::create_account` for buffer pubkey `B` with owner `bpf_loader_upgradeable`.
2. Victim's client is about to submit `InitializeBuffer` naming `authority_address = V` (victim's key).
3. Attacker observes `B` is a writable, `Uninitialized`, loader-owned account (e.g., via RPC `getProgramAccounts` scanning or mempool observation) and submits `InitializeBuffer` with accounts `[B, A]` where `A` is the attacker's own pubkey (not required to sign), which lands first.
4. `B`'s state becomes `Buffer { authority_address: Some(A) }` as shown at `programs/bpf_loader/src/lib.rs:169-171`.
5. Victim's own `InitializeBuffer` now fails with `AccountAlreadyInitialized` (`programs/bpf_loader/src/lib.rs:162-165`).
6. Attacker calls `Close` on `B` with themselves as signer for `authority_address` and any recipient pubkey, draining `B`'s lamports per `programs/bpf_loader/src/lib.rs:710-716` and `common_close_account`.

*Note:* I was unable to view the full body of `common_close_account` before running out of tool calls; based on the surrounding code and existing test coverage (`test_bpf_loader_upgradeable_set_buffer_authority`, `test_bpf_loader_upgradeable_initialize_buffer`), it enforces that the provided `authority_address` account is a signer, but I could not confirm its exact recipient-redirection logic with 100% certainty from source alone.
