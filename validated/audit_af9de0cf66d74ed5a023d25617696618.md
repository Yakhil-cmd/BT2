### Title
Reuse of the same L1 BTC lockup outpoint across multiple `register-for-bond` calls double-counts one Bitcoin commitment as collateral for multiple bonds - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`validate-l1-lockup` deduplicates a proven Bitcoin lockup outpoint (`txid` + `output-index`) only *within a single* `register-for-bond` call, via the fold-local `seen-outpoints` list. There is no persistent, contract-level map recording that a given L1 outpoint has already been consumed as collateral for a bond. Because the proof itself never gets marked as spent on the Stacks side, the same L1 BTC lockup proof can be resubmitted in a later, non-overlapping `register-for-bond` call by the same staker to back a second (or Nth) bond period, letting a single locked-BTC UTXO be counted as collateral more than once.

### Finding Description
`verify-l1-lockups` folds over the caller-supplied outputs via `validate-l1-lockup`, and the only anti-replay check is the in-fold `seen-outpoints` accumulator that rejects duplicates *inside the same call*: [1](#0-0) 

The output's script is checked against `construct-lockup-output-script`, which is a function of `staker`, `unlock-burn-height`, `staker-unlock-bytes`, and `early-unlock-bytes` — it does **not** bind the proof to a specific `bond-index`: [2](#0-1) 

`register-for-bond` only blocks a staker from having two *overlapping* memberships (`ERR_ALREADY_REGISTERED` via `bond-overlaps-new-position?`); once a staker's earlier bond period ends (or during the roll-over unlock window), they can call `register-for-bond` again for a new `bond-index`: [3](#0-2) 

Nowhere in `register-for-bond` / `verify-l1-lockups` / `validate-l1-lockup` is there a persistent map (e.g. `used-l1-outpoints`) that would prevent the exact same outpoint from being submitted again for a subsequent, non-overlapping bond. As long as the underlying Bitcoin timelock's baked-in `unlock-burn-height` is set far enough in the future to satisfy `>= minimum-unlock-height` for each later bond (`ERR_INVALID_UNLOCK_HEIGHT` check at lines 2074-2079), the staker can present the identical merkle/txid proof over and over for consecutive bond registrations, since the BTC itself is never actually re-locked or spent between calls.

This is the same bug class as the reported Sablier issue: a unique identifier meant to gate a single credit event (there: the Merkle leaf index; here: the L1 BTC outpoint) is checked for uniqueness only in a narrow, local scope (there: never checked at all; here: only within one fold call) rather than globally, allowing the same underlying commitment to be counted more than once.

### Impact Explanation
Each `register-for-bond` L1 path treats `sats-total` (derived from the proven BTC lockup) as the basis for `min-ustx-for-sats-amount`, i.e., it establishes how much STX collateral the sats "back." If the same L1-locked BTC output can be presented for multiple, sequential bond registrations, the protocol treats one real Bitcoin commitment as if it independently backs multiple bond periods' STX-collateral requirements (`is-l1-lock: true` in `protocol-bond-memberships`) — a double-counting of a Bitcoin-lockup commitment. This falls under the Critical impact category ("double-counting a commitment or reward"), since it lets a staker satisfy the sats-collateral requirement for more STX-locked bonds than the actual amount of BTC permanently locked would justify.

### Likelihood Explanation
Exploitation requires only that a staker deliberately create one on-chain Bitcoin timelock whose baked-in `unlock-burn-height` is set far enough in the future to satisfy several successive bonds' `minimum-unlock-height` checks, then reuse the identical (tx, header, merkle-proof, output-index) tuple in separate, non-overlapping `register-for-bond` calls. No signer/administrator cooperation or race condition is needed — it is a straightforward unprivileged repeat call using data the staker already possesses from their first registration. The main gating factor is bond-period non-overlap (`ERR_ALREADY_REGISTERED`), which is easily satisfied by waiting for/rolling into subsequent bond periods.

### Recommendation
Track used L1 outpoints persistently and globally (e.g., a `(define-map used-l1-outpoints { txid: (buff 32), output-index: uint } bool)` populated inside `validate-l1-lockup`), and assert that an outpoint has not previously been credited to *any* bond membership, not just within the current call's fold. Alternatively/additionally, bind the lockup script to the specific `bond-index` (include it in the script/witness derivation) so a given L1 lockup output can only ever satisfy one bond.

### Proof of Concept
1. Staker creates a single Bitcoin UTXO locked via the canonical timelock script from `construct-lockup-output-script(staker, unlock-burn-height = H_far, staker-unlock-bytes, early-unlock-bytes)`, where `H_far` is far enough in the future to satisfy the `minimum-unlock-height` of several future bonds.
2. Staker calls `register-for-bond(bond-index = N, ..., btc-lockup = ok {outputs: [proof for the UTXO], ...})`. `validate-l1-lockup` accepts it (script, amount, merkle proof, and per-call outpoint dedup all pass), and the staker's `sats-total` is credited to back bond `N` — [4](#0-3) .
3. Once bond `N`'s membership no longer overlaps (bond ended, or within its roll-over window), staker calls `register-for-bond(bond-index = N+6, ..., btc-lockup = ok {outputs: [the SAME proof tuple], ...})`. `bond-overlaps-new-position?` does not object because the two memberships don't overlap, and `validate-l1-lockup`'s `seen-outpoints` dedup only applies within the current call, so the identical outpoint is accepted again — the same locked BTC is now used as the collateral basis for a second bond period.
4. Repeat for further bond periods — one Bitcoin lockup transaction backs an unbounded number of separate bond registrations over time, each time satisfying `min-ustx-for-sats-amount` and being recorded with `is-l1-lock: true`.

Note: I was not able to fully trace the bond-exit/withdrawal path (`exit`/`withdraw-bond` logic) within the available iterations to confirm whether it independently re-verifies that the L1 UTXO is still locked/unspent at exit time; this would be a useful area for a background agent to double check, since it could either aggravate or partially mitigate the double-counting depending on how exit accounting is structured.
