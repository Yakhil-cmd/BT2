### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled`, allowing attacker-controlled `shipit.yml` review-stack creation with arbitrary `kubernetes.namespace`/`context` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` in [1](#0-0)  is written as `A && B || (C && D) || (E && F)`, but due to Ruby's `&&`/`||` precedence, the intended guard `repository.review_stacks_enabled &&` only binds to the first disjunct, not the second or third. This lets a repo with `review_stacks_enabled == false` and `provisioning_behavior == :prevent_with_label` still auto-create a `ReviewStack` for any unlabeled PR, whose `branch` is the attacker's own fork ref, allowing the attacker's `shipit.yml` (with attacker-chosen `kubernetes.namespace`/`context`) to reach `kubernetes-deploy` execution on the deploy host.

### Finding Description
The broken binding: the code intends `review_stacks_enabled == true` to gate **every** provisioning path, i.e. `provision? == review_stacks_enabled && (allow_all || (allow_with_label && has_label) || (prevent_with_label && !has_label))`. What is actually implemented is:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` has higher precedence than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. With `review_stacks_enabled == false` and `provisioning_behavior == prevent_with_label`, the third disjunct `prevent_with_label? && !has_label` evaluates independent of `review_stacks_enabled` and returns `true` for any PR without the provisioning label — so `provision?` returns `true` even though review stacks are supposed to be entirely disabled for the repo.

Call path: attacker opens a PR (`action == "opened"`) on their fork against a repo they don't control settings of; `OpenedHandler#process` calls `respond_to_pull_request_opened?` → `provision?` → true due to the bug → `ReviewStackAdapter#find_or_create!` → `create!` builds the stack with `stack_attributes`, where `branch: params.pull_request.head.ref` is the attacker's own fork branch [2](#0-1) . The new `ReviewStack` is queued via `Shipit::ReviewStackProvisioningQueue.add(stack)` [3](#0-2) , which drives provisioning/deploy against that branch. Since the deploy spec (`shipit.yml`) is resolved from the stack's `branch` (the attacker's fork ref), an attacker-controlled `kubernetes.namespace`/`kubernetes.context` value flows into `Kubernetes Discovery#deploy_steps`, producing a `kubernetes-deploy --max-watch-seconds ... <attacker_namespace> <attacker_context>` command line that is ultimately executed by `Command#start`/`PTY.spawn` on the deploy host.

No existing guard catches this: `respond_to_pull_request_opened?` only checks `params.action == "opened" && provision?` [4](#0-3) ; there is no separate, un-conditioned check of `repository.review_stacks_enabled` before calling `provision?`. The webhook signature/`ExplicitParameters` schema validate payload shape only, not this business-logic invariant, and `Repository`'s validations do not enforce any relationship between `review_stacks_enabled` and `provisioning_behavior`.

### Impact Explanation
An attacker who can open a pull request (no Shipit credentials required) can force Shipit to provision a review stack and run deploy commands on a repository where the operator explicitly set `review_stacks_enabled = false`. Combined with `kubernetes.namespace`/`kubernetes.context` values sourced from the attacker's own PR-branch `shipit.yml`, this yields command-line arguments to `kubernetes-deploy` under the attacker's control, executed via `PTY.spawn` on the deploy host against whatever contexts are configured there — an unauthorized deploy action. This matches the Critical category ("unauthorized deploy ... via `Command`/`PTY.spawn`"). Blast radius is limited to repositories that have `provisioning_behavior == prevent_with_label` configured (regardless of `review_stacks_enabled`), but is repeatable per PR/branch by the same or different attackers.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior == :prevent_with_label` (a legitimate, documented setting) combined with `review_stacks_enabled == false` (intended to fully disable review stacks) — a plausible operator configuration, e.g., disabling review stacks temporarily while leaving the provisioning behavior column at its label-based default. The attacker cost is trivial: open a PR without the provisioning label from a fork, no label needed, no privileged Shipit role needed. This is fully repeatable against any repository matching that configuration.

### Recommendation
Fix the boolean grouping to make `review_stacks_enabled` gate all branches:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the identical fix pattern anywhere the same construct is duplicated (e.g., `LabeledHandler#respond_to_label_change?` already explicitly ANDs `review_stacks_enabled` at the top level, but `archive?`/`unarchive?` should be reviewed for the same precedence issue).

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
1. Create a `Repository` fixture with `review_stacks_enabled: false`, `provisioning_behavior: "prevent_with_label"`.
2. Build webhook `params` for a PR `opened` event with `pull_request.labels == []` and `pull_request.head.ref == "attacker-branch"`.
3. Assert equality-before: expected `repository.review_stacks_enabled == false` should imply `OpenedHandler.new(params).send(:provision?) == false`.
4. Actual: call `OpenedHandler.new(params).process` (or the private `provision?` via `.send`) and assert it returns/creates a stack (`Shipit::ReviewStack.exists?(environment: "pr#{number}")` is `true`), demonstrating the equality is violated.
5. Follow-up (deploy-steps binding): construct a `DeploySpec::FileSystem`-backed spec loaded from a fixture `shipit.yml` containing `kubernetes: {namespace: "attacker-ns", context: "attacker-ctx"}`, call `deploy_steps`, and assert the resulting command array contains the literal strings `"attacker-ns"` and `"attacker-ctx"` verbatim, confirming pass-through into the `kubernetes-deploy` argv used by `Command#start`.
