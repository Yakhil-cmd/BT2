### Title
Permission whitelist in `initialize_with_permission` is checked against `payer`, not `creator` - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` derives its allowlist gate (`permission`) from the fee-paying `payer` account, while the `creator` field that is actually recorded as the pool's privileged `pool_creator` is a completely unchecked, non-signing account. This mirrors the UnionToken bug: the access-control check is bound to the transaction's payer/caller (`msg.sender`-analog) instead of to the entity that actually receives the privileged role (`from`-analog).

### Finding Description
In `InitializeWithPermission`, the whitelist PDA is derived solely from `payer`: [1](#0-0) 

`payer` is only required to sign and fund the transaction: [2](#0-1) 

but `creator` — the account that is written into `pool_state.pool_creator` and thereby granted ongoing creator-fee rights — is an `UncheckedAccount` with no signature requirement and no relationship to `payer` or to the `permission` PDA: [3](#0-2) [4](#0-3) 

The `Permission` account is an allowlist entry that only admin (or the designated `create_permission_pda_owner`) can create for a specific `permission_authority`: [5](#0-4) [6](#0-5) 

Because the on-chain check only proves "the `payer` of this transaction has a `Permission` record," and never checks that `creator` is the permissioned identity (or even requires `creator` to sign), anyone can submit `initialize_with_permission` with a whitelisted `payer` (e.g., a relayer/service account that holds a valid `Permission` PDA) and an arbitrary attacker-chosen `creator` address. The resulting pool's `pool_creator` privilege — which allows draining accrued creator fees via `collect_creator_fee` (gated only by `address = pool_state.load()?.pool_creator`) — is granted to that attacker-chosen address, not to the vetted/whitelisted identity: [7](#0-6) 

This contrasts with the ungated `Initialize` (public) instruction, where the same account is both the signer/payer and the `creator`: [8](#0-7) 

showing that `initialize_with_permission` intentionally splits the roles but fails to bind the whitelist check to the role (`creator`) that actually receives the privileged, gated capability.

### Impact Explanation
The permission allowlist is meant to restrict who may create permissioned pools and hold the associated `pool_creator` fee-collection rights (`collect_creator_fee` / `collect_creator_fee_permissionless`). Because the whitelist is enforced on `payer` rather than `creator`, a single permissioned account effectively acts as an unrestricted relay: any unprivileged caller can piggyback on that one permission to mint arbitrary `pool_creator` privileges for themselves or any address they choose, completely sidestepping the intended admin-controlled whitelist gate on pool creation and creator-fee entitlement.

### Likelihood Explanation
High. The exploit requires no special privileges beyond knowledge of one permissioned `payer` account's public key (which is derivable/observable on-chain via existing `Permission` PDAs) and does not require that account's signature to be attacker-controlled if the whitelisted party is a relayer/service that is willing to pay on behalf of others, or if the same permissioned identity is reused as `payer` for many unrelated `creator`s. The transaction is a single, ordinary call to `initialize_with_permission` with attacker-chosen `creator`.

### Recommendation
Bind the `permission` PDA derivation and the `Permission` account check to `creator` instead of (or in addition to) `payer`, and require `creator` to be a `Signer` so the permissioned identity provably consents to becoming `pool_creator`. Alternatively, add an explicit constraint asserting `creator.key() == permission.authority` (or `payer.key() == creator.key()`) before recording `pool_creator`.

### Proof of Concept
1. Admin creates a `Permission` PDA for `permission_authority = P` via `create_permission_pda`.
2. Attacker `A` (any unprivileged account) constructs a call to `initialize_with_permission` setting `payer = P` (or convinces/pays a service running as `P` to co-sign) and `creator = A`.
3. The `permission` account check succeeds because it is derived from `payer.key() = P`, which has a valid `Permission` record.
4. `pool_state.initialize(...)` records `ctx.accounts.creator.key()` i.e. `A` as `pool_creator`, even though `A` was never vetted/whitelisted.
5. `A` now calls `collect_creator_fee` (gated only by `address = pool_state.load()?.pool_creator`) to claim creator-fee revenue that was intended only for admin-approved creators.

#[derive(Accounts)]
pub struct CreatePermissionPda<'info> {
    #[account(
        mut,
        constraint = (owner.key() == crate::admin::ID || owner.key() == crate::create_permission_pda_owner::ID) @ ErrorCode::InvalidOwner
    )]
    pub owner: Signer<'info>,

    /// CHECK: permission account authority
    pub permission_authority: UncheckedAccount<'info>,

    /// Initialize config state account to store protocol owner address and fee rates.
    #[account(
        init,
        seeds = [
            PERMISSION_SEED.as_bytes(),
            permission_authority.key().as_ref()
        ],
        bump,
        payer = owner,
        space = Permission::LEN
    )]
    pub permission: Account<'info, Permission>,

    pub system_program: Program<'info, System>,
}

pub fn create_permission_pda(ctx: Context<CreatePermissionPda>) -> Result<()> {
    let permission = ctx.accounts.permission.deref_mut();
    permission.authority = ctx.accounts.permission_authority.key();
    Ok(())
}
