### Title
Webhook organization used for signature verification is decoupled from the repository the event handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using the `repository.owner.login` (or `organization.login`) field of the *unauthenticated* JSON body, but the event handlers that subsequently mutate state (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) operate on the full, unfiltered `params`, including `repository.full_name`/`repository.id`, which is never checked to belong to the organization whose secret validated the request. This breaks the binding: `organization authenticated == repository written`.

### Finding Description
The signature check is: [1](#0-0) 

`repository_owner` is computed purely from the attacker-controlled payload: [2](#0-1) 

and `verify_webhook_signature` trivially returns `true` whenever no `webhook_secret` is configured for that organization — a state explicitly documented as a supported, optional configuration (`docs/setup.md`, "Webhook secret (optional)"): [3](#0-2) 

Once `verify_signature` passes, the full raw JSON `params` (not scoped to `repository_owner`) is handed to every registered handler: [4](#0-3) 

In a multi-organization Shipit deployment (`Shipit.github(organization:)` supports per-organization `webhook_secret`/`app_id` — see `lib/shipit.rb` `TOP_LEVEL_GH_KEYS`), an attacker can:
1. Craft a JSON body where `repository.owner.login` (or `organization.login`) is set to any organization Shipit has configured **without** a `webhook_secret` (a documented-valid, low-friction setup).
2. Set `repository.full_name`/other repository identifiers inside the same payload to point at a completely different, unrelated stack/repository (one belonging to an organization that *does* have a properly protected GitHub App).
3. POST directly to `/webhooks` with the fabricated `X-Github-Event` header and no valid signature at all — `verify_webhook_signature` short-circuits to `true` because it only checks whether *the org named in the payload* has a secret, not whether the repository actually being acted upon does.

Handlers then process the forged event against the real target stack (e.g. queuing `GithubSyncJob`, recording commit `Status`, creating check-suite refreshes, or creating `Team`/`User` records via the `membership` handler) as verified by the test suite's own webhook fixtures, which show handlers keying off `repository`/`commit` fields independent of the org used for `verify_signature`: [5](#0-4) [6](#0-5) 

### Impact Explanation
This lets a fully unprivileged, unauthenticated network caller forge GitHub events (push syncs, commit statuses, check-suite refreshes, team/user membership) against an arbitrary stack/repository that it has no relationship with, by only needing to know the name of *any* organization Shipit trusts that happens to be configured without a webhook secret. Forged `status`/`check_suite` events can flip CI gating used by the merge queue (`ci.require`/`ci.blocking` in `shipit.yml`), and forged `push` events can trigger `GithubSyncJob` against unrelated stacks — a cross-repository write/trust bypass, matching the Critical "unauthorized deploy" and High "unauthenticated ... task streams" impact classes described in the rules.

### Likelihood Explanation
Any Shipit deployment that manages multiple GitHub organizations (a documented, supported configuration per `docs/setup.md` "Using Multiple Github Applications") and where at least one of those organizations has not set a `webhook_secret` (also explicitly documented as optional) is exposed. No credentials, sessions, or GitHub App access are required — only knowledge of one configured organization's login name and the target repository's `full_name`.

### Recommendation
Bind the verified organization to the repository being acted upon: after `verify_webhook_signature` succeeds, re-validate that `repository.full_name`'s owner matches the same `repository_owner` used to select the GitHub App, and reject payloads where they diverge, regardless of whether a `webhook_secret` is configured for that organization. Alternatively, require a `webhook_secret` for every configured organization to be present, and validate every payload against the store owning the target repository, not merely the organization named at the top of the payload.

### Proof of Concept
Assume `secrets.yml` configures two orgs: `openorg` (no `webhook_secret` set) and `victimorg` (properly secured, hosting stack `victimorg/prod-app`).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "repository": {
    "owner": { "login": "openorg" },
    "full_name": "victimorg/prod-app"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
`verify_signature` resolves `Shipit.github(organization: "openorg")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured), so no `X-Hub-Signature` header is even required. The `push` handler then processes the event against `victimorg/prod-app` (identified via `repository.full_name`), enqueuing `GithubSyncJob` for that stack despite the request never having been authenticated against `victimorg`'s GitHub App.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
