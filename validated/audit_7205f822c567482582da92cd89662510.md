Missing upper-bound validation on `timestamp`/`mci`/`age` values in address/asset definitions allows permanent freezing of counterparty funds in shared/escrow addresses - ([File: definition.js])

### Summary
`validateDefinition()` in `definition.js` accepts `timestamp`, `mci`, and `age` op arguments as long as they pass only `isNonnegativeInteger(value)` — there is no upper bound. Just like `createVestingSchedule`'s `_start`/`_cliff` arguments, a value that is astronomically far in the future (or otherwise nonsensical) is accepted as a "valid" definition. When such a clause is embedded in a co-owned address (shared address / arbiter-contract escrow, both constructed and exchanged between two independent, mutually untrusted parties via `wallet_defined_by_addresses.js` and `arbiter_contract.js`), the counterparty ends up locked out of a spending branch that they believed was time-bound and recoverable, because the "unlock after timestamp X" branch can never realistically become true.

### Finding Description
In `definition.js`, `validateDefinition()` handles the `mci`/`age`/`timestamp` ops: [1](#0-0) 
The only numeric check performed is `isNonnegativeInteger(value)`, i.e., value ≥ 0 and integer — there is no ceiling. This is the address/asset-definition-level analog of the report's `_start`/`_cliff`/`duration`/`_slicePeriodSeconds` bugs: a numeric time parameter that governs when funds become spendable is accepted with no sanity range.

This op is directly reachable by any two mutually-distrusting wallet users who set up a *shared address* — e.g., a payment escrow, an arbiter contract, or any custom co-signed address — since a `timestamp`/`mci`/`age` condition is a normal, documented way to build "either party can spend after time X" or "refund after timeout" branches. The relevant code paths that accept and only lightly validate such attacker/peer-supplied definitions are:
- `wallet_defined_by_addresses.js`'s `handleNewSharedAddress()`, which calls `validateAddressDefinition()` → `Definition.validateDefinition()` on a definition received from a peer device: [2](#0-1) [3](#0-2) 
- `arbiter_contract.js`'s `deriveSharedAddress()`, which builds an `["or", [...]]` definition combining both parties' addresses and data-feed/oracle conditions for an escrow arrangement between an "offeror" and an "acceptor": [4](#0-3) 

Because `timestamp`/`mci`/`age` values are accepted at any magnitude, a party proposing such a shared/escrow address (or the value used inside a `definition template` that gets filled with peer-controlled params) can set a "refund after timestamp T" fallback branch to a value effectively unreachable (e.g., far beyond any realistic timestamp/mci the network will ever produce), while presenting the counterparty with what looks like a legitimate time-locked refund clause. The counterparty, believing they can eventually reclaim their share of the funds via the time-based branch, signs and funds the shared address, and their funds become permanently unspendable through that branch.

### Impact Explanation
High: funds locked in a shared/escrow address behind an unreachable `timestamp`/`mci`/`age` clause can never be recovered through that clause. If it was the only fallback/refund branch offered to the counterparty (e.g., in an arbiter contract or vesting-style escrow built on ocore addresses), that counterparty's coins are frozen indefinitely, matching the "AA/definition fund freezing" impact class.

### Likelihood Explanation
Low, mirroring the original report: it requires one of the two co-signing parties (or a template author) to embed an out-of-range time value, whether through error or malicious intent, when proposing a shared/escrow address to a counterparty who does not independently validate the numeric sanity of the clause before signing/funding the address.

### Recommendation
Add sensible upper bounds to the `timestamp`, `mci`, and `age` (and correspondingly the `min_mci` argument used by `in data feed`/`in merkle`) checks in `validateDefinition()` (`definition.js` lines 480-495 and 476), e.g., reject `timestamp` values that are absurdly far from `objValidationState.last_ball_timestamp`/current time, and reject `mci`/`age`/`min_mci` values far beyond any plausible future MCI. Additionally, wallet-side code that accepts peer-proposed shared-address definitions (`handleNewSharedAddress`, `deriveSharedAddress`) should independently sanity-check any time-based unlock/refund clauses before allowing the user to fund the resulting address.

### Proof of Concept
1. Peer A proposes a shared/escrow address to Peer B using a definition of the form:
   `["or", [ ["address", "B_ADDR_ONLY_WITH_SECRET_COND"], ["and", [["address","B_ADDR"], ["timestamp", [">", 99999999999999]]]] ]]`
   presented as "B can reclaim funds after timestamp 99999999999999 if the deal falls through."
2. `validateDefinition()` accepts this because `isNonnegativeInteger(99999999999999)` is true, with no upper-bound check (`definition.js:491-492`).
3. B, believing the refund branch is legitimate, cosigns and funds the shared address via `wallet_defined_by_addresses.js`/`arbiter_contract.js` flows.
4. Because the network's real timestamp will never approach `99999999999999` within any practical timeframe, B's refund branch never becomes satisfiable, and B's coins under that address are effectively frozen forever unless A cooperates via the other branch.
