### Title
`StatusHandler` resolves commits globally by SHA, bypassing the organization binding enforced by webhook signature verification - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App configuration of a single organization, derived from the payload's `repository.owner.login` (or `organization.login`) field. [1](#0-0)  That verification only proves "this payload was signed with organization X's webhook secret." It does not constrain which database rows the event handler is allowed to mutate. `StatusHandler`, however, ignores the repository/organization context entirely and updates **every** `Commit` row in the whole Shipit instance whose `sha` matches the payload, regardless of which stack/repository/organization owns that commit. [2](#0-1) 

### Finding Description
The binding that should hold is:
`organization authenticated by verify_webhook_signature == organization whose repositories are written by the handler`

Before/after this binding breaks:
- **Before (intended)**: `Shipit.github(organization: repository_owner)` selects the webhook secret for organization X, so only a status event legitimately signed by organization X's GitHub App installation should be able to influence stacks belonging to organization X's repositories. [3](#0-2) 
- **After (actual)**: Once the signature check passes, `Shipit::Webhooks.for_event(event)` dispatches the raw parsed payload to `StatusHandler`, which does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a query with no `stack_id`/`repository` scoping at all. [2](#0-1) 

Compare this with `Handler#stacks`, used by every other handler (e.g. `PushHandler`), which properly scopes to `Repository.from_github_repo_name(repository_name)` before touching any stack. [4](#0-3)  `StatusHandler` is the outlier: it does not use `stacks` or `repository_name` at all, so the repository field that was part of the signed payload is never checked against the commit being updated.

On a Shipit deployment that hosts multiple organizations (a documented, supported configuration - "Using Multiple Github Applications" [5](#0-4) ), an attacker who controls their own GitHub organization/App installation (and thus legitimately knows its `webhook_secret` and can trigger arbitrary `status` webhook deliveries for their own repositories) can forge a status event carrying any `sha` value that happens to match a commit belonging to a *different* organization's stack tracked by the same Shipit instance (e.g. shared upstream history, forked/mirrored repos, or simply the same open-source commit hash tracked in two configured stacks). The signature check succeeds (it only verifies the attacker's own org's secret), but `StatusHandler` applies the forged status (state, description, target_url, context) to the matching `Commit` row belonging to the victim organization's stack via `create_status_from_github!` → `add_status`. [6](#0-5) 

### Impact Explanation
`Commit#status` drives `deployable?`, which gates whether a commit can be deployed/merged: `!locked? && (stack.ignore_ci? || (success? && !blocked?))`. [7](#0-6)  Forging a `success` status on a victim commit can unblock CI gating and trigger `stack.schedule_merges` and continuous delivery via `schedule_continuous_delivery`. [8](#0-7) [9](#0-8)  This is a cross-repository/cross-organization write that can lead to an unauthorized deploy — matching the "unauthorized deploy" High-severity impact class, since it is triggered purely by an unprivileged party who only controls their own GitHub organization webhook, not the victim's.

### Likelihood Explanation
Exploitability requires: (1) a multi-organization Shipit deployment (explicitly documented/supported), and (2) a `sha` collision between a commit the attacker can trigger a webhook for (their own repo) and a commit tracked in a victim stack. Since SHA-1 commit hashes are content-derived, this is not trivially forgeable for arbitrary content, but is realistic for forks/mirrors of the same upstream history (a very common Shipit use case — organizations mirroring public repos or shared internal forks) where identical commits legitimately exist under multiple owners with the exact same SHA. This keeps likelihood moderate rather than universal, but the root-cause code defect (missing scoping) is unconditionally present.

### Recommendation
Scope `StatusHandler#process` to the repository indicated by the verified payload, mirroring the base `Handler#stacks` pattern:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This binds the mutated `Commit` rows to the same repository/organization that was authenticated by `verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled GitHub App/installation, attacker knows its `webhook_secret`) and `OrgVictim` (victim's stack), as supported by the multi-app config schema. [5](#0-4) 
2. Identify (or arrange, e.g. via a shared upstream/fork) a commit SHA `S` that exists both in a repository under `OrgA` and in `OrgVictim`'s tracked stack.
3. Trigger (or directly send, since the attacker owns the GitHub App/webhook config for `OrgA`) a `status` webhook event with `repository.owner.login = OrgA`, `sha = S`, `state = success`, signed with `OrgA`'s legitimate `webhook_secret`.
4. `WebhooksController#verify_signature` succeeds using `Shipit.github(organization: "OrgA")`. [3](#0-2) 
5. `StatusHandler#process` runs `Commit.where(sha: S)`, finds the `OrgVictim` commit, and applies the forged `success` status to it. [2](#0-1) 
6. If this makes `deployable?` true for the victim's commit, `schedule_merges`/`schedule_continuous_delivery` may act on it, resulting in an unauthorized deploy/merge for `OrgVictim` triggered entirely by `OrgA`'s webhook credentials.
