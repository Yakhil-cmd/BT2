### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler resolves and mutates the target repository from the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . Once the signature is accepted, `Shipit::Webhooks::Handlers::Handler#repository_name` and every concrete handler (`PushHandler`, `PullRequest::ClosedHandler`, etc.) resolve the actual `Repository`/`Stack` records to mutate using a completely separate field, `payload.dig('repository', 'full_name')` [2](#0-1) [3](#0-2) . These two fields are never checked for consistency.

### Finding Description
This is the same completeness-check bug class as H-4: a value that is computed/used for a "commit"-like decision (which key material authenticates the message) is never bound to the value that is actually acted upon (which repository record is written to). In Pico, `global_cumulative_sum` was computed and placed in public values but never asserted to be zero when `flag_complete` — i.e., the "authorized" state and the "committed" state diverged. Here:

- **Authenticated side**: `repository_owner` (from `repository.owner.login`, falling back to `organization.login`) picks the `GitHubApp` config (and thus the `webhook_secret`) used in `verify_webhook_signature` [4](#0-3) .
- **Acted-upon side**: `repository_name` (from `repository.full_name`) is what every handler uses via `Repository.from_github_repo_name` to load the `Repository`/`Stack` scope that gets mutated (`stack.sync_github`, `review_stack.archive!`, commit statuses, etc.) [2](#0-1) [5](#0-4) .

Shipit explicitly supports multiple independently-configured GitHub Apps/organizations, each with its own `webhook_secret`, keyed by organization name in `secrets.github` [6](#0-5) , exactly as documented in "Using Multiple Github Applications" [7](#0-6) . In that (documented, supported) deployment mode, an org owner who legitimately controls the GitHub App / webhook secret for their own organization ("OrgA") can sign an arbitrary JSON payload with OrgA's `webhook_secret`, set `repository.owner.login = "OrgA"` (so `verify_signature` succeeds against OrgA's app), but set `repository.full_name = "OrgB/some-repo"` for a repository belonging to a different, unrelated organization onboarded to the same Shipit instance. The controller/handler layer never checks that these two fields agree, so the request is accepted as authentic and dispatched to mutate OrgB's `Stack`/`Repository` records.

The binding that should hold is:
`organization_that_authenticated(repository.owner.login) == organization_owning(repository.full_name)`
but this equality is never asserted anywhere between `WebhooksController#verify_signature` and the handler dispatch in `WebhooksController#create` [8](#0-7) .

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding called out explicitly in the analog rules. Concretely, with `PushHandler`, an attacker who controls OrgA's webhook secret can forge a `push` event with `repository.full_name` pointing at OrgB's tracked repository and an arbitrary `after` SHA, causing `stack.sync_github(expected_head_sha: ...)` to run against OrgB's stack [5](#0-4) . With `PullRequest::ClosedHandler`, the same trick lets the attacker archive a review stack belonging to OrgB [9](#0-8) . Depending on which handler is targeted, this is a cross-repository/cross-organization write into stacks the attacker's GitHub App/organization has no legitimate relationship to — this maps to the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Requires that the Shipit instance be configured with the multi-organization GitHub App schema (a documented, supported configuration) and that the attacker legitimately controls one of the onboarded organizations' GitHub App (and therefore its own `webhook_secret`) — not the target organization's secret, and not any Shipit session or `ApiClient` token. No repository-write access to the *victim* repository, no Shipit account, and no privileged Shipit role is required; only control of an independent GitHub App entry already trusted by the same instance.

### Recommendation
In `WebhooksController#verify_signature` / `#create`, or centrally in `Handlers::Handler`, assert that the organization used to select the verifying `GitHubApp` (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before dispatching to any handler. Reject the request (e.g., `head(422)`) if they differ.

### Proof of Concept
Given a Shipit instance configured for two GitHub organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md`'s multi-org example):
1. Attacker controls `OrgA`'s GitHub App and thus knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a JSON payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, payload)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret [4](#0-3) .
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` via `repository_name` (`repository.full_name`) [2](#0-1) , and `process` calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on OrgB's stack [5](#0-4) , despite the request never being authenticated for OrgB.

(Note: exploitation strictly requires the multi-org GitHub App configuration to be in use; this could not be independently verified beyond the documented/supported configuration path and the code paths cited above, since no live deployment was available to test against.)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
