### Title
Excess unbonded pool balance is dropped and stuck when `withdraw_unbonded` caps `balance_to_unbond` to `transferable_balance` while sub-pools/points are already fully dissolved - ([File: substrate/frame/nomination-pools/src/lib.rs])

### Summary
`pallet-nomination-pools::withdraw_unbonded` computes `balance_to_unbond` by fully dissolving the member's unlocked points from the relevant sub-pool(s), then caps the *transferred* amount with `.min(transferable_balance)`. Because the sub-pool balance/points are already permanently deducted inside the `fold` regardless of this cap, any amount above `transferable_balance` is silently dropped from the pool's internal accounting while the underlying tokens remain in the pool account. For pools still using the deprecated `TransferStake` strategy, there is no "dangling balance" reclamation path (unlike `DelegateStake`, which supports `member_delegation_balance` / `do_claim_trapped_balance`), so the excess becomes permanently stranded in the pool account.

In `withdraw_unbonded` (`substrate/frame/nomination-pools/src/lib.rs`), the withdrawal amount is computed as: [1](#0-0) 

The `.fold` unconditionally calls `era_pool.dissolve(*unlocked_points)` (and `sub_pools.no_era.dissolve(...)`), which mutates/reduces the sub-pool's `points` and `balance` for the *entire* set of `withdrawn_points` (obtained from `member.withdraw_unlocked(active_era)`, which also permanently removes those points from the member). Only *after* this full dissolution is the resulting `balance_to_unbond` clamped via `.min(T::StakeAdapter::transferable_balance(...))`.

The clamped amount is then transferred with: [2](#0-1) 

For the `TransferStake` adapter, `transferable_balance` simply returns the pool account's `reducible_balance`: [3](#0-2) 

and critically, `member_delegation_balance` always returns `None` for `TransferStake`: [4](#0-3) 

Back in `withdraw_unbonded`, the "dangling" reclamation logic that would otherwise recover any gap between accounting and actual balance only fires when `member_delegation_balance` returns `Some(..)`: [5](#0-4) 

Since `TransferStake::member_delegation_balance` always returns `None`, this branch always resolves to `dangling_withdrawal = Zero::zero()` for pools using `TransferStake`. Consequently, the difference between the fully-dissolved `balance_to_unbond` (as tracked in the sub-pool ledger) and the amount actually transferred (capped by `transferable_balance`) is neither transferred to the member nor retained in any accounting structure — it is simply orphaned inside the pool account with no code path to ever claim it for `TransferStake` pools. The generic `do_claim_trapped_balance` recovery function is explicitly gated to the `Delegate` strategy only: [6](#0-5) 

The pallet's own code comment acknowledges the scenario where the transferable balance of the pool account can be less than what the sub-pool ledger believes is available (e.g. dusting before the last member withdraws, or a slashing-hook bug leaving `sub_pools.balance` stale) and explicitly optimizes for "gracefully proceed" rather than reverting: [7](#0-6) 

This is architecturally the same bug class as the reported `BlueBerryBank::withdrawLend`: the code takes `min(computed_amount, actual_available)` for the *transfer*, but the *internal ledger* (there: `pos.underlyingAmount`; here: `sub_pools` balance/points and the member's `unbonding_eras`) is already reduced by the full uncapped amount, so the shortfall becomes permanently unaccounted-for and stuck.

Reachability: `withdraw_unbonded` is a standard signed, permissionless-in-many-cases extrinsic (`Call::withdraw_unbonded`) callable by any pool member (or, under the documented permissionless conditions, by any account on behalf of a destroying pool/depositor). No privileged role, governance action, or malicious validator/collator is required — only ordinary `unbond`/`withdraw_unbonded` sequencing by legitimate pool members while the pool uses the (still-supported, though deprecated) `TransferStake` adapter.

### Impact Explanation
Tokens legitimately owed to withdrawing pool members (or still nominally accounted for pool bookkeeping) become permanently locked in the pool's account, unreachable by any subsequent call, once the member's points/sub-pool balance have already been reduced to reflect the full unlocked amount. This is a fund-freezing bug (loss of member funds) rather than a "stuck contract balance recoverable later" issue, since there is no salvage path for `TransferStake` pools. Given `TransferStake` remains a supported, non-test adapter in-tree (only "deprecated", not removed) and is presumably still in use in some production runtimes that have not migrated to `DelegateStake`, this is a genuine asset-freezing risk. I could not, within the scope explored, definitively enumerate every concrete trigger condition that causes `transferable_balance < balance_to_unbond` in a fully realistic runtime (e.g., precise interplay with existential deposit reaping, `reducible_balance` semantics, and slashing-hook staleness); the pallet's own comments indicate the authors are aware such a gap can occur, but I was not able to fully confirm a minimal concrete numeric scenario or exclude that `reducible_balance`/ED handling always keeps `transferable_balance >= balance_to_unbond` in practice for `TransferStake`.

### Likelihood Explanation
Medium: the code comment in `lib.rs` (lines ~2486-2492) explicitly documents that the pool's stash can become dusted or the sub-pool balance can become stale relative to the actual account balance ("this check is also defensive in cases where the unbond pool does not update its balance"), which is precisely the condition needed to trigger this bug for `TransferStake` pools. However, exploiting it does not require any attacker action beyond normal, permissionless usage of `unbond`/`withdraw_unbonded`, but does require a pre-existing accounting/dusting divergence that I was unable to reproduce concretely with the tools available in this pass.

### Recommendation
For `TransferStake` pools, either (a) do not zero out/dissolve sub-pool points and balance beyond what is actually transferable — i.e., cap the *dissolution* itself to `transferable_balance` rather than capping only the outgoing transfer, leaving the shortfall represented in the sub-pool ledger for future retry; or (b) extend the "dangling balance" reclamation mechanism (`do_claim_trapped_balance`) to also support `TransferStake`, tracking excess pool-account balance not backed by any member's points and allowing it to be claimed once the pool account's liquidity recovers.

### Proof of Concept
I was not able to construct and execute a concrete minimal Rust/FRAME integration test within this pass demonstrating the precise pre-state (`transferable_balance < balance_to_unbond` for a `TransferStake`-strategy pool via non-privileged member actions) required by the reproduction requirements. The existing test suite (`substrate/frame/nomination-pools/src/tests.rs`, `mod withdraw_unbonded`) only exercises this "min-capping" logic for the `DelegateStake` mock adapter (`DelegateMock`), where the shortfall is correctly recovered via `dangling_delegation`/`released_balance` events (e.g. `Event::Withdrawn { balance: 20, points: 40 }` followed by `MemberRemoved { released_balance: 20 }` in `substrate/frame/nomination-pools/src/tests.rs:3884-3919`). I did not find (nor was able to author, given tool constraints) an equivalent test exercising the pure `TransferStake` adapter path with a real accounting/liquidity gap, so I cannot assert with certainty that the gap is reachable end-to-end in a production runtime configuration versus being purely defensive/theoretical. This finding should therefore be treated as Medium-confidence pending an executed reproduction against `TransferStake`.
