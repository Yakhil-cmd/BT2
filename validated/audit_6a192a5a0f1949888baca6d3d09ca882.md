### Title
Cross-organization webhook forgery — signature checked against `repository.owner.login`'s app, but handlers act on `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit.github(organization: repository_owner)` selects the GitHub App/secret used to verify `X-Hub-Signature` based on `repository_owner`, a field parsed from the *same untrusted JSON body* (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves the actual `Stack`/`Repository` to mutate using a *different* field of that same body: `payload.dig('repository', 'full_name')`. Because per-organization `webhook_secret` is optional (`return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`), any organization configured without a secret becomes a universal signature bypass for webhooks whose "acted-upon" repository field points anywhere else.

### Finding Description
`Shipit` supports multi-organization configuration where each org has its own `GitHubApp` instance and optional `webhook_secret` (see `config/secrets.development.shopify.yml`, `lib/shipit.rb#github_app_config`). Verification of an inbound webhook happens in `WebhooksController#verify_signature`: [1](#0-0) 

Signature verification is delegated to `GitHubApp#verify_webhook_signature`: [2](#0-1) 

Critically, if the resolved organization's `webhook_secret` is blank, verification returns `true` unconditionally — no signature is required at all.

`repository_owner`, the value used to pick *which* org's `GitHubApp`/secret to check, is itself taken from the unverified JSON payload: [3](#0-2) 

Once verification passes (trivially, if the chosen org has no secret), the raw payload is dispatched to handlers. Every handler determines the actual target `Repository`/`Stack` using a **different** field from the same body — `repository.full_name` — via `Handler#repository_name`/`#stacks` or per-handler `Repository.from_github_repo_name(params.repository.full_name)`: [4](#0-3) [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used for key selection) and `repository.full_name` (used for the actual write target) are independent, attacker-controlled JSON fields with no cross-field binding or shared cryptographic coverage tied to the *specific* org that owns the target repo, an attacker can:

1. Configure/observe that the Shipit instance is multi-org (`Shipit.github_organizations`), and that at least one configured organization has `webhook_secret` unset (a state explicitly shown as a normal/default configuration in `config/secrets.development.shopify.yml` and `config/secrets.development.example.yml`, both showing `webhook_secret: # nil`).
2. Craft a forged webhook body (e.g., a `push`, `pull_request`, `status`, `check_suite`, or `membership` event) where `repository.owner.login` = the no-secret organization (so `verify_signature` trivially passes with no valid HMAC needed), but `repository.full_name` = `victim-org/victim-repo`, a repository belonging to a *different*, secret-protected organization.
3. POST this to `/webhooks`. `verify_signature` calls `Shipit.github(organization: 'no-secret-org')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` without checking any HMAC.
4. `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` then runs handlers that resolve the stack via `repository.full_name`, i.e., the victim org's repo, and act on it — e.g. `PushHandler` enqueues `GithubSyncJob` for the victim stack (`expected_head_sha` from attacker-controlled `after`), `StatusHandler` writes fabricated commit statuses, `PullRequest::OpenedHandler`/`ClosedHandler`/`LabeledHandler` create/archive/unarchive review stacks, `MembershipHandler` creates/deletes team memberships.

This breaks exactly the equality the scan targets: **organization authenticated (`repository_owner`, used to pick the verification secret) ≠ repository written (`repository.full_name`, used by handlers to select the target Stack)**. Nothing in the engine enforces `repository.owner.login == repository.full_name.split('/').first`.

### Impact Explanation
This crosses an authentication boundary: an attacker with no GitHub credentials, no Shipit session, and no knowledge of any *victim* organization's `webhook_secret` can trigger authenticated-looking webhook actions against any Stack in the installation, as long as any other configured organization in the same Shipit deployment lacks (or has a leaked) `webhook_secret`. This is not merely a spoofed commit status — `PushHandler`/`GithubSyncJob` triggers pipeline state changes (e.g., commit ingestion, potentially influencing which commit is considered "deployable"/"undeployed" and downstream trigger of continuous deployment via `Stack.schedule_continuous_delivery`), and `PullRequest` handlers can archive/unarchive review stacks or capture attacker-supplied `pull_request.labels` for a real repository, causing cross-repository state writes performed by the Shipit app's own GitHub credentials. This satisfies the "cross-repository writes" / "unauthorized deploy trigger" high/critical bar via a webhook-signature confusion, analogous to the reported `MagicLP` bug where one signed/trusted quantity (locked totals) diverged from the quantity actually used to compute economic state (targets vs. reserves), enabling value extraction across the mismatch.

### Likelihood Explanation
Requires the Shipit deployment to use the multi-organization GitHub config schema (`Shipit.github_default_organization` non-nil) with at least one organization lacking a `webhook_secret`. This is a real, documented, and default-looking configuration state (both shipped example secrets files ship `webhook_secret: # nil` for every org), making misconfiguration plausible in real deployments that manage multiple GitHub orgs, especially ones added later without immediately provisioning a webhook secret. No repository write access, session, or API token is needed by the attacker — only network access to `/webhooks`.

### Recommendation
- Verify the webhook signature using the secret of the organization that actually owns the repository referenced by `repository.full_name` (or `organization.login` for org-level events), not a value independently choosable by the payload.
- Require `webhook_secret` to be present for every configured organization; refuse to boot / refuse webhook processing if any organization is missing one (fail closed rather than "return true unless webhook_secret").
- Cross-check that `repository.owner.login` (or `organization.login`) is consistent with `repository.full_name`'s owner before dispatching to handlers, rejecting mismatches.

### Proof of Concept
Given a Shipit config:
```yaml
github:
  no-secret-org:
    app_id: 1
    installation_id: 1
    private_key: ...
    # webhook_secret: not set
  victim-org:
    app_id: 2
    installation_id: 2
    webhook_secret: "s3cr3t"
    private_key: ...
```
Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or any garbage value), body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefattackerchosen",
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
- `WebhooksController#repository_owner` returns `"no-secret-org"`.
- `Shipit.github(organization: "no-secret-org").verify_webhook_signature(...)` returns `true` immediately because `webhook_secret` is blank — [7](#0-6)  — regardless of the header value.
- `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("victim-org/victim-repo")` via `Handler#repository_name` — [4](#0-3)  — and enqueues `GithubSyncJob` with attacker-supplied `expected_head_sha` for the victim's real stack, with no valid signature ever having been produced by `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
