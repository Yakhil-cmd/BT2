The Ghost CVE concerns an authentication rate-limit bypass via spoofed `X-Forwarded-For` headers. The closest structural analog in this codebase is the Substrate JSON-RPC server's proxy-header handling in `get_proxy_ip` (`substrate/client/rpc-servers/src/utils.rs:249-286`), which is used only to determine per-IP rate-limit whitelisting/keys in `substrate/client/rpc-servers/src/lib.rs:357-371`. However, this mechanism is:

1. **Opt-in and defaults to distrust**: `rate_limit_trust_proxy_headers` defaults to `false`, and the CLI help text explicitly states operators must only enable it when the RPC server sits behind a reverse proxy that always sets these headers [1](#0-0) . This mirrors the exact mitigating stance the Ghost vendor itself recommends, so the code already implements the documented safe posture rather than a bypassable one.
2. **Not a runtime/user-entry vector**: This is node-operator RPC configuration, not a signed extrinsic, contract call, or XCM message path as required by the analysis method. It has no bearing on FRAME pallets, balances, staking, contracts, or bridges.
3. **Impact is DoS/rate-limiting only**: Even a misconfigured operator trusting spoofed headers would at most affect connection-level RPC throttling, which falls under explicitly excluded categories (resource-exhaustion/rate-limit claims, config-only findings) per the report's own exclusion rules.

A separate `RateLimiter` in `substrate/client/hop/src/rate_limit.rs:108-171` keys by cryptographic `SenderId` (derived from account, not IP), so it isn't susceptible to header-spoofing at all [2](#0-1) .

No demonstrable Critical/High analog involving theft, unbacked issuance, unauthorized dispatch, or chain-integrity break exists here.
