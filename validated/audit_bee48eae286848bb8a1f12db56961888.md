### Title
`initialize_with_permission` sets `pool_state.pool_creator` from an unchecked, non-signing account with no zero-address validation, permanently freezing creator fees — (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` accepts a `creator` account that is only an `UncheckedAccount` (not a `Signer`) and stores its key directly into `PoolState.pool_creator` with no validation that it isn't `Pubkey::default()` (the zero/all-zero address), unlike the analogous `require_keys_neq!(new_owner, Pubkey::default())` checks present in `update_config.rs`'s owner-setters.

### Finding Description
In `InitializeWithPermission`, `creator` is declared as an `UncheckedAccount<'info>` with only a doc comment (`/// CHECK: creator of pool`) and no ownership/signer constraint: [1](#0-0) 

The permission-gated caller is `payer` (validated via the `permission` PDA seeded on `payer.key()`), while `creator` is a completely independent, attacker-chosen account: [2](#0-1) 

At the end of the handler, `pool_state.initialize(...)` is called, which unconditionally copies `ctx.accounts.creator.key()` into `PoolState.pool_creator`, with no zero-address (or any other) validation: [3](#0-2) [4](#0-3) 

This is precisely the bug class described in the external report: a critical authority/owner field is set from caller-supplied input without excluding `Pubkey::default()`. The codebase's own admin setters (`set_new_protocol_owner`, `set_new_fund_owner`) demonstrate that the project is aware of this exact hazard and defends against it there: [5](#0-4) 

but the equivalent check is missing when `pool_creator` is set during pool creation via `initialize_with_permission`. Note that the sibling instruction `initialize` (permissionless pool creation) does not have this issue because there `creator` is a `Signer<'info>`, and nobody can produce a valid signature for `Pubkey::default()`: [6](#0-5) 

`pool_creator` subsequently gates both fee-collection paths:
- `collect_creator_fee` requires `creator` to be a `Signer` whose key equals `pool_state.pool_creator`: [7](#0-6) 
- `collect_creator_fee_permissionless` sends accumulated fees to an ATA whose authority is `creator` (still constrained to equal `pool_state.pool_creator`, but never validated as non-zero): [8](#0-7) 

### Impact Explanation
If `pool_creator` is set to `Pubkey::default()` at pool creation (either by mistake or intentionally by the permission-holding `payer`), the accrued `creator_fees_token_0`/`creator_fees_token_1` become permanently unrecoverable:
- `collect_creator_fee` can never be invoked because no one can produce a valid signature for the zero address.
- `collect_creator_fee_permissionless` would transfer the fees into an associated token account whose authority is the zero address — an account no wallet can ever control, permanently locking those tokens.

This is a permanent freezing of funds (accumulated creator fees) inside the protocol's vaults/ATAs, satisfying the "permanent freezing of user or LP funds" acceptance criterion.

### Likelihood Explanation
The `creator` account is a free-form `UncheckedAccount` supplied directly in the instruction's account list with no signer or non-default constraint, so any account that holds a valid `Permission` PDA can trigger this by simply passing the System Program ID (`11111111111111111111111111111111`, which is `Pubkey::default()`) as `creator` when calling `initialize_with_permission`. This requires no privileged escalation beyond the existing permission-gate that already allows pool creation, and can happen accidentally (fat-fingered client) as well as be triggered deliberately.

### Recommendation
Add a check that `ctx.accounts.creator.key() != Pubkey::default()` (e.g. `require_keys_neq!(ctx.accounts.creator.key(), Pubkey::default())`) in `initialize_with_permission` before calling `pool_state.initialize(...)`, mirroring the existing zero-address guards used in `update_config.rs`.

### Proof of Concept
1. Admin grants a `Permission` PDA to address `P` via `create_permission_pda`.
2. `P` (as `payer`) calls `initialize_with_permission`, supplying `creator = Pubkey::default()` (System Program ID) instead of a real wallet.
3. The instruction succeeds; `pool_state.pool_creator` is now `11111111111111111111111111111111`.
4. As swaps accrue creator fees (`creator_fees_token_0`/`_1` on `PoolState`), no one can call `collect_creator_fee` (no valid signer for the zero key exists).
5. Anyone calling `collect_creator_fee_permissionless` moves the fees into an ATA owned by `Pubkey::default()`, from which they can never be withdrawn — the funds are permanently frozen.
