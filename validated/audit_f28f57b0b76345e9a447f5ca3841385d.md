### Title
GitHub App installation token stored via `git credential approve` is exposed to any submodule sharing the same host as `--repo` - (File: main.go, function repoSync.RefreshGitHubAppToken / StoreCredentials)

### Summary
`RefreshGitHubAppToken` mints a short-lived GitHub App installation token scoped to the specific repo/org the app is installed on, and stores it via `StoreCredentials`, which calls `git credential approve` with the exact `git.repo` URL. Git's built-in `store`/`cache` credential helpers match credentials by protocol+host (and only by full path if `credential.useHttpPath` is enabled, which git-sync does not set), so any submodule URL under the same host (e.g. `github.com`) will receive the same token during `git submodule update --recursive`.

### Finding Description
`git.StoreCredentials` builds a `url=...\nusername=...\npassword=...` blob and passes it to `git credential approve` [1](#0-0) . `RefreshGitHubAppToken` calls this with `git.repo` (the primary `--repo` URL) and the installation token as the password [2](#0-1) . Git's credential subsystem, by default, does not scope credential lookups by full path — `credential.useHttpPath` defaults to false, meaning `git credential fill` matches on `protocol://host` only, not the specific repo path. Git-sync does not set `credential.useHttpPath=true` anywhere in the codebase (confirmed by search — no occurrences of `useHttpPath` in `main.go`).

When submodules are enabled (`--submodules`), git-sync recurses into `.gitmodules`-declared URLs during clone/fetch/checkout. If an attacker controls the content of the synced repository (an explicitly allowed threat model — "attacker controls repo content and refs"), they can add or modify `.gitmodules` to point a submodule at `https://github.com/attacker/other` — same host as the primary `--repo`, different repo/org. When git internally calls `git credential fill` for that submodule URL, the stored credential (the GitHub App installation token, keyed only by host) is returned and used to authenticate the fetch to the attacker's repository/server path.

This is a real secret-confinement failure: the GitHub App token, which is supposed to be scoped by GitHub's server-side authorization to only the installed repo/org, is functionally usable by the local git client against **any URL on the same host**, and git-sync's credential storage does nothing to prevent presenting it to attacker-chosen paths on that host. Whether the attacker can actually exfiltrate the token value depends on where the request goes (e.g., if attacker controls a git server on that host reachable via public internet — which is the case for github.com itself, they can just observe the Authorization header/Basic auth password git sends when fetching their "attacker/other" repo).

### Impact Explanation
If exploitable, this results in confidential credential (GitHub App installation token) disclosure to a repository/path the operator did not intend to grant access to, within the scope of the same host. This maps to a secret-disclosure / credential-leakage impact class. However, the actual damage is bounded: GitHub App installation tokens are scoped server-side to the specific repositories the app is installed on/granted access to — presenting the token to `attacker/other` doesn't grant the attacker access to any *other* repos via the GitHub API (GitHub authorizes token scope server-side, not just via the git credential local matching). The attacker's practical gain is capturing a copy of the live installation token (via HTTP Basic-Auth header sent to their attacker-controlled endpoint on the same host, if they can stand one up under that hostname — impossible for github.com's actual host, since that requires DNS/hosting control of github.com itself) OR simply confirming/using the token against a private repo they don't own but which happens to be under an org the app also has access to (unlikely, orthogonal to git-sync's control).

### Likelihood Explanation
Requires GitHub App auth flags to be configured (non-default, but a documented, supported feature) and `--submodules` enabled (non-default but documented). The attacker also needs the ability to modify `.gitmodules` in the synced repo (already an allowed precondition — "attacker controls repo content"). Critically, for the attacker to actually *observe* the leaked token, they would need to control a git server on the **same hostname** as the legitimate `--repo` (e.g., `github.com`), which they do not — they only control repo content, not DNS/hosting for that host. Without control of an endpoint on that host, the token is merely presented to the same well-known server (e.g., real github.com) for a repo they don't have access to, which will simply fail authorization; no secret is disclosed to the attacker in that case. This significantly limits real-world exploitability.

### Recommendation
Set `credential.useHttpPath=true` (or equivalent per-URL scoping) when storing GitHub App tokens and other narrowly-scoped credentials via `git config`, so git's credential matching includes the path and does not bleed across repos on the same host. Additionally, document/warn that GitHub App and other host-scoped credentials, when combined with `--submodules`, can be presented to any repo path under the same host unless `useHttpPath` is set, and consider isolating submodule fetches (e.g., via `--credential` for specific submodule URLs, or explicit host+path credential entries) rather than relying on git's coarse host-level default matching.

### Proof of Concept
```bash
# Setup: git config credential.helper store (default git-sync flow)
git config --global credential.helper "store --file $DIR/gitcreds"

# Simulate RefreshGitHubAppToken storing a token for the primary repo
printf 'url=https://github.com/org/repo\nusername=-\npassword=SECRET_APP_TOKEN\n' | git credential approve

# Simulate submodule fetch to an attacker-controlled repo path, same host
git credential fill <<EOF
url=https://github.com/attacker/other
EOF
# Expected (if vulnerable): output includes password=SECRET_APP_TOKEN
# because credential.useHttpPath is unset/false, so matching is host-only.

# Contrast: with credential.useHttpPath=true set for github.com,
# the same `git credential fill` call for attacker/other should NOT
# return SECRET_APP_TOKEN.
```
This test would confirm that `git-sync--009`'s failure to set `credential.useHttpPath` (no occurrence found anywhere in `main.go`) is what allows the token stored via `StoreCredentials`/`RefreshGitHubAppToken` [1](#0-0) [2](#0-1)  to be matched against a differing repo path on the same host.

```go
// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
```
