### Title
Fee-on-Transfer ERC20 Token Causes Inflated `RequestValueTransfer` Event and Counterpart Bridge Over-Mint or Insolvency — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeFee.sol`)

### Summary

`requestERC20Transfer` and `onERC20Received` in `BridgeTransferERC20.sol` pull tokens from the caller using `safeTransferFrom` for the nominal amount `_value + _feeLimit`, but never verify the actual balance change. For fee-on-transfer (deflationary) ERC20 tokens, the bridge receives fewer tokens than the nominal amount. The `RequestValueTransfer` event is then emitted with the full nominal `_value`, causing the counterpart bridge to mint or transfer the full `_value` to the recipient — more than was actually locked or burned on the source side.

### Finding Description

In `requestERC20Transfer`:

```solidity
// BridgeTransferERC20.sol line 133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

The bridge pulls `_value + _feeLimit` tokens. For a fee-on-transfer token with rate `r`, the bridge actually receives `(_value + _feeLimit) * (1 - r)`. No balance-before/after check is performed.

`_requestERC20Transfer` then calls `_payERC20FeeAndRefundChange` which attempts to transfer `fee` to `feeReceiver` and `_feeLimit - fee` back to the sender — both from the bridge's balance — and then emits `RequestValueTransfer` with the full nominal `_value`:

```solidity
// BridgeTransferERC20.sol line 91, 97-107
uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);
...
emit RequestValueTransfer(
    TokenType.ERC20, _from, _to, _tokenAddress,
    _value,          // <-- nominal, not actual received
    requestNonce, fee, _extraData
);
``` [2](#0-1) 

`_payERC20FeeAndRefundChange` in `BridgeFee.sol` transfers fee and refund using nominal amounts:

```solidity
// BridgeFee.sol line 74, 78
IERC20(_token).safeTransfer(feeReceiver, fee);
IERC20(_token).safeTransfer(from, feeRefund);
``` [3](#0-2) 

The counterpart bridge's operators observe the `RequestValueTransfer` event and call `handleERC20Transfer` with the full nominal `_value`:

```solidity
// BridgeTransferERC20.sol line 68-72
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
``` [4](#0-3) 

The same path is reachable via the 1-step `onERC20Received` entry point, where the token contract itself calls the bridge after transferring tokens:

```solidity
// ERC20ServiceChain.sol line 44-46
function requestValueTransfer(...) external {
    require(transfer(bridge, _amount.add(_feeLimit)), "requestValueTransfer: transfer failed");
    IERC20BridgeReceiver(bridge).onERC20Received(msg.sender, _to, _amount, _feeLimit, _extraData);
}
``` [5](#0-4) 

`onERC20Received` passes the nominal `_value` directly to `_requestERC20Transfer` without any balance check. [6](#0-5) 

### Impact Explanation

**Mint/burn mode:** The counterpart bridge mints `_value` tokens to the recipient, but only `_value * (1 - r) - feeRefund` tokens were actually burned on the source chain (or the burn itself reverts if the bridge balance is insufficient). This constitutes an unauthorized mint of bridged assets on the counterpart chain proportional to the token's transfer fee rate.

**Lock mode:** The source bridge retains `(_value + _feeLimit) * (1 - r) - _feeLimit` tokens but the counterpart bridge attempts to transfer the full `_value`. If `(_value + _feeLimit) * (1 - r) - _feeLimit < _value`, the bridge becomes insolvent for this token, and subsequent `handleERC20Transfer` calls drain tokens deposited by other users.

The exact corrupted value is the `valueOrTokenId` field in the `RequestValueTransfer` event: it records the nominal `_value` instead of the actual net amount received by the bridge after the token's internal transfer fee.

### Likelihood Explanation

Token registration requires `onlyOwner` (`BridgeTokens.sol` line 57–71), so an arbitrary user cannot register a new token. [7](#0-6) 

However, once a fee-on-transfer token is registered by the owner (possibly without awareness of its transfer-fee behavior), **any user** can call `requestERC20Transfer` or trigger `onERC20Received` with that token. The exploit requires no special privilege beyond holding the registered token. Service-chain bridge operators are expected to support a variety of tokens, making accidental registration of a fee-on-transfer token a realistic scenario.

### Recommendation

- **Short term:** In `requestERC20Transfer`, record `balanceBefore = IERC20(_tokenAddress).balanceOf(address(this))` before the `safeTransferFrom` call and compute `actualReceived = balanceAfter - balanceBefore`. Use `actualReceived` (minus the fee portion) as the bridged value in the `RequestValueTransfer` event and for the subsequent burn.
- **Long term:** Establish a token integration checklist that explicitly flags fee-on-transfer tokens as incompatible with the bridge's current accounting model, and consider adding an on-chain registry flag (analogous to `needCheckBalance`) that operators must set before a token can be used for transfers.

### Proof of Concept

1. Owner registers a fee-on-transfer ERC20 token `FeeToken` (2% transfer fee) on both sides of the bridge.
2. Alice calls `requestERC20Transfer(FeeToken, Bob, 1000, 100, "")` on the source bridge.
3. Bridge calls `safeTransferFrom(Alice, bridge, 1100)`. Due to the 2% fee, bridge receives `1078` tokens (1100 × 0.98).
4. `_payERC20FeeAndRefundChange` attempts to transfer `feeOfERC20[FeeToken]` to `feeReceiver` and refund the remainder of `_feeLimit` to Alice — both from the bridge's 1078-token balance.
5. `RequestValueTransfer` is emitted with `valueOrTokenId = 1000` (nominal).
6. In **mint/burn mode**: counterpart bridge operators call `handleERC20Transfer(..., 1000, ...)` → `mint(Bob, 1000)`. Bob receives 1000 tokens on the counterpart chain, but only ~978 tokens of value were actually consumed on the source chain. The shortfall of ~22 tokens per transfer is an unauthorized mint.
7. In **lock mode**: counterpart bridge calls `safeTransfer(Bob, 1000)`. If the source bridge's net retained balance is less than 1000, the transfer reverts or drains other users' deposits.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
