### Title
Liquidation `SeizeMode::Credit` to the liquidated account itself resurrects seized collateral via a stale in-memory `Account` copy - (File: contracts/controller/src/positions/liquidation/apply.rs)

### Summary
`liquidate` accepts `SeizeMode::Credit(receiver_id)` and resolves the receiver into a **second, independently loaded in-memory `Account`** via `resolve_seize_receiver` (contracts/controller/src/positions/liquidation/mod.rs:53-55). If the liquidator passes the liquidated `account_id` as the receiver, the flow debits seized supply shares from one in-memory copy (`account`) and credits them into the other (`receiving_account`), which is a stale snapshot taken before the seizure — the same bug class as CVE-2024-50274 (using a resource snapshot/pointer whose authoritative state has moved on). `finalize_position_flow` then persists the receiver copy **after** the liquidated account copy, overwriting the seizure debit and leaving the account with its original collateral plus the credited (bonus-inclusive) shares — minting unbacked supply shares.

### Finding Description
In `liquidate` (contracts/controller/src/positions/liquidation/mod.rs:42-137):

1. `let mut account = storage::get_account(env, account_id)` loads the liquidated account.
2. `resolve_seize_receiver(env, liquidator, account_id, &account, seize_mode, &mut cache)` loads the receiver account. For `Credit(existing_id)` the caller-side docs require "the receiving ID is not the liquidated account", but the enforcement surface in the read code path only requires owner-or-active-delegate authority and `PositionMode::Normal`. If a liquidator owns/controls the liquidated account's NFT (or is its delegate), nothing in `apply_liquidation_share_credit` rejects `receiver_id == account_id` — the only cross-checks are `receiver.spoke_id == account.spoke_id` (apply.rs:165-169, trivially true) and a fee-split arithmetic assertion (apply.rs:170-174).
3. `apply_liquidation_share_credit` debits `seized_scaled` from `account.supply_positions` via `update_or_remove_supply_position(account, ...)` (apply.rs:177-179) and credits `liquidator_scaled` into `receiver.supply_positions` (apply.rs:188, `credit_supply_shares`). When receiver == liquidated account, `receiver` was loaded before the debit, so it still contains the pre-seizure position; the credit adds bonus shares on top.
4. `finalize_position_flow` first persists `account` (mod.rs:114-121 — the correctly debited map), then persists `receiving_account` (mod.rs:123-133), overwriting `ControllerKey::SupplyPositions(account_id)` with the stale map: original position + credited shares.
5. `check_bad_debt_after_liquidation` only removes the account if `borrow_positions` is empty or debt is socializable (apply.rs:308-315). A partial liquidation that leaves residual non-dust debt keeps the account alive with the inflated supply.

The persisted result is `original_supply + bonus_shares` instead of `original_supply − seized`: collateral shares equal to the seized leg (plus the liquidation bonus) are duplicated out of thin air. The liquidator repays debt but effectively keeps all collateral, and can withdraw the resurrected shares afterward — pool cash is drained against shares that should have been burned.

### Impact Explanation
Theft of user funds and protocol insolvency. Every partial liquidation with `SeizeMode::Credit(own_account_id)` converts seized collateral into free supply shares for the attacker's own account. The attacker repays a chosen small debt leg, self-seizes collateral with the HF-based bonus, and the share map is overwritten with pre-seizure plus credited shares. Repeating or fully liquidating lets the attacker extract other suppliers' pool cash — the duplicate shares redeem against real reserves while the seized debt was never actually collateralized.

### Likelihood Explanation
Reachable by any unprivileged address: the attacker supplies collateral, borrows, moves the price (or waits for it), and calls `liquidate` on their own account with `SeizeMode::Credit(their_account_id)`. Self-liquidation authority is satisfied because the attacker owns the account NFT (`is_owner_or_delegate`, account.rs:116-127). The exploit needs only a liquidatable position and `Credit` mode support — both permissionless entrypoints. The only open dependency is that `resolve_seize_receiver` does not contain an explicit `receiver_id != account_id` guard (not visible in the reviewed lines); if such a guard exists there, this path is blocked and the finding reduces to a defense-in-depth note.

### Recommendation
In `resolve_seize_receiver` (or at the top of `apply_liquidation_share_credit`), assert `receiver_id != account_id` and panic with `GenericError::InvalidPayments` on equality — mirroring the kernel fix's "don't dereference the stale object" approach by refusing to hold two mutable snapshots of the same account. Additionally, `credit_supply_shares` could re-read the receiver position from a single canonical `Account` rather than a second load, and `persist_account_positions` could reject persisting the same `account_id` twice in one flow.

### Proof of Concept
1. Attacker `supply(hub A: USDC, X)` then `borrow(hub A: ETH, D)` on account `N` (spoke S, Normal mode).
2. Price moves so `N` is liquidatable but not socializable bad debt (e.g., HF < 1, collateral above the dust cap so `is_socializable_bad_debt` is false and residual debt remains).
3. Attacker calls `liquidate(liquidator=attacker, account_id=N, debt_payments=[(ETH, d)] partial, seize_mode=Credit(N))`. Auth passes: attacker owns NFT `N`.
4. `apply_liquidation_share_credit` debits seized USDC shares from `account` copy and credits net shares into the stale `receiving_account` copy of `N`.
5. `finalize_position_flow` writes `account`'s debited map, then overwrites with `receiving_account`'s inflated map (mod.rs:114-133). `check_bad_debt_after_liquidation` sees remaining borrow positions and does not clean up.
6. Attacker calls `withdraw(N, USDC)` and redeems original collateral + bonus shares, having only paid the partial debt `d`. Net: collateral duplicated; pool cash drained.
