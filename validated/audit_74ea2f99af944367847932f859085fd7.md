### Title
Cross-organization webhook signature confusion allows forging commit statuses / triggering syncs on victim stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate an incoming webhook against based solely on `repository.owner.login` (or `organization.login`) taken from the *same untrusted JSON body it is trying to authenticate*. [1](#0-0) [2](#0-1)  Once the HMAC check passes for that organization's own secret, every downstream handler is free to reference a *completely different* field of the same payload (`repository.full_name`, or in the `status` event, a bare `sha` with no repository scoping at all) to decide what data to mutate. Because the field that is cryptographically bound (`repository.owner.login`) and the field that is actually acted upon (`repository.full_name` / commit `sha`) are never cross-validated against each other, any tenant that legitimately owns one configured GitHub organization/webhook secret in a multi-org Shipit deployment can forge webhook events that mutate state belonging to a different organization's stacks.

### Finding Description
`verify_signature` computes `repository_owner` from the request body itself and uses it to look up which org's webhook secret to validate the signature with: [1](#0-0) [2](#0-1) 

The signature is a valid HMAC-SHA1 over the raw body using the secret configured for whatever organization is named in the body (`Shipit.github(organization: repository_owner)`), per `GithubApp#verify_webhook_signature`. [3](#0-2)  This only proves the caller knows the secret associated with the org they *claim to be*; it says nothing about which repository/commit the rest of the payload references.

Handlers, however, resolve the actual target using unrelated fields:
- `Handlers::Handler#repository_name` reads `payload.dig('repository', 'full_name')`, independent of `repository.owner.login`. [4](#0-3) 
- `PushHandler#process` uses that repository/branch lookup to call `stack.sync_github(expected_head_sha: params.after)` on any matching stack. [5](#0-4) 
- `StatusHandler#process` is worse: it doesn't even use the repository at all — it matches **every** `Commit` row in the entire database by `sha` and calls `create_status_from_github!`, with zero scoping to the organization that was authenticated: [6](#0-5) 

`Commit#create_status_from_github!` → `Commit#deployable?` shows that a forged "success" status can make an otherwise non-CI-passing commit deployable: [7](#0-6) [8](#0-7) 

The binding that should hold is: `organization authenticated by signature == repository/commit whose data is written`. The engine instead only enforces `organization authenticated == organization named in one JSON field`, while separately trusting other JSON fields (`repository.full_name`, `sha`) that are never checked against that authenticated organization.

### Impact Explanation
In a Shipit deployment configured for multiple GitHub organizations (each with its own `webhook_secret`, as shown by the `github:` map supporting several orgs in `config/secrets.development.shopify.yml`/`template.rb`), a tenant that legitimately controls Organization A's webhook secret can:
1. Set `repository.owner.login` (or `organization.login`) to `"OrgA"` so `verify_signature` validates successfully against OrgA's known secret.
2. Set `sha` (for the `status` event) to the SHA of a commit belonging to a stack under a completely different, victim organization (`OrgB`), and `state: "success"`, to forge a passing CI status on that commit — because `StatusHandler` matches on `sha` globally with no repository scoping at all.
3. This can flip `Commit#deployable?` to `true` for a victim commit that never actually passed CI, enabling an **unauthorized deploy** of that commit once deploy criteria (`ignore_ci`/success) are (falsely) satisfied — this matches the explicit Critical impact "unauthorized deploy" in scope.
4. Similarly, `push`/`pull_request` handlers can be triggered against arbitrary victim stacks by setting `repository.full_name` to the victim repo while `repository.owner.login` matches the attacker's own authenticated org, causing spurious `sync_github` calls, review-stack archive/unarchive actions, etc. on repositories the attacker does not own.

This is a cross-tenant integrity break reachable by any org already onboarded to a multi-org Shipit instance, without needing a Shipit session, `ApiClient` token, `api_clients_secret`, or the victim's own webhook secret/private key.

### Likelihood Explanation
Exploitation only requires knowledge of one's own organization's webhook secret (which the attacker, as the admin who configured their org's GitHub App integration, legitimately possesses) and the ability to send a raw HTTP POST to the public `webhooks` endpoint — it does not require compromising GitHub, intercepting traffic, or obtaining any victim credentials. The victim commit's SHA is often public/discoverable information (e.g., visible via GitHub itself), making the `status` handler path (fully unscoped `Commit.where(sha: ...)` lookup) trivially reachable.

### Recommendation
Cross-validate the organization used for signature verification against the organization actually referenced by the payload's target repository/commit before dispatching to handlers, and scope `StatusHandler` (and any handler resolving records only by GitHub-provided identifiers such as `sha`) to the repository the request claims to originate from rather than matching globally across all stacks/organizations. Concretely: derive `repository_owner` once, verify the signature, and then require handlers such as `StatusHandler` to filter `Commit` by `stack.repository.owner == repository_owner` (or equivalent) instead of a bare `sha` match, and have `Handlers::Handler#repository_name`/its consumers assert `repository.owner.login == repository_owner` used for signature verification.

### Proof of Concept
Assume a multi-org Shipit instance with two configured organizations, `attacker-org` (attacker knows/configured `webhook_secret_A`) and `victim-org` (hosts stack `victim-org/victim-repo`, with a pending/failing commit `deadbeef...`).

1. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "deadbeef000000000000000000000000000000",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, raw_body)>` using their own known secret for `attacker-org`.
3. POST to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, loads `webhook_secret_A`, and the HMAC validates successfully. [1](#0-0) 
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: 'deadbeef...')` with no org/repo filter and calls `create_status_from_github!`, marking the victim's commit as having a successful `ci/required-check` status — even though the attacker has no relationship to `victim-org`. [6](#0-5) 
6. If that was the last blocking CI requirement, `Commit#deployable?` now returns `true` for the victim commit, and it can be deployed by anyone permitted to trigger deploys — an integrity bypass of `victim-org`'s CI gating enforced entirely through data the attacker was never authorized to write.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
