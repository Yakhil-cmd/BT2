### Title
Webhook signature verified against `repository.owner.login`/`organization.login` but the acted-upon repository is taken from a different field (`repository.full_name`), allowing cross-organization webhook forgery in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on an attacker-controlled JSON field (`repository.owner.login` or `organization.login`), while the actual repository that gets mutated (synced, its status updated, etc.) is looked up from a different attacker-controlled field, `repository.full_name`, in `Handler#stacks`/`#repository_name`. These two fields are never checked for consistency, breaking the intended binding "organization whose secret authenticated the request == organization that owns the repository being written to."

### Finding Description
`Shipit.github(organization:)` supports configuring one `GitHubApp` (and one distinct `webhook_secret`) per GitHub organization [1](#0-0) . When a webhook arrives, `WebhooksController#verify_signature` resolves the app/secret to verify against purely from the JSON body:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`verify_webhook_signature` just checks the HMAC of the raw body against the secret configured for that organization: [3](#0-2) 

Once verification passes, `create` dispatches the full raw payload to handlers (e.g. `PushHandler`) which resolve the repository to act on from a **different** JSON field:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) [5](#0-4) 

Because the JSON body is a single attacker-controlled blob whose fields are not cross-validated, `repository.owner.login` (used only to pick the HMAC key) and `repository.full_name` (used to pick the Stack/Repository to mutate) can point at two different organizations/repositories in the same signed request. An attacker who legitimately administers a GitHub App/webhook_secret for one organization ("OrgTwo", configured in Shipit's multi-org `secrets.github` map, e.g. as shown in `secrets_double_github_app.yml`) can sign a POST body whose `repository.owner.login`/`organization.login` is `"OrgTwo"` (so `verify_signature` fetches and validates against OrgTwo's known secret) while `repository.full_name` names a repository belonging to a completely different, unrelated organization ("OrgOne/some-repo") tracked by the same Shipit instance.

This breaks the equality that should hold: **organization authenticated by the signature == organization/repository the payload is allowed to mutate**. Nothing in `WebhooksController` or `Handler` enforces that `repository.owner.login == repository.full_name.split('/').first`.

### Impact Explanation
Handlers gated only by this signature check act directly on stack/task state for arbitrary repositories tracked by the Shipit instance, not just the organization whose secret was used:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for any stack matching the forged `full_name`/branch, regardless of the signing organization [6](#0-5) .
- Other handlers (`status`, `check_suite`, `pull_request`, `membership`, etc.) similarly resolve their target objects from payload fields independent of `repository_owner`.

This constitutes a cross-repository/cross-organization write: an attacker who is a legitimate, low-privilege GitHub App owner for one org configured in the Shipit instance can inject fabricated push/status/check-run events against a different org's repositories, causing incorrect commit statuses, triggering unwanted `GithubSyncJob`s, or corrupting deploy-relevant state (commit status = required for deploy safety checks) for repositories they don't control. This matches the "authentication bypass across a repository/organization boundary" impact category (a GitHub identity/secret scoped to one org is used to write into another org's tracked state).

### Likelihood Explanation
This requires the Shipit installation to be configured with multiple organizations (multi-org `secrets.github` config, as documented and tested in this repo via `secrets_double_github_app.yml`), and the attacker must hold legitimate control of at least one configured organization's GitHub App/webhook secret. This is a realistic operating mode for shared/hosted Shipit deployments serving several orgs, and does not require any Shipit account, API token, or repository write access — just knowledge of one org's own webhook_secret (which that org's own admins hold legitimately) and the ability to send an arbitrary POST to the shared `/webhooks` endpoint.

### Recommendation
After a signature is verified for organization `O` (derived from `repository_owner`), enforce that every entity the handler subsequently acts on (`repository.full_name`, `organization.login` used by other handlers, etc.) actually belongs to organization `O`. Concretely, in `WebhooksController#verify_signature`/`create`, validate that `params.dig('repository','full_name')&.split('/')&.first == repository_owner` (case-insensitively) before dispatching to handlers, and reject (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), both syncing repositories tracked by the same Shipit instance.
2. Attacker legitimately controls `OrgTwo`'s GitHub App and therefore knows `OrgTwo`'s `webhook_secret`.
3. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha, e.g. a malicious/failing commit already pushed to OrgOne/target-repo>",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "OrgOne/target-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgTwo_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgTwo")` (from `repository.owner.login`) and validates successfully against `OrgTwo`'s secret [7](#0-6) .
6. `PushHandler#stacks` resolves the target via `repository.full_name = "OrgOne/target-repo"`, finding and syncing the `OrgOne` stack that `OrgTwo`'s secret never authenticated [4](#0-3) , causing `stack.sync_github` to run for a repository outside the authenticated organization's scope.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
