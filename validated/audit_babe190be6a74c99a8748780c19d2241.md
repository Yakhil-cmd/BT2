## Title
Underpaying `gas` on Snowbridge V2 `Command::CallContract` (or `ContractCall::V1`) can cause the target-chain execution to revert while the attached `value` and delivery fee are irrecoverably consumed - ([File: bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs])

### Summary
Snowbridge's outbound queue V2 exposes a `Command::CallContract { target, calldata, gas, value }` command whose `gas` field is attacker/user-controlled and is used both to compute the delivery fee and as the actual gas forwarded to the target contract on Ethereum. This is structurally analogous to Optimism's user-controlled `l2Gas` parameter in `depositETHTo`/`depositERC20To`: if the supplied gas is insufficient for the target call to succeed, the call reverts on the destination chain, but on the source chain (BridgeHub/Polkadot) the message has already been committed/queued and the associated `value`/fee has already been withdrawn from the user or their agent.

### Finding Description
`Command::CallContract` carries a fully user-controlled `gas: u64` field: [1](#0-0) 

This `gas` value is used directly as the dispatch gas limit reported to the fee calculation and (via the `abi::CommandWrapper.gas` field) as the actual gas forwarded to the target contract on the Ethereum Gateway: [2](#0-1) [3](#0-2) 

The command is user-reachable: an XCM `Transact` on the source chain is converted into a `ContractCall`/`CallContract` command, which carries its own `gas` field supplied by whoever crafted the XCM message: [4](#0-3) 

The `gas` value is not validated against the actual computational requirements of the target call — it's an opaque, user-supplied upper bound that is trusted for both the fee charged and the amount forwarded to the destination.

The message pipeline (`snowbridge-pallet-outbound-queue-v2`) validates, enqueues, and commits the message (charging local processing fee and remote fee) before the relayer ever executes it on Ethereum: [5](#0-4) 

If the destination call requires more gas than the user supplied, execution on Ethereum reverts (out-of-gas), but the Polkadot-side commitment, delivery fee, and any `value` transferred to fund the `CallContract` (via the agent contract) have already been irreversibly deducted/locked, exactly mirroring the underpaid-`l2Gas` failure mode described in the Optimism bridge report: the deposit/action is committed on the source side while the destination-side execution can fail due to underestimated, user-chosen gas.

### Impact Explanation
This is an availability/fund-loss risk to end users, not a protocol-level fund theft or unbacked issuance. If a user underestimates `gas` for a `CallContract` invocation (e.g., a proxy call routed through an agent contract with attached `value`), the call can revert on Ethereum. Depending on the Gateway's handling of a failed dispatch (whether ether/value is refunded to the agent or is consumed regardless), the `value` and/or delivery fee may be unrecoverable or require a costly/impossible retry, since the same nonce/commitment has already been finalized on the source chain merkle-committed message set.

### Likelihood Explanation
Likelihood is Medium: this requires a user to construct a raw `CallContract`/`ContractCall::V1` message (typically via `Transact`) with an underestimated `gas` value — an ordinary user error, not a privileged or adversarial action, similar to the original Optimism finding. There is no on-chain enforcement/floor check tying the supplied `gas` to the encoded calldata's complexity, so a naive/miscalculated value is easy to submit.

### Recommendation
- Document clearly (in Snowbridge developer docs / XCM `Transact`-to-Ethereum guidance) that supplying insufficient `gas` for `CallContract` can cause irreversible loss of the attached `value` and fees if the target call reverts.
- Consider adding a sane minimum-gas floor check per target/calldata heuristics, or emitting a warning/dry-run estimate before commitment.
- Investigate whether the Ethereum Gateway contract can refund `value` back to the calling agent on a reverted dispatch rather than consuming it unconditionally, to reduce the blast radius of underpaid gas.

### Proof of Concept
No end-to-end PoC was executed. Investigation was limited to static code tracing within the indexed codebase snapshot (`bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs`, `.../mod.rs`, `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`, and `convert.rs`). I was unable to fully inspect `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs` (only match locations were returned, not full content) to confirm exactly how `value`/`gas` are validated when converting an XCM `Transact` into `ContractCall`/`CallContract`, nor could I inspect the Solidity Gateway contract logic for what happens to attached `value` on a reverted dispatch (out of scope of the indexed Rust codebase). These gaps mean the exact fund-loss mechanics on the Ethereum side (whether value is refunded or burned on revert) remain unverified and should be confirmed by a Devin session with full repository and Solidity-contract access before treating this as a confirmed, exploitable finding rather than a plausible structural analog.

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
