### Title
Unbounded in-memory buffering of git subprocess stdout/stderr enables memory-exhaustion DoS from a malicious/untrusted git server - (File: pkg/cmd/cmd.go)

### Summary
Every `git` subcommand executed by `git-sync` (including `git fetch` against the configured, potentially attacker‑influenced remote) has its entire stdout and stderr captured into unbounded, in-memory `bytes.Buffer` objects with no maximum size enforcement, mirroring the root cause described in the SEDA report (missing size limit on subprocess output buffers).

### Finding Description
All git invocations in `git-sync` are funneled through `runWithStdin` in `pkg/cmd/cmd.go`: [1](#0-0) 

Both `outbuf` and `errbuf` are plain `bytes.Buffer` values with no cap on how much data `cmd.Run()` may write into them before returning, and the resulting `stdout`/`stderr` strings are then propagated further (returned to callers, embedded into `fmt.Errorf` messages, and logged verbatim via `log.V(6).Info(...)`), exactly analogous to how the SEDA report describes stdout/stderr being "collected without size limits and passed through multiple layers of memory allocation and copying." [2](#0-1) 

This runner is used for the core sync path, including `git fetch` from the configured remote: [3](#0-2) 

`git fetch` uses git's sideband protocol, through which the remote server can emit arbitrary `remote: ...` progress/informational text that git relays to stderr. Because `runWithStdin` places no bound on `errbuf`'s growth, a malicious or compromised upstream git server (the "untrusted repo content" source that `git-sync` is designed to pull from) can stream large volumes of sideband text during a single `fetch`, forcing `git-sync` to accumulate that entire payload in process memory before the call even returns.

### Impact Explanation
Because `outbuf`/`errbuf` are unbounded, a malicious remote can force unbounded memory growth in the `git-sync` sidecar process on every periodic sync cycle. This can exhaust the container's memory limit, causing the process to be OOM-killed by the kubelet/cgroup, or to crash outright — resulting in **persistent sync denial** (the sidecar can no longer complete syncs and application containers stop receiving updates), which matches one of the accepted impact categories.

### Likelihood Explanation
Likelihood is moderate: it requires the configured git remote/server (or content it relays, e.g., via `remote:` sideband messages during fetch) to be attacker-influenced/untrusted, which is within `git-sync`'s explicit threat surface (it fetches from a configured, potentially external, repository). No special flags are required — this affects the default `Run`/`RunWithStdin` path used by every git invocation, since there is no size-limiting wrapper anywhere in `pkg/cmd/cmd.go`.

### Recommendation
Wrap `cmd.Stdout`/`cmd.Stderr` with a size-limited writer (e.g., an `io.Writer` that truncates or errors once a configurable maximum, similar in spirit to `MAX_VM_RESULT_SIZE_BYTES` in the referenced fix) instead of raw `bytes.Buffer`, so that no single git invocation can cause unbounded memory allocation regardless of how much data the remote/server emits on stdout or stderr.

### Proof of Concept
1. Point `git-sync`'s `--repo` at a git server under attacker control (or a legitimate server compromised/configured to abuse the sideband channel).
2. Configure that server to emit an extremely large volume of `remote:` sideband text during the `upload-pack` negotiation for every `git fetch`.
3. `git-sync`'s periodic sync loop calls `git.Run(ctx, ..., "fetch", ...)`, which internally uses `runWithStdin` in `pkg/cmd/cmd.go` — `errbuf` (a `bytes.Buffer`) grows unbounded as it absorbs the entire sideband stream before `cmd.Run()` returns.
4. Repeating/enlarging this payload across sync cycles drives the sidecar's memory usage up until it is OOM-killed or crashes, denying further syncs. [4](#0-3)

func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
	log.V(6).Info("command result", "stdout", stdout, "stderr", stderr, "time", wallTime)

	return stdout, stderr, nil
}
