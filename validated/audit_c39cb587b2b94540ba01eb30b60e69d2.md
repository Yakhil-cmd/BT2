### Title
Webhook signature verification is bound to the wrong organization, letting one onboarded org forge GitHub events (push/status/pull_request/etc.) for another org's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which per-organization `webhook_secret` to HMAC-verify a payload against by reading `repository.owner.login` (falling back to `organization.login`) out of the *unauthenticated* request body itself, then hands the *entire same payload* to event handlers that resolve the target `Stack`/`Repository` from a completely different field: `repository.full_name`. Nothing ties these two lookups together, so a payload that is validly signed for organization A can name a repository belonging to organization B, and Shipit will act on B's stack.

### Finding Description
Signature verification: [1](#0-0) 
picks the verifying secret using: [2](#0-1) 

That is, `Shipit.github(organization: repository_owner)` looks up the org's `webhook_secret` from `secrets.yml` (per-organization config, see `config/secrets.development.shopify.yml`), and `verify_webhook_signature` just confirms the raw body was HMAC-signed with *that org's* secret: [3](#0-2) 

Once verification passes, `create` dispatches the *whole payload* to handlers: [4](#0-3) 

Handlers, however, resolve the affected stacks from a different, independent field — `repository.full_name` — not from `repository.owner.login`/`organization.login` that was used for signature verification: [5](#0-4) [6](#0-5) 

`PushHandler` and `StatusHandler` then act on whatever stack that `full_name` resolves to: [7](#0-6) [8](#0-7) 

**Binding broken (as required by scope):** *"an organization that authenticated" (`repository_owner`, used to pick the HMAC secret) ≠ "the repository that is written"* (`repository.full_name`, used by `Handler#stacks` / `Repository.from_github_repo_name` to pick the target `Stack`). The controller never asserts that the repository named in the payload actually belongs to the organization whose secret validated the signature.

In a Shipit deployment that onboards multiple independent GitHub organizations (each with its own entry, and its own `webhook_secret`, in `secrets.yml`/`Shipit.github`), any org admin who legitimately knows their *own* org's configured webhook secret (they configure it themselves when wiring up their org's GitHub webhook to Shipit's public `/github/webhooks` endpoint) can craft an arbitrary JSON body, set `organization.login` (or `repository.owner.login`) to their own org so it passes `verify_signature`, but set `repository.full_name` to a **victim org's stack**. Because `stacks` is keyed only off `full_name`, Shipit will act on the victim stack as if the event genuinely came from GitHub for that repository.

### Impact Explanation
This is a cross-organization forged-event/confused-deputy bug. Concretely, `StatusHandler` lets the attacker forge a `success` commit status (`commit.create_status_from_github!(params)`) for commits belonging to a stack they do not control: [9](#0-8) 
Shipit's CI-gating and merge/continuous-deployment logic (`required_statuses`/`StatusChecker`, continuous delivery scheduling) trusts `Status` records created this way when deciding whether a commit is deployable/mergeable: [10](#0-9) [11](#0-10) 
By injecting fabricated "green" CI statuses for a victim's stack, an attacker in a multi-tenant Shipit instance can make required CI checks appear satisfied, enabling an **unauthorized deploy or merge** on a repository they do not own — matching the Critical/High impact bar (unauthorized deploy/merge via cross-organization write). `PushHandler` similarly lets the attacker trigger `stack.sync_github` for a victim's stack on demand.

### Likelihood Explanation
Requires an attacker who legitimately administers at least one GitHub organization onboarded onto the same Shipit deployment (i.e., knows the `webhook_secret` value they themselves configured for their own org's webhook), and requires the target instance to be multi-tenant (hosting stacks for more than one organization in `secrets.yml`/`Shipit.github` config, which is an explicitly documented supported configuration — see `secrets.development.shopify.yml` listing multiple orgs). No Shipit session, `ApiClient` token, or GitHub write access to the victim's repository is needed — only a directly-POSTed, self-signed HTTP request to the public webhook endpoint. This is a realistic SaaS/multi-org deployment scenario for this engine.

### Recommendation
After signature verification, re-derive the organization implied by the *verified* field and require every downstream lookup (`Handler#stacks`, `Repository.from_github_repo_name`) to be scoped to that same organization — i.e., ensure `repository.full_name.split('/').first` (or `repository.owner.login`) equals the `repository_owner` that was used to select the verifying secret, and reject (422) the request otherwise. Do not let handlers resolve target stacks purely from unauthenticated payload fields that were not part of the value used to select the verification secret.

### Proof of Concept
1. Shipit instance configured with two orgs in `Shipit.github`, e.g. `attacker-org` (secret `S_A`, known to the attacker because they configured their own org's webhook) and `victim-org` (secret `S_V`, unknown to attacker), each with at least one onboarded `Stack`/`Repository`.
2. Attacker crafts a JSON body for a `status` event:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "victim-org/victim-repo", "owner": {} },
  "organization": { "login": "attacker-org" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(S_A, raw_body)>` using their own known secret `S_A`.
4. POST to `/github/webhooks` with header `X-Github-Event: status`.
5. `repository_owner` resolves to `"attacker-org"` (from `organization.login`, since `repository.owner.login` is absent) → `verify_signature` succeeds using `S_A`.
6. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) looks up `Commit.where(sha: params.sha)` — which belongs to `victim-org/victim-repo` — and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status for the victim's commit even though the request was never signed by `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
