## Analog Vulnerability Found

### Title
AA trigger identity is misattributed to `authors[0]` instead of the actual paying signer in multi-author units - (File: `aa_composer.js`)

### Summary
The Pulp advisory describes objects created inside an asynchronously-processed task being attributed to the wrong user — the *oldest* permission holder rather than the actual dispatcher — because the attribution logic used a proxy heuristic instead of the real actor. `ocore` has a structurally identical flaw in Autonomous Agent (AA) trigger processing: when an AA is triggered by a unit with multiple co-authors, the AA framework decides "who is interacting with the AA" (`trigger.address`) using an incidental ordering property — the alphabetically-first author address — rather than the address that actually supplied the funds/intent for the AA call.

### Finding Description
`getTrigger()` unconditionally sets the trigger's identity from the first author in the unit's `authors` array: [1](#0-0) 

Because `validateAuthors()` requires unit authors to be strictly sorted by address (`objAuthor.address <= prev_address` is rejected), `authors[0]` is simply whichever co-author address happens to sort alphabetically first — it has no relationship to which co-author actually funded the payment to the AA: [2](#0-1) 

Meanwhile, the actual AA payment amount (`trigger.outputs`) is computed independently by summing payment outputs addressed to the AA, with no requirement that the payer correspond to `authors[0]`: [3](#0-2) 

`trigger.address` (and its propagated `trigger.initial_address`) is then used pervasively by AA oscript code as "the sender/owner" — for example to assign object ownership, or as the destination for bounced/returned funds: [4](#0-3) [5](#0-4) 

A concrete real-world use of `trigger.address` for ownership assignment is shown in the shipped sample AA, where the paying address is recorded as the owner of a registered asset purely based on `trigger.address`: [6](#0-5) 

Any unprivileged user can construct a unit with multiple authors (up to `MAX_AUTHORS_PER_UNIT`) that pays into an AA — e.g. combining a co-author's UTXO purely as a "filler" input alongside the true payer's UTXO. If the filler co-author's address sorts before the true payer's address, `trigger.address` becomes the filler co-author, not the payer, even though the payer's funds are what the AA actually receives and processes.

### Impact Explanation
This is a direct analog of CVE-2024-7143's identity-misattribution root cause applied to fund/asset ownership: an AA that assigns ownership, records "who sent this", or refunds/bounces funds "to the sender" will attribute the outcome to the wrong co-author. Concretely:
- A malicious secondary co-author (who consents to being included in the unit, e.g. as a required fee-sharing party) can cause an AA's ownership-assignment logic (`var['owner'] = trigger.address`) to register an asset/state to themselves instead of the true payer, effectively stealing AA-issued assets or entitlements from the actual funder.
- On AA bounce, refunded bytes are sent to `trigger.address`, so bounced funds intended for the real payer can instead be routed to a different co-author of the same unit.

This causes unauthorized reassignment of AA-managed assets/state and misdirected fund flows — a concrete "AA fund loss" / unauthorized ownership scenario, matching the accepted impact categories.

### Likelihood Explanation
Exploitation only requires an attacker to get themselves included as a co-author of a multi-author unit that triggers a vulnerable AA (any AA whose oscript uses `trigger.address` for ownership/refund logic, such as the shipped `things_registry_and_marketplace` sample), and to control an address that sorts alphabetically before the victim co-author's address (trivially satisfiable by grinding an address, since ocore addresses are content hashes the attacker can choose the underlying definition/pubkey for). No special privileges, node cooperation, or race conditions are required — it is a pure unit-composition issue reachable by any unprivileged AA trigger sender.

### Recommendation
Do not derive `trigger.address` from `objUnit.authors[0].address` for multi-author trigger units. Either: (a) disallow/require single-author units for triggers whose AA logic depends on trigger identity, (b) require the AA definition/oscript to explicitly select which author paid (e.g., matching the payment message's implicit payer via `unit_authors`/`inputs` ownership rather than array position), or (c) document and enforce that multi-author AA triggers are non-attributable and disallow using `trigger.address` as an ownership key in that case, validating at AA-definition time that this ambiguity is handled.

### Proof of Concept
1. Attacker controls address `A` (grindable to sort before victim's address) and colludes/tricks a flow where victim address `V` needs to co-sign a joint unit (e.g., splitting header/payload commissions or combining inputs), with `V`'s output paying into AA `X` whose oscript does `var['owner_'||$id] = trigger.address` (as in `things_registry_and_marketplace.oscript`).
2. Attacker composes a unit with two authors, `A` and `V` (sorted `A < V`), where the payment message sends the register/purchase amount to AA `X` from an output effectively attributable to `V`'s funds, per `getTrigger()`'s output-scanning logic in `aa_composer.js` lines 379-396.
3. `getTrigger()` sets `trigger.address = objUnit.authors[0].address = A` per `aa_composer.js` lines 375-376, since `A` sorts first.
4. The AA registers the "thing" to `var['owner_'||$id] = A`, not `V`, even though `V` was the intended/actual payer — demonstrating unauthorized ownership attribution analogous to the Pulp RBAC misattribution bug.
