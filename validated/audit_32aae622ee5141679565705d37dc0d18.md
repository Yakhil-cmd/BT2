### Title
Donation-based manipulation of the pool's built-in TWAP oracle via unaccounted direct vault-balance transfers - (File: `programs/cp-swap/src/states/pool.rs`, `programs/cp-swap/src/instructions/swap_base_input.rs`, `programs/cp-swap/src/states/oracle.rs`)

### Summary
The core flaw in the referenced Ichi report is that the oracle's price is derived from live, directly-readable reserve balances (`getTotalAmounts()` → `balanceOf`) rather than an internally accounted reserve, so anyone can "donate" tokens straight to the vault to skew the price feed. Raydium `cp-swap` has an analogous pattern: its on-chain TWAP oracle (`ObservationState`) is fed, on every swap, with a spot price computed directly from the *live* SPL token-account balances of the vaults (`ctx.accounts.input_vault.amount` / `output_vault.amount`), not from an internally tracked reserve that only changes through `deposit`/`withdraw`/`swap` accounting.

### Finding Description
`swap_base_input` (and `swap_base_output`) read the vault balances straight off the passed-in `TokenAccount`s and pass them into `PoolState::get_swap_params`, which in turn calls `token_price_x32` to compute `token_0_price_x64`/`token_1_price_x64`: [1](#0-0) [2](#0-1) 

These prices are then written unconditionally into the pool's persistent oracle account: [3](#0-2) 

`ObservationState::update` accumulates `token_price_x32 * time_since_last_update` into the cumulative price array used for TWAP calculations: [4](#0-3) 

Because `input_vault.amount`/`output_vault.amount` are simply the SPL token account's live balance (any account, including the pool's PDA-owned vault, can receive an unsolicited SPL `Transfer` from anyone), an attacker can, within a single transaction:
1. Transfer tokens directly into `token_0_vault` or `token_1_vault` (a normal SPL transfer instruction, not a `deposit`/`swap` CPI, so it bypasses all pool accounting, fee bookkeeping, and `lp_supply` updates).
2. Immediately call `swap_base_input`/`swap_base_output` with a minimal trade amount.

The swap instruction re-reads the now-inflated vault balance and computes a heavily skewed `token_price_x32`, which is recorded into `ObservationState`'s cumulative accumulator weighted by `time_since_last_update` (the elapsed time since the last recorded observation) — not weighted by any measure of trade volume or cost incurred by the attacker. This lets an attacker cheaply implant an arbitrarily large price deviation into the pool's own TWAP for the entire elapsed window, exactly analogous to how the Ichi vault's price could be warped by donating token0/token1 directly to the vault to inflate `getTotalAmounts()`.

Note that the constant-product invariant check (`require_gte!(constant_after, constant_before)`) only validates the internal swap-fee math is not decreasing value; it does not detect or reject donations that occurred outside of the swap instruction, since `total_input_token_amount`/`total_output_token_amount` are derived from the (already inflated) live balances at the start of the very same instruction call. [5](#0-4) 

### Impact Explanation
The `oracle.rs` module states its purpose explicitly: "Oracle provides price data useful for a wide variety of system designs" [6](#0-5) , i.e., it is meant to be consumed by external protocols (e.g. lending/liquidation systems) as a TWAP price feed, mirroring the exact consumption pattern in the original Ichi report where a lending protocol read the vault-derived price as collateral valuation. A single attacker-controlled transaction can inject an arbitrary spot price into the accumulator with only the cost of a token transfer (fully recoverable by the attacker afterward since it is not burned or locked — it merely sits in the vault as unaccounted balance until reclaimed via further transfers/swaps or, if a future deposit is skipped, effectively donated). Any downstream integrator computing a TWAP over the manipulated window would get a materially wrong price, enabling over-borrowing, mispriced liquidations, or other insolvency-causing effects in the consuming protocol — the same high-severity impact class as the source report.

### Likelihood Explanation
Reachable by any unprivileged party with a single transaction using only standard, permissionless instructions (SPL `Transfer` to a known vault PDA address plus `swap_base_input`/`swap_base_output`, both of which take attacker-chosen `amount_in`/`minimum_amount_out`). No privileged signer, leaked key, or off-chain component is required. The attacker only needs the pool's vault addresses, which are public PDAs derivable from `POOL_VAULT_SEED`.

### Recommendation
Do not feed the oracle purely from the instruction's live vault balances that can be inflated by out-of-band transfers. Either (a) maintain the reserve amounts internally in `PoolState` and update them only through accounted operations (`deposit`/`withdraw`/`swap`), reconciling any surplus via an explicit `sync`-style instruction whose effect is bounded/rate-limited, or (b) weight the TWAP update by the swap's actual trade size/cost rather than raw elapsed time, and/or clamp per-swap price deviation similarly to how spot-vs-TWAP deviation checks are used elsewhere, so a single unaccounted balance change cannot dominate the cumulative price accumulator for an entire observation window.

### Proof of Concept
1. Attacker identifies pool `P` with vaults `V0`, `V1` and `ObservationState` account `O`.
2. Attacker submits one transaction containing:
   a. `spl_token::transfer` of a large amount of token_0 into `V0` (a plain, permissionless SPL transfer to the vault's public address).
   b. `swap_base_input` (or `swap_base_output`) on pool `P` with a minimal `amount_in`.
3. Inside `swap_base_input`, `ctx.accounts.input_vault.amount`/`output_vault.amount` reflect the inflated balance from step (a); `get_swap_params`/`token_price_x32` compute a skewed `token_0_price_x64`/`token_1_price_x64`.
4. `ObservationState::update` accumulates this skewed price weighted by `time_since_last_update`, corrupting the TWAP for that window — all done in a single transaction paid for only by the transferred tokens (which remain recoverable by the attacker through subsequent transfers/swaps).
