### Title
Withdraw permanently locks a user's LP position if their receiving token account for `token_0`/`token_1` becomes frozen or otherwise blocked from receiving transfers — ([File: programs/cp-swap/src/instructions/withdraw.rs])

### Summary
The external report's root cause is that a staking contract bundles reward-token transfers into the same atomic user action as unstaking, with no fallback "claim" path, so a single blocked transfer (USDC blacklist) permanently locks the user's principal. `raydium-cp-swap`'s `withdraw` instruction has the analogous structural flaw: burning the user's LP tokens and transferring out `token_0`/`token_1` happen in one atomic instruction with no alternative claim mechanism, so if either token's transfer to the user's own account can be blocked (e.g., a frozen SPL token account, which any mint with a freeze authority — such as USDC-style stablecoins — can impose), that specific LP provider can never withdraw again.

### Finding Description
`withdraw()` first computes amounts, then burns the user's LP tokens via `token_burn`, decrements `pool_state.lp_supply`, and only afterward performs `transfer_from_pool_vault_to_user` for `token_0` and then `token_1`: [1](#0-0) 

Because Solana instructions are atomic, if the second transfer (or either transfer) reverts — for example because `ctx.accounts.token_0_account` (owned/authorized by the withdrawing `owner`) has been frozen by the mint's freeze authority, or is a Token-2022 account subject to a blacklist-style restriction — the entire `withdraw` call reverts, including the LP burn. There is no separate "claim" or internal-balance accounting step comparable to what the external report recommends (`pendingBalances` + a distinct claim instruction). The instruction forces a synchronous transfer to the user's own account as a hard prerequisite for redeeming LP tokens, exactly the anti-pattern flagged in the report.

The `Withdraw` accounts struct requires `token_0_account`/`token_1_account` to already exist with `token::mint = token_*_vault.mint`, and does not allow specifying an alternate, unblocked destination: [2](#0-1) 

If the mint of `token_0` or `token_1` has a freeze authority (a standard SPL Token feature, used by many real-world-asset/stablecoin issuers to enforce blacklists) and that authority freezes the specific LP's associated token account, every subsequent `withdraw` call from that LP will fail at the transfer step, since the transfer function performs the CPI to the token program unconditionally: [3](#0-2) 

This mirrors `collect_creator_fee`/`collect_creator_fee_permissionless`, which similarly force a transfer to the creator's account as the only means of realizing accrued fees, with no internal-balance fallback: [4](#0-3) 

### Impact Explanation
Impact is High for the affected liquidity provider: their deposited principal (share of `token_0_vault`/`token_1_vault`), represented by LP tokens, becomes permanently unredeemable once their receiving account for either pool token is frozen/blacklisted, since `withdraw` provides no alternative claim path and always attempts a synchronous transfer to that same account. This matches the external report's "permanent freezing of user funds" criterion, scoped to the individual affected user (not a pool-wide insolvency).

### Likelihood Explanation
Likelihood is Low, consistent with the original report: freeze-authority/blacklist enforcement is an edge-case administrative action by the token issuer, not a routine operation. It requires a pool to include a mint with an active freeze authority (or comparable blacklist mechanism) and that authority to freeze the specific LP's token account.

### Recommendation
Decouple LP redemption from the forced token transfer. Either (a) allow the withdrawing user to redirect proceeds to an arbitrary destination token account they control (so they can use a non-frozen account), or (b) adopt an internal-accounting/claim pattern: burn LP and credit an internal "pending withdrawal" balance keyed by token, then expose a separate `claim` instruction that performs the transfer, so a blocked transfer for one token does not prevent the LP burn/accounting update from completing.

### Proof of Concept
1. Pool is initialized with `token_0_mint` = a standard SPL token that has an active freeze authority (e.g., a stablecoin mirroring USDC's blacklist behavior) — accepted by `initialize` since no check excludes mints with a freeze authority: [5](#0-4) 
2. LP provider deposits and receives LP tokens normally via `deposit`.
3. The freeze authority freezes the LP provider's `token_0_account` (their own ATA for `token_0`).
4. LP provider calls `withdraw` with a valid `lp_token_amount`; execution proceeds through the LP burn at line 179-186 and then reaches `transfer_from_pool_vault_to_user` for `token_0` at line 188, which fails because the destination account is frozen, reverting the entire instruction (including the burn).
5. Every subsequent `withdraw` attempt fails identically; the LP provider's LP tokens remain intact but can never be redeemed, permanently freezing their share of the pool.
