### Title
Unfiltered PR label names injected into process environment enable `GIT_TEMPLATE_DIR` RCE on review-stack `git clone` - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the environment hash with no key allowlist, and this hash flows unfiltered through `TaskCommands#env`/`DeployCommands#env` into `Shipit::Command#unbundled_env`, which is passed straight to `PTY.spawn` for every git and deploy command the stack runs, including `git clone`. An attacker who can label a PR on a `review_stacks_enabled` repository can therefore set arbitrary environment variable names, including `GIT_TEMPLATE_DIR`, which git honors on `clone`/`checkout` to copy attacker-controlled hook scripts into the new repository and execute them.

### Finding Description
The broken binding: `Command#unbundled_env` should equal `BASE_ENV.merge(PATH).merge(@env)` where `@env` contains only operator/spec-approved keys, but for review stacks `@env` actually equals `Stack#env.merge(pull_request.labels.each_with_object({}){|n,h| h[n.upcase]='true'})` with **no key allowlist** [1](#0-0) .

Path:
1. GitHub webhook `pull_request` payload updates `PullRequest#labels` from `github_pull_request.labels.map(&:name)` (initial sync) [2](#0-1) , and subsequent label events persist label names verbatim via `LabelCapturingHandler#capture_labels` (`pull_request.update!(labels: params.pull_request.labels.map(&:name))`) [3](#0-2) .
2. `ReviewStack#env` merges these label names, uppercased, as environment variable keys with values `"true"`, with no filtering against any allowlist [1](#0-0) . This is confirmed by existing tests demonstrating arbitrary label-derived keys reach `env` unfiltered: [4](#0-3)  and [5](#0-4) .
3. `TaskCommands#env` merges `@stack.env` into the task's command environment [6](#0-5) , and `DeployCommands#env` further extends it [7](#0-6) .
4. This env is passed into `git(...)`/`Command.new(..., env:)` calls for the `clone`/`checkout` steps [8](#0-7) , and `Command#start` builds `unbundled_env` (`BASE_ENV.merge('PATH'=>...).merge(@env.stringify_keys)`) and hands it to `PTY.spawn` [9](#0-8) .

The `EnvironmentVariables#permit`/`filter_deploy_envs` allowlist mechanism (`lib/shipit/environment_variables.rb`, `deploy_spec.rb#filter_deploy_envs`) only sanitizes the **user-submitted** `deploy.env` parameter from the controller (`deploy_params` permits only `@stack.deploy_variables.map(&:name)`) [10](#0-9)  — it is never applied to `Stack#env`/`ReviewStack#env`, so it does not guard this path at all. No other guard (`verify_signature`, `ExplicitParameters`, model validation) restricts the *content* of label names or filters keys before they reach `Command`.

### Impact Explanation
An attacker who can attach a label to a pull request on a repository with `review_stacks_enabled` and `provisioning_behavior` of `allow_with_label`/`allow_all` can set `GIT_TEMPLATE_DIR` (or other dangerous vars such as `GIT_SSH`, `GIT_PROXY_COMMAND`) as a PR label, causing every subsequent git operation on that review stack (clone of the cache, checkout, deploy) to run with that variable set. `GIT_TEMPLATE_DIR` causes git to copy files (including hooks) from the attacker-supplied directory into `.git/hooks` on `git clone`, and those hooks execute on the Shipit deploy host — arbitrary command execution scoped to that review stack's process, repeatable on every deploy/task run for that stack. This matches the Critical RCE class described in scope.

### Likelihood Explanation
Requires: `review_stacks_enabled` and `allow_with_label`/`allow_all` provisioning configured on the target repository, and the attacker's ability to attach a label with the desired uppercased name to a PR (per this audit's stated attacker capabilities). No Shipit credentials, API tokens, or GitHub team membership are needed. The cost is a single labeled PR; the resulting env-var injection persists for the life of the review stack and is exercised on every subsequent clone/checkout/deploy of that stack.

### Recommendation
Do not merge raw PR label names into process environment variables without an allowlist. `ReviewStack#env` should either (a) not expose label-derived variables into the git/process environment at all, or (b) restrict injected keys to a fixed, non-overridable prefix (e.g., `SHIPIT_LABEL_<hash>`) and explicitly block any name colliding with sensitive variables (`GIT_*`, `LD_*`, `PATH`, etc.), or (c) run `EnvironmentVariables.with(...).permit(...)` against a strict allowlist before merging into `Command`'s env.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extension)
test "#env does not allow labels to inject GIT_TEMPLATE_DIR into the process environment" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["git_template_dir"]

  # broken binding under test: env["GIT_TEMPLATE_DIR"] should be nil (not attacker controlled)
  refute_equal "true", stack.env["GIT_TEMPLATE_DIR"]
end

# test/lib/shipit/deploy_commands_test.rb (extension)
test "deploy commands env does not leak label-controlled GIT_TEMPLATE_DIR to Command#unbundled_env" do
  stack = shipit_stacks(:review_stack)
  deploy = stack.trigger_continuous_delivery
  stack.pull_request.labels = ["git_template_dir"]

  env = Shipit::DeployCommands.new(deploy).env
  command = Shipit::Command.new("git clone", env: env, chdir: ".")

  refute_equal "true", command.unbundled_env["GIT_TEMPLATE_DIR"]
end
```
Current behavior: both assertions fail because `env["GIT_TEMPLATE_DIR"]` / `command.unbundled_env["GIT_TEMPLATE_DIR"]` equal `"true"`, proving the fork-controllable key reaches the spawned process.
