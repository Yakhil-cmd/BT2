### Title
Cross-repository CI status forgery via organization/repository binding mismatch in webhook signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify a webhook's HMAC signature against using `repository_owner`, derived from the attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), *before* the body has been authenticated. [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` for any organization that has no `webhook_secret` configured: [3](#0-2) 
and Shipit's own sample multi-org config explicitly ships with `webhook_secret: # nil` per organization. [4](#0-3) 

Once the request passes this "authentication" step (which only proves the payload came signed under some org's — possibly secretless — key, or none at all), the actual event handler `StatusHandler` never re-checks which organization/repository was authenticated. It updates commit statuses purely by SHA, globally, across the entire `Commit` table: [5](#0-4) 

This breaks the equality the engine is supposed to enforce: `organization authenticated by verify_signature == repository/commit actually written by the handler`. An attacker only needs to know (a) an organization login configured in Shipit with no `webhook_secret` (or any org, if the deployment's config omits secrets, which is explicitly shown as a supported/default configuration) and (b) the SHA of a commit belonging to a completely different, victim stack/repository that *does* have `webhook_secret` protection. The `sha` field is a global, unscoped key with no relation back to the `repository_owner` used to pick the verification secret.

### Finding Description
1. `verify_signature` computes `repository_owner` from the untrusted request body itself, then fetches `Shipit.github(organization: repository_owner)` and checks the signature against *that* organization's secret. [1](#0-0) 
2. If that organization's `webhook_secret` is blank/nil, `verify_webhook_signature` unconditionally returns `true` — no cryptographic authentication actually occurred. [3](#0-2) 
3. The `status` event is dispatched to `StatusHandler`, whose `process` method resolves target records purely via `Commit.where(sha: params.sha)` — it does not use `Handler#stacks`/`repository_name` (unlike `PushHandler`, which does scope to `stacks.where(branch:)`), so it is not bound to the organization/repository that was "authenticated" in step 1 at all. [6](#0-5) 
4. Because `Commit` records are global (not filtered by any owner claim from the payload), an attacker can submit a `status` webhook whose `repository.owner.login` names an unmonitored/secretless org, while the `sha` field names a commit that belongs to an entirely different, security-sensitive stack tracked under a different, properly-secured GitHub App/org.
5. The result: `commit.create_status_from_github!(params)` creates a forged, attacker-controlled `Status` (state/context/description/target_url) attached to a real commit in a repository the attacker never authenticated against.

This is a direct analog of the reported `burnAndBridge` bug class: a field acted upon (`sha`, and implicitly "which repository's data gets mutated") is never covered/bound by the verification that was actually performed (`repository_owner`-keyed HMAC check). The "destination" of the write (arbitrary commit/repo) is disconnected from the "authorization" that was checked (an unrelated, possibly secretless, organization).

### Impact Explanation
Shipit's deploy gating relies on commit CI status: `required_statuses`/`blocking_statuses` configured in `shipit.yml` gate whether a commit is `deployable?`. By forging a `status` webhook that marks an arbitrary commit as passing (`state: "success"`) for the exact `context` Shipit is configured to require, an attacker can flip a victim stack's commit into a deployable state without any real CI having run, enabling an **unauthorized deploy** of unreviewed/failing code — one of the explicitly listed Critical impacts ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability depends on the deployment having at least one configured GitHub organization entry with no `webhook_secret` (shown in the shipped sample config as the default/nil value) or any organization the attacker can name that Shipit hasn't configured a secret for; `Shipit.github(organization:)` raises `GithubOrganizationUnknown` only for entirely unlisted logins, and any listed org with a blank secret sails through verification. Given that `webhook_secret` is optional per-org and the repo owner name is fully attacker-controlled JSON, no session, API token, or GitHub write access is required — only knowledge of a target commit SHA, which is public information on GitHub. This is an unprivileged, network-reachable path (`WebhooksController#create` has no authentication before `verify_signature`, and `verify_signature` itself can be bypassed as shown).

### Recommendation
- Bind webhook signature verification identity to the exact resource being mutated: require that the `webhook_secret` used for verification belongs to the same organization/repository as the `repository.full_name` (or `sha`'s owning repository) actually acted upon by the handler, not merely `repository.owner.login`/`organization.login` read independently.
- In `StatusHandler` (and any other handler resolving records without going through `Handler#stacks`), scope the `Commit` lookup to repositories owned by the authenticated organization, mirroring `PushHandler`'s use of `stacks`.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for a production configuration; at minimum, log/alert and refuse cross-organization side effects when no secret is configured.

### Proof of Concept
1. Configure Shipit with two GitHub orgs: `victim-org` (has `webhook_secret` set, hosts the real tracked stack and its CI) and `attacker-org` (listed but with `webhook_secret: nil`, e.g. as in the shipped `config/secrets.development.shopify.yml` template).
2. Attacker finds the SHA of a commit under a `victim-org` stack that is pending/blocked by a required status context, e.g. `ci/tests`.
3. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # irrelevant, no secret configured for attacker-org

{
  "sha": "<victim-org commit sha>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (bogus) `X-Hub-Signature`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a `Status` record with `state: "success"` on the victim commit, satisfying `required_statuses` for a stack the attacker never authenticated against, allowing the commit to become `deployable?` and be shipped.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
