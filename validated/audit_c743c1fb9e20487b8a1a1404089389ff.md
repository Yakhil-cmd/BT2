### Title
`ReviewStack#env` merges uppercased pull-request label names into the deploy environment with no key allowlist, letting a fork PR inject `PERL5LIB` into `deploy.override` steps - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased, value `"true"`) into the environment hash used by `TaskCommands#env`/`DeployCommands#env` with no allowlist. `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook body, and this merged env reaches `Command#start`'s `PTY.spawn(unbundled_env, ...)` unfiltered for `deploy.override` steps, because that path never calls `EnvironmentVariables#permit`.

### Finding Description
The broken binding: the environment passed to `PTY.spawn` for `deploy.override` steps should equal `Command::BASE_ENV.merge('PATH' => ...)` merged only with vetted keys (`SHA`, `SHIPIT_LINK`, task-level whitelisted `@task.env`, etc.). Instead it equals that merge unioned with `pull_request.labels.map(&:upcase) => "true"` with zero key filtering: [1](#0-0) 

`LabelCapturingHandler#capture_labels` writes `params.pull_request.labels.map(&:name)` directly from the webhook payload with no character/format restriction beyond `String` type in the params schema: [2](#0-1) [3](#0-2) 

`TaskCommands#env` (used by `DeployCommands#env`, its subclass) merges `@stack.env` (which for a `ReviewStack` includes the label-derived hash) directly, with no `EnvironmentVariables.with(env).permit(...)` call anywhere in this chain: [4](#0-3) [5](#0-4) 

Contrast this with the explicit allowlisting that IS applied to controller-supplied env params via `EnvironmentVariables#permit`, e.g. in `TasksController#task_params` and `RollbacksController#rollback_params`, and via `DeploySpec#filter_deploy_envs`/`filter_rollback_envs`: [6](#0-5) [7](#0-6) 

Those `filter_deploy_envs`/`filter_rollback_envs` methods exist in `DeploySpec` but are never invoked in the `TaskCommands#env`/`DeployCommands#env` chain that actually builds the `Command` objects for `deploy.override` steps (`TaskCommands#perform` at line 23-27 calls `Command.new(command_line, env:, chdir: ...)` using the unfiltered `env` method). The label-derived hash flows straight through `Command#initialize` → `Command#unbundled_env` (`BASE_ENV.merge(...).merge(@env.stringify_keys)`) → `PTY.spawn(unbundled_env, *interpolated_arguments, ...)`: [8](#0-7) 

Exploit flow: an attacker opens a PR from a fork against a repo configured with `provisioning_behavior: allow_all` (per `ReviewStack` provisioning), and applies (or has GitHub auto-apply via label webhook) a label literally named `perl5lib`. The `pull_request_labeled` webhook fires `LabelCapturingHandler`, which persists `"perl5lib"` into `stack.pull_request.labels`. When `ReviewStack#env` is later computed (during a deploy triggered by CI status/merge, or continuous delivery), `"perl5lib".upcase` = `"PERL5LIB"` is merged with value `"true"` into the env hash that reaches `Command#start`/`PTY.spawn` for the `deploy.override` steps defined in the same fork's `shipit.yml` (readable/writable by the attacker as PR author, since `allow_all` uses the fork's spec). If `deploy.override` script (or any interpreter invoked by it, e.g. a perl-based deploy script) respects `PERL5LIB`, the attacker's crafted Perl module directory can be loaded and executed as arbitrary code on the deploy host — RCE.

Existing guards that fail to prevent this: `EnvironmentVariables#permit` exists and is used for user-submitted `env` params in controllers and for `deploy.variables`/`rollback.variables`, but it is never applied to the label-derived hash injected via `ReviewStack#env`. `LabelCapturingHandler`'s params schema only enforces `String` type on `name`, not a safe format/allowlist. `provisioning_behavior=allow_all` is by design intended to allow untrusted forks to run their own `shipit.yml`, but it does not intend for the *stack's persistent runtime environment* to be attacker-controlled beyond the fork's own script content — this label mechanism is a side channel bypassing that boundary.

### Impact Explanation
An unprivileged fork-PR author can set an arbitrary environment variable key (any label name, uppercased) with value `"true"` in the deploy execution environment of their own review-stack's `deploy.override`/`deploy.post`/task steps, with no allowlist. If any tool invoked by the deploy script is sensitive to well-known environment variables like `PERL5LIB`, `RUBYOPT`, `PYTHONPATH`, `LD_PRELOAD` (subject to `Command::BASE_ENV`/`unbundled_env` not already fixing/dropping it), this can escalate to code execution on the Shipit deploy host — Critical RCE per the stated Immunefi category. This is repeatable per PR/per label, and blast radius is scoped to the attacker's own review stack (their own fork's deploy host execution), but since deploy hosts are typically shared infrastructure, RCE on that host has broader implications (credential theft: `GITHUB_TOKEN`, other stacks' secrets on the same host).

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior: allow_all` (or `allow_with_label`, once the review stack exists) enabled — a Shipit maintainer configuration choice, and the fork's `deploy.override` step must invoke an interpreter/tool sensitive to attacker-controlled env vars like `PERL5LIB` (not guaranteed by default; depends on repo's actual deploy script). No secrets are required by the attacker; only ability to open a PR and apply a label (self-serviceable by any GitHub user on a repo they can open PRs against, and PR authors can self-label if the repo settings permit, or trigger via arbitrary webhook body content field names test coverage confirms names flow through with only `String` type checks, including emoji, per `label_capturing_handler_test.rb`'s "accepts extended unicode characters (emoji) in label names" test) . This is a straightforward, repeatable one-request-per-label technique.

### Recommendation
Apply `EnvironmentVariables.with(...).permit(...)` (or an explicit safe-key allowlist / drop known-dangerous keys such as `PERL5LIB`, `RUBYOPT`, `PYTHONPATH`, `LD_PRELOAD`, `NODE_OPTIONS`) to the label-derived hash in `ReviewStack#env` before merging it into the executable environment, or exclude the label-derived env entirely from `deploy`/`rollback`/`task` command environments and restrict it to metadata-only consumers (e.g., only for status/UI display, or gate merged keys through `deploy_variables`/`rollback_variables`/`task.definition.variables` allowlists, consistent with how user-submitted `env` params are already filtered in `TasksController`/`RollbacksController` and `DeploySpec#filter_deploy_envs`/`filter_rollback_envs`).

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extend existing suite)
test "#env does not leak dangerous interpreter env vars from pull request labels" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["perl5lib"]

  env = stack.env
  # Broken binding under test: env["PERL5LIB"] should NOT be settable via a PR label
  assert_nil env["PERL5LIB"], "PERL5LIB leaked into stack env via PR label upcasing"
end

test "deploy.override step env includes attacker label-derived PERL5LIB (proves the vulnerable path)" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["perl5lib"]
  deploy = stack.trigger_continuous_delivery

  command_env = Shipit::DeployCommands.new(deploy).env

  # Demonstrates the unfiltered merge reaching the Command env used by PTY.spawn
  assert_equal "true", command_env["PERL5LIB"]
end
```
Both assertions demonstrate the equality mismatch: the expected safe binding (`env["PERL5LIB"]` should be absent/nil, matching the allowlisted variables only) diverges from the actual observed binding (`env["PERL5LIB"] == "true"`), confirming the vulnerable, unfiltered merge path from `ReviewStack#env` through `DeployCommands#env` into the `Command` environment that reaches `PTY.spawn`.
