### Title
Contract Caller's KLAY Permanently Lost via Bridge Fallback Using `msg.sender` as Counterpart-Chain Recipient — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

The fallback function of `BridgeTransferKLAY` unconditionally uses `msg.sender` as the `_to` recipient on the counterpart chain. When a contract calls this fallback (by sending KLAY directly to the bridge), `msg.sender` is the contract's address on the source chain. The bridge operator then delivers KLAY to that same address on the counterpart chain. Because contract addresses are derived from deployer address + nonce (CREATE) or salt (CREATE2), the same address on the counterpart chain is almost certainly not controlled by the same entity — and may have no private key at all — causing the bridged KLAY to be permanently lost.

---

### Finding Description

In `contracts/service_chain/bridge/BridgeTransferKLAY.sol`, the fallback function is:

```solidity
// () requests transfer KLAY to msg.sender address on relative chain.
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
``` [1](#0-0) 

`_requestKLAYTransfer` emits a `RequestValueTransfer` event with `to = msg.sender`:

```solidity
emit RequestValueTransfer(
    TokenType.KLAY,
    msg.sender,
    _to,          // <-- msg.sender passed in from fallback
    address(0),
    msg.value.sub(_feeLimit),
    requestNonce,
    fee,
    _extraData
);
``` [2](#0-1) 

The bridge operator on the counterpart chain reads this event and calls `handleKLAYTransfer` with `_to = contract_address`, which unconditionally sends KLAY to that address:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [3](#0-2) 

There is no guard anywhere in this path that checks whether `msg.sender` is a contract. The `Address.isContract()` utility exists in the codebase but is not applied here: [4](#0-3) 

The Go-layer bridge manager faithfully relays the `to` field from the event without any EOA check: [5](#0-4) 

---

### Impact Explanation

When a contract (e.g., a multisig, a DeFi vault, a contract wallet) sends KLAY directly to the bridge address, the fallback fires with `msg.sender = contract_address`. The `RequestValueTransfer` event records `to = contract_address`. The bridge operator delivers KLAY to that address on the counterpart chain. Because:

- Contract addresses derived via `CREATE` are `keccak256(rlp(deployer, nonce))[12:]` — unique per chain.
- The same address on the counterpart chain is either an EOA with no known private key, a completely different contract, or simply an empty account.

In all cases the contract that initiated the bridge call cannot access the funds on the counterpart chain. The KLAY is permanently locked at an uncontrollable address. The `requestNonce` is consumed and the bridge nonce advances, so there is no recovery path.

---

### Likelihood Explanation

Any contract that holds KLAY and interacts with the bridge via a plain value transfer (e.g., `bridge.transfer(amount)`, `bridge.call{value: amount}("")`, or a `receive()`/`fallback()` that forwards KLAY) will trigger this path. Contract wallets, multisigs, and DeFi integrations that automate bridging are realistic callers. No special privilege is required — any unprivileged contract can trigger the loss.

---

### Recommendation

Add an EOA check in the fallback function and revert if `msg.sender` is a contract:

```solidity
function () external payable {
    uint256 size;
    address sender = msg.sender;
    assembly { size := extcodesize(sender) }
    require(size == 0, "contract callers must use requestKLAYTransfer with explicit _to");
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
```

Alternatively, remove the fallback entirely and require all callers to use `requestKLAYTransfer(address _to, ...)` with an explicit recipient, mirroring the fix applied to the analogous zksync bug.

---

### Proof of Concept

1. Deploy a contract `Forwarder` on the child chain that holds KLAY and has a function `bridge(address bridgeAddr) external { bridgeAddr.call{value: address(this).balance}(""); }`.
2. Call `Forwarder.bridge(childBridgeAddr)`. The fallback fires; `msg.sender = address(Forwarder)`. `RequestValueTransfer` is emitted with `to = address(Forwarder)`.
3. The bridge operator observes the event and calls `handleKLAYTransfer(..., _to = address(Forwarder), ...)` on the parent-chain bridge.
4. The parent-chain bridge executes `address(Forwarder).call{value: amount}("")`. Since `Forwarder` was not deployed at that address on the parent chain, this sends KLAY to a plain EOA address for which no private key exists.
5. The call succeeds (plain ETH/KLAY transfer to an empty account always succeeds), `requestNonce` is consumed, and the KLAY is permanently inaccessible.
