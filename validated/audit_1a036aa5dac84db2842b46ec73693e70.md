### Title
Cross-organization webhook confusion allows forged CI status / unauthorized deploy gating on unrelated stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate a delivery against using `params.dig('repository','owner','login')`, but the handlers that actually act on the payload (e.g. `StatusHandler`, `PushHandler`) resolve the target `Repository`/`Stack` using an entirely different, independently attacker-controlled field: `payload.dig('repository','full_name')`. Nothing binds the two fields together, so the field the signature check trusts is not the field the business logic trusts.

### Finding Description
`verify_signature` picks the `GitHubApp` config to validate against from `repository_owner`: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly bypasses validation entirely when the matched organization has no `webhook_secret` configured — a state the docs call out as optional/normal for multi-org setups: [3](#0-2) [4](#0-3) 

Once a request passes `verify_signature`, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs handlers against the raw, attacker-suppliable payload: [5](#0-4) 

Every handler resolves its target repository from `payload.dig('repository', 'full_name')`, a field never checked against `repository_owner`: [6](#0-5) 

`StatusHandler` uses the resolved commits to create a `Status` directly from unauthenticated payload fields (`state`, `description`, `target_url`, `context`): [7](#0-6) 

That status feeds directly into deploy/merge gating logic: `Commit#deployable?` and `#blocked?` depend on status state, and `MergeRequest#reject_unless_mergeable!` / `StatusChecker` consult the same statuses to decide whether a PR can be auto-merged by the merge queue: [8](#0-7) [9](#0-8) 

**Attack**: In any deployment where multiple GitHub organizations are configured (the documented "Using Multiple GitHub Applications" setup) and at least one organization has an empty/optional `webhook_secret` (explicitly allowed by the docs), an unauthenticated internet client can POST to the shared `/webhooks` endpoint with:
- `X-Github-Event: status`
- `repository.owner.login` = the name of the org whose `webhook_secret` is blank (so `verify_webhook_signature` returns `true` unconditionally)
- `repository.full_name` = `victim-org/victim-repo`, targeting a completely different, properly secured stack tracked by the same Shipit instance
- `sha` = a real commit SHA on the victim stack, `state: "success"`, `context` matching a required/blocking CI context

Because `verify_signature` only ever inspects `owner.login` and `StatusHandler`/`Handler#repository_name` only ever inspects `full_name`, the forged, unsigned status is written onto the victim commit, which can flip `deployable?`/merge-queue gating for that unrelated organization's stack.

Binding broken (as equality): `repository_owner` used to select the verifying `GitHubApp` (and thus the org whose signature/secret authenticates the request) ≠ `repository.full_name` used to select the `Repository`/`Stack` that is actually written to.

### Impact Explanation
This crosses "High — escalation into repository authorization; unauthenticated read/write of stack state" because it lets an unauthenticated attacker inject fabricated CI status data into a specific, targeted organization's commit/stack that they do not control and have no relationship to, purely by knowing that a Shipit instance also serves some other, weakly-configured (no-secret) organization. This can unblock the merge queue (`any_status_checks_failed?`/`any_status_checks_missing?` become false) or mark a commit `deployable?`/unblock deploys, contributing to an unauthorized merge/deploy on the victim stack, without ever touching the victim organization's own webhook secret.

### Likelihood Explanation
Requires: (1) the operator uses the documented multi-org GitHub App configuration, and (2) at least one configured org has no `webhook_secret` set (explicitly presented in `docs/setup.md` as optional). Both conditions are realistic in real deployments (e.g. an internal/test org left without a secret) and require no credentials, tokens, or GitHub write access from the attacker — only knowledge of the org name lacking a secret and the target's `full_name`/commit sha, both of which are often publicly discoverable (public repos, PR URLs).

### Recommendation
Bind the two fields together: after selecting the `GitHubApp`/organization used for signature verification, require that the resolved `Repository`/`Stack` in `Handler#repository_name` (payload `repository.full_name`) belongs to that same verified organization before executing side effects. Alternatively, always require a non-blank `webhook_secret` per organization (removing the "no secret" bypass in `GitHubApp#verify_webhook_signature`) and reject requests where the two owner references disagree.

### Proof of Concept
1. Configure Shipit with two orgs per the multi-org doc: `victim-org` (has `webhook_secret` set, tracks a real stack) and `empty-org` (no `webhook_secret`, per docs this is allowed).
2. As an unauthenticated attacker, POST to `/webhooks`:
```
X-Github-Event: status
Body:
{
  "sha": "<real sha of a commit on a victim-org stack tracked by Shipit>",
  "state": "success",
  "context": "<required or blocking CI context for that stack>",
  "repository": { "owner": { "login": "empty-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. `verify_signature` resolves `repository_owner` = `"empty-org"`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no valid `X-Hub-Signature` is required.
4. `StatusHandler` resolves the target commit via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"`, unrelated to the org that "authenticated" the request, and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled `success` status onto the victim's commit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

      false
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    def any_status_checks_missing?
      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).missing?
    end
