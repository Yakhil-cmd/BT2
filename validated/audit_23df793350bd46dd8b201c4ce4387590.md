### Title
Missing minimum-value enforcement on `tps_interval`/`base_tps_fee`/`tps_fee_multiplier` system votes allows fee-formula overflow that can halt unit confirmation - (File: `validation.js`)

### Summary
The LibRaw advisory describes a class of bug where a numeric field taken from untrusted input (`w0`/`w1` in tag `0x412`) is used in a critical calculation without a lower-bound ("minimum value") check, letting an attacker drive the computation into an invalid/degenerate state. `ocore` has a structurally identical pattern: the `system_vote` message handler validates the numeric values for `base_tps_fee`, `tps_interval`, and `tps_fee_multiplier` but only enforces a **minimum** value for these fields when `mci >= constants.pemCurvesFixMci` (or an equivalent light-node condition). Below that mci gate, only `> 0` is required, so `tps_interval` can be set to an arbitrarily small positive number.

### Finding Description
In `validateInlinePayload`'s `case "system_vote":` branch: [1](#0-0) 

the check is:
```
case "base_tps_fee":
case "tps_interval":
case "tps_fee_multiplier":
    if (!(typeof payload.value === 'number' && isFinite(payload.value) && payload.value > 0))
        return callback(payload.subject + " must be a positive number");
    if (mci >= pemCurvesFixMci || ...) {
        if (payload.subject === "tps_interval" && payload.value < 0.1) return callback(...);
        ...
    }
```

Only `> 0` is guaranteed unconditionally; the actual minimum (`0.1` for `tps_interval`) is gated behind an mci/upgrade condition. This is the exact analog of the LibRaw defect: a value that feeds a denominator/exponent in a downstream formula is checked for "positive" but not for a safe minimum in all code paths.

`tps_interval` (and `base_tps_fee`) are later read via `storage.getSystemVar` and used as divisors/multipliers inside the exponential TPS-fee formulas: [2](#0-1) [3](#0-2) [4](#0-3) 

All three functions compute `exp(tps / tps_interval)`. If `tps_interval` is allowed to be extremely small (e.g. `1e-300`, still `> 0` and thus passing validation before the upgrade point, or on any node/config path that does not yet apply the `pemCurvesFixMci` gate), `tps/tps_interval` explodes, `exp()` overflows to `Infinity`, and `Math.round(base_tps_fee * (Infinity - 1))` yields `Infinity`/`NaN`.

### Impact Explanation
`getFinalTpsFee`, `getLocalTpsFee`, and `getCurrentTpsFee` feed directly into `validateTpsFee` (`validation.js`): [5](#0-4) 

If the minimum-value check is bypassed (pre-upgrade mci, or any deployment/light-node path that doesn't apply the same gate consistently), every unit's required `tps_fee` becomes `Infinity`/`NaN`. Because `NaN`/`Infinity` comparisons (`tps_fees_balance + objUnit.tps_fee * share < min_tps_fee * share`) are meaningless, nodes can no longer consistently accept or reject units paying the tps fee — this can manifest as the network becoming unable to confirm new units (every new unit is rejected as underpaying an effectively infinite fee), which is one of the explicitly in-scope, network-halting impacts. It is also a source of divergent behavior between nodes that are or are not past the `pemCurvesFixMci` gate, which is a stability/consensus disagreement risk.

### Likelihood Explanation
Casting a `system_vote` message is available to any address that can post a unit (no special hub/witness/peer privilege is required), matching the "unprivileged unit poster" threat model. The vote must still accumulate sufficient weight to become the effective `system_vars` value (weighted by stake/votes, tallied through `system_vote_count`), so an attacker needs enough economic weight to win the vote — this raises the cost but does not require any node-operator or peer-level privilege, and it is a pure on-chain/unit-posting path exactly like the required "single posted unit" threat model in scope.

### Recommendation
Enforce the same minimum bounds (`tps_interval >= 0.1`, `base_tps_fee <= 1e8`, `tps_fee_multiplier` between `1` and `1000`) unconditionally, regardless of `mci`/`pemCurvesFixMci` gating, or ensure the gate is always satisfied for every code path that can compute/apply these system vars (including light clients and any pre-upgrade replay/catch-up logic). Additionally, harden `getFinalTpsFee`/`getLocalTpsFee`/`getCurrentTpsFee` to reject/clamp non-finite results defensively, so a bad `tps_interval` value can never propagate `Infinity`/`NaN` into consensus-critical fee validation.

### Proof of Concept
1. On a node state where `last_ball_mci < constants.pemCurvesFixMci` (or any code path lacking the gate), post a `system_vote` unit with `subject: "tps_interval"`, `value: 1e-300` (passes `> 0` check).
2. Accumulate enough voting weight (per `system_vote_count`/vote-tally logic in `main_chain.js`) for this value to become the active `system_vars` entry for `tps_interval`.
3. Once active, any subsequent unit triggers `getFinalTpsFee`/`getLocalTpsFee`, computing `exp(tps / 1e-300)` → `Infinity`, producing `NaN`/`Infinity` required fees in `validateTpsFee`, breaking fee-based unit acceptance network-wide.
