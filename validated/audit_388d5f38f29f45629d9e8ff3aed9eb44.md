### Title
Commission-account lamports are silently dropped (neither delivered nor burned) if a vote account is closed between reward calculation and distribution - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
This is analogous to the reported MarinateV2 issue: an amount of value (reward-token balance / here, commission lamports) that the system has already committed to pay out can end up stuck/unaccounted-for because the code path that removes/misses the destination silently discards the value instead of requiring/guaranteeing it is either delivered or explicitly tracked as burned. In `load_and_reward_commission_accounts`, when the legacy (`custom_commission_collector == false`) commission path can't find the commission account at distribution time, the reward is dropped with only a `debug!` log and no adjustment to either the distributed or burned lamport totals.

### Finding Description
`load_and_reward_commission_accounts` iterates the previously-calculated `RewardCommission`s and re-loads each commission account "at distribution time" so it can add `commission_lamports` [1](#0-0) . For the legacy, non-custom-commission-collector path, the code assumes the account "should always exist" because pre-SIMD-0232 commission accounts are vote accounts that "cannot be closed unless the account hasn't voted for at least a full epoch" [2](#0-1) . If that assumption is violated (the vote account was in fact closed — e.g. by its authorized withdrawer, an ordinary un-privileged action once the validator has been delinquent long enough to satisfy `withdraw`'s `reject_active_vote_account_close` check [3](#0-2) ), this branch simply `return None` for that commission entry — it does **not** add `*commission_lamports` to `total_non_incinerator_burned_lamports` (unlike the two sibling error branches a few lines later, which do call `.fetch_add(*commission_lamports, Relaxed)` on failure) [4](#0-3) .

The final `RewardCommissionLamportAmounts` is computed purely from `accounts_with_rewards` (successfully-credited accounts) and `total_non_incinerator_burned_lamports`/`total_incinerator_lamports` [5](#0-4) . Because the "missing account" branch increments neither counter, the `commission_lamports` for that entry vanishes from all downstream bookkeeping: it isn't credited to any account, and it isn't recorded as burned. This mirrors the reported bug class exactly — value that the contract/protocol has already earmarked for payout becomes permanently unaccounted for once its intended destination (the reward token holder / the commission account) is removed, with no assertion or invariant enforcing that the amount is either delivered or explicitly destroyed.

### Impact Explanation
The epoch's `EpochRewards` sysvar tracks `total_rewards` and `distributed_rewards`, and the reward-accounting invariant (exercised in tests such as `test_alpenglow_partitioned_rewards_use_epoch_start_budget_after_burn`, which explicitly asserts "every recorded reward lamport must still be paid" [6](#0-5) ) depends on every calculated reward lamport being classified as either distributed or burned. This silent-drop path breaks that invariant: the affected commission lamports are neither added to `distributed_rewards` nor to any burned-lamports accounting, so `total_rewards` and the sum of (distributed + burned) diverge for that epoch. This corrupts the deterministic reward-accounting ledger that every validator computes identically at the epoch boundary, an accounting/bookkeeping defect in the core inflation-reward distribution path rather than a peer/operator-only issue.

### Likelihood Explanation
This is a narrow, edge-case window: it requires `custom_commission_collector` to be disabled (legacy path) and the affected vote account to be closed (balance withdrawn to zero) by its own authorized withdrawer in between the reward-calculation and reward-distribution phases of the same epoch boundary. Vote-account closure is gated by `reject_active_vote_account_close`, requiring at least a full epoch without earning credits, so in practice this is limited to already-delinquent vote accounts whose withdraw authority chooses to close them right as an epoch reward distribution is in flight. The code's own comment acknowledges this "should always exist" but is not actually enforced, and the `debug!` (not `error!`/`panic!`) handling indicates the authors recognized it as reachable, just unlikely.

### Recommendation
Treat a missing commission account in the legacy path the same as the other failure branches: increment `total_non_incinerator_burned_lamports` (or an equivalent explicit "burned" counter) by `*commission_lamports` before returning `None`, so every calculated reward lamport is guaranteed to be classified as either distributed or burned, preserving the `total_rewards == distributed_rewards + burned_lamports` invariant.

### Proof of Concept
1. A validator's vote account becomes delinquent for at least the epochs required to satisfy `reject_active_vote_account_close` (no epoch credits for ≥2 epochs) [3](#0-2) .
2. During the reward *calculation* phase for a preceding epoch, this vote account is scheduled to receive commission lamports via `RewardCommission` (with `custom_commission_collector` disabled, i.e., `is_vote_account = true`).
3. Before the *distribution* phase runs, the authorized withdrawer calls `Withdraw` for the full account balance, closing/zeroing the vote account (an ordinary, unprivileged withdraw operation) [7](#0-6) .
4. `load_and_reward_commission_accounts` runs during distribution, calls `get_account_with_fixed_root_no_cache` on the now-closed commission pubkey, gets `None`, logs a debug message, and returns `None` for that entry without updating `total_non_incinerator_burned_lamports` [8](#0-7) .
5. The resulting `RewardCommissionLamportAmounts.distributed_lamports` and `.burned_lamports` together undercount the original calculated commission amount by exactly `commission_lamports`, breaking the epoch-wide reward-accounting invariant relied upon elsewhere in the codebase (e.g. the test-asserted invariant at [6](#0-5) ).
