## Title
Cross-organization commit-status spoofing via webhook `sha` global lookup bypasses CI-gated deploy checks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook handler resolves the target of a signed GitHub payload purely by commit `sha`, with no check that the `sha` belongs to a repository owned by the organization whose `webhook_secret` produced the signature. This breaks the binding "organization that authenticated versus the repository that is written."

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) to validate the request using only `repository_owner`, i.e. `params.dig('repository', 'owner', 'login')`: [1](#0-0) 

Once the signature check passes for that one organization, `Shipit::Webhooks.for_event('status')` is dispatched to `Handlers::StatusHandler`, which performs a **global, unscoped** lookup by `sha` across the entire `Commit` table, with no filter on repository or stack ownership: [2](#0-1) 

Compare this with the other handlers (`PushHandler`, `PullRequest::*Handler`), which all derive their write scope from `Handler#stacks`/`#repository_name`, itself taken from `payload.dig('repository', 'full_name')`: [3](#0-2) 

`StatusHandler` uniquely departs from this pattern — it never touches `repository.full_name` at all, so the equality that should hold ("the org whose secret signed this payload" == "the org whose commit is being written") is never checked. The only fields the signature covers are the raw bytes of the JSON body, but nothing in the application logic re-derives or cross-checks `repository.owner.login` against the `sha`'s owning stack.

An operator running Shipit in the documented multi-organization mode (`docs/setup.md`, `config/secrets.yml` keyed by org) legitimately gives each onboarded GitHub organization its own `webhook_secret`: [4](#0-3) 

Any org admin who is legitimately onboarded (and thus knows/controls only their own org's webhook secret and endpoint) — an "unprivileged attacker" with respect to every other tenant on the same Shipit instance — can craft a POST to `/webhooks` with:
- `X-Github-Event: status`
- `X-Hub-Signature` computed with **their own** org's `webhook_secret`
- a JSON body whose `repository.owner.login` is their own org (so it authenticates), but whose `sha`/`state`/`context` target a commit that belongs to a **different** organization's stack.

Because `StatusHandler#process` does `Commit.where(sha: params.sha)` with no owner/repo filter, the forged status is written onto that victim commit regardless of which org actually owns it: `Commit#create_status_from_github!`.

### Impact Explanation
Commit statuses directly gate deploy safety via `Commit#deployable?` and `DeploySpec#required_statuses`/`ci.require`: [5](#0-4) [6](#0-5) 

An attacker who controls any single tenant org onboarded to a shared, multi-org Shipit instance can inject a fabricated `success` status for a required CI context onto a commit sha in a completely unrelated victim organization's stack, satisfying `ci.require` and flipping `deployable?` to true. Combined with continuous deployment (`Commit#schedule_continuous_delivery`) or a subsequent legitimate/authorized deploy trigger, this can unblock or trigger an unauthorized deploy of a commit that never actually passed CI, and it also feeds `MergeRequest` status-check gating used by the merge queue. This qualifies as "an unauthorized deploy" under the Critical impact bucket. It also constitutes an authorization bypass: falsifying deploy-eligibility state cross-tenant without holding any credential belonging to the victim organization.

### Likelihood Explanation
This does not require compromising any Shipit user account, `ApiClient` token, or `api_clients_secret` — only knowledge of a webhook secret the attacker legitimately possesses for their own onboarded organization in a shared, multi-tenant Shipit deployment (the documented "Using Multiple GitHub Applications" configuration). Colliding on a specific target `sha` requires the attacker to know or guess a victim commit sha, which is often discoverable (public repos, GitHub API, PR URLs), making this practically exploitable in the common shared-instance case.

### Recommendation
In `StatusHandler`, scope the commit lookup by the repository asserted in the payload (`payload.dig('repository', 'full_name')`), consistent with `Handler#stacks`, and reject/ignore the event if the commit's stack repository does not match the authenticated `repository_owner`/`full_name`. More generally, `WebhooksController#verify_signature` should assert that `repository.owner.login` is consistent with `repository.full_name` before dispatching to any handler, so every handler can rely on that invariant.

### Proof of Concept
1. Operator runs Shipit with two orgs configured, `victim-org` (owns `victim-org/app`, stack `S_v`) and `attacker-org` (owns `attacker-org/app`, stack `S_a`), each with distinct `webhook_secret` values (`docs/setup.md` multi-org example).
2. Attacker knows only `attacker-org`'s `webhook_secret` (legitimately, as the GitHub App owner for that org).
3. Attacker learns a pending commit `sha` on `victim-org/app` (e.g. from a public PR) that is required to have `ci/required-check` = success before Shipit will deploy it.
4. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body:
```json
{
  "sha": "<victim_commit_sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/app" }
}
```
5. `X-Hub-Signature` is computed with `attacker-org`'s webhook_secret over this exact body — `verify_signature` passes because it only checks `repository.owner.login == "attacker-org"`.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit belonging to `S_v`, and calls `create_status_from_github!`, marking it `success` for `ci/required-check` even though `attacker-org` has no relationship to `victim-org/app`.
7. `victim_commit.deployable?` now returns true for CI purposes, potentially triggering continuous deployment or allowing a deploy of unreviewed/untested code on the victim's stack.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
