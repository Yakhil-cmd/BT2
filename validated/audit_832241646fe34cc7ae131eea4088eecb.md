### Title
Signature-verifying organization vs. write-target repository binding break in `WebhooksController` allows cross-organization sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against based on `repository.owner.login` (or `organization.login`) taken from the still-unverified JSON payload, while the downstream event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`) resolves the target `Repository`/`Stack` from a *different* field of that same payload: `repository.full_name`. In a multi-organization Shipit deployment (multiple entries under `secrets.github`), these two fields are never checked for consistency, so the org whose secret validates the signature is not guaranteed to be the org whose stack gets written to.

### Finding Description
Binding that should hold: `organization_whose_secret_verified_signature == organization_owning_repository_that_is_synced`.

Before the pull request/attack: for a legitimate GitHub push webhook, `repository.owner.login` and `repository.full_name`'s owner segment are always the same, because GitHub itself generates and signs the payload as a whole for a specific repository — the signature covers the raw body and is computed with that repository owner's configured `webhook_secret`.

The engine breaks this natural equality: `verify_signature` computes:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

while the actual mutation target is resolved independently by:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

and `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` for every matching stack: [3](#0-2) 

`verify_webhook_signature` itself only proves the raw body was HMAC-signed with *some* configured org's `webhook_secret` — it carries no assertion about which repository inside the body is legitimate for that org:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [4](#0-3) 

Multi-organization support is real and documented: `Shipit.github(organization:)` looks up per-organization configs from `secrets.github`, and each organization can have its own distinct `webhook_secret`: [5](#0-4) [6](#0-5) 

After the attack: an attacker who has learned (or brute-forced, or obtained through any weaker channel) the `webhook_secret` of *any one* configured organization (call it Org B) on a shared multi-org Shipit install can craft a POST to `/webhooks` with:
- `repository.owner.login = "OrgB"` (so `verify_signature` selects Org B's `GitHubApp` and the HMAC validates),
- `repository.full_name = "OrgA/some-repo"`, `ref`, and `after` set to attacker-chosen values (so `Handler#repository_name` / `PushHandler` resolves and syncs a stack that actually belongs to Org A).

Signature verification passes because it never inspects `full_name`, and the sync proceeds against Org A's stack using attacker-controlled `after` (head SHA) and `ref`, even though the attacker never possessed Org A's `webhook_secret` and has no GitHub access to Org A's repository.

### Impact Explanation
This breaks the equality the analog targets: the identity that authenticated (Org B, via its own leaked/weaker webhook secret) is substituted for the identity whose resource is mutated (Org A's `Stack`/`Repository`). Concretely, `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on Org A's stack with an attacker-supplied `after` value, which can desynchronize Shipit's view of the deployable head for Org A's stack — a repository/stack write performed under a false organizational identity. This is a genuine cross-organization write, matching the report's minter-style pattern where a "privileged" field (the organization used for authentication) is not what the downstream logic actually trusts/acts on.

### Likelihood Explanation
Requires the deployment to configure more than one GitHub organization under `secrets.github` (a supported, documented configuration) and requires the attacker to know one organization's `webhook_secret` (out of scope items like TLS interception or repository write access are not needed — only knowledge of one org's webhook secret, which could leak via that lower-trust organization's own webhook delivery logs, misconfiguration, or a less-guarded integration, independent of Org A). Given the rules explicitly flag "an organization that authenticated versus the repository that is written" as an in-scope binding, and the code confirms the fields are genuinely different and unreconciled, this is a real, low-effort-once-a-secret-is-known exploitation path — though it is contingent on multi-org deployment and secret exposure for one org, which the report/validate step cannot fully verify is common in practice.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler#repository_name`, assert that the organization/owner used to select the verifying `webhook_secret` matches the owner segment of `repository.full_name` (and `organization.login` if present) before dispatching to handlers. Reject the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, per `docs/setup.md` multi-org schema.
2. Obtain `OrgB`'s `webhook_secret` (e.g., leaked from a less-trusted CI system integrated with OrgB).
3. Craft a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/target-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1 with OrgB's webhook_secret>` over the raw JSON body.
5. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` selects `Shipit.github(organization: "OrgB")`, validates successfully, and `PushHandler` resolves `Repository.from_github_repo_name("OrgA/target-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on Org A's stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
  - Repository permissions:
    - Checks: Read & write
    - Commit statuses: Read-only
    - Contents: Read & write (to allow merging)
    - Deployments: Read & write
    - Issues: Read & write (to allow closing related issues on merge)
    - Metadata: Read-only
    - Pull requests: Read & write
```
