## Analysis

This confirms the multi-org config model: `Shipit.github(organization:)` in `lib/shipit.rb` looks up a per-organization `GitHubApp` (with its own `webhook_secret`) from `github_organizations`/`github_app_config`, supporting multiple GitHub organizations on one Shipit instance. [1](#0-0) 

### Title
Webhook signature verification is bound to `repository.owner.login`, not to the repository the payload actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC against using `repository_owner` (parsed from the unauthenticated payload), but the handlers that act on the payload use a completely different field, `repository.full_name` / `payload.dig('repository','id')`, to decide *which* stack/repository/commit to mutate. Nothing binds these two fields together.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization, via `github_app_config(organization)`. [1](#0-0) 

Once the HMAC check passes, the raw JSON is dispatched unmodified to handlers such as `PushHandler`/`StatusHandler`, which resolve the target using `Handler#repository_name` = `payload.dig('repository', 'full_name')` (for push/PR handlers via `stacks`), or, for `status` events, purely by `sha` lookup across the *entire* `Commit` table with no repository/organization scoping at all. [3](#0-2) [4](#0-3) [5](#0-4) 

Because the HMAC is computed over `request.raw_post` using a secret keyed only by `repository.owner.login`, an attacker who legitimately controls webhook delivery for **their own** onboarded organization (i.e., knows Org A's `webhook_secret`) can forge an arbitrary JSON body — keeping `repository.owner.login = "OrgA"` so the correct secret is selected — while setting `repository.full_name` (push/PR handlers) or `sha`/`state` (status handler, unscoped by owner at all) to reference a stack/commit belonging to a completely different organization/repository (`OrgB`) hosted on the same Shipit instance. The signing organization and the mutated repository are never checked for equality: `repository_owner (signed) == repository.full_name (acted upon)` is never enforced.

### Impact Explanation
- For `push` events: `PushHandler` calls `stack.sync_github(expected_head_sha:)` on any not-archived stack whose branch matches, for the forged `full_name` — this can trigger `GithubSyncJob` for a stack in Org B that the attacker doesn't own, potentially kicking off continuous-deployment task creation for a stack the attacker has no access to, i.e. an unauthorized ship trigger.
- For `status` events: `StatusHandler#process` matches purely by `sha` across the whole `Commit` table with **no owner/repository scoping whatsoever** — an attacker can forge a "success" CI status for any known commit sha in any org's stack, which can satisfy Shipit's deploy-gating checks and enable an unauthorized deploy of a commit that never actually passed CI.
This crosses the exact boundary the rules call out: "an organization that authenticated versus the repository that is written," and the resulting effect (unauthorized deploy / forged deploy-gating status) meets the Critical/High impact bar.

### Likelihood Explanation
Requires the attacker to be a legitimate (even low-privilege) webhook-delivering party for at least one organization/repository already integrated with the same Shipit instance — a realistic multi-tenant deployment. No Shipit account, `ApiClient` token, or GitHub App key is needed; only knowledge of one org's `webhook_secret`, which the attacker can obtain by configuring their own repo's webhook (they choose the secret when installing GitHub webhooks pointed at Shipit, or already know it as an org admin).

### Recommendation
After signature verification, re-derive the organization/repository from the same payload used for verification and assert it matches the repository/stack the handler is about to act on (e.g., verify `payload.dig('repository','full_name')`'s owner matches `repository_owner`, and scope `StatusHandler`'s `Commit.where(sha:)` lookup by repository/owner instead of a global sha search).

### Proof of Concept
1. Shipit instance configured with two orgs, `OrgA` (attacker-controlled webhook secret `secretA`) and `OrgB` (victim), per `github_app_config`.
2. Attacker crafts JSON body:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"},
  "sha": "<victim commit sha>",
  "state": "success",
  ...
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(secretA, body)`.
4. POST to `/github/webhooks` with `X-Github-Event: status` (or `push`).
5. `verify_signature` resolves `repository_owner = "OrgA"`, fetches `GitHubApp` for OrgA, and successfully verifies the HMAC using `secretA` (which the attacker legitimately knows).
6. `StatusHandler#process` (unscoped by owner) matches `Commit.where(sha: params.sha)` against OrgB's commit and creates a forged "success" status — or `PushHandler` triggers `GithubSyncJob`/`sync_github` for OrgB's stack — without the attacker ever having credentials to OrgB.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```
