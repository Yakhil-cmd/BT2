### Title
Pool vaults can be permanently frozen by a mint's `freeze_authority`, since `is_supported_mint` never checks it, causing a permanent DoS of `deposit`/`withdraw`/`swap` - (File: `programs/cp-swap/src/utils/token.rs`)

### Summary
The reNFT report describes a pausable ERC721/1155 token whose pause switch makes `stopRent`'s reclaim transfer permanently revert, locking the lender/renter's assets; the mitigation was to whitelist tokens allowed into the protocol. Raydium `cp-swap` implements an analogous whitelist gate, `is_supported_mint`, that is checked once at pool creation, but it only inspects SPL Token-2022 **extension types** and never inspects the mint's base `freeze_authority` field. A mint (legacy SPL Token or Token-2022) with an active freeze authority can therefore be used to create a pool, and the freeze authority can later freeze the pool's vault token account at any time, permanently reverting every `deposit`, `withdraw`, and `swap_base_input`/`swap_base_output` transfer that touches that vault — an unremovable, on-chain analog of the "pause" DoS from the report.

### Finding Description
`is_supported_mint` in `programs/cp-swap/src/utils/token.rs` only allowlists specific Token-2022 extensions (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`) and rejects any other extension type: [1](#0-0) 

This check is invoked from `initialize` (and `initialize_with_permission`) as the sole gate on which mints may be used to create a pool: [2](#0-1) 

Crucially, `freeze_authority` is a base field of the SPL Mint account (present on both legacy `Token` and `Token2022` mints), not an "extension type," so it is never examined by `is_supported_mint`. A mint can therefore pass this whitelist check while still having a live, arbitrary freeze authority. After pool creation, all fund-moving instructions (`deposit`, `withdraw`, `swap_base_input`, `swap_base_output`) route token movement through `transfer_from_user_to_pool_vault` / `transfer_from_pool_vault_to_user`, both of which perform a plain `transfer_checked` CPI with no handling for a frozen source/destination account: [3](#0-2) 

If the mint's freeze authority freezes the pool's `token_0_vault`/`token_1_vault` (or a user's associated token account), any subsequent `transfer_checked` CPI against that frozen account fails at the token-program level, and the calling instruction (`deposit.rs`, `withdraw.rs`, `swap_base_input.rs`, `swap_base_output.rs`) has no fallback path — it simply propagates the CPI error, exactly mirroring how the reNFT `stopRent` → `reclaimRentalOrder` call reverts unconditionally when the underlying NFT contract is paused.

### Impact Explanation
Once a vault account (or a required user token account) tied to a pool is frozen by the mint's freeze authority, every `deposit`, `withdraw`, and `swap` operation touching that vault permanently reverts. LPs cannot withdraw their liquidity and swappers cannot trade against the pool — this is a permanent freeze of LP and user funds with no on-chain recovery path (there is no admin unfreeze mechanism or pull-based settlement, unlike what the judge in the original report suggested as mitigation). Because the whitelist check that is supposed to prevent exactly this class of non-standard/malicious token behavior does not inspect `freeze_authority`, the protection is incomplete for this specific analog.

### Likelihood Explanation
Any unprivileged pool creator can call `initialize`/`initialize_with_permission` with a mint that has `freeze_authority` set (this is a completely standard, default-permitted field for both legacy SPL Token and Token-2022 mints, not a non-default/exotic feature). The pool will be created successfully because `is_supported_mint` performs no check on it. The only additional actor needed is the mint's freeze authority (an external party equivalent to the game/token issuer in the original Axie Infinity report, not a Raydium-privileged role) exercising a capability that is inherent and expected for many real-world tokens.

### Recommendation
Extend `is_supported_mint` (or add an explicit check in `initialize`/`initialize_with_permission`) to reject mints that have a non-`None` `freeze_authority`, in addition to the existing extension-type allowlist, closing the same class of gap that the extension whitelist was designed to close.

### Proof of Concept
1. Create/control a Token-2022 (or legacy SPL Token) mint `M` with `freeze_authority = attacker` and no extensions outside the allowed set (or none at all).
2. Call `initialize` with `token_0_mint = M`; `is_supported_mint` returns `true` since `freeze_authority` is never inspected — pool creation succeeds, and vault `token_0_vault` (an ATA/PDA owned by `M`) is created.
3. Attacker (freeze authority) issues `FreezeAccount` against `token_0_vault`.
4. Any subsequent `withdraw`/`deposit`/`swap_base_input`/`swap_base_output` call that must transfer `token_0` to/from `token_0_vault` now fails inside `transfer_from_pool_vault_to_user`/`transfer_from_user_to_pool_vault` (`token_2022::transfer_checked` CPI errors on a frozen account), permanently reverting for all users of that pool. pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
