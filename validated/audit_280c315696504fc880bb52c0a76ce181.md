### Title
Whale-scale market at sustained high utilization permanently freezes via i128 overflow before the borrow-index cap engages - (File: contracts/pool/src/interest.rs)

### Summary
The bug class of the external report (unchecked arithmetic on an input-driven magnitude causing a crash/DoS, `gif2tiff` `readextension` buffer overflow) maps onto XOXNO Lending's accrual path: the per-market RAY value `scaled_shares * index` can overflow `i128` before the `MAX_BORROW_INDEX_RAY` index cap engages, and because every mutating entrypoint calls `interest::global_sync` first, the overflow permanently bricks the market — no repay, withdraw, borrow, liquidation, or `update_indexes` can ever succeed again.

### Finding Description
Accrual runs through `accrue_chunk` → `accrue_step`, which calls `update_borrow_index` (clamps only the *index* at `MAX_BORROW_INDEX_RAY = 1e36`) and then `calculate_supplier_rewards`, which computes `borrowed.mul(env, new_borrow_index)` — i.e. `scaled_debt * index / RAY` — via `scaled_to_original`. That product is checked and panics with `GenericError::MathOverflow` when `scaled * index` exceeds `i128`. The same overflow exists in `update_supply_index` (`supplied.mul(env, old_index)`) and `supply_index_reward_shortfall`. The index cap protects the index magnitude, not the value product, so a large enough scaled book overflows the value computation while `borrow_index < MAX_BORROW_INDEX_RAY`. The protocol's own harness confirms this exact end state: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` shows accrual panicking at ~170× index growth, `last.borrow_index < MAX_BORROW_INDEX_RAY`, and both `try_withdraw_raw` and `try_repay` reverting with `MATH_OVERFLOW` — the market is frozen.

Since `global_sync` runs at the top of every market verb (`supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `flash_loan`, `recapitalize`, `claim_revenue`, `update_indexes`), the panic is permanent and unrecoverable — indexes are only committed after accrual succeeds, so no call can advance or bypass it. `clean_bad_debt`/`recapitalize` cannot help because they also accrue first.

### Impact Explanation
Permanent freezing of all funds in the affected `(hub, token)` market: suppliers can never withdraw, borrowers can never repay, and liquidations/seizures against that book revert, so collateral backing positions on the spoke is effectively stranded. This is a permanent freeze of user funds, squarely in scope.

### Likelihood Explanation
Triggering requires pushing one market's scaled RAY book near the `i128` value ceiling: a whale-scale deposit (on the order of 10^9 whole tokens at high decimals) plus ~98% sustained utilization for many years on a steep rate curve, or an accelerated version via direct token transfer games is not possible since indexes grow only with real borrowed debt. An unprivileged attacker can reach it purely through `controller.supply`/`borrow` (or direct `pool` verbs via the owner path is not needed — controller spokes drive the same pool books), but it demands enormous capital and long dwell time, or a market that organically accumulates to that scale. Medium severity: severe tail-risk impact, high economic cost to trigger.

### Recommendation
- In `update_supply_index`/`calculate_supplier_rewards`/`scaled_to_original`, use the saturating/`try_` variants (e.g. `try_mul_div_half_up` / `mul_div_floor_saturating`) for the value product and clamp the resulting *index* delta, mirroring the cap-fails-open treatment already given to `calculate_scaled_cap`.
- Alternatively enforce the value ceiling explicitly: when `scaled * index` would overflow, cap `index` at `i128::MAX / scaled` so accrual saturates instead of reverting, keeping repay/withdraw paths alive (withdrawals unscale per-position and stay under the ceiling).

### Proof of Concept
Existing harness test demonstrates the end state: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs` `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` supplies `BILLION * 10^18` of an 18-decimal asset, borrows 98%, advances time until `try_update_indexes_for` fails with `MATH_OVERFLOW`, then shows `try_withdraw_raw` and `try_repay` both fail identically while `borrow_index < MAX_BORROW_INDEX_RAY`. Root cause chain: `interest::global_sync` → `accrue_step` → `update_borrow_index` (caps index only, `common/src/rates/index.rs:13-19`) → `calculate_supplier_rewards` (`common/src/rates/index.rs:80-83`) → `scaled_to_original` (`common/src/rates/scaling.rs:14-16`) → checked `Ray::mul` panic.
