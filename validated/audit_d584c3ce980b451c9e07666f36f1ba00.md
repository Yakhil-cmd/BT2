### Title
Unprivileged dust-gate griefing of `clean_bad_debt` via third-party supply top-up permanently disables permissionless bad-debt cleanup - (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary
The permissionless `clean_bad_debt` entrypoint is the protocol's analogue of a "delete request": it deletes an insolvent account, burns its position NFT, reclassifies residual collateral as revenue, and writes off the debt against the market's supply index. Admission requires collateral at or below a fixed $5 dust threshold. Because `supply` lets any third party top up an *existing* supply position on someone else's account, an attacker can push an insolvent account's collateral just above $5 and permanently disable the permissionless cleanup path, converting every deletion attempt into `CannotCleanBadDebt`. This mirrors the GitLab bug class: mishandled delete requests leading to denial of service.

### Finding Description
`process_clean_bad_debt` only checks caller auth and the flash-loan guard before delegating to `clean_bad_debt_standalone` → `socialize_bad_debt` with `BadDebtGate::DustCapped`:

```rust

    validation::require_not_flash_loaning(env);
    clean_bad_debt_standalone(env, account_id);

The dust cap is fixed at $5 (documented in INV-LIQ-04 and the force-socialize runbook: "permissionless cleanup requires collateral at or below the fixed $5 dust threshold").

Meanwhile `process_supply` permits arbitrary third parties to deposit into an existing supply market of any account — the only check is that the `HubAssetKey` already exists in `supply_positions`:

```rust

There is no minimum amount, no health-factor gate on `supply`, and no consent from the account owner ("Ordinary `supply` and `repay` skip these checks"). The attacker therefore donates a small amount of the victim's existing collateral asset so that `total_collateral` lands just above $5 while `total_debt > total_collateral` still holds. Every subsequent `clean_bad_debt` call reverts with `CannotCleanBadDebt` (#114), as demonstrated by the harness test that asserts the gate refuses accounts above $5 (`test_force_socialize_bad_debt_above_dust_threshold`, `bad_debt_index.rs:146-180`).

The donated collateral is also trapped: `withdraw` requires owner/delegate auth, so the attacker cannot retrieve it, but it costs only ~$1–2 per re-grief since the gate only needs to be pushed over $5. The attacker can repeat the top-up any time the price moves collateral back under the threshold, keeping the account permanently uncleanable by keepers.

### Impact Explanation
- **Blocked cleanup is a real state, not just a revert.** With the account stuck, its debt positions keep accruing at the borrow index, so the eventual supply-index write-down grows monotonically — supplier losses increase the longer cleanup is denied.
- **Loss socialization is deferred indefinitely.** `execute_bad_debt_cleanup` is what writes the bad debt down pro-rata via the supply index and seizes residual collateral into revenue. While it is blocked, suppliers retain nominal claims that exceed pool cash; early withdrawers can still drain the remaining cash at par (withdrawal is oracle-free for debtless accounts), concentrating the eventual loss on later withdrawers instead of socializing it.
- **The dust collateral never becomes claimable revenue** and the phantom debt continues to inflate utilization and interest rates on that market.
- The only remaining remedy is the owner-only `force_socialize_bad_debt` governance operation (Sensitive delay tier). This qualifies as temporary freezing of funds / denial of the cleanup operation: user funds sit in a broken state until privileged governance intervenes, which the permissionless path was specifically designed to avoid.

### Likelihood Explanation
- Fully unprivileged: any address holding dust of an asset the insolvent account already supplies can execute it in one `supply` call.
- Cheap and repeatable: the required donation is bounded by ( $5 − current collateral + ε ); it can be re-applied whenever prices push collateral back under the threshold.
- No timing or oracle manipulation required — the gate compares USD totals the attacker directly controls on the collateral side.
- Detectable but not preventable: keepers cannot remove the attacker's donation, and ordinary liquidation cannot fix it because the same `is_socializable_bad_debt` dust gate is what makes an insolvent account eligible for cleanup (`check_bad_debt_after_liquidation` shares this admission logic), and the attacker's top-up keeps the account collateralized just enough to break it.

### Recommendation
Apply the dust test to the victim's *own* contribution rather than the post-top-up collateral total — e.g., evaluate `is_socializable_bad_debt` against collateral value net of supply shares the attacker (non-owner) added, or track per-position "third-party donated" shares. Simpler alternatives:

- Gate third-party `supply` on insolvency: reject deposits to accounts whose current `total_debt > total_collateral` (supply already loads the account; a `calculate_account_risk_totals` check for non-owner callers would stop the grief without affecting owner self-rescue).
- Replace the absolute $5 cap with a relative test (e.g., collateral ≤ max($5, x% of debt)), so a small donation cannot flip the gate.
- Make `clean_bad_debt` accept an explicit `max_collateral_wad` bound from the caller and ignore third-party top-ups above the victim's pre-insolvency snapshot.

### Proof of Concept
1. Alice supplies 30 units of collateral token LIQC and borrows 12 units of debt token LIQD.
2. LIQC crashes so collateral ≈ $4.5 and debt ≈ $12 → `D > C` and `C ≤ $5`: `clean_bad_debt` is callable by anyone (this exact shape is exercised in `tests/integration/flows/liquidation.sh` `flow_clean_bad_debt` and `test_keeper_clean_bad_debt_decreases_supply_index`).
3. Attacker calls `supply(caller=attacker, account_id=alice_id, spoke_id, assets=[(LIQC_key, dust_amount)])` with ~$1 of LIQC. `require_third_party_existing_supply` passes because LIQC is already in Alice's `supply_positions` (`supply.rs:86-95`).
4. Collateral is now ~$5.5 > $5 while `D > C` still holds. `clean_bad_debt(caller=keeper, account_id=alice_id)` reverts with `CollateralError::CannotCleanBadDebt` — identical to the `xfail fs_permissionless_denied 'Error\(Contract, #114\)'` case in `liquidation.sh:360`.
5. Repeating step 3 on each price drift keeps the account permanently un-cleanable by keepers; only a governance `force_socialize_bad_debt` on the Sensitive delay tier can delete it, while the debt continues accruing against suppliers.

/// Admission condition for bad-debt socialization.
#[derive(Clone, Copy, PartialEq)]
enum BadDebtGate {
    /// Permissionless: insolvent *and* collateral at or below the dust threshold.
    DustCapped,
    /// Owner-only: insolvent alone, with no cap on the collateral left behind.
    InsolventOnly,
}

/// Requires open debt and the selected insolvency gate, then cleans up the account.
fn socialize_bad_debt(env: &Env, account_id: u64, gate: BadDebtGate) {
    let mut cache = Context::new(env);
    let account = storage::get_account(env, account_id);

    assert_with_error!(
        env,
        !account.borrow_positions.is_empty(),
        CollateralError::DebtPositionNotFound
    );

    let totals = risk::calculate_account_risk_totals(
        env,
        &mut cache,
        &account.supply_positions,
        &account.borrow_positions,
    );

    let admits = match gate {
        BadDebtGate::DustCapped => {
            is_socializable_bad_debt(totals.total_debt, totals.total_collateral)
        }
        BadDebtGate::InsolventOnly => totals.total_debt > totals.total_collateral,
    };
    assert_with_error!(env, admits, CollateralError::CannotCleanBadDebt);
```
