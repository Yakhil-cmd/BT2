This confirms the vulnerability. `Handler#stacks` scopes to `Repository.from_github_repo_name(repository_name)&.stacks` using `payload.dig('repository', 'full_name')` [1](#0-0) , and other handlers like `PushHandler#process` correctly use this scope: `stacks.not_archived.where(branch:)` [2](#0-1) . But `StatusHandler#process` bypasses `stacks` entirely and instead does a bare, repository-unscoped `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . The `StatusHandler` params schema also never requires/reads a `repository` field [4](#0-3) .

### Title
`StatusHandler#process` writes Status records by global SHA lookup with no repository binding, letting a legitimately-signed webhook from one tracked repo satisfy CI checks on an unrelated Stack/PR sharing the same commit SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Every other webhook handler (e.g. `PushHandler`) scopes its side effects through `Handler#stacks`, which resolves `Stack`s strictly via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [1](#0-0) . `StatusHandler`, however, ignores this binding and does a bare `Commit.where(sha: params.sha)` across the entire `commits` table, writing a `Status` row to any `Commit`, from any `Stack`, that happens to share that SHA [3](#0-2) . That status is then consumed unfiltered by `Commit#statuses_and_check_runs` (`statuses + check_runs`) [5](#0-4)  and by `MergeRequest#all_status_checks_passed?` (`StatusChecker.new(head, head.statuses_and_check_runs, ...).success?`) [6](#0-5) , which `merge!` relies on before calling `stack.github_api.merge_pull_request` [7](#0-6) .

### Finding Description
The binding that must hold is: `status.commit.sha == status_payload.sha AND status_payload.repository.full_name == status.commit.stack.repository.full_name`. `verify_signature` in `WebhooksController` only proves the payload was genuinely signed by GitHub for *some* organization configured in Shipit (`Shipit.github(organization: repository_owner).verify_webhook_signature(...)`) [8](#0-7)  - it says nothing about which repository within that org the SHA belongs to, and `StatusHandler` never checks `payload['repository']['full_name']` at all. So the second half of the binding is never enforced, breaking the equality.

Exploit path: if the attacker legitimately owns/controls another repository that is also tracked by this same Shipit instance under an org Shipit already trusts (a normal, unprivileged multi-tenant scenario - the attacker need not know any secret, since GitHub itself signs the webhook for their own repo's CI events), and that repository shares a commit object (identical SHA, e.g. via a fork, shared upstream history, or cherry-pick preserving all metadata) with the head commit of a PR they open against the victim's Stack, then a genuine `status` webhook fired by the attacker's own CI for their own repo is delivered to `/webhooks`, passes `verify_signature` (real GitHub signature for a real, trusted org), and is processed by `StatusHandler#process`. Because the lookup is `Commit.where(sha: params.sha)` with no repository filter, the resulting `Status` row is attached to *every* `Commit` record sharing that SHA - including the one belonging to the victim's Stack/PR - regardless of which repository the webhook actually came from.

Once that `success` status lands on the victim Stack's `Commit`, `MergeRequest#all_status_checks_passed?` reports success for a PR whose actual required CI on the target repository never ran or failed [6](#0-5) , `reject_unless_mergeable!` no longer rejects it for `ci_missing`/`ci_failing` [9](#0-8) , and `merge!` proceeds to call `stack.github_api.merge_pull_request` [7](#0-6) , merging code that never passed the victim repo's real CI.

### Impact Explanation
This is a cross-tenant integrity failure: a `status` webhook honestly delivered for repository A can write CI state onto a `Commit` belonging to repository B's Stack, purely because both share a SHA. When that Commit is the head of a pending `MergeRequest`, this directly enables an unauthorized merge (`stack.github_api.merge_pull_request`) of a PR that never passed the target repository's required checks - matching the Critical "unauthorized merge" category. Blast radius scales to any pair of Stacks/repositories on the same Shipit instance that can ever produce colliding SHAs (forks, shared history, imported/split repos), and it is repeatable per PR/commit.

### Likelihood Explanation
Preconditions: (1) the attacker needs a repository that is also a genuine Shipit-tracked Stack under some org Shipit trusts (common in shared/self-serve Shipit deployments where any team can onboard a repo), (2) a commit SHA collision between that repository and the victim's PR head, which is realistic whenever repos share git history (forks of the same upstream, mirrors, or repos split from a monorepo) rather than requiring a cryptographic SHA-1 collision. No secrets, sessions, or elevated roles are required - the attacker only needs their own legitimate, independently-signed CI status delivery. This is a real, demonstrable app-layer authorization gap, not a theoretical one.

### Recommendation
In `StatusHandler#process`, scope the lookup through the same `stacks` binding used by other handlers, e.g. resolve `stacks` from `payload.dig('repository','full_name')` and only update commits belonging to those stacks (`stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or a joined query filtering `commits.stack_id IN stacks`), instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`, or a `MergeRequestTest` as suggested):
1. Create two fixtures: `stack_victim` (repository `victim/repo`) with a pending `MergeRequest` `@pr` whose `head` `Commit` has SHA `X` and no/failing status for context `ci/travis`; and `stack_attacker` (repository `attacker/repo`) with its own `Commit` also having SHA `X` (simulating shared history).
2. Assert baseline: `assert_not @pr.all_status_checks_passed?` (binding side 1: no status for repo `victim/repo`).
3. Simulate the attacker's webhook by invoking `StatusHandler.call({'sha' => 'X', 'state' => 'success', 'context' => 'ci/travis', 'repository' => {'full_name' => 'attacker/repo'}})` directly, or POST to `/webhooks` with `X-Github-Event: status` signed for the `attacker` org.
4. Assert the victim's Commit received the status: `assert @pr.head.reload.statuses.exists?(context: 'ci/travis', state: 'success')` even though the payload named `attacker/repo`, proving `status_payload.repository.full_name != stack.repository.full_name` yet the write occurred.
5. Assert the broken binding's consequence: `assert @pr.all_status_checks_passed?` becomes `true`, and `@pr.reject_unless_mergeable!` no longer returns `'ci_missing'`/`'ci_failing'`.
