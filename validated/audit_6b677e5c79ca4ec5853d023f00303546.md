Confirmed: private assets sent to an AA address are deliberately excluded from AA trigger handling and balance tracking, and the AA has no ability to spend them back out. This is the strongest analog to the Executor missing-receive() issue — funds get permanently stuck rather than reverting, but the root cause (asset-handling code path that cannot process an incoming payment type, resulting in unrecoverable fund loss) is the same bug class.

### Title
Private assets sent to an Autonomous Agent become permanently locked and unspendable - ([File: aa_composer.js], [File: main_chain.js], [File: storage.js])

### Summary
Private (hidden) asset payments to an AA address are silently excluded from the AA's tracked balance and are never selected as primary triggers, yet the private outputs are still valid, spendable-looking outputs sitting at the AA's address. Because the AA composer refuses to ever include a private asset in an outgoing payment ("it'll fail validation anyway due to lack of spend_proofs"), an AA can never generate the spend_proofs needed to move a private asset out again. Any private asset accidentally or maliciously sent to an AA is permanently and irrecoverably stuck, analogous to the Connext `Executor` reverting because it lacks a `receive()` function to accept value that was sent to it — the recipient contract/address has no code path to acknowledge or make use of the incoming asset.

### Finding Description
`main_chain.js`'s `handleAATriggers()` only turns an output into an AA primary trigger when `(outputs.asset IS NULL OR is_private=0)` [1](#0-0) , meaning private-asset outputs sent to an AA address never fire the AA logic at all — they are neither bounced back nor processed.

Even in the rare cases where private-asset balances are recomputed for an AA (e.g. re-definition bookkeeping in `storage.js`), the query explicitly filters `AND (is_private=0 OR is_private IS NULL)` [2](#0-1) , so a private asset sitting at the AA's address is never added to `aa_balances` and the AA logic can never "see" that it holds the funds.

Separately, even if an AA somehow tried to construct an outgoing payment in a private asset (e.g. forwarding it), `aa_composer.js`'s `sendUnit()` explicitly rejects it: `if (objAsset.is_private) return cb("sending private asset from AA");` with the comment "it'll fail validation anyway due to lack of spend_proofs" [3](#0-2) . This confirms AAs structurally cannot produce the spend_proofs required to move private assets, because computing/revealing a spend_proof chain requires interactive, off-chain disclosure between payer and payee that an AA (a deterministic on-DAG program) cannot perform.

The combined effect is: (1) the trigger mechanism ignores private-asset outputs sent to AAs, and (2) the AA has no mechanism to spend private assets even if it wanted to. There is no bounce, no notification, and no way for the AA definer to retrieve the funds — the private asset is permanently locked at the AA address, exactly mirroring the "recipient has no code path to use/acknowledge the incoming value" root cause of the `Executor` bug, just manifesting as silent fund-loss instead of an on-chain revert.

### Impact Explanation
This is a High severity fund-loss issue: any private asset payment made to an AA address is unrecoverable. Users interacting with AAs that accept assets generically (a common oscript pattern, e.g. `test/samples/a_bank_without_percent.oscript`, which silently accepts "coins" of any non-base asset via `trigger.output[[asset!=base]]`) could unknowingly send a private asset instead of a public one and permanently lose those funds, since the AA never even becomes aware it received them and can never emit them back.

### Likelihood Explanation
Likelihood is moderate: it requires a user (or wallet bug) to send a private asset to an AA address, which is a straightforward payment operation requiring no special privileges — any unprivileged asset issuer/holder can trigger this by simply composing a private-asset payment to any known AA address using the standard wallet payment functions (e.g. `sendMultiPayment`/`composeIndivisibleAssetPaymentJoint`/`composeDivisibleAssetPaymentJoint`), which do not block private-asset payments to AA addresses.

### Recommendation
- In `validatePaymentInputsAndOutputs`/`validatePayment` (validation.js) or in `aa_addresses` output validation, reject (bounce or invalidate) payments of private assets to AA addresses at the unit-validation stage, the same way `checkNotAAs` guards other message types, so senders get immediate, visible feedback that the payment cannot be processed instead of silent fund loss.
- Alternatively, extend `handleAATriggers()` in `main_chain.js` to also pick up private-asset outputs sent to AAs specifically so they can be automatically bounced back to the sender with an explicit error, rather than being ignored entirely.

### Proof of Concept
1. Define/issue a private, divisible asset `X` (e.g. via `asset` app message, `is_private: true`).
2. Send a payment of asset `X` to an existing AA's address using a normal wallet private-payment flow (`composeDivisibleAssetPaymentJoint` / `sendMultiPayment` with `asset: X`).
3. Observe that:
   - `main_chain.js` `handleAATriggers()` never inserts an `aa_triggers` row for this unit because `is_private=0` fails in the `WHERE` clause [4](#0-3) .
   - `aa_balances` for the AA address is never credited with asset `X` (see the `(is_private=0 OR is_private IS NULL)` filter) [5](#0-4) .
   - Even if the AA's oscript attempted `{app: 'payment', payload: {asset: X, outputs: [...]}}` to move the funds back out, `sendUnit()` would reject it with `"sending private asset from AA"` [3](#0-2) .
4. The asset `X` payment remains a valid, unspent output at the AA's address forever, with no code path in ocore that lets the AA (or anyone else) reclaim or spend it.
