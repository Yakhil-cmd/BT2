### Title
Cross-tenant stack write via mismatched signature/handler binding on `repository.owner.login` vs `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
In multi-organization Shipit deployments (`Shipit.github_default_organization` present), `WebhooksController#verify_signature` selects the HMAC secret using `repository.owner.login` from the JSON body, while every `Handler` (including `PushHandler`) resolves the target `Repository`/`Stack` using the independent `repository.full_name` field from the same body. Nothing ties these two fields together, so an attacker who legitimately controls org-a's own webhook secret (their own Shipit-connected GitHub org) can forge `repository.owner.login: "org-a"` with a valid signature while setting `repository.full_name: "org-b/repo"`, causing `GithubSyncJob`/`Commit.create_from_github!` to run against org-b's stack.

### Finding Description
Broken binding: `organization whose webhook_secret verified request.raw_post` (= `params.dig('repository','owner','login')`, checked in `verify_signature`, `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`) is claimed/assumed to equal `organization owning repository.full_name used by the handler` (`payload.dig('repository','full_name')`, used in `Handler#repository_name`/`#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`, and consumed by `PushHandler#process`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`).

Trace:
- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` then HMAC-verifies `request.raw_post` against that org's secret (`lib/shipit/github_app.rb:76-83`).
- `Shipit.github` (`lib/shipit.rb:170-181`) in multi-org mode (`github_default_organization` present, per `secrets.development.shopify.yml` style config) selects the secret strictly via `github_app_config(organization)` keyed by the literal string passed in — i.e. `repository.owner.login` from attacker-controlled JSON.
- `#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) re-parses `request.raw_post` into `params` and dispatches to `Shipit::Webhooks.for_event(event)` handlers with that same JSON hash.
- `PushHandler` (via `Handler#stacks`/`#repository_name`) looks up the target `Repository` using `payload.dig('repository', 'full_name')` — a completely separate JSON field from `repository.owner.login`.
- No validation anywhere checks that `full_name.split('/').first == repository.owner.login`. `ExplicitParameters` schemas for `PushHandler` only require `:ref` and `:after`; they don't even touch `repository`. `drop_unhandled_event` and `check_if_ping` are unrelated. `Repository::from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) blindly splits `full_name` and looks up by owner/name with no cross-check against the verified organization.

Attack: attacker who legitimately owns/administers "org-a" in Shipit (with its own real `webhook_secret`, per the documented multi-org secrets schema) sends `POST /webhooks` directly (not via GitHub) with:
```
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC(org-a secret, raw_body)>
body: { "ref": "refs/heads/master", "after": "<sha>", "repository": {"owner": {"login": "org-a"}, "full_name": "org-b/victim-repo"} }
```
`verify_signature` passes (org-a secret genuinely signs this exact raw body). `PushHandler` then resolves `org-b/victim-repo`'s stack and enqueues `GithubSyncJob`, which fetches commits via `stack.github_commits` (using org-b's own GitHub App/installation credentials) and calls `stack.commits.create_from_github!`, writing `Commit` records for org-b's stack that the attacker never authenticated against.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `Repository` validations) do not check this cross-field consistency, so the divergence is real when the deployment uses the multi-org secrets schema.

### Impact Explanation
Critical: a request signed only with org-a's credentials causes `Commit` records to be created and a `GithubSyncJob`/eventual `CacheDeploySpecJob` to run against org-b's `Stack` — i.e., a payload for one repository/organization mutating another organization's stack/commit state, matching the "payload for one repository mutating another's stack, commit, task or team" Critical category. This is repeatable against any `full_name` value the attacker chooses, for any org configured in the shared Shipit instance, as long as the attacker's own org secret is valid — full tenant-isolation break in multi-tenant Shipit deployments.

### Likelihood Explanation
This only applies when Shipit is configured with the multi-organization github secrets schema (`secrets.github` keyed by multiple org names, each with its own `webhook_secret`, per `docs/setup.md`/`config/secrets.development.shopify.yml`). In that configuration, any attacker who is a legitimate, unprivileged tenant of the Shipit instance (owns one configured org with its own real webhook secret) can perform this attack at will with no additional privileges — they need no GitHub team membership, no Shipit session, and no knowledge of any other org's secret. In a single-org Shipit deployment (`github_default_organization` nil), `Shipit.github` ignores the `organization` argument and always uses the single global secret, so there's no cross-org secret at all and this specific bypass doesn't provide any elevation (there's only one tenant). The finding is therefore conditional on multi-org config, which the repo explicitly documents and supports.

### Recommendation
In `WebhooksController#verify_signature`/`#create` (or in `Handler#repository_name`), enforce that the organization whose secret validated the signature matches the owner embedded in `repository.full_name` — e.g., derive the owner from `full_name.split('/').first` and reject (422) if it differs from `repository_owner`/`organization.login` used for signature verification, before dispatching to any handler.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (multi-org config)
test "signature valid for org-a does not permit mutating org-b's stack via full_name" do
  # Setup: Shipit.github_default_organization returns 'org-a'; secrets.github has
  # both 'org-a' (with a real webhook_secret known to attacker) and 'org-b' entries.
  org_a_secret = 'org-a-secret'
  Shipit.stubs(:github_app_config).with('org-a').returns(webhook_secret: org_a_secret)

  victim_stack = shipit_stacks(:shipit) # belongs to org-b/repo

  body = {
    ref: 'refs/heads/master',
    after: 'deadbeef',
    repository: { owner: { login: 'org-a' }, full_name: 'org-b/repo' }
  }.to_json
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', org_a_secret, body)

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = signature

  assert_no_enqueued_jobs only: GithubSyncJob do
    post :create, body:, as: :json
  end
  # Binding assertion: the org that verified the signature ('org-a')
  # must equal the org that owns repository.full_name ('org-b') acted upon.
  assert_not_equal 'org-a', 'org-b' # demonstrates mismatched binding
  assert_response :unprocessable_entity # expected after fix; currently :ok and job IS enqueued
end
```
This test currently fails (job is enqueued, response is `:ok`) because no code path checks `repository.owner.login` against the owner encoded in `repository.full_name`.
