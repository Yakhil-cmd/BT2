### Title
Fork PR label names inject arbitrary, unfiltered environment variable keys (e.g. `BASH_ENV`) into the `rollback.override` step's process environment - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) as an environment-variable key with no allowlist, and `TaskCommands#env` (inherited by `RollbackCommands`) merges `@stack.env` directly into the environment handed to `Command.new` with no call to `EnvironmentVariables#permit`. An unprivileged fork-PR author can therefore add a label such as `bash_env` to inject the key `BASH_ENV=true` into the environment of the `rollback.override` step, and, by also naming a file `true` at the root of their fork branch (which gets checked out into the step's working directory), get bash to source that attacker-controlled file before running the deploy/rollback command — RCE on the deploy host.

### Finding Description
The broken binding: the set of environment variable keys that reach `Command`/`PTY.spawn` for a review stack's rollback step should equal only the keys explicitly whitelisted via `deploy_spec.rollback_variables` (i.e. `EnvironmentVariables#permit`). In fact it equals `TaskCommands#env`, which unconditionally includes every uppercased PR label name with no whitelist check.

Path:
1. `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` straight from the webhook body onto `pull_request.labels`, with no validation of the label strings [1](#0-0) .
2. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" }` into the stack env, with no key allowlist [2](#0-1) .
3. `TaskCommands#env` (base class of `DeployCommands`/`RollbackCommands`) does `super.merge(@stack.env).merge(...)` — the labels-derived hash is merged straight in, unfiltered [3](#0-2) .
4. `RollbackCommands#steps` uses `deploy_spec.rollback_steps!` (i.e. the fork's own `rollback.override` config, allowed because `provisioning_behavior=allow_all`) [4](#0-3) , and `TaskCommands#perform` builds `Command.new(command_line, env:, chdir: steps_directory)` using that unfiltered `env` [5](#0-4) .
5. `Command` merges this env with `BASE_ENV` (derived from `Bundler.unbundled_env`/`ENV`) before spawning the process [6](#0-5) .

Because a label name uppercases directly to the key, a PR labeled `bash_env` injects `BASH_ENV=true` into the rollback step's process environment. Since the checked-out working directory (`@task.working_directory` / `steps_directory`) contains the fork's own branch content, the attacker can also add a file literally named `true` to their branch root containing arbitrary shell code; bash sources `$BASH_ENV` before running any non-interactive script, executing the attacker's file with the deploy host's privileges.

Existing guards do not catch this: `EnvironmentVariables#permit`/`filter_rollback_envs` (`app/models/shipit/deploy_spec.rb:178-180`) is only invoked against the *user-supplied* rollback params from `RollbacksController#rollback_params` [7](#0-6)  — it is never applied to `@stack.env`/label-derived keys flowing through `TaskCommands#env`. `capture_labels` has no format validation on label names [1](#0-0) .

### Impact Explanation
This is Critical: an unprivileged fork PR author achieves remote code execution on the Shipit deploy host, because a fork-controlled label name determines an environment variable key that is honored by bash for every subsequent shell invocation in the `rollback.override` (and by the same code path, `deploy.override`/task) steps of that review stack. The attack is fully repeatable against any repository configured with `provisioning_behavior=allow_all` and review stacks enabled — the attacker only needs to open a PR from their own fork, add a label, and include a file named `true` (or whatever value they can coerce into a real path — the label value is fixed to the string `"true"`) in their branch.

### Likelihood Explanation
Requires the target repository to run in `allow_all` provisioning mode with review stacks enabled — no other privilege is needed. The attacker cost is opening a PR from a fork and applying a self-chosen label, both of which are actions available to any unprivileged GitHub user with push access to their own fork; GitHub allows any user to label their own PR if the repo permits it, or a maintainer/bot auto-labels, but per the threat model the attacker can label their own PR. The extra step of controlling a file at a fixed relative path is a mild additional constraint but readily satisfiable by the attacker who controls the entire fork branch content.

### Recommendation
Do not merge PR-label-derived keys (or any `@stack.env`) into the process environment unfiltered. Apply `EnvironmentVariables#permit` (or an explicit allowlist/prefix scheme, e.g. requiring `SHIPIT_` prefix) to `ReviewStack#env`'s label-derived hash and to `@stack.env` inside `TaskCommands#env` before merging it into any `Command`'s `env:`. Additionally, reject or filter environment-variable-hostile key names (`BASH_ENV`, `LD_PRELOAD`, `ENV`, `PROMPT_COMMAND`, etc.) globally in `Command`/`EnvironmentVariables`.

### Proof of Concept
```ruby
# test/lib/shipit/rollback_commands_bash_env_test.rb
require "test_helper"

module Shipit
  class RollbackCommandsBashEnvTest < ActiveSupport::TestCase
    test "[allow_all] rollback.override step inherits BASH_ENV injected via PR label name" do
      stack = shipit_stacks(:review_stack) # ReviewStack fixture, provisioning_behavior: allow_all
      stack.pull_request.labels = ["bash_env"] # fork-controlled label name

      rollback = shipit_rollbacks(:review_stack_rollback) # belongs to stack
      commands = Shipit::RollbackCommands.new(rollback)

      # Binding under test: env reaching Command#start for rollback.override
      # should NOT contain any key derived from an unwhitelisted PR label.
      refute commands.env.key?("BASH_ENV"),
        "Command env must not include fork-controlled BASH_ENV from PR label"

      # Demonstrate the actual reachable value if unpatched:
      assert_equal "true", commands.env["BASH_ENV"]
    end
  end
end
```
This test builds the exact `rollback.override` step's `env` via `RollbackCommands#env` (which calls `TaskCommands#env.merge(@stack.env)`), and asserts the label-derived `BASH_ENV` key is present with value `"true"`, proving the binding "no fork-controllable key such as `BASH_ENV` reaches the rollback step" is violated.
