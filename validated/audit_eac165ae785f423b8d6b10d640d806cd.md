### Title
Unfiltered pull-request label names injected into `ReviewStack#env` allow forcing `BUNDLE_GEMFILE=true`, redirecting Bundler to an attacker-controlled file in the review-stack checkout - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment-variable **key** with a hardcoded value of `"true"`, with no allowlist of permitted keys. This hash flows unfiltered into `Command#env`/`unbundled_env`, which is merged on top of `Bundler.unbundled_env` and passed directly to `PTY.spawn`, so a label such as `bundle_gemfile` forces `BUNDLE_GEMFILE=true` for every command run against that review stack (any deploy/task phase that reads `stack.env`, not just a specific "ci.require" step).

### Finding Description
The broken binding is: attacker expects `env["BUNDLE_GEMFILE"]` to remain unset/`nil` (or under operator control) for any command spawned for a review stack; instead `env["BUNDLE_GEMFILE"]` can be forced to the fixed string `"true"` by anyone who can label the corresponding pull request.

Path:
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` and merges this straight into `super` (the base `Stack#env`, `app/models/shipit/stack.rb:54+`) with **no key allowlist**.
- `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) persists `params.pull_request.labels.map(&:name)` verbatim from the webhook payload onto `pull_request.labels`, and this handler fires on `opened`/`labeled`/`unlabeled`/`reopened` for any active, non-archived stack — it does not require any privileged role beyond being able to label the PR (which the attacker model in this exercise explicitly grants: "label their own PR").
- Whatever command a review stack ultimately runs (e.g., dependency install, CI-related shell invocations) constructs a `Shipit::Command` with `env: stack.env` (merged with any task-specific vars). `Command#initialize` stores `@env = env.transform_values { |v| v&.to_s }` (`lib/shipit/command.rb:34`), and `Command#unbundled_env` computes `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` (`lib/shipit/command.rb:103-105`) — i.e. `@env` always **overrides** `BASE_ENV`, which itself is `Bundler.unbundled_env`/`Bundler.clean_env` (`lib/shipit/command.rb:17-18`). `Command#start` passes this merged hash straight to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (`lib/shipit/command.rb:92`).
- No code in `Stack#env`, `ReviewStack#env`, or `Command` filters/rejects reserved Bundler variable names (`BUNDLE_GEMFILE`, `RUBYOPT`, `GEM_HOME`, etc.) before this merge.

Exploit flow: the attacker opens/labels a fork PR against a repo whose review stack is active, with a label literally named `bundle_gemfile` (case-insensitive, since it's uppercased). The webhook (`opened`/`labeled`) is captured by `LabelCapturingHandler`, persisting the label. `ReviewStack#env` then always includes `"BUNDLE_GEMFILE" => "true"` for that stack. Because the label's *value* is hardcoded to `"true"` (not attacker-controlled text), the attacker cannot point `BUNDLE_GEMFILE` at an arbitrary path/URL — only at the literal relative filename `true`. However, since the attacker also controls the contents of their own fork/branch that gets checked out into the review stack's working directory (`chdir`), they can commit a file named `true` in the checkout root containing a malicious `Gemfile`-style Ruby payload (Gemfiles are evaluated as Ruby and can contain arbitrary top-level code, e.g. `system(...)`). Any subsequent bundler invocation in that working directory with this environment will load and evaluate `./true` instead of the real `Gemfile`, executing attacker code with the deploy host's privileges.

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the webhook is genuinely from GitHub for that repository — they do not restrict which label names can be used. There is no `EnvironmentVariables#permit` (no such method/allowlist exists for the label-to-env merge in `ReviewStack#env`) and no reserved-key check in `Command`.

### Impact Explanation
If a review stack ever spawns a bundler-driven command (dependency install, CI script, etc.) using `stack.env`, the fork author can cause arbitrary Ruby to execute on the Shipit deploy host under the process's privileges, potentially exposing `GITHUB_TOKEN`, other stacks' deploy secrets on the same host, or pivoting to further hosts. This is scoped to the repository/stack that has `provisioning_behavior=allow_with_label` and an active review stack for that PR; it does not directly let the attacker mutate other tenants' stacks, but the deploy host itself may be shared across tenants, making the blast radius host-wide (Critical - RCE class).

### Likelihood Explanation
Preconditions: the target repository must use `provisioning_behavior: allow_with_label` (or otherwise auto-provision review stacks for fork PRs) and some command executed for that stack must consult Bundler using the process environment (i.e., not explicitly pass `BUNDLE_GEMFILE=` or unset it). The attacker needs no Shipit credentials — only the ability to open a PR, label it (as granted by the exercise's attacker model), and push a file named `true` to their fork. This is cheap and repeatable per PR/label event. The main uncertainty is whether any command actually invoked for a review stack in this codebase relies on ambient Bundler environment variables without controlling them explicitly (the specific "ci.require" phase referenced in the question corresponds in `shipit.yml` schema to a list of required CI status-check names used for merge/deploy gating, not to a command-execution step) — I could not confirm within the available tooling that a concrete command-spawn path consumes `stack.env` in a way that lets `BUNDLE_GEMFILE` affect a real bundler invocation.

### Recommendation
In `ReviewStack#env`, restrict label-derived keys to an explicit allowlist (e.g., a configurable prefix like `PR_LABEL_*`) instead of merging raw uppercased label names, and in `Command#unbundled_env`/`Stack#env` strip or refuse to override reserved environment variables such as `BUNDLE_GEMFILE`, `RUBYOPT`, `GEM_HOME`, `GEM_PATH`, `RUBYLIB` before merging user/label-derived env into the process environment passed to `PTY.spawn`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (illustrative)
test "#env allows a PR label to inject BUNDLE_GEMFILE" do
  stack = shipit_review_stacks(:review_stack) # active review stack with pull_request assoc
  stack.pull_request.update!(labels: ['bundle_gemfile'])

  assert_equal 'true', stack.env['BUNDLE_GEMFILE']

  command = Shipit::Command.new('echo', chdir: Dir.tmpdir, env: stack.env)
  assert_equal 'true', command.unbundled_env['BUNDLE_GEMFILE']
end
```
This confirms the binding `stack.env['BUNDLE_GEMFILE']` (expected `nil`) vs actual `"true"`, and that this value reaches `Command#unbundled_env`, the hash passed to `PTY.spawn`. I was not able to locate, within the available tool budget, a concrete command-spawn call site tied specifically to a "ci.require" phase in `app/models/shipit/deploy_spec.rb` that consumes this env for a bundler invocation — this part of the claimed entrypoint remains unverified.
