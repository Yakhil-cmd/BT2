### Title
`Api::CCMenuController#stack` bypasses stack-scoped API client authorization - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController#stack` resolves the target stack through `stacks.from_param!` where `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a single stack [1](#0-0) . `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, bypassing the `current_api_client.stack_id` restriction entirely [2](#0-1) . A client token scoped to stack A with `read:stack` permission can therefore fetch CCMenu deploy status for any stack B by supplying B's id as `stack_id`.

### Finding Description
The intended binding is: for any stack-scoped `ApiClient`, `resolved_stack.id ∈ {current_api_client.stack_id}`, enforced via `stacks` in `BaseController` [3](#0-2) . `Api::StacksController`, `Api::TasksController`, and `Api::DeploysController` inherit `#stack`/`#stacks` unmodified, so this binding holds for them.

`Api::CCMenuController`, however, redefines `#stack` as:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 
This removes the `current_api_client.stack_id` scoping. It calls `Stack.from_param!` on the full `Stack` relation (all stacks), not the `stacks` method from `BaseController`. The class does declare `require_permission :read, :stack` [4](#0-3) , which checks `current_api_client.permissions.include?('read:stack')` via `check_permissions!` [5](#0-4) , but this permission check is a coarse capability check — it does not verify that the requested `stack_id` matches `current_api_client.stack_id`. So a token created with `stack_id = A` and `permissions = ['read:stack']` (e.g., the read-only token generated by `CcmenuUrlController#fetch`, which is exactly this kind of single-stack-scoped, `read:stack`-permissioned client) can be replayed with `stack_id` swapped to any other stack B and will successfully render B's CCMenu XML (deploy status/name).

Attacker request: `GET /api/stacks/:stackB_id/ccmenu.xml?token=<token issued for stack A>` (or whatever the CCMenu route pattern is, per `config/routes.rb`) — same authenticated token, different `stack_id` path param.

Existing guards that fail to prevent this: `require_permission!`/`check_permissions!` only checks operation:scope strings, not `stack_id` membership [5](#0-4) ; the `stacks` scoping method that would have prevented it is simply not called in this subclass [2](#0-1) .

### Impact Explanation
An attacker holding a stack-A-scoped, `read:stack`-permissioned `ApiClient` token can read CCMenu deploy-status information (stack name, latest deploy/rollback status, timestamps) for any other stack B in the Shipit instance, not just A. This is a cross-tenant authorization bypass on a read path — matching "unauthenticated read of stack state / deploy output" in spirit, except here it's read of *another tenant's* stack state using a token deliberately scoped to a single stack. It is fully repeatable against every stack ID in the system (IDs are sequential/enumerable), giving blast radius across all stacks/tenants sharing the Shipit instance. It does not, however, allow mutation, task/task-log reading, secret exfiltration, or command execution — CCMenu's `show` action only reads `stack.deploys_and_rollbacks.last` and renders a small XML status fragment [6](#0-5) .

### Likelihood Explanation
Requires possession of a valid `ApiClient` token scoped to at least one stack with `read:stack` permission — e.g. any token issued by `CcmenuUrlController#fetch`, which creates exactly such a read-only, stack-scoped client automatically for any logged-in user [7](#0-6) . Given that precondition, exploitation costs a single HTTP GET with a different `stack_id`; no secrets, signatures, or elevated roles are needed beyond the token itself. This is a straightforward IDOR/authorization-bypass, high feasibility once the precondition is met.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited scoping instead of querying `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This makes it consistent with `Api::StacksController`, `Api::TasksController`, and `Api::DeploysController`, restoring the `current_api_client.stack_id` binding.

### Proof of Concept
Minitest (functional/controller test) plan for `test/controllers/api/ccmenu_controller_test.rb`:
1. Create stack A and stack B (`shipit_stacks(:shipit)` and a second fixture/stack).
2. Create `ApiClient` `client_a` with `stack_id: stack_a.id`, `permissions: ['read:stack']`.
3. `GET :show, params: { stack_id: stack_b.to_param, token: client_a.authentication_token }`.
4. Assert on the base-controller-consistent binding: `Api::TasksController#index` with the same `client_a` token and `stack_id: stack_b.to_param` returns `:not_found` (since `stack_b.id ∉ {stack_a.id}` via `stacks`).
5. Assert the divergence: `Api::CCMenuController#show` with the same setup returns `:ok` and renders stack B's CCMenu XML — demonstrating `stack.id == stack_b.id` even though `current_api_client.stack_id == stack_a.id`, violating the intended equality `resolved_stack.id ∈ {current_api_client.stack_id}`.
