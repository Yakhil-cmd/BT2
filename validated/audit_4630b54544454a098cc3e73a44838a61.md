### Title
Missing network/chain identifier in `signed_message` hash allows cross-network replay of off-chain signed packages used by `is_valid_signed_package` - (File: `signed_message.js`, `object_hash.js`)

### Summary
The off-chain "signed package" mechanism (`signed_message.signMessage` / `signed_message.validateSignedMessage`, exposed to oscript/AA authors via the `is_valid_signed_package` formula operator) hashes only `{signed_message, authors, last_ball_unit, version}`. Neither this hash nor the address derivation used to validate the signature include any network/chain identifier (`alt`), so a signature produced for one ocore-based network can be replayed as valid on another network that shares the same protocol code and AA bytecode.

### Finding Description
`getSignedPackageHashToSign()` computes the hash that authors sign for a "signed package": [1](#0-0) 

Unlike full unit hashing (`getUnitHashToSign` via `getNakedUnit`, which clones the *entire* unit object — including the `alt` field that is present on every unit and is checked in `validate()` against `constants.alt`), the signed-package object is a bespoke minimal structure created explicitly without an `alt`/chain-id field: [2](#0-1) 

`validateSignedMessage()` also enumerates the only allowed top-level fields, and `alt`/chain-id is not one of them: [3](#0-2) 

When the package is not "network aware" (no `last_ball_unit`), verification reduces to nothing more than "does `getChash160(author.definition)` equal `author.address`" — there is no binding whatsoever to a specific network, genesis unit, or chain: [4](#0-3) 

Address derivation itself (`getChash160`) is also network-independent — it hashes only the definition array, never `alt`: [5](#0-4) 

This "signed package" object is exactly the reachable, unprivileged, attacker-postable structure: any unit poster can supply it as AA trigger data (`trigger.data.X`), and any AA author can gate spending logic on it via `is_valid_signed_package(signedPackage, address)`: [6](#0-5) [7](#0-6) 

Real-world AA patterns in this codebase use exactly this primitive for high-value logic: off-chain payment-channel state updates and order-book order matching, both gated only by `is_valid_signed_package`: [8](#0-7) [9](#0-8) 

Because neither the address nor the signed-message hash is bound to a specific network/chain, and the AA address itself (`this_address`, checked in the channel example) is also derived purely from the AA definition (network-independent), the *same* AA bytecode deployed on two different ocore-based networks (e.g. testnet vs. mainnet, or any private ocore fork sharing the codebase) yields an identical AA address and identical counterparty addresses whenever the same private keys/definitions are reused. A signed package legitimately created and consumed on one network is a byte-for-byte-identical, still-validly-signed object on the other network.

### Impact Explanation
An attacker who observes a validly signed package on one ocore-based network (e.g. a payment-channel closing state authorizing a balance split, or a matched trading order) can replay it verbatim against the equivalent AA instance on another ocore-based network that shares the same AA definition/address and where the counterparty reused the same signing key/address. `is_valid_signed_package` will return `true` there as well, because:
- the signature check only verifies the ECDSA signature over `getSignedPackageHashToSign`, which carries no chain identifier;
- the address check only verifies `getChash160(definition) === address`, which also carries no chain identifier.

This lets the attacker trigger AA logic (payment-channel closure/fraud proof, order execution) on a network where the message was never intended to apply, causing unauthorized fund movement / AA balance manipulation — an AA fund-loss condition consistent with the "unauthorized spending" and "AA fund loss" impact classes.

### Likelihood Explanation
Exploitability requires that the same AA bytecode/address and the same counterparty signing address exist on two ocore-based networks that the attacker can access — a realistic scenario for private/enterprise ocore deployments, testnets mirroring mainnet configuration, or any hard-fork/sidechain scenario using the same codebase (`constants.js` shows `bTestnet`/`devnet` are simply protocol-string variants of the same code, not different signing domains for `signed_message`). Any AA author using `is_valid_signed_package` for spending decisions (as the shipped payment-channel and order-book examples do) is affected, and the vulnerable primitive is reachable directly by posting AA trigger data — no privileged access required.

### Recommendation
Bind the signed-package hash (and/or the signed_message payload itself) to the network by including `constants.alt` (and ideally a genesis-unit hash) as a mandatory field validated in `validateSignedMessage()` and hashed in `getSignedPackageHashToSign()`, mirroring how full unit hashing already implicitly carries `alt` through `getNakedUnit`. Reject signed packages whose `alt` does not match the local node's `constants.alt`.

### Proof of Concept
1. Deploy the identical AA definition (e.g. the payment-channel oscript sample) on two ocore-based networks, Network A and Network B, both using the same codebase version.
2. Party P uses the same private key/address on both networks (a common practice for testnet/mainnet parity or private forks).
3. P signs a channel-closing "signed package" `{signed_message: {channel: AA_address, period: N, amount_spent: X}, authors: [...]}` for Network A via `signed_message.signMessage`, per [2](#0-1) .
4. Attacker captures this package (it is posted as AA trigger data, hence public) and re-submits it verbatim as `trigger.data.sentByPeer` to the same AA definition deployed on Network B.
5. The AA on Network B calls `is_valid_signed_package(trigger.data.sentByPeer, counterparty_address)`, which succeeds because the signature check (`getSignedPackageHashToSign`) and address check (`getChash160`) never referenced `alt`/network, per [1](#0-0)  and [4](#0-3) .
6. The AA on Network B accepts a state transition/payment that was never authorized for that network, moving funds out of the Network B AA instance.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
