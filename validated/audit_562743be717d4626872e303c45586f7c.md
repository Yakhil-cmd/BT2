### Title
Missing serial/`good`-sequence check in `dataFeedExists()` unstable-AA scan allows a non-serial (double-spend loser) data-feed message to satisfy `in data feed` / `in_data_feed` conditions - ([File: data_feeds.js])

### Summary
`data_feeds.js` contains two parallel code paths that scan `storage.assocUnstableMessages` for data-feed messages authored by oracle addresses while an AA is being triggered: `dataFeedExists()` (used by the boolean `in data feed` address-definition op and the `in_data_feed` oscript/formula op) and `readDataFeedValue()` (used by the value-returning `data_feed()` formula function). Only the latter filters out units whose `sequence` is not `'good'`. The former performs no such filter, so a data-feed message coming from a unit that is going to be judged non-serial (`temp-bad`/`final-bad`, e.g. the loser of a double-spend) can still satisfy an `in data feed`/`in_data_feed` boolean check.

`dataFeedExists()` is reached from two attacker-controllable entry points:
- The `in data feed` address-definition/spending-condition operator, evaluated in `validateAuthentifiers`/`evaluate` in `definition.js`: [3](#0-2) 
- The `in_data_feed` oscript/formula operator, evaluated while running an AA trigger in `formula/evaluation.js`: [4](#0-3) 

Both call straight into `dataFeedExists(arrAddresses, feed_name, relation, value, min_mci, max_mci, bAA, cb2)`, with `bAA=true` while processing an AA trigger, causing the code to consult `storage.assocUnstableMessages` — the pool of not-yet-stable units, which can include units that are already known locally to conflict with each other (one destined to be `temp-bad`/`final-bad`) but have not yet been excluded from this particular scan because the `sequence` filter present in the sibling function is absent here.

This is the same bug class as the external GitLab report: a piece of data is exposed/consumed through one query path that omits an authorization/validity gate that an analogous, correctly-guarded path enforces ("under specific conditions" the check is skipped).

### Impact Explanation
An AA author (or any unit poster who is also the oracle address referenced in another party's address definition or AA `in_data_feed` condition) can post two conflicting (double-spending) units from the same oracle address in the same unstable window: one carrying the data-feed payload they want an unrelated AA/address definition to see, and one that is otherwise unremarkable. Because both units are conflicting authors of the same address, one of them will resolve to non-`good` sequence. `dataFeedExists()` does not filter on sequence, so as long as the message-carrying unit is still in `assocUnstableMessages` and matches the mci window and address, `in data feed`/`in_data_feed` can evaluate to `true` based on a unit that is not a valid, serial transaction from that oracle.

Consequences reachable purely from a posted unit/AA trigger:
- **AA fund loss/incorrect execution**: an `in_data_feed` branch in an AA's oscript can take the wrong path and release/withhold funds based on a feed message that should not count as authoritative.
- **Address spending-condition bypass**: an address protected by `['in data feed', [oracle_addrs, name, '=', value]]` can be unlocked prematurely/incorrectly based on a non-serial unit's payload.
- **Node disagreement**: because the evaluation happens against the locally-known unstable pool (`assocUnstableMessages`), and different nodes may not have identical local knowledge of which conflicting unit will resolve to `good` at the exact moment the trigger/spending condition is evaluated, two witnesses/nodes computing the same AA response or unit validity can diverge on whether the condition was satisfied — a disagreement on unit validity.

### Likelihood Explanation
Reachability requires only unprivileged actions already possible with ocore: (1) an oracle-controlled address (or any address referenced as an oracle in someone else's `in data feed` condition) posting a data-feed message, and (2) creating a conflicting/double-spending unit from that same address so that one copy is destined to be marked non-`good`. Both are within reach of a single unprivileged unit poster / AA trigger sender referencing that oracle, with no special network position, hub trust, or leaked keys needed. The main uncertainty is the exact timing window in which the losing unit remains in `assocUnstableMessages` before being fully resolved to `final-bad` and pruned/ignored by other consumers, which affects how easy it is to reliably win the race in practice; I could not fully trace how long an entry that is destined for `final-bad` persists as `temp-bad` inside `assocUnstableMessages` before this scan runs, since that requires deeper tracing of `storage.js`'s in-memory bookkeeping than could be completed in this session.

### Recommendation
Add the same `if (objUnit.sequence !== 'good') continue;` guard to the unstable-AA scan inside `dataFeedExists()` (data_feeds.js, around line 38), mirroring the check already present in `readDataFeedValue()`, so that `in data feed` and `in_data_feed` only ever consider data-feed messages from units that are (or will become) serial.

### Proof of Concept
Conceptual sequence (cannot be executed without a live devnet, but derivable purely from the code above):
1. Attacker controls oracle address `O`.
2. Victim AA (or another address) has an `in_data_feed`/`in data feed` condition referencing `O` and feed name `X` with an expected value.
3. Attacker posts unit `U1` from `O` with `data_feed {X: desired_value}`, and, using the same last-ball/parents state, a conflicting unit `U2` from `O` that double-spends the same input as `U1` (making `U1` and `U2` mutually conflicting authors of `O`).
4. Depending on ordering, one of `U1`/`U2` will resolve to a non-`good` sequence once conflicts are detected, but while both remain in `storage.assocUnstableMessages` before that resolution/pruning completes, a trigger for the victim AA (or a unit spending from the address gated by `in data feed`) is processed and calls `dataFeedExists(['O'], 'X', '=', desired_value, min_mci, max_mci, true, cb)`.
5. Because `dataFeedExists()`'s unstable-AA loop never checks `objUnit.sequence`, the loop can match the data-feed message from the losing (non-`good`) unit and return `true`, unlocking funds/branch logic that should require a genuinely valid, serial data-feed post from `O`.
