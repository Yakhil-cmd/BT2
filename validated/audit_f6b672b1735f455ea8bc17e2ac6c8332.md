### Title
Fail-open webhook signature verification for orgs without `webhook_secret` allows forged `pull_request opened` events to auto-provision Review Stacks - (File: lib/shipit/github_app.rb, app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` delegates trust entirely to `GitHubApp#verify_webhook_signature`, which explicitly returns `true` "unless webhook_secret" is configured for the org named in the payload. Any org configured (by an operator's own choice, per `docs/setup.md`, `webhook_secret` is marked "optional") without a `webhook_secret` therefore accepts any payload with any (or no) `X-Hub-Signature`, letting an attacker forge a `pull_request` `opened` event that reaches `OpenedHandler` and provisions a `ReviewStack` when the target repository has `review_stacks_enabled` + `allow_all`.

### Finding Description
The broken binding: the code treats `signature_valid == true` as equivalent to `webhook_secret_configured == true`, when it should require `signature_valid == true AND webhook_secret_configured == true` before trusting `params`.

- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves `github_app = Shipit.github(organization: repository_owner)` from the attacker-controlled `repository.owner.login`/`organization.login` field, then calls `github_app.verify_webhook_signature(header, raw_post)`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`):
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
When `@webhook_secret` (`lib/shipit/github_app.rb:50`, `@config[:webhook_secret].presence`) is blank for that org's config, the method short-circuits to `true` regardless of the `X-Hub-Signature` header content — including a missing/garbage header.
- If verification passes, `WebhooksController#create` dispatches `Shipit::Webhooks.for_event('pull_request').each { |handler| handler.call(params) }`, reaching `OpenedHandler#process` (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:41-46`), which — when `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?` (line 66-67) — calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` using attacker-supplied `params.pull_request.head.ref`/`sha`.

Exploit flow: attacker crafts `POST /webhooks` with `X-Github-Event: pull_request`, body `{"action":"opened","pull_request":{...,"head":{"ref":"<attacker-branch>","sha":"..."}},"repository":{"owner":{"login":"<org-without-secret>"},"full_name":"<victim-org>/<victim-repo>"}, ...}`, and any signature header. Because that org has no `webhook_secret` configured, `verify_webhook_signature` returns `true`, `check_if_ping`/`drop_unhandled_event` pass, and `OpenedHandler` provisions the review stack.

Existing guards don't stop this: `drop_unhandled_event` only checks the event name is handled; `ExplicitParameters` only validates payload shape, not authenticity; there is no `require_permission!`/session check on this unauthenticated controller by design (webhooks are meant to be authenticated purely by HMAC signature). The only real trust boundary is the HMAC check, and it is bypassed by design whenever the operator leaves `webhook_secret` unset for that org.

### Impact Explanation
For an org whose `webhook_secret` is not configured, an attacker can trigger `OpenedHandler` (and by the same code path, `ClosedHandler`, `LabeledHandler`, `ReopenedHandler`, `push`, `status`, `membership`, etc.) for any repository/stack under that org without ever proving ownership of a real GitHub webhook delivery. Combined with `review_stacks_enabled` + `allow_all`, this causes a `ReviewStack` to be provisioned and its pipeline (which executes `shipit.yml`) to run — a state change (and potential command execution) on a stack the forged request never cryptographically authenticated. This is repeatable per request and applies to every repository under that unauthenticated org, so blast radius spans all stacks under that org's configuration. This matches the Critical class ("payload... mutating another's stack... unauthenticated" / RCE-adjacent via CI execution), though it is strictly scoped to orgs an operator has configured without a `webhook_secret`.

### Likelihood Explanation
This requires a precondition entirely under the Shipit operator's control: leaving `github.webhook_secret` unset for an org in `config/secrets.yml` (the setup doc explicitly labels it "optional", `docs/setup.md:30`,`:119`). If that precondition holds, the attacker's cost is a single unauthenticated HTTP POST with no valid GitHub signature, no session, and no API token — fully within the declared unprivileged attacker capability. If every configured org *does* have a `webhook_secret` set, this path is fully closed by the `SecureCompare.secure_compare` HMAC check in the same method. The vulnerability is therefore conditional on configuration rather than a pure code logic flaw in an otherwise-secured path, but the code's fail-open default (rather than fail-closed / requiring a secret) is what turns a missing-secret misconfiguration into full authentication bypass instead of a hard failure.

### Recommendation
Make `GitHubApp#verify_webhook_signature` fail closed: if `webhook_secret` is not configured, reject the webhook (return `false`) instead of returning `true`, and log/alert on the missing secret so operators are forced to configure it. Optionally, enforce at boot/config-load time that every configured GitHub org must provide a non-blank `webhook_secret`, refusing to start (or refusing to route requests for) any org lacking one.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "forged pull_request opened is accepted and provisions a ReviewStack when org has no webhook_secret" do
  repo = shipit_repositories(:shipit) # ensure review_stacks_enabled: true, provisioning_behavior: 'allow_all'
  repo.update!(review_stacks_enabled: true, provisioning_behavior: 'allow_all')

  # Org configured WITHOUT webhook_secret
  Shipit.stubs(:github).with(organization: 'no-secret-org').returns(
    Shipit::GitHubApp.new('no-secret-org', { app_id: 1, installation_id: 1 }) # no webhook_secret key
  )

  body = {
    action: 'opened',
    number: 99,
    pull_request: {
      id: 1, number: 99, url: 'https://api.github.com/x', title: 't', state: 'open',
      additions: 1, deletions: 0,
      head: { sha: 'deadbeef', ref: 'attacker-branch' },
      user: { login: 'attacker' }, assignees: [], labels: []
    },
    repository: { full_name: repo.full_name, owner: { login: 'no-secret-org' } },
    sender: { login: 'attacker' }
  }.to_json

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = 'sha1=totally-invalid-signature'

  # Binding under test: signature_valid should equal webhook_secret_present AND hmac_match,
  # but verify_webhook_signature returns true purely because webhook_secret is absent.
  assert_difference -> { repo.review_stacks.count }, 1 do
    post :create, body:, as: :json
  end
  assert_response :ok
end
```
This demonstrates the divergence: `signature_valid` is `true` even though `hmac_match` is false/absent, and a `ReviewStack` (state change) is produced for a repository/stack that never authenticated the request.
