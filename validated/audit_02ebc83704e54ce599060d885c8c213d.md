### Title
Unbounded network-wide mempool scan in `data_feed()` unstable-value lookup enables AA evaluation DoS - (File: data_feeds.js)

### Summary
`readDataFeedValue()` in `data_feeds.js`, when called with `unstable_opts` set (i.e. an oscript `data_feed()` call that also considers unstable/unconfirmed data), iterates over the **entire** `storage.assocUnstableMessages` map — every message in every currently-unstable unit network-wide — before falling back to the indexed stable lookup. [1](#0-0) 

This is structurally the same bug class as `getBestBid()` in the reported `NFTMarketAuction`: a function that is supposed to look at data related to one "item" (there, an auction; here, one set of oracle addresses/feed name) instead loops over an attacker-inflatable global collection (`bids[]` there, `assocUnstableMessages` here), and any unprivileged unit poster can grow that collection cheaply and repeatedly.

### Finding Description
`readDataFeedValue(arrAddresses, feed_name, value, min_mci, max_mci, unstable_opts, ...)` is reachable from any AA formula that calls `data_feed(..., unstable_opts)` (via `readDataFeedValueByParams`, invoked from `formula/evaluation.js`). When `bIncludeUnstableAAs` is true, the function does:
```
for (var unit in storage.assocUnstableMessages) { ... storage.assocUnstableMessages[unit].forEach(...) }
``` [2](#0-1) 

`storage.assocUnstableMessages` holds the messages of **every unit that is not yet stable** on the whole DAG, not just units authored by the oracle addresses being queried — the address filter (`_.intersection(arrAddresses, objUnit.author_addresses)`) is only applied *inside* the loop, after the unit has already been pulled from the map and its messages iterated. [3](#0-2) 

Any unprivileged user can post many small units (any `app`, e.g. `data_feed` or `text`) that remain unstable for a while (unstable window depends on witnessing/DAG depth, which an active network naturally has), inflating the size of `storage.assocUnstableMessages`. This is directly analogous to the reported issue's "mass placing bids... causing the mapping `bids[]` array to grow substantially," which forced expensive iteration in `getBestBid()`. Here, every AA trigger anywhere on the network that uses `data_feed()` with the `unstable` option pays the cost of scanning the inflated global unstable-message set, even though its own oracle addresses have nothing to do with the attacker's spam units.

### Impact Explanation
Because AA trigger processing (including `bounce` fee handling) is on the hot path for confirming units and advancing the AA response for the triggering payment, an attacker-inflated `assocUnstableMessages` map slows down every trigger that touches `data_feed(unstable_opts=...)`, across all nodes independently (since each full node maintains its own `assocUnstableMessages`). This can:
- Delay or fail AA trigger evaluation (turning it into a bounce, causing the triggering party to lose part of their funds to the bounce fee — an AA fund loss scenario), and
- Degrade the node's ability to timely evaluate/relay AA responses network-wide, which is the DAG-analog of "a network unable to confirm new units" in a timely fashion, since AA response generation blocks on this evaluation.

This is a Medium/High severity resource-exhaustion issue reachable purely from posting ordinary units — no privileged role required.

### Likelihood Explanation
Likelihood is fairly high: posting many small units is cheap (just the standard headers/payload commission), any address can do it, and the loop cost is paid by every full node that has to evaluate any AA trigger using `data_feed(unstable_opts)` while the attacker's spam units remain unstable. No special timing (like the auction's "extend near expiry") is required — the attacker simply needs to keep the unstable set populated, which is achievable during normal network operation with sustained spam.

### Recommendation
Index `storage.assocUnstableMessages` (or maintain a secondary index) by author address and by `app === 'data_feed'`, so that `readDataFeedValue`'s unstable-value lookup can directly retrieve only the candidate messages authored by `arrAddresses`, rather than doing a full O(all unstable units) scan and filtering afterward. Alternatively, cap/limit the number of unstable messages considered per lookup and/or per author, mirroring the recommended "only allow one (relevant) entry per author" mitigation from the original report.

### Proof of Concept
1. Attacker repeatedly posts inexpensive units from many different addresses (or the same address, sequentially) each containing an unrelated message (or a bogus `data_feed` message) that will remain unstable for some time due to normal DAG witnessing delay.
2. This grows `storage.assocUnstableMessages` on every full node.
3. A victim AA that calls `data_feed(['OracleAddr'], 'price', ..., 'unstable')` triggers `readDataFeedValueByParams` → `readDataFeedValue`, which executes the `for (var unit in storage.assocUnstableMessages)` loop over the now-inflated map at lines 213-240 of `data_feeds.js`, incurring cost proportional to total network-wide unstable message count rather than to the oracle's own message count. [4](#0-3) 
4. Repeating step 1 continuously keeps the map large, degrading trigger-processing latency/throughput for any AA using unstable data feeds, and can push slow trigger evaluations toward bounce, incurring fund loss for triggering users.
