### Title
`StatusHandler` writes GitHub commit statuses to commits in unrelated stacks because `Commit.where(sha:)` is unscoped by repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` across the entire `commits` table, without scoping to the repository that sent the webhook. Unlike `PushHandler`, which resolves stacks via `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`), `StatusHandler` never uses `repository_name`/`stacks` at all, so any commit row in any stack whose `sha` happens to match the incoming payload's `sha` receives a new `Status`.

### Finding Description
The broken binding: `Commit.where(sha: params.sha).count == 1` (assumed to be "the sending repository's own commit") is not enforced anywhere - there is no uniqueness constraint on `sha` scoped globally, and `sha` is only unique per `stack_id` at the model/DB level (each `Stack` tracks its own commits). The handler code is: [1](#0-0) 

Compare with the base `Handler` class, which exposes a `stacks` helper scoped by the payload's `repository.full_name`: [2](#0-1) 

and with `PushHandler`, which correctly uses `stacks.not_archived.where(branch:)` before acting: [3](#0-2) 

`StatusHandler` ignores `stacks`/`repository_name` entirely and iterates over every `Commit` row with a matching `sha`, regardless of which stack (and thus which GitHub repository) it belongs to, calling `commit.create_status_from_github!(params)` on each: [4](#0-3) 

This delegates to `Status.replicate_from_github!`, which creates a new `Status` row scoped to `commit.stack_id`, i.e. to whatever stack contains the colliding-sha commit — not the stack that corresponds to the webhook's originating repository: [5](#0-4) 

**Attacker request/path**: `WebhooksController#create` dispatches the raw parsed JSON body to every registered handler for the `status` event after `verify_signature` passes: [6](#0-5) 

`verify_signature` validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the payload's own `repository.owner.login`/`organization.login` field: [7](#0-6) 

This only proves that the payload was correctly signed for *some organization Shipit knows about* (i.e. the attacker's own GitHub App installation/webhook secret for their own org/repo) — it says nothing about whether the `sha` field inside the payload actually belongs to a commit in that repository. Git commit SHAs are content-addressed, so if the victim's Shipit stack tracks a public repository, an attacker who forks that repository (or otherwise reproduces an identical commit) shares identical SHAs for the common history. The attacker can then trigger (or directly send, if they can reach `POST /webhooks` with a validly signed payload for an org Shipit has configured) a `status` event naming the victim's commit SHA but under the attacker's own, differently-owned repository/stack context. Since `StatusHandler` never checks that the SHA belongs to a commit within `stacks` derived from the webhook's own `repository.full_name`, the resulting `Status` is attached to **every** `Commit` row across all stacks sharing that SHA, including the victim's stack.

Existing guards do not catch this: `verify_signature` only authenticates the sender as *a* legitimate source for *an* organization, not that the SHA belongs to that organization's repo; `ExplicitParameters` (`params do requires :sha, String ... end`) only validates types/presence, not repository ownership; there is no `drop_unhandled_event` or model validation that scopes `Status` creation to the commit's originating repository.

### Impact Explanation
An attacker who controls (or forks) a public repository whose commit history overlaps with a victim's tracked stack can inject `Status` records — and, by repeated abuse (e.g., alternating `success`/`failure`/`pending` states), corrupt the derived `Commit#state` and `Stack#branch_status` used to gate CI-based deployability — for a stack belonging to a different GitHub organization/repository than the one the attacker owns. This is a cross-tenant "payload for one repository mutating another's commit" scenario. The blast radius is limited to `Status` rows on commits with a colliding SHA (real SHA collisions require literal shared git history, e.g. via forks, rather than arbitrary attacker-chosen values), but within that constraint the write is fully attacker-controlled, repeatable, and reaches production commit-state used for deploy decisions in another tenant's stack.

### Likelihood Explanation
Exploitation requires: (1) Shipit must have a GitHub App/webhook secret configured for an organization the attacker controls (or the attacker must otherwise get a validly-signed `status` webhook delivered, e.g. by owning a fork whose upstream/parent repo triggers GitHub's own status propagation, or by directly installing the Shipit webhook on their own repo if that's permitted), and (2) the victim stack must contain a commit whose SHA is reproducible by the attacker — realistically achieved by forking the victim's public repository and sharing its commit history. This is a common configuration (public open-source repos on shared GitHub orgs/Shipit instances), making the precondition plausible but not universal; it does not require any Shipit secret, session, or elevated privilege.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository that sent the webhook, mirroring `PushHandler`'s use of `stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a `status` webhook can only affect commits belonging to stacks whose tracked repository matches the payload's `repository.full_name`.

### Proof of Concept
Minitest plan (no live GitHub, existing fixtures/factories):
1. Create two `Stack` fixtures for two different repositories (`repo_a`, `repo_b`).
2. Create `Commit` A in `repo_a`'s stack and `Commit` B in `repo_b`'s stack with the **same** `sha` value (e.g. `"deadbeef..." * `).
3. Build a `status` webhook payload whose `repository.full_name` is `repo_a`'s full name, `sha` equal to the shared sha, and `state` = `"success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, as the question binding is about the handler's own scoping, not signature checking).
5. Assert:
   - Before: `Status.where(commit_id: commit_a.id).count == 0` and `Status.where(commit_id: commit_b.id).count == 0`.
   - After: `Status.where(commit_id: commit_a.id).count == 1` (expected, same repo) **and** `Status.where(commit_id: commit_b.id).count == 1` (unexpected — proves cross-stack corruption), i.e. `Commit.where(sha: shared_sha).count == 2` while the handler treats it as `== 1`.
6. This demonstrates that a payload declaring `repository.full_name == repo_a` mutates `commit_b`'s stack (`repo_b`), violating the tenant-isolation invariant.
