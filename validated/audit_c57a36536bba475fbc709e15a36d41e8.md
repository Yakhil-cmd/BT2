## Finding

### Title
Boundary-less prefix comparison in `pathIncludesOneOfAuthentifiers` allows authentifier path confusion across numerically-adjacent definition branches - (File: definition.js)

### Summary
`definition.js` gates whether a nested `['address', …]` branch of an address/asset definition is evaluated at all during signature verification by checking whether *any* supplied authentifier "belongs" to that branch's path. That check is done with a raw `substr` comparison that has no separator/boundary check, so path `"r.1"` is treated as a prefix of `"r.10"`, `"r.11"`, …, `"r.19"`, `"r.100"`, etc. This is the exact bug class described in the external CORS advisory (suffix/prefix matching without a boundary delimiter causing unrelated strings to be accepted as matching).

### Finding Description
`pathIncludesOneOfAuthentifiers` is defined as: [1](#0-0) 

```
function pathIncludesOneOfAuthentifiers(path, arrAuthentifierPaths, bAssetCondition){
	...
	for (var i=0; i<arrAuthentifierPaths.length; i++){
		var authentifier_path = arrAuthentifierPaths[i];
		if (authentifier_path.substr(0, path.length) === path)
			return true;
	}
	return false;
}
```

Definition tree paths are built by dotted numeric indices ("r", "r.0", "r.1", …, "r.10", …) as branches of `or`, `and`, `r of set`, `weighted and` are walked. Because the comparison only checks that `authentifier_path` starts with the literal characters of `path` — with no check that the next character is a path separator (`.`) or end-of-string — a supplied authentifier at path `"r.10"` (or `"r.11"`, `"r.100"`, …) satisfies `pathIncludesOneOfAuthentifiers("r.1", …)` even though `"r.10"` is a completely unrelated branch.

This function is the sole gate used in `validateAuthentifiers`'s `'address'` case to decide whether a nested address's own definition is even evaluated: [2](#0-1) 

```

		ifFound: function(arrInnerAddressDefinition){
			evaluate(arrInnerAddressDefinition, path, cb2);
		},

```

If the referenced inner address's definition does not itself require a signature at that exact path (e.g. it is composed purely of `seen address`, `attested`, `in data feed`, `cosigned by`, or other query-based/self-referential conditions rather than `sig`/`hash`), then reaching this branch is sufficient to make the branch evaluate to `true` — no authentifier tied specifically to that branch is actually needed, only an authentifier whose *path string* happens to collide due to the missing boundary check.

Where `arrAuthentifierPaths = Object.keys(assocAuthentifiers)` (the caller-supplied signature/hash paths): [3](#0-2) 

### Impact Explanation
Address definitions (including jointly authored shared/multisig addresses built via `wallet_defined_by_addresses.js`) are attacker-authorable data: any party posting a unit can define a new address, and any cosigner contributing to a shared address definition controls the exact shape/paths of the `or`/`and`/`r of set` tree. Because branch paths are simply the dot-joined index of the branch's position, a definition author can engineer a numeric collision (e.g., branch `1` and branch `10`) between an *innocuous-looking* required branch and a branch that references another address whose own definition needs no attacker-provided signature at all (`seen address`, `attested`, a permanently-true condition, etc.).

At verification time, supplying a genuinely required signature for the "real" branch (e.g., branch `10`) spuriously also "unlocks" evaluation of the unrelated branch `1`, which can then be satisfied without ever providing the signature that branch was nominally designed to require. In a shared/multisig address this lets a minority signer (or a maliciously crafted definition) bypass the intended M-of-N authorization structure, resulting in unauthorized spending of funds from an address that appeared, from its human-readable JSON definition, to require additional cosigner authentication for that branch. This directly maps to "unauthorized spending" in the validation-target list, reached purely through attacker-controlled address/definition and authentifier data (`definition.js`, `validateAuthentifiers`), with no privileged network role required.

### Likelihood Explanation
Exploitability requires the address (typically a shared/multisig address) to contain 10+ sibling branches in an `or`/`and`/`r of set`/`weighted and` construct so that single- and double-digit indices collide as string prefixes (`"r.1"` vs `"r.10"`), and for one colliding branch to reference another address whose definition doesn't itself gate on a signature at that path. This is a specific but entirely realizable definition shape that a malicious co-author of a shared address, or a single author of a self-defined address with many branches, can deliberately construct. It does not require any privileged/network position — only the ability to post units defining addresses/definitions, which is explicitly in-scope unprivileged behavior.

### Recommendation
Fix `pathIncludesOneOfAuthentifiers` to compare on a path-boundary basis instead of a raw substring, e.g.:
```
if (authentifier_path === path || authentifier_path.substr(0, path.length + 1) === path + '.')
	return true;
```
This ensures `"r.1"` only matches `"r.1"` itself or paths beginning with `"r.1."`, not `"r.10"`, `"r.11"`, etc.

### Proof of Concept
1. Author (or a colluding cosigner of) a shared address with a definition of the form:
```
['or', [
  ['sig', {pubkey: honest_pubkey}],                 // path "r.0"
  ['sig', {pubkey: cosigner1}],                     // path "r.1"  <- intended to require cosigner1's signature
  ['sig', {pubkey: cosigner2}],                      // "r.2"
  ... (branches "r.3".."r.9")
  ['address', 'ADDRESS_WITH_SEEN_ADDRESS_CONDITION'] // path "r.10" <- e.g. ['seen address', attacker_address], always satisfiable once attacker has posted any unit
]]
```
2. When spending, the attacker supplies only a valid signature for the leaf at path `"r.10"` (satisfying `['address', ADDRESS_WITH_SEEN_ADDRESS_CONDITION]`'s own internal sig if any, or none if that address's definition requires none) — but per the `substr` bug, `assocAuthentifiers` keyed with path `"r.10"` also causes `pathIncludesOneOfAuthentifiers("r.1", ["r.10"])` to return `true`.
3. Branch `"r.1"` (nominally requiring `cosigner1`'s signature) is then evaluated even though no `cosigner1` signature/authentifier at path `"r.1"` was supplied — if that branch's actual code path can be short-circuited or the OR is satisfied via branch `"r.10"` alone, the fund-controlling authorization intended to require `cosigner1` is bypassed.
4. Validate directly by unit-testing `Definition.pathIncludesOneOfAuthentifiers("r.1", ["r.10.sig"], false)` and observing it returns `true`.
