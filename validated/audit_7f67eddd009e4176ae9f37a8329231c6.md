### Title
Webhook signature verification is bypassed when `webhook_secret` is unset, allowing unauthorized forged GitHub events including CI-status manipulation that triggers unauthorized merges - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature`, used by `WebhooksController#verify_signature` as the sole authenticity gate for the `/webhooks` endpoint, unconditionally returns `true` whenever `webhook_secret` is not configured — regardless of the value (or absence) of the `X-Hub-Signature` header. This mirrors the reported ISM defect exactly: an optional security control (ISM / webhook secret) that, when left unset, causes the framework to accept unauthenticated input as if it had been verified.

### Finding Description
`WebhooksController#verify_signature` is the only authenticity check standing between an unauthenticated network request and the internal `Webhooks::Handlers` that mutate `Team`, `Membership`, `Commit`, and `Status` records: [1](#0-0) 

The check delegates entirely to `GitHubApp#verify_webhook_signature`: [2](#0-1) 

`webhook_secret` is explicitly documented as optional (`Webhook secret (optional)` and `webhook_secret: # nil` in the example config), and is stored via `.presence`, so it is commonly `nil`: [3](#0-2) 

The binding that should hold is: **`request originates from the trusted GitHub App installation` == `payload is trusted and used to mutate Team/Membership/Commit-status state`**. When `webhook_secret` is unset, `verify_webhook_signature` returns `true` for *any* payload with *any* (or missing) signature header, breaking that binding — exactly analogous to Hyperlane's default ISM accepting any message when no ISM is configured.

This lets an unauthenticated attacker POST arbitrary event payloads to `/webhooks` that are processed by the registered handlers: [4](#0-3) 

Two concrete exploitable handlers:

1. `MembershipHandler` trusts the forged `team`/`member` payload to add an attacker-chosen GitHub login to a `Team` record without any verification that the addition really happened on GitHub: [5](#0-4) 
If the targeted `Team.github_id` matches one of the org's `Shipit.github_teams`, this membership record directly satisfies `User#authorized?`: [6](#0-5) 

2. `StatusHandler` trusts the forged `sha`/`state` payload to create a CI status for any commit matching that SHA: [7](#0-6) 
`Commit#add_status` schedules merge processing whenever a status becomes `pending` or `success`: [8](#0-7) 
`ProcessMergeRequestsJob` then merges any pending PR whose head commit `all_status_checks_passed?`: [9](#0-8) 
and `MergeRequest#all_status_checks_passed?`/`merge!` rely purely on locally stored `Status` rows, which the forged webhook can set to `success` for any required CI context: [10](#0-9) 

### Impact Explanation
If the operator leaves `webhook_secret` unset (an explicitly supported, documented configuration), an unauthenticated attacker can:
- Forge `status` events to satisfy required CI checks on an arbitrary pending pull request, causing Shipit to call `merge_pull_request` via the app's GitHub credentials and merge the PR — an **unauthorized merge**, matching the Critical impact bar defined in scope rules.
- Forge `membership` events to add an arbitrary GitHub login to a `Team` matching `Shipit.github_teams`, escalating that identity into Shipit's authorization set — matching the High "escalation into `Shipit.github_teams` authorization" bar.

### Likelihood Explanation
Requires only that the operator not configure `webhook_secret`, which the shipped documentation and example config both present as optional/nil-by-default — the same precondition class ("ISM not configured") that the referenced report treats as Medium-but-valid. No GitHub credentials, Shipit session, or API token are required to send the forged request; only knowledge of the target's `/webhooks` URL and repository/organization name (both public).

### Recommendation
Require `webhook_secret` to be present and reject webhook delivery (return `422`/`401`) when it is not configured, instead of defaulting to "verified" — i.e., invert the `return true unless webhook_secret` fallback in `GitHubApp#verify_webhook_signature` to fail closed.

### Proof of Concept
1. Deploy Shipit with `github.webhook_secret` unset (as permitted by `docs/setup.md` and `config/secrets.development.example.yml`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{"sha":"<head-sha-of-pending-PR>","state":"success","context":"<required-ci-context>","branches":[{"name":"<target-branch>"}]}
```
No valid `X-Hub-Signature` is required — `verify_webhook_signature` returns `true` because `webhook_secret` is blank.
3. `StatusHandler#process` creates a `success` `Status` for the commit, `Commit#add_status` schedules `ProcessMergeRequestsJob`, and the job calls `MergeRequest#merge!`, causing Shipit to merge the pull request via the app's GitHub credentials — despite the attacker never having repository write access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
