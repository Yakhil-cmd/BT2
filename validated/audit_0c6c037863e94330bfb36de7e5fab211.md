### Title
AA bounce refund is fully abandoned for all assets when just one asset's bounce fee exceeds its trigger amount - ([File: aa_composer.js])

### Summary
`bounce()` in `aa_composer.js` refunds the trigger sender the unused portion of every asset they sent to an AA, minus a per-asset bounce fee, whenever the AA's trigger handling fails. The refund loop iterates all assets present in `trigger.outputs`, but as soon as it encounters a single asset whose `bounce_fees[asset]` exceeds the amount sent in that asset, it aborts the entire refund by returning immediately — abandoning refunds for every other asset that was sent in an amount large enough to be safely refunded. This mirrors the keep-tecdsa pattern: a loop that frees/returns several independent resources is guarded by a strict, per-item condition, and failure of that condition for just one item blocks the recovery of all the others, permanently stranding funds at the AA address.

### Finding Description
When an AA trigger fails validation/execution, `handleTrigger`'s `bounce()` function tries to return the unspent value to the trigger sender: [1](#0-0) 

```
var bBouncing = false;
function bounce(error) {
	...
	if ((trigger.outputs.base || 0) < bounce_fees.base)
		return finish(null);
	var messages = [];
	// iteration order is standardized since ECMAScript 2020
	for (var asset in trigger.outputs) {
		var amount = trigger.outputs[asset];
		var fee = bounce_fees[asset] || 0;
		if (fee > amount)
			return finish(null);
		if (fee === amount)
			continue;
		var bounced_amount = amount - fee;
		messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});
	}
	if (messages.length === 0)
		return finish(null);
	sendUnit(messages);
}
```

`trigger.outputs` is a map keyed by every asset that was included in the trigger unit's payment message(s), coming directly from the units posted by an arbitrary, unprivileged AA trigger sender. The `for...in` loop is meant to build one refund `payment` message per asset (skipping assets whose fee equals the amount, i.e. fully consumed by the fee). However, `if (fee > amount) return finish(null);` causes the function to bail out of the *entire* loop — discarding any refund messages that were already queued for previously-processed assets, and never even evaluating assets that come later in iteration order. This is analogous to `KeepBonding.freeBond`'s `require(lockedBonds[bondID] > 0)` reverting the whole `closeKeep()` call because of a single member's zero-bond bond, blocking release of the others' bonds — here, a single "too small" asset amount blocks the return of the base coins and all other assets, none of which will ever be refunded through this path, since a failed trigger produces no state update and no other automatic release mechanism for the trigger's payment outputs exists.

Any unprivileged AA trigger sender fully controls the amounts and assets bundled into the trigger unit; they can trivially construct a unit that sends a normal (refundable) amount of `base` bytes plus a tiny/dust amount of some other asset (below that asset's bounce fee) alongside a trigger designed to make the AA bounce (e.g., calling with invalid `trigger.data` so no `case` matches, or exploiting any legitimate bounce condition in the target AA). Because `bounce_fees.base` alone is checked to allow entering the loop, the base check can pass while a later asset in the map still trips the `fee > amount` bail-out, losing the base refund that would otherwise have gone through.

### Impact Explanation
This causes funds sent by users to be permanently stuck in the AA address (an AA fund freezing / loss scenario) whenever a trigger bounces and any one of the multiple assets attached to the trigger has an amount below its bounce fee. The tokens are not returned to the sender and are not consumed by any state-changing logic (since the trigger bounced), so they sit unspendable at the AA's address forever, since there's no other automated recovery path once the response object records the trigger as bounced.

### Likelihood Explanation
Likelihood is high in principle for any user who (deliberately or accidentally) sends multiple assets to an AA in the same trigger unit where the AA is caused to bounce and one of the attached asset amounts is smaller than that asset's configured bounce fee. Users regularly attach multiple payment messages in a single unit to interact with multi-asset AAs (e.g., market-maker/DEX AAs seen in the AA examples), so the multi-asset trigger scenario is common; only the specific combination of "at least one dust-sized asset amount + a bounce" is required to trigger fund loss, and both are fully controllable/observable by the trigger's author.

### Recommendation
In `bounce()`, do not abort the whole refund loop when one asset's fee exceeds its amount. Instead, `continue` to the next asset (skip refunding that particular asset, consistent with the `fee === amount` case) rather than calling `return finish(null)`, so that refundable assets are still returned even if one attached asset is too small to refund. Additionally, reconsider whether it is safe to still exit early when `trigger.outputs.base < bounce_fees.base` given that non-base assets could otherwise still be refunded — this check should likewise not stop other assets' bounce fee collection/refunds unless base funds are strictly required to pay for the bounce unit itself.

### Proof of Concept
1. Deploy any AA that bounces on a specific `trigger.data` condition (e.g., `bounce('bad request')`), and that accepts multiple assets in messages (a common multi-asset AA such as an exchange/AMM).
2. As an unprivileged user, post a trigger unit containing two payment messages: (a) a `base` payment with an amount `> bounce_fees.base` (so it would qualify for a base refund), and (b) a payment in some other registered asset with an amount smaller than that asset's `bounce_fees[asset]` (e.g., 1 unit of dust).
3. Ensure the trigger data causes the AA to bounce.
4. Observe in `bounce()` that the loop processes `base` first (queues a refund message for the base amount minus fee), then encounters the dust asset where `fee > amount`, triggering `return finish(null)` — discarding the already-queued base refund message. No refund unit is ever sent: `sendUnit(messages)` is never called.
5. The user's base bytes and asset dust remain stuck at the AA address with no state update recorded and no way to reclaim them through this trigger. [2](#0-1)
