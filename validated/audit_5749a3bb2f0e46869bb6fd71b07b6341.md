### Title
Webhook signature is validated against the payload's `repository.owner.login`, but event handlers act on unrelated fields (`repository.full_name`, `sha`) with no cross-check to the authenticated organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository_owner` (`params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')`), then dispatches the *entire* raw JSON payload to `Shipit::Webhooks::Handlers` for processing. Nothing re-validates that the specific fields the handlers act on (`repository.full_name` in `Handler#repository_name`, or `sha` in `StatusHandler`) actually belong to the organization whose secret was used to verify the signature. This mirrors the reported bug class: a verified/authenticated identifier (the version in the CVE, the organization here) is disconnected from the value the code actually operates on (the loaded version in the CVE, the target repository/commit here).

### Finding Description
`verify_signature` computes the secret to check via `Shipit.github(organization: repository_owner)`: [1](#0-0) 
`repository_owner` is read purely from the payload's `repository.owner.login` (or `organization.login`) field: [2](#0-1) 

Once the signature check passes (using organization A's `webhook_secret`), the same raw payload — fully attacker-controlled, since it is only constrained by "produces a valid HMAC under organization A's secret" — is handed to handlers. The base `Handler` derives the target repository/stacks from a *different* JSON field, `repository.full_name`, with no comparison back to `repository.owner.login`: [3](#0-2) 

Worse, `StatusHandler` doesn't even scope by repository/stack at all — it looks up commits globally by `sha` across the entire Shipit installation: [4](#0-3) 

An operator who owns/administers organization A's GitHub App inside a shared, multi-org Shipit deployment (the documented multi-org config format) legitimately knows organization A's `webhook_secret`: [5](#0-4) 
They can therefore produce a validly-signed `status` (or `push`/`check_suite`) webhook whose `repository.owner.login` is `"orgA"` (to pass `verify_signature`) while its `sha` (for `status`) or `repository.full_name` (for `push`/`check_suite`) references a commit/stack that belongs to a completely different organization's repository, e.g. `"orgB/victim-repo"`.

### Impact Explanation
Via a forged `status` event, an attacker who only controls organization A's webhook secret can inject a GitHub commit status (e.g. `state: "success"`, arbitrary `context`) for any commit SHA that happens to exist in *any* stack in the Shipit instance, including stacks belonging to organization B, which they have no GitHub permissions on. `Commit#add_status` reacts to this by evaluating `deployable?` and triggering `stack.schedule_merges` when the new status is `pending` or `success`: [6](#0-5) [7](#0-6) 
Since `deployable?` gates whether continuous delivery proceeds, and `schedule_merges`/`schedule_continuous_delivery` can advance the deploy pipeline once a commit looks green, this can unlock an unauthorized deploy for a stack the attacker does not control, satisfying the Critical-tier "unauthorized deploy" impact. Similarly, `push`/`check_suite` events keyed on `repository.full_name` let an org-A-authenticated caller enqueue `GithubSyncJob`/`RefreshCheckRunsJob` against organization B's stack: [8](#0-7) [9](#0-8) 

### Likelihood Explanation
This requires the attacker to legitimately administer at least one organization/GitHub App onboarded to the shared Shipit instance (and thus know that org's `webhook_secret`), which is a realistic scenario for any multi-tenant Shipit deployment (explicitly supported per the multi-org config in `config/secrets.development.example.yml`). No GitHub write access to the victim organization/repository is required — only knowledge of a sibling organization's webhook secret and the ability to guess/know a target commit SHA (obtainable from a public repo, PR, or CI log) or a target stack's `owner/name`.

### Recommendation
Cross-validate the identifiers used for authorization against the identifiers used for state mutation:
- In `WebhooksController`/`Handler`, ensure `repository.owner.login` (used to pick the verifying secret) matches the owner portion of `repository.full_name` (used to select stacks) before processing.
- In `StatusHandler`, scope the `Commit.where(sha: ...)` lookup to commits whose `stack.repository.owner` equals the verified `repository_owner`, rather than searching globally by SHA.
- More generally, treat the verified organization as a hard boundary: every handler should filter results to repositories under `repository_owner`, never trusting other payload-supplied identifiers as equivalent to the verified one.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `orgA` and `orgB`, each with a distinct `webhook_secret` (per `config/secrets.development.example.yml`).
2. As the operator of `orgA` (who legitimately knows `orgA`'s `webhook_secret`), craft a `status` webhook payload:
   ```json
   {
     "sha": "<sha of a commit belonging to an orgB stack>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/some-repo" }
   }
   ```
3. Sign it with `orgA`'s `webhook_secret` (`sha1=` HMAC as computed in `Hook::DeliverySigner`/`GithubApp#verify_webhook_signature`) and POST it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` to `"orgA"`, uses `orgA`'s secret, and the signature is valid — passing verification.
5. `StatusHandler#process` finds the commit by `sha` alone (no org check) and calls `commit.create_status_from_github!`, injecting a fabricated `"success"` status onto a commit in `orgB`'s stack, potentially triggering `stack.schedule_merges` / continuous delivery for a stack the attacker does not control.
