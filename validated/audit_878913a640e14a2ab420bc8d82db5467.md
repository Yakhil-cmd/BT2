Rationale: the Sherlock report's root cause is specific to Arbitrum's L1→L2 sequencer message-queue mechanism, where a TX enqueued during sequencer downtime retains its original L1 submission timestamp rather than its processing timestamp, letting stale Chainlink price data slip through `chainlinkAdaptor.sol`. That failure mode depends on an L2 rollup's dual-clock (L1 timestamp vs. L2 processing time) architecture and a sequencer/L1↔L2 messaging queue — neither of which exists in Substrate/FRAME. Polkadot SDK runtimes derive time from `pallet_timestamp` set once per block by the block author and validated by other validators/collators, with no analogous "enqueue with stale L1 timestamp" path.

The closest on-chain price-feed analog in this repo is `pallet-oracle` [1](#0-0) , which timestamps every submission using `T::Time::now()` at the time of dispatch [2](#0-1)  and already filters out values older than a configurable `ExpiresIn` window before aggregation [3](#0-2) . Since timestamps are assigned at actual on-chain execution time (not pre-recorded by some external L1 submission queue), there is no mechanism by which a value could be processed with an artificially old timestamp the way an Arbitrum-queued TX can. Submission is gated by `T::Members` (permissioned oracle operators) or root [4](#0-3) , so there is no unprivileged, attacker-controlled entry point analogous to "TX submission during sequencer downtime" either.

No demonstrable, non-EVM-specific analog with a real unprivileged entry point and a concrete stale-timestamp acceptance path was found in this codebase.
