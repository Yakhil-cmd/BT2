### Title
Missing binding between pairing request and legitimate pairing session allows pairing hijack via race on `pairing_secret` - (File: device.js)

### Summary
`handlePairingMessage` in `device.js` validates only that the presented `pairing_secret` exists and is not expired; it never verifies that this specific "pairing" message is the first/legitimate response to a still-outstanding pairing invitation, nor does it serialize acceptance atomically with invalidation of the secret. This mirrors the root cause of CVE-2024-51738 (Sunshine): the protocol accepts any request that carries the shared secret without enforcing that only the first, legitimate completion of the handshake wins, allowing a race/hijack of the pairing flow.

### Finding Description
A device waiting to be paired calls `startWaitingForPairing`/`getOrGeneratePermanentPairingInfo`, which stores a `pairing_secret` in the `pairing_secrets` table and hands the code (`pubkey@hub#secret`) to the user to share out-of-band (QR/URI, see `uri.js` parsing of the `pairing` URI type). [1](#0-0) 

Any device that later presents this `pairing_secret` in a `pairing` message is accepted as the correspondent, as long as the secret is found and not expired: [2](#0-1) 

Crucially:
- The lookup query treats a literal `'*'` value as a valid match in addition to the real secret (`pairing_secret IN(?,'*')`), a leftover wildcard-acceptance branch with no corresponding safeguard shown elsewhere in the pairing code, widening acceptance beyond a single specific request. [3](#0-2) 
- The one-time secret is only deleted from `pairing_secrets` **after** the correspondent has already been written into `correspondent_devices` and marked confirmed, i.e. invalidation happens at the very end of the handling chain, not atomically with the initial validation: [4](#0-3) 
- Messages "from hub" are only serialized by a single mutex key `"from_hub"` local to this device's own message queue at the wallet-message-dispatch layer, which serializes handling for *this device instance* but provides no protocol-level binding that ties a `pairing` message to the specific pairing invitation it is responding to (no nonce/challenge tied to the invitation, no confirmation step, no check that pairing is still "expected" beyond a coarse expiry date): [5](#0-4) 
- `pairing` is also one of the whitelisted subjects accepted from completely unknown correspondents at the hub-message layer, i.e. the protocol is explicitly designed to accept the very first party that shows up with the secret, without any additional binding to the party the user actually intended to pair with: [6](#0-5) 

Because the only "authentication" of a pairing attempt is knowledge of the `pairing_secret` (a value that must be relayed out-of-band and is not bound to a session/challenge or single specific counter-party), and because the accept-then-delete sequence is not atomic, an attacker who can capture or race the delivery of the pairing code (e.g., intercept the out-of-band QR/URL channel, or race a concurrent `pairing` message to the hub before the legitimate device's message is fully processed and the secret invalidated) can complete pairing with the victim device instead of, or in addition to, the intended counterpart — exactly the "improper enforcement of pairing protocol request order" bug class described in CVE-2024-51738.

### Impact Explanation
A successful pairing hijack lets the attacker's device become a trusted correspondent of the victim (`correspondent_devices`, `is_confirmed=1`). Trusted correspondents in ocore can initiate shared-address flows, arbiter contracts, private-payment chains, and wallet-related device messages (`arbiter_contract.js`, `wallet.js` message handlers), so a hijacked pairing is a stepping stone to unauthorized fund-related interactions (e.g., being addressed as a payment counterparty, arbiter contract peer, or shared-wallet co-signer) and to denial of pairing/service for the legitimate party. This satisfies the "unauthorized... AA fund loss" / "node disagreement" class of impact required, via impersonation of a paired device that the victim's wallet subsequently trusts for further asset/contract negotiation.

### Likelihood Explanation
Exploitation requires the attacker to obtain or race the `pairing_secret` before/at the same time as the legitimate counterpart — feasible whenever the out-of-band channel carrying the pairing code (screen share, copied link, chat message, QR photograph) is observable by a third party, or when the attacker can beat the legitimate peer's message to the hub. Given `pairing` is explicitly reachable from unknown/unauthenticated correspondents and requires no challenge/response tied to a specific expected peer, the likelihood is non-trivial for a MITM/observer of the pairing exchange, matching the CVE's AC:L/AT:P/PR:N/UI:P profile.

### Recommendation
Bind pairing completion to the specific outstanding invitation rather than only to secret-possession: generate the secret with a bound expected use (single accept, verified atomically with deletion in the same transaction before crediting the correspondent), remove the unused `'*'` wildcard match branch, and consider requiring an explicit user confirmation step correlated to the specific pairing attempt (e.g., displaying the requester's device name/fingerprint) before marking the correspondent confirmed, so that a race or interception of the shared code cannot silently complete the pairing on the attacker's behalf.

### Proof of Concept
1. Victim device A calls `startWaitingForPairing`, generating `pairing_secret` S and displaying `pubkey_A@hub#S` for device B to scan. [7](#0-6) 
2. Attacker intercepts/observes S before B uses it (e.g., screenshot of QR, shared link, or races the hub message).
3. Attacker's device sends a `pairing` message to A's hub with `body.pairing_secret = S` before B's legitimate message is fully processed and S is deleted. [2](#0-1) 
4. `handlePairingMessage` finds S still valid, inserts the attacker as a confirmed correspondent, and only afterwards deletes S — the attacker is now paired with A instead of (or ahead of) B. [4](#0-3)
