### Title
Bad-debt write-down clamps the supply index to `SUPPLY_INDEX_FLOOR_RAW`, leaving stranded "phantom" supply claims that drain fresh deposits - (File: contracts/pool/src/interest.rs)

### Summary
The analog of CVE-2023-35951 (an attacker-influenced write that overflows its intended bounds and corrupts adjacent state) in XOXNO Lending is the supply-index write-down in `apply_bad_debt_to_supply_index`. When bad debt exceeds the total supplied value, the function clamps the supply index up to `SUPPLY_INDEX_FLOOR_RAW` instead of reducing positions to zero. Every pre-existing supply share retains a floor-priced claim the pool never intends to back, and any later deposit into the empty market can be withdrawn by the stranded claimant.

### Finding Description
`apply_bad_debt_to_supply_index` computes `reduction_factor = remaining / total_supplied_value`, applies it to the supply index, and then clamps the result to at least `SUPPLY_INDEX_FLOOR_RAW` (= `RAY / 1_000`) [1](#0-0) [2](#0-1) . When `bad_debt >= total_supplied_value`, `capped` saturates, `remaining` is zero, and the "correct" index is zero — but the floor clamp sets it to a strictly positive value. Because share balances (`supplied`) are untouched, each existing share is still redeemable at the floored index.

The pool's own test `test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard` demonstrates the exploit primitive: after a wipeout clamps the index, `unscale_supply_floor` on a stranded position still reports a positive claim; a fresh deposit mints shares at the same floored index and credits cash; the stranded holder then calls `resolve_withdrawal`/`require_reserves`/`burn_supply`/`debit_cash` and extracts exactly the new depositor's funds, leaving the honest supplier's claim unbacked [3](#0-2) .

Root cause is a bounds clamp applied to the wrong variable: like the OFF parser overflowing a fixed buffer, the write-down "overflows" the representable loss (100%) and the clamp preserves residual entitlement that should have been zeroed. There is no guard tying post-write-down withdrawability to remaining cash coverage (`require_reserves` only checks the debit, not that stranded claims were extinguished), and no deficit tracking marks the market as wiped out.

### Impact Explanation
Theft of user funds / protocol insolvency: after any full-wipeout bad-debt event, every legacy supplier retains a phantom claim priced at `SUPPLY_INDEX_FLOOR_RAW × shares`. The first honest depositor into the damaged market funds those claims; the stranded holder (or the attacker who deliberately kept a supply position in the market they griefed) withdraws the fresh cash in full. `claim_revenue`'s cap-by-cash logic confirms cash is the binding constraint [4](#0-3) .

### Likelihood Explanation
Reachable by a single unprivileged address: the attacker supplies into a market, creates an underwater borrow (own or another account's), and lets `liquidate`/`clean_bad_debt` socialize the loss through the pool's seize path (`contracts/pool/src/ops/seize.rs`, `contracts/controller/src/positions/liquidation/bad_debt.rs`), which routes to `apply_bad_debt_to_supply_index`. If the bad debt meets or exceeds total supplied value (small/young markets, or the attacker dominating both sides), the floor clamp engages. The attacker then races or waits for any subsequent `supply`/`deposit` and withdraws the phantom claim. Exploiting requires an actual bad-debt event, so likelihood is conditional on achieving a wipeout rather than certain.

### Recommendation
Do not clamp the post-write-down supply index to `SUPPLY_INDEX_FLOOR_RAW` when `bad_debt >= total_supplied_value`; instead zero out the market's supply claims (or record a permanent deficit/wipeout flag that blocks `withdraw`/`claim_revenue` for legacy shares). Alternatively, on wipeout, burn all existing supply shares or gate withdrawals on a per-market deficit ledger so stranded claims cannot be exercised against fresh cash.

### Proof of Concept
Conceptual PoC (mirroring the existing unit test):

1. Attacker supplies `A` units into a market and arranges bad debt `>= A × supply_index` (e.g., via an underwater borrow liquidated through `clean_bad_debt`, hitting `seize.rs` → `apply_bad_debt_to_supply_index`).
2. Supply index is clamped to `SUPPLY_INDEX_FLOOR_RAW`; attacker's `scaled_A` shares still unscale to `stranded > 0`.
3. Victim deposits `c` units; pool mints `scaled_B` and credits `c` cash.
4. Attacker calls controller `withdraw` for their full position; pool resolves `gross = stranded` (= `c` at the floored index), `debit_cash(gross)` succeeds, attacker receives the victim's deposit.
5. Victim's claim `b_claim = c` is now unbacked: `cash == 0 < b_claim` — funds stolen exactly as asserted in `contracts/pool/tests/interest.rs:356-368` [5](#0-4) .

Caveat: I confirmed the pool-side mechanics and the existence of the controller `clean_bad_debt`/liquidation bad-debt path (`contracts/controller/src/positions/liquidation/bad_debt.rs`, `contracts/controller/src/lib.rs`), but did not fully trace whether the seize path allows `bad_debt` to reach `>= total_supplied_value` in a single unprivileged flow; if dust thresholds cap per-call write-downs, repeated calls or a market where the attacker is the dominant supplier still satisfy the precondition.

pub(crate) fn apply_bad_debt_to_supply_index(cache: &mut Cache, bad_debt: Ray) {
    let total_supplied_value = cache.supplied().mul(cache.env(), cache.supply_index());

    if total_supplied_value == Ray::ZERO {
        return;
    }

    let capped = bad_debt.min(total_supplied_value);
    let remaining = total_supplied_value.checked_sub(cache.env(), capped);

    let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
    let new_supply_index = cache
        .supply_index()
        .mul_floor(cache.env(), reduction_factor);

    cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
}
```

fn test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard() {
    let t = TestSetup::new();
    t.as_contract(|| {
        let scaled_a_raw = 1_000_000 * RAY;
        let mut cache = t.fresh_cache(PoolStateRaw {
            supplied: scaled_a_raw,
            borrowed: 0,
            revenue: 0,
            borrow_index: RAY,
            supply_index: RAY,
            last_timestamp: 0,
            cash: 0,
        });
        let scaled_a = Ray::from(scaled_a_raw);

        apply_bad_debt_to_supply_index(&mut cache, Ray::from(2_000_000 * RAY));
        assert_eq!(
            cache.supply_index().raw(),
            SUPPLY_INDEX_FLOOR_RAW,
            "wipeout must clamp supply index UP to the floor, not reset the base"
        );

        let stranded = cache.unscale_supply_floor(scaled_a);
        assert!(stranded > 0, "floor clamp leaves userA a phantom claim");
        assert_eq!(cache.cash(), 0, "empty market: no cash to extract yet");

        let c = stranded;
        let scaled_b = cache.calculate_scaled_supply(c);
        cache.mint_supply(scaled_b);
        cache.credit_cash(c);

        let b_claim = cache.unscale_supply_floor(scaled_b);
        assert_eq!(b_claim, c, "userB's honest claim equals their deposit");

        let (burn, gross) = cache.resolve_withdrawal(i128::MAX, scaled_a);
        cache.require_reserves(gross);
        cache.burn_supply(burn);
        cache.debit_cash(gross);

        assert!(gross > 0, "stranded position pays out non-zero");
        assert_eq!(
            gross, c,
            "userA drains exactly userB's fresh deposit out of the pool"
        );

        assert!(
            cache.cash() < b_claim,
            "pool cash ({}) can no longer cover userB's claim ({}): honest supplier lost funds",
            cache.cash(),
            b_claim
        );
        assert_eq!(cache.cash(), 0, "userA drained the pool to empty");
    });
```
