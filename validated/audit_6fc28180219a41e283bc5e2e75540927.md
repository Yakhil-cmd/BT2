Based on my investigation, I found a concrete admission-boundary weakness in the multisig transaction validation flow, though its severity is tied to a feature flag whose default status I could not fully confirm in the index.

### Title
Multisig transaction prologue admits payload that was never approved by owners when `abort_if_multisig_payload_mismatch` is not enabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, which is the VM prologue (admission) check for `MultisigTransaction`, is supposed to guarantee that the payload about to execute is the one that received the required owner approvals. When the multisig transaction was created with the full payload stored on-chain (via `create_transaction`, not `create_transaction_with_hash`), the equality check between the on-chain approved `transaction.payload` and the caller-supplied `payload` argument is itself gated behind `features::abort_if_multisig_payload_mismatch_enabled()`.

### Finding Description
In `validate_multisig_transaction`: [1](#0-0) 

- If `transaction.payload_hash` is `Some` (created via `create_transaction_with_hash`), the hash of the caller-supplied `payload` is always checked.
- If `transaction.payload` is `Some` (full payload stored via `create_transaction`), the equality check against the caller-supplied `payload` bytes only runs `if (features::abort_if_multisig_payload_mismatch_enabled() && transaction.payload.is_some() && !payload.is_empty())`.

This means that when the feature is disabled, an owner executing the multisig transaction can supply a `payload` argument for the `MultisigTransaction` that differs from the `transaction.payload` the other owners actually voted to approve, and admission (`validate_multisig_transaction`, called both from mempool VM-validation and the on-chain prologue) does not reject it: [2](#0-1) 

The same "provided_payload" computation is mirrored at actual execution time in `execute_multisig_transaction`, which fetches the payload to run via `GET_NEXT_TRANSACTION_PAYLOAD` using the same caller-controlled bytes: [3](#0-2) 

Because the equality assertion in `validate_multisig_transaction` is the only admission-time guarantee that the executed payload matches what owners approved, and it is conditionally skipped, a transaction whose actual payload was never voted on by the required quorum of owners can still pass admission and commit as the multisig account.

### Impact Explanation
If `abort_if_multisig_payload_mismatch_enabled` is not turned on, any single owner who can produce the required number of approvals for *some* transaction id (e.g. a benign transfer that legitimately gathered quorum) can, at execution time, substitute an entirely different, unapproved entry function/arguments and have it executed under the multisig account's authority — effectively bypassing the k-of-n approval requirement that is the entire security guarantee of the multisig scheme. This is a "pre-validation mismatch that causes a transaction which should fail admission to execute and commit," directly matching the Admission Pivots. Impact is high, as it allows unauthorized action under the multisig account's signer identity without full approval-set validation.

### Likelihood Explanation
Likelihood is fully dependent on the on-chain state of the `abort_if_multisig_payload_mismatch` feature flag: [4](#0-3) . I was not able to conclusively determine, from the indexed code, whether this flag is enabled by default on mainnet/testnet in the current codebase revision — this needs to be verified directly (e.g. via `aptos-move/framework/aptos-framework/sources/genesis.move` or the release feature-flag manifest) before treating this as exploitable in production. The presence of a dedicated feature flag strongly suggests this exact gap was previously identified and the flag is the fix, which reduces novelty and may mean it is already enabled by default — this needs explicit confirmation.

### Recommendation
Make the payload-equality check for the full-payload case (`transaction.payload.is_some()`) unconditional, the same way the payload-hash check is unconditional, rather than gating it behind `abort_if_multisig_payload_mismatch_enabled`. Alternatively, deprecate/remove the feature flag once fully rolled out so there is no configuration under which the admission check can be bypassed.

### Proof of Concept
Conceptual PoC (I could not run this in the index, so it should be validated in an e2e-move-tests environment):
1. Owner A creates a multisig transaction via `create_transaction` with a benign payload (e.g., `transfer(recipient, 1)`), storing the full payload on-chain.
2. Owners B, C approve, reaching quorum (`num_signatures_required`).
3. Owner A submits a `MultisigTransaction` with `transaction_payload = Some(malicious_entry_function)` (e.g., `transfer(attacker, all_funds)`) instead of the approved one.
4. If `abort_if_multisig_payload_mismatch_enabled()` is `false`, `validate_multisig_transaction`'s payload-equality assert is skipped (`transaction.payload_hash` is `None` since `create_transaction` was used, and the `is_some()`-gated check is bypassed by the feature flag), so the prologue passes.
5. `execute_multisig_transaction` / `GET_NEXT_TRANSACTION_PAYLOAD` executes the malicious payload as the multisig account, using approvals that were never granted for it.

**Caveat**: I was unable to fully trace the internal Move implementation of `get_next_transaction_payload` (referenced only via the `GET_NEXT_TRANSACTION_PAYLOAD` constant in `aptos-move/aptos-vm/src/system_module_names.rs`) to confirm byte-for-byte that it returns the caller-supplied payload rather than always the stored one in this code path. This should be verified with a live Devin session that can read the full file and run the e2e Move test suite (`aptos-move/e2e-move-tests`) before treating this as a confirmed, exploitable bug.

pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };

    session
        .execute_function_bypass_visibility(
            &MULTISIG_ACCOUNT_MODULE,
            VALIDATE_MULTISIG_TRANSACTION,
            vec![],
            serialize_values(&vec![
                MoveValue::Signer(txn_data.sender),
                MoveValue::Address(multisig_address),
                MoveValue::vector_u8(provided_payload),
            ]),
            &mut UnmeteredGasMeter,
            traversal_context,
            module_storage,
        )
        .map(|_return_vals| ())
        .map_err(expect_no_verification_errors)
        .or_else(|err| convert_prologue_error(err, log_context))
}
