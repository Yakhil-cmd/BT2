### Title
Webhook Signature Verification Is Keyed by `repository.owner.login` but Event Processing Trusts `repository.full_name`, Allowing Cross-Organization Forged Webhooks When Any Configured Org Omits `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App (and thus which HMAC secret) to verify a webhook against using the attacker-controlled field `repository.owner.login` (or `organization.login`) from the unauthenticated request body, while every event `Handler` acts on a *different* field of the same payload, `repository.full_name`, to resolve the target `Stack`/`Repository`. These two fields are never cross-checked, and `webhook_secret` is explicitly documented as optional per organization.

### Finding Description
`WebhooksController#verify_signature` picks the verifying `GitHubApp` like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')`), and used to look up the org-specific `GitHubApp` via `Shipit.github(organization: repository_owner)`.

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization has no `webhook_secret` configured: [3](#0-2) 

The setup docs explicitly mark `webhook_secret` as optional per organization in the multi-org config layout: [4](#0-3) 

Meanwhile, every webhook `Handler` resolves the actual `Repository`/`Stack` to act on from a *different* JSON field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

This is used by `PushHandler` (triggers a GitHub sync of a stack), `CheckSuiteHandler` (schedules refresh of check runs used for deploy gating), `StatusHandler` (creates a `Status` used to gate deploys via commit statuses), and the `PullRequest::*` handlers (drive review-stack provisioning/archiving): [6](#0-5) [7](#0-6) [8](#0-7) 

**The broken binding (as an equality that should hold but doesn't):**
`organization used to select the verifying webhook_secret (repository.owner.login)` should equal `organization whose repository is actually written to (owner segment of repository.full_name)`. Nothing in `verify_signature` or `Handler#repository_name` enforces this equality — the two are read from independent, attacker-supplied fields of the same unauthenticated JSON body.

**Before the attack:** In a multi-org Shipit install (`config/secrets.yml` `github:` keyed by org, per `docs/setup.md`), org `A` (e.g., a low-value/test org an operator installed the app for, perhaps without bothering to set `webhook_secret`) is configured with `webhook_secret: nil`, and org `B` (a legitimate, high-value org) has stacks configured and a real `webhook_secret`.

**After the attack:** An unauthenticated attacker (no GitHub App install, no Shipit session, no `ApiClient` token) POSTs a forged JSON body to `/webhooks` with `X-Github-Event` set (e.g. `push`), no valid `X-Hub-Signature` needed, and a body where `repository.owner.login = "A"` (or `organization.login = "A"`) but `repository.full_name = "B/some-repo"`. `verify_signature` resolves `Shipit.github(organization: "A")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally — the request passes verification without any real signature check. The event is then dispatched to `PushHandler`/`StatusHandler`/`CheckSuiteHandler`, which resolve the target stack using `repository.full_name` = `"B/some-repo"`, i.e., org `B`'s actual production stack, and perform privileged side effects (triggering `GithubSyncJob`, forging commit statuses for CI, scheduling check-run refreshes, or manipulating review-stack provisioning) against a repository whose organization never authenticated this particular request.

### Impact Explanation
This lets an unauthenticated external attacker inject forged GitHub events that are processed as if legitimately signed by org B, as long as *any* other org configured on the same Shipit instance lacks (or is misconfigured without) a `webhook_secret`. Concretely reachable effects on org B's stacks with no credentials at all:
- `StatusHandler` fabricates arbitrary commit `Status` records (state/description/context) for real commits, which downstream deploy-gating logic (merge/deploy readiness) may rely on — this is a path toward an unauthorized deploy by forging a green CI status.
- `PushHandler` can trigger `GithubSyncJob`/`sync_github` for arbitrary stacks, and `CheckSuiteHandler` can force check-run refresh scheduling, both against repositories the attacker doesn't control.
- `PullRequest` handlers can archive/unarchive/provision review stacks for org B's repositories.

This satisfies the High/Critical impact bar around "an unauthorized deploy" enabled by forged CI status, reachable purely by an unauthenticated network attacker — no GitHub App install, Shipit session, or API token required.

### Likelihood Explanation
Requires a specific but realistic deployment condition: a multi-organization Shipit instance where at least one configured organization has an empty/absent `webhook_secret` — which the project's own setup documentation presents as an acceptable, optional configuration. Given that, exploitation requires zero credentials and a single crafted HTTP POST; the vulnerable code path (`verify_signature` deriving trust from `repository.owner.login` while handlers act on `repository.full_name`) is unconditionally present regardless of configuration.

### Recommendation
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for a *specific* configured organization in multi-org mode; either require `webhook_secret` for all orgs when multiple orgs are configured, or fail closed.
- Bind signature verification and repository resolution to the same trust anchor: after selecting the verifying `GitHubApp` by `repository.owner.login`/`organization.login`, verify that `repository.full_name`'s owner segment matches that same organization before dispatching to handlers, rejecting mismatches.

### Proof of Concept
1. Configure Shipit with two GitHub Apps per `docs/setup.md`'s multi-org format: org `A` with `webhook_secret:` left blank, and org `B` with a real `webhook_secret` and an existing `Stack` for `B/prod-repo`.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, and body:
```json
{
  "sha": "<real commit sha in B/prod-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "A" }, "full_name": "B/prod-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "A")` → `webhook_secret` nil → `verify_webhook_signature` returns `true` regardless of the (absent/invalid) signature header.
4. `StatusHandler` looks up commits by `sha` (unaffected by which org "verified") and creates a forged `Status` on org B's real commit, which can then be consumed by deploy/merge gating logic.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
