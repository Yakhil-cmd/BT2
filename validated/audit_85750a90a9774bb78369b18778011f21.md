### Title
Unbounded HTTP response accumulation in arbiter/arbstore requests enables memory-exhaustion DoS from a malicious arbiter/arbstore counterparty - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` implements the client side of arbiter-contract negotiation between two wallet users. When a contract references an `arbiter_address`/`arbstore_address`, the wallet resolves that address to a URL via the hub and then talks HTTP(S) directly to whatever server sits at that URL (`getAppealFee`, `openDispute`) through the local `httpRequest` helper.

### Finding Description
`httpRequest` buffers the entire HTTP response body into a plain JS string with no size cap and no request/response timeout: [1](#0-0) 

The host contacted is not fixed — it is resolved from `objContract.arbiter_address` / `objContract.arbstore_address` via `device.requestFromHub("hub/get_arbstore_url"...)`, and these fields originate from the arbiter contract negotiated with a counterparty over the paired-device channel: [2](#0-1) [3](#0-2) 

A counterparty in a private arbiter-contract negotiation can choose (or set up) an arbitrary arbiter/arbstore identity for the contract. When the victim's wallet later calls `getAppealFee` or `openDispute` for that contract, it connects to the resolved arbstore's HTTP endpoint and reads the response into memory with no upper bound — mirroring exactly the go-getter bug class (client performs an unsafe download of a server-controlled response with no size/redirect/timeout limits, enabling asymmetric resource exhaustion: a small malicious response triggers unbounded memory/CPU consumption on the client).

### Impact Explanation
A malicious arbstore/arbiter server (which the attacker fully controls, since arbiter identity in a contract is negotiated between the two private parties) can respond to `/api/get_appeal_fee` or `/api/appeal/new` with an extremely large or slow-drip body. Since `httpRequest` has no length limit, no timeout, and concatenates into a string forever until `end`, this can exhaust the victim wallet process's memory or hang it, denying wallet functionality (including subsequent legitimate payment/appeal operations) — a resource-exhaustion DoS triggerable by an unprivileged private-payment counterparty who is a party to (or self-designates as) the arbiter/arbstore for a contract.

### Likelihood Explanation
Moderate/high: no special privileges are needed beyond being a counterparty in an arbiter contract, which is a normal wallet-to-wallet negotiation flow. The attacker only needs to control (or collude with) the arbstore server referenced by `arbiter_address`/`arbstore_address`, then wait for the victim to call `getAppealFee`/`openDispute`.

### Recommendation
- Enforce a maximum response size in `httpRequest` (abort/destroy the response stream once a threshold is exceeded).
- Add connection/response timeouts (`req.setTimeout`, socket idle timeout) and abort on timeout.
- Consider streaming JSON parsing with a hard cap rather than unbounded string concatenation.

### Proof of Concept
1. Victim negotiates/accepts an arbiter contract where `arbiter_address` (or `arbstore_address`) resolves, via the hub, to a URL controlled by the attacker.
2. Victim's wallet calls `getAppealFee(hash, cb)` (or `openDispute`), which performs `httpRequest(url, "/api/get_appeal_fee", "", cb)`.
3. Attacker's server responds with HTTP 200 and streams gigabytes of data (or an endless stream) without closing the connection.
4. `resp.on("data", ...)` keeps appending to the `data` string indefinitely because there is no length check or timeout in `arbiter_contract.js:388-408`, exhausting the victim node's memory and potentially crashing the wallet process. [4](#0-3)

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}
