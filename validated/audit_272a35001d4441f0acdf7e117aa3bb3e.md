### Title
Stack-scoped ApiClient token can read CI status of any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup method used by every other API controller. Everywhere else in the API, an `ApiClient` that is scoped to a single stack (`ApiClient#stack_id`) can only ever resolve `stack` from the subset of stacks it is authorised for. `CCMenuController` instead resolves the stack directly from the request parameter with no such scoping, so a token that is only supposed to authorise `read:stack` on one stack can be replayed against the CCMenu status endpoint of any other stack.

### Finding Description
The standard API authorization binding is: **the stack a token authorises == the stack the request touches**. This is implemented in `Shipit::Api::BaseController`: [1](#0-0) 

`stacks` is filtered to `current_api_client.stack_id` when the client is scoped, and `stack` is looked up only from that filtered relation (`stacks.from_param!`). Every controller that inherits this method (stacks, deploys, tasks, hooks controllers, etc.) is therefore bound to the client's authorised stack.

`Shipit::Api::CCMenuController` breaks this binding by redefining `stack`: [2](#0-1) 

Here `stack` is resolved with `Stack.from_param!(params[:stack_id])` — a global, unscoped lookup — completely bypassing `current_api_client.stack_id`. The controller's only authorization gate is: [3](#0-2) 

which merely checks the client possesses the generic `read:stack` permission string via `ApiClient#check_permissions!`: [4](#0-3) 

`check_permissions!` never inspects which stack is being accessed — it only checks that the permission name `"read:stack"` is in the client's `permissions` array. The stack-level restriction is supposed to come entirely from the scoped `stacks`/`stack` helper in `BaseController`, which `CCMenuController` does not use.

Before the attacker's request: a token created for Stack A (`ApiClient.stack_id == A.id`, `permissions: ["read:stack"]`) is only supposed to authorise `stack == A`.
After the attacker's request: the same token, sent with `params[:stack_id] == B`, resolves `stack == B` because `CCMenuController#stack` ignores `current_api_client.stack_id` entirely. The binding "stack authorised by token" == "stack touched by request" is broken.

`CCMenuController` also supports authenticating via a query-string `token` parameter instead of the `Authorization` header: [5](#0-4) 

which is consistent with these being long-lived, narrowly-scoped tokens intentionally embedded in third-party CI dashboard tools (see `CCMenuUrlController`), making the scoping guarantee especially important since such tokens are commonly exposed to less trusted software.

### Impact Explanation
This allows unauthenticated-for-other-stacks read of stack state: an attacker holding (or leaking, e.g. from a CI dashboard config) a `read:stack`-scoped-to-one-stack token can query `/​:owner/:repo/:env/ccmenu.xml?token=...` for any other stack and obtain its last deploy/build status, name, and activity — data the token was never authorised to see. This matches the "High - unauthenticated read of stack state" impact category, since the cross-stack read occurs purely due to a scoping/binding defect in the controller, not through any credential compromise beyond the originally-issued narrow token.

### Likelihood Explanation
Any holder of a valid, stack-scoped API token (which by design is meant to be handed out narrowly, e.g. embedded in a CCMenu URL as shown by `CCMenuUrlController`) can trivially trigger this by changing the `stack_id`/`owner`/`repo_name` path segment of the request. No signature forgery, no privilege escalation beyond having *any* single-stack token is required.

### Recommendation
Make `Shipit::Api::CCMenuController#stack` use the same scoped lookup as `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so that a stack-scoped `ApiClient` cannot resolve stacks outside `current_api_client.stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A with `permissions: ["read:stack"]` (`stack_id = A.id`).
2. Obtain `token = api_client.authentication_token`.
3. Send `GET /:owner_b/:repo_b/:env_b/ccmenu.xml?token=<token>` where `owner_b/repo_b/env_b` identify Stack B (a different stack the client was never scoped to).
4. `CCMenuController#authenticate_api_client` succeeds via `ApiClient.authenticate(params[:token])`.
5. `require_permission :read, :stack` passes because the client's `permissions` array contains `"read:stack"` regardless of which stack is requested.
6. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` for Stack B, unfiltered by `current_api_client.stack_id`, and the response renders Stack B's CI/deploy status — data the token was not authorised to access.
