### Title
Stack-scoped ApiClient token can read any stack's deploy status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single `Stack` via `stack_id` [1](#0-0) . Every other API controller resolves the target stack through `Shipit::Api::BaseController#stack`, which filters through the `stacks` helper honoring that scope [2](#0-1) . `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, skipping the scope check entirely [3](#0-2) .

### Finding Description
The binding that should hold is: **the stack a token is authorized for == the stack the request actually touches**. `require_permission :read, :stack` on `CCMenuController` only checks that the string `"read:stack"` is present in `current_api_client.permissions` [4](#0-3)  — it never checks `current_api_client.stack_id`. The only place that scope is normally enforced is the `stacks`/`stack` helper in `BaseController` [2](#0-1) , which every other controller (`StacksController`, `TasksController`, etc.) relies on implicitly by calling `stack`/`stacks`.

`CCMenuController` redefines `stack` to bypass that helper:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

Because `Stack.from_param!` resolves against `Stack` (all stacks), not the scoped `stacks` relation, a token created with a specific `stack_id` (i.e., meant to only see one stack, as verified by the existing test "an api client scoped to a stack will only see that one stack" for `StacksController#index` [6](#0-5) ) can be replayed against `/ccmenu/*stack_id` with an arbitrary `stack_id` path segment and still pass the `read:stack` permission check, since that check is scope-agnostic.

### Impact Explanation
An attacker holding (or an integration holding) a deliberately narrow-scoped `ApiClient` token — the exact mechanism used to limit a third party's visibility to a single stack — can use the CCMenu (CCTray/CCMenu XML) endpoint to read the latest deploy/build status (`id`, `running?`, `ended_at`, name, activity, `lastBuildStatus`, `lastBuildLabel`, etc., per `app/views/shipit/ccmenu/project.*`) of **any** other stack in the Shipit instance, not just the one it was scoped to. This is an authorization-scope escalation: read access to stack state that the token issuer never intended to grant, matching the engine's "stack a token authorizes vs. stack it touches" binding.

### Likelihood Explanation
Any holder of a valid, narrowly-scoped API token (the intended low-privilege case, e.g. a CI status widget for one team's stack) can trivially exploit this by changing the `stack_id` segment of the CCMenu URL — no additional credentials, no code path outside normal request handling, and it requires only permission `read:stack` which is a very commonly granted, low-privilege permission.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped helper instead of querying `Stack` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so it inherits the same `current_api_client.stack_id` restriction enforced elsewhere in `BaseController`.

### Proof of Concept
1. Create an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id, and obtain its `authentication_token`.
2. Call `GET /ccmenu/*<Stack B's to_param>?token=<token>` where Stack B is a different, unrelated stack the client was never scoped to.
3. Observe `Shipit::Api::CCMenuController#show` renders Stack B's `deploys_and_rollbacks.last` project XML successfully (HTTP 200), because `#stack` resolves via `Stack.from_param!` rather than the scoped `stacks` relation, and `require_permission :read, :stack` only checks the permission string, not the client's stack scope.
