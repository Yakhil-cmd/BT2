### Title
Falsy-zero fallback in AA asset issue-amount calculation can bypass an asset's `cap` when the cap formula evaluates to `0` - (File: aa_composer.js)

### Summary
`aa_composer.js` computes the amount of an asset to self-issue in an AA response using a JavaScript `||` fallback: `var issue_amount = objAsset.cap || (target_amount - total_amount);` [1](#0-0)  This mirrors the reported "adjustedRectangle == 0" bug class: an intermediate value that is legitimately allowed to be `0` is tested with a falsy check instead of an explicit `undefined`/type check, so a `0` result silently falls through to a completely different (and unbounded) computation branch instead of surfacing an error.

### Finding Description
`objAsset.cap` for an asset defined by an AA can be specified either as a literal positive integer or as an oscript **formula string**, per the AA asset-definition validator: `if (typeof payload.cap === 'number') {...} else if (typeof payload.cap === 'string') { var f = getFormula(payload.cap); ... }` [2](#0-1)  Formula-based caps are evaluated dynamically per-response, so their value can depend on `trigger.data`, state vars, or balances supplied/influenced by an unprivileged AA trigger sender.

When the AA later needs to self-issue units of that asset (because it doesn't hold enough balance to satisfy a payment message), `issueAsset()` computes:
```
var issue_amount = objAsset.cap || (target_amount - total_amount);
``` [1](#0-0) 
If the cap formula evaluates to `0` (a value the code and the formula language treat as a normal, valid, falsy number — not `undefined`/`null`), the `||` operator does not use `0` as the cap. Instead it falls through to `(target_amount - total_amount)`, exactly as in the reported bug where `adjustedRectangle == 0` caused `excessSCX` to fall back to the entire `scxMinted` instead of the intended (near-zero) value. Here the fallback goes the opposite direction: instead of issuing (up to) `0` units — which should either bounce or issue nothing — the code issues however many units are needed to cover `target_amount - total_amount`, i.e., an uncapped, potentially large amount, for an asset the AA author explicitly intended to be capped.

The identical falsy-zero pattern also exists in the non-AA coin-selection path used when composing ordinary payments of an asset: `var issue_amount = objAsset.cap || (required_amount - total_amount) || 1;` [3](#0-2) 

### Impact Explanation
If an AA author defines an asset with a formula-based `cap` intended to enforce a hard issuance limit (e.g., a cap that can legitimately compute to `0` under certain trigger/state conditions, such as "no more issuance allowed this round"), the falsy check causes the engine to silently ignore the enforced cap of `0` and issue an amount derived from `target_amount - total_amount` instead. This can result in:
- Supply inflation of a capped asset beyond the author's intended limit.
- `issueAsset`'s cap-uniqueness check (`SELECT 1 FROM inputs WHERE type='issue' AND asset=?`) is only invoked for the `objAsset.cap` truthy branch [4](#0-3) ; taking the other branch instead performs a serial-number-based issuance with no "already issued" guard, compounding the inflation risk since the asset can then be issued repeatedly.

This matches the accepted "supply inflation" impact category.

### Likelihood Explanation
Likelihood is moderate/uncertain: it requires an AA author to define an asset with a `cap` as an oscript formula (an explicitly supported, documented feature) whose value can evaluate to exactly `0` in some trigger path, and for that same AA to also reach the auto-issuance branch of `sendUnit()`/`completePaymentPayload()` when it lacks a full balance of that asset. I was not able to fully trace, within the available search budget, every code path that evaluates `cap` formulas for AA-defined assets in `storage.js`/`formula/evaluation.js` to confirm the exact plumbing that turns a formula-cap into the numeric `objAsset.cap` field consumed at `aa_composer.js:1179`; this final linkage should be verified with direct file reads of `storage.js` (`loadAssetWithListOfAttestedAuthors` and cap-formula evaluation) before treating this as confirmed exploitable in production. The core anti-pattern (`x.cap || fallback` treating `0` the same as `undefined`) is nonetheless clearly present and structurally identical to the reported bug class.

### Recommendation
Replace the falsy `||` checks with explicit presence/type checks, e.g.:
```js
var issue_amount = (typeof objAsset.cap === 'number') ? objAsset.cap : (target_amount - total_amount);
```
and treat a resolved cap of `0` as "cannot issue" (bounce) rather than silently falling back to an unrelated computation, in both `aa_composer.js` (`issueAsset`) [1](#0-0)  and `inputs.js` (`issueAsset`) [3](#0-2) .

### Proof of Concept
1. An AA author defines an asset via an `asset` message with `cap` set to a formula that evaluates to `0` under a certain trigger condition, e.g. `cap: "{ trigger.data.allow_issue ? 1e6 : 0 }"` (formula-based caps are permitted per `aa_validation.js` [2](#0-1) ).
2. A trigger sender sends a trigger with `data.allow_issue = false` (or omits it), causing the evaluated `objAsset.cap` to resolve to `0` at response-composition time.
3. The AA's response includes a payment message in that asset with an output amount exceeding the AA's current balance, forcing `sendUnit()` to call `issueAsset()`.
4. At `aa_composer.js:1179`, `objAsset.cap || (target_amount - total_amount)` evaluates the falsy `0` cap as "no cap set" and issues `target_amount - total_amount` units instead of bouncing or issuing `0`, inflating the asset supply beyond the author's intended `0`-cap for that round.

(Note: full end-to-end confirmation that formula-based `cap` values reach `objAsset.cap` as a plain evaluated number in this exact code path was not completed due to search-tool limits; this should be verified against `storage.js` before remediation is prioritized.)
