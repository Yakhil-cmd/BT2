### Title
Merkle Proof Verification Allows Forged "Node-as-Leaf" Membership Proofs, Bypassing `in merkle` Authentifiers and `is_valid_merkle_proof()` Whitelist Gates - ([File: merkle.js])

### Summary
`merkle.js`'s `verifyMerkleProof()` hashes leaf elements and internal tree nodes with the exact same construction (`hash(x)` / `hash(a+b)`) and performs no domain separation or depth/index bound validation, a defect the code itself flags with the comment "Node-as-Leaf issue might matter in some cases". This is the same class of bug as the reported Rocket Pool issue: a Merkle validation routine fails to reject cryptographically well-formed but structurally invalid witnesses (here, an internal node masquerading as a leaf; there, an index/depth that shouldn't exist), letting an attacker satisfy a membership check they were never entitled to pass.

### Finding Description
`getMerkleRoot()`/`getMerkleProof()` build internal nodes as `hash(arrHashes[i] + arrHashes[hash2_index])` [1](#0-0) , while `verifyMerkleProof()` computes the leaf hash the caller supplies as simply `hash(element)` and then folds it up the tree using `proof.siblings` and `proof.index` [2](#0-1) . Because leaves and internal nodes are hashed identically (no leaf/node prefix byte), if an attacker knows any two adjacent hash values `h1`, `h2` that appear together as siblings in the real tree, they can submit `element = h1 + h2` as their "leaf". `hash(element)` will equal exactly the real internal node's hash one level up, and by pairing that with the correct sibling path for that internal node's position, `verifyMerkleProof()` reproduces the legitimate root — even though `h1+h2` was never one of the tree's actual data elements. There is no check that `proof.index`/`proof.siblings.length` correspond to a genuine leaf depth, analogous to the missing `maxDepth`/depth-multiple check in Rocket Pool's `getPollardRootIndex()`.

This routine is reachable by any unprivileged party in two places:
- The `in merkle` authentifier evaluated during unit/address-definition validation, where a unit author supplies the serialized proof as an authentifier and the code only checks `merkle.verifyMerkleProof(element, proof)` before trusting `proof.root` against an oracle-posted data feed value [3](#0-2) .
- The `is_valid_merkle_proof()` oscript function, callable from any AA trigger, which deserializes/validates only the `siblings` array shape (non-empty strings, length ≤ 50) but never validates `index` bounds or leaf/node domain separation before calling `merkle.verifyMerkleProof()` [4](#0-3) .

### Impact Explanation
`in merkle` definitions and `is_valid_merkle_proof()` are the documented mechanism for gating address spending conditions or AA payouts on membership in a large, oracle/author-committed set (whitelists, allow-lists, airdrop eligibility, etc.), with the tree root anchored via a data feed or hardcoded/state value. The node-as-leaf flaw undermines the core security guarantee of that primitive: an attacker who can observe the tree's internal hash values (trivially possible if the underlying dataset or any adjacent proofs are public, which is the normal deployment model for these whitelists) can construct a proof for a value that was never a genuine member. Where such a gate is used to authorize fund release from an AA or to satisfy an address's spending authentifier, this enables unauthorized AA fund loss / unauthorized use of the gated address.

### Likelihood Explanation
Exploitability depends on the attacker being able to derive two real sibling hashes from the committed tree, which is realistic whenever the underlying set (or any legitimate proof for another element) is publicly obtainable — the typical case for whitelist/airdrop trees meant to be provable by many independent parties. The attack requires no breaking of SHA-256 itself, only exploiting the missing leaf/internal-node domain separation, which the developers' own comment acknowledges as a known risk that was never mitigated.

### Recommendation
Add domain separation between leaf and internal node hashing (e.g., prefix leaves with `0x00` and internal nodes with `0x01` before hashing, or hash leaves with a different tag) in `getMerkleRoot()`, `getMerkleProof()`, and `verifyMerkleProof()` in `merkle.js`. Additionally, validate that `proof.index` is a non-negative integer strictly less than `2**proof.siblings.length` before use, matching the fix philosophy of rejecting witnesses whose implied depth/position cannot correspond to a real tree.

### Proof of Concept
1. Given any Merkle tree built with `merkle.getMerkleRoot(arrElements)` whose two children hashes at some level are `h1 = hash(arrElements[0])` and `h2 = hash(arrElements[1])` (attacker can compute these if `arrElements[0]`/`arrElements[1]` or their hashes are known/public, e.g. from a legitimate proof for a neighboring element).
2. Attacker crafts `forged_element = h1 + h2` and takes `forged_proof = { index: <index of that internal node one level up>, siblings: <the real siblings for that node's position>, root: <the real tree root> }`.
3. Call `merkle.verifyMerkleProof(forged_element, forged_proof)` — it returns `true`, exactly as it would for `is_valid_merkle_proof(forged_element, forged_proof)` in an AA trigger [5](#0-4)  or for the `in merkle` authentifier in `definition.js` [6](#0-5) , despite `forged_element` never being one of `arrElements`.

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
