### Title
Status webhook handler resolves commits by SHA alone, broadcasting state changes to unrelated stacks - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no scoping to the repository named in the webhook payload, unlike sibling handlers such as `PushHandler` which scope through the repository-bound `stacks` association. Because the `commits` table enforces uniqueness only on the composite `[sha, stack_id]` (not `sha` alone), the same SHA can legitimately exist as separate `Commit` rows on multiple, unrelated stacks, and a validly-signed status webhook for one repository will update and broadcast on all of them.

### Finding Description
The claimed binding is: `webhook.repository.full_name == commit.stack.repository.full_name` for every `Commit` row that gets its status updated by a given webhook. In the actual code this binding does not hold.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only verifies that the payload was signed with the secret configured for `repository_owner` (the org). It never checks that the specific `sha`/commit referenced belongs to the same repository that owns that secret. [1](#0-0) 
- `StatusHandler#process` then resolves target commits purely by SHA, globally: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — with no `stacks` scoping and no comparison against `params.dig('repository', 'full_name')`. [2](#0-1) 
- Contrast with `PushHandler#process`, which correctly scopes to `stacks.not_archived.where(branch:)` — i.e., through the repository-bound `stacks` relation exposed by the base `Handler` class — before acting. [3](#0-2) 
- The schema itself confirms SHAs are not globally unique: the unique index is `[sha, stack_id]`, not `sha` alone, meaning the same commit SHA is expected to exist independently across multiple stacks/repositories (forks, repo splits/renames, mirrored repos, monorepo migrations, multiple stacks tracking the same underlying repo). [4](#0-3) 
- Each matched `Status` create triggers `after_commit :broadcast_update` and `Status#broadcast_update` delegates to `commit.broadcast_update`, which is itself delegated further to the owning `stack`, publishing on that stack's pubsub channel — regardless of which repository's webhook actually triggered it. [5](#0-4) [6](#0-5) [7](#0-6) 

**Exploit flow**: Any repository whose org already has a Shipit-configured GitHub App/webhook secret can deliver a genuinely GitHub-signed `status` event (attacker needs push/webhook-triggering access to *some* repo under that org — e.g., their own fork if the org is configured permissively, or any repo the org's installed App covers). If a `Commit` row with the same SHA exists on a different, unrelated stack (a realistic occurrence given the schema explicitly permits it via `[sha, stack_id]`), that unrelated stack's commit gets a new `Status`, its `state`/CI status is mutated, and a `broadcast_update` fires on that victim stack's channel — all without the payload's repository ever having any relationship to the victim stack.

Existing guards do not close this gap: `verify_signature` validates org-level authenticity only, not repo-to-commit binding; `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` validate shape (`sha`, `state`, etc.) but not repository identity; there is no `Repository`-based filter anywhere in `StatusHandler`.

### Impact Explanation
A webhook genuinely signed for repository A can write a `Status` record and fire deploy-relevant callbacks (`schedule_continuous_delivery`, CI-state transitions, `enable_ci_on_stack`) against a `Commit` belonging to stack B, and broadcast that mutation to any browser watching stack B's task-stream/pubsub channel — a write against a repository/stack that never authenticated or authorized it. This matches the "payload for one repository mutating another's stack/commit" Critical category, since it is a real, code-level write across tenant boundaries, not merely an observation artifact. The broadcast itself is a visible side effect corroborating that an unauthenticated cross-tenant write occurred; it is not a separate root cause.

### Likelihood Explanation
Requires: (1) the attacker's repository is under an org for which Shipit already holds a webhook secret (i.e., not literally an arbitrary internet org, but any repo within an org Shipit trusts — commonly the case for public/monorepo orgs with many teams/stacks sharing one GitHub App installation), and (2) a SHA collision with a real target commit, which — per the `[sha, stack_id]` unique-index design — is an anticipated, not merely theoretical, occurrence (forked/mirrored repos, renamed/split repositories, multiple stacks tracking the same underlying repository). No Shipit session, API token, or additional secret is needed beyond what GitHub already signs on the attacker's own repository's behalf.

### Recommendation
Scope `StatusHandler#process` (and `refresh_statuses!`/`create_status_from_github!` callers) to commits belonging to stacks whose repository matches `params.dig('repository', 'full_name')`, mirroring the `stacks` scoping already used in `PushHandler`, instead of matching by `sha` alone.

### Proof of Concept
In `test/models/webhooks/handlers/status_handler_test.rb` (or controller-level `test/controllers/webhooks_controller_test.rb`):
```ruby
test "status webhook for repository A does not update or broadcast on stack B's commit sharing the same sha" do
  stack_a = shipit_stacks(:shipit)                      # repo A
  stack_b = shipit_stacks(:cyclimse)                     # repo B, unrelated
  shared_sha = "a" * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, message: "x", author: nil, committer: nil)
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "y", author: nil, committer: nil)

  request.headers['X-Github-Event'] = 'status'
  body = { 'sha' => shared_sha, 'state' => 'success', 'branches' => [{ 'name' => stack_a.branch }] }
           .merge(repository_params_for(stack_a)).to_json  # signed for repo A only

  assert_no_difference -> { commit_b.statuses.count } do
    Pubsubstub.expects(:publish).with { |channel, *| channel != stack_b.pusher_channel }.at_least_once
    Pubsubstub.expects(:publish).with(stack_b.pusher_channel, anything, anything).never
    post :create, body:, as: :json
  end
end
```
Assertion on both sides of the equality: `commit_b.statuses.count` before == after (currently fails, it increases), and `Pubsubstub.publish` is never invoked with `stack_b`'s channel for a webhook signed only for `stack_a`'s repository (currently fails, since `broadcast_update` fires unconditionally via `Commit#create_status_from_github!` for every matching `sha`).
