### Title
Missing Validation of P2P-Delivered `P2PStakingInfo` Arrays Enables Incorrect Reward Distribution During Fast Sync — (`datasync/downloader/queue.go`)

---

### Summary

The fast-sync queue's `DeliverStakingInfos` function contains an explicit placeholder that skips all content validation. A malicious sync peer can deliver a `P2PStakingInfo` message with crafted `CouncilStakingAmounts` values that do not match the actual on-chain staking amounts. These values are stored to the database without any array-length or value consistency check, and are subsequently consumed by the reward distribution and proposer-selection logic for pre-Kaia blocks, resulting in incorrect KAIA reward distribution.

---

Compare this with `DeliverReceipts`, which validates the receipt root against the block header, and `DeliverBodies`, which validates the transaction root. `DeliverStakingInfos` performs no equivalent check. [2](#0-1) 

**Conversion without validation — `kaiax/staking/p2p_staking_info.go`:**

`ToStakingInfo` blindly copies all four parallel arrays (`CouncilNodeAddrs`, `CouncilStakingAddrs`, `CouncilRewardAddrs`, `CouncilStakingAmounts`) into a `StakingInfo` struct without checking that their lengths are equal. [3](#0-2) 

**Unchecked index access — `kaiax/staking/staking_info.go`:**

`consolidateNodes()` iterates over `si.NodeIds` and directly indexes into `si.RewardAddrs[i]`, `si.StakingContracts[i]`, and `si.StakingAmounts[i]` without any bounds guard. [4](#0-3) 

**Storage path — `datasync/downloader/downloader.go`:**

Both the fast-sync commit path and the explicit staking-info recovery path store the peer-supplied data directly to the database:

```go
d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
``` [5](#0-4) [6](#0-5) 

**Read-back without re-validation — `kaiax/staking/impl/schema.go`:**

`ReadStakingInfo` JSON-unmarshals the stored bytes into `StakingInfoLegacy` and calls `ToStakingInfo()`, again without any array-length consistency check. [7](#0-6) 

**Downstream consumption — reward distribution:**

The stored `StakingInfo` is consumed by `assignStakingRewards` and `assignStakingRewardsFlex`, which call `si.ConsolidatedNodes()` → `consolidateNodes()`. Staking amounts drive the proportional KAIA reward split among validators. [8](#0-7) 

**Downstream consumption — proposer selection:**

`generateProposerListWeighted` also calls `collectStakingAmounts` → `si.ConsolidatedNodes()`. Staking amounts determine how many times each validator appears in the weighted proposer list. [9](#0-8) 

---

### Impact Explanation

A malicious sync peer that responds to a `StakingInfoRequestMsg` can craft a `P2PStakingInfo` where `CouncilStakingAmounts` contains inflated values for chosen validators (e.g., multiplying one validator's amount by 10×). Because `DeliverStakingInfos` performs no validation, the crafted data passes through `ToStakingInfo` and is persisted to the database. When the node subsequently processes pre-Kaia blocks (for which staking info is read from the database rather than computed from state), `assignStakingRewards` distributes KAIA according to the attacker-controlled amounts, sending more KAIA to the favoured validator's reward address and less to others. The same manipulation skews the weighted proposer list, giving the favoured validator disproportionate block-proposal opportunities and the associated block rewards.

The corrupted value is `StakingInfo.StakingAmounts[i]` for each validator `i`, which directly scales the KAIA reward allocated to `StakingInfo.RewardAddrs[i]`.

---

### Likelihood Explanation

The attacker must be the peer from which the victim node is fast-syncing (the `deliver` function rejects responses from peers with no pending request). Any registered P2P peer can become the sync peer if it is selected during peer discovery or if the operator explicitly targets it. The `SyncStakingInfo` API path is operator-triggered, but the `commitFastSyncData` path is exercised automatically during every fast sync. Nodes syncing pre-Kaia historical blocks are directly exposed.

---

### Recommendation

1. **Implement the missing validation** in `queue.DeliverStakingInfos` (the `// TODO-Kaia-Snapsync update validation logic` placeholder). At minimum, verify that `len(CouncilNodeAddrs) == len(CouncilStakingAddrs) == len(CouncilRewardAddrs) == len(CouncilStakingAmounts)` before accepting the delivery.
2. **Add a consistency check in `ToStakingInfo`** that returns an error (or nil) when array lengths are mismatched, rather than silently constructing a malformed `StakingInfo`.
3. **Add a consistency check in `ReadStakingInfo`** after JSON-unmarshal, before returning the struct to callers.
4. **Consider cross-validating staking amounts** against the block hash or a Merkle commitment supplied by the serving peer, analogous to how receipt roots are validated in `DeliverReceipts`.

### Proof of Concept

```
Attacker (malicious sync peer) crafts a StakingInfoMsg response:

P2PStakingInfo{
    BlockNum:              86400,          // a pre-Kaia staking interval block
    CouncilNodeAddrs:      [A, B, C],
    CouncilStakingAddrs:   [SA, SB, SC],
    CouncilRewardAddrs:    [RA, RB, RC],
    CouncilStakingAmounts: [50_000_000,    // A's real amount × 10
                            5_000_000,
                            5_000_000],
}

1. Victim node sends StakingInfoRequestMsg for block 86400.
2. Attacker responds with the crafted P2PStakingInfo.
3. handleStakingInfoMsg (node/cn/handler.go:1199) decodes via RLP — no content check.
4. DeliverStakingInfos (queue.go:953) validate() returns nil — no content check.
5. commitFastSyncData (downloader.go:1882) calls:
       PutStakingInfoToDB(86400, ToStakingInfo(crafted))
   → WriteStakingInfo JSON-marshals and stores the crafted amounts.
6. When the node processes block 86401 (pre-Kaia), GetStakingInfo(86401)
   reads from DB → ReadStakingInfo → ToStakingInfo (no validation).
7. assignStakingRewards calls si.ConsolidatedNodes():
       consolidateNodes() reads StakingAmounts[0] = 50_000_000 for A.
8. A's reward share = 50M / (50M+5M+5M) ≈ 83% instead of the correct 33%.
   Excess KAIA is credited to RA; RB and RC receive proportionally less.
```

func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
}
