### Title
Unhandled invariant-violation `throw Error` in TPS accounting (`getFinalTps`/`getLocalTps`) can crash node during MC stabilization, causing a persistent DoS on confirming new units - ([File: storage.js])

### Summary
`storage.js`'s `getFinalTps()` and `getLocalTps()` compute a TPS-based fee by walking parent units and comparing two independently derived counters (`count` from a parent-chain walk vs `countAll`/`count` from `assocStableUnitsByMci`). Both functions assume a strict relationship between these counters and `throw Error(...)` if it does not hold. These functions are invoked unconditionally on every MC-index stabilization (triggered by simply posting any valid unit), analogous to the Minter's `circulating_supply()` being invoked unconditionally inside the periodic `update_period()` and reverting the whole operation whenever an assumed invariant (`_flow.totalSupply() >= _ve.totalSupply()`) fails.

### Finding Description
`getFinalTps()` walks best-parent/parent chains starting at the MC unit for `mci`, counting units (`count`) while separately summing `1 + count_aa_responses` for every unit recorded in `assocStableUnitsByMci` between `last_ball_mci` and `mci` (`countAll`): [1](#0-0) 

The two invariant checks:
```
if (countAll < count) throw Error(...)
if (objUnitProps.parent_units.length === 1 && countAll !== count) throw Error(...)
```
assume that the graph-walk count can never exceed the "all units at these MCIs" count, and that for single-parent units the two counts must be exactly equal. A similar unchecked assumption exists in `getLocalTps()`: [2](#0-1) 

Both `getFinalTps` (via `getFinalTpsFee`) and `getLocalTps` are reached from `storage.updateTpsFees()`, which is called synchronously and unconditionally after every MC-index stabilization step, both in `main_chain.js`'s `stabilizeMci()`/`finish()` and in `writer.js`'s post-commit stabilization loop: [3](#0-2) [4](#0-3) 

Because MC stabilization is triggered by any single unit being posted and accepted by the DAG (an unprivileged action), if the parent-graph/AA-response bookkeeping (`count_aa_responses`, `bAA` flags, `best_parent_unit`, cache eviction from `assocStableUnits`) ever diverges from the assumed relationship for a specific DAG shape, the thrown `Error` is uncaught at these call sites and propagates out of the write/stabilization pipeline, analogous to the Minter's `circulating_supply()` reverting inside `update_period()`.

### Impact Explanation
An uncaught `Error` thrown from within `updateTpsFees`/`getFinalTps`/`getLocalTps` during MC stabilization is not defensively handled at any of the calling sites (`stabilizeMci`, `finish()` in `main_chain.js`, or the post-commit loop in `writer.js`); it will bubble up and crash the node process. Because stabilization always re-attempts advancing the MC on the next unit/joint received, if the underlying condition that triggers the mismatch persists (i.e., the same DAG state is reprocessed on restart), the node will repeatedly crash at the same MCI, unable to progress past it — a systemic denial-of-service preventing the network node from confirming new units, directly mirroring the "Minter unable to periodically emit tokens" impact in the referenced report (an assumed subtraction/comparison invariant that isn't actually guaranteed, embedded in a mandatory periodic path).

### Likelihood Explanation
The precise scenario that flips the parent-walk/`assocStableUnitsByMci` counters out of sync (e.g., discrepancies from AA response counting, best-parent selection, or removed/evicted cache entries) requires a specific, potentially attacker-craftable DAG shape (unit parent selection, AA trigger/response counts, or `max_aa_responses` mismatches) that any unprivileged unit poster can influence by choosing parents and triggering AAs. This makes the likelihood non-trivial though it depends on the exact edge case in the counting logic — the same class of risk flagged in the source report where "this situation is possible" under specific but reachable conditions.

### Recommendation
Replace the hard `throw Error(...)` invariant checks in `getFinalTps()` and `getLocalTps()` with defensive handling that does not crash the node process on a documented-but-unverified invariant violation — e.g., log a `nonfatal_error` (as already done elsewhere via `throwError()`/`eventBus.emit('nonfatal_error', ...)`) and fall back to a safe default TPS value, or explicitly wrap all callers of `updateTpsFees` in try/catch and treat unexpected mismatches as recoverable rather than fatal so that MC stabilization (and thus unit confirmation) can continue.

### Proof of Concept
Not applicable — reproducing the exact DAG shape that violates the `countAll`/`count` invariant would require constructing a specific sequence of units/AA triggers whose interaction with `count_aa_responses`/`best_parent_unit`/cache-eviction causes the two independently-computed counters in `getFinalTps`/`getLocalTps` to diverge; this needs live-network-level testing beyond static analysis, similar to how the original report required a PoC to establish the flow/ve token supply divergence.

async function stabilizeMci(mci) {
	const conn = await db.takeConnectionFromPool();
	await conn.query("BEGIN");
	const batch = kvstore.batch();
	const count_aa_triggers = await markMcIndexStable(conn, batch, mci);
	await util.promisify(batch.write.bind(batch))({ sync: true });
	await conn.query("COMMIT");
	conn.release();
	if (count_aa_triggers > 0) {
		console.log(`executing ${count_aa_triggers} AA triggers after stabilizing MCI ${mci}`);
		// every trigger takes its own db connection
		const aa_composer = require("./aa_composer.js");
		await aa_composer.handleAATriggers();
	}
	if (mci >= constants.v4UpgradeMci) {
		console.log(`updating tps fees after stabilizing MCI ${mci}`);
		// get a new connection to write tps fees
		const conn = await db.takeConnectionFromPool();
		await conn.query("BEGIN");
		await storage.updateTpsFees(conn, [mci]);
		await conn.query("COMMIT");
		conn.release();
	}
}
