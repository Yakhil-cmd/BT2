### Title
Unscoped `sha` lookup in `StatusHandler#process` lets one repository's status webhook flip CI state on commits belonging to other repositories/stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by SHA (`Commit.where(sha: params.sha)`) with no check that the commit belongs to a stack tied to the repository that authenticated the webhook. Since the `webhook_secret`/`verify_webhook_signature` check only proves the payload came from *a* repository the attacker legitimately owns, and `Commit#sha` is not unique across stacks, an attacker who can produce a commit with the same SHA as one tracked by a victim stack (e.g. via an empty/fixed-content commit, a common base commit, a merge commit, or any git history collision opportunity) can push a `status` event that also mutates the victim's `Shipit::Commit` and `Shipit::Status` rows.

### Finding Description
The broken binding is: `commit.stack.repository == verified_signature.repository_owner/repository_name` should hold for every `commit` on which `StatusHandler` acts, but the code never checks it:

```ruby
# app/models/shipit/webhooks/handlers/status_handler.rb
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Compare this to `PushHandler`, which correctly scopes to the authenticated repository via the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`): [1](#0-0) [2](#0-1) 

`StatusHandler` ignores this helper entirely and queries the global `Commit` table by `sha` only: [3](#0-2) 

`WebhooksController#verify_signature` only authenticates that the payload came from the organization named in `repository_owner`/`repository.full_name` — it does not restrict which `Commit` rows the handler is allowed to touch: [4](#0-3) 

`Commit#create_status_from_github!` then unconditionally creates a `Status` row scoped to `commit.stack_id` and re-evaluates deployability via `add_status`: [5](#0-4) [6](#0-5) 

Exploit flow: the attacker owns Repo A (any GitHub repo they control, wired to Shipit as a tracked repository/stack). They craft a commit in Repo A whose SHA collides with (or is deliberately identical to, e.g. an empty commit with fixed tree/parent/author/committer/timestamp producing the same SHA1, or simply a shared ancestor/cherry-picked commit) a commit already present in victim Stack B (Repo B), for example because both repos share history (fork, subtree, vendored branch) or because the victim stack ingested a commit whose SHA the attacker can also reproduce. The attacker then triggers (or directly POSTs) a `status` webhook for Repo A with `sha: <shared-sha>`, `context: "ci/integration"`, `state: "success"`. This webhook is signed with Repo A's legitimate GitHub webhook secret (attacker controls Repo A, so this signature check passes normally through GitHub, or the attacker can trigger it by owning Repo A and using GitHub's real delivery). `StatusHandler#process` finds **all** `Commit` rows with that `sha`, including the victim's row in Stack B, and writes a new `Status` there, changing `commit.status` for Stack B. If `ci/integration` is part of Stack B's `ci.require`, this flips `deployable?` and can enqueue `stack.schedule_merges`, enabling an unauthorized deploy/merge decision on a commit the attacker never authenticated for.

Existing guards do not catch this: `verify_signature` validates the webhook came from the org named in the payload (Repo A, which the attacker legitimately owns), not that the affected `Commit` rows belong to that org; `ExplicitParameters` only validates payload shape (`sha`, `state`, `context`, etc.), not ownership; there is no model-level uniqueness constraint on `commit.sha` scoped globally, and `Commit` scoping by `stack_id` is bypassed because the handler queries without a stack/repository filter at all.

### Impact Explanation
A payload authenticated for one repository can write a `Status` row and change `deployable?`/merge eligibility for a **different repository's stack** — this is the "payload for one repository mutating another's stack/commit" category, rated Critical. The blast radius spans any stack whose commits happen to share a SHA with an attacker-controlled repo (forks, subtrees, shared release branches, vendored code, or any git history overlap), and is repeatable for every subsequent status event the attacker sends for that SHA.

### Likelihood Explanation
Preconditions: the attacker must control (or be able to trigger webhooks from) at least one repository tracked by the Shipit instance, and must get a commit with a matching SHA into both their own history and be aware/target a specific victim's commit SHA. Genuine SHA1 preimage/collision attacks are infeasible, but the far more practical scenario is **shared history**: forks of the same upstream repo, cherry-picked/rebased commits, or merge commits frequently reused across multiple tracked repos/stacks in the same Shipit instance will produce identical SHAs recorded in multiple `Stack`s' commit tables. In that realistic scenario the attack requires no special privilege beyond normal repository push access and is trivially repeatable.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks for the authenticated repository, mirroring `PushHandler`/`Handler#stacks`:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ensures a status event can only ever mutate commits belonging to the repository that signed the webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual file may need to be created):
```ruby
test "process does not update commits belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  victim_stack.update!(ignore_ci: false)
  # simulate ci.require including 'ci/integration' via deploy_spec stub if needed

  attacker_repo = Shipit::Repository.create!(owner: 'attacker', name: 'evil-repo')
  attacker_stack = Shipit::Stack.create!(repository: attacker_repo, environment: 'production', branch: 'master')

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'victim commit')
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'attacker commit')

  before_status = victim_commit.reload.status
  before_deployable = victim_commit.deployable?

  params = { sha: shared_sha, state: 'success', context: 'ci/integration' }
  Shipit::Webhooks::Handlers::StatusHandler.call(params.merge('repository' => { 'full_name' => attacker_repo.full_name }))

  after_status = victim_commit.reload.status
  after_deployable = victim_commit.deployable?

  # THIS ASSERTS THE VULNERABILITY (should fail after fix is applied):
  refute_equal before_status, after_status, "victim commit's status group changed from an unrelated repository's webhook"
  refute_equal before_deployable, after_deployable, "victim commit's deployable? changed from an unrelated repository's webhook"
end
```
After applying the recommended fix (scoping by `stacks`), the same test should show `before_status == after_status` and `before_deployable == after_deployable`, proving the victim commit is unaffected by the attacker-authenticated webhook.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state

          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))

      end
      new_status
