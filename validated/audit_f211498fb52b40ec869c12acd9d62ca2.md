Based on my investigation, I found a strong structural analog to the reported bug class in `gh release verify-asset`.

### Title
Attestation verification bound to release-ref digest, not the actual asset digest, allows verification bypass with substituted file content - (File: pkg/cmd/release/verify-asset/verify_asset.go)

### Summary
The original report describes a bug where a state-changing operation validates one quantity (collateral locked) but the actual balance mutation is checked/applied against a different, un-decremented field, letting the attacker "double spend" using stale accounting. The structural analog in `gh` is in `gh release verify-asset`: the command selects a candidate attestation by comparing the *plain string digest* of the local file against the attestation subject, but then performs the actual cryptographic Sigstore verification against the digest of the **release ref (git commit SHA)**, not the file. The plain-string subject match is not part of what gets cryptographically checked.

### Finding Description
In `verifyAssetRun` [1](#0-0) , the code computes `fileDigest` from the actual asset on disk, but builds `releaseRefDigest` from the release's git ref SHA. Attestations are first fetched by `releaseRefDigest.DigestWithAlg()` [2](#0-1) , then narrowed with `FilterAttestationsByFileDigest`, which only performs an unauthenticated string comparison between the statement's subject digest map and the locally computed `fileDigest.Digest()` [3](#0-2) .

Critically, the final cryptographic verification call is:
```go
verified, err := config.AttVerifier.VerifyAttestation(releaseRefDigest, filteredAttestations[0])
``` [4](#0-3) 

`VerifyAttestation` builds the Sigstore policy's artifact-digest constraint from the `art` argument it receives [5](#0-4) , and `buildVerificationPolicy` binds `verify.WithArtifactDigest` from that same object [6](#0-5) . Since `releaseRefDigest` (the commit SHA) is passed here instead of `fileDigest` (the asset's own digest), Sigstore's DSSE/in-toto subject-digest enforcement — the only step that cryptographically ties the attestation to a specific digest — verifies the ref digest is present in the signed statement, **not** that the asset file's digest is cryptographically bound. The only check that ties the *asset content* to the attestation is the earlier plain, unauthenticated string comparison in `FilterAttestationsByFileDigest`, which operates on parsed-but-unverified statement JSON before Sigstore signature verification has taken place.

This mirrors the reported flaw's structure exactly: two related quantities (locked/deposited amounts vs. seized/verified amount) are supposed to move together, but only one of them is actually enforced by the authoritative check, while the other is trusted from an earlier, weaker computation.

### Impact Explanation
If an attacker can influence or supply attestation bundle data reaching `filteredAttestations[0]` (e.g. a spoofed/duplicate attestation record, or a race where multiple attestations exist with mismatched subjects for the same release), `gh release verify-asset` could report cryptographic verification success for a file whose actual bytes were never checked against the signed statement's subject digest by Sigstore itself — only against an unauthenticated, pre-verification string comparison. This can lead a user or CI pipeline to trust a tampered asset as "verified", undermining the entire purpose of the command (supply-chain integrity assurance).

### Likelihood Explanation
Reaching this code path requires no special privilege — it's the default flow of `gh release verify-asset <tag> <file>` [7](#0-6) . Any attacker able to get GitHub to record multiple/crafted attestations tied to a release ref (or exploit collisions in the pre-filter), or any bug/version skew in `FilterAttestationsByFileDigest`'s manual JSON parsing, would bypass the intended per-file cryptographic binding while the command still prints "Verification succeeded!".

### Recommendation
Pass `fileDigest` (the actual asset's `DigestedArtifact`), not `releaseRefDigest`, into `config.AttVerifier.VerifyAttestation` so that Sigstore's `WithArtifactDigest` policy check cryptographically enforces that the signed statement's subject matches the asset that was hashed on disk. If verification against the release ref is also required, both checks should be performed and both must be authoritative (cryptographically enforced), not one string-compared pre-filter and a different authoritative check.

### Proof of Concept
Conceptual PoC (cannot be fully executed without live GitHub attestation infrastructure, so this is reasoned rather than run):
1. An attacker with the ability to publish additional attestations for a release (or exploiting any bug that lets a mismatched attestation reach `filteredAttestations`) crafts/obtains an attestation whose signed subject digest matches the release ref SHA, and a `statement.predicate` field that includes a `sha256` digest matching a malicious file's hash they wish to get "verified."
2. `FilterAttestationsByFileDigest` performs a plain string match on the attacker-influenced subject map without any cryptographic check yet, and includes the attestation in `filteredAttestations` [3](#0-2) .
3. `VerifyAttestation` is invoked with `releaseRefDigest`, so Sigstore only cryptographically validates that the attestation's subject contains the release ref SHA — which it does, since that's a legitimate GitHub-issued attestation for the release — never validating the local file's digest cryptographically [4](#0-3) .
4. `gh release verify-asset` prints `✓ Verification succeeded!` for the malicious local file.

**Note**: I was unable to fully trace whether GitHub's attestation issuance backend structurally prevents multiple attestations with divergent subject digests from being associated with the same release (which would be an out-of-scope, server-side mitigating control not visible in this client repo). This uncertainty affects the practical exploitability but not the description of the root-cause logic flaw in the client-side verification code itself.

func verifyAssetRun(config *VerifyAssetConfig) error {
	ctx := context.Background()
	opts := config.Opts

			return err
		}
		tagName = release.TagName

	fileName := getFileName(opts.AssetFilePath)

func (v *AttestationVerifier) VerifyAttestation(art *artifact.DigestedArtifact, att *api.Attestation) (*verification.AttestationProcessingResult, error) {
	td, err := v.AttClient.GetTrustDomain()
	if err != nil {
		return nil, err
	}

	verifier, err := verification.NewLiveSigstoreVerifier(verification.SigstoreConfig{
		ExternalHttpClient: v.ExternalHttpClient,
		Logger:             att_io.NewHandler(v.IO),
		NoPublicGood:       true,
		TrustDomain:        td,
		TrustedRoot:        v.TrustedRoot,
	})
	if err != nil {
		return nil, err
	}

	policy := buildVerificationPolicy(*art, td)
	sigstoreVerified, err := verifier.Verify([]*api.Attestation{att}, policy)
	if err != nil {
		return nil, err
	}

	return sigstoreVerified[0], nil
}

func FilterAttestationsByFileDigest(attestations []*api.Attestation, fileDigest string) ([]*api.Attestation, error) {
	var filtered []*api.Attestation
	for _, att := range attestations {
		statement := att.Bundle.Bundle.GetDsseEnvelope().Payload
		var statementData v1.Statement
		err := protojson.Unmarshal([]byte(statement), &statementData)

		if err != nil {
			return nil, fmt.Errorf("failed to unmarshal statement: %w", err)
		}
		subjects := statementData.Subject
		for _, subject := range subjects {
			digestMap := subject.GetDigest()
			alg := "sha256"

			digest := digestMap[alg]
			if digest == fileDigest {
				filtered = append(filtered, att)
			}
		}

	}
	return filtered, nil
}

// buildVerificationPolicy constructs a verification policy for GitHub releases
func buildVerificationPolicy(a artifact.DigestedArtifact, trustDomain string) verify.PolicyBuilder {
	// If no trust domain is specified, default to "dotcom"
	if trustDomain == "" {
		trustDomain = "dotcom"
	}
	// SAN must match the GitHub releases domain. No issuer extension (match anything)
	sanMatcher, _ := verify.NewSANMatcher("", fmt.Sprintf("^https://%s\\.releases\\.github\\.com$", trustDomain))
	issuerMatcher, _ := verify.NewIssuerMatcher("", ".*")
	certId, _ := verify.NewCertificateIdentity(sanMatcher, issuerMatcher, certificate.Extensions{})

	artifactDigestPolicyOption, _ := verification.BuildDigestPolicyOption(a)
	return verify.NewPolicy(artifactDigestPolicyOption, verify.WithCertificateIdentity(certId))
}
