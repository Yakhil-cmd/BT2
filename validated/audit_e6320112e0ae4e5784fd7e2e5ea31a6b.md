### Title
Vote weight in `countVotes()` is computed from the voter's **current** balance instead of a balance snapshot taken at vote time, allowing coordinated balance shifts to swing OP-list elections and system-parameter votes - ([File: main_chain.js])

### Summary
The RAAC report describes a governance bug where quorum is recomputed dynamically from *current* total voting power rather than a value fixed at proposal creation, letting colluding holders withdraw stake mid-vote to shrink the quorum and pass a proposal with minority support. The same structural flaw — using a **live, re-computable balance** instead of a **snapshot taken at commitment time** — exists in ocore's on-chain system-voting mechanism (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`), which is the DAG's analog to "governance parameters."

### Finding Description
Any unit author can cast a `system_vote` message (subject/value pair) and, separately, trigger a `system_vote_count` message that schedules `countVotes()` to run for that subject at the end of processing the current MCI: [1](#0-0) 

`countVotes()` collects **all addresses that have ever cast a vote for the subject** and re-weights each vote by that address's balance **at the moment the count executes** (i.e., current stable-good, unspent balance), not the balance the address held when it voted: [2](#0-1) 

This freshly-read balance is then used directly to:
- Select the winning `op_list` (top `COUNT_WITNESSES` addresses ranked by `SUM(balance)`): [3](#0-2) 
- Compute the weighted median for numeric system parameters such as `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`: [4](#0-3) 

There is also a rolling look-back window (`since_timestamp`) meant to ensure a minimum share of the fixed constant `TOTAL_WHITEBYTES` has participated, but this only decides *how far back* to include voters — it does nothing to protect against balance manipulation at count time: [5](#0-4) [6](#0-5) 

Because the balance used for weighting is read live rather than locked/snapshotted when the vote was cast, a coordinated group can:
1. Cast `system_vote` messages from several addresses supporting a desired outcome (op-list slate, or a favorable `threshold_size`/`tps` value) while holding minimal balance.
2. Just before/at the MCI where `system_vote_count` triggers the tally, transfer large sums of `base` asset into these already-voted addresses (a purely internal transfer among colluding parties, at effectively zero net cost since the funds are only transiently held).
3. Let `countVotes()` sum the inflated balances, causing the attacker-favored value/op-slate to win the weighted median or top-`COUNT_WITNESSES` ranking.
4. Move the funds back out immediately afterward — the "stake" behind the winning vote was never held for any meaningful duration and does not represent real economic support.

This mirrors the RAAC bug exactly in structure: a protocol-level decision (quorum / winning proposal there; OP list / system parameter there vs. here) is decided using a value (voting power / balance) that is recomputed dynamically at decision time from mutable, attacker-controlled state, rather than fixed at the moment of commitment (proposal creation / vote casting).

### Impact Explanation
- **Node disagreement / consensus risk on system parameters**: `op_list` determines the order providers (witnesses) that every node uses for main-chain stability; `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier` are consensus-critical fee/throughput parameters read by every full node (`storage.systemVars`). Manipulating any of these via transient balance inflation can push the network toward an OP set or fee parameters that do not reflect genuine long-term stakeholder consensus, undermining trust in main-chain stability and fee-based DoS protection (`base_tps_fee`).
- Because `countVotes` runs deterministically as part of `markMcIndexStable`, all nodes compute the same (manipulated) result, so this is not merely griefing a single node — it produces a network-wide, protocol-accepted but illegitimate parameter/OP-list change, analogous to the RAAC proposal "succeeding" without true majority support.

### Likelihood Explanation
Medium-High: the transfer of `base` currency between addresses that have already voted is a normal, unprivileged unit-posting operation available to anyone; no special role (OP, hub, node) is required. The only requirement is coordinating the timing of a `system_vote_count` trigger relative to internal balance transfers, both of which are actions any ordinary unit poster/asset holder can perform. The main constraint is having sufficient capital to transiently outweigh genuine long-term voters at the moment of tallying, similar to the "coordinated withdrawal" capital requirement in the RAAC PoC.

### Recommendation
- Snapshot each voter's balance at the time the `system_vote` message is included (stabilized), and store that balance alongside the vote in `system_votes`/`numerical_votes`, rather than re-reading current balance in `countVotes()`.
- Alternatively, require voting balance to be locked/committed (e.g., via a time-locked output) for a minimum duration before and after the vote, so momentary balance inflation cannot influence the tally.
- Consider weighting by a time-decayed or time-averaged balance over the full lookback window instead of a point-in-time balance read at count time.

### Proof of Concept
Conceptual PoC on ocore:
1. Addresses A and B (colluding) each hold minimal balance; both send `system_vote` units voting `threshold_size = X` (attacker-favored value) and are included and stabilized normally — see validation path in `validation.js` case `"system_vote"` (`threshold_size` subject) at: [7](#0-6) 
2. Shortly before the MCI that will host a `system_vote_count` message (any address can post one to trigger `countVotes()` for the subject at `main_chain.js:1575-1578`), address C sends a large `base` payment to A and B.
3. When the vote-count MCI stabilizes, `countVotes()` reads A's and B's **current** balances (now inflated) via the `bal_rows` query at `main_chain.js:1757-1773`, sums them into `total_balance` for value `X`, and the weighted-median logic at `main_chain.js:1893-1902` selects `X` as the new `threshold_size` even though A/B never held that capital during any meaningful voting period.
4. A/B/C move the funds back afterward with no lasting economic commitment, having swung a consensus-critical system parameter.

This cannot be fully verified against the entire `validation.js` handling of the `"system_vote_count"` app (only partial context was retrieved), so it is not confirmed whether additional restrictions exist there; however, the core weighting logic in `countVotes()` in `main_chain.js`, which is the decisive computation, unambiguously uses live balances rather than vote-time snapshots.
