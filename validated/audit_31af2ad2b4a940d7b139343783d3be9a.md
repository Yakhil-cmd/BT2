### Title
CCMenu API leaks build status of any stack regardless of the ApiClient's stack scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#show` authorizes the request against a generic `read:stack` permission but resolves the target stack from `Stack.from_param!(params[:stack_id])` directly, instead of going through the stack-scoped lookup that every other API controller uses. This breaks the equality that should hold between "the stack a token authorizes" and "the stack the token can touch."

### Finding Description
`Api::BaseController` establishes a binding between an `ApiClient` and the stack(s) it may act on: `stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a stack, and `stack` resolves `stacks.from_param!(params[:stack_id])` on top of that restricted relation. [1](#0-0) 

`Api::StacksController` (and other resource controllers) rely on this scoped `stack`/`stacks` helper, so a token created with a `stack_id` (e.g. the CCMenu token minted by `CCMenuUrlController`) can only resolve to the stack it was issued for. [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
It only enforces `require_permission :read, :stack`, which is `ApiClient#check_permissions!` checking the client's `permissions` array for `"read:stack"` — it never checks `current_api_client.stack_id` against the requested `params[:stack_id]`. [3](#0-2) [4](#0-3) 

Before the request: token T is scoped to stack A (`ApiClient#stack_id == A.id`), permission `read:stack` present.
After the request: an attacker holding T can request `GET /api/A/... /ccmenu.xml?stack_id=B&token=T` for any stack B, and `CCMenuController#stack` resolves `Stack.from_param!(B)` unconditionally, returning deploy/build status data for stack B even though T was never authorized for B. The binding "stack a token authorizes == stack a token can touch" is broken; the check only verifies "does this token have the `read:stack` permission at all," not "for this stack."

This mirrors the reported bug class: the code validates one dimension of the input (has-permission) but omits the corresponding bound (for-this-scope), silently accepting an out-of-scope value that ends up being fully acted upon (rendering another stack's CI/deploy state).

### Impact Explanation
This yields unauthenticated read of stack state across stack boundaries using a token that is supposed to be scoped to a single stack — matching the "High: unauthenticated read of stack state, task streams or deploy output" impact category. The leaked payload (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, lock state) can reveal deploy failures, lock reasons/authors, and build metadata for private stacks the token holder has no legitimate access to.

### Likelihood Explanation
Likelihood is moderate to high: exploitation requires only possession of any valid CCMenu token (which is deliberately handed out per-stack via `CCMenuUrlController#fetch` to any authenticated user who can view a stack's CCMenu URL) and knowledge/guessing of another stack's `to_param` (owner/repo/environment or numeric id), which is not a secret. No privileged credentials beyond a single low-privilege scoped token are needed.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped lookup used elsewhere in the API, e.g. `stacks.from_param!(params[:stack_id])` (inherited from `BaseController`), so that a stack-scoped `ApiClient` can only ever resolve to its own stack, consistent with `StacksController` and other resource controllers.

### Proof of Concept
1. As a legitimate user, request a CCMenu URL for stack A via `GET /stacks/:A/ccmenu_url` — this mints (or reuses) an `ApiClient` with `permissions: ["read:stack"]` and `stack_id: A.id`, returning a token T.
2. Using T, call the CCMenu API endpoint for a different stack B: `GET /api/stacks/B/ccmenu.xml?token=T` (or with `stack_id: B` in query/path per routing).
3. `authenticate_api_client` resolves `@current_api_client` to the token's `ApiClient` (scoped to A), and `require_permission :read, :stack` passes because the client's `permissions` includes `read:stack` (no stack-id comparison performed).
4. `show` calls `stack` → `Stack.from_param!(params[:stack_id])`, which looks up stack B directly, bypassing the `stacks` scoping relation that would have restricted results to stack A only.
5. The controller renders `shipit/ccmenu/project` XML with stack B's `lastBuildStatus`, `lastBuildLabel`, `activity`, and lock information, disclosing state for a stack the token was never authorized for.
