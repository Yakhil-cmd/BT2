### Title

RAY total-value overflow during accrual permanently freezes a saturated market - (File: common/src/rates/simulate.rs)

### Summary

An unprivileged user can leave a market with extremely large scaled supply and debt balances, then let ordinary index growth push `scaled_total × index` above the `i128` RAY-value domain. The next permissionless `controller::update_indexes` call panics inside accrual, and because repayment, withdrawal, liquidation, and other market actions synchronize the market before mutating it, those actions subsequently revert indefinitely.

### Finding Description

`controller::update_indexes(caller, assets)` is callable by any address and forwards each selected `HubAssetKey` to the pool's accrual path. [1](#0-0) [2](#0-1) 

Every pool operation that touches an existing market loads a `Cache` and runs `interest::global_sync` before applying the operation. [3](#0-2) 

`accrue_step` first converts the entire scaled borrowed and supplied balances to their current values with `scaled_to_original`. [4](#0-3)  `scaled_to_original` directly multiplies the scaled RAY total by the index. [5](#0-4) 

The borrow index is capped only after calculating its next value, so the cap does not prevent the current market value from exceeding `i128::MAX` before that ceiling is reached. [6](#0-5) 

When either `borrowed × borrow_index` or `supplied × supply_index` exceeds the representable RAY-value range, accrual reverts before `last_timestamp` advances. Every later call retries the same overflowing conversion, so there is no in-contract way to repay debt, withdraw collateral, liquidate the account, or otherwise reduce the oversized total.

The repository already contains a deterministic reproduction: a 1-billion-token, 18-decimal market at 98% utilization eventually makes `update_indexes` fail with `MathOverflow`, while the borrow index remains below `MAX_BORROW_INDEX_RAY`. [7](#0-6) [8](#0-7) [9](#0-8) 

### Impact Explanation

This is a permanent freezing-of-funds condition for all users of the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot process positions touching the market, and revenue or recapitalization paths that synchronize the same market also fail. The pool retains the token balance, but its accounting can no longer be advanced without a code change or migration.

The repository's regression test explicitly demonstrates that both a withdrawal and a repayment fail with `MathOverflow` after the accrual overflow. [10](#0-9) 

### Likelihood Explanation

The attack requires either a market already near the numeric boundary or enough admitted liquidity to push it there, plus live debt so interest keeps increasing the index. That is a significant economic prerequisite, which lowers the likelihood compared with a small crafted input.

However, no privileged call is needed at the trigger point: any user can invoke `controller::update_indexes` once ledger time has elapsed. The failing condition is reached through ordinary `supply` and `borrow` calls under an admitted market configuration, and the deterministic test reaches the cliff through normal protocol mechanics rather than storage corruption.

### Recommendation

Calculate market totals and utilization in a wider internal type, or make RAY-value conversion saturating where an exact `i128` result is not required. In particular, utilization can be calculated from a widened `borrowed × borrow_index / (supplied × supply_index)` without first forcing either total into `i128`.

Index ceilings should also be enforced relative to the current scaled totals: the largest stored index must keep both `borrowed × index / RAY` and `supplied × index / RAY` representable. If exact debt exceeds the asset domain, clamp the index and expose the saturation explicitly rather than allowing every market operation to revert before reducing the position.

Add a boundary regression for the first accrual that would overflow and verify `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, `recapitalize`, and `update_indexes` remain executable afterward.

### Proof of Concept

1. In a listed 18-decimal market with an admitted cap above 1 billion whole tokens and a steep high-utilization rate curve, an attacker supplies:

   ```text
   supply(
       caller = attacker,
       account_id = 0,
       spoke_id = S,
       assets = [({hub_id = H, asset = T}, 1_000_000_000 * 10^18)]
   )
   ```

   This creates 10^36 scaled supply shares. [11](#0-10) 

2. Using separately posted collateral, the attacker borrows 98% of that market:

   ```text
   borrow(
       caller = attacker,
       account_id = id,
       borrows = [({hub_id = H, asset = T}, 980_000_000 * 10^18)],
       to = None
   )
   ```

   The deterministic test uses exactly this 98% debt ratio. [12](#0-11) 

3. After sufficient ledger time, anyone calls:

   ```text
   update_indexes(
       caller = attacker_or_keeper,
       assets = [{hub_id = H, asset = T}]
   )
   ```

   The test repeatedly advances one year and calls the same index-update path until it returns `MathOverflow`. [13](#0-12) 

4. The failed call leaves the index below `MAX_BORROW_INDEX_RAY`, proving that the value-domain overflow occurs before the intended index ceiling can stop growth. [14](#0-13) 

5. Subsequent `withdraw` and `repay` calls still fail with `MathOverflow`, because they run accrual before attempting to reduce the position. [10](#0-9)
