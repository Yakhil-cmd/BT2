## Title
Ambiguous, separator-less concatenation in arbiter-contract hash allows different contract terms to collide on the same hash - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js`'s `getHashSrc()` concatenates the free-text and numeric fields of an arbiter (escrow) contract with **no separator** before hashing, exactly the bug class described in the external report (`BaseRouter._getRawData()` concatenating operations/parameters without delimiters). Because the hash is used across the wallet as the unique commitment to a specific set of contract terms (title, text, parties, amount, asset), an attacker who is one of the two contracting parties can craft two different term sets that concatenate to the identical byte string, and therefore hash identically, letting them misrepresent the agreed amount/party while still passing all hash-equality checks.

### Finding Description
`getHashSrc()` builds the string to be hashed as a plain concatenation for any contract whose `creation_date` is not after `exports.NEW_HASH_DATE`: [1](#0-0) 

```js
const src = contract.creation_date > exports.NEW_HASH_DATE
	 ? [...].join(exports.DELIMITER)
	 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
```

`exports.NEW_HASH_DATE` is set to `'2026-11-01'`, a date in the future relative to the current system date, so **every contract created today still uses the vulnerable, delimiter-less branch**: [2](#0-1) 

Because `title`, `text`, `payer_name` and `payee_name` are attacker-controlled free-text strings that sit directly adjacent to each other and to the numeric `amount` field with no separator, a contract creator can shift characters across a field boundary and still reproduce the exact same concatenated byte string and thus the same SHA-256 hash, e.g.:

- `payee_name = "Bob"`, `amount = 100` → `...Bob` + `100` + `null`
- `payee_name = "Bob10"`, `amount = 0` → `...Bob10` + `0` + `null`

Both produce the substring `"Bob100null"`, so `getHash()` returns an identical value for two contracts that a human would read as carrying different payee names and different amounts: [3](#0-2) 

This `contract.hash` is not a cosmetic identifier — it is relied on as an integrity commitment throughout the contract flow:
- it is the primary key used to store/retrieve the contract (`getByHash`, `store`),
- it is embedded as `contract_text_hash` in the on-chain `data` message that accompanies the multisig payment unit, and the receiving peer's code trusts a literal equality check against this hash to accept the signed unit as matching the agreed contract: [4](#0-3) 
- it is used to derive the `CONTRACT_<hash>` / `CONTRACT_DONE_<hash>` data-feed keys baked into the shared address definition that actually controls fund release conditions: [5](#0-4) 
- it is sent, together with the human-readable fields, to the arbiter/arbstore when a dispute is opened or appealed: [6](#0-5) 

Since none of these consumers re-derive or bound-check the individual fields against an unambiguous encoding, whichever party controls contract creation can present one interpretation of the terms to the counterparty/cosigner/arbiter while a colliding, differently-parsed interpretation (different amount or payee) hashes identically.

### Impact Explanation
This breaks the integrity guarantee that `contract.hash` uniquely commits to a specific set of escrow terms (parties, amount, asset). A malicious contracting party (an ordinary wallet user acting as counterparty in the arbiter/escrow flow — no special privilege required) can exploit the collision to make dispute data, cosigner confirmations, or peer-side hash checks pass for terms other than what they display, undermining the arbitration/escrow trust model and creating a path to fund loss/misdirection for the counterparty relying on the hash to represent an agreed amount. This matches the "private-payment counterparty" actor class explicitly in scope, and the consequence (fund loss / disputed fund release under fabricated terms) is a concrete Medium-severity issue in the arbiter contract subsystem.

### Likelihood Explanation
Exploitation only requires being one of the two parties in an arbiter/escrow contract (a normal, unprivileged wallet capability) and knowing basic string arithmetic to construct a colliding field split — no cryptographic break, no privileged network position, and no dependency on any other actor's misbehavior. The vulnerable code path is active for essentially all contracts created before `2026-11-01`, i.e., currently all contracts, since the delimiter fix has not yet taken effect.

### Recommendation
Always hash contract terms using a length-prefixed or delimiter-separated (and 0x00-escaped, similar to `string_utils.getSourceString`) encoding, regardless of `creation_date`. Retire the `creation_date`-gated legacy branch, or immediately hard-cut `NEW_HASH_DATE` to the past so the delimiter-based (`exports.DELIMITER`) hashing is used for all contracts, and additionally validate that none of `title`/`text`/`party names` contain the chosen delimiter (as `string_utils.js` already does for its `STRING_JOIN_CHAR`).

### Proof of Concept
```js
const arbiter_contract = require('./arbiter_contract.js');

const base = {
  title: 't', text: 'x', creation_date: '2025-01-01 00:00:00',
  me_is_payer: true, my_party_name: 'Alice', peer_party_name: 'Bob',
  my_address: 'A'.repeat(32), peer_address: 'P'.repeat(32),
  arbiter_address: 'R'.repeat(32),
  amount: 100, asset: null
};
const collide = { ...base, peer_party_name: 'Bob10', amount: 0 };

console.log(arbiter_contract.getHashSrc(base));
console.log(arbiter_contract.getHashSrc(collide));
// both produce the same substring "...Bob100null", hence identical SHA-256 hash,
// despite representing different payee names / amounts (100 vs 0).
```

```javascript
function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
```
