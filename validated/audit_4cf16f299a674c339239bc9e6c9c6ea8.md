`provision?` operator precedence bypasses `review_stacks_enabled` opt-out for label-based provisioning behaviors - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`PullRequest::OpenedHandler#provision?` uses Ruby `&&`/`||` operator precedence such that `repository.review_stacks_enabled` only gates the `provisioning_behavior_allow_all?` clause, not the `provisioning_behavior_allow_with_label?` or `provisioning_behavior_prevent_with_label?` clauses. As a result, a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` will still create and queue a review stack for any opened PR that lacks the provisioning label.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == true` should gate **all** provisioning paths (`enabled` is meant to be a master opt-out switch). The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to `&&` binding tighter than `||` in Ruby, this parses as:

```ruby
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```

So `review_stacks_enabled` is only checked in the first disjunct. If the repository's `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, the result of `provision?` is completely independent of `review_stacks_enabled`.

Call path: webhook `POST /webhooks` with a `pull_request` `opened` event → `OpenedHandler#process` → `respond_to_pull_request_opened?` (`params.action == "opened" && provision?`) → `provision?` returns true even with `review_stacks_enabled: false` → `ReviewStackAdapter#find_or_create!` → `create!` → `scope.create!(stack_attributes)` with `branch: params.pull_request.head.ref` and `Shipit::ReviewStackProvisioningQueue.add(stack)`, per [2](#0-1) , [3](#0-2) .

No existing guard rejects this: `respond_to_pull_request_opened?` only checks `params.action`, and there's no separate `review_stacks_enabled` check upstream of `provision?` for `OpenedHandler` (unlike `LabeledHandler`/`UnlabeledHandler`, which do check `repository.review_stacks_enabled` directly in `respond_to_label_change?`, per [4](#0-3) ). Repository lookup is by `full_name` from the webhook payload and does not require any secret to trigger, so any attacker who owns/controls a repo that Shipit already tracks (i.e., is registered as a `Shipit::Repository`) can open a PR against it and set this behavior into motion; webhook signature verification and payload schema validation are orthogonal and do not check this business-logic condition.

### Impact Explanation
An attacker who can open a pull request against a Shipit-tracked repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (or `allow_with_label`) can force creation of a `Shipit::ReviewStack` and queue it for provisioning, bypassing the repository owner's explicit opt-out of review-stack automation. This is a record written (a stack created and queued) for a repository whose administrator explicitly disabled that feature — a control bypass, though scoped to a single repository's own review-stack feature (not cross-tenant mutation of another repository's stacks). This matches the "unauthorized... deploy" adjacent category insofar as it queues provisioning work (which can run deploy/build commands) against operator intent, but does not itself grant cross-repository or cross-tenant access, credential exfiltration, or arbitrary command execution beyond what the repository's own configured provisioning pipeline would do.

### Likelihood Explanation
Preconditions: the target repository must already be onboarded into Shipit (`Shipit::Repository` record exists) with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` — this is a deliberate, plausible admin configuration meant to disable review stacks while retaining behavior settings. Attacker cost is trivial: open a PR (label-omitted, for `prevent_with_label`) and no privileged token, secret, or Shipit account is required beyond the ability to open a PR against the tracked repo. Fully repeatable per PR opened.

### Recommendation
Add explicit parentheses to `provision?` so `review_stacks_enabled` gates every clause, e.g.:

```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:

```ruby

  configure_provisioning_behavior(
    repository:,

    behavior: :prevent_with_label,

  )
```

With the current code, this assertion fails: `Shipit::Stack.count` increases by 1 because `provision?` evaluates to `true` regardless of `review_stacks_enabled == false`, demonstrating the broken binding.
