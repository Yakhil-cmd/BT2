### Title
Unsigned/unauthenticated `membership` webhook lets any org without a `webhook_secret` be granted arbitrary `Shipit.github_teams` membership - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for an organization, with no dependency on signature algorithm at all. Combined with `Shipit::WebhooksController#verify_signature`, this means any attacker can POST a forged `membership` event with `action: "added"` for such an organization, and `MembershipHandler` will create/find the referenced `Team` and `User` and add the membership row, directly affecting what `User#authorized?` evaluates.

### Finding Description
The claimed broken binding is: *a `membership` webhook should only mutate team membership for a repository/organization that cryptographically authenticated the payload with its `webhook_secret`*, i.e. `verified == (HMAC-SHA1(webhook_secret, raw_body) == signature)`.

Tracing the code:
- `Shipit::WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` from attacker-controlled `params.dig('organization', 'login')` or `params.dig('repository', 'owner', 'login')` [1](#0-0)  and then calls `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)`.
- `GitHubApp#verify_webhook_signature` is: `return true unless webhook_secret` — i.e., if the organization config has **no** `webhook_secret` set, verification is bypassed entirely, with no signature, HMAC, or algorithm check performed at all [2](#0-1) .
- For organizations that *do* have a secret, the code additionally restricts verification to the legacy `sha1` algorithm (`return false unless algorithm == 'sha1'`), ignoring `X-Hub-Signature-256` [3](#0-2) , but this branch is irrelevant once `webhook_secret` is absent — the `return true unless webhook_secret` short-circuit fires first.
- Once `verified` is true (or unconditionally true for a no-secret org), `WebhooksController#create` dispatches the raw JSON to `Shipit::Webhooks.for_event(event)` handlers [4](#0-3) .
- `MembershipHandler#process` unconditionally trusts `params.team.id`, `params.organization.login`, and `params.member.login` from the forged body to find-or-create a `Team` and a `User`, and then calls `team.add_member(member)` for `action == 'added'` [5](#0-4) .
- `Team#add_member` appends the member to `members` (backed by the `memberships` join table) with no additional authorization check [6](#0-5) .
- `User#authorized?` is exactly the security-relevant consumer of that membership: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) . If the forged `params.team.id` corresponds to (or is made to correspond to, by `find_or_create_team!` creating a new `Team` row with an attacker-chosen `github_id`) a team that is configured in `Shipit.github_teams`, the attacker-named `User` (created purely from `params.member.login`, with no GitHub-side validation) becomes `authorized?` in Shipit.

No existing guard intercepts this: `drop_unhandled_event` only checks that a handler exists for the event type, not that the payload is genuine [8](#0-7) ; the `ExplicitParameters` schema in `MembershipHandler` validates shape, not authenticity; and `verify_signature`'s only substantive check (the HMAC) is skipped entirely for organizations without a configured `webhook_secret`.

### Impact Explanation
For any Shipit organization/host configuration where `webhook_secret` is not set, an unauthenticated, unprivileged attacker can:
1. Create arbitrary `Team` rows with attacker-chosen `github_id`/`organization`/`slug` via `find_or_create_team!`.
2. Create arbitrary `User` rows via `User.find_or_create_by_login!(params.member.login)` (note this also triggers `Shipit.github.api.user(login)` — an outbound call, but the local `Team`/`Membership` rows are written regardless of that call's outcome for pre-existing users, and the membership join happens in-process).
3. Insert a `Membership` row linking that user to that team.

If the targeted/created team's `github_id` matches an ID in `Shipit.github_teams` (the operator-configured authorization list), the attacker has just made an arbitrary Shipit user "authorized" per `User#authorized?`, which is the exact permission check gating privileged UI/actions across the app. This is an authentication/authorization-bypass class impact (a webhook forged without any valid secret is accepted as trusted and mutates team-authorization state used elsewhere), matching the Critical impact category of "forged webhook accepted as trusted" leading to authorization bypass. This is repeatable against any org lacking a `webhook_secret`, and each request produces persistent database state (unlike a resource-exhaustion or transient effect).

### Likelihood Explanation
Preconditions: the target organization's GitHub App/webhook config in Shipit must have no `webhook_secret` set (a realistic and common Shipit deployment/config state — this is a first-class supported configuration branch in `GitHubApp#verify_webhook_signature`, not a misconfiguration edge case introduced by the attacker). No GitHub App private key, no `secret_key_base`, no session, and no repository-maintainer role are required. The attacker needs only network access to `POST /webhooks` with a crafted JSON body and the `X-Github-Event: membership` header; the `X-Hub-Signature` header is not even inspected on this path since `verify_webhook_signature` short-circuits before reaching signature parsing. Cost is a single unauthenticated HTTP request, fully repeatable and scriptable.

### Recommendation
- Never accept a webhook payload for an organization/repository without a configured, provisioned `webhook_secret`; treat a missing secret as "reject the event" (`return false`), not "trust unconditionally."
- Support and require `X-Hub-Signature-256` (SHA-256) verification, removing or hardening the SHA-1-only acceptance path.
- Ensure `verify_signature` runs before any handler dispatch for every event type with no bypass branch tied to configuration.

### Proof of Concept
Minitest plan (illustrative — actual test would live under `test/controllers/webhooks_controller_test.rb` and `test/models/shipit/webhooks/handlers/membership_handler_test.rb`, both out of scope to write here but describing the exact assertions requested):

1. Configure `Shipit.github_teams` to include a team with `github_id: 999`.
2. Configure (or use the default/unstubbed) organization `"acme"` in `Shipit.github(organization: "acme")` such that `@webhook_secret` is `nil`/blank.
3. Assert precondition: `Shipit.github(organization: "acme").send(:webhook_secret)` is blank, and `Shipit.github(organization: "acme").verify_webhook_signature("sha1=deadbeef", "{}")` returns `true` (any signature, even garbage, passes) — this is the broken binding: `verified == true` regardless of `HMAC-SHA1(webhook_secret, raw_body) == signature` because `webhook_secret` is absent.
4. `POST /webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature: "sha1=0000000000000000000000000000000000000000"`, and JSON body:
   ```json
   {
     "action": "added",
     "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/999" },
     "organization": { "login": "acme" },
     "member": { "login": "attacker" }
   }
   ```
5. Assert response is `200 OK` (not `422`).
6. Assert `Shipit::Team.find_by(github_id: 999)` exists and `Shipit::User.find_by(login: "attacker").teams.exists?(github_id: 999)` is `true`.
7. Assert `Shipit::User.find_by(login: "attacker").authorized?` is `true`, proving the forged, unsigned webhook granted authorization equivalent to a legitimate GitHub team-membership event.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
