### Title
`InitializeWithPermission` allows unauthorized attribution of pool authorship / creator-fee rights via an unchecked `creator` account - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` accepts a `creator` account that is only `UncheckedAccount<'info>` — it is not required to sign, and it is never checked against the authorized `payer`/`permission` PDA. The value passed in this slot is written directly into `PoolState.pool_creator`, which is the privileged field used everywhere in the program to gate `collect_creator_fee`. This mirrors the Craft CMS mass-assignment bug class: a caller with limited permission ("create pool") can inject an arbitrary identity into a privileged authorship field that the backend never validates belongs to them or was authorized by them.

### Finding Description
In `InitializeWithPermission`, `payer: Signer<'info>` is the party whose permission is actually checked (via the `permission` PDA seeded on `payer.key()`), but `creator` is declared only as: [1](#0-0) 

with no signer requirement, no `constraint = creator.key() == payer.key()`, and no relation to the `permission` account: [2](#0-1) 

The raw, attacker-supplied `creator` pubkey is then written straight into `PoolState.pool_creator` at pool initialization: [3](#0-2) 

`PoolState.pool_creator` is the sole authorization field that later gates who may pull accumulated creator fees out of the pool via `collect_creator_fee`: [4](#0-3) 

and it is also the recipient identity used by the permissionless variant, `collect_creator_fee_permissionless`, which creates an ATA for whatever `creator` address is on record and forwards the accumulated fees there regardless of who calls it: [5](#0-4) 

Contrast this with the plain (non-permissioned) `Initialize` instruction, where `creator` is correctly a `Signer<'info>` and thus cannot be spoofed: [6](#0-5) 

So the permissioned path (`initialize_with_permission`) uniquely drops the requirement that the entity credited as "pool creator" actually be the one authorizing the transaction — exactly the pattern in the CraftCMS advisory where an unvalidated `authorId`-style field is trusted from the request body instead of being derived from the authenticated actor.

### Impact Explanation
Because `creator` need not sign and need not equal `payer`, any account permitted to call `initialize_with_permission` (i.e., anyone holding a valid `Permission` PDA as `payer`) can set `pool_creator` to:
- An address they don't control (including a random/unowned pubkey), permanently locking all future accumulated `creator_fees_token_0`/`creator_fees_token_1` for that pool, since only `pool_creator` (or a permissionless caller sending funds to `pool_creator`'s ATA) can ever release them — this is an unrecoverable freeze of pool fee-ledger funds.
- Someone else's known address (e.g., a partner, competitor, or even a program-recognized address) without that party's consent, spoofing authorship/ownership of the pool's fee stream and diverting future creator-fee revenue to an account the actual pool operator did not intend, bypassing the entire permission-gating model that `Permission`/`PERMISSION_SEED` is meant to enforce.

This is a real, on-chain, unauthorized privileged effect (misattribution and effective transfer/freezing of creator-fee rights) reachable in a single transaction with attacker-chosen accounts, matching the "unbacked accounting" / "unauthorized privileged effect" impact bar.

### Likelihood Explanation
High reachability: any account that already holds a `Permission` PDA (the intended gate for who may create permissioned pools) can trivially set an arbitrary `creator` account in the same instruction with no additional signature or constraint required. No special conditions, races, or privileged keys are needed beyond what's already required to call the instruction legitimately.

### Recommendation
Require `creator` to either be the transaction signer (`Signer<'info>`) or add an explicit constraint tying `creator` to the authorized `payer`/`permission.authority`, e.g. `constraint = creator.key() == payer.key()` or `constraint = creator.key() == permission.authority`, so that pool-creator attribution cannot be set to an arbitrary, unauthorized/unowned address.

### Proof of Concept
1. Attacker (or any account holding a valid `Permission` PDA) calls `initialize_with_permission` as `payer`, supplying their own token accounts for `payer_token_0`/`payer_token_1` and depositing initial liquidity.
2. Instead of passing their own key as `creator`, they pass an arbitrary pubkey — either an address they don't control (e.g., a freshly generated keypair with no known private key) or a third party's known wallet address, since `creator` is only `UncheckedAccount` with no signer/constraint requirement (`programs/cp-swap/src/instructions/initialize_with_permission.rs:26-27`).
3. `pool_state.initialize(...)` stores this attacker-chosen value as `PoolState.pool_creator` (`initialize_with_permission.rs:357-372`).
4. As trading occurs, `creator_fees_token_0`/`creator_fees_token_1` accumulate in `PoolState` per the fee-split logic in `swap_base_input`/`swap_base_output`.
5. Because `collect_creator_fee` requires `creator.address == pool_state.pool_creator` as a signer (`collect_creator_fee.rs:12-13`), and the recorded `pool_creator` is an address nobody controls (or a non-consenting third party), the accumulated creator fees become permanently unclaimable by the actual pool operator/payer — verifiable by observing that no legitimate signer can ever satisfy the `address = pool_state.load()?.pool_creator` constraint.
