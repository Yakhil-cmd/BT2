### Title
ERC20Transactor assumes exact transfer amount for fee-on-transfer ERC20 tokens, causing overstated XCM holdings and stuck transfers - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor`, the `TransactAsset` implementation that lets XCM move ERC20 tokens deployed on `pallet-revive`, credits/debits the XCM holding register with the *requested* `amount` whenever the underlying `IERC20::transfer` call returns `true`, without ever verifying the actual balance delta on the token contract. This reproduces the exact "fee-on-transfer underlying" bug class from the original report inside FRAME/XCM: any ERC20 that deducts a fee (or otherwise transfers less than requested) on `transfer()` will desynchronize the XCM holding register's accounting from the real token balance of the transactor's checking account, ultimately causing legitimate withdraw/deposit operations to fail.

### Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` withdraws an asset from a user by invoking the ERC20 `transfer` function to move `amount` into the pallet's `TransfersCheckingAccount`: [1](#0-0) 

It only inspects the boolean return value of `transferCall` (`is_success`); if `true`, it unconditionally creates `Erc20Credit(amount)` — i.e., it assumes the checking account received exactly `amount`, never comparing the checking account's balance before and after the call: [2](#0-1) 

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary and, on success, simply consumes the holding's `amount` from `AssetsInHolding` without reconciling it against what the beneficiary actually received: [3](#0-2) 

If the target ERC20 token deducts a fee on `transfer` (returns `true` but moves less than `amount` to the recipient — the exact scenario described in the referenced report for USDT-style tokens), the XCM holding register will believe it holds the full `amount` while the checking account's real token balance is smaller by the accumulated fees. This is the precise Polkadot/XCM analog of the reported invariant violation: "the contract wrongly assumes balances values" after a transfer of a fee-charging token.

`ERC20Transactor` is wired into a live runtime configuration, confirming reachability from a normal, unprivileged, signed XCM program (e.g. via `pallet_xcm::execute` or a local/remote transfer instruction that includes such an asset): [4](#0-3) 
(`ERC20Transactor` referenced in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`)

### Impact Explanation
Once the checking account's on-chain ERC20 balance falls below what the XCM holding register believes is backed (due to accumulated transfer fees), subsequent legitimate `deposit_asset_with_surplus` calls for that asset will call `IERC20::transfer` for an amount the checking account no longer actually has. Depending on the ERC20 implementation this either reverts (`return_value.did_revert()`) or returns `false`, both of which are already handled as `XcmError::FailedToTransactAsset`, causing the enclosing XCM program to fail and, per XCM/`AssetsInHolding` semantics, potentially trap the held assets. This can block ordinary users from completing withdraw/redeem-style XCM programs for that ERC20 asset — a direct on-chain analog of "this effectively blocks users from redeeming the underlying" from the original report. It is a value-freezing/availability issue for a specific, non-attacker-controlled asset class (fee-charging ERC20s), not a direct token-theft primitive, since no minting/over-issuance of a backed fungible asset occurs — the discrepancy exists purely inside the ERC20 transactor's private checking-account bookkeeping.

### Likelihood Explanation
This requires only that a fee-on-transfer (or otherwise non-standard, less-than-requested-amount) ERC20 token be registered/used through `ERC20Transactor` in an XCM-enabled runtime such as `asset-hub-westend`. No privileged role, governance action, or malicious peer is needed — any user submitting a normal signed XCM extrinsic referencing such a token triggers the code path. The main variable is operational: whether the deployment registers or allows arbitrary/fee-charging ERC20 contracts through this transactor (a governance/registration decision, not an attacker action), which affects likelihood but not the code-level validity of the missing check.

### Recommendation
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` should measure the checking/beneficiary account's ERC20 balance before and after the `transfer` call (similar to Compound's `doTransferIn` pattern referenced in the original report) and use the actual delta as the amount credited/debited in `AssetsInHolding`, rather than trusting the requested `amount` whenever the boolean return is `true`.

### Proof of Concept
No executable PoC was run. This is a static code-analysis finding derived from inspecting `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` and confirming its wiring into `asset-hub-westend`'s XCM configuration; I did not have the tooling in this session to deploy a fee-on-transfer ERC20 fixture on `pallet-revive` and execute a full XCM integration test to observe the resulting `FailedToTransactAsset`/holding-mismatch in practice.
