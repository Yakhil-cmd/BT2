## Title
Encrypted-transaction ciphertext-to-sender/signer binding (`Ciphertext::verify` / `AssociatedData`) is never enforced by the consensus decryption pipeline, only at the optional REST submission gate — ([File: consensus/src/pipeline/decryption_pipeline_builder.rs])

## Summary
Aptos's encrypted-mempool feature binds an encrypted payload to the transaction's sender and signer authentication keys via `PayloadAssociatedData` and `Ciphertext::verify(&associated_data)` [1](#0-0) . The comment on the underlying trait states explicitly that "Validators *must* verify each ciphertext before approving it to be decrypted, in order to prevent malleability attacks" [2](#0-1) . However, this AD/ciphertext binding check (`payload.verify(sender, signer_auth_keys)`) is only invoked in the REST API submission handler [3](#0-2) , which is a client-facing, network-bypassable gate. It is never called by the VM validator (`aptos_vm.rs::validate_transaction`), by mempool, or — critically — by the consensus decryption pipeline (`decrypt_validator_path` / `decrypt_observer_path` in `decryption_pipeline_builder.rs`) before a ciphertext is prepared and decrypted for on-chain execution.

## Finding Description
The encrypted-transaction design relies on `PayloadAssociatedData::V1 { sender, signer_auth_keys }` to cryptographically bind a ciphertext to the specific sender/signer identities that were used at encryption time [4](#0-3) . The `Ciphertext::verify` implementation checks that `associated_data_bytes` supplied matches what is embedded/committed in the ciphertext (`Id::from_verifying_key_and_ad`) and validates a signature over `(bibe_ct, associated_data_bytes)` [5](#0-4) .

The only call site that performs this binding check, `EncryptedPayload::verify(sender, signer_auth_keys)`, is invoked from the REST transaction-submission handler `api/src/transactions.rs` when a transaction with an `Encrypted` payload is submitted via the public API [3](#0-2) .

Tracing the full life cycle of an encrypted transaction on the consensus/decryption side:
- `decrypt_validator_path` partitions encrypted vs regular txns, checks batch/round/epoch-end limits, computes a digest, calls `FPTXWeighted::prepare_ct` on the raw `Ciphertext`, and later calls `do_final_decryption` [6](#0-5) [7](#0-6) [8](#0-7) .
- At no point in this path (`prepare_ct`, `do_final_decryption`, or `try_into_decrypted`) is `Ciphertext::verify`/`verify_ct` called with the transaction's actual `sender`/`signer_auth_keys` to confirm that the ciphertext was in fact bound to that sender.
- `try_into_decrypted` only checks `payload_hash == CryptoHash::hash(&plaintext)` and an optional `claimed_entry_fun` match; it never re-derives or checks `PayloadAssociatedData` against the transaction's sender/authenticator [9](#0-8) .
- The VM validator (`AptosVM::validate_transaction`) only checks whether encrypted payloads are feature-gated, not whether the ciphertext binds to the sender [10](#0-9) .

Because mempool gossip and validator-to-validator broadcast (`shared_mempool` broadcasting, quorum store, and direct consensus ingestion) do not require passing through the REST endpoint, an attacker can craft (or copy) a `SignedTransaction` whose `EncryptedInner.ciphertext` was originally bound (at encryption time) to a *different* sender/signer set, wrap it in a new `RawTransaction` with their own address as `sender`, sign it validly with their own key (the Ed25519 signature over the raw transaction only covers the opaque ciphertext bytes, not the semantic sender binding inside the ciphertext), and inject it directly into the p2p/mempool/consensus path, bypassing the REST-only `payload.verify()` gate entirely. This constitutes a pre-admission binding check that is asserted by design and by an explicit code comment ("Validators *must* verify...") but is not actually enforced at any binding admission point (mempool `validate_transaction`, VM validator, or the decryption pipeline that treats decrypted content as authoritative for execution).

## Impact Explanation
This breaks the "authenticator/binding must bind to the intended account set" admission invariant for encrypted transactions specifically: the ciphertext-to-sender/signer cryptographic binding that the protocol's own comments declare mandatory for validators is never actually checked outside of a bypassable REST gate. This allows a decrypted, previously-hidden transaction (whose content and intent were meant to be tied to one identity via `PayloadAssociatedData`) to be admitted and executed/committed under a different signer/sender pairing than the one it was cryptographically bound to at encryption time — a pre-validation mismatch that lets a transaction which should fail admission (binding check) proceed to decryption and execution. This maps to malleability/MEV-theft and identity-confusion risks in the encrypted-mempool design (front-running or hijacking another user's not-yet-revealed transaction content under attacker-controlled sender/fee-payer fields), which is High severity given it undermines a security property the code explicitly documents as mandatory ("Validators *must* verify...").

## Likelihood Explanation
Likelihood is somewhat constrained by uncertainty: I was not able to fully confirm (within available search budget) whether some other layer — e.g. mempool's admission logic before broadcasting into quorum store, or a check inside `FPTXWeighted::prepare_ct`/`decrypt` that I could not fully inspect — silently performs the missing binding validation. The grep for `verify_ct`/`.verify(&associated_data)`/`ciphertext().verify` across the repo returned matches only in benches, tests, the trait definition, and the REST handler — none in the mempool or consensus decryption code paths — which supports the conclusion that the check is genuinely absent from the admission-critical path, but this is not a 100%-exhaustive proof of absence given the constraints of static search.

## Recommendation
Enforce `EncryptedPayload::verify(sender, signer_auth_keys)` (or an equivalent ciphertext/associated-data check) as a mandatory admission-time check at every point where an encrypted transaction is accepted for propagation or decryption — specifically in `AptosVM::validate_transaction`/`vm-validator` before mempool admission, and again in `decrypt_validator_path`/`decrypt_observer_path` (or `FPTXWeighted::prepare_ct`) before a ciphertext is trusted for decryption. Reject transactions whose ciphertext does not verify against the transaction's own `sender`/`all_signer_auth_keys()`.

## Proof of Concept
Conceptual (not independently executed, given no runtime access):
1. User A submits a normal encrypted transaction via REST; `EncryptedPayload::verify(A, A_auth_keys)` succeeds and it is gossiped to the mempool (still `Encrypted`).
2. Attacker observes the gossiped `SignedTransaction` (ciphertext bytes are public before decryption) and extracts the `EncryptedInner` (ciphertext, extra_config, payload_hash, encryption_epoch).
3. Attacker builds a new `RawTransaction` with `sender = attacker`, reusing the same `EncryptedPayload::Encrypted(EncryptedInner)` from step 2, and signs it with their own private key — this signature is valid since it only covers the ciphertext bytes, not the sender binding baked into the ciphertext's `Id`.
4. Attacker submits this transaction directly to a validator's mempool network endpoint (bypassing the REST `submit_transaction` handler and its `payload.verify()` call at `api/src/transactions.rs:1387`).
5. During consensus, `decrypt_validator_path` calls `FPTXWeighted::prepare_ct` and `do_final_decryption` on the ciphertext without ever checking that it is bound to `attacker`/`attacker_auth_keys` — the check is architecturally absent from this path — and the transaction is decrypted using the same plaintext originally intended for user A, then executed as if submitted by the attacker.

This scenario could not be validated against a running node in this session; confirmation would require setting up the encrypted-transaction test harness (as used in `aptos-move/e2e-move-tests/src/tests/vm.rs` and `consensus/src/pipeline/decryption_pipeline_builder.rs` test module) to submit a ciphertext under one `(sender, auth_keys)` pair inside a `RawTransaction` carrying a different sender, and observing whether `decrypt_validator_path` still decrypts and forwards it as `Decrypted`.

    /// Verify the decrypted plaintext against the stored commitments and, on success,
    /// transition `self` to `Decrypted`. On mismatch, `self` is left as `Encrypted` and the
    /// failure reason is returned so the caller can mark the payload failed.
    pub fn try_into_decrypted(
        &mut self,
        eval_proof: EvalProof,
        plaintext: DecryptedPlaintext,
    ) -> Result<(), DecryptionFailureReason> {
        let Self::Encrypted(original) = self else {
            panic!("try_into_decrypted called on non-Encrypted state");
        };

        if original.payload_hash != CryptoHash::hash(&plaintext) {
            return Err(DecryptionFailureReason::PayloadHashMismatch);
        }

        if let Some(claim) = &original.claimed_entry_fun {
            let TransactionExecutable::EntryFunction(entry_fun) = plaintext.executable() else {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            };
            if *entry_fun.module() != claim.module {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
            if let Some(claimed_function_id) = &claim.function
                && entry_fun.function() != claimed_function_id.as_ident_str()
            {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
        }

        *self = Self::Decrypted {
            original: original.clone(),
            eval_proof,
            decrypted: plaintext,
        };
        Ok(())
    }

impl<PCT: InnerCiphertext> Ciphertext<PCT> {
    pub fn verify(&self, associated_data: &impl AssociatedData) -> Result<()> {
        let hashed_id = Id::from_verifying_key_and_ad(&self.vk, associated_data);

        (self.associated_data_bytes == bcs::to_bytes(associated_data)?)
            .then_some(())
            .ok_or(BatchEncryptionError::CTVerifyError(
                CTVerifyError::AssociatedDataDoesNotMatch,
            ))?;

        (self.bibe_ct.id() == hashed_id).then_some(()).ok_or(
            BatchEncryptionError::CTVerifyError(CTVerifyError::IdDoesNotMatchHashedVKAndAD),
        )?;

        let to_verify = (&self.bibe_ct, &self.associated_data_bytes);

        self.vk
            .verify(&bcs::to_bytes(&to_verify)?, &self.signature)
            .map_err(|e| {
                BatchEncryptionError::CTVerifyError(CTVerifyError::SigVerificationFailed(e))
            })?;

        Ok(())
    }
