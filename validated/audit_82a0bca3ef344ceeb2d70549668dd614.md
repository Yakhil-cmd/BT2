## Analysis

Confirmed: `ApiClient` records can be scoped to a single `Stack` via the `stack_id` column (fixture `here_come_the_walrus` demonstrates this, and `Shipit::Api::BaseController#stacks`/`#stack` enforce that scoping everywhere else). [1](#0-0) [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly instead of the inherited `stacks.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id?` restriction entirely. [3](#0-2) 

### Title
Stack-scoped API tokens can read CCMenu build status of any stack, bypassing per-stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` tokens can be created scoped to a single `Stack` (`stack_id` column), and every other API endpoint enforces this scope through `BaseController#stacks`/`#stack`. `CCMenuController` overrides `#stack` and resolves the target stack directly from `Stack.from_param!`, so the `stack_id` restriction on the token is never applied.

### Finding Description
The binding that should hold is: *the stack a token authorizes == the stack it touches*. In `Shipit::Api::BaseController`, this is implemented as:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`StacksController`, `TasksController`, `CommitsController` all inherit this and are therefore correctly scoped, as shown by the test "an api client scoped to a stack will only see that one stack". [4](#0-3) 

`CCMenuController`, however, redefines `#stack` to bypass the `stacks` scoping method:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

`require_permission :read, :stack` only checks that the permission name `read:stack` is present in `ApiClient#permissions`; it never checks `stack_id`: `check_permissions!` just does `permissions.include?(required_permission)`. [6](#0-5) 

So an `ApiClient` created with `stack_id` set to Stack A (e.g. via `CCMenuUrlController`, which mints tokens with `read:stack` permission per-user) can call `GET /api/stacks/:stack_id/ccmenu.xml` with any other `stack_id` (Stack B) and successfully read Stack B's build/deploy status, `lastBuildStatus`, `lastBuildLabel`, lock status, etc., even though the token's `stack_id` scope only authorizes Stack A.

### Impact Explanation
This breaks the "stack a token authorizes vs. stack it touches" binding: an attacker holding a token limited to one stack (the least-privileged type of Shipit API credential) can read stack state, build status, and lock status for every other stack in the deployment — an authorization bypass yielding cross-stack information disclosure of deploy/task/build state, matching the specified High-severity class ("escalation ... unauthenticated/unauthorized read of stack state, task streams or deploy output").

### Likelihood Explanation
Any actor who possesses a stack-scoped `ApiClient` token (the intended low-privilege credential type, e.g. issued by `CCMenuUrlController#client` for CI status badges) can trivially trigger this by supplying a different `stack_id` in the request path — no other authorization step or GitHub credential is required beyond having a valid, narrowly-scoped token.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited scoping helper (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so stack-scoped tokens are restricted the same way as in every other API controller.

### Proof of Concept
1. As user U, visit stack A's page to trigger `CCMenuUrlController#fetch`, which creates/returns an `ApiClient` named "CCMenu Client" with `permissions: %w[read:stack]` (unscoped by default) — but assume/administer a token where `stack_id` is explicitly set to stack A (e.g. `here_come_the_walrus` fixture pattern). [7](#0-6) 
2. Using that token, call `GET /api/stacks/B/ccmenu.xml?token=<stack-A-scoped-token>` where `B` is a stack the token was never authorized for.
3. `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly (ignoring `current_api_client.stack_id`), so the request succeeds and returns stack B's `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock status. [8](#0-7)  Compare with `StacksController`/`TasksController`, where the equivalent request would 404 via `stacks.from_param!` scoping. [4](#0-3)
