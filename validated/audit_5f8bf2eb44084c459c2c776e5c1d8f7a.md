### Title
Bridge Lock-Mode ERC20 Reserve Insolvency with Fee-on-Transfer Tokens — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge's `requestERC20Transfer` records the caller-supplied `_value` in the `RequestValueTransfer` event without measuring the actual tokens received by the bridge contract. When a fee-on-transfer (deflationary) ERC20 token is registered and used in lock mode (`modeMintBurn = false`), each deposit leaves the bridge holding fewer tokens than the event promises. The counterpart bridge later calls `handleERC20Transfer` and sends the full nominal `_value` to each recipient. After enough deposits, the bridge's real reserve falls below the sum of outstanding claims, and later users cannot withdraw their bridged assets.

---

### Finding Description

**Deposit path — `requestERC20Transfer`:**

```solidity
// BridgeTransferERC20.sol line 133
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

The bridge pulls `_value + _feeLimit` from the caller. For a fee-on-transfer token with rate `f`, the bridge actually receives `(_value + _feeLimit) × (1 − f)`. No balance-before/after check is performed. The internal `_requestERC20Transfer` then emits `RequestValueTransfer` with the original `_value`:

```solidity
// BridgeTransferERC20.sol lines 97-107
emit RequestValueTransfer(
    TokenType.ERC20,
    _from, _to, _tokenAddress,
    _value,          // ← nominal, not actual received
    requestNonce, fee, _extraData
);
``` [2](#0-1) 

**Withdrawal path — `handleERC20Transfer`:**

```solidity
// BridgeTransferERC20.sol line 71
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [3](#0-2) 

The counterpart bridge sends the full nominal `_value` regardless of what was actually deposited. Each withdrawal drains the reserve by `_value`, while each deposit only added `(_value + _feeLimit) × (1 − f) − fee_transfers`.

The `_payERC20FeeAndRefundChange` helper also issues additional `safeTransfer` calls (fee to `feeReceiver`, refund to `from`), each of which incurs the token's transfer tax, further widening the gap: [4](#0-3) 

---

### Impact Explanation

**Invariant broken:** `sum of all pending handleERC20Transfer._value ≤ bridge.balanceOf(token)`.

With N users each depositing nominal `V` tokens (fee rate `f`):
- Bridge actual balance after N deposits: `≈ N × V × (1 − f)` (minus additional fee-transfer taxes)
- Sum of outstanding claims: `N × V`

The first `⌊(1−f)/f⌋` users can withdraw successfully; remaining users receive a revert from `safeTransfer` because the bridge is insolvent. Users who deposited identical amounts receive different outcomes purely based on withdrawal order — exactly the unfair-withdrawal pattern from the seed report.

This constitutes **loss of bridged assets** for later users, matching the allowed impact: *"Unauthorized transfer … affecting … bridged assets."*

---

### Likelihood Explanation

- The bridge operator must register the fee-on-transfer token (`registerToken`). This is a semi-trusted precondition, not a privileged-only attack: operators legitimately register rebasing/deflationary tokens (e.g., tokens with burn-on-transfer mechanics).
- Once registered, **any unprivileged user** calling `requestERC20Transfer` or `onERC20Received` triggers the accounting discrepancy.
- The vulnerability is silent — no revert occurs at deposit time; the bridge appears to function normally until reserves are exhausted.

---

### Recommendation

1. **Measure actual received amount** using a balance-before/balance-after pattern in `requestERC20Transfer`:
   ```solidity
   uint256 before = IERC20(_tokenAddress).balanceOf(address(this));
   IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
   uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)) - before;
   require(actualReceived >= _value, "fee-on-transfer: insufficient received");
   ```
2. Emit `RequestValueTransfer` with `actualReceived − fee` rather than the caller-supplied `_value`.
3. Alternatively, document and enforce that only non-fee-on-transfer tokens may be registered, and add a guard in `registerToken` or `setERC20Fee`.

---

### Proof of Concept

Setup: fee-on-transfer token with 1% burn per transfer, bridge in lock mode (`modeMintBurn = false`), `feeOfERC20 = 0`.

| Step | Action | Bridge balance (nominal) | Bridge balance (actual) |
|------|--------|--------------------------|-------------------------|
| 1 | Alice deposits 100 | 100 | 99 |
| 2 | Bob deposits 100 | 200 | 198 |
| 3 | Eve deposits 100 | 300 | 297 |
| 4 | Alice withdraws 100 | 200 | 197 (safeTransfer sends 100, Alice gets 99) |
| 5 | Bob withdraws 100 | 100 | 97 |
| 6 | Eve withdraws 100 | 0 | **revert** — bridge holds 97 < 100 |

Eve deposited the same 100 tokens as Alice but cannot withdraw at all. Alice and Bob each lost 1 token to the token's own fee; Eve lost her entire 100 tokens to bridge insolvency — a direct analog of the seed report's ordering-dependent unfair loss. [5](#0-4) [3](#0-2)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
