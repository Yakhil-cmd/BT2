### Title
Arbitrary route pool can drain unrelated caller tokens through the signed authorization tree - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
A route can name an arbitrary contract as a swap `pool`, and the router invokes that contract while the caller’s authorization for the enclosing strategy remains active. The malicious pool can therefore request an unrelated `token.transfer(victim, attacker, amount)` as a child authorization; if the victim signs the simulated authorization tree, the token moves even though it is not part of the route. This is the on-chain analogue of trusting an attacker-controlled path outside the intended media/storage boundary.

### Finding Description
`Controller::swap_collateral` accepts caller-supplied `swap` bytes and forwards them into the strategy path after owner-or-delegate authorization. [1](#0-0) [2](#0-1) 

The router authenticates the sender, decodes the payload, and treats `assets[idx_a]` for each swap operation as the pool address. [3](#0-2) [4](#0-3) 

`dispatch_hop` selects only a venue adapter from the opcode; it does not verify that `hop.pool` is a deployed pool for that venue or belongs to an allowlist. [5](#0-4) 

Every adapter invokes the payload-selected `pool`; for example, the Soroswap adapter calls `get_reserves` and `swap` on `ctx.hop.pool`. [6](#0-5) [7](#0-6) 

Because the malicious contract runs below the authorized `swap_collateral` invocation, a token transfer it requests from the caller can be represented as a child of that authorization tree. The router’s measured-input and measured-output checks constrain routed balances but do not prevent the nested contract from requesting an unrelated caller-token transfer. [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker who supplies the route can steal any spendable token balance that the victim’s signed authorization tree covers, including an asset unrelated to the lending position or swap. The attack can still satisfy the router’s input-spend and positive-output checks by returning enough of the expected output token to the router, so the enclosing strategy can complete while the unrelated wallet transfer also succeeds. [10](#0-9) [8](#0-7) 

This is theft of user funds. The theft amount is bounded by the victim’s token balances and signed child invocation, not by `total_in` or the strategy’s minimum output. [11](#0-10) 

### Likelihood Explanation
The malicious route requires the victim to sign a poisoned authorization tree, so this is not an unauthenticated direct drain. However, routes are opaque packed/XDR data constructed off-chain, and the authorization tree produced by simulation can contain a nested token transfer that is difficult for a wallet or user to associate with the displayed swap. [12](#0-11) 

The attacker only needs to deploy a contract implementing the selected adapter’s expected calls and persuade the victim to execute a caller-authorized strategy such as `swap_collateral`, `multiply`, `swap_debt`, or `repay_debt_with_collateral`. Those strategies all accept a caller-controlled `swap` payload. [13](#0-12) [14](#0-13) [15](#0-14) [16](#0-15) 

### Recommendation
Enforce the venue boundary before dispatch: maintain or derive an allowlist/registry of valid pool addresses for each venue, or validate pool identity against a trusted factory/registry where available. At minimum, reject a route whose pool address is not attested for the selected venue rather than treating every `assets` entry as executable code. [4](#0-3) [17](#0-16) 

The controller or router should also isolate the route execution authorization context so nested venue code cannot consume the user’s top-level strategy authorization for unrelated token transfers. Clients should additionally simulate, decode, and reject any authorization tree containing a token transfer other than the expected router input pull. [18](#0-17) [19](#0-18) 

### Proof of Concept
1. Attacker deploys `RoguePool` configured with `(victim, unrelated_token, attacker, unrelated_token_balance)` and funds it with enough `new_token` to satisfy the route’s minimum output.

2. `RoguePool` implements the Soroswap-facing calls used by the adapter: `get_reserves` returns reserves that produce a positive `requested_out`, and `swap(amount_0_out, amount_1_out, to)` transfers `new_token` to the router. Before returning, it calls `unrelated_token.transfer(victim, attacker, unrelated_token_balance)`. [6](#0-5) [7](#0-6) 

3. Attacker constructs a `StrategyPayload` whose `assets` registry contains `RoguePool` as `idx_a`, the collateral token as `token_in`, and `new_token` as `token_out`, with one opcode `0`/`Soroswap` instruction. [20](#0-19) [21](#0-20) 

4. Victim calls `Controller::swap_collateral(caller=victim, account_id, current, amount, new, swap=payload)`. The controller authorizes the strategy, withdraws `current`, and invokes the router. [1](#0-0) [22](#0-21) 

5. The router pulls the exact input, dispatches to `RoguePool`, measures a positive `new_token` receipt, pays it out, and completes the collateral redeposit. [10](#0-9) [11](#0-10) 

6. During the `RoguePool::swap` call, the extra `unrelated_token.transfer(victim, attacker, ...)` executes if the victim signed the simulated authorization tree containing that child. The strategy succeeds while the victim loses the unrelated wallet token.

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };
