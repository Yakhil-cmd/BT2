## Title
Headers-commission distribution among multiple `earned_headers_commission_recipients` rounds independently per recipient, causing bytes to be lost or minted - ([File: headers_commission.js])

### Summary
When a unit that redistributes its earned headers commission to several addresses (via `earned_headers_commission_recipients`) wins a headers-commission payout, each recipient's share of the fixed `full_amount` is rounded independently with `Math.round`/SQL `ROUND()`. Because each recipient's amount is rounded separately instead of the last recipient receiving the remainder, the sum of the rounded amounts can differ from the actual `full_amount` that was already committed/paid by the fee-payer unit, exactly the rounding-loss pattern described in the referenced report.

### Finding Description
Any unpriveleged unit poster can create a multi-authored unit and set `earned_headers_commission_recipients` with several addresses whose `earned_headers_commission_share` values sum to exactly 100 (this is the only invariant enforced): [1](#0-0) 

When headers commissions are later calculated for a winning unit that has more than one recipient, each recipient's cut is computed independently by rounding `full_amount * share / 100`: [2](#0-1) 

The same independent-rounding pattern also exists in the MySQL/in-memory reconciliation path: [3](#0-2) 

and in the raw SQL used for the MySQL backend: [4](#0-3) 

`full_amount` (the payer unit's `headers_commission`) is a fixed integer that was already accounted for when the payer unit was validated — the unit's balance equation requires `total_input === total_output + headers_commission + ...`: [5](#0-4) 

Because each recipient's share is rounded on its own (e.g. three recipients at 33/33/34% of an odd `full_amount`), the sum of the individually-rounded amounts inserted into `headers_commission_contributions` (and later aggregated into `headers_commission_outputs`) can be less than or greater than `full_amount`. There is no step that adjusts the last recipient to absorb the rounding remainder, unlike the recommendation given in the referenced report.

### Impact Explanation
- If the roundings sum to **less** than `full_amount`, the difference is never inserted as any recipient's `headers_commission_contributions` row, so those bytes become permanently unspendable — the exact "stranded tokens" scenario from the report, applied to header-commission fee redistribution instead of loan-collateral claims.
- If the roundings sum to **more** than `full_amount`, extra bytes are created that were never actually paid by any unit, i.e. a supply-inflation bug: `headers_commission_outputs`, which back the `type: "headers_commission"` spendable inputs validated in `validatePaymentInputsAndOutputs`, would allow recipients to collectively spend more than the payer ever paid.

Both cases violate ocore's fixed total-money-supply invariant, which is normally maintained by fee inputs/outputs balancing exactly at every unit.

### Likelihood Explanation
The trigger requires only a normal, unprivileged multi-authored unit with a crafted `earned_headers_commission_recipients` list (odd percentages such as 33/33/34) that later wins headers commission from a descendant unit — a common, easily reachable path with no special privileges, and deterministic (both DB backends compute it the same way, so no node-disagreement risk, but the supply drift is real and accumulates unit by unit).

### Recommendation
When distributing `full_amount` across multiple `earned_headers_commission_recipients`, round all but the last recipient normally, then assign the last recipient `full_amount - sum(previous roundings)` so the total always reconciles to `full_amount`, mirroring the fix recommended in the source report. Apply this fix consistently in both the SQL-based (`headers_commission.js` lines 50-51, 199-205) and in-memory (`headers_commission.js` lines 179-188) computation paths.

### Proof of Concept
1. Post a multi-authored unit `U` with `earned_headers_commission_recipients` = `[{address: A, share: 33}, {address: B, share: 33}, {address: C, share: 34}]` (sums to 100, passes `validateHeadersCommissionRecipients`).
2. Arrange for `U` (or a descendant that inherits the recipient list) to win a headers commission whose `full_amount` is not evenly divisible by the shares, e.g. `full_amount = 5`.
3. `headers_commission.js` computes `round(5*33/100)=2`, `round(5*33/100)=2`, `round(5*34/100)=2`, summing to `6 ≠ 5` — one extra byte is credited to `headers_commission_contributions`/`headers_commission_outputs` beyond what the payer unit actually paid.
4. Alternatively, choose shares/`full_amount` combinations that round down (e.g., `full_amount=7`, shares 20/20/20/20/20) to see `1+1+1+1+1=5 ≠ 7`, permanently stranding 2 bytes that are unspendable by anyone.
