### Title
Missing anti-replay check lets an arbiter-contract counterparty force duplicate/late "paid" and "in_dispute" status re-triggers, allowing double `sendMultiPayment` execution - ([File: arbiter_contract.js])

### Summary
`InvestmentManager._reviewRedemptionRequest`'s bug class is: an action is approved based on a state read (`status`), but the state is not atomically updated/locked before the fund-moving side effect executes, so the same request can be "reviewed"/executed more than once. The same root cause exists in `arbiter_contract.js`'s `pay()`/`complete()` functions and in the `arbiter_contract_update` message handler in `wallet.js`: contract state is read via `getByHash()`, checked against a small set of allowed values, and only written back with `setField()` *after* an async operation (a payment or a device round-trip) completes — with no lock or idempotency guard against a second, concurrent invocation of the same transition while the first is still in flight.

### Finding Description
`pay()` reads the contract, checks `objContract.status !== "signed"`, then calls `walletInstance.sendMultiPayment(...)`, and only updates status to `"paid"` inside the payment's callback: [1](#0-0) 

`complete()` follows the identical pattern: it reads the contract, checks `objContract.status !== "paid" && objContract.status !== "in_dispute"`, then performs `walletInstance.sendMultiPayment(...)` and only afterwards calls `setField(objContract.hash, "status", ...)`: [2](#0-1) 

Because the state check (`getByHash`) and the state write (`setField`) are separated by an asynchronous, potentially long-running operation (`sendMultiPayment` can involve multisig round-trips over the network, explicitly called out as "can take long if multisig" elsewhere in the file), any two overlapping invocations of `pay()`/`complete()` for the same contract hash will both pass the status check before either write lands, exactly mirroring the report's "accepted, but reviewable again before it is marked done" flaw.

The trigger for a second invocation is externally influenced: the peer/arbiter counterparty (a paired device, explicitly in scope) can drive contract-state transitions via `arbiter_contract_update` messages handled in `wallet.js`, and via the `new_my_transactions`/`my_transactions_became_stable` event listeners in `arbiter_contract.js` that also call `setField(..., "status", "paid"/"in_dispute", ...)` off of the same stale-read pattern: [3](#0-2) [4](#0-3) 

The `wallet.js` handler for `arbiter_contract_update` performs its `isOK` validation against a single `getByHash` snapshot taken at the start of message processing, then performs further async DB lookups (`wallet_signing_paths` join) before finally calling `setField()`: [5](#0-4) 
If the peer (who controls the timing and content of these device messages) sends two `arbiter_contract_update` messages with the same target status in quick succession — or if a peer can cause `pay()`/`complete()` to be invoked twice (e.g., by racing a device message that flips status back to an allowed source state, or by the wallet's own UI/automation calling `pay`/`complete` again before the first payment's status write completes) — both branches observe the same pre-transition status and both proceed to spend funds via `sendMultiPayment`, while the status column is written twice, non-atomically, with no guard against having already been written once.

This is architecturally identical to the reported bug: state is used to gate a fund-moving action, but the action and the state commit are not atomic, and there is no explicit "already processed / already paid" guard analogous to the recommended "revert if the request is already queued" fix.

### Impact Explanation
If a second `pay()` or `complete()` execution races the first, the wallet composes and broadcasts a second `sendMultiPayment` for the same contract — either double-funding the shared arbiter address (in `pay()`) or double-releasing funds from the shared address to the peer/arbiter cut (in `complete()`). This is a direct unauthorized/duplicate spend of the wallet owner's funds, caused by a counterparty-controllable message race rather than any signature or definition-level protection (the underlying `sendMultiPayment` calls are otherwise properly authorized/signed, but are invoked more times than the business logic intends). The severity is bounded by needing precise timing of concurrent device messages/payment completions, similar to the "low risk" characterization of the original finding, but the fund-loss primitive (duplicate spend authorized by the user's own signing keys but triggered redundantly by attacker-controlled timing) is real.

### Likelihood Explanation
Exploitation requires the arbiter-contract counterparty (a paired device, which is in the allowed attacker surface) to induce two overlapping status-check-then-spend sequences — for example by sending duplicate/rapid `arbiter_contract_update` messages, or by the natural race between the `new_my_transactions` listener and a manual `pay()`/`complete()` call for the same contract while a `sendMultiPayment` (potentially multisig, hence slow) is still pending. This requires network-timing control but does not require compromising any keys, hubs, or nodes — it is purely a client-side missing-idempotency issue reachable from a normal paired-device correspondent, making it a plausible, low-to-medium likelihood but genuine confirmable analog.

### Recommendation
Add an explicit, atomic "already processing / already transitioned" guard before invoking `sendMultiPayment` in `pay()` and `complete()` — e.g., transactionally flip `status` to an intermediate "paying"/"completing" state (or acquire a mutex keyed by contract hash) before calling `sendMultiPayment`, and reject re-entrant calls while that lock/intermediate state is held. Apply the same idempotency guard to the `arbiter_contract_update` status-transition handler in `wallet.js` and to the `setField(..., "status", ...)` calls inside the `new_my_transactions` / `my_transactions_became_stable` listeners in `arbiter_contract.js`, so that a given transition (e.g., "signed→paid", "paid→in_dispute") can only be committed once per contract, consistent with how `unit` and `shared_address` fields are already protected against being set twice.

### Proof of Concept
1. Two contract parties agree on an arbiter contract; contract status reaches `"signed"`.
2. The wallet owner (or an automated flow) calls `arbiter_contract.pay(hash, walletInstance, [], cb)` — this begins `getByHash` → status check (`"signed"`) → `sendMultiPayment(...)`, which is slow because it requires multisig cosigning round-trips over the network with the peer device.
3. Before the first `sendMultiPayment` callback fires (and thus before `setField(hash, "status", "paid", ...)` runs), the same `pay()` call is invoked again for the same `hash` (e.g., a retried UI action, or a second call triggered by a duplicate/racing message from the peer's paired device).
4. The second call also finds `status === "signed"` (stale read) and issues its own `sendMultiPayment`, resulting in two separate on-chain payments being funded from the wallet owner's addresses to the shared arbiter address for a single logical contract, only after which the status field is (redundantly) set to `"paid"` twice — a duplicate spend caused purely by the missing atomic transition guard, mirroring the reviewed-redemption-twice pattern from the original report.

function pay(hash, walletInstance, arrSigningDeviceAddresses, cb) {
	getByHash(hash, function(objContract) {
		if (!objContract.shared_address || objContract.status !== "signed" || !objContract.me_is_payer)
			return cb("contract can't be paid");
		var opts = {
			asset: objContract.asset,
			to_address: objContract.shared_address,
			amount: objContract.amount,
			spend_unconfirmed: walletInstance.spendUnconfirmed ? 'all' : 'own'
		};
		if (arrSigningDeviceAddresses.length)
			opts.arrSigningDeviceAddresses = arrSigningDeviceAddresses;
		walletInstance.sendMultiPayment(opts, function(err, unit){								
			if (err)
				return cb(err);
			setField(objContract.hash, "status", "paid", function(objContract){
				cb(null, objContract, unit);
			});

				if (assetInfo && assetInfo.is_private)
					db.query("INSERT "+db.getIgnore()+" INTO my_watched_addresses (address) VALUES (?)", [objContract.peer_address]);
			});
		});
	});

					setField(objContract.hash, "status", status, function(objContract){

					});
				});
