## Analysis

The Opal report's bug class is: a function decides "is there enough X to authorize action A" by counting balance that is not actually free/uncommitted for A (idle + deployed, both counted as "available"), which lets an attacker corrupt the equality between what's counted and what's really available, breaking withdrawals. The strongest reachable analog in this repo is in `register-for-bond` (and `stake`) in `pox-5.clar`, combined with the node-side lock dispatcher in `pox-locking/src/pox_5.rs`.

### The equality that should hold
STX that is already locked by an *unrelated, active* PoX commitment must not be treated as "available" to back a brand-new pox-5 commitment, and a lock may only be converted/extended ("rolled over") when the existing lock is genuinely a pox-5 position that is legitimately ending (verified overlap/rollover-window checks against pox-5's own bookkeeping).

### Root cause
In `register-for-bond`:
```
(stx-balance (stx-account tx-sender))
(total-balance (+ (get locked stx-balance) (get unlocked stx-balance)))
...
(asserts! (>= total-balance amount-ustx) ERR_INSUFFICIENT_STX)
``` [1](#0-0) 

`total-balance` is `stx-account`'s generic `locked + unlocked`, which is agnostic of *which* PoX contract created the lock. The comment justifies this only for the legitimate case of "rolling over" from an ending pox-5 bond/stake, where the node-side handler is expected to extend the *same* lock. But the gates that decide whether a rollover is legitimate — `existing-membership`, `existing-stake`, `bond-overlaps-new-position?`, `verify-bond-rollover-window` — are pulled from pox-5's own maps (`protocol-bond-memberships`, `staker-info`), not from the generic account lock state: [2](#0-1) [3](#0-2) 

If a staker currently has an *unrelated* lock from an earlier PoX version (e.g., still locked under pox-4 for a separate stacking commitment that has nothing to do with pox-5), pox-5's own maps show no `existing-membership`/`existing-stake`, so the overlap/rollover-window checks trivially pass, while `total-balance >= amount-ustx` also passes because the pox-4-locked STX is counted as "available."

On the node side, `handle_lockup_pox_v5` decides whether to treat the call as a fresh lock or a roll-over purely via the generic, version-agnostic check `snapshot.has_locked_tokens()`:
```
let already_locked = {
    let mut snapshot = global_context.database.get_stx_balance_snapshot(&staker)?;
    snapshot.has_locked_tokens()?
};
let lock_result = if already_locked {
    pox_rollover_v5(...)
} else {
    pox_lock_v5(...)
};
``` [4](#0-3) 

The doc comment on this handler explicitly states the trust model: *"the contract is responsible for gating the roll-over ... if the contract returns ok, this handler trusts the call is legitimate."* [5](#0-4) 

But as shown above, pox-5's Clarity-level gate does not actually verify that the pre-existing lock is a *pox-5* lock ending on schedule — it only checks generic total balance. Contrast this with the sibling `pox_lock_increase_v2/v3/v4` functions, which explicitly assert `snapshot.is_v2_locked()?` / `is_v3_locked()?` before allowing an "increase," rejecting cross-version manipulation: [6](#0-5) 
No equivalent version check exists in the pox-5 rollover path (`pox_rollover_v5` is invoked solely based on `has_locked_tokens()`, and `pox_lock_v5` itself only checks `has_locked_tokens()` to reject as `PoxAlreadyLocked`, not `is_v5_locked()`): [7](#0-6) 

### Impact
A staker with an active, unrelated pox-4 lock can call `register-for-bond` (or `stake`) in pox-5, pass the "sufficient funds" check by counting the pox-4-locked STX as available, get credited pox-5 reward-set shares for `amount-ustx`, and have the node-side handler treat this as a legitimate roll-over — converting/overwriting the account's lock state into a PoX-5 lock with pox-5's amount/unlock-height. This either (a) double-counts a single locked STX balance as backing two different, non-consensual stacking commitments (pox-4's original commitment and pox-5's new bond), or (b) effectively force-terminates/reschedules the pox-4 lock outside of pox-4's own unlock rules — an unsigned/unauthorised stacking action against the pox-4 commitment, and a case of signing/reward weight being granted in pox-5 that exceeds STX genuinely free to back it.

### What I could not verify
I was not able to view the full body of `pox_rollover_v5` (only `pox_lock_v5`, `pox_unstake_v5`, and `pox_lock_update_v5` were inspected within the iteration budget) to see whether it independently re-validates that the existing lock is a pox-5 lock before overwriting it. Given the codebase's explicit stated trust model ("this handler trusts the call is legitimate" once the contract returns ok) and the absence of any `is_v5_locked()`-style guard in the functions I did inspect, the contract-level gate identified above appears to be the sole safeguard — and it is insufficient because it only checks aggregate balance, not lock provenance. Confirming `pox_rollover_v5`'s exact behavior would require an additional read; if it does perform a strict provenance check omitted from my excerpt, this finding would need to be downgraded to a documentation/clarity concern rather than an exploitable path.

### Title
Cross-version lock confusion in `register-for-bond`/`stake` treats unrelated PoX-4-locked STX as available collateral for new PoX-5 commitments - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`, `pox-locking/src/pox_5.rs`)

### Summary
`register-for-bond` and `stake` in pox-5.clar authorize a new stacking commitment using `stx-account`'s generic `locked + unlocked` total, which does not distinguish whether the "locked" portion belongs to a pox-5 position that is legitimately ending or to a wholly unrelated, still-active lock from an earlier PoX contract (e.g. pox-4). The node-side dispatcher in `pox_5.rs` likewise decides "fresh lock vs. roll-over" using the version-agnostic `has_locked_tokens()`, and documents that it fully trusts the contract's authorization once it returns `ok`.

### Finding Description
See root-cause analysis above: pox-5's own overlap/rollover-window gates (`existing-membership`, `existing-stake`, `bond-overlaps-new-position?`, `verify-bond-rollover-window`) are keyed off pox-5-specific maps and are vacuously satisfied when there is no pre-existing pox-5 position, while the balance sufficiency check (`total-balance >= amount-ustx`) is satisfied by counting an unrelated pox-4 lock. The node then dispatches to `pox_rollover_v5` purely because `has_locked_tokens()` is true, converting the lock into pox-5 terms.

### Impact Explanation
This breaks the equality that locked STX backing one PoX commitment cannot be silently repurposed/double-counted to also back a different, unrelated commitment without going through that commitment's own unlock rules. It can result in over-crediting pox-5 reward shares/signing weight beyond genuinely free STX, and/or early or unauthorized alteration of a pox-4 lock's schedule — falling under "signing weight or reward slots exceeding locked value" / "an unsigned stacking action" (High), and potentially "double-counting a commitment" (Critical) if it can be leveraged to have the same STX simultaneously reflected as locked collateral in two reward sets.

### Likelihood Explanation
Requires only that an ordinary, unprivileged account hold an active lock from an earlier PoX contract while calling a pox-5 entry point — no privileged role, miner, or other user's key is needed, matching the analog's "wrong accounting enables an unprivileged attacker" class. Likelihood depends on confirming `pox_rollover_v5`'s exact validation, which I could not fully inspect.

### Recommendation
In `register-for-bond`/`stake`, verify that any pre-existing lock counted toward "available" balance is specifically a pox-5 lock that is genuinely ending (e.g., assert `is-v5-locked`/provenance at the node-side handler, mirroring the `is_v2_locked`/`is_v3_locked`/`is_v4_locked` guards used in the increase-lock paths of earlier PoX versions) before treating the call as a legitimate roll-over; otherwise require the unrelated lock to fully unlock first.

### Proof of Concept
Not independently reproduced (test harness/network unavailable in this analysis context); the flow is derived from static tracing:
1. Staker holds an active lock under pox-4 for amount `L`.
2. Staker calls `pox-5.register-for-bond` with `amount-ustx = A`, where `A <= L + unlocked` but `A` exceeds what is actually free once the pox-4 commitment is honored.
3. `total-balance >= amount-ustx` passes (counts pox-4's `L` as available) at [8](#0-7) ; overlap/rollover checks vacuously pass since pox-5 has no record of this staker.
4. Contract returns `ok`; `handle_lockup_pox_v5` sees `has_locked_tokens() == true` (due to the pox-4 lock) and calls `pox_rollover_v5` instead of a fresh `pox_lock_v5`, converting the lock to pox-5 terms at [9](#0-8) .

pub fn pox_lock_v5(
    db: &mut ClarityDatabase,
    principal: &PrincipalData,
    lock_amount: u128,
    unlock_burn_height: u64,
) -> Result<(), LockingError> {
    if unlock_burn_height == 0 {
        return Err(LockingError::PoxInvalidUnlockHeight);
    }
    if lock_amount == 0 {
        return Err(LockingError::PoxInvalidLockAmount);
    }

    let mut snapshot = db.get_stx_balance_snapshot(principal)?;

    if snapshot.has_locked_tokens()? {
        return Err(LockingError::PoxAlreadyLocked);
    }
    if !snapshot.can_transfer(lock_amount)? {
        return Err(LockingError::PoxInsufficientBalance);
    }
    snapshot.lock_tokens_v5(lock_amount, unlock_burn_height)?;

    debug!(
        "PoX v5 lock applied";
        "pox_locked_ustx" => snapshot.balance().amount_locked(),
        "available_ustx" => snapshot.balance().amount_unlocked(),
        "unlock_burn_height" => unlock_burn_height,
        "account" => %principal,
    );

    snapshot.save()?;
    Ok(())
}

pub fn pox_lock_increase_v2(
    db: &mut ClarityDatabase,
    principal: &PrincipalData,
    new_total_locked: u128,
) -> Result<STXBalance, LockingError> {
    assert!(new_total_locked > 0);

    let mut snapshot = db.get_stx_balance_snapshot(principal)?;

    if !snapshot.has_locked_tokens()? {
        return Err(LockingError::PoxExtendNotLocked);
    }

    if !snapshot.is_v2_locked()? {
        return Err(LockingError::PoxIncreaseOnV1);
    }

    let bal = snapshot.canonical_balance_repr()?;
    let total_amount = bal
        .amount_unlocked()
        .checked_add(bal.amount_locked())
        .expect("STX balance overflowed u128");
    if total_amount < new_total_locked {
        return Err(LockingError::PoxInsufficientBalance);
    }

    if bal.amount_locked() > new_total_locked {
        return Err(LockingError::PoxInvalidIncrease);
    }
