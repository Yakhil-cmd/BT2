### Title
Cross-repository commit-status injection via SHA-only matching in `StatusHandler#process` flips `Commit#deployable?` and enables unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach an incoming GitHub "status" webhook to using only the commit SHA, with no check that the payload's `repository.full_name` matches the repository backing the target `Commit#stack`. Since GitHub commit SHAs are content-addressed and portable across repositories, any repository sharing the same GitHub App installation as the tracked repository's organization can emit a validly-signed webhook that writes a `Status` onto an unrelated stack's commit, flipping `Commit#success?`/`Commit#deployable?` and enabling `Stack#trigger_continuous_delivery` to ship code that was never actually validated for that stack.

### Finding Description
The broken binding, stated as an equality that the code fails to enforce: `Status`'s owning repository (`payload['repository']['full_name']`) == `Commit#stack.repository.full_name`. Tracing the code:

- `WebhooksController#verify_signature` authenticates the request only against the **organization** derived from the payload (`repository_owner` = `params.dig('repository','owner','login')`), via `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature` [1](#0-0) , [2](#0-1) . A GitHub App installed on an organization shares a single `webhook_secret` for every repository under that installation, so this check validates "some repo in this org sent this," not "this specific repo sent this."
- `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` [3](#0-2) .
- `StatusHandler#process` resolves target commits purely by SHA, with **no repository filter at all**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . Note the base `Handler` class even defines a `stacks`/`repository_name`-scoped helper [5](#0-4) , but `StatusHandler` does not use it — unlike, e.g., `CheckSuiteHandler`, which does scope by `stacks.where(branch: ...)` before touching commits [6](#0-5) .
- `Commit#create_status_from_github!` writes the status scoped only to `stack_id` (the commit's own stack), via `statuses.replicate_from_github!(stack_id, github_status)` [7](#0-6) , `Status.replicate_from_github!` [8](#0-7) . Nothing here checks that the `github_status`'s originating repository matches `commit.stack`'s repository.
- `Commit#status` reads `statuses_and_check_runs` (i.e., the just-written `Status`) [9](#0-8) , `success?` is delegated to it [10](#0-9) , and `deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [11](#0-10) .
- A new `success` `Status` triggers `schedule_continuous_delivery` on create [12](#0-11) , [13](#0-12) , which — if `deployable?` and `stack.continuous_deployment?` and `stack.deployable?` — enqueues `ContinuousDeliveryJob`, feeding into `Stack#trigger_continuous_delivery`.

Exploit flow: The attacker needs write/admin access to at least one repository that shares the same GitHub App installation/org (and thus the same `webhook_secret`) as the target Shipit-tracked repository — this is a realistic multi-repo/multi-tenant Shipit deployment where one GitHub App is installed org-wide across many repositories, and the attacker is an unprivileged contributor/owner of one of those repositories but not the victim repository. The attacker:
1. Learns/observes the SHA of a victim commit that is currently `pending?`/`error?` on the target stack (SHAs are content-addressed and often public, e.g. via the Shipit UI, GitHub, PR pages).
2. Pushes/creates a commit with the **identical SHA** into their own controlled repository (trivially achievable since a commit's SHA depends only on its content/parents, not its location — the same commit object can exist in multiple repositories).
3. Uses GitHub's Statuses API (which they can freely call as owner/admin of their own repository) to set state `success` on that SHA in their own repo. GitHub fires a real, correctly-signed "status" webhook for their own repo.
4. Shipit's `WebhooksController#verify_signature` passes because the signature is valid for the shared org/installation secret.
5. `StatusHandler#process` matches `Commit.where(sha: ...)` and finds the **victim's commit** (in a completely different stack/repository), and writes a `success` `Status` onto it, without ever checking that the payload's repository matches the commit's stack repository.
6. `Commit#success?` flips true, `Commit#deployable?` flips true, and if continuous deployment is enabled, `ContinuousDeliveryJob`/`Stack#trigger_continuous_delivery` may deploy attacker-influenced-but-unreviewed code that Shipit believes passed CI.

Existing guards do not stop this: `verify_signature` checks organization-level, not repository-level, authenticity; `drop_unhandled_event` only filters unknown event types; `ExplicitParameters` schema in `StatusHandler` validates payload shape but not repository identity [14](#0-13) ; there is no model validation tying `Status` to a specific GitHub repository.

### Impact Explanation
A payload authenticated for repository/org X can flip `success?`/`deployable?` for a commit belonging to an entirely different stack/repository Y (as long as both are served by the same Shipit instance and share a GitHub App installation secret), enabling `Stack#trigger_continuous_delivery` to deploy or merge-queue-advance code that was never actually validated by that stack's real CI. This is a payload for one repository mutating another repository's commit/stack state, and can escalate to an unauthorized deploy — matching the Critical impact category. It is repeatable against any tracked stack whose commit SHA the attacker can learn and duplicate into a repository they control within the same GitHub App installation, and the blast radius covers every stack sharing that installation on the Shipit instance (a realistic "multi-tenant single-org" Shipit deployment).

### Likelihood Explanation
The precondition is that the attacker controls (owns/admins) at least one repository under the same GitHub organization/App installation as the victim's tracked repository — a common real-world setup for large single-org Shipit deployments tracking many repositories with one shared GitHub App. No Shipit session, API token, or secret is required; the attacker only needs standard GitHub repository-owner privileges on their own repo (which they may legitimately have as a low-privilege engineer/contributor in the org) and the ability to duplicate a known commit SHA into that repo and set a status via GitHub's normal API — both trivial, repeatable, low-cost actions requiring no social engineering or secret compromise.

### Recommendation
In `StatusHandler#process`, scope commit lookup by the payload's repository, mirroring the pattern already used in `CheckSuiteHandler`: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and only update commits within `stacks.commits.where(sha: params.sha)` (or verify `commit.stack.repository.full_name == repository_name` before calling `create_status_from_github!`). This restores the repository binding and prevents cross-repository status injection.

### Proof of Concept
Minitest plan (model-level, no live GitHub required), demonstrating the binding is broken:

```ruby
test "StatusHandler writes a status onto a commit from an unrelated repository, flipping deployable?" do
  victim_stack  = shipit_stacks(:shipit)                 # repository: "shopify/shipit-engine"
  victim_commit = shipit_commits(:fifth)                 # pending/error, belongs to victim_stack
  attacker_repo = shipit_repositories(:cyclimse)          # unrelated repository, e.g. "attacker/other-repo"

  # Binding under test, stated explicitly before tracing:
  refute_equal victim_stack.repository.full_name, attacker_repo.full_name

  refute_predicate victim_commit, :success?
  refute_predicate victim_commit, :deployable?

  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_repo.full_name, 'owner' => { 'login' => attacker_repo.owner } },
    'branches' => []
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  victim_commit.reload
  assert_predicate victim_commit, :success?     # flips from false -> true
  assert_predicate victim_commit, :deployable?  # flips from false -> true
  # despite forged_payload['repository']['full_name'] != victim_stack.repository.full_name
end
```

This demonstrates that `commit.deployable?` transitions false → true purely from a `StatusHandler.call` payload whose `repository.full_name` differs from `commit.stack.repository.full_name`, confirming the broken binding.
