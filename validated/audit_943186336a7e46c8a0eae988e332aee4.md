### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Trust The Unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook's HMAC against using `repository.owner.login` (falling back to `organization.login`) pulled straight out of the untrusted JSON body, but every event handler that actually mutates state (`PushHandler`, `StatusHandler`, all `PullRequest::*Handler`s) resolves the target `Stack`/`Repository`/`Commit` using a *different*, independently-attacker-controlled field in the same payload: `repository.full_name`. In a multi-organization Shipit deployment, these two fields are never checked to be consistent, so a valid signature from one tenant organization can be replayed to act on another tenant's repositories.

### Finding Description
`Shipit.github(organization:)` supports per-organization GitHub App configuration (multiple orgs, each with its own `webhook_secret`), and `verify_signature` looks up the app/secret to check the signature purely from `repository_owner`: [1](#0-0) 

Meanwhile, every webhook `Handler` (base class and all subclasses) resolves the affected repository/stack from the unrelated `repository.full_name` field of the same JSON body: [2](#0-1) 

`PushHandler`, for instance, uses that repository/stack resolution to trigger `stack.sync_github(expected_head_sha: params.after)` for arbitrary SHAs: [3](#0-2) 

`StatusHandler` uses `params.sha` (no owner scoping at all) to write a commit status for any matching `Commit` row in the whole instance: [4](#0-3) 

The equality the code implicitly assumes but never enforces is:
`organization whose webhook_secret authenticated the request == organization owning the repository/commit the handler subsequently writes to`.

Because `repository.owner.login` (used for signature selection) and `repository.full_name` (used by handlers to pick the Stack/Commit) are two independent, attacker-supplied JSON fields inside the same unsigned-at-the-field-level payload, nothing binds them together. `Shipit.github` confirms the multi-org config model exists: [5](#0-4) 

### Impact Explanation
An entity that legitimately controls a GitHub App/organization onboarded to a shared, multi-tenant Shipit instance (i.e., knows *their own* org's `webhook_secret`, with no privileged Shipit session or API token) can forge a request whose HMAC is computed with their own org's secret, while setting `repository.full_name` to a **different** tenant's repository/stack. This lets them:
- Trigger `GithubSyncJob`/`sync_github` for arbitrary commit SHAs on a victim org's stacks (`PushHandler`).
- Inject arbitrary/forged commit statuses for a victim org's commits (`StatusHandler`), which feed `deployable_status`/merge-status checks used elsewhere in the engine to gate whether a commit is safe to deploy.

Forged "success" statuses can make a commit appear deployable when it is not, directly crossing into "unauthorized deploy" territory — one of the explicitly listed Critical impacts.

### Likelihood Explanation
Requires only that the attacker be a legitimate administrator of *some* organization/GitHub App configured on the same shared Shipit instance (a realistic scenario for any multi-tenant deployment using the documented `github: <org>: ...` config schema), and no Shipit session, API token, or repository write access on the victim org is needed — matching the "unprivileged attacker crossing a trust boundary" threat model in scope.

### Recommendation
`verify_signature` must bind the verified organization to the org actually acted upon: either reject/ignore any handler action where `repository.full_name`'s owner does not match the `repository_owner` used to select the webhook secret, or have handlers resolve the `Repository`/`Stack`/`Commit` scoped to the already-verified organization rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Shipit is configured for two tenant orgs, `OrgA` (attacker-controlled webhook secret) and `OrgB` (victim), per the multi-org schema in `config/secrets.development.example.yml`.
2. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` over a `push` payload where:
   - `repository.owner.login = "OrgA"` (so `verify_signature` selects and validates against `OrgA`'s secret)
   - `repository.full_name = "OrgB/victim-repo"`, `ref = "refs/heads/master"`, `after = "<attacker-chosen-sha>"`
3. `WebhooksController#verify_signature` passes because the signature matches `OrgA`'s secret.
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on `OrgB`'s stack despite the request only ever being authenticated for `OrgA`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
