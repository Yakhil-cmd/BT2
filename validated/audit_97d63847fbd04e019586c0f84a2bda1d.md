### Title
`StatusHandler#process` fires `Hook.emit(:deployable_status, ...)` for any stack sharing a commit `sha`, regardless of the webhook's authenticated repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` records purely by `params.sha`, with no filtering by the `repository` that the GitHub App webhook signature actually authenticated. If two different stacks (different repositories) happen to have a `Commit` row with the same `sha`, an attacker-controlled repository's `status` webhook drives `commit.create_status_from_github!` on the victim's `Commit`/`Stack`, causing `Shipit::Hook.emit(:deployable_status, victim_stack, ...)` to fire using the victim stack's own webhook binding but with attacker-fabricated status content.

### Finding Description
The broken binding: `webhook.authenticated_repository.full_name == commit.stack.repository.full_name` is assumed by `Hook.emit(:deployable_status, stack, ...)` but is never enforced in the status flow.

- `WebhooksController#verify_signature` only checks that the payload's HMAC matches the `webhook_secret` configured for `Shipit.github(organization: repository_owner)` [1](#0-0) . This proves the request came from GitHub for *some* organization's installed app, it does **not** bind the event to a specific stack/repository beyond that the `repository_owner` login must resolve to a configured GitHub App/org. Any repository the attacker owns/controls that is registered under an app installation with a valid webhook secret (this can be the attacker's own public repo in the same GitHub App installation scope, e.g., a GitHub App installed org-wide, or any repo for which the attacker can trigger a genuine GitHub-signed `status` event) will pass this check.
- Unlike the generic `Handler` base class, which exposes a `stacks` helper scoped by `Repository.from_github_repo_name(repository_name)` [2](#0-1) , `StatusHandler#process` does **not** use this scoping at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
It looks up **every** `Commit` row across **every** stack/repository sharing that `sha`, ignoring the `repository` field of the inbound payload entirely.
- `Commit#create_status_from_github!` calls `add_status`, which computes `previous_status`/`new_status` and, on a `simple_state` transition while not already deployed, calls `Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))` [4](#0-3) . The `stack` used here is `commit.stack` — i.e., whichever stack the matched `Commit` row belongs to, not the stack tied to the webhook's authenticated repository.
- Because git commit SHAs are content-addressed (tree + parents + author/committer identity + timestamps + message), an attacker who can observe a target commit's metadata (trivial for public repos) can reconstruct an object with an identical SHA in a repository they control (e.g., via `git commit-tree` with matching parent/tree/author/committer/date/message), then configure a CI check on that attacker repo to POST a `status` event for that SHA. GitHub signs that webhook correctly for the attacker's own app installation, and it sails through `verify_signature`. `StatusHandler` then applies it to the victim's `Commit` row that happens to have the same `sha` and belongs to `victim_stack`.
- None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) check that the payload's `repository.full_name` matches the stack that owns the matched `Commit`. The `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/etc, not repository identity [5](#0-4) .

### Impact Explanation
An outbound `deployable_status` `Hook` belonging to `victim_stack` is triggered with attacker-controlled `state`/`description`/`context`/`target_url` content, without the attacker ever touching the victim's repository, its GitHub App installation, or its Shipit configuration. Downstream consumers of that hook (Slack channels, CI dashboards, other automation configured by the victim's operators) receive a forged notification claiming the victim's commit toggled deployable status (e.g., failure→success), which can influence human/automated deploy decisions. This is a cross-tenant payload injection ("a payload for one repository mutating another's stack/commit"), matching the Critical impact category. It is repeatable against any stack whose commits happen to collide in `sha` with an attacker-crafted commit object, which the attacker fully controls by choice of parent/tree/author metadata for any commit whose content is already public.

### Likelihood Explanation
Preconditions: (1) `victim_stack` has a `Shipit::Hook` row subscribed to `deployable_status`; (2) a `Commit` row with the colliding `sha` exists in `victim_stack` and is not yet deployed; (3) the attacker can get a real GitHub-signed `status` webhook delivered for that `sha` from a repository under an app installation whose `webhook_secret` validates. Producing a SHA-identical git commit object in an attacker-controlled repo is a known, low-cost technique when the original commit's tree/parents/author/timestamps are known (which they are, for any commit visible via `Commit#sha` in Shipit's UI or via the source repo). No Shipit secrets, sessions, or privileged roles are required — only ordinary GitHub repository ownership and the ability to enable a CI/status integration on it.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stacks owned by the payload's authenticated repository, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    if commit = stack.commits.by_sha(params.sha)
      commit.create_status_from_github!(params)
    end
  end
end
```
This binds the `Hook.emit` call's `stack` argument to the same repository that the inbound webhook's signature authenticated, closing the divergence.

### Proof of Concept
Minitest plan (model/controller test, no live GitHub):
1. Create `stack_a` (attacker-owned repo `attacker/repo`) and `stack_b` (`victim/repo`) each with a `Commit` sharing `sha: 'deadbeef'`.
2. Give `stack_b` a `Shipit::Hook` for event `deployable_status`; ensure `stack_b`'s commit is not deployed and has an initial status of `failure`.
3. Stub `Shipit::Hook.emit` and post a `status` webhook payload whose `repository.full_name == 'attacker/repo'` (i.e., authenticated for `stack_a`) with `sha: 'deadbeef', state: 'success'` through `WebhooksController#create` (or directly call `StatusHandler.call(params)`).
4. Assert: `Hook.emit` is invoked with `stack_b` (`victim_stack`) as the second argument and `deployable_status: <success status>` in the payload — i.e. `payload_repository = 'attacker/repo'` but `emitted_stack.repository.full_name == 'victim/repo'`, proving the equality `webhook.authenticated_repository == commit.stack.repository` is violated.
5. After applying the recommended fix (scoping via `stacks`/`stack.commits.by_sha`), rerun the same test and assert `Hook.emit` is **not** called for `stack_b`, only (if at all) for `stack_a` when it has a matching commit.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))

      end

    end
