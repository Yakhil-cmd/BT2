### Title
Fail-open rule engine crash via type-confused `tool_matcher` YAML field bypasses ALL hookify rules - ([File: plugins/hookify/core/config_loader.py, plugins/hookify/core/rule_engine.py, plugins/hookify/hooks/pretooluse.py])

### Summary
The custom minimal YAML frontmatter parser in `extract_frontmatter` (config_loader.py) allows a rule's `tool_matcher` field to be parsed as a `list` instead of a `str` when the value is written as an indented YAML list rather than an inline string, and `Rule.from_dict` performs no type validation on it. When `RuleEngine._matches_tool` later calls `matcher.split('|')` on this list, it raises an uncaught `AttributeError` inside `evaluate_rules`, which is caught only by the hook's blanket `except Exception` in `main()`, causing the hook to emit a `systemMessage`-only JSON (no `hookSpecificOutput`/`permissionDecision: deny`) and always `sys.exit(0)`, silently converting what should be a blocking decision into an allow for every rule evaluated in that call.

### Finding Description
`load_rules`/`load_rule_file` in `plugins/hookify/core/config_loader.py` wrap individual file parsing in broad `try/except` blocks [1](#0-0) , but this only guards *construction* of `Rule` objects, not their later *use*. `Rule.from_dict` assigns `tool_matcher=frontmatter.get('tool_matcher')` directly with no type check [2](#0-1) . The hand-rolled `extract_frontmatter` parser treats any top-level key with an empty value followed by indented `- item` lines as a YAML list [3](#0-2) [4](#0-3) . So a rule file containing:
```
tool_matcher:
  - Bash
```
produces `frontmatter['tool_matcher'] = ['Bash']` (a `list`), which passes through `load_rule_file` and `load_rules` without error since no exception occurs during loading.

Later, during evaluation, `RuleEngine._rule_matches` calls `self._matches_tool(rule.tool_matcher, tool_name)` [5](#0-4) , and `_matches_tool` unconditionally calls `matcher.split('|')` [6](#0-5) , which raises `AttributeError: 'list' object has no attribute 'split'` since `matcher` is a list. This exception is raised inside the `for rule in rules` loop of `evaluate_rules` [7](#0-6) , aborting evaluation of that rule and all remaining rules in the same call — with no per-rule isolation.

The exception propagates uncaught out of `evaluate_rules` into the hook's `main()`, where it is caught only by the blanket `except Exception as e:` which builds a `systemMessage`-only error dict (no `hookSpecificOutput`/`decision`) [8](#0-7) , and the `finally: sys.exit(0)` guarantees the hook process always reports success [9](#0-8) . Since Claude Code interprets an empty/non-deny hook response as an implicit allow, any legitimate `block` rule that would have fired in the same `evaluate_rules()` call is silently skipped — not just the malformed rule. This applies identically to `posttooluse.py` [10](#0-9)  and `stop.py` [11](#0-10) .

### Impact Explanation
A single malformed or maliciously crafted `.claude/hookify.*.local.md` rule file (plugin-shipped or committed to a repo) permanently disables enforcement of every other hookify rule on every `PreToolUse`/`PostToolUse`/`Stop` invocation, because `load_rules` scans and loads *all* rule files together and `evaluate_rules` processes them in one loop with no isolation between rules. This defeats the entire purpose of hookify as a guardrail — dangerous `Bash`, `Edit`, `Write`, or `MultiEdit` operations that should be blocked (`action: block`) are instead silently allowed, and the operator receives only a generic `Hookify error: ...` system message with no indication that enforcement failed closed vs. open incorrectly.

### Likelihood Explanation
Exploitation requires only the ability to place or influence one hookify rule markdown file with a specific but plausible-looking YAML shape (`tool_matcher:` as a multi-line list instead of a string) — no special privileges beyond what's already needed to contribute a plugin rule file or committed repo config, matching the "attacker supplies a plugin-shipped or repo-committed hookify rule" precondition. It is 100% repeatable: every subsequent tool call triggers the crash while the malformed rule remains loaded and matches the rule's `event` filter (e.g., `event: all`), since `load_rules` includes it unless filtered out.

### Recommendation
Validate types of all frontmatter-derived `Rule`/`Condition` fields (`tool_matcher`, `field`, `operator`, `pattern`, `action`, `event`) in `Rule.from_dict`/`Condition.from_dict`, rejecting or coercing non-`str` values with a clear parse error handled at load time (already covered by `load_rule_file`'s per-file `try/except`). Additionally, wrap each rule's evaluation individually inside `evaluate_rules`'s loop (`try/except` per rule) so one malformed rule cannot abort evaluation of all others, and ensure the hook's fallback error path in `main()` never represents an implicit allow — e.g., have it explicitly return `permissionDecision: "ask"` or preserve a `deny` state when uncertain, rather than defaulting to allow.

### Proof of Concept
Unit/integration test plan:
1. Write a `.claude/hookify.malicious.local.md` file with frontmatter:
```
---
name: crash-rule
enabled: true
event: all
tool_matcher:
  - Bash
conditions:
  - field: command
    operator: contains
    pattern: x
action: warn
---
noop
```
and a second legitimate rule file `.claude/hookify.block-rm.local.md` with `action: block`, `tool_matcher: "*"`, and a condition matching `rm -rf`.
2. Feed a `PreToolUse` JSON payload to `plugins/hookify/hooks/pretooluse.py` via stdin with `tool_name: "Bash"`, `tool_input: {"command": "rm -rf /"}`.
3. Assert: process exit code is `0` (per `finally: sys.exit(0)`), but stdout JSON contains only `{"systemMessage": "Hookify error: 'list' object has no attribute 'split'"}` and **lacks** `hookSpecificOutput.permissionDecision == "deny"`, demonstrating that the `block-rm` rule's deny was silently suppressed by the unrelated malformed `crash-rule`.
4. Fuzz variant: parametrize `tool_matcher` (and other `Rule`/`Condition` fields) across `str`, `list`, `dict`, `int` types generated via the same multi-line YAML-list frontmatter shape, and assert that for every type that causes `RuleEngine.evaluate_rules` to raise, the hook's final JSON output never contains a `deny`/`block` decision for a co-loaded `block` rule that should have matched.
