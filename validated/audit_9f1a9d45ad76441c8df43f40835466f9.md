### Title
`pull_request action=reopened` cross-org `LabelCapturingHandler` label injection via `repository.owner.login` / `repository.full_name` divergence - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the request signature using `repository_owner`, which reads `params.dig('repository','owner','login')`. `LabelCapturingHandler` (and its siblings) instead resolve the actual `Repository`/stack to mutate using `params.repository.full_name`, parsed independently via `Repository.from_github_repo_name`. These two fields are never checked for consistency, so an attacker who controls a GitHub org/repo with no configured `webhook_secret` can forge a payload where `owner.login` names their own no-secret org (making `verify_webhook_signature` return `true` unconditionally) while `full_name` names an entirely different, victim-owned repository.

### Finding Description
The broken binding: the code implicitly assumes `params.repository.owner.login == owner(params.repository.full_name)`, but nothing enforces this equality.

- `WebhooksController#verify_signature` picks the app via `Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(sig, raw_post)`, and `repository_owner` is `params.dig('repository','owner','login')`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is configured for that organization — i.e., any org with no configured secret authenticates any signature. [3](#0-2) 
- `LabelCapturingHandler#repository` resolves the repository to mutate purely from `params.repository.full_name`, independent of `owner.login`: [4](#0-3) 
- `Repository.from_github_repo_name` simply splits `full_name` on `/`, with no cross-check against the value used for signature verification: [5](#0-4) 
- The handler then finds the review stack by deterministic environment name `"pr#{params.number}"` (not tied to commit SHA at all for this handler) and persists attacker-supplied label names onto the victim's `PullRequest`: [6](#0-5) [7](#0-6) [8](#0-7) 

Exploit flow:
1. Attacker registers/owns a GitHub org `attacker-org` that is not configured in Shipit's github organizations config (or is configured with `webhook_secret` blank) — so `verify_webhook_signature` for that org always returns `true`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, body: `action: "reopened"`, `repository.owner.login: "attacker-org"`, `repository.full_name: "victim-org/victim-repo"`, `number: <existing victim review stack PR number>`, and `pull_request.labels: [{name: "MALICIOUS_ENV_KEY"}, ...]`.
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`; that app has no `webhook_secret`, so signature check passes trivially regardless of the actual HMAC value.
4. `LabelCapturingHandler` runs, resolves `Repository.from_github_repo_name("victim-org/victim-repo")` — the real victim repo — finds the review stack by `"pr#{number}"`, and calls `pull_request.update!(labels: [...])`, persisting attacker-chosen label names onto the victim's `PullRequest` record.
5. Those label names become uppercased environment-variable keys in the review stack's deploy environment (per `ReviewStack#env`, confirmed to exist by grep though full body wasn't retrieved before iteration limit was reached — **not fully verified**), which could inject or override environment variables consumed by deploy commands / `PTY.spawn`.

The commit-SHA-collision detail from the question is not required for the `LabelCapturingHandler` path — the stack lookup is by PR number/environment name, not commit SHA, so that portion of the question's premise does not additionally amplify this specific handler's write.

None of the listed guards prevent this: `drop_unhandled_event` only checks the event type is handled; `verify_signature` verifies against the wrong org's secret; there is no `ExplicitParameters` cross-field validation between `repository.owner.login` and `repository.full_name`; `force_github_authentication`/`User#authorized?`/`require_permission!` are not on the unauthenticated webhook path at all.

### Impact Explanation
An unprivileged attacker can write arbitrary label names onto any victim `Stack`'s `PullRequest` record for any repository whose review-stack PR number is guessable/known (`pr#{number}` is low-entropy), as long as they control (or can name) any GitHub org with no `webhook_secret` configured in the Shipit deployment. This is a payload from one repository (attacker-controlled, unauthenticated) mutating another repository's stack/PR state — matching the Critical "payload for one repository mutating another's stack" category. The downstream effect (label names becoming env var keys, per the question) could extend to environment-variable injection into deploy tasks, but that final hop through `ReviewStack#env` was not fully confirmed within the available investigation budget.

### Likelihood Explanation
Preconditions: the Shipit deployment must have at least one GitHub organization configured without a `webhook_secret` (or the attacker must otherwise control an org whose secret can be leaked/guessed — out of scope here, but "no secret configured" is a plausible/common misconfiguration since `verify_webhook_signature` explicitly supports secret-less orgs as a fallback). The attacker needs no Shipit credentials, no GitHub App key, and only needs to know/guess the target `full_name` and PR number. This is fully repeatable and scriptable against arbitrary repositories/stacks that share this Shipit instance.

### Recommendation
Cross-check that the organization used to select/verify the webhook signature matches the organization portion of `repository.full_name` (and reject if they diverge) before dispatching to handlers; alternatively, require every configured org to have a mandatory `webhook_secret` and fail closed (rather than defaulting to `true`) when no secret is configured, and derive `repository_owner` used for signature verification consistently from the same field the handlers use to resolve the target repository.

### Proof of Concept
minitest plan (under `test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/label_capturing_handler_test.rb`):
1. Configure `Shipit.github_organizations` (or equivalent) with `attacker-org` having no `webhook_secret`, and `victim-org` having a real `webhook_secret`.
2. Create `victim_repo = Repository.create!(owner: "victim-org", name: "victim-repo")`, a `ReviewStack` under it with `environment: "pr42"`, and its `PullRequest` with `labels: []`.
3. Assert the binding before the request: `victim_repo.review_stacks.find_by(environment: "pr42").pull_request.labels == []`.
4. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, JSON body: `{"action":"reopened","number":42,"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"pull_request":{...,"labels":[{"name":"INJECTED"}]},"sender":{"login":"attacker"}}`.
5. Assert response is `200 OK` (signature check passed despite wrong/garbage signature, because it validated against `attacker-org`'s absent secret).
6. Assert the binding after: `victim_repo.review_stacks.find_by(environment: "pr42").pull_request.reload.labels == ["INJECTED"]`, proving a payload authenticated under `attacker-org` mutated `victim-org`'s stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
