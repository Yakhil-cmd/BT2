### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while handlers act on the unbound `repository.full_name` field, breaking the org-authenticates ≠ repo-written binding - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate an inbound webhook based on `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), but every downstream `Handler` (e.g. `Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the target repository/stack from the sibling field `payload.dig('repository','full_name')`. These two payload fields are never checked for consistency, so the value that determines *which secret validates the request* is not the value that determines *which repository is written to*.

### Finding Description
Shipit supports multiple GitHub organizations, each configured with its own GitHub App and its own `webhook_secret` [1](#0-0) . Signature verification in the controller is:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The signature is checked with `HMAC(secret_for_org_X, raw_body)` where `org_X` is read purely from `repository.owner.login` in the JSON body [3](#0-2) .

Once verification succeeds, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw payload* to handlers [4](#0-3) . Every handler that touches a repository resolves it independently via:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`repository.owner.login` and `repository.full_name` are two independent strings in the JSON body — nothing in the controller or the `ExplicitParameters` schemas (see `PushHandler`, `CheckSuiteHandler`) enforces that `full_name`'s owner segment matches `owner.login` [6](#0-5) [7](#0-6) .

**Binding that should hold:** `organization_used_to_select_verifying_secret == organization_that_owns_the_repository_the_handler_mutates`.

**Before the attack:** for a legitimate GitHub-originated webhook, GitHub itself guarantees `repository.owner.login` and the owner segment of `repository.full_name` refer to the same repository, so the binding holds implicitly.

**After the attack:** an operator who legitimately controls their own GitHub App installation on `org-attacker` (and therefore genuinely knows `org-attacker`'s `webhook_secret`, which Shipit's admin configured for them in `Shipit.github_apps`/`Shipit.app` per-organization config) can send a POST to `/webhooks` with:
- `repository.owner.login = "org-attacker"` (or `organization.login`) — used only for secret selection and passes verification because they know that secret,
- `repository.full_name = "org-victim/some-repo"` — used by every handler to select the actual `Stack`/`Repository` to mutate.

Because the two fields are never cross-checked, the request is accepted as authentic and dispatched with a `repository.full_name` pointing at a repository/organization the sender does not administer.

### Impact Explanation
Depending on the event type this crosses a hard organizational boundary using another organization's identity:
- `push` → `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` on stacks belonging to `org-victim/some-repo`, forcing the victim's stack to sync/deploy against an attacker-chosen SHA/branch state, i.e. an unauthorized deploy trigger for a repository the attacker's org has no relationship to [8](#0-7) .
- `check_suite` → forces `schedule_refresh_check_runs!` on the victim's commits [9](#0-8) .
- `status` → `StatusHandler` looks up commits purely `by sha` globally (no repository scoping at all) and calls `commit.create_status_from_github!(params)`, letting a request "authenticated" as `org-attacker` write arbitrary CI status/state onto any commit sha in the system, regardless of owning repository [10](#0-9) .

This is a cross-repository/cross-organization write performed by an entity that only proved control of a different, unrelated organization's webhook secret — this matches the "cross-repository writes" / "unauthorized deploy" Critical impact criteria, since it enables triggering deploys and manipulating commit status state on a stack the caller does not own.

### Likelihood Explanation
Requires only that Shipit be configured for multiple GitHub organizations/apps (a documented, normal multi-tenant deployment, see `docs/setup.md` App-per-org guidance) and that the attacker administers one legitimate org's GitHub App with its own webhook secret — no session, `ApiClient` token, or the victim org's `webhook_secret` is needed. Crafting the payload is trivial (a normal HTTP POST with a valid HMAC of the attacker's own secret). This is a realistic, low-effort path for any org onboarded onto a shared Shipit instance to attack sibling organizations/repos.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), require that the owner segment of `repository.full_name` (and `organization.login` if present) matches `repository.owner.login`/the organization used to select the verifying secret, and reject the request (422) on mismatch before dispatching to any handler. Alternatively, derive the GitHub App/secret from `repository.full_name`'s owner segment consistently and use that same resolved value everywhere handlers key off, so a single canonical, signature-covered field determines both the secret used to verify and the repository written to.

### Proof of Concept
1. Configure two organizations in Shipit's GitHub App config, `org-attacker` and `org-victim`, each with a distinct `webhook_secret`, and create a `Stack` for `org-victim/some-repo`.
2. As the operator of `org-attacker`'s GitHub App, construct a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/some-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(org-attacker_webhook_secret, raw_body)` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` selects `Shipit.github(organization: "org-attacker")`, verifies successfully using the attacker's own secret [11](#0-10) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-victim/some-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` [8](#0-7) , causing `org-victim`'s stack to sync against a SHA chosen entirely by the attacker, despite the attacker never having proven control of `org-victim`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end
