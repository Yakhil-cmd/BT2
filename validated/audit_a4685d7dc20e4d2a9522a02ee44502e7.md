### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` with no join or filter on the webhook's `repository`/organization, so a validly-signed `status` webhook from repository B can write a status onto a `Commit` row that actually belongs to Stack A's repository, as long as the two rows share a `sha`. Because git commit SHAs are pure content hashes with no repository binding, an attacker who fully controls a commit's content can reproduce the identical SHA in two different repositories they can push to, defeating the intended binding "repo whose CI produced status == repo whose merge request consumes it."

### Finding Description
The broken binding, stated explicitly: the code implicitly assumes
`payload.repository.full_name == commit.stack.repository.full_name`
for every `Commit` row updated by a `status` event, but this equality is never checked.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies that the raw payload was signed by the GitHub App/webhook secret configured for `repository_owner` (`params.dig('repository','owner','login')`). This proves the payload really originated from GitHub for *that org's* repository — it says nothing about which `Commit` rows in Shipit's database the `sha` inside the payload may also match.
2. `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` (`app/models/shipit/webhooks.rb:19`).
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This query is **global**, not scoped to the stack/repository named in the webhook payload. Any `Commit` row in any `Stack`/repository sharing that `sha` gets a new `Status` record.
4. `Commit#create_status_from_github!` → `#add_status` (`app/models/shipit/commit.rb:365-386`) persists the status and, on a state transition to `pending`/`success`, calls `stack.schedule_merges`, enqueuing `ProcessMergeRequestsJob` for **that commit's own stack** — i.e., for Stack A, even though the webhook came from repo B. [1](#0-0) 

Root cause: SHA is treated as a globally unique, repository-scoped key, but a git commit SHA is a content hash of tree/parents/author/committer/message — it carries no information about which repository stores it. An attacker who authors a commit fully controls all of these fields, so they can push the **identical commit object** (identical SHA) into two different repositories they control push access to: (a) their real PR branch on the repo backing Stack A, and (b) any other repository of theirs that is *also* onboarded as a Shipit stack (Stack B), enabling them to legitimately obtain a GitHub-signed `status` webhook for that exact SHA from repo B (e.g. by using their own CI/Actions or the GitHub Status API on their own repo).

Exploit flow:
1. Attacker opens a normal PR against Stack A's repo with commit `C` (attacker fully authors `C`, so its SHA is fully attacker-determined by fixing tree/parents/timestamps/message).
2. Attacker pushes the byte-identical commit `C` (same SHA) into repo B, a separate repository they control that is already registered as a Shipit stack (Stack B).
3. Attacker (or their own CI) posts a `success` status for `C` in repo B via the ordinary GitHub API — GitHub emits a real, correctly signed `status` webhook naming repo B.
4. `verify_signature` passes (correct signature for repo B's org).
5. `StatusHandler#process` matches `Commit.where(sha: 'C')`, which returns **both** Stack B's row and Stack A's row for the same SHA, and calls `create_status_from_github!` on both — writing a fabricated success `Status` onto Stack A's commit and triggering `stack.schedule_merges` for Stack A.
6. `ProcessMergeRequestsJob#perform` (`app/jobs/shipit/process_merge_requests_job.rb`) subsequently calls `merge_request.refresh!`, which re-fetches real statuses from Stack A's real GitHub repo. If Stack A's real CI has not yet reported (or if the forged `context` is one the real CI never emits, e.g. a required check name copied by the attacker), the injected `Status` row remains in `head.statuses_and_check_runs` and can flip `MergeRequest#all_status_checks_passed?` (`app/models/shipit/merge_request.rb:193-197`) to `true` before the genuine CI result exists, letting `merge!` fire prematurely.

Existing guards do not stop this: `verify_signature` only authenticates the *sender org*, not the *sha-to-stack binding*; `ExplicitParameters` (the `params do ... end` block) only validates payload shape, not repository ownership of the sha; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
An attacker can write a `Status` record into an arbitrary Stack's `Commit` for any SHA whose content they can reproduce (i.e., any commit they author), without ever touching Stack A's repository, its webhook secret, or holding any Shipit session/API token. This is a cross-tenant write: "a payload for one repository mutating another's stack/commit," matching the **Critical** impact category (unauthorized data affecting merge decisions across stacks). Repeatable against any Stack whose commits the attacker can reproduce content for, and blast radius spans every stack sharing the Shipit instance, since the SHA space is entirely attacker-chosen and the query has zero repository filter.

### Likelihood Explanation
Preconditions: the attacker needs (a) an onboarded, attacker-controlled repository already registered as a second Shipit stack (Stack B) — feasible in any org that lets any member add/track their own fork or scratch repo as a stack, a very common Shipit deployment pattern — and (b) the ability to author a commit and push the identical object into both repos, which is trivial since SHA computation is fully deterministic from content the attacker writes. No Shipit or GitHub secret material is required; only ordinary GitHub write access to a repo the attacker owns. This makes the attack cheap, deterministic (no cryptographic collision needed), and repeatable at will.

### Recommendation
Scope the `StatusHandler` lookup to commits belonging to stacks whose `repository` matches the webhook's `repository.full_name`/`owner`, e.g.:
```ruby
def process
  Commit.joins(:stack).merge(Stack.where(repository: Repository.from_github_repo_name(params.name)))
        .where(sha: params.sha)
        .each { |commit| commit.create_status_from_github!(params) }
end
```
or otherwise join through `stack.repository` and reject/ignore commits whose stack's repository doesn't match the payload's repository before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook from repo B cannot write a status onto a commit belonging to stack A's repo" do
  stack_a = shipit_stacks(:shipit)          # repo A
  stack_b = shipit_stacks(:cyclimse)        # repo B, different repository

  shared_sha = '1234567890abcdef1234567890abcdef12345678'
  commit_a = stack_a.commits.create!(sha: shared_sha, message: 'x', author: shipit_users(:walrus))
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'x', author: shipit_users(:walrus))

  merge_request = stack_a.merge_requests.create!(number: 999, head: commit_a, merge_status: 'pending')

  # binding under test, before
  assert_equal stack_a.repository.full_name, merge_request.stack.repository.full_name
  refute_predicate merge_request, :all_status_checks_passed?

  payload = ActionController::Parameters.new(
    sha: shared_sha, state: 'success', context: 'ci/travis',
    repository: { full_name: stack_b.repository.full_name, owner: { login: stack_b.repository.owner } }
  )

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload) # simulate already-verified, signed webhook from repo B

  commit_a.reload
  assert_predicate commit_a, :success?      # status leaked onto stack A's commit
  assert merge_request.reload.all_status_checks_passed? # binding is broken: repo B's CI unlocked stack A's merge
end
```
This demonstrates the write occurring for stack A's `Commit` from a payload whose `repository` is stack B's, with no live GitHub calls, confirming the equality `payload.repository == commit.stack.repository` is violated.
