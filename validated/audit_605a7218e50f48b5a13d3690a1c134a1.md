### Title
Cross-repository status forgery via organization/repository binding mismatch in webhook signature verification - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify an inbound webhook using the *organization* derived from the payload (`repository.owner.login`, falling back to `organization.login`), but the `status` event handler that actually writes state does not check that organization/repository at all — it looks up the target `Commit` purely by `sha` across the entire Shipit instance. In a multi-tenant Shipit deployment (multiple GitHub orgs, each with its own configured `webhook_secret`), this breaks the intended binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` computes the signing organization from the payload and verifies the signature with that organization's secret: [2](#0-1) [3](#0-2) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization from `secrets.github`: [1](#0-0) 

Once the signature check passes (proving only that the request was legitimately signed for *some* organization configured on this instance), the raw JSON `params` are dispatched to the registered handler for the event type: [4](#0-3) 

For `status` events, `Handlers::StatusHandler#process` does not use the generic `Handler#stacks` scoping helper (which resolves via `Repository.from_github_repo_name`); instead it queries `Commit` globally by SHA, with no repository or organization filter whatsoever: [5](#0-4) 

This writes a `Status` record on whatever commit(s) match that SHA anywhere in the Shipit database, via `Commit#create_status_from_github!`: [6](#0-5) 

The equality that should hold is: *organization whose secret validated the signature == owner of the repository whose commit status is mutated*. Instead the code only guarantees "signature is valid for organization X," while the actual write target is "any commit anywhere with SHA=S," decoupling the two. An operator/admin of organization X's onboarded repositories can therefore deliver a validly-signed `status` webhook (signed with X's own configured `webhook_secret`) whose `sha` value targets a commit belonging to a completely unrelated organization Y's stack, and have Shipit accept and persist that status as if GitHub itself reported it for Y.

### Impact Explanation
A forged/favorable status (e.g. `state: success` for a required CI context) written onto a victim stack's commit can make `Commit#deployable?` return true and, if the victim stack has continuous deployment enabled, trigger `schedule_continuous_delivery` → `ContinuousDeliveryJob`, resulting in an **unauthorized deploy** of a stack the attacker does not own or have credentials for: [7](#0-6) [8](#0-7) . This satisfies the "unauthorized deploy" Critical-impact criterion, since it lets an attacker who legitimately controls (or has webhook-signing knowledge for) one organization on a shared/multi-tenant Shipit instance manipulate CI-gating state for a different organization's stacks.

### Likelihood Explanation
Exploitation requires the attacker to be able to produce a validly HMAC-signed webhook for *some* organization configured on the instance — which is realistic for a self-hosted, multi-tenant Shipit deployment where multiple independent GitHub organizations/teams share one instance, each with the ability to trigger real GitHub events (pushes, status updates) from their own repos that GitHub signs and forwards. The attacker also needs to know or guess the target commit's SHA, which is generally public information on GitHub. The `push` handler is less exposed (it does scope via `Repository.from_github_repo_name`), but `StatusHandler` has no such scoping, making this the most direct path.

### Recommendation
In `Handlers::StatusHandler#process` (and any other handler), scope the `Commit` lookup to the repository identified in the payload (via `Repository.from_github_repo_name(repository_name)` / `stacks`) rather than matching by `sha` alone, so a status update can only affect commits belonging to the same repository whose organization was used to verify the signature. Additionally, `WebhooksController#verify_signature` should assert that the verified organization matches the repository's actual owner (not just be used to pick which secret to try) before any handler runs.

### Proof of Concept
1. Deployment hosts multiple orgs: `org-attacker` and `org-victim`, each configured in `secrets.github` with distinct `webhook_secret`s, both onboarded as stacks in the same Shipit instance.
2. Attacker owns/administers a repo under `org-attacker` and can trigger GitHub to send a real, validly-signed `status` webhook to Shipit's `/github/webhooks` endpoint (e.g. via any legitimate CI integration on their own repo).
3. Attacker crafts (or influences, e.g. via a custom third-party status integration they control on their own repo) the webhook body's `sha` field to equal the SHA of a specific commit that exists in `org-victim`'s stack (SHAs are public via GitHub's API/UI), with `state: "success"` and `context` matching one of `org-victim`'s `ci.require` contexts.
4. `WebhooksController#verify_signature` resolves `repository_owner` from the payload's own `repository.owner.login` (= `org-attacker`) and verifies successfully using `org-attacker`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the `org-victim` commit (matched purely by SHA, with no ownership check), calling `create_status_from_github!`, which marks it `success` for `org-victim`'s stack.
6. If `org-victim`'s stack has continuous deployment enabled and this satisfies all required statuses, `ContinuousDeliveryJob` deploys the commit automatically — an unauthorized deploy triggered entirely from `org-attacker`'s webhook credentials.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
