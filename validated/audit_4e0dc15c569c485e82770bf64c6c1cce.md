### Title
Cross-organization webhook forgery via mismatched signature-verification key and repository-name binding - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub webhook secret to verify the incoming signature against using `repository_owner`, which is read directly from the untrusted, not-yet-verified JSON payload (`repository.owner.login`, falling back to `organization.login`). The handler that subsequently *acts* on the webhook, `Shipit::Webhooks::Handlers::Handler#repository_name`, instead reads `repository.full_name` from the same payload to decide which `Stack`/`Repository` to operate on. In Shipit's multi-tenant GitHub App mode (`Shipit.github_organizations`, `Shipit.github_app_config`), each organization has its own independently-configured `webhook_secret`. Nothing ties the organization whose secret validated the signature to the repository that is actually mutated.

### Finding Description
Shipit supports hosting multiple GitHub organizations, each with a distinct `webhook_secret` under `secrets.github.<org>.webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's app/secret to check against based purely on the attacker-supplied `repository_owner` field, computed *before* any signature check has taken place: [2](#0-1) [3](#0-2) 

Once `verify_signature` passes, `create` dispatches the full raw payload to handlers: [4](#0-3) 

Every handler resolves the target stacks using a *different* field of the same payload — `repository.full_name` — not the organization login used for verification: [5](#0-4) 

Because the HMAC is computed over the entire `request.raw_post`, it does protect payload integrity in general — but the *choice of which secret to check it against* is controlled by an attacker-writable field (`repository.owner.login`/`organization.login`) that is independent of the field the handlers trust for the target repository (`repository.full_name`). This breaks the equality:

`organization authenticated (repository_owner, selects webhook_secret) == repository written (repository.full_name, selects Stack/Repository)`

An attacker who legitimately administers their own GitHub organization/App installation on the same Shipit instance (a normal, unprivileged tenant, not requiring theft of any other org's secret, `GITHUB_TOKEN`, or a Shipit session) knows their own organization's genuine `webhook_secret` (GitHub gives it to whoever configures the App). They can craft an arbitrary payload, set `repository.owner.login` to their own org (so `verify_signature` selects their own valid secret) while setting `repository.full_name` to any other tracked repository (e.g., `"OrgA/private-repo"`), and self-sign it with their own org's secret. The signature check succeeds because it is checked against the attacker's own genuine secret, yet the handler acts on the victim repository named in `full_name`.

### Impact Explanation
This lets a tenant with access to only one organization's webhook secret forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`) against *any* repository/stack tracked by the shared Shipit instance:
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha: ...)` for the victim stack's branch [6](#0-5) , forcing a resync from GitHub, potentially affecting continuous-deployment triggers on a stack the attacker does not own.
- `StatusHandler#process` writes arbitrary commit statuses (`state`, `context`, `description`, `target_url`) onto any commit SHA already known to Shipit [7](#0-6) , which can be used to spoof a passing CI status (`ci.require` context) on a victim's stack, bypassing the CI gate that guards deploys/merges — an unauthorized-deploy-enabling primitive.

This crosses a real authorization boundary (a tenant acting on another organization's repository state) without needing that organization's secret, satisfying the "unauthorized deploy" / cross-repository-write impact class.

### Likelihood Explanation
Requires only that the Shipit deployment is configured in multi-organization mode (`secrets.github` keyed by multiple orgs, per `Shipit.github_organizations`) and that the attacker legitimately controls one tenant organization's webhook secret — a normal, unprivileged capability granted to any organization onboarded onto the shared instance, not a privileged Shipit account or stolen secret. No user interaction or session is required; it's a single crafted HTTP POST to the public `/github/webhooks` endpoint.

### Recommendation
After `verify_signature` succeeds, re-derive the organization from the *same* field the handlers use to select the target repository (`repository.full_name`'s owner segment, or `repository.owner.login` compared against `full_name`), and reject the request if they diverge. Alternatively, have handlers scope `Repository.from_github_repo_name` lookups by the verified `repository_owner`/organization rather than trusting `full_name` independently, ensuring the field verified by the signature-selection logic and the field used to select the mutated resource are the same.

### Proof of Concept
1. Deploy Shipit in multi-org mode with two organizations configured, `orgA` (victim, tracks stack `orgA/app`) and `orgC` (attacker-administered, webhook secret known to attacker).
2. Attacker builds payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already known to Shipit>",
  "repository": { "owner": { "login": "orgC" }, "full_name": "orgA/app" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgC_webhook_secret, raw_body)` and sends `POST /github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'orgC')`, verifies successfully using `orgC`'s own genuine secret [8](#0-7) .
5. `PushHandler` resolves stacks via `Repository.from_github_repo_name('orgA/app')` [5](#0-4)  and triggers `sync_github` on the victim's stack, despite the attacker never possessing `orgA`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
