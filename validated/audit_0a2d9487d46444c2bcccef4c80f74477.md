### Title
Webhook Signature Verified Against Payload's `repository.owner.login`, but Handlers Act on the Unverified `repository.full_name` Field — Cross-Organization Stack Sync/Deploy Trigger - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to HMAC-validate the request body based on `repository_owner`, which is read from the payload's `repository.owner.login` field. [1](#0-0) [2](#0-1)  However, every webhook handler resolves the `Repository`/`Stack` to act on using a **different** payload field, `repository.full_name`, via `Handler#repository_name`. [3](#0-2)  Since Shipit is multi-tenant (a distinct `github.webhook_secret` per organization, per `docs/setup.md`), any organization admin who legitimately installs the Shipit GitHub App on their own org knows their own `webhook_secret` and can therefore forge a signature that Shipit accepts, while independently controlling the `repository.full_name` field to point at a victim organization's repository.

### Finding Description
The equality the engine is supposed to preserve is:

`organization authenticated by verify_webhook_signature == organization owning the repository/stack that the handler mutates`

Before/after the attack:
- **Before**: for genuine GitHub-originated payloads, `repository.owner.login` and `repository.full_name`'s owner segment are always identical, so the binding holds implicitly.
- **After**: an attacker who controls a legitimately configured organization ("attacker-org", with its own `github.webhook_secret` known to them) crafts a raw POST body directly to `/webhooks` with:
  - `repository.owner.login = "attacker-org"` (so `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and successfully verifies the HMAC using a secret the attacker legitimately knows) [1](#0-0) 
  - `repository.full_name = "victim-org/victim-repo"` (an unrelated, unverified field)
  - `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, body)`

`verify_signature` passes because the signature is valid for the organization the attacker actually controls. [4](#0-3)  Execution then proceeds to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [5](#0-4)  For a `push` event, `PushHandler#process` calls `stacks`, which resolves `Repository.from_github_repo_name(repository_name)` using the forged `full_name`, i.e., the victim repository, and invokes `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack. [6](#0-5) [3](#0-2) 

The root cause is that `repository_owner`, the value gating cryptographic authentication, is never cross-checked against `repository_name`, the value driving which `Repository`/`Stack` record is mutated — these are two independent fields of the same untrusted JSON body, and only one of them is covered by the signature check's *organization selection logic* (the HMAC covers the whole body's bytes, but it is computed with a secret keyed off a field the attacker also controls and can set to their own, legitimately-known organization).

### Impact Explanation
This allows any organization onboarded onto a shared/multi-tenant Shipit instance (i.e., any org admin who installed the Shipit GitHub App on their own org and therefore knows their own webhook secret) to trigger `stack.sync_github` for stacks belonging to a completely different, victim organization/repository, without ever needing that victim's webhook secret. Depending on stack configuration (e.g., `continuous_deployment` enabled), a forced GitHub sync can result in new commits being pulled into Shipit's tracked state and can be a precursor to triggering an unauthorized deploy pipeline for the victim's stack — a cross-repository write driven entirely by attacker-controlled, unauthenticated payload fields. This matches the "cross-repository writes" / "unauthorized deploy" Critical impact class.

### Likelihood Explanation
Exploitation requires only that the attacker controls (or can register) one organization on the shared Shipit instance and knows that organization's own configured `webhook_secret` — a credential they legitimately possess by design, not a privileged secret of the victim. No GitHub-side trigger is needed since the attacker can POST directly to Shipit's public `/webhooks` endpoint. This is a low-effort, directly reachable attack once multi-organization onboarding is in place.

### Recommendation
In `Handler#repository_name`/`stacks`, and in `WebhooksController#repository_owner`, derive both the signature-verification organization and the acted-upon repository from the same, single trusted source (e.g., parse `full_name` once, verify its owner segment matches the organization whose secret validated the signature, or resolve `Repository` and confirm `repository.owner == verified_organization` before invoking any handler).

### Proof of Concept
1. Attacker admin installs the Shipit GitHub App on `attacker-org`, obtaining/knowing `github.webhook_secret` for `attacker-org` as configured in Shipit's `secrets.yml`.
2. Attacker crafts:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC-SHA1(attacker-org_webhook_secret, body)` and sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<computed>
<body>
```
4. `verify_signature` resolves `repository_owner = "attacker-org"`, loads that org's app, and successfully verifies the signature. [1](#0-0) 
5. `PushHandler` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker chosen sha>")` on victim's stacks. [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
