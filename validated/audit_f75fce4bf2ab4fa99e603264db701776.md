### Title
Webhook signature verification keys off an unverified `repository.owner.login`/`organization.login` field while every event handler dispatches on the sibling `repository.full_name` field of the same untrusted JSON body, letting an attacker forge Shipit-consumed GitHub events for any repository as long as one configured GitHub App has no `webhook_secret` set - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `Shipit::GitHubApp` (and therefore which HMAC `webhook_secret`) to verify the incoming payload against by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated request body, before any signature check has run. [1](#0-0)  Every event handler that actually mutates state, however, resolves its target `Repository`/`Stack` from a different field of the same JSON object: `repository.full_name`. [2](#0-1)  Because the two fields are never checked for consistency, and because `verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured, an attacker can pick any configured-but-secret-less organization for `repository.owner.login` to bypass signature verification entirely while pointing `repository.full_name` at a completely different (secret-protected) organization's repository.

### Finding Description
The trust binding that should hold is: *"the GitHub organization whose secret validated this payload" == "the repository/organization the payload's handlers will act on."* This engine breaks that binding.

1. `verify_signature` computes the app/secret to check against purely from attacker-controlled JSON, prior to any cryptographic check:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

2. `GitHubApp#verify_webhook_signature` bypasses verification whenever `webhook_secret` is blank for that app config:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3)  `webhook_secret` is an optional key — the shipped example configs explicitly leave it `nil` by default (`webhook_secret: # nil`). [5](#0-4)  In a multi-GitHub-App deployment (a supported configuration, documented and tested via `secrets_double_github_app.yml`), it's plausible for one organization's App entry to be configured without a webhook secret while another organization/stack that Shipit tracks does have one. [6](#0-5) 

3. Once `verify_signature` passes (`head(422)` not called), `create` re-parses the same raw body and dispatches it, unmodified, to every registered handler for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [7](#0-6) 

4. All state-changing handlers (`PushHandler`, `StatusHandler`, the `PullRequest::*Handler`s, etc.) resolve their target stack via `Base::Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a sibling field to the one used for signature-org selection, not the one actually verified:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

An attacker who knows (or can enumerate) that some organization configured in this Shipit instance has no `webhook_secret` can therefore craft a single JSON body where `repository.owner.login` = `"orgWithoutSecret"` (making `Shipit.github(organization: ...)` return the secret-less app, so `verify_webhook_signature` trivially returns `true`), while `repository.full_name` = `"victim-org/victim-repo"` (the real, secret-protected repository Shipit deploys). The forged payload passes `verify_signature` and is then processed by handlers as if it were a legitimately-signed event for the victim repository.

### Impact Explanation
This crosses exactly the boundary called out in scope: *"an organization that authenticated versus the repository that is written."* Concretely, an attacker with no session, no `ApiClient` token, and no knowledge of any real `webhook_secret` can:
- Inject forged commit statuses for arbitrary commits on a tracked stack via `StatusHandler#process` → `commit.create_status_from_github!`, which feeds into Shipit's CI/deployability gating used to decide whether a commit is safe to deploy. [8](#0-7) 
- Force `GithubSyncJob`/stack synchronization or PR/review-stack lifecycle transitions (open/reopen/label/merge-related state) for a repository the attacker does not control, using the resolved `Repository.from_github_repo_name(params.repository.full_name)` target. [9](#0-8) [10](#0-9) 

Manipulating gating commit statuses to make an un-reviewed/malicious commit appear "green" can enable an unauthorized deploy of that commit under continuous-deployment configurations, satisfying the Critical bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability depends entirely on operational configuration: the engine only becomes exploitable if (a) more than one GitHub organization/App is configured (a documented, supported, and tested layout) and (b) at least one of those configured organizations has no `webhook_secret` set — which is the documented default value in every shipped example configuration file. No attacker-held credential, session, or private key is needed; the only prerequisite is discoverable/likely-guessable knowledge of a secret-less org slug in a multi-org install, which is a realistic and not-implausible operational state given the default examples ship with `webhook_secret: # nil`.

### Recommendation
Verify the webhook signature using the same field that handlers use to resolve the write target (`repository.full_name`, or equivalently derive the verification org from the resolved `Repository`/`Stack`, not from a free-standing `repository.owner.login`/`organization.login` field read independently). Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is unset for an organization that is going to be used to authorize writes to other organizations' repositories — either require `webhook_secret` to be present for any multi-org configuration, or scope handler repository resolution strictly to the same organization value that passed signature verification (reject the event with 422 if `repository.full_name`'s owner segment does not match `repository_owner`).

### Proof of Concept
Assume `config/secrets.yml` configures two GitHub Apps: `OrgWithoutSecret` (no `webhook_secret`) and `VictimOrg` (has `webhook_secret` set, and owns a repo tracked by a Shipit `Stack`).

1. Attacker sends, unauthenticated, with any/garbage `X-Hub-Signature` header:
```
POST /github_webhooks
X-Github-Event: status
X-Hub-Signature: sha1=deadbeef

{
  "repository": { "owner": { "login": "OrgWithoutSecret" }, "full_name": "VictimOrg/victim-repo" },
  "sha": "<sha of a real commit on the victim stack>",
  "state": "success",
  "context": "ci/attacker-forged",
  "created_at": "2026-09-02T00:00:00Z"
}
```
2. `verify_signature` computes `repository_owner` = `"OrgWithoutSecret"`, loads that app's config, and calls `verify_webhook_signature`, which returns `true` immediately because that app has no `webhook_secret` (`return true unless webhook_secret`). [4](#0-3) 
3. `create` re-parses the body and dispatches it to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` — a commit belonging to `VictimOrg/victim-repo` — and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled `success` status for that commit, with no knowledge of `VictimOrg`'s real `webhook_secret`. [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
