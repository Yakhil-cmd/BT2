### Title
Unauthenticated cross-stack disclosure of deploy status via unscoped CCMenu token - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
### Finding Description
Shipit's CCMenu integration is designed to hand out a lightweight, unauthenticated-by-session, token-based URL that lets external CI radiators/status tools poll a *single* stack's build status. The binding that must hold is: **the stack a token authorises == the stack it can touch**. Two independent defects in this feature break that binding.

1. `CCMenuUrlController#client` mints/reuses the `ApiClient` that backs the shareable URL, but never scopes it to the stack the URL was generated for: [1](#0-0) 
`find_or_create_by!(creator: current_user, name: 'CCMenu Client')` is keyed only on `creator` + `name`, and `create_with(permissions: %w[read:stack])` never sets `stack:`. Because `stack_id` is never populated, `ApiClient#stack_id?` is false, so the base controller's own scoping helper (`stacks` → `Stack.all`) treats this client as authorised for *every* stack: [2](#0-1) 

2. Even if the client *were* stack-scoped, `CCMenuController` overrides the base `stack` accessor and bypasses the scoping entirely: [3](#0-2) 
It calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`, so `current_api_client.stack_id` is never consulted. `require_permission :read, :stack` only checks that the string `"read:stack"` is present in the client's `permissions` array via `ApiClient#check_permissions!`; it never checks which stack the permission applies to: [4](#0-3) 

Authentication for this controller is done purely via the `token` query parameter (no Shipit session, no organization membership check): [5](#0-4) 

### Impact Explanation
An attacker holding *any* valid CCMenu token (which is designed to be embedded in public dashboards, CI radiators, or README badges — the entire point of the feature) can replay it against `/services/api/*/ccmenu/<other_stack_id>?token=...` for any other stack in the Shipit installation and receive that stack's build/deploy/lock status, even for stacks they have no access to and never received a token for. This is an unauthenticated (token-only, no login/session) disclosure of stack deploy state — "unauthenticated read of stack state ... or deploy output" — which is explicitly a High severity outcome under this program's scope.

### Likelihood Explanation
Likelihood is high for anyone who already possesses one legitimately-issued CCMenu URL (a low bar, since these URLs are intended to be shared/embedded publicly by design). No privileged credentials, GitHub App secrets, or Shipit session are required — only substitution of the `stack_id` path segment in an otherwise valid, previously obtained token URL.

### Recommendation
- In `CCMenuUrlController#client`, scope the created/found `ApiClient` to the specific stack: include `stack:` in both the `find_or_create_by!` lookup and `create_with` attributes so each stack gets its own distinctly-scoped client/token.
- In `CCMenuController`, remove the private `stack` override and use the inherited, properly scoped `stacks.from_param!(params[:stack_id])` from `BaseController` so the `current_api_client.stack_id` restriction is enforced.

### Proof of Concept
1. User A (or a public CI radiator with no Shipit login) requests `GET /stacks/*id/ccmenu` for `stack_A`; `CCMenuUrlController#fetch` returns a URL like `https://shipit.example.com/services/api/stack_A/ccmenu?token=T`, backed by an `ApiClient` record with `permissions: ["read:stack"]` and `stack_id: nil` (bug 1).
2. Attacker takes token `T` and issues `GET /services/api/stack_B/ccmenu?token=T` for an unrelated `stack_B`.
3. `CCMenuController#authenticate_api_client` authenticates `T` successfully (`ApiClient.authenticate` only checks signature validity, not stack).
4. `require_permission :read, :stack` passes because `permissions` includes `"read:stack"` regardless of stack.
5. `CCMenuController#stack` resolves `stack_B` directly via `Stack.from_param!`, bypassing any stack scoping.
6. Response renders `stack_B`'s CCMenu XML (`lastBuildStatus`, `activity`, etc.), disclosing deploy/lock state of a stack the attacker was never authorised to view.
