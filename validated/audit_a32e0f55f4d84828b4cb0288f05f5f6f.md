### Title
Malicious route pool executes arbitrary contract code inside the caller's signed auth tree, draining unrelated wallet tokens - (File: contracts/swap-aggregator/src/program.rs)

### Summary
Analog of CVE-2020-14454 (redirection mishandled → attacker-chosen content executes in the victim's application context). The swap router executes whatever pool address a route payload names, with no venue allowlist. A rogue "pool" contract called as a route hop can issue `token.transfer(victim, attacker, ...)` for any token the victim holds; in transaction simulation that transfer is recorded as a child of the caller's own authorization entry, and if the caller signs the simulated tree, the host authorizes the theft. Reachable by an unprivileged address through `execute_strategy` and through controller strategy verbs (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) that forward a caller-supplied route.

### Finding Description
`Program::validate` in `contracts/swap-aggregator/src/program.rs` checks only structural properties of the packed route — opcode validity, index bounds against the asset registry, `Prev` links, split weights (lines 239–303). Nothing validates that a hop's `pool` address is a genuine, audited DEX pool. `dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs:34-40` then invokes the venue adapter against `hop.pool`, an address fully controlled by whoever crafted the route XDR.

The controller path grants the router only a single exact input transfer (`authorize_transfer_as_current` in `contracts/controller/src/strategies/swap.rs:34`), so the routed amount itself is bounded. But the venue call runs deeper in the same authorization tree rooted at the victim's `require_auth`. An attacker-deployed contract placed as a hop pool can therefore call `token::Client::transfer(&victim, &attacker, &amount)` on any Stellar asset contract. Simulation (recording mode) attaches that invocation as a sub-invocation of the victim's auth entry; when the victim signs the simulated tree, enforcing mode accepts it.

This is proven by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: a `RogueHopPool` named in the route transfers Alice's entire unrelated `wallet_token` balance to the attacker (lines 224–227), and the enforced-auth test shows the theft succeeds exactly when the signed tree includes the recorded rogue transfer (lines 259–268), while the honest root-only tree is refused by the host (lines 243–256). The threat model itself acknowledges the gap: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md`).

### Impact Explanation
Theft of user funds beyond the routed amount. The victim's loss is not bounded by `total_in`, the payload `min_out`, or the final account risk check — the rogue hop steals any token balance the victim's address holds (in the test, a 77,770-unit wallet token unrelated to the protocol). The swap still settles correctly (fair output is paid, risk gates pass), so on-chain nothing looks anomalous; only the extra child in the auth tree distinguishes the poisoned transaction.

### Likelihood Explanation
Requires a user to sign a route containing the attacker's pool and to accept the poisoned authorization tree produced by simulation — matching the CVE's user-interaction (UI:R) requirement. An attacker can distribute such routes through a malicious or compromised quote source/frontend, which is the same trust path users already rely on for route construction. No privileged access is needed: any address can deploy a `RogueHopPool` and craft a route XDR naming it, since `validate` enforces no allowlist. Mitigating factors (host rejects unsigned rogue children, careful clients decode routes) keep this at Medium rather than High.

### Recommendation
Enforce a venue/pool allowlist or pool-identity verification in `Program::validate` or per-venue adapters (e.g., verify Aquarius pools against the factory `get_pool`/`share_id` binding, as `assert_share_token` already does for LP legs) so a hop cannot target arbitrary contract code. Independently, clients should decode the signed auth tree and refuse any child beyond the single expected input transfer — but relying on client behavior leaves contract callers and `execute_strategy` users exposed, so the fix belongs on-chain.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

- `UnlistedPoolRouter::execute_strategy` (lines 39–47) invokes whatever `hop_pool` the payload names via `env.invoke_contract`, mirroring `dispatch_hop` dispatching on caller-supplied `hop.pool` with no allowlist.
- `RogueHopPool::swap` (lines 62–71) executes `token.transfer(victim → attacker, WALLET_BALANCE)` on an arbitrary token.
- `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (lines 194–227): after `mock_all_auths` simulation through `controller.swap_collateral`, the recorded auth tree contains the wallet-draining transfer as a child of Alice's own entry; `assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE)` confirms the theft.
- `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` (lines 229–268): signing the simulated (poisoned) tree authorizes the transfer; Alice's wallet goes to 0 while her position still receives the fair swap output, so the protocol-level checks all pass.
