### Title
`pull_request` webhook signature check uses `repository.owner.login` while `LabeledHandler` mutates the stack resolved from `repository.full_name` - cross-tenant forged event - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/org config to verify the HMAC signature using `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) , while `LabeledHandler#repository` resolves the actual repository/stack to mutate from the independent field `params.repository.full_name` [3](#0-2) . Because `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected org has no `webhook_secret` configured [4](#0-3) , an attacker can pick a no-secret org for `repository.owner.login` to trivially pass verification, then point `repository.full_name` at a victim org/repo whose secret was never checked, causing `LabeledHandler` to archive/unarchive the victim's review stack.

### Finding Description
The invariant that should hold is:
`org_used_to_verify_signature(params.repository.owner.login) == org_that_owns_mutated_repository(params.repository.full_name)`

Tracing the code shows these are two independently attacker-controlled JSON fields with no cross-check:

- `verify_signature` builds `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's config has no `webhook_secret` set, before ever computing/comparing an HMAC: `return true unless webhook_secret` [4](#0-3) .
- After signature "verification" passes, `WebhooksController#create` dispatches the raw parsed JSON body to the matched handlers, unchanged [5](#0-4) .
- `LabeledHandler#repository` resolves the actual repository to act on via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, a completely separate field from `repository.owner.login` [3](#0-2) .
- `LabeledHandler#handle` then calls `stack.archive!` or `stack.unarchive!` on the review stack derived from that repository [6](#0-5) .

Exploit flow: attacker crafts a `pull_request`/`labeled` JSON body where `repository.owner.login` = some org configured in `Shipit.github_teams`/app config with no `webhook_secret` set, and `repository.full_name` = `"victim-org/victim-repo"` (a real repo Shipit manages, with `review_stacks_enabled` and a provisioning label configured). The attacker sends this to `POST /webhooks` with the `X-Github-Event: pull_request` header and any `X-Hub-Signature` value (or none) — it is never checked because `webhook_secret` is blank for the org actually consulted. `verify_signature` passes, `LabeledHandler` runs against the victim's real stack and archives/unarchives it based on the label state the attacker also fully controls in the same forged payload (`pull_request.labels`, `pull_request.head`, etc., all attacker-supplied since this is an unauthenticated request with no real GitHub involved).

Existing guards do not catch this: `drop_unhandled_event` only checks event type presence [7](#0-6) ; there is no code anywhere that asserts `repository.owner.login`'s org matches the org portion of `repository.full_name`.

### Impact Explanation
An unprivileged internet requester can forge a `pull_request`/`labeled` webhook that mutates the review stack of an arbitrary victim repository/stack that they do not own or control, provided any org in the Shipit deployment's GitHub App config lacks a `webhook_secret`. This directly matches the rule's Critical category: "a payload for one repository mutating another's stack." The archive/unarchive action changes stack provisioning/deploy-eligible state; combined with `merge_queue_enabled` stacks, this stack-state flip can influence whether `MergeRequest`/merge-queue processing proceeds for that stack, i.e., an attacker-triggered unauthorized change to deploy/merge pipeline behavior of a stack they don't own. The attack is repeatable against any victim repository/full_name string, at zero cost, from any unauthenticated client.

### Likelihood Explanation
Preconditions:
1. At least one org configured in Shipit's GitHub App config without a `webhook_secret` (the "no-secret org" named in the question) — a realistic/common misconfiguration for e.g. dev/staging or freshly onboarded orgs.
2. Victim stack has `review_stacks_enabled` and a provisioning label configured (feature must be in use), and, per the question, `merge_queue_enabled: true`.

Given these, the attack requires only crafting one JSON POST with attacker-chosen field values — no GitHub account interaction, no secrets, no privileged Shipit role. This is trivially repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature`, require a non-blank `webhook_secret` for the resolved org and reject the request (422) if verification cannot be cryptographically evaluated instead of treating a missing secret as automatic success. Additionally, after signature verification, enforce that the org derived from `repository.full_name` (used by the handlers) matches the org used for `verify_signature` (`repository.owner.login`), rejecting mismatches before dispatching to any handler.

### Proof of Concept
Minitest plan (under `test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/labeled_handler_test.rb`):

1. Configure two orgs in `Shipit.github_teams`/app config: `no_secret_org` (no `webhook_secret`) and `victim_org` (with a real `webhook_secret`, unused/uncompromised).
2. Create a `victim_org/victim-repo` `Shipit::Repository` with `review_stacks_enabled: true` and a provisioning label configured; create an associated `Stack` with `merge_queue_enabled: true` and an active review stack currently archived (or unarchived, whichever is the "before" state).
3. Assert binding before request: `stack.archived?` == known baseline value (e.g. `false`).
4. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or a garbage one), and JSON body where `repository.owner.login = "no_secret_org"` and `repository.full_name = "victim_org/victim-repo"`, `action = "labeled"`, `pull_request.state = "open"`, and `pull_request.labels` containing the provisioning label to force `archive?`/`unarchive?` to trigger a transition.
5. Assert response status is `200 OK` (signature check passed) — proving verification used `no_secret_org`, not `victim_org`.
6. Reload `stack` and assert `stack.archived?` flipped to the opposite of the baseline — proving `LabeledHandler` mutated the victim stack despite the signature never having been checked against `victim_org`'s real secret.
7. (Optional amplification) With `merge_queue_enabled: true` and a green head commit already queued, assert that the queue advances / `merge!` is invoked as a consequence of the state flip, per `Shipit::MergeRequest`/`MergeStatusController` logic.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
