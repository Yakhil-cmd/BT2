### Title
Webhook organization-verification uses query-string-influenced `params` while event processing uses the raw JSON body, allowing signature-scope confusion across GitHub organizations - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects **which** GitHub App/organization's `webhook_secret` to verify the HMAC signature against by reading `repository_owner` from `params` (Rails' merged parameters, which include the URL query string), while the `create` action that actually dispatches the event to handlers re-parses `JSON.parse(request.raw_post)` — a value the query string cannot influence. This is the same class of bug as the reported `_transferThere()` issue: one code path derives a value from a source that is *not* the value that ultimately gets acted upon, breaking the binding between "what was verified" and "what gets written."

### Finding Description [1](#0-0) 
```

  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```
The event handlers act strictly on the JSON body parsed directly from `request.raw_post`. [2](#0-1) 
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
...
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`repository_owner` is computed from the controller's `params` method (an `ActionController::Parameters`), not from `request.raw_post`. In Rails, `ActionDispatch::Http::Parameters#parameters` merges `query_parameters` **over** `request_parameters` (the parsed body) for identical top-level keys, then merges `path_parameters` on top. This means an attacker-supplied query string such as `?repository[owner][login]=SomeOrg` overrides the `repository` key that would otherwise come from the JSON body for the purpose of selecting which organization's `GitHubApp`/`webhook_secret` is used in `verify_signature`.

`Shipit::GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization has no `webhook_secret` configured — which the setup docs explicitly describe as optional (`docs/setup.md` — “Webhook secret (optional)”): [3](#0-2) 
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret

  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'

  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```
Multi-organization Shipit deployments configure a separate `GitHubApp` (and separate `webhook_secret`) per organization, resolved via `Shipit.github(organization:)`: [4](#0-3) 

By choosing `repository_owner` (via the query string) to point at any organization in the deployment whose `webhook_secret` is blank/unset, an unauthenticated caller passes `verify_signature` unconditionally — even though the *real* JSON body sent to `create` targets a completely different organization/repository whose GitHub App is fully secured with its own secret.

**Binding broken:** `organization authenticated in verify_signature (params, query-string-controllable)` ≠ `organization/repository actually written by the handler (JSON.parse(request.raw_post))`.

Downstream handlers act on the raw-body-derived payload without re-checking that its `repository`/`organization` matches the organization that was authenticated: [5](#0-4) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
and, more critically, `MembershipHandler`, which creates/mutates `Team` membership directly from the (unverified-for-that-org) payload: [6](#0-5) 
```
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)

  case params.action
  when 'added'
    team.add_member(member)
  when 'removed'
    team.members.delete(member)
  ...
```
`Team` membership directly feeds `User#authorized?`, which gates access to the whole application: [7](#0-6) 
```
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
```

### Impact Explanation
An unprivileged, unauthenticated network attacker who can reach `/webhooks` can:
1. Send a POST whose query string sets `repository[owner][login]` (or `organization[login]`) to any organization configured in the Shipit instance that has no `webhook_secret` set (an explicitly optional, commonly-skipped setting per `docs/setup.md`), causing `verify_signature` to unconditionally pass regardless of the actual `X-Hub-Signature` header.
2. Supply an arbitrary JSON body (unaffected by the query string) claiming to be a `membership` event for `Shipit.github_teams`, adding an attacker-controlled GitHub login to an authorized team.
3. Complete normal GitHub OAuth login as that attacker-controlled login; `User#authorized?` now returns true because of the forged `Membership`, granting the attacker full application access — an authentication/authorization bypass.

Alternatively, the same organization-confusion can be used to forge `push`/`status`/`check_suite` events for a completely different repository's stack, triggering unauthorized `GithubSyncJob`s or falsified commit statuses, again without ever knowing that target organization's real webhook secret.

This satisfies the "High: escalation into `Shipit.github_teams` authorization" / "unauthenticated... state" impact bar, and can chain into an authentication bypass for the whole application if the attacker becomes a member of an authorized team.

### Likelihood Explanation
Requires only network access to the public `/webhooks` endpoint — no credentials, tokens, or secrets. The only precondition is that the Shipit deployment either (a) uses the documented multi-organization configuration with at least one organization lacking a `webhook_secret` (explicitly optional per the setup docs), or (b) has any organization with a weak/known secret. Given the docs actively describe `webhook_secret` as optional, this is a realistic deployment state, not a hypothetical misconfiguration outside the documented setup.

### Recommendation
- Derive `repository_owner` (and any other value used to select the verifying `GitHubApp`) from the same parsed raw body used by `create`, not from `params`, so it cannot be influenced by the query string.
- After selecting the organization and verifying the signature, re-validate that the `repository`/`organization` embedded in the verified raw body actually belongs to the organization whose secret validated it, before dispatching to handlers.
- Consider making `webhook_secret` mandatory (or logging/rejecting webhooks with no secret configured) for any deployment using multiple GitHub organizations.

### Proof of Concept
Given a multi-org deployment (`test/dummy/config/secrets_double_github_app.yml` pattern) where `OrgOne` has `webhook_secret: nil` and `OrgVictim` has a real secret and owns repository `OrgVictim/secret-repo` tracked by Shipit:

```
POST /webhooks?repository[owner][login]=OrgOne HTTP/1.1
Content-Type: application/json
X-Github-Event: membership
X-Hub-Signature: sha1=anything-or-omitted

{
  "action": "added",
  "team": {"id": 1, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/1"},
  "organization": {"login": "OrgVictim"},
  "member": {"login": "attacker-github-login"}
}
```
- `verify_signature` computes `repository_owner` from `params`, which the `repository[owner][login]=OrgOne` query parameter overrides to `"OrgOne"`.
- `Shipit.github(organization: "OrgOne").verify_webhook_signature(...)` returns `true` immediately because `OrgOne` has no `webhook_secret`.
- `create` then parses the real JSON body (`organization.login == "OrgVictim"`) and `MembershipHandler` adds `attacker-github-login` to team `deployers` for `OrgVictim`, regardless of `OrgVictim`'s real, unbroken webhook secret.
- The attacker then logs in via GitHub OAuth as `attacker-github-login`; `User#authorized?` now returns `true`.
