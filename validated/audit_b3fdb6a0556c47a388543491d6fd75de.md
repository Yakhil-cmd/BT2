### Title
Unhandled `throw Error` on duplicate-output check crashes node on a normal (non-malicious) private payment chain - (File: private_payment.js)

### Summary
`validateAndSavePrivatePaymentChain()` in `private_payment.js` assumes that a query for existing outputs matching `unit`, `asset`, and `message_index` can return at most one row, and calls `throw Error(...)` if it returns more than one. This assumption does not hold for divisible-asset payment messages, which routinely contain multiple outputs (destination + change, or multiple destinations) sharing the same `unit`/`asset`/`message_index`. This is directly analogous to the TensorFlow `SetSize` bug, where an unchecked structural assumption (`set_shape` is 1-D) leads to a `CHECK`-fail/crash when a caller supplies input that violates it — here an unchecked assumption ("at most one output row per unit/asset/message_index") leads to an uncaught `throw` that crashes the node process.

### Finding Description
In `validateAndSavePrivatePaymentChain`, for non-fixed-denomination (divisible) assets, the de-duplication query omits an `output_index` filter: [1](#0-0) 

```
var sql = "SELECT address, denomination, amount, blinding FROM outputs WHERE unit=? AND asset=? AND message_index=?";
...
if (objAsset.fixed_denominations){
    ... sql += " AND output_index=?"; ...
}
conn.query(sql, params, function(rows){
    if (rows.length > 1)
        throw Error("more than one output "+sql+' '+params.join(', '));
```

However, `outputs` table rows are keyed by `(unit, message_index, output_index)`, and a single payment message can legitimately contain many output rows for the same asset in the same `message_index` — e.g., a destination output plus a change output, exactly as produced by `divisible_asset.js`'s payment composition logic where change is appended to `payload.outputs` (destination output + change output, both same asset, same message index): [2](#0-1) 

Once such a unit is written and its outputs are persisted (`writer.js` inserts one row per output index for the message): [3](#0-2) 

any subsequent call to `validateAndSavePrivatePaymentChain` for that `unit`/`asset`/`message_index` (e.g., a private-payment counterparty resending/forwarding a private chain, or a legitimate re-delivery of a chain a wallet already partially knows about) will match ≥2 rows and hit the `throw Error(...)`. This throw occurs inside a DB-driver async callback with no surrounding try/catch, so it becomes an uncaught exception that crashes the Node.js process (default behavior for uncaught exceptions is process termination unless a `domain`/global handler intercepts it — none is visible around this call path).

### Impact Explanation
A crash reachable from an unprivileged private-payment counterparty (or any peer forwarding a private chain, e.g., via `network.js`) constitutes a remotely triggerable denial of service against the receiving node/wallet — matching the "network unable to confirm new units" / node-crash class of impact accepted by the validation rules. Any wallet or hub processing private payment chains for divisible assets with multi-output messages (a completely normal, non-malicious payment pattern) can be made to crash by simply causing the duplicate-check path to be exercised twice for the same message.

### Likelihood Explanation
High: multi-output payment messages (destination + change) are the default/common case for divisible-asset payments in this codebase, not a corner case. Any resend or repeated delivery of a private payment chain for such a message — which can legitimately happen over the private-chain forwarding/repost paths reachable by a private-payment counterparty — triggers the faulty `rows.length > 1` branch deterministically.

### Recommendation
- For divisible assets, filter the duplicate check by `output_index` as well (the caller already knows which specific output the chain reveals), instead of matching on `unit + asset + message_index` alone.
- Replace the `throw Error(...)` with a call to `transaction_callbacks.ifError(...)` (or equivalent), so that an unexpected multi-row result is treated as a validation failure/rollback rather than crashing the process.
- Wrap DB-driver callbacks that currently rely on `throw` for "impossible" conditions with proper error propagation, consistent with `callbacks.ifError` patterns used elsewhere in the same function.

### Proof of Concept
1. Compose (or receive) a divisible-asset private payment unit whose payment message has 2 outputs for the same asset in the same message (e.g., 1 destination output + 1 change output) — this is the normal output of `composeDivisibleAssetPaymentJoint`.
2. Allow the unit to be written/stabilized so both output rows exist in the `outputs` table for that `unit`/`asset`/`message_index`.
3. As the private-payment counterparty, submit (or resend) a private payment chain (`arrPrivateElements`) referencing this unit/asset/message_index to `validateAndSavePrivatePaymentChain`.
4. The de-duplication `SELECT` returns 2 rows (both outputs of the message); `rows.length > 1` is true, and `throw Error("more than one output ...")` is executed inside the async `conn.query` callback, crashing the receiving process.
