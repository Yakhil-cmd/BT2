### Title
Webhook signature verification is keyed by `repository.owner.login`, but event processing trusts the independent `repository.full_name` field, allowing an org onboarded with its own GitHub App secret to forge events for any other org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. That value determines authentication of the *sender*, but every `Webhooks::Handlers::Handler` subclass resolves the *target* repository/stack from an entirely different field of the same unverified body: `payload.dig('repository', 'full_name')`. Because these two fields are never checked for consistency, and Shipit explicitly supports onboarding multiple, independently‑secreted GitHub Apps for different organizations in a single instance (`docs/setup.md` "Using Multiple Github Applications"), an org that legitimately possesses its own `webhook_secret` can sign a payload with `repository.owner.login` set to its own org while setting `repository.full_name` to a different, unrelated org/repo that is also tracked by the same Shipit instance.

### Finding Description
`verify_signature` is a `before_action` that looks up the app/secret to check against purely from attacker-controlled JSON body content, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` resolves a per-organization `GitHubApp` (and its distinct `webhook_secret`) from `secrets.github`, exactly as documented for multi-org installs: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (HMAC matches the secret belonging to `repository_owner`), `create` dispatches the *same raw payload* to handlers: [5](#0-4) 

But every handler resolves the actual repository/stack to act on from `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) [8](#0-7) 

`Repository.from_github_repo_name` does a plain owner/name lookup with no relation back to `repository.owner.login`: [9](#0-8) 

The binding that is broken is: **organization authenticated (`repository.owner.login`, checked against a specific `webhook_secret`) ≠ repository that is written (`repository.full_name`, used by every handler to locate the `Stack`)**. The signature only proves "this body was HMAC-signed with organization X's secret"; it proves nothing about which repository the body's other fields describe. An attacker who legitimately administers the GitHub App for org X (and therefore knows/controls X's `webhook_secret`, which they configured themselves when onboarding into the shared Shipit instance) can set `repository.owner.login: "X"` (to pass `verify_signature`) while setting `repository.full_name: "victim-org/victim-repo"` (to make handlers act on a stack belonging to a different, unrelated organization also hosted on the same Shipit instance).

### Impact Explanation
This lets a legitimately onboarded, low-privilege organization forge webhook events against a stack it does not own, without any Shipit account, session, or API token:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` on the victim's stack, enqueuing `GithubSyncJob` for a repository the attacker does not control - this can force out‑of‑band syncs and, depending on continuous-deployment configuration, unauthorized deploys of the victim's stack.
- `pull_request` handlers (`opened_handler.rb`, `reopened_handler.rb`, `unlabeled_handler.rb`, etc.) can create, archive, or unarchive review stacks belonging to the victim repository.
- `status`/`check_suite` handlers can inject commit/CI statuses that unlock deploy gating checks on the victim's stack.

This crosses the "cross-repository writes" / "unauthorized deploy, rollback" bar because it lets one onboarded org's credentials cause state changes on another org's stacks that Shipit's trust model assumes are isolated per-organization.

### Likelihood Explanation
Requires only that the Shipit instance is configured with the multi-org GitHub App layout documented in `docs/setup.md`, and that the attacker is one of the (possibly many, less-trusted) onboarded organizations - a realistic deployment for any shared/SaaS-style Shipit install tracking repositories across multiple orgs/customers. No Shipit session, API token, or GitHub org privilege on the victim side is needed; the attacker only uses secrets/capabilities it legitimately owns for its own org.

### Recommendation
After signature verification succeeds, re-derive `repository_owner` from the *same* field the handlers use (`repository.full_name`'s owner segment, or vice versa) and require it to match the organization whose secret validated the signature; reject the request (422) on mismatch instead of allowing handlers to trust a differently-scoped field.

### Proof of Concept
1. Shipit is configured with `secrets.github` containing two orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret` values (per `docs/setup.md` multi-org config), and both host repositories tracked as Shipit stacks.
2. Attacker, who administers the GitHub App for `attacker-org` (and therefore knows its `webhook_secret`), crafts a `push` webhook body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and POSTs it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')`, verifies the HMAC against `attacker-org`'s secret - it matches, so the request passes.
5. `PushHandler` runs `Repository.from_github_repo_name('victim-org/victim-repo')`, finds the real victim stack, and calls `stack.sync_github(expected_head_sha: '<attacker-chosen sha>')`, causing Shipit to sync/act on a repository the attacker never authenticated against.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
