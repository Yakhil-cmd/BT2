## Title
Cross-organization webhook forgery via mismatched `repository.owner.login` (used for signature verification) and `repository.full_name` (used for repository resolution) - ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController` selects which GitHub App/organization's webhook secret to verify a request against using the `repository.owner.login` (or `organization.login`) field of the JSON body, but every webhook handler resolves the actual `Repository`/`Stack` to write to using the *separate* `repository.full_name` field of the same body. These two fields are never cross-checked, so in any multi-organization deployment where at least one configured organization has no `webhook_secret` set (documented as "optional"), an unprivileged attacker can forge a payload whose `repository.owner.login` points at the secret-less organization (bypassing HMAC verification entirely) while `repository.full_name` points at a repository/stack belonging to a *different, properly-secured* organization, causing writes to that victim stack.

## Finding Description
`WebhooksController#verify_signature` picks the verifying GitHub App config purely from an attacker-controlled JSON field: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config, and each organization can independently have (or lack) a `webhook_secret`: [3](#0-2) 

If that organization's `webhook_secret` is blank, `GitHubApp#verify_webhook_signature` short-circuits and accepts the payload with **no signature check whatsoever**: [4](#0-3) 

This behavior is explicitly documented as supported/optional configuration (`webhook_secret: # nil`): [5](#0-4) 

After verification, every webhook `Handler` resolves the target repository from a **different** field of the same JSON body — `repository.full_name` — with no check that it is consistent with the `repository.owner.login`/`organization.login` value used to select the verifying secret: [6](#0-5) [7](#0-6) 

Concrete handlers that act on `repository.full_name` (and thus a stack chosen independently of the verified organization) include `PushHandler`, which triggers `stack.sync_github`: [8](#0-7) 

and `StatusHandler`, which forges CI/commit statuses used to gate deploys: [9](#0-8) 

as well as the pull request handlers, which resolve `repository` purely from `params.repository.full_name` to archive/create review stacks: [10](#0-9) 

**Binding broken (as an equality that should hold but doesn't):**
`organization_used_for_signature_verification (repository.owner.login) == organization_of_repository_written_to (derived from repository.full_name)`

Before the attacker's request: for legitimate GitHub-originated webhooks, both fields always describe the same repository (GitHub itself generates the whole payload consistently), so the two never diverge.

After the attacker's request: because the attacker controls the entire raw JSON body when targeting an organization with no `webhook_secret`, they can set `repository.owner.login = "org-with-no-secret"` (making `verify_signature` pass trivially) while setting `repository.full_name = "org-with-secret/victim-repo"` (making the handler act on a stack belonging to a different, properly-secured organization). The equality is violated, and Shipit processes the forged event as if it legitimately originated from GitHub for the victim organization's repository.

## Impact Explanation
This breaks the intended per-organization webhook trust boundary in a multi-tenant Shipit deployment. An unprivileged attacker (no Shipit session, no `webhook_secret`, no GitHub access to the victim org/repo) can:
- Forge `status` events (`StatusHandler`) to inject fake successful CI statuses onto arbitrary commit SHAs of a victim stack, which can unblock `ci.require`-gated deploys — an unauthorized-deploy escalation path.
- Forge `push` events (`PushHandler`) to force `stack.sync_github` against a victim stack.
- Forge `pull_request`/`membership` events to archive/create review stacks or manipulate `Team`/`Membership` records tied to a victim organization.

This is a cross-organization write achieved purely by exploiting the divergence between the field used to authenticate the request and the field used to determine what gets written — matching the required "Critical/High" impact bar (cross-repository writes / unauthorized deploy path), without requiring any credential, session, or secret belonging to the victim organization.

## Likelihood Explanation
Likelihood is Medium: it requires the deployment to be configured with the multi-organization GitHub schema and at least one of the configured organizations to have an unset `webhook_secret` — a state explicitly supported and documented as valid ("optional") configuration, not an edge case outside the engine's documented deployment model. Given that, exploitation requires no privileges at all — just a POST to the public `/webhooks` endpoint with a crafted `X-Github-Event` header and JSON body.

## Recommendation
Cross-validate that the field used to select the verifying webhook secret (`repository.owner.login` / `organization.login`) matches the organization implied by `repository.full_name` before dispatching to handlers, and reject the request otherwise. Alternatively, resolve organization and repository from a single, consistently-derived field, and consider requiring a non-blank `webhook_secret` per organization (or globally) rather than silently trusting unsigned payloads when a secret is absent.

## Proof of Concept
1. Configure Shipit with two organizations: `org-a` (no `webhook_secret` set) and `org-b` (has `webhook_secret` set, hosts a real production stack `org-b/prod-app`).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: status` and no/garbage `X-Hub-Signature`, and body:
```json
{
  "sha": "<victim commit sha in org-b/prod-app>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/prod-app"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: 'org-a')`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`).
4. `StatusHandler#process` resolves the target via `Commit.where(sha: params.sha)` for the commit belonging to `org-b/prod-app` and creates a forged successful status, potentially satisfying `ci.require` for that stack despite the attacker having no relationship to `org-b`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
