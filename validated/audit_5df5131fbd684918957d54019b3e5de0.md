### Title
`StatusHandler#process` updates commit statuses by bare SHA match across all repositories/stacks, ignoring the webhook's authenticated repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no filter on `repository`/`stack`, unlike the `stacks` helper defined on the base `Handler` class. Any webhook signed for one GitHub organization can therefore mutate `Status` rows belonging to a `Commit` in a completely unrelated stack/repository/org if their `sha` values happen to match.

### Finding Description
The broken binding: `Handler#stacks` (`Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`) is meant to scope which stacks/commits a handler may touch, i.e. it should hold that `{commits mutated by StatusHandler#process} == {commits belonging to stacks in Handler#stacks}`. In `app/models/shipit/webhooks/handlers/status_handler.rb`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`stacks` is never called, and `params.repository`/`payload.dig('repository','full_name')` is never compared against `commit.stack.repository`. `Commit#sha` has no uniqueness constraint scoped to (or otherwise) the repository/stack in the schema referenced here, so `Commit.where(sha:)` can return rows from arbitrarily many stacks/repositories/organizations.

The request path: `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) verifies the signature only against the organization derived from the payload's own `repository.owner.login` (`verify_signature`, lines 24-49) — this authenticates that the *attacker's own org* sent the payload, but does nothing to restrict which `Commit` rows get updated. It then dispatches to `Shipit::Webhooks.for_event('status')`, i.e. `StatusHandler`, passing the raw parsed JSON. `StatusHandler#process` subsequently touches every `Commit` row matching `sha`, regardless of which repository/stack owns it.

An attacker who controls a Shipit-tracked GitHub org can send `POST /webhooks` with `X-Github-Event: status`, a signature valid for their own org, and `{sha: <sha also present in victim's Commit table>, state: 'success', repository: {full_name: 'attacker/evil'}}`. If a `Commit` in a victim's stack has the same `sha` (e.g., an empty/no-op commit with identical author/committer/timestamp/message across two repos, which is a documented way distinct repositories can produce identical git SHA-1 values without any cryptographic collision), `commit.create_status_from_github!(params)` runs for the victim's `Commit` too, calling `Commit#add_status` (`app/models/shipit/commit.rb:366-386`), creating a `Status` row, potentially flipping `Commit#deployable?` (line 227) to true and firing `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`, which can enqueue `ProcessMergeRequestsJob` and ultimately unlock a deploy on a stack the attacker never authenticated for.

None of the existing guards prevent this: `verify_signature` only checks the org that matches the payload's *own* `repository`/`organization` field — it never re-checks that field against the `Commit`s that end up mutated. `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` only validate presence/type of `sha`, `state`, etc., not repository ownership. `Handler#stacks` exists precisely to perform this scoping but is simply not invoked by `StatusHandler#process`.

### Impact Explanation
A single-org-authenticated webhook can write `Status` rows (and downstream: trigger deploy hooks, merge-request processing, and change `Commit#deployable?`) for `Commit`s owned by a stack/repository/organization the attacker does not control. This is a cross-tenant mutation of another org's Commit/Status state from a request authenticated only for the attacker's own org, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It's repeatable against any commit whose `sha` collides with one visible in the attacker's own repository, and the blast radius spans every stack/org configured in the same Shipit instance.

### Likelihood Explanation
Exploitation requires the attacker to control (or convincingly configure) a GitHub org/repo already registered in Shipit and to produce a commit whose `sha` matches a commit already present in a victim's stack. Cryptographically colliding SHA-1 of attacker-chosen arbitrary content is infeasible, but identical, content-determined commits (e.g., empty commits with identical author/committer/date/message, or shared upstream history/fixture data reused across repos) legitimately produce identical SHA-1 in unrelated repositories — this is the documented precondition in the question, not a novel crypto attack. Given that precondition, the attacker's cost is a single signed webhook POST from their own org, fully within reach of an "unprivileged" GitHub org owner as defined in scope.

### Recommendation
Scope `StatusHandler#process` to only the stacks/commits belonging to the authenticated repository, e.g. iterate `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) using the existing `Handler#stacks` helper, so a webhook can only mutate commits under the repository it was signed for.

### Proof of Concept
Minitest in `test/controllers/webhooks_controller_test.rb` style (illustrative, not to be placed in `test/` per scope but describing the exact assertion):
```ruby
test ":status cross-tenant mutation via sha collision" do
  victim_stack = shipit_stacks(:shipit) # repository e.g. "shopify/shipit-engine"
  attacker_stack = Stack.create!(repository: Repository.create!(owner: 'attacker', name: 'evil'), ...)
  collided_sha = 'deadbeef' * 5
  victim_commit = victim_stack.commits.create!(sha: collided_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: collided_sha, ...)

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulates a valid signature for attacker's own org

  body = { sha: collided_sha, state: 'success', repository: { full_name: 'attacker/evil' } }.to_json

  assert_difference -> { victim_commit.reload.statuses.count }, 1 do
    post :create, body:, as: :json
  end
end
```
Assert `victim_commit.stack.repository.full_name != 'attacker/evil'` (left side of the broken binding — the mutated commit's repository) yet `victim_commit.statuses.count` increased (right side — actual mutation performed), proving `Handler#stacks`/repository scoping was never applied in `StatusHandler#process`.
