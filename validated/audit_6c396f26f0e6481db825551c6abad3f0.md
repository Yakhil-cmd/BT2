### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while `CheckSuiteHandler` mutates state keyed off the independent `repository.full_name` field, letting an attacker forge cross-tenant `RefreshCheckRunsJob` enqueues - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/check_suite_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` derives the "org" used for HMAC verification from `payload.dig('repository','owner','login')` (or `organization.login`), but `Handler#stacks` (used by `CheckSuiteHandler#process`) derives the target repository from the independent `payload.dig('repository','full_name')` field. Because these are two separate, entirely attacker-controlled JSON fields with no cross-validation, an attacker who can satisfy verification for one (misconfigured/no-`webhook_secret`) org can point `full_name` at a completely different, properly-secured repository and trigger `schedule_refresh_check_runs!` on its commits.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `organization_that_verified_signature (payload.repository.owner.login)` == `organization_owning_the_mutated_stack (payload.repository.full_name.split('/').first)`.

Code path:
- `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `repository_owner` from `params.dig('repository','owner','login')` (line 61) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-82) returns `true` unconditionally when `webhook_secret` is blank for that org's config.
- If verification passes, `create` runs `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (app/controllers/shipit/webhooks_controller.rb:11-12), passing the **raw, attacker-controlled** JSON body straight to the handler.
- `Handler#stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-38) resolves the target via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` — a completely separate JSON field from the one used for signature-org lookup.
- `CheckSuiteHandler#process` (app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17) then calls `stack.commits.where(sha: ...).each(&:schedule_refresh_check_runs!)`, mutating state on whatever stack `full_name` resolves to.

Nothing in the code enforces that `repository.owner.login` (used to pick the verifying `webhook_secret`) is consistent with `repository.full_name` (used to pick the mutated stack) — they are independently attacker-supplied JSON values in the same POST body.

Existing guards checked and found insufficient:
- `drop_unhandled_event` only filters by event type, not payload content.
- `verify_signature`'s `rescue GithubOrganizationUnknown` only fires when the org name is *unrecognized*; it does not fire for a recognized org whose config simply lacks `webhook_secret`.
- In single-org mode, `Shipit.github` ignores the `organization:` argument entirely (`lib/shipit.rb:170-181`), so the flaw only manifests in multi-org (`github_organizations`) configurations, where per-org config lookup is keyed by attacker-supplied `repository_owner`.
- `ExplicitParameters` schema on `CheckSuiteHandler` only validates the shape of `check_suite.head_sha`/`head_branch`, not that the enclosing `repository` payload is internally consistent.

Attacker request: `POST /webhooks` with `X-Github-Event: check_suite`, body `{"repository":{"full_name":"victim-org/victim-repo","owner":{"login":"noSecretOrg"}},"check_suite":{"head_branch":"main","head_sha":"<known-sha>"}}`, where `noSecretOrg` is a Shipit-configured GitHub org whose `webhook_secret` is blank/unset.

### Impact Explanation
A successful request enqueues `RefreshCheckRunsJob` against commits in a stack belonging to `victim-org` — a repository/organization the attacker never authenticated against — purely because an unrelated, misconfigured org's blank `webhook_secret` was used to pass the signature check. This is a cross-tenant state mutation triggered by a payload whose claimed identity (`repository.owner.login`) diverges from the identity actually acted upon (`repository.full_name`), matching the "payload for one repository mutating another's stack/commit" Critical category. It is repeatable against any repository/branch/sha the attacker can enumerate (branch names and commit SHAs are frequently public), and the same divergence pattern affects every other `Handler` subclass that reads `repository.full_name` (pull_request handlers, etc.), widening blast radius across all repositories hosted on a multi-org Shipit instance.

### Likelihood Explanation
Exploitation strictly requires that the Shipit multi-org deployment has at least one configured GitHub org entry with a blank/absent `webhook_secret` — this is an operator misconfiguration, not something the attacker can create themselves. Given that precondition, the attack costs nothing beyond a single unauthenticated HTTP POST with a crafted body (no signature computation needed, since `verify_webhook_signature` short-circuits to `true`). No secrets, sessions, or privileged roles are required. Feasibility is high once the misconfiguration exists; without it (i.e., every configured org has a non-blank `webhook_secret`), the path is not exploitable because a valid HMAC over the full attacker-controlled body would be required and the attacker does not know any `webhook_secret`.

### Recommendation
Stop deriving the verification identity and the mutation identity from two independent payload fields. Either (a) derive the org used for `Shipit.github(organization:)` from the same `repository.full_name` value used by `Handler#stacks` (e.g., split the owner off `full_name` rather than trusting `repository.owner.login`/`organization.login` separately), or (b) after signature verification, additionally assert that `repository.owner.login` matches the owner segment of `repository.full_name` and reject (422) on mismatch. Additionally, treat a configured org with a blank `webhook_secret` as invalid/rejectable rather than silently trusted, or require `webhook_secret` to be present for any org listed under `github_organizations`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, illustrative — not to be placed under `test/` per audit scope but demonstrating the assertions):
1. Configure two orgs in `Shipit.github_organizations`/secrets: `no-secret-org` (no `webhook_secret`) and `secured-org` (real `webhook_secret`).
2. Create `Repository` for `secured-org/victim-repo` with a `Stack` on branch `main`, and a `Commit` with sha `deadbeef` belonging to that stack.
3. POST to `/webhooks` with header `X-Github-Event: check_suite`, no `X-Hub-Signature` (or garbage signature), body:
   `{"repository":{"full_name":"secured-org/victim-repo","owner":{"login":"no-secret-org"}},"check_suite":{"head_branch":"main","head_sha":"deadbeef"}}`.
4. Assert response is `200 OK` (not `422`), proving `repository_owner` (`no-secret-org`) ≠ org owning the mutated stack (`secured-org`).
5. Assert `RefreshCheckRunsJob` was enqueued for the `Commit` with sha `deadbeef` belonging to `secured-org/victim-repo`, i.e., `assert_enqueued_with(job: RefreshCheckRunsJob, args: [commit.id])`, demonstrating unauthorized cross-tenant state mutation.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
