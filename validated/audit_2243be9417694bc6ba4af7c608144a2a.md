### Title
Cross-organization webhook signature bypass via empty-string `webhook_secret` decoupled from `repository.full_name` trust - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's secret to verify against using `repository_owner`, which falls back to `params.dig('organization','login')` when `repository.owner.login` is absent. `GitHubApp#initialize` converts an empty-string `webhook_secret: ''` config value into `nil` via `.presence`, and `verify_webhook_signature` auto-passes (`return true unless webhook_secret`) whenever the secret is falsy. Because the actual data-mutating handlers (e.g. `LabelCapturingHandler`) look up the target repository/stack independently via `params.repository.full_name`, an attacker can pick any org configured with an empty-string secret for the *verification* step while naming a completely different, legitimately-configured org/repo as the mutation target.

### Finding Description
The broken binding: the codebase implicitly assumes `repository_owner used to select the verifying GitHubApp` == `owner of the repository actually mutated by the handler`. In fact these are two independent reads of the same untrusted JSON body:

- Verification org: `app/controllers/shipit/webhooks_controller.rb:59-62` — `params.dig('repository','owner','login') || params.dig('organization','login')`.
- Mutation target: `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:110-114` — `Shipit::Repository.from_github_repo_name(params.repository.full_name)`.

`LabelCapturingHandler`'s `ExplicitParameters` schema (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:33-35`) only `requires :repository { requires :full_name, String }` — it does **not** require `repository.owner.login`. So a payload can supply `repository.full_name` (e.g. `"realorg/target-repo"`) while omitting `repository.owner` entirely and adding a top-level `organization: { login: "attacker-org" }`. `repository_owner` then resolves to `"attacker-org"` for signature verification (`app/controllers/shipit/webhooks_controller.rb:61`), while the handler processes and mutates the stack belonging to `"realorg/target-repo"`.

If `"attacker-org"` is configured in `secrets.github` with `webhook_secret: ''`, `GitHubApp#initialize` sets `@webhook_secret = @config[:webhook_secret].presence` (`lib/shipit/github_app.rb:50`), turning `''` into `nil`. `verify_webhook_signature` then hits `return true unless webhook_secret` (`lib/shipit/github_app.rb:76-77`) and accepts **any** signature/body pair unconditionally for that org — with no requirement that the attacker know any real secret.

Attacker request: POST `/webhooks` with header `X-Github-Event: pull_request`, any (even garbage) `X-Hub-Signature`, and body:
```json
{
  "action": "labeled",
  "number": 2,
  "pull_request": { ... valid schema fields ..., "labels": [{"name":"malicious-label"}] },
  "repository": { "full_name": "realorg/target-repo" },
  "organization": { "login": "attacker-org" },
  "sender": { "login": "attacker" }
}
```
`verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, auto-verifies true, and the request proceeds to `Shipit::Webhooks.for_event('pull_request').each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:10-15`), which dispatches to `LabelCapturingHandler` (and other `pull_request` handlers such as `LabeledHandler`/`UnlabeledHandler`, which have the identical `repository { requires :full_name }`-only schema and the identical `from_github_repo_name(params.repository.full_name)` lookup) — mutating `realorg/target-repo`'s stack (labels, archive/unarchive state) without ever needing `realorg`'s real webhook secret.

Why guards don't catch this: `drop_unhandled_event` only checks the event type is handled; `verify_signature` only checks a signature against a secret chosen by attacker-controlled `organization.login`; the `ExplicitParameters` schema validates shape/types, not that `repository.owner` matches `organization.login` or that `repository.full_name`'s owner equals the verified organization; `Repository` model validations only constrain owner/name character sets for records that already exist — they don't bind the verified org to the acted-upon repo.

### Impact Explanation
This is a payload for one repository mutating another (and, worse, a different tenant/organization) that did not authenticate the request — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Concretely, an attacker can flip labels on arbitrary tracked review-stack PRs, archive/unarchive stacks (`LabeledHandler`/`UnlabeledHandler`), or trigger other `pull_request`-family handler side effects on any repository already registered in Shipit, as long as *any single organization* in the deployment's multi-org GitHub config has `webhook_secret: ''`. This is repeatable indefinitely and across every repository/stack tracked by Shipit, not just those belonging to the misconfigured org.

### Likelihood Explanation
This requires a specific, non-default multi-org configuration precondition: at least one organization entry in `secrets.github` (the multi-org schema, see `test/dummy/config/secrets_double_github_app.yml`) with `webhook_secret` set to the empty string `''` rather than `nil`/omitted. This is plausible as a "common misconfiguration" (e.g. templated secrets files or environment-variable interpolation producing `''` instead of unset), but it is a genuine precondition and not the default (documented examples show `webhook_secret:` commented/nil). Given the precondition holds, attacker cost is trivial: no secrets, no session, just a raw HTTP POST with a crafted JSON body and an arbitrary `X-Hub-Signature` value.

### Recommendation
- In `WebhooksController#repository_owner`, do not fall back silently to `organization.login` for events that structurally include a `repository` object (e.g. `pull_request`); require `repository.owner.login` to be present for such events and reject/422 if absent.
- In `GitHubApp#initialize`, treat an explicitly-empty string `webhook_secret` as a configuration error (raise) rather than silently normalizing it to "no secret configured" via `.presence`.
- Additionally/defense-in-depth: after verification, assert that the organization used to verify the signature matches the owner segment of `params.repository.full_name` before dispatching handlers.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "empty-string webhook_secret for an unrelated org allows forging events for a different repository" do
  Shipit.stubs(:github_app_config).with('attacker-org').returns(webhook_secret: '')
  # or configure secrets.github['attacker-org'][:webhook_secret] = ''

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # arbitrary, unverifiable signature

  payload = payload_parsed(:pull_request_labeled)
  payload['repository'] = { 'full_name' => 'shopify/shipit-engine' } # no owner.login key
  payload['organization'] = { 'login' => 'attacker-org' }

  stack = shipit_repositories(:shipit).stacks.last # pre-existing, unrelated stack

  post :create, body: payload.to_json, as: :json

  assert_response :ok
  # Prove mutation happened on the target stack without knowledge of its real secret
  assert_includes stack.reload.pull_request.labels, payload['pull_request']['labels'].last['name']
end
```

And directly on `GitHubApp`:
```ruby
# minitest, no live GitHub
app = Shipit::GitHubApp.new('attacker-org', webhook_secret: '')
assert_nil app.instance_variable_get(:@webhook_secret)
assert app.verify_webhook_signature('sha1=anything', '{"any":"body"}')
```

Both sides of the claimed equality — `repository_owner` used for verification ("attacker-org") vs. the owner of `params.repository.full_name` actually mutated ("shopify") — diverge, confirming the vulnerability under the stated empty-string-secret precondition.
