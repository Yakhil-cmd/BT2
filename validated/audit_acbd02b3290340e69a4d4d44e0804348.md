### Title
Reward accounting overstates distributed sBTC in `calculate-rewards`/`calculate-bond-rewards`, causing rewards to become permanently stuck and unclaimable - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar`'s reward engine mirrors the reward-accumulator pattern described in the external report: an aggregate pool of newly-received sBTC is computed once (`get-new-rewards`), then split across bonds and STX stakers by converting it into a *per-share* rate (`rewards-per-token-for-cycle`) using floor division, while the top-level bookkeeping variable `last-accounted-rewards-only` is advanced by the full nominal amount rather than by the amount that per-share floor division actually makes claimable. This creates a persistent gap between "rewards the contract believes it distributed" and "rewards a user can actually sum up and claim," exactly the pattern that caused the `TroveManager` bug in the referenced report.

### Finding Description
`calculate-rewards` computes `gross-accrued-rewards` once from the contract's real sBTC balance (`get-new-rewards`, `stackslib/src/chainstate/stacks/boot/pox-5.clar:2147-2156`), then folds over `bond-periods` via `calculate-bond-rewards`. [1](#0-0) 

For each bond, `earned` (an aggregate uint) is converted to `accrued-rewards-per-sat` by floor-dividing by `total-sats` and multiplying by `PRECISION`. The fold's `available-rewards` accumulator is then reduced by the full aggregate `earned` value, not by `(accrued-rewards-per-sat * total-sats) / PRECISION` — the amount that stakers can actually redeem when they later apply `compute-earned-rewards`. [2](#0-1) 

The same pattern repeats at the top level for STX stakers: [3](#0-2) 

`accrued-rewards-per-ustx` is `stx-staker-rewards * PRECISION / cycle-staked-ustx` (floor division), yet `last-accounted-rewards-only` is advanced by `gross-accrued-rewards - reserve-deposit`, i.e. the *nominal* `stx-staker-rewards`+bond totals, not the sum that `compute-earned-rewards` will actually let individual stakers extract: [4](#0-3) 

`compute-earned-rewards` applies `(shares * (rpt-current - rpt-paid)) / PRECISION` per staker — another independent floor division. Summed over all stakers this is always `<=` the nominal amount already recorded as "accounted for" in `last-accounted-rewards-only`. The difference (analogous to the `firstWeekEmissions` vs `userReward*2` gap in the external PoC) is real sBTC sitting in the contract's balance that is neither reflected in `reserve-balance` nor recoverable by any staker's claim, because `last-accounted-rewards-only` already "spent" it on paper. Since `get-rewards`/`get-new-rewards` (`pox-5.clar:2134-2156`) derive future distributable amounts from `current-balance - last-accounted-rewards-only`, and `last-accounted-rewards-only` is inflated relative to what claims will actually consume, the true residual balance grows out of sync with the accounting variables that gate future distributions — the same "some rewards are effectively lost" failure mode as the report, just with sBTC/STX-staker rewards instead of `BabelVault` emissions.

### Impact Explanation
This causes a portion of legitimately-earned, already-deposited sBTC rewards to become permanently unclaimable by any staker or signer, while also not being credited back to the `reserve-balance` that the protocol can otherwise account for and use. This matches the "permanent freezing of reserve or fees" High-impact bucket: value that should be distributed or reserved is instead stranded in contract balance with no code path to reclaim it, growing every cycle that has non-trivial `total-sats`/`cycle-staked-ustx` denominators relative to reward numerators (small stake, high precision loss).

### Likelihood Explanation
This triggers on essentially every `calculate-rewards` call whenever `earned`/`stx-staker-rewards` isn't an exact multiple of `total-sats`/`cycle-staked-ustx` — i.e., under normal operating conditions, not requiring any privileged action or malicious actor. It compounds cycle over cycle as more emissions flow through the same lossy per-share conversion.

### Recommendation
Track and carry forward the *actual* per-share-distributable remainder rather than the nominal aggregate amount:
- In `calculate-bond-rewards`, decrement the fold's `available-rewards` by `(accrued-rewards-per-sat * total-sats) / PRECISION` (the true amount now claimable) rather than by `earned`, and add the truncated remainder back into the pool for the next bond or into the reserve.
- In `calculate-rewards`, similarly advance `last-accounted-rewards-only` by `(accrued-rewards-per-ustx * cycle-staked-ustx) / PRECISION` for the STX-staker portion (plus the same corrected sum for bonds) instead of the full nominal `gross-accrued-rewards - reserve-deposit`, and route the rounding remainder into `reserve-balance` so it stays accounted for and eventually usable/withdrawable rather than silently stuck.

### Proof of Concept
Conceptually (mirroring the external PoC structure), an integration test on `pox-5.test.ts`/`utils.ts` reward-model harness would:
1. Set up a cycle with a bond and/or STX stakers whose `total-sats`/`cycle-staked-ustx` does not evenly divide the computed `earned`/`stx-staker-rewards` (e.g., an odd `PRECISION`-scaled remainder as already demonstrated for signer fee dust in `contrib/core-contract-tests/tests/pox-5/signer-manager.test.ts:248-322`, but applied to the top-level `calculate-rewards`/`claim-rewards` path instead of `signer-manager`'s already-isolated dust accounting).
2. Call `calculate-rewards`, then have all stakers/bonds claim via `claim-rewards`.
3. Compare `sum(claims)` to the `gross-accrued-rewards` reported by `calculate-rewards`, and re-run `get-new-rewards`/`get-rewards` in the following cycle to show the discrepancy is not returned to `reserve-balance` and is unreachable by any subsequent claim — confirming the residual is permanently stranded, exactly as `residualDust` was explicitly tracked and swept in `signer-manager.test.ts` but is *not* tracked or swept for the higher-level `calculate-rewards`/`claim-rewards` bond/STX-staker path in `pox-5.clar`.
