### Title
CCMenu API token is not bound to the stack it was issued for, allowing installation-wide `read:stack` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` with `read:stack` permission but never associates it with the requested stack, and `Api::CCMenuController#stack` resolves `params[:stack_id]` against `Stack.from_param!` directly instead of the scoped `stacks` helper used elsewhere. Any holder of a CCMenu token generated for one stack can therefore query the CI status of any stack in the installation.

### Finding Description
The intended binding is `current_api_client.stack_id == stack.id`, i.e. a CCMenu token issued while viewing stack A's settings page must only authorize reads of stack A.

- `CCMenuUrlController#fetch` creates the client without ever setting `stack:`: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, so `client.stack_id` is always `nil`. [1](#0-0) 
- `Shipit::Api::BaseController` already has a scoping mechanism intended for exactly this: `stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when `stack_id?` is true, and the generic `stack` helper uses that scoped relation. [2](#0-1) 
- `Shipit::Api::CCMenuController` overrides `stack` and bypasses that scoping entirely, resolving against the full table: `@stack ||= Stack.from_param!(params[:stack_id])`. [3](#0-2) 
- `require_permission :read, :stack` only checks that `"read:stack"` is in `permissions`, it does not check `current_api_client.stack_id` against the resolved stack: `check_permissions!` just tests `permissions.include?(required_permission)`. [4](#0-3) 

Even if `stack_id` were populated on the CCMenu client, the controller-level bypass means it would never be enforced. Combined with the fact that `stack_id` is never even set, the CCMenu token functions as an unscoped, installation-wide `read:stack` bearer credential.

Attack flow: an operator visits stack A's settings page and clicks "Fetch URL", hitting `CCMenuUrlController#fetch`, which returns a URL containing `?token=<token>` for a freshly created/reused "CCMenu Client" `ApiClient`. That URL is pasted into a third-party CI dashboard/aggregator (a normal CCMenu usage pattern). The attacker operating that dashboard/proxy observes the URL (e.g., via `Referer` header on an embedded asset request) and extracts the `token`. The attacker then calls `GET /api/stacks/:stack_id/ccmenu?token=<token>` with an arbitrary `stack_id` (stack B), authenticating via `Api::CCMenuController#authenticate_api_client`, which accepts any valid token regardless of stack. [5](#0-4) 

Existing guards do not prevent this: `authenticate_api_client` only validates the token's signature via `ApiClient.authenticate`, `require_permission` only checks the permission string, and `Stack.from_param!` performs no ownership check tying the resolved stack back to the client's `stack_id`. No signature, session, or webhook verification is relevant here since this is a legitimate, correctly-signed token being replayed against an unintended resource.

### Impact Explanation
Any leaked CCMenu token — from a single stack — grants unauthenticated read access to the CI/build status (`show` renders `deploys_and_rollbacks.last`, name, activity, last build status/label/time, web URL) of every stack in the Shipit installation, not just the one it was generated for. This is a cross-tenant/cross-repository authorization bypass matching "unauthenticated read of stack state" and is repeatable indefinitely since the token does not expire and works for any `stack_id`.

### Likelihood Explanation
No special Shipit configuration is required beyond default operation; `read:stack` CCMenu tokens are created via the standard "Fetch URL" UI flow that Shipit explicitly documents for integrating with CI dashboards/badges. The attacker needs only to observe one such URL (via the described Referer-leak vector to a public CI aggregator, or any equally trivial leak channel) and can then immediately enumerate/query arbitrary stacks — no GitHub secrets, sessions, or elevated roles are needed.

### Recommendation
- In `CCMenuUrlController#client`, set `stack: stack` when creating/finding the `ApiClient` so `stack_id` reflects the intended target.
- In `Shipit::Api::CCMenuController`, remove the custom `stack` override and use the base `stacks.from_param!` (or explicitly assert `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id`) so the permission check is properly scoped to the client's bound stack.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a CCMenu token issued for one stack cannot read another stack" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: "foo", name: "bar"), branch: "main")

  # simulate CCMenuUrlController#fetch for stack_a
  client = ApiClient.create_with(permissions: %w[read:stack])
                     .find_or_create_by!(creator: shipit_users(:walrus), name: 'CCMenu Client')
  token = client.authentication_token

  # binding under test: client.stack_id == stack_a.id should hold, but doesn't
  assert_nil client.stack_id

  get :show, params: { stack_id: stack_b.to_param, token: token }
  assert_response :ok # currently succeeds; should be :forbidden/:not_found for a client not bound to stack_b
end
```
This demonstrates that `current_api_client.stack_id` (nil/unbound) never equals `stack.id` (stack B) yet the request still succeeds, confirming the missing binding.
