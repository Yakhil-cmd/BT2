### Title
Front-runnable issuance of AA-defined capped assets permanently bricks AA logic that depends on that asset - (File: aa_composer.js, aa_validation.js, validation.js)

### Summary
When an Autonomous Agent (AA) defines a nested `asset` with a `cap`, `aa_composer.js` assumes ("only our AA can issue, no unstable consensus-breaking issues possible", `aa_composer.js:1195`) that the capped asset's single `issue` input (serial_number 1) can only ever be created by the AA itself. However, neither `aa_validation.js` (validation of the nested asset definition inside an AA) nor `validation.js` (validation of a plain `asset` definition message and of `payment` messages that issue units of it) forces `issued_by_definer_only=true` whenever `cap` is set. If the AA definition sets (or a formula evaluates to) `issued_by_definer_only=false` for a capped asset, any unprivileged user can post an ordinary `payment` message that issues serial_number 1 of that asset before the AA ever gets a chance to issue it itself, permanently consuming the uniqueness slot the AA logic relies on.

### Finding Description
For AA-defined assets with a cap, the "already issued" check that gates the AA's own issuance is a global, asset-scoped uniqueness check with no authorization restriction unless `issued_by_definer_only` is explicitly `true`: [1](#0-0) 

The comment at `aa_composer.js:1195` ("only our AA can issue, no unstable consensus-breaking issues possible") documents the intended invariant, but this invariant is never enforced by the validators. `aa_validation.js`'s validation of the nested `asset` message inside an AA definition only forbids `issued_by_definer_only=true` combined with `is_private`/`fixed_denominations`; it never requires `issued_by_definer_only=true` when `cap` is present: [2](#0-1) [3](#0-2) 

Similarly, `validation.js`'s general `asset` definition validation and the `payment`/issue-input validation logic never tie `cap` to `issued_by_definer_only`: [4](#0-3) [5](#0-4) 

Consequently, if `issued_by_definer_only` for a capped asset is `false` (either because the AA author explicitly sets it, or a formula for that boolean field evaluates to `false` under attacker-influenced state at definition time), the check in `validatePaymentInputsAndOutputs` only requires the issuer address to be an author of the unit that posts the issue input — it does not require the issuer to be the AA: [6](#0-5) 

Any unprivileged wallet can therefore build and broadcast a normal `payment` unit that issues serial_number 1 of the AA's capped asset (as long as `objAsset.cap && !objAsset.fixed_denominations` require `input.amount === objAsset.cap`, which the attacker can trivially satisfy). This consumes the sole allowed issue slot in the `inputs` table (`type='issue' AND asset=?`), the very check the AA's `issueAsset()` relies on: [7](#0-6) 

From then on, every time the AA is triggered and its oscript logic reaches the branch that tries to issue this asset, `issueAsset()`'s query `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` finds the attacker's row and returns `cb2('already issued')`, which bounces the AA's response unit for good — the asset can never be issued by the AA.

### Impact Explanation
This is a permanent denial-of-service / fund-freezing bug for any AA whose business logic (e.g. a crowdsale/ICO AA that issues shares/reward tokens with a fixed `cap`, similar to patterns shown in `test/samples/ico_with_milestones.oscript` and `test/samples/create_an_asset.oscript`) depends on being able to issue its own capped token. A malicious, unprivileged user who notices the AA's definition (which is public once posted, and definitions can even be inspected before the AA becomes reachable) can pre-empt the single allowed issuance, permanently bricking the AA's token-issuance path. Since the token underlies the AA's accounting (shares, LP-like tokens, etc.), users who deposit funds into the AA expecting to receive this asset in return can lose access to the intended payout — an AA fund-freezing condition, matching the "freezing" impact class described in the rules.

### Likelihood Explanation
Likelihood is limited by whether an AA developer actually creates a capped asset with `issued_by_definer_only != true`. This is not enforced anywhere, so it is a normal, allowed configuration for asset definitions inside an AA (validators impose no restriction requiring `issued_by_definer_only=true` when `cap` is set). Given how common capped, non-restricted assets are in DODO-analog patterns (fundraising/ICO templates in this very repo's test samples), and that front-running an issuance transaction on a public DAG requires no special privilege — just knowledge of the AA address and asset id, both public as soon as the AA is defined — the likelihood that this class of AA is vulnerable is non-trivial whenever `issued_by_definer_only` is left `false`/unset via formula.

### Recommendation
Enforce the documented invariant at validation time: when an `asset` message defined inside an AA definition (or any `asset` definition whose definer is later found to be an AA address) has `cap` set, require `issued_by_definer_only` to evaluate to `true`. This should be checked both in `aa_validation.js` (`case 'asset':` block around line 230) at AA-definition-validation time, and defensively in `aa_composer.js`'s `issueAsset()` before relying on the "already issued" global check, so that a capped asset can never be defined by an AA without restricting issuance to the AA itself.

### Proof of Concept
1. Deploy an AA whose definition includes a nested asset message:
```
{
  app: 'asset',
  payload: { cap: 1000000, is_private: false, is_transferrable: true, auto_destroy: false,
             fixed_denominations: false, issued_by_definer_only: false, cosigned_by_definer: false,
             spender_attested: false }
}
```
This passes `aa_validation.js` validation because `issued_by_definer_only` is only restricted when `true`, per `aa_validation.js:297-300`.

2. Once the AA response unit that defines this asset stabilizes, the asset id (the defining unit hash) is public.

3. Before the AA's oscript logic triggers the `issueAsset()` branch (e.g., before the first crowdsale contribution is processed), an attacker crafts and broadcasts an ordinary `payment` unit, single-authored by an arbitrary address, with:
```
inputs: [{ type: 'issue', amount: <cap>, serial_number: 1 }],
outputs: [{ address: <attacker_address>, amount: <cap> }],
asset: <asset_unit>
```
This passes `validatePaymentInputsAndOutputs` in `validation.js` because `issued_by_definer_only` is `false`, so no definer check is applied (`validation.js:2329-2353`), and `input.amount === objAsset.cap` is satisfied.

4. When the AA later executes `issueAsset()` (`aa_composer.js:1195-1200`), the query `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` now returns a row, so the AA's issuance attempt returns `'already issued'` and the triggering unit is bounced, permanently blocking that AA's ability to issue the capped asset it depends on.
