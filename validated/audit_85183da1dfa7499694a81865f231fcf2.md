### Title
Coins/tokens sent to an AA-issued asset (or plain AA payment) outside a matching `if` case are silently and permanently destroyed instead of refunded — supply/peg loss for AA-based token issuers (`File: aa_composer.js`)

### Summary
An Autonomous Agent (AA) that issues a custom asset representing a claim on funds it holds (ICO tokens, pool shares, wrapped/pegged tokens, etc.) relies entirely on its own `messages.cases[].if` formulas to decide when to honor a redemption/refund. If a user's payment to the AA (sending the asset back, or bytes in) does not exactly satisfy any case condition, the AA composer treats the whole trigger as a no-op that is unconditionally consumed — the incoming funds/tokens are "eaten" with **no bounce and no compensating payment**, while any locked backing value (bytes/other asset) held by the AA remains untouched. This is the same bug class as the reported `L2ECO.burn()` issue: a user-reachable path destroys/locks value on one side of a peg (the AA-issued token) without the corresponding release of the backing value, breaking the 1:1 relationship the token is supposed to represent.

### Finding Description
When a unit pays to an AA address, `aa_composer.js` builds a `trigger` from all payment outputs addressed to that AA, across every asset present in the unit (`getTrigger`, `aa_composer.js:375-397`). The AA's `messages.cases` are evaluated in order and only the first case whose `if` formula is true produces response messages (`aa_composer.js:1868-1886`).

Critically, if **no** case matches (or the matching case's messages get filtered out), the composer does not bounce and does not return the received funds:
```
messages = messages.filter(...);
if (messages.length === 0) { // eat the received coins and send no response, state changes are still performed
    error_message = 'no messages after filtering';
    return handleSuccessfulEmptyResponseUnit(null);
}
``` [1](#0-0) 

`handleSuccessfulEmptyResponseUnit` finishes the trigger successfully (not a bounce), so any coins/tokens sent are simply absorbed into the AA's balance with no acknowledgment or refund [2](#0-1) . This "eat the coins" behavior is confirmed by the test suite, where a payment that produces `amount * 0` still results in the trigger's funds being kept by the AA and only reported as "no messages after removing 0-outputs, then no state changes" [3](#0-2) .

Real AA templates shipped in the repo rely on this exact "send token back to the AA" pattern as the *only* redemption path, e.g. `test/samples/ico_with_milestones.oscript`, where the refund case only fires under narrow, state-dependent conditions:
```
{ // refund
  if: `{$asset AND trigger.output[[asset=$asset]] > 0 AND $finished AND var['total'] < $target}`,
  messages: [ { app:'payment', payload:{ asset:'base', outputs:[{address:"{trigger.address}", amount:"{round(trigger.output[[asset=$asset]] * $price)}"}]}}]
}
``` [4](#0-3) 

Any token holder who sends the ICO token back to the AA address *before* `$finished` is set, or *after* the ICO already met its target (`var['total'] >= $target`), falls through every case in the array; the tokens are consumed by the AA with zero compensation and no state update crediting the sender. The underlying bytes the token was meant to be redeemable against stay fully intact in the AA's balance, so the token supply the AA still considers "outstanding" (as tracked in patterns like `var['mm_asset_outstanding']` in `test/samples/uniswap_like_market_maker.oscript`, lines 62-63/83) is not reduced to match — an unaccounted, permanent value loss for the sender and a peg mismatch between the AA's issued asset and its backing reserve, mirroring the `L2ECO.burn()` report's "L2 tokens destroyed while L1 collateral stays locked" scenario.

The situation is even more absolute for assets explicitly defined with `auto_destroy: true` and `issued_by_definer_only`/`is_transferrable:false` pointing at the AA as definer: the protocol layer treats any payment to the definer address as a valid, final transferability exception [5](#0-4)  and marks outputs owned by that address for that asset as destroyed — never selectable again even by the AA itself [6](#0-5) , and rejected as spendable input for future issuance/transfer [7](#0-6) . Combined with the "eat the coins on no matching case" behavior above, this makes destruction unconditional and irreversible at the consensus layer regardless of whether the AA's oscript logic actually processes the compensating leg of the exchange.

### Impact Explanation
Any unprivileged AA trigger sender can lose funds permanently by sending an AA-issued token (or any asset) back to the AA outside the AA author's anticipated exact case conditions. This:
- Destroys the value of the sent asset with no possibility of recovery (satisfies "AA fund loss or freezing").
- Leaves the AA's backing balance for that asset/byte reserve unchanged, so the ratio between outstanding AA-issued tokens and backing funds recorded in AA state variables becomes inconsistent with reality — a supply/peg mismatch analogous to the reported bridge issue.
- Is fully reachable by any address that posts a normal payment unit to a public AA address; no privileged role is required.

### Likelihood Explanation
This requires only an ordinary payment unit sent by any user to a live AA — no special timing relative to other actors, no malicious peer/hub/node behavior, and no elevated privileges. Templates shipped as canonical AA examples in this very repository (ICO refund, market-maker divestment) use exactly this "receive asset at definer address to trigger redemption" pattern, so any AA following this common idiom is exposed whenever a case's `if` guard can legitimately be missed by a normal user action (wrong timing, wrong state, rounding to zero, etc.).

### Recommendation
- In `aa_composer.js`, when no case matches and the trigger carries non-zero asset/byte outputs beyond bounce fees, prefer bouncing (returning the funds) over silently "eating" them, or at minimum surface this outcome so AA authors can react in `state` formulas (e.g. an explicit "else" default case that refunds unmatched payments).
- Provide AA authors a documented, tool-enforced pattern (or a language-level safeguard) ensuring every combination of `trigger.output` for AA-issued assets is either matched by an explicit case or defaults to refunding the asset, rather than falling through to a no-op success.
- Consider making `auto_destroy` combined with AA-as-definer require an accompanying, statically checked "catch-all" case so tokens can never be destroyed without the AA's state accounting being updated in the same response.

### Proof of Concept
1. Deploy an AA modeled on `test/samples/ico_with_milestones.oscript`, defining an ICO token asset with `issued_by_definer_only:true`.
2. As investor A, contribute bytes and receive ICO tokens via the "contribute" case.
3. Before the fundraiser calls `trigger.data.finish` (i.e., `$finished` is still false), send the received ICO tokens back to the AA address as a normal payment.
4. Observe: none of the `if` conditions match (`define` is false, `contribute` requires `output[[asset=base]]`, `finish`/`milestone` require specific trigger.data, `refund` requires `$finished`), so `messages.length === 0` and `handleSuccessfulEmptyResponseUnit` runs — confirmed by the "eaten coins" behavior demonstrated in `test/aa.test.js:1024-1076`.
5. The tokens are gone from investor A's balance permanently; the AA's `var['total']`/backing byte balance is unaffected, so the token supply vs. backing accounting used later in `finish`/`milestone`/`refund` calculations is now inconsistent with the actual number of tokens in circulation.
