Based on the investigation, I found a concrete binding mismatch in the webhook signature verification path.

### Title
Webhook signature verification is scoped to the payload's claimed organization, not the repository that handlers actually write to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository_owner`, a value read from the **unverified** JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). Every webhook handler, however, resolves the actual `Repository`/`Stack` to mutate using a **different** field from the same unverified body: `payload.dig('repository', 'full_name')` (via `Shipit::Webhooks::Handlers::Handler#repository_name`). In a multi-organization Shipit deployment (`docs/setup.md` "Using Multiple Github Applications"), these two fields are never checked against each other, and the signature computed by GitHub only covers the raw byte payload — it does not bind "owner" to "full_name" from Shipit's perspective, and Shipit doesn't cross-check them either.

### Finding Description
The relevant code is: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

and [2](#0-1) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) only validates that the HMAC of the raw body matches the secret configured for the org picked via `repository_owner`; if that org has no `webhook_secret` configured (`return true unless webhook_secret`), verification trivially passes for *any* payload claiming that owner, regardless of content. Because `repository_owner` and `repository_name`/`full_name` are two independent, attacker-controlled fields inside the same unsigned-by-Shipit JSON body, an attacker who can produce a valid signature for organization A (e.g., because A has no `webhook_secret` set, or because they know/leak A's secret) can set `repository.owner.login = "A"` (to pass `verify_signature`) while setting `repository.full_name = "B/some-repo"` (to make the push/pull_request/status handler act on a stack belonging to a completely different, secured organization B). The equality that should hold — "the organization whose secret authenticated this webhook" == "the repository the handler is about to mutate" — is never enforced.

### Impact Explanation
This allows cross-repository/cross-organization forged webhook delivery: an attacker can trigger `GithubSyncJob`, push handling, `check_suite`/`check_run` refreshes, `status` updates, or pull-request-driven review-stack provisioning/archival against a stack that belongs to an organization whose webhook secret the attacker does not know, as long as they can satisfy verification for any organization present in the Shipit config (including ones with no webhook secret configured at all, which the code treats as "always verified"). This crosses the "unauthorized deploy/rollback" boundary category since `sync_github`/push-triggered flows and check-run refreshes influence CI/deployability signals (`Commit#deployable?`) that gate deploys.

### Likelihood Explanation
Likelihood is elevated in the documented multi-org setup, where operators are explicitly told they can leave `webhook_secret` blank per org (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml` all show `webhook_secret: # nil`). Any org left without a secret becomes a free pass to forge `repository.owner.login` for that org while targeting arbitrary `repository.full_name` values across the whole installation. No prior credential is required against the target org; the attacker only needs to be able to hit the shared `/webhooks` endpoint and pick a "no-secret" or otherwise-known-secret org as their spoofed owner.

### Recommendation
In `WebhooksController#verify_signature`/`create`, or in `Shipit::Webhooks::Handlers::Handler`, require that the organization used to select the webhook secret (`repository_owner`) match the owner embedded in `repository.full_name` before any handler resolves stacks/repositories to mutate. Additionally, consider treating a missing `webhook_secret` as "reject all webhooks for this org" rather than "accept unconditionally," or require a webhook secret for every configured organization.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orgA` (no `webhook_secret`) and `orgB` (has stacks and a secret, unknown to attacker).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/production-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: 'orgA')`; since `orgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`), regardless of the (even absent) `X-Hub-Signature` header.
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('orgB/production-repo')` and calls `stack.sync_github(expected_head_sha: ...)` on the orgB stack — an org the attacker never authenticated against.
