## Finding

### Title
Unhandled Exception in `definition template` Evaluation Crashes Node - (File: `definition.js`)

### Summary
`ocore`'s address-definition language supports a `['definition template', ['unit', params]]` operator that looks up a previously posted `definition_template` message by unit id and fills a template with attacker/user-supplied parameters. The lookup code assumes exactly one matching row will be returned and `throw`s an uncaught `Error` otherwise. Because nothing in the codebase enforces that a referenced unit contains exactly one `definition_template` message, an attacker can post a unit containing two (or zero, though zero is the harder-to-hit case) `definition_template` messages and later reference that unit from a `definition template` op in any address/asset condition or AA-reachable definition. When that condition is evaluated during normal validation of a subsequent unit, the synchronous `throw` inside the SQL callback escapes all `try/catch` boundaries in the async validation pipeline and is caught only by the top-level `process.on('uncaughtException')` handler in `network.js`, which re-throws to intentionally crash the process.

### Finding Description
The vulnerable code is in `evaluate()` inside `validateDefinition`/`validateAuthentifiers` of `definition.js`: [1](#0-0) 

```
case 'definition template':
    ...
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            ...
```

The query filters by `unit` and `app='definition_template'` but not by `message_index`, so if the referenced unit contains **more than one** message with `app='definition_template'`, `rows.length` will be `>1` and the `throw` fires. Nothing earlier in unit-content validation restricts the number of `definition_template` messages a single unit may carry (unlike, e.g., the one-per-address restriction enforced for `address_definition_change`, see `validateInlinePayload` at [2](#0-1) , which explicitly limits definition changes to one per address — no analogous limit exists for `definition_template`).

This mirrors the CVE-2024-54129 bug class: a message/reference that is syntactically valid and passes the generic structural checks (a legitimate `unit` id, a well-formed `definition_template` payload) but is not properly validated against an implicit invariant ("exactly one template exists for this reference") assumed by the downstream handling code, leading to an unhandled fault that takes the whole node down instead of being reported as a benign validation error.

Because the `throw` happens inside a SQL callback (`conn.query(...)`), it is asynchronous relative to the `evaluate()` call stack, so it cannot be intercepted by any caller-level `try/catch`. It surfaces only at the process level: [3](#0-2) 

```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

### Impact Explanation
Any unprivileged unit poster can: (1) post one unit containing two `definition_template` messages (a purely self-contained, valid-looking unit), wait for it to become stable, then (2) post/trigger validation of any other unit (a normal payment, an AA trigger, or a shared-address/asset definition referencing `['definition template', [<unit_of_step_1>, {...}]]`) whose address/asset condition is evaluated by any full node during ordinary unit validation. Evaluating that condition causes every full node that processes the referencing unit (which is required for consensus/witnessing/relaying) to crash. This matches the "network unable to confirm new units"/node-disagreement class: a crashed node stops validating/witnessing until manually restarted, and if the crash is deterministic and widely propagated (units are gossiped to all peers), it can be used to repeatedly take down multiple/most full nodes in the network, disrupting confirmation of new units.

### Likelihood Explanation
Likelihood is high for a technically capable attacker: posting a unit with two `app='definition_template'` messages requires no special privilege (any unit author can add arbitrary messages up to `MAX_MESSAGES_PER_UNIT`), and referencing it via `definition template` in an address/asset/AA definition is a documented, ordinary feature. No signature, funds, or special role is required beyond the ability to post units, which is the baseline capability assumed by the threat model.

### Recommendation
- In the `definition template` lookup query in `definition.js`, either constrain the query to a single, unambiguous message (e.g., include `message_index` in the reference, matching how other by-unit-message references work) or treat `rows.length !== 1` as a normal validation failure (`return cb2(false)` / `cb("template not found")`) instead of `throw`.
- Add a structural validation rule (mirrored on the `address_definition_change` one-per-unit restriction) limiting units to at most one `definition_template` message, closing the root cause at the source.
- Audit other `throw Error(...)` statements inside asynchronous `conn.query` callbacks reached from `evaluate()` in `definition.js` (e.g., the "more than 1 address definition" checks) for the same non-catchable-crash pattern, even though those particular ones are currently unreachable due to unique-author-address enforcement.

### Proof of Concept
1. Attacker posts unit `U1` with two messages: `{app: 'definition_template', payload: <template A>}` and `{app: 'definition_template', payload: <template B>}`. This unit passes all current structural checks and becomes stable.
2. Attacker (or anyone) creates a new address/asset condition, AA definition, or shared-wallet definition template containing `['definition template', ['U1', {param1: 'value1'}]]` and posts/references it (e.g. as part of an authentifier evaluation for a later unit spending from/authored by that address, or inside an AA trigger condition).
3. When any full node validates the referencing unit and evaluates this address/asset condition, `evaluate()` runs the `definition template` branch; the SQL query returns 2 rows for `unit=U1`; `rows.length !== 1` is true; `throw Error("not 1 template")` executes inside the async callback.
4. This exception is uncaught by any surrounding logic and is only caught by `process.on('uncaughtException')` in `network.js`, which re-throws and crashes the node process, matching the "unresponsive/crash on properly-formed-but-improperly-initialized reference" bug class described in CVE-2024-54129.
