### Title
Permanently Undeliverable KLAY Bridge Transfer Locks User Funds With No Recovery Path — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`handleKLAYTransfer` in the service-chain bridge performs all nonce-accounting state updates and then calls `_to.call.value(_value)("")`, requiring the call to succeed. If the destination address is a contract that reverts on receiving KLAY (due to a bug, upgrade, or deliberate design), the entire transaction reverts, the nonce is never marked handled, `lowerHandleNonce` never advances past it, and the user's KLAY locked in the source bridge is permanently unrecoverable. No cancel or refund path exists.

### Finding Description

When a user calls `requestKLAYTransfer` on the source bridge, KLAY is locked in the contract and a `RequestValueTransfer` event is emitted with a monotonically increasing `requestNonce`. Bridge operators observe this event and call `handleKLAYTransfer` on the destination bridge.

Inside `handleKLAYTransfer`:

```solidity
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");   // ← reverts everything above
``` [1](#0-0) 

Because the `require` is placed after the state-mutating calls, a revert from `_to` rolls back `handleNoncesToBlockNums[_requestedNonce]`, the `_updateHandleNonce` advancement, and the event emission. The nonce is therefore never recorded as handled.

`_updateHandleNonce` advances `lowerHandleNonce` only through a consecutive run of handled nonces:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [2](#0-1) 

If nonce N is permanently stuck, `lowerHandleNonce` never advances past N and `recoveryBlockNumber` never advances past the block of nonce N−1. The value-transfer recovery daemon (`vt_recovery.go`) uses `recoveryBlockNumber` as its scan start: [3](#0-2) 

It will re-queue the stuck event on every recovery interval, but every retry will also revert, creating an infinite retry loop with no forward progress.

There is no `cancelTransfer`, `refundKLAY`, or skip-nonce function anywhere in the bridge contract suite.

### Impact Explanation

The user's KLAY is permanently locked in the source bridge contract. The destination never receives the funds. Because `lowerHandleNonce` is frozen, the `recoveryBlockNumber` is also frozen, causing the recovery daemon to re-scan the same historical block range indefinitely. This is a permanent, irrecoverable loss of bridged KAIA for the affected transfer.

### Likelihood Explanation

Any of the following realistic conditions trigger the issue:

1. The destination is a smart-contract wallet or multisig that has been paused, upgraded to remove its `payable` fallback, or has a reentrancy guard that rejects the bridge's call.
2. The destination contract is deliberately constructed to revert (griefing a specific user's bridge transfer).
3. The destination contract runs out of gas in its receive hook (gas stipend from `.call.value()` is 2300 in Solidity 0.5.x, which is insufficient for many contracts).

The user specifies `_to` at request time; by the time operators handle the transfer the contract state may have changed. No operator-side check can detect this before submitting the transaction.

### Recommendation

Apply the checks-effects-interactions pattern correctly: perform the external KLAY transfer **before** recording the nonce as handled, or — more robustly — implement a pull-payment pattern where the recipient claims KLAY rather than having it pushed. Additionally, add an owner-callable `skipHandleNonce` function (analogous to `indicesToSkip` in EigenLayer's `slashQueuedWithdrawal`) that allows operators to mark a nonce as permanently skipped and advance `lowerHandleNonce`, so that subsequent transfers are not indefinitely stalled by the recovery daemon.

### Proof of Concept

1. Alice calls `requestKLAYTransfer(address(maliciousContract), 1 ether, "")` on the source bridge. KLAY is locked; `requestNonce` becomes N.
2. Operators call `handleKLAYTransfer(..., N, ...)` on the destination bridge.
3. `maliciousContract.receive()` reverts. The entire `handleKLAYTransfer` transaction reverts.
4. `handleNoncesToBlockNums[N]` remains 0; `lowerHandleNonce` stays at N; `recoveryBlockNumber` stays at the block of nonce N−1.
5. The VTR daemon (`vt_recovery.go`) detects `requestNonce > handleNonce`, re-queues the event, and retries — forever.
6. Alice's 1 KLAY is permanently locked in the source bridge with no refund path. [4](#0-3) [5](#0-4) [6](#0-5)

    // _updateHandleNonce increases lower and upper handle nonce after the _requestedNonce is handled.
    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }

    function _lowerHandleNonceCheck(uint64 _requestedNonce) internal {
