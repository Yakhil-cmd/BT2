### Title
`Api::CCMenuController#stack` bypasses the `stack_id`-scoping enforced by `Api::BaseController#stacks` - ([File: app/controllers/shipit/api/ccmenu_controller.rb#stack])

### Summary
`Api::BaseController` restricts API clients whose `stack_id` is set to only see their own stack via the `stacks` scope, but `Api::CCMenuController` overrides `#stack` to resolve directly from `Stack.from_param!(params[:stack_id])`, skipping the `stacks` scope entirely. Any API client holding the generic `read:stack` permission — even one intended to be locked to a single stack — can fetch the CCMenu XML (deploy status, most recent deploy/rollback) for any other stack on the instance.

### Finding Description
The binding claimed by the base controller is: `Api::BaseController#stack` == an element of `Api::BaseController#stacks`, i.e. `stacks.from_param!(params[:stack_id])` [1](#0-0) . This scoping is what would make `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` meaningful for stack-restricted tokens.

`Api::CCMenuController` however defines its own private `#stack`: [2](#0-1) 
which calls `Stack.from_param!(params[:stack_id])` directly, never touching `stacks`/`current_api_client.stack_id`. The only authorization check performed is `require_permission :read, :stack`, which resolves in `ApiClient#check_permissions!` to a purely name-based check — `permissions.include?("read:stack")` — with no per-stack scoping: [3](#0-2) .

Exploit flow: an attacker who obtains (or is issued) any token carrying the `read:stack` permission — regardless of whether `ApiClient#stack_id` is set to a specific stack — can call `GET /api/stacks/*stack_id/ccmenu?token=...` with an arbitrary `stack_id` for a stack they are not scoped to, and `show` will render that other stack's CCMenu project XML (latest deploy/rollback status) [4](#0-3) .

Existing guards do not prevent this: `authenticate_api_client` only validates the token itself [5](#0-4) ; `require_permission!`/`check_permissions!` checks only the operation:scope name, not which stack the token is bound to; and the `stacks` scoping method that would enforce `current_api_client.stack_id` restriction is never invoked because `#stack` is fully overridden.

One caveat found while tracing the specific precondition in the question: the in-app token minting flow `CCMenuUrlController#fetch` creates its `ApiClient` via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator:, name: 'CCMenu Client')`, which never sets `stack_id` [6](#0-5) . So tokens minted by that specific endpoint are already global (`stack_id` nil) and `stacks` would resolve to `Stack.all` for them anyway — the `fetch` flow itself does not demonstrate a "narrowly-scoped" token. However, `ApiClient` model does support `stack_id` (`belongs_to :stack, optional: true`) [7](#0-6) , and any such stack-scoped token (created by an operator through the console/other means) is subject to this bypass — the vulnerability is in the controller override itself, independent of how the scoped token was minted.

### Impact Explanation
A holder of any token with `read:stack` permission can read cross-tenant stack build/deploy state (latest deploy/rollback id and status) for stacks outside their intended scope, via `Api::CCMenuController#show`. This is a confidentiality bypass of the per-token stack restriction (`ApiClient#stack_id`) that the rest of the API (`stacks_controller`, etc., via `Api::BaseController#stack`) correctly enforces. This matches "High - unauthenticated/unauthorized read of stack state" since it defeats the intended per-token authorization scoping across arbitrary stacks, and is repeatable for every stack on the instance with a single request each.

### Likelihood Explanation
Exploitation requires possession of a valid API token with `read:stack` permission. If that token is stack-scoped (`ApiClient#stack_id` set), which is a supported and presumably intended restriction mechanism, the attacker only needs to know or guess another stack's `stack_id` param (repo/branch/environment based, easily enumerable) — no further authentication or privilege is required. The main uncertainty is how commonly operators create stack-scoped tokens in practice, since the in-app UI (`ApiClientsController`) does not expose setting `stack_id`, and the only in-code minting path found (`CCMenuUrlController#fetch`) produces unscoped tokens. Thus the divergence in `CCMenuController#stack` is a genuine code defect, but real-world exploitability depends on the existence of a stack-scoped `ApiClient` record, which must be created by some other (unverified/out-of-index) mechanism.

### Recommendation
Remove the private `#stack` override in `Api::CCMenuController` and instead reuse the inherited `#stack` (which resolves via the scoped `#stacks`), or explicitly scope: `@stack ||= stacks.from_param!(params[:stack_id])`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
module Shipit
  module Api
    class CCMenuControllerScopingTest < ActionController::TestCase
      tests Shipit::Api::CCMenuController

      test "a stack-scoped api client cannot read another stack's ccmenu" do
        owned_stack = shipit_stacks(:shipit)
        other_stack = shipit_stacks(:cyclimse) # any other fixture stack
        client = ApiClient.create!(
          creator: shipit_users(:walrus),
          name: 'scoped-client',
          permissions: %w[read:stack],
          stack_id: owned_stack.id,
        )

        get :show, params: { stack_id: other_stack.to_param, token: client.authentication_token }

        # Binding under test: Api::BaseController#stack (scoped) vs
        # Api::CCMenuController#stack (unscoped) — assert they diverge.
        assert_not_equal owned_stack.id, other_stack.id
        assert_response :success # currently succeeds — should be :not_found / 403
        assert_includes response.body, other_stack.to_param
      end
    end
  end
end
```
This demonstrates that `Api::CCMenuController#stack` resolves `other_stack` even though `Api::BaseController#stacks` for this client would only ever yield `owned_stack`.
