### Title
Stack-scoped API tokens can read CCMenu build status of any stack, not just the stack they were bound to - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` records can be restricted to a single stack via `belongs_to :stack, optional: true`, and `Api::BaseController` enforces that binding for every other API endpoint by resolving the requested stack through the `stacks` scope, which filters by `current_api_client.stack_id` when the client is stack-scoped. `Api::CCMenuController`, however, overrides the `stack` accessor to resolve the stack directly from `Stack.from_param!`, completely bypassing the per-client stack restriction, so any stack-scoped, `read:stack`-permissioned token can read the CI/build status of an arbitrary stack by simply changing the `stack_id` in the URL.

### Finding Description
`Api::BaseController#stack` is the authorization-aware accessor used by the rest of the JSON API: [1](#0-0) 
`stacks` is deliberately narrowed to `current_api_client.stack_id` when the authenticated `ApiClient` is bound to one stack — this is the equality the engine relies on: *stack a token authorises == stack it touches*.

`Api::CCMenuController` is mounted under a completely separate, unauthenticated-by-default route (`/ccmenu/*stack_id`, resolved via `token` query param rather than HTTP Basic auth) and re-implements `stack` without going through the `stacks` scope: [2](#0-1) 

Note the `authenticate_api_client` override here also fetches an `ApiClient` purely by `params[:token]` via `ApiClient.authenticate`, which only verifies the signed id — it does not re-check that the resolved client's `stack_id` (if any) matches the `stack_id` in the request. Then `require_permission :read, :stack` (declared at the class level) only checks that the token carries the string permission `read:stack` in its `permissions` array — it has no knowledge of which specific stack the request is for: [3](#0-2) 

So the binding that should hold — *the stack this specific token is authorized for == the stack whose data is returned* — is broken specifically for the CCMenu endpoint, because it resolves `stack` with `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!(params[:stack_id])` used everywhere else (e.g. `Api::DeploysController`, `Api::StacksController`, which inherit `stack` from `BaseController`).

### Impact Explanation
An attacker who already legitimately possesses (or otherwise obtains, e.g. via a leaked CCMenu URL — these tokens are embedded directly in a plaintext URL query string as shown in `CCMenuUrlController#fetch`) a valid `read:stack`-permissioned API token that was meant to be scoped to a single stack can enumerate `stack_id` values and read the CI/build status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of every other stack managed by the Shipit instance, not just the one the token creator intended to expose. This is an authorization-scope escalation: unauthenticated-relative-to-other-stacks read of stack state, matching the "unauthenticated read of stack state" High-impact category, since access to arbitrary stacks' deploy status was never granted to that token.

### Likelihood Explanation
Likelihood is high for anyone already holding a single stack-scoped CCMenu/API token (a routine, low-privilege artifact deliberately generated and shared for CI dashboard integrations per `CCMenuUrlController`): no additional secrets, sessions, or elevated permissions are needed — only changing the `stack_id` segment of the URL that already carries their own token.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack through the same authorization-aware scope used elsewhere, e.g. `stacks.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction is honored consistently across all API surfaces, including CCMenu.

### Proof of Concept
1. As a stack admin, create (or have the system create, e.g. via `CCMenuUrlController#fetch`) an `ApiClient` scoped to `stack_id: A` with permission `read:stack`, and note its `authentication_token`.
2. Send `GET /ccmenu/*B?token=<tokenScopedToA>` where `B` is any other stack in the instance.
3. Because `Api::CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` instead of the client-scoped `stacks.from_param!`, and `require_permission :read, :stack` only checks the permission string, the request succeeds and returns stack `B`'s CCMenu build-status XML, even though the token was only authorized for stack `A`.
