### Title
Cross-organization Team/Membership write via `organization.login` vs `repository_owner` provenance divergence in `MembershipHandler` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` derives the signing organization ("provenance") solely from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')` only when `repository` is absent), while `MembershipHandler#find_or_create_team!` scopes the created/updated `Team` to `params.organization.login` unconditionally. Because a `membership` webhook payload can contain both an attacker-crafted `repository` key and an independent `organization` key, and nothing anywhere asserts they refer to the same org, an attacker who can satisfy signature verification for org A can write a `Team`/`Membership` scoped to an arbitrary org B.

### Finding Description
The broken binding, stated as an equality that the code never enforces: `repository_owner (org used by GithubApp#verify_webhook_signature) == params.organization.login (org written into Team#organization)`.

Code path:
- `WebhooksController#verify_signature` resolves the signer via `repository_owner`, which prefers `repository.owner.login` over `organization.login`: [1](#0-0) 
- `Shipit.github(organization: repository_owner)` looks up a per-organization `GitHubApp` config and calls `verify_webhook_signature`, which explicitly *passes* when no `webhook_secret` is configured for that org: [2](#0-1) 
- `MembershipHandler#find_or_create_team!` never reads `repository_owner`/`repository`; it scopes the new `Team` purely off `params.organization.login`, which is a completely separate field with no cross-check against the org that was actually verified: [3](#0-2) 

Attacker request: an unprivileged internet user POSTs directly to `/webhooks` with `X-Github-Event: membership`, a body containing `repository: { owner: { login: "orgA" } }` where `orgA` is any org configured in Shipit without a `webhook_secret` (so `verify_webhook_signature` unconditionally returns `true`), and `organization: { login: "orgB" }` where `orgB` is the attacker's real target. `find_or_create_team!` then creates/updates a `Team` record with `organization: "orgB"` and applies the `team.add_member(member)` / `team.members.delete(member)` mutation, without orgB ever having signed or even seen the request.

Root cause: the two org-identifying fields (`repository.owner.login` used for provenance, `organization.login` used for mutation scope) are read from disjoint parts of the same attacker-controlled JSON body and are never compared. `Team.find_or_create_by!(github_id: params.team.id)` further means the mutation also depends only on an attacker-supplied numeric `team.id`, with no repository/org ownership check at all. Existing guards do not close this gap: `verify_signature` only proves the request was signed by *some* org (or was unsigned but that org has no secret configured); it says nothing about `params.organization`. The `ExplicitParameters` schema in `MembershipHandler.params` only validates types/presence, not cross-field equality.

### Impact Explanation
A successful request creates or mutates a `Team`/`Membership` row attributed to an organization (`orgB`) that never authenticated the request; the write is fully repeatable against any org name the attacker chooses. If `orgB`'s handle is later referenced by `Shipit.github_teams` (`github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }`, used for OAuth-team-based authorization) [4](#0-3) , an attacker-controlled `github_id`/`member` could pre-seed or tamper with `Team`/`Membership` records that back that authorization check, i.e., escalation into `Shipit.github_teams` authorization — matching the High severity category for authorization escalation. The blast radius spans every organization configured on the Shipit instance, since the attacker only needs one org (anywhere) with a missing `webhook_secret` to stage the bypass and can target any other org's handle as the mutation scope.

### Likelihood Explanation
Preconditions: at least one organization must be registered in Shipit's `secrets.github` multi-org config without a `webhook_secret` set (this is an explicitly supported, non-error configuration per `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret`). The attacker needs no session, token, or secret — only the ability to know that org's login (often discoverable/guessable) and to POST arbitrary JSON to `/webhooks`. This is low-cost and fully repeatable/scriptable. The main uncertainty is deployment-dependent: in the "legacy" single-org config schema, `Shipit.github(organization:)` ignores the passed organization and always uses the single global config [5](#0-4) , which does not change the underlying flaw (the handler still uses `organization.login` unchecked) but does change how signature bypass is achieved.

### Recommendation
In `MembershipHandler`, require and enforce that the org used to authorize the webhook equals the org being mutated, e.g., pass the verified `repository_owner`/signer organization into the handler and assert `params.organization.login.casecmp?(verified_organization)` before calling `find_or_create_team!`, raising/dropping the event on mismatch. More generally, `WebhooksController#verify_signature` should not silently fall back from `repository.owner.login` to `organization.login`; it should use the field the specific handler actually trusts for scoping, and handlers should never write org-scoped records from event fields that were not part of the verified provenance.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (proof-of-concept, minitest)
test ":membership can write a Team scoped to an organization that never signed the request" do
  @request.headers['X-Github-Event'] = 'membership'

  # org used for signature verification (attacker's own / secret-less org)
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true)
  )

  payload = {
    action: 'added',
    team: { id: 999, name: 'Injected', slug: 'injected', url: 'https://example.com' },
    organization: { login: 'victim-org' },       # <- mutation scope
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } } # <- provenance/signature scope
  }.to_json

  assert_difference -> { Team.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  team = Team.find_by(github_id: 999)
  refute_nil team
  assert_equal 'victim-org', team.organization
  refute_equal 'attacker-org', team.organization # signer org != mutated org
end
```
This demonstrates that `repository_owner` (`attacker-org`, used in `verify_signature`) and `Team#organization` (`victim-org`, written by `find_or_create_team!`) diverge, with no assertion anywhere binding them together.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
