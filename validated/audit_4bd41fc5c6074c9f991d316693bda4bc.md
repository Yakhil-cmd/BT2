### Title
Webhook signature verified against payload-supplied `repository.owner.login` while all event handlers act on the independently-attacker-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp`/webhook secret to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body, then verifies the signature using that organization's configured secret. [1](#0-0)  Once the signature check passes, the raw, unmodified payload is dispatched to every registered handler. [2](#0-1)  Those handlers determine which repository/stack to mutate not from `repository.owner.login`, but from a separate field, `repository.full_name`. [3](#0-2)  Nothing binds these two fields together, so the organization whose secret authenticated the request is not necessarily the repository that gets written.

### Finding Description
The equality that should hold is:

`organization whose webhook secret signed the request == organization owning the repository the handler mutates`

In this engine that binding is implemented as two independent JSON reads of the same untrusted, attacker-supplied payload:

- Verification side: `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, used to look up `Shipit.github(organization: repository_owner)` and verify `X-Hub-Signature` with that organization's secret. [1](#0-0) [4](#0-3) 
- Execution side: `Shipit::Webhooks::Handlers::Handler#repository_name` reads `payload.dig('repository', 'full_name')` and resolves it to a `Repository`/`Stack` via `Repository.from_github_repo_name(repository_name)`, which is the target that gets synced, has commits appended, statuses updated, PRs closed, etc. [3](#0-2) 

Because `repository.owner.login` and `repository.full_name` are two separate JSON keys inside the same attacker-forgeable payload, an entity that legitimately owns a GitHub App/organization already onboarded to this Shipit instance (and therefore knows or can trigger deliveries signed with that organization's `webhook_secret`) can send a body where `repository.owner.login` equals their own organization (so `verify_webhook_signature` succeeds against their own secret) while `repository.full_name` is set to `"other-org/other-repo"` — a completely different, unrelated organization's repository tracked by the same Shipit instance. `verify_signature` never re-checks that the organization used for verification matches the organization embedded in `full_name`; it only fails closed on `GithubOrganizationUnknown` (unrecognized org), not on a mismatch between two valid orgs. [5](#0-4) 

For example the `push` handler flow: the controller verifies the signature using org A's secret, then dispatches to handlers using `full_name = "orgB/target"`, and `GithubSyncJob` is enqueued for whatever `Stack` matches that resolved repository — pulling commits, changing commit/task state, marking stacks (in)accessible, etc. for org B's stack, despite the request only ever being cryptographically authenticated as coming from org A. [6](#0-5)  The same disconnect applies to every other handler that derives `stacks`/`repository_name` from `full_name` (`pull_request` opened/closed/labeled handlers, `status`, `check_suite`, etc.), all of which inherit `Handler#repository_name`/`#stacks`. [7](#0-6) 

### Impact Explanation
This breaks the deployment-trust binding between "the organization that authenticated the webhook" and "the repository that is written," letting a party who controls one onboarded GitHub organization's webhook secret spoof events that mutate the tracked state (commits, CI statuses, check suites, PR/merge-queue state, stack accessibility) of an entirely different organization's Stack in the same Shipit install. Depending on which handler is exercised (`pull_request` closed/merge-queue handlers, `status`, `check_suite`), this can influence what commits are considered deployable/mergeable or trigger cross-repository automation without ever needing that other organization's actual webhook secret — a cross-repository write across an authentication boundary that is not supposed to be crossable. It qualifies as High/Critical under the given rubric (cross-repository write via a broken deployment-trust binding).

### Likelihood Explanation
Requires the attacker to control (or be a legitimate admin of) at least one GitHub organization already configured in this Shipit instance's `Shipit.github_apps`-style config with a known `webhook_secret`, and to be able to send an arbitrary crafted webhook body to the public `/webhooks` endpoint signed with that org's secret — both are attacker-achievable without any Shipit session, API token, or GitHub repository write access to the victim org, since the webhook body's `repository.owner.login` and `repository.full_name` are fully attacker-controlled JSON fields with no GitHub-side consistency enforcement by Shipit. This is a realistic scenario for any Shipit instance onboarding multiple independent organizations/tenants.

### Recommendation
After computing `repository_owner` for signature verification, re-derive the organization from `repository.full_name` (i.e., `full_name.split('/').first`) and reject the request (422) unless it matches `repository_owner`/`organization.login` used for verification, ensuring the org whose secret signed the payload is the same org that owns the repository the handlers will act upon.

### Proof of Concept
1. Shipit instance has two configured GitHub organizations, `org-a` and `org-b`, each with its own `webhook_secret`, and tracks a Stack for `org-b/target-repo`.
2. Attacker (an admin of `org-a`, or anyone who has captured `org-a`'s `webhook_secret` through a lesser-privileged channel) POSTs to `/webhooks` with:
   - Header `X-Github-Event: push`
   - Header `X-Hub-Signature` computed as `sha1=` HMAC over the body using `org-a`'s `webhook_secret`
   - Body: `{"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/target-repo"}, "after": "<attacker-chosen sha>", ...}`
3. `verify_signature` calls `Shipit.github(organization: 'org-a')` (from `repository.owner.login`) and successfully verifies the signature against `org-a`'s secret. [1](#0-0) 
4. `create` dispatches the same payload to the `push` handler, which resolves `repository_name` from `full_name` = `"org-b/target-repo"` and enqueues `GithubSyncJob` for `org-b`'s stack, causing Shipit to fetch/append commits and change stack state for `org-b`'s repository — despite the request never being signed by `org-b`. [3](#0-2) [6](#0-5)

      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
