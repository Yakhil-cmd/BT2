### Title
Missing cap/denominations consistency check in AA asset definitions causes uncaught crash - (File: `aa_validation.js`)

### Summary
`aa_validation.js`'s validation of an `asset` message issued by an Autonomous Agent (`case 'asset':`) never checks that `cap` and the sum of `denominations[].count_coins * denomination` are consistent, unlike the equivalent check performed for ordinary user-authored asset definitions in `validation.js`. An AA can therefore publish an internally inconsistent asset (e.g. `cap` set but `denominations` uncapped, or vice versa). When any wallet later tries to compose an indivisible (fixed-denomination) payment for that asset, `indivisible_asset.js` hits an unconditional `throw Error("invalid asset cap and count_coins")` inside an async DB callback, crashing the node process. This mirrors CVE-2022-49707: a feature flag (`resize_inode`/`cap`) and a dependent count (`s_reserved_gdt_blocks`/`count_coins`) are allowed to diverge because a consistency check present on one code path is missing on another, and downstream code assumes the invariant holds, causing an unhandled fault.

### Finding Description
For ordinary (human-authored) asset definitions, `validateAssetDefinition()` in `validation.js` enforces that `cap` matches the sum of capped denominations and rejects mixed capped/uncapped denomination sets: [1](#0-0) 

However, when an Autonomous Agent defines an asset via a `case 'asset':` message inside its bytecode, the validator in `aa_validation.js` only checks each field's own type/range (cap format, denomination format, count_coins format) but never cross-checks `cap` against the aggregate of `denominations[].count_coins`: [2](#0-1) 

This lets an AA author (or an AA whose logic composes such a payload from user-controlled trigger data) publish an asset where, for example, `cap` is a positive number but `denominations` contains only uncapped entries (no `count_coins`), or `cap` is absent/zero while `denominations` are capped. Because this payload passes AA validation, it is written verbatim into the `assets`/`asset_denominations` tables by `writer.js`, with no additional consistency check performed there either: [3](#0-2) 

Later, when any wallet/node composes a fixed-denomination payment spending or issuing this asset, `indivisible_asset.js`'s `issueNextCoin()` reads a denomination row and asserts the very invariant that was never validated at definition time: [4](#0-3) 

Because `!!row.count_coins !== !!objAsset.cap` is now true for the malicious asset, the code executes `throw Error("invalid asset cap and count_coins")` inside a database query callback. This throw is not passed through the `cb`/`onDone` callback chain used everywhere else in this function — it is a raw synchronous `throw` inside an asynchronous callback, which in Node.js becomes an uncaught exception and crashes the process.

### Impact Explanation
Any AA author can define such an inconsistent asset at zero cost (defining an asset in an AA is a normal, permissionless operation — asset definition and issuance are explicitly in-scope reachable actions for an unprivileged AA author). Once defined, the asset is a "landmine": every node/wallet (light or full) that attempts to compose an indivisible payment (issue or transfer) involving that asset will hit the uncaught `throw` and crash the ocore process. Because ocore is the shared core library used by full nodes, hubs, and wallets alike, this allows an attacker to deny service against any node that interacts with the poisoned asset — an availability impact on the specific node/wallet handling the asset, consistent with "AA fund loss or freezing" (funds tied to the asset can become unspendable because any attempt to compose a payment for it repeatedly crashes the composing node) and a node-availability failure for the affected process.

### Likelihood Explanation
High reachability, no special privileges required: any user can trigger an AA to emit an `asset` message with `fixed_denominations: true`, a numeric or formula `cap`, and a `denominations` array of purely uncapped (or mismatched) entries — none of the aa_validation.js checks (lines 226-336) reject this combination. The only barrier is that some wallet must subsequently try to compose a fixed-denomination payment for that asset, which is a normal action any holder or the AA itself (via user interaction) would eventually perform.

### Recommendation
Add the same cross-field consistency checks used in `validation.js`'s `validateAssetDefinition` (reject mixed capped/uncapped denominations, and require `total_cap_from_denominations === cap` when both are numeric literals) to the `case 'asset':` branch of `aa_validation.js`, including a corresponding check that runs after formula evaluation at AA execution time if either `cap` or `denominations`/`count_coins` are formulas resolved dynamically. Additionally, replace the raw `throw Error(...)` in `indivisible_asset.js:531-532` with a properly propagated error via the callback chain so that even a leftover inconsistency (e.g., from data written before the fix) degrades gracefully as an error to the caller instead of crashing the process.

### Proof of Concept
1. Publish an AA whose bytecode contains an `asset` message with:
   ```json
   {"app":"asset","payload":{
     "cap": 1000,
     "is_private": false, "is_transferrable": true, "auto_destroy": false,
     "fixed_denominations": true,
     "issued_by_definer_only": true, "cosigned_by_definer": false, "spender_attested": false,
     "denominations": [{"denomination": 100}]
   }}
   ```
   Note `denominations[0]` has no `count_coins` (uncapped) while top-level `cap` is set — `aa_validation.js` (lines 225-296) accepts this because it never sums `count_coins` and compares to `cap`.
2. Trigger the AA so it defines the asset; `writer.js` (lines 218-242) persists `assets.cap=1000` and `asset_denominations` row with `count_coins=NULL`.
3. From any wallet, attempt to compose an indivisible/fixed-denomination payment issuing or spending this asset (`pickIndivisibleCoinsForAmount` → `issueNextCoin` in `indivisible_asset.js`).
4. `row.count_coins` is `NULL` (falsy) while `objAsset.cap` is `1000` (truthy) → `!!row.count_coins !== !!objAsset.cap` is `true` → `throw Error("invalid asset cap and count_coins")` executes inside the DB callback, crashing the composing node process.
