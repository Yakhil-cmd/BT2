### Title
First-depositor share-rounding attack in the `uniswap_like_market_maker.oscript` liquidity-share AA - (File: `test/samples/uniswap_like_market_maker.oscript`)

### Summary
The `uniswap_like_market_maker.oscript` sample AA (shipped in the ocore repo as a documented AA template, parsed and tested by `test/ojson.test.js`) implements a vault-like liquidity pool that issues a share token (`$mm_asset`) proportional to a depositor's contribution relative to the pool's existing balances. Just like `GovernanceHYBR.deposit`, the "invest in MM" branch computes shares with a proportional formula and never checks that the resulting `$issue_amount` is non-zero, so an attacker who controls the pool's balance/shares ratio can cause a subsequent depositor to receive `0` shares while their funds are absorbed into the pool balance and become claimable by the existing shareholder(s).

### Finding Description
In the "invest in MM" case, once the pool is non-empty, new shares are minted as: [1](#0-0) 

```
$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance;
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
```

This is functionally identical to the vulnerable `shares = assets * totalShares / totalAssets` computation in `GovernanceHYBR.sol`. There is no check that `$issue_amount > 0` before the shares are paid out and `var['mm_asset_outstanding']` is incremented, mirroring the missing `require(shares > 0)` flagged in the external report.

The "initial deposit" branch that seeds the pool sets the first depositor's share amount directly to the current byte balance without any dust-share safeguard: [2](#0-1) 

An attacker (the pool's first investor) can then skew the ratio between `balance[base]`/`balance[$asset]` and `var['mm_asset_outstanding']` before a victim invests, e.g. by:
- Sending bytes/asset directly to the AA's address in amounts/shapes that do not satisfy any `if` condition in the `cases` list (none of the four cases match, e.g. amounts at or below the `1e5` threshold used in every case check), which are silently absorbed into the AA's balance without minting any `$mm_asset` shares, exactly as `receivePenaltyReward` was abused to inflate `totalAssets` in the report.
- Using the "exchange bytes to asset" / "exchange asset to bytes" swap cases (lines 34 and 46 region) which move balances between `$asset` and `base` without touching `var['mm_asset_outstanding']`.

Once `balance[base]` (and/or `balance[$asset]`) is inflated relative to `mm_asset_outstanding` while the attacker remains sole/majority shareholder, a genuine depositor's `$issue_amount` computed via `round($investor_share_of_prev_balance * var['mm_asset_outstanding'])` can round down to `0`, since `round()` truncates any fair share below `0.5` units. The victim's deposited bytes/asset are still accepted into the AA's balance (the payment message still executes and the state update `var['mm_asset_outstanding'] += $issue_amount` runs with `$issue_amount = 0`), so the victim receives no shares while their funds become divisible by the existing `$mm_asset` holder(s) via the "divest MM shares" case.

### Impact Explanation
Any unprivileged unit poster (AA trigger sender) who is first (or an early/majority) holder of `$mm_asset` can cause later depositors to lose their entire deposit to the existing shareholder(s), a direct fund-loss/theft condition equivalent to the original report's "AA fund loss" impact class. This is deployable by any AA author using this documented pattern, and reachable purely through ordinary AA trigger payments—no special privilege, node/hub compromise, or off-chain component is required.

### Likelihood Explanation
The attack requires only: (1) being an early investor in the pool (trivial, permissionless), and (2) sending additional payments to the AA that either don't match any `if` condition (silently absorbed) or using the exposed swap cases to shift the balance/shares ratio. Both are standard, unprivileged interactions available to any wallet holder, making this readily exploitable whenever this AA template (or any AA copying its share-issuance logic) is deployed with real value.

### Recommendation
- In the "invest in MM" case, `bounce()` if `$issue_amount == 0` (or more generally `$issue_amount < some minimum`), mirroring the report's `require(shares > 0)` recommendation.
- Consider seeding an unredeemable minimum share amount at pool creation (burn-to-zero-address pattern) to prevent the first-depositor ratio from ever becoming attacker-controlled with near-zero share counts.
- Ensure any direct/incidental payment to the AA that doesn't match a defined case is either bounced or properly attributed to shares, rather than silently increasing the balance available for redemption by existing holders.

### Proof of Concept
1. Attacker `Alice` sends the first "invest in MM" trigger with `1e5+1` bytes and `1` unit of `$asset`; pool is empty so `$issue_amount = balance[base]` and she becomes sole holder of `~1e5` `$mm_asset` shares, per: [3](#0-2) .
2. Alice sends further bytes to the AA in amounts that satisfy none of the `if` conditions in the `cases` array (e.g., below the `1e5` threshold used by every case check), which are accepted into `balance[base]` without any state/message being triggered, silently inflating the pool.
3. Victim `Bob` sends a legitimate "invest in MM" trigger with a modest amount of bytes/asset. Because `$bytes_balance` (denominator) has been inflated by Alice's donations while `var['mm_asset_outstanding']` stayed unchanged, `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])` computes to `0`.
4. Bob's payment message still executes (`$issue_amount = 0` mm_asset sent to Bob, i.e. nothing), and `var['mm_asset_outstanding'] += 0` leaves Alice as sole holder while `balance[base]`/`balance[$asset]` now include Bob's contribution.
5. Alice invokes the "divest MM shares" case with her full `$mm_asset` balance and redeems `round($investor_share * balance[$asset])` and `round($investor_share * balance[base])`, capturing Bob's deposited funds entirely: [4](#0-3) .
