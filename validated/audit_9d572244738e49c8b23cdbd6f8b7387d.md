### Title
Cross-repository/cross-organization commit-status forgery via unscoped `StatusHandler` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by selecting a per-organization secret based on an attacker-controlled field in the JSON body (`repository.owner.login`), then verifies the HMAC over the raw body against that organization's `webhook_secret` [1](#0-0) . This proves only "this payload was produced by someone who knows organization X's webhook secret" — it does not bind that organization to the specific repository/commit the payload subsequently mutates. `StatusHandler#process`, however, updates commit statuses by looking up `Commit.where(sha: params.sha)` globally, with no scoping to the repository/organization that was actually authenticated [2](#0-1) . Any operator who legitimately controls one Shipit-configured organization's webhook secret can therefore forge a `status` event that writes a commit status onto a `Commit` row belonging to an entirely different, unrelated organization's tracked stack, as long as they can produce (e.g. by forking a public repo) a commit with the same `sha`.

### Finding Description
`Shipit.github(organization: repository_owner)` picks the `GithubApp`/secret purely from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback) — a field taken straight from the unauthenticated JSON body [3](#0-2) . The signature check only proves the raw body was HMAC-signed with *that named organization's* secret [4](#0-3) . Nothing ties the verified organization identity to the repository whose data is subsequently written.

`Handler#stacks`/`#repository_name` do scope most handlers (`PushHandler`, `CheckSuiteHandler`) by `payload.dig('repository', 'full_name')` [5](#0-4) , but `StatusHandler` does not use `stacks`/`repository_name` at all — it matches solely on `sha` across the entire `commits` table and calls `commit.create_status_from_github!(params)` for every match [2](#0-1) .

This is the same class of trust-binding break described in the analog report: the value that is *verified* (the organization named in the payload, matched against a secret) is not the same value that is *acted upon* (the commit/stack actually mutated). Just as the `RecoverableWallet` example shows a gap between "offer accepted" and "cancellation mined," here there is a gap between "signature verified for org A" and "commit status written for a commit that may belong to org B's stack."

### Impact Explanation
An attacker who legitimately operates one org onboarded into a multi-tenant Shipit instance (and thus knows that org's own `webhook_secret`) can forge a `status` webhook, signed correctly for their own org, to mark an arbitrary existing commit (identified only by `sha`) as `success` in any other tracked stack, including ones belonging to other organizations. Because `Commit#deployable?`/CI-gating logic in the deploy/rollback flow relies on stored commit statuses, this can be used to flip CI gating and enable an unauthorized deploy on a stack the attacker has no legitimate access to — matching the "unauthorized deploy" / "cross-repository writes" Critical/High impact categories.

### Likelihood Explanation
This requires the attacker to already be an authorized, distinct-organization tenant in the same Shipit instance (i.e., they know their own org's webhook secret — no privileged Shipit account, `ApiClient` token, or GitHub App private key is needed) and to be able to produce a commit whose SHA collides with a target commit — trivially achievable for public repositories by forking, since GitHub commit SHAs are deterministic and shared identically across forks of the same commit. This makes the exploit reachable without social engineering, TLS interception, or host access, but it does depend on Shipit being configured to serve multiple organizations with independently-controlled webhook secrets and on the target commit existing in a public/forkable repo.

### Recommendation
Scope `StatusHandler#process` (and any other handler that does not currently use `Handler#stacks`) to only update commits belonging to stacks whose `Repository` matches the verified `repository_owner`/`full_name`, mirroring what `PushHandler` and `CheckSuiteHandler` already do. Additionally, `WebhooksController#verify_signature` should ideally re-validate that the organization used to select the secret matches the organization implied by every repository reference acted upon downstream, not just the outer field used for secret selection.

### Proof of Concept
1. Attacker-org is a legitimate, independently configured Shipit tenant; attacker knows `attacker-org`'s `webhook_secret`.
2. Attacker forks (or otherwise reproduces) a commit that is also tracked as part of `victim-org/victim-repo`'s Shipit stack, obtaining the identical commit `sha`.
3. Attacker crafts a `status` event payload:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci",
     "repository": {"full_name": "attacker-org/attacker-repo", "owner": {"login": "attacker-org"}}
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org-secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and the HMAC check passes, since it was signed with the attacker's own known secret [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, updating the victim commit's status without any check that it belongs to `attacker-org` [2](#0-1) .
7. The victim stack's commit now shows a forged `success` status, potentially satisfying CI-gating and enabling an unauthorized deploy trigger on a repository the attacker never had credentials for.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
