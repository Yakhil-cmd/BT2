### Title
Cross-repository CI status forgery via unscoped `StatusHandler` webhook processing - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `WebhooksController` authenticates an inbound webhook against the GitHub organization derived from the payload, but the `status` event handler then writes commit-status state using only the commit `sha`, with no binding back to the repository/organization that was actually verified. This breaks the equality: *organization that authenticated the request* == *stack/repository whose state is written*.

### Finding Description
`WebhooksController#verify_signature` derives the authenticating organization purely from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) and validates the HMAC signature using that organization's configured `webhook_secret` [1](#0-0) . This is legitimate for a multi-organization Shipit deployment (`Shipit.github(organization:)` supports per-org apps/secrets) [2](#0-1) .

Once the signature is accepted, `Shipit::Webhooks.for_event(event)` dispatches to the matching handler with the raw, attacker-influenced `params` [3](#0-2) . Most handlers (`PushHandler`, `CheckSuiteHandler`, all `pull_request/*` handlers) re-derive the target `Repository`/`Stack` from `params.repository.full_name`, so the org that authenticated and the repository written are the same field and stay consistent [4](#0-3) [5](#0-4) .

`StatusHandler`, however, does not require or use a `repository` field at all. It looks up commits **globally by `sha`** across the entire installation and writes a status to every matching commit, regardless of which stack/repository/organization owns it: [6](#0-5) 

Because git commit SHAs are content-addressed, it is common (forks, shared history, cherry-picks, vendored branches, mirrored repos) for the same SHA to exist in commits tracked by more than one Shipit stack, potentially belonging to a different GitHub organization/app-secret than the one that signed the incoming webhook. An attacker who legitimately controls (or compromises) any repository/organization onboarded into this Shipit instance — and can therefore trigger a validly-signed `status` webhook for their own org — can post an arbitrary `state`/`context`/`description` for any `sha` value they choose, and it will be applied to **every** `Commit` record in the database with that `sha`, including ones belonging to unrelated stacks under a different organization's authentication boundary.

### Impact Explanation
`Commit#deployable?` and the merge queue rely on CI status (`success?`, `blocking?`) computed from these `statuses` records [7](#0-6) , and a status change re-schedules merges/continuous delivery [8](#0-7) . An attacker controlling one onboarded org can forge a "success" status for a shared-SHA commit belonging to another org's stack, causing that stack to treat the commit as CI-passed and proceed with an **unauthorized deploy** — satisfying the "unauthorized deploy" High/Critical impact criterion, without needing write access to the victim repository, a Shipit session, or an API token. This matches the requested binding: an organization authenticated via its own webhook signature is used to write state for a repository it does not control.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit instance (documented, supported configuration) where the attacker legitimately controls at least one onboarded organization/repository, and (2) a commit SHA collision/sharing between the attacker's repo and the victim's tracked stack (realistic via forks, shared submodules/branches, or cherry-picked/mirrored commits, which are common in organizations that fork or mirror repositories). This is a moderate-likelihood, not purely theoretical, scenario given how commonly repositories share history across organizational boundaries in CI/CD setups.

### Recommendation
Scope `StatusHandler` (and any other handler that trusts payload-derived identifiers without an explicit repository check) to the repository indicated in the webhook payload, mirroring `PushHandler`/`CheckSuiteHandler`. Require and use `params.repository.full_name` to restrict `Commit.where(sha: ...)` to commits belonging to stacks under that specific repository, ensuring the authenticated organization and the repository/commit being mutated are always the same entity.

### Proof of Concept
1. Configure Shipit with multiple GitHub organizations, each with its own `webhook_secret` (as supported by `docs/setup.md`'s "Using Multiple Github Applications").
2. Attacker controls Org A (onboarded, with a valid webhook secret) and pushes/forks a commit whose SHA is identical to a commit already tracked in Org B's stack (e.g., by forking Org B's public repo, or via a shared commit due to common history).
3. Attacker triggers (or crafts, since they know Org A's secret) a `status` webhook event with `sha` = the shared SHA and `state` = `success`, correctly signed with Org A's webhook secret.
4. `WebhooksController#verify_signature` validates the signature against Org A (the payload's `repository.owner.login` matches Org A) and accepts the request.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matching the commit in **Org B's** stack too, and calls `commit.create_status_from_github!(params)`, marking that commit as `success` in Org B's stack — even though the request was never signed for Org B.
6. Org B's stack now considers the commit `deployable?` and may proceed with continuous delivery/merge based on the forged status. [9](#0-8)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
