### Title
Session Fixation on GitHub OAuth Login — GitHub Identity Bound to Session Without Session Rotation - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` binds a freshly authenticated GitHub identity to the *current* session (`session[:user_id]`, `session[:authenticated]`) without first calling `reset_session`. `logout` explicitly calls `reset_session`, but the login path does not, so the equality "session ID that existed pre-authentication" == "session ID that carries the authenticated `User`" is never broken across the trust boundary of login. This is the classic session-fixation pattern.

### Finding Description
The OAuth callback handler is: [1](#0-0) 

It writes `session[:user_id] = sign_in_github(auth)` and `session[:authenticated] = true` directly into whatever session cookie the browser presented, with no `reset_session` call. Contrast this with `logout`, which does call `reset_session`: [2](#0-1) 

`current_user` is resolved purely from `session[:user_id]`: [3](#0-2) 

Because Rails' cookie-based session store does not rotate the session ID on its own, if an attacker can get a victim to carry a session ID that was known/set before authentication (e.g. by planting a cookie via a subdomain, a response-splitting/cookie-injection vector, or a shared network without `Secure`/`HttpOnly` protections, or simply by having the victim click a login link that carries an attacker-supplied `_session_id` cookie set on a shared domain), and the victim then completes the GitHub OAuth login, the resulting `session[:user_id]` is written to the *same* session identifier the attacker already knows. The attacker can then use that identifier to act as the now-authenticated victim, effectively bypassing the GitHub-identity-to-session binding the login flow is meant to establish.

### Impact Explanation
This crosses the "GitHub identity versus the `User` bound to the session" boundary explicitly called out in scope: an attacker who never authenticated as the victim gains a session bound to the victim's `User` record, including `github_access_token`, team memberships, and deploy authorization (`current_user.authorized?`). This can lead to unauthorized deploys/rollbacks and exposure of the victim's session-scoped GitHub privileges — matching the "High: session fixation / forced OAuth completion" impact category.

### Likelihood Explanation
Exploitability depends on the attacker's ability to fix the victim's session ID before the OAuth callback runs (e.g. cookie tossing on a shared parent domain, or an attacker-supplied session cookie value accepted by the app before login). No `reset_session` call exists anywhere on the successful-login path to mitigate this, which is a definite root-cause gap; the attacker does not need any repository access, `ApiClient` token, `webhook_secret`, or the GitHub App private key — only the ability to plant/predict a session identifier and have the victim click through OAuth once.

### Recommendation
Call `reset_session` (or otherwise rotate the session ID) in `GithubAuthenticationController#callback` immediately before or after setting `session[:user_id]` / `session[:authenticated]`, mirroring what `logout` already does, so that a pre-authentication session identifier can never carry post-authentication privileges.

### Proof of Concept
1. Attacker visits the Shipit host and obtains/predicts a session ID `S` from an unauthenticated response (e.g. via cookie injection on a shared parent domain or a session ID that is never invalidated).
2. Attacker sets the victim's browser cookie to session `S` (fixation), then lures the victim to the Shipit login URL.
3. Victim completes the GitHub OAuth flow; `GithubAuthenticationController#callback` executes `session[:user_id] = sign_in_github(auth)` inside session `S` — no `reset_session` occurs.
4. Attacker reuses session `S` and is now treated by `Authentication#current_user` as the victim's `User`, inheriting their authorization and ability to trigger deploys/rollbacks.

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```
