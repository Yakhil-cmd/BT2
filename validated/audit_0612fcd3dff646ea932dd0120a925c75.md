### Title
Webhook signature is verified against the org named in `repository.owner.login`, but the handler acts on a completely unrelated `repository.full_name` from the same unverified body - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which organization's* HMAC secret to check against solely from a payload field, then the actual `Shipit::Webhooks::Handlers::Handler` used to process the event resolves the *target repository/stack* from a second, independent payload field. Because the whole raw request body is what gets HMAC'd, an attacker who legitimately knows the webhook secret for **any one** organization configured in the multi-tenant Shipit instance can craft a body whose `repository.owner.login` matches that known org (so the signature check passes) while `repository.full_name` names a stack belonging to a **different, unrelated organization/repository**. This breaks the "organization authenticated" vs "repository written" binding.

### Finding Description
`verify_signature` resolves the GitHub App/secret using `repository_owner`, which is read straight from the untrusted JSON body before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` HMACs the **entire raw body** with the secret configured for that one organization: [3](#0-2) 

Once the request passes this check, `WebhooksController#create` dispatches the full parsed body to every registered handler for the event: [4](#0-3) 

Handlers, however, do not re-check `repository_owner`; they resolve the affected stacks purely from `repository.full_name`, a sibling field in the same body: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used to select the HMAC key) and `repository.full_name` (used to select the target stack) are two independent, attacker-controlled fields of the same signed byte string, an attacker who legitimately controls a Shipit-integrated organization (i.e., knows *its* `webhook_secret`, a normal administrative artifact for onboarding a repo — not `Shipit.api_clients_secret`, not a session, not a GitHub App private key) can:
1. Build a JSON body where `repository.owner.login`/`organization.login` = "attacker-org" (an org they legitimately administer and know the secret for), and `repository.full_name` = "victim-org/victim-repo" (any other repo tracked by the same Shipit instance).
2. Compute a valid `X-Hub-Signature` over that exact body using attacker-org's secret.
3. POST directly to `/github/webhooks` (a public endpoint, not gated by a Shipit session or `ApiClient` token).

`verify_signature` succeeds because it only checks the signature against attacker-org's own secret, and never confirms that `repository.owner.login == repository.full_name.split('/').first`, nor that the resolved stack's organization matches the org whose secret authenticated the request.

### Impact Explanation
For the `push` event, `PushHandler#process` queues a `GithubSyncJob` for every non-archived stack of the victim repository on the matching branch, passing an attacker-chosen `expected_head_sha`: [7](#0-6) 

`GithubSyncJob#perform` then fetches new commits from GitHub (using the victim stack's own `github_api`, i.e., Shipit's legitimate credentials for that org) and re-syncs the stack's commit list/cache based on this forged trigger: [8](#0-7) 

Since `Stack#sync_github` / continuous-deployment logic reacts to newly-synced commits, this lets an unrelated org's collaborator force a resync (and, if continuous deployment is enabled, a deploy trigger) on a victim stack they have no relationship to, purely by knowing a different org's webhook secret. Other handlers keyed the same way (`pull_request` label/close/reopen handlers) can similarly archive/unarchive or mutate review stacks belonging to a victim repository: [9](#0-8) 

This crosses the "organization authenticated vs. repository written" trust boundary and can result in an unauthorized deploy/state-mutation on a repository the attacker's org has no legitimate relationship to.

### Likelihood Explanation
Requires the attacker to be a legitimate, low-privileged administrator of **any one** organization already onboarded to the shared Shipit instance (a realistic scenario for any multi-tenant deployment covering several orgs/teams), plus knowledge of that repository's own `full_name` (public information). No session, `ApiClient` token, or the victim org's secret is required — only the attacker's own org's secret, which they are entitled to know by design.

### Recommendation
After signature verification succeeds for a given organization, cross-check that every `repository.full_name` / `organization.login` referenced later in the same payload actually belongs to the organization whose secret was used to authenticate the request (e.g., compare `repository.owner.login` against the first path segment of `repository.full_name`, and reject/log mismatches before dispatching to handlers).

### Proof of Concept
1. Attacker registers/administers `attacker-org` in the shared Shipit instance and knows its `webhook_secret` (e.g. `S_ATTACKER`).
2. Attacker builds a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(S_ATTACKER, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates the signature against `S_ATTACKER` — it matches, so the request passes.
5. `PushHandler#process` resolves stacks via `repository.full_name` = `"victim-org/victim-repo"` and queues `GithubSyncJob` for that stack with the attacker-supplied `expected_head_sha`, despite the signature never having been checked against `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
