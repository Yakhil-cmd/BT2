### Title
Webhook Signature Verified Against `repository.owner.login` While Handlers Act On The Unrelated `repository.full_name` Field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` pulled from the still-unverified JSON body, then, once "verified," hands the *entire* raw payload to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Individual handlers (e.g. `PushHandler`) never re-check that `repository.owner.login` matches the repository they actually act on — they instead resolve the target repository/stack from the independent `repository.full_name` field via `Handler#repository_name` and `Repository.from_github_repo_name`. Because the signature only proves "this body was signed with organization X's webhook secret," not "the repository referenced inside is owned by organization X," an operator of one configured GitHub App/org can forge a validly-signed webhook whose `repository.full_name` points at a completely different organization's repository/stack.

### Finding Description
`verify_signature` computes the org used to look up the verification secret before the signature is actually checked: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')`, and the signature is validated with `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` using that organization's own `webhook_secret`: [3](#0-2) 

Once verification passes, the full, attacker-controlled JSON body is dispatched unchanged to handlers: [4](#0-3) 

`Handler#stacks`/`repository_name`, however, resolve the target repository using the **separate** `repository.full_name` field, not `repository.owner.login`: [5](#0-4) 

`PushHandler#process` then loads stacks for that repository and asks them to sync to an attacker-supplied `after` SHA: [6](#0-5) 

Since Shipit is designed to be configured with multiple independent GitHub Apps/organizations, each with its own `webhook_secret` (as documented in the multi-org secrets template), the operator of *any one* onboarded organization's GitHub App knows that organization's `webhook_secret` and can compute a valid `X-Hub-Signature` for a payload whose `repository.owner.login` is their own org (so verification passes) while `repository.full_name` names a repository belonging to an entirely different, unrelated organization: [7](#0-6) 

This breaks the intended binding "organization that authenticated == repository that is written," matching the bug-class hint in the external report (a validated field that doesn't match the field actually acted upon).

### Impact Explanation
An attacker who legitimately controls one organization's GitHub App integration in a shared/multi-tenant Shipit deployment can forge cross-organization webhook events (`push`, `status`, `check_suite`, `pull_request`, etc.) targeting any other onboarded repository's stacks, without ever needing that victim organization's webhook secret or repository write access. For `push` events this can force `Stack#sync_github` to run against an attacker-chosen `expected_head_sha` for a repository the attacker does not control, and other handlers (status/check_suite/pull_request) can similarly be spoofed for arbitrary victim repositories, since none of them re-validate `repository.owner.login` against the org whose secret verified the signature. This is a cross-repository/cross-organization write triggered on an unauthenticated basis relative to the victim repository.

### Likelihood Explanation
Exploitability requires only that the attacker be an authorized administrator of *one* GitHub App/organization onboarded onto the shared Shipit instance (not the victim's), which is a standard, low-privilege configuration in multi-tenant Shipit deployments as documented in the setup guide and multi-org secrets example. No access to the victim's secrets, GitHub tokens, or Shipit sessions is required, and the crafted request is a plain HTTP POST to the public `/webhooks` endpoint.

### Recommendation
In `Handler#repository_name` (or a shared pre-processing step in `WebhooksController`), require that the resolved `repository.full_name`'s owner match the same `repository.owner.login` (or `organization.login`) value that was used to select the verifying `webhook_secret`, rejecting the payload otherwise. Alternatively, resolve the target `Repository` first and verify the signature using that repository's own organization's secret, ensuring the two are always the same value end-to-end.

### Proof of Concept
1. Shipit is configured for two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (as in `config/secrets.development.shopify.yml`), both with stacks tracked by Shipit.
2. Attacker, an admin of `attacker-org`'s GitHub App, knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker signs the raw JSON body with `attacker-org`'s `webhook_secret` using HMAC-SHA1 and sets `X-Hub-Signature` and `X-Github-Event: push`, then POSTs to `/webhooks`.
5. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s GitHub App, and verification succeeds because the attacker signed with the correct secret for that org. [1](#0-0) 
6. `create` dispatches the raw payload to `PushHandler`, which resolves the repository via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, unrelated to the verifying org, and triggers `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for all matching `victim-org/victim-repo` stacks. [5](#0-4) [6](#0-5) 

Note: I was unable to inspect `Stack#sync_github` / `GithubSyncJob` implementation in full within the indexed context, so I cannot confirm what downstream validation (if any, e.g. re-fetching the commit via the victim's own GitHub API credentials) might partially mitigate the ultimate consequence of the forged SHA; a Devin session with full repository access would be needed to trace that job's exact behavior.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
