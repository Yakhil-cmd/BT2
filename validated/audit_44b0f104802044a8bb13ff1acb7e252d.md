### Title
NAV-priced collateral has no market-price cross-check — the dual-leg deviation gate compares two readings of the same fundamental value - (File: contracts/price-aggregator/src/engine.rs)

### Summary
The external report's bug class — a yield-bearing/exchange-rate collateral priced from a slow, self-referential rate oracle with no on-chain deviation check against a market price — maps directly onto XOXNO Lending's `Scaled`/`Feed` oracle composition for fundamental assets such as SolvBTC/xSolvBTC. Both configured legs derive from the same NAV publisher, so the tolerance gate in `blend()` cannot detect the NAV/market divergence that the Usual report describes, and the sanity band ($20k–$300k for a BTC-denominated asset) is far too wide to catch a real impairment.

### Finding Description
The price aggregator blends up to two source legs and flags `deviation` only when the two leg prices fall outside `oracle.tolerance` (`within_tolerance_band`), and flags `stale` only per-leg or when two `Market` legs exceed `MAX_LEG_AGE_SPREAD_SECONDS` — the age-spread bound is explicitly disabled when either leg is `FeedNature::Fundamental`. [1](#0-0) 

For SolvBTC, mainnet configures leg 1 as `Scaled { factor: SolvBTC_FUNDAMENTAL × Ref(BTC) }` and leg 2 as `SolvBTC_FUNDAMENTAL/USD`, both `Fundamental` RedStone feeds on the same contract with `independence: AllowShared` on that single publisher. [2](#0-1)  Leg 1 is algebraically `NAV_ratio × BTC_price` and leg 2 is `NAV_in_USD` — both are functions of the same underlying NAV observation. Any common-mode error or lag in that NAV moves both legs together, so the deviation gate is structurally incapable of firing for exactly the failure mode the Usual report describes (exchange rate/NAV lags the market). `read_scaled` only bounds the factor to `[min_factor_wad, max_factor_wad]`, a static configured range, and resolves the quote recursively — it never compares the result to a traded price. [3](#0-2) 

Staleness does not help either: the factor leg allows `max_stale_seconds = 93600` (26h), and since neither leg is `Market`, the `MAX_LEG_AGE_SPREAD_SECONDS` cross-leg freshness check in `blend()` does not apply (`spread_bounded` requires both legs `Market`). [4](#0-3)  The remaining gate, `failure()`'s sanity check, enforces only `[min_sanity_price_wad, max_sanity_price_wad]` = $20,000–$300,000 for SolvBTC — a crash of the token to a fraction of BTC parity stays inside the band. [5](#0-4)  This mirrors Usual's `TokenOracle` returning a stale `stEthPerToken()` with no threshold check reachable by `DaoCollateral`.

### Impact Explanation
If SolvBTC/xSolvBTC (or any comparably configured yield/NAV asset, e.g. USTRY/CETES-style listings whose second leg is the same publisher's fundamental feed) suffers an impairment — issuer insolvency, underlying-asset depeg, forced redemption at a discount — secondary markets reprice immediately while both NAV legs continue reporting the pre-event value for up to ~26 hours, all gates passing. An unprivileged attacker buys the discounted token on Aquarius/Soroswap and calls controller `supply` to post it as collateral at the stale NAV valuation, then calls `borrow` to draw other hub assets (XLM, USDC, BTC) far above the collateral's real value. The resulting position is permanently undercollateralized; `clean_bad_debt`/`recapitalize` socialize the loss to suppliers. This is protocol insolvency / theft of user funds, reachable entirely through unprivileged entrypoints (`supply`, `borrow`, and own DEX trades for acquisition).

### Likelihood Explanation
Requires a genuine NAV-impairment or liquidity event on a NAV-priced collateral — the same precondition as the Usual finding (mass slashing / issuer event). It does not require oracle dishonesty: the feeds report honestly, just slowly, exactly like Lido's 24h accounting oracle. The attack window is bounded by `max_stale_seconds` (26h for the factor leg, 16h for the USD leg), which comfortably exceeds the time needed to buy the discounted token and execute `supply`+`borrow`. Not independently verified: whether SolvBTC/xSolvBTC are enabled as collateral (nonzero LTV) on a mainnet spoke — the finding holds in full only where such a listing exists; the ops configs reference spoke listings for these assets but I could not confirm the collateral flag/LTV within available iterations.

### Recommendation
For fundamental/NAV-priced collateral, require one leg to be a `Market`-nature source (e.g., a DEX-derived or market-quoted price) so the tolerance gate provides a true NAV-vs-market deviation check, and so the `MAX_LEG_AGE_SPREAD_SECONDS` cross-leg freshness bound applies. Alternatively or additionally, tighten per-asset sanity bands so they track expected value rather than a fixed absolute range, and bound the Scaled factor's deviation relative to the quote leg's implied market value. Where no market leg can exist (deeply illiquid NAV tokens), compensate with materially lower LTV/liquidation thresholds and tighter borrow caps on the spoke listing, since the oracle provides no black-swan protection.

### Proof of Concept
1. Wait for (or observe) an impairment of SolvBTC's backing: market price drops, e.g., to 0.5×BTC, while both `SolvBTC_FUNDAMENTAL` and `SolvBTC_FUNDAMENTAL/USD` feeds still report the pre-event NAV (within their 57600/93600s staleness budgets).
2. Attacker buys discounted SolvBTC on Aquarius/Soroswap at the crashed market price.
3. Attacker calls controller `supply(SolvBTC, amount)` — the aggregator resolves `factor(≈1.0)×BTC ≈ NAV_USD` on leg 1 and the same stale `NAV_USD` on leg 2: `within_tolerance_band` passes, `stale` is false, and the blended price is inside the $20k–$300k sanity band, so `failure()` returns `None` and the price is accepted.
4. Attacker calls `borrow(USDC_or_XLM, max)` against the inflated collateral value, then walks away; the position's real collateral is worth a fraction of the debt. Bad debt is later socialized via `clean_bad_debt`/`recapitalize` at suppliers' expense.

```rust
fn read_scaled(
    session: &mut Session,
    scaled: &ScaledSource,
    depth: u32,
) -> Result<Option<(OracleObservation, bool)>, OracleError> {
    let env = session.env().clone();
    let Some((factor, factor_stale)) = read_feed(session, &scaled.factor) else {
        return Ok(None);
    };

    if factor.price_wad < scaled.min_factor_wad || factor.price_wad > scaled.max_factor_wad {
        return Err(OracleError::FactorOutOfBounds);
    }

    let quote = resolve_nested(session, &scaled.quote, depth + 1)?;

    let Some(price_wad) = Wad::from(factor.price_wad).try_mul(&env, Wad::from(quote.price_wad))
    else {
        return Err(OracleError::InvalidPrice);
    };

    Ok(Some((
        OracleObservation {
            price_wad: price_wad.raw(),
            timestamp: factor.timestamp.min(quote.timestamp),
        },
        factor_stale,
    )))
```
