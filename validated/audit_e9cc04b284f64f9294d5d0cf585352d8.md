This confirms the root cause. `get-assets` at [1](#0-0)  builds the position's full enabled-asset list (all enabled collateral + debt for the borrower, `mask-to-list-collateral` over `safe-mask`) and calls `price-multi-resolve` with `(unwrap-panic ...)`, which panics/aborts the entire transaction if resolution of **any single asset** in the list fails.

`price-multi-resolve`/`iter-price-multi` propagate a hard failure for the whole call if one `price-resolve` fails: [2](#0-1) . `price-resolve` itself uses `try!`/`asserts!` against `ERR-ORACLE-PYTH`, `ERR-ORACLE-DIA`, `ERR-PRICE-CONFIDENCE-LOW`, and `ERR-ORACLE-INVARIANT` (staleness/legality check) rather than degrading gracefully: [3](#0-2) .

`liquidate()` calls `get-assets mask` to compute `get-notional-evaluation` for the **borrower's own enabled-asset mask** (all enabled collateral and debt on the position, not just the collateral/debt pair the liquidator is targeting) before it can compute LTV and proceed: [4](#0-3) . Error code documentation confirms `ERR-ORACLE-PYTH` (u400012), `ERR-ORACLE-DIA` (u400013), `ERR-ORACLE-INVARIANT` (u400014), and `ERR-ORACLE-MULTI` (u400015) exist as distinct hard-revert paths rather than a "return 0" fallback: [5](#0-4) .

### Title
Liquidation of an insolvent position is permanently blocked if any single one of the borrower's enabled collateral/debt assets fails price resolution, causing bad debt to accrue and socializing losses to vault suppliers - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`liquidate()` requires a full notional valuation of **every** enabled collateral and debt asset on the target borrower's position mask, computed via `get-assets` → `price-multi-resolve` → `price-resolve`. Any single asset whose oracle call reverts, whose confidence check fails, or whose price/timestamp fails the staleness/legality assertion causes the entire chain to abort (`unwrap-panic`, `try!`, `asserts!`), which reverts the whole `liquidate()` transaction — even though the failing asset may have nothing to do with the specific `collateral-ft`/`debt-ft` pair the liquidator is trying to act on.

### Finding Description
`get-assets` (mainnet/contracts/market/v0-4-market.clar:482-492) collects all assets enabled under the position's `safe-mask` (which can include up to 64 assets) and calls `price-multi-resolve` wrapped in `unwrap-panic`. `price-multi-resolve` (lines 397-403) folds over every asset's oracle config via `iter-price-multi`, and if `price-resolve` returns an error for any single asset, `iter-price-multi` marks the whole computation invalid, and `price-multi-resolve` asserts failure with `ERR-ORACLE-MULTI`. `price-resolve` (lines 373-395) itself hard-fails on: a reverting Pyth/DIA call (`ERR-ORACLE-PYTH`/`ERR-ORACLE-DIA`), a confidence check failure (`ERR-PRICE-CONFIDENCE-LOW`), or a stale/illegal price (`ERR-ORACLE-INVARIANT`).

`liquidate()` (lines 1382-1436) calls `get-liquidation-position` → `get-assets mask` to compute `total-collateral-usd`/`total-debt-usd` for the borrower **before** any of the liquidator-supplied pair-specific logic runs. Because this evaluation spans the borrower's entire enabled-asset set rather than just the pair being liquidated, a single stale/failing feed for an unrelated enabled asset on that borrower's position (e.g., a low-liquidity asset whose Pyth/DIA feed update lags past its configured `max-staleness`, or fails the confidence check) makes the borrower's whole position permanently unevaluable to any liquidator — mirroring exactly the "getUnderlyingPrice() should return 0 instead of reverting" class from the external report, except here the effect is on `liquidate()` (an action taken by one unprivileged principal, the liquidator, on another unprivileged principal's, the borrower's, position), and the position remains unliquidatable for as long as that one feed remains broken.

### Impact Explanation
While that asset's feed remains broken/stale/low-confidence, the position cannot be evaluated or liquidated by anyone, even though it is genuinely insolvent. Debt continues to accrue interest against collateral that is not being seized, and once the position is finally liquidatable (feed recovers, if ever), the accumulated shortfall becomes bad debt that the protocol's bad-debt-socialization mechanism spreads across all suppliers of that vault — an unprivileged third party distinct from both the borrower and the liquidator. This is a temporary (and potentially permanent, if the feed never recovers) freezing of the ability to realize collateral value and a path to protocol insolvency for the affected vault, matching the "temporary freezing of funds" / "protocol insolvency" impact classes.

### Likelihood Explanation
This does not require any attacker action to manipulate price data — it can be triggered by ordinary conditions already anticipated by the protocol's own staleness/confidence checks (a legitimate feed simply lagging past `max-staleness`, or momentary low liquidity causing wide Pyth confidence intervals) on **any one** of the (up to 64) enabled assets on a borrower's position, independent of the asset pair a liquidator is trying to act on. Multi-collateral positions with several enabled assets increase the probability that at least one feed is stale/low-confidence at any given time, making this a realistic and recurring operational condition rather than a rare edge case.

### Recommendation
Decouple the liquidation health/valuation check from assets irrelevant to the liquidator's targeted pair, or make `price-resolve`/`price-multi-resolve` fail soft (e.g., return `0`/skip and exclude that asset's value from the notional totals with an explicit flag) analogous to the Compound-style "return 0 on error" pattern recommended in the referenced report, instead of using `unwrap-panic`/hard `asserts!` that abort the entire `liquidate()` call over one unrelated feed.

### Proof of Concept
1. Borrower opens a position enabling collateral assets A (e.g., `zUSDC`) and B (a lower-liquidity asset with tight `max-staleness`), and borrows against them such that LTV exceeds `LTV-LIQ-PARTIAL`.
2. Asset B's Pyth feed is not updated for longer than its configured `max-staleness`, or its confidence ratio momentarily exceeds `max-confidence-ratio` (ordinary market conditions, no attacker action required).
3. A liquidator calls `liquidate(borrower, collateral-ft=A, debt-ft=..., ...)` intending to liquidate only asset A's collateral against the debt.
4. `get-liquidation-position` → `get-assets` resolves prices for **all** enabled assets on the borrower's mask, including B; `price-resolve` for B fails staleness/confidence checks, `price-multi-resolve` asserts `ERR-ORACLE-MULTI`, and the entire `liquidate()` call reverts.
5. The borrower's position, despite being liquidatable via asset A alone, cannot be liquidated at all until asset B's feed recovers; meanwhile debt keeps accruing, and eventual bad debt is socialized to vault suppliers. [1](#0-0) [4](#0-3)

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))

        (ident (get ident data))
        (key { type: type, ident: ident })

        (timestamp (get timestamp resolution))
